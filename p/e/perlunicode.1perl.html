NOMBRE

perlunicode - Soporte Unicode en Perl

DESCRIPCIÓN

Si aún no lo ha hecho, antes de leer este documento, debe familiarizarse con perlunitut y perluniintro.

Unicode tiene como objetivo **UNI**ficar las codifi-**CODE**-aciones de todos los conjuntos de caracteres del mundo en un único Estándar. Para bastantes de los diversos estándares de codificación que existían cuando se creó Unicode por primera vez, la conversión desde cada uno a Unicode significaba esencialmente sumar una constante a cada punto de código del estándar original, y la conversión inversa implicaba simplemente restar esa misma constante. Para ASCII e ISO-8859-1, la constante es 0. Para ISO-8859-5 (cirílico), es 864; para hebreo (ISO-8859-8), es 1488; tailandés (ISO-8859-11), 3424; y así sucesivamente. Esto facilitó las conversiones y promovió la adopción de Unicode.

Y funcionó; hoy en día, esos estándares heredados rara vez se usan. Casi todo el mundo usa Unicode.

Unicode es un estándar completo. Especifica muchas cosas fuera del alcance de Perl, como la forma de mostrar secuencias de caracteres. Para una discusión completa de todos los aspectos de Unicode, consulte https://www.unicode.org.

Además, el uso de Unicode puede presentar problemas de seguridad que no son obvios, consulte "Implicaciones de seguridad de Unicode" a continuación.

Lo más seguro es "use feature 'unicode_strings'"
Para mantener la compatibilidad retroactiva, Perl no activa el soporte interno completo de Unicode a menos que se especifique el pragmatismo "use feature 'unicode_strings'". (Esto se selecciona automáticamente si "use v5.12" o superior.) No hacer esto puede generar sorpresas inesperadas. Consulte "El "Bug de Unicode"" a continuación.

Este pragmatismo no afecta a la E/S. Tampoco cambia la representación interna de las cadenas, solo su interpretación. Todavía hay varios lugares donde Unicode no es totalmente compatible, como en los nombres de archivo.

Semántica de Bytes y Caracteres

Antes de Unicode, la mayoría de las codificaciones usaban 8 bits (un solo byte) para codificar cada carácter. Por lo tanto, un carácter era un byte, y un byte era un carácter, y solo podía haber 256 o menos caracteres posibles. La sección "Semántica de Bytes" en el título de esta sección se refiere a este comportamiento. No había necesidad de distinguir entre "Byte" y "Carácter".

Entonces llegó Unicode, que tiene espacio para más de un millón de caracteres (y Perl permite incluso más). Esto significa que un carácter puede requerir más de un solo byte para representarlo, por lo que los dos términos ya no son equivalentes. Lo que importa son los caracteres como entidades completas, y no suelen ser los bytes que los componen. A eso se refiere el término "Semántica de Caracteres" en el título de esta sección.

Perl tuvo que cambiar internamente para desacoplar los "bytes" de los "caracteres". Es importante que usted también cambie sus ideas, si aún no lo ha hecho, para que "byte" y "carácter" ya no signifiquen lo mismo en su mente.

El bloque de construcción básico de las cadenas de Perl siempre ha sido un "carácter". Los cambios básicamente se reducen a que la implementación ya no piensa que un carácter es siempre solo un solo byte.

Reglas ASCII frente a Reglas Unicode

Antes de Unicode, cuando un carácter era un byte era un carácter, Perl solo conocía los 128 caracteres definidos por ASCII, puntos de código 0 a 127 (excepto bajo "use locale"). Eso dejaba los puntos de código 128 a 255 sin asignar y disponibles para cualquier uso que un programa pudiera desear. La única semántica que tienen es sus números ordinales, y que son miembros de ninguna de las clases de caracteres no negativos. Ninguno se considera que coincida con "\w", por ejemplo, pero todos coinciden con "\W".

Unicode, por supuesto, asigna a cada uno de esos puntos de código un significado particular (junto con los superiores a 255). Para preservar la compatibilidad hacia atrás, Perl solo utiliza los significados de Unicode cuando hay alguna indicación de que se pretende Unicode; de lo contrario, los puntos de código no ASCII siguen tratándose como si no estuvieran asignados.

Aquí están las formas en que Perl sabe que una cadena debe tratarse como Unicode:

  • Dentro del alcance de "use utf8"

    Si todo el programa es Unicode (indicado por el uso de formato de transformación Unicode de 8 bits o UTF-8), entonces todas las cadenas literales dentro de él deben ser Unicode.

  • Dentro del alcance de "use feature 'unicode_strings'"

    Este pragmatismo se creó para que puedas indicar explícitamente a Perl que las operaciones ejecutadas dentro de su alcance deben usar reglas Unicode. Más operaciones se ven afectadas con perls más nuevos. Ver "El "Bug de Unicode"".

  • Dentro del alcance de "use v5.12" o superior

    Esto activa implícitamente "use feature 'unicode_strings'".

  • Dentro del alcance de "use locale 'not_characters'", o "use locale" y la configuración regional actual es una configuración regional UTF-8.

    La primera se define para implicar el manejo de Unicode; y la segunda indica una configuración regional Unicode, por lo tanto, una interpretación Unicode de todas las cadenas dentro de ella.

  • Cuando la cadena contiene un punto de código exclusivo de Unicode

    Perl nunca ha aceptado puntos de código superiores a 255 sin que sean Unicode, por lo que su uso implica Unicode para toda la cadena.

  • Cuando la cadena contiene un punto de código Unicode con nombre "\N{...}"

    La construcción "\N{...}" se refiere explícitamente a un punto de código Unicode, incluso si es uno que también está en ASCII. Por lo tanto, la cadena que lo contiene debe ser Unicode.

  • Cuando la cadena proviene de una fuente externa marcada como Unicode

    La opción de línea de comandos "-C" puede especificar que ciertas entradas al programa son Unicode, y los valores de esta pueden ser leídos por su código Perl, ver "${^UNICODE}" en perlvar.

  • Cuando la cadena ha sido mejorada a UTF-8

    La función utf8::utf8_upgrade() se puede usar explícitamente para que (a menos que se llame a una posterior utf8::utf8_downgrade()) una cadena se trate permanentemente como Unicode.

  • Existen métodos adicionales para patrones de expresiones regulares

    Un patrón que se compila con los modificadores "/u" o "/a" se trata como Unicode (aunque hay algunas restricciones con "/a"). Bajo los modificadores "/d" y "/l", hay varias otras indicaciones para Unicode; ver "Modificadores de conjunto de caracteres" en perlre.

Tenga en cuenta que todo lo anterior se anula dentro del alcance de "use bytes"; pero solo debe usar este pragmatismo para depurar.

Tenga en cuenta también que algunas interacciones con el sistema operativo de la plataforma nunca utilizan reglas Unicode.

Cuando las reglas Unicode están en vigor:

  • Los operadores de traducción de mayúsculas y minúsculas utilizan las tablas de traducción de mayúsculas y minúsculas de Unicode.

    Tenga en cuenta que uc(), o "\U" en cadenas interpoladas, traduce a mayúsculas, mientras que "ucfirst", o "\u" en cadenas interpoladas, traduce a mayúsculas iniciales en idiomas que marcan la distinción (que es equivalente a mayúsculas en idiomas sin distinción).

    Hay un módulo CPAN, "Unicode::Casing", que le permite definir sus propios mapeos para usarlos en lc(), lcfirst(), uc(), ucfirst(), y "fc" (o sus versiones incrustadas en cadenas de doble comilla, como "\U"). (Antes de Perl 5.16, esta funcionalidad se proporcionaba parcialmente en el núcleo de Perl, pero sufría de una serie de inconvenientes insuperables, por lo que se escribió el módulo CPAN en su lugar.)

  • Las clases de caracteres en expresiones regulares coinciden basándose en las propiedades de caracteres especificadas en la base de datos de propiedades de Unicode.

    "\w" se puede usar para que coincida con un ideograma japonés, por ejemplo; y "[[:digit:]]" un número bengalí.

  • Las propiedades, scripts y rangos de bloques de Unicode con nombre se pueden usar (como clases de caracteres entre corchetes) utilizando la construcción "\p{}" "coincide con la propiedad" y la negación "\P{}", "no coincide con la propiedad".

    Ver "Propiedades de Caracteres Unicode" para más detalles.

    Puede definir sus propias propiedades de caracteres y usarlas en la expresión regular con la construcción "\p{}" o "\P{}". Ver "Propiedades de Caracteres Definidas por el Usuario" para más detalles.

Clusters de Graphemación Extendidos (Caracteres Lógicos)

Considere un carácter, digamos "H". Podría aparecer con varias marcas alrededor, como un acento agudo, o un circunflejo, o varios ganchos, círculos, flechas, *etc.*, arriba, abajo, a un lado u otro, *etc*. Hay muchas posibilidades entre los idiomas del mundo. El número de combinaciones es astronómico, y si hubiera un carácter para cada combinación, pronto agotaría los más de un millón de caracteres posibles de Unicode. Así que Unicode adoptó un enfoque diferente: hay un carácter para la "H" base, y un carácter para cada una de las marcas posibles, y estos se pueden combinar de diversas maneras para obtener un carácter lógico final. Así que un carácter lógico —lo que parece ser un solo carácter— puede ser una secuencia de más de un carácter individual. El estándar Unicode llama a estos "clusters de graphemación extendidos" (que es una versión mejorada del "cluster de graphemación" que ya no se usa mucho); Perl proporciona la construcción de expresiones regulares "\X" para que coincida con tales secuencias en su totalidad.

Pero la intención de Unicode es unificar los estándares y prácticas del conjunto de caracteres existentes, y varios estándares preexistentes tienen caracteres únicos que significan lo mismo que algunas de estas combinaciones, como ISO-8859-1, que tiene bastantes de ellas. Por ejemplo, "LATIN CAPITAL LETTER E WITH ACUTE" ya estaba en este estándar cuando apareció Unicode. Unicode, por lo tanto, lo añadió a su repertorio como ese único carácter. Pero este carácter se considera por Unicode equivalente a la secuencia que consiste en el carácter "LATIN CAPITAL LETTER E" seguido del carácter "COMBINING ACUTE ACCENT".

"LATIN CAPITAL LETTER E WITH ACUTE" se llama un carácter "precompuesto", y su equivalencia con la secuencia "E" y "ACENTO COMBINADO" se llama equivalencia canónica. Se dice que todos los caracteres precompuestos tienen una descomposición (en la secuencia equivalente), y el tipo de descomposición también se llama canónica. Una cadena puede consistir en la mayor medida posible en caracteres precompuestos, o puede consistir en caracteres completamente descompuestos. Unicode llama a estos respectivamente, "Forma de Normalización Compuesta" (NFC) y "Forma de Normalización Descompuesta". El módulo "Unicode::Normalize" contiene funciones que convierten entre los dos. Una cadena también puede tener caracteres compuestos y descompuestos; este módulo se puede usar para hacer que todo sea una cosa o la otra.

Puede que se le presenten cadenas en cualquiera de estas formas equivalentes. Actualmente no hay nada en Perl 5 que ignore las diferencias. Así que tendrá que manejarlo especialmente. El consejo habitual es convertir sus entradas a "NFD" antes de procesarlas más.

Para obtener información más detallada, consulte http://unicode.org/reports/tr15/.

Propiedades de Caracteres Unicode

(La única vez que Perl considera una secuencia de puntos de código individuales como un solo carácter lógico es en la construcción "\X", mencionada anteriormente. Por lo tanto, "carácter" en esta discusión significa un solo punto de código Unicode.)

Casi todas las propiedades de caracteres de Unicode son accesibles a través de expresiones regulares utilizando la construcción "\p{}" "coincide con la propiedad" y la construcción "\P{}" "no coincide con la propiedad" para su negación.

Por ejemplo, s"\p{Uppercase}" coincide con cualquier carácter individual con la propiedad Unicode "Uppercase", mientras que "\p{L}" coincide con cualquier carácter con una "General_Category" de "L" (letra) propiedad (ver "General_Category" abajo). Los corchetes no son necesarios para nombres de propiedad de una sola letra, por lo que "\p{L}" es equivalente a "\pL".

Más formalmente, "\p{Uppercase}" coincide con cualquier carácter individual cuyo valor de propiedad Unicode "Uppercase" sea "True", y "\P{Uppercase}" coincide con cualquier carácter cuyo valor de propiedad "Uppercase" sea "False", y podrían haber sido escritos como "\p{Uppercase=True}" y "\p{Uppercase=False}", respectivamente.

Esta formalidad es necesaria cuando las propiedades no son binarias; es decir, si pueden tomar más valores que solo "True" y "False". Por ejemplo, la propiedad "Bidi_Class" (ver "Bidirectional Character Types" abajo), puede tomar varios valores diferentes, como "Left", "Right", "Whitespace", y otros. Para coincidir con estos, se necesita especificar tanto el nombre de la propiedad ("Bidi_Class") COMO el valor con el que se compara ("Left", "Right", *etcétera*). Esto se hace, como en los ejemplos anteriores, teniendo los dos componentes separados por un signo de igual (o indistintamente, un dos puntos), como "\p{Bidi_Class: Left}".

Todas las propiedades de caracteres definidas por Unicode pueden escribirse en estas formas compuestas de "\p{propiedad=valor}" o "\p{propiedad:valor}", pero Perl proporciona algunas propiedades adicionales que solo se escriben en forma simple, así como atajos de forma simple para todas las propiedades binarias y ciertos otros descritos a continuación, en los que puede omitir el nombre de la propiedad y el separador de igual o dos puntos.

La mayoría de las propiedades de caracteres Unicode tienen al menos dos sinónimos (o alias si lo prefiere): uno corto que es más fácil de escribir y uno más largo que es más descriptivo y, por lo tanto, más fácil de entender. Por lo tanto, las propiedades "L" y "Letter" anteriores son equivalentes y se pueden usar indistintamente. Del mismo modo, "Upper" es un sinónimo de "Uppercase", y podríamos haber escrito "\p{Uppercase}" de forma equivalente como "\p{Upper}". Además, normalmente hay varios sinónimos para los valores que puede tener la propiedad. Para propiedades binarias, "True" tiene 3 sinónimos: "T", "Yes" y "Y"; y "False" tiene correspondientemente "F", "No" y "N". Pero tenga cuidado. Una forma corta de un valor para una propiedad puede no significar lo mismo que la forma corta escrita de la misma manera para otra. Por lo tanto, para la propiedad "General_Category", "L" significa "Letter", pero para la propiedad "Bidi_Class", "L" significa "Left". Una lista completa de propiedades y sinónimos se encuentra en perluniprops.

Las diferencias entre mayúsculas y minúsculas en nombres y valores de propiedades son irrelevantes; por lo tanto, "\p{Upper}" significa lo mismo que "\p{upper}" o incluso "\p{UpPeR}". Del mismo modo, puede agregar o restar guiones bajos en cualquier lugar en medio de una palabra, de modo que estas también sean equivalentes a "\p{U_p_p_e_r}". Y el espacio en blanco generalmente es irrelevante adyacente a caracteres que no son de palabra, como las llaves y los separadores de igual o dos puntos, por lo que "\p{ Upper }" y "\p{ Upper_case : Y }" son equivalentes a estas también. De hecho, el espacio en blanco e incluso los guiones se pueden agregar o eliminar generalmente en cualquier lugar. Por lo tanto, incluso "\p{ Up-per case = Yes}" es equivalente. Todo esto se llama "coincidencia laxa" (loose-matching) por Unicode. La propiedad "name" tiene algunas restricciones debido a unos pocos nombres atípicos. Los detalles completos se encuentran en https://www.unicode.org/reports/tr44/tr44-24.html#UAX44-LM2.

Los pocos lugares donde se utiliza una coincidencia más estricta son en el medio de los números, la propiedad "name" y las propiedades de extensión de Perl que comienzan o terminan con un guion bajo. La coincidencia más estricta tiene en cuenta los espacios en blanco (excepto los adyacentes a caracteres que no son de palabra), los guiones y los guiones bajos no interiores.

También puede usar la negación tanto en "\p{}" como en "\P{}" introduciendo un circunflejo ("^") entre la primera llave y el nombre de la propiedad: "\p{^Tamil}" es igual a "\P{Tamil}".

Casi todas las propiedades son inmunes a la coincidencia insensible a mayúsculas y minúsculas. Es decir, agregar un modificador de expresión regular "/i" no cambia lo que coinciden. Hay dos conjuntos que se ven afectados. El primer conjunto es "Uppercase_Letter", "Lowercase_Letter" y "Titlecase_Letter", todos los cuales coinciden con "Cased_Letter" bajo la coincidencia "/i". Y el segundo conjunto es "Uppercase", "Lowercase" y "Titlecase", todos los cuales coinciden con "Cased" bajo la coincidencia "/i". Este conjunto también incluye sus subconjuntos "PosixUpper" y "PosixLower", ambos los cuales bajo la coincidencia "/i" coinciden con "PosixAlpha". (La diferencia entre estos conjuntos es que algunas cosas, como los números romanos, vienen en mayúsculas y minúsculas, por lo que son "Cased", pero no se consideran letras, por lo que no son "Cased_Letter".)

Consulte "Beyond Unicode code points" para consideraciones especiales al comparar propiedades Unicode con puntos de código no Unicode.

Scripts

Los idiomas del mundo se escriben en muchos scripts diferentes. Esta frase (a menos que la estés leyendo en una traducción) está escrita en Latín, mientras que el ruso se escribe en Cirílico y el griego se escribe, bueno, en Griego; el japonés principalmente en Hiragana o Katakana. Hay muchos más.

Las propiedades de Unicode "Script" y "Script_Extensions" indican en qué script se encuentra un carácter dado. La propiedad "Script_Extensions" es una versión mejorada de "Script", como se demuestra a continuación. Cualquiera de las dos propiedades se puede especificar con la forma compuesta como "\p{Script=Hebrew}" (abreviado: "\p{sc=hebr}"), o "\p{Script_Extensions=Javanese}" (abreviado: "\p{scx=java}"). Además, Perl proporciona atajos para todos los nombres de propiedades de "Script_Extensions". Puedes omitir todo hasta el signo igual (o los dos puntos) y simplemente escribir "\p{Latin}" o "\P{Cyrillic}". (Esto no es cierto para "Script", que debe escribirse en la forma compuesta. Antes de Perl v5.26, la forma simple devolvía la antigua versión "Script", pero se cambió porque "Script_Extensions" da mejores resultados.)

La diferencia entre estas dos propiedades involucra caracteres que se usan en múltiples scripts. Por ejemplo, los dígitos '0' a '9' se usan en muchas partes del mundo. Estos se colocan en un script llamado "Common". Otros caracteres se usan en solo unos pocos scripts. Por ejemplo, el "KATAKANA-HIRAGANA DOUBLE HYPHEN" se usa en ambos scripts japoneses, Katakana y Hiragana, pero en ningún otro lugar. La propiedad "Script" coloca todos los caracteres que se usan en múltiples scripts en el script "Common", mientras que la propiedad "Script_Extensions" coloca aquellos que se usan en solo unos pocos scripts en cada uno de esos scripts; mientras sigue usando "Common" para aquellos que se usan en muchos scripts. Por lo tanto, ambos coinciden:

"0" =~ /\p{sc=Common}/     # Coincide
"0" =~ /\p{scx=Common}/    # Coincide

y solo el primero de estos coincide:

"\N{KATAKANA-HIRAGANA DOUBLE HYPHEN}" =~ /\p{sc=Common}  # Coincide
"\N{KATAKANA-HIRAGANA DOUBLE HYPHEN}" =~ /\p{scx=Common} # No coincide

Y solo los dos últimos de estos coinciden:

"\N{KATAKANA-HIRAGANA DOUBLE HYPHEN}" =~ /\p{sc=Hiragana}  # No coincide
"\N{KATAKANA-HIRAGANA DOUBLE HYPHEN}" =~ /\p{sc=Katakana}  # No coincide
"\N{KATAKANA-HIRAGANA DOUBLE HYPHEN}" =~ /\p{scx=Hiragana} # Coincide
"\N{KATAKANA-HIRAGANA DOUBLE HYPHEN}" =~ /\p{scx=Katakana} # Coincide

"Script_Extensions" es, por lo tanto, una mejora de "Script", en la que hay menos caracteres en el script "Common" y, en consecuencia, más en otros scripts. Es nuevo en la versión 6.0 de Unicode, y es probable que sus datos cambien significativamente en versiones posteriores, a medida que las cosas se vayan resolviendo. El nuevo código probablemente debería usar "Script_Extensions" y no simplemente "Script". Si compilas perl con una versión de Unicode que no tiene "Script_Extensions", las extensiones de Perl de forma simple se referirán en cambio a la propiedad "Script" simple. Si compilas con una versión de Unicode que no tiene la propiedad "Script", estas extensiones no se definirán en absoluto.

(En realidad, además de "Common", el script "Inherited", contiene caracteres que se usan en múltiples scripts. Estos son caracteres modificadores que heredan el valor del script del carácter de control. Algunos de estos se usan en muchos scripts, y por lo tanto van en "Inherited" tanto en "Script" como en "Script_Extensions". Otros se usan en solo unos pocos scripts, por lo que están en "Inherited" en "Script", pero no en "Script_Extensions".)

Vale la pena destacar que hay varios conjuntos diferentes de dígitos en Unicode que son equivalentes a 0-9 y se pueden comparar con "\d" en una expresión regular. Si se usan en un solo idioma, están en el "Script" y "Script_Extensions" de ese idioma. Si se usan en más de un script, estarán en "sc=Common", pero solo si se usan en muchos scripts deberían estar en "scx=Common".

La explicación anterior ha omitido algunos detalles; consulte UAX #24 "Propiedad de Script de Unicode": https://www.unicode.org/reports/tr24

Uso del prefijo "Is"

Por compatibilidad retroactiva (con Perl 5.6 antiguo), todas las propiedades que se pueden escribir sin usar la forma compuesta mencionada hasta ahora pueden tener "Is" o "Is_" antepuestos a su nombre, por lo que "\P{Is_Lu}", por ejemplo, es igual a "\P{Lu}", y "\p{IsScript:Arabic}" es igual a "\p{Arabic}".

Bloques

Además de los scripts, Unicode también define bloques de caracteres. La diferencia entre scripts y bloques es que el concepto de scripts se acerca más a los idiomas naturales, mientras que el concepto de bloques es más una agrupación artificial basada en grupos de caracteres Unicode con valores ordinales consecutivos. Por ejemplo, el bloque "Basic Latin" son todos los caracteres cuyos ordinales están entre 0 y 127, inclusive; en otras palabras, los caracteres ASCII. El script "Latin" contiene algunas letras de este como también varios otros bloques, como "Latin-1 Supplement", "Latin Extended-A", etcétera, pero no contiene todos los caracteres de esos bloques. No contiene, por ejemplo, los dígitos 0-9, porque esos dígitos son compartidos entre muchos scripts y, por lo tanto, están en el script "Common".

Para más información sobre scripts frente a bloques, consulte UAX #24 "Propiedad de Script de Unicode": https://www.unicode.org/reports/tr24

Es probable que las propiedades "Script_Extensions" o "Script" sean las que desee utilizar al procesar lenguaje natural; la propiedad "Block" puede ser útil ocasionalmente para trabajar con los detalles de Unicode.

Los nombres de bloques se comparan en la forma compuesta, como "\p{Block: Arrows}" o "\p{Blk=Hebrew}". A diferencia de la mayoría de las otras propiedades, solo unos pocos nombres de bloques tienen un nombre corto definido por Unicode.

Perl también define sinónimos de forma simple para la propiedad de bloque en casos en que estos no entren en conflicto con otra cosa. Pero no use ninguno de estos, ya que son inestables. Dado que son extensiones de Perl, están subordinadas a los nombres de propiedades oficiales de Unicode; Unicode no sabe ni le importan las extensiones de Perl. Puede suceder que un nombre que actualmente significa la extensión de Perl cambie más tarde sin previo aviso para significar una propiedad de Unicode diferente en una versión futura del intérprete de perl que use una versión posterior de Unicode, y su código ya no funcionaría. Las extensiones se mencionan aquí por completitud: tome el nombre del bloque y antepóngale uno de: "In" (por ejemplo "\p{Blk=Arrows}" actualmente se puede escribir como "\p{In_Arrows}"); o a veces "Is" (como "\p{Is_Arrows}"); o a veces sin prefijo alguno ("\p{Arrows}"). Al momento de escribir esto (Unicode 9.0) no hay conflictos al usar el prefijo "In_", pero hay muchos con las otras dos formas. Por ejemplo, "\p{Is_Hebrew}" y "\p{Hebrew}" significan "\p{Script_Extensions=Hebrew}" lo cual NO es lo mismo que "\p{Blk=Hebrew}". Nuestra recomendación solía ser usar el prefijo "In_" como una forma simple de especificar un bloque. Pero Unicode 8.0 agregó propiedades cuyos nombres comienzan con "In", y ahora está claro que solo la suerte ha evitado hasta ahora un conflicto. Usar "In" requiere solo marginalmente menos escritura que "Blk:", y el significado de este último es más claro de todos modos, y está garantizado que nunca entrará en conflicto. Así que no se arriesgue. Use "\p{Blk=foo}" para código nuevo. Y asegúrese de que el bloque sea lo que realmente, realmente quiere hacer. En la mayoría de los casos, los scripts son lo que desea en su lugar.

Es algo así como un dígito 1, pero no exactamente; su descomposición en el dígito 1 se llama descomposición "compatible", específicamente una descomposición "super" (de "superscript"). Existen varias descomposiciones de compatibilidad de este tipo (ver https://www.unicode.org/reports/tr44). qr/(?[ \P{DT=Canonical} - \p{DT=None} ])/

(Tenga en cuenta que una de las descomposiciones no canónicas se denomina "compat", que quizás podría haberse denominado mejor "miscellaneous". Incluye solo aquellas cosas para las que Unicode no pudo encontrar un nombre genérico mejor).

Esto es lo mismo que "\h" y "\p{Blank}": un carácter que cambia el espaciado horizontalmente.

Esto es un sinónimo de "\p{Present_In=*}"

"\p{Posix...}"
Existen varias de estas, que son equivalentes, utilizando la notación "\p{}", para clases Posix y se describen en "POSIX Character Classes" en perlrecharclass.
"\p{Present_In: *}" (Corto: "\p{In=*}")
Esta propiedad se utiliza cuando necesita saber en qué versión(es) de Unicode se encuentra un carácter.

El "*" anterior representa algún número de versión de Unicode, como 1.1 o 12.0; o el "*" también puede ser "Unassigned". Esta propiedad coincidirá con los puntos de código cuya disposición final se haya decidido a partir de la versión de Unicode dada; "\p{Present_In: Unassigned}" coincidirá con aquellos puntos de código cuyo significado aún no se ha asignado.

Por ejemplo, "U+0041" "LATIN CAPITAL LETTER A" estaba presente en la primera versión de Unicode disponible, que es 1.1, por lo que esta propiedad es verdadera para todas las versiones válidas de "*". Por otro lado, "U+1EFF" no se asignó hasta la versión 5.1 cuando se convirtió en "LATIN SMALL LETTER Y WITH LOOP", por lo que los únicos "*" que coincidirían con él son 5.1, 5.2 y posteriores.

Unicode proporciona la propiedad "Age" de la cual se deriva esta. El problema con Age es que una interpretación estricta de ella (que Perl toma) hace que coincida con la versión exacta en la que se introduce el significado de un punto de código. Por lo tanto, "U+0041" coincidiría solo con 1.1; y "U+1EFF" solo con 5.1. Esto no suele ser lo que se desea.

Algunas implementaciones no de Perl de la propiedad Age pueden cambiar su significado para que sea el mismo que la propiedad Perl "Present_In"; solo tenga en cuenta eso.

Otra confusión con ambas propiedades es que la definición no es que el punto de código haya sido *asignado*, sino que el significado del punto de código ha sido *determinado*. Esto se debe a que 66 puntos de código siempre estarán sin asignar, y por lo tanto la "Age" para ellos es la versión de Unicode en la que se tomó la decisión de hacerlos así. Por ejemplo, "U+FDD0" permanecerá permanentemente sin asignar a un carácter, y la decisión de hacerlo se tomó en la versión 3.1, por lo que "\p{Age=3.1}" coincide con este carácter, al igual que "\p{Present_In: 3.1}" y posteriores.

"\p{SpacePerl}"

"\p{VertSpace}"
Esto es lo mismo que "\v": un carácter que cambia el espaciado verticalmente.

Comparación de "\N{...}" y "\p{name=...}"

A partir de Perl 5.32, puedes especificar un carácter por su nombre en patrones de expresiones regulares usando "\p{name=...}". Esto se suma al método tradicional de usar "\N{...}". Lo siguiente resume las diferencias entre estos dos:

                      \N{...}       \p{Name=...}
puede interpolar   solo con eval       sí            [1]
nombres personalizados      sí             no             [2]
alias de nombres        sí             sí             [3]
secuencias nombradas      sí             sí             [4]
análisis de valor de nombre       exacto   Unicode flexible       [5]
[1]
La capacidad de interpolar significa que puedes hacer algo como 
qr/\p{na=latin capital letter $which}/

y especificar $which en otro lugar.

[2]
Puedes crear tus propios nombres para caracteres y anular los oficiales al usar "\N{...}". Ver "ALIAS PERSONALIZADOS" en charnames.
[3]
Algunos caracteres tienen múltiples nombres (sinónimos).
[4]
Algunas secuencias particulares de caracteres reciben un solo nombre, además de sus nombres individuales.
[5]
La coincidencia exacta del valor del nombre significa que debes especificar mayúsculas, guiones, guiones bajos y espacios precisamente en el nombre que quieres. La coincidencia flexible sigue las reglas de Unicode https://www.unicode.org/reports/tr44/tr44-24.html#UAX44-LM2, donde estos son en su mayoría irrelevantes. Excepto por algunos nombres de caracteres atípicos, estas son las mismas reglas que ya se utilizan para cualquier otra propiedad de "\p{...}".

Comodines en Valores de Propiedad

A partir de Perl 5.30, es posible hacer algo como esto:

qr!\p{numeric_value=/\A[0-5]\z/}!

o, al abreviar y añadir "/x",

qr! \p{nv= /(?x) \A [0-5] \z / }!

Esto coincide con todos los puntos de código cuyo valor numérico es uno de 0, 1, 2, 3, 4 o 5. Este ejemplo en particular podría haber sido escrito en su lugar como

qr! \A [ \p{nv=0}\p{nv=1}\p{nv=2}\p{nv=3}\p{nv=4}\p{nv=5} ] \z !xx

en versiones anteriores de Perl, por lo que en este caso esta característica simplemente hace que las cosas sean más fáciles y cortas de escribir. Si no hubiéramos incluido "\A" y "\z", habrían coincidido con cosas como "1/2" porque contiene un 1 (así como un 2). Tal como está escrito, coincide con cosas como subíndices que tienen estos valores numéricos. Si solo quisiéramos los dígitos decimales con esos valores numéricos, podríamos decir,

qr! (?[ \d & \p{nv=/[0-5]/} ]) }!x

El "\d" elimina la necesidad de anclar el patrón, ya que fuerza a que el resultado solo coincida con "[0-9]", y el "[0-5]" lo restringe aún más.

El texto en los ejemplos anteriores encerrado entre los caracteres "/" puede ser prácticamente cualquier expresión regular. Es independiente del patrón principal, por lo que no comparte ningún grupo de captura, *etc.* Los delimitadores deben ser signos de puntuación ASCII, pero NO pueden ser delimitados por "{", ni "}" ni contener un "}" literal, ya que eso delimita el final del "\p{}" envolvente. Como cualquier patrón, ciertos otros delimitadores son terminados por sus imágenes especulares. Estos son "(", ""["", y "<". Si el delimitador es alguno de "-", "_", "+", o "\", o es el mismo delimitador que se usa para el patrón envolvente, debe ir precedido por una barra invertida de escape, tanto al principio como al final.

Tenga cuidado al usar "$" para indicar que coincida con el final de la cadena. Puede interpretarse fácilmente como una variable de puntuación, como $/.

No pueden seguir modificadores al delimitador final. En su lugar, use "(?adlupimnsx-imnsx)" en perlre y/o "(?adluimnsx-imnsx:patrón)" en perlre para especificar modificadores. Sin embargo, ciertos modificadores son ilegales en su subpatrón comodín. El único modificador de conjunto de caracteres especificable es "/aa"; cualquier otro conjunto de caracteres, y "-m", y "p", y "s" son todos ilegales. Especificar modificadores como "qr/.../gc" que no son legales en la notación "(?...)" normalmente genera una advertencia, pero con subpatrones comodín, su uso es un error. El modificador "m" es ineficaz; todo lo que coincida será una sola línea.

Por defecto, su patrón se compara sin distinguir entre mayúsculas y minúsculas, como si se hubiera especificado "/i". Puede cambiar esto diciendo "(?-i)" en su patrón.

También hay ciertas operaciones que son ilegales. No puede anidar llamadas "\p{...}" y "\P{...}" dentro de un subpatrón comodín, y "\G" no tiene sentido, por lo que también está prohibido.

Y el cuantificador "*" (o su equivalente "(0,}") es ilegal.

Esta característica no está disponible cuando el lado izquierdo está precedido por "Is_", ni para ninguna forma que esté marcada como "Desaconsejada" en "Desaconsejada" en perluniprops.

Esta característica experimental se ha añadido para empezar a implementar https://www.unicode.org/reports/tr18/#Wildcard_Properties. Su uso generará una advertencia (activada por defecto) en la categoría "experimental::uniprop_wildcards". Nos reservamos el derecho de cambiar su funcionamiento a medida que ganemos experiencia.

Su subpatrón puede ser prácticamente cualquier cosa, pero para que tenga alguna utilidad, debe coincidir cuando se llama con el nombre completo de la propiedad con guiones bajos (y/o espacios en la propiedad Block) y algunas cosas en mayúsculas; o b) el valor de la propiedad en minúsculas sin espacios ni guiones bajos. Por ejemplo,

qr!\p{Blk=/Old I.*/}!
qr!\p{Blk=/oldi.*/}!

coincidirían con lo mismo.

Otro ejemplo que muestra que dentro de "\p{...}", "/x" no es necesario para tener espacios:

qr!\p{scx= /Hebrew|Greek/ }!

Para estar seguros, deberíamos haber anclado el ejemplo anterior, para evitar coincidencias con algo como "Hebrew_Braille", pero hasta ahora no hay nombres de script como ese. Se emite una advertencia si ninguno de los valores legales para una propiedad coincide con su patrón. Es probable que una futura versión emita una advertencia si su patrón termina causando que todos los puntos de código posibles coincidan.

A partir de la versión 5.32, se permite la comparación de las propiedades Name, Name Aliases y Named Sequences. Se consideran una sola propiedad combinada, como ha sido el caso durante mucho tiempo para "\N{}". La coincidencia flexible no funciona exactamente de la misma manera para estas propiedades que para los valores de otras propiedades. Las reglas se dan en https://www.unicode.org/reports/tr44/tr44-24.html#UAX44-LM2. Como resultado, Perl no intenta la coincidencia flexible, como lo hace en otras propiedades. Todas las letras en los nombres están en mayúsculas, pero puede añadir "(?i)" a su subpatrón para ignorar mayúsculas y minúsculas. Si no está seguro de dónde hay un espacio, puede usar " ?" en su subpatrón. Ningún nombre de carácter contiene un guion bajo, así que no se moleste en intentar coincidir uno. El uso de guiones es particularmente problemático; consulte el enlace anterior. Pero tenga en cuenta que, a partir de Unicode 13.0, el único script de uso moderno que tiene rarezas con estos es el tibetano; también los dos caracteres coreanos U+116C HANGUL JUNGSEONG OE y U+1180 HANGUL JUNGSEONG O-E. Unicode no promete no añadir nombres problemáticos con guiones en el futuro.

Usar comodines en estas propiedades consume muchos recursos, dado los cientos de miles de nombres legales que deben ser verificados.

Un ejemplo de uso de comodines en la propiedad Name es

qr!\p{name=/(SMILING|GRINNING) FACE/}!

Otro es

qr/(?[ \p{name=\/CJK\/} - \p{ideographic} ])/

que son los aproximadamente 200 (a partir de Unicode 13.0) caracteres CJK que no son ideográficos.

Propiedades de Caracteres Definidas por el Usuario

Puedes definir tus propias propiedades de caracteres binarias definiendo subrutinas cuyos nombres comiencen con "In" o "Is". (La característica de conjuntos de expresiones regulares "(?[ ])" en perlre proporciona una alternativa que permite definiciones más complejas.) Las subrutinas pueden definirse en cualquier paquete. Anulan cualquier propiedad Unicode expresada con los mismos nombres. Las subrutinas reciben un solo parámetro, que es 0 si la comparación sin distinción entre mayúsculas y minúsculas está activa y distinto de cero si la comparación sin distinción entre mayúsculas y minúsculas está activa. La subrutina puede devolver valores diferentes dependiendo del valor del indicador. Pero la subrutina nunca se llama más de una vez por cada valor del indicador (cero o distinto de cero). El valor de retorno se guarda y se usa en lugar de llamar a la subrutina de nuevo. Si la subrutina está definida en el momento en que se compila el patrón, se llamará entonces; si no, se llamará la primera vez que se necesite su valor (para ese indicador) durante la ejecución.

Ten en cuenta que si la expresión regular está contaminada (tainted), Perl morirá en lugar de llamar a la subrutina cuando el nombre de la subrutina sea determinado por los datos contaminados.

      The following items are mostly for reference and general Unicode knowledge, Perl doesn't use these constructs internally.

      Like UTF-8, UTF-16 is a variable-width encoding, but where UTF-8 uses 8-bit code units, UTF-16 uses 16-bit code units. All code points occupy either 2 or 4 bytes in UTF-16: code points "U+0000..U+FFFF" are stored in a single 16-bit unit, and code points "U+10000..U+10FFFF" in two 16-bit units. The latter case is using surrogates, the first 16-bit unit being the high surrogate, and the second being the low surrogate.

      Surrogates are code points set aside to encode the "U+10000..U+10FFFF" range of Unicode code points in pairs of 16-bit units. The high surrogates are the range "U+D800..U+DBFF" and the low surrogates are the range "U+DC00..U+DFFF". The surrogate encoding is

      $hi = ($uni - 0x10000) / 0x400 + 0xD800;
$lo = ($uni - 0x10000) % 0x400 + 0xDC00;

      and the decoding is

      $uni = 0x10000 + ($hi - 0xD800) * 0x400 + ($lo - 0xDC00);

      Because of the 16-bitness, UTF-16 is byte-order dependent. UTF-16 itself can be used for in-memory computations, but if storage or transfer is required either UTF-16BE (big-endian) or UTF-16LE (little-endian) encodings must be chosen.

      This introduces another problem: what if you just know that your data is UTF-16, but you don't know which endianness? Byte Order Marks, or "BOM"'s, are a solution to this. A special character has been reserved in Unicode to function as a byte order marker: the character with the code point "U+FEFF" is the "BOM".

      The trick is that if you read a "BOM", you will know the byte order, since if it was written on a big-endian platform, you will read the bytes "0xFE 0xFF", but if it was written on a little-endian platform, you will read the bytes "0xFF 0xFE". (And if the originating platform was writing in ASCII platform UTF-8, you will read the bytes "0xEF 0xBB 0xBF".)

      The way this trick works is that the character with the code point "U+FFFE" is not supposed to be in input streams, so the sequence of bytes "0xFF 0xFE" is unambiguously ""BOM", represented in little-endian format" and cannot be "U+FFFE", represented in big-endian format".

      Surrogates have no meaning in Unicode outside their use in pairs to represent other code points. Unicode does define semantics for them, such as their "General_Category" is "Cs". But because their use is somewhat dangerous, Perl will warn (using the warning category "surrogate", which is a sub-category of "utf8") if an attempt is made to do things like take the lower case of one, or match case-insensitively, or to output them. (But don't try this on Perls before 5.14.)

    Cuando Unicode No Ocurre

    Todavía hay muchos lugares donde Unicode (en alguna codificación o la otra) puede darse como argumentos o recibirse como resultados, o ambos en Perl, pero no es así, a pesar de que Perl tiene amplias formas de entrada y salida en Unicode, y algunos otros "puntos de entrada" como la matriz @ARGV (que a veces puede interpretarse como UTF-8).

    Las siguientes son tales interfaces. También, ver "El "Error de Unicode"". Para todas estas interfaces, Perl actualmente (a partir de la versión v5.16.0) simplemente asume cadenas de bytes tanto como argumentos como resultados, o cadenas UTF-8 si se ha utilizado el pragma (obsoleto) "encoding".

    Una razón por la que Perl no intenta resolver el rol de Unicode en estas situaciones es que las respuestas dependen en gran medida del sistema operativo y de los sistemas de archivos. Por ejemplo, si los nombres de archivo pueden estar en Unicode y en qué tipo de codificación exactamente, no es exactamente un concepto portable. De manera similar para "qx" y "system": ¿qué tan bien manejará la "interfaz de línea de comandos" (y cuál de ellas?) Unicode?

    • "chdir", "chmod", "chown", "chroot", "exec", "link", "lstat", "mkdir", "rename", "rmdir", "stat", "symlink", "truncate", "unlink", "utime", "-X"
    • %ENV
    • "glob" (también conocido como "<*>")
    • "open", "opendir", "sysopen"
    • "qx" (también conocido como el operador de comillas invertidas), "system"
    • "readdir", "readlink"

    El "Error de Unicode"

    El término "error de Unicode" se ha aplicado a una inconsistencia con los puntos de código en el bloque "Suplemento Latino-1", es decir, entre 128 y 255. Sin una localización especificada, a diferencia de todos los demás caracteres o puntos de código, estos caracteres pueden tener semánticas muy diferentes dependiendo de las reglas en vigor. (Los caracteres cuyos puntos de código son superiores a 255 fuerzan las reglas de Unicode; mientras que las reglas para los caracteres ASCII son las mismas bajo las reglas ASCII y Unicode.)

    Bajo las reglas de Unicode, estos caracteres superiores de Latin1 se interpretan como puntos de código Unicode, lo que significa que tienen la misma semántica que Latin-1 (ISO-8859-1) y controles C1.

    Como se explica en "Reglas ASCII frente a Reglas Unicode", bajo las reglas ASCII, se consideran caracteres no asignados.

    Esto puede conducir a resultados inesperados. Por ejemplo, la semántica de una cadena puede cambiar súbitamente si se le añade un punto de código superior a 255, lo que cambia las reglas de ASCII a Unicode. Como ejemplo, considere el siguiente programa y su salida:

    $ perl -le'
    no feature "unicode_strings";
    $s1 = "\xC2";
    $s2 = "\x{2660}";
    for ($s1, $s2, $s1.$s2) {
        print /\w/ || 0;
    }
'
0
0
1

    Si no hay un "\w" en "s1" ni en "s2", ¿por qué su concatenación tiene uno?

    Esta anomalía se deriva del intento de Perl de no perturbar los programas antiguos que no usaban Unicode, junto con el deseo de Perl de añadir soporte Unicode sin problemas. Pero el resultado no fue sin problemas. (Por cierto, puedes elegir que te avisen cuando sucedan cosas como esta. Ver "encoding::warnings".)

    "use feature 'unicode_strings'" se añadió, a partir de Perl v5.12, para abordar este problema. Afecta a estas cosas:

    • Cambiar la mayúscula/minúscula de un escalar, es decir, usar uc(), ucfirst(), lc() y lcfirst(), o "\L", "\U", "\u" y "\l" en contextos de doble comilla, como sustituciones de expresiones regulares.

      Bajo "unicode_strings" a partir de Perl 5.12.0, generalmente se utilizan reglas de Unicode. Ver "lc" en perlfunc para más detalles sobre cómo funciona esto en combinación con varios otros pragmas.

    • Usar coincidencia de expresiones regulares sin distinción de mayúsculas y minúsculas ("/i").

      A partir de Perl 5.14.0, las expresiones regulares compiladas dentro del alcance de "unicode_strings" utilizan reglas de Unicode incluso cuando se ejecutan o compilan en expresiones regulares más grandes fuera del alcance.

    • Coincidir con cualquiera de varias propiedades en expresiones regulares.

      Estas propiedades son "\b" (sin llaves), "\B" (sin llaves), "\s", "\S", "\w", "\W", y todas las clases de caracteres Posix *excepto* "[[:ascii:]]".

      A partir de Perl 5.14.0, las expresiones regulares compiladas dentro del alcance de "unicode_strings" utilizan reglas de Unicode incluso cuando se ejecutan o compilan en expresiones regulares más grandes fuera del alcance.

    • En "quotemeta" o su equivalente en línea "\Q".

      A partir de Perl 5.16.0, se utilizan reglas de comillas consistentes dentro del alcance de "unicode_strings", como se describe en "quotemeta" en perlfunc. Antes de eso, o fuera de su alcance, ningún punto de código superior a 127 se cita en cadenas codificadas en UTF-8, pero en cadenas codificadas por bytes, los puntos de código entre 128-255 siempre se citan.

    • En el operador de rango "..".

      A partir de Perl 5.26.0, el operador de rango en cadenas trata sus longitudes de manera consistente dentro del alcance de "unicode_strings". Antes de eso, o fuera de su alcance, podía producir cadenas cuya longitud en caracteres superaba la del lado derecho, donde el lado derecho ocupaba más bytes que el punto final del rango correcto.

    • En la división de espacios en blanco de caso especial de "split".

      A partir de Perl 5.28.0, la función "split" con un patrón especificado como una cadena que contiene un solo espacio maneja los caracteres de espacio en blanco de manera consistente dentro del alcance de "unicode_strings". Antes de eso, o fuera de su alcance, los caracteres que son espacios en blanco según las reglas de Unicode pero no según las reglas ASCII se trataban como contenido de campo en lugar de separadores de campo cuando aparecían en cadenas codificadas por bytes.

    Como se puede ver en lo anterior, el efecto de "unicode_strings" aumentó durante varios lanzamientos de Perl. (Y el soporte de Perl para Unicode continúa mejorando; es mejor usar la última versión disponible para obtener los resultados más completos y precisos posibles). Tenga en cuenta que "unicode_strings" se elige automáticamente si "use v5.12" o superior.

    Para las versiones de Perl anteriores a las descritas anteriormente, o cuando una cadena se pasa a una función fuera del alcance de "unicode_strings", consulte la siguiente sección.

    Forzar Unicode en Perl (O Quitar Unicode en Perl)

    A veces (ver "Cuando Unicode No Ocurre" o "El "Error de Unicode"") hay situaciones en las que simplemente necesita forzar una cadena de bytes a UTF-8, o viceversa. El módulo estándar Encode puede usarse para esto, o las llamadas de bajo nivel utf8::upgrade($bytestring) y "utf8::downgrade($utf8string[, FAIL_OK])".

    Tenga en cuenta que utf8::downgrade() puede fallar si la cadena contiene caracteres que no caben en un byte.

    Llamar a cualquiera de las funciones en una cadena que ya está en el estado deseado no tiene efecto.

    perlunicode - Tutorial de Unicode para Perl

    DESCRIPCIÓN

    Este tutorial cubre las características de Unicode en Perl, incluyendo el modelo de cadenas, la codificación, la interfaz con el sistema operativo y las diferencias entre versiones de Perl.

    MODELO DE CADENA

    Perl distingue entre cadenas que son secuencias de bytes y cadenas que son secuencias de caracteres Unicode. Una cadena se marca como que contiene datos Unicode mediante un "flag UTF8".

    • Cuando se crea una cadena que se sabe que es Unicode (por ejemplo, mediante "use utf8" o mediante ciertas funciones), Perl la marca con el flag UTF8.
    • Cuando se opera con datos que provienen de fuentes externas (archivos, red, etc.), Perl los trata como secuencias de bytes a menos que se le indique lo contrario (por ejemplo, usando el modo ":encoding()" en open).
    • Las operaciones que no dependen de la representación de caracteres (como la mayoría de las operaciones de cadenas de bytes) funcionan de manera transparente en cadenas con el flag UTF8.
    • Las operaciones que sí dependen de la representación de caracteres (como length(), substr(), expresiones regulares con ciertas propiedades) pueden ser más lentas en cadenas con el flag UTF8, ya que necesitan interpretar la cadena como caracteres Unicode en lugar de simples bytes.

    Puerto de código desde Perl-5.6.X

    Las versiones de Perl a partir de la 5.8 tienen un modelo Unicode diferente al de la 5.6. En la 5.6, el programador debía usar el pragma "utf8" para declarar que un ámbito determinado esperaba tratar con datos Unicode y debía asegurarse de que solo los datos Unicode llegaran a ese ámbito. Si tiene código que funciona con la 5.6, necesitará algunos de los siguientes ajustes en su código. Los ejemplos están escritos de tal manera que el código seguirá funcionando bajo la 5.6, por lo que debería ser seguro probarlos.

    • Un manejador de archivo que debe leer o escribir UTF-8 
      if ($] > 5.008) {
  binmode $fh, ":encoding(UTF-8)";
}
    • Un escalar que se pasará a alguna extensión

      Ya sea "Compress::Zlib", "Apache::Request" o cualquier extensión que no mencione Unicode en su página man, debe asegurarse de que el flag UTF8 se elimine. Tenga en cuenta que en el momento de escribir esto (enero de 2012), los módulos mencionados no son conscientes de UTF-8. Por favor, consulte la documentación para verificar si esto sigue siendo cierto.

      if ($] > 5.008) {
  require Encode;
  $val = Encode::encode("UTF-8", $val); # hacer octetos
}
    • Un escalar que hemos obtenido de una extensión

      Si cree que el escalar regresa como UTF-8, lo más probable es que quiera que se restaure el flag UTF8:

      if ($] > 5.008) {
  require Encode;
  $val = Encode::decode("UTF-8", $val);
}
    • Lo mismo, si está realmente seguro de que es UTF-8 
      if ($] > 5.008) {
  require Encode;
  Encode::_utf8_on($val);
}
    • Un envoltorio para "fetchrow_array" y "fetchrow_hashref" de DBI

      Cuando la base de datos contiene solo UTF-8, una función o método envoltorio es una forma conveniente de reemplazar todas sus llamadas a "fetchrow_array" y "fetchrow_hashref". Una función envoltorio también facilitará la adaptación a futuras mejoras en su controlador de base de datos. Tenga en cuenta que en el momento de escribir esto (enero de 2012), DBI no tiene una forma estandarizada de tratar con datos UTF-8. Por favor, consulte la documentación de DBI para verificar si eso sigue siendo cierto.

      sub fetchrow {
  # $what es uno de fetchrow_{array,hashref}
  my($self, $sth, $what) = @_;
  if ($] < 5.008) {
    return $sth->$what;
  } else {
    require Encode;
    if (wantarray) {
      my @arr = $sth->$what;
      for (@arr) {
        defined && /[^\000-\177]/ && Encode::_utf8_on($_);
      }
      return @arr;
    } else {
      my $ret = $sth->$what;
      if (ref $ret) {
        for my $k (keys %$ret) {
          defined
          && /[^\000-\177]/
          && Encode::_utf8_on($_) for $ret->{$k};
        }
        return $ret;
      } else {
        defined && /[^\000-\177]/ && Encode::_utf8_on($_) for $ret;
        return $ret;
      }
    }
  }
}
    • Un escalar grande que sabe que solo puede contener ASCII

      Los escalares que contienen solo ASCII y están marcados como UTF-8 a veces son una carga para su programa. Si reconoce tal situación, simplemente elimine el flag UTF8:

      utf8::downgrade($val) if $] > 5.008;

    Interacción con Extensiónes

    Cuando Perl intercambia datos con una extensión, la extensión debería ser capaz de entender el flag UTF8 y actuar en consecuencia. Si la extensión no reconoce ese flag, es probable que la extensión devuelva datos marcados incorrectamente.

    Por lo tanto, si está trabajando con datos Unicode, consulte la documentación de cada módulo que esté utilizando si hay algún problema con el intercambio de datos Unicode. Si la documentación no habla de Unicode en absoluto, sospeche lo peor y probablemente mire el código fuente para aprender cómo está implementado el módulo. Los módulos escritos completamente en Perl no deberían causar problemas. Los módulos que acceden directa o indirectamente a código escrito en otros lenguajes de programación están en riesgo.

    Para las funciones afectadas, la estrategia simple para evitar la corrupción de datos es hacer siempre explícita la codificación de los datos intercambiados. Elija una codificación que sepa que la extensión puede manejar. Convierta los argumentos pasados a las extensiones a esa codificación y convierta los resultados de vuelta desde esa codificación. Escriba funciones envoltorio que realicen las conversiones por usted, para que pueda cambiar las funciones más tarde cuando la extensión se ponga al día.

    Para proporcionar un ejemplo, digamos que la popular función "Foo::Bar::escape_html" aún no maneja datos Unicode. La función envoltorio convertiría el argumento a UTF-8 crudo y convertiría el resultado de vuelta a la representación interna de Perl de la siguiente manera:

    sub my_escape_html ($) {
    my($what) = shift;
    return unless defined $what;
    Encode::decode("UTF-8", Foo::Bar::escape_html(
                                 Encode::encode("UTF-8", $what)));
}

    A veces, cuando la extensión no convierte datos sino que solo los almacena y recupera, podrá usar la función Encode::_utf8_on(), que de otra manera es peligrosa. Digamos que la popular extensión "Foo::Bar", escrita en C, proporciona un método "param" que le permite almacenar y recuperar datos según estos prototipos:

    $self->param($name, $value);            # establecer un escalar
$value = $self->param($name);           # recuperar un escalar

    Si aún no proporciona soporte para ninguna codificación, se podría escribir una clase derivada con dicho método "param":

    sub param {
  my($self,$name,$value) = @_;
  utf8::upgrade($name);     # asegurarse de que esté codificado en UTF-8
  if (defined $value) {
    utf8::upgrade($value);  # asegurarse de que esté codificado en UTF-8
    return $self->SUPER::param($name,$value);
  } else {
    my $ret = $self->SUPER::param($name);
    Encode::_utf8_on($ret); # sabemos que está codificado en UTF-8
    return $ret;
  }
}

    Algunas extensiones proporcionan filtros en los puntos de entrada/salida de datos, como "DB_File::filter_store_key" y familia. Busque tales filtros en la documentación de sus extensiones; pueden facilitar mucho la transición a datos Unicode.

    Velocidad

    Algunas funciones son más lentas cuando trabajan con cadenas codificadas en UTF-8 que con cadenas codificadas en bytes. Todas las funciones que necesitan saltar sobre caracteres como length(), substr() o index(), o coincidir con expresiones regulares pueden funcionar **mucho** más rápido cuando los datos subyacentes están codificados en bytes.

    En Perl 5.8.0 la lentitud era a menudo bastante espectacular; en Perl 5.8.1 se introdujo un esquema de caché que mejoró la situación. En general, las operaciones con cadenas codificadas en UTF-8 siguen siendo más lentas. Como ejemplo, las propiedades Unicode (clases de caracteres) como "\p{Nd}" son conocidas por ser bastante más lentas (5-20 veces) que sus contrapartes más simples como "[0-9]" (por otro lado, hay cientos de caracteres Unicode que coinciden con "Nd" en comparación con los 10 caracteres ASCII que coinciden con "[0-9]").
