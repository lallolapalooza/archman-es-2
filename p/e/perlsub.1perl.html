NOMBRE

perlsub - Subrutinas de Perl (funciones definidas por el usuario)

SINOPSIS

Para declarar subrutinas:

sub NOMBRE;                       # Una declaración "adelantada".
sub NOMBRE(PROTO);                #  ídem, pero con prototipos
sub NOMBRE : ATTRS;               #  con atributos
sub NOMBRE(PROTO) : ATTRS;        #  con atributos y prototipos
sub NOMBRE BLOQUE                  # Una declaración y una definición.
sub NOMBRE(PROTO) BLOQUE           #  ídem, pero con prototipos
sub NOMBRE : ATTRS BLOQUE          #  con atributos
subNOMBRE(PROTO) : ATTRS BLOQUE   #  con prototipos y atributos
use feature 'signatures';
sub NOMBRE(SIG) BLOQUE                     # con firma
sub NOMBRE :ATRIBUTOS(SIG) BLOQUE             # con firma, atributos
subNOMBRE :prototipo(PROTO) (SIG) BLOQUE  # con firma, prototipo

Para definir una subrutina anónima en tiempo de ejecución:

$ref_sub = sub BLOQUE;                    # sin proto
$ref_sub = sub (PROTO) BLOQUE;            # con proto
$ref_sub = sub : ATTRS BLOQUE;            # con atributos
$ref_sub = sub (PROTO) : ATTRS BLOQUE;    # con proto y atributos
use feature 'signatures';
$ref_sub = sub (SIG) BLOQUE;          # con firma
$ref_sub = sub : ATTRS(SIG) BLOQUE;   # con firma, atributos

Para importar subrutinas:

use MÓDULO qw(NOMBRE1 NOMBRE2 NOMBRE3);

Para llamar a subrutinas:

NOMBRE(LISTA);     # Llamada regular a subrutina.
NOMBRE LISTA;      # Los paréntesis son opcionales si está predeclarada/importada.
&NOMBRE(LISTA);    # Ignorar prototipos.
&NOMBRE;          # Hace que @_ actual sea visible para la subrutina llamada.

DESCRIPCIÓN

Al igual que muchos lenguajes, Perl proporciona subrutinas definidas por el usuario. Estas pueden ubicarse en cualquier lugar del programa principal, cargarse desde otros archivos a través de las palabras clave "do", "require" o "use", o generarse sobre la marcha usando "eval" o subrutinas anónimas. Incluso puede llamar a una función indirectamente usando una variable que contenga su nombre o una referencia de CÓDIGO.

El modelo de Perl para la llamada de funciones y los valores de retorno es simple: todas las funciones se pasan como parámetros en una única lista plana de escalares, y todas las funciones de igual manera devuelven a su llamador una única lista plana de escalares. Cualquier array o hash en estas listas de llamada y retorno colapsará, perdiendo su identidad; pero siempre puede usar paso por referencia en su lugar para evitar esto. Tanto las listas de llamada como las de retorno pueden contener tantos o tan pocos elementos escalares como desee. (A menudo, una función sin una declaración `return` explícita se llama subrutina, pero en realidad no hay ninguna diferencia desde la perspectiva de Perl).

En una subrutina que utiliza firmas (ver "Firmas" abajo), los argumentos se asignan a variables léxicas introducidas por la firma. En la implementación actual de Perl, también son accesibles en el array @_ de la misma manera que para las subrutinas sin firma, pero acceder a ellos de esta manera ahora está desaconsejado dentro de dicha subrutina que usa firmas.

En una subrutina que no utiliza firmas, cualquier argumento pasado aparece en el array @_. Por lo tanto, si llamó a una función con dos argumentos, estos se almacenarían en $_[0] y $_[1]. El array @_ es un array local, pero sus elementos son alias de los parámetros escalares reales. En particular, si un elemento $_[0] se actualiza, el argumento correspondiente se actualiza (o ocurre un error si no es actualizable). Si un argumento es un elemento de array o hash que no existía cuando se llamó a la función, ese elemento se crea solo cuando (y si) se modifica o se toma una referencia a él. (Algunas versiones anteriores de Perl creaban el elemento independientemente de si se le asignaba algo). Asignar al array completo @_ elimina ese aliasing y no actualiza ningún argumento.

Cuando no se utilizan firmas, Perl no proporciona ningún otro medio para crear parámetros formales con nombre. En la práctica, todo lo que hace es asignar a una lista my() de estos. Las variables que no se declaran como privadas son variables globales. Para obtener detalles exhaustivos sobre la creación de variables privadas, consulte "Variables privadas a través de my()" y "Valores temporales a través de local()". Para crear entornos protegidos para un conjunto de funciones en un paquete separado (y probablemente un archivo separado), consulte "Paquetes" en perlmod.

Una declaración "return" puede usarse para salir de una subrutina, especificando opcionalmente el valor de retorno, que se evaluará en el contexto apropiado (lista, escalar o nulo) dependiendo del contexto de la llamada a la subrutina. Si no especifica un valor de retorno, la subrutina devuelve una lista vacía en contexto de lista, el valor indefinido en contexto escalar, o nada en contexto nulo. Si devuelve uno o más agregados (arrays y hashes), estos se aplanarán juntos en una gran lista indistinguible.

Si no se encuentra un "return" y si la última instrucción es una expresión, se devuelve su valor. Si la última instrucción es una estructura de control de bucle como un "foreach" o un "while", el valor de retorno no está especificado. La subrutina vacía devuelve la lista vacía.

Ejemplo:

sub max {
    my $max = shift(@_);
    foreach $foo (@_) {
        $max = $foo if $max < $foo;
    }
    return $max;
}
$mejor_dia = max($lun,$mar,$mie,$jue,$vie);

Ejemplo:

# obtener una línea, combinando líneas de continuación
#  que comienzan con espacio en blanco
sub obtener_linea {
    $esta_linea = $predefinida;  # ¡variables globales!
    LINEA: while (defined($predefinida = <STDIN>)) {
        if ($predefinida =~ /^[ \t]/) {
            $esta_linea .= $predefinida;
        }
        else {
            last LINEA;
        }
    }
    return $esta_linea;
}
$predefinida = <STDIN>;       # obtener la primera línea
while (defined($linea = obtener_linea())) {
    ...
}

Asignar a una lista de variables privadas para nombrar sus argumentos:

sub puede_establecer {
    my($clave, $valor) = @_;
    $Foo{$clave} = $valor unless $Foo{$clave};
}

Debido a que la asignación copia los valores, esto también tiene el efecto de convertir la llamada por referencia en llamada por valor. De lo contrario, una función es libre de realizar modificaciones in situ de @_ y cambiar los valores de su llamador.

mayusculas_en($v1, $v2);  # esto cambia $v1 y $v2
sub mayusculas_en {
    for (@_) { tr/a-z/A-Z/ }
}

Por supuesto, no se le permite modificar constantes de esta manera. Si un argumento fuera realmente literal e intentara cambiarlo, tendría una excepción (presumiblemente fatal). Por ejemplo, esto no funcionará:

mayusculas_en("federico");

Sería mucho más seguro si la función mayusculas_en() estuviera escrita para devolver una copia de sus parámetros en lugar de cambiarlos in situ:

($v3, $v4) = mayusculas($v1, $v2);  # esto no cambia $v1 ni $v2
sub mayusculas {
    return unless defined wantarray;  # contexto nulo, no hacer nada
    my @parms = @_;
    for (@parms) { tr/a-z/A-Z/ }
    return wantarray ? @parms : $parms[0];
}

Observe cómo esta función (sin prototipo) no se preocupa de si se le pasaron escalares reales o arrays. Perl ve todos los argumentos como una única lista de parámetros grande y larga y plana en @_. Esta es un área donde el simple estilo de paso de argumentos de Perl brilla. La función mayusculas() funcionaría perfectamente bien sin cambiar la definición de mayusculas() incluso si le alimentáramos cosas como estas:

@nueva_lista   = mayusculas(@lista1, @lista2);
@nueva_lista   = mayusculas( split /:/, $var );

Sin embargo, no se deje tentar a hacer esto:

(@x, @y)   = mayusculas(@lista1, @lista2);

Al igual que la lista de parámetros de entrada aplanada, la lista de retorno también se aplana al retornar. Por lo tanto, todo lo que ha logrado hacer aquí ha sido almacenar todo en @x y hacer que @y esté vacía. Vea "Paso por Referencia" para ver alternativas.

Una subrutina puede ser llamada usando un prefijo "&" explícito. El "&" es opcional en Perl moderno, al igual que los paréntesis si la subrutina ha sido pre-declarada. El "&" *no* es opcional cuando solo se nombra la subrutina, como cuando se usa como argumento para defined() o undef(). Tampoco es opcional cuando se desea hacer una llamada indirecta a una subrutina con un nombre de subrutina o una referencia usando las construcciones &$ref_sub() o "&{$ref_sub}()", aunque la notación $ref_sub->() resuelve ese problema. Las subrutinas pueden ser llamadas recursivamente. Si una subrutina es llamada usando la forma "&", la lista de argumentos es opcional, y si se omite, no se establece un array @_ para la subrutina: el array @_ en el momento de la llamada es visible para la subrutina en su lugar. Este es un mecanismo de eficiencia que los nuevos usuarios tal vez deseen evitar.

&foo(1,2,3);        # pasa tres argumentos
foo(1,2,3);         # lo mismo
foo();              # pasa una lista de argumentos vacía
&foo();             # lo mismo
&foo;               # foo() recibe los argumentos actuales, ¡como foo(@_)!
use strict 'subs';
foo;                # como foo() si la sub foo predeclarada, si no
                    # un error de tiempo de compilación
no strict 'subs';
foo;                # como foo() si la sub foo predeclarada, si no
                    # una cadena literal "foo"

La forma "&" no solo hace que la lista de argumentos sea opcional, sino que también deshabilita cualquier verificación de prototipo en los argumentos que sí proporcionas. Esto es en parte por razones históricas, y en parte para tener una forma conveniente de hacer trampa si sabes lo que estás haciendo. Ver "Prototypes" más abajo.

Desde Perl 5.16.0, el token "__SUB__" está disponible bajo use feature 'current_sub' y "use v5.16". Se evaluará como una referencia a la subrutina en ejecución, lo que permite llamadas recursivas sin conocer el nombre de tu subrutina.

use v5.16;
my $factorial = sub {
    my ($x) = @_;
    return 1 if $x == 1;
    return($x * __SUB__->( $x - 1 ) );
};

El comportamiento de "__SUB__" dentro de un bloque de código de expresión regular (como "/(?{...})/") está sujeto a cambios.

Firmas

Perl tiene una facilidad para permitir que los parámetros formales de una subrutina sean declarados mediante una sintaxis especial, separada del código procedimental del cuerpo de la subrutina. La lista de parámetros formales se conoce como firma.

Esta facilidad debe ser habilitada antes de que pueda ser utilizada. Se habilita automáticamente mediante una declaración "use v5.36" (o superior), o de forma más directa mediante "use feature 'signatures'", en el ámbito actual.

La firma es parte del cuerpo de una subrutina. Normalmente, el cuerpo de una subrutina es simplemente un bloque de código entre llaves, pero cuando se usa una firma, la firma es una lista entre paréntesis que va inmediatamente antes del bloque, después de cualquier nombre o atributos.

Por ejemplo,

sub foo :lvalue ($x, $y = 1, @z) { .... }

La firma declara variables léxicas que están en ámbito para el bloque. Cuando se llama a la subrutina, la firma toma el control primero. Rellena las variables de la firma a partir de la lista de argumentos que se pasaron. Si la lista de argumentos no cumple los requisitos de la firma, entonces lanzará una excepción. Cuando el procesamiento de la firma se completa, el control pasa al bloque.

Los parámetros posicionales se manejan simplemente nombrando variables escalares en la firma. Por ejemplo,

sub foo ($left, $right) {
    return $left + $right;
}

toma dos parámetros posicionales, que deben ser rellenados en tiempo de ejecución por dos argumentos. Por defecto, los parámetros son obligatorios, y no se permite pasar más argumentos de los esperados. Así que lo anterior es equivalente a

sub foo {
    die "Demasiados argumentos para la subrutina" unless @_ <= 2;
    die "Pocos argumentos para la subrutina" unless @_ >= 2;
    my $left = $_[0];
    my $right = $_[1];
    return $left + $right;
}

Un argumento puede ser ignorado omitiendo la parte principal del nombre de una declaración de parámetro, dejando solo un sigilo desnudo "$". Por ejemplo,

sub foo ($first, $, $third) {
    return "first=$first, third=$third";
}

Aunque el argumento ignorado no va a una variable, sigue siendo obligatorio para el que llama pasarlo.

Un parámetro posicional se hace opcional dándole un valor predeterminado, separado del nombre del parámetro por "=":

sub foo ($left, $right = 0) {
    return $left + $right;
}

La subrutina anterior puede ser llamada con uno o dos argumentos. La expresión del valor predeterminado se evalúa cuando se llama a la subrutina, por lo que puede proporcionar valores predeterminados diferentes para llamadas diferentes. Solo se evalúa si el argumento fue omitido de la llamada. Por ejemplo,

my $auto_id = 0;
sub foo ($thing, $id = $auto_id++) {
    print "$thing tiene ID $id";
}

asigna automáticamente IDs secuenciales distintos a las cosas para las que el llamador no proporcionó un ID. Una expresión de valor predeterminado también puede hacer referencia a parámetros anteriores en la firma, haciendo que el valor predeterminado de un parámetro varíe según los parámetros anteriores. Por ejemplo,

sub foo ($first_name, $surname, $nickname = $first_name) {
    print "$first_name $surname es conocido como \"$nickname\"";
}

Desde Perl 5.38, una expresión de valor predeterminado también puede escribirse usando el operador "//=", donde se evaluará y se usará si el que llama omitió un valor o el valor proporcionado fue "undef".

sub foo ($name //= "world") {
    print "Hola, $name";
}
foo(undef);  # imprimirá "Hola, world"

De manera similar, desde Perl 5.38, el operador "||=" puede usarse para proporcionar una expresión predeterminada a ser usada siempre que el que llama proporcionó un valor falso (y recuerda que un valor faltante o "undef" también son falsos).

sub foo ($x ||= 10) {
    return 5 + $x;
}

Un parámetro opcional

ter puede ser anónimo, al igual que un parámetro obligatorio. Por ejemplo: ```perl sub foo ($cosa, $ = 1) { print $cosa; } ``` El valor predeterminado del parámetro aún se evaluará si no se proporciona el argumento correspondiente, aunque el valor no se almacenará en ningún lugar. Esto es por si la evaluación tiene efectos secundarios importantes. Sin embargo, se evaluará en contexto void, por lo que si no tiene efectos secundarios y no es trivial, generará una advertencia si la categoría de advertencia "void" está habilitada. Si el valor predeterminado de un parámetro opcional anónimo no es importante, se puede omitir al igual que se omitió el nombre del parámetro: ```perl sub foo ($cosa, $=) { print $cosa; } ``` Los parámetros posicionales opcionales deben venir después de todos los parámetros posicionales obligatorios. (Si no hay parámetros posicionales obligatorios, entonces los parámetros posicionales opcionales pueden ser lo primero en la firma). Si hay múltiples parámetros posicionales opcionales y no se proporcionan suficientes argumentos para llenarlos todos, se llenarán de izquierda a derecha. Después de los parámetros posicionales, se pueden capturar argumentos adicionales en un parámetro "slurpy". La forma más simple de esto es simplemente una variable de matriz: ```perl sub foo ($filtro, @entradas) { print $filtro->($_) foreach @entradas; } ``` Con un parámetro "slurpy" en la firma, no hay límite superior en la cantidad de argumentos que se pueden pasar. Un parámetro de matriz "slurpy" puede ser anónimo al igual que un parámetro posicional, en cuyo caso su único efecto es desactivar el límite de argumentos que de otro modo se aplicaría: ```perl sub foo ($cosa, @) { print $cosa; } ``` Un parámetro "slurpy" puede ser en cambio un hash, en cuyo caso los argumentos disponibles para él se interpretan como pares alternos de claves y valores. Debe haber tantas claves como valores: si hay un argumento impar, se lanzará una excepción. Las claves se convertirán en cadenas y, si hay duplicados, la instancia posterior prevalecerá sobre la anterior, como en la construcción estándar de hash. ```perl sub foo ($filtro, %entradas) { print $filtro->($_, $entradas{$_}) foreach sort keys %entradas; } ``` Un parámetro de hash "slurpy" puede ser anónimo al igual que otros tipos de parámetros. Aún insiste en que el número de argumentos disponibles para él sea par, aunque no se estén colocando en una variable. ```perl sub foo ($cosa, %) { print $cosa; } ``` Un parámetro "slurpy", ya sea de matriz o de hash, debe ser lo último en la firma. Puede seguir a los parámetros posicionales obligatorios y opcionales; también puede ser lo único en la firma. Los parámetros "slurpy" no pueden tener valores predeterminados: si no se proporcionan argumentos para ellos, se obtiene una matriz vacía o un hash vacío. Una firma puede estar completamente vacía, en cuyo caso su único propósito es verificar que el llamador no pasó ningún argumento: ```perl sub foo () { return 123; } ``` Antes de Perl 5.36, se consideraban experimentales y emitían una advertencia en la categoría `"experimental::signatures"`. A partir de Perl 5.36, esto ya no ocurre, aunque la categoría de advertencia todavía existe para la retrocompatibilidad con código que intenta deshabilitarla con una declaración como: ```perl no warnings 'experimental::signatures'; ``` En la implementación actual de Perl, cuando se utiliza una firma, los argumentos también están disponibles en la variable especial de matriz `@_`. Sin embargo, acceder a ellos a través de esta matriz ahora está desaconsejado y no debe confiarse en él en código nuevo, ya que esta capacidad puede cambiar en una versión futura. El código que intente acceder a la matriz `@_` generará advertencias en la categoría `"experimental::args_array_with_signatures"` al compilar: ```perl sub f ($x) { # Esta línea emite la advertencia que se ve a continuación print "Los argumentos son @_"; } ``` ``` Uso de @_ en join o cadena con subrutina con firma es experimental en ... ``` Hay una diferencia entre las dos formas de acceder a los argumentos: `@_` *aliasing* los argumentos, pero las variables de firma obtienen *copias* de los argumentos. Por lo tanto, escribir en una variable de firma solo cambia esa variable y no tiene ningún efecto en las variables del llamador, pero escribir en un elemento de `@_` modifica lo que sea que el llamador usó para proporcionar ese argumento. Existe una posible ambigüedad sintáctica entre las firmas y los prototipos (ver "Prototypes"), ya que ambos comienzan con un paréntesis de apertura y ambos pueden aparecer en algunos de los mismos lugares, como justo después del nombre en una declaración de subrutina. Por razones históricas, cuando las firmas no están habilitadas, cualquier paréntesis de apertura en dicho contexto activará un análisis de prototipos muy flexible. La mayoría de las firmas se interpretarán como prototipos en esas circunstancias, pero no serán prototipos válidos. (Un prototipo válido no puede contener ningún carácter alfabético). Esto conducirá a mensajes de error algo confusos. Para evitar ambigüedades, cuando las firmas están habilitadas, se desactiva la sintaxis especial para prototipos. No se intenta adivinar si un grupo entre paréntesis estaba destinado a ser un prototipo o una firma. Para dar a una subrutina un prototipo en estas circunstancias, use un atributo de prototipo. Por ejemplo: ```perl sub foo :prototype($) { $_[0] } ``` Es totalmente posible que una subrutina tenga tanto un prototipo como una firma. Realizan trabajos diferentes: el prototipo afecta la compilación de las llamadas a la subrutina, y la firma pone los valores de los argumentos en variables léxicas en tiempo de ejecución. Por lo tanto, puede escribir: ```perl sub foo :prototype($$) ($izquierda, $derecha) { return $izquierda + $derecha; } ``` El atributo de prototipo, y cualquier otro atributo, debe venir antes de la firma. La firma precede inmediatamente al bloque del cuerpo de la subrutina.

Variables Privadas a través de my()

Sinopsis:

my $foo;            # declara $foo local léxicamente
my (@wid, %get);    # declara lista de variables locales
my $foo = "flurp";  # declara $foo léxico y lo inicializa
my @oof = @bar;     # declara @oof léxico y lo inicializa
my $x : Foo = $y;   # similar, con un atributo aplicado

ADVERTENCIA: El uso de listas de atributos en declaraciones de "my" aún está evolucionando. La semántica y la interfaz actuales están sujetas a cambios. Consulte atributos y Attribute::Handlers.

El operador "my" declara que las variables listadas están confinadas léxicamente al bloque envolvente, condicional ("if"/"unless"/"elsif"/"else"), bucle ("for"/"foreach"/"while"/"until"/"continue"), subrutina, "eval", o archivo "do"/"require"/"use"'d. Si se enumera más de un valor, la lista debe colocarse entre paréntesis. Todos los elementos enumerados deben ser lvalues legales. Solo los identificadores alfanuméricos pueden tener alcance léxico; los "magical built-ins" como $/ actualmente deben ser "local"izados con "local" en su lugar para limitar su alcance dinámicamente.

A diferencia de las variables globales o de paquete localizadas por el operador "local", las variables léxicas declaradas con "my" están totalmente ocultas del mundo exterior, incluidas las subrutinas llamadas. Esto es cierto si es la misma subrutina llamada desde sí misma o desde otro lugar; cada llamada obtiene su propia copia.

Esto no significa que una variable "my" declarada en un ámbito léxico estáticamente envolvente sería invisible. Solo los ámbitos dinámicos se cortan. Por ejemplo, la función bumpx() a continuación tiene acceso a la variable léxica $x porque tanto el "my" como el "sub" ocurrieron en el mismo ámbito, presumiblemente el ámbito del archivo.

my $x = 10;
sub bumpx { $x++ }

Sin embargo, un eval() puede ver las variables léxicas del ámbito en el que se está evaluando, siempre que los nombres no estén ocultos por declaraciones dentro del propio eval(). Ver perlref.

La lista de parámetros para my() se puede asignar si se desea, lo que le permite inicializar sus variables. (Si no se proporciona inicializador para una variable determinada, se crea con el valor indefinido). Comúnmente se usa para nombrar parámetros de entrada para una subrutina. Ejemplos:

$arg = "fred";          # variable "global"
$n = cube_root(27);
print "$arg piensa que la raíz es $n\n";

sub cube_root {

El "my" es simplemente un modificador sobre algo a lo que se puede asignar. Por lo tanto, cuando se asigna a variables en su lista de argumentos, "my" no cambia si esas variables se ven como escalares o matrices. Entonces:

my ($foo) = <STDIN>;                # ¿INCORRECTO?
my @FOO = <STDIN>;

ambos proporcionan un contexto de lista al lado derecho, mientras que:

my $foo = <STDIN>;

proporciona un contexto escalar. Pero lo siguiente declara solo una variable:

my $foo, $bar = 1;                  # INCORRECTO

Eso tiene el mismo efecto que:

my $foo;
$bar = 1;

La variable declarada no se introduce (no es visible) hasta después de la declaración actual. Por lo tanto:

my $x = $x;

se puede usar para inicializar un nuevo $x con el valor del $x antiguo, y la expresión

my $x = 123 and $x == 123

es falsa a menos que el $x antiguo haya tenido casualmente el valor 123.

Lexical Scoping

A variable declared with "my" is lexically scoped. This means that its scope extends from its declaration through the rest of that conditional, including any "elsif" and "else" clauses, but not beyond it. See "Simple Statements" in perlsyn for information on the scope of variables in statements with modifiers.

The "foreach" loop defaults to scoping its index variable dynamically in the manner of "local". However, if the index variable is prefixed with the keyword "my", or if there is already a lexical by that name in scope, then a new lexical is created instead. Thus in the loop

for my $i (1, 2, 3) {
    some_function();
}

the scope of $i extends to the end of the loop, but not beyond it, rendering the value of $i inaccessible within some_function().

Some users may wish to encourage the use of lexically scoped variables. As an aid to catching implicit uses to package variables, which are always global, if you say

use strict 'vars';

then any variable mentioned from there to the end of the enclosing block must either refer to a lexical variable, be predeclared via "our" or "use vars", or else must be fully qualified with the package name. A compilation error results otherwise. An inner block may countermand this with "no strict 'vars'".

A "my" has both a compile-time and a run-time effect. At compile time, the compiler takes notice of it. The principal usefulness of this is to quiet "use strict 'vars'", but it is also essential for generation of closures as detailed in perlref. Actual initialization is delayed until run time, though, so it gets executed at the appropriate time, such as each time through a loop, for example.

Variables declared with "my" are not part of any package and are therefore never fully qualified with the package name. In particular, you're not allowed to try to make a package variable (or other global) lexical:

my $pack::var;      # ERROR!  Illegal syntax

In fact, a package or global variable is still accessible using the fully qualified "::" notation even while a lexical of the same name is also visible:

package main;
our $x = 10;
my  $x = 20;
print "$x and $::x\n";

That will print out 20 and 10.

You may declare "my" variables at the outermost scope of a file to hide any such identifiers from the world outside that file. This is similar in spirit to C's static variables when they are used at the file level. To do this with a subroutine requires the use of a closure (an anonymous function that accesses enclosing lexicals). If you want to create a private subroutine that cannot be called from outside that block, it can declare a lexical variable containing an anonymous sub reference:

my $secret_version = '1.001-beta';
my $secret_sub = sub { print $secret_version };
$secret_sub->();

As long as the reference is never returned by any function within the module, no outside module can see the subroutine, because its name is not in any package's symbol table. Remember that it's not REALLY called $some_pack::secret_version or anything; it's just $secret_version, unqualified and unqualifiable.

This does not work with object methods, however; all object methods have to be in the symbol table of some package to be found. See "Function Templates" in perlref for something of a work-around to this.

Persistent Private Variables

There are two ways to build persistent private variables in Perl 5.10. First, you can simply use the "state" feature. Or, you can use closures, if you want to stay compatible with releases older than 5.10.

Persistent variables via state()

Beginning with Perl 5.10.0, you can declare variables with the "state" keyword in place of "my". For that to work, though, you must have enabled that feature beforehand, either by using the "feature" pragma, or by using "-E" on one-liners (see feature). Beginning with Perl 5.16, the "CORE::state" form does not require the "feature" pragma.

The "state" keyword creates a lexical variable (following the same scoping rules as "my") that persists from one subroutine call to the next. If a state variable resides inside an anonymous subroutine, then each copy of the subroutine has its own copy of the state variable. However, the value of the state variable will still persist between calls to the same copy of the anonymous subroutine. (Don't forget that "sub { ... }" creates a new subroutine each time it is executed.)

For example, the following code maintains a private counter, incremented each time the gimme_another() function is called:

use feature 'state';
sub gimme_another { state $x; return ++$x }

And this example uses anonymous subroutines to create separate counters:

use feature 'state';
sub create_counter {
    return sub { state $x; return ++$x }
}

Also, since $x is lexical, it can't be reached or modified by any Perl code outside.

When combined with variable declaration, simple assignment to "state" variables (as in "state $x = 42") is executed only the first time. When such statements are evaluated subsequent times, the assignment is ignored. The behavior of assignment to "state" declarations where the left hand side of the assignment involves any parentheses is currently undefined.

Persistent variables with closures

Just because a lexical variable is lexically (also called statically) scoped to its enclosing block, "eval", or "do" FILE, this doesn't mean that within a function it works like a C static. It normally works more like a C auto, but with implicit garbage collection.

Unlike local variables in C or C++, Perl's lexical variables don't necessarily get recycled just because their scope has exited. If something more permanent is still aware of the lexical, it will stick around. So long as something else references a lexical, that lexical won't be freed--which is as it should be. You wouldn't want memory being free until you were done using it, or kept around once you were done. Automatic garbage collection takes care of this for you.

This means that you can pass back or save away references to lexical variables, whereas to return a pointer to a C auto is a grave error. It also gives us a way to simulate C's function statics. Here's a mechanism for giving a function private variables with both lexical scoping and a static lifetime. If you do want to create something like C's static variables, just enclose the whole function in an extra block, and put the static variable outside the function but in the block.

{
    my $secret_val = 0;
    sub gimme_another {
        return ++$secret_val;
    }
}

# $secret_val now becomes unreachable by the outside # world, but retains its value between calls to gimme_another

If this function is being sourced in from a separate file via "require" or "use", then this is probably just fine. If it's all in the main program, you'll need to arrange for the "my" to be executed early, either by putting the whole block above your main program, or more likely, placing merely a "BEGIN" code block around it to make sure it gets executed before your program starts to run:

BEGIN {
    my $secret_val = 0;
    sub gimme_another {
        return ++$secret_val;
    }
}

See "BEGIN, UNITCHECK, CHECK, INIT and END" in perlmod about the special triggered code blocks, "BEGIN", "UNITCHECK", "CHECK", "INIT" and "END".

If declared at the outermost scope (the file scope), then lexicals work somewhat like C's file statics. They are available to all functions in that same file declared below them, but are inaccessible from outside that file. This strategy is sometimes used in modules to create private variables that the whole module can see.

Temporary Values via local()

WARNING: In general, you should be using "my" instead of "local", because it's faster and safer. Exceptions to this include the global punctuation variables, global filehandles and formats, and direct manipulation of the Perl symbol table itself. "local" is mostly used when the current value of a variable must be visible to called subroutines.

Synopsis:

# localization of values
local $foo;                # make $foo dynamically local
local (@wid, %get);        # make list of variables local
local $foo = "flurp";      # make $foo dynamic, and init it
local @oof = @bar;         # make @oof dynamic, and init it
local $hash{key} = "val";  # sets a local value for this hash entry
delete local $hash{key};   # delete this entry for the current block
local ($cond ? $v1 : $v2); # several types of lvalues support
                           # localization
# localization of symbols
local *FH;                 # localize $FH, @FH, %FH, &FH  ...
local *merlyn = *randal;   # now $merlyn is really $randal, plus
                           #     @merlyn is really @randal, etc
local *merlyn = 'randal';  # SAME THING: promote 'randal' to *randal
local *merlyn = \$randal;  # just alias $merlyn, not @merlyn etc

A "local" modifies its listed variables to be "local" to the enclosing block, "eval", or "do FILE"--and to any subroutine called from within that block. When the block is exited, the variables revert to their previous values (or lack thereof). This form of localization is dynamic scoping, not lexical scoping. In particular, the values of variables are visible to subroutines called during the execution of the block, even if those subroutines are defined outside the block.

The "local" keyword is used to create temporary values. If you say "local($x = 5)", then $x is set to 5 within the current scope, and its original value is restored when the scope is exited. The important point is that if you call a subroutine within that scope, that subroutine will see the local value of $x.

When you localize a symbol table entry (using "local *name"), it localizes all variables associated with that name (e.g., $name, @name, %name, &name, etc.).

You can also localize a symbol table entry to another: "local *merlyn = *randal;" makes merlyn's symbol table entry an alias for randal's. Any changes to one (like $merlyn = 1) affect the other.

You can also localize a symbol table entry to a specific scalar variable: "local *merlyn = \$randal;" makes $merlyn an alias for $randal, but leaves @merlyn, %merlyn, etc., unaffected. Note that the scalar must be passed by reference.

It is also possible to localize a hash or array element, or a slice thereof. The value set by the "local" operation is temporary. However, unlike a simple "local $scalar", this doesn't restore a previous value; it merely ensures that the specified hash element or array element (or slice) is deleted when the scope is exited.

For example:

local $hash{key} = "original";
print "Before: $hash{key}\n";
{
    local $hash{key} = "new";
    print "Inside: $hash{key}\n";
}
print "After: $hash{key}\n";

This prints:

Before: original
Inside: new
After: original

If you use "delete local $hash{key}", the key is deleted for the duration of the block. This is useful for temporarily disabling a hash key that might otherwise be magically created by some module or AUTOLOAD function.

The "local" keyword can also be applied to various other lvalues, including the results of dereferencing symbol table entries (e.g., "local ${ *foo{SCALAR} } = 1;"). See "Symbol Table API" in perlfunc.

WARNING: Because "local" works by dynamically saving and restoring values, it is significantly slower than "my". Furthermore, dynamically scoped variables are a common source of bugs, especially in larger programs. You should therefore prefer "my" whenever possible.

LOCAL

A "local" is a special operator that is used to give temporary values to global (meaning package) variables. It affects the variable for the duration of the enclosing block, subroutine, or eval. It is very similar in operation to "my", but it is dynamically scoped rather than lexically scoped. It is also much less efficient than "my".

"local" makes a copy of the variable's value before the block, and restores the original value when the block is exited. This means that any subroutines called from within that block will see the new, temporary value. A "local" just gives temporary values to global (meaning package) variables. It does not create a local variable. This is known as dynamic scoping. Lexical scoping is done with "my", which works more like C's auto declarations.

Some types of lvalues can be localized as well: hash and array elements and slices, conditionals (provided that their result is always localizable), and symbolic references. As for simple variables, this creates new, dynamically scoped values.

If more than one variable or expression is given to "local", they must be placed in parentheses. This operator works by saving the current values of those variables in its argument list on a hidden stack and restoring them upon exiting the block, subroutine, or eval. This means that called subroutines can also reference the local variable, but not the global one. The argument list may be assigned to if desired, which allows you to initialize your local variables. (If no initializer is given for a particular variable, it is created with an undefined value.)

Because "local" is a run-time operator, it gets executed each time through a loop. Consequently, it's more efficient to localize your variables outside the loop.

Grammatical note on local()

A "local" is simply a modifier on an lvalue expression. When you assign to a "local"ized variable, the "local" doesn't change whether its list is viewed as a scalar or an array. So

local($foo) = <STDIN>;
local @FOO = <STDIN>;

both supply a list context to the right-hand side, while

local $foo = <STDIN>;

supplies a scalar context.

Localization of special variables

If you localize a special variable, you'll be giving a new value to it, but its magic won't go away. That means that all side-effects related to this magic still work with the localized value.

This feature allows code like this to work :

# Read the whole contents of FILE in $slurp
{ local $/ = undef; $slurp = <FILE>; }

Note, however, that this restricts localization of some values ; for example, the following statement dies, as of Perl 5.10.0, with an error Modification of a read-only value attempted, because the $1 variable is magical and read-only :

local $1 = 2;

One exception is the default scalar variable: starting with Perl 5.14 local($_) will always strip all magic from $_, to make it possible to safely reuse $_ in a subroutine.

WARNING: Localization of tied arrays and hashes does not currently work as described. This will be fixed in a future release of Perl; in the meantime, avoid code that relies on any particular behavior of localising tied arrays or hashes (localising individual elements is still okay). See "Localising Tied Arrays and Hashes Is Broken" in perl58delta for more details.

Localization of globs

The construct

local *name;

creates a whole new symbol table entry for the glob "name" in the current package. That means that all variables in its glob slot ($name, @name, %name, &name, and the "name" filehandle) are dynamically reset.

This implies, among other things, that any magic eventually carried by those variables is locally lost. In other words, saying "local */" will not have any effect on the internal value of the input record separator.

Localization of elements of composite types

It's also worth taking a moment to explain what happens when you "local"ize a member of a composite type (i.e. an array or hash element). In this case, the element is "local"ized by name. This means that when the scope of the local() ends, the saved value will be restored to the hash element whose key was named in the local(), or the array element whose index was named in the local(). If that element was deleted while the local() was in effect (e.g. by a delete() from a hash or a shift() of an array), it will spring back into existence, possibly extending an array and filling in the skipped elements with "undef". For instance, if you say

%hash = ( 'This' => 'is', 'a' => 'test' );
@ary  = ( 0..5 );
{
    local($ary[5]) = 6;
    local($hash{'a'}) = 'drill';
    while (my $e = pop(@ary)) {
        print "$e . . .\n";
        last unless $e > 3;
    }
    if (@ary) {
        $hash{'only a'} = 'test';
        delete $hash{'a'};
    }
}
print join(' ', map { "$_ $hash{$_}" } sort keys %hash),".\n";
print "The array has ",scalar(@ary)," elements: ",
    join(', ', map { defined $_ ? $_ : 'undef' } @ary),"\n";

Perl will print

6 . . .
4 . . .
3 . . .
This is a test only a test.
The array has 6 elements: 0, 1, 2, undef, undef, 5

The behavior of local() on non-existent members of composite types is subject to change in future. The behavior of local() on array elements specified using negative indexes is particularly surprising, and is very likely to change.

Localized deletion of elements of composite types

You can use the "delete local $array[$idx]" and "delete local $hash{key}" constructs to delete a composite type entry for the current block and restore it when it ends. They return the array/hash value before the localization, which means that they are respectively equivalent to

do {
    my $val = $array[$idx];
    local  $array[$idx];
    delete $array[$idx];
    $val
}

and

do {
    my $val = $hash{key};
    local  $hash{key};
    delete $hash{key};
    $val
}

except that for those the "local" is scoped to the "do" block. Slices are also accepted.

my %hash = (
    a => [ 7, 8, 9 ],
    b => 1,
)
{
    my $x = delete local $hash{a};
    # $x is [ 7, 8, 9 ]
    # %hash is (b => 1)
    {
        my @nums = delete local @$x[0, 2]
        # @nums is (7, 9)
        # $x is [ undef, 8 ]
        $x[0] = 999; # will be erased when the scope ends
    }
    # $x is back to [ 7, 8, 9 ]
}
# %hash is back to its original state

This construct is supported since Perl v5.12.

Lvalue subroutines

It is possible to return a modifiable value from a subroutine. To do this, you have to declare the subroutine to return an lvalue.

my $val;
sub canmod : lvalue {
    $val;  # or:  return $val;
}
sub nomod {
    $val;
}
canmod() = 5;   # assigns to $val
nomod()  = 5;   # ERROR

The scalar/list context for the subroutine and for the right-hand side of assignment is determined as if the subroutine call is replaced by a scalar. For example, consider:

data(2,3) = get_data(3,4);

Both subroutines here are called in a scalar context, while in:

(data(2,3)) = get_data(3,4);

and in:

(data(2),data(3)) = get_data(3,4);

all the subroutines are called in a list context.

Lvalue subroutines are convenient, but you have to keep in mind that, when used with objects, they may violate encapsulation. A normal mutator can check the supplied argument before setting the attribute it is protecting, an lvalue subroutine cannot. If you require any special processing when storing and retrieving the values, consider using the CPAN module Sentinel or something similar.

Lexical Subroutines

Beginning with Perl 5.18, you can declare a private subroutine with "my" or "state". As with state variables, the "state" keyword is only available under "use feature 'state'" or "use v5.10" or higher.

Prior to Perl 5.26, lexical subroutines were deemed experimental and were available only under the "use feature 'lexical_subs'" pragma. They also produced a warning unless the "experimental::lexical_subs" warnings category was disabled.

These subroutines are only visible within the block in which they are declared, and only after that declaration:

# Include these two lines if your code is intended to run under Perl
# versions earlier than 5.26.
no warnings "experimental::lexical_subs";
use feature 'lexical_subs';
foo();              # calls the package/global subroutine
state sub foo {
    foo();          # also calls the package subroutine
}
foo();              # calls "state" sub
my $ref = \&foo;    # take a reference to "state" sub
my sub bar { ... }
bar();              # calls "my" sub

You can't (directly) write a recursive lexical subroutine:

# WRONG
my sub baz {
    baz();
}

This example fails because baz() refers to the package/global subroutine "baz", not the lexical subroutine currently being defined.

The solution is to use "__SUB__":

my sub baz {
    __SUB__->();    # calls itself
}

It is possible to predeclare a lexical subroutine. The "sub foo {...}" subroutine definition syntax respects any previous "my sub;" or "state sub;" declaration. Using this to define recursive subroutines is a bad idea, however:

my sub baz;         # predeclaration
sub baz {           # define the "my" sub
    baz();          # WRONG: calls itself, but leaks memory
}

Just like "my $f; $f = sub { $f->() }", this example leaks memory. The name "baz" is a reference to the subroutine, and the subroutine uses the name "baz"; they keep each other alive (see "Circular References" in perlref).

"state sub" vs

"my" subs

¿Cuál es la diferencia entre las subrutinas "state" y las "my"? Cada vez que la ejecución entra en un bloque cuando se declaran subrutinas "my", se crea una nueva copia de cada subrutina. Las subrutinas "state" persisten de una ejecución del bloque contenedor a la siguiente.

Por lo tanto, en general, las subrutinas "state" son más rápidas. Pero las subrutinas "my" son necesarias si quieres crear cierres (closures):

sub whatever {
    my $x = shift;
    my sub inner {
        ... haz algo con $x ...
    }
    inner();
}

En este ejemplo, se crea un nuevo $x cuando se llama a "whatever", y también un nuevo "inner", que puede ver el nuevo $x. Una subrutina "state" solo verá el $x de la primera llamada a "whatever".

Subrutinas "our"

Al igual que "our $variable", "our sub" crea un alias léxico a la subrutina del paquete del mismo nombre.

Los dos usos principales para esto son cambiar de nuevo al uso de la subrutina del paquete dentro de un ámbito interno:

sub foo { ... }
sub bar {
    my sub foo { ... }
    {
        # necesita usar el foo externo aquí
        our sub foo;
        foo();
    }
}

y hacer que una subrutina sea visible para otros paquetes en el mismo ámbito:

package MySneakyModule;
our sub do_something { ... }
sub do_something_with_caller {
    package DB;
    () = caller 1;          # establece @DB::args
    do_something(@args);    # usa MySneakyModule::do_something
}

Paso de Entradas de Tabla de Símbolos (typeglobs)

ADVERTENCIA: El mecanismo descrito en esta sección fue originalmente la única forma de simular el paso por referencia en versiones anteriores de Perl. Si bien todavía funciona bien en versiones modernas, el nuevo mecanismo de referencias es generalmente más fácil de usar. Ver más abajo.

A veces, no quieres pasar el valor de un array a una subrutina, sino su nombre, para que la subrutina pueda modificar la copia global en lugar de trabajar con una copia local. En Perl puedes referirte a todos los objetos de un nombre particular prefijando el nombre con una estrella: *foo. Esto a menudo se conoce como "typeglob", porque la estrella al frente puede pensarse como un comodín que coincide con todos los caracteres de prefijo divertidos en variables y subrutinas, etc.

Cuando se evalúa, el typeglob produce un valor escalar que representa todos los objetos de ese nombre, incluido cualquier manejador de archivo, formato o subrutina. Cuando se le asigna, hace que el nombre mencionado se refiera a cualquier valor de "*" que se le haya asignado. Ejemplo:

sub doubleary {
    local(*someary) = @_;
    foreach $elem (@someary) {
        $elem *= 2;
    }
}
doubleary(*foo);
doubleary(*bar);

Los escalares ya se pasan por referencia, por lo que puedes modificar los argumentos escalares sin usar este mecanismo refiriéndote explícitamente a $_[0], etc. Puedes modificar todos los elementos de un array pasando todos los elementos como escalares, pero tienes que usar el mecanismo de "*" (o el mecanismo de referencia equivalente) para "push", "pop", o cambiar el tamaño de un array. Ciertamente será más rápido pasar el typeglob (o la referencia).

Incluso si no quieres modificar un array, este mecanismo es útil para pasar múltiples arrays en una sola LISTA, porque normalmente el mecanismo de LISTA fusiona todos los valores del array para que no puedas extraer los arrays individuales. Para más información sobre typeglobs, consulta "Typeglobs y manejadores de archivos" en perldata.

Cuándo seguir usando local()

A pesar de la existencia de "my", todavía hay tres lugares donde el operador "local" todavía brilla. De hecho, en estos tres lugares, *debes* usar "local" en lugar de "my".

1.
Necesitas darle a una variable global un valor temporal, especialmente a $_.

Las variables globales, como @ARGV o las variables de puntuación, deben ser "local"izadas con local(). Este bloque lee el archivo /etc/motd, y lo divide en fragmentos separados por líneas de signos iguales, que se colocan en @Fields.

{
    local @ARGV = ("/etc/motd");
    local $/ = undef;
    local $_ = <>;
    @Fields = split /^\s*=+\s*$/;
}

En particular, es importante "local"izar $_ en cualquier rutina que le asigne un valor. Ten cuidado con las asignaciones implícitas en los condicionales "while".

2.
Necesitas crear un manejador de archivos o directorios local o una función local.

Una función que necesita su propio manejador de archivos debe usar local() en un typeglob completo. Esto se puede usar para crear nuevas entradas de tabla de símbolos:

sub ioqueue {
    local  (*READER, *WRITER);    # ¡no my!
    pipe    (READER,  WRITER)     or die "pipe: $!";
    return (*READER, *WRITER);
}
($head, $tail) = ioqueue();

Consulta el módulo Symbol para ver una forma de crear entradas de tabla de símbolos anónimas.

Dado que la asignación de una referencia a un typeglob crea un alias, esto se puede usar para crear lo que es efectivamente una función local, o al menos, un alias local.

{
    local *grow = \&shrink; # solo hasta que este bloque termine
    grow();                # realmente llama a shrink()
    move();                # si move() grow(), también shrink()
}
grow();                    # vuelve a obtener el grow() real

Consulta "Plantillas de funciones" en perlref para obtener más información sobre la manipulación de funciones por nombre de esta manera.

3.
Quieres cambiar temporalmente solo un elemento de un array o hash.

Puedes "local"izar solo un elemento de un agregado. Normalmente esto se hace en dinámicas:

{
    local $SIG{INT} = 'IGNORE';
    funct();                            # no interrumptible
}
# la interrupción se restaura automáticamente aquí

Pero también funciona en agregados declarados léxicamente.

Paso por Referencia

Si quieres pasar más de un array o hash a una función -o devolverlos desde ella- y que mantengan su integridad, entonces vas a tener que usar un paso por referencia explícito. Antes de hacer eso, necesitas entender las referencias como se detalla en perlref. Esta sección puede no tener mucho sentido para ti de lo contrario.

Aquí hay algunos ejemplos simples. Primero, pasemos varios arrays a una función y hagamos que extraigan todos de ellos, devolviendo una nueva lista de todos sus últimos elementos:

@tailings = popmany ( \@w, \@x, \@y, \@z );
sub popmany {
    my $aref;
    my @retlist;
    foreach $aref ( @_ ) {
        push @retlist, pop @$aref;
    }
    return @retlist;
}

Así es como podrías escribir una función que devuelve una lista de claves que ocurren en todos los hashes que se le pasan:

@common = inter( \%foo, \%bar, \%joe );
sub inter {
    my ($k, $href, %seen); # locales
    foreach $href (@_) {
        while ( $k = each %$href ) {
            $seen{$k}++;
        }
    }
    return grep { $seen{$_} == @_ } keys %seen;
}

Hasta ahora, estamos usando solo el mecanismo normal de retorno de lista. ¿Qué pasa si quieres pasar o devolver un hash? Bueno, si solo usas uno de ellos, o no te importa que se concatenen, entonces la convención de llamada normal está bien, aunque un poco costosa.

Donde la gente se mete en problemas es aquí:

    (@w, @x) = func(@y, @z);
o
    (%w, %x) = func(%y, %z);

Esa sintaxis simplemente no funcionará. Establece solo @w o %w y borra @x o %x. Además, la función no recibió dos arrays o hashes separados: recibió una lista larga en @_, como siempre.

Si puedes organizar para que todos traten con esto a través de referencias, es un código más limpio, aunque no tan agradable a la vista. Aquí tienes una función que toma dos referencias de array como argumentos, devolviendo los dos elementos del array en orden según la cantidad de elementos que tienen:

($wref, $xref) = func(\@y, \@z);
print "@$wref tiene más que @$xref\n";
sub func {
    my ($yref, $zref) = @_;
    if (@$yref > @$zref) {
        return ($yref, $zref);
    } else {
        return ($zref, $yref);
    }
}

Resulta que en realidad también puedes hacer esto:

(*w, *x) = func(\@y, \@z);
print "@w tiene más que @x\n";
sub func {
    local (*y, *z) = @_;
    if (@y > @z) {
        return (\@y, \@z);
    } else {
        return (\@z, \@y);
    }
}

Aquí estamos usando los typeglobs para hacer alias de tabla de símbolos. Sin embargo, es un poco sutil, y tampoco funcionará si estás usando variables "my", porque solo los globales (incluso disfrazados de "local"s) están en la tabla de símbolos.

Si estás pasando manejadores de archivos, generalmente podrías usar el typeglob desnudo, como *STDOUT, pero las referencias a typeglobs también funcionan. Por ejemplo:

splutter(\*STDOUT);
sub splutter {
    my $fh = shift;
    print $fh "her um well a hmmm\n";
}
$rec = get_rec(\*STDIN);
sub get_rec {
    my $fh = shift;
    return scalar <$fh>;
}

Si planeas generar nuevos manejadores de archivos, podrías hacer esto. Nota que para devolver solo el *FH desnudo, no su referencia.

sub openit {
    my $path = shift;
    local *FH;
    return open (FH, $path) ? *FH : undef;
}

Perl admite un tipo muy limitado de verificación de argumentos en tiempo de compilación utilizando prototipos de funciones. Esto se puede declarar en la sección PROTO o con un atributo de prototipo. Si declaras alguno de los siguientes:

sub mypush (\@@)
sub mypush :prototype(\@@)

entonces mypush() toma argumentos exactamente como lo hace push().

Prototypes

Si las firmas ("Signatures") están habilitadas, entonces la sintaxis más corta PROTO no está disponible, porque entraría en conflicto con las firmas. En ese caso, un prototipo solo se puede declarar en forma de atributo.

La declaración de la función debe ser visible en tiempo de compilación. El prototipo solo afecta la interpretación de las llamadas regulares a la función, donde regular se define como no usar el sigilo "&". En otras palabras, si la llamas como una función incorporada, entonces se comporta como una función incorporada. Si la llamas como una subrutina al viejo estilo (perl4), entonces se comporta como una subrutina al viejo estilo. De esta regla se desprende naturalmente que los prototipos no tienen influencia en las referencias a subrutinas como "\&foo" o en las llamadas indirectas a subrutinas como "&{$subref}()" o $subref->().

Las llamadas a métodos tampoco se ven influenciadas por los prototipos, porque la función a llamar es indeterminada en tiempo de compilación, ya que el código exacto llamado depende de la herencia.

Dado que la intención de esta característica es principalmente permitirle definir subrutinas que funcionen como funciones incorporadas, aquí hay prototipos para algunas otras funciones que se analizan casi exactamente como las incorporadas correspondientes.

Cualquier carácter de prototipo con barra invertida representa un argumento real que debe comenzar con ese carácter (opcionalmente precedido por "my", "our" o "local"), con la excepción de "$", que aceptará cualquier expresión lvalue escalar, como "$foo = 7" o "my_function()->[0]". El valor pasado como parte de @_ será una referencia al argumento real dado en la llamada a la subrutina, obtenido aplicando "\" a ese argumento.

Puedes usar la notación de grupo de barras invertidas "\[]" para especificar más de un tipo de argumento permitido. Por ejemplo:

permitirá llamar a myref() como

y el primer argumento de myref() será una referencia a un escalar, un array, un hash, una subrutina o un glob.

Los caracteres de prototipo sin barra invertida tienen significados especiales. Cualquier "@" o "%" sin barra invertida consume todos los argumentos restantes y fuerza el contexto de lista. Un argumento representado por "$" fuerza el contexto escalar. Un "&" requiere una subrutina anónima, que, si se pasa como primer argumento, puede parecer un bloque desnudo: no requiere la palabra clave "sub" ni una coma posterior.

Un "*" permite que la subrutina acepte un bareword, una constante, una expresión escalar, un typeglob o una referencia a un typeglob en esa posición. El valor estará disponible para la subrutina ya sea como un escalar simple, o (en los dos últimos casos) como una referencia al typeglob. Si deseas convertir siempre dichos argumentos a una referencia de typeglob, utiliza Symbol::qualify_to_ref() de la siguiente manera:

use Symbol 'qualify_to_ref';

    ...
}

El prototipo "+" es una alternativa especial a "$" que actuará como "\[@%]" cuando se le da una variable de array o hash literal, pero de lo contrario forzará el contexto escalar en el argumento. Esto es útil para funciones que deben aceptar un array literal o una referencia a un array como argumento:

    push @$aref, @_;

Un punto y coma (";") separa los argumentos obligatorios de los opcionales. Es redundante antes de "@" o "%", que consumen todo lo demás.

Como último carácter de un prototipo, o justo antes de un punto y coma, un "@" o un "%", puedes usar "_" en lugar de "$": si este argumento no se proporciona, se utilizará $_ en su lugar.

Inlining Subroutines

Some subroutines can be compiled directly into the calling code, making them faster by avoiding the overhead of a subroutine call. This is called inlining. Inlining is typically done only for simple subroutines that don't have unusual characteristics. For example, subroutines that contain loops, recursion, or references to $_ may not be inlined.

Subroutines with a "()" prototype are candidates for inlining. This prototype says that the subroutine takes no arguments. It also serves to distinguish it from subroutines that are intended to be called as methods (which are never inlined).

The "return" statement within a subroutine, when the subroutine has a "()" prototype, acts as a strong hint to the compiler that the subroutine *should* be inlined. This is because it behaves consistently with subroutines containing inner scopes.) You can countermand inlining by using an explicit "return":

sub baz_val () {
    if (OPT_BAZ) {
        return 23;
    }
    else {
        return 42;
    }
}
sub bonk_val () { return 12345 }

As alluded to earlier you can also declare inlined subs dynamically at BEGIN time if their body consists of a lexically-scoped scalar which has no other references. Only the first example here will be inlined:

BEGIN {
    my $var = 1;
    no strict 'refs';
    *INLINED = sub () { $var };
}
BEGIN {
    my $var = 1;
    my $ref = \$var;
    no strict 'refs';
    *NOT_INLINED = sub () { $var };
}

A not so obvious caveat with this (see [RT #79908]) is what happens if the variable is potentially modifiable. For example:

BEGIN {
    my $x = 10;
    *FOO = sub () { $x };
    $x++;
}
print FOO(); # printed 10 prior to 5.32.0

From Perl 5.22 onwards this gave a deprecation warning, and from Perl 5.32 onwards it became a run-time error. Previously the variable was immediately inlined, and stopped behaving like a normal lexical variable; so it printed 10, not 11.

If you still want such a subroutine to be inlined (with no warning), make sure the variable is not used in a context where it could be modified aside from where it is declared.

# Fine, no warning
BEGIN {
    my $x = 54321;
    *INLINED = sub () { $x };
}
# Error
BEGIN {
    my $x;
    $x = 54321;
    *ALSO_INLINED = sub () { $x };
}

Perl 5.22 also introduced the "const" attribute as an alternative. It was initially experimental, but made stable in Perl 5.40. When applied to an anonymous subroutine, it forces the sub to be called when the "sub" expression is evaluated. The return value is captured and turned into a constant subroutine:

my $x = 54321;
*INLINED = sub : const { $x };
$x++;

The return value of "INLINED" in this example will always be 54321, regardless of later modifications to $x. You can also put any arbitrary code inside the sub, at it will be executed immediately and its return value captured the same way.

If you really want a subroutine with a "()" prototype that returns a lexical variable you can easily force it to not be inlined by adding an explicit "return":

BEGIN {
    my $x = 10;
    *FOO = sub () { return $x };
    $x++;
}
print FOO(); # prints 11

The easiest way to tell if a subroutine was inlined is by using B::Deparse. Consider this example of two subroutines returning 1, one with a "()" prototype causing it to be inlined, and one without (with deparse output truncated for clarity):

$ perl -MO=Deparse -e 'sub ONE { 1 } if (ONE) { print ONE if ONE }'
sub ONE {
    1;
}
if (ONE ) {
    print ONE() if ONE ;
}
$ perl -MO=Deparse -e 'sub ONE () { 1 } if (ONE) { print ONE if ONE }'
sub ONE () { 1 }
do {
    print 1
};

If you redefine a subroutine that was eligible for inlining, you'll get a warning by default. You can use this warning to tell whether or not a particular subroutine is considered inlinable, since it's different than the warning for overriding non-inlined subroutines:

$ perl -e 'sub one () {1} sub one () {2}'
Constant subroutine one redefined at -e line 1.
$ perl -we 'sub one {1} sub one {2}'
Subroutine one redefined at -e line 1.

The warning is considered severe enough not to be affected by the -w switch (or its absence) because previously compiled invocations of the function will still be using the old value of the function. If you need to be able to redefine the subroutine, you need to ensure that it isn't inlined, either by dropping the "()" prototype (which changes calling semantics, so beware) or by thwarting the inlining mechanism in some other way, e.g. by adding an explicit "return", as mentioned above:

sub not_inlined () { return 23 }

Overriding Built-in Functions

Many built-in functions may be overridden, though this should be tried only occasionally and for good reason. Typically this might be done by a package attempting to emulate missing built-in functionality on a non-Unix system.

Overriding may be done only by importing the name from a module at compile time--ordinary predeclaration isn't good enough. However, the "use subs" pragma lets you, in effect, predeclare subs via the import syntax, and these names may then override built-in ones:

use subs 'chdir', 'chroot', 'chmod', 'chown';
chdir $somewhere;
sub chdir { ... }

To unambiguously refer to the built-in form, precede the built-in name with the special package qualifier "CORE::". For example, saying CORE::open() always refers to the built-in open(), even if the current package has imported some other subroutine called &open() from elsewhere. Even though it looks like a regular function call, it isn't: the "CORE::" prefix in that case is part of Perl's syntax, and works for any keyword, regardless of what is in the "CORE" package. Taking a reference to it, that is, "\&CORE::open", only works for some keywords. See CORE.

Library modules should not in general export built-in names like "open" or "chdir" as part of their default @EXPORT list, because these may sneak into someone else's namespace and change the semantics unexpectedly. Instead, if the module adds that name to @EXPORT_OK, then it's possible for a user to import the name explicitly, but not implicitly. That is, they could say

use Module 'open';

and it would import the "open" override. But if they said

use Module;

they would get the default imports without overrides.

The foregoing mechanism for overriding built-in is restricted, quite deliberately, to the package that requests the import. There is a second method that is sometimes applicable when you wish to override a built-in everywhere, without regard to namespace boundaries. This is achieved by importing a sub into the special namespace "CORE::GLOBAL::". Here is an example that quite brazenly replaces the "glob" operator with something that understands regular expressions.

package REGlob;
require Exporter;
@ISA = 'Exporter';
@EXPORT_OK = 'glob';
sub import {
    my $pkg = shift;
    return unless @_;
    my $sym = shift;
    my $where = ($sym =~ s/^GLOBAL_// ? 'CORE::GLOBAL' : caller(0));
    $pkg->export($where, $sym, @_);
}
sub glob {
    my $pat = shift;
    my @got;
    if (opendir my $d, '.') {
        @got = grep /$pat/, readdir $d;
        closedir $d;
    }
    return @got;
}
1;

And here's how it could be (ab)used:

#use REGlob 'GLOBAL_glob';      # override glob() in ALL namespaces
package Foo;
use REGlob 'glob';              # override glob() in Foo:: only
print for <^[a-z_]+\.pm\$>;     # show all pragmatic modules

The initial comment shows a contrived, even dangerous example. By overriding "glob" globally, you would be forcing the new (and subversive) behavior for the "glob" operator for every namespace, without the complete cognizance or cooperation of the modules that own those namespaces. Naturally, this should be done with extreme caution--if it must be done at all.

The "REGlob" example above does not implement all the support needed to cleanly override Perl's "glob" operator. The built-in "glob" has different behaviors depending on whether it appears in a scalar or list context, but our "REGlob" doesn't. Indeed, many Perl built-ins have such context sensitive behaviors, and these must be adequately supported by a properly written override. For a fully functional example of overriding "glob", study the implementation of "File::DosGlob" in the standard library.

When you override a built-in, your replacement should be consistent (if possible) with the built-in native syntax. You can achieve this by using a suitable prototype. To get the prototype of an overridable built-in, use the "prototype" function with an argument of "CORE::builtin_name" (see "prototype" in perlfunc).

Note however that some built-ins can't have their syntax expressed by a prototype (such as "system" or "chomp"). If you override them you won't be able to fully mimic their original syntax.

The built-ins "do", "require" and "glob" can also be overridden, but due to special magic, their original syntax is preserved, and you don't have to define a prototype for their replacements. (You can't override the "do BLOCK" syntax, though).

"require" has special additional dark magic: if you invoke your "require" replacement as "require Foo::Bar", it will actually receive the argument "Foo/Bar.pm" in @_. See "require" in perlfunc.

And, as you'll have noticed from the previous example, if you override "glob", the "<*>" glob operator is overridden as well.

In a similar fashion, overriding the "readline" function also overrides the equivalent I/O operator "<FILEHANDLE>". Also, overriding "readpipe" also overrides the operators `` and "qx//".

Finally, some built-ins (e.g. "exists" or "grep") can't be overridden.

NAME

perlsub - Definiciones de subrutinas y llamadas

SYNOPSIS

    sub my_sub { ... }
    my $coderef = \&my_sub;
    my_sub();
    $coderef->();
    package::method();

DESCRIPTION

Una subrutina es simplemente una secuencia de código con nombre que puede ser ejecutada.

Se puede declarar una subrutina usando la forma:

    sub name
    sub name : ATTRLIST
    sub name ( PLIST ) : ATTRLIST
    sub name { BODY }
    sub name ( PLIST ) { BODY }

donde name es el nombre de la subrutina, PLIST es una lista de parámetros que la subrutina espera, y BODY es el código que la subrutina ejecutará. Si se proporciona un ATTRLIST, se aplica a la subrutina. Consulte "Subroutine Attributes" a continuación.

Si se proporciona PLIST, se supone que la subrutina se llama con paréntesis. Si no se proporcionan paréntesis, la subrutina se puede llamar sin ellos, pero la lista de parámetros sólo se comprueba en cuanto a si sus paréntesis ('(',')') anidan correctamente.

Si se omite BODY, la subrutina se declara pero no se define. Esto es útil para predeclarar subrutinas que se definirán más tarde, o para importar subrutinas de otros paquetes. Por ejemplo:

    package Foo;
    sub bar; # Predeclaración de subrutina
    sub baz(); # Predeclaración de subrutina vacía
    sub qux : Useless; # Predeclaración de subrutina con atributo
    package main;
    require Foo;
    Foo::bar(); # Llama a Foo::bar, que debe estar definida en alguna parte

Cuando se define una subrutina, su nombre se puede usar como un código de referencia para la subrutina, o la subrutina se puede llamar directamente por su nombre. La llamada a una subrutina puede realizarse sin paréntesis si la subrutina no espera argumentos y no devuelve una lista de valores. Por ejemplo, las siguientes llamadas son todas equivalentes:

    &foo;
    foo;
    &Foo::bar(1, 2);
    Foo::bar(1, 2);
    my $scalar_ref = \&foo;
    my @array_ref = &foo;
    my $list_ref = \&foo;
    $scalar_ref->();
    $array_ref->(@args);
    $list_ref->(@args);

Cuando se llama a una subrutina, sus argumentos se empaquetan en la lista especial @_. La subrutina puede acceder a estos argumentos asignando a @_, o asignando a variables escalares individuales del contexto de la subrutina. Por ejemplo:

    sub export {
        my ($arg1, $arg2) = @_;
        my $arg3 = shift;
        # ...
    }
    # o
    sub import {
        my ($class, $caller, @args) = @_;
        # ...
    }
    # o incluso
    sub process {
        my $count = shift;
        my ($name, $value) = @_;
        # ...
    }

Las subrutinas también pueden devolver valores. Si se produce una sentencia return, se devuelve el valor especificado. Si no hay ninguna sentencia return, el valor devuelto es el valor de la última expresión evaluada en la subrutina. Si la subrutina se llama en un contexto de lista, se devuelve una lista de valores; si se llama en un contexto escalar, se devuelve el primer valor de la lista devuelta. Si se llama en un contexto de matriz, se devuelve la última matriz devuelta.

Si intenta llamar a una subrutina que no está definida, normalmente obtendría un error fatal inmediato quejándose de que la subrutina no existe. (Lo mismo ocurre con las subrutinas que se utilizan como métodos, cuando el método no existe en ninguna clase base del paquete de la clase.) Sin embargo, si se define una subrutina "AUTOLOAD" en el paquete o paquetes utilizados para localizar la subrutina original, entonces esa subrutina "AUTOLOAD" se llama con los argumentos que se habrían pasado a la subrutina original. El nombre completo de la subrutina original aparece mágicamente en la variable global $AUTOLOAD del mismo paquete que la rutina "AUTOLOAD". El nombre no se pasa como un argumento ordinario porque, bueno, sólo porque sí. (Como excepción, una llamada a método a un método "import" o "unimport" inexistente simplemente se omite en su lugar. Además, si la subrutina AUTOLOAD es una XSUB, hay otras formas de recuperar el nombre de la subrutina. Consulte "Autoloading with XSUBs" en perlguts para obtener más detalles.)

Muchas rutinas "AUTOLOAD" cargan una definición para la subrutina solicitada usando eval(), y luego ejecutan esa subrutina usando una forma especial de goto() que borra el marco de pila de la rutina "AUTOLOAD" sin dejar rastro. (Consulte el código fuente del módulo estándar documentado en AutoLoader, por ejemplo.) Pero una rutina "AUTOLOAD" también puede simplemente emular la rutina y nunca definirla. Por ejemplo, pretendamos que una función que no estaba definida debería simplemente invocar "system" con esos argumentos. Todo lo que tendría que hacer es:

    sub AUTOLOAD {
        our $AUTOLOAD;              # mantener 'use strict' feliz
        my $program = $AUTOLOAD;
        $program =~ s/.*:://;
        system($program, @_);
    }
    date();
    who();
    ls('-l');

De hecho, si predeclara funciones que desea llamar de esa manera, ni siquiera necesita paréntesis:

    use subs qw(date who ls);
    date;
    who;
    ls '-l';

Un ejemplo más completo de esto es el módulo Shell en CPAN, que puede tratar las llamadas a subrutinas indefinidas como llamadas a programas externos.

Existen mecanismos para ayudar a los escritores de módulos a dividir sus módulos en archivos cargables automáticamente. Consulte el módulo estándar AutoLoader descrito en AutoLoader y en AutoSplit, los módulos estándar SelfLoader en SelfLoader, y el documento sobre cómo añadir funciones C al código Perl en perlxs.

Atributos de subrutina

Una declaración o definición de subrutina puede tener una lista de atributos asociados. Si está presente dicha lista de atributos, se divide en los límites de espacio o dos puntos y se trata como si se hubiera visto un "use attributes". Consulte attributes para obtener detalles sobre qué atributos se admiten actualmente. A diferencia de la limitación con el obsoleto "use attrs", la sintaxis "sub : ATTRLIST" funciona para asociar los atributos con una predeclaración, y no sólo con una definición de subrutina.

Los atributos deben ser válidos como nombres de identificadores simples (sin puntuación aparte del carácter '_'). Pueden tener una lista de parámetros adjunta, que sólo se comprueba en cuanto a si sus paréntesis ('(',')') anidan correctamente.

Ejemplos de sintaxis válida (aunque los atributos sean desconocidos):

    sub fnord (&\%) : switch(10,foo(7,3))  :  expensive;
    sub plugh () : Ugly('\(") :Bad;
    sub xyzzy : _5x5 { ... }

Ejemplos de sintaxis no válida:

    sub fnord : switch(10,foo();    # la cadena () no está equilibrada
    sub snoid : Ugly('(');          # la cadena () no está equilibrada
    sub xyzzy : 5x5;                # "5x5" no es un identificador válido
    sub plugh : Y2::north;          # "Y2::north" no es un identificador simple
    sub snurt : foo + bar;          # "+" no es un dos puntos ni un espacio

La lista de atributos se pasa como una lista de cadenas constantes al código que los asocia con la subrutina. En particular, el segundo ejemplo de sintaxis válida anterior se ve actualmente así en términos de cómo se analiza e invoca:

    use attributes __PACKAGE__, \&plugh, q[Ugly('\(")], 'Bad';

Para más detalles sobre las listas de atributos y su manipulación, consulte attributes y Attribute::Handlers.
