PERLCLIB(1perl) Guía de referencia para programadores de Perl PERLCLIB(1perl)

NOMBRE

perlclib - Interactuar con funciones de la biblioteca C estándar

DESCRIPCIÓN

El intérprete de Perl está escrito en C; el código XS también se expande a C. Inevitablemente, este código llamará a algunas funciones de la biblioteca C, "libc". Este documento ofrece algunas directrices sobre cómo interactuar con esa biblioteca.

Una cosa que los portadores de Perl deben tener en cuenta es que *perl* no tiende a utilizar mucha de la biblioteca estándar C internamente; verás muy poco uso de, por ejemplo, las funciones de *ctype.h* en él. Esto se debe a que Perl tiende a reimplementar o abstraer funciones de la biblioteca estándar, de modo que sepamos exactamente cómo van a operar.

funciones de libc a evitar

Existen muchas, muchas funciones de libc. La mayoría de ellas son de uso aceptable, pero algunas no lo son. Algunas de las posibles razones son:

  • Es probable que interfieran con el funcionamiento del intérprete de Perl, como su contabilidad, manejo de señales, asignación de memoria o cualquier número de cosas perjudiciales.
  • No están implementadas en todas las plataformas, pero existe una alternativa que sí lo está.

    O pueden ser erróneas o estar obsoletas en algunas o en todas las plataformas.

  • No son adecuadas para operaciones con hilos, pero existe una alternativa que sí lo es, y es igual de fácil de usar.

    Es posible que no esperes que tu código se utilice nunca en hilos, pero el código tiene una forma de adaptarse más allá de nuestras expectativas iniciales. Si es igual de fácil usar algo que se puede utilizar en hilos, es mejor usarlo ahora, por si acaso.

  • En funciones que tratan con cadenas, pueden surgir complicaciones porque la cadena puede estar codificada de diferentes maneras, por ejemplo, en UTF-8. Para estas, es probable que sea mejor colocar la cadena en un SV y utilizar las funciones de manejo de cadenas SV de Perl que contienen una extensa lógica para tratar con esto.
  • En funciones que tratan con números, pueden surgir complicaciones porque los números se vuelven demasiado grandes o pequeños, y cuáles son esos límites depende de la plataforma actual. De nuevo, los tipos de datos numéricos SV de Perl tienen una lógica extensa para hacerse cargo de este tipo de problemas.
  • Son conscientes de la configuración regional, y es posible que tu llamador no quiera esto.

Los siguientes comentarios y tablas presentan algunas funciones en la primera columna que no deben usarse en código C o XS, con la alternativa preferida (si la hay) en la segunda columna.

Convenciones

En las siguientes tablas:

"~"
marca la función como obsoleta; no debe usarse bajo ninguna circunstancia.
"t"
es un tipo.
"p"
es un puntero.
"n"
es un número.
"s"
es una cadena.

"sv", "av", "hv", etc. representan variables de sus respectivos tipos.

Operaciones de Archivo

En lugar de las funciones de *stdio.h*, debes usar la capa de abstracción de Perl. En lugar de tipos "FILE*", necesitas manejar tipos "PerlIO*". No olvides que con la nueva abstracción de E/S en capas de PerlIO, los tipos "FILE*" pueden no estar disponibles. Consulta también la documentación de "perlapio" para más información sobre las siguientes funciones:

                              cente)

Entrada y Salida de Archivo

Ten en cuenta que los equivalentes de PerlIO de "fread" y "fwrite" son ligeramente diferentes de sus homólogos de la biblioteca C:

Gestión de Memoria y Manejo de Cadenas

En lugar de:                    Usar:
t* p = malloc(n)               Newx(p, n, t)
t* p = calloc(n, s)            Newxz(p, n, t)
p = realloc(p, n)              Renew(p, n, t)

No es portable intentar asignar 0 bytes; asignar 1 o más es portable. Nunca pases punteros entre "Newx", "Renew", "Safefree" y los equivalentes de *libc* "malloc", "realloc", "free". No son del mismo grupo de memoria o asignador. O bien se producirá una *SEGV* instantánea o retrasada, o fugas de memoria sutiles o corrupción sutil del heap.

memcpy(dst, src, n)            Copy(src, dst, n, t)
memmove(dst, src, n)           Move(src, dst, n, t)
memcpy(dst, src, sizeof(t))    StructCopy(src, dst, t)

Observa el orden diferente de los argumentos para "Copy" y "Move" en comparación con los utilizados en "memcpy" y "memmove".

memset(dst, 0, n * sizeof(t))  Zero(dst, n, t)
memzero(dst, 0)                Zero(dst, n, char)
free(p)                        Safefree(p)
strdup(p)                      savepv(p)
strndup(p, n)                  savepvn(p, n) (¡Eh, strndup no
                                              existe!)

A veces, en lugar de inicializar a cero la memoria asignada usando Newxz(), deberías considerar "envenenar" los datos. Esto significa escribir un patrón de bits en ella que debería ser ilegal como punteros (y números de punto flotante), y también lo suficientemente sorprendente como enteros, para que cualquier código que intente usar los datos sin pensar se rompa antes que después. El envenenamiento se puede hacer usando las macros Poison(), que tienen argumentos similares a Zero():

PoisonWith(dst, n, t, b)    escribir memoria con el byte b
PoisonNew(dst, n, t)        igual a PoisonWith(dst, n, t, 0xAB)
PoisonFree(dst, n, t)       igual a PoisonWith(dst, n, t, 0xEF)
Poison(dst, n, t)           igual a PoisonFree(dst, n, t)
strstr(big, little)            instr(big, little)
memmem(big, blen, little, len) ninstr(big, bigend, little, little_end)
strcmp(s1, s2)                 strLE(s1, s2) / strEQ(s1, s2)
                                             / strGT(s1,s2)
strncmp(s1, s2, n)             strnNE(s1, s2, n) / strnEQ(s1, s2, n)
memcmp(p1, p2, n)              memNE(p1, p2, n)
!memcmp(p1, p2, n)             memEQ(p1, p2, n)

La mayoría de las veces, sin embargo, querrás tratar con SVs internamente en lugar de cadenas de "char *" en bruto:

strlen(s)                   sv_len(sv)
strcpy(dt, src)             sv_setpv(sv, s)
strncpy(dt, src, n)         sv_setpvn(sv, s, n)
strcat(dt, src)             sv_catpv(sv, s)
strncat(dt, src)            sv_catpvn(sv, s)

Si necesitas cadenas en bruto, usa estas en su lugar:

my_strnlen(s, maxlen)
my_strlcpy(dt, src, sizeof(dt)

String and IO functions

There are a few dozen string and IO functions in the standard C library. Most of them are available in Perl's C API, though some are given new names to avoid conflicts or to make them more Perl-like.

In the following tables, the "Instead Of" column is a function from the C library, and the "Use" column is the Perl C API equivalent.

String creation

For creating strings in Perl's internal format (SV), you can use these functions:

sprintf(s, fmt, ...)    sv_setpvf(sv, fmt, ...)
vsprintf(str, fmt, va_list) sv_vsetpvf(sv, fmt, va_list)
strncat(dt, src, len)   sv_catpv(sv, src)
strcat(dt, src)         sv_catpv(sv, src)
strncpy(dt, src, len)   sv_copypv(sv, src)
strcpy(dt, src)         sv_copypv(sv, src)
snprintf(dt, len, fmt, ...) sv_setpvf(sv, fmt, ...)

The sv_setpvf and sv_vsetpvf functions expect an already-created SV*. If you want to create a new one, you would do something like:

SV *sv = sv_newmortal();
sv_setpvf(sv, "Hello %s, you are %d\n", name, age);

Or, more commonly, you want to append to an existing string.

SV *sv = ...; /* an existing SV */
sv_catpv(sv, "some text");
sv_catpvf(sv, " and some more text, like %d", number);

See also sv_catprintf, sv_catvsprintf, sv_setpvn, sv_vsetpvn, sv_catpvn, sv_vcatpvn.

The functions Perl_sv_vcatpvf and Perl_sv_vcatpvn are also available if you have a va_list already.

These replacement functions are not always drop-in replacements. For instance, my_strlcat is intended to be safer than strcat in that it is guaranteed not to overflow the destination buffer. The Perl equivalent, sv_catpv, is generally safe because SVs are dynamically sized. When converting C code, you might find it easier to use something like:

char dt[100];
char *src = "some string";
...
my_strlcat(dt, src, sizeof(dt))

Similiarly, you can use SVs for creating strings from formats

sprintf(s, fmt, ...)         sv_setpvf(sv, fmt, ...)
vsprintf(str, fmt, va_list)  sv_vsetpvf(sv, fmt, va_list)

Or for raw strings,

my_snprintf(dt, len, fmt, ...)
my_vsnprintf(dt, len, fmt, va_list)
vsprintf(str, fmt, va_list)  sv_vsnprintf(sv, fmt, va_list)

Note also the existence of "sv_catpvf" and "sv_vcatpvfn", combining concatenation with formatting; and "Perl_form"() for another form of formatted populating.

Note that glibc printf(), sprintf(), etc. are buggy before glibc version 2.17. They won't allow a "%.s" format with a precision to create a string that isn't valid UTF-8 if the current underlying locale of the program is UTF-8. What happens is that the %s and its operand are simply skipped without any notice. https://sourceware.org/bugzilla/show_bug.cgi?id=6530.

Character Class Tests

There are several types of character class tests that Perl implements. All are more fully described in "Character classification" in perlapi and "Character case changing" in perlapi.

The C library routines listed in the table below return values based on the current locale. Use the entries in the final column for that functionality. The other two columns always assume a POSIX (or C) locale. The entries in the ASCII column are only meaningful for ASCII inputs, returning FALSE for anything else. Use these only when you know that is what you want. The entries in the Latin1 column assume that the non-ASCII 8-bit characters are as Unicode defines them, the same as ISO-8859-1, often called Latin 1.

isascii(c)  isASCII(c)                             isASCII_LC(c)
isblank(c)  isBLANK(c)        isBLANK_L1(c)        isBLANK_LC(c)
iscntrl(c)  isCNTRL(c)        isCNTRL_L1(c)        isCNTRL_LC(c)

For the corresponding functions like iswupper(), etc., use isUPPER_uvchr() for non-locale; or isUPPER_LC_uvchr() for locale. And use toLOWER_uvchr() instead of towlower(), etc.. There are no direct equivalents for locale; best to put the string into an SV.

Don't use any of the functions like isalnum_l(). Those are non-portable, and interfere with Perl's internal handling.

To emphasize that you are operating only on ASCII characters, you can append "_A" to each of the macros in the ASCII column: "isALPHA_A", "isDIGIT_A", and so on.

(There is no entry in the Latin1 column for "isascii" even though there is an "isASCII_L1", which is identical to "isASCII"; the latter name is clearer. There is no entry in the Latin1 column for "toupper" because the result can be non-Latin1. You have to use "toUPPER_uvchr", as described in "Character case changing" in perlapi.)

Note that the libc caseless comparisons are crippled; Unicode provides a richer set, using the concept of folding. If you need more than equality/non-equality, it's probably best to store your strings in an SV and use SV functions to do the comparision. Similarly for collation.

Typical use is to do range checks on "uv" before casting:

int i; UV uv;

    && uv <= INT_MAX)

Perl y la configuración regional

Cuando su código C o XS llama a una función de la biblioteca C que está sujeta a la configuración regional, su código puede verse afectado por la configuración regional actual.

aio_cancel()         fstatat()           posix_fallocate()
aio_error()          futimens()          posix_fadvise()
aio_fsync()          getlogin_r()        pread()
aio_read()           getnameinfo()       pread64()
aio_suspend()        getpeername()       preadv()
aio_write()          getsockname()       preadv64()
alphasort()          getsockopt()        pwrite()
alphasort64()        getxattr()          pwrite64()
asprintf()           glob()              pwritev()
...

(La lista no incluye funciones que manipulan la configuración regional, como setlocale().)

Si alguna de estas funciones se llama directa o indirectamente desde su código, se verá afectado por la configuración regional actual.

Lo primero que debe saber sobre esta lista es que existen mejores alternativas para muchas de las funciones, que es muy probable que deba usar en su lugar. Consulte "funciones de libc a evitar" arriba. Esto incluye el uso de E/S de Perl perlapio.

Lo segundo que debe saber es que se documenta que Perl no presta atención a la configuración regional actual, excepto para el código ejecutado dentro del ámbito de una instrucción "use locale". Si viola esto, puede estar creando errores, dependiendo de la aplicación.

Lo siguiente que debe saber es que muchas de estas funciones dependen solo de la configuración regional en lo que respecta a los valores numéricos. Es probable que su código se haya escrito esperando que el punto decimal (la base) sea un punto (U+002E: PUNTO FINAL), y que las cadenas de números enteros no se separen en grupos (1,000,000 en una configuración regional americana significa un millón; es probable que su código no espere las comas). La buena noticia es que normalmente (a partir de Perl v5.22), su código se llamará con la configuración regional establecida para que esas expectativas se cumplan. Se debe tomar una acción explícita para cambiar esto (descrito un poco más adelante). Esto se logra haciendo que Perl no cambie realmente a una configuración regional que no cumpla con estas expectativas, excepto cuando se le indica explícitamente que lo haga. Las rutinas de entrada/salida y formato de Perl realizan este cambio automáticamente por usted, si es apropiado, y luego vuelven a cambiar. Si, por alguna razón, necesita hacerlo usted mismo, la forma más fácil desde C y código XS es usar la macro ""WITH_LC_NUMERIC_SET_TO_NEEDED"" en perlapi. Puede envolver esta macro alrededor de un bloque completo de código que desea que se ejecute en el entorno correcto. La conclusión es que es probable que su código funcione como se espera en este sentido sin que tenga que tomar ninguna medida.

Esto deja las funciones restantes. Su código se llamará con todas las porciones de la configuración regional, excepto las numéricas, establecidas en la configuración regional subyacente. A menudo, la configuración regional no es de gran importancia para su código, y tampoco tendrá que tomar ninguna medida; las cosas simplemente funcionarán. Pero debe examinar las páginas del manual de las que utilice para verificarlo. A menudo, Perl tiene mejores maneras de realizar la misma funcionalidad. Considere usar SVs y sus rutinas de acceso en lugar de llamar a las funciones de bajo nivel que, por ejemplo, calculan cuántos bytes tiene un carácter codificado en UTF-8.

Puede determinar si ha sido llamado desde el ámbito de un "use locale" utilizando la macro booleana ""IN_LOCALE"" en perlapi.

Si necesita no estar dentro de la configuración regional subyacente, puede llamar a ""Perl_setlocale"" en perlapi para cambiarla temporalmente a la que necesita (probablemente la configuración regional "C"), y luego volver a cambiarla antes de regresar. Esto puede ser **muy** problemático en perls con hilos en algunas plataformas. Consulte "Lidiar con perls integrados y hilos".

Un problema con el cambio de la configuración regional de una sola categoría es que puede surgir mojibake en algunas plataformas si la categoría "LC_CTYPE" y la categoría cambiada no son las mismas. En las plataformas donde eso no es un problema, se definirá la directiva del preprocesador "LIBC_HANDLES_MISMATCHED_CTYPE". De lo contrario, es posible que deba cambiar más de una categoría para completar su tarea correctamente. Y habrá muchas combinaciones de configuraciones regionales en las que el mojibake probablemente no ocurrirá, por lo que no se enfrentará a esto hasta que el código se ejecute en el campo por alguien que no hable muy bien su idioma.

Anteriormente mencionamos que se requiere una acción explícita para que su código se llame con las porciones numéricas de la configuración regional que no cumplen las expectativas típicas de tener un punto para el carácter base y ninguna puntuación que separe grupos de dígitos. Esa acción es llamar a la función ""switch_to_global_locale"" en perlapi.

switch_to_global_locale() se escribió inicialmente para hacer frente a la biblioteca "Tk", pero es lo suficientemente general para otras situaciones similares. "Tk" cambia la configuración regional global para que coincida con sus expectativas (versiones posteriores de la misma permiten desactivar esto). Esto presenta un conflicto con Perl pensando que también controla la configuración regional. Llamar a esta función le dice a Perl que ceda el control. Llamar a ""sync_locale"" en perlapi le dice a Perl que tome el control nuevamente, aceptando lo que sea que haya cambiado la configuración regional en el ínterin. Si su código se llama durante ese ínterin, todas las porciones de la configuración regional serán los valores subyacentes brutos. En caso de que necesite manipular números, está solo en cuanto al carácter base y la agrupación. Si se encuentra en esta situación, generalmente es mejor hacer que el intervalo entre las llamadas a estas dos funciones sea lo más corto posible y evitar los cálculos hasta después de que perl tenga el control nuevamente.

Es importante que perl conozca todas las categorías de configuración regional posibles en la plataforma, incluso si no se utilizan aparentemente en su programa. Perl conoce todas las de Linux. Si su plataforma tiene otras, puede enviar un problema en https://github.com/Perl/perl5/issues para su inclusión en la próxima versión. Mientras tanto, es posible editar el código fuente de Perl para enseñarle sobre la categoría y luego recompilar. Busque instancias de, por ejemplo, "LC_PAPER" en el código fuente y úselo como plantilla para agregar el omitido.

Existen complicaciones adicionales en operaciones multihilo. Continúe leyendo.

Lidiar con perls integrados y hilos

Es posible integrar un intérprete de Perl dentro de un programa más grande. Consulte perlembed.

MULTIPLICITY es la forma en que esto se logra internamente; se describe en "Cómo se admite la compatibilidad con múltiples intérpretes y concurrencia" en perlguts. Se pueden integrar múltiples intérpretes de Perl.

También es posible compilar perl para admitir hilos. Consulte perlthrtut. La implementación de hilos de Perl requiere MULTIPLICITY, pero no al revés.

MULTIPLICITY sin hilos significa que solo se ejecuta una cosa a la vez, por lo que no hay problemas de concurrencia, pero cada componente o instancia puede afectar el estado global, interfiriendo potencialmente con la ejecución de otras instancias. Esto puede suceder si una instancia:

  • cambia el directorio de trabajo actual
  • chan

Las aplicaciones de Perl pueden ser seguras en cuanto a hilos (thread-safe) o seguras en cuanto a multiplicidad (safe under MULTIPLICITY). La seguridad en cuanto a multiplicidad significa que se pueden ejecutar múltiples instancias de la aplicación Perl en el mismo proceso (por ejemplo, en un servidor web como Apache con mod_perl). La seguridad en cuanto a hilos significa que la aplicación Perl puede ser ejecutada en múltiples hilos dentro del mismo proceso.

Una aplicación Perl no es segura en cuanto a hilos o multiplicidad si hace lo siguiente:

  • Cambia el entorno del proceso.
  • Cambia la configuración regional global en la que opera el proceso.
  • Escribe en memoria compartida o en un archivo compartido.
  • Utiliza un descriptor de archivo compartido (incluyendo un iterador de base de datos).
  • Lanza una señal a la que son sensibles las funciones de otras instancias.

Si su código no hace ninguna de estas cosas, ni depende de ninguno de sus valores, ¡¡felicidades!!, no tiene que preocuparse por MULTIPLICITY o los hilos. Pero esperen, un número sorprendente de funciones de la libc dependen de datos globales para el proceso de alguna manera que puede no ser obvia de inmediato. Por ejemplo, llamar a strtok(3) cambia el estado global de un proceso y, por lo tanto, necesita atención especial.

    Cuestiones generales con la seguridad de subprocesos

    Algunas funciones de la biblioteca C utilizan y/o modifican un estado global, como una base de datos. Las funciones de la biblioteca C presumen que solo hay una instancia operando en esa base de datos a la vez. Ocurren resultados impredecibles si más de una lo hace, incluso si la base de datos no se modifica. Por ejemplo, típicamente hay un iterador global para una base de datos de este tipo y ese iterador es mantenido por la biblioteca C, de modo que cada nueva lectura de cualquier instancia lo avanza, lo que significa que ninguna instancia verá todas las entradas. La única forma de hacer que estas sean seguras para subprocesos es tener un bloqueo exclusivo en un mutex desde la llamada open hasta la llamada close. Se le recomienda no usar tales bases de datos desde más de una instancia a la vez.

    Otros ejemplos de funciones que utilizan un estado global incluyen generadores de números pseudoaleatorios. Algunas implementaciones de la biblioteca C de BAqrand()', por ejemplo, pueden compartir los datos entre subprocesos; y otras pueden tener datos por subproceso. Los compartidos tendrán resultados irreproducibles, ya que los subprocesos variarán en sus tiempos e interacciones. Esto puede ser lo que usted quiere; o puede que no lo sea. (Esta función en particular es candidata a ser eliminada del Estándar POSIX debido a estos problemas.)

    Las funciones que generan salida a un flujo también se consideran inseguras para subprocesos cuando no se realiza el bloqueo. Pero las consecuencias típicas son solo que los datos se generan en un orden impredecible; ese resultado puede ser totalmente aceptable para usted.

    Dado que el directorio de trabajo actual es global para un proceso, todas las instancias dependen de él. Una instancia que realiza un chdir(2) afecta a todas las demás instancias. En un entorno multihilo, cualquier llamada a la biblioteca C que espere que el directorio no cambie durante la ejecución tendrá resultados indefinidos si otro subproceso la interrumpe en el momento equivocado y cambia el directorio. Las páginas man solo enumeran una de esas llamadas, nftw(). Pero puede haber otros problemas ocultos.

    Funciones equivalentes reentrantes

    Algunas funciones que son problemáticas con respecto a MULTIPLICITY tienen versiones reentrantes (en algunas o todas las plataformas) que son más adecuadas, con menos (quizás ninguna) condiciones de carrera cuando se ejecutan bajo hilos.

    Algunas de estas funciones reentrantes que están disponibles en todas las plataformas deberían usarse de todos modos; están en las listas directamente debajo de "funciones de la biblioteca C a evitar".

O puede ser simplemente más complicado y tedioso usar la versión reentrante. Para estos, perl tiene un mecanismo para sustituir automáticamente esa versión reentrante cuando está disponible y es deseable, al tiempo que oculta las complicaciones de su código. Esta característica está habilitada por defecto para el código del núcleo de Perl y sus extensiones. Para habilitarla en otros módulos XS,

    #define PERL_REENTRANT

    Es más simple para usted usar la versión no preferida en su código y confiar en esta característica para hacer lo mejor, en parte porque no se realiza ninguna sustitución si la alternativa no está disponible o no es deseable en la plataforma, ni si los hilos no están habilitados. Usted simplemente escribe como si no hubiera hilos, y obtiene el mejor comportamiento sin tener que pensar en ello.

Perl comenzará con un búfer pequeño, pero seguirá reintentando y ampliando el búfer de resultados hasta que el resultado encaje. Si este crecimiento ilimitado le parece malo por razones de seguridad o consumo de memoria, puede recompilar Perl con "PERL_REENTRANT_MAXSIZE" #definido al número máximo de bytes que permitirá.

    perlclib(1perl)

    Embedded Perl functions and constants.

    perlclib

    The core of the Perl language is written in C. This manual page describes some C functions that are used by the Perl interpreter, or that might be used by C code that embeds the Perl interpreter. Note that the behavior of many of these functions can be significantly different under threads.

    Dealing with embedded perls and threads

    This section is intended for those who embed the Perl interpreter in a C/C++ application. If you are just writing Perl code, you can skip this section.

    Perl's internals are not thread-safe. Some C library functions are also not thread-safe. This section highlights some of the potential problems and points to solutions.

    The following functions are known to be problematic under threads, often because they rely on global state that can be modified by other threads.

    catopen()
    The global state of the catopen() function is shared between all threads.

    If you want to use catopen() in a threaded application, you need to use catopen_r(). The catopen_r() function is thread-safe.

    gethostbyname(), gethostbyaddr(), etc.
    The gethostbyname(), gethostbyaddr(), getnetbyname(), getnetbyaddr(), getprotoent(), getservent(), and getaliasent() functions, as well as their reentrant counterparts gethostbyname_r(), etc., are not thread-safe.

    They use static data structures to store their return values. If multiple threads call these functions concurrently, the return values may be overwritten by another thread, leading to incorrect results.

    The recommended way to use these functions in a threaded environment is to use the reentrant versions (e.g. gethostbyname_r()) and provide a thread-specific buffer for the return values.

    Alternatively, you can use the getaddrinfo() and getnameinfo() functions, which are designed to be thread-safe.

    getopt()
    The getopt() function is not thread-safe because it uses global variables (optarg, optind, opterr, optopt) to store its state.

    If you need to use getopt() in a threaded application, you should use the getopt_r() function, which is the reentrant version. It takes pointers to variables that will store the state, making it thread-safe.

    glob()
    The glob() function is not thread-safe because it uses global variables to store its state.

    If you need to use glob() in a threaded application, you should consider using a thread-safe alternative or implementing your own thread-safe globbing mechanism.

    setlocale()
    The setlocale() function modifies the global locale state of the process. This can cause problems in a threaded environment, as one thread changing the locale can affect all other threads.

    Perl tries to mitigate this by using thread-local locales when available (see Locale-specific issues below). However, if your C code needs to call setlocale() directly, you should be aware of the potential issues.

    Consider using thread-local storage to manage locales on a per-thread basis if possible.

    syslog()
    The syslog() function itself is generally thread-safe, but the underlying system facilities it uses may not be.

    If you are embedding Perl and need to log messages from your C code and from Perl, it is recommended to use a single logging mechanism (e.g., a thread-safe logging library) to avoid race conditions and ensure consistent log output.

    tzset()
    The tzset() function updates the global time zone information. This can lead to race conditions in a threaded application if one thread calls tzset() while another thread is performing time-related operations.

    It is generally recommended to avoid calling tzset() directly in a threaded application. If you need to change the time zone, consider doing so only during application initialization or in a way that minimizes contention.

    Other functions
    Many other functions may present a real problem under threads given the circumstances in which they are used. You can go directly to the column 2 replacement, but beware of the ones that are marked. Some of those may be nonexistent or flaky on some platforms.

    Functions that need the environment to be constant

    Since the environment is global to a process, all instances depend on it. One instance changing the environment affects all the other instances. Under threads, any libc call that expects the environment to not change for the duration of its execution will have undefined results if another thread interrupts it at just the wrong time and changes it. These are the functions that the man pages list as being sensitive to that.

endnetent()             gethostid()         setlocale()

execvpe()               getopt()            strftime()

    Perl defines mutexes "ENV_READ_LOCK" and "ENV_READ_UNLOCK" with which to wrap calls to these functions. You need to consider the possibility of deadlock. It is expected that a different mechanism will be in place and preferred for Perl v5.42.

    Locale-specific issues

    C language programs originally had a single locale global to the entire process. This was later found to be inadequate for many purposes, so later extensions changed that, first with Windows, and then POSIX 2008. In Windows, you can change any thread at any time to operate either with a per-thread locale, or with the global one, using a special new libc function. In POSIX, the original API operates only on the global locale, but there is an entirely new API to manipulate either per-thread locales or the global one. As with Windows (but using the new API), a thread can be switched at any time to operate on the global locale, or a per-thread one.

    When one instance changes the global locale, all other instances using the global locale are affected. Almost all the locale-related functions in the list directly under "Dealing with embedded perls and threads" have undefined behavior if another thread interrupts their execution and changes the locale. Under threads, another thread could do exactly that.

    But, on systems that have per-thread locales, starting with Perl v5.28, perl uses them after initialization; the global locale is not used except if XS code has called switch_to_global_locale(). Doing so affects only the thread that called it. If a maximum of one instance is using the global locale, no other instances are affected, the locale of concurrently executing functions in other threads is not changed, and this becomes a non-issue. The C preprocessor symbol "USE_THREAD_SAFE_LOCALE" will be defined if per-thread locales are available and perl has been compiled to use them. The implementation of per-thread locales on some platforms, like most *BSD-based ones, is so buggy that the perl hints files for them deliberately turn off the possibility of using them.

    The converse is that on systems with only a global locale, having different threads using different locales is not likely to work well; and changing the locale is dangerous, often leading to crashes.

    Perl has extensive code to work as well as possible on both types of systems. You should always use Perl_setlocale() to change and query the locale, as it portably works across the range of possibilities.
