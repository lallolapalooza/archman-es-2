NOMBRE

perlos2 - Perl en OS/2, DOS, Win0.3*, Win0.95 y WinNT.

SINOPSIS

Se puede leer este documento en los siguientes formatos:

view perl perlos2

Para leer la versión *.INF* de la documentación (*muy* recomendada) fuera de OS/2, se necesita un lector de IBM (¿disponible en sitios FTP de IBM? (¿URL?)) o incluido con PC DOS 7.0 e IBM Visual Age C++ 3.5.

en *?:\\JUST_ADD\\view.exe*. Esto también da acceso a la documentación *.INF* de EMX (la forma de texto está disponible en */emx/doc* en la distribución de EMX). También hay un visor diferente llamado xview.

DESCRIPCIÓN

Objetivo

El objetivo es hacer de OS/2 una de las plataformas mejor soportadas para usar/construir/desarrollar Perl y *aplicaciones Perl*, así como hacer de Perl el mejor lenguaje para usar en OS/2. El objetivo secundario es intentar que esto funcione también en DOS y Win* (pero no *demasiado*).

El estado actual está bastante cerca de este objetivo. Limitaciones conocidas:

  • Algunos programas *nix usan *fork()* mucho; con los sabores de perl más útiles para OS/2 (hay varios construidos simultáneamente) esto está soportado; pero algunos sabores no lo soportan (por ejemplo, cuando Perl se llama desde REXX). Usar *fork()* después de *use*ar extensiones de carga dinámica no funcionaría con versiones *muy* antiguas de EMX.
  • Necesita un ejecutable de perl separado *perl__.exe* (ver "perl__.exe") si desea usar código PM en su aplicación (como hacen los módulos Perl/Tk u OpenGL Perl) sin tener una ventana de modo de texto presente.

    Si bien usar el *perl.exe* estándar desde una ventana de modo de texto también es posible, he visto casos en los que esto causa una degradación de la estabilidad del sistema. Usar *perl__.exe* evita tal degradación.

  • No hay una forma sencilla de acceder a los objetos WPS. La única forma que conozco es a través de las extensiones "OS2::REXX" y "SOM" (ver OS2::REXX, SOM). Sin embargo, no tenemos acceso a métodos de conveniencia de Object-REXX. (¿Es posible en absoluto? ¿Conozco alguna API de Object-REXX?) La extensión "SOM" (actualmente en texto alfa) puede eventualmente eliminar esta deficiencia; sin embargo, debido al hecho de que DII no es compatible con el módulo "SOM", usar "SOM" no es tan conveniente como uno quisiera.

Por favor, mantenga esta lista actualizada informándome de otros elementos.

Otros OSes

Dado que el port de perl para OS/2 utiliza un entorno EMX notable, puede ejecutarse (y construir extensiones, y -posiblemente- construirse a sí mismo) en cualquier entorno que pueda ejecutar EMX. La lista actual es DOS, DOS dentro de OS/2, Win0.3*, Win0.95 y WinNT. De los muchos sabores de perl, solo uno funciona, ver "*perl_.exe*".

Tenga en cuenta que no todas las características de Perl están disponibles en estos entornos. Esto depende de las características que el *extensor* - lo más probable es que RSX - decidió implementar.

Cf. "Prerrequisitos".

Prerrequisitos

EMX
Se requiere el tiempo de ejecución EMX (puede ser sustituido por RSX). Tenga en cuenta que es posible hacer que *perl_.exe* se ejecute bajo DOS sin ningún soporte externo enlazando *emx.exe*/*rsx.exe* a él, ver emxbind(1). Tenga en cuenta que bajo DOS, para obtener mejores resultados, se debe usar el tiempo de ejecución RSX, que tiene muchas más funciones funcionando (como "fork", "popen" y similares). De hecho, RSX es necesario si no hay VCPI presente. Tenga en cuenta que RSX requiere DPMI. Se sabe que muchas implementaciones de DPMI son muy defectuosas, ¡cuidado!

Solo se admite el último tiempo de ejecución, actualmente "0.9d fix 03". Perl puede ejecutarse bajo versiones anteriores de EMX, pero esto no ha sido probado.

Se pueden obtener diferentes partes de EMX de, por ejemplo:

ftp://crydee.sai.msu.ru/pub/comp/os/os2/leo/gnu/emx+gcc/
http://hobbes.nmsu.edu/h-browse.php?dir=/pub/os2/dev/emx/v0.9d/

El componente de tiempo de ejecución debe tener el nombre *emxrt.zip*.

NOTA. Al usar *emx.exe*/*rsx.exe*, es suficiente tenerlos en su ruta. No es necesario especificarlos explícitamente (aunque esto

emx perl_.exe -de 0

también funcionará.)

RSX
Para ejecutar Perl en plataformas DPMI, se necesita el tiempo de ejecución RSX. Esto es necesario bajo DOS dentro de OS/2, Win0.3*, Win0.95 y WinNT (ver "Otros OSes"). RSX no funcionaría solo con VCPI, como lo haría EMX, requiere DMPI.

Teniendo RSX y el último *sh.exe*, se obtiene un entorno totalmente funcional estilo *nix* bajo DOS, por ejemplo, *fork*, `` y pipe-*open* funcionan. De hecho, MakeMaker funciona (para compilación estática), por lo que se puede tener un entorno de desarrollo Perl bajo DOS.

Se puede obtener RSX de, por ejemplo:

http://cd.textfiles.com/hobbesos29804/disk1/EMX09C/
ftp://crydee.sai.msu.ru/pub/comp/os/os2/leo/gnu/emx+gcc/contrib/

Póngase en contacto con el autor en "rainer@mathematik.uni-bielefeld.de".

El último *sh.exe* con hooks de DOS está disponible en

http://www.ilyaz.org/software/os2/

como *sh_dos.zip* o bajo nombres similares que comiencen con "sh", "pdksh", etc.

HPFS
A Perl no le importan los sistemas de archivos, pero la biblioteca de perl contiene muchos archivos con nombres largos, por lo que para instalarla intacta se necesita un sistema de archivos que soporte nombres de archivo largos.

Tenga en cuenta que si no planea compilar el propio perl, puede ser posible engañar a EMX para que trunque los nombres de archivo. Esto no está soportado, lea la documentación de EMX para ver cómo hacerlo.

pdksh
Para iniciar programas externos con líneas de comando complicadas (como con pipes entre ellos y/o entrecomillado de argumentos), Perl usa un shell externo. Con el port de EMX, dicho shell debe llamarse *sh.exe* y ubicarse en las ubicaciones codificadas durante la compilación (generalmente *F:/bin*) o en una ubicación configurable (ver ""PERL_SH_DIR"").

Para obtener mejores resultados, use EMX pdksh. El binario estándar (5.2.14 o posterior) también se ejecuta bajo DOS (con "RSX"), ver

http://www.ilyaz.org/software/os2/

Iniciar programas Perl en OS/2 (y DOS y...)

Inicie su programa Perl *foo.pl* con los argumentos "arg1 arg2 arg3" de la misma manera que en cualquier otra plataforma, usando

perl foo.pl arg1 arg2 arg3

Si desea especificar opciones de perl "-my_opts" para el propio perl (en contraposición a su programa), use

perl -my_opts foo.pl arg1 arg2 arg3

Alternativamente, si usa un shell estilo OS/2, como CMD o 4os2, ponga lo siguiente al principio de su script de perl:

extproc perl -S -my_opts

renombre su programa a *foo.

COMMAND LINE

The command line is parsed by the C library's getopt() routine, which recognizes the following options:

-w
Warns about questionable constructs, such as references to undefined variables and subroutines, and syntax errors that are not fatal. This is usually a good idea.
-W
Turns off warnings.
-x
Ignores the contents of the script itself, treating the script file as a library file. This is primarily useful for building modules that should not be executable on their own. See also perlmod.
-X
Turns off the special processing of files starting with "#!" (see below).
-S
Searches the PATH for the script to run. This is useful if you want to run a script whose name doesn't contain any path information, for example, perl foo. Perl will then look for foo in the directories specified by the PATH environment variable. If you specify a full path to the script, it will be executed directly.
-P
Process a file using the C preprocessor. This is useful for embedding C code within Perl scripts, or for using conditional compilation within Perl scripts.
-s
Enables the use of switchable options. If you use the -s switch, then any command-line arguments that look like switches (e.g., -d, -t) will be treated as boolean variables that are set to true if the switch is present on the command line. For example, if you run perl -s myscript.pl -d, then the variable $d will be true within myscript.pl. Note that the -s switch itself is not processed this way.
-u
Prints a usage message and exits. This is useful for providing help information to users of your script.
-v
Prints the version of Perl you are running and exits.
-V
Prints detailed information about the Perl installation and exits.
-d
Turns on the debugger. This is useful for stepping through your script and inspecting variables.
-D
Turns on debugging output from the Perl interpreter. This is useful for diagnosing problems with Perl itself.
-c
Checks the syntax of the script without actually running it. This is useful for catching syntax errors before you run your script.
-MM
Load the module M before running the script. This is equivalent to putting use M; at the beginning of your script.
-mM
Load the module M before running the script, but do not execute its import() method. This is useful for modules that should be loaded but not automatically imported.
-a
Autof splits lines into the @F array. This is equivalent to putting $, = "\n"; @F = split; at the beginning of your script.
-F/pattern/
Sets the default split pattern for the -a switch. The default pattern is whitespace.
-i[extension]
Edits files in place. This is equivalent to using the $^I variable. If extension is supplied, Perl will create a backup of each file with that extension. For example, perl -i.bak -pe 's/foo/bar/' file will replace "foo" with "bar" in file, and create a backup named file.bak.
-n
Wraps the script in a while (<>) { ... } loop. This is useful for processing files line by line.
-p
Wraps the script in a while (<>) { ...; print } loop. This is useful for making simple modifications to files.
-l[octal_code]
Enables automatic line ending processing. If octal_code is supplied, it is used as the input and output line ending. Otherwise, $\ is set to \n, and input lines are chomped. This is equivalent to setting the $/ and $\ variables.
-0[octal_code]
Specifies the default input record separator. The default is \n (newline). If octal_code is given, that is the input record separator.

Any other arguments are treated as the name of the script to execute, followed by any arguments to be passed to the script.

For example, to run a script named foo.cmd with arguments arg1, arg2, and arg3, you would type:

perl foo.cmd arg1 arg2 arg3

If foo.cmd is not in the current directory, you can use the -S switch to search the PATH:

perl -S foo arg1 arg2 arg3

Note that because of OS/2 limitations, the full path of the Perl script is not available when using "extproc". Thus, you are forced to use the -S Perl switch, and your script must be on the PATH. As a bonus, if you know the full path to your script, you can still start it with:

perl ../../blah/foo.cmd arg1 arg2 arg3

(Note that the argument "-my_opts" is handled by the "extproc" line in your script; see "extproc" on the first line).

To understand what the above magic does, read the Perl documentation about the -S switch (see perlrun) and about "extproc" (see cmdref):

view perl perlrun
man perlrun
view cmdref extproc
help extproc

or use whatever method you prefer.

There are also endless possibilities to use executable extensions of 4OS2, associations of WPS, and so on. However, if you use a *nix-like shell (like sh.exe supplied in the binary distribution), you need to follow the syntax specified in "Command Switches" in perlrun.

Note that the -S switch supports scripts with additional extensions .cmd, .btm, .bat, .pl as well.

Starting OS/2 (and DOS) programs under Perl

This is what system() (see "system" in perlfunc), `` (see "I/O Operators" in perlop), and open pipe (see "open" in perlfunc) are for. (Avoid exec() (see "exec" in perlfunc) unless you know what you are doing).

Note, however, that to use some of these operators, you need to have a sh-syntax shell installed (see "Pdksh", "Frequently asked questions"), and Perl must be able to find it (see ""PERL_SH_DIR"").

The cases when the shell is used are:

1.
One-argument system() (see "system" in perlfunc), exec() (see "exec" in perlfunc) with redirection or shell meta-characters;
2.
Pipe-open (see "open" in perlfunc) with the command which contains redirection or shell meta-characters;
3.
Backticks `` (see "I/O Operators" in perlop) with the command which contains redirection or shell meta-characters;
4.
If the executable called by system()/exec()/pipe-open()/`` is a script with the "magic" "#!" line or "extproc" line which specifies a shell;
5.
If the executable called by system()/exec()/pipe-open()/`` is a script without a "magic" line, and $ENV{EXECSHELL} is set to a shell;
6.
If the executable called by system()/exec()/pipe-open()/`` is not found (is this remark obsolete?);
7.
For globbing (see "glob" in perlfunc, "I/O Operators" in perlop) (obsolete? Perl uses built-in globbing nowadays...).

For the sake of speed, in the common case, in the above algorithms backslashes in the command name are not considered as shell metacharacters.

Perl starts scripts that begin with the cookies "extproc" or "#!" directly, without shell intervention. Perl uses the same algorithm to find the executable as pdksh: if the path on the "#!" line does not work, and contains "/", then the directory part of the executable is ignored, and the executable is searched for in . and on the PATH. To find arguments for these scripts, Perl uses a different algorithm than pdksh: up to 3 arguments are recognized, and trailing whitespace is stripped.

If a script does not contain such a cookie, then to avoid calling sh.exe, Perl uses the same algorithm as pdksh: if $ENV{EXECSHELL} is set, the script is given as the first argument to this command; if not set, then "$ENV{COMSPEC} /c" is used (or a hardwired guess if $ENV{COMSPEC} is not set).

When starting scripts directly, Perl uses exactly the same algorithm as for the search of a script given by the -S command-line option: it will look in the current directory, then on components of $ENV{PATH} using the following order of appended extensions: no extension, .cmd, .btm, .bat, .pl.

Note that Perl will start looking for scripts only if OS/2 cannot start the specified application, thus "system 'blah'" will not look for a script if there is an executable file blah.exe anywhere on the PATH. In other words, the PATH is essentially searched twice: once by the OS for an executable, then by Perl for scripts.

Note also that executable files on OS/2 can have an arbitrary extension, but .exe will be automatically appended if no dot is present in the name. The workaround is simple: since blah. and blah denote the same file (at least on FAT and HPFS file systems), to start an executable residing in file n:/bin/blah (no extension) give an argument "n:/bin/blah." (dot appended) to system().

Perl will start PM programs from a VIO (=text-mode) Perl process in a separate PM session; the opposite is not true: when you start a non-PM program from a PM Perl process, Perl will not run it in a separate session. If a separate session is desired, either ensure that a shell will be used, as in "system 'cmd /c myprog'", or start it using optional arguments to system() documented in the "OS2::Process" module. This is considered a feature.

Frequently asked questions

"It does not work"

Perl binary distributions come with a testperl.cmd script which tries to detect common problems with misconfigured installations. There is a pretty large chance it will discover which step of the installation you managed to goof. ";-)"

I cannot run external programs

  • Did you run your programs with the -w switch? See "Starting OS/2 (and DOS) programs under Perl".
  • Are you trying to run internal shell commands, like `copy a b` (internal to cmd.exe), or `glob a*b` (internal to ksh)? You need to specify your shell explicitly, like `cmd /c copy a b`, since Perl cannot deduce which commands are internal to your shell.

I cannot embed Perl into my program, or use perl.dll from my program.

Is your program EMX-compiled with "-Zmt -Zcrtdll"?
Well, nowadays the Perl DLL should be usable from a differently compiled program too... If you can run Perl code from REXX scripts (see OS2::REXX), then there are some other aspects of interaction that are overlooked by the current hackish code to support differently-compiled principal programs.

If all else fails, you need to build a stand-alone DLL for Perl. Contact me, I did it once. Sockets would not work, as would many other things.

Did you use ExtUtils::Embed?
Some time ago I had reports it did not work. Nowadays it is checked in the Perl test suite, so grep the ./t subdirectory of the build tree (as well as *.t files in the ./lib subdirectory) to find how it should be done "correctly".

`` and pipe-"open" do not work under DOS

This might be a variant of just "I cannot run external programs", or a deeper problem. Basically: you need RSX (see "Prerequisites") for these commands to work, and you may need a port of sh.exe that understands command arguments. One such port is listed in "Prerequisites" under RSX. Do not forget to set the variable ""PERL_SH_DIR"" as well.

DPMI is required for RSX.

Cannot start "find.exe "pattern" file"

The whole idea of the "standard C API to start applications" is that the forms "foo" and "foo" of program arguments are completely interchangeable. find breaks this paradigm;

find "pattern" file
find pattern file

are not equivalent; find cannot be started directly using the above API. One needs a way to surround the double quotes in some other quoting construction, necessarily having an extra non-Unixish shell in between.

Use one of

system 'cmd', '/c', 'find "pattern" file';
`cmd /c 'find "pattern" file'`

This would start find.exe via cmd.exe via "sh.exe" via "perl.exe", but this is the price to pay if you want to use a non-conforming program.

INSTALLATION

Instalación automática de binarios

La forma más cómoda de instalar una distribución binaria de perl es a través del instalador de perl install.exe. Simplemente sigue las instrucciones y el 99% de los problemas de instalación desaparecerán.

Sin embargo, ten en cuenta que necesitas tener unzip.exe en tu PATH y el entorno EMX en ejecución. Esto último significa que si acabas de instalar EMX e hiciste todos los cambios necesarios en Config.sys, es posible que necesites reiniciar entre medias. Comprueba el tiempo de ejecución de EMX ejecutando

emxrev

El instalador binario también crea una carpeta en tu escritorio con algunos objetos útiles. Si necesitas cambiar algunos aspectos del funcionamiento del instalador binario, no dudes en editar el archivo Perl.pkg. Esto puede ser útil, por ejemplo, si necesitas ejecutar el instalador muchas veces y no quieres realizar muchos cambios interactivos en la GUI.

Cosas que no se tienen en cuenta con la instalación automática de binarios:

"PERL_BADLANG"
Puede ser necesario si cambias tu página de códigos después de la instalación de perl y el nuevo valor no es compatible con EMX. Consulta ""PERL_BADLANG"".
"PERL_BADFREE"
Consulta ""PERL_BADFREE"".
Config.pm
Este archivo reside en algún lugar profundo de la ubicación donde instalaste tu biblioteca de perl, descúbrelo ejecutando 
perl -MConfig -le "print $INC{'Config.pm'}"

Si bien la mayoría de los valores importantes de este archivo son actualizados por el instalador binario, algunos de ellos pueden necesitar ser editados manualmente. No conozco tales datos, por favor, mantenme informado si encuentras alguno. Además, los cambios manuales en la versión instalada pueden necesitar ir acompañados de una edición de este archivo.

NOTA. Debido a un error tipográfico, el instalador binario de 5.00305 instalaría una variable "PERL_SHPATH" en Config.sys. Por favor, elimina esta variable y pon "PERL_SH_DIR" en su lugar.

Instalación manual de binarios

A partir de la versión 5.00305, la distribución binaria de perl para OS/2 viene dividida en 11 componentes. Desafortunadamente, para permitir una instalación binaria configurable, las rutas de los archivos en los archivos zip no son absolutas, sino relativas a algún directorio.

Ten en cuenta que la extracción con las rutas almacenadas sigue siendo necesaria (por defecto con unzip, especifica "-d" a pkunzip). Sin embargo, necesitas saber dónde extraer los archivos. También necesitas cambiar manualmente las entradas en Config.sys para reflejar dónde pusiste los archivos. Ten en cuenta que si tienes un descompresor primitivo (como "pkunzip"), puedes obtener muchas advertencias/errores durante la descompresión. Actualiza a "(w)unzip".

A continuación, se muestra un ejemplo de lo que hay que hacer para reproducir la configuración en mi máquina. En VIEW.EXE puedes presionar "Ctrl-Insert" ahora y copiar y pegar desde el archivo resultante, creado en el directorio desde el que iniciaste VIEW.EXE.

Para cada componente, mencionamos variables de entorno relacionadas con cada directorio de instalación. O elige directorios que coincidan con tus valores de las variables, o crea/añade variables para tener en cuenta los directorios.

Ejecutables VIO y PM de Perl (enlazados dinámicamente)
unzip perl_exc.zip *.exe *.ico -d f:/emx.add/bin
unzip perl_exc.zip *.dll -d f:/emx.add/dll

(tener los directorios con "*.exe" en PATH, y "*.dll" en LIBPATH);

Ejecutable VIO de Perl (enlazado estáticamente)
unzip perl_aou.zip -d f:/emx.add/bin

(tener el directorio en PATH);

Ejecutables para utilidades de Perl
unzip perl_utl.zip -d f:/emx.add/bin

(tener el directorio en PATH);

Biblioteca principal de Perl
unzip perl_mlb.zip -d f:/perllib/lib

Si este directorio es exactamente el mismo que el prefijo que se compiló en perl.exe, no necesitas cambiar nada. Sin embargo, para que perl encuentre la biblioteca si utilizas una ruta diferente, necesitas "set PERLLIB_PREFIX" en Config.sys, consulta ""PERLLIB_PREFIX"".

Módulos adicionales de Perl
unzip perl_ste.zip -d f:/perllib/lib/site_perl/5.42.0/

La misma observación que aplica arriba. Adicionalmente, si este directorio no es uno de los directorios en @INC (y @INC está influenciado por "PERLLIB_PREFIX"), necesitas poner este directorio y el subdirectorio ./os2 en la variable "PERLLIB" o "PERL5LIB". No uses "PERL5LIB" a menos que ya lo tengas configurado. Consulta "ENVIRONMENT" en perl.

[¡Comprueba si este directorio de extracción sigue siendo aplicable con el nuevo diseño de la estructura de directorios!]

Herramientas para compilar módulos de Perl
unzip perl_blb.zip -d f:/perllib/lib

Misma observación que para perl_ste.zip.

Páginas de manual para Perl y utilidades
unzip perl_man.zip -d f:/perllib/man

Este directorio debería estar en "MANPATH". Necesitas tener un man funcional para acceder a estos archivos.

Páginas de manual para módulos de Perl
unzip perl_mam.zip -d f:/perllib/man

Este directorio debería estar en "MANPATH". Necesitas tener un man funcional para acceder a estos archivos.

Fuente de la documentación de Perl
unzip perl_pod.zip -d f:/perllib/lib

Esto es utilizado por el programa "perldoc" (ver perldoc), y puede ser utilizado para generar documentación HTML utilizable por navegadores WWW, y documentación en una infinidad de otros formatos: "info", "LaTeX", "Acrobat", "FrameMaker" y así sucesivamente. [Usa programas como pod2latex, etc.]

Manual de Perl en formato .INF
unzip perl_inf.zip -d d:/os2/book

Este directorio debería estar en "BOOKSHELF".

Pdksh
unzip perl_sh.zip -d f:/bin

Esto es utilizado por perl para ejecutar comandos externos que requieren explícitamente un shell, como los comandos que usan redirección y metacaracteres de shell. También se utiliza en lugar de /bin/sh explícito.

Configura "PERL_SH_DIR" (ver ""PERL_SH_DIR"") si mueves sh.exe de la ubicación anterior.

Nota. Puede ser posible usar algún otro shell compatible con sh (no probado).

Después de instalar los componentes que necesitabas y actualizar Config.sys correspondientemente, necesitas editar manualmente Config.pm. Este archivo reside en algún lugar profundo de la ubicación donde instalaste tu biblioteca de perl, descúbrelo ejecutando

perl -MConfig -le "print $INC{'Config.pm'}"

Necesitas corregir todas las entradas que parezcan rutas de archivo (actualmente empiezan con "f:/").

Advertencia

La instalación automática y manual de perl deja rutas precompiladas dentro de los ejecutables de perl. Si bien estas rutas son sobrescritas (ver ""PERLLIB_PREFIX"", ""PERL_SH_DIR""), algunas personas pueden preferir la edición binaria de las rutas dentro de los ejecutables/DLLs.

Acceso a la documentación

Dependiendo de cómo compilaste/instalaste perl, puedes tener (de lo contrario idéntica) documentación de Perl en los siguientes formatos:

Archivo OS/2 .INF

Probablemente la forma más cómoda. En OS/2, visualízalo como

view perl
view perl perlfunc
view perl less
view perl ExtUtils::MakeMaker

(actualmente los dos últimos pueden apuntar a una ubicación incorrecta, pero esto puede mejorar pronto). En Win* ver "SYNOPSIS".

pod2ipf > perl.ipf

en el directorio /perllib/lib/pod, luego

ipfc /inf perl.ipf

(Espera muchos errores durante ambos pasos). Ahora muévelo a tu ruta de BOOKSHELF.

Building static modules

This is a more involved process because you have to identify all the modules that are dynamically loaded by the Perl interpreter. The MakeMaker module has a "test" target that should identify them. Then you need to build these modules statically linked into the Perl executable. The Perl builder is designed to do that, but it requires you to know which modules are needed.

It is a lot simpler to create an executable with a specific set of statically loaded modules. We describe this first, and then continue to the general case.

We assume that you have already generated a Perl executable, perl_.exe, that includes a minimal set of extensions. Now you want to build the full set of extensions into a new executable that you will distribute. The procedure is as follows:

1.
Generate a new dummy Makefile.PL in an empty directory. It should look like this:
use ExtUtils::MakeMaker;
WriteMakefile(
    NAME => 'dummy',
    VERSION_FROM => 'perl.h', /* Version info is not used, but required */
    OBJECT => 'perlmain.obj', /* A dummy object file */
);
2.
Run the Perl builder of your choice, using the dummy Makefile.PL. The first iteration might look like this:
perl_.exe Makefile.PL |& tee 00c
make perl                  |& tee 00p
3.
Examine perlmain.c (which is generated by the Makefile) and find the list of newXS() calls near the end. These are the dynamically loaded modules. The first run should load only a few modules. Copy the generated perl.exe executable to perl_5.8.2.exe.
4.
Copy the dummy Makefile.PL to a new directory. Make sure that the generated libraries (.a files) are in the current directory. Generate the new Makefile.PL with the following additions:
use ExtUtils::MakeMaker;
use Config;
use File::Find;
my @dirs;
find( sub { push @dirs, $File::Find::name if -d },
      "$Config{archlib}/auto");
my @libs;
foreach my $dir (@dirs) {
    my $file = "$dir.a";
    push @libs, $file if -e $file;
}
WriteMakefile(
    NAME              => 'dummy',
    VERSION_FROM      => 'perl.h',
    OBJECT            => 'perlmain.obj',
    LIBS              => [ "-L.", @libs ],
    dynamic_lib       => 1,
    PERL_CORE         => 1, # Needed to prevent build of extensions
);
5.
Run the Perl builder again. This time, you should see more modules being linked. Examine perlmain.c again. You'll notice that the list of dynamically loaded modules has grown. Copy the generated perl.exe to perl_5.8.2.exe.
6.
Repeat steps 4 and 5 until the list of dynamically loaded modules in perlmain.c stabilizes, i.e., no new modules are added during subsequent iterations.
7.
Once the list of modules has converged, you have all the necessary .a libraries for these Perl modules in the places where the Perl builder can find them. Use the Perl builder: change to an empty directory, create a "dummy" Makefile.PL again, and run
perl_5.8.2.exe Makefile.PL |& tee 00c
make perl                  |& tee 00p
This should create an executable ./perl.exe with all the statically loaded extensions built in. Compare the generated perlmain.c files to make sure that during the iterations the number of loaded extensions only increases. Rename ./perl.exe to perl_5.8.2.exe on the "PATH".
When it converges, you have a functional variant of perl_5.8.2.exe; copy it to "perl_.exe". You are done with the generation of the local Perl installation.
8.
Make sure that the installed modules are actually installed in the location of the new Perl, and are not inherited from entries of @INC given for inheritance from the older versions of Perl: set "PERLLIB_582_PREFIX" to redirect the new version of Perl to a new location, and copy the installed files to this new location. Redo the tests to make sure that the versions of modules inherited from older versions of Perl are not needed.

Actually, the log output of pod2ipf(1) during step 6 gives very detailed info about which modules are loaded from which place; so you may use it as an additional verification tool.

Check that some temporary files did not make it into the perl install tree. Run something like this

pfind . -f "!(/\.(pm|pl|ix|al|h|a|lib|txt|pod|imp|bs|dll|ld|bs|inc|xbm|yml|cgi|uu|e2x|skip|packlist|eg|cfg|html|pub|enc|all|ini|po|pot)$/i or /^\w+$/") | less

in the install tree (both top one and sitelib one).

Compress all the DLLs with lxlite. The tiny .exe can be compressed with "/c:max" (the bug only appears when there is a fixup in the last 6 bytes of a page (?); since the tiny executables are much smaller than a page, the bug will not hit). Do not compress "perl_.exe" - it would not work under DOS.

9.
Now you can generate the binary distribution. This is done by running the test of the CPAN distribution "OS2::SoftInstaller". Tune up the file test.pl to suit the layout of the current version of Perl first. Do not forget to pack the necessary external DLLs accordingly. Include the description of the bugs and test suite failures you could not fix. Include the small-stack versions of Perl executables from the Perl build directory.

Include perl5.def so that people can relink the perl DLL preserving the binary compatibility, or can create compatibility DLLs. Include the diff files ("diff -pu old new") of fixes you did so that people can rebuild your version. Include perl5.map so that one can use remote debugging.

10.
Share what you did with the other people. Relax. Enjoy the fruits of your work.
11.
Brace yourself for thanks, bug reports, hate mail, and spam coming as result of the previous step. No good deed should remain unpunished!

Making executables with a custom search paths

The default perl executable is flexible enough to support most usages. However, one may want something yet more flexible; for example, one may want to find Perl DLL relatively to the location of the EXE file; or one may want to ignore the environment when setting the Perl-library search patch, etc.

If you are comfortable with the embedding interface (see perlsembed), such things are easy to do by repeating the steps outlined in "Making executables with a custom collection of statically loaded extensions", and doing more comprehensive edits to main() of perlmain.c. People with little desire to understand Perl can just rename main(), and do necessary modifications in a custom main() which calls the renamed function at the appropriate time.

However, there is a third way: the perl DLL exports the main() function and several callbacks to customize the search path. Below is a complete example of a "Perl loader" which

1.
Looks for Perl DLL in the directory "$exedir/../dll";
2.
Prepends the above directory to "BEGINLIBPATH";
3.
Fails if the Perl DLL found via "BEGINLIBPATH" is different from what was loaded in step 1; e.g., another process could have loaded it from "LIBPATH" or from a different value of "BEGINLIBPATH". In these cases, one needs to modify the system settings so that this other process either does not run, or loads the DLL from "BEGINLIBPATH" with "LIBPATHSTRICT=T" (available with kernels after September 2000).
4.

(Mal)características específicas del puerto OS/2

"setpriority", "getpriority"

Ten en cuenta que estas funciones son compatibles con *nix, no con los puertos más antiguos de '94 - '95. Las prioridades son absolutas, van de 32 a -95, cuanto más bajo es, más rápido. 0 es la prioridad por defecto.

ADVERTENCIA. Llamar a "getpriority" en un proceso inexistente podría bloquear el sistema antes del fixpak22 de Warp3. A partir de Warp3, Perl utilizará una solución alternativa: aborta getpriority() si el proceso no está presente. Esto no es posible en versiones anteriores "2.*", y de todos modos tiene una condición de carrera.

system()

La forma de varios argumentos de system() permite un argumento numérico adicional. El significado de este argumento se describe en OS2::Process.

Al buscar un programa para ejecutar, Perl primero pregunta al SO que busque ejecutables en "PATH" (OS/2 añade la extensión .exe si no hay extensión presente). Si no se encuentra, busca un script con extensiones posibles añadidas en este orden: sin extensión, .cmd, .btm, .bat, .pl. Si se encuentra, Perl comprueba el inicio del archivo en busca de cadenas mágicas "#!" y "extproc ". Si se encuentran, Perl utiliza el resto de la primera línea como inicio de la línea de comandos para ejecutar este script. La única manipulación realizada en la primera línea es la extracción de argumentos (actualmente hasta 3), e ignorando la parte de la ruta del nombre del "intérprete" si no se puede encontrar usando la ruta completa.

Por ejemplo, "system 'foo', 'bar', 'baz'" puede llevar a Perl a encontrar C:/emx/bin/foo.cmd con la primera línea siendo

extproc /bin/bash    -x   -c

Si no se encuentra /bin/bash.exe, entonces Perl busca un ejecutable bash.exe en "PATH". Si se encuentra en C:/emx.add/bin/bash.exe, entonces el system() anterior se traduce a

system qw(C:/emx.add/bin/bash.exe -x -c C:/emx/bin/foo.cmd bar baz)

Se realiza una traducción adicional: en lugar de /bin/sh, Perl utiliza el shell codificado o personalizado (consulta ""PERL_SH_DIR"").

La búsqueda anterior de "intérprete" es recursiva: si no se encuentra el ejecutable bash, pero sí se encuentra bash.btm, Perl investigará su primera línea, etc. El único límite codificado en la profundidad de la recursión es implícito: hay un límite de 4 en el número de argumentos adicionales insertados antes de los argumentos reales dados a system(). En particular, si no se especifican argumentos adicionales en las primeras líneas "mágicas", entonces el límite de profundidad es 4.

Si Perl descubre que el ejecutable encontrado es de tipo PM cuando la sesión actual no lo es, iniciará un nuevo proceso en una sesión separada del tipo necesario. Llama a través de "OS2::Process" para deshabilitar esta magia.

ADVERTENCIA. Debido a la lógica descrita, necesitas especificar explícitamente la extensión .com si es necesario. Además, si se solicita el ejecutable perl5.6.1, Perl no buscará perl5.6.1.exe. [Esto puede cambiar en el futuro.]

"extproc" en la primera línea

Si los primeros caracteres de un script de Perl son "extproc ", esta línea se trata como una línea "#!", por lo tanto, todos los interruptores de esta línea se procesan (dos veces si el script se inició a través de cmd.exe). Consulta "DESCRIPCIÓN" en perlrun.

Centralized management of resources

Since to call certain OS/2 API one needs to have a correctly initialized "Win" subsystem, OS/2-specific extensions may require getting "HAB"s and "HMQ"s. If an extension would do it on its own, another extension could fail to initialize.

Perl provides a centralized management of these resources:

"HAB"
To get the HAB, the extension should call "hab = perl_hab_GET()" in C. After this call is performed, "hab" may be accessed as "Perl_hab". There is no need to release the HAB after it is used.
If by some reasons perl.h cannot be included, use
extern int Perl_hab_GET(void);
instead.
"HMQ"
There are two cases:
  • the extension needs an "HMQ" only because some API will not work otherwise. Use "serve = 0" below.
  • the extension needs an "HMQ" since it wants to engage in a PM event loop. Use "serve = 1" below.

To get an "HMQ", the extension should call "hmq = perl_hmq_GET(serve)" in C. After this call is performed, "hmq" may be accessed as "Perl_hmq".

To signal to Perl that HMQ is not needed any more, call perl_hmq_UNSET(serve). Perl process will automatically morph/unmorph itself into/from a PM process if HMQ is needed/not-needed. Perl will automatically enable/disable "WM_QUIT" message during shutdown if the message queue is served/not-served.

NOTE. If during a shutdown there is a message queue which did not disable WM_QUIT, and which did not process the received WM_QUIT message, the shutdown will be automatically cancelled. Do not call perl_hmq_GET(1) unless you are going to process messages on an orderly basis.

Treating errors reported by OS/2 API
There are two principal conventions (it is useful to call them "Dos*" and "Win*" - though this part of the function signature is not always determined by the name of the API) of reporting the error conditions of OS/2 API. Most of "Dos*" APIs report the error code as the result of the call (so 0 means success, and there are many types of errors). Most of "Win*" API report success/fail via the result being "TRUE"/ "FALSE"; to find the reason for the failure one should call WinGetLastError() API.
Some "Win*" entry points also overload a "meaningful" return value with the error indicator; having a 0 return value indicates an error. Yet some other "Win*" entry points overload things even more, and 0 return value may mean a successful call returning a valid value 0, as well as an error condition; in the case of a 0 return value one should call WinGetLastError() API to distinguish a successful call from a failing one.
By convention, all the calls to OS/2 API should indicate their failures by resetting $^E. All the Perl-accessible functions which call OS/2 API may be broken into two classes: some die()s when an API error is encountered, the other report the error via a false return value (of course, this does not concern Perl-accessible functions which expect a failure of the OS/2 API call, having some workarounds coded).
Obviously, in the situation of the last type of the signature of an OS/2 API, it is must more convenient for the users if the failure is indicated by die()ing: one does not need to check $^E to know that something went wrong. If, however, this solution is not desirable by some reason, the code in question should reset $^E to 0 before making this OS/2 API call, so that the caller of this Perl-accessible function has a chance to distinguish a success-but-0-return value from a failure. (One may return undef as an alternative way of reporting an error.)
The macros to simplify this type of error propagation are
CheckOSError(expr)
Returns true on error, sets $^E. Expects expr() be a call of "Dos*"-style API.
CheckWinError(expr)
Returns true on error, sets $^E. Expects expr() be a call of "Win*"-style API.
SaveWinError(expr)
Returns "expr", sets $^E from WinGetLastError() if "expr" is false.
"SaveCroakWinError(expr,die,name1,name2)"
Returns "expr", sets $^E from WinGetLastError() if "expr" is false, and die()s if "die" and $^E are true. The message to die is the concatenated strings "name1" and "name2", separated by ": " from the contents of $^E.
"WinError_2_Perl_rc"
Sets "Perl_rc" to the return value of WinGetLastError().
"FillWinError"
Sets "Perl_rc" to the return value of WinGetLastError(), and sets $^E to the corresponding value.
FillOSError(rc)
Sets "Perl_rc" to "rc", and sets $^E to the corresponding value.

Why strange names?

Since Perl processes the "#!"-line (cf. "DESCRIPTION" in perlrun, "Command Switches" in perlrun, "No Perl script found in input" in perldiag), it should know when a program is a Perl. There is some naming convention which allows Perl to distinguish correct lines from wrong ones. The above names are almost the only names allowed by this convention which do not contain digits (which have absolutely different semantics).

Why dynamic linking?

Well, having several executables dynamically linked to the same huge library has its advantages, but this would not substantiate the additional work to make it compile. The reason is the complicated-to-developers but very quick and convenient-to-users "hard" dynamic linking used by OS/2.

There are two distinctive features of the dyna-linking model of OS/2: first, all the references to external functions are resolved at the compile time; second, there is no runtime fixup of the DLLs after they are loaded into memory. The first feature is an enormous advantage over other models: it avoids conflicts when several DLLs used by an application export entries with the same name. In such cases "other" models of dyna-linking just choose between these two entry points using some random criterion - with predictable disasters as results. But it is the second feature which requires the build of perl.dll.

The address tables of DLLs are patched only once, when they are loaded. The addresses of the entry points into DLLs are guaranteed to be the same for all the programs which use the same DLL. This removes the runtime fixup - once DLL is loaded, its code is read-only.

While this allows some (significant?) performance advantages, this makes life much harder for developers, since the above scheme makes it impossible for a DLL to be "linked" to a symbol in the .EXE file. Indeed, this would need a DLL to have different relocations tables for the (different) executables which use this DLL.

However, a dynamically loaded Perl extension is forced to use some symbols from the perl executable, e.g., to know how to find the arguments to the functions: the arguments live on the perl internal evaluation stack. The solution is to put the main code of the interpreter into a DLL, and make the .EXE file which just loads this DLL into memory and supplies command-arguments. The extension DLL cannot link to symbols in .EXE, but it has no problem linking to symbols in the .DLL.

This *greatly* increases the load time for the application (as well as complexity of the compilation). Since interpreter is in a DLL, the C RTL is basically forced to reside in a DLL as well (otherwise extensions would not be able to use CRT). There are some advantages if you use different flavors of perl, such as running perl.exe and perl__.exe simultaneously: they share the memory of perl.dll.

NOTE. There is one additional effect which makes DLLs more wasteful: DLLs are loaded in the shared memory region, which is a scarse resource given the 512M barrier of the "standard" OS/2 virtual memory. The code of .EXE files is also shared by all the processes which use the particular .EXE, but they are "shared in the private address space of the process"; this is possible because the address at which different sections of the .EXE file are loaded is decided at compile-time, thus all the processes have these sections loaded at same addresses, and no fixup of internal links inside the .EXE is needed.

Since DLLs may be loaded at run time, to have the same mechanism for DLLs one needs to have the address range of *any of the loaded* DLLs in the system to be available *in all the processes* which did not load a particular DLL yet. This is why the DLLs are mapped to the shared memory region.

Why chimera build?

Current EMX environment does not allow DLLs compiled using Unixish "a.out" format to export symbols for data (or at least some types of data). This forces "omf"-style compile of perl.dll.

Current EMX environment does not allow .EXE files compiled in "omf" format to fork(). fork() is needed for exactly three Perl operations:

  • explicit fork() in the script,
  • "open FH, \"|- \""
  • "open FH, \"-|\"", in other words, opening pipes to itself.

While these operations are not questions of life and death, they are needed for a lot of useful scripts. This forces "a.out"-style compile of perl.exe.

Ofuscación de nombres DLL: 5.6.2 y posteriores

De hecho, la ofuscación de las DLL de extensión se realizó debido a un malentendido del modelo de carga dinámica de OS/2. OS/2 (efectivamente) mantiene dos tablas diferentes de DLL cargadas:

Globales de DLL
aquellas cargadas por el nombre base desde "LIBPATH"; incluidas las asociadas en tiempo de enlace;
específicas de DLL
cargadas por el nombre completo.

Al resolver una solicitud de una DLL global, la tabla de DLL específicas ya cargadas se ignora (efectivamente); además, las DLL específicas se cargan siempre desde la ruta especificada.

Hay/hubo un pequeño giro que hace que este esquema sea frágil: ¿qué hacer con las DLL cargadas desde

"BEGINLIBPATH" y "ENDLIBPATH"
(que dependen del proceso)
. desde "LIBPATH"
que efectivamente depende del proceso (aunque "LIBPATH" es el mismo para todos los procesos).

A menos que "LIBPATHSTRICT" esté configurado en "T" (y el kernel sea posterior al 2000/09/01), dichas DLL se consideran globales. Al cargar una DLL global, primero se busca en la tabla de DLL globales ya cargadas. Debido a esto, el hecho de que un ejecutable cargara una DLL desde "BEGINLIBPATH" y "ENDLIBPATH", o . desde "LIBPATH" puede afectar cuál DLL se carga cuando otro ejecutable solicita una DLL con el mismo nombre. Esta es la razón de la ofuscación específica de la versión del nombre de la DLL para la DLL de perl.

Dado que las DLL de extensión de Perl siempre se cargan con la ruta completa, no es necesario ofuscar sus nombres de forma específica de la versión: su directorio ya refleja la versión correspondiente de perl, y @INC tiene en cuenta la compatibilidad binaria con versiones anteriores. A partir de la 5.6.2, el esquema de ofuscación de nombres se corrige para que sea el mismo que para Perl 5.005_53 (igual que en una popular versión binaria). Por lo tanto, los nuevos Perl podrán resolver los nombres de las DLL de extensión antiguas si @INC permite encontrar sus directorios.

Sin embargo, esto todavía no garantiza que esas DLL puedan ser cargadas. La razón es la ofuscación del nombre de la DLL de Perl. Y dado que las DLL de extensión se enlazan con la DLL de Perl, las DLL de extensión para versiones antiguas cargarían una DLL de Perl antigua y muy probablemente fallarían (ya que los datos en esa DLL no están inicializados correctamente).

Existe una solución parcial (que puede ser completa con kernels OS/2 más recientes): cree una DLL de reenvío con el mismo nombre que la DLL de la versión anterior de Perl, que reenvía los puntos de entrada a la DLL del nuevo Perl. Haga que esta DLL sea accesible en (digamos) el "BEGINLIBPATH" del ejecutable nuevo de Perl. Cuando el nuevo ejecutable acceda a las DLL de extensión del Perl antiguo, solicitarían la DLL del Perl antiguo por nombre, obtendrían el reenviador en su lugar, por lo que efectivamente se enlazarían con la DLL de Perl en ejecución (la nueva).

Esto puede fallar de dos maneras:

  • Se inicia un ejecutable de Perl antiguo cuando un ejecutable nuevo está en ejecución ha cargado una extensión compilada para el ejecutable antiguo (¡ups!). En este caso, el ejecutable antiguo obtendrá una DLL de reenvío en lugar de la DLL de Perl antigua, por lo que se enlazará con la DLL de Perl nueva. Aunque no sea directamente fatal, se comportará igual que el ejecutable nuevo. Esto anula todo el propósito de iniciar explícitamente un ejecutable antiguo.
  • Un ejecutable nuevo carga una extensión compilada para el ejecutable antiguo cuando se está ejecutando un ejecutable de Perl antiguo. En este caso, la extensión no obtendrá el reenviador, con resultados fatales.

Con soporte para "LIBPATHSTRICT" esto puede evitarse, a menos que una de las DLL se inicie desde . de "LIBPATH" (no sé si "LIBPATHSTRICT" afecta a este caso).

OBSERVACIÓN. A menos que los kernels más recientes permitan . en "BEGINLIBPATH" (los más antiguos no lo hacen), este lío no se puede limpiar por completo. (Resulta que a principios de 2002, . no está permitido, pero .\. sí lo está, y tiene el mismo efecto).

OBSERVACIÓN. "LIBPATHSTRICT", "BEGINLIBPATH" y "ENDLIBPATH" no son variables de entorno, aunque cmd.exe las emula en las líneas "SET ...". Desde Perl se puede acceder a ellas mediante Cwd::extLibpath y Cwd::extLibpath_set.

This document describes the OS/2 port of Perl 5.003. It covers building Perl on OS/2, specific issues and features of the OS/2 port.

It's assumed that you have a working understanding of Perl itself. The reader should also be familiar with the OS/2 command line interface, and the general concepts of OS/2 programming.

Frequently asked questions

See the FAQ below for answers to common questions about the OS/2 port.

INSTALLATION

The most straightforward way to install Perl on OS/2 is to use the pre-built binary distribution.

If you want to build Perl yourself, you should start by reading the "INSTALL" file in the top-level directory of the Perl source distribution.

Accessing documentation

The standard Perl documentation is available online in the "pod/" directory of the distribution. You can read it using the "pod2text" utility (or "pod2html", "pod2man" etc.).

For example, to read the documentation for the perl command itself:

    pod2text pod/perl.pod | more

Or using the installed pod2text utility:

    pod2text $PERLINC/pod/perl.pod | more

where $PERLINC is the directory where Perl scripts are installed.

BUILD

The OS/2 port of Perl is built using the EMX compiler suite. You will need EMX version 0.9c or later.

The build process is initiated by running the "Configure" script. This script will ask you a series of questions about your system and your preferences. Answer these questions carefully.

The most important choice you'll make is whether to build a statically linked executable or a dynamically linked one (DLL). The DLL version is generally recommended for most users.

Building a binary distribution

If you intend to distribute the Perl binaries you build to others, you should follow the instructions in the "INSTALL" file regarding the creation of binary distributions.

Building custom .EXE files

To build custom executables, you'll need to edit the "hints/os2.sh" file. This file contains various settings specific to the OS/2 port.

You can also use the "Configure -D" option to override specific settings.

Build FAQ

Q: Why doesn't "Configure" work?

A: Make sure you have EMX installed and in your PATH. Also, ensure you have a recent version of EMX (0.9c or later).

Q: I'm getting errors about missing libraries.

A: This usually means you need to install additional libraries from the EMX distribution, or that your linker path is not set up correctly. Consult the EMX documentation for details.

Specific (mis)features of OS/2 port

Perl flavors

Perl for OS/2 comes in two flavors: a static executable ( perl.exe) and a dynamically linked library ( perl.dll). The DLL version is generally preferred as it allows multiple Perl processes to share the same code segment, reducing memory usage.

The static executable is useful for creating self-contained applications that don't rely on the presence of perl.dll in the system's PATH.

ENVIRONMENT

PERLLIB: This environment variable can be used to specify additional directories where Perl should look for modules. It works the same way as on other platforms.

PATH: Ensure that the directory containing perl.exe (and possibly perl.dll) is in your system's PATH environment variable.

Evolution

The OS/2 port of Perl has evolved significantly since its early days. Initially, it was a direct port of the Unix version, with many limitations. Over time, platform-specific optimizations and features have been added.

A notable change was the introduction of a custom memory allocator, which significantly improved performance. Also, support for OS/2 threads has been gradually improved.

The way external programs are invoked has also been refined. Previously, all external commands were run through the OS/2 command interpreter (CMD.EXE). Now, Perl can directly execute programs that start with a shebang line ("#!") or the "extproc" directive.

The system() function in Perl now uses "CORE::system('cmd.exe', '/c', shift)".

If you have some working code for "OS2::Cmd", please send it to me, I will include it into distribution. I have no need for such a module, so cannot test it.

For the details of the current situation with calling external programs, see "Starting OS/2 (and DOS) programs under Perl". Set us mention a couple of features:

  • External scripts may be called by their basename. Perl will try the same extensions as when processing -S command-line switch.
  • External scripts starting with "#!" or "extproc " will be executed directly, without calling the shell, by calling the program specified on the rest of the first line.

Memory allocation

Perl uses its own malloc() under OS/2 - interpreters are usually malloc-bound for speed, but perl is not, since its malloc is lightning-fast. Perl-memory-usage-tuned benchmarks show that Perl's malloc is 5 times quicker than EMX one. I do not have convincing data about memory footprint, but a (pretty random) benchmark showed that Perl's one is 5% better.

Combination of perl's malloc() and rigid DLL name resolution creates a special problem with library functions which expect their return value to be free()d by system's free(). To facilitate extensions which need to call such functions, system memory-allocation functions are still available with the prefix "emx_" added. (Currently only DLL perl has this, it should propagate to perl_.exe shortly.)

Threads

One can build perl with thread support enabled by providing "-D usethreads" option to Configure. Currently OS/2 support of threads is very preliminary.

Most notable problems:

"COND_WAIT"
may have a race condition (but probably does not due to edge-triggered nature of OS/2 Event semaphores). (Needs a reimplementation (in terms of chaining waiting threads, with the linked list stored in per-thread structure?)?)
os2.c
has a couple of static variables used in OS/2-specific functions. (Need to be moved to per-thread structure, or serialized?)

Note that these problems should not discourage experimenting, since they have a low probability of affecting small programs.
