PERF-STAT(1) Manual de perf PERF-STAT(1)

NOMBRE

perf-stat - Ejecutar un comando y recopilar estadísticas de contadores de rendimiento

SINOPSIS

perf stat [-e <EVENTO> | --event=EVENTO] [-a] <comando>
perf stat [-e <EVENTO> | --event=EVENTO] [-a] -- <comando> [<opciones>]
perf stat [-e <EVENTO> | --event=EVENTO] [-a] record [-o archivo] -- <comando> [<opciones>]
perf stat report [-i archivo]

DESCRIPCIÓN

Este comando ejecuta un comando y recopila estadísticas de contadores de rendimiento del mismo.

OPCIONES

<comando>...

Cualquier comando que puedas especificar en un shell.

record

Ver STAT RECORD.

report

Ver STAT REPORT.

-e, --event=

Seleccionar el evento PMU. La selección puede ser:
•un nombre de evento simbólico (usa perf list para listar todos los eventos)
•un evento PMU bruto en formato rN donde N es un valor hexadecimal que representa la codificación del registro bruto con el diseño de los registros de control de eventos descrito por las entradas en /sys/bus/event_source/devices/cpu/format/*.
•un evento PMU simbólico o bruto seguido opcionalmente por dos puntos y una lista de modificadores de eventos, por ejemplo, cpu-cycles:p. Consulta la página del manual de perf-list(1) para obtener detalles sobre los modificadores de eventos.
•un evento formado simbólicamente como pmu/param1=0x3,param2/ donde param1 y param2 se definen como formatos para el PMU en /sys/bus/event_source/devices/<pmu>/format/* 
'percore' es un calificador de evento que suma los recuentos de eventos para
hilos de hardware en un núcleo. Por ejemplo:
perf stat -A -a -e cpu/event,percore=1/,otherevent ...
•un evento formado simbólicamente como pmu/config=M,config1=N,config2=K/ donde M, N, K son números (en formato decimal, hexadecimal, octal). Los valores aceptables para cada uno de los parámetros config, config1 y config2 se definen por entradas correspondientes en /sys/bus/event_source/devices/<pmu>/format/* 
Tenga en cuenta que las dos últimas sintaxis admiten coincidencia de prefijos y
globbing en el nombre del PMU para simplificar la creación de eventos en
múltiples instancias del mismo tipo de PMU en sistemas grandes (por ejemplo,
PMUs de controlador de memoria). Las instancias de PMU múltiples son típicas para
los PMUs sin núcleo, por lo que el prefijo 'uncore_' también se ignora al
realizar esta coincidencia.

-i, --no-inherit

las tareas hijas no heredan contadores

-p, --pid=<pid>

estadísticas de eventos en el ID de proceso existente (lista separada por comas)

-t, --tid=<tid>

estadísticas de eventos en el ID de hilo existente (lista separada por comas)

-b, --bpf-prog

estadísticas de eventos en el ID de programa bpf existente (lista separada por comas), requiere derechos de root. bpftool-prog podría usarse para encontrar el ID de programa de todos los programas bpf en el sistema. Por ejemplo: 
# bpftool prog | head -n 1
17247: tracepoint  name sys_enter  tag 192d548b9d754067  gpl
# perf stat -e cycles,instructions --bpf-prog 17247 --timeout 1000
Estadísticas de contadores de rendimiento para 'programas BPF 17247':
85.967      ciclos
28.982      instrucciones              #    0.34  insn por ciclo
1.102235068 segundos de tiempo transcurrido

--bpf-counters

Utilizar programas BPF para agregar lecturas de perf_events. Esto permite que múltiples sesiones de perf-stat que cuentan la misma métrica (ciclos, instrucciones, etc.) compartan contadores de hardware. Para usar programas BPF en eventos comunes por defecto, usa "perf config stat.bpf-counter-events=<lista_de_eventos>".

--bpf-attr-map

Con la opción "--bpf-counters", diferentes sesiones de perf-stat comparten información sobre programas BPF y mapas compartidos a través de un hashmap anclado. Usa "--bpf-attr-map" para especificar la ruta de este hashmap anclado. La ruta predeterminada es /sys/fs/bpf/perf_attr_map.

--pfm-events eventos

Selecciona un evento PMU usando la sintaxis libpfm4 (ver http://perfmon2.sf.net) incluyendo soporte para filtros de eventos. Por ejemplo --pfm-events inst_retired:any_p:u:c=1:i. Se pueden pasar más de un evento a la opción usando el separador de comas. Los eventos de hardware y los eventos genéricos de hardware no pueden mezclarse. Estos últimos deben usarse con la opción -e. Las opciones -e y esta pueden mezclarse. Los eventos se pueden agrupar usando la notación {}.

-a, --all-cpus

recopilación a nivel de sistema de todas las CPUs (por defecto si no se especifica destino)

--no-scale

No escalar/normalizar los valores del contador

-d, --detailed

imprimir estadísticas más detalladas, se puede especificar hasta 3 veces 
      -d:          eventos detallados, caché de datos L1 y LLC
   -d -d:     eventos más detallados, eventos dTLB e iTLB
-d -d -d:     eventos muy detallados, añadiendo eventos de prefetch

-r, --repeat=<n>

repetir comando e imprimir promedio + desv. estándar (máx: 100). 0 significa para siempre.

-B, --big-num

imprimir números grandes con separadores de miles según la configuración regional. Habilitado por defecto. Usa "--no-big-num" para deshabilitarlo. La configuración predeterminada se puede cambiar con "perf config stat.big-num=false".

-C, --cpu=

Contar solo en la lista de CPUs proporcionada. Se pueden proporcionar varias CPUs como una lista separada por comas sin espacios: 0,1. Los rangos de CPUs se especifican con -: 0-2. En modo por hilo, esta opción se ignora. La opción -a todavía es necesaria para activar la monitorización a nivel de sistema. Por defecto, se cuenta en todas las CPUs.

-A, --no-aggr

No agregar recuentos entre todas las CPUs monitoreadas.

-n, --null

ejecución nula - No iniciar ningún contador.

Esto puede ser útil para medir solo el tiempo de reloj transcurrido o para evaluar la sobrecarga bruta del propio perf stat, sin ejecutar ningún contador.

-v, --verbose

ser más verboso (mostrar errores al abrir contadores, etc.)

-x SEP, --field-separator SEP

imprimir recuentos usando una salida estilo CSV para que sea fácil importarlos directamente en hojas de cálculo. Las columnas están separadas por la cadena especificada en SEP.

--table

Mostrar el tiempo para cada ejecución (opción -r), en formato de tabla, por ejemplo: 
$ perf stat --null -r 5 --table perf bench sched pipe
Estadísticas de contadores de rendimiento para 'perf bench sched pipe' (5 ejecuciones):
# Tabla de mediciones individuales:
5.189 (-0.293) #
5.189 (-0.294) #
5.186 (-0.296) #
5.663 (+0.181) ##
6.186 (+0.703) ####
# Resultado final:
5.483 +- 0.198 segundos de tiempo transcurrido  ( +-  3.62% )

-G nombre, --cgroup nombre

monitorear solo en el contenedor (cgroup) llamado "nombre". Esta opción solo está disponible en modo por CPU. El sistema de archivos cgroup debe estar montado. Todos los hilos pertenecientes al contenedor "nombre" son monitoreados cuando se ejecutan en las CPUs monitoreadas. Se pueden proporcionar varios cgroups. Cada cgroup se aplica al evento correspondiente, es decir, el primer cgroup al primer evento, el segundo cgroup al segundo evento y así sucesivamente. Es posible proporcionar un cgroup vacío (monitorear todo el tiempo) usando, por ejemplo, -G foo,,bar. Los cgroups deben tener eventos correspondientes, es decir, siempre se refieren a eventos definidos anteriormente en la línea de comandos. Si el usuario desea rastrear múltiples eventos para un cgroup específico, puede usar -e e1 -e e2 -G foo,foo o simplemente usar -e e1 -e e2 -G foo.

Si deseas monitorear, por ejemplo, cycles para un cgroup y también para todo el sistema, se puede usar la siguiente línea de comandos: perf stat -e cycles -G cgroup_name -a -e cycles.

--for-each-cgroup nombre

Expande la lista de eventos para cada cgroup en "nombre" (permite múltiples cgroups separados por coma). También soporta patrones de expresiones regulares para coincidir con múltiples grupos. Esto tiene el mismo efecto que repetir la opción -e y la opción -G para cada evento x nombre. Esta opción no se puede usar con la opción -G/--cgroup.

-o archivo, --output archivo

Imprimir la salida en el archivo designado.

--append

Agregar al archivo de salida designado con la opción -o. Se ignora si no se especifica -o.

LOGGING AND CONTROL

--log-fd

Registra la salida en un descriptor de archivo (fd), en lugar de stderr. Complementario a --output, y mutuamente excluyente con él. Se puede usar --append aquí. Ejemplos: 3>resultados perf stat --log-fd 3 -- $cmd 3>>resultados perf stat --log-fd 3 --append -- $cmd

--control=fifo:ctl-fifo[,ack-fifo], --control=fd:ctl-fd[,ack-fd]

Los fifo/ack-fifo ctl / fd/ack-fd se abren y utilizan de la siguiente manera. Escucha en el descriptor ctl-fd comandos para controlar la medición (enable: habilitar eventos, disable: deshabilitar eventos). Las mediciones se pueden iniciar con eventos deshabilitados usando la opción --delay=-1. Opcionalmente, envía la finalización del comando de control (ack\n) al descriptor ack-fd para sincronizar con el proceso de control. Ejemplo de script de shell bash para habilitar y deshabilitar eventos durante las mediciones: 
#!/bin/bash
ctl_dir=/tmp/
ctl_fifo=${ctl_dir}perf_ctl.fifo
test -p ${ctl_fifo} && unlink ${ctl_fifo}
mkfifo ${ctl_fifo}
exec {ctl_fd}<>${ctl_fifo}
ctl_ack_fifo=${ctl_dir}perf_ctl_ack.fifo
test -p ${ctl_ack_fifo} && unlink ${ctl_ack_fifo}
mkfifo ${ctl_ack_fifo}
exec {ctl_fd_ack}<>${ctl_ack_fifo}
perf stat -D -1 -e cpu-cycles -a -I 1000 \
          --control fd:${ctl_fd},${ctl_fd_ack} \
          -- sleep 30 &
perf_pid=$!
sleep 5 && echo 'enable' >&${ctl_fd} && read -u ${ctl_fd_ack} e1 && echo "enabled(${e1})"
sleep 10 && echo 'disable' >&${ctl_fd} && read -u ${ctl_fd_ack} d1 && echo "disabled(${d1})"
exec {ctl_fd_ack}>&-
unlink ${ctl_ack_fifo}
exec {ctl_fd}>&-
unlink ${ctl_fifo}
wait -n ${perf_pid}
exit $?

--pre, --post

Ganchos pre y post medición, por ejemplo:

perf stat --repeat 10 --null --sync --pre make -s O=defconfig-build/clean -- make -s -j64 O=defconfig-build/ bzImage

-I msecs, --interval-print msecs

Imprime deltas de recuento cada N milisegundos (mínimo: 1ms). El porcentaje de sobrecarga puede ser alto en algunos casos, por ejemplo, con intervalos pequeños, inferiores a 100 ms. Úselo con precaución. Ejemplo: perf stat -I 1000 -e cycles -a sleep 5

Si la métrica existe, se calcula mediante los recuentos generados en este intervalo y la métrica se imprime después de #.

--interval-count times

Imprime deltas de recuento un número fijo de veces. Esta opción debe usarse junto con la opción "-I". Ejemplo: perf stat -I 1000 --interval-count 2 -e cycles -a

--interval-clear

Borra la pantalla antes del siguiente intervalo.

--timeout msecs

Detiene la sesión perf stat e imprime deltas de recuento después de N milisegundos (mínimo: 10 ms). Esta opción no es compatible con la opción "-I". Ejemplo: perf stat --time 2000 -e cycles -a

--metric-only

Solo imprime métricas calculadas. Imprímelas en una sola línea. No muestre ningún valor bruto. No compatible con --per-thread.

--per-socket

Agrega recuentos por socket de procesador para mediciones en modo de sistema completo. Este es un modo útil para detectar desequilibrios entre sockets. Para habilitar este modo, use --per-socket además de -a. (sistema completo). La salida incluye el número de socket y el número de procesadores en línea en ese socket. Esto es útil para evaluar la cantidad de agregación.

--per-die

Agrega recuentos por die de procesador para mediciones en modo de sistema completo. Este es un modo útil para detectar desequilibrios entre dies. Para habilitar este modo, use --per-die además de -a. (sistema completo). La salida incluye el número de die y el número de procesadores en línea en ese die. Esto es útil para evaluar la cantidad de agregación.

--per-cluster

Agrega recuentos por clúster de procesador para mediciones en modo de sistema completo. Este es un modo útil para detectar desequilibrios entre clústeres. Para habilitar este modo, use --per-cluster además de -a. (sistema completo). La salida incluye el número de clúster y el número de procesadores en línea en ese clúster. Esto es útil para evaluar la cantidad de agregación. La información del ID del clúster y las CPU relacionadas se puede obtener de /sys/devices/system/cpu/cpuX/topology/cluster_{id, cpus}.

--per-cache

Agrega recuentos por instancia de caché para mediciones en modo de sistema completo. Por defecto, la agregación se realiza para el nivel de caché en el índice más alto del sistema. Para especificar un nivel particular, mencione el nivel de caché junto con la opción en el formato [Ll][1-9][0-9]*. Por ejemplo: Usar la opción "--per-cache=l3" o "--per-cache=L3" agregará la información en el límite del nivel 3 de caché en el sistema.

--per-core

Agrega recuentos por procesador físico para mediciones en modo de sistema completo. Este es un modo útil para detectar desequilibrios entre núcleos físicos. Para habilitar este modo, use --per-core además de -a. (sistema completo). La salida incluye el número de núcleo y el número de procesadores lógicos en línea en ese procesador físico.

--per-thread

Agrega recuentos por hilos monitoreados, cuando se monitorean hilos (-t opción) o procesos (-p opción).

--per-node

Agrega recuentos por nodos NUMA para mediciones en modo de sistema completo. Este es un modo útil para detectar desequilibrios entre nodos NUMA. Para habilitar este modo, use --per-node además de -a. (sistema completo).

-D msecs, --delay msecs

Después de iniciar el programa, espere msecs antes de medir (-1: iniciar con eventos deshabilitados). Esto es útil para filtrar la fase de inicio del programa, que a menudo es muy diferente.

-T, --transaction

Imprime estadísticas de ejecución transaccional si es compatible.

--metric-no-group

Por defecto, los eventos para calcular una métrica se colocan en grupos débiles. El grupo intenta forzar la programación de todos o ninguno de los eventos. La opción --metric-no-group coloca los eventos fuera de los grupos y puede aumentar la probabilidad de que el evento se programe, lo que lleva a una mayor precisión. Sin embargo, dado que los eventos pueden no programarse juntos, la precisión de métricas como las instrucciones por ciclo puede ser menor, ya que ambas métricas ya no se miden al mismo tiempo.

--metric-no-merge

Por defecto, los eventos de métrica en diferentes grupos débiles pueden compartirse si un grupo contiene todos los eventos necesarios para otro. En tales casos, un grupo se eliminará, reduciendo la multiplexación de eventos y haciendo que ciertos grupos de métricas sumen el 100%. Una desventaja de compartir un grupo es que el grupo puede requerir multiplexación y, por lo tanto, la precisión de un grupo pequeño que no necesita multiplexación disminuye. Esta opción prohíbe que la lógica de fusión de eventos comparta eventos entre grupos y puede usarse para aumentar la precisión en este caso.

--metric-no-threshold

Los umbrales de métrica pueden aumentar el número de eventos necesarios para calcular si una métrica ha excedido su expresión de umbral. Esto puede no ser deseable, por ejemplo, ya que los eventos pueden introducir multiplexación. Esta opción deshabilita la adición de eventos de expresión de umbral para una métrica. Sin embargo, si hay suficientes eventos para calcular el umbral, el umbral todavía se calcula y se usa para colorear el valor calculado de la métrica.

--quiet

No imprima salida, advertencias o mensajes. Esto es útil con perf stat record a continuación para escribir solo datos en el archivo perf.data.

-M, --metrics

Imprime métricas o grupos de métricas especificados en una lista separada por comas. Para un grupo, se agregan todas las métricas del grupo. Los eventos de las métricas se miden automáticamente. Consulte la salida de perf list para ver las métricas y grupos de métricas posibles. 
Cuando hay información de umbral disponible para una métrica,
se usa el color rojo para indicar que una métrica ha excedido un umbral,
mientras que el verde indica que no lo ha hecho. El color predeterminado
significa que no hubo información de umbral disponible o que el umbral
no pudo calcularse.

-A, --no-aggr, --no-merge

No agrega/fusiona recuentos entre CPU o PMU monitoreados.

Cuando se crean múltiples eventos a partir de una sola especificación de evento, stat, por defecto, agregará los recuentos de eventos y mostrará el resultado en una sola fila. Esta opción deshabilita ese comportamiento y muestra los eventos y recuentos individuales.

Se crean múltiples eventos a partir de una sola especificación de evento cuando:

1. No se solicita el monitoreo de PID y el sistema tiene más de una CPU. Por ejemplo, un sistema con 8 hilos SMT tendrá un evento abierto en cada hilo y la agregación se realiza entre ellos.
2. Se utiliza el prefijo o comodín para el nombre de la PMU. Por ejemplo, puede haber múltiples PMU de controlador de memoria, típicamente con un sufijo _0, _1, etc. Por defecto, los recuentos de eventos se combinarán si la PMU se especifica sin el sufijo, como uncore_imc en lugar de uncore_imc_0.
3. Se utilizan alias, que se enumeran inmediatamente después de los eventos PMU del Kernel por perf list.

NAME

perf-stat - Provide performance counter statistics

SYNOPSIS

perf stat [OPTIONS] [COMMAND]

DESCRIPTION

This command is a performance counter monitoring tool. It provides system-wide or per-thread/per-process event counts.

OPTIONS

The options can be divided into the following groups.

-e event[,event...]
Specify the event(s) to count. The available events depend on the hardware and kernel configuration. Use perf list to see the available events. The default event is cpu-cycles.
-E event[,event... ]
Specify the event(s) to count with explicit pmu.
-p pid[,pid...]
Monitor events on processes named PID.
-t tid[,tid...]
Monitor events on threads named TID.
-a
System-wide mode. Count events on all CPUs.
-j
JSON format output.
-c command
A command line for which to drain counters.
-i
Disable the interval timer.
-s
Print syscalls.
-v
Increase verbosity.
-I milliseconds
Update interval in milliseconds (default 1000).
-r N
Repeat command N times and display variance.
-o filename
Write the output to a file, not to stdout.
--version
Show version.
--help
Show help.

STAT RECORD

This section describes the behavior of perf stat and perf record when dealing with hybrid CPU architectures, like Intel Hybrid Technology.

On hybrid platforms, the kernel exposes two types of PMUs (Performance Monitoring Units):

  • cpu_core: for performance cores (P-cores).
  • cpu_atom: for efficiency cores (E-cores).

The available event codes for these PMUs can be random and may vary between systems or even kernel versions. However, the PMU type identifiers are consistent.

STAT REPORT

When perf stat is used without specifying a particular PMU (e.g., perf stat -e cycles -a), the kernel automatically creates two cycles events:

  • One associated with the cpu_core PMU.
  • One associated with the cpu_atom PMU.

These events are then reported separately in the output.

For instance, running perf stat -e cycles -a might produce output like:

Performance counter stats for 'system wide':
6,744,979      cpu_core/cycles/
1,965,552      cpu_atom/cycles/

Here, the first count corresponds to the cpu_core PMU, and the second to the cpu_atom PMU.

EXAMPLES

Thread mode example:

When running a specific task, like triad_loop, on an atom core (e.g., CPU 16), perf stat might show scaled counts and percentages.

Command:

perf stat -e cycles -- taskset -c 16 ./triad_loop

The output might look like this:

Performance counter stats for 'taskset -c 16 ./triad_loop':
233,066,666      cpu_core/cycles/                                              (0.43%)
604,097,080      cpu_atom/cycles/                                              (99.57%)

The percentages indicate the proportion of time the event was active relative to the total time the event was enabled.

perf-record:

If -e is not specified with perf record on a hybrid platform, it defaults to creating two cycles events (one for core, one for atom) and adds them to the event list.

perf-stat default events:

If -e is not specified with perf stat on a hybrid platform, in addition to software events, the following events are added by default:

cpu_core/cycles/, cpu_atom/cycles/, cpu_core/instructions/,
cpu_atom/instructions/, cpu_core/branches/, cpu_atom/branches/,
cpu_core/branch-misses/, cpu_atom/branch-misses/

Explicitly specifying hybrid events:

perf stat and perf record support enabling specific hybrid events:

perf stat -e cpu_core/cycles/
perf stat -e cpu_atom/cycles/
perf stat -e cpu_core/r1a/
perf stat -e cpu_atom/L1-icache-loads/
perf stat -e cpu_core/cycles/,cpu_atom/instructions/
perf stat -e {cpu_core/cycles/,cpu_core/instructions/}

Grouping restrictions:

Attempting to group events from different PMUs (e.g., cpu_core and cpu_atom) in a single group will result in a warning, and grouping will be disabled. For example:

{cpu_core/cycles/,cpu_atom/instructions/}

will trigger a warning because the PMUs in the group do not match.

TIMINGS

The read_format field in the perf_event_attr structure controls how timing information is presented. The following flags can be used:

TOTAL_TIME_ENABLED
Includes time when the event was enabled but not necessarily running (e.g., due to task switching).
TOTAL_TIME_RUNNING
Includes only time when the event was actively running.

When perf stat uses these flags (e.g., in the hybrid example), the percentages displayed are calculated as:

Percentage = (event's running time / event's enabling time) * 100

Or, more precisely, using the enabled and running time counters provided by the kernel.

CSV FORMAT

With the -o option and specifying a filename ending in .csv, perf stat can output data in CSV format.

Example:

perf stat -e cycles -a -o stats.csv

The output file stats.csv will contain comma-separated values representing the collected statistics.

INTEL HYBRID SUPPORT

This section details how perf stat and perf record handle Intel's hybrid architectures (e.g., Alder Lake).

On such platforms, there are typically two types of CPU cores:

  • P-cores (Performance cores): Generally denoted as cpu_core in perf events.
  • E-cores (Efficiency cores): Generally denoted as cpu_atom in perf events.

When an event like cycles is requested without specifying a particular PMU (e.g., perf stat -e cycles -a), the system automatically creates and monitors the event on both types of cores. This results in separate counts for cpu_core/cycles/ and cpu_atom/cycles/.

Example with perf stat:

When enabling a hardware event without specifying a pmu, such as, perf stat -e cycles -a (use system-wide in this example), two events are created automatically.

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x400000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

and

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x800000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

Type 0 is PERF_TYPE_HARDWARE. 0x4 in 0x400000000 indicates it's cpu_core pmu. 0x8 in 0x800000000 indicates it's cpu_atom pmu (atom pmu type id is random).

The kernel creates cycles (0x400000000) on cpu0-cpu15 (core cpus), and creates cycles (0x800000000) on cpu16-cpu23 (atom cpus).

For perf-stat result, it displays two events:

Performance counter stats for 'system wide':
6,744,979      cpu_core/cycles/
1,965,552      cpu_atom/cycles/

The first cycles is the core event, the second cycles is the atom event.

Thread mode example:

perf-stat reports the scaled counts for hybrid events and with a percentage displayed. The percentage is the event's running time/enabling time.

One example, triad_loop runs on cpu16 (atom core), while we can see the scaled value for core cycles is 160,444,092 and the percentage is 0.47%.

perf stat -e cycles -- taskset -c 16 ./triad_loop

As previous, two events are created.

perf_event_attr:
  size                             120
  config                           0x400000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  enable_on_exec                   1
  exclude_guest                    1
.ft

and

.ft C
perf_event_attr:
  size                             120
  config                           0x800000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  enable_on_exec                   1
  exclude_guest                    1
.ft
Performance counter stats for 'taskset -c 16 ./triad_loop':
233,066,666      cpu_core/cycles/                                              (0.43%)
604,097,080      cpu_atom/cycles/                                              (99.57%)

perf-record:

If there is no -e specified in perf record, on hybrid platform, it creates two default cycles and adds them to event list. One is for core, the other is for atom.

perf-stat:

If there is no -e specified in perf stat, on hybrid platform, besides of software events, following events are created and added to event list in order.

cpu_core/cycles/, cpu_atom/cycles/, cpu_core/instructions/, cpu_atom/instructions/, cpu_core/branches/, cpu_atom/branches/, cpu_core/branch-misses/, cpu_atom/branch-misses/

Of course, both perf-stat and perf-record support to enable hybrid event with a specific pmu.

e.g. perf stat -e cpu_core/cycles/ perf stat -e cpu_atom/cycles/ perf stat -e cpu_core/r1a/ perf stat -e cpu_atom/L1-icache-loads/ perf stat -e cpu_core/cycles/,cpu_atom/instructions/ perf stat -e {cpu_core/cycles/,cpu_core/instructions/}

But {cpu_core/cycles/,cpu_atom/instructions/} will return warning and disable grouping, because the pmus in group are not matched (cpu_core vs. cpu_atom).

JSON FORMAT

With -j, perf stat is able to print out a JSON format output that can be used for parsing.

•interval : optional timestamp in fractions of second (with -I)
•optional aggregate options:
•core : core identifier (with --per-core)
•die : die identifier (with --per-die)
•socket : socket identifier (with --per-socket)
•node : node identifier (with --per-node)
•thread : thread identifier (with --per-thread)
•counters : number of aggregated PMU counters
•counter-value : counter value
•unit : unit of the counter value or empty
•event : event name
•variance : optional variance if multiple values are collected (with -r)
•event-runtime : run time of the event
•pcnt-running : percentage of time the event was running
•metric-value : optional metric value
•metric-unit : optional unit of metric
