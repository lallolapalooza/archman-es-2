PERLIPC(1perl) Guía de referencia para programadores de Perl PERLIPC(1perl)

NOMBRE

perlipc - comunicación entre procesos de Perl (señales, fifos, tuberías, subprocesos seguros, sockets y semáforos)

DESCRIPCIÓN

Las instalaciones básicas de IPC de Perl se construyen a partir de las buenas y viejas utilidades de Unix: señales, tuberías con nombre (named pipes), aperturas de tuberías (pipe opens), rutinas de socket Berkeley y llamadas a IPC de SysV. Cada una se utiliza en situaciones ligeramente diferentes.

Señales

Perl utiliza un modelo simple de manejo de señales: el hash %SIG contiene nombres o referencias a manejadores de señales instalados por el usuario. Estos manejadores serán llamados con un argumento que es el nombre de la señal que los activó. Una señal puede ser generada intencionalmente desde una secuencia de teclado particular como control-C o control-Z, enviada desde otro proceso, o activada automáticamente por el kernel cuando ocurren eventos especiales, como la salida de un proceso hijo, que tu propio proceso se quede sin espacio en la pila o que alcance un límite de tamaño de archivo del proceso.

Por ejemplo, para capturar una señal de interrupción, configura un manejador así:

our $shucks;
sub catch_zap {
    my $signame = shift;
    $shucks++;
    die "Alguien me envió una SIG$signame";
}
$SIG{INT} = __PACKAGE__ . "::catch_zap";
$SIG{INT} = \&catch_zap;  # mejor estrategia

Antes de Perl 5.8.0 era necesario hacer lo menos posible en tu manejador; observa que todo lo que hacemos es establecer una variable global y luego lanzar una excepción. Esto se debe a que en la mayoría de los sistemas, las bibliotecas no son reentrantes; en particular, las rutinas de asignación de memoria y E/S no lo son. Eso significaba que hacer casi *cualquier cosa* en tu manejador podría, en teoría, desencadenar un fallo de memoria y un volcado de núcleo subsiguiente; consulta "Señales Diferidas (Señales Seguras)" a continuación.

Los nombres de las señales son los que se listan con "kill -l" en tu sistema, o puedes recuperarlos usando el módulo CPAN IPC::Signal.

También puedes optar por asignar las cadenas "IGNORE" o "DEFAULT" como manejador, en cuyo caso Perl intentará descartar la señal o hacer lo predeterminado.

En la mayoría de las plataformas Unix, la señal "CHLD" (a veces también conocida como "CLD") tiene un comportamiento especial con respecto a un valor de "IGNORE". Establecer $SIG{CHLD} a "IGNORE" en una plataforma de este tipo tiene el efecto de no crear procesos zombis cuando el proceso padre no logra wait() en sus procesos hijos (es decir, los procesos hijos son recolectados automáticamente). Llamar wait() con $SIG{CHLD} establecido a "IGNORE" generalmente devuelve -1 en tales plataformas.

Algunas señales no pueden ser ni capturadas ni ignoradas, como las señales KILL y STOP (pero no TSTP). Ten en cuenta que ignorar señales hace que desaparezcan. Si solo quieres bloquearlas temporalmente sin que se pierdan, tendrás que usar el módulo POSIX "POSIX" sigprocmask.

Enviar una señal a un ID de proceso negativo significa que envías la señal a todo el grupo de procesos de Unix. Este código envía una señal de colgar (hang-up) a todos los procesos del grupo de procesos actual, y también establece $SIG{HUP} a "IGNORE" para que no se mate a sí mismo:

# ámbito de bloque para local
{
    local $SIG{HUP} = "IGNORE";
    kill HUP => -getpgrp();
    # escritura elegante de: kill("HUP", -getpgrp())
}

Otra señal interesante para enviar es el número de señal cero. Esto en realidad no afecta a un proceso hijo, sino que verifica si está vivo o si ha cambiado sus UID.

unless (kill 0 => $kid_pid) {
    warn "algo terrible le pasó a $kid_pid";
}

El número de señal cero puede fallar porque no tienes permiso para enviar la señal a un proceso cuyo UID real o guardado no sea idéntico al UID real o efectivo del proceso que envía, aunque el proceso esté vivo. Puede que puedas determinar la causa del fallo usando $! o "%!".

unless (kill(0 => $pid) || $!{EPERM}) {
    warn "$pid parece muerto";
}

También podrías querer emplear funciones anónimas para manejadores de señales simples:

$SIG{INT} = sub { die "\n¡Fuera de aquí!\n" };

Los manejadores de SIGCHLD requieren un cuidado especial. Si un segundo hijo muere mientras está en el manejador de señales causado por la primera muerte, no recibiremos otra señal. Por lo tanto, debemos iterar aquí, de lo contrario dejaremos al hijo no recolectado como un zombi. Y la próxima vez que mueran dos hijos, obtendremos otro zombi. Y así sucesivamente.

use POSIX ":sys_wait_h";
$SIG{CHLD} = sub {
    while ((my $child = waitpid(-1, WNOHANG)) > 0) {
        $Kid_Status{$child} = $?;
    }
};
# haz algo que se bifurque...

Ten cuidado: qx(), system() y algunos módulos para llamar a comandos externos hacen un fork(), luego esperan (wait()) el resultado. Por lo tanto, se llamará a tu manejador de señales. Como system() o qx() ya llamaron a wait(), el wait() en el manejador de señales no verá más zombis y, por lo tanto, se bloqueará.

La mejor manera de evitar este problema es usar waitpid(), como en el siguiente ejemplo:

use POSIX ":sys_wait_h"; # para lectura no bloqueante
my %children;
$SIG{CHLD} = sub {
    # no cambiar $! y $? fuera del manejador
    local ($!, $?);
    while ( (my $pid = waitpid(-1, WNOHANG)) > 0 ) {
        delete $children{$pid};
        cleanup_child($pid, $?);
    }
};
while (1) {
    my $pid = fork();
    die "no se puede bifurcar" unless defined $pid;
    if ($pid == 0) {
        # ...
        exit 0;
    } else {
        $children{$pid}=1;
        # ...
        system($command);
        # ...
   }
}

El manejo de señales también se utiliza para tiempos de espera (timeouts) en Unix. Mientras estás protegido de forma segura dentro de un bloque "eval{}", configuras un manejador de señales para capturar señales de alarma y luego programas que se te entregue una en una cantidad de segundos. Luego intentas tu operación de bloqueo, cancelando la alarma cuando termine, pero no antes de haber salido de tu bloque "eval{}". Si se dispara, usarás die() para saltar fuera del bloque.

Aquí tienes un ejemplo:

my $ALARM_EXCEPTION = "reinicio del reloj de alarma";
eval {
    local $SIG{ALRM} = sub { die $ALARM_EXCEPTION };
    alarm 10;
    flock($fh, 2)    # bloqueo de escritura bloqueante
                    || die "no se puede hacer flock: $!";
    alarm 0;
};
if ($@ && $@ !~ quotemeta($ALARM_EXCEPTION)) { die }

Si la operación a la que se le está aplicando el tiempo de espera es system() o qx(), esta técnica es propensa a generar zombis. Si esto te importa, necesitarás hacer tu propio fork() y exec(), y matar al proceso hijo errante.

Para un manejo de señales más complejo, podrías consultar el módulo estándar POSIX. Lamentablemente, esto está casi completamente sin documentar, pero el archivo ext/POSIX/t/sigaction.t de la distribución fuente de Perl tiene algunos ejemplos.

Un proceso que generalmente se inicia cuando el sistema arranca y se apaga cuando el sistema se apaga se llama daemon (Disk And Execution MONitor). Si un proceso daemon tiene un archivo de configuración que se modifica después de que el proceso ha sido iniciado, debería haber una manera de decirle a ese proceso que relea su archivo de configuración sin detener el proceso. Muchos daemons proporcionan este mecanismo utilizando un manejador de señales "SIGHUP". Cuando quieres decirle al daemon que relea el archivo, simplemente envíale la señal "SIGHUP".

Señales Diferidas (Señales Seguras)

Antes de Perl 5.8.0, instalar código Perl para manejar señales te exponía a peligros de dos tipos. Primero, pocas funciones de la biblioteca del sistema son reentrantes. Si la señal interrumpe mientras Perl está ejecutando una función (como malloc(3) o printf(3)), y tu manejador de señales llama de nuevo a la misma función, podrías obtener un comportamiento impredecible, a menudo un volcado de memoria (core dump).

Segundo, Perl en sí mismo no es reentrante en sus niveles más bajos. Si la señal interrumpe a Perl mientras este está cambiando sus propias estructuras de datos internas, puede resultar un comportamiento igualmente impredecible.

Había dos cosas que podías hacer, sabiendo esto: ser paranoico o ser pragmático. El enfoque paranoico era hacer lo mínimo posible en tu manejador de señales. Establecer una variable entera existente que ya tuviera un valor y retornar. Esto no te ayuda si estás en una llamada de sistema lenta, la cual simplemente se reiniciará. Eso significa que tienes que "morir" para hacer un longjmp(3) fuera del manejador. Incluso esto es un poco cauto para el verdadero paranoico, que evita "morir" en un manejador porque el sistema *está* en tu contra. El enfoque pragmático era decir "Sé los riesgos, pero prefiero la conveniencia" y hacer cualquier cosa que quisieras en tu manejador de señales, y estar preparado para limpiar volcados de memoria de vez en cuando.

Perl 5.8.0 y posteriores evitan estos problemas "diferiendo" las señales. Es decir, cuando la señal es entregada al proceso por el sistema (al código C que implementa Perl), se establece una bandera y el manejador retorna inmediatamente. Luego, en puntos "seguros" estratégicos en el intérprete Perl (por ejemplo, cuando está a punto de ejecutar un nuevo opcode), se verifican las banderas y se ejecuta el manejador de nivel Perl de %SIG. El esquema "diferido" permite mucha más flexibilidad en la codificación de los manejadores de señales, ya que sabemos que el intérprete Perl está en un estado seguro y que no estamos en una función de la biblioteca del sistema cuando se llama al manejador. Sin embargo, la implementación difiere de los Perl anteriores de las siguientes maneras:

Opcodes de larga duración
Como el intérprete Perl mira las banderas de señal solo cuando está a punto de ejecutar un nuevo opcode, una señal que llega durante un opcode de larga duración (por ejemplo, una operación de expresión regular en una cadena muy grande) no se verá hasta que el opcode actual se complete.

Si una señal de cualquier tipo dado se dispara múltiples veces durante un opcode (como de un temporizador de grano fino), el manejador para esa señal se llamará solo una vez, después de que el opcode se complete; todas las demás instancias se descartarán. Además, si la cola de señales de tu sistema se inunda hasta el punto de que hay señales que se han disparado pero aún no se han capturado (y por lo tanto no se han diferido) en el momento en que un opcode se completa, esas señales bien podrían ser capturadas y diferidas durante opcodes subsiguientes, con resultados a veces sorprendentes. Por ejemplo, puedes ver alarmas entregadas incluso después de llamar a alarm(0), ya que esto último detiene el disparo de alarmas pero no cancela la entrega de alarmas disparadas pero aún no capturadas. No dependas de los comportamientos descritos en este párrafo, ya que son efectos secundarios de la implementación actual y pueden cambiar en versiones futuras de Perl.

Interrumpir E/S
Cuando se entrega una señal (por ejemplo, SIGINT desde un control-C), el sistema operativo interrumpe operaciones de E/S como read(2), que se usa para implementar la función readline() de Perl, el operador "<>". En Perls más antiguos, el manejador se llamaba inmediatamente (y como "read" no es "inseguro", esto funcionaba bien). Con el esquema "diferido", el manejador *no* se llama inmediatamente, y si Perl está usando la biblioteca "stdio" del sistema, esa biblioteca puede reiniciar la "read" sin retornar a Perl para darle la oportunidad de llamar al manejador de %SIG. Si esto sucede en tu sistema, la solución es usar la capa ":perlio" para realizar E/S, al menos en aquellos manejadores que deseas poder interrumpir con señales. (La capa ":perlio" verifica las banderas de señal y llama a los manejadores de %SIG antes de reanudar la operación de E/S.)

El valor predeterminado en Perl 5.8.0 y posteriores es usar automáticamente la capa ":perlio".

Ten en cuenta que no es aconsejable acceder a un manejador de archivos dentro de un manejador de señales donde esa señal ha interrumpido una operación de E/S en ese mismo manejador. Si bien Perl hará todo lo posible para no fallar, no hay garantías de integridad de los datos; por ejemplo, algunos datos podrían perderse o escribirse dos veces.

Algunas funciones de la biblioteca de red como gethostbyname() son conocidas por tener sus propias implementaciones de tiempos de espera que pueden entrar en conflicto con tus tiempos de espera. Si tienes problemas con dichas funciones, intenta usar la función POSIX sigaction(), que omite las señales seguras de Perl. Ten en cuenta que esto te expone a una posible corrupción de memoria, como se describió anteriormente.

En lugar de establecer $SIG{ALRM}:

local $SIG{ALRM} = sub { die "alarm" };

intenta algo como lo siguiente:

use POSIX qw(SIGALRM);
POSIX::sigaction(SIGALRM,
                 POSIX::SigAction->new(sub { die "alarm" }))
         || die "Error setting SIGALRM handler: $!\n";

Otra forma de deshabilitar el comportamiento de señales seguras localmente es usar el módulo "Perl::Unsafe::Signals" de CPAN, que afecta a todas las señales.

Llamadas al sistema reanudables
En sistemas que lo soportaban, versiones anteriores de Perl usaban la bandera SA_RESTART al instalar manejadores de %SIG. Esto significaba que las llamadas al sistema reanudables continuarían en lugar de retornar cuando llegaba una señal. Para entregar señales diferidas prontamente, Perl 5.8.0 y posteriores *no* usan SA_RESTART. En consecuencia, las llamadas al sistema reanudables pueden fallar (con $! establecido a "EINTR") en lugares donde previamente habrían tenido éxito.

La capa predeterminada ":perlio" reintenta "read", "write" y "close" como se describió anteriormente; las llamadas "wait" y "waitpid" interrumpidas siempre se reintentarán.

Señales como "fallos"
Ciertas señales como SEGV, ILL, BUS y FPE son generadas por errores de dirección de memoria virtual y "fallos" similares. Estos son normalmente fatales: hay poco que un manejador de nivel Perl pueda hacer con ellos. Por lo tanto, Perl los entrega inmediatamente en lugar de intentar diferirlos.

Es posible capturarlos con un manejador de %SIG (ver perlvar), pero además de los problemas usuales de señales "inseguras", es probable que la señal se vuelva a lanzar inmediatamente al retornar del manejador de señales, por lo que dicho manejador debería "morir" o "salir" en su lugar.

Señales disparadas por el estado del sistema operativo
En algunos sistemas operativos, ciertos manejadores de señales deben "hacer algo" antes de retornar. Un ejemplo puede ser CHLD o CLD, que indica que un proceso hijo ha completado. En algunos sistemas operativos, se espera que el manejador de señales haga un "wait" para el proceso hijo completado. En dichos sistemas, el esquema de señales diferidas no funcionará para esas señales: no realiza el "wait". De nuevo, el fallo parecerá un bucle, ya que el sistema operativo volverá a emitir la señal porque hay procesos hijos completados que aún no han sido "esperados".

Si deseas recuperar el comportamiento antiguo de señales a pesar de una posible corrupción de memoria, establece la variable de entorno "PERL_SIGNALS" a "unsafe". Esta característica apareció por primera vez en Perl 5.8.1.

Tuberías con nombre

Una tubería con nombre (a menudo referida como FIFO) es un antiguo mecanismo de IPC de Unix para que los procesos se comuniquen en la misma máquina. Funciona igual que las tuberías anónimas normales, excepto que los procesos se encuentran usando un nombre de archivo y no necesitan estar relacionados.

Para crear una tubería con nombre, usa la función POSIX::mkfifo().

use POSIX qw(mkfifo);
mkfifo($path, 0700)     ||  die "mkfifo $path failed: $!";

También puedes usar el comando de Unix mknod(1), o en algunos sistemas, mkfifo(1). Es posible que estos no estén en tu ruta normal, sin embargo.

# el valor de retorno del sistema es al revés, por lo que && en lugar de ||
#
$ENV{PATH} .= ":/etc:/usr/etc";
if  (      system("mknod",  $path, "p")
        && system("mkfifo", $path) )
{
    die "mk{nod,fifo} $path failed";
}

Así, por ejemplo, en lugar de usar:

open(my $ps_pipe, "-|", "ps aux") || die "no se puede abrir pipe ps: $!";

Se usaría cualquiera de estas:

open(my $ps_pipe, "-|", "ps", "aux")
                                  || die "no se puede abrir pipe ps: $!";
my @ps_args = qw[ ps aux ];
open(my $ps_pipe, "-|", @ps_args)
                                  || die "no se puede abrir @ps_args|: $!";

Debido a que hay más de tres argumentos para open(), se hace un fork del comando ps(1) *sin* iniciar un shell, y se lee su salida estándar a través del manejador de archivos $ps_pipe. La sintaxis correspondiente para *escribir* en pipes de comandos es usar "|-" en lugar de "-|".

Este fue, admitámoslo, un ejemplo bastante tonto, porque estás usando literales de cadena cuyo contenido es perfectamente seguro. Por lo tanto, no hay motivo para recurrir a la forma de open() de pipe con múltiples argumentos, que es más difícil de leer. Sin embargo, siempre que no puedas estar seguro de que los argumentos del programa están libres de metacaracteres del shell, se debe usar la forma más sofisticada de open(). Por ejemplo:

my @grep_args = ("egrep", "-i", $some_pattern, @many_files);
open(my $grep_pipe, "-|", @grep_args)
                    || die "no se puede abrir @grep_args|: $!";

Aquí, la forma de múltiples argumentos de open() de pipe es preferible porque el patrón e incluso los nombres de archivo pueden contener metacaracteres.

Evitar Interbloqueos de Pipe

Siempre que tengas más de un subproceso, debes tener cuidado de que cada uno cierre la mitad de los pipes creados para la comunicación interprocesos que no esté utilizando. Esto se debe a que cualquier proceso hijo que lea del pipe y espere un EOF nunca lo recibirá y, por lo tanto, nunca terminará. Cerrar un pipe por un solo proceso no es suficiente; el último proceso con el pipe abierto debe cerrarlo para que se lea EOF.

Ciertas características integradas de Unix ayudan a prevenir esto la mayor parte del tiempo. Por ejemplo, los manejadores de archivos tienen una bandera de "cerrar en ejecución", que se establece *en masa* bajo el control de la variable $^F. Esto es para que cualquier manejador de archivos que no hayas enrutado explícitamente a STDIN, STDOUT o STDERR de un programa hijo se cierre automáticamente.

Siempre llama explícita e inmediatamente a close() en el extremo de escritura de cualquier pipe, a menos que ese proceso realmente esté escribiendo en él. Incluso si no llamas explícitamente a close(), Perl seguirá llamando a close() en todos los manejadores de archivos durante la destrucción global. Como se discutió anteriormente, si esos manejadores de archivos se abrieron con Safe Pipe Open, esto resultará en llamar a waitpid(), lo que nuevamente puede causar un interbloqueo.

Comunicación Bidireccional con Otro Proceso

Si bien esto funciona razonablemente bien para la comunicación unidireccional, ¿qué pasa con la comunicación bidireccional? El enfoque más obvio no funciona:

# ¡ESTO NO FUNCIONA!
open(my $prog_for_reading_and_writing, "| some program |")

Si olvidas "use warnings", te perderás por completo el útil mensaje de diagnóstico:

Can't do bidirectional pipe at -e line 1.

Si realmente quieres, puedes usar el open2() estándar del módulo IPC::Open2 para capturar ambos extremos. También hay un open3() en IPC::Open3 para E/S tridireccional, por lo que también puedes capturar STDERR de tu hijo, pero hacer eso requeriría un incómodo bucle select() y no te permitiría usar operaciones normales de entrada de Perl.

Si miras su código fuente, verás que open2() utiliza primitivas de bajo nivel como las llamadas al sistema pipe() y exec() para crear todas las conexiones. Aunque podría haber sido más eficiente al usar socketpair(), esto habría sido aún menos portable de lo que ya es. Es poco probable que las funciones open2() y open3() funcionen en cualquier lugar excepto en un sistema Unix, o al menos en uno que pretenda cumplir con POSIX.

Aquí tienes un ejemplo de uso de open2():

use IPC::Open2;
my $pid = open2(my $reader, my $writer, "cat -un");
print $writer "stuff\n";
my $got = <$reader>;
waitpid $pid, 0;

El problema con esto es que el almacenamiento en búfer realmente te arruinará el día. A pesar de que tu manejador de archivos $writer se vacía automáticamente para que el proceso del otro lado reciba tus datos a tiempo, generalmente no puedes hacer nada para forzar que ese proceso te envíe sus datos de manera similarmente rápida. En este caso especial, realmente podríamos hacerlo, porque le dimos a cat una bandera -u para hacerlo sin búfer. Pero muy pocos comandos están diseñados para operar a través de pipes, por lo que esto rara vez funciona a menos que tú mismo hayas escrito el programa al otro lado del pipe de doble extremo.

Una solución a esto es usar una biblioteca que utilice pseudoterminales para hacer que tu programa se comporte de manera más razonable. De esta manera, no necesitas tener control sobre el código fuente del programa que estás utilizando. El módulo "Expect" de CPAN también aborda este tipo de cosas. Este módulo requiere otros dos módulos de CPAN, "IO::Pty" y "IO::Stty". Configura un pseudoterminal para interactuar con programas que insisten en hablar con el controlador de dispositivo de terminal. Si tu sistema es compatible, esta puede ser tu mejor opción.

Comunicación Bidireccional Contigo Mismo

Si lo deseas, puedes realizar llamadas al sistema pipe() y fork() de bajo nivel para unir esto manualmente. Este ejemplo solo se comunica consigo mismo, pero podrías reabrir los manejadores apropiados a STDIN y STDOUT y llamar a otros procesos. (El siguiente ejemplo carece de la comprobación de errores adecuada).

#!/usr/bin/perl
# pipe1 - comunicación bidireccional usando dos pares de pipes
#         diseñado para los que tienen problemas con socketpair
use v5.36;
use IO::Handle;  # habilita el método autoflush antes de Perl 5.14
pipe(my $parent_rdr, my $child_wtr);  # XXX: ¿verificar fallo?

$parent_wtr->autoflush(1);

    close $parent_rdr;
    close $parent_wtr;
    print $child_wtr "Parent Pid $$ is sending this\n";
    chomp(my $line = <$child_rdr>);
    print "Parent Pid $$ just read this: '$line'\n";
    close $child_rdr; close $child_wtr;
    waitpid($pid, 0);
} else {
    die "no se puede forkear: $!" unless defined $pid;
    close $child_rdr;
    close $child_wtr;
    chomp(my $line = <$parent_rdr>);
    print "Child Pid $$ just read this: '$line'\n";
    print $parent_wtr "Child Pid $$ is sending this\n";
    close $parent_rdr;
    close $parent_wtr;
    exit(0);
}

Pero en realidad no tienes que hacer dos llamadas a pipe. Si tienes la llamada al sistema socketpair(), hará todo esto por ti.

#!/usr/bin/perl
# pipe2 - comunicación bidireccional usando socketpair
#   "los mejores siempre van en ambos sentidos"
use v5.36;
use Socket;
use IO::Handle;  # habilita el método autoflush antes de Perl 5.14
# Decimos AF_UNIX porque aunque *_LOCAL es la
# forma de constante de POSIX 1003.1g, muchas máquinas
# todavía no lo tienen.
socketpair(my $child, my $parent, AF_UNIX, SOCK_STREAM, PF_UNSPEC)
                            ||  die "socketpair: $!";
$child->autoflush(1);
$parent->autoflush(1);
if ($pid = fork()) {
    close $parent;
    print $child "Parent Pid $$ is sending this\n";
    chomp(my $line = <$child>);
    print "Parent Pid $$ just read this: '$line'\n";
    close $child;
    waitpid($pid, 0);
} else {
    die "no se puede forkear: $!" unless defined $pid;
    close $child;
    chomp(my $line = <$parent>);
    print "Child Pid $$ just read this: '$line'\n";
    print $parent "Child Pid $$ is sending this\n";
    close $parent;
    exit(0);
}

Sockets: Comunicación Cliente/Servidor

Sockets: Comunicación Cliente/Servidor

Aunque no se limita exclusivamente a los sistemas operativos derivados de Unix (por ejemplo, WinSock en PC proporciona soporte para sockets, al igual que algunas bibliotecas de VMS), es posible que no tenga sockets en su sistema, en cuyo caso esta sección probablemente no le será de mucha utilidad. Con los sockets, puede realizar circuitos virtuales como flujos TCP y datagramas como paquetes UDP. Es posible que pueda hacer aún más dependiendo de su sistema.

Las funciones de Perl para tratar con sockets tienen los mismos nombres que las llamadas al sistema correspondientes en C, pero sus argumentos tienden a diferir por dos razones. En primer lugar, los manejadores de archivos de Perl funcionan de manera diferente a los descriptores de archivos de C. En segundo lugar, Perl ya conoce la longitud de sus cadenas, por lo que no necesita pasar esa información.

Uno de los principales problemas con el código de socket antiguo, de antes del milenio, en Perl era que utilizaba valores codificados de forma rígida para algunas de las constantes, lo que perjudicaba gravemente la portabilidad. Si alguna vez ve código que hace algo como establecer explícitamente "$AF_INET = 2", sabe que se va a meter en grandes problemas. Un enfoque inmensurablemente superior es usar el módulo Socket, que concede un acceso más fiable a las diversas constantes y funciones que necesitará.

Si no está escribiendo un servidor/cliente para un protocolo existente como NNTP o SMTP, debería reflexionar sobre cómo sabrá el servidor cuándo ha terminado de hablar el cliente, y viceversa. La mayoría de los protocolos se basan en mensajes y respuestas de una línea (por lo que una parte sabe que la otra ha terminado cuando se recibe un "\n") o mensajes y respuestas de varias líneas que terminan con un punto en una línea vacía ("\n.\n" termina un mensaje/respuesta).

Terminadores de Línea de Internet

El terminador de línea de Internet es "\015\012". En las variantes ASCII de Unix, eso normalmente se podría escribir como "\r\n", pero en otros sistemas, "\r\n" podría ser a veces "\015\015\012", "\012\012\015", o algo completamente diferente. Los estándares especifican escribir "\015\012" para ser conformes (ser estricto en lo que proporciona), pero también recomiendan aceptar un solo "\012" en la entrada (ser indulgente en lo que requiere). No siempre hemos sido muy buenos en eso en el código de este manual, pero a menos que esté en un Mac de su oscura era pre-Unix, probablemente estará bien.

Clientes y Servidores TCP de Internet

Utilice sockets de dominio de Internet cuando desee realizar comunicaciones cliente-servidor que puedan extenderse a máquinas fuera de su propio sistema.

Aquí tiene un ejemplo de cliente TCP que utiliza sockets de dominio de Internet:

#!/usr/bin/perl
use v5.36;
use Socket;
my $remote  = shift || "localhost";
my $port    = shift || 2345;  # puerto aleatorio
if ($port =~ /\D/) { $port = getservbyname($port, "tcp") }
die "Sin puerto" unless $port;
my $iaddr   = inet_aton($remote)       || die "no host: $remote";
my $paddr   = sockaddr_in($port, $iaddr);
my $proto   = getprotobyname("tcp");
socket(my $sock, PF_INET, SOCK_STREAM, $proto)  || die "socket: $!";
connect($sock, $paddr)              || die "connect: $!";
while (my $line = <$sock>) {
    print $line;
}
close ($sock)                        || die "close: $!";
exit(0);

Y aquí tiene un servidor correspondiente para acompañarlo. Dejaremos la dirección como "INADDR_ANY" para que el kernel pueda elegir la interfaz adecuada en hosts multihoming. Si desea permanecer en una interfaz particular (como el lado externo de una máquina gateway o cortafuegos), rellene esto con su dirección real en su lugar.

#!/usr/bin/perl -T
use v5.36;
BEGIN { $ENV{PATH} = "/usr/bin:/bin" }

            inet_ntoa($iaddr), "]
            en el puerto $port";

                    scalar localtime(), $EOL;

Y aquí tiene una versión multitarea. Es multitarea en el sentido de que, como la mayoría de los servidores típicos, genera (hace fork()) un servidor hijo para manejar la solicitud del cliente, de modo que el servidor maestro pueda volver rápidamente para atender a un nuevo cliente.

#!/usr/bin/perl -T
use v5.36;
BEGIN { $ENV{PATH} = "/usr/bin:/bin" }
use Socket;
use Carp;
my $EOL = "\015\012";
sub spawn;  # declaración anticipada
sub logmsg { print "$0 $$: @_ at ", scalar localtime(), "\n" }
my $port  = shift || 2345;
die "puerto invalido" unless $port =~ /^ \d+ $/x;
my $proto = getprotobyname("tcp");
socket(my $server, PF_INET, SOCK_STREAM, $proto) || die "socket: $!";
setsockopt($server, SOL_SOCKET, SO_REUSEADDR, pack("l", 1))
                                              || die "setsockopt: $!";
bind($server, sockaddr_in($port, INADDR_ANY)) || die "bind: $!";
listen($server, SOMAXCONN)                    || die "listen: $!";
logmsg "servidor iniciado en el puerto $port";
my $waitedpid = 0;
use POSIX ":sys_wait_h";
use Errno;
sub REAPER {
    local $!;   # evitar que waitpid() sobrescriba el error actual
    while ((my $pid = waitpid(-1, WNOHANG)) > 0 && WIFEXITED($?)) {
        logmsg "reaped $waitedpid" . ($? ? " con salida $?" : "");
    }
    $SIG{CHLD} = \&REAPER;  # lo aborrezco SysV
}
$SIG{CHLD} = \&REAPER;
while (1) {
    my $paddr = accept(my $client, $server) || do {
        # intentar de nuevo si accept() devolvió porque recibió una señal
        next if $!{EINTR};
        die "accept: $!";
    };
    my ($port, $iaddr) = sockaddr_in($paddr);
    my $name = gethostbyaddr($iaddr, AF_INET);
    logmsg "conexión desde $name [",
           inet_ntoa($iaddr),
           "] en el puerto $port";
    spawn $client, sub {
        $| = 1;
        print "Hola, $name, ahora son las ",
              scalar localtime(),
              $EOL;
        exec "/usr/games/fortune"       # XXX: terminadores de línea "incorrectos"
            or confess "no se puede ejecutar fortune: $!";
    };
    close $client;
}
sub spawn {
    my $client = shift;
    my $coderef = shift;
    unless (@_ == 0 && $coderef && ref($coderef) eq "CODE") {
        confess "uso: spawn CLIENT CODEREF";
    }
    my $pid;
    unless (defined($pid = fork())) {
        logmsg "no se puede forkear: $!";
        return;
    }
    elsif ($pid) {
        logmsg "creé $pid";
        return; # soy el padre
    }
    # de lo contrario, soy el hijo -- procedo a generar
    open(STDIN,  "<&", $client)   || die "no se puede duplicar cliente a stdin";
    open(STDOUT, ">&", $client)   || die "no se puede duplicar cliente a stdout";
    ## open(STDERR, ">&", STDOUT) || die "no se puede duplicar stdout a stderr";
    exit($coderef->());
}

Este servidor se encarga de clonar una versión hija mediante fork() para cada solicitud entrante. De esta manera, puede manejar muchas solicitudes a la vez, lo que puede no ser lo que siempre desea. Incluso si no hace fork(), listen() permitirá tantas conexiones pendientes. Los servidores que utilizan fork deben tener especial cuidado en limpiar sus hijos muertos (llamados "zombies" en la jerga de Unix), porque de lo contrario llenará rápidamente su tabla de procesos. La subrutina REAPER se utiliza aquí para llamar a waitpid() para cualquier proceso hijo que haya terminado, asegurando así que terminen limpiamente y no se unan a las filas de los muertos vivientes.

Dentro del bucle while, llamamos a accept() y comprobamos si devuelve un valor falso. Esto normalmente indicaría un error del sistema que debe ser reportado. Sin embargo, la introducción de señales seguras (ver "Señales Diferidas (Señales Seguras)" arriba) en Perl 5.8.0 significa que accept() también puede ser interrumpido cuando el proceso recibe una señal. Esto ocurre típicamente cuando uno de los subprocesos generados sale y notifica al proceso padre con una señal CHLD.

Si accept() es interrumpido por una señal, $! se establecerá en EINTR. Si esto sucede, podemos continuar de forma segura a la siguiente iteración del bucle y a otra llamada a accept(). Es importante que su código de manejo de señales no modifique el valor de $!, o bien esta prueba probablemente fallará. En la subrutina REAPER creamos una versión local de $! antes de llamar a waitpid(). Cuando waitpid() establece $! a ECHILD, como inevitablemente hace cuando ya no tiene hijos esperando, actualiza la copia local y deja la original sin cambios.

Debería usar la bandera -T para habilitar la comprobación de "taint" (ver perlsec) incluso si no estamos ejecutando como setuid o setgid. Esta es siempre una buena idea para servidores o cualquier programa ejecutado en nombre de otra persona (como scripts CGI), ya que reduce las posibilidades de que personas externas puedan comprometer su sistema. Tenga en cuenta que perl puede ser compilado sin soporte de "taint". Hay dos modos diferentes: en uno, -T simplemente no hará nada. En el otro modo, -T resulta en un error fatal.

Echemos un vistazo a otro cliente TCP. Este se conecta al servicio TCP "time" en varias máquinas diferentes y muestra cuánto difieren sus relojes del sistema en el que se está ejecutando:

    my $hisiaddr = inet_aton($host)     || die "host desconocido";

Clientes y Servidores TCP de Dominio Unix

Eso está bien para clientes y servidores de dominio de Internet, pero ¿qué pasa con las comunicaciones locales? Aunque puedes usar la misma configuración, a veces no quieres hacerlo. Los sockets de dominio Unix son locales al host actual y a menudo se usan internamente para implementar tuberías. A diferencia de los sockets de dominio de Internet, los sockets de dominio Unix pueden aparecer en el sistema de archivos con una lista de ls(1).

% ls -l /dev/log
srw-rw-rw-  1 root            0 Oct 31 07:23 /dev/log

Puedes comprobar esto con la prueba de archivo -S de Perl:

unless (-S "/dev/log") {
    die "algo anda mal con el sistema de registro";
}

Aquí tienes un ejemplo de cliente de dominio Unix:

#!/usr/bin/perl
use v5.36;
use Socket;
my $rendezvous = shift || "catsock";
socket(my $sock, PF_UNIX, SOCK_STREAM, 0) || die "socket: $!";
connect($sock, sockaddr_un($rendezvous))  || die "connect: $!";
while (defined(my $line = <$sock>)) {
    print $line;
}
exit(0);

Y aquí tienes un servidor correspondiente. No tienes que preocuparte por los terminadores de red tontos aquí porque los sockets de dominio Unix están garantizados para estar en el localhost, y por lo tanto todo funciona bien.

use v5.36;

unlink($NAME);

listen($server, SOMAXCONN)                  || die "listen: $!";
logmsg "servidor iniciado en $NAME";

use POSIX ":sys_wait_h";
sub REAPER {
    my $child;
    while (($waitedpid = waitpid(-1, WNOHANG)) > 0) {
        logmsg "reaped $waitedpid" . ($? ? " con salida $?" : "");
    }
    $SIG{CHLD} = \&REAPER;  # odiar SysV
}
$SIG{CHLD} = \&REAPER;
for ( $waitedpid = 0;
      accept(my $client, $server) || $waitedpid;
      $waitedpid = 0, close $client)
{
    next if $waitedpid;
    logmsg "conexión en $NAME";
    spawn $client, sub {
        print "Hola, ahora son las ", scalar localtime(), "\n";
        exec("/usr/games/fortune")  || die "no se puede ejecutar fortune: $!";
    };
}
sub spawn {
    my $client = shift();
    my $coderef = shift();
    unless (@_ == 0 && $coderef && ref($coderef) eq "CODE") {
        confess "uso: spawn CLIENT CODEREF";
    }
    my $pid;
    unless (defined($pid = fork())) {
        logmsg "no se puede forkear: $!";
        return;
    }
    elsif ($pid) {
        logmsg "engendrado $pid";
        return; # Soy el padre
    }
    else {
        # Soy el hijo -- voy a engendrar
    }
    open(STDIN,  "<&", $client)
        || die "no se puede duplicar cliente a stdin";
    open(STDOUT, ">&", $client)
        || die "no se puede duplicar cliente a stdout";
    ## open(STDERR, ">&", STDOUT)
    ##  || die "no se puede duplicar stdout a stderr";
    exit($coderef->());
}

Como ves, es notablemente similar al servidor TCP de dominio de Internet, tanto es así que hemos omitido varias funciones duplicadas: spawn(), logmsg(), ctime() y REAPER(), que son las mismas que en el otro servidor.

Entonces, ¿por qué querrías usar un socket de dominio Unix en lugar de una tubería con nombre más simple? Porque una tubería con nombre no te da sesiones. No puedes distinguir los datos de un proceso de los de otro. Con la programación de sockets, obtienes una sesión separada para cada cliente; es por eso que accept() toma dos argumentos.

Por ejemplo, digamos que tienes un demonio de servidor de base de datos de larga ejecución al que quieres que la gente pueda acceder desde la Web, pero solo si pasan por una interfaz CGI. Tendrías un programa CGI pequeño y simple que haga las comprobaciones y registros que desees, y luego actúe como un cliente de dominio Unix y se conecte a tu servidor privado.

Un Cliente Sencillo

Aquí tienes un cliente que crea una conexión TCP al servicio "daytime" en el puerto 13 del nombre de host "localhost" e imprime todo lo que el servidor allí se molesta en proporcionar.

use v5.36;
use IO::Socket;
my $remote = IO::Socket::INET->new(
                    Proto    => "tcp",

Aquí tienes lo que significan esos parámetros para el constructor new():

"Proto"
Este es el protocolo a utilizar. En este caso, el manejador de socket devuelto estará conectado a un socket TCP, porque queremos una conexión orientada a flujos, es decir, una que actúe prácticamente como un archivo normal. No todos los sockets son de este tipo. Por ejemplo, el protocolo UDP se puede utilizar para crear un socket de datagramas, utilizado para el paso de mensajes.
"PeerAddr"
Este es el nombre o la dirección de Internet del host remoto en el que se está ejecutando el servidor. Podríamos haber especificado un nombre más largo como "www.perl.com", o una dirección como "207.171.7.72". Para fines de demostración, hemos utilizado el nombre de host especial "localhost", que siempre debería significar la máquina actual en la que te estás ejecutando. La dirección de Internet correspondiente para localhost es "127.0.0.1", si prefieres usar esa.
"PeerPort"
Este es el nombre del servicio o número de puerto al que nos gustaría conectarnos. Podríamos habernos salido con la nuestra usando solo "daytime" en sistemas con un archivo de servicios del sistema bien configurado [FOOTNOTE: El archivo de servicios del sistema se encuentra en /etc/services en sistemas tipo Unix.], pero aquí hemos especificado el número de puerto (13) entre paréntesis. Usar solo el número también habría funcionado, pero los literales numéricos ponen nerviosos a los programadores cuidadosos.

Un Cliente Webget

Aquí tienes un cliente sencillo que toma un host remoto del cual obtener un documento, y luego una lista de archivos para obtener de ese host. Este es un cliente más interesante que el anterior porque primero envía algo al servidor antes de obtener la respuesta del servidor.

#!/usr/bin/perl
use v5.36;
use IO::Socket;
unless (@ARGV > 1) { die "uso: $0 host url ..." }
my $host = shift(@ARGV);
my $EOL = "\015\012";
my $BLANK = $EOL x 2;
for my $document (@ARGV) {
    my $remote = IO::Socket::INET->new( Proto     => "tcp",
                                        PeerAddr  => $host,
                                        PeerPort  => "http(80)",
              )     || die "no se puede conectar a httpd en $host";
    $remote->autoflush(1);
    print $remote "GET $document HTTP/1.0" . $BLANK;
    while ( <$remote> ) { print }
    close $remote;
}

Se asume que el servidor web que maneja el servicio HTTP está en su puerto estándar, el número 80. Si el servidor al que intentas conectarte está en un puerto diferente, como 1080 u 8080, deberías especificarlo como el par de parámetros nombrados, "PeerPort => 8080". El método "autoflush" se utiliza en el socket porque de lo contrario el sistema almacenaría en búfer la salida que le enviamos. (Si estás en una Mac prehistórica, también necesitarás cambiar cada "\n" en tu código que envía datos a través de la red a ser un "\015\012" en su lugar).

Conectarse al servidor es solo la primera parte del proceso: una vez que tienes la conexión, tienes que usar el lenguaje del servidor. Cada servidor en la red tiene su propio pequeño lenguaje de comandos que espera como entrada. La cadena que enviamos al servidor comenzando con "GET" está en sintaxis HTTP. En este caso, simplemente solicitamos cada documento especificado. Sí, realmente estamos haciendo una nueva conexión para cada documento, aunque sea el mismo host. Así es como siempre tenías que hablar HTTP. Las versiones recientes de los navegadores web pueden solicitar que el servidor remoto deje la conexión abierta un tiempo, pero el servidor no tiene que honrar tal solicitud.

Clientes TCP con IO::Socket

El ejemplo más simple de un cliente TCP que usa IO::Socket es uno que simplemente copia de un socket a salida estándar. Esto se hace muy fácilmente al dividir el programa en dos procesos. El padre simplemente copia del socket a la salida estándar, mientras que el hijo copia simultáneamente de la entrada estándar al socket. Lograr lo mismo usando solo un proceso sería mucho más difícil, porque es más fácil codificar dos procesos para que hagan una cosa que codificar un proceso para que haga dos cosas. (Este principio de mantener la simplicidad es una piedra angular de la filosofía Unix, y también de la buena ingeniería de software, razón por la cual probablemente se ha extendido a otros sistemas.)

Aquí está el código:

#!/usr/bin/perl
use v5.36;
use IO::Socket;
unless (@ARGV == 2) { die "usage: $0 host port" }
my ($host, $port) = @ARGV;
# crea una conexión tcp al host y puerto especificados
my $handle = IO::Socket::INET->new(Proto     => "tcp",
                                   PeerAddr  => $host,
                                   PeerPort  => $port)
           || die "no se puede conectar al puerto $port en $host: $!";
$handle->autoflush(1);       # para que la salida llegue de inmediato
print STDERR "[Conectado a $host:$port]\n";
# divide el programa en dos procesos, gemelos idénticos
die "no se puede hacer fork: $!" unless defined(my $kidpid = fork());
# el bloque if{} se ejecuta solo en el proceso padre
if ($kidpid) {
    # copia el socket a la salida estándar
    while (defined (my $line = <$handle>)) {
        print STDOUT $line;
    }
    kill("TERM", $kidpid);   # envía SIGTERM al hijo
}
# el bloque else{} se ejecuta solo en el proceso hijo
else {
    # copia la entrada estándar al socket
    while (defined (my $line = <STDIN>)) {
        print $handle $line;
    }
    exit(0);                # por si acaso
}

La función "kill" en el bloque "if" del padre está ahí para enviar una señal a nuestro proceso hijo, que se está ejecutando actualmente en el bloque "else", tan pronto como el servidor remoto haya cerrado su extremo de la conexión.

Si el servidor remoto envía datos byte a byte, y necesita esos datos inmediatamente sin esperar una nueva línea (que podría no ocurrir), puede que desee reemplazar el bucle "while" en el padre con lo siguiente:

my $byte;
while (sysread($handle, $byte, 1) == 1) {
    print STDOUT $byte;
}

Realizar una llamada al sistema por cada byte que se desea leer no es muy eficiente (por decirlo suavemente), pero es lo más simple de explicar y funciona razonablemente bien.

Servidores TCP con IO::Socket

Como siempre, configurar un servidor es un poco más complicado que ejecutar un cliente. El modelo es que el servidor crea un tipo especial de socket que no hace nada más que escuchar en un puerto particular las conexiones entrantes. Esto se hace llamando al método "IO::Socket::INET->new()" con argumentos ligeramente diferentes a los que usó el cliente.

Proto
Este es el protocolo que se utilizará. Al igual que nuestros clientes, seguiremos especificando "tcp" aquí.
LocalPort
Especificamos un puerto local en el argumento "LocalPort", lo cual no hicimos para el cliente. Este es el nombre del servicio o número de puerto para el cual desea ser el servidor. (En Unix, los puertos por debajo de 1024 están restringidos al superusuario.) En nuestro ejemplo, usaremos el puerto 9000, pero puede usar cualquier puerto que no esté actualmente en uso en su sistema. Si intenta usar uno que ya está en uso, recibirá un mensaje de "Address already in use". En Unix, el comando "netstat -a" mostrará qué servicios tienen actualmente servidores.
Listen
El parámetro "Listen" se establece en el número máximo de conexiones pendientes que podemos aceptar hasta que rechacemos clientes entrantes. Piénselo como una cola de llamada en espera para su teléfono. El módulo de bajo nivel Socket tiene un símbolo especial para el máximo del sistema, que es SOMAXCONN.
Reuse
El parámetro "Reuse" es necesario para que podamos reiniciar nuestro servidor manualmente sin esperar unos minutos para que se limpien los búferes del sistema.

Una vez que se ha creado el socket genérico del servidor utilizando los parámetros enumerados anteriormente, el servidor espera a que un nuevo cliente se conecte a él. El servidor se bloquea en el método "accept", que finalmente acepta una conexión bidireccional del cliente remoto. (Asegúrese de hacer autoflush de este manejador para evitar el almacenamiento en búfer.)

Para aumentar la amigabilidad, nuestro servidor solicita comandos al usuario. La mayoría de los servidores no hacen esto. Debido a la solicitud sin nueva línea, tendrá que usar la variante "sysread" del cliente interactivo anterior.

Este servidor acepta uno de cinco comandos diferentes, enviando salida de vuelta al cliente. A diferencia de la mayoría de los servidores de red, este solo maneja un cliente entrante a la vez. Los servidores multitarea se cubren en el Capítulo 16 del Camel.

Aquí está el código.

#!/usr/bin/perl
use v5.36;
use IO::Socket;
use Net::hostent;      # para la versión orientada a objetos de gethostbyaddr
my $PORT = 9000;       # elige algo que no esté en uso
my $server = IO::Socket::INET->new( Proto     => "tcp",
                                    LocalPort => $PORT,
                                    Listen    => SOMAXCONN,
                                    Reuse     => 1);
die "no se puede configurar el servidor" unless $server;
print "[Servidor $0 aceptando clientes]\n";
while (my $client = $server->accept()) {
  $client->autoflush(1);
  print $client "Bienvenido a $0; escribe help para la lista de comandos.\n";
  my $hostinfo = gethostbyaddr($client->peeraddr);
  printf "[Conexión desde %s]\n",
         $hostinfo ? $hostinfo->name : $client->peerhost;
  print $client "Comando? ";
  while ( <$client>) {
    next unless /\S/;     # línea en blanco
    if    (/quit|exit/i)  { last                                      }
    elsif (/date|time/i)  { printf $client "%s\n", scalar localtime() }
    elsif (/who/i )       { print  $client `who 2>&1`                 }
    elsif (/cookie/i )    { print  $client `/usr/games/fortune 2>&1`  }
    elsif (/motd/i )      { print  $client `cat /etc/motd 2>&1`       }
    else {
      print $client "Comandos: quit date who cookie motd\n";
    }
  } continue {
     print $client "Comando? ";
  }
  close $client;
}

UDP: Paso de Mensajes

Otro tipo de configuración cliente-servidor es uno que utiliza mensajes en lugar de conexiones. Las comunicaciones UDP implican una sobrecarga mucho menor pero también proporcionan menos confiabilidad, ya que no hay garantías de que los mensajes lleguen, y mucho menos en orden y sin modificaciones. Sin embargo, UDP ofrece algunas ventajas sobre TCP, incluida la capacidad de "transmitir" o "multicast" a un montón de hosts de destino a la vez (generalmente en su subred local). Si se encuentra demasiado preocupado por la confiabilidad y comienza a crear comprobaciones en su sistema de mensajes, entonces probablemente debería usar TCP desde el principio.

Los datagramas UDP no son un flujo de bytes y no deben tratarse como tales. Esto hace que el uso de mecanismos de E/S con búferes internos como stdio (es decir, print() y similares) sea especialmente engorroso. Use syswrite(), o mejor aún send(), como en el siguiente ejemplo.

Aquí hay un programa UDP similar al ejemplo de cliente de Internet TCP proporcionado anteriormente. Sin embargo, en lugar de verificar un host a la vez, la versión UDP verificará muchos de ellos de forma asíncrona simulando un multicast y luego utilizando select() para esperar con tiempo de espera para E/S. Para hacer algo similar con TCP, tendría que usar un manejador de socket diferente para cada host.

#!/usr/bin/perl
use v5.36;
use Socket;
use Sys::Hostname;
my $SECS_OF_70_YEARS = 2_208_988_800;
my $iaddr = gethostbyname(hostname());
my $proto = getprotobyname("udp");
my $port = getservbyname("time", "udp");
my $paddr = sockaddr_in(0, $iaddr); # 0 significa que el kernel elija
socket(my $socket, PF_INET, SOCK_DGRAM, $proto) || die "socket: $!";
bind($socket, $paddr)                           || die "bind: $!";
$| = 1;
printf "%-12s %8s %s\n",  "localhost", 0, scalar localtime();
my $count = 0;
for my $host (@ARGV) {
    $count++;
    my $hisiaddr = inet_aton($host)         || die "host desconocido";
    my $hispaddr = sockaddr_in($port, $hisiaddr);
    defined(send($socket, 0, 0, $hispaddr)) || die "send $host: $!";
}
my $rout = my $rin = "";
vec($rin, fileno($socket), 1) = 1;
# tiempo de espera después de 10.0 segundos
while ($count && select($rout = $rin, undef, undef, 10.0)) {
    my $rtime = "";
    my $hispaddr = recv($socket, $rtime, 4, 0) || die "recv: $!";
    my ($port, $hisiaddr) = sockaddr_in($hispaddr);
    my $host = gethostbyaddr($hisiaddr, AF_INET);
    my $histime = unpack("N", $rtime) - $SECS_OF_70_YEARS;
    printf "%-12s ", $host;
    printf "%8d %s\n", $histime - time(), scalar localtime($histime);
    $count--;
}

Este ejemplo no incluye reintentos y, en consecuencia, puede fallar al contactar un host accesible. La razón más destacada de esto es la congestión de las colas en el host de envío si el número de hosts a contactar es suficientemente grande.

DESCRIPTION

This document is intended as a gentle introduction to interprocess communication (IPC) under Perl.

Perl provides several mechanisms for interprocess communication, ranging from simple filehandles to more complex System V IPC facilities. It's important to choose the right tool for the job, and to understand the tradeoffs involved.

Signals

Signals are a simple way for processes to communicate. One process can send a signal to another process, which can then take a predefined action or execute a Perl subroutine.

# Example of sending a signal
kill 15, $pid;

# Example of catching a signal
$SIG{TERM} = sub {
    print "Received TERM signal\n";
    # Perform cleanup tasks
    exit;
};

Named Pipes

Named pipes, also known as FIFOs (First-In, First-Out), are files that act as conduits for communication between processes. Data written to a named pipe by one process can be read by another.

# Create a named pipe
`mkfifo mypipe`;

# Open the pipe for reading or writing
open my $pipe_rx, '<', 'mypipe' or die "Cannot open pipe: $!";
open my $pipe_tx, '>', 'mypipe' or die "Cannot open pipe: $!";

Using open() for IPC

The open() function in Perl can be used to establish pipes to child processes, allowing for two-way communication.

# Open a pipe for writing to a child process
open my $pipe_tx, '|', 'some_command' or die "Cannot pipe to command: $!";
print $pipe_tx "Data to send\n";
close $pipe_tx;

# Open a pipe for reading from a child process
open my $pipe_rx, '-', 'some_command' or die "Cannot open pipe from command: $!";
my $line = <$pipe_rx>;
close $pipe_rx;

Sockets: Client/Server Communication

Sockets provide a robust mechanism for network communication between processes, whether they are on the same machine or different machines. Perl's Socket module provides a low-level interface to socket operations, while modules like IO::Socket offer a higher-level, object-oriented approach.

TCP Clients with IO::Socket

use IO::Socket;
my $sock = IO::Socket::INET->new(
    PeerAddr => 'www.example.com:80',
    Proto    => 'tcp',
) or die "Cannot connect: $@";
print $sock "GET / HTTP/1.0\r\n\r\n";
my $response = do { local $/; <$sock> };
close $sock;
print $response;

TCP Servers with IO::Socket

use IO::Socket;
my $socket = IO::Socket::INET->new(
    Listen    => 5,
    LocalPort => 8080,
    Proto     => 'tcp',
) or die "Cannot create socket: $@";
while (my $conn = $socket->accept()) {
    print $conn "Hello, world!\n";
    close $conn;
}

UDP: Message Passing

UDP (User Datagram Protocol) is a connectionless protocol suitable for sending individual messages (datagrams) without the overhead of establishing a connection. This can be useful for broadcasting or sending small amounts of data where reliability is less critical.

# Example of sending a UDP datagram
use IO::Socket;
my $sock = IO::Socket::INET->new(
    Proto => 'udp',
) or die "Cannot create socket: $@";
$sock->sendto('192.168.1.255', 12345, 0, "Broadcast message");

# Example of receiving a UDP datagram
use IO::Socket;
my $socket = IO::Socket::INET->new(
    LocalPort => 12345,
    Proto     => 'udp',
) or die "Cannot create socket: $@";
my $datagram = $socket->recvfrom(my $buffer, 1024);
print "Received from $datagram\n";

SysV IPC

Perl provides access to the System V IPC facilities (semaphores, shared memory, and message queues) through functions that mirror the C system calls. These can be powerful but are also more complex to use.

Example using semaphores to ensure only one process accesses a resource at a time:

First, create a semaphore in one process:

# create a semaphore
my $IPC_KEY = 1234;
my $id = semget($IPC_KEY, 1, 0666 | IPC_CREAT);
defined($id) || die "semget: $!";
print "sem id $id\n";

# Initialize the semaphore to 1
$semnum = 0;
$semop = 1;
$semflag = 0;
$opstring = pack("s!s!s!", $semnum, $semop, $semflag);
semop($id, $opstring) || die "semop: $!";

# ... critical section ...

# Decrement the semaphore to release the resource
$semop = -1;
$opstring = pack("s!s!s!", $semnum, $semop, $semflag);
semop($id, $opstring) || die "semop: $!";

Put this code in a separate file to be run in more than one process. Call the file take:

# create a semaphore
my $IPC_KEY = 1234;
my $id = semget($IPC_KEY, 0, 0);
defined($id) || die "semget: $!";
print "sem id $id\n";
my $semnum  = 0;
my $semflag = 0;
# "take" semaphore
# wait for semaphore to be zero
my $semop = 0;
my $opstring1 = pack("s!s!s!", $semnum, $semop, $semflag);
# Increment the semaphore count
$semop = 1;
my $opstring2 = pack("s!s!s!", $semnum, $semop, $semflag);
my $opstring  = $opstring1 . $opstring2;
semop($id, $opstring) || die "semop: $!";

Put this code in a separate file to be run in more than one process. Call this file give:

# "give" the semaphore
# run this in the original process and you will see
# that the second process continues
my $IPC_KEY = 1234;
my $id = semget($IPC_KEY, 0, 0);
die unless defined($id);
my $semnum  = 0;
my $semflag = 0;
# Decrement the semaphore count
my $semop = -1;
my $opstring = pack("s!s!s!", $semnum, $semop, $semflag);
semop($id, $opstring) || die "semop: $!";

The SysV IPC code above was written long ago, and it's definitely clunky looking. For a more modern look, see the IPC::SysV module.

A small example demonstrating SysV message queues:

use IPC::SysV qw(IPC_PRIVATE IPC_RMID IPC_CREAT S_IRUSR S_IWUSR);
my $id = msgget(IPC_PRIVATE, IPC_CREAT | S_IRUSR | S_IWUSR);
defined($id) || die "msgget failed: $!";
my $sent      = "message";
my $type_sent = 1234;
msgsnd($id, pack("l! a*", $type_sent, $sent), 0)
|| die "msgsnd failed: $!";
msgrcv($id, my $rcvd_buf, 60, 0, 0)
|| die "msgrcv failed: $!";
my($type_rcvd, $rcvd) = unpack("l! a*", $rcvd_buf);
if ($rcvd eq $sent) {
    print "okay\n";
} else {
    print "not okay\n";
}
msgctl($id, IPC_RMID, 0) || die "msgctl failed: $!\n";

NOTES

Most of these routines quietly but politely return "undef" when they fail instead of causing your program to die right then and there due to an uncaught exception. (Actually, some of the new Socket conversion functions do croak() on bad arguments.) It is therefore essential to check return values from these functions. Always begin your socket programs this way for optimal success, and don't forget to add the -T taint-checking flag to the "#!" line for servers:

#!/usr/bin/perl -T
use v5.36;
use sigtrap;
use Socket;

BUGS

These routines all create system-specific portability problems. As noted elsewhere, Perl is at the mercy of your C libraries for much of its system behavior. It's probably safest to assume broken SysV semantics for signals and to stick with simple TCP and UDP socket operations; e.g., don't try to pass open file descriptors over a local UDP datagram socket if you want your code to stand a chance of being portable.
