NOMBRE

perlsec - Seguridad en Perl

DESCRIPCIÓN

Perl está diseñado para facilitar la programación segura incluso cuando se ejecuta con privilegios adicionales, como programas setuid o setgid. A diferencia de la mayoría de los shells de línea de comandos, que se basan en múltiples pases de sustitución en cada línea del script, Perl utiliza un esquema de evaluación más convencional con menos trampas ocultas. Además, debido a que el lenguaje tiene más funcionalidad incorporada, puede depender menos de programas externos (y posiblemente no confiables) para lograr sus propósitos.

INFORMACIÓN DE CONTACTO PARA VULNERABILIDADES DE SEGURIDAD

Si cree que ha encontrado una vulnerabilidad de seguridad en el intérprete de Perl o en módulos mantenidos en el código base principal de Perl, envíe los detalles a perl-security@perl.org <mailto:perl-security@perl.org>. Esta dirección es una lista de correo de membresía cerrada monitoreada por el equipo de seguridad de Perl.

Consulte perlsecpolicy para obtener información adicional.

MECANISMOS Y PREOCUPACIONES DE SEGURIDAD

Modo de "taint" (contaminación)

Por defecto, Perl habilita automáticamente un conjunto de comprobaciones de seguridad especiales, llamado modo de taint, cuando detecta que su programa se ejecuta con IDs de usuario o grupo reales y efectivos diferentes. El bit setuid en los permisos de Unix es el modo 04000, el bit setgid el modo 02000; uno o ambos pueden estar establecidos. También puede habilitar el modo de taint explícitamente usando la bandera de línea de comandos -T. Esta bandera se recomienda encarecidamente para programas de servidor y cualquier programa ejecutado en nombre de otra persona, como un script CGI. Una vez que el modo de taint está activado, permanece así durante el resto de su script.

Mientras está en este modo, Perl toma precauciones especiales llamadas comprobaciones de taint para evitar trampas tanto obvias como sutiles. Algunas de estas comprobaciones son razonablemente simples, como verificar que los directorios de ruta no sean escribibles por otros; los programadores cuidadosos siempre han utilizado comprobaciones como estas. Otras comprobaciones, sin embargo, se soportan mejor con el propio lenguaje, y son estas comprobaciones especialmente las que contribuyen a hacer que un programa Perl set-id sea más seguro que el programa C correspondiente.

El soporte para comprobaciones de taint añade una sobrecarga a todos los programas Perl, ya sea que esté utilizando o no las características de taint. Perl 5.18 introdujo símbolos del preprocesador C que se pueden usar para deshabilitar las características de taint al compilar Perl.

Cuando el taint está habilitado, no puede usar datos derivados del exterior de su programa para afectar algo fuera de su programa, al menos, no por accidente. Todos los argumentos de la línea de comandos, variables de entorno, información de localización (ver perllocale), resultados de ciertas llamadas al sistema (readdir(), readlink(), la variable de shmread(), los mensajes devueltos por msgrcv(), los campos de contraseña, gcos y shell devueltos por las llamadas getpwxxx()), y toda la entrada de archivos se marcan como "tainted". Los datos tainted no pueden usarse directa o indirectamente en ningún comando que invoque un subshell, ni en ningún comando que modifique archivos, directorios o procesos, con las siguientes excepciones:

  • Los argumentos para "print" y "syswrite" no se verifican en busca de taintedness.
  • Los métodos simbólicos 
    $obj->$method(@args);

    y las referencias a subrutinas simbólicas

    &{$foo}(@args);
$foo->(@args);

    no se verifican en busca de taintedness. Esto requiere un cuidado adicional a menos que desee que los datos externos afecten su flujo de control. A menos que limite cuidadosamente cuáles son estos valores simbólicos, las personas podrán llamar a funciones fuera de su código Perl, como POSIX::system, en cuyo caso podrán ejecutar código externo arbitrario.

  • Las claves de hash nunca están taintadas.

Por razones de eficiencia, Perl adopta una visión conservadora sobre si los datos están taintados. Si una expresión contiene datos taintados, cualquier subexpresión puede considerarse taintada, incluso si el valor de la subexpresión no se ve afectado por los datos taintados.

Debido a que la taintedness se asocia con cada valor escalar, algunos elementos de un array o hash pueden estar taintados y otros no. Las claves de un hash nunca están taintadas.

Por ejemplo:

$arg = shift;               # $arg está tainted
$hid = $arg . 'bar';        # $hid también está tainted
$line = <>;                 # Tainted
$line = <STDIN>;            # También tainted
open FOO, "/home/me/bar" or die $!;
$line = <FOO>;              # Todavía tainted
$path = $ENV{'PATH'};       # Tainted, pero ver más abajo
$data = 'abc';              # No tainted
system "echo $arg";         # Inseguro
system "/bin/echo", $arg;   # Considerado inseguro
                            # (Perl no conoce /bin/echo)
system "echo $hid";         # Inseguro
system "echo $data";        # Inseguro hasta que se establezca PATH
$path = $ENV{'PATH'};       # $path ahora está tainted
$ENV{'PATH'} = '/bin:/usr/bin';
delete @ENV{'IFS', 'CDPATH', 'ENV', 'BASH_ENV'};
$path = $ENV{'PATH'};       # $path ahora NO está tainted
system "echo $data";        # ¡Ahora es seguro!
open(FOO, "< $arg");        # OK - archivo de solo lectura
open(FOO, "> $arg");        # No OK - intentando escribir
open(FOO,"echo $arg|");     # No OK
open(FOO,"-|")
    or exec 'echo', $arg;   # Tampoco OK
$shout = `echo $arg`;       # Inseguro, $shout ahora tainted
unlink $data, $arg;         # Inseguro
umask $arg;                 # Inseguro
exec "echo $arg";           # Inseguro
exec "echo", $arg;          # Inseguro
exec "sh", '-c', $arg;      # ¡Muy inseguro!
@files = <*.c>;             # inseguro (usa readdir() o similar)
@files = glob('*.c');       # inseguro (usa readdir() o similar)
# En cualquier caso, los resultados de glob están taintados, ya que la lista de
# nombres de archivo proviene del exterior del programa.
$bad = ($arg, 23);          # $bad estará tainted
$arg, `true`;               # Inseguro (aunque realmente no lo es)

Si intenta hacer algo inseguro, obtendrá un error fatal que dirá algo como "Insecure dependency" o "Insecure $ENV{PATH}".

La excepción al principio de "un valor tainted contamina toda la expresión" es el operador condicional ternario "?:". Dado que el código con un condicional ternario

$result = $tainted_value ? "Untainted" : "Also untainted";

es efectivamente

if ( $tainted_value ) {
    $result = "Untainted";
} else {
    $result = "Also untainted";
}

no tiene sentido que $result esté tainted.

Lavado y Detección de Datos Tainted

Para probar si una variable contiene datos taintados, y cuyo uso provocaría un mensaje de "Insecure dependency", puede usar la función tainted() del módulo Scalar::Util, disponible en su espejo CPAN más cercano, e incluido en Perl a partir de la versión 5.8.0. O puede que pueda usar la siguiente función is_tainted().

sub is_tainted {
    local $@;   # No contaminar el valor del llamador.
    return ! eval { eval("#" . substr(join("", @_), 0, 0)); 1 };
}

Esta función aprovecha el hecho de que la presencia de datos taintados en cualquier parte de una expresión hace que toda la expresión esté taintada. Sería ineficiente que cada operador probara cada argumento en busca de taintedness. En cambio, se utiliza el enfoque ligeramente más eficiente y conservador de que si se ha accedido a algún valor tainted dentro de la misma expresión, toda la expresión se considera taintada.

Pero probar la taintedness solo te lleva hasta cierto punto. A veces, simplemente tienes que limpiar la taintedness de tus datos. Los valores pueden descontaminarse usándolos como claves en un hash; de lo contrario, la única manera de evitar el mecanismo de taint es haciendo referencia a subpatrones de una coincidencia de expresión regular. Perl presume que si hace referencia a una subcadena usando $1, $2, etc. en un patrón no taintado, usted sabía lo que estaba haciendo cuando escribió ese patrón. Taint mode

Taint mode ("-T") is a mode that Perl can run in which tries to prevent you from doing stupid things with data that came from outside the program. It is not intended as a comprehensive security mechanism, but rather as a way to catch potentially embarrassing mistakes.

When running in taint mode, Perl assumes that all command-line arguments, environment variables, and filehandles opened for reading are tainted. Tainted data may not be used in operations that could potentially have security implications. These include:

Proteger sus programas

Hay varias maneras de ocultar el código fuente de sus programas Perl, con distintos niveles de "seguridad".

En primer lugar, sin embargo, *no puedes* quitar el permiso de lectura, porque el código fuente debe ser legible para poder ser compilado e interpretado. (Eso no significa que el código fuente de un script CGI sea legible por personas en la web, sin embargo.) Así que tienes que dejar los permisos en el nivel socialmente amigable de 0755. Esto permite que las personas en tu sistema local solo vean tu código fuente.

Algunas personas consideran erróneamente esto como un problema de seguridad. Si tu programa hace cosas inseguras y depende de que la gente no sepa cómo explotar esas inseguridades, no es seguro. A menudo es posible que alguien determine las cosas inseguras y las explote sin ver el código fuente. La seguridad a través de la oscuridad, el nombre para ocultar tus errores en lugar de arreglarlos, es muy poca seguridad.

Puedes intentar usar cifrado a través de filtros de origen (Filter::* de CPAN, o Filter::Util::Call y Filter::Simple desde Perl 5.8). Pero los crackers podrían ser capaces de descifrarlo. Puedes intentar usar el compilador e intérprete de bytecode descrito a continuación, pero los crackers podrían ser capaces de descompilarlo. Puedes intentar usar el compilador de código nativo descrito a continuación, pero los crackers podrían ser capaces de desensamblarlo. Estos presentan diferentes grados de dificultad para las personas que quieren acceder a tu código, pero ninguno puede ocultarlo definitivamente (esto es cierto para todos los lenguajes, no solo para Perl).

Si te preocupa que la gente se beneficie de tu código, la conclusión es que nada más que una licencia restrictiva te dará seguridad legal. Licencia tu software y salpícalo con declaraciones amenazantes como "Este es software propietario no publicado de XYZ Corp. Tu acceso a él no te da permiso para usarlo bla bla bla". Deberías consultar a un abogado para asegurarte de que la redacción de tu licencia sea válida en los tribunales.

Ataques de complejidad algorítmica

Ciertos algoritmos internos utilizados en la implementación de Perl pueden ser atacados eligiendo la entrada cuidadosamente para consumir grandes cantidades de tiempo o espacio, o ambos. Esto puede llevar a los llamados ataques de *Denegación de Servicio* (DoS).

•
Algoritmo Hash - Los algoritmos hash como el utilizado en Perl son bien conocidos por ser vulnerables a ataques de colisión en su función hash. Dichos ataques implican la construcción de un conjunto de claves que colisionan en el mismo bucket, produciendo un comportamiento ineficiente. Dichos ataques a menudo dependen del descubrimiento de la semilla de la función hash utilizada para mapear las claves a los buckets. Esa semilla se utiliza luego para probar por fuerza bruta un conjunto de claves que se puede usar para montar un ataque de denegación de servicio. En Perl 5.8.1 se introdujeron cambios para endurecer Perl contra tales ataques, y luego más tarde en Perl 5.18.0 estas características se mejoraron y se agregaron protecciones adicionales.

En el momento de escribir esto, Perl 5.18.0 se considera bien protegido contra ataques de complejidad algorítmica en su implementación hash. Esto se debe en gran medida a las siguientes medidas que mitigan los ataques:

Aleatorización de la Semilla Hash
Para hacer imposible saber qué semilla generar un conjunto de claves de ataque, esta semilla se inicializa aleatoriamente al inicio del proceso. Esto puede ser anulado usando la variable de entorno PERL_HASH_SEED, ver "PERL_HASH_SEED" en perlrun. Esta variable de entorno controla cómo se almacenan realmente los elementos, no cómo se presentan a través de "keys", "values" y "each".
Aleatorización del Recorrido Hash
Independientemente de la semilla utilizada en la función hash, "keys", "values" y "each" devuelven elementos en un orden aleatorio por hash. Modificar un hash mediante inserción cambiará el orden de iteración de ese hash. Este comportamiento puede ser anulado usando hash_traversal_mask() de Hash::Util o usando la variable de entorno PERL_PERTURB_KEYS, ver "PERL_PERTURB_KEYS" en perlrun. Tenga en cuenta que esta característica controla el orden "visible" de las claves, y no el orden real en que se almacenan.
Perturbación del Orden de los Buckets
Cuando los elementos colisionan en un bucket hash dado, el orden en que se almacenan en la cadena ya no es predecible en Perl 5.18. La intención de esto es dificultar la observación de una colisión. Este comportamiento puede ser anulado usando la variable de entorno PERL_PERTURB_KEYS, ver "PERL_PERTURB_KEYS" en perlrun.
Nueva Función Hash Predeterminada
La función hash predeterminada se ha modificado con la intención de dificultar la inferencia de la semilla hash.
Funciones Hash Alternativas
El código fuente incluye múltiples algoritmos hash para elegir. Si bien creemos que el hash de Perl predeterminado es robusto al ataque, hemos incluido la función hash Siphash como opción de respaldo. En el momento del lanzamiento de Perl 5.18.0, se cree que Siphash tiene fortaleza criptográfica. Esta no es la opción predeterminada, ya que es mucho más lenta que el hash predeterminado.

Sin compilar un Perl especial, no hay forma de obtener el comportamiento exacto de las versiones anteriores a Perl 5.18.0. Lo más cercano que se puede conseguir es estableciendo PERL_PERTURB_KEYS a 0 y estableciendo PERL_HASH_SEED a un valor conocido. No recomendamos esas configuraciones para uso en producción debido a las consideraciones de seguridad anteriores.

Perl nunca ha garantizado ningún orden de las claves hash, y el orden ya ha cambiado varias veces durante la vida de Perl 5. Además, el orden de las claves hash siempre ha sido, y continúa siendo, afectado por el orden de inserción y el historial de cambios realizados en el hash a lo largo de su vida útil.

También tenga en cuenta que, si bien el orden de los elementos hash puede ser aleatorio, esta "pseudo-ordenación" no debe utilizarse para aplicaciones como barajar una lista aleatoriamente (use List::Util::shuffle() para eso, ver List::Util, un módulo central estándar desde Perl 5.8.0; o el módulo CPAN "Algorithm::Numerical::Shuffle"), ni para generar permutaciones (use, por ejemplo, los módulos CPAN "Algorithm::Permute" o "Algorithm::FastPermute"), ni para ninguna aplicación criptográfica.

Los hashes enlazados pueden tener su propio orden y ataques de complejidad algorítmica.

  • Expresiones regulares - El motor de expresiones regulares de Perl es el llamado NFA (Autómata Finito No Determinista), lo que entre otras cosas significa que puede consumir fácilmente grandes cantidades de tiempo y espacio si la expresión regular puede coincidir de varias maneras. Una cuidadosa elaboración de las expresiones regulares puede ayudar, pero a menudo no hay mucho que se pueda hacer (el libro "Mastering Regular Expressions" es lectura obligatoria, ver perlfaq2). Quedarse sin espacio se manifiesta por el hecho de que Perl se queda sin memoria.
  • Ordenación - el algoritmo quicksort utilizado en Perl antes de 5.8.0 para implementar la función sort() era muy fácil de engañar para que se comportara mal, de modo que consumiera mucho tiempo. A partir de Perl 5.8.0, se utiliza por defecto un algoritmo de ordenación diferente, mergesort. Mergesort no puede comportarse mal con ninguna entrada.

Consulte https://www.usenix.org/legacy/events/sec03/tech/full_papers/crosby/crosby.pdf para más información, y cualquier libro de texto de informática sobre complejidad algorítmica.

La popular herramienta "sudo" proporciona una forma controlada para que los usuarios puedan ejecutar programas como otros usuarios. Sanea el entorno de ejecución hasta cierto punto, y

Si no tiene la versión segura de los scripts set-id, entonces "sudo" puede ser una forma más conveniente de ejecutar un script como otro usuario que escribir un envoltorio C.

Sin embargo, "sudo" establece el ID de usuario o grupo real al de la identidad de destino, no solo el ID efectivo como hacen los bits set-id. Como resultado, Perl no puede detectar que se está ejecutando bajo "sudo", y por lo tanto no tomará automáticamente sus propias precauciones de seguridad, como activar el modo taint. Donde la configuración de "sudo" dicta exactamente qué comando se puede ejecutar, el comando aprobado puede incluir una opción "-T" para perl para habilitar el modo taint.

En general, es necesario evaluar la idoneidad de un script para ejecutarse bajo "sudo" específicamente teniendo en cuenta ese tipo de entorno de ejecución.
