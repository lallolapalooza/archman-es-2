NOMBRE

perlobj - Referencia a objetos de Perl

DESCRIPCIÓN

Este documento proporciona una referencia para las características de orientación a objetos de Perl. Si está buscando una introducción a la programación orientada a objetos en Perl, consulte perlootut.

Para comprender los objetos de Perl, primero debe comprender las referencias en Perl. Consulte perlreftut para obtener detalles.

Este documento describe todas las características de orientación a objetos (OO) de Perl desde cero. Si solo está buscando escribir su propio código orientado a objetos, probablemente le convenga utilizar uno de los sistemas de objetos de CPAN descritos en perlootut.

Si está buscando escribir su propio sistema de objetos, o necesita mantener código que implemente objetos desde cero, este documento le ayudará a comprender exactamente cómo Perl maneja la orientación a objetos.

Hay algunos principios básicos que definen la Perl orientada a objetos:

1.
Un objeto es simplemente una estructura de datos que sabe a qué clase pertenece.
2.
Una clase es simplemente un paquete. Una clase proporciona métodos que esperan operar sobre objetos.
3.
Un método es simplemente una subrutina que espera una referencia a un objeto (o un nombre de paquete, para métodos de clase) como primer argumento.

Examinemos cada uno de estos principios en profundidad.

Un Objeto es Simplemente una Estructura de Datos

A diferencia de muchos otros lenguajes que soportan la orientación a objetos, Perl no proporciona una sintaxis especial para construir un objeto. Los objetos son meramente estructuras de datos de Perl (hashes, arrays, escalares, filehandles, etc.) que se han asociado explícitamente con una clase en particular.

Esa asociación explícita se crea mediante la función incorporada "bless", que normalmente se utiliza dentro de la subrutina constructor de la clase.

Aquí hay un constructor simple:

package File;
sub new {
    my $class = shift;
    return bless {}, $class;
}

El nombre "new" no es especial. Podríamos nombrar nuestro constructor de otra manera:

package File;
sub load {
    my $class = shift;
    return bless {}, $class;
}

La convención moderna para los módulos OO es usar siempre "new" como el nombre del constructor, pero no hay ningún requisito para hacerlo. Cualquier subrutina que bendiga una estructura de datos en una clase es un constructor válido en Perl.

En los ejemplos anteriores, el código "{}" crea una referencia a un hash anónimo vacío. La función "bless" toma esa referencia y asocia el hash con la clase en $class. En el caso más simple, la variable $class terminará contiendo la cadena "File".

También podemos usar una variable para almacenar una referencia a la estructura de datos que se está bendiciendo como nuestro objeto:

sub new {
    my $class = shift;
    my $self = {};
    bless $self, $class;
    return $self;
}

Una vez que hemos bendecido el hash al que se refiere $self, podemos empezar a llamar a métodos sobre él. Esto es útil si desea colocar la inicialización del objeto en su propio método separado:

sub new {
    my $class = shift;
    my $self = {};
    bless $self, $class;
    $self->_initialize();
    return $self;
}

Dado que el objeto también es un hash, puede tratarlo como tal, utilizándolo para almacenar datos asociados con el objeto. Típicamente, el código dentro de la clase puede tratar el hash como una estructura de datos accesible, mientras que el código fuera de la clase siempre debe tratar el objeto como opaco. Esto se llama encapsulación. La encapsulación significa que el usuario de un objeto no tiene que saber cómo está implementado. El usuario simplemente llama a métodos documentados en el objeto.

Sin embargo, tenga en cuenta que (a diferencia de la mayoría de los demás lenguajes OO) Perl no garantiza ni impone la encapsulación de ninguna manera. Si desea que los objetos sean realmente opacos, debe organizarlo usted mismo. Esto se puede hacer de varias maneras, incluido el uso de "objetos Inside-Out" o módulos de CPAN.

Los objetos son bendecidos; las variables no

Cuando bendecimos algo, no estamos bendiciendo la variable que contiene una referencia a esa cosa, ni estamos bendiciendo la referencia que la variable almacena; estamos bendiciendo la cosa a la que se refiere la variable (a veces conocida como el referente). Esto se demuestra mejor con este código:

use Scalar::Util 'blessed';
my $foo = {};
my $bar = $foo;
bless $foo, 'Class';
print blessed( $bar ) // 'not blessed';    # imprime "Class"
$bar = "some other value";
print blessed( $bar ) // 'not blessed';    # imprime "not blessed"

Cuando llamamos a "bless" en una variable, en realidad estamos bendiciendo la estructura de datos subyacente a la que se refiere la variable. No estamos bendiciendo la referencia en sí, ni la variable que contiene esa referencia. Es por eso que la segunda llamada a blessed( $bar ) devuelve falso. En ese momento $bar ya no almacena una referencia a un objeto.

A veces verá libros o documentación más antiguos que mencionan "bendecir una referencia" o describen un objeto como una "referencia bendecida", pero esto es incorrecto. No es la referencia lo que se bendice como objeto; es la cosa a la que se refiere la referencia (es decir, el referente).

Una Clase es Simplemente un Paquete

Perl no proporciona ninguna sintaxis especial para las definiciones de clases. Un paquete es simplemente un espacio de nombres que contiene variables y subrutinas. La única diferencia es que, en una clase, las subrutinas pueden esperar una referencia a un objeto o el nombre de una clase como primer argumento. Esto es puramente una cuestión de convención, por lo que una clase puede contener tanto métodos como subrutinas que no operan sobre un objeto o clase.

Cada paquete contiene un array especial llamado @ISA. El array @ISA contiene una lista de las clases padre de esa clase, si las hay. Este array se examina cuando Perl realiza la resolución de métodos, lo que cubriremos más adelante.

Llamar a métodos desde un paquete significa que debe ser cargado, por supuesto, por lo que a menudo querrá cargar un módulo y agregarlo a @ISA al mismo tiempo. Puede hacerlo en un solo paso utilizando la pragmática parent. (En código más antiguo puede encontrar la pragmática base, que hoy en día se desaconseja excepto cuando tenga que trabajar con la igualmente desaconsejada pragmática fields.)

Sin embargo se establezcan las clases padre, la variable @ISA del paquete contendrá una lista de esos padres. Esto es simplemente una lista de escalares, cada uno de los cuales es una cadena que corresponde a un nombre de paquete.

Todas las clases heredan de la clase UNIVERSAL implícitamente. La clase UNIVERSAL es implementada por el núcleo de Perl y proporciona varios métodos predeterminados, como isa(), can() y VERSION(). La clase "UNIVERSAL" nunca aparecerá en la variable @ISA de un paquete.

Perl solo proporciona la herencia de métodos como una característica incorporada. La herencia de atributos se deja a cargo de la clase implementarla. Consulte la sección "Escritura de Accesorios" para obtener más detalles.

Un Método es Simplemente una Subrutina

Perl no proporciona ninguna sintaxis especial para definir un método. Un método es simplemente una subrutina regular y se declara con "sub". Lo que hace especial a un método es que espera recibir un objeto o un nombre de clase como su primer argumento.

Perl sí proporciona sintaxis especial para la invocación de métodos, el operador "->". Cubriremos esto con más detalle más adelante.

La mayoría de los métodos que escribirá esperarán operar sobre objetos:

sub save {
    my $self = shift;
    open my $fh, '>', $self->path() or die $!;
    print {$fh} $self->data()       or die $!;
    close $fh                       or die $!;
}

Invocación de Métodos

Llamar a un método en un objeto se escribe como "$object->method".

The Invocation Operator

The arrow operator (->) is used to invoke methods on objects, or to invoke class methods on a class name.

    $object->method( arg1, arg2 )
    ClassName->method( arg1, arg2 )

In both cases, the left-hand side is the object (or class name), and the right-hand side is the method name.

my $pod = File->new( 'perlobj.pod', $data );
$pod->save();

The -> syntax is also used when dereferencing a reference. It looks like the same operator, but these are two different operations.

When you call a method, the thing on the left side of the arrow is passed as the first argument to the method. That means when we call Critter->new(), the new() method receives the string "Critter" as its first argument. When we call $fred->speak(), the $fred variable is passed as the first argument to speak().

Just as with any Perl subroutine, all of the arguments passed in @_ are aliases to the original argument. This includes the object itself. If you assign directly to $_[0] you will change the contents of the variable that holds the reference to the object. We recommend that you don't do this unless you know exactly what you're doing.

Perl knows what package the method is in by looking at the left side of the arrow. If the left hand side is a package name, it looks for the method in that package. If the left hand side is an object, then Perl looks for the method in the package that the object has been blessed into.

If the left hand side is neither a package name nor an object, then the method call will cause an error, but see the section on "Method Call Variations" for more nuances.

Inheritance

We already talked about the special @ISA array and the parent pragma.

When a class inherits from another class, any methods defined in the parent class are available to the child class. If you attempt to call a method on an object that isn't defined in its own class, Perl will also look for that method in any parent classes it may have.

package File::MP3;
use parent 'File';    # sets @File::MP3::ISA = ('File');
my $mp3 = File::MP3->new( 'Andvari.mp3', $data );
$mp3->save();

Since we didn't define a save() method in the "File::MP3" class, Perl will look at the "File::MP3" class's parent classes to find the save() method. If Perl cannot find a save() method anywhere in the inheritance hierarchy, it will die.

In this case, it finds a save() method in the "File" class. Note that the object passed to save() in this case is still a "File::MP3" object, even though the method is found in the "File" class.

We can override a parent's method in a child class. When we do so, we can still call the parent class's method with the SUPER pseudo-class.

sub save {
    my $self = shift;
    say 'Prepare to rock';
    $self->SUPER::save();
}

The SUPER modifier can only be used for method calls. You can't use it for regular subroutine calls or class methods:

SUPER::save($thing);     # FAIL: looks for save() sub in package SUPER
SUPER->save($thing);     # FAIL: looks for save() method in class
                         #       SUPER
$thing->SUPER::save();   # Okay: looks for save() method in parent
                         #       classes

How SUPER is Resolved

The SUPER pseudo-class is resolved from the package where the call is made. It is not resolved based on the object's class. This is important, because it lets methods at different levels within a deep inheritance hierarchy each correctly call their respective parent methods.

package A;
sub new {
    return bless {}, shift;
}
sub speak {
    my $self = shift;
    say 'A';
}
package B;
use parent -norequire, 'A';
sub speak {
    my $self = shift;
    $self->SUPER::speak();
    say 'B';
}
package C;
use parent -norequire, 'B';
sub speak {
    my $self = shift;
    $self->SUPER::speak();
    say 'C';
}
my $c = C->new();
$c->speak();

In this example, we will get the following output:

A
B
C

This demonstrates how SUPER is resolved. Even though the object is blessed into the "C" class, the speak() method in the "B" class can still call SUPER::speak() and expect it to correctly look in the parent class of "B" (i.e., the class the method call is in), not in the parent class of "C" (i.e. the class the object belongs to).

There are rare cases where this package-based resolution can be a problem. If you copy a subroutine from one package to another, SUPER resolution will be done based on the original package.

Multiple Inheritance

Multiple inheritance often indicates a design problem, but Perl always gives you enough rope to hang yourself with if you ask for it.

To declare multiple parents, you simply need to pass multiple class names to use parent:

package MultiChild;
use parent 'Parent1', 'Parent2';

Method Resolution Order

Method resolution order only matters in the case of multiple inheritance. In the case of single inheritance, Perl simply looks up the inheritance chain to find a method:

Grandparent
  |
Parent
  |
Child

If we call a method on a "Child" object and that method is not defined in the "Child" class, Perl will look for that method in the "Parent" class and then, if necessary, in the "Grandparent" class.

If Perl cannot find the method in any of these classes, it will die with an error message.

When a class has multiple parents, the method lookup order becomes more complicated.

By default, Perl does a depth-first left-to-right search for a method. That means it starts with the first parent in the @ISA array, and then searches all of its parents, grandparents, etc. If it fails to find the method, it then goes to the next parent in the original class's @ISA array and searches from there.

          SharedGreatGrandParent
          /                    \
PaternalGrandparent       MaternalGrandparent
          \                    /
           Father        Mother
                 \      /
                  Child

So given the diagram above, Perl will search "Child", "Father", "PaternalGrandparent", "SharedGreatGrandParent", "Mother", and finally "MaternalGrandparent". This may be a problem because now we're looking in "SharedGreatGrandParent" before we've checked all its derived classes (i.e. before we tried "Mother" and "MaternalGrandparent").

It is possible to ask for a different method resolution order with the mro pragma.

package Child;
use mro 'c3';
use parent 'Father', 'Mother';

This pragma lets you switch to the "C3" resolution order. In simple terms, "C3" order ensures that shared parent classes are never searched before child classes, so Perl will now search: "Child", "Father", "PaternalGrandparent", "Mother" "MaternalGrandparent", and finally "SharedGreatGrandParent". Note however that this is not "breadth-first" searching: All the "Father" ancestors (except the common ancestor) are searched before any of the "Mother" ancestors are considered.

The C3 order also lets you call methods in sibling classes with the next pseudo-class. See the mro documentation for more details on this feature.

Method Resolution Caching

When Perl searches for a method, it caches the lookup so that future calls to the method do not need to search for it again. Changing a class's parent class or adding subroutoutines to a class will invalidate the cache for that class.

The mro pragma provides some functions for manipulating the method cache directly.

Writing Constructors

As we mentioned earlier, Perl provides no special constructor syntax. This means that a class must implement its own constructor. A constructor is simply a class method that returns a reference to a new object.

The constructor can also accept additional parameters that define the object. Let's write a real constructor for the "File" class we used earlier:

package File;
sub new {
    my $class = shift;
    my ( $path, $data ) = @_;
    my $self = bless {
        path => $path,
        data => $data,
    }, $class;
    return $self;
}

As you can see, we've stored the path and file data in the object itself. Remember, under the hood, this object is still just a hash. Later, we'll write accessors to manipulate this data.

For our "File::MP3" class, we can check to make sure that the path we're given ends with ".mp3":

package File::MP3;
sub new {
    my $class = shift;
    my ( $path, $data ) = @_;
    die "You cannot create a File::MP3 without an mp3 extension\n"
        unless $path =~ /\.mp3\z/;
    return $class->SUPER::new(@_);
}

This constructor lets its parent class do the actual object construction.

Attributes

An attribute is a piece of data belonging to a particular object. Unlike most object-oriented languages, Perl provides no special syntax or support for declaring and manipulating attributes.

Atributos y Acceso

Los atributos a menudo se almacenan en el objeto mismo. Por ejemplo, si el objeto es un hash anónimo, podemos almacenar los valores de los atributos en el hash usando el nombre del atributo como clave.

Si bien es posible referirse directamente a estas claves de hash fuera de la clase, se considera una buena práctica envolver todo el acceso al atributo con métodos accesores.

Esto tiene varias ventajas. Los accesores facilitan el cambio de la implementación de un objeto más adelante, preservando al mismo tiempo la API original.

Un accesor le permite agregar código adicional alrededor del acceso al atributo. Por ejemplo, podría aplicar un valor predeterminado a un atributo que no se estableció en el constructor, o podría validar que un nuevo valor para el atributo sea aceptable.

Finalmente, el uso de accesores hace que la herencia sea mucho más simple. Las subclases pueden usar los accesores en lugar de tener que saber cómo una clase padre está implementada internamente.

Escribiendo Accesores

Al igual que con los constructores, Perl no proporciona una sintaxis especial para la declaración de accesores, por lo que las clases deben proporcionar métodos accesores escritos explícitamente. Hay dos tipos comunes de accesores, de solo lectura y de lectura/escritura.

Un accesor simple de solo lectura simplemente obtiene el valor de un único atributo:

sub path {
    my $self = shift;
    return $self->{path};
}

Un accesor de lectura/escritura permitirá al llamador establecer el valor así como obtenerlo:

sub path {
    my $self = shift;
    if (@_) {
        $self->{path} = shift;
    }
    return $self->{path};
}

Una Pausa Sobre Código Más Inteligente y Seguro

Nuestro constructor y accesores no son muy inteligentes. No verifican que un $path esté definido, ni verifican que un $path sea una ruta de sistema de archivos válida.

Realizar estas verificaciones manualmente puede volverse tedioso rápidamente. Escribir un montón de accesores manualmente también es increíblemente tedioso. Hay muchos módulos en CPAN que pueden ayudarlo a escribir código más seguro y conciso, incluidos los módulos que recomendamos en perlootut.

Variaciones de Llamada a Métodos

Perl admite varias otras formas de llamar a métodos además del uso "$object->method()" que hemos visto hasta ahora.

Nombres de Métodos con un Nombre Completamente Calificado

Perl le permite llamar a métodos usando su nombre completamente calificado (el paquete y el nombre del método):

my $mp3 = File::MP3->new( 'Regin.mp3', $data );
$mp3->File::save();

Cuando llama a un nombre de método completamente calificado como "File::save", la búsqueda de resolución de métodos para el método "save" comienza en la clase "File", omitiendo cualquier método "save" que la clase "File::MP3" pueda haber definido. Todavía busca en los padres de la clase "File" si es necesario.

Si bien esta característica se usa más comúnmente para llamar explícitamente a métodos heredados de una clase ancestral, no existe una restricción técnica que lo impida:

my $obj = Tree->new();
$obj->Dog::bark();

Esto llama al método "bark" de la clase "Dog" en un objeto de la clase "Tree", incluso si las dos clases no están relacionadas en absoluto. Use esto con gran cuidado.

La pseudoclase "SUPER" que se describió anteriormente *no* es lo mismo que llamar a un método con un nombre completamente calificado. Consulte la sección anterior "Herencia" para obtener más detalles.

Nombres de Métodos como Cadenas

Perl le permite usar una variable escalar que contiene una cadena como nombre de método:

my $file = File->new( $path, $data );
my $method = 'save';
$file->$method();

Esto funciona exactamente como llamar "$file->save()". Esto puede ser muy útil para escribir código dinámico. Por ejemplo, le permite pasar un nombre de método para llamarlo como parámetro a otro método.

Nombres de Clases como Cadenas

Perl también le permite usar un escalar que contiene una cadena como nombre de clase:

my $class = 'File';
my $file = $class->new( $path, $data );

Nuevamente, esto permite un código muy dinámico.

Referencias de Subrutinas como Métodos

También puede usar una referencia de subrutina como método:

my $sub = sub {
    my $self = shift;
    $self->save();
};
$file->$sub();

Esto es exactamente equivalente a escribir $sub->($file). Puede ver este modismo en uso combinado con una llamada a "can":

if ( my $meth = $object->can('foo') ) {
    $object->$meth();
}

Desreferenciando la Llamada a Método

Perl también le permite usar una referencia escalar desreferenciada en una llamada a método. Eso es un trabalenguas, así que veamos algo de código:

$file->${ \'save' };
$file->${ returns_scalar_ref() };
$file->${ \( returns_scalar() ) };
$file->${ returns_ref_to_sub_ref() };

Esto funciona si la desreferenciación produce una cadena *o* una referencia de subrutina.

Llamadas a Métodos en Filehandles

En el fondo, los filehandles de Perl son instancias de la clase "IO::Handle" o "IO::File". Una vez que tiene un filehandle abierto, puede llamar a métodos en él. Además, puede llamar a métodos en los filehandles "STDIN", "STDOUT" y "STDERR".

open my $fh, '>', 'path/to/file';
$fh->autoflush();
$fh->print('content');
STDOUT->autoflush();

Invocando Métodos de Clase

Debido a que Perl le permite usar barewords para nombres de paquetes y nombres de subrutinas, a veces interpreta incorrectamente el significado de un bareword. Por ejemplo, la construcción "Class->new()" puede interpretarse como "'Class'->new()" o "Class()->new()". En español, esa segunda interpretación se lee como "llamar a una subrutina llamada Class(), luego llamar a new() como un método sobre el valor de retorno de Class()". Si hay una subrutina llamada Class() en el espacio de nombres actual, Perl siempre interpretarará "Class->new()" como la segunda alternativa: una llamada a new() sobre el objeto devuelto por una llamada a Class().

Puede forzar a Perl a usar la primera interpretación (es decir, como una llamada a método en la clase llamada "Class") de dos maneras. Primero, puede agregar un "::" al nombre de la clase:

Class::->new()

Perl siempre interpretará esto como una llamada a método.

Alternativamente, puede citar el nombre de la clase:

'Class'->new()

Por supuesto, si el nombre de la clase está en un escalar, Perl hará lo correcto también:

my $class = 'Class';
$class->new();

Sintaxis de Objeto Indirecto

Fuera del caso del filehandle, se desaconseja el uso de esta sintaxis, ya que puede confundir al intérprete de Perl. Consulte a continuación para obtener más detalles.

Perl admite otra sintaxis de invocación de métodos llamada notación de "objeto indirecto". Esta sintaxis se llama "indirecta" porque el método precede al objeto sobre el que se invoca.

Esta sintaxis se puede usar con cualquier método de clase u objeto:

my $file = new File $path, $data;
save $file;

Recomendamos que evite esta sintaxis por varias razones.

Primero, puede ser confuso de leer. En el ejemplo anterior, no está claro si "save" es un método proporcionado por la clase "File" o simplemente una subrutina que espera un objeto de archivo como su primer argumento.

Cuando se usa con métodos de clase, el problema es aún peor. Dado que Perl permite que los nombres de subrutinas se escriban como barewords, Perl tiene que adivinar si el bareword después del método es un nombre de clase o un nombre de subrutina. En otras palabras, Perl puede resolver la sintaxis como "File->new( $path, $data )" *o* "new( File( $path, $data ) )".

Para analizar este código, Perl utiliza una heurística basada en los nombres de paquetes que ha visto, qué subrutinas existen en el paquete actual, qué barewords ha visto previamente y otra entrada. No hace falta decir que las heurísticas pueden producir resultados muy sorprendentes.

La documentación anterior (y algunos módulos CPAN) fomentaron esta sintaxis, particularmente para los constructores, por lo que es posible que aún la encuentre en uso. Sin embargo, le recomendamos que evite usarla en código nuevo.

Puede forzar a Perl a interpretar el bareword como un nombre de clase agregando "::", como vimos anteriormente:

my $file = new File:: $path, $data;

La sintaxis de objeto indirecto solo está disponible cuando la característica con nombre "indirect" está habilitada. Esto está habilitado por defecto, pero puede ser deshabilitado si se solicita. Esta característica está presente en paquetes de versiones de características anteriores, pero se eliminó del paquete ":5.36"; por lo tanto, una declaración de "use VERSION" de "v5.36" o superior también deshabilitará la característica.

use v5.36;
# la sintaxis de objeto indirecto ya no está disponible

"bless", "blessed", y "ref"

Como vimos anteriormente, un objeto es simplemente una estructura de datos que ha sido bendecida en una clase a través de la función "bless". La función "bless" puede tomar uno o dos argumentos:

my $object = bless {}, $class;
my $object = bless {};

En la primera forma, el hash anónimo está siendo bendecido en la clase en $class. En la segunda forma, el hash anónimo se bendice en el paquete actual.

La segunda forma se desaconseja enérgicamente, ya que rompe la capacidad de una subclase para reutilizar el constructor del padre, pero es posible que aún la encuentre en código existente.

Determining if a Scalar Refers to an Object

To know if a particular scalar refers to an object, you can use the "blessed" function exported by Scalar::Util, which is included with the Perl core.

use Scalar::Util 'blessed';
if ( defined blessed($thing) ) { ... }

If $thing refers to an object, then this function returns the name of the package the object has been blessed into. If $thing does not contain a reference to a blessed object, the "blessed" function returns "undef".

Note that blessed($thing) also returns false if $thing has been blessed into a class named "0". This is possible, but quite pathological. Don't create a class named "0" unless you know what you are doing.

Similarly, Perl's built-in "ref" function treats a reference to a blessed object specially. If you call ref($thing) and $thing holds a reference to an object, it will return the name of the class into which the object has been blessed.

If you simply want to check that a variable contains an object reference, we recommend using "defined blessed($object)", since "ref" returns true values for all references, not just objects.

The UNIVERSAL Class

All classes automatically inherit from the UNIVERSAL class, which is built into the Perl core. This class provides a number of methods, all of which can be called on either a class or an object. You can also choose to override some of these methods in your class. If you do so, we recommend that you follow the built-in semantics described below.

isa($class)
The "isa" method returns *true* if the object is a member of the class in $class, or a member of a subclass of $class.

If you override this method, it should never throw an exception.

DOES($role)
The "DOES" method returns *true* if its object claims to perform the role $role. By default, this is equivalent to "isa". This method is provided for use by object system extensions that implement roles, such as "Moose" and "Role::Tiny".

You can also override "DOES" directly in your own classes. If you override this method, it should never throw an exception.

can($method)
The "can" method checks to see if the class or object it was called on has a method named $method. This checks for the method in the class and all of its parents. If the method exists, then a reference to the subroutine is returned. If it does not, then "undef" is returned.

If your class responds to method calls via "AUTOLOAD", you may want to overload "can" to return a subroutine reference for methods that your "AUTOLOAD" method handles.

If you override this method, it should never throw an exception.

VERSION($need)
The "VERSION" method returns the version number of the class (package).

If the $need argument is provided, it will check that the current version (as defined by the $VERSION variable in the package) is greater than or equal to $need; it will die if this is not the case. This method is called automatically by the "VERSION" form of "use".

use Package 1.2 qw(some imported subs);
# implies:
Package->VERSION(1.2);

We recommend using this method to access another package's version, rather than looking directly at $Package::VERSION. The package you are looking at could have overridden the "VERSION" method.

We also recommend using this method to check whether a module has a sufficient version. The internal implementation uses the version module to ensure that different types of version numbers are compared correctly.

AUTOLOAD

If you call a method that doesn't exist in a class, Perl will throw an error. However, if that class or any of its parent classes defines an "AUTOLOAD" method, that "AUTOLOAD" method is called instead.

"AUTOLOAD" is called as a regular method, and the caller will not know the difference. Whatever value your "AUTOLOAD" method returns is returned to the caller.

The fully qualified method name that was called is available in the $AUTOLOAD package global for your class. Since this is a global, if you want to refer to it without a package name prefix under strict 'vars', you need to declare it.

# XXX - this is a terrible way to implement accessors, but it makes
# for a simple example.
our $AUTOLOAD;
sub AUTOLOAD {
    my $self = shift;
    # Remove qualifier from original method name...
    my $called =  $AUTOLOAD =~ s/.*:://r;
    # Is there an attribute of that name?
    die "No such attribute: $called"
        unless exists $self->{$called};
    # If so, return it...
    return $self->{$called};
}
sub DESTROY { } # see below

Without the "our $AUTOLOAD" declaration, this code will not compile under the strict pragma.

As the comment says, this is not a good way to implement accessors. It's slow and too clever by far. However, you may see this as a way to provide accessors in older Perl code. See perlootut for recommendations on OO coding in Perl.

If your class has an "AUTOLOAD" method, we strongly recommend that you also override "can" in your class. Your overridden "can" method should return a subroutine reference for any method that your "AUTOLOAD" responds to.

Destructors

When the last reference to an object goes away, the object is destroyed. If you only have one reference to an object stored in a lexical scalar, the object is destroyed when that scalar goes out of scope. If you store the object in a package global, that object may not go out of scope until the program exits.

If you want to do something when the object is destroyed, you can define a "DESTROY" method in your class. This method will always be called by Perl at the appropriate time, unless the method is empty.

This is called just like any other method, with the object as the first argument. It does not receive any additional arguments. However, the $_[0] variable will be read-only in the destructor, so you cannot assign a value to it.

If your "DESTROY" method throws an exception, this will not cause any control transfer beyond exiting the method. The exception will be reported to "STDERR" as a warning, marked "(in cleanup)", and Perl will continue with whatever it was doing before.

Because "DESTROY" methods can be called at any time, you should localize any global status variables that might be set by anything you do in your "DESTROY" method. If you are in doubt about a particular status variable, it doesn't hurt to localize it. There are five global status variables, and the safest way is to localize all five of them:

sub DESTROY {
    local($., $@, $!, $^E, $?);
    my $self = shift;
    ...;
}

If you define an "AUTOLOAD" in your class, then Perl will call your "AUTOLOAD" to handle the "DESTROY" method. You can prevent this by defining an empty "DESTROY", like we did in the autoloading example. You can also check the value of $AUTOLOAD and return without doing anything when called to handle "DESTROY".

Global Destruction

The order in which objects are destroyed during global destruction before the program exits is unpredictable. This means that any objects contained by your object may already have been destroyed. You should check that a contained object is defined before calling a method on it:

sub DESTROY {
    my $self = shift;
    $self->{handle}->close() if $self->{handle};
}

You can use the "${^GLOBAL_PHASE}" variable to detect if you are currently in the global destruction phase:

sub DESTROY {
    my $self = shift;
    return if ${^GLOBAL_PHASE} eq 'DESTRUCT';
    $self->{handle}->close();
}

Note that this variable was added in Perl 5.14.0. If you want to detect the global destruction phase on older versions of Perl, you can use the "Devel::GlobalDestruction" module on CPAN.

If your "DESTROY" method issues a warning during global destruction, the Perl interpreter will append the string " during global destruction" to the warning.

During global destruction, Perl will always garbage collect objects before unblessed references. See "PERL_DESTRUCT_LEVEL" in perlhacktips for more information about global destruction.

Perl Object Oriented Programming

NAME

perlobj - Perl Object Oriented Programming

DESCRIPTION

This document describes object-oriented programming in Perl.

This document describes three ways that one might approach object-oriented programming in Perl. These are:

  • Referent-based objects (the most common approach)

  • Inside-out objects

  • Pseudo-hashes (now deprecated)

Referent-based objects

The most common approach to object-oriented programming in Perl is to use referent-based objects. In this approach, an object is simply a reference to some data structure (typically a hash reference), which is associated with a specific class. The association is made using the bless builtin function, which takes a reference and a class name, and returns the reference associated with that class.

There are two common ways to use referent-based objects:

A hash reference is used as the object.
This is the most common approach. The hash reference is used to store the object's attributes. Methods are then called using the arrow operator.
package Person;
use v5.36;
sub new {
    my $class = shift;
    my %self = @_;
    return bless { %self }, $class;
}
sub name {
    my $self = shift;
    return $self->{name};
}
my $person = Person->new(name => 'Alice');
print $person->name(); # prints Alice
A scalar reference is used as the object.
This approach is less common, but is still sometimes seen. The scalar reference is used to store a single value, which can be a more complex data structure such as a tied array or hash. Methods are then called using the arrow operator.

It is possible to bless any type of data structure or referent, including scalars, globs, and subroutines. You may see this sort of thing when looking at code in the wild.

Here's an example of a module as a blessed scalar:

package Time;
use v5.36;
sub new {
    my $class = shift;
    my $time = time;
    return bless \$time, $class;
}
sub epoch {
    my $self = shift;
    return $$self;
}
my $time = Time->new();
print $time->epoch();

Inside-Out objects

In the past, the Perl community experimented with a technique called "inside-out objects". An inside-out object stores its data outside of the object's reference, indexed on a unique property of the object, such as its memory address, rather than in the object itself. This has the advantage of enforcing the encapsulation of object attributes, since their data is not stored in the object itself.

This technique was popular for a while (and was recommended in Damian Conway's Perl Best Practices), but never achieved universal adoption. The Object::InsideOut module on CPAN provides a comprehensive implementation of this technique, and you may see it or other inside-out modules in the wild.

Here is a simple example of the technique, using the Hash::Util::FieldHash core module. This module was added to the core to support inside-out object implementations.

package Time;
use v5.36;
use Hash::Util::FieldHash 'fieldhash';
fieldhash my %time_for;
sub new {
    my $class = shift;
    my $self = bless \( my $object ), $class;
    $time_for{$self} = time;
    return $self;
}
sub epoch {
    my $self = shift;
    return $time_for{$self};
}
my $time = Time->new;
print $time->epoch;

Pseudo-hashes

The pseudo-hash feature was an experimental feature introduced in earlier versions of Perl and removed in 5.10.0. A pseudo-hash is an array reference which can be accessed using named keys like a hash. You may run into some code in the wild which uses it. See the fields pragma for more information.
