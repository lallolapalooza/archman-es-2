PERLHACK(1perl) Perl Programmers Reference Guide PERLHACK(1perl)

NOMBRE

perlhack - Cómo desarrollar Perl

DESCRIPCIÓN

Este documento explica cómo funciona el desarrollo de Perl. Incluye detalles sobre la lista de correo de Perl 5 Porters, el repositorio de Perl, el sistema de seguimiento de errores de Perl, las directrices para los parches y comentarios sobre la filosofía de desarrollo de Perl.

GUÍA SUPER RÁPIDA DE PARCHES

Si solo quieres enviar un parche pequeño, como una corrección de documentación (pod), una prueba para un error, correcciones de comentarios, etc., ¡es fácil! Aquí te explicamos cómo:

  • Obtén el repositorio fuente

    El código fuente de Perl está en un repositorio Git. Puedes clonar el repositorio con el siguiente comando:

    % git clone https://github.com/Perl/perl5.git perl
  • Asegúrate de seguir los últimos consejos

    En caso de que los consejos de esta guía se hayan actualizado recientemente, lee la última versión directamente desde el código fuente de Perl:

    % perldoc pod/perlhack.pod
  • Crea una rama para tu cambio

    Crea una rama basada en `blead` para confirmar tu cambio, que luego se usará para enviarlo al sistema de seguimiento de incidencias de Perl.

    % git checkout -b mi_cambio
  • Realiza tu cambio

    Programa, programa, programa. Ten en cuenta que Perl se ejecuta en muchas plataformas diferentes, con sistemas operativos distintos que tienen capacidades diferentes, organizaciones de sistemas de archivos diferentes e incluso conjuntos de caracteres diferentes. `perlhacktips` ofrece consejos sobre esto.

  • Prueba tu cambio

    Puedes ejecutar todas las pruebas con los siguientes comandos:

    % ./Configure -des -Dusedevel
% make test

    Sigue programando hasta que las pruebas pasen.

  • Confirma tu cambio

    Confirmar tu trabajo guardará el cambio *en tu sistema local*:

    % git commit -a -m 'Mensaje de confirmación va aquí'

    Asegúrate de que el mensaje de confirmación describa tu cambio en una sola frase. Por ejemplo, "Se corrigieron errores ortográficos en perlhack.pod".

  • Envía tu cambio al sistema de seguimiento de incidencias de Perl

    El siguiente paso es enviar tu parche al sistema de seguimiento de incidencias del núcleo de Perl.

    Crea una bifurcación (fork) de GitHub del repositorio `perl5` y añádela como un control remoto (remote), si aún no lo has hecho, como se describe en la documentación de GitHub en https://help.github.com/en/articles/working-with-forks.

    % git remote add fork git@github.com:TuUsuario/perl5.git

    Para más información, consulta "Conectarse a GitHub con SSH" https://docs.github.com/es/free-pro-team@latest/github/authenticating-to-github/connecting-to-github-with-ssh.

    Si prefieres usar una URL HTTPS para tu `git push`, consulta "Clonar con URL HTTPS" https://docs.github.com/es/free-pro-team@latest/github/using-git/which-remote-url-should-i-use#cloning-with-https-urls.

    % git remote add fork https://github.com/TuUsuario/perl5.git

    Luego, sube tu nueva rama a tu bifurcación.

    % git push -u fork mi_cambio

    Finalmente, crea una Solicitud de Extracción (Pull Request) en GitHub desde tu rama hacia `blead`, como se describe en la documentación de GitHub en https://help.github.com/en/articles/creating-a-pull-request-from-a-fork.

  • Gracias

    Los desarrolladores aprecian el tiempo que dedicaste a ayudar a mejorar Perl. ¡Gracias!

  • Reconocimiento

    Todos los contribuyentes son reconocidos (por nombre y dirección de correo electrónico) en el archivo `AUTHORS`, que forma parte de la distribución de Perl, así como en el historial de confirmaciones de Git.

    Si no deseas ser incluido en el archivo `AUTHORS`, simplemente háznoslo saber. De lo contrario, tomaremos tu envío de un parche como permiso para reconocerte en el archivo `AUTHORS`.

  • La próxima vez

    La próxima vez que desees hacer un parche, necesitas empezar desde la última versión de Perl en un estado prístino. Verifica que no tengas cambios locales o archivos añadidos en tu copia de Perl que desees conservar, luego ejecuta estos comandos:

    % git checkout blead
% git pull
% git reset --hard origin/blead
% git clean -dxf

REPORTE DE ERRORES

Si quieres reportar un error en Perl, o buscar errores y parches de Perl existentes, usa el sistema de seguimiento de incidencias de GitHub en https://github.com/perl/perl5/issues.

Por favor, revisa el archivo de la lista `perl5-porters` (ver abajo) y/o el sistema de seguimiento de errores antes de enviar un reporte de error. A menudo, encontrarás que el error ya ha sido reportado.

Puedes iniciar sesión en el sistema de seguimiento de incidencias y comentar sobre los reportes de errores existentes. Si tienes información adicional sobre un error existente, por favor añádela. Esto ayudará a los desarrolladores a corregir el error.

PERL 5 PORTERS

La lista de correo de los desarrolladores de Perl 5 (p5p) es donde se mantiene y desarrolla la distribución estándar de Perl. Las personas que mantienen Perl también se conocen como los "Perl 5 Porters", "p5p" o simplemente los "porters".

Un archivo consultable de la lista está disponible en https://markmail.org/search/?q=perl5-porters. También hay un archivo en https://archive.develooper.com/perl5-porters@perl.org/.

Lista de correo perl-changes

La lista de correo `perl5-changes` recibe una copia de cada parche que se envía a las ramas de mantenimiento y desarrollo del repositorio de Perl. Consulta https://lists.perl.org/list/perl5-changes.html para información sobre suscripción y archivo.

#p5p en IRC

Muchos desarrolladores también participan activamente en el canal <irc://irc.perl.org/#p5p>. No dudes en unirte al canal y hacer preguntas sobre el desarrollo del núcleo de Perl.

OBTENIENDO EL CÓDIGO FUENTE DE PERL

Todo el código fuente de Perl se mantiene centralmente en un repositorio Git en github.com. El repositorio contiene muchas revisiones de Perl desde la versión 1 en adelante y todas las revisiones de Perforce, el sistema de control de versiones anterior.

Para obtener muchos más detalles sobre el uso de Git con el repositorio de Perl, consulta `perlgit`.

Acceso de lectura vía Git

Necesitarás una copia de Git en tu computadora. Puedes obtener una copia del repositorio usando el protocolo git:

% git clone git@github.com:Perl/perl5.git perl

Esto clona el repositorio y crea una copia local en el directorio perl.

Si no puedes usar el protocolo git por razones de firewall, también puedes clonar vía http:

% git clone https://github.com/Perl/perl5.git perl

Acceso de lectura vía web

Puedes acceder al repositorio a través de la web. Esto te permite navegar por el árbol, ver commits recientes, suscribirte a notificaciones del repositorio, buscar commits específicos y más. Puedes acceder a él en https://github.com/Perl/perl5.

Acceso de escritura vía git

Si tienes permiso para escribir (commit bit), consulta `perlgit` para más detalles sobre el uso de Git.

If you are submitting a patch for a bug, please make sure to reference the bug number in your pull request description.

Envío de parches

Si tienes un pequeño parche que enviar, por favor envíalo a través del flujo de trabajo de Solicitudes de Extracción de GitHub. También puedes enviar parches a la lista p5p.

Los parches se revisan y discuten en GitHub o en la lista p5p. Los parches simples y no controvertidos generalmente se aplicarán sin ninguna discusión. Cuando el parche se aplique, el ticket se actualizará y recibirás un correo electrónico.

En otros casos, el parche requerirá más trabajo o discusión. Se te anima a participar en la discusión y defender tu parche. A veces, tu parche puede perderse en el proceso. Es apropiado enviar un correo electrónico de recordatorio a p5p si no se ha tomado ninguna medida en un mes. Por favor, recuerda que los desarrolladores de Perl 5 son voluntarios, y sé educado.

Los cambios siempre se aplican directamente a la rama de desarrollo principal, llamada "blead". Algunos parches pueden ser retroportados a una rama de mantenimiento. Si crees que tu parche es apropiado para la rama de mantenimiento (ver "RAMAS DE MANTENIMIENTO" en perlpolicy), por favor explica por qué al enviarlo.

Obtener la aceptación de tu parche

Si estás enviando un parche de código, hay varias cosas que puedes hacer para ayudar a los Porteros de Perl 5 a aceptar tu parche.

Estilo del parche

Utilizando el flujo de trabajo de Solicitudes de Extracción de GitHub, tu parche estará automáticamente disponible en un formato adecuado. Si deseas enviar un parche a la lista p5p para su revisión, asegúrate de crearlo apropiadamente.

Si utilizaste git para descargar el código fuente de Perl, entonces usar "git format-patch" producirá un parche en un estilo adecuado para Perl. El comando "format-patch" produce un archivo de parche por cada commit que hayas realizado. Si prefieres enviar un solo parche para todos los commits, puedes usar "git diff".

% git checkout blead
% git pull
% git diff blead mi-rama-nombre

Esto produce un parche basado en la diferencia entre blead y tu rama actual. Es importante asegurarse de que blead esté actualizado antes de producir el diff, por eso llamamos a "git pull" primero.

Recomendamos encarecidamente que uses git si es posible. Te facilitará la vida, y la nuestra también.

Sin embargo, si no usas git, aún puedes producir un parche adecuado. Necesitarás una copia prístina del código fuente de Perl para comparar. Los porteros prefieren diffs unificados. Usando GNU "diff", puedes producir un diff como este:

% diff -Npurd perl.pristino perl.mio

Asegúrate de ejecutar "make realclean" en tu copia de Perl para eliminar cualquier artefacto de compilación, o podrías obtener un resultado confuso.

Mensaje de commit

Al crear cada parche que pretendes enviar al núcleo de Perl, es importante escribir un buen mensaje de commit. Esto es especialmente importante si tu envío consistirá en una serie de commits.

La primera línea del mensaje de commit debe ser una descripción corta sin punto final. No debe exceder la línea de asunto de un correo electrónico, siendo 50 caracteres una buena regla general.

Muchas herramientas de Git (Gitweb, GitHub, git log --pretty=oneline, ...) solo mostrarán la primera línea (cortada a 50 caracteres) al presentar resúmenes de commits.

El mensaje de commit debe incluir una descripción del problema que el parche corrige o la nueva funcionalidad que el parche añade.

Como regla general, tu mensaje de commit debe ayudar a un programador que conoce el núcleo de Perl a entender rápidamente qué intentabas hacer, cómo lo intentabas hacer y por qué el cambio es importante para Perl.

  • Por qué

    Tu mensaje de commit debe describir por qué el cambio que estás haciendo es importante. Cuando alguien vea tu cambio en seis meses o seis años, tu intención debe ser clara.

    Si estás deprecando una característica con la intención de simplificar posteriormente otra parte del código, dilo. Si estás corrigiendo un problema de rendimiento o añadiendo una nueva característica para soportar otra parte del núcleo, menciónalo.

  • Qué

    Tu mensaje de commit debe describir qué parte del núcleo de Perl estás cambiando y qué esperas que haga tu parche.

  • Cómo

    Aunque no es necesario para cambios en la documentación, nuevas pruebas o parches triviales, a menudo vale la pena explicar cómo funciona tu cambio. Incluso si hoy te resulta claro, puede que no lo sea para un portero el próximo mes o el próximo año.

Un mensaje de commit no pretende reemplazar los comentarios en tu código. Los mensajes de commit deben describir el cambio que hiciste, mientras que los comentarios del código deben describir el estado actual del código.

Si acabas de implementar una nueva característica, completa con documentación, pruebas y código bien comentado, un breve mensaje de commit a menudo será suficiente. Si, sin embargo, solo has cambiado un solo carácter en lo profundo del analizador o el lexer, es posible que necesites escribir una novela corta para asegurar que los futuros lectores entiendan lo que hiciste y por qué lo hiciste.

Comentarios, Comentarios, Comentarios

Asegúrate de comentar adecuadamente tu código. Si bien comentar cada línea es innecesario, cualquier cosa que aproveche los efectos secundarios de los operadores, que cree cambios que se sentirán fuera de la función que se está parcheando, o que otros puedan encontrar confuso, debe documentarse. Si vas a errar, es mejor errar por añadir demasiados comentarios que por muy pocos.

Los mejores comentarios explican *por qué* el código hace lo que hace, no *qué* hace.

Estilo

En general, sigue el estilo particular del código que estás parcheando.

En particular, sigue estas directrices generales para parchear las fuentes de Perl:

  • Indentaciones de 4 espacios para código, indentaciones de 2 espacios para CPP anidado "#define"s, con tabulaciones de 8 espacios.
  • Usa espacios para la indentación, no caracteres de tabulación.

    La base de código es una mezcla de tabulaciones y espacios para la indentación, y nos estamos moviendo solo a espacios. Convertir las líneas que estás parcheando de tabulaciones de 8 espacios a espacios ayudará a esta migración.

  • Intenta no exceder las 79 columnas

    En general, apuntamos a líneas de 80 columnas. Cuando ceñirse a 80 columnas conduciría a un código tortuoso o a un retrabajo, está bien extenderse. Intenta mantener tu exceso más allá de 80 al mínimo.

  • Prototipos de C ANSI
  • Elses sin agrupar y estilo "K&R" para indentar constructos de control.
  • No comentarios estilo C++ (//).
  • Marca lugares que necesiten ser revisados con XXX (¡y revisa a menudo!).
  • La llave de apertura se alinea con "if" cuando la condición abarca múltiples líneas; de lo contrario, debe estar al final de la línea.
  • En definiciones de función, el nombre comienza en la columna 0 (el tipo de valor de retorno está en la línea anterior).
  • Espacio simple después de palabras clave seguidas de paréntesis, sin espacio entre el nombre de la función y el paréntesis siguiente.
  • Evita asignaciones en condicionales, pero si son inevitables, usa paréntesis extra, por ejemplo, "if (a && (b = c)) ...".
  • "return foo;" en lugar de "return(foo);".
  • "if (!foo) ..." en lugar de "if (foo == FALSE) ..." etc.
  • No declares variables usando "register". Puede ser contraproducente con compiladores modernos y está obsoleto en C++, con el cual el código fuente de Perl se compila regularmente.
  • Las funciones en línea que están en cabeceras accesibles para código XS deben poder compilarse sin advertencias con flags de compilación adicionales comúnmente utilizados, como el "-Wswitch-default" de gcc, que advierte siempre que una sentencia switch no tiene un caso "default". El uso de estos flags adicionales es para capturar problemas potenciales en código C legal, y a menudo es utilizado por agregadores de Perl, como los distribuidores de Linux.

Suite de pruebas

Si tu parche cambia código (en lugar de solo cambiar documentación), también deberías incluir uno o más casos de prueba que ilustren el error que estás corrigiendo o validen la nueva funcionalidad que estás añadiendo. En general, deberías actualizar un archivo de prueba existente en lugar de crear uno nuevo.

Tus adiciones a la suite de pruebas generalmente deben seguir estas directrices (cortesía de Gurusamy Sarathy <gsar@activestate.com>):

  • Conoce lo que estás probando. Lee la documentación y el código fuente.
  • Tiende a fallar, no a tener éxito.
  • Interpreta los resultados estrictamente.
  • Usa características no relacionadas (esto eliminará interacciones extrañas).
  • Usa modismos no estándar (de lo contrario, no estás probando TIMTOWTDI).
  • Evita usar números de prueba codificados siempre que sea posible (el EXPECTED/GOT que se encuentra en t/op/tie.t es mucho más mantenible y da mejores informes de fallos).
  • Proporciona mensajes de error significativos cuando una prueba falla.
  • Evita usar qx// y system() a menos que estés probándolos. Si los usas, asegúrate de cubrir *todas* las plataformas de perl.
  • Elimina cualquier archivo temporal que crees.
  • Promueve advertencias imprevistas a errores con $SIG{__WARN__}.
  • Asegúrate de usar las bibliotecas y módulos incluidos con la versión que se está probando, no los que ya estaban instalados.
  • Agrega comentarios al código explicando lo que estás probando.
  • Haz que la actualización de la cadena '1..42' sea innecesaria. O asegúrate de actualizarla.
  • Prueba *todos* los comportamientos de un operador, biblioteca o función dada.

    Prueba todos los argumentos opcionales.

    Prueba los valores de retorno en varios contextos (booleano, escalar, lista, lvalue).

    Usa variables globales y léxicas.

    No olvides los casos excepcionales y patológicos.

Parchear un módulo principal

Esto funciona igual que parchear cualquier otra cosa, con una consideración adicional.

Los módulos en el directorio cpan/ del árbol de fuentes se mantienen fuera del núcleo de Perl. Cuando el autor actualiza el módulo, las actualizaciones simplemente se copian al núcleo. Consulta la documentación de ese módulo o su listado en https://metacpan.org/ para obtener más información sobre cómo informar de errores y enviar parches.

PORTING

Perl is a living language and the core is constantly being updated. The process of porting Perl to a new platform or keeping the Perl core updated on an existing platform is a complex one. This document outlines the process and responsibilities involved.

Core Modules

A module is considered part of the core if it is distributed with Perl itself. This is usually indicated by the module residing in the lib/ or ext/ directories of the Perl source tree. Modules in dist/ are also considered core modules, but are maintained externally.

If you modify a core module, you should mark it as "CUSTOMIZED" in the Porting/Maintainers.pl file to flag that a local modification has been made. See Porting/Maintainers.pl for more details.

In contrast, modules in the dist/ directory are maintained in the core.

Updating perldelta

For changes significant enough to warrant a pod/perldelta.pod entry, the porters will greatly appreciate it if you submit a delta entry along with your actual change. Significant changes include, but are not limited to:

  • Adding, deprecating, or removing core features
  • Adding, deprecating, removing, or upgrading core or dual-life modules
  • Adding new core tests
  • Fixing security issues and user-visible bugs in the core
  • Changes that might break existing code, either on the perl or C level
  • Significant performance improvements
  • Adding, removing, or significantly changing documentation in the pod/ directory
  • Important platform-specific changes

Please make sure you add the perldelta entry to the right section within pod/perldelta.pod. More information on how to write good perldelta entries is available in the "Style" section of Porting/how_to_write_a_perldelta.pod.

What makes for a good patch?

New features and extensions to the language can be contentious. There is no specific set of criteria which determine what features get added, but here are some questions to consider when developing a patch:

Does the concept match the general goals of Perl?

Our goals include, but are not limited to:

1.
Keep it fast, simple, and useful.
2.
Keep features/concepts as orthogonal as possible.
3.
No arbitrary limits (platforms, data sizes, cultures).
4.
Keep it open and exciting to use/patch/advocate Perl everywhere.
5.
Either assimilate new technologies, or build bridges to them.

Where is the implementation?

All the talk in the world is useless without an implementation. In almost every case, the person or people who argue for a new feature will be expected to be the ones who implement it. Porters capable of coding new features have their own agendas, and are not available to implement your (possibly good) idea.

Backwards compatibility

It's a cardinal sin to break existing Perl programs. New warnings can be contentious--some say that a program that emits warnings is not broken, while others say it is. Adding keywords has the potential to break programs, changing the meaning of existing token sequences or functions might break programs.

The Perl 5 core includes mechanisms to help porters make backwards incompatible changes more compatible such as the feature and deprecate modules. Please use them when appropriate.

Could it be a module instead?

Perl 5 has extension mechanisms, modules and XS, specifically to avoid the need to keep changing the Perl interpreter. You can write modules that export functions, you can give those functions prototypes so they can be called like built-in functions, you can even write XS code to mess with the runtime data structures of the Perl interpreter if you want to implement really complicated things.

Whenever possible, new features should be prototyped in a CPAN module before they will be considered for the core.

Is the feature generic enough?

Is this something that only the submitter wants added to the language, or is it broadly useful? Sometimes, instead of adding a feature with a tight focus, the porters might decide to wait until someone implements the more generalized feature.

Does it potentially introduce new bugs?

Radical rewrites of large chunks of the Perl interpreter have the potential to introduce new bugs.

How big is it?

The smaller and more localized the change, the better. Similarly, a series of small patches is greatly preferred over a single large patch.

Does it preclude other desirable features?

A patch is likely to be rejected if it closes off future avenues of development. For instance, a patch that placed a true and final interpretation on prototypes is likely to be rejected because there are still options for the future of prototypes that haven't been addressed.

Is the implementation robust?

Good patches (tight code, complete, correct) stand more chance of going in. Sloppy or incorrect patches might be placed on the back burner until fixes can be made, or they might be discarded altogether without further notice.

Is the implementation generic enough to be portable?

The worst patches make use of system-specific features. It's highly unlikely that non-portable additions to the Perl language will be accepted.

Is the implementation tested?

Patches which change behaviour (fixing bugs or introducing new features) must include regression tests to verify that everything works as expected.

Without tests provided by the original author, how can anyone else changing perl in the future be sure that they haven't unwittingly broken the behaviour the patch implements? And without tests, how can the patch's author be confident that his/her hard work put into the patch won't be accidentally thrown away by someone in the future?

Is there enough documentation?

Patches without documentation are probably ill-thought out or incomplete. No features can be added or changed without documentation, so submitting a patch for the appropriate pod docs as well as the source code is important.

Is there another way to do it?

Larry said "Although the Perl Slogan is There's More Than One Way to Do It, I hesitate to make 10 ways to do something". This is a tricky heuristic to navigate, though--one man's essential addition is another man's pointless cruft.

Does it create too much work?

Work for the committers, work for Perl programmers, work for module authors, ... Perl is supposed to be easy.

Patches speak louder than words

Working code is always preferred to pie-in-the-sky ideas. A patch to add a feature stands a much higher chance of making it to the language than does a random feature request, no matter how fervently argued the request might be. This ties into "Will it be useful?", as the fact that someone took the time to make the patch demonstrates a strong desire for the feature.

TESTING

The core uses the same testing style as the rest of Perl, a simple "ok/not ok" run through Test::Harness, but there are a few special considerations.

There are three ways to write a test in the core: Test::More, t/test.pl and ad hoc "print $test ? "ok 42\n" : "not ok 42\n"". The decision of which to use depends on what part of the test suite you're working on. This is a measure to prevent a high-level failure (such as Config.pm breaking) from causing basic functionality tests to fail.

The t/test.pl library provides some of the features of Test::More, but avoids loading most modules and uses as few core features as possible.

If you write your own test, use the Test Anything Protocol https://testanything.org.

  • t/base, t/comp and t/opbasic

    Since we don't know if "require" works, or even subroutines, use ad hoc tests for these three. Step carefully to avoid using the feature being tested. Tests in t/opbasic, for instance, have been placed there rather than in t/op because they test functionality which t/test.pl presumes has already been demonstrated to work.

  • All other subdirectories of t/

    Now that basic require() and subroutines are tested, you can use the t/test.pl library.

    You can also use certain libraries like Config conditionally, but be sure to skip the test gracefully if it's not there.

  • Test files not found under t/

    This category includes .t files underneath directories such as dist, ext and lib. Since the core of Perl has now been tested, Test::More can and now should be used. You can also use the full suite of core modules in the tests. (As noted in "Patching a core module" above, changes to .t files found under cpan/ should be submitted to the upstream maintainers of those modules.)

When you say "make test", Perl uses the t/TEST program to run the test suite (except under Win32 where it uses t/harness instead). All tests are run from the t/ directory, not the directory which contains the test. This causes some problems with the tests in lib/, so here's some opportunity for some patching.

You must be triply conscious of cross-platform concerns. This usually boils down to using File::Spec, avoiding things like fork() and system() unless absolutely necessary, and not assuming that a given character has a particular ordinal value (code point) or that its UTF-8 representation is composed of particular bytes.

There are several functions available to specify characters and code points portably in tests. The always-preloaded functions utf8::unicode_to_native() and its inverse utf8::native_to_unicode() take code points and translate appropriately. The file t/charset_tools.pl has several functions that can be useful. It has versions of the previous two functions that take strings as inputs -- not single numeric code points: uni_to_native() and native_to_uni(). If you must look at the individual bytes comprising a UTF-8 encoded string, byte_utf8a_to_utf8n() takes as input a string of those bytes encoded for an ASCII platform, and returns the equivalent string in the native platform. For example, byte_utf8a_to_utf8n("\xC2\xA0") returns the byte sequence on the current platform that form the UTF-8 for "U+00A0", since "\xC2\xA0" son los bytes UTF-8 en una plataforma ASCII para ese punto de código. Esta función devuelve "\xC2\xA0" en una plataforma ASCII y "\x80\x41" en una EBCDIC 1047.

Pero lo más fácil es, si el carácter se puede especificar como un literal, como "A" o "%", usarlo; si no se puede especificar así, puedes usar "\N{}", si los efectos secundarios no son problemáticos. Simplemente especifica todos tus caracteres en hexadecimal, usando "\N{U+ZZ}" en lugar de "\xZZ". "\N{}" es el nombre Unicode, y por lo tanto siempre te da el carácter Unicode. "\N{U+41}" es el carácter cuyo punto de código Unicode es 0x41, por lo tanto es 'A' en todas las plataformas. Los efectos secundarios son:

  • Estos seleccionan reglas Unicode. Eso significa que en cadenas entre comillas dobles, la cadena siempre se convierte a UTF-8 para forzar una interpretación Unicode (puedes utf8::downgrade() después para convertir de nuevo a no UTF-8, si es posible). En patrones de expresiones regulares, la conversión no se realiza, pero si el modificador de conjunto de caracteres fuera "/d", se cambia a "/u".
  • Si usas la forma "\N{nombre del carácter}", el módulo charnames se carga automáticamente. Esto puede no ser adecuado para el nivel de prueba que estás realizando.

Si estás probando locales (ver perllocale), hay funciones auxiliares en t/loc_tools.pl para que puedas ver qué locales existen en la plataforma actual.

Objetivos especiales de "make test"

Hay varios objetivos especiales de `make` que se pueden usar para probar Perl de forma ligeramente diferente al objetivo estándar "test". No se espera que todos ellos tengan una tasa de éxito del 100%. Muchos de ellos tienen varios alias, y muchos de ellos no están disponibles en ciertos sistemas operativos.

  • test_porting

    Ejecuta algunas pruebas de cordura básicas en el árbol de fuentes y ayuda a detectar errores básicos antes de enviar un parche.

  • minitest

    Ejecuta miniperl en las pruebas t/base, t/comp, t/cmd, t/run, t/io, t/op, t/uni y t/mro.

    miniperl es un perl minimalista construido para arrancar la compilación de extensiones, utilidades, documentación, etc. No admite carga dinámica y, dependiendo del punto del proceso de compilación, solo tendrá acceso a un conjunto limitado de módulos principales. miniperl no está pensado para el uso diario.

  • test.valgrind check.valgrind

    (Solo en Linux) Ejecuta todas las pruebas usando la herramienta de detección de fugas de memoria y acceso a memoria incorrecto "valgrind". Los archivos de registro se llamarán testname.valgrind.

  • test_harness

    Ejecuta la suite de pruebas con el programa controlador t/harness, en lugar de t/TEST. t/harness es más sofisticado y utiliza el módulo Test::Harness, por lo que usar este objetivo de prueba supone que perl funciona en su mayor parte. La principal ventaja para nuestros propósitos es que imprime un resumen detallado de las pruebas fallidas al final. Además, a diferencia de t/TEST, no redirige stderr a stdout.

    Tenga en cuenta que en Win32 t/harness siempre se usa en lugar de t/TEST, por lo que no hay un objetivo especial "test_harness".

    En el proceso de compilación de Unix, puede usar los parámetros TEST_ARGS y TEST_FILES para pasar argumentos al `harness` subyacente. Esto significa que, por ejemplo, podría hacer

    make test_harness TEST_ARGS="-v -re pat"

    que haría, y luego ejecutar el `harness` de prueba en modo verboso sobre archivos que contengan "pat". O podría hacer

    make test_harness TEST_ARGS="-torture" TEST_FILES="op/*.t"

    y ejecutar pruebas de tortura en archivos que coincidan con el patrón glob "op/*.t".

    En Win32, en el objetivo "test", puede usar las variables de entorno TEST_SWITCHES y TEST_FILES para controlar el comportamiento de t/harness. Esto significa que puede decir

    nmake test TEST_FILES="op/*.t"
nmake test TEST_SWITCHES="-torture" TEST_FILES="op/*.t"

    Tenga en cuenta que para compatibilidad con el proceso de compilación de Unix, TEST_ARGS también se puede usar en lugar del argumento tradicional TEST_SWITCHES.

  • test-notty test_notty

    Establece PERL_SKIP_TTY_TEST a true antes de ejecutar la prueba normal.

Pruebas paralelas

La distribución principal ahora puede ejecutar sus pruebas de regresión en paralelo en plataformas tipo Unix y Windows. En Unix, en lugar de ejecutar "make test", establezca "TEST_JOBS" en su entorno al número de pruebas a ejecutar en paralelo, y ejecute "make test_harness". En un shell tipo Bourne, esto se puede hacer así:

TEST_JOBS=3 make test_harness  # Ejecuta 3 pruebas en paralelo

Se utiliza una variable de entorno, en lugar de `make` paralelo en sí, porque TAP::Harness necesita poder programar scripts de prueba individuales no conflictivos, y no hay una interfaz estándar para las utilidades de "make" para interactuar con sus planificadores de tareas.

Las pruebas se ejecutan normalmente en un orden lógico, con las pruebas de cordura primero, luego las pruebas principales de la funcionalidad central de Perl, luego las pruebas para los módulos no principales. En sistemas con muchos núcleos, esto puede no utilizar el hardware de manera tan efectiva como sea posible. Al especificar también

TEST_JOBS=19 PERL_TEST_HARNESS_ASAP=1 make -j19 test_harness

señalas que deseas que las pruebas terminen en el tiempo de reloj lo más corto posible. Después de que las pruebas de cordura se completen, esto hace que las restantes se empaqueten en los núcleos disponibles lo más ajustadamente posible. Esto tiene su mayor efecto en sistemas más lentos con muchos núcleos. El rendimiento se aceleró en un 20% en un sistema obsoleto de 24 núcleos; menos en sistemas más recientes y más rápidos con menos núcleos.

Tenga en cuenta que el comando anterior agregó un parámetro "-j" a `make`, para provocar la compilación en paralelo. Esto puede o no funcionar en su plataforma.

Normalmente, los datos sobre cuánto tardan las pruebas se almacenan en t/test_state, sin embargo, puede cambiar esto para usar un nombre de archivo diferente estableciendo la variable de entorno "PERL_TEST_STATE_FILE" a algo diferente, o a un valor falso (0 o la cadena vacía) para deshabilitar el uso del mecanismo de estado por completo. No hay protecciones contra el cambio del formato del archivo de estado con el tiempo, por lo que si tiene algún problema relacionado con este archivo, depende de usted eliminar el archivo manualmente y luego dejar que el `harness` lo recree, aunque el formato del archivo no cambia con frecuencia, por lo que esto no debería ser necesario con mucha frecuencia.

Ejecutando pruebas manualmente

Puedes ejecutar parte de la suite de pruebas manualmente usando uno de los siguientes comandos desde el directorio t/:

./perl -I../lib TEST list-of-.t-files

o

./perl -I../lib harness list-of-.t-files

(Si no especificas scripts de prueba, se ejecutará toda la suite de pruebas.)

Usando t/harness para pruebas

Si usas "harness" para pruebas, tienes varias opciones de línea de comandos disponibles. Los argumentos son los siguientes, y están en el orden en que deben aparecer si se usan juntos.

harness -v -torture -re=pattern LISTA DE ARCHIVOS A PROBAR
harness -v -torture -re LISTA DE PATRONES A COINCIDIR

Si se omite "LISTA DE ARCHIVOS A PROBAR", la lista de archivos se obtiene del manifiesto. La lista de archivos puede incluir comodines del shell que se expandirán.

  • -v

    Ejecuta las pruebas en modo verboso para que puedas ver qué pruebas se ejecutaron y la salida de depuración.

  • -torture

    Ejecuta las pruebas de tortura además del conjunto normal.

  • -re=PATTERN

    Filtra la lista de archivos para que todos los archivos de prueba que se ejecuten coincidan con PATTERN. Tenga en cuenta que esta forma es distinta de la forma -re LISTA DE PATRONES a continuación en que permite que se proporcione la lista de archivos.

  • -re LISTA DE PATRONES

    Filtra la lista de archivos para que todos los archivos de prueba que se ejecuten coincidan con /(LISTA|DE|PATRONES)/. Tenga en cuenta que con esta forma los patrones se unen por '|' y no puede proporcionar una lista de archivos, en su lugar, los archivos de prueba se obtienen del MANIFIESTO.

Puedes ejecutar una prueba individual con un comando similar a

./perl -I../lib path/to/foo.t

excepto que los `harness` configuran algunas variables de entorno que pueden afectar la ejecución de la prueba:

  • PERL_CORE=1

    indica que estamos ejecutando esta prueba como parte de la suite de pruebas principal de perl. Esto es útil para módulos que tienen una doble vida en CPAN.

  • PERL_DESTRUCT_LEVEL=2

    se establece en 2 si no está ya establecido (ver "PERL_DESTRUCT_LEVEL" en perlhacktips).

  • PERL

    (usado solo por t/TEST) si está establecido, anula la ruta al ejecutable de perl que debe usarse para ejecutar las pruebas (el valor predeterminado es ./perl).

  • PERL_SKIP_TTY_TEST

    si está establecido, indica que se omitan las pruebas que necesitan una terminal. En realidad, está configurado automáticamente por el Makefile, pero también se puede forzar artificialmente ejecutando 'make test_notty'.

Otras variables de entorno que pueden influir en las pruebas

  • PERL_TEST_Net_Ping

    Establecer esta variable ejecuta todas las pruebas de los módulos Net::Ping; de lo contrario, se omiten algunas pruebas que interactúan con el mundo exterior. Ver perl58delta.

  • PERL_TEST_NOVREXX

    Establecer esta variable omite las pruebas vrexx.t para OS2::REXX.

  • PERL_TEST_NUMCONVERTS

    Esto establece una variable en op/numconvert.t.

  • PERL_TEST_MEMORY

    Establecer esta variable incluye la prueb

PRUEBAS Y PERL

La ejecución de las pruebas estándar es un paso crucial en el desarrollo de Perl. El script make test ejecuta todas las pruebas incluidas en el conjunto de fuentes de Perl.

La mayoría de las pruebas se encuentran en el directorio t/. Los resultados de las pruebas se suelen generar en el archivo t/TEST.pl. En caso de que alguna prueba falle, obtendrá información de diagnóstico que le ayudará a corregir el problema.

Pruebas de memoria

Algunas pruebas pueden consumir mucha memoria. Si es un desarrollador que participa en las pruebas y corre el riesgo de quedarse sin memoria durante la ejecución de las pruebas, puede limitar la cantidad de memoria que puede utilizar una prueba determinada mediante la variable de entorno PERL_TEST_MEMORY.

Por ejemplo, si su sistema tiene 8 GiB de RAM, pero solo desea ejecutar las pruebas que consumen hasta 4 GiB, establezca la variable de entorno:

PERL_TEST_MEMORY=4

Por lo tanto, se ejecutarán las pruebas en t/bigmem/. Esto debe establecerse en el número de gigabytes de memoria disponibles para las pruebas, por ejemplo, "PERL_TEST_MEMORY=4" indica que las pruebas que requieren 4 GiB de memoria disponible pueden ejecutarse de forma segura.

  • Véase también la documentación de los módulos Test y Test::Harness, para variables de entorno adicionales que afectan a las pruebas.

Pruebas de rendimiento

El archivo t/perf/benchmarks contiene fragmentos de código perl que están destinados a ser evaluados en una variedad de versiones de perl mediante la herramienta Porting/bench.pl. Si corrige o mejora un problema de rendimiento, puede que desee añadir una muestra de código representativa al archivo, luego ejecutar bench.pl contra las versiones de perl anteriores y actuales para ver qué diferencia ha supuesto, y si algo más se ha ralentizado como consecuencia.

El archivo t/perf/opcount.t está diseñado para probar si un fragmento de código determinado se ha compilado en un optree que contiene números especificados de tipos de op concretos. Esto es útil para probar si las optimizaciones que alteran los op, como la conversión de un op "aelem" a un op "aelemfast", realmente lo están haciendo.

Los archivos t/perf/speed.t y t/re/speed.t están diseñados para probar cosas que se ejecutan miles de veces más lentas si una optimización concreta está rota (por ejemplo, la caché de longitud utf8 en cadenas utf8 largas). Añada una prueba que tarde una fracción de segundo normalmente, y minutos de lo contrario, haciendo que el archivo de prueba expire en caso de fallo.

Compilando perl en commits anteriores

En el curso de la modificación de la distribución principal de Perl, puede que tenga la ocasión de configurar, compilar y probar perl en un commit anterior. A veces "make" fallará durante este proceso. Si eso sucede, puede que sea capaz de salvar la situación utilizando la biblioteca Devel::PatchPerl de CPAN (no incluida en el núcleo) para llevar el código fuente de ese commit a un estado compilable.

Aquí hay un ejemplo del mundo real, tomado del trabajo realizado para resolver el perl #10118 https://github.com/Perl/perl5/issues/10118. El uso de Porting/bisect.pl había identificado el commit "ba77e4cc9d1ceebf472c9c5c18b2377ee47062e6" como el commit en el que se corrigió un error. Para confirmarlo, un desarrollador de P5P quería configurar y compilar perl en el commit "ba77e4c^" (presumiblemente "malo") y luego en "ba77e4c" (presumiblemente "bueno"). Se intentó la configuración y compilación normales:

$ sh ./Configure -des -Dusedevel
$ make test_prep

"make", sin embargo, falló con una salida (extractada) como esta:

cc -fstack-protector -L/usr/local/lib -o miniperl \
  gv.o toke.o perly.o pad.o regcomp.o dump.o util.o \
  mg.o reentr.o mro.o hv.o av.o run.o pp_hot.o sv.o \
  pp.o scope.o pp_ctl.o pp_sys.o doop.o doio.o regexec.o \
  utf8.o taint.o deb.o universal.o globals.o perlio.o \
  numeric.o mathoms.o locale.o pp_pack.o pp_sort.o  \
  miniperlmain.o opmini.o perlmini.o
pp.o: En la función `Perl_pp_pow':
pp.c:(.text+0x2db9): referencia no definida a `pow'
...
collect2: error: ld devolvió 1 estado de salida
makefile:348: recipe para el objetivo 'miniperl' falló
make: *** [miniperl] Error 1

Otro contribuidor de P5P recomendó la instalación y el uso de Devel::PatchPerl para esta situación, primero para determinar la versión de perl en el commit en cuestión, luego para parchear el código fuente en ese punto para facilitar una compilación.

$ perl -MDevel::PatchPerl -e \
    'print Devel::PatchPerl->determine_version("/path/to/sourcecode"),
           "\n";'
5.11.1
$ perl -MDevel::PatchPerl -e \
    'Devel::PatchPerl->patch_source("5.11.1", "/path/to/sourcecode");'

Una vez parcheado el código fuente, se llamaron a "./Configure" y "make test_prep" y se completaron correctamente, lo que permitió confirmar los hallazgos en RT #72414.

NAME

perlhack - hacking on Perl

DESCRIPTION

This document aims to help you get started hacking on Perl. It is not intended to be a complete reference, nor to explain every nuance of the Perl source code. Rather, it tries to provide enough information to get you started, and point you to the right places to look for more details.

The Perl source code is a complex beast. This document is intended to be a guide to navigating it, rather than a detailed explanation of how it works.

There are several ways to contribute to Perl. You can:

  • Fix bugs.
  • Add new features.
  • Improve documentation.
  • Write tests.
  • Triage bug reports.
  • Help with releases.
  • Help out on the mailing lists.

The best way to start is to fix a bug. This will help you get familiar with the Perl source code, and with the build and test process.

If you are interested in contributing, please join the perl5-porters mailing list. This is where most of the development discussion happens.

SUPER QUICK PATCH GUIDE

Here's the absolute minimum you need to know to get a patch submitted:

  1. Get the source code (see below).

  2. Configure and build it. You'll likely want to run sh Configure -des -Dprefix=/tmp/perl and then make and make install.

  3. Make your change.

  4. Run make test to ensure you haven't broken anything.

  5. Create a patch using git diff. Make sure your patch is clean and easy to understand.

  6. Submit the patch to the Perl 5 Porters mailing list (perl5-porters@perl.org).

BUG REPORTING

If you find a bug in Perl, please report it. The best place to report bugs is the Perl bug tracker: https://rt.perl.org/.

When reporting a bug, please include as much information as possible:

  • The version of Perl you are using.
  • Your operating system and version.
  • A small, self-contained test case that demonstrates the bug.
  • Any error messages you receive.

If you can, try to fix the bug yourself. This is a great way to learn about the Perl internals.

PERL 5 PORTERS

The Perl 5 Porters are the people who develop and maintain Perl. They are a group of volunteers who work on Perl in their spare time.

The main communication channel for the Perl 5 Porters is the perl5-porters@perl.org mailing list. This is where discussions about new features, bug fixes, and release planning take place.

You can subscribe to the mailing list by sending an email to perl5-porters-subscribe@perl.org.

The archives of the mailing list are available at https://nntp.perl.org/group/perl.perl5.porters.

GETTING THE PERL SOURCE

The Perl source code is hosted on GitHub: https://github.com/Perl/perl5.

You can clone the repository using git:

git clone https://github.com/Perl/perl5.git

It is recommended to check out the latest stable release branch (e.g., git checkout bleadperl for the development branch, or git checkout perl-5.38.0 for a specific release). Use git branch -a to see all available branches.

PATCHING PERL

The Perl source code is managed using git. When you make changes, you should create a patch file that can be applied to the original source code.

To create a patch, use the git diff command. For example, if you have made changes to the file t/op/basic.t, you can create a patch like this:

git diff t/op/basic.t > basic.patch

It is also a good idea to include the output of git log in your patch email, so that the context of your changes is clear.

When submitting a patch, please make sure it is:

  • Clean: No unnecessary whitespace or commented-out code.
  • Self-contained: Addresses a single issue or feature.
  • Well-documented: Includes a clear explanation of what the patch does and why.

It is also customary to include a quotation from J.R.R. Tolkien at the beginning of your patch, in the format used in the Perl source code itself. For example:

   # The Road goes ever on and on,
   # Down from the door where it began.
   # Now far ahead the Road is lost,
   # And now it is high time to go.

This practice is a long-standing tradition in the Perl community, originating from the Perl 5 release notes. The quotes are typically taken from Tolkien's works, especially *The Hobbit* and *The Lord of the Rings*.

If you are unsure about which edition to quote from, the following are generally acceptable:

  • The original 1954-1955 editions of *The Lord of the Rings*.

  • The revised edition of *The Lord of the Rings* (1965).

  • The single-volume editions published by George Allen & Unwin.

  • The 3-volume omnibus edition of 2002.

  • Various trade-paper editions by Harper Collins or Houghton Mifflin.

Other JRRT books that are fair game for quotes would thus include *The Adventures of Tom Bombadil*, *The Silmarillion*, *Unfinished Tales*, and *The Tale of the Children of Hurin*, all but the first posthumously assembled by CJRT. But *The Lord of the Rings* itself is perfectly fine and probably best to quote from, provided you can find a suitable quote there.

So if you were to supply a new, complete, top-level source file to add to Perl, you should conform to this peculiar practice by yourself selecting an appropriate quotation from Tolkien, retaining the original spelling and punctuation and using the same format the rest of the quotes are in. Indirect and oblique is just fine; remember, it's a metaphor, so being meta is, after all, what it's for.

TESTING

Perl has an extensive test suite. You should always run the tests after making changes to ensure you haven't broken anything.

To run the tests, navigate to the root of the Perl source directory and run:

make test

This will run all the tests in the test suite. If any tests fail, it will indicate a problem with your changes.

You can also run individual tests or groups of tests. For example, to run the tests in the t/op directory, you can run:

make test_harness t/op

Refer to the TESTING file in the Perl source distribution for more information on running and writing tests.

MORE READING FOR GUTS HACKERS

If you want to dive deeper into the Perl source code, here are some resources:

  • perl.c: The main C file for Perl. This is where the core interpreter logic resides.

  • op.c, op.h: Defines the abstract syntax tree (AST) nodes used by Perl's compiler.

  • pp.h, pp_*.c: The "Perl-Perl" code, which defines the low-level operations that the Perl compiler generates.

  • regcomp.c: The regular expression compiler.

  • The Perl Internals Book: A comprehensive guide to the Perl internals, although it may be somewhat dated.

  • The source code itself! The best way to understand how Perl works is to read the code.

CPAN TESTERS AND PERL SMOKERS

The CPAN Testers project provides automated testing of Perl modules on a wide variety of platforms. Perl Smokers do the same for Perl itself.

Contributing to CPAN Testers or Perl Smokers is a great way to help ensure the stability and quality of Perl and its ecosystem.

See the CPAN Testers website for more information.
