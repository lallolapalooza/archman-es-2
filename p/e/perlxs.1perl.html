NOMBRE

perlxs - manual de referencia del lenguaje XS

DESCRIPCIÓN

Introducción

XS es un formato de archivo de descripción de interfaz utilizado para crear una interfaz de extensión entre Perl y código C (o una biblioteca C) que se desea utilizar con Perl. La interfaz XS se combina con la biblioteca para crear una nueva biblioteca que luego puede cargarse dinámicamente o enlazarse estáticamente a perl. La descripción de la interfaz XS está escrita en el lenguaje XS y es el componente central de la interfaz de extensión de Perl.

Este documento describe el lenguaje XS, pero es importante notar primero que el código XS tiene acceso completo a las llamadas del sistema, incluidas las funciones de la biblioteca C. Por lo tanto, tiene la capacidad de interferir con cosas que el núcleo de Perl u otros módulos han configurado, como manejadores de señales o descriptores de archivos. Podría dañar la memoria, o una serie de cosas perjudiciales. No lo hagas. Más detalles se encuentran en perlclib, que deberías leer antes de escribir código XS de producción.

Un XSUB forma la unidad básica de la interfaz XS. Después de la compilación por el compilador xsubpp, cada XSUB se traduce a una definición de función C que proporcionará el pegamento entre las convenciones de llamada de Perl y las convenciones de llamada de C.

El código de pegamento extrae los argumentos de la pila de Perl, convierte estos valores de Perl a los formatos esperados por una función C, llama a esta función C y luego transfiere los valores de retorno de la función C de vuelta a Perl. Los valores de retorno aquí pueden ser un valor de retorno C convencional o cualquier argumento de función C que pueda servir como parámetros de salida. Estos valores de retorno pueden pasarse de vuelta a Perl colocándolos en la pila de Perl, o modificando los argumentos suministrados desde el lado de Perl.

Lo anterior es una visión algo simplificada de lo que realmente sucede. Dado que Perl permite convenciones de llamada más flexibles que C, los XSUB pueden hacer mucho más en la práctica, como verificar la validez de los parámetros de entrada, lanzar excepciones (o devolver undef/lista vacía) si el valor de retorno de la función C indica un fallo, llamar a diferentes funciones C según los números y tipos de los argumentos, proporcionar una interfaz orientada a objetos, etc.

Por supuesto, uno podría escribir dicho código de pegamento directamente en C. Sin embargo, esto sería una tarea tediosa, especialmente si uno necesita escribir pegamento para múltiples funciones C, y/o si uno no está lo suficientemente familiarizado con la disciplina de la pila de Perl y otros arcana similares. XS viene al rescate aquí: en lugar de escribir este código de pegamento C de forma explícita, uno puede escribir una descripción más concisa en atajo de lo que se debe hacer por el pegamento, y dejar que el compilador XS xsubpp se encargue del resto.

El lenguaje XS permite describir el mapeo entre cómo se utiliza la rutina C y cómo se utiliza la rutina de Perl correspondiente. También permite la creación de rutinas de Perl que se traducen directamente a código C y que no están relacionadas con una función C preexistente. En los casos en que la interfaz C coincide con la interfaz de Perl, la declaración XS es casi idéntica a la declaración de una función C (estilo K&R). En tales circunstancias, existe otra herramienta llamada "h2xs" que es capaz de traducir un archivo de encabezado C completo a un archivo XS correspondiente que proporcionará pegamento a las funciones/macros descritas en el archivo de encabezado.

El compilador XS se llama xsubpp. Este compilador crea las construcciones necesarias para que un XSUB manipule valores de Perl y crea el pegamento necesario para que Perl llame al XSUB. El compilador utiliza typemaps para determinar cómo mapear los parámetros y valores de salida de las funciones C a valores de Perl y viceversa. El typemap predeterminado (que viene con Perl) maneja muchos tipos C comunes. También puede ser necesario un typemap suplementario para manejar estructuras y tipos especiales para la biblioteca que se está enlazando. Para más información sobre typemaps, consulte perlxstypemap.

Un archivo en formato XS comienza con una sección de lenguaje C que continúa hasta la primera directiva "MODULE =". Pueden seguir otras directivas XS y definiciones de XSUB después de esta línea. El "lenguaje" utilizado en esta parte del archivo se conoce generalmente como el lenguaje XS. xsubpp reconoce y omite POD (ver perlpod) tanto en las secciones de lenguaje C como de XS, lo que permite que el archivo XS contenga documentación incrustada.

Consulte perlxstut para obtener un tutorial sobre todo el proceso de creación de extensiones.

Nota: Para algunas extensiones, el sistema SWIG de Dave Beazley puede proporcionar un mecanismo significativamente más conveniente para crear el código de pegamento de la extensión. Consulte http://www.swig.org/ para obtener más información.

Para enlaces sencillos a bibliotecas C, así como a otras bibliotecas de código máquina, considere en su lugar utilizar la interfaz libffi mucho más sencilla http://sourceware.org/libffi/ a través de módulos CPAN como FFI::Platypus o FFI::Raw.

En el camino

Muchos de los ejemplos que siguen se centrarán en la creación de una interfaz entre Perl y las funciones de la biblioteca de enlace ONC+ RPC. La función rpcb_gettime() se utiliza para demostrar muchas características del lenguaje XS. Esta función tiene dos parámetros; el primero es un parámetro de entrada y el segundo es un parámetro de salida. La función también devuelve un valor de estado.

bool_t rpcb_gettime(const char *host, time_t *timep);

Desde C, esta función se llamará con las siguientes sentencias.

#include <rpc/rpc.h>
bool_t status;
time_t timep;
status = rpcb_gettime( "localhost", &timep );

Si se crea un XSUB para ofrecer una traducción directa entre esta función y Perl, entonces este XSUB se utilizará desde Perl con el siguiente código. Las variables $status y $timep contendrán la salida de la función.

use RPC;
$status = rpcb_gettime( "localhost", $timep );

El siguiente archivo XS muestra una subrutina XS, o XSUB, que demuestra una posible interfaz para la función rpcb_gettime(). Este XSUB representa una traducción directa entre C y Perl y, por lo tanto, conserva la interfaz incluso desde Perl. Este XSUB se invocará desde Perl con el uso mostrado anteriormente. Tenga en cuenta que las primeras tres declaraciones #include, para "EXTERN.h", "perl.h" y "XSUB.h", estarán siempre presentes al principio de un archivo XS. Este enfoque y otros se ampliarán más adelante en este documento. Debería estar presente una #define para "PERL_NO_GET_CONTEXT" para obtener el contexto del intérprete de manera más eficiente, consulte perlguts para obtener detalles.

#define PERL_NO_GET_CONTEXT
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include <rpc/rpc.h>
MODULE = RPC  PACKAGE = RPC
bool_t
rpcb_gettime(host,timep)
     char *host
     time_t &timep
   OUTPUT:
     timep

Cualquier extensión de Perl, incluidas aquellas que contienen XSUBs, debe tener un módulo de Perl para servir como bootstrap que incorpore la extensión en Perl. Este módulo exportará las funciones y variables de la extensión al programa de Perl y provocará que los XSUBs de la extensión se enlacen a Perl. El siguiente módulo se utilizará para la mayoría de los ejemplos en este documento y debe usarse desde Perl con el comando "use" como se mostró anteriormente. Los módulos de Perl se explican con más detalle más adelante en este documento.

package RPC;
require Exporter;
require DynaLoader;
@ISA = qw(Exporter DynaLoader);
@EXPORT = qw( rpcb_gettime );
bootstrap RPC;
1;

A lo largo de este documento se explorarán una variedad de interfaces para el XSUB rpcb_gettime(). Los XSUB tomarán sus parámetros en diferentes órdenes o tomarán diferentes números de parámetros. En cada caso, el XSUB es una abstracción entre Perl y la función C real rpcb_gettime(), y el XSUB siempre debe asegurar que la función C real rpcb_gettime() se llame con los parámetros correctos. Esta abstracción permitirá al programador crear una interfaz más similar a Perl para la función C.

La anatomía de un XSUB

Los XSUBs más simples constan de 3 partes: una descripción del valor de retorno, el nombre de la rutina XSUB y los nombres de sus argumentos, y una descripción de los tipos o formatos de los argumentos.

El siguiente XSUB permite a un programa de Perl acceder a una función de biblioteca C llamada sin(). El XSUB imitará la función C que toma un solo argumento y devuelve un solo valor.

double
sin(x)
  double x

Esto hace que este XSUB se parezca a una declaración ANSI C. Se permite un punto y coma opcional después de la lista de argumentos, como en

double
sin(double x);

Los parámetros con tipos de puntero C pueden tener semántica diferentes: funciones C con declaraciones similares

bool string_looks_as_a_number(char *s);
bool make_char_uppercase(char *c);

se utilizan de manera absolutamente incompatible. Los parámetros de estas funciones podrían describirse a xsubpp de la siguiente manera:

char *  s
char    &c

Ambas declaraciones XS corresponden al tipo C "char*", pero tienen semántica diferente, véase "El Operador Unario &".

Es conveniente pensar que el operador de indirección "*" debe considerarse parte del tipo y el operador de dirección "&" debe considerarse parte de la variable. Véase perlxstypemap para más información sobre el manejo de calificadores y operadores unarios en tipos C.

El nombre de la función y el tipo de retorno deben colocarse en líneas separadas y deben estar alineados a la izquierda.

INCORRECTO                       CORRECTO
double sin(x)                    double
  double x                       sin(x)
                                   double x

El resto de la descripción de la función puede estar indentado o alineado a la izquierda. El siguiente ejemplo muestra una función con su cuerpo alineado a la izquierda. La mayoría de los ejemplos en este documento indentarán el cuerpo para una mejor legibilidad.

CORRECTO
double
sin(x)
double x

Los XSUBs más complicados pueden contener muchas otras secciones. Cada sección de un XSUB comienza con la palabra clave correspondiente, como INIT: o CLEANUP:. Sin embargo, las dos primeras líneas de un XSUB siempre contienen los mismos datos: descripciones del tipo de retorno y los nombres de la función y sus parámetros. Todo lo que sigue inmediatamente a esto se considera una sección INPUT:, a menos que se marque explícitamente con otra palabra clave. (Véase "La Palabra Clave INPUT:".)

Una sección XSUB continúa hasta que se encuentra otra palabra clave de inicio de sección.

La Pila de Argumentos

La pila de argumentos de Perl se utiliza para almacenar los valores que se envían como parámetros al XSUB y para almacenar el/los valor(es) de retorno del XSUB. En realidad, todas las funciones de Perl (incluidas las que no son XSUB) mantienen sus valores en esta pila todo el tiempo, cada una limitada a su propio rango de posiciones en la pila. En este documento, la primera posición en esa pila que pertenece a la función activa se denominará posición 0 para esa función.

Los XSUBs se refieren a sus argumentos de pila con la macro ST(x), donde x se refiere a una posición en la parte de la pila de este XSUB. La posición 0 para esa función sería conocida por el XSUB como ST(0). Los parámetros de entrada y los valores de retorno de salida del XSUB siempre comienzan en ST(0). Para muchos casos simples, el compilador xsubpp generará el código necesario para manejar la pila de argumentos incrustando fragmentos de código que se encuentran en los typemaps. En casos más complejos, el programador debe suministrar el código.

La Variable RETVAL

La variable RETVAL es una variable C especial que se declara automáticamente para usted. El tipo C de RETVAL coincide con el tipo de retorno de la función de biblioteca C. El compilador xsubpp declarará esta variable en cada XSUB con un tipo de retorno distinto de "void". Por defecto, la función C generada utilizará RETVAL para mantener el valor de retorno de la función de biblioteca C que se está llamando. En casos simples, el valor de RETVAL se colocará en ST(0) de la pila de argumentos, donde Perl puede recibirlo como el valor de retorno del XSUB.

Si el XSUB tiene un tipo de retorno de "void", el compilador no declarará una variable RETVAL para esa función. Cuando se utiliza una sección PPCODE:, no se requiere ninguna manipulación de la variable RETVAL; la sección puede utilizar la manipulación directa de la pila para colocar valores de salida en la pila.

Si no se utiliza la directiva PPCODE:, el valor de retorno "void" solo debe utilizarse para subrutinas que no devuelven ningún valor, *incluso si* se utiliza la directiva CODE: que establece ST(0) explícitamente.

Las versiones anteriores de este documento recomendaban usar el valor de retorno "void" en tales casos. Se descubrió que esto podría provocar fallos de segmentación en casos en los que el XSUB era *verdaderamente* "void". Esta práctica ahora está obsoleta y puede no ser compatible en alguna versión futura. Utilice el valor de retorno "SV *" en tales casos. (Actualmente "xsubpp" contiene algo de código heurístico que intenta desambiguar entre funciones "verdaderamente-void" y funciones "declaradas como void según la vieja práctica". Por lo tanto, su código está a merced de estas heurísticas a menos que utilice "SV *" como valor de retorno.)

Retornando SVs, AVs y HVs a través de RETVAL

Cuando utiliza RETVAL para devolver un "SV *", hay algo de magia que ocurre detrás de escena y que debe mencionarse. Cuando manipula la pila de argumentos usando la macro ST(x), por ejemplo, generalmente tiene que prestar especial atención a los recuentos de referencias. (Para más información sobre recuentos de referencias, consulte perlguts). Para facilitarle la vida, el archivo typemap automáticamente hace que "RETVAL" sea mortal cuando devuelve un "SV *". Por lo tanto, los siguientes dos XSUBs son más o menos equivalentes:

void
alpha()
    PPCODE:
        ST(0) = newSVpv("Hello World",0);
        sv_2mortal(ST(0));
        XSRETURN(1);
SV *
beta()
    CODE:
        RETVAL = newSVpv("Hello World",0);
    OUTPUT:
        RETVAL

Esto es bastante útil ya que generalmente mejora la legibilidad. Si bien esto funciona bien para un "SV *", desafortunadamente no es tan fácil tener un "AV *" o un "HV *" como valor de retorno. *Debería* poder escribir:

AV *
array()
    CODE:
        RETVAL = newAV();
        /* hacer algo con RETVAL */
    OUTPUT:
        RETVAL

Pero debido a un error irresoluble (corregirlo rompería muchos módulos CPAN existentes) en el archivo typemap, el recuento de referencias del "AV *" no se decrementa correctamente. Por lo tanto, el XSUB anterior filtraría memoria cada vez que se llamara. El mismo problema existe para "HV *", "CV *" y "SVREF" (que indica una referencia escalar, no un "SV *" general). En el código XS en perls a partir de perl 5.16, puede anular los typemaps para cualquiera de estos tipos con una versión que tenga un manejo adecuado de los recuentos de referencias. En su sección "TYPEMAP", haga:

AV*   T_AVREF_REFCOUNT_FIXED

para obtener la variante reparada. Para la compatibilidad con versiones anteriores de perl, puede decrementar manualmente el recuento de referencias cuando devuelva uno de los tipos mencionados anteriormente usando "sv_2mortal":

AV *
array()
    CODE:
        RETVAL = newAV();
        sv_2mortal((SV*)RETVAL);
        /* hacer algo con RETVAL */
    OUTPUT:
        RETVAL

Recuerde que no tiene que hacer esto para un "SV *". La documentación de referencia para todos los typemaps principales se puede encontrar en perlxstypemap.

La Palabra Clave MODULE

La palabra clave MODULE se utiliza para iniciar el código XS y para especificar el paquete de las funciones que se están definiendo. Todo el texto anterior a la primera palabra clave MODULE se considera código C y se pasa al resultado con POD eliminado, pero de lo contrario sin cambios. Cada módulo XS tendrá una función de bootstrap que se utiliza para vincular los XSUBs a Perl. El nombre del paquete de esta función de bootstrap coincidirá con el valor de la última declaración MODULE en los archivos de origen XS. El valor de MODULE siempre debe permanecer constante dentro del mismo archivo XS, aunque esto no es obligatorio.

El siguiente ejemplo iniciará el código XS y colocará todas las funciones en un paquete llamado RPC.

MODULE = RPC

La Palabra Clave PACKAGE

Cuando las funciones dentro de un archivo de origen XS deben separarse en paquetes, se debe utilizar la palabra clave PACKAGE. Esta palabra clave se utiliza con la palabra clave MODULE y debe seguir inmediatamente después de ella cuando se usa.

MODULE = RPC  PACKAGE = RPC
[ Código XS en el paquete RPC ]
MODULE = RPC  PACKAGE = RPCB
[ Código XS en el paquete RPCB ]
MODULE = RPC  PACKAGE = RPC
[ Código XS en el paquete RPC ]

El mismo nombre de paquete se puede usar más de una vez, permitiendo código no contiguo. Esto es útil si tiene un principio de ordenación más fuerte que los nombres de paquetes.

Aunque esta palabra clave es opcional y en algunos casos proporciona información redundante, siempre debe usarse. Esta palabra clave asegurará que los XSUBs aparezcan en el paquete deseado.

La Palabra Clave PREFIX

La palabra clave PREFIX designa prefijos que deben eliminarse de los nombres de funciones de Perl. Si la función C es rpcb_gettime() y el valor de PREFIX es "rpcb_", entonces Perl verá esta función como gettime().

Esta palabra clave debe seguir a la palabra clave PACKAGE cuando se utiliza. Si no se usa PACKAGE, entonces PREFIX debe seguir a la palabra clave MODULE.

MODULE = RPC  PREFIX = rpc_
MODULE = RPC  PACKAGE = RPCB  PREFIX = rpcb_

La Palabra Clave OUTPUT:

La palabra clave OUTPUT: indica que ciertos parámetros de la función deben actualizarse (nuevos valores hechos visibles para Perl) cuando el XSUB termina o que ciertos valores deben devolverse a la función Perl que llama. Para funciones simples que no tienen una sección CODE: o PPCODE:, como la función sin() anterior, la variable RETVAL se designa automáticamente como un valor de salida. Keywords

The OUTPUT: Keyword

This keyword will normally be used to complement the CODE: keyword. The RETVAL variable is not recognized as an output variable when the CODE: keyword is present. The OUTPUT: keyword is used in this situation to tell the compiler that RETVAL really is an output variable.

The OUTPUT: keyword can also be used to indicate that function parameters are output variables. This may be necessary when a parameter has been modified within the function and the programmer would like the update to be seen by Perl.

bool_t
rpcb_gettime(host,timep)
     char *host
     time_t &timep
   OUTPUT:
     timep

The OUTPUT: keyword will also allow an output parameter to be mapped to a matching piece of code rather than to a typemap.

bool_t
rpcb_gettime(host,timep)
     char *host
     time_t &timep
   OUTPUT:
     timep sv_setnv(ST(1), (double)timep);

xsubpp emite un SvSETMAGIC() automático para todos los parámetros en la sección OUTPUT de la XSUB, excepto RETVAL. Este es el comportamiento deseado usualmente, ya que se encarga de invocar correctamente la magia de 'set' en los parámetros de salida (necesaria para parámetros de elementos de hash o array que deben crearse si no existían). Si por alguna razón, este comportamiento no se desea, la sección OUTPUT puede contener una línea "SETMAGIC: DISABLE" para deshabilitarlo para el resto de los parámetros en la sección OUTPUT. Igualmente, "SETMAGIC: ENABLE" puede usarse para volver a habilitarlo para el resto de la sección OUTPUT. Ver perlguts para más detalles sobre la magia de 'set'.

El NO_OUTPUT Keyword

NO_OUTPUT puede colocarse como el primer token de la XSUB. Este keyword indica que aunque la subrutina C a la que proporcionamos una interfaz tiene un tipo de retorno distinto de "void", el valor de retorno de esta subrutina C no debe devolverse desde la subrutina Perl generada.

Con este keyword presente, se crea "La Variable RETVAL", y en la llamada generada a la subrutina se le asigna esta variable, pero el valor de esta variable no se utilizará en el código auto-generado.

Este keyword solo tiene sentido si "RETVAL" va a ser accedido por el código suministrado por el usuario. Es especialmente útil para hacer que una interfaz de función sea más parecida a Perl, especialmente cuando el valor de retorno de C es solo un indicador de condición de error. Por ejemplo,

NO_OUTPUT int
delete_file(char *name)
  POSTCALL:
    if (RETVAL != 0)
        croak("Error %d while deleting file '%s'", RETVAL, name);

Aquí la función XS generada no devuelve nada en caso de éxito y hará die() con un mensaje de error significativo en caso de error.

El CODE: Keyword

Este keyword se utiliza en XSUBs más complicadas que requieren un manejo especial para la función C. La variable RETVAL todavía se declara, pero no se devolverá a menos que se especifique en la sección OUTPUT:.

La siguiente XSUB es para una función C que requiere manejo especial de sus parámetros. El uso en Perl se da primero.

$status = rpcb_gettime( "localhost", $timep );

La XSUB sigue.

bool_t
rpcb_gettime(host,timep)
     char *host
     time_t timep
   CODE:
          RETVAL = rpcb_gettime( host, &timep );
   OUTPUT:
     timep
     RETVAL

El INIT: Keyword

El keyword INIT: permite insertar inicialización en la XSUB antes de que el compilador genere la llamada a la función C. A diferencia del keyword CODE: anterior, este keyword no afecta la forma en que el compilador maneja RETVAL.

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    INIT:
      printf("# Host is %s\n", host );
    OUTPUT:
      timep

Otro uso para la sección INIT: es verificar precondiciones antes de realizar una llamada a la función C:

long long
lldiv(a,b)
    long long a
    long long b
  INIT:
    if (a == 0 && b == 0)
        XSRETURN_UNDEF;
    if (b == 0)
        croak("lldiv: cannot divide by 0");

El NO_INIT Keyword

El keyword NO_INIT se utiliza para indicar que un parámetro de función se está utilizando solo como valor de salida. El compilador xsubpp normalmente generará código para leer los valores de todos los parámetros de la función de la pila de argumentos y asignarlos a variables C al entrar en la función. NO_INIT le indicará al compilador que algunos parámetros se utilizarán para salida en lugar de entrada y que se manejarán antes de que la función termine.

El siguiente ejemplo muestra una variación de la función rpcb_gettime(). Esta función utiliza la variable timep solo como variable de salida y no le importa su contenido inicial.

bool_t
rpcb_gettime(host,timep)
     char *host
     time_t &timep = NO_INIT
   OUTPUT:
     timep

El TYPEMAP: Keyword

A partir de Perl 5.16, puedes incrustar typemaps en tu código XS en lugar de o además de los typemaps en un archivo separado. Múltiples typemaps incrustados de este tipo se procesarán en el orden de aparición en el código XS y, al igual que los archivos typemap locales, tendrán prioridad sobre el typemap predeterminado. Los typemaps incrustados pueden sobrescribir definiciones anteriores de secciones TYPEMAP, INPUT y OUTPUT. La sintaxis para los typemaps incrustados es

TYPEMAP: <<HERE
... tu código typemap aquí ...
HERE

donde el keyword "TYPEMAP" debe aparecer en la primera columna de una nueva línea.

Consulta perlxstypemap para obtener detalles sobre cómo escribir typemaps.

Inicializando Parámetros de Funciones

Los parámetros de las funciones C se inicializan normalmente con sus valores de la pila de argumentos (que a su vez contiene los parámetros que se pasaron a la XSUB desde Perl). Los typemaps contienen los segmentos de código que se utilizan para traducir los valores de Perl a los parámetros C. Sin embargo, al programador se le permite anular los typemaps y proporcionar segmentos de código de inicialización alternativos (o adicionales). El código de inicialización comienza con el primer "=", ";" o "+" en una línea en la sección INPUT:. La única excepción ocurre si este ";" termina la línea, entonces este ";" se ignora silenciosamente.

El siguiente código demuestra cómo proporcionar código de inicialización para parámetros de funciones. El código de inicialización es evaluado entre comillas dobles por el compilador antes de agregarse a la salida, por lo que cualquier cosa que deba interpretarse literalmente [principalmente "$", "@" o "\\"] debe protegerse con barras invertidas. Las variables $var, $arg y $type se pueden usar como en los typemaps.

bool_t
rpcb_gettime(host,timep)
     char *host = (char *)SvPVbyte_nolen($arg);
     time_t &timep = 0;
   OUTPUT:
     timep

Esto no debe usarse para proporcionar valores predeterminados para parámetros. Uno normalmente lo usaría cuando un parámetro de función debe ser procesado por otra función de biblioteca antes de que pueda usarse. Los parámetros predeterminados se cubren en la siguiente sección.

Si la inicialización comienza con "=", entonces se emite en la declaración de la variable de entrada, reemplazando la inicialización proporcionada por el typemap. Si la inicialización comienza con ";" o "+", entonces se realiza después de que se hayan declarado todas las variables de entrada. En el caso de ";", la inicialización normalmente proporcionada por el typemap no se realiza. Para el caso de "+", la declaración de la variable incluirá la inicialización del typemap. Una variable global, %v, está disponible para el caso verdaderamente raro en que se necesite información de una inicialización en otra inicialización.

Aquí hay un ejemplo verdaderamente oscuro:

bool_t
rpcb_gettime(host,timep)
     time_t &timep; /* \$v{timep}=@{[$v{timep}=$arg]} */
     char *host + SvOK($v{timep}) ? SvPVbyte_nolen($arg) : NULL;
   OUTPUT:
     timep

La construcción "\$v{timep}=@{[$v{timep}=$arg]}" utilizada en el ejemplo anterior tiene un doble propósito: primero, cuando esta línea es procesada por xsubpp, se evalúa el fragmento de Perl "$v{timep}=$arg". Segundo, el texto del fragmento evaluado se emite en el archivo C generado (¡dentro de un comentario C!). Durante el procesamiento de la línea "char *host", $arg se evaluará como ST(0), y $v{timep} se evaluará como ST(1).

Valores Predeterminados de Parámetros

Los valores predeterminados para los argumentos de XSUB se pueden especificar colocando una sentencia de asignación en la lista de parámetros. El valor predeterminado puede ser un número, una cadena o la cadena especial "NO_INIT". Los valores predeterminados siempre deben usarse solo en los parámetros más a la derecha.

Para permitir que la XSUB para rpcb_gettime() tenga un valor de host predeterminado, los parámetros de la XSUB podrían reorganizarse. La XSUB luego llamará a la función real rpcb_gettime() con los parámetros en el orden correcto. Esta XSUB se puede llamar desde Perl con cualquiera de las siguientes sentencias:

$status = rpcb_gettime( $timep, $host );
$status = rpcb_gettime( $timep );

La XSUB se verá como el código que sigue. Se utiliza un bloque CODE: para llamar a la función real rpcb_gettime() con los parámetros en el orden correcto para esa función.

bool_t
rpcb_gettime(timep,host="localhost")
     char *host
     time_t timep = NO_INIT
   CODE:
          RETVAL = rpcb_gettime( host, &timep );
   OUTPUT:
     timep
     RETVAL

La palabra clave VERSIONCHECK: corresponde a las opciones "-versioncheck" y de xsubpp. Esta palabra clave anula las opciones de la línea de comandos. La verificación de versiones está habilitada por defecto. Cuando la verificación de versiones está habilitada, el módulo XS intentará verificar que su versión coincida con la versión del módulo PM.

Para habilitar la verificación de versiones:

Para deshabilitar la verificación de versiones:

Tenga en cuenta que si la versión del módulo PM es una NV (un número de punto flotante), se convertirá a cadena con una posible pérdida de precisión (actualmente se trunca a nueve decimales) para que no coincida con la versión del módulo XS. Se recomienda entrecomillar la declaración $VERSION para que sea una cadena si se utilizan números de versión largos.

La Palabra Clave ALIAS:

La palabra clave ALIAS: permite que un XSUB tenga dos o más nombres de Perl únicos y que sepa cuál de esos nombres se usó cuando se invocó. Los nombres de Perl pueden estar completamente calificados con nombres de paquetes. A cada alias se le asigna un índice. El compilador configurará una variable llamada que contendrá el índice del alias que se utilizó. Cuando el XSUB se llama con su nombre declarado, será 0.

El siguiente ejemplo creará alias FOO::gettime() y BAR::getit() para esta función.

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    ALIAS:
        FOO::gettime = 1
        BAR::getit = 2
    INIT:
      printf("# ix = %d\n", ix );
    OUTPUT:
      timep

Se generará una advertencia cuando cree más de un alias para el mismo valor. Esto se puede solucionar de manera compatible con versiones anteriores creando múltiples defines que se resuelven al mismo valor, o con una versión moderna de ExtUtils::ParseXS puede usar un alias simbólico, que se denota con un en lugar de un . Por ejemplo, podría cambiar lo anterior para que la sección de alias se vea así:

ALIAS:
    FOO::gettime = 1
    BAR::getit = 2
    BAZ::gettime => FOO::gettime

esto tendría el mismo efecto que esto:

ALIAS:
    FOO::gettime = 1
    BAR::getit = 2
    BAZ::gettime = 1

excepto que este último generará advertencias durante el proceso de compilación. Un mecanismo que funcionaría de manera compatible con versiones anteriores con versiones anteriores de nuestra cadena de herramientas sería hacer esto:

#define FOO_GETTIME 1
#define BAR_GETIT 2
#define BAZ_GETTIME 1
bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    ALIAS:
        FOO::gettime = FOO_GETTIME
        BAR::getit = BAR_GETIT
        BAZ::gettime = BAZ_GETTIME
    INIT:
      printf("# ix = %d\n", ix );
    OUTPUT:
      timep

La Palabra Clave OVERLOAD:

En lugar de escribir una interfaz sobrecargada usando Perl puro, también puede usar la palabra clave OVERLOAD para definir nombres de Perl adicionales para sus funciones (similar a la palabra clave ALIAS: anterior). Sin embargo, las funciones sobrecargadas deben definirse de manera que acepten el número de parámetros suministrados por el sistema de sobrecarga de perl. Para la mayoría de los métodos de sobrecarga, serán tres parámetros; para la función , serán cuatro. Sin embargo, los operadores a nivel de bits , , y pueden ser llamados con tres o cinco argumentos (ver overload).

Si alguna función tiene la palabra clave OVERLOAD:, se definirán varias líneas adicionales en el archivo c generado por xsubpp para registrarse con la magia de sobrecarga.

Dado que los objetos bendecidos se almacenan en realidad como RVs, es útil usar las características de typemap para preprocesar parámetros y extraer el SV real almacenado dentro del RV bendecido. Consulte el ejemplo para T_PTROBJ_SPECIAL en perlxstypemap.

Para usar la palabra clave OVERLOAD:, cree una función XS que tome tres parámetros de entrada (o use la definición de estilo C '...') de la siguiente manera:

SV *
cmp (lobj, robj, swap)
My_Module_obj    lobj
My_Module_obj    robj
IV               swap
OVERLOAD: cmp <=>
{ /* la función se define aquí */}

En este caso, la función sobrecargará ambos operadores de comparación de tres vías. Para todas las operaciones de sobrecarga que usan caracteres no alfabéticos, debe escribir el parámetro sin comillas, separando múltiples sobrecargas con espacios en blanco. Tenga en cuenta que "" (la sobrecarga de conversión a cadena) debe ingresarse como \"\" (es decir, escapada).

Dado que, como se mencionó anteriormente, los operadores a nivel de bits pueden tomar argumentos adicionales, es posible que desee usar algo como "(lobj, robj, swap, ...)" (con ... literal) como su lista de parámetros.

La Palabra Clave FALLBACK:

Además de la palabra clave OVERLOAD, si necesita controlar cómo Perl autogenera los operadores sobrecargados faltantes, puede establecer la palabra clave FALLBACK en la sección del encabezado del módulo, de la siguiente manera:

MODULE = RPC  PACKAGE = RPC
FALLBACK: TRUE
...

donde FALLBACK puede tomar cualquiera de los tres valores TRUE, FALSE o UNDEF. Si no establece ningún valor FALLBACK cuando usa OVERLOAD, el valor predeterminado es UNDEF. FALLBACK no se utiliza excepto cuando se ha definido una o más funciones que utilizan OVERLOAD. Consulte "fallback" en overload para obtener más detalles.

La Palabra Clave INTERFACE:

Esta palabra clave declara el XSUB actual como un conservador de la firma de llamada dada. Si sigue algún texto a esta palabra clave, se considera una lista de funciones que tienen esta firma y deben adjuntarse al XSUB actual.

Por ejemplo, si tiene 4 funciones C multiply(), divide(), add(), subtract() todas con la firma:

simbólico f(simbólico, simbólico);

puede hacer que todas utilicen el mismo XSUB usando esto:

simbólico
interface_s_ss(arg1, arg2)
    simbólico        arg1
    simbólico        arg2
INTERFACE:
    multiply divide
    add subtract

(¡Este es el código XSUB completo para 4 funciones de Perl!) Cuatro funciones de Perl generadas comparten nombres con las funciones C correspondientes.

La ventaja de este enfoque en comparación con la palabra clave ALIAS: es que no hay necesidad de codificar una declaración switch, cada función de Perl (que comparte el mismo XSUB) sabe qué función C debe llamar. Además, uno puede adjuntar una función adicional remainder() en tiempo de ejecución usando

CV *mycv = newXSproto("Symbolic::remainder",
                      XS_Symbolic_interface_s_ss, __FILE__, "$$");
XSINTERFACE_FUNC_SET(mycv, remainder);

por ejemplo, desde otro XSUB. (Este ejemplo supone que no hubo una sección INTERFACE_MACRO:, de lo contrario, se necesita usar algo más en lugar de , consulte la siguiente sección).

La Palabra Clave INTERFACE_MACRO:

Esta palabra clave permite definir una INTERFACE utilizando una forma diferente de extraer un puntero de función de un XSUB. El texto que sigue a esta palabra clave debe dar el nombre de las macros que extraerían/establecerían un puntero de función. La macro extractora recibe el tipo de retorno, , y para este . La macro configuradora recibe cv y el puntero de función.

El valor predeterminado es y . Se puede omitir una palabra clave INTERFACE con una lista vacía de funciones si se utiliza la palabra clave INTERFACE_MACRO.

Suponga que en el ejemplo anterior los punteros de función para multiply(), divide(), add(), subtract() se almacenan en una matriz C global con los desplazamientos siendo , , , . Entonces se puede usar

#define XSINTERFACE_FUNC_BYOFFSET(ret,cv,f) \
    ((XSINTERFACE_CVT_ANON(ret))fp[CvXSUBANY(cv).any_i32])
#define XSINTERFACE_FUNC_BYOFFSET_set(cv,f) \
    CvXSUBANY(cv).any_i32 = CAT2( f, _off )

en la sección C,

simbólico
interface_s_ss(arg1, arg2)
    simbólico        arg1
    simbólico        arg2
INTERFACE_MACRO:
    XSINTERFACE_FUNC_BYOFFSET XSINTERFACE_FUNC_BYOFFSET_set
INTERFACE:
    multiply divide
    add subtract

En este caso, el primer argumento de cada macro de INTERFACE_MACRO es para extraer el puntero de función, y el segundo es para establecerlo.

bolic arg2 INTERFACE_MACRO: XSINTERFACE_FUNC_BYOFFSET XSINTERFACE_FUNC_BYOFFSET_set INTERFACE: multiply divide add subtract

en la sección XSUB.

La Palabra clave INCLUDE:

Esta palabra clave se puede utilizar para incluir otros archivos en el módulo XS. Los otros archivos pueden tener código XS. INCLUDE: también se puede utilizar para ejecutar un comando para generar el código XS que se incluirá en el módulo.

El archivo Rpcb1.xsh contiene nuestra función rpcb_gettime():

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    OUTPUT:
      timep

El módulo XS puede usar INCLUDE: para incluir ese archivo en él.

INCLUDE: Rpcb1.xsh

Si los parámetros de la palabra clave INCLUDE: van seguidos de una barra vertical ("|"), el compilador interpretará los parámetros como un comando. Esta característica está ligeramente obsoleta en favor de la directiva "INCLUDE_COMMAND:", como se documenta a continuación.

INCLUDE: cat Rpcb1.xsh |

No utilice esto para ejecutar perl: "INCLUDE: perl |" ejecutará el perl que sea el primero en su ruta y no necesariamente el mismo perl que se utiliza para ejecutar "xsubpp". Véase "La Palabra clave INCLUDE_COMMAND:".

La Palabra clave INCLUDE_COMMAND:

Ejecuta el comando proporcionado e incluye su salida en el documento XS actual. "INCLUDE_COMMAND" asigna un significado especial al token $^X, ya que ejecuta el mismo intérprete de perl que está ejecutando "xsubpp":

INCLUDE_COMMAND: cat Rpcb1.xsh
INCLUDE_COMMAND: $^X -e ...

La Palabra clave CASE:

La palabra clave CASE: permite que una XSUB tenga múltiples partes distintas, cada parte actuando como una XSUB virtual. CASE: es codicioso y si se utiliza, todas las demás palabras clave XS deben estar contenidas dentro de un CASE:. Esto significa que nada puede preceder al primer CASE: en la XSUB y todo lo que siga al último CASE: se incluirá en ese caso.

Un CASE: puede cambiar a través de un parámetro de la XSUB, a través de la variable del alias "ix" (véase "La Palabra clave ALIAS:"), o quizás a través de la variable "items" (véase "Listas de parámetros de longitud variable"). El último CASE: se convierte en el caso predeterminado si no está asociado a una condición. El siguiente ejemplo muestra CASE cambiando a través de "ix" con una función rpcb_gettime() que tiene un alias x_gettime(). Cuando la función se llama como rpcb_gettime() sus parámetros son los habituales "(char *host, time_t *timep)", pero cuando la función se llama como x_gettime() sus parámetros se invierten, "(time_t *timep, char *host)".

long
rpcb_gettime(a,b)
  CASE: ix == 1
    ALIAS:
      x_gettime = 1
    INPUT:
      # 'a' es timep, 'b' es host
      char *b
      time_t a = NO_INIT
    CODE:
           RETVAL = rpcb_gettime( b, &a );
    OUTPUT:
      a
      RETVAL
  CASE:
      # 'a' es host, 'b' es timep
      char *a
      time_t &b = NO_INIT
    OUTPUT:
      b
      RETVAL

Esa función se puede llamar con cualquiera de las siguientes sentencias. Tenga en cuenta las diferentes listas de argumentos.

$status = rpcb_gettime( $host, $timep );
$status = x_gettime( $timep, $host );

La Palabra clave EXPORT_XSUB_SYMBOLS:

La palabra clave EXPORT_XSUB_SYMBOLS: es probablemente algo que nunca necesitará. En las versiones de perl anteriores a 5.16.0, esta palabra clave no hace nada. A partir de la versión 5.16, los símbolos de XSUB ya no se exportan por defecto. Es decir, son funciones "estáticas". Si incluye

EXPORT_XSUB_SYMBOLS: ENABLE

en su código XS, las XSUBs que sigan esta línea no se declararán "estáticas". Puede deshabilitar esto más tarde con

EXPORT_XSUB_SYMBOLS: DISABLE

que, de nuevo, es el valor predeterminado que probablemente nunca debería cambiar. No puede utilizar esta palabra clave en versiones de perl anteriores a la 5.16 para hacer que las XSUBs sean "estáticas".

El Operador Unario &

El operador unario "&" en la sección INPUT: se utiliza para indicar a xsubpp que convierta un valor de Perl a/desde C utilizando el tipo C a la izquierda de "&", pero que proporcione un puntero a este valor cuando se llame a la función C.

Esto es útil para evitar un bloque CODE: para una función C que toma un parámetro por referencia. Típicamente, el parámetro no debe ser un tipo puntero (un "int" o "long", pero no un "int*" o "long*").

La siguiente XSUB generará código C incorrecto. El compilador xsubpp lo convertirá en código que llama a rpcb_gettime() con los parámetros "(char *host, time_t timep)", pero la rpcb_gettime() real quiere que el parámetro "timep" sea de tipo "time_t*" en lugar de "time_t".

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t timep
    OUTPUT:
      timep

Ese problema se corrige utilizando el operador "&". El compilador xsubpp ahora lo convertirá en código que llama a rpcb_gettime() correctamente con los parámetros "(char *host, time_t *timep)". Lo hace pasando el "&", por lo que la llamada a la función se ve como "rpcb_gettime(host, &timep)".

bool_t
rpcb_gettime(host,timep)
      char *host
      time_t &timep
    OUTPUT:
      timep

Insertar POD, Comentarios y Directivas del Preprocesador C

Las directivas del preprocesador C están permitidas dentro de los bloques BOOT:, PREINIT:, INIT:, CODE:, PPCODE:, POSTCALL: y CLEANUP:, así como fuera de las funciones. Los comentarios están permitidos en cualquier lugar después de la palabra clave MODULE. El compilador pasará las directivas del preprocesador sin modificaciones y eliminará las líneas comentadas. La documentación POD está permitida en cualquier punto, tanto en las secciones de lenguaje C como XS. POD debe terminar con un comando "=cut"; "xsubpp" saldrá con un error si no lo hace. Es muy poco probable que el código C generado por humanos se confunda con POD, ya que la mayoría de los estilos de indentación dan como resultado espacios en blanco delante de cualquier línea que comience con "=". Los archivos XS generados por máquinas pueden caer en esta trampa a menos que se tenga cuidado para asegurar que un espacio rompa la secuencia "\n=".

Se pueden agregar comentarios a las XSUBs colocando un "#" como el primer carácter que no sea espacio en blanco de una línea. Se debe tener cuidado para evitar que el comentario parezca una directiva del preprocesador C, para que no se interprete como tal. La forma más sencilla de evitarlo es poner un espacio en blanco delante del "#".

Si utiliza directivas del preprocesador para elegir una de las dos versiones de una función, utilice

#if ... version1
#else /* ... version2  */
#endif

y no

#if ... version1
#endif
#if ... version2
#endif

porque de lo contrario xsubpp creería que ha realizado una definición duplicada de la función. Además, ponga una línea en blanco antes de #else/#endif para que no se vea como parte del cuerpo de la función.

Usar XS Con C++

Si el nombre de una XSUB contiene "::", se considera un método C++. La función Perl generada asumirá que su primer argumento es un puntero a objeto. El puntero a objeto se almacenará en una variable llamada THIS. El objeto debe haber sido creado por C++ con la función new() y debe haber sido bendecido por Perl con la macro sv_setref_pv(). La bendición del objeto por Perl puede ser manejada por un typemap. Un ejemplo de typemap se muestra al final de esta sección.

Si el tipo de retorno de la XSUB incluye "static", el método se considera un método estático. Llamará a la función C++ utilizando la sintaxis class::method(). Si el método no es estático, la función se llamará utilizando la sintaxis THIS->method().

Los siguientes ejemplos utilizarán la siguiente clase C++.

class color {
     public:
     color();
     ~color();
     int blue();
     void set_blue( int );
     private:
     int c_blue;
};

Las XSUBs para los métodos blue() y set_blue() se definen con el nombre de la clase, pero el parámetro para el objeto (THIS, o "self") es implícito y no se lista.

int
color::blue()
void
color::set_blue( val )
     int val

Ambas funciones Perl esperarán un objeto como primer parámetro. En el código C++ generado, el objeto se llama "THIS" y la llamada al método se realizará sobre este objeto. Así que en el código C++, los métodos blue() y set_blue() se llamarán de la siguiente manera:

RETVAL = THIS->blue();
THIS->set_blue( val );

También podría escribir un único método get/set utilizando un argumento opcional:

int
color::blue( val = NO_INIT )
    int val
    PROTOTYPE $;$
    CODE:
        if (items > 1)
            THIS->set_blue( val );
        RETVAL = THIS->blue();
    OUTPUT:
        RETVAL

Si el nombre de la función es DESTROY, se llamará a la función C++ "delete" y se pasará "THIS" como parámetro. El código C++ generado para

void
color::DESTROY()

se verá así:

color *THIS = ...;  // Inicializado como en el typemap
delete THIS;

TYPEMAP

If the function's name is new then the C++ "new" function will be called to create a dynamic C++ object. The XSUB will expect the class name, which will be kept in a variable called "CLASS", to be given as the first argument.

color *
color::new()

The generated C++ code will call "new".

RETVAL = new color();

The following is an example of a typemap that could be used for this C++ example.

TYPEMAP
color *  O_OBJECT
OUTPUT
# The Perl object is blessed into 'CLASS', which should be a
# char* having the name of the package for the blessing.
O_OBJECT
    sv_setref_pv( $arg, CLASS, (void*)$var );
INPUT
O_OBJECT
    if( sv_isobject($arg) && (SvTYPE(SvRV($arg)) == SVt_PVMG) )
        $var = ($type)SvIV((SV*)SvRV( $arg ));
    else{
        warn(\"${Package}::$func_name() -- \"
            \"$var is not a blessed SV reference\");
        XSRETURN_UNDEF;
    }

Estrategia de Interfaz

Al diseñar una interfaz entre Perl y una biblioteca C, una traducción directa de C a XS (como la creada por "h2xs -x") suele ser suficiente. Sin embargo, a veces la interfaz se verá muy parecida a C y ocasionalmente poco intuitiva, especialmente cuando la función C modifica uno de sus parámetros o devuelve un error en banda (como en "los valores de retorno negativos significan error"). En los casos en que el programador desee crear una interfaz más parecida a Perl, la siguiente estrategia puede ayudar a identificar las partes más críticas de la interfaz.

Identificar las funciones C con parámetros de entrada/salida o salida. Las XSUBs para estas funciones pueden ser capaces de devolver listas a Perl.

Identificar las funciones C que utilizan alguna información en banda como indicación de error. Pueden ser candidatas a devolver `undef` o una lista vacía en caso de error. Si el error puede detectarse sin llamar a la función C, es posible que desee utilizar una sección `INIT:` para informar del error. Para los errores detectables después de que la función C devuelva, puede que desee utilizar una sección `POSTCALL:` para procesar el error. En casos más complicados, utilice las secciones `CODE:` o `PPCODE:`.

Si muchas funciones utilizan la misma indicación de error basada en el valor de retorno, puede que desee crear un `typedef` especial para manejar esta situación. Ponga

typedef int negative_is_failure;

cerca del principio del archivo XS, y cree una entrada de `typemap` de SALIDA para "negative_is_failure" que convierta los valores negativos a "undef", o quizás llame a croak(). Después de esto, el valor de retorno de tipo "negative_is_failure" creará una interfaz más parecida a Perl.

Identificar qué valores son utilizados solo por las funciones C y XSUB en sí mismas, por ejemplo, cuando un parámetro de una función debe ser el contenido de una variable global. Si Perl no necesita acceder al contenido del valor, puede que no sea necesario proporcionar una traducción para ese valor de C a Perl.

Identificar los punteros en las listas de parámetros y valores de retorno de las funciones C. Algunos punteros pueden ser utilizados para implementar parámetros de entrada/salida o de salida, pueden manejarse en XS con el operador unario "&" y, posiblemente, utilizando la palabra clave `NO_INIT`. Otros requerirán el manejo de tipos como "int *", y uno necesita decidir qué hará una traducción útil de Perl en tal caso. Cuando la semántica sea clara, es aconsejable incluir la traducción en un archivo `typemap`.

Identificar las estructuras utilizadas por las funciones C. En muchos casos, puede ser útil utilizar el `typemap` `T_PTROBJ` para estas estructuras, de modo que puedan ser manipuladas por Perl como objetos bendecidos. (Esto lo maneja automáticamente "h2xs -x".)

Si el mismo tipo C se utiliza en varios contextos diferentes que requieren traducciones distintas, cree `typedef` de varios tipos nuevos mapeados a este tipo C y cree entradas de `typemap` separadas para estos tipos nuevos. Utilice estos tipos en las declaraciones del tipo de retorno y los parámetros de las XSUBs.

Objetos Perl y Estructuras C

Al tratar con estructuras C, se debe seleccionar `T_PTROBJ` o `T_PTRREF` para el tipo XS. Ambos tipos están diseñados para manejar punteros a objetos complejos. El tipo `T_PTRREF` permitirá que el objeto Perl sea desbendecido, mientras que el tipo `T_PTROBJ` requiere que el objeto sea bendecido. Al utilizar `T_PTROBJ`, se puede lograr una forma de comprobación de tipos, ya que la XSUB intentará verificar que el objeto Perl sea del tipo esperado.

El siguiente código XS muestra la función getnetconfigent() que se utiliza con ONC+ TIRPC. La función getnetconfigent() devolverá un puntero a una estructura C y tiene el prototipo C que se muestra a continuación. El ejemplo demostrará cómo el puntero C se convertirá en una referencia Perl. Perl considerará esta referencia como un puntero a un objeto bendecido e intentará llamar a un destructor para el objeto. Se proporcionará un destructor en la fuente XS para liberar la memoria utilizada por getnetconfigent(). Los destructores en XS se pueden crear especificando una función XSUB cuyo nombre termine con la palabra `DESTROY`. Los destructores XS se pueden utilizar para liberar memoria que pudo haber sido asignada con `malloc` por otra XSUB.

struct netconfig *getnetconfigent(const char *netid);

Se creará un `typedef` para "struct netconfig". El objeto Perl será bendecido en una clase que coincida con el nombre del tipo C, con la etiqueta "Ptr" añadida, y el nombre no debe tener espacios incrustados si va a ser un nombre de paquete Perl. El destructor se colocará en una clase correspondiente a la clase del objeto y se utilizará la palabra clave `PREFIX` para recortar el nombre a la palabra `DESTROY`, tal como espera Perl.

typedef struct netconfig Netconfig;
MODULE = RPC  PACKAGE = RPC
Netconfig *
getnetconfigent(netid)
     char *netid
MODULE = RPC  PACKAGE = NetconfigPtr  PREFIX = rpcb_
void
rpcb_DESTROY(netconf)
     Netconfig *netconf
   CODE:
     printf("Now in NetconfigPtr::DESTROY\n");
     free( netconf );

Este ejemplo requiere la siguiente entrada de `typemap`. Consulte perlxstypemap para obtener más información sobre cómo añadir nuevos `typemaps` para una extensión.

TYPEMAP
Netconfig *  T_PTROBJ

Este ejemplo se utilizará con las siguientes sentencias Perl.

use RPC;
$netconf = getnetconfigent("udp");

Cuando Perl destruya el objeto referenciado por $netconf, enviará el objeto a la función `DESTROY` XSUB proporcionada. Perl no puede determinar, y no le importa, que este objeto sea una estructura C y no un objeto Perl. En este sentido, no hay diferencia entre el objeto creado por la XSUB getnetconfigent() y un objeto creado por una subrutina Perl normal.

Almacenamiento Seguro de Datos Estáticos en XS

A partir de Perl 5.8, se ha definido un marco de macros para permitir que los datos estáticos se almacenen de forma segura en módulos XS que serán accedidos desde un Perl multihilo.

Aunque están diseñadas principalmente para su uso con Perl multihilo, las macros se han diseñado para que funcionen también con Perl no multihilo.

Por lo tanto, se recomienda encarecidamente que estas macros sean utilizadas por todos los módulos XS que hagan uso de datos estáticos.

La forma más fácil de obtener un conjunto de plantillas de macros para utilizar es especificando la opción "-g" ("--global") con h2xs (ver h2xs).

A continuación se muestra un módulo de ejemplo que utiliza las macros.

#define PERL_NO_GET_CONTEXT
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
/* Global Data */
#define MY_CXT_KEY "BlindMice::_guts" XS_VERSION
typedef struct {
    int count;
    char name[3][100];
} my_cxt_t;
START_MY_CXT
MODULE = BlindMice           PACKAGE = BlindMice
BOOT:
{
    MY_CXT_INIT;
    MY_CXT.count = 0;
    strcpy(MY_CXT.name[0], "None");
    strcpy(MY_CXT.name[1], "None");
    strcpy(MY_CXT.name[2], "None");
}
int
newMouse(char * name)
    PREINIT:
      dMY_CXT;
    CODE:
      if (MY_CXT.count >= 3) {
          warn("Already have 3 blind mice");
          RETVAL = 0;
      }
      else {
          RETVAL = ++ MY_CXT.count;
          strcpy(MY_CXT.name[MY_CXT.count - 1], name);
      }
    OUTPUT:
      RETVAL
char *
get_mouse_name(index)
      int index
    PREINIT:
      dMY_CXT;
    CODE:
      if (index > MY_CXT.count)
        croak("There are only 3 blind mice.");
      else
        RETVAL = MY_CXT.name[index - 1];
    OUTPUT:
      RETVAL
void
CLONE(...)
    CODE:
      MY_CXT_CLONE;

REFERENCIA MY_CXT

MY_CXT_KEY
Esta macro se utiliza para definir una clave única para referirse a los datos estáticos de un módulo XS. El esquema de nomenclatura sugerido, como el utilizado por h2xs, es usar una cadena que consista en el nombre del módulo, la cadena "::_guts" y el número de versión del módulo. 
#define MY_CXT_KEY "MyModule::_guts" XS_VERSION
typedef my_cxt_t
Esta `typedef` de struct *debe* llamarse siempre "my_cxt_t". Las otras macros "CXT*" asumen la existencia del nombre de `typedef` "my_cxt_t".

Declare un `typedef` llamado "my_cxt_t" que sea una estructura que contenga todos los datos que necesitan ser locales al intérprete.

typedef struct {
    int some_value;
} my_cxt_t;
START_MY_CXT
Coloque siempre la macro `START_MY_CXT` directamente después de la declaración de "my_cxt_t".
MY_CXT_INIT
La macro `MY_CXT_INIT` inicializa el almacenamiento para la estructura "my_cxt_t".

Debe llamarse exactamente una vez, normalmente en una sección `BOOT:`. Si está manteniendo múltiples intérpretes, debe llamarse una vez en cada instancia de intérprete, excepto en los intérpretes clonados de los existentes. (Pero véase "MY_CXT_CLONE" más abajo.)

dMY_CXT
Utilice la macro `dMY_CXT` (una declaración) en todas las funciones que accedan a `MY_CXT`.
MY_CXT
La macro `MY_CXT` es la forma de acceder a los datos de la estructura `my_cxt_t` definidos por el intérprete actual.
MY_CXT_CLONE
Esta macro debe ser llamada por el manejador `CLONE` para asegurar que los datos estáticos del módulo son clonados adecuadamente para el nuevo hilo. Si su módulo tiene datos estáticos que deben ser específicos del hilo, debe implementarse un manejador `CLONE` para el módulo.

MY_CXT

MY_CXT
Utilice la macro MY_CXT para acceder a los miembros de la struct "my_cxt_t". Por ejemplo, si "my_cxt_t" es 
typedef struct {
    int index;
} my_cxt_t;

entonces use esto para acceder al miembro "index"

dMY_CXT;
MY_CXT.index = 2;
aMY_CXT/pMY_CXT
"dMY_CXT" puede ser bastante costoso de calcular, y para evitar la sobrecarga de invocarlo en cada función, es posible pasar la declaración a otras funciones usando las macros "aMY_CXT"/"pMY_CXT", por ejemplo 
void sub1() {
    dMY_CXT;
    MY_CXT.index = 1;
    sub2(aMY_CXT);
}
void sub2(pMY_CXT) {
    MY_CXT.index = 2;
}

Análogamente a "pTHX", existen formas equivalentes para cuando la macro es la primera o la última en múltiples argumentos, donde un guion bajo representa una coma, es decir, "_aMY_CXT", "aMY_CXT_", "_pMY_CXT" y "pMY_CXT_".

MY_CXT_CLONE
Por defecto, cuando se crea un nuevo intérprete como una copia de uno existente (por ejemplo, a través de "threads->create()"), ambos intérpretes comparten la misma estructura física my_cxt_t. Llamar a "MY_CXT_CLONE" (típicamente a través de la función CLONE() del paquete), causa que se tome una copia byte a byte de la estructura, y cualquier dMY_CXT futuro causará que se acceda a la copia en su lugar.
MY_CXT_INIT_INTERP(my_perl)
dMY_CXT_INTERP(my_perl)
Estas son versiones de las macros que toman un intérprete explícito como argumento.

Tenga en cuenta que estas macros solo funcionarán juntas dentro del mismo archivo fuente; es decir, un dMY_CTX en un archivo fuente accederá a una estructura diferente que un dMY_CTX en otro archivo fuente.

CAVEATS

Uso de funciones de biblioteca C estándar

Ver perlclib.

Bucles de eventos y flujo de control

Algunos módulos tienen un bucle de eventos, esperando entrada del usuario. Es muy poco probable que dos módulos de este tipo funcionen adecuadamente juntos en una sola aplicación Perl.

En general, el intérprete de perl se considera el centro del universo en lo que respecta al programa Perl. El código XS se considera una ayuda, para lograr cosas que perl no hace, o no hace lo suficientemente rápido, pero siempre subordinado a perl. Cuanto más se adhiera el código XS a este modelo, menos probable será que ocurran conflictos.

DIAGNÓSTICOS DEL AUTOR

A partir de la versión 3.49, ciertas advertencias están deshabilitadas por defecto. Mientras desarrolla, puede establecer $ENV{AUTHOR_WARNINGS} en verdadero en su entorno o en su Makefile.PL, o establecer $ExtUtils::ParseXS::AUTHOR_WARNINGS en verdadero a través de código, o pasar explícitamente "author_warnings=>1" a process_file(). Actualmente esto habilitará una comprobación de alias más estricta, pero es posible que se agreguen más advertencias en el futuro. El tipo de advertencias que esto habilitará solo es útil para el autor del archivo XS, y los diagnósticos producidos no incluirán detalles específicos de la instalación, por lo que solo son útiles para el mantenedor del código XS en sí.
