NOMBRE

perlsecpolicy - Política de gestión de informes de seguridad de Perl

DESCRIPCIÓN

El proyecto Perl se toma en serio los problemas de seguridad.

La responsabilidad de gestionar los informes de seguridad de manera oportuna y eficaz se ha delegado a un equipo de seguridad compuesto por un subconjunto de los desarrolladores principales de Perl.

Este documento describe cómo opera el equipo de seguridad de Perl y cómo el equipo evalúa los nuevos informes de seguridad.

INFORMAR DE PROBLEMAS DE SEGURIDAD EN PERL

Si cree que ha encontrado una vulnerabilidad de seguridad en el intérprete de Perl o en los módulos mantenidos en la base de código principal de Perl, envíe los detalles por correo electrónico a perl-security@perl.org <mailto:perl-security@perl.org>. Esta dirección es una lista de correo de membresía cerrada monitoreada por el equipo de seguridad de Perl.

Debería recibir una respuesta inicial a su informe dentro de las 72 horas. Si no recibe una respuesta en ese tiempo, póngase en contacto con el Consejo de Dirección de Perl <mailto:steering-council@perl.org>.

Cuando los miembros del equipo de seguridad respondan a sus mensajes, generalmente incluirán la dirección perl-security@perl.org en los campos "Para" o "CC" de la respuesta. Esto permite que todo el equipo de seguridad siga la discusión y participe según sea necesario. Utilice la funcionalidad "Responder a todos" de su cliente de correo electrónico al enviar respuestas posteriores para que todo el equipo de seguridad reciba el mensaje.

El equipo de seguridad evaluará su informe y determinará inicialmente si es probable que se ajuste al alcance de los problemas que el equipo maneja. Las pautas generales sobre cómo se determina esto se detallan en la sección "QUÉ SON LOS PROBLEMAS DE SEGURIDAD".

Si su informe cumple con los criterios del equipo, se le proporcionará el(los) ID(s) CVE del problema. Los identificadores de problemas tienen el formato CVE-AAAA-NNNNN, donde AAAA es el año en que se informó el CVE y NNNNN es un número único. Incluya este identificador con cualquier mensaje posterior que envíe.

El equipo de seguridad enviará actualizaciones periódicas sobre el estado de su problema y lo guiará a través de cualquier acción adicional que sea necesaria para completar el proceso de remediación de la vulnerabilidad. Las etapas por las que pasan típicamente las vulnerabilidades se explican en la sección "CÓMO GESTIONAMOS LOS PROBLEMAS DE SEGURIDAD".

QUÉ SON LOS PROBLEMAS DE SEGURIDAD

Una vulnerabilidad es un comportamiento de un sistema de software que compromete las protecciones esperadas de confidencialidad, integridad o disponibilidad del sistema.

Un problema de seguridad es un error en uno o más componentes específicos de un sistema de software que crea una vulnerabilidad.

El software escrito en el lenguaje de programación Perl generalmente se compone de muchas capas de software escritas por muchos grupos diferentes. Puede ser muy complicado determinar qué capa específica de una aplicación compleja del mundo real fue responsable de prevenir un comportamiento vulnerable, pero esta es una parte esencial de la corrección de la vulnerabilidad.

Software cubierto por el equipo de seguridad de Perl

El equipo de seguridad de Perl maneja problemas de seguridad en:

  • El intérprete de Perl
  • Los módulos de Perl que se envían con el intérprete y que se desarrollan en el repositorio principal de Perl
  • Las herramientas de línea de comandos que se envían con el intérprete y que se desarrollan en el repositorio principal de Perl

Los archivos bajo el directorio cpan/ en el repositorio y las cintas de lanzamiento de Perl se desarrollan y mantienen de forma independiente. El equipo de seguridad de Perl no maneja directamente los problemas de seguridad de estos módulos, pero dado que este código se incluye con Perl, ayudaremos a reenviar el problema al(los) mantenedor(es) relevante(s) y aún puede informarnos estos problemas en secreto.

Errores que pueden calificar como problemas de seguridad en Perl

Perl está diseñado para ser un lenguaje de programación de propósito general, rápido y flexible. El intérprete de Perl y los módulos de Perl facilitan la escritura de aplicaciones seguras, pero tienen limitaciones.

Como regla general, un error en Perl debe cumplir todos los siguientes criterios para ser considerado un problema de seguridad:

  • El comportamiento vulnerable no se menciona en la documentación de Perl ni en el rastreador de problemas público.
  • El comportamiento vulnerable no se implica por un comportamiento esperado.
  • El comportamiento vulnerable no es una limitación generalmente aceptada de la implementación.
  • Es probable que el comportamiento vulnerable quede expuesto a ataques en aplicaciones escritas en Perl que de otro modo serían seguras.
  • El comportamiento vulnerable proporciona un beneficio tangible específico a un atacante que desencadena el comportamiento.

Errores que no califican como problemas de seguridad en Perl

Hay ciertas categorías de errores que se informan frecuentemente al equipo de seguridad que no cumplen con los criterios enumerados anteriormente.

La siguiente es una lista de errores comúnmente informados que no se manejan como problemas de seguridad.

Alimentar código no confiable al intérprete

El analizador de Perl no está diseñado para evaluar código no confiable. Si su aplicación requiere la evaluación de código no confiable, debe depender de un entorno aislado a nivel del sistema operativo para su seguridad.

Desbordamientos de pila debido a recursión excesiva

La recursión excesiva a menudo es causada por código que no impone límites a las entradas. El intérprete de Perl asume que los límites de recursión serán impuestos por la aplicación.

Errores de falta de memoria

Construcciones comunes de Perl como "pack", el operador "x" y las expresiones regulares aceptan cuantificadores numéricos que controlan cuánta memoria se asignará para almacenar valores o resultados intermedios. Si permite que un atacante proporcione estos cuantificadores y consuma toda la memoria disponible, el intérprete de Perl no lo evitará.

Escape de un compartimento seguro

Las restricciones de opcode y los compartimentos seguros no se admiten como mecanismos de seguridad. El analizador de Perl no está diseñado para evaluar código no confiable.

Uso de las plantillas de empaquetado "p" y "P"

Estas plantillas no son seguras por diseño.

Problemas de pila no referenciada

Estos errores típicamente se presentan como errores de uso después de liberado o como fallos de aserción en el tipo de un "SV". Las fallas de pila no referenciada generalmente ocurren porque el código está modificando una referencia o glob y utilizando los valores a los que hace referencia ese glob o referencia.

Este tipo de error es un problema de larga data con el intérprete de Perl que rara vez ocurre en código normal. Los ejemplos de este tipo de error generalmente suponen que el código suministrado por el atacante será evaluado por el intérprete de Perl.

Descongelar datos proporcionados por el atacante con Storable

Storable está diseñado para ser un formato de serialización muy rápido. No está diseñado para ser seguro para deserializar entradas no confiables.

Uso de bases de datos SDBM_File proporcionadas por el atacante

El módulo SDBM_File no está diseñado para usarse con bases de datos SDBM no confiables.

Escalares marcados como UTF-8 mal codificados

Este tipo de error ocurre cuando la capa PerlIO ":utf8" se utiliza para leer datos mal codificados, o se utilizan otros mecanismos para manipular directamente la bandera UTF-8 en un SV.

Un SV marcado como UTF-8 mal codificado no es un SV válido. El código que crea SV de esta manera está corrompiendo el estado interno de Perl.

Problemas que existen solo en blead, o en un candidato a lanzamiento

La rama blead y los candidatos a lanzamiento de Perl no reciben soporte de seguridad. Los defectos de seguridad que solo están presentes en versiones previas al lanzamiento de Perl se manejan a través del proceso normal de informes y resolución de errores.

Módulos CPAN o otros recursos del proyecto Perl

El equipo de seguridad de Perl se enfoca en el intérprete de Perl y los módulos mantenidos en la base de código principal de Perl. El equipo no tiene acceso especial para corregir módulos CPAN,

Comportamientos POSIX emulados en sistemas Windows

El intérprete de Perl intenta emular "fork", "system", "exec" y otros comportamientos POSIX en sistemas Windows. Esta emulación tiene muchas peculiaridades que están ampliamente documentadas en el rastreador de problemas públicos de Perl. Cambiar estos comportamientos causaría una interrupción significativa para los usuarios existentes en Windows.

Errores que requieren categorización especial

Algunos errores en el intérprete de Perl ocurren en áreas del código base que son sensibles a la seguridad y propensas a fallar durante el uso normal.

Expresiones regulares

Las expresiones regulares no confiables son generalmente seguras para compilar y comparar con varias advertencias. Los siguientes comportamientos del motor de expresiones regulares de Perl son responsabilidad del desarrollador de limitarlos.

La evaluación de expresiones regulares no confiables mientras "use re 'eval';" está activa nunca es segura.

No se garantiza que las expresiones regulares se compilen o evalúen en un marco de tiempo finito específico.

Las expresiones regulares pueden consumir toda la memoria disponible del sistema cuando se compilan o evalúan.

Las expresiones regulares pueden causar recursión excesiva que detiene el intérprete de perl.

Como regla general, no espere que el motor de expresiones regulares de Perl sea resistente a ataques de denegación de servicio.

Bases de datos DB_File, ODBM_File o GDBM_File

Estos módulos dependen de bibliotecas externas para interactuar con archivos de bases de datos.

Los errores causados por la lectura y escritura de estos formatos de archivo generalmente son causados por la implementación de la biblioteca subyacente y no son problemas de seguridad en Perl.

Los errores en los que Perl maneja incorrectamente valores de retorno válidos inesperados de las bibliotecas subyacentes pueden calificarse como problemas de seguridad en Perl.

Ataques de complejidad algorítmica

El intérprete de perl es razonablemente robusto frente a ataques de complejidad algorítmica. No es inmune a ellos.

Los errores de complejidad algorítmica que dependen del intérprete que procesa cantidades extremadamente grandes de datos proporcionados por el atacante generalmente no se manejan como problemas de seguridad.

Consulte "Algorithmic Complexity Attacks" en perlsec para obtener información adicional.

CÓMO MANEJAMOS LOS PROBLEMAS DE SEGURIDAD

El equipo de seguridad de Perl sigue prácticas de divulgación responsable. Los problemas de seguridad se mantienen en secreto hasta que una solución esté fácilmente disponible para la mayoría de los usuarios. Esto minimiza los riesgos inherentes que enfrentan los usuarios por vulnerabilidades en Perl.

Ocultar problemas a los usuarios temporalmente es un compromiso necesario para mantenerlos seguros. Ocultar problemas a los usuarios de forma permanente no es el objetivo.

Cuando informa un problema de seguridad de forma privada a la dirección de contacto perl-security@perl.org , normalmente esperamos que siga las prácticas de divulgación responsable en el manejo del informe. Si no puede o no desea mantener el problema en secreto hasta que una solución esté disponible para los usuarios, debe indicarlo claramente en el informe inicial.

El flujo de trabajo de remediación de vulnerabilidades del equipo de seguridad está diseñado para ser lo más abierto y transparente posible sobre el estado de su informe de seguridad.

Flujo de trabajo de remediación de vulnerabilidades de Perl

Contacto inicial

Los nuevos informes de vulnerabilidad recibirán una respuesta inicial dentro de las 72 horas siguientes a su llegada a la lista de correo del equipo de seguridad. Si no recibe ninguna respuesta en ese tiempo, póngase en contacto con el Consejo de Dirección de Perl .

La respuesta inicial enviada por el equipo de seguridad confirmará que su mensaje fue recibido y proporcionará un plazo estimado para el análisis de triaje del equipo de seguridad.

Triaje inicial

El equipo de seguridad evaluará el informe y determinará si es probable que cumpla los criterios para ser tratado como un problema de seguridad.

El equipo de seguridad tiene como objetivo completar el triaje inicial del informe en un plazo de dos semanas. Los problemas complejos que requieran una discusión o investigación significativas pueden llevar más tiempo.

Si el informe de seguridad no se puede reproducir o no cumple los criterios del equipo para ser tratado como un problema de seguridad, se le notificará por correo electrónico y se le dará la oportunidad de responder.

Asignación de CVE

Los informes de seguridad que superan el análisis de triaje inicial se convierten en CVE. Cuando un informe progresa a este punto, el equipo de seguridad reserva uno o más CVE. Los identificadores de problemas tienen el formato CVE-AAAA-NNNNN, donde AAAA es el año en que se informó el CVE y NNNNN es un número único. El CVE se utilizará en cualquier comunicación posterior sobre el problema.

La asignación de estos IDs no confirma que un informe de seguridad represente una vulnerabilidad en Perl. Muchos informes requieren un análisis adicional para llegar a esa determinación. La vulnerabilidad no debe discutirse públicamente en esta etapa.

También se abrirá una incidencia interna. Estos identificadores tienen el formato perl-security#NNN o Perl/perl-security#NNN.

Los problemas en el rastreador privado del equipo de seguridad se utilizan para recopilar detalles sobre el problema y rastrear el progreso hacia una resolución. Estas notas y otros detalles no se hacen públicos cuando se resuelve el problema. Mantener las notas del problema privadas permite al equipo de seguridad discutir libremente métodos de ataque, herramientas de ataque y otros problemas privados relacionados.

Desarrollo de parches

Los miembros del equipo de seguridad inspeccionarán el informe y el código relacionado en detalle para producir correcciones para las versiones compatibles de Perl.

Si el equipo descubre que el problema informado no cumple los criterios del equipo en esta etapa, se le notificará por correo electrónico y se le dará la oportunidad de responder antes de que se cierre el problema.

El equipo puede discutir posibles correcciones con usted o proporcionarle parches para fines de prueba durante este período.

Se redacta el CVE

Una vez que un problema se confirma por completo y se encuentra una posible solución, el equipo de seguridad se comunicará con el Grupo de Seguridad de CPAN CNA https://security.metacpan.org/.

Se deben recopilar detalles como el rango de versiones de Perl vulnerables y las identidades de las personas que descubrieron la falla.

El equipo de seguridad puede pedirle que aclare el nombre exacto que debemos usar al acreditar el descubrimiento del problema. La sección "Crédito de vulnerabilidad y recompensas" de este documento explica nuestro formato preferido para este crédito.

Notificaciones previas al lanzamiento

Cuando el equipo de seguridad esté satisfecho de que la corrección para un problema de seguridad está lista para ser lanzada públicamente, se enviará un anuncio de notificación previa al lanzamiento a la Lista de Distros de Openwall https://oss-security.openwall.org/wiki/mailing-lists/distros. Se notificará a otros empaquetadores adicionales.

NOTA: Cualquier información embargada enviada a la Lista de Distros de Openwall expira dentro de las 2 semanas posteriores a su divulgación a esa ubicación.

Este anuncio previo al lanzamiento incluye una lista de las versiones de Perl afectadas por la falla, un análisis de los riesgos para los usuarios, los parches que el equipo de seguridad ha producido y cualquier información sobre mitigaciones o retroportación de correcciones a versiones anteriores de Perl que el equipo de seguridad tenga disponible.

El anuncio previo al lanzamiento incluirá una fecha objetivo específica para el anuncio público del problema. El período de tiempo entre el anuncio previo al lanzamiento y la fecha de lanzamiento permite a los redistribuidores preparar y probar sus propias actualizaciones y anuncios. Durante este período, los detalles de la vulnerabilidad y las correcciones están embargados (ver "Período de embargo") y no deben compartirse públicamente. Este "Período de embargo" puede extenderse aún más si se descubren problemas durante las pruebas.

Se le enviarán las partes de los anuncios previos al lanzamiento que sean relevantes para el problema específico que informó. Este correo electrónico incluirá la fecha de lanzamiento objetivo. Se enviarán actualizaciones adicionales si la fecha de lanzamiento objetivo cambia.

Pruebas previas al lanzamiento

El equipo de seguridad de Perl no produce directamente lanzamientos oficiales de Perl. El equipo lanza correcciones de seguridad colocando commits en el repositorio público de git de Perl y enviando anuncios.

Muchos usuarios y redistribuidores prefieren utilizar lanzamientos oficiales de Perl en lugar de aplicar parches a una versión anterior. El equipo de seguridad trabaja con los gerentes de lanzamiento de Perl para que esto sea posible.

Los nuevos lanzamientos oficiales de Perl generalmente se producen y prueban en sistemas privados durante el "Período de embargo" previo al lanzamiento.

Lanzamiento de correcciones y anuncios

El "Período de embargo" finaliza cuando las correcciones de seguridad se insertan en el repositorio público de git de Perl. Se enviarán anuncios a las listas de correo perl5-porters https://lists.perl.org/list/perl5-porters.html y oss-security https://oss-security.openwall.org/wiki/mailing-lists/oss-security.

Si los lanzamientos oficiales de Perl están listos, se publicarán en este momento y se anunciarán en la lista de correo perl5-porters https://lists.perl.org/list/perl5-porters.html.

El equipo de seguridad enviará una notificación de seguimiento a todos los que participaron en el "Período de embargo" previo al lanzamiento una vez que finalice el proceso de lanzamiento. Los informantes de vulnerabilidades y los redistribuidores de Perl no deben publicar sus propios anuncios o correcciones hasta que finalice el proceso de lanzamiento del equipo de seguridad de Perl.

Problemas de seguridad públicamente conocidos y de día cero

El flujo de trabajo de remediación de vulnerabilidades del equipo de seguridad asume que los problemas se informan de forma privada y se mantienen en secreto hasta que se resuelven. Este no siempre es el caso y la información ocasionalmente se filtra antes de que una solución esté lista.

En estas situaciones, el equipo debe decidir si operar en secreto aumenta o disminuye el riesgo para los usuarios de Perl. En algunos casos, ser abierto sobre el riesgo que crea un problema de seguridad permitirá a los usuarios

Handling of security issues by the Perl security team

The Perl security team uses the following policy for handling security issues discovered in Perl.

A security issue is any bug in Perl which may allow for unauthorized access to a system, or that may cause denial of service or data corruption.

The Perl security team prefers to handle security issues privately and responsibly. If you find a security issue then please report it to perl-security@perl.org <mailto:perl-security@perl.org>.

The team will work with you to try to get a fix out to the public as quickly as possible.

Coordinated disclosure

Perl follows a policy of coordinated disclosure. This means that when a security issue is found, the Perl security team will work with the discoverer of the issue to get a fix prepared and released to the public. The details of the issue will not be released until a fix is available. This protects users from being attacked while fixes are being prepared.

When details of a security issue are disclosed

Details of a security issue are disclosed when a fix is available in the public repository. This is typically done via email announcements to mailing lists such as perl5-porters <https://lists.perl.org/list/perl5-porters.html> and oss-security <https://oss-security.openwall.org/wiki/mailing-lists/oss-security>, and the issue is documented in the public defect tracker.

This ensures that users are aware of the issue and can update their installations promptly.

Publicity and zero-days

The Perl security team generally avoids publicizing security issues until a fix is available. In some cases, making an issue public before a fix is ready can be harmful, as it may alert attackers to a vulnerability they were not previously aware of.

However, if a critical security issue is already being actively exploited in the wild (a "zero-day" exploit), the security team will prioritize rapid communication of available mitigations and fixes. In such cases, announcements may be made sooner, and the public defect tracker will be used to provide timely updates on the progress of the fix.

The decision to disclose information about a security issue before a fix is available will be made on a case-by-case basis, considering the potential risks and benefits. The primary goal is always to protect the users of Perl.

Other leaks of security issue information

Depending on the prominence of the information revealed about a security issue and the issue's risk of becoming a zero-day attack, the security team may skip all or part of its normal remediation workflow.

If the security team learns of a significant security issue after it has been identified and resolved in Perl's public issue tracker, the team will request a CVE ID and send an announcement to inform users.

Vulnerability credit and bounties

The Perl project appreciates the effort security researchers invest in making Perl safe and secure.

Since much of this work is hidden from the public, crediting researchers publicly is an important part of the vulnerability remediation process.

Credits in vulnerability announcements

When security issues are fixed we will attempt to credit the specific researcher(s) that discovered the flaw in our announcements.

Credits are announced using the researcher's preferred full name.

If the researcher's contributions were funded by a specific company or part of an organized vulnerability research project, we will include a short name for this group at the researcher's request.

Perl's announcements are written in the English language using the 7bit ASCII character set to be reproducible in a variety of formats. We do not include hyperlinks, domain names or marketing material with these acknowledgments.

In the event that proper credit for vulnerability discovery cannot be established or there is a disagreement between the Perl security team and the researcher about how the credit should be given, it will be omitted from announcements.

Bounties for Perl vulnerabilities

The Perl project is a non-profit volunteer effort. We do not provide any monetary rewards for reporting security issues in Perl.

Embargo Period

In the context of Perl's coordinated vulnerability disclosure process, an "embargo" refers to the period of time during which information about a reported vulnerability is kept confidential. This embargo begins when a security issue is reported to the Perl security team and lasts until a fix has been developed and a fix is provided in a public location.

The purpose of the embargo is to allow the security team to work on a fix and prepare a coordinated release without the risk of the vulnerability being exploited or disclosed prematurely. This helps ensure that users of Perl and its modules are protected from potential attacks while the security issue is being addressed.

Embargo lengths can vary depending on the complexity of the issue and the time required to develop a fix. The security team will communicate the expected duration of the embargo to the reporter and any other parties involved in the process.

As a goal, the security team aims to keep the total embargo period to less than 60 days. This may be extended due to the following factors:

  • The complexity of the issue
  • The time required to develop a fix
  • The need for additional testing or validation
  • The availability of resources to address the issue
  • Public holidays which might affect the ability of end users to apply the fix.

During this period:

  • Details of the vulnerability are shared only with a restricted group of trusted contributors (such as core maintainers, toolchain maintainers, and packagers), solely for the purpose of preparing and testing a fix.
  • Reporters are asked not to disclose the issue publicly or share details with third parties until the embargo is lifted.
  • The duration of the embargo may vary depending on the severity and complexity of the issue, but typically lasts until the relevant security patch is released and announced.
  • Breaking the embargo — by prematurely disclosing details — undermines the coordinated disclosure process and can hinder the coordinated effort to protect users effectively.

The Perl security team strives to resolve vulnerabilities promptly and encourages all parties to respect the embargo period to help protect users and downstream distributions.

Example Release Process

This section provides an example of how a security issue reported by a third party might be handled by the Perl security team, from the initial report to the final release.

Step 1: Reporting the Vulnerability

A security researcher discovers a vulnerability in the Perl interpreter that allows an attacker to cause a denial of service under specific conditions. The researcher emails the details of the issue to perl-security@perl.org <mailto:perl-security@perl.org>, including a proof-of-concept script and a description of the impact.

Step 2: Initial Response

Within 72 hours, the security team acknowledges receipt of the report and confirms that the issue is under investigation. The researcher is informed of the expected timeline for triage.

Step 3: Initial Triage

The security team reproduces the issue using the provided proof-of-concept and determines that it meets the criteria for handling as a security issue. One or more CVEs are reserved in coordination with the CPAN Security Group CNA https://security.metacpan.org/2025/02/25/cpansec-is-cna-for-perl-and-cpan.html. The team notifies the researcher referencing the CVE IDs.

Step 4: Development of a Fix

The security team analyzes the affected code and develops a patch to address the vulnerability. The patch is tested against various scenarios to ensure it resolves the issue without introducing regressions. The researcher is invited to test the patch privately and provide feedback.

Step 5: Pre-Release Notification

The security team prepares a pre-release notification, including details of the vulnerability, the affected Perl versions, and the patch. This notification is sent to major redistributors of Perl under embargo, giving them time to prepare their own updates.

Step 6: Pre-Release Testing

During the remaining embargo period, pre-notified redistributors prepare packages for release and test the patch to ensure compatibility with their systems.

Step 7: Public Release

On the scheduled release date, the patch is committed to Perl's public git repository. An official announcement is sent to the perl5-porters https://lists.perl.org/list/perl5-porters.html and oss-security https://oss-security.openwall.org/wiki/mailing-lists/oss-security mailing lists. If applicable, a new Perl release containing the fix is published.

The security team will notify CPAN Security Group CNA to publish the CVE.

Step 8: Vendor and Third-Party Updates

Vendors and third-party maintainers incorporate the patch or updated Perl release into their distributions. The security team follows up with all parties involved to ensure the issue is resolved and users are protected.
