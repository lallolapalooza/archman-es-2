psusan(1) Conjunto de herramientas PuTTY psusan(1)

NOMBRE

psusan - pseudo-SSH para redes no espiables y autenticadas por separado

SINOPSIS

psusan [ opciones ]

DESCRIPCIÓN

psusan es un programa servidor que se comporta como la capa más interna de `conexión' de una sesión SSH, sin las dos capas de seguridad exteriores de cifrado y autenticación. Proporciona todas las características posteriores a la autenticación de una conexión SSH:

•
elegir si ejecutar una sesión de terminal interactiva o un único comando especificado
•
múltiples sesiones de terminal a la vez (o una mezcla de estas y comandos especificados)
•
transferencia de archivos SFTP
•
todas las opciones estándar de reenvío de puertos SSH
•
reenvío X11
•
reenvío de agente SSH

La pega es que, al carecer de las capas exteriores de SSH, tienes que ejecutarlo sobre algún tipo de canal de datos que ya esté autenticado como el usuario correcto, y que ya esté protegido a tu satisfacción contra el espionaje y el secuestro de sesiones. Una buena regla general es que cualquier canal sobre el que estuvieras dispuesto a ejecutar una sesión de shell *sin formato*, puedes ejecutar psusan en su lugar, lo que añade todas las comodidades mencionadas sin cambiar las propiedades de seguridad.

El protocolo que habla psusan también lo hablan PuTTY, Plink, PSCP y PSFTP, si seleccionas el tipo de protocolo `Bare ssh-connection' o la opción de línea de comandos -ssh-connection y especificas la ruta absoluta al socket de dominio Unix apropiado en lugar de un nombre de host.

EJEMPLOS

La idea de un canal de datos seguro y preautenticado parece extraña a la gente que piensa en conexiones de *red*. Pero hay muchos ejemplos en el contexto de un único sistema Unix, y ahí es donde psusan suele ser útil.

Docker

Un buen ejemplo es el canal de consola o E/S estándar que conduce a un contenedor o sistema de virtualización. Docker es un ejemplo familiar. Si quieres iniciar un contenedor Docker y ejecutar un shell directamente dentro de él, podrías decir algo como

docker run -i -t alguna:imagen

lo que te permitirá ejecutar una única sesión de shell dentro del contenedor, en la misma terminal desde la que iniciaste Docker.

Supongamos que prefieres ejecutar *múltiples* sesiones de shell en el mismo contenedor a la vez (quizás para que una de ellas pueda usar herramientas de depuración para hurgar en lo que hace otra). Y quizás dentro de ese contenedor vas a ejecutar un programa en el que no confías con acceso completo a tu red, pero estás preparado para permitirle establecer una o dos conexiones de red específicas del tipo que podrías configurar con un reenvío de puertos SSH.

En ese caso, puedes eliminar la opción -t de esa línea de comandos de Docker (que significa `asignar un dispositivo de terminal'), y decirle que ejecute psusan dentro del contenedor:

docker run -i alguna:imagen /ruta/alguna/hacia/psusan

(Por supuesto, tendrás que asegurarte de que psusan esté instalado en algún lugar dentro de la imagen del contenedor.)

Si haces eso desde una línea de comandos de shell, verás una línea de encabezado que se parece a esto:

SSHCONNECTION@putty.projects.tartarus.org-2.0-PSUSAN_Release_0.75

lo cual no es particularmente útil, excepto que te dice que psusan se ha iniciado correctamente.

Para hablar con este servidor de forma *útil*, puedes configurar una sesión guardada de PuTTY de la siguiente manera:

•
Establece el protocolo en `Bare ssh-connection' (el protocolo psusan).
•
Escribe *algo* en el campo del nombre de host. Aparecerá en el título de la ventana de PuTTY (si ejecutas PuTTY gráfico), por lo que puede que quieras escribir algo que te recuerde qué tipo de ventana es. Si no tienes preferencia, algo genérico como `dummy' servirá.
•
En el panel de configuración `Proxy', establece el tipo de proxy en `Local', e introduce el comando `docker run' anterior en el campo de edición `Telnet command, or local proxy command'.
•
En el panel de configuración `SSH', es muy probable que quieras activar el uso compartido de conexiones. (Ver más abajo.)

Esto hace que cuando PuTTY se inicie, ejecute el comando Docker como se muestra arriba en lugar de hacer una conexión de red, y hable con ese comando usando el protocolo tipo SSH de psusan.

El efecto es que todavía obtendrás una sesión de shell en el contexto de un contenedor Docker. Pero esta vez, tiene todas las comodidades de SSH. Si también activas el uso compartido de conexiones en la configuración `SSH', entonces la opción `Duplicate Session' te dará un segundo shell en el *mismo* contenedor Docker (en lugar de un shell primario en una instancia separada). Puedes transferir archivos hacia y desde el contenedor mientras se ejecuta usando PSCP o PSFTP; puedes reenviar puertos de red, programas X11 y/o un agente SSH al contenedor.

Por supuesto, otra forma de hacer todo esto sería ejecutar el protocolo SSH *completo* sobre el mismo canal. Esto implica más configuración: tienes que inventar una clave de host SSH para el contenedor, aceptarla en el cliente, y lidiar con que quede en la caché de claves de host de tu cliente cuando se deseche el contenedor. Y tienes que configurar algunos detalles de inicio de sesión en el contenedor: o bien configurar una contraseña y escribirla en el cliente, o copiar la mitad pública de alguna clave SSH que ya tuvieras. Y todas estas incomodidades son *innecesarias*, porque son precauciones que necesitas tomar cuando la conexión entre dos sistemas va a través de una red hostil. En este caso, solo va a través de un canal IPC del kernel que garantiza ir al lugar correcto, por lo que esas precauciones de seguridad son redundantes, y solo añaden torpeza.

Linux en modo de usuario

Linux en modo de usuario es otro tipo de contenedor al que puedes hablar de la misma manera. Aquí tienes un pequeño ejemplo práctico.

La forma *más sencilla* de ejecutar UML es usar su tipo de sistema de archivos `hostfs' para dar al kernel invitado acceso al mismo sistema de archivos virtual que tienes en el host. Por ejemplo, una línea de comandos como esta te da un prompt de shell dentro de una instancia de UML que comparte tu sistema de archivos existente:

linux mem=512M rootfstype=hostfs rootflags=/ rw init=/bin/bash

Si ejecutas esto en una línea de comandos (asumiendo que tienes un kernel UML disponible en tu PATH bajo el nombre `linux'), entonces deberías ver muchos mensajes de inicio del kernel, seguidos de un prompt de shell parecido a

root@(none):/#

Para convertir esto en una sesión UML basada en psusan, necesitamos ajustar la línea de comandos para que en lugar de ejecutar bash, ejecute psusan. Pero ejecutar psusan directamente no es suficiente, porque psusan dependerá de una pequeña cantidad de configuración, como tener /proc montado. Así que en su lugar, establecemos el proceso init a un script de shell que hará la configuración necesaria y *luego* invocará a psusan.

Además, ejecutar psusan directamente sobre el dispositivo de consola UML es una mala idea, porque entonces el protocolo binario de psusan se mezclará con los mensajes de texto de la consola. Así que un mejor plan es redirigir la consola de UML al error estándar del proceso linux, y mapear su entrada y salida estándar a un puerto serie. Por lo que la línea de comandos UML de reemplazo podría parecer algo así:

linux mem=512M rootfstype=hostfs rootflags=/ rw \
        con=fd:2,fd:2 ssl0=fd:0,fd:1 init=/ruta/alguna/hacia/uml-psusan.sh

Y el script de configuración uml-psusan.sh podría parecerse a esto:

#!/bin/bash
# Configurar pseudosisistemas de archivos vitales
mount -t proc none /proc
mount -t devpts none /dev/pts
# Redirigir E/S al puerto serie, pero stderr a la consola
exec 0<>/dev/ttyS0 1>&0 2>/dev/console
# Poner el puerto serie en modo raw, para ejecutar un protocolo binario
stty raw -echo
# Elegir qué shell quieres ejecutar dentro de psusan
export

Linux User Mode Linux

UML is a way of running a full Linux kernel as an ordinary user-level process. The user-mode Linux kernel itself then runs other user-level processes inside it.

When you use UML, you'll typically want to start it up with a command that specifies how it's to be launched. A common way to do this is to provide a shell script that will be executed by the UML kernel upon startup. This script could look something like this:

00A0;SHELL=/bin/bash
# Set up a default path
export PATH=/usr/local/bin:/usr/local/sbin:/usr/bin:/usr/sbin:/bin:/sbin
# And now run psusan over the serial port
exec /home/simon/src/putty/misc/psusan

Now set up a PuTTY saved session as in the Docker example above. Basically you'll want to use the above linux command as the local proxy command. However, it's worth wrapping it in setsid(1), because when UML terminates, it kills its entire process group. So it's better that PuTTY should not be part of that group, and should have the opportunity to shut down cleanly by itself. So probably you end up setting the proxy command to be something more like:

setsid linux mem=512M rootfstype=hostfs rootflags=/ rw \
    con=fd:2,fd:2 ssl0=fd:0,fd:1 init=/some/path/to/uml-psusan.sh

You may also find that you have to enable the bug workaround that indicates that the server `Discards data sent before its greeting', because otherwise PuTTY's outgoing protocol greeting can be accidentally lost during UML startup. (See Debian bug #991958.)

Once you've done that, you'll have a PuTTY session that starts up a clean UML instance when you run it, and (if you enabled connection sharing) further instances of the same session will connect to the same instance again.

Windows Subsystem for Linux

On Windows, the default way to use WSL is to run the wsl program, or one of its aliases, in a Windows console, either by launching it from an existing command prompt, or by using a shortcut that opens it in a fresh console. This gives you a Linux terminal environment, but in a Windows console window.

If you'd prefer to interact with the same environment using PuTTY as the terminal (for example, if you prefer PuTTY's mouse shortcuts for copy and paste), you can set it up by installing psusan in the Linux environment, and then setting up a PuTTY saved session that talks to it. A nice way to do this is to use the name of the WSL distribution as the `host name':

•
set the local proxy command to `wsl -d %host /usr/local/bin/psusan' (or wherever you installed psusan in the Linux system)
•
enter the name of a particular WSL distribution in the host name box. (For example, if you installed WSL Debian in the standard way from the Windows store, this will just be `Debian'.)
•
set the protocol to `Bare ssh-connection', as usual.

Like all the other examples here, this also permits you to forward ports in and out of the WSL environment (e.g. expose a WSL2 network service through the hypervisor's internal NAT), forward Pageant into it, and so on.

Cygwin

Another Unix-like environment on Windows is Cygwin. That comes with its own GUI terminal application, mintty (as it happens, a derivative of PuTTY); but if you'd prefer to use PuTTY itself to talk to your Cygwin terminal sessions, psusan can help.

To do this, you'll first need to build the Unix PuTTY tools inside Cygwin (via the usual cmake method). Then, copy the resulting psusan.exe into Cygwin's /bin directory. (It has to be in that directory for non-Cygwin programs to run it; otherwise it won't be able to find the Cygwin DLL at startup.)

Then set up your PuTTY saved session like this:

•
set the local proxy command to run psusan.exe via its real Windows path. You might also want to add the --sessiondir option so that shell sessions start up in your Cygwin home directory. For example, you might use the command `c:\cygwin64\bin\psusan.exe --sessiondir /home/simon' (changing the pathname and username to match your setup).
•
enter anything you like in the host name box; `Cygwin' is probably a good choice
•
set the protocol to `Bare ssh-connection', as usual.

Port forwarding is probably not particularly useful in this case, since Cygwin shares the same network port space as the host machine. But turning on agent forwarding is useful, because then the Cygwin command-line SSH client can talk to Pageant without any further configuration.

schroot

Another example of a container-like environment is the alternative filesystem layout set up by schroot(1).

schroot is another program that defaults to running an interactive shell session in the terminal you launched it from. But again, you can get a psusan connection into the schroot environment by setting up a PuTTY saved session whose local proxy command is along the lines of

schroot -c chroot-name /some/path/to/psusan

Depending on how much of the chroot environment is copied from your main one, you might find this makes it easier to (for example) run X11 programs inside the chroot that open windows on your main X display, or transfer files in and out of the chroot.

Between network namespaces

If you've set up multiple network namespaces on a Linux system, with different TCP/IP configurations, then psusan can be a convenient unprivileged-user gateway between them, if you run it as a non-root user in the non-default one of your namespaces, listening for connections on a Unix-domain socket.

If you do that, then it gives you convenient control over which of your outgoing network connections use which TCP/IP configuration: you can use PuTTY to run a shell session in the context of the other namespace if you want to run commands like ping, or you can set up individual port forwardings or even a SOCKS server so that processes running in one namespace can send their network connections via the other one.

For this application, it's probably most convenient to use the --listen option in psusan, which makes it run as a server and listen for connections on a Unix-domain socket. Then you can enter that socket name in PuTTY's host name configuration field (and also still select the `Bare ssh-connection' protocol option), to connect to that socket as if it were an SSH client.

Provided the Unix-domain socket is inside a directory that only the right user has access to, this will ensure that authentication is done implicitly by the Linux kernel.

Between user ids, via GNU userv

If you use multiple user ids on the same machine, say for purposes of privilege separation (running some less-trusted program with limited abilities to access all your stuff), then you probably have a `default' or most privileged account where you run your main login session, and sometimes need to run a shell in another account.

psusan can be used as an access channel between the accounts, using GNU userv(1) as the transport. In the account you want to access, write a userv configuration stanza along the lines of

if (glob service psusan & glob calling-user my-main-account-name)
   reset
   execute /some/path/to/psusan
fi

This gives your main account the right to run the command

userv my-sub-account-name psusan

and you can configure that command name as a PuTTY local proxy command, in the same way as most of the previous examples.

Of course, there are plenty of ways already to access one local account from another, such as sudo. One advantage of doing it this way is that you don't need the system administrator to intervene when you want to change the access controls (e.g. change which of your accounts have access to another): as long as you have some means of getting into each account in the first place, and userv is installed, you can make further configuration changes without having to bother root about it.

Another advantage is that it might make file transfer between the accounts easier. If you're the kind of person who keeps your home directories private, then it's awkward to copy a file from one of your accounts to another just by using the cp command, because there's nowhere convenient that you can leave it in one account where the other one can read it. But with psusan over userv, you don't need any shared piece of filesystem: you can scp files back and forth without any difficulty.

OPTIONS

The command-line options supported by psusan are:

--listen unix-socket-name
Run psusan in listening mode. unix-socket-name is the pathname of a Unix-domain socket to listen on. You should ensure that this pathname is inside a directory whose read and exec permissions are restricted to only the user(s) you want to be able to access the environment that psusan is running in.

The listening socket has to be a Unix-domain socket. psusan does not provide an option to run over TCP/IP, because the unauthenticated nature of the protocol would make it inherently insecure.

--listen-once
In listening mode, this option causes psusan to listen for only one connection, and exit immediately after that connection terminates.
--sessiondir pathname
This option sets the directory that shell sessions and subprocesses will start in. By default it is psusan's own working directory, but in some situations it's easier to change it with a command-line option than by wrapping psusan in a script that changes directory before starting it.
-v, --verbose
This option causes psusan to print verbose log messages on its standard error. This is probably most useful in listening mode.
-sshlog logfile

-sshrawlog logfile

-sshrawlog logfile
Estas opciones hacen que psusan registre detalles del protocolo en un archivo, de manera similar a las opciones de registro en PuTTY y Plink.

-sshlog registra paquetes SSH decodificados y otros eventos (aquellos que -v imprimiría). -sshrawlog adicionalmente registra los datos brutos de la red, incluyendo el formato de paquete externo y los saludos iniciales.
