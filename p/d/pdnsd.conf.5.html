PDNSD.CONF(5) Manual de formatos de archivo PDNSD.CONF(5)

NOMBRE

pdnsd.conf - El archivo de configuración para pdnsd

DESCRIPCIÓN

Esta página del manual describe la disposición del archivo de configuración de pdnsd(8) y las opciones de configuración disponibles. La ubicación predeterminada del archivo es /etc/pdnsd.conf. Esto puede cambiarse con la opción de línea de comandos -c. Un ejemplo de pdnsd.conf viene con la distribución de pdnsd en el directorio de documentación o en /etc/pdnsd.conf.sample.

FORMATO DEL ARCHIVO

El archivo de configuración se divide en secciones. Cada sección va precedida por el nombre de la sección y llaves de apertura ({) y se cierra con llaves de cierre (}). En cada sección, las opciones de configuración se pueden dar en el formato

nombre_opcion=valor_opcion;

El valor de la opción puede ser una cadena literal, un número, una especificación de tiempo o una constante. En versiones anteriores de pdnsd, las cadenas debían ir entre comillas ("), pero desde la versión 1.1.10 ya no es necesario, a menos que una cadena contenga un carácter especial como espacio en blanco, un token que normalmente inicia un comentario, o uno de ",;{} Desde la versión 1.2.9, una barra invertida (\) dentro de una cadena se interpreta como un carácter de escape, por lo que es posible incluir caracteres especiales en cadenas (tanto entre comillas como sin ellas) precediéndolos con una barra invertida. Algunas secuencias de escape se interpretan como en el lenguaje de programación C, por ejemplo \t se convierte en una tabulación, \0 se convierte en un carácter de control de nueva línea.
Una especificación de tiempo consiste en una secuencia de dígitos seguida de un sufijo de una letra. Los siguientes sufijos son reconocidos: s (segundos), m (minutos), h (horas), d (días) y w (semanas). Si falta el sufijo, se asumen segundos. Si se concatenan varias especificaciones de tiempo, sus valores se suman; por ejemplo, 2h30m se interpreta como 2*60*60 + 30*60 = 9000 segundos.
Algunas opciones toman más de un valor; en este caso, los valores se separan con comas.
Si se puede proporcionar uno de un conjunto de valores posibles a una opción, esto se indica en la documentación como (opcion1|opcion2|opcion3|...)
Las constantes true|false y yes|no se aceptan como sinónimos de las constantes on|off.
Los comentarios pueden ir entre /* y */, los comentarios anidados son posibles. Si el signo # o dos barras (//) aparecen en el archivo de configuración, todo lo que va desde estos signos hasta el final de la línea actual se considera un comentario y se ignora.
Hay ejemplos para casi todas las opciones en el archivo de configuración de muestra.

Sección global

La sección global especifica parámetros que afectan el comportamiento general del servidor. Si especifica varias secciones globales, la configuración de las últimas en el archivo sobrescribirá los valores dados anteriormente.
Estas son las opciones posibles:

perm_cache=(número|off);
Desactivar la caché en disco o proporcionar un tamaño máximo de caché en kB. Si la caché en disco está desactivada, todavía se escribirán 8 bytes en el disco. La caché de memoria siempre es 10kB más grande que la caché de archivo. Este valor es 2048 (2 MB) por defecto.
cache_dir=cadena;
Establecer el directorio donde desea mantener la caché. El valor predeterminado es "/var/cache/pdnsd" (a menos que pdnsd se haya compilado con un valor predeterminado diferente).
server_port=número;
Establecer el puerto del servidor. Esto es especialmente útil cuando se desea iniciar el servidor y no se es root. Tenga en cuenta que tampoco puede especificar uptest=ping en la sección del servidor como no root.
El puerto predeterminado es 53, el estándar RFC. Tenga en cuenta que solo debe usar puertos no estándar cuando solo necesite que los clientes de su máquina se comuniquen con el servidor; otros probablemente fallarán si intentan contactar al servidor basándose en un registro NS, ya que el registro A que proporciona la dirección para (entre otros) los servidores de nombres no tiene una especificación de número de puerto.
server_ip=cadena;
o
interface=cadena;
Establecer la dirección IP en la que escucha pdnsd las solicitudes. Esto puede ser útil cuando el host tiene varias interfaces y desea que pdnsd no escuche en todas las interfaces. Por ejemplo, es posible vincular pdnsd para que escuche en 127.0.0.2 para permitir que pdnsd sea un reenviador para BIND. La configuración predeterminada para esta opción es server_ip=any, lo que significa que pdnsd escuchará en todas sus interfaces locales. Actualmente solo puede especificar una dirección aquí; si desea que pdnsd escuche en múltiples interfaces pero no en todas, deberá especificar server_ip=any y usar reglas de firewall para restringir el acceso.
La dirección IP solía necesitar comillas alrededor, pero desde la versión 1.1.10 ya no es necesario.
Si pdnsd se ha compilado con soporte para IPv4 e IPv6, y desea especificar una dirección IPv6 aquí, entonces a menos que pdnsd se haya compilado para iniciarse en modo IPv6 de forma predeterminada, deberá usar la opción de línea de comandos -6 o establecer run_ipv4=off primero (ver más abajo) para garantizar que la dirección IPv6 se interprete correctamente.
Si pdnsd se está ejecutando en modo IPv6 y especifica una dirección IPv4 aquí, se mapeará automáticamente a una dirección IPv6.
Nuevo en la versión 1.2: También puede dar el nombre de una interfaz, como "lo" o "eth0", aquí, en lugar de una dirección IP (esto se ha probado en Linux y puede funcionar o no en otras plataformas). pdnsd no se vinculará al nombre de la interfaz, sino que buscará la dirección de la interfaz al inicio y escuchará en esa dirección. Si la dirección de la interfaz cambia mientras pdnsd se está ejecutando, pdnsd no lo notará. Deberá reiniciar pdnsd en ese caso.
outgoing_ip=cadena;
o
outside_interface=cadena;
Nuevo en la versión 1.2.9: Establecer la dirección IP de la interfaz utilizada por pdnsd para las consultas salientes. Esto puede ser útil cuando el host tiene varias interfaces y desea que pdnsd envíe consultas salientes solo a través de una de ellas. Por ejemplo, si pdnsd se está ejecutando en un host con una interfaz con dirección IP 192.168.1.1 conectada a la red local, y otra con dirección IP 123.xxx.yyy.zzz conectada a Internet, puede especificar server_ip=192.168.1.1 y outgoing_ip=123.xxx.yyy.zzz para garantizar que pdnsd solo responda a las consultas recibidas de la red local y solo envíe consultas salientes a través de la interfaz conectada a Internet.
La configuración predeterminada para esta opción es any, lo que significa que el kernel es libre de decidir qué interfaz usar. Al igual que con la opción server_ip, también puede dar el nombre de una interfaz aquí, en lugar de una dirección IP.
linkdown_kluge=(on|off);
Esta opción habilita una solución improvisada que algunas personas pueden necesitar: cuando todos los servidores están marcados como caídos, con esta opción activada, la caché no se utiliza incluso cuando se recibe una consulta, y se devuelve un error DNS en cualquier caso. La única excepción es que los registros locales (como se especifica en las secciones rr y source) todavía se sirven normalmente. En general, probablemente querrá obtener entradas cacheadas incluso cuando la red está caída, por lo que esto está desactivado por defecto.
max_ttl=tiempospec;
Esta opción establece el tiempo máximo que un registro permanece en la caché. Todos los registros de recursos DNS tienen un campo de tiempo de vida (time to live) que indica durante qué período de tiempo el registro puede ser cacheados antes de que necesite ser consultado de nuevo. Si esto es más que el valor dado con max_ttl, este valor de tiempo de vida se establece en max_ttl. Esto se hace para evitar que los registros se cachen durante un período de tiempo inapropiadamente largo, ya que eso casi nunca es algo bueno. El valor predeterminado es 604800s (una semana).
min_ttl=tiempospec;
Esta opción establece el tiempo mínimo que un registro permanece en la caché. Todos los registros de recursos DNS tienen un campo de tiempo de vida que indica durante qué período de tiempo el registro puede ser cacheados antes de que necesite ser consultado de nuevo. Si esto es menor que el valor dado con min_ttl, este valor de tiempo de vida se establece en min_ttl. El valor predeterminado es 120 segundos.
neg_ttl=tiempospec;
Esta opción establece el tiempo que los registros cacheados negativamente seguirán siendo válidos en la caché si no se puede determinar un tiempo de vida. Esto siempre ocurre cuando se están cacheando dominios enteros negativamente, y además cuando se cachean tipos de registro nega

neg_rrs_pol=(on|off|auth|default);
Esto establece la política de RR set para el caché negativo; esto le dice a pdnsd bajo qué circunstancias debe almacenar en caché un tipo de registro negativamente para un dominio determinado. `off` desactivará el caché negativo de tipos de registro, `on` siempre añadirá una entrada de caché negativa cuando un servidor de nombres no devuelva un tipo de registro que le solicitamos, y `auth` solo añadirá dichas entradas si la respuesta provino de un servidor de nombres autoritativo para ese dominio.
Nuevo en la versión 1.2.8: La configuración `default` añadirá un registro almacenado en caché negativamente si la respuesta fue autoritativa o si la respuesta indicó que el servidor de nombres tenía "recursión disponible" mientras la consulta solicitaba explícitamente dicha recursión.
El preestablecido es "default" (antes era auth).
neg_domain_pol=(on|off|auth);
Esto es análogo a `neg_rrs_pol` para el caché negativo de dominios completos. Debería ser seguro configurarlo en `on`, ya que no he visto un servidor de caché que afirme falsamente que un dominio no existe.
El predeterminado es `auth`.
run_as=string;
Esta opción te permite que pdnsd cambie su ID de usuario y grupo después de que se hayan realizado las operaciones que necesitaban privilegios. Esto ayuda a minimizar los riesgos de seguridad y, por lo tanto, se recomienda. La cadena proporcionada da un nombre de usuario cuyos ID de usuario y grupo primario se toman.
Un poco más de detalles: después de leer el archivo de configuración, convertirse en un demonio (si se especifica) y iniciar el hilo de estado del servidor, el hilo principal cambia su gid y uid, al igual que todos los hilos creados posteriormente. Al tomar otro uid y gid, esos hilos se ejecutan con los privilegios del usuario especificado. En Linux y FreeBSD, el hilo de estado del servidor se ejecuta con los privilegios originales solo cuando la opción `strict_setuid` está configurada en `off` (ver más abajo, activada por defecto), ya que estos pueden ser necesarios para las pruebas de `exec`. El hilo del administrador también conserva sus privilegios originales en este caso. Debes asegurarte de que el usuario que especifiques tenga permisos de escritura en tu archivo de caché y en la tubería de estado (si necesitas una tubería de estado). Debes prestar atención a mensajes de error como "permission denied" y "operation not permitted" para detectar problemas de permisos.
strict_setuid=(on|off);
Cuando se usa junto con la opción `run_as`, esta opción te permite especificar que todos los hilos del programa se ejecutarán con los privilegios del usuario `run_as`. Esto proporciona una mayor seguridad que la opción `run_as` normal, pero no siempre es posible. Ver la opción `run_as` para una mayor discusión.
Esta opción está activada por defecto.
Ten en cuenta que esta opción no tiene efecto en sistemas que no sean Linux.
paranoid=(on|off);
Normalmente, pdnsd consulta a todos los servidores en modo recursivo (es decir, instruye a los servidores para que consulten a otros servidores si es posible, y para que devuelvan respuestas para dominios que pueden no estar en su autoridad), y acepta registros adicionales con información para servidores que no están en la autoridad del servidor consultado. Esto abre la posibilidad de un llamado envenenamiento de caché: un atacante malicioso podría configurar un servidor DNS que, al ser consultado, devuelva registros adicionales falsificados. De esta manera, podría reemplazar servidores de confianza con los suyos al hacer que su servidor DNS devuelva direcciones IP incorrectas. Esta opción lo protege del envenenamiento de caché al rechazar registros adicionales que no describen dominios en el espacio de autoridad de los servidores consultados y al dejar de realizar consultas recursivas. Una excepción a esta regla son los servidores que especifica en su archivo de configuración, los cuales son de confianza.
La penalización es una posible disminución del rendimiento, en particular, podrían ser necesarias más consultas para la misma operación.
También debe notar que puede haber otros problemas de seguridad similares, que son esencialmente problemas del DNS, es decir, cualquier servidor "tradicional" los tiene (las extensiones de seguridad DNS resuelven estos problemas, pero no están ampliamente soportadas). Una de estas vulnerabilidades es que un atacante puede bombardearlo con respuestas falsificadas con la esperanza de que alguna coincida con una consulta que haya realizado. Si ha realizado una consulta de este tipo, una de cada 65536 paquetes será exitosa (es decir, se necesita un promedio de 32768 paquetes para ese ataque). pdnsd puede usar TCP para las consultas, lo que tiene una sobrecarga ligeramente mayor, pero es mucho menos vulnerable a tales ataques en sistemas operativos sanos. Además, pdnsd elige IDs de consulta aleatorios, de modo que un atacante no pueda tomar un atajo. Si el atacante puede escuchar su tráfico de red, este ataque es relativamente fácil, aunque.
Esta vulnerabilidad no es culpa de pdnsd, y es posible usando cualquier servidor de nombres convencional (pdnsd es quizás un poco más seguro contra este tipo de ataques si lo hace usar TCP).
La opción `paranoid` está desactivada por defecto.
ignore_cd=(on|off);
Nuevo en la versión 1.2.8: Esta opción le permite especificar que se ignorará el bit CD de una consulta DNS. De lo contrario, pdnsd responderá FORMERR a los clientes que establezcan este bit en una consulta. Es seguro habilitar esta opción, ya que el bit CD se refiere a 'Checking Disabled' (Comprobación Desactivada), lo que significa que el cliente aceptará datos no autenticados.
Esta opción está activada por defecto. Desactívela si desea el comportamiento anterior (antes de la versión 1.2.8).
scheme_file=string;
Además de las pruebas de `uptests` normales, puede especificar que algunos servidores solo se consultarán cuando un esquema específico de pcmcia-cs esté activo (solo en Linux). Para ello, pdnsd necesita saber dónde reside el archivo que contiene la información del esquema pcmcia. Normalmente, este es `/var/lib/pcmcia/scheme` o `/var/state/pcmcia/scheme`.
status_ctl=(on|off);
Esto tiene el mismo efecto que la opción de línea de comandos `-s`: el control de estado se habilita cuando se especifica `on`.
Añadido por Paul Rombouts: Tenga en cuenta que `pdnsd-ctl` permite la configuración en tiempo de ejecución de pdnsd, incluso las direcciones IP de los servidores de nombres se pueden cambiar. Si no está utilizando `pdnsd-ctl` y desea la máxima seguridad, no habilite esta opción. Está deshabilitada por defecto.
daemon=(on|off);
Esto tiene el mismo efecto que la opción de línea de comandos `-d`: el modo demonio se habilita cuando se especifica `on`.
El predeterminado es `off`.
tcp_server=(on|off);
`tcp_server=on` tiene el mismo efecto que la opción de línea de comandos `-t` o `--tcp`: habilita el servicio TCP. De manera similar, `tcp_server=off` es como la opción de línea de comandos `--notcp`.
El predeterminado es `on`.
pid_file=string;
Esto tiene el mismo efecto que la opción de línea de comandos `-p`: puede especificar un archivo en el que pdnsd escribirá su pid cuando comience en modo demonio.
verbosity=number;
Esto tiene el mismo efecto que la opción de línea de comandos `-v`: puede establecer la verbosidad de los mensajes de pdnsd con él. El argumento es un número entre 0 (pocos mensajes) y 3 (la mayoría de los mensajes).
query_method=(tcp_only|udp_only|tcp_udp|udp_tcp);
Esto tiene el mismo efecto que la opción de línea de comandos `-m`. Lea la documentación de la opción de línea de comandos sobre esto. `tcp_only` corresponde al argumento `to`, `udp_only` al `uo`, `tcp_udp` al `tu` y `udp_tcp` al `ut` de la opción de línea de comandos.
Si utiliza `query_method=tcp_udp`, se recomienda que también establezca la opción de tiempo de espera global a al menos el doble del tiempo de espera del servidor más largo.
run_ipv4=(on|off);
Esto tiene el mismo efecto que la opción de línea de comandos `-4` o `-6`: si se especifica `on`, se habilita el soporte IPv4 y se deshabilita el soporte IPv6 (si está disponible). Si se especifica `off`, IPv4 se deshabilitará y se habilitará IPv6. Para que esta opción sea significativa, pdnsd debe compilarse con soporte para el protocolo que elija. Si pdnsd se compiló con soporte para IPv4 e IPv6, y desea incluir direcciones IPv6 en el archivo de configuración, probablemente necesitará especificar primero `run_ipv4=off` para asegurar que las direcciones IPv6 se analicen correctamente.
debug=(on|off);
Esto tiene el mismo efecto que la opción de línea de comandos `-g`: los mensajes de depuración se habilitan cuando se especifica `on`.
ctl_perms=number;
Esta opción le permite establecer los permisos de archivo que tendrá el socket de control de estado de pdnsd. Estos son los mismos que los permisos de archivo. El propietario del archivo será el usuario `run_as`, o, si no se especifica ninguno, el usuario que inició pdnsd. Si desea especificar los permisos en octal (como de costumbre), ¡no olvide el cero inicial (0600 en lugar de 600!). Para usar el control de estado, se necesita acceso de escritura. El predeterminado es 0600 (solo el propietario puede leer o escribir).
Tenga en cuenta que el socket se mantiene en el directorio de caché, y que los permisos del directorio de caché también pueden necesitar ser ajustados. Asegúrese de que el directorio de caché no sea escribible para usuarios no confiables.
proc_limit=number;
Con esta opción, puede establecer un límite en los hilos de pdnsd que estarán activos simultáneamente. Si se excede este número, las consultas se ponen en cola y pueden retrasarse un tiempo. Ver también la opción `procq_limit`.
El predeterminado para esta opción es 40.
procq_limit=number;
Cuando se excede el límite de hilos de consulta `proc_limit`, los intentos de conexión a pdnsd se ponen en cola. Con esta opción, puede establecer la longitud máxima de la cola. Si también se excede esta longitud, las consultas entrantes se descartarán. Eso significa que las conexiones TCP se cerrarán y las consultas UDP simplemente se descartarán, lo que probablemente hará que el resolvedor consultante espere una respuesta hasta que expire el tiempo de espera.

OPTIONS

cache_dir=path;
This option sets the directory where pdnsd stores its cache files. It defaults to /var/cache/pdnsd/. If the directory does not exist, pdnsd will try to create it.
This option is only meaningful if pdnsd is run with the -c option.
The default for this option is 60.
tcp_qtimeout=timespec;
This option sets a timeout for tcp queries. If no full query has been received on a tcp connection after that time has passed, the connection will be closed. The default is set using the --with-tcp-qtimeout option to configure.
par_queries=number;
This option used to set the maximum number of remote servers that would be queried simultaneously, for every query that pdnsd receives.
Since version 1.1.11, the meaning of this option has changed slightly. It is now the increment with which the number of parallel queries is increased when the previous set of servers has timed out. For example, if we have a list server1, server2, server3, etc. of available servers and par_queries=2, then pdnsd will first send queries to server1 and server2, and listen for responses from these servers.
If these servers do not send a reply within their timeout period, pdnsd will send additional queries to server3 and server4, and listen for responses from server1, server2, server3 and server4, and so on until a useful reply is received or the list is exhausted.
In the worst case there will be pending queries to all the servers in the list of available servers. We may be using more system resources this way (but only if the first servers in the list are slow or unresponsive), but the advantage is that we have a greater chance of catching a reply. After all, if we wait longer anyway, why not for more servers.
See also the explanation of the global timeout option below.
1 or 2 are good values for this option. The default is set at compile time using the --with-par-queries option to configure.
timeout=timespec;
This is the global timeout parameter for dns queries. This specifies the minimum period of time pdnsd will wait after sending the first query to a remote server before giving up without having received a reply. The timeout options in the configuration file are now only minimum timeout intervals. Setting the global timeout option makes it possible to specify quite short timeout intervals in the server sections (see below). This will have the effect that pdnsd will start querying additional servers fairly quickly if the first servers are slow to respond (but will still continue to listen for responses from the first ones). This may allow pdnsd to get an answer more quickly in certain situations.
If you use query_method=tcp_udp it is recommended that you make the global timeout at least twice as large as the largest server timeout, otherwise pdnsd may not have time to try a UDP query if a TCP connection times out.
Default value is 0.
randomize_recs=(on|off);
If this option is turned on, pdnsd will randomly reorder the cached records of one type when creating an answer. This supports round-robin DNS schemes and increases fail safety for hosts with multiple IP addresses, so this is usually a good idea.
On by default.
query_port_start=(number|none);
If a number is given, this defines the start of the port range used for queries of pdnsd. The value given must be >= 1024. The purpose of this option is to aid certain firewall configurations that are based on the source port. Please keep in mind that another application may bind a port in that range, so a stateful firewall using target port and/or process uid may be more effective. In case a query start port is given pdnsd uses this port as the first port of a specified port range (see query_port_end) used for queries. pdnsd will try to randomly select a free port from this range as local port for the query.
To ensure that there are enough ports for pdnsd to use, the range between query_port_start and query_port_end should be adjusted to at least (par_queries * proc_limit). A larger range is highly recommended for security reasons, and also because other applications may allocate ports in that range. If possible, this range should be kept out of the space that other applications usually use.
The default for this option is 1024. Together with the default value of query_port_end, this makes it the hardest for an attacker to guess the source port used by the pdnsd resolver. If you specify none here, pdnsd will let the kernel choose the source port, but this may leave pdnsd more vulnerable to an attack.
query_port_end=number;
Used if query_port_start is not none. Defines the last port of the range started by query_port_start used for querys by pdnsd. The default is 65535, which is also the maximum legal value for this option. For details see the description of query_port_start.
delegation_only=string;
Added by Paul Rombouts: This option specifies a "delegation-only" zone. This means that if pdnsd receives a query for a name that is in a subdomain of a "delegation-only" zone but the remote name server returns an answer with an authority section lacking any NS RRs for subdomains of that zone, pdnsd will answer NXDOMAIN (unknown domain). This feature can be used for undoing the undesired effects of DNS "wildcards". Several "delegation-only" zones may be specified together. If you specify root servers in a server section it is important that you set root_server=on in such a section.
Example:

delegation_only="com","net";

This feature is off by default. It is recommended that you only use this feature if you actually need it, because there is a risk that some legitimate names will be blocked, especially if the remote name servers queried by pdnsd return answers with empty authority sections.

ipv4_6_prefix=string;
This option has the same effect as the -i command-line option. When pdnsd runs in IPv6 mode, this option specifies the prefix pdnsd uses to convert IPv4 addresses in the configuration file (or addresses specified with pdnsd-ctl) to IPv6-mapped addresses. The string must be a valid IPv6 address. Only the first 96 bits are used. Note that this only effects the parsing of IPv4 addresses listed after this option.
The default is "::ffff.0.0.0.0".
use_nss=(on|off);
If this option is turned on, pdnsd will call initgroups() to set up the group access list, whenever pdnsd changes its user and group id (see run_as option). There is a possible snag, though, if initgroups() uses NSS (Name Service Switch) and NSS in turn uses DNS. In such a case you may experience lengthy timeouts and stalls. By setting use_nss=off, you can disable the initgroups() call (only possible in versions 1.2.5 and later).
This option was contributed by Jan-Marek Glogowski.
On by default.
udpbufsize=number;
New in version 1.2.9: This option sets the upper limit on the size of UDP DNS messages. The default is 1024.
See also the edns_query server option below.

server Section

Each server section specifies a set of name servers that pdnsd should try to get resource records or authoritative name server information from. The servers are queried in the order of their appearance (or parallel to a limited extend). If one fails, the next one is taken and so on.
You probably want to specify the dns server in your LAN, the caching dns servers of your internet provider or even a list of root servers in one or more server sections.
The supported options in this section are:

label=string;
Specify a label for the server section. This can be used to refer to this section when using pdnsd-ctl, the pdnsd control utility.
You can give several server sections the same label, but if you want to change the addresses of a server section (see ip option below) during run-time with "pdnsd-ctl server label up dns1,dns2,...", the label must be unique.
ip=string;
Give the IP (the address, not the host name) of the server.
Multiple IP addresses can be given per server section. This can be done by entering multiple lines of the form ip=string; or a single line like this:

ip=string,string,string;

IP addresses do not have to be specified in the configuration file. A server section without IP addresses will remain inactive until it is assigned one or more addresses with pdnsd-ctl, the pdnsd control utility.
If pdnsd has been compiled with both IPv4 and IPv6 support, any IPv6 addresses you specify here will be skipped with a warning message, unless pdnsd is running in IPv6 mode. Thus, unless pdnsd was compiled to startup in IPv6 mode by default, you need to use the command-line option -6 or set run_ipv4=off first (see global section) in order to ensure that IPv6 addresses are parsed correctly.
If pdnsd is running in IPv6 mode and you specify an IPv4 address here, it will automatically be mapped to an IPv6 address.

file=string;
New in version 1.2: This option allows you to give the name of a resolv.conf-style file. Of the lines beginning with the nameserver keyword, the second field will be parsed as an IP address, as if it were specified with the ip= option. The remaining lines will be ignored. If the contents of the file changes while pdnsd is running, you can make pdnsd aware of the changes through the use of pdnsd-ctl, the pdnsd control utility. This is usually most conveniently done by placing the command "pdnsd-ctl config" in a script that is automatically run whenever the DNS configuration changes.
For example, suppose you have a ppp client that writes the DNS configuration for your ISP to the file /etc/ppp/resolv.conf and runs the script /etc/ppp/ip-u
p cuando se establece una nueva conexión. Una forma de asegurar que pdnsd se reconfigure automáticamente es agregar una sección de servidor en el archivo de configuración con file=/etc/ppp/resolv.conf y agregar el comando "pdnsd-ctl config" a /etc/ppp/ip-up.
port=número;
Indica el puerto en el que escucha el servidor de nombres remoto. El valor predeterminado es 53 (el puerto oficial de DNS).
uptest=(ping|none|if|dev|diald|exec|query);
Determina el método para comprobar si el servidor está disponible. Los métodos definidos actualmente son:
• ping: Envía una solicitud ICMP_ECHO al servidor. Si no responde dentro del tiempo de espera, se considera no disponible hasta la próxima sondeo.
• none: El estado de disponibilidad no cambia, solo se actualiza la marca de tiempo.
• if: Comprueba si la interfaz (especificada en la opción interface=) existe, está activa y funcionando. Esto funciona actualmente para todas las interfaces de red "ordinarias", interfaces que desaparecen cuando están inactivas (¿por ejemplo, ppp?) y, además, para interfaces isdn de Linux (a partir del kernel 2.2). Tenga en cuenta que necesita un archivo de dispositivo /dev/isdninfo (major#45, minor#255), o la prueba de conexión isdn siempre fallará.
• dev y diald: Realiza una prueba de conexión if y, si tiene éxito, comprueba adicionalmente si se está ejecutando un programa que ha bloqueado un dispositivo (módem) dado. Los parámetros necesarios son una interfaz (especificada como para la prueba de conexión if, por ejemplo, "ppp0") y un dispositivo relativo a /dev (por ejemplo, "modem" para /dev/modem especificado mediante la opción device=. pdnsd buscará un archivo pid para la interfaz dada en /var/lock (por ejemplo, /var/run/ppp0.pid) y un archivo de bloqueo para el dispositivo dado (por ejemplo, /var/lock/LCK..modem), y luego probará si el proceso de bloqueo es el proceso que creó el archivo pid y si este proceso sigue activo. Si este es el caso, se ejecuta la prueba de conexión if normal para la interfaz dada.
La opción dev es para pppd de marcación bajo demanda, diald es lo mismo para usuarios de diald.
• exec: Ejecuta un comando dado en el shell /bin/sh (como /bin/sh -c <comando>) y evalúa el resultado (el código de retorno del último comando) de la manera en que el shell maneja los códigos de retorno, es decir, 0 indica éxito, todos los demás indican fallo. El nombre del proceso del shell será uptest_sh. El comando se proporciona con la opción uptest_cmd (ver más abajo). Por motivos de seguridad, consulte también esa entrada.
• query: Nuevo en la versión 1.2: Esto funciona de manera similar a la prueba ping, excepto que envía una consulta DNS (vacía) al servidor remoto. Si el servidor envía una respuesta bien formada dentro del período de tiempo de espera (excepto SERVFAIL), se considerará disponible. Esta prueba es útil si un servidor remoto no responde a las solicitudes ICMP_ECHO en absoluto, lo cual lamentablemente es bastante común en estos días. También puede suceder que un servidor remoto esté en línea pero ignore las consultas DNS vacías. En ese caso, deberá establecer la opción query_test_name (ver más abajo). En muchos casos, esta prueba será un indicador de disponibilidad más confiable que los mencionados anteriormente.

El valor predeterminado es none.

NOTA: Si utiliza marcación bajo demanda, utilice none, if, dev, diald o exec, ya que ping o query enviarán paquetes en el intervalo especificado y la interfaz marcará con frecuencia.

ping_timeout=número;
Establece el tiempo de espera para la prueba ping en décimas de segundo (esta unidad se usa por razones de compatibilidad; en realidad, la implementación actual solo es precisa hasta un segundo).
El valor predeterminado es 600 (un minuto).
ping_ip=cadena;
La dirección IP para la prueba ping. El valor predeterminado es la IP del servidor de nombres.
query_test_name=cadena;
Nuevo en la versión 1.2.9: Establece el nombre que se consultará al usar la prueba de disponibilidad uptest=query. Si la cadena es la constante no citada none, se utiliza una consulta vacía (este es el valor predeterminado), de lo contrario, se enviará una consulta de tipo A para el nombre de dominio especificado aquí. No es necesario que el nombre de dominio exista o tenga un registro de tipo A para que la prueba de conexión tenga éxito.
Si el servidor remoto ignora las consultas vacías, probablemente querrá establecer query_test_name="." (el dominio raíz).
uptest_cmd=cadena,cadena;
o
uptest_cmd=cadena;
Establece el comando para la función uptest=exec en la primera cadena. Si se proporciona la segunda cadena, especifica un usuario con cuyo ID de usuario y grupo principal se ejecuta el comando.
Esto es especialmente útil si está ejecutando el servidor como root, pero no desea que la prueba de conexión se realice con privilegios de root. De hecho, nunca debe ejecutar la prueba de conexión como root si puede evitarlo.
Si el servidor se está ejecutando con setuid o setgid, se intenta descartar los privilegios obtenidos incluso antes de cambiar la identidad al usuario especificado para evitar agujeros de seguridad de setuid/gid (de lo contrario, cualquier usuario podría ejecutar comandos como root si establece setuid en el ejecutable).
Tenga en cuenta que esto no siempre es posible y que pdnsd nunca debe instalarse como setuid o setgid. El comando se ejecuta usando /bin/sh, por lo que debería poder usar comandos integrados del shell.
interval=(timespec|onquery|ontimeout);
Establece el intervalo para la prueba de conexión del servidor. El valor predeterminado es 900 segundos; sin embargo, se fuerza una prueba cuando una consulta excede el tiempo de espera y la marca de tiempo se restablece.
Si especifica onquery en lugar de un tiempo de espera, la interfaz se probará antes de cada consulta. Esto es para evitar que las interfaces de marcación automática (diald/pppd o ippp) marquen en consultas DNS. Está diseñado para usarse en combinación con una prueba de conexión de interfaz ;-)
Tenga en cuenta que usar uptest=exec puede generar problemas de rendimiento en máquinas lentas cuando usa esta opción. NO use onquery con uptest=ping o uptest=query, ya que puede causar retrasos si el servidor no responde (por cierto, tampoco tiene sentido). Tenga en cuenta también que usar onquery no garantiza que la interfaz no se utilizará. Cuando otro servidor DNS (accesible) le indica a pdnsd que consulte a un tercer servidor DNS para obtener datos, pdnsd lo hará y no tendrá forma de verificar si esto activará la interfaz o no. Sin embargo, esta debería ser una situación poco común.
Nuevo en la versión 1.2.3: Una tercera posibilidad es especificar interval=ontimeout. En este caso, el servidor no se prueba al inicio/reconfiguración, ni a intervalos regulares, sino solo después de que una consulta DNS a un servidor excede el tiempo de espera. Ciertos tipos de problemas de red, como una conexión rechazada, también harán que el servidor se considere no disponible. Sin embargo, una vez que un servidor se declara inactivo, nunca se vuelve a considerar a menos que se reactive utilizando un comando pdnsd-ctl config o server. La idea detrás de esta opción es minimizar las pruebas de conexión asumiendo que todos los servidores están disponibles hasta que haya motivos para creer lo contrario.
interface=cadena;
La interfaz de red (o dispositivo de red, por ejemplo, "eth0") para la opción uptest=if. Debe especificarse si se proporciona uptest=if.
device=cadena;
El dispositivo (módem) que se utiliza para la prueba de conexión dev. Si utiliza esto para una prueba de conexión ppp de marcación bajo demanda (junto con uptest=dev), debe ingresar el dispositivo que está utilizando para su pppd aquí, por ejemplo, modem para /dev/modem.
Debe especificarse si se proporciona uptest=dev.
timeout=timespec;
Establece el tiempo de espera para la consulta DNS. El valor predeterminado es 120 segundos. Probablemente querrá establecer un valor más bajo.
Los tiempos de espera especificados en el archivo de configuración solo se tratan como el período mínimo de tiempo para esperar una respuesta. Las consultas a un servidor remoto no se cancelan hasta que se haya recibido una respuesta útil, o todas las demás consultas hayan excedido el tiempo de espera o fallado.
Si también ha establecido la opción global timeout, puede considerar establecer un valor bastante pequeño aquí. Consulte la explicación de la opción timeout en la sección global para saber qué significa eso.
purge_cache=(on|off);
En cada registro DNS obtenido, hay un tiempo de espera de caché, que especifica cuánto tiempo se pueden almacenar los datos obtenidos hasta que necesiten ser recargados. Si purge_cache se establece en off, los registros obsoletos no se eliminan (a menos que el tamaño de la caché se supere, en cuyo caso se eliminan los registros más antiguos). En cambio, todavía se sirven si no se pueden actualizar correctamente (por ejemplo, porque todos los servidores están inactivos).
El valor predeterminado es off.
caching=(on|off);
Especifica si se realizará caché para este servidor en absoluto. El valor predeterminado es on.
lean_query=(on|off);
Especifica si se utilizará el modo de consulta "lean". En este modo, solo se resuelven y almacenan en caché la información consultada activamente a pdnsd. Esto tiene la ventaja de que generalmente se utiliza menos espacio en la caché y la consulta suele ser más rápida. En el 90% de los casos, solo se necesitan registros de dirección (A). Si se desactiva, pdnsd almacenará en caché todos los datos sobre un host que pueda encontrar y solicitará específicamente todos los registros disponibles (bueno, al menos es una buena aproximación de lo que realmente hace ;-) Esto, por supuesto, aumentará el tamaño de los paquetes de respuesta.
Algunos servidores de nombres defectuosos pueden no entregar registros CNAME cuando no se solicitan todos los registros. No sé si existen tales servidores, pero si tiene problemas para resolver ciertos nombres de host, intente desactivar esta opción.
Una última nota: si utiliza varios pdnsd que se acceden entre sí, activar esta opción probablemente sea una gran ventaja.
Esto está activado por defecto.
edns_query=(on|off);
Nuevo en la versión 1.2.9: Especifica si se utilizará EDNS (Extension Mechanisms for DNS) para las consultas salientes. Actualmente, esto solo es útil para permitir tamaños de mensajes UDP mayores a 512 bytes. Tenga en cuenta que activar esta opción puede causar problemas en combinación con algunos sistemas o software heredados, incluyendo, vergonzosamente, versiones anteriores de pdnsd.
El valor predeterminado es off, pero si su red
pueden manejar cargas útiles UDP significativamente mayores de 512 bytes, el valor recomendado es encendido.
Tenga en cuenta que esta opción solo afecta a las consultas salientes. Si pdnsd recibe una consulta usando EDNS, responderá usando EDNS independientemente del valor de esta opción.

Ver también la opción udpbufsize anterior.

scheme=cadena;
Puede especificar un esquema pcmcia-cs que se utiliza además de las pruebas de actividad. Si especifica un esquema aquí, el servidor para esta sección solo recibirá consultas si el esquema dado está activo. Se permiten comodines de shell (* y ?) en la cadena con sus significados especiales. Debe usar la opción scheme_file en la sección global para que esta opción funcione.
preset=(encendido|apagado);
Esto le permite especificar el estado inicial de un servidor antes de realizar cualquier prueba de actividad. Encendido especifica que el servidor se considera disponible. El valor predeterminado es encendido. Esto es especialmente útil cuando establece uptest=none; y desea cambiar el estado de un servidor solo a través de pdnsd-ctl.
proxy_only=(encendido|apagado);
Cuando esta opción se establece en encendido, las respuestas dadas por los servidores son siempre aceptadas, y no se consultan otros servidores (como, por ejemplo, especificados en los registros NS del dominio de la consulta). Si no enciende esta opción, pdnsd realizará tales consultas en algunos casos (en particular al procesar consultas ANY).
Esta opción es útil cuando no desea que pdnsd establezca conexiones con servidores externos por alguna razón (por ejemplo, cuando un firewall bloquea tales consultas).
Recomiendo que encienda lean_query al usar esta opción.
El valor predeterminado es apagado.
root_server=(encendido|apagado|descubrir);
Establezca esta opción en encendido si los servidores especificados en una sección son servidores raíz. Un servidor raíz típicamente solo dará los servidores de nombres para el dominio de nivel superior en su respuesta. Establecer root_server=encendido hará que pdnsd intente usar información en caché sobre dominios de nivel superior para reducir el número de consultas a servidores raíz, haciendo que la resolución de nuevos nombres sea más eficiente. Puede obtener una lista de servidores raíz disponibles ejecutando el comando "dig . ns".
Esta opción también es necesaria si usa la opción delegation_only.
Nuevo en la versión 1.2.8: Esta opción también puede establecerse en "descubrir". Esto hará que pdnsd consulte los servidores proporcionados con la opción ip= para obtener la lista completa de servidores raíz. Las direcciones del servidor raíz reemplazarán las direcciones especificadas con la opción ip=. Esto solo se hará una vez al inicio, o después de un comando "pdnsd-ctl config". En este caso, los servidores de nombres especificados con la opción ip= no tienen que ser servidores raíz, solo tienen que conocer los nombres y direcciones de los servidores raíz. Después del descubrimiento del servidor raíz, pdnsd se comportará como si se hubiera especificado root_server=encendido.
El valor predeterminado es apagado.
randomize_servers=(encendido|apagado);
Nuevo en la versión 1.2.6: Establezca esta opción en encendido para dar a cada servidor de nombres de esta sección la misma oportunidad de ser consultado. Si esta opción está apagada, los servidores de nombres siempre se consultan comenzando con el primero especificado. Incluso con esta opción activada, el orden de consulta no es verdaderamente aleatorio. Solo se selecciona aleatoriamente el primer servidor; los siguientes se consultan en orden consecutivo, volviendo al principio de la lista cuando se alcanza el final. Tenga en cuenta que esta opción solo afecta el orden dentro de una sección. Los servidores de la primera sección (activa) siempre se consultan antes que los de la segunda, etc.
El valor predeterminado es apagado, pero si está resolviendo desde servidores raíz, se recomienda encarecidamente establecer esta opción en encendido. Si root_server=encendido, esta opción también afecta el orden de consulta de los servidores de nombres para los dominios de nivel superior.
reject=cadena;
Nuevo en la versión 1.2.6: Esta opción se puede usar para hacer que pdnsd rechace respuestas que contengan ciertas direcciones IP. Puede especificar una única dirección IP, que coincidirá exactamente, o un rango de direcciones usando un par dirección/máscara. La máscara se puede especificar como un número entero simple, indicando el número de bits iniciales de 1 en la máscara, o en la notación de dirección IP habitual. Las direcciones IP pueden ser IPv4 o IPv6 (siempre que haya suficiente soporte en las bibliotecas C y no se haya deshabilitado el soporte para registros AAAA). Cuando las direcciones en la lista de rechazo se comparan con las de una respuesta, solo los bits correspondientes a los establecidos en la máscara de red son significativos, el resto se ignora.
Se pueden especificar varias direcciones o pares dirección/máscara; esto se puede hacer ingresando varias líneas de la forma reject=cadena; o una sola línea como esta:

reject=cadena,cadena,cadena;

Cómo reacciona pdnsd cuando una dirección en la respuesta coincide con una en la lista de rechazo, depende de la opción reject_policy, ver abajo.

reject_policy=(fallar|negar);
Nuevo en la versión 1.2.6: Esta opción determina qué hace pdnsd cuando una dirección en la respuesta de un servidor de nombres coincide con la lista de rechazo (ver arriba). Si esta opción se establece en fallar, pdnsd intentará con otro servidor, o, si no quedan más servidores para intentar, devolverá la respuesta SERVFAIL. Si esta opción se establece en negar, pdnsd devolverá inmediatamente la respuesta NXDOMAIN (dominio desconocido) sin consultar servidores adicionales. La configuración de fallar es útil si no siempre confía en los servidores de esta sección, pero sí confía en los servidores de la siguiente sección. La configuración de negar se puede usar para censurar completamente ciertas direcciones IP. En este caso, debe colocar la misma lista de rechazo en cada sección de servidor y también establecer la opción reject_recursively (ver abajo) en verdadero.
El valor predeterminado es fallar.
reject_recursively=(encendido|apagado);
Nuevo en la versión 1.2.6: Normalmente pdnsd verifica las direcciones en la lista de rechazo (ver arriba) solo cuando la respuesta proviene directamente de un servidor de nombres listado en el archivo de configuración. Con esta opción establecida en encendido, pdnsd también realizará esta verificación para los servidores de nombres que se obtuvieron de los registros NS en la sección de autoridad de una respuesta anterior (que era incompleta y no autoritativa).
El valor predeterminado es apagado.
policy=(incluido|excluido|solo_simple|solo_fqdn);
pdnsd admite listas de inclusión/exclusión para secciones de servidor: con include= y exclude= (ver abajo) puede especificar nombres de dominio para los cuales se utilizará o no este servidor. La primera coincidencia cuenta (es decir, la primera regla include o exclude en una sección de servidor que coincide con un nombre de dominio se aplica y la búsqueda de otras reglas se termina). Si ninguna regla coincidió con un nombre de dominio dado, la opción policy= determina si este servidor se usa para la búsqueda de ese nombre de dominio; cuando se da incluido, se preguntará al servidor, y cuando se da excluido, no. Si se da solo_simple, el servidor se usará si el nombre a buscar es un nombre de dominio simple (de una sola etiqueta), por otro lado, si se da solo_fqdn, el servidor solo se usará para nombres que consisten en dos o más etiquetas (es decir, el nombre tiene al menos un punto en medio).
Si no hay ningún servidor disponible para un dominio consultado, pdnsd devolverá un mensaje de error al cliente que generalmente detendrá los intentos del cliente de resolver un dominio específico desde este servidor (el resolvedor libc, por ejemplo, devolverá un error a la aplicación que intentó resolver el dominio si no hay otros servidores disponibles en resolv.conf). Esto puede ser útil a veces.
Nota: las constantes solo_simple y solo_fqdn fueron agregadas por Paul Rombouts. Son útiles para controlar qué servidores de nombres (si los hay) utilizará pdnsd para resolver nombres de host simples (de una sola etiqueta). solo_fqdn solía significar "solo nombre de dominio completamente calificado", pero esto es en realidad un nombre inapropiado. Los nombres en las consultas recibidas por pdnsd siempre se consideran completamente calificados. Si no entiende exactamente para qué sirven las opciones solo_simple y solo_fqdn, probablemente sea mejor no usarlas.
El valor predeterminado para esta opción es incluido.
include=cadena;
Esta opción agrega una entrada a la lista de exclusión/inclusión. Si un dominio coincide con el nombre dado como cadena, se consulta el servidor si esta fue la primera regla coincidente (ver también la entrada para policy).
Si el nombre dado comienza con un punto, se hace coincidir todo el subdominio del nombre dado, incluido el de ese nombre, por ejemplo, ".foo.bar." coincidirá con los nombres de dominio a.foo.bar., a.b.c.foo.bar. y foo.bar.
Si no comienza con un punto, solo coincidirá exactamente el nombre dado (ignorando la capitalización, por supuesto) (pista: si desea incluir todos los subdominios, pero no el dominio del nombre dado en sí, coloque una regla de exclusión de coincidencia exacta antes de la regla de inclusión, por ejemplo: exclude="foo.bar."; include=".foo.bar.";
Las versiones anteriores de pdnsd requerían que los nombres dados con esta y la siguiente opción terminaran en un punto, pero desde la versión 1.1.8b1-par8, pdnsd agrega automáticamente un punto al final si falta.
pdnsd ahora también acepta una notación más compacta para agregar varias entradas "include" en una sola línea, por ejemplo:

include=".foo",".bar",".my.dom";

exclude=cadena;
Esta opción agrega una entrada a la lista de exclusión/inclusión. Si un dominio coincide con el nombre dado como cadena, no se consulta el servidor si esta fue la primera regla coincidente (ver también la entrada para policy).
Si el nombre dado comienza con un punto, se hace coincidir todo el subdominio del nombre dado, incluido el de ese nombre, por ejemplo, ".foo.bar." coincidirá con los nombres de dominio a.foo.bar., a.b.c.foo.bar. y foo.bar.
Si no comienza con un punto, solo coincidirá exactamente el nombre dado (ignorando la capitalización, por supuesto) (pista: si desea excluir todos los subdominios, pero no el dominio del nombre dado en sí, coloque una regla de inclusión de coincidencia exacta antes de la regla de exclusión, por ejemplo: include="foo.bar."; exclude=".foo.bar.";
pdnsd ahora también acepta una notación más compacta para agregar varias entradas "exclude" en una sola línea, por ejemplo:

exclude=".foo",".bar",".my.dom";

(y quizás incluso uno o dos hosts) sin tener que iniciar un servidor de nombres adicional si sus servidores de nombres cacheados no sirven esos registros. **NO** está pensado y no es capaz de funcionar como un servidor de nombres con todas las funciones.

name=string;
Especifica el nombre de los registros de recursos, es decir, el nombre de dominio del recurso que describe el registro. Esta opción debe especificarse antes de cualquier registro a, ptr, cname, mx, ns o soa. Los nombres se interpretan como nombres de dominio absolutos (es decir, pdnsd asume que terminan en el dominio raíz). Para esta y todas las siguientes opciones que toman nombres de dominio, debe especificar los nombres de dominio en notación de puntos (ejemplo venera.isi.edu.).
Las versiones anteriores de pdnsd requerían que los nombres de dominio dados en el archivo de configuración terminaran en un punto, pero desde la versión 1.1.8b1-par8, pdnsd asume automáticamente un punto al final si falta.
Nuevo en la versión 1.2: También es posible especificar un nombre que comience con la etiqueta *. Tal nombre se llama comodín. El * en un comodín puede coincidir con una o más etiquetas en un nombre consultado, pero solo etiquetas completas. Cualquier otro carácter * en un comodín, aparte del inicial, solo coincidirá con un * literal.
Por ejemplo, *.mydomain coincidirá con a.mydomain o www.a.mydomain, pero no con mydomain. *.a*.mydomain coincidirá con www.a*.mydomain, pero no con www.ab.mydomain. *a.mydomain solo coincidirá consigo mismo.
Antes de poder especificar una sección rr con name=*.mydomain, debe definir algunos registros para mydomain, típicamente registros NS y/o SOA. Ejemplo:


rr {
name = mydomain;
ns = localhost;
soa = localhost, root.localhost, 42, 86400, 900, 86400, 86400;
}
rr {
name = *.mydomain;
a = 192.168.1.10;
}

En este ejemplo, www.mydomain y ftp.mydomain se resolverán a la dirección numérica 192.168.1.10 (a menos que agregue secciones rr que especifiquen explícitamente direcciones diferentes para www.mydomain o ftp.mydomain). Si desea que mydomain también se resuelva a una dirección numérica, agregue un registro A a la primera sección rr.

ttl=timespec;
Especifica el ttl (tiempo de vida) para todos los registros de recursos en esta sección después de esta entrada. Esto se puede redefinir. El valor predeterminado es 86400 segundos (=1 día).
authrec=(on|off);
Si esto está activado, pdnsd creará registros locales autoritativos para esta sección rr. Esto significa que pdnsd marca el registro de dominio para que los registros de este dominio que no están presentes en la caché se traten como inexistentes, es decir, no se consultarán otros servidores para ese tipo de registro, y se devolverá una respuesta que no contenga ninguno de esos registros. Esto es lo que la mayoría de la gente quiere: si agrega un registro A para un host y no tiene un registro AAAA (por lo tanto, ninguna dirección IPv6), normalmente no querrá que otros servidores de nombres sean consultados.
Esto está activado por defecto.
Tenga en cuenta que esto solo tiene un efecto si precede a la opción name.
reverse=(on|off);
Nuevo en la versión 1.2: Si desea que un nombre definido localmente se resuelva a una dirección numérica y viceversa, puede lograr esto configurando reverse=on antes de definir el registro A (ver más abajo). La alternativa es definir un registro PTR separado, pero probablemente encontrará esta opción mucho más conveniente.
El valor predeterminado es off.
a=string;
Define un registro A (dirección de host). El argumento es una dirección IPv4 en notación de puntos. pdnsd servirá esta dirección para el nombre de host dado en la opción name.
Siempre que haya suficiente soporte en las bibliotecas C y el soporte para registros AAAA no se haya deshabilitado, la cadena de argumento también puede ser una dirección IPv6, en cuyo caso se definirá un registro AAAA.
Esta opción se puede usar varias veces dentro de una sección rr, lo que causa que se definan varias direcciones para el nombre. Sin embargo, si coloca las diferentes direcciones en diferentes secciones rr para el mismo nombre, la definición en la última sección rr cancelará las definiciones de las anteriores.
ptr=string;
Define un registro PTR (puntero de nombre de dominio). El argumento es un nombre de host en notación de puntos (ver name). El registro ptr es para resolver direcciones en nombres. Por ejemplo, si desea que la dirección 127.0.0.1 se resuelva a localhost y localhost a 127.0.0.1, necesita algo como las siguientes secciones:


rr {
name = localhost;
a = 127.0.0.1;
owner = localhost;
soa = localhost, root.localhost, 42, 86400, 900, 86400, 86400;
}
rr {
name = 1.0.0.127.in-addr.arpa;
ptr = localhost;
owner = localhost;
soa = localhost, root.localhost, 42, 86400, 900, 86400, 86400;
}

La segunda sección es para la resolución inversa y utiliza la opción ptr. Tenga en cuenta que puede obtener el mismo efecto especificando solo la primera sección rr con reverse=on.
Hay algo especial en el nombre de la segunda sección: cuando un resolvedor quiere obtener un nombre de host a partir de una dirección de Internet, compone una dirección que se construye a partir de la dirección IP en orden inverso de bytes (1.0.0.127 en lugar de 127.0.0.1) donde cada byte de la dirección escrito como número constituye un subdominio bajo el dominio in-addr.arpa.
Por lo tanto, si desea componer una dirección para la resolución inversa, tome su IP en notación de puntos (por ejemplo, 1.2.3.4), invierta el orden de los bytes (4.3.2.1) y agregue in-addr.arpa. (4.3.2.1.in-addr.arpa.) Luego, defina una sección rr que proporcione esta dirección como nombre y el nombre de dominio correspondiente a esa IP en la opción ptr.

cname=string;
Define un registro CNAME (nombre canónico). El argumento debe ser un nombre de host completamente calificado en notación de puntos (ver name). Un CNAME es el equivalente en DNS de un alias o enlace simbólico.
Una aplicación útil para los CNAME es dar apodos cortos y fáciles de recordar a hosts con nombres complicados. Por ejemplo, es posible que desee que el nombre "news" se refiera al servidor de noticias de su ISP "nntp2.myisp.com". En lugar de agregar un registro A para "news" con la misma dirección que "nntp2.myisp.com", podría poner un CNAME que apunte a "nntp2.myisp.com", de modo que si la dirección IP del servidor de noticias cambia, no hay necesidad de actualizar el registro para "news".
Para implementar esto con pdnsd, podría agregar la siguiente sección a su archivo de configuración:


rr {
name = news;
cname = nntp2.myisp.com;
owner = localhost;
}

mx=string,number;
Define un registro MX (intercambio de correo). La cadena es el nombre del host del servidor de correo en notación de puntos (ver name). El número especifica el nivel de preferencia.
Cuando envía correo a alguien, su correo generalmente va desde su cliente de correo electrónico a un servidor SMTP. El servidor SMTP luego verifica el registro MX del dominio en la dirección de correo electrónico. Por ejemplo, con joe@example.com, buscaría el registro MX para example.com y encontraría que el nombre del servidor de correo para ese dominio es, digamos, mail.example.com. El servidor SMTP luego obtiene el registro A para mail.example.com y se conecta al servidor de correo.
Si hay varios registros MX, el servidor SMTP elegirá uno según el nivel de preferencia (comenzando con el número de preferencia más bajo, subiendo).
No defina registros MX con pdnsd a menos que sepa lo que está haciendo.
owner=string;
o
ns=string;
Define un registro NS (servidor de nombres). Especifica el nombre del host que debe ser autoritativo para los registros que definió en la sección rr. Este es típicamente el host en el que se ejecuta pdnsd.
Nota: En versiones anteriores de pdnsd, esta opción tenía que especificarse antes que cualquier entrada a, ptr, cname, mx o soa. En la versión 1.2, las restricciones en esta opción son las mismas que las opciones mencionadas anteriormente, y debe listarse después de la opción name=. Esto puede ser un problema si desea usar un archivo de configuración antiguo que especifica owner= antes que name= (lo siento por eso). Además de una mayor consistencia, la ventaja es que ahora puede especificar tantos registros NS como desee (incluido cero).
soa=string,string,number,timespec,timespec,timespec,timespec;
Esto define un registro soa (inicio de autoridad). La primera cadena es el nombre de dominio del servidor y debe ser igual al nombre que especificó como owner.
La segunda cadena especifica la dirección de correo electrónico del mantenedor del servidor de nombres. También se especifica como un nombre de dominio, por lo que deberá reemplazar el signo @ en el nombre con un punto (.) para obtener el nombre que debe especificar aquí. El siguiente parámetro (el primer número) es el número de serie del registro. Debe incrementar este número si cambia el registro.
El cuarto parámetro es el tiempo de espera de actualización (refresh timeout). Especifica después de qué cantidad de tiempo un servidor de caché debe intentar actualizar el registro cacheador.
El quinto parámetro especifica un tiempo después del cual un servidor de caché debe intentar actualizar el registro después de un fallo de actualización (refresh failure).
El sexto parámetro define el tiempo de espera después del cual un registro cacheador caduca si no ha sido actualizado.
El séptimo parámetro es el ttl que se especifica en cada rr y debe ser el mismo que el proporcionado con la opción ttl (si no especifica un ttl, use el valor predeterminado 86400).
txt=string,...,string;
Nuevo en la versión 1.2.9: Define un registro TXT. Puede especificar una o más cadenas aquí.

NAME

pdnsd.conf — pdnsd configuration file format

DESCRIPTION

This file describes the format of the configuration file used by pdnsd(8), the pdnsd DNS server.

Global Sections

These sections define global parameters of the pdnsd daemon. They may only occur once and must be at the beginning of the configuration file.

server=timespec;
Specifies the server time out. The default is 10 seconds.
pidfile=string;
The pid file is written contains the process id of the running pdnsd daemon. The default is /var/run/pdnsd.pid.
status=string;
The status file contains status information about pdnsd. The default is /var/run/pdnsd.status.
procmax=integer;
Maximum number of child processes. Default is 10.
threads=integer;
Number of threads to use. Default is 2. Use 0 to disable threading.
verbosity=integer;
Sets the verbosity level for logging. Default is 0.
logfile=string;
Specifies the log file. If it is omitted logging goes to syslog.
daemon=on|off;
If turned on, pdnsd forks itself into the background. Default is on.
allow_from=(ip_address[/prefix_length]|...);
A list of IP addresses or networks that are allowed to query the pdnsd server. If empty or omitted, all IP addresses are allowed. This option can be specified multiple times. For example:
allow_from=127.0.0.1/32; allow_from=192.168.1.0/24; allow_from=::1/128;
deny_from=(ip_address[/prefix_length]|...);
A list of IP addresses or networks that are denied querying the pdnsd server. If a query matches both allow_from and deny_from, the deny_from rule takes precedence. This option can be specified multiple times.
quiet=(on|off);
If set to on, pdnsd will only log critical messages. Default is off.
paranoid=on|off;
If set to on, pdnsd checks if the source IP address of a query is the same as the IP address the query was sent to. This should prevent cache poisoning. Default is on.
user=string;
Run pdnsd as the specified user. Default is nobody.
group=string;
Run pdnsd as the specified group. Default is nogroup.

RR Section

RR sections define resource records that should be served authoritatively. This means pdnsd will answer queries for these records without querying any other hosts. This is useful for defining local host names like localhost.

name=string;
Specifies the name of the record. This option must be specified before the type option. Names are interpreted as absolute domain names (i.e. pdnsd assumes they end in the root domain). You need to specify domain names in dotted notation (example venera.isi.edu.).
Previous versions of pdnsd required that domain names given in the configuration file ended in a dot, but since version 1.1.8b1-par8, pdnsd automatically assumes a dot at the end if it is missing.
type=rr_type;
Specifies the type of the resource record. It can be any valid RR type, e.g. A, CNAME, NS, PTR, MX, AAAA, ...
The command pdnsd-ctl list-rrtypes will give you a complete list of these types. pdnsd-ctl is built along with pdnsd and will be installed in the same directory as the pdnsd binary during make install.
ttl=timespec;
Specifies the ttl (time to live) for the resource record. The default is 86400 seconds (=1 day).
data=string;
Specifies the data of the resource record. The format of the data depends on the type of the record.
authrec=(on|off);
If this is turned on, pdnsd will create authoritative records from the data given. This is useful for setting up local DNS servers. If it is off, pdnsd will behave like a normal caching server.
This is on by default.

Neg Section

Every neg section specifies a dns resource record or a dns domain that should be cached negatively locally. Queries for negatively cached records are always answered immediatley with an error or an empty answer without querying other hosts as long as the record is valid. The records defined with neg sections remain valid until they are explicitely invalidated or deleted by the user using pdnsd-ctl(8).
This is useful if a certain application asks periodically for nonexisting hosts or RR types and you do not want a query to go out every time the cached record has timed out. Example: Netscape Communicator will ask for the servers news and mail on startup if unconfigured. If you do not have a dns search list for your network, you can inhibit outgoing queries for these by specifying


neg {
name = news;
types = domain;
}
neg {
name = mail;
types = domain;
}

in your config file. If you have a search list, you have to repeat that for any entry in your search list in addition to the entries given above!
In versions 1.1.11 and later, if you negate whole domains this way, all subdomains will be negated as well. Thus if you specify
neg {name=example.com; types=domain;} in the config file, this will also negate www.example.com, xxx.adserver.example.com, etc.

name=string;
Specifies the name of the domain for which negative cache entries are created. This option must be specified before the types option. Names are interpreted as absolute domain names (i.e. pdnsd assumes they end in the root domain). You need to specify domain names in dotted notation (example venera.isi.edu.).
Previous versions of pdnsd required that domain names given in the configuration file ended in a dot, but since version 1.1.8b1-par8, pdnsd automatically assumes a dot at the end if it is missing.
ttl=timespec;
Specifies the ttl (time to live) for all resource records in this section after this entry. This may be redefined. The default is 86400 seconds (=1 day).
types=(domain|rr_type[,rr_type[,rr_type[,...]]]);
Specifies what is to be cached negatively: domain will cache the whole domain negatively; alternatively, you can specify a comma-separated list of RR types which are to be cached negatively. You may specify multiple types options, but domain and the RR types are mutually exclusive.
The RR types are specified using their official names from the RFC's in capitals, e.g. A, CNAME, NS, PTR, MX, AAAA, ...
The command pdnsd-ctl list-rrtypes will give you a complete list of those types. pdnsd-ctl is built along with pdnsd and will be installed in the same directory as the pdnsd binary during make install.

source Section

Every source section allows you to let pdnsd read the records from a file in an /etc/hosts-like format. pdnsd will generate records to resolve the entries address from its host name and vice versa for every entry in the file. This is normally easier than defining an rr for every of your addresses, since localhost and your other FQDNs are normally given in /etc/hosts.
The accepted format is as follows: The #-sign initiates a comment, the rest of the line from the first occurence of this character on is ignored. Empty lines are tolerated.
The first entry on a line (preceded by an arbitrary number of tabs and spaces) is the IP in dotted notation, the second entry on one line (separated by the first by an arbitrary number of tabs and spaces) is the FQDN (fully qualified domain name) for that ip. The rest of the line is ignored by default (in the original /etc/hosts, it may contain information not needed by pdnsd).

owner=string;
Specifies the name of the host pdnsd runs on and that are specified in dns answers (specifically, nameserver records). Must be specified before any file entries.
Names are interpreted as absolute domain names (i.e. pdnsd assumes they end in the root domain). You need to specify domain names in dotted notation (example venera.isi.edu.).
Previous versions of pdnsd required that domain names given in the configuration file ended in a dot, but since version 1.1.8b1-par8, pdnsd automatically assumes a dot at the end if it is missing.
ttl=timespec;
Specifies the ttl (time to live) for all resource records in this section after this entry. This may be redefined. The default is 86400 seconds (=1 day).
file=string;
The string specifies a file name. For every file entry in a source section, pdnsd will try to load the given file as described above. Failure is indicated only when the file cannot be opened, malformed entries will be ignored.
serve_aliases=(on|off);
If this is turned on pdnsd will serve the aliases given in a hosts-style file. These are the third entry in a line of a hosts-style file, which usually give a "short name" for the host. This may be used to support broken clients without a proper domain-search option. If no aliases are given in a line of the file, pdnsd behaves as without this option for this line.
This feature was suggested by Bert Frederiks.
It is off by default.
authrec=(on|off);
If this is turned on, pdnsd will create authoritative local records with the data from the hosts file. Please see the description of the option of the same name in the rr section for a closer description of what this means. Please note that this only has an effect for files sourced with file options subsequent to this option.
This is on by default.

include Section

A configuration file may include other configuration files. However, only the top-level configuration file may contain global and server sections, thus include files are effectively limited to sections that add local definitions to the cache.
Include sections currently only have one type of option, which may be given multiple times within a single section.

file=string;
The string specifies a file name. For every file option in an include section, pdnsd will parse the given file as described above. The file may contain include sections itself, but as a precaution pdnsd checks that a certain maximum depth is not exceeded to guard against the possibility of infinite recursion.
