NOMBRE

pipe - resumen de tuberías y FIFOs

DESCRIPCIÓN

Las tuberías (pipes) y las FIFOs (también conocidas como tuberías con nombre) proporcionan un canal de comunicación unidireccional entre procesos. Una tubería tiene un extremo de lectura y un extremo de escritura. Los datos escritos en el extremo de escritura de una tubería pueden leerse desde el extremo de lectura de la tubería.

Una tubería se crea usando pipe(2), que crea una nueva tubería y devuelve dos descriptores de archivo, uno que se refiere al extremo de lectura de la tubería y el otro al extremo de escritura. Las tuberías pueden usarse para crear un canal de comunicación entre procesos relacionados; véase pipe(2) para un ejemplo.

Una FIFO (abreviatura de First In First Out) tiene un nombre dentro del sistema de archivos (creada usando mkfifo(3)) y se abre usando open(2). Cualquier proceso puede abrir una FIFO, siempre que los permisos de archivo lo permitan. El extremo de lectura se abre usando el flag O_RDONLY; el extremo de escritura se abre usando el flag O_WRONLY. Véase fifo(7) para más detalles. Nota: aunque las FIFOs tienen una ruta en el sistema de archivos, las I/O en FIFOs no implican operaciones en el dispositivo subyacente (si lo hay).

I/O en tuberías y FIFOs

La única diferencia entre las tuberías y las FIFOs es la forma en que se crean y abren. Una vez que estas tareas se han completado, la I/O en tuberías y FIFOs tiene exactamente la misma semántica.

Si un proceso intenta leer de una tubería vacía, entonces read(2) se bloqueará hasta que haya datos disponibles. Si un proceso intenta escribir en una tubería llena (véase más abajo), entonces write(2) se bloqueará hasta que se hayan leído suficientes datos de la tubería para permitir que la escritura se complete.

La I/O no bloqueante es posible utilizando la operación F_SETFL de fcntl(2) para habilitar el flag de estado de archivo abierto O_NONBLOCK o abriendo una fifo(7) con O_NONBLOCK. Si algún proceso tiene la tubería abierta para escritura, las lecturas fallan con EAGAIN; de lo contrario —sin escritores potenciales— las lecturas tienen éxito y devuelven vacío.

El canal de comunicación proporcionado por una tubería es un flujo de bytes: no hay concepto de límites de mensajes.

Si todos los descriptores de archivo que se refieren al extremo de escritura de una tubería se han cerrado, entonces un intento de read(2) de la tubería verá el fin de archivo (read(2) devolverá 0). Si todos los descriptores de archivo que se refieren al extremo de lectura de una tubería se han cerrado, entonces un write(2) provocará que se genere una señal SIGPIPE para el proceso que llama. Si el proceso que llama ignora esta señal, entonces write(2) falla con el error EPIPE. Una aplicación que utiliza pipe(2) y fork(2) debe usar llamadas close(2) adecuadas para cerrar descriptores de archivo duplicados innecesarios; esto asegura que el fin de archivo y SIGPIPE/EPIPE se entreguen cuando sea apropiado.

No es posible aplicar lseek(2) a una tubería.

Capacidad de la tubería

Una tubería tiene una capacidad limitada. Si la tubería está llena, entonces una write(2) se bloqueará o fallará, dependiendo de si el flag O_NONBLOCK está activado (véase más abajo). Diferentes implementaciones tienen límites diferentes para la capacidad de la tubería. Las aplicaciones no deben depender de una capacidad particular: una aplicación debe diseñarse de modo que un proceso lector consuma los datos tan pronto como estén disponibles, para que un proceso escritor no permanezca bloqueado.

Antes de Linux 2.6.11, la capacidad de una tubería era la misma que el tamaño de página del sistema (por ejemplo, 4096 bytes en i386). Desde Linux 2.6.11, la capacidad de la tubería es de 16 páginas (es decir, 65.536 bytes en un sistema con tamaño de página de 4096 bytes). Desde Linux 2.6.35, la capacidad predeterminada de la tubería es de 16 páginas, pero la capacidad se puede consultar y establecer usando las operaciones F_GETPIPE_SZ y F_SETPIPE_SZ de fcntl(2). Véase fcntl(2) para más información. Desde Linux 4.5, la capacidad predeterminada de la tubería es inferior a 16 páginas cuando se excede el límite pipe-user-pages-soft.

La siguiente operación de ioctl(2), que se puede aplicar a un descriptor de archivo que se refiere a cualquiera de los extremos de una tubería, coloca un recuento del número de bytes no leídos en la tubería en el búfer int al que apunta el último argumento de la llamada:


ioctl(fd, FIONREAD, &nbytes);

La operación FIONREAD no está especificada en ningún estándar, pero se proporciona en muchas implementaciones.

Archivos /proc

En Linux, los siguientes archivos controlan cuánta memoria se puede usar para tuberías:

/proc/sys/fs/pipe-max-pages (solo en Linux 2.6.34)
Un límite superior, en páginas, en la capacidad que un usuario no privilegiado (uno sin la capacidad CAP_SYS_RESOURCE) puede establecer para una tubería.
El valor predeterminado para este límite es 16 veces la capacidad predeterminada de la tubería (véase más arriba); el límite inferior es de dos páginas.
Esta interfaz se eliminó en Linux 2.6.35, en favor de /proc/sys/fs/pipe-max-size.
/proc/sys/fs/pipe-max-size (desde Linux 2.6.35)
El tamaño máximo (en bytes) de tuberías individuales que pueden ser establecidas por usuarios sin la capacidad CAP_SYS_RESOURCE. El valor asignado a este archivo puede redondearse hacia arriba, para reflejar el valor realmente empleado para una implementación conveniente. Para determinar el valor redondeado, muestre el contenido de este archivo después de asignarle un valor.
El valor predeterminado para este archivo es 1048576 (1 MiB). El valor mínimo que se puede asignar a este archivo es el tamaño de página del sistema. Los intentos de establecer un límite inferior al tamaño de página provocan que write(2) falle con el error EINVAL.
Desde Linux 4.9, el valor en este archivo también actúa como un techo para la capacidad predeterminada de una nueva tubería o FIFO recién abierta.
/proc/sys/fs/pipe-user-pages-hard (desde Linux 4.5)
El límite estricto del tamaño total (en páginas) de todas las tuberías creadas o establecidas por un solo usuario no privilegiado (es decir, uno que no tiene ni la capacidad CAP_SYS_RESOURCE ni la CAP_SYS_ADMIN). Mientras el número total de páginas asignadas a los búferes de tubería para este usuario esté en este límite, los intentos de crear nuevas tuberías serán denegados, y los intentos de aumentar la capacidad de una tubería serán denegados.
Cuando el valor de este límite es cero (que es el predeterminado), no se aplica ningún límite estricto.
/proc/sys/fs/pipe-user-pages-soft (desde Linux 4.5)
El límite blando del tamaño total (en páginas) de todas las tuberías creadas o establecidas por un solo usuario no privilegiado (es decir, uno que no tiene ni la capacidad CAP_SYS_RESOURCE ni la CAP_SYS_ADMIN). Mientras el número total de páginas asignadas a los búferes de tubería para este usuario esté en este límite, las tuberías individuales creadas por un usuario estarán limitadas a dos páginas (una página antes de Linux 5.14), y los intentos de aumentar la capacidad de una tubería serán denegados.
Cuando el valor de este límite es cero, no se aplica ningún límite blando. El valor predeterminado para este archivo es 16384, lo que permite crear hasta 1024 tuberías con la capacidad predeterminada.

Antes de Linux 4.9, algunos errores afectaron el manejo de los límites pipe-user-pages-soft y pipe-user-pages-hard; véase ERRORES.

PIPE_BUF

POSIX.1 dice que las escrituras de menos de PIPE_BUF bytes deben ser atómicas: los datos de salida se escriben en la tubería como una secuencia contigua. Las escrituras de más de PIPE_BUF bytes pueden ser nonatomicas: el kernel puede intercalar los datos con datos escritos por otros procesos. POSIX.1 requiere que PIPE_BUF sea al menos 512 bytes. (En Linux, PIPE_BUF es 4096 bytes). La semántica precisa depende de si el descriptor de archivo no es bloqueante (O_NONBLOCK), si hay múltiples escritores

pipe(7) - Linux manual pages

NOMBRE

pipe - tuberías de comunicación entre procesos

DESCRIPCIÓN

Una tubería es un conducto de comunicación unidireccional. Los datos escritos en una tubería pueden ser leídos por otro proceso. Las tuberías son útiles para la comunicación entre procesos (IPC) y se implementan comúnmente usando la llamada al sistema pipe(2).

Las tuberías son un tipo especial de archivo, similar a los archivos regulares, pero con algunas diferencias clave:

  • Los datos escritos en una tubería se leen en el mismo orden.
  • Las tuberías son unidireccionales: los datos fluyen solo en una dirección.
  • Las tuberías no tienen un nombre en el sistema de archivos y solo existen mientras los procesos que las usan están activos.

Cuando se crea una tubería con pipe(2), se devuelven dos descriptores de archivo: uno para leer y otro para escribir. El descriptor de escritura se usa para escribir datos en la tubería, y el descriptor de lectura se usa para leer datos de la tubería.

El tamaño de la tubería está limitado por el valor de PIPE_BUF. Si se escribe más de PIPE_BUF bytes en la tubería de una vez, el comportamiento depende del indicador de apertura O_NONBLOCK y del tamaño de los datos a escribir.

Límites del tamaño de la tubería

El tamaño máximo de escritura atómica en una tubería se define por la constante simbólica PIPE_BUF. Su valor exacto depende del sistema, pero está garantizado que sea al menos 512 bytes.

El comportamiento de la operación de escritura en una tubería depende de si el indicador O_NONBLOCK está habilitado y del número de bytes a escribir (n) en comparación con PIPE_BUF:

O_NONBLOCK deshabilitado, n <= PIPE_BUF
write(2) escribe todos los n bytes atómicamente; write(2) puede bloquearse si no hay espacio suficiente para escribir n bytes inmediatamente.
O_NONBLOCK habilitado, n <= PIPE_BUF
Si hay espacio para escribir n bytes en la tubería, write(2) se completa inmediatamente, escribiendo los n bytes; de lo contrario, write(2) falla, con errno establecido en EAGAIN.
O_NONBLOCK deshabilitado, n > PIPE_BUF
La escritura no es atómica: los datos proporcionados a write(2) pueden intercalarse con las escrituras de otros procesos; write(2) se bloquea hasta que se hayan escrito n bytes.
O_NONBLOCK habilitado, n > PIPE_BUF
Si la tubería está llena, write(2) falla, con errno establecido en EAGAIN. De lo contrario, se pueden escribir de 1 a n bytes (es decir, puede ocurrir una "escritura parcial"; la aplicación que llama debe verificar el valor de retorno de write(2) para ver cuántos bytes se escribieron realmente), y estos bytes pueden intercalarse con escrituras de otros procesos.

Indicadores de estado del archivo abierto

Los únicos indicadores de estado del archivo abierto que se pueden aplicar de forma significativa a una tubería o FIFO son O_NONBLOCK y O_ASYNC.

Establecer el indicador O_ASYNC para el extremo de lectura de una tubería provoca que se genere una señal (SIGIO por defecto) cuando haya nueva entrada disponible en la tubería. El destino para la entrega de señales debe establecerse usando el comando fcntl(2) F_SETOWN. En Linux, O_ASYNC es compatible con tuberías y FIFOs solo desde Linux 2.6.

Notas de portabilidad

En algunos sistemas (pero no en Linux), las tuberías son bidireccionales: los datos se pueden transmitir en ambas direcciones entre los extremos de la tubería. POSIX.1 solo requiere tuberías unidireccionales. Las aplicaciones portátiles deben evitar depender de la semántica de tuberías bidireccionales.

ERRORES

Antes de Linux 4.9, algunos errores afectaron el manejo de los límites pipe-user-pages-soft y pipe-user-pages-hard al usar la operación fcntl(2) F_SETPIPE_SZ para cambiar la capacidad de una tubería:

(a)
Al aumentar la capacidad de la tubería, las comprobaciones contra los límites blando y duro se realizaban sobre el consumo existente y excluían la memoria requerida para la capacidad aumentada de la tubería. El nuevo aumento de la capacidad de la tubería podría entonces empujar la memoria total utilizada por el usuario para las tuberías (posiblemente muy por encima) del límite. (Esto también podría desencadenar el problema descrito a continuación).
A partir de Linux 4.9, la verificación de límites incluye la memoria requerida para la nueva capacidad de la tubería.
(b)
Las verificaciones de límites se realizaban incluso cuando la nueva capacidad de la tubería era menor que la capacidad existente de la tubería. Esto podría generar problemas si un usuario establecía una gran capacidad de tubería y luego se bajaban los límites, con el resultado de que el usuario ya no podía disminuir la capacidad de la tubería.
A partir de Linux 4.9, las verificaciones contra los límites solo se realizan al aumentar la capacidad de una tubería; un usuario no privilegiado siempre puede disminuir la capacidad de una tubería.
(c)
La contabilidad y la verificación contra los límites se realizaban de la siguiente manera:
(1)
Probar si el usuario ha excedido el límite.
(2)
Realizar la nueva asignación de búfer de tubería.
(3)
Contabilizar la nueva asignación contra los límites.
Esto era propenso a condiciones de carrera. Múltiples procesos podían pasar el punto (1) simultáneamente, y luego asignar búferes de tubería que solo se contabilizaban en el paso (3), con el resultado de que la asignación de búferes de tubería del usuario podía exceder el límite.
A partir de Linux 4.9, el paso de contabilidad se realiza antes de la asignación, y la operación falla si se excede el límite.

Antes de Linux 4.9, errores similares a los puntos (a) y (c) también podían ocurrir cuando el kernel asignaba memoria para un nuevo búfer de tubería; es decir, al llamar a pipe(2) y al abrir un FIFO previamente no abierto.
