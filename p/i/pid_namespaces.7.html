NOMBRE

pid_namespaces - resumen de los namespaces PID de Linux

DESCRIPCIÓN

Para un resumen de los namespaces, ver namespaces(7).

Los namespaces PID aíslan el espacio de números de identificación de proceso, lo que significa que los procesos en diferentes namespaces PID pueden tener el mismo PID. Los namespaces PID permiten a los contenedores proporcionar funcionalidades tales como suspender/reanudar el conjunto de procesos en el contenedor y migrar el contenedor a un nuevo host mientras los procesos dentro del contenedor mantienen los mismos PIDs.

Los PIDs en un nuevo namespace PID comienzan en 1, similar a un sistema autónomo, y las llamadas a fork(2), vfork(2), o clone(2) producirán procesos con PIDs que son únicos dentro del namespace.

El uso de namespaces PID requiere un kernel configurado con la opción CONFIG_PID_NS.

El proceso init del namespace

El primer proceso creado en un nuevo namespace (es decir, el proceso creado usando clone(2) con el flag CLONE_NEWPID, o el primer hijo creado por un proceso después de una llamada a unshare(2) usando el flag CLONE_NEWPID) tiene el PID 1, y es el proceso "init" para el namespace (ver init(1)). Este proceso se convierte en el padre de cualquier proceso hijo que quede huérfano porque un proceso que reside en este namespace PID terminó (ver más abajo para más detalles).

Si el proceso "init" de un namespace PID termina, el kernel termina todos los procesos en el namespace a través de una señal SIGKILL. Este comportamiento refleja el hecho de que el proceso "init" es esencial para el correcto funcionamiento de un namespace PID. En este caso, una llamada posterior a fork(2) a este namespace PID fallará con el error ENOMEM; no es posible crear un nuevo proceso en un namespace PID cuyo proceso "init" ha terminado. Tales escenarios pueden ocurrir cuando, por ejemplo, un proceso utiliza un descriptor de archivo abierto para un archivo /proc/pid/ns/pid correspondiente a un proceso que estaba en un namespace para setns(2) a ese namespace después de que el proceso "init" ha terminado. Otro escenario posible puede ocurrir después de una llamada a unshare(2): si el primer hijo creado posteriormente por un fork(2) termina, entonces las llamadas posteriores a fork(2) fallarán con ENOMEM.

Solo las señales para las cuales el proceso "init" ha establecido un manejador de señales pueden ser enviadas al proceso "init" por otros miembros del namespace PID. Esta restricción se aplica incluso a procesos privilegiados, y evita que otros miembros del namespace PID maten accidentalmente al proceso "init".

Igualmente, un proceso en un namespace ancestral puede —sujeto a las comprobaciones de permisos habituales descritas en kill(2)— enviar señales al proceso "init" de un namespace PID hijo solo si el proceso "init" ha establecido un manejador para esa señal. (Dentro del manejador, el campo si_pid de siginfo_t descrito en sigaction(2) será cero.) SIGKILL o SIGSTOP se tratan excepcionalmente: estas señales se entregan forzosamente cuando se envían desde un namespace PID ancestral. Ninguna de estas señales puede ser capturada por el proceso "init", y por lo tanto resultarán en las acciones habituales asociadas con esas señales (respectivamente, terminar y detener el proceso).

A partir de Linux 3.4, la llamada al sistema reboot(2) provoca el envío de una señal al proceso "init" del namespace. Ver reboot(2) para más detalles.

Anidamiento de namespaces PID

Los namespaces PID pueden anidarse: cada namespace PID tiene un padre, excepto el namespace PID inicial ("raíz"). El padre de un namespace PID es el namespace PID del proceso que creó el namespace usando clone(2) o unshare(2). Por lo tanto, los namespaces PID forman un árbol, con todos los namespaces rastreando finalmente su ascendencia hasta el namespace raíz. Desde Linux 3.7, el kernel limita la profundidad máxima de anidamiento para los namespaces PID a 32.

Un proceso es visible para otros procesos en su namespace PID, y para los procesos en cada namespace PID ancestral directo que se remonta al namespace PID raíz. En este contexto, "visible" significa que un proceso puede ser el objetivo de operaciones por parte de otro proceso usando llamadas al sistema que especifican un ID de proceso. A la inversa, los procesos en un namespace PID hijo no pueden ver procesos en el namespace padre y más alejados ancestros. Más sucintamente: un proceso puede ver (por ejemplo, enviar señales con kill(2), establecer valores nice con setpriority(2), etc.) solo los procesos contenidos en su propio namespace PID y en los descendientes de ese namespace.

Un proceso tiene un ID de proceso en cada una de las capas de la jerarquía de namespaces PID en las que es visible, y caminando hacia atrás a través de cada namespace ancestral directo hasta el namespace PID raíz. Las llamadas al sistema que operan sobre IDs de proceso siempre operan utilizando el ID de proceso que es visible en el namespace PID del llamante. Una llamada a getpid(2) siempre devuelve el PID asociado con el namespace en el que se creó el proceso.

Algunos procesos en un namespace PID pueden tener padres que están fuera del namespace. Por ejemplo, el padre del proceso inicial en el namespace (es decir, el proceso init(1) con PID 1) está necesariamente en otro namespace. Igualmente, los hijos directos de un proceso que usa setns(2) para que sus hijos se unan a un namespace PID están en un namespace PID diferente al del llamante de setns(2). Las llamadas a getppid(2) para tales procesos devuelven 0.

Si bien los procesos pueden descender libremente a namespaces PID hijos (por ejemplo, usando setns(2) con un descriptor de archivo de namespace PID), no pueden moverse en la dirección opuesta. Es decir, los procesos no pueden entrar a ningún namespace ancestral (padre, abuelo, etc.). Cambiar de namespaces PID es una operación unidireccional.

La operación NS_GET_PARENT de ioctl(2) puede usarse para descubrir la relación parental entre namespaces PID; ver ioctl_nsfs(2).

semántica de setns(2) y unshare(2)

Las llamadas a setns(2) que especifican un descriptor de archivo de namespace PID y las llamadas a unshare(2) con el flag CLONE_NEWPID hacen que los hijos creados posteriormente por el llamante se coloquen en un namespace PID diferente al del llamante. (Desde Linux 4.12, ese namespace PID se muestra a través del archivo /proc/pid/ns/pid_for_children, como se describe en namespaces(7).) Sin embargo, estas llamadas no cambian el namespace PID del proceso llamante, porque hacerlo cambiaría la idea del llamante de su propio PID (como lo informa getpid()), lo que rompería muchas aplicaciones y bibliotecas.

Dicho de otra manera: la membresía del namespace PID de un proceso se determina cuando el proceso es creado y no puede cambiarse después. Entre otras cosas, esto significa que la relación parental entre procesos refleja la relación parental entre namespaces PID: el padre de un proceso está ya sea en el mismo namespace o reside en el namespace PID padre inmediato.

Un proceso puede llamar a unshare(2) con el flag CLONE_NEWPID solo una vez. Después de haber realizado esta operación, su enlace simbólico /proc/pid/ns/pid_for_children estará vacío hasta que se cree el primer hijo en el namespace.

Adopción de hijos huérfanos

Cuando un proceso en un namespace PID termina, sus hijos son adoptados por el proceso "init" de ese namespace (el proceso con PID 1). Si el proceso "init" de un namespace PID termina, todos los procesos descendientes en ese namespace son terminados por el kernel con una señal SIGKILL.

clone(2), fork(2), getpid(2), init(1), namespaces(7), setns(2), signal(7), unshare(2)

ADOPCIÓN DE NIÑOS HUÉRFANOS

Cuando un proceso hijo queda huérfano, se le reasigna al proceso "init" en el espacio de nombres PID de su padre (a menos que uno de los ancestros más cercanos del padre haya empleado el comando prctl(2) PR_SET_CHILD_SUBREAPER para marcarse a sí mismo como el que se hará cargo de los procesos descendientes huérfanos). Tenga en cuenta que, debido a las semánticas de setns(2) y unshare(2) descritas anteriormente, este podría ser el proceso "init" en el espacio de nombres PID que es el *padre* del espacio de nombres PID del hijo, en lugar del proceso "init" en el propio espacio de nombres PID del hijo.

Compatibilidad de CLONE_NEWPID con otros flags CLONE_*

En las versiones actuales de Linux, CLONE_NEWPID no se puede combinar con CLONE_THREAD. Los hilos deben estar en el mismo espacio de nombres PID para que los hilos de un proceso puedan enviarse señales entre sí. Del mismo modo, debe ser posible ver todos los hilos de un proceso en el sistema de archivos proc(5). Además, si dos hilos estuvieran en espacios de nombres PID diferentes, el ID del proceso que envía una señal no se podría codificar de manera significativa cuando se envía una señal (vea la descripción del tipo siginfo_t en sigaction(2)). Dado que esto se calcula cuando se pone en cola una señal, una cola de señales compartida por procesos en múltiples espacios de nombres PID invalidaría eso.

En versiones anteriores de Linux, CLONE_NEWPID también estaba prohibido (fallando con el error EINVAL) en combinación con CLONE_SIGHAND (antes de Linux 4.3), así como con CLONE_VM (antes de Linux 3.12). Los cambios que levantaron estas restricciones también se han portado a kernels estables anteriores.

/proc y los espacios de nombres PID

Un sistema de archivos /proc muestra (en los directorios /proc/pid) solo los procesos visibles en el espacio de nombres PID del proceso que realizó el montaje, incluso si el sistema de archivos /proc se ve desde procesos en otros espacios de nombres.

Después de crear un nuevo espacio de nombres PID, es útil que el hijo cambie su directorio raíz y monte una nueva instancia de procfs en /proc para que herramientas como ps(1) funcionen correctamente. Si se crea simultáneamente un nuevo espacio de nombres de montaje al incluir CLONE_NEWNS en el argumento flags de clone(2) o unshare(2), entonces no es necesario cambiar el directorio raíz: se puede montar una nueva instancia de procfs directamente sobre /proc.

Desde un shell, el comando para montar /proc es:


$ mount -t proc proc /proc

Llamar a readlink(2) en la ruta /proc/self devuelve el ID del proceso del llamador en el espacio de nombres PID del montaje de procfs (es decir, el espacio de nombres PID del proceso que montó el procfs). Esto puede ser útil para fines de introspección, cuando un proceso quiere descubrir su PID en otros espacios de nombres.

Archivos /proc

/proc/sys/kernel/ns_last_pid (desde Linux 3.3)
Este archivo (que está virtualizado por espacio de nombres PID) muestra el último PID que se asignó en este espacio de nombres PID. Cuando se asigne el próximo PID, el kernel buscará el PID no asignado más bajo que sea mayor que este valor, y cuando este archivo se lea posteriormente, mostrará ese PID.
Este archivo es escribible por un proceso que tiene la capacidad CAP_SYS_ADMIN o (desde Linux 5.9) CAP_CHECKPOINT_RESTORE dentro del espacio de nombres de usuario que posee el espacio de nombres PID. Esto hace posible determinar el PID que se asigna al próximo proceso que se crea dentro de este espacio de nombres PID.

Varios

Cuando un ID de proceso se pasa a través de un socket de dominio UNIX a un proceso en un espacio de nombres PID diferente (ver la descripción de SCM_CREDENTIALS en unix(7)), se traduce al valor PID correspondiente en el espacio de nombres PID del proceso receptor.
