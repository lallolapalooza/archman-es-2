PIMSYNC.CONF(5) Manual de formatos de archivo PIMSYNC.CONF(5)

NOMBRE

pimsync.conf — archivo de configuración para pimsync(1)

DESCRIPCIÓN

pimsync.conf se divide en tres tipos principales de secciones:

CONFIGURACIÓN GLOBAL
Ajustes globales para pimsync.
SECCIONES DE ALMACENAMIENTO
Configuración para almacenamientos individuales.
SECCIONES DE PAREJA
Reglas para sincronizar parejas de almacenamientos.

Ver pimsync(1) para detalles sobre la ruta por defecto del archivo de configuración y cómo especificar una ruta alternativa.

CONFIGURACIÓN GLOBAL

Los siguientes ajustes se pueden establecer globalmente:

status_path ruta
Ruta a un directorio que contendrá la base de datos de estado utilizada internamente por pimsync.

SECCIONES DE ALMACENAMIENTO

Un almacenamiento describe una ubicación donde se guardan calendarios o contactos. Cada almacenamiento se declara en su propia sección, y cada sección de almacenamiento comienza con la declaración del nombre del almacenamiento.

storage nombre {…}
Declara un almacenamiento con el nombre nombre.

Las directivas se declaran dentro de las llaves para cada sección, una por línea. Las siguientes directivas se aplican a todos los tipos de almacenamiento:

type tipo
Donde tipo puede ser uno de los siguientes:
vdir/icalendar
Un directorio donde cada subdirectorio representa un calendario. Cada uno de estos subdirectorios contiene archivos iCalendar individuales, cada uno representando un evento (o una serie de eventos recurrentes), tarea o entrada de diario.
vdir/vcard
Un directorio donde cada subdirectorio representa una agenda. Cada uno de estos subdirectorios contiene archivos vCard individuales, cada uno representando un contacto.
caldav
Un servidor CalDAV, que contiene calendarios con eventos, tareas y/o entradas de diario.
carddav
Un servidor CardDAV que contiene agendas con contactos.
webcal
Un recurso HTTP o HTTPS que expone un único archivo iCalendar que puede contener cero o más eventos, tareas o entradas de diario. Este almacenamiento es de solo lectura.
jmap/icalendar
Un servidor JMAP con soporte de calendario. ¡Este almacenamiento es experimental y aún puede contener errores graves!
jmap/vcard
Un servidor JMAP con soporte de calendario. ¡Este almacenamiento es experimental y aún puede contener errores graves!
interval segundos
Cuando monitorear un almacenamiento no es posible, verifica cambios cada la cantidad de segundos especificada. El valor por defecto es 300 segundos.
readonly
No realizar ninguna operación de escritura en este almacenamiento. Esta directiva no toma parámetros.

Los almacenamientos de tipo vdir aceptan las siguientes directivas:

path ruta
Ruta a un directorio que almacena un vdir. Una tilde inicial se expandirá para coincidir con el directorio de inicio del usuario actual.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

fileext extensión
Opcional. Extensión de archivo para los elementos guardados en este vdir. Si no se especifica, se usa ics para los almacenamientos de calendario y vcf para los almacenamientos de agenda.

Los almacenamientos de tipo caldav o carddav aceptan las siguientes directivas:

url url
URL del servidor Dav. Si esta URL no informa las capacidades DAV apropiadas, se realizará un descubrimiento de servicio para esta URL y su dominio para encontrar la ubicación exacta del servidor y la colección del conjunto de inicio.

Las URLs deben especificar el esquema http, https. o unix. Las URLs que comienzan con unix:// se tratarán como una ruta a un socket de dominio Unix.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

username nombre de usuario
Opcional. Nombre de usuario a utilizar para la autenticación HTTP Basic.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

password contraseña
Opcional. Contraseña a utilizar para la autenticación HTTP Basic.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

collection_id_segment last | second-last
Opcional. Segmento de ruta de la URL a utilizar como ID de colección. Los valores válidos son last (el valor por defecto) o second-last. Ver la documentación de uso avanzado para más detalles.

Los almacenamientos de tipo webcal aceptan las siguientes directivas:

url url
URL de un archivo iCalendar. Este archivo puede contener múltiples elementos de calendario. El esquema debe ser http o https.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

collection_id nombre
Nombre a utilizar al mapear esta colección a otra en el almacenamiento opuesto.

Los almacenamientos de tipo jmap aceptan las siguientes directivas:

url url
URL base del servidor JMAP.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

username nombre de usuario
Opcional. Nombre de usuario a utilizar para la autenticación HTTP Basic.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

password contraseña
Opcional. Contraseña a utilizar para la autenticación HTTP Basic.

Soporta PARÁMETROS DINÁMICOS (ver abajo).

DIRECTIVAS DE CONFIGURACIÓN

Las siguientes directivas pueden usarse para configurar el comportamiento de pimsync. Pueden aparecer en la sección principal del archivo de configuración, o dentro de una sección storage.

user_agent user_agent
Opcional. Establece la cabecera User-Agent a user_agent para las solicitudes HTTP salientes. El valor predeterminado utiliza "pimsync/" seguido del número de versión actual. Por ejemplo: pimsync/1.0.0.
tls_root path
Opcional. Utiliza el almacén de certificados raíz en path al verificar el certificado TLS del servidor. Deshabilita la verificación del certificado contra las autoridades de certificados del sistema. Ver tls_fingerprint a continuación.
tls_fingerprint fingerprint
Opcional. Acepta el certificado si su huella digital coincide con fingerprint. Si se especifica junto con la directiva tls_root, el certificado se verifica con la raíz especificada. Si tls_root no se especifica, el certificado del servidor no se valida contra ninguna raíz y solo se realiza una verificación de huella digital.
auth_cert certificate key
Opcional. Utiliza el certificate y la key proporcionados para la autenticación de cliente TLS.
auth_cert pem_bundle
Opcional. Utiliza el certificado y la clave del paquete especificado para la autenticación de cliente TLS.

PARÁMETROS DINÁMICOS

Los campos url, username, password y path pueden definirse en el archivo de configuración o pueden especificar un bloque con un comando para recuperar este valor de un sistema externo. Al especificar un comando externo, en lugar de definir un valor para la directiva, especifique un nuevo bloque con una sola directiva cmd.

Por ejemplo, para leer una contraseña a través del comando externo secret-store --get-caldav-password, use la siguiente sintaxis:

password {
	cmd secret-store --get-caldav-password
}

También es posible especificar un script de shell, que se ejecuta a través de 'sh -c'. Por ejemplo:

password {
	shell pass show communication/migadu.com | head -1
}

Se recomienda almacenar credenciales y otros valores sensibles en un servicio de almacenamiento seguro.

SECCIONES DE PAREJA

Una pareja declara cómo se sincronizarán dos almacenes entre sí. Cada sección de pareja comienza con la declaración del nombre de la pareja:

pair name {…}
Declara una pareja con el nombre name.

Cada pareja se define por un bloque de directivas, una por línea, entre llaves:

storage_a name
El name del primer almacén que se sincronizará con otro.
storage_b name
El name del segundo almacén que se sincronizará con el otro.
collections all
Sincroniza todas las colecciones encontradas en ambos almacenes. Las colecciones se sincronizarán con otras que tengan un id coincidente en el otro lado. Este es el valor recomendado si simplemente desea sincronizar todas las colecciones de ambos almacenes.
collections from a
Sincroniza todas las colecciones encontradas en storage_a. Cada colección se sincronizará con la colección que tenga el mismo id de colección en storage_b.
collections from b
Sincroniza todas las colecciones encontradas en storage_b. Cada colección se sincronizará con la colección que tenga el mismo id de colección en storage_a.
collection id
Sincroniza la colección con el id id. Se puede especificar más de una vez.
collection file ... {…}
Sincroniza la colección definida por las reglas dadas. Ver SECCIONES DE COLECCIÓN a continuación. Se puede especificar más de una vez.
on_empty skip
Cuando una colección se vacía por completo en un lado, se omite. Este es el valor predeterminado.
on_empty sync
Cuando una colección se vacía por completo en un lado, se vacía su contraparte en el otro lado. Tenga cuidado al usar esta opción. Si elimina completamente una colección en un lado, pimsync.conf no la restaurará. En su lugar, eliminará la misma colección (y todos sus elementos) en el otro lado.
on_delete sync
Cuando la propia colección se elimina en un lado, se elimina en el otro lado. Esto solo se aplica si la colección ya está vacía. Este es el valor predeterminado. Esto es generalmente seguro, especialmente cuando se combina con on_empty skip.
on_delete skip
Cuando la propia colección se elimina en un lado, se omite.

La directiva conflict_resolution especifica qué acción se debe tomar si un elemento se modificó en ambos lados:

conflict_resolution cmd command [args]
Ejecuta command para resolver conflictos entre ambos lados. args se pasarán como argumentos, seguidos de la ruta a dos archivos; uno que contiene los datos en el almacén a, y el otro que contiene los datos en el almacén b. El conflicto se considerará resuelto si y solo si ambos archivos son iguales cuando el comando finalice y el comando finalice con un código de salida cero.
conflict_resolution keep a
En caso de conflicto, conserva la versión del almacén a.
conflict_resolution keep b
En caso de conflicto, conserva la versión del almacén a.

SECCIONES DE COLECCIÓN

Un bloque de colecciones define un mapeo entre dos colecciones que se van a sincronizar; una de ellas en storage_a y la otra en storage_b.

Estas secciones solo se utilizan en configuraciones avanzadas que necesitan mapear colecciones existentes entre sí sin cambiar su ubicación en ninguno de los lados.

Cada bloque debe incluir un alias:

alias name
Un alias para este par de colecciones que se utilizará para cualquier salida.

Se debe incluir exactamente una referencia a una colección en storage_a:

id_a id
Utiliza la colección con el id id.
href_a href
Utiliza la colección con la ruta href.

Se debe incluir exactamente una referencia a una colección en storage_b:

id_b id
Utiliza la colección con el id id.
href_b href
Utiliza la colección con la ruta href.

Por ejemplo, para sincronizar una colección con id work con otra en la ruta /calendars/mine/work/, use:

collection {
	alias work
	id_a work
	href_b /calendars/mine/work/
}
Especificar un id y un href para el mismo almacén no está permitido.

ID DE COLECCIÓN

El id de una colección es un concepto específico de pimsync(1) y vdirsyncer(1).

Para los almacenes vdir, el id de una colección es el nombre del directorio que le corresponde.

Para los almacenes caldav o carddav, el id de una colección es el último componente de su URL por defecto. Esto se puede cambiar para usar el penúltimo componente a través de la directiva de configuración collection_id_segment.

Para los almacenes webcal, el id debe especificarse explícitamente a través de la directiva de configuración collection_id.

A menos que se configure de otra manera, las colecciones con el mismo id en ambos almacenes se sincronizan entre sí.

EXAMPLES

Este ejemplo sincroniza dos almacenamientos con libretas de direcciones. El primero es un conjunto local de directorios que contienen archivos vCard, el segundo son servidores remotos CardDAV. Las credenciales se proporcionan a través de la herramienta de línea de comandos hiq(1).

status_path "~/.local/share/pimsync/status/"

pair contacts {
	storage_a contacts_local
	storage_b contacts_remote
	collections all
	conflict_resolution cmd nvim -d
}

storage contacts_local {
	type vdir/vcard
	path ~/.local/share/contacts/cards/
	fileext vcf
	interval 30
}

storage contacts_remote {
	type carddav
	url https://carddav.example.com/
	username hugo@example.com
	password {
		cmd hiq -dFpassword proto=carddavs username=hugo@example.com
	}
	interval 30
}

El siguiente ejemplo sincroniza dos almacenamientos con datos de calendario. El primero son directorios locales con archivos iCalendar, el segundo es un servidor remoto CalDAV.

status_path "~/.local/share/pimsync/status/"

pair calendars {
	storage_a calendars_local
	storage_b calendars_remote
	collections from b
	conflict_resolution cmd nvim -d
}

storage calendars_local {
	type vdir/icalendar
	path ~/.local/share/calendars/
	fileext ics
	interval 30
}

storage calendars_remote {
	type caldav
	url https://caldav.example.com/
	username hugo@example.com
	password {
	 cmd hiq -dFpassword proto=caldavs username=hugo@example.com
	}
	interval 30
}

El siguiente ejemplo sincroniza dos almacenamientos con datos de calendario. El primero es un directorio local llamado "italki" con archivos de calendario, el segundo es un servidor http que publica un archivo iCalendar.

Tenga en cuenta que el primer almacenamiento es el mismo que el anterior, y solo debe especificarse una vez si ambas configuraciones se especifican en el mismo archivo.

La URL exacta del archivo iCalendar expuesto a través de http se obtiene a través de la herramienta hiq(1), utilizada para consultar el almacén de secretos himitsu(7).

status_path "~/.local/share/pimsync/status/"

pair study_calendars {
	storage_a calendars_local
	storage_b calendars_italki
	collection italki
}

storage calendars_local {
	type vdir/icalendar
	path ~/.local/share/calendars/
	fileext ics
	interval 30
}

storage calendars_italki {
	type webcal
	collection_id italki
	url {
		cmd hiq -dFurl proto=webcal alias=italki-mine
	}
}

Este ejemplo sincroniza dos almacenamientos con datos de calendario. El primero es un servidor CardDAV, al que se accede a través de un socket de dominio Unix. El segundo almacenamiento utiliza un sistema de archivos local con archivos vCard.

status_path "~/.local/share/pimsync/status/"

pair unixtest {
	storage_a unix_a
	storage_b unix_b
	collections all
}

storage unix_a {
	type carddav
	url unix:///tmp/xandikos.sock
}

storage unix_b {
	type vdir/vcard
	path /tmp/test_storage/
	fileext vcf
}
