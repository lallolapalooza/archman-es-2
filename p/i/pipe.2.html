pipe(2) Manual de llamadas al sistema pipe(2)

NOMBRE

pipe, pipe2 - crear tubería

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <unistd.h>
int pipe(int pipefd[2]);
#define _GNU_SOURCE             /* Ver feature_test_macros(7) */
#include <fcntl.h>              /* Definición de constantes O_* */
#include <unistd.h>
int pipe2(int pipefd[2], int flags);
/* En Alpha, IA-64, MIPS, SuperH y SPARC/SPARC64, pipe() tiene el
   siguiente prototipo; ver VERSIONS */
#include <unistd.h>
struct fd_pair {
    long fd[2];
};
struct fd_pair pipe(void);

DESCRIPCIÓN

pipe() crea una tubería, un canal de datos unidireccional que puede usarse para la comunicación entre procesos. El array pipefd se usa para devolver dos descriptores de archivo que se refieren a los extremos de la tubería. pipefd[0] se refiere al extremo de lectura de la tubería. pipefd[1] se refiere al extremo de escritura de la tubería. Los datos escritos en el extremo de escritura de la tubería son almacenados en búfer por el kernel hasta que se leen del extremo de lectura de la tubería. Para más detalles, ver pipe(7).

Si flags es 0, entonces pipe2() es lo mismo que pipe(). Los siguientes valores pueden ser combinados mediante OR bit a bit en flags para obtener un comportamiento diferente:

O_CLOEXEC
Establece el flag de cierre al ejecutar (FD_CLOEXEC) en los dos nuevos descriptores de archivo. Ver la descripción del mismo flag en open(2) para saber por qué esto puede ser útil.
O_DIRECT (desde Linux 3.4)
Crea una tubería que realiza I/O en modo "paquete". Cada write(2) a la tubería se trata como un paquete separado, y las read(2) desde la tubería leerán un paquete a la vez. Tenga en cuenta los siguientes puntos:
•
Las escrituras de más de PIPE_BUF bytes (ver pipe(7)) se dividirán en múltiples paquetes. La constante PIPE_BUF se define en <limits.h>.
•
Si una read(2) especifica un tamaño de búfer menor que el siguiente paquete, entonces se leen el número de bytes solicitados y los bytes excedentes en el paquete se descartan. Especificar un tamaño de búfer de PIPE_BUF será suficiente para leer los paquetes más grandes posibles (ver el punto anterior).
•
Los paquetes de longitud cero no son compatibles. (Una read(2) que especifica un tamaño de búfer de cero es una operación nula y devuelve 0).
Los kernels anteriores que no soportan este flag lo indicarán con un error EINVAL.
Desde Linux 4.5, es posible cambiar la configuración O_DIRECT de un descriptor de archivo de tubería usando fcntl(2).
O_NONBLOCK
Establece el flag de estado de archivo O_NONBLOCK en las descripciones de archivo abiertas a las que se refieren los nuevos descriptores de archivo. Usar este flag ahorra llamadas adicionales a fcntl(2) para lograr el mismo resultado.
O_NOTIFICATION_PIPE
Desde Linux 5.8, el mecanismo general de notificación se construye sobre la tubería, donde el kernel inserta mensajes de notificación en las tuberías abiertas por el espacio de usuario. El propietario de la tubería debe indicar al kernel qué fuentes de eventos observar y también se pueden aplicar filtros para seleccionar qué subeventos se colocarán en la tubería.

VALOR DE RETORNO

En caso de éxito, se devuelve cero. En caso de error, se devuelve -1, se establece errno para indicar el error y pipefd permanece sin cambios.

En Linux (y otros sistemas), pipe() no modifica pipefd en caso de fallo. Un requisito que estandariza este comportamiento se añadió en POSIX.1-2008 TC2. La llamada al sistema específica de Linux pipe2() tampoco modifica pipefd en caso de fallo.

ERRORES

EFAULT
pipefd no es válido.
EINVAL
(pipe2()) Valor inválido en flags.
EMFILE
Se ha alcanzado el límite por proceso de número de descriptores de archivo abiertos.
ENFILE
Se ha alcanzado el límite total de archivos abiertos en todo el sistema.
ENFILE
Se ha alcanzado el límite de usuario (hard limit) de memoria que se puede asignar para tuberías y el llamante no tiene privilegios; ver pipe(7).
ENOPKG
(pipe2()) Se pasó O_NOTIFICATION_PIPE en flags y el soporte para notificaciones (CONFIG_WATCH_QUEUE) no está compilado en el kernel.

VERSIONES

La ABI de System V en algunas arquitecturas permite el uso de más de un registro para devolver múltiples valores; varias arquitecturas (a saber, Alpha, IA-64, MIPS, SuperH y SPARC/SPARC64) (ab)usan esta característica para implementar la llamada al sistema pipe() de manera funcional: la llamada no toma ningún argumento y devuelve un par de descriptores de archivo como valor de retorno en caso de éxito. La función wrapper pipe() de glibc se encarga de esto de forma transparente. Ver syscall(2) para información sobre los registros utilizados para almacenar el segundo descriptor de archivo.

Después de fork(2), cada proceso cierra los descriptores de archivo que no necesita para la tubería (ver pipe(7)).
