PCRE2POSIX(3) Manual de Funciones de Librería PCRE2POSIX(3)

NOMBRE

PCRE2 - Expresiones regulares compatibles con Perl (API revisada)

SINOPSIS

#include <pcre2posix.h>

int pcre2_regcomp(regex_t *preg, const char *pattern,
     int cflags);

int pcre2_regexec(const regex_t *preg, const char *string,
     size_t nmatch, regmatch_t pmatch[], int eflags);

size_t pcre2_regerror(int errcode, const regex_t *preg,
     char *errbuf, size_t errbuf_size);

void pcre2_regfree(regex_t *preg);

DESCRIPCIÓN

Este conjunto de funciones proporciona una API de estilo POSIX para la librería PCRE2 de expresiones regulares de 8 bits. No existen wrappers de estilo POSIX para las librerías de 16 y 32 bits de PCRE2. Consulte la documentación de pcre2api para obtener una descripción de la API nativa de PCRE2, que contiene funcionalidad adicional.

NOTA IMPORTANTE: Las funciones descritas aquí NO son seguras para hilos (thread-safe) y no deben usarse en aplicaciones multihilo. También están limitadas a procesar sujetos que no sean mayores de 2 GB. Use la API nativa en su lugar.

Estas funciones son funciones envoltorio que, en última instancia, llaman a la API nativa de PCRE2. Sus prototipos están definidos en el archivo de cabecera pcre2posix.h, y todas tienen nombres únicos que comienzan con pcre2_. Sin embargo, el archivo de cabecera pcre2posix.h también contiene definiciones de macros que convierten los nombres POSIX estándar como regcomp() en pcre2_regcomp(), etc. Esto significa que un programa puede usar los nombres POSIX habituales sin el riesgo de vincularse accidentalmente con funciones POSIX de otra librería.

En sistemas tipo Unix, la librería POSIX de PCRE2 se llama libpcre2-posix, por lo que se puede acceder añadiendo -lpcre2-posix al comando para enlazar una aplicación. Dado que las funciones POSIX llaman a las nativas, también es necesario añadir -lpcre2-8.

En sistemas Windows, si se enlaza a una versión DLL de la librería, se recomienda definir PCRE2POSIX_SHARED antes de incluir el archivo de cabecera pcre2posix.h, ya que permitirá una forma más eficiente de invocar las funciones añadiendo el decorador __declspec(dllimport).

Aunque no se definieron como prototipos en pcre2posix.h, las versiones 10.33 a 10.36 de la librería contenían funciones con los nombres POSIX regcomp(), etc. Estas simplemente pasaban sus argumentos a las funciones PCRE2. Estas funciones se proporcionaron para compatibilidad hacia atrás con versiones anteriores de PCRE2, que solo tenían nombres POSIX. Sin embargo, esto ha resultado problemático en situaciones donde un programa se enlaza con varias librerías, algunas de las cuales usan la interfaz POSIX de PCRE2 mientras que otras usan las funciones POSIX reales. Por esta razón, los nombres POSIX se eliminaron desde la versión 10.37.

Llamar al archivo de cabecera pcre2posix.h evita cualquier conflicto con otras librerías POSIX. Puede, por supuesto, renombrarse o aliasearse como regex.h, que es el nombre "correcto", si no hay conflicto. Proporciona dos tipos de estructuras, regex_t para formas internas compiladas, y regmatch_t para devolver subcadenas capturadas. También define algunas constantes cuyos nombres comienzan con "REG_"; estas se utilizan para establecer opciones e identificar códigos de error.

USANDO LAS FUNCIONES POSIX

Tenga en cuenta que estas funciones son solo wrappers de estilo POSIX para la API nativa de PCRE2. No proporcionan un comportamiento de expresiones regulares POSIX, y no son seguras para hilos ni siquiera compatibles con POSIX.

Se han implementado aquellos bits de opciones POSIX que se pueden mapear razonablemente a opciones nativas de PCRE2. Además, la opción REG_EXTENDED se define con el valor cero. Esto no tiene ningún efecto, pero dado que los programas escritos para la interfaz POSIX la utilizan frecuentemente, esto facilita la inserción de PCRE2 como librería de reemplazo. Otras opciones POSIX ni siquiera están definidas.

También hay algunas opciones que no están definidas por POSIX. Estas se han añadido a petición de usuarios que desean utilizar ciertas características específicas de PCRE2 a través de la interfaz de llamada POSIX o para añadir funcionalidad BSD o GNU.

Cuando se llama a PCRE2 a través de estas funciones, solo la API es de estilo similar a POSIX. La sintaxis y semántica de las expresiones regulares en sí mismas siguen siendo las de Perl, sujetas a la configuración de varias opciones de PCRE2, como se describe a continuación. "Similar a POSIX en estilo" significa que la API se aproxima a la definición POSIX; no es totalmente compatible con POSIX, y en dominios de codificación multielemento probablemente sea aún menos compatible.

Las descripciones siguientes utilizan los nombres reales de las funciones, pero, como se describió anteriormente, también se pueden usar los nombres POSIX estándar (sin el prefijo pcre2_).

COMPILANDO UN PATRÓN

La función pcre2_regcomp() se llama para compilar un patrón en una forma interna. Por defecto, el patrón es una cadena C terminada por un cero binario (pero consulte REG_PEND a continuación). El argumento preg es un puntero a una estructura regex_t que se utiliza como base para almacenar información sobre la expresión regular compilada. También se utiliza para entrada cuando se establece REG_PEND. La estructura regex_t utilizada por pcre2_regcomp() está definida en pcre2posix.h y no es la misma que la estructura utilizada por otras librerías que proporcionan coincidencia de estilo POSIX.

El argumento cflags es cero, o contiene uno o más de los bits definidos por las siguientes macros:


REG_DOTALL

La opción PCRE2_DOTALL se establece cuando la expresión regular se pasa para compilar a la función nativa. Tenga en cuenta que REG_DOTALL no forma parte del estándar POSIX.


REG_ICASE

La opción PCRE2_CASELESS se establece cuando la expresión regular se pasa para compilar a la función nativa.


REG_NEWLINE

La opción PCRE2_MULTILINE se establece cuando la expresión regular se pasa para compilar a la función nativa. Tenga en cuenta que esto *no* imita el comportamiento POSIX definido para REG_NEWLINE (ver la siguiente sección).


REG_NOSPEC

La opción PCRE2_LITERAL se establece cuando la expresión regular se pasa para compilar a la función nativa. Esto deshabilita todos los metacaracteres en el patrón, haciendo que se trate como una cadena literal. Las únicas otras opciones permitidas con REG_NOSPEC son REG_ICASE, REG_NOSUB, REG_PEND y REG_UTF. Tenga en cuenta que REG_NOSPEC no forma parte del estándar POSIX.


REG_NOSUB

Cuando un patrón compilado con esta bandera se pasa a pcre2_regexec() para la coincidencia, los argumentos nmatch y pmatch se ignoran y no se devuelven cadenas capturadas. Las versiones de la librería PCRE2 anteriores a la 10.22 solían establecer la opción de compilación PCRE2_NO_AUTO_CAPTURE, pero esto ya no ocurre porque deshabilita el uso de retroreferencias.


REG_PEND

Si se establece esta opción, el campo reg_endp en la estructura preg (que tiene el tipo const char *) debe configurarse para que apunte al carácter posterior al final del patrón antes de llamar a pcre2_regcomp(). El patrón en sí ahora puede contener ceros binarios, que se tratan como caracteres de datos. Sin REG_PEND, un cero binario termina el patrón y el campo re_endp se ignora. Esta es una extensión GNU al estándar POSIX y debe usarse con precaución en software destinado a ser portable a otros sistemas.


REG_UCP

La opción PCRE2_UCP se establece cuando la expresión regular se pasa para compilar a la función nativa. Esto hace que PCRE2 utilice propiedades Unicode al coincidir con \d, \w, etc., en lugar de solo reconocer valores ASCII. Tenga en cuenta que REG_UCP no forma parte del estándar POSIX.


REG_UNGREEDY

La opción PCRE2_UNGREEDY se establece cuando la expresión regular se pasa para compilar a la función nativa. Tenga en cuenta que REG_UNGREEDY no forma parte del estándar POSIX.


REG_UTF

La opción PCRE2_UTF se establece cuando la expresión regular se pasa para compilar a la función nativa. Esto hace que el patrón en sí y todas las cadenas de datos utilizadas para su coincidencia se traten como cadenas UTF-8. Tenga en cuenta que REG_UTF no forma parte del estándar POSIX.

En ausencia de estas banderas, no se pasan opciones a la función nativa. Esto significa que la expresión regular se compila con la semántica predeterminada de PCRE2. En particular, la forma en que maneja los caracteres de nueva línea en el.

pcre2posix(3) — PCRE2 POSIX API

NAME

pcre2posix - PCRE2 POSIX API wrapper

SYNOPSIS

#include <pcre2posix.h>

int regcomp(regex_t *preg, const char *regex, int cflags);
int regexec(const regex_t *preg, const char *string, size_t nmatch,
    regmatch_t pmatch[], int eflags);
size_t regerror(int errcode, const regex_t *preg, char *errbuf, size_t errbuf_size);
void regfree(regex_t *preg);
int regcomp_x(regex_t *preg, const char *regex, int cflags,
    const PCRE2_UCHAR *(*matching_context)(const char *),
    void *context_data);
int regexec_x(const regex_t *preg, const char *string, size_t nmatch,
    regmatch_t pmatch[], int eflags,
    const PCRE2_UCHAR *(*matching_context)(const char *),
    void *context_data);

DESCRIPTION

This module is a wrapper around the PCRE2 library which implements a POSIX-style API. The functions provided mirror those specified in the IEEE Standard 1003.2 (POSIX.2) specification for regular expression matching.

Note that PCRE2 is fundamentally a Perl-compatible regular expression engine, not a POSIX-compatible one. While this wrapper makes it possible to use PCRE2 via a POSIX API, it does not change the underlying matching behaviour. For example, PCRE2's default handling of newline characters is that of Perl, not POSIX.

USING THE POSIX FUNCTIONS

The functions are largely as described in the POSIX standard. The main differences are:

  • The Perl-style escape sequence \C is not supported, as it breaks POSIX string matching.
  • The POSIX flag REG_NOSUB is supported.
  • The PCRE2 internal options PCRE2_ANCHORED, PCRE2_CASELESS, PCRE2_DOLLAR_ENDONLY, PCRE2_EXTENDED, PCRE2_MULTILINE, PCRE2_NO_IGNORE_MATCH, PCRE2_NOTBOL, PCRE2_NOTEOL, PCRE2_UTF, and PCRE2_UNGREEDY can be passed via the cflags argument to regcomp() by using the PCRE2_* constants defined in pcre2.h. Note that the POSIX standard only defines REG_BASIC, REG_EXTENDED, REG_ICASE, REG_NOSUB, and REG_NEWLINE.

The regcomp_x and regexec_x functions are not POSIX standard, but allow custom matching contexts to be passed to the underlying PCRE2 functions.

COMPILING A PATTERN

The regcomp() function compiles the regular expression given by regex into an internal format, which is suitable for later use by regexec(). The result is stored in the structure pointed to by preg. The cflags argument is a bitmask of the following options:

REG_BASIC
Interpret the pattern as a Basic Regular Expression (BRE). This is the default.
REG_EXTENDED
Interpret the pattern as an Extended Regular Expression (ERE). This is equivalent to the PCRE2 option PCRE2_EXTENDED.
REG_ICASE
Ignore case during matching. This is equivalent to the PCRE2 option PCRE2_CASELESS.
REG_NOSUB
Do not report subexpression matches. If this option is set, then the pmatch argument to regexec() is ignored.
REG_NEWLINE
Modify the behaviour of the . and $ metacharacters. With this option, . matches any character except newline, and $ matches the end of the string, or any character followed by a newline. Without this option, . matches any character (including newline), and $ matches only the end of the string. This is different from the Perl way, not the POSIX way. Note that setting REG_NEWLINE only has *some* of the effects specified for REG_NEWLINE. It does not affect the way newlines are matched by the dot metacharacter (they are not) or by a negative class such as [^a] (they are).

The yield of pcre2_regcomp() is zero on success, and non-zero otherwise. The preg structure is filled in on success, and one other member of the structure (as well as re_endp) is public: re_nsub contains the number of capturing subpatterns in the regular expression. Various error codes are defined in the header file.

NOTE: If the yield of pcre2_regcomp() is non-zero, you must not attempt to use the contents of the preg structure. If, for example, you pass it to pcre2_regexec(), the result is undefined and your program is likely to crash.

MATCHING NEWLINE CHARACTERS

This area is not simple, because POSIX and Perl take different views of things. It is not possible to get PCRE2 to obey POSIX semantics, but then PCRE2 was never intended to be a POSIX engine. The following table lists the different possibilities for matching newline characters in Perl and PCRE2:


Default Change with


. matches newline no PCRE2_DOTALL
newline matches [^a] yes not changeable
$ matches \n at end yes PCRE2_DOLLAR_ENDONLY
$ matches \n in middle no PCRE2_MULTILINE
^ matches \n in middle no PCRE2_MULTILINE

This is the equivalent table for a POSIX-compatible pattern matcher:


Default Change with


. matches newline yes REG_NEWLINE
newline matches [^a] yes REG_NEWLINE
$ matches \n at end no REG_NEWLINE
$ matches \n in middle no REG_NEWLINE
^ matches \n in middle no REG_NEWLINE

This behaviour is not what happens when PCRE2 is called via its POSIX API. By default, PCRE2's behaviour is the same as Perl's, except that there is no equivalent for PCRE2_DOLLAR_ENDONLY in Perl. In both PCRE2 and Perl, there is no way to stop newline from matching [^a].

Default POSIX newline handling can be obtained by setting PCRE2_DOTALL and PCRE2_DOLLAR_ENDONLY when calling pcre2_compile() directly, but there is no way to make PCRE2 behave exactly as for the REG_NEWLINE action. When using the POSIX API, passing REG_NEWLINE to PCRE2's pcre2_regcomp() function causes PCRE2_MULTILINE to be passed to pcre2_compile(), and REG_DOTALL passes PCRE2_DOTALL. There is no way to pass PCRE2_DOLLAR_ENDONLY.

MATCHING A PATTERN

The function pcre2_regexec() is called to match a compiled pattern preg against a given string, which is by default terminated by a zero byte (but see REG_STARTEND below), subject to the options in eflags. These can be:


REG_NOTBOL

The PCRE2_NOTBOL option is set when calling the underlying PCRE2 matching function.


REG_NOTEMPTY

The PCRE2_NOTEMPTY option is set when calling the underlying PCRE2 matching function. Note that REG_NOTEMPTY is not part of the POSIX standard. However, setting this option can give more POSIX-like behaviour in some situations.


REG_NOTEOL

The PCRE2_NOTEOL option is set when calling the underlying PCRE2 matching function.


REG_STARTEND

When this option is set, the subject string starts at string + pmatch[0].rm_so and ends at string + pmatch[0].rm_eo, which should point to the first character beyond the string. There may be binary zeros within the subject string, and indeed, using REG_STARTEND is the only way to pass a subject string that contains a binary zero.

Whatever the value of pmatch[0].rm_so, the offsets of the matched string and any captured substrings are still given relative to the start of string itself. (Before PCRE2 release 10.30 these were given relative to string + pmatch[0].rm_so, but this differs from other implementations.)

This is a BSD extension, compatible with but not specified by IEEE Standard 1003.2 (POSIX.2), and should be used with caution in software intended to be portable to other systems. Note that a non-zero rm_so does not imply REG_NOTBOL; REG_STARTEND affects only the location and length of the string, not how it is matched. Setting REG_STARTEND and passing pmatch as NULL are mutually exclusive; the error REG_INVARG is returned.

If the pattern was compiled with the REG_NOSUB flag, no data about any matched strings is returned. The nmatch and pmatch arguments of pcre2_regexec() are ignored (except possibly as input for REG_STARTEND).

The value of nmatch may be zero, and the value pmatch may be NULL (unless REG_STARTEND is set); in both these cases no data about any matched strings is returned.

Otherwise, the portion of the string that was matched, and also any captured substrings, are returned via the pmatch argument, which points to an array of nmatch structures of type regmatch_t, containing the members rm_so and rm_eo. These contain the byte offset to the first character of each substring and the offset to the first character after the end of each substring, respectively. The 0th element of the vector relates to the entire portion of string that was matched; subsequent elements relate to the capturing subpatterns of the regular expression. Unused entries in the array have both structure members set to -1.

regmatch_t as well as the regoff_t typedef it uses are defined in pcre2posix.h and are not warranted to have the same size or layout as other similarly named types from other libraries that provide POSIX-style matching.

A successful match yields a zero return; various error codes are defined in the header file, of which REG_NOMATCH is the "expected" failure code.

ERROR MESSAGES

The pcre2_regerror() function maps a non-zero errorcode from either pcre2_regcomp() or pcre2_regexec() to a printable message. If preg is not NULL, the error should have arisen from the use of that structure. A message terminated by a binary zero is placed in errbuf. If the buffer is too short, only the first errbuf_size - 1 characters of the error message are used. The yield of the function is the size of buffer needed to hold the whole message, including the terminating zero. This value is greater than errbuf_size if the message was truncated.

MEMORY USAGE

Compiling a regular expression causes memory to be allocated and associated with the preg structure. The function pcre2_regfree() frees all such memory, after which preg may no longer be used as a compiled expression.
