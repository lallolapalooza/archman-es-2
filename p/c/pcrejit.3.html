NOMBRE

PCRE - expresiones regulares compatibles con Perl

SOPORTE DEL COMPILADOR JUST-IN-TIME (JIT) DE PCRE

La compilación Just-in-Time (JIT) es una optimización pesada que puede acelerar enormemente la coincidencia de patrones. Sin embargo, tiene un costo de procesamiento adicional antes de que se realice la coincidencia. Por lo tanto, es de mayor beneficio cuando el mismo patrón se va a hacer coincidir muchas veces. Esto no significa necesariamente muchas llamadas a una función de coincidencia; si el patrón no está anclado, los intentos de coincidencia pueden ocurrir muchas veces en varias posiciones del sujeto, incluso para una sola llamada. Por lo tanto, si la cadena del sujeto es muy larga, aún puede valer la pena usar JIT para coincidencias únicas.

El soporte JIT solo se aplica a la función de coincidencia tradicional compatible con Perl. No se aplica cuando se utiliza la función de coincidencia DFA. El código para este soporte fue escrito por Zoltan Herczeg.

SOPORTE PARA 8, 16 Y 32 BITS

El soporte JIT está disponible para todas las bibliotecas PCRE de 8, 16 y 32 bits. Para mantener esta documentación simple, solo se describe la interfaz de 8 bits en lo que sigue. Si está utilizando la biblioteca de 16 bits, sustituya las funciones de 16 bits y las estructuras de 16 bits (por ejemplo, pcre16_jit_stack en lugar de pcre_jit_stack). Si está utilizando la biblioteca de 32 bits, sustituya las funciones de 32 bits y las estructuras de 32 bits (por ejemplo, pcre32_jit_stack en lugar de pcre_jit_stack).

DISPONIBILIDAD DEL SOPORTE JIT

El soporte JIT es una característica opcional de PCRE. La opción de configuración --enable-jit (o la opción CMake equivalente) debe establecerse al compilar PCRE si desea utilizar JIT. El soporte se limita a las siguientes plataformas de hardware:


ARM v5, v7 y Thumb2
Intel x86 de 32 y 64 bits
MIPS de 32 bits
Power PC de 32 y 64 bits
SPARC de 32 bits (experimental)

Si --enable-jit se establece en una plataforma no compatible, la compilación falla.

Un programa vinculado con PCRE 8.20 o posterior puede verificar si el soporte JIT está disponible llamando a pcre_config() con la opción PCRE_CONFIG_JIT. El resultado es 1 cuando JIT está disponible y 0 en caso contrario. Sin embargo, un programa simple no necesita verificar esto para usar JIT. La API normal se implementa de manera que recurre al código interpretativo si JIT no está disponible. Para programas que necesitan el mejor rendimiento posible, también existe una API de "ruta rápida" específica de JIT.

Si su programa puede vincularse ocasionalmente con versiones de PCRE anteriores a la 8.20, pero desea usar JIT cuando esté disponible, puede verificar los valores de PCRE_MAJOR y PCRE_MINOR, o la existencia de una macro JIT como PCRE_CONFIG_JIT, para controlar su código en tiempo de compilación. Tenga en cuenta también que la función pcre_jit_exec() no estuvo disponible en absoluto antes de la 8.32, y puede que no esté disponible en absoluto si PCRE no se compila con --enable-jit. Consulte la sección "API de ruta rápida JIT" a continuación para obtener más detalles.

USO SIMPLE DE JIT

Debe hacer dos cosas para utilizar el soporte JIT de la forma más sencilla:


(1) Llame a pcre_study() con la opción PCRE_STUDY_JIT_COMPILE para
cada patrón compilado, y pase el bloque pcre_extra resultante a
pcre_exec().


(2) Utilice pcre_free_study() para liberar el bloque pcre_extra cuando ya no sea necesario, en lugar de liberarlo
usted mismo. Esto garantiza que también se liberen los datos JIT.

Para un programa que puede vincularse con versiones de PCRE anteriores a la 8.20, puede insertar


#ifndef PCRE_STUDY_JIT_COMPILE
#define PCRE_STUDY_JIT_COMPILE 0
#endif

para que no se pase ninguna opción a pcre_study(), y luego utilice algo como esto para liberar los datos de estudio:


#ifdef PCRE_CONFIG_JIT
pcre_free_study(study_ptr);
#else
pcre_free(study_ptr);
#endif

PCRE_STUDY_JIT_COMPILE solicita al compilador JIT que genere código para coincidencias completas. Si desea ejecutar coincidencias parciales utilizando las opciones PCRE_PARTIAL_HARD o PCRE_PARTIAL_SOFT de pcre_exec(), debe establecer una o ambas de las siguientes opciones además de, o en lugar de, PCRE_STUDY_JIT_COMPILE al llamar a pcre_study():


PCRE_STUDY_JIT_PARTIAL_HARD_COMPILE
PCRE_STUDY_JIT_PARTIAL_SOFT_COMPILE

Si utiliza pcre_jit_exec() y soporta una versión de PCRE anterior a la 8.32, puede insertar:


#if PCRE_MAJOR >= 8 && PCRE_MINOR >= 32
pcre_jit_exec(...);
#else
pcre_exec(...)
#endif

pero como se describe en la sección "API de ruta rápida JIT", esto asume versiones 8.32 y posteriores compiladas con --enable-jit, lo que puede causar problemas.

El compilador JIT genera código optimizado diferente para cada uno de los tres modos (normal, parcial suave, parcial duro). Cuando se llama a pcre_exec(), se ejecuta el código apropiado si está disponible. De lo contrario, el patrón se hace coincidir utilizando código interpretativo.

En algunas circunstancias, es posible que deba llamar a funciones adicionales. Estas se describen en la sección titulada "Controlar la pila JIT" a continuación.

Si el soporte JIT no está disponible, PCRE_STUDY_JIT_COMPILE, etc., se ignoran y no se crean datos JIT. De lo contrario, el patrón compilado se pasa al compilador JIT, que lo convierte en código de máquina que se ejecuta mucho más rápido que el código interpretativo normal. Cuando pcre_exec() recibe un bloque pcre_extra que contiene un puntero a código JIT del modo apropiado (normal o parcial duro/suave), obedece ese código en lugar de ejecutar el intérprete. El resultado es idéntico, pero el código JIT compilado se ejecuta mucho más rápido.

Hay algunas opciones de pcre_exec() que no son compatibles con la ejecución JIT. También hay algunos elementos de patrón que JIT no puede manejar. Los detalles se dan a continuación. En ambos casos, la ejecución recurre automáticamente al código interpretativo. Si desea saber si JIT se utilizó realmente para una coincidencia particular, debe asegurarse de que se configure una función de devolución de llamada JIT como se describe en la sección titulada "Controlar la pila JIT" a continuación, incluso si no necesita proporcionar una pila JIT no predeterminada. Dicha función de devolución de llamada se llama cada vez que se va a obedecer código JIT. Si las opciones de ejecución no son adecuadas para la ejecución JIT, la función de devolución de llamada no se obedece.

Si el compilador JIT encuentra un elemento no compatible, no se generan datos JIT. Puede averiguar si la ejecución JIT está disponible después de estudiar un patrón llamando a pcre_fullinfo() con la opción PCRE_INFO_JIT. Un resultado de 1 significa que la compilación JIT fue exitosa. Un resultado de 0 significa que el soporte JIT no está disponible, o que el patrón no se estudió con PCRE_STUDY_JIT_COMPILE, etc., o que el compilador JIT no pudo manejar el patrón.

Una vez que un patrón ha sido estudiado, con o sin JIT, puede ser utilizado tantas veces como se desee para hacer coincidir diferentes cadenas sujeto.

OPCIONES Y ELEMENTOS DE PATRÓN NO COMPATIBLES

Las únicas opciones de pcre_exec() compatibles con la ejecución JIT son PCRE_NO_UTF8_CHECK, PCRE_NO_UTF16_CHECK, PCRE_NO_UTF32_CHECK, PCRE_NOTBOL, PCRE_NOTEOL, PCRE_NOTEMPTY, PCRE_NOTEMPTY_ATSTART, PCRE_PARTIAL_HARD y PCRE_PARTIAL_SOFT.

Los únicos elementos de patrón no compatibles son \C (hacer coincidir una única unidad de datos) cuando se ejecuta en un modo UTF, y una llamada inmediatamente antes de una condición de aserción en un grupo condicional.

VALORES DE RETORNO DE LA EJECUCIÓN JIT

Cuando un patrón se hace coincidir utilizando la ejecución JIT, los valores de retorno son los mismos que los proporcionados por el código interpretativo de pcre_exec(), con la adición de un nuevo código de error: PCRE_ERROR_JIT_STACKLIMIT. Esto significa que la memoria utilizada para la pila JIT fue insuficiente. Consulte "Controlar la pila JIT" a continuación para una discusión sobre el uso de la pila JIT. Para compatibilidad con el código interpretativo de pcre_exec(), no se utiliza más de dos tercios del argumento ovector para devolver las subcadenas capturadas.

El código de error PCRE_ERROR_MATCHLIMIT es devuelto por el J

CÓDIGO IT

si la búsqueda de un árbol de patrones muy grande se prolonga demasiado, como ocurre en la misma circunstancia cuando no se utiliza JIT, pero los detalles de lo que se cuenta exactamente no son los mismos. El código de error PCRE_ERROR_RECURSIONLIMIT nunca es devuelto por la ejecución JIT.

GUARDAR Y RESTAURAR PATRONES COMPILADOS

El código que genera el compilador JIT es específico de la arquitectura y también depende de la posición. Por estas razones, no se puede guardar (en un archivo o base de datos) y restaurar más tarde como el bytecode y otros datos de un patrón compilado. Guardar y restaurar patrones compilados no es algo que mucha gente haga. Hay más detalles sobre esta funcionalidad en la documentación de pcreprecompile. Debería ser posible ejecutar pcre_study() en un patrón guardado y restaurado, y así recrear los datos JIT, pero dado que la compilación JIT utiliza recursos significativos, probablemente no valga la pena hacerlo; podría ser mejor recompilar el patrón original.

CONTROLAR LA PILA JIT

Cuando el código JIT compilado se ejecuta, necesita un bloque de memoria para usarlo como pila. Por defecto, utiliza 32K en la pila de la máquina. Sin embargo, algunos patrones grandes o complicados necesitan más que esto. El error PCRE_ERROR_JIT_STACKLIMIT se produce cuando no hay suficiente pila. Se proporcionan tres funciones para gestionar bloques de memoria para ser utilizados como pilas JIT. Hay más discusión sobre el uso de pilas JIT en la sección titulada "JIT stack FAQ" a continuación.

La función pcre_jit_stack_alloc() crea una pila JIT. Sus argumentos son un tamaño inicial y un tamaño máximo, y devuelve un puntero a una estructura opaca de tipo pcre_jit_stack, o NULL si hay un error. La función pcre_jit_stack_free() puede utilizarse para liberar una pila que ya no se necesite. (Para los tecnicismos: el espacio de direcciones se asigna mediante mmap o VirtualAlloc.)

JIT utiliza mucha menos memoria para la recursión que el código interpretativo, y un tamaño máximo de pila de 512K a 1M debería ser más que suficiente para cualquier patrón.

La función pcre_assign_jit_stack() especifica qué pila debe usar el código JIT. Sus argumentos son los siguientes:


pcre_extra *extra
pcre_jit_callback callback
void *data

El argumento extra debe ser el resultado de estudiar un patrón con PCRE_STUDY_JIT_COMPILE, etc. Hay tres casos para los valores de las otras dos opciones:


(1) Si callback es NULL y data es NULL, se utiliza un bloque interno de 32K en la pila de la máquina.


(2) Si callback es NULL y data no es NULL, data debe ser
una pila JIT válida, el resultado de llamar a pcre_jit_stack_alloc().


(3) Si callback no es NULL, debe apuntar a una función que se llama
con data como argumento al inicio de la coincidencia, para configurar
una pila JIT. Si el retorno de la función callback es NULL, se utiliza la
pila interna de 32K; de lo contrario, el valor de retorno debe ser una pila
JIT válida, el resultado de llamar a pcre_jit_stack_alloc().

Una función de devolución de llamada se obedece siempre que el código JIT está a punto de ejecutarse; no se obedece cuando se llama a pcre_exec() con opciones que son incompatibles para la ejecución JIT. Una función de devolución de llamada puede utilizarse, por lo tanto, para determinar si una operación de coincidencia fue ejecutada por JIT o por el intérprete.

Puede utilizar de forma segura la misma pila JIT para más de un patrón (ya sea asignándola directamente o mediante una devolución de llamada), siempre que los patrones se coincidan secuencialmente en el mismo hilo. En una aplicación multihilo, si no especifica una pila JIT, o si asigna o devuelve NULL desde una devolución de llamada, eso es seguro para hilos, porque cada hilo tiene su propia pila de máquina. Sin embargo, si asigna o devuelve una pila JIT no NULL, esta debe ser una pila diferente para cada hilo para que la aplicación sea segura para hilos.

Estrictamente hablando, incluso se permite más. Puede asignar la misma pila no NULL a cualquier número de patrones siempre que no se utilicen para la coincidencia por múltiples hilos al mismo tiempo. Por ejemplo, puede asignar la misma pila a todos los patrones compilados y utilizar un mutex global en la devolución de llamada para esperar hasta que la pila esté disponible para su uso. Sin embargo, esta es una solución ineficiente y no se recomienda.

Esta es una sugerencia sobre cómo podría operar un programa multihilo que necesite configurar pilas JIT no predeterminadas:


Durante la inicialización del hilo
variable_local_hilo = pcre_jit_stack_alloc(...)


Durante la salida del hilo
pcre_jit_stack_free(variable_local_hilo)


Utilizar una función de devolución de llamada de una línea
devolver variable_local_hilo

Todas las funciones descritas en esta sección no hacen nada si JIT no está disponible, y pcre_assign_jit_stack() no hace nada a menos que el argumento extra no sea NULL y apunte a un bloque pcre_extra que sea el resultado de un estudio exitoso con PCRE_STUDY_JIT_COMPILE, etc.

JIT STACK FAQ

(1) ¿Por qué necesitamos pilas JIT?

PCRE (y JIT) es un motor recursivo de profundidad, por lo que necesita una pila donde los datos locales del nodo actual se empujen antes de verificar sus nodos hijos. Asignar una pila de máquina real en algunas plataformas es difícil. Por ejemplo, la cadena de pila debe actualizarse cada vez si extendemos la pila en PowerPC. Aunque es posible, el tiempo de sobrecarga de su actualización disminuye el rendimiento. Así que hacemos la recursión en memoria.

(2) ¿Por qué no asignamos simplemente bloques de memoria con malloc()?

Los sistemas operativos modernos tienen una característica útil: pueden reservar un espacio de direcciones en lugar de asignar memoria. Podemos asignar páginas de memoria de forma segura dentro de este espacio de direcciones, por lo que la pila podría crecer sin mover los datos de memoria (esto es importante debido a los punteros). Por lo tanto, podemos asignar 1M de espacio de direcciones y usar solo una página de memoria (generalmente 4K) si es suficiente. Sin embargo, aún podemos crecer hasta 1M en cualquier momento si es necesario.

(3) ¿Quién "posee" una pila JIT?

El propietario de la pila es el programa de usuario, no el patrón estudiado por JIT ni nada más. El programa de usuario debe asegurarse de que si una pila es utilizada por pcre_exec() (es decir, está asignada al patrón que se está ejecutando actualmente), esa pila no debe ser utilizada por ningún otro hilo (para evitar sobrescribir la misma área de memoria). La mejor práctica para programas multihilo es asignar una pila para cada hilo y devolver esta pila a través de la función de devolución de llamada JIT.

(4) ¿Cuándo se debe liberar una pila JIT?

Puede liberar una pila JIT en cualquier momento, siempre que no sea utilizada de nuevo por pcre_exec(). Cuando asigna la pila a un patrón, solo se establece un puntero. No hay conteo de referencias ni ninguna otra magia. Puede liberar los patrones y las pilas en cualquier orden, en cualquier momento. Simplemente *no* llame a pcre_exec() con un patrón que apunte a una pila ya liberada, ya que eso causará un SEGFAULT. (Tampoco libere una pila utilizada actualmente por pcre_exec() en otro hilo). También puede reemplazar la pila de un patrón en cualquier momento. Incluso puede liberar la pila anterior antes de asignar un reemplazo.

(5) ¿Debo asignar/liberar una pila cada vez antes/después de llamar a pcre_exec()?

No, porque esto es demasiado costoso en términos de recursos. Sin embargo, podría implementar alguna idea inteligente que libere la pila si no se usa durante, digamos, dos minutos. La devolución de llamada JIT puede ayudar a lograr esto sin mantener una lista de los patrones estudiados por JIT actualmente.

(6) OK, la pila es para asignación de memoria a largo plazo. ¿Pero qué sucede si un patrón causa un desbordamiento de pila con una pila de 1M? ¿Se mantiene ese 1M hasta que se libere la pila?

Especialmente en sistemas integrados, podría ser una buena idea liberar memoria a veces sin liberar la pila. Actualmente no hay una API para esto. Probablemente una llamada a una función que devuelva la memoria actualmente asignada para cualquier pila y otra que permita liberar memoria (encoger la pila) sería una buena idea si alguien la necesita.

(7) Esto es demasiado complicado. ¿No hay una mejor solución para el manejo de pilas JIT?

No, gracias a Windows. Si se usaran hilos POSIX en todas partes, podríamos deshacernos de esta complicada API.

CÓDIGO DE EJEMPLO

Este es un ejemplo de un solo hilo que especifica una pila JIT sin usar una devolución de llamada.


int rc;
int ovector[30];
pcre *re;
pcre_extra *extra;
pcre_jit_stack *jit_stack;


re = pcre_compile(pattern, 0, &error, &erroffset, NULL);
/* Comprobar errores */
extra = pcre_study(re, PCRE_STUDY_JIT_COMPILE, &error);
jit_stack = pcre_jit_stack_alloc(32*1024, 512*1024);
/* Comprobar error (NULL) */
pcre_assign_jit_stack(extra, NULL, jit_stack);
rc = pcre_exec(re, extra, subject, length, 0, 0, ovector, 30);
/* Comprobar resultados */
pcre_free(re);
pcre_free_study(extra);
pcre_jit_stack_free(jit_stack);

JIT FAST PATH API

Dado que la API descrita anteriormente recurre a la ejecución interpretada cuando JIT no está disponible, es conveniente para programas que están escritos para uso general en muchos entornos. Sin embargo, llamar a JIT a través de pcre_exec() tiene un impacto en el rendimiento. Los programas que están escritos para su uso donde se sabe que JIT está disponible, y que necesitan el mejor rendimiento posible, pueden en su lugar usar una API de "ruta rápida" para llamar a la ejecución JIT directamente en lugar de llamar a pcre_exec() (obviamente solo para patrones que han sido estudiados con éxito por JIT).

La función de ruta rápida se llama pcre_jit_exec() y toma exactamente los mismos argumentos que pcre_exec(), más un argumento adicional que debe apuntar a una pila JIT. Las disposiciones de la pila JIT descritas anteriormente no se aplican. Los valores de retorno son los mismos que para pcre_exec().

Cuando llama a pcre_exec(), además de probar opciones no válidas, se realizan una serie de otras comprobaciones de integridad en los argumentos. Por ejemplo, si el puntero del sujeto es NULL, o su longitud es negativa, se produce un error inmediato. Además, a menos que se establezca PCRE_NO_UTF[8|16|32], se prueba la validez de una cadena de sujeto UTF. En aras de la velocidad, estas comprobaciones no ocurren en la ruta rápida JIT, y si se pasan datos inválidos, el resultado no está definido.

API RUTA RÁPIDA DE JIT

Bypassear las comprobaciones de cordura y el envoltorio de pcre_exec() puede dar aceleraciones de más del 10%.

Tenga en cuenta que la función pcre_jit_exec() no está disponible en versiones de PCRE anteriores a la 8.32 (lanzada en noviembre de 2012). Si necesita soportar versiones tan antiguas, debe usar la más lenta pcre_exec(), o cambiar entre las dos rutas de código comprobando los valores de PCRE_MAJOR y PCRE_MINOR.

Debido a un desafortunado descuido en la implementación, incluso en las versiones 8.32 y posteriores, no habrá una función stub pcre_jit_exec() definida cuando PCRE se compile con --disable-jit, que es la opción por defecto, y no hay forma de detectar si PCRE se compiló con --enable-jit a través de una macro.

Si necesita soportar versiones anteriores a la 8.32, o versiones que podrían no construirse con --enable-jit, debe usar la más lenta pcre_exec(), o cambiar entre las dos rutas de código comprobando los valores de PCRE_MAJOR y PCRE_MINOR.

Cambiar entre las dos comprobando la versión asume que todas las versiones de destino se construyen con --enable-jit. Para también soportar compilaciones que puedan usar --disable-jit, se debe usar pcre_exec(), o una comprobación en tiempo de compilación para JIT a través de pcre_config() (que asume que el entorno de ejecución será el mismo), o como decidió hacer el proyecto Git, simplemente asumir que pcre_jit_exec() está presente en la versión 8.32 o posterior a menos que se proporcione una bandera en tiempo de compilación, vea el commit "grep: un-break building with PCRE >= 8.32 without --enable-jit" en git.git para un ejemplo de ello.
