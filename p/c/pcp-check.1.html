PCP-CHECK(1) Manual de Comandos Generales PCP-CHECK(1)

NOMBRE

pcp-check - gestionar la configuración de componentes opcionales de PCP

SINOPSIS

$pcp-check [-a] [-d] [-l] [-n] [-s] [-v] [-x] [componente ...]
$pcp-check [-a] [-c script]] [-d] [-l] [-n] [-s] [-v] [-x]
$PCP_BINADM_DIR/pmcheck ...

DESCRIPCIÓN

El Performance Co-Pilot (PCP) incluye un número de componentes centrales que probablemente estén preconfigurados y operativos, pero también incluye un número mayor de componentes que no están activos por defecto. En el contexto de pmcheck, estos componentes cubren servicios que típicamente se inician como parte del procedimiento de arranque del sistema, por ejemplo pmcd(1), pmlogger(1), pmproxy(1), etc., o Agentes de Dominio de Métricas de Rendimiento (PMDA) opcionales que aumentan las métricas de rendimiento disponibles exportadas por pmcd(1).

pmcheck permite la interrogación del estado de los componentes con la opción -s, --state. Los componentes pueden ser activados con la opción -a, --activate, o desactivados con la opción -d, --deactivate. Estas tres opciones son claramente mutuamente excluyentes para cualquier ejecución individual de pmcheck, y en ausencia de cualquiera de ellas se asume que -s es la opción por defecto.

El conjunto de componentes a interrogar o configurar se especifica mediante el nombre(s) del componente desde la línea de comandos, de lo contrario, todos los componentes conocidos en ausencia de argumentos de componente. Cuando se especifican uno o más argumentos de componente, estos pueden ser opcionalmente patrones de sh(1) (glob) que coinciden con los nombres de los componentes conocidos.

La opción -l, --list informa sobre los componentes conocidos. Con uno o más componentes, se informa sobre cada uno de ellos. Sin argumentos de componente, la opción -l lista todos los componentes conocidos, que son simplemente todos los scripts de componentes (ver la sección SCRIPTS DE COMPONENTES abajo) almacenados en el directorio $PCP_SHARE_DIR/lib/pmcheck. Si la opción -v también se utiliza, se muestra una breve descripción de cada componente solicitado.

Componentes adicionales pueden integrarse en el framework de pmcheck, y la opción -c, --file permite usar un script de sh(1) alternativo en lugar de un script asociado con un componente conocido.

En conjunto con las opciones -a o -d, la opción -n, --show-me realiza una simulación, mostrando los comandos de sh(1) que serían necesarios para realizar la reconfiguración, pero no se realiza ninguna reconfiguración. Los comandos que necesitan ser ejecutados como ``root'' se prefijan con # y otros comandos se prefijan con $.

La opción -v, --verbose aumenta la verbosidad de los informes.

La opción -x, --trace puede usarse para especificar que los scripts de componentes se ejecuten con la opción -x de sh(1). Esto puede ayudar a depurar el fallo de un script de componente o durante el desarrollo de un nuevo script de componente, probablemente involucrando también la opción -c de pmcheck.

La opción -?, --help muestra un mensaje de uso.

Como conveniencia, pmcheck . es un alias para pcp-check.

SCRIPTS DE COMPONENTES

El framework pmcheck es extensible, ya que el conjunto de componentes conocidos se define por los nombres de los scripts de componentes en el directorio $PCP_SHARE_DIR/lib/pmcheck.

Cada script de componente debe cumplir las siguientes reglas para una correcta integración con pmcheck:

  • El script se ejecutará con sh(1); si necesita algún otro lenguaje de scripting, debe proporcionar un wrapper de sh(1).
  • Dado que cada script es responsable de un componente, el nombre del componente se infiere, sin embargo, el nombre del componente también se pasa desde pmcheck como el único argumento después de las opciones. Esto permite implementar scripts de componentes genéricos como enlaces duros debajo de $PCP_SHARE_DIR/lib/pmcheck.
  • Cuando se llama con la opción -l, --list, el script no hace nada, a menos que también se llame con la opción -v, en cuyo caso se muestra una breve descripción del componente en la salida estándar.
  • Cuando se llama con la opción -s, --state, el script debe salir con un código de salida que indique el estado del componente, específicamente 0 (activo), 1 (inactivo, pero podría ser activado por pmcheck), 2 (inactivo y no puede ser activado por pmcheck). La distinción entre los códigos de salida 1 y 2 se basa en muchos factores, pero 1 generalmente significa que todos los paquetes de software requeridos (PCP y otros) están instalados, los servicios prerrequisitos requeridos se están ejecutando o podrían iniciarse de forma segura, y la configuración del componente puede asumir valores por defecto o deducirse de manera fiable, por ejemplo, un número de puerto para las comunicaciones. Por el contrario, 2 significa que la activación automática del componente no es posible y se requiere alguna intervención del usuario final.
  • Cuando se llama con la opción -a, --activate, el script debe activar el componente. Esto significa realizar cualquier cambio de configuración necesario para que se reinicie en el próximo arranque del sistema o reinicio de pmcd(1), y iniciar el componente si está inactivo actualmente.
  • Cuando se llama con la opción -d, --deactivate, el script debe desactivar el componente. Esto significa detener el componente si está activo actualmente, y realizar cualquier cambio de configuración necesario para que no se reinicie en el próximo arranque del sistema o reinicio de pmcd(1).
  • Cuando se llama con la opción -n, --show-me, el script debe realizar una simulación y mostrar los comandos requeridos en la salida estándar según las reglas descritas anteriormente para la opción -n de pmcheck.
  • Si también se especifica la opción -v, --verbose, el script debe proporcionar texto explicativo en la salida estándar para ayudar a explicar, particularmente en casos donde el componente no está activo o la reconfiguración falló.

Para ayudar en el desarrollo de scripts de componentes, el archivo $PCP_SHARE_DIR/lib/checkproc.sh puede ser incluido (después de incluir $PCP_DIR/etc/pcp.env). checkproc.sh proporciona los siguientes servicios:

  • Se crea un directorio temporal y la variable de shell $tmp se asigna a la ruta completa del directorio.
  • La variable de shell $status se utiliza para devolver el estado de salida del script [valor por defecto 0].
  • La variable de shell $component se asigna al nombre del componente asociado.
  • La variable de shell $prog se asigna al nombre base del script (por lo tanto, el nombre del componente en el caso por defecto).
  • Se instala una trampa para limpiar $tmp y salir con $status.
  • Un procedimiento de shell _do_args que maneja todo el análisis de argumentos de comandos.
  • Las variables de shell $aflag, $dflag, $lflag o $sflag tienen valores por defecto de false y se establecen a true por _do_args cuando se analizan las opciones -a, -d, -l o -s.
  • La variable de shell $show_me tiene el valor por defecto de false y se establece a true por _do_args cuando se analiza la opción -n.
  • La variable de shell $verbose cuenta el número de opciones -v analizadas por _do_args.
  • Un procedimiento de shell _ctl_svc que maneja las solicitudes de estado y todas las operaciones de reconfiguración para los servicios que son gestionados por systemctl(1) o init(1) u otras capas de infraestructura similares. _ctl_svc toma 2 argumentos, el primero es una acción (una de state, start, stop, activate (habilitar e iniciar), o deactivate (detener y deshabilitar)), y el segundo es el nombre del componente; para los componentes gestionados por systemctl(1), nombre debe ser el nombre base del servicio, por ejemplo, pmcd para la unidad de systemd(1) pmcd.service, de lo contrario nombre es el nombre del script de init(1) o similar ``rc''.
  • _ctl_svc devolverá un valor (a través de $? cuando se llama desde un script de shell) que coincide con los códigos de salida definidos anteriormente para cada

pcp-check(1) — Performance Co-Pilot — Arch Linux

NAME

pcp-check - verify Performance Co-Pilot (PCP) services and PMDAs

SYNOPSIS

pcp-check [-a|-d|-s] [-v] [-c component] [-h host] [-H host] [-p port] [-P port] [-t timeout] [-m] [-V]

DESCRIPTION

The pcp-check utility is used to query the status of PCP services and PMDAs, and to activate or deactivate them.

The default action is to query the status of all installed PCP services and PMDAs.

The following options are supported:

-a
Activate the specified component(s). This is the default action if no action option is specified and the component is not running.
-c component
Specify a component to check. This can be a service (e.g., pmcd, pmlogger) or a PMDA (e.g., pmda_cpu).
-d
Deactivate the specified component(s).
-h host
Connect to a remote pmcd on the specified host.
-H host
Connect to a remote pmlogger control port on the specified host.
-p port
Connect to a remote pmcd on the specified port.
-P port
Connect to a remote pmlogger control port on the specified port.
-s
Query the status of the specified component(s). This is the default action.
-t timeout
Set the timeout for connection to pmcd to timeout seconds.
-v
Verbose output. Show more details about the status of components.
-m
List all available components.
-V
Display version information and exit.

COMPONENT SCRIPTS

This utility relies on component scripts located in $PCP_LIB_DIR/components. These scripts are responsible for managing the lifecycle of individual PCP services and PMDAs.

There are two types of component scripts:

  • A _ctl_svc shell procedure that handles status requests and all reconfiguration operations for a PCP service (e.g., pmcd, pmlogger). _ctl_svc takes at least 2 arguments, the first is an action (one of state, activate or deactivate, and the second argument is the name of the service.
  • A _ctl_pmda shell procedure that handles status requests and all reconfiguration operations for a PMDA that is connected to pmcd(1). _ctl_pmda takes at least 2 arguments, the first is an action (one of state, activate or deactivate, and the second argument is the name of the PMDA. For the install action, there is a third argument for the name of the PMDA's executable or DSO and an optional fourth argument is the name of a file providing the input required for the PMDA's Install script (defaults to /dev/null).
  • _ctl_pmda will return a value (via $? when called from a shell script) that matches the exit codes defined above for each action.

So the following is the simplest possible component script for a system service.

#!/bin/sh
. $PCP_DIR/etc/pcp.env || exit 1
. $PCP_SHARE_DIR/lib/checkproc.sh

_do_args "$@"

if $lflag
then
    [ $verbose -gt 0 ] && echo "my description"
elif $sflag
then
    _ctl_svc state $component
    status=$?
elif $aflag
then
    _ctl_svc activate $component || status=1
elif $dflag
then
    _ctl_svc deactivate $component || status=1
fi

And the following is the simplest possible component script for a PMDA.

#!/bin/sh
. $PCP_DIR/etc/pcp.env || exit 1
. $PCP_SHARE_DIR/lib/checkproc.sh

_do_args "$@"

if $lflag
then
    [ $verbose -gt 0 ] && echo "my description"
elif $sflag
then
    _ctl_pmda state $component
    status=$?
elif $aflag
then
    _ctl_pmda activate $component || status=1
elif $dflag
then
    _ctl_pmda deactivate $component || status=1
fi

DIAGNOSTICS

For pmcheck (not the component scripts) the exit status is typically 0, but values of 9 or 99 indicate serious internal botches.

When the -a or -d options are used, the success or failure of the reconfiguration is reported on standard output.

CAVEAT

Some components have prerequisites that demand additional non-PCP services be installed, configured and operational, e.g. a database server or a key-value server. In these cases, probing the status of the non-PCP service may be subject to some access controls and if pmcheck is run as a non-root user, then the output from -s (the default) may be incomplete or misleading; in these circumstances, running pmcheck as root should provide a more accurate report.

PCP ENVIRONMENT

Environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).
