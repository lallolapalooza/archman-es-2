NOMBRE

PCRE - expresiones regulares compatibles con Perl

PCRE RENDIMIENTO

A continuación se discuten dos aspectos del rendimiento: el uso de memoria y el tiempo de procesamiento. La forma en que expresas tu patrón como una expresión regular puede afectar a ambos.

USO DE MEMORIA DEL PATRÓN COMPILADO

PCRE compila los patrones en un código interpretativo razonablemente eficiente, por lo que la mayoría de los patrones simples no utilizan mucha memoria. Sin embargo, hay un caso en el que el uso de memoria de un patrón compilado puede ser inesperadamente grande. Si un subpatrón entre paréntesis tiene un cuantificador con un mínimo mayor que 1 y/o un máximo limitado, todo el subpatrón se repite en el código compilado. Por ejemplo, el patrón


(abc|def){2,4}

se compila como si fuera


(abc|def)(abc|def)((abc|def)(abc|def)?)?

(Nota técnica: Se hace de esta manera para que los puntos de retroceso dentro de cada una de las repeticiones puedan mantenerse de forma independiente.)

Para expresiones regulares cuyos cuantificadores usan solo números pequeños, esto no suele ser un problema. Sin embargo, si los números son grandes, y en particular si tales repeticiones están anidadas, el uso de memoria puede ser vergonzoso. Por ejemplo, el patrón muy simple


((ab){1,1000}c){1,3}

usa 51K bytes cuando se compila utilizando la biblioteca de 8 bits. Cuando PCRE se compila con su tamaño de puntero interno predeterminado de dos bytes, el límite de tamaño en un patrón compilado es de 64K unidades de datos, y esto se alcanza con el patrón anterior si la repetición externa aumenta de 3 a 4. PCRE se puede compilar para usar punteros internos más grandes y así manejar patrones compilados más grandes, pero es mejor tratar de reescribir tu patrón para usar menos memoria si puedes.

Una forma de reducir el uso de memoria para tales patrones es aprovechar la instalación de "subrutina" de PCRE. Reescribiendo el patrón anterior como


((ab)(?2){0,999}c)(?1){0,2}

reduce los requisitos de memoria a 18K, y de hecho permanece por debajo de 20K incluso con la repetición externa aumentada a 100. Sin embargo, este patrón no es exactamente equivalente, porque las llamadas de "subrutina" se tratan como grupos atómicos en los que no puede haber retroceso si hay un fallo de coincidencia posterior. Por lo tanto, PCRE no puede hacer este tipo de reescritura automáticamente. Además, hay una pérdida notable de velocidad al ejecutar el patrón modificado. Sin embargo, si la agrupación atómica no es un problema y la pérdida de velocidad es aceptable, este tipo de reescritura te permitirá procesar patrones que PCRE no puede manejar de otra manera.

USO DE PILAS EN TIEMPO DE EJECUCIÓN

Cuando se utiliza pcre_exec() o pcre[16|32]_exec() para la coincidencia, ciertos tipos de patrones pueden hacer que utilice grandes cantidades de la pila del proceso. En algunos entornos, la pila del proceso predeterminada es bastante pequeña, y si se agota, el resultado es a menudo SIGSEGV. Este problema es probablemente el que se plantea con mayor frecuencia con PCRE. Reescribir tu patrón a menudo puede ayudar. La documentación de pcrestack discute este problema en detalle.

TIEMPO DE PROCESAMIENTO

Ciertos elementos en los patrones de expresiones regulares se procesan de manera más eficiente que otros. Es más eficiente usar una clase de caracteres como [aeiou] que un conjunto de alternativas de un solo carácter como (a|e|i|o|u). En general, la construcción más simple que proporciona el comportamiento requerido suele ser la más eficiente. El libro de Jeffrey Friedl contiene mucha discusión general útil sobre la optimización de expresiones regulares para un rendimiento eficiente. Este documento contiene algunas observaciones sobre PCRE.

El uso de propiedades de caracteres Unicode (los escapes \p, \P y \X) es lento, porque PCRE tiene que usar una búsqueda en tablas de varias etapas cada vez que necesita la propiedad de un carácter. Si puedes encontrar un patrón alternativo que no utilice propiedades de caracteres, probablemente será más rápido.

Por defecto, las secuencias de escape \b, \d, \s y \w, y las clases de caracteres POSIX como [:alpha:] no usan propiedades Unicode, en parte por compatibilidad con versiones anteriores y en parte por razones de rendimiento. Sin embargo, puedes establecer PCRE_UCP si deseas que se usen propiedades de caracteres Unicode. Esto puede duplicar el tiempo de coincidencia para elementos como \d, cuando se coincide con una función de coincidencia tradicional; la pérdida de rendimiento es menor con una función de coincidencia DFA, y en ambos casos no hay mucha diferencia para \b.

Cuando un patrón comienza con .* no entre paréntesis, o entre paréntesis que no son el sujeto de una referencia inversa, y la opción PCRE_DOTALL está establecida, el patrón está implícitamente anclado por PCRE, ya que solo puede coincidir al principio de una cadena sujeto. Sin embargo, si PCRE_DOTALL no está establecido, PCRE no puede hacer esta optimización, porque el metacaracter . no coincide con una nueva línea, y si la cadena sujeto contiene nuevas líneas, el patrón puede coincidir desde el carácter inmediatamente después de una de ellas en lugar de desde el principio. Por ejemplo, el patrón


.*segundo

coincide con el sujeto "primero\nsegundo" (donde \n representa un carácter de nueva línea), con la coincidencia comenzando en el séptimo carácter. Para hacer esto, PCRE tiene que reintentar la coincidencia comenzando después de cada nueva línea en el sujeto.

Si estás utilizando un patrón de este tipo con cadenas sujeto que no contienen nuevas líneas, se obtiene el mejor rendimiento estableciendo PCRE_DOTALL, o comenzando el patrón con ^.* o ^.*? para indicar un anclaje explícito. Eso evita que PCRE tenga que escanear a lo largo del sujeto buscando una nueva línea para reiniciar.

Ten cuidado con los patrones que contienen repeticiones indefinidas anidadas. Estos pueden tardar mucho tiempo en ejecutarse cuando se aplican a una cadena que no coincide. Considera el fragmento de patrón


^(a+)*

Esto puede coincidir con "aaaa" de 16 maneras diferentes, y este número aumenta muy rápidamente a medida que la cadena se hace más larga. (La repetición * puede coincidir 0, 1, 2, 3 o 4 veces, y para cada uno de esos casos excepto 0 o 4, las repeticiones + pueden coincidir con un número diferente de veces). Cuando el resto del patrón es tal que la coincidencia completa va a fallar, PCRE en principio tiene que probar cada variación posible, y esto puede llevar un tiempo extremadamente largo, incluso para cadenas relativamente cortas.

Una optimización captura algunos de los casos más simples como


(a+)*b

donde sigue un carácter literal. Antes de embarcarse en el procedimiento de coincidencia estándar, PCRE comprueba que hay una "b" más adelante en la cadena sujeto, y si no la hay, falla la coincidencia inmediatamente. Sin embargo, cuando no hay un literal que siga, esta optimización no se puede utilizar. Puedes ver la diferencia comparando el comportamiento de


(a+)*\d

con el patrón anterior. El primero da un fallo casi al instante cuando se aplica a una línea completa de caracteres "a", mientras que el segundo tarda un tiempo considerable con cadenas más largas de unos 20 caracteres.

En muchos casos, la solución a este tipo de problema de rendimiento es usar un grupo atómico o un cuantificador posesivo.
