PCRE2UNICODE(3) Manual de Funciones de Biblioteca PCRE2UNICODE(3)

NOMBRE

PCRE2 - Expresiones regulares compatibles con Perl (API revisada)

SOPORTE DE UNICODE Y UTF

PCRE2 normalmente se compila con soporte de Unicode, aunque si no lo necesita, puede compilarse sin él, en cuyo caso la biblioteca será más pequeña. Con soporte de Unicode, PCRE2 tiene conocimiento de las propiedades de los caracteres Unicode y puede procesar cadenas de texto en formato UTF-8, UTF-16 y UTF-32 (dependiendo del ancho de la unidad de código), pero esto no es lo predeterminado. A menos que se solicite específicamente, PCRE2 trata cada unidad de código en una cadena como un carácter.

Hay dos formas de indicar a PCRE2 que cambie al modo UTF, donde los caracteres pueden consistir en más de una unidad de código y el rango de valores está restringido. El programa puede llamar a pcre2_compile() con la opción PCRE2_UTF, o el patrón puede comenzar con la secuencia (*UTF). Sin embargo, esta última facilidad puede ser bloqueada por la opción PCRE2_NEVER_UTF. Es decir, el programador puede impedir que el proveedor del patrón cambie al modo UTF.

Tenga en cuenta que la opción PCRE2_MATCH_INVALID_UTF (ver más abajo) fuerza que se establezca PCRE2_UTF.

En modo UTF, tanto el patrón como las cadenas sujetas que se comparan con él se tratan como cadenas UTF en lugar de cadenas de caracteres individuales de una unidad de código. También hay algunos otros cambios en la forma en que se manejan los caracteres, como se documenta a continuación.

SOPORTE DE PROPIEDADES UNICODE

Cuando PCRE2 se compila con soporte de Unicode, se pueden usar las secuencias de escape \p{..}, \P{..} y \X. Esto no depende de la configuración de PCRE2_UTF. Las propiedades Unicode que se pueden probar son un subconjunto de las que soporta Perl. Actualmente se limitan a las propiedades de categoría general como Lu para una letra mayúscula o Nd para un número decimal, las propiedades derivadas Any y Lc (sinónimo L&), los nombres de script de Unicode como Arabic o Han, Bidi_Class, Bidi_Control y algunas propiedades binarias.

Las listas completas se encuentran en la documentación de pcre2pattern y pcre2syntax. En general, solo se admiten los nombres cortos para las propiedades. Por ejemplo, \p{L} coincide con una letra. Su sinónimo más largo, \p{Letter}, no es compatible. Además, en Perl, muchas propiedades pueden ir opcionalmente precedidas por "Is", por compatibilidad con Perl 5.6. PCRE2 no admite esto.

CARACTERES ANCHOS Y MODOS UTF

Los puntos de código inferiores a 256 se pueden especificar en patrones mediante secuencias de escape hexadecimales, con o sin llaves (por ejemplo, \x{b3} o \xb3). Los valores más grandes deben usar secuencias con llaves. También se reconocen puntos de código octales sin llaves hasta \777; los más grandes se pueden codificar usando \o{...}.

La secuencia de escape \N{U+<dígitos hexadecimales>} se reconoce como otra forma de especificar un carácter Unicode por punto de código en modo UTF. No está permitida en modo no UTF.

En modo UTF, los cuantificadores de repetición se aplican a caracteres UTF completos, no a unidades de código individuales.

En modo UTF, el metacaracter punto coincide con un carácter UTF en lugar de una sola unidad de código.

En modo UTF, los nombres de los grupos de captura no están restringidos a ASCII y pueden contener cualquier letra y dígito decimal Unicode, además de guión bajo.

La secuencia de escape \C se puede usar para coincidir con una sola unidad de código en modo UTF, pero su uso puede provocar algunos efectos extraños ya que rompe caracteres de múltiples unidades (ver la descripción de \C en la documentación de pcre2pattern). Por esta razón, existe una opción de tiempo de compilación que deshabilita el soporte para \C por completo. También existe una opción de tiempo de compilación menos drástica para bloquear el uso de \C cuando se compila un patrón.

El uso de \C no es compatible con la función de coincidencia alternativa pcre2_dfa_match() cuando está en modo UTF-8 o UTF-16, es decir, cuando un carácter puede consistir en más de una unidad de código. El uso de \C en estos modos provoca un error en tiempo de coincidencia. Además, la optimización JIT no admite \C en estos modos. Si se solicita la optimización JIT para un patrón UTF-8 o UTF-16 que contiene \C, no tendrá éxito, y por lo tanto, cuando se llame a pcre2_match(), la coincidencia se realizará mediante la función interpretada.

Las secuencias de escape de caracteres \b, \B, \d, \D, \s, \S, \w y \W prueban correctamente caracteres de cualquier valor de código, pero, por predeterminado, los caracteres que PCRE2 reconoce como dígitos, espacios o caracteres de palabra siguen siendo el mismo conjunto que en el modo no UTF, todos con puntos de código inferiores a 256. Esto sigue siendo cierto incluso cuando PCRE2 se compila para incluir soporte de Unicode, ya que de lo contrario ralentizaría la coincidencia en muchos casos comunes. Tenga en cuenta que esto también se aplica a \b y \B, ya que se definen en términos de \w y \W. Si desea probar un sentido más amplio de, por ejemplo, "dígito", puede usar pruebas explícitas de propiedades de Unicode como \p{Nd}. Alternativamente, si establece la opción PCRE2_UCP, la forma en que funcionan las secuencias de escape de caracteres cambia para que se utilicen las propiedades de Unicode para determinar qué caracteres coinciden, aunque hay algunas opciones que suprimen esto para escapes individuales. Para obtener detalles, consulte la sección sobre tipos de caracteres genéricos en la documentación de pcre2pattern.

Al igual que las secuencias de escape, los caracteres que coinciden con las clases de caracteres nombradas POSIX son todos caracteres de valor bajo a menos que se establezca la opción PCRE2_UCP, pero existe una opción para anular esto.

En contraste con las secuencias de escape de caracteres y las clases de caracteres, las secuencias especiales de espacio en blanco horizontal y vertical (\h, \H, \v y \V) coinciden con todos los caracteres Unicode apropiados, ya sea que PCRE2_UCP esté configurado o no.

EQUIVALENCIA DE MAYÚSCULAS Y MINÚSCULAS UNICODE

Si se establece PCRE2_UTF o PCRE2_UCP, el procesamiento de mayúsculas y minúsculas utiliza propiedades de Unicode, excepto para los caracteres cuyos puntos de código son inferiores a 128 y que tienen como máximo dos valores equivalentes en mayúsculas/minúsculas. Para estos, se utiliza una búsqueda directa en tabla para mayor velocidad. Pocos caracteres Unicode como sigma griego tienen más de dos puntos de código que son equivalentes en mayúsculas/minúsculas, y estos se tratan de manera especial. Establecer PCRE2_UCP sin PCRE2_UTF permite el procesamiento de mayúsculas/minúsculas estilo Unicode para codificaciones de caracteres no UTF, como UCS-2.

Hay dos caracteres ASCII (S y K) que, además de sus equivalentes en minúsculas ASCII, tienen uno no ASCII (S larga y signo de Kelvin). El reconocimiento de estos caracteres no ASCII como equivalentes en mayúsculas/minúsculas a sus contrapartes ASCII puede deshabilitarse estableciendo la opción PCRE2_EXTRA_CASELESS_RESTRICT. Cuando esto se establece, todos los caracteres en una equivalencia de mayúsculas/minúsculas deben ser ASCII o no ASCII; no puede haber mezcla.


Sin PCRE2_EXTRA_CASELESS_RESTRICT:
'k' = 'K' = U+212A (signo de Kelvin)
's' = 'S' = U+017F (S larga)
Con PCRE2_EXTRA_CASELESS_RESTRICT:
'k' = 'K'
U+212A (signo de Kelvin) solo equivalente en mayúsculas/minúsculas a sí mismo
's' = 'S'
U+017F (S larga) solo equivalente en mayúsculas/minúsculas a sí mismo

Una familia de idiomas, el turco y el azerí, tiene sus propias reglas de insensibilidad a mayúsculas/minúsculas, que se pueden seleccionar estableciendo PCRE2_EXTRA_TURKISH_CASING. Esto altera el comportamiento de los caracteres 'i', 'I', U+0130 (i mayúscula con punto arriba) y U+0131 (i minúscula sin punto).


Sin PCRE2_EXTRA_TURKISH_CASING:
'i' = 'I'
U+0130 (i mayúscula con punto arriba) solo equivalente en mayúsculas/minúsculas a sí mismo
U+0131 (i minúscula sin punto) solo equivalente en mayúsculas/minúsculas a sí mismo
Con PCRE2_EXTRA_TURKISH_CASING:
'i' = U+0130 (i mayúscula con punto arriba)
U+0131 (i minúscula sin punto) = 'I'

No está permitido especificar juntas PCRE2_EXTRA_CASELESS_RESTRICT y PCRE2_EXTRA_TURKISH_CASING.

Desde la versión 10.45, las propiedades de letras de Unicode Lu (mayúscula), Ll (minúscula) y Lt (title case) se tratan todas como Lc (letra con mayúscula/minúscula) cuando la coincidencia sin distinción entre mayúsculas y minúsculas se establece mediante la opción PCRE2_CASELESS o (?i) dentro del patrón.

SECuencias de GUIONES

Las construcciones de patrones (*script_run:...) y (*atomic_script_run:...), con sinónimos (*sr:...) y (*asr:...), verifican que la cadena que coincide dentro de los paréntesis es una secuencia de guiones. En concepto, una secuencia de guiones es una secuencia de caracteres que son todos del mismo guion de Unicode. Sin embargo, debido a que algunos guiones se usan comúnmente juntos, y porque algunas marcas diacríticas y otras marcas se usan con múltiples guiones, no es tan simple.

Cada carácter Unicode tiene una propiedad de Guion, en su mayoría con un valor que corresponde al nombre de un guion, como Latin, Greek o Cyrillic. También hay tres valores especiales:

<

"Unknown" se usa para puntos de código que no han sido asignados, y también para los puntos de código sustitutos. En la biblioteca PCRE2 de 32 bits, los caracteres cuyos puntos de código son mayores que el máximo de Unicode (U+10FFFF), a los que solo se puede acceder en modo no UTF, se les asigna el script Desconocido.

"Common" se usa para caracteres que se utilizan con muchos scripts. Estos incluyen signos de puntuación, emojis, símbolos matemáticos, musicales y de moneda, y los dígitos ASCII de 0 a 9.

"Inherited" se usa para caracteres como marcas diacríticas que modifican un carácter anterior. Se considera que estos adoptan el script del carácter que modifican.

Algunos caracteres Heredados se usan con muchos scripts, pero muchos de ellos solo se usan normalmente con un pequeño número de scripts. Por ejemplo, U+102E0 (marca copta de miles de efactas) solo se usa con árabe y copto. Para hacer posible la comprobación de esto, existe una propiedad de Unicode llamada Extensión de Script. Su valor es una lista de scripts que se aplican al carácter. Para la mayoría de los caracteres, la lista contiene solo un script, el mismo que la propiedad Script. Sin embargo, para caracteres como U+102E0 se enumeran más de un Script. También hay algunos caracteres Comunes que tienen un solo script, no Común, en su lista de Extensión de Script.

La siguiente sección describe las reglas básicas para decidir si una cadena dada de caracteres es una ejecución de script. Tenga en cuenta, sin embargo, que hay algunos casos especiales que involucran el script Chino Han, y una restricción adicional para los dígitos decimales. Estos se cubren en secciones posteriores.

Reglas básicas de ejecución de scripts

Una cadena que tiene menos de dos caracteres de longitud es una ejecución de script. Este es el único caso en el que un carácter Desconocido puede ser parte de una ejecución de script. Las cadenas más largas se comprueban utilizando solo la propiedad Extensiones de Script, no la propiedad Script básica.

Si la propiedad Extensión de Script de un carácter es el único valor "Heredado", siempre se acepta como parte de una ejecución de script. Esto también es cierto para la propiedad "Common", sujeto a la verificación de dígitos decimales descrita a continuación. Todos los caracteres restantes en una ejecución de script deben tener al menos un script en común en sus listas de Extensiones de Script. En terminología de teoría de conjuntos, la intersección de todos los conjuntos de scripts no debe estar vacía.

Un ejemplo simple es un nombre de Internet como "google.com". Las letras están todas en el script Latín, y el punto es Común, por lo que esta cadena es una ejecución de script. Sin embargo, la letra Cirílica "o" se ve exactamente igual que la Latín "o"; una cadena que se ve igual, pero con "o" cirílicas, no es una ejecución de script.

Ejemplos más interesantes involucran caracteres con más de un script en su Extensión de Script. Considere los siguientes caracteres:


U+060C Coma árabe
U+06D4 Punto final árabe

El primero tiene la lista de Extensión de Script árabe, Hanifi Rohingya, siríaco y thaana; el segundo solo tiene árabe y Hanifi Rohingya. Ambos podrían aparecer en ejecuciones de script en árabe o Hanifi Rohingya. El primero también podría aparecer en ejecuciones de script siríaco o thaana, pero el segundo no.

El script Chino Han

El script Chino Han se usa comúnmente junto con otros scripts para escribir ciertos idiomas. El japonés usa los scripts Hiragana y Katakana junto con Han; el coreano usa Hangul y Han; el mandarín taiwanés usa Bopomofo y Han. Estas tres combinaciones se tratan como casos especiales al verificar ejecuciones de script y son, en efecto, "scripts virtuales". Por lo tanto, una ejecución de script puede contener una mezcla de Hiragana, Katakana y Han, o una mezcla de Hangul y Han, o una mezcla de Bopomofo y Han, pero no, por ejemplo, una mezcla de Hangul y Bopomofo y Han. PCRE2 (al igual que Perl) sigue el Estándar Técnico 39 de Unicode ("Mecanismos de seguridad de Unicode", http://unicode.org/reports/tr39/) al permitir tales mezclas.

Dígitos decimales

Unicode contiene muchos conjuntos de 10 dígitos decimales en diferentes scripts, y algunos scripts (incluido el script Común) contienen más de un conjunto. Algunos de estos dígitos decimales son visualmente indistinguibles de los dígitos ASCII comunes. Además de la verificación de script descrita anteriormente, si una ejecución de script contiene algún dígito decimal, todos deben provenir del mismo conjunto de 10 caracteres adyacentes.

VALIDEZ DE LAS CADENAS UTF

Cuando la opción PCRE2_UTF está configurada, las cadenas pasadas como patrones y temas se verifican (por defecto) en busca de validez al ingresar a las funciones relevantes. Si se pasa una cadena UTF no válida, se devuelve un código de error negativo. La compensación de unidades de código del carácter infractor se puede extraer del bloque de datos de coincidencia llamando a pcre2_get_startchar(), que se utiliza para este propósito después de un error UTF.

En algunas situaciones, es posible que ya sepa que sus cadenas son válidas y, por lo tanto, quiera omitir estas verificaciones para mejorar el rendimiento, por ejemplo, en el caso de una cadena de tema larga que se escanea repetidamente. Si configura la opción PCRE2_NO_UTF_CHECK en tiempo de compilación o en tiempo de coincidencia, PCRE2 asume que el patrón o tema que se le proporciona (respectivamente) contiene solo secuencias de unidades de código UTF válidas.

Si pasa una cadena UTF no válida cuando PCRE2_NO_UTF_CHECK está configurado, el resultado es indefinido y su programa puede fallar o entrar en un bucle infinito o dar resultados incorrectos. Sin embargo, hay un modo de coincidencia que puede manejar cadenas de tema UTF no válidas. Esto se habilita pasando PCRE2_MATCH_INVALID_UTF a pcre2_compile() y se discute a continuación en la siguiente sección. El resto de esta sección cubre el caso en que PCRE2_MATCH_INVALID_UTF no está configurado.

Pasar PCRE2_NO_UTF_CHECK a pcre2_compile() solo deshabilita la verificación UTF para el patrón; no se aplica a las cadenas de tema. Si desea deshabilitar la verificación para una cadena de tema, debe pasar la misma opción a pcre2_match() o pcre2_dfa_match().

Las cadenas UTF-16 y UTF-32 pueden indicar su orden de bytes mediante códigos especiales conocidos como marca de orden de bytes (BOM). Las funciones PCRE2 no manejan esto, esperando que las cadenas estén en el orden de bytes del host.

A menos que PCRE2_NO_UTF_CHECK esté configurado, una cadena UTF se verifica antes de que se realice cualquier otro procesamiento. En el caso de las llamadas pcre2_match() y pcre2_dfa_match() con un desplazamiento inicial distinto de cero, la verificación se aplica solo a esa parte del tema que se puede inspeccionar durante la coincidencia, y hay una verificación de que el desplazamiento inicial apunta a la primera unidad de código de un carácter o al final del tema. Si no hay aserciones de lookbehind en el patrón, la verificación comienza en el desplazamiento inicial. De lo contrario, comienza en la longitud del lookbehind más largo antes del desplazamiento inicial, o al principio del tema si no hay tantos caracteres antes del desplazamiento inicial. Tenga en cuenta que las secuencias \b y \B son lookbehinds de un carácter.

Además de verificar el formato de la cadena, hay una verificación para asegurar que todos los puntos de código se encuentren en el rango U+0 a U+10FFFF, excluyendo el área sustituta. Los llamados puntos de código "no carácter" no se excluyen porque la corrección #9 de Unicode aclara que no deberían serlo.

Los caracteres en el "Área sustituta" de Unicode están reservados para su uso por UTF-16, donde se utilizan en pares para codificar puntos de código con valores mayores que 0xFFFF. Los puntos de código que son codificados por pares UTF-16 están disponibles de forma independiente en las codificaciones UTF-8 y UTF-32. (En otras palabras, todo el asunto de los sustitutos es una solución para UTF-16 que desafortunadamente afecta a UTF-8 y UTF-32).

Establecer PCRE2_NO_UTF_CHECK en tiempo de compilación no deshabilita el error que se produce si se encuentra una secuencia de escape para un punto de código Unicode no válido en el patrón. Si desea permitir secuencias de escape como \x{d800} (un punto de código sustituto), puede establecer la opción extra PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES. Sin embargo, esto solo es posible en modos UTF-8 y UTF-32, ya que estos valores no son representables en UTF-16.

Errores en cadenas UTF-8

Los siguientes códigos de error negativos se dan para cadenas UTF-8 no válidas:


PCRE2_ERROR_UTF8_ERR1
PCRE2_ERROR_UTF8_ERR2
PCRE2_ERROR_UTF8_ERR3
PCRE2_ERROR_UTF8_ERR4
PCRE2_ERROR_UTF8_ERR5

La cadena termina con un carácter UTF-8 truncado; el código especifica cuántos bytes faltan (de 1 a 5). Aunque RFC 3629 restringe los caracteres UTF-8 a no más de 4 bytes, el esquema de codificación (originalmente definido por RFC 2279) permite hasta 6 bytes, y esto se verifica primero; de ahí la posibilidad de 4 o 5 bytes faltantes.


PCRE2_ERROR_UTF8_ERR6
PCRE2_ERROR_UTF8_ERR7
PCRE2_ERROR_UTF8_ERR8
PCRE2_ERROR_UTF8_ERR9
PCRE2_ERROR_UTF8_ERR10

Los dos bits más significativos del segundo byte, tercer byte, cuarto byte, quinto byte o sexto byte del carácter no tienen el valor binario 0b10 (es decir, el bit más significativo es 0, o el siguiente bit es 1).


PCRE2_ERROR_UTF8_ERR11
PCRE2_ERROR_UTF8_ERR12

Un carácter que es válido según las reglas RFC 2279 tiene 5 o 6 bytes de longitud; estos puntos de código están excluidos por RFC 3629.


PCRE2_ERROR_UTF8_ERR13

Un carácter de 4 bytes tiene un valor mayor que 0x10ffff; estos puntos de código están excluidos por RFC 3629.


PCRE2_ERROR_UTF8_ERR14

Un carácter de 3 bytes tiene un valor en el rango 0xd800 a 0xdfff; este rango de puntos de código está reservado por RFC 3629 para su uso con UTF-16, y por lo tanto está excluido de UTF-8.


PCRE2_ERROR_UTF8_ERR15
PCRE2_ERROR_UTF8_ERR16
PCRE2_ERROR_UTF8_ERR17
PCRE2_ERROR_UTF8_ERR18
PCRE2_ERROR_UTF8_ERR19

Un carácter de 2, 3, 4, 5 o 6 bytes es "sobredimensionado", es decir, codifica un valor que se puede representar con menos bytes, lo cual es inválido. Por ejemplo, los dos bytes 0xc0, 0xae dan el valor 0x2e, cuya codificación correcta utiliza solo un byte.


PCRE2_ERROR_UTF8_ERR20

Los dos bits más significativos del primer byte de un carácter tienen el valor binario 0b10 (es decir, el bit más significativo es 1 y el segundo es 0). Tal byte solo puede ocurrir válidamente como el segundo o subsiguiente byte de un carácter multibyte.


PCRE2_ERROR_UTF8_ERR2

VALIDITY OF UTF STRINGS

When PCRE2 is compiled with UTF support enabled, it checks that subject strings contain valid UTF-8, UTF-16, or UTF-32 sequences, depending on the character width and the PCRE2_UTF option. Invalid sequences cause match failures. The specific error codes that are returned for invalid UTF sequences are:

Errors in UTF-8 strings

The following negative error codes are given for invalid UTF-8 strings:


PCRE2_ERROR_UTF8_ERR1 Invalid UTF-8 sequence
PCRE2_ERROR_UTF8_ERR2 Malformed UTF-8 byte sequence

A byte with the value 0xfe or 0xff can never occur in a valid UTF-8 string.

Errors in UTF-16 strings

The following negative error codes are given for invalid UTF-16 strings:


PCRE2_ERROR_UTF16_ERR1 Missing low surrogate at end of string
PCRE2_ERROR_UTF16_ERR2 Invalid low surrogate follows high surrogate
PCRE2_ERROR_UTF16_ERR3 Isolated low surrogate

Errors in UTF-32 strings

The following negative error codes are given for invalid UTF-32 strings:


PCRE2_ERROR_UTF32_ERR1 Surrogate character (0xd800 to 0xdfff)
PCRE2_ERROR_UTF32_ERR2 Code point is greater than 0x10ffff

MATCHING IN INVALID UTF STRINGS

You can run pattern matches on subject strings that may contain invalid UTF sequences if you call pcre2_compile() with the PCRE2_MATCH_INVALID_UTF option. This is supported by pcre2_match(), including JIT matching, but not by pcre2_dfa_match(). When PCRE2_MATCH_INVALID_UTF is set, it forces PCRE2_UTF to be set as well. Note, however, that the pattern itself must be a valid UTF string.

If you do not set PCRE2_MATCH_INVALID_UTF when calling pcre2_compile, and you are not certain that your subject strings are valid UTF sequences, you should not make use of the JIT "fast path" function pcre2_jit_match() because it bypasses sanity checks, including the one for UTF validity. An invalid string may cause undefined behaviour, including looping, crashing, or giving the wrong answer.

Setting PCRE2_MATCH_INVALID_UTF does not affect what pcre2_compile() generates, but if pcre2_jit_compile() is subsequently called, it does generate different code. If JIT is not used, the option affects the behaviour of the interpretive code in pcre2_match(). When PCRE2_MATCH_INVALID_UTF is set at compile time, PCRE2_NO_UTF_CHECK is ignored at match time.

In this mode, an invalid code unit sequence in the subject never matches any pattern item. It does not match dot, it does not match \p{Any}, it does not even match negative items such as [^X]. A lookbehind assertion fails if it encounters an invalid sequence while moving the current point backwards. In other words, an invalid UTF code unit sequence acts as a barrier which no match can cross.

You can also think of this as the subject being split up into fragments of valid UTF, delimited internally by invalid code unit sequences. The pattern is matched fragment by fragment. The result of a successful match, however, is given as code unit offsets in the entire subject string in the usual way. There are a few points to consider:

The internal boundaries are not interpreted as the beginnings or ends of lines and so do not match circumflex or dollar characters in the pattern.

If pcre2_match() is called with an offset that points to an invalid UTF-sequence, that sequence is skipped, and the match starts at the next valid UTF character, or the end of the subject.

At internal fragment boundaries, \b and \B behave in the same way as at the beginning and end of the subject. For example, a sequence such as \bWORD\b would match an instance of WORD that is surrounded by invalid UTF code units.

Using PCRE2_MATCH_INVALID_UTF, an application can run matches on arbitrary data, knowing that any matched strings that are returned are valid UTF. This can be useful when searching for UTF text in executable or other binary files.

Note, however, that the 16-bit and 32-bit PCRE2 libraries process strings as sequences of uint16_t or uint32_t code points. They cannot find valid UTF sequences within an arbitrary string of bytes unless such sequences are suitably aligned.
