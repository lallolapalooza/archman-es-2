PCREPOSIX(3) Manual de Funciones de Biblioteca PCREPOSIX(3)

NOMBRE

PCRE - expresiones regulares compatibles con Perl.

SINOPSIS

#include <pcreposix.h>

int regcomp(regex_t *preg, const char *pattern,
     int cflags);

int regexec(regex_t *preg, const char *string,
     size_t nmatch, regmatch_t pmatch[], int eflags);
     size_t regerror(int errcode, const regex_t *preg,
     char *errbuf, size_t errbuf_size);

void regfree(regex_t *preg);

DESCRIPCIÓN

Este conjunto de funciones proporciona una API de estilo POSIX para la biblioteca de expresiones regulares de 8 bits de PCRE. Consulte la documentación de pcreapi para obtener una descripción de la API nativa de PCRE, que contiene mucha funcionalidad adicional. No existe un envoltorio de estilo POSIX para la biblioteca de 16 y 32 bits de PCRE.

Las funciones descritas aquí son solo funciones de envoltura que en última instancia llaman a la API nativa de PCRE. Sus prototipos están definidos en el archivo de cabecera pcreposix.h y, en sistemas Unix, la biblioteca en sí se llama pcreposix.a, por lo que se puede acceder agregando -lpcreposix al comando para enlazar una aplicación que los utiliza. Debido a que las funciones POSIX llaman a las nativas, también es necesario agregar -lpcre.

Solo he implementado aquellos bits de opción POSIX que se pueden mapear razonablemente a las opciones nativas de PCRE. Además, la opción REG_EXTENDED se define con el valor cero. Esto no tiene ningún efecto, pero dado que los programas escritos para la interfaz POSIX a menudo la usan, esto facilita la inserción de PCRE como biblioteca de reemplazo. Otras opciones POSIX ni siquiera están definidas.

También hay algunas otras opciones que no están definidas por POSIX. Estas se han agregado a petición de los usuarios que desean utilizar ciertas características específicas de PCRE a través de la interfaz de llamada POSIX.

Cuando se llama a PCRE a través de estas funciones, solo la API es de estilo POSIX. La sintaxis y la semántica de las expresiones regulares en sí siguen siendo las de Perl, sujetas a la configuración de varias opciones de PCRE, como se describe a continuación. "Estilo POSIX" significa que la API se aproxima a la definición POSIX; no es totalmente compatible con POSIX, y en dominios de codificación multibyte es probablemente aún menos compatible.

La cabecera para estas funciones se suministra como pcreposix.h para evitar cualquier posible conflicto con otras bibliotecas POSIX. Puede, por supuesto, ser renombrada o aliased como regex.h, que es el nombre "correcto". Proporciona dos tipos de estructuras, regex_t para formas internas compiladas, y regmatch_t para devolver subcadenas capturadas. También define algunas constantes cuyos nombres comienzan con "REG_"; estas se utilizan para establecer opciones e identificar códigos de error.

COMPILACIÓN DE UN PATRÓN

La función regcomp() se llama para compilar un patrón en una forma interna. El patrón es una cadena C terminada por un cero binario, y se pasa en el argumento pattern. El argumento preg es un puntero a una estructura regex_t que se utiliza como base para almacenar información sobre la expresión regular compilada.

El argumento cflags es cero o contiene uno o más de los bits definidos por las siguientes macros:


REG_DOTALL

La opción PCRE_DOTALL se establece cuando la expresión regular se pasa para su compilación a la función nativa. Tenga en cuenta que REG_DOTALL no forma parte del estándar POSIX.


REG_ICASE

La opción PCRE_CASELESS se establece cuando la expresión regular se pasa para su compilación a la función nativa.


REG_NEWLINE

La opción PCRE_MULTILINE se establece cuando la expresión regular se pasa para su compilación a la función nativa. Tenga en cuenta que esto *no* imita el comportamiento POSIX definido para REG_NEWLINE (ver la siguiente sección).


REG_NOSUB

La opción PCRE_NO_AUTO_CAPTURE se establece cuando la expresión regular se pasa para su compilación a la función nativa. Además, cuando un patrón que se compila con esta bandera se pasa a regexec() para coincidir, los argumentos nmatch y pmatch se ignoran, y no se devuelven subcadenas capturadas.


REG_UCP

La opción PCRE_UCP se establece cuando la expresión regular se pasa para su compilación a la función nativa. Esto hace que PCRE utilice propiedades Unicode al coincidir con \d, \w, etc., en lugar de solo reconocer valores ASCII. Tenga en cuenta que REG_UTF8 no forma parte del estándar POSIX.


REG_UNGREEDY

La opción PCRE_UNGREEDY se establece cuando la expresión regular se pasa para su compilación a la función nativa. Tenga en cuenta que REG_UNGREEDY no forma parte del estándar POSIX.


REG_UTF8

La opción PCRE_UTF8 se establece cuando la expresión regular se pasa para su compilación a la función nativa. Esto hace que el patrón en sí y todas las cadenas de datos utilizadas para coincidir con él se traten como cadenas UTF-8. Tenga en cuenta que REG_UTF8 no forma parte del estándar POSIX.

En ausencia de estas banderas, no se pasan opciones a la función nativa. Esto significa que la expresión regular se compila con la semántica predeterminada de PCRE. En particular, la forma en que maneja los caracteres de nueva línea en la cadena de asunto es a la manera de Perl, no a la de POSIX. Tenga en cuenta que establecer PCRE_MULTILINE solo tiene *algunos* de los efectos especificados para REG_NEWLINE. No afecta la forma en que se corresponden los saltos de línea con . (no lo hacen) o con una clase negativa como [^a] (lo hacen).

El resultado de regcomp() es cero en caso de éxito y distinto de cero en caso contrario. La estructura preg se rellena en caso de éxito, y un miembro de la estructura es público: re_nsub contiene el número de subpatrones de captura en la expresión regular. Se definen varios códigos de error en el archivo de cabecera.

NOTA: Si el resultado de regcomp() es distinto de cero, no debe intentar utilizar el contenido de la estructura preg. Si, por ejemplo, la pasa a regexec(), el resultado no está definido y es probable que su programa falle.

COINCIDENCIA DE CARACTERES DE NUEVA LÍNEA

Esta área no es sencilla, ya que POSIX y Perl tienen puntos de vista diferentes. No es posible hacer que PCRE obedezca las semánticas POSIX, pero entonces PCRE nunca fue concebido para ser un motor POSIX. La siguiente tabla enumera las diferentes posibilidades para hacer coincidir caracteres de nueva línea en PCRE:


Cambio predeterminado con


. coincide con nueva línea no PCRE_DOTALL
nueva línea coincide con [^a] sí no se puede cambiar
$ coincide con \n al final sí PCRE_DOLLARENDONLY
$ coincide con \n en el medio no PCRE_MULTILINE
^ coincide con \n en el medio no PCRE_MULTILINE

Esta es la tabla equivalente para POSIX:


Cambio predeterminado con


. coincide con nueva línea sí REG_NEWLINE
nueva línea coincide con [^a] sí REG_NEWLINE
$ coincide con \n al final no REG_NEWLINE
$ coincide con \n en el medio no REG_NEWLINE
^ coincide con \n en el medio no REG_NEWLINE

El comportamiento de PCRE es el mismo que el de Perl, excepto que no hay equivalente para PCRE_DOLLAR_ENDONLY en Perl. Tanto en PCRE como en Perl, no hay forma de evitar que la nueva línea coincida con [^a].

Se puede obtener el manejo predeterminado de nuevas líneas de POSIX estableciendo PCRE_DOTALL y PCRE_DOLLAR_ENDONLY, pero no hay forma de hacer que PCRE se comporte exactamente como para la acción REG_NEWLINE.

COINCIDENCIA DE UN PATRÓN

La función regexec() se llama para hacer coincidir un patrón compilado preg contra una string dada, que por defecto está terminada por un byte cero (pero ver REG_STARTEND más abajo), sujeta a las opciones en eflags. Estas pueden ser:


REG_NOTBOL

La opción PCRE_NOTBOL se establece al llamar a la función de coincidencia subyacente de PCRE.


REG_NOTEMPTY

La opción PCRE_NOTEMPTY se establece al llamar a la función de coincidencia subyacente de PCRE. Tenga en cuenta que REG_NOTEMPTY no forma parte del estándar POSIX. Sin embargo, establecer esta opción puede dar un comportamiento más parecido a POSIX en algunas situaciones.


REG_NOTEOL

La opción PCRE_NOTEOL se establece al llamar a la función de coincidencia subyacente de PCRE.


REG_STARTEND

La cadena se considera que comienza en string + pmatch[0].rm_so y que tiene una termina

pcreposix(3) - ArchWiki

NAME

pcreposix - PCRE POSIX-class functions, POSIX regular expressions

SYNOPSIS

#include <sys/types.h>
#include <regex.h>

int regcomp(regex_t *preg, const char *regex, int cflags);
int regexec(const regex_t *preg, const char *string, size_t nmatch,
    regmatch_t pmatch[], int eflags);
void regfree(regex_t *preg);
size_t regerror(int errcode, const regex_t *preg, char *errbuf,
    size_t errbuf_size);

DESCRIPTION

These functions implement POSIX.2 regular expression matching using the PCRE library. They are intended to be a compatible substitute for the POSIX regular expression functions found in many C libraries.

A regular expression is defined by the string in regex. It is compiled into an internal form by regcomp(), which stores the result in the structure pointed to by preg. This structure must be passed to subsequent calls to regexec() and regfree().

regexec() attempts to match the compiled regular expression preg against the input string string. The results of the match are returned via the pmatch argument. regfree() releases any memory that was allocated by regcomp().

regerror() converts error codes returned by regcomp() and regexec() into human-readable error messages.

REGCOMP

The regcomp() function compiles the regular expression contained in the null-terminated string regex and stores the compiled representation in the structure pointed to by preg. The cflags argument is the bitwise OR of zero or more of the following compilation flags:

REG_BASIC
Use POSIX Basic Regular Expressions (BRE) syntax. This is the default if no other syntax flag is given. This is available in PCRE.
REG_EXTENDED
Use POSIX Extended Regular Expressions (ERE) syntax. This is equivalent to PCRE's default syntax.
REG_NOSUB
Report only whether the expression matched or not. Do not return information about the substrings that were matched.
REG_NEWLINE
A period character (.) or any character in a character class does not match a newline character. If this flag is not set, periods and characters in character classes do not match newline characters by default. This is available in PCRE.
REG_ICASE
Ignore case distinctions in the matching. This is equivalent to PCRE's PCRE_ISET flag.
REG_NOSUB
Report only whether the expression matched or not. Do not return information about the substrings that were matched.
REG_COMPAT
Use syntax that is compatible with older versions of the POSIX standard.
REG_NOSUB
Report only whether the expression matched or not. Do not return information about the substrings that were matched.
REG_UTF8
The regular expression is expected to be in UTF-8 format. This is equivalent to PCRE's PCRE_UTF8 flag.
REG_STARTEND
This flag affects how the substring offsets are returned by regexec(). If it is set, then the values in the rm_so and rm_eo fields of the pmatch array are treated as offsets from the start and end of the string respectively. If rm_so is not -1, the match must begin at or after the offset specified in rm_so. If rm_eo is not -1, the match must end at or before the offset specified in rm_eo. This flag may only be used if the expression was compiled without the REG_NOSUB flag. See also the description of eflags for regexec(). This is available in PCRE.

MATCHING NEWLINE CHARACTERS

By default, in POSIX.2 ERE and BRE syntax, the period character (.) and the characters in character classes do not match newline characters. The REG_NEWLINE flag changes this behaviour. If REG_NEWLINE is set, then the period and characters in character classes will match newline characters. If REG_NEWLINE is not set, they will not. PCRE's default behaviour is to not match newline characters, equivalent to setting the REG_NEWLINE flag.

MATCHING A PATTERN

The regexec() function attempts to match the compiled regular expression referenced by preg against the input string string. The eflags argument is the bitwise OR of zero or more of the following execution flags:

REG_NOTBOL
The string is not the beginning of the line. The caret character (^) will not match the beginning of the string. This is available in PCRE.
REG_STARTEND
This flag affects the interpretation of the pmatch array. If set, the rm_so and rm_eo members of the pmatch array specify offsets from the start and end of the string, respectively. The match must start at or after the offset in rm_so (if not -1) and end at or before the offset in rm_eo (if not -1). This flag may only be used if the expression was compiled without the REG_NOSUB flag. It is compatible with, but not specified by, IEEE Standard 1003.2 (POSIX.2).

If the REG_STARTEND flag is set, the first element of the pmatch array (i.e., pmatch[0]) specifies the start and end of the substring to be matched. If pmatch[0].rm_so is not -1, the match must start at or after that offset. If pmatch[0].rm_eo is not -1, the match must end at or before that offset. If pmatch[0].rm_so and pmatch[0].rm_eo are both -1, then there is no restriction on the start or end of the match. The actual start and end offsets of the matched substring are returned in pmatch[0].rm_so and pmatch[0].rm_eo respectively. If the string is null-terminated, and the match extends to the end of the string, then pmatch[0].rm_eo will be set to the offset of the trailing NULL

string + pmatch[0].rm_eo (there need not actually be a NUL at that location), regardless of the value of nmatch. This is a BSD extension, compatible with but not specified by IEEE Standard 1003.2 (POSIX.2), and should be used with caution in software intended to be portable to other systems. Note that a non-zero rm_so does not imply REG_NOTBOL; REG_STARTEND affects only the location of the string, not how it is matched.

If the pattern was compiled with the REG_NOSUB flag, no data about any matched strings is returned. The nmatch and pmatch arguments of regexec() are ignored.

If the value of nmatch is zero, or if the value pmatch is NULL, no data about any matched strings is returned.

Otherwise,the portion of the string that was matched, and also any captured substrings, are returned via the pmatch argument, which points to an array of nmatch structures of type regmatch_t, containing the members rm_so and rm_eo. These contain the offset to the first character of each substring and the offset to the first character after the end of each substring, respectively. The 0th element of the vector relates to the entire portion of string that was matched; subsequent elements relate to the capturing subpatterns of the regular expression. Unused entries in the array have both structure members set to -1.

A successful match yields a zero return; various error codes are defined in the header file, of which REG_NOMATCH is the "expected" failure code.

ERROR MESSAGES

The regerror() function maps a non-zero errorcode from either regcomp() or regexec() to a printable message. If preg is not NULL, the error should have arisen from the use of that structure. A message terminated by a binary zero is placed in errbuf. The length of the message, including the zero, is limited to errbuf_size. The yield of the function is the size of buffer needed to hold the whole message.

MEMORY USAGE

Compiling a regular expression causes memory to be allocated and associated with the preg structure. The function regfree() frees all such memory, after which preg may no longer be used as a compiled expression.
