NOMBRE

pcap-filter - sintaxis del filtro de paquetes

DESCRIPCIÓN

pcap_compile(3PCAP) se utiliza para compilar una cadena en un programa de filtro. El programa de filtro resultante se puede aplicar a un flujo de paquetes para determinar qué paquetes se proporcionarán a pcap_loop(3PCAP), pcap_dispatch(3PCAP), pcap_next(3PCAP) o pcap_next_ex(3PCAP).

La expresión de filtro consta de uno o más primitivos. Los primitivos suelen consistir en un id (nombre o número) precedido de uno o más calificadores. Hay tres tipos diferentes de calificadores:

tipo
Los calificadores de tipo indican a qué tipo de elemento se refiere el nombre o número del id. Los tipos posibles son host, net, port y portrange. Por ejemplo, `host foo', `net 128.3', `port 20', `portrange 6000-6008'. Si no hay calificador de tipo, se asume host.
dir
Los calificadores de dir especifican una dirección de transferencia particular hacia y/o desde id. Las direcciones posibles son src, dst, src or dst, src and dst, ra, ta, addr1, addr2, addr3 y addr4. Por ejemplo, `src foo', `dst net 128.3', `src or dst port ftp-data'. Si no hay calificador de dir, se asume `src or dst'. Los calificadores ra, ta, addr1, addr2, addr3 y addr4 solo son válidos para capas de enlace de Redes de Área Local inalámbrica IEEE 802.11.
proto
Los calificadores de proto restringen la coincidencia a un protocolo particular. Los protocolos posibles son: ether, fddi, tr, wlan, ip, ip6, arp, rarp, decnet, sctp, tcp y udp. Por ejemplo, `ether src foo', `arp net 128.3', `tcp port 21', `udp portrange 7000-7009', `wlan addr2 0:2:3:4:5:6'. Si no hay calificador de proto, se asumen todos los protocolos consistentes con el tipo. Por ejemplo, `src foo' significa `(ip6 or ip or arp or rarp) src foo', `net bar' significa `(ip or arp or rarp) net bar' y `port 53' significa `(tcp or udp or sctp) port 53' (tenga en cuenta que estos ejemplos usan sintaxis inválida para ilustrar el principio).

[fddi es en realidad un alias de ether; el analizador los trata de manera idéntica, significando "el nivel de enlace de datos utilizado en la interfaz de red especificada". Las cabeceras FDDI contienen direcciones de origen y destino similares a Ethernet, y a menudo contienen tipos de paquetes similares a Ethernet, por lo que puede filtrar en estos campos FDDI al igual que con los campos Ethernet análogos. Las cabeceras FDDI también contienen otros campos, pero no puede nombrarlos explícitamente en una expresión de filtro.

De manera similar, tr y wlan son alias de ether; las declaraciones del párrafo anterior sobre las cabeceras FDDI también se aplican a las cabeceras de Red de Token y Redes de Área Local inalámbrica 802.11. Para las cabeceras 802.11, la dirección de destino es el campo DA y la dirección de origen es el campo SA; los campos BSSID, RA y TA no se prueban.]

Además de lo anterior, hay algunas "primitivas" especiales que no siguen el patrón: gateway, broadcast, less, greater y expresiones aritméticas. Todas estas se describen a continuación.

Expresiones de filtro más complejas se construyen usando las palabras and, or y not (o equivalentemente: `&&', `||' y `!' respectivamente) para combinar primitivos. Por ejemplo, `host foo and not port ftp and not port ftp-data'. Para ahorrar escritura, se pueden omitir listas de calificadores idénticas. Por ejemplo, `tcp dst port ftp or ftp-data or domain' es exactamente lo mismo que `tcp dst port ftp or tcp dst port ftp-data or tcp dst port domain'.

Las primitivas permitidas son:

dst host hostnameaddr
Verdadero si el campo de destino IPv4/v6 del paquete es hostnameaddr, que puede ser una dirección o un nombre.
src host hostnameaddr
Verdadero si el campo de origen IPv4/v6 del paquete es hostnameaddr.
host hostnameaddr
Verdadero si el origen o el destino IPv4/v6 del paquete es hostnameaddr.
Cualquiera de las expresiones de host anteriores puede ser precedida por las palabras clave, ip, arp, rarp o ip6, como en: 
ip host hostnameaddr

que es equivalente a: 
ether proto \ip and host hostnameaddr

Si hostnameaddr es un nombre con múltiples direcciones IPv4/v6, cada dirección se verificará para ver si coincide.
ether dst ethernameaddr
Verdadero si la dirección de destino de Ethernet es ethernameaddr. ethernameaddr puede ser un nombre de /etc/ethers o una dirección MAC numérica del tipo "xx:xx:xx:xx:xx:xx", "xx.xx.xx.xx.xx.xx", "xx-xx-xx-xx-xx-xx", "xxxx.xxxx.xxxx", "xxxxxxxxxxxx", o varias mezclas de ':', '.', y '-', donde cada "x" es un dígito hexadecimal (0-9, a-f, o A-F).
ether src ethernameaddr
Verdadero si la dirección de origen de Ethernet es ethernameaddr.
ether host ethernameaddr
Verdadero si la dirección de origen o destino de Ethernet es ethernameaddr.
gateway host
Verdadero si el paquete utilizó host como puerta de enlace. Es decir, la dirección de origen o destino de Ethernet era host pero ni el origen ni el destino IP eran host. Host debe ser un nombre y debe ser encontrado tanto por los mecanismos de resolución de nombre de host a dirección IP de la máquina (archivo de nombres de host, DNS, NIS, etc.) como por el mecanismo de resolución de nombre de host a dirección Ethernet de la máquina (/etc/ethers, etc.). (Una expresión equivalente es 
ether host ethernameaddr and not host hostnameaddr

que puede usarse con nombres o números para hostnameaddr / ethernameaddr.) Esta sintaxis no funciona en configuraciones habilitadas para IPv6 en este momento.
dst net netnameaddr
Verdadero si la dirección de destino IPv4/v6 del paquete tiene un número de red de netnameaddr. Net puede ser un nombre de la base de datos de redes (/etc/networks, etc.) o un número de red. Un número de red IPv4 se puede escribir como un quad decimal (p. ej., 192.168.1.0), triple decimal (p. ej., 192.168.1), par decimal (p. ej., 172.16), o número único (p. ej., 10); la máscara de red es 255.255.255.255 para un quad decimal (lo que significa que es realmente una coincidencia de host), 255.255.255.0 para un triple decimal, 255.255.0.0 para un par decimal, o 255.0.0.0 para un número único. Un número de red IPv6 debe escribirse completamente; la máscara de red es ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffff, por lo que las coincidencias de "red" IPv6 son siempre coincidencias de host, y una coincidencia de red requiere una longitud de máscara de red.
src net netnameaddr
Verdadero si la dirección de origen IPv4/v6 del paquete tiene un número de red de netnameaddr.
net netnameaddr
Verdadero si la dirección de origen o destino IPv4/v6 del paquete tiene un número de red de netnameaddr.
net netaddr mask netmask
Verdadero si la dirección IPv4 coincide con netaddr con la netmask específica. Puede ser calificada con src o dst. Tenga en cuenta que esta sintaxis no es válida para netaddr IPv6.
net netaddr/len
Verdadero si la dirección IPv4/v6 coincide con netaddr con una longitud de máscara de red de len bits. Puede ser calificada con src o dst.
dst port portnamenum
Verdadero si el paquete es IPv4/v6 TCP, UDP o SCTP y tiene un valor de puerto de destino de portnamenum. El portnamenum puede ser un número o un nombre utilizado en /etc/services (ver tcp(4P) y udp(4P)
>udp(4P)). Si se utiliza un nombre, se comprueban tanto el número de puerto como el protocolo. Si se utiliza un número o un nombre ambiguo, solo se comprueba el número de puerto (por ejemplo, `dst port 513' imprimirá tanto el tráfico tcp/login como el tráfico udp/who, y `port domain' imprimirá tanto el tráfico tcp/domain como el tráfico udp/domain).
src port portnamenum
Verdadero si el paquete tiene un valor de puerto de origen de portnamenum.
port portnamenum
Verdadero si el puerto de origen o destino del paquete es portnamenum.
dst portrange portnamenum1-portnamenum2
Verdadero si el paquete es TCP, UDP o SCTP IPv4/v6 y tiene un valor de puerto de destino entre portnamenum1 y portnamenum2 (ambos inclusive). portnamenum1 y portnamenum2 se interpretan de la misma manera que el parámetro portnamenum para port.
src portrange portnamenum1-portnamenum2
Verdadero si el paquete tiene un valor de puerto de origen entre portnamenum1 y portnamenum2 (ambos inclusive).
portrange portnamenum1-portnamenum2
Verdadero si el puerto de origen o destino del paquete está entre portnamenum1 y portnamenum2 (ambos inclusive).
Cualquiera de las expresiones de puerto o rango de puertos anteriores puede ir precedida de las palabras clave tcp, udp o sctp, como en: 
tcp src port portnamenum

que coincide solo con paquetes TCP cuyo puerto de origen es portnamenum.
less length
Verdadero si el paquete tiene una longitud menor o igual a length. Esto es equivalente a: 
len <= length

greater length
Verdadero si el paquete tiene una longitud mayor o igual a length. Esto es equivalente a: 
len >= length

ip proto protocol
Verdadero si el paquete es un paquete IPv4 (ver ip(4P)) del tipo de protocolo protocol. Protocol puede ser un número o uno de los nombres reconocidos por getprotobyname(3) (como por ejemplo `getent(1) protocols'), típicamente de una entrada en /etc/protocols, por ejemplo: ah, esp, eigrp (solo en Linux, FreeBSD, NetBSD, DragonFly BSD y macOS), icmp, igmp, igrp (solo en OpenBSD), pim, sctp, tcp, udp o vrrp. Tenga en cuenta que la mayoría de estos identificadores de ejemplo también son palabras clave y deben escaparse con una barra invertida (\). Tenga en cuenta que esta primitiva no sigue la cadena de encabezados del protocolo.
icmp
Abreviatura de: 
ip proto 1

ip6 proto protocol
Verdadero si el paquete es un paquete IPv6 del tipo de protocolo protocol. (Ver `ip proto' arriba para el significado de protocol.) Tenga en cuenta que la variante IPv6 de ICMP utiliza un número de protocolo diferente, denominado ipv6-icmp en AIX, FreeBSD, illumos, Linux, macOS, NetBSD, OpenBSD, Solaris y Windows. Tenga en cuenta que esta primitiva no sigue la cadena de encabezados del protocolo.
icmp6
Abreviatura de: 
ip6 proto 58

proto protocol
Verdadero si el paquete es un paquete IPv4 o IPv6 del tipo de protocolo protocol. (Ver `ip proto' arriba para el significado de protocol.) Tenga en cuenta que esta primitiva no sigue la cadena de encabezados del protocolo.
ah, esp, pim, sctp, tcp, udp
Abreviaturas de: 
proto \protocol

donde protocol es uno de los protocolos anteriores.
ip6 protochain protocol
Verdadero si el paquete es un paquete IPv6 y contiene un encabezado de protocolo con el tipo protocol en su cadena de encabezados de protocolo. (Ver `ip proto' arriba para el significado de protocol.) Por ejemplo, 
ip6 protochain 6

coincide con cualquier paquete IPv6 con un encabezado de protocolo TCP en la cadena de encabezados de protocolo. El paquete puede contener, por ejemplo, un encabezado de autenticación, un encabezado de enrutamiento o un encabezado de opciones hop-by-hop entre el encabezado IPv6 y el encabezado TCP. El código BPF emitido por esta primitiva es complejo y no puede ser optimizado por el código de optimización BPF, y no es compatible con los motores de filtro en el kernel, por lo que puede ser algo lento y puede provocar que se descarten más paquetes.
ip protochain protocol
Equivalente a ip6 protochain protocol, pero esto es para IPv4. (Ver `ip proto' arriba para el significado de protocol.)
protochain protocol
Verdadero si el paquete es un paquete IPv4 o IPv6 del tipo de protocolo protocol. (Ver `ip proto' arriba para el significado de protocol.) Tenga en cuenta que esta primitiva sigue la cadena de encabezados del protocolo.
ether broadcast
Verdadero si el paquete es un paquete de difusión Ethernet. La palabra clave ether es opcional.
ip broadcast
Verdadero si el paquete es un paquete de difusión IPv4. Comprueba tanto las convenciones de difusión de todos los ceros como de todos los unos, y busca la máscara de subred en la interfaz en la que se está realizando la captura.
Si la máscara de subred de la interfaz en la que se está realizando la captura no está disponible, ya sea porque la interfaz en la que se está realizando la captura no tiene máscara de red o porque la captura se está realizando en la interfaz "any" de Linux, que puede capturar en más de una interfaz, esta comprobación no funcionará correctamente.
ether multicast
Verdadero si el paquete es un paquete multicast Ethernet. La palabra clave ether es opcional. Esto es un atajo para `ether[0] & 1 != 0'.
ip multicast
Verdadero si el paquete es un paquete multicast IPv4.
ip6 multicast
Verdadero si el paquete es un paquete multicast IPv6.
ether proto protocol
Verdadero si el paquete es del tipo ether protocol. Protocol puede ser un número o uno de los nombres aarp, arp, atalk, decnet, ip, ip6, ipx, iso, lat, loopback, mopdl, moprc, netbeui, rarp, sca o stp. Tenga en cuenta que estos identificadores (excepto loopback) también son palabras clave y deben escaparse con una barra invertida (\).
[En el caso de FDDI (por ejemplo, `fddi proto \arp'), Token Ring (por ejemplo, `tr proto \arp') y redes locales inalámbricas IEEE 802.11 (por ejemplo, `wlan proto \arp'), para la mayoría de esos protocolos, la identificación del protocolo proviene del encabezado de Control de Enlace Lógico (LLC) 802.2, que generalmente se superpone al encabezado FDDI, Token Ring o 802.11.
Al filtrar para la mayoría de los identificadores de protocolo en FDDI, Token Ring o 802.11, el filtro comprueba solo el campo de identificación del protocolo de un encabezado LLC en formato SNAP con un Identificador de Unidad Organizacional (OUI) de 0x000000, para Ethernet encapsulada; no comprueba si el paquete está en formato SNAP con un OUI de 0x000000. Las excepciones son:
iso
el filtro comprueba los campos DSAP (Destination Service Access Point) y SSAP (Source Service Access Point) del encabezado LLC;
stp y netbeui
el filtro comprueba el DSAP del encabezado LLC;
atalk
el filtro comprueba un paquete en formato SNAP con un OUI de 0x080007 y el etype de AppleTalk.
En el caso de Ethernet, el filtro comprueba el campo de tipo Ethernet para la mayoría de esos protocolos. Las excepciones son:
iso, stp, y netbeui
el filtro comprueba un trama 802.3 y luego comprueba el encabezado LLC como lo hace para FDDI, Token Ring y 802.11;
atalk
el filtro comprueba tanto el etype de AppleTalk en una trama Ethernet como un paquete en formato SNAP, como lo hace para FDDI, Token Ring y 802.11;
aarp
el filtro comprueba el etype ARP de AppleTalk en una trama Ethernet o una trama SNAP 802.2 con un OUI de 0x000000;
ipx
el filtro comprueba el etype IPX en una trama Ethernet, el DSAP IPX en el encabezado LLC, la encapsulación IPX de 802.3 sin encabezado LLC, y el etype IPX en una trama SNAP.
ip, ip6, arp, rarp, atalk, aarp, decnet, iso, stp, ipx, netbeui
Abreviaturas de: 
ether proto \protocol

donde protocol es uno de los protocolos anteriores.
lat, moprc, mopdl
Abreviaturas de: 
ether proto \protocol

donde protocol es uno de los protocolos anteriores. Tenga en cuenta que no todas las aplicaciones que utilizan pcap(3PCAP) saben actualmente cómo analizar estos protocolos.
decnet src decnetaddr
Verdadero si la dirección de origen DECnet es decnetaddr, que puede ser una dirección de la forma ``10.123'', o un nombre de host DECnet. [El soporte de nombres de host DECnet solo está disponible en sistemas ULTRIX configurados para ejecutar DECnet.]
decnet dst decnetaddr
Verdadero si la dirección de destino DECnet es decnetaddr.
decnet host decnetaddr
Verdadero si la dirección de origen o destino DECnet es decnetaddr.
llc
Verdadero si el paquete tiene una cabecera LLC 802.2. Esto incluye:
Paquetes Ethernet con un campo de longitud en lugar de un campo de tipo que no son paquetes NetWare-over-802.3 sin procesar;
Paquetes de datos IEEE 802.11;
Paquetes Token Ring (no se realiza ninguna comprobación de tramas LLC);
Paquetes FDDI (no se realiza ninguna comprobación de tramas LLC);
Paquetes ATM encapsulados en LLC, para SunATM en Solaris.
llc type
Verdadero si el paquete tiene una cabecera LLC 802.2 y tiene el type especificado. type puede ser uno de los siguientes:
i
PDUs de Información (I)
s
PDUs de Supervisión (S)
u
PDUs No Numeradas (U)
rr
PDUs S de Receptor Listo (RR)
rnr
PDUs S de Receptor No Listo (RNR)
rej
PDUs S de Rechazo (REJ)
ui
PDUs U de Información No Numerada (UI)
ua
PDUs U de Reconocimiento No Numerado (UA)
disc
PDUs U de Desconexión (DISC)
sabme
PDUs U de Establecimiento de Modo Equilibrado Asíncrono Extendido (SABME)
test
PDUs U de Prueba (TEST)
xid
PDUs U de Intercambio de Identificación (XID)
frmr
PDUs U de Rechazo de Trama (FRMR)
inbound
El paquete fue recibido por el host que realiza la captura en lugar de ser enviado por ese host. Esto solo se admite para ciertos tipos de enlace, como SLIP y el modo de captura "cocinado" de Linux utilizado para el dispositivo "any" y para algunos otros tipos de dispositivo.
outbound
El paquete fue enviado por el host que realiza la captura en lugar de ser recibido por ese host. Esto solo se admite para ciertos tipos de enlace, como SLIP y el modo de captura "cocinado" de Linux utilizado para el dispositivo "any" y para algunos otros tipos de dispositivo.
ifindex interface_index
Verdadero si el paquete se registró a través de la interfaz especificada (se aplica solo a paquetes registrados por la interfaz cocinada v2 "any" de Linux).
ifname interface
Verdadero si el paquete se registró como proveniente de la interfaz especificada (se aplica solo a paquetes registrados por pf(4) de OpenBSD o FreeBSD).
on interface
Sinónimo del modificador ifname.
rnr num
Verdadero si el paquete se registró como coincidente con el número de regla PF especificado (se aplica solo a paquetes registrados por pf(4) de OpenBSD o FreeBSD).
rulenum num
Sinónimo del modificador rnr.
reason code
Verdadero si el paquete se registró con el código de razón PF especificado. Los códigos conocidos son: match, bad-offset, fragment, short, normalize y memory (se aplica solo a paquetes registrados por pf(4) de OpenBSD o FreeBSD).
rset name
Verdadero si el paquete se registró como coincidente con el nombre del conjunto de reglas PF especificado de un conjunto de reglas anclado (se aplica solo a paquetes registrados por pf(4) de OpenBSD o FreeBSD).
ruleset name
Sinónimo del modificador rset.
srnr num
Verdadero si el paquete se registró como coincidente con el número de regla PF especificado de un conjunto de reglas anclado (se aplica solo a paquetes registrados por pf(4) de OpenBSD o FreeBSD).
subrulenum num
Sinónimo del modificador srnr.
action act
Verdadero si PF tomó la acción especificada al registrar el paquete. Las acciones conocidas son: pass y block y, con versiones posteriores de pf(4), nat, rdr, binat y scrub (se aplica solo a paquetes registrados por pf(4) de OpenBSD o FreeBSD).
wlan ra ehost
Verdadero si la RA IEEE 802.11 es ehost. El campo RA se utiliza en todas las tramas excepto en las tramas de gestión.
wlan ta ehost
Verdadero si la TA IEEE 802.11 es ehost. El campo TA se utiliza en todas las tramas excepto en las tramas de gestión y las tramas de control CTS (Clear To Send) y ACK (Acknowledgment).
wlan addr1 ehost
Verdadero si la primera dirección IEEE 802.11 es ehost.
wlan addr2 ehost
Verdadero si la segunda dirección IEEE 802.11, si está presente, es ehost. El segundo campo de dirección se utiliza en todas las tramas excepto en las tramas de control CTS (Clear To Send) y ACK (Acknowledgment).
wlan addr3 ehost
Verdadero si la tercera dirección IEEE 802.11, si está presente, es ehost. El tercer campo de dirección se utiliza en tramas de gestión y datos, pero no en tramas de control.
wlan addr4 ehost
Verdadero si la cuarta dirección IEEE 802.11, si está presente, es ehost. El cuarto campo de dirección solo se utiliza para tramas WDS (Wireless Distribution System).
type wlan_type
Verdadero si el tipo de trama IEEE 802.11 coincide con el wlan_type especificado. Los wlan_types válidos son: mgt, ctl y data.
type wlan_type subtype wlan_subtype
Verdadero si el tipo de trama IEEE 802.11 coincide con el wlan_type especificado y el subtipo de trama coincide con el wlan_subtype especificado.
Si el wlan_type especificado es mgt, entonces los wlan_subtypes válidos son: assoc-req, assoc-resp, reassoc-req, reassoc-resp, probe-req, probe-resp, beacon, atim, disassoc, auth y deauth.
Si el wlan_type especificado es ctl, entonces los wlan_subtypes válidos son: ps-poll, rts, cts, ack, cf-end y cf-end-ack.
Si el wlan_type especificado es data, entonces los wlan_subtypes válidos son: data, data-cf-ack, data-cf-poll, data-cf-ack-poll, null, cf-ack, cf-poll, cf-ack-poll, qos-data, qos-data-cf-ack, qos-data-cf-poll, qos-data-cf-ack-poll, qos, qos-cf-poll y qos-cf-ack-poll.
subtype wlan_subtype
Verdadero si el subtipo de trama IEEE 802.11 coincide con el wlan_subtype especificado y la trama tiene el tipo al que pertenece el wlan_subtype especificado.
dir direction
Verdadero si la dirección de la trama IEEE 802.11 coincide con la direction especificada. Las direcciones válidas son: nods, tods, fromds, dstods, o un valor numérico.
vlan [vlan_id]
Verdadero si el paquete es un paquete VLAN IEEE 802.1Q. Si se especifica el vlan_id opcional, solo será verdadero si el paquete tiene el vlan_id especificado. Tenga en cuenta que la primera palabra clave vlan encontrada en una expresión cambia los desplazamientos de decodificación para el resto de la expresión asumiendo que el paquete es un paquete VLAN. La palabra clave `vlan [vlan_id]` se puede usar más de una vez, para filtrar en jerarquías VLAN. Cada uso de esa palabra clave incrementa los desplazamientos del filtro en 4.
Por ejemplo: 
vlan 100 && vlan 200

filtra en VLAN 200 encapsulado dentro de VLAN 100, y 
vlan && vlan 300 && ip

filtra el protocolo IPv4 encapsulado en VLAN 300 encapsulado dentro de cualquier VLAN de orden superior.
mpls [label_num]
Verdadero si el paquete es un paquete MPLS. Si se especifica el label_num opcional, solo será verdadero si el paquete tiene el label_num especificado. Tenga en cuenta que la primera palabra clave mpls encontrada en una expresión cambia los desplazamientos de decodificación para el resto de la expresión asumiendo que el paquete es un paquete IP encapsulado en MPLS. La palabra clave `mpls [label_num]` se puede usar más de una vez, para filtrar en jerarquías MPLS. Cada uso de esa palabra clave incrementa los desplazamientos del filtro en 4.
Por ejemplo: 
mpls 100000 && mpls 1024

filtra paquetes con una etiqueta externa de 100000 y una etiqueta interna de 1024, y 
mpls && mpls 1024 && host 192.9.200.1

filtra paquetes hacia o desde 192.9.200.1 con una etiqueta interna de 1024 y cualquier etiqueta externa.
pppoed
Verdadero si el paquete es un paquete de descubrimiento PPP-over-Ethernet (tipo Ethernet 0x886
3).
pppoes [session_id]
Verdadero si el paquete es un paquete de sesión PPP sobre Ethernet (tipo Ethernet 0x8864). Si se especifica el session_id opcional, solo es verdadero si el paquete tiene el session_id especificado. Tenga en cuenta que la primera palabra clave pppoes encontrada en una expresión cambia los desplazamientos de decodificación para el resto de la expresión, asumiendo que el paquete es un paquete de sesión PPPoE.
Por ejemplo: 
pppoe 0x27 && ip

filtra el protocolo IPv4 encapsulado en el id de sesión PPPoE 0x27.
geneve [vni]
Verdadero si el paquete es un paquete Geneve (puerto UDP 6081). Si se especifica el vni opcional, solo es verdadero si el paquete tiene el vni especificado. Tenga en cuenta que cuando se encuentra la palabra clave geneve en una expresión, cambia los desplazamientos de decodificación para el resto de la expresión, asumiendo que el paquete es un paquete Geneve.
Por ejemplo: 
geneve 0xb && ip

filtra el protocolo IPv4 encapsulado en Geneve con VNI 0xb. Esto coincidirá tanto con IPv4 directamente encapsulado en Geneve como con IPv4 contenido dentro de una trama Ethernet.
iso proto protocolo
Verdadero si el paquete es un paquete OSI de tipo de protocolo protocolo. Protocolo puede ser un número o uno de los nombres clnp, esis o isis.
clnp, esis, isis
Abreviaturas para: 
iso proto \protocolo

donde protocolo es uno de los protocolos anteriores.
l1, l2, iih, lsp, snp, csnp, psnp
Abreviaturas para tipos de PDU IS-IS.
vpi n
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, con un identificador de ruta virtual de n.
vci n
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, con un identificador de canal virtual de n.
lane
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y es un paquete ATM LANE. Tenga en cuenta que la primera palabra clave lane encontrada en una expresión cambia las pruebas realizadas en el resto de la expresión, asumiendo que el paquete es un paquete Ethernet emulado por LANE o un paquete de control LE de LANE. Si lane no se especifica, las pruebas se realizan asumiendo que el paquete es un paquete encapsulado en LLC.
oamf4s
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y es una celda de flujo OAM F4 de segmento (VPI=0 & VCI=3).
oamf4e
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y es una celda de flujo OAM F4 de extremo a extremo (VPI=0 & VCI=4).
oamf4
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y es una celda de flujo OAM F4 de segmento o de extremo a extremo (VPI=0 & (VCI=3 | VCI=4)).
oam
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y es una celda de flujo OAM F4 de segmento o de extremo a extremo (VPI=0 & (VCI=3 | VCI=4)).
metac
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y está en un circuito de señalización meta (VPI=0 & VCI=1).
bcc
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y está en un circuito de señalización de difusión (VPI=0 & VCI=2).
sc
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y está en un circuito de señalización (VPI=0 & VCI=5).
ilmic
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y está en un circuito ILMI (VPI=0 & VCI=16).
connectmsg
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y está en un circuito de señalización y es un mensaje Q.2931 Setup, Call Proceeding, Connect, Connect Ack, Release o Release Done.
metaconnect
Verdadero si el paquete es un paquete ATM, para SunATM en Solaris, y está en un circuito de señalización meta y es un mensaje Q.2931 Setup, Call Proceeding, Connect, Release o Release Done.
expr1 relop expr2
Verdadero si la relación se cumple. Relop es uno de {>, <, >=, <=, =, ==, !=} (donde = significa lo mismo que ==). Cada uno de expr1 y expr2 es una expresión aritmética compuesta por constantes enteras (expresadas en sintaxis estándar de C), los operadores binarios normales {+, -, *, /, %, &, |, ^, <<, >>}, un operador de longitud y accesores especiales de datos de paquetes. Tenga en cuenta que todas las comparaciones son sin signo, por lo que, por ejemplo, 0x80000000 y 0xffffffff son > 0.
Los operadores % y ^ actualmente solo se admiten para filtrar en el kernel en sistemas operativos específicos (por ejemplo: FreeBSD, Linux con kernels 3.7 y posteriores, NetBSD); en todos los demás sistemas (por ejemplo: AIX, illumos, Solaris, OpenBSD), si se utilizan esos operadores, el filtrado se realizará en modo de usuario, lo que aumentará la sobrecarga de la captura de paquetes y puede provocar que se descarten más paquetes.
El operador de longitud, indicado por la palabra clave len, proporciona la longitud del paquete.
Para acceder a datos dentro del paquete, use la siguiente sintaxis: 
proto [ expr : size ]

Proto es uno de arp, atalk, carp, decnet, ether, fddi, icmp, icmp6, igmp, igrp, ip, ip6, lat, link, mopdl, moprc, pim, ppp, radio, rarp, sca, sctp, slip, tcp, tr, udp, vrrp o wlan, e indica la capa de protocolo para la operación de índice. (ether, fddi, link, ppp, slip, tr y wlan se refieren a la capa de enlace. radio se refiere a la "cabecera de radio" añadida a algunas capturas de 802.11.) Tenga en cuenta que tcp, udp y otros tipos de protocolos de capa superior solo se aplican a IPv4, no a IPv6 (esto se corregirá en el futuro). El desplazamiento de bytes, relativo a la capa de protocolo indicada, viene dado por expr. Size es opcional e indica el número de bytes en el campo de interés; puede ser uno, dos o cuatro, y por defecto es uno.

Por ejemplo, `ether[0] & 1 != 0' captura todo el tráfico multicast. La expresión `ip[0] & 0xf != 5' captura todos los paquetes IPv4 con opciones. La expresión `ip[6:2] & 0x1fff = 0' captura solo datagramas IPv4 no fragmentados y el fragmento cero de datagramas IPv4 fragmentados. Esta comprobación se aplica implícitamente a las operaciones de índice de tcp y udp. Por ejemplo, tcp[0] siempre significa el primer byte de la cabecera TCP, y nunca el primer byte de un fragmento intermedio.

Algunos desplazamientos y valores de campo se pueden expresar como nombres en lugar de valores numéricos. Los siguientes desplazamientos de campos de cabecera de protocolo están disponibles: icmptype (campo de tipo ICMP), icmp6type (campo de tipo ICMPv6), icmpcode (campo de código ICMP), icmp6code (campo de código ICMPv6) y tcpflags (campo de banderas TCP).
Los siguientes valores de campo de tipo ICMP están disponibles: icmp-echoreply, icmp-unreach, icmp-sourcequench, icmp-redirect, icmp-echo, icmp-routeradvert, icmp-routersolicit, icmp-timxceed, icmp-paramprob, icmp-tstamp, icmp-tstampreply, icmp-ireq, icmp-ireqreply, icmp-maskreq, icmp-maskreply.
Los siguientes valores de campo de tipo ICMPv6 están disponibles: icmp6-destinationunreach, icmp6-packettoobig, icmp6-timeexceeded, icmp6-parameterproblem, icmp6-echo, icmp6-echoreply, icmp6-multicastlistenerquery, icmp6-multicastlistenerreportv1, icmp6-multicastlistenerdone, icmp6-routersolicit, icmp6-routeradvert, icmp6-neighborsolicit, icmp6-neighboradvert, icmp6-redirect, icmp6-routerrenum, icmp6-nodeinformationquery, icmp6-nodeinformationresponse, icmp6-ineighbordiscoverysolicit, icmp6-ineighbordiscoveryadvert, icmp6-multicastlistenerreportv2, icmp6-homeagentdiscoveryrequest, icmp6-homeagentdiscoveryreply, icmp6-mobileprefixsolicit, icmp6-mobileprefixadvert, icmp6-certpathsolicit, icmp6-certpathadvert, icmp6-multicastrouteradvert, icmp6-multicastroutersolicit, icmp6-multicastrouterterm.
Los siguientes valores de campo de banderas TCP están disponibles: tcp-fin, tcp-syn, tcp-rst, tcp-push, tcp-ack, tcp-urg, tcp-ece, tcp-cwr.

Los primitivos pueden combinarse usando:

Un grupo entre paréntesis de primitivos y operadores.
Negación (`!' o `not').
Concatenación (`&&' o `and').
Alternancia (`||' o `or').

La negación tiene la precedencia más alta. La alternancia y la concatenación tienen la misma precedencia y se asocian de izquierda a derecha.

Si se proporciona un identificador sin una palabra clave, se asume la palabra clave más reciente. Por ejemplo, 

not host vs and ace
es una abreviatura de 
not host vs and host ace
que no debe confundirse con 
not (host vs or ace)

EJEMPLOS

Para seleccionar todos los paquetes que llegan o salen de `sundown':

host sundown

Para seleccionar el tráfico entre `helios' y `hot' o `ace':

host helios y (hot o ace)

Para seleccionar todos los paquetes IPv4 entre `ace' y cualquier host excepto `helios':

ip host ace y no helios

Para seleccionar todo el tráfico entre hosts locales y hosts en Berkeley:

net ucb-ether

Para seleccionar todo el tráfico FTP a través de la puerta de enlace de Internet `snup':

gateway snup y (puerto ftp o ftp-data)

Para seleccionar tráfico IPv4 que no se origina ni se destina a hosts locales (si te conectas a otra red, este tráfico nunca debería llegar a tu red local).

ip y no net localnet

Para seleccionar los paquetes de inicio y fin (los paquetes SYN y FIN) de cada conversación TCP que involucre a un host no local.

tcp[tcpflags] & (tcp-syn|tcp-fin) != 0 y no src y dst net localnet

Para seleccionar los paquetes TCP con las banderas RST y ACK ambas establecidas. (es decir, seleccionar solo las banderas RST y ACK en el campo de banderas, y si el resultado es "RST y ACK ambas establecidas", coincidir)


tcp[tcpflags] & (tcp-rst|tcp-ack) == (tcp-rst|tcp-ack)

Para seleccionar todos los paquetes HTTP IPv4 hacia y desde el puerto 80, es decir, imprimir solo los paquetes que contienen datos, no, por ejemplo, los paquetes SYN y FIN ni los paquetes solo ACK. (IPv6 se deja como ejercicio para el lector).

tcp port 80 y (((ip[2:2] - ((ip[0]&0xf)<<2)) - ((tcp[12]&0xf0)>>2)) != 0)

Para seleccionar paquetes IPv4 de más de 576 bytes enviados a través de la puerta de enlace `snup':

gateway snup y ip[2:2] > 576

Para seleccionar paquetes de broadcast o multicast IPv4 que *no* fueron enviados a través de broadcast o multicast Ethernet:

ether[0] & 1 = 0 y ip[16] >= 224

Para seleccionar todos los paquetes ICMP que no son solicitudes/respuestas de eco (es decir, no son paquetes ping):


icmp[icmptype] != icmp-echo y icmp[icmptype] != icmp-echoreply

icmp6[icmp6type] != icmp6-echo y icmp6[icmp6type] != icmp6-echoreply

Los nombres de los códigos de tipo ICMPv6, así como los nombres de las banderas TCP tcp-ece y tcp-cwr estuvieron disponibles en libpcap 1.9.0.

ERRORES

Para informar de un problema de seguridad, envíe un correo electrónico a security@tcpdump.org.

Para informar de errores y otros problemas, contribuir con parches, solicitar una característica, proporcionar comentarios generales, etc., consulte el archivo CONTRIBUTING.md en la raíz del árbol fuente de libpcap.

Las expresiones de filtro en campos distintos de los de las cabeceras Token Ring no manejarán correctamente los paquetes Token Ring con enrutamiento de origen.

Las expresiones de filtro en campos distintos de los de las cabeceras 802.11 no manejarán correctamente los paquetes de datos 802.11 con To DS y From DS establecidos.

`ip6 proto' debería seguir la cadena de cabeceras, pero en este momento no lo hace. Se proporciona `ip6 protochain' para este comportamiento. Por ejemplo, para hacer coincidir fragmentos IPv6: `ip6 protochain 44'

La expresión aritmética contra las cabeceras de la capa de transporte, como tcp[0], no funciona contra paquetes IPv6. Solo examina paquetes IPv4.
