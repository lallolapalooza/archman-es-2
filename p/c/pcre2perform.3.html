NOMBRE

PCRE2 - expresiones regulares compatibles con Perl (API revisada)

PCRE2 RENDIMIENTO

A continuación se discuten dos aspectos del rendimiento: el uso de memoria y el tiempo de procesamiento. La forma en que expresas tu patrón como una expresión regular puede afectar a ambos.

USO DE MEMORIA DEL PATRÓN COMPILADO

Los patrones son compilados por PCRE2 en un código interpretativo razonablemente eficiente, de modo que la mayoría de los patrones simples no usan mucha memoria para almacenar la versión compilada. Sin embargo, hay un caso en el que el uso de memoria de un patrón compilado puede ser inesperadamente grande. Si un grupo entre paréntesis tiene un cuantificador con un mínimo mayor que 1 y/o un máximo limitado, todo el grupo se repite en el código compilado. Por ejemplo, el patrón


(abc|def){2,4}

se compila como si fuera


(abc|def)(abc|def)((abc|def)(abc|def)?)?

(Aclaración técnica: se hace de esta manera para que los puntos de retroceso dentro de cada una de las repeticiones puedan mantenerse de forma independiente.)

Para expresiones regulares cuyos cuantificadores usan solo números pequeños, esto no suele ser un problema. Sin embargo, si los números son grandes, y en particular si tales repeticiones están anidadas, el uso de memoria puede volverse embarazoso. Por ejemplo, el patrón muy simple


((ab){1,1000}c){1,3}

usa más de 50KiB cuando se compila usando la biblioteca de 8 bits. Cuando PCRE2 se compila con su tamaño de puntero interno predeterminado de dos bytes, el límite de tamaño en un patrón compilado es de 65535 unidades de código en las bibliotecas de 8 y 16 bits, y este se alcanza con el patrón anterior si la repetición externa se incrementa de 3 a 4. PCRE2 puede compilarse para usar punteros internos más grandes y así manejar patrones compilados más grandes, pero es mejor intentar reescribir tu patrón para usar menos memoria si puedes.

Una forma de reducir el uso de memoria para tales patrones es hacer uso de la instalación de "subrutina" de PCRE2. Reescribiendo el patrón anterior como


((ab)(?2){0,999}c)(?1){0,2}

reduce los requisitos de memoria a alrededor de 16KiB, y de hecho permanece por debajo de 20KiB incluso con la repetición externa aumentada a 100. Sin embargo, este tipo de patrón no siempre es exactamente equivalente, ya que las capturas dentro de las llamadas a subrutinas se pierden cuando la subrutina se completa. Si esto no es un problema, este tipo de reescritura te permitirá procesar patrones que PCRE2 de otra manera no puede manejar. El rendimiento de coincidencia de las dos versiones diferentes del patrón es aproximadamente el mismo. (Esto se aplica a partir de la versión 10.30 - las cosas eran diferentes en versiones anteriores.)

USO DE PILAS Y MONTÓN EN TIEMPO DE EJECUCIÓN

A partir de la versión 10.30, la versión interpretativa (no JIT) de pcre2_match() utiliza muy poca pila del sistema en tiempo de ejecución. En versiones anteriores, las llamadas recursivas a funciones podían usar mucha pila, y esto podía causar problemas, pero este uso se ha eliminado. Las posiciones de retroceso ahora se recuerdan explícitamente en marcos de memoria controlados por el código.

El tamaño de cada marco depende del tamaño de las variables de puntero y del número de grupos entre paréntesis de captura en el patrón que se está emparejando. En un sistema de 64 bits, el tamaño del marco para un patrón sin capturas es de 128 bytes. Por cada grupo de captura, el tamaño aumenta en 16 bytes.

Hasta la versión 10.41, se asignaba un vector inicial de 20KiB de marcos en la pila del sistema, pero esto todavía causaba algunos problemas para aplicaciones multihilo donde cada hilo tiene una pila muy pequeña. A partir de la versión 10.41, los marcos de memoria de retroceso siempre se almacenan en memoria del montón. Se obtiene una asignación inicial del montón la primera vez que se pasa un bloque de datos de coincidencia a pcre2_match(). Esto se recuerda con el bloque de datos de coincidencia y se reutiliza si ese bloque se usa para otra coincidencia. Se libera cuando el propio bloque de datos de coincidencia se libera.

El tamaño del bloque inicial es el mayor entre 20KiB o diez veces el tamaño del marco del patrón, a menos que el límite del montón sea menor que esto, en cuyo caso se utiliza el límite del montón. Si el bloque inicial resulta ser demasiado pequeño durante la coincidencia, se reemplaza por un bloque más grande, sujeto al límite del montón. El límite del montón solo se verifica cuando se va a asignar un nuevo bloque. Reducir el límite del montón entre llamadas a pcre2_match() con el mismo bloque de datos de coincidencia no afecta al bloque guardado.

En contraste con pcre2_match(), pcre2_dfa_match() utiliza llamadas recursivas a funciones, pero solo para procesar grupos atómicos, aserciones de lookaround y recursión dentro del patrón. La versión original del código solía asignar vectores de espacio de trabajo internos bastante grandes en la pila, lo que causaba algunos problemas para algunos patrones en entornos con pilas pequeñas. A partir de la versión 10.32, el código para pcre2_dfa_match() ha sido reestructurado para usar memoria del montón cuando sea necesario para el espacio de trabajo interno al recursar, aunque todavía se utilizan llamadas recursivas a funciones.

El parámetro "profundidad de coincidencia" se puede usar para limitar la profundidad de la recursión de la función, y el parámetro "montón de coincidencia" para limitar la memoria del montón en pcre2_dfa_match().

TIEMPO DE PROCESAMIENTO

Ciertos elementos en los patrones de expresiones regulares se procesan de manera más eficiente que otros. Es más eficiente usar una clase de caracteres como [aeiou] que un conjunto de alternativas de un solo carácter como (a|e|i|o|u). En general, la construcción más simple que proporciona el comportamiento requerido suele ser la más eficiente. El libro de Jeffrey Friedl contiene muchas discusiones generales útiles sobre la optimización de expresiones regulares para un rendimiento eficiente. Este documento contiene algunas observaciones sobre PCRE2.

El uso de propiedades de caracteres Unicode (los escapes \p, \P y \X) es lento, porque PCRE2 tiene que usar una búsqueda de tabla de varias etapas cada vez que necesita la propiedad de un carácter. Si puedes encontrar un patrón alternativo que no use propiedades de caracteres, probablemente sea más rápido.

Por defecto, las secuencias de escape \b, \d, \s y \w, y las clases de caracteres POSIX como [:alpha:] no usan propiedades Unicode, en parte por razones de compatibilidad retroactiva y en parte por razones de rendimiento. Sin embargo, puedes establecer la opción PCRE2_UCP o comenzar el patrón con (*UCP) si deseas que se utilicen propiedades de caracteres Unicode. Esto puede duplicar el tiempo de coincidencia para elementos como \d, cuando se empareja con pcre2_match(); la pérdida de rendimiento es menor con una función de coincidencia DFA, y en ambos casos no hay mucha diferencia para \b.

Cuando un patrón comienza con .* no en paréntesis atómicos, ni en paréntesis que son el sujeto de una referencia inversa, y la opción PCRE2_DOTALL está establecida, el patrón está implícitamente anclado por PCRE2, ya que solo puede coincidir al principio de una cadena sujeto. Si el patrón tiene múltiples ramas de nivel superior, todas deben ser anclables. La optimización puede ser deshabilitada por la opción PCRE2_NO_DOTSTAR_ANCHOR, y se deshabilita automáticamente si el patrón contiene (*PRUNE) o (*SKIP).

Si PCRE2_DOTALL no está establecido, PCRE2 no puede realizar esta optimización, porque el metacaracter punto no coincide con un salto de línea, y si la cadena sujeto contiene saltos de línea, el patrón puede coincidir desde el carácter inmediatamente posterior a uno de ellos en lugar de desde el principio. Por ejemplo, el patrón


.*segundo

coincide con el sujeto "primero\nY segundo", (donde \n representa un carácter de salto de línea), con la coincidencia comenzando en el séptimo carácter. Para hacer esto, PCRE2 tiene que reintentar la coincidencia comenzando después de cada salto de línea en el sujeto.

Si estás usando tal patrón con cadenas sujeto que no contienen saltos de línea, el mejor rendimiento se obtiene estableciendo PCRE2_DOTALL, o comenzando el patrón con ^.* o ^.*? para indicar un anclaje explícito. Eso evita que PCRE2 tenga que escanear la cadena buscando un salto de línea para reiniciar.

Cuidado con los patrones que contienen repeticiones indefinidas anidadas. Estos pueden tardar mucho tiempo en ejecutarse cuando se aplican a una cadena que no coincide. Considera el fragmento de patrón


^(a+)*

Esto puede coincidir con "aaaa" de 16 maneras diferentes, y este número aumenta muy rápidamente a medida que la cadena se alarga. (La repetición * puede coincidir 0, 1, 2, 3 o 4 veces, y para cada uno de esos casos, excepto 0 o 4, las repeticiones + pueden coincidir con diferentes números de veces.) Cuando el resto del patrón es tal que toda la coincidencia va a fallar, PCRE2 en principio tiene que probar cada posible variación, y esto puede llevar un tiempo extremadamente largo, incluso para cadenas relativamente cortas.

>Una optimización captura algunos de los casos más simples, como


(a+)*b

donde sigue un carácter literal. Antes de embarcarse en el procedimiento de coincidencia estándar, PCRE2 comprueba que hay una "b" más adelante en la cadena del sujeto y, si no la hay, falla la coincidencia inmediatamente. Sin embargo, cuando no hay un literal siguiente, esta optimización no se puede utilizar. Puede ver la diferencia comparando el comportamiento de


(a+)*\d

con el patrón anterior. El primero falla casi instantáneamente cuando se aplica a toda una línea de caracteres "a", mientras que el segundo tarda un tiempo considerable con cadenas de más de unos 20 caracteres.

En muchos casos, la solución a este tipo de problemas de rendimiento es utilizar un grupo atómico o un cuantificador posesivo. Esto a menudo puede reducir también los requisitos de memoria. Como otro ejemplo, considere este patrón:


([^<]|<(?!inet))+

Coincide desde donde empiece hasta que encuentre "<inet" o el final de los datos, y es el tipo de patrón que podría usarse al procesar un archivo XML. Cada iteración de los paréntesis externos coincide con un carácter que no es "<" o un "<" que no va seguido de "inet". Sin embargo, cada vez que se procesan los paréntesis, se pasa una posición de retroceso, por lo que esta formulación utiliza un marco de memoria por cada carácter coincidente. Para una cadena larga, se requiere mucha memoria. Considere ahora este patrón reescrito, que coincide exactamente con las mismas cadenas:


([^<]++|<(?!inet))+

Esto se ejecuta mucho más rápido, porque las secuencias de caracteres que no contienen "<" se "tragan" en un solo elemento dentro de los paréntesis, y se utiliza un cuantificador posesivo para detener cualquier retroceso en las secuencias de caracteres que no son "<". Esta versión también utiliza mucha menos memoria porque la entrada a un nuevo conjunto de paréntesis solo ocurre cuando se encuentra un carácter "<" que no va seguido de "inet" (y asumimos que esto es relativamente raro).

Este ejemplo muestra que una forma de optimizar el rendimiento al hacer coincidir cadenas de sujetos largas es escribir subpatrones repetidos entre paréntesis para que coincidan con más de un carácter siempre que sea posible.

CONFIGURACIÓN DE LÍMITES DE RECURSOS

Puede establecer límites en la cantidad de procesamiento que se lleva a cabo al hacer coincidir, y en la cantidad de memoria del heap que se utiliza. Los valores predeterminados de los límites son muy grandes y es poco probable que se activen. Se pueden cambiar cuando se compila PCRE2, y también se pueden establecer cuando se llama a pcre2_match() o pcre2_dfa_match(). Para obtener detalles sobre estas interfaces, consulte la documentación de pcre2build y la sección titulada "El contexto de coincidencia" en la documentación de pcre2api.

El programa de prueba pcre2test tiene un modificador llamado "find_limits" que, si se aplica a una línea de sujeto, hace que encuentre los límites más pequeños que permiten que un patrón coincida. Esto se hace coincidiendo repetidamente con diferentes límites.
