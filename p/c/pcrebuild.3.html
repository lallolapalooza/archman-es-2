PCREBUILD(3) Manual de Funciones de Biblioteca PCREBUILD(3)

NOMBRE

PCRE - expresiones regulares compatibles con Perl

COMPILACIÓN DE PCRE

PCRE se distribuye con un script configure que puede ser utilizado para compilar la biblioteca en entornos similares a Unix utilizando las aplicaciones conocidas como Autotools. También en la distribución hay archivos para soportar la compilación utilizando CMake en lugar de configure. El archivo de texto README contiene información general sobre la compilación con Autotools (parte de la cual se repite a continuación), y también tiene algunos comentarios sobre la compilación en varios sistemas operativos. Hay mucha más información sobre la compilación de PCRE sin usar Autotools (incluida información sobre el uso de CMake y la compilación "manual") en el archivo de texto llamado NON-AUTOTOOLS-BUILD. Debería consultar este archivo así como el archivo README si está compilando en un entorno no similar a Unix.

OPCIONES DE TIEMPO DE COMPILACIÓN DE PCRE

El resto de este documento describe las características opcionales de PCRE que se pueden seleccionar al compilar la biblioteca. Asume el uso del script configure, donde las características opcionales se seleccionan o deseleccionan proporcionando opciones a configure antes de ejecutar el comando make. Sin embargo, las mismas opciones se pueden seleccionar tanto en entornos similares a Unix como no similares a Unix utilizando la funcionalidad GUI de cmake-gui si está utilizando CMake en lugar de configure para compilar PCRE.

Si no está utilizando Autotools o CMake, la selección de opciones se puede realizar editando el archivo config.h, o pasando parámetros al compilador, como se describe en NON-AUTOTOOLS-BUILD.

La lista completa de opciones para configure (que incluye las estándar como la selección del directorio de instalación) se puede obtener ejecutando


./configure --help

Las siguientes secciones incluyen descripciones de opciones cuyos nombres comienzan con --enable o --disable. Estas configuraciones especifican cambios en los valores predeterminados para el comando configure. Debido a la forma en que funciona configure, --enable y --disable siempre vienen en pares, por lo que la opción complementaria siempre existe también, pero como especifica el valor predeterminado, no se describe.

COMPILACIÓN DE BIBLIOTECAS DE 8-BIT, 16-BIT Y 32-BIT

Por defecto, se compila una biblioteca llamada libpcre, que contiene funciones que toman argumentos de cadena de caracteres contenidos en vectores de bytes, ya sea como caracteres de un solo byte, o interpretados como cadenas UTF-8. También puede compilar una biblioteca separada, llamada libpcre16, en la que las cadenas de caracteres se contienen en vectores de unidades de datos de 16 bits y se interpretan como caracteres de unidad única o cadenas UTF-16, añadiendo


--enable-pcre16

al comando configure. También puede compilar otra biblioteca separada, llamada libpcre32, en la que las cadenas de caracteres se contienen en vectores de unidades de datos de 32 bits y se interpretan como caracteres de unidad única o cadenas UTF-32, añadiendo


--enable-pcre32

al comando configure. Si no desea la biblioteca de 8 bits, añada


--disable-pcre8

también. Se debe compilar al menos una de las tres bibliotecas. Tenga en cuenta que los envoltorios C++ y POSIX son solo para la biblioteca de 8 bits, y que pcregrep es un programa de 8 bits. Ninguno de estos se compila si solo selecciona las bibliotecas de 16 bits o 32 bits.

COMPILACIÓN DE BIBLIOTECAS COMPARTIDAS Y ESTÁTICAS

El proceso de compilación de PCRE de Autotools utiliza libtool para compilar bibliotecas compartidas y estáticas por defecto. Puede suprimir una de ellas añadiendo una de las siguientes opciones:


--disable-shared
--disable-static

a el comando configure, según sea necesario.

SOPORTE DE C++

Por defecto, si se está compilando la biblioteca de 8 bits, el script configure buscará un compilador de C++ y archivos de cabecera de C++. Si los encuentra, compila automáticamente la biblioteca envoltorio de C++ (que solo soporta cadenas de 8 bits). Puede deshabilitar esto añadiendo


--disable-cpp

al comando configure.

SOPORTE DE UTF-8, UTF-16 Y UTF-32

Para compilar PCRE con soporte para cadenas de caracteres Unicode UTF, añada


--enable-utf

al comando configure. Esta configuración se aplica a las tres bibliotecas, añadiendo soporte para UTF-8 a la biblioteca de 8 bits, soporte para UTF-16 a la biblioteca de 16 bits y soporte para UTF-32 a la biblioteca de 32 bits. No hay opciones separadas para habilitar UTF-8, UTF-16 y UTF-32 de forma independiente porque eso permitiría configuraciones ridículas como solicitar soporte UTF-16 mientras se compila solo la biblioteca de 8 bits. No es posible compilar una biblioteca con soporte UTF y otra sin él en la misma configuración. (Por compatibilidad, --enable-utf8 es un sinónimo de --enable-utf.)

Por sí mismo, esta configuración no hace que PCRE trate las cadenas como UTF-8, UTF-16 o UTF-32. Además de compilar PCRE con esta opción, también debe establecer la opción PCRE_UTF8, PCRE_UTF16 o PCRE_UTF32 (según corresponda) al llamar a una de las funciones de compilación de patrones.

Si establece --enable-utf al compilar en un entorno EBCDIC, PCRE espera que su entrada sea ASCII o UTF-8 (dependiendo de la opción en tiempo de ejecución). No es posible soportar códigos EBCDIC y UTF-8 en la misma versión de la biblioteca. En consecuencia, --enable-utf y --enable-ebcdic son mutuamente excluyentes.

SOPORTE DE PROPIEDADES DE CARACTERES UNICODE

El soporte UTF permite a las bibliotecas procesar puntos de código de caracteres de hasta 0x10ffff en las cadenas que manejan. Por sí solo, sin embargo, no proporciona ninguna facilidad para acceder a las propiedades de dichos caracteres. Si desea poder utilizar los escapes de patrón \P, \p y \X, que se refieren a las propiedades de caracteres Unicode, debe añadir


--enable-unicode-properties

al comando configure. Esto implica soporte UTF, incluso si no lo ha solicitado explícitamente.

Incluir soporte para propiedades Unicode añade alrededor de 30K de tablas a la biblioteca PCRE. Solo se soportan las propiedades de categoría general como Lu y Nd. Los detalles se dan en la documentación de pcrepattern.

SOPORTE DE COMPILADOR JUST-IN-TIME

El soporte del compilador just-in-time se incluye en la compilación especificando


--enable-jit

Este soporte solo está disponible para ciertas arquitecturas de hardware. Si esta opción se establece para una arquitectura no soportada, se produce un error de compilación. Consulte la documentación de pcrejit para una discusión sobre el uso de JIT. Cuando el soporte JIT está habilitado, pcregrep lo utiliza automáticamente, a menos que añada


--disable-pcregrep-jit

al comando "configure".

VALOR DE CÓDIGO DE NUEVA LÍNEA

Por defecto, PCRE interpreta el carácter de salto de línea (LF) como indicativo del final de una línea. Este es el carácter de nueva línea normal en sistemas similares a Unix. Puede compilar PCRE para usar retorno de carro (CR) en su lugar, añadiendo


--enable-newline-is-cr

al comando configure. También existe la opción --enable-newline-is-lf, que especifica explícitamente el salto de línea como carácter de nueva línea.

Alternativamente, puede especificar que los finales de línea estén indicados por la secuencia de dos caracteres CRLF. Si desea esto, añada


--enable-newline-is-crlf

al comando configure. Hay una cuarta opción, especificada por


--enable-newline-is-anycrlf

que hace que PCRE reconozca cualquiera de las tres secuencias CR, LF o CRLF como indicativo de un final de línea. Finalmente, una quinta opción, especificada por


--enable-newline-is-any

hace que PCRE reconozca cualquier U

LINE ENDING CONVENTION

PCRE can be built to recognize the sequence \R as matching either the standard newline sequence for the operating system at build time, or as matching CR, LF, or CRLF. The default is the former.

You can change the default at build time by adding one of the following options to the configure command:

--enable-newline-is-cr
Make \R match only CR.
--enable-newline-is-lf
Make \R match only LF.
--enable-newline-is-crlf
Make \R match only CRLF.
--enable-newline-is-anycrlf
Make \R match CR, LF, or CRLF.
--enable-bsr-anycrlf
This is an alternative way of specifying that \R should match CR, LF, or CRLF. It is for use with PCRE 7.0 and later versions. In earlier versions, the only way to specify that \R should match any newline sequence was to use the --enable-bsr-anycrlf option. In later versions, this option still works but is deprecated.

The default behaviour, if none of these options is specified, is to use the operating system's standard line ending sequence. For Unix, this is LF. For Windows, this is CRLF. For Macintosh, this is CR.

Whatever line ending convention is selected when PCRE is built can be overridden when the library functions are called.

WHAT \R MATCHES

By default, the sequence \R in a pattern matches any Unicode newline sequence, whatever has been selected as the line ending sequence. If you specify


--enable-bsr-anycrlf

the default is changed so that \R matches only CR, LF, or CRLF. Whatever is selected when PCRE is built can be overridden when the library functions are called.

POSIX MALLOC USAGE

When the 8-bit library is called through the POSIX interface (see the pcreposix documentation), additional working storage is required for holding the pointers to capturing substrings, because PCRE requires three integers per substring, whereas the POSIX interface provides only two. If the number of expected substrings is small, the wrapper function uses space on the stack, because this is faster than using malloc() for each call. The default threshold above which the stack is no longer used is 10; it can be changed by adding a setting such as


--with-posix-malloc-threshold=20

to the configure command.

HANDLING VERY LARGE PATTERNS

Within a compiled pattern, offset values are used to point from one part to another (for example, from an opening parenthesis to an alternation metacharacter). By default, in the 8-bit and 16-bit libraries, two-byte values are used for these offsets, leading to a maximum size for a compiled pattern of around 64K. This is sufficient to handle all but the most gigantic patterns. Nevertheless, some people do want to process truly enormous patterns, so it is possible to compile PCRE to use three-byte or four-byte offsets by adding a setting such as


--with-link-size=3

to the configure command. The value given must be 2, 3, or 4. For the 16-bit library, a value of 3 is rounded up to 4. In these libraries, using longer offsets slows down the operation of PCRE because it has to load additional data when handling them. For the 32-bit library the value is always 4 and cannot be overridden; the value of --with-link-size is ignored.

AVOIDING EXCESSIVE STACK USAGE

When matching with the pcre_exec() function, PCRE implements backtracking by making recursive calls to an internal function called match(). In environments where the size of the stack is limited, this can severely limit PCRE's operation. (The Unix environment does not usually suffer from this problem, but it may sometimes be necessary to increase the maximum stack size. There is a discussion in the pcrestack documentation.) An alternative approach to recursion that uses memory from the heap to remember data, instead of using recursive function calls, has been implemented to work round the problem of limited stack size. If you want to build a version of PCRE that works this way, add


--disable-stack-for-recursion

to the configure command. With this configuration, PCRE will use the pcre_stack_malloc and pcre_stack_free variables to call memory management functions. By default these point to malloc() and free(), but you can replace the pointers so that your own functions are used instead.

Separate functions are provided rather than using pcre_malloc and pcre_free because the usage is very predictable: the block sizes requested are always the same, and the blocks are always freed in reverse order. A calling program might be able to implement optimized functions that perform better than malloc() and free(). PCRE runs noticeably more slowly when built in this way. This option affects only the pcre_exec() function; it is not relevant for pcre_dfa_exec().

LIMITING PCRE RESOURCE USAGE

Internally, PCRE has a function called match(), which it calls repeatedly (sometimes recursively) when matching a pattern with the pcre_exec() function. By controlling the maximum number of times this function may be called during a single matching operation, a limit can be placed on the resources used by a single call to pcre_exec(). The limit can be changed at run time, as described in the pcreapi documentation. The default is 10 million, but this can be changed by adding a setting such as


--with-match-limit=500000

to the configure command. This setting has no effect on the pcre_dfa_exec() matching function.

In some environments it is desirable to limit the depth of recursive calls of match() more strictly than the total number of calls, in order to restrict the maximum amount of stack (or heap, if --disable-stack-for-recursion is specified) that is used. A second limit controls this; it defaults to the value that is set for --with-match-limit, which imposes no additional constraints. However, you can set a lower limit by adding, for example,


--with-match-limit-recursion=10000

to the configure command. This value can also be overridden at run time.

CREATING CHARACTER TABLES AT BUILD TIME

PCRE uses fixed tables for processing characters whose code values are less than 256. By default, PCRE is built with a set of tables that are distributed in the file pcre_chartables.c.dist. These tables are for ASCII codes only. If you add


--enable-rebuild-chartables

to the configure command, the distributed tables are no longer used. Instead, a program called dftables is compiled and run. This outputs the source for new set of tables, created in the default locale of your C run-time system. (This method of replacing the tables does not work if you are cross compiling, because dftables is run on the local host. If you need to create alternative tables when cross compiling, you will have to do so "by hand".)

USING EBCDIC CODE

PCRE assumes by default that it will run in an environment where the character code is ASCII (or Unicode, which is a superset of ASCII). This is the case for most computer operating systems. PCRE can, however, be compiled to run in an EBCDIC environment by adding


--enable-ebcdic

to the configure command. This setting implies --enable-rebuild-chartables. You should only use it if you know that you are in an EBCDIC environment (for example, an IBM mainframe operating system). The --enable-ebcdic option is incompatible with --enable-utf.

The EBCDIC character that corresponds to an ASCII LF is assumed to have the value 0x15 by default. However, in some EBCDIC environments, 0x25 is used. In such an environment you should use


--enable-ebcdic-nl25

as well as, or instead of, --enable-ebcdic. The EBCDIC character for CR has the same value as in ASCII, namely, 0x0d. Whichever of 0x15 and 0x25 is not chosen as LF is made to correspond to the Unicode NEL character (which, in Unicode, is 0x85).

The options that select newline behaviour, such as --enable-newline-is-cr, and equivalent run-time options, refer to these character values in an EBCDIC environment.

PCREGREP OPTIONS FOR COMPRESSED FILE SUPPORT

By default, pcregrep reads all files as plain text. You can build it so that it recognizes files whose names end in .gz or .bz2, and reads them with libz or libbz2, respectively, by adding one or both of


--enable-pcregrep-libz
--enable-pcregrep-libbz2

to the configure command. These options naturally require that the relevant libraries are installed on your system. Configuration will fail if they are not.

PCREGREP BUFFER SIZE

pcregrep uses an internal buffer to hold a "window" on the file it is scanning, in order to be able to output "before" and "after" lines when it finds a match. The size of the buffer is controlled by a parameter whose default value is 20K. The buffer itself is three times this size, but because of the way it is used for holding "before" lines, the longest line that is guaranteed to be processable is the parameter size. You can change the default parameter value by adding, for example,


--with-pcregrep-bufsize=50K

to the configure command. The caller of pcregrep can, however, override this value by specifying a run-time option.

PCRETEST OPTION FOR LIBREADLINE SUPPORT

If you add


--enable-pcretest-libreadline

to the configure command, pcretest is linked with the libreadline library, and when its input is from a terminal, it reads it using the readline() function. This provides line-editing and history facilities. Note that libreadline is GPL-licensed, so if you distribute a binary of pcretest linked in this way, there may be licensing issues.

Setting this option causes the -lreadline option to be added to the pcretest build. In many operating environments with a sytem-installed libreadline this is sufficient. NAME

pcrebuild - instructions for building PCRE

BUILDING PCRE

This document provides instructions for building PCRE. It is intended for users who need to build PCRE from source code, for example, to enable or disable certain features, or to run PCRE on an unusual platform. Users who simply want to install PCRE on a common platform should use their operating system's package manager.

The standard procedure for building PCRE is:

  1. Download the source code tarball from the PCRE website (https://www.pcre.org/).

  2. Extract the tarball, for example:


    tar -xvzf pcre-X.Y.tar.gz

    where X.Y is the version number.

  3. Change to the source directory:


    cd pcre-X.Y

  4. Configure the build. This step checks your system and prepares the Makefiles. The simplest way is to run:


    ./configure

    This will create a Makefile tailored to your system. You can use various options to control the build process. See the PCRE BUILD-TIME OPTIONS section below for details.

  5. Compile the library:


    make

  6. Optionally, run the test suite to verify the build:


    make check

  7. Install the library, headers, and documentation (requires root privileges):


    make install

PCRE BUILD-TIME OPTIONS

The configure script accepts various options to customize the build. You can see a full list by running ./configure --help.

Some of the most common and important options are described below.

BUILDING 8-BIT, 16-BIT AND 32-BIT LIBRARIES

By default, only the 8-bit library is built. You can enable the 16-bit and 32-bit libraries using the following options:


--enable-pcre16


--enable-pcre32

You can build all three libraries by using


--enable-build-all

The 16-bit and 32-bit libraries require the corresponding C types (uint16_t and uint32_t) to be available. These are usually provided by <stdint.h>, which is part of the C99 standard.

BUILDING SHARED AND STATIC LIBRARIES

By default, both shared and static libraries are built. You can disable the building of shared libraries with


--disable-shared

and disable the building of static libraries with


--disable-static

C++ SUPPORT

PCRE includes C++ wrapper classes. To build these, you need a C++ compiler and the --enable-cpp option must be passed to configure.

UTF-8, UTF-16 AND UTF-32 SUPPORT

Support for UTF-8 (Unicode) strings is enabled by default for the 8-bit library if the build system detects that the necessary C99 support is available. Support for UTF-16 and UTF-32 is enabled if you build the 16-bit and 32-bit libraries respectively.

You can disable Unicode support using


--disable-unicode-properties

and re-enable it with


--enable-unicode-properties

Note that disabling Unicode support means that Unicode properties (like \p{L}) will not be recognized, and UTF-8 strings will be treated as sequences of bytes. However, the internal representation of Unicode characters (UTF-8, UTF-16, UTF-32) is still handled correctly when the relevant library is built.

UNICODE CHARACTER PROPERTY SUPPORT

The support for Unicode character properties is enabled by default when Unicode support is enabled. You can disable it using


--disable-unicode-properties

This option only affects the recognition of properties like \p{L} and \P{L}. It does not disable the handling of UTF-8, UTF-16, or UTF-32 strings.

JUST-IN-TIME COMPILER SUPPORT

PCRE includes an optional just-in-time (JIT) compiler that can speed up regex matching. To enable it, use the following option:


--enable-jit

The JIT compiler requires appropriate CPU support and may not be available on all systems. If the JIT compiler is enabled but cannot be built, the build will fail.

CODE VALUE OF NEWLINE

The code value of the newline character can be set using the environment variable NEWLINE before running configure. For example:


NEWLINE=$'\r\n' ./configure

This sets the newline character to CR+LF (carriage return followed by line feed). The default is LF (line feed).

WHAT \R MATCHES

The sequence \R in a PCRE pattern matches a universal newline character. By default, this means LF (0x0A), CR (0x0D), CRLF (0x0D0A), and the two characters NEL (U+0085) and LSEP (U+2028). The newline definition can be modified at build time using the NEWLINE environment variable (see previous section).

If you want \R to match only LF and CRLF, you can use the option


--disable-universal-newlines

If you want \R to match only LF, you can use the option


--enable-newline-is-lf

POSIX MALLOC USAGE

If PCRE is to be used with functions that conform to the POSIX standard for regular expressions, it may be necessary to use the system's malloc() implementation. This is enabled by default. To disable it, use


--disable-posix-malloc

HANDLING VERY LARGE PATTERNS

PCRE's pattern compiler can be made safer against denial-of-service attacks from very large patterns by using the option


--enable-large-code-size

This increases the amount of memory that can be used by the compiler, but may lead to slightly slower compilation times.

AVOIDING EXCESSIVE STACK USAGE

The recursive nature of the matching algorithm can lead to excessive stack usage when matching certain complex patterns. To mitigate this, you can use the option


--enable-recursion-guard

This adds a check to limit the depth of recursion, preventing stack overflows. However, it may slightly reduce matching performance.

LIMITING PCRE RESOURCE USAGE

To prevent denial-of-service attacks that involve extremely complex or long-running regular expression matches, PCRE provides mechanisms to limit resource usage. These limits can be controlled at runtime using functions like pcre_set_recursion_limit() and pcre_set_callout_limit(). However, you can also enforce limits at compile time.

The maximum recursion depth can be limited at compile time using the option:


--with-recursion-limit=N

where N is the maximum recursion depth. The default is 10 million.

The maximum number of callouts can be limited at compile time using the option:


--with-callout-limit=N

where N is the maximum number of callouts. The default is 10 million.

CREATING CHARACTER TABLES AT BUILD TIME

PCRE uses tables to define character properties (e.g., what is a letter, what is a digit). These tables are usually generated at build time. If you need to use pre-generated tables (e.g., if you are cross-compiling), you can use the options:


--disable-rebuild

and provide the tables manually. This is an advanced feature and usually not needed.

USING EBCDIC CODE

If you are building PCRE on an EBCDIC system (e.g., some IBM mainframes), you should use the option


--enable-ebcdic

This ensures that character constants and comparisons are handled correctly for EBCDIC encoding.

PCREGREP OPTIONS FOR COMPRESSED FILE SUPPORT

The pcregrep utility can optionally support compressed files (gzip, bzip2, xz). To enable this, you need to have the corresponding libraries installed (zlib, libbz2, liblzma). The options are:


--enable-compressed-file-support

This option enables support for all supported compression formats if the necessary libraries are found. You can also enable/disable specific formats:


--enable-pcregrep-zlib


--enable-pcregrep-bz2


--enable-pcregrep-lzma

PCREGREP BUFFER SIZE

The default buffer size used by pcregrep for reading files can be changed at build time using the option:


--with-pcregrep-bufsize=N

where N is the buffer size in bytes. The default is 8192.

PCRETEST OPTION FOR LIBREADLINE SUPPORT

The pcretest utility can optionally use the readline library for command-line editing and history. To enable this, you need to have the readline library installed. The option is:


--enable-readline

If your environment has not been set up so that an appropriate library is automatically included, you may need to add something like


LIBS="-lreadline -lncurses"

immediately before the configure command.

DEBUGGING WITH VALGRIND SUPPORT

By adding the


--enable-valgrind

option to to the configure command, PCRE will use valgrind annotations to mark certain memory regions as unaddressable. This allows it to detect invalid memory accesses, and is mostly useful for debugging PCRE itself.

CODE COVERAGE REPORTING

If your C compiler is gcc, you can build a version of PCRE that can generate a code coverage report for its test suite. To enable this, you must install lcov version 1.6 or above. Then specify


--enable-coverage

to the configure command and build PCRE in the usual way.

Note that using ccache (a caching C compiler) is incompatible with code coverage reporting. If you have configured ccache to run automatically on your system, you must set the environment variable


CCACHE_DISABLE=1

before running make to build PCRE, so that ccache is not used.

When --enable-coverage is used, the following addition targets are added to the Makefile:


make coverage

This creates a fresh coverage report for the PCRE test suite. It is equivalent to running "make coverage-reset", "make coverage-baseline", "make check", and then "make coverage-report".


make coverage-reset

This zeroes the coverage counters, but does nothing else.


make coverage-baseline

This captures baseline coverage information.


make coverage-report

This creates the coverage report.


make coverage-clean-report

This removes the generated coverage report without cleaning the coverage data itself.


make coverage-clean-data

This removes the captured coverage data without removing the coverage files created at compile time (*.gcno).


make coverage-clean

This cleans all coverage data including the generated coverage report. For more information about code coverage, see the gcov and lcov documentation.
