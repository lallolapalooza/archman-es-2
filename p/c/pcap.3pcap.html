NOMBRE

pcap - Librería de captura de paquetes

SINOPSIS

#include <pcap/pcap.h>

DESCRIPCIÓN

La librería de captura de paquetes proporciona una interfaz de alto nivel a los sistemas de captura de paquetes. Todos los paquetes de la red, incluso aquellos destinados a otros hosts, son accesibles a través de este mecanismo. También soporta guardar los paquetes capturados en un "savefile", y leer paquetes desde un "savefile".

Inicialización

pcap_init() inicializa la librería. Toma un argumento que proporciona opciones; actualmente, las opciones son:

PCAP_CHAR_ENC_LOCAL
Trata todas las cadenas suministradas como argumentos, y devuelve todas las cadenas al llamante, como si estuvieran en la codificación de caracteres local.
PCAP_CHAR_ENC_UTF_8
Trata todas las cadenas suministradas como argumentos, y devuelve todas las cadenas al llamante, como si estuvieran en UTF-8.

En sistemas tipo UNIX, se asume que la codificación de caracteres local es UTF-8, por lo que no se realizan transformaciones de codificación de caracteres.

En Windows, la codificación de caracteres local es la página de códigos ANSI local.

Si se llama a pcap_init(), la rutina obsoleta pcap_lookupdev() siempre falla, por lo que no debe usarse y, en Windows, pcap_create() no intenta manejar cadenas UTF-16LE.

Si no se llama a pcap_init(), las cadenas se tratan como si estuvieran en la página de códigos ANSI local en Windows, pcap_lookupdev() tendrá éxito si hay un dispositivo en el que capturar, y pcap_create() intenta comprobar si la cadena pasada como argumento es una cadena UTF-16LE - tenga en cuenta que este intento no es seguro, ya que puede salirse del final de la cadena - para manejar pcap_lookupdev() devolviendo una cadena UTF-16LE. Los programas que no llaman a pcap_init() deben, en Windows, llamar a pcap_wsockinit() para inicializar Winsock; esto no es necesario si se llama a pcap_init(), ya que pcap_init() inicializará Winsock por sí mismo en Windows.

Abrir un manejador de captura para leer

Para abrir un manejador para una captura en vivo, dado el nombre de la red u otra interfaz en la que se debe realizar la captura, llame a pcap_create(), establezca las opciones apropiadas en el manejador y luego actívelo con pcap_activate(). Si pcap_activate() falla, el manejador debe cerrarse con pcap_close().

Para obtener una lista de dispositivos que se pueden abrir para una captura en vivo, llame a pcap_findalldevs(); para liberar la lista devuelta por pcap_findalldevs(), llame a pcap_freealldevs(). pcap_lookupdev() devolverá el primer dispositivo de esa lista que no sea una interfaz de red "loopback".

Para abrir un manejador para un "savefile" desde el que leer paquetes, dado el nombre de ruta del "savefile", llame a pcap_open_offline(); para configurar un manejador para un "savefile", dado un FILE * que se refiera a un archivo ya abierto para lectura, llame a pcap_fopen_offline().

Para obtener un pcap_t "falso" para usar en rutinas que requieren un pcap_t como argumento, como las rutinas para abrir un "savefile" para escribir y compilar una expresión de filtro, llame a pcap_open_dead().

pcap_create(), pcap_open_offline(), pcap_fopen_offline() y pcap_open_dead() devuelven un puntero a un pcap_t, que es el manejador utilizado para leer paquetes del flujo de captura o del "savefile", y para obtener información sobre el flujo de captura o el "savefile". Para cerrar un manejador, use pcap_close().

Las opciones que se pueden establecer en un manejador de captura incluyen:

longitud de instantánea
Si, al capturar, se captura el contenido completo del paquete, eso requiere más tiempo de CPU para copiar el paquete a su aplicación, más ancho de banda de disco y posiblemente de red para escribir los datos del paquete en un archivo, y más espacio en disco para guardar el paquete. Si no necesita el contenido completo del paquete, por ejemplo, si solo está interesado en las cabeceras TCP de los paquetes, puede establecer la "longitud de instantánea" para la captura a un valor apropiado. Si la longitud de instantánea se establece en snaplen, y snaplen es menor que el tamaño de un paquete que se captura, solo los primeros snaplen bytes de ese paquete se capturarán y proporcionarán como datos del paquete.
Una longitud de instantánea de 65535 debería ser suficiente, en la mayoría de las redes, si no en todas, para capturar todos los datos disponibles del paquete.
La longitud de instantánea se establece con pcap_set_snaplen().
modo promiscuo
En LANs de difusión como Ethernet, si la red no está conmutada, o si el adaptador está conectado a un "puerto espejo" en un switch al que se envían todos los paquetes que pasan por el switch, un adaptador de red recibe todos los paquetes de la LAN, incluidos los paquetes unicast o multicast no enviados a una dirección de red que el adaptador no está configurado para reconocer.
Normalmente, el adaptador descartará esos paquetes; sin embargo, muchos adaptadores de red admiten el "modo promiscuo", que es un modo en el que todos los paquetes, incluso si no se envían a una dirección que el adaptador reconoce, se proporcionan al host. Esto es útil para capturar pasivamente el tráfico entre dos o más hosts para su análisis.
Tenga en cuenta que incluso si una aplicación no establece el modo promiscuo, el adaptador podría estar en modo promiscuo por alguna otra razón.
Por ahora, esto no funciona en el dispositivo "any"; si se proporciona un argumento de "any" o NULL, la configuración del modo promiscuo se ignora.
El modo promiscuo se establece con pcap_set_promisc().
modo monitor
En las redes LAN inalámbricas IEEE 802.11, incluso si un adaptador está en modo promiscuo, solo proporcionará al host los fotogramas para la red con la que está asociado. También podría proporcionar solo fotogramas de datos, no fotogramas de gestión o control, y podría no proporcionar la cabecera 802.11 o una pseudo-cabecera de información de radio para esos fotogramas.
En "modo monitor", a veces también llamado "modo rfmon" (por "Radio Frequency MONitor"), el adaptador proporcionará todos los fotogramas que reciba, con cabeceras 802.11, y podría proporcionar una pseudo-cabecera con información de radio sobre el fotograma también.
Tenga en cuenta que en modo monitor, el adaptador puede desasociarse de la red con la que está asociado, de modo que no podrá usar ninguna red inalámbrica con ese adaptador. Esto podría impedir el acceso a archivos en un servidor de red, o la resolución de nombres de host o direcciones de red, si está capturando en modo monitor y no está conectado a otra red con otro adaptador.
El modo monitor se establece con pcap_set_rfmon(), y pcap_can_set_rfmon() se puede usar para determinar si un adaptador puede configurarse en modo monitor.
tiempo de espera del búfer de paquetes
Si, al capturar, los paquetes se entregan tan pronto como llegan, la aplicación que captura los paquetes se despertará para cada paquete a medida que llega, y podría tener que hacer una o más llamadas al sistema operativo para obtener cada paquete.
Si, en cambio, los paquetes no se entregan tan pronto como llegan, sino que se entregan después de un breve retraso (llamado "tiempo de espera del búfer de paquetes"), se pueden acumular más de un paquete antes de que se entreguen los paquetes, de modo que se realizaría una única notificación para múltiples paquetes, y cada conjunto de llamadas realizadas al sistema operativo proporcionaría múltiples paquetes, en lugar de un único paquete. Esto reduce la sobrecarga de CPU por paquete si los paquetes llegan a una alta velocidad, aumentando el número de paquetes por segundo que se pueden capturar.

packet buffer timeout
The packet buffer timeout is the maximum amount of time that you are willing to wait for packets to arrive. If the timeout expires before enough packets have arrived to fill the packet buffer, the packets that have arrived are returned to the application. If the timeout expires and no packets have arrived, an empty list of packets is returned. A timeout of 0 means that you are willing to wait indefinitely, until enough packets have arrived to fill the packet buffer. A timeout of -1 means that you are willing to wait indefinitely, until enough packets have arrived to fill the packet buffer, because the timeout is invalid.
Not all platforms support a packet buffer timeout; on platforms that don't, the packet buffer timeout is ignored. A zero value for the timeout, on platforms that support a packet buffer timeout, will cause a read to wait forever to allow enough packets to arrive, with no timeout. A negative value is invalid; the result of setting the timeout to a negative value is unpredictable.
NOTE: the packet buffer timeout cannot be used to cause calls that read packets to return within a limited period of time, because, on some platforms, the packet buffer timeout isn't supported, and, on other platforms, the timer doesn't start until at least one packet arrives. This means that the packet buffer timeout should NOT be used, for example, in an interactive application to allow the packet capture loop to ``poll'' for user input periodically, as there's no guarantee that a call reading packets will return after the timeout expires even if no packets have arrived.
The packet buffer timeout is set with pcap_set_timeout().
immediate mode
In immediate mode, packets are always delivered as soon as they arrive, with no buffering. Immediate mode is set with pcap_set_immediate_mode().
buffer size
Packets that arrive for a capture are stored in a buffer, so that they do not have to be read by the application as soon as they arrive. On some platforms, the buffer's size can be set; a size that's too small could mean that, if too many packets are being captured and the snapshot length doesn't limit the amount of data that's buffered, packets could be dropped if the buffer fills up before the application can read packets from it, while a size that's too large could use more non-pageable operating system memory than is necessary to prevent packets from being dropped.
The buffer size is set with pcap_set_buffer_size().
timestamp type
On some platforms, the time stamp given to packets on live captures can come from different sources that can have different resolutions or that can have different relationships to the time values for the current time supplied by routines on the native operating system. See pcap-tstamp(7) for a list of time stamp types.
The time stamp type is set with pcap_set_tstamp_type().

Reading packets from a network interface may require that you have special privileges:

Under SunOS 3.x or 4.x with NIT or BPF:
You must have read access to /dev/nit or /dev/bpf*.
Under Solaris with DLPI:
You must have read/write access to the network pseudo device, e.g. /dev/le. On at least some versions of Solaris, however, this is not sufficient to allow tcpdump to capture in promiscuous mode; on those versions of Solaris, you must be root, or the application capturing packets must be installed setuid to root, in order to capture in promiscuous mode. Note that, on many (perhaps all) interfaces, if you don't capture in promiscuous mode, you will not see any outgoing packets, so a capture not done in promiscuous mode may not be very useful.
In newer versions of Solaris, you must have been given the net_rawaccess privilege; this is both necessary and sufficient to give you access to the network pseudo-device - there is no need to change the privileges on that device. A user can be given that privilege by, for example, adding that privilege to the user's defaultpriv key with the usermod(8) command.
Under HP-UX with DLPI:
You must be root or the application capturing packets must be installed setuid to root.
Under IRIX with snoop:
You must be root or the application capturing packets must be installed setuid to root.
Under Linux:
You must be root or the application capturing packets must be installed setuid to root, unless your distribution has a kernel that supports capability bits such as CAP_NET_RAW and code to allow those capability bits to be given to particular accounts and to cause those bits to be set on a user's initial processes when they log in, in which case you must have CAP_NET_RAW in order to capture.
Under ULTRIX and Digital UNIX/Tru64 UNIX:
Any user may capture network traffic. However, no user (not even the super-user) can capture in promiscuous mode on an interface unless the super-user has enabled promiscuous-mode operation on that interface using pfconfig(8), and no user (not even the super-user) can capture unicast traffic received by or sent by the machine on an interface unless the super-user has enabled copy-all-mode operation on that interface using pfconfig, so useful packet capture on an interface probably requires that either promiscuous-mode or copy-all-mode operation, or both modes of operation, be enabled on that interface.
Under BSD (this includes macOS):
You must have read access to /dev/bpf* on systems that don't have a cloning BPF device, or to /dev/bpf on systems that do. On BSDs with a devfs (this includes macOS), this might involve more than just having somebody with super-user access setting the ownership or permissions on the BPF devices - it might involve configuring devfs to set the ownership or permissions every time the system is booted, if the system even supports that; if it doesn't support that, you might have to find some other way to make that happen at boot time.

Reading a saved packet file doesn't require special privileges.

The packets read from the handle may include a ``pseudo-header'' containing various forms of packet meta-data, and probably includes a link-layer header whose contents can differ for different network interfaces. To determine the format of the packets supplied by the handle, call pcap_datalink(); https://www.tcpdump.org/linktypes.html lists the values it returns and describes the packet formats that correspond to those values.

Do NOT assume that the packets for a given capture or ``savefile`` will have any given link-layer header type, such as DLT_EN10MB for Ethernet. For example, the "any" device on Linux will have a link-layer header type of DLT_LINUX_SLL or DLT_LINUX_SLL2 even if all devices on the system at the time the "any" device is opened have some other data link type, such as DLT_EN10MB for Ethernet.

To obtain the FILE * corresponding to a pcap_t opened for a ``savefile'', call pcap_file().

Lectura de paquetes

Los paquetes se leen con pcap_dispatch() o pcap_loop(), que procesan uno o más paquetes, llamando a una rutina de retrollamada para cada paquete, o con pcap_next() o pcap_next_ex(), que devuelven el siguiente paquete. La retrollamada para pcap_dispatch() y pcap_loop() recibe un puntero a una struct pcap_pkthdr, que incluye los siguientes miembros:

ts
una struct timeval que contiene la hora en que se capturó el paquete
caplen
un bpf_u_int32 que indica el número de bytes del paquete que están disponibles en la captura
len
un bpf_u_int32 que indica la longitud del paquete, en bytes (que podría ser mayor que el número de bytes disponibles en la captura, si la longitud del paquete es mayor que el número máximo de bytes a capturar).

La retrollamada también recibe un puntero const u_char a los primeros caplen bytes de datos del paquete (como se indica en la struct pcap_pkthdr mencionada anteriormente). Esto no será necesariamente el paquete completo; para capturar el paquete completo, tendrá que proporcionar un valor para snaplen en su llamada a pcap_set_snaplen() que sea lo suficientemente grande como para obtener todos los datos del paquete (un valor de 65535 debería ser suficiente en la mayoría, si no en todas, las redes). Al leer desde un "archivo de captura", la longitud de la instantánea especificada cuando se realizó la captura limitará la cantidad de datos del paquete disponibles.

pcap_next() recibe un argumento que apunta a una estructura struct pcap_pkthdr y la completa con los valores de marca de tiempo y longitud del paquete. Devuelve un const u_char * a los primeros bytes caplen del paquete en caso de éxito, y NULL en caso de error.

pcap_next_ex() recibe dos argumentos de puntero, uno de los cuales apunta a un struct pcap_pkthdr * y el otro apunta a un const u_char *. Establece el primer puntero para que apunte a una estructura struct pcap_pkthdr con los valores de marca de tiempo y longitud del paquete, y establece el segundo puntero para que apunte a los primeros caplen bytes del paquete.

Para forzar la terminación del bucle en pcap_dispatch() o pcap_loop(), llame a pcap_breakloop().

Por defecto, al leer paquetes de una interfaz abierta para captura en vivo, pcap_dispatch(), pcap_next() y pcap_next_ex() bloquearán, si no hay paquetes disponibles para leer, esperando a que los paquetes estén disponibles. En algunas, pero *no en todas*, las plataformas, si se especificó un tiempo de espera del búfer de paquetes, la espera terminará después de que expire el tiempo de espera del búfer de paquetes; las aplicaciones deben estar preparadas para esto, ya que ocurre en algunas plataformas, pero no deben depender de ello, ya que no ocurre en otras plataformas. Tenga en cuenta que la espera puede terminar o no, incluso si no hay paquetes disponibles; las aplicaciones deben estar preparadas para que esto suceda, pero no deben depender de que suceda.

Un manejador puede ponerse en "modo no bloqueante", de modo que esas rutinas, en lugar de bloquear, devuelvan una indicación de que no hay paquetes disponibles para leer. Llame a pcap_setnonblock() para poner un manejador en modo no bloqueante o sacarlo del modo no bloqueante; llame a pcap_getnonblock() para determinar si un manejador está en modo no bloqueante. Tenga en cuenta que el modo no bloqueante no funciona correctamente en Mac OS X 10.6.

El modo no bloqueante a menudo se combina con rutinas como select(2) o poll(2) u otras rutinas que ofrece una plataforma para esperar a que cualquiera de un conjunto de descriptores esté listo para leer. Para obtener, para un manejador, un descriptor que se pueda usar en esas rutinas, llame a pcap_get_selectable_fd(). Si la rutina indica que hay datos disponibles para leer en el descriptor, se debe intentar leer del dispositivo.

No todos los manejadores tienen un descriptor disponible; pcap_get_selectable_fd() devolverá -1 si no hay un descriptor disponible. Si no hay un descriptor disponible, esto puede deberse a que el dispositivo debe ser consultado periódicamente en busca de paquetes; en ese caso, pcap_get_required_select_timeout() devolverá un puntero a una struct timeval cuyo valor se puede usar como tiempo de espera en esas rutinas. Cuando la rutina devuelva, se debe intentar leer paquetes del dispositivo. Si pcap_get_required_select_timeout() devuelve NULL, no hay un tiempo de espera disponible, y esas rutinas no se pueden usar con el dispositivo.

Además, por diversas razones, una o más de esas rutinas no funcionarán correctamente con el descriptor; la documentación para pcap_get_selectable_fd() proporciona detalles. Tenga en cuenta que, al igual que un intento de leer paquetes de un pcap_t puede no devolver ningún paquete si expira el tiempo de espera del búfer de paquetes, una llamada a select(), poll() u otra llamada similar puede, si expira el tiempo de espera del búfer de paquetes, indicar que un descriptor está listo para leer incluso si no hay paquetes disponibles para leer.

Filtros

Para obtener solo ciertos paquetes al leerlos, se puede establecer un filtro en un manejador. Para una captura en vivo, el filtrado se realizará en modo kernel, si es posible, para evitar copiar paquetes ``no interesantes'' del kernel al espacio de usuario.

Un filtro puede especificarse como una cadena de texto; la sintaxis y semántica de la cadena se describen en pcap-filter(7). Una cadena de filtro se compila en un programa en un lenguaje de pseudo-máquina mediante pcap_compile() y el programa resultante se puede establecer como filtro para un manejador con pcap_setfilter(). El resultado de pcap_compile() se puede liberar con una llamada a pcap_freecode(). pcap_compile() puede requerir una máscara de red para ciertas expresiones en la cadena de filtro; pcap_lookupnet() se puede utilizar para encontrar la dirección de red y la máscara de red para un dispositivo de captura dado.

Un filtro compilado también se puede aplicar directamente a un paquete que se ha leído usando pcap_offline_filter().

Rutinas
pcap_compile(3PCAP)
compilar expresión de filtro a un programa de código de pseudo-máquina
pcap_freecode(3PCAP)
liberar un programa de filtro
pcap_setfilter(3PCAP)
establecer filtro para un pcap_t
pcap_lookupnet(3PCAP)
obtener dirección de red y máscara de red para un dispositivo de captura
pcap_offline_filter(3PCAP)
aplicar un programa de filtro a un paquete

Paquetes entrantes y salientes

Por defecto, libpcap intentará capturar tanto los paquetes enviados por la máquina como los recibidos por la máquina. Para limitarlo a capturar solo los paquetes recibidos por la máquina o, si es posible, solo los paquetes enviados por la máquina, llame a pcap_setdirection().

Rutinas

Abrir un manejador para escribir paquetes capturados

Para abrir un ``archivo de guardado'' al que escribir paquetes, dado la ruta del ``archivo de guardado'', llame a pcap_dump_open(). Para abrir un ``archivo de guardado'' al que escribir paquetes, dado la ruta del ``archivo de guardado'', llame a pcap_dump_open(); para configurar un manejador para un ``archivo de guardado'', dado un FILE * que refiera a un archivo ya abierto para escritura, llame a pcap_dump_fopen(). Cada uno devuelve punteros a un pcap_dumper_t, que es el manejador utilizado para escribir paquetes en el ``archivo de guardado''. Si tiene éxito, habrá creado el archivo si no existe y truncado el archivo si ya existe. Para cerrar un pcap_dumper_t, llame a pcap_dump_close().

cerrar un pcap_dumper_t
pcap_dump_file(3PCAP)
obtener el FILE * para un pcap_dumper_t abierto para un ``archivo de guardado''

Escribir paquetes

Para escribir un paquete en un pcap_dumper_t, llame a pcap_dump(). Los paquetes escritos con pcap_dump() pueden ser almacenados en búfer, en lugar de ser escritos inmediatamente en el ``archivo de guardado''. Cerrar el pcap_dumper_t hará que todos los paquetes almacenados en búfer pero aún no escritos se escriban en el ``archivo de guardado''. Para forzar que todos los paquetes escritos al pcap_dumper_t, y que aún no se han escrito en el ``archivo de guardado'' porque están en búfer por el pcap_dumper_t, se escriban en el ``archivo de guardado'', sin cerrar el pcap_dumper_t, llame a pcap_dump_flush().

Rutinas
pcap_dump(3PCAP)
escribir paquete a un pcap_dumper_t
pcap_dump_flush(3PCAP)
vaciar paquetes en búfer escritos a un pcap_dumper_t al ``archivo de guardado''
pcap_dump_ftell(3PCAP)
obtener la posición actual del archivo para un pcap_dumper_t

COMPATIBILIDAD HACIA ATRÁS

En versiones de libpcap anteriores a la 1.0, el archivo de cabecera pcap.h no estaba en un directorio pcap en la mayoría de las plataformas; si está escribiendo una aplicación que debe funcionar en versiones de libpcap anteriores a la 1.0, incluya <pcap.h>, que incluirá <pcap/pcap.h> por usted, en lugar de incluir <pcap/pcap.h>.

pcap_create() y pcap_activate() no estaban disponibles en versiones de libpcap anteriores a la 1.0; si está escribiendo una aplicación que debe funcionar en versiones de libpcap anteriores a la 1.0, use pcap_open_live() para obtener un manejador para una captura en vivo o, si desea poder usar las capacidades adicionales que ofrece el uso de pcap_create() y pcap_activate(), use un script de autoconf(1) o algún otro script de configuración para verificar si las APIs de libpcap 1.0 están disponibles y úselas solo si lo están.
