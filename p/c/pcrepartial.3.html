NOMBRE

PCRE - expresiones regulares compatibles con Perl

COINCIDENCIA PARCIAL EN PCRE

En el uso normal de PCRE, si la cadena de sujeto que se pasa a una función de coincidencia coincide hasta donde llega, pero es demasiado corta para coincidir con el patrón completo, se devuelve PCRE_ERROR_NOMATCH. Hay circunstancias en las que podría ser útil distinguir este caso de otros casos en los que no hay coincidencia.

Considere, por ejemplo, una aplicación en la que un humano debe ingresar datos para un campo con requisitos de formato específicos. Un ejemplo podría ser una fecha en el formato ddmmm aa, definida por este patrón:


^\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d$

Si la aplicación ve las pulsaciones de teclas del usuario una por una y puede verificar que lo que se ha escrito hasta ahora es potencialmente válido, puede generar un error tan pronto como se cometa un error, haciendo un pitido y no reflejando el carácter que se ha escrito, por ejemplo. Esta retroalimentación inmediata es probable que sea una mejor interfaz de usuario que una verificación que se retrasa hasta que se ingresa la cadena completa. La coincidencia parcial también puede ser útil cuando la cadena de sujeto es muy larga y no está disponible por completo a la vez.

PCRE admite la coincidencia parcial mediante las opciones PCRE_PARTIAL_SOFT y PCRE_PARTIAL_HARD, que se pueden establecer al llamar a cualquiera de las funciones de coincidencia. Por compatibilidad con versiones anteriores, PCRE_PARTIAL es sinónimo de PCRE_PARTIAL_SOFT. La diferencia esencial entre las dos opciones es si se prefiere o no una coincidencia parcial a una coincidencia completa alternativa, aunque los detalles difieren entre los dos tipos de funciones de coincidencia. Si se establecen ambas opciones, PCRE_PARTIAL_HARD tiene precedencia.

Si desea utilizar la coincidencia parcial con código optimizado justo a tiempo, debe llamar a pcre_study(), pcre16_study() o pcre32_study() con una o ambas de estas opciones:


PCRE_STUDY_JIT_PARTIAL_SOFT_COMPILE
PCRE_STUDY_JIT_PARTIAL_HARD_COMPILE

PCRE_STUDY_JIT_COMPILE también debe establecerse si va a ejecutar coincidencias no parciales en el mismo patrón. Si no se ha establecido el modo de estudio JIT apropiado para una coincidencia, se utiliza el código de coincidencia interpretativo.

Establecer una opción de coincidencia parcial deshabilita dos de las optimizaciones estándar de PCRE. PCRE recuerda la última unidad de datos literal en un patrón y abandona la coincidencia inmediatamente si no está presente en la cadena de sujeto. Esta optimización no se puede utilizar para una cadena de sujeto que podría coincidir solo parcialmente. Si se estudió el patrón, PCRE conoce la longitud mínima de una cadena coincidente y no se molesta en ejecutar la función de coincidencia en cadenas más cortas. Esta optimización también se deshabilita para la coincidencia parcial.

COINCIDENCIA PARCIAL USANDO pcre_exec() O pcre[16|32]_exec()

Una coincidencia parcial ocurre durante una llamada a pcre_exec() o pcre[16|32]_exec() cuando se llega al final de la cadena de sujeto con éxito, pero la coincidencia no puede continuar porque se necesitan más caracteres. Sin embargo, se debe haber inspeccionado al menos un carácter en el sujeto. Este carácter no necesita formar parte de la cadena coincidente final; las aserciones de retroceso y la secuencia de escape \K proporcionan formas de inspeccionar caracteres antes del inicio de una subcadena coincidente. El requisito de inspeccionar al menos un carácter existe porque una cadena vacía siempre puede coincidir; sin tal restricción, siempre habría una coincidencia parcial de una cadena vacía al final del sujeto.

Si hay al menos dos ranuras en el vector de desfases cuando se devuelve una coincidencia parcial, la primera ranura se establece en el desfase del carácter más temprano que se inspeccionó. Para mayor comodidad, el segundo desfase apunta al final del sujeto para que se pueda identificar fácilmente una subcadena. Si hay al menos tres ranuras en el vector de desfases, la tercera ranura se establece en el desfase del carácter donde comenzó la coincidencia.

Para la mayoría de los patrones, el contenido de la primera y la tercera ranura serán los mismos. Sin embargo, para patrones que contienen aserciones de retroceso, o que comienzan con \b o \B, los caracteres antes del que comenzó la coincidencia pueden haber sido inspeccionados mientras se llevaba a cabo la coincidencia. Por ejemplo, considere este patrón:


/(?<=abc)123/

Este patrón coincide con "123", pero solo si está precedido por "abc". Si la cadena de sujeto es "xyzabc12", los dos primeros desfases después de una coincidencia parcial son para la subcadena "abc12", porque todos estos caracteres fueron inspeccionados. Sin embargo, el tercer desfase se establece en 6, porque ese es el desfase donde comenzó la coincidencia.

Lo que sucede cuando se identifica una coincidencia parcial depende de cuál de las dos opciones de coincidencia parcial esté establecida.

PCRE_PARTIAL_SOFT CON pcre_exec() O pcre[16|32]_exec()

Si se establece PCRE_PARTIAL_SOFT cuando pcre_exec() o pcre[16|32]_exec() identifican una coincidencia parcial, la coincidencia parcial se recuerda, pero la coincidencia continúa de forma normal y se prueban otras alternativas en el patrón. Si no se encuentra ninguna coincidencia completa, se devuelve PCRE_ERROR_PARTIAL en lugar de PCRE_ERROR_NOMATCH.

Esta opción es "suave" porque prefiere una coincidencia completa a una coincidencia parcial. Todos los diversos elementos coincidentes en un patrón se comportan como si la cadena de sujeto fuera potencialmente completa. Por ejemplo, \z, \Z y $ coinciden al final del sujeto, como de costumbre, y para \b y \B, el final del sujeto se trata como un no alfanumérico.

Si hay más de una coincidencia parcial, la primera que se encontró proporciona los datos que se devuelven. Considere este patrón:


/123\w+X|dogY/

Si se compara con la cadena de sujeto "abc123dog", ambas alternativas fallan al coincidir, pero se llega al final del sujeto durante la coincidencia, por lo que se devuelve PCRE_ERROR_PARTIAL. Los desfases se establecen en 3 y 9, identificando "123dog" como la primera coincidencia parcial que se encontró. (En este ejemplo, hay dos coincidencias parciales, porque "dog" por sí solo coincide parcialmente con la segunda alternativa).

PCRE_PARTIAL_HARD CON pcre_exec() O pcre[16|32]_exec()

Si se establece PCRE_PARTIAL_HARD para pcre_exec() o pcre[16|32]_exec(), se devuelve PCRE_ERROR_PARTIAL tan pronto como se encuentra una coincidencia parcial, sin continuar buscando posibles coincidencias completas. Esta opción es "dura" porque prefiere una coincidencia parcial anterior a una coincidencia completa posterior. Por esta razón, se hace la suposición de que el final de la cadena de sujeto suministrada puede no ser el final real de los datos disponibles, y por lo tanto, si se encuentran \z, \Z, \b, \B o $ al final del sujeto, el resultado es PCRE_ERROR_PARTIAL, siempre que se haya inspeccionado al menos un carácter en el sujeto.

Establecer PCRE_PARTIAL_HARD también afecta la forma en que se verifican las cadenas de sujeto UTF-8 y UTF-16 para ver si son válidas. Normalmente, una secuencia inválida provoca el error PCRE_ERROR_BADUTF8 o PCRE_ERROR_BADUTF16. Sin embargo, en el caso especial de un carácter truncado al final del sujeto, se devuelve PCRE_ERROR_SHORTUTF8 o PCRE_ERROR_SHORTUTF16 cuando se establece PCRE_PARTIAL_HARD.

Comparando la coincidencia parcial dura y suave

La diferencia entre las dos opciones de coincidencia parcial se puede ilustrar con un patrón como:


/dog(sbody)?/

Esto coincide con "dog" o "dogsbody", de forma codiciosa (es decir, prefiere la cadena más larga si es posible). Si se compara con la cadena "dog" con PCRE_PARTIAL_SOFT, produce una coincidencia completa para "dog". Sin embargo, si se establece PCRE_PARTIAL_HARD, el resultado es PCRE_ERROR_PARTIAL. Por otro lado, si el patrón se vuelve no codicioso, el resultado es diferente:


/dog(sbody)??/

En este caso, el resultado es siempre una coincidencia completa porque esa se encuentra primero, y la coincidencia nunca continúa después de encontrar una coincidencia completa. Podría ser más fácil seguir esta explicación pensando en los dos patrones de esta manera:


/dog(sbody)?/ es lo mismo que /dogsbody|dog/
/dog(sbody)??/ es lo mismo que /dog|dogsbody/

COINCIDENCIA PARCIAL USANDO pcre_dfa_exec() O pcre[16|32]_dfa_exec()

Las funciones DFA avanzan por la cadena de sujeto carácter por carácter, sin retroceso, buscando todas las coincidencias posibles simultáneamente. Si se alcanza el final del sujeto antes del final del patrón, existe la posibilidad de una coincidencia parcial, siempre que se hayan inspeccionado al menos un carácter.

Cuando se establece PCRE_PARTIAL_SOFT, PCRE_ERROR_PARTIAL se devuelve solo si no ha habido coincidencias completas. De lo contrario, se devuelven las coincidencias completas. Sin embargo, si se establece PCRE_PARTIAL_HARD, una coincidencia parcial tiene precedencia sobre cualquier coincidencia completa. La porción de la cadena que se inspeccionó cuando se encontró la coincidencia parcial más larga se establece como la primera cadena coincidente, siempre que haya al menos dos ranuras en el vector de desplazamientos.

Debido a que las funciones DFA siempre buscan todas las coincidencias posibles, y no hay diferencia entre la repetición codiciosa y la no codiciosa, su comportamiento es diferente al de las funciones estándar cuando se establece PCRE_PARTIAL_HARD. Considere la cadena "dog" emparejada contra el patrón no codicioso que se muestra arriba:


/dog(sbody)??/

Mientras que las funciones estándar se detienen tan pronto como encuentran la coincidencia completa para "dog", las funciones DFA también encuentran la coincidencia parcial para "dogsbody", y por lo tanto la devuelven cuando se establece PCRE_PARTIAL_HARD.

COINCIDENCIA PARCIAL Y LÍMITES DE PALABRA

Si un patrón termina con una de las secuencias \b o \B, que prueban los límites de palabra, la coincidencia parcial con PCRE_PARTIAL_SOFT puede dar resultados contra-intuitivos. Considere este patrón:


/\bcat\b/

Esto coincide con "cat", siempre que haya un límite de palabra en cada extremo. Si la cadena de sujeto es "the cat", la comparación de la "t" final con un carácter siguiente no puede ocurrir, por lo que se encuentra una coincidencia parcial. Sin embargo, la coincidencia normal continúa, y \b coincide al final del sujeto cuando el último carácter es una letra, por lo que se encuentra una coincidencia completa. El resultado, por lo tanto, *no* es PCRE_ERROR_PARTIAL. Usar PCRE_PARTIAL_HARD en este caso sí produce PCRE_ERROR_PARTIAL, porque entonces la coincidencia parcial tiene precedencia.

PATRONES ANTERIORMENTE RESTRINGIDOS

Para las versiones de PCRE anteriores a la 8.00, debido a la forma en que se implementaron ciertas optimizaciones internas en la función pcre_exec(), la opción PCRE_PARTIAL (predecesora de PCRE_PARTIAL_SOFT) no se podía usar con todos los patrones. A partir de la versión 8.00, las restricciones ya no se aplican, y se puede solicitar la coincidencia parcial para cualquier patrón.

Los elementos que anteriormente estaban restringidos eran caracteres únicos repetidos y metasecuencias repetidas. Si se establecía PCRE_PARTIAL para un patrón que no cumplía con las restricciones, pcre_exec() devolvía el código de error PCRE_ERROR_BADPARTIAL (-13). Este código de error ya no está en uso. La llamada PCRE_INFO_OKPARTIAL a pcre_fullinfo() para averiguar si un patrón compilado se puede usar para coincidencia parcial ahora siempre devuelve 1.

EJEMPLO DE COINCIDENCIA PARCIAL USANDO PCRETEST

Si la secuencia de escape \P está presente en una línea de datos de pcretest, se utiliza la opción PCRE_PARTIAL_SOFT para la coincidencia. Aquí hay una ejecución de pcretest que utiliza el ejemplo de fecha citado anteriormente:


re> /^\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d$/
data> 25jun04\P
0: 25jun04
1: jun
data> 25dec3\P
Partial match: 23dec3
data> 3ju\P
Partial match: 3ju
data> 3juj\P
No match
data> j\P
No match

La primera cadena de datos coincide completamente, por lo que pcretest muestra las subcadenas coincidentes. Las cuatro cadenas restantes no coinciden con el patrón completo, pero las dos primeras son coincidencias parciales. Se obtiene una salida similar si se utiliza la coincidencia DFA.

Si la secuencia de escape \P está presente más de una vez en una línea de datos de pcretest, la opción PCRE_PARTIAL_HARD se establece para la coincidencia.

COINCIDENCIA MULTISEGMENTO CON pcre_dfa_exec() O pcre[16|32]_dfa_exec()

Cuando se ha encontrado una coincidencia parcial utilizando una función de coincidencia DFA, es posible continuar la coincidencia proporcionando datos de sujeto adicionales y llamando nuevamente a la función con la misma expresión regular compilada, estableciendo esta vez la opción PCRE_DFA_RESTART. Debe pasar el mismo espacio de trabajo que antes, ya que aquí es donde se almacenan los detalles de la coincidencia parcial anterior. Aquí hay un ejemplo usando pcretest, utilizando la secuencia de escape \R para establecer la opción PCRE_DFA_RESTART (\D especifica el uso de la función de coincidencia DFA):


re> /^\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d$/
data> 23ja\P\D
Partial match: 23ja
data> n05\R\D
0: n05

La primera llamada tiene "23ja" como sujeto y solicita coincidencia parcial; la segunda llamada tiene "n05" como sujeto para la coincidencia continuada (reiniciada). Observe que cuando la coincidencia se completa, solo se muestra la última parte; PCRE no conserva la cadena previamente coincidida parcialmente. Depende del programa que llama hacer eso si es necesario.

Eso significa que, para un patrón sin ancla, si una coincidencia continuada falla, no es posible volver a intentarlo en un nuevo punto de inicio. Todo lo que esta instalación es capaz de hacer es continuar con el intento de coincidencia anterior. En el ejemplo anterior, si los segundos datos son "ug23", el resultado es sin coincidencia, aunque habría una coincidencia para "aug23" si toda la cadena se diera a la vez. Dependiendo de la aplicación, esto puede ser lo que desea o no. La única forma de permitir el inicio de nuevo en el siguiente carácter es conservar la parte coincidente del sujeto e intentar una nueva coincidencia completa.

Puede establecer las opciones PCRE_PARTIAL_SOFT o PCRE_PARTIAL_HARD con PCRE_DFA_RESTART para continuar la coincidencia parcial en múltiples segmentos. Esta instalación se puede utilizar para pasar cadenas de sujeto muy largas a las funciones de coincidencia DFA.

COINCIDENCIA MULTISEGMENTO CON pcre_exec() O pcre[16|32]_exec()

A partir de la versión 8.00, las funciones de coincidencia estándar también se pueden utilizar para realizar coincidencias multissegmento. A diferencia de las funciones DFA, no es posible reiniciar la coincidencia anterior con un nuevo segmento de datos. En su lugar, se deben agregar nuevos datos a la cadena de sujeto anterior y volver a ejecutar toda la coincidencia, comenzando desde el punto en que ocurrió la coincidencia parcial. Los datos anteriores pueden descartarse.

Es mejor usar PCRE_PARTIAL_HARD en esta situación, ya que no trata el final de un segmento como el final del sujeto al coincidir \z, \Z, \b, \B y $. Considere un patrón sin ancla que coincide con fechas:


re> /\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d/
data> The date is 23ja\P\P
Partial match: 23ja

En esta etapa, una aplicación podría descartar el texto que precede a "23ja", agregar texto del siguiente segmento y volver a llamar a la función de coincidencia. A diferencia de las funciones de coincidencia DFA, la cadena de coincidencia completa debe estar siempre disponible, y todo el proceso de coincidencia ocurre para cada llamada, por lo que se necesita más memoria y más tiempo de procesamiento.

Nota: Si el patrón contiene aserciones lookbehind, \K, o comienza con \b o \B, la cadena que se devuelve para una coincidencia parcial incluye caracteres que preceden al inicio de lo que se devolvería para una coincidencia completa, ya que contiene todos los caracteres que se inspeccionaron durante la coincidencia parcial.

PROBLEMAS CON LA COINCIDENCIA MULTISEGMENTO

Ciertos tipos de patrón pueden presentar problemas con la coincidencia multissegmento, independientemente de la función de coincidencia utilizada.

1. Si el patrón contiene una prueba para el inicio de una línea, necesita pasar la opción PCRE_NOTBOL cuando la cadena de sujeto de cualquier llamada comience al inicio de una línea. También existe una opción PCRE_NOTEOL, pero en la práctica, al hacer coincidencia multissegmento, debería usar PCRE_PARTIAL_HARD, que incluye el efecto de PCRE_NOTEOL.

2. Las aserciones lookbehind que ya se han cumplido se tienen en cuenta en los desplazamientos que se devuelven para una coincidencia parcial. Sin embargo, una aserción lookbehind posterior en el patrón podría requerir que se inspeccionen caracteres aún anteriores. Puede manejar este caso usando la opción PCRE_INFO_MAXLOOKBEHIND de las funciones pcre_fullinfo() o pcre[16|32]_fullinfo() para obtener la longitud del lookbehind más largo en el patrón. Esta longitud se da en caracteres, no en bytes. Si siempre conserva al menos esa cantidad de caracteres antes de la cadena parcialmente coincidente, todo debería ir bien. (Por supuesto, cerca del inicio del sujeto, puede haber menos caracteres; en ese caso, se deben conservar todos los caracteres.)

A partir de la versión 8.33, hay una forma más precisa de decidir qué caracteres conservar. En lugar de restar la longitud del lookbehind más largo del carácter inspeccionado más temprano (offsets[0]), se debe usar la posición de inicio de la coincidencia (offsets[2]), y el siguiente intento de coincidencia se debe iniciar en el carácter offsets[2] estableciendo el argumento *startoffset* de pcre_exec() o pcre_dfa_exec().

Por ejemplo, si el patrón "(?<=123)abc" coincide parcialmente con la cadena "xx123a", los tres valores de desplazamiento devueltos son 2, 6 y 5. Esto indica que el proceso de coincidencia que dio una coincidencia parcial comenzó en el desplazamiento 5, pero se inspeccionaron todos los caracteres "123a". El lookbehind máximo para ese patrón es 3, por lo que restarlo de 5 muestra que solo necesitamos conservar "123a", y el siguiente intento de coincidencia se puede iniciar en el desplazamiento 3 (es decir, en "a") cuando se hayan agregado caracteres adicionales. Cuando el inicio de la coincidencia no es el carácter inspeccionado más temprano, pcretest lo muestra

NAME

pcrepartial — PCRE partial matching

PARTIAL MATCHING IN PCRE

PCRE supports matching in stages, returning a partial match if a full match has not been found when the end of the subject string is reached. This can be invoked in two ways:

1. By calling pcre_exec() or pcre32_exec() or pcre16_exec() with the PCRE_PARTIAL option set.

2. By calling pcre_dfa_exec() or pcre32_dfa_exec() or pcre16_dfa_exec(). These functions always operate in partial mode, returning PCRE_ERROR_PARTIAL if no complete match is found when the end of the subject string is reached.

The meaning of a partial match is a string that could be the start of a valid match, but which has been terminated prematurely by the end of the subject string. In the case of pcre_exec() etc., this behaviour is controlled by the PCRE_PARTIAL flag. For pcre_dfa_exec() etc., this is the default behaviour.

There are two modes of partial matching:

PCRE_PARTIAL_SOFT
If a complete match is found anywhere in the subject string, it is returned. Only if no complete match is found is a partial match returned. This is the default behaviour when using the DFA matching functions.
PCRE_PARTIAL_HARD
A partial match is returned only if it is impossible to find a complete match anywhere in the subject string. If a complete match is found, it is returned, otherwise the longest possible partial match is returned. This is the behaviour when using pcre_exec() etc. with the PCRE_PARTIAL flag set.

This document is concerned with the behaviour of PCRE when partial matches occur.

PARTIAL MATCHING USING pcre_exec() OR pcre[16|32]_exec()

When the PCRE_PARTIAL option is set, pcre_exec() returns PCRE_ERROR_PARTIAL if the end of the subject string is reached but a complete match has not been found. The offset of the partial match is returned in the third argument (the match start offset). The length of the partial match is the difference between the offset of the end of the string and the offset of the partial match. A value of zero is returned for the match length if the partial match is at the very end of the string.

For example:


re> /abc(.*)def/
data> abc\P
Partial match at offset 0

Here, the string "abc" is a partial match, starting at offset 0. Because the end of the string was reached, PCRE_ERROR_PARTIAL is returned. A full match would require "def" to appear later.

If the pattern contains lookarounds, a partial match can be zero length. For example:


re> /abc(?=def)/
data> abc\P
Partial match at offset 3

In this case, the string "abc" has been consumed. The lookahead condition (?=def) is evaluated at the end of the string. Because "def" is not present, the lookahead fails. However, because no complete match was found, and the end of the string was reached, PCRE_ERROR_PARTIAL is returned. The partial match starts at offset 3, which is the point immediately after the consumed substring.

PARTIAL MATCHING USING pcre_dfa_exec() OR pcre[16|32]_dfa_exec()

These functions always operate in partial mode, returning PCRE_ERROR_PARTIAL if no complete match is found when the end of the subject string is reached. The PCRE_PARTIAL option is ignored. The offset of the partial match is returned in the third argument (the match start offset). The length of the partial match is the difference between the offset of the end of the string and the offset of the partial match. A value of zero is returned for the match length if the partial match is at the very end of the string.

The behaviour of these functions is slightly different from pcre_exec() etc. with PCRE_PARTIAL set, in that they always return the longest possible partial match if no complete match is found. For example:


re> /abcdef/
data> abc\P
Partial match at offset 0

Here, the entire string "abc" is considered a partial match because it could be the start of a full match for "abcdef". This is in contrast to pcre_exec() with PCRE_PARTIAL, which would return a zero-length partial match at offset 3.

PARTIAL MATCHING AND WORD BOUNDARIES

Word boundary assertions (\b and \B) can cause unexpected behaviour when partial matching is used with the DFA matching functions. This is because the DFA matching functions may stop matching at the end of a segment if they encounter a word boundary. Consider the pattern:


re> /\bword\b/
data> \bwo\P
Partial match at offset 0

Here, the first character is a word boundary, so the pattern starts matching. "wo" is consumed, and the end of the subject is reached. A partial match is returned. However, if the input was:


re> /\bword\b/
data> awo\P
No match

The first character 'a' is not a word boundary, so the pattern cannot start. The DFA matching function returns "No match". If PCRE_PARTIAL was set for pcre_exec(), the result would be the same. This might be unexpected if you were expecting a partial match to be found.

The problem is that the word boundary check is performed at the point where the match starts. If the check fails, the match fails immediately. This can be avoided by ensuring that the pattern is anchored at the start of the string, or by using PCRE_PARTIAL_HARD mode with pcre_exec().

FORMERLY RESTRICTED PATTERNS

Some patterns were formerly restricted in partial matching mode, because they could lead to excessive backtracking. These include patterns containing nested quantifiers or alternations with overlapping alternatives. This restriction has been lifted in later versions of PCRE, but might still apply in older versions.

The main issue is that a partial match should always be the *longest* possible partial match. If a pattern has multiple ways of matching part of a string, the longest one should be preferred. For example:


re> /(a|ab)c/
data> a\P
Partial match at offset 0

In this case, "a" could be matched by the first alternative, or it could be the start of a match using the second alternative ("ab"). The longest partial match is "a" (from the second alternative). If PCRE_PARTIAL is set, a partial match is returned at offset 0. The length of the partial match is 1.

If the input string contained lookbehinds, a partial match might have zero length. For example:


re> /(?<=123)abc/
data> xx123a\P
Partial match at offset 5: 123a

3. Because a partial match must always contain at least one character, what might be considered a partial match of an empty string actually gives a "no match" result. For example:


re> /c(?<=abc)x/
data> ab\P
No match

If the next segment begins "cx", a match should be found, but this will only happen if characters from the previous segment are retained. For this reason, a "no match" result should be interpreted as "partial match of an empty string" when the pattern contains lookbehinds.

4. Matching a subject string that is split into multiple segments may not always produce exactly the same result as matching over one single long string, especially when PCRE_PARTIAL_SOFT is used. The section "Partial Matching and Word Boundaries" above describes an issue that arises if the pattern ends with \b or \B. Another kind of difference may occur when there are multiple matching possibilities, because (for PCRE_PARTIAL_SOFT) a partial match result is given only when there are no completed matches. This means that as soon as the shortest match has been found, continuation to a new subject segment is no longer possible. Consider again this pcretest example:


re> /dog(sbody)?/
data> dogsb\P
0: dog
data> do\P\D
Partial match: do
data> gsb\R\P\D
0: g
data> dogsbody\D
0: dogsbody
1: dog

The first data line passes the string "dogsb" to a standard matching function, setting the PCRE_PARTIAL_SOFT option. Although the string is a partial match for "dogsbody", the result is not PCRE_ERROR_PARTIAL, because the shorter string "dog" is a complete match. Similarly, when the subject is presented to a DFA matching function in several parts ("do" and "gsb" being the first two) the match stops when "dog" has been found, and it is not possible to continue. On the other hand, if "dogsbody" is presented as a single string, a DFA matching function finds both matches.

Because of these problems, it is best to use PCRE_PARTIAL_HARD when matching multi-segment data. The example above then behaves differently:


re> /dog(sbody)?/
data> dogsb\P\P
Partial match: dogsb
data> do\P\D
Partial match: do
data> gsb\R\P\P\D
Partial match: gsb

5. Patterns that contain alternatives at the top level which do not all start with the same pattern item may not work as expected when PCRE_DFA_RESTART is used. For example, consider this pattern:


1234|3789

If the first part of the subject is "ABC123", a partial match of the first alternative is found at offset 3. There is no partial match for the second alternative, because such a match does not start at the same point in the subject string. Attempting to continue with the string "7890" does not yield a match because only those alternatives that match at one point in the subject are remembered. The problem arises because the start of the second alternative matches within the first alternative. There is no problem with anchored patterns or patterns such as:


1234|ABCD

where no string can be a partial match for both alternatives. This is not a problem if a standard matching function is used, because the entire match has to be rerun each time:


re> /1234|3789/
data> ABC123\P\P
Partial match: 123
data> 1237890
0: 3789

Of course, instead of using PCRE_DFA_RESTART, the same technique of re-running the entire match can also be used with the DFA matching functions. Another possibility is to work with two buffers. If a partial match at offset n in the first buffer is followed by "no match" when PCRE_DFA_RESTART is used on the second buffer, you can then try a new match starting at offset n+1 in the first buffer.
