PCRETEST(1) Manual de Comandos Generales PCRETEST(1)

NOMBRE

pcretest - un programa para probar expresiones regulares compatibles con Perl.

SINOPSIS

pcretest [opciones] [archivo de entrada [archivo de salida]]

pcretest fue escrito como un programa de prueba para la biblioteca de expresiones regulares PCRE en sí misma, pero también puede ser utilizado para experimentar con expresiones regulares. Este documento describe las características del programa de prueba; para obtener detalles sobre las expresiones regulares en sí, consulte la documentación de pcrepattern. Para obtener detalles sobre las llamadas a funciones de la biblioteca PCRE y sus opciones, consulte la documentación de pcreapi, pcre16 y pcre32.

La entrada para pcretest es una secuencia de patrones de expresión regular y cadenas a comparar, como se describe a continuación. La salida muestra el resultado de cada coincidencia. Las opciones en la línea de comandos y los patrones controlan las opciones de PCRE y exactamente qué se produce en la salida.

A medida que PCRE ha evolucionado, ha adquirido muchas características diferentes y, como resultado, pcretest ahora tiene bastantes opciones obsoletas para probar todas las características posibles. Algunas de estas opciones están diseñadas específicamente para su uso junto con el script de prueba y los archivos de datos que se distribuyen como parte de PCRE, y es poco probable que sean útiles de otra manera. Todas están documentadas aquí, pero sin mucha justificación.

FORMATO DE DATOS DE ENTRADA

La entrada para pcretest se procesa línea por línea, ya sea llamando a la función fgets() de la biblioteca C, o a través de la biblioteca libreadline (ver más abajo). En entornos tipo Unix, fgets() trata cualquier byte que no sea una nueva línea como caracteres de datos. Sin embargo, en algunos entornos de Windows, el carácter 26 (hex 1A) causa un fin de archivo inmediato, y no se leen más datos. Para una máxima portabilidad, por lo tanto, es más seguro usar solo caracteres ASCII en los archivos de entrada de pcretest.

La entrada se procesa utilizando las funciones de cadena de C, por lo que no debe contener ceros binarios, aunque en entornos tipo Unix, fgets() trata cualquier byte que no sea una nueva línea como caracteres de datos.

BIBLIOTECAS DE 8-BITAS, 16-BITAS Y 32-BITAS DE PCRE

A partir de la versión 8.30, se pueden compilar dos bibliotecas PCRE separadas. La original soporta cadenas de caracteres de 8 bits, mientras que la biblioteca más nueva de 16 bits soporta cadenas de caracteres codificadas en unidades de 16 bits. A partir de la versión 8.32, se puede compilar una tercera biblioteca, que soporta cadenas de caracteres codificadas en unidades de 32 bits. El programa pcretest puede ser utilizado para probar las tres bibliotecas. Sin embargo, él mismo sigue siendo un programa de 8 bits, que lee entrada de 8 bits y produce salida de 8 bits. Al probar la biblioteca de 16 o 32 bits, los patrones y las cadenas de datos se convierten al formato de 16 o 32 bits antes de ser pasados a las funciones de la biblioteca PCRE. Los resultados se convierten a 8 bits para su salida.

Las referencias a funciones y estructuras de la forma pcre[16|32]_xx a continuación significan "pcre_xx al usar la biblioteca de 8 bits, pcre16_xx al usar la biblioteca de 16 bits, o pcre32_xx al usar la biblioteca de 32 bits".

OPCIONES DE LA LÍNEA DE COMANDOS

-8
Si la biblioteca de 8 bits ha sido compilada, esta opción causa que sea utilizada (este es el valor predeterminado). Si la biblioteca de 8 bits no ha sido compilada, esta opción causa un error.
-16
Si la biblioteca de 16 bits ha sido compilada, esta opción causa que sea utilizada. Si solo la biblioteca de 16 bits ha sido compilada, este es el valor predeterminado. Si la biblioteca de 16 bits no ha sido compilada, esta opción causa un error.
-32
Si la biblioteca de 32 bits ha sido compilada, esta opción causa que sea utilizada. Si solo la biblioteca de 32 bits ha sido compilada, este es el valor predeterminado. Si la biblioteca de 32 bits no ha sido compilada, esta opción causa un error.
-b
Comportarse como si cada patrón tuviera el modificador /B (mostrar código de bytes); la forma interna se muestra después de la compilación.
-C
Mostrar el número de versión de la biblioteca PCRE, y toda la información disponible sobre las características opcionales incluidas, y luego salir con un código de salida cero. Todas las demás opciones son ignoradas.
-C opción
Mostrar información sobre una opción específica de tiempo de compilación, y luego salir. Esta funcionalidad está destinada a ser utilizada en scripts como RunTest. Las siguientes opciones muestran el valor y establecen el código de salida como se indica:

0x15 o 0x25
0 si se usa en un entorno ASCII
el código de salida es siempre 0
linksize el tamaño de enlace interno configurado (2, 3 o 4)
el código de salida se establece al tamaño de enlace
newline la configuración predeterminada de nueva línea:
CR, LF, CRLF, ANYCRLF o ANY
el código de salida es siempre 0
bsr la configuración predeterminada para lo que coincide \R:
ANYCRLF o ANY
el código de salida es siempre 0

Las siguientes opciones muestran 1 para verdadero o 0 para falso, y establecen el código de salida al mismo valor:

jit soporte just-in-time disponible
pcre16 la biblioteca de 16 bits fue compilada
pcre32 la biblioteca de 32 bits fue compilada
pcre8 la biblioteca de 8 bits fue compilada
ucp soporte de propiedades Unicode disponible
utf soporte UTF-8 y/o UTF-16 y/o UTF-32
disponible

Si se proporciona una opción desconocida, se muestra un mensaje de error; el código de salida es 0.

-d
Comportarse como si cada patrón tuviera el modificador /D (depurar); la forma interna y la información sobre el patrón compilado se muestran después de la compilación; -d es equivalente a -b -i.
-dfa
Comportarse como si cada línea de datos contuviera la secuencia de escape \D; esto hace que se utilice la función de coincidencia alternativa, pcre[16|32]_dfa_exec(), en lugar de la función estándar pcre[16|32]_exec() (se dan más detalles a continuación).
-help
Mostrar un breve resumen de estas opciones y luego salir.
-i
Comportarse como si cada patrón tuviera el modificador /I; se proporciona información sobre el patrón compilado después de la compilación.
-M
Comportarse como si cada línea de datos contuviera la secuencia de escape \M; esto hace que PCRE descubra los límites mínimos de MATCH_LIMIT y MATCH_LIMIT_RECURSION llamando repetidamente a pcre[16|32]_exec() con límites diferentes.
-m
Mostrar el tamaño de cada patrón compilado después de que haya sido compilado. Esto es equivalente a agregar /M a cada expresión regular. El tamaño se da en bytes para ambas bibliotecas.
-O
Comportarse como si cada patrón tuviera el modificador /O, es decir, desactivar la auto-posesión para todos los patrones.
-o tamaño_salida
Establecer el número de elementos en el vector de salida que se utiliza al llamar a pcre[16|32]_exec() o pcre[16|32]_dfa_exec() a ser tamaño_salida. El valor predeterminado es 45, que es suficiente para 14 subexpresiones de captura para pcre[16|32]_exec() o 22 coincidencias diferentes para pcre[16|32]_dfa_exec(). El tamaño del vector se puede cambiar para llamadas de coincidencia individuales incluyendo \O en la línea de datos (ver abajo).
-p
Comportarse como si cada patrón tuviera el modificador /P; la API envoltorio POSIX se utiliza para llamar a PCRE. Ninguna de las otras opciones tiene efecto cuando se establece -p. Esta opción solo se puede usar con la biblioteca de 8 bits.
-q
No mostrar el número de versión de pcretest al inicio de la ejecución.
-S tamaño
En sistemas tipo Unix, establecer el tamaño de la pila en tiempo de ejecución a tamaño megabytes.

NAME

pcretest

a program for testing the PCRE 8-bit, 16-bit, and 32-bit unoptimized and JIT-compiled library functions

SYNOPSIS

pcretest [-biCDG`...] [-M size] [-m size] [-q] [-s] [-u] [-V] [-?] [inputfile]

DESCRIPTION

The pcretest utility is a driver program that calls the various functions within the PCRE library, allowing them to be tested on a set of inputs. It reads input lines, interprets them as PCRE functions to be called, and checks the results. It is used by the PCRE developers to test new releases of the library, and it can also be used by application developers to test their understanding of PCRE regular expressions.

The program can be run in two modes: interpret mode (the default) and script mode. In interpret mode, it reads lines from the input file (or standard input if no file is given) and executes them one by one. In script mode (activated by the -s option), it reads a script that specifies a sequence of tests to be run.

The lines in the input file are interpreted as follows:

<
Lines starting with an opening angle bracket are commands to pcretest itself. Currently, these are:
  < forbid ...
  < help
  < set ...
  < show ...
  < verify ...

Lines starting with @ are interpreted as strings that should be compiled. They are passed to pcre_compile() or pcre16_compile() or pcre32_compile().

Lines starting with # are comments and are ignored.

All other lines are passed as the subject string to pcre_exec(), pcre16_exec(), or pcre32_exec(). The pattern to be used is the one that was last compiled.

A compiled pattern may be followed by one or more modifiers, which affect how the pattern is compiled or how the matching is performed. The modifiers are single letters, preceded by a slash. For example:

  @^.(?=.*word).*\b$ /dxim /+

This compiles the pattern ^.(?=.*word).*\b$ with the modifiers d, x, i, m, and then applies the + modifier to the subsequent matching phase.

The modifiers are described in the section "PATTERNS AND MODIFIERS".

If the -b option is given, binary data may be used as subject strings. This is mainly for testing purposes.

If the -i option is given, the pattern is automatically compiled with the PCRE_IGNORE_MATCH_CASE compile option. This option can be overridden by the /i modifier.

If the -C option is given, the output includes the values of constants defined in pcre.h.

If the -D option is given, the output includes the version number of the PCRE library, obtained by calling pcre_config() with the PCRE_CONFIG_VERSION option.

If the -G option is given, the output includes the values of the JIT compiler options defined in pcre.h. This option requires that PCRE was compiled with JIT support.

If the -M option is given, it sets the maximum number of matches that PCRE will attempt to find when a /g or /G modifier is used. The argument must be a decimal integer.

If the -m option is given, it sets the maximum depth of the recursion stack that PCRE may use during matching. The argument must be a decimal integer. This is used to test the pcre_stack_guard feature.

If the -q option is given, diagnostic output from the pcre_stack_guard check is suppressed.

If the -u option is given, the pattern is automatically compiled with the PCRE_UTF8 compile option. This option can be overridden by the /u modifier.

If the -V option is given, the output includes the version number of the PCRE library, obtained by calling pcre_version().

If the -? option is given, a help message is displayed and the program exits.

The inputfile is the name of the file containing the tests. If it is omitted, standard input is used.

The pcretest program operates on patterns and subject strings. For each line starting with @, it calls pcre_compile() (or its 16-bit or 32-bit equivalent) to compile the pattern. The result of the compilation is checked, and error information is printed if it fails. A pattern can be associated with a name by following the @ with the name and a colon, e.g. @name:pattern. This allows patterns to be re-used by later lines that start with :name instead of a pattern.

For each subsequent line that is not a command or a comment, pcretest calls pcre_exec() (or its 16-bit or 32-bit equivalent) using the current pattern and the subject string from the line. The result of the execution is checked, and details of the match (offsets of substrings, and so on) are printed.

When matching is done, the results are printed in a standard format, showing the overall result code, followed by the starting and ending offsets of the substrings that were matched. If the pattern contained capture groups, the offsets for these are also printed, identified by their group number.

Details of the options and modifiers are given below.

PATTERNS AND MODIFIERS

A pattern line starts with '@' or ':'. It may be followed by one or more modifiers, which are single letters preceded by a slash. The modifiers affect how the pattern is compiled and/or how matching is performed. The following modifiers are available:

/a
Sets the PCRE_ANCHOR compile-time option. This forces the pattern to match only at the start of the subject string.
/b
Sets the PCRE_EXTENDED compile-time option. This suppresses the meaning of white space in the pattern, and allows comments starting with #.
/c
Sets the PCRE_CASELESS compile-time option. This makes the matching case-insensitive.
/d
Sets the PCRE_DOLLAR_ENDONLY compile-time option. This changes the behavior of the '$' character so that it only matches at the end of the string, not before a newline at the end of the string.
/e
Sets the PCRE_EXTRA compile-time option. This requests that a pcre_extra block is returned by pcre_exec(), even if no study information is available. This is used for testing.
/f
Sets the PCRE_FIRSTLINE compile-time option. This causes the '$' metacharacter to match only at the end of the string, and also causes '.' and '^' to match newline characters.
/g
Requests repeated matching. After a match is found, the next search starts immediately after the previous match.
/G
Requests repeated matching, similar to /g, but the search restarts at the beginning of the remaining substring. This makes a difference if the pattern begins with a lookbehind assertion.
/h
Sets the PCRE_ALT_VERBOSITY compile-time option. This makes the matching case-insensitive for characters with the ISO 8859 definition.
/j
Sets the PCRE_UNGREEDY compile-time option. This makes all default quantifiers into non-greedy quantifiers.
/k
Sets the PCRE_NO_AUTO_CALLOUT compile-time option. This disables any auto-callout that might be present in the pattern.
/l
Sets the PCRE_UTF16_LITTLE_ENDIAN compile-time option for 16-bit patterns. For 32-bit patterns, it sets PCRE_UTF32_LITTLE_ENDIAN.
/m
Sets the PCRE_MULTILINE compile-time option. This causes '^' and '$' to match at the start and end of lines, respectively, in addition to the start and end of the string.
/n
Sets the PCRE_NO_UTF8 compile-time option. This disables UTF-8 support for patterns that might otherwise have it.
/o
Sets the PCRE_NO_AUTO_POSSESSIVE compile-time option. This disables the automatic conversion of nested quantifiers into possessive quantifiers.
/p
Sets the PCRE_PARTIAL compile-time option. This enables partial matching support.
/q
Sets the PCRE_UTF16_BIG_ENDIAN compile-time option for 16-bit patterns. For 32-bit patterns, it sets PCRE_UTF32_BIG_ENDIAN.
/r
Sets the PCRE_RECURSION compile-time option. This enables recursion in patterns.
/s
Sets the PCRE_DOTALL compile-time option. This causes the '.' metacharacter to match any character, including newline characters.
/t
Sets the PCRE_UTF8 compile-time option for 8-bit patterns. For 16-bit patterns, it sets PCRE_UTF16. For 32-bit patterns, it sets PCRE_UTF32.
/u
Sets the PCRE_UNICODE compile-time option. This enables Unicode property support.
/v
Sets the PCRE_VECURISE compile-time option. This is for testing the alternative way of handling recursion.
/w
Sets the PCRE_NO_AUTO_CAPTURE compile-time option. This disables automatic numbering of capturing groups.
/x
Sets the PCRE_EXTENDED compile-time option. This suppresses the meaning of white space in the pattern, and allows comments starting with #.
/z
Sets the PCRE_JAVASCRIPT_COMPAT compile-time option. This makes the '$' metacharacter match only at the end of the string, and also causes '.' and '^' to match newline characters.

Finding all matches in a string

Searching for all possible matches within each subject string can be requested by the /g or /G modifier. After finding a match, PCRE is called again to search the remainder of the subject string. The difference between /g and /G is that the former uses the startoffset argument to pcre[16|32]_exec() to start searching at a new point within the entire string (which is in effect what Perl does), whereas the latter passes over a shortened substring. This makes a difference to the matching process if the pattern begins with a lookbehind assertion (including \b or \B).

If any call to pcre[16|32]_exec() in a /g or /G sequence matches an empty string, the next call is done with the PCRE_NOTEMPTY_ATSTART and PCRE_ANCHORED flags set in order to search for another, non-empty, match at the same point. If this second match fails, the start offset is advanced, and the normal match is retried. This imitates the way Perl handles such cases when using the /g modifier or the split() function. Normally, the start offset is advanced by one character, but if the newline convention recognizes CRLF as a newline, and the current character is CR followed by LF, an advance of two is used.

Other modifiers

There are yet more modifiers for controlling the way pcretest operates.

The /+ modifier requests that as well as outputting the substring that matched the entire pattern, pcretest should in addition output the remainder of the subject string. This is useful for tests where the subject contains multiple copies of the same substring. If the + modifier appears twice, the same action is taken for captured substrings. In each case the remainder is output on the following line with a plus character following the capture number. Note that this modifier must not immediately follow the /S modifier because /S+ and /S++ have other meanings.

The /= modifier requests that the values of all potential captured parentheses be output after a match. By default, only those up to the highest one actually used in the match are output (corresponding to the return code from pcre[16|32]_exec()). Values in the offsets vector corresponding to higher numbers should be set to -1, and these are output as "<unset>". This modifier gives a way of checking that this is happening.

The /B modifier is a debugging feature. It requests that pcretest output a representation of the compiled code after compilation. Normally this information contains length and offset values; however, if /Z is also present, this data is replaced by spaces. This is a special feature for use in the automatic test scripts; it ensures that the same output is generated for different internal link sizes.

The /D modifier is a PCRE debugging feature, and is equivalent to /BI, that is, both the /B and the /I modifiers.

The /F modifier causes pcretest to flip the byte order of the 2-byte and 4-byte fields in the compiled pattern. This facility is for testing the feature in PCRE that allows it to execute patterns that were compiled on a host with a different endianness. This feature is not available when the POSIX interface to PCRE is being used, that is, when the /P pattern modifier is specified. See also the section about saving and reloading compiled patterns below.

The /I modifier requests that pcretest output information about the compiled pattern (whether it is anchored, has a fixed first character, and so on). It does this by calling pcre[16|32]_fullinfo() after compiling a pattern. If the pattern is studied, the results of that are also output. In this output, the word "char" means a non-UTF character, that is, the value of a single data item (8-bit, 16-bit, or 32-bit, depending on the library that is being tested).

The /K modifier requests pcretest to show names from backtracking control verbs that are returned from calls to pcre[16|32]_exec(). It causes pcretest to create a pcre[16|32]_extra block if one has not already been created by a call to pcre[16|32]_study(), and to set the PCRE_EXTRA_MARK flag and the mark field within it, every time that pcre[16|32]_exec() is called. If the variable that the mark field points to is non-NULL for a match, non-match, or partial match, pcretest prints the string to which it points. For a match, this is shown on a line by itself, tagged with "MK:". For a non-match it is added to the message.

The /L modifier must be followed directly by the name of a locale, for example,


/pattern/Lfr_FR

For this reason, it must be the last modifier. The given locale is set, pcre[16|32]_maketables() is called to build a set of character tables for the locale, and this is then passed to pcre[16|32]_compile() when compiling the regular expression. Without an /L (or /T) modifier, NULL is passed as the tables pointer; that is, /L applies only to the expression on which it appears.

The /M modifier causes the size in bytes of the memory block used to hold the compiled pattern to be output. This does not include the size of the pcre[16|32] block; it is just the actual compiled data. If the pattern is successfully studied with the PCRE_STUDY_JIT_COMPILE option, the size of the JIT compiled code is also output.

The /Q modifier is used to test the use of pcre_stack_guard. It must be followed by '0' or '1', specifying the return code to be given from an external function that is passed to PCRE and used for stack checking during compilation (see the pcreapi documentation for details).

The /S modifier causes pcre[16|32]_study() to be called after the expression has been compiled, and the results used when the expression is matched. There are a number of qualifying characters that may follow /S. They may appear in any order.

If /S is followed by an exclamation mark, pcre[16|32]_study() is called with the PCRE_STUDY_EXTRA_NEEDED option, causing it always to return a pcre_extra block, even when studying discovers no useful information.

If /S is followed by a second S character, it suppresses studying, even if it was requested externally by the -s command line option. This makes it possible to specify that certain patterns are always studied, and others are never studied, independently of -s. This feature is used in the test files in a few cases where the output is different when the pattern is studied.

If the /S modifier is followed by a + character, the call to pcre[16|32]_study() is made with all the JIT study options, requesting just-in-time optimization support if it is available, for both normal and partial matching. If you want to restrict the JIT compiling modes, you can follow /S+ with a digit in the range 1 to 7:


1 normal match only
2 soft partial match only
3 normal match and soft partial match
4 hard partial match only
6 soft and hard partial match
7 all three modes (default)

If /S++ is used instead of /S+ (with or without a following digit), the text "(JIT)" is added to the first output line after a match or no match when JIT-compiled code was actually used.

Note that there is also an independent /+ modifier; it must not be given immediately after /S or /S+ because this will be misinterpreted.

If JIT studying is successful, the compiled JIT code will automatically be used when pcre[16|32]_exec() is run, except when incompatible run-time options are specified. For more details, see the pcrejit documentation. See also the \J escape sequence below for a way of setting the size of the JIT stack.

Finally, if /S is followed by a minus character, JIT compilation is suppressed, even if it was requested externally by the -s command line option. This makes it possible to specify that JIT is never to be used for certain patterns.

The /T modifier must be followed by a single digit. It causes a specific set of built-in character tables to be passed to pcre[16|32]_compile(). It is used in the standard PCRE tests to check behaviour with different character tables. The digit specifies the tables as follows:


0 the default ASCII tables, as distributed in
pcre_chartables.c.dist
1 a set of tables defining ISO 8859 characters

In table 1, some characters whose codes are greater than 128 are identified as letters, digits, spaces, etc.

Using the POSIX wrapper API

The /P modifier causes pcretest to call PCRE via the POSIX wrapper API rather than its native API. This supports only the 8-bit library. When /P is set, the following modifiers set options for the regcomp() function:


/i REG_ICASE
/m REG_NEWLINE
/N REG_NOSUB
/s REG_DOTALL )
/U REG_UNGREEDY ) These options are not part of
/W REG_UCP ) the POSIX standard
/8 REG_UTF8 )

The /+ modifier works as described above. All other modifiers are ignored.

Locking out certain modifiers

PCRE can be compiled with or without support for certain features such as UTF-8/16/32 or Unicode properties. Accordingly, the standard tests are split up into a number of different files that are selected for running depending on which features are available. When updating the tests, it is all too easy to put a new test into the wrong file by mistake; for example, to put a test that requires UTF support into a file that is used when it is not available. To help detect such mistakes as early as possible, there is a facility for locking out specific modifiers. If an input line for pcretest starts with the string "< forbid " the following sequence of characters is taken as a list of forbidden modifiers. For example, in the test files that must not use UTF or Unicode property support, this line appears:


< forbid 8W

This locks out the /8 and /W modifiers. An immediate error is given if they are subsequently encountered. If the ch

caracteres de cadena contienen < pero no >, todos los modificadores de varios caracteres que comienzan con < están bloqueados. De lo contrario, dichos modificadores deben enumerarse explícitamente, por ejemplo:


< prohibir <JS><cr>

Debe haber un solo espacio entre < y "prohibir" para que esta característica sea reconocida. Si no lo hay, la línea se interpreta ya sea como una solicitud para recargar un patrón precompilado (ver "GUARDAR Y RECARGAR PATRONES COMPILADOS" abajo) o, si hay otro carácter <, como un patrón que utiliza < como delimitador.

Tenga en cuenta que \xhh especifica un byte en lugar de un carácter en modo UTF-8; esto hace posible construir secuencias UTF-8 inválidas con fines de prueba. Por otro lado, \x{hh} se interpreta como un carácter UTF-8 en modo UTF-8, generando más de un byte si el valor es mayor que 127. Al probar la biblioteca de 8 bits no en modo UTF-8, \x{hh} genera un byte para valores menores que 256, y causa un error para valores mayores.

En modo UTF-16, se aceptan todos los valores \x{hhhh} de 4 dígitos. Esto hace posible construir secuencias UTF-16 inválidas con fines de prueba.

En modo UTF-32, se aceptan todos los valores \x{...} de 4 a 8 dígitos. Esto hace posible construir secuencias UTF-32 inválidas con fines de prueba.

Los escapes que especifican secuencias de fin de línea son cadenas literales, exactamente como se muestran. No debe haber más de una configuración de nueva línea presente en ninguna línea de datos.

Una barra invertida seguida de cualquier otra cosa simplemente escapa a ese "cualquier otra cosa". Si el último carácter es una barra invertida, se ignora. Esto proporciona una forma de pasar una línea vacía como datos, ya que una línea vacía real termina la entrada de datos.

El escape \J proporciona una forma de establecer el tamaño máximo de pila que utiliza el código de optimización just-in-time. Se ignora si no se está utilizando la optimización JIT. Proporcionar una pila más grande que el valor predeterminado de 32K solo es necesario para patrones muy complicados.

Si está presente \M, pcretest llama a pcre[16|32]_exec() varias veces, con diferentes valores en los campos match_limit y match_limit_recursion de la estructura de datos pcre[16|32]_extra, hasta que encuentra los números mínimos para cada parámetro que permiten que pcre[16|32]_exec() se complete sin errores. Debido a que esto prueba una característica específica de la ejecución normal interpretada de pcre[16|32]_exec(), el uso de cualquier optimización JIT que pueda haberse configurado mediante el calificador /S+ de la opción -s+ se deshabilita.

El número match_limit es una medida de la cantidad de backtracking que tiene lugar, y comprobarlo puede ser instructivo. Para la mayoría de las coincidencias simples, el número es bastante pequeño, pero para patrones con un gran número de posibilidades de coincidencia, puede crecer rápidamente con el aumento de la longitud de la cadena sujeto. El número match_limit_recursion es una medida de cuánta memoria de pila (o, si PCRE está compilado con NO_RECURSE, cuánta memoria del heap) se necesita para completar el intento de coincidencia.

Cuando se utiliza \O, el valor especificado puede ser superior o inferior al tamaño establecido por la opción de línea de comandos -O (o el valor predeterminado de 45); \O se aplica solo a la llamada de pcre[16|32]_exec() para la línea en la que aparece.

Si el modificador /P estuvo presente en el patrón, lo que provocó el uso de la API de envoltura POSIX, las únicas secuencias de configuración de opciones que tienen algún efecto son \B, \N y \Z, lo que provoca que REG_NOTBOL, REG_NOTEMPTY y REG_NOTEOL, respectivamente, se pasen a regexec().

LA FUNCIÓN DE COINCIDENCIA ALTERNATIVA

Por defecto, pcretest utiliza la función de coincidencia estándar de PCRE, pcre[16|32]_exec(), para hacer coincidir cada línea de datos. PCRE también admite una función de coincidencia alternativa, pcre[16|32]_dfa_test(), que opera de manera diferente y tiene algunas restricciones. Las diferencias entre las dos funciones se describen en la documentación de pcrematching.

Si una línea de datos contiene la secuencia de escape \D, o si la línea de comandos contiene la opción -dfa, se utiliza la función de coincidencia alternativa. Esta función encuentra todas las coincidencias posibles en un punto dado. Sin embargo, si la secuencia de escape \F está presente en la línea de datos, se detiene después de encontrar la primera coincidencia. Esta es siempre la coincidencia más corta posible.

SALIDA POR DEFECTO DE PCRETEST

Esta sección describe la salida cuando se está utilizando la función de coincidencia normal, pcre[16|32]_exec().

Cuando una coincidencia tiene éxito, pcretest muestra la lista de subcadenas capturadas que devuelve pcre[16|32]_exec(), comenzando con el número 0 para la cadena que coincidió con el patrón completo. De lo contrario, muestra "No match" cuando el retorno es PCRE_ERROR_NOMATCH, y "Partial match:" seguido de la subcadena parcialmente coincidente cuando pcre[16|32]_exec() devuelve PCRE_ERROR_PARTIAL. (Tenga en cuenta que esta es la subcadena completa que se inspeccionó durante la coincidencia parcial; puede incluir caracteres anteriores al inicio real de la coincidencia si se trataba de una aserción lookbehind, \K, \b o \B). Para cualquier otro retorno, pcretest muestra el número de error negativo de PCRE y una frase descriptiva corta. Si el error es una verificación fallida de cadena UTF, también se muestra el desplazamiento del inicio del carácter fallido y el código de motivo, siempre que el tamaño del vector de salida sea al menos dos. Aquí hay un ejemplo de una ejecución interactiva de pcretest.


$ pcretest
Versión PCRE 8.13 2011-04-30


re> /^abc(\d+)/
datos> abc123
0: abc123
1: 123
datos> xyz
No match

Las subcadenas de captura no establecidas que no van seguidas de una establecida no son devueltas por pcre[16|32]_exec(), y no son mostradas por pcretest. En el siguiente ejemplo, hay dos subcadenas de captura, pero cuando la primera línea de datos coincide, la segunda subcadena no establecida i

no se muestra. Una subcadena "interna" no establecida se muestra como "<unset>", como en la segunda línea de datos.


re> /(a)|(b)/
data> a
0: a
1: a
data> b
0: b
1: <unset>
2: b

Si las cadenas contienen caracteres no imprimibles, se muestran como escapes \xhh si el valor es menor que 256 y el modo UTF no está establecido. De lo contrario, se muestran como escapes \x{hh...}. Consulte a continuación la definición de caracteres no imprimibles. Si el patrón tiene el modificador /+, la salida de la subcadena 0 va seguida del resto de la cadena sujeto, identificada por "0+" de la siguiente manera:


re> /cat/+
data> cataract
0: cat
0+ aract

Si el patrón tiene el modificador /g o /G, los resultados de intentos de coincidencia sucesivos se muestran en secuencia, así:


re> /\Bi(\w\w)/g
data> Mississippi
0: iss
1: ss
0: iss
1: ss
0: ipp
1: pp

Solo se muestra "No match" si el primer intento de coincidencia falla. Aquí hay un ejemplo de un mensaje de error (el desplazamiento 4 que se especifica con \>4 está más allá del final de la cadena sujeto):


re> /xyz/
data> xyz\>4
Error -24 (mal valor de desplazamiento)

Si alguna de las secuencias \C, \G o \L está presente en una línea de datos que coincide con éxito, las subcadenas extraídas por las funciones de conveniencia se muestran con C, G o L después del número de cadena en lugar de dos puntos. Esto es además de la lista completa normal. La longitud de la cadena (es decir, el retorno de la función de extracción) se proporciona entre paréntesis después de cada cadena para \C y \G.

Tenga en cuenta que, si bien los patrones se pueden continuar en varias líneas (se utiliza un simple prompt ">" para las continuaciones), las líneas de datos no pueden. Sin embargo, se pueden incluir saltos de línea en los datos mediante la secuencia de escape \n (o \r, \r\n, etc., según la configuración de la secuencia de salto de línea).

SALIDA DE LA FUNCIÓN DE COINCIDENCIA ALTERNATIVA

Cuando se utiliza la función de coincidencia alternativa, pcre[16|32]_dfa_exec() (mediante la secuencia de escape \D o la opción de línea de comandos -dfa), la salida consiste en una lista de todas las coincidencias que comienzan en el primer punto del sujeto donde hay al menos una coincidencia. Por ejemplo:


re> /(tang|tangerine|tan)/
data> yellow tangerine\D
0: tangerine
1: tang
2: tan

(Usar la función de coincidencia normal en estos datos solo encuentra "tang".) La cadena coincidente más larga siempre se presenta primero (y se numera cero). Después de un retorno PCRE_ERROR_PARTIAL, la salida es "Partial match:", seguida de la subcadena parcialmente coincidente. (Tenga en cuenta que esta es la subcadena completa que se inspeccionó durante la coincidencia parcial; puede incluir caracteres anteriores al inicio de la coincidencia real si se involucró una aserción de retroceso, \K, \b o \B).

Si /g está presente en el patrón, la búsqueda de coincidencias adicionales se reanuda al final de la coincidencia más larga. Por ejemplo:


re> /(tang|tangerine|tan)/g
data> yellow tangerine and tangy sultana\D
0: tangerine
1: tang
2: tan
0: tang
1: tan
0: tan

Dado que la función de coincidencia no admite la captura de subcadenas, las secuencias de escape relacionadas con subcadenas capturadas no son relevantes.

REINICIO DESPUÉS DE UNA COINCIDENCIA PARCIAL

Cuando la función de coincidencia alternativa ha devuelto PCRE_ERROR_PARTIAL, lo que indica que el sujeto coincidió parcialmente con el patrón, puede reiniciar la coincidencia con datos de sujeto adicionales mediante la secuencia de escape \R. Por ejemplo:


re> /^\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d$/
data> 23ja\P\D
Partial match: 23ja
data> n05\R\D
0: n05

Para obtener más información sobre la coincidencia parcial, consulte la documentación de pcrepartial.

LLAMADAS DE RETORNO

Si el patrón contiene solicitudes de llamada de retorno, la función de llamada de retorno de pcretest se llama durante la coincidencia. Esto funciona con ambas funciones de coincidencia. Por defecto, la función llamada muestra el número de llamada de retorno, las posiciones de inicio y actual en el texto en el momento de la llamada de retorno y el siguiente elemento del patrón a probar. Por ejemplo:


--->pqrabcdef
0 ^ ^ \d

Esta salida indica que ocurrió la llamada de retorno número 0 para un intento de coincidencia que comenzó en el cuarto carácter de la cadena sujeto, cuando el puntero estaba en el séptimo carácter de los datos y cuando el siguiente elemento del patrón era \d. Solo se muestra un circunflejo si las posiciones de inicio y actual son las mismas.

Las llamadas de retorno numeradas 255 se suponen llamadas de retorno automáticas, insertadas como resultado del modificador de patrón /C. En este caso, en lugar de mostrar el número de llamada de retorno, se muestra el desplazamiento en el patrón, precedido de un signo más. Por ejemplo:


re> /\d?[A-E]\*/C
data> E*
--->E*
+0 ^ \d?
+3 ^ [A-E]
+8 ^^ \*
+10 ^ ^
0: E*

Si un patrón contiene elementos (*MARK), se muestra una línea adicional cada vez que se pasa un cambio de marca más reciente a la función de llamada de retorno. Por ejemplo:


re> /a(*MARK:X)bc/C
data> abc
--->abc
+0 ^ a
+1 ^^ (*MARK:X)
+10 ^^ b
Latest Mark: X
+11 ^ ^ c
+12 ^ ^
0: abc

La marca cambia entre la coincidencia de "a" y "b", pero permanece igual durante el resto de la coincidencia, por lo que no se muestra nada más. Si, como resultado de la retroalimentación, la marca vuelve a no estar establecida, se muestra el texto "<unset>".

La función de llamada de retorno en pcretest devuelve cero (continuar la coincidencia) por defecto, pero puede usar un elemento \C en una línea de datos (como se describe anteriormente) para cambiar esto y otros parámetros de la llamada de retorno.

Insertar llamadas de retorno puede ser útil al usar pcretest para verificar expresiones regulares complicadas. Para obtener más información sobre las llamadas de retorno, consulte la documentación de pcrecallout.

CARACTERES NO IMPRIMIBLES

Cuando pcretest muestra texto en la versión compilada de un patrón, los bytes distintos de 32-126 siempre se tratan como caracteres no imprimibles y, por lo tanto, se muestran como escapes hexadecimales.

Cuando pcretest muestra texto que es parte de una cadena sujeto que coincide, se comporta de la misma manera, a menos que se haya establecido una configuración regional diferente para el patrón (usando el modificador /L). En este caso, se utiliza la función isprint() para distinguir entre caracteres imprimibles y no imprimibles.

GUARDAR Y RECARGAR PATRONES COMPILADOS

Las funciones descritas en esta sección no están disponibles cuando se utiliza la interfaz POSIX de PCRE, es decir, cuando se especifica el modificador de patrón /P.

Cuando la interfaz POSIX no está en uso, puede hacer que pcretest escriba un patrón compilado en un archivo, siguiendo los modificadores con > y un nombre de archivo. Por ejemplo:


/pattern/im >/some/file

Consulte la documentación de pcreprecompile para ver una discusión sobre cómo guardar y reutilizar patrones compilados. Tenga en cuenta que si el patrón se estudió correctamente con optimización JIT, los datos JIT no se pueden guardar.

Los datos que se escriben son binarios. Los primeros ocho bytes son la longitud de los datos del patrón compilado seguida de la longitud de los datos opcionales de estudio, cada uno escrito como cuatro bytes en orden big-endian (el byte más significativo primero). Si no hay datos de estudio (ya sea que el patrón no se estudió o que el estudio no devolvió datos), la segunda longitud es cero. Las longitudes van seguidas de una copia exacta del patrón compilado. Si hay datos de estudio adicionales, estos (excluyendo cualquier dato JIT) siguen inmediatamente después del patrón compilado. Después de escribir el archivo, pcretest espera leer un nuevo patrón.

Un patrón guardado se puede recargar en pcretest especificando < y un nombre de archivo en lugar de un patrón. No debe haber espacio entre < y el nombre del archivo, que no debe contener un carácter <, ya que de lo contrario pcretest interpretará la línea como un patrón delimitado por caracteres <. Por ejemplo:


re> </some/file
Compiled pattern loaded from /some/file
No study data

Si el patrón se estudió previamente con la optimización JIT, la información JIT no se puede guardar y restaurar, por lo que se pierde. Cuando se ha cargado el patrón, pcretest procede a leer las líneas de datos de la manera habitual.

Puede copiar un archivo escrito por pcretest a otro host y recargarlo allí, incluso si el nuevo host tiene una inversión de bytes con respecto al host en el que se compiló el patrón. Por ejemplo, puede compilar en una máquina i86 y ejecutar en una máquina SPARC. Cuando un patrón se recarga en un host con inversión de bytes, el mensaje de confirmación cambia a:


Compiled pattern (byte-inverted) loaded from /some/file

El conjunto de pruebas contiene algunos patrones precompilados guardados con diferentes inversiones de bytes. Estos se recargan usando "<!" en lugar de solo "<". Esto suprime el texto "(byte-inverted)" para que la salida sea la misma en todos los hosts. También fuerza la salida de depuración una vez que el patrón se ha recargado.

Los nombres de archivo para guardar y recargar pueden ser absolutos o relativos, pero tenga en cuenta que la función del shell para expandir un nombre de archivo que comienza con una tilde (~) no está disponible.

La capacidad de guardar y recargar archivos en pcretest está destinada a pruebas y experimentación. No está destinada al uso en producción porque solo se puede escribir un patrón en un archivo. Además, no hay ninguna instalación para proporcionar tablas de caracteres personalizadas para su uso con un patrón recargado. Si el patrón original se compiló con tablas personalizadas, un intento de coincidir con una cadena sujeto usando un patrón recargado probablemente causará que pcretest falle.
