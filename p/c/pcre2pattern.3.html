NOMBRE

PCRE2 - expresiones regulares compatibles con Perl (API revisada)

DETALLES DE EXPRESIONES REGULARES PCRE2

La sintaxis y semántica de las expresiones regulares que son soportadas por PCRE2 se describen en detalle a continuación. Hay un resumen de la sintaxis de referencia rápida en la página pcre2syntax. PCRE2 intenta que la sintaxis y semántica de Perl coincidan lo más posible. PCRE2 también soporta alguna sintaxis alternativa de expresiones regulares que no entra en conflicto con la sintaxis de Perl para proporcionar cierta compatibilidad con expresiones regulares de Python, .NET y Oniguruma. Adicionalmente, hay algunas opciones que habilitan sintaxis y semánticas alternativas que no son las mismas que en Perl.

Las expresiones regulares de Perl se describen en su propia documentación, y las expresiones regulares en general se cubren en varios libros, algunos de los cuales tienen abundantes ejemplos. El libro de Jeffrey Friedl "Mastering Regular Expressions", publicado por O'Reilly, cubre las expresiones regulares con gran detalle. Esta descripción de las expresiones regulares de PCRE2 está pensada como material de referencia.

Este documento discute los patrones de expresiones regulares que son soportados por PCRE2 cuando se usa su función principal de coincidencia, pcre2_match(). PCRE2 también tiene una función de coincidencia alternativa, pcre2_dfa_match(), que coincide usando un algoritmo diferente que no es compatible con Perl. Algunas de las características discutidas a continuación no están disponibles cuando se usa la coincidencia DFA. Las ventajas y desventajas de la función alternativa, y cómo difiere de la función normal, se discuten en la página pcre2matching.

CODIGOS DE CARACTER EBCDIC

La mayoría de los ordenadores utilizan ASCII o Unicode para codificar caracteres, y PCRE2 asume esto por defecto. Sin embargo, puede ser compilado para ejecutarse en un entorno que utiliza el código EBCDIC, que es el caso de algunos sistemas operativos de mainframes de IBM. En las secciones a continuación, los valores de los códigos de caracteres son ASCII o Unicode; en un entorno EBCDIC, estos caracteres pueden tener valores de código diferentes, y no hay puntos de código mayores que 255. Las diferencias en el comportamiento cuando PCRE2 se ejecuta en un entorno EBCDIC se describen en la sección "Entornos EBCDIC" a continuación, la cual puedes ignorar a menos que realmente estés en un entorno EBCDIC.

ELEMENTOS ESPECIALES DE INICIO DE PATRON

Varias opciones que se pueden pasar a pcre2_compile() también se pueden establecer mediante elementos especiales al inicio de un patrón. Estos no son compatibles con Perl, pero se proporcionan para hacer estas opciones accesibles a los escritores de patrones que no pueden cambiar el programa que procesa el patrón. Puede aparecer cualquier número de estos elementos, pero todos deben estar juntos al principio de la cadena del patrón, y las letras deben estar en mayúsculas.

Soporte UTF

En las bibliotecas PCRE2 de 8 bits y 16 bits, los caracteres pueden ser codificados como unidades de código únicas o como múltiples unidades de código UTF-8 o UTF-16. UTF-32 puede ser especificado para la biblioteca de 32 bits, en cuyo caso restringe los valores de los caracteres a puntos de código Unicode válidos. Para procesar cadenas UTF, PCRE2 debe ser compilado para incluir soporte Unicode (que es el predeterminado). Al usar cadenas UTF, debes llamar a la función de compilación con una o ambas opciones PCRE2_UTF o PCRE2_MATCH_INVALID_UTF, o el patrón debe comenzar con la secuencia especial (*UTF), que es equivalente a establecer la PCRE2_UTF relevante. Cómo el establecimiento de un modo UTF afecta la coincidencia de patrones se menciona en varios lugares a continuación. También hay un resumen de las características en la página pcre2unicode.

Algunas aplicaciones que permiten a sus usuarios suministrar patrones pueden desear restringirlos a datos no UTF por razones de seguridad. Si la opción PCRE2_NEVER_UTF se pasa a pcre2_compile(), (*UTF) no está permitido, y su aparición en un patrón causa un error.

Soporte de propiedades Unicode

Otra secuencia especial que puede aparecer al principio de un patrón es (*UCP). Esto tiene el mismo efecto que establecer la opción PCRE2_UCP: hace que secuencias como \d y \w utilicen propiedades Unicode para determinar tipos de caracteres, en lugar de reconocer solo caracteres con códigos menores que 256 mediante una tabla de búsqueda. También hace que las operaciones de mayúsculas/minúsculas utilicen propiedades Unicode para caracteres con puntos de código mayores que 127, incluso cuando UTF no está establecido. Estos comportamientos se pueden cambiar dentro del patrón; ver la sección titulada "Establecimiento Interno de Opciones" a continuación.

Algunas aplicaciones que permiten a sus usuarios suministrar patrones pueden desear restringirlos por razones de seguridad. Si la opción PCRE2_NEVER_UCP se pasa a pcre2_compile(), (*UCP) no está permitido, y su aparición en un patrón causa un error.

Bloqueo de coincidencia de cadena vacía

Iniciar un patrón con (*NOTEMPTY) o (*NOTEMPTY_ATSTART) tiene el mismo efecto que pasar la opción PCRE2_NOTEMPTY o PCRE2_NOTEMPTY_ATSTART a la función de coincidencia que se llame posteriormente para coincidir con el patrón. Estas opciones bloquean la coincidencia de cadenas vacías, ya sea completamente, o solo al principio del sujeto.

Deshabilitacion de la auto-posesion

Si un patrón comienza con (*NO_AUTO_POSSESS), tiene el mismo efecto que establecer la opción PCRE2_NO_AUTO_POSSESS, o llamar a pcre2_set_optimize() con una directiva PCRE2_AUTO_POSSESS_OFF. Esto impide que PCRE2 haga posesivos los cuantificadores cuando lo que sigue no puede coincidir con el elemento repetido. Por ejemplo, por defecto a+b se trata como a++b. Para más detalles, ver la documentación de pcre2api.

Deshabilitacion de optimizaciones de inicio

Si un patrón comienza con (*NO_START_OPT), tiene el mismo efecto que establecer la opción PCRE2_NO_START_OPTIMIZE, o llamar a pcre2_set_optimize() con una directiva PCRE2_START_OPTIMIZE_OFF. Esto deshabilita varias optimizaciones para llegar rápidamente a resultados de "sin coincidencia". Para más detalles, ver la documentación de pcre2api.

Deshabilitacion del anclaje automatico

Si un patrón comienza con (*NO_DOTSTAR_ANCHOR), tiene el mismo efecto que establecer la opción PCRE2_NO_DOTSTAR_ANCHOR, o llamar a pcre2_set_optimize() con una directiva PCRE2_DOTSTAR_ANCHOR_OFF. Esto deshabilita optimizaciones que se aplican a patrones cuyas ramas de nivel superior comienzan todas con .* (coincidir con cualquier número de caracteres arbitrarios). Para más detalles, ver la documentación de pcre2api.

Deshabilitacion de la compilacion JIT

Si un patrón que comienza con (*NO_JIT) se compila correctamente, se ignora un intento de la aplicación de aplicar la optimización JIT llamando a pcre2_jit_compile().

Establecimiento de limites de recursos de coincidencia

La función pcre2_match() contiene un contador que se incrementa cada vez que entra en su bucle principal. El llamante de pcre2_match() puede establecer un límite en este contador, lo que por lo tanto limita la cantidad de recursos informáticos utilizados para una coincidencia. La profundidad máxima de retroceso anidado también puede ser limitada; esto restringe indirectamente la cantidad de memoria de montón que se utiliza, pero también hay un límite de memoria explícito que se puede establecer.

Estas facilidades se proporcionan para detectar coincidencias descontroladas que son provocadas por patrones con enormes árboles de coincidencia. Un ejemplo común es un patrón con repeticiones anidadas ilimitadas aplicadas a una cadena larga que no coincide. Cuando se alcanza uno de estos límites, pcre2_match() devuelve un error. (*LIMIT_DEPTH=d)

CONFIGURACIÓN

A través de la interfaz de configuración, los límites para la profundidad de la recursión, la longitud de la cadena y la memoria utilizada por las expresiones regulares se pueden establecer a un nivel inferior al establecido por el programador en la llamada a la función. En otras palabras, el escritor del patrón puede rebajar los límites establecidos por el programador, pero no aumentarlos. Si existe más de un ajuste para uno de estos límites, se utiliza el valor inferior. El límite de memoria se especifica en kibibytes (unidades de 1024 bytes).

Antes de la versión 10.30, LIMIT_DEPTH se llamaba LIMIT_RECURSION. Este nombre todavía se reconoce por motivos de compatibilidad.

El límite de memoria solo se aplica cuando se utilizan los intérpretes pcre2_match() o pcre2_dfa_match() para la coincidencia. No se aplica a JIT. El límite de coincidencia se utiliza (pero de forma diferente) cuando se utiliza JIT, o cuando se llama a pcre2_dfa_match(), para limitar el uso de recursos informáticos por parte de estas funciones de coincidencia. El límite de profundidad es ignorado por JIT pero es relevante para la coincidencia DFA, que utiliza recursión de funciones para recursiones dentro del patrón y para aserciones de lookaround y grupos atómicos. En este caso, el límite de profundidad controla la profundidad de dicha recursión.

Convenciones de saltos de línea

PCRE2 admite seis convenciones diferentes para indicar saltos de línea en cadenas: un único carácter CR (retorno de carro), un único carácter LF (avance de línea), la secuencia de dos caracteres CRLF, cualquiera de los tres anteriores, cualquier secuencia Unicode de salto de línea o el carácter NUL (cero binario). La página pcre2api contiene más información sobre los saltos de línea y muestra cómo establecer la convención de saltos de línea al llamar a pcre2_compile().

También es posible especificar una convención de saltos de línea comenzando una cadena de patrón con una de las siguientes secuencias:


(*CR) retorno de carro
(*LF) avance de línea
(*CRLF) retorno de carro, seguido de avance de línea
(*ANYCRLF) cualquiera de los tres anteriores
(*ANY) todas las secuencias Unicode de salto de línea
(*NUL) el carácter NUL (cero binario)

Estos anulan el valor predeterminado y las opciones dadas a la función de compilación. Por ejemplo, en un sistema Unix donde LF es la secuencia de salto de línea predeterminada, el patrón


(*CR)a.b

cambia la convención a CR. Ese patrón coincide con "a\nb" porque LF ya no es un salto de línea. Si hay más de uno de estos ajustes, se utiliza el último.

La convención de saltos de línea afecta a dónde son verdaderas las aserción de circunflejo y dólar. También afecta la interpretación del metacaracter punto cuando no está establecido PCRE2_DOTALL, y el comportamiento de \N cuando no va seguido de una llave de apertura. Sin embargo, no afecta a qué coincide la secuencia de escape \R. Por defecto, esta es cualquier secuencia de salto de línea Unicode, para compatibilidad con Perl. Sin embargo, esto se puede cambiar; véase la siguiente sección y la descripción de \R en la sección titulada "Secuencias de saltos de línea" más abajo. Un cambio en el ajuste de \R se puede combinar con un cambio en la convención de saltos de línea.

Especificar lo que coincide \R

Es posible restringir \R para que coincida solo con CR, LF o CRLF (en lugar del conjunto completo de finales de línea Unicode) estableciendo la opción PCRE2_BSR_ANYCRLF en tiempo de compilación. Este efecto también se puede lograr comenzando un patrón con (*BSR_ANYCRLF). Para mayor exhaustividad, también se reconoce (*BSR_UNICODE), que corresponde a PCRE2_BSR_UNICODE.

CARACTERES Y METACARACTERES

Una expresión regular es un patrón que se compara con una cadena sujeto de izquierda a derecha. La mayoría de los caracteres se representan a sí mismos en un patrón y coinciden con los caracteres correspondientes en el sujeto. Como ejemplo trivial, el patrón


El rápido zorro marrón

coincide con una porción de una cadena sujeto que es idéntica a sí misma. Cuando se especifica coincidencia sin distinción entre mayúsculas y minúsculas (la opción PCRE2_CASELESS o (?i) dentro del patrón), las letras se comparan independientemente de su caso. Tenga en cuenta que hay dos caracteres ASCII, K y S, que, además de sus equivalentes ASCII en minúsculas, son equivalentes en mayúsculas con Unicode U+212A (signo Kelvin) y U+017F (ese larga) respectivamente cuando se establece PCRE2_UTF o PCRE2_UCP, a menos que la opción PCRE2_EXTRA_CASELESS_RESTRICT esté en vigor (ya sea pasada a pcre2_compile() o establecida por (*CASELESS_RESTRICT) o (?r) dentro del patrón). Si la opción PCRE2_EXTRA_TURKISH_CASING está en vigor (ya sea pasada a pcre2_compile() o establecida por (*TURKISH_CASING) dentro del patrón), entonces las letras 'i' se comparan según los idiomas turco y azerí.

El poder de las expresiones regulares proviene de la capacidad de incluir comodines, clases de caracteres, alternativas y repeticiones en el patrón. Estos se codifican en el patrón mediante el uso de metacaracteres, que no se representan a sí mismos sino que se interpretan de alguna manera especial.

Hay dos conjuntos diferentes de metacaracteres: los que se reconocen en cualquier lugar del patrón excepto dentro de corchetes, y los que se reconocen dentro de corchetes. Fuera de los corchetes, los metacaracteres son los siguientes:


\ carácter de escape general con varios usos
^ aserta el inicio de la cadena (o línea, en modo multilínea)
$ aserta el final de la cadena (o línea, en modo multilínea)
. coincide con cualquier carácter excepto salto de línea (por defecto)
[ inicio de la definición de clase de caracteres
| inicio de rama alternativa
( inicio de grupo o verbo de control
) fin de grupo o verbo de control
* 0 o más cuantificador
+ 1 o más cuantificador; también "cuantificador posesivo"
? 0 o 1 cuantificador; también minimizador de cuantificador
{ inicio potencial de cuantificador min/max

Los caracteres de llave { y } también se utilizan para encerrar datos para construcciones como \g{2} o \k{nombre}. En casi todos los usos de llaves, los espacios en blanco y/o tabulaciones horizontales que siguen a { o preceden a } están permitidos y se ignoran. En el caso de los cuantificadores, también pueden aparecer antes o después de la coma. La excepción a esto es \u{...} que es una característica de compatibilidad con ECMAScript que solo se reconoce cuando se establece la opción PCRE2_EXTRA_ALT_BSUX. ECMAScript no ignora dichos espacios en blanco; hace que el elemento se interprete como literal.

Parte de un patrón que está entre corchetes se llama "clase de caracteres". En una clase de caracteres, los únicos metacaracteres son:


\ carácter de escape general
^ niega la clase, pero solo si es el primer carácter
- indica rango de caracteres
[ clase de caracteres POSIX (si va seguida de sintaxis POSIX)
] termina la clase de caracteres

Si un patrón se compila con la opción PCRE2_EXTENDED, la mayoría de los espacios en blanco en el patrón, que no estén en una clase de caracteres, dentro de una secuencia \Q...\E, o entre un # fuera de una clase de caracteres y el siguiente salto de línea, inclusive, se ignoran. Se puede usar una barra invertida de escape para incluir un carácter de espacio en blanco o un carácter # como parte del patrón. Si se establece la opción PCRE2_EXTENDED_MORE, se aplica lo mismo, pero además los caracteres de espacio y tabulación horizontal sin escapar se ignoran dentro de una clase de caracteres. Nota: solo estos dos caracteres se ignoran, no el conjunto completo de caracteres de espacio en blanco del patrón que se ignoran fuera de una clase de caracteres. La configuración de opciones se puede cambiar dentro de un patrón; véase la sección titulada "Configuración interna de opciones" más abajo.

Las siguientes secciones describen el uso de cada uno de los metacaracteres.

BARRA INVERTIDA

El carácter de barra invertida tiene varios usos. En primer lugar, si va seguido de un carácter que no es un dígito ni una letra, elimina cualquier significado especial que dicho carácter pueda tener. Este uso de la barra invertida como carácter de escape se aplica tanto dentro como fuera de las clases de caracteres.

Por ejemplo, si desea buscar un carácter *, debe escribir \* en el patrón. Esta acción de escape se aplica independientemente de si el carácter siguiente se interpretaría de otro modo como un metacaracter, por lo que siempre es seguro preceder un carácter no alfanumérico con una barra invertida para especificar que representa sí mismo. En particular, si desea buscar una barra invertida, escriba \\.

Solo los dígitos y letras ASCII tienen algún significado especial después de una barra invertida. Todos los demás caracteres (en particular, aquellos cuyos puntos de código son mayores que 127) se tratan como literales.

Si desea tratar todos los caracteres de una secuencia como literales, puede hacerlo poniéndolos entre \Q y \E. Tenga en cuenta que esto incluye los espacios en blanco incluso cuando la opción PCRE2_EXTENDED está establecida, de modo que la mayoría de los otros espacios en blanco se ignoran. El comportamiento es diferente al de Perl, ya que $ y @ se manejan como literales en secuencias \Q...\E en PCRE2, mientras que en Perl, $ y @ causan la interpolación de variables. Además, Perl realiza la "interpolación de barra invertida tipo comillas dobles" en cualquier barra invertida entre \Q y \E, lo que, según su documentación, "puede llevar a resultados confusos". PCRE2 trata una barra invertida entre \Q y \E igual que cualquier otro carácter. Tenga en cuenta los siguientes ejemplos:


Patrón PCRE2 coincide Perl coincide


\Qabc$xyz\E abc$xyz abc seguido del
contenido de $xyz
\Qabc\$xyz\E abc\$xyz abc\$xyz
\Qabc\E\$\Qxyz\E abc$xyz abc$xyz
\QA\B\E A\B A\B
\Q\\E \ \\E

La secuencia \Q...\E se reconoce tanto dentro como fuera de las clases de caracteres. Una \E aislada que no va precedida de \Q se ignora. Si \Q no va seguido de \E más adelante en el patrón, la interpretación literal continúa hasta el final del patrón (es decir, se asume \E al final). Si la \Q aislada está dentro de una clase de caracteres, esto provoca un error, ya que la clase de caracteres no se termina con un corchete de cierre.

Otra diferencia con Perl es que cualquier aparición de \Q o \E dentro de lo que de otro modo podría ser un cuantificador hace que PCRE2 no reconozca la secuencia como un cuantificador. Perl reconoce un cuantificador si (redundantemente) cualquiera de los números está dentro de \Q...\E, pero no si la coma separadora lo está. Cuando no se reconoce como cuantificador, una secuencia como {\Q1\E,2} se trata como la cadena literal "{1,2}".

Caracteres no imprimibles

Un segundo uso de la barra invertida proporciona una forma de codificar caracteres no imprimibles en patrones de manera visible. No hay restricción en la aparición de caracteres no imprimibles en un patrón, pero cuando un patrón se está preparando mediante edición de texto, a menudo es más fácil usar una de las siguientes secuencias de escape en lugar del carácter binario que representan. En un entorno ASCII o Unicode, estas escapes son las siguientes:


\a alarma, es decir, el carácter BEL (hex 07)
\cx "control-x", donde x es un carácter ASCII de control
\e escape (hex 1B)
\f avance de página (hex 0C)

ESCAPES

The following special sequences can be used in patterns:


\n avance de línea (hex 0A)
\r retorno de carro (hex 0D) (pero véase abajo)
\t tabulación (hex 09)
\0dd carácter con código octal 0dd
\ddd carácter con código octal ddd, o referencia inversa
\o{ddd..} carácter con código octal ddd..
\xhh carácter con código hexadecimal hh
\x{hhh..} carácter con código hexadecimal hhh..
\N{U+hhh..} carácter con código hexadecimal Unicode hhh..

La descripción de cómo funcionan las referencias inversas se da más adelante, siguiendo la discusión de los grupos entre paréntesis.

Por defecto, después de \x que no va seguido de {, se leen uno o dos dígitos hexadecimales (las letras pueden ser mayúsculas o minúsculas). Si el carácter que sigue a \x no es ni { ni un dígito hexadecimal, se produce un error. Esto es diferente del comportamiento predeterminado de Perl, que genera un carácter NUL, pero está en línea con el comportamiento del modo 'strict' de Perl en expresiones regulares.

Puede aparecer cualquier número de dígitos hexadecimales entre \x{ y }. Si aparece un carácter que no sea un dígito hexadecimal entre \x{ y }, o si no hay un final con }, se produce un error.

Los caracteres cuyos puntos de código son menores que 256 pueden definirse por cualquiera de las dos sintaxis para \x o por una secuencia octal. No hay diferencia en la forma en que se manejan. Por ejemplo, \xdc es exactamente lo mismo que \x{dc} o \334. Sin embargo, el uso de las versiones entre llaves facilita la lectura de dichas secuencias.

Se dispone de soporte para algunas secuencias de escape de ECMAScript (también conocido como JavaScript) a través de dos opciones de tiempo de compilación. Si PCRE2_ALT_BSUX está establecido, la secuencia \x seguida de { no se reconoce. Solo si \x va seguido de dos dígitos hexadecimales se reconoce como un escape de carácter. De lo contrario, se interpreta como un carácter literal "x". En este modo, el soporte para puntos de código mayores que 256 se proporciona mediante \u, que debe ir seguido de cuatro dígitos hexadecimales; de lo contrario, se interpreta como un carácter literal "u".

PCRE2_EXTRA_ALT_BSUX tiene el mismo efecto que PCRE2_ALT_BSUX y, además, \u{hhh..} se reconoce como el carácter especificado por el punto de código hexadecimal. Puede haber cualquier número de dígitos hexadecimales, pero a diferencia de otros lugares que también usan llaves, los espacios no están permitidos y darían lugar a que la cadena se interpretara como literal. Esta sintaxis es de ECMAScript 6.

La secuencia de escape \N{U+hhh..} se reconoce solo cuando PCRE2 está operando en modo UTF. Perl también usa \N{nombre} para especificar caracteres por nombre Unicode; PCRE2 no soporta esto. Nótese que cuando \N no va seguido de una llave de apertura (corchete), tiene un significado completamente diferente, coincidiendo con cualquier carácter que no sea una nueva línea.

Hay algunas aplicaciones heredadas donde se espera que la secuencia de escape \r coincida con una nueva línea. Si la opción PCRE2_EXTRA_ESCAPED_CR_IS_LF está establecida, \r en un patrón se convierte a \n para que coincida con un carácter LF (avance de línea) en lugar de un carácter CR (retorno de carro).

Se produce un error si \c no va seguido de un carácter cuyo punto de código ASCII esté en el rango de 32 a 126. El efecto preciso de \cx es el siguiente: si x es una letra minúscula, se convierte a mayúscula. Luego, el bit 6 del carácter (hex 40) se invierte. Por lo tanto, \cA a \cZ se convierten en hex 01 a hex 1A (A es 41, Z es 5A), pero \c{ se convierte en hex 3B ({ es 7B), y \c; se convierte en hex 7B (; es 3B). Si la unidad de código que sigue a \c tiene un punto de código menor que 32 o mayor que 126, se produce un error de compilación.

Para diferencias en la forma en que algunos escapes se comportan en entornos EBCDIC, consulte la sección "Entornos EBCDIC" más abajo.

Escapes octales y referencias inversas

El escape \o debe ir seguido de una secuencia de dígitos octales, encerrados entre llaves. Se produce un error si no es así. Este escape proporciona una forma de especificar puntos de código de caracteres como números octales mayores que 0777, y también permite distinguir inequívocamente números octales y referencias inversas.

Si no se usan llaves, después de \0 se leen hasta dos dígitos octales adicionales. Sin embargo, si PCRE2_EXTRA_NO_BS0 está establecido, al menos un dígito octal más debe seguir a \0 (use \00 para generar un carácter NUL). Asegúrese de suministrar dos dígitos después del cero inicial si el carácter del patrón que sigue es en sí mismo un dígito octal.

Dentro de una clase de caracteres, cuando una barra invertida va seguida de cualquier dígito octal, se leen hasta tres dígitos octales para generar un punto de código. Cualquier dígito subsiguiente se interpreta como sí mismo. Las secuencias \8 y \9 se tratan como los caracteres literales "8" y "9".

Secuencias de escape en clases de caracteres

Todas las secuencias que definen un único valor de carácter se pueden usar tanto dentro como fuera de las clases de caracteres. Además, dentro de una clase de caracteres, \b se interpreta como el carácter de retroceso (hex 08).

Secuencias de escape no soportadas

En Perl, las secuencias \F, \l, \L, \u y \U son reconocidas por su manejador de cadenas y se usan para modificar la capitalización de los caracteres siguientes. La secuencia \g seguida de un número con signo o sin signo, opcionalmente encerrado entre llaves, es una referencia inversa absoluta o relativa. Clusters grafemáticos extendidos

El escape \X coincide con cualquier número de caracteres Unicode que forman un "cluster grafemático extendido", y trata la secuencia como un grupo atómico (ver más abajo). Unicode admite varios tipos de caracteres compuestos al dar a cada carácter una propiedad de quiebre de grafemas y tener reglas que utilizan estas propiedades para definir los límites de los clusters grafemáticos extendidos. Las reglas se definen en el Anexo de Estándares Unicode 29, "Segmentación de Texto Unicode". Unicode 11.0.0 abandonó el uso de algunas propiedades anteriores que se habían utilizado para emojis. En su lugar, introdujo varias propiedades específicas de emojis. PCRE2 utiliza solo la propiedad Pictographic Extendida.

\X siempre coincide con al menos un carácter. Luego, decide si añadir caracteres adicionales de acuerdo con las siguientes reglas para finalizar un cluster:

1. Terminar al final de la cadena del sujeto.

2. No terminar entre CR y LF; de lo contrario, terminar después de cualquier carácter de control.

3. No interrumpir secuencias de sílabas Hangul (un guión coreano). Los caracteres Hangul son de cinco tipos: L, V, T, LV y LVT. Un carácter L puede ser seguido por un carácter L, V, LV o LVT; un carácter LV o V puede ser seguido por un carácter V o T; un carácter LVT o T solo puede ser seguido por un carácter T.

4. No terminar antes de caracteres de extensión, marcas espaciadoras o el carácter de unión de ancho cero (ZWJ). Los caracteres con la propiedad "mark" (marca) siempre tienen la propiedad de quiebre de grafema "extend" (extender).

5. No terminar después de caracteres de pre-adjunto.

6. No terminar dentro de secuencias de modificadores de emoji o secuencias ZWJ (unión de ancho cero) de emoji. Una secuencia ZWJ de emoji consiste en un carácter con la propiedad Extended_Pictographic, seguido opcionalmente por uno o más caracteres con la propiedad Extend, seguido por el carácter ZWJ, seguido por otro carácter Extended_Pictographic.

7. No interrumpir secuencias de banderas de emoji. Es decir, no interrumpir entre caracteres indicadores regionales (RI) si hay un número impar de caracteres RI antes del punto de quiebre.

8. De lo contrario, finalizar el cluster.

Restableciendo el inicio de la coincidencia

En uso normal, la secuencia de escape \K hace que cualquier carácter previamente coincidente no se incluya en la secuencia coincidente final que se devuelve. Por ejemplo, el patrón:


foo\Kbar

coincide con "foobar", pero informa que ha coincidido con "bar". \K no interactúa con los anclajes de ninguna manera. El patrón:


^foo\Kbar

coincide solo cuando el sujeto comienza con "foobar" (en modo de una sola línea), aunque nuevamente informa la cadena coincidente como "bar". Esta característica es similar a una aserción de búsqueda previa (descrita a continuación), pero la parte del patrón que precede a \K no está limitada a coincidir con un número limitado de caracteres, como se requiere para una aserción de búsqueda previa. El uso de \K no interfiere con la configuración de las subcadenas capturadas. Por ejemplo, cuando el patrón


(foo)\Kbar

coincide con "foobar", la primera subcadena todavía se establece en "foo".

A partir de la versión 5.32.0, Perl prohíbe el uso de \K en aserciónes de búsqueda (lookaround). A partir de la versión 10.38, PCRE2 también lo prohíbe por defecto. Sin embargo, la opción PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK puede usarse al llamar a pcre2_compile() para volver a habilitar el comportamiento anterior. Cuando se establece esta opción, \K se actúa sobre cuando ocurre dentro de aserciónes positivas, pero se ignora en aserciónes negativas. Tenga en cuenta que cuando un patrón como (?=ab\K) coincide, el inicio reportado de la coincidencia puede ser mayor que el final de la coincidencia. OFFSET AND LENGTH OF MATCH

The starting offset of a match is the offset of the first character in the substring that matched the pattern. The length of the match is the number of characters in that substring. For example, if the pattern is foo and the subject is foobar, the match starts at offset 0 and has length 3.

If a pattern contains capturing groups, the offsets and lengths of the substrings captured by these groups can also be returned. For example, if the pattern is f(o+)b(ar) and the subject is foooobar, there are three captured substrings: "ooo" (starting at offset 1, length 3), and "ar" (starting at offset 5, length 2). The entire match is "foooobar" (starting at offset 0, length 8).

It is possible for a match to have zero length. This occurs when the pattern matches a position but not any characters. For example, the pattern ^ matches the start of the string, which is a zero-length match at offset 0. Similarly, the pattern \b matches a word boundary, which is a zero-length match. If the pattern is b* and the subject is a, the match is the empty string starting at offset 0.

A zero-length match can occur anywhere in the string. For example, in the string abc, the pattern b? matches the empty string at offset 1. The function pcre2_match() will return the offset of the start of the match. If the match is zero-length, the reported offset might be *later* than the actual start of the match. For example, if pcre2_match() is called with a starting offset of 3 on the subject foobar and a pattern of bar, the match occurs starting at offset 3. If the pattern is foobar and the starting offset is 3, the function pcre2_match() succeeds and reports the matching string as "foobar", that is, the start of the reported match is earlier than where the match started.

Assertions simple

El último uso de la barra invertida es para ciertas aserciones simples. Una aserción especifica una condición que debe cumplirse en un punto particular de una coincidencia, sin consumir ningún carácter de la cadena sujeto. El uso de grupos para aserciones más complicadas se describe a continuación. Las aserciones con barra invertida son:


\b coincide en un límite de palabra
\B coincide cuando no está en un límite de palabra
\A coincide al principio del sujeto
\Z coincide al final del sujeto
también coincide antes de una nueva línea al final del sujeto
\z coincide solo al final del sujeto
\G coincide en la primera posición de coincidencia en el sujeto

Dentro de una clase de caracteres, \b tiene un significado diferente; coincide con el carácter de retroceso (backspace). Si alguna otra de estas aserciones aparece en una clase de caracteres, se genera un error de "secuencia de escape inválida".

Un límite de palabra es una posición en la cadena sujeto donde el carácter actual y el carácter anterior no coinciden ambos con \w o \W (es decir, uno coincide con \w y el otro con \W), o el inicio o el final de la cadena si el primer o último carácter coincide con \w, respectivamente. Cuando PCRE2 se compila con soporte Unicode, los significados de \w y \W pueden cambiar al establecer la opción PCRE2_UCP. Cuando esto se hace, también afecta a \b y \B. Ni PCRE2 ni Perl tienen una meta-secuencia separada de "inicio de palabra" o "fin de palabra". Sin embargo, lo que sigue a \b normalmente determina cuál es. Por ejemplo, el fragmento \ba coincide con "a" al principio de una palabra.

Las aserciones \A, \Z y \z difieren de las comillas simples y el signo de dólar tradicionales (descritos en la siguiente sección) en que solo coinciden al principio y al final de la cadena sujeto, independientemente de las opciones establecidas. Por lo tanto, son independientes del modo multilínea. Estas tres aserciones no se ven afectadas por las opciones PCRE2_NOTBOL o PCRE2_NOTEOL, que solo afectan al comportamiento de los meta-caracteres de comillas simples y signo de dólar. Sin embargo, si el argumento *startoffset* de pcre2_match() es distinto de cero, lo que indica que la coincidencia debe comenzar en un punto distinto del principio del sujeto, \A nunca puede coincidir. La diferencia entre \Z y \z es que \Z coincide antes de una nueva línea al final de la cadena así como al final mismo, mientras que \z coincide solo al final.

La aserción \G es verdadera solo cuando la posición de coincidencia actual está en el punto de inicio del proceso de coincidencia, según lo especificado por el argumento *startoffset* de pcre2_match(). Difiere de \A cuando el valor de *startoffset* es distinto de cero. Al llamar a pcre2_match() varias veces con argumentos apropiados, puede imitar la opción /g de Perl, y es en este tipo de implementación donde \G puede ser útil.

Tenga en cuenta, sin embargo, que la implementación de \G de PCRE2, al ser verdadera en el carácter de inicio del proceso de coincidencia, es sutilmente diferente de la de Perl, que la define como verdadera al final de la coincidencia anterior. En Perl, estos pueden ser diferentes cuando la cadena previamente coincidente estaba vacía. Dado que PCRE2 realiza una sola coincidencia a la vez, no puede reproducir este comportamiento.

Si todas las alternativas de un patrón comienzan con \G, la expresión está anclada a la posición de coincidencia de inicio, y el indicador "anclado" se establece en la expresión regular compilada.

CIRCUNFLEJO Y DÓLAR

Los meta-caracteres de circunflejo y dólar son aserciones de ancho cero. Es decir, prueban si una condición particular es verdadera sin consumir ningún carácter de la cadena sujeto. Estos dos meta-caracteres se ocupan de hacer coincidir los inicios y finales de las líneas. Si la convención de nueva línea se establece de modo que solo la secuencia de dos caracteres CRLF se reconozca como nueva línea, los caracteres CR y LF aislados se tratan como caracteres de datos ordinarios y no se reconocen como nuevas líneas.

Fuera de una clase de caracteres, en el modo de coincidencia predeterminado, el carácter de circunflejo es una aserción que solo es verdadera si el punto de coincidencia actual está al principio de la cadena sujeto. Si el argumento *startoffset* de pcre2_match() es distinto de cero, o si se establece PCRE2_NOTBOL, el circunflejo nunca puede coincidir si la opción PCRE2_MULTILINE no está establecida. Dentro de una clase de caracteres, el circunflejo tiene un significado completamente diferente (ver más abajo).

El circunflejo no necesita ser el primer carácter del patrón si hay varias alternativas involucradas, pero debe ser lo primero en cada alternativa en la que aparezca si el patrón alguna vez debe coincidir con esa rama. Si todas las alternativas posibles comienzan con un circunflejo, es decir, si el patrón está restringido a coincidir solo al principio del sujeto, se dice que es un patrón "anclado". (También hay otras construcciones que pueden hacer que un patrón esté anclado).

El carácter de dólar es una aserción que solo es verdadera si el punto de coincidencia actual está al final de la cadena sujeto, o inmediatamente antes de una nueva línea al final de la cadena (por defecto), a menos que se establezca PCRE2_NOTEOL. Tenga en cuenta, sin embargo, que en realidad no coincide con la nueva línea. El dólar no necesita ser el último carácter del patrón si hay varias alternativas involucradas, pero debe ser el último elemento en cualquier rama en la que aparezca. El dólar no tiene ningún significado especial en una clase de caracteres.

El significado del dólar se puede cambiar para que coincida solo al final de la cadena, estableciendo la opción PCRE2_DOLLAR_ENDONLY en tiempo de compilación. Esto no afecta a la aserción \Z.

Los significados de los meta-caracteres de circunflejo y dólar se cambian si se establece la opción PCRE2_MULTILINE. Cuando esto ocurre, un carácter de dólar coincide antes de cualquier nueva línea en la cadena, así como al final mismo, y un circunflejo coincide inmediatamente después de las nuevas líneas internas, así como al principio de la cadena sujeto. No coincide después de una nueva línea que termina la cadena, por compatibilidad con Perl. Sin embargo, esto puede cambiarse estableciendo la opción PCRE2_ALT_CIRCUMFLEX.

Por ejemplo, el patrón /^abc$/ coincide con la cadena sujeto "def\nabc" (donde \n representa una nueva línea) en modo multilínea, pero no de lo contrario. En consecuencia, los patrones que están anclados en modo de línea única porque todas las ramas comienzan con ^ no están anclados en modo multilínea, y es posible una coincidencia para el circunflejo cuando el argumento *startoffset* de pcre2_match() es distinto de cero. La opción PCRE2_DOLLAR_ENDONLY se ignora si se establece PCRE2_MULTILINE.

Cuando la convención de nueva línea (ver "Convenciones de nueva línea" a continuación) reconoce la secuencia de dos caracteres CRLF como nueva línea, esta se prefiere, incluso si los caracteres individuales CR y LF también se reconocen como nuevas líneas. Por ejemplo, si la convención de nueva línea es "cualquiera", un circunflejo en modo multilínea coincide antes de "xyz" en la cadena "abc\r\nxyz" en lugar de después de CR, aunque CR por sí solo sea una nueva línea válida. (También coincide al principio mismo de la cadena, por supuesto).

Tenga en cuenta que las secuencias \A, \Z y \z se pueden usar para coincidir con el principio y el final del sujeto en ambos modos, y si todas las ramas de un patrón comienzan con \A, siempre está anclado, independientemente de si se establece PCRE2_MULTILINE o no.

PUNTO SEGUIDO (PUNTO, COMA) Y \N

Fuera de una clase de caracteres, un punto en el patrón coincide con cualquier carácter individual en la cadena sujeto excepto (por defecto) un carácter que signifique fin de línea. Se pueden especificar uno o más caracteres como terminadores de línea (ver "Convenciones de nueva línea" arriba).

El punto nunca coincide con un carácter individual de fin de línea. Cuando la secuencia de dos caracteres CRLF es el único fin de línea, el punto no coincide con CR si le sigue inmediatamente LF, pero de lo contrario coincide con todos los caracteres (incluidos CR y LF aislados). Cuando se selecciona ANYCRLF para los finales de línea, ninguna ocurrencia de CR o LF coincide con el punto. Cuando se reconocen todos los finales de línea Unicode, el punto no coincide con CR o LF ni con ningún otro carácter de fin de línea.

El comportamiento del punto con respecto a las nuevas líneas puede cambiarse. Si se establece la opción PCRE2_DOTALL, un punto coincide con cualquier carácter individual, sin excepción. Si la secuencia de dos caracteres CRLF está presente en la cadena sujeto, se necesitan dos puntos para que coincida.

El manejo del punto es completamente independiente del manejo del circunflejo y el dólar, la única relación es que ambos involucran nuevas líneas. El punto no tiene significado especial en una clase de caracteres.

La secuencia de escape \N cuando no va seguida de una llave de apertura se comporta como un punto, excepto que no se ve afectada por la opción PCRE2_DOTALL. En otras palabras, coincide con cualquier carácter excepto uno que signifique fin de línea.

Cuando \N va seguida de una llave de apertura, tiene un significado diferente. Consulte la sección titulada "Caracteres no imprimibles" anterior para obtener detalles. Perl también usa \N{nombre} para especificar caracteres por nombre Unicode; PCRE2 no soporta esto.

COINCIDIR UNA SOLA UNIDAD DE CÓDIGO

Fuera de una clase de caracteres, la secuencia de escape \C coincide con cualquier unidad de código individual, independientemente de si se establece un modo UTF o no. En la biblioteca de 8 bits, una unidad de código es un byte; en la biblioteca de 16 bits es una unidad de 16 bits; en la biblioteca de 32 bits es una unidad de 32 bits. A diferencia de un punto, \C siempre coincide con los caracteres de fin de línea. La característica se proporciona en Perl para hacer coincidir bytes individuales en modo UTF-8, pero no está claro cómo se puede utilizar de forma útil.

Debido a que \C rompe los caracteres en unidades de código individuales, hacer coincidir una unidad con \C en modo UTF-8 o UTF-16 significa que el resto de la cadena puede comenzar con un carácter UTF mal formado. Esto tiene resultados indefinidos, porque PCRE2 asume que está haciendo coincidir carácter por carácter en una cadena UTF válida (por defecto, comprueba la validez de la cadena sujeto al inicio del procesamiento, a menos que se utilice la opción PCRE2_NO_UTF_CHECK o PCRE2_MATCH_INVALID_UTF).

Una aplicación puede bloquear el uso de \C estableciendo la opción PCRE2_NEVER_BACKSLASH_C al compilar un patrón. También es posible compilar PCRE2 con el uso de \C deshabilitado permanentemente.

PCRE2 no permite que \C aparezca en aserciones lookbehind (descritas a continuación) en modos UTF-8 o UTF-16, porque esto haría imposible calcular la longitud del lookbehind. Ni la función de coincidencia alternativa pcre2_dfa_match() ni el optimizador JIT soportan \C en estos modos UTF. La primera genera un error en tiempo de coincidencia; la segunda no optimiza y, por lo tanto, la coincidencia siempre se ejecuta utilizando el intérprete.

La yuxtaposición es el operador de unión implícito y se une más fuertemente que cualquier operador explícito. Por lo tanto, una secuencia de literales y/o rangos se comporta como si estuviera encerrada entre corchetes. Por ejemplo, [A-Z0-9&&[^E8]] es lo mismo que [[A-Z0-9]&&[^E8]], que coincide con cualquier carácter alfanumérico en mayúsculas, excepto "E" o "8".

La precedencia entre los operadores explícitos no está definida, por lo que mezclar operadores es un error de sintaxis. Por ejemplo, [A&&B--C] es un error, pero [A&&[B--C]] es válido.

Esta es una sintaxis emergente que se está adoptando gradualmente en el ecosistema de expresiones regulares: por ejemplo, JavaScript adoptó la bandera "/v" en ECMAScript 2024; el módulo "re" de Python reserva la sintaxis para uso futuro con un FutureWarning para el uso sin escapar de "[" como literal dentro de las clases de caracteres. Debido a que UTS#18 proporciona una orientación insuficiente, los motores interpretan la sintaxis de manera diferente. El crate "regex" de Rust y el módulo PyPi "regex" de Python implementan clases extendidas UTS#18, pero con ligeras incompatibilidades ([A||B&&C] se analiza como [A||[B&&C]] en "regex" de Python, pero como [[A||B]&&C] en "regex" de Rust).

La sintaxis de PCRE2 añade restricciones sintácticas similares al indicador /v de ECMAScript, de modo que todas las clases extendidas UTS#18 aceptadas como válidas por PCRE2 tienen la propiedad de que se interpretan con el mismo comportamiento, o como inválidas, por todos los demás motores principales. Por favor, envíe un informe de error si conoce diferencias de comportamiento entre motores en PCRE2 y otro motor principal.

CLASES DE CARACTERES POSIX

Perl admite la notación POSIX para clases de caracteres. Esta utiliza nombres encerrados entre [: y :] dentro de los corchetes de cierre. PCRE2 también admite esta notación, tanto en clases ordinarias como extendidas. Por ejemplo,


[01[:alpha:]%]

coincide con "0", "1", cualquier carácter alfabético o "%". Los nombres de clase admitidos son:


alnum letras y dígitos
alpha letras
ascii códigos de caracteres 0 - 127
blank espacio o tabulación solamente
cntrl caracteres de control
digit dígitos decimales (igual que \d)
graph caracteres de impresión, excluyendo el espacio
lower letras minúsculas
print caracteres de impresión, incluyendo el espacio
punct caracteres de impresión, excluyendo letras y dígitos y espacio
space espacio en blanco (igual que \s desde PCRE2 8.34)
upper letras mayúsculas
word caracteres de "palabra" (igual que \w)
xdigit dígitos hexadecimales

Los caracteres de "espacio en blanco" predeterminados son HT (9), LF (10), VT (11), FF (12), CR (13) y espacio (32). Si se está realizando una coincidencia específica de la configuración regional, la lista de caracteres de espacio en blanco puede ser diferente; puede haber menos o más de ellos. "Space" y \s coinciden con el mismo conjunto de caracteres, al igual que "word" y \w.

El nombre "word" es una extensión de Perl, y "blank" es una extensión de GNU de Perl 5.8. Otra extensión de Perl es la negación, que se indica con un carácter ^ después de los dos puntos. Por ejemplo,


[12[:^digit:]]

coincide con "1", "2" o cualquier carácter que no sea un dígito. PCRE2 (y Perl) también reconocen la sintaxis POSIX [.ch.] y [=ch=] donde "ch" es un "elemento de ordenación", pero estos no son compatibles y se produce un error si se encuentran.

Por defecto, los caracteres con valores mayores que 127 no coinciden con ninguna de las clases de caracteres POSIX, aunque esto puede ser diferente para los caracteres en el rango 128-255 cuando se está realizando una coincidencia específica de la configuración regional. Sin embargo, en modo UCP, a menos que se establezcan ciertas opciones (ver abajo), algunas de las clases se modifican para que se utilicen propiedades de caracteres Unicode. Esto se logra reemplazando las clases POSIX con otras secuencias, como sigue:


[:alnum:] se convierte en \p{Xan}
[:alpha:] se convierte en \p{L}
[:blank:] se convierte en \h
[:cntrl:] se convierte en \p{Cc}
[:digit:] se convierte en \p{Nd}
[:lower:] se convierte en \p{Ll}
[:space:] se convierte en \p{Xps}
[:upper:] se convierte en \p{Lu}
[:word:] se convierte en \p{Xwd}

Las versiones negadas, como [:^alpha:], usan \P en lugar de \p. Otras cuatro clases POSIX se manejan de forma especial en modo UCP:

[:graph:]
Esto coincide con caracteres que tienen glifos que marcan la página al imprimirse. En términos de propiedades Unicode, coincide con todos los caracteres con las propiedades L, M, N, P, S o Cf, excepto:


U+061C Marca de letra árabe
U+180E Separador de vocales mongolas
U+2066 - U+2069 Varios "aislamientos"

[:print:]
Esto coincide con los mismos caracteres que [:graph:] más los caracteres de espacio en blanco que no son de control, es decir, caracteres con la propiedad Zs.
[:punct:]
Esto coincide con todos los caracteres que tienen la propiedad P (puntuación) de Unicode, más aquellos caracteres con puntos de código inferiores a 256 que tienen la propiedad S (Símbolo).
[:xdigit:]
Además de los dígitos hexadecimales ASCII, esto también coincide con las versiones "de ancho completo" de esos caracteres, cuyos puntos de código Unicode comienzan en U+FF10. Este es un cambio que se realizó en la versión 10.43 de PCRE2 para compatibilidad con Perl.

Las otras clases POSIX no se ven afectadas por PCRE2_UCP y solo coinciden con caracteres con puntos de código inferiores a 256.

Hay dos opciones que se pueden usar para restringir las clases POSIX a caracteres ASCII cuando PCRE2_UCP está configurado. La opción PCRE2_EXTRA_DIGITO_ASCII afecta solo a [:digit:] y [:xdigit:]. Dentro de un patrón, esto se puede configurar y desconfigurar mediante (?aT) y (?-aT). La opción PCRE2_EXTRA_POSIX_ASCII deshabilita el procesamiento UCP para todas las clases POSIX, incluidas [:digit:] y [:xdigit:]. Dentro de un patrón, (?aP) y (?-aP) configuran y desconfiguran ambas opciones para mayor coherencia.

CARACTERÍSTICA DE COMPATIBILIDAD PARA LÍMITES DE PALABRA

En la biblioteca compatible con POSIX.2 que se incluyó en 4.4BSD Unix, se utiliza la sintaxis poco elegante [[:<:]] y [[:>:]] para coincidir con "inicio de palabra" y "fin de palabra". PCRE2 trata estos elementos de la siguiente manera:


[[:<:]] se convierte en \b(?=\w)
[[:>:]] se convierte en \b(?<=\w)

Solo se reconocen estas secuencias de caracteres exactas. Una secuencia como [a[:<:]b] genera un error por un nombre de clase POSIX no reconocido. Esta compatibilidad no es compatible con Perl. Se proporciona para ayudar a las migraciones desde otros entornos, y es mejor no utilizarla en patrones nuevos. Tenga en cuenta que \b coincide al principio y al final de una palabra (ver "Aserciones simples" arriba), y en un patrón de estilo Perl, el carácter anterior o posterior normalmente indica cuál se desea, sin necesidad de las aserciones que se utilizan anteriormente para dar exactamente el comportamiento POSIX. Tenga en cuenta también que la opción PCRE2_UCP cambia el significado de \w (y por lo tanto \b) por defecto, por lo que también afecta a estas secuencias POSIX.

BARRA VERTICAL

Los caracteres de barra vertical se utilizan para separar patrones alternativos. Por ejemplo, el patrón


gilbert|sullivan

coincide con "gilbert" o "sullivan". Pueden aparecer varias alternativas, y se permite una alternativa vacía (que coincide con la cadena vacía). El proceso de coincidencia intenta cada alternativa en orden, de izquierda a derecha, y se utiliza la primera que tiene éxito. Si las alternativas están dentro de un grupo (definido a continuación), "tener éxito" significa coincidir con el resto del patrón principal, así como con la alternativa en el grupo.

ESTABLECIMIENTO DE OPCIONES INTERNAS

La configuración de varias opciones se puede cambiar dentro de un patrón mediante una secuencia de letras encerradas entre "(?" y ")". Las siguientes son compatibles con Perl y se describen en detalle en la documentación de pcre2api. Las letras de opción son:


i para PCRE2_CASELESS
m para PCRE2_MULTILINE
n para PCRE2_NO_AUTO_CAPTURE
s para PCRE2_DOTALL
x para PCRE2_EXTENDED
xx para PCRE2_EXTENDED_MORE

Por ejemplo, (?im) establece la coincidencia sin distinción entre mayúsculas y minúsculas y multilínea. También es posible desconfigurar estas opciones anteponiendo un guion a las letras relevantes, por ejemplo (?-im). CAPTURES NOMBRADOS

Para ver un ejemplo de cómo se utilizan los grupos de captura con nombre, considere un patrón que coincide con los nombres de los días de la semana, ya sea como una abreviatura de 3 letras o como el nombre completo, y en ambos casos desea extraer la abreviatura. Este patrón (ignorando los saltos de línea) hace el trabajo:


(?J)
(?<DN>Mon|Fri|Sun)(?:day)?|
(?<DN>Tue)(?:sday)?|
(?<DN>Wed)(?:nesday)?|
(?<DN>Thu)(?:rsday)?|
(?<DN>Sat)(?:urday)?

Hay cinco grupos de captura, pero solo uno se establece después de una coincidencia. Las funciones de conveniencia para extraer datos por nombre devuelven la subcadena del primer (y en este ejemplo, el único) grupo de ese nombre que coincidió. Esto ahorra la búsqueda para encontrar qué grupo numerado era. (Una forma alternativa de resolver este problema es usar un grupo de "restablecimiento de rama", como se describe en la sección anterior).

Si hace una retroreferencia a un grupo con nombre no único desde otro lugar del patrón, los grupos a los que se refiere el nombre se verifican en el orden en que aparecen en el patrón general. Se utiliza el primero que se establece para la referencia. Por ejemplo, este patrón coincide con "foofoo" y "barbar" pero no con "foobar" ni "barfoo":


(?J)(?:(?<n>foo)|(?<n>bar))\k<n>

Si realiza una llamada de subrutina a un grupo con nombre no único, se utiliza el que corresponde a la primera aparición del nombre. En ausencia de números duplicados, es el que tiene el número más bajo.

Si utiliza una referencia nombrada en una prueba de condición (vea la sección sobre condiciones a continuación), ya sea para verificar si un grupo de captura ha coincidido o para verificar la recursión, se prueban todos los grupos con el mismo nombre. Si la condición es verdadera para alguno de ellos, la condición general es verdadera. Este es el mismo comportamiento que la prueba por número. Para obtener más detalles sobre las interfaces para manejar grupos de captura con nombre, consulte la documentación de pcre2api.

REPETICIÓN

La repetición se especifica mediante cuantificadores, que pueden seguir cualquiera de estos elementos:


un carácter de datos literal
el metacaracter punto
la secuencia de escape \C
la secuencia de escape \R
la secuencia de escape \X
cualquier secuencia de escape que coincida con un solo carácter
una clase de caracteres
una retroreferencia
un grupo entre paréntesis (incluidas las aserciones de lookaround)
una llamada de subrutina (recursiva o de otro tipo)

Si un cuantificador no sigue a un elemento repetible, se produce un error. El cuantificador de repetición general especifica un número mínimo y máximo de coincidencias permitidas dando dos números entre llaves (corchetes), separados por una coma. Los números deben ser inferiores a 65536, y el primero debe ser menor o igual que el segundo. Por ejemplo,


z{2,4}

coincide con "zz", "zzz" o "zzzz". Una llave de cierre por sí sola no es un carácter especial. Si se omite el segundo número, pero está presente la coma, no hay límite superior; si se omiten tanto el segundo número como la coma, el cuantificador especifica un número exacto de coincidencias requeridas. Por lo tanto,


[aeiou]{3,}

coincide con al menos 3 vocales sucesivas, pero puede coincidir con muchas más, mientras que


\d{8}

coincide con exactamente 8 dígitos. Si se omite el primer número, el límite inferior se considera cero; en este caso, el límite superior debe estar presente.


X{,4} se interpreta como X{0,4}

Este es un cambio de comportamiento que ocurrió en Perl 5.34.0 y PCRE2 10.43. En versiones anteriores, tal secuencia no se interpretaba como un cuantificador. Otros motores de expresiones regulares pueden comportarse de una u otra manera.

Si los caracteres que siguen a una llave de apertura no coinciden con la sintaxis de un cuantificador, la llave se toma como un carácter literal. En particular, esto significa que {,} es una cadena literal de tres caracteres.

Tenga en cuenta que no toda llave de apertura es potencialmente el inicio de un cuantificador, ya que las llaves se utilizan en otros elementos como \N{U+345} o \k{name}.

En modos UTF, los cuantificadores se aplican a caracteres en lugar de a unidades de código individuales. Por lo tanto, por ejemplo, \x{100}{2} coincide con dos caracteres, cada uno de los cuales está representado por una secuencia de dos bytes en una cadena UTF-8. De manera similar, \X{3} coincide con tres clústeres de grafemas extendidos de Unicode, cada uno de los cuales puede tener varias unidades de código de longitud (y pueden ser de diferentes longitudes).

El cuantificador {0} está permitido, haciendo que la expresión se comporte como si el elemento anterior y el cuantificador no estuvieran presentes. Esto puede ser útil para grupos de captura a los que se hace referencia como subrutinas desde otro lugar del patrón (pero vea también la sección titulada "Definición de grupos de captura para uso solo por referencia" a continuación). Excepto para los grupos entre paréntesis, los elementos que tienen un cuantificador {0} se omiten del patrón compilado.

Para mayor comodidad, los tres cuantificadores más comunes tienen abreviaturas de un solo carácter:


* es equivalente a {0,}
+ es equivalente a {1,}
? es equivalente a {0,1}

Es posible construir bucles infinitos siguiendo un grupo que puede coincidir con ningún carácter con un cuantificador que no tiene límite superior, por ejemplo:


(a?)*

Las versiones anteriores de Perl y PCRE1 solían dar un error en tiempo de compilación para tales patrones. Sin embargo, dado que hay casos en los que esto puede ser útil, tales patrones ahora se aceptan, pero siempre que una iteración de dicho grupo no coincida con ningún carácter, la coincidencia avanza al siguiente elemento del patrón en lugar de coincidir repetidamente con una cadena vacía. Esto no impide el retroceso a ninguna de las iteraciones si un elemento posterior falla al coincidir.

Por defecto, los cuantificadores son "codiciosos" (greedy), es decir, coinciden tanto como sea posible (hasta el número máximo de repeticiones permitidas), sin causar que el resto del patrón falle. El ejemplo clásico de dónde esto causa problemas es al intentar hacer coincidir comentarios en programas C. Estos aparecen entre /* y */ y dentro del comentario, los caracteres individuales * y / pueden aparecer. Un intento de hacer coincidir comentarios C aplicando el patrón


/\*.*\*/

a la cadena


/* primer comentario */ no es comentario /* segundo comentario */

falla, porque coincide con toda la cadena debido a la codicia del elemento .*. Sin embargo, si un cuantificador va seguido de un signo de interrogación, deja de ser codicioso y, en cambio, coincide con el número mínimo de veces posible, por lo que el patrón


/\*.*?\*/

hace lo correcto con los comentarios C. El significado de los diversos cuantificadores no se cambia de otra manera, solo el número preferido de coincidencias. No confunda este uso del signo de interrogación con su uso como cuantificador por derecho propio. Debido a que tiene dos usos, a veces puede aparecer duplicado, como en


\d??\d

que coincide con un dígito por preferencia, pero puede coincidir con dos si esa es la única forma en que el resto del patrón coincide.

Si se establece la opción PCRE2_UNGREEDY (una opción que no está disponible en Perl), los cuantificadores no son codiciosos por defecto, pero los individuales se pueden hacer codiciosos siguiéndolos con un signo de interrogación. En otras palabras, invierte el comportamiento por defecto.

Cuando un grupo entre paréntesis se cuantifica con un recuento de repetición mínimo mayor que 1 o con un máximo limitado, se requiere más memoria para el patrón compilado, en proporción al tamaño del mínimo o máximo.

Si un patrón comienza con .* o .{0,} y se establece la opción PCRE2_DOTALL (equivalente al /s de Perl), permitiendo así que el punto coincida con saltos de línea, el patrón se ancla implícitamente, porque lo que siga se probará contra cada posición de carácter en la cadena sujeto, por lo que no tiene sentido reintentar la coincidencia general en ninguna posición después de la primera. PCRE2 normalmente trata tal patrón como si estuviera precedido por \A.

En casos donde se sabe que la cadena sujeto no contiene saltos de línea, vale la pena establecer PCRE2_DOTALL para obtener esta optimización, o alternativamente, usar ^ para indicar el anclaje explícitamente.

Sin embargo, hay algunos casos en los que la optimización no se puede utilizar. Cuando .* está dentro de paréntesis de captura que son el sujeto de una retroreferencia en otro lugar del patrón, una coincidencia al principio puede fallar donde una posterior tiene éxito. Considere, por ejemplo:


(.*)abc\1

Si el sujeto es "xyz123abc123", el punto de coincidencia es el cuarto carácter. Por esta razón, tal patrón no se ancla implícitamente.

Otro caso donde no se aplica el anclaje implícito es cuando el .* inicial está dentro de un grupo atómico. Una vez más, una coincidencia al principio puede fallar donde una posterior tiene éxito. Considere este patrón:


(?>.*?a)b

Coincide con "ab" en el sujeto "aab". El uso de los verbos de control de retroceso (*PRUNE) y (*SKIP) también deshabilita esta optimización. Para hacerlo explícitamente, pase la opción de compilación PCRE2_NO_DOTSTAR_ANCHOR o llame a pcre2_set_optimize() con una directiva PCRE2_DOTSTAR_ANCHOR_OFF.

Cuando un grupo de captura se repite, el valor capturado es la subcadena que coincidió con la iteración final. Por ejemplo, después de


(tweedle[dume]{3}\s*)+

ha coincidido con "tweedledum tweedledee", el valor de la subcadena capturada es "tweedledee". Sin embargo, si hay grupos de captura anidados, los valores capturados correspondientes pueden haber sido establecidos en iteraciones anteriores. Por ejemplo, después de


(a|(b))+

coincide con "aba", el valor de la segunda subcadena capturada es "b".

AGRUPACIÓN ATÓMICA Y CUANTIFICADORES POSESIVOS

Tanto con la repetición maximizadora ("codiciosa") como con la minimizadora ("no codiciosa" o "perezosa"), el fallo de lo que sigue normalmente hace que el elemento repetido se reevalúe para ver si un número diferente de repeticiones permite que el resto del patrón coincida. A veces es útil evitar esto, ya sea para cambiar la naturaleza de la coincidencia, o para hacer que falle antes de lo que podría hacerlo, cuando el autor del patrón sabe que no tiene sentido continuar.

Considere, por ejemplo, el patrón \d+foo cuando se aplica a la línea sujeto


123456bar

Después de hacer coincidir los 6 dígitos y luego no hacer coincidir "foo", la acción normal del casador es intentar de nuevo con solo 5 dígitos coincidiendo con el elemento \d+, y luego con 4, y así sucesivamente, antes de fallar finalmente. La "agrupación atómica" (un término tomado del libro de Jeffrey Friedl) proporciona los medios para especificar que una vez que un grupo ha coincidido, no se debe reevaluar de esta manera.

Si usamos la agrupación atómica para el ejemplo anterior, el coincididor se rinde inmediatamente al no poder coincidir con "foo" la primera vez. La notación es una especie de paréntesis especiales, que empiezan con (?> como en este ejemplo:


(?>\d+)foo

Perl 5.28 introdujo una forma alfabética experimental que empieza con (* y que puede ser más fácil de recordar:


(*atomic:\d+)foo

Este tipo de grupo entre paréntesis "bloquea" la parte del patrón que contiene una vez que ha coincidido, y se evita que un fallo más adelante en el patrón retroceda hacia él. Sin embargo, retroceder más allá de él hacia elementos anteriores funciona con normalidad.

Una descripción alternativa es que un grupo de este tipo coincide exactamente con la cadena de caracteres que un patrón independiente idéntico coincidiría, si estuviera anclado en el punto actual de la cadena sujeto.

Los grupos atómicos no son grupos de captura. Casos simples como el ejemplo anterior pueden considerarse como un repetidor maximizador que debe consumir todo lo que pueda. Por lo tanto, mientras que \d+ y \d+? están preparados para ajustar el número de dígitos que coinciden para que el resto del patrón coincida, (?>\d+) solo puede coincidir con una secuencia completa de dígitos.

Los grupos atómicos en general pueden, por supuesto, contener expresiones arbitrariamente complicadas y pueden anidarse. Sin embargo, cuando el contenido de un grupo atómico es solo un elemento repetido simple, como en el ejemplo anterior, se puede usar una notación más simple, llamada "cuantificador posesivo". Este consiste en un carácter + adicional que sigue a un cuantificador. Usando esta notación, el ejemplo anterior puede reescribirse como


\d++foo

Tenga en cuenta que se puede usar un cuantificador posesivo con un grupo completo, por ejemplo:


(abc|xyz){2,3}+

Los cuantificadores posesivos son siempre codiciosos; se ignora la configuración de la opción PCRE2_UNGREEDY. Son una notación conveniente para las formas más simples de grupo atómico. Sin embargo, no hay diferencia en el significado de un cuantificador posesivo y el grupo atómico equivalente, aunque puede haber una diferencia de rendimiento; los cuantificadores posesivos deberían ser ligeramente más rápidos.

La sintaxis del cuantificador posesivo es una extensión de la sintaxis de Perl 5.8. Jeffrey Friedl originó la idea (y el nombre) en la primera edición de su libro. A Mike McCloskey le gustó, así que la implementó cuando construyó el paquete Java de Sun, y PCRE1 la copió de allí. Llegó a Perl en la versión 5.10.

PCRE2 tiene una optimización que "posesiviza" automáticamente ciertos constructos de patrones simples. Por ejemplo, la secuencia A+B se trata como A++B porque no tiene sentido retroceder a una secuencia de A cuando B debe seguir. Esta característica se puede deshabilitar con la opción PCRE2_NO_AUTO_POSSESS, llamando a pcre2_set_optimize() con una directiva PCRE2_AUTO_POSSESS_OFF, o empezando el patrón con (*NO_AUTO_POSSESS).

Cuando un patrón contiene una repetición ilimitada dentro de un grupo que a su vez puede repetirse un número ilimitado de veces, el uso de un grupo atómico es la única forma de evitar que algunas coincidencias fallidas tarden mucho tiempo. El patrón


(\D+|<\d+>)*[!?]

coincide con un número ilimitado de subcadenas que consisten en no dígitos, o dígitos entre <>, seguidos de ! o ?. Cuando coincide, se ejecuta rápidamente. Sin embargo, si se aplica a


aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa

tarda mucho tiempo antes de informar de un fallo. Esto se debe a que la cadena puede dividirse entre la repetición interna \D+ y la repetición externa * de un gran número de maneras, y todas deben ser probadas. (El ejemplo usa [!?] en lugar de un solo carácter al final, porque tanto PCRE2 como Perl tienen una optimización que permite fallos rápidos cuando se usa un solo carácter. Recuerdan el último carácter individual que se requiere para una coincidencia, y fallan pronto si no está presente en la cadena.) Si el patrón se cambia para que use un grupo atómico, como este:


((?>\D+)|<\d+>)*[!?]

las secuencias de no dígitos no se pueden romper, y el fallo ocurre rápidamente.

REFERENCIAS DIRECTAS

Fuera de una clase de caracteres, una barra invertida seguida de un dígito mayor que 0 (y posiblemente más dígitos) es una referencia directa a un grupo de captura anterior (es decir, a su izquierda) en el patrón, siempre que haya habido ese número de grupos de captura previos.

Sin embargo, si el número decimal que sigue a la barra invertida es menor que 8, siempre se toma como una referencia directa y solo causa un error si no hay tantos grupos de captura en todo el patrón. En otras palabras, el grupo al que se hace referencia no tiene por qué estar a la izquierda de la referencia para números menores que 8. Una "referencia directa hacia adelante" de este tipo puede tener sentido cuando hay una repetición involucrada y el grupo de la derecha ha participado en una iteración anterior.

No es posible tener una "referencia directa hacia adelante" numérica a un grupo cuyo número sea 8 o más utilizando esta sintaxis, porque una secuencia como \50 se interpreta como un carácter definido en octal. Vea la subsección titulada "Caracteres no imprimibles" más arriba para más detalles sobre el manejo de dígitos después de una barra invertida. Otras formas de referenciación directa no sufren esta restricción. En particular, no hay problema cuando se utilizan grupos de captura con nombre (ver más abajo).

Otra forma de evitar la ambigüedad inherente al uso de dígitos después de una barra invertida es usar la secuencia de escape \g. A esta secuencia le debe seguir un número con signo o sin signo, opcionalmente entre llaves. Todos estos ejemplos son idénticos:


(ring), \1
(ring), \g1
(ring), \g{1}

Un número sin signo especifica una referencia absoluta sin la ambigüedad que presenta la sintaxis más antigua. También es útil cuando dígitos literales siguen a la referencia. Un número con signo es una referencia relativa. Considere este ejemplo:


(abc(def)ghi)\g{-1}

La secuencia \g{-1} es una referencia al grupo de captura cuyo número es uno menos que el número del siguiente grupo que se iniciará, por lo que en este ejemplo (donde el siguiente grupo sería el número 3) es equivalente a \2, y \g{-2} sería equivalente a \1. Tenga en cuenta que si este constructo está dentro de un grupo de captura, ese grupo se incluye en el recuento, por lo que en este ejemplo \g{-2} también se refiere al grupo 1:


(A)(\g{-2}B)

El uso de referencias relativas puede ser útil en patrones largos, y también en patrones que se crean uniendo fragmentos que contienen referencias dentro de sí mismos.

La secuencia \g{+1} es una referencia al siguiente grupo de captura que se inicia después de este elemento, y \g{+2} se refiere al siguiente, y así sucesivamente. Este tipo de referencia hacia adelante puede ser útil en patrones que se repiten. Perl no admite el uso de + de esta manera.

Una referencia directa coincide con lo que realmente coincidió más recientemente con el grupo de captura en la cadena sujeto actual, en lugar de cualquier cosa que coincida con el grupo (ver "Grupos como subrutinas" más abajo para una forma de hacer eso). Por lo tanto, el patrón


(sens|respons)e and \1ibility

coincide con "sense and sensibility" y "response and responsibility", pero no con "sense and responsibility". Si la coincidencia sensible a mayúsculas/minúsculas está activa en el momento de la referencia directa, la mayúscula/minúscula de las letras es relevante. Por ejemplo,


((?i)rah)\s+\1

coincide con "rah rah" y "RAH RAH", pero no con "RAH rah", incluso aunque el grupo de captura original haya coincidido sin distinguir mayúsculas/minúsculas.

Hay varias formas diferentes de escribir referencias directas a grupos de captura con nombre. La sintaxis de .NET es \k{name}, la sintaxis de Python es (?=name), y la sintaxis original de Perl es \k<name> o \k'name'. Todas estas ahora son compatibles con Perl y PCRE2. La sintaxis unificada de referencia directa de Perl 5.10, en la que \g se puede usar para referencias numéricas y con nombre, también es compatible con PCRE2. Podríamos reescribir el ejemplo anterior de cualquiera de las siguientes maneras:


(?<p1>(?i)rah)\s+\k<p1>
(?'p1'(?i)rah)\s+\k{p1}
(?P<p1>(?i)rah)\s+(?P=p1)
(?<p1>(?i)rah)\s+\g{p1}

Un grupo de captura que se referencia por nombre puede aparecer en el patrón antes o después de la referencia.

Puede haber más de una referencia directa al mismo grupo. Si un grupo no se ha utilizado realmente en una coincidencia particular, las referencias directas a él siempre fallan por defecto. Por ejemplo, el patrón


(a|(bc))\2

siempre falla si empieza a coincidir con "a" en lugar de "bc". Sin embargo, si la opción PCRE2_MATCH_UNSET_BACKREF se establece en tiempo de compilación, una referencia directa a un valor no establecido coincide con una cadena vacía.

Debido a que puede haber muchos grupos de captura en un patrón, todos los dígitos que siguen a una barra invertida se toman como parte de un número de referencia directa potencial. Si el patrón continúa con un carácter de dígito, se debe usar algún delimitador para terminar la referencia directa. Si la opción PCRE2_EXTENDED o PCRE2_EXTENDED_MORE está establecida, esto puede ser un espacio en blanco. De lo contrario, se puede usar la sintaxis \g{} o un comentario vacío (ver "Comentarios" más abajo).

Referencias directas recursivas

Una referencia directa que ocurre dentro del grupo al que se refiere falla cuando el grupo se usa por primera vez, por lo que, por ejemplo, (a\1) nunca coincide. Sin embargo, tales referencias pueden ser útiles dentro de grupos repetidos. Por ejemplo, el patrón


(a|b\1)+

coincide con cualquier número de "a"s y también "aba", "ababbaa", etc. En cada iteración del grupo, la referencia directa coincide con la cadena de caracteres correspondiente a la iteración anterior. Para que esto funcione, el patrón debe ser tal que la primera iteración no necesite coincidir con la referencia directa. Esto se puede hacer usando alternancia, como en el ejemplo anterior, o mediante un cuantificador con un mínimo de cero.

Para versiones de PCRE2 anteriores a 10.25, las referencias directas de este tipo solían hacer que el grupo al que se referían se tratara como un grupo atómico. Esta restricción ya no se aplica, y se puede producir retroceso en tales grupos como de costumbre.

AFIRMACIONES

Una afirmación es una prueba que no consume ningún carácter. La prueba debe tener éxito para que la coincidencia continúe. Las afirmaciones simples codificadas como \b, \B, \A, \G, \Z, \z, ^ y $ se describen anteriormente.

Las afirmaciones más complicadas se codifican como grupos entre paréntesis. Si la coincidencia de un grupo de este tipo tiene éxito, la coincidencia continúa después de él, pero con la posición de coincidencia en la

El subject string se restablece a como estaba antes de que se procesara la aserción.

Una clase especial de aserción, llamada aserción de "cadena de escaneo", coincide con un subpatrón contra una subcadena capturada previamente. Esto se describe en la sección titulada "Aserciones de subcadena de escaneo" a continuación. Es una extensión de PCRE2, no compatible con Perl.

Las otras aserciones basadas en grupos son de dos tipos: aquellas que miran hacia adelante desde la posición actual en la cadena de caracteres del sujeto, y aquellas que miran hacia atrás desde ella, y en cada caso una aserción puede ser positiva (debe coincidir para que la aserción sea verdadera) o negativa (no debe coincidir para que la aserción sea verdadera).

Las aserciones de mirada (lookaround) compatibles con Perl son atómicas. Si una aserción es verdadera, pero hay un fallo de coincidencia posterior, no hay retroceso en la aserción. Sin embargo, hay algunos casos en los que las aserciones no atómicas pueden ser útiles. PCRE2 tiene cierto soporte para ellas, descrito en la sección titulada "Aserciones no atómicas" a continuación, pero no son compatibles con Perl.

Una aserción de mirada puede aparecer como condición en un grupo condicional (ver más abajo). En este caso, el resultado de la coincidencia de la aserción determina qué rama de la condición se sigue.

Los grupos de aserción no son grupos de captura. Si una aserción contiene grupos de captura dentro de ella, estos se cuentan a efectos de numeración de los grupos de captura en el patrón completo. Dentro de cada rama de una aserción, las subcadenas capturadas localmente pueden ser referenciadas de la manera habitual. Por ejemplo, una secuencia como (.)\g{-1} puede usarse para verificar que dos caracteres adyacentes son iguales.

Cuando una rama dentro de una aserción no coincide, las subcadenas que fueron capturadas se descartan (como sucede con cualquier rama de patrón que no coincide). Una aserción negativa es verdadera solo cuando todas sus ramas no coinciden; esto significa que nunca se conservan subcadenas capturadas después de una aserción negativa exitosa. Cuando una aserción contiene una rama que coincide, lo que sucede depende del tipo de aserción.

Para una aserción positiva, las subcadenas capturadas internamente en la rama exitosa se conservan, y la coincidencia continúa con el siguiente elemento del patrón después de la aserción. Para una aserción negativa, una rama que coincide significa que la aserción no es verdadera. Si tal aserción se está utilizando como condición en un grupo condicional (ver más abajo), las subcadenas capturadas se conservan, ya que la coincidencia continúa con la rama "no" de la condición. Para otras aserciones negativas fallidas, el control pasa al punto de retroceso anterior, descartando así las cadenas capturadas dentro de la aserción.

La mayoría de los grupos de aserción pueden repetirse; aunque no tiene sentido afirmar lo mismo varias veces, el efecto secundario de la captura en aserciones positivas puede ser ocasionalmente útil. Sin embargo, una aserción que forma la condición para un grupo condicional no puede ser cuantificada. PCRE2 solía restringir la repetición de aserciones, pero desde la versión 10.35 la única restricción es que una repetición máxima ilimitada se cambia a ser una más que el mínimo. Por ejemplo, {3,} se trata como {3,4}.

Nombres alfabéticos de aserción

Tradicionalmente, se han utilizado secuencias simbólicas como (?= y (?<= para especificar aserciones de mirada. Perl 5.28 introdujo algunas alternativas alfabéticas experimentales que podrían ser más fáciles de recordar. Todas comienzan con (* en lugar de (? y deben escribirse en letras minúsculas. PCRE2 admite los siguientes sinónimos:


(*positive_lookahead: o (*pla: es lo mismo que (?=
(*negative_lookahead: o (*nla: es lo mismo que (?!
(*positive_lookbehind: o (*plb: es lo mismo que (?<=
(*negative_lookbehind: o (*nlb: es lo mismo que (?<!

Por ejemplo, (*pla:foo) es la misma aserción que (?=foo). En las siguientes secciones, las diversas aserciones se describen utilizando las formas simbólicas originales.

Aserciones de mirada hacia adelante

Las aserciones de mirada hacia adelante comienzan con (?= para las aserciones positivas y (?! para las aserciones negativas. Por ejemplo,


\w+(?=;)

coincide con una palabra seguida de un punto y coma, pero no incluye el punto y coma en la coincidencia, y


foo(?!bar)

coincide con cualquier ocurrencia de "foo" que no esté seguida por "bar". Tenga en cuenta que el patrón aparentemente similar


(?!foo)bar

no encuentra una ocurrencia de "bar" que esté precedida por algo que no sea "foo"; encuentra cualquier ocurrencia de "bar" en general, porque la aserción (?!foo) siempre es verdadera cuando los siguientes tres caracteres son "bar". Se necesita una aserción de mirada hacia atrás para lograr el otro efecto.

Si desea forzar un fallo de coincidencia en algún punto de un patrón, la forma más conveniente de hacerlo es con (?!) ya que una cadena vacía siempre coincide, por lo que una aserción que requiere que no haya una cadena vacía debe fallar siempre. El verbo de control de retroceso (*FAIL) o (*F) es un sinónimo de (?!).

Aserciones de mirada hacia atrás

Las aserciones de mirada hacia atrás comienzan con (?<= para las aserciones positivas y (?<! para las aserciones negativas. Por ejemplo,


(?<!foo)bar

encuentra una ocurrencia de "bar" que no está precedida por "foo". El contenido de una aserción de mirada hacia atrás está restringido de tal manera que debe haber un máximo conocido para las longitudes de todas las cadenas que coincide. Hay dos casos:

Si cada alternativa de nivel superior coincide con una longitud fija, por ejemplo


(?<=colour|color)

hay un límite de 65535 caracteres para las longitudes, que no tienen por qué ser las mismas, como demuestra este ejemplo. Este es el único tipo de mirada hacia atrás soportado por las versiones de PCRE2 anteriores a la 10.43 y por la función de coincidencia alternativa pcre2_dfa_match().

En PCRE2 10.43 y posteriores, pcre2_match() admite aserciones de mirada hacia atrás en las que una o más alternativas de nivel superior pueden coincidir con más de una longitud de cadena, por ejemplo


(?<=colou?r)

La longitud máxima de coincidencia para cada rama de la mirada hacia atrás se limita a un valor establecido por el programa que llama (por defecto 255 caracteres). La repetición ilimitada (por ejemplo \d*) no está soportada. En algunos casos, la secuencia de escape \K (ver más arriba) se puede utilizar en lugar de una aserción de mirada hacia atrás al principio de un patrón para evitar la restricción del límite de longitud.

En los modos UTF-8 y UTF-16, PCRE2 no permite que la secuencia de escape \C (que coincide con una sola unidad de código incluso en modo UTF) aparezca en las aserciones de mirada hacia atrás, porque hace imposible calcular la longitud de la mirada hacia atrás. Las secuencias de escape \X y \R, que pueden coincidir con diferentes números de unidades de código, nunca están permitidas en las miradas hacia atrás.

Las llamadas a "subrutinas" (ver más abajo) como (?2) o (?&X) están permitidas en las miradas hacia atrás, siempre que el grupo de captura llamado coincida con una subcadena de longitud limitada. Sin embargo, la recursión, es decir, una llamada a "subrutina" a un grupo que ya está activo, no está soportada.

PCRE2 admite retroreferencias en miradas hacia atrás, pero solo si se cumplen ciertas condiciones. La opción PCRE2_MATCH_UNSET_BACKREF no debe estar establecida, no debe haber uso de (?| en el patrón (crea números de grupo duplicados) y, si la retroreferencia es por nombre, el nombre debe ser único. Por supuesto, el grupo referenciado debe coincidir con una subcadena de longitud limitada. El siguiente patrón coincide con palabras que contienen al menos dos caracteres que comienzan y terminan con el mismo carácter:


\b(\w)\w++(?<=\1)

Los cuantificadores posesivos se pueden usar junto con las aserciones de mirada hacia atrás para especificar una coincidencia eficiente al final de las cadenas del sujeto. Considere un patrón simple como


abcd$

cuando se aplica a una cadena larga que no coincide. Como la coincidencia procede de izquierda a derecha, PCRE2 buscará cada "a" en el sujeto y luego verá si lo que sigue coincide con el resto del patrón. Si el patrón se especifica como


^.*abcd$

el .* inicial coincide con toda la cadena al principio, pero cuando esto falla (porque no hay una "a" siguiente), retrocede para coincidir con toda la cadena menos el último carácter, luego toda la cadena menos los dos últimos caracteres, y así sucesivamente. Una vez más, la búsqueda de "a" cubre toda la cadena, de derecha a izquierda, por lo que no mejoramos. Sin embargo, si el patrón está escrito como


^.*+(?<=abcd)

no puede haber retroceso para el elemento .*+ debido al cuantificador posesivo; solo puede coincidir con toda la cadena. La aserción de mirada hacia atrás posterior realiza una sola prueba en los últimos cuatro caracteres. Si falla, la coincidencia falla inmediatamente. Para cadenas largas, este enfoque marca una diferencia significativa en el tiempo de procesamiento.

Usando múltiples aserciones

Varias aserciones (de cualquier tipo) pueden aparecer sucesivamente. Por ejemplo,


(?<=\d{3})(?<!999)foo

coincide con "foo" precedido por tres dígitos que no son "999". Observe que cada una de las aserciones se aplica de forma independiente en el mismo punto de la cadena del sujeto. Primero hay una verificación de que los tres caracteres anteriores son todos dígitos, y luego hay una verificación de que los mismos tres caracteres no son "999". Este patrón *no* coincide con "foo" precedido por seis caracteres, los primeros de los cuales son dígitos y los últimos tres de los cuales no son "999". Por ejemplo, no coincide con "123abcfoo". Un patrón para hacer eso es


(?<=\d{3}...)(?<!999)foo

Esta vez, la primera aserción mira los seis caracteres precedentes, verificando que los primeros tres son dígitos, y luego la segunda aserción verifica que los tres caracteres precedentes no son "999".

Las aserciones se pueden anidar de cualquier combinación. Por ejemplo,


(?<=(?<!foo)bar)baz

coincide con una ocurrencia de "baz" que está precedida por "bar" que a su vez no está precedida por "foo", mientras que


(?<=\d{3}(?!999)...)foo

es otro patrón que coincide con "foo" precedido por tres dígitos y tres caracteres cualesquiera que no sean "999".

ASERCIONES NO ATÓMICAS

Las aserciones de mirada tradicionales son atómicas. Es decir, si una aserción es verdadera, pero hay una

fallo de concordancia posterior, no hay vuelta atrás en la aserción. Sin embargo, hay casos en los que las aserciones positivas no atómicas pueden ser útiles. PCRE2 las proporciona utilizando la siguiente sintaxis:


(*non_atomic_positive_lookahead: o (*napla: o (?*
(*non_atomic_positive_lookbehind: o (*naplb: o (?<*

Considere el problema de encontrar la palabra más a la derecha en una cadena que también aparece antes en la cadena, es decir, debe aparecer al menos dos veces en total. Este patrón devuelve el resultado requerido como subcadena capturada 1:


^(?x)(*napla: .* \b(\w++)) (?> .*? \b\1\b ){2}

Para un sujeto como "word1 word2 word3 word2 word3 word4" el resultado es "word3". ¿Cómo funciona? Al principio, ^(?x) ancla el patrón y establece la opción "x", que hace que el espacio en blanco (introducido por legibilidad) se ignore. Dentro de la aserción, el .* codicioso consume inicialmente toda la cadena, pero luego tiene que retroceder hasta que el resto de la aserción pueda coincidir con una palabra, que es capturada por el grupo 1. En otras palabras, cuando la aserción tiene éxito por primera vez, captura la palabra más a la derecha en la cadena.

El punto de concordancia actual se restablece al inicio del sujeto, y el resto del patrón de concordancia busca dos ocurrencias de la palabra capturada, utilizando un .*? no codicioso para escanear desde la izquierda. Si esto tiene éxito, hemos terminado, pero si la última palabra en la cadena no se encuentra dos veces, esta parte del patrón falla. Si se hubiera utilizado una búsqueda atómica tradicional (?= o (*pla:, la aserción no podría ser reingresada, y toda la concordancia fallaría. El patrón solo tendría éxito si la última palabra en el sujeto se encontrara dos veces.

Sin embargo, el uso de una búsqueda no atómica significa que cuando la última palabra no se encuentra dos veces en la cadena, la búsqueda puede retroceder y encontrar la penúltima palabra, y así sucesivamente, hasta que la concordancia tenga éxito o se hayan probado todas las palabras.

Deben cumplirse dos condiciones para que una aserción no atómica sea útil: el contenido de uno o más grupos de captura debe cambiar después de una vuelta atrás en la aserción, y debe haber una referencia posterior a un grupo modificado más adelante en el patrón. Si este no es el caso, el resto de la concordancia del patrón falla exactamente como antes porque nada ha cambiado, por lo que usar una aserción no atómica solo desperdicia recursos.

Hay una excepción a la vuelta atrás en una aserción no atómica. Si se activa un verbo de control (*ACCEPT), la aserción tiene éxito atómicamente. Es decir, un fallo posterior de la concordancia no puede retroceder en la aserción.

Las aserciones no atómicas no son compatibles con la función de concordancia alternativa pcre2_dfa_match(). Son compatibles con JIT, pero solo si no contienen verbos de control como (*ACCEPT). (Esto puede cambiar en el futuro). Tenga en cuenta que las aserciones que aparecen como condiciones para grupos condicionales (ver más abajo) deben ser atómicas.

ASERCIONES DE ESCANEO DE SUBSTRING

Un tipo especial de aserción, no compatible con Perl, permite comprobar el contenido de una subcadena capturada haciéndola coincidir con un subpatrón. Dado que esto implica captura, esta característica no es compatible con pcre2_dfa_match().

Una aserción de escaneo de subcadena comienza con la secuencia (*scan_substring: o (*scs: seguida de una lista de números de subcadena (absolutos o relativos) y/o nombres de subcadena encerrados entre comillas simples o corchetes angulares, todo dentro de paréntesis. El resto del elemento es el subpatrón que se aplica a la subcadena, como se muestra en estos ejemplos:


(*scan_substring:(1)...)
(*scs:(-2)...)
(*scs:('AB')...)
(*scs:(1,'AB',-2)...)

La lista de grupos se comprueba en el orden en que se dan, y es el contenido del primer grupo que se encuentra establecido el que se escanea. Cuando PCRE2_DUPNAMES está configurado y hay nombres de grupo ambiguos, todos los grupos con el mismo nombre se comprueban en orden numérico. Una aserción de escaneo de subcadena falla si ninguno de los grupos que referencia ha sido establecido.

La concordancia del patrón en la subcadena siempre está anclada, es decir, debe coincidir desde el inicio de la subcadena. No hay "avance" si no coincide al principio. El final del sujeto se restablece temporalmente para ser el final de la subcadena, por lo que \Z, \z y $ coincidirán allí. Sin embargo, el inicio del sujeto *no* se restablece. Esto significa que ^ solo coincide si la subcadena está realmente al principio del sujeto principal, pero también significa que son posibles las búsquedas hacia atrás en lo que precede a la subcadena.

Aquí hay un ejemplo muy simple: encontrar una palabra que contenga la rara (en inglés) secuencia de letras "rh" que no está al principio:


\b(\w++)(*scs:(1).+rh)

El primer grupo captura una palabra que luego es escaneada por el segundo grupo. Este ejemplo en realidad no necesita esta característica pesada; la misma concordancia se puede lograr con:


\b\w+?rh\w*\b

Sin embargo, cuando las cosas se complican, escanear una subcadena capturada puede ser una forma útil de describir la concordancia requerida. Por ejemplo, hay un patrón bastante complicado en los datos de prueba de PCRE2 que comprueba una cadena de sujeto completa para un palíndromo, es decir, la secuencia de letras es la misma en ambas direcciones. Supongamos que desea buscar palabras individuales de dos o más caracteres, como "level", que son palíndromos:


(\b\w{2,}+\b)(*scs:(1)...patrón-que-coincide-con-palíndromo...)

Dentro de un subpatrón de escaneo de subcadena, las referencias a otros grupos funcionan de forma normal. Pueden aparecer grupos de captura y conservarán sus valores durante la concordancia en curso si la aserción tiene éxito.

EJECUCIONES DE SCRIPT

En concepto, una ejecución de script es una secuencia de caracteres que provienen todos del mismo script Unicode, como el latino o el griego. Sin embargo, debido a que algunos scripts se usan comúnmente juntos, y debido a que algunas marcas diacríticas y otras marcas se usan con múltiples scripts, no es tan simple. Hay una descripción completa de las reglas que PCRE2 utiliza en la sección titulada "Ejecuciones de Script" en la documentación de pcre2unicode.

Si parte de un patrón está encerrado entre (*script_run: o (*sr: y un paréntesis de cierre, falla si la secuencia de caracteres que coincide no es una ejecución de script. Después de un fallo, ocurre la vuelta atrás normal. Las ejecuciones de script se pueden usar para detectar ataques de suplantación utilizando caracteres que parecen iguales, pero provienen de diferentes scripts. La cadena "paypal.com" es un ejemplo infame, donde las letras podrían ser una mezcla de latín y cirílico. Este patrón asegura que los caracteres coincidentes en una secuencia de no espacios que siguen a un espacio en blanco sean una ejecución de script:


\s+(*sr:\S+)

Para asegurarse de que todos son del script latino (por ejemplo), se puede usar una búsqueda:


\s+(?=\p{Latin})(*sr:\S+)

Esto funciona siempre que se espere que el primer carácter sea un carácter de ese script, y no (por ejemplo) puntuación, que está permitida con cualquier script. Si este no es el caso, se necesita una búsqueda más creativa. Por ejemplo, si se permiten dígitos, guiones bajos y puntos al principio:


\s+(?=[0-9_.]*\p{Latin})(*sr:\S+)

En muchos casos, no es deseable retroceder en un fragmento de patrón de ejecución de script. La ejecución de script puede emplear un grupo atómico para evitar esto. Dado que este es un requisito común, se proporciona una notación abreviada mediante (*atomic_script_run: o (*asr:


(*asr:...) es lo mismo que (*sr:(?>...))

Tenga en cuenta que el grupo atómico está dentro de la ejecución del script. Ponerlo fuera no evitaría la vuelta atrás en el patrón de ejecución del script.

El soporte para ejecuciones de script no está disponible si PCRE2 se compila sin soporte Unicode. Se produce un error de compilación si se encuentra alguna de las construcciones anteriores. Las ejecuciones de script no son compatibles con la función de concordancia alternativa, pcre2_dfa_match(), ya que utilizan el mismo mecanismo que los paréntesis de captura.

Advertencia: El verbo de control (*ACCEPT) (ver más abajo) no debe utilizarse dentro de un grupo de ejecución de script, ya que provoca una salida inmediata del grupo, omitiendo la comprobación de la ejecución del script.

GRUPOS CONDICIONALES

Es posible hacer que el proceso de concordancia obedezca un fragmento de patrón condicionalmente o elegir entre dos fragmentos alternativos, dependiendo del resultado de una aserción, o de si un grupo de captura específico ya ha coincidido. Las dos formas posibles de grupo condicional son:


(?(condition)yes-pattern)
(?(condition)yes-pattern|no-pattern)

Si la condición se cumple, se utiliza el yes-pattern; de lo contrario, se utiliza el no-pattern (si está presente). Un no-pattern ausente es equivalente a una cadena vacía (siempre coincide). Si hay más de dos alternativas en el grupo, se produce un error de compilación. Cada una de las dos alternativas puede contener grupos anidados de cualquier forma, incluidos grupos condicionales; la restricción a dos alternativas se aplica solo al nivel de la propia condición. Este fragmento de patrón es un ejemplo donde las alternativas son complejas:


(?(1) (A|B|C) | (D | (?(2)E|F) | E) )

Hay cinco tipos de condición: referencias a grupos de captura, referencias a recursión, dos pseudo-condiciones llamadas DEFINE y VERSION, y aserciones.

Comprobación de un grupo de captura usado por número

Si el texto entre los paréntesis consiste en una secuencia de dígitos, la condición es verdadera si un grupo de captura de ese número ha coincidido previamente. Si hay más de un grupo de captura con el mismo número (ver la sección anterior sobre números de grupo duplicados), la condición es verdadera si alguno de ellos ha coincidido. Una notación alternativa, que es una extensión de PCRE2, no compatible con Perl, es preceder los dígitos con un signo más o menos. En este caso, el número del grupo es relativo en lugar de absoluto. El grupo de captura abierto más reciente (que podría estar encerrando esta condición) se puede referenciar con (?(-1), el siguiente más reciente con (?(-2), y así sucesivamente. Dentro de los bucles, también puede tener sentido referirse a grupos subsiguientes. El siguiente grupo de captura que se abrirá se puede referenciar como (?(+1), y así sucesivamente. El valor cero en cualquiera de estas formas no se utiliza; provoca un error de compilación.

Considere el siguiente patrón, que contiene espacios en blanco no significativos para hacerlo más legible (asuma la opción PCRE2_EXTENDED) y para dividirlo en tres partes para facilitar la discusión:


( \( )? [^()]+ (?(1) \) )

PATRONES CONDICIONALES

Un patrón condicional empieza con la secuencia (?(. La parte que sigue hasta el siguiente ) es la condición. Si la condición es verdadera, se evalúa el patrón que sigue inmediatamente, de lo contrario se evalúa el patrón que sigue a un | opcional. Si no hay | y la condición es falsa, el patrón condicional no coincide.

Hay varias clases de condiciones:

Comprobación de un grupo de captura usado por número

La primera parte coincide con un paréntesis de apertura opcional, y si ese carácter está presente, lo establece como la primera subcadena capturada. La segunda parte coincide con uno o más caracteres que no son paréntesis. La tercera parte es un grupo condicional que prueba si el primer grupo de captura coincidió o no. Si lo hizo, es decir, si el sujeto comenzó con un paréntesis de apertura, la condición es verdadera, y por lo tanto se ejecuta el patrón de "sí" y se requiere un paréntesis de cierre. De lo contrario, dado que el patrón de "no" no está presente, el grupo condicional no coincide con nada. En otras palabras, este patrón coincide con una secuencia de no paréntesis, opcionalmente encerrada en paréntesis.

Si estuvieras incrustando este patrón en uno más grande, podrías usar una referencia relativa:


...otras cosas... ( \( )? [^()]+ (?(-1) \) ) ...

Esto hace que el fragmento sea independiente de los paréntesis en el patrón más grande.

Comprobación de un grupo de captura usado por nombre

Perl utiliza la sintaxis (?<nombre>...) o ?('nombre'...) para comprobar un grupo de captura usado por nombre. Para compatibilidad con versiones anteriores de PCRE1, que tenían esta facilidad antes que Perl, la sintaxis (?(nombre)...) también se reconoce. Ten en cuenta, sin embargo, que los nombres sin delimitadores que consisten en la letra R seguida de dígitos son ambiguos (ver la siguiente sección). Reescribiendo el ejemplo anterior para usar un grupo con nombre se obtiene:


(?<ABIERTO> \( )? [^()]+ (?(<ABIERTO>) \) )

Si el nombre utilizado en una condición de este tipo es un duplicado, la prueba se aplica a todos los grupos del mismo nombre, y es verdadera si alguno de ellos ha coincidido.

Comprobación de recursión de patrón

La "recursión" en este sentido se refiere a cualquier llamada similar a una subrutina desde una parte del patrón a otra, independientemente de si es realmente recursiva. Ver las secciones tituladas "Patrones recursivos" y "Grupos como subrutinas" más abajo para detalles sobre recursión y llamadas a subrutinas.

Si una condición es la cadena (R), y no hay un grupo de captura con el nombre R, la condición es verdadera si la coincidencia está actualmente en una recursión o llamada a subrutina del patrón completo o de cualquier grupo de captura. Si los dígitos siguen a la letra R, y no hay grupo con ese nombre, la condición es verdadera si la llamada más reciente es a un grupo con el número dado, que debe existir en algún lugar del patrón general. Este es un ejemplo forzado que es equivalente a a+b:


((?(R1)a+|(?1)b))

Sin embargo, en ambos casos, si hay un grupo de captura con un nombre coincidente, la condición comprueba si está establecido, como se describe en la sección anterior, en lugar de comprobar la recursión. Por ejemplo, crear un grupo con el nombre R1 añadiendo (?<R1>) al patrón anterior cambia completamente su significado.

Si un nombre precedido por una ampersand sigue a la letra R, por ejemplo:


(?(R&nombre)...)

la condición es verdadera si la recursión más reciente es a un grupo de ese nombre (que debe existir dentro del patrón).

Esta condición no comprueba toda la pila de recursión. Prueba solo el nivel actual. Si el nombre utilizado en una condición de este tipo es un duplicado, la prueba se aplica a todos los grupos del mismo nombre, y es verdadera si alguno de ellos es la recursión más reciente.

En el "nivel superior", todas estas condiciones de prueba de recursión son falsas.

Definición de grupos de captura para uso solo por referencia

Si la condición es la cadena (DEFINE), la condición es siempre falsa, incluso si hay un grupo con el nombre DEFINE. En este caso, solo puede haber una alternativa en el resto del grupo condicional. Siempre se omite si el control llega a este punto del patrón; la idea de DEFINE es que se puede usar para definir subrutinas a las que se puede hacer referencia desde otro lugar. (El uso de subrutinas se describe más abajo.) Por ejemplo, un patrón para hacer coincidir una dirección IPv4 como "192.168.23.245" podría escribirse así (ignorar espacios en blanco y saltos de línea):


(?(DEFINE) (?<byte> 2[0-4]\d | 25[0-5] | 1\d\d | [1-9]?\d) )
\b (?&byte) (\.(?&byte)){3} \b

La primera parte del patrón es un grupo DEFINE dentro del cual se define otro grupo llamado "byte". Este coincide con un componente individual de una dirección IPv4 (un número menor que 256). Cuando se produce la coincidencia, esta parte del patrón se omite porque DEFINE actúa como una condición falsa. El resto del patrón utiliza referencias al grupo con nombre para hacer coincidir los cuatro componentes de una dirección IPv4 separados por puntos, insistiendo en un límite de palabra en cada extremo.

Comprobación de la versión de PCRE2

Los programas que se enlazan con una biblioteca PCRE2 pueden comprobar la versión llamando a pcre2_config() con los argumentos apropiados. Los usuarios de aplicaciones que no tienen acceso al código subyacente no pueden hacer esto. Una "condición" especial llamada VERSION existe para permitir que dichos usuarios descubran con qué versión de PCRE2 están tratando utilizando esta condición para hacer coincidir una cadena como "síno". VERSION debe ir seguido de "=" o ">=" y un número de versión. Por ejemplo:


(?(VERSION>=10.4)sí|no)

Este patrón coincide con "sí" si la versión de PCRE2 es mayor o igual a 10.4, o "no" de lo contrario. La parte fraccionaria del número de versión podría omitirse.

Condiciones de aserción

Si la condición no tiene ninguno de los formatos anteriores, debe ser una aserción entre paréntesis. Puede ser una aserción de búsqueda anticipada (lookahead) o búsqueda retrospectiva (lookbehind) positiva o negativa. Sin embargo, debe ser una aserción atómica tradicional, no una de las aserciones no atómicas.

Considere este patrón, que de nuevo contiene espacios en blanco no significativos, y con las dos alternativas en la segunda línea:


(?(?=[^a-z]*[a-z])
\d{2}-[a-z]{3}-\d{2} | \d{2}-\d{2}-\d{2} )

La condición es una aserción de búsqueda anticipada positiva que coincide con una secuencia opcional de no letras seguida de una letra. En otras palabras, comprueba la presencia de al menos una letra en el sujeto. Si se encuentra una letra, el sujeto coincide con la primera alternativa; de lo contrario, coincide con la segunda. Este patrón coincide con cadenas en una de las dos formas dd-aaa-dd o dd-dd-dd, donde aaa son letras y dd son dígitos.

Cuando una aserción que es una condición contiene grupos de captura, cualquier captura que ocurra en una rama coincidente se retiene después, tanto para aserciones positivas como negativas, porque la coincidencia continúa siempre después de la aserción, ya tenga éxito o falle. (Comparar con aserciones no condicionales, para las cuales las capturas solo se retienen para aserciones positivas que tienen éxito.)

COMENTARIOS

Hay dos formas de incluir comentarios en patrones que son procesados por PCRE2. En ambos casos, el inicio del comentario no debe estar en una clase de caracteres, ni en medio de ninguna otra secuencia de caracteres relacionados como (?: o un nombre o número de grupo o un nombre de propiedad Unicode. Los caracteres que componen un comentario no juegan ningún papel en la coincidencia del patrón.

La secuencia (?# marca el inicio de un comentario que continúa hasta el siguiente paréntesis de cierre. No se permiten paréntesis anidados. Si la opción PCRE2_EXTENDED o PCRE2_EXTENDED_MORE está establecida, un carácter # sin escapar también introduce un comentario, que en este caso continúa hasta inmediatamente después del siguiente salto de línea o secuencia de caracteres en el patrón. Qué caracteres se interpretan como saltos de línea se controla mediante una opción pasada a la función de compilación o mediante una secuencia especial al inicio del patrón, como se describe en la sección titulada "Convenciones de saltos de línea" anterior. Tenga en cuenta que el final de este tipo de comentario es una secuencia de salto de línea literal en el patrón; las secuencias de escape que casualmente representan un salto de línea no cuentan. Por ejemplo, considere este patrón cuando PCRE2_EXTENDED está establecido, y la convención de salto de línea por defecto (un único carácter de salto de línea) está en vigor:


abc #comentario \n todavía comentario

Al encontrar el carácter #, pcre2_compile() avanza, buscando un salto de línea en el patrón. La secuencia \n sigue siendo literal en esta etapa, por lo que no termina el comentario. Solo un carácter real con el valor de código 0x0a (el salto de línea por defecto) lo hace.

PATRONES RECURSIVOS

Considere el problema de hacer coincidir una cadena entre paréntesis, permitiendo un número ilimitado de paréntesis anidados. Sin el uso de recursión, lo mejor que se puede hacer es usar un patrón que coincida hasta una profundidad de anidamiento fija. No es posible manejar una profundidad de anidamiento arbitraria.

Durante algún tiempo, Perl ha proporcionado una facilidad que permite que las expresiones regulares recursen (entre otras cosas). Lo hace interpolando código Perl en la expresión en tiempo de ejecución, y el código puede referirse a la expresión misma. Un patrón de Perl que utiliza la interpolación de código para resolver el problema de los paréntesis se puede crear así:


$re = qr{\( (?: (?>[^()]+) | (?p{$re}) )* \)}x;

El ítem (?p{...}) interpola código Perl en tiempo de ejecución, y en este caso se refiere recursivamente al patrón en el que aparece.

Obviamente, PCRE2 no puede soportar la interpolación de código Perl. En su lugar, soporta sintaxis especial para la recursión de todo el patrón, y también para la recursión de grupos de captura individuales. Después de su introducción en PCRE1 y Python, este tipo de recursión se introdujo posteriormente en Perl en la versión 5.10.

Un ítem especial que consiste en (? seguido de un número mayor que cero y un paréntesis de cierre es una llamada recursiva a subrutina del grupo de captura del número dado, siempre que ocurra dentro de ese grupo. (Si no es así, es una llamada a subrutina no recursiva, que se describe en la siguiente sección.) El ítem especial (?R) o (?0) es una llamada recursiva de toda la expresión regular.

Este patrón PCRE2 resuelve el problema de los paréntesis anidados (asuma que la opción PCRE2_EXTENDED está establecida para que se ignoren los espacios en blanco):


\( ( [^()]++ | (?R) )* \)

Primero coincide con un paréntesis de apertura. Luego coincide con cualquier número de subcadenas que pueden ser una secuencia

de no paréntesis, o una coincidencia recursiva del patrón en sí (es decir, una subcadena correctamente entre paréntesis). Finalmente, hay un paréntesis de cierre. Tenga en cuenta el uso de un cuantificador posesivo para evitar retroceder en secuencias de no paréntesis.

Si esto fuera parte de un patrón más grande, no querría recurrir a todo el patrón, por lo que en su lugar podría usar esto:


( \( ( [^()]++ | (?1) )* \) )

Hemos puesto el patrón entre paréntesis y hemos hecho que la recursión se refiera a ellos en lugar de a todo el patrón.

En un patrón más grande, hacer un seguimiento de los números de los paréntesis puede ser complicado. Esto se facilita mediante el uso de referencias relativas. En lugar de (?1) en el patrón anterior, puede escribir (?-2) para referirse a los paréntesis abiertos más recientemente, contando hacia atrás desde el punto en que se encuentra. En otras palabras, un número negativo cuenta los paréntesis de captura hacia la izquierda desde el punto en que se encuentran.

Tenga en cuenta, sin embargo, que si se utilizan números de grupo de captura duplicados, las referencias relativas se refieren al primer grupo con el número apropiado. Considere, por ejemplo:


(?|(a)|(b)) (c) (?-2)

Los dos primeros grupos de captura (a) y (b) son ambos numerados 1, y el grupo (c) es el número 2. Cuando se encuentra la referencia (?-2), los segundos paréntesis abiertos más recientemente tienen el número 1, pero es el primer grupo de este tipo (el grupo (a)) al que se refiere la recursión. Sería lo mismo si se utilizara una referencia absoluta (?1). En otras palabras, las referencias relativas son solo una abreviatura para calcular un número de grupo.

También es posible referirse a grupos de captura posteriores, escribiendo referencias como (?+2). Sin embargo, estos no pueden ser recursivos porque la referencia no está dentro de los paréntesis a los que se hace referencia. Siempre son llamadas de subrutina no recursivas, como se describe en la siguiente sección.

Un enfoque alternativo es usar paréntesis con nombre. La sintaxis de Perl para esto es (?&nombre); la sintaxis anterior de PCRE1 (?P>nombre) también es compatible. Podríamos reescribir el ejemplo anterior de la siguiente manera:


(?<pn> \( ( [^()]++ | (?&pn) )* \) )

Si hay más de un grupo con el mismo nombre, se utiliza el primero.

El patrón de ejemplo que hemos estado mirando contiene repeticiones ilimitadas anidadas, por lo que el uso de un cuantificador posesivo para hacer coincidir cadenas de no paréntesis es importante al aplicar el patrón a cadenas que no coinciden. Por ejemplo, cuando este patrón se aplica a


(aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa()

genera "sin coincidencia" rápidamente. Sin embargo, si no se usa un cuantificador posesivo, la coincidencia dura mucho tiempo porque hay muchas formas diferentes en que las repeticiones + y * pueden dividir el sujeto, y todas deben probarse antes de que se pueda informar del fallo.

Al final de una coincidencia, los valores de los paréntesis de captura son los del nivel más externo. Si desea obtener valores intermedios, se puede usar una función de llamada (consulte a continuación y la documentación de pcre2callout). Si el patrón anterior se compara con


(ab(cd)ef)

el valor de los paréntesis de captura internos (numerados 2) es "ef", que es el último valor tomado en el nivel superior. Si un grupo de captura no coincide en el nivel superior, su valor de captura final se establece en ninguno, incluso si se estableció (temporalmente) en un nivel más profundo durante el proceso de coincidencia.

No confunda el elemento (?R) con la condición (R), que prueba la recursión. Considere este patrón, que coincide con texto entre corchetes angulares, permitiendo anidamiento arbitrario. Solo se permiten dígitos en los corchetes anidados (es decir, al recursar), mientras que se permiten caracteres cualquiera en el nivel exterior.


< (?: (?(R) \d++ | [^<>]*+) | (?R)) * >

En este patrón, (?(R) es el inicio de un grupo condicional, con dos alternativas diferentes para los casos recursivos y no recursivos. El elemento (?R) es la llamada recursiva real.

Diferencias en el procesamiento de recursividad entre PCRE2 y Perl

Algunas diferencias anteriores entre PCRE2 y Perl ya no existen.

Antes de la versión 10.30, el procesamiento de recursividad en PCRE2 difería de Perl en que una llamada de subrutina recursiva siempre se trataba como un grupo atómico. Es decir, una vez que había hecho coincidir parte de la cadena del sujeto, nunca se volvía a entrar, incluso si contenía alternativas no probadas y había un fallo posterior en la coincidencia. (Nota histórica: PCRE implementó la recursividad antes que Perl).

A partir de la versión 10.30, las llamadas de subrutina recursiva ya no se tratan como atómicas. Es decir, se puede volver a entrar en ellas para probar alternativas no utilizadas si hay un fallo de coincidencia posterior en el patrón. Esto ahora es compatible con la forma en que funciona Perl. Si desea que una llamada de subrutina sea atómica, debe incluirla explícitamente en un grupo atómico.

La compatibilidad con el retroceso en las recursiones simplifica ciertos tipos de patrones recursivos. Por ejemplo, este patrón coincide con cadenas palindrómicas:


^((.)(?1)\2|.?)$

La segunda rama del grupo coincide con un solo carácter central en el palíndromo cuando hay un número impar de caracteres, o nada cuando hay un número par de caracteres, pero para funcionar tiene que poder probar el segundo caso cuando el resto del patrón no coincide. Si desea hacer coincidir frases palindrómicas típicas, el patrón tiene que ignorar todos los caracteres que no son de palabra, lo que se puede hacer así:


^\W*+((.)\W*+(?1)\W*+\2|\W*+.?)\W*+$

Si se ejecuta con la opción PCRE2_CASELESS, este patrón coincide con frases como "A man, a plan, a canal: Panama!". Tenga en cuenta el uso del cuantificador posesivo *+ para evitar retroceder en secuencias de caracteres que no son de palabra. Sin esto, PCRE2 tarda mucho más (diez veces o más) en hacer coincidir frases típicas, y Perl tarda tanto que se piensa que ha entrado en un bucle.

Otra forma en que PCRE2 y Perl solían diferir en su procesamiento de recursividad es en el manejo de valores capturados. Anteriormente en Perl, cuando un grupo se llamaba recursivamente o como subrutina (ver la siguiente sección), no tenía acceso a ningún valor que hubiera sido capturado fuera de la recursividad, mientras que en PCRE2 estos valores podían ser referenciados. Considere este patrón:


^(.)(\1|a(?2))

Este patrón coincide con "bab". Los primeros paréntesis de captura coinciden con "b", luego en el segundo grupo, cuando la referencia posterior \1 no coincide con "b", la segunda alternativa coincide con "a" y luego recurre. En la recursión, \1 ahora coincide con "b" y, por lo tanto, toda la coincidencia tiene éxito. Esta coincidencia solía fallar en Perl, pero en versiones posteriores (probé 5.024) ahora funciona.

Grupos como subrutinas

Si la sintaxis para una llamada de grupo recursiva (ya sea por número o por nombre) se usa fuera de los paréntesis a los que se refiere, opera un poco como una subrutina en un lenguaje de programación. Más precisamente, PCRE2 trata el grupo al que se hace referencia como un subpatrón independiente que intenta hacer coincidir en la posición de coincidencia actual. El grupo llamado puede definirse antes o después de la referencia. Una referencia numerada puede ser absoluta o relativa, como en estos ejemplos:


(...(absoluta)...)...(?2)...
(...(relativa)...)...(?-1)...
(...(?+1)...(relativa)...

Un ejemplo anterior señaló que el patrón


(sens|respons)e and \1ibility

coincide con "sense and sensibility" y "response and responsibility", pero no con "sense and responsibility". Si en cambio se usa el patrón


(sens|respons)e and (?1)ibility

coincide con "sense and responsibility" además de las otras dos cadenas. Otro ejemplo se da en la discusión de DEFINE anteriormente.

Al igual que las recursiones, las llamadas de subrutinas solían tratarse como atómicas, pero esto cambió en la versión 10.30 de PCRE2, por lo que ahora pueden ocurrir retrocesos en las llamadas de subrutinas. Sin embargo, cualquier paréntesis de captura que se establezca durante la llamada de subrutina vuelve a sus valores anteriores después.

Las opciones de procesamiento como la independencia de mayúsculas y minúsculas se fijan cuando se define un grupo, por lo que si se utiliza como subrutina, tales opciones no se pueden cambiar para diferentes llamadas. Por ejemplo, considere este patrón:


(abc)(?i:(?-1))

Coincide con "abcabc". No coincide con "abcABC" porque el cambio de la opción de procesamiento no afecta al grupo llamado.

El comportamiento de los verbos de control de retroceso en los grupos cuando se llaman como subrutinas se describe en la sección titulada "Verbos de retroceso en subrutinas" a continuación.

Recursividad y subrutinas con grupos de captura devueltos

Desde PCRE2 10.46, las llamadas de recursividad y subrutina también pueden especificar una lista de grupos de captura para devolver. Esta es una extensión de sintaxis de PCRE2 no compatible con Perl. La coincidencia de patrones recursiva en la expresión referenciada como se describe anteriormente, sin embargo, cuando la recursión regresa a la expresión que llama, los subgrupos capturados durante la recursión pueden conservarse cuando se restaura el contexto de la expresión que llama.

Cuando se utiliza como subrutina, esto permite que los grupos de captura de la subrutina se utilicen como valores de retorno.

Solo se conservarán los grupos de captura específicos enumerados por el llamador, utilizando la siguiente sintaxis:


(?R(grupolista)) recursión de patrón completo, devolviendo grupos de captura
(?n(grupolista)) )
(?+n(grupolista)) )
(?-n(grupolista)) ) llamada de subrutina, devolviendo grupos de captura
(?&nombre(grupolista)) )
(?P>nombre(grupolista)) )

La lista de grupos de captura "grupolista" es una lista separada por comas de números de grupo (absolutos o relativos) y nombres de grupo entrecomillados o entre corchetes angulares.

Aquí hay un ejemplo que primero usa la condición DEFINE para crear una rutina reutilizable para hacer coincidir un día de la semana, luego llama a esa subrutina y conserva los grupos que captura para usarlos más tarde:


(?x: # ignora espacios en blanco para mayor claridad
# Define la rutina "weekendday" que coincide con sábado o
# domingo, y devuelve el prefijo Sábado/Domingo como \k<short>.
(?(DEFINE) (?<weekendday>
(?|(?<short>Sat)urday|(?<short>Sun)day) ) )
# Llama a la rutina. Coincide con "Saturday,Sat" o "Sunday,Sun".
(?&weekendday(<short>)),\k<short> )

Esta característica no está disponible utilizando la sintaxis de Oniguruma \g<...> o \g'...' a continuación.

Sintaxis de subrutina de Oniguruma

Para compatibilidad con Oniguruma, la sintaxis no Perl \g seguida por un nombre o un número encerrado entre corchetes angulares o comillas simples, es una sintaxis alternativa para llamar a un grupo como una subrutina, posiblemente recursivamente. Aquí hay dos de los ejemplos utilizados anteriormente, reescritos usando esta sintaxis:


(?<pn> \( ( (?>[^()]+) | \g<pn> )* \) )
(sens|respons)e y \g'1'ibilidad

PCRE2 admite una extensión de Oniguruma: si a un número le precede un signo más o menos, se toma como una referencia relativa. Por ejemplo:


(abc)(?i:\g<-1>)

Tenga en cuenta que \g{...} (sintaxis Perl) y \g<...> (sintaxis de Oniguruma) *no* son sinónimos. El primero es una retroreferencia; el segundo es una llamada a subrutina.

LLAMADAS A FUNCIONES

Perl tiene una característica por la cual el uso de la secuencia (?{...}) hace que código Perl arbitrario sea obedecido en medio de la coincidencia de una expresión regular. Esto hace posible, entre otras cosas, extraer diferentes subcadenas que coinciden con el mismo par de paréntesis cuando hay una repetición.

PCRE2 proporciona una característica similar, pero por supuesto no puede obedecer código Perl arbitrario. La característica se llama "llamada a función" (callout). El llamador de PCRE2 proporciona una función externa colocando su punto de entrada en un contexto de coincidencia usando la función pcre2_set_callout(), y luego pasando ese contexto a pcre2_match() o pcre2_dfa_match(). Si no se pasa ningún contexto de coincidencia, o si el punto de entrada de la llamada a función se establece en NULL, los puntos de llamada a función se omitirán silenciosamente durante la coincidencia. Para deshabilitar las llamadas a función en la sintaxis del patrón, puede usar la opción PCRE2_EXTRA_NEVER_CALLOUT.

Dentro de una expresión regular, (?C<arg>) indica un punto en el que se debe llamar a la función externa. Hay dos tipos de llamadas a función: aquellas con un argumento numérico y aquellas con un argumento de cadena. (?C) solo sin argumento se trata como (?C0). Un argumento numérico permite a la aplicación distinguir entre diferentes llamadas a función. Los argumentos de cadena se añadieron para la versión 10.20 para hacer posible que los lenguajes de script que usan PCRE2 incrusten scripts cortos dentro de patrones de una manera similar a Perl.

Durante la coincidencia, cuando PCRE2 llega a un punto de llamada a función, se llama a la función externa. Se le proporciona el número o el argumento de cadena de la llamada a función, la posición en el patrón y un elemento de datos que también se establece en el bloque de coincidencia. La función de llamada a función puede hacer que la coincidencia continúe, que retroceda o que falle.

Por defecto, PCRE2 implementa una serie de optimizaciones en el momento de la coincidencia, y un efecto secundario es que a veces se omiten las llamadas a función. Si necesita que ocurran todas las llamadas a función posibles, necesita establecer opciones que deshabiliten las optimizaciones relevantes. Se proporcionan más detalles, incluida una descripción completa de la interfaz de programación para la función de llamada a función, en la documentación de pcre2callout.

Llamadas a función con argumentos numéricos

Si solo desea tener un medio para identificar diferentes puntos de llamada a función, coloque un número menor que 256 después de la letra C. Por ejemplo, este patrón tiene dos puntos de llamada a función:


(?C1)abc(?C2)def

Si el indicador PCRE2_AUTO_CALLOUT se pasa a pcre2_compile(), las llamadas a función numéricas se instalan automáticamente antes de cada elemento en el patrón. Todas tienen el número 255. Si hay un grupo condicional en el patrón cuya condición es una aserción, se inserta una llamada a función adicional justo antes de la condición. También se puede establecer una llamada a función explícita en esta posición, como en este ejemplo:


(?(?C9)(?=a)abc|def)

Tenga en cuenta que esto se aplica solo a las condiciones de aserción, no a otros tipos de condiciones.

Llamadas a función con argumentos de cadena

Se puede usar una cadena delimitada en lugar de un número como argumento de llamada a función. El delimitador de inicio debe ser uno de ` ' " ^ % # $ { y el delimitador de fin es el mismo que el de inicio, excepto para {, donde el delimitador de fin es }. Si el delimitador de fin se necesita dentro de la cadena, debe duplicarse. Por ejemplo:


(?C'ab ''c'' d')xyz(?C{cualquier texto})pqr

El duplicado se elimina antes de que la cadena se pase a la función de llamada a función.

CONTROL DE RETROCESO

Hay una serie de "Verbos de Control de Retroceso" especiales (para usar la terminología de Perl) que modifican el comportamiento del retroceso durante la coincidencia. Generalmente tienen la forma (*VERB) o (*VERB:NOMBRE). Algunos verbos aceptan ambas formas y pueden comportarse de manera diferente dependiendo de si está presente o no un argumento de nombre. Los nombres no son necesariamente únicos dentro del patrón.

Por defecto, para compatibilidad con Perl, un nombre es cualquier secuencia de caracteres que no incluya un paréntesis de cierre. El nombre no se procesa de ninguna manera, y no es posible incluir un paréntesis de cierre en el nombre. Esto se puede cambiar estableciendo la opción PCRE2_ALT_VERBNAMES, pero el resultado ya no es compatible con Perl.

Cuando PCRE2_ALT_VERBNAMES está establecido, se aplica el procesamiento de barras invertidas a los nombres de los verbos y solo un paréntesis de cierre sin escapar termina el nombre. Sin embargo, los únicos elementos de barra invertida permitidos son \Q, \E y secuencias como \x{100} que definen puntos de código de caracteres. Los escapes de tipo de carácter como \d generan un error.

Se puede incluir un paréntesis de cierre en un nombre, ya sea como \) o entre \Q y \E. Además del procesamiento de barras invertidas, si las opciones PCRE2_EXTENDED o PCRE2_EXTENDED_MORE también están establecidas, se omite el espacio en blanco sin escapar en los nombres de los verbos, y se reconocen los comentarios #- (comentarios), exactamente como en el resto del patrón. PCRE2_EXTENDED y PCRE2_EXTENDED_MORE no afectan a los nombres de los verbos a menos que PCRE2_ALT_VERBNAMES también esté establecido.

La longitud máxima de un nombre es de 255 en la biblioteca de 8 bits y 65535 en las bibliotecas de 16 y 32 bits. Si el nombre está vacío, es decir, si el paréntesis de cierre sigue inmediatamente a los dos puntos, el efecto es como si los dos puntos no estuvieran allí. Se puede usar cualquier número de estos verbos en un patrón. Excepto (*ACCEPT), no se pueden cuantificar.

Dado que estos verbos están relacionados específicamente con el retroceso, la mayoría de ellos solo se pueden usar cuando el patrón debe coincidir utilizando la función de coincidencia tradicional o JIT, ya que utilizan algoritmos de retroceso. Con la excepción de (*FAIL), que se comporta como una aserción negativa fallida, los verbos de control de retroceso causan un error si los encuentra la función de coincidencia DFA.

El comportamiento de estos verbos en grupos repetidos, aserciones y en grupos de captura llamados como subrutinas (ya sea recursivamente o no) se documenta a continuación.

Optimizaciones que afectan a los verbos de retroceso

PCRE2 contiene algunas optimizaciones que se utilizan para acelerar la coincidencia ejecutando algunas comprobaciones al inicio de cada intento de coincidencia. Por ejemplo, puede conocer la longitud mínima del sujeto que coincide, o que debe estar presente un carácter en particular. Cuando una de estas optimizaciones omite la ejecución de una coincidencia, los verbos de retroceso incluidos, por supuesto, no se procesarán. Puede suprimir las optimizaciones de inicio de coincidencia estableciendo la opción PCRE2_NO_START_OPTIMIZE al llamar a pcre2_compile(), llamando a pcre2_set_optimize() con una directiva PCRE2_START_OPTIMIZE_OFF, o iniciando el patrón con (*NO_START_OPT). Hay más discusión sobre esta opción en la sección titulada "Compilación de un patrón" en la documentación de pcre2api.

Los experimentos con Perl sugieren que también tiene optimizaciones similares, y al igual que PCRE2, desactivarlas puede cambiar el resultado de una coincidencia.

Verbos que actúan inmediatamente

Los siguientes verbos actúan tan pronto como se encuentran.


(*ACCEPT) o (*ACCEPT:NOMBRE)

Este verbo hace que la coincidencia termine con éxito, omitiendo el resto del patrón. Sin embargo, cuando está dentro de un grupo de captura que se llama como una subrutina, solo ese grupo termina con éxito. Luego, la coincidencia continúa en el nivel exterior. Si (*ACCEPT) se activa en una aserción positiva, la aserción tiene éxito; en una aserción negativa, la aserción falla.

Si (*ACCEPT) está dentro de paréntesis de captura, los datos hasta el momento se capturan. Por ejemplo:


A((?:A|B(*ACCEPT)|C)D)

Esto coincide con "AB", "AAD" o "ACD"; cuando coincide con "AB", "B" es capturado por los paréntesis exteriores.

(*ACCEPT) es el único verbo de retroceso que puede ser cuantificado porque una cuantificación perezosa con un mínimo de cero actúa solo cuando ocurre un retroceso. Considere, por ejemplo,


(A(*ACCEPT)??B)C

donde A, B y C pueden ser expresiones complejas. Después de coincidir con "A", el casador procesa "BC"; si eso falla, causando un retroceso, (*ACCEPT) se activa y la coincidencia tiene éxito. En ambos casos, todo excepto C se captura. Mientras que (*COMMIT) (ver abajo) significa "fallar en el retroceso", un (*ACCEPT) repetido de este tipo significa "tener éxito en el retroceso".

Advertencia: (*ACCEPT) no debe usarse dentro de un grupo de ejecución de script, ya que provoca una salida inmediata del grupo, omitiendo la verificación de ejecución del script.


(*FAIL) o (*FAIL:NOMBRE)

Este verbo causa un fallo de coincidencia, forzando el retroceso. Puede abreviarse como (*F). Es equivalente a (?!) pero más fácil de leer. La documentación de Perl señala que probablemente solo sea útil cuando se combina con (?{}) o (??{}). Esas son, por supuesto, características de Perl que no están presentes en PCRE2. El equivalente más cercano es la característica de llamada a función, como por ejemplo en este patrón:


a+(?C)(*FAIL)

Una coincidencia con la cadena "aaaa" siempre falla, pero la llamada a función se realiza antes de cada retroceso (en este ejemplo, 10 veces).

(*ACCEPT:NOMBRE) y (*FAIL:NOMBRE) se comportan como (*MARK:NOMBRE)(*ACCEPT) y (*MARK:NOMBRE)(*FAIL), respectivamente, es decir, se registra un (*MARK) justo antes de que actúe el verbo.

Grabación de la ruta tomada

Existe un verbo cuyo propósito principal es rastrear cómo se llegó a una coincidencia, aunque también tiene un uso secundario en conjunto con el avance del punto de inicio de la coincidencia (ver (*SKIP) más abajo).


(*MARK:NOMBRE) o (*:NOMBRE)

Siempre se requiere un nombre con este verbo. Para todos los demás verbos de control de retroceso, el argumento NOMBRE es opcional.

Cuando una coincidencia tiene éxito, el nombre de la última marca encontrada en la ruta de la coincidencia se devuelve al llamador, como se describe en la sección titulada "Otra información sobre la coincidencia" en la documentación de pcre2api. Esto se aplica a todas las instancias de (*MARK) y otros verbos, incluidos aquellos dentro de aserciones y grupos atómicos. Sin embargo, hay diferencias en esos casos cuando (*MARK) se usa en conjunto con (*SKIP), como se describe a continuación.

Se devuelve el nombre de la marca encontrada más recientemente en la ruta de la coincidencia. Un verbo sin argumento NOMBRE se ignora para este propósito. Aquí hay un ejemplo de la salida de pcre2test, donde el modificador "mark" solicita la recuperación y la salida de datos de (*MARK):


re> /X(*MARK:A)Y|X(*MARK:B)Z/mark
data> XY
0: XY
MK: A
XZ
0: XZ
MK: B

El nombre de (*MARK) se etiqueta con "MK:" en esta salida, y en este ejemplo indica cuál de las dos alternativas coincidió. Esta es una forma más eficiente de obtener esta información que poner cada alternativa en sus propios paréntesis de captura.

Si se encuentra un verbo con un nombre en una aserción positiva que es verdadera, el nombre se registra y se devuelve si es el último encontrado. Esto no sucede para aserciones negativas o aserciones positivas fallidas.

Después de una coincidencia parcial o una coincidencia fallida, se devuelve el último nombre encontrado en todo el proceso de coincidencia. Por ejemplo:


re> /X(*MARK:A)Y|X(*MARK:B)Z/mark
data> XP
No match, mark = B

Tenga en cuenta que en este ejemplo sin anclar, la marca se conserva del intento de coincidencia que comenzó en la letra "X" del sujeto. Los intentos de coincidencia posteriores que comienzan en "P" y luego con una cadena vacía no llegan hasta el elemento (*MARK), pero aun así no lo restablecen.

Si está interesado en los valores de (*MARK) después de coincidencias fallidas, probablemente debería establecer la opción PCRE2_NO_START_OPTIMIZE o llamar a pcre2_set_optimize() con una directiva PCRE2_START_OPTIMIZE_OFF (ver arriba) para asegurarse de que la coincidencia siempre se intente.

Verbos que actúan después del retroceso

Los siguientes verbos no hacen nada cuando se encuentran. La coincidencia continúa con lo que sigue, pero si hay una falla posterior de coincidencia, que causa un retroceso al verbo, se fuerza una falla. Es decir, el retroceso no puede pasar a la izquierda del verbo. Sin embargo, cuando uno de estos verbos aparece dentro de un grupo atómico o en una aserción de mirada atómica que es verdadera, su efecto se limita a ese grupo, ya que una vez que se ha emparejado el grupo, nunca hay retroceso en él. El retroceso desde más allá de una aserción o grupo atómico ignora todo el grupo y busca un punto de retroceso anterior.

Estos verbos difieren en exactamente qué tipo de falla ocurre cuando el retroceso llega a ellos. El comportamiento descrito a continuación es lo que sucede cuando el verbo no está en una subrutina o una aserción. Las secciones posteriores cubren estos casos especiales.


(*COMMIT) o (*COMMIT:NOMBRE)

Este verbo causa que toda la coincidencia falle rotundamente si hay una falla de coincidencia posterior que hace que el retroceso llegue a él. Incluso si el patrón no está anclado, no se realizan más intentos de encontrar una coincidencia avanzando el punto de inicio. Si (*COMMIT) es el único verbo de retroceso que se encuentra, una vez que se ha pasado, pcre2_match() está comprometido a encontrar una coincidencia en el punto de inicio actual, o no en absoluto.

Por ejemplo:


a+(*COMMIT)b

Esto coincide con "xxaab" pero no con "aacaab". Puede considerarse una especie de ancla dinámica, o "He empezado, así que debo terminar".

El comportamiento de (*COMMIT:NOMBRE) no es el mismo que (*MARK:NOMBRE)(*COMMIT). Es como (*MARK:NOMBRE) en que el nombre se recuerda para devolverlo al llamador. Sin embargo, (*SKIP:NOMBRE) solo busca nombres que se establecen con (*MARK), ignorando los establecidos por cualquiera de los otros verbos de retroceso.

Si hay más de un verbo de retroceso en un patrón, es posible que se active primero uno diferente que siga a (*COMMIT), por lo que simplemente pasar por (*COMMIT) durante una coincidencia no garantiza siempre que una coincidencia deba estar en este punto de inicio.

Tenga en cuenta que (*COMMIT) al principio de un patrón no es lo mismo que un ancla, a menos que las optimizaciones de inicio de coincidencia de PCRE2 estén desactivadas, como se muestra en esta salida de pcre2test:


re> /(*COMMIT)abc/
data> xyzabc
0: abc
data>
re> /(*COMMIT)abc/no_start_optimize
data> xyzabc
No match

Para el primer patrón, PCRE2 sabe que cualquier coincidencia debe comenzar con "a", por lo que la optimización salta a lo largo del sujeto hasta "a" antes de aplicar el patrón al primer conjunto de datos. El intento de coincidencia tiene éxito. El segundo patrón desactiva la optimización que salta hasta el primer carácter. El patrón ahora se aplica comenzando en "x", y por lo tanto (*COMMIT) hace que la coincidencia falle sin intentar ningún otro punto de inicio.


(*PRUNE) o (*PRUNE:NOMBRE)

Este verbo provoca que la coincidencia falle en la posición de inicio actual en el sujeto si hay una falla de coincidencia posterior que hace que el retroceso llegue a él. Si el patrón no está anclado, se produce el avance normal de "bumpalong" al siguiente carácter de inicio. El retroceso puede ocurrir como de costumbre a la izquierda de (*PRUNE), antes de que se alcance, o al coincidir a la derecha de (*PRUNE), pero si no hay coincidencia a la derecha, el retroceso no puede cruzar (*PRUNE). En casos simples, el uso de (*PRUNE) es simplemente una alternativa a un grupo atómico o un cuantificador posesivo, pero hay algunos usos de (*PRUNE) que no se pueden expresar de ninguna otra manera. En un patrón anclado, (*PRUNE) tiene el mismo efecto que (*COMMIT).

El comportamiento de (*PRUNE:NOMBRE) no es el mismo que (*MARK: NOMBRE)(*PRUNE). Es como (*MARK: NOMBRE) en que el nombre se recuerda para devolverlo al llamador. Sin embargo, (*SKIP: NOMBRE) solo busca nombres establecidos con (*MARK), ignorando los establecidos por otros verbos de retroceso.


(*SKIP)

Este verbo, cuando se da sin nombre, es como (*PRUNE), excepto que si el patrón no está anclado, el avance de "bumpalong" no es al siguiente carácter, sino a la posición en el sujeto donde se encontró (*SKIP). (*SKIP) significa que cualquier texto que coincidió hasta él no puede ser parte de una coincidencia exitosa si hay una falla posterior. Considere:


a+(*SKIP)b

Si el sujeto es "aaaac...", después de que el primer intento de coincidencia falla (comenzando en el primer carácter de la cadena), el punto de inicio salta para comenzar el siguiente intento en "c". Tenga en cuenta que un cuantificador posesivo no tiene el mismo efecto que este ejemplo; aunque suprimiría el retroceso durante el primer intento de coincidencia, el segundo intento comenzaría en el segundo carácter en lugar de saltar a "c".

Si (*SKIP) se utiliza para especificar una nueva posición de inicio que es la misma que la posición de inicio de la coincidencia actual, o (al estar dentro de una mirada hacia atrás) anterior, la posición especificada por (*SKIP) se ignora y, en cambio, se produce el "bumpalong" normal.


(*SKIP:NOMBRE)

Cuando (*SKIP) tiene un nombre asociado, su comportamiento se modifica. Cuando se activa un (*SKIP) de este tipo, la ruta anterior a través del patrón se busca para encontrar la marca (*MARK) más reciente que tenga el mismo nombre. Si se encuentra una, el avance de "bumpalong" se realiza a la posición del sujeto que corresponde a esa (*MARK) en lugar de a donde se encontró (*SKIP). Si no se encuentra ninguna (*MARK) con un nombre coincidente, se ignora (*SKIP).

La búsqueda de un nombre de (*MARK) utiliza el mecanismo de retroceso normal, lo que significa que no ve las configuraciones de (*MARK) que están dentro de grupos atómicos o aserciones, porque nunca se vuelven a ingresar por retroceso. Compare los siguientes ejemplos de pcre2test:


re> /a(?>(*MARK:X))(*SKIP:X)(*F)|(.)/
data: abc
0: a
1: a
data:
re> /a(?:(*MARK:X))(*SKIP:X)(*F)|(.)/
data: abc
0: b
1: b

En el primer ejemplo, la configuración de (*MARK) está en un grupo atómico, por lo que no se ve cuando se activa (*SKIP:X), lo que hace que (*SKIP) se ignore. Esto permite que la segunda rama del patrón se pruebe en la primera posición de carácter. En el segundo ejemplo, la configuración de (*MARK) no está en un grupo atómico. Esto permite que (*SKIP:X) encuentre la (*MARK) cuando retrocede, y esto hace que un nuevo intento de coincidencia comience en el segundo carácter. Esta vez, la (*MARK) nunca se ve porque "a" no coincide con "b", por lo que el comparador salta inmediatamente a la segunda rama del patrón.

Tenga en cuenta que (*SKIP:NOMBRE) solo busca nombres establecidos por (*MARK:NOMBRE). Ignora los nombres establecidos por otros verbos de retroceso.


(*THEN) o (*THEN:NOMBRE)

Este verbo provoca un salto a la siguiente alternativa más interna cuando el retroceso llega a él. Es decir, cancela cualquier retroceso adicional dentro de la alternativa actual. Su nombre proviene de la observación de que se puede usar para un bloque if-then-else basado en patrones:

Si el patrón COND1 coincide, se prueba FOO (y posiblemente elementos adicionales después del final del grupo si FOO tiene éxito); en caso de falla, el comparador salta a la segunda alternativa y prueba COND2, sin retroceder en COND1. Si eso tiene éxito y BAR falla, se prueba COND3. Si posteriormente BAZ falla, no hay más alternativas, por lo que hay un retroceso a lo que vino antes del grupo completo. Si (*THEN) no está dentro de una alternancia, actúa como (*PRUNE).

El comportamiento de (*THEN: NOMBRE) no es el mismo que (*MARK: NOMBRE)(*THEN). Es como (*MARK: NOMBRE) en que el nombre se recuerda para devolverlo al llamador. Sin embargo, (*SKIP: NOMBRE) solo busca nombres establecidos con (*MARK), ignorando los establecidos por otros verbos de retroceso.

Control Verbs

PCRE2 supports a number of control verbs that can be used to influence the way that backtracking is handled. They are all of the form (*VERB) or (*VERB:NAME) or (*VERB:INT) where VERB is one of the verbs described below. The characters VERB can be uppercase or lowercase. NAME is an identifier, and INT is a non-negative integer. Backtracking verbs are only permitted in specific contexts; a complete list is given in the pcre2syntax page.

The verbs are:

  • (*ACCEPT)

This section describes the effect of verbs that influence backtracking when a subsequent part of the match fails. These are (*ACCEPT), (*COMMIT), (*CURTAIN), (*FAIL), (*PRUNE), (*SKIP), and (*THEN).

Alternating control

When a pattern contains alternatives, separated by the | character, the default behaviour is that if a match attempt starting from the beginning of an alternative fails, matching is abandoned, and a new attempt is made starting at the next character (if the pattern is not anchored). If an alternative fails part way through, matching may backtrack into previous parts of the pattern, potentially trying different alternatives at earlier stages.

Control verbs can change this behaviour. They come into play when a failure occurs *after* the verb has been encountered during the matching process. The verb's action is then executed.

Consider this pattern, where A, B, etc. are complex pattern fragments that do not contain any | characters at this level:


A (B(*THEN)C) | D

If A and B are matched, but there is a failure in C, matching does not backtrack into A; instead it moves to the next alternative, that is, D. However, if the group containing (*THEN) is given an alternative, it behaves differently:


A (B(*THEN)C | (*FAIL)) | D

The effect of (*THEN) is now confined to the inner group. After a failure in C, matching moves to (*FAIL), which causes the whole group to fail because there are no more alternatives to try. In this case, matching does backtrack into A.

Note that a conditional group is not considered as having two alternatives, because only one is ever used. In other words, the | character in a conditional group has a different meaning. Ignoring white space, consider:


^.*? (?(?=a) a | b(*THEN)c )

If the subject is "ba", this pattern does not match. Because .*? is ungreedy, it initially matches zero characters. The condition (?=a) then fails, the character "b" is matched, but "c" is not. At this point, matching does not backtrack to .*? as might perhaps be expected from the presence of the | character. The conditional group is part of the single alternative that comprises the whole pattern, and so the match fails. (If there was a backtrack into .*?, allowing it to match "b", the match would succeed.)

The verbs just described provide four different "strengths" of control when subsequent matching fails. (*THEN) is the weakest, carrying on the match at the next alternative. (*PRUNE) comes next, failing the match at the current starting position, but allowing an advance to the next character (for an unanchored pattern). (*SKIP) is similar, except that the advance may be more than one character. (*COMMIT) is the strongest, causing the entire match to fail.

More than one backtracking verb

If more than one backtracking verb is present in a pattern, the one that is backtracked onto first acts. For example, consider this pattern, where A, B, etc. are complex pattern fragments:


(A(*COMMIT)B(*THEN)C|ABD)

If A matches but B fails, the backtrack to (*COMMIT) causes the entire match to fail. However, if A and B match, but C fails, the backtrack to (*THEN) causes the next alternative (ABD) to be tried. This behaviour is consistent, but is not always the same as Perl's. It means that if two or more backtracking verbs appear in succession, all but the last of them has no effect. Consider this example:


...(*COMMIT)(*PRUNE)...

If there is a matching failure to the right, backtracking onto (*PRUNE) causes it to be triggered, and its action is taken. There can never be a backtrack onto (*COMMIT).

Backtracking verbs in repeated groups

PCRE2 sometimes differs from Perl in its handling of backtracking verbs in repeated groups. For example, consider:


/(a(*COMMIT)b)+ac/

If the subject is "abac", Perl matches unless its optimizations are disabled, but PCRE2 always fails because the (*COMMIT) in the second repeat of the group acts.

Backtracking verbs in assertions

(*FAIL) in any assertion has its normal effect: it forces an immediate backtrack. The behaviour of the other backtracking verbs depends on whether or not the assertion is standalone or acting as the condition in a conditional group.

(*ACCEPT) in a standalone positive assertion causes the assertion to succeed without any further processing; captured strings and a mark name (if set) are retained. In a standalone negative assertion, (*ACCEPT) causes the assertion to fail without any further processing; captured substrings and any mark name are discarded.

If the assertion is a condition, (*ACCEPT) causes the condition to be true for a positive assertion and false for a negative one; captured substrings are retained in both cases.

The remaining verbs act only when a later failure causes a backtrack to reach them. This means that, for the Perl-compatible assertions, their effect is confined to the assertion, because Perl lookaround assertions are atomic. A backtrack that occurs after such an assertion is complete does not jump back into the assertion. Note in particular that a (*MARK) name that is set in an assertion is not "seen" by an instance of (*SKIP:NAME) later in the pattern.

PCRE2 now supports non-atomic positive assertions and also "scan substring" assertions, as described in the sections entitled "Non-atomic assertions" and "Scan substring assertions" above. These assertions must be standalone (not used as conditions). They are not Perl-compatible. For these assertions, a later backtrack does jump back into the assertion, and therefore verbs such as (*COMMIT) can be triggered by backtracks from later in the pattern.

The effect of (*THEN) is not allowed to escape beyond an assertion. If there are no more branches to try, (*THEN) causes a positive assertion to be false, and a negative assertion to be true. This behaviour differs from Perl when the assertion has only one branch.

The other backtracking verbs are not treated specially if they appear in a standalone positive assertion. In a conditional positive assertion, backtracking (from within the assertion) into (*COMMIT), (*SKIP), or (*PRUNE) causes the condition to be false. However, for both standalone and conditional negative assertions, backtracking into (*COMMIT), (*SKIP), or (*PRUNE) causes the assertion to be true, without considering any further alternative branches.

Backtracking verbs in subroutines

These behaviours occur whether or not the group is called recursively.

(*ACCEPT) in a group called as a subroutine causes the subroutine match to succeed without any further processing. Matching then continues after the subroutine call. Perl documents this behaviour. Perl's treatment of the other verbs in subroutines is different in some cases.

(*FAIL) in a group called as a subroutine has its normal effect: it forces an immediate backtrack.

(*COMMIT), (*SKIP), and (*PRUNE) cause the subroutine match to fail when triggered by being backtracked to in a group called as a subroutine. There is then a backtrack at the outer level.

(*THEN), when triggered, skips to the next alternative in the innermost enclosing group that has alternatives (its normal behaviour). However, if there is no such group within the subroutine's group, the subroutine match fails and there is a backtrack at the outer level.

EBCDIC ENVIRONMENTS

Differences in the way PCRE behaves when it is running in an EBCDIC environment are covered in this section.

Escape sequences

When PCRE2 is compiled in EBCDIC mode, \N{U+hhh..} is not supported. \a, \e, \f, \n, \r, and \t generate the appropriate EBCDIC code values. The \c escape is processed as specified for Perl in the perlebcdic document. The only characters that are allowed after \c are A-Z, a-z, or one of @, [, \, ], ^, _, or ?. Any other character provokes a compile-time error. The sequence \c@ encodes character code 0; after \c the letters (in either case) encode characters 1-26 (hex 01 to hex 1A); [, \, ], ^, and _ encode characters 27-31 (hex 1B to hex 1F), and \c? becomes either 255 (hex FF) or 95 (hex 5F).

Thus, apart from \c?, these escapes generate the same character code values as they do in an ASCII or Unicode environment, though the meanings of the values mostly differ. For example, \cG always generates code value 7, which is BEL in ASCII but DEL in EBCDIC.

The sequence \c? generates DEL (127, hex 7F) in an ASCII environment, but because 127 is not a control character in EBCDIC, Perl makes it generate the APC character. Unfortunately, there are several variants of EBCDIC. In most of them the APC character has the value 255 (hex FF), but in the one Perl calls POSIX-BC its value is 95 (hex 5F). If certain other characters have POSIX-BC values, PCRE2 makes \c? generate 95; otherwise it generates 255.

Character classes

In character classes there is a special case in EBCDIC environments for ranges whose end points are both specified as literal letters in the same case. For compatibility with Perl, EBCDIC code points within the range that are not letters are omitted. For example, [h-k] matches only four characters, even though the EBCDIC codes for h and k are 0x88 and 0x92, a range of 11 code points. However, if the range is specified numerically, for example, [\x88-\x92] or [h-\x92], all code points are included.
