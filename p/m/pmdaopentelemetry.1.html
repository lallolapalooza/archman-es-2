PMDAOPENTELEMETRY(1) Manual de Comandos Generales PMDAOPENTELEMETRY(1)

NOMBRE

pmdaopentelemetry - PMDA de OpenTelemetry

SINOPSIS

$PCP_PMDAS_DIR/opentelemetry/pmdaopentelemetry [-D] [-n] [-c config] [-d dominio] [-l archivo_log] [-r raiz] [-t tiempo_espera] [-u usuario]

DESCRIPCIÓN

pmdaopentelemetry es un Agente de Dominio de Métricas de Rendimiento (PMDA) que crea dinámicamente métricas de PCP a partir de puntos finales de OpenTelemetry configurados que proporcionan acceso basado en HTTP a métricas de aplicaciones.

El directorio config por defecto es $PCP_PMDAS_DIR/opentelemetry/config.d/, consulte "FUENTES DE CONFIGURACIÓN" a continuación. El tiempo_espera por defecto para recuperar URL es de 2 segundos. El usuario por defecto, si no se especifica con la opción -u, es el usuario "pcp". Si se proporciona la opción -n, la lista de archivos de configuración no se ordenará antes de procesarla. Esta lista se ordena por defecto, pero eso puede ser costoso si hay un gran número de archivos de configuración (URL y/o scripts).

Si se proporciona la opción -D, se escribirán mensajes diagnósticos adicionales en el archivo de log del PMDA, que es $PCP_LOG_DIR/pmcd/opentelemetry.log por defecto (consulte también -l a continuación). Además, la métrica opentelemetry.control.debug controla el mismo indicador de depuración y se puede configurar con el siguiente comando:

pmstore opentelemetry.control.debug valor

donde valor es 1 (para habilitar mensajes de log detallados) o 0 (para deshabilitar mensajes de log detallados). Esto es particularmente útil para examinar las cabeceras http pasadas a cada solicitud de recuperación, la configuración de filtros y otros detalles de procesamiento que se registran cuando el indicador de depuración está habilitado.

La opción -d puede usarse para anular el número de dominio de métricas de rendimiento por defecto, que es 164. Se recomienda encarecidamente no cambiarlo. El número de dominio debe ser diferente para cada PMDA en un mismo host, y se debe usar el mismo número de dominio para el PMDA pmdaopentelemetry en todos los hosts. Consulte también la opción -r, que permite cambiar la raíz del espacio de nombres dinámico de la predeterminada opentelemetry.

La opción -l puede usarse para especificar archivo_log como destino de los mensajes del PMDA en lugar del valor por defecto, $PCP_LOG_DIR/pmcd/opentelemetry.log. Como caso especial, archivo_log puede ser "-" para enviar mensajes al flujo stderr en su lugar, por ejemplo, -l-. Este sería normalmente el flujo stderr para el proceso padre, pmcd(1), que puede tener su stderr redirigido. Esta redirección es normalmente más útil en un entorno contenedorizado, o cuando se usa dbpmda(1).

La opción -r permite cambiar la raíz del espacio de nombres dinámico a raiz desde la predeterminada, opentelemetry. En conjunción con otras opciones de línea de comandos, esto permite que pmdaopentelemetry se despliegue como un PMDA diferente con un espacio de nombres de métricas y un dominio de métricas distintos en el mismo sistema host. Tenga en cuenta que todos los PMDA requieren un número de dominio único, por lo que la opción -d también debe especificarse. El uso de la opción -r también puede cambiar los valores predeterminados para algunas otras opciones de línea de comandos, por ejemplo, el nombre del archivo de log por defecto y el directorio de configuración por defecto.

FUENTES DE CONFIGURACIÓN

Mientras se ejecuta, pmdaopentelemetry escanea periódicamente de forma recursiva el directorio $PCP_PMDAS_DIR/opentelemetry/config.d (o el directorio especificado con la opción -c), buscando archivos de URL de origen (*.url) y scripts o binarios ejecutables. Cualquier archivo que no tenga el sufijo .url o que no sea ejecutable, se ignora; esto permite que archivos de documentación como "README" y definiciones de funciones de script no ejecutables "common" estén presentes sin ser considerados como archivos de configuración.

Un servidor remoto no tiene que estar en funcionamiento o seguir funcionando; el PMDA tolera URL remotos que pueden aparecer y desaparecer con el tiempo. El PMDA transmitirá datos y metadatos cuando/si están disponibles, y devolverá errores cuando/si están caídos. Los IDs de métricas de PCP, los identificadores de dominio de instancia internos y externos se persisten y se restaurarán cuando las fuentes de métricas individuales estén disponibles y/o cuando se reinicie el PMDA. Además, el PMDA comprueba las marcas de tiempo de modificación del directorio y re-escaneará dinámicamente los archivos de configuración nuevos o modificados. *No* es necesario reiniciar el PMDA al agregar, eliminar o modificar archivos de configuración.

FUENTES URL

Cada archivo con el sufijo .url encontrado en el directorio de configuración o subdirectorio contiene una URL HTTP o HTTPS completa en la que pmdaopentelemetry puede alcanzar un punto final de OpenTelemetry. También se admite el acceso a archivos locales con una URL convencional file:///alguna_ruta/algún_archivo, en cuyo caso alguna_ruta/algún_archivo debería contener datos de métricas formateados en OpenTelemetry.

La primera línea de un archivo de configuración .url debe ser la URL, como se describió anteriormente. Las líneas subsiguientes, si las hay, se prefijan con una palabra clave que se puede usar para alterar la solicitud GET http. Una palabra clave debe terminar con dos puntos : y el texto se extiende hasta el final de la línea. Las líneas de comentario que comienzan con # y las líneas en blanco se ignoran. Las únicas palabras clave actualmente admitidas son HEADER: y FILTER:.

HEADER: nombre_cabecera: valor ... hasta el final de la línea
Agrega nombre_cabecera y su valor a las cabeceras pasadas en la solicitud GET http para la URL configurada. Un archivo de configuración de ejemplo que proporciona 3 cabeceras comúnmente usadas y un token de autenticación podría ser:


http://algunhost/ruta/endpoint.html
# este es un comentario
HEADER: Accept: text/html
HEADER: Keep-Alive: 300
HEADER: Connection: keep-alive
HEADER: Authorization: token ABCDEF1234567890

Como se mencionó anteriormente, los valores de las cabeceras se extienden hasta el final de la línea. Pueden contener cualquier carácter válido, incluidos los dos puntos. Múltiples espacios se colapsarán en un solo espacio, y los espacios al principio y al final se recortarán. Un uso común para las cabeceras es configurar un agente proxy y los parámetros asociados que pueda requerir.

FILTRADO DE MÉTRICAS

El filtrado de métricas es una característica del archivo de configuración que permite incluir o excluir, es decir, filtrar, las métricas ingeridas. Esto es útil porque la mayoría de los puntos finales devuelven múltiples métricas, y generalmente solo algunas son interesantes para fines de monitoreo. La sintaxis es:
FILTER: INCLUDE METRIC regex
o
FILTER: EXCLUDE METRIC regex
Los nombres de métricas creados dinámicamente que coinciden con regex se incluirán o excluirán del espacio de nombres, según lo especificado. Tenga en cuenta que solo el componente hoja del nombre de la métrica en el PMNS (tal como se ingiere de la fuente URL) se compara con el patrón regex. La regla simple es que el primer filtro regex coincidente para un nombre de hoja de métrica particular es la regla que prevalece. Si no coincide ningún regex de filtro (o no hay filtros), entonces la métrica se incluye por defecto, es decir, el filtro por defecto si no se especifica ninguno es FILTER: INCLUDE METRIC .* Esto es compatible con versiones anteriores del archivo de configuración que no admitían filtros. Normalmente se usarían múltiples líneas FILTER:, por ejemplo, para incluir algunas métricas pero excluir todas las demás, use FILTER: EXCLUDE METRIC .* como la última de varias filtros que incluyen las métricas deseadas. Por el contrario, para excluir algunas métricas pero incluir todas las demás, use FILTER: EXCLUDE METRIC regex. En este caso no es necesario (aunque no perjudica) especificar el final FILTER: INCLUDE METRIC .* porque, como se indicó anteriormente, cualquier métrica que no coincida con ningún regex de filtro se incluirá por defecto.

FILTRADO DE ETIQUETAS

El filtrado de etiquetas utiliza una sintaxis y semántica similar de FILTER: a la del filtrado de métricas. FILTER: EXCLUDE LABEL regex eliminará todas las etiquetas con nombres de etiqueta que coincidan con regex de todas las métricas definidas por el archivo de configuración. Las mismas reglas que para los filtros de métricas se aplican también a los filtros de etiquetas; una regla implícita: FILTER: INCLUDE LABEL .* se aplica a todas las etiquetas que no coincidan con ninguna regla de filtro anterior. FILTRADO Y NOMBRES DE INSTANCIA

Las etiquetas de métrica devueltas (es decir, incluidas), pero no se deben usar como parte de los nombres de instancia externos. Todas las etiquetas incluidas que no son opcionales (es decir, las etiquetas intrínsecas) se concatenarán y se utilizarán para la denominación externa de instancias. Además, las etiquetas no intrínsecas (es decir, las etiquetas marcadas como OPCIONAL) tendrán el indicador PM_LABEL_OPTIONAL establecido en los conjuntos de etiquetas devueltos por las devoluciones de llamada de notes. Este indicador afecta cómo se utilizan las etiquetas en ciertos clientes. Para obtener más detalles, consulte pmLookupLabels(3) y las páginas de manual relacionadas para obtener más detalles. Tenga en cuenta que los nombres de instancia externos comienzan con el identificador numérico único interno de la instancia seguido de un espacio, por lo que los nombres de instancia externos son siempre únicos.

Se necesita precaución con el filtrado de etiquetas porque, de forma predeterminada, todas las etiquetas se utilizan para construir el nombre de la instancia de PCP. Al excluir algunas etiquetas (o cambiarlas a opcionales), los nombres de instancia cambiarán. Al excluir algunas etiquetas, diferentes instancias devueltas por la URL o la entrada de configuración con script para la misma métrica pueden convertirse en duplicados. Cuando ocurren dichos duplicados, la última instancia duplicada devuelta por el punto final de la URL o el script prevalece sobre las instancias anteriores. Por estas razones, se recomienda configurar las reglas de filtrado de etiquetas cuando se define por primera vez el archivo de configuración y no modificarlas después. Si se requiere un cambio en el filtrado de etiquetas, el archivo de configuración debe ser renombrado, lo que efectivamente define una nueva métrica (o conjunto de métricas intermedias según lo devuelto por la URL o el script), con la nueva (o modificada) denominación de instancia.

Las palabras clave no reconocidas en los archivos de configuración se informan en el archivo de registro de PMDA, pero de lo contrario se ignoran.

FUENTES CON SCRIPT

Los scripts ejecutables presentes en el directorio $PCP_PMDAS_DIR/opentelemetry/config.d o sus subdirectorios se ejecutarán y el flujo stdout que contiene datos de métricas con formato OpenTelemetry se analizará como si hubiera provenido de una URL o archivo. El flujo stderr de un script se enviará al archivo de registro de PMDA, que de forma predeterminada se puede encontrar en $(PCP_LOG_DIR)/pmcd/opentelemetry.log.

Tenga en cuenta que las fuentes con script no admiten el filtrado de etiquetas o métricas (como se describe anteriormente para las fuentes de URL): simplemente pueden hacer su propio filtrado en el script con sed(1), awk(1), o la herramienta que se desee.

Para obtener detalles completos de los formatos de exposición de OpenTelemetry, consulte https://github.com/open-telemetry/opentelemetry-proto/
blob/main/opentelemetry/proto/metrics/v1/metrics.proto.

CONSIDERACIONES SELinUX

Los archivos de configuración con script son ejecutados por el PMDA pmdaopentelemetry con el mismo contexto y política SELinux que el pmcd(1) local. Para scripts simples, esto normalmente está bien. Sin embargo, pueden surgir errores de AVC para scripts que realizan llamadas a bibliotecas o al sistema que están restringidas por el contexto y las políticas SELinux predominantes. En estos casos, no es factible otorgar unilateralmente a pmcd o sus PMDA una política de ejecución sin restricciones. En estos casos específicos del sitio, será necesario crear un módulo de política SELinux local. Esto se puede hacer capturando el registro (o registros) de AVC del registro de auditoría local, generando un módulo de política local usando audit2allow y luego cargando el nuevo módulo usando semodule, por ejemplo, de la siguiente manera: 

    $ sudo grep '^type=AVC.*pcp' /var/log/audit/audit.log \
    | audit2allow -M mypolicy
    $ sudo semodule -i mypolicy.pp

Si estas políticas locales necesitan ser persistentes tras los reinicio, se puede agregar un script similar al ejemplo anterior al archivo RC local de pmcd (típicamente /etc/pcp/pmcd/rc.local). Para obtener más detalles, consulte audit2allow(1) y semodule(1).

NOMBRES DE MÉTRICAS

Todas las métricas de un archivo llamado JOB.* se exportarán como métricas de PCP con el prefijo de nombre de métrica opentelemetry.JOB. Por lo tanto, el nombre de JOB debe ser un nombre válido no hoja para los nombres de métricas de PMNS de PCP. Si el nombre de JOB tiene varios componentes separados por puntos, los nombres de PMNS resultantes incluirán esos componentes y se debe tener cuidado para asegurar que no haya definiciones superpuestas, por ejemplo, las métricas devueltas por JOB.response pueden superponerse o entrar en conflicto con las métricas devueltas por JOB.response.time.

Las entradas del archivo de configuración (URLs o scripts) que se encuentran en subdirectorios del directorio de configuración también resultarán en nombres de métricas jerárquicos. Por ejemplo, un archivo de configuración llamado $PCP_PMDAS_DIR/opentelemetry/config.d/mysource/latency/get.url resultará en la creación de métricas (al obtener esa URL de origen) debajo de opentelemetry.mysource.latency.get en el espacio de nombres de PCP. Los scripts que se encuentran en subdirectorios del directorio de configuración producen de manera similar nombres de métricas de PCP jerárquicos.

NOMBRES DE MÉTRICAS DINÁMICAS

Como se describió anteriormente, se pueden realizar cambios y adiciones a los archivos en el directorio de configuración sin tener que reiniciar el PMDA. Estos cambios se detectan automáticamente y los nombres de las métricas de PCP debajo de opentelemetry en PMNS se actualizarán en consecuencia, es decir, se agregarán nuevas métricas dinámicamente y/o se eliminarán las métricas existentes. Además, pmdaopentelemetry cumple con el protocolo de llamada PMCD_NAMES_CHANGE pmFetch(3) que se introdujo en la versión 4.0 de PCP. En particular, si las métricas de opentelemetry están siendo registradas por un pmlogger(1) de versión 4.0 o posterior de PCP, las nuevas métricas que aparezcan como resultado de cambios en el directorio de configuración de opentelemetry comenzarán a registrarse automáticamente, siempre que la raíz del espacio de nombres de las métricas de opentelemetry esté configurada para el registro en el archivo de configuración de pmlogger. Consulte pmlogger(1) para obtener detalles. Un ejemplo de dicho archivo de configuración de pmlogger es:

log mandatory on 2 second {
	# log all metrics below the root of the opentelemetry namespace
	opentelemetry
}

METADATOS

Los datos de métricas devueltos por archivos de configuración con script o URL pueden contener metadatos que pueden ser utilizados por el PMDA opentelemetry para especificar la semántica, el tipo de datos, la escala y las unidades de las métricas creadas dinámicamente. Estos metadatos se encuentran para cada métrica bajo el encabezado de lista metric en la estructura de datos JSON de opentelemetry. Para obtener información adicional sobre los metadatos de PCP, consulte pmLookupDesc(3) y pmParseUnitsStr(3) y los ejemplos en los archivos de configuración enviados.

Los metadatos deben ser proporcionados en los datos JSON por el punto final de origen de opentelemetry (URL o script). Una alternativa es especificarlos directamente en el archivo de configuración de la URL, lo que tiene la ventaja de no tener que modificar la fuente/punto final si los metadatos son incorrectos o faltan. Los metadatos especificados en el archivo de configuración de la URL anulan cualquier metadato en línea.

La sintaxis del archivo de configuración para especificar metadatos es:
METADATA: regex type indom semantics units ... hasta EOL
Donde:
METADATA: es literal
regex es una expresión regular extendida para coincidir con uno o más nombres de métricas devueltos por la URL,
type es uno de los tipos numéricos de PCP (32, u32, 64, u64, float o double),
indom es un nombre de dominio de instancia arbitrario, o PM_INDOM_NULL,
semantics es counter, instant o discrete y
units es none o una cadena que se extiende hasta el final de la línea que puede ser analizada por pmParseUnitsStr(3), es decir, las unidades, dimensiones y escala que se utilizarán para las métricas de coincidencia.

Un archivo de configuración de ejemplo que ingiere métricas del punto final de Grafana /metrics en localhost, filtra todas las métricas devueltas por esa URL *excepto* grafana_api_response_status_total y luego especifica que el tipo de métrica es un entero sin signo de 32 bits con un dominio de instancia no singular llamado response y semántica de counter con unidades de count.

http://localhost:3000/metrics
FILTER: INCLUDE METRIC grafana_api_response_status_total
FILTER: EXCLUDE METRIC .*
METADATA: grafana_api_response_status_total u32 response counter count

Tenga en cuenta que el nombre en el campo indom se ignora actualmente a menos que sea PM_INDOM_NULL, en cuyo caso la métrica no tiene dominio de instancia (es decir, singular), incluso si tiene etiquetas que de otro modo se usarían para la denominación de instancias.

MÉTRICAS DE CONTROL

El PMDA mantiene métricas de control especiales, como se describe a continuación. Aparte de opentelemetry.control.debug, cada una de estas métricas tiene una instancia por cada fuente de métricas configurada. Todas estas métricas tienen valores enteros con semántica de contador, excepto opentelemetry.control.status, que tiene un valor de cadena. Es importante tener en cuenta que la obtención de cualquiera de las métricas opentelemetry.control solo actualizará los contadores y los valores de estado si realmente se obtiene la URL correspondiente. Si la URL de origen no se obtiene, los valores de las métricas de control no activan una actualización y los valores de control informados representan la obtención más reciente de cada origen correspondiente.

El dominio de instancia para las métricas opentelemetry.control se ajusta dinámicamente a medida que se descubren nuevas fuentes. Si no hay fuentes configuradas, los nombres de las métricas todavía están definidos, pero el dominio de instancia estará vacío y una obtención no devolverá ningún valor.

opentelemetry.control.status
Una cadena que representa el estado de la última obtención de la fuente correspondiente. Generalmente será success para un código de respuesta http de 200. Esta métrica se puede utilizar para el monitoreo de la disponibilidad del servicio, siempre que, como se mencionó anteriormente, también se obtenga la URL de la fuente correspondiente.
opentelemetry.control.status_code
Esta métrica es similar a opentelemetry.control.status, excepto que es el código de respuesta entero de la última obtención. Un valor de 200 generalmente significa
significa éxito y cualquier otro valor, fracaso. Esta métrica también se puede utilizar para monitorear la disponibilidad del servicio, con las mismas advertencias que opentelemetry.control.status.
opentelemetry.control.calls
número total de veces que cada fuente de métricas configurada ha sido obtenida (si es una URL) o ejecutada (si es un script), desde que se inició el PMDA. Esta métrica tiene semántica de contador y normalmente se convertiría a una tasa/segundo por las herramientas del cliente.
opentelemetry.control.fetch_time
Tiempo total en milisegundos que cada fuente de métricas configurada ha tardado en devolver un documento, excluyendo el tiempo de análisis del documento. Esta métrica tiene semántica de contador y normalmente sería convertida a tasa por las herramientas del cliente, pero también es útil en su forma bruta como el tiempo de análisis acumulado desde que se inició el PMDA.
opentelemetry.control.parse_time
Tiempo total en milisegundos que cada fuente de métricas configurada ha tardado en analizar cada documento, excluyendo el tiempo de obtención del documento. Esta métrica tiene semántica de contador y normalmente sería convertida a tasa por las herramientas del cliente, pero también es útil en su forma bruta como el tiempo de análisis acumulado desde que se inició el PMDA.

Cuando se convierte a una tasa, la métrica calls representa la tasa promedio de obtención de cada fuente durante el intervalo de muestreo (delta de tiempo entre muestras). Los contadores fetch_time y parse_time, cuando se convierten a una tasa, representan la latencia promedio de obtención y análisis (respectivamente), durante el intervalo de muestreo.

La métrica opentelemetry.control.debug tiene un valor singular, por defecto 0. Si se almacena un valor distinto de cero en esta métrica usando pmstore(1), se escribirán mensajes de depuración adicionales en el archivo de registro del PMDA.

LIMITACIONES

pmdaopentelemetry e libpcp internamente imponen algunas restricciones numéricas sobre el número de fuentes (4095), métricas (1024) dentro de cada fuente, e instancias para cada métrica (4194304).

INSTALACIÓN

Instale el PMDA de OpenTelemetry usando el script Install como root:

# cd $PCP_PMDAS_DIR/opentelemetry
# ./Install

Para desinstalar, se debe hacer lo siguiente como root:

# cd $PCP_PMDAS_DIR/opentelemetry
# ./Remove

pmdaopentelemetry es lanzado por pmcd(1) y nunca debe ser ejecutado directamente. Los scripts Install y Remove notifican a pmcd cuando el agente es instalado o removido.

Cuando se agregan, eliminan o modifican scripts y archivos .url en el directorio de configuración, generalmente no es necesario reiniciar el PMDA; los cambios se detectarán y gestionarán en solicitudes posteriores al PMDA.

archivo de registro predeterminado para mensajes de error de pmdaopentelemetry
$PCP_VAR_DIR/config/164.*
archivos que contienen tablas internas para la persistencia de números de identificación de métricas e instancias (dominio 164).

ENTORNO PCP

Las variables de entorno con el prefijo PCP_ se utilizan para parametrizar los nombres de archivos y directorios utilizados por PCP. En cada instalación, el archivo /etc/pcp.conf contiene los valores locales para estas variables. La variable $PCP_CONF se puede usar para especificar un archivo de configuración alternativo, como se describe en pcp.conf(5).
