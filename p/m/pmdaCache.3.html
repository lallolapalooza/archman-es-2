DESCRIPCIÓN

La familia de rutinas pmdaCache proporciona servicios para soportar el mantenimiento de dominios de instancia complejos para los PMDA de Performance Co-Pilot. Potencialmente existe una caché de información para cada dominio de instancia, y para cada instancia la caché mantiene:

  • nombre de instancia externo (suministrado por el PMDA)
  • identificador de instancia interno (asignado por pmdaCacheStore o calculado a partir de una "pista" por pmdaCacheStoreKey)
  • estado, donde las instancias activas son visibles y forman parte del dominio de instancia actual, y las instancias inactivas están ocultas, pero no olvidadas; se puede usar pmdaCacheStore o pmdaCacheStoreKey para cambiar el estado de una instancia
  • un puntero opaco opcional a datos que están asociados con la instancia, pero mantenidos por el PMDA
  • una clave opaca opcional que se utiliza como "pista" para pmdaCacheStoreKey al adivinar el identificador de instancia interno inicial
  • la última vez que se guardó la caché y la instancia se marcó como activa en algún momento desde la operación anterior de carga o guardado de la caché

La semántica de un dominio de instancia de PCP requiere que se sigan una serie de reglas, a saber:

1.
Cada identificador de instancia interno debe ser único y estar en el rango de 0 a 2^31 - 1. Esta regla es impuesta por la familia de rutinas pmdaCache.
2.
El nombre de instancia externo debe ser único. Cuando el nombre de instancia contiene un espacio, se restringe aún más de modo que el nombre a la izquierda del primer espacio (el nombre corto) también debe ser único. Consulte la sección COINCIDENCIA DE NOMBRES DE INSTANCIA a continuación. El PMDA debe cumplir esta regla, la familia de rutinas pmdaCache detectará intentos de violar esta regla.
3.
Donde un nombre de instancia externo corresponde a algún objeto o entidad, existe la expectativa de que la asociación entre el nombre y el objeto sea fija, por ejemplo, ``/dev/hda'' es siempre el nombre del mismo disco en un sistema particular. Esta regla es quizás responsabilidad del PMDA, pero es a menudo una característica del entorno en el que se ejecuta el PMDA.
4.
Es preferible, aunque no obligatorio, que la asociación entre un nombre de instancia externo y un identificador de instancia interno sea persistente. Esta regla es compatible con la familia de rutinas pmdaCache.
5.
Cuando se utilizan claves opacas, los valores de las claves deben ser únicos en todas las instancias dentro de un dominio de instancia. Esta regla es impuesta por la familia de rutinas pmdaCache.

La interfaz visible de la caché está orientada al desarrollador del PMDA que más se preocupa por los nombres de las instancias, mientras que los detalles de cómo el resto de la infraestructura de PCP espera que se gestionen los identificadores de instancia internos no son relevantes.

Las instancias se actualizan en la caché para el dominio de instancia indom llamando a pmdaCacheStore o pmdaCacheStoreKey con el nombre externo de la instancia pasado a través de name. El puntero opaco private puede usarse para asociar datos adicionales con la entrada en la caché; si no se requieren dichos datos, private debe ser NULL. Cualquier manipulación de los datos adicionales (incluida la asignación o liberación) es responsabilidad del llamador del PMDA, ya que la caché simplemente mantiene el puntero a los datos (pasado a través de private).

El límite superior para los identificadores asignados para cualquier caché indom dada puede reducirse opcionalmente del valor por defecto (2^31 - 1) a un máximo menor, usando pmdaCacheResize. Este máximo se persistirá y restaurará de la manera habitual, y por lo tanto puede asociarse permanentemente con una caché una vez establecido. Esto tiene aplicaciones al usar estas interfaces como cachés de identificadores de propósito general, y es menos aplicable cuando se usan para el almacenamiento en caché de dominios de instancia.

Para casos en los que el desarrollador del PMDA desea influir en la asignación de identificadores de instancia internos, por ejemplo, para dominios de instancia con más de una dimensión natural, o donde existe el deseo de asignar el mismo identificador de instancia cada vez que se inicia el PMDA, incluso en diferentes hosts, se puede usar pmdaCacheStoreKey. En este caso, se proporciona una "pista" inicial para el identificador de instancia como una clave opaca a través de los primeros keylen bytes en key (que podrían ser cualquier tipo de datos, incluidos valores binarios) o si keylen es menor que 1 o key es NULL, entonces se usa name como la "pista". La "pista" se hashea para producir un identificador de instancia inicial en el rango de 0 a 2^31 - 1 (o un máximo menor, si se establece). Si este identificador de instancia ya está asignado, el valor se vuelve a hashear. Este procedimiento se repite hasta que se encuentra un identificador de instancia no asignado, o pmdaCacheStoreKey se rinde y devuelve PM_ERR_GENERIC. Para cada dominio de instancia, la "pista" debe ser única en todas las instancias, o pmdaCacheStoreKey devolverá PM_ERR_INST.

El argumento flags controla cómo se procesará la instancia en la caché de la siguiente manera:

PMDA_CACHE_ADD
Inserta la entrada en la caché si aún no está allí y la marca como activa. Si la entrada ya está en la caché, la marca como activa.
PMDA_CACHE_HIDE
Marca la entrada en la caché como inactiva, pero recuerda los detalles de la asociación entre el nombre de instancia externo y el identificador de instancia interno. Las entradas que están inactivas se ocultarán de la traversa de caché a través de operaciones PMDA_CACHE_WALK_NEXT, pero permanecerán visibles para las solicitudes pmdaCacheLookup, pmdaCacheLookupName y pmdaCacheLookupKey.
PMDA_CACHE_CULL
Elimina la entrada de la caché.

En caso de éxito, pmdaCacheStore o pmdaCacheStoreKey devolverá el identificador de instancia interno de la entrada de caché asociada. Se garantiza que los identificadores de instancia válidos son únicos y no negativos. El fallo se indicará con un valor negativo (adecuado para decodificar con pmErrStr(3)) y lo más probablemente PM_ERR_INST para indicar que la instancia solicitada no está en la caché, o -EINVAL para indicar una posible violación de la propiedad de unicidad del nombre corto (ver la sección COINCIDENCIA DE NOMBRES DE INSTANCIA a continuación).

pmdaCacheLookup se utiliza para buscar las entradas en la caché basándose en el identificador de instancia interno inst.

En caso de éxito, el valor de retorno será PMDA_CACHE_ACTIVE o PMDA_CACHE_INACTIVE (dependiendo del estado activo o inactivo de la entrada de la caché), name (si no es NULL) y private (si no es NULL) se establecerán al nombre de instancia externo y los datos asociados...

NAME

pmdaCache, pmdaCacheStore, pmdaCacheLookup, pmdaCacheStoreKey, pmdaCacheLookupKey, pmdaCacheOp - PMDA performance metric instance cache

C SYNOPSIS

#include <pcp/pmapi.h>
#include <pcp/pmda.h>

int
pmdaCache(pmdaInterface *dp, pmdaCache **cache,
        const char *indom_name, pmdaCacheType type,
        void *private_data);

int
pmdaCacheStore(pmdaCache *cache, int inst, const char *name,
        void *value);

int
pmdaCacheLookup(pmdaCache *cache, const char *name, int *inst,
        void **value);

int
pmdaCacheStoreKey(pmdaCache *cache, const char *key, void *value);

int
pmdaCacheLookupKey(pmdaCache *cache, const char *key, void **value);

int
pmdaCacheOp(pmdaCache *cache, int op, ...);

DESCRIPTION

The pmdaCache routines provide a generic, PMDA-local, in-memory cache for performance metric instance domains. This can be used to manage the association between metric instance identifiers and their corresponding instance names (or other user-defined instance-specific values).

The cache is initialized via a call to pmdaCache. The dp argument is a pointer to the PMDA interface structure. The cache argument is a pointer to a pmdaCache pointer, which will be updated by pmdaCache to point to the newly allocated cache. The indom_name argument specifies the instance domain name. The type argument controls the cache's behavior, and may be one of the following:

  • PMDA_CACHE_NAMES: The cache maps instance names (strings) to instance identifiers (integers) and vice versa. The value in pmdaCacheStore and pmdaCacheLookup is a string. The value in pmdaCacheStoreKey and pmdaCacheLookupKey is an integer instance identifier.
  • PMDA_CACHE_STRINGS: The cache maps instance names (strings) to string values. The value in pmdaCacheStore, pmdaCacheLookup, pmdaCacheStoreKey and pmdaCacheLookupKey is a string.
  • PMDA_CACHE_KEYS: The cache maps arbitrary keys (strings) to arbitrary values (void pointers). The key in pmdaCacheStore is ignored. The inst in pmdaCacheLookup is ignored.

The private_data argument is a pointer to user-defined data which will be associated with the cache. This pointer can be retrieved later using pmdaCacheOp with the PMDA_CACHE_GET_PRIVATE operation.

pmdaCacheStore adds or updates an entry in the cache. For PMDA_CACHE_NAMES and PMDA_CACHE_STRINGS types, inst is the instance identifier and name is the instance name. For PMDA_CACHE_KEYS type, inst is ignored and name is the key. value is the data associated with the entry.

pmdaCacheLookup searches the cache for an entry matching name. For PMDA_CACHE_NAMES and PMDA_CACHE_STRINGS types, name is the instance name. For PMDA_CACHE_KEYS type, name is the key. On success, the instance identifier (if applicable) is returned in inst, and the associated value is returned in value.

pmdaCacheStoreKey and pmdaCacheLookupKey are used for the PMDA_CACHE_NAMES type to store and retrieve instance identifiers based on an arbitrary key string (e.g. a hint string). This allows a PMDA to use external information to locate an instance. The key argument is the key string, and value is the integer instance identifier for pmdaCacheStoreKey, or a pointer to an integer instance identifier for pmdaCacheLookupKey.

pmdaCacheOp performs various operations on the cache. The possible operations are:

PMDA_CACHE_DELETE
Delete an entry from the cache. The subsequent argument must be the instance name (or key for PMDA_CACHE_KEYS type) of the entry to delete.
PMDA_CACHE_FLUSH
Remove all entries from the cache.
PMDA_CACHE_GET_PRIVATE
Return the user-defined private data pointer associated with the cache. No subsequent arguments are needed.
PMDA_CACHE_GET_STATS
Return statistics about the cache usage. The subsequent argument must be a pointer to a pmdaCacheStats structure, which will be filled with the cache statistics. This includes hit/miss counts, total entries, etc. The statistics are cleared after being retrieved. 
typedef struct {
    unsigned long long cache_hits;
    unsigned long long cache_misses;
    unsigned long long cache_entries;
    unsigned long long cache_collisions;
    unsigned long long cache_overhead;
} pmdaCacheStats;
This also includes dumping the internal hashing structures used to support lookup by instance name, lookup by instance identifier and the collision statistics for ``hint'' hashing from pmdaCacheStoreKey.

pmdaCacheOp returns a non-negative value on success, and failure is indicated by a negative return value (suitable for decoding with pmErrStr(3)).

OTHER CONSIDERATIONS

When the pmdaCache routines are used for particular instance domain, pmdaInstance(3) and the instance domain enumeration behind pmdaFetch(3) will attempt to extract instance domain information from the cache, thereby avoiding reference to the pmdaIndom data structures that have historically been used to define instance domains and service instance requests. A PMDA can adopt a hybrid approach and choose to implement some instance domains via the traditional pmdaIndom method, and others via the pmdaCache approach, however attempts to manage the same instance domain by both methods will result in the pmdaCache method silently prevailing.

If all instances in a PMDA are to be serviced from a pmdaCache then a pmdaIndom is not required, and the pmdaInit(3) call becomes 

    pmdaInit(dp, NULL, 0, metrictab, nmetrics);


However, the PMDA will need to explicitly initialize the indom field of the pmDesc in the metrictab entries, as this cannot be done by pmdaInit(3) if indomtab is missing entries for the instance domains maintained in the cache.

Independent of how the instance domain is being maintained, to refresh an instance domain prior to a fetch or an instance domain operation, the standard methods of a ``wrapper'' to the pmdaInstance(3) and pmdaFetch(3) methods should be used.

Refer to the simple PMDA source code for an example use of the pmdaCache routines.

When using pmdaCacheStoreKey, if there is a desire to ensure the given ``hint'' generates the same initial instance identifier across all platforms, then the caller should ensure the endian and word-size issues are considered, e.g. if the natural data structure used for the key is an array of 32-bit integers, then htonl(3) should be used on each element of the array before calling pmdaCacheStoreKey or pmdaCacheLookupKey.

FILES

Cache persistence uses files with names constructed from the indom within the $PCP_VAR_DIR/config/pmda directory.
