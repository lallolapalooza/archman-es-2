PMLOGGER(1) Manual de Comandos Generales PMLOGGER(1)

NOMBRE

pmlogger - crear un archivo para métricas de rendimiento

SINOPSIS

pmlogger [-CLNoPruy?] [-c archivo_conf] [-D depuracion] [-d directorio] [-h host] [-H nombre_host] [-I version] [-K espec] [-l archivo_log] [-m nota] [-n archivo_pmns] [-p pid] [-s tamaño_fin] [-t intervalo] [-T tiempo_fin] [-U nombre_usuario] [-v tamaño_vol] [-V version] [-x fd] [archivo]

DESCRIPCIÓN

pmlogger crea los archivos de valores de métricas de rendimiento que pueden ser "reproducidos" por otras herramientas de Performance Co-Pilot (ver PCPIntro(1)). Estos registros forman la base del paradigma de VCR y los servicios de análisis de rendimiento retrospectivo comunes en el kit de herramientas PCP.

El argumento obligatorio archivo es el nombre base para los archivos físicos que constituyen un archivo en el sistema de archivos local, o el servidor HTTP remoto que recibirá los datos registrados.

El argumento archivo local puede contener meta-caracteres de strftime(3), que se sustituirán antes de crear los archivos del archivo. Cuando pmlogger se ejecuta como un servicio (ver pmlogger_daily(1)), el nombre base estándar del archivo es %Y%m%d.%H.%M.

La forma remota de archivo especifica la ubicación del servidor pmproxy(1) al que se envían los componentes del archivo a medida que son generados por pmlogger. El valor proporcionado debe contener el protocolo, el nombre de host y el puerto opcional, por ejemplo http://example.com:44322. Este servidor pmproxy seleccionará un nombre de archivo basado en la hora de inicio, de forma similar al modelo utilizado por defecto en pmlogger_check(1).

La opción -V especifica la versión del archivo que se genera. Por defecto, se utiliza la versión de archivo $PCP_ARCHIVE_VERSION (establecida en 3 en las versiones actuales de PCP), y los únicos valores actualmente admitidos para version son 2 o 3.

A menos que se dirija a otro host con la opción -h o al usar directamente PMDAs con la opción -o, pmlogger se conectará al demonio recolector de métricas de rendimiento (PMCD) en el host local y lo utilizará como fuente de los valores de métricas a registrar.

Para admitir la flexibilidad y el control requeridos sobre qué se registra y cuándo, pmlogger mantiene un estado de registro independiente de dos niveles para cada instancia de cada métrica de rendimiento. En el primer nivel (obligatorio), el registro puede estar activado (con un intervalo asociado entre muestras), o desactivado o quizás. En este último caso, el segundo nivel (consultivo) permite que el registro esté activado (con un intervalo asociado entre muestras) o desactivado.

El nivel obligatorio permite especificar universalmente que algunas métricas deben registrarse, o no deben registrarse. El estado predeterminado para todas las instancias de todas las métricas cuando pmlogger se inicia es obligatorio quizás y consultivo desactivado.

Use pmlc(1) para interrogar y cambiar el estado de registro una vez que pmlogger esté en ejecución.

Si el estado de una métrica es obligatorio (activado o desactivado) y se realiza una solicitud para cambiarlo a obligatorio quizás, el nuevo estado es obligatorio quizás y consultivo desactivado. Si el estado de una métrica ya es consultivo (activado o desactivado) y se realiza una solicitud para cambiarlo a obligatorio quizás, se conserva el estado actual.

No es posible que pmlogger registre instancias específicas de una métrica y todas las instancias de la misma métrica simultáneamente. Si se están registrando instancias específicas y se realiza una solicitud para registrar todas las instancias, entonces todas las instancias de la métrica se registrarán según la nueva solicitud, reemplazando cualquier solicitud de registro anterior para la métrica. Una solicitud para registrar todas las instancias de una métrica reemplazará cualquier solicitud anterior para registrar todas las instancias. Se rechaza una solicitud para registrar instancias específicas de una métrica cuando todas las instancias ya están siendo registradas. Para hacerlo, primero se debe desactivar el registro para todas las instancias de la métrica. En cada caso, primero se verifica la validez de la solicitud; por ejemplo, una solicitud para cambiar el estado de registro de una métrica a consultivo activado cuando actualmente está obligatorio desactivado nunca se permite (es necesario cambiar primero el estado a obligatorio quizás).

Opcionalmente, cada sistema que ejecuta pmcd(1) también puede configurarse para ejecutar una instancia "primaria" de pmlogger. Esta instancia de pmlogger es iniciada por $PCP_RC_DIR/pmlogger, y se ve afectada por los archivos $PCP_SYSCONF_DIR/pmlogger/control, $PCP_SYSCONF_DIR/pmlogger/control.d/*, (use chkconfig(8), systemctl(1) o comandos similares específicos de la plataforma para activar o desactivar la instancia "primaria" de pmlogger), $PCP_SYSCONFIG_DIR/pmlogger (configuración de variables de entorno para el pmlogger "primario") $PCP_SYSCONF_DIR/pmlogger/pmlogger.options (opciones de línea de comandos pasadas al pmlogger "primario") y $PCP_VAR_DIR/config/pmlogger/config.default (el archivo de configuración inicial predeterminado para el pmlogger "primario").

La instancia "primaria" de pmlogger se identifica mediante la opción -P. Puede haber como máximo una instancia "primaria" de pmlogger en cada sistema. La instancia "primaria" de pmlogger (si la hay) debe ejecutarse en el mismo host que el pmcd(1) al que se conecta (si lo hay), por lo que las opciones -h y -P son mutuamente excluyentes.

El registro de algunas métricas es posible incluso en ausencia de un pmcd(1) local, utilizando el modo de operación de "contexto local". Esto se activa usando la opción -o, y hace que pmlogger utilice PMDAs DSO locales en lugar de comunicarse con pmcd(1). Al operar usando un contexto local, la opción -K puede usarse para controlar los PMDAs DSO que deben ser accesibles. El argumento espec se ajusta a la sintaxis descrita en pmSpecLocalPMDA(3). Se pueden usar múltiples opciones -K.

Cuando se inicia como una instancia no primaria, pmlogger saldrá inmediatamente si el archivo de configuración no programa ningún registro de métricas. La opción -L anula este comportamiento, y hace que una instancia de pmlogger no primaria "persista", presumiblemente a la espera de alguna futura reconfiguración dinámica y cambio de estado a través de pmlc(1). pmlogger también persistirá sin que se use la opción -L si todas las métricas a registrar se registran como métricas de una sola vez. Cuando se hayan registrado las métricas de una sola vez, se generará un mensaje de advertencia indicando que la cola de eventos está vacía y no se programarán más eventos.

Por defecto, todos los diagnósticos y errores de pmlogger se escriben en el archivo pmlogger.log en el directorio donde se inicia pmlogger. La opción -l puede usarse para anular el comportamiento predeterminado. Si el archivo de registro no se puede crear o no es escribible, la salida se escribe en la salida de error estándar en su lugar. Si el archivo_log para la opción -l es "-" (es decir, -l-), entonces los mensajes de registro se escriben en el flujo de salida estándar. Esto puede ser particularmente útil cuando se ejecuta pmlogger manualmente, en lugar de como un servicio demonio.

La opción -N dirige pmlogger a notificar a un gestor de servicios, típicamente systemd(1), cuando ha comenzado y está a punto de comenzar a escribir archivos PCP. Esta opción normalmente solo se usaría cuando pmlogger se ejecuta como un servicio demonio bajo el control de un gestor de servicios. Para más detalles, ver __pmServerNotifyServiceManagerReady(3) y systemd(1). En plataformas que no usan un gestor de servicios que soporte notificaciones, la opción -N es básicamente una operación nula.

Si se especifica, la opción -s instruye a pmlogger a terminar después de que se haya acumulado un cierto tamaño en registros, bytes o unidades de tiempo. Si tamaño_fin es un entero, entonces se escribirán tamaño_fin registros en el archivo. Si tamaño_fin es un entero seguido de b o bytes, entonces se escribirán tamaño_fin bytes de los datos del archivo (tenga en cuenta, sin embargo, que los límites de registro del archivo no se romperán y, por lo tanto, este límite puede superarse ligeramente). Otras unidades de tamaño de archivo viables incluyen: K, Kb, KiB, Kbyte, Kilobyte para kilobytes y M, Mb, MiB, Mbyte, Megabyte para megabytes y G, Gb, GiB, Gbyte, Gigabyte para gigabytes. Estas unidades pueden ir opcionalmente seguidas por una s y pueden ser de cualquier combinación de mayúsculas y minúsculas. Alternativamente, endsize puede ser un número entero o un número de punto flotante seguido de una unidad de tiempo como se describe en PCPIntro(1) para el argumento interval (a la opción de línea de comandos estándar de PCP -t).

Algunos ejemplos de diferentes formatos:
-s 100
-s 100bytes
-s 100K
-s 100Mb
-s 10Gbyte
-s 10mins
-s 1.5hours
Por defecto, pmlogger se ejecuta indefinidamente.

La opción -r hace que el tamaño del/los registro(s) físico(s) para cada grupo de métricas y la contribución esperada del grupo al tamaño del archivo PCP para un día completo de recopilación se registren en el archivo de registro. Esta información se registra la primera vez que cada grupo se escribe correctamente en el archivo.

La opción -U especifica la cuenta de usuario bajo la cual se ejecutará pmlogger. Por defecto, es la cuenta de usuario actual para uso interactivo. Cuando se ejecuta como un demonio, la cuenta no privilegiada "pcp" se utiliza en las versiones actuales de PCP, pero en versiones anteriores se utilizaba la cuenta de superusuario ("root") por defecto.

El archivo es potencialmente un conjunto de datos de múltiples volúmenes, y la opción -v hace que pmlogger inicie un nuevo volumen después de que se haya acumulado un cierto tamaño en registros, bytes o unidades de tiempo para el volumen actual. El formato de esta especificación de tamaño es idéntico al de la opción -s (ver arriba). Por defecto, pmlogger crea un archivo de un solo volumen. Los cambios de volumen adicionales también se pueden forzar de forma asíncrona utilizando pmlc(1) o enviando una señal SIGHUP a pmlogger (ver abajo). Tenga en cuenta que si hay un cambio de volumen programado debido a la opción -v, sus contadores se restablecerán después de un cambio asíncrono.

Independientemente de cualquier opción -v, cada volumen de un archivo tiene un límite máximo de 2^31 bytes, por lo que pmlogger creará automáticamente un nuevo volumen para el archivo antes de alcanzar este límite.

Normalmente, pmlogger opera en el Espacio de Nombres de Métricas de Rendimiento (PMNS) distribuido; sin embargo, si se especifica la opción -n, se carga un PMNS local alternativo desde el archivo pmnsfile.

En circunstancias normales, pmlogger se ejecutará indefinidamente (excepto por la opción -s o una señal de terminación). La opción -T puede utilizarse para limitar el tiempo de ejecución utilizando el formato de tiempo prescrito por PCPIntro(1). El tiempo se interpreta dentro de la zona horaria del servidor PMCD, a menos que se proporcione la opción -y, en cuyo caso se utiliza la zona horaria de este host del registrador.

Algunos ejemplos de diferentes formatos:
-T 10mins
-T '@ 11:30'
De esto se desprende que -T 10mins y -s 10mins realizan acciones idénticas.

Alternativamente, el tiempo de ejecución de pmlogger puede limitarse a la vida útil de otro proceso utilizando la opción -p o --PID para designar el PID del proceso de interés. En este caso, pmlogger saldrá cuando el otro proceso ya no exista.

Cuando pmlogger recibe una señal SIGHUP, el volumen actual del archivo se cierra y se abre un nuevo volumen. Este mecanismo (o el mecanismo alternativo a través de pmlc(1)) puede utilizarse para gestionar el crecimiento de los archivos de registro; una vez que un volumen de registro se cierra, ese archivo puede archivarse sin afectar negativamente la operación continua de pmlogger. Véase también la opción -v anterior.

Cuando pmlogger recibe una señal SIGUSR2, el archivo actual se cierra y se abre un nuevo archivo. Para que esto tenga éxito, el argumento original archive debe incluir meta-caracteres strftime(3) (por ejemplo, %Y%m%d.%H.%M), de lo contrario pmlogger saldrá porque los archivos de archivo ya existirán y pmlogger no sobrescribirá los archivos de archivo existentes. Tenga en cuenta que SIGUSR2 hace que pmlogger se re-ejecute y re-analice todos los argumentos originales. Esto significa que los límites de tiempo relativos colocados en su tiempo de terminación o límite de muestreo se restablecen y comienzan de nuevo. Esto solo afecta a los tiempos de terminación relativos, no a los tiempos absolutos; por ejemplo, -T 5s se ve afectado, pero -T 5pm no.

Históricamente, los búferes para el archivo actual podían ser vaciados en disco utilizando el comando flush de pmlc(1), o utilizando la opción -u. La versión actual de pmlogger y las rutinas de libpcp que sustentan pmlogger utilizan incondicionalmente escrituras sin búfer y una única fwrite(3) para cada registro lógico escrito, por lo que el "vaciado" no fuerza la escritura de datos adicionales al sistema de archivos. La opción -u y el comando flush de pmlc(1) se conservan por compatibilidad con versiones anteriores.

Cuando se inicia con la opción -x, pmlogger aceptará solicitudes de control asíncronas en el descriptor de archivo fd. Se espera que esta opción solo sea utilizada internamente por aplicaciones PCP que admitan el "modo de registro en vivo".

La opción -m permite que la cadena note se añada al archivo mapa de esta instancia de pmlogger en el directorio $PCP_TMP_DIR/pmlogger. Esto se utiliza actualmente internamente para documentar el descriptor de archivo (fd) cuando se utiliza la opción -x, o para indicar que esta instancia de pmlogger fue iniciada bajo el control de pmlogger_check(1), (-m pmlogger_check) o fue re-ejecutada (ver execvp(3)) debido a la recepción de una señal SIGUSR2 como se describió anteriormente (-m reexec).

La opción -H permite anular el nombre de host escrito en la etiqueta del archivo. Esto refleja la opción -H de pmcd(1), pero permite que se especifique en el proceso pmlogger. Sin esta opción, se utiliza el valor devuelto por el pmcd(1) registrado.

La opción -C hará que se analice el archivo de configuración y pmlogger saldrá entonces sin crear un archivo de salida, por lo que cuando se especifica -C, el argumento de línea de comandos archive no es necesario. Se informan los errores en el archivo de configuración.

La opción -d o --directory puede utilizarse para especificar el directorio donde se debe crear el archive. directory puede incluir metacaracteres de sh(1), como $(...) o `...` o $var y pmlogger los expandirá para producir una ruta de directorio final. La ruta resultante debe ser absoluta, no relativa. La opción -d está pensada principalmente para ser utilizada por pmlogger_check(1) y los usuarios normales no necesitarían típicamente usar la opción, ya que el directorio para archive se infiere de archive si contiene componentes de directorio o el directorio actual por defecto.

SINTAXIS DEL ARCHIVO DE CONFIGURACIÓN

El archivo de configuración puede especificarse con la opción -c. Si no es así, las especificaciones de configuración se leen de la entrada estándar.

Si conffile no existe, se realiza una búsqueda en el directorio $PCP_VAR_DIR/config/pmlogger de un archivo con el mismo nombre, y si se encuentra, se utiliza ese archivo; por ejemplo, si config.mumble no existe en el directorio actual y el archivo $PCP_VAR_DIR/config/pmlogger/config.mumble sí existe, entonces -c config.mumble y -c $PCP_VAR_DIR/config/pmlogger/config.mumble son equivalentes.

La sintaxis del archivo de configuración es la siguiente.

1.
Las palabras están separadas por espacios en blanco (espacio, tabulación o nueva línea).
2.
El símbolo "#" (almohadilla) introduce un comentario, y todo el texto hasta la siguiente nueva línea se ignora.
3.
Las palabras clave (mostradas en negrita a continuación) deben aparecer literalmente (es decir, en minúsculas).
4.
Cada especificación comienza con la palabra clave opcional log, seguida de uno de los estados mandatory on, mandatory off, mandatory maybe, advisory on o advisory off.
5.
Para los estados on, debe seguir un intervalo de registro utilizando la sintaxis "once", o "default", o "every N timeunits", o simplemente "N timeunits". N es un número entero sin signo, y timeunits es una de las palabras clave msec, millisecond, sec, second, min, minute, hour o la forma plural de una de las anteriores.

Las limitaciones internas requieren que el intervalo sea menor que (aproximadamente) 74 horas. Un valor de intervalo de cero es sinónimo de once. Un intervalo de default significa usar el intervalo de registro predeterminado de 60 segundos; este valor predeterminado puede cambiarse a interval con la opción de línea de comandos -t.

El argumento interval sigue la sintaxis descrita en PCPIntro(1), y en su forma más simple puede ser un número entero sin signo (las unidades implícitas en este caso son segundos).
6.
Después de las especificaciones de estado y posible intervalo viene una "{", seguida de una lista de una o más especificaciones de métricas y una "}" de cierre. La lista está separada por espacios en blanco (o comas). Si solo hay una especificación de métrica en la lista, las llaves son opcionales.
7.
Una especificación de métrica consiste en un nombre de métrica opcionalmente seguido por un conjunto de nombres de instancia. El nombre de la métrica sigue las convenciones de nomenclatura estándar de PCP, ver PMNS(5), y si el nombre de la métrica es un nodo hoja en el PMNS (ver PMNS(5)), entonces pmlogger descenderá recursivamente el PMNS y aplicará la especificación de registro a todos los nombres de métricas descendientes que sean nodos hoja en el PMNS. El conjunto de nombres de instancia es un "[", seguido de una lista de uno o más nombres, números o cadenas separados por espacios (o comas), y un "]" de cierre. Los elementos de la lista que son números se asumen que son identificadores de instancia internos, otros elementos se asumen que son identificadores de instancia externos - ver pmGetInDom(3) para más información.

Si no se proporcionan instancias, la especificación de registro se aplica a todas las instancias de la métrica asociada.

8.
Puede haber un número arbitrario de especificaciones de registro.
9.
A partir de la versión 4.0 de PCP y posteriores, cualquier especificación de nombre de métrica que no se resuelva en un nodo hoja en el PMNS se añade a una lista interna

CONFIGURATION

The pmlogger utility logs performance metrics from a Performance Co-Pilot (PCP) data source. The data source is specified by the command line options, and the metrics to be logged are specified in a configuration file. The default configuration file is named pmlogger.conf and is located in $PCP_PMCD_PATH/pmlogger.

The configuration file syntax is described below.

1.
The configuration file consists of a number of logging specifications, possibly followed by an optional access control section.
2.
A logging specification consists of a keyword, followed by optional modifiers, and then a list of performance metrics.
3.
The keyword indicates the mandatory or advisory nature of the logging:
mandatory
metrics specified are mandatory and must be logged.
advisory
metrics specified are advisory and may be logged if the PMDA supports them and if the system load permits.
4.
The optional modifiers specify the frequency of logging. The syntax is ``on spec'', where spec can be:
5.
One of:
once
Log the metrics exactly once, at the beginning of the logging session.
every N units
Log the metrics every N units. The default logging interval is 60 seconds. The possible units are: seconds, minutes, hours, days, weeks, months, years. The units may be abbreviated to their first letter, e.g. every 10 minutes can be written as every 10m. The default logging interval is controlled by the environment variable PMLOGGER_INTERVAL.
instant
Log the metrics exactly once, when the configuration is read. This is only allowed for advisory metrics.
now
Same as instant.
6.
The optional modifiers may also include a PID, used to control logging for a specific process. The syntax is ``on pid PID'', where PID is the process identifier. This is only allowed for mandatory metrics.
7.
The list of performance metrics follows the logging specification. The list is enclosed in curly braces { }. Each metric name is a string, and may be followed by an optional instance list in square brackets [ ]. For example, to log the number of network packets on interface et0, you would specify network.interface.in.packets[ "et0" ]. The metric names and instance names are fully documented in pcp.conf(5).
8.
A special metric name, ., may be used to indicate that all available metrics from a PMDA should be logged. This is only supported for PMDAs that are capable of dynamically exporting metrics.
9.
A PMDA can dynamically create new metrics below a dynamic root node in its PMNS, and send a notification to clients that the PMNS has changed. This mechanism is currently supported by pmdaopenmetrics(1) and pmdammv(1). When a fetch issued by pmlogger returns with the PMDA_EXT_NAMES_CHANGE flag set, pmlogger will traverse the internal list of possible dynamic subtree nodes and dynamically discover any new metrics. In effect, as of PCP version 4.0 and later, pmlogger can be configured to dynamically log new metrics that appear in the future, after the configuration file is initially parsed.
10.
Following all of the logging specifications, there may be an optional access control section, introduced by the literal token [access]. Thereafter come access control rules that allow or disallow operations from particular hosts or groups of hosts.

The operations may be used to interrogate or control a running pmlogger using pmlc(1) and fall into the following classes:

enquire
interrogate the status of pmlogger and the metrics it is logging
advisory
Change advisory logging.
mandatory
Change mandatory logging.
all
All of the above.

Access control rules are of the form ``allow hostlist : operationslist ;'' and ``disallow hostlist : operationslist ;''.

The hostlist follows the syntax and semantics for the access control mechanisms used by PMCD and are fully documented in pmcd(1). An operationslist is a comma separated list of the operations advisory, mandatory, enquire and all.

A missing [access] section allows all access and is equivalent to allow * : all;.

The configuration (either from standard input or conffile) is initially scanned by pmcpp(1) with the options -rs and -I $PCP_VAR_DIR/config/pmlogger. This extends the configuration file syntax with include file processing (%include), a common location to search for include files ($PCP_VAR_DIR/config/pmlogger), macro definitions (%define), macro expansion (%name and %{name}) and conditional inclusion of lines (%ifdef name ... %else ... %endif and %ifndef name ... %else ... %endif).

OPTIONS

The available command line options are:

-c conffile, --config=conffile
Specify the conffile file to use.
-C, --check
Parse configuration and exit.
-h host, --host=host
Fetch performance metrics from pmcd(1) on host, rather than from the default localhost.
-H hostname, --labelhost=hostname
Specify the hostname to use instead of the one returned by pmcd(1).
-I version, --pmlc-ipc-version=version
Normally, pmlogger and pmlc(1) will autonegotiate a mutually acceptable version for their private IPC channel. Use -I to force pmlogger to offer (at most) version as the version to be used. This option may be required if pmlogger needs to be managed by an older version of pmlc(1) that fails to autonegotiate correctly.
-K spec, --spec-local=spec
When fetching metrics from a local context (see -o), the -K option may be used to control the DSO PMDAs that should be made accessible. The spec argument conforms to the syntax described in pmSpecLocalPMDA(3). More than one -K option may be used.
-l logfile, --log=logfile
Write all diagnostics to logfile instead of the default pmlogger.log.
-L, --linger
Run even if not the primary logger instance and nothing to log.
-m note, --note=note
Append note to the port map file for this instance.
-n pmnsfile, --namespace=pmnsfile
Load an alternative Performance Metrics Name Space (PMNS(5)) from the file pmnsfile.
-N, --notify
Notify service manager such as systemd(1) as needed.
-o, --local-PMDA
Use a local context to collect metrics from DSO PMDAs on the local host without PMCD. See also -K.
-p PID, --PID=PID
Log specified metrics for the lifetime of the process identified by PID.
-P, --primary
Run as primary logger instance. See above for more detailed description of this.
-r, --report
Report record sizes and archive growth rate.
-s endsize, --size=endsize
Terminate after archive size exceeds endsize.
-t interval, --interval=interval
Specify the logging interval. The default value is 60 seconds. Please refer to the ENVIRONMENT and FILES sections below regarding the PMLOGGER_INTERVAL environment variable and its impact on the default logging interval.
-T endtime, --finish=endtime
Specify the endtime when to end logging.
-u
Use unbuffered output. This is the default (so this option does nothing).
-U username, --username=username
When in daemon mode, run as user username.
-v volsize, --volsize=volsize
Switch volumes after reaching archive volume size volsize.
-V version, --version=version
Specify archive version. The default and the only accepted value is 2.
-x fd
Allow asynchronous control requests on the file descriptor fd.
-y
Use local timezone instead of the timezone from the pmcd(1) host.
-?, --help
Display usage message and exit.

EXAMPLES

For each PCP utility, there is a sample pmlogger configuration file that could be used to create an archive suitable for replaying with that tool (i.e. includes all of the performance metrics used by the tool). For a tool named foo this configuration file is located in $PCP_VAR_DIR/config/pmlogger/config.foo.

The following is a simple default configuration file for a primary pmlogger instance, and demonstrates most of the capabilities of the configuration specification language.


log mandatory on once { hinv.ncpu hinv.ndisk }
log mandatory on every 10 minutes {
    disk.all.write
    disk.all.read
    network.interface.in.packets [ "et0" ]
    network.interface.out.packets [ "et0" ]
    nfs.server.reqs [ "lookup" "getattr" "read" "write" ]
}
log advisory on every 30 minutes {
    environ.temp
    pmcd.pdu_in.total
    pmcd.pdu_out.total
}

HOSTNAME CHANGES

The hostname of the PMCD that is providing metrics to pmlogger is used in several ways.

PMCD's hostname (or the argument from the -H option) is included in the archive label and may be used to ensure that subsequent operations on multiple archives, e.g. pmlogextract(1), are only applied to archives from the same host.

For pmlogger instances using a local PMCD that are launched and managed by pmlogger_check(1) and pmlogger_daily(1), (or the systemd(1) or cron(8) services that use these scripts), the local hostname may also be used to construct the name of a directory where all the archives for the one host are stored, e.g. $PCP_ARCHIVE_DIR/<hostname>.

And PMCD's hostname is also stored in the archive via the pmcd.pmlogger.hostname metric.

RESUMING COLLECTION

If the hostname of the PMCD host changes, pmlogger will detect this condition when it next attempts to fetch performance metrics from PMCD. If the hostname has changed, pmlogger will perform a re-exec of itself using the same command line arguments that were originally supplied, but with the new hostname substituted for the old one.

This mechanism is used to ensure continuity of performance data after the nightly archive rotation by pmlogger_daily(1).

El nombre de host del host PMCD puede cambiar durante el tiempo de arranque cuando el sistema transita de un nombre de host temporal a un nombre de host persistente, o por acción administrativa explícita en cualquier momento después de que el sistema se haya arrancado. Cuando esto sucede, pmlogger puede necesitar tomar medidas especiales, específicamente si la instancia de pmlogger fue lanzada desde pmlogger_check(1) o pmlogger_daily(1), entonces pmlogger debe salir. En circunstancias normales systemd(1) o cron(8) lanzará un nuevo pmlogger poco después, y esta nueva instancia de pmlogger operará en el contexto del nuevo nombre de host para el host donde se está ejecutando PMCD.

MÉTRICAS DERIVADAS

Como se describe en pmRegisterDerived(3), las métricas derivadas proporcionan un mecanismo para extender el PMNS con nuevas métricas definidas en el lado del cliente de PCP utilizando expresiones sobre las métricas de rendimiento existentes. Las métricas derivadas pueden incluirse en un archivo de configuración de pmlogger, pero vienen con algunas reglas de manejo especiales.

Primero, los valores de una métrica derivada, no las métricas operandos en la expresión de la métrica derivada, se almacenan en el archivo. Esto se debe a que la definición de una métrica derivada existe independientemente de pmlogger y del archivo y puede ser diferente, o no existir en absoluto, cuando el archivo se reproduce.

Para evitar ambigüedades durante la reproducción del archivo, el identificador de métrica de rendimiento (PMID) de cada métrica derivada se reescribe (o ``se reasigna'') para indicar que esta era, pero ahora no es, una métrica derivada; consulte pmRegisterDerived(3) para una descripción detallada de la reasignación de PMID.

DIAGNÓSTICO

Los archivos son lo suficientemente valiosos como para que pmlogger no trunque un archivo físico existente. Un mensaje de la forma

...: "foo.index" ya existe, no se sobrescribe
...: El archivo existe
indica que esta situación ha surgido. Debe eliminar explícitamente los archivos y volver a lanzar pmlogger.

Puede haber como máximo una instancia principal de pmlogger por host monitoreado; intentar doblar esta regla produce el error:

pmlogger: ya hay un pmlogger principal en ejecución

Varios otros mensajes relacionados con la creación y/o eliminación de archivos en $PCP_TMP_DIR/pmlogger sugieren un problema de permisos en este directorio, o que han aparecido archivos errantes en él.

ARCHIVOS

archivo.meta
metadatos (descripciones de métricas, dominios de instancias, etc.) para el archivo
archivo.0
volumen inicial de valores de métricas (volúmenes subsiguientes tienen sufijos 1, 2, ...)
archivo.index
índice temporal para soportar acceso aleatorio rápido a los otros archivos en el archivo
$PCP_TMP_DIR/pmlogger
pmlogger mantiene los archivos en este directorio como el mapa entre el ID de proceso de la instancia de pmlogger y el puerto IPC que puede usarse para controlar cada instancia de pmlogger (como usa pmlc(1))
$PCP_VAR_DIR/config/pmlogger/config.default
archivo de configuración predeterminado para la instancia del registrador principal lanzada desde $PCP_RC_DIR/pmlogger
$PCP_VAR_DIR/config/pmlogger/config.*
archivos de configuración variados adecuados para crear registros que puedan ser reproducidos posteriormente con las herramientas de visualización y monitoreo de PCP
$PCP_ARCHIVE_DIR/<nombre_host>
Directorio predeterminado para los archivos de archivo de PCP para valores de métricas de rendimiento recolectados del host <nombre_host>.
$PCP_SYSCONFIG_DIR/pmlogger

./pmlogger.log
(o $PCP_ARCHIVE_DIR/<nombre_host>/pmlogger.log cuando se inicia automáticamente por $PCP_RC_DIR/pmlogger o uno de los scripts de monitoreo de pmlogger(1) como pmlogger_check(1))

AMBIENTE

Normalmente pmlogger crea un socket para recibir mensajes de control de pmlc(1) en el primer puerto TCP/IP disponible numerado 4330 o superior. La variable de entorno PMLOGGER_PORT puede usarse para especificar un número de puerto de inicio alternativo.

Si se establece en el valor 1, la variable de entorno PMLOGGER_LOCAL hará que pmlogger se ejecute en un modo de operación solo de localhost, donde se vincula solo a la interfaz de bucle inverso.

La variable PMLOGGER_REQUEST_TIMEOUT puede ser establecida por aplicaciones como pmlc(1) para especificar un tiempo de espera en segundos para las solicitudes de conexión al puerto de control de pmlogger. Si no se establece, las conexiones pueden bloquearse indefinidamente. Esta variable normalmente no sería establecida por pmlogger mismo.

La variable PMLOGGER_MAXPENDING puede establecerse para indicar la longitud máxima que puede alcanzar la cola de conexiones pendientes de pmlc.

El intervalo de muestreo predeterminado utilizado por pmlogger se puede establecer usando la variable PMLOGGER_INTERVAL (si no se establece, se usarán 60 segundos). Tanto la línea de comandos como las directivas en el archivo de configuración anularán este valor. Es un entero en unidades de segundos.

En plataformas que utilizan systemd(1), y cuando se proporciona la opción -N, la variable de entorno NOTIFY_SOCKET normalmente sería establecida por el gestor de servicios antes de lanzar pmlogger.

Dos variables de entorno adicionales se utilizan como parte del traspaso de una instancia de pmlogger a la siguiente durante una operación de re-ejecución, a saber, __PMLOGGER_REEXEC y __PMLOGGER_TZ. Los detalles de cómo se utilizan son un detalle de implementación interna, pero los usuarios finales deben evitar usar variables con estos nombres en el entorno de su shell.

AMBIENTE PCP

Las variables de entorno con el prefijo PCP_ se utilizan para parametrizar los nombres de archivos y directorios utilizados por PCP. En cada instalación, el archivo /etc/pcp.conf contiene los valores locales para estas variables. La variable $PCP_CONF puede usarse para especificar un archivo de configuración alternativo, como se describe en pcp.conf(5).

OPCIONES DE DEPURACIÓN

La opción -D o --debug habilita la salida de diagnósticos adicionales en stderr para ayudar a clasificar problemas, aunque la información es a veces críptica y está destinada principalmente a proporcionar orientación para los desarrolladores en lugar de para los usuarios finales. debug es una lista separada por comas de opciones de depuración; use pmdbg(1) con la opción -l para obtener una lista de las opciones de depuración disponibles y su significado.

Las opciones de depuración específicas para pmlogger son las siguientes:

Opción Descripción
appl0 PDUs de solicitud de control hacia y desde pmlc(1)
appl1 intercambio de credenciales
appl2 diagnósticos del bucle de alarma (temporización), trabajo de devolución de llamada y mensajes del modo de control de registro
appl3 devoluciones de llamada de señales y registro de salida
appl4 marcas de tiempo de registro en logfile a medida que se alcanzan los hitos
appl5 estadísticas de PDU después de procesar el archivo conffile
appl6 construcción de la caché de metadatos desde conffile para acelerar el rendimiento de inicio, trabajo de pass0()
appl7 suprimir la construcción de la caché de metadatos, pass0() se convierte en una operación nula
appl8 actualizaciones y consultas de hist_hash para soportar el comando query de pmlc(1)
