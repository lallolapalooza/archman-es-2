NOMBRE

pmdaInit, pmdaRehash, pmdaSetData, pmdaExtGetData, pmdaExtSetData, pmdaSetFlags, pmdaSetCommFlags, pmdaExtSetFlags - inicializar un PMDA

C SINOPSIS

#include <pcp/pmapi.h>
#include <pcp/pmda.h>

void pmdaInit(pmdaInterface *dispatch,
pmdaIndom *indoms, int nindoms, pmdaMetric *metrics, int nmetrics);

void pmdaRehash(pmdaExt *pmda,
pmdaMetric *metrics, int nmetrics);

void pmdaSetFlags(pmdaInterface *dispatch, int flags);
void pmdaSetCommFlags(pmdaInterface *dispatch, int flags);
void pmdaExtSetFlags(pmdaExt *pmda, int flags);
void pmdaSetData(pmdaInterface *dispatch, void *data);
void pmdaExtSetData(pmdaExt *pmda, void *data);
void *pmdaExtGetData(pmdaExt *pmda);

cc ... -lpcp_pmda -lpcp

DESCRIPCIÓN

pmdaInit inicializa un PMDA para que esté listo para recibir PDUs de pmcd(1). La función espera como argumentos la tabla de dominios de instancia (indoms) y la tabla de descripción de métricas (metrics) que son inicializadas por el PMDA. Los argumentos nindoms y nmetrics deben establecerse en el número de instancias y métricas en las tablas, respectivamente.

Gran parte de la estructura pmdaInterface puede ser inicializada automáticamente con pmdaDaemon(3), pmdaGetOpt(3) y pmdaDSO(3). pmdaInit completa la fase de inicialización del PMDA con tres operaciones. La primera operación agrega los números de dominio e instancia a las tablas de instancia y métricas. Las métricas singulares (métricas sin un dominio de instancia) deben tener el dominio de instancia PM_INDOM_NULL establecido en el campo indom de la estructura pmDesc (ver pmLookupDesc(3)). Las métricas con un dominio de instancia deben establecer este campo para que sea el número de serie del dominio de instancia en la tabla indoms.

La tabla de dominios de instancia puede dejarse vacía estableciendo indoms a NULL y nindoms a 0. Esto permite al llamador proporcionar funciones de devolución de llamada personalizadas de Fetch e Instance. La tabla de métricas puede dejarse vacía estableciendo metrics a NULL y nmetrics a 0. Esto permite al llamador proporcionar funciones de devolución de llamada personalizadas de Fetch y Descriptor.

EJEMPLO

Por ejemplo, un PMDA tiene tres métricas: A, B y C, y dos dominios de instancia X e Y, con dos instancias en cada dominio de instancia. Las tablas de descripción de dominios de instancia y métricas podrían definirse como:

static pmdaInstid _X[] = {
    { 0, "X1" }, { 1, "X2" }
};
static pmdaInstid _Y[] = {
    { 0, "Y1" }, { 1, "Y2" }
};
static pmdaIndom indomtab[] = {
#define X_INDOM 0
    { X_INDOM, 2, _X },
#define Y_INDOM 3
    { Y_INDOM, 2, _Y }
};
static pmdaMetric metrictab[] = {
/* A */
    { (void *)0,
      { PMDA_PMID(0,0), PM_TYPE_U32, PM_INDOM_NULL, PM_SEM_INSTANT,
        { 0,0,0,0,0,0} }, },
/* B */
    { (void *)0,
      { PMDA_PMID(0,1), PM_TYPE_U32, X_INDOM, PM_SEM_INSTANT,
        { 0,0,0,0,0,0} }, },
/* C */
    { (void *)0,
      { PMDA_PMID(0,2), PM_TYPE_DOUBLE, Y_INDOM, PM_SEM_INSTANT,
        { 0,1,0,0,PM_TIME_SEC,0} }, }
};

La tabla de descripción de métricas define la métrica A sin dominio de instancia, la métrica B con dominio de instancia X y la métrica C con dominio de instancia Y. La métrica C tiene unidades de segundos, mientras que las otras métricas no tienen unidades (contadores simples). pmdaInit tomará estas estructuras y asignará el número de dominio PMDA(3) al campo it_indom de cada dominio de instancia. Este identificador también reemplaza el campo indom de todas las métricas que tienen ese dominio de instancia, para que estén correctamente asociadas.

La segunda etapa abre el archivo de texto de ayuda, si se especificó con la opción de línea de comandos -h (ver pmdaGetOpt(3)) o como un argumento helptext a pmdaDSO(3) o pmdaDaemon(3).

La etapa final implica la preparación de la estrategia de búsqueda de la tabla de métricas.

BÚSQUEDA DE MÉTRICAS

Cuando se realizan solicitudes de obtención y descriptor al PMDA, cada PMID solicitado debe mapearse a una entrada de la tabla de métricas. Actualmente existen tres estrategias para realizar este mapeo: directo, lineal y hash. Cada una tiene su propio conjunto de compensaciones y se debe seleccionar una estrategia apropiada para cada PMDA.

Si todos los números de ítem PMID de la métrica corresponden a la posición en la tabla metrics, entonces se utiliza el mapeo directo. Esta es la más eficiente de las funciones de búsqueda, ya que implica un índice de matriz directo (no se requiere memoria adicional ni sobrecarga de procesamiento adicional). Si los requisitos de numeración de PMID son cumplidos por el PMDA, es ideal. Esta estrategia se puede solicitar explícitamente llamando a pmdaSetFlags(pmda, PMDA_EXT_FLAG_DIRECT) antes de llamar a pmdaInit. En este caso, si el mapeo directo no es posible (por ejemplo, debido a un descuido por parte del desarrollador del PMDA), se registra una advertencia y se utiliza la estrategia lineal en su lugar.

La segunda estrategia (búsqueda lineal) es la predeterminada, cuando no se puede establecer un mapeo directo. Esto proporciona una mayor flexibilidad en el esquema de numeración de PMID, ya que los números de ítem del PMDA no tienen que ser únicos (por lo tanto, los números de clúster PMID se pueden usar con más libertad, lo que a menudo es extremadamente conveniente para el desarrollador del PMDA). Sin embargo, la búsqueda implica un recorrido lineal desde el inicio de la tabla de métricas hasta que se encuentra un PMID coincidente, para cada PMID solicitado en una solicitud.

La tercera estrategia (búsqueda hash) se puede solicitar llamando a pmdaSetFlags(pmda, PMDA_EXT_FLAG_HASHED) antes de llamar a pmdaInit. Esta estrategia es más útil para PMDAs con un gran número de métricas (cientos o miles). Dichos PMDAs casi siempre utilizarán el esquema de numeración de clústeres, por lo que el esquema de búsqueda directa se vuelve inapropiado. También pueden estar dispuestos a sacrificar una pequeña cantidad de memoria adicional para una tabla hash, que mapea PMID a offsets de tabla de métricas, para acelerar las búsquedas en sus vastas tablas de métricas.

Esta estrategia final también puede ser utilizada por los PMDAs que sirven métricas numeradas dinámicamente. Para este caso, la función pmdaRehash debe usarse para reemplazar la tabla de métricas cuando nuevas métricas estén disponibles, o cuando se eliminen las métricas existentes. El mapeo hash de PMID se recalculará al mismo tiempo que se instala la nueva tabla de métricas.

CAMBIOS DE MÉTRICAS

Los autores de PMDA deben entender bien que los metadatos de métricas para métricas individuales son fijos y, idealmente, nunca deberían cambiar. En la situación en la que los metadatos son incorrectos y se actualizan, dicho cambio requiere corrección en las métricas registradas usando pmlogrewrite(1), y como resultado, debe evitarse siempre que sea posible.

Sin embargo, un PMDA puede enterarse de nuevas métricas de dominio en tiempo de ejecución, y en este caso es ideal exportarlas inmediatamente (sin ningún reinicio del sistema colector). En esta situación, el PMDA puede informar a todos los clientes de PMAPI en ejecución que ya han explorado el espacio de nombres de métricas (por ejemplo, usando pmTraversePMNS(3)) sobre el cambio en el espacio de nombres de métricas.

Esto se logra usando pmdaSetFlags(pmda, PMDA_EXT_NAMES_CHANGE), lo que resultará en que la notificación de cambio de estado PMCD_NAMES_CHANGE se envíe a cada cliente de PMAPI en la próxima obtención. Si las métricas recién descubiertas tienen metadatos de etiqueta asociados, entonces el flag PMDA_EXT_LABEL_CHANGE también puede ser establecido, lo que resultará en que la notificación PMCD_LABEL_CHANGE se envíe también.

pmdaExtSetFlags es equivalente a pmdaSetFlags, y se proporciona como una interfaz de conveniencia en situaciones donde pmdaExt está más disponible que la estructura pmdaInterface.

pmdaInit(3)

NAME

pmdaInit - initialize a PMDA (Performance Metrics Domain Agent)

C SYNOPSIS

cc [...] -I$PCP_INC -L$PCP_LIB -lpcp -lpmda [...]

#include <pcp/pmda.h>

int pmdaInit(int argc, char **argv, pmdaDispatch **dispatch);

DESCRIPTION

The pmdaInit function is used to initialize a Performance Metrics Domain Agent (PMDA). It is the first function called by any PMDA, whether it is loaded dynamically as a DSO (see pmdaDSO(3)) or run as a separate daemon (see pmdaDaemon(3)).

pmdaInit parses the command line arguments, initializes the Performance Co-Pilot (PCP) library, and sets up the PMDA dispatch table. The dispatch table is a structure that the PMDA uses to register callback functions for various PMAPI (Performance Metrics API) operations. The pmdaInit function returns a pointer to this dispatch table via the dispatch argument.

The pmdaInit function initializes the PMDA environment. It parses command line arguments, sets up the PMDA dispatch table, and performs necessary initializations for the PMDA to interact with the Performance Co-Pilot system daemon (pmcd(1)).

The argc and argv parameters are the standard command line arguments passed to the PMDA. pmdaInit will process PCP-specific arguments and remove them from the argument list before returning. The remaining arguments can then be processed by the PMDA itself.

The dispatch parameter is a pointer to a pointer to a pmdaDispatch structure. Upon successful return, this pointer will point to the initialized dispatch table, which the PMDA must populate with its callback functions.

EXAMPLE

A typical initialization sequence in a PMDA would look like:

int
main(int argc, char **argv)
{
    pmdaDispatch *dispatch;
    int sts;

    sts = pmdaInit(argc, argv, &dispatch);
    if (sts != 0) {
        /* Handle error */
        exit(1);
    }

    /* ... populate dispatch table ... */

    /* ... start PMDA main loop ... */

    return 0;
}

METRIC LOOKUP

When pmdaInit is called, it attempts to locate and load the PMNS (Performance Metrics Name Space) and any associated metric description files. The PMNS is a hierarchical namespace that maps human-readable metric names to internal Performance Metrics Identifiers (PMIDs). The metric description files contain detailed information about each metric, such as its data type, semantics, and units.

The search path for these files is determined by PCP configuration settings and command-line options. If pmdaInit cannot locate the necessary files, it may issue warning messages or return an error.

METRIC CHANGES

PMDAs can dynamically change the set of metrics they export. This can be done using the pmdaSetStateChange() function, which signals to pmcd(1) that the PMDA's metric set has changed. pmcd(1) will then re-query the PMDA for its current metric descriptions.

This is useful for PMDAs that monitor resources whose availability or characteristics can change during runtime.

COMMUNICATION ATTRIBUTES

The PMDA can query certain communication attributes established between the PMDA and pmcd or a local context client. The function pmdaGetFlags(3) can be used to retrieve these attributes. Valid flags are PMDA_FLAG_AUTHORIZE (for authentication related attributes) and PMDA_FLAG_CONTAINER (for container name related attributes).

PRIVATE DATA

A facility for associating private PMDA data with the pmdaExt structure is available. This allows a PMDA to associate an arbitrary (and typically not global) pointer with the pmdaExt such that it can be later obtained during callbacks. The interfaces for setting this pointer are pmdaSetData and pmdaExtSetData, and pmdaExtGetData for subsequently retrieving it.

CAVEAT

The PMDA must be using PMDA_INTERFACE_2 or later, as specified in the call to pmdaDSO(3) or pmdaDaemon(3) to use pmdaInit.

The PMDA must use PMDA_INTERFACE_7 or later to issue state change notifications using pmdaSetFlags or pmdaExtSetFlags.

DIAGNOSTICS

pmdaInit will set dispatch->status to a value less than zero if there is an error that would prevent the PMDA(3) from successfully running. pmcd(1) will terminate the connection to the PMDA(3) if this occurs.

pmdaInit may issue any of these messages:

PMDA interface version interface not supported
The interface version is not supported by pmdaInit.
Using pmdaFetch() but fetch call back not set
The fetch callback, pmdaFetch(3), requires an additional callback to be provided using pmdaSetFetchCallBack(3).
Illegal instance domain inst for metric pmid
The instance domain inst that was specified for metric pmid is not within the range of the instance domain table.
No help text path specified
The help text callback, pmdaText(3), requires a help text file for the metrics to have been opened, however no path to the help text was specified as a command line option, or as an argument to pmdaDSO(3) or pmdaDaemon(3). This message is only a warning.
Direct mapping for metrics disabled @ num
The unit numbers of the metrics did not correspond to the index in the metric description table. The direct mapping failed for metric number num in the metrics table. This is less efficient but is not fatal and the message is only a warning.
Hashed mapping for metrics disabled @ num
A memory allocation failure occurred while building the hash table to index the metric description table. This is a non-fatal warning message - a fallback to linear searching will be automatically performed should this situation arise.
