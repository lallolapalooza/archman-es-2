Paquete: pcp

PMREGISTERDERIVED(3) Manual de Funciones de Librería PMREGISTERDERIVED(3)

NOMBRE

pmRegisterDerived, pmRegisterDerivedMetric - registrar un nombre y definición global de métrica derivada

SINOPSIS

#include <pcp/pmapi.h>

char *pmRegisterDerived(char *name, char *expr);
int pmRegisterDerivedMetric(char *name,
char *expr, char **errmsg);

cc ... -lpcp

DESCRIPCIÓN

Las métricas derivadas proporcionan una forma de extender el Espacio de Nombres de Métricas de Rendimiento (PMNS) con nuevas métricas definidas en el lado del cliente de PCP utilizando expresiones sobre las métricas de rendimiento existentes.

Los usos típicos serían agregar un número de métricas similares para proporcionar una métrica de resumen de nivel superior o para soportar la clase de métricas de ``valor delta de A sobre valor delta de B'' que no son posibles en la semántica de datos base de PCP. Un ejemplo de la última clase sería el tamaño promedio de E/S, definido como

delta(disk.dev.total_bytes) / delta(disk.dev.total)
donde ambas métricas de disk.dev son contadores, y lo que se requiere es muestrear ambas métricas, calcular la diferencia entre los valores actual y anterior y luego calcular la relación de estas diferencias.

Los argumentos para pmRegisterDerived son el nombre de la nueva métrica derivada y expr es una expresión que define cómo se deben calcular los valores de name.

pmRegisterDerivedMetric es el equivalente funcional exacto a pmRegisterDerived, excepto que proporciona un modelo simplificado de manejo de errores, donde se devuelve un mensaje formateado a través del parámetro errmsg.

Se realiza una verificación sintáctica en el momento en que se llama a pmRegisterDerived, pero la verificación semántica se pospone hasta que se crea cada nuevo contexto PMAPI con pmNewContext(3) o se restablece con pmReconnectContext(3), momento en el cual el PMNS y la metadatos están disponibles para permitir la verificación semántica y la determinación de los metadatos de las métricas derivadas.

Si pmRegisterDerived se llama después de que se hayan abierto uno o más contextos PMAPI, las métricas recién registradas estarán disponibles en esos contextos; sin embargo, el uso más normal sería realizar todas las llamadas a pmRegisterDerived (posiblemente a través de pmLoadDerivedConfig(3)) o pmRegisterDerivedMetric antes de llamar a pmNewContext(3).

Todas las métricas derivadas globales definidas están disponibles en todos los contextos PMAPI.

También es posible definir métricas derivadas por contexto una vez que se ha establecido un contexto PMAPI. Estas métricas derivadas son privadas para el contexto en el que se definen utilizando las rutinas asociadas pmAddDerived(3) y pmAddDerivedMetric(3).

Para anular la definición de una métrica derivada por nombre, consulte pmUnregisterDerived(3), que elimina todas las instancias de la métrica derivada en todos los contextos, independientemente de cómo se definió la métrica derivada.

name debe seguir las reglas sintácticas para los nombres de las métricas de rendimiento, a saber, uno o más componentes separados por un punto (``.''), y cada componente debe comenzar con una letra seguida de cero o más caracteres extraídos de letras, números y guion bajo (``_''). Para más detalles, consulte PCPIntro(1) y PMNS(5).

name debe ser único entre todas las métricas derivadas y no debe coincidir con el nombre de ninguna métrica regular en el PMNS. Es aceptable que name comparta parte de su prefijo con un subárbol existente del PMNS, por ejemplo, la métrica de tamaño promedio de E/S anterior podría llamarse disk.dev.avgsz, lo que la colocaría entre las otras métricas de disk.dev en el PMNS. Alternativamente, las métricas derivadas podrían poblar su propio subárbol del PMNS, por ejemplo, la métrica de tamaño promedio de E/S anterior podría llamarse my.summary.disk.avgsz.

La expresión expr sigue estas reglas sintácticas:

  • Los elementos terminales son nombres de métricas existentes o constantes numéricas. No se permiten definiciones recursivas, por lo que solo se pueden utilizar los nombres de métricas regulares (no otras métricas derivadas). Las constantes numéricas son enteros limitados a la precisión de enteros sin signo de 32 bits o números de punto flotante de doble precisión.
  • Se admiten los operadores aritméticos binarios habituales, a saber, suma (``+''), resta (``-''), multiplicación (``*'') y división (``/'') con las reglas de precedencia normales, donde la multiplicación y la división tienen mayor precedencia que la suma y la resta, por lo que a+b*c se evalúa como a+(b*c).
  • Se puede usar negación unaria, por ejemplo, -3*some.metric.
  • Se admiten operadores relacionales estilo C, a saber, ``<'', ``<='', ``=='', ``>='', ``>'' y ``!=''. Las expresiones relacionales devuelven un valor como un número sin signo de 32 bits, siendo 0 para falso y 1 para verdadero. Se aplican las reglas de precedencia de operadores esperadas, por lo que los operadores aritméticos tienen mayor precedencia que los operadores relacionales, y a-b>c+d se evalúa como (a-b)>(c+d). Todos los operadores relacionales tienen la misma precedencia, por lo que la expresión (ligeramente extraña) que involucra operadores relacionales consecutivos a>b!=c se evalúa como (a>b)!=c.
  • Se admiten operadores booleanos estilo C, a saber, AND (``&&'') y OR (``||''). Las expresiones booleanas devuelven un valor como un número sin signo de 32 bits, siendo 0 para falso y 1 para verdadero. Se aplican las reglas de precedencia de operadores esperadas, por lo que los operadores relacionales tienen mayor precedencia que los operadores booleanos, y a>b*c&&d<=e+f se evalúa como (a>(b*c))&&(d<=(e+f)). Ambos operadores booleanos tienen la misma precedencia, por lo que la expresión que involucra operadores booleanos consecutivos a>=b||b>c&&d!=e||f>g se evalúa como (((a>=b)||(b>c))&&(d!=e))||(f>g).
  • Adicionalmente, el operador ``!'' se puede usar para negar una expresión booleana o relacional, devolviendo un valor como un número sin signo de 32 bits, siendo 0 para falso y 1 para verdadero. Se aplican las reglas de precedencia de operadores esperadas, por lo que los operadores booleanos (y relacionales) tienen mayor precedencia que la negación booleana, y !a>b||c<d se evalúa como !((a>b)||(c<d)), mientras que !a<b+c se evalúa como !(a<(b+c)).
  • Se admiten expresiones condicionales ternarias estilo C. En términos generales, la expresión check ? foo : bar se evalúa como foo (el operando ``verdadero'') si check (el ``guardia'') es verdadero, de lo contrario, la expresión se evalúa como bar (el operando ``falso''). Se aplican algunas reglas semánticas especiales al operando ``guardia'' y a los otros dos operandos:
(a)
Cada expresión puede involucrar un valor singular o un conjunto de valores (cuando la expresión involucra una o más métricas con un dominio de instancias).
(b)
Todas las expresiones con un conjunto de valores deben definirse sobre el mismo dominio de instancias.
(c)
Ambas expresiones operandos deben tener la misma metadatos, es decir, el mismo tipo de métrica, semántica y unidades (dimensión y escala).
(d)
La expresión ``guardia'' debe tener un valor aritmético, relacional o booleano, para que pueda evaluarse como 0 para falso, de lo contrario, verdadero.
(e)
Si la expresión ``guardia'' tiene un valor singular y una o más de las otras expresiones operandos involucran un dominio de instancias, el ``guardia'' se aplica a todas las instancias.
(f)
Si la expresión ``guardia'' tiene un conjunto de valores y una o más de las otras expresiones operandos involucran un dominio de instancias, el ``guardia'' se evalúa una vez por cada instancia (debe haber un dominio de instancias según la regla (b) anterior).
(g)
Si una de las expresiones operandos tiene un valor singular y la otra tiene un conjunto de valores, y el valor singular se selecciona en función de la evaluación del ``guardia'', el resultado es un conjunto de valores (todos iguales) con la enumeración de instancias tomada de la otra expresión operando. (h)
Como caso especial, cualquiera (pero no ambos) de las expresiones foo o bar puede ser el constructor especial novalue(). Si novalue() necesita ser evaluado, no devolverá ningún valor. El uso más común de novalue() es en conjunción con defined() como en el siguiente ejemplo:

mumble = defined(abc.def) ? count(abc.def) : novalue()

Los metadatos para novalue() se toman del operando par del operador :, haciendo que las condiciones (b) y (c) anteriores sean trivialmente verdaderas; si el operando par no se puede evaluar, entonces los metadatos predeterminados para novalue() son un entero discreto singular sin unidades, y las condiciones (b) y (c) se omiten.

Una extensión de novalue() es novalue(<metadatos>) donde los <metadatos> se pueden especificar usando uno o más parámetros de la forma etiqueta=valor o etiqueta="valor" como se describe para el constructor mkconst() a continuación, por ejemplo:

novalue(tipo=float, semantica=instante, unidades="Kbytes/sec")

(i)
Como un caso adicional, si check tiene la forma defined(somemetric), entonces se permiten referencias a métricas no definidas en cualquiera de foo o bar que no sea requerido una vez que se ha establecido la existencia de somemetric. Esto permite usos de la forma:


fumble = defined(new.metric) ? new.metric : old.metric

lo cual es válido cuando new.metric está definido y cuando new.metric no está definido, aunque esto significa que las reglas (b) y (c) se relajan en este caso, lo que además significa que novalue() puede no tener un operando par para proporcionar metadatos.

Se admite una generalización de esta construcción para cualquier check que se pueda evaluar estáticamente, por lo que una expresión booleana que involucre predicados defined(), por ejemplo:

bar = !defined(a) || !defined(b) ? novalue() : a + b

•
La selección de una instancia única se puede especificar mediante la construcción ``[nombre_instancia]'' que se puede agregar a un nombre de métrica o a una expresión entre paréntesis. Por ejemplo:

fw.bytes = network.interface.in.bytes[eth1] + \
  network.interface.out.bytes[eth1]

o (equivalente):

fw.bytes = (network.interface.in.bytes + \
  network.interface.out.bytes)[eth1]

Todos los caracteres entre ``['' y ``]'' se consideran parte del nombre de instancia (externo), así que tenga cuidado de evitar cualquier espacio en blanco espurio. Se puede usar una barra invertida como prefijo de escape en el (improbable) caso de que el nombre de instancia externo contenga un ``]''.

•
Las constantes numéricas también se pueden especificar usando el constructor mkconst() que toma varios argumentos: el primero es una constante numérica (entera o de punto flotante), luego siguen uno o más parámetros de la forma etiqueta=valor o etiqueta="valor" donde los valores permitidos de etiqueta y valor son los siguientes:
etiqueta valor
tipo uno de los tipos de métrica numérica de <pcp/pmapi.h>, despojado del prefijo PM_TYPE_, por lo tanto 32, U32, 64, U64, FLOAT o DOUBLE.
semantica uno de los tipos semánticos de <pcp/pmapi.h>, despojado del prefijo PM_SEM_, por lo tanto COUNTER, INSTANT o DISCRETE.
unidades una especificación de dimensión y escala (que forman juntas las unidades), en la sintaxis aceptada por pmParseUnitsStr(3).
meta un nombre de métrica y esa métrica proporciona los metadatos base que pueden ser modificados por otros parámetros

El valor puede opcionalmente estar entre comillas dobles, y puede aparecer en cualquier combinación de mayúsculas y/o minúsculas. La etiqueta debe estar en minúsculas como se muestra en la tabla anterior.

Esto es más útil cuando la semántica de la expresión requiere un tipo y/o semántica y/o unidades coincidentes para los operandos, por ejemplo:

idle = mem.util.free > mkconst(10485760, unidades=Kbyte)
avg_io_size = delta(disk.dev.total) == 0 ? \
mkconst(1.0, semantica=instante, unidades="kbyte / count") : \
delta(disk.dev.total_bytes) / delta(disk.dev.total)

•
Las expresiones se pueden reescalar usando la función rescale que toma dos argumentos. El primero es una expresión aritmética para reescalar, y el segundo son las unidades deseadas después de reescalar, que es un valor de cadena en la sintaxis aceptada por pmParseUnitsStr(3). Por ejemplo:

rescale(network.interface.total.bytes, "Mbytes/hour")

La expresión y las unidades deseadas deben tener la misma dimensión, por ejemplo Espacio=1, Tiempo=-1 y Recuento=0 en el ejemplo anterior.

  • Las siguientes funciones unarias operan sobre una única métrica de rendimiento y devuelven uno o más valores. Para todas las funciones (excepto count() y defined()), el tipo de métrica operando debe ser aritmético (entero de varios tamaños y signo, flotante o doble).
    Función Valor
    avg(x) Una instancia singular que es el valor promedio en todas las instancias para la métrica x.
    count(x) Una instancia singular que es el recuento del número de instancias para la métrica x. Como caso especial, si la obtención de la métrica x devuelve un error, entonces count(x) será 0.
    defined(x) Un valor booleano que es verdadero (``1'') si la métrica x está definida en el PMNS, de lo contrario falso (``0''). La función se evalúa cuando se crea un nuevo contexto PMAPI con pmNewContext(3) o se restablece con pmReconnectContext(3). Por lo tanto, cualquier cambio posterior en el PMNS después de que se haya establecido el contexto PMAPI no cambiará el valor de esta función en la evaluación de la expresión.
    max(x) Una instancia singular que es el valor máximo en todas las instancias para la métrica x.
    min(x) Una instancia singular que es el valor mínimo en todas las instancias para la métrica x.
    sum(x) Una instancia singular que es la suma de los valores en todas las instancias para la métrica x.
  • La siguiente función unaria devuelve el valor instantáneo de una expresión, no el valor convertido a tasa que es el predeterminado para las expresiones con la semántica de PM_SEM_COUNTER.
    Función Valor
    instant(expr) Devuelve el valor actual de la expresión, incluso si tiene la semántica de un contador, es decir, PM_SEM_COUNTER. La semántica de la métrica derivada se basa en la semántica de la expresión expr; si expr tiene semántica PM_SEM_COUNTER, la semántica de instant(expr) es PM_SEM_INSTANT, de lo contrario la semántica de la métrica derivada es la misma que la semántica de expr.
  • Las siguientes funciones unarias devuelven valores calculados a partir del valor de una expresión en muestras consecutivas, o llamadas a pmFetch(3). La expresión (expr a continuación) puede involucrar una o más métricas pero debe tener un valor aritmético (entero de varios tamaños y signo, flotante o doble) para todas las instancias.

Si expr es una expresión de valor de conjunto, entonces solo las instancias que aparecen en ambas muestras aparecerán en el resultado.

Función Valor
delta(expr) Devuelve la diferencia entre el valor de la expresión en la muestra actual y el valor en la muestra anterior. Las unidades y semántica de la expresión resultante se derivan de las de expr. Para las métricas con semántica PM_SEM_COUNTER, esto es equivalente a la tasa de cambio, es decir, la tasa de la expresión. Para otras semánticas, esta función puede ser útil para calcular la variación entre muestras.
derivada(expr) Devuelve la tasa de cambio de la expresión por unidad de tiempo. Las unidades de la expresión resultante son las unidades de la expresión original divididas por la unidad de tiempo (por ejemplo, Kbytes/segundo). La semántica de la expresión resultante es PM_SEM_COUNTER. derivada(expr) es equivalente a delta(expr) / delta(time).
•
El operador de división por cero se detecta para las siguientes operaciones aritméticas binarias: división, módulo y exponenciación. Si se detecta una división por cero, el valor de la expresión será novalue(). Esto se puede usar para evitar errores fatales o para informar de forma segura que no se puede calcular un valor. Por ejemplo:

error_rate = (request_error / request_total) * 100

Esta expresión es segura ya que devolverá novalue() si request_total es cero. Si necesita obtener un valor predeterminado específico en lugar de novalue() en caso de división por cero, puede utilizar el operador ternario como en el siguiente ejemplo:

error_rate = request_total == 0 ? 0 : (request_error / request_total) * 100

FUNCTIONS

The following functions may be used to construct derived metrics:

Function Value
delta(expr) Devuelve la diferencia en los valores de la expresión entre una llamada a pmFetch(3) y la siguiente. Hay un valor en el resultado por cada instancia que aparece tanto en la muestra actual como en la anterior. Si la expresión no tiene signo, entonces el tipo del resultado se convierte para asegurar que se retenga la mayor precisión posible, por lo que si la expresión tiene tipo PM_TYPE_U32, el resultado es de tipo PM_TYPE_64; de lo contrario, si la expresión tiene tipo PM_TYPE_U64, el resultado es de tipo PM_TYPE_DOUBLE. De lo contrario, el tipo del resultado es el mismo que el tipo de la expresión.
rate(expr) Devuelve la diferencia en los valores de la expresión entre una llamada a pmFetch(3) y la siguiente, dividida por el tiempo transcurrido entre las llamadas a pmFetch(3). La semántica de la métrica derivada se basa en la semántica de la expresión con la dimensión en el dominio del tiempo disminuida en uno y escalada si es necesario en el caso de utilización del tiempo donde el operando está en unidades de tiempo, y la métrica derivada no tiene unidades. Hay un valor en el resultado por cada instancia que aparece tanto en la muestra actual como en la anterior, excepto en el caso donde la expresión tiene la semántica de un contador, es decir, PM_SEM_COUNTER, y el valor actual de una instancia es menor que el valor anterior de la misma instancia, entonces no se devuelve ningún valor para esta instancia (esto corresponde a un "desbordamiento de contador" o un "reinicio de contador"). Estas reglas imitan la conversión de tasa aplicada a métricas de contador por herramientas como pmval(1), pmie(1) y pmchart(1).
•
La función matchinst puede usarse para seleccionar un subconjunto de instancias de un dominio de instancias para una métrica o expresión. La función toma dos argumentos:
(a)
Un filtro de instancia que consiste en un operador de negación opcional ``!'' seguido de una expresión regular delimitada por caracteres ``/''. La expresión regular sigue la sintaxis de expresiones regulares extendidas POSIX, como se describe en regex(3). Se puede usar una barra invertida simple para escapar el delimitador de expresión regular ``/'', pero se requieren barras invertidas dobles para escapar cualquier carácter especial de expresión regular, por ejemplo, para el caso (extremadamente improbable) de querer hacer coincidir nombres de instancia como ``algún*texto/otro[texto]'' se requeriría una expresión regular de la forma /algún\\*texto\/otro\\[texto]/. Si está presente, el operador de negación invierte el sentido del filtrado, por lo que se seleccionarán todas las instancias que no coincidan con la expresión regular.
(b)
Una métrica o expresión que debe estar definida sobre un dominio de instancias.

Por ejemplo, la siguiente expresión tendrá valores para la métrica network.interface.in.bytes para todas las interfaces de red excepto los dispositivos de loopback y puentes virtuales:


matchinst(!/^(lo)|(vbir)/, network.interface.in.bytes)

•
La función scalar puede usarse para convertir una métrica o expresión definida sobre un dominio de instancias en un valor escalar que pueda usarse en otras expresiones. Por ejemplo:

net.in.bytes = scalar(network.interface.in.bytes[eth0]) + \
  scalar(network.interface.in.bytes[eth1])

El dominio de instancias se elimina de los metadatos del resultado y el identificador de instancia se elimina del valor durante la obtención.

Si la métrica o expresión involucra más de una instancia, el resultado se forma seleccionando la primera instancia; esto es arbitrario e implica que la función scalar solo debe usarse para métricas o expresiones que se espera que contengan cero o una instancia, por ejemplo, la construcción ``[nombre_instancia]'' o la función matchinst con un patrón que coincida con una o como máximo una instancia.

  • Se pueden usar paréntesis para agrupaciones explícitas.
  • Una línea que termina con ``\'' se trata como "continuará" y la línea siguiente se adjunta después de eliminar ``\'' y el salto de línea incrustado.
  • Las líneas que comienzan con ``#'' se tratan como comentarios y se ignoran.
  • Se ignora el espacio en blanco.

VERIFICACIONES Y REGLAS SEMÁNTICAS

Existen una serie de conversiones necesarias para determinar los metadatos de una métrica derivada y para asegurar que la semántica de las expresiones sea correcta.

En una expresión aritmética o relacional, si la semántica de ambos operandos no es un contador (es decir, PM_SEM_INSTANT o PM_SEM_DISCRETE), el resultado tendrá la semántica PM_SEM_INSTANT, a menos que ambos operandos sean PM_SEM_DISCRETE, en cuyo caso el resultado también es PM_SEM_DISCRETE.

Para una expresión aritmética, la dimensión de cada operando debe ser la misma. Para una expresión relacional, la dimensión de cada operando debe ser la misma, excepto que se permiten constantes numéricas (sin dimensión), por ejemplo, en la expresión network.interface.in.drops > 0.

Para evitar combinaciones arbitrarias y sin sentido, se aplican algunas restricciones a las expresiones que combinan métricas con semántica de contador para producir un resultado con semántica de contador. Para una expresión aritmética, si ambos operandos tienen la semántica de un contador, solo se permiten la suma o la resta; o si el operando izquierdo es un contador y el derecho no lo es, solo se permiten la multiplicación o la división; o si el operando izquierdo no es un contador y el derecho lo es, solo se permite la multiplicación.

Dado que las expresiones relacionales utilizan solo el valor actual y producen un resultado que no es un contador, uno o ambos operandos de una expresión relacional pueden ser contadores.

El mapeo de las unidades (pmUnits) de los metadatos utiliza las siguientes reglas:

  • Si ambos operandos tienen una dimensión de Conteo (Count) y las escalas no son las mismas, use la escala mayor y convierta los valores del operando con la escala menor.
  • Si ambos operandos tienen una dimensión de Tiempo (Time) y las escalas no son las mismas, use la escala mayor y convierta los valores del operando con la escala menor.
  • Si ambos operandos tienen una dimensión de Espacio (Space) y las escalas no son las mismas, use la escala mayor y convierta los valores del operando con la escala menor.
  • Para la suma y la resta, todas las dimensiones de cada uno de los operandos y el resultado son idénticas.
  • Para la multiplicación, las dimensiones del resultado son la suma de las dimensiones de los operandos.
  • Para la división, las dimensiones del resultado son la diferencia de las dimensiones de los operandos.

La conversión de escala implica división si la dimensión es positiva, de lo contrario, multiplicación si la dimensión es negativa. Si se aplica conversión de escala a alguno de los operandos, el resultado se promueve al tipo PM_TYPE_DOUBLE.

Poniendo todo esto junto en un ejemplo, considere la métrica derivada definida de la siguiente manera:
x = network.interface.speed - delta(network.interface.in.bytes) / delta(sample.milliseconds)
El tipo, la dimensión y la escala se propagarían en el árbol de expresiones de la siguiente manera.

Expresión Tipo Dimensión y Escala Factores de Escala
sample.milliseconds DOUBLE millisec
delta(...) DOUBLE millisec
network...bytes U64 byte
delta(...) U64 byte
delta(...) / delta(...) DOUBLE byte/millisec /1048576 y *1000
network...speed FLOAT Mbyte/sec
x DOUBLE Mbyte/sec

Las expresiones que involucran selección de instancia única o la función matchinst deben asociarse con métricas subyacentes que tengan un dominio de instancia. Estos constructores no tienen sentido para métricas singulares.

Debido a que la verificación semántica no se puede realizar en el momento en que se llama a pmRegisterDerived, los errores encontrados durante la verificación semántica (cuando cualquier llamada posterior a pmNewContext(3) o pmReconnectContext(3) tenga éxito) se informan usando pmprintf(3). Estos incluyen:

Error: métrica derivada <nombre1>: operando: <nombre2>: <razón>

Error: métrica derivada <nombre1>: operando (<nombre2> [<pmid2>]): <razón>
Hubo un problema al llamar a pmLookupDesc(3) para identificar la métrica operando <nombre2> con PMID <pmid2> utilizada en la definición de la métrica derivada <nombre1>.
Error semántico: métrica derivada <nombre>: <operando> : <operando> Diferente <metadatos> para ternario

Semantic errors

Semantic error: derived metric <name>: <operand> <op> <operand>: Metadata mismatch for ternary operands
For a ternary expression, the ``true'' operand and the ``false'' operand must have exactly the same metadata, so type, semantics, instance domain, and units (dimension and scale).
Semantic error: derived metric <name>: <operand> <op> <operand>: Dimensions are not the same
Operands must have the same units (dimension and scale) for each of addition, subtraction, the relational operators and the boolean ``and'' or ``or'' operators.
Semantic error: derived metric <name>: <operand> <op> <operand>: Illegal operator for counter and non-counter
Only multiplication or division are allowed if the left operand has the semantics of a counter and the right operand is not a counter.
Semantic error: derived metric <name>: <operand> <op> <operand>: Illegal operator for counters
If both operands have the semantics of counter, only addition or subtraction make sense, so multiplication and division are not allowed.
Semantic error: derived metric <name>: <operand> <op> <operand>: Illegal operator for non-counter and counter
Only multiplication is allowed if the right operand has the semantics of a counter and the left operand is not a counter.
Semantic error: derived metric <metric> <expr> RESCALE <units>: Incompatible dimensions
The parameters <expr> and <units> to the rescale function must have the same dimension along the axes of Time, Space and Count.
Semantic error: derived metric <name>: Incorrect time dimension for operand
Rate conversion using the rate() function is only possible for operand metrics with a Time dimension of 0 or 1 (see pmLookupDesc(3)). If the operand metric's Time dimension is 0, then the derived metrics has a value "per second" (Time dimension of -1). If the operand metric's Time dimension is 1, then the derived metrics has a value of time utilization (Time dimension of 0).
Semantic error: derived metric <name>: <function>(<operand>): Non-arithmetic operand for function
The unary functions are only defined if the operand has arithmetic type. Similarly the first argument to the rescale function must be of arithmetic type.
Semantic error: derived metric <name>: <expr> ? ...: Non-arithmetic operand for ternary guard
The first expression for a ternary operator must have an arithmetic type.
Semantic error: derived metric <name>: ... - ...: Non-arithmetic operand for unary negation
Unary negation only makes sense if the following expression has an arithmetic type.
Semantic error: derived metric <name>: <operand> <op> <operand>: Non-arithmetic type for <left-or-right> operand
The binary arithmetic operators are only allowed with operands with an arithmetic type (integer of various sizes and signedness, float or double).
Semantic error: derived metric <name>: <operand> <op> <operand>: Non-counter and not dimensionless for <left-or-right> operand
For multiplication or division or any of the relational operators, if one of the operands has the semantics of a counter and the other has the semantics of a non-counter (instantaneous or discrete) then the non-counter operand must have no units (dimension and scale).
Semantic error: derived metric <name>: <expr> ? <expr> : <expr>: Non-scalar ternary guard with scalar expressions
If the ``true'' and ``false'' operands of a ternary expression have a scalar value, then the ``guard'' expression must also have a scalar value.
Semantic error: derived metric <name>: <expr> <op> <expr>: Operands should have the same instance domain
For all of the binary operators (arithmetic and relational), if both operands have non-scalar values, then they must be defined over the same instance domain.
Semantic error: derived metric <name>: operand <dname>: Illegal nested derived metric
A derived metric (<dname>) cannot be nested (i.e. used) in the definition of another derived metric (<name>).
Semantic error: derived metric <name>: <expr> <op> <expr>: Illegal operator for non-counters
Metrics with counter semantics may be added or subtracted, but <op> (division or multiplication) is not allowed.
Semantic error: derived metric <name>: operand <bname>: Unknown metric for ternary expression
When a new context was established, the metric <bname> was not in the PMNS of the new context and <bname> is a required operand in the definition of the derived metric <name>.

NAME

pmRegisterDerived, pmAddDerived, pmAddDerivedMetric, pmDerivedErrStr, pmUnregisterDerived - register and unregister derived performance metrics

C SYNOPSIS

#include <pcp/pmapi.h>

int
pmRegisterDerived(const char *exprlist);

int
pmAddDerived(const char *name, const char *expr);

int
pmAddDerivedMetric(const char *name, const char *expr, char **errmsg);

const char *
pmDerivedErrStr(void);

int
pmUnregisterDerived(void);

DESCRIPTION

The Performance Co-Pilot (PCP) system provides a mechanism to define new performance metrics based on existing metrics. These new metrics are called "derived metrics". The derived metrics mechanism is implemented by the set of functions described in this manual page.

The core functionality is the ability to define new metrics using arbitrary arithmetic expressions involving existing performance metrics. The syntax for these expressions is described in PMNS(5).

Derived metrics can be defined globally or on a per-context basis. The context is established using pmNewContext(3) or pmReconnectContext(3), and the derived metrics are registered using pmAddDerived(3) or pmAddDerivedMetric(3).

pmRegisterDerived may be used to register a list of derived metric definitions, as described in PMNS(5).

pmAddDerived registers a single derived metric named name with the expression expr. The metric is registered globally and is available in all contexts established after the call to pmAddDerived.

pmAddDerivedMetric is similar to pmAddDerived, but it allows for error reporting. If the expression expr does not conform to the required syntax, pmAddDerivedMetric returns -1 and sets errmsg to point to a dynamically allocated error message string. The caller is responsible for freeing this string using free(3). If the expression is syntactically correct, pmAddDerivedMetric returns 0 and errmsg is undefined.

pmDerivedErrStr returns the last parser error message generated by pmAddDerivedMetric(3).

pmUnregisterDerived unregisters all derived metrics that have been registered using pmAddDerived(3) or pmAddDerivedMetric(3).

SEMANTIC CHECKS AND RULES

The following semantic checks and rules are applied when derived metrics are registered:

  • All derived metrics must be unique within a given context. A derived metric definition cannot use the same name as an existing base metric or another derived metric.
  • The expression used to define a derived metric must refer to existing performance metrics.
  • Derived metrics can be defined in terms of other derived metrics.
  • The set of performance metrics referenced by a derived metric definition must be available in the context in which the derived metric is to be evaluated.
  • The semantics of derived metrics are influenced by the context's access to instance domains. If a derived metric is defined using an expression that references metrics with different instance domain semantics, the derived metric will inherit the most general semantics. For example, if a derived metric uses metrics from both a global instance domain and a per-context instance domain, the derived metric will be considered to have a per-context instance domain.

EXPRESSION EVALUATION

Derived metrics are evaluated when requested by a client application, typically via a call to pmFetch(3) or pmFetchArchive(3). The evaluation process involves parsing the expression, resolving the referenced metrics, and performing the specified computations.

The following table summarizes the behavior of derived metrics based on the `derived.type` attribute, which specifies how instances are handled:

derived.type derived.indom derived.flags derived.mask global
no no no no none; the metric is undefined
no no no yes global derived
no no yes no per-context derived
no no yes yes per-context derived
no yes no no remapped
no yes no yes remapped
no yes yes no remapped
no yes yes yes remapped
yes no no no base metric
yes no no yes base metric
yes no yes no base metric
yes no yes yes base metric
yes yes - - cannot happen; for any name there can be at most one of a base metric or a remapped metric

When masking happens, it is done silently. Most PCP applications support -Dderive on the command line and this pmdbg(1) debug option will report derived metric operations (including masking) on stderr.

CAVEATS

Derived metrics are not available when using pmFetchArchive(3) as this routine does not use a target list of PMIDs that could be remapped (as is done for pmFetch(3)).

DIAGNOSTICS

On success, pmRegisterDerived returns NULL.

If a syntactic error is found at the time of registration, the value returned by pmRegisterDerived is a pointer into expr indicating where the error was found. To identify what the error was, the application should call pmDerivedErrStr(3) to retrieve the corresponding parser error message.

pmRegisterDerivedMetric returns 0 and errmsg is undefined if the parsing is successful.

If the given expr does not conform to the required syntax pmRegisterDerivedMetric returns -1 and a dynamically allocated error message string in errmsg. The error message is terminated with a newline and includes both the input name and expr, along with an indicator of the position at which the error was detected. e.g.

Error: pmRegisterDerivedMetric("my.disk.rates", ...) syntax error
4rat(disk.dev.read)
^

The position indicator line may be followed by an additional diagnostic line describing the nature of the error, when available.

In the case of an error, the pmRegisterDerivedMetric caller is responsible for calling free(3) to release the space allocated for errmsg.
