PMFETCH(3) Manual de funciones de biblioteca PMFETCH(3)

NOMBRE

pmFetch - obtener valores de métricas de rendimiento

C SINTAXIS

#include <pcp/pmapi.h>

int pmFetch(int numpmid,
pmID *pmidlist, pmResult **result);

cc ... -lpcp

DESCRIPCIÓN

Dada una lista de Identificadores de Métricas de Rendimiento (PMID)s, p. ej., como los construidos por pmLookupName(3), a través de pmidlist y numpmid, obtener los valores para estas métricas de rendimiento.

Una llamada a pmFetch se ejecuta en el contexto de una fuente de métricas, un perfil de instancia y un tiempo de recolección, previamente establecidos por llamadas a las funciones de contexto y perfil apropiadas, es decir, algunas de pmNewContext(3), pmDupContext(3), pmUseContext(3), pmAddProfile(3), pmDelProfile(3) y pmSetMode(3).

El resultado principal de pmFetch se devuelve en el argumento result como un árbol, utilizando las siguientes estructuras de datos de componentes;

typedef struct {
      unsigned int vtype : 8;        /* tipo de valor (igual que pmDesc.type) */
      unsigned int vlen : 24;        /* bytes para vtype/vlen + vbuf */
      char         vbuf[1];          /* uno o más valores */
} pmValueBlock;
typedef struct {
      int      inst;                 /* identificador de instancia */
      union {
            pmValueBlock *pval;      /* puntero al bloque de valor */
            int          lval;       /* valor entero in situ */
      } value;
} pmValue;
typedef struct {
      pmID      pmid;                /* identificador de métrica */
      int       numval;              /* número de valores o código de error */
      int       valfmt;              /* formato del valor, in situ o puntero */
      pmValue   vlist[1];            /* conjunto de instancias/valores */
} pmValueSet;
/* Resultado devuelto por pmFetch() */
typedef struct {
      struct timespec timestamp;     /* marca de tiempo del colector */
      int            numpmid;        /* número de PMIDs */
      pmValueSet     *vset[1];       /* conjunto de conjuntos de valores */
} pmResult;

Para acomodar métricas con múltiples instancias de valor, el campo numval indica cuántos valores se devuelven para cada PMID solicitado. El campo valfmt en la estructura pmValueSet indica si los valores para esta métrica se almacenan in situ en el campo lval, es decir, una cantidad entera de 32 bits (entero, sin signo, largo o sin signo largo) o si los valores se mantienen en estructuras pmValueBlock asociadas. La estructura pmValueBlock siempre se utiliza para valores de punto flotante (float o double) y también acomoda datos binarios de tamaño arbitrario como métricas de "valor de cadena" y métricas con tipos de datos agregados o complejos. La longitud máxima de un búfer pmValueBlock es de PM_VAL_VLEN_MAX bytes. Si se utiliza el formato pmValueBlock, el campo vtype indica el tipo de dato del valor. Este campo tiene la misma interpretación que el campo type en la estructura pmDesc, ver pmLookupDesc(3).

Tenga en cuenta que el valor in situ puede ser un entero de 32 bits con signo o sin signo, un valor largo de 32 bits con signo o sin signo (en plataformas de 32 bits). En los casos especiales descritos a continuación, también puede ser un valor de punto flotante de 32 bits. Si la aplicación necesita conocer el tipo de un valor in situ, lo cual es casi siempre el caso, es necesario obtener el descriptor de la métrica e interpretar el campo type, como se describe en detalle en pmLookupDesc(3). Cuando el pmResult se recibe de un pmcd de PCP1.x, los valores in situ también pueden ser valores de punto flotante de 32 bits (de tipo PM_TYPE_FLOAT). En todos los casos, es una buena práctica utilizar pmLookupDesc(3) para obtener el descriptor de la métrica e interpretar el campo type en él. Tenga en cuenta también que la PMAPI(3) traducirá automáticamente del formato PCP2.0 al formato PCP1.x cuando un cliente PCP1.x solicite valores de punto flotante de 32 bits de un pmcd de PCP2.0, pero la traducción inversa no ocurre (porque el pmcd de PCP2.0 no puede distinguir automáticamente entre valores de punto flotante arbitrarios de 32 bits y enteros de 32 bits).

Si un valor (es decir, asociado con una instancia particular) para una métrica solicitada no está "disponible" (en el momento solicitado), entonces no hay una estructura pmValue asociada en el result. Si no hay valores disponibles para una métrica, entonces numval será cero y la instancia pmValue[] asociada estará vacía (valfmt no está definido en estas circunstancias, sin embargo pmid se establecerá correctamente al PMID de la métrica sin valores).

Como extensión de este protocolo, si el Sistema de Recolección de Métricas de Rendimiento (PMCS) puede proporcionar una razón por la cual no hay valores disponibles para una métrica particular, esto se codifica como un código de error estándar en el numval correspondiente. Dado que los códigos de error son todos negativos, los valores para una métrica solicitada no están "disponibles" si numval es menor o igual a cero. El valor de una métrica de rendimiento puede no estar "disponible" por varias razones; la siguiente lista es ilustrativa pero no exhaustiva: del software para el Dominio de Métricas de Rendimiento asociado

+
La recolección no está activada actualmente en el software para el Dominio de Métricas de Rendimiento asociado
+
El PMID asociado no se conoce
+
La configuración actual del sistema no incluye el componente de hardware asociado y/o el módulo de software asociado, por ejemplo, un disco no está instalado o está fuera de línea, o Oracle no está instalado
+
La métrica es una para la cual se requiere un perfil de instancia, y no se proporcionó ninguno (hay un pequeño número de métricas en esta categoría, típicamente aquellas con dominios de instancia muy grandes y/o muy dinámicos, y/o métodos de instanciación de métricas costosos).
+
Si el contexto actual implica la obtención de métricas de un archivo, los valores pueden no estar disponibles en la región alrededor de un registro <mark> (ver pmlogextract(1)) que indiquen una discontinuidad temporal en la serie temporal de valores de métricas.

En general, es posible que no podamos diferenciar entre los diversos casos, y si la diferenciación no es posible, numval simplemente será cero.

La definición de argumento y las especificaciones de resultado se han construido para garantizar que para cada PMID en la pmidlist solicitada haya exactamente un pmValueSet en el result, y además los PMIDs aparecen exactamente en la misma secuencia tanto en pmidlist como en result. Esto hace que el número y el orden de las entradas en result sean completamente deterministas, y simplifica enormemente la lógica de programación de aplicaciones después de la llamada a pmFetch.

La estructura result devuelta por pmFetch se asigna dinámicamente utilizando una combinación de llamadas a malloc(3) y estrategias de asignación especializadas, y debe liberarse cuando ya no sea necesaria llamando a pmFreeResult(3). Bajo ninguna circunstancia se debe llamar a free(3) directamente para liberar este espacio.

Dado que las condiciones de error comunes se codifican en la estructura de datos result, esperaríamos que solo eventos catastróficos causaran que se devolviera un valor de error. Un ejemplo sería si la fuente de métricas fuera un host remoto, y ese host o el PMCS en ese host dejara de ser accesible. De lo contrario, el valor devuelto por la función pmFetch será no negativo.

Si el contexto actual implica la obtención de métricas de un Daemon Recolector de Métricas de Rendimiento (PMCD), entonces el valor de retorno puede utilizarse para codificar cambios fuera de banda en el estado del PMCD y los Agentes de Métricas de Rendimiento (PMDA) asociados, como un "or" a nivel de bits de los siguientes valores:

PMCD_RESTART_AGENT
Se ha intentado reiniciar al menos un PMDA fallido.
PMCD_ADD_AGENT
Al menos un PMDA se ha iniciado.
PMCD_DROP_AGENT
PMCD ha notado la terminación de al menos un PMDA.
PMCD_AGENT_CHANGE
Una macro de conveniencia para cualquiera de los tres cambios de PMDA.
PMCD_LABEL_CHANGE

NAME

pmFetch, pmFetchGroup — obtener los valores de métricas de rendimiento

C SYNOPSIS

#include <pcp/pmapi.h>

int pmFetch(pmContext *handle, int num_desc, pmDesc *desc, pmResult **result);
int pmFetchGroup(pmContext *handle, int num_desc, pmDesc *desc, pmFetchGroupCB callback, void *data);

DESCRIPTION

The pmFetch routine is the fundamental primitive for fetching performance metric values and instance identifiers from the Performance Co-Pilot (PCP) system. The context for the fetch is specified by handle, which is a pointer to a PCP context created by pmNewContext(3).

The metrics to be fetched are identified by an array of pmDesc structures, specified by desc, and the number of such structures is given by num_desc. Each pmDesc structure should contain a valid metric identifier (desc_metric) and possibly a set of instance identifiers (desc_instance). If desc_instance is PM_IN_ALL, all available instances of the metric will be fetched. If desc_instance is PM_IN_SPEC, then the specific instances identified by desc_instlist within the pmDesc structure will be fetched. If desc_instance is PM_IN_NODE, then the instance specified by desc_node will be fetched. If the metric does not support instances, then desc_instance should be PM_IN_NONE and desc_instance is ignored. The pmDesc structures are typically obtained via calls to pmLookupDesc(3) or pmLookupName(3).

The result argument is a pointer to a pointer to a pmResult structure. On successful completion, pmFetch will allocate and return a pointer to a populated pmResult structure via the result argument. The caller is responsible for freeing this structure using pmFreeResult(3).

The pmResult structure is defined as:

typedef struct {
    pm_uint_t       pm_serial;     /* serial number for the result */
    time_t          pm_time;       /* timestamp of the result */
    pm_int_t        pm_numpval;    /* number of values in pval */
    pm_value_t      *pm_pval;      /* array of values */
} pmResult;

The pm_serial field is a serial number that is incremented each time a new result is fetched. This can be used to detect if the underlying data source has changed between calls. The pm_time field is the time at which the result was fetched. The pm_numpval and pm_pval fields contain the actual performance metric values and their associated instance identifiers.

The pm_value_t structure is a union that holds the value of a performance metric. The type of the value is determined by the metric's data type, as specified in the pmDesc structure. The possible data types are:

PM_TYPE_INT32
32-bit signed integer
PM_TYPE_UINT32
32-bit unsigned integer
PM_TYPE_INT64
64-bit signed integer
PM_TYPE_UINT64
64-bit unsigned integer
PM_TYPE_FLOAT
Single-precision floating-point number
PM_TYPE_DOUBLE
Double-precision floating-point number
PM_TYPE_STRING
Null-terminated string
PM_TYPE_BINARY
Arbitrary binary data

The pm_value_t union provides access to these values through members such as int32, uint32, int64, uint64, f, d, str, and bin.

The pmResult structure returned by pmFetch contains an array of pm_value_t structures. Each element in this array corresponds to a requested metric-instance pair. The order of the values in the pm_pval array corresponds to the order of the metric-instance pairs in the desc array passed to pmFetch.

The pmFetchGroup routine provides a higher-level interface for fetching performance metrics. It accepts a callback function callback that is invoked for each fetched metric-instance pair. This allows the application to process metric values as they are received, without needing to manage the memory allocation and deallocation of the pmResult structure.

The callback function should have the following signature:

typedef int (*pmFetchGroupCB)(pm_uint_t pm_serial, time_t pm_time,
                              pm_int_t item, pm_value_t *pm_value, void *data);

Where:

pm_serial
The serial number of the result.
pm_time
The timestamp of the result.
item
The index of the metric-instance pair in the original desc array. This can be used to identify which metric-instance the current value corresponds to.
pm_value
A pointer to the pm_value_t structure containing the fetched value.
data
A pointer to the user-provided data passed to pmFetchGroup.

The callback function should return 0 on success, or a negative error code on failure. If the callback returns a negative error code, pmFetchGroup will terminate and return that error code.

The following status codes can be returned by pmFetch and pmFetchGroup:

PM_ERR_APPEND
PMCD has been informed of changes to global (context) labels, or new metrics have appeared which have associated labels.
PMCD_NAMES_CHANGE
PMCD has been informed that the namespace has been modified, such that new metrics have appeared or existing metrics have been removed.
PMCD_HOSTNAME_CHANGE
The hostname on the host where PMCD is running has changed. This may be the result of changes from temporary to permanent hostname after a system reboot or some subsequent explicit change to the system's hostname.

The default is to return zero to indicate no change in state, however the pmResult returned by pmFetch has the same interpretation independent of the return value being zero or greater than zero.

COMPATIBILITY

Prior to PCP 7.0 the timestamp field in the pmResult struct was a struct timeval. To support PMAPI transition, the old interface and semantics can be used if applications are recompiled with -DPMAPI_VERSION=2.

For a time in PCP 6.x there was a routine with the same semantics as the current pmFetch called pmFetchHighRes, and a struct with the same definition as the current pmResult struct called pmResultHighRes, although both are now deprecated and compile-time support for pmFetchHighRes (and the historically misnamed alias pmHighResFetch) and pmResultHighRes will be removed in a future release.

SEE ALSO

pmcd(1), pmAddProfile(3), PMAPI(3), pmDelProfile(3), pmDupContext(3), pmExtractValue(3), pmFetchArchive(3), pmFreeResult(3), pmGetInDom(3), pmLookupDesc(3), pmLookupLabels(3), pmLookupName(3), pmNewContext(3), pmSetMode(3), pmUseContext(3) and pmWhichContext(3).

Note that pmFetch is the most primitive method for fetching metric values from the PMCS. See the pmFetchGroup(3) API for a higher level method that insulates the user from the intricacies of looking up metric names and metadata, setting up instance profiles, pmResult traversal, conversions, and scaling.

DIAGNOSTICS

As mentioned above, pmFetch return error codes insitu in the argument result. If no result is returned, e.g. due to IPC failure using the current PMAPI context, or end of file on an archive, then these routines will return a negative error code which may be examined using pmErrStr(3).

PM_ERR_EOL
When fetching records from an archive, pmFetch returns this error code to indicate the end of the archive has been passed (or the start of the archive has been passed, if the direction of traversal is backwards in time). If the ``mode'' for the current PMAPI context (see pmSetMode(3)) is PM_MODE_INTERP then the time origin is advanced, even when this error code is returned. In this way applications that position the time outside the range defined by the records in the archive, and then commence to pmFetch will eventually see valid results once the time origin moves inside the temporal span of the archive.
-EAGAIN
If the current context involves fetching metrics from pmcd, then a return value of -EAGAIN indicates the caller has created too many contexts.

ENVIRONMENT

Many of the performance metrics exported from PCP agents have the semantics of counter meaning they are expected to be monotonically increasing. Under some circumstances, one value of these metrics may be smaller than the previously fetched value. This can happen when a counter of finite precision overflows, or when the PCP agent has been reset or restarted, or when the PCP agent is exporting values from some underlying instrumentation that is subject to some asynchronous discontinuity.

The environment variable PCP_COUNTER_WRAP may be set to indicate that all such cases of a decreasing ``counter'' should be treated as a counter overflow, and hence the values are assumed to have wrapped once in the interval between consecutive samples. This ``wrapping'' behavior was the default in earlier PCP versions, but by default has been disabled in PCP version 1.3 and later.
