PMLOGREWRITE(1) General Commands Manual PMLOGREWRITE(1)

NOMBRE

pmlogrewrite - reescribe archivos Performance Co-Pilot

SINOPSIS

pmlogrewrite [-Cdiqsvw?] [-c config] [-D debug] [-V version] inlog [outlog]

DESCRIPCIÓN

pmlogrewrite lee un conjunto de archivos PCP (Performance Co-Pilot) identificados por inlog y crea un archivo PCP en outlog. En uso normal, se utilizará la opción -c para designar un archivo o archivos de configuración que contengan las especificaciones (ver la sección SINTAXIS DE LAS REGLAS DE REESCRITURA a continuación) que describen cómo se deben transformar los datos y metadatos de inlog para producir outlog.

Los usos típicos para pmlogrewrite serían acomodar la evolución de los Agentes de Dominio de Métricas de Rendimiento (PMDA), donde los nombres, metadatos y semántica de las métricas y sus dominios de instancia asociados pueden cambiar con el tiempo, por ejemplo, promocionar el tipo de una métrica de un entero de 32 bits a uno de 64 bits, o renombrar un grupo de métricas. Consulte la sección EJEMPLOS para ver algunos casos de uso adicionales.

pmlogrewrite también puede usarse para expurgar información sensible de los archivos PCP en situaciones donde los archivos deben ser enviados a otra organización o para cumplir con políticas de privacidad o requisitos legislativos. Consulte pmlogredact(1) para un ejemplo de uso de pmlogrewrite en este contexto.

pmlogrewrite es más útil cuando los cambios en PMDA, o errores en el entorno de producción, resultan en archivos que no pueden combinarse con pmlogextract(1). Al preprocesar los archivos con pmlogrewrite, los archivos resultantes podrán fusionarse con pmlogextract(1).

El archivo de entrada inlog debe ser un conjunto de archivos PCP creados por pmlogger(1), o posiblemente una de las herramientas que leen y crean archivos PCP, por ejemplo, pmlogextract(1) y pmlogreduce(1). inlog es una lista separada por comas de nombres, cada uno de los cuales puede ser el nombre base de un archivo o el nombre de un directorio que contiene uno o más archivos.

Si no se especifica la opción -c, el comportamiento por defecto simplemente crea outlog como una copia de inlog. Esto es un poco más complicado que cat(1), ya que cada archivo PCP está formado por varios archivos físicos.

Si bien pmlogrewrite puede usarse para reparar algunos problemas de consistencia de datos en archivos PCP, también existe una clase de tareas de reparación que no pueden ser manejadas por pmlogrewrite y pmloglabel(1) puede ser una herramienta útil en estos casos.

OPCIONES

Las opciones de línea de comandos disponibles son:

-c config, --config=config
Si config es un archivo o enlace simbólico, lee y analiza las reglas de reescritura desde allí. Si config es un directorio, entonces todos los archivos o enlaces simbólicos en ese directorio (excluyendo aquellos que comienzan con un punto ``.'') se utilizarán para proporcionar las reglas de reescritura. Se permiten múltiples opciones -c.
-C, --check
Analiza las reglas de reescritura y sale. No se crea outlog, por lo que este argumento de línea de comandos es opcional con -C. Cuando se especifica -C, también se establecen -v y -w para que todas las advertencias y mensajes detallados se muestren mientras se analiza config.
-d, --desperate
Modo desesperado. Normalmente, si ocurre un error fatal, se elimina todo rastro del archivo PCP outlog parcialmente escrito. Con la opción -d, el archivo outlog parcialmente creado no se elimina.
-i
En lugar de crear outlog, inlog se reescribe en su lugar cuando se utiliza la opción -i. Se crea un nuevo archivo utilizando nombres de archivo temporales y luego se renombra a inlog de tal manera que, si se encuentran errores (no advertencias), inlog permanece inalterado.
-q, --quick
Modo rápido, donde si no hay acciones de reescritura que realizar (ninguno de los datos globales, dominios de instancia o métricas de inlog será cambiado), pmlogrewrite saldrá (con estado 0, éxito) inmediatamente después de analizar el(los) archivo(s) de configuración y no se creará outlog.
-s, --scale
Cuando las ``unidades'' de una métrica se cambian, si la dimensión en términos de espacio, tiempo y recuento no se altera, entonces el factor de escala está cambiando, por ejemplo, BYTE a KBYTE, o MSEC-1 a USEC-1, o el compuesto MBYTE.SEC-1 a KBYTE.USEC-1. La motivación puede ser (a) que los metadatos originales eran incorrectos pero los valores en inlog son correctos, o (b) los metadatos están cambiando, por lo que los valores también necesitan cambiar. El comportamiento por defecto de pmlogrewrite coincide con el caso (a). Si aplica el caso (b), use la opción -s y los valores de todas las métricas con un cambio de factor de escala en cada resultado serán reescalados. Para un control más fino sobre el reescalado de valores, consulte la opción RESCALE para la cláusula UNITS de la regla de reescritura de métricas descrita abajo.
-v, --verbose
Habilita el modo detallado.
-V version, --version=version
Especifica la versión del archivo PCP de salida que se está produciendo. Actualmente se admiten las versiones 2 y 3 del formato de archivo. La versión de inlog debe ser al menos version (por lo que se permite la actualización de versión, pero no la degradación). Por defecto, en ausencia de la opción -V, la versión de outlog es la misma que la versión de inlog.
-w, --warnings
Emite advertencias. Normalmente pmlogrewrite permanece en silencio para cualquier advertencia que no sea fatal y se espera que para un archivo particular, algunas (o de hecho, todas) las especificaciones de reescritura puedan no aplicarse. Por ejemplo, los cambios en un PMDA pueden ser capturados en un conjunto de reglas de reescritura, pero un solo archivo puede no contener todas las métricas modificadas ni todos los dominios de instancia y/o instancias modificados. Dado que estos casos se esperan, no impiden que pmlogrewrite se ejecute, y las reglas que no se aplican a inlog son ignoradas silenciosamente por defecto. De manera similar, algunas reglas de reescritura pueden no implicar ningún cambio porque los metadatos en inlog ya coinciden con la intención de la regla de reescritura para corregir datos de una versión anterior de un PMDA. La bandera -w fuerza la emisión de advertencias para todos estos casos.
-?, --help
Muestra el mensaje de uso y sale.

El argumento outlog es requerido en todos los casos, excepto cuando se especifica -i.

SINTAXIS DE LAS REGLAS DE REESCRITURA

Un archivo de configuración contiene cero o más reglas de reescritura según se define a continuación.

Las palabras clave y los caracteres de puntuación especiales se muestran a continuación en fuente de **_tipo de letra_** y no distinguen entre mayúsculas y minúsculas, por lo que METRIC, metric y Metric son equivalentes en las reglas de reescritura.

El carácter ``#'' introduce un comentario y el resto de la línea se ignora. De lo contrario, la entrada tiene un formato relativamente libre con espacio en blanco opcional (espacios, tabulaciones o nuevas líneas) entre los elementos léxicos de las reglas.

Una regla de reescritura global tiene la forma:

GLOBAL { globalspec ... }

donde globalspec es cero o más de las siguientes cláusulas:

HOSTNAME -> hostname

Modifica los registros de etiquetas en el archivo PCP de outlog, de modo que las métricas parezcan haber sido recolectadas del host hostname.

TIME -> delta

Tanto los valores de las métricas como los metadatos del dominio de instancia en un archivo PCP llevan marcas de tiempo. Esta cláusula fuerza que todas las marcas de tiempo se ajusten por delta, donde delta es un signo opcional ``+'' (th

e predeterminado) o `-'`, un número opcional de horas seguido de dos puntos `':'`, un número opcional de minutos seguido de dos puntos `':'`, un número de segundos, una fracción opcional de segundos seguida de un punto `'.'`. El ejemplo más simple sería `30` para aumentar las marcas de tiempo en 30 segundos. Un ejemplo más complejo sería `-23:59:59.999` para retroceder las marcas de tiempo un milisegundo menos que un día.

TIMEZONE -> "zona horaria"
TZ -> "zona horaria"

Modifica los registros de etiquetas en el archivo PCP outlog, de modo que las métricas parezcan haber sido recopiladas de un host con una zona horaria local de zona horaria. zona horaria debe estar entre comillas dobles y debe cumplir con las reglas de sintaxis de zona horaria válidas para la plataforma local, generalmente un formato Posix TZ, por ejemplo, AEST-10. Consulte tzset(3) para obtener más información.

TZ es un alias para TIMEZONE.

ZONEINFO -> "información de zona"

Modifica los registros de etiquetas en el archivo PCP outlog, de modo que las métricas parezcan haber sido recopiladas de un host con una zona horaria local de información de zona. información de zona debe estar entre comillas dobles y debe cumplir con las reglas de sintaxis de zona horaria de información de zona válidas para la plataforma local, generalmente dos puntos seguidos de una ruta de acceso debajo de /usr/share/zoneinfo, por ejemplo, :Africa/Timbuktu. Consulte tzset(3) para obtener más información.

La cláusula zoneinfo solo se permite si la versión del archivo de salida es al menos 3.

FEATURES -> bits de características

Modifica los registros de etiquetas en el archivo PCP outlog, de modo que las métricas parezcan haber sido recopiladas de un sistema con un pmlogger(1) que admita las "características" definidas por el valor entero bits de características, que se forma mediante la operación "o" de las marcas de características deseadas, según se definen en LOGARCHIVE(5). Alternativamente, bits de características se puede especificar usando la "macro" BITS() que toma una lista de argumentos separados por comas de enteros (en el rango inclusivo de 0 a 31) y establece los bits correspondientes. Por ejemplo

features -> bits(31,7,1)

La cláusula features solo se permite si la versión del archivo de salida es al menos 3.

Una regla de reescritura indom modifica un dominio de instancia y tiene el siguiente formato:

INDOM dominio.serie { especificación de indom ... }

donde dominio y serie identifican uno o más dominios de instancia existentes de inlog - típicamente dominio sería un entero en el rango de 1 a 510 y serie sería un entero en el rango de 0 a 4194304.

Como caso especial, serie podría ser un asterisco `*` que significa que la regla se aplica a cada dominio de instancia con un número de dominio de dominio.

Si un dominio de instancia designado no está en inlog, la regla no tiene ningún efecto.

La especificación de indom son cero o más de las siguientes cláusulas:

INAME "nombreantiguo" -> "nombrenuevo"

La instancia identificada por el nombre de instancia externo nombreantiguo se renombra a nombrenuevo. Tanto nombreantiguo como nombrenuevo deben estar entre comillas dobles.

Como caso especial, el nuevo nombre puede ser la palabra clave DELETE (sin comillas dobles), y luego la instancia nombreantiguo se eliminará de outlog, lo que la eliminará de los metadatos del dominio de instancia y eliminará todos los valores de esta instancia para todas las métricas asociadas.

Si los nombres de instancia contienen espacios incrustados, se debe tener especial cuidado con la regla de nombres de instancia de PCP que trata la parte inicial no espacial del nombre de instancia como la porción única del nombre para fines de coincidencia y para garantizar la unicidad dentro de un dominio de instancia; consulte pmdaInstance(3) para una discusión de este problema.

Como ilustración, considere el dominio de instancia hipotético para una métrica que contiene 2 instancias con los siguientes nombres:

red
eek urk

Entonces, algunas posibles cláusulas INAME podrían ser:

"eek" -> "amarillo como una flor"
Aceptable, nombreantiguo "eek" coincide con la instancia "eek urk".
"red" -> "eek"
Error, nombrenuevo "eek" coincide con la instancia existente "eek urk".
"eek urk" -> "rojo de otro tono"
Error, nombrenuevo "rojo de otro tono" coincide con la instancia existente "rojo".

INAME REPLACE /patrón/ -> "reemplazo"

Cada nombre de instancia externo en el dominio de instancia se compara con la expresión regular patrón y, cuando se encuentra una coincidencia, el nombre se cambia según las partes del nombre que coinciden con patrón y la receta de reemplazo. patrón sigue la sintaxis de una Expresión Regular Extendida de Posix (ver regex(7)) y reemplazo sigue la sintaxis del comando s de sed(1), por lo que & y \1 a \9 se pueden usar para seleccionar todas o subcadenas del nombre de instancia que coinciden con patrón.

Tenga en cuenta que la coincidencia y reemplazo se realiza como máximo una vez por nombre de instancia externo, por lo que si hay secuencias repetidas del nombre que coinciden con patrón, solo la **primera** coincidirá y se aplicará el reemplazo.

patrón normalmente se encierra entre barras (/) o comillas dobles ("). Se puede usar una barra invertida (\) antes de cualquier metacaracter descrito en regex(3) para especificar un carácter literal, por ejemplo, \( o \[ o \+ ... Los delimitadores de encierro no se pueden escapar, por lo que para incrustar una barra literal, use comillas dobles como delimitador, o viceversa.

reemplazo normalmente se encierra entre comillas dobles (") o barras (/). Se puede usar una barra invertida (\) antes de & o \ para especificar estos caracteres literalmente. Los delimitadores de encierro no se pueden escapar, por lo que para incrustar una comilla doble, use barras como delimitador, o viceversa.

Si los nombres de instancia después del reemplazo contienen espacios incrustados, se debe tener especial cuidado con la regla de nombres de instancia de PCP que trata la parte inicial no espacial del nombre de instancia como la porción única del nombre para fines de coincidencia y para garantizar la unicidad dentro de un dominio de instancia. Consulte pmdaInstance(3) para una discusión de este problema.

Aquí hay algunos ejemplos:

{ iname replace /[a-z]*foo[a-z]*/ -> "FOO" }
reemplaza cualquier palabra que contenga "foo" por "FOO"
{ iname replace "([0-9]+) /.*/(.*)" -> "\1 \2" }
elimina una ruta de directorio, de modo que el nombre de instancia (para una de las métricas del PMDA proc) "2981799 /home/kenj/bin/foobar" se convertiría en "2981799 foobar", ocultando el directorio personal del usuario y, implícitamente, el nombre de inicio de sesión del usuario

INAME REDACT

Reemplaza cada nombre de instancia externo en el dominio de instancia por la cadena "inst [redactado]" donde inst es el identificador interno de instancia en formato ASCII.

INDOM -> nuevodominio.nuevaserie

Modifica los metadatos del dominio de instancia y de cada métrica asociada con el dominio de instancia. Como caso especial, nuevaserie podría ser un asterisco `*` que significa usar serie de la regla de reescritura indom, aunque esto es más útil cuando serie también es un asterisco. Por ejemplo:

indom 29.* { indom -> 109.* }
moverá todos los dominios de instancia del dominio 29 al dominio 109.

INDOM -> DUPLICATE nuevodominio.nuevaserie

Un caso especial de la cláusula INDOM anterior donde el dominio de instancia es una copia duplicada del dominio de instancia dominio.serie de la regla de reescritura indom, y luego se aplican todas las reglas de mapeo al dominio de instancia copiado nuevodominio.nuevaserie. Esto es útil cuando un PMDA se divide y el mismo dominio de instancia necesita ser replicado para el dominio dominio y el dominio nuevodominio. Por ejemplo, si las métricas foo.one y foo.two se definen sobre el dominio de instancia 12.34, y foo.two se mueve a otro PMDA usando el dominio 27, entonces se podrían usar las siguientes reglas de reescritura:

indom 12.34 { indom -> duplicate 27.34 }
metric foo.two { indom -> 27.34 pmid -> 27.*.* }

INST idantiguo -> idnuevo

La instancia identificada por el identificador interno de instancia idantiguo se renombra a idnuevo. Tanto idantiguo como idnuevo son enteros en el rango de 0 a 231-1.

Como caso especial, idnuevo puede ser la palabra clave DELETE y luego la instancia idantiguo se eliminará de outlog, lo que la eliminará de los metadatos del dominio de instancia y eliminará todos los valores de esta instancia para todas las métricas asociadas.

Una regla de reescritura metric tiene el siguiente formato:

METRIC idmetric* { especificaciónde metric* ... }

donde idmetric* identifica una o más métricas existentes de inlog utilizando un nombre de métrica o la codificación interna para el PMID de una métrica como dominio.clúster.ítem. En este último caso, típicamente dominio sería un entero en el rango de 1 a 510, clúster sería un entero en el rango de 0 a 4095, y ítem sería un entero en elEl rango de 0 a 1023.

Como casos especiales, *item* puede ser un asterisco ``*'', lo que significa que la regla se aplica a cada métrica con un número de dominio *domain* y un número de clúster *cluster*, o *cluster* puede ser un asterisco, lo que significa que la regla se aplica a cada métrica con un número de dominio *domain* y un número de ítem *item*, o tanto *cluster* como *item* pueden ser asteriscos, y la regla se aplica a cada métrica con un número de dominio *domain*.

Si una métrica designada no está en *inlog*, la regla no tiene efecto.

El *metricspec* es cero o más de las siguientes cláusulas:

DELETE

La métrica se elimina por completo de *outlog*, tanto los metadatos como todos los valores en los resultados se expurgan.

INDOM -> newdomain.newserial [ pick ]

Modifica los metadatos para cambiar el dominio de instancia para esta métrica. El nuevo dominio de instancia debe existir en *outlog*.

La cláusula opcional *pick* puede usarse para seleccionar un valor de entrada, o calcular un valor agregado de las instancias en un resultado de entrada, o asignar un identificador de instancia interno a un único valor de salida. Si no se especifica una cláusula *pick*, el comportamiento predeterminado es copiar todos los valores de entrada de cada resultado de entrada a un resultado de salida; sin embargo, si el dominio de instancia de entrada es singular (indom PM_INDOM_NULL), entonces el valor de salida único debe asignarse a un identificador de instancia interno, que es 0 por predeterminado, a menos que se anule con una cláusula INST o INAME según se define a continuación.

Las opciones para *pick* son las siguientes:

OUTPUT FIRST
elige el valor de la primera instancia de cada resultado de entrada
OUTPUT LAST
elige el valor de la última instancia de cada resultado de entrada
OUTPUT INST instid
elige el valor de la instancia con identificador de instancia interno *instid* de cada resultado; la secuencia de reglas de reescritura asegura que el procesamiento de OUTPUT ocurra antes de la renumeración de identificadores de instancia de cualquier regla indom asociada, por lo que *instid* debe ser uno de los identificadores de instancia internos que aparece en *inlog*
OUTPUT INAME "name"
elige el valor de la instancia con *name* como su nombre de instancia externo de cada resultado; la secuencia de reglas de reescritura asegura que el procesamiento de OUTPUT ocurra antes del cambio de nombre de instancia de cualquier regla indom asociada, por lo que *name* debe ser uno de los nombres de instancia externos que aparece en *inlog*
OUTPUT MIN
elige el valor más pequeño en cada resultado (el tipo de métrica debe ser numérico y la instancia de salida será 0 para un dominio de instancia no singular)
OUTPUT MAX
elige el valor más grande en cada resultado (el tipo de métrica debe ser numérico y la instancia de salida será 0 para un dominio de instancia no singular)
OUTPUT SUM
elige la suma de todos los valores en cada resultado (el tipo de métrica debe ser numérico y la instancia de salida será 0 para un dominio de instancia no singular)
OUTPUT AVG
elige el promedio de todos los valores en cada resultado (el tipo de métrica debe ser numérico y la instancia de salida será 0 para un dominio de instancia no singular)

Si el dominio de instancia de entrada es singular (indom PM_INDOM_NULL), entonces independientemente de cualquier especificación de *pick*, hay como máximo un valor en cada resultado de entrada y, por lo tanto, FIRST, LAST, MIN, MAX, SUM y AVG son equivalentes y el identificador de instancia de salida será 0.

En general, es un error especificar una acción de reescritura para los mismos metadatos o valores de resultado más de una vez, por ejemplo, más de una cláusula INDOM para el mismo dominio de instancia. La única excepción es la posible interacción entre las cláusulas INDOM en las reglas indom y metric. Por ejemplo, la métrica *sample.bin* se define sobre el dominio de instancia 29.2 en *inlog* y lo siguiente es aceptable (aunque redundante):

indom 29.* { indom -> 109.* }
metric sample.bin { indom -> 109.2 }
Sin embargo, lo siguiente es un error, porque el dominio de instancia para *sample.bin* tiene dos definiciones conflictivas: 
indom 29.* { indom -> 109.* }
metric sample.bin { indom -> 123.2 }

INDOM -> NULL[ pick ]

La métrica (que debe haber sido definida previamente sobre un dominio de instancia) se está modificando para ser una métrica singular. Esto implica un cambio de metadatos y la consolidación de todos los resultados de esta métrica para que múltiples valores se conviertan en un solo valor.

La parte opcional *pick* de la cláusula define cómo se debe calcular el único valor para cada resultado y sigue las mismas reglas descritas para el caso INDOM no NULL anterior.

En ausencia de *pick*, el valor predeterminado es OUTPUT FIRST.

NAME -> newname

Renombra la métrica en los metadatos del archivo PCP que soportan el Espacio de Nombres de Métricas de Rendimiento (PMNS). *newname* no debe coincidir con ningún nombre existente en el PMNS del archivo y debe seguir las reglas sintácticas para nombres de métricas válidos, tal como se describe en PMNS(5).

PMID -> newdomain.newcluster.newitem

Modifica los metadatos y resultados para renumerar el PMID de la métrica. Como casos especiales, *newcluster* puede ser un asterisco ``*'', lo que significa usar el *cluster* de la regla de reescritura metric y/o *item* puede ser un asterisco, lo que significa usar el *item* de la regla de reescritura metric. Esto es más útil cuando *cluster* y/o *item* también son asteriscos. Por ejemplo:

metric 30.*.* { pmid -> 123.*.* }
moverá todas las métricas del dominio 30 al dominio 123.

SEM -> newsem

Cambia la semántica de la métrica. *newsem* debe ser la parte XXX del nombre de una de las macros PM_SEM_XXX definidas en <pcp/pmapi.h> o pmLookupDesc(3), por ejemplo, COUNTER para PM_TYPE_COUNTER.

No se realiza ninguna reescritura de valores de datos como resultado de la cláusula SEM, por lo que su utilidad se limita a casos en los que una versión del PMDA asociado exportaba semánticas incorrectas para la métrica. pmlogreduce(1) puede proporcionar una alternativa en casos donde se desee la recompilación de valores de resultado.

TYPE -> newtype

Cambia el tipo de la métrica, lo que altera los metadatos y puede cambiar la codificación de los valores en los resultados. *newtype* debe ser la parte XXX del nombre de una de las macros PM_TYPE_XXX definidas en <pcp/pmapi.h> o pmLookupDesc(3), por ejemplo, FLOAT para PM_TYPE_FLOAT.

La conversión de tipos solo se admite para casos en los que el tipo de métrica anterior sea numérico, por lo que PM_TYPE_STRING, PM_TYPE_AGGREGATE, PM_TYPE_EVENT y PM_TYPE_HIGHRES_EVENT no están permitidos. Del mismo modo, el nuevo tipo de métrica debe ser numérico o PM_TYPE_STRING. Incluso en los casos numéricos, algunas conversiones pueden producir errores en tiempo de ejecución, por ejemplo, desbordamiento entero, o intentar reescribir un valor negativo en un tipo sin signo, o imprecisión, por ejemplo, al convertir un flotante o un doble a una cadena.

TYPE IF oldtype -> newtype

Lo mismo que la cláusula TYPE anterior, excepto que el tipo de la métrica solo se cambia a *newtype* si el tipo de la métrica en *inlog* es *oldtype*.

Esto es útil en casos en los que el tipo de *metricid* en *inlog* puede depender de la plataforma y, por lo tanto, se requiere más de una regla de reescritura de tipos.

UNITS -> newunits [ RESCALE ]

*newunits* son seis valores separados por comas. Los primeros 3 valores describen la dimensión de la métrica en las dimensiones de espacio, tiempo y conteo; estos son valores enteros, generalmente 0, 1 o -1. Los 3 valores restantes describen la escala de los valores de la métrica en las dimensiones de espacio, tiempo y conteo. Los valores de escala de espacio deben ser 0 (si la dimensión de espacio es 0), de lo contrario, la parte XXX del nombre de una de las macros PM_SPACE_XXX, por ejemplo, KBYTE para PM_TYPE_KBYTE. Los valores de escala de tiempo deben ser 0 (si la dimensión de tiempo es 0), de lo contrario, la parte XXX del nombre de una de las macros PM_TIME_XXX, por ejemplo, SEC para PM_TIME_SEC. Los valores de escala de conteo deben ser 0 (si la dimensión de tiempo es 0), de lo contrario, ONE para PM_COUNT_ONE.

Las macros PM_SPACE_XXX, PM_TIME_XXX y PM_COUNT_XXX se definen en <pcp/pmapi.h> o pmLookupDesc(3).

Cuando se cambia la escala (pero la dimensión no se altera), la palabra clave opcional RESCALE se puede usar para elegir el redimensionamiento de valores según la opción de línea de comandos **-s**, pero aplicado solo a esta métrica.

VALUE REPLACE /pattern/ -> "replacement"

El valor de cada instancia de la métrica se compara con la expresión regular *pattern* y cuando se encuentra una coincidencia, el valor se cambia según las partes del valor que coinciden con *pattern* y la receta de *replacement*. *pattern* sigue la sintaxis de una Expresión Regular Extendida de Posix (ver regex(7)) y *replacement* sigue la sintaxis del comando **s** de sed(1), por lo que **&** y **\1** a **\9** se pueden usar para seleccionar todas o subcadenas del valor que coinciden con *pattern*.

Tenga en cuenta que el

la coincidencia y reemplazo se realiza como máximo una vez por métrica valor, por lo que si hay secuencias repetidas del valor métrico que coinciden patrón solo el primero coincidirá y se aplicará reemplazo.

patrón normalmente se encierra entre barras (/) o comillas dobles ("). Se puede usar una barra invertida (\) antes de cualquiera de los metacaracteres descritos en regex(3) para especificar un carácter literal, por ejemplo \( o \[ o \+ ... Los delimitadores de cierre no se pueden escapar, por lo que para incrustar una barra literal, use comillas dobles como delimitador, o viceversa.

reemplazo normalmente se encierra entre comillas dobles (") o barras (/). Se puede usar una barra invertida (\) antes de & o \ para especificar estos caracteres literalmente. Los delimitadores de cierre no se pueden escapar, por lo que para incrustar una comilla doble, use barras como delimitador, o viceversa.

La palabra clave REPLACE es opcional.

Esta cláusula solo se puede aplicar a métricas con valores de tipo PM_TYPE_STRING.

Aquí hay algunos ejemplos:

{ value /.*/ -> "" }
elimina el valor en todas partes
value "/.*/(.*)" -> "\1" }
elimina una ruta de directorio, de modo que el valor métrico "mumble /home/kenj/bin/foobar fumble" se convertiría en "mumble foobar fumble", ocultando el directorio de inicio del usuario e implícitamente el nombre de inicio de sesión del usuario

Reglas de reescritura de texto

Al cambiar el número de dominio para una métrica o dominio de instancia, el nuevo número de dominio generalmente coincidirá con el número de dominio de un PMDA existente. Si este no es el caso, el nuevo número de dominio no debe elegirse al azar; consulte $PCP_VAR_DIR/pmns/stdpmid para los números de dominio que ya están asignados a los PMDA.

Reglas de reescritura de texto

Una regla de reescritura text modifica un registro de texto de ayuda y tiene la forma:

TEXT textid [ texttype ] [ "textcontent" ] { textspec ... }

donde textid identifica la métrica o el dominio de instancia con el que está asociado actualmente el texto, y es METRIC metricid o INDOM domain.serial.

metricid tiene la misma forma y significado que para una regla de reescritura METRIC (ver arriba) y domain.serial tiene la misma forma y significado que para una regla de reescritura INDOM (ver arriba).

El texttype opcional identifica el tipo de texto y puede ser ONELINE para seleccionar el texto de ayuda de una línea, HELP para seleccionar el texto de ayuda completo, o ALL o un asterisco ``*'' para seleccionar ambos tipos de texto de ayuda. Si no se especifica texttype, el valor predeterminado es ONELINE.

El textcontent opcional restringe aún más los registros de texto seleccionados a aquellos que contienen el contenido especificado. Los caracteres como las comillas dobles se pueden escapar precediéndolos con una barra invertida ``\ ''.

Si un registro de texto de ayuda designado no está en inlog, la regla no tiene ningún efecto.

El textspec son cero o más de las siguientes cláusulas:

DELETE

El texto seleccionado se elimina completamente de outlog.

INDOM -> newdomain.newserial

Reasocia el texto con el dominio de instancia especificado. Como caso especial, newserial podría ser un asterisco ``*'' lo que significa usar serial de la regla de reescritura text, aunque esto es más útil cuando serial también es un asterisco. Entonces, por ejemplo:

text indom 29.* all { indom -> 109.* }
reasociará todo el texto asociado con dominios de instancia del dominio 29 al dominio 109.

METRIC -> newdomain.newcluster.newitem

Reasocia el texto con la métrica especificada. Como casos especiales, newcluster podría ser un asterisco ``*'' lo que significa usar cluster de la regla de reescritura text y/o item podría ser un asterisco lo que significa usar item de la regla de reescritura text. Esto es más útil cuando cluster y/o item también son asteriscos. Entonces, por ejemplo:

text metric 30.*.* all { metric -> 123.*.* }
reasociará todo el texto asociado con métricas del dominio 30 al dominio 123.

TEXT -> "new-text"

Reemplaza el contenido del texto seleccionado con new-text.

Reglas de reescritura de etiquetas

Una regla de reescritura label modifica un registro de etiqueta y tiene la forma:

LABEL labelid [ instance ] [ "label-name" ] [ "label-value" ] { labelspec ... }

donde labelid se refiere al contexto global o identifica el dominio métrico, clúster métrico, ítem métrico, dominio de instancia o instancias de dominio de instancia con las que está asociado actualmente la etiqueta, y es CONTEXT o DOMAIN domainid o CLUSTER domainid.clusterid o ITEM metricid o INDOM domain.serial o INSTANCES domain.serial.

metricid tiene la misma forma y significado que para una regla de reescritura METRIC (ver arriba). clusterid puede ser un asterisco ``*'' lo que significa que la regla se aplica a cada métrica con un número de dominio de domainid de la misma manera que un asterisco puede usarse para el clúster dentro de metricid.

domain.serial tiene la misma forma y significado que para una regla de reescritura INDOM (ver arriba).

En el caso de un labelid INSTANCES, el nombre o número de una instancia específica puede especificarse opcionalmente como instance. Este nombre o número puede omitirse o especificarse como un asterisco ``*'' para indicar que se seleccionan etiquetas para todas las instancias del dominio de instancia especificado. Si se especifica un nombre de instancia, debe estar entre comillas dobles. Si el nombre de la instancia contiene espacios incrustados, se debe tener especial cuidado con respecto a la regla de nomenclatura de instancias de PCP que trata la parte inicial no espacial del nombre de la instancia como la porción única del nombre para los fines de coincidencia y para garantizar la unicidad dentro de un dominio de instancia, consulte pmdaInstance(3) para una discusión de este problema.

En todos los casos, se pueden especificar opcionalmente una "label-name" y/o un "label-value" entre comillas dobles para seleccionar etiquetas con el nombre dado y/o el valor dado. Estos pueden omitirse individualmente o especificarse como asteriscos ``*'' para indicar que se seleccionan etiquetas con todos los nombres y/o valores.

Si un registro de etiqueta designado no está en inlog, la regla no tiene ningún efecto.

El labelspec son cero o más de las siguientes cláusulas:

DELETE

Las etiquetas seleccionadas se eliminan completamente de outlog.

NEW "new-label-name" "new-label-value"

Se crea una nueva etiqueta con el nombre "new-label-name" y el valor "new-label-value" y se asocia con el labelid especificado y el instance opcional (en el caso de un labelid INSTANCES). Si se especificaron "label-name" o "label-value", se ignoran con una advertencia. Si no se especifica instance para un labelid INSTANCES, se creará una nueva etiqueta para cada instancia en el dominio de instancia especificado.

LABEL -> "new-label-name"

El nombre de la(s) etiqueta(s) seleccionada(s) se cambia a "new-label-name".

VALUE -> "new-label-value"

El valor de la(s) etiqueta(s) seleccionada(s) se cambia a "new-label-value".

DOMAIN -> newdomain

Reasocia la(s) etiqueta(s) seleccionada(s) con el dominio métrico especificado. Por ejemplo:

label domain 30 { domain -> 123 }
reasociará todas las etiquetas asociadas con dominios del dominio 30 al dominio 123.

CLUSTER -> newdomain.newcluster

Reasocia la(s) etiqueta(s) seleccionada(s) con el clúster métrico especificado. Como caso especial, newcluster podría ser un asterisco ``*'' lo que significa usar cluster de la regla de reescritura label. Esto es más útil cuando cluster también es un asterisco. Entonces, por ejemplo:

label cluster 30.* { cluster -> 123.* }
reasociará todas las etiquetas asociadas con clústeres del dominio 30 al dominio 123.

ITEM -> newdomain.newcluster.newitem

Reasocia la(s) etiqueta(s) seleccionada(s) con el ítem métrico especificado. Como casos especiales, newcluster podría ser un asterisco ``*'' lo que significa usar cluster de la regla de reescritura label y/o item podría ser un asterisco lo que significa usar item de la regla de reescritura label. Esto es más útil cuando cluster y/o item también son asteriscos. Entonces, por ejemplo:

label item 30.*.* { item -> 123.*.* }
reasociará todas las etiquetas asociadas con métricas del dominio 30 al dominio 123.

INDOM -> newdomain.newserial

pmlogrewrite(1)

NAME

pmlogrewrite - rewrite Performance Co-Pilot (PCP) archives

SYNOPSIS

pmlogrewrite [-c config] [-D debug] [-e end] [-f] [-h] [-i inlog] [-l logend] [-m] [-o outlog] [-q] [-r] [-s size] [-t interval] [-V] [-Z]

DESCRIPTION

pmlogrewrite is a utility for rewriting Performance Co-Pilot (PCP) archives. This might be useful for several reasons:

  • To change the data type of metrics, e.g. from 32-bit to 64-bit integers.
  • To change the metric identifiers (PMIDs) for a set of metrics.
  • To change the instance domain identifiers (INDOMs) and instance names for a set of metrics.
  • To change the archive volume size.
  • To change the archive suffix.

The changes to be made are described in a set of rewriting rules, which are described below in the REWRITING RULES SYNTAX section.

By default, pmlogrewrite reads from the archive named $PCP_LOG_DIR/local/YYYYMMDD/archive and writes to $PCP_LOG_DIR/local/YYYYMMDD/archive. The default values for inlog and outlog can be overridden by the -i and -o options, or by specifying the archive suffixes in the rewriting rules.

The format of the rewriting rules is similar to the syntax for pmlogger(1) configuration files.

OPTIONS

-c config
Use the rewriting rules defined in the specified config file. If this option is not specified, then the rewriting rules are read from standard input.
-D debug
Enable various debugging messages, as described in the DEBUGGING OPTIONS section.
-e end
Stop processing after timestamp end. The default is to process the entire archive.
-f
Overwrite the output archive if it already exists.
-h
Print a usage summary and exit.
-i inlog
Read input from the archive named inlog. The default is to read from the archive named $PCP_LOG_DIR/local/YYYYMMDD/archive.
-l logend
The rewritten archive will be named logend. The default is to use the same name as the input archive.
-m
Create a new archive volume after each metric descriptor change. This is mainly useful when rewriting archives with a very large number of metric descriptors.
-o outlog
Write output to the archive named outlog. The default is to write to the archive named $PCP_LOG_DIR/local/YYYYMMDD/archive.
-q
Enable quick exit mode. If no rewriting rules are specified that affect the current record, and if the output archive already exists and is up-to-date, then the input archive is simply copied to the output archive without processing.
-r
Enable archive recalculation mode. This is similar to quick exit mode, but it will always process the entire archive, even if no rewriting rules are specified.
-s size
Set the maximum size of each archive volume to size bytes. The default is 1024 MB. This option overrides the archive volume size specified in the rewriting rules.
-t interval
Stop processing after timestamp interval. This is an alternative to the -e option, specifying the interval in seconds.
-V
Print version information and exit.
-Z
Handle timezone information correctly.

REWRITING RULES SYNTAX

The rewriting rules are specified in a configuration file, one rule per line. Comments start with a '#' character and extend to the end of the line.

The following types of rules are supported:

metric pmid [ selector ] { changes }
Specifies a set of rewriting rules for metrics matching the specified pmid. The pmid can be a single metric identifier, or a pattern using the wildcard characters '*' and '?'. The optional selector can be used to further restrict the matching of metrics. The changes are specified within curly braces { }. Supported changes are:
  • pmid -> newpmid: Change the metric identifier to newpmid.
  • type -> newtype: Change the data type to newtype. Supported types are UCHAR, SCHA, UCHAR, USHORT, SSHORT, UINT, SINT, ULONG, SLONG, ULLONG, SLLONG, FLOAT, DOUBLE, STRING, OPAQUE.
  • name -> newname: Change the metric name to newname.
  • unit -> newunit: Change the metric units.
  • indom -> newindom: Change the instance domain identifier to newindom.
  • label labelname -> newlabelvalue: Change the value of the specified label.
indom indom [ selector ] { changes }
Specifies a set of rewriting rules for instance domains matching the specified indom. The indom can be a single instance domain identifier, or a pattern using the wildcard characters '*' and '?'. The optional selector can be used to further restrict the matching of instance domains. The changes are specified within curly braces { }. Supported changes are:
  • indom -> newindom: Change the instance domain identifier to newindom.
  • iname old_iname -> new_iname: Change the instance name old_iname to new_iname.
  • newserial -> serial: Change the serial number for the instance domain. If serial is an asterisk "*", use the serial from the label rewriting rule.
instances indom -> newdomain.newserial
This is the same as INDOM except that it re-associates the selected label(s) with the instances of the specified instance domain.

As a special case, newserial could be an asterisk ``*'' which means use serial from the label rewriting rule, although this is most useful when serial is also an asterisk. So for example:

label indom 29.* { indom -> 109.* }
will re-associate all labels associated with instance domains from domain 29 to domain 109.

INSTANCES -> newdomain.newserial

This is the same as INDOM except that it re-associates the selected label(s) with the instances of the specified instance domain.

EXAMPLES

To promote the values of the per-disk IOPS metrics to 64-bit to allow aggregation over a long time period for capacity planning, or because the PMDA has changed to export 64-bit counters and we want to convert old archives so they can be processed alongside new archives.

metric disk.dev.read { type -> U64 }
metric disk.dev.write { type -> U64 }
metric disk.dev.total { type -> U64 }

The instances associated with the load average metric kernel.all.load could be renamed and renumbered by the rules below.

# for the Linux PMDA, the kernel.all.load metric is defined
# over instance domain 60.2
indom 60.2 {
    inst 1 -> 60 iname "1 minute" -> "60 second"
    inst 5 -> 300 iname "5 minute" -> "300 second"
    inst 15 -> 900 iname "15 minute" -> "900 second"
}

If we decide to split the ``proc'' metrics out of the Linux PMDA, this will involve changing the domain number for the PMID of these metrics and the associated instance domains. The rules below would rewrite an old archive to match the changes after the PMDA split.

# all Linux proc metrics are in 7 clusters
metric 60.8.* { pmid -> 123.*.* }
metric 60.9.* { pmid -> 123.*.* }
metric 60.13.* { pmid -> 123.*.* }
metric 60.24.* { pmid -> 123.*.* }
metric 60.31.* { pmid -> 123.*.* }
metric 60.32.* { pmid -> 123.*.* }
metric 60.51.* { pmid -> 123.*.* }
# only one instance domain for Linux proc metrics
indom 60.9 { indom -> 123.0 }

If the metric foo.count_em was exported as a native ``long'' then it could be a 32-bit integer on some platforms and a 64-bit integer on other platforms. Subsequent investigations show the value is in fact unsigned, so the following rules could be used.

metric foo.count_em {
    type if 32 -> U32
    type if 64 -> U64
}

DIAGNOSTICS

All error conditions detected by pmlogrewrite are reported on stderr with textual (if sometimes terse) explanation.

Should the input archive be corrupted (this can happen if the pmlogger instance writing the archive suddenly dies), then pmlogrewrite will detect and report the position of the corruption in the file, and any subsequent information from that archive will not be processed.

If the input archive contains no archive records then an ``empty archive'' warning is issued and no processing is performed.

If any error is detected, pmlogrewrite will exit with a non-zero status.

FILES

For each of the inlog and outlog archives, several physical files are used.

archive.meta
metadata (metric descriptions, instance domains, etc.) for the archive
archive.0
initial volume of metrics values (subsequent volumes have suffixes 1, 2, ...).
archive.index
temporal index to support rapid random access to the other files in the archive.

PCP ENVIRONMENT

Environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).

For environment variables affecting PCP tools, see pmGetOptions(3).

DEBUGGING OPTIONS

The -D or --debug option enables the output of additional diagnostics on stderr to help triage problems, although the information is sometimes cryptic and primarily intended to provide guidance for developers rather end-users. debug is a comma separated list of debugging options; use pmdbg(1) with the -l option to obtain a list of the available debugging options and their meaning.

Debugging options specific to pmlogrewrite are as follows:

Option Description
appl0 archive reads and writes for data and metadata volumes
appl1 metadata changes (metric descriptors, instance domains, help text, metric labels)
appl2 metric value (pmResult) changes
appl3 -q handling and explanation of required changes that are the reason for not taking a quick exit
appl4 config file parser diagnostics
appl5 Rregex(7) matching for metric value changes and instance name changes
appl6 lexical scanner called from config file parser
appl7 temporal index generation diagnostics
