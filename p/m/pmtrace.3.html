PMTRACE(3) Manual de funciones de biblioteca PMTRACE(3)

NOMBRE

pmtracebegin, pmtraceend, pmtraceabort, pmtracepoint, pmtraceobs, pmtracecounter, pmtracestate, pmtraceerrstr - servicios de instrumentación de rendimiento a nivel de aplicación

SINOPSIS C

#include <pcp/trace.h>

int pmtracebegin(const char *tag);
int pmtraceend(const char *tag);
int pmtraceabort(const char *tag);
int pmtracepoint(const char *tag);
int pmtraceobs(const char *tag, double value);
int pmtracecounter(const char *tag, double value);
char *pmtraceerrstr(int code);
int pmtracestate(int flags);

cc ... -lpcp_trace

SINOPSIS FORTRAN

character*(*) tag
integer code
integer flags
integer state
character*(*) estr
real*8 value

code = pmtracebegin(tag)
code = pmtraceend(tag)
code = pmtraceabort(tag)
code = pmtracepoint(tag)
code = pmtraceobs(tag, value)
code = pmtracecounter(tag, value)
pmtraceerrstr(code, estr)
state = pmtracestate(flags)

f77 ... -lpcp_trace or f90 ... -lpcp_trace

SINOPSIS JAVA

int trace.pmtracecounter(String tag, double value);
String trace.pmtraceerrstr(int code);
int trace.pmtracestate(int flags);

DESCRIPCIÓN

La biblioteca pcp_trace proporciona un mecanismo para identificar secciones de un programa como transacciones o eventos para ser utilizados por el Agente de Dominio de Métricas de Rendimiento de Traza (consulte pmdatrace(1) y PMDA(3)).

La monitorización de transacciones utilizando la infraestructura del Copiloto de Rendimiento (PCP) se inicia mediante una llamada a pmtracebegin. El tiempo se registrará desde el final de cada llamada a pmtracebegin hasta el inicio de la siguiente llamada a pmtraceend, donde se utiliza el mismo identificador tag en ambas llamadas. A partir de esto, no se producirá ninguna grabación visible hasta que se realice al menos una llamada a pmtraceend haciendo referencia a un tag utilizado previamente en una llamada a pmtracebegin.

Una transacción que está actualmente en curso puede cancelarse llamando a pmtraceabort. No se exportarán datos de transacción recopilados para esa transacción en particular, aunque los datos de transacciones exitosas anteriores y posteriores con ese nombre de tag aún se exportan. Esto es más útil cuando surge una condición de error durante el procesamiento de la transacción y esta no se completa.

El argumento tag para pmtracebegin, pmtraceend y pmtraceabort se utiliza para identificar de forma única cada transacción dentro de la biblioteca pcp_trace y más tarde por el PMDA de traza como los identificadores de dominio de instancia para las métricas de rendimiento de transacciones que exporta. Estas rutinas son más útiles cuando se usan alrededor de bloques de código que probablemente se ejecuten varias veces durante un período de tiempo relativamente largo (en un proceso demonio, por ejemplo).

pmtracebegin tiene dos roles distintos: en primer lugar, como iniciador de una nueva transacción, y en segundo lugar, como mecanismo para establecer una nueva hora de inicio. De manera similar, pmtraceend se utiliza para registrar un nuevo tag y su estado inicial con el PMDA de traza, o alternativamente para actualizar las estadísticas que el PMDA asocia actualmente con el tag dado.

Una segunda forma de instrumentación de programas se puede obtener de pmtracepoint. Esta es una forma más simple de monitorización, ya que solo exporta el número de veces que se ha pasado un punto particular en un programa. Esto difiere de la monitorización de transacciones ofrecida por pmtracebegin y pmtraceend, que exporta un recuento continuo de finalizaciones de transacciones exitosas, así como estadísticas sobre el intervalo de tiempo entre los puntos de inicio y fin de cada transacción. Esta función es más útil cuando los puntos de inicio y fin no están bien definidos. Ejemplos de esto serían cuando el código se bifurca de tal manera que una transacción no se puede identificar claramente, o cuando el procesamiento no sigue un modelo transaccional, o la instrumentación deseada se asemeja a tasas de eventos en lugar de tiempos de servicio de eventos.

Las funciones pmtraceobs y pmtracecounter tienen semánticas similares a pmtracepoint, pero también permiten pasar un valor numérico arbitrario al PMDA de traza. El valor más reciente para cada tag está entonces inmediatamente disponible desde el PMDA. La única diferencia entre pmtraceobs y pmtracecounter es que se asume que el valor exportado a través de pmtracecounter es un valor de contador monotónicamente creciente (por ejemplo, el número de bytes leídos de un socket), mientras que el valor exportado a través de pmtraceobs puede ser cualquier valor.

pmtracestate permite a la aplicación establecer flags de estado que son honrados por llamadas posteriores a las rutinas de la biblioteca pcp_trace. Actualmente existen dos tipos de flags: flags de depuración y el flag de protocolo asíncrono. Una sola llamada puede especificar un número de flags juntos, combinados usando una operación LÓGICA OR (bitwise), y anula la configuración de estado anterior.

Los flags de depuración para pmtracestate hacen que pcp_trace imprima mensajes de diagnóstico en el flujo de salida estándar en puntos de procesamiento importantes. El protocolo predeterminado utilizado entre el PMDA de traza y las aplicaciones cliente individuales de pcp_trace es un protocolo síncrono, que permite que las conexiones perdidas se restablezcan más tarde si esto fuera posible. También está disponible un protocolo asíncrono que no proporciona la capacidad de reconexión, pero que elimina gran parte de la sobrecarga inherente a la comunicación síncrona. Este comportamiento se puede alternar usando la llamada pmtracestate, pero debe llamarse antes que otras llamadas a la biblioteca. Esto difiere del comportamiento del estado de depuración, que puede modificarse en cualquier momento. pmtracestate devuelve el estado anterior (configuración previa a ser llamado).

La siguiente tabla describe cada uno de los flags de pmtracestate; se incluyen ejemplos del uso de estos flags en cada lenguaje compatible en las aplicaciones de demostración (consulte la sección ``ARCHIVOS'' a continuación).

Flags de estado Semántica
0 NONE PDUs síncronos y sin diagnósticos (predeterminado)
1 API Muestra el procesamiento justo debajo de la API (depuración)
2 COMMS Muestra actividad relacionada con la red (depuración)
4 PDU Muestra tráfico IPC app<->PMDA (depuración)
8 PDUBUF Muestra la gestión interna del búfer IPC (depuración)
16 NOAGENT Ninguna comunicación con el PMDA en absoluto (depuración)
32 ASYNC Utiliza el protocolo PDU asíncrono (control)

Si alguna de las funciones de la biblioteca pcp_trace devuelve un valor negativo, ha ocurrido un error. Esto se puede diagnosticar más a fondo utilizando la rutina pmtraceerrstr, que toma el valor de retorno negativo como su argumento code y, en la interfaz llamable en C, devuelve un puntero al mensaje de error asociado. Este puntero apunta a una tabla de errores estática y, por lo tanto, no debe pasarse a free(3). La interfaz llamable en Fortran tiene una sintaxis ligeramente diferente, que requiere que el array de caracteres de destino se pase como segundo argumento. La interfaz llamable en Java devuelve una cadena UTF-8, creada utilizando la rutina JNI (Java Native Interface) NewStringUTF.

NOTAS

La interfaz de la clase Java pcp_trace ha sido desarrollada y verificada utilizando la versión 1.1 de la especificación Java Native Interface (JNI).

ADVERTENCIA

Las aplicaciones que utilizan gethostbyname(3) deben tener precaución, ya que los campos estáticos en struct hostent pueden no conservarse en algunas llamadas de pcp_trace. En particular, pmtracebegin, pmtraceend, pmtracepoint, pmtracecounter y pmtraceobs pueden llamar internamente a gethostbyname(3).

DIAGNÓSTICO

Un valor de retorno negativo de una función de pcp_trace indica que ha ocurrido un error; en ese caso, el valor de retorno se puede pasar a pmtraceerrstr para obtener el mensaje de error asociado.

El éxito se indica con un valor de retorno de cero.

pmtracestate también devuelve un entero que representa las flags de estado que se establecieron antes de la llamada.

ENTORNO

Las rutinas de pcp_trace se comunican con el PMDA de trazado a través de una conexión de socket, que por defecto utiliza el número de puerto TCP/IP 4323. Esto se puede anular estableciendo PCP_TRACE_PORT a un número de puerto diferente cuando se inicia la aplicación. El host donde se ejecuta el PMDA de trazado es, por defecto, localhost, pero esto se puede cambiar utilizando PCP_TRACE_HOST. Al intentar conectarse a un PMDA de trazado remoto, después de que haya transcurrido un intervalo de tiempo especificado, el intento de conexión se abortará y se devolverá un estado de error. El intervalo de tiempo de espera por defecto es de 3 segundos y se puede modificar estableciendo PCP_TRACE_TIMEOUT en el entorno a un número real de segundos para el tiempo de espera deseado. Esto es más útil en casos donde el host remoto se encuentra al final de una red lenta, lo que requiere latencias más largas para establecer la conexión correctamente.

ENTORNO PCP

Las variables de entorno con el prefijo PCP_ se utilizan para parametrizar los nombres de archivo y directorio utilizados por PCP. En cada instalación, el archivo /etc/pcp.conf contiene los valores locales para estas variables. La variable $PCP_CONF se puede utilizar para especificar un archivo de configuración alternativo, como se describe en pcp.conf(5). Los valores de estas variables se pueden obtener programáticamente utilizando la función pmGetConfig(3).
