pmdaMain(3)

PMDAMAIN(3) Manual de Funciones de Librería PMDAMAIN(3)

NOMBRE

pmdaMain, pmdaGetContext, pmdaSetResultCallBack, pmdaSetCheckCallBack, pmdaSetDoneCallBack, pmdaSetEndContextCallBack - procesamiento genérico de PDU para un PMDA

#include <pcp/pmapi.h>

pmdaDoneCallBack callback);

pmdaResultCallBack callback);

void pmdaSetEndContextCallBack(pmdaInterface *dispatch,
pmdaEndContextCallBack callback);

int pmdaGetContext(void);

cc ... -lpcp_pmda -lpcp

DESCRIPCIÓN

Para Agentes de Dominio de Métricas de Rendimiento (PMDA(3)) que usan los protocolos PDU binarios para comunicarse con pmcd(1), la rutina pmdaMain proporciona una implementación genérica del bucle principal controlado por PDU.

dispatch describe cómo procesar cada PDU entrante. Es un vector de punteros a funciones, uno por tipo de PDU de solicitud, como se usa en la interfaz DSO para un PMDA, a saber:

/*
 * Definiciones de Interfaz para Métodos PMDA
 */
typedef struct {
    int domain;         /* establecer/devolver el ID del dominio de métricas de rendimiento aquí */
    struct {
        unsigned int    pmda_interface: 8; /* Versión de interfaz DSO del PMDA */
        unsigned int    pmapi_version : 8; /* Versión de PMAPI */
        unsigned int    flags : 16;        /* Banderas de características opcionales */
    } comm;             /* establecer/devolver información de comunicación y versión */
    int status;         /* devolver el estado de inicialización aquí */
    union {
        struct {                              /* PMDA_INTERFACE_2 o _3 */
            pmdaExt *ext;
            int (*profile)(pmProfile *, pmdaExt *);
            int (*fetch)(int, pmID *, pmResult **, pmdaExt *);
            int (*desc)(pmID, pmDesc *, pmdaExt *);
            int (*instance)(pmInDom, int, char *, pmInResult **, pmdaExt *);
            int (*text)(int, int, char **, pmdaExt *);
            int (*store)(pmResult *, pmdaExt *);
        } two, three;
        struct {                              /* PMDA_INTERFACE_4 o _5 */
            pmdaExt *ext;
            int     (*profile)(pmProfile *, pmdaExt *);
            int     (*fetch)(int, pmID *, pmResult **, pmdaExt *);
            int     (*desc)(pmID, pmDesc *, pmdaExt *);
            int     (*instance)(pmInDom, int, char *, pmInResult **, pmdaExt *);
            int     (*text)(int, int, char **, pmdaExt *);
            int     (*store)(pmResult *, pmdaExt *);
            int     (*pmid)(char *, pmID *, pmdaExt *);
            int     (*name)(pmID, char ***, pmdaExt *);
            int     (*children)(char *, int, char ***, int **, pmdaExt *);
        } four, five;
        struct {                              /* PMDA_INTERFACE_6 */
            pmdaExt *ext;
            int     (*profile)(pmProfile *, pmdaExt *);
            int     (*fetch)(int, pmID *, pmResult **, pmdaExt *);
            int     (*desc)(pmID, pmDesc *, pmdaExt *);
            int     (*instance)(pmInDom, int, char *, pmInResult **, pmdaExt *);
            int     (*text)(int, int, char **, pmdaExt *);
            int     (*store)(pmResult *, pmdaExt *);
            int     (*pmid)(char *, pmID *, pmdaExt *);
            int     (*name)(pmID, char ***, pmdaExt *);
            int     (*children)(char *, int, char ***, int **, pmdaExt *);
            int     (*attribute)(int, int, const char *, int, pmdaExt *);
        } six;
    } version;
} pmdaInterface;

Esta estructura ha sido extendida para incorporar las múltiples versiones de interfaz que han evolucionado con el tiempo. Para pmdaMain, dispatch->domain y dispatch->status se ignoran. El campo comm.pmda_interface se utiliza para determinar la interfaz utilizada por el PMDA. Establecer este campo en PMDA_INTERFACE_2 o PMDA_INTERFACE_3 forzará a pmdaMain a usar las devoluciones de llamada en la estructura version.two o version.three. Un ajuste de PMDA_INTERFACE_4 o PMDA_INTERFACE_5 forzará a pmdaMain a usar las devoluciones de llamada en la estructura version.four o version.five, y de manera similar, un ajuste de PMDA_INTERFACE_6 fuerza a pmdaMain a usar las devoluciones de llamada en la estructura version.six. Cualquier otro valor resultará en un error y terminación de pmdaMain.

Tenga en cuenta que el uso de dispatch como interfaz entre pmcd(1) y los métodos del PMDA permite que cada PMDA se implemente como si fuera un DSO, con pmdaMain proporcionando un envoltorio conveniente que puede usarse para convertir de la interfaz DSO a la interfaz PDU binaria (PMDA del demonio).

pmdaMain se ejecuta como un bucle continuo, retornando solo cuando se encuentra un fin de archivo en el descriptor de archivo de entrada PDU.

CALLBACKS

Además de las devoluciones de llamada individuales de procesamiento de PDU - pmdaProfile(3), pmdaFetch(3), pmdaDesc(3), pmdaInstance(3), pmdaText(3), pmdaStore(3), pmdaPMID(3), pmdaName(3), pmdaChildren(3), y pmdaAttribute(3), existen otras devoluciones de llamada que pueden afectar o informar sobre todo el procesamiento de PDU dentro de un PMDA, a saber check, done y end. Estas devoluciones de llamada deben configurarse con pmdaSetCheckCallBack, pmdaSetDoneCallBack y pmdaSetEndContextCallBack.

Si no es nulo, se llama a check después de recibir cada PDU (pero antes de procesarla), y se llama a done después de enviar cada PDU. Si check devuelve un valor menor que cero (típicamente PM_ERR_AGAIN), se omite el procesamiento de la PDU y, en la mayoría de los casos, el valor de la función se devuelve como una PDU de error a pmcd(1). Esto puede usarse para PMDAs que requieren algún tipo de protocolos de conexión o reconexión diferida para las fuentes subyacentes de métricas de rendimiento, por ejemplo, un DBMS. La indicación de error de check no se devuelve a pmcd(1) en los casos en que no se espera acuse de recibo, por ejemplo, para una PDU_PROFILE.

La devolución de llamada end permite a un PMDA realizar un seguimiento del estado para clientes individuales que le solicitan realizar acciones (procesamiento de PDU). Usando pmdaGetContext, un PMDA puede determinar, en cualquier momento, un identificador entero que identifica de forma única las herramientas cliente en el extremo remoto de PMCD (para modos de contexto local, este identificador es siempre cero). Esto se vuelve muy importante para manejar métricas de eventos, donde cada evento debe propagarse una sola vez a cada cliente interesado. También subyace al mecanismo mediante el cual la información de conexión se pasa al PMDA, como las credenciales (identificadores de usuario y grupo) para la herramienta cliente.

Se proporciona un último mecanismo de devolución de llamada para manejar el pmResult construido para una PDU_RESULT en respuesta a una solicitud PDU_FETCH. Por defecto, pmdaMain liberará el pmResult una vez que el resultado se haya enviado a pmcd(1). Para algunos PMDAs, esto es inapropiado, por ejemplo, el pmResult está asignado estáticamente o contiene una combinación de información de búfer PDU fijada e información asignada dinámicamente. pmdaSetResultCallBack se puede utilizar para definir una devolución de llamada alternativa desde pmdaMain.

DIAGNÓSTICOS

Estos mensajes pueden ser añadidos al archivo de registro del PMDA:

Versión de la interfaz PMDA interfaz no soportada
La versión interfaz no es soportada por pmdaMain.
Tipo de PDU no reconocido
El PMDA recibió una PDU de pmcd que no reconoce. Esto puede indicar que el proceso pmcd está usando una interfaz más avanzada que pmdaMain.

Si las opciones de control de depuración de PMAPI(3) tienen la opción ``libpmda'' activada, entonces cada PDU que se recibe se reporta en el archivo de registro del PMDA.
