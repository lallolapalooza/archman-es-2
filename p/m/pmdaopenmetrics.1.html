PMDAOPENMETRICS(1) Manual de Comandos Generales PMDAOPENMETRICS(1)

NOMBRE

pmdaopenmetrics - PMDA de OpenMetrics

SINOPSIS

$PCP_PMDAS_DIR/openmetrics/pmdaopenmetrics [-D] [-n] [-c config] [-d dominio] [-l archivo_log] [-R tiempo_espera_refresco] [-r raiz] [-t tiempo_espera] [-u usuario]

DESCRIPCIÓN

pmdaopenmetrics es un Agente de Dominio de Métricas de Rendimiento (PMDA) que crea dinámicamente métricas de PCP a partir de endpoints de OpenMetrics configurados, los cuales proporcionan acceso basado en HTTP a métricas de aplicaciones. El PMDA esencialmente implementa un puente entre Prometheus y PCP, permitiendo a PCP ingerir fácilmente datos de rendimiento de más de 650 endpoints registrados y muchos otros endpoints específicos de aplicaciones.

El directorio config por defecto es $PCP_PMDAS_DIR/openmetrics/config.d/, ver ``FUENTES DE CONFIGURACIÓN'' a continuación. El tiempo_espera por defecto para la obtención de URLs es de 2 segundos. El usuario por defecto, si no se especifica con la opción -u, es el usuario actual. Si se proporciona la opción -n, la lista de archivos de configuración no se ordenará antes de procesarla. Esta lista se ordena por defecto, pero eso puede ser costoso si hay un gran número de archivos de configuración (URLs y/o scripts).

Si se proporciona la opción -D, se escribirán mensajes de diagnóstico adicionales en el archivo de log del PMDA, que es $PCP_LOG_DIR/pmcd/openmetrics.log por defecto (ver también -l abajo). Además, la métrica openmetrics.control.debug controla la misma bandera de depuración y se puede establecer con el siguiente comando:

pmstore openmetrics.control.debug valor

donde valor es 1 (para habilitar mensajes de log detallados) o 0 (para deshabilitar mensajes de log detallados). Esto es particularmente útil para examinar las cabeceras http pasadas a cada solicitud de obtención, la configuración de filtros y otros detalles de procesamiento que se registran cuando la bandera de depuración está habilitada.

La opción -d puede usarse para anular el número de dominio de métricas de rendimiento por defecto, que es 144. Se recomienda encarecidamente no cambiarlo. El número de dominio debe ser diferente para cada PMDA en el mismo host, y el mismo número de dominio debe usarse para el PMDA pmdaopenmetrics en todos los hosts. Ver también la opción -r, que permite que la raíz del espacio de nombres dinámico se cambie de openmetrics por defecto.

La opción -l puede usarse para especificar archivo_log como destino de los mensajes del PMDA en lugar del valor por defecto, $PCP_LOG_DIR/pmcd/openmetrics.log. Como caso especial, archivo_log puede ser "-" para enviar mensajes al stream stderr en su lugar, por ejemplo -l-. Este sería normalmente el stream stderr del proceso padre, pmcd(1), que puede tener el stderr redirigido. Esta redirección es normalmente más útil en un entorno contenedorizado, o cuando se utiliza dbpmda(1).

La opción -r permite que la raíz del espacio de nombres dinámico se cambie a raiz desde el valor por defecto, openmetrics. En conjunción con otras opciones de línea de comandos, esto permite que pmdaopenmetrics se implemente como un PMDA diferente con un espacio de nombres de métricas y un dominio de métricas distintos en el mismo sistema host. Tenga en cuenta que todos los PMDA requieren un número de dominio único, por lo que la opción -d también debe especificarse. El uso de la opción -r también puede cambiar los valores por defecto para algunas otras opciones de línea de comandos, por ejemplo, el nombre del archivo de log por defecto y el directorio de configuración por defecto.

La opción -R permite al usuario configurar el tiempo_espera, en segundos, entre los refrescos del clúster. El valor por defecto es de 10 segundos.

FUENTES DE CONFIGURACIÓN

Mientras se ejecuta, pmdaopenmetrics escanea periódicamente de forma recursiva el directorio $PCP_PMDAS_DIR/openmetrics/config.d (o el directorio especificado con la opción -c), buscando archivos fuente de URL (*.url) y scripts o binarios ejecutables. Cualquier archivo que no tenga el sufijo .url o que no sea ejecutable, se ignora; esto permite que archivos de documentación como "README" y definiciones de funciones de script "comunes" no ejecutables estén presentes sin ser considerados como archivos de configuración.

Un servidor remoto no tiene por qué estar en funcionamiento o permanecer activo; el PMDA tolera URLs remotos que pueden aparecer y desaparecer con el tiempo. El PMDA retransmitirá datos y metadatos cuando/si están disponibles, y devolverá errores cuando/si están caídos. Los IDs de métricas de PCP, los identificadores de dominio de instancias internos y externos se persisten y se restaurarán cuando las fuentes de métricas individuales estén disponibles y/o cuando el PMDA se reinicie. Además, el PMDA comprueba las marcas de tiempo de modificación del directorio y volverá a escanear dinámicamente para buscar archivos de configuración nuevos o modificados. No es necesario reiniciar el PMDA al añadir, eliminar o modificar archivos de configuración.

FUENTES DE URL

Cada archivo con el sufijo .url encontrado en el directorio de configuración o subdirectorio contiene una URL HTTP o HTTPS completa en la que pmdaopenmetrics puede alcanzar un endpoint de OpenMetrics. El acceso a archivos locales también es compatible con una URL convencional file:///alguna_ruta/algun_archivo, en cuyo caso alguna_ruta/algun_archivo debería contener datos métricos formateados en OpenMetrics.

La primera línea de un archivo de configuración .url debe ser la URL, como se describe arriba. Las líneas subsiguientes, si las hay, comienzan con una palabra clave que se puede usar para modificar la solicitud GET http. Una palabra clave debe terminar con : (dos puntos) y el texto se extiende hasta el final de la línea. Las líneas de comentario que comienzan con # y las líneas en blanco se ignoran. Las únicas palabras clave actualmente soportadas son HEADER: y FILTER:.

HEADER: nombre_cabecera: valor ... hasta el final de la línea
Añade nombre_cabecera y su valor a las cabeceras pasadas en la solicitud GET http para la URL configurada. Un archivo de configuración de ejemplo que proporciona 3 cabeceras comúnmente usadas y un token de autenticación podría ser:


http://algunhost/ruta/endpoint.html
# esto es un comentario
HEADER: Accept: text/html
HEADER: Keep-Alive: 300
HEADER: Connection: keep-alive
HEADER: Authorization: token ABCDEF1234567890

Como se mencionó anteriormente, los valores de las cabeceras se extienden hasta el final de la línea. Pueden contener cualquier carácter válido, incluidos los dos puntos. Múltiples espacios se colapsarán en un solo espacio, y los espacios al principio y al final se eliminarán. Un uso común para las cabeceras es configurar un agente proxy y los parámetros variados que pueda requerir.

FILTRADO DE MÉTRICAS

El filtrado de métricas es una característica del archivo de configuración que permite incluir o excluir, es decir, filtrar, las métricas ingeridas. Esto es útil porque la mayoría de los endpoints devuelven múltiples métricas, y normalmente solo algunas son interesantes para fines de monitoreo. La sintaxis es:
FILTER: INCLUDE METRIC regex
o
FILTER: EXCLUDE METRIC regex
Los nombres de métricas creados dinámicamente que coincidan con regex serán incluidos o excluidos del espacio de nombres, según se especifique. Tenga en cuenta que solo el componente hoja del nombre de la métrica en el PMNS (tal como se ingiere de la fuente de la URL) se compara con el patrón regex. La regla simple es que el primer regex de filtro coincidente para un nombre de hoja de métrica particular es la regla que prevalece. Si ningún regex de filtro coincide (o no hay filtros), entonces la métrica se incluye por defecto, es decir, el filtro por defecto si no se especifica ninguno es FILTER: INCLUDE METRIC .* Esto es compatible con versiones anteriores del archivo de configuración que no admitían filtros. Normalmente se usarían múltiples líneas FILTER:, por ejemplo, para incluir algunas métricas pero excluir todas las demás, use FILTER: EXCLUDE METRIC .* como la última de varias filtros que incluyen las métricas deseadas. Por el contrario, para excluir algunas métricas pero incluir todas las demás, use FILTER: EXCLUDE METRIC regex. En este caso, no es necesario (aunque no hace daño) especificar el final FILTER: INCLUDE METRIC .* porque, como se indicó anteriormente, cualquier métrica que no coincida con ningún regex de filtro se incluirá por defecto.

El filtrado de etiquetas utiliza una sintaxis y semántica de FILTER: similar al filtrado de métricas. FILTER: EXCLUDE LABEL regex eliminará todas las etiquetas con el nombre de etiqueta

FILTRADO DE ETIQUETAS

El filtrado de etiquetas permite definir qué etiquetas se utilizan para construir nombres de instancia externos y qué etiquetas se incluyen en los conjuntos de etiquetas devueltos por las devoluciones de llamada de métricas.

Las reglas de filtro de etiquetas son similares a las reglas de filtro de métricas. Cada regla de filtro de etiquetas es una línea en el archivo de configuración que comienza con FILTRO: seguida de una palabra clave y un argumento opcional.

Las palabras clave admitidas son:

INCLUDE ETIQUETA expresión regular
Incluye todas las etiquetas cuyos nombres coinciden con la expresión regular proporcionada en los conjuntos de etiquetas devueltos. Las etiquetas incluidas también se utilizan para construir nombres de instancia externos.
EXCLUIR ETIQUETA expresión regular
Excluye todas las etiquetas cuyos nombres coinciden con la expresión regular proporcionada de los conjuntos de etiquetas devueltos y de la construcción de nombres de instancia externos.
ETIQUETA OPCIONAL expresión regular
Las etiquetas que coinciden con la expresión regular se incluyen en los conjuntos de etiquetas devueltos (es decir, se incluyen), pero **no** se utilizan como parte de los nombres de instancia externos.

Una regla implícita: FILTRO: INCLUIR ETIQUETA .* se aplica a todas las etiquetas que no coinciden con ninguna regla de filtro de etiquetas anterior.

Las etiquetas incluidas que no son opcionales (es decir, las etiquetas *intrínsecas*) se concatenarán y se utilizarán para la nomenclatura de instancias externas. Además, las etiquetas no intrínsecas (es decir, las etiquetas marcadas como **OPCIONAL**) tendrán el indicador **PM_LABEL_OPTIONAL** establecido en los conjuntos de etiquetas devueltos por las devoluciones de llamada de notas. Este indicador afecta a cómo se utilizan las etiquetas en ciertos clientes. Para obtener más detalles, consulte pmLookupLabels(3) y las páginas de manual relacionadas para más detalles. Tenga en cuenta que los nombres de instancia externos comienzan con el identificador numérico único de la instancia interna seguido de un espacio, por lo que los nombres de instancia externos son siempre únicos.

Se debe tener cuidado con el filtrado de etiquetas porque, por defecto, todas las etiquetas se utilizan para construir el nombre de la instancia de PCP. Al excluir algunas etiquetas (o cambiarlas a opcionales), los nombres de instancia cambiarán. Además, excluir todas las etiquetas de una métrica particular la convierte en singular, es decir, sin dominio de instancia. Al excluir algunas etiquetas, diferentes instancias devueltas por la URL o la entrada de configuración con script para la misma métrica pueden convertirse en duplicados. Cuando se producen duplicados de este tipo, la última instancia duplicada devuelta por el punto final de la URL o el script prevalece sobre las instancias anteriores. Por estas razones, se recomienda configurar las reglas de filtrado de etiquetas cuando se define por primera vez el archivo de configuración y no modificarlas posteriormente. Si se requiere un cambio en el filtrado de etiquetas, el archivo de configuración debe renombrarse, lo que efectivamente define una nueva métrica (o conjunto de métricas pares devueltas por la URL o script), con la nomenclatura de instancia nueva (o modificada).

Las palabras clave no reconocidas en los archivos de configuración se informan en el archivo de registro de PMDA pero se ignoran de lo contrario.

FUENTES CON SCRIPT

Los scripts ejecutables presentes en el directorio $PCP_PMDAS_DIR/openmetrics/config.d o sus subdirectorios se ejecutarán y la transmisión stdout que contiene datos de métricas con formato openmetrics se analizará como si hubiera provenido de una URL o archivo. La transmisión stderr de un script se enviará al archivo de registro de PMDA, que por defecto se puede encontrar en $(PCP_LOG_DIR)/pmcd/openmetrics.log.

Tenga en cuenta que las fuentes con script no admiten el filtrado de etiquetas o métricas (como se describe anteriormente para las fuentes de URL); simplemente pueden realizar su propio filtrado en el script con sed(1), awk(1), o la herramienta que se desee.

Un ejemplo simple de una entrada de configuración con script sigue: 

#! /bin/sh
awk '{
    print("# HELP loadavg carga promedio local")
    print("# TYPE loadavg gauge")
    printf("loadavg {interval=\"1-minute\"} %.2f\n", $1)
    printf("loadavg {interval=\"5-minute\"} %.2f\n", $2)
    printf("loadavg {interval=\"15-minute\"} %.2f\n", $3)
}' /proc/loadavg

Este script produce los siguientes datos de métricas con formato OpenMetrics cuando se ejecuta: 

# HELP loadavg carga promedio local
# TYPE loadavg gauge
loadavg {interval="1-minute"} 0.12
loadavg {interval="5-minute"} 0.27
loadavg {interval="15-minute"} 0.54

Si el script anterior se guardara y se hiciera ejecutable en un archivo llamado $PCP_PMDAS_DIR/openmetrics/config.d/local/system.sh, esto daría como resultado una nueva métrica de PCP llamada openmetrics.local.system.loadavg que tendría tres instancias para los valores actuales de carga promedio: 1 minuto, 5 minutos y 15 minutos.

Las entradas de configuración con script pueden producir más de un nombre de métrica hoja de PCP. Por ejemplo, el script "system.sh" anterior también podría exportar otras métricas, como estadísticas de CPU, leyendo /proc/stat en el sistema local. Dichas métricas adicionales aparecerían como métricas pares en el mismo subárbol de métricas de PCP. En el caso de los contadores de CPU, la definición del tipo de métrica debería ser **counter**, no **gauge**. Para obtener detalles completos de los formatos de exposición de openmetrics, consulte https://github.com/OpenObservability/OpenMetrics/blob/master/specification/OpenMetrics.md.

CONSIDERACIONES SELinux

Los archivos de configuración con script son ejecutados por el PMDA pmdaopenmetrics con el mismo contexto y política SELinux que el pmcd(1) local. Para scripts simples, como el ejemplo de carga promedio descrito anteriormente, esto normalmente está bien. Sin embargo, pueden producirse errores de AVC para scripts que realizan llamadas a bibliotecas o al sistema que están restringidas por el contexto y las políticas SELinux vigentes. En estos casos, no es factible otorgar unilateralmente a pmcd o a sus PMDA una política de ejecución no restringida. En estos casos específicos del sitio, será necesario crear un módulo de política SELinux local. Esto se puede hacer capturando el registro (o registros) de AVC del registro de auditoría local, generando un módulo de política local usando audit2allow y luego cargando el nuevo módulo usando semodule, por ejemplo, de la siguiente manera: 

    $ sudo grep '^type=AVC.*pcp' /var/log/audit/audit.log \
    | audit2allow -M mypolicy
    $ sudo semodule -i mypolicy.pp

Si estas políticas locales necesitan ser persistentes después de reiniciar, entonces un fragmento de script similar al ejemplo anterior puede agregarse al archivo RC de pmcd local (típicamente /etc/pcp/pmcd/rc.local). Para obtener más detalles, consulte audit2allow(1) y semodule(1).

NOMENCLATURA DE MÉTRICAS

Todas las métricas de un archivo llamado JOB.* se exportarán como métricas de PCP con el prefijo de nombre de métrica openmetrics.JOB. Por lo tanto, el nombre JOB debe ser un nombre válido no hoja para los nombres de métricas PMNS de PCP. Si el nombre JOB tiene varios componentes separados por puntos, los nombres PMNS resultantes incluirán esos componentes y se debe tener cuidado para garantizar que no haya definiciones superpuestas, por ejemplo, las métricas devueltas por JOB.response pueden superponerse o entrar en conflicto con las métricas devueltas por JOB.response.time.

Las entradas de archivo de configuración (URLs o scripts) que se encuentran en subdirectorios del directorio de configuración también darán lugar a nombres de métricas jerárquicas. Por ejemplo, un archivo de configuración llamado $PCP_PMDAS_DIR/openmetrics/config.d/mysource/latency/get.url dará lugar a la creación de métricas (al obtener esa URL de origen) debajo de openmetrics.mysource.latency.get en el espacio de nombres de PCP. Los scripts que se encuentran en subdirectorios del directorio de configuración dan lugar de manera similar a nombres de métricas jerárquicas de PCP.

NOMBRES DE MÉTRICAS DINÁMICAS

Como se describió anteriormente, se pueden realizar cambios y agregar nuevas adiciones a los archivos en el directorio de configuración sin tener que reiniciar el PMDA. Estos cambios se detectan automáticamente y los nombres de métricas de PCP debajo de openmetrics en el PMNS se actualizarán en consecuencia, es decir, se agregarán nuevas métricas dinámicamente y/o se eliminarán las métricas existentes. Además, pmdaopenmetrics respeta el protocolo PMCD_NAMES_CHANGE de pmFetch(3) que se introdujo en la versión 4.0 de PCP. En particular, si las métricas de openmetrics están siendo registradas por un pmlogger(1) de PCP versión 4.0 o posterior, las nuevas métricas que aparezcan como resultado de cambios en el directorio de configuración de PMDA comenzarán a registrarse automáticamente, siempre que la raíz del espacio de nombres de métricas de openmetrics esté configurada para el registro en el archivo de configuración de pmlogger. Consulte pmlogger(1) para obtener detalles. Un ejemplo de un archivo de configuración de pmlogger de este tipo es: 

log mandatory on 2 second {
	# registrar todas las métricas debajo de la raíz del espacio de nombres openmetrics
	openmetrics
}

METADATOS

Los datos de métricas devueltos por archivos de configuración de URL o con script pueden contener metadatos que pueden ser utilizados por el PMDA openmetrics para especificar la semántica, el tipo de datos, la escala y las unidades de las métricas creadas dinámicamente. Estos metadatos tienen el prefijo # PCP5 o # PCP en los datos de métricas ingeridos. Para obtener información adicional sobre los metadatos de PCP, consulte pmLookupDesc(3) y pmParseUnitsStr(3) y los ejemplos en los archivos de configuración enviados.

Los metadatos "PCP5" en línea deben ser proporcionados por el punto final de origen de métricas (URL o script). Una alternativa es especificarlos directamente en el archivo de configuración de la URL, lo que tiene la ventaja de no tener que modificar la fuente/punto final si los metadatos son incorrectos o faltan. Los metadatos especificados en el archivo de configuración de la URL anulan cualquier metadato en línea.

La sintaxis del archivo de configuración para especificar metadatos es:
METADATOS: expresión regular tipo indom semántica unidades ... hasta el final de la línea
Donde:
METADATOS: es literal
expresión regular es una expresión regular extendida para coincidir con uno o más nombres de métricas devueltos por la URL,
tipo es uno de los tipos numéricos de PCP (32, u32, 64, u64, float o double),
indom es un nombre de dominio de instancia arbitrario, o PM_INDOM_NULL,
semántica es counter, instant o discrete y
unidades es none o una cadena que se extiende hasta el final de la línea y que puede ser analizada por pmParseUnitsStr(3), es decir, las unidades, dimensiones y escala que se utilizarán para que las métricas coincidan.

Un archivo de configuración de ejemplo que ingiere métricas del punto final de Grafana /metrics en localhost, filtra todas las métricas devueltas por esa URL *excepto* por grafana_api_response_status_total y luego especifica que el *tipo* de métrica es un entero sin signo de 32 bits con un dominio de instancia no singular llamado response y una semántica de *counter* con *unidades* de count.

http://localhost:3000/metrics
FILTRO: INCLUIR MÉTRICA grafana_api_response_status_total
FILTRO: EXCLUIR MÉTRICA .*
METADATOS: grafana_api_response_status_total u32 response counter count

MÉTRICAS DE CONTROL

El PMDA mantiene métricas de control especiales, como se describe a continuación. Aparte de openmetrics.control.debug, cada una de estas métricas tiene una instancia por cada fuente de métricas configurada. Todas estas métricas tienen valores enteros con semántica de contador, excepto openmetrics.control.status, que tiene un valor de cadena. Es importante tener en cuenta que la recuperación de cualquiera de las métricas openmetrics.control solo actualizará los contadores y los valores de estado si la URL correspondiente se recupera realmente. Si la URL de origen no se recupera, los valores de la métrica de control no activan una actualización y los valores de control informados representan la recuperación más reciente de cada origen correspondiente.

El dominio de instancias para las métricas de openmetrics.control se ajusta dinámicamente a medida que se descubren nuevas fuentes. Si no hay fuentes configuradas, los nombres de las métricas siguen estando definidos, pero el dominio de instancias estará vacío y una recuperación no devolverá ningún valor.

openmetrics.control.status
Una cadena que representa el estado de la última recuperación de la fuente correspondiente. Generalmente será success para un código de respuesta http de 200. Esta métrica se puede utilizar para la monitorización de la disponibilidad del servicio, siempre que, como se mencionó anteriormente, también se recupere la URL de la fuente correspondiente.
openmetrics.control.status_code
Esta métrica es similar a openmetrics.control.status, excepto que es el código de respuesta entero de la última recuperación. Un valor de 200 suele indicar éxito y cualquier otro valor indica fallo. Esta métrica también puede utilizarse para la monitorización de la disponibilidad del servicio, con las mismas advertencias que openmetrics.control.status.
openmetrics.control.calls
Número total de veces que cada fuente de métricas configurada ha sido recuperada (si es una URL) o ejecutada (si es un script), desde que se inició el PMDA. Esta métrica tiene semántica de contador y normalmente sería convertida a una tasa/segundo por las herramientas cliente.
openmetrics.control.fetch_time
Tiempo total en milisegundos que cada fuente de métricas configurada ha tardado en devolver un documento, excluyendo el tiempo de análisis del documento. Esta métrica tiene semántica de contador y normalmente sería convertida a tasa por las herramientas cliente, pero también es útil en su forma bruta como el tiempo de análisis acumulado desde que se inició el PMDA.
openmetrics.control.parse_time
Tiempo total en milisegundos que cada fuente de métricas configurada ha tardado en analizar cada documento, excluyendo el tiempo de recuperación del documento. Esta métrica tiene semántica de contador y normalmente sería convertida a tasa por las herramientas cliente, pero también es útil en su forma bruta como el tiempo de análisis acumulado desde que se inició el PMDA.

Cuando se convierte a una tasa, la métrica calls representa la tasa de recuperación promedio de cada fuente durante el intervalo de muestreo (delta de tiempo entre muestras). Los contadores fetch_time y parse_time, cuando se convierten a una tasa, representan la latencia promedio de recuperación y análisis (respectivamente), durante el intervalo de muestreo.

La métrica openmetrics.control.debug tiene un valor singular, que por defecto es 0. Si se almacena un valor distinto de cero en esta métrica usando pmstore(1), se escribirán mensajes de depuración adicionales en el archivo de registro del PMDA.

LIMITACIONES

Los internos de pmdaopenmetrics y libpcp imponen algunas restricciones numéricas sobre el número de fuentes (4095), métricas (1024) dentro de cada fuente, y instancias para cada métrica (4194304).

INSTALACIÓN

Instale el PMDA OpenMetrics utilizando el script Install como root:

# cd $PCP_PMDAS_DIR/openmetrics
# ./Install

Para desinstalar, se debe hacer lo siguiente como root:

# cd $PCP_PMDAS_DIR/openmetrics
# ./Remove

pmdaopenmetrics es iniciado por pmcd(1) y nunca debe ejecutarse directamente. Los scripts Install y Remove notifican a pmcd cuando el agente se instala o se elimina.

Cuando se agregan, eliminan o cambian scripts y archivos *.url* en el directorio de configuración, generalmente no es necesario reiniciar el PMDA; los cambios se detectarán y gestionarán en las solicitudes posteriores al PMDA.

ENTORNO PCP

Las variables de entorno con el prefijo PCP_ se utilizan para parametrizar los nombres de archivos y directorios utilizados por PCP. En cada instalación, el archivo /etc/pcp.conf contiene los valores locales para estas variables. La variable $PCP_CONF puede usarse para especificar un archivo de configuración alternativo, como se describe en pcp.conf(5).
