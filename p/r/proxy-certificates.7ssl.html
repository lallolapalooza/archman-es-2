NOMBRE

proxy-certificates - Certificados proxy en OpenSSL

DESCRIPCIÓN

Los certificados proxy se definen en la RFC 3820. Se utilizan para extender derechos a otra entidad (normalmente un proceso informático, o a veces al propio usuario). Esto permite a la entidad realizar operaciones en nombre del propietario del certificado de la Entidad Final (EE).

Los requisitos para un certificado proxy válido son:

  • Son emitidos por una Entidad Final, ya sea un certificado EE normal, o otro certificado proxy.
  • No deben tener las extensiones subjectAltName o issuerAltName.
  • Deben tener la extensión proxyCertInfo.
  • Deben tener el sujeto de su emisor, con un commonName añadido.

Habilitación de la verificación de certificados proxy

OpenSSL espera que las aplicaciones que desean utilizar certificados proxy sean especialmente conscientes de ellos, y lo hagan explícito. Esto se hace estableciendo una bandera de verificación X509:

X509_STORE_CTX_set_flags(ctx, X509_V_FLAG_ALLOW_PROXY_CERTS);

o

X509_VERIFY_PARAM_set_flags(param, X509_V_FLAG_ALLOW_PROXY_CERTS);

Consulte "NOTAS" para una discusión sobre este requisito.

Creación de certificados proxy

La creación de certificados proxy se puede realizar utilizando el comando openssl-x509(1), con algunas extensiones adicionales:

[ proxy ]
# Un certificado proxy NUNCA debe ser un certificado CA.
basicConstraints = CA:FALSE
# ID de clave de autoridad habitual
authorityKeyIdentifier = keyid,issuer:always
# La extensión que marca este certificado como proxy
proxyCertInfo = critical,language:id-ppl-anyLanguage,pathlen:1,policy:text:AB

También es posible especificar la extensión proxy en una sección separada:

proxyCertInfo = critical,@proxy_ext
[ proxy_ext ]
language = id-ppl-anyLanguage
pathlen = 0
policy = text:BC

El valor de la política tiene una sintaxis específica, syntag:string, donde el syntag determina lo que se hará con la cadena. Se reconocen los siguientes syntags:

text
indica que la cadena es una secuencia de bytes, sin ninguna codificación: 
policy=text:räksmörgås
hex
indica que la cadena es datos binarios codificados en hexadecimal, con dos puntos entre cada byte (cada dos dígitos hexadecimales): 
policy=hex:72:E4:6B:73:6D:F6:72:67:E5:73
file
indica que el texto de la política se tomará de un archivo. La cadena es entonces un nombre de archivo. Esto es útil para políticas que son de más de unas pocas líneas, como XML u otro marcado.

Tenga en cuenta que el valor de la política proxy es lo que determina los derechos otorgados al proceso durante el certificado proxy, y depende de la aplicación interpretar y combinar estas políticas.

Con una extensión proxy, la creación de un certificado proxy es cuestión de dos comandos:

openssl req -new -config proxy.cnf \
    -out proxy.req -keyout proxy.key \
    -subj "/DC=org/DC=openssl/DC=users/CN=proxy"
openssl x509 -req -CAcreateserial -in proxy.req -out proxy.crt \
    -CA user.crt -CAkey user.key -days 7 \
    -extfile proxy.cnf -extensions proxy

También puede crear un certificado proxy utilizando otro certificado proxy como emisor. Tenga en cuenta que este ejemplo utiliza una sección de configuración diferente para las extensiones proxy:

openssl req -new -config proxy.cnf \
    -out proxy2.req -keyout proxy2.key \
    -subj "/DC=org/DC=openssl/DC=users/CN=proxy/CN=proxy 2"
openssl x509 -req -CAcreateserial -in proxy2.req -out proxy2.crt \
    -CA proxy.crt -CAkey proxy.key -days 7 \
    -extfile proxy.cnf -extensions proxy_2

Uso de certificados proxy en aplicaciones

Para interpretar las políticas proxy, la aplicación normalmente comenzaría con algunos derechos predeterminados (quizás ninguno), luego calcularía los derechos resultantes comprobando los derechos contra la cadena de certificados proxy, el certificado de usuario y los certificados CA.

La parte complicada es averiguar cómo pasar datos entre su aplicación y el procedimiento de validación del certificado.

Los siguientes ingredientes son necesarios para dicho procesamiento:

  • una función de devolución de llamada (callback) que se llamará para cada certificado que se esté validando. La función de devolución de llamada se llama varias veces para cada certificado, por lo que debe tener cuidado de realizar la interpretación de la política proxy en el momento adecuado. También debe rellenar los valores predeterminados cuando se comprueba el certificado EE.
  • una estructura de datos que se comparte entre el código de su aplicación y la función de devolución de llamada.
  • una función envolvente (wrapper) que lo configura todo.
  • una función de índice ex_data que crea un índice en el almacén genérico ex_data adjunto a un contexto de validación X509.

El siguiente código esqueleto puede utilizarse como punto de partida:

    unsigned char rights[(total_rights + 7) / 8];

{
    static volatile int idx = -1;
    if (idx < 0) {
        X509_STORE_lock(X509_STORE_CTX_get0_store(ctx));
        if (idx < 0) {
            idx = X509_STORE_CTX_get_ex_new_index(0,
                                                  "for verify callback",
                                                  NULL,NULL,NULL);
        }
        X509_STORE_unlock(X509_STORE_CTX_get0_store(ctx));
    }
    return idx;
}

proxy-certificates(7ssl)

NAME

proxy-certificates – Proxy certificate DESCRIPTION

DESCRIPTION

Proxy certificates are defined in RFC 3820. They allow the holder of a certificate to delegate the rights contained in the certificate to another party, without having to involve a CA.

The OpenSSL library provides support for proxy certificates. This support is not enabled by default. It must be explicitly enabled by the application developer.

The main mechanism for enabling this support is to set the X509_V_FLAG_ALLOW_PROXY_CERTS flag using X509_STORE_set_flags(3). If this flag is not set, then proxy certificates will be treated as non-proxy certificates, and any proxy-specific extensions will cause a verification error.

When the X509_V_FLAG_ALLOW_PROXY_CERTS flag is set, the certificate chain is searched for proxy certificates. If a proxy certificate is found, its contents are examined to determine the rights that are delegated to the holder of the proxy certificate.

The process of examining the proxy certificate is handled by the proxy certificate verification callback. This callback is invoked when a proxy certificate is encountered in the chain. The callback is responsible for extracting the proxy-specific information from the certificate, such as the delegated rights, and for verifying the integrity of the proxy certificate.

The following code snippet demonstrates how to set up a verification callback for proxy certificates:

 static int verify_callback(int ok, X509_STORE_CTX *ctx)
 {
     X509 *xs = X509_STORE_CTX_get_current_cert(ctx);
     PROXY_CERT_INFO_EXTENSION *pci;
     YOUR_RIGHTS tmp_rights;
     int i;
     long n;
     char *cp;
     unsigned char *ucp;
     int ok_ret = ok;
     if (!xs)
         return ok;
     /* Check for proxy certificate specific extensions */
     if ((pci = PROXY_CERT_INFO_EXTENSION_from_X509(xs)) != NULL) {
         /* We have a proxy certificate */
         /*
          * The following procedure takes a string and its
          * length, interprets it and sets the bits
          * in the YOUR_RIGHTS pointed at by the
          * third argument.
          */
         process_rights((char *) pci->proxyPolicy->policy->data,
                        pci->proxyPolicy->policy->length,
                        &tmp_rights);
         /*
          * If we have already accumulated rights from a previous
          * proxy certificate, intersect the new rights with the
          * existing ones. Otherwise, use the new rights as the
          * basis.
          */
         if (X509_STORE_CTX_get_ex_data(ctx,
                 get_proxy_auth_ex_data_idx(ctx))) {
             YOUR_RIGHTS *rights =
                 (YOUR_RIGHTS *)X509_STORE_CTX_get_ex_data(ctx,
                     get_proxy_auth_ex_data_idx(ctx));
             for(i = 0; i < total_rights / 8; i++)
                 rights->rights[i] &= tmp_rights.rights[i];
         } else {
             YOUR_RIGHTS *rights =
                 (YOUR_RIGHTS *)X509_STORE_CTX_get_ex_data(ctx,
                     get_proxy_auth_ex_data_idx(ctx));
             memcpy(rights, &tmp_rights, sizeof(YOUR_RIGHTS));
             X509_STORE_CTX_set_ex_data(ctx,
                 get_proxy_auth_ex_data_idx(ctx), rights);
         }
         PROXY_CERT_INFO_EXTENSION_free(pci);
     } else if (!(X509_get_extension_flags(xs) & EXFLAG_CA)) {
         /* We have an EE certificate, let's use it to set default! */
         YOUR_RIGHTS *rights =
             (YOUR_RIGHTS *)X509_STORE_CTX_get_ex_data(ctx,
                 get_proxy_auth_ex_data_idx(ctx));
         /*
          * The following procedure finds out what rights the
          * owner of the current certificate has, and sets them
          * in the YOUR_RIGHTS structure pointed at by the
          * second argument.
          */
         set_default_rights(xs, rights);
     }
     return ok_ret;
 }
 /*
  * Check if the accumulated rights are sufficient for the requested operation.
  */
 static int check_needed_rights(YOUR_RIGHTS rights, YOUR_RIGHTS *needed_rights)
 {
     int i;
     for (i = 0; i < total_rights / 8; i++) {
         if ((rights.rights[i] & needed_rights->rights[i]) !=
             needed_rights->rights[i]) {
             return 0; /* Missing rights */
         }
     }
     return 1; /* All rights are present */
 }
 static int my_X509_verify_cert(X509_STORE_CTX *ctx,
                                YOUR_RIGHTS *needed_rights)
 {
     int ok;
     int (*save_verify_cb)(int ok,X509_STORE_CTX *ctx) =
         X509_STORE_CTX_get_verify_cb(ctx);
     YOUR_RIGHTS rights;
     X509_STORE_CTX_set_verify_cb(ctx, verify_callback);
     X509_STORE_CTX_set_ex_data(ctx, get_proxy_auth_ex_data_idx(ctx),
                                &rights);
     X509_STORE_CTX_set_flags(ctx, X509_V_FLAG_ALLOW_PROXY_CERTS);
     ok = X509_verify_cert(ctx);
     if (ok == 1) {
         ok = check_needed_rights(rights, needed_rights);
     }
     X509_STORE_CTX_set_verify_cb(ctx, save_verify_cb);
     return ok;
 }

If you use SSL or TLS, you can easily set up a callback to have the certificates checked properly, using the code above:

 SSL_CTX_set_cert_verify_callback(s_ctx, my_X509_verify_cert,
                                  &needed_rights);

NOTES

To this date, it seems that proxy certificates have only been used in environments that are aware of them, and no one seems to have investigated how they can be used or misused outside of such an environment.

For that reason, OpenSSL requires that applications aware of proxy certificates must also make that explicit.

subjectAltName and issuerAltName are forbidden in proxy certificates, and this is enforced in OpenSSL. The subject must be the same as the issuer, with one commonName added on.
