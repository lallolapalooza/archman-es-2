DESCRIPCIÓN

Todas las "funciones" mencionadas aquí se pasan como punteros de función entre libcrypto y el proveedor en los arrays OSSL_DISPATCH(3), en la llamada a la función de inicialización del proveedor. Consulte "Proveedor" en provider(7) para una descripción de la función de inicialización. Se conocen como "upcalls".

Todas estas "funciones" tienen una definición de tipo de función correspondiente llamada OSSL_FUNC_{nombre}_fn, y una función auxiliar para recuperar el puntero de función de un elemento OSSL_DISPATCH(3) llamada OSSL_FUNC_{nombre}. Por ejemplo, la "función" core_gettable_params() tiene estos:

typedef OSSL_PARAM *
    (OSSL_FUNC_core_gettable_params_fn)(const OSSL_CORE_HANDLE *handle);
static ossl_inline OSSL_NAME_core_gettable_params_fn
    OSSL_FUNC_core_gettable_params(const OSSL_DISPATCH *opf);

Funciones centrales

core_gettable_params() devuelve un array constante de descriptores OSSL_PARAM(3), para parámetros que core_get_params() puede manejar.

core_get_params() recupera parámetros del núcleo para el handle dado. Ver "Parámetros del núcleo" a continuación para una descripción de los parámetros conocidos actualmente.

La función core_thread_start() informa al núcleo que el proveedor ha manifestado interés en el hilo actual. El núcleo informará al proveedor cuando el hilo finalmente se detenga. Debe pasársele el handle para este proveedor, así como una función de devolución de llamada handfn que se llamará cuando el hilo se detenga. Posteriormente, se llamará a la función de devolución de llamada, con el argumento suministrado arg, desde el hilo que se está deteniendo y se le pasa el contexto del proveedor como argumento. Esto puede ser útil para realizar limpiezas específicas del hilo, como liberar variables locales del hilo.

core_get_libctx() recupera el contexto del núcleo en el que se almacena el objeto de la biblioteca para el proveedor actual, accesible a través del handle. Esta función solo es útil para proveedores integrados, como el proveedor predeterminado. Nunca convierta esto a OSSL_LIB_CTX en un proveedor que no esté integrado, ya que el OSSL_LIB_CTX de la biblioteca que carga el proveedor podría ser una estructura completamente diferente del OSSL_LIB_CTX de la biblioteca a la que está enlazado el proveedor. Utilice OSSL_LIB_CTX_new_child(3) en su lugar para obtener un contexto de biblioteca adecuado que esté enlazado al contexto de la biblioteca de la aplicación.

core_new_error(), core_set_error_debug() y core_vset_error() son bloques de construcción para reportar un error al núcleo, con referencia al handle.

core_new_error()
asigna un nuevo registro de error específico del hilo.

Esto corresponde a la función de OpenSSL ERR_new(3).

core_set_error_debug()
establece información de depuración en el registro de error específico del hilo actual. La información de depuración incluye el nombre del archivo file, la línea line y el nombre de la función func donde ocurrió el error.

Esto corresponde a la función de OpenSSL ERR_set_debug(3).

core_vset_error()
establece la razón del error, junto con datos adicionales. La razón es un número definido por el proveedor y utilizado para indexar la tabla de cadenas de razones que se devuelve mediante provider_get_reason_strings(). Los datos adicionales se proporcionan como una cadena de formato fmt y un conjunto de argumentos args, que se tratan de la misma manera que con BIO_vsnprintf(). file y line también se pueden pasar para indicar exactamente dónde ocurrió o se informó el error.

Esto corresponde a la función de OpenSSL ERR_vset_error(3).

core_set_error_mark()
establece una marca en el registro de error superior actual si existe.

Esto corresponde a la función de OpenSSL ERR_set_mark(3).

core_clear_last_error_mark()
elimina la última marca añadida si existe.

Esto corresponde a la función de OpenSSL ERR_clear_last_mark(3).

core_pop_error_to_mark()
elimina de la pila de errores hasta que se encuentra una marca. La marca se elimina entonces. Si no hay marca, se elimina toda la pila.

Esto corresponde a la función de OpenSSL ERR_pop_to_mark(3).

core_count_to_mark()
devuelve el número de entradas en la pila de errores por encima de la entrada marcada más reciente, sin incluir esa entrada. Si no hay marca en la pila de errores, se devuelve el número de entradas en la pila de errores.

Esto corresponde a la función de OpenSSL ERR_count_to_mark(3).

La función core_obj_create() registra un nuevo OID y su nombre corto asociado sn y nombre largo ln para el handle dado. Es similar a la función de OpenSSL OBJ_create(3), excepto que devuelve 1 en caso de éxito o 0 en caso de fallo. Tratará como éxito el caso en que el OID ya exista (incluso si el nombre corto sn o el nombre largo ln proporcionados como argumentos difieren de los asociados con el OID existente, en cuyo caso los nuevos nombres no se asocian).

La función core_obj_add_sigid() registra un nuevo algoritmo de firma compuesto (sign_name) que consiste en un algoritmo de firma subyacente (pkey_name) y un algoritmo de digest (digest_name) para el handle dado. Asume que los OID para el algoritmo de firma compuesto, así como para los algoritmos de firma y digest subyacentes, son conocidos por OpenSSL o han sido registrados mediante una llamada a core_obj_create(). Corresponde a la función de OpenSSL OBJ_add_sigid(3), excepto que los objetos se identifican por nombre en lugar de un NID numérico. Se puede utilizar cualquier nombre (OID, nombre corto o nombre largo) para identificar el objeto. Tratará como éxito el caso en que el algoritmo de firma compuesto ya exista (incluso si se registró contra un algoritmo de firma o digest subyacente diferente). Para digest_name, se permite NULL o una cadena vacía para los algoritmos de firma que no necesitan un digest para funcionar correctamente. La función devuelve 1 en caso de éxito o 0 en caso de fallo.

CRYPTO_malloc(), CRYPTO_zalloc(), CRYPTO_free(), CRYPTO_clear_free(), CRYPTO_realloc(), CRYPTO_clear_realloc(), CRYPTO_secure_malloc(), CRYPTO_secure_zalloc(), CRYPTO_secure_free(), CRYPTO_secure_clear_free(), CRYPTO_secure_allocated(), BIO_new_file(), BIO_new_mem_buf(), BIO_read_ex(), BIO_write_ex(), BIO_up_ref(), BIO_free(), BIO_vprintf(), BIO_vsnprintf(), BIO_gets(), BIO_puts(), BIO_ctrl(), OPENSSL_cleanse() y OPENSSL_hexstr2buf() corresponden exactamente a las funciones públicas con el mismo nombre. De hecho, los punteros en el array OSSL_DISPATCH(3) suelen ser punteros directos a esas funciones públicas. Tenga en cuenta que las funciones BIO toman un tipo OSSL_CORE_BIO en lugar del tipo estándar BIO. Esto es para garantizar que un proveedor no mezcle BIOs del núcleo con BIOs utilizados en el lado del proveedor (los dos no son compatibles). OSSL_SELF_TEST_set_callback() se utiliza para establecer una función de devolución de llamada opcional que se puede pasar a un proveedor. Un proveedor puede ignorar esto.

get_entropy() recupera material de siembra del sistema operativo. El material de siembra tendrá al menos entropy bytes de aleatoriedad y la salida tendrá al menos min_len y como máximo max_len bytes. La dirección del búfer se almacena en *pout y la longitud del búfer se devuelve al llamador. En caso de error, se devuelve cero.

get_user_entropy() es lo mismo que get_entropy() excepto que intentará recopilar material de siembra a través de la fuente de siembra especificada por una llamada a RAND_set_seed_source_type(3) o a través de la "Configuración Aleatoria" en config(5).

cleanup_entropy() se utiliza para limpiar y liberar el búfer devuelto por get_entropy(). El puntero de entropía devuelto por get_entropy() se pasa en buf y su longitud en len.

cleanup_user_entropy() se utiliza para limpiar y liberar el búfer devuelto por get_user_entropy(). El puntero de entropía devuelto por get_user_entropy() se pasa en buf y su longitud en len.

get_nonce() recupera un nonce utilizando el parámetro salt pasado de longitud salt_len e información específica del sistema operativo. El salt debe contener información de identificación única y esta se incluye, de forma no especificada, como parte de la salida. La salida se almacena en un búfer que contiene al menos min_len y como máximo max_len bytes. La dirección del búfer se almacena en *pout y la longitud del búfer se devuelve al llamador. En caso de error, se devuelve cero.

get_user_nonce() es lo mismo que get_nonce() excepto que intentará recopilar material de siembra a través de la fuente de siembra especificada por una llamada a RAND_set_seed_source_type(3) o a través de la "Configuración Aleatoria" en config(5).

cleanup_nonce() se utiliza para limpiar y liberar el búfer devuelto por get_nonce(). El puntero del nonce devuelto por get_nonce() se pasa en buf y su longitud en len.

cleanup_user_nonce() se utiliza para limpiar y liberar el búfer devuelto por get_user_nonce().

CAPABILITIES

The capabilities are defined using key/value pairs. The keys are strings identifying the capability, and the values are of various types, including integers and strings. The available capabilities are listed below.

"TLS-GROUP" Capability

The "TLS-GROUP" capability can be queried by libssl to discover the list of TLS cipher groups that a provider can support. Each group is described by a set of properties, which are supplied as key/value pairs. The following properties are defined:

"tls-group-name" (OSSL_CAPABILITY_TLS_GROUP_NAME) <UTF8 string>
The name of the TLS group. This is the name that libssl will use to refer to the group, for example, "X25519". This value must be supplied.
"tls-group-type" (OSSL_CAPABILITY_TLS_GROUP_TYPE) <unsigned integer>
The type of TLS group. This indicates whether the group is intended for use in key exchange (KEX) or key encapsulation (KEM). The value can be OSSL_TLS_GROUP_TYPE_KEM or OSSL_TLS_GROUP_TYPE_KEX. This value must be supplied.
"tls-group-prime-num" (OSSL_CAPABILITY_TLS_GROUP_PRIME_NUM) <unsigned integer>
The number of bits in the prime modulus for Diffie-Hellman groups. This parameter is only relevant for DH groups. This value is optional.
"tls-group-generator-num" (OSSL_CAPABILITY_TLS_GROUP_GENERATOR_NUM) <unsigned integer>
The generator for Diffie-Hellman groups. This parameter is only relevant for DH groups. This value is optional.
"tls-group-digest-name" (OSSL_CAPABILITY_TLS_GROUP_DIGEST_NAME) <UTF8 string>
The name of the digest algorithm to be used with the TLS group. This parameter is required if the group is intended for use in key exchange (KEX). The digest algorithm is used to derive the shared secret from the key exchange material. This value must be supplied.
"tls-group-private-key-type" (OSSL_CAPABILITY_TLS_GROUP_PRIVATE_KEY_TYPE) <UTF8 string>
The type of private key associated with the TLS group. This parameter is used to specify the key type that the provider expects to be used with this group. Keys created should be able to support key exchange or key encapsulation method (KEM), as implied by the optional OSSL_CAPABILITY_TLS_GROUP_IS_KEM flag. The algorithm must support key and parameter generation as well as the key/parameter generation parameter, OSSL_PKEY_PARAM_GROUP_NAME. The group name given via "tls-group-name-internal" above will be passed via OSSL_PKEY_PARAM_GROUP_NAME when libssl wishes to generate keys/parameters.
"tls-group-sec-bits" (OSSL_CAPABILITY_TLS_GROUP_SECURITY_BITS) <unsigned integer>
The number of bits of security offered by keys in this group. The number of bits should be comparable with the ones given in table 2 and 3 of the NIST SP800-57 document.
"tls-group-is-kem" (OSSL_CAPABILITY_TLS_GROUP_IS_KEM) <unsigned integer>
Boolean flag to describe if the group should be used in key exchange (KEX) mode (0, default) or in key encapsulation method (KEM) mode (1).

This parameter is optional: if not specified, KEX mode is assumed as the default mode for the group.

In KEX mode, in a typical Diffie-Hellman fashion, both sides execute keygen then derive against the peer public key. To operate in KEX mode, the group implementation must support the provider functions as described in provider-keyexch(7).

In KEM mode, the client executes keygen and sends its public key, the server executes encapsulate using the client's public key and sends back the resulting ciphertext, finally the client executes decapsulate to retrieve the same shared secret generated by the server's encapsulate. To operate in KEM mode, the group implementation must support the provider functions as described in provider-kem(7).

Both in KEX and KEM mode, the resulting shared secret is then used according to the protocol specification.

"tls-min-tls" (OSSL_CAPABILITY_TLS_GROUP_MIN_TLS) <integer>
"tls-max-tls" (OSSL_CAPABILITY_TLS_GROUP_MAX_TLS) <integer>
"tls-min-dtls" (OSSL_CAPABILITY_TLS_GROUP_MIN_DTLS) <integer>
"tls-max-dtls" (OSSL_CAPABILITY_TLS_GROUP_MAX_DTLS) <integer>
These parameters can be used to describe the minimum and maximum TLS and DTLS versions supported by the group. The values equate to the on-the-wire encoding of the various TLS versions. For example TLSv1.3 is 0x0304 (772 decimal), and TLSv1.2 is 0x0303 (771 decimal). A 0 indicates that there is no defined minimum or maximum. A -1 indicates that the group should not be used in that protocol.

"TLS-SIGALG" Capability

The "TLS-SIGALG" capability can be queried by libssl to discover the list of TLS signature algorithms that a provider can support. Each signature supported can be used for client- or server-authentication in addition to the built-in signature algorithms. TLS1.3 clients can advertise the list of TLS signature algorithms they support in the signature_algorithms extension, and TLS servers can select an algorithm from the offered list that they also support. In this way a provider can add to the list of signature algorithms that libssl already supports with additional ones.

Each TLS signature algorithm that a provider supports should be described via the callback passed in through the provider_get_capabilities function. Each algorithm can have the following details supplied:

"iana-name" (OSSL_CAPABILITY_TLS_SIGALG_IANA_NAME) <UTF8 string>
The name of the signature algorithm as given in the IANA TLS Signature Scheme registry as "Description": https://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml#tls-signaturescheme. This value must be supplied.
"iana-code-point" (OSSL_CAPABILITY_TLS_SIGALG_CODE_POINT) <unsigned integer>
The TLS algorithm ID value as given in the IANA TLS SignatureScheme registry. This value must be supplied.

It is possible to register the same code point from within different providers. Users should note that if no property query is specified, or more than one implementation matches the property query then it is unspecified which implementation for a particular code point will be used.

"sigalg-name" (OSSL_CAPABILITY_TLS_SIGALG_NAME) <UTF8 string>
A name for the full (possibly composite hash-and-signature) signature algorithm. The provider may, but is not obligated to, provide a signature implementation with this name; if it doesn't, this is assumed to be a composite of a pure signature algorithm and a hash algorithm, which must be given with the parameters "sig-name" and "hash-name". This value must be supplied.
"sigalg-oid" (OSSL_CAPABILITY_TLS_SIGALG_OID) <UTF8 string>
The OID of the "sigalg-name" algorithm in canonical numeric text form. If this parameter is given, OBJ_create() will be used to create an OBJ and a NID for this OID, using the "sigalg-name" parameter for its (short) name. Otherwise, it's assumed to already exist in the object database, possibly done by the provider with the core_obj_create() upcall. This value is optional.
"sig-name" (OSSL_CAPABILITY_TLS_SIGALG_SIG_NAME) <UTF8 string>
The name of the pure signature algorithm that is part of a composite "sigalg-name". If "sigalg-name" is implemented by the provider, this parameter is redundant and must not be given. This value is optional.
"sig-oid" (OSSL_CAPABILITY_TLS_SIGALG_SIG_OID) <UTF8 string>
The OID of the "sig-name" algorithm in canonical numeric text form. If this parameter is given, OBJ_create() will be used to create an OBJ and a NID for this OID, using the "sig-name" parameter for its (short) name. Otherwise, it is assumed to already exist in the object database. This can be done by the provider using the core_obj_create() upcall. This value is optional.
"hash-name" (OSSL_CAPABILITY_TLS_SIGALG_HASH_NAME) <UTF8 string>
The name of the hash algorithm that is part of a composite "sigalg-name". If "sigalg-name" is implemented by the provider, this parameter is redundant and must not be given. This value is optional.
"hash-oid" (OSSL_CAPABILITY_TLS_SIGALG_HASH_OID) <UTF8 string>
The OID of the "hash-name" algorithm in canonical numeric text form. If this parameter is given, OBJ_create() will be used to create an OBJ and a NID for this OID, using the "hash-name" parameter for its (short) name. Otherwise, it's assumed to already exist in the object database, possibly done by the provider with the core_obj_create() upcall. This value is optional.
"key-type" (OSSL_CAPABILITY_TLS_SIGALG_KEYTYPE) <UTF8 string>
The key type of the public key of applicable certificates. If this parameter isn't present, it's assumed to be the same as "sig-name" if that's present, otherwise "sigalg-name". This value is optional.
"key-type-oid" (OSSL_CAPABILITY_TLS_SIGALG_KEYTYPE_OID) <UTF8 string>
The OID of the "key-type" in canonical numeric text form. If this parameter is given, OBJ_create() will be used to create an OBJ and a NID for this OID, using the "key-type" parameter for its (short) name. Otherwise, it's assumed to already exist in the object database, possibly done by the provider with the core_obj_create() upcall. This value is optional.
"sec-bits" (OSSL_CAPABILITY_TLS_SIGALG_SECURITY_BITS) <unsigned integer>
The number of bits of security offered by keys of this algorithm. The number of bits should be comparable with the ones given in table 2 and 3 of the NIST SP800-57 document. This number is used to determine the security strength of the algorithm if no digest algorithm has been registered that otherwise defines the security strength. If the signature algorithm implements its own digest internally, this value needs to be set to properly reflect the overall security strength. This value must be supplied.
"tls-min-tls" (OSSL_CAPABILITY_TLS_SIGALG_MIN_TLS) <integer>
"tls-max-tls" (OSSL_CAPABILITY_TLS_SIGALG_MAX_TLS) <integer>
"tls-min-dtls" (OSSL_CAPABILITY_TLS_SIGALG_MIN_DTLS) <integer>
"tls-max-dtls" (OSSL_CAPABILITY_TLS_SIGALG_MAX_DTLS) <integer>
These parameters can be used to describe the minimum and maximum TLS and DTLS versions supported by the signature algorithm. The values equate to the on-the-wire encoding of the various TLS versions. For example TLSv1.3 is 0x0304 (772 decimal), and TLSv1.2 is 0x0303 (771 decimal). A 0 indicates that there is no defined minimum or maximum. A -1 in either the min or max field indicates that the signature algorithm should not be used in that protocol. Presently, provider signature algorithms are used only with TLS 1.3, if that's enclosed in the specified range.

NOTES

The core_obj_create() and core_obj_add_sigid() functions were not thread safe in OpenSSL 3.0.

struct foo_ctx_st {
    struct prov_ctx_st *provctx;
    int b;
};
static void *foo_newctx(void *provctx)
{
    struct foo_ctx_st *fooctx = malloc(sizeof(*fooctx));
    if (fooctx != NULL)
        fooctx->provctx = provctx;
    else
        c_put_error(provctx->handle, E_MALLOC, __FILE__, __LINE__);
    return fooctx;
}
static void foo_freectx(void *fooctx)
{
    free(fooctx);
}
static int foo_init(void *vfooctx)
{
    struct foo_ctx_st *fooctx = vfooctx;
    fooctx->b = 0x33;
}
static int foo_update(void *vfooctx, unsigned char *in, size_t inl)
{
    struct foo_ctx_st *fooctx = vfooctx;
    /* ¿esperabas algo serio? */
    if (inl == 0)
        return 1;
    for (; inl-- > 0; in++)
        *in ^= fooctx->b;
    return 1;
}

{
    struct foo_ctx_st *fooctx = vfooctx;
    fooctx->b = 0x66;
}

    { OSSL_FUNC_BAR_NEWCTX, (void (*)(void))foo_newctx },
    { OSSL_FUNC_BAR_FREECTX, (void (*)(void))foo_freectx },

    { OSSL_FUNC_BAR_FINAL, (void (*)(void))foo_final },

    { "FOO", "provider=chumbawamba", foo_fns },
    { NULL, NULL, NULL }
};

                                     int *no_store)

    switch (operation_id) {

    }
    return NULL;

    struct prov_ctx_st *pctx = NULL;
    for (; in->function_id != 0; in++)
        switch (in->function_id) {
        case OSSL_FUNC_CORE_PUT_ERROR:
            c_put_error = OSSL_FUNC_core_put_error(in);
            break;
