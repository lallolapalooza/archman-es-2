NOMBRE

getrlimit, setrlimit, prlimit - obtener/establecer límites de recursos

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/resource.h>
int getrlimit(int recurso, struct rlimit *rlim);
int setrlimit(int recurso, const struct rlimit *rlim);
int prlimit(pid_t pid, int recurso,
            const struct rlimit *_Nullable nuevo_límite,
            struct rlimit *_Nullable límite_anterior);
struct rlimit {
    rlim_t  rlim_cur;  /* Límite blando */
    rlim_t  rlim_max;  /* Límite duro (techo para rlim_cur) */
};
typedef /* ... */  rlim_t;  /* Tipo entero sin signo */

DESCRIPCIÓN

Las llamadas al sistema getrlimit() y setrlimit() obtienen y establecen límites de recursos. Cada recurso tiene un límite blando y uno duro asociados, según se define en la estructura rlimit.

El límite blando es el valor que el kernel aplica para el recurso correspondiente. El límite duro actúa como un techo para el límite blando: un proceso no privilegiado solo puede establecer su límite blando a un valor en el rango de 0 hasta el límite duro y (irreversiblemente) reducir su límite duro. Un proceso privilegiado (en Linux: uno con la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario inicial) puede realizar cambios arbitrarios en cualquiera de los valores de límite.

El valor RLIM_INFINITY denota que no hay límite para un recurso (tanto en la estructura devuelta por getrlimit() como en la estructura pasada a setrlimit()).

El argumento recurso debe ser uno de:

RLIMIT_AS
Este es el tamaño máximo de la memoria virtual del proceso (espacio de direcciones). El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), mmap(2) y mremap(2), que fallan con el error ENOMEM al exceder este límite. Además, la expansión automática de la pila falla (y genera una señal SIGSEGV que mata al proceso si no se ha proporcionado una pila alternativa mediante sigaltstack(2)). Dado que el valor es un long, en máquinas con un long de 32 bits, este límite es como máximo de 2 GiB, o este recurso es ilimitado.
RLIMIT_CORE
Este es el tamaño máximo de un archivo core (ver core(5)) en bytes que el proceso puede volcar. Cuando es 0, no se crean archivos core. Cuando es distinto de cero, los volcados más grandes se truncan a este tamaño.
RLIMIT_CPU
Este es un límite, en segundos, sobre la cantidad de tiempo de CPU que el proceso puede consumir. Cuando el proceso alcanza el límite blando, se le envía una señal SIGXCPU. La acción predeterminada para esta señal es terminar el proceso. Sin embargo, la señal puede ser capturada y el manejador puede devolver el control al programa principal. Si el proceso continúa consumiendo tiempo de CPU, se le enviará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se le enviará SIGKILL. (Este último punto describe el comportamiento de Linux. Las implementaciones varían en cómo tratan a los procesos que continúan consumiendo tiempo de CPU después de alcanzar el límite blando. Las aplicaciones portátiles que necesitan capturar esta señal deben realizar una terminación ordenada al recibir SIGXCPU por primera vez.)
RLIMIT_DATA
Este es el tamaño máximo del segmento de datos del proceso (datos inicializados, datos no inicializados y montículo). El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), sbrk(2) y (desde Linux 4.7) mmap(2), que fallan con el error ENOMEM al encontrar el límite blando de este recurso.
RLIMIT_FSIZE
Este es el tamaño máximo en bytes de los archivos que el proceso puede crear. Los intentos de extender un archivo más allá de este límite dan lugar a la entrega de una señal SIGXFSZ. Por defecto, esta señal termina un proceso, pero un proceso puede capturar esta señal en su lugar, en cuyo caso la llamada al sistema relevante (por ejemplo, write(2), truncate(2)) falla con el error EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 a Linux 2.4.24)
Este es un límite en el número combinado de bloqueos de flock(2) y concesiones de fcntl(2) que este proceso puede establecer.
RLIMIT_MEMLOCK
Este es el número máximo de bytes de memoria que pueden fijarse en la RAM. Este límite se redondea hacia abajo al múltiplo más cercano del tamaño de página del sistema. Este límite afecta a mlock(2), mlockall(2) y la operación MAP_LOCKED de mmap(2). Desde Linux 2.6.9, también afecta a la operación SHM_LOCK de shmctl(2), donde establece un máximo en los bytes totales en segmentos de memoria compartida (ver shmget(2)) que pueden ser fijados por el ID de usuario real del proceso que llama. Los bloqueos SHM_LOCK de shmctl(2) se contabilizan por separado de los bloqueos de memoria por proceso establecidos por mlock(2), mlockall(2) y mmap(2) con MAP_LOCKED; un proceso puede fijar bytes hasta este límite en cada una de estas dos categorías.
Antes de Linux 2.6.9, este límite controlaba la cantidad de memoria que podía ser fijada por un proceso privilegiado. Desde Linux 2.6.9, no se aplican límites a la cantidad de memoria que un proceso privilegiado puede fijar, y este límite rige la cantidad de memoria que un proceso no privilegiado puede fijar.
RLIMIT_MSGQUEUE (desde Linux 2.6.8)
Este es un límite en el número de bytes que se pueden asignar para colas de mensajes POSIX para el ID de usuario real del proceso que llama. Este límite se aplica en mq_open(3). Cada cola de mensajes que el usuario crea cuenta (hasta que se elimina) contra este límite según la fórmula:
Desde Linux 3.5:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* Para sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Para datos del mensaje */

Linux 3.4 y anteriores:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* Para sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Para datos del mensaje */

donde attr es la estructura mq_attr especificada como cuarto argumento a mq_open(3), y las estructuras msg_msg y posix_msg_tree_node son estructuras internas del kernel.
La parte de "sobrecarga" en la fórmula tiene en cuenta los bytes de sobrecarga requeridos por la implementación y asegura que el usuario no pueda crear un número ilimitado de mensajes de longitud cero (dichos mensajes consumen de todos modos algo de memoria del sistema para la sobrecarga de gestión).
RLIMIT_NICE (desde Linux 2.6.12, pero ver BUGS abajo)
Esto especifica un techo al que se puede elevar el valor nice del proceso usando setpriority(2) o nice(2). El techo real para el valor nice se calcula como 20 - rlim_cur. El rango útil

PRLIMIT

La llamada al sistema prlimit() es una versión más flexible de getrlimit() y setrlimit(). Permite a un proceso obtener o establecer los límites de recursos para un proceso específico (determinado por pid), en lugar de solo para el proceso que llama. Si pid es 0, se aplica al proceso que llama.

Si nuevo_límite es diferente de NULL, se aplicará el nuevo límite para el recurso especificado, sujeto a las mismas reglas que setrlimit(). Si límite_anterior es diferente de NULL, se devolverá el valor antiguo del límite en la estructura apuntada por límite_anterior.

Solo un proceso con la capacidad CAP_SYS_PTRACE puede usar prlimit() para establecer límites para otro proceso (si el pid no es 0). Los procesos sin esta capacidad solo pueden usar prlimit() para modificar sus propios límites (es decir, cuando pid es 0).

VALOR DE RETORNO

En caso de éxito, getrlimit(), setrlimit(), y prlimit() devuelven 0.

En caso de error, devuelven -1 y errno se establece para indicar el error.

ERRORES

EFAULT
rlim apunta fuera del espacio de direcciones accesible del usuario.
EINVAL
El valor de recurso no es válido, o setrlimit() o prlimit() intentan aumentar un límite duro, o el límite blando establecido es mayor que el límite duro.
EPERM
Un proceso no privilegiado intenta aumentar un límite duro o relajar un límite blando a un valor mayor que el límite duro actual.
ESRCH
El pid especificado en prlimit() no existe.

CONFORME A

getrlimit() y setrlimit() cumplen con POSIX.1-2001 y POSIX.1-2008. prlimit() es una extensión de Linux.

NOTAS

El tipo de datos rlim_t es un tipo entero sin signo, cuyo tamaño es suficiente para representar el mayor valor posible de límite de recursos en el sistema.

En Linux, los límites de recursos se pueden configurar de forma persistente en el archivo /etc/security/limits.conf. Ver limits.conf(5).

Para obtener los límites de recursos de un proceso específico en Linux, también puede consultar la interfaz de pseudo-sistema de archivos /proc/[pid]/limits.

El valor de RLIM_INFINITY es un valor específico de la implementación para indicar un límite infinito. Suele ser un valor muy grande (por ejemplo, 2^63-1 en arquitecturas de 64 bits).

El número de descriptores de archivo abiertos (RLIMIT_NOFILE) se trata de forma especial. El valor devuelto por getrlimit() es el límite actual, mientras que el valor que se puede establecer está limitado por el valor máximo que el kernel puede manejar (normalmente 1024 en sistemas antiguos, pero puede ser mayor en sistemas más nuevos, hasta el valor de /proc/sys/fs/file-max). El límite blando no puede exceder el límite duro.

A partir de Linux 2.4.22, se puede usar RLIMIT_NPROC para limitar el número de procesos que un usuario puede crear.

Para la mayoría de los recursos (excepto RLIMIT_CPU y RLIMIT_FSIZE), los límites se aplican en unidades de bytes. Para RLIMIT_CPU, la unidad es segundos. Para RLIMIT_NOFILE, la unidad es descriptores de archivo.

Consulte <sys/resource.h> para obtener la lista completa de recursos disponibles.

RLIMIT_AS

Los sistemas modernos de 64 bits a menudo tienen un límite de memoria virtual que es mucho mayor que 2^64 bytes. El valor devuelto por getrlimit para RLIMIT_AS no puede exceder el valor máximo representable por rlim_t. En sistemas de 32 bits, el límite RLIMIT_AS es generalmente 2 o 3 GiB. En arquitecturas de 64 bits, el límite es mucho mayor, pero aún está limitado por el tamaño de la arquitectura (por ejemplo, 256 TiB en x86-64 para kernels recientes).

Dado que el valor se devuelve en un tipo de dato long, en sistemas de 32 bits, esto puede causar problemas si se intentan establecer límites superiores a 2GiB (que es el máximo de un long con signo).

RLIMIT_MSGQUEUE

El límite RLIMIT_MSGQUEUE se introdujo en Linux 2.6.8. Las versiones anteriores de Linux no lo soportan.

RLIMIT_NICE

El valor del límite RLIMIT_NICE se puede establecer en un valor entre 0 y 100. El valor real del nice se calcula como 20 menos el valor del límite. Por lo tanto, un valor de límite de 0 permite un nice de 20 (el más lento), y un valor de límite de 100 permite un nice de -80 (el más rápido).

El valor del límite blando no se puede aumentar más allá del valor predeterminado que el proceso heredó de su padre.

Este límite no se aplica a los procesos con la capacidad CAP_SYS_NICE.

RLIMIT_RTPRIO

Este límite se introdujo en Linux 2.6.13. Es el máximo nivel de prioridad real-time que un proceso puede usar para configurar su política de tiempo de ejecución de real-time.

RLIMIT_RTTIME

Este límite se introdujo en Linux 2.6.13. Es un límite en la cantidad total de CPU que un proceso puede consumir cuando se ejecuta con una política de tiempo de ejecución de real-time. Cuando se alcanza el límite blando, se envía una señal SIGXCPU al proceso. Cuando se alcanza el límite duro, se envía una señal SIGKILL.

RLIMIT_SIGPENDING

Este límite se introdujo en Linux 2.6.8. Es el número máximo de señales pendientes que un proceso puede tener en cola. Este límite se aplica a las señales de todos los tipos, incluidas las señales de la cola de alta prioridad de POSIX.

RLIMIT_STACK

Este es el tamaño máximo de la pila del proceso en bytes. Esto afecta a las llamadas de asignación de memoria de pila. El límite está redondeado al múltiplo más cercano del tamaño de página.

BUGS

En las primeras versiones de Linux (antes de 2.6.12), el límite RLIMIT_NICE no funcionaba correctamente y siempre permitía al proceso establecer un nice de hasta 0. Esto se corrigió en Linux 2.6.12.

En las primeras versiones de Linux (antes de 2.6.13), el límite RLIMIT_RTPRIO no funcionaba. Esto se corrigió en Linux 2.6.13.

En las primeras versiones de Linux (antes de 2.6.13), el límite RLIMIT_RTTIME no funcionaba. Esto se corrigió en Linux 2.6.13.

RLIMIT_NOFILE
Esto especifica un valor uno mayor que el número máximo de descriptores de archivo que puede abrir este proceso. Los intentos (open(2), pipe(2), dup(2), etc.) de exceder este límite producen el error EMFILE. (Históricamente, este límite se denominó RLIMIT_OFILE en BSD.)
Desde Linux 4.5, este límite también define el número máximo de descriptores de archivo que un proceso no privilegiado (uno sin la capacidad CAP_SYS_RESOURCE) puede tener "en tránsito" hacia otros procesos, al ser pasados a través de sockets de dominio UNIX. RLIMIT_NPROC
Este es un límite en el número de procesos existentes (o, más precisamente en Linux, hilos) para el ID de usuario real del proceso que llama. Siempre que el número actual de procesos que pertenecen al ID de usuario real de este proceso sea mayor o igual a este límite, fork(2) falla con el error EAGAIN.
El límite RLIMIT_NPROC no se aplica a los procesos que tienen la capacidad CAP_SYS_ADMIN o CAP_SYS_RESOURCE, o que se ejecutan con el ID de usuario real 0.
RLIMIT_RSS
Este es un límite (en bytes) en el conjunto residente del proceso (el número de páginas virtuales residentes en RAM). Este límite solo tiene efecto en Linux 2.4.x, x < 30, y solo afecta a las llamadas a madvise(2) que especifican MADV_WILLNEED.
RLIMIT_RTPRIO (desde Linux 2.6.12, pero ver BUGS)
Esto especifica un techo para la prioridad en tiempo real que se puede establecer para este proceso usando sched_setscheduler(2) y sched_setparam(2).
Para más detalles sobre las políticas de planificación en tiempo real, ver sched(7)
RLIMIT_RTTIME (desde Linux 2.6.25)
Este es un límite (en microsegundos) en la cantidad de tiempo de CPU que un proceso planificado bajo una política de planificación en tiempo real puede consumir sin realizar una llamada al sistema bloqueante. Para el propósito de este límite, cada vez que un proceso realiza una llamada al sistema bloqueante, el recuento de su tiempo de CPU consumido se reinicia a cero. El recuento de tiempo de CPU no se reinicia si el proceso continúa intentando usar la CPU pero es desalojado, su segmento de tiempo expira, o llama a sched_yield(2).
Al alcanzar el límite blando, se envía una señal SIGXCPU al proceso. Si el proceso captura o ignora esta señal y continúa consumiendo tiempo de CPU, entonces se generará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se enviará una señal SIGKILL al proceso.
El uso previsto de este límite es detener un proceso en tiempo real descontrolado de bloquear el sistema.
Para más detalles sobre las políticas de planificación en tiempo real, ver sched(7)
RLIMIT_SIGPENDING (desde Linux 2.6.8)
Este es un límite en el número de señales que pueden estar en cola para el ID de usuario real del proceso que llama. Tanto las señales estándar como las de tiempo real se cuentan para el propósito de verificar este límite. Sin embargo, el límite solo se aplica a sigqueue(3); siempre es posible usar kill(2) para poner en cola una instancia de cualquiera de las señales que no estén ya en cola para el proceso.
RLIMIT_STACK
Este es el tamaño máximo de la pila del proceso, en bytes. Al alcanzar este límite, se genera una señal SIGSEGV. Para manejar esta señal, un proceso debe emplear una pila de señales alternativa (sigaltstack(2)).
Desde Linux 2.6.23, este límite también determina la cantidad de espacio utilizada para los argumentos de línea de comandos y las variables de entorno del proceso; para detalles, ver execve(2).

prlimit()

La llamada al sistema específica de Linux prlimit() combina y extiende la funcionalidad de setrlimit() y getrlimit(). Se puede utilizar tanto para establecer como para obtener los límites de recursos de un proceso arbitrario.

El argumento resource tiene el mismo significado que para setrlimit() y getrlimit().

Si el argumento new_limit no es NULL, entonces la estructura rlimit a la que apunta se utiliza para establecer nuevos valores para los límites blando y duro para resource. Si el argumento old_limit no es NULL, entonces una llamada exitosa a prlimit() coloca los límites blando y duro anteriores para resource en la estructura rlimit apuntada por old_limit.

El argumento pid especifica el ID del proceso sobre el cual se va a operar la llamada. Si pid es 0, entonces la llamada se aplica al proceso que llama. Para establecer o obtener los recursos de un proceso que no sea el propio, el llamador debe tener la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario del proceso cuyos límites de recursos se están cambiando, o los IDs de usuario real, efectivo y de conjunto guardado del proceso de destino deben coincidir con el ID de usuario real del llamador y los IDs de grupo real, efectivo y de conjunto guardado del proceso de destino deben coincidir con el ID de grupo real del llamador.

VALOR DE RETORNO

En caso de éxito, estas llamadas al sistema devuelven 0. En caso de error, se devuelve -1 y errno se establece para indicar el error.

ERRORES

EFAULT
Un argumento de puntero apunta a una ubicación fuera del espacio de direcciones accesible.
EINVAL
El valor especificado en resource no es válido; o, para setrlimit() o prlimit(): rlim->rlim_cur era mayor que rlim->rlim_max.
EPERM
Un proceso no privilegiado intentó aumentar el límite duro; la capacidad CAP_SYS_RESOURCE se requiere para hacer esto.
EPERM
El llamador intentó aumentar el límite duro RLIMIT_NOFILE por encima del máximo definido por /proc/sys/fs/nr_open (ver proc(5))
EPERM
(prlimit()) El proceso que llama no tenía permiso para establecer límites para el proceso especificado por pid.
ESRCH
No se pudo encontrar un proceso con el ID especificado en pid.

NOTAS

Un proceso hijo creado a través de fork(2) hereda los límites de recursos de su padre. Los límites de recursos se conservan en las llamadas a execve(2).

Los límites de recursos son atributos por proceso que son compartidos por todos los hilos en un proceso.

Reducir el límite blando para un recurso por debajo del consumo actual del proceso de ese recurso tendrá éxito (pero impedirá que el proceso aumente aún más su consumo del recurso).

Se pueden establecer los límites de recursos del shell usando el comando incorporado ulimit (limit en csh(1)). Los límites de recursos del shell son heredados por los procesos que crea para ejecutar comandos.

Desde Linux 2.6.24, los límites de recursos de cualquier proceso se pueden inspeccionar a través de /proc/pid/limits; ver proc(5).

NAME

prlimit — get and set resource limits of a process

LIBRARY

Linux User Manual - Set 2

SYNOPSIS

#include <sys/resource.h>

int prlimit(pid_t pid, int resource,
const struct rlimit *new_rlim, struct rlimit *old_rlim);

DESCRIPTION

The prlimit() system call allows a process to get and set the resource limits of another process (specified by pid). The resource argument specifies the resource whose limits are to be manipulated. The new_rlim and old_rlim arguments are pointers to struct rlimit structures. They specify the new limits and where to store the old limits, respectively.

If new_rlim is not NULL, then the soft and hard limits for the specified resource are set according to the values in the rlim_cur and rlim_max fields of the structure pointed to by new_rlim. If old_rlim is not NULL, then the previous soft and hard limits are stored in the structure pointed to by old_rlim.

If new_rlim is NULL, then old_rlim is updated with the current soft and hard limits for the specified resource, and no limits are changed.

The pid argument specifies the process ID of the target process. If pid is 0, then the limits of the calling process are manipulated.

A process can only change the limits of another process if it has appropriate privileges (typically, the CAP_SYS_RESOURCE capability). A process can always change its own limits.

The following resources are defined:

RLIMIT_AS
The maximum size of the process's virtual address space.
RLIMIT_CORE
The maximum size of a core file that may be created by a process.
RLIMIT_CPU
The maximum amount of CPU time (in seconds) that a process may consume.
RLIMIT_DATA
The maximum size of the process's data segment (initially, after the executable and data are loaded).
RLIMIT_FSIZE
The maximum size of files that a process may create.
RLIMIT_LOCKS
The maximum number of locks that a process may hold.
RLIMIT_MEMLOCK
The maximum number of pages that may be locked into memory by a process.
RLIMIT_MSGQUEUE
The maximum number of bytes that can be allocated for POSIX message queues.
RLIMIT_NICE
The maximum value of the niceness (priority adjustment) that can be set for a process. This corresponds to the value used by setpriority(2).
RLIMIT_NOFILE
The maximum number of file descriptors that a process may have open.
RLIMIT_NPROC
The maximum number of processes that can be created by a user.
RLIMIT_NPTS
The maximum number of pseudo-terminals that can be allocated.
RLIMIT_RSS
The maximum resident set size (physical memory) that may be used by a process.
RLIMIT_RTPRIO
The maximum real-time priority that may be set for a process.
RLIMIT_RTTIME
The maximum amount of CPU time (in microseconds) that a process may consume for real-time scheduling.
RLIMIT_SIGPENDING
The maximum number of signals that may be pending for the calling process.
RLIMIT_STACK
The maximum size of the process's stack.
RLIMIT_SWAP
The maximum amount of swap space that may be used by a process.
RLIMIT_MEMLOCK
The maximum number of pages that may be locked into memory by a process.
RLIMIT_STAK
The maximum size of the process's stack.

Resource limits are specified by two values: a soft limit and a hard limit. The soft limit is the value that the kernel enforces for the corresponding resource. The hard limit serves as a ceiling for the soft limit. A process can reduce its soft limit, but can only increase it up to the hard limit. A non-privileged process can only decrease its hard limit (down to the soft limit), while a privileged process (typically, one with the CAP_SYS_RESOURCE capability) can increase or decrease either the hard or soft limit.

The value RLIM_INFINITY represents an unlimited resource. This value is defined in <sys/resource.h>.

The struct rlimit structure contains at least the following fields:

  • rlim_cur: The soft limit.
  • rlim_max: The hard limit.

Both fields are of type rlim_t, which is an unsigned integer type.

RETURN VALUE

On success, prlimit() returns 0. On error, it returns -1, and errno is set to indicate the error.

ERRORS

The following errors can occur:

EACCES
The calling process does not have permission to change the limits of the target process.
EINVAL
The resource specified is invalid, or the requested new limit is invalid (e.g., the soft limit is greater than the hard limit, or the hard limit is not RLIM_INFINITY or a valid limit).
EPERM
The calling process does not have sufficient privileges to change the limits of the target process.
ESRCH
No process with the specified pid exists.

NOTES

The getrlimit(2) and setrlimit(2) functions provide similar functionality but are limited to manipulating the limits of the calling process. They also have some historical quirks and limitations that prlimit() overcomes.

Since glibc 2.13, the glibc getrlimit() and setrlimit() wrapper functions no longer invoke the corresponding system calls, but instead employ prlimit(), for the reasons described in BUGS.

The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

BUGS

In older Linux kernels, the SIGXCPU and SIGKILL signals delivered when a process encountered the soft and hard RLIMIT_CPU limits were delivered one (CPU) second later than they should have been. This was fixed in Linux 2.6.8.

In Linux 2.6.x kernels before Linux 2.6.17, a RLIMIT_CPU limit of 0 is wrongly treated as "no limit" (like RLIM_INFINITY). Since Linux 2.6.17, setting a limit of 0 does have an effect, but is actually treated as a limit of 1 second.

A kernel bug means that RLIMIT_RTPRIO does not work in Linux 2.6.12; the problem is fixed in Linux 2.6.13.

In Linux 2.6.12, there was an off-by-one mismatch between the priority ranges returned by getpriority(2) and RLIMIT_NICE. This had the effect that the actual ceiling for the nice value was calculated as 19 - rlim_cur. This was fixed in Linux 2.6.13.

Since Linux 2.6.12, if a process reaches its soft RLIMIT_CPU limit and has a handler installed for SIGXCPU, then, in addition to invoking the signal handler, the kernel increases the soft limit by one second. This behavior repeats if the process continues to consume CPU time, until the hard limit is reached, at which point the process is killed. Other implementations do not change the RLIMIT_CPU soft limit in this manner, and the Linux behavior is probably not standards conformant; portable applications should avoid relying on this Linux-specific behavior. The Linux-specific RLIMIT_RTTIME limit exhibits the same behavior when the soft limit is encountered.

Kernels before Linux 2.4.22 did not diagnose the error EINVAL for setrlimit() when rlim->rlim_cur was greater than rlim->rlim_max.

Linux doesn't return an error when an attempt to set RLIMIT_CPU has failed, for compatibility reasons.

Representation of "large" resource limit values on 32-bit platforms

The glibc getrlimit() and setrlimit() wrapper functions use a 64-bit rlim_t data type, even on 32-bit platforms. However, the rlim_t data type used in the getrlimit() and setrlimit() system calls is a (32-bit) unsigned long. Furthermore, in Linux, the kernel represents resource limits on 32-bit platforms as unsigned long. However, a 32-bit data type is not wide enough. The most pertinent limit here is RLIMIT_FSIZE, which specifies the maximum size to which a file can grow: to be useful, this limit must be represented using a type that is as wide as the type used to represent file offsets—that is, as wide as a 64-bit off_t (assuming a program compiled with _FILE_OFFSET_BITS=64).

To work around this kernel limitation, if a program tried to set a resource limit to a value larger than can be represented in a 32-bit unsigned long, then the glibc setrlimit() wrapper function silently converted the limit value to RLIM_INFINITY. In other words, the requested resource limit setting was silently ignored.

Since glibc 2.13, glibc works around the limitations of the getrlimit() and setrlimit() system calls by implementing setrlimit() and getrlimit() as wrapper functions that call prlimit().

EXAMPLES

The program below demonstrates the use of prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Usage: %s <pid> [<new-soft-limit> "
                "<new-hard-limit>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID of target process */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Set CPU time limit of target process; retrieve and display
       previous limit */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Previous limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Retrieve and display new CPU time limit */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("New limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
