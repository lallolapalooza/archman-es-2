NOMBRE

provider-decoder - Las funciones de la biblioteca OSSL_DECODER <-> proveedor

SINOPSIS

#include <openssl/core_dispatch.h>
/*
 * Ninguna de estas es una función real, sino que se muestra así para
 * las firmas de funciones que se ofrecen como punteros de función en matrices OSSL_DISPATCH.
 */
/* Accesor y descriptor de parámetros del decodificador */
const OSSL_PARAM *OSSL_FUNC_decoder_gettable_params(void *provctx);
int OSSL_FUNC_decoder_get_params(OSSL_PARAM params[]);
/* Funciones para construir / destruir / manipular el contexto del decodificador */
void *OSSL_FUNC_decoder_newctx(void *provctx);
void OSSL_FUNC_decoder_freectx(void *ctx);
const OSSL_PARAM *OSSL_FUNC_decoder_settable_ctx_params(void *provctx);
int OSSL_FUNC_decoder_set_ctx_params(void *ctx, const OSSL_PARAM params[]);
/* Funciones para comprobar el soporte de selección */
int OSSL_FUNC_decoder_does_selection(void *provctx, int selection);
/* Funciones para decodificar datos de objetos */
int OSSL_FUNC_decoder_decode(void *ctx, OSSL_CORE_BIO *in,
                             int selection,
                             OSSL_CALLBACK *data_cb, void *data_cbarg,
                             OSSL_PASSPHRASE_CALLBACK *cb, void *cbarg);
/* Funciones para exportar un objeto decodificado */
int OSSL_FUNC_decoder_export_object(void *ctx,
                                      const void *objref, size_t objref_sz,
                                      OSSL_CALLBACK *export_cb,
                                      void *export_cbarg);

DESCRIPCIÓN

El término "decodificar" se usa en este manual. Esto incluye, pero no se limita a la deserialización, ya que los decodificadores individuales también pueden realizar la decodificación en formatos de datos intermedios.

La operación DECODER es un método genérico para crear una referencia de objeto nativa del proveedor o datos decodificados intermedios a partir de una forma codificada leída del OSSL_CORE_BIO proporcionado. Si el llamador quiere decodificar datos de la memoria, debe proporcionar un BIO_s_mem(3) BIO. Los datos decodificados o la referencia del objeto se pasan junto con metadatos eventuales al metadata_cb como parámetros de OSSL_PARAM(3).

El decodificador no necesita saber más sobre el puntero OSSL_CORE_BIO que poder pasarlo a las llamadas apropiadas de BIO (ver "Funciones principales" en provider-base(7)).

La implementación del DECODER puede ser parte de una cadena, donde los datos se pasan de uno a otro. Por ejemplo, puede haber una implementación para decodificar un objeto de PEM a DER, y otra que decodifique DER a un objeto nativo del proveedor.

Se espera que el último paso de decodificación en la cadena de decodificación cree normalmente una referencia de objeto nativa del proveedor. Para importar ese objeto a un proveedor diferente, se puede llamar a OSSL_FUNC_decoder_export_object() como paso final del proceso de decodificación.

Todas las "funciones" mencionadas aquí se pasan como punteros de función entre libcrypto y el proveedor en matrices OSSL_DISPATCH(3) a través de matrices OSSL_ALGORITHM(3) que son devueltas por la función provider_query_operation() del proveedor (ver "Funciones del proveedor" en provider-base(7)).

Todas estas "funciones" tienen un tipo de función correspondiente llamado OSSL_FUNC_{name}_fn, y una función auxiliar para recuperar el puntero de función de un elemento OSSL_DISPATCH(3) llamado OSSL_FUNC_{name}. Por ejemplo, la "función" OSSL_FUNC_decoder_decode() tiene:

typedef int
    (OSSL_FUNC_decoder_decode_fn)(void *ctx, OSSL_CORE_BIO *in,
                                  int selection,
                                  OSSL_CALLBACK *data_cb, void *data_cbarg,
                                  OSSL_PASSPHRASE_CALLBACK *cb, void *cbarg);
static ossl_inline OSSL_FUNC_decoder_decode_fn*
    OSSL_FUNC_decoder_decode(const OSSL_DISPATCH *opf);

OSSL_DISPATCH(3) Las matrices se indexan mediante números que se proporcionan como macros en openssl-core_dispatch.h(7), como sigue:

OSSL_FUNC_decoder_get_params          OSSL_FUNC_DECODER_GET_PARAMS
OSSL_FUNC_decoder_gettable_params     OSSL_FUNC_DECODER_GETTABLE_PARAMS
OSSL_FUNC_decoder_newctx              OSSL_FUNC_DECODER_NEWCTX
OSSL_FUNC_decoder_freectx             OSSL_FUNC_DECODER_FREECTX
OSSL_FUNC_decoder_set_ctx_params      OSSL_FUNC_DECODER_SET_CTX_PARAMS
OSSL_FUNC_decoder_settable_ctx_params OSSL_FUNC_DECODER_SETTABLE_CTX_PARAMS
OSSL_FUNC_decoder_does_selection      OSSL_FUNC_DECODER_DOES_SELECTION
OSSL_FUNC_decoder_decode              OSSL_FUNC_DECODER_DECODE
OSSL_FUNC_decoder_export_object       OSSL_FUNC_DECODER_EXPORT_OBJECT

Nombres y propiedades

El nombre de una implementación debe coincidir con el tipo de objeto de destino que decodifica. Por ejemplo, una implementación que decodifica una clave RSA debería llamarse "RSA". Igualmente, una implementación que decodifica datos DER de entrada PEM debería llamarse "DER".

Las propiedades, tal como se definen en el elemento de matriz OSSL_ALGORITHM(3) de cada implementación de decodificador, pueden usarse para especificar más detalles sobre una implementación:

input
Esta propiedad se utiliza para especificar qué formato de entrada puede decodificar la implementación.

Esta propiedad es obligatoria.

Los proveedores de OpenSSL reconocen los siguientes tipos de entrada:

pem
Una implementación con ese tipo de entrada decodifica datos con formato PEM.
der
Una implementación con ese tipo de entrada decodifica datos con formato DER.
msblob
Una implementación con ese tipo de entrada decodifica datos con formato MSBLOB.
pvk
Una implementación con ese tipo de entrada decodifica datos con formato PVK.
structure
Esta propiedad se utiliza para especificar la estructura que se espera que tengan los datos decodificados.

Esta propiedad es opcional.

Estructuras actualmente reconocidas por los decodificadores incorporados:

"type-specific"
Estructura específica del tipo.
"pkcs8"
Estructura según la especificación PKCS#8.
"SubjectPublicKeyInfo"
Codificación de claves públicas según la Información de Clave Pública del Sujeto de RFC 5280.

Los posibles valores de ambas propiedades son abiertos. Un proveedor puede especificar tipos de entrada y estructuras que libcrypto no conozca en absoluto.

Selecciones de subconjuntos

A veces, un objeto tiene más de un subconjunto de datos que es interesante tratar por separado o juntos. Es posible especificar qué subconjuntos se van a decodificar, con un conjunto de bits selection que se pasan en un int.

Este conjunto de bits depende enteramente de qué tipo de objeto del lado del proveedor se va a decodificar. Por ejemplo, se asume que estos bits son los mismos que los utilizados con provider-keymgmt(7) (ver "Objetos clave" en provider-keymgmt(7)) cuando el objeto es un par de claves asimétricas, por ejemplo, OSSL_KEYMGMT_SELECT_PRIVATE_KEY si el objeto a decodificar debe contener componentes de clave privada.

OSSL_FUNC_decoder_does_selection() debería indicar si una implementación particular admite alguna de las combinaciones dadas por selection.

Funciones de contexto

OSSL_FUNC_decoder_newctx() devuelve un contexto que se utilizará con el resto de las funciones.

OSSL_FUNC_decoder_freectx() libera el ctx dado tal como fue creado por OSSL_FUNC_decoder_newctx().

OSSL_FUNC_decoder_set_ctx_params() establece datos de contexto de acuerdo con los parámetros de params que reconoce. Los parámetros no reconocidos deben ignorarse. Pasar NULL para params debería devolver verdadero.

OSSL_FUNC_decoder_settable_ctx_params() devuelve un OSSL_PARAM

NAME

provider-decoder - Decoder operations

SYNOPSIS

This manual page describes the decoder operations that are available from OpenSSL provider modules.

DESCRIPTION

An OpenSSL provider module can implement a decoder. A decoder is used to decode data into an object. The object can be of any type, and it can be for internal use within the provider module, or it can be intended for use by other provider modules, or by the OpenSSL library itself.

Creation and destruction

OSSL_FUNC_DECODER_newctx() creates a new decoder context. This context is specific to the decoder implementation and is used to hold any state that the decoder needs.

OSSL_FUNC_DECODER_freectx() destroys a decoder context.

OSSL_FUNC_DECODER_dupctx() duplicates a decoder context. This is useful if multiple threads need to use the same decoder configuration.

Parameter management

OSSL_FUNC_decoder_set_ctx_params() sets parameters on the decoder context. The parameters that are supported depend on the decoder implementation.

OSSL_FUNC_decoder_settable_ctx_params() returns a list of parameters that the decoder context supports. This list is an OSSL_PARAM(3) array describing the parameters that OSSL_FUNC_decoder_set_ctx_params() can handle.

See OSSL_PARAM(3) for further details on the parameters structure used by OSSL_FUNC_decoder_set_ctx_params() and OSSL_FUNC_decoder_settable_ctx_params().

Export function

When a provider-native object is created by a decoder it would be unsuitable for direct use with a foreign provider. The export function allows for exporting the object into that foreign provider if the foreign provider supports the type of the object and provides an import function.

OSSL_FUNC_decoder_export_object() should export the object of size objref_sz referenced by objref as an OSSL_PARAM(3) array and pass that into the export_cb as well as the given export_cbarg.

Decoding functions

OSSL_FUNC_decoder_decode() should decode the data as read from the OSSL_CORE_BIO in to produce decoded data or an object to be passed as reference in an OSSL_PARAM(3) array along with possible other metadata that was decoded from the input. This OSSL_PARAM(3) array is then passed to the data_cb callback. The selection bits, if relevant, should determine what the input data should contain. The decoding functions also take an OSSL_PASSPHRASE_CALLBACK(3) function pointer along with a pointer to application data cbarg, which should be used when a pass phrase prompt is needed.

It's important to understand that the return value from this function is interpreted as follows:

True (1)
This means "carry on the decoding process", and is meaningful even though this function couldn't decode the input into anything, because there may be another decoder implementation that can decode it into something.

The data_cb callback should never be called when this function can't decode the input into anything.

False (0)
This means "stop the decoding process", and is meaningful when the input could be decoded into some sort of object that this function understands, but further treatment of that object results into errors that won't be possible for some other decoder implementation to get a different result.

The conditions to stop the decoding process are at the discretion of the implementation.

Decoder operation parameters

There are currently no operation parameters currently recognised by the built-in decoders.

Parameters currently recognised by the built-in pass phrase callback:

"info" (OSSL_PASSPHRASE_PARAM_INFO) <UTF8 string>
A string of information that will become part of the pass phrase prompt. This could be used to give the user information on what kind of object it's being prompted for.

RETURN VALUES

OSSL_FUNC_decoder_newctx() returns a pointer to a context, or NULL on failure.

OSSL_FUNC_decoder_set_ctx_params() returns 1, unless a recognised parameter was invalid or caused an error, for which 0 is returned.

OSSL_FUNC_decoder_settable_ctx_params() returns a pointer to an array of constant OSSL_PARAM(3) elements.

OSSL_FUNC_decoder_does_selection() returns 1 if the decoder implementation supports any of the selection bits, otherwise 0.

OSSL_FUNC_decoder_decode() returns 1 to signal that the decoding process should continue, or 0 to signal that it should stop.
