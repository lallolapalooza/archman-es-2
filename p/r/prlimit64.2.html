getrlimit(2) Manual de llamadas al sistema getrlimit(2)

NOMBRE

getrlimit, setrlimit, prlimit - obtener/establecer límites de recursos

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/resource.h>
int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
int prlimit(pid_t pid, int resource,
            const struct rlimit *_Nullable new_limit,
            struct rlimit *_Nullable old_limit);
struct rlimit {
    rlim_t  rlim_cur;  /* Límite blando */
    rlim_t  rlim_max;  /* Límite duro (techo para rlim_cur) */
};
typedef /* ... */  rlim_t;  /* Tipo entero sin signo */
Requisitos de macro de prueba de características para glibc (ver feature_test_macros(7)):

prlimit():

    _GNU_SOURCE

DESCRIPCIÓN

Las llamadas al sistema getrlimit() y setrlimit() obtienen y establecen límites de recursos. Cada recurso tiene un límite blando y uno duro asociado, tal como se define en la estructura rlimit.

El límite blando es el valor que el kernel aplica para el recurso correspondiente. El límite duro actúa como un techo para el límite blando: un proceso no privilegiado solo puede establecer su límite blando a un valor en el rango de 0 hasta el límite duro, y (de forma irreversible) reducir su límite duro. Un proceso privilegiado (en Linux: uno con la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario inicial) puede realizar cambios arbitrarios en cualquiera de los valores de límite.

El valor RLIM_INFINITY denota que no hay límite en un recurso (tanto en la estructura devuelta por getrlimit() como en la estructura pasada a setrlimit()).

El argumento resource debe ser uno de:

RLIMIT_AS
Este es el tamaño máximo de la memoria virtual (espacio de direcciones) del proceso. El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), mmap(2) y mremap(2), que fallan con el error ENOMEM al superar este límite. Además, la expansión automática de la pila falla (y genera una SIGSEGV que mata al proceso si no se ha puesto a disposición una pila alternativa mediante sigaltstack(2)). Dado que el valor es un long, en máquinas con un long de 32 bits, este límite es como máximo de 2 GiB, o este recurso es ilimitado.
RLIMIT_CORE
Este es el tamaño máximo de un archivo core (ver core(5)) en bytes que el proceso puede volcar. Cuando es 0, no se crean archivos de volcado core. Cuando es distinto de cero, los volcados más grandes se truncan a este tamaño.
RLIMIT_CPU
Este es un límite, en segundos, sobre la cantidad de tiempo de CPU que el proceso puede consumir. Cuando el proceso alcanza el límite blando, se le envía una señal SIGXCPU. La acción predeterminada para esta señal es terminar el proceso. Sin embargo, la señal puede ser capturada y el manejador puede devolver el control al programa principal. Si el proceso continúa consumiendo tiempo de CPU, se le enviará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se le enviará SIGKILL. (Esto último describe el comportamiento de Linux. Las implementaciones varían en cómo tratan a los procesos que continúan consumiendo tiempo de CPU después de alcanzar el límite blando. Las aplicaciones portátiles que necesitan capturar esta señal deben realizar una terminación ordenada al recibir SIGXCPU por primera vez).
RLIMIT_DATA
Este es el tamaño máximo del segmento de datos del proceso (datos inicializados, datos no inicializados y heap). El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), sbrk(2) y (desde Linux 4.7) mmap(2), que fallan con el error ENOMEM al encontrar el límite blando de este recurso.
RLIMIT_FSIZE
Este es el tamaño máximo en bytes de los archivos que el proceso puede crear. Los intentos de extender un archivo más allá de este límite provocan la entrega de una señal SIGXFSZ. Por defecto, esta señal termina un proceso, pero un proceso puede capturar esta señal en su lugar, en cuyo caso la llamada al sistema relevante (por ejemplo, write(2), truncate(2)) falla con el error EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 a Linux 2.4.24)
Este es un límite sobre el número combinado de bloqueos flock(2) y leases fcntl(2) que este proceso puede establecer.
RLIMIT_MEMLOCK
Este es el número máximo de bytes de memoria que pueden ser fijados en RAM. Este límite se redondea hacia abajo al múltiplo más cercano del tamaño de página del sistema. Este límite afecta a mlock(2), mlockall(2) y a la operación MAP_LOCKED de mmap(2). Desde Linux 2.6.9, también afecta a la operación SHM_LOCK de shmctl(2), donde establece un máximo sobre los bytes totales en segmentos de memoria compartida (ver shmget(2)) que pueden ser fijados por el ID de usuario real del proceso llamante. Los bloqueos SHM_LOCK de shmctl(2) se contabilizan por separado de los bloqueos de memoria por proceso establecidos por mlock(2), mlockall(2) y la operación MAP_LOCKED de mmap(2); un proceso puede fijar bytes hasta este límite en cada una de estas dos categorías.
Antes de Linux 2.6.9, este límite controlaba la cantidad de memoria que podía ser fijada por un proceso privilegiado. Desde Linux 2.6.9, no se imponen límites a la cantidad de memoria que un proceso privilegiado puede fijar, y este límite rige en su lugar la cantidad de memoria que un proceso no privilegiado puede fijar.
RLIMIT_MSGQUEUE (desde Linux 2.6.8)
Este es un límite sobre el número de bytes que pueden ser asignados para colas de mensajes POSIX para el ID de usuario real del proceso llamante. Este límite se aplica a mq_open(3). Cada cola de mensajes que el usuario crea cuenta (hasta que se elimina) contra este límite según la fórmula:
Desde Linux 3.5:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* Para sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Para datos del mensaje */

Linux 3.4 y anteriores:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* Para sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Para datos del mensaje */

donde attr es la estructura mq_attr especificada como cuarto argumento de mq_open(3), y las estructuras msg_msg y posix_msg_tree_node son estructuras internas del kernel.
El sumando de "sobrecarga" en la fórmula contabiliza los bytes de sobrecarga requeridos por la implementación y asegura que el usuario no pueda crear un número ilimitado de mensajes de longitud cero (tales mensajes, sin embargo, consumen algo de memoria del sistema para la gestión de la contabilidad).
RLIMIT_NICE (desde Linux 2.6.12, pero ver BUGS abajo)
Esto especifica un techo hasta el cual se puede elevar el valor de nice del proceso usando setpriority(2) o nice(2). El techo real para el valor de nice se calcula como 20 - rlim_cur. La subida útil nge para este límite es, por lo tanto, de 1 (correspondiente a un valor agradable de 19) a 40 (correspondiente a un valor agradable de -20). Esta elección inusual de rango fue necesaria porque los números negativos no se pueden especificar como valores de límite de recursos, ya que típicamente tienen significados especiales. Por ejemplo, RLIM_INFINITY típicamente es lo mismo que -1. Para más detalles sobre el valor agradable, ver sched(7).
RLIMIT_NOFILE
Esto especifica un valor uno mayor que el número máximo de descriptores de archivo que pueden ser abiertos por este proceso. Los intentos (open(2), pipe(2), dup(2), etc.) de exceder este límite producen el error EMFILE. (Históricamente, este límite se denominó RLIMIT_OFILE en BSD.)
Desde Linux 4.5, este límite también define el número máximo de descriptores de archivo que un proceso no privilegiado (uno sin la capacidad CAP_SYS_RESOURCE) puede tener "en tránsito" a otros procesos, al ser pasados a través de sockets de dominio UNIX. Este límite se aplica a la llamada al sistema sendmsg(2). Para más detalles, ver unix(7).
RLIMIT_NPROC
Este es un límite en el número de procesos existentes (o, más precisamente en Linux, hilos) para el ID de usuario real del proceso que llama. Mientras el número actual de procesos que pertenecen al ID de usuario real de este proceso sea mayor o igual a este límite, fork(2) falla con el error EAGAIN.
El límite RLIMIT_NPROC no se aplica a los procesos que tienen la capacidad CAP_SYS_ADMIN o CAP_SYS_RESOURCE, o que se ejecutan con ID de usuario real 0.
RLIMIT_RSS
Este es un límite (en bytes) en el conjunto residente del proceso (el número de páginas virtuales residentes en RAM). Este límite solo tiene efecto en Linux 2.4.x, x < 30, y allí solo afecta a las llamadas a madvise(2) especificando MADV_WILLNEED.
RLIMIT_RTPRIO (desde Linux 2.6.12, pero ver BUGS)
Esto especifica un techo en la prioridad de tiempo real que puede ser establecida para este proceso usando sched_setscheduler(2) y sched_setparam(2).
Para más detalles sobre las políticas de planificación en tiempo real, ver sched(7)
RLIMIT_RTTIME (desde Linux 2.6.25)
Este es un límite (en microsegundos) en la cantidad de tiempo de CPU que un proceso planificado bajo una política de planificación en tiempo real puede consumir sin realizar una llamada al sistema bloqueante. Para el propósito de este límite, cada vez que un proceso realiza una llamada al sistema bloqueante, el recuento de su tiempo de CPU consumido se reinicia a cero. El recuento de tiempo de CPU no se reinicia si el proceso continúa intentando usar la CPU pero es desalojado, su fragmento de tiempo expira o llama a sched_yield(2).
Al alcanzar el límite suave, se envía una señal SIGXCPU al proceso. Si el proceso captura o ignora esta señal y continúa consumiendo tiempo de CPU, entonces se generará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se enviará una señal SIGKILL al proceso.
El uso previsto de este límite es detener un proceso en tiempo real descontrolado de bloquear el sistema.
Para más detalles sobre las políticas de planificación en tiempo real, ver sched(7)
RLIMIT_SIGPENDING (desde Linux 2.6.8)
Este es un límite en el número de señales que pueden estar en cola para el ID de usuario real del proceso que llama. Tanto las señales estándar como las de tiempo real se cuentan para el propósito de verificar este límite. Sin embargo, el límite solo se aplica a sigqueue(3); siempre es posible usar kill(2) para poner en cola una instancia de cualquiera de las señales que no estén ya en cola para el proceso.
RLIMIT_STACK
Este es el tamaño máximo de la pila del proceso, en bytes. Al alcanzar este límite, se genera una señal SIGSEGV. Para manejar esta señal, un proceso debe emplear una pila de señales alternativa (sigaltstack(2)).
Desde Linux 2.6.23, este límite también determina la cantidad de espacio utilizada para los argumentos de línea de comandos y las variables de entorno del proceso; para detalles, ver execve(2).

prlimit()

La llamada al sistema específica de Linux prlimit() combina y extiende la funcionalidad de setrlimit() y getrlimit(). Puede usarse tanto para establecer como para obtener los límites de recursos de un proceso arbitrario.

El argumento resource tiene el mismo significado que para setrlimit() y getrlimit().

Si el argumento new_limit no es NULL, entonces la estructura rlimit a la que apunta se utiliza para establecer nuevos valores para los límites suave y duro para resource. Si el argumento old_limit no es NULL, entonces una llamada exitosa a prlimit() coloca los límites suave y duro anteriores para resource en la estructura rlimit apuntada por old_limit.

El argumento pid especifica el ID del proceso sobre el cual se va a operar. Si pid es 0, entonces la llamada se aplica al proceso que llama. Para establecer o obtener los recursos de un proceso distinto de sí mismo, el llamador debe tener la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario del proceso cuyos límites de recursos se están modificando, o los IDs de usuario real, efectivo y de conjunto guardado del proceso de destino deben coincidir con el ID de usuario real del llamador *y* los IDs de grupo real, efectivo y de conjunto guardado del proceso de destino deben coincidir con el ID de grupo real del llamador.

VALOR DE RETORNO

En caso de éxito, estas llamadas al sistema devuelven 0. En caso de error, se devuelve -1, y errno se establece para indicar el error.

ERRORES

EFAULT
Un argumento de puntero apunta a una ubicación fuera del espacio de direcciones accesible.
EINVAL
El valor especificado en resource no es válido; o, para setrlimit() o prlimit(): rlim->rlim_cur era mayor que rlim->rlim_max.
EPERM
Un proceso no privilegiado intentó aumentar el límite duro; la capacidad CAP_SYS_RESOURCE es necesaria para hacer esto.
EPERM
El llamador intentó aumentar el límite duro RLIMIT_NOFILE por encima del máximo definido por /proc/sys/fs/nr_open (ver proc(5))
EPERM
(prlimit()) El proceso que llama no tenía permiso para establecer límites para el proceso especificado por pid.
ESRCH
No se pudo encontrar un proceso con el ID especificado en pid.

NOTAS

Un proceso hijo creado a través de fork(2) hereda los límites de recursos de su padre. Los límites de recursos se conservan a través de execve(2).

Los límites de recursos son atributos por proceso que son compartidos por todos los hilos de un proceso.

Reducir el límite suave para un recurso por debajo del consumo actual del proceso de ese recurso tendrá éxito (pero impedirá que el proceso aumente aún más su consumo del recurso).

Se pueden establecer los límites de recursos del shell usando el comando incorporado ulimit (limit en csh(1)). Los límites de recursos del shell son heredados por los procesos que crea para ejecutar comandos.

Desde Linux 2.6.24, los límites de recursos de cualquier proceso pueden ser inspeccionados a través de /proc/pid/limits; ver proc(5).

Sistemas antiguos proporcionaban una función vlimit() con un propósito similar a setrlimit(). Para compatibilidad retroactiva, glibc

prlimit64(2) — Linux manual pages

NAME

prlimit64 — adjust and examine resource limits

LIBRARY

Linux User API (libc, version 2.10)

SYNOPSIS

#define _GNU_SOURCE /* See feature_test_macros(7) */
int prlimit64(pid_t pid, int resource,
               const struct rlimit64 *new_rlim,
               struct rlimit64 *old_rlim);

DESCRIPTION

The prlimit64() function retrieves and optionally modifies the resource limits of a process specified by pid. The resource argument specifies the resource to be acted upon; see getrlimit(2) for a list of the available resources.

The behavior of prlimit64() depends on the values of the arguments:

  • If both new_rlim and old_rlim are non-NULL, then the current limit for the specified resource is set to the value in new_rlim->rlim_cur, and the soft limit is set to new_rlim->rlim_max. The previous limit is stored in the location pointed to by old_rlim.
  • If new_rlim is NULL, then old_rlim must be non-NULL, and the current limit for the specified resource is retrieved and stored in the location pointed to by old_rlim. No changes are made to the process's limits.
  • If new_rlim is non-NULL and old_rlim is NULL, then the current limit for the specified resource is set to the values in new_rlim->rlim_cur and new_rlim->rlim_max. The previous limit is not retrieved.

The structure struct rlimit64 is defined as:

typedef uint64_t rlim64_t;

struct rlimit64 {
    rlim64_t rlim_cur; /* Current (soft) limit */
    rlim64_t rlim_max; /* Hard limit */
};

The pid argument specifies the process ID of the target process. If pid is 0, the limits of the calling process are modified.

A privileged process (on Linux, one with the CAP_SYS_RESOURCE capability) can set or retrieve the limits for any process. Unprivileged processes can only set or retrieve the limits for processes that are their own descendants (but see prlimit(1) for a note about setuid programs). An unprivileged process can only decrease the hard limit; it cannot increase it.

The prlimit64() function is intended to provide a way to manage resource limits for a specified process without needing to send signals to it, unlike the older setrlimit(2) and getrlimit(2) functions. It also allows explicit control over 64-bit resource limit values, which might not be properly handled by older versions of getrlimit(2) and setrlimit(2), especially on 32-bit systems.

The RLIM_INFINITY macro represents an unlimited resource.

C library/kernel ABI differences

Since glibc 2.13, the glibc getrlimit() and setrlimit() wrapper functions no longer invoke the corresponding system calls, but instead employ prlimit(), for the reasons described in BUGS.

The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

BUGS

In older Linux kernels, the SIGXCPU and SIGKILL signals delivered when a process encountered the soft and hard RLIMIT_CPU limits were delivered one (CPU) second later than they should have been. This was fixed in Linux 2.6.8.

In Linux 2.6.x kernels before Linux 2.6.17, a RLIMIT_CPU limit of 0 is wrongly treated as "no limit" (like RLIM_INFINITY). Since Linux 2.6.17, setting a limit of 0 does have an effect, but is actually treated as a limit of 1 second.

A kernel bug means that RLIMIT_RTPRIO does not work in Linux 2.6.12; the problem is fixed in Linux 2.6.13.

In Linux 2.6.12, there was an off-by-one mismatch between the priority ranges returned by getpriority(2) and RLIMIT_NICE. This had the effect that the actual ceiling for the nice value was calculated as 19 - rlim_cur. This was fixed in Linux 2.6.13.

Since Linux 2.6.12, if a process reaches its soft RLIMIT_CPU limit and has a handler installed for SIGXCPU, then, in addition to invoking the signal handler, the kernel increases the soft limit by one second. This behavior repeats if the process continues to consume CPU time, until the hard limit is reached, at which point the process is killed. Other implementations do not change the RLIMIT_CPU soft limit in this manner, and the Linux behavior is probably not standards conformant; portable applications should avoid relying on this Linux-specific behavior. The Linux-specific RLIMIT_RTTIME limit exhibits the same behavior when the soft limit is encountered.

Kernels before Linux 2.4.22 did not diagnose the error EINVAL for setrlimit() when rlim->rlim_cur was greater than rlim->rlim_max.

Linux doesn't return an error when an attempt to set RLIMIT_CPU has failed, for compatibility reasons.

Representation of "large" resource limit values on 32-bit platforms

The glibc getrlimit() and setrlimit() wrapper functions use a 64-bit rlim_t data type, even on 32-bit platforms. However, the rlim_t data type used in the getrlimit() and setrlimit() system calls is a (32-bit) unsigned long. Furthermore, in Linux, the kernel represents resource limits on 32-bit platforms as unsigned long. However, a 32-bit data type is not wide enough. The most pertinent limit here is RLIMIT_FSIZE, which specifies the maximum size to which a file can grow: to be useful, this limit must be represented using a type that is as wide as the type used to represent file offsets—that is, as wide as a 64-bit off_t (assuming a program compiled with _FILE_OFFSET_BITS=64).

To work around this kernel limitation, if a program tried to set a resource limit to a value larger than can be represented in a 32-bit unsigned long, then the glibc setrlimit() wrapper function silently converted the limit value to RLIM_INFINITY. In other words, the requested resource limit setting was silently ignored.

Since glibc 2.13, glibc works around the limitations of the getrlimit() and setrlimit() system calls by implementing setrlimit() and getrlimit() as wrapper functions that call prlimit().

EXAMPLES

The program below demonstrates the use of prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Usage: %s <pid> [<new-soft-limit> "
                "<new-hard-limit>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID of target process */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Set CPU time limit of target process; retrieve and display
       previous limit */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Previous limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Retrieve and display new CPU time limit */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("New limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
