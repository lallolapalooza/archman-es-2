NOMBRE

pecan - Documentación de Pecan

Pecan fue creado para llenar un vacío en el mundo de los frameworks web de Python: un framework muy ligero que proporciona enrutamiento de estilo de despacho de objetos. Pecan no pretende ser un framework de "pila completa", y por lo tanto no incluye soporte integrado para cosas como sesiones o bases de datos (aunque se incluyen tutoriales para integrar estos fácilmente en solo unas pocas líneas de código). Pecan se enfoca en HTTP.

Aunque es ligero, Pecan ofrece un conjunto de características extensas para construir aplicaciones basadas en HTTP, incluyendo:

  • Despacho de objetos para un enrutamiento fácil
  • Soporte completo para controladores de estilo REST
  • Framework de seguridad extensible
  • Soporte extensible para lenguajes de plantillas
  • Soporte extensible para JSON
  • Configuración fácil basada en Python

INSTALACIÓN

Versión Estable

$ virtualenv pecan-env
$ cd pecan-env
$ source bin/activate

Los comandos anteriores crean un entorno virtual y lo activan. Esto aislará las instalaciones de dependencias de Pecan de los paquetes de tu sistema, facilitando la depuración de problemas si es necesario.

A continuación, instalemos Pecan:

$ pip install pecan

Versión de Desarrollo (Inestable)

Si quieres ejecutar la última versión de desarrollo de Pecan, necesitarás instalar git y clonar el repositorio de GitHub:

$ git clone https://github.com/pecan/pecan.git

Suponiendo que tu entorno virtual todavía está activado, llama a setup.py para instalar la versión de desarrollo:

$ cd pecan
$ python setup.py develop

NOTA:

La rama de desarrollo master es volátil y generalmente no se recomienda para uso en producción.

Alternativamente, también puedes instalar directamente desde GitHub con pip:

$ pip install -e git://github.com/pecan/pecan.git#egg=pecan

La Raíz de la Aplicación

El Controlador Raíz es el punto de entrada de su aplicación. Puede pensarlo como análogo a la ruta URL raíz de su aplicación (en nuestro caso, http://localhost:8080/).

Así es como se ve en la plantilla del proyecto (test_project.controllers.root.RootController):

from pecan import expose
from webob.exc import status_map
class RootController(object):
    @expose(generic=True, template='index.html')
    def index(self):
        return dict()
    @index.when(method='POST')
    def index_post(self, q):
        redirect('https://pecan.readthedocs.io/en/latest/search.html?q=%s' % q)
    @expose('error.html')
    def error(self, status):
        try:
            status = int(status)
        except ValueError:
            status = 0
        message = getattr(status_map.get(status), 'explanation', '')
        return dict(status=status, message=message)

Puede especificar clases y métodos adicionales si necesita hacerlo, pero por ahora, examinemos el proyecto de ejemplo, controlador por controlador:

@expose(generic=True, template='index.html')
def index(self):
    return dict()

El método index() está marcado como *públicamente disponible* a través del decorador expose() (que a su vez utiliza la plantilla index.html) en la raíz de la aplicación (http://127.0.0.1:8080/), por lo que cualquier solicitud HTTP GET que llegue a la raíz de su aplicación (/) se dirigirá a este método.

Observe que el método index() devuelve un diccionario de Python. Este diccionario se utiliza como un espacio de nombres para renderizar la plantilla especificada (index.html) a HTML, y es el principal mecanismo por el cual los datos se pasan del controlador a la plantilla.

@index.when(method='POST')
def index_post(self, q):
    redirect('https://pecan.readthedocs.io/en/latest/search.html?q=%s' % q)

El método index_post() recibe un argumento HTTP POST (q). Dado que el argumento method para @index.when() se ha establecido en 'POST', cualquier solicitud HTTP POST a la raíz de la aplicación (en el proyecto de ejemplo, el envío de un formulario) se dirigirá a este método.

@expose('error.html')
def error(self, status):
    try:
        status = int(status)
    except ValueError:
        status = 0
    message = getattr(status_map.get(status), 'explanation', '')
    return dict(status=status, message=message)

Finalmente, tenemos el método error(), que permite a la aplicación mostrar páginas personalizadas para ciertos errores HTTP (404, etc...).

CONTROLADORES Y ENRUTAMIENTO

Pecan utiliza una estrategia de enrutamiento conocida como object-dispatch para mapear una solicitud HTTP a un controlador y luego al método a llamar. Object-dispatch comienza dividiendo la ruta en una lista de componentes y luego recorre una ruta de objetos, comenzando en el controlador raíz. Puede imaginar los controladores de su aplicación como un árbol de objetos (las ramas del árbol de objetos se mapean directamente a las rutas de URL).

Veamos una simple aplicación de librería:

from pecan import expose
class BooksController(object):
    @expose()
    def index(self):
        return "Welcome to book section."
    @expose()
    def bestsellers(self):
        return "We have 5 books in the top 10."
class CatalogController(object):
    @expose()
    def index(self):
        return "Welcome to the catalog."
    books = BooksController()
class RootController(object):
    @expose()
    def index(self):
        return "Welcome to store.example.com!"
    @expose()
    def hours(self):
        return "Open 24/7 on the web."
    catalog = CatalogController()

Una solicitud de /catalog/books/bestsellers de la tienda en línea comenzaría con Pecan dividiendo la solicitud en catalog, books y bestsellers. Luego, Pecan buscaría catalog en el controlador raíz. Usando el objeto catalog, Pecan buscaría entonces books, seguido de bestsellers. ¿Qué pasa si la URL termina en una barra? Pecan buscará un método index en el último objeto controlador.

Para ilustrarlo aún más, las siguientes rutas:

└── /
    ├── /hours
    └── /catalog
         └── /catalog/books
            └── /catalog/books/bestsellers

se enrutan a los siguientes métodos del controlador:

└── RootController.index
    ├── RootController.hours
    └── CatalogController.index
         └── BooksController.index
            └── BooksController.bestsellers

Exponiendo Controladores

Usted le dice a Pecan qué métodos en una clase son visibles públicamente a través de expose(). Si un método no está decorado con expose(), Pecan nunca dirigirá una solicitud a él.

expose() se puede usar de diversas maneras. El caso más simple implica no pasar ningún argumento. En este escenario, el controlador devuelve una cadena que representa el cuerpo de la respuesta HTML.

from pecan import expose
class RootController(object):
    @expose()
    def hello(self):
        return 'Hello World'

Un caso de uso más común es especificar una plantilla y un espacio de nombres:

from pecan import expose
class RootController(object):
    @expose('html_template.mako')
    def hello(self):
        return {'msg': 'Hello!'}
<!-- html_template.mako -->
<html>
    <body>${msg}</body>
</html>

Pecan también tiene soporte incorporado para un renderizador JSON especial, que traduce los espacios de nombres de plantillas en texto renderizado JSON:

from pecan import expose
class RootController(object):
    @expose('json')
    def hello(self):
        return {'msg': 'Hello!'}

Las llamadas a expose() también se pueden apilar, lo que le permite serializar el contenido de manera diferente según cómo se solicite el contenido:

from pecan import expose
class RootController(object):
    @expose('json')
    @expose('text_template.mako', content_type='text/plain')
    @expose('html_template.mako')
    def hello(self):
        return {'msg': 'Hello!'}

Notará que llamamos a expose() tres veces, con argumentos diferentes.

@expose('json')

El primero le dice a Pecan que serialice el espacio de nombres de la respuesta utilizando la serialización JSON cuando el cliente solicite /hello.json o si hay presente una cabecera Accept: application/json.

@expose('text_template.mako', content_type='text/plain')

El segundo le dice a Pecan que use el archivo de plantilla text_template.mako cuando

el cliente solicita /hello.txt o solicita text/plain a través de una cabecera Accept.

@expose('html_template.mako')

El tercero indica a Pecan que utilice el archivo de plantilla html_template.mako cuando el cliente solicite /hello.html. Si el cliente solicita /hello, Pecan utilizará el tipo de contenido text/html por defecto; en ausencia de un tipo de contenido explícito, Pecan asume que el cliente desea HTML.

Especificar segmentos de ruta explícitos

Ocasionalmente, puede que desee utilizar un segmento de ruta en su enrutamiento que no funcione con el enfoque declarativo de enrutamiento de Pecan debido a restricciones en la sintaxis de Python. Por ejemplo, si quisiera enrutar para una ruta que incluye guiones, como /some-path/, lo siguiente *no* es Python válido:

class RootController(object):
    @pecan.expose()
    def some-path(self):
        return dict()

Para solucionar esto, Pecan le permite especificar un segmento de ruta explícito en el decorador expose():

class RootController(object):
    @pecan.expose(route='some-path')
    def some_path(self):
        return dict()

En este ejemplo, la aplicación Pecan responderá con un HTTP 200 para las solicitudes realizadas a /some-path/, pero las solicitudes realizadas a /some_path/ generarán un HTTP 404.

route() también se puede utilizar explícitamente como una alternativa al argumento route en expose():

class RootController(object):
    @pecan.expose()
    def some_path(self):
        return dict()
pecan.route('some-path', RootController.some_path)

El enrutamiento a subcontroladores se puede manejar de manera similar utilizando route():

class ChildController(object):
    @pecan.expose()
    def child(self):
        return dict()
class RootController(object):
    pass
pecan.route(RootController, 'child-path', ChildController())

En este ejemplo, la aplicación Pecan responderá con un HTTP 200 para las solicitudes realizadas a /child-path/child/.

Enrutamiento basado en el método de solicitud

El argumento generic de expose() proporciona soporte para sobrecargar URLs basándose en el método de solicitud. En el siguiente ejemplo, la misma URL puede ser atendida por dos métodos diferentes (uno para manejar HTTP GET, otro para HTTP POST) utilizando controladores genéricos:

from pecan import expose
class RootController(object):
    # HTTP GET /
    @expose(generic=True, template='json')
    def index(self):
        return dict()
    # HTTP POST /
    @index.when(method='POST', template='json')
    def index_POST(self, **kw):
        uuid = create_something()
        return dict(uuid=uuid)

Algoritmo de enrutamiento de Pecan

A veces, el enrutamiento estándar de despacho de objetos no es suficiente para enrutar correctamente una URL a un controlador. Pecan proporciona varias formas de cortocircuitar el sistema de despacho de objetos para procesar URLs con más control, incluyendo los métodos especiales _lookup(), _default() y _route(). Definir estos métodos en sus objetos controladores proporciona flexibilidad adicional para procesar todo o parte de una URL.

Enrutamiento a subcontroladores con _lookup

El método especial _lookup() proporciona una forma de procesar una porción de una URL y luego devolver un nuevo objeto controlador al que enrutar para el resto.

Un método _lookup() puede aceptar uno o más argumentos, segmentos de la ruta de la URL a procesar (divididos por /). _lookup() también debe aceptar argumentos posicionales variables que representen el resto de la ruta, y debe incluir cualquier porción de la ruta que no procese en su valor de retorno. El siguiente ejemplo utiliza una lista *remainder* que se pasará al controlador devuelto cuando el algoritmo de despacho de objetos continúe.

Además de ser utilizado para crear controladores dinámicamente, _lookup() se llama como último recurso, cuando ningún otro método controlador coincide con la URL y no hay ningún método _default().

from pecan import expose, abort
from somelib import get_student_by_name
class StudentController(object):
    def __init__(self, student):
        self.student = student
    @expose()
    def name(self):
        return self.student.name
class RootController(object):
    @expose()
    def _lookup(self, primary_key, *remainder):
        student = get_student_by_primary_key(primary_key)
        if student:
            return StudentController(student), remainder
        else:
            abort(404)

Una solicitud GET HTTP a /8/name devolvería el nombre del estudiante donde primary_key == 8.

Recurrir con _default

El método _default() se llama como último recurso cuando ningún otro método controlador coincide con la URL a través del despacho de objetos estándar.

from pecan import expose
class RootController(object):
    @expose()
    def english(self):
        return 'hello'
    @expose()
    def french(self):
        return 'bonjour'
    @expose()
    def _default(self):
        return 'I cannot say hello in that language'

En el ejemplo anterior, una solicitud a /spanish se enrutaría a RootController._default().

Definir enrutamiento personalizado con _route

El método _route() permite a un controlador anular completamente el mecanismo de enrutamiento de Pecan. El propio Pecan utiliza el método _route() para implementar su RestController. Si desea diseñar un sistema de enrutamiento alternativo sobre Pecan, definir una clase base controladora que defina un método _route() le permitirá tener un control total.

Interactuar con los objetos de solicitud y respuesta

Para cada solicitud HTTP, Pecan mantiene una referencia local al hilo al objeto de solicitud y respuesta, pecan.request y pecan.response. Estas son instancias de pecan.Request y pecan.Response, respectivamente, y se puede interactuar con ellas desde el código del controlador de Pecan:

@pecan.expose()
def login(self):
    assert pecan.request.path == '/login'
    username = pecan.request.POST.get('username')
    password = pecan.request.POST.get('password')
    pecan.response.status = 403
    pecan.response.text = 'Bad Login!'

Si bien Pecan abstrae gran parte de la necesidad de interactuar con estos objetos directamente, puede haber situaciones en las que desee acceder a ellos, como por ejemplo:

  • Inspeccionar componentes de la URI
  • Determinar aspectos de la solicitud, como la dirección IP del usuario o la cabecera referer
  • Establecer cabeceras de respuesta específicas
  • Renderizar manualmente un cuerpo de respuesta

Especificar una respuesta personalizada

Establezca un código de respuesta HTTP específico (como 203 Información no autorizada) modificando el atributo status del objeto de respuesta.

from pecan import expose, response
class RootController(object):
    @expose('json')
    def hello(self):
        response.status = 203
        return {'foo': 'bar'}

Utilice la función de utilidad abort() para generar errores HTTP.

from pecan import expose, abort
class RootController(object):
    @expose('json')
    def hello(self):
        abort(404)

abort() genera una instancia de WSGIHTTPException que es utilizada por Pecan para renderizar cuerpos de respuesta por defecto para errores HTTP. Esta excepción se almacena en el entorno de solicitud WSGI en pecan.original_exception, donde se puede acceder más tarde en el ciclo de solicitud (por ejemplo, por otro middleware o por Documentos de Error Personalizados).

Si desea devolver una respuesta explícita, puede hacerlo usando Response:

from pecan import expose, Response
class RootController(object):
    @expose()
    def hello(self):
        return Response('Hello, World!', 202)

Extender los objetos de solicitud y respuesta de Pecan

Las implementaciones de solicitud y respuesta proporcionadas por WebOb son potentes, pero a veces puede ser útil extender el comportamiento específico de la aplicación a su solicitud y respuesta (como el análisis especializado de las cabeceras de solicitud o la serialización personalizada del cuerpo de respuesta). Para ello, defina clases personalizadas que hereden de pecan.Request y pecan.Response, respectivamente:

class MyRequest(pecan.Request):
    pass
class MyResponse(pecan.Response):
    pass

y modifique la configuración de su aplicación para utilizarlas:

from myproject import MyRequest, MyResponse
app = {
    'root' : 'project.controllers.root.RootController',
    'modules' : ['project'],
    'static_root'   : '%(confdir)s/public',
    'template_path' : '%(confdir)s/project/templates',
    'request_cls': MyRequest,
    'response_cls': MyResponse
}

CONTROLADORES Y ENRUTAMIENTO

Mapeo de Argumentos del Controlador

En Pecan, las variables HTTP GET y POST que no se consumen durante el proceso de enrutamiento pueden pasarse al método del controlador como argumentos.

Dependiendo de la firma del método, estos argumentos pueden mapearse explícitamente a argumentos:

from pecan import expose
class RootController(object):
    @expose()
    def index(self, arg):
        return arg
    @expose()
    def kwargs(self, **kwargs):
        return str(kwargs)
$ curl http://localhost:8080/?arg=foo
foo
$ curl http://localhost:8080/kwargs?a=1&b=2&c=3
{u'a': u'1', u'c': u'3', u'b': u'2'}

o pueden consumirse posicionalmente:

from pecan import expose
class RootController(object):
    @expose()
    def args(self, *args):
        return ','.join(args)
$ curl http://localhost:8080/args/one/two/three
one,two,three

El mismo efecto se puede lograr con variables del cuerpo HTTP POST:

from pecan import expose
class RootController(object):
    @expose()
    def index(self, arg):
        return arg
$ curl -X POST "http://localhost:8080/" -H "Content-Type: application/x-www-form-urlencoded" -d "arg=foo"
foo

Servicio de Archivos Estáticos

Dado que Pecan le brinda acceso directo a la Request subyacente, servir una descarga de archivo estático es tan simple como configurar el app_iter de WSGI y especificar el tipo de contenido:

import os
from random import choice
from webob.static import FileIter
from pecan import expose, response
class RootController(object):
    @expose(content_type='image/gif')
    def gifs(self):
        filepath = choice((
            "/path/to/funny/gifs/catdance.gif",
            "/path/to/funny/gifs/babydance.gif",
            "/path/to/funny/gifs/putindance.gif"
        ))
        f = open(filepath, 'rb')
        response.app_iter = FileIter(f)
        response.headers[
            'Content-Disposition'
        ] = 'attachment; filename="%s"' % os.path.basename(f.name)

Si no conoce el tipo de contenido con anticipación (por ejemplo, si recupera archivos y sus tipos de contenido de un almacén de datos), puede especificarlo a través de response.headers en lugar de en el decorador expose():

import os
from mimetypes import guess_type
from webob.static import FileIter

Determinación de la URL de un Controlador

Dada la capacidad de cambiar drásticamente el enrutamiento en tiempo de ejecución, no siempre es posible determinar correctamente una correspondencia entre un método de controlador y una URL.

Por ejemplo, en el siguiente código que utiliza _lookup() para alterar el enrutamiento según una condición:

from pecan import expose, abort
from somelib import get_user_region
class DefaultRegionController(object):
    @expose()
    def name(self):
        return "Default Region"
class USRegionController(object):
    @expose()
    def name(self):
        return "US Region"
class RootController(object):
    @expose()
    def _lookup(self, user_id, *remainder):
        if get_user_region(user_id) == 'us':
            return USRegionController(), remainder
        else:
            return DefaultRegionController(), remainder

Esta lógica depende de la geolocalización de un usuario determinado y devuelve una clase completamente diferente según la condición. Un auxiliar para determinar a qué URL pertenece USRegionController.name fallaría en hacerlo correctamente.

ESCRITURA DE SERVICIOS WEB RESTFUL CON CONTROLADORES GENÉRICOS

Pecan simplifica los servicios web RESTful proporcionando una forma de sobrecargar las URLs basándose en el método de la petición. Para la mayoría de las API, el uso de definiciones de controlador genérico te da todo lo que necesitas para construir interfaces RESTful robustas (y es el enfoque *recomendado* para escribir servicios web RESTful en pecan):

from pecan import expose
from pecan.rest import RestController
from mymodel import Book
class BooksController(RestController):
    @expose()
    def get(self, id):
        book = Book.get(id)
        if not book:
            abort(404)
        return book.title

Mapeo de URLs

Por defecto, RestController enruta de la siguiente manera:

Método Descripción Ejemplo(s) de Método(s) / URL(s)
get_one Muestra un registro. GET /books/1
get_all Muestra todos los registros de un recurso. GET /books/
get Una combinación de get_one y get_all. GET /books/
GET /books/1
new Muestra una página para crear un nuevo recurso. GET /books/new
edit Muestra una página para editar un recurso existente. GET /books/1/edit
post Crea un nuevo registro. POST /books/
put Actualiza un registro existente. POST /books/1?_method=put
PUT /books/1
get_delete Muestra una página de confirmación de eliminación. GET /books/1/delete
delete Elimina un registro existente. POST /books/1?_method=delete
DELETE /books/1

El RestController de Pecan usa la cadena de consulta ?_method= para solucionar la falta de soporte para los verbos PUT y DELETE al enviar formularios en la mayoría de los navegadores actuales.

Además de manejar REST, el RestController también soporta las anulaciones de enrutamiento index(), _default() y _lookup().

ADVERTENCIA:

Si necesitas anular _route(), asegúrate de llamar a RestController._route() al final de tu método personalizado para que el enrutamiento REST descrito anteriormente siga ocurriendo.

Anidación de RestController

Las instancias de RestController pueden anidarse para que los recursos hijos reciban los parámetros necesarios para buscar los recursos padre.

Por ejemplo:

from pecan import expose
from pecan.rest import RestController
from mymodel import Author, Book
class BooksController(RestController):
    @expose()
    def get(self, author_id, id):
        author = Author.get(author_id)
        if not author_id:
            abort(404)
        book = author.get_book(id)
        if not book:
            abort(404)
        return book.title
class AuthorsController(RestController):
    books = BooksController()
    @expose()
    def get(self, id):
        author = Author.get(id)
        if not author:
            abort(404)
        return author.name
class RootController(object):
    authors = AuthorsController()

Acceder a /authors/1/books/2 invoca BooksController.get() con author_id establecido a 1 y id establecido a 2.

Para determinar qué argumentos están asociados con el recurso padre, Pecan mira las firmas de los métodos get_one() y luego get(), en ese orden, en el controlador padre. Si el recurso padre toma un número variable de argumentos, Pecan le pasará todo hasta el nombre del controlador del recurso hijo (por ejemplo, books en el ejemplo anterior).

Definición de Acciones Personalizadas

Además de los métodos por defecto definidos anteriormente, puedes añadir comportamientos adicionales a un RestController definiendo un diccionario especial _custom_actions.

Por ejemplo:

from pecan import expose
from pecan.rest import RestController
from mymodel import Book
class BooksController(RestController):
    _custom_actions = {
        'checkout': ['POST']
    }
    @expose()
    def checkout(self, id):
        book = Book.get(id)
        if not book:
            abort(404)
        book.checkout()

_custom_actions mapea los nombres de los métodos a la lista de verbos HTTP válidos para esas acciones personalizadas. En este caso checkout() soporta POST.

CONFIGURACIÓN DE APLICACIONES PECAN

Pecan es muy fácil de configurar. Siempre que sigas ciertas convenciones, usar, configurar y tratar con la configuración debería ser muy intuitivo.

Los archivos de configuración de Pecan son Python puro. Cada "sección" de la configuración es un diccionario asignado a un nombre de variable en el módulo de configuración.

Valores Predeterminados

A continuación se muestra la lista completa de valores predeterminados que utiliza el framework:

Una configuración de aplicación típica podría verse así:

    'root' : 'proyecto.controladores.raiz.ControladorRaiz',
    'modules' : ['proyecto'],
    'static_root'   : '%(confdir)s/publico',
    'template_path' : '%(confdir)s/proyecto/plantillas',
    'debug' : True
}

Analicemos cada valor y su significado:

módulos
Una lista de módulos donde Pecan buscará aplicaciones. Generalmente, esto debería contener un solo elemento, el nombre del paquete de Python de tu proyecto. Al menos uno de los módulos listados debe contener una función app.setup_app que se llama para crear la aplicación WSGI. En otras palabras, este paquete debe ser donde se encuentra tu archivo app.py, y este archivo debe contener una función setup_app.
raíz
El controlador raíz de tu aplicación. Recuerda proporcionar una cadena que represente una ruta de Python a algún llamable (por ejemplo, "tua_app.controladores.raiz.ControladorRaiz").
raíz_estática
El directorio donde se pueden encontrar tus archivos estáticos (relativo a la raíz del proyecto). Pecan viene con middleware que se puede usar para servir archivos estáticos (como archivos CSS y Javascript) durante el desarrollo.
ruta_plantillas
Apunt a al directorio donde residen tus archivos de plantilla (relativo a la raíz del proyecto).
depuración
Habilita la capacidad de mostrar seguimientos de pila en el navegador y depurar interactivamente durante el desarrollo.

Pecan no proporciona soporte predeterminado para la autenticación, pero te da las herramientas necesarias para manejar la autenticación y autorización según lo consideres conveniente.

Básicos del Decorador secure

Puedes envolver subárboles de controladores completos o llamadas a métodos individuales con controles de acceso utilizando el decorador secure().

Para decorar un método, usa un argumento:

secure('<nombre_método_verificar_permisos>')

Para asegurar una clase, invoca con dos argumentos:

secure(instancia_objeto, '<nombre_método_verificar_permisos>')

desde pecan.secure importar secure
clase ControladorAltamenteClasificado(objeto):
    pasar
clase ControladorNoClasificado(objeto):
    pasar
clase ControladorRaiz(objeto):
    @classmethod
    def verificar_permisos(cls):
        if usuario_es_admin():
            return True
        return False
    @exponer()
    def index(self):
      #
      # Este controlador está desbloqueado para todos,
      # y no ejecutará ninguna verificación de seguridad.
      #
      return dict()

Más sobre secure

El método secure() tiene varios usos avanzados que te permiten crear políticas de seguridad robustas para tu aplicación.

Primero, puedes pasar a través de una cadena el nombre de un método de clase o un método de instancia del controlador para usarlo como método check_permissions(). Los métodos de instancia son particularmente útiles si deseas autorizar el acceso a atributos de una instancia de modelo. Considera el siguiente

Ejemplo de un sistema de archivos virtual básico.

from pecan import expose
from pecan.secure import secure
from myapp.session import get_current_user
from myapp.model import FileObject
class FileController(object):
    def __init__(self, name):
        self.file_object = FileObject(name)
    def read_access(self):
        self.file_object.read_access(get_current_user())
    def write_access(self):
        self.file_object.write_access(get_current_user())
    @secure('write_access')
    @expose()
    def upload_file(self):
        pass
    @secure('read_access')
    @expose()
    def download_file(self):
        pass
class RootController(object):
    @expose()
    def _lookup(self, name, *remainder):
        return FileController(name), remainder

El método secure() también acepta un argumento de función. Al pasar una función, asegúrate de que la función se importe de otro archivo o se defina en el mismo archivo antes de la definición de la clase, de lo contrario, probablemente obtendrás un error durante la importación del módulo.

from pecan import expose
from pecan.secure import secure
from myapp.auth import user_authenitcated
class RootController(object):
    @secure(user_authenticated)
    @expose()
    def index(self):
        return 'Logged in'

También puedes usar el método secure() para cambiar el comportamiento de un SecureController. Decorar un método o envolver un subcontrolador le indica a Pecan que use una función de seguridad diferente a la del método del controlador predeterminado. Esto es útil para situaciones en las que deseas un nivel o tipo de seguridad diferente.

from pecan import expose
from pecan.secure import SecureController, secure
from myapp.auth import user_authenticated, admin_user
class ApiController(object):
    pass
class RootController(SecureController):
    @classmethod
    def check_permissions(cls):
        return user_authenticated()
    @classmethod
    def check_api_permissions(cls):
        return admin_user()
    @expose()
    def index(self):
        return 'logged in user'
    api = secure(ApiController(), 'check_api_permissions')

En el ejemplo anterior, Pecan llamará solamente a admin_user() cuando se realice una solicitud para /api/.

Múltiples Controladores Seguros

Los controladores seguros se pueden anidar para proporcionar niveles crecientes de seguridad en los subcontroladores. En el siguiente ejemplo, cuando se realiza una solicitud para /admin/index/, Pecan primero llama a check_permissions() en el RootController y luego llama a check_permissions() en el AdminController.

from pecan import expose
from pecan.secure import SecureController
from myapp.auth import user_logged_in, is_admin
class AdminController(SecureController):
    @classmethod
    def check_permissions(cls):
        return is_admin()
    @expose()
    def index(self):
        return 'admin dashboard'
class RootController(SecureController):
    @classmethod
    def check_permissions(cls):
        return user_logged_in
    @expose()
    def index(self):
        return 'user dashboard'

GANCHOS DE PECAN

Aunque es fácil usar middleware WSGI con Pecan, puede ser difícil (a veces imposible) tener acceso a los internos de Pecan desde el middleware. Los ganchos de Pecan son una forma de interactuar con el framework, sin tener que escribir middleware separado.

Los ganchos te permiten ejecutar código en puntos clave durante el ciclo de vida de tu solicitud:

  • on_route(): se llama antes de que Pecan intente enrutar una solicitud a un controlador
  • before(): se llama después del enrutamiento, pero antes de que se ejecute el código del controlador
  • after(): se llama después de que se haya ejecutado el código del controlador
  • on_error(): se llama cuando una solicitud genera una excepción

Implementación de un Gancho de Pecan

En el siguiente ejemplo, un gancho simple recopilará información sobre la solicitud y la imprimirá en stdout.

Tu implementación de gancho necesita importar PecanHook para poder usarlo como clase base. A partir de ahí, querrás sobrescribir los métodos on_route(), before(), after() u on_error() para definir el comportamiento.

from pecan.hooks import PecanHook
class SimpleHook(PecanHook):
    def before(self, state):
        print "\nabout to enter the controller..."
    def after(self, state):
        print "\nmethod: \t %s" % state.request.method
        print "\nresponse: \t %s" % state.response.status

A on_route(), before() y after() se les pasa un objeto de estado compartido que incluye información útil, como los objetos de solicitud y respuesta, y qué controlador fue seleccionado por el enrutamiento de Pecan:

class SimpleHook(PecanHook):
    def on_route(self, state):
        print "\nabout to map the URL to a Python method (controller)..."
        assert state.controller is None  # Routing hasn't occurred yet
        assert isinstance(state.request, webob.Request)
        assert isinstance(state.response, webob.Response)
        assert isinstance(state.hooks, list)  # A list of hooks to apply
    def before(self, state):
        print "\nabout to enter the controller..."
        if state.request.path == '/':
            #
            # `state.controller` is a reference to the actual
            # `@pecan.expose()`-ed controller that will be routed to
            # and used to generate the response body
            #
            assert state.controller.__func__ is RootController.index.__func__
            assert isinstance(state.arguments, inspect.Arguments)
            print state.arguments.args
            print state.arguments.varargs
            print state.arguments.keywords
        assert isinstance(state.request, webob.Request)
        assert isinstance(state.response, webob.Response)
        assert isinstance(state.hooks, list)

A on_error() se le pasa un objeto de estado compartido y la excepción original. Si un manejador de on_error() devuelve un objeto Response, esta respuesta se devolverá al usuario final y no se ejecutarán más ganchos on_error():

class CustomErrorHook(PecanHook):
    def on_error(self, state, exc):
        if isinstance(exc, SomeExceptionType):
            return webob.Response('Custom Error!', status=500)

    priority = 2

# to avoid double calls

    @expose('json')
    def index(self):
        print "\nI AM THE SUB!"
        return dict()
class RootController(HookController):
    __hooks__ = [common, ParentHook()]
    @expose('json')
    def index(self):
        print "\nI AM THE ROOT!"
        return dict()
    sub = SubController()

MANEJO DE JSON

Pecan viene con soporte incorporado para la serialización de objetos a JSON. Cuando un controlador de Pecan está configurado para retornar JSON, Pecan intentará serializar cualquier objeto que sea retornado. Por defecto, Pecan sabe cómo serializar tipos de datos estándar de Python (incluyendo objetos datetime) a JSON.

Sin embargo, si su aplicación está utilizando modelos de datos personalizados (por ejemplo, instancias de una clase ORM), deberá decirle a Pecan cómo serializar esos objetos.

Supongamos que tiene un controlador que retorna una instancia de un objeto User:

@pecan.expose('json')
def index(self):
    return get_current_user()

Para que este controlador funcione, Pecan necesitará saber cómo convertir el objeto User en tipos de datos compatibles con JSON. Una forma de decirle a Pecan cómo convertir un objeto a JSON es definir una regla en su json.py:

from pecan.jsonify import jsonify
from myproject import model
@jsonify.register(model.User)
def jsonify_user(user):
    return dict(
        name = user.name,
        email = user.email,
        birthday = user.birthday.isoformat()
    )

En este ejemplo, cuando una instancia de la clase model.User es retornada desde un controlador que está configurado para retornar JSON, la regla jsonify_user() será llamada para convertir el objeto a datos compatibles con JSON. Note que la regla no genera una cadena JSON, sino un diccionario de Python que contiene solo tipos de datos amigables para JSON.

Alternativamente, la regla puede ser especificada en el propio objeto, definiendo un método __json__() en la clase:

class User(object):
    def __init__(self, name, email, birthday):
        self.name = name
        self.email = email
        self.birthday = birthday
    def __json__(self):
        return dict(
            name = self.name,
            email = self.email,
            birthday = self.birthday.isoformat()
        )

El beneficio de usar un módulo json.py es tener todas sus reglas JSON definidas en una ubicación central, pero algunos proyectos prefieren la simplicidad de mantener las reglas JSON adjuntas directamente a sus objetos modelo.

CONTEXTO/LOCALS DE HILO VS. PASO EXPLÍCITO DE ARGUMENTOS

En cualquier aplicación Pecan, pecan.request y pecan.response a nivel de módulo son objetos proxy que siempre apuntan a la solicitud y respuesta que se está manejando en el hilo actual.

Esta localidad de hilo asegura que usted pueda acceder de forma segura a una referencia global de la solicitud y respuesta actuales en un entorno multihilo sin tener que pasar constantemente referencias de objeto en su código; es una característica de Pecan que hace que la escritura de aplicaciones web tradicionales sea más fácil y menos verbosa.

Algunas personas sienten que los locals de hilo son demasiado implícitos o mágicos, y que el paso explícito de referencias es mucho más claro y mantenible a largo plazo. Además, la implementación predeterminada proporcionada por Pecan utiliza threading.local() para asociar estos objetos proxy locales de contexto con el identificador de hilo del hilo del servidor actual. En modelos de servidor asíncronos - donde muchas tareas se ejecutan por cortos períodos de tiempo en un único hilo compartido - el soporte para este mecanismo implica el "monkeypatching" de threading.local() para que se comporte de manera local a los greenlets.

Desactivar los Proxies Locales de Hilo

Si está seguro de que no desea utilizar locals de contexto/hilo en su proyecto, puede hacerlo pasando el argumento use_context_locals=False en el archivo de configuración de su aplicación:

app = {
    'root': 'project.controllers.root.RootController',
    'modules': ['project'],
    'static_root': '%(confdir)s/public',
    'template_path': '%(confdir)s/project/templates',
    'debug': True,
    'use_context_locals': False
}

Además, deberá actualizar todos sus controladores de Pecan para que acepten argumentos posicionales para la solicitud y respuesta actuales:

class RootController(object):
    @pecan.expose('json')
    def index(self, req, resp):
        return dict(method=req.method) # path: /
    @pecan.expose()
    def greet(self, req, resp, name):
        return name  # path: /greet/joe

Es imperativo que los argumentos de solicitud y respuesta vengan después de self y antes de cualquier argumento posicional de forma.

''' arguments = pecan.commands.BaseCommand.arguments + ({ 'name': 'path', 'help': 'la ruta URI del recurso a solicitar' },) def run(self, args): super(GetCommand, self).run(args) app = TestApp(self.load_app()) print app.get(args.path).body ``` Analicemos este fragmento pieza por pieza. ## Anulación del método run Primero, estamos creando una subclase de `BaseCommand` y extendiendo el método `run()` para: * Cargar una aplicación Pecan - `load_app()` * Envolverla en un entorno falso de WSGI - [TestApp](https://docs.pylonsproject.org/projects/webtest/en/latest/api.html#webtest.app.TestApp) * Emitir una solicitud GET HTTP contra ella - [get()](https://docs.pylonsproject.org/projects/webtest/en/latest/api.html#webtest.app.TestApp.get) ## Definición de Argumentos Personalizados El atributo de clase `arguments` se utiliza para definir argumentos de línea de comandos específicos para tu comando personalizado. Notarás en este ejemplo que estamos *añadiendo* a la lista de argumentos proporcionada por `BaseCommand` (que ya proporciona un argumento para `config_file`), en lugar de anularla por completo. El formato del atributo de clase `arguments` es una [tupla](https://docs.python.org/3/library/stdtypes.html#tuple) de diccionarios, con cada diccionario representando una definición de argumento en el mismo formato aceptado por el módulo [argparse](https://docs.python.org/3/library/argparse.html#module-argparse) de Python (más específicamente, [add_argument()](https://docs.python.org/3/library/argparse.html#argparse.ArgumentParser.add_argument)). Seguir esta convención te permite integrar fácilmente un resumen para tu comando en la herramienta de línea de comandos de Pecan. ## Registro de un Comando Personalizado Ahora que has escrito tu comando personalizado, necesitarás decirle al `setup.py` de tu distribución sobre su existencia y reinstalarlo.     REGISTRO

    El registro es una parte importante de la depuración y la solución de problemas de una aplicación. Pecan utiliza el módulo de registro estándar de Python.

    Configuración del registro en Pecan

    La configuración del registro se realiza en el bloque logging de su archivo de configuración (por ejemplo, config.py).

    Pecan aplica las siguientes convenciones de registro:

    • El logger llamado myapp se utiliza para los mensajes de registro de su aplicación.
    • El logger llamado root se utiliza para los mensajes de registro generados por Pecan y sus dependencias.

    A continuación se muestra un ejemplo de configuración de registro básico:

    # myapp/config.py
# ...
logging = {
    'version': 1,
    'disable_existing_loggers': False,
    'formatters': {
        'verbose': {
            'format': '%(asctime)s %(levelname)s %(name)s %(message)s'
        },
        'simple': {
            'format': '%(levelname)s %(message)s'
        },
    },
    'handlers': {
        'console': {
            'level': 'DEBUG',
            'class': 'logging.StreamHandler',
            'formatter': 'simple'
        },
    },
    'loggers': {
        'myapp': {
            'handlers': ['console'],
            'level': 'DEBUG',
            'propagate': False,
        },
        'root': {
            'handlers': ['console'],
            'level': 'INFO',
            'propagate': False,
        }
    }
}

    Con la configuración anterior:

    • El logger myapp registra mensajes enviados a un nivel superior o igual a DEBUG en el manejador console.
    • El logger root registra mensajes a un nivel superior o igual a INFO en el manejador console.

    Escritura de mensajes de registro en su aplicación

    El logger llamado myapp está reservado para su uso en su aplicación Pecan.

    Una vez que haya configurado su registro, puede colocar llamadas de registro en su código. Usar el framework de registro es muy simple.

    • FileHandler - se utiliza para registrar mensajes en un archivo en el sistema de archivos.
    • RotatingFileHandler - similar a FileHandler, pero también rota los registros periódicamente.
    • SysLogHandler - se utiliza para registrar mensajes en un syslog de UNIX.
    • SMTPHandler - se utiliza para registrar mensajes a una dirección de correo electrónico vía SMTP.

    Usar cualquiera de ellos es tan simple como definir un nuevo manejador en el bloque logging de su aplicación y asignarlo a uno o más loggers.

    Binding Within the Application

    There are several approaches to wrapping your application's requests with calls to appropriate model function calls. One approach is WSGI middleware. We also recommend Pecan Pecan Hooks. Pecan comes with TransactionHook, a hook which can be used to wrap requests in database transactions for you. To use it, simply include it in your project's app.py file and pass it a set of functions related to database binding.

    from pecan import conf, make_app
from pecan.hooks import TransactionHook
from test_project import model
app = make_app(
    conf.app.root,
    static_root     = conf.app.static_root,
    template_path   = conf.app.template_path,
    debug           = conf.app.debug,
    hooks           = [
        TransactionHook(
            model.start,
            model.start_read_only,
            model.commit,
            model.rollback,
            model.clear
        )
    ]
)

    In the above example, on HTTP POST, PUT, and DELETE requests, TransactionHook takes care of the transaction automatically by following these rules:

    1.
    Before controller routing has been determined, model.start() is called. This function should bind to the appropriate SQLAlchemy engine and start a transaction.
    2.
    Controller code is run and returns.
    3.
    If your controller or template rendering fails and raises an exception, model.rollback() is called and the original exception is re-raised. This allows you to rollback your database transaction to avoid committing work when exceptions occur in your application code.
    4.
    If the controller returns successfully, model.commit() and model.clear() are called.

    On idempotent operations (like HTTP GET and HEAD requests), TransactionHook handles transactions following different rules.

    1.
    model.start_read_only() is called. This function should bind to your SQLAlchemy engine.
    2.
    Controller code is run and returns.
    3.
    If the controller returns successfully, model.clear() is called.

    Also note that there is a useful after_commit() decorator provided in pecan.decorators -- Pecan Decorators.

        return dict()
    @index.when(method='POST')
    def index_post(self, q):
        redirect('https://pecan.readthedocs.io/en/latest/search.html?q=%s' % q)
    ## custom handling of '404 Page Not Found' messages
    @expose('error.html')
    def notfound(self):
        return dict(status=404, message="test_project does not have this page")
    @expose('error.html')
    def error(self, status):
        try:
            status = int(status)
        except ValueError:
            status = 0
        message = getattr(status_map.get(status), 'explanation', '')
        return dict(status=status, message=message)

pecan.routing.route(*args)
Esta función se utiliza para definir una ruta explícita para un segmento de ruta.

Generalmente, solo querrás usar esto en situaciones en las que el segmento de ruta deseado no sea un nombre de variable/función válido en Python.

Por ejemplo, si quisieras poder enrutar a:

/ruta/con-guiones/

...la siguiente sintaxis de Python no es válida:

class Controller(object):
    con-guiones = SubController()

...así que en su lugar definirías la ruta explícitamente:

class Controller(object):
    pass
pecan.route(Controller, 'con-guiones', SubController())
