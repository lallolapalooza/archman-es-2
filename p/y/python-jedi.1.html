NOMBRE

jedi - Herramienta de análisis estático para Python

Jedi es una herramienta de análisis estático para Python que se utiliza típicamente en plugins de IDE/editores. Jedi se centra en la funcionalidad de autocompletado y "ir a definición". Otras características incluyen refactorización, búsqueda de código y búsqueda de referencias.

Aquí tienes un ejemplo sencillo de la funcionalidad de autocompletado:

>>> import jedi
>>> source = '''
... import json
... json.lo'''
>>> script = jedi.Script(source, path='example.py')
>>> script
<Script: 'example.py' ...>
>>> completions = script.complete(3, len('json.lo'))
>>> completions
[<Completion: load>, <Completion: loads>]
>>> print(completions[0].complete)
ad
>>> print(completions[0].name)
load

Características y Limitaciones

Las principales llamadas a la API y características de Jedi son:

  • Autocompletado: Script.complete(); también es posible que funcione en tu REPL (IPython, etc.)
  • Ir a/Inferencia de tipo: Script.goto() y Script.infer()
  • Análisis estático: Script.get_names() y Script.get_syntax_errors()
  • Refactorizaciones: Script.rename(), Script.inline(), Script.extract_variable() y Script.extract_function()
  • Búsqueda de código: Script.search() y Project.search()

Características Básicas

  • Compatibilidad con Python 3.6+
  • Ignora errores de sintaxis e indentación incorrecta
  • Puede manejar estructuras complejas de módulos/funciones/clases
  • Gran compatibilidad con virtualenv/venv
  • Funciona muy bien con las sugerencias de tipo de Python,
  • Comprende archivos stub
  • Puede inferir argumentos de función para docstrings de sphinx, epydoc y numpydoc básicos
  • Es, en general, una pieza de software muy sólida que ha sido refinada durante mucho tiempo. Los informes de errores son muy bienvenidos y generalmente se resuelven en unas pocas semanas.

Características de Python Admitidas

Jedi admite muchas de las características de Python más utilizadas:

  • builtins
  • retornos, yields, yield from
  • asignaciones de tuplas / indexación de arrays / indexación de diccionarios / desempaquetado de estrellas
  • sentencia with / manejo de excepciones
  • *args / **kwargs
  • decoradores / lambdas / clausuras
  • generadores / iteradores
  • descriptores: property / staticmethod / classmethod / descriptores personalizados
  • algunos métodos mágicos: __call__, __iter__, __next__, __get__, __getitem__, __init__
  • list.append(), set.add(), list.extend(), etc.
  • (anidaciones) de listas por comprensión / expresiones ternarias
  • importaciones relativas
  • getattr() / __getattr__ / __getattribute__
  • anotaciones de función
  • modificaciones simples/típicas de sys.path
  • comprobaciones isinstance para if/while/assert
  • paquetes de namespace (incluye pkgutil, pkg_resources y namespaces PEP420)
  • Soporte para Django / Flask / Buildout
  • Comprende fixtures de Pytest

Limitaciones

En general, el límite de Jedi es bastante alto, pero para proyectos muy grandes o código muy complejo, a veces Jedi detiene intencionalmente la inferencia de tipos para evitar colgarse durante mucho tiempo.

Además, hay algunos patrones de Python que Jedi no admite. Esto es intencional y a continuación debería estar una lista completa:

  • Metaclases arbitrarias: Algunas metaclases como enums y dataclasses se reimplementan en Jedi para hacerlas funcionar. La mayoría de las veces, los stubs son suficientes para que la inferencia de tipos funcione, incluso cuando las metaclases están involucradas.
  • setattr(), __import__()
  • Escritura en algunos diccionarios: globals(), locals(), object.__dict__
  • Manipulaciones de instancias fuera de las variables de instancia sin usar métodos

Problemas de Rendimiento

Importar numpy puede ser bastante lento a veces, al igual que cargar los builtins la primera vez. Si quieres acelerar las cosas, puedes precargar librerías en Jedi, con preload_module(). Sin embargo, una vez cargadas, esto no debería ser un problema. Lo mismo ocurre con módulos enormes como PySide, wx, tensorflow, pandas, etc.

Seguridad

Para Script

La seguridad es un tema importante para Jedi. Por defecto, no se ejecuta ningún código dentro de Jedi. Siempre que escribas Python puro, todo se infiere estáticamente. Si activas load_unsafe_extensions=True para tu Project y usas módulos built-in (c_builtin), Jedi ejecutará esos módulos. Si no confías en una base de código, por favor, no actives esa opción. Podría llevar a la ejecución arbitraria de código.

Para Interpreter

Si quieres seguridad para Interpreter, no lo uses. Jedi ejecuta propiedades y, en general, no es muy cuidadoso para evitar la ejecución de código. Esto es intencional: la mayoría de la gente confía en las bases de código que ha importado, porque en ese momento una base de código maliciosa ya habría ejecutado código.

Script

class jedi.Script(code=None, *, path=None, environment=None, project=None)
Un Script es la base para autocompletar, ir a o cualquier cosa que quieras hacer con Jedi. La contraparte de esta clase es Interpreter, que trabaja con diccionarios reales y puede funcionar con una REPL. Esta clase debe usarse cuando un usuario edita código en un editor.

Puedes usar el parámetro code o path para leer un archivo. Normalmente querrás usar ambos (en un editor).

El sys.path de Script es muy personalizable:

  • Si se proporciona project con un sys_path, ese será el que se use.
  • Si se proporciona environment, se usará su sys.path (ver Environment.get_sys_path);
  • De lo contrario, sys.path coincidirá con el del entorno predeterminado de Jedi, que normalmente coincide con la ruta sys utilizada en el momento en que se importó Jedi.

La mayoría de los métodos tienen parámetros line y column. Las líneas en Jedi siempre son basadas en 1 y las columnas siempre son basadas en 0. Para evitar repeticiones, no siempre se documentan. Puedes omitir tanto la línea como la columna. Jedi entonces simplemente realizará la acción que estés llamando al final del archivo. Si solo proporcionas la línea, completará al final de esa línea.

ADVERTENCIA:

Por defecto, jedi.settings.fast_parser está habilitado, lo que significa que parso reutiliza módulos (es decir, no son inmutables). Con esta configuración, Jedi no es seguro para hilos y tampoco es seguro usar múltiples instancias de Script y sus definiciones al mismo tiempo.

Si eres un desarrollador de plugins normal, esto no debería ser un problema. Es un problema para personas que hacen cosas más complejas con Jedi.

Interpreter

class jedi.Interpreter(code, namespaces, *, project=None, **kwds)
API de Jedi para REPLs de Python.

Implementa todos los métodos que están presentes en Script también.

Además de las completaciones que hace la completación normal de REPL como str.upper, Jedi también soporta la completación de código basada en análisis estático de código. Por ejemplo, Jedi completará str().upper.

>>> from os.path import join
>>> namespace = locals()
>>> script = Interpreter('join("").up', [namespace])
>>> print(script.complete()[0].name)
upper

Todos los argumentos de palabra clave son los mismos que los argumentos para Script.

Parámetros
  • code (str) -- Código a analizar.
  • namespaces (List[dict]) -- Una lista de diccionarios de espacios de nombres como el devuelto por globals() y locals().

Proyectos

Los proyectos son una forma de manejar proyectos de Python dentro de Jedi. Para plugins más simples, es posible que no quieras lidiar con proyectos, pero si quieres darle al usuario más flexibilidad para definir rutas sys e intérpretes de Python para un proyecto, Project es la forma perfecta de permitirlo.

Los proyectos se pueden guardar en disco y cargar de nuevo, para permitir que las definiciones de proyectos se utilicen en diferentes repositorios.

Los proyectos son una forma sencilla de gestionar carpetas de Python y definir cómo Jedi realiza la resolución de importaciones. Se utiliza principalmente como parámetro para Script. Además, existen funciones para buscar en todo un proyecto.

El Núcleo de Jedi

El núcleo de Jedi consta de tres partes:

  • Analizador (Parser)
  • Inferencia de tipos de Python
  • API

La mayoría de las personas probablemente estarán interesadas en la inferencia de tipos, porque es donde ocurre toda la magia. Necesito introducir el analizador primero, porque jedi.inference lo utiliza extensamente.

Analizador (Parser)

Inferencia de tipos de código Python (inference/__init__.py)

La inferencia de tipos de código Python en Jedi se basa en tres suposiciones:

  • El código utiliza el menor número posible de efectos secundarios. Jedi comprende ciertas modificaciones de listas/tuplas/conjuntos, pero no hay garantía de que Jedi detecte todo (por ejemplo, `list.append` en diferentes módulos).
  • No se utiliza magia:
  • metaclases
  • setattr() / __import__()
  • escritura en globals(), locals(), object.__dict__
•
El programador no es un completo idiota, por ejemplo, como este :-)

El algoritmo real se basa en un principio que llamo inferencia de tipos perezosa. Dicho esto, el punto de entrada típico para el análisis estático es llamar a infer_expr_stmt. Hay una lógica separada para la autocompletación en la API, el estado de inferencia se trata de inferir una expresión.

Ahora necesitas entender qué sigue después de infer_expr_stmt. Hagamos un ejemplo:

import datetime
datetime.date.toda# <-- cursor aquí

En primer lugar, este módulo no se preocupa por la completitud. Realmente solo se preocupa por datetime.date. Al final del procedimiento, infer_expr_stmt devolverá la clase date.

Para visualizar esto (simplificado):

  • InferenceState.infer_expr_stmt no hace mucho, ya que no hay asignación.
  • Context.infer_node se encarga de resolver la ruta punteada.
  • InferenceState.find_types busca definiciones globales de `datetime`, que encuentra en la definición de una importación, escaneando el árbol de sintaxis.
  • Usando la lógica de importación, se encuentra el módulo `datetime`.
  • Ahora find_types es llamado nuevamente por infer_node para encontrar date dentro del módulo `datetime`.

Ahora, ¿qué sucedería si quisiéramos datetime.date.foo.bar? Dos llamadas más a find_types. Sin embargo, la segunda llamada se ignoraría, porque la primera no devolvería nada (no hay atributo `foo` en date).

¿Qué pasaría si la importación contuviera otra ExprStmt como esta:

from foo import bar
Date = bar.baz

Bueno... Ya lo entiendes. Simplemente otra recursión de infer_expr_stmt. Es realmente fácil. Python obviamente puede ser mucho más complicado que esto. Para entender asignaciones de tuplas, comprensiones de listas y todo lo demás, se tuvo que escribir mucho más código.

Jedi ha sido probado muy bien, así que puedes empezar a modificar el código. Es mejor escribir tu propia prueba primero para tu "nueva" característica. No tengas miedo de romper cosas. Mientras las pruebas pasen, lo más probable es que estés bien.

Debo mencionar ahora que la inferencia de tipos perezosa es realmente buena porque solo infiere lo que necesita ser inferido. Todas las sentencias y módulos que no se utilizan simplemente se ignoran.

Valores de Inferencia (inference/base_value.py)

Los Valores son los "valores" que Python devolvería. Sin embargo, los Valores son al mismo tiempo también los "valores" en los que se encuentra actualmente un usuario.

Un ValueSet se utiliza típicamente para especificar el retorno de una función o cualquier otra operación de análisis estático. En jedi, siempre hay múltiples retornos y no solo uno.

Resolución de nombres (inference/finder.py)

Búsqueda de nombres con un ámbito y nombre dados. Esto es muy central en Jedi y Python. La resolución de nombres es bastante complicada con descriptores, __getattribute__, __getattr__, global, etc.

Comprobaciones de flujo

Las comprobaciones de flujo no son realmente maduras. Solo hay una comprobación para isinstance. Comprobaría si un flujo tiene la forma de if isinstance(a, type_or_tuple). Desafortunadamente, todo lo demás se ignora (por ejemplo, sería fácil comprobar `a == ''` -> `a` es una cadena). Hay un gran potencial en estas comprobaciones.

API (api/__init__.py y api/classes.py)

Completitud de parámetros (inference/dynamic_params.py)

Una de las características realmente importantes de Jedi es tener una opción para entender código como este:

def foo(bar):
    bar. # completitud aquí
foo(1)

No hay duda de si `bar` es un int o no, pero si también hay una llamada como foo('str'), ¿qué sucedería? Bueno, simplemente mostraremos ambos. Porque eso es lo que un humano esperaría.

Funciona de la siguiente manera:

  • Jedi ve un parámetro.
  • busca llamadas a funciones llamadas foo.
  • ejecuta estas llamadas y verifica la entrada.

Docstrings (inference/docstrings.py)

Los docstrings son otra fuente de información para funciones y clases. jedi.inference.dynamic_params intenta encontrar todas las ejecuciones de funciones, mientras que el análisis de docstrings es mucho más fácil. Hay tres tipos diferentes de docstrings que Jedi entiende:

  • Sphinx
  • Epydoc
  • Numpydoc

Por ejemplo, la anotación de sphinx :type foo: str indica claramente que el tipo de foo es str.

Como complemento a la búsqueda de parámetros, este módulo también proporciona anotaciones de retorno.

Configuración

La configuración de recursión es importante si no desea que el código de Python extremadamente recursivo se vuelva completamente loco.

Los valores predeterminados se basan en experimentos mientras se completa la propia biblioteca de Jedi (¡incepción!). Pero no creo que haya ninguna otra biblioteca de Python que utilice la recursión de una manera similarmente extrema. La completación también debería ser rápida y, por lo tanto, la calidad puede no ser siempre máxima.

jedi.inference.recursion.recursion_limit = 15
Al igual que sys.getrecursionlimit(), solo para Jedi.
jedi.inference.recursion.total_function_execution_limit = 200
Este es un límite estricto de cuántas funciones no incorporadas pueden ser ejecutadas.
jedi.inference.recursion.per_function_execution_limit = 6
La cantidad máxima de veces que una función específica puede ser ejecutada.
jedi.inference.recursion.per_function_recursion_limit = 2
Una función no puede ser ejecutada más veces de las que indica este número de forma recursiva.

Pruebas de Jedi

La suite de pruebas depende de pytest:

pip install pytest

Si desea probar solo una versión específica de Python (por ejemplo, Python 3.8), es tan fácil como:

¿Quieres añadir una prueba para Jedi? ¡Genial! Nos encanta eso. Normalmente deberías escribir tus pruebas como Pruebas de Caja Negra. La mayoría de las pruebas encajarían allí.

Para pruebas de API específicas, utilizamos pruebas unitarias simples, con un enfoque en una estructura de pruebas simple y legible.

Pruebas de Integración (run.py)

Jedi se prueba principalmente con lo que yo llamaría "pruebas de integración". Estas pruebas verifican la inferencia de tipos con la API pública. Esto tiene mucho sentido para Jedi. Además, es difícil escribir doctests/unittests para las estructuras de datos internas.

Hay diferentes tipos de pruebas:

  • completions / inferencia #?
  • goto: #!
  • referencias: #<

¿Cómo ejecutar las pruebas?

La mayoría de los casos de prueba de integración se encuentran en el directorio test/completion y cada caso de prueba comienza con uno de estos comentarios:

  • #? (completions / inferencia)
  • #! (goto)
  • #< (referencias)

También hay soporte para bibliotecas de terceros. En una ejecución normal de pruebas, no se ejecutan; debes proporcionar la opción --thirdparty.

Además de las opciones -k y -m de pytest, puedes usar la opción -T (--test-files`) para especificar qué casos de prueba deben ejecutarse. Toma el formato de ``NOMBRE_ARCHIVO[:LÍNEA[,LÍNEA[,...]]] donde NOMBRE_ARCHIVO es un archivo en test/completion y LÍNEA es un número de línea del comentario de prueba. Aquí hay algunos ejemplos:

Ejecutar pruebas solo en completion/basic.py y completion/imports.py:

pytest test/test_integration.py -T basic.py -T imports.py

Ejecutar pruebas en las líneas 4, 6 y 8 de completion/basic.py:

pytest test/test_integration.py -T basic.py:4,6,8

Consulta pytest --help para más información.

Si quieres depurar una prueba, simplemente usa la opción --pdb.

Ejecutor de Pruebas Alternativo

Si no te gusta la salida de pytest, hay un ejecutor de pruebas alternativo que puedes iniciar ejecutando ./run.py. El ejemplo anterior podría ejecutarse así:

./run.py basic 4 6 8 50-80

La ventaja de este ejecutor es la simplicidad y los informes de errores más personalizados.

Pruebas de Autocompletado

Utiliza un comentario para especificar una prueba en la siguiente línea. El comentario define las completaciones esperadas. El comentario siempre comienza con #?. La última fila simboliza el cursor. Por ejemplo:

#? ['upper']
a = 'foo'; a.upp

Pruebas de Inferencia

Las pruebas de inferencia se ven muy similares. La diferencia es que las pruebas de inferencia no usan corchetes:

#? int()
ab = 3; ab

Pruebas de Goto

Las pruebas de Goto se ven así:

abc = 1
#! ['abc=1']
abc

Adicionalmente, es posible especificar la columna agregando un número, que describe la posición de la prueba (de lo contrario, es solo el final de la línea):

#! 2 ['abc=1']
abc

Pruebas de Referencia

Las pruebas se ven así:

abc = 1
#< (1,0), (3,0)
abc

Pruebas de Refactorización (refactor.py)

Las pruebas de refactorización funcionan de manera un poco similar a las pruebas de integración. Pero la idea aquí es comparar dos versiones de código. Si desea agregar un nuevo caso de prueba, simplemente mire los existentes en la carpeta test/refactor y cópielos.
