Este proyecto implementa clientes y servidores Socket.IO que pueden ejecutarse de forma independiente o integrarse con una variedad de frameworks web de Python.

EMPEZANDO

¿Qué es Socket.IO?

Socket.IO es un protocolo de transporte que permite la comunicación bidireccional en tiempo real basada en eventos entre clientes (típicamente, aunque no siempre, navegadores web) y un servidor. Las implementaciones oficiales de los componentes cliente y servidor están escritas en JavaScript. Este paquete proporciona implementaciones de Python de ambos, cada una con variantes estándar y asyncio.

Compatibilidad de versiones

El protocolo Socket.IO ha pasado por varias revisiones, y algunas de ellas introdujeron cambios incompatibles hacia atrás, lo que significa que el cliente y el servidor deben usar versiones compatibles para que todo funcione.

Si está utilizando el cliente y servidor de Python, la forma más fácil de garantizar la compatibilidad es utilizar la misma versión de este paquete para el cliente y el servidor. Si está utilizando este paquete con un cliente o servidor diferente, debe asegurarse de que las versiones sean compatibles.

La siguiente tabla de compatibilidad de versiones mapea las versiones de este paquete a las versiones de la implementación de referencia de JavaScript y a las versiones de los protocolos Socket.IO y Engine.IO.

Ejemplos de cliente

El siguiente ejemplo muestra un cliente simple de Python:

import socketio
sio = socketio.Client()
@sio.event
def connect():
    print('conexión establecida')
@sio.event
def my_message(data):
    print('mensaje recibido con ', data)
    sio.emit('my response', {'response': 'mi respuesta'})
@sio.event
def disconnect():
    print('desconectado del servidor')
sio.connect('http://localhost:5000')
sio.wait()

A continuación, un cliente similar, codificado para asyncio (solo Python 3.5+):

import asyncio
import socketio
sio = socketio.AsyncClient()
@sio.event
async def connect():
    print('conexión establecida')
@sio.event
async def my_message(data):
    print('mensaje recibido con ', data)
    await sio.emit('my response', {'response': 'mi respuesta'})
@sio.event
async def disconnect():
    print('desconectado del servidor')
async def main():
    await sio.connect('http://localhost:5000')
    await sio.wait()
if __name__ == '__main__':
    asyncio.run(main())

Características del cliente

  • Puede conectarse a otros servidores Socket.IO que sean compatibles con el servidor de referencia Socket.IO de JavaScript.
  • Compatible con Python 3.8+.
  • Dos versiones del cliente, una para Python estándar y otra para asyncio.
  • Utiliza una arquitectura basada en eventos implementada con decoradores que ocultan los detalles del protocolo.
  • Implementa transportes de sondeo largo HTTP y WebSocket.
  • Se reconecta automáticamente al servidor si se pierde la conexión.

    '/': {'content_type': 'text/html', 'filename': 'index.html'}

    print('desconectar ', sid)
if __name__ == '__main__':
    eventlet.wsgi.server(eventlet.listen(('', 5000)), app)

Para instalar el cliente estándar de Python junto con sus dependencias, use el siguiente comando:

Usando el Cliente Sencillo

La ventaja del cliente sencillo es que abstrae la lógica requerida para mantener una conexión Socket.IO. Este cliente maneja desconexiones y reconexiones de manera completamente transparente, sin añadir complejidad a la aplicación.

Creación de una Instancia de Cliente

La forma más fácil de crear un cliente Socket.IO es usar la interfaz de administrador de contexto:

import socketio
# Python estándar
with socketio.SimpleClient() as sio:
    # ... conéctate a un servidor y usa el cliente
    # ... ¡no es necesario desconectar manualmente!
# asyncio
async with socketio.AsyncSimpleClient() as sio:
    # ... conéctate a un servidor y usa el cliente
    # ... ¡no es necesario desconectar manualmente!

Con este uso, el administrador de contexto asegurará que el cliente se desconecte correctamente antes de salir del bloque with o async with.

Si se prefiere, un cliente puede instanciarse manualmente:

import socketio
# Python estándar
sio = socketio.SimpleClient()
# asyncio
sio = socketio.AsyncSimpleClient()

Conexión a un Servidor

La conexión a un servidor se establece llamando al método connect():

sio.connect('http://localhost:5000')

En el caso del cliente asyncio, el método es una corrutina:

await sio.connect('http://localhost:5000')

Por defecto, el cliente primero se conecta al servidor usando el transporte de sondeo largo (long-polling) y luego intenta actualizar la conexión para usar WebSocket. Para conectarse directamente usando WebSocket, use el argumento transports:

sio.connect('http://localhost:5000', transports=['websocket'])

Tras la conexión, el servidor asigna al cliente un identificador de sesión único. La aplicación puede encontrar este identificador en el atributo sid:

print('mi sid es', sio.sid)

El transporte Socket.IO que se utiliza en la conexión se puede obtener del atributo transport:

print('mi transporte es', sio.transport)

El transporte se proporciona como una cadena y puede ser 'websocket' o 'polling'.

Soporte TLS/SSL

El cliente soporta conexiones TLS/SSL. Para habilitarlo, use una URL de conexión https://:

sio.connect('https://example.com')

O al usar asyncio:

await sio.connect('https://example.com')

El cliente verifica los certificados del servidor por defecto. Consulte la documentación para el cliente basado en eventos para obtener información sobre cómo personalizar este comportamiento.

Emisión de Eventos

El cliente puede emitir un evento al servidor usando el método emit():

sio.emit('my message', {'foo': 'bar'})

O en el caso de asyncio, como una corrutina:

await sio.emit('my message', {'foo': 'bar'})

Los argumentos proporcionados al método son el nombre del evento a emitir y los datos opcionales que se pasan al servidor. Los datos pueden ser de tipo str, bytes, dict, list o tuple. Al enviar una list o tuple, los elementos dentro de ella deben ser de cualquier tipo permitido excepto tuple. Cuando se usa una tupla, los elementos de la tupla se pasarán como argumentos individuales a la función del manejador de eventos del lado del servidor.

Recepción de Eventos

El cliente puede esperar a que el servidor emita un evento con el método receive():

event = sio.receive()
print(f'evento recibido: "{event[0]}" con argumentos {event[1:]}')

Al usar asyncio, este método necesita ser esperado (awaited):

event = await sio.receive()
print(f'evento recibido: "{event[0]}" con argumentos {event[1:]}')

El valor de retorno de receive() es una lista. El primer elemento de esta lista es el nombre del evento, mientras que los elementos restantes son los argumentos pasados por el servidor.

Con el uso mostrado anteriormente, el método receive() devolverá un valor solo cuando se reciba un evento del servidor. Se puede pasar un tiempo de espera opcional en segundos para evitar que el cliente espere indefinidamente:

from socketio.exceptions import TimeoutError
try:
    event = sio.receive(timeout=5)
except TimeoutError:
    print('tiempo de espera agotado esperando evento')
else:
    print('evento recibido:', event)

O con asyncio:

from socketio.exceptions import TimeoutError
try:
    event = await sio.receive(timeout=5)
except TimeoutError:
    print('tiempo de espera agotado esperando evento')
else:
    print('evento recibido:', event)

Desconexión del Servidor

En cualquier momento, el cliente puede solicitar ser desconectado del servidor invocando el método disconnect():

sio.disconnect()

Para el cliente asyncio, este es una corrutina:

await sio.disconnect()

Depuración y Solución de Problemas

Para ayudarte a depurar problemas, el cliente puede configurarse para mostrar registros en la terminal:

import socketio
# Python estándar
sio = socketio.Client(logger=True, engineio_logger=True)
# asyncio
sio = socketio.AsyncClient(logger=True, engineio_logger=True)

El argumento logger controla los registros relacionados con el protocolo Socket.IO, mientras que engineio_logger controla los registros que se originan en el transporte de bajo nivel Engine.IO. Estos argumentos pueden establecerse en True para mostrar registros en stderr, o en un objeto compatible con el paquete logging de Python donde se emitirán los registros. Un valor de False deshabilita los registros.

Los registros pueden ayudar a identificar la causa de problemas de conexión, desconexiones inesperadas y otros inconvenientes.

Usando el Cliente Basado en Eventos

Creación de una Instancia de Cliente

Para instanciar un cliente Socket.IO, simplemente cree una instancia de la clase de cliente apropiada:

import socketio
# Python estándar
sio = socketio.Client()
# asyncio
sio = socketio.AsyncClient()

Definición de Manejadores de Eventos

El protocolo Socket.IO está basado en eventos. Cuando un servidor quiere comunicarse con un cliente, emite un evento. Cada evento tiene un nombre y una lista de argumentos. El cliente registra funciones manejadoras de eventos con los decoradores socketio.Client.event() <#socketio.Client.event> o socketio.Client.on() <#socketio.Client.on>:

@sio.event
def message(data):
    print('¡Recibí un mensaje!')
@sio.on('my message')
def on_message(data):
    print('¡Recibí un mensaje!')

En el primer ejemplo, el nombre del evento se obtiene del nombre de la función manejadora. El segundo ejemplo es un poco más verboso, pero permite que el nombre del evento sea diferente del nombre de la función o que incluya caracteres ilegales en nombres de función, como espacios.

Para el cliente asyncio, los manejadores de eventos pueden ser funciones regulares como las anteriores, o también pueden ser corrutinas:

@sio.event
async def message(data):
    print('¡Recibí un mensaje!')

Si el servidor incluye argumentos con un evento, estos se pasan a la función manejadora como argumentos.

Manejadores de Eventos y Espacios de Nombres "Catch-All"

Un manejador de eventos "catch-all" se invoca para cualquier evento que no tenga un manejador de eventos. Puede definir un manejador "catch-all" usando '*' como nombre del evento:

@sio.on('*')
def any_event(event, sid, data):
     pass

Los servidores asyncio también pueden usar una corrutina:

@sio.on('*')
async def any_event(event, sid, data):
    pass

Un manejador de eventos "catch-all" recibe el nombre del evento como primer argumento. Los argumentos restantes son los mismos que para un manejador de eventos regular.

Los eventos connect y disconnect deben definirse explícitamente y no se invocan en un manejador de eventos "catch-all".

De manera similar, un manejador de espacio de nombres "catch-all" se invoca para cualquier espacio de nombres conectado que no tenga un manejador de eventos definido explícitamente. Al igual que con los eventos "catch-all", se utiliza '*' en lugar de un espacio de nombres:

@sio.on('my_event', namespace='*')
def my_event_any_namespace(namespace, sid, data):
    pass

Para estos eventos, el espacio de nombres se pasa como primer argumento, seguido de los argumentos regulares del evento.

Finalmente, también es posible

Manejadores de eventos de "catch-all"

Es posible definir un manejador "catch-all" para todos los eventos en todos los namespaces:

@sio.on('*', namespace='*')
def any_event_any_namespace(event, namespace, sid, data):
    pass

Los manejadores de eventos con eventos y namespaces "catch-all" reciben el nombre del evento y el namespace como primer y segundo argumento.

Manejadores de eventos de conexión, error de conexión y desconexión

Los eventos connect, connect_error y disconnect son especiales; se invocan automáticamente cuando un cliente se conecta o desconecta del servidor:

@sio.event
def connect():
    print("¡Estoy conectado!")
@sio.event
def connect_error(data):
    print("¡La conexión falló!")
@sio.event
def disconnect(reason):
    print("¡Estoy desconectado! motivo:", reason)

El manejador connect_error se invoca cuando un intento de conexión falla. Si el servidor proporciona argumentos, estos se pasan al manejador. El servidor puede usar un argumento para proporcionar información al cliente sobre la falla de la conexión.

El manejador disconnect se invoca para desconexiones iniciadas por la aplicación, desconexiones iniciadas por el servidor o desconexiones accidentales, por ejemplo, debido a fallos de red. En caso de una desconexión accidental, el cliente intentará reconectarse inmediatamente después de invocar el manejador de desconexión. Tan pronto como se restablezca la conexión, el manejador de conexión se invocará nuevamente. El manejador recibe un argumento reason que proporciona la causa de la desconexión:

@sio.event
def disconnect(reason):
    if reason == sio.reason.CLIENT_DISCONNECT:
        print('el cliente se desconectó')
    elif reason == sio.reason.SERVER_DISCONNECT:
        print('el servidor desconectó al cliente')
    else:
        print('motivo de desconexión:', reason)

Consulte el atributo socketio.Client.reason <#socketio.Client.reason> para obtener una lista de posibles razones de desconexión.

Los eventos connect, connect_error y disconnect deben definirse explícitamente y no se invocan en un manejador de eventos "catch-all".

sio.connect('https://example.com')

O al usar asyncio:

Para deshabilitar la verificación del certificado, o para usar otras opciones menos comunes como certificados de cliente, el cliente debe inicializarse con un objeto de sesión HTTP personalizado que esté configurado con las opciones TLS/SSL deseadas.

http_session = requests.Session()

Emitiendo eventos

El cliente puede emitir un evento al servidor usando el método emit():

sio.emit('my message', {'foo': 'bar'})

O en el caso de asyncio, como una corrutina:

await sio.emit('my message', {'foo': 'bar'})

Los argumentos proporcionados al método son el nombre del evento a emitir y los datos opcionales que se pasan al servidor. Los datos pueden ser de tipo str, bytes, dict, list o tuple. Al enviar una lista o una tupla, los elementos dentro de ella deben ser de cualquiera de los tipos permitidos excepto tuple. Cuando se utiliza una tupla, los elementos de la tupla se pasarán como argumentos individuales a la función del manejador de eventos del lado del servidor.

El método emit() se puede invocar dentro de un manejador de eventos como respuesta a un evento del servidor, o en cualquier otra parte de la aplicación, incluyendo tareas en segundo plano.

Callbacks de eventos

Cuando un servidor emite un evento a un cliente, puede proporcionar opcionalmente una función de callback, para ser invocada como una forma de acuse de recibo de que el servidor ha procesado el evento. Si bien esto es administrado completamente por el servidor, el cliente puede proporcionar una lista de valores de retorno que se pasarán a la función de callback configurada por el servidor. Esto se logra simplemente devolviendo los valores deseados de la función manejadora:

@sio.event
def my_event(sid, data):
    # manejar el mensaje
    return "OK", 123

Del mismo modo, el cliente puede solicitar que se invoque una función de callback después de que el servidor haya procesado un evento. El método socketio.Server.emit() <#socketio.Server.emit> tiene un argumento opcional callback que se puede establecer en un callable. Si se proporciona este argumento, el callable se invocará después de que el servidor haya procesado el evento, y cualquier valor devuelto por el manejador del servidor se pasará como argumentos a esta función.

Namespaces

El protocolo Socket.IO admite múltiples conexiones lógicas, todas multiplexadas en la misma conexión física. Los clientes pueden abrir múltiples conexiones especificando un namespace diferente en cada una. Los namespaces utilizan una sintaxis de ruta que comienza con una barra diagonal. Una lista de namespaces puede ser proporcionada por el cliente en la llamada connect(). Por ejemplo, este ejemplo crea dos conexiones lógicas, la predeterminada más una segunda conexión bajo el namespace /chat:

sio.connect('http://localhost:5000', namespaces=['/chat'])

Para definir manejadores de eventos en un namespace, se debe agregar el argumento namespace al decorador correspondiente:

@sio.event(namespace='/chat')
def my_custom_event(sid, data):
    pass
@sio.on('connect', namespace='/chat')
def on_connect():
    print("¡Estoy conectado al namespace /chat!")

Del mismo modo, el cliente puede emitir un evento al servidor en un namespace proporcionándolo en la llamada emit():

sio.emit('my message', {'foo': 'bar'}, namespace='/chat')

Si no se proporciona el argumento namespaces de la llamada connect(), cualquier namespace utilizado en los manejadores de eventos se conectará automáticamente.

Namespaces basados en clases

Como alternativa a los manejadores de eventos basados en decoradores, los manejadores de eventos que pertenecen a un namespace pueden crearse como métodos de una subclase de socketio.ClientNamespace <#socketio.ClientNamespace>:

class MyCustomNamespace(socketio.ClientNamespace):
    def on_connect(self):
        pass
    def on_disconnect(self, reason):
        pass
    def on_my_event(self, data):
        self.emit('my_response', data)
sio.register_namespace(MyCustomNamespace('/chat'))

Cuando se utilizan espacios de nombres basados en clases, cualquier evento recibido por el cliente se distribuye a un método llamado con el nombre del evento y el prefijo on_. Por ejemplo, el evento my_event será manejado por un método llamado on_my_event. Si se recibe un evento para el cual no hay un método correspondiente definido en la clase del espacio de nombres, entonces el evento se ignora. Todos los nombres de eventos utilizados en espacios de nombres basados en clases deben usar caracteres que sean legales en los nombres de métodos.

Como una conveniencia para los métodos definidos en un espacio de nombres basado en clases, la instancia del espacio de nombres incluye versiones de varios de los métodos de las clases socketio.Client <#socketio.Client> y socketio.AsyncClient <#socketio.AsyncClient> que por defecto usan el espacio de nombres correcto cuando no se proporciona el argumento namespace.

En el caso de que un evento tenga un manejador en un espacio de nombres basado en clases y también un manejador de función basado en decoradores, solo se invoca el manejador de función independiente.

Desconexión del Servidor

En cualquier momento, el cliente puede solicitar ser desconectado del servidor invocando el método disconnect():

```python sio.disconnect() ```

Para el cliente asyncio esto es una corrutina:

```python await sio.disconnect() ```

Gestión de Tareas en Segundo Plano

Cuando se establece una conexión de cliente con el servidor, se inician algunas tareas en segundo plano para mantener la conexión activa y manejar los eventos entrantes. La aplicación que se ejecuta en el hilo principal es libre de realizar cualquier trabajo, ya que esto no impedirá el funcionamiento del cliente Socket.IO.

Si la aplicación no tiene nada que hacer en el hilo principal y solo quiere esperar hasta que finalice la conexión con el servidor, puede llamar al método wait():

```python sio.wait() ```

O en la versión asyncio:

```python await sio.wait() ```

Para mayor comodidad de la aplicación, se proporciona una función auxiliar para iniciar una tarea personalizada en segundo plano:

```python def my_background_task(my_argument): # do some background work here! pass task = sio.start_background_task(my_background_task, 123) ```

Los argumentos pasados a este método son la función de fondo y cualquier argumento posicional o de palabra clave para invocar la función.

Aquí está la versión asyncio:

```python async def my_background_task(my_argument): # do some background work here! pass task = sio.start_background_task(my_background_task, 123) ```

Tenga en cuenta que esta función no es una corrutina, ya que no espera a que finalice la función de fondo. La función de fondo debe ser una corrutina.

El método sleep() es una segunda función de conveniencia que se proporciona en beneficio de las aplicaciones que trabajan con sus propias tareas en segundo plano:

```python sio.sleep(2) ```

O para asyncio:

```python await sio.sleep(2) ```

El único argumento pasado al método es el número de segundos a esperar.

Depuración y Solución de Problemas

Para ayudarle a depurar problemas, el cliente se puede configurar para mostrar registros en la terminal:

```python import socketio # Python estándar sio = socketio.Client(logger=True, engineio_logger=True) # asyncio sio = socketio.AsyncClient(logger=True, engineio_logger=True) ```

El argumento logger controla los registros relacionados con el protocolo Socket.IO, mientras que engineio_logger controla los registros que se originan en el transporte de nivel inferior Engine.IO. Sirviendo Archivos Estáticos

El servidor Socket.IO se puede configurar para servir archivos estáticos a los clientes. Esto es particularmente útil para entregar archivos HTML, CSS y JavaScript a los clientes cuando este paquete se utiliza sin un framework web complementario.

Los archivos estáticos se configuran con un diccionario de Python en el que cada par clave/valor es una regla de mapeo de archivo estático. En su forma más simple, este diccionario tiene una o más URL de archivos estáticos como claves y los archivos correspondientes en el servidor como valores:

```python static_files = { '/': 'latency.html', '/static/socket.io.js': 'static/socket.io.js', '/static/style.css': 'static/style.css', } ```

Con esta configuración de ejemplo, cuando el servidor recibe una solicitud para / (la URL raíz), devolverá el contenido del archivo latency.html en el directorio actual y asignará un tipo de contenido basado en la extensión del archivo, en este caso text/html.

Los archivos con extensiones de archivo .html, .css, .js, .json, .jpg, .png, .gif y .txt se reconocen automáticamente y se les asigna el tipo de contenido correcto. Para archivos con otras extensiones de archivo o sin extensión de archivo, se utiliza el tipo de contenido application/octet-stream como predeterminado.

Si se desea, se puede proporcionar un tipo de contenido explícito para un archivo estático de la siguiente manera:

```python static_files = { '/': {'filename': 'latency.html', 'content_type': 'text/plain'}, } ```

También es posible configurar un directorio completo en una única r

ule, de modo que todos los archivos en él se sirvan como archivos estáticos:

static_files = {
    '/static': './public',
}

En este ejemplo, cualquier archivo con URL que comience con /static se servirá directamente desde la carpeta public en el directorio actual, por lo que, por ejemplo, la URL /static/index.html devolverá el archivo local ./public/index.html y la URL /static/css/styles.css devolverá el archivo local ./public/css/styles.css.

Si se solicita una URL que termina en un /, se le añadirá un nombre de archivo predeterminado de index.html. En el ejemplo anterior, una solicitud para la URL /static/ devolvería el archivo local ./public/index.html. El nombre de archivo predeterminado para servir URLs que terminan en barra se puede establecer en el diccionario de archivos estáticos con una clave vacía:

static_files = {
    '/static': './public',
    '': 'image.gif',
}

Con esta configuración, una solicitud para /static/ devolvería el archivo local ./public/image.gif. También se puede especificar un tipo de contenido no estándar si es necesario:

static_files = {
    '/static': './public',
    '': {'filename': 'image.gif', 'content_type': 'text/plain'},
}

El diccionario de configuración de archivos estáticos se pasa como argumento static_files a las clases socketio.WSGIApp o socketio.ASGIApp:

# para aplicaciones WSGI estándar
sio = socketio.Server()
app = socketio.WSGIApp(sio, static_files=static_files)
# para aplicaciones ASGI basadas en asyncio
sio = socketio.AsyncServer()
app = socketio.ASGIApp(sio, static_files=static_files)

La precedencia de enrutamiento en estas dos clases es la siguiente:

  • Primero, la ruta se comprueba con el punto final de Socket.IO.
  • A continuación, la ruta se comprueba con la configuración de archivos estáticos, si está presente.
  • Si la ruta no coincide con el punto final de Socket.IO ni con ningún archivo estático, el control se pasa a la aplicación secundaria si está configurada, de lo contrario, se devuelve un error 404.

Nota: el servicio de archivos estáticos está pensado solo para uso en desarrollo y, como tal, carece de funciones importantes como el almacenamiento en caché. No lo utilice en un entorno de producción.

Eventos

El protocolo Socket.IO se basa en eventos. Cuando un cliente desea comunicarse con el servidor, o el servidor desea comunicarse con uno o más clientes, emiten un evento a la otra parte. Cada evento tiene un nombre y una lista opcional de argumentos.

Escuchando Eventos

Para recibir eventos de los clientes, la aplicación del servidor debe registrar funciones de manejo de eventos. Estas funciones se invocan cuando los eventos correspondientes son emitidos por los clientes. Para registrar un manejador para un evento, se utilizan los decoradores socketio.Server.event() <#socketio.Server.event> o socketio.Server.on() <#socketio.Server.on>:

@sio.event
def mi_evento(sid, datos):
    pass
@sio.on('mi evento personalizado')
def otro_evento(sid, datos):
    pass

En el primer ejemplo, el nombre del evento se obtiene del nombre de la función manejadora. El segundo ejemplo es un poco más verboso, pero permite que el nombre del evento sea diferente del nombre de la función o que incluya caracteres que son ilegales en los nombres de función, como espacios.

Para servidores asyncio, los manejadores de eventos pueden proporcionarse opcionalmente como corrutinas:

@sio.event
async def mi_evento(sid, datos):
    pass

El argumento sid que se pasa a todos los manejadores es el ID de sesión de Socket.IO, un identificador único que Socket.IO asigna a cada conexión de cliente. Todos los eventos enviados por un cliente determinado tendrán el mismo valor sid.

Eventos de Conexión y Desconexión

Los eventos connect y disconnect son especiales; se invocan automáticamente cuando un cliente se conecta o desconecta del servidor:

@sio.event
def connect(sid, environ, auth):
    print('conectar ', sid)
@sio.event
def disconnect(sid, reason):
    print('desconectar ', sid, reason)

El evento connect es el lugar ideal para realizar la autenticación del usuario y cualquier mapeo necesario entre las entidades de usuario en la aplicación y el sid que se asignó al cliente.

Además del sid, el manejador de conexión recibe environ como argumento, con la información de la solicitud en formato WSGI estándar, incluyendo las cabeceras HTTP. El manejador de conexión también recibe el argumento auth con los detalles de autenticación pasados por el cliente, o None si el cliente no pasó ninguna autenticación.

Después de inspeccionar los argumentos, el manejador del evento de conexión puede devolver False para rechazar la conexión con el cliente. A veces es útil pasar datos al cliente que está siendo rechazado. En ese caso, en lugar de devolver False, se puede generar una excepción socketio.exceptions.ConnectionRefusedError <#socketio.exceptions.ConnectionRefusedError>, y todos sus argumentos se enviarán al cliente con el mensaje de rechazo:

from socketio.exceptions import ConnectionRefusedError
@sio.event
def connect(sid, environ, auth):
    raise ConnectionRefusedError('fallo de autenticación')

El manejador de desconexión recibe el sid asignado al cliente y una reason, que proporciona la causa de la desconexión:

@sio.event
def disconnect(sid, reason):
    if reason == sio.reason.CLIENT_DISCONNECT:
        print('el cliente se desconectó')
    elif reason == sio.reason.SERVER_DISCONNECT:
        print('el servidor desconectó al cliente')
    else:
        print('razón de desconexión:', reason)

Consulte el atributo socketio.Server.reason <#socketio.Server.reason> para ver una lista de posibles razones de desconexión.

Manejadores de Eventos "Catch-All"

Un manejador de eventos "catch-all" se invoca para cualquier evento que no tenga un manejador de eventos. Puede definir un manejador "catch-all" usando '*' como nombre de evento:

@sio.on('*')
def cualquier_evento(event, sid, data):
     pass

Los servidores asyncio también pueden usar una corrutina:

@sio.on('*')
async def cualquier_evento(event, sid, data):
    pass

Un manejador de eventos "catch-all" recibe el nombre del evento como primer argumento. Los argumentos restantes son los mismos que para un manejador de eventos regular.

Tenga en cuenta que los eventos connect y disconnect deben definirse explícitamente y no se invocan en un manejador de eventos "catch-all".

Emisión de Eventos a Clientes

Socket.IO es un protocolo bidireccional, por lo que en cualquier momento el servidor puede enviar un evento a sus clientes conectados. El método socketio.Server.emit() <#socketio.Server.emit> se utiliza para esta tarea:

sio.emit('mi evento', {'datos': 'foobar'})

El primer argumento es el nombre del evento, seguido de una carga útil de datos opcional de tipo str, bytes, list, dict o tuple. Al enviar una list, dict o tuple, los elementos también están restringidos a los mismos tipos de datos. Cuando se envía un tuple, los elementos de la tupla se pasarán como argumentos múltiples a la función manejadora de eventos en el lado del cliente.

El ejemplo anterior enviará el evento a todos los clientes que están conectados. A veces, el servidor puede querer enviar un evento solo a un cliente en particular. Esto se puede lograr añadiendo un argumento to a la llamada de emisión, con el sid del cliente:

sio.emit('mi evento', {'datos': 'foobar'}, to=user_sid)

El argumento to se utiliza para identificar al cliente que debe recibir el evento, y se establece en el valor sid asignado a la conexión de ese cliente con el servidor. Cuando se omite to, el evento se difunde a todos los clientes conectados.

Acuses de Recibo de Eventos

Cuando un cliente envía un evento al servidor, puede solicitar opcionalmente recibir un acuse de recibo del servidor. El envío de acuses de recibo es gestionado automáticamente por el servidor Socket.IO, pero la función manejadora de eventos puede proporcionar una lista de valores que se pasarán al cliente con el acuse de recibo simplemente devolviéndolos:

@sio.event
def mi_evento(sid, datos):
    # manejar el mensaje
    return "OK", 123  # <-- el cliente tendrá estos como acuse de recibo

Solicitando Acuses de Recibo del Cliente

De forma similar a cómo los clientes pueden solicitar acuses de recibo del servidor, cuando el servidor está emitiendo a un solo cliente, también puede pedir al cliente que acuse recibo del evento y, opcionalmente, devuelva uno o más valores como respuesta.

El servidor Socket.IO admite dos formas de trabajar con acuses de recibo del cliente. El método más conveniente es reemplazar socketio.Server.emit() <#socketio.Server.emit> con socketio.Server.call() <#socketio.Server.call>. El método call() emitirá el evento y luego esperará hasta que el cliente envíe un acuse de recibo, devolviendo cualquier valor proporcionado por el cliente:

respuesta = sio.call('mi evento', {'datos': 'foobar'}, to=user_sid)

Una solución de acuse de recibo mucho más primitiva utiliza funciones de devolución de llamada. El método socketio.Server.emit() <#socketio.Server.emit> tiene un argumento opcional callback que se puede establecer en un objeto invocable. Si se proporciona este argumento, el objeto invocable se llamará después de que el cliente haya procesado el evento, y cualquier valor devuelto por el cliente se pasará como argumentos a esta función:

def mi_callback():
    print("¡callback invocado!")

{ "a": { "b": "foobar" }, "to": "user_sid", "callback": "my_callback" } ```

Habitaciones

Para facilitar que el servidor emita eventos a grupos de clientes relacionados, la aplicación puede poner a sus clientes en "habitaciones" y luego dirigir los mensajes a estas habitaciones.

En ejemplos anteriores, el argumento to del método socketio.SocketIO.emit() se utilizó para designar un cliente específico como destinatario del evento. Al argumento to también se le puede dar el nombre de una habitación, y entonces todos los clientes que estén en esa habitación recibirán el evento.

La aplicación puede crear tantas habitaciones como sea necesario y gestionar qué clientes están en ellas utilizando los métodos socketio.Server.enter_room() <#socketio.Server.enter_room> y socketio.Server.leave_room() <#socketio.Server.leave_room>. Los clientes pueden estar en tantas habitaciones como sea necesario y pueden ser movidos entre habitaciones cuando sea necesario.

@sio.event
def begin_chat(sid):
    sio.enter_room(sid, 'chat_users')
@sio.event
def exit_chat(sid):
    sio.leave_room(sid, 'chat_users')

En aplicaciones de chat, a menudo se desea que un evento se transmita a todos los miembros de la habitación excepto a uno, que es el originador del evento, como un mensaje de chat. El método socketio.Server.emit() <#socketio.Server.emit> proporciona un argumento opcional skip_sid para indicar un cliente que debe ser omitido durante la transmisión.

@sio.event
def my_message(sid, data):
    sio.emit('my reply', data, room='chat_users', skip_sid=sid)

Espacios de nombres

El protocolo Socket.IO admite múltiples conexiones lógicas, todas multiplexadas en la misma conexión física. Los clientes pueden abrir múltiples conexiones especificando un espacio de nombres diferente en cada una. Un espacio de nombres es proporcionado por el cliente como una ruta de URL después del nombre de host y el puerto. Por ejemplo, conectarse a http://example.com:8000/chat abriría una conexión al espacio de nombres /chat.

Cada espacio de nombres funciona independientemente de los demás, con IDs de sesión (sids), manejadores de eventos y habitaciones separados. Los espacios de nombres se pueden definir directamente en las funciones de manejo de eventos, o también se pueden crear como clases.

Espacios de nombres basados en decoradores

Los espacios de nombres basados en decoradores son manejadores de eventos regulares que incluyen el argumento namespace en su decorador:

@sio.event(namespace='/chat')
def my_custom_event(sid, data):
    pass
@sio.on('my custom event', namespace='/chat')
def my_custom_event(sid, data):
    pass

Al emitir un evento, el argumento opcional namespace se utiliza para especificar en qué espacio de nombres enviarlo. Cuando se omite el argumento namespace, se utiliza el espacio de nombres predeterminado de Socket.IO, que se llama /.

Es importante que las aplicaciones que utilizan múltiples espacios de nombres especifiquen el espacio de nombres correcto al configurar sus manejadores de eventos y habitaciones utilizando el argumento opcional namespace. Este argumento también debe especificarse al emitir eventos bajo un espacio de nombres. La mayoría de los métodos de la clase socketio.Server <#socketio.Server> tienen el argumento opcional namespace.

Espacios de nombres basados en clases

Como alternativa a los espacios de nombres basados en decoradores, los manejadores de eventos que pertenecen a un espacio de nombres se pueden crear como métodos en una subclase de socketio.Namespace <#socketio.Namespace>:

class MyCustomNamespace(socketio.Namespace):
    def on_connect(self, sid, environ):
        pass
    def on_disconnect(self, sid, reason):
        pass
    def on_my_event(self, sid, data):
        self.emit('my_response', data)
sio.register_namespace(MyCustomNamespace('/test'))

Para servidores basados en asyncio, los espacios de nombres deben heredar de socketio.AsyncNamespace <#socketio.AsyncNamespace>, y pueden definir manejadores de eventos como corrutinas si se desea:

class MyCustomNamespace(socketio.AsyncNamespace):
    def on_connect(self, sid, environ):
        pass
    def on_disconnect(self, sid, reason):
        pass
    async def on_my_event(self, sid, data):
        await self.emit('my_response', data)
sio.register_namespace(MyCustomNamespace('/test'))

Cuando se utilizan espacios de nombres basados en clases, cualquier evento recibido por el servidor se distribuye a un método con el nombre del evento y el prefijo on_. Por ejemplo, el evento my_event será manejado por un método llamado on_my_event. Si se recibe un evento para el cual no hay un método correspondiente definido en la clase del espacio de nombres, el evento se ignora. Todos los nombres de eventos utilizados en las clases de espacios de nombres deben usar caracteres que sean legales en los nombres de métodos.

Como conveniencia para los métodos definidos en un espacio de nombres basado en clases, la instancia del espacio de nombres incluye versiones de varios métodos de las clases socketio.Server <#socketio.Server> y socketio.AsyncServer <#socketio.AsyncServer> que, por defecto, utilizan el espacio de nombres correcto cuando no se proporciona el argumento namespace.

En el caso de que un evento tenga un manejador en un espacio de nombres basado en clases, y también una función manejadora basada en decoradores, solo se invocará el manejador de función independiente.

Es importante tener en cuenta que los espacios de nombres basados en clases son singleton. Esto significa que se utiliza una única instancia de una clase de espacio de nombres para todos los clientes y, en consecuencia, una instancia de espacio de nombres no se puede utilizar para almacenar información específica del cliente.

Espacios de nombres de captura general

De manera similar a los manejadores de eventos de captura general, se puede usar un espacio de nombres de "captura general" al definir manejadores de eventos para cualquier espacio de nombres conectado que no tenga un manejador de eventos explícitamente definido. Al igual que con los eventos de captura general, se usa '*' en lugar de un espacio de nombres:

@sio.on('my_event', namespace='*')
def my_event_any_namespace(namespace, sid, data):
    pass

Para estos eventos, el espacio de nombres se pasa como primer argumento, seguido de los argumentos regulares del evento.

Se puede definir un manejador de espacio de nombres basado en clases de captura general pasando '*' como el espacio de nombres durante el registro:

sio.register_namespace(MyCustomNamespace('*'))

Se puede definir un manejador de "captura general" para todos los eventos en todos los espacios de nombres de la siguiente manera:

@sio.on('*', namespace='*')
def any_event_any_namespace(event, namespace, sid, data):
    pass

Los manejadores de eventos con eventos y espacios de nombres de captura general reciben el nombre del evento y el espacio de nombres como primer y segundo argumento.

Sesiones de usuario

El servidor puede mantener información específica de la aplicación en una sesión de usuario dedicada a cada cliente conectado. Las aplicaciones pueden usar la sesión de usuario para guardar cualquier detalle sobre el usuario que deba conservarse durante la vida de la conexión, como nombres de usuario o IDs de usuario.

Los métodos save_session() y get_session() se utilizan para almacenar y recuperar información en la sesión de usuario:

@sio.event
def connect(sid, environ):
    username = authenticate_user(environ)
    sio.save_session(sid, {'username': username})
@sio.event
def message(sid, data):
    session = sio.get_session(sid)
    print('message from ', session['username'])

Para el servidor asyncio, estos métodos son corrutinas:

@sio.event
async def connect(sid, environ):
    username = authenticate_user(environ)
    await sio.save_session(sid, {'username': username})
@sio.event
async def message(sid, data):
    session = await sio.get_session(sid)
    print('message from ', session['username'])

La sesión también se puede manipular con el gestor de contexto session():

@sio.event
def connect(sid, environ):
    username = authenticate_user(environ)
    with sio.session(sid) as session:
        session['username'] = username
@sio.event
def message(sid, data):
    with sio.session(sid) as session:
        print('message from ', session['username'])

Para el servidor asyncio, se utiliza un gestor de contexto asíncrono:

@sio.event
async def connect(sid, environ):
    username = authenticate_user(environ)
    async with sio.session(sid) as session:
        session['username'] = username
@sio.event
async def message(sid, data):
    async with sio.session(sid) as session:
        print('message from ', session['username'])

Los métodos get_session(), save_session() y session() toman un argumento opcional namespace. Si no se proporciona este argumento, la sesión se adjunta al espacio de nombres predeterminado.

Nota: el contenido de la sesión del usuario se destruye cuando el cliente se desconecta. En particular, el contenido de la sesión del usuario no se conserva cuando un cliente se reconecta después de una desconexión inesperada del servidor.

Controles de origen cruzado

Por razones de seguridad, este servidor aplica una política del mismo origen por defecto. En términos prácticos, esto significa lo siguiente:

  • Si una solicitud HTTP o WebSocket entrante incluye el encabezado Origin, este encabezado debe coincidir con el esquema y el host de la URL de conexión. En caso de discrepancia, se devuelve una respuesta con código de estado 400 y se rechaza la conexión.
  • No se imponen restricciones a las solicitudes entrantes que no incluyen el encabezado Origin.

Si es necesario, la opción cors_allowed_origins se puede utilizar para permitir otros orígenes. Este argumento se puede establecer como una cadena para establecer un único origen permitido, o como una lista para permitir múltiples orígenes. Se puede usar un valor especial de '*' para indicar al servidor que permita todos los orígenes, pero esto debe hacerse con cuidado, ya que podría hacer que el servidor sea vulnerable a ataques de falsificación de solicitud entre sitios (CSRF).

Admin UI

El servidor está configurado para aceptar conexiones de la interfaz de administración oficial de Socket.IO https://socket.io/docs/v4/admin-ui/. Esta herramienta proporciona información en tiempo real sobre los clientes conectados actualmente, las salas en uso y los eventos que se emiten. Dado que habilitar esta característica puede afectar el rendimiento del servidor, está deshabilitada por defecto. Para habilitarla, llama al método instrument() <#socketio.Server.instrument>. Por ejemplo:

import os
import socketio
sio = socketio.Server(cors_allowed_origins=[
    'http://localhost:5000',
    'https://admin.socket.io',
])
sio.instrument(auth={
    'username': 'admin',
    'password': os.environ['ADMIN_PASSWORD'],
})

Esto configura el servidor para aceptar conexiones del cliente alojado de la interfaz de administración. Los administradores pueden entonces abrir https://admin.socket.io en sus navegadores web e iniciar sesión con el nombre de usuario admin y la contraseña proporcionada por la variable de entorno ADMIN_PASSWORD. Para asegurar que la interfaz de administración frontal pueda conectarse, también se configura CORS.

Depuración y Solución de problemas

Para ayudarte a depurar problemas, el servidor puede configurarse para mostrar registros en la terminal:

import socketio
# Python estándar
sio = socketio.Server(logger=True, engineio_logger=True)
# asyncio

El argumento logger controla el registro relacionado con el protocolo Socket.IO, mientras que engineio_logger controla los registros que se originan en el transporte de bajo nivel Engine.IO. Concurrencia e Integración con Servidor Web

El servidor Socket.IO puede configurarse con diferentes modelos de concurrencia según las necesidades de la aplicación y el servidor web que se utilice. El modelo de concurrencia se especifica mediante el argumento async_mode en el servidor. Por ejemplo:

sio = socketio.Server(async_mode='threading')

Las siguientes subsecciones describen las opciones de concurrencia disponibles para servidores síncronos y asíncronos.

Modos Estándar

  • threading: el servidor utilizará hilos de Python para la concurrencia y se ejecutará en cualquier servidor WSGI multihilo. Este es el modo por defecto cuando no hay otras bibliotecas de concurrencia instaladas.
  • gevent: el servidor utilizará greenlets a través de la biblioteca gevent http://www.gevent.org/ para la concurrencia. Se requiere un servidor web compatible con gevent.
  • gevent_uwsgi: una variación del modo gevent diseñada para funcionar con el servidor web uWSGI https://uwsgi-docs.readthedocs.io/en/latest/.
  • eventlet: el servidor utilizará greenlets a través de la biblioteca eventlet http://eventlet.net/ para la concurrencia. Se requiere un servidor web compatible con eventlet. No se recomienda el uso de eventlet ya que este proyecto se encuentra en modo de mantenimiento.

Modos Asyncio

Las opciones asíncronas se basan todas en el paquete asyncio https://docs.python.org/3/library/asyncio.html de la biblioteca estándar de Python, con ligeras variaciones según la plataforma de servidor web que se utilice.

  • asgi: se requiere el uso de cualquier servidor web ASGI https://asgi.readthedocs.io/en/latest/.
  • aiohttp: se requiere el uso del framework y servidor web aiohttp http://aiohttp.readthedocs.io/.
  • tornado: se requiere el uso del framework y servidor web Tornado http://www.tornadoweb.org/.
  • sanic: se requiere el uso del framework y servidor web Sanic http://sanic.readthedocs.io/. Al usar Sanic, se recomienda usar el modo asgi en su lugar.

Estrategias de Despliegue

Las siguientes secciones describen una variedad de estrategias de despliegue para servidores Socket.IO.

Gunicorn

La estrategia de despliegue más sencilla para el servidor Socket.IO es utilizar el popular servidor web Gunicorn http://gunicorn.org en modo multihilo. El servidor Socket.IO debe ser envuelto por la clase socketio.WSGIApp <#socketio.WSGIApp>, para que sea compatible con el protocolo WSGI:

sio = socketio.Server(async_mode='threading')
app = socketio.WSGIApp(sio)

Si se desea, la clase socketio.WSGIApp puede reenviar cualquier tráfico que no sea Socket.IO a otra aplicación WSGI, lo que permite desplegar una aplicación web WSGI estándar construida con frameworks como Flask o Django y el servidor Socket.IO como un paquete:

sio = socketio.Server(async_mode='threading')
app = socketio.WSGIApp(sio, other_wsgi_app)

El siguiente ejemplo muestra cómo iniciar una aplicación Socket.IO utilizando la clase de trabajador con hilos de Gunicorn:

$ gunicorn --workers 1 --threads 100 --bind 127.0.0.1:5000 module:app

Con la configuración anterior, el servidor podrá manejar cerca de 100 clientes concurrentes.

También es posible utilizar más de un proceso de trabajador, pero esto tiene dos requisitos adicionales:

  • Los clientes deben conectarse directamente a través de WebSocket. El transporte de sondeo largo (long-polling) es incompatible con la forma en que Gunicorn equilibra la carga de las solicitudes entre los trabajadores. Para deshabilitar el sondeo largo en el servidor, añade transports=['websocket'] en el constructor del servidor. Los clientes tendrán una opción similar para iniciar la conexión con WebSocket.
  • Las instancias de socketio.Server() <#socketio.Server> en cada trabajador deben configurarse con una cola de mensajes para permitir que los trabajadores se comuniquen entre sí. Consulta la sección Uso de una cola de mensajes para obtener más información.

Al utilizar varios trabajadores, el número aproximado de conexiones que el servidor podrá aceptar se puede calcular como el número de trabajadores multiplicado por el número de hilos por trabajador.

Ten en cuenta que Gunicorn también se puede usar junto con uvicorn, gevent y eventlet. Estas opciones se discuten en las secciones correspondientes a continuación.

Uvicorn (y otros servidores web ASGI)

Cuando se trabaja con un servidor Socket.IO asíncrono, la estrategia de despliegue más sencilla es utilizar un servidor web ASGI como Uvicorn https://www.uvicorn.org/.

La clase socketio.ASGIApp es una aplicación compatible con ASGI que puede reenviar el tráfico Socket.IO a una instancia de socketio.AsyncServer:

sio = socketio.AsyncServer(async_mode='asgi')
app = socketio.ASGIApp(sio)

Si se desea, la clase socketio.ASGIApp puede reenviar cualquier tráfico que no sea Socket.IO a otra aplicación ASGI, lo que permite desplegar una aplicación web ASGI estándar construida con un framework como FastAPI y el servidor Socket.IO como un paquete:

sio = socketio.AsyncServer(async_mode='asgi')
app = socketio.ASGIApp(sio, other_asgi_app)

El siguiente ejemplo inicia la aplicación con Uvicorn:

uvicorn --port 5000 module:app

Uvicorn también se puede usar a través de su trabajador Gunicorn:

gunicorn --workers 1 --worker-class uvicorn.workers.UvicornWorker --bind 127.0.0.1:5000

Consulta la sección Gunicorn anterior para obtener información sobre cómo usar Gunicorn con varios trabajadores.

Hypercorn, Daphne y otros servidores ASGI

Para utilizar un servidor web ASGI que no sea Uvicorn, configura la aplicación para ASGI como se muestra arriba para Uvicorn, luego sigue la documentación de tu servidor web elegido para iniciar la aplicación.

Aiohttp

Otra opción para desplegar un servidor Socket.IO asíncrono es utilizar el framework y servidor web Aiohttp http://aiohttp.readthedocs.io/. Las instancias de la clase socketio.AsyncServer utilizarán automáticamente Aiohttp si la biblioteca está instalada. Para solicitar explícitamente su uso, se puede proporcionar la opción async_mode en el constructor:

sio = socketio.AsyncServer(async_mode='aiohttp')

Un servidor configurado para Aiohttp debe adjuntarse a una aplicación existente:

app = web.Application()
sio.attach(app)

La aplicación Aiohttp puede definir rutas regulares que coexistirán con el servidor Socket.IO. Un patrón típico es añadir rutas que sirvan a una aplicación cliente y a cualquier archivo estático asociado.

La aplicación Aiohttp se ejecuta entonces de la manera habitual:

> 
if __name__ == '__main__':
    web.run_app(app)

Gevent

Cuando un servidor web multihilo no es capaz de satisfacer los requisitos de concurrencia y escalabilidad de la aplicación, una opción a probar es Gevent http://www.gevent.org. Gevent es una biblioteca de concurrencia basada en corrutinas, la cual se basa en greenlets, que son significativamente más ligeros que los hilos.

Las instancias de la clase socketio.Server usarán automáticamente Gevent si la biblioteca está instalada. Para solicitar explícitamente la selección de gevent, se puede proporcionar la opción async_mode en el constructor:

sio = socketio.Server(async_mode='gevent')

El servidor Socket.IO debe ser encapsulado por la clase socketio.WSGIApp <#socketio.WSGIApp>, para que sea compatible con el protocolo WSGI:

app = socketio.WSGIApp(sio)

Si se desea, la clase socketio.WSGIApp puede reenviar cualquier tráfico que no sea Socket.IO a otra aplicación WSGI, haciendo posible desplegar una aplicación web WSGI estándar construida con frameworks como Flask o Django y el servidor Socket.IO como un paquete:

sio = socketio.Server(async_mode='gevent')
app = socketio.WSGIApp(sio, other_wsgi_app)

Un servidor configurado para Gevent se despliega como una aplicación WSGI regular utilizando la clase socketio.WSGIApp proporcionada:

from gevent import pywsgi
pywsgi.WSGIServer(('', 8000), app).serve_forever()

Gevent con Gunicorn

Una alternativa a ejecutar el servidor WSGI de gevent como se muestra arriba es usar Gunicorn <gunicorn.org> con su worker de Gevent. El comando para lanzar la aplicación bajo Gunicorn y Gevent se muestra a continuación:

$ gunicorn -k gevent -w 1 -b 127.0.0.1:5000 module:app

Consulte la sección Gunicorn de arriba para obtener información sobre cómo usar Gunicorn con múltiples workers.

Gevent proporciona una función monkey_patch() que reemplaza todas las funciones bloqueantes de la biblioteca estándar con versiones asíncronas equivalentes. Si bien el servidor Socket.IO no requiere monkey patching, es probable que otras bibliotecas, como los drivers de bases de datos o colas de mensajes, lo requieran.

Gevent con uWSGI

Al usar el servidor uWSGI en combinación con gevent, el servidor Socket.IO puede aprovechar el soporte nativo de WebSockets de uWSGI.

Las instancias de la clase socketio.Server usarán automáticamente esta opción para operaciones asíncronas si tanto gevent como uWSGI están instalados y eventlet no lo está. Para solicitar explícitamente este modo asíncrono, se puede proporcionar la opción async_mode en el constructor:

# gevent con uWSGI
sio = socketio.Server(async_mode='gevent_uwsgi')

Una explicación completa de la configuración y el uso del servidor uWSGI está fuera del alcance de esta documentación. El servidor uWSGI es un paquete bastante complejo que proporciona un conjunto grande y completo de opciones. Debe compilarse con soporte para WebSockets y SSL para que el transporte WebSocket esté disponible. Como introducción, el siguiente comando inicia un servidor uWSGI para el ejemplo latency.py en el puerto 5000:

$ uwsgi --http :5000 --gevent 1000 --http-websockets --master --wsgi-file latency.py --callable app

Las instancias de la clase socketio.AsyncServer usarán automáticamente Tornado http://www.tornadoweb.org// si la biblioteca está instalada. Para solicitar explícitamente su uso, se puede proporcionar la opción async_mode en el constructor:

Uso de una Cola de Mensajes

Al trabajar con aplicaciones distribuidas, a menudo es necesario acceder a la funcionalidad de Socket.IO desde múltiples procesos. Hay dos casos de uso específicos:

  • Las aplicaciones de alta disponibilidad pueden querer utilizar el escalado horizontal del servidor Socket.IO para poder manejar un número muy grande de clientes concurrentes.
  • Las aplicaciones que utilizan colas de trabajo como Celery http://www.celeryproject.org/ pueden necesitar emitir un evento a un cliente una vez que un trabajo en segundo plano se completa. El lugar más conveniente para llevar a cabo esta tarea es el proceso worker que manejó ese trabajo.

Como solución a los problemas anteriores, el servidor Socket.IO puede configurarse para conectarse a una cola de mensajes como Redis http://redis.io/ o RabbitMQ https://www.rabbitmq.com/, para comunicarse con otros servidores Socket.IO relacionados o workers auxiliares.

Redis

Para usar una cola de mensajes Redis, se debe instalar un cliente Python de Redis:

# Clase socketio.Server
pip install redis

La cola Redis se configura a través de las clases socketio.RedisManager <#socketio.RedisManager> y socketio.AsyncRedisManager <#socketio.AsyncRedisManager>. Estas clases se conectan directamente al almacén Redis y utilizan la funcionalidad pub/sub de la cola:

# Clase socketio.Server
mgr = socketio.RedisManager('redis://')
sio = socketio.Server(client_manager=mgr)
# Clase socketio.AsyncServer
mgr = socketio.AsyncRedisManager('redis://')
sio = socketio.AsyncServer(client_manager=mgr)

El argumento client_manager instruye al servidor a conectarse a la cola de mensajes dada y a coordinarse con otros procesos conectados a la cola.

Kombu

Kombu http://kombu.readthedocs.org/en/latest/ es un paquete de Python que proporciona acceso a RabbitMQ y a muchas otras colas de mensajes. Se puede instalar con pip:

pip install kombu

Para usar RabbitMQ u otras colas compatibles con el protocolo AMQP, esa es la única dependencia requerida. Pero para otras colas de mensajes, Kombu puede requerir paquetes adicionales. Por ejemplo, para usar una cola Redis a través de Kombu, también se debe instalar el paquete Python para Redis:

pip install redis

La cola se configura a través de socketio.KombuManager <#socketio.KombuManager>:

mgr = socketio.KombuManager('amqp://')
sio = socketio.Server(client_manager=mgr)

La URL de conexión pasada al constructor de KombuManager se pasa directamente al objeto Connection de Kombu http://kombu.readthedocs.org/

Message Queues

To scale a Socket.IO deployment to more than one server, a message queue is required for the servers to communicate with each other. The following message queues are supported:

Redis

Redis https://redis.io/ is supported through the redis-py https://redis-py.readthedocs.io/en/latest/ package:

pip install redis-py

Access to Redis is configured through the socketio.RedisManager <#socketio.RedisManager> class:

mgr = socketio.RedisManager('redis://')
sio = socketio.Server(client_manager=mgr)

The connection URL uses the standard Redis URL format. See https://redis-py.readthedocs.io/en/latest/connections.html#redis-url-format, so the redis-py documentation should be consulted for information on how to build the correct URL for a given Redis instance.

Note that Redis currently does not support asyncio, so it cannot be used with the socketio.AsyncServer <#socketio.AsyncServer> class.

Kombu https://kombu.readthedocs.io/en/latest/ is a client library that implements the AMQP protocol, which is used by RabbitMQ, and other message brokers. It can be installed with pip:

pip install kombu

mgr = socketio.KombuManager('amqp://')

Deploying the Message Queue for Production

For a production deployment there are a few recommendations to keep your application secure.

First of all, the message queue should never be listening on a public network interface, to ensure that external clients never connect to it. For a single node deployment, the queue should only listen on localhost. For a multi-node system the use of a private network (VPC), where the communication between servers can happen privately is highly recommended.

In addition, all message queues support authentication and encryption, which can strenthen the security of the deployment. Authentication ensures that only the Socket.IO servers and related processes have access, while encryption prevents data from being collected by a third-party that is listening on the network. Access credentials can be included in the connection URLs that are passed to the client managers.

Horizontal Scaling

Socket.IO is a stateful protocol, which makes horizontal scaling more difficult. When deploying a cluster of Socket.IO processes, all processes must connect to the message queue by passing the client_manager argument to the server instance. This enables the workers to communicate and coordinate complex operations such as broadcasts.

If the long-polling transport is used, then there are two additional requirements that must be met:

  • Each Socket.IO process must be able to handle multiple requests concurrently. This is needed because long-polling clients send two requests in parallel. Worker processes that can only handle one request at a time are not supported.
  • The load balancer must be configured to always forward requests from a client to the same worker process, so that all requests coming from a client are handled by the same node. Load balancers call this sticky sessions, or session affinity.

Emitting from external processes

To have a process other than a server connect to the queue to emit a message, the same client manager classes can be used as standalone objects. In this case, the write_only argument should be set to True to disable the creation of a listening thread, which only makes sense in a server. For example:

# connect to the redis queue as an external process
external_sio = socketio.RedisManager('redis://', write_only=True)
# emit an event
external_sio.emit('my event', data={'foo': 'bar'}, room='my room')

A limitation of the write-only client manager object is that it cannot receive callbacks when emitting. When the external process needs to receive callbacks, using a client to connect to the server with read and write support is a better option than a write-only client manager.

    NAME

    python-socketio — asynchronous Python client/server for Socket.IO

    GETTING STARTED

    This package provides the python-socketio library, which offers a client and a server component for real-time bidirectional event-based communication.

    To use the server, you typically integrate it with an ASGI or WSGI web framework like FastAPI, Flask, or Django.

    To use the client, you can connect to a Socket.IO server.

    THE SOCKET.IO CLIENTS

    The client module provides classes for connecting to Socket.IO servers.

    Client(async_mode='asgi', logger=False, engineio_logger=False, **engineio_options)
    The main client class.
    AsyncClient(async_mode='asgi', logger=False, engineio_logger=False, **engineio_options)
    Asynchronous client class. This is the recommended client to use in asynchronous applications.

    THE SOCKET.IO SERVER

    The server module provides classes for creating a Socket.IO server.

    Server(async_mode='asgi', cors_allowed_origins='*', logger=False, engineio_logger=False, **engineio_options)
    The main server class.

    API REFERENCE

    This section details some of the key methods available in the python-socketio library.

    e_disconnect(sid, namespace)
    Put the client in the to-be-disconnected list.

    This allows the client data structures to be present while the disconnect handler is invoked, but still recognize the fact that the client is soon going away.

    async trigger_callback(sid, id, data)
    Invoke an application callback.
