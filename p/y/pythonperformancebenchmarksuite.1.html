PYTHONPERFORMANCEBENCHMARKSUITE(1) Suite de pruebas de rendimiento de Python PYTHONPERFORMANCEBENCHMARKSUITE(1)

NOMBRE

pythonperformancebenchmarksuite - Documentación de la Suite de pruebas de rendimiento de Python

El proyecto pyperformance está destinado a ser una fuente autorizada de pruebas de rendimiento para todas las implementaciones de Python. El enfoque está en pruebas de rendimiento del mundo real, en lugar de pruebas sintéticas, utilizando aplicaciones completas cuando sea posible.

  • Documentación de pyperformance http://pyperformance.readthedocs.io/
  • Proyecto GitHub de pyperformance https://github.com/python/pyperformance (código fuente, incidencias)
  • Descargar pyperformance en PyPI https://pypi.python.org/pypi/pyperformance

pyperformance se distribuye bajo la licencia MIT.

USO

Instalación

Comando para instalar pyperformance:

python3 -m pip install pyperformance

El comando instala un nuevo programa pyperformance.

Si es necesario, las dependencias pyperf y six se instalan automáticamente.

pyperformance funciona en Python 3.6 y versiones posteriores, pero puede funcionar en Python 3.4 y 3.5.

En tiempo de ejecución, los archivos de desarrollo de Python (archivos de cabecera) pueden ser necesarios para instalar algunas dependencias como dulwich_log o psutil, para compilar su extensión C. Comandos en Fedora para instalar dependencias:

  • Python 3: sudo dnf install python3-devel
  • PyPy: sudo dnf install pypy-devel

Notas en Windows

En Windows, para permitir que pyperformance compile dependencias desde el código fuente como greenlet, dulwich o psutil, si desea utilizar un python.exe compilado desde el código fuente, no debe usar python.exe directamente. En su lugar, debe ejecutar el comando poco conocido PC\layout para crear una estructura de sistema de archivos que se asemeje a un Python instalado:

.\python.bat -m PC.layout --preset-default --copy installed -v

(Use el indicador --help para más información sobre PC\layout.)

Ahora puede usar el ejecutable de Python "installed":

installed\python.exe -m pip install pyperformance
installed\python.exe -m pyperformance run ...

Usar un ejecutable de Python *realmente* instalado (por ejemplo, a través de py) también funciona bien.

Ejecutar pruebas de rendimiento

Comandos para comparar el rendimiento de Python 3.6 y Python 3.7:

pyperformance run --python=python3.6 -o py36.json
pyperformance run --python=python3.7 -o py37.json
pyperformance compare py36.json py37.json

Nota: la sintaxis python3 -m pyperformance ... también funciona (ej: python3 -m pyperformance run -o py37.json), pero requiere instalar pyperformance en cada versión de Python probada.

Los archivos JSON son producidos por el módulo pyperf y, por lo tanto, pueden ser analizados utilizando comandos de pyperf:

python3 -m pyperf show py36.json
python3 -m pyperf check py36.json
python3 -m pyperf metadata py36.json
python3 -m pyperf stats py36.json
python3 -m pyperf hist py36.json
python3 -m pyperf dump py36.json
(...)

También es posible usar pyperf para comparar los resultados de dos archivos JSON:

python3 -m pyperf compare_to py36.json py37.json --table

2to3

Ejecuta la herramienta 2to3 en el directorio pyperformance/benchmarks/data/2to3/: copia de los archivos django/core/*.py de Django 1.1.4, 9 archivos.

Ejecuta el comando python -m lib2to3 -f all <archivos> donde python es sys.executable. Por lo tanto, la prueba no solo mide el rendimiento de Python en sí, sino también el rendimiento del módulo lib2to3, que puede variar según la versión de Python.

Nota:

Los archivos se denominan .py.txt en lugar de .py para evitar que se les apliquen las comprobaciones de PEP 8 y, en general, para no modificarlos.

async_tree

Benchmark de carga de trabajo asíncrona, que llama a asyncio.gather() en un árbol (6 niveles de profundidad, 6 ramas por nivel) con los nodos hoja simulando algún trabajo [potencialmente] asíncrono (dependiendo de la variante del benchmark). Variantes disponibles:

  • async_tree: sin trabajo asíncrono real en ningún nodo hoja.
  • async_tree_io: todos los nodos hoja simulan carga de trabajo de IO asíncrona (async sleep 50ms).
  • async_tree_memoization: todos los nodos hoja simulan carga de trabajo de IO asíncrona con el 90% de los datos memorizados.
  • async_tree_cpu_io_mixed: la mitad de los nodos hoja simulan carga de trabajo intensiva en CPU (math.factorial(500)) y la otra mitad simula la misma carga de trabajo que la variante async_tree_memoization.

Estos benchmarks también tienen un sabor "eager" que utiliza la fábrica de tareas "eager" de asyncio, si está disponible.

chaos

Crea fractales similares al juego del caos. Opciones de línea de comandos:

--thickness THICKNESS
                      Grosor (por defecto: 0.25)

crypto_pyaes

Benchmarking de una implementación en puro Python del cifrador de bloque AES en modo CTR utilizando el módulo pyaes.

El benchmark es más lento en CPython 3 en comparación con CPython 2.7, porque CPython 3 ya no tiene el tipo de "entero pequeño" (int). El tipo int de CPython 3 ahora siempre tiene un tamaño arbitrario, como el tipo long de CPython 2.7.

Ver pyaes https://github.com/ricmoo/pyaes: Una implementación en puro Python del algoritmo de cifrado de bloque AES y los modos comunes de operación (CBC, CFB, CTR, ECB y OFB).

deepcopy

Benchmark del método copy.deepcopy de Python. El método deepcopy se realiza sobre un diccionario anidado y una clase de datos (dataclass).

deltablue

Benchmark DeltaBlue

Adaptado para el proyecto PyPy. Contribuido por Daniel Lindsley

Esta implementación del benchmark DeltaBlue fue portada directamente del código fuente de V8 https://github.com/v8/v8/blob/master/benchmarks/deltablue.js, que a su vez se derivó de la implementación de Smalltalk por John Maloney y Mario Wolczko. La implementación original en Javascript tenía licencia GPL.

dulwich_log

Itera sobre los commits del repositorio Git de asyncio utilizando el módulo Dulwich. Utiliza el repositorio pyperformance/benchmarks/data/asyncio.git/.

Pseudocódigo del benchmark:

repo = dulwich.repo.Repo(repo_path)
head = repo.head()
for entry in repo.get_walker(head):
    pass

Ver el proyecto Dulwich https://www.dulwich.io/.

    Sometimes a benchmark will have one or more variants that run using the same script. Variants like this are supported by pyperformance without requiring much extra effort.

Benchmark Directory Structure

Normally a benchmark is structured like this:

bm_NAME/
   data/  # if needed
   requirements.txt  # lock file, if any
   pyproject.toml
   run_benchmark.py

(Note the "bm_" prefix on the directory name.)

"pyproject.toml" holds the metadata. "run_benchmark.py" holds the actual benchmark code. Both are necessary.

pyperformance treats the metadata file as the fundamental source of information about a benchmark. A manifest for a set of benchmarks is effectively a mapping of names to metadata files. So a metadata file is essential. It can be located anywhere on disk. However, if it isn't located in the structure described above then the metadata must identify where to find the other files.

Other than that, only a benchmark script (e.g. "run_benchmark.py" above) is required. All other files are optional.

When a benchmark has variants, each has its own metadata file next to the normal "pyproject.toml", named "bm_NAME.toml". (Note the "bm_" prefix.) The format of variant metadata files is exactly the same. pyperformance treats them the same, except that the sibling "pyproject.toml" is inherited by default.

Manifest Files

A manifest file identifies a set of benchmarks, as well as (optionally) how they should be grouped. pyperformance uses the manifest to determine which benchmarks are available to run (and thus which to run by default).

A manifest normally looks like this:

[benchmarks]
name        metafile
bench1      somedir/bm_bench1/pyproject.toml
bench2      somedir/pyproject.toml
bench3      ../anotherdir

The "benchmarks" section is a table with rows of tab-separated-values. The "name" value is how pyperformance will identify the benchmark. The "metafile" value is where pyperformance will look for the benchmark's metadata. If a metafile is a directory then it looks for "pyproject.toml" in that directory.

Benchmark Groups

The other secti

Los `sections` en el archivo de manifiesto se relacionan con la agrupación: ``` [benchmarks] name metafile bench1 somedir/bm_bench1 bench2 somedir/bm_bench2 bench3 anotherdir/mybench.toml [groups] tag1 tag2 [group default] bench2 bench3 [group tricky] bench2 ``` La sección `groups` especifica los grupos disponibles que pueden ser identificados por etiquetas de benchmark (ver sobre etiquetas en la sección de metadatos más abajo). Cualquier otra sección de grupo en el manifiesto se añade automáticamente a la lista de grupos disponibles. Si no se especifica ningún grupo `default`, se añade automáticamente uno con todos los benchmarks de la sección `benchmarks`. Si no hay sección `groups` ni secciones de grupo individuales (aparte de `default`), el conjunto de todas las etiquetas de los benchmarks conocidos se trata como `groups`. Un grupo llamado `all` también se añade automáticamente, el cual contiene todos los benchmarks conocidos. Los benchmarks pueden ser excluidos de un grupo usando un prefijo `-` (menos). Cualquier benchmark que ya esté en la lista (en ese momento) y coincida, será eliminado de la lista. Si la primera entrada en la sección es una exclusión, todos los benchmarks conocidos se añaden primero a la lista antes de aplicar la exclusión. Por ejemplo: ``` [benchmarks] name metafile bench1 somedir/bm_bench1 bench2 somedir/bm_bench2 bench3 anotherdir/mybench.toml [group default] -bench1 ``` Esto significa que por defecto solo se ejecutan `bench2` y `bench3`.

Fusión de Manifiestos

Para combinar manifiestos, usa la sección [includes] en el manifiesto:

[includes]
project1/benchmarks/MANIFEST
project2/benchmarks/MANIFEST
<default>

Ten en cuenta que <default> es lo mismo que incluir el archivo de manifiesto para los benchmarks predeterminados de pyperformance.

Un Conjunto de Benchmarks Local

A menudo, un proyecto tendrá más de un benchmark que tratará como un conjunto. pyperformance maneja esto sin ningún trabajo adicional.

En el directorio que contiene el archivo de manifiesto, coloca todos los benchmarks. Luego, pon <local> en la columna "metafile", así:

[benchmarks]
name        metafile
bench1      <local>
bench2      <local>
bench3      <local>
bench4      <local>
bench5      <local>

Buscará en DIR/bm_NAME/pyproject.toml.

Si también hay variantes, identifica el benchmark principal en el valor "metafile", así:

[benchmarks]
name        metafile
bench1      <local>
bench2      <local>
bench3      <local>
variant1    <local:bench3>
variant2    <local:bench3>

pyperformance buscará en DIR/bm_BASE/bm_NAME.toml, donde "BASE" es la parte después de "local:".

El Conjunto de Benchmarks de un Proyecto

Un proyecto de Python puede identificar su conjunto de benchmarks colocando la ruta al archivo de manifiesto en el pyproject.toml de nivel superior del proyecto. También se pueden identificar manifiestos adicionales:

[tool.pyperformance]
manifest = "..."
manifests = ["...", "..."]

(Recordatorio: ese es el pyproject.toml, no el archivo de manifiesto.)

Archivos de Metadatos de Benchmarks

El archivo de metadatos de un benchmark (generalmente pyproject.toml) sigue el formato especificado en PEP 621 https://www.python.org/dev/peps/pep-0621 y PEP 518 https://www.python.org/dev/peps/pep-0518. Por lo tanto, hay dos secciones admitidas en el archivo: "project" y "tool.pyperformance".

Un archivo de metadatos típico se vería algo así:

[project]
version = "0.9.1"
dependencies = ["pyperf"]
dynamic = ["name"]
[tool.pyperformance]
name = "my_benchmark"

Uno muy detallado podría verse así:

[project]
name = "pyperformance_bm_json_dumps"
version = "0.9.1"
description = "A benchmark for json.dumps()"
requires-python = ">=3.8"
dependencies = ["pyperf"]
urls = {repository = "https://github.com/python/pyperformance"}
dynamic = ["version"]
[tool.pyperformance]
name = "json_dumps"
tags = "serialize"
runscript = "bench.py"
datadir = ".data-files/extras"
extra_opts = ["--special"]

Herencia

Para que un benchmark herede de otro (o de metadatos comunes), el campo "inherits" está disponible:

[project]
dependencies = ["pyperf"]
dynamic = ["name", "version"]
[tool.pyperformance]
name = "my_benchmark"
inherits = "../common.toml"

Todos los valores en cualquiera de las secciones de los metadatos heredados se tratan como valores predeterminados, sobre los cuales se aplican los metadatos actuales. En el ejemplo anterior, por ejemplo, se usaría aquí un valor para "version" en common.toml.

Si el valor "inherits" es un directorio (incluso para ".."), entonces se heredará "base.toml" en ese directorio.

Para las variantes, el pyproject.toml base es el valor predeterminado para "inherits".

Valores Inferidos

En algunas situaciones, los valores omitidos se inferirán de otros datos disponibles (incluso para campos requeridos).

  • project.name <= tool.pyperformance.name
  • project.* <= metadatos heredados (excepto "name" y "dynamic")
  • tool.pyperformance.name <= nombre del archivo de metadatos
  • tool.pyperformance.* <= metadatos heredados (excepto "name" y "inherits")

Cuando el nombre se infiere del nombre del archivo para un benchmark estructurado regularmente, se elimina el prefijo "bm_" del directorio del benchmark. Si es una variante, se elimina ese prefijo del nombre del archivo de metadatos, así como la extensión .toml.

campo tipo R T B D
project.name str X X
project.version ver X X X
project.dependencies [str] X
project.dynamic [str]

"R": requerido "T": inferido de la sección tool "B": inferido de los metadatos heredados "D": para benchmarks predeterminados, inferido de pyperformance

"dynamic" es requerido por PEP 621 para cuando un campo será rellenado dinámicamente por la herramienta. Esto es especialmente importante para campos requeridos.

Todos los demás campos PEP 621 son opcionales (por ejemplo, requires-python = ">=3.8", {repository = "https://github.com/..."}).

      Historial

      El proyecto se trasladó a https://github.com/python/performance en agosto de 2016. Archivos reorganizados, benchmarks parcheados para usar el módulo perf para ejecutar benchmarks en múltiples procesos.

      El proyecto comenzó en diciembre de 2008 por Collin Winter y Jeffrey Yasskin para el proyecto Unladen Swallow. El proyecto estuvo alojado en https://hg.python.org/benchmarks hasta febrero de 2016

      Otros benchmarks de Python:

      • CPython: speed.python.org https://speed.python.org/ usa pyperf, pyperformance y Codespeed https://github.com/tobami/codespeed/ (aplicación web Django)
      • PyPy: speed.pypy.org http://speed.pypy.org/ usa benchmarks de PyPy https://bitbucket.org/pypy/benchmarks
      • Pyston: pyston-perf https://github.com/dropbox/pyston-perf y speed.pyston.org http://speed.pyston.org/
      • Benchmarks de Numba http://numba.pydata.org/numba-benchmark/
      • Cython: Demos/benchmarks de Cython https://github.com/cython/cython/tree/master/Demos/benchmarks
      • Pythran: numpy-benchmarks https://github.com/serge-sans-paille/numpy-benchmarks

      Ver también la lista de correo de velocidad de Python https://mail.python.org/mailman/listinfo/speed y el módulo pyperf de Python http://pyperf.readthedocs.io/ (usado por pyperformance).

      pyperformance aún no está optimizado para PyPy: usar el proyecto de benchmarks de PyPy https://foss.heptapod.net/pypy/benchmarks en su lugar para medir el rendimiento de PyPy.
