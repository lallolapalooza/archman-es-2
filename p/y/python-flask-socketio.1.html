INTRODUCCIÓN

Instalación

Puedes instalar este paquete de la forma habitual usando pip:

pip install flask-socketio

Requisitos

Flask-SocketIO es compatible con Python 3.6+. Los servicios asíncronos en los que se basa este paquete se pueden seleccionar entre tres opciones:

  • eventlet es la opción de mejor rendimiento, con soporte para transportes de sondeo largo (long-polling) y WebSocket.
  • gevent es compatible en varias configuraciones diferentes. El transporte de sondeo largo está totalmente soportado con el paquete gevent, pero a diferencia de eventlet, gevent no tiene soporte nativo para WebSocket. Para añadir soporte para WebSocket, actualmente hay dos opciones. Instalar el paquete gevent-websocket añade soporte WebSocket a gevent o se puede usar el servidor web uWSGI, que viene con funcionalidad WebSocket. El uso de gevent es también una opción de buen rendimiento, pero ligeramente inferior a eventlet.
  • El servidor de desarrollo de Flask basado en Werkzeug también puede ser utilizado, con la advertencia de que este servidor web está destinado solo para uso en desarrollo, por lo que solo debe usarse para simplificar el flujo de trabajo de desarrollo y no para producción.

La extensión detecta automáticamente qué framework asíncrono utilizar basándose en lo que está instalado. Se da preferencia a eventlet, seguido de gevent. Para soporte WebSocket en gevent, se prefiere uWSGI, seguido de gevent-websocket. Si ni eventlet ni gevent están instalados, se utiliza el servidor de desarrollo de Flask.

Compatibilidad de versiones

El protocolo Socket.IO ha pasado por varias revisiones, y algunas de estas introdujeron cambios incompatibles hacia atrás, lo que significa que el cliente y el servidor deben usar versiones compatibles para que todo funcione.

EMPEZANDO

Inicialización

El siguiente ejemplo de código muestra cómo añadir Flask-SocketIO a una aplicación Flask:

from flask import Flask, render_template
from flask_socketio import SocketIO
app = Flask(__name__)
app.config['SECRET_KEY'] = 'secreto!'
socketio = SocketIO(app)
if __name__ == '__main__':
    socketio.run(app)

También se admite el estilo de inicialización init_app(). Para iniciar el servidor web, simplemente ejecuta tu script. Observa la forma en que se inicia el servidor web. La función socketio.run() encapsula el inicio del servidor web y reemplaza el inicio estándar del servidor de desarrollo de Flask app.run(). Cuando la aplicación está en modo de depuración, todavía se utiliza el servidor de desarrollo Werkzeug y se configura correctamente dentro de socketio.run(). En modo de producción, se utiliza el servidor web eventlet si está disponible, de lo contrario se utiliza el servidor web gevent. Si eventlet y gevent no están instalados, se utiliza el servidor de desarrollo Werkzeug.

El comando flask run introducido en Flask 0.11 puede ser utilizado para iniciar un servidor de desarrollo Flask-SocketIO basado en Werkzeug, pero este método de inicio del servidor Flask-SocketIO no se recomienda debido a la falta de soporte WebSocket. Las versiones anteriores de este paquete incluían una versión personalizada del comando flask run que permitía el uso de WebSocket en servidores de producción eventlet y gevent, pero esta funcionalidad ha sido descontinuada en favor del método de inicio socketio.run(app) que se muestra arriba, el cual es más robusto.

Recepción de mensajes

Al usar SocketIO, los mensajes son recibidos por ambas partes como eventos. En el lado del cliente se usan callbacks de Javascript. Con Flask-SocketIO, el servidor necesita registrar manejadores para estos eventos, de manera similar a cómo las rutas son manejadas por funciones de vista.

El siguiente ejemplo crea un manejador de eventos en el lado del servidor para un evento sin nombre:

@socketio.on('message')
def handle_message(data):
    print('mensaje recibido: ' + data)

Otros Servidores Web

Si bien el servidor de desarrollo que viene con Flask es suficiente para la creación de prototipos, no está destinado a la producción. Para el despliegue, necesita un servidor WSGI más robusto. Flask-SocketIO es compatible con muchos de estos servidores, pero solo algunos tienen soporte nativo para WebSockets. En esta sección se describen los servidores más populares que son compatibles con Flask-SocketIO.

Servidor Web Gunicorn

Gunicorn es un servidor WSGI muy popular. Puede ejecutarse en modo de un solo proceso o en modo de múltiples procesos. Cuando se ejecuta en modo de múltiples procesos, Gunicorn utiliza un algoritmo de balanceo de carga simple para distribuir las solicitudes de entrada entre sus procesos de trabajo. La desventaja de este algoritmo es que no es posible utilizar múltiples procesos de trabajo de Gunicorn con Flask-SocketIO, ya que cada proceso de trabajo solo ve un subconjunto de las conexiones de los clientes, lo que hace que el servidor de chat no funcione correctamente.

gunicorn -w 1 --threads 100 module:app

En todos estos comandos, module es el módulo o paquete de Python que define la instancia de la aplicación, y app es la propia instancia de la aplicación.

Debido al limitado algoritmo de balanceo de carga utilizado por gunicorn, no es posible usar más de un proceso de trabajo cuando se utiliza este servidor web. Por esta razón, todos los ejemplos anteriores incluyen la opción -w 1.

Servidor Web uWSGI

Cuando se utiliza el servidor uWSGI en combinación con gevent, el servidor Socket.IO puede aprovechar el soporte nativo de WebSocket de uWSGI.

Una explicación completa de la configuración y el uso del servidor uWSGI está fuera del alcance de esta documentación. El servidor uWSGI es un paquete bastante complejo que proporciona un conjunto de opciones amplio y completo. Debe compilarse con soporte para WebSocket y SSL para que el transporte WebSocket esté disponible. Como introducción, el siguiente comando inicia un servidor uWSGI para la aplicación de ejemplo app.py en el puerto 5000:

$ uwsgi --http :5000 --gevent 1000 --http-websockets --master --wsgi-file app.py --callable app

Uso de nginx como Proxy Inverso de WebSocket

Es posible utilizar nginx como un proxy inverso de front-end que reenvía las solicitudes a la aplicación. Sin embargo, solo las versiones de nginx 1.4 y posteriores admiten el proxy del protocolo WebSocket. A continuación se muestra una configuración básica de nginx que reenvía solicitudes HTTP y WebSocket:

server {
    listen 80;
    server_name _;
    location / {
        include proxy_params;
        proxy_pass http://127.0.0.1:5000;
    }
    location /static/ {
        alias <ruta-a-tu-aplicacion>/static/;
        expires 30d;
    }
    location /socket.io {
        include proxy_params;
        proxy_http_version 1.1;
        proxy_buffering off;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";
        proxy_pass http://127.0.0.1:5000/socket.io;
    }
}

El siguiente ejemplo agrega soporte para balancear la carga de múltiples servidores Socket.IO:

upstream socketio_nodes {
    ip_hash;
    server 127.0.0.1:5000;
    server 127.0.0.1:5001;
    server 127.0.0.1:5002;
    # ¡para escalar la aplicación, solo agrega más nodos aquí!
}
server {
    listen 80;
    server_name _;
    location / {
        include proxy_params;
        proxy_pass http://127.0.0.1:5000;
    }
    location /static/ {
        alias <ruta-a-tu-aplicacion>/static/;
        expires 30d;
    }
    location /socket.io {
        include proxy_params;
        proxy_http_version 1.1;
        proxy_buffering off;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "Upgrade";
        proxy_pass http://socketio_nodes/socket.io;
    }
}

Si bien los ejemplos anteriores pueden funcionar como una configuración inicial, ten en cuenta que una instalación de producción de nginx necesitará una configuración más completa que cubra otros aspectos de despliegue, como el soporte SSL.

Uso de Múltiples Trabajadores

Flask-SocketIO admite múltiples trabajadores detrás de un balanceador de carga a partir de la versión 2.0. Desplegar múltiples trabajadores brinda a las aplicaciones que utilizan Flask-SocketIO la capacidad de distribuir las conexiones de clientes entre múltiples procesos y hosts, y de esta manera escalar para admitir un número muy grande de clientes concurrentes.

Hay dos requisitos para usar múltiples trabajadores de Flask-SocketIO:

  • El balanceador de carga debe configurarse para reenviar todas las solicitudes HTTP de un cliente determinado siempre al mismo trabajador. Esto a veces se conoce como "sesiones persistentes". Para nginx, usa la directiva ip_hash para lograr esto. Gunicorn no se puede usar con múltiples trabajadores porque su algoritmo de balanceo de carga no admite sesiones persistentes.
  • Dado que cada uno de los servidores posee solo un subconjunto de las conexiones de clientes, los servidores utilizan una cola de mensajes como Redis o RabbitMQ para coordinar operaciones complejas como la difusión y las salas.

Cuando se trabaja con una cola de mensajes, hay dependencias adicionales que deben instalarse:

  • Para Redis, el paquete redis debe estar instalado (pip install redis).
  • Para RabbitMQ, el paquete kombu debe estar instalado (pip install kombu).
  • Para Kafka, el paquete kafka-python debe estar instalado (pip install kafka-python).
  • Para otras colas de mensajes compatibles con Kombu, consulta la documentación de Kombu para averiguar qué dependencias se necesitan.
  • Si se utilizan eventlet o gevent, normalmente se requiere el monkey patching de la biblioteca estándar de Python para forzar al paquete de la cola de mensajes a utilizar funciones y clases amigables con las corrutinas.

Para eventlet, el monkey patching se realiza con:

import eventlet
eventlet.monkey_patch()

Para gevent, puedes hacer monkey patching de la biblioteca estándar con:

from gevent import monkey
monkey.patch_all()

En ambos casos, se recomienda aplicar el monkey patching al principio de tu script principal, incluso antes de tus importaciones.

Para iniciar múltiples servidores Flask-SocketIO, primero debes asegurarte de que el servicio de cola de mensajes esté en ejecución. Para iniciar un servidor Socket.IO y hacer que se conecte a la cola de mensajes, agrega el argumento message_queue al constructor de SocketIO:

socketio = SocketIO(app, message_queue='redis://')

El valor del argumento message_queue es la URL de conexión del servicio de cola que se utiliza. Para una cola de redis que se ejecuta en el mismo host que el servidor, se puede usar la URL 'redis://'. Del mismo modo, para una cola RabbitMQ predeterminada, se puede usar la URL 'amqp://'. Para Kafka, usa una URL kafka://. El paquete Kombu tiene una sección de *documentación* que describe el formato de las URL para todas las colas compatibles.

Emitir desde un Proceso Externo

Para muchos tipos de aplicaciones, es necesario emitir eventos desde un proceso que no sea el servidor SocketIO, por ejemplo, un trabajador de Celery. Si el servidor o servidores SocketIO están configurados para escuchar en una cola de mensajes como se muestra en la sección anterior, entonces cualquier otro proceso puede crear su propia instancia de SocketIO y usarla para emitir eventos de la misma manera que lo hace el servidor.

Por ejemplo, para una aplicación que se ejecuta en un servidor web eventlet y utiliza una cola de mensajes Redis, el siguiente script de Python transmite un evento a todos los clientes:

socketio = SocketIO(message_queue='redis://')
socketio.emit('my event', {'data': 'foo'}, namespace='/test')

Cuando se utiliza la instancia de SocketIO de esta manera, la instancia de la aplicación Flask no se pasa al constructor.

El argumento channel de SocketIO se puede utilizar para seleccionar un canal de comunicación específico a través de la cola de mensajes. Usar un nombre de canal personalizado es necesario cuando hay múltiples servicios SocketIO independientes compartiendo la misma cola.

Flask-SocketIO no aplica monkey patching cuando se utilizan eventlet o gevent. Pero cuando se trabaja con una cola de mensajes, es muy probable que el paquete de Python que se comunica con el servicio de cola de mensajes se bloquee si la biblioteca estándar de Python no se monkey patch. Es importante tener en cuenta que un proceso externo que desea conectarse a un servidor SocketIO no necesita usar eventlet o gevent como el servidor principal. Tener un servidor que use un framework de corrutinas, mientras que un proceso externo no es un problema. Por ejemplo, los trabajadores de Celery no necesitan ser configurados para usar eventlet o gevent solo porque el servidor principal lo hace. Pero si tu proceso externo utiliza un framework de corrutinas por alguna razón, entonces es probable que se necesite monkey patching, para que el acceso a la cola de mensajes utilice funciones y clases amigables con las corrutinas.

Controles de Origen Cruzado

Por razones de seguridad, este servidor aplica una política de mismo origen por defecto. En términos prácticos, esto significa lo siguiente:

  • Si una solicitud HTTP o WebSocket entrante incluye la cabecera Origin, esta cabecera debe coincidir con el esquema y el host de la URL de conexión. En caso de discrepancia, se devuelve una respuesta con código de estado 400 y se rechaza la conexión.
  • No se imponen restricciones a las solicitudes entrantes que no incluyen la cabecera Origin.

Si es necesario, la opción cors_allowed_origins puede usarse para permitir otros orígenes. Este argumento puede configurarse como una cadena para establecer un único origen permitido, o como una lista para permitir múltiples orígenes. Un valor especial de '*' se puede usar para indicar al servidor que permita todos los orígenes, pero esto debe hacerse con cuidado, ya que podría hacer que el servidor sea vulnerable a ataques de Falsificación de Solicitud entre Sitios (CSRF).

Actualización a Flask-SocketIO 5.x desde las versiones 4.x

El protocolo Socket.IO introdujo recientemente una serie de cambios incompatibles con versiones anteriores. Las versiones 5.x de Flask-SocketIO adoptaron estos cambios y, por esa razón, solo se puede usar con clientes que también se hayan actualizado

al protocolo actual. En particular, esto significa que el cliente JavaScript debe actualizarse a una versión 3.x, y si tu cliente no se ha actualizado a la última versión del protocolo Socket.IO, entonces debes usar una versión 4.x de Flask-SocketIO. Los siguientes cambios en el protocolo son de importancia, ya que pueden afectar a las aplicaciones existentes: * El namespace por defecto '/' ya no se conecta automáticamente y ahora se trata de la misma manera que otros namespaces. * Cada conexión de namespace tiene su propio valor sid, diferente de los demás y diferente del sid de Engine.IO. * Flask-SocketIO ahora utiliza los mismos valores de intervalo y tiempo de espera de ping que la implementación de referencia de JavaScript, que son 25 y 5 segundos respectivamente. * El mecanismo de ping/pong se ha invertido. En la versión actual del protocolo, el servidor emite un ping y el cliente responde con un pong. * El tamaño máximo de carga útil permitido por defecto para los paquetes de long-polling se ha reducido de 100MB a 1MB. * La cookie io ya no se envía al cliente por defecto.

Este método emite un evento con una devolución de llamada y espera a que la devolución de llamada sea invocada por el cliente antes de retornar. Si la devolución de llamada no se invoca antes del tiempo de espera, se genera una excepción TimeoutError. Si la conexión de Socket.IO se interrumpe durante la espera, este método todavía espera hasta el tiempo de espera especificado. Ejemplo:

def get_status(client, data):

Parámetros
  • event -- El nombre del evento de usuario a emitir.
  • args -- Un diccionario con los datos JSON para enviar como carga útil.
  • namespace -- El espacio de nombres bajo el cual se enviará el mensaje. Por defecto, el espacio de nombres global.

python-flask-socketio(1)

NOMBRE

python-flask-socketio - Extensión Flask-SocketIO.

INTRODUCCIÓN

Socket.IO permite la comunicación bidireccional en tiempo real entre el cliente y el servidor. También proporciona una garantía de conexión en tiempo real.

Flask-SocketIO es una extensión para Flask que facilita la integración de Socket.IO en una aplicación Flask.

EMPEZANDO

Para empezar con Flask-SocketIO, necesita instalar la extensión y luego inicializarla con su aplicación Flask:


pip install Flask-SocketIO
                    

from flask import Flask
from flask_socketio import SocketIO

app = Flask(__name__)
socketio = SocketIO(app)

@app.route('/')
def index():
    return "¡Hola, mundo!"

if __name__ == '__main__':
    socketio.run(app, debug=True)

Esto creará una aplicación Flask básica con Socket.IO habilitado. Puede conectarse a esta aplicación usando un cliente Socket.IO.

NOTAS DE IMPLEMENTACIÓN

Flask-SocketIO está construido sobre la biblioteca Socket.IO de Python, que proporciona la funcionalidad principal de Socket.IO. Flask-SocketIO agrega una capa de integración con Flask, lo que facilita la configuración y el uso de Socket.IO dentro de una aplicación Flask.

DESPLIEGUE

Al desplegar una aplicación Flask-SocketIO, debe tener en cuenta que Socket.IO requiere un servidor web que pueda manejar conexiones WebSocket. Se recomienda utilizar un servidor web como Gunicorn o uWSGI con un proxy inverso como Nginx.

Aquí hay un ejemplo de configuración de Gunicorn para Flask-SocketIO:


gunicorn -k geventwebsocket.gunicorn.workers.GeventWebSocketWorker -w 1 myapp:app

Deberá instalar el worker de geventwebsocket:


pip install geventwebsocket

ACTUALIZANDO A FLASK-SOCKETIO 5.X DESDE LAS RELEASES 4.X

La versión 5.x de Flask-SocketIO introduce varios cambios importantes respecto a la versión 4.x. Estos cambios están diseñados para mejorar el rendimiento y la flexibilidad de la extensión.

Los cambios clave incluyen:

  • Soporte para gevent y eventlet mejorado.
  • Cambios en la API para un uso más intuitivo.
  • Mejoras en el manejo de errores y la gestión de desconexiones.

Consulte la documentación oficial de Flask-SocketIO para obtener una guía detallada sobre cómo actualizar su aplicación.

REFERENCIA API

Flask-SocketIO expone varias clases y funciones que puede utilizar para interactuar con Socket.IO. Las más importantes son:

  • SocketIO(app=None, **kwargs): La clase principal para inicializar Flask-SocketIO.
  • socketio.emit(event, data, ...): Emite un evento a uno o varios clientes.
  • socketio.on(event, handler): Registra un manejador para un evento específico.
  • socketio.send(data, ...): Envía un mensaje a todos los clientes conectados.
  • socketio.receive(handler): Registra un manejador para recibir mensajes.

Para obtener una lista completa de la API, consulte la documentación oficial.
