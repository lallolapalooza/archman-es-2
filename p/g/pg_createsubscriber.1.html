NOMBRE

pg_createsubscriber - convertir una réplica física en una nueva réplica lógica

SINOPSIS

pg_createsubscriber [opción...] {-d | --database}nombre_db {-D | --pgdata}directorio_datos {-P | --publisher-server}cadena_conexion

DESCRIPCIÓN

pg_createsubscriber crea una nueva réplica lógica a partir de un servidor standby físico. Todas las tablas en la base de datos especificada se incluyen en la configuración de replicación lógica. Se crea un par de objetos de publicación y suscripción para cada base de datos. Debe ejecutarse en el servidor de destino.

Después de una ejecución exitosa, el estado del servidor de destino es análogo a una configuración de replicación lógica recién creada. La principal diferencia entre la configuración de replicación lógica y pg_createsubscriber es cómo se realiza la sincronización de datos. pg_createsubscriber no copia los datos iniciales de la tabla. Solo realiza la fase de sincronización, que asegura que cada tabla alcance un estado sincronizado.

pg_createsubscriber está dirigido a sistemas de bases de datos grandes porque en la configuración de replicación lógica, la mayor parte del tiempo se dedica a la copia inicial de datos. Además, un efecto secundario de este largo tiempo dedicado a sincronizar datos suele ser una gran cantidad de cambios a aplicar (que se produjeron durante la copia inicial de datos), lo que aumenta aún más el tiempo hasta que la réplica lógica esté disponible. Para bases de datos más pequeñas, se recomienda configurar la replicación lógica con sincronización de datos inicial. Para más detalles, consulte la opción copy_data de CREATE SUBSCRIPTION.

OPCIONES

pg_createsubscriber acepta los siguientes argumentos de línea de comandos:

-a
--all

Crea una suscripción por base de datos en el servidor de destino. Se exceptúan las bases de datos de plantilla y las bases de datos que no permiten conexiones. Para descubrir la lista de todas las bases de datos, conecte al servidor de origen usando el nombre de la base de datos especificado en la cadena de conexión --publisher-server, o si no se especifica, se usará la base de datos postgres, o si esta no existe, se usará template1. Se utilizan nombres generados automáticamente para suscripciones, publicaciones y slots de replicación cuando se especifica esta opción. Esta opción no se puede usar junto con --database, --publication, --replication-slot o --subscription.

-d nombre_db
--database=nombre_db

El nombre de la base de datos en la que crear una suscripción. Se pueden seleccionar varias bases de datos escribiendo varios intercambios -d. Esta opción no se puede usar junto con -a. Si la opción -d no se proporciona, el nombre de la base de datos se obtendrá de la opción -P. Si el nombre de la base de datos no se especifica ni en la opción -d ni en la opción -P, y la opción -a no se especifica, se informará un error.

-D directorio
--pgdata=directorio

El directorio de destino que contiene un directorio de clúster de una réplica física.

-n
--dry-run

Haz todo excepto modificar realmente el directorio de destino.

-p puerto
--subscriber-port=puerto

El número de puerto en el que el servidor de destino está escuchando conexiones. Por defecto, el servidor de destino se ejecuta en el puerto 50432 para evitar conexiones de clientes no intencionadas.

-P cadena_conexion
--publisher-server=cadena_conexion

La cadena de conexión al editor. Para detalles, consulte la Sección 32.1.1.

-s dir
--socketdir=dir

El directorio a utilizar para los sockets postmaster en el servidor de destino. El valor predeterminado es el directorio actual.

-t segundos
--recovery-timeout=segundos

El número máximo de segundos a esperar a que finalice la recuperación. Establecerlo en 0 lo deshabilita. El valor predeterminado es 0.

-T
--enable-two-phase

Habilita la confirmación en dos fases (two_phase commit) para la suscripción. Cuando se especifican varias bases de datos, esta opción se aplica uniformemente a todas las suscripciones creadas en esas bases de datos. El valor predeterminado es falso.

-U nombre_usuario
--subscriber-username=nombre_usuario

El nombre de usuario para conectarse en el servidor de destino. El valor predeterminado es el nombre de usuario del sistema operativo actual.

-v
--verbose

Habilita el modo detallado. Esto hará que pg_createsubscriber muestre mensajes de progreso e información detallada sobre cada paso en la salida de error estándar. Repetir la opción causa que aparezcan mensajes adicionales de nivel de depuración en la salida de error estándar.

--clean=tipo_objeto

Elimina todos los objetos del tipo especificado de las bases de datos especificadas en el servidor de destino.
•publications: Las publicaciones FOR ALL TABLES establecidas para este suscriptor siempre se eliminan; especificar este tipo de objeto hace que todas las demás publicaciones replicadas desde el servidor de origen también se eliminen.

Los objetos seleccionados para ser eliminados se registran individualmente, incluso durante un --dry-run. No hay oportunidad de afectar o detener la eliminación de los objetos seleccionados, por lo que se recomienda hacer una copia de seguridad de ellos usando pg_dump.

--config-file=nombre_archivo

Utiliza el archivo de configuración principal del servidor especificado para el directorio de datos de destino. pg_createsubscriber utiliza internamente el comando pg_ctl para iniciar y detener el servidor de destino. Le permite especificar el archivo de configuración postgresql.conf real si está almacenado fuera del directorio de datos.

--publication=nombre

El nombre de la publicación para configurar la replicación lógica. Se pueden especificar varias publicaciones escribiendo varios intercambios --publication. El número de nombres de publicación debe coincidir con el número de bases de datos especificadas, de lo contrario se informará un error. El orden de los varios intercambios de nombres de publicación debe coincidir con el orden de los intercambios de bases de datos. Si esta opción no se especifica, se asignará un nombre generado al nombre de la publicación. Esta opción no se puede usar junto con --all.

--replication-slot=nombre

El nombre del slot de replicación para configurar la replicación lógica. Se pueden especificar varios slots de replicación escribiendo varios intercambios --replication-slot. El número de nombres de slots de replicación debe coincidir con el número de bases de datos especificadas, de lo contrario se informará un error. El orden de los varios intercambios de nombres de slots de replicación debe coincidir con el orden de los intercambios de bases de datos. Si esta opción no se especifica, se asignará el nombre de la suscripción al nombre del slot de replicación. Esta opción no se puede usar junto con --all.

--subscription=nombre

El nombre de la suscripción para configurar la replicación lógica. Se pueden especificar varias suscripciones escribiendo varios intercambios --subscription. El número de nombres de suscripción debe coincidir con el número de bases de datos especificadas, de lo contrario se informará un error. El orden de los varios intercambios de nombres de suscripción debe coincidir con el orden de los intercambios de bases de datos. Si esta opción no se especifica, se asignará un nombre generado al nombre de la suscripción. Esta opción no se puede usar junto con --all.

-V
--version

Imprime la versión de pg_createsubscriber y sale.

-?
--help

Muestra ayuda sobre los argumentos de línea de comandos de pg_createsubscriber y sale.

NOTAS

Prerrequisitos

Existen algunos prerrequisitos para que pg_createsubscriber convierta el servidor de destino en una réplica lógica. Si no se cumplen, se informará un error. Los servidores de origen y destino deben tener la misma versión mayor que pg_createsubscriber. El directorio de datos de destino proporcionado debe tener el mismo identificador de sistema que el directorio de datos de origen. El usuario de base de datos proporcionado para el directorio de datos de destino debe tener privilegios para crear suscripciones y usar pg_replication_origin_advance().

El servidor de destino debe usarse como un standby físico. El servidor de destino debe tener max_active_replication_origins y max_logical_replication_worker configurados correctamente.

s configurado a un valor mayor o igual al número de bases de datos especificadas. El servidor de destino debe tener `max_worker_processes` configurado a un valor mayor que el número de bases de datos especificadas. El servidor de destino debe aceptar conexiones locales. Si planeas usar el interruptor --enable-two-phase, también deberás configurar `max_prepared_transactions` apropiadamente.

El servidor de origen debe aceptar conexiones del servidor de destino. El servidor de origen no debe estar en modo de recuperación. El servidor de origen debe tener `wal_level` como `logical`. El servidor de origen debe tener `max_replication_slots` configurado a un valor mayor o igual al número de bases de datos especificadas más las ranuras de replicación existentes. El servidor de origen debe tener `max_wal_senders` configurado a un valor mayor o igual al número de bases de datos especificadas y los procesos de envío de WAL existentes.

Advertencias

Si `pg_createsubscriber` falla después de que el servidor de destino ha sido promovido, es probable que el directorio de datos no se encuentre en un estado recuperable. En tal caso, se recomienda crear un nuevo servidor secundario.

`pg_createsubscriber` generalmente inicia el servidor de destino con configuraciones de conexión diferentes durante la transformación. Por lo tanto, las conexiones al servidor de destino deberían fallar.

Dado que los comandos DDL no son replicados por la replicación lógica, evita ejecutar comandos DDL que cambien el esquema de la base de datos mientras se ejecuta `pg_createsubscriber`. Si el servidor de destino ya se ha convertido en réplica lógica, los comandos DDL podrían no ser replicados, lo que podría causar un error.

Si `pg_createsubscriber` falla durante el procesamiento, los objetos (publicaciones, ranuras de replicación) creados en el servidor de origen se eliminan. La eliminación podría fallar si el servidor de destino no puede conectarse al servidor de origen. En tal caso, un mensaje de advertencia informará sobre los objetos que quedan. Si el servidor de destino está en ejecución, se detendrá.

Si la replicación utiliza `primary_slot_name`, se eliminará del servidor de origen después de la configuración de la replicación lógica.

Si el servidor de destino es una réplica síncrona, los commits de transacciones en el primario podrían esperar a la replicación mientras se ejecuta `pg_createsubscriber`.

A menos que se especifique el interruptor --enable-two-phase, `pg_createsubscriber` configura la replicación lógica con confirmación en dos fases deshabilitada. Esto significa que cualquier transacción preparada se replicará en el momento de COMMIT PREPARED, sin preparación anticipada. Una vez completada la configuración, puedes eliminar y volver a crear manualmente la(s) suscripción(es) con la opción `two_phase` habilitada.

`pg_createsubscriber` cambia el identificador del sistema usando `pg_resetwal`. Evitará situaciones en las que el servidor de destino pueda utilizar archivos WAL del servidor de origen. Si el servidor de destino tiene un secundario, la replicación se romperá y se debería crear un nuevo secundario.

Pueden ocurrir fallos de replicación si faltan archivos WAL necesarios. Para evitar esto, el servidor de origen debe configurar `max_slot_wal_keep_size` a -1 para asegurar que los archivos WAL necesarios no se eliminen prematuramente.

Cómo Funciona

La idea básica es tener un punto de inicio de replicación desde el servidor de origen y configurar una replicación lógica para comenzar desde este punto:

1.Inicia el servidor de destino con las opciones de línea de comandos especificadas. Si el servidor de destino ya está en ejecución, `pg_createsubscriber` terminará con un error.
2.Verifica si el servidor de destino puede ser convertido. También hay algunas verificaciones en el servidor de origen. Si alguno de los prerrequisitos no se cumple, `pg_createsubscriber` terminará con un error.
3.Crea una publicación y una ranura de replicación para cada base de datos especificada en el servidor de origen. Cada publicación se crea usando FOR ALL TABLES. Si la opción --publication no se especifica, la publicación tiene el siguiente patrón de nombre: "pg_createsubscriber_%u_%x" (parámetros: OID de la base de datos, entero aleatorio). Si la opción --replication-slot no se especifica, la ranura de replicación tiene el siguiente patrón de nombre: "pg_createsubscriber_%u_%x" (parámetros: OID de la base de datos, entero aleatorio). Estas ranuras de replicación serán utilizadas por las suscripciones en un paso posterior. La última ranura de replicación LSN se utiliza como punto de detención en el parámetro `recovery_target_lsn` y por las suscripciones como punto de inicio de replicación. Esto garantiza que no se perderá ninguna transacción.
4.Escribe los parámetros de recuperación en el directorio de datos de destino y reinicia el servidor de destino. Especifica un LSN (`recovery_target_lsn`) de la ubicación del registro de escritura anticipada hasta el cual procederá la recuperación. También especifica `promote` como la acción que el servidor debe tomar una vez que se alcanza el objetivo de recuperación. Se agregan parámetros de recuperación adicionales para evitar comportamientos inesperados durante el proceso de recuperación, como el fin de la recuperación tan pronto como se alcanza un estado consistente (el WAL debe aplicarse hasta la ubicación de inicio de la replicación) y múltiples objetivos de recuperación que pueden causar un fallo. Este paso finaliza una vez que el servidor sale del modo en espera y está aceptando transacciones de lectura/escritura. Si se establece la opción --recovery-timeout, `pg_createsubscriber` terminará si la recuperación no finaliza dentro del número de segundos dado.
5.Crea una suscripción para cada base de datos especificada en el servidor de destino. Si la opción --subscription no se especifica, la suscripción tiene el siguiente patrón de nombre: "pg_createsubscriber_%u_%x" (parámetros: OID de la base de datos, entero aleatorio). No copia los datos existentes del servidor de origen. No crea una ranura de replicación. En su lugar, utiliza la ranura de replicación que se creó en el paso anterior. La suscripción se crea pero aún no está habilitada. La razón es que el progreso de la replicación debe establecerse en el punto de inicio de la replicación antes de iniciar la replicación.
6.Elimina las publicaciones en el servidor de destino que fueron replicadas porque se crearon antes de la ubicación de inicio de la replicación. No tienen utilidad en el suscriptor.
7.Establece el progreso de la replicación al punto de inicio de la replicación para cada suscripción. Cuando el servidor de destino inicia el proceso de recuperación, se pone al día con el punto de inicio de la replicación. Este es el LSN exacto que se utilizará como ubicación de replicación inicial para cada suscripción. El nombre del origen de replicación se obtiene ya que la suscripción fue creada. El nombre del origen de replicación y el punto de inicio de la replicación se utilizan en pg_replication_origin_advance() para configurar la ubicación de replicación inicial.
8.Habilita la suscripción para cada base de datos especificada en el servidor de destino. La suscripción comienza a aplicar transacciones desde el punto de inicio de la replicación.
9.Si el servidor secundario utilizaba `primary_slot_name`, ya no es útil, así que elimínalo.
10.Si el servidor secundario contiene ranuras de replicación de conmutación por error, ya no se pueden sincronizar, así que elimínalas.
11.Actualiza el identificador del sistema en el servidor de destino. Se ejecuta pg_resetwal(1) para modificar el identificador del sistema. El servidor de destino se detiene como requisito de pg_resetwal.

EJEMPLOS

Para crear una réplica lógica para las bases de datos `hr` y `finance` a partir de una réplica física en `foo`:

$ pg_createsubscriber -D /usr/local/pgsql/data -P "host=foo" -d hr -d finance
