NOMBRE

pgbouncer.ini - archivo de configuración para pgbouncer

DESCRIPCIÓN

El archivo de configuración tiene formato "ini". Los nombres de sección se encuentran entre "[" y "]". Las líneas que comienzan con ";" o "#" se consideran comentarios y se ignoran. Los caracteres ";" y "#" no se reconocen como especiales cuando aparecen más adelante en la línea.

CONFIGURACIÓN GENÉRICA

logfile

Especifica el archivo de registro. Para demonización (-d), se debe establecer este parámetro o syslog.

El archivo de registro permanece abierto, por lo que después de rotarlo, se debe enviar una señal HUP (kill -HUP) o, en consola, ejecutar RELOAD;. En Windows, el servicio debe detenerse y reiniciarse.

Tenga en cuenta que establecer logfile no desactiva el registro en stderr por sí mismo. Utilice la opción de línea de comandos -q o -d para ello.

Predeterminado: no establecido

pidfile

Especifica el archivo PID. Sin el parámetro pidfile establecido, no se permite la demonización (-d).

Predeterminado: no establecido

listen_addr

Especifica una lista (separada por comas) de direcciones donde escuchar conexiones TCP. También puede usar * que significa "escuchar en todas las direcciones". Cuando no se establece, solo se aceptan conexiones de socket Unix.

Las direcciones se pueden especificar numéricamente (IPv4/IPv6) o por nombre.

Predeterminado: no establecido

listen_port

Puerto en el que escuchar. Se aplica tanto a sockets TCP como Unix.

Predeterminado: 6432

unix_socket_dir

Especifica la ubicación de los sockets Unix. Se aplica tanto al socket de escucha como a las conexiones de servidor. Si se establece como una cadena vacía, los sockets Unix se deshabilitan. Un valor que comienza con @ especifica que se debe crear un socket Unix en el espacio de nombres abstracto (actualmente compatible en Linux y Windows).

Para que el reinicio en línea (-R) funcione, se debe configurar un socket Unix y debe estar en el espacio de nombres del sistema de archivos.

Predeterminado: /tmp (vacío en Windows)

unix_socket_mode

Modo de archivo para el socket Unix. Se ignora para sockets en el espacio de nombres abstracto. No compatible con Windows.

Predeterminado: 0777

unix_socket_group

Nombre del grupo a utilizar para el socket Unix. Se ignora para sockets en el espacio de nombres abstracto. No compatible con Windows.

Predeterminado: no establecido

user

Si se establece, especifica el usuario de Unix al que cambiar después del inicio. Funciona solo si PgBouncer se inicia como root o si ya se está ejecutando como el usuario dado. No compatible con Windows.

Predeterminado: no establecido

pool_mode

Especifica cuándo una conexión de servidor puede ser reutilizada por otros clientes.

session
El servidor se devuelve a la pool después de que el cliente se desconecta. Predeterminado.
transaction
El servidor se devuelve a la pool después de que la transacción finaliza.
statement
El servidor se devuelve a la pool después de que la consulta finaliza. Las transacciones que abarcan múltiples sentencias no están permitidas en este modo.

max_client_conn

Número máximo de conexiones de cliente permitidas.

Cuando esta configuración aumenta, es posible que también sea necesario aumentar los límites de descriptores de archivo en el sistema operativo. Tenga en cuenta que el número de descriptores de archivo potencialmente utilizados es superior a max_client_conn. Si cada usuario se conecta bajo su propio nombre de usuario al servidor, el máximo teórico utilizado es:

max_client_conn + (max pool_size * total bases de datos * total usuarios)

Si se especifica un usuario de base de datos en la cadena de conexión (todos los usuarios se conectan bajo el mismo nombre de usuario), el máximo teórico es:

max_client_conn + (max pool_size * total bases de datos)

El máximo teórico nunca debería alcanzarse, a menos que alguien diseñe deliberadamente una carga especial para ello. Aún así, significa que debe establecer el número de descriptores de archivo a un número seguro y alto.

Busque ulimit en la página del manual de su shell favorito. Nota: ulimit no se aplica en un entorno Windows.

Predeterminado: 100

default_pool_size

Cuántas conexiones de servidor permitir por par de usuario/base de datos. Se puede anular en la configuración por base de datos.

Predeterminado: 20

min_pool_size

Añadir más conexiones de servidor a la pool si está por debajo de este número. Mejora el comportamiento cuando la carga normal regresa súbitamente después de un período de inactividad total. El valor se limita efectivamente al tamaño de la pool.

Solo se aplica a las pools donde al menos una de las siguientes condiciones es verdadera:

•
la entrada en la sección [database] para la pool tiene un valor establecido para la clave de usuario (también conocido como usuario forzado)
•
hay al menos un cliente conectado a la pool

Predeterminado: 0 (deshabilitado)

reserve_pool_size

Cuántas conexiones adicionales permitir a una pool (ver reserve_pool_timeout). 0 deshabilita.

Predeterminado: 0 (deshabilitado)

reserve_pool_timeout

Si un cliente no ha sido atendido en este tiempo, utilice conexiones adicionales de la pool de reserva. 0 deshabilita. [segundos]

Predeterminado: 5.0

max_db_connections

No permitir más de tantas conexiones de servidor por base de datos (independientemente del usuario). Esto considera la base de datos de PgBouncer a la que se ha conectado el cliente, no la base de datos PostgreSQL de la conexión saliente.

Esto también se puede establecer por base de datos en la sección [databases].

Tenga en cuenta que cuando se alcanza el límite, cerrar una conexión de cliente a una pool no permitirá inmediatamente que se establezca una conexión de servidor para otra pool, ya que la conexión de servidor para la primera pool todavía está abierta. Una vez que la conexión de servidor se cierra (debido al tiempo de espera de inactividad), se abrirá inmediatamente una nueva conexión de servidor para la pool en espera.

Predeterminado: 0 (ilimitado)

max_user_connections

No permitir más de tantas conexiones de servidor por usuario (independientemente de la base de datos). Esto considera al usuario de PgBouncer que está asociado con una pool, que es o bien el usuario especificado para la conexión del servidor o, en ausencia de eso, el usuario con el que el cliente se ha conectado.

Esto también se puede establecer por usuario en la sección [users].

Tenga en cuenta que cuando se alcanza el límite, cerrar una conexión de cliente a una pool no permitirá inmediatamente que se establezca una conexión de servidor para otra pool, ya que la conexión de servidor para la primera pool todavía está abierta. Una vez que la conexión de servidor se cierra (debido al tiempo de espera de inactividad), se abrirá inmediatamente una nueva conexión de servidor para la pool en espera.

Predeterminado: 0 (ilimitado)

server_round_robin

Por defecto, PgBouncer reutiliza las conexiones de servidor de manera LIFO (último en entrar, primero en salir), de modo que pocas conexiones reciben la mayor carga. Esto proporciona el mejor rendimiento

rmance si tiene un solo servidor que sirve a una base de datos. Pero si hay un sistema de round-robin detrás de una dirección de base de datos (TCP, DNS o lista de hosts), entonces es mejor que PgBouncer también use conexiones de esa manera, logrando así una carga uniforme.

Predeterminado: 0

track_extra_parameters

Por defecto, PgBouncer rastrea los parámetros client_encoding, datestyle, timezone, standard_conforming_strings y application_name por cliente. Para permitir rastrear otros parámetros, estos pueden especificarse aquí, para que PgBouncer sepa que deben mantenerse en la caché de variables del cliente y restaurarse en el servidor cada vez que el cliente se active.

Si necesita especificar múltiples valores, use una lista separada por comas (por ejemplo, default_transaction_readonly, IntervalStyle)

Nota: La mayoría de los parámetros no se pueden rastrear de esta manera. Los únicos parámetros que se pueden rastrear son aquellos que PostgreSQL informa al cliente. PostgreSQL tiene una lista oficial de parámetros que informa al cliente (https://www.postgresql.org/docs/15/protocol-flow.html#PROTOCOL-ASYNC). Sin embargo, las extensiones de PostgreSQL pueden cambiar esta lista, pueden agregar parámetros ellos mismos que también informan, y pueden comenzar a informar parámetros ya existentes que PostgreSQL no informa. Notablemente, Citus 12.0+ hace que PostgreSQL también informe search_path.

El protocolo de PostgreSQL permite especificar la configuración de parámetros, tanto directamente como un parámetro en el paquete de inicio, o dentro del paquete de inicio de opciones (https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-OPTIONS). Los parámetros especificados usando ambos métodos son compatibles con track_extra_parameters. Sin embargo, no es posible incluir las opciones en sí en track_extra_parameters, solo los parámetros contenidos en options.

Predeterminado: IntervalStyle

ignore_startup_parameters

Por defecto, PgBouncer solo permite parámetros que puede rastrear en paquetes de inicio: client_encoding, datestyle, timezone y standard_conforming_strings. Todos los demás parámetros generarán un error. Para permitir otros parámetros, estos se pueden especificar aquí, para que PgBouncer sepa que son manejados por el administrador y pueda ignorarlos.

Si necesita especificar múltiples valores, use una lista separada por comas (por ejemplo, options,extra_float_digits)

El protocolo de PostgreSQL permite especificar la configuración de parámetros, tanto directamente como un parámetro en el paquete de inicio, o dentro del paquete de inicio de opciones (https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-OPTIONS). Los parámetros especificados usando ambos métodos son compatibles con ignore_startup_parameters. Incluso es posible incluir las opciones en sí en track_extra_parameters, lo que resulta en que se ignoren los parámetros desconocidos contenidos dentro de options.

Predeterminado: vacío

peer_id

El ID de par utilizado para identificar este proceso PgBouncer en un grupo de procesos PgBouncer que están emparejados entre sí. El valor de peer_id debe ser único dentro de un grupo de procesos PgBouncer emparejados. Cuando se establece en 0, el emparejamiento de pgbouncer está deshabilitado. Consulte la documentación de la sección [peers] para obtener más información. El valor máximo que se puede utilizar para peer_id es 16383.

Predeterminado: 0

disable_pqexec

Deshabilita el protocolo de Consulta Simple (PQexec). A diferencia del protocolo de Consulta Extendida, Consulta Simple permite múltiples consultas en un solo paquete, lo que permite algunas clases de ataques de inyección SQL. Deshabilitarlo puede mejorar la seguridad. Obviamente, esto significa que solo los clientes que usan exclusivamente el protocolo de Consulta Extendida seguirán funcionando.

Predeterminado: 0

application_name_add_host

Agrega la dirección IP y el puerto del host del cliente al nombre de la aplicación establecido al inicio de la conexión. Esto ayuda a identificar la fuente de consultas erróneas, etc. Esta lógica se aplica solo al inicio de una conexión. Si application_name se cambia posteriormente con SET, PgBouncer no lo vuelve a cambiar.

Predeterminado: 0

conffile

Muestra la ubicación del archivo de configuración actual. Cambiarlo hará que PgBouncer utilice otro archivo de configuración para la próxima recarga / SIGHUP.

Predeterminado: archivo de la línea de comandos

service_name

Se utiliza en el registro del servicio win32.

Predeterminado: pgbouncer

job_name

Alias de service_name.

stats_period

Establece con qué frecuencia se actualizan los promedios que se muestran en varios comandos SHOW y con qué frecuencia se escriben estadísticas agregadas en el registro (pero vea log_stats). [segundos]

Predeterminado: 60

max_prepared_statements

Cuando este valor se establece en un valor distinto de cero, PgBouncer rastrea los comandos relacionados con sentencias preparadas con nombre a nivel de protocolo enviados por el cliente en modo de agrupación de transacciones y sentencias. PgBouncer se asegura de que cualquier sentencia preparada por un cliente esté disponible en la conexión del servidor subyacente incluso cuando la sentencia se preparó originalmente en otra conexión de servidor.

PgBouncer examina internamente todas las consultas que se envían como sentencias preparadas por los clientes y asigna a cada cadena de consulta única un nombre interno con el formato PGBOUNCER_{id_único}. Si la misma cadena de consulta se prepara varias veces (posiblemente por diferentes clientes), entonces estas consultas comparten el mismo nombre interno. PgBouncer solo prepara la sentencia en el servidor PostgreSQL real usando el nombre interno (no el nombre proporcionado por el cliente). PgBouncer realiza un seguimiento del nombre que el cliente le dio a cada sentencia preparada. Luego, reescribe cada comando que usa una sentencia preparada para reemplazar el nombre del lado del cliente con el nombre interno (por ejemplo, reemplazando mi_sentencia_preparada con PGBOUNCER_123) antes de reenviar ese comando al servidor. Más importante aún, si la sentencia preparada que el cliente quiere ejecutar aún no está preparada en el servidor (por ejemplo, porque un servidor diferente ahora está asignado al cliente que cuando el cliente preparó la sentencia), entonces PgBouncer la prepara de forma transparente antes de ejecutarla.

Nota: Este rastreo y reescritura de comandos de sentencias preparadas no funciona para comandos de sentencias preparadas a nivel SQL, por lo que PREPARE, EXECUTE y DEALLOCATE se reenvían directamente a PostgreSQL. La excepción a esta regla son los comandos DEALLOCATE ALL y DISCARD ALL, estos funcionan como se esperaba y borrarán las sentencias preparadas que PgBouncer rastreó para el cliente que envía este comando.

El valor real de esta configuración controla la cantidad de sentencias preparadas que se mantienen activas en una caché LRU en una sola conexión de servidor. Cuando la configuración se establece en 0, el soporte para sentencias preparadas para la agrupación de transacciones y sentencias está deshabilitado. Para obtener el mejor rendimiento, debe intentar asegurarse de que esta configuración sea mayor que la cantidad de sentencias preparadas comúnmente utilizadas en su aplicación. Tenga en cuenta que cuanto mayor sea este valor, mayor será la huella de memoria de cada conexión de PgBouncer en su servidor PostgreSQL, ya que mantendrá más consultas preparadas en esas conexiones. También aumenta la huella de memoria de PgBouncer en sí, ya que ahora necesita rastrear las cadenas de consulta.

Sin embargo, el impacto en el uso de memoria de PgBouncer no es tan grande: - Cada consulta única se almacena una vez en una caché de consultas global. - Cada conexión de cliente mantiene un búfer que utiliza para reescribir paquetes. Esto es como máximo 4 veces el tamaño de pkt_buf. Sin embargo, este límite a menudo no se alcanza, solo ocurre cuando las consultas en sus sentencias preparadas tienen entre 2 y 4 veces el tamaño de pkt_buf.

Entonces, si considera el siguiente escenario como ejemplo: - Hay 1000 clientes activos - Los clientes preparan 200 consultas únicas - El tamaño promedio de una consulta es de 5kB - El parámetro pkt_buf se establece en el valor predeterminado de 4096 (4kB)

Entonces PgBouncer necesita como máximo la siguiente cantidad de memoria para manejar estas sentencias preparadas:

200 x 5kB + 1000 x 4 x 4kB = ~17MB de memoria.

El rastreo de sentencias preparadas no solo tiene un costo de memoria, sino también un mayor uso de CPU, ya que PgBouncer necesita inspeccionar y reescribir las consultas. Múltiples instancias de PgBouncer pueden escuchar en el mismo puerto para usar más de un núcleo para el procesamiento; consulte la documentación de la opción so_reuseport para obtener detalles.

Pero, por supuesto, también hay beneficios de rendimiento para las sentencias preparadas. Al igual que al conectarse directamente a PostgreSQL, al preparar una consulta que se ejecuta muchas veces, se reduce la cantidad total de análisis y planificación que debe realizarse. La forma en que PgBouncer rastrea las sentencias preparadas es especialmente beneficiosa para el rendimiento cuando varios clientes preparan las mismas consultas. Debido a que las conexiones de los clientes reutilizan automáticamente una sentencia preparada en una conexión de servidor incluso si fue preparada por otro cliente. Por ejemplo, si tiene un pool_size de 20 y tiene 100 clientes que preparan exactamente la misma consulta, entonces la consulta se prepara (y, por lo tanto, se analiza) solo 20 veces en el servidor PostgreSQL.

La reutilización de sentencias preparadas tiene una desventaja. Si los tipos de retorno o argumento de una sentencia preparada cambian entre ejecuciones, PostgreSQL actualmente arroja un error como:

ERROR:  cached plan must not change result type

Puede evitar tales errores al no tener múltiples clientes que usen la misma cadena de consulta exacta en una sentencia preparada, pero esperando diferentes tipos de argumentos o resultados. Una de las formas más comunes de encontrar este problema es durante una migración DDL en la que agrega una nueva columna o cambia el tipo de una columna en una tabla existente. En esos casos, puede ejecutar RECONNECT en la consola de administración de PgBouncer después de realizar la migración para forzar una reprogramación de la consulta y hacer que el error desaparezca.

Predeterminado: 0

auth_type

Cómo autenticar a los usuarios.

cert
El cliente debe conectarse a través de una conexión TLS con un certificado de cliente válido. El nombre de usuario se toma del campo CommonName del certificado.
md5
Utiliza verificación de contraseña basada en MD5. Este es el método de autenticación predeterminado. auth_file puede contener contraseñas cifradas con MD5 y contraseñas en texto plano. Si md5 está configurado y un usuario tiene un secreto SCRAM, entonces SCRAM se usa automáticamente en su lugar.
scram-sha-256
Utiliza verificación de contraseña con SCRAM-SHA-256. auth_file debe contener secretos SCRAM o contraseñas en texto plano.
plain
La contraseña en texto plano se envía por la red. Obsoleto.
trust
No se realiza ninguna autenticación. El nombre de usuario aún debe existir en auth_file.
any
Similar al método trust, pero el nombre de usuario proporcionado se ignora. Requiere que todas las bases de datos estén configuradas para iniciar sesión como un usuario específico. Adicionalmente, la base de datos de consola permite que cualquier usuario inicie sesión como administrador.
hba
El tipo de autenticación real se carga desde auth_hba_file. Esto permite diferentes métodos de autenticación para diferentes rutas de acceso, por ejemplo: las conexiones a través de sockets Unix usan el método de autenticación peer, las conexiones a través de TCP deben usar TLS.
pam
PAM se utiliza para autenticar usuarios, auth_file se ignora. Este método no es compatible con bases de datos que utilizan la opción auth_user. El nombre de servicio informado a PAM es “pgbouncer”. pam no es compatible en el archivo de configuración HBA.

auth_hba_file

Archivo de configuración HBA a utilizar cuando auth_type es hba.

Predeterminado: no establecido

auth_file

El nombre del archivo desde el cual cargar nombres de usuario y contraseñas. Consulte la sección Formato del archivo de autenticación a continuación para obtener detalles.

La mayoría de los tipos de autenticación (ver arriba) requieren que auth_file o auth_user estén establecidos; de lo contrario, no habría usuarios definidos.

Predeterminado: no establecido

auth_user

Si auth_user está establecido, cualquier usuario no especificado en auth_file será consultado a través de la consulta auth_query de pg_shadow en la base de datos, usando auth_user. La contraseña de auth_user se tomará de auth_file. (Si auth_user no requiere una contraseña, entonces no necesita ser definido en auth_file).

El acceso directo a pg_shadow requiere derechos de administrador. Es preferible usar un usuario no superusuario que llame a una función SECURITY DEFINER en su lugar.

Predeterminado: no establecido

auth_query

Consulta para cargar la contraseña del usuario desde la base de datos.

El acceso directo a pg_shadow requiere derechos de administrador. Es preferible usar un usuario no superusuario que llame a una función SECURITY DEFINER en su lugar.

Tenga en cuenta que la consulta se ejecuta dentro de la base de datos de destino. Por lo tanto, si se utiliza una función, debe instalarse en cada base de datos.

Predeterminado: SELECT usename, passwd FROM pg_shadow WHERE usename=$1

VERIFICACIONES DE CONSISTENCIA DE CONEXIÓN, TIEMPOS DE ESPERA

server_reset_query

Consulta enviada al servidor al liberar la conexión, antes de ponerla a disposición de otros clientes. En ese momento no hay ninguna transacción en curso, por lo que el valor no debe incluir ABORT o ROLLBACK.

La consulta debe limpiar cualquier cambio realizado en la sesión de la base de datos para que el siguiente cliente reciba la conexión en un estado bien definido. El valor predeterminado es DISCARD ALL, que limpia todo, pero deja al siguiente cliente sin estado precargado. Se puede hacer más ligero, por ejemplo, DEALLOCATE ALL para simplemente descartar sentencias preparadas, si la aplicación no falla cuando se conserva algo de estado.

Cuando se utiliza la agrupación de transacciones, server_reset_query no se utiliza, porque en ese modo, los clientes no deben utilizar ninguna característica basada en sesiones, ya que cada transacción termina en una conexión diferente y, por lo tanto, obtiene un estado de sesión diferente.

Predeterminado: DISCARD ALL

server_reset_query_always

Si server_reset_query se ejecutará en todos los modos de agrupación. Cuando esta configuración está desactivada (predeterminada), server_reset_query se ejecutará solo en agrupaciones que estén en modo de agrupación de sesiones. Las conexiones en modo de agrupación de transacciones no deberían necesitar una consulta de restablecimiento.

Esta configuración es para solucionar problemas de configuraciones defectuosas que ejecutan aplicaciones que usan características de sesión a través de un PgBouncer agrupado por transacciones. Cambia el comportamiento de fallos no deterministas a fallos deterministas: los clientes siempre pierden su estado después de cada transacción.

Predeterminado: 0

server_check_delay

Cuánto tiempo mantener las conexiones liberadas disponibles para su reutilización inmediata, sin ejecutar server_check_query en ellas. Si es 0, la verificación se ejecuta siempre.

Predeterminado: 30.0

server_check_query

Consulta simple que no hace nada para verificar si la conexión del servidor está activa.

Si es una cadena vacía, la verificación de consistencia está deshabilitada.

Predeterminado: select 1

server_fast_close

Desconecta un servidor en modo de agrupación de sesiones inmediatamente o después del final de la transacción actual si está en modo “close_needed” (establecido por RECONNECT, RELOAD que cambia la configuración de conexión, o cambio de DNS), en lugar de esperar hasta el final de la sesión. En modo de agrupación de sentencias o transacciones, esto no tiene efecto, ya que ese es el comportamiento predeterminado allí.

Si debido a esta configuración se cierra una conexión de servidor antes del final de la sesión del cliente, la conexión del cliente también se cierra. Esto asegura que el cliente note que la sesión ha sido interrumpida.

Esta configuración hace que los cambios en la configuración de la conexión surtan efecto antes si se utiliza la agrupación de sesiones y sesiones de larga duración. La desventaja es que las sesiones del cliente pueden ser interrumpidas por un cambio de configuración, por lo que las aplicaciones cliente necesitarán lógica para reconectarse y restablecer el estado de la sesión. SECCIÓN [DATABASES]

La sección [databases] define los nombres de las bases de datos a las que los clientes de PgBouncer pueden conectarse y especifica a dónde se enrutarán esas conexiones. La sección contiene líneas de clave=valor como

dbname = cadena de conexión

donde la clave se tomará como un nombre de base de datos y el valor como una cadena de conexión, que consta de pares clave=valor de parámetros de conexión, descritos a continuación (similar a libpq, pero libpq real no se utiliza y el conjunto de funciones disponibles es diferente). Ejemplo:

foodb = host=host1.example.com port=5432
bardb = host=localhost dbname=bazdb

El nombre de la base de datos puede contener caracteres _0-9A-Za-z sin comillas. Los nombres que contienen otros caracteres deben entrecomillarse con las comillas de identificador SQL estándar: comillas dobles, con `""` para una instancia única de una comilla doble.

El nombre de base de datos `pgbouncer` está reservado para la consola de administración y no se puede utilizar como clave aquí.

`*` actúa como una base de datos de respaldo: si el nombre exacto no existe, su valor se toma como cadena de conexión para la base de datos solicitada. Por ejemplo, si hay una entrada (y ninguna otra entrada que la anule)

* = host=foo

entonces una conexión a PgBouncer especificando una base de datos `bar` se comportará efectivamente como si existiera una entrada

bar = host=foo dbname=bar

(aprovechando el valor predeterminado para `dbname` que es el nombre de la base de datos del lado del cliente; ver más abajo).

Dichas entradas de base de datos creadas automáticamente se eliminan si permanecen inactivas durante más tiempo que el especificado por el parámetro `autodb_idle_timeout`.

dbname

Nombre de la base de datos de destino.

Valor por defecto: igual que el nombre de la base de datos del lado del cliente

host

Nombre del host o dirección IP a la que conectarse. Los nombres de host se resuelven en el momento de la conexión, el resultado se almacena en caché según el parámetro `dns_max_ttl`. Cuando la resolución de un nombre de host cambia, las conexiones de servidor existentes se cierran automáticamente cuando se liberan (según el modo de agrupación), y las nuevas conexiones de servidor utilizan inmediatamente la nueva resolución. Si DNS devuelve varios resultados, se utilizan de forma aleatoria (round-robin).

Si el valor comienza con /, entonces se utiliza un socket Unix en el espacio de nombres del sistema de archivos. Si el valor comienza con @, entonces se utiliza un socket Unix en el espacio de nombres abstracto.

Se puede especificar una lista de nombres de host o direcciones separada por comas. En ese caso, las conexiones se realizan de forma aleatoria (round-robin). (Si una lista de hosts contiene nombres de host que a su vez se resuelven a través de DNS a varias direcciones, los sistemas de round-robin operan de forma independiente. Esta es una dependencia de implementación que está sujeta a cambios). Tenga en cuenta que en una lista, todos los hosts deben estar disponibles

SECTION [DATABASE]

This section defines the databases PgBouncer will connect to. A database definition looks like this:

database_name = setting1=value1 setting2=value2 ...

The database name can be anything, but it’s recommended to use the actual database name. The first database definition can contain the name of the default database, if any, that clients can connect to if they don’t specify one.

The available settings are:

connection_limit

Set the maximum number of connections to this database. If not set, the default_pool_size is used.

A value of 0 means no limit.

host

The database server to connect to. Can be a hostname, IP address, or a Unix domain socket path. If multiple hosts are listed, they are tried in order until a connection is successful. This is not a list of hosts to load balance across at all times: There are no mechanisms to skip unreachable hosts or to select only available hosts from a list or similar. (This is different from what a host list in libpq means.) Also note that this only affects how the destinations of new connections are chosen. See also the setting server_round_robin for how clients are assigned to already established server connections.

Examples:

host=localhost
host=127.0.0.1
host=2001:0db8:85a3:0000:0000:8a2e:0370:7334
host=/var/run/postgresql
host=192.168.0.1,192.168.0.2,192.168.0.3

Default: not set, meaning to use a Unix socket

port

Default: 5432

user

If user= is set, all connections to the destination database will be done with the specified user, meaning that there will be only one pool for this database.

Otherwise, PgBouncer logs into the destination database with the client user name, meaning that there will be one pool per user.

password

If no password is specified here, the password from the auth_file or auth_query will be used.

auth_user

Override of the global auth_user setting, if specified.

auth_query

Override of the global auth_query setting, if specified. The entire SQL statement needs to be enclosed in single quotes.

auth_dbname

Override of the global auth_dbname setting, if specified.

pool_size

Set the maximum size of pools for this database. If not set, the default_pool_size is used.

min_pool_size

Set the minimum pool size for this database. If not set, the global min_pool_size is used.

Only enforced if at least one of the following is true:

•
this entry in the [database] section has a value set for the user key (aka forced user)
•

Set additional connections for this database. If not set, reserve_pool_size is used.

connect_query

Query to be executed after a connection is established, but before allowing the connection to be used by any clients. If the query raises errors, they are logged but ignored otherwise.

pool_mode

Set the pool mode specific to this database. If not set, the default pool_mode is used.

max_db_connections

SECTION [PEERS]

The section [peers] defines the peers that PgBouncer can forward cancellation requests to and where those cancellation requests will be routed.

PgBouncer processes can be peered together in a group by defining a peer_id value and a [peers] section in the configs of all the PgBouncer processes. These PgBouncer processes can then forward cancellations requests to the process that it originated from. This is needed to make cancellations work when multiple PgBouncer processes (possibly on different servers) are behind the same TCP load balancer. Cancellation requests are sent over different TCP connections than the query they are cancelling, so a TCP load balancer might send the cancellation request connection to a different process than the one that it was meant for. By peering them these cancellation requests eventually end up at the right process. A more in-depth explanation is provided in this recording of a conference talk (https://www.youtube.com/watch?v=M585FfbboNA).

The section contains key=value lines like

peer_id = connection string

Where the key will be taken as a peer_id and the value as a connection string, consisting of key=value pairs of connection parameters, described below (similar to libpq, but the actual libpq is not used and the set of available features is different). Example:

1 = host=host1.example.com
2 = host=/tmp/pgbouncer-2  port=5555

Note 1: For peering to work, the peer_id of each PgBouncer process in the group must be unique within the peered group. And the [peers] section should contain entries for each of those peer ids. An example can be found in the examples section of these docs. It is allowed, but not necessary, for the [peers] section to contain the peer_id of the PgBouncer that the config is for. Such an entry will be ignored, but it is allowed to config management easy. Because it allows using the exact same [peers] section for multiple configs.

Note 2: Cross-version peering is supported as long as all peers are on the same side of the v1.21.0 version boundary. In v1.21.0 some breaking changes were made in how we encode the cancellation tokens that made them incompatible with the ones created by earlier versions.

host

Host name or IP address to connect to. Host names are resolved at connection time, the result is cached per dns_max_ttl parameter. If DNS returns several results, they are used in a round-robin manner. But in general it’s not recommended to use a hostname that resolves to multiple IPs, because then the cancel request might still be forwarded to the wrong node and it would need to be forwarded again (which is only allowed up to three times).

If the value begins with /, then a Unix socket in the file-system namespace is used. If the value begins with @, then a Unix socket in the abstract namespace is used.

Examples:

host=localhost
host=127.0.0.1
host=2001:0db8:85a3:0000:0000:8a2e:0370:7334
host=/var/run/pgbouncer-1

port

Default: 6432

pool_size

Set the maximum number of cancel requests that can be in flight to the peer at the same time. It’s quite normal for cancel requests to arrive in bursts, e.g. when the backing Postgres server slow or down. So it’s important for pool_size to not be so low that it cannot handle these bursts.

If not set, the default_pool_size is used.

INCLUDE DIRECTIVE

The PgBouncer configuration file can contain include directives, which specify another configuration file to read and process. This allows splitting the configuration file into physically separate parts. The include directives look like this:

%include filename

If the file name is not an absolute path, it is taken as relative to the current working directory.

SECTION [USERS]

This section is used for storing user credentials when auth_type is set to md5, plain, or scram_sha_256 and auth_file is used.

Each line in this section defines a user and their password hash.

Format:

username = password_hash

Example:

user1 = $1$somesalt$5a6a10178a0b07a144032f737a07b58b
user2 = password

The password hash format depends on the auth_type setting.

For md5, the hash is in the format: $1$<salt>$<hash>.

For plain, the hash is the plain text password.

For scram_sha_256, the hash is in the PostgreSQL SCRAM secret format:

SCRAM-SHA-256$<iterations>:<salt>$<storedkey>:<serverkey>

See the PostgreSQL documentation and RFC 5803 for details on this.

The passwords or secrets stored in the authentication file serve two purposes. First, they are used to verify the passwords of incoming client connections, if a password-based authentication method is configured. Second, they are used as the passwords for outgoing connections to the backend server, if the backend server requires password-based authentication (unless the password is specified directly in the database’s connection string). The latter works if the password is stored in plain text or MD5-hashed. SCRAM secrets can only be used for logging into a server if the client authentication also uses SCRAM, the PgBouncer database definition does not specify a user name, and the SCRAM secrets are identical in PgBouncer and the PostgreSQL server (same salt and iterations, not merely the same password). This is due to an inherent security property of SCRAM: The stored SCRAM secret cannot by itself be used for deriving login credentials.

The authentication file can be written by hand, but it’s also useful to generate it from some other list of users and passwords. See ./etc/mkauth.py for a sample script to generate the authentication file from the pg_shadow system table. Alternatively, use auth_query instead of auth_file to avoid having to maintain a separate authentication file.

HBA FILE FORMAT

The location of the HBA file is specified by the setting auth_hba_file. It is only used if auth_type is set to hba.

The file follows the format of the PostgreSQL pg_hba.conf file (see https://www.postgresql.org/docs/current/auth-pg-hba-conf.html).

•
Supported record types: local, host, hostssl, hostnossl.
•
Database field: Supports all, sameuser, @file, multiple names. Not supported: replication, samerole, samegroup.
•
User name field: Supports all, @file, multiple names. Not supported: +groupname.
•
Address field: Supports IPv4, IPv6. Not supported: DNS names, domain prefixes.
•
Auth-method field: Only methods supported by PgBouncer’s auth_type are supported, plus peer and reject, but except any and pam, which only work globally. User name map (map=) parameter is not supported.
