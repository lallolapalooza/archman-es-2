NOMBRE

pg_rewind - sincronizar un directorio de datos de PostgreSQL con otro directorio de datos que se haya bifurcado de él

SINOPSIS

pg_rewind [opción...] {-D | --target-pgdata} directorio {--source-pgdata=directorio | --source-server=cadena_conexion}

DESCRIPCIÓN

pg_rewind es una herramienta para sincronizar un clúster de PostgreSQL con otra copia del mismo clúster, después de que las líneas de tiempo de los clústeres se hayan bifurcado. Un escenario típico es volver a poner en línea un servidor primario antiguo después de un failover, como un standby que sigue al nuevo primario.

Después de un rebobinado exitoso, el estado del directorio de datos de destino es análogo a una copia de seguridad base del directorio de datos de origen. A diferencia de tomar una nueva copia de seguridad base o usar una herramienta como rsync, pg_rewind no requiere comparar o copiar bloques de relación no modificados en el clúster. Solo se copian los bloques modificados de los archivos de relación existentes; todos los demás archivos, incluidos los nuevos archivos de relación, los archivos de configuración y los segmentos WAL, se copian en su totalidad. Como tal, la operación de rebobinado es significativamente más rápida que otros enfoques cuando la base de datos es grande y solo una pequeña fracción de los bloques difiere entre los clústeres.

pg_rewind examina los historiales de líneas de tiempo de los clústeres de origen y destino para determinar el punto donde se bifurcaron, y espera encontrar WAL en el directorio pg_wal del clúster de destino que llegue hasta el punto de bifurcación. El punto de bifurcación se puede encontrar en la línea de tiempo de destino, en la línea de tiempo de origen o en su ancestro común. En el escenario típico de failover donde el clúster de destino se apagó poco después de la bifurcación, esto no es un problema, pero si el clúster de destino se ejecutó durante mucho tiempo después de la bifurcación, es posible que sus archivos WAL antiguos ya no estén presentes. En este caso, puede copiarlos manualmente desde el archivo WAL al directorio pg_wal, o ejecutar pg_rewind con la opción -c para recuperarlos automáticamente del archivo WAL. El uso de pg_rewind no se limita al failover; por ejemplo, un servidor standby puede ser promovido, ejecutar algunas transacciones de escritura y luego ser rebobinado para volver a ser un standby.

Después de ejecutar pg_rewind, la reproducción de WAL debe completarse para que el directorio de datos esté en un estado consistente. Cuando se reinicie el servidor de destino, entrará en modo de recuperación y reproducirá todo el WAL generado en el servidor de origen desde el último punto de control antes del punto de bifurcación. Si parte del WAL ya no estaba disponible en el servidor de origen cuando se ejecutó pg_rewind, y por lo tanto no se pudo copiar durante la sesión de pg_rewind, debe estar disponible cuando se inicie el servidor de destino. Esto se puede hacer creando un archivo recovery.signal en el directorio de datos de destino y configurando un restore_command adecuado en postgresql.conf.

pg_rewind requiere que el servidor de destino tenga habilitada la opción wal_log_hints en postgresql.conf o que los sumarios de datos estén habilitados cuando el clúster se inicializó con initdb. Ninguna de estas opciones está activada por defecto actualmente. full_page_writes también debe estar configurada en on, pero está habilitada por defecto.


Advertencia: Fallos durante el rebobinado

Si pg_rewind falla durante el procesamiento, el directorio de datos de destino probablemente no estará en un estado recuperable. En tal caso, se recomienda realizar una nueva copia de seguridad fresca.

Como pg_rewind copia completamente los archivos de configuración del origen, puede ser necesario corregir la configuración utilizada para la recuperación antes de reiniciar el servidor de destino, especialmente si el destino se reintroduce como un standby del origen. Si reinicia el servidor después de que la operación de rebobinado haya finalizado pero sin configurar la recuperación, el destino puede volver a divergir del primario.

pg_rewind fallará inmediatamente si encuentra archivos a los que no puede escribir directamente. Esto puede suceder, por ejemplo, cuando el servidor de origen y el de destino utilizan el mismo mapeo de archivos para claves y certificados SSL de solo lectura. Si tales archivos están presentes en el servidor de destino, se recomienda eliminarlos antes de ejecutar pg_rewind. Después de realizar el rebobinado, algunos de estos archivos pueden haber sido copiados del origen, en cuyo caso puede ser necesario eliminar los datos copiados y restaurar el conjunto de enlaces utilizado antes del rebobinado.

OPCIONES

pg_rewind acepta los siguientes argumentos de línea de comandos:

-D directorio
--target-pgdata=directorio

Esta opción especifica el directorio de datos de destino que se sincroniza con el origen. El servidor de destino debe estar apagado limpiamente antes de ejecutar pg_rewind

--source-pgdata=directorio

Especifica la ruta del sistema de archivos al directorio de datos del servidor de origen con el que se sincroniza el destino. Esta opción requiere que el servidor de origen esté apagado limpiamente.

--source-server=cadena_conexion

Especifica una cadena de conexión libpq para conectarse al servidor PostgreSQL de origen con el que se sincroniza el destino. La conexión debe ser una conexión normal (no de replicación) con un rol que tenga suficientes permisos para ejecutar las funciones utilizadas por pg_rewind en el servidor de origen (ver sección de Notas para más detalles) o un rol de superusuario. Esta opción requiere que el servidor de origen esté en ejecución y aceptando conexiones.

-R
--write-recovery-conf

Crea standby.signal y añade la configuración de conexión a postgresql.auto.conf en el directorio de salida. El dbname se registrará solo si el dbname se especificó explícitamente en la cadena de conexión o en la variable de entorno. --source-server es obligatorio con esta opción.

-n
--dry-run

Haz todo excepto modificar realmente el directorio de destino.

-N
--no-sync

Por defecto, pg_rewind esperará a que todos los archivos se escriban de forma segura en el disco. Esta opción hace que pg_rewind retorne sin esperar, lo cual es más rápido, pero significa que una posterior caída del sistema operativo puede dejar el directorio de datos corrupto. En general, esta opción es útil para pruebas pero no debe usarse en una instalación de producción.

-P
--progress

Habilita la notificación de progreso. Activar esta opción entregará un informe de progreso aproximado mientras se copian los datos del clúster de origen.

-c
--restore-target-wal

Utiliza el restore_command definido en la configuración del clúster de destino para recuperar archivos WAL del archivo WAL si estos archivos ya no están disponibles en el directorio pg_wal.

--config-file=nombre_archivo

Utiliza el archivo de configuración principal del servidor especificado para el clúster de destino. Esto afecta a pg_rewind cuando utiliza internamente el comando postgres para la operación de rebobinado en este clúster (al recuperar restore_command con la opción -c/--restore-target-wal y al forzar la finalización de la recuperación ante fallos).

--debug

Imprime una salida de depuración detallada que es útil principalmente para los desarrolladores que depuran pg_rewind.

--no-ensure-shutdown

pg_rewind requiere que el servidor de destino esté apagado limpiamente antes de rebobinar. Por defecto, si el servidor de destino no está apagado limpiamente, pg_rewind inicia el servidor de destino en modo monousuario para completar primero la recuperación ante fallos y luego lo detiene. Al pasar esta opción, pg_rewind se salta esto y se produce un error inmediatamente si el servidor no está apagado limpiamente. Se espera que los usuarios manejen la situación ellos mismos en ese caso.

--sync-method=método

Cuando se establece en fsync, que es el valor predeterminado, pg_rewind abrirá recursivamente y sincronizará todos los archivos en el directorio de datos. La búsqueda de archivos seguirá enlaces simbólicos para el directorio WAL y cada tablespace configurado.

En Linux, se puede usar syncfs en su lugar para pedir al sistema operativo que sincronice todos los sistemas de archivos que contienen el directorio de datos, los archivos WAL y cada tablespace. Consulte recovery_init_sync_method para obtener información sobre las advertencias a tener en cuenta al usar syncfs.

Esta opción no tiene ningún efecto cuando se utiliza --no-sync.

-V
--version

Muestra la información de la versión y luego sale.

-?
--help

Muestra la ayuda y luego sale.

NOTAS

Al ejecutar pg_rewind utilizando un clúster en línea como fuente, se puede usar un rol con permisos suficientes para ejecutar las funciones utilizadas por pg_rewind en el clúster fuente en lugar de un superusuario. Aquí se explica cómo crear dicho rol, llamado rewind_user:

CREATE USER rewind_user LOGIN;
GRANT EXECUTE ON function pg_catalog.pg_ls_dir(text, boolean, boolean) TO rewind_user;
GRANT EXECUTE ON function pg_catalog.pg_stat_file(text, boolean) TO rewind_user;
GRANT EXECUTE ON function pg_catalog.pg_read_binary_file(text) TO rewind_user;
GRANT EXECUTE ON function pg_catalog.pg_read_binary_file(text, bigint, bigint, boolean) TO rewind_user;

Cómo Funciona

La idea básica es copiar todos los cambios a nivel del sistema de archivos del clúster fuente al clúster de destino:

1.Escanee el registro WAL del clúster de destino, comenzando desde el último punto de control antes del momento en que el historial de línea de tiempo del clúster fuente se bifurcó del clúster de destino. Para cada registro WAL, registre cada bloque de datos que se tocó. Esto produce una lista de todos los bloques de datos que se modificaron en el clúster de destino después de que el clúster fuente se bifurcó. Si algunos de los archivos WAL ya no están disponibles, intente volver a ejecutar pg_rewind con la opción -c para buscar los archivos faltantes en el archivo WAL.
2.Copie todos esos bloques modificados del clúster fuente al clúster de destino, ya sea utilizando acceso directo al sistema de archivos (--source-pgdata) o SQL (--source-server). Los archivos de relación ahora estarán en un estado equivalente al momento del último punto de control completado anterior al momento en que las líneas de tiempo WAL del origen y el destino divergieron, más el estado actual en el origen de los bloques modificados en el destino después de esa divergencia.
3.Copie todos los demás archivos, incluidos los nuevos archivos de relación, segmentos WAL, pg_xact y archivos de configuración del clúster fuente al clúster de destino. De manera similar a las copias de seguridad base, el contenido de los directorios pg_dynshmem/, pg_notify/, pg_replslot/, pg_serial/, pg_snapshots/, pg_stat_tmp/ y pg_subtrans/ se omite de los datos copiados del clúster fuente. Se omiten los archivos backup_label, tablespace_map, pg_internal.init, postmaster.opts, postmaster.pid y .DS_Store, así como cualquier archivo o directorio que comience con pgsql_tmp.
4.Cree un archivo backup_label para comenzar la reproducción WAL en el punto de control creado en la conmutación por error y configure el archivo pg_control con un LSN de consistencia mínimo definido como el resultado de pg_current_wal_insert_lsn() al rebobinar desde una fuente en vivo o el último LSN del punto de control al rebobinar desde una fuente detenida.
5.Al iniciar el destino, PostgreSQL reproduce todo el WAL requerido, lo que resulta en un directorio de datos en un estado consistente.
