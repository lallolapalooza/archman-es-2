NOMBRE

pgbench - ejecuta una prueba de referencia en PostgreSQL

SINOPSIS

pgbench -i [opción...] [dbname]

pgbench [opción...] [dbname]

DESCRIPCIÓN

pgbench es un programa simple para ejecutar pruebas de referencia en PostgreSQL. Ejecuta la misma secuencia de comandos SQL una y otra vez, posiblemente en múltiples sesiones de base de datos concurrentes, y luego calcula la tasa promedio de transacciones (transacciones por segundo). Por defecto, pgbench prueba un escenario que se basa libremente en TPC-B, que implica cinco comandos SELECT, UPDATE e INSERT por transacción. Sin embargo, es fácil probar otros casos escribiendo sus propios archivos de script de transacciones.

La salida típica de pgbench se parece a:

tipo de transacción: <integrado: TPC-B (más o menos)>
factor de escala: 10
modo de consulta: simple
número de clientes: 10
número de hilos: 1
número máximo de intentos: 1
número de transacciones por cliente: 1000
número de transacciones procesadas realmente: 10000/10000
número de transacciones fallidas: 0 (0.000%)
latencia promedio = 11.013 ms
latencia stddev = 7.351 ms
tiempo de conexión inicial = 45.758 ms
tps = 896.967014 (sin tiempo de conexión inicial)

Las primeras siete líneas informan sobre algunos de los parámetros más importantes. La sexta línea informa sobre el número máximo de intentos para transacciones con errores de serialización o bloqueo (ver Fallos y Reintentos de Serialización/Bloqueo para más información). La octava línea informa sobre el número de transacciones completadas e intentadas (la última siendo solo el producto del número de clientes y el número de transacciones por cliente); estos serán iguales a menos que la ejecución falle antes de completarse o algunos comandos SQL fallen. (En modo -T, solo se imprime el número real de transacciones). La siguiente línea informa sobre el número de transacciones fallidas debido a errores de serialización o bloqueo (ver Fallos y Reintentos de Serialización/Bloqueo para más información). La última línea informa sobre el número de transacciones por segundo.

La prueba de transacción predeterminada similar a TPC-B requiere que se configuren tablas específicas de antemano. pgbench debe invocarse con la opción -i (inicializar) para crear y poblar estas tablas. (Cuando está probando un script personalizado, no necesita este paso, sino que deberá realizar la configuración que necesite su prueba).

pgbench -i [ otras-opciones ] dbname

donde dbname es el nombre de la base de datos ya creada para probar. (También puede necesitar las opciones -h, -p y/o -U para especificar cómo conectarse al servidor de base de datos).


Precaución

pgbench -i crea cuatro tablas: pgbench_accounts, pgbench_branches, pgbench_history y pgbench_tellers, destruyendo cualquier tabla existente con estos nombres. ¡Tenga mucho cuidado al usar otra base de datos si tiene tablas con estos nombres!

Con el factor de escala predeterminado de 1, las tablas contienen inicialmente el siguiente número de filas:

tabla                   # de filas
---------------------------------
pgbench_branches        1
pgbench_tellers         10
pgbench_accounts        100000
pgbench_history         0

Puede (y, para la mayoría de los propósitos, probablemente debería) aumentar el número de filas usando la opción -s (factor de escala). La opción -F (fillfactor) también se puede usar en este momento.

Una vez que haya realizado la configuración necesaria, puede ejecutar su prueba de referencia con un comando que no incluya -i, es decir:

pgbench [ opciones ] dbname

En casi todos los casos, necesitará algunas opciones para hacer una prueba útil. Las opciones más importantes son -c (número de clientes), -t (número de transacciones), -T (límite de tiempo) y -f (especificar un archivo de script personalizado). Vea abajo para una lista completa.

OPCIONES

Lo siguiente se divide en tres subsecciones. Se utilizan diferentes opciones durante la inicialización de la base de datos y al ejecutar las pruebas de referencia, pero algunas opciones son útiles en ambos casos.

Opciones de inicialización

pgbench acepta los siguientes argumentos de inicialización en la línea de comandos:

[-d] dbname
[--dbname=]dbname

Especifica el nombre de la base de datos en la que realizar la prueba. Si no se especifica, se utiliza la variable de entorno PGDATABASE. Si esta no está configurada, se utiliza el nombre de usuario especificado para la conexión.

-i
--initialize

Requerido para invocar el modo de inicialización.

-I pasos_iniciales
--init-steps=pasos_iniciales

Realiza solo un conjunto seleccionado de los pasos de inicialización normales. pasos_iniciales especifica los pasos de inicialización que se realizarán, usando un carácter por paso. Cada paso se invoca en el orden especificado. El valor predeterminado es dtgvp. Los pasos disponibles son:

d (Drop/Eliminar)

Elimina cualquier tabla existente de pgbench.

t (create Tables/crear Tablas)

Crea las tablas utilizadas por el escenario estándar de pgbench, a saber, pgbench_accounts, pgbench_branches, pgbench_history y pgbench_tellers.

g o G (Generate data, client-side or server-side/Generar datos, del lado del cliente o del servidor)

Genera datos y los carga en las tablas estándar, reemplazando cualquier dato ya presente.

Con g (generación de datos del lado del cliente), los datos se generan en el cliente pgbench y luego se envían al servidor. Esto utiliza intensivamente el ancho de banda del cliente/servidor a través de un COPY. pgbench utiliza la opción FREEZE para cargar datos en tablas normales (no particionadas) con la versión 14 o posterior de PostgreSQL para acelerar el VACUUM posterior. Usar g hace que el registro imprima un mensaje cada 100,000 filas mientras genera datos para todas las tablas.

Con G (generación de datos del lado del servidor), solo se envían consultas pequeñas desde el cliente pgbench y luego los datos se generan realmente en el servidor. Esta variante no requiere un ancho de banda significativo, pero el servidor hará más trabajo. Usar G hace que el registro no imprima ningún mensaje de progreso mientras genera datos.

El comportamiento de inicialización predeterminado utiliza la generación de datos del lado del cliente (equivalente a g).

v (Vacuum/Vaciar)

Invoca VACUUM en las tablas estándar.

p (create Primary keys/crear Claves Primarias)

Crea índices de clave primaria en las tablas estándar.

f (create Foreign keys/crear Claves Foráneas)

Crea restricciones de clave foránea entre las tablas estándar. (¡Tenga en cuenta que este paso no se realiza por defecto!)

-F fillfactor
--fillfactor=fillfactor

Crea las tablas pgbench_accounts, pgbench_tellers y pgbench_branches con el fillfactor dado. El valor predeterminado es 100.

-n
--no-vacuum

No realiza ningún vacío durante la inicialización. (Esta opción suprime el paso de inicialización v, incluso si se especificó en -I).

-q
--quiet

Cambia el registro a modo silencioso, produciendo solo un mensaje de progreso cada 5 segundos. El registro predeterminado imprime un mensaje cada 100,000 filas, lo que a menudo genera muchas líneas por segundo (especialmente en hardware bueno).

Esta configuración no tiene efecto si G se especifica en -I.

-s escala_factor
--scale=escala_factor

Multiplica el número de filas generadas por el factor de escala. Por ejemplo, -s 100 creará 10,000,000 de filas en la tabla pgbench_accounts. El valor predeterminado es 1. Cuando la escala es de 20,000 o mayor, las columnas utilizadas para almacenar identificadores de cuenta (columnas aid) cambiarán a enteros más grandes (bigint), para que sean lo suficientemente grandes como para almacenar el rango de identificadores de cuenta.

--foreign-keys

Crea restricciones de clave foránea entre las tablas estándar. (Esta opción agrega el paso f a la secuencia de pasos de inicialización, si aún no está presente).

--index-tablespace=tablespace_indices

Crea índices en el tablespace especificado, en lugar del tablespace predeterminado.

--partition-method=NOMBRE

Crea una tabla pgbench_accounts particionada con el método NOMBRE. Los valores esperados son range o hash. Esta opción requiere que --partitions esté configurado a

Opciones de ejecución

pgbench acepta los siguientes argumentos de línea de comandos para la ejecución:

-c clientes
--clients=clientes

Número de clientes (hilos) concurrentes que se ejecutarán. El valor predeterminado es 1.

-j hilos
--threads=hilos

Número de hilos que se utilizarán para la ejecución. El valor predeterminado es 1. Si se especifica, se utilizarán hilos hilos para simular el número especificado de clientes. Esto es útil para simular un mayor número de clientes que el número de CPU disponibles.

-l
--log

Registra las estadísticas de latencia de cada transacción en un archivo llamado pgbench_log. No se genera ningún resumen de la prueba en la salida estándar en este modo.

-L factor_latencia
--latency-file=factor_latencia

Registra las estadísticas de latencia en el archivo especificado. El archivo debe contener los datos de latencia generados por una ejecución anterior de pgbench con la opción -l. Si se especifica, el tiempo total de ejecución será el tiempo que tardan en procesarse las transacciones de un cliente, y los tiempos de acceso a la base de datos se simularán basándose en las latencias registradas en el archivo. Esto puede ser útil para probar el impacto de la latencia de red en el rendimiento.

-M modo_consulta
--protocol=modo_consulta

Modo de consulta a utilizar. Los valores posibles son: simple (para usar sentencias SQL simples), extended (para usar sentencias SQL preparadas), y prepared_statement (para usar sentencias SQL preparadas sin utilizar el protocolo de ejecución de la API de PostgreSQL). El valor predeterminado es simple.

-P nombre_esquema
--schema=nombre_esquema

Especifica el nombre del esquema para usar con el modo de consulta prepared_statement. El valor predeterminado es public.

-p puerto
--port=puerto

Especifica el puerto TCP o el socket de dominio Unix local para la conexión.

-r
--rate

Intenta alcanzar una tasa de transacciones constante. Consulte la sección “Control de la Tasa” para obtener más detalles.

-R tasa_objetivo
--target-rate=tasa_objetivo

Establece la tasa objetivo de transacciones por segundo para la opción -r. El valor predeterminado es 1000.0.

-S secuencia_acceso
--vacuum-tables=secuencia_acceso

Establece el orden de acceso a las tablas. La secuencia de acceso está determinada por la cadena de caracteres proporcionada. La secuencia de caracteres predeterminada es 'a'. Las letras disponibles son:

a (accounts/cuentas)

b (branches/sucursales)

t (tellers/cajeros)

h (history/historial)

Por ejemplo, para acceder a las tablas en el orden 'branches', 'tellers', 'accounts', 'history', use '-S bth'.

-t transacciones
--transactions=transacciones

Número de transacciones a ejecutar por cliente. El valor predeterminado es 1000.

-T segundos
--time=segundos

Tiempo en segundos durante el cual se ejecutarán las transacciones. Cuando se especifica esta opción, el parámetro transacciones se ignora.

-v
--verbose

Genera estadísticas de latencia detalladas para cada transacción.

--sampling=porcentaje

Muestra solo el porcentaje especificado de transacciones. El valor predeterminado es 100.

--stabilize=segundos

Omite las estadísticas durante los segundos especificados al principio de la prueba. Esto puede ser útil para permitir que el sistema se estabilice antes de que comiencen las mediciones.

--report-latencies

Imprime un resumen de las estadísticas de latencia para todas las transacciones, en lugar de solo el promedio y la desviación estándar. Esto se hace solo si se utiliza la opción -v.

--script-names

Imprime el nombre de cada script de transacción que se está ejecutando.

--show-counts

Imprime el número de veces que se ha ejecutado cada tipo de transacción.

--without-initial-connection

No incluye el tiempo de conexión inicial en el cálculo de tps.

-h host

Especifica el nombre de host o la dirección IP de la máquina en la que se ejecuta el servidor de base de datos.

-p puerto
--port=puerto

Especifica el puerto TCP o el socket de dominio Unix local para la conexión.

-U nombre_usuario

Especifica el nombre de usuario para conectarse como.

-w
--no-password

Nunca solicite una contraseña. Si el servidor requiere autenticación por contraseña y no se proporciona una contraseña de alguna otra manera (por ejemplo, a través de la variable de entorno PGPASSWORD), la conexión fallará.

-d
--debug

Habilita la salida de depuración detallada.

-V

Imprime la versión de pgbench y sal.

-?

EJEMPLOS

Para inicializar una base de datos llamada mydb con el factor de escala predeterminado:

pgbench -i mydb

Para inicializar la misma base de datos con 100 veces más datos:

pgbench -i -s 100 mydb

Para ejecutar una prueba de referencia en mydb con 16 clientes concurrentes y 100000 transacciones por cliente:

pgbench -c 16 -t 100000 mydb

Para ejecutar una prueba de referencia en mydb durante 10 minutos (600 segundos) con 16 clientes concurrentes:

pgbench -c 16 -T 600 mydb

Para ejecutar una prueba de referencia utilizando un script personalizado llamado my_script.sql con 8 clientes concurrentes y 10000 transacciones por cliente:

pgbench -f my_script.sql -c 8 -t 10000 mydb

Para ejecutar una prueba de referencia utilizando un script personalizado llamado my_script.sql durante 5 minutos (300 segundos) con 8 clientes concurrentes:

pgbench -f my_script.sql -c 8 -T 300 mydb

Para inicializar la base de datos mydb creando tablas particionadas por hash en la tabla de cuentas, con 32 particiones:

pgbench --partition-method=hash --partitions=32 -i -s 100 mydb

FALLOS Y REINTENTOS

pgbench registrará las transacciones fallidas si ocurre alguno de los siguientes:

  1. Un error de serialización ha ocurrido. Esto puede ocurrir si dos transacciones intentan modificar la misma fila al mismo tiempo. pgbench reintentará la transacción automáticamente. Se pueden realizar hasta 10 reintentos por transacción.
  2. Un bloqueo (deadlock) ha ocurrido. pgbench reintentará la transacción automáticamente. Se pueden realizar hasta 10 reintentos por transacción.
  3. Un error de restricción de clave foránea ha ocurrido. Esto puede ocurrir si un cliente intenta insertar una fila que hace referencia a una fila que no existe. pgbench no reintentará automáticamente estas transacciones, sino que las registrará como fallidas.
  4. Cualquier otro error SQL. pgbench no reintentará automáticamente estas transacciones, sino que las registrará como fallidas.

Se puede controlar el número de reintentos para errores de serialización y bloqueo utilizando la opción --max-tries. El valor predeterminado es 10.

El parámetro retry_delay en la sección [ PostgreSQL ] del archivo de configuración postgresql.conf controla la cantidad de tiempo que pgbench esperará antes de reintentar una transacción fallida debido a serialización o bloqueo. El valor predeterminado es 100 milisegundos.

CONTROL DE LA TASA

pgbench puede intentar alcanzar una tasa de transacciones constante utilizando la opción -r. Cuando se utiliza esta opción, pgbench intentará mantener una tasa de transacciones de -R transacciones por segundo. Esto se logra ajustando el número de clientes que ejecutan transacciones activamente. Si el número de clientes excede el número de transacciones por segundo objetivo, algunos clientes se pondrán en espera para evitar sobrecargar el servidor.

El control de la tasa es útil para simular cargas de trabajo del mundo real, donde la tasa de transacciones no es constante, sino que fluctúa con el tiempo. También puede ser útil para determinar la máxima tasa de transacciones que puede manejar un servidor antes de que el rendimiento se degrade.

El control de la tasa requiere que se especifique la opción -r y la opción -R (o el valor predeterminado de 1000.0 TPS). También se puede usar la opción -c para especificar un número máximo de clientes. Si no se especifica, el número de clientes se establecerá automáticamente.

Opciones de benchmarking

pgbench acepta los siguientes argumentos de línea de comandos para el benchmarking:

-b scriptname[@weight]
--builtin=scriptname[@weight]

Agrega el script incorporado especificado a la lista de scripts a ejecutar. Los scripts incorporados disponibles son: tpcb-like, simple-update y select-only. Se aceptan prefijos no ambiguos de nombres incorporados. Con el nombre especial list, se muestra la lista de scripts incorporados y se sale inmediatamente.

Opcionalmente, escriba un peso entero después de @ para ajustar la probabilidad de seleccionar este script en comparación con otros. El peso predeterminado es 1. Ver más abajo para más detalles.

-c clients
--client=clients

Número de clientes simulados, es decir, número de sesiones de base de datos concurrentes. El valor predeterminado es 1.

-C
--connect

Establece una nueva conexión para cada transacción, en lugar de hacerlo una sola vez por sesión de cliente. Esto es útil para medir la sobrecarga de la conexión.

-D varname=value
--define=varname=value

Define una variable para su uso en un script personalizado (ver más abajo). Se permiten múltiples opciones -D.

-f filename[@weight]
--file=filename[@weight]

Agrega un script de transacciones leído de filename a la lista de scripts a ejecutar.

Opcionalmente, escriba un peso entero después de @ para ajustar la probabilidad de seleccionar este script en comparación con otros. El peso predeterminado es 1. (Para usar un nombre de archivo de script que incluya un carácter @, agregue un peso para que no haya ambigüedad, por ejemplo, filen@me@1). Ver más abajo para más detalles.

-j threads
--jobs=threads

Número de hilos de trabajo dentro de pgbench. Usar más de un hilo puede ser útil en máquinas con varias CPU. Los clientes se distribuyen lo más uniformemente posible entre los hilos disponibles. El valor predeterminado es 1.

-l
--log

Escribe información sobre cada transacción en un archivo de registro. Ver más abajo para más detalles.

-L limit
--latency-limit=limit

Las transacciones que duran más de limit milisegundos se cuentan y se informan por separado, como tardías.

Cuando se utiliza la limitación de velocidad (--rate=...), las transacciones que se retrasan más de limit ms con respecto a lo programado, y que por lo tanto no tienen esperanza de cumplir el límite de latencia, no se envían al servidor en absoluto. Se cuentan y se informan por separado como omitidas.

Cuando se utiliza la opción --max-tries, una transacción que falla debido a una anomalía de serialización o a un interbloqueo no se reintentará si el tiempo total de todos sus intentos es superior a limit ms. Para limitar solo el tiempo de los intentos y no su número, use --max-tries=0. Por defecto, la opción --max-tries se establece en 1 y las transacciones con errores de serialización/interbloqueo no se reintentan. Ver Fallos y reintentos de serialización/interbloqueo para más información sobre el reintento de dichas transacciones.

-M querymode
--protocol=querymode

Protocolo a utilizar para enviar consultas al servidor:
•simple: usa el protocolo de consulta simple.
•extended: usa el protocolo de consulta extendida.
•prepared: usa el protocolo de consulta extendida con sentencias preparadas.

En el modo preparado, pgbench reutiliza el resultado del análisis sintáctico a partir de la segunda iteración de la consulta, por lo que pgbench se ejecuta más rápido que en otros modos.

El valor predeterminado es el protocolo de consulta simple. (Ver Capítulo 54 para más información).

-n
--no-vacuum

No realiza vacuum antes de ejecutar la prueba. Esta opción es necesaria si está ejecutando un escenario de prueba personalizado que no incluye las tablas estándar pgbench_accounts, pgbench_branches, pgbench_history y pgbench_tellers.

-N
--skip-some-updates

Ejecuta el script incorporado simple-update. Abreviatura de -b simple-update.

-P sec
--progress=sec

Muestra el informe de progreso cada sec segundos. El informe incluye el tiempo transcurrido desde el inicio de la ejecución, las TPS desde el último informe y el promedio de latencia de transacciones, la desviación estándar y el número de transacciones fallidas desde el último informe. Bajo limitación de velocidad (-R), la latencia se calcula con respecto al tiempo de inicio programado de la transacción, no al tiempo de inicio real de la transacción, por lo que también incluye el tiempo promedio de retraso de programación. Cuando se utiliza --max-tries para habilitar reintentos de transacciones después de errores de serialización/interbloqueo, el informe incluye el número de transacciones reintentadas y la suma de todos los reintentos.

-r
--report-per-command

Informa las siguientes estadísticas para cada comando después de que finaliza el benchmarking: la latencia promedio por sentencia (tiempo de ejecución desde la perspectiva del cliente), el número de fallos y el número de reintentos después de errores de serialización o interbloqueo en este comando. El informe muestra estadísticas de reintento solo si la opción --max-tries no es igual a 1.

-R rate
--rate=rate

Ejecuta transacciones apuntando a la tasa especificada en lugar de ejecutarse lo más rápido posible (el valor predeterminado). La tasa se da en transacciones por segundo. Si la tasa objetivo está por encima de la tasa máxima posible, el límite de tasa no afectará los resultados.

La tasa se alcanza iniciando transacciones a lo largo de una línea de tiempo de programación distribuida según Poisson. El tiempo de inicio programado esperado avanza según cuándo comenzó el cliente por primera vez, no cuándo terminó la transacción anterior. Este enfoque significa que cuando las transacciones superan su tiempo de finalización programado original, es posible que las posteriores vuelvan a alcanzarlo.

Cuando la limitación de velocidad está activa, la latencia de la transacción informada al final de la ejecución se calcula a partir de los tiempos de inicio programados, por lo que incluye el tiempo que cada transacción tuvo que esperar a que terminara la transacción anterior. El tiempo de espera se llama tiempo de retraso de programación, y su promedio y máximo también se informan por separado. La latencia de la transacción con respecto al tiempo de inicio real de la transacción, es decir, el tiempo dedicado a ejecutar la transacción en la base de datos, se puede calcular restando el tiempo de retraso de programación de la latencia informada.

Si se utiliza --latency-limit junto con --rate, una transacción puede retrasarse tanto que ya supere el límite de latencia cuando termine la transacción anterior, porque la latencia se calcula a partir de los tiempos de inicio programados. Dichas transacciones no se envían al servidor, sino que se omiten por completo y se cuentan por separado.

Un tiempo de retraso de programación alto es una indicación de que el sistema no puede procesar transacciones a la tasa especificada, con el número elegido de clientes e hilos. Cuando el tiempo promedio de ejecución de la transacción es más largo que el intervalo programado entre cada transacción, cada transacción sucesiva se retrasará cada vez más, y el tiempo de retraso de programación seguirá aumentando cuanto más tiempo se ejecute la prueba. Cuando esto suceda, deberá reducir la tasa de transacciones especificada.

¿Qué «Transacción» se Realiza Realmente en pgbench?

pgbench ejecuta scripts de prueba elegidos aleatoriamente de una lista especificada. Los scripts pueden incluir scripts incorporados especificados con -b y scripts proporcionados por el usuario especificados con -f. A cada script se le puede asignar un peso relativo especificado después de un @ para cambiar su probabilidad de selección. El peso predeterminado es 1. Los scripts con un peso de 0 se ignoran.

El script de transacción incorporado predeterminado (también invocado con -b tpcb-like) emite siete comandos por transacción sobre aid, tid, bid y delta elegidos aleatoriamente. El escenario está inspirado en el benchmark TPC-B, pero en realidad no es TPC-B, de ahí el nombre.

1.BEGIN;
2.UPDATE pgbench_accounts SET abalance = abalance + :delta WHERE aid = :aid;
3.SELECT abalance FROM pgbench_accounts WHERE aid = :aid;
4.UPDATE pgbench_tellers SET tbalance = tbalance + :delta WHERE tid = :tid;
5.UPDATE pgbench_branches SET bbalance = bbalance + :delta WHERE bid = :bid;
6.INSERT INTO pgbench_history (tid, bid, aid, delta, mtime) VALUES (:tid, :bid, :aid, :delta, CURRENT_TIMESTAMP);
7.END;

Si selecciona el incorporado simple-update (también -N), los pasos 4 y 5 no se incluyen en la transacción. Esto evitará la contención de actualización en estas tablas, pero hace que el caso de prueba se parezca aún menos a TPC-B.

Si selecciona el incorporado select-only (también -S), solo se emite el SELECT.

Scripts Personalizados

pgbench tiene soporte para ejecutar escenarios de benchmark personalizados reemplazando el script de transacción predeterminado (descrito anteriormente) con un script de transacción leído de un archivo (opción -f). En este caso, una «transacción» cuenta como una ejecución de un archivo de script.

Un archivo de script contiene uno o más comandos SQL terminados por puntos y comas. Las líneas vacías y las líneas que comienzan con -- se ignoran. Los archivos de script también pueden contener «meta-comandos», que son interpretados por pgbench mismo, como se describe a continuación.


Nota

Antes de PostgreSQL 9.6, los comandos SQL en los archivos de script estaban terminados por saltos de línea, por lo que no podían continuarse en varias líneas. Ahora se requiere un punto y coma para separar comandos SQL consecutivos (aunque un comando SQL no necesita uno si va seguido de un meta-comando). Si necesita crear un archivo de script que funcione con versiones antiguas y nuevas de pgbench, asegúrese de escribir cada comando SQL en una sola línea que termine con un punto y coma.

Se asume que los scripts de pgbench no contienen bloques incompletos de transacciones SQL. Si en tiempo de ejecución el cliente llega al final del script sin completar el último bloque de transacción, será abortado.

Existe una instalación simple de sustitución de variables para archivos de script. Los nombres de las variables deben consistir en letras (incluidas letras no latinas), dígitos y guiones bajos, y el primer carácter no debe ser un dígito. Las variables se pueden establecer mediante la opción de línea de comandos -D, explicada anteriormente, o mediante los meta-comandos explicados a continuación. Además de cualquier variable preestablecida por opciones de línea de comandos -D, hay algunas variables que se preestablecen automáticamente, enumeradas en la Tabla 301. Un valor especificado para estas variables usando -D tiene precedencia sobre los preajustes automáticos. Una vez establecida, el valor de una variable se puede insertar en un comando SQL escribiendo :nombrevariable. Al ejecutar más de una sesión de cliente, cada sesión tiene su propio conjunto de variables. pgbench admite hasta 255 usos de variables en una sola sentencia.

\gset [prefix] \aset [prefix]

Estos comandos se pueden utilizar para finalizar consultas SQL, ocupando el lugar del punto y coma terminador (;).

Cuando se utiliza el comando \gset, se espera que la consulta SQL precedente devuelva una fila, cuyas columnas se almacenan en variables con nombres derivados de los nombres de las columnas y prefijadas con prefix si se proporciona.

Cuando se utiliza el comando \aset, todas las consultas SQL combinadas (separadas por \;) tienen sus columnas almacenadas en variables con nombres derivados de los nombres de las columnas y prefijadas con prefix si se proporciona. Si una consulta no devuelve ninguna fila, no se realiza ninguna asignación y la variable puede ser probada por su existencia para detectarlo. Si una consulta devuelve más de una fila, se conserva el último valor.

\gset y \aset no se pueden utilizar en modo pipeline, si

\gset

El comando \gset se usa para almacenar el resultado de la última consulta ejecutada en una o más variables. Esto es útil para reutilizar valores obtenidos de la base de datos en comandos posteriores dentro del script de pgbench. A diferencia de \set, que asigna un valor calculado o literal a una variable, \gset extrae valores de los resultados de una consulta SQL.

Cuando se usa sin argumentos, \gset toma el resultado de la última consulta SQL y lo asigna a una variable cuyo nombre coincide con el nombre de la columna devuelta por la consulta. Si la consulta devuelve múltiples columnas, \gset creará una variable para cada columna.

Para asignar los resultados a nombres de variables específicos, se puede proporcionar un prefijo o nombres de variables individuales como argumentos para \gset. Si se proporciona un prefijo, cada resultado se asignará a una variable que combine el prefijo y el nombre de la columna. Si se proporcionan nombres de variables individuales, el número de nombres de variables debe coincidir con el número de columnas en el resultado de la consulta.

Es importante tener en cuenta que \gset solo funciona correctamente con consultas que devuelven exactamente una fila. Si la consulta devuelve cero filas, las variables no se establecerán. Si devuelve más de una fila, solo se utilizará la primera fila para establecer las variables.

El uso de \gset es crucial en escenarios donde los valores calculados por una consulta deben ser utilizados en operaciones posteriores, como actualizaciones condicionales o para alimentar parámetros en consultas subsiguientes. Sin embargo, su aplicación está limitada a la captura de resultados inmediatos después de la ejecución de una consulta, y no puede prever o recuperar valores que aún no están disponibles en el momento en que los comandos los necesitarían.

El siguiente ejemplo coloca el saldo final de la cuenta de la primera consulta en la variable abalance, y llena las variables p_two y p_three con enteros de la tercera consulta. El resultado de la segunda consulta se descarta. El resultado de las dos últimas consultas combinadas se almacena en las variables four y five.

UPDATE pgbench_accounts
  SET abalance = abalance + :delta
  WHERE aid = :aid
  RETURNING abalance \gset
-- compound of two queries
SELECT 1 \;
SELECT 2 AS two, 3 AS three \gset p_
SELECT 4 AS four \; SELECT 5 AS five \aset

La función random genera valores usando una distribución uniforme, es decir, todos los valores se extraen dentro del rango especificado con igual probabilidad. Las funciones random_exponential, random_gaussian y random_zipfian requieren un parámetro doble adicional que determina la forma precisa de la distribución.

•Para una distribución exponencial, parameter controla la distribución truncando una distribución exponencial que decrece rápidamente en parameter, y luego proyectando en enteros entre los límites. Para ser precisos, con 
f(x) = exp(-parameter * (x - min) / (max - min + 1)) / (1 - exp(-parameter))

Entonces el valor i entre min y max inclusive se extrae con probabilidad: f(i) - f(i + 1).

Intuitivamente, cuanto mayor sea el parameter, con más frecuencia se accederán los valores cercanos a min, y con menos frecuencia los valores cercanos a max. Cuanto más cerca de 0 esté el parameter, más plana (más uniforme) será la distribución de acceso. Una aproximación burda de la distribución es que el 1% de los valores más frecuentes en el rango, cercanos a min, se extraen el parameter% de las veces. El valor parameter debe ser estrictamente positivo.

•Para una distribución Gaussiana, el intervalo se mapea a una distribución normal estándar (la curva Gaussiana clásica en forma de campana) truncada en -parameter a la izquierda y +parameter a la derecha. Los valores en el medio del intervalo son más propensos a ser extraídos. Para ser precisos, si PHI(x) es la función de distribución acumulada de la distribución normal estándar, con media mu definida como (max + min) / 2.0, con 
f(x) = PHI(2.0 * parameter * (x - mu) / (max - min + 1)) /
       (2.0 * PHI(parameter) - 1)

entonces el valor i entre min y max inclusive se extrae con probabilidad: f(i + 0.5) - f(i - 0.5). Intuitivamente, cuanto mayor sea el parameter, con más frecuencia se extraerán los valores cercanos al medio del intervalo, y con menos frecuencia los valores cercanos a los límites min y max. Aproximadamente el 67% de los valores se extraen del medio 1.0 / parameter, es decir, un relativo 0.5 / parameter alrededor de la media, y el 95% del medio 2.0 / parameter, es decir, un relativo 1.0 / parameter alrededor de la media; por ejemplo, si parameter es 4.0, el 67% de los valores se extraen del cuarto medio (1.0 / 4.0) del intervalo (es decir, de 3.0 / 8.0 a 5.0 / 8.0) y el 95% de la mitad media (2.0 / 4.0) del intervalo (segundo y tercer cuartiles). El valor mínimo permitido de parameter es 2.0.

•random_zipfian genera una distribución Zipfiana acotada. parameter define cuán sesgada está la distribución. Cuanto mayor sea el parameter, con más frecuencia se extraerán los valores más cercanos al principio del intervalo. La distribución es tal que, asumiendo que el rango comienza en 1, la relación de la probabilidad de extraer k versus extraer k+1 es ((k+1)/k)**parameter. Por ejemplo, random_zipfian(1, ..., 2.5) produce el valor 1 aproximadamente 5.66 veces más frecuentemente que 2, el cual a su vez se produce 2.76 veces más frecuentemente que 3, y así sucesivamente.

La implementación de pgbench se basa en "Non-Uniform Random Variate Generation", Luc Devroye, págs. 550-551, Springer 1986. Debido a las limitaciones de ese algoritmo, el valor de parameter está restringido al rango [1.001, 1000].


Nota

Al diseñar un benchmark que selecciona filas de manera no uniforme, tenga en cuenta que las filas elegidas pueden estar correlacionadas con otros datos, como identificadores de una secuencia o el orden físico de las filas, lo que puede sesgar las mediciones de rendimiento.

Para evitar esto, puede que desee utilizar la función permute, o algún otro paso adicional con un efecto similar, para barajar las filas seleccionadas y eliminar tales correlaciones.

Las funciones hash hash, hash_murmur2 y hash_fnv1a aceptan un valor de entrada y un parámetro de semilla opcional. En caso de que la semilla no se proporcione, se utiliza el valor de :default_seed, que se inicializa aleatoriamente a menos que se establezca mediante la opción de línea de comandos -D.

permute acepta un valor de entrada, un tamaño y un parámetro de semilla opcional. Genera una permutación pseudoaleatoria de enteros en el rango [0, size), y devuelve el índice del valor de entrada en los valores permutados. La permutación elegida está parametrizada por la semilla, que por defecto es :default_seed, si no se especifica. A diferencia de las funciones hash, permute asegura que no haya colisiones ni huecos en los valores de salida. Los valores de entrada fuera del intervalo se interpretan módulo el tamaño. La función genera un error si el tamaño no es positivo. permute se puede usar para dispersar la distribución de funciones aleatorias no uniformes como random_zipfian o random_exponential, de modo que los valores extraídos con más frecuencia no estén trivialmente correlacionados. Por ejemplo, el siguiente script de pgbench simula una posible carga de trabajo del mundo real típica para plataformas de redes sociales y blogs donde unas pocas cuentas generan una carga excesiva:

\set size 1000000
\set r random_zipfian(1, :size, 1.07)
\set k 1 + permute(:r, :size)

En algunos casos, se necesitan varias distribuciones distintas que no se correlacionen entre sí, y es aquí donde el parámetro de semilla opcional resulta útil:

\set k1 1 + permute(:r, :size, :default_seed + 123)
\set k2 1 + permute(:r, :size, :default_seed + 321)

Un comportamiento similar también se puede aproximar con hash:

\set size 1000000
\set r random_zipfian(1, 100 * :size, 1.07)
\set k 1 + abs(hash(:r)) % :size

Sin embargo, dado que hash genera colisiones, algunos valores no serán alcanzables y otros serán más frecuentes de lo esperado respecto a la distribución original.

Como ejemplo, la definición completa de la transacción integrada similar a TPC-B es:

\set aid random(1, 100000 * :scale)
\set bid random(1, 1 * :scale)
\set tid random(1, 10 * :scale)
\set delta random(-5000, 5000)
BEGIN;
UPDATE pgbench_accounts SET abalance = abalance + :delta WHERE aid = :aid;
SELECT abalance FROM pgbench_accounts WHERE aid = :aid;
UPDATE pgbench_tellers SET tbalance = tbalance + :delta WHERE tid = :tid;
UPDATE pgbench_branches SET bbalance = bbalance + :delta WHERE bid = :bid;
INSERT INTO pgbench_history (tid, bid, aid, delta, mtime) VALUES (:tid, :bid, :aid, :delta, CURRENT_TIMESTAMP);
END;

Este script permite que cada iteración de la transacción haga referencia a filas diferentes y elegidas al azar. (Este ejemplo también muestra por qué es importante que cada sesión de cliente tenga sus propias variables; de lo contrario, no estarían tocando filas diferentes de forma independiente).

Registro por Transacción

Con la opción -l (pero sin la opción --aggregate-interval), pgbench escribe información sobre cada transacción en un archivo de registro. El archivo de registro se llamará prefix.nnn, donde prefix por defecto es pgbench_log, y nnn es el PID del proceso de pgbench. El prefijo se puede cambiar utilizando la opción --log-prefix. Si la opción -j es 2 o superior, de modo que haya varios hilos trabajadores, cada uno tendrá su propio archivo de registro. El primer trabajador utilizará el mismo nombre para su archivo de registro que en el caso estándar de un solo trabajador. Los archivos de registro adicionales para los otros trabajadores se llamarán prefix.nnn.mmm, donde mmm es un número secuencial para cada trabajador comenzando con 1.

Cada línea en un archivo de registro describe una transacción. Contiene los siguientes campos separados por espacios:

client_id

identifica la sesión de cliente que ejecutó la transacción

transaction_no

cuenta cuántas transacciones ha ejecutado esa sesión

time

tiempo transcurrido de la transacción, en microsegundos

script_no

identifica el archivo de script que se utilizó para la transacción (útil cuando se especifican múltiples scripts con -f o -b)

time_epoch

hora de finalización de la transacción, como marca de tiempo de la época Unix

time_us

parte fraccional de segundo de la hora de finalización de la transacción, en microsegundos

schedule_lag

retraso de inicio de la transacción, es decir, la diferencia entre la hora de inicio programada de la transacción y la hora en que realmente comenzó, en microsegundos (presente solo si se especifica --rate)

retries

recuento de reintentos después de errores de serialización o interbloqueo durante la transacción (presente solo si --max-tries no es igual a uno)

Cuando se utilizan tanto --rate como --latency-limit, el time para una transacción omitida se informará como omitida. Si la transacción finaliza con un error, su time se informará como fallida. Si utiliza la opción --failures-detailed, el time de la transacción fallida se informará como serialización o interbloqueo dependiendo del tipo de error (ver Errores y Reintentos de Serialización/Interbloqueo para más información).

Fallos y Reintentos de Serialización/Bloqueo

Al ejecutar pgbench, existen tres tipos principales de errores:

•Errores del programa principal. Son los más graves y siempre resultan en una salida inmediata de pgbench con el mensaje de error correspondiente. Incluyen:
•errores al inicio de pgbench (por ejemplo, un valor de opción no válido);
•errores en el modo de inicialización (por ejemplo, falla la consulta para crear tablas para scripts incorporados);
•errores antes de iniciar los hilos (por ejemplo, no se pudo conectar al servidor de base de datos, error de sintaxis en el comando meta, fallo en la creación del hilo);
•errores internos de pgbench (que se supone que nunca ocurren...).
•Errores cuando el hilo administra sus clientes (por ejemplo, el cliente no pudo iniciar una conexión con el servidor de base de datos / el socket para conectar el cliente al servidor de base de datos se ha vuelto inválido). En tales casos, todos los clientes de este hilo se detienen mientras otros hilos continúan funcionando. Sin embargo, si se especifica --exit-on-abort, todos los hilos se detienen inmediatamente en este caso.
•Errores directos del cliente. Llevan a una salida inmediata de pgbench con el mensaje de error correspondiente en caso de un error interno de pgbench (que se supone que nunca ocurre...) o cuando se especifica --exit-on-abort. De lo contrario, en el peor de los casos, solo conducen a la interrupción del cliente fallido mientras otros clientes continúan su ejecución (pero algunos errores del cliente se manejan sin la interrupción del cliente y se informan por separado, ver más abajo). Más adelante en esta sección, se asume que los errores discutidos son solo errores directos del cliente y no son errores internos de pgbench.

La ejecución de un cliente se interrumpe en caso de un error grave; por ejemplo, se perdió la conexión con el servidor de base de datos o se alcanzó el final del script sin completar la última transacción. Además, si la ejecución de un comando SQL o meta falla por razones distintas a los errores de serialización o bloqueo, el cliente se interrumpe. De lo contrario, si un comando SQL falla con errores de serialización o bloqueo, el cliente no se interrumpe. En tales casos, la transacción actual se revierte, lo que también incluye establecer las variables del cliente como estaban antes de la ejecución de esta transacción (se asume que un script de transacción contiene solo una transacción; vea Qué es en realidad la "Transacción" Realizada en pgbench? para más información). Las transacciones con errores de serialización o bloqueo se repiten después de las reversiones hasta que se completan con éxito o alcanzan el número máximo de intentos (especificado por la opción --max-tries) /

el tiempo máximo de reintentos (especificado por la opción --latency-limit) / el final de la prueba de rendimiento (especificado por la opción --time). Si la última ejecución de prueba falla, esta transacción se informará como fallida, pero el cliente no se abortará y continuará funcionando.


Nota

Sin especificar la opción --max-tries, una transacción nunca se reintentará después de un error de serialización o bloqueo porque su valor predeterminado es 1. Utilice un número ilimitado de intentos (--max-tries=0) y la opción --latency-limit para limitar solo el tiempo máximo de los intentos. También puede utilizar la opción --time para limitar la duración de la prueba de rendimiento con un número ilimitado de intentos.

Tenga cuidado al repetir scripts que contengan varias transacciones: el script siempre se repite en su totalidad, por lo que las transacciones exitosas se pueden realizar varias veces.

Tenga cuidado al repetir transacciones con comandos de shell. A diferencia de los resultados de los comandos SQL, los resultados de los comandos de shell no se revierten, excepto el valor de la variable del comando \setshell.

La latencia de una transacción exitosa incluye todo el tiempo de ejecución de la transacción con reversiones y reintentos. La latencia se mide solo para transacciones y comandos exitosos, pero no para transacciones o comandos fallidos.

El informe principal contiene el número de transacciones fallidas. Si la opción --max-tries no es igual a 1, el informe principal también contiene estadísticas relacionadas con los reintentos: el número total de transacciones reintentadas y el número total de reintentos. El informe por script hereda todos estos campos del informe principal. El informe por instrucción muestra estadísticas de reintento solo si la opción --max-tries no es igual a 1.

Si desea agrupar los fallos por tipos básicos en los registros por transacción y de agregación, así como en los informes principal y por script, utilice la opción --failures-detailed. Si también desea distinguir todos los errores y fallos (errores sin reintento) por tipo, incluyendo qué límite para los reintentos se excedió y cuánto se excedió para los fallos de serialización/bloqueo, utilice la opción --verbose-errors.

Métodos de Acceso a Tabla

Puede especificar el Método de Acceso a Tabla para las tablas de pgbench. La variable de entorno PGOPTIONS especifica las opciones de configuración de la base de datos que se pasan a PostgreSQL a través de la línea de comandos (ver Sección 19.1.4). Por ejemplo, un método de acceso a tabla predeterminado hipotético para las tablas que pgbench crea, llamado wuzza, se puede especificar con:

PGOPTIONS='-c default_table_access_method=wuzza'

Buenas Prácticas

Es muy fácil usar pgbench para producir números completamente sin sentido. Aquí hay algunas pautas para ayudarlo a obtener resultados útiles.

En primer lugar, *nunca* crea ninguna prueba que se ejecute solo por unos pocos segundos. Utilice la opción -t o -T para que la ejecución dure al menos unos pocos minutos, para promediar el ruido. En algunos casos, podría necesitar horas para obtener números que sean reproducibles. Es una buena idea probar la ejecución varias veces, para averiguar si sus números son reproducibles o no.

Para el escenario de prueba predeterminado similar a TPC-B, el factor de escala de inicialización (-s) debe ser al menos tan grande como el mayor número de clientes que pretende probar (-c); de lo contrario, estará midiendo principalmente la contención de actualizaciones. Solo hay -s filas en la tabla pgbench_branches, y cada transacción quiere actualizar una de ellas, por lo que los valores de -c en exceso de -s sin duda resultarán en muchas transacciones bloqueadas esperando a otras transacciones.

El escenario de prueba predeterminado también es bastante sensible a cuánto tiempo ha pasado desde que se inicializaron las tablas: la acumulación de filas muertas y espacio muerto en las tablas cambia los resultados. Para comprender los resultados, debe hacer un seguimiento del número total de actualizaciones y cuándo ocurren las limpiezas (vacuuming). Si autovacuum está habilitado, puede resultar en cambios impredecibles en el rendimiento medido.

Una limitación de pgbench es que puede convertirse en el cuello de botella al intentar probar un gran número de sesiones de cliente. Esto se puede aliviar ejecutando pgbench en una máquina diferente al servidor de la base de datos, aunque la baja latencia de red será esencial. Incluso podría ser útil ejecutar varias instancias de pgbench concurrentemente, en varias máquinas cliente, contra el mismo servidor de base de datos.

Seguridad

Si usuarios no confiables tienen acceso a una base de datos que no ha adoptado un patrón de uso de esquema seguro, no ejecute pgbench en esa base de datos. pgbench utiliza nombres no calificados y no manipula la ruta de búsqueda.
