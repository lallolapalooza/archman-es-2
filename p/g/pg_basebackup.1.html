pg_basebackup(1)

Paquete: postgresql

Licencias: PostgreSQL

PG_BASEBACKUP(1) PostgreSQL 18.1 Documentation PG_BASEBACKUP(1)

NOMBRE

pg_basebackup - tomar una copia de seguridad base de un clúster de PostgreSQL

SINOPSIS

pg_basebackup [opción...]

DESCRIPCIÓN

pg_basebackup se utiliza para tomar una copia de seguridad base de un clúster de bases de datos PostgreSQL en ejecución. La copia de seguridad se realiza sin afectar a otros clientes de la base de datos y se puede utilizar tanto para la recuperación ante fallos puntual (véase la Sección 25.3) como punto de partida para un servidor standby de log-shipping o streaming replication (véase la Sección 26.2).

pg_basebackup puede tomar una copia de seguridad base completa o incremental. Cuando se utiliza para tomar una copia de seguridad completa, realiza una copia exacta de los archivos del clúster de base de datos. Cuando se utiliza para tomar una copia de seguridad incremental, algunos archivos que habrían sido parte de una copia de seguridad completa pueden ser reemplazados por versiones incrementales de los mismos archivos, que contienen solo aquellos bloques que han sido modificados desde la copia de seguridad de referencia. Una copia de seguridad incremental no se puede usar directamente; en su lugar, se debe usar pg_combinebackup(1) primero para combinarla con las copias de seguridad anteriores de las que depende. Consulte la Sección 25.3.3 para obtener más información sobre las copias de seguridad incrementales y la Sección 25.3.5 para conocer los pasos para recuperarse de una copia de seguridad.

En cualquier modo, pg_basebackup se asegura de que el servidor se ponga y se saque del modo de copia de seguridad automáticamente. Las copias de seguridad siempre se toman de todo el clúster de bases de datos; no es posible respaldar bases de datos u objetos de base de datos individuales. Para copias de seguridad selectivas, se debe usar otra herramienta como pg_dump(1).

La copia de seguridad se realiza a través de una conexión PostgreSQL regular que utiliza el protocolo de replicación. La conexión debe realizarse con un ID de usuario que tenga permisos de REPLICACIÓN (véase la Sección 21.2) o que sea un superusuario, y pg_hba.conf debe permitir la conexión de replicación. El servidor también debe estar configurado con max_wal_senders suficientemente alto para proporcionar al menos un walsender para la copia de seguridad más uno para el streaming de WAL (si se utiliza).

Puede haber múltiples pg_basebackup ejecutándose al mismo tiempo, pero generalmente es mejor desde el punto de vista del rendimiento realizar solo una copia de seguridad y copiar el resultado.

pg_basebackup puede realizar una copia de seguridad base no solo desde un servidor primario sino también desde un standby. Para tomar una copia de seguridad desde un standby, configure el standby para que pueda aceptar conexiones de replicación (es decir, establezca max_wal_senders y hot_standby, y configure su pg_hba.conf adecuadamente). También necesitará habilitar full_page_writes en el primario.

Tenga en cuenta que existen algunas limitaciones al tomar una copia de seguridad desde un standby:

•El archivo de historial de copias de seguridad no se crea en el clúster de bases de datos respaldado.
•pg_basebackup no puede forzar al standby a cambiar a un nuevo archivo WAL al final de la copia de seguridad. Cuando se usa -X none, si la actividad de escritura en el primario es baja, pg_basebackup puede tener que esperar mucho tiempo hasta que el último archivo WAL requerido para la copia de seguridad sea cambiado y archivado. En este caso, puede ser útil ejecutar pg_switch_wal en el primario para activar un cambio inmediato del archivo WAL.
•Si el standby se promueve a primario durante la copia de seguridad, la copia de seguridad falla.
•Todos los registros WAL requeridos para la copia de seguridad deben contener suficientes escrituras de página completa, lo que requiere que habilite full_page_writes en el primario.

Cada vez que pg_basebackup está tomando una copia de seguridad base, la vista pg_stat_progress_basebackup del servidor informará el progreso de la copia de seguridad. Consulte la Sección 27.4.6 para obtener más detalles.

OPCIONES

Las siguientes opciones de línea de comandos controlan la ubicación y el formato de la salida:

-D directorio
--pgdata=directorio

Establece el directorio de destino para escribir la salida. pg_basebackup creará este directorio (y cualquier directorio padre faltante) si no existe. Si ya existe, debe estar vacío.

Cuando la copia de seguridad está en formato tar, el directorio de destino puede especificarse como - (guion), haciendo que el archivo tar se escriba en stdout.

Esta opción es obligatoria.

-F formato
--format=formato

Selecciona el formato para la salida. formato puede ser uno de los siguientes:

p
plain

Escribe la salida como archivos planos, con la misma estructura que el directorio de datos del servidor de origen y los tablespaces. Cuando el clúster no tiene tablespaces adicionales, toda la base de datos se colocará en el directorio de destino. Si el clúster contiene tablespaces adicionales, el directorio de datos principal se colocará en el directorio de destino, pero todos los demás tablespaces se colocarán en la misma ruta absoluta que tienen en el servidor de origen. (Véase --tablespace-mapping para cambiar eso.)

Este es el formato predeterminado.

t
tar

Escribe la salida como archivos tar en el directorio de destino. El contenido del directorio de datos principal se escribirá en un archivo llamado base.tar, y cada tablespace adicional se escribirá en un archivo tar separado con el nombre del OID de ese tablespace.

Si el directorio de destino se especifica como - (guion), el contenido tar se escribirá en la salida estándar, adecuado para canalizarlo (por ejemplo) a gzip. Esto solo está permitido si el clúster no tiene tablespaces adicionales y no se utiliza streaming de WAL.

-i archivo_manifiesto_antiguo
--incremental=archivo_manifiesto_antiguo

Realiza una copia de seguridad incremental. El manifiesto de copia de seguridad para la copia de seguridad de referencia debe ser proporcionado y se cargará en el servidor, que responderá enviando la copia de seguridad incremental solicitada.

-R
--write-recovery-conf

Crea un archivo standby.signal

y anexa la configuración de conexión al archivo postgresql.auto.conf en el directorio de destino (o dentro del archivo de archivo base cuando se usa el formato tar). Esto facilita la configuración de un servidor standby utilizando los resultados de la copia de seguridad.

El archivo postgresql.auto.conf registrará la configuración de conexión y, si se especifica, la ranura de replicación que está utilizando pg_basebackup, de modo que la replicación en streaming y la sincronización de ranuras de replicación lógica utilizarán la misma configuración más adelante. El nombre de la base de datos se registrará solo si el nombre de la base de datos se especificó explícitamente en la cadena de conexión o en la variable de entorno.

-t destino
--target=destino

Instruye al servidor dónde colocar la copia de seguridad base. El destino predeterminado es client, que especifica que la copia de seguridad debe enviarse a la máquina donde se está ejecutando pg_basebackup. Si el destino se establece en server:/algún/ruta en su lugar, la copia de seguridad se almacenará en la máquina donde se encuentra el servidor en el directorio /algún/ruta. Almacenar una copia de seguridad en el servidor requiere privilegios de superusuario o tener privilegios del rol pg_write_server_files. Si el destino se establece en blackhole, el contenido se descarta y no se almacena en ningún lugar. Esto solo debe usarse con fines de prueba, ya que no obtendrá una copia de seguridad real.

Dado que el streaming de WAL es implementado por pg_basebackup en lugar del servidor, esta opción no se puede usar junto con -Xstream. Dado que ese es el valor predeterminado, cuando se especifica esta opción, también debe especificar -Xfetch o -Xnone.

-T directorio_antiguo=directorio_nuevo
--tablespace-mapping=directorio_antiguo=directorio_nuevo

Reubica el tablespace en el directorio directorio_antiguo a directorio_nuevo durante la copia de seguridad. Para ser efectivo, directorio_antiguo debe coincidir exactamente con la especificación de ruta del tablespace tal como está definido en el servidor fuente. (Pero no es un error si no hay un tablespace en directorio_antiguo en el servidor fuente.) Mientras tanto, directorio_nuevo es un directorio en el sistema de archivos del host receptor. Al igual que con el directorio de destino principal, directorio_nuevo no necesita existir previamente, pero si existe debe estar vacío. Tanto directorio_antiguo como directorio_nuevo deben ser rutas absolutas. Si alguna de las rutas necesita contener un signo igual (=), preceda eso con una barra invertida. Esta opción se puede especificar varias veces para varios tablespaces.

Si un tablespace se reubica de esta manera, los enlaces simbólicos dentro del directorio de datos principal se actualizan para apuntar a la nueva ubicación. Por lo tanto, el nuevo directorio de datos está listo para ser utilizado para una nueva instancia de servidor con todos los tablespaces en las ubicaciones actualizadas.

Actualmente, esta opción solo funciona con el formato de salida plain; se ignora si se selecciona el formato tar.

--waldir=directorio_wal

Establece el directorio donde se escribirán los archivos WAL (write-ahead log). Por defecto, los archivos WAL se colocarán en el subdirectorio pg_wal del directorio de destino, pero esta opción se puede usar para colocarlos en otro lugar. waldir debe ser una ruta absoluta. Al igual que con el directorio de destino principal, waldir no necesita existir previamente, pero si existe, debe estar vacío. Esta opción solo se puede especificar cuando la copia de seguridad está en formato plano (plain).

-X método
--wal-method=método

Incluye los archivos WAL (write-ahead log) necesarios en la copia de seguridad. Esto incluirá todos los write-ahead logs generados durante la copia de seguridad. A menos que se especifique el método "none", es posible iniciar un postmaster en el directorio de destino sin necesidad de consultar el archivo WAL, lo que hace que la salida sea una copia de seguridad completamente independiente.

Los siguientes métodos para recopilar los write-ahead logs son compatibles:

n
none

No incluye los write-ahead logs en la copia de seguridad.

f
fetch

Los archivos write-ahead log se recopilan al final de la copia de seguridad. Por lo tanto, es necesario que el parámetro wal_keep_size del servidor de origen se establezca lo suficientemente alto como para que los datos del log requeridos no se eliminen antes del final de la copia de seguridad. Si los datos del log requeridos se han reciclado antes de que sea hora de transferirlos, la copia de seguridad fallará y será inutilizable.

Cuando se utiliza el formato tar, los archivos write-ahead log se incluirán en el archivo base.tar.

s
stream

Transmite los datos de write-ahead log mientras se realiza la copia de seguridad. Este método abrirá una segunda conexión al servidor y comenzará a transmitir el write-ahead log en paralelo mientras ejecuta la copia de seguridad. Por lo tanto, requerirá dos conexiones de replicación, no solo una. Siempre que el cliente pueda seguir el ritmo de los datos del write-ahead log, el uso de este método no requiere que se guarden write-ahead logs adicionales en el servidor de origen.

Cuando se utiliza el formato tar, los archivos write-ahead log se escribirán en un archivo separado llamado pg_wal.tar (si el servidor es una versión anterior a la 10, el archivo se llamará pg_xlog.tar).

Este valor es el predeterminado.

-z
--gzip

Habilita la compresión gzip del archivo tar de salida, con el nivel de compresión predeterminado. La compresión solo está disponible cuando se utiliza el formato tar, y el sufijo .gz se agregará automáticamente a todos los nombres de archivo tar.

-Z nivel
-Z [{cliente|servidor}-]método[:detalle]
--compress=nivel
--compress=[{cliente|servidor}-]método[:detalle]

Solicita la compresión de la copia de seguridad. Si se incluye cliente o servidor, especifica dónde se realizará la compresión. Comprimir en el servidor reducirá el ancho de banda de transferencia, pero aumentará el consumo de CPU del servidor. El valor predeterminado es cliente, excepto cuando se utiliza --target. En ese caso, la copia de seguridad no se está enviando al cliente, por lo que solo la compresión del servidor es sensata. Cuando se utiliza -Xstream, que es el valor predeterminado, la compresión del lado del servidor no se aplicará al WAL. Para comprimir el WAL, use la compresión del lado del cliente o especifique -Xfetch.

El método de compresión se puede establecer en gzip, lz4, zstd, none para ninguna compresión o un entero (ninguna compresión si es 0, gzip si es mayor que 0). Opcionalmente, se puede especificar una cadena de detalle de compresión. Si la cadena de detalle es un entero, especifica el nivel de compresión. De lo contrario, debe ser una lista separada por comas de elementos, cada uno de la forma palabra clave o palabra clave=valor. Actualmente, las palabras clave admitidas son level, long y workers. La cadena de detalle no se puede utilizar cuando el método de compresión se especifica como un entero simple.

Si no se especifica ningún nivel de compresión, se utilizará el nivel de compresión predeterminado. Si solo se especifica un nivel sin mencionar un algoritmo, se utilizará la compresión gzip si el nivel es mayor que 0 y no se utilizará compresión si el nivel es 0.

Cuando se utiliza el formato tar con gzip, lz4 o zstd, el sufijo .gz, .lz4 o .zst, respectivamente, se agregará automáticamente a todos los nombres de archivo tar. Cuando se utiliza el formato plano, la compresión del lado del cliente no se puede especificar, pero aún es posible solicitar la compresión del lado del servidor. Si esto se hace, el servidor comprimirá la copia de seguridad para su transmisión, y el cliente la descomprimirá y extraerá.

Cuando esta opción se utiliza en combinación con -Xstream, pg_wal.tar se comprimirá usando gzip si se selecciona la compresión gzip del lado del cliente, pero no se comprimirá si se selecciona cualquier otro algoritmo de compresión o si se selecciona la compresión del lado del servidor.

Las siguientes opciones de línea de comandos controlan la generación de la copia de seguridad y la invocación del programa:

-c {fast|spread}
--checkpoint={fast|spread}

Establece el modo de punto de control en rápido (inmediato) o distribuido (predeterminado) (ver Sección 25.3.4).

-C
--create-slot

Especifica que la ranura de replicación nombrada por la opción --slot debe crearse antes de iniciar la copia de seguridad. Se genera un error si la ranura ya existe.

-l etiqueta
--label=etiqueta

Establece la etiqueta para la copia de seguridad. Si no se especifica ninguna, se utilizará el valor predeterminado "pg_basebackup base backup".

-n
--no-clean

Por defecto, cuando pg_basebackup se interrumpe con un error, elimina cualquier directorio que haya podido crear antes de descubrir que no puede completar el trabajo (por ejemplo, el directorio de destino y el directorio de write-ahead log). Esta opción inhibe la limpieza y, por lo tanto, es útil para la depuración.

Tenga en cuenta que los directorios de tablespace tampoco se limpian de ninguna manera.

-N
--no-sync

Por defecto, pg_basebackup esperará a que todos los archivos se escriban de forma segura en el disco. Esta opción hace que pg_basebackup regrese sin esperar, lo que es más rápido, pero significa que una posterior caída del sistema operativo puede dejar la copia de seguridad base corrupta. En general, esta opción es útil para pruebas, pero no debe utilizarse al crear una instalación de producción.

-P
--progress

Habilita la presentación de informes de progreso. Activar esto proporcionará un informe de progreso aproximado durante la copia de seguridad. Dado que la base de datos puede cambiar durante la copia de seguridad, esto es solo una aproximación y puede que no termine exactamente en el 100%. En particular, cuando el registro WAL se incluye en la copia de seguridad, la cantidad total de datos no se puede estimar con anticipación, y en este caso, el tamaño objetivo estimado aumentará una vez que supere la estimación total sin WAL.

-r tasa
--max-rate=tasa

Establece la tasa de transferencia máxima a la que se recopilan los datos del servidor de origen. Esto puede ser útil para limitar el impacto de pg_basebackup en el servidor. Los valores están en kilobytes por segundo. Utilice un sufijo M para indicar megabytes por segundo. También se acepta un sufijo k, que no tiene ningún efecto. Los valores válidos están entre 32 kilobytes por segundo y 1024 megabytes por segundo.

Esta opción siempre afecta la transferencia del directorio de datos. La transferencia de archivos WAL solo se ve afectada si el método de recopilación es fetch.

-S slotname
--slot=slotname

Esta opción solo se puede usar junto con -X stream. Hace que la transmisión WAL utilice la ranura de replicación especificada. Si la copia de seguridad base está destinada a ser utilizada como un standby de replicación en streaming utilizando una ranura de replicación, el standby debe usar el mismo nombre de ranura de replicación que primary_slot_name. Esto asegura que el servidor primario no elimine ningún dato WAL necesario durante el tiempo transcurrido entre el final de la copia de seguridad base y el inicio de la replicación en streaming en el nuevo standby.

La ranura de replicación especificada debe existir a menos que también se utilice la opción -C.

Si esta opción no se especifica y el servidor admite ranuras de replicación temporales (versión 10 y posteriores), entonces se utiliza automáticamente una ranura de replicación temporal para la transmisión WAL.

--sync-method=método

Cuando se establece en fsync, que es el valor predeterminado, pg_basebackup abrirá y sincronizará recursivamente todos los archivos en el directorio de copia de seguridad. Cuando se utiliza el formato plano, la búsqueda de archivos seguirá los enlaces simbólicos para el directorio WAL y cada tablespace configurado.

En Linux, syncfs puede usarse en su lugar para pedir al sistema operativo que sincronice todo el sistema de archivos que contiene el directorio de copia de seguridad. Cuando se utiliza el formato plano, pg_basebackup también sincronizará los sistemas de archivos que contienen los archivos WAL y cada tablespace. Consulte recovery_init_sync_method para obtener información sobre las advertencias a tener en cuenta al usar syncfs.

Esta opción no tiene ningún efecto cuando se utiliza --no-sync.

-v
--verbose

Habilita el modo detallado. Mostrará algunos pasos adicionales durante el inicio y el cierre, además de mostrar el nombre exacto del archivo que se está procesando actualmente si el informe de progreso también está habilitado.

--manifest-checksums=algoritmo

Especifica el algoritmo de suma de verificación que se aplicará a cada archivo incluido en el manifiesto de copia de seguridad. Actualmente, los algoritmos disponibles son NONE, CRC32C, SHA224, SHA256, SHA384 y SHA512. El valor predeterminado es CRC32C.

Si se selecciona NONE, el manifiesto de copia de seguridad no contendrá ninguna suma de verificación. De lo contrario, contendrá una suma de verificación de cada archivo en la copia de seguridad utilizando el algoritmo especificado. Además, el manifiesto siempre contendrá una suma de verificación SHA256 de su propio contenido. Los algoritmos SHA son significativamente más intensivos en CPU que CRC32C, por lo que seleccionar uno de ellos puede aumentar el tiempo necesario para completar la copia de seguridad.

El uso de una función hash SHA proporciona un resumen criptográficamente seguro de cada archivo para los usuarios que deseen verificar que la copia de seguridad no ha sido manipulada, mientras que el algoritmo CRC-32C proporciona una suma de verificación que se calcula mucho más rápido; es bueno para detectar errores debido a cambios accidentales, pero no es resistente a modificaciones maliciosas. Tenga en cuenta que, para ser útil contra un adversario que tenga acceso a la copia de seguridad, el manifiesto de copia de seguridad tendría que almacenarse de forma segura en otro lugar o verificarse de otra manera para que no se haya modificado desde que se tomó la copia de seguridad.

pg_verifybackup(1) se puede usar para verificar la integridad de una copia de seguridad contra el manifiesto de copia de seguridad.

--manifest-force-encode

Fuerza que todos los nombres de archivo en el manifiesto de copia de seguridad se codifiquen en hexadecimal. Si esta opción no se especifica, solo los nombres de archivo que no son UTF8 se codifican en hexadecimal. Esta opción está destinada principalmente a probar que las herramientas que leen un archivo de manifiesto de copia de seguridad funcionen correctamente.
handle this case.

--no-estimate-size

Evita que el servidor estime la cantidad total de datos de copia de seguridad que se transmitirán, lo que resulta en que la columna backup_total en la vista pg_stat_progress_basebackup sea siempre NULL.

Sin esta opción, la copia de seguridad comenzará enumerando el tamaño de toda la base de datos y luego volverá a enviar el contenido real. Esto puede hacer que la copia de seguridad tarde un poco más, y en particular, tardará más antes de que se envíe el primer dato. Esta opción es útil para evitar dicho tiempo de estimación si es demasiado largo.

Esta opción no está permitida cuando se usa --progress.

--no-manifest

Deshabilita la generación de un manifiesto de copia de seguridad. Si esta opción no se especifica, el servidor generará y enviará un manifiesto de copia de seguridad que se puede verificar usando pg_verifybackup(1). El manifiesto es una lista de todos los archivos presentes en la copia de seguridad, con la excepción de cualquier archivo WAL que pueda incluirse. También almacena el tamaño, la hora de la última modificación y una suma de verificación opcional para cada archivo.

--no-slot

Evita la creación de una ranura de replicación temporal para la copia de seguridad.

Por defecto, si se selecciona la transmisión de registros pero no se proporciona un nombre de ranura con la opción -S, se crea una ranura de replicación temporal (si es compatible con el servidor de origen).

El propósito principal de esta opción es permitir tomar una copia de seguridad base cuando el servidor no tiene ranuras de replicación libres. Usar una ranura de replicación es casi siempre preferible, ya que evita que el WAL necesario sea eliminado por el servidor durante la copia de seguridad.

--no-verify-checksums

Deshabilita la verificación de sumas de verificación, si están habilitadas en el servidor del que se toma la copia de seguridad base.

Por defecto, se verifican las sumas de verificación y las fallas de suma de verificación resultarán en un estado de salida distinto de cero. Sin embargo, la copia de seguridad base no se eliminará en tal caso, como si se hubiera utilizado la opción --no-clean. Las fallas de verificación de suma de verificación también se informarán en la vista pg_stat_database.

Las siguientes opciones de línea de comandos controlan la conexión al servidor de origen:

-d connstr
--dbname=connstr

Especifica los parámetros utilizados para conectarse al servidor, como una cadena de conexión; estos anularán cualquier opción de línea de comandos conflictiva.

Esta opción se llama --dbname por consistencia con otras aplicaciones cliente, pero debido a que pg_basebackup no se conecta a ninguna base de datos en particular del clúster, cualquier nombre de base de datos incluido en la cadena de conexión será ignorado por el servidor. Sin embargo, un nombre de base de datos proporcionado de esa manera anula el nombre de base de datos predeterminado (replication) a efectos de buscar la contraseña de la conexión de replicación en ~/.pgpass. De manera similar, middleware o proxies utilizados para conectarse a PostgreSQL podrían utilizar el nombre para fines como el enrutamiento de conexiones. El nombre de la base de datos también puede ser utilizado por la sincronización de ranuras de replicación lógica.

-h host
--host=host

Especifica el nombre del host de la máquina en la que se ejecuta el servidor. Si el valor comienza con una barra, se utiliza como directorio para un socket de dominio Unix. El valor predeterminado se toma de la variable de entorno PGHOST, si está configurada, de lo contrario, se intenta una conexión de socket de dominio Unix.

-p port
--port=port

Especifica el puerto TCP o la extensión del archivo de socket de dominio Unix local en el que el servidor está escuchando conexiones. El valor predeterminado es la variable de entorno PGPORT, si está configurada, o un valor predeterminado compilado.

-s interval
--status-interval=interval

Especifica el número de segundos entre paquetes de estado enviados de vuelta al servidor de origen. Valores más pequeños permiten un monitoreo más preciso del progreso de la copia de seguridad desde el servidor. Un valor de cero deshabilita las actualizaciones de estado periódicas por completo, aunque se enviará una actualización cuando sea solicitada por el servidor, para evitar desconexiones basadas en tiempo de espera. El valor predeterminado es 10 segundos.

-U username
--username=username

Especifica el nombre de usuario con el que conectarse.

-w
--no-password

Evita solicitar una contraseña. Si el servidor requiere autenticación de contraseña y no hay una contraseña disponible por otros medios, como un archivo .pgpass, el intento de conexión fallará. Esta opción puede ser útil en trabajos por lotes y scripts donde no hay ningún usuario presente para ingresar una contraseña.

-W
--password

Obliga a pg_basebackup a solicitar una contraseña antes de conectarse al servidor de origen.

Esta opción nunca es esencial, ya que pg_basebackup solicitará automáticamente una contraseña si el servidor exige autenticación de contraseña. Sin embargo, pg_basebackup desperdiciará un intento de conexión al descubrir que el servidor quiere una contraseña. En algunos casos, vale la pena escribir -W para evitar el intento de conexión adicional.

También hay otras opciones disponibles:

-V
--version

Imprime la versión de pg_basebackup y sale.

-?
--help

Muestra ayuda sobre los argumentos de la línea de comandos de pg_basebackup y sale.

ENTORNO

Esta utilidad, como la mayoría de las otras utilidades de PostgreSQL, utiliza las variables de entorno compatibles con libpq (ver Sección 32.15).

La variable de entorno PG_COLOR especifica si se debe usar color en los mensajes de diagnóstico. Los valores posibles son always, auto y never.

NOTAS

Al principio de la copia de seguridad, se necesita realizar un punto de control en el servidor de origen. Esto puede llevar algún tiempo (especialmente si no se usa la opción --checkpoint=fast), durante el cual pg_basebackup parecerá inactivo.

La copia de seguridad incluirá todos los archivos en el directorio de datos y las tablespaces, incluidos los archivos de configuración y cualquier archivo adicional colocado en el directorio por terceros, excepto ciertos archivos temporales administrados por PostgreSQL y archivos del sistema operativo. Pero solo se copian archivos y directorios regulares, excepto que se conservan los enlaces simbólicos utilizados para las tablespaces. Los enlaces simbólicos que apuntan a ciertos directorios conocidos por PostgreSQL se copian como directorios vacíos. Otros enlaces simbólicos y archivos de dispositivos especiales se omiten. Ver Sección 54.4 para los detalles precisos.

En formato plano, las tablespaces se copiarán a la misma ruta que tienen en el servidor de origen, a menos que se utilice la opción --tablespace-mapping. Sin esta opción, ejecutar una copia de seguridad base en formato plano en el mismo host que el servidor no funcionará si se usan tablespaces, ya que la copia de seguridad tendría que escribirse en las mismas ubicaciones de directorio que las tablespaces originales.

Cuando se utiliza el formato tar, es responsabilidad del usuario descomprimir cada archivo tar antes de iniciar un servidor PostgreSQL que utilice los datos. Si hay tablespaces adicionales, los archivos tar para ellos deben descomprimirse en las ubicaciones correctas. En este caso, los enlaces simbólicos para esas tablespaces serán creados por el servidor de acuerdo con el contenido del archivo tablespace_map que se incluye en el archivo base.tar.

pg_basebackup funciona con servidores de la misma versión o de versiones anteriores, hasta la 9.1. Sin embargo, el modo de transmisión de WAL (-X stream) solo funciona con servidores de la versión 9.3 y posteriores, el formato tar (--format=tar) solo funciona con servidores de la versión 9.5 y posteriores, y la copia de seguridad incremental (--incremental) solo funciona con servidores de la versión 17 y posteriores.

pg_basebackup preservará los permisos de grupo para los archivos de datos si los permisos de grupo están habilitados en el clúster de origen.

EJEMPLOS

Para crear una copia de seguridad base del servidor en mydbserver y almacenarla en el directorio local /usr/local/pgsql/data:

$ pg_basebackup -h mydbserver -D /usr/local/pgsql/data

Para crear una copia de seguridad del servidor local con un archivo tar comprimido para cada tablespace, y almacenarla en el directorio backup, mostrando un informe de progreso mientras se ejecuta:

$ pg_basebackup -D backup -Ft -z -P

Para crear una copia de seguridad de una base de datos local con una sola tablespace y comprimirla con bzip2:

$ pg_basebackup -D - -Ft -X fetch | bzip2 > backup.tar.bz2

(Este comando fallará si hay varias tablespaces en la base de datos).

Para crear una copia de seguridad de una base de datos local donde la tablespace en /opt/ts se reubica a ./backup/ts:

$ pg_basebackup -D backup/data -T /opt/ts=$(pwd)/backup/ts

Para crear una copia de seguridad del servidor local con un archivo tar para cada tablespace comprimido con gzip en el nivel 9, almacenado en el directorio backup:

$ pg_basebackup -D backup -Ft --compress=gzip:9

    NOMBRE

    pg_basebackup — utilidad de copia de seguridad de la base de datos PostgreSQL

    SINOPSIS

    pg_basebackup [OPTION]...

    DESCRIPCIÓN

    pg_basebackup es una utilidad para crear una copia de seguridad base (física) de un clúster de base de datos PostgreSQL. Una copia de seguridad base es una copia de todo el directorio de datos del clúster, junto con un segmento de WAL (Write-Ahead Logging) que cubre el período de tiempo durante el cual se realizó la copia de seguridad. Se puede utilizar para crear un nuevo servidor de réplica o como punto de partida para una recuperación incremental.

    La copia de seguridad se transfiere a través de una conexión SSL a un servidor PostgreSQL en ejecución. El servidor puede estar en el modo de servidor principal o de réplica. Se pueden especificar varios parámetros de conexión para conectarse al servidor.

    La copia de seguridad se puede realizar en formato tar o como un archivo de datos sin formato. El archivo tar se puede comprimir con gzip, bzip2 o xz. El archivo de datos sin formato se puede comprimir con gzip. Los archivos resultantes se pueden escribir en la salida estándar o en un directorio especificado.

    OPCIONES

    -D, --directory=DIRECTORY
    Escribe la copia de seguridad en el directorio especificado. Si el directorio no existe, se creará. Si ya existe y está vacío, se utilizará. De lo contrario, se producirá un error.
    -F, --format=FORMAT
    Especifica el formato de la copia de seguridad. t (tar) o p (plain, sin formato). El valor predeterminado es p.
    -z, --gzip
    Comprime la copia de seguridad con gzip. Solo se puede utilizar con el formato t.
    -Z, --compress=COMPRESS
    Comprime la copia de seguridad con la utilidad especificada. Solo se puede utilizar con el formato t.
    -j, --jobs=NUMBER
    Especifica el número de conexiones paralelas que se utilizarán para transferir los datos. Los valores mayores que 1 solo son compatibles con el formato p.
    -l, --label=LABEL
    Especifica una etiqueta para la copia de seguridad. Esto es útil para identificar la copia de seguridad más tarde.
    -v, --verbose
    Habilita la salida detallada. Muestra el progreso de la copia de seguridad y otra información útil.
    -V, --version
    Imprime la versión de pg_basebackup y sal.
    -?, --help
    Muestra la ayuda y sal.

    EJEMPLOS

    Crear una copia de seguridad base del clúster de base de datos en el directorio /var/lib/pgsql/backups/mydb:

    pg_basebackup -D /var/lib/pgsql/backups/mydb

    Crear una copia de seguridad base comprimida con gzip en formato tar en el directorio /var/lib/pgsql/backups/mydb:

    pg_basebackup -D /var/lib/pgsql/backups/mydb -F t -z

    Crear una copia de seguridad base con 4 trabajos paralelos en formato sin formato en el directorio /var/lib/pgsql/backups/mydb:

    pg_basebackup -D /var/lib/pgsql/backups/mydb -j 4
