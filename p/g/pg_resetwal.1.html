PG_RESETWAL(1) Documentación de PostgreSQL 18.1 PG_RESETWAL(1)

NOMBRE

pg_resetwal - reinicia el log de escritura anticipada (WAL) y otra información de control de un clúster de bases de datos de PostgreSQL

SINOPSIS

pg_resetwal [-f | --force] [-n | --dry-run] [opción...] [-D | --pgdata]datadir

DESCRIPCIÓN

pg_resetwal borra el log de escritura anticipada (WAL) y opcionalmente reinicia otra información de control almacenada en el archivo pg_control. Esta función a veces es necesaria si estos archivos se han corrompido. Solo debe usarse como último recurso, cuando el servidor no arranca debido a dicha corrupción.

Algunas opciones, como --wal-segsize (ver más abajo), también se pueden utilizar para modificar ciertas configuraciones globales de un clúster de bases de datos sin necesidad de volver a ejecutar initdb. Esto se puede hacer de forma segura en un clúster de bases de datos que de otro modo sería correcto, si no se utilizan los modos peligrosos mencionados a continuación.

Si pg_resetwal se utiliza en un directorio de datos donde el servidor se ha apagado limpiamente y el archivo de control está intacto, no tendrá ningún efecto sobre el contenido del sistema de bases de datos, excepto que se limpiarán los archivos WAL que ya no se utilizan. Cualquier otro uso es potencialmente peligroso y debe hacerse con mucho cuidado. pg_resetwal requerirá que se especifique la opción -f (force) antes de trabajar en un directorio de datos en un estado de apagado incompleto o con un archivo de control corrupto.

Después de ejecutar este comando en un directorio de datos con WAL corrupto o un archivo de control corrupto, debería ser posible iniciar el servidor, pero tenga en cuenta que la base de datos podría contener datos inconsistentes debido a transacciones parcialmente confirmadas. Debe volcar sus datos inmediatamente, ejecutar initdb y restaurar. Después de la restauración, compruebe si hay inconsistencias y repárelas según sea necesario.

Si pg_resetwal se queja de que no puede determinar datos válidos para pg_control, puede forzarlo a proceder de todos modos especificando la opción -f (force). En este caso, se sustituirán valores plausibles para los datos faltantes. La mayoría de los campos se espera que coincidan, pero puede ser necesaria asistencia manual para los campos de OID siguiente, ID de transacción y época siguiente, ID de multitransacción y desplazamiento siguiente, y ubicación de inicio de WAL. Estos campos se pueden establecer utilizando las opciones que se comentan a continuación. Si no puede determinar los valores correctos para todos estos campos, todavía se puede usar -f, pero la base de datos recuperada debe tratarse con aún más sospecha de lo habitual: un volcado y restauración inmediatos son imperativos. *No* ejecute ninguna operación que modifique datos en la base de datos antes de volcar, ya que cualquier acción de este tipo probablemente empeorará la corrupción.

Esta utilidad solo puede ser ejecutada por el usuario que instaló el servidor, ya que requiere acceso de lectura/escritura al directorio de datos.

OPCIONES

datadir
-D datadir
--pgdata=datadir

Especifica la ubicación del directorio de bases de datos. Por motivos de seguridad, debe especificar el directorio de datos en la línea de comandos. pg_resetwal no utiliza la variable de entorno PGDATA.

-f
--force

Forza a pg_resetwal a continuar incluso en situaciones en las que podría ser peligroso, como se explica anteriormente. Específicamente, esta opción es necesaria para continuar si el servidor no se apagó limpiamente o si pg_resetwal no puede determinar datos válidos para pg_control.

-n
--dry-run

La opción -n/--dry-run indica a pg_resetwal que imprima los valores reconstruidos de pg_control y los valores que están a punto de ser modificados, y luego salga sin modificar nada. Esto es principalmente una herramienta de depuración, pero puede ser útil como una verificación de cordura antes de permitir que pg_resetwal continúe realmente.

-V
--version

Muestra información de la versión y luego sale.

-?
--help

Muestra la ayuda y luego sale.

Las siguientes opciones solo son necesarias cuando pg_resetwal no puede determinar valores apropiados leyendo pg_control. Se pueden determinar valores seguros como se describe a continuación. Para valores que toman argumentos numéricos, se pueden especificar valores hexadecimales usando el prefijo 0x. Tenga en cuenta que estas instrucciones solo se aplican con el tamaño de bloque predeterminado de 8 kB.

-c xid,xid
--commit-timestamp-ids=xid,xid

Establece manualmente los ID de transacción más antiguos y más recientes para los cuales se puede recuperar la marca de tiempo de confirmación.

Se puede determinar un valor seguro para el ID de transacción más antiguo para el cual se puede recuperar la marca de tiempo de confirmación (primera parte) buscando el nombre de archivo numéricamente más pequeño en el directorio pg_commit_ts dentro del directorio de datos. Por el contrario, se puede determinar un valor seguro para el ID de transacción más reciente para el cual se puede recuperar la marca de tiempo de confirmación (segunda parte) buscando el nombre de archivo numéricamente mayor en el mismo directorio. Los nombres de archivo están en hexadecimal.

-e xid_epoch
--epoch=xid_epoch

Establece manualmente la época del siguiente ID de transacción.

La época del ID de transacción no se almacena realmente en ningún lugar de la base de datos, excepto en el campo que se establece mediante pg_resetwal, por lo que cualquier valor funcionará en lo que respecta a la base de datos. Es posible que deba ajustar este valor para garantizar que los sistemas de replicación como Slony-I y Skytools funcionen correctamente; si es así, se debería poder obtener un valor apropiado del estado de la base de datos replicada aguas abajo.

-l walfile
--next-wal-file=walfile

Establece manualmente la ubicación de inicio de WAL especificando el nombre del siguiente archivo de segmento WAL.

El nombre del siguiente archivo de segmento WAL debe ser mayor que cualquier nombre de archivo de segmento WAL existente actualmente en el directorio pg_wal dentro del directorio de datos. Estos nombres también están en hexadecimal y tienen tres partes. La primera parte es la "ID de línea de tiempo" y generalmente debe mantenerse igual. Por ejemplo, si 00000001000000320000004A es la entrada más grande en pg_wal, use -l 00000001000000320000004B o superior.

Tenga en cuenta que al utilizar tamaños de segmento WAL no predeterminados, los números en los nombres de los archivos WAL son diferentes de los LSN que informan las funciones del sistema y las vistas del sistema. Esta opción toma un nombre de archivo WAL, no un LSN.


Nota
pg_resetwal en sí mismo mira los archivos en pg_wal y elige una configuración predeterminada para -l más allá del último nombre de archivo existente. Por lo tanto, el ajuste manual de -l solo debería ser necesario si usted es consciente de los archivos de segmento WAL que no están presentes actualmente en pg_wal, como las entradas en un archivo fuera de línea; o si el contenido de pg_wal se ha perdido por completo.

-m mxid,mxid
--multixact-ids=mxid,mxid

Establece manualmente el ID de multitransacción siguiente y más antiguo.

Se puede determinar un valor seguro para el ID de multitransacción siguiente (primera parte) buscando el nombre de archivo numéricamente mayor en el directorio pg_multixact/offsets dentro del directorio de datos, sumando uno y luego multiplicando por 65536 (0x10000). Por el contrario, se puede determinar un valor seguro para el ID de multitransacción más antiguo (segunda parte de -m) buscando el nombre de archivo numéricamente más pequeño en el mismo directorio y multiplicando por 65536. Los nombres de archivo están en hexadecimal, por lo que la forma más fácil de hacerlo es especificar el valor de la opción en hexadecimal y agregar cuatro ceros.

-o oid
--next-oid=oid

Establece manualmente el siguiente OID.

No hay una forma comparativamente fácil de determinar un siguiente OID que esté más allá del más grande en la base de datos, pero afortunadamente no es crítico acertar la configuración del siguiente OID.

-O mxoff
--multixact-offset=mxoff

Establece manualmente el desplazamiento de multitransacción siguiente.

Se puede determinar un valor seguro buscando el nombre de archivo numéricamente mayor en el directorio pg_multixact/members dentro del directorio de datos, sumando uno y luego multiplicando por 52352 (0xCC80). Los nombres de archivo están en hexadecimal. No hay una receta simple como las de otras opciones de agregar ceros.

-u xid
--oldest-transaction-id=xid

Establece manualmente el ID de transacción no congelado más antiguo.

Un valor seguro para el ID de transacción no congelado más antiguo se puede determinar mirando el nombre de archivo numéricamente más pequeño en el directorio pg_xact dentro del directorio de datos. El nombre de archivo está en hexadecimal.

-w
--swap-wal-files

Intercambia los archivos WAL existentes con nuevos archivos WAL. Esto es útil si los archivos WAL existentes están corruptos y necesita reemplazarlos con nuevos archivos WAL.

-X command
--exec-command=command

Ejecuta command después de que la recuperación se haya completado. El comando se ejecuta en el directorio de datos. Esto se puede utilizar para realizar una copia de seguridad automática después de la recuperación.

NOTAS

Esta utilidad solo puede ser ejecutada por el usuario que instaló el servidor.

Si el servidor no se puede iniciar debido a corrupción en los archivos WAL, puede usar esta utilidad para limpiar el WAL y poner la base de datos en un estado consistente. Sin embargo, los datos podrían estar en un estado inconsistente, por lo que se recomienda encarecidamente hacer una copia de seguridad de sus datos inmediatamente después de ejecutar esta utilidad y luego restaurar a partir de la copia de seguridad.

EJEMPLOS

Para borrar el WAL y reiniciar la base de datos en un directorio de datos dado:

pg_resetwal -f /var/lib/pgsql/data

Para hacer una simulación antes de borrar el WAL:

pg_resetwal -n /var/lib/pgsql/data

Establece manualmente el próximo ID de transacción.

Un valor seguro se puede determinar buscando el nombre de archivo numéricamente más grande en el directorio pg_xact bajo el directorio de datos, sumando uno y luego multiplicando por 1048576 (0x100000). --char-signedness=option

Establece manualmente la representacion por defecto de char. Los valores posibles son signed y unsigned.

Para un clúster de base de datos que pg_upgrade actualizó desde una versión de PostgreSQL anterior a la 18, el valor seguro sería la representacion por defecto de char de la plataforma que ejecutó el clúster antes de esa actualización. Para todos los demás clústeres, signed sería el valor seguro. Sin embargo, esta opción es exclusivamente para uso con pg_upgrade y normalmente no debe usarse manualmente.

--wal-segsize=wal_segment_size

Establece el nuevo tamaño del segmento WAL, en megabytes. El valor debe ser una potencia de 2 entre 1 y 1024 (megabytes). Consulte la misma opción de initdb(1) para obtener más información.

Esta opción también se puede utilizar para cambiar el tamaño del segmento WAL de un clúster de base de datos existente, evitando la necesidad de volver a ejecutar initdb.


Nota
Mientras que pg_resetwal establecerá la dirección de inicio de WAL más allá del último archivo de segmento WAL existente, algunos cambios en el tamaño del segmento pueden hacer que se reutilicen los nombres de archivos WAL anteriores. Se recomienda utilizar -l junto con esta opción para establecer manualmente la dirección de inicio de WAL si la superposición de nombres de archivos WAL causa problemas con su estrategia de archivo.

ENTORNO

PG_COLOR

Especifica si se debe usar color en los mensajes de diagnóstico. Los valores posibles son always, auto y never.

NOTAS

Este comando no debe usarse cuando el servidor está en ejecución. pg_resetwal se negará a iniciarse si encuentra un archivo de bloqueo del servidor en el directorio de datos. Si el servidor falló, es posible que haya quedado un archivo de bloqueo; en ese caso, puede eliminar el archivo de bloqueo para permitir que se ejecute pg_resetwal. Pero antes de hacerlo, asegúrese de que no haya ningún proceso de servidor aún activo.

pg_resetwal solo funciona con servidores de la misma versión principal.
