NOMBRE

pt-replica-restart - Vigila y reinicia la replicación de MySQL tras errores.

SINOPSIS

Uso: pt-replica-restart [OPCIONES] [DSN]

pt-replica-restart vigila una o más réplicas de replicación de MySQL en busca de errores e intenta reiniciar la replicación si se detiene.

RIESGOS

Percona Toolkit es maduro, probado en el mundo real y bien testeado, pero todas las herramientas de base de datos pueden suponer un riesgo para el sistema y el servidor de base de datos. Antes de usar esta herramienta, por favor:

  • Lea la documentación de la herramienta
  • Revise los "BUGS" conocidos de la herramienta
  • Pruebe la herramienta en un servidor no productivo
  • Haga una copia de seguridad de su servidor de producción y verifique las copias de seguridad

DESCRIPCIÓN

pt-replica-restart vigila una o más réplicas de replicación de MySQL e intenta omitir sentencias que causan errores. Sondea las réplicas inteligentemente con un tiempo de espera exponencialmente variable. Puede especificar errores a omitir y ejecutar las réplicas hasta una posición de binlog determinada.

Aunque esta herramienta puede ayudar a una réplica a superar errores, no debe depender de ella para "solucionar" la replicación. Si los errores de réplica ocurren con frecuencia o inesperadamente, debe identificar y corregir la causa raíz.

SALIDA

pt-replica-restart imprime una línea cada vez que detecta que la réplica tiene un error. Por defecto, esta línea es: una marca de tiempo, información de conexión, relay_log_file, relay_log_pos y last_errno. Puede añadir más información usando la opción "--verbose". Puede suprimir toda la salida usando la opción "--quiet".

ESPERA

pt-replica-restart espera inteligentemente entre sondeos de la réplica. El tiempo de espera actual varía.

  • El tiempo de espera inicial viene dado por "--sleep".
  • Si comprueba y encuentra un error, reduce a la mitad el tiempo de espera anterior.
  • Si no encuentra ningún error, duplica el tiempo de espera anterior.
  • El tiempo de espera está acotado inferiormente por "--min-sleep" y superiormente por "--max-sleep".
  • Inmediatamente después de encontrar un error, pt-replica-restart asume que es muy probable que ocurra otro error a continuación, por lo que espera el tiempo de espera actual o el tiempo de espera inicial, el que sea menor.

IDS DE TRANSACCIÓN GLOBALES

A partir de Percona Toolkit 2.2.8, pt-replica-restart admite IDs de Transacción Globales introducidos en MySQL 5.6.5. Es importante tener en cuenta que:

  • pt-replica-restart no omitirá transacciones cuando se estén utilizando múltiples hilos de replicación (replica_parallel_workers > 0). pt-replica-restart no conoce el evento GTID de la transacción fallida de un hilo de réplica específico.
  • El comportamiento predeterminado es omitir la siguiente transacción de la fuente de la réplica. Las escrituras pueden originarse en diferentes servidores, cada uno con su propio UUID.

    Vea "--source-uuid".

ESTADO DE SALIDA

Un estado de salida de 0 (a veces también llamado valor de retorno o código de retorno) indica éxito. Cualquier otro valor representa el estado de salida del propio proceso de Perl, o del último proceso bifurcado que salió si había varios servidores que monitorizar.

COMPATIBILIDAD

pt-replica-restart debería funcionar en muchas versiones de MySQL. La capitalización de muchas columnas de salida de SHOW REPLICA STATUS ha cambiado con el tiempo, por lo que las trata todas como minúsculas.

If "--monitor" isn't specified, "pt-replica-restart" will exit after creating the file. If it is specified, "pt-replica-restart" will wait the interval given by "--max-sleep", then remove the file and continue working.

You might find this handy to stop cron jobs gracefully if necessary, or to replace one running instance with another. For example, if you want to stop and restart "pt-replica-restart" every hour (just to make sure that it is restarted every hour, in case of a server crash or some other problem), you could use a "crontab" line like this:

The non-default "--sentinel" will make sure the hourly "cron" job stops only instances previously started with the same options (that is, from the same "cron" job).

NAME

pt-slave-restart

restart stalled replication slaves

SYNOPSIS

pt-slave-restart [OPTIONS] [--pid=FILE] [--interval=N] [--down-master-message=MSG]

RISKS

This tool is potentially dangerous. It is designed to restart replication slaves. If replication is stalled for a reason other than a master failure, this tool might inadvertently perpetuate the problem.

Always test this tool on a staging system before using it in production.

DESCRIPTION

This tool monitors replication slaves and restarts them when replication has stalled. It is designed to be run from cron, so it is idempotent and can be run repeatedly without ill effect.

The tool can restart replication in two ways:

  • If the master is running, it restarts the slave by executing CHANGE MASTER TO and START SLAVE. The tool is careful to detect the correct values to use for CHANGE MASTER TO, so you don't have to specify them.

  • If the master is not running, the tool waits for the master to become available. When the master becomes available, it restarts the slave.

By default, the tool detects and restarts stalled slaves, but it won't restart a slave if the master is down. If the master is down, it prints a message and exits. This behavior is configurable with the --down-master-message option.

The tool assumes that you are monitoring replication from the slave's perspective. It checks the output of SHOW SLAVE STATUS for errors and stalled replication. It also checks the master's status to ensure that it is running.

The tool is written in Perl and uses the DBI module to connect to MySQL.

OUTPUT

The tool prints status messages to STDOUT. These messages indicate whether replication is stalled, whether the master is down, and whether replication has been restarted. The tool also prints error messages to STDERR.

The tool's output is designed to be easily parsed by other tools or scripts. For example, you can use it to trigger alerts or notifications when replication stalls.

SLEEP

The tool sleeps for the interval specified by the --interval option between checks. The default is 60 seconds.

GLOBAL TRANSACTION IDS

If the master is using global transaction identifiers (GTIDs), the tool will detect this and use GTIDs to restart replication. If the master is not using GTIDs, the tool will use traditional binary log positions.

EXIT STATUS

The tool exits with a status of 0 if replication is running correctly. It exits with a status of 1 if replication is stalled and the tool was unable to restart it. It exits with a status of 2 if the master is down. It exits with a status of 3 if there was an error connecting to the database.

COMPATIBILITY

This tool is compatible with MySQL 5.1 and later.

OPTIONS

–config=file

Read this tool's options from a file and the given command-line options will override them. If the file is a MySQL-option file, the tool reads the [client] section and any options specific to the tool.

–defaults-file=file

Use only the given MySQL-option file. See the MySQL manual for syntax.

–defaults-group=group

Use only the given group from the MySQL-option file. The default is for the tool to read the [client] section and any options specific to the tool. See the MySQL manual for syntax.

--down-master-message=MSG

If the master is down, print the specified message to STDOUT and exit with status 2. The default is: "Master is down; replication is stopped"

–help

Show help and exit.

–interval=N

Sleep for N seconds between checks. The default is 60.

–log=file

Log the tool's actions to the specified file. The default is not to log.

–pid=file

Create a PID file with the specified name. The tool locks the PID file when it runs, and removes it when it exits. If the PID file exists and the process specified in it is running, the tool exits. This prevents multiple instances of the tool from running simultaneously.

–print-defaults

VERSION CHECK

The Percona Toolkit versions have a version-check feature that periodically checks for updates and known problems with the tool. By default, this check is performed once every 24 hours. The check is performed by connecting to a Percona-hosted database server and printing any relevant information to STDOUT.

You can disable this feature by adding the following line to your Percona Toolkit configuration file:

[tool-options]
version-check=0

The tool avoids reporting issues with old versions of software that have been superseded. For example, MySQL 5.5.25 had a critical bug and was re-released as 5.5.25a.

A secure connection to Percona’s Version Check database server is done to perform these checks. Each request is logged by the server, including software version numbers and unique ID of the checked system. The ID is generated by the Percona Toolkit installation script or when the Version Check database call is done for the first time.

Any updates or known problems are printed to STDOUT before the tool's normal output. This feature should never interfere with the normal operation of the tool.

For more information, visit https://www.percona.com/doc/percona-toolkit/LATEST/version-check.html.
