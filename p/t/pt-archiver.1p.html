NOMBRE

pt-archiver - Archiva filas de una tabla MySQL en otra tabla o en un archivo.

SINOPSIS

Uso: pt-archiver [OPCIONES] --source DSN --where WHERE

pt-archiver consume registros de una tabla MySQL. Los argumentos --source y --dest utilizan sintaxis DSN; si COPY es sí, --dest por defecto es el valor de la clave de --source.

Ejemplos:

Archivar todas las filas de oltp_server a olap_server y a un archivo:

pt-archiver --source h=oltp_server,D=test,t=tbl --dest h=olap_server \
  --file '/var/log/archive/%Y-%m-%d-%D.%t'                           \
  --where "1=1" --limit 1000 --commit-each

Purgar (eliminar) filas huérfanas de una tabla hija:

pt-archiver --source h=host,D=db,t=child --purge \
  --where 'NOT EXISTS(SELECT * FROM parent WHERE col=child.col)'

  • Lea la documentación de la herramienta
  • Revise los "BUGS" conocidos de la herramienta
  • Pruebe la herramienta en un servidor no productivo
  • Haga una copia de seguridad de su servidor de producción y verifique las copias de seguridad

DESCRIPCIÓN

pt-archiver es la herramienta para archivar tablas como se describe en https://web.archive.org/web/20071014031743/http://www.xaprb.com/blog/2006/05/02/how-to-write-efficient-archiving-and-purging-jobs-in-sql. El objetivo es un trabajo de bajo impacto, hacia adelante, para consumir datos antiguos de la tabla sin afectar mucho las consultas OLTP. Puede insertar los datos en otra tabla, que no tiene por qué estar en el mismo servidor. También puede escribirlos en un archivo en un formato adecuado para LOAD DATA INFILE. O puede no hacer ninguna de las dos cosas, en cuyo caso es solo un DELETE incremental.

pt-archiver es extensible a través de un mecanismo de plugins. Puede inyectar su propio código para agregar lógica de archivo avanzada que podría ser útil para archivar datos dependientes, aplicar reglas de negocio complejas o construir un almacén de datos durante el proceso de archivo.

Debe elegir cuidadosamente los valores para algunas opciones. Las más importantes son "--limit", "--retries" y "--txn-size".

La estrategia es encontrar las primeras filas, luego escanear un índice de avance para encontrar más filas de manera eficiente. Cada consulta subsiguiente no debe escanear toda la tabla; debe buscar en el índice, luego escanear hasta que encuentre más filas archivables. Especificar el índice con la parte 'i' del argumento "--source" puede ser crucial para esto; use "--dry-run" para examinar las consultas generadas y asegúrese de EXPLAIN para ver si son eficientes (la mayoría de las veces probablemente querrá escanear la clave PRIMARIA, que es la predeterminada). Mejor aún, examine la diferencia en los contadores de estado del Manejador antes y después de ejecutar la consulta, y asegúrese de que no esté escaneando toda la tabla en cada consulta.

Puede deshabilitar las optimizaciones de búsqueda-luego-escaneo parcial o totalmente con "--no-ascend" y "--ascend-first". A veces, esto puede ser más eficiente para claves multicolumna. Tenga en cuenta que pt-archiver está diseñado para comenzar al principio del índice que elige y escanearlo solo hacia adelante. Esto podría resultar en largos escaneos de tabla si está intentando consumir desde el final de la tabla por un índice que no sea el que prefiere. Vea "--source" y lea la documentación sobre la parte de "i" si esto se aplica a usted.

Percona XtraDB Cluster

pt-archiver funciona con Percona XtraDB Cluster (PXC) 5.5.28-23.7 y versiones posteriores, pero hay tres limitaciones que debe considerar antes de archivar en un clúster:

Error en el commit
pt-archiver no verifica si hay errores al confirmar transacciones. Los commits en PXC pueden fallar, pero la herramienta aún no verifica ni reintenta la transacción cuando esto sucede. Si sucede, la herramienta morirá.
Tablas MyISAM
Archivar tablas MyISAM funciona, pero el soporte de MyISAM en PXC todavía es experimental en el momento de esta versión. Hay varios errores conocidos con PXC, tablas MyISAM y columnas "AUTO_INCREMENT". Por lo tanto, debe asegurarse de que el archivo no resulte directa o indirectamente en el uso de valores predeterminados de "AUTO_INCREMENT" para una tabla MyISAM. Por ejemplo, esto sucede con "--dest" si se usa "--columns" y la columna "AUTO_INCREMENT" no está incluida. ¡La herramienta no verifica esto!
Opciones no de clúster
Ciertas opciones pueden o no funcionar. Por ejemplo, si un nodo de clúster no es también una réplica, entonces "--check-replica-lag" no funciona. Y dado que las tablas PXC suelen ser InnoDB, pero InnoDB no soporta "INSERT DELAYED", entonces "--delayed-insert" no funciona. Otras opciones también pueden no funcionar, pero la herramienta no las verifica, por lo tanto, debe probar el archivo en un clúster de prueba antes de archivar en su clúster real.

SALIDA

Si especifica "--progress", la salida es una fila de encabezado, más una salida de estado a intervalos. Cada fila en la salida de estado lista la fecha y hora actuales, cuántos segundos ha estado ejecutándose pt-archiver y cuántas filas ha archivado.

Si especifica "--statistics", "pt-archiver" genera información de tiempo y otra información para ayudarle a identificar qué parte de su proceso de archivo consume más tiempo.

MANEJO DE ERRORES

pt-archiver intenta capturar señales y salir limpiamente; por ejemplo, si le envía SIGTERM (Ctrl-C en sistemas tipo UNIX), capturará la señal, imprimirá un mensaje sobre la señal y saldrá de manera bastante normal. No ejecutará "--analyze" u "--optimize", ya que estos pueden tardar mucho en finalizar. Ejecutará todo el demás código de forma normal, incluida la llamada a after_finish() en cualquier plugin (ver "EXTENSIÓN").

En otras palabras, una señal, si se captura, saldrá del bucle principal de archivo y omitirá la optimización/análisis.

OPCIONES

Especifique al menos una de las opciones "--dest", "--file" o "--purge".

"--ignore" y "--replace" son mutuamente excluyentes.

"--txn-size" y "--commit-each" son mutuamente excluyentes.

"--low-priority-insert" y "--delayed-insert" son mutuamente excluyentes.

"--share-lock" y "--for-update" son mutuamente excluyentes.

"--analyze" y "--optimize" son mutuamente excluyentes.

"--no-ascend" y "--no-delete" son mutuamente excluyentes.

Los valores DSN en "--dest" por defecto son los valores de "--source" si COPY es sí.

--all

Archive all rows. This option is used to perform the archiving of all rows from the source table. It is equivalent to specifying a LIMIT clause that covers all rows in the table. This can be useful when you want to ensure that every row is considered for archiving, regardless of its current status or any other filtering criteria.

Note: Using this option might lead to significant performance implications, especially on large tables, as it requires processing every single row. Ensure that your system can handle the load before proceeding.

--analyze

Analyze the table after archiving.

After the archiving process is complete, this option triggers an `ANALYZE TABLE` command on the source table. This helps update table statistics, which can improve the performance of subsequent queries against the table. This is particularly useful if archiving removes a significant number of rows, as it can help the query optimizer make better decisions.

--archive

Archive rows to a different table.

This option designates the destination table where the archived rows will be stored. You must specify a DSN (Data Source Name) for the destination table using the --dest option. The --archive option implies --dest and sets the destination table to the one specified.

Example:

pt-archiver --source h=source_host,D=db1,t=table1 --archive h=dest_host,D=db2,t=archived_table1

This command archives rows from db1.table1 to db2.archived_table1.

--ascend-index

Archive rows in ascending order of the specified index.

By default, pt-archiver selects rows in the order they are found in the table. This can lead to inefficient disk I/O if the rows are scattered across the disk. Using --ascend-index allows you to specify an index (typically the primary key) by which the rows should be selected. This ensures that rows are processed in a more sequential order, improving disk performance.

When specifying --ascend-index, pt-archiver selects rows in chunks. For each chunk, it finds the minimum and maximum values of the index column(s) within that chunk. It then uses these values to select the next chunk of rows. This strategy provides a performance boost over not ascending the index at all, while avoiding the cost of ascending the whole index.

See "EXTENDING" for a discussion of how this interacts with plugins.

--ask-pass

Prompt for a password when connecting to MySQL.

If the connection to the MySQL server requires a password, this option will cause pt-archiver to prompt the user to enter the password interactively. This is a more secure way to handle passwords than hardcoding them in scripts or configuration files.

--buffer

Buffer output to "--file" and flush at commit.

Disables autoflushing to "--file" and flushes "--file" to disk only when a transaction commits. This typically means the file is block-flushed by the operating system, so there may be some implicit flushes to disk between commits as well. The default is to flush "--file" to disk after every row.

The danger is that a crash might cause lost data.

The performance increase I have seen from using "--buffer" is around 5 to 15 percent. Your mileage may vary.

--bulk-delete

Delete each chunk with a single statement (implies "--commit-each").

Delete each chunk of rows in bulk with a single "DELETE" statement. The statement deletes every row between the first and last row of the chunk, inclusive. It implies "--commit-each", since it would be a bad idea to "INSERT" rows one at a time and commit them before the bulk "DELETE".

The normal method is to delete every row by its primary key. Bulk deletes might be a lot faster. They also might not be faster if you have a complex "WHERE" clause.

This option completely defers all "DELETE" processing until the chunk of rows is finished. If you have a plugin on the source, its "before_delete" method will not be called. Instead, its "before_bulk_delete" method is called later.

WARNING: if you have a plugin on the source that sometimes doesn't return true from is_archivable(), you should use this option only if you understand what it does. If the plugin instructs "pt-archiver" not to archive a row, it will still be deleted by the bulk delete!

--[no]bulk-delete-limit

default: yes

Add "--limit" to "--bulk-delete" statement.

This is an advanced option and you should not disable it unless you know what you are doing and why! By default, "--bulk-delete" appends a "--limit" clause to the bulk delete SQL statement. In certain cases, this clause can be omitted by specifying "--no-bulk-delete-limit". "--limit" must still be specified.

--bulk-insert

Insert each chunk with LOAD DATA INFILE (implies "--bulk-delete" "--commit-each").

Insert each chunk of rows with "LOAD DATA LOCAL INFILE". This may be much faster than inserting a row at a time with "INSERT" statements. It is implemented by creating a temporary file for each chunk of rows, and writing the rows to this file instead of inserting them. When the chunk is finished, it uploads the rows.

To protect the safety of your data, this option forces bulk deletes to be used. It would be unsafe to delete each row as it is found, before inserting the rows into the destination first. Forcing bulk deletes guarantees that the deletion waits until the insertion is successful.

The "--low-priority-insert", "--replace", and "--ignore" options work with this option, but "--delayed-insert" does not.

If "LOAD DATA LOCAL INFILE" throws an error in the lines of "The used command is not allowed with this MySQL version", refer to the documentation for the "L" DSN option.

--channel

type: string

Channel name used when connected to a server using replication channels. Suppose you have two sources, source_a at port 12345, source_b at port 1236 and a replica connected to both sources using channels chan_source_a and chan_source_b. If you want to run pt-archiver to synchronize the replica against source_a, pt-archiver won't be able to determine what's the correct source since SHOW REPLICA STATUS will return 2 rows. In this case, you can use --channel=chan_source_a to specify the channel name to use in the SHOW REPLICA STATUS command.

--charset

short form: -A; type: string

Default character set. If the value is utf8, sets Perl's binmode on STDOUT to utf8, passes the mysql_enable_utf8 option to DBD::mysql, and runs SET NAMES UTF8 after connecting to MySQL. Any other value sets binmode on STDOUT without the utf8 layer, and runs SET NAMES after connecting to MySQL.

Note that only charsets as known by MySQL are recognized; So for example, "UTF8" will work, but "UTF-8" will not.

See also "--[no]check-charset".

--[no]check-charset

default: yes

Ensure connection and table character sets are the same. Disabling this check may cause text to be erroneously converted from one character set to another (usually from utf8 to latin1) which may cause data loss or mojibake. Disabling this check may be useful or necessary when character set conversions are intended.

--[no]check-columns

default: yes

Ensure "--source" and "--dest" have same columns.

Enabled by default; causes pt-archiver to check that the source and destination tables have the same columns. It does not check column order, data type, etc. It just checks that all columns in the source exist in the destination and vice versa. If there are any differences, pt-archiver will exit with an error.

To disable this check, specify --no-check-columns.

--check-interval

type: time; default: 1s

If "--check-replica-lag" is given, this defines how long the tool pauses each
time it discovers that a replica is lagging.
This check is performed every 100 rows.

--check-replica-lag

type: string; repeatable: yes

Pause archiving until the specified DSN's replica lag is less than "--max-lag". This option can be specified multiple times for checking more than one replica.

--check-slave-lag

type: string; repeatable: yes

This option is deprecated and will be removed in future releases. Use "--check-replica-lag" instead.

--columns

short form: -c; type: array

Comma-separated list of columns to archive.

Specify a comma-separated list of columns to fetch, write to the file, and insert into the destination table. If specified, pt-archiver ignores other columns unless it needs to add them to the "SELECT" statement for ascending an index or deleting rows. It fetches and uses these extra columns internally, but does not write them to the file or to the destination table. It does pass them to plugins.

See also "--primary-key-only".

--commit-each

Commit each set of fetched and archived rows (disables "--txn-size").

Commits transactions and flushes "--file" after each set of rows has been archived, before fetching the next set of rows, and before sleeping if "--sleep" is specified. Disables "--txn-size"; use "--limit" to control the transaction size with "--commit-each".

This option is useful as a shortcut to make "--limit" and "--txn-size" the same value, but more importantly it avoids transactions being held open while searching for more rows. For example, imagine you are archiving old rows from the beginning of a very large table, with "--limit" 1000 and "--txn-size" 1000. After some period of finding and archiving 1000 rows at a time, pt-archiver finds the last 999 rows and archives them, then executes the next SELECT to find more rows. This scans the rest of the table, but never finds any more rows. It has held open a transaction for a very long time, only to determine it is finished anyway. You can use "--commit-each" to avoid this.

--file
tipo: string

Archivo al que archivar, con formato similar a DATE_FORMAT().

Nombre del archivo donde se escribirán las filas archivadas. Se permite un subconjunto de los códigos de formato de DATE_FORMAT() de MySQL en el nombre del archivo, como los siguientes:

%d    Día del mes, numérico (01..31)
%H    Hora (00..23)
%i    Minutos, numéricos (00..59)
%m    Mes, numérico (01..12)
%s    Segundos (00..59)
%Y    Año, numérico, cuatro dígitos

También puede utilizar los siguientes códigos de formato adicionales:

%D    Nombre de la base de datos
%t    Nombre de la tabla

Ejemplo:

--file '/var/log/archive/%Y-%m-%d-%D.%t'

El contenido del archivo tiene el mismo formato que el utilizado por SELECT INTO OUTFILE, como se documenta en el manual de MySQL: las filas terminan con saltos de línea, las columnas terminan con tabulaciones, los caracteres NULL se representan como "\N" y los caracteres especiales se escapan con "\". Esto le permite recargar un archivo con los ajustes predeterminados de LOAD DATA INFILE.

Si desea una cabecera de columna al principio del archivo, consulte "--header". El archivo se vacía automáticamente por defecto; consulte "--buffer".

--max-lag
tipo: time; por defecto: 1s

Pausa el archivado si la réplica dada por "--check-replica-lag" se retrasa.

Esta opción hace que pt-archiver mire la réplica cada vez que está a punto de obtener otra fila. Si el retraso de la réplica es mayor que el valor de la opción, o si la réplica no se está ejecutando (por lo que su retraso es NULL), pt-archiver duerme durante "check-interval" segundos y luego vuelve a mirar el retraso. Repite hasta que la réplica se ponga al día, y luego procede a obtener y archivar la fila.

Esta opción puede eliminar la necesidad de "--sleep" o "--sleep-coef".

--no-ascend
No usar optimización de índice ascendente.

La optimización por defecto de índice ascendente hace que "pt-archiver" optimice las consultas "SELECT" repetidas para que busquen en el índice donde terminó la consulta anterior, y luego escaneen a lo largo de él, en lugar de escanear desde el principio de la tabla cada vez. Esto está habilitado por defecto porque generalmente es una buena estrategia para accesos repetidos.

Los índices grandes y de múltiples columnas pueden hacer que la cláusula WHERE sea lo suficientemente compleja como para que esto sea menos eficiente. Considere, por ejemplo, una clave PRIMARIA de cuatro columnas en (a, b, c, d). La cláusula WHERE para empezar donde terminó la última consulta es la siguiente:

WHERE (a > ?)
   OR (a = ? AND b > ?)
   OR (a = ? AND b = ? AND c > ?)
   OR (a = ? AND b = ? AND c = ? AND d >= ?)

Poblar los marcadores de posición con valores consume memoria y CPU, añade tráfico de red y sobrecarga de análisis, y puede dificultar la optimización de la consulta por parte de MySQL. Una clave de cuatro columnas no es un gran problema, pero una clave de diez columnas en la que cada columna permite "NULL" podría serlo.

Ascender el índice podría no ser necesario si sabe que simplemente está eliminando filas del principio de la tabla en bloques, pero sin dejar huecos, por lo que empezar desde el principio de la tabla es en realidad lo más eficiente.

Ver también "--ascend-first". Ver "EXTENDING" para una discusión sobre cómo esto interactúa con los plugins.

--no-delete
No eliminar filas archivadas.

Hace que "pt-archiver" no elimine las filas después de procesarlas. Esto deshabilita "--no-ascend", ya que habilitar ambos causaría un bucle infinito.

Si hay un plugin en el DSN de origen, su método "before_delete" se llama de todos modos, aunque "pt-archiver" no ejecute la eliminación. Ver "EXTENDING" para más información sobre plugins.

--stop
Detiene las instancias en ejecución creando el archivo centinela.

Hace que pt-archiver cree el archivo centinela especificado por "--sentinel" y salga. Esto debería tener el efecto de detener todas las instancias en ejecución que están vigilando el mismo archivo centinela. Ver también "--unstop".

--txn-size
tipo: entero; predeterminado: 1

Número de filas por transacción.

Especifica el tamaño, en número de filas, de cada transacción. Cero deshabilita las transacciones por completo. Después de que pt-archiver procesa esta cantidad de filas, confirma tanto el "--source" como el "--dest" si se proporcionan, y vacía el archivo dado por "--file".

Este parámetro es crítico para el rendimiento. Si está archivanndo desde un servidor en vivo, que por ejemplo está realizando un trabajo intensivo de OLTP, necesita elegir un buen equilibrio entre el tamaño de la transacción y el sobrecoste de la confirmación. Transacciones más grandes crean la posibilidad de más contención de bloqueo y puntos muertos, pero transacciones más pequeñas causan un sobrecoste de confirmación más frecuente, que puede ser significativo. Para dar una idea, en un pequeño conjunto de prueba trabajado mientras se escribía pt-archiver, un valor de 500 hizo que el archivado tomara aproximadamente 2 segundos por cada 1000 filas en una instancia de MySQL de lo contrario silenciosa en una máquina de escritorio, archivando en disco y a otra tabla. Deshabilitar transacciones con un valor de cero, que activa el autocommit, redujo el rendimiento a 38 segundos por mil filas.

Si no está archivando desde o hacia un motor de almacenamiento transaccional, es posible que desee deshabilitar las transacciones para que pt-archiver no intente confirmar.

EXTENSIÓN

pt-archiver es extensible mediante la conexión de módulos Perl externos para manejar parte de la lógica y/o acciones. Puede especificar un módulo tanto para "--source" como para "--dest", con la parte 'm' de la especificación. Por ejemplo:

--source D=test,t=test1,m=My::Module1 --dest m=My::Module2,t=test2

Esto hará que pt-archiver cargue los paquetes My::Module1 y My::Module2, cree instancias de ellos y luego los llame durante el proceso de archivado.

También puede especificar un plugin con "--plugin".

El módulo debe proporcionar esta interfaz:

new(dbh => $dbh, db => $db_name, tbl => $tbl_name)
Al constructor del plugin se le pasa una referencia al manejador de base de datos, el nombre de la base de datos y el nombre de la tabla. El plugin se crea justo después de que pt-archiver abre la conexión, y antes de que examine la tabla dada en los argumentos. Esto le da al plugin la oportunidad de crear y poblar tablas temporales, o realizar otro trabajo de configuración.
before_begin(cols => \@cols, allcols => \@allcols)
Este método se llama justo antes de que pt-archiver comience a iterar sobre las filas y archivarlas, pero después de que realiza todo el demás trabajo de configuración (examinar estructuras de tablas, diseñar consultas SQL, etc.). Este es el único momento en que pt-archiver informa al plugin los nombres de las columnas para las filas que pasará al plugin durante el archivado.

El argumento "cols" son los nombres de las columnas que el usuario solicitó archivar, ya sea por defecto o mediante la opción "--columns". El argumento "allcols" es la lista de nombres de columnas para cada fila que pt-archiver obtendrá de la tabla de origen. Puede obtener más columnas de las que el usuario solicitó, porque necesita algunas columnas para su propio uso. Cuando las funciones de plugin posteriores reciben una fila, es la fila completa que contiene todas las columnas adicionales, si las hay, añadidas al final.

is_archivable(row => \@row)
Este método se llama para cada fila para determinar si es archivada. Esto se aplica solo a "--source". El argumento es la fila en sí, como un arrayref. Si el método devuelve verdadero, la fila se archivará; de lo contrario, se omitirá.

Omitir una fila añade complicaciones para los no

índices únicos

Normalmente, pt-archiver utiliza una cláusula WHERE diseñada para apuntar a la última fila procesada como punto de inicio para el siguiente comando SELECT. Si ha omitido la fila devolviendo false desde is_archivable(), pt-archiver podría entrar en un bucle infinito porque la fila todavía existe. Por lo tanto, cuando especifica un plugin para el argumento "--source", pt-archiver modificará ligeramente su cláusula WHERE. En lugar de comenzar en "mayor o igual que" la última fila procesada, comenzará en "estrictamente mayor que". Esto funcionará bien en índices únicos como las claves primarias, pero puede omitir filas (dejar huecos) en índices no únicos o al ordenar solo la primera columna de un índice.

«pt-archiver» modificará la cláusula de la misma manera si especifica "--no-delete", porque nuevamente es posible un bucle infinito.

Si especifica la opción "--bulk-delete" y devuelve false desde este método, «pt-archiver» puede no hacer lo que espera. La fila no se archivará, pero se eliminará, ya que las eliminaciones masivas operan sobre rangos de filas y no saben qué filas seleccionó el plugin para conservar.

Si especifica la opción "--bulk-insert", el valor de retorno de este método influirá en si la fila se escribe en el archivo temporal para la inserción masiva, por lo que las inserciones masivas funcionarán según lo esperado. Sin embargo, las inserciones masivas requieren eliminaciones masivas.

before_delete(row => \@row)
Este método se llama para cada fila justo antes de que se elimine. Esto se aplica solo a "--source". Este es un buen lugar para manejar dependencias, como eliminar elementos que tienen claves externas a la fila que está a punto de eliminar. También podría usar esto para archivar recursivamente todas las tablas dependientes.

Este método de plugin se llama incluso si se proporciona "--no-delete", pero no si se proporciona "--bulk-delete".

before_bulk_delete(first_row => \@row, last_row => \@row)
Este método se llama justo antes de que se ejecute una eliminación masiva. Es similar al método «before_delete», excepto que sus argumentos son la primera y la última fila del rango que se eliminará. Se llama incluso si se proporciona "--no-delete".
before_insert(row => \@row)
Este método se llama para cada fila justo antes de que se inserte. Esto se aplica solo a "--dest". Podría usar esto para insertar la fila en varias tablas, quizás con una cláusula ON DUPLICATE KEY UPDATE para crear tablas de resumen en un almacén de datos.

Este método no se llama si se proporciona "--bulk-insert".

before_bulk_insert(first_row => \@row, last_row => \@row, filename => bulk_insert_filename)
Este método se llama justo antes de que se ejecute una inserción masiva. Es similar al método «before_insert», excepto que sus argumentos son la primera y la última fila del rango que se eliminará.
custom_sth(row => \@row, sql => $sql)
Este método se llama justo antes de insertar la fila, pero después de before_insert(). Permite al plugin especificar una sentencia INSERT diferente si se desea. El valor de retorno (si lo hay) debe ser un manejador de sentencias DBI. El parámetro sql es el texto SQL utilizado para preparar la sentencia INSERT predeterminada. Este método no se llama si especifica "--bulk-insert".

Si no se devuelve ningún valor, se utiliza el manejador de sentencias INSERT predeterminado.

Este método se aplica solo al plugin especificado para "--dest", por lo que si su plugin no hace lo que espera, verifique que lo haya especificado para el destino y no para el origen.

custom_sth_bulk(first_row => \@row, last_row => \@row, sql => $sql, filename => $bulk_insert_filename)
Si ha especificado "--bulk-insert", este método se llama justo antes de la inserción masiva, pero después de before_bulk_insert(), y los argumentos son diferentes.

El valor de retorno de este método, etc., es similar al método «custom_sth()».

after_finish()
Este método se llama después de que pt-archiver sale del bucle de archivado, confirma todos los manejadores de bases de datos, cierra "--file" e imprime las estadísticas finales, pero antes de que pt-archiver ejecute ANALYZE u OPTIMIZE (ver "--analyze" y "--optimize").

Si especifica un plugin tanto para "--source" como para "--dest", pt-archiver construye, llama a before_begin() y llama a after_finish() en los dos plugins en el orden "--source", "--dest".

pt-archiver asume que controla las transacciones y que el plugin NO confirmará ni revertirá el manejador de la base de datos. El manejador de la base de datos que se pasa al constructor del plugin es el mismo manejador que utiliza el propio pt-archiver. Recuerde que "--source" y "--dest" son manejadores separados.

Un módulo de ejemplo podría verse así:

package My::Module;
sub new {
   my ( $class, %args ) = @_;
   return bless(\%args, $class);
}
sub before_begin {
   my ( $self, %args ) = @_;
   # Guarda los nombres de las columnas para más tarde
   $self->{cols} = $args{cols};
}
sub is_archivable {
   my ( $self, %args ) = @_;
   # Realiza alguna lógica avanzada con $args{row}
   return 1;
}
sub before_delete {} # No realiza ninguna acción
sub before_insert {} # No realiza ninguna acción
sub custom_sth    {} # No realiza ninguna acción
sub after_finish  {} # No realiza ninguna acción
1;

MEDIO AMBIENTE

La variable de entorno PTDEBUG habilita la salida detallada de depuración en STDERR. Para habilitar la depuración y capturar toda la salida en un archivo, ejecute la herramienta así:

PTDEBUG=1 pt-archiver ... > ARCHIVO 2>&1

NAME

pt-archiver — archives or deletes rows from MySQL tables

SYNOPSIS

pt-archiver [ --source DSN ] [ --where “WHERE clause” ] [ --limit N ] [ --txn-size N ] [ --purge ] [ --statistics ] [ --dry-run ] [ --progress N ] [ --set-vars var=value,... ] [ --help ] [ --version ]

RISKS

pt-archiver deletes rows from tables. This is a dangerous operation that can lead to data loss if used incorrectly. Always back up your data before using pt-archiver . Test pt-archiver on a staging environment before using it on a production server.

pt-archiver can consume significant resources and can impact the performance of your MySQL server. Use the --progress option to monitor its progress and the --txn-size option to control the transaction size.

DESCRIPTION

pt-archiver is a tool for archiving or deleting rows from MySQL tables. It is designed to be used with large tables where deleting rows can be slow and resource-intensive.

pt-archiver works by selecting rows based on a WHERE clause and then either archiving them to another table or deleting them. It does this in batches to minimize the impact on the server.

Percona XtraDB Cluster

pt-archiver is compatible with Percona XtraDB Cluster.

OUTPUT

pt-archiver prints information about its progress, including the number of rows processed, the time taken, and any errors encountered.

ERROR-HANDLING

pt-archiver provides detailed error messages to help diagnose problems.

OPTIONS

--source DSN: The DSN for the MySQL server.

--where “WHERE clause”: The WHERE clause to select rows to archive or delete.

--limit N: The maximum number of rows to process.

--txn-size N: The number of rows to include in each transaction.

--purge: Delete the rows instead of archiving them.

--statistics: Print statistics about the operation.

--dry-run: Do not actually delete or archive any rows; just print what would be done.

--progress N: Print progress information every N rows.

--set-vars var=value,...: Set MySQL variables.

--help: Show help message.

--version: Show version information.

DSN OPTIONS

pt-archiver supports DSN options for connecting to MySQL. These include:

  • h: hostname
  • P: port
  • u: username
  • p: password
  • D: database

Example: --source h=localhost,u=root,p=secret,D=test

EXTENDING

pt-archiver can be extended by creating custom scripts that use its functionality.

ENVIRONMENT

pt-archiver uses the following environment variables:

  • PT_CONFIG_DIR: Directory for configuration files.

ATTENTION

pt-archiver is a powerful tool that can be dangerous if used incorrectly. Always back up your data before using this tool.
