NOMBRE

pt-query-digest - Analiza consultas MySQL de logs, processlist y tcpdump.

SINOPSIS

Uso: pt-query-digest [OPCIONES] [ARCHIVOS] [DSN]

pt-query-digest analiza consultas MySQL de archivos de log lentos, generales y binarios. También puede analizar consultas de "SHOW PROCESSLIST" y datos del protocolo MySQL de tcpdump. Por defecto, las consultas se agrupan por huella digital (fingerprint) y se reportan en orden descendente de tiempo de consulta (es decir, primero las consultas más lentas). Si no se proporcionan "ARCHIVOS", la herramienta lee desde "STDIN". El "DSN" opcional se utiliza para ciertas opciones como "--since" y "--until".

Reportar las consultas más lentas de "slow.log":

pt-query-digest slow.log

Reportar las consultas más lentas de la lista de procesos en host1:

pt-query-digest --processlist h=host1

Capturar datos del protocolo MySQL con tcpdump y luego reportar las consultas más lentas:

tcpdump -s 65535 -x -nn -q -tttt -i any -c 1000 port 3306 > mysql.tcp.txt
pt-query-digest --type tcpdump mysql.tcp.txt

Guardar datos de consultas de "slow.log" en host2 para revisión posterior y análisis de tendencias:

pt-query-digest --review h=host2 --no-report slow.log

DESCRIPCIÓN

pt-query-digest es una herramienta sofisticada pero fácil de usar para analizar consultas MySQL. Puede analizar consultas de logs lentos, generales y binarios de MySQL. (Los logs binarios deben ser convertidos a texto primero, ver "--type"). También puede usar "SHOW PROCESSLIST" y datos del protocolo MySQL de tcpdump. Por defecto, la herramienta reporta cuáles consultas son las más lentas y, por lo tanto, las más importantes de optimizar. Se pueden crear reportes más complejos y personalizados utilizando opciones como "--group-by", "--filter" y "--embedded-attributes".

El análisis de consultas es una buena práctica que debe realizarse con frecuencia. Para facilitar esto, pt-query-digest tiene dos funciones: revisión de consultas ("--review") e historial de consultas ("--history"). Cuando se utiliza la opción "--review", todas las consultas únicas se guardan en una base de datos. Cuando la herramienta se ejecuta de nuevo con "--review", las consultas marcadas como revisadas en la base de datos no se imprimen en el informe. Esto resalta las nuevas consultas que necesitan ser revisadas. Cuando se utiliza la opción "--history", las métricas de consulta (tiempo de consulta, tiempo de bloqueo, etc.) para cada consulta única se guardan en una base de datos. Cada vez que la herramienta se ejecuta con "--history", se guardan más datos históricos que pueden usarse para analizar las tendencias del rendimiento de las consultas a lo largo del tiempo.

ATRIBUTOS

pt-query-digest opera sobre eventos, que son una colección de pares clave-valor llamados atributos. Reconocerá la mayoría de los atributos inmediatamente: "Query_time", "Lock_time", y así sucesivamente. Puede simplemente mirar un log lento y verlos. Sin embargo, hay algunos que no existen en el log lento, y los logs lentos pueden incluir diferentes tipos de atributos (por ejemplo, puede tener un servidor con los parches de Percona).

Consulte "REFERENCIA DE ATRIBUTOS" cerca del final de esta documentación para obtener una lista de atributos comunes y específicos de "--type". Es necesaria una familiaridad con estos atributos para trabajar con "--filter", "--ignore-attributes", y otras opciones relacionadas con atributos.

Con un uso creativo de "--filter", puede crear nuevos atributos derivados de atributos existentes. Por ejemplo, para crear un atributo llamado "Row_ratio" para examinar la relación entre "Rows_sent" y "Rows_examined", especifique un filtro como:

--filter '($event->{Row_ratio} = $event->{Rows_sent} / ($event->{Rows_examined})) && 1'

El truco "&& 1" es necesario para crear una sintaxis de una sola línea válida que siempre sea cierta, incluso si la asignación resulta falsa. El nuevo atributo aparecerá automáticamente en la salida:

# Row ratio        1.00    0.00      1    0.50      1    0.71    0.50

Los atributos creados de esta manera se pueden especificar para "--order-by" o cualquier opción que requiera un atributo.

SALIDA

La "--output" por defecto es un informe de análisis de consultas. La opción "--[no]report" controla si este informe se imprime o no. A veces puede querer analizar todas las consultas pero suprimir el informe, por ejemplo, al usar "--review" o "--history".

Hay un párrafo por cada clase de consulta analizada. Una "clase" de consultas tiene el mismo valor para el atributo "--group-by", que por defecto es "fingerprint". (Ver "ATRIBUTOS"). Una huella digital es una versión abstracta del texto de la consulta con literales eliminados, espacios colapsados, etc. El informe está formateado de manera que sea fácil de pegar en correos electrónicos sin saltos de línea, y todas las líneas que no son de consulta comienzan con un comentario, para que pueda guardarlo en un archivo .sql y abrirlo en su editor de texto favorito con resaltado de sintaxis. Hay un perfil de tiempo de respuesta al principio.

La salida descrita aquí está controlada por "--report-format". Esa opción le permite especificar qué imprimir y en qué orden. La salida por defecto en el orden por defecto se describe aquí.

El informe, por defecto, comienza con un párrafo sobre toda la ejecución del análisis. La información es muy similar a la que verá para cada clase de consultas en el log, pero no tiene información que sería demasiado costosa de mantener globalmente para el análisis. También tiene estadísticas sobre la ejecución del código en sí, como el uso de CPU y memoria, la fecha y hora local de la ejecución y una lista de los archivos de entrada leídos/analizados.

ANÁLISIS DE REGISTROS LENTOS

Este es un fragmento de un registro lento de MySQL:

# Time, ID, User, Host, Query_time, Lock_time, Rows_sent, Rows_examined, SQL_query
# YYYY-MM-DD HH:MM:SS, [id], [user] [hostname] : [db] <= SET timestamp=...;
#                   [id] [user] [hostname] : [db] <= <Query Text>
# administrator command: Query end

Aquí, una consulta específica (ya que solo estamos interesado en una) es:

# Time, ID, User, Host, Query_time, Lock_time, Rows_sent, Rows_examined, SQL_query
# YYYY-MM-DD HH:MM:SS, [id], [user] [hostname] : [db] <= SET timestamp=...;
#                   [id] [user] [hostname] : [db] <= SELECT ... FROM ... WHERE
#                   ... some query ...
#                   ...
#                   ... LIMIT 1, 1000000;
# administrator command: Query end

Podemos buscarla de forma más eficiente usando el checksum:

pt-query-digest slow.log \
   --no-report \
   --output slowlog \
   --filter '$event->{fingerprint} \
        && make_checksum($event->{fingerprint}) eq "FDEA8D2993C9CAF3"'

Ten en cuenta que debes eliminar el prefijo "0x" del checksum.

Finalmente, en caso de que quieras encontrar una muestra de la consulta en el archivo de registro, existe el desplazamiento de bytes donde puedes buscar. (Esto no siempre es exacto, debido a algunas anomalías en el formato del registro lento, pero generalmente es correcto). La posición se refiere a la peor muestra, de la que veremos más a continuación.

A continuación, se presenta la tabla de métricas sobre esta clase de consultas.

#           pct   total    min    max     avg     95%  stddev  median
# Count       0       2
# Exec time  13   1105s   552s   554s    553s    554s      2s    553s
# Lock time   0   216us   99us  117us   108us   117us    12us   108us
# Rows sent  20   6.26M  3.13M  3.13M   3.13M   3.13M   12.73   3.13M
# Rows exam   0   6.26M  3.13M  3.13M   3.13M   3.13M   12.73   3.13M

La primera línea son los encabezados de columna de la tabla. El porcentaje es el porcentaje del total para toda la ejecución del análisis, y el total es el valor real de la métrica especificada. Por ejemplo, en este caso podemos ver que la consulta se ejecutó 2 veces, lo que representa el 13% del número total de consultas en el archivo. Las columnas min, max y avg son autoexplicativas. La columna 95% muestra el percentil 95; el 95% de los valores son menores o iguales a este valor. La desviación estándar te muestra qué tan agrupados están los valores. La desviación estándar y la mediana se calculan a partir del percentil 95, descartando los valores extremadamente grandes.

Las estadísticas de stddev, median y percentil 95 son aproximadas. Las estadísticas exactas requieren conservar cada valor visto, ordenarlo y realizar algunos cálculos sobre ellos. Esto consume mucha memoria. Para evitar esto, mantenemos 1000 cubetas, cada una un 5% más grande que la anterior, que van desde .000001 hasta un número muy grande. Cuando vemos un valor, incrementamos la cubeta en la que cae. Así tenemos memoria fija por clase de consulta. La desventaja es la imprecisión, que típicamente cae en el rango del 5 por ciento.

A continuación, tenemos estadísticas sobre los usuarios, bases de datos y el rango de tiempo para la consulta.

# Users       1   user1
# Databases   2     db1(1), db2(1)
# Time range 2008-11-26 04:55:18 to 2008-11-27 00:15:15

#   1us
#  10us
# 100us
#   1ms
#  10ms  #####
# 100ms  ####################
#    1s  ##########
#  10s+

La primera cubeta son todos los valores en el "rango de microsegundos individuales", es decir, menos de 10us. La segunda son "decenas de microsegundos", que es de 10us hasta (pero sin incluir) 100us; y así sucesivamente. REVISIÓN DE CONSULTAS

Una consulta "--review" es el proceso de almacenar todas las huellas digitales de consultas analizadas. Esto tiene varios beneficios:

  • Puedes agregar metadatos a clases de consultas, como marcarlas para seguimiento, agregar notas a las consultas o marcarlas con un ID de incidencia para tu sistema de seguimiento de incidencias.
  • Puedes referirte a los valores almacenados en ejecuciones posteriores para saber si has visto una consulta antes. Esto puede ayudarte a reducir el trabajo duplicado.
  • Puedes almacenar datos históricos como el recuento de filas, tiempos de consulta y, en general, cualquier cosa que puedas ver en el informe.

Para usar esta función, ejecuta pt-query-digest con la opción "--review". Almacenará las huellas digitales y otra información en la tabla que especifiques. La próxima vez que lo ejecutes con la misma opción, hará lo siguiente:

  • No te mostrará las consultas que ya has revisado. Una consulta se considera ya revisada si has establecido un valor para la columna "reviewed_by". (Si quieres ver las consultas que ya has revisado, usa la opción "--report-all").
  • Las consultas que has revisado y que no aparecen en la salida causarán brechas en la secuencia de números de consulta en la primera línea de cada párrafo. Y el valor que hayas especificado para "--limit" seguirá siendo respetado. Por lo tanto, si has revisado todas las consultas en el top 10 y pides el top 10, no verás nada en la salida.
  • Si quieres ver las consultas que ya has revisado, puedes especificar "--report-all". Entonces verás la salida normal del análisis, pero también verás la información de la tabla de revisión, justo debajo del gráfico de tiempo de ejecución. Por ejemplo, 
    # Review information
#      comments: really bad IN() subquery, fix soon!
#    first_seen: 2008-12-01 11:48:57
#   jira_ticket: 1933
#     last_seen: 2008-12-18 11:49:07
#      priority: high
#   reviewed_by: xaprb
#   reviewed_on: 2008-12-18 15:03:11

    Estos metadatos son útiles porque, a medida que analizas tus consultas, tus comentarios se integran directamente en el informe.

HUELLAS DIGITALES DE CONSULTAS

Una huella digital de consulta es la forma abstracta de una consulta, que permite agrupar consultas similares. La abstracción de una consulta elimina valores literales, normaliza el espacio en blanco, etc. Por ejemplo, considera estas dos consultas:

SELECT name, password FROM user WHERE id='12823';
select name,   password from user
   where id=5;

Ambas consultas tendrán la siguiente huella digital:

select name, password from user where id=?

Una vez que se conoce la huella digital de la consulta, podemos hablar de una consulta como si representara a todas las consultas similares.

Lo que hace "pt-query-digest" es análogo a una sentencia GROUP BY en SQL. (¡Pero ten en cuenta que "múltiples columnas" no define una agrupación de múltiples columnas; define múltiples informes!). Si tu comando se ve así,

pt-query-digest \
    --group-by fingerprint \
    --order-by Query_time:sum \
    --limit 10 \
    slow.log

El SQL pseudo-equivalente se vería así:

SELECT WORST(query BY Query_time), SUM(Query_time), ...
FROM /ruta/al/slow.log
GROUP BY FINGERPRINT(query)
ORDER BY SUM(Query_time) DESC
LIMIT 10

También puedes usar el valor "distill", que es una especie de super-huella digital. Ver "--group-by" para más detalles.

La creación de huellas digitales de consultas acomoda muchos casos especiales, que han demostrado ser necesarios en el mundo real. Por ejemplo, una lista "IN" con 5 literales es realmente equivalente a una con 4 literales, por lo que las listas de literales se colapsan a una sola. Si encuentras algo que no se está creando una huella digital correctamente, por favor envía un informe de error con un caso de prueba reproducible.

Aquí hay una lista de transformaciones durante la creación de huellas digitales, que podría no ser exhaustiva:

  • Agrupar todas las consultas SELECT de mysqldump juntas, incluso si son contra tablas diferentes. Lo mismo se aplica a todas las consultas de pt-table-checksum.
  • Acortar sentencias INSERT de múltiples valores a una sola lista VALUES().
  • Eliminar comentarios.
  • Abstraer las bases de datos en sentencias USE, para que todas las sentencias USE se agrupen juntas.
  • Reemplazar todos los literales, como cadenas entre comillas. Para mayor eficiencia, el código que reemplaza números literales es algo no selectivo, y podría reemplazar algunas cosas como números cuando realmente no lo son. Los literales hexadecimales también se reemplazan. NULL se trata como un literal. Los números incrustados en identificadores también se reemplazan, por lo que las tablas con nombres similares tendrán la misma huella digital (por ejemplo, users_2009 y users_2010 tendrán la misma huella digital).
  • Colapsar todo el espacio en blanco en un solo espacio.
  • Convertir toda la consulta a minúsculas.
  • Reemplazar todos los literales dentro de las listas IN() y VALUES() con un solo marcador de posición, independientemente de la cardinalidad.
  • Colapsar múltiples consultas UNION idénticas en una sola.

OPCIONES

Esta herramienta acepta argumentos de línea de comandos adicionales. Consulte la "SINOPSIS" y la información de uso para obtener detalles.

--ask-pass
Solicitar una contraseña al conectarse a MySQL.
--attribute-aliases
tipo: array; por defecto: db|Schema

Lista de atributo|alias, etc.

Ciertos atributos tienen múltiples nombres, como db y Schema. Si un evento no tiene el atributo principal, pt-query-digest busca un atributo alias. Si encuentra un alias, crea el atributo principal con el valor del atributo alias y elimina el atributo alias.

Si el evento tiene el atributo principal, todos los atributos alias se eliminan.

Esto ayuda a simplificar los atributos del evento para que, por ejemplo, no haya líneas de informe tanto para db como para Schema.

es. Si el valor del atributo es mayor que este, se utiliza en su lugar el valor visto por última vez para esa clase de consulta. Deshabilitado por defecto.

--embedded-attributes
tipo: array

Dos patrones de expresiones regulares de Perl para capturar pseudo-atributos incrustados en consultas.

Los atributos incrustados pueden ser pares de atributos-valor especiales que hayas ocultado en comentarios. La primera expresión regular debe coincidir con todo el conjunto de atributos (en caso de que haya varios). La segunda expresión regular debe coincidir y capturar pares de atributos-valor de la primera expresión regular.

Por ejemplo, supongamos que tu consulta se ve así:

SELECT * from users -- file: /login.php, line: 493;

Podrías ejecutar pt-query-digest con la siguiente opción:

pt-query-digest --embedded-attributes ' -- .*','(\w+): ([^\,]+)'

La primera expresión regular captura todo el comentario:

" -- file: /login.php, line: 493;"

La segunda lo divide en pares de atributos-valor y los agrega al evento:

ATTRIBUTE  VALUE
=========  ==========
file       /login.php
line       493

NOTA: Todas las comas en los patrones de expresiones regulares deben escaparse con \ de lo contrario, el patrón se romperá.

--expected-range
tipo: array; predeterminado: 5,10

Explica los elementos cuando hay más o menos de lo esperado.

Define el número de elementos que se espera ver en el informe proporcionado por "--[no]report", controlado por "--limit" y "--outliers". Si hay más o menos elementos en el informe, cada uno explicará por qué fue incluido.

--explain
tipo: DSN

Ejecuta EXPLAIN para la consulta de ejemplo con este DSN e imprime los resultados.

Esto solo funciona cuando "--group-by" incluye "fingerprint". Hace que pt-query-digest ejecute EXPLAIN e incluya la salida en el informe. Por seguridad, las consultas que parezcan tener una subconsulta que EXPLAIN ejecutará no se explicarán. Esas son típicamente consultas de "tabla derivada" de la forma

select ... from ( select .... ) der;

Los resultados de EXPLAIN se imprimen como un formato vertical completo en el informe del evento, que aparece al final de cada informe de evento en estilo vertical ("\G") tal como lo imprime MySQL.

--filter
tipo: cadena

Descarta eventos para los cuales este código Perl no devuelve verdadero.

Esta opción es una cadena de código Perl o un archivo que contiene código Perl que se compila en una subrutina con un argumento: $event. Esto es un hashref. Si el valor dado es un archivo legible, entonces pt-query-digest lee el archivo completo y usa su contenido como código. El archivo no debe contener una línea shebang (#!/usr/bin/perl).

Si el código devuelve verdadero, la cadena de callbacks continúa; de lo contrario, termina. El código es la última declaración en la subrutina aparte de "return $event". La plantilla de la subrutina es:

sub { $event = shift; filter && return $event; }

Los filtros dados en la línea de comandos se envuelven entre paréntesis como "( filter )". Para filtros complejos y de varias líneas, debes poner el código dentro de un archivo para que no se envuelva entre paréntesis. De cualquier manera, el filtro debe producir código sintácticamente válido dado la plantilla. Por ejemplo, una rama if-else dada en la línea de comandos no sería válida:

--filter 'if () { } else { }'  # INCORRECTO

Dado que se proporciona en la línea de comandos, la rama if-else se envolvería entre paréntesis, lo que no es sintácticamente válido. Por lo tanto, para lograr algo más complejo como esto, se requeriría poner el código en un archivo, por ejemplo, filter.txt:

my $event_ok; if (...) { $event_ok=1; } else { $event_ok=0; } $event_ok

Luego, especifica "--filter filter.txt" para leer el código de filter.txt.

Si el código del filtro no compila, pt-query-digest morirá con un error. Si el código del filtro compila, aún puede ocurrir un error en tiempo de ejecución si el código intenta hacer algo incorrecto (como hacer coincidencia de patrones con un valor indefinido). pt-query-digest no proporciona ninguna salvaguarda, ¡así que codifica con cuidado!

Un ejemplo de filtro que descarta todo excepto las declaraciones SELECT:

--filter '$event->{arg} =~ m/^select/i'

Esto se compila en una subrutina como la siguiente:

sub { $event = shift; ( $event->{arg} =~ m/^select/i ) && return $event; }

Es permisible que el código tenga efectos secundarios (para alterar $event).

Consulta "REFERENCIA DE ATRIBUTOS" para obtener una lista de atributos comunes y específicos de "--type".

Aquí hay más ejemplos de código de filtro:

Host/IP coincide con domain.com
--filter '($event->{host} || $event->{ip} || "") =~ m/domain.com/'

A veces MySQL registra el host donde se espera la IP. Por lo tanto, comprobamos ambos.

Usuario coincide con john

La consulta es de 1 MB o más grande

--run-time-mode
type: string; default: clock

Set what the value of "--run

-time" opera. A continuación, se muestran los valores posibles para esta opción:

reloj
"--run-time" especifica una cantidad de tiempo real de reloj durante la cual la herramienta debe ejecutarse por cada "--iterations".
evento
"--run-time" especifica una cantidad de tiempo de registro. El tiempo de registro se determina mediante marcas de tiempo en el registro. Se recuerda la primera marca de tiempo vista y cada marca de tiempo posterior se compara con la primera para determinar cuánto tiempo de registro ha transcurrido. Por ejemplo, si la primera marca de tiempo vista es "12:00:00" y la siguiente es "12:01:30", eso son 1 minuto y 30 segundos de tiempo de registro. La herramienta leerá eventos hasta que el tiempo de registro sea mayor o igual al valor especificado de "--run-time".

Dado que las marcas de tiempo en los registros no siempre se imprimen, o no siempre se imprimen con frecuencia, este modo varía en precisión.

intervalo
"--run-time" especifica los límites del intervalo de tiempo de registro en los que se dividen los eventos y se generan los informes. Este modo es diferente de los demás porque no especifica cuánto tiempo ejecutar. El valor de "--run-time" debe ser un intervalo que se divida uniformemente en minutos, horas o días. Por ejemplo, "5m" se divide uniformemente en horas (60/5=12, por lo que 12 intervalos de 5 minutos por hora), pero "7m" no (60/7=8.6).

Especificar "--run-time-mode interval --run-time 30m --iterations 0" es similar a especificar "--run-time-mode clock --run-time 30m --iterations 0". En este último caso, pt-query-digest se ejecutará indefinidamente, produciendo informes cada 30 minutos, pero esto solo funciona de manera efectiva con entradas continuas como STDIN y la lista de procesos. Para entradas fijas, como archivos de registro, el primer ejemplo produce múltiples informes al dividir el registro en intervalos de 30 minutos basados en marcas de tiempo.

Los intervalos se calculan a partir del segundo/minuto/hora cero en el que ocurre una marca de tiempo, no a partir de la hora que especifica. Por ejemplo, con intervalos de 30 minutos y una marca de tiempo de "12:10:30", el intervalo *no* es de "12:10:30" a "12:40:30", sino de "12:00:00" a "12:29:59". O, con intervalos de 1 hora, es de "12:00:00" a "12:59:59". Cuando una nueva marca de tiempo excede el intervalo, se imprime un informe y se recalcula el siguiente intervalo basándose en la nueva marca de tiempo.

Dado que "--iterations" es 1 por defecto, probablemente querrá especificar un nuevo valor, de lo contrario, pt-query-digest solo obtendrá e informará sobre el primer intervalo del registro, ya que 1 intervalo = 1 iteración. Si desea obtener e informar sobre cada intervalo en un registro, especifique "--iterations" 0.

La herramienta imprime una advertencia y continúa si una variable no se puede establecer.

--show-all
tipo: Hash

Muestra todos los valores para estos atributos.

Por defecto, pt-query-digest solo muestra tantos valores de un atributo como quepan en una sola línea. Esta opción le permite especificar atributos para los que se mostrarán todos los valores (se ignora el ancho de línea). Esto solo funciona para atributos con valores de cadena como usuario, host, db, etc. Se pueden especificar varios atributos, separados por comas.

--since
tipo: string

Analiza solo las consultas más recientes que este valor (analiza las consultas desde esta fecha).

Esta opción le permite ignorar las consultas anteriores a un determinado valor y analizar solo aquellas consultas que son más recientes que el valor. El valor puede ser de varios tipos:

* Valor de tiempo simple N con sufijo opcional: N[shmd], donde
  s=segundos, h=horas, m=minutos, d=días (s por defecto si no se
  indica sufijo); esto es como decir "desde hace N[shmd]"
* Fecha completa con horas opcionales:minutos:segundos:
  YYYY-MM-DD [HH:MM:SS]
* Fecha corta, estilo MySQL:
  YYMMDD [HH:MM:SS]
* Cualquier expresión de tiempo evaluada por MySQL:
  CURRENT_DATE - INTERVAL 7 DAY

Si proporciona una expresión de tiempo de MySQL y no ha especificado una DSN para "--explain", "--processlist" o "--review", entonces debe especificar una DSN en la línea de comandos para que pt-query-digest pueda conectarse a MySQL para evaluar la expresión.

La expresión de tiempo de MySQL se envuelve dentro de una consulta como "SELECT UNIX_TIMESTAMP(<expresión>)", así que asegúrese de que la expresión sea válida dentro de esta consulta. Por ejemplo, no use UNIX_TIMESTAMP() porque UNIX_TIMESTAMP(UNIX_TIMESTAMP()) devuelve 0.

Se asume que los eventos están en orden cronológico: eventos más antiguos al principio del registro y eventos más recientes al final del registro. "--since" es estricto: ignora todas las consultas hasta que se encuentra una que sea lo suficientemente reciente. Por lo tanto, si los eventos de consulta no tienen marcas de tiempo consistentes, algunos que son lo suficientemente recientes pueden ser ignorados.

Ver también "--until".

--socket
forma corta: -S; tipo: string

Archivo de socket a utilizar para la conexión.

--timeline
Muestra una línea de tiempo de eventos.

Esta opción hace que pt-query-digest imprima otro tipo de informe: una línea de tiempo de los eventos. Cada consulta todavía se agrupa y agrega en clases según "--group-by", pero luego se imprimen en orden cronológico. El informe de línea de tiempo imprime la marca de tiempo, el intervalo, la cuenta y el valor de cada clase.

Si lo único que desea es el informe de línea de tiempo, entonces especifique "--no-report" para suprimir el informe de análisis de consulta predeterminado. De lo contrario, el informe de línea de tiempo se imprimirá al final antes del perfil de tiempo de respuesta (ver "--report-format" y "OUTPUT").

Por ejemplo, esto:

pt-query-digest /path/to/log --group-by distill --timeline

imprimirá algo como:

# ########################################################
# informe de destilación
# ########################################################
# 2009-07-25 11:19:27 1+00:00:01   2 SELECT foo
# 2009-07-27 11:19:30      00:01   2 SELECT bar
# 2009-07-27 11:30:00 1+06:30:00   2 SELECT foo
--type
tipo: Array; por defecto: slowlog

El tipo de entrada a analizar. Los tipos permitidos son

binlog
Analiza un archivo de registro binario que primero ha sido convertido a texto usando mysqlbinlog.

Por ejemplo:

mysqlbinlog mysql-bin.000441 > mysql-bin.000441.txt
pt-query-digest --type binlog mysql-bin.000441.txt
genlog
Analiza un archivo de registro general de MySQL. Los registros generales carecen de muchos "ATTRIBUTES", en particular "Query_time". El "--order-by" predeterminado para los registros generales cambia a "Query_time:cnt".
slowlog
Analiza un archivo de registro en cualquier variación del formato de registro lento de MySQL.
tcpdump
Inspecciona paquetes de red y decodifica el protocolo cliente de MySQL, extrayendo consultas y respuestas del mismo.

pt-query-digest en realidad no observa la red (es decir, NO "escucha paquetes"). En cambio, solo analiza la salida de tcpdump. Usted es responsable de generar esta salida; pt-query-digest no lo hace por usted. Luego, envía esto a pt-query-digest como lo haría con cualquier archivo de registro: como archivos en la línea de comandos o a STDIN.

El analizador espera que la entrada tenga el formato con las siguientes opciones: "-x -n -q -tttt". Por ejemplo, si desea capturar la salida de su máquina local, puede hacer algo como lo siguiente (el puerto debe ser el último en FreeBSD):

tcpdump -s 65535 -x -nn -q -tttt -i any -c 1000 port 3306 \
  > mysql.tcp.txt
pt-query-digest --type tcpdump mysql.tcp.txt

Los otros parámetros de tcpdump, como -s, -c e -i, dependen de usted. Solo asegúrese de que la salida se vea así (hay un salto de línea en la primera línea para evitar problemas de página de manual):

2009-04-12 09:50:16.804849 IP 127.0.0.1.42167
       > 127.0.0.1.3306: tcp 37
    0x0000:  4508 0059 6eb2 4000 4006 cde2 7f00 0001
    0x0010:  ....

¡Recuerde que tcpdump tiene una útil opción -c para detenerse después de capturar un cierto número de paquetes! Eso es muy útil para probar su comando tcpdump. Tenga en cuenta que tcpdump no puede capturar tráfico en un socket Unix. Lea http://bugs.mysql.com/bug.php?id=31577 si está confundido acerca de esto

Devananda Van Der Veen explicó en el blog de rendimiento de MySQL cómo capturar tráfico sin perder paquetes en servidores ocupados. La pérdida de paquetes hace que pt-query-digest no vea la respuesta a una solicitud, luego vea la respuesta a una solicitud posterior y asigne un tiempo de ejecución incorrecto a la consulta. Puede cambiar el filtro a algo como lo siguiente para ayudar a capturar un subconjunto de las consultas. (Ver https://www.percona.com/blog/how-to-use-tcpdump-on-very-busy-hosts/ para más detalles.)

tcpdump -i any -s 65535 -x -n -q -tttt \
   'port 3306 and tcp[1] & 7 == 2 and tcp[3] & 7 == 2'

Todos los servidores MySQL que se ejecutan en el puerto 3306 se detectan automáticamente en la salida de tcpdump. Por lo tanto, si la salida de tcpdump contiene paquetes de varios servidores en el puerto 3306 (por ejemplo, 10.0.0.1:3306, 10.0.0.2:3306, etc.), todos los paquetes/consultas de todos estos servidores se analizarán juntos como si fueran un solo servidor.

Si está analizando tráfico para un servidor MySQL que no se está ejecutando en el puerto 3306, consulte "--watch-server".

Tenga en cuenta también que pt-query-digest puede no informar la base de datos para las consultas al analizar la salida de tcpdump. La base de datos se descubre solo en los eventos de conexión iniciales para un nuevo cliente o cuando se ejecuta <USE db>. Si la salida de tcpdump no contiene ninguno de estos, entonces pt-query-digest no puede descubrir la base de datos.

Se admiten las sentencias preparadas del lado del servidor. El tráfico cifrado con SSL no se puede inspeccionar ni decodificar.

rawlog
Los registros sin procesar no son registros de MySQL, sino archivos de texto simples con una instrucción SQL por línea, como:
SELECT c FROM t WHERE id=1
/* Hello, world! */ SELECT * FROM t2 LIMIT 1
INSERT INTO t (a, b) VALUES ('foo', 'bar')
INSERT INTO t SELECT * FROM monkeys

Dado que los registros sin procesar no tienen métricas, muchas opciones y funciones de pt-query-digest no funcionan con ellos.

Un caso de uso para registros sin procesar es clasificar consultas por recuento cuando la única información disponible es una lista de consultas, obtenida al consultar "SHOW PROCESSLIST", por ejemplo.

--until
tipo: string

Analiza solo consultas más antiguas que este valor (analiza consultas hasta esta fecha).

Esta opción le permite ignorar consultas más nuevas que un valor determinado y analizar solo aquellas consultas que son más antiguas que el valor. El valor puede ser de uno de los tipos enumerados para "--since".

A diferencia de "--since", "--until" no es estricto: todas las consultas se analizan hasta que una tenga una marca de tiempo igual o mayor que "--until". Luego, todas las consultas posteriores se ignoran.

--user
forma corta: -u; tipo: string

Usuario para iniciar sesión si no es el usuario actual.

--variations
tipo: Array

Informa el número de variaciones en los valores de estos atributos.

Las variaciones muestran cuántos valores distintos tuvo un atributo dentro de una clase. El valor habitual para esta opción es "arg", que muestra cuántas consultas distintas hubo en la clase. Esto puede ser útil para determinar la cachabilidad de una consulta.

Los valores distintos se determinan mediante sumas de verificación CRC32 de los valores de los atributos. Estas sumas de verificación se informan en el informe de consulta para los atributos especificados por esta opción, como:

# arg crc      109 (1/25%), 144 (1/25%)... 2 more

En esa clase hubo 4 consultas distintas. Se muestran las sumas de verificación de las dos primeras variaciones, y cada una ocurrió una vez (o, el 25% de las veces).

Los recuentos de variaciones distintas son aproximados porque solo se guardan 1000 variaciones. Se guarda el mod (%) 1000 de la suma de verificación CRC32 completa, por lo que algunas sumas de verificación distintas se tratan como iguales.

--version
Muestra la versión y sale.

predeterminado: yes

Primero, la herramienta verifica su propia versión y también las versiones del siguiente software: sistema operativo, Percona Monitoring and Management (PMM), MySQL, Perl, controlador MySQL para Perl (DBD::mysql) y Percona Toolkit. --watch-server
tipo: string

Esta opción le indica a pt-query-digest qué dirección IP y puerto del servidor (como "10.0.0.1:3306") debe monitorear al analizar tcpdump (para el tipo "--type" tcpdump); todos los demás servidores se ignoran. Si no lo especifica, pt-query-digest monitorea todos los servidores buscando cualquier dirección IP que use el puerto 3306 o "mysql". Si está monitoreando un servidor con un puerto no estándar, esto no funcionará, por lo que debe especificar la dirección IP y el puerto a monitorear.

Si desea monitorear una combinación de servidores, algunos que se ejecutan en el puerto estándar 3306 y otros en puertos no estándar, debe crear salidas de tcpdump separadas para los servidores con puertos no estándar y luego especificar esta opción para cada uno. Actualmente, pt-query-digest no puede detectar automáticamente servidores en el puerto 3306 y al mismo tiempo se le indica que monitoree un servidor en un puerto no estándar.

OPCIONES DSN

Estas opciones DSN se utilizan para crear un DSN. Cada opción se proporciona como "opcion=valor". Las opciones distinguen entre mayúsculas y minúsculas, por lo que P y p no son la misma opción. No puede haber espacios en blanco antes o después del signo "=" y si el valor contiene espacios en blanco debe entrecomillarse. Las opciones DSN están separadas por comas. Consulte la página del manual de percona-toolkit para obtener detalles completos.

  • A

    dsn: charset; copia: yes

    Juego de caracteres predeterminado.

  • D

    dsn: database; copia: yes

    Base de datos predeterminada a usar al conectarse a MySQL.

  • F

    dsn: mysql_read_default_file; copia: yes

    Lee solo las opciones predeterminadas del archivo dado.

  • h

    dsn: host; copia: yes

    Conéctate al host.

  • p

    dsn: password; copia: yes

    Contraseña a usar al conectarse. Si la contraseña contiene comas, deben escaparse con una barra invertida: "exam\,ple"

  • P

    dsn: port; copia: yes

    Número de puerto a usar para la conexión.

  • S

    dsn: mysql_socket; copia: yes

    Archivo de socket a usar para la conexión.

  • t

    La tabla "--review" o "--history".

  • u

    dsn: user; copia: yes

    Usuario para iniciar sesión si no es el usuario actual.

  • s

    dsn: mysql_ssl; copia: yes

    Crear conexión SSL

PTDEBUG=1 pt-query-digest ... > FILE 2>&1

REFERENCIA DE ATRIBUTOS

Los eventos pueden tener los siguientes atributos. Si estás escribiendo un filtro, asegúrate de que un atributo esté definido en cada evento antes de usarlo, de lo contrario, el código del filtro podría bloquear la herramienta con un error de "uso de valor no inicializado".

Puedes volcar los atributos de eventos para cualquier entrada como:

$ pt-query-digest                  \
    slow.log                       \
    --filter 'print Dumper $event' \
    --no-report                    \
    --sample 1

Eso producirá una gran cantidad de salida con pares de "atributo => valor" como:

$VAR1 = {
  Query_time => '0.033384',
  Rows_examined => '0',
  Rows_sent => '0',
  Thread_id => '10',
  Tmp_table => 'No',
  Tmp_table_on_disk => 'No',
  arg => 'SELECT col FROM tbl WHERE id=5',
  bytes => 103,
  cmd => 'Query',
  db => 'db1',
  fingerprint => 'select col from tbl where id=?',
  host => '',
  pos_in_log => 1334,
  ts => '071218 11:48:27',
  user => '[SQL_SLAVE]'
};

COMÚN

Estos atributos son comunes a todos los "--type" de entrada y "--processlist", excepto donde se indique lo contrario.

arg
El texto de la consulta, o el comando para comandos de administración como "Ping".
bytes
La longitud en bytes del "arg".
cmd
"Query" o "Admin".
db
La base de datos actual. El valor proviene de las sentencias USE database. Por defecto, "Schema" es un alias que se cambia automáticamente a "db"; ver "--attribute-aliases".
fingerprint
Una forma abstracta de la consulta. Ver "FINGERPRINTS".
host
El host del cliente que ejecutó la consulta.
pos_in_log
El desplazamiento en bytes del evento en el log o tcpdump, excepto para "--processlist".
Query_time
El tiempo total que tardó la consulta, incluido el tiempo de bloqueo.
ts
La marca de tiempo de cuándo finalizó la consulta.

LOGS LENTOS, GENERALES Y BINARIOS

Los eventos tienen todos los atributos disponibles del archivo de log. Por lo tanto, solo necesitas mirar el archivo de log para ver qué eventos están disponibles, pero recuerda: no todos los eventos tienen los mismos atributos.

Percona Server añade muchos atributos al log lento; ver http://www.percona.com/docs/wiki/patches:slow_extended para más información.

TCPDUMP

Error_no

ip

No_good_index_used
Sí o No si no existía un buen índice para la consulta (bandera establecida por el servidor).
