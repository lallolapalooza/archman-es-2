PRÓLOGO

Esta página del manual es parte del Manual del Programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

pthread_cond_broadcast, pthread_cond_signal — transmitir o señalar una condición

SINOPSIS

#include <pthread.h>
int pthread_cond_broadcast(pthread_cond_t *cond);
int pthread_cond_signal(pthread_cond_t *cond);

DESCRIPCIÓN

Estas funciones desbloquearán hilos bloqueados en una variable de condición.

La función pthread_cond_broadcast() desbloqueará todos los hilos actualmente bloqueados en la variable de condición especificada cond.

La función pthread_cond_signal() desbloqueará al menos uno de los hilos que están bloqueados en la variable de condición especificada cond (si hay hilos bloqueados en cond).

Si más de un hilo está bloqueado en una variable de condición, la política de programación determinará el orden en que se desbloquean los hilos. Cuando cada hilo desbloqueado como resultado de una pthread_cond_broadcast() o pthread_cond_signal() regrese de su llamada a pthread_cond_wait() o pthread_cond_timedwait(), el hilo poseerá el mutex con el que llamó a pthread_cond_wait() o pthread_cond_timedwait(). Los hilos que se desbloquean competirán por el mutex de acuerdo con la política de programación (si es aplicable), y como si cada uno hubiera llamado a pthread_mutex_lock().

Las funciones pthread_cond_broadcast() o pthread_cond_signal() pueden ser llamadas por un hilo, ya sea que posea actualmente el mutex que los hilos que llaman a pthread_cond_wait() o pthread_cond_timedwait() han asociado con la variable de condición durante sus esperas; sin embargo, si se requiere un comportamiento de programación predecible, ese mutex debe estar bloqueado por el hilo que llama a pthread_cond_broadcast() o pthread_cond_signal().

Las funciones pthread_cond_broadcast() y pthread_cond_signal() no tendrán ningún efecto si no hay hilos actualmente bloqueados en cond.

El comportamiento no está definido si el valor especificado por el argumento cond a pthread_cond_broadcast() o pthread_cond_signal() no se refiere a una variable de condición inicializada.

VALOR DE RETORNO

Si tiene éxito, las funciones pthread_cond_broadcast() y pthread_cond_signal() devolverán cero; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

Estas funciones no devolverán un código de error de [EINTR].

Las siguientes secciones son informativas.

EJEMPLOS

Ninguno.

USO DE LA APLICACIÓN

La función pthread_cond_broadcast() se utiliza siempre que el estado de la variable compartida ha sido modificado de manera que más de un hilo puede continuar con su tarea. Considere un problema de un solo productor/múltiples consumidores, donde el productor puede insertar varios elementos en una lista a la que acceden los consumidores uno a la vez. Al llamar a la función pthread_cond_broadcast(), el productor notificaría a todos los consumidores que pudieran estar esperando, y por lo tanto la aplicación recibiría más rendimiento en un multiprocesador. Además, pthread_cond_broadcast() facilita la implementación de un bloqueo de lectura-escritura. La función pthread_cond_broadcast() es necesaria para despertar a todos los lectores en espera cuando un escritor libera su bloqueo. Finalmente, el algoritmo de confirmación en dos fases puede usar esta función de transmisión para notificar a todos los clientes de una confirmación de transacción inminente.

No es seguro usar la función pthread_cond_signal() en un manejador de señales que se invoca de forma asíncrona. Incluso si fuera seguro, todavía existiría una condición de carrera entre la prueba de la condición booleana pthread_cond_wait() que no podría eliminarse de manera eficiente.

Por lo tanto, los mutex y las variables de condición no son adecuados para liberar un hilo en espera enviando una señal desde código que se ejecuta en un manejador de señales.

FUNDAMENTO

Si una implementación detecta que el valor especificado por el argumento cond a pthread_cond_broadcast() o pthread_cond_signal() no se refiere a una variable de condición inicializada, se recomienda que la función falle y reporte un error [EINVAL].

Múltiples Despertares por Señal de Condición

En un multiprocesador, puede ser imposible para una implementación de pthread_cond_signal() evitar el desbloqueo de más de un hilo bloqueado en una variable de condición. Por ejemplo, considere la siguiente implementación parcial de pthread_cond_wait() y pthread_cond_signal(), ejecutada por dos hilos en el orden dado. Un hilo intenta esperar en la variable de condición, otro está ejecutando concurrentemente pthread_cond_signal(), mientras que un tercer hilo ya está esperando.

pthread_cond_wait(mutex, cond):
    value = cond->value; /* 1 */
    pthread_mutex_unlock(mutex); /* 2 */
    pthread_mutex_lock(cond->mutex); /* 10 */
    if (value == cond->value) { /* 11 */
        me->next_cond = cond->waiter;
        cond->waiter = me;
        pthread_mutex_unlock(cond->mutex);
        unable_to_run(me);
    } else
        pthread_mutex_unlock(cond->mutex); /* 12 */
    pthread_mutex_lock(mutex); /* 13 */
pthread_cond_signal(cond):
    pthread_mutex_lock(cond->mutex); /* 3 */
    cond->value++; /* 4 */
    if (cond->waiter) { /* 5 */
        sleeper = cond->waiter; /* 6 */
        cond->waiter = sleeper->next_cond; /* 7 */
        able_to_run(sleeper); /* 8 */
    }
    pthread_mutex_unlock(cond->mutex); /* 9 */

El efecto es que más de un hilo puede regresar de su llamada a pthread_cond_wait() o pthread_cond_timedwait() como resultado de una llamada a pthread_cond_signal(). Este efecto se llama ``despertar espurio''. Tenga en cuenta que la situación se autocorrige en el sentido de que el número de hilos que se despiertan de esta manera es finito; por ejemplo, el siguiente hilo en llamar a pthread_cond_wait() después de la secuencia de eventos anterior se bloqueará.

Si bien este problema podría resolverse, la pérdida de eficiencia para una condición marginal que ocurre solo en raras ocasiones es inaceptable, especialmente dado que de todos modos hay que verificar el predicado asociado con una variable de condición. Corregir este problema reduciría innecesariamente el grado de concurrencia en este bloque de construcción básico para todas las operaciones de sincronización de nivel superior.

Un beneficio adicional de permitir despertares espurios es que las aplicaciones se ven obligadas a codificar un bucle de prueba de predicado alrededor de la espera de condición. Esto también hace que la aplicación tolere transmisiones o señales de condición superfluas en la misma variable de condición que puedan estar codificadas en alguna otra parte de la aplicación. Las aplicaciones resultantes son, por lo tanto, más robustas. Por lo tanto, POSIX.1‐2008 documenta explícitamente que pueden ocurrir despertares espurios.

NAME

pthread_cond_broadcast, pthread_cond_signal — broadcast or signal a condition variable

SYNOPSIS

#include <pthread.h>

int pthread_cond_broadcast(pthread_cond_t *cond;

int pthread_cond_signal(pthread_cond_t *cond;

DESCRIPTION

The pthread_cond_broadcast() function shall unblock all threads currently blocked waiting on the condition variable referenced by cond. If any threads are unblocked, their corresponding pthread_cond_wait() or pthread_cond_timedwait() calls shall return.

The pthread_cond_signal() function shall unblock at least one of the threads currently blocked waiting on the condition variable referenced by cond. If no threads are blocked waiting on cond, the function shall have no effect.

When a condition wait is satisfied, the call to pthread_cond_wait() or pthread_cond_timedwait() shall return.

The condition variable shall be locked by the calling thread before calling pthread_cond_broadcast() or pthread_cond_signal(). The condition variable shall be unlocked when pthread_cond_wait() or pthread_cond_timedwait() returns.

The behaviour is undefined if the value specified by the cond argument does not refer to an initialised condition variable.

The behavior is undefined if any of the following conditions occur:

  • The value specified by the cond argument does not refer to an initialized condition variable.
  • The condition variable was destroyed by a call to pthread_cond_destroy() before this call.
  • The calling thread does not own the mutex that is associated with the condition variable.

RETURN VALUE

Upon successful completion, pthread_cond_broadcast() and pthread_cond_signal() shall return a value of 0.

Otherwise, on error, they shall return an error identifier.

ERRORS

The pthread_cond_broadcast() and pthread_cond_signal() functions shall fail if:

EINVAL
The value specified by the cond argument is invalid.

The pthread_cond_signal() function may fail if:

EDEADLK
A deadlock is detected.

In the case of pthread_cond_broadcast(), the return value EDEADLK is not specified.

APPLICATION USAGE

It is recommended that the condition variable and mutex be initialized using pthread_cond_init() and pthread_mutex_init(), respectively, before use.

If the condition variable is associated with a mutex that is not in the state PTHREAD_MUTEX_STALLED, the behaviour is undefined.

RATIONALE

The pthread_cond_broadcast() function is used to wake up all threads that are waiting on a condition variable. This is useful when a condition change might satisfy the needs of multiple threads. For example, if a resource becomes available and multiple threads are waiting for it, pthread_cond_broadcast() can be used to wake them all up so they can compete for the resource.

The pthread_cond_signal() function is used to wake up one thread that is waiting on a condition variable. This is useful when a condition change only satisfies the needs of a single thread, or when it is more efficient to wake up only one thread. For example, if a resource becomes available and only one thread can use it at a time, pthread_cond_signal() can be used to wake up a single waiting thread.

Both functions require the calling thread to own the mutex associated with the condition variable. This is because the condition variable operations are performed atomically with respect to the mutex. If the mutex were not locked, a race condition could occur where a thread might miss the condition signal or broadcast.
