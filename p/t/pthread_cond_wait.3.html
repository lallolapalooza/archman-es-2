pthread_cond_init(3) Manual de Funciones de Biblioteca pthread_cond_init(3)

NOMBRE

pthread_cond_init, pthread_cond_signal, pthread_cond_broadcast, pthread_cond_wait, pthread_cond_timedwait, pthread_cond_destroy - operaciones en condiciones

SINOPSIS

#include <pthread.h>
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
int pthread_cond_init(pthread_cond_t *cond,
                      pthread_condattr_t *cond_attr);
int pthread_cond_signal(pthread_cond_t *cond);
int pthread_cond_broadcast(pthread_cond_t *cond);
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_timedwait(pthread_cond_t *cond, pthread_mutex_t *mutex,
                      const struct timespec *abstime);
int pthread_cond_destroy(pthread_cond_t *cond);

DESCRIPCIÓN

Una condición (abreviatura de "variable de condición") es un dispositivo de sincronización que permite a los hilos suspender su ejecución y ceder los procesadores hasta que se cumpla algún predicado sobre datos compartidos. Las operaciones básicas sobre condiciones son: señalizar la condición (cuando el predicado se vuelve verdadero) y esperar la condición, suspendiendo la ejecución del hilo hasta que otro hilo señale la condición.

Una variable de condición siempre debe estar asociada a un mutex, para evitar la condición de carrera en la que un hilo se prepara para esperar en una variable de condición y otro hilo la señala justo antes de que el primer hilo espere realmente en ella.

pthread_cond_init() inicializa la variable de condición cond, utilizando los atributos de condición especificados en cond_attr, o atributos predeterminados si cond_attr es NULL. La implementación de LinuxThreads no admite atributos para las condiciones, por lo tanto, el parámetro cond_attr se ignora en realidad.

Las variables de tipo pthread_cond_t también se pueden inicializar estáticamente, utilizando la constante PTHREAD_COND_INITIALIZER.

pthread_cond_signal() reinicia uno de los hilos que están esperando en la variable de condición cond. Si no hay hilos esperando en cond, no ocurre nada. Si varios hilos están esperando en cond, se reinicia exactamente uno, pero no se especifica cuál.

pthread_cond_broadcast() reinicia todos los hilos que están esperando en la variable de condición cond. No ocurre nada si no hay hilos esperando en cond.

pthread_cond_wait() desbloquea atómicamente el mutex (según pthread_unlock_mutex()) y espera a que la variable de condición cond sea señalizada. La ejecución del hilo se suspende y no consume ningún tiempo de CPU hasta que la variable de condición sea señalizada. El mutex debe estar bloqueado por el hilo que llama al entrar en pthread_cond_wait(). Antes de regresar al hilo que llama, pthread_cond_wait() vuelve a adquirir el mutex (según pthread_mutex_lock()).

El desbloqueo del mutex y la espera en la variable de condición se realizan de forma atómica. Por lo tanto, si todos los hilos adquieren siempre el mutex antes de señalar la condición, esto garantiza que la condición no pueda ser señalizada (y por lo tanto ignorada) entre el momento en que un hilo bloquea el mutex y el momento en que espera en la variable de condición. Véase ADVERTENCIAS más abajo.

pthread_cond_timedwait() desbloquea atómicamente el mutex y espera en cond, como lo hace pthread_cond_wait(), pero también limita la duración de la espera. Si cond no ha sido señalizado dentro del tiempo especificado por abstime, el mutex mutex se vuelve a adquirir y pthread_cond_timedwait() devuelve el error ETIMEDOUT. El parámetro abstime especifica un tiempo absoluto, con el mismo origen que time(2) y gettimeofday(2): un abstime de 0 corresponde a las 00:00:00 GMT, 1 de enero de 1970.

pthread_cond_destroy() destruye una variable de condición, liberando los recursos que pueda tener. Ningún hilo debe estar esperando en la variable de condición al entrar en pthread_cond_destroy(). En la implementación de LinuxThreads, no hay recursos asociados a las variables de condición, por lo que pthread_cond_destroy() en realidad no hace nada excepto comprobar que la condición no tiene hilos esperando.

CANCELACIÓN

pthread_cond_wait() y pthread_cond_timedwait() son puntos de cancelación. Si un hilo es cancelado mientras está suspendido en una de estas funciones, el hilo reanuda inmediatamente su ejecución, luego vuelve a bloquear el mutex argumento de pthread_cond_wait() y pthread_cond_timedwait(), y finalmente ejecuta la cancelación. Por consiguiente, se garantiza que los manejadores de limpieza tendrán el mutex bloqueado cuando sean llamados.

SEGURIDAD SEÑAL ASÍNCRONA

Las funciones de condición no son seguras para señales asíncronas y no deben llamarse desde un manejador de señales. En particular, llamar a pthread_cond_signal() o pthread_cond_broadcast() desde un manejador de señales puede provocar un interbloqueo del hilo que llama.

VALOR DE RETORNO

Todas las funciones de variables de condición devuelven 0 en caso de éxito y un código de error distinto de cero en caso de error.

ERRORES

pthread_cond_init(), pthread_cond_signal(), pthread_cond_broadcast() y pthread_cond_wait() nunca devuelven un código de error.

La función pthread_cond_timedwait() devuelve los siguientes códigos de error en caso de error:

ETIMEDOUT
La variable de condición no fue señalizada hasta el tiempo de espera especificado por abstime.

La función pthread_cond_destroy() devuelve el siguiente código de error en caso de error:

EBUSY
Algunos hilos están esperando actualmente en cond.

VER TAMBIÉN

pthread_condattr_init(3), pthread_mutex_lock(3), pthread_mutex_unlock(3), gettimeofday(2), nanosleep(2).

ADVERTENCIAS

La implementación de las funciones proporcionadas hasta glibc 2.25 utilizaba un bloqueo de datos interno. Este bloqueo no admitía la herencia de prioridades y estaba sujeto a inversión de prioridades ilimitada, visible en un sistema de tiempo real.

Después de la reescritura de la implementación en glibc 2.25, el uso del bloqueo interno cambió. El bloqueo interno siempre lo adquieren las funciones de señalización pthread_cond_signal() y pthread_cond_broadcast(). La función de espera adquiere el bloqueo si el proceso de espera fue interrumpido. La interrupción puede ser causada, por ejemplo, por un tiempo de espera especificado, y se denota con el valor de error ETIMEDOUTA, o por una señal recibida, que se denota con el valor de error EINTR.

EJEMPLO

Considere dos variables compartidas x e y, protegidas por el mutex mut, y una variable de condición cond que debe ser señalizada cuando x sea mayor que y.

int x,y;
pthread_mutex_t mut = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;

Esperar hasta que x sea mayor que y se realiza de la siguiente manera:

pthread_mutex_lock(&mut);
while (x <= y) {
        pthread_cond_wait(&cond, &mut);
}
/* operar sobre x e y */
pthread_mutex_unlock(&mut);

Las modificaciones en x e y que pueden hacer que x sea mayor que y deben señalar la condición si es necesario:

pthread_mutex_lock(&mut);
/* modificar x e y */
if (x > y) pthread_cond_broadcast(&cond);
pthread_mutex_unlock(&mut);

Para esperar a que x sea mayor que y con un tiempo de espera de 5 segundos, haga:

struct timeval now;
struct timespec timeout;
int retcode;
pthread_mutex_lock(&mut);
gettimeofday(&now);

timeout.tv_nsec = now.tv_usec * 1000;
retcode = 0;
while (x <= y && retcode != ETIMEDOUT) {
        retcode = pthread_cond_timedwait(&cond, &mut, &timeout);

} else {
        /* operar con x e y */
}
