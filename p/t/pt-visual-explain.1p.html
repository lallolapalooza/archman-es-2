NOMBRE

pt-visual-explain - Formatea la salida de EXPLAIN como un árbol.

SINOPSIS

Uso: pt-visual-explain [OPCIONES] [ARCHIVOS]

pt-visual-explain transforma la salida de EXPLAIN en una representación de árbol del plan de consulta. Si se proporciona un ARCHIVO, la entrada se lee de los archivos. Sin ARCHIVO, o cuando ARCHIVO es -, lee la entrada estándar.

Ejemplos:

pt-visual-explain <archivo_que_contiene_salida_explain>
pt-visual-explain -c <archivo_que_contiene_consulta>
mysql -e "explain select * from mysql.user" | pt-visual-explain

RIESGOS

Percona Toolkit es maduro, probado en el mundo real y bien probado, pero todas las herramientas de bases de datos pueden representar un riesgo para el sistema y el servidor de la base de datos. Antes de usar esta herramienta, por favor:

  • Lea la documentación de la herramienta
  • Revise los "BUGS" conocidos de la herramienta
  • Pruebe la herramienta en un servidor no productivo
  • Haga una copia de seguridad de su servidor de producción y verifique las copias de seguridad

DESCRIPCIÓN

pt-visual-explain realiza ingeniería inversa de la salida EXPLAIN de MySQL en un plan de ejecución de consulta, que luego formatea como un árbol profundo-izquierdo -- la misma forma en que el plan se representa dentro de MySQL. Es posible hacerlo a mano, o leer la salida de EXPLAIN directamente, pero requiere paciencia y experiencia. A muchas personas les resulta más comprensible una representación de árbol.

Puede canalizar la entrada a pt-visual-explain o especificar un nombre de archivo en la línea de comandos, incluido el nombre de archivo mágico '-', que leerá desde la entrada estándar. Puede hacer dos cosas con la entrada: analizarla en busca de algo que parezca una salida EXPLAIN, o conectarse a una instancia de MySQL y ejecutar EXPLAIN sobre la entrada.

Al analizar su entrada, pt-visual-explain entiende tres formatos: tabular como el que se muestra en el cliente de línea de comandos de mysql, vertical como el creado al usar el terminador de línea \G en el cliente de línea de comandos de mysql, y separado por tabulaciones. Ignora cualquier línea que no sepa cómo analizar.

Al ejecutar la entrada, pt-visual-explain reemplaza todo en la entrada hasta la primera palabra clave SELECT con 'EXPLAIN SELECT,' y luego ejecuta el resultado. Debe especificar "--connect" para ejecutar la entrada como una consulta.

De cualquier manera, construye un árbol a partir del conjunto de resultados y lo imprime en la salida estándar. Para la siguiente consulta,

select * from sakila.film_actor join sakila.film using(film_id);

pt-visual-explain genera este plan de consulta:

JOIN
+- Bookmark lookup
|  +- Table
|  |  table          film_actor
|  |  possible_keys  idx_fk_film_id
|  +- Index lookup
|     key            film_actor->idx_fk_film_id
|     possible_keys  idx_fk_film_id
|     key_len        2
|     ref            sakila.film.film_id
|     rows           2
+- Table scan
   rows           952
   +- Table
      table          film
      possible_keys  PRIMARY

El plan de consulta es profundo-izquierdo, búsqueda en profundidad, y la raíz del árbol es el nodo de salida -- el último paso en el plan de ejecución. En otras palabras, léalo de esta manera:

1.
Escanee la tabla 'film', que accede a un estimado de 952 filas.
2.
Por cada fila, encuentre filas coincidentes realizando una búsqueda de índice en el índice film_actor->idx_fk_film_id con el valor de sakila.film.film_id, luego una búsqueda de marcador en la tabla film_actor.

Para más información sobre cómo leer la salida de EXPLAIN, por favor consulte http://dev.mysql.com/doc/en/explain.html.

MÓDULOS

Este programa es en realidad un módulo ejecutable, no solo un script Perl ordinario. De hecho, hay dos módulos incrustados en él. Esto facilita las pruebas unitarias, pero también le permite usar la funcionalidad de análisis y construcción de árboles si lo desea.

El paquete ExplainParser acepta una cadena y analiza lo que considera que parece una salida EXPLAIN de ella. La sinopsis es la siguiente:

require "pt-visual-explain";
my $p    = ExplainParser->new();
my $rows = $p->parse("some text");
# $rows es un arrayref de hashrefs.

El paquete ExplainTree acepta un conjunto de filas y las convierte en un árbol. Para mayor comodidad, también puede delegar a ExplainParser y analizar texto por usted. Aquí está la sinopsis:

require "pt-visual-explain";
my $e      = ExplainTree->new();
my $tree   = $e->parse("some text", \%options);
my $output = $e->pretty_print($tree);
print $tree;

ALGORITMO

Esta sección explica el algoritmo que convierte EXPLAIN en un árbol. Puede que le interese leer esto si quiere entender EXPLAIN más a fondo, o intentar averiguar cómo funciona esto, pero de lo contrario, esta sección probablemente no hará su vida más rica.

El árbol se puede construir examinando las columnas id, select_type y table de cada fila.

La columna id es el número secuencial de la selección. Esto no indica anidamiento; simplemente proviene de contar SELECT desde la izquierda de la declaración SQL. Es como capturar paréntesis en una expresión regular.

Si dos filas adyacentes tienen el mismo valor de id, se unen con el método estándar de multijunção de barrido único.

La columna select_type indica a) que se ha abierto un nuevo subámbito b) qué tipo de relación tiene la fila con la fila anterior c) qué tipo de operación representa la fila.

  • SIMPLE significa que no hay subconsultas ni uniones en toda la consulta.
  • PRIMARY significa que las hay, pero esta es la SELECT más externa.
  • [DEPENDENT] UNION significa que este resultado se une (UNION) con el resultado anterior (no fila; un resultado puede abarcar más de una fila).
  • UNION RESULT termina un conjunto de resultados UNIONados.
  • [DEPENDENT|UNCACHEABLE] SUBQUERY significa que se está abriendo un nuevo subámbito. Este es el tipo de subconsulta que ocurre en una cláusula WHERE, lista SELECT o similar; no devuelve una llamada "tabla derivada".
  • DERIVED es una subconsulta en la cláusula FROM.

Las tablas que se unen tienen el mismo select_type. Por ejemplo, si une tres tablas dentro de una subconsulta dependiente, todas dirán lo mismo: DEPENDENT SUBQUERY.

La columna table generalmente especifica el nombre de la tabla o el alias, pero también puede decir <derivedN> o <unionN,N...N>. Si dice <derivedN>, la fila representa un acceso a la tabla temporal que contiene el resultado de la subconsulta cuyo id es N. Si dice <unionN,..N> es lo mismo, pero se refiere a los resultados que une.

Finalmente, el orden importa. Si el id de una fila es menor que el de la anterior, significa que es dependiente de algo distinto a la anterior. Por ejemplo,

explain select
   (select 1 from sakila.film),
   (select 2 from sakila.film_actor),
   (select 3 from sakila.actor);
| id | select_type | table      |
+----+-------------+------------+
|  1 | PRIMARY     | NULL       |
|  4 | SUBQUERY    | actor      |
|  3 | SUBQUERY    | film_actor |
|  2 | SUBQUERY    | film       |

Si los resultados estuvieran en orden 2-3-4, significaría que 3 es una subconsulta de 2, 4 es una subconsulta de 3. Tal como está, esto significa que 4 es una subconsulta de la fila reciente anterior más cercana con un id menor, que es 1. Lo mismo para 3 y 2.

Esta estructura es difícil de construir programáticamente en un árbol por la misma razón por la que es difícil de entender por inspección: hay referencias tanto hacia adelante como hacia atrás. <derivedN> es una referencia hacia adelante a selectN, mientras que <unionM,N> es una referencia hacia atrás a selectM y selectN. Eso hace que la recursión y otros algoritmos de construcción de árboles sean difíciles de acertar (NOTA: después de la implementación, ahora veo cómo sería posible lidiar con referencias tanto hacia adelante como hacia atrás, pero no tengo motivación para cambiar algo que funciona). Considere lo siguiente:

select * from (
   select 1 from sakila.actor as actor_1
   union
   select 1 from sakila.actor as actor_2
) as der_1
union
select * from (
   select 1 from sakila.actor as actor_3
   union all
   select 1 from sakila.actor as actor_4
) as der_2;
| id   | select_type  | table      |
+------+--------------+------------+
|  1   | PRIMARY      | <derived2> |
|  2   | DERIVED      | actor_1    |
|  3   | UNION        | actor_2    |
| NULL | UNION RESULT | <union2,3> |
|  4   | UNION        | <derived5> |
|  5   | DERIVED      | actor_3    |
|  6   | UNION        | actor_4    |
| NULL | UNION RESULT | <union5,6> |
| NULL | UNION RESULT | <union1,4> |

El objetivo es hacer que los planes de ejecución sean fáciles de entender. 'pt-visual-explain' lee la salida de 'EXPLAIN' para una consulta SQL, y la convierte en una representación de árbol de texto. Esto hace que sea mucho más fácil para los humanos entender cómo MySQL ejecutará una consulta. El script se basa en la suposición de que MySQL genera la salida de 'EXPLAIN' en un orden que puede usarse para deducir la estructura de árbol. El orden de las filas en la salida de 'EXPLAIN' es importante. Se supone que las filas se presentan en un orden que se parece a un recorrido en profundidad de un árbol, donde cada nodo hijo tiene un ID de fila mayor que su padre. La excepción principal a esto es el tipo de consulta UNION. Cuando el tipo de consulta es UNION, la salida de EXPLAIN puede parecer un poco confusa. Aquí hay un ejemplo: Se espera que los IDs de fila se presenten en orden ascendente dentro de un ámbito determinado. Sin embargo, a veces hay una reordenación. Además, aunque hace que sea más fácil de leer, no facilita la manipulación programática; así que está bien dejarlos numerados como están. El objetivo de la reordenación es facilitar la determinación de qué filas son hijas de qué filas en el plan de ejecución. Dada la lista reordenada y alguna fila cuya tabla es o , es fácil encontrar el comienzo del segmento de filas que deben ser nodos hijos en el árbol: solo busca la primera fila cuyo ID sea el mismo que el primer número en la tabla. La siguiente pregunta es cómo encontrar la última fila que debe ser un nodo hijo de un UNION o DERIVED. Comenzaremos con DERIVED, porque la solución hace que UNION sea fácil. Considere cómo MySQL numera las SELECT secuencialmente según su posición en el SQL, de izquierda a derecha. Dado que una tabla DERIVED encierra todo dentro de un ámbito, que se convierte en una tabla temporal, solo hay dos cosas a tener en cuenta: sus subconsultas hijas y uniones (si las hay), y sus siguientes hermanos en el ámbito que lo encierra. Sus hijos tendrán todos un id mayor que él, por definición, por lo que cualquier fila posterior con un id menor termina el ámbito. Aquí hay un ejemplo. La tabla derivada intermedia aquí tiene una subconsulta y una UNION para hacerla un poco más compleja para el ejemplo. explain select 1 from ( select film_id from sakila.film limit 1 ) as der_1 join ( select film_id, actor_id, (select count(*) from sakila.rental) as r from sakila.film_actor limit 1 union all select 1, 1, 1 from sakila.film_actor as dummy ) as der_2 using (film_id) join ( select actor_id from sakila.actor limit 1 ) as der_3 using (actor_id); Aquí está la salida de EXPLAIN: | id | select_type | table | | 1 | PRIMARY | | | 1 | PRIMARY | | | 1 | PRIMARY | | | 6 | DERIVED | actor | | 3 | DERIVED | film_actor | | 4 | SUBQUERY | rental | | 5 | UNION | dummy | | NULL | UNION RESULT | | | 2 | DERIVED | film | Los hermanos tienen todos el id 1, y el intermedio que nos importa es derived3. (Note que MySQL no los ejecuta en el orden en que se definen, lo cual está bien). Ahora note que MySQL imprime las filas en el orden inverso en que se definieron las subconsultas: 6, 3, 2. Siempre parece hacer esto, y puede haber otros métodos para encontrar los límites del ámbito, incluido buscar el límite inferior del siguiente hermano mayor, pero esta es una heurística suficientemente buena. Estamos obligados a confiar en ella para subconsultas no-DERIVED, así que confiamos en ella aquí también. Por lo tanto, decidimos que todo lo mayor o igual a 3 pertenece al ámbito DERIVED. La regla para UNION es simple: consumen todo el ámbito envolvente, y para encontrar las partes componentes de cada uno, encuentras el comienzo de cada parte como se hace referencia en la definición de , y su final es bien justo antes del siguiente, o si es la última parte, el final es el final del ámbito. Esto solo es simple porque UNION consume todo el ámbito, que es bien la declaración completa, o el ámbito de una tabla DERIVED. Esto se debe a que un UNION no puede ser un hermano de otro UNION o de una tabla, sea DERIVED o no. (Intenta escribir una declaración así si no lo ves intuitivamente). Por lo tanto, puedes simplemente encontrar los límites del ámbito envolvente, y el resto es fácil. Es un ID mayor que 1, por lo que es una subconsulta, junto con cada otra fila cuyo ID sea mayor que 2. * Dentro de este ámbito, ver 2 y 2 y UNIRLOS. Ver 4. UNION es un poco más complicado que simplemente "todo el ámbito es un UNION", porque el UNION podría estar dentro de un ámbito envolvente que solo está indicado por el primer elemento dentro del UNION. Solo hay tres tipos de ámbitos envolventes: UNION, DERIVED y SUBQUERY. Un UNION no puede envolver un UNION, y un DERIVED tiene sus propios "marcadores de ámbito", pero una SUBQUERY en versiones anteriores podía envolver completamente un UNION, como este extraño ejemplo en la tabla vacía t1: explain select * from t1 where not exists( (select t11.i from t1 t11) union (select t12.i from t1 t12)); | id | select_type | table | Extra | +------+--------------+------------+--------------------------------+ | 1 | PRIMARY | t1 | const row not found | | 2 | SUBQUERY | NULL | No tables used | | 3 | SUBQUERY | NULL | no matching row in const table | | 4 | UNION | t12 | const row not found | | NULL | UNION RESULT | | | Las referencias inversas del UNION podrían hacer parecer que el UNION envuelve la subconsulta, pero estudiar la consulta deja claro que este no es el caso. Así que cuando la primera fila de un UNION dice SUBQUERY, es este caso especial que no podemos repetir a partir de MySQL 5.7. Con este conocimiento, es posible usar recursión para convertir la relación padre-hijo entre todas las filas en un árbol que representa el plan de ejecución. MySQL imprime las filas en orden de ejecución, incluso las referencias hacia adelante y hacia atrás. En cualquier ámbito dado, las filas se procesan como un árbol profundo izquierdo. MySQL no hace planes de ejecución "dispersos". Comienza con una tabla, encuentra una fila coincidente en la siguiente tabla, y continúa hasta la última tabla, cuando emite una fila. Cuando se agota, retrocede hasta que pueda encontrar la siguiente fila y repite. Hay sutilezas, por supuesto, pero este es el plan básico. Es por esto que MySQL transforma todos los RIGHT OUTER JOINs en LEFT OUTER JOINs y no puede hacer FULL OUTER JOIN. Esto significa que en cualquier ámbito dado, por ejemplo: | id | select_type | table | | 1 | SIMPLE | tbl1 | | 1 | SIMPLE | tbl2 | | 1 | SIMPLE | tbl3 | El plan de ejecución se parece a un recorrido en profundidad de este árbol: JOIN / \ JOIN tbl3 / \ tbl1 tbl2 El JOIN podría no ser un JOIN. Podría ser una subconsulta, por ejemplo. Esto proviene del tipo de columna de EXPLAIN. La documentación dice que es un "tipo de join", pero "tipo de acceso" puede ser más preciso, porque es "cómo MySQL accede a las filas". pt-visual-explain decora el árbol significativamente más que solo convertir las filas en nodos. Cada nodo puede obtener una serie de transformaciones que lo convierten en un subárbol de más de un nodo. Por ejemplo, un escaneo de índice no marcado con 'Using index' debe hacer una búsqueda de marcador en las filas de la tabla; eso es un subárbol de tres nodos. OPTIONS

--format
type: string; default: tree

Establece el formato de salida.

El valor predeterminado es un árbol conciso con formato bonito. Los valores válidos son:

Valor  Significado
=====  ================================================
tree   Árbol conciso con formato bonito.
dump   Salida de Data::Dumper (ver Data::Dumper para más detalles).
--help
Muestra la ayuda y sale.
--host
forma corta: -h; type: string

Conecta al host.

--mysql_ssl
forma corta: -s; type: int

Crea una conexión MySQL SSL.

--password
forma corta: -p; type: string

Contraseña a usar al conectar. Si la contraseña contiene comas, deben escaparse con una barra invertida: "exam\,ple"

--pid
type: string

Crea el archivo PID dado. La herramienta no se iniciará si el archivo PID ya existe y el PID que contiene es diferente al PID actual. Sin embargo, si el archivo PID existe y el PID que contiene ya no se está ejecutando, la herramienta sobrescribirá el archivo PID con el PID actual. El archivo PID se elimina automáticamente cuando la herramienta sale.

--port
forma corta: -P; type: int

Número de puerto a usar para la conexión.

--set-vars
type: Array

Establece las variables de MySQL en esta lista separada por comas de pares de "variable=valor".

Por defecto, la herramienta establece:

wait_timeout=10000

Las variables especificadas en la línea de comandos anulan estos valores predeterminados. Por ejemplo, especificar "--set-vars wait_timeout=500" anula el valor predeterminado de 10000.

La herramienta imprime una advertencia y continúa si una variable no se puede establecer.

--socket
forma corta: -S; type: string

Archivo de socket a usar para la conexión.

--user
forma corta: -u; type: string

Usuario para iniciar sesión si no es el usuario actual.

--version
Muestra la versión y sale.

AMBIENTE

La variable de entorno "PTDEBUG" habilita la salida de depuración detallada a STDERR. Para habilitar la depuración y capturar toda la salida en un archivo, ejecute la herramienta como:

PTDEBUG=1 pt-visual-explain ... > ARCHIVO 2>&1

Tenga cuidado: la salida de depuración es voluminosa y puede generar varios megabytes de salida.

ATENCIÓN

El uso de <PTDEBUG> puede exponer contraseñas. Cuando la depuración está habilitada, todos los parámetros de la línea de comandos se muestran en la salida.

  • Archivos de entrada (archivos de registro/volcado/configuración, etc.)

Si es posible, incluya la salida de depuración ejecutando la herramienta con "PTDEBUG"; consulte "AMBIENTE".
