PRÓLOGO

NOMBRE

pthread_cond_timedwait, pthread_cond_wait — esperar en una condición

SINOPSIS

#include <pthread.h>
int pthread_cond_timedwait(pthread_cond_t *restrict cond,
    pthread_mutex_t *restrict mutex,
    const struct timespec *restrict abstime);
int pthread_cond_wait(pthread_cond_t *restrict cond,
    pthread_mutex_t *restrict mutex);

DESCRIPCIÓN

Las funciones pthread_cond_timedwait() y pthread_cond_wait() se bloquearán en una variable de condición. La aplicación deberá asegurarse de que estas funciones se llamen con mutex bloqueado por el hilo que realiza la llamada; de lo contrario, se producirá un error (para mutexes de error y robustos) o un comportamiento indefinido (para otros mutexes).

Estas funciones liberan atómicamente mutex y hacen que el hilo que llama se bloquee en la variable de condición cond; atómicamente aquí significa "atómico con respecto al acceso de otro hilo al mutex y luego a la variable de condición". Es decir, si otro hilo puede adquirir el mutex después de que el hilo a punto de bloquearse lo haya liberado, una llamada posterior a pthread_cond_broadcast() o pthread_cond_signal() en ese hilo se comportará como si se hubiera emitido después de que el hilo a punto de bloquearse se hubiera bloqueado.

Al regresar con éxito, el mutex se habrá bloqueado y será propiedad del hilo que llama. Si mutex es un mutex robusto donde un propietario terminó mientras mantenía el bloqueo y el estado es recuperable, el mutex se adquirirá incluso si la función devuelve un código de error.

Al utilizar variables de condición, siempre hay un predicado booleano que involucra variables compartidas asociadas con cada espera de condición que es verdadero si el hilo debe proceder. Pueden ocurrir despertares espurios de las funciones pthread_cond_timedwait() o pthread_cond_wait(). Dado que el regreso de pthread_cond_timedwait() o pthread_cond_wait() no implica nada sobre el valor de este predicado, el predicado debe ser reevaluado tras dicho regreso.

Cuando un hilo espera en una variable de condición, habiendo especificado un mutex particular para la operación pthread_cond_timedwait() o pthread_cond_wait(), se forma una unión dinámica entre ese mutex y la variable de condición que permanece vigente mientras al menos un hilo esté bloqueado en la variable de condición. Durante este tiempo, el efecto de un intento por parte de cualquier hilo de esperar en esa variable de condición usando un mutex diferente es indefinido. Una vez que todos los hilos en espera hayan sido desbloqueados (como por la operación pthread_cond_broadcast()), la próxima operación de espera en esa variable de condición formará una nueva unión dinámica con el mutex especificado por esa operación de espera. Incluso si la unión dinámica entre la variable de condición y el mutex puede eliminarse o reemplazarse entre el momento en que un hilo se desbloquea de una espera en la variable de condición y el momento en que regresa al llamador o comienza la limpieza de cancelación, el hilo desbloqueado siempre volverá a adquirir el mutex especificado en la llamada de espera de condición de la que regresa.

Una espera de condición (ya sea con tiempo o no) es un punto de cancelación. Cuando el tipo de cancelabilidad de un hilo se establece en PTHREAD_CANCEL_DEFERRED, un efecto secundario de actuar sobre una solicitud de cancelación mientras está en una espera de condición es que el mutex se (vuelve a) adquirir antes de llamar al primer manejador de limpieza de cancelación. El efecto es como si el hilo se desbloqueara, se le permitiera ejecutarse hasta el punto de regresar de la llamada a pthread_cond_timedwait() o pthread_cond_wait(), pero en ese punto se da cuenta de la solicitud de cancelación y, en lugar de regresar al llamador de pthread_cond_timedwait() o pthread_cond_wait(), inicia las actividades de cancelación del hilo, lo que incluye llamar a los manejadores de limpieza de cancelación.

Un hilo que ha sido desbloqueado porque ha sido cancelado mientras estaba bloqueado en una llamada a pthread_cond_timedwait() o pthread_cond_wait() no consumirá ninguna señal de condición que pueda dirigirse concurrentemente a la variable de condición si hay otros hilos bloqueados en la variable de condición.

La función pthread_cond_timedwait() será equivalente a pthread_cond_wait(), excepto que se devolverá un error si la hora absoluta especificada por abstime pasa (es decir, la hora del sistema es igual o excede abstime) antes de que la condición cond se señale o se difunda, o si la hora absoluta especificada por abstime ya ha pasado en el momento de la llamada. Cuando ocurren tales tiempos de espera, pthread_cond_timedwait() aún así liberará y volverá a adquirir el mutex referenciado por mutex, y puede consumir una señal de condición dirigida concurrentemente a la variable de condición.

La variable de condición tendrá un atributo de reloj que especifica el reloj que se utilizará para medir el tiempo especificado por el argumento abstime. La función pthread_cond_timedwait() es también un punto de cancelación.

Si se entrega una señal a un hilo que espera una variable de condición, al regresar del manejador de señales, el hilo reanuda la espera de la variable de condición como si no hubiera sido interrumpido, o regresará cero debido a un despertar espurio.

El comportamiento es indefinido si el valor especificado por el argumento cond o mutex en estas funciones no se refiere a una variable de condición inicializada o a un objeto mutex inicializado, respectivamente.

VALOR DE RETORNO

Excepto por [ETIMEDOUT], [ENOTRECOVERABLE] y [EOWNERDEAD], todas estas comprobaciones de error actuarán como si se hubieran realizado inmediatamente al principio del procesamiento de la función y provocarán un retorno de error, en efecto, antes de modificar el estado del mutex especificado por mutex o la variable de condición especificada por cond.

Al completarse con éxito, se devolverá el valor cero; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

Estas funciones fallarán si:

ENOTRECOVERABLE

El estado protegido por el mutex no es recuperable.
EOWNERDEAD

El mutex es un mutex robusto y el proceso que contiene el hilo propietario anterior terminó mientras mantenía el bloqueo del mutex. El bloqueo del mutex será adquirido por el hilo que llama y depende del nuevo propietario hacer que el estado sea consistente.
EPERM
El tipo de mutex es PTHREAD_MUTEX_ERRORCHECK o el mutex es un mutex robusto, y el hilo actual no posee el mutex.

La función pthread_cond_timedwait() fallará si:

ETIMEDOUT
El tiempo especificado por abstime en pthread_cond_timedwait() ha pasado.
EINVAL
El argumento abstime especificó un valor de nanosegundos menor que cero o mayor o igual a 1000 millones.

Estas funciones pueden fallar si:

EOWNERDEAD

El mutex es un mutex robusto y el hilo propietario anterior terminó mientras mantenía el bloqueo del mutex. El bloqueo del mutex será adquirido por el hilo que llama y depende del nuevo propietario hacer que el estado sea consistente.

Estas funciones no devolverán un código de error de [EINTR].

NAME

pthread_mutex_consistent, PTHREAD_MUTEX_CONSISTENT, PTHREAD_MUTEX_INCONSISTENT, PTHREAD_MUTEX_DETECT_INCONSISTENT - robust mutexes and inconsistent state detection

SYNOPSIS

#include <pthread.h>

int pthread_mutex_consistent(pthread_mutex_t *mutex);

DESCRIPTION

The pthread_mutex_consistent() function shall be used to mark the mutex object referred to by mutex as being in a consistent state.

The mutex attribute, PTHREAD_MUTEX_ROBUST, is provided for robust mutexes. When a thread terminates while holding a robust mutex, the mutex is marked as inconsistent. Any subsequent attempt by another thread to acquire the mutex that is protecting a currently inconsistent state is [EOWNERDEAD]. Applications that do not check the error returns, due to ruling out the possibility of such errors arising, should not use robust mutexes. If an application is supposed to work with normal and robust mutexes, it should check all return values for error conditions and if necessary take appropriate action.

RATIONALE

If an implementation detects that the value specified by the cond argument to pthread_cond_timedwait() or pthread_cond_wait() does not refer to an initialized condition variable, or detects that the value specified by the mutex argument to pthread_cond_timedwait() or pthread_cond_wait() does not refer to an initialized mutex object, it is recommended that the function should fail and report an [EINVAL] error.

Condition Wait Semantics

It is important to note that when pthread_cond_wait() and pthread_cond_timedwait() return without error, the associated predicate may still be false. Similarly, when pthread_cond_timedwait() returns with the timeout error, the associated predicate may be true due to an unavoidable race between the expiration of the timeout and the predicate state change.

The application needs to recheck the predicate on any return because it cannot be sure there is another thread waiting on the thread to handle the signal, and if there is not then the signal is lost. The burden is on the application to check the predicate.

Some implementations, particularly on a multi-processor, may sometimes cause multiple threads to wake up when the condition variable is signaled simultaneously on different processors.

In general, whenever a condition wait returns, the thread has to re-evaluate the predicate associated with the condition wait to determine whether it can safely proceed, should wait again, or should declare a timeout. A return from the wait does not imply that the associated predicate is either true or false.

It is thus recommended that a condition wait be enclosed in the equivalent of a ``while loop'' that checks the predicate.

Timed Wait Semantics

An absolute time measure was chosen for specifying the timeout parameter for two reasons. First, a relative time measure can be easily implemented on top of a function that specifies absolute time, but there is a race condition associated with specifying an absolute timeout on top of a function that specifies relative timeouts. For example, assume that clock_gettime() returns the current time and cond_relative_timed_wait() uses relative timeouts:

clock_gettime(CLOCK_REALTIME, &now)
reltime = sleep_til_this_absolute_time -now;
cond_relative_timed_wait(c, m, &reltime);

If the thread is preempted between the first statement and the last statement, the thread blocks for too long. Blocking, however, is irrelevant if an absolute timeout is used. An absolute timeout also need not be recomputed if it is used multiple times in a loop, such as that enclosing a condition wait.

For cases when the system clock is advanced discontinuously by an operator, it is expected that implementations process any timed wait expiring at an intervening time as if that time had actually occurred.

Cancellation and Condition Wait

A condition wait, whether timed or not, is a cancellation point. That is, the functions pthread_cond_wait() or pthread_cond_timedwait() are points where a pending (or concurrent) cancellation request is noticed. The reason for this is that an indefinite wait is possible at these points—whatever event is being waited for, even if the program is totally correct, might never occur; for example, some input data being awaited might never be sent. By making condition wait a cancellation point, the thread can be canceled and perform its cancellation cleanup handler even though it may be stuck in some indefinite wait.

A side-effect of acting on a cancellation request while a thread is blocked on a condition variable is to re-acquire the mutex before calling any of the cancellation cleanup handlers. This is done in order to ensure that the cancellation cleanup handler is executed in the same state as the critical code that lies both before and after the call to the condition wait function. This rule is also required when interfacing to POSIX threads from languages, such as Ada or C++, which may choose to map cancellation onto a language exception; this rule ensures that each exception handler guarding a critical section can always safely depend upon the fact that the associated mutex has already been locked regardless of exactly where within the critical section the exception was raised. Without this rule, there would not be a uniform rule that exception handlers could follow regarding the lock, and so coding would become very cumbersome.

Therefore, since some statement has to be made regarding the state of the lock when a cancellation is delivered during a wait, a definition has been chosen that makes application coding most convenient and error free.

When acting on a cancellation request while a thread is blocked on a condition variable, the implementation is required to ensure that the thread does not consume any condition signals directed at that condition variable if there are any other threads waiting on that condition variable. This rule is specified in order to avoid deadlock conditions that could occur if these two independent requests (one acting on a thread and the other acting on the condition variable) were not processed independently.

Performance of Mutexes and Condition Variables

Mutexes are expected to be locked only for a few instructions. This practice is almost automatically enforced by the desire of programmers to avoid long serial regions of execution (which would reduce total effective parallelism).

When using mutexes and condition variables, one tries to ensure that the usual case is to lock the mutex, access shared data, and unlock the mutex. Waiting on a condition variable should be a relatively rare situation. For example, when implementing a read-write lock, code that acquires a read-lock typically needs only to increment the count of readers (under mutual-exclusion) and return. The calling thread would actually wait on the condition variable only when there is already an active writer. So the efficiency of a synchronization operation is bounded by the cost of mutex lock/unlock and not by condition wait. Note that in the usual case there is no context switch.

This is not to say that the efficiency of condition waiting is unimportant. Since there needs to be at least one context switch per Ada rendezvous, the efficiency of waiting on a condition variable is important. The cost of waiting on a condition variable should be little more than the minimal cost for a context switch plus the time to unlock and lock the mutex.

Features of Mutexes and Condition Variables

It had been suggested that the mutex acquisition and release be decoupled from condition wait. This was rejected because it is the combined nature of the operation that, in fact, facilitates realtime implementations. Those implementations can atomically move a high-priority thread between the condition variable and the mutex in a manner that is transparent to the caller. This can prevent extra context switches and provide more deterministic acquisition of a mutex when the waiting thread is signaled. Thus, fairness and priority issues can be dealt with directly by the scheduling discipline. Furthermore, the current condition wait operation matches existing practice.

Scheduling Behavior of Mutexes and Condition Variables

Synchronization primitives that attempt to interfere with scheduling policy by specifying an ordering rule are considered undesirable. Threads waiting on mutexes and condition variables are selected to proceed in an order dependent upon the scheduling policy rather than in some fixed order (for example, FIFO or priority). Thus, the scheduling policy determines which thread(s) are awakened and allowed to proceed.

Timed Condition Wait

The pthread_cond_timedwait() function allows an application to give up waiting for a particular condition after a given amount of time. An example of its use follows:

(void) pthread_mutex_lock(&t.mn);
    t.waiters++;
    clock_gettime(CLOCK_REALTIME, &ts);
    ts.tv_sec += 5;
    rc = 0;
    while (! mypredicate(&t) && rc == 0)
        rc = pthread_cond_timedwait(&t.cond, &t.mn, &ts);
    t.waiters--;
    if (rc == 0 || mypredicate(&t))
        setmystate(&t);
(void) pthread_mutex_unlock(&t.mn);

By making the timeout parameter absolute, it does not need to be recomputed each time the program checks its blocking predicate. If the timeout was relative, it would have to be recomputed before each call. This would be especially difficult since such code would need to take into account the possibility of extra wakeups that result from extra broadcasts or signals on the condition variable that occur before either the predicate is true or the timeout is due.
