NOMBRE

pt-index-usage - Lee consultas de un registro y analiza cómo utilizan los índices.

SINOPSIS

Uso: pt-index-usage [OPCIONES] [ARCHIVOS]

pt-index-usage lee consultas de registros y analiza cómo utilizan los índices.

Analiza las consultas en slow.log e imprime informes:

pt-index-usage /ruta/a/slow.log --host localhost

Deshabilita informes y guarda resultados en la base de datos percona para análisis posterior:

pt-index-usage slow.log --no-report --save-results-database percona

RIESGOS

Percona Toolkit es maduro, probado en el mundo real y bien testeado, pero todas las herramientas de base de datos pueden suponer un riesgo para el sistema y el servidor de base de datos. Antes de usar esta herramienta, por favor:

  • Lee la documentación de la herramienta
  • Revisa los "BUGS" conocidos de la herramienta
  • Prueba la herramienta en un servidor no de producción
  • Haz una copia de seguridad de tu servidor de producción y verifica las copias de seguridad

DESCRIPCIÓN

Esta herramienta se conecta a un servidor de base de datos MySQL, lee un registro de consultas y utiliza EXPLAIN para preguntar a MySQL cómo utilizará cada consulta. Cuando termina, imprime un informe sobre los índices que las consultas no utilizaron.

El registro de consultas debe estar en el formato de registro de consultas lentas de MySQL. Si necesitas introducir un formato diferente, puedes usar pt-query-digest para traducir los formatos. Si no especificas un nombre de archivo, la herramienta lee desde STDIN.

La herramienta ejecuta dos etapas. En la primera etapa, la herramienta inventaría todas las tablas e índices de tu base de datos, para poder comparar los índices existentes con los que realmente fueron utilizados por las consultas en el registro. En la segunda etapa, ejecuta EXPLAIN en cada consulta del registro de consultas. Utiliza conexiones de base de datos separadas para inventariar las tablas y ejecutar EXPLAIN, por lo que abre dos conexiones a la base de datos.

Si una consulta no es un SELECT, intenta transformarla en una consulta SELECT aproximadamente equivalente para que pueda ser explicada. Este no es un proceso perfecto, pero es lo suficientemente bueno como para ser útil.

La herramienta omite el paso EXPLAIN para consultas que son duplicados exactos de las vistas anteriormente. Asume que la misma consulta generará el mismo plan EXPLAIN que lo hizo anteriormente (generalmente una suposición segura, y generalmente buena para el rendimiento), y simplemente incrementa el número de veces que se utilizaron los índices. Sin embargo, las consultas que tienen la misma huella digital pero diferentes sumas de verificación se volverán a explicar. Las consultas que tienen diferentes constantes literales pueden tener diferentes planes de ejecución, y esto es importante de medir.

Después de explicar la consulta, es necesario intentar mapear los alias en la consulta de vuelta a los nombres de tabla originales. Por ejemplo, considera el plan EXPLAIN para la siguiente consulta:

SELECT * FROM tbl1 AS foo;

La salida de EXPLAIN mostrará el acceso a la tabla "foo", y eso debe traducirse de nuevo a "tbl1". Este proceso implica un análisis complejo. Generalmente es muy preciso, pero existe la posibilidad de que no funcione correctamente. Si encuentras casos en los que falla, envía un informe de error y un caso de prueba reproducible.

Las consultas que no se pueden explicar harán que todas las consultas posteriores con la misma huella digital sean puestas en una lista negra. Esto es para reducir el trabajo que causan y evitar que continúen imprimiendo mensajes de error.

SALIDA

Después de leer todos los eventos en el registro, la herramienta imprime sentencias DROP para cada índice que no se utilizó. Omite los índices para tablas que nunca fueron accedidas por ninguna consulta en el registro, para evitar resultados falsos positivos.

Si no especificas "--quiet", la herramienta también emite advertencias sobre sentencias que no se pueden explicar y similares. Estas van a la salida de error estándar.

Los informes de progreso están habilitados por defecto (ver "--progress"). Estos también van a la salida de error estándar.

--save-results-database
tipo: DSN

Guardar resultados en tablas de esta base de datos. La información sobre índices, consultas, tablas y su uso se almacena en varias tablas en la base de datos especificada. Las tablas se crean automáticamente si no existen. Si la base de datos no existe, se puede crear automáticamente con "--create-save-results-database". pt-index-usage ejecuta sentencias INSERT para guardar los resultados. Por lo tanto, debe tener cuidado si utiliza esta función en un servidor de producción. Podría aumentar la carga o causar problemas si no desea que el servidor sea escrito, etc.

Después de una ejecución, puede consultar las tablas de uso para responder varias preguntas sobre el uso de índices. Las tablas tienen las siguientes definiciones CREATE TABLE:

MAGIC_create_indexes:

CREATE TABLE IF NOT EXISTS indexes (
  db           VARCHAR(64) NOT NULL,
  tbl          VARCHAR(64) NOT NULL,
  idx          VARCHAR(64) NOT NULL,
  cnt          BIGINT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY  (db, tbl, idx)
)

MAGIC_create_queries:

CREATE TABLE IF NOT EXISTS queries (
  query_id     CHAR(32) NOT NULL,
  fingerprint  TEXT NOT NULL,
  sample       TEXT NOT NULL,
  PRIMARY KEY  (query_id)
)

MAGIC_create_tables:

CREATE TABLE IF NOT EXISTS tables (
  db           VARCHAR(64) NOT NULL,
  tbl          VARCHAR(64) NOT NULL,
  cnt          BIGINT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY  (db, tbl)
)

MAGIC_create_index_usage:

CREATE TABLE IF NOT EXISTS index_usage (
  query_id      CHAR(32) NOT NULL,
  db            VARCHAR(64) NOT NULL,
  tbl           VARCHAR(64) NOT NULL,
  idx           VARCHAR(64) NOT NULL,
  cnt           BIGINT UNSIGNED NOT NULL DEFAULT 1,
  UNIQUE INDEX  (query_id, db, tbl, idx)
)

MAGIC_create_index_alternatives:

CREATE TABLE IF NOT EXISTS index_alternatives (
  query_id      CHAR(32) NOT NULL,        -- Esta consulta utilizó
  db            VARCHAR(64) NOT NULL,     -- este índice, pero...
  tbl           VARCHAR(64) NOT NULL,     --
  idx           VARCHAR(64) NOT NULL,     --
  alt_idx       VARCHAR(64) NOT NULL,     -- fue una alternativa
  cnt           BIGINT UNSIGNED NOT NULL DEFAULT 1,
  UNIQUE INDEX  (query_id, db, tbl, idx, alt_idx),
  INDEX         (db, tbl, idx),
  INDEX         (db, tbl, alt_idx)
)

Las siguientes son algunas consultas que puede ejecutar contra estas tablas para responder preguntas comunes que pueda tener. Cada consulta también se crea como una vista (con MySQL v5.0 y versiones posteriores) si "--[no]create-views" es true (lo es por defecto). Los nombres de las vistas son las cadenas después del prefijo "MAGIC_view_".

Pregunta: ¿qué consultas utilizan a veces índices diferentes y qué fracción del tiempo se elige cada índice? MAGIC_view_query_uses_several_indexes:

SELECT iu.query_id, CONCAT_WS('.', iu.db, iu.tbl, iu.idx) AS idx,
   variations, iu.cnt, iu.cnt / total_cnt * 100 AS pct
FROM index_usage AS iu
   INNER JOIN (
      SELECT query_id, db, tbl, SUM(cnt) AS total_cnt,
        COUNT(*) AS variations
      FROM index_usage
      GROUP BY query_id, db, tbl
      HAVING COUNT(*) > 1
   ) AS qv USING(query_id, db, tbl);

Pregunta: ¿qué índices tienen muchas alternativas, es decir, se eligen en lugar de otros índices, y para qué consultas? MAGIC_view_index_has_alternates:

SELECT CONCAT_WS('.', db, tbl, idx) AS idx_chosen,
   GROUP_CONCAT(DISTINCT alt_idx) AS alternatives,
   GROUP_CONCAT(DISTINCT query_id) AS queries, SUM(cnt) AS cnt
FROM index_alternatives
GROUP BY db, tbl, idx
HAVING COUNT(*) > 1;

Pregunta: ¿qué índices se consideran alternativas para otros índices y para qué consultas? MAGIC_view_index_alternates:

SELECT CONCAT_WS('.', db, tbl, alt_idx) AS idx_considered,
   GROUP_CONCAT(DISTINCT idx) AS alternative_to,
   GROUP_CONCAT(DISTINCT query_id) AS queries, SUM(cnt) AS cnt
FROM index_alternatives
GROUP BY db, tbl, alt_idx
HAVING COUNT(*) > 1;

Pregunta: ¿cuáles de estos nunca son elegidos por ninguna consulta y, por lo tanto, son superfluos? MAGIC_view_unused_index_alternates:

SELECT CONCAT_WS('.', i.db, i.tbl, i.idx) AS idx,
   alt.alternative_to, alt.queries, alt.cnt
FROM indexes AS i
   INNER JOIN (
      SELECT db, tbl, alt_idx, GROUP_CONCAT(DISTINCT idx) AS alternative_to,
         GROUP_CONCAT(DISTINCT query_id) AS queries, SUM(cnt) AS cnt
      FROM index_alternatives
      GROUP BY db, tbl, alt_idx
      HAVING COUNT(*) > 1
   ) AS alt ON i.db = alt.db AND i.tbl = alt.tbl
     AND i.idx = alt.alt_idx
WHERE i.cnt = 0;

Pregunta: dado una tabla, ¿qué índices se utilizaron, por cuántas consultas, con cuántos huellas dactilares distintas? ¿Hubo alternativas? ¿Qué índices no se utilizaron? Puede editar la lista SELECT de la siguiente consulta para ver también los IDs de consulta en cuestión. MAGIC_view_index_usage:

SELECT i.idx, iu.usage_cnt, iu.usage_total,
   ia.alt_cnt, ia.alt_total
FROM indexes AS i
   LEFT OUTER JOIN (
      SELECT db, tbl, idx, COUNT(*) AS usage_cnt,
         SUM(cnt) AS usage_total, GROUP_CONCAT(query_id) AS used_by
      FROM index_usage
      GROUP BY db, tbl, idx
   ) AS iu ON i.db=iu.db AND i.tbl=iu.tbl AND i.idx = iu.idx
   LEFT OUTER JOIN (
      SELECT db, tbl, idx, COUNT(*) AS alt_cnt,
         SUM(cnt) AS alt_total,
         GROUP_CONCAT(query_id) AS alt_queries
      FROM index_alternatives
      GROUP BY db, tbl, idx
   ) AS ia ON i.db=ia.db AND i.tbl=ia.tbl AND i.idx = ia.idx;

Pregunta: ¿qué índices en una tabla dada son vitales para al menos una consulta (no hay alternativa)? MAGIC_view_required_indexes:

SELECT i.db, i.tbl, i.idx, no_alt.queries
FROM indexes AS i
   INNER JOIN (
      SELECT iu.db, iu.tbl, iu.idx,
         GROUP_CONCAT(iu.query_id) AS queries
      FROM index_usage AS iu
         LEFT OUTER JOIN index_alternatives AS ia
            USING(db, tbl, idx)
      WHERE ia.db IS NULL
      GROUP BY iu.db, iu.tbl, iu.idx
   ) AS no_alt ON no_alt.db = i.db AND no_alt.tbl = i.tbl
      AND no_alt.idx = i.idx
ORDER BY i.db, i.tbl, i.idx, no_alt.queries;
--set-vars
tipo: Array

Establecer las variables de MySQL en esta lista separada por comas de pares "variable=valor".

Por defecto, la herramienta establece:

wait_timeout=10000

Las variables especificadas en la línea de comandos anulan estos valores predeterminados. Por ejemplo, especificar "--set-vars wait_timeout=500" anula el valor predeterminado de 10000.

La herramienta imprime una advertencia y continúa si una variable no se puede establecer.

Primero, la herramienta comprueba su propia versión y también las versiones del siguiente software: sistema operativo, Percona Monitoring and Management (PMM), MySQL, Perl, driver de MySQL para Perl (DBD::mysql) y Percona Toolkit. Cada solicitud es registrada por el servidor, incluyendo los números de versión del software y el ID único del sistema comprobado. El ID se genera mediante el script de instalación de Percona Toolkit o cuando se realiza la llamada a la base de datos de Verificación de Versiones por primera vez.

Cualquier actualización o problema conocido se imprime en STDOUT antes de la salida normal de la herramienta. Esta función nunca debe interferir con el funcionamiento normal de la herramienta.

OPCIONES DE DSN

Estas opciones de DSN se utilizan para crear un DSN. Cada opción se proporciona como "opcion=valor". Las opciones distinguen entre mayúsculas y minúsculas, por lo que P y p no son la misma opción. No puede haber espacios antes o después del signo "=".

y si el valor contiene espacios en blanco, debe entrecomillarse. Las opciones DSN se separan por comas. Consulte la página man de percona-toolkit para obtener todos los detalles.

  • A

    dsn: charset; copy: yes

    Juego de caracteres predeterminado.

  • D

    dsn: database; copy: yes

    Base de datos a la que conectarse.

  • F

    dsn: mysql_read_default_file; copy: yes

    Solo leer opciones predeterminadas del archivo dado

  • h

    dsn: host; copy: yes

    Conectar al host.

  • p

    dsn: password; copy: yes

    Contraseña a usar al conectarse. Si la contraseña contiene comas, deben escaparse con una barra invertida: "exam\,ple"

  • P

    dsn: port; copy: yes

    Número de puerto a usar para la conexión.

  • S

    dsn: mysql_socket; copy: yes

    Archivo de socket a usar para la conexión.

  • u

    dsn: user; copy: yes

    Usuario para iniciar sesión si no es el usuario actual.

  • s

    dsn: mysql_ssl; copy: yes

    Crear conexión SSL

ENTORNO

La variable de entorno "PTDEBUG" habilita la salida de depuración detallada a STDERR. Para habilitar la depuración y capturar toda la salida en un archivo, ejecute la herramienta así:

PTDEBUG=1 pt-index-usage ... > ARCHIVO 2>&1

Tenga cuidado: la salida de depuración es voluminosa y puede generar varios megabytes de salida.

ATENCIÓN

Usar <PTDEBUG> puede exponer contraseñas. Cuando la depuración está habilitada, todos los parámetros de la línea de comandos se muestran en la salida.

REQUISITOS DEL SISTEMA
