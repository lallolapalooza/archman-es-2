PROLOGO

NOMBRE

pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock — bloquear y desbloquear un mutex

SINOPSIS

#include <pthread.h>
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);

DESCRIPCIÓN

El objeto mutex referenciado por mutex será bloqueado por una llamada a pthread_mutex_lock() que devuelva cero o [EOWNERDEAD]. Si el mutex ya está bloqueado por otro hilo, el hilo que llama se bloqueará hasta que el mutex esté disponible. Esta operación devolverá con el objeto mutex referenciado por mutex en estado bloqueado con el hilo que llama como su propietario. Si un hilo intenta volver a bloquear un mutex que ya ha bloqueado, pthread_mutex_lock() se comportará según se describe en la columna **Rebloqueo** de la siguiente tabla. Si un hilo intenta desbloquear un mutex que no ha bloqueado o un mutex que está desbloqueado, pthread_mutex_unlock() se comportará según se describe en la columna **Desbloqueo cuando no es propietario** de la siguiente tabla.

Tipo de mutex Robustez Rebloqueo Desbloqueo cuando no es propietario
NORMAL no robusto interbloqueo comportamiento indefinido
NORMAL robusto interbloqueo devuelve error
ERRORCHECK cualquiera devuelve error devuelve error
RECURSIVE cualquiera recursivo devuelve error
(ver abajo)
DEFAULT no robusto indefinido comportamiento indefinido†

DEFAULT robusto indefinido devuelve error
comportamiento†
†
Si el tipo de mutex es PTHREAD_MUTEX_DEFAULT, el comportamiento de pthread_mutex_lock() puede corresponder a uno de los otros tres tipos de mutex estándar como se describe en la tabla anterior. Si no corresponde a ninguno de esos tres, el comportamiento es indefinido para los casos marcados con †.

Donde la tabla indica comportamiento recursivo, el mutex mantendrá el concepto de un contador de bloqueos. Cuando un hilo adquiere un mutex con éxito por primera vez, el contador de bloqueos se establecerá en uno. Cada vez que un hilo rebloquea este mutex, el contador de bloqueos se incrementará en uno. Cada vez que el hilo desbloquea el mutex, el contador de bloqueos se decrementará en uno. Cuando el contador de bloqueos llega a cero, el mutex estará disponible para que otros hilos lo adquieran.

La función pthread_mutex_trylock() será equivalente a pthread_mutex_lock(), excepto que si el objeto mutex referenciado por mutex está actualmente bloqueado (por cualquier hilo, incluido el hilo actual), la llamada devolverá inmediatamente. Si el tipo de mutex es PTHREAD_MUTEX_RECURSIVE y el mutex está actualmente en posesión del hilo que llama, el contador de bloqueos del mutex se incrementará en uno y la función pthread_mutex_trylock() devolverá inmediatamente éxito.

La función pthread_mutex_unlock() liberará el objeto mutex referenciado por mutex. La forma en que se libera un mutex depende del atributo de tipo del mutex. Si hay hilos bloqueados en el objeto mutex referenciado por mutex cuando se llama a pthread_mutex_unlock(), lo que resulta en que el mutex esté disponible, la política de planificación determinará qué hilo adquirirá el mutex.

(En el caso de mutexes PTHREAD_MUTEX_RECURSIVE, el mutex estará disponible cuando el contador llegue a cero y el hilo que llama ya no tenga bloqueos en este mutex.)

Si se entrega una señal a un hilo que espera un mutex, al regresar del manejador de señales, el hilo reanudará la espera del mutex como si no hubiera sido interrumpido.

Si mutex es un mutex robusto y el proceso que contiene el hilo propietario terminó mientras mantenía el bloqueo del mutex, una llamada a pthread_mutex_lock() devolverá el valor de error [EOWNERDEAD]. Si mutex es un mutex robusto y el hilo propietario terminó mientras mantenía el bloqueo del mutex, una llamada a pthread_mutex_lock() puede devolver el valor de error [EOWNERDEAD] incluso si el proceso en el que reside el hilo propietario no ha terminado. En estos casos, el mutex está bloqueado por el hilo, pero el estado que protege se marca como inconsistente. La aplicación debe asegurarse de que el estado se haga consistente para su reutilización y, una vez completado, llamar a pthread_mutex_consistent(). Si la aplicación no puede recuperar el estado, debe desbloquear el mutex sin una llamada previa a pthread_mutex_consistent(), después de lo cual el mutex se marca como permanentemente inutilizable.

Si mutex no se refiere a un objeto mutex inicializado, el comportamiento de pthread_mutex_lock(), pthread_mutex_trylock() y pthread_mutex_unlock() es indefinido.

VALOR DE RETORNO

Si tiene éxito, las funciones pthread_mutex_lock(), pthread_mutex_trylock() y pthread_mutex_unlock() devolverán cero; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

Las funciones pthread_mutex_lock() y pthread_mutex_trylock() fallarán si:

EAGAIN
No se pudo adquirir el mutex porque se ha superado el número máximo de bloqueos recursivos para mutex.
EINVAL
El mutex se creó con el atributo protocol con el valor PTHREAD_PRIO_PROTECT y la prioridad del hilo que llama es superior al techo de prioridad actual del mutex.
ENOTRECOVERABLE

El estado protegido por el mutex no es recuperable.
EOWNERDEAD

El mutex es un mutex robusto y el proceso que contenía el hilo anterior propietario terminó mientras mantenía el bloqueo del mutex. El bloqueo del mutex será adquirido por el hilo que llama y depende del nuevo propietario hacer que el estado sea consistente.

La función pthread_mutex_lock() fallará si:

EDEADLK
El tipo de mutex es PTHREAD_MUTEX_ERRORCHECK y el hilo actual ya posee el mutex.

La función pthread_mutex_trylock() fallará si:

EDEADLK
El tipo de mutex es PTHREAD_MUTEX_ERRORCHECK y el hilo actual ya posee el mutex.

La función pthread_mutex_unlock() fallará si:

EINVAL
El mutex no se refiere a un objeto mutex inicializado, o el mutex no está bloqueado.
EPERM
El hilo que llama no posee el mutex.

Las siguientes condiciones también pueden aplicarse a pthread_mutex_lock(), pthread_mutex_trylock() y pthread_mutex_unlock():

EINVAL
El valor del argumento mutex no representa un objeto mutex válido.

Las funciones correspondientes también pueden fallar si:

ENOMEM
Memoria insuficiente para el nuevo hilo.

La siguiente condición también puede aplicarse a pthread_mutex_unlock():

EBUSY
El mutex está protegido por un protocolo de herencia de prioridades, y el hilo que llama tiene una prioridad mayor que la prioridad techo del mutex.

La siguiente condición también puede aplicarse a pthread_mutex_lock():

EINTR
La llamada fue interrumpida por una señal, y el bloqueo del mutex no se ha adquirido todavía.

CONSIDERACIONES ESPECIALES DE POSIX

Si el mutex está protegido por el protocolo PTHREAD_PRIO_INHERIT o PTHREAD_PRIO_PROTECT, y el hilo que llama tiene una prioridad mayor que el techo de prioridad del mutex, entonces pthread_mutex_lock() devolverá [EINVAL].

CONFORME

XSI, POSIX.1-2001.

NAME

pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock - thread mutual exclusion primitive lock and unlock

SYNOPSIS

     #include <pthread.h>

     int pthread_mutex_lock(pthread_mutex_t *mutex);
     int pthread_mutex_trylock(pthread_mutex_t *mutex);
     int pthread_mutex_unlock(pthread_mutex_t *mutex);

DESCRIPTION

These functions shall be used to lock and unlock mutexes. A mutex provides a mechanism to enforce mutual exclusion. The lock owner is the thread that currently holds the mutex lock. If the mutex is not currently locked, the calling thread acquires the lock. If the mutex is already locked by another thread, the calling thread shall block until the lock is released. If the mutex is already locked by the calling thread, the behaviour depends on the mutex's type attribute.

The pthread_mutex_trylock() function shall be equivalent to pthread_mutex_lock() except that if the mutex is already locked by another thread, the function shall return immediately without blocking.

The pthread_mutex_unlock() function shall release the lock held by the calling thread on the specified mutex. The calling thread must be the owner of the mutex lock.

The behaviour of these functions is undefined if the value specified by the mutex argument does not refer to an initialized mutex object.

If a thread attempts to lock a mutex that it already owns, the behaviour depends on the type of the mutex:

PTHREAD_MUTEX_NORMAL
The behaviour is undefined. It may deadlock or fail with an error.
PTHREAD_MUTEX_ERRORCHECK
The function shall return an error code of [EDEADLK].
PTHREAD_MUTEX_RECURSIVE
The thread shall reacquire the lock. The thread must call pthread_mutex_unlock() once for each time it successfully locked the mutex.
PTHREAD_MUTEX_DEFAULT
The behaviour is undefined. It may deadlock or fail with an error.

The default mutex type is PTHREAD_MUTEX_NORMAL.

If a thread attempts to unlock a mutex that it does not own, the behaviour depends on the type of the mutex:

PTHREAD_MUTEX_NORMAL
The behaviour is undefined.
PTHREAD_MUTEX_ERRORCHECK
The function shall return an error code of [EPERM].
PTHREAD_MUTEX_RECURSIVE
The function shall release the lock. If the lock is still held by the calling thread after the unlock, the thread can continue to use the mutex. If the unlock causes the count of owned locks to drop to zero, the mutex becomes unlocked and available for other threads to lock.
PTHREAD_MUTEX_DEFAULT
The behaviour is undefined.

If a thread attempts to unlock a mutex that is not locked, the behaviour is undefined.

If the mutex is robust, the lock state of a robust mutex can be affected by the termination of the thread that holds the lock. If the terminating thread was not explicitly joining with the robust mutex, the mutex becomes a stale lock. A thread attempting to lock a robust mutex that is a stale lock shall receive a [EOWNERDEAD] error code upon acquiring the lock. The calling thread is then responsible for making the state protected by the robust mutex consistent and then calling pthread_mutex_consistent() to mark the mutex as consistent.

If the mutex is robust, the lock state of a robust mutex can be affected by the termination of the thread that holds the lock. If the terminating thread was explicitly joining with the robust mutex, the mutex is not considered a stale lock. The thread that successfully locks the robust mutex shall receive a [EOWNERDEAD] error code. The calling thread is then responsible for making the state protected by the robust mutex consistent and then calling pthread_mutex_consistent() to mark the mutex as consistent.

RETURN VALUE

On success, these functions shall return zero. Otherwise, on error, they shall return an error number to indicate the error.

The pthread_mutex_lock() function shall return zero if the mutex has been successfully locked, or an error number in the event of an error. Any value returned in mutex in the event of [EOWNERDEAD] is implementation-defined.

The pthread_mutex_trylock() function shall return zero if the mutex has been successfully locked, or an error number in the event of an error.

The pthread_mutex_unlock() function shall return zero if the mutex has been successfully unlocked, or an error number in the event of an error.

ERRORS

The pthread_mutex_lock() function shall fail if:

EDEADLK
A deadlock condition was detected.
EINVAL
The value specified by mutex is invalid.
ENOMEM
Insufficient memory exists to initialize the mutex.
EOWNERDEAD
The mutex is a robust mutex and the previous owning thread terminated while holding the mutex lock. The mutex lock shall be acquired by the calling thread and it is up to the new owner to make the state consistent.

The pthread_mutex_trylock() function shall fail if:

EBUSY
The mutex could not be acquired because it was already locked.
EINVAL
The value specified by mutex is invalid.
ENOMEM
Insufficient memory exists to initialize the mutex.
EOWNERDEAD

The mutex is a robust mutex and the previous owning thread terminated while holding the mutex lock. The mutex lock shall be acquired by the calling thread and it is up to the new owner to make the state consistent.

The pthread_mutex_unlock() function shall fail if:

EPERM
The mutex type is PTHREAD_MUTEX_ERRORCHECK or PTHREAD_MUTEX_RECURSIVE, or the mutex is a robust mutex, and the current thread does not own the mutex.
EINVAL
The value specified by mutex is invalid.

The pthread_mutex_lock() and pthread_mutex_trylock() functions may fail if:

EOWNERDEAD

The mutex is a robust mutex and the previous owning thread terminated while holding the mutex lock. The mutex lock shall be acquired by the calling thread and it is up to the new owner to make the state consistent.

The pthread_mutex_lock() function may fail if:

EDEADLK
A deadlock condition was detected.

These functions shall not return an error code of [EINTR].

The following sections are informative.

EXAMPLES

None.

APPLICATION USAGE

Applications that have assumed that non-zero return values are errors will need updating for use with robust mutexes, since a valid return for a thread acquiring a mutex which is protecting a currently inconsistent state is [EOWNERDEAD]. Applications that do not check the error returns, due to ruling out the possibility of such errors arising, should not use robust mutexes. If an application is supposed to work with normal and robust mutexes it should check all return values for error conditions and if necessary take appropriate action.

RATIONALE

Mutex objects are intended to serve as a low-level primitive from which other thread synchronization functions can be built. As such, the implementation of mutexes should be as efficient as possible, and this has ramifications on the features available at the interface.

The mutex functions and the particular default settings of the mutex attributes have been motivated by the desire to not preclude fast, inlined implementations of mutex locking and unlocking.

Since most attributes only need to be checked when a thread is going to be blocked, the use of attributes does not slow the (common) mutex-locking case.

Likewise, while being able to extract the thread ID of the owner of a mutex might be desirable, it would require storing the current thread ID when each mutex is locked, and this could incur unacceptable levels of overhead. Similar arguments apply to a mutex_tryunlock operation.

For further rationale on the extended mutex types, see the Rationale (Informative) volume of POSIX.1‐2017, Threads Extensions.

If an implementation detects that the value specified by the mutex argument does not refer to an initialized mutex object, it is recommended that the function should fail and report an [EINVAL] error.
