PTHREAD_CANCEL(3P) Manual de programador de POSIX PTHREAD_CANCEL(3P)

PRÓLOGO

Esta página del manual forma parte del Manual del Programador de POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

pthread_cancel — cancelar la ejecución de un hilo

SINOPSIS

#include <pthread.h>
int pthread_cancel(pthread_t thread);

DESCRIPCIÓN

La función pthread_cancel() solicita que thread sea cancelado. El estado y el tipo de cancelabilidad del hilo de destino determinan cuándo la cancelación surte efecto. Cuando se actúa sobre la cancelación, se llamarán los manejadores de limpieza de cancelación para thread. Cuando el último manejador de limpieza de cancelación retorne, se llamarán las funciones destructoras de datos específicas del hilo para thread. Cuando la última función destructora retorne, thread será terminado.

El procesamiento de cancelación en el hilo de destino se ejecutará de forma asíncrona con respecto al retorno de la función pthread_cancel() desde el hilo que la llama.

VALOR DE RETORNO

Si la operación es exitosa, la función pthread_cancel() devolverá cero; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

La función pthread_cancel() no devolverá un código de error de [EINTR].

FUNDAMENTO RACIONAL

Se consideraron dos funciones alternativas para enviar la notificación de cancelación a un hilo. Una sería definir una nueva señal SIGCANCEL que tuviera la semántica de cancelación cuando se entregara; la otra era definir la nueva función pthread_cancel(), que activaría la semántica de cancelación.

La ventaja de una nueva señal era que gran parte de los criterios de entrega eran idénticos a los utilizados al intentar entregar una señal, por lo que hacer que la notificación de cancelación fuera una señal se consideró coherente. De hecho, muchas implementaciones implementan la cancelación utilizando una señal especial. Por otro lado, no habría funciones de señal que pudieran usarse con esta señal, excepto pthread_kill(), y el comportamiento de la señal de cancelación entregada sería diferente al de cualquier señal definida previamente.

Los beneficios de una función especial incluyen el reconocimiento de que esta señal se definiría debido a los criterios de entrega similares y que este es el único comportamiento común entre una solicitud de cancelación y una señal. Además, el mecanismo de entrega de cancelación no tiene que implementarse como una señal. También hay paralelismos fuertes, si no más fuertes, con los mecanismos de excepción de lenguaje que con las señales, que se ven ofuscados potencialmente si el mecanismo de entrega está visiblemente más cerca de las señales.

Al final, se consideró que, dado que había tantas excepciones al uso de la nueva señal con las funciones de señal existentes, sería engañoso. Una función especial resolvió este problema. Esta función se definió cuidadosamente para que una implementación que deseara proporcionar las funciones de cancelación sobre señales pudiera hacerlo. La función especial también significa que las implementaciones no están obligadas a implementar la cancelación con señales.

Si una implementación detecta el uso de un ID de hilo después del final de su vida útil, se recomienda que la función falle y reporte un error [ESRCH].
