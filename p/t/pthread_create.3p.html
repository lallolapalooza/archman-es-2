PTHREAD_CREATE(3P) Manual de programador POSIX PTHREAD_CREATE(3P)

PROLOG

Esta página del manual forma parte del Manual de programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para obtener detalles sobre el comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

pthread_create — creación de hilos

SINOPSIS

#include <pthread.h>
int pthread_create(pthread_t *restrict thread,
    const pthread_attr_t *restrict attr,
    void *(*start_routine)(void*), void *restrict arg);

DESCRIPCIÓN

La función pthread_create() crea un nuevo hilo dentro de un proceso, con los atributos especificados por attr. Si attr es NULL, se utilizarán los atributos predeterminados. Si los atributos especificados por attr se modifican posteriormente, los atributos del hilo no se verán afectados. Tras la finalización exitosa, pthread_create() almacenará el ID del hilo creado en la ubicación referenciada por thread.

El hilo se crea ejecutando start_routine con arg como su único argumento. Si start_routine retorna, el efecto será como si se hubiera realizado una llamada implícita a pthread_exit() utilizando el valor de retorno de start_routine como estado de salida. Tenga en cuenta que el hilo en el que se invocó originalmente main() difiere de esto. Cuando se retorna de main(), el efecto será como si se hubiera realizado una llamada implícita a exit() utilizando el valor de retorno de main() como estado de salida.

El estado de señales del nuevo hilo se inicializará de la siguiente manera:

*
La máscara de señales se heredará del hilo que la crea.
*
El conjunto de señales pendientes para el nuevo hilo estará vacío.

La configuración local actual del hilo y la pila alternativa no se heredarán.

El entorno de punto flotante se heredará del hilo que la crea.

Si pthread_create() falla, no se crea ningún hilo nuevo y el contenido de la ubicación referenciada por thread no está definido.

Si _POSIX_THREAD_CPUTIME está definido, el nuevo hilo tendrá un reloj de tiempo de CPU accesible, y el valor inicial de este reloj se establecerá en cero.

El comportamiento no está definido si el valor especificado por el argumento attr de pthread_create() no hace referencia a un objeto de atributos de hilo inicializado.

VALOR DE RETORNO

Si tiene éxito, la función pthread_create() devolverá cero; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

La función pthread_create() fallará si:

EAGAIN
El sistema carecía de los recursos necesarios para crear otro hilo, o se excedería el límite impuesto por el sistema en el número total de hilos en un proceso {PTHREAD_THREADS_MAX}.
EPERM
El llamador no tiene los privilegios adecuados para establecer los parámetros de planificación o la política de planificación requeridos.

La función pthread_create() no devolverá un código de error de [EINTR].

EJEMPLOS

Ninguno.

USO DE APLICACIONES

No existe ningún requisito para la implementación de que el ID del hilo creado esté disponible antes de que el hilo recién creado comience a ejecutarse. El hilo llamador puede obtener el ID del hilo creado a través del argumento thread de la función pthread_create(), y el hilo recién creado puede obtener su ID mediante una llamada a pthread_self().

RACIONAMIENTO

Una alternativa sugerida a pthread_create() sería definir dos operaciones separadas: crear e iniciar. Algunas aplicaciones encontrarían este comportamiento más natural. Ada, en particular, separa la ``creación'' de una tarea de su ``activación''.

Dividir la operación fue rechazado por los desarrolladores del estándar por muchas razones:

*
El número de llamadas requeridas para iniciar un hilo aumentaría de una a dos y, por lo tanto, impondría una carga adicional a las aplicaciones que no requieren la sincronización adicional. La segunda llamada, sin embargo, podría evitarse con la complicación adicional de un atributo de estado de inicio.
*
Se introduciría un estado adicional: ``creado pero no iniciado''. Esto requeriría que el estándar especificara el comportamiento de las operaciones del hilo cuando el objetivo aún no ha comenzado a ejecutarse.
*
Para aquellas aplicaciones que requieren dicho comportamiento, es posible simular los dos pasos separados con las instalaciones que se proporcionan actualmente. La start_routine() puede sincronizarse esperando en una variable de condición que es señalada por la operación de inicio.

Un implementador de Ada puede optar por crear el hilo en uno de dos puntos del programa Ada: cuando se crea el objeto de tarea, o cuando se activa la tarea (generalmente en un ``begin''). Si se adopta el primer enfoque, la start_routine() necesita esperar en una variable de condición para recibir la orden de comenzar la ``activación''. El segundo enfoque no requiere tal variable de condición ni sincronización adicional. En cualquiera de los enfoques, se crearía un bloque de control de tarea Ada separado cuando se crea el objeto de tarea para mantener colas de rendezvous, etc.

Una extensión del modelo anterior sería permitir que el estado del hilo se modifique entre la creación y el inicio. Esto permitiría eliminar el objeto de atributos del hilo. Esto ha sido rechazado porque:

*
Todo el estado del objeto de atributos del hilo debe poder establecerse para el hilo. Esto requeriría la definición de funciones para modificar los atributos del hilo. No habría reducción en el número de llamadas a funciones requeridas para configurar el hilo. De hecho, para una aplicación que crea todos los hilos utilizando atributos idénticos, el número de llamadas a funciones requeridas para configurar los hilos aumentaría drásticamente. El uso de un objeto de atributos de hilo permite a la aplicación realizar un conjunto de llamadas a funciones de establecimiento de atributos. De lo contrario, el conjunto de llamadas a funciones de establecimiento de atributos debe realizarse para cada creación de hilo.
*
Dependiendo de la arquitectura de implementación, las funciones para establecer el estado del hilo requerirían llamadas al kernel, o por otras razones de implementación no podrían implementarse como macros, lo que aumentaría el costo de la creación del hilo.
*
Se perdería la capacidad de las aplicaciones para segregar hilos por clase.

Otra alternativa sugerida utiliza un modelo similar al de la creación de procesos, como ``thread fork''. La semántica de fork proporcionaría más flexibilidad y la función ``create'' se podría implementar simplemente haciendo un thread fork seguido inmediatamente por una llamada a la ``start routine'' deseada para el hilo. Esta alternativa tiene estos problemas:

*
Para muchas implementaciones, la pila completa del hilo llamador tendría que duplicarse, ya que en muchas arquitecturas no hay forma de determinar el tamaño del marco llamador.
*
La eficiencia se reduce, ya que al menos parte de la pila tiene que copiarse, aunque en la mayoría de los casos el hilo nunca necesita el contexto copiado, ya que simplemente llama a la rutina de inicio deseada.

Si una implementación detecta que el valor especificado por el argumento attr de pthread_create() no hace referencia a un objeto de atributos de hilo inicializado, se recomienda que la función falle e informe un error [EINVAL].
