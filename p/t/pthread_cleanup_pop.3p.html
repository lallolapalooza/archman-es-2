PTHREAD_CLEANUP_POP(3P) Manual del Programador POSIX PTHREAD_CLEANUP_POP(3P)

PRÓLOGO

Esta página del manual forma parte del Manual del Programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

pthread_cleanup_pop, pthread_cleanup_push — establecer manejadores de cancelación

SINOPSIS

#include <pthread.h>
void pthread_cleanup_pop(int execute);
void pthread_cleanup_push(void (*routine)(void*), void *arg);

DESCRIPCIÓN

La función pthread_cleanup_pop() eliminará la rutina en la parte superior de la pila de limpieza de cancelación del hilo de llamada y la invocará opcionalmente (si execute es distinto de cero).

La función pthread_cleanup_push() insertará el manejador de limpieza de cancelación especificado routine en la pila de limpieza de cancelación del hilo de llamada. El manejador de limpieza de cancelación se extraerá de la pila de limpieza de cancelación y se invocará con el argumento arg cuando:

*
El hilo finaliza (es decir, llama a pthread_exit()).
*
El hilo actúa sobre una solicitud de cancelación.
*
El hilo llama a pthread_cleanup_pop() con un argumento execute distinto de cero.

No se especifica si pthread_cleanup_push() y pthread_cleanup_pop() son macros o funciones. Si se suprime una definición de macro para acceder a una función real, o si un programa define un identificador externo con cualquiera de estos nombres, el comportamiento es indefinido. La aplicación se asegurará de que aparezcan como sentencias, y en pares dentro del mismo ámbito léxico (es decir, la macro pthread_cleanup_push() puede considerarse que se expande a una lista de tokens cuyo primer token es '{' con pthread_cleanup_pop() expandiéndose a una lista de tokens cuyo último token es el correspondiente '}').

El efecto de llamar a longjmp() o siglongjmp() es indefinido si ha habido alguna llamada a pthread_cleanup_push() o pthread_cleanup_pop() sin la llamada coincidente desde que se llenó el búfer de salto. El efecto de llamar a longjmp() o siglongjmp() desde dentro de un manejador de limpieza de cancelación también es indefinido, a menos que el búfer de salto también se haya llenado en el manejador de limpieza de cancelación.

El efecto del uso de return, break, continue y goto para salir prematuramente de un bloque de código descrito por un par de funciones pthread_cleanup_push() y pthread_cleanup_pop() es indefinido.

VALOR DE RETORNO

Las funciones pthread_cleanup_push() y pthread_cleanup_pop() no devolverán un valor.

ERRORES

No se definen errores.

Estas funciones no devolverán un código de error de [EINTR].

EJEMPLOS

El siguiente es un ejemplo que utiliza primitivas de hilos para implementar un bloqueo de lectura/escritura cancelable, con prioridad para los escritores:

typedef struct {
    pthread_mutex_t lock;
    pthread_cond_t rcond,
        wcond;
    int lock_count; /* < 0 .. Sostenido por el escritor. */
                    /* > 0 .. Sostenido por lock_count lectores. */
                    /* = 0 .. Sostenido por nadie. */
    int waiting_writers; /* Contador de escritores en espera. */
} rwlock;
void
waiting_reader_cleanup(void *arg)
{
    rwlock *l;
    l = (rwlock *) arg;
    pthread_mutex_unlock(&l->lock);
}
void
lock_for_read(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    pthread_cleanup_push(waiting_reader_cleanup, l);
    while ((l->lock_count < 0) || (l->waiting_writers != 0))
        pthread_cond_wait(&l->rcond, &l->lock);
    l->lock_count++;
   /*
    * Tenga en cuenta que pthread_cleanup_pop ejecuta
    * waiting_reader_cleanup.
    */
    pthread_cleanup_pop(1);
}
void
release_read_lock(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    if (--l->lock_count == 0)
        pthread_cond_signal(&l->wcond);
    pthread_mutex_unlock(&l->lock);
}
void
waiting_writer_cleanup(void *arg)
{
    rwlock *l;
    l = (rwlock *) arg;
    if ((--l->waiting_writers == 0) && (l->lock_count >= 0)) {
       /*
        * Esto solo ocurre si hemos sido cancelados. Si el
        * bloqueo no está en manos de un escritor, puede haber lectores que
        * estaban bloqueados porque waiting_writers era positivo; ahora
        * pueden ser desbloqueados.
        */
        pthread_cond_broadcast(&l->rcond);
    }
    pthread_mutex_unlock(&l->lock);
}
void
lock_for_write(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    l->waiting_writers++;
    pthread_cleanup_push(waiting_writer_cleanup, l);
    while (l->lock_count != 0)
        pthread_cond_wait(&l->wcond, &l->lock);
    l->lock_count = -1;
   /*
    * Tenga en cuenta que pthread_cleanup_pop ejecuta
    * waiting_writer_cleanup.
    */
    pthread_cleanup_pop(1);
}
void
release_write_lock(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    l->lock_count = 0;
    if (l->waiting_writers == 0)
        pthread_cond_broadcast(&l->rcond);
    else
        pthread_cond_signal(&l->wcond);
    pthread_mutex_unlock(&l->lock);
}
/*
 * Esta función se llama para inicializar el bloqueo de lectura/escritura.
 */
void
initialize_rwlock(rwlock *l)
{
    pthread_mutex_init(&l->lock, pthread_mutexattr_default);
    pthread_cond_init(&l->wcond, pthread_condattr_default);
    pthread_cond_init(&l->rcond, pthread_condattr_default);
    l->lock_count = 0;
    l->waiting_writers = 0;
}
reader_thread()
{
    lock_for_read(&lock);
    pthread_cleanup_push(release_read_lock, &lock);
   /*
    * El hilo tiene el bloqueo de lectura.
    */
    pthread_cleanup_pop(1);
}
writer_thread()
{
    lock_for_write(&lock);
    pthread_cleanup_push(release_write_lock, &lock);
   /*
    * El hilo tiene el bloqueo de escritura.
    */
pthread_cleanup_pop(1);
}

USO DE LA APLICACIÓN

Las dos rutinas que insertan y extraen manejadores de limpieza de cancelación, pthread_cleanup_push() y pthread_cleanup_pop(), pueden considerarse como paréntesis de apertura y cierre. Siempre deben coincidir.

FUNDAMENTOS

La restricción de que las dos rutinas que insertan y extraen manejadores de limpieza de cancelación, pthread_cleanup_push() y pthread_cleanup_pop(), deben aparecer en el mismo ámbito léxico permite implementaciones eficientes con macros o compiladores y una gestión eficiente del almacenamiento. Una implementación de ejemplo de estas rutinas como macros podría parecerse a esto:

#define pthread_cleanup_push(rtn,arg) { \
    struct _pthread_handler_rec __cleanup_handler, **__head; \
    __cleanup_handler.rtn = rtn; \
    __cleanup_handler.arg = arg; \
    (void) pthread_getspecific(_pthread_handler_key, &__head); \
    __cleanup_handler.next = *__head; \
    *__head = &__cleanup_handler;
#define pthread_cleanup_pop(ex) \
    *__head = __cleanup_handler.next; \
    if (ex) (*__cleanup_handler.rtn)(__cleanup_handler.arg); \
}

Una implementación más ambiciosa de estas rutinas podría hacer incluso mejor al permitir que el compilador note que el manejador de limpieza de cancelación es una constante y puede expandirse en línea.

Este volumen de POSIX.1‐2017 deja actualmente sin especificar el efecto de llamar a longjmp() desde un manejador de señales que se ejecuta en una función de interfaz de sistema POSIX. Si una implementación quiere permitir esto y dar al programador un comportamiento razonable, la función longjmp() tiene que llamar a todos los manejadores de limpieza de cancelación que se hayan insertado pero no extraído desde el momento en que se llamó a setjmp().

Considere un hilo multihilo llamado por un hilo que utiliza señales. Si se entregara una señal a un manejador de señales durante la operación de qsort() y ese manejador llamara a longjmp() (que, a su vez, no llamara a los manejadores de limpieza de cancelación), los hilos auxiliares creados por la función qsort() no serían cancelados. En cambio, continuarían ejecutándose y escribiendo en la matriz de argumentos, aunque la matriz pudiera haber sido eliminada de la pila.
