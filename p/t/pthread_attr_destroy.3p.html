NOMBRE

pthread_attr_destroy, pthread_attr_init — destruir e inicializar el objeto de atributos de hilo

SINOPSIS

#include <pthread.h>
int pthread_attr_destroy(pthread_attr_t *attr);
int pthread_attr_init(pthread_attr_t *attr);

DESCRIPCIÓN

La función pthread_attr_destroy() destruye un objeto de atributos de hilo. Una implementación puede hacer que pthread_attr_destroy() establezca attr en un valor inválido definido por la implementación. Un objeto de atributos attr destruido puede ser reinicializado usando pthread_attr_init(); los resultados de referenciar el objeto de otra manera después de haber sido destruido no están definidos.

La función pthread_attr_init() inicializa un objeto de atributos de hilo attr con el valor por defecto para todos los atributos individuales utilizados por una implementación dada.

El objeto de atributos resultante (posiblemente modificado al establecer valores de atributos individuales) cuando se utiliza por pthread_create() define los atributos del hilo creado. Un único objeto de atributos puede ser utilizado en múltiples llamadas simultáneas a pthread_create(). Los resultados no están definidos si se llama a pthread_attr_init() especificando un objeto de atributos attr ya inicializado.

El comportamiento no está definido si el valor especificado por el argumento attr a pthread_attr_destroy() no se refiere a un objeto de atributos de hilo inicializado.

VALOR DE RETORNO

Tras una finalización exitosa, pthread_attr_destroy() y pthread_attr_init() devolverán un valor de 0; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

La función pthread_attr_init() fallará si:

ENOMEM
No existe suficiente memoria para inicializar el objeto de atributos de hilo.

Estas funciones no devolverán un código de error de [EINTR].

FUNDAMENTO

Los objetos de atributos se proporcionan para hilos, mutexes y variables de condición como un mecanismo para soportar la posible estandarización futura en estas áreas sin requerir que la función en sí sea modificada.

Los objetos de atributos proporcionan un aislamiento limpio de los aspectos configurables de los hilos. Por ejemplo, el "tamaño de pila" es un atributo importante de un hilo, pero no se puede expresar de forma portable. Al portar un programa con hilos, los tamaños de pila a menudo necesitan ser ajustados. El uso de objetos de atributos puede ayudar permitiendo que los cambios se aíslen en un solo lugar, en lugar de distribuirse en cada instancia de creación de hilos.

Los objetos de atributos se pueden usar para configurar "clases" de hilos con atributos similares; por ejemplo, "hilos con pilas grandes y alta prioridad" o "hilos con pilas mínimas". Estas clases se pueden definir en un solo lugar y luego referenciarse donde sea que se necesiten crear hilos. Los cambios en las decisiones de "clase" se vuelven sencillos, y no se requiere un análisis detallado de cada llamada a pthread_create().

Los objetos de atributos se definen como tipos opacos como ayuda a la extensibilidad. Si estos objetos se hubieran especificado como estructuras, la adición de nuevos atributos obligaría a recompilar todos los programas multihilo cuando los objetos de atributos se extiendan; esto podría no ser posible si diferentes componentes del programa fueran suministrados por diferentes proveedores.

Además, los objetos de atributos opacos presentan oportunidades para mejorar el rendimiento. La validez de los argumentos se puede verificar una vez cuando se establecen los atributos, en lugar de cada vez que se crea un hilo. Las implementaciones a menudo necesitan almacenar en caché objetos del núcleo que son costosos de crear. Los objetos de atributos opacos proporcionan un mecanismo eficiente para detectar cuándo los objetos almacenados en caché se vuelven inválidos debido a cambios en los atributos.

Dado que la asignación no está necesariamente definida en un tipo opaco dado, los valores por defecto definidos por la implementación no pueden definirse de forma portable. La solución a este problema es permitir que los objetos de atributos se inicialicen dinámicamente mediante funciones de inicialización de objetos de atributos, de modo que la implementación pueda suministrar automáticamente valores por defecto.

La siguiente propuesta se proporcionó como una alternativa sugerida a los atributos suministrados:

1.
Mantener el estilo de pasar un parámetro formado por la OR inclusiva a nivel de bits de banderas a las rutinas de inicialización (pthread_create(), pthread_mutex_init(), pthread_cond_init()). El parámetro que contiene las banderas debe ser un tipo opaco para la extensibilidad. Si no se establecen banderas en el parámetro, entonces los objetos se crean con características por defecto. Una implementación puede especificar valores de banderas definidos por la implementación y su comportamiento asociado.
2.
Si se necesita una mayor especialización de mutexes y variables de condición, las implementaciones pueden especificar procedimientos adicionales que operan en los objetos pthread_mutex_t y pthread_cond_t (en lugar de en los objetos de atributos).

Las dificultades con esta solución son:

1.
Una máscara de bits no es opaca si las bits tienen que establecerse en objetos de atributos de vector de bits utilizando operaciones explícitas de OR inclusivas a nivel de bits. Si el conjunto de opciones excede un int, los programadores de aplicaciones necesitan conocer la ubicación de cada bit. Si los bits se establecen o leen mediante encapsulación (es decir, funciones de obtención y establecimiento), entonces la máscara de bits es simplemente una implementación de objetos de atributos tal como se definen actualmente y no debe exponerse al programador.
2.
Muchos atributos no son booleanos o valores enteros muy pequeños. Por ejemplo, la política de programación puede caber en 3 o 4 bits, pero la prioridad requiere 5 bits o más, ocupando así al menos 8 bits de un total posible de 16 bits en máquinas con enteros de 16 bits. Debido a esto, la máscara de bits solo puede controlar razonablemente si se establecen o no atributos particulares, y no puede servir como repositorio del valor en sí. El valor necesita especificarse como parámetro de una función (lo cual no es extensible), o estableciendo un campo de estructura (lo cual no es opaco), o mediante funciones de obtención y establecimiento (haciendo que la máscara de bits sea una adición redundante a los objetos de atributos).

El tamaño de pila se define como un atributo opcional porque la propia noción de pila es inherentemente dependiente de la máquina. Algunas implementaciones pueden no poder cambiar el tamaño de la pila, por ejemplo, y otras pueden no necesitar hacerlo porque las páginas de pila pueden ser discontiguas y se pueden asignar y liberar bajo demanda.

El mecanismo de atributos ha sido diseñado en gran medida para la extensibilidad. Las futuras extensiones al mecanismo de atributos o a cualquier objeto de atributos definido en este volumen de POSIX.1‐2017 deben hacerse con cuidado para no afectar la compatibilidad binaria.

Los objetos de atributos, incluso si se asignan mediante funciones de asignación dinámica como malloc(), pueden tener su tamaño fijo en tiempo de compilación. Esto significa, por ejemplo, que un pthread_create() en una implementación con extensiones a pthread_attr_t no puede mirar más allá del área que la aplicación binaria asume que es válida. Esto sugiere que las implementaciones deben mantener un campo de tamaño en el objeto de atributos, así como posiblemente información de versión, si se van a acomodar extensiones en diferentes direcciones (posiblemente por diferentes proveedores).

Si una implementación detecta que el valor especificado por el argumento attr a pthread_attr_destroy() no se refiere a un objeto de atributos de hilo inicializado, se recomienda que la función falle y reporte un error [EINVAL].

NAME

pthread_attr_init - initialize thread attributes object

SYNOPSIS

#include <pthread.h>

int pthread_attr_init(pthread_attr_t *attr);

DESCRIPTION

The pthread_attr_init() function shall initialize the thread attributes object referred to by attr with the default thread attributes.

The default values for the thread attributes are implementation-dependent and are defined in "Default Thread Creation Attributes" in POSIX.1-2017.

The behavior is undefined if the thread attributes object has previously been initialized by any of the pthread_attr_* initialization functions (pthread_attr_init(), pthread_attr_setstacksize(), pthread_attr_setguardsize(), etc.).

RETURN VALUE

On success, pthread_attr_init() shall return 0. On error, it shall return an error number that indicates the error. If the object referred to by attr has previously been initialized by pthread_attr_init() or any other pthread_attr_* initialization function, pthread_attr_init() returns an error number indicating that the object is busy.

ERRORS

The pthread_attr_init() function may fail if:

ENOMEM
Insufficient memory is available to initialize the thread attributes object.

If the object referred to by attr has previously been initialized by pthread_attr_init() or any other pthread_attr_* initialization function, pthread_attr_init() may return [EBUSY].

EXAMPLES

None.

APPLICATION USAGE

The thread attributes object should be initialized using pthread_attr_init() before any other attributes manipulation functions are called on it. The attributes object should be destroyed using pthread_attr_destroy() when it is no longer needed.
