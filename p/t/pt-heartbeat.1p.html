PT-HEARTBEAT(1p) Documentación de Perl contribuida por el usuario PT-HEARTBEAT(1p)

NOMBRE

pt-heartbeat - Monitoriza el retardo de la replicación de MySQL.

SINOPSIS

Uso: pt-heartbeat [OPCIONES] [DSN] --update|--monitor|--check|--stop

pt-heartbeat mide el retardo de replicación en un servidor MySQL o PostgreSQL. Puedes usarlo para actualizar un origen de replicación o monitorizar una réplica. Si es posible, las opciones de conexión de MySQL se leen de tu archivo .my.cnf.

Inicia un proceso demonizado para actualizar la tabla test.heartbeat en el origen de replicación:

pt-heartbeat -D test --update -h servidor-origen --daemonize

Monitoriza el retardo de replicación en la réplica:

pt-heartbeat -D test --monitor -h servidor-replica
pt-heartbeat -D test --monitor -h servidor-replica --dbi-driver Pg

Comprueba el retardo de la réplica una vez y sale (usando un DSN opcional para especificar el host de la réplica):

pt-heartbeat -D test --check h=servidor-replica

DESCRIPCIÓN

pt-heartbeat es un sistema de monitorización de retardo de replicación de MySQL y PostgreSQL en dos partes que mide el retardo observando los datos replicados reales. Esto evita depender del propio mecanismo de replicación, que es poco fiable. (Por ejemplo, "SHOW REPLICA STATUS" en MySQL).

La primera parte es una instancia de pt-heartbeat "--update" que se conecta a un origen de replicación y actualiza una marca de tiempo (un "registro de latido") cada X segundos ("--interval"). Dado que la tabla de latidos puede contener registros de múltiples orígenes de replicación (ver "JERARQUÍA MULTI-RÉPLICA"), el ID del servidor (@@server_id) se utiliza para identificar los registros.

La segunda parte es una instancia de pt-heartbeat "--monitor" o "--check" que se conecta a una réplica, examina el registro de latido replicado de su origen inmediato o del "--source-server-id" especificado, y calcula la diferencia con la hora actual del sistema. Si la replicación entre la réplica y el origen está retrasada o rota, la diferencia calculada será mayor que cero y potencialmente aumentará si se especifica "--monitor".

Debes crear manualmente la tabla de latidos en el origen de replicación o usar "--create-table". Consulta "--create-table" para ver la estructura correcta de la tabla de latidos. Se sugiere el motor de almacenamiento "MEMORY", pero no es obligatorio, para MySQL.

La tabla de latidos debe contener una fila de latido. Por defecto, se inserta una fila de latido si no existe. Esta característica se puede deshabilitar con la opción "--[no]insert-heartbeat-row" en caso de que el usuario de la base de datos no tenga privilegios de INSERT.

pt-heartbeat depende únicamente de que el registro de latido se replique en la réplica, por lo que funciona independientemente del mecanismo de replicación (replicación integrada, un sistema como Continuent Tungsten, etc.). Funciona a cualquier profundidad en la jerarquía de replicación; por ejemplo, informará de forma fiable cuánto se retrasa una réplica respecto al origen del origen del origen. Y si la replicación se detiene, seguirá funcionando e informará (¡con precisión!) que la réplica se está quedando cada vez más atrás del origen.

pt-heartbeat tiene una resolución máxima de 0.01 segundos. Los relojes en los servidores de origen y réplica deben estar estrechamente sincronizados mediante NTP. Por defecto, las comprobaciones de "--update" ocurren en el borde del segundo (ej. 00:01) y las comprobaciones de "--monitor" ocurren a mitad de segundo (ej. 00:01.5). Mientras los relojes de los servidores estén estrechamente sincronizados y los eventos de replicación se propaguen en menos de medio segundo, pt-heartbeat informará cero segundos de retraso.

pt-heartbeat intentará reconectarse si la conexión tiene un error, pero no reintentará si no puede obtener una conexión cuando empieza.

La opción "--dbi-driver" te permite usar pt-heartbeat para monitorizar PostgreSQL también. Se informa que funciona bien con la replicación Slony-1.

JERARQUÍA MULTI-RÉPLICA

Si la jerarquía de replicación tiene múltiples réplicas que son orígenes de otras réplicas, como "origen -> réplica1 -> réplica2", se pueden ejecutar instancias de "--update" en las réplicas además de en el origen. La tabla de latidos por defecto (ver "--create-table") se indexa en la columna "server_id", por lo que cada servidor actualizará la fila donde "server_id=@@server_id".

Para "--monitor" y "--check", si no se especifica "--source-server-id", la herramienta intenta descubrir y usar el origen inmediato de la réplica. Si esto falla, o si deseas monitorizar el retardo de otro origen, puedes especificar el "--source-server-id" a usar.

Por ejemplo, si la jerarquía de replicación es "origen -> réplica1 -> réplica2" con los IDs de servidor correspondientes 1, 2 y 3, puedes:

pt-heartbeat --daemonize -D test --update -h origen
pt-heartbeat --daemonize -D test --update -h replica1

Luego, comprueba (o monitoriza) el retardo de replicación de origen a réplica2:

pt-heartbeat -D test --source-server-id 1 --check replica2

O comprueba el retardo de replicación de réplica1 a réplica2:

pt-heartbeat -D test --source-server-id 2 --check replica2

Detener la instancia de "--update" en replica1 no afectará a la instancia en el origen.

REGISTRO BINARIO (MAESTRO) Y ESTADO DE LA RÉPLICA

La tabla de latidos por defecto (ver "--create-table") tiene columnas para guardar información de "SHOW BINARY LOG STATUS" ("SHOW MASTER STATUS" antes de MySQL 8.4) y "SHOW REPLICA STATUS". Estas columnas son opcionales. Si alguna está presente, su información correspondiente se guardará.

Percona XtraDB Cluster

Aunque pt-heartbeat debería funcionar con todas las versiones soportadas de Percona XtraDB Cluster (PXC), recomendamos usar 5.5.28-23.7 y superior.

Si estás configurando instancias de latido entre nodos del clúster, ten en cuenta que, dado que la velocidad del clúster está determinada por su nodo más lento, pt-heartbeat no informará sobre la velocidad del clúster en sí, sino solo sobre la velocidad a la que los eventos se replican de un nodo a otro.

Debes especificar "--source-server-id" para las instancias de "--monitor" y "--check".

pt-heartbeat - measure replica lag and insert/monitor heartbeat data

pt-heartbeat [OPTIONS] [--update | --monitor | --check] [--databases=DB1,DB2,...] [--tables=T1,T2,...] [--master-server-id=ID | --source-server-id=ID]

pt-heartbeat [OPTIONS] --create-table

pt-heartbeat is a tool that can be used to measure replica lag and to insert and monitor heartbeat data. It works by querying the replication status of MySQL servers.

The tool supports both traditional and newer versions of the heartbeat table. It automatically detects the version of the table and adjusts its behavior accordingly.

pt-heartbeat can also be used to discover and check replicas recursively in a multi-replica hierarchy.

default: yes

Check if the server is read-only and if so, wait. If the server is read-only, the tool sleeps for "--read-only-interval" seconds and tries again. If the server is not read-only, the tool does nothing and exits. This option is useful when you want to ensure that the server is not read-only before performing any operations. This option is ignored when "--update" is specified and the tool skips doing any inserts. See also "--read-only-interval"

type: Array

Read this comma-separated list of config files; if specified, this must be the first option on the command line.

Create the heartbeat "--table" if it does not exist.

This option causes the table specified by "--database" and "--table" to be created with the following MAGIC_create_heartbeat table definition:

CREATE TABLE heartbeat (
  ts                    varchar(26) NOT NULL,
  server_id             int unsigned NOT NULL PRIMARY KEY,
  file                  varchar(255) DEFAULT NULL,    -- SHOW BINARY LOG STATUS
  position              bigint unsigned DEFAULT NULL, -- SHOW BINARY LOG STATUS
  relay_source_log_file varchar(255) DEFAULT NULL,    -- SHOW REPLICA STATUS
  exec_source_log_pos   bigint unsigned DEFAULT NULL  -- SHOW REPLICA STATUS
);

The heartbeat table requires at least one row. If you manually create the heartbeat table, then you must insert a row by doing:

INSERT INTO heartbeat (ts, server_id) VALUES (NOW(), N);

or if using "--utc":

INSERT INTO heartbeat (ts, server_id) VALUES (UTC_TIMESTAMP(), N);

where "N" is the server's ID; do not use @@server_id because it will replicate and replicas will insert their own server ID instead of the source's server ID.

This is done automatically by "--create-table".

A legacy version of the heartbeat table is still supported:

CREATE TABLE heartbeat (
  id int NOT NULL PRIMARY KEY,
  ts datetime NOT NULL
);

Legacy tables do not support "--update" instances on each replica of a multi-replica hierarchy like "source -> replica1 -> replica2". To manually insert the one required row into a legacy table:

INSERT INTO heartbeat (id, ts) VALUES (1, NOW());

or if using "--utc":

INSERT INTO heartbeat (id, ts) VALUES (1, UTC_TIMESTAMP());

The tool automatically detects if the heartbeat table is legacy.

See also "MULTI-REPLICA HIERARCHY".

type: float; default: 1.0

How often to update or check the heartbeat "--table". Updates and checks begin on the first whole second then repeat every "--interval" seconds for "--update" and every "--interval" plus "--skew" seconds for "--monitor".

For example, if at 00:00.4 an "--update" instance is started at 0.5 second intervals, the first update happens at 00:01.0, the next at 00:01.5, etc. If at 00:10.7 a "--monitor" instance is started at 0.05 second intervals with the default 0.5 second "--skew", then the first check happens at 00:11.5 (00:11.0 + 0.5) which will be "--skew" seconds after the last update which, because the instances are checking at synchronized intervals, happened at 00:11.0.

The tool waits for and begins on the first whole second just to make the interval calculations simpler. Therefore, the tool could wait up to 1 second before updating or checking.

The minimum (fastest) interval is 0.01, and the maximum precision is two decimal places, so 0.015 will be rounded to 0.02.

If a legacy heartbeat table (see "--create-table") is used, then the maximum precision is 1s because the "ts" column is type "datetime".

pt-heartbeat - records the timestamp of the last master event. This is useful for measuring replication lag.

NAME

pt-heartbeat - records the timestamp of the last master event. This is useful for measuring replication lag.

SYNOPSIS

pt-heartbeat --host PERL_HOST --user PERL_USER --password
      PERL_PASS --port PERL_PORT --socket PERL_SOCKET --interval SECONDS
      [--binlog-file BINLOG_FILE] [--binlog-position BINLOG_POSITION]
      [--create-table-def TABLE_DEF] [--defaults-file FILE]
      [--help] [--[no]print-user-password] [--pidFILE FILE]
      [--slave-type SLAVE_TYPE] [--table TABLE] [--utc_time] [--version]

RISKS

This tool requires the REPLICATION SLAVE privileges on the master server, and the REPLICATION CLIENT privilege on the slave server. It requires the SUPER privilege to create the "heartbeat" table.

If you run this tool with the "--print-user-password" option, you will be prompted for your password, and the password will be printed on the screen, which is a security risk.

DESCRIPTION

Replication lag is a common problem in MySQL replication. When replication lag occurs, the slave is behind the master. You can measure replication lag by running this tool on the master and the slave. The tool writes the timestamp of the last event to a table, and you can then query the table on the slave to see how far behind it is.

The tool can also be used to measure the replication lag between multiple masters and slaves. For example, you can run this tool on a master, and then run it on multiple slaves to see how far behind each slave is.

MULTI-REPLICA HIERARCHY

This tool is useful for measuring replication lag in a multi-replica hierarchy. For example, if you have a master, and multiple slaves that replicate from the master, you can run this tool on each slave to see how far behind each slave is. You can also run this tool on a master, and then run it on a slave that replicates from the master, and then run it on another slave that replicates from the first slave to see how far behind each slave is.

BINARY LOG (MASTER) AND REPLICA STATUS

This tool requires the binary log to be enabled on the master server. It also requires that the slave server is configured to replicate from the master server.

The tool writes the timestamp of the last event to a table named "heartbeat" by default. You can change the table name by using the "--table" option. The table has two columns: "ts" (timestamp) and "master_id" (master ID). The "ts" column stores the timestamp of the last event, and the "master_id" column stores the ID of the master server.

Percona XtraDB Cluster

This tool is not compatible with Percona XtraDB Cluster.

OPTIONS

The options are as follows:

--binlog-file
The name of the binary log file on the master server.
--binlog-position
The position in the binary log file on the master server.
--create-table-def
The CREATE TABLE definition for the heartbeat table. This is useful if you want to create the table with specific options.
--defaults-file
The file to read MySQL options from.
--help
Print help and exit.
--host
The host to connect to.
--interval
The interval in seconds to write the timestamp to the heartbeat table.
--password
The password to connect to the server.
--port
The port to connect to.
--print-user-password
Print the user password.
--pidfile
Write the process ID to the specified file.
--slave-type
The type of slave server. This can be "mysql" or "mariadb".
--socket
The socket to connect to.
--table
The name of the heartbeat table.
--user
The user to connect to.
--utc_time
Use UTC time for timestamps.
--version
Print version and exit.

These options specify DSN (Data Source Name) parameters for the master and slave servers.

--MASTER_DSN
DSN for the master server.
--SLAVE_DSN
DSN for the slave server.

You can specify multiple DSNs for master and slave servers.
