PTHREAD_MUTEX_DESTROY(3P) Manual del programador POSIX PTHREAD_MUTEX_DESTROY(3P)

PRÓLOGO

Esta página del manual forma parte del Manual del programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual correspondiente de Linux para conocer los detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

pthread_mutex_destroy, pthread_mutex_init — destruir e inicializar un mutex

SINOPSIS

#include <pthread.h>
int pthread_mutex_destroy(pthread_mutex_t *mutex);
int pthread_mutex_init(pthread_mutex_t *restrict mutex,
    const pthread_mutexattr_t *restrict attr);
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

DESCRIPCIÓN

La función pthread_mutex_destroy() destruye el objeto mutex referenciado por mutex; el objeto mutex se vuelve, en efecto, no inicializado. Una implementación puede hacer que pthread_mutex_destroy() establezca el objeto referenciado por mutex en un valor inválido.

Un objeto mutex destruido puede ser reinicializado usando pthread_mutex_init(); los resultados de referenciar de otro modo el objeto después de que haya sido destruido no están definidos.

Debe ser seguro destruir un mutex inicializado que esté desbloqueado. Intentar destruir un mutex bloqueado, o un mutex que otro hilo está intentando bloquear, o un mutex que se está utilizando en una llamada a pthread_cond_timedwait() o pthread_cond_wait() por otro hilo, produce un comportamiento indefinido.

La función pthread_mutex_init() inicializa el mutex referenciado por mutex con los atributos especificados por attr. Si attr es NULL, se utilizan los atributos predeterminados del mutex; el efecto será el mismo que pasar la dirección de un objeto de atributos de mutex predeterminados. Tras la inicialización exitosa, el estado del mutex se vuelve inicializado y desbloqueado.

Consulte la Sección 2.9.9, Copias de Objetos de Sincronización y Asignaciones Alternativas para obtener requisitos adicionales.

Intentar inicializar un mutex ya inicializado produce un comportamiento indefinido.

En casos donde los atributos predeterminados del mutex son apropiados, la macro PTHREAD_MUTEX_INITIALIZER puede usarse para inicializar mutexes. El efecto será equivalente a la inicialización dinámica mediante una llamada a pthread_mutex_init() con el parámetro attr especificado como NULL, excepto que no se realizan comprobaciones de errores.

El comportamiento es indefinido si el valor especificado por el argumento mutex a pthread_mutex_destroy() no se refiere a un mutex inicializado.

El comportamiento es indefinido si el valor especificado por el argumento attr a pthread_mutex_init() no se refiere a un objeto de atributos de mutex inicializado.

VALOR DE RETORNO

Si tiene éxito, las funciones pthread_mutex_destroy() y pthread_mutex_init() devolverán cero; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

La función pthread_mutex_init() fallará si:

EAGAIN
Al sistema le faltaban los recursos necesarios (aparte de la memoria) para inicializar otro mutex.
ENOMEM
No hay suficiente memoria para inicializar el mutex.
EPERM
El llamante no tiene privilegios para realizar la operación.

La función pthread_mutex_init() puede fallar si:

EINVAL
El objeto de atributos referenciado por attr tiene el atributo de mutex robusto establecido sin que el atributo shared entre procesos esté establecido.

Estas funciones no devolverán un código de error de [EINTR].

Las siguientes secciones son informativas.

EJEMPLOS

Ninguno.

USO DE APLICACIÓN

Ninguno.

JUSTIFICACIÓN

Si una implementación detecta que el valor especificado por el argumento mutex a pthread_mutex_destroy() no se refiere a un mutex inicializado, se recomienda que la función falle e informe un error [EINVAL].

Si una implementación detecta que el valor especificado por el argumento mutex a pthread_mutex_destroy() o pthread_mutex_init() se refiere a un mutex bloqueado o un mutex que es referenciado (por ejemplo, mientras se usa en una llamada a pthread_cond_timedwait() o pthread_cond_wait()) por otro hilo, o detecta que el valor especificado por el argumento mutex a pthread_mutex_init() se refiere a un mutex ya inicializado, se recomienda que la función falle e informe un error [EBUSY].

Si una implementación detecta que el valor especificado por el argumento attr a pthread_mutex_init() no se refiere a un objeto de atributos de mutex inicializado, se recomienda que la función falle e informe un error [EINVAL].

Posibles Implementaciones Alternativas

Este volumen de POSIX.1‐2017 admite varias implementaciones alternativas de mutexes. Una implementación puede almacenar el bloqueo directamente en el objeto de tipo pthread_mutex_t. Alternativamente, una implementación puede almacenar el bloqueo en el heap y simplemente almacenar un puntero, manejador o ID único en el objeto mutex. Cualquiera de las implementaciones tiene ventajas o puede ser requerida en ciertas configuraciones de hardware. Para que se pueda escribir código portable que sea invariante a esta elección, este volumen de POSIX.1‐2017 no define la asignación ni la igualdad para este tipo, y utiliza el término ``inicializar'' para reforzar la noción (más restrictiva) de que el bloqueo puede residir realmente en el propio objeto mutex.

Tenga en cuenta que esto excluye una sobre-especificación del tipo de mutex o variable de condición y motiva la opacidad del tipo.

Se permite, pero no se requiere, que una implementación haga que pthread_mutex_destroy() almacene un valor ilegal en el mutex. Esto puede ayudar a detectar programas erróneos que intentan bloquear (o referenciar de otra manera) un mutex que ya ha sido destruido.

Compromiso entre Comprobaciones de Errores y Rendimiento Soportado

Muchas condiciones de error que pueden ocurrir no requieren ser detectadas por la implementación para permitir que las implementaciones intercambien rendimiento versus grado de comprobación de errores de acuerdo con las necesidades de sus aplicaciones específicas y entorno de ejecución. Como regla general, las condiciones causadas por el sistema (como memoria insuficiente) deben ser detectadas, pero las condiciones causadas por una aplicación codificada erróneamente (como no proporcionar sincronización adecuada para evitar que un mutex sea eliminado mientras está en uso) se especifican para producir un comportamiento indefinido.

Por lo tanto, se permite una amplia gama de implementaciones. Por ejemplo, una implementación destinada a la depuración de aplicaciones puede implementar todas las comprobaciones de errores, pero una implementación que ejecuta una aplicación única y demostrablemente correcta bajo estrictas restricciones de rendimiento en un ordenador embebido puede implementar comprobaciones mínimas. Una implementación puede incluso proporcionarse en dos versiones, similar a las opciones que ofrecen los compiladores: una versión con comprobación completa, pero más lenta; y una versión con comprobación limitada, pero más rápida. Prohibir esta opcionalidad sería un perjuicio para los usuarios.

Al limitar cuidadosamente el uso de "comportamiento indefinido" solo a cosas que una aplicación errónea (mal codificada) podría hacer, y al definir que los errores de "recurso no disponible" son obligatorios, este volumen de POSIX.1‐2017 garantiza que una aplicación totalmente conforme sea portable a través de toda la gama de implementaciones, sin obligar a todas las implementaciones a agregar sobrecarga para comprobar numerosas cosas que un programa correcto nunca hace. Cuando el comportamiento es indefinido, no se devuelve ningún número de error.

PROLOG

This section describes the intended behavior of the POSIX Threads standard. It is not executable code. It is meant to help designers of implementations make choices that will result in implementations that are both portable and efficient.

NAME

pthread_mutex_destroy, pthread_cond_destroy - destroy a mutex or condition variable

SYNOPSIS

#include <pthread.h>

int pthread_mutex_destroy(pthread_mutex_t *mutex);
int pthread_cond_destroy(pthread_cond_t *cond);

DESCRIPTION

These functions shall destroy the specified mutex or condition variable, freeing in-use resources. Once destroyed, the mutex or condition variable can be re-initialized or re-created. If the mutex or condition variable is locked or is referenced by another thread, the result of destroying it is undefined.

The destruction functions are intended to be used for dynamically allocated synchronization objects, although they can be used for statically allocated objects as well.

The behavior is undefined if any of the following conditions are met:

  • The mutex argument references a locked mutex.
  • The cond argument references a condition variable for which other threads are currently waiting.
  • The mutex argument references a mutex that is currently being used in a pthread_cond_timedwait() or pthread_cond_wait() call by another thread.

A mutex can be destroyed immediately after it is unlocked. A condition variable can be destroyed immediately after no other threads are waiting on it. Care must be taken to ensure that no other thread may be referencing the object being destroyed.

Refer to Rationale for POSIX Threads
Implementation of Mutexes and Condition Variables section for a discussion of the possibility of implementing these functions such that they return an error number if the mutex is locked or if another thread is waiting on the condition variable.

RETURN VALUE

On success, these functions shall return 0.

On failure, they shall return an error number to indicate the cause of the failure.

ERRORS

The pthread_mutex_destroy() and pthread_cond_destroy() functions shall fail if:

[EINVAL]
The value specified by mutex or cond is not a valid mutex or condition variable.
[EBUSY]
The mutex is locked, or the condition variable is being waited upon by another thread.

These functions shall not return an error code [ENOMEM].

The standard requires that these functions return [EBUSY] if the mutex is locked or if the condition variable is being waited upon by another thread. However, the standard also states that attempting to destroy a locked mutex or a condition variable that is being waited upon results in undefined behavior. This is because undefined behavior means *anything* can happen, which includes returning with any value (which might happen to be a valid, but different, error number).

However, since the error number might be useful to application developers when diagnosing problems during application development, a recommendation is made in the Rationale section that implementors should return a particular error number if their implementation does detect the condition.

RATIONALE

Error Reporting on Destroy

The standard requires that the destruction of a locked mutex or a condition variable for which other threads are waiting results in undefined behavior. This is specified because the destruction of such objects is a programmer error. A programmer who destroys a locked mutex or a condition variable that is being waited upon is violating the semantics of mutexes and condition variables. Since the behavior is undefined, the implementation is free to do anything. It can return an error, it can crash, or it can continue execution.

Since the behavior is undefined, an implementation is not required to detect the condition. If an implementation does detect the condition, it is recommended that it return [EBUSY]. This is because [EBUSY] is the most appropriate error number to indicate that the object is in use and cannot be destroyed. However, the application developer should not rely on this error number being returned, as it is not guaranteed by the standard. The application developer should ensure that mutexes are unlocked and that no threads are waiting on condition variables before attempting to destroy them.

The same logic applies to attempts to destroy mutexes that are being used in pthread_cond_timedwait() or pthread_cond_wait() calls. This is also a programmer error, and the behavior is undefined. Implementations are recommended to return [EBUSY] if they detect this condition, but applications should not rely on this behavior.

Note that the standard does not specify any return value for successfully destroying a mutex or condition variable. It is assumed that these operations will not fail under normal circumstances. If an implementation does return an error code, it is usually [EINVAL] if the object is not a valid mutex or condition variable.

Why No Limits are Defined

Defining symbols for the maximum number of mutexes and condition variables was considered but rejected because the number of these objects may change dynamically. Furthermore, many implementations place these objects into application memory; thus, there is no explicit maximum.

Static Initializers for Mutexes and Condition Variables

Providing for static initialization of statically allocated synchronization objects allows modules with private static synchronization variables to avoid runtime initialization tests and overhead. Furthermore, it simplifies the coding of self-initializing modules. Such modules are common in C libraries, where for various reasons the design calls for self-initialization instead of requiring an explicit module initialization function to be called. An example use of static initialization follows.

Without static initialization, a self-initializing routine foo() might look as follows:

static pthread_once_t foo_once = PTHREAD_ONCE_INIT;
static pthread_mutex_t foo_mutex;
void foo_init()
{
    pthread_mutex_init(&foo_mutex, NULL);
}
void foo()
{
    pthread_once(&foo_once, foo_init);
    pthread_mutex_lock(&foo_mutex);
   /* Do work. */
    pthread_mutex_unlock(&foo_mutex);
}

With static initialization, the same routine could be coded as follows:

static pthread_mutex_t foo_mutex = PTHREAD_MUTEX_INITIALIZER;
void foo()
{
    pthread_mutex_lock(&foo_mutex);
   /* Do work. */
    pthread_mutex_unlock(&foo_mutex);
}

Note that the static initialization both eliminates the need for the initialization test inside pthread_once() and the fetch of &foo_mutex to learn the address to be passed to pthread_mutex_lock() or pthread_mutex_unlock().

Thus, the C code written to initialize static objects is simpler on all systems and is also faster on a large class of systems; those where the (entire) synchronization object can be stored in application memory.

Yet the locking performance question is likely to be raised for machines that require mutexes to be allocated out of special memory. Such machines actually have to have mutexes and possibly condition variables contain pointers to the actual hardware locks. For static initialization to work on such machines, pthread_mutex_lock() also has to test whether or not the pointer to the actual lock has been allocated. If it has not, pthread_mutex_lock() has to initialize it before use. The reservation of such resources can be made when the program is loaded, and hence return codes have not been added to mutex locking and condition variable waiting to indicate failure to complete initialization.

This runtime test in pthread_mutex_lock() would at first seem to be extra work; an extra test is required to see whether the pointer has been initialized. On most machines this would actually be implemented as a fetch of the pointer, testing the pointer against zero, and then using the pointer if it has already been initialized. While the test might seem to add extra work, the extra effort of testing a register is usually negligible since no extra memory references are actually done. As more and more machines provide caches, the real expenses are memory references, not instructions executed.

Alternatively, depending on the machine architecture, there are often ways to eliminate all overhead in the most important case: on the lock operations that occur after the lock has been initialized. This can be done by shifting more overhead to the less frequent operation: initialization. Since out-of-line mutex allocation also means that an address has to be dereferenced to find the actual lock, one technique that is widely applicable is to have static initialization store a bogus value for that address; in particular, an address that causes a machine fault to occur. When such a fault occurs upon the first attempt to lock such a mutex, validity checks can be done, and then the correct address for the actual lock can be filled in. Subsequent lock operations incur no extra overhead since they do not ``fault''. This is merely one technique that can be used to support static initialization, while not adversely affecting the performance of lock acquisition. No doubt there are other techniques that are highly machine-dependent.

The locking overhead for machines doing out-of-line mutex allocation is thus similar for modules being implicitly initialized, where it is improved for those doing mutex allocation entirely inline. The inline case is thus made much faster, and the out-of-line case is not significantly worse.

Besides the issue of locking performance for such machines, a concern is raised that it is possible that threads would serialize contending for initialization locks when attempting to finish initializing statically allocated mutexes. (Such finishing would typically involve taking an internal lock, allocating a structure, storing a pointer to the structure in the mutex, and releasing the internal lock.) First, many implementations would reduce such serialization by hashing on the mutex address. Second, such serialization can only occur a bounded number of times. In particular, it can happen at most as many times as there are statically allocated synchronization objects. Dynamically allocated objects would still be initialized via pthread_mutex_init() or pthread_cond_init().

Finally, if none of the above optimization techniques for out-of-line allocation yields sufficient performance for an application on some implementation, the application can avoid static initialization altogether by explicitly initializing all synchronization objects with the corresponding pthread_*_init() functions, which are supported by all implementations. An implementation can also document the tradeoffs and advise which initialization technique is more efficient for that particular implementation.

Destroying Mutexes

A mutex can be destroyed immediately after it is unlocked. However, since attempting to destroy a locked mutex, or a mutex that another thread is attempting to lock, or a mutex that is being used in a pthread_cond_timedwait() or pthread_cond_wait() call by another thread, results in undefined behavior, care must be taken to ensure that no other thread may be referencing the mutex.

Robust Mutexes

Implementations are required to provide robust mutexes for mutexes with the process-shared attribute set to PTHREAD_PROCESS_SHARED. Implementations are allowed, but not required, to provide robust mutexes when the process-shared attribute is set to PTHREAD_PROCESS_PRIVATE.
