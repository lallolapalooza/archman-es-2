NOMBRE

pam.conf, pam.d - Archivos de configuración de PAM

DESCRIPCIÓN

Cuando se inicia una aplicación que concede privilegios con conocimiento de PAM, se activa su conexión a la API de PAM. Esta activación realiza una serie de tareas, la más importante de las cuales es la lectura del(los) archivo(s) de configuración: /etc/pam.conf. Alternativamente y preferiblemente, la configuración puede establecerse mediante archivos de configuración individuales ubicados en un directorio pam.d. La presencia de este directorio hará que Linux-PAM ignore /etc/pam.conf.

Estos archivos listan los PAMs que realizarán las tareas de autenticación requeridas por este servicio, y el comportamiento apropiado de la API de PAM en caso de que los PAMs individuales fallen.

La sintaxis del archivo de configuración /etc/pam.conf es la siguiente. El archivo consta de una lista de reglas, cada regla se coloca típicamente en una sola línea, pero puede extenderse con un salto de línea escapado: `\<LF>'. Los comentarios se anteponen con marcas de `#' y se extienden hasta el siguiente salto de línea.

El formato de cada regla es una colección de tokens separados por espacios, los tres primeros no distinguen entre mayúsculas y minúsculas:

servicio tipo control ruta_módulo argumentos_módulo

La sintaxis de los archivos contenidos en el directorio /etc/pam.d/, es idéntica excepto por la ausencia de cualquier campo servicio. En este caso, el servicio es el nombre del archivo en el directorio /etc/pam.d/. Este nombre de archivo debe estar en minúsculas.

Una característica importante de PAM es que se pueden apilar varias reglas para combinar los servicios de varios PAMs para una tarea de autenticación dada.

El servicio es típicamente el nombre familiar de la aplicación correspondiente: login y su son buenos ejemplos. El nombre de servicio, other, está reservado para dar reglas predeterminadas. Solo las líneas que mencionan el servicio actual (o en ausencia de tales, las entradas other) se asociarán con la aplicación de servicio dada.

El tipo es el grupo de gestión al que corresponde la regla. Se utiliza para especificar a cuál de los grupos de gestión se asociará el módulo subsiguiente. Las entradas válidas son:

account

este tipo de módulo realiza la gestión de cuentas no basada en la autenticación. Se utiliza típicamente para restringir/permitir el acceso a un servicio basándose en la hora del día, los recursos del sistema actualmente disponibles (número máximo de usuarios) o quizás la ubicación del usuario solicitante: solo inicio de sesión 'root' en la consola.

auth

este tipo de módulo proporciona dos aspectos de la autenticación del usuario. En primer lugar, establece que el usuario es quien dice ser, al instruir a la aplicación que solicite al usuario una contraseña o otros medios de identificación. En segundo lugar, el módulo puede otorgar membresía de grupo u otros privilegios a través de sus propiedades de concesión de credenciales.

password

este tipo de módulo es necesario para actualizar el token de autenticación asociado con el usuario. Típicamente, hay un módulo para cada tipo de autenticación basado en 'desafío/respuesta' (auth).

session

este tipo de módulo se asocia con la realización de acciones que deben realizarse para el usuario antes/después de que se le pueda conceder el servicio. Tales acciones incluyen el registro de información concerniente a la apertura/cierre de algún intercambio de datos con un usuario, montaje de directorios, etc.

Si el valor tipo de la lista anterior va precedido por un carácter -, la biblioteca PAM no registrará en el registro del sistema si no es posible cargar el módulo porque falta en el sistema. Esto puede ser útil especialmente para módulos que no siempre están instalados en el sistema y no son necesarios para la autenticación y autorización correctas de la sesión de inicio de sesión.

El tercer campo, control, indica el comportamiento de la API de PAM en caso de que el módulo no logre su tarea de autenticación. Hay dos tipos de sintaxis para este campo de control: la simple tiene una sola palabra clave simple; la más complicada implica una selección entre corchetes de pares valor=acción.

Para la sintaxis simple (histórica), los valores de control válidos son:

required

el fallo de un PAM de este tipo conducirá finalmente a que la API de PAM devuelva fallo, pero solo después de que los módulos restantes apilados (para este servicio y tipo) hayan sido invocados.

requisite

similar a required, sin embargo, en caso de que dicho módulo devuelva un fallo, el control se devuelve directamente a la aplicación o a la pila PAM superior. El valor de retorno es el asociado con el primer módulo requerido o requisito que falle. Nota, este indicador puede usarse para proteger contra la posibilidad de que un usuario tenga la oportunidad de ingresar una contraseña a través de un medio inseguro. Es concebible que dicho comportamiento informe a un atacante sobre cuentas válidas en un sistema. Esta posibilidad debe sopesarse frente a las preocupaciones no insignificantes de exponer una contraseña sensible en un entorno hostil.

sufficient

si dicho módulo tiene éxito y ningún módulo required anterior ha fallado, el framework PAM devuelve éxito a la aplicación o a la pila PAM superior inmediatamente sin llamar a ningún módulo adicional en la pila. El fallo de un módulo sufficient se ignora y el procesamiento de la pila de módulos PAM continúa sin verse afectado.

optional

el éxito o el fallo de este módulo solo es importante si es el único módulo en la pila asociado con este servicio+tipo.

include

incluye todas las líneas del tipo dado del archivo de configuración especificado como argumento para este control.

substack

incluye todas las líneas del tipo dado del archivo de configuración especificado como argumento para este control. Esto difiere de include en que la evaluación de las acciones done y die en un substack no provoca el salto del resto de la pila de módulos completa, sino solo del substack. Los saltos en un substack tampoco pueden hacer que la evaluación salte fuera de él, y todo el substack se cuenta como un módulo cuando se realiza el salto en una pila superior. La acción reset restablecerá el estado de una pila de módulos al estado en el que se encontraba al inicio de la evaluación del substack.

Para la sintaxis más complicada, los valores de control válidos tienen la siguiente forma:

      [valor1=acción1 valor2=acción2 ...]

Donde valorN corresponde al código de retorno de la función invocada en el módulo para el cual se define la línea. Se selecciona de uno de estos: success, open_err, symbol_err, service_err, system_err, buf_err, perm_denied, auth_err, cred_insufficient, authinfo_unavail, user_unknown, maxtries, new_authtok_reqd, acct_expired, session_err, cred_unavail, cred_expired, cred_err, no_module_data, conv_err, authtok_err, authtok_recover_err, authtok_lock_busy, authtok_disable_aging, try_again, ignore, abort, authtok_expired, module_unknown, bad_item, conv_again, incomplete, y default.

El último de estos, default, implica 'todos los valorN' no mencionados explícitamente. Tenga en cuenta que la lista completa de errores PAM está disponible en /usr/include/security/_pam_types.h. La acciónN puede tener una de las siguientes formas:

ignore

cuando se utiliza con una pila de módulos, el estado de retorno del módulo no contribuirá al código de retorno que la aplicación obtiene.

bad

esta acción indica que el código de retorno debe ser considerado como indicativo de que el módulo ha fallado. Si este módulo es el primero en fallar en la pila, su valor de estado se utilizará para toda la pila. Esta es la acción predeterminada para todos los códigos de retorno.

die

equivalente a bad con el efecto secundario de terminar la pila de módulos y que PAM devuelva inmediatamente a la aplicación.

ok

esto le dice a PAM que el administrador piensa que este código de retorno debe contribuir directamente al código de retorno de la pila completa de módulos. En otras palabras, si el estado anterior de la pila conduciría a un retorno de PAM_SUCCESS, el código de retorno del módulo anulará este valor. Tenga en cuenta que si el estado anterior de la pila tiene algún valor que indique un fallo del módulo, este valor 'ok' no se utilizará para anular ese valor.

done

equivalente a ok con el efecto secundario de terminar la pila de módulos y que PAM devuelva inmediatamente a la aplicación, a menos que haya habido un fallo de módulo no ignorado antes.

DESCRIPCIÓN

N (un entero sin signo)

salta los siguientes N módulos en la pila. Ten en cuenta que N igual a 0 no está permitido, se trataría como ignorar en tal caso. El efecto secundario depende de la llamada a la función PAM: para pam_authenticate, pam_acct_mgmt, pam_chauthtok y pam_open_session es ignorar; para pam_setcred y pam_close_session es uno de ignorar, ok o bad dependiendo del valor de retorno del módulo.

reiniciar

borra toda la memoria del estado de la pila de módulos y comienza de nuevo con el siguiente módulo apilado.

Si la acción de un código de retorno no está específicamente definida mediante un token valorN, y no se especifica el valor predeterminado, la acción de ese código de retorno será bad por defecto.

Cada una de las cuatro palabras clave: required; requisite; sufficient; y optional, tienen una expresión equivalente en términos de la sintaxis [...] . Son las siguientes:

required

[success=ok new_authtok_reqd=ok ignore=ignore default=bad]

requisite

[success=ok new_authtok_reqd=ok ignore=ignore default=die]

sufficient

[success=done new_authtok_reqd=done default=ignore]

optional

[success=ok new_authtok_reqd=ok default=ignore]

ruta_modulo es el nombre de archivo completo del PAM a ser utilizado por la aplicación (comienza con '/'), o una ruta de acceso relativa desde la ubicación predeterminada de módulos: /lib/security/ o /lib64/security/, dependiendo de la arquitectura.

argumentos_modulo son una lista de tokens separados por espacios que se pueden utilizar para modificar el comportamiento específico del PAM dado. Dichos argumentos se documentarán para cada módulo individual. Tenga en cuenta que si desea incluir espacios en un argumento, debe rodear ese argumento con corchetes.

    squid auth required pam_mysql.so user=passwd_query passwd=mada \
          db=eminence [query=select user_name from internet_service \
          where user_name='%u' and password=PASSWORD('%p') and \
        service='web_proxy']

Al usar esta convención, puede incluir caracteres `[' dentro de la cadena, y si desea incluir un carácter `]' dentro de la cadena que sobreviva al análisis de argumentos, debe usar `\]'. En otras palabras:

    [..[..\]..]    -->   ..[..]..

Cualquier línea en (uno de) los archivos de configuración que no esté formateada correctamente, generalmente tenderá (por precaución) a hacer que el proceso de autenticación falle. Se escribe un error correspondiente en los archivos de registro del sistema con una llamada a syslog(3).

Más flexible que el archivo de configuración único es configurar libpam a través del contenido de los directorios pam.d. En este caso, los directorios se llenan con archivos, cada uno con un nombre de archivo igual a un nombre de servicio (en minúsculas): es el archivo de configuración personal para el servicio con nombre.

Los archivos de configuración PAM suministrados por el proveedor pueden instalarse en el directorio del sistema /usr/lib/pam.d/ o en un directorio específico del proveedor configurable en lugar del directorio de configuración de la máquina /etc/pam.d/. Si no se encuentra ningún archivo de configuración de la máquina, se utiliza el archivo suministrado por el proveedor. Todos los archivos en /etc/pam.d/ anulan los archivos con el mismo nombre en otros directorios.

La sintaxis de cada archivo en pam.d es similar a la del archivo /etc/pam.conf y consta de líneas de la siguiente forma:

type  control  ruta_modulo  argumentos_modulo

La única diferencia es que no está presente el nombre del servicio. El nombre del servicio es, por supuesto, el nombre del archivo de configuración dado. Por ejemplo, /etc/pam.d/login contiene la configuración para el servicio login.

ARCHIVOS

/etc/pam.conf

el archivo de configuración

/etc/pam.d

el directorio de configuración de Linux-PAM. Generalmente, si este directorio está presente, se ignora el archivo /etc/pam.conf.

/usr/lib/pam.d

el directorio de configuración del proveedor de Linux-PAM. Los archivos en /etc/pam.d anulan los archivos con el mismo nombre en este directorio.
