NOMBRE

packet - interfaz de paquetes a nivel de dispositivo

SINOPSIS

#include <sys/socket.h>
#include <linux/if_packet.h>
#include <net/ethernet.h> /* los protocolos L2 */
packet_socket = socket(AF_PACKET, int tipo_socket, int protocolo);

DESCRIPCIÓN

Los sockets de paquetes se utilizan para recibir o enviar paquetes en bruto a nivel del controlador de dispositivo (Capa 2 del OSI). Permiten al usuario implementar módulos de protocolo en el espacio de usuario sobre la capa física.

El tipo_socket es SOCK_RAW para paquetes en bruto, incluida la cabecera de nivel de enlace, o SOCK_DGRAM para paquetes "cocinados" con la cabecera de nivel de enlace eliminada. La información de la cabecera de nivel de enlace está disponible en un formato común en una estructura sockaddr_ll. protocolo es el número de protocolo IEEE 802.3 en orden de bytes de red. Consulte el archivo de inclusión <linux/if_ether.h> para obtener una lista de protocolos permitidos. Cuando el protocolo se establece en htons(ETH_P_ALL), se reciben todos los protocolos. Todos los paquetes entrantes de ese tipo de protocolo se pasarán al socket de paquetes antes de pasarlos a los protocolos implementados en el kernel. Si protocolo se establece en cero, no se reciben paquetes. Se puede llamar a bind(2) opcionalmente con un sll_protocol distinto de cero para comenzar a recibir paquetes para los protocolos especificados.

Para crear un socket de paquetes, un proceso debe tener la capacidad CAP_NET_RAW en el espacio de nombres de usuario que rige su espacio de nombres de red.

Los paquetes SOCK_RAW se pasan al y desde el controlador de dispositivo sin cambios en los datos del paquete. Al recibir un paquete, la dirección aún se analiza y se pasa en una estructura de dirección estándar sockaddr_ll. Al transmitir un paquete, el búfer proporcionado por el usuario debe contener la cabecera de la capa física. Ese paquete se pone en cola sin modificar al controlador de red de la interfaz definida por la dirección de destino. Algunos controladores de dispositivo siempre agregan otras cabeceras. SOCK_RAW es similar pero no compatible con el obsoleto AF_INET/SOCK_PACKET de Linux 2.0.

SOCK_DGRAM opera en un nivel ligeramente superior. La cabecera física se elimina antes de que el paquete se pase al usuario. Los paquetes enviados a través de un socket de paquetes SOCK_DGRAM obtienen una cabecera de capa física adecuada basada en la información de la dirección de destino sockaddr_ll antes de ser puestos en cola.

Por defecto, todos los paquetes del tipo de protocolo especificado se pasan a un socket de paquetes. Para obtener paquetes solo de una interfaz específica, use bind(2) especificando una dirección en una estructura sockaddr_ll para enlazar el socket de paquetes a una interfaz. Los campos utilizados para enlazar son sll_family (debe ser AF_PACKET), sll_protocol y sll_ifindex.

La operación connect(2) no es compatible con los sockets de paquetes.

Cuando se pasa el indicador MSG_TRUNC a recvmsg(2), recv(2) o recvfrom(2), siempre se devuelve el tamaño real del paquete en la red, incluso si es más largo que el búfer.

Tipos de dirección

La estructura sockaddr_ll es una dirección de capa física independiente del dispositivo.


struct sockaddr_ll {
    unsigned short sll_family;   /* Siempre AF_PACKET */
    unsigned short sll_protocol; /* Protocolo de capa física */
    int            sll_ifindex;  /* Número de interfaz */
    unsigned short sll_hatype;   /* Tipo de hardware ARP */
    unsigned char  sll_pkttype;  /* Tipo de paquete */
    unsigned char  sll_halen;    /* Tamaño de la dirección */
    unsigned char  sll_addr[8];  /* Dirección de capa física */
};

Los campos de esta estructura son los siguientes:

sll_protocol
es el tipo de protocolo estándar de ethernet en orden de bytes de red, tal como se define en el archivo de inclusión <linux/if_ether.h>. Por defecto, es el protocolo del socket.
sll_ifindex
es el índice de interfaz de la interfaz (ver netdevice(7)); 0 coincide con cualquier interfaz (solo permitido para enlazar). sll_hatype es un tipo ARP como se define en el archivo de inclusión <linux/if_arp.h>.
sll_pkttype
contiene el tipo de paquete. Los tipos válidos son PACKET_HOST para un paquete dirigido al host local, PACKET_BROADCAST para un paquete de difusión de capa física, PACKET_MULTICAST para un paquete enviado a una dirección de multidifusión de capa física, PACKET_OTHERHOST para un paquete dirigido a otro host que ha sido capturado por un controlador de dispositivo en modo promiscuo, y PACKET_OUTGOING para un paquete originado en el host local que se reenvía a un socket de paquetes. Estos tipos solo tienen sentido para la recepción.
sll_addr
sll_halen
contienen la dirección de capa física (por ejemplo, IEEE 802.3) y su tamaño. La interpretación exacta depende del dispositivo.

Cuando envía paquetes, es suficiente especificar sll_family, sll_addr, sll_halen, sll_ifindex y sll_protocol. Los otros campos deben ser 0. sll_hatype y sll_pkttype se establecen en los paquetes recibidos para su información.

Opciones de socket

Las opciones de socket de paquetes se configuran llamando a setsockopt(2) con el nivel SOL_PACKET.

PACKET_ADD_MEMBERSHIP
PACKET_DROP_MEMBERSHIP
Los sockets de paquetes se pueden usar para configurar la multidifusión de capa física y el modo promiscuo. PACKET_ADD_MEMBERSHIP agrega un enlace y PACKET_DROP_MEMBERSHIP lo elimina. Ambos esperan una estructura packet_mreq como argumento:

struct packet_mreq {
    int            mr_ifindex;    /* índice de interfaz */
    unsigned short mr_type;       /* acción */
    unsigned short mr_alen;       /* tamaño de dirección */
    unsigned char  mr_address[8]; /* dirección de capa física */
};

mr_ifindex contiene el índice de la interfaz para la que se debe cambiar el estado. El campo mr_type especifica qué acción realizar. PACKET_MR_PROMISC habilita la recepción de todos los paquetes en un medio compartido (a menudo conocido como "modo promiscuo"), PACKET_MR_MULTICAST enlaza el socket al grupo de multidifusión de capa física especificado en mr_address y mr_alen, y PACKET_MR_ALLMULTI configura el socket para recibir todos los paquetes de multidifusión que llegan a la interfaz.
Además, se pueden utilizar los ioctls tradicionales SIOCSIFFLAGS, SIOCADDMULTI, SIOCDELMULTI para el mismo propósito.
PACKET_AUXDATA (desde Linux 2.6.21)
Si esta opción binaria está habilitada, el socket de paquetes pasa una estructura de metadatos junto con cada paquete en el campo de control de recvmsg(2). La estructura se puede leer con cmsg(3). Está definida como

struct tpacket_auxdata {
    __u32 tp_status;
    __u32 tp_len;      /* tamaño del paquete */
    __u32 tp_snaplen;  /* tamaño capturado */
    __u16 tp_mac;
    __u16 tp_net;
    __u16 tp_vlan_tci;
    __u16 tp_vlan_tpid; /* Desde Linux 3.14; antes, estos
                           eran bytes de relleno sin usar */
};

PACKET_FANOUT (desde Linux 3.1)
Para escalar el procesamiento entre hilos, los sockets de paquetes pueden formar un grupo de "fanout". En este modo, cada paquete coincidente se encola en un solo socket del grupo. Un socket se une a un grupo de fanout llamando a setsockopt(2)

packet.7 - Linux manual page

NAME

packet - packet interface

SYNOPSIS


#include <sys/socket.h>
#include <linux/if_packet.h>
#include <net/ethernet.h>



int socket(AF_PACKET, SOCK_RAW, int protocol);
int socket(AF_PACKET, SOCK_DGRAM, int protocol);

DESCRIPTION

The packet socket type provides a way to send and receive raw network packets directly from network devices. It can be used to interact with devices at the physical layer, and to filter and capture packets.

Packet sockets operate at the link layer. They allow access to packets from the device driver up to the link layer protocol (e.g., Ethernet, Wi-Fi).

The packet socket address structure is defined in <linux/if_packet.h>:


struct sockaddr_ll {
    unsigned short    sll_family;   // AF_PACKET
    unsigned short    sll_protocol; // Packet protocol
    int               sll_ifindex;  // Interface number
    unsigned short    sll_hatype;   // Header type
    unsigned char     sll_pkttype;  // Packet type
    char              sll_addr[8];  // Link layer address
    unsigned char     sll_addr_len; // Length of the link layer address
};

The sll_family must be set to AF_PACKET. The sll_protocol specifies the protocol to be received or sent. This is typically an Ethernet protocol type (e.g., ETH_P_IP for IP, ETH_P_ARP for ARP).

The sll_ifindex specifies the interface to which the packet socket is bound. If set to 0, it binds to all interfaces.

The sll_hatype specifies the hardware address type (e.g., ARPHRD_ETHER for Ethernet).

The sll_pkttype specifies the type of packet received. Possible values are:

  • PACKET_HOST: Received packet is destined for this host.
  • PACKET_BROADCAST: Received packet is a broadcast packet.
  • PACKET_MULTICAST: Received packet is a multicast packet.
  • PACKET_OTHERHOST: Received packet is destined for another host.
  • PACKET_OUTGOING: Packet is being sent out on the interface.

The sll_addr field contains the link layer address. For Ethernet, this is the MAC address.

Packet sockets can be created with either SOCK_RAW or SOCK_DGRAM.

  • SOCK_RAW: Provides raw access to packets, including the link layer header. When sending, the entire packet, including the link layer header, must be provided. When receiving, the link layer header is included in the received data.
  • SOCK_DGRAM: Provides access to packets without the link layer header. When sending, the kernel adds the appropriate link layer header based on the specified protocol. When receiving, only the payload of the packet is returned.

The protocol argument to the socket() call specifies the protocol to filter or receive. If set to 0, all protocols are received. Specific protocols can be specified using values from <net/ethernet.h>, such as ETH_P_IP, ETH_P_ARP, etc.

When sending a packet with SOCK_DGRAM, the kernel uses the standard Ethernet DIX encapsulation with the protocol field filled in. The user must supply the LLC header to get a fully conforming packet when using the 802.2 protocol.

Incoming 802.3 packets are not multiplexed on the DSAP/SSAP protocol fields; instead they are supplied to the user as protocol ETH_P_802_2 with the LLC header prefixed. It is thus not possible to bind to ETH_P_802_3; bind to ETH_P_802_2 instead and do the protocol multiplex yourself.

Packet sockets are not subject to the input or output firewall chains.

Compatibility

In Linux 2.0, the only way to get a packet socket was with the call:


socket(AF_INET, SOCK_PACKET, protocol)

This is still supported, but deprecated and strongly discouraged. The main difference between the two methods is that SOCK_PACKET uses the old struct sockaddr_pkt to specify an interface, which doesn't provide physical-layer independence.


struct sockaddr_pkt {
    unsigned short spkt_family;
    unsigned char  spkt_device[14];
    unsigned short spkt_protocol;
};

spkt_family contains the device type, spkt_protocol is the IEEE 802.3 protocol type as defined in <sys/if_ether.h> and spkt_device is the device name as a null-terminated string, for example, eth0.

This structure is obsolete and should not be used in new code.

BUGS

LLC header handling

The IEEE 802.2/803.3 LLC handling could be considered as a bug.

MSG_TRUNC issues

The MSG_TRUNC recvmsg(2) extension is an ugly hack and should be replaced by a control message. There is currently no way to get the original destination address of packets via SOCK_DGRAM.

spkt_device device name truncation

The spkt_device field of sockaddr_pkt has a size of 14 bytes, which is less than the constant IFNAMSIZ defined in <net/if.h> which is 16 bytes and describes the system limit for a network interface name. This means the names of network devices longer than 14 bytes will be truncated to fit into spkt_device. All these sizes include the terminating null byte ('\0')).

Issues from this with old code typically show up with very long interface names used by the Predictable Network Interface Names feature enabled by default in many modern Linux distributions.

The preferred solution is to rewrite code to avoid SOCK_PACKET. Possible user solutions are to disable Predictable Network Interface Names or to rename the interface to a name of at most 13 bytes, for example using the ip(8) tool.

Documentation issues

Socket filters are not documented.
