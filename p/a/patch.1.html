PATCH(1) Manual de Comandos Generales PATCH(1)

NOMBRE

patch - aplica un archivo de diferencias a un original

SINOPSIS

patch [opciones] [archivo_original [archivo_de_parche]]

pero usualmente solo

patch -pnum <archivo_de_parche

DESCRIPCIÓN

patch toma un archivo de parche archivo_de_parche que contiene una lista de diferencias producida por el programa diff y aplica esas diferencias a uno o más archivos originales, produciendo versiones parcheadas. Normalmente las versiones parcheadas se colocan en lugar de las originales. Se pueden crear copias de seguridad; véase la opción -b o --backup. Los nombres de los archivos a parchear se toman usualmente del archivo de parche, pero si solo hay un archivo que parchear, se puede especificar en la línea de comandos como archivo_original.

Al iniciarse, patch intenta determinar el tipo de la lista de diferencias, a menos que se anule con una opción -c (--context), -e (--ed), -n (--normal), o -u (--unified). Las diferencias de contexto (estilo antiguo, estilo nuevo y unificadas) y las diferencias normales son aplicadas por el propio programa patch, mientras que las diferencias de ed simplemente se alimentan al editor ed(1) a través de una tubería.

patch intenta omitir cualquier basura inicial, aplicar el parche y luego omitir cualquier basura final. Por lo tanto, podría alimentar un mensaje de correo electrónico que contenga una lista de diferencias a patch, y debería funcionar. Si todo el parche está indentado por una cantidad constante, si las líneas terminan en CRLF, o si un parche está encapsulado una o más veces anteponiendo "- " a las líneas que comienzan con "-" como se especifica en el RFC 934 de Internet, esto se tiene en cuenta. Después de eliminar la indentación o el encapsulamiento, las líneas que comienzan con # se ignoran, ya que se consideran comentarios.

Con las diferencias de contexto, y en menor medida con las diferencias normales, patch puede detectar cuándo los números de línea mencionados en el parche son incorrectos, e intenta encontrar el lugar correcto para aplicar cada bloque del parche. Como primera suposición, toma el número de línea mencionado para el bloque, más o menos el desplazamiento utilizado al aplicar el bloque anterior. Si ese no es el lugar correcto, patch escanea hacia adelante y hacia atrás para encontrar un conjunto de líneas que coincidan con el contexto dado en el bloque. Primero patch busca un lugar donde coincidan todas las líneas del contexto. Si no se encuentra ningún lugar, y es una diferencia de contexto, y el factor de "fuzz" máximo se establece en 1 o más, entonces se realiza otro escaneo ignorando la primera y la última línea de contexto. Si eso falla, y el factor de "fuzz" máximo se establece en 2 o más, se ignoran las dos primeras y las dos últimas líneas de contexto, y se realiza otro escaneo. (El factor de "fuzz" máximo predeterminado es 2.)

Los bloques con menos contexto de prefijo que de sufijo (después de aplicar el "fuzz") deben aplicarse al principio del archivo si su primer número de línea es 1. Los bloques con más contexto de prefijo que de sufijo (después de aplicar el "fuzz") deben aplicarse al final del archivo.

Si patch no puede encontrar un lugar para instalar ese bloque del parche, lo saca a un archivo de rechazo, que normalmente es el nombre del archivo de salida más un sufijo .rej, o # si .rej generara un nombre de archivo demasiado largo (si incluso añadir el único carácter # hace que el nombre del archivo sea demasiado largo, entonces # reemplaza el último carácter del nombre del archivo).

El bloque rechazado sale en formato de diferencia unificada o de contexto. Si la entrada era una diferencia normal, muchos de los contextos son simplemente nulos. Los números de línea en los bloques del archivo de rechazo pueden ser diferentes a los del archivo de parche: reflejan la ubicación aproximada donde patch cree que deberían ir los bloques fallidos en el nuevo archivo en lugar del antiguo.

A medida que cada bloque se completa, se le informa si el bloque falló y, en ese caso, en qué línea (en el nuevo archivo) patch creía que el bloque debería ir. Si el bloque se instala en una línea diferente a la especificada en la diferencia, se le informa el desplazamiento. Un único desplazamiento grande *puede* indicar que un bloque se instaló en el lugar equivocado. También se le informa si se utilizó un factor de "fuzz" para que la coincidencia se realizara, en cuyo caso también debería ser un poco sospechoso. Si se proporciona la opción --verbose, también se le informan los bloques que coinciden exactamente.

Si no se especifica ningún archivo original archivo_original en la línea de comandos, patch intenta deducir del encabezado de basura qué nombre tiene el archivo a editar, utilizando las siguientes reglas.

Primero, patch toma una lista ordenada de nombres de archivo candidatos como sigue:

  • Si el encabezado es el de una diferencia de contexto, patch toma los nombres de archivo antiguos y nuevos en el encabezado. Se ignora un nombre si no tiene suficientes barras para satisfacer la opción -pnum o --strip=num. El nombre /dev/null también se ignora.
  • Si hay una línea Index: en la basura inicial y si los nombres antiguos y nuevos están ausentes o si patch cumple con POSIX, patch toma el nombre en la línea Index:.
  • Para el propósito de las siguientes reglas, los nombres de archivo candidatos se consideran en el orden (antiguo, nuevo, índice), independientemente del orden en que aparezcan en el encabezado.

Luego, patch selecciona un nombre de archivo de la lista de candidatos como sigue:

  • Si algunos de los archivos nombrados existen, patch selecciona el primer nombre si cumple con POSIX, y el mejor nombre de lo contrario.
  • Si patch no está ignorando RCS, ClearCase, Perforce y SCCS (vea la opción -g num o --get=num), y ningún archivo nombrado existe pero se encuentra un maestro de RCS, ClearCase, Perforce o SCCS, patch selecciona el primer archivo nombrado con un maestro de RCS, ClearCase, Perforce o SCCS.
  • Si no existen archivos nombrados, no se encontró ningún maestro de RCS, ClearCase, Perforce o SCCS, se proporcionan algunos nombres, patch no cumple con POSIX, y el parche parece crear un archivo, patch selecciona el mejor nombre que requiere la creación de la menor cantidad de directorios.
  • Si no se obtiene ningún nombre de archivo de las heurísticas anteriores, se le solicita el nombre del archivo a parchear, y patch selecciona ese nombre.

Para determinar el *mejor* de una lista no vacía de nombres de archivo, patch primero toma todos los nombres con el menor número de componentes de nombre de ruta; de esos, luego toma todos los nombres con el nombre base más corto; de esos, luego toma todos los nombres más cortos; finalmente, toma el primer nombre restante.

Adicionalmente, si la basura inicial contiene una línea Prereq:, patch toma la primera palabra de la línea de prerrequisitos (normalmente un número de versión) y verifica el archivo original para ver si esa palabra se puede encontrar. Si no, patch solicita confirmación antes de continuar.

El resultado de todo esto es que debería poder ejecutar algo como el siguiente comando de shell:

patch -d /usr/src/local/blurfl

y parchear un archivo en el directorio blurfl directamente desde un parche que se lee desde la entrada estándar.

Si el archivo de parche contiene más de un parche, patch intenta aplicar cada uno de ellos como si provinieran de archivos de parche separados. Esto significa, entre otras cosas, que se asume que el nombre del archivo a parchear debe determinarse para cada lista de diferencias, y que la basura antes de cada lista de diferencias contiene cosas interesantes como nombres de archivo y niveles de revisión, como se mencionó anteriormente.

OPCIONES

-b o --backup
Crear archivos de copia de seguridad. Es decir, al parchear un archivo, renombrar o copiar el original en lugar de eliminarlo. Vea la opción -V o --version-control para detalles sobre cómo se determinan los nombres de los archivos de copia de seguridad.
--backup-if-mismatch
Hacer una copia de seguridad de un archivo si el parche no coincide exactamente con el archivo y si las copias de seguridad no se solicitan de otro modo. Este es el valor predeterminado a menos que patch cumpla con POSIX.
--no-backup-if-mismatch
No hacer una copia de seguridad de un archivo si el parche no coincide exactamente con el archivo y si las copias de seguridad no se solicitan de otro modo. Este es el valor predeterminado si patch cumple con POSIX.
-B pref o --prefix=pref
Utilizar el método simple para determinar los nombres de los archivos de copia de seguridad (vea la opción -V método o --version-control método) y añadir pref al nombre de un archivo al generar el nombre de su archivo de copia de seguridad.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

Por ejemplo, con -B /junk/ el nombre de archivo de copia de seguridad simple para src/patch/util.c es /junk/src/patch/util.c.
--binary
Escribe todos los archivos en modo binario, excepto la salida estándar y /dev/tty. Al leer, desactiva la heurística para transformar los finales de línea CRLF en finales de línea LF. Esta opción es necesaria en sistemas POSIX al aplicar parches generados en sistemas no POSIX a archivos no POSIX. (En sistemas POSIX, las lecturas y escrituras de archivos nunca transforman los finales de línea. En Windows, las lecturas y escrituras transforman los finales de línea por defecto, y los parches deben ser generados por diff --binary cuando los finales de línea son significativos.)
-c o --context
Interpreta el archivo de parche como un diff de contexto ordinario.
-d dir o --directory=dir
Cambia al directorio dir inmediatamente, antes de hacer nada más.
-D define o --ifdef=define
Usa la construcción #ifdef ... #endif para marcar cambios, con define como el símbolo diferenciador.
--dry-run
Imprime los resultados de aplicar los parches sin modificar realmente ningún archivo.
-e o --ed
Interpreta el archivo de parche como un script de ed.
-E o --remove-empty-files
Elimina los archivos de salida que queden vacíos después de aplicar los parches. Normalmente esta opción es innecesaria, ya que patch puede examinar las marcas de tiempo en la cabecera para determinar si un archivo debe existir después de aplicar el parche. Sin embargo, si la entrada no es un diff de contexto o si patch cumple con POSIX, patch no elimina los archivos parcheados vacíos a menos que se proporcione esta opción. Cuando patch elimina un archivo, también intenta eliminar cualquier directorio ancestral vacío.
-f o --force
Asume que el usuario sabe exactamente lo que está haciendo y no hace ninguna pregunta. Omite parches cuyas cabeceras no indican qué archivo se va a parchear; aplica parches a archivos aunque tengan la versión incorrecta para la línea Prereq: en el parche; y asume que los parches no están invertidos incluso si parecen estarlo. Esta opción no suprime los comentarios; usa -s para eso.
-F num o --fuzz=num
Establece el factor de "fuzz" máximo. Esta opción solo se aplica a diffs que tienen contexto, y hace que patch ignore hasta ese número de líneas de contexto al buscar lugares donde instalar un "hunk". Ten en cuenta que un factor de "fuzz" mayor aumenta la probabilidad de un parche defectuoso. El factor de "fuzz" por defecto es 2. Un factor de "fuzz" mayor o igual al número de líneas de contexto en el diff de contexto, normalmente 3, ignora todo el contexto.
-g num o --get=num
Esta opción controla las acciones de patch cuando un archivo está bajo control de RCS o SCCS, y no existe o está de solo lectura y coincide con la versión por defecto, o cuando un archivo está bajo control de ClearCase o Perforce y no existe. Si num es positivo, patch obtiene (o registra) el archivo del sistema de control de revisiones; si es cero, patch ignora RCS, ClearCase, Perforce y SCCS y no obtiene el archivo; y si es negativo, patch pregunta al usuario si debe obtener el archivo. El valor por defecto de esta opción se da por el valor de la variable de entorno PATCH_GET si está establecida; si no, el valor por defecto es cero.
--help
Imprime un resumen de las opciones y sale.
-i patchfile o --input=patchfile
Lee el parche desde patchfile. Si patchfile es -, lee desde la entrada estándar, que es la opción por defecto.
-l o --ignore-whitespace
Coincide con patrones de forma laxa, en caso de que las tabulaciones o los espacios se hayan modificado en tus archivos. Cualquier secuencia de uno o más espacios en el archivo de parche coincide con cualquier secuencia en el archivo original, y las secuencias de espacios al final de las líneas se ignoran. Los caracteres normales todavía deben coincidir exactamente. Cada línea del contexto debe seguir coincidiendo con una línea en el archivo original.
--merge o --merge=merge o --merge=diff3
Fusiona un archivo de parche en los archivos originales de forma similar a diff3(1) o merge(1). Si se encuentra un conflicto, patch emite una advertencia y delimita el conflicto con las líneas <<<<<<< y >>>>>>>. Un conflicto típico se verá así:
<<<<<<<
líneas del archivo original
|||||||
líneas originales del parche
=======
líneas nuevas del parche
>>>>>>>
El argumento opcional de --merge determina el formato de salida para los conflictos: el formato diff3 muestra la sección ||||||| con las líneas originales del parche; en el formato merge, esta sección falta. El formato merge es el valor por defecto.

Esta opción implica --forward y no tiene en cuenta la opción --fuzz=num.

-n o --normal
Interpreta el archivo de parche como un diff normal.
-N o --forward
Cuando un parche no se aplica, patch normalmente comprueba si el parche parece haber sido aplicado ya intentando aplicar inversamente el primer "hunk". La opción --forward lo evita. Ver también -R.
-o outfile o --output=outfile
Envía la salida a outfile en lugar de parchear los archivos in situ. No uses esta opción si outfile es uno de los archivos que se van a parchear. Cuando outfile es -, envía la salida a la salida estándar, y envía cualquier mensaje que normalmente iría a la salida estándar al error estándar.
-pnum o --strip=num
Elimina el prefijo más pequeño que contiene num barras inclinadas iniciales de cada nombre de archivo encontrado en el archivo de parche. Una secuencia de una o más barras inclinadas adyacentes se cuenta como una sola barra inclinada. Esto controla cómo se tratan los nombres de archivo encontrados en el archivo de parche, en caso de que guardes tus archivos en un directorio diferente al de la persona que envió el parche. Por ejemplo, suponiendo que el nombre de archivo en el archivo de parche fuera
/u/howard/src/blurfl/blurfl.c

establecer -p0 da el nombre de archivo completo sin modificar, -p1 da

u/howard/src/blurfl/blurfl.c

sin la barra inclinada inicial, -p4 da

blurfl/blurfl.c

y no especificar -p en absoluto solo te da blurfl.c. Lo que sea que obtengas se busca en el directorio actual, o en el directorio especificado por la opción -d.

--posix
Cumple más estrictamente con el estándar POSIX, de la siguiente manera.
  • Toma el primer archivo existente de la lista (antiguo, nuevo, índice) al deducir nombres de archivo de las cabeceras diff.
  • No elimina archivos que quedan vacíos después de parchear.
  • No pregunta si se deben obtener archivos de RCS, ClearCase, Perforce o SCCS.
  • Requiere que todas las opciones precedan a los archivos en la línea de comandos.
  • No realiza copias de seguridad de archivos cuando hay una discrepancia.
--quoting-style=word
Usa el estilo word para citar los nombres de salida. La palabra word debe ser una de las siguientes:
literal
Nombres de salida tal cual.
shell
Cita nombres para el shell si contienen metacaracteres del shell o causarían una salida ambigua.
shell-always
Cita nombres para el shell, incluso si normalmente no requerirían comillas.
c
Cita nombres como para una cadena del lenguaje C.
escape
Cita como con c excepto que omite los caracteres de comillas dobles circundantes.

Puedes especificar el valor por defecto de la opción --quoting-style con la variable de entorno QUOTING_STYLE. Si esa variable de entorno no está establecida, el valor por defecto es shell.

-r rejectfile o --reject-file=rejectfile
Coloca los rechazos en rejectfile en lugar del archivo .rej por defecto. Cuando rejectfile es -, descarta los rechazos.
-R o --reverse
Asume que este parche se creó con los archivos antiguo y nuevo intercambiados. (Sí, me temo que eso ocurre de vez en cuando, siendo la naturaleza humana lo que es.) patch intenta intercambiar cada "hunk" antes de aplicarlo. Los rechazos salen en el formato intercambiado. La opción -R no funciona con los scripts diff de ed porque hay muy poca información para reconstruir la operación inversa.

Si el primer "hunk" de un parche falla, patch invierte el "hunk" para ver si se puede aplicar de esa manera. Si se puede, se te pregunta si quieres que se establezca la opción -R. Si no se puede, el parche continúa aplicándose normalmente. (Nota: este método no puede detectar un parche invertido si es un diff normal y si el primer comando es una adición (es decir, debería haber sido una eliminación) ya que las adiciones siempre tienen éxito, debido al hecho de que un contexto nulo coincide en cualquier lugar. Por suerte, la mayoría de los parches añaden o cambian líneas en lugar de eliminarlas, por lo que la mayoría de los diffs normales invertidos comienzan con una eliminación, que falla, activando la heurística.)

--read-only=behavior
Actúa como se solicita al intentar modificar un archivo de solo lectura: ignore el problema potencial, warn sobre él (el valor por defecto), o fail.

NOTAS PARA QUIENES ENVÍAN PARCHES

Si utiliza la opción -N, no envíe una salida que se parezca a esto:

diff -Naur v2.0.29/prog/README prog/README
--- v2.0.29/prog/README Mon Mar 10 15:13:12 2024
+++ prog/README Mon Mar 17 14:58:22 2024

porque los dos nombres de archivo tienen un número diferente de barras inclinadas, y diferentes versiones de patch interpretan los nombres de archivo de forma diferente. Para evitar confusiones, envíe una salida que se parezca a esto en su lugar:

diff -Naur v2.0.29/prog/README v2.0.30/prog/README
--- v2.0.29/prog/README Mon Mar 10 15:13:12 2024
+++ v2.0.30/prog/README Mon Mar 17 14:58:22 2024

Evite enviar parches que comparen nombres de archivos de copia de seguridad como README.orig, ya que esto podría confundir a patch y hacer que aplique el parche a un archivo de copia de seguridad en lugar del archivo real. En su lugar, envíe parches que comparen los mismos nombres de archivo base en directorios diferentes, por ejemplo, old/README y new/README.

Tenga cuidado de no enviar parches invertidos, ya que esto hace que la gente se pregunte si ya aplicaron el parche.

Intente no tener su parche que modifique archivos derivados (por ejemplo, el archivo configure donde hay una línea configure: configure.ac en su makefile), ya que el destinatario debería poder regenerar los archivos derivados de todos modos. Si debe enviar diffs de archivos derivados, genere los diffs usando UTC, haga que los destinatarios apliquen el parche con la opción -Z o --set-utc, y haga que eliminen cualquier archivo sin parchear que dependa de archivos parcheados (por ejemplo, con make clean).

Si bien es posible que pueda salirse con la suya al incluir 582 listados de diff en un solo archivo, puede ser más prudente agrupar parches relacionados en archivos separados en caso de que algo salga mal.

DIAGNÓSTICOS

Los diagnósticos generalmente indican que patch no pudo analizar su archivo de parche.

Si se proporciona la opción --verbose, el mensaje Hmm... indica que hay texto sin procesar en el archivo de parche y que patch está intentando intuir si hay un parche en ese texto y, si es así, qué tipo de parche es.

El estado de salida de patch es 0 si todos los fragmentos se aplican correctamente, 1 si algunos fragmentos no se pueden aplicar o hubo conflictos de fusión, y 2 si hay problemas más graves. Al aplicar un conjunto de parches en un bucle, es recomendable comprobar este estado de salida para no aplicar un parche posterior a un archivo parcialmente parcheado.

ADVERTENCIAS

Los diffs de contexto no pueden representar de manera confiable la creación o eliminación de archivos vacíos, directorios vacíos o archivos especiales como enlaces simbólicos. Tampoco pueden representar cambios en los metadatos del archivo como la propiedad, los permisos o si un archivo es un enlace duro a otro. Si también se requieren cambios como estos, se deben adjuntar instrucciones separadas (por ejemplo, un script de shell) para lograrlos.

patch no puede saber si los números de línea están mal en un script ed, y solo puede detectar números de línea incorrectos en un diff normal cuando encuentra un cambio o una eliminación. Un diff de contexto con un factor de "fuzz" de 3 puede tener el mismo problema. Probablemente debería hacer un diff de contexto en estos casos para ver si los cambios tenían sentido. Por supuesto, compilar sin errores es una buena indicación de que el parche funcionó, pero no siempre.

patch generalmente produce resultados correctos, incluso cuando tiene que hacer muchas suposiciones. Sin embargo, los resultados solo se garantizan como correctos cuando el parche se aplica exactamente a la misma versión del archivo del que se generó el parche.

PROBLEMAS DE COMPATIBILIDAD

El estándar POSIX especifica un comportamiento que difiere del patch de GNU.

  • En POSIX patch, cuando no se utiliza -b, no se crean copias de seguridad, incluso cuando hay una discrepancia. En patch de GNU, este comportamiento se habilita con la opción --no-backup-if-mismatch, o cumpliendo con POSIX con la opción --posix o estableciendo la variable de entorno POSIXLY_CORRECT.
  • Al intuir el nombre del archivo que se va a parchear a partir del encabezado del parche, patch utiliza un método complicado que es opcionalmente compatible con POSIX. El método es equivalente a POSIX si los nombres de archivo en el encabezado del diff de contexto y la línea Index: son todos idénticos después de eliminar el prefijo. Su parche es normalmente compatible si los nombres de archivo de cada encabezado contienen el mismo número de barras inclinadas.
  • Límite a las siguientes opciones cuando envíe instrucciones destinadas a ser ejecutadas por cualquier persona que ejecute patch de GNU o un patch que cumpla con POSIX. Los espacios son opcionales en la siguiente lista. 
    -b
-c
-d dir
-D define
-e
-i patchfile
-l
-n
-N
-o outfile
-p num
-R
-r rejectfile
-u

ERRORES

Por favor, informe de los errores por correo electrónico a <bug-patch@gnu.org>.

Si el código se ha duplicado (por ejemplo, con #ifdef OLDCODE ... #else ... #endif), patch es incapaz de parchear ambas versiones y, si funciona, probablemente parcheará la incorrecta y le dirá que tuvo éxito.

Si aplica un parche que ya aplicó, patch cree que es un parche invertido y ofrece desaplicar el parche. Esto podría interpretarse como una característica.

Calcular cómo fusionar un fragmento es significativamente más difícil que usar el algoritmo difuso estándar. Fragmentos más grandes, más contexto, un mayor desplazamiento desde la ubicación original y una peor coincidencia ralentizan el algoritmo.
