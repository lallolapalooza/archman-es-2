PATCH(1P) Manual del programador POSIX PATCH(1P)

PROLOG

Esta página del manual forma parte del Manual del programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para obtener detalles sobre el comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

patch — aplica cambios a archivos

SINOPSIS

patch [-blNR] [-c|-e|-n|-u] [-d dir] [-D define] [-i patchfile]
    [-o outfile] [-p num] [-r rejectfile] [file]

DESCRIPCIÓN

La utilidad patch leerá un archivo fuente (parche) que contiene cualquiera de las cuatro formas de listado de diferencias (diff) producidas por la utilidad diff (contexto normal, contexto copiado, contexto unificado, o al estilo de ed) y aplicará esas diferencias a un archivo. Por defecto, patch leerá de la entrada estándar.

La utilidad patch intentará determinar el tipo del listado de diff, a menos que sea anulado por una opción -c, -e, -n o -u.

Si el archivo de parche contiene más de un parche, patch intentará aplicar cada uno de ellos como si provinieran de archivos de parche separados. (En este caso, la aplicación se asegurará de que el nombre del archivo de parche sea determinable para cada listado de diff.)

OPCIONES

La utilidad patch se ajustará a las Definiciones Base del volumen de POSIX.1‐2017, Sección 12.2, Directrices de sintaxis de utilidad.

Las siguientes opciones serán compatibles:

-b
Guardará una copia del contenido original de cada archivo modificado, antes de aplicar las diferencias, en un archivo del mismo nombre al que se le añadirá el sufijo .orig. Si el archivo ya existe, será sobrescrito; si se aplican múltiples parches al mismo archivo, el archivo .orig se escribirá solo para el primer parche. Cuando la opción -o outfile también se especifica, no se creará file.orig pero, si outfile ya existe, se creará outfile.orig.
-c
Interpreta el archivo de parche como una diferencia de contexto copiado (la salida de la utilidad diff cuando se especifican las opciones -c o -C).
-d dir
Cambiará el directorio actual a dir antes de procesar, como se describe en la sección DESCRIPCIÓN EXTENDIDA.
-D define
Marcará los cambios con una de las siguientes construcciones del preprocesador C:
#ifdef define
...
#endif
#ifndef define
...
#endif

opcionalmente combinada con la construcción del preprocesador C #else. Si el archivo parcheado se procesa con el preprocesador C, donde la macro define está definida, la salida contendrá los cambios del archivo de parche; de lo contrario, la salida no contendrá los parches especificados en el archivo de parche.

-e
Interpreta el archivo de parche como un script de ed, en lugar de un script de diff.
-i patchfile
Lee la información del parche del archivo nombrado por la ruta patchfile, en lugar de la entrada estándar.
-l
(La letra ele.) Causa que cualquier secuencia de caracteres de <espacio> en el script de diferencia coincida con cualquier secuencia de caracteres de <espacio> en el archivo de entrada. Otros caracteres se corresponderán exactamente.
-n
Interpreta el script como una diferencia normal.
-N
Ignora los parches cuyas diferencias ya se han aplicado al archivo; por defecto, los parches ya aplicados serán rechazados.
-o outfile
En lugar de modificar los archivos (especificados por el operando file o los listados de diferencia) directamente, escribe una copia del archivo referenciado por cada parche, con las diferencias apropiadas aplicadas, en outfile. Múltiples parches para un solo archivo se aplicarán a las versiones intermedias del archivo creadas por parches anteriores, y resultarán en múltiples versiones concatenadas del archivo escritas en outfile.
-p num
Para todas las rutas en el archivo de parche que indican los nombres de los archivos a parchear, elimina num componentes de ruta del principio de cada ruta. Si la ruta en el archivo de parche es absoluta, cualquier carácter de <barra> inicial se considerará el primer componente (es decir, -p 1 eliminará los caracteres de <barra> iniciales). Especificar -p 0 causará que se use la ruta completa. Si no se especifica -p, solo se usará el nombre base (el componente de ruta final).
-R
Invierte el sentido del script de parche; es decir, asume que el script de diferencia se creó de la versión nueva a la versión antigua. La opción -R no se puede usar con scripts de ed. La utilidad patch intentará invertir cada porción del script antes de aplicarla. Las diferencias rechazadas se guardarán en formato invertido. Si esta opción no se especifica, y hasta que se aplique con éxito una porción del archivo de parche, patch intentará aplicar cada porción en su sentido invertido así como en su sentido normal. Si el intento tiene éxito, se le pedirá al usuario que determine si la opción -R debe ser establecida.
-r rejectfile
Anula el nombre de archivo de rechazo por defecto. En el caso por defecto, el archivo de rechazo tendrá el mismo nombre que el archivo de salida, con el sufijo .rej añadido al final; ver Aplicación de Parches.
-u
Interpreta el archivo de parche como una diferencia de contexto unificado (la salida de la utilidad diff cuando se especifican las opciones -u o -U).

OPERANDOS

El siguiente operando será compatible:

file
Una ruta de un archivo a parchear.

STDIN

Ver la sección ARCHIVOS DE ENTRADA.

ARCHIVOS DE ENTRADA

Los archivos de entrada serán archivos de texto.

ARCHIVOS DE SALIDA

La salida de la utilidad patch, los archivos de guardado (sufijos .orig) y los archivos de rechazo (sufijos .rej) serán archivos de texto.

DESCRIPCIÓN EXTENDIDA

Un archivo de parche puede contener instrucciones de parcheo para más de un archivo; los nombres de archivo se determinarán según lo especificado en Determinación del nombre de archivo. Cuando se especifica la opción -b, para cada archivo parcheado, el original se guardará en un archivo con el mismo nombre al que se le añadirá el sufijo .orig.

Para cada archivo parcheado, también se puede crear un archivo de rechazo como se indica en Aplicación del parche. En ausencia de la opción -r, el nombre de este archivo se formará añadiendo el sufijo .rej al nombre de archivo original.

Formato del archivo de parche

El archivo de parche contendrá cero o más líneas de información de encabezado seguidas de uno o más parches. Cada parche contendrá cero o más líneas de identificación de nombre de archivo en el formato producido por las opciones -c, -C, -u o -U de la utilidad diff, y uno o más conjuntos de salida de diff, que se denominan habitualmente trozos.

La utilidad patch reconocerá la siguiente expresión en la información del encabezado:

Index: ruta

El archivo que se parcheará se llama ruta.

Si todas las líneas (incluidos los encabezados) dentro de un parche comienzan con la misma secuencia inicial de caracteres de <espacio>, la utilidad patch eliminará esta secuencia antes de continuar. Dentro de cada parche, si el tipo de diferencia es contexto común, la utilidad patch reconocerá las siguientes expresiones:

*** nombrearchivo marcaDeTiempo

Los parches surgieron de nombrearchivo.
--- nombrearchivo marcaDeTiempo

Los parches deben aplicarse a nombrearchivo.

Si el tipo de diferencia es contexto unificado, la utilidad patch reconocerá las siguientes expresiones:

--- nombrearchivo marcaDeTiempo

Los parches surgieron de nombrearchivo.
+++ nombrearchivo marcaDeTiempo

Los parches deben aplicarse a nombrearchivo.

Cada trozo dentro de un parche será la salida de diff para cambiar un rango de líneas dentro del archivo original. Los números de línea para trozos sucesivos dentro de un parche ocurrirán en orden ascendente.

Determinación del nombre de archivo

Si no se especifica ningún operando archivo, patch realizará los siguientes pasos para determinar el nombre de archivo a utilizar:

1.
Si el tipo de diff es contexto, la utilidad patch eliminará los componentes de la ruta (según lo especificado por la opción -p) del nombre de archivo en la línea que comienza con "***" (si el contexto copiado) o "---" (si el contexto unificado), luego probará la existencia de este archivo en relación con el directorio actual (o el directorio especificado con la opción -d). Si el archivo existe, la utilidad patch usará este nombre de archivo.
2.
Si el tipo de diff es contexto, la utilidad patch eliminará los componentes de la ruta (según lo especificado por la opción -p) del nombre de archivo en la línea que comienza con "---" (si el contexto copiado) o "+++" (si el contexto unificado), luego probará la existencia de este archivo en relación con el directorio actual (o el directorio especificado con la opción -d). Si el archivo existe, la utilidad patch usará este nombre de archivo.
3.
Si la información del encabezado contiene una línea que comienza con la cadena Index:, la utilidad patch eliminará los componentes de la ruta (según lo especificado por la opción -p) de esta línea, luego probará la existencia de este archivo en relación con el directorio actual (o el directorio especificado con la opción -d). Si el archivo existe, la utilidad patch usará este nombre de archivo.
4.
Si existe un directorio SCCS en el directorio actual, patch intentará ejecutar un comando get -e SCCS/s.nombrearchivo para recuperar una versión editable del archivo. Si el archivo existe, la utilidad patch usará este nombre de archivo.
5.
La utilidad patch mostrará un aviso en la salida estándar y solicitará interactivamente un nombre de archivo desde la terminal de control (por ejemplo, /dev/tty).

Aplicación del parche

Si está presente la opción -c, -e, -n o -u, la utilidad patch interpretará la información dentro de cada trozo como una diferencia de contexto copiada, una diferencia de ed, una diferencia normal o una diferencia de contexto unificado, respectivamente. En ausencia de cualquiera de estas opciones, la utilidad patch determinará el tipo de diferencia basándose en el formato de la información dentro del trozo.

Para cada trozo, la utilidad patch comenzará a buscar el lugar para aplicar el parche en el número de línea al principio del trozo, más o menos cualquier desplazamiento utilizado al aplicar el trozo anterior. Si no se encuentran líneas que coincidan con el contexto del trozo, patch buscará hacia adelante y hacia atrás al menos 1000 bytes un conjunto de líneas que coincidan con el contexto del trozo.

Si no se encuentra ningún lugar y se trata de una diferencia de contexto, se realizará otra búsqueda, ignorando la primera y la última línea de contexto. Si eso falla, se ignorarán las dos primeras y las dos últimas líneas de contexto y se realizará otra búsqueda. Las implementaciones pueden buscar más exhaustivamente lugares de instalación.

Si no se puede encontrar ningún lugar, la utilidad patch añadirá el trozo al archivo de rechazo. Un trozo rechazado que sea una diferencia de contexto copiada, una diferencia de ed o una diferencia normal se escribirá en formato de diferencia de contexto copiada, independientemente del formato del archivo de parche. Está definido por la implementación si un trozo rechazado que es una diferencia de contexto unificado se escribe en formato de diferencia de contexto copiada o en formato de diferencia de contexto unificado. Si la entrada fue una diferencia de estilo normal o ed, el archivo de rechazo puede contener diferencias con cero líneas de contexto. Los números de línea en los trozos del archivo de rechazo pueden ser diferentes de los números de línea en el archivo de parche, ya que reflejarán las ubicaciones aproximadas de los trozos fallidos en el nuevo archivo en lugar del antiguo.

Si el tipo de parche es una diferencia de ed, la implementación puede realizar el parcheo invocando la utilidad ed.

ESTADO DE SALIDA

Se devolverán los siguientes valores de salida:

 0
Finalización exitosa.
 1
Se escribieron una o más líneas en un archivo de rechazo.
>1
Ocurrió un error.

Los parches que no se puedan colocar correctamente en el archivo se escribirán en un archivo de rechazo.

USO DE LA APLICACIÓN

La opción -R no funciona con los scripts de ed porque hay muy poca información para reconstruir la operación inversa.

La opción -p permite personalizar un archivo de parche para las estructuras de directorios locales del usuario sin editar manualmente el archivo de parche. Por ejemplo, si el nombre de archivo en el archivo de parche era:

/curds/whey/src/blurfl/blurfl.c

Establecer -p 0 da la ruta completa sin modificar; -p 1 da:

curds/whey/src/blurfl/blurfl.c

sin la barra inicial, -p 4 da:

blurfl/blurfl.c

y no especificar -p en absoluto da:

blurfl.c .

FUNDAMENTACIÓN

Parte de la funcionalidad en las implementaciones históricas de patch no estaba especificada. Lo siguiente documenta aquellas características presentes en implementaciones históricas que no han sido especificadas.

Una funcionalidad eliminada fue la pseudo-opción '+' que permitía pasar un conjunto adicional de opciones y un operando de archivo de parche. Esto se consideró insuficientemente útil para estandarizar.

En implementaciones históricas, si la cadena "Prereq:" aparecía en el encabezado, la utilidad patch buscaría la información de versión correspondiente (la cadena especificada en el encabezado, delimitada por caracteres de <espacio> o el principio o final de una línea o el archivo) y

RATIONALE

The original proposal for this utility included a mechanism for identifying patches by a unique identifier string which could be stored in the file being patched.

This identifier was to be delimited by:

<<<<<<<

followed by the identifier, followed by

>>>>>>>

This mechanism was deleted as too simplistic and insufficiently trustworthy a mechanism to standardize. For example, if:

Prereq: 1.2

were in the header, the presence of a delimited 1.2 anywhere in the file would satisfy the prerequisite.

The following options were dropped from historical implementations of patch as insufficiently useful to standardize:

-b
The -b option historically provided a method for changing the name extension of the backup file from the default .orig. This option has been modified and retained in this volume of POSIX.1‐2017.
-F
The -F option specified the number of lines of a context diff to ignore when searching for a place to install a patch.
-f
The -f option historically caused patch not to request additional information from the user.
-r
The -r option historically provided a method of overriding the extension of the reject file from the default .rej.
-s
The -s option historically caused patch to work silently unless an error occurred.
-x
The -x option historically set internal debugging flags.

In some file system implementations, the saving of a .orig file may produce unwanted results. In the case of 12, 13, or 14-character filenames (on file systems supporting 14-character maximum filenames), the .orig file overwrites the new file. The reject file may also exceed this filename limit. It was suggested, due to some historical practice, that a <tilde> ('~') suffix be used instead of .orig and some other character instead of the .rej suffix. This was rejected because it is not obvious to the user which file is which. The suffixes .orig and .rej are clearer and more understandable.

The -b option has the opposite sense in some historical implementations—do not save the .orig file. The default case here is not to save the files, making patch behave more consistently with the other standard utilities.

The -w option in early proposals was changed to -l to match historical practice.

The -N option was included because without it, a non-interactive application cannot reject previously applied patches. For example, if a user is piping the output of diff into the patch utility, and the user only wants to patch a file to a newer version non-interactively, the -N option is required.

Changes to the -l option description were proposed to allow matching across <newline> characters in addition to just <blank> characters. Since this is not historical practice, and since some ambiguities could result, it is suggested that future developments in this area utilize another option letter, such as -L.

The -u option of GNU patch has been added, along with support for unified context formats.
