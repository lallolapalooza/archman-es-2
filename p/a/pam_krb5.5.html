NOMBRE

pam_krb5 - módulo PAM de Kerberos

SINOPSIS

auth            sufficient      pam_krb5.so minimum_uid=1000
session         required        pam_krb5.so minimum_uid=1000
account         required        pam_krb5.so minimum_uid=1000
password        sufficient      pam_krb5.so minimum_uid=1000

DESCRIPCIÓN

El módulo de servicio Kerberos para PAM, típicamente instalado en /lib/security/pam_krb5.so, proporciona funcionalidad para las cuatro operaciones de PAM: autenticación, gestión de cuentas, gestión de sesiones y gestión de contraseñas. pam_krb5.so es un objeto compartido que es cargado dinámicamente por el subsistema PAM según sea necesario, basándose en la configuración PAM del sistema. PAM es un sistema para conectar módulos externos de autenticación y gestión de sesiones, de modo que cada aplicación no tenga que conocer la mejor manera de verificar la autenticación del usuario o crear una sesión de usuario en ese sistema. Para obtener detalles sobre cómo configurar PAM en su sistema, consulte la página man de PAM, a menudo pam(7).

Estas son las acciones de este módulo cuando se llama desde cada grupo:

auth
Proporciona implementaciones de pam_authenticate() y pam_setcred(). La primera toma el nombre de usuario de la sesión PAM, solicita la contraseña del usuario (a menos que se configure para usar una contraseña ya introducida) y luego realiza una autenticación inicial de Kerberos, almacenando las credenciales obtenidas (si tiene éxito) en una caché de tickets temporal. La segunda, dependiendo de las banderas con las que se llame, toma el contenido de la caché de tickets temporal y lo escribe en una caché de tickets persistente propiedad del usuario o utiliza la caché de tickets temporal para refrescar una caché de tickets de usuario existente.

Las contraseñas de longitud igual o superior a PAM_MAX_RESP_SIZE octetos (normalmente 512 octetos) serán rechazadas, ya que las contraseñas excesivamente largas pueden ser utilizadas como un ataque de denegación de servicio.

Después de realizar la autenticación inicial, el módulo PAM de Kerberos intentará obtener tickets para una clave en el keytab del sistema local y luego verificará esos tickets. A menos que se realice este paso, la autenticación es vulnerable al spoofing de KDC, pero requiere que el sistema tenga una clave local y que el módulo PAM se ejecute como un usuario que pueda leer el archivo keytab (normalmente /etc/krb5.keytab. Puede apuntar el módulo PAM de Kerberos a un keytab diferente con la opción keytab. Si no se puede leer ese keytab o si no se encuentran claves en él, el comportamiento predeterminado (potencialmente inseguro) es omitir esta verificación. Si desea fallar la autenticación si los tickets obtenidos no se pueden verificar, establezca "verify_ap_req_nofail" a true en la sección [libdefaults] de /etc/krb5.conf. Tenga en cuenta que esto afectará a aplicaciones distintas de este módulo PAM.

Por defecto, cada vez que el usuario es autenticado, también se realizará una verificación básica de autorización utilizando krb5_kuserok(). El comportamiento predeterminado de esta función es verificar la cuenta del usuario en busca de un archivo .k5login y, si está presente, asegurarse de que el principal del usuario esté listado en ese archivo. Si .k5login no está presente, la verificación por defecto es asegurar que el principal del usuario esté en el realm local predeterminado y que la parte del usuario del principal coincida con el nombre de la cuenta (esto se puede cambiar configurando un mapeo de aname a localname personalizado en krb5.conf; consulte la documentación de Kerberos para obtener detalles). Esto se puede personalizar con varias opciones de configuración; consulte a continuación.

Si el nombre de usuario proporcionado a PAM contiene un "@" y Kerberos puede, tratando el nombre de usuario como un principal, mapearlo a un nombre de cuenta local, pam_authenticate() cambiará el usuario PAM a ese nombre de cuenta local. Esto permite a los usuarios iniciar sesión con su principal de Kerberos y dejar que Kerberos haga el mapeo a una cuenta. Esto se puede deshabilitar con la opción no_update_user. Tenga en cuenta, sin embargo, que esta funcionalidad no se puede usar con OpenSSH. OpenSSH rechazará nombres de usuario que no coincidan con cuentas locales antes de que se realice este remapeo y pasará una contraseña inválida al módulo PAM. Tenga también en cuenta que varios otros módulos PAM comunes, como pam_securetty, esperan poder buscar el usuario con getpwnam() y no pueden ser llamados antes de pam_krb5 al usar esta función.

Cuando se llama a pam_setcred() para inicializar una nueva caché de tickets, la variable de entorno KRB5CCNAME se establece en la ruta de esa caché de tickets. Por defecto, la caché se llamará /tmp/krb5cc_UID_RANDOM, donde UID es el UID del usuario y RANDOM son seis letras elegidas aleatoriamente. Esto se puede configurar con las opciones ccache y ccache_dir.

pam-krb5 no utiliza la ubicación predeterminada de la caché de tickets ni default_cc_name en la sección "[libdefaults]" de krb5.conf. La ubicación predeterminada de la caché compartiría una caché para todas las sesiones del mismo usuario, lo que causa un comportamiento confuso cuando el usuario cierra sesión en una de varias sesiones.

Si pam_setcred() inicializa una nueva caché de tickets, también configurará esa caché de tickets para que se elimine cuando se cierre la sesión PAM. Normalmente, el programa que llama (login, sshd, etc.) ejecutará el shell del usuario como un subproceso, esperará a que este termine y luego cerrará la sesión PAM, limpiando así la sesión del usuario.

session
Proporciona implementaciones de pam_open_session(), que es equivalente a llamar a pam_setcred() con la bandera PAM_ESTABLISH_CRED, y pam_close_session(), que destruye la caché de tickets creada por pam_setcred().
account
Proporciona una implementación de pam_acct_mgmt(). Todo lo que hace es realizar la misma verificación de autorización que la realizada por la implementación de pam_authenticate() descrita anteriormente.
password
Proporciona una implementación de pam_chauthtok(), que implementa los cambios de contraseña. Se le pide al usuario su contraseña existente (a menos que se configure para usar una ya introducida) y el módulo PAM obtiene las credenciales para el principal especial de Kerberos "kadmin/changepw". Luego pide al usuario una nueva contraseña, dos veces para asegurar que el usuario la introdujo correctamente (de nuevo, a menos que se configure para usar una ya introducida) y luego realiza un cambio de contraseña de Kerberos.

Las contraseñas de longitud igual o superior a PAM_MAX_RESP_SIZE octetos (normalmente 512 octetos) serán rechazadas, ya que las contraseñas excesivamente largas pueden ser utilizadas como un ataque de denegación de servicio.

A diferencia del módulo de contraseñas Unix normal, este módulo permitirá a cualquier usuario cambiar la contraseña de cualquier otro usuario si conoce la contraseña antigua. Además, a diferencia del módulo de contraseñas Unix normal, siempre se le pedirá a root la contraseña antigua, ya que root no tiene ningún estado especial en Kerberos. (Para cambiar contraseñas en Kerberos sin conocer la contraseña antigua, utilice en su lugar kadmin(8)).

Tanto las llamadas de gestión de cuentas como las de sesión del módulo PAM de Kerberos devolverán PAM_IGNORE si se llaman en el contexto de una sesión PAM para un usuario que no se autenticó con Kerberos (un código de retorno de "ignore" en el lenguaje de configuración PAM de Linux).

Tenga en cuenta que este módulo asume que la red está disponible para realizar una autenticación Kerberos. Si la red no está disponible, algunas bibliotecas Kerberos tienen tiempos de espera más largos que el tiempo de espera impuesto por el proceso de inicio de sesión. Esto significa que usar este módulo de forma imprudente puede hacer imposible iniciar sesión en la consola como root. Por esta razón, siempre debe usar las opciones ignore_root o minimum_uid, listar un módulo de autenticación local como pam_unix primero con un campo de control de "sufficient" para que el módulo PAM de Kerberos se omita si la autenticación de contraseña local fue exitosa.

Este no es el mismo módulo PAM que el módulo PAM de Kerberos disponible en Sourceforge, o el que se incluye en los sistemas Red Hat. Admite muchas de las mismas opciones, tiene algunas opciones adicionales y no admite algunas de las opciones que esos módulos sí tienen.

NAME

pam_krb5 - Kerberos V5 PAM module

DESCRIPTION

The pam_krb5 module provides PAM support for Kerberos V5 authentication. It can be used to authenticate users, check account validity, and set up Kerberos credentials.

This module handles the user authentication against a Kerberos KDC. It can be configured to use a variety of methods, including standard Kerberos principals, local user accounts mapped to Kerberos principals, and the .k5login file. The module's behavior can be controlled through various options specified either in the PAM configuration file or in the system krb5.conf file.

The following options can be used to configure the behavior of the pam_krb5 module:

Options can be specified in the PAM configuration file for the pam_krb5.so module. Any options not relevant to a particular PAM group (auth, account, password, session) will be silently ignored. Any of these options can be set in the PAM configuration as arguments listed after "pam_krb5.so". Some of the options can also be set in the system krb5.conf file; if this is possible, it will be noted below in the option description.

To set a boolean option in the PAM configuration file, just give the name of the option in the arguments. To set an option that takes an argument, follow the option name with an equal sign (=) and the value, with no separating whitespace. Whitespace in option arguments is not supported in the PAM configuration.

To set an option for the PAM module in the system krb5.conf file, put that option in the "[appdefaults]" section. All options must be followed by an equal sign (=) and a value, so for boolean options add "= true". The Kerberos PAM module will look for options either at the top level of the "[appdefaults]" section or in a subsection named "pam", inside or outside a section for the realm. For example, the following fragment of a krb5.conf file would set forwardable to true, minimum_uid to 1000, and set ignore_k5login only if the realm is EXAMPLE.COM.

[appdefaults]
    forwardable = true
    pam = {
        minimum_uid = 1000
        EXAMPLE.COM = {
            ignore_k5login = true
        }
    }

For more information on the syntax of krb5.conf, see krb5.conf(5). Note that options that depend on the realm will be set only on the basis of the default realm, either as configured in krb5.conf(5) or as set by the realm option described below. If the user authenticates to an account qualified with a realm, that realm will not be used when determining which options will apply.

There is no difference to the PAM module whether options are specified at the top level or in a "pam" section; the "pam" section is supported in case there are options that should be set for the PAM module but not for other applications.

If the same option is set in krb5.conf and in the PAM configuration, the latter takes precedent. Note, however, that due to the configuration syntax, there's no way to turn off a boolean option in the PAM configuration that was turned on in krb5.conf.

The start of each option description is annotated with the version of pam-krb5 in which that option was added with the current meaning.

Authorization

alt_auth_map=<format>
[3.12] This functions similarly to the search_k5login option. The <format> argument is used as the authentication Kerberos principal, with any %s in <format> replaced with the username. If the username contains an "@", only the part of the username before the realm is used to replace %s. If <format> contains a realm, it will be used; otherwise, the realm of the username (if any) will be appended to the result. There is no quote removal.

If this option is present, the default behavior is to try this alternate principal first and then fall back to the standard behavior if it fails. The primary usage is to allow alternative principals to be used for authentication in programs like sudo. Most examples will look like:

alt_auth_map=%s/root

which attempts authentication as the root instance of the username first and then falls back to the regular username (but see force_alt_auth and only_alt_auth).

This option also allows a cheap way to attempt authentication in an alternative realm first and then fall back to the primary realm. A setting like:

alt_auth_map=%s@EXAMPLE.COM

will attempt authentication in the EXAMPLE.COM realm first and then fall back on the local default realm. This is more convenient than running the module multiple times with multiple default realms set with realm, but it is very limited: only two realms can be tried, and the alternate realm is always tried first.

This option can be set in "[appdefaults]" in krb5.conf, although normally it doesn't make sense to do that; normally it is used in the PAM options of configuration for specific programs. It is only applicable to the auth and account groups. If this option is set for the auth group, be sure to set it for the account group as well or account authorization may fail.

force_alt_auth
[3.12] This option is used with alt_auth_map and forces authentication as the mapped principal if that principal exists in the KDC. Only if the KDC returns principal unknown does the Kerberos PAM module fall back to normal authentication. This can be used to force authentication with an alternate instance. If alt_auth_map is not set, it has no effect.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

ignore_k5login
[2.0] Never look for a .k5login file in the user's home directory. Instead, only check that the Kerberos principal maps to the local account name. The default check is to ensure the realm matches the local realm and the user portion of the principal matches the local account name, but this can be customized by setting up an aname to localname mapping in krb5.conf.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth and account groups.

ignore_root
[1.1] Do not do anything if the username is "root". The authentication and password calls will silently fail (allowing that status to be ignored via a control of "optional" or "sufficient"), and the account and session calls (including pam_setcred) will return PAM_IGNORE, telling the PAM library to proceed as if they weren't mentioned in the PAM configuration. This option is supported and will remain, but normally you want to use minimum_uid instead.

This option can be set in "[appdefaults]" in krb5.conf.

minimum_uid=<uid>
[2.0] Do not do anything if the authenticated account name corresponds to a local account and that local account has a UID lower than <uid>. If both of those conditions are true, the authentication and password calls will silently fail (allowing that status to be ignored via a control of "optional" or "sufficient"), and the account and session calls (including pam_setcred) will return PAM_IGNORE, telling the PAM library to proceed as if they weren't mentioned in the PAM configuration.

Using this option is highly recommended if you don't need to use Kerberos to authenticate password logins to the root account (which isn't recommended since Kerberos requires a network connection). It provides some defense in depth against user principals that happen to match a system account incorrectly authenticating as that system account.

This option can be set in "[appdefaults]" in krb5.conf.

only_alt_auth
[3.12] This option is used with alt_auth_map and forces the use of the mapped principal for authentication. It disables fallback to normal authentication in all cases and overrides search_k5login and force_alt_auth. If alt_auth_map is not set, it has no effect and the standard authentication behavior is used.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

search_k5login
[2.0] Normally, the Kerberos implementation of pam_authenticate attempts to obtain tickets for the authenticating username in the local realm. If this option is set and the local user has a .k5login file in their home directory, the module will instead open and read that .k5login file, attempting to use the supplied password to authenticate as each principal listed there in turn. If any of those authentications succeed, the user will be successfully authenticated; otherwise, authentication will fail. This option is useful for allowing password authentication (via console or sshd without GSS-API support) to shared accounts. If there is no .k5login file, the behavior is the same as normal. Using this option requires that the user's .k5login file be readable at the time of authentication.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

Kerberos Behavior

anon_fast
[4.6] Attempt to use Flexible Authentication Secure Tunneling (FAST) by first authenticating as the anonymous user (WELLKNOWN/ANONYMOUS) and using its credentials as the FAST armor. This requires anonymous PKINIT be enabled for the local realm, that PKINIT be configured on the local system, and that the Kerberos library support FAST and anonymous PKINIT.

FAST is a mechanism to protect Kerberos against password guessing attacks and provide other security improvements. To work, FAST requires that a ticket be obtained with a strong key to protect exchanges with potentially weaker user passwords. This option uses anonymous authentication to obtain that key and then uses it to protect the subsequent authentication.

If anonymous PKINIT is not available or fails, FAST will not be used and the authentication will proceed as normal.

OPTIONS

anon_fast
[4.3] This option allows the use of anonymous PKINIT to protect the FAST exchange. Anonymous PKINIT requires that the KDC support PKINIT and anonymous authentication, and that the local realm be configured to permit it. If these conditions are not met, FAST will not be used and the authentication will proceed normally. This option is intended to be used when the user does not have an existing ticket cache for the FAST credentials, use fast_ccache instead of this option. If both fast_ccache and anon_fast are set, the ticket cache named by fast_ccache will be tried first, and the Kerberos PAM module will fall back on attempting anonymous PKINIT if that cache could not be used.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth and password groups.

The operation is the same as if using the fast_ccache option, but the cache is created and destroyed automatically. If both fast_ccache and anon_fast options are used, the fast_ccache takes precedent and no anonymous authentication is done.

fast_ccache=<ccache_name>
[4.3] The same as anon_fast, but use an existing Kerberos ticket cache rather than anonymous PKINIT. This allows use of FAST with a realm that doesn't support PKINIT or doesn't support anonymous authentication.

<ccache_name> should be a credential cache containing a ticket obtained using a strong key, such as the randomized key for the host principal of the local system. If <ccache_name> names a ticket cache that is readable by the authenticating process and has tickets then FAST will be attempted. The easiest way to use this option is to use a program like k5start to maintain a ticket cache using the host's keytab. This ticket cache should normally only be readable by root, so this option will not be able to protect authentications done as non-root users (such as screensavers).

If no credentials are present in the ticket cache, or if the ticket cache does not exist or is not readable, FAST will not used and authentication will proceed as normal. However, if the credentials in that ticket cache are expired, authentication will fail if the KDC supports FAST.

To use anonymous PKINIT to protect the FAST exchange, use the anon_fast option instead. anon_fast is easier to configure, since no existing ticket cache is required, but requires PKINIT be available and configured and that the local realm support anonymous authentication. If both fast_ccache and anon_fast are set, the ticket cache named by fast_ccache will be tried first, and the Kerberos PAM module will fall back on attempting anonymous PKINIT if that cache could not be used.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth and password groups.

forwardable
[1.0] Obtain forwardable tickets. If set (to either true or false, although it can only be set to false in krb5.conf), this overrides the Kerberos library default set in the [libdefaults] section of krb5.conf.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

keytab=<path>
[3.0] Specifies the keytab to use when validating the user's credentials. The default is the default system keytab (normally /etc/krb5.keytab), which is usually only readable by root. Applications not running as root that use this PAM module for authentication may wish to point it to another keytab the application can read. The first principal found in the keytab will be used as the principal for credential verification.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

realm=<realm>
[2.2] Set the default Kerberos realm and obtain credentials in that realm, rather than in the normal default realm for this system. If this option is used, it should be set for all groups being used for consistent results. This setting will affect authorization decisions since it changes the default realm. This setting will also change the service principal used to verify the obtained credentials to be in the specified realm.

If you only want to set the realm assumed for user principals without changing the realm for authorization decisions or the service principal used to verify credentials, see the user_realm option.

renew_lifetime=<lifetime>
[2.0] Obtain renewable tickets with a maximum renewable lifetime of <lifetime>. <lifetime> should be a Kerberos lifetime string such as "2d4h10m" or a time in minutes. If set, this overrides the Kerberos library default set in the [libdefaults] section of krb5.conf.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

ticket_lifetime=<lifetime>
[3.0] Obtain tickets with a maximum lifetime of <lifetime>. <lifetime> should be a Kerberos lifetime string such as "2d4h10m" or a time in minutes. If set, this overrides the Kerberos library default set in the [libdefaults] section of krb5.conf.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

user_realm
[4.6] Obtain credentials in the specified realm rather than in the default realm for this system. If this option is used, it should be set for all groups being used for consistent results (although the account group currently doesn't care about realm). This will not change authorization decisions. If the obtained credentials are supposed to allow access to a shell account, the user will need an appropriate .k5login file entry or the system will have to have a custom aname_to_localname mapping.

PAM Behavior

clear_on_fail
[3.9] When changing passwords, PAM first does a preliminary check through the complete password stack, and then calls each module again to do the password change. After that preliminary check, the order of module invocation is fixed. This means that even if the Kerberos password change fails (or if one of the other password changes in the stack fails), other password PAM modules in the stack will still be called even if the failing module is marked required or requisite. When using multiple password PAM modules to synchronize passwords between multiple systems when they change, this behavior can cause unwanted differences between the environments.

Setting this option provides a way to work around this behavior. If this option is set and a Kerberos password change is attempted and fails (due to network errors or password strength checking on the KDC, for example), this module will clear the stored password in the PAM stack. This will force any subsequent modules that have use_authtok set to fail so that those environments won't get out of sync with the password in Kerberos. The Kerberos PAM module will not meddle with the stored password if it skips the user due to configuration such as minimum_uid.

Unfortunately, setting this option interferes with other desirable PAM configurations, such as attempting to change the password in Kerberos first and falling back on the local Unix password database if that fails. It therefore isn't the default. Turn it on (and list pam_krb5 first after pam_cracklib if used) when synchronizing passwords between multiple environments.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the password group.

debug
[1.0] Log more verbose trace and debugging information to syslog at LOG_DEBUG priority, including entry and exit from each of the external PAM interfaces (except pam_close_session).

This option can be set in "[appdefaults]" in krb5.conf.

defer_pwchange
[3.11] By default, pam-krb5 lets the Kerberos library handle prompting for a password change if an account's password is expired during the auth group. If this fails, pam_authenticate() returns an error.

According to the PAM standard, this is not the correct way to handle expired passwords. Instead, pam_authenticate() should return success without attempting a password change, and then pam_acct_mgmt() should return PAM_NEW_AUTHTOK_REQD, at which point the calling application is responsible for either rejecting the authentication or calling pam_chauthtok(). However, following the standard requires that all applications call pam_acct_mgmt() and check its return status; otherwise, expired accounts may be able to successfully authenticate. Many applications do not do this.

If this option is set, pam-krb5 uses the fully correct PAM mechanism for handling expired accounts instead of failing in pam_authenticate(). Due to the security risk of widespread broken applications, be very careful about enabling this option. It should normally only be turned on to solve a specific problem (such as using Solaris Kerberos libraries that don't support prompting for password changes during authentication), and then only for specific applications known to call pam_acct_mgmt() and check its return status properly.

This option is only supported when pam-krb5 is built with MIT Kerberos. If built against Heimdal, this option does nothing and normal expired password change handling still happens. (Heimdal is missing the required API to implement this option, at least as of version 1.6.)

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

fail_pwchange
[4.2] By default, pam-krb5 lets the Kerberos library handle prompting for a password change if an account's password is expired during the auth group.

Opciones de autenticación

allow_empty_pass
[4.0] If this option is set, expired passwords are instead treated as an authentication failure identical to an incorrect password. Also see defer_pwchange and force_pwchange.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

force_pwchange
[3.11] If this option is set and authentication fails with a Kerberos error indicating the user's password is expired, attempt to immediately change their password during the authenticate step. Under normal circumstances, this is unnecessary. Most Kerberos libraries will do this for you, and setting this option will prompt the user twice to change their password if the first attempt (done by the Kerberos library) fails. However, some system Kerberos libraries (such as Solaris's) have password change prompting disabled in the Kerberos library; on those systems, you can set this option to simulate the normal library behavior.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

no_update_user
[4.7] Normally, if pam-krb5 is able to canonicalize the principal to a local name using krb5_aname_to_localname() or similar calls, it changes the PAM_USER variable for this PAM session to the canonicalized local name. Setting this option disables this behavior and leaves PAM_USER set to the initial authentication identity.

This option can be set in "[appdefaults]" in krb5.conf and is only applicable to the auth group.

silent
[1.0] Don't show messages and errors from Kerberos, such as warnings of expiring passwords, to the user via the prompter. This is equivalent to the behavior when the application passes in PAM_SILENT, but can be set in the PAM configuration.

This option is only applicable to the auth and password groups.

trace=<archivo-log>
[4.6] Habilita el registro de rastreo de la biblioteca Kerberos en el archivo de log especificado si es compatible con la biblioteca Kerberos. Esto está pensado para depuración temporal. El archivo especificado se añadirá sin más comprobaciones de seguridad, así que no especifique un archivo en un directorio públicamente escribible como /tmp.

PKINIT

pkinit_anchors=<anclas>
[3.0] Al realizar la autenticación PKINIT, utiliza <anclas> como anclas de confianza del cliente. Normalmente, es una referencia a un archivo que contiene las autoridades de certificación de confianza. Esta opción solo se utiliza si se establecen try_pkinit o use_pkinit.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable a los grupos auth y password.

pkinit_prompt
[3.0] Antes de intentar la autenticación PKINIT, solicita al usuario que inserte una tarjeta inteligente. Es posible que desee establecer esta opción para programas como gnome-screensaver que llaman a PAM tan pronto como se toca el ratón y no dan al usuario la oportunidad de introducir la tarjeta inteligente primero. Se ignora cualquier información introducida en el primer aviso. Si se establece try_pkinit, un usuario que desee utilizar una contraseña en su lugar puede simplemente pulsar Enter y luego introducir su contraseña de forma normal. Esta opción solo se utiliza si se establecen try_pkinit o use_pkinit.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable a los grupos auth y password.

pkinit_user=<userid>
[3.0] Al realizar la autenticación PKINIT, utiliza <userid> como ID de usuario. El valor de esta cadena depende en gran medida del tipo de implementación PKINIT que estés utilizando, pero generalmente será algo como: 
PKCS11:/usr/lib/pkcs11/lib/soft-pkcs11.so

para especificar el módulo a utilizar con una tarjeta inteligente. También puede apuntar a un certificado de usuario u otros tipos de IDs de usuario. Consulte la documentación de la biblioteca Kerberos para obtener más detalles. Esta opción solo se utiliza si se establecen try_pkinit o use_pkinit.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable a los grupos auth y password.

preauth_opt=<opción>
[3.3] Establece una opción de preautenticación (actualmente solo aplicable cuando se compila con MIT Kerberos). <opción> es un par clave/valor con la clave separada del valor por "=" o una opción booleana (en cuyo caso se activa). En krb5.conf, varias opciones deben separarse por espacios en blanco. En la configuración PAM, esta opción se puede especificar varias veces para establecer varias opciones. En cualquier caso, <opción> no puede contener espacios en blanco.

El uso principal de esta opción, al menos en el futuro cercano, será para establecer opciones para el soporte PKINIT de MIT Kerberos. Para obtener la lista completa de opciones posibles, consulte la documentación del plugin PKINIT. En el momento de escribir esto, "X509_user_identity" es equivalente a pkinit_user y "X509_anchors" es equivalente a pkinit_anchors. "flag_DSA_PROTOCOL" solo se puede establecer a través de esta opción.

Cualquier configuración realizada con esta opción se aplica después de las opciones pkinit_anchors y pkinit_user, por lo que si se realiza una configuración equivalente a través de preauth_opt, probablemente anulará la otra configuración.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable a los grupos auth y password. Tenga en cuenta que no hay forma de eliminar una configuración realizada en krb5.conf utilizando la configuración PAM, pero las opciones establecidas en la configuración PAM se aplican después de las opciones establecidas en krb5.conf y, por lo tanto, pueden anular configuraciones anteriores.

try_pkinit
[3.0] Intenta la autenticación PKINIT antes de probar una contraseña normal. Probablemente también necesitará establecer la opción de configuración pkinit_user. Si PKINIT falla, el módulo PAM recurrirá a la autenticación de contraseña normal. Esta opción actualmente solo se admite si pam-krb5 se compiló contra Heimdal 0.8rc1 o posterior o MIT Kerberos 1.6.3 o posterior.

Si esta opción está configurada y pam-krb5 se compila contra MIT Kerberos, y PKINIT falla y el módulo recurre a la autenticación por contraseña, la contraseña del usuario no se almacenará en la pila PAM para módulos posteriores. Este es un error en la interacción entre el módulo y MIT Kerberos que requiere una reestructuración del método de autenticación PKINIT para solucionarlo.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable a los grupos auth y password.

use_pkinit
[3.0, 4.9 para MIT Kerberos] Requiere autenticación PKINIT. Probablemente también necesitará establecer la opción de configuración pkinit_user. Si PKINIT falla, la autenticación fallará. Esta opción solo se admite si pam-krb5 se compiló contra Heimdal 0.8rc1 o posterior o MIT Kerberos 1.12 o posterior.

Tenga en cuenta que, con MIT Kerberos, esta opción se implementa utilizando un respondedor sin un solicitante, por lo que los mensajes informativos de las bibliotecas Kerberos o KDC durante la autenticación no se mostrarán.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable a los grupos auth y password.

banner=<banner>
[3.0] Por defecto, los avisos al cambiar la contraseña son: 
Contraseña Kerberos actual:
Introduce la nueva contraseña Kerberos:
Vuelve a introducir la nueva contraseña Kerberos:

La cadena "Kerberos" se inserta para que los usuarios no se confundan sobre qué contraseña están cambiando. Establecer esta opción reemplaza la palabra "Kerberos" por lo que sea que se establezca esta opción. Establecer esta opción en la cadena vacía elimina completamente la palabra antes de "contraseña:".

Si se establece en la configuración PAM, <banner> no puede contener espacios en blanco. Si desea un valor que contenga espacios en blanco, establécelo en krb5.conf.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable al grupo password.

expose_account
[3.0] Por defecto, el aviso de contraseña del módulo PAM Kerberos es simplemente "Contraseña:". Esto evita la fuga de información sobre el reino del sistema o las conversiones de cuenta a principal. Si se establece esta opción, la cadena "para <principal>" se añade antes de los dos puntos, donde <principal> es el principal del usuario. Esta cadena también se añade antes de los dos puntos en los avisos al cambiar la contraseña del usuario.

Habilitar esta opción con ChallengeResponseAuthentication habilitado en OpenSSH puede causar problemas a algunos clientes ssh que solo reconocen "Contraseña:" como aviso. Esta opción se deshabilita automáticamente si search_k5login está habilitado ya que el principal mostrado sería inexacto.

Esta opción se puede establecer en "[appdefaults]" en krb5.conf y solo es aplicable a los grupos auth y password.

force_first_pass
[4.0] Utiliza la contraseña obtenida por un módulo de autenticación o contraseña anterior para autenticar al usuario sin solicitarla de nuevo. Si ningún módulo anterior obtuvo la contraseña del usuario, falla sin solicitarla. También vea try_first_pass y use_first_pass para versiones más débiles de esta opción.

Esta opción solo es aplicable a los grupos auth y password. Para el grupo password, se aplica solo a la opción antigua

CAVEATS

Asegúrese de incluir este módulo en el grupo de sesión, así como en el grupo de autenticación cuando lo utilice para inicios de sesión interactivos. De lo contrario, algunas aplicaciones (como OpenSSH) no configurarán correctamente la caché de tickets del usuario.

La biblioteca Kerberos, a través de pam-krb5, pedirá al usuario que cambie su contraseña si esta ha caducado, pero al usar OpenSSH, esto solo funcionará cuando ChallengeResponseAuthentication esté habilitado. A menos que esta opción esté habilitada, OpenSSH no pasa mensajes PAM al usuario y solo puede responder a una solicitud de contraseña simple.

Si está utilizando MIT Kerberos, tenga en cuenta que a los usuarios cuyas contraseñas han caducado no se les pedirá que cambien su contraseña a menos que la configuración del KDC para su reino en [realms] en krb5.conf contenga una configuración master_kdc o, si utiliza registros SRV de DNS, tenga una entrada de DNS para _kerberos-master, así como para _kerberos.

pam_authenticate() devuelve un fallo cuando se llama para una cuenta ignorada, lo que requiere que el administrador del sistema utilice "optional" o "sufficient" para ignorar el módulo y pasar al siguiente. Es argumentablemente más correcto devolver PAM_IGNORE, que hace que el módulo se ignore como si no estuviera en la configuración, pero esto aumenta el riesgo de agujeros de seguridad inadvertidos al listar pam-krb5 como el único módulo de autenticación.

Este módulo trata la contraseña vacía como un fallo de autenticación en lugar de intentar usar esa contraseña para evitar un comportamiento de solicitud no deseado en las bibliotecas Kerberos. Si tiene un principal Kerberos que intencionalmente tiene una contraseña vacía, no funcionará con este módulo.

Este módulo no actualizará una caché de tickets existente si se llama con un UID o GID efectivo diferente al UID o GID real, ya que la actualización de una caché de tickets existente requiere confiar en la variable de entorno KRB5CCNAME y el entorno no debe ser confiado en un contexto setuid.

Se sabe que versiones antiguas de OpenSSH llaman a pam_authenticate seguido de pam_setcred(PAM_REINITIALIZE_CRED) sin llamar primero a pam_open_session, solicitando así que se renueve una caché de tickets existente (similar a lo que querría un salvapantallas) en lugar de solicitar la creación de una nueva caché de tickets. Dado que este comportamiento es indistinguible a nivel de PAM de un salvapantallas, pam-krb5 cuando se usa con estas versiones antiguas de OpenSSH actualizará la caché de tickets del demonio OpenSSH en lugar de configurar una nueva caché de tickets para el usuario. La caché de tickets resultante tendrá los permisos correctos, pero no se llamará correctamente ni se hará referencia en el entorno del usuario y será sobrescrita por el próximo inicio de sesión del usuario. La mejor solución a este problema es actualizar OpenSSH. No estoy seguro exactamente cuándo se solucionó este problema, pero al menos OpenSSH 4.3 y posteriores no lo presentan.
