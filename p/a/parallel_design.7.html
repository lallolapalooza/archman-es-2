Diseño de GNU Parallel

Este documento describe las decisiones de diseño tomadas en el desarrollo de GNU parallel y el razonamiento detrás de ellas. Dará una visión general de por qué parte del código tiene el aspecto que tiene, y ayudará a los nuevos mantenedores a entender mejor el código.

Programa en un archivo

GNU parallel es un script de Perl en un solo archivo. Es orientado a objetos, pero a diferencia de los scripts normales de Perl, cada clase no está en su propio archivo. Esto se debe a la experiencia del usuario: El objetivo es que, en un apuro, el usuario pueda hacer que GNU parallel funcione simplemente copiando un solo archivo: No hay necesidad de meterse con variables de entorno como PERL5LIB.

Elección del lenguaje de programación

GNU parallel está diseñado para poder ejecutarse en sistemas antiguos. Eso significa que no puede depender de que se instale un compilador, y especialmente no de un compilador de un lenguaje que tenga menos de 20 años.

El objetivo es que puedas usar GNU parallel en cualquier sistema, incluso si no tienes permitido instalar software adicional.

De todos los sistemas que he experimentado, todavía no he visto un sistema que tuviera GCC instalado y que no tuviera Perl. Lo mismo ocurre con Rust, Go, Haskell y otros lenguajes más jóvenes. Sin embargo, he visto sistemas con Perl sin ninguno de los compiladores mencionados.

La mayoría de los sistemas modernos también tienen Python2 o Python3 instalados, pero aún así no puedes estar seguro de qué versión, y dado que Python2 no puede ejecutarse bajo Python3, Python no es una opción.

Perl tiene el beneficio adicional de que implementar la cadena de reemplazo {= perlexpr =} fue bastante fácil.

La principal desventaja es que Perl es lento. Por lo tanto, hay una sobrecarga de 3-10 ms/trabajo y 1 ms/MB de salida (e incluso más si usas --tag).

Estilo antiguo de Perl

GNU parallel utiliza algunas construcciones antiguas y obsoletas. Esto se debe al objetivo de poder ejecutarse en instalaciones antiguas. Actualmente, el objetivo es CentOS 3.9 y Perl 5.8.0.

Escalabilidad hacia arriba y hacia abajo

El sistema más pequeño en el que se prueba GNU parallel es un ASUS WL500gP de 32 MB. El más grande es una máquina de 2 TB con 128 núcleos. Escala hasta alrededor de 100 máquinas, dependiendo de la duración de cada trabajo.

Retroceso exponencial

GNU parallel espera activamente (busy waits). Esto se debe a que la razón por la que un trabajo no se inicia puede deberse a la carga promedio (al usar --load), y por lo tanto no tendría sentido simplemente esperar a que un trabajo termine. En cambio, la carga promedio debe ser reevaluada regularmente. La carga promedio no es la única razón: --timeout tiene un problema similar.

Para no consumir demasiada CPU, GNU parallel duerme durante períodos de tiempo cada vez más largos si no sucede nada, hasta un máximo de 1 segundo.

Compatibilidad de la shell

El objetivo es que GNU parallel funcione igual de bien en cualquier shell. Sin embargo, en la práctica, GNU parallel se desarrolla en bash y, por lo tanto, las pruebas en otras shells se limitan a los errores reportados.

Cuando se encuentra una incompatibilidad, a menudo no hay una solución fácil: Arreglar el problema en csh a menudo lo rompe en bash. En estos casos, la solución suele ser usar un pequeño script de Perl y llamarlo.

env_parallel

env_parallel es un script de shell ficticio que se ejecutará si env_parallel no es un alias o una función y le dirá al usuario cómo activar el alias/función para las shells compatibles.

El alias o función copiará el entorno actual y ejecutará el comando con GNU parallel en la copia del entorno.

El problema es que no se puede acceder a todo el entorno actual dentro de Perl. Por ejemplo, alias, funciones y variables de shell no exportadas.

La idea es, por lo tanto, tomar el entorno y ponerlo en $PARALLEL_ENV, que GNU parallel antepondrá a cada comando.

La única forma de tener acceso al entorno es directamente desde la shell, por lo que el programa debe estar escrito en un script de shell que se cargará (sourced) y deberá lidiar con el dialecto de la shell relevante.

env_parallel.*

Estos son los archivos que implementan el alias o la función env_parallel para una shell dada. Se podría argumentar que deberían colocarse en algún lugar poco visible bajo /usr/lib, pero al colocarlos en tu PATH, se vuelve trivial encontrar la ruta a ellos y cargarlos (source):

source `which env_parallel.foo`

La belleza es que se pueden colocar en cualquier lugar del PATH sin que el usuario tenga que conocer la ubicación. Por lo tanto, si el PATH del usuario incluye /afs/bin/i386_fc5 o /usr/pkg/parallel/bin o /usr/local/parallel/20161222/sunos5.6/bin, los archivos se pueden colocar en el directorio que tenga más sentido para el administrador del sistema.

env_parallel.bash / env_parallel.sh / env_parallel.ash / env_parallel.dash / env_parallel.zsh / env_parallel.ksh / env_parallel.mksh

env_parallel.(bash|sh|ash|dash|ksh|mksh|zsh) define la función env_parallel. Utiliza alias y typeset para volcar la configuración (con algunas excepciones) en $PARALLEL_ENV antes de ejecutar GNU parallel.

Después de que GNU parallel finaliza, $PARALLEL_ENV se elimina.

env_parallel.csh

env_parallel.csh tiene dos propósitos: Si env_parallel no es un alias: convertirlo en un alias que establece $PARALLEL con argumentos y llama a env_parallel.csh.

Si env_parallel es un alias, entonces env_parallel.csh utiliza $PARALLEL como los argumentos para GNU parallel.

Exporta el entorno escribiendo una definición de variable en un archivo para cada variable. Las definiciones de alias se añaden a este archivo. Finalmente, el archivo se coloca en $PARALLEL_ENV.

Luego se llama a GNU parallel y se elimina $PARALLEL_ENV.

env_parallel.fish

Primero, todas las definiciones de funciones se generan usando un bucle y functions.

Volcar las definiciones de variables escalares es más difícil.

fish puede representar caracteres no imprimibles de (al menos) 2 maneras. Para evitar problemas, todos los escalares se convierten a codificación \XX.

Luego se crean comandos para generar las definiciones y se separan por NUL.

Esto se canaliza a un script de Perl que codifica todos los valores. Los elementos de la lista se añadirán con dos espacios.

Finalmente, \n se convierte en \1 porque las variables de fish no pueden contener \n. GNU parallel posteriormente convertirá todos los \1 de $PARALLEL_ENV a \n.

Todo esto se guarda en $PARALLEL_ENV.

Se llama a GNU parallel y se elimina $PARALLEL_ENV.

parset (compatible con sh, ash, dash, bash, zsh, ksh, mksh)

parset es una función de shell. Esta es la razón por la que parset puede establecer variables: se ejecuta en la shell que lo está llamando.

También es la razón por la que parset no funciona cuando los datos se canalizan hacia él: ... | parset ... hace que parset se inicie en una subshell, y, por lo tanto, cualquier cambio en el entorno no puede regresar a la shell que lo llama.

Ranuras de trabajo

La forma más fácil de explicar lo que hace GNU parallel es suponer que hay un número de ranuras de trabajo, y cuando una ranura queda disponible, un trabajo de la cola se ejecutará en esa ranura. Pero originalmente GNU parallel no modelaba las ranuras de trabajo en el código. Las ranuras de trabajo se han añadido para hacer posible el uso de {%} como cadena de reemplazo.

avanza, el trabajo el slot solo se puede calcular en el momento en que un slot queda disponible. Por lo tanto, se ha implementado como una pila con evaluación perezosa: Si sacas uno de una pila vacía, la pila se extiende en uno. Cuando un trabajo termina, se vuelve a colocar el slot de trabajo disponible en la pila.

Esta implementación también significa que si vuelves a ejecutar los mismos trabajos, no puedes asumir que los trabajos obtendrán los mismos slots. Y si usas ejecuciones remotas, no puedes asumir que un slot de trabajo dado permanecerá en el mismo servidor remoto. Esto se duplica ya que el número de slots de trabajo se puede ajustar sobre la marcha (dando a --jobs un nombre de archivo).

Versión del protocolo Rsync

rsync 3.1.x utiliza el protocolo 31, que no es compatible con la versión 2.5.7. Eso significa que no puedes enviar un archivo a un sistema remoto usando el protocolo 31 de rsync si el sistema remoto utiliza 2.5.7. rsync no retrocede automáticamente al protocolo 30.

GNU parallel no requiere el protocolo 31, por lo que si la versión de rsync es >= 3.1.0, se añade --protocol 30 para forzar a los rsync más nuevos a hablar con la versión 2.5.7.

Compresión

GNU parallel almacena la salida en archivos temporales. --compress comprime los datos almacenados en búfer. Esto es un poco complicado porque no debería haber archivos que limpiar si GNU parallel es interrumpido por un corte de energía.

GNU parallel primero selecciona un programa de compresión. Si el usuario no ha seleccionado uno, se utiliza el primero de estos que esté en $PATH: pzstd lbzip2 pbzip2 zstd pixz lz4 pigz lzop plzip lzip gzip lrz pxz bzip2 lzma xz clzip. Están ordenados por velocidad en una máquina de 128 núcleos.

Esquemáticamente, la configuración es la siguiente:

comando iniciado por parallel | comprimir > archivo_temporal
cattail archivo_temporal | descomprimir | parallel que lee la salida

La configuración se duplica tanto para la salida estándar (stdout) como para el error estándar (stderr).

GNU parallel canaliza la salida del comando ejecutado hacia el programa de compresión, que guarda los datos en un archivo temporal. GNU parallel registra el PID del programa de compresión. Al mismo tiempo, se inicia un pequeño script de Perl (llamado cattail arriba): Básicamente hace cat seguido de tail -f, pero también elimina el archivo temporal tan pronto como se lee el primer byte y verifica continuamente si el PID del programa de compresión está muerto. Si el programa de compresión está muerto, cattail lee el resto del archivo temporal y sale.

Como la mayoría de los programas de compresión escriben una cabecera al inicio, el archivo temporal en la práctica es eliminado por cattail después de unos 40 ms.

Más detalladamente funciona así:

bash ( comando ) |
  sh ( emptywrapper ( bash ( compound compress ) >archivo_temporal ) )
cattail ( rm archivo_temporal; compound decompress ) < archivo_temporal

Esta configuración compleja sirve para asegurar que el programa de compresión solo se inicie si hay entrada. Esto significa que cada trabajo causará la ejecución de 8 procesos. Si se combina con --keep-order, estos procesos se ejecutarán hasta que se imprima el trabajo.

--fifo
perl -e '($s,$c,$f) = @ARGV;
  # mkfifo $PARALLEL_TMP
  system "mkfifo", $f;
  # spawn $shell -c $command &
  $pid = fork || exec $s, "-c", $c;
  open($o,">",$f) || die $!;
  # cat > $PARALLEL_TMP
  while(sysread(STDIN,$buf,131072)){
     syswrite $o, $buf;
  }
  close $o;
  # waitpid to get the exit code from $command
  waitpid $pid,0;
  # Cleanup
  unlink $f;
  exit $?/256;' $SHELL -c $COMMAND $PARALLEL_TMP

Esta es una forma elaborada de: mkfifo {}; ejecuta $COMMAND en segundo plano usando $SHELL; copia STDIN a {}; espera a que se complete el proceso en segundo plano; elimina {} y sale con el código de salida de $COMMAND.

Se hace de esta manera para ser compatible con *csh/fish.

--pipepart
< $FILE perl -e 'while(@ARGV) {
    sysseek(STDIN,shift,0) || die;
    $left = shift;
    while($read =
          sysread(STDIN,$buf,
                  ($left > 131072 ? 131072 : $left))){
      $left -= $read;
      syswrite(STDOUT,$buf);
    }
  }' $STARTPOS $LENGTH

Esto leerá $LENGTH bytes de $FILE comenzando en $STARTPOS y lo enviará a STDOUT.

El orden del encapsulado es importante:

  • $PARALLEL_ENV, que se establece en env_parallel.*, debe anteponerse al comando primero, ya que el comando puede contener variables o funciones exportadas.
  • --nice/--cat/--fifo deben hacerse en la máquina remota.
  • --pipepart/--pipe deben hacerse en la máquina local dentro de --tmux.

Opciones de conveniencia --nice --basefile --transfer --return --cleanup --tmux --group --compress --cat --fifo --workdir --tag --tagstring

Todas estas son opciones de conveniencia que facilitan la realización de una tarea. Pero, lo que es más importante: están probadas para funcionar también en casos extremos. Tome --nice como ejemplo:

nice parallel command ...

funcionará bien. Pero cuando se ejecuta de forma remota, necesita mover el comando nice para que se ejecute en el servidor:

parallel -S server nice command ...

Y esto volverá a funcionar bien, siempre que ejecute un solo comando. Cuando ejecute un comando compuesto, necesita que nice se aplique a todo el comando, y se vuelve aún más difícil:

parallel -S server -q nice bash -c 'command1 ...; cmd2 | cmd3'

No es imposible, pero al usar --nice, GNU parallel hará lo correcto por usted. De manera similar al transferir archivos: se vuelve difícil cuando los nombres de archivo contienen espacios, :, `, *, u otros caracteres especiales.

Para ejecutar los comandos en una sesión de tmux, básicamente solo necesita citar el comando. Para comandos simples eso es fácil, pero cuando los comandos contienen caracteres especiales, se vuelve mucho más difícil de hacer correctamente.

--compress no solo comprime la salida estándar (stdout) sino también el error estándar (stderr); y lo hace en archivos, que están abiertos pero eliminados, por lo que una falla no dejará estos archivos activos.

--cat y --fifo son fáciles de hacer manualmente, hasta que desea limpiar el archivo temporal y conservar el código de salida del comando.

El verdadero problema surge cuando intenta combinar varios de estos: Hacerlo correctamente para todos los casos extremos es casi imposible de hacer manualmente.

--shard

La forma sencilla de implementar el sharding sería:

1.
iniciar n trabajos,
2.
dividir cada línea en columnas,
3.
seleccionar los datos de la columna relevante
4.
calcular un valor hash a partir de los datos
5.
tomar el módulo n del valor hash
6.
pasar la línea completa al slot de trabajo que tiene el valor calculado

Desafortunadamente, Perl es bastante lento para calcular el valor hash (y algo lento para dividir en columnas).

Una solución es usar un lenguaje compilado para la división y el hashing, pero eso iría en contra de los criterios de diseño de no depender de un compilador.

Afortunadamente, esas tareas se pueden paralelizar. Por lo tanto, GNU parallel inicia n sharders que realizan los pasos 2-6, y pasa bloques de 100k a cada uno de ellos en un modo de asignación por turnos. Para asegurarse de que estos sharders calculen el hash de la misma manera, $PERL_HASH_SEED se establece en el mismo valor para todos los sharders.

Ejecutar n sharders presenta un nuevo problema: en lugar de tener n salidas (una para cada valor calculado), ahora tiene n salidas para cada uno de los n valores, lo que da un total de n*n salidas; y necesita fusionar estas n*n salidas en n salidas.

Esto se puede hacer simplemente ejecutando 'parallel -j0 --lb cat ::: outputs_for_one_value', pero eso es bastante ineficiente, ya que genera un proceso por cada archivo. En su lugar, se ejecuta el código central de 'parcat', que también es un poco más rápido.

Todos los sharders y parcats se comunican a través de tuberías con nombre que se eliminan tan pronto como se abren.

Shell shock

El error shell shock en bash no afectó a GNU parallel, pero las soluciones sí. bash introdujo primero funciones en variables llamadas: BASH_FUNC_myfunc() y más tarde lo cambió a BASH_FUNC_myfunc%%. Al transferir funciones, GNU parallel lee la función y la convierte en una definición de función, que se copia al sistema remoto y se ejecuta antes de que se ejecute el comando real. Por lo tanto, GNU parallel necesita saber cómo leer la función.

A partir de la versión 20150122, GNU parallel prueba tanto la versión con () como la versión con %%, y la definición de función funciona en versiones de bash anteriores y posteriores a shell shock.

El envoltorio del sistema remoto

El envoltorio del sistema remoto realiza algunas inicializaciones antes de iniciar el comando en el sistema remoto.

Hacer que las comillas no sean necesarias codificando todo en hexadecimal

Cuando ejecuta ssh server foo, foo debe citarse una vez:

ssh server "echo foo; echo bar"

Si ejecuta ssh server1 ssh server2 foo, foo debe citarse dos veces:

ssh server1 ssh server2 \'"echo foo; echo bar"\'

GNU parallel evita esto empaquetando todo en valores hexadecimales y ejecutando un comando que no necesita comillas:

perl -X -e GNU_Parallel_worker,eval+pack+q/H10000000/,join+q//,@ARGV

Este comando lee hexadecimal de la línea de comandos y lo convierte en bytes que luego se evalúan como una expresión de Perl.

La cadena GNU_Parallel_worker no es necesaria. Simplemente está ahí para que el usuario sepa que este proceso es GNU parallel trabajando.

Ctrl-C y error estándar (stderr)

Si el usuario presiona Ctrl-C, espera que los trabajos se detengan. Esto funciona sin problemas si los trabajos se ejecutan localmente. Desafortunadamente, no es tan simple si los trabajos se ejecutan de forma remota.

Si los trabajos remotos se ejecutan en un tty usando ssh -tt, Ctrl-C funciona, pero toda la salida al error estándar (stderr) se envía a la salida estándar (stdout). Esto no es lo que el usuario espera.

Si los trabajos remotos se ejecutan sin un tty usando ssh (sin -tt), la salida al error estándar (stderr) se mantiene en stderr, pero Ctrl-C no mata los trabajos remotos. Esto no es lo que el usuario espera.

Entonces, lo que se necesita es una forma de tener ambos. Parece que la razón por la que Ctrl-C no mata los trabajos remotos es porque el shell no propaga la señal de colgar desde sshd. Pero cuando sshd muere, el padre del shell de inicio se convierte en init (identificador de proceso 1). Por lo tanto, al ejecutar un envoltorio de Perl para monitorear el ppid y matar al hijo si el ppid se convierte en 1, Ctrl-C funciona y stderr se mantiene en stderr.

Ctrl-C, sin embargo, mata la conexión ssh, por lo que se pierde cualquier salida de un proceso remoto que muere.

Para poder matar a todos los (bis)*nietos, se inicia un nuevo grupo de procesos.

--nice

El nice del proceso remoto se realiza mediante setpriority(0,0,$nice). Algunos sistemas antiguos no implementan esto y --nice no es compatible en ellos.

Estableciendo $PARALLEL_TMP

$PARALLEL_TMP es utilizado por --fifo y --cat y debe apuntar a un archivo inexistente en $TMPDIR. Este nombre de archivo se calcula en el sistema remoto.

El envoltorio

El envoltorio se ve así:

$shell = $PARALLEL_SHELL || $SHELL;
$tmpdir = $TMPDIR || $PARALLEL_REMOTE_TMPDIR;
$nice = $opt::nice;
$termseq = $opt::termseq;
# Comprobar que $tmpdir se puede escribir
-w $tmpdir ||
    die("$tmpdir no se puede escribir.".
      " Establecer PARALLEL_REMOTE_TMPDIR");
# Establecer $PARALLEL_TMP a un nombre de archivo inexistente en $TMPDIR
do {
    $ENV{PARALLEL_TMP} = $tmpdir."/par".
      join"", map { (0..9,"a".."z","A".."Z")[rand(62)] } (1..5);
} while(-e $ENV{PARALLEL_TMP});
# Establecer $script a un nombre de archivo inexistente en $TMPDIR
do {
    $script = $tmpdir."/par".
      join"", map { (0..9,"a".."z","A".."Z")[rand(62)] } (1..5);
} while(-e $script);
# Crear un script a partir del código hexadecimal
# que se elimina a sí mismo y ejecuta los comandos
open($fh,">",$script) || die;
# ' necesario debido a rc-shell
print($fh("rm \'$script\'\n",$bashfunc.$cmd));
close $fh;
my $parent = getppid;
my $done = 0;
$SIG{CHLD} = sub { $done = 1; };
$pid = fork;
unless($pid) {
    # Crear un grupo de procesos propio para poder matarlo con HUP más tarde
    eval { setpgrp };
    # Establecer valor nice
    eval { setpriority(0,0,$nice) };
    # Ejecutar el script
    exec($shell,$script);
    die("exec fallido: $!");
}
while((not $done) and (getppid == $parent)) {
    # El ppid no se ha cambiado, por lo que sshd está activo
    # Duerme exponencialmente hasta 1 segundo
    $s = $s < 1 ? 0.001 + $s * 1.03 : $s;
    select(undef, undef, undef, $s);
}
if(not $done) {
    # sshd está muerto: el usuario presionó Ctrl-C
    # Matar según --termseq
    my @term_seq = split/,/,$termseq;
    if(not @term_seq) {
      @term_seq
= ("TERM",200,"TERM",100,"TERM",50,"KILL",25); } while(@term_seq && kill(0,-$pid)) { kill(shift @term_seq, -$pid); select(undef, undef, undef, (shift @term_seq)/1000); } } wait; exit ($? & 127 ? 128 + ($? & 127) : 1 + ($? >> 8));

Transferencia de variables y funciones

La transferencia de variables y funciones dadas por --env se realiza ejecutando un script de Perl de forma remota que llama al comando real. El script de Perl establece $ENV{variable} al valor correcto antes de ejecutar un shell que ejecuta la definición de la función seguida del comando real.

La función env_parallel copia el entorno actual completo en la variable de entorno PARALLEL_ENV. Esta variable es recogida por GNU parallel y se utiliza para crear el script de Perl mencionado anteriormente.

bzip2 codificado en Base64

csh limita las palabras de los comandos a 1024 caracteres. Esto a menudo es demasiado poco cuando GNU parallel codifica variables de entorno y envuelve el comando con diferentes plantillas. Todas estas se combinan y entrecomillan en una sola palabra, que a menudo es más larga que 1024 caracteres.

Cuando la línea a ejecutar tiene más de 1000 caracteres, GNU parallel codifica la línea a ejecutar. La codificación comprime la línea a ejecutar con bzip2, la convierte a base64, divide la base64 en bloques de 1000 caracteres (para que csh no falle) y la antepone con este script de Perl que decodifica, descomprime y evalúa la línea.

@GNU_Parallel=("use","IPC::Open3;","use","MIME::Base64");
eval "@GNU_Parallel";
$SIG{CHLD}="IGNORE";
# Busca bzip2. No encontrado => usa la ruta predeterminada
my $zip = (grep { -x $_ } "/usr/local/bin/bzip2")[0] || "bzip2";
# $in = stdin en $zip, $out = stdout de $zip
my($in, $out, $eval);
open3($in, $out, ">&STDERR", $zip, "-dc");
if (my $perlpid = fork) {
    close $in;
    $eval = join "", <$out>;
    close $out;
} else {
    close $out;
    # Canaliza base64 decodificado a 'bzip2 -dc'
    print $in (decode_base64(join "", @ARGV));
    close $in;
    exit;
}
wait;
eval $eval;

Perl y bzip2 deben estar instalados en el sistema remoto, pero una pequeña prueba mostró que bzip2 está instalado por defecto en todas las plataformas que ejecutan GNU parallel, por lo que esto no es un gran problema.

La ventaja adicional de esto es que ahora se pueden transferir entornos mucho más grandes, ya que estarán por debajo del límite de 131072 caracteres de bash.

¿Qué shell usar?

Diferentes shells se comportan de manera diferente. Un comando que funciona en tcsh puede no funcionar en bash. Por lo tanto, es importante que se utilice el shell correcto cuando GNU parallel ejecuta comandos.

GNU parallel se esfuerza por utilizar el shell correcto. Si GNU parallel se llama desde tcsh, utilizará tcsh. Si se llama desde bash, utilizará bash. Lo hace examinando el proceso (abuelo)*padre: Si el proceso (abuelo)*padre es un shell, usa ese shell; de lo contrario, examina el padre de este (abuelo)*padre. Si ninguno de los (abuelo)*padres son shells, entonces se utiliza $SHELL.

Esto hará lo correcto si se llama desde:

  • un shell interactivo
  • un script de shell
  • un script de Perl en `` o usando system si se llama como una cadena única.

Si bien estos cubren la mayoría de los casos, hay situaciones en las que fallará:

  • Cuando se ejecuta usando exec.
  • Cuando se ejecuta como el último comando usando -c desde otro shell (porque algunos shells usan exec): 
    zsh% bash -c "parallel 'echo {} is not run in bash; \
     set | grep BASH_VERSION' ::: This"

    Puede solucionar esto añadiendo '&& true':

    zsh% bash -c "parallel 'echo {} is run in bash; \
     set | grep BASH_VERSION' ::: This && true"
  • Cuando se ejecuta en un script de Perl usando system con parallel como la primera cadena: 
    #!/usr/bin/perl
system("parallel",'setenv a {}; echo $a'," ::: ",2);

    Aquí depende de qué shell se utilice para llamar al script de Perl. Si el script de Perl se llama desde tcsh funcionará bien, pero si se llama desde bash fallará, porque el comando setenv no es conocido por bash.

Si GNU parallel adivina mal en estas situaciones, establezca el shell usando $PARALLEL_SHELL.

Ejecutar siempre comandos en un shell

Si el comando es un comando simple sin redirección ni configuración de variables, el comando *podría* ejecutarse sin iniciar un shell. Por ejemplo, este simple grep que coincide con 'ls ' o ' wc >> c':

parallel "grep -E 'ls | wc >> c' {}" ::: foo

podría ejecutarse como:

system("grep","-E","ls | wc >> c","foo");

Sin embargo, tan pronto como el comando sea un poco más complejo, *debe* iniciarse un shell:

parallel "grep -E 'ls | wc >> c' {} | wc >> c" ::: foo
parallel "LANG=C grep -E 'ls | wc >> c' {}" ::: foo

Es imposible saber cómo interpretar '| wc >> c' sin analizar la cadena (¿es '|' una tubería en el shell o una alternancia en una expresión regular de grep? ¿Es 'LANG=C' un comando en csh o la configuración de una variable en bash? ¿Es '>>' una redirección o parte de una expresión regular?).

Además de esto, los scripts de envoltura a menudo requerirán que se inicie un shell.

La desventaja es que necesita entrecomillar los caracteres especiales del shell dos veces:

parallel echo '*' ::: Esto expandirá el asterisco
parallel echo "'*'" ::: Esto no lo hará
parallel "echo '*'" ::: Esto no lo hará
parallel echo '\*' ::: Esto no lo hará
parallel echo '\'*'\'' ::: Esto no lo hará
parallel -q echo '*' ::: Esto no lo hará

-q entrecomillará todos los caracteres especiales, por lo que la redirección no funcionará: esto imprime '* > out.1' y *no* guarda '*' en el archivo out.1:

parallel -q echo "*" ">" out.{} ::: 1

GNU parallel intenta cumplir con el Principio de la Menor Sorpresa (POLA), y el requisito de usar -q es difícil de entender cuando no se ve el panorama completo.

Entrecomillado

El entrecomillado depende del shell. Para la mayoría de los shells, el entrecomillado '- se utiliza para cadenas que contienen caracteres especiales.

Para tcsh/csh, el salto de línea se entrecomilla como \ seguido de un salto de línea. Otros caracteres especiales también se entrecomillan con \.

Para rc, todo se entrecomilla usando '.

--pipepart vs. --pipe

Aunque --pipe y --pipepart parecen muy similares para el usuario, se implementan de manera muy diferente.

Con --pipe, GNU parallel lee los bloques de la entrada estándar (stdin), que luego se pasan al comando en la entrada estándar (stdin); por lo tanto, cada bloque es procesado por el propio GNU parallel. Esta es la razón por la que --pipe alcanza un máximo de alrededor de 500 MB/seg.

--pipepart, por otro lado, primero identifica en qué posiciones de bytes comienzan los bloques y cuánto duran. Lo hace buscando en el archivo por el tamaño de un bloque y luego leyendo hasta que encuentra el final de un bloque. La búsqueda explica por qué GNU parallel no conoce el número de línea y por qué -L/-l y -N no funcionan.

Con un tamaño de bloque y archivo razonable, esta búsqueda es más de 1000 veces más rápida que leer el archivo completo. Las posiciones de bytes se pasan luego a un pequeño script que lee de la posición X a Y y envía la salida a la salida estándar (stdout). Este pequeño script se antepone al comando y el comando completo se ejecuta como si GNU parallel hubiera estado en su modo normal. El script se ve así:

< file perl -e 'while(@ARGV) {
   sysseek(STDIN,shift,0) || die;
   $left = shift;
   while($read = sysread(STDIN,$buf,
                         ($left > 131072 ? 131072 : $left))){
     $left -= $read; syswrite(STDOUT,$buf);
   }
}' startbyte length_in_bytes

Ofrece 1 GB/s por núcleo.

En lugar del script, se intentó usar dd, pero muchas versiones de dd no admiten la lectura de un byte a otro y podrían causar datos parciales. Vea este ejemplo sorprendente:

yes | dd bs=1024k count=10 | wc

Ajuste de --block-size

Cada vez que GNU parallel detecta un registro más grande que --block-size, aumenta el tamaño del bloque en un 30%. Un --block-size pequeño da un rendimiento muy pobre; al aumentar exponencialmente el tamaño del bloque, el rendimiento no se verá afectado.

GNU parallel desperdiciará potencia de CPU si --block-size no contiene un registro completo, porque intenta encontrar un registro completo y fallará. Por lo tanto, la recomendación es usar un --block-size > 2 registros, para que siempre obtenga al menos un registro completo cuando lea un bloque.

Si usa -N, entonces --block-size debe ser lo suficientemente grande como para contener N+1 registros.

Cálculo automático de --block-size

Con --pipepart, GNU parallel puede calcular --block-size automáticamente. Un --block-size de -1 usará un tamaño de bloque para que cada ranura de trabajo reciba aproximadamente 1 bloque. --block -2 pasará 2 bloques a cada ranura de trabajo y -n pasará n bloques a cada ranura de trabajo.

Esto se puede hacer porque --pipepart lee de archivos, y podemos calcular el tamaño total de la entrada.

--jobs y --onall

Al ejecutar los mismos comandos en muchos servidores, ¿qué debería significar --jobs? ¿Es el número de servidores en los que ejecutar en paralelo? ¿Es el número de trabajos ejecutados en paralelo en cada servidor?

GNU parallel permite que --jobs represente el número de servidores en los que ejecutar en paralelo. Esto es para hacer posible ejecutar una secuencia de comandos (que no se puede paralelizar) en cada servidor, pero ejecutar la misma secuencia en múltiples servidores.

--shuf

Al usar --shuf para mezclar los trabajos, todos los trabajos se leen, luego se mezclan y finalmente se ejecutan. Al usar SQL, esto hace que el --sqlmaster sea la parte que mezcla los trabajos. Los --sqlworker simplemente ejecutan según el número de secuencia.

--csv

--pipepart es incompatible con --csv porque puedes tener registros como:

a,b,c
a,"
a,b,c
a,b,c
a,b,c
",c
a,b,c

Aquí el segundo registro contiene un campo multilínea que parece registros. Dado que --pipepart no lee el archivo completo al buscar terminadores de registro, puede comenzar a leer dentro de este campo multilínea, lo que sería incorrecto.

Almacenamiento en búfer en disco

GNU parallel almacena la salida en búfer, porque si la salida no se almacena en búfer, tienes que ser ridículamente cuidadoso con los tamaños para evitar la mezcla de salidas (ver el excelente ejemplo en https://catern.com/posts/pipes.html).

GNU parallel almacena en búfer en disco en $TMPDIR usando archivos, que se eliminan tan pronto como se crean, pero que permanecen abiertos. Por lo tanto, incluso si GNU parallel se interrumpe por un corte de energía, no habrá archivos que limpiar después. Otra ventaja es que el sistema de archivos es consciente de que estos archivos se perderán en caso de un fallo, por lo que no es necesario sincronizarlos al disco.

Esto da la extraña situación de que un disco puede estar completamente utilizado, pero no hay archivos visibles en él.

Almacenamiento parcial en búfer en memoria

Al usar los formatos de salida SQL y CSV, GNU Parallel tiene que leer toda la salida en memoria. Cuando se ejecuta normalmente, solo leerá la salida de un solo trabajo. Pero al usar --linebuffer, cada línea impresa también se almacenará en búfer en memoria, para todos los trabajos que se estén ejecutando actualmente.

Si la memoria es escasa, no utilice el formato de salida SQL/CSV con --linebuffer.

Disco lleno

GNU parallel almacena en búfer en disco. Si el disco está lleno, los datos pueden perderse. Para comprobar si el disco está lleno, GNU parallel escribe un archivo de 8193 bytes cada segundo. Si este archivo se escribe correctamente, se elimina inmediatamente. Si no se escribe correctamente, el disco está lleno. El tamaño 8193 se eligió porque 8192 daba resultados incorrectos en algunos sistemas de archivos, mientras que 8193 hacía lo correcto en todos los sistemas de archivos probados.

Uso de memoria

Normalmente, GNU parallel utiliza alrededor de 17 MB de RAM constantemente, sin importar cuántos trabajos o cuánta salida haya. Hay algunas cosas que hacen que el uso de memoria aumente:

  • Múltiples fuentes de entrada. GNU parallel lee una fuente de entrada solo una vez. Esto es por diseño, ya que una fuente de entrada puede ser un flujo (por ejemplo, FIFO, tubería, entrada estándar (stdin)) que no se puede rebobinar y leer de nuevo. Al leer una única fuente de entrada, la memoria se libera tan pronto como el trabajo se completa, manteniendo así el uso de memoria constante.

    Pero al leer múltiples fuentes de entrada, GNU parallel conserva los valores ya leídos para generar todas las combinaciones con otras fuentes de entrada.

  • Calcular el número de trabajos. --bar, --eta y --halt xx% usan total_jobs() para calcular el número total de trabajos. Esto lo hace generando las estructuras de datos para todos los trabajos. Todas estas estructuras de datos de trabajos se almacenarán en memoria y ocuparán alrededor de 400 bytes por trabajo.
  • Almacenamiento en búfer de una línea completa. --linebuffer leerá una línea completa por trabajo en ejecución. Una línea de salida muy larga (por ejemplo, 1 GB sin \n) aumentará temporalmente el uso de RAM: desde que se lee el principio de la línea hasta que se imprime la línea.
  • Almacenamiento en búfer de la salida completa de un solo trabajo. Esto ocurre al usar --results *.csv/*.tsv o --sql*. Aquí, GNU parallel leerá toda la salida de un solo trabajo y la guardará como csv/tsv o SQL.

Separadores de argumentos ::: :::: :::+ ::::+

El separador de argumentos ::: se eligió porque nunca he visto ::: utilizado en ningún comando. La opción natural -- sería una mala idea, ya que no es improbable que el comando plantilla contenga --. He visto :: utilizado en lenguajes de programación para separar clases, y no quería que el usuario se confundiera pensando que el separador tenía algo que ver con clases.

::: también crea una separación visual, lo cual es bueno si hay varios :::.

Cuando se eligió :::, :::: surgió como una extensión bastante natural.

Al vincular fuentes de entrada, fue necesario decidir alguna forma de indicar la vinculación de ::: y ::::. Se eligieron :::+ y ::::+, para que fueran similares a ::: y ::::.

En 2022 me di cuenta de que /// habría sido una opción aún mejor, porque no se puede tener un archivo llamado ///, mientras que SÍ se puede tener un archivo llamado :::.

Cadenas de reemplazo de Perl, {= =}, y --rpl

Las abreviaturas para las cadenas de reemplazo hacen que un comando parezca más críptico. Diferentes usuarios necesitarán diferentes cadenas de reemplazo. En lugar de inventar más abreviaturas, obtienes cadenas de reemplazo más flexibles si pueden ser programadas por el usuario.

El lenguaje Perl se eligió porque GNU parallel está escrito en Perl y fue fácil y razonablemente rápido ejecutar el código proporcionado por el usuario.

Si un usuario necesita la misma cadena de reemplazo programada una y otra vez, puede que quiera crear su propia abreviatura para ella. Para eso sirve --rpl. Funciona tan bien que incluso las propias abreviaturas de GNU parallel se implementan usando --rpl.

En el código Perl, los bigramas {= y =} rara vez existen. Parecen un par coincidente y se pueden introducir en todos los teclados. Esto los convirtió en buenos candidatos para encerrar la expresión de Perl en las cadenas de reemplazo. Se rechazó otro candidato ,, y ,, porque no parecen un par coincidente. Se creó --parens, para que los usuarios aún puedan usar ,, y ,, si lo desean: --parens ,,,,

Sin embargo, internamente, {= y =} se reemplazan por \257< y \257>. Esto es para simplificar la creación de expresiones regulares. Solo necesitas mirar un carácter hacia adelante y nunca tener que mirar hacia atrás.

Suite de pruebas

GNU parallel utiliza su propio marco de pruebas. Esto se debe en gran medida a razones históricas. Maneja razonablemente bien las pruebas que dependen de cuánto tiempo dura una prueba determinada (por ejemplo, más de 10 segundos es un éxito, pero menos es un fallo). Paraleliza la mayoría de las pruebas, pero es fácil forzar que una prueba se ejecute como la única prueba (lo que puede ser importante para problemas de tiempo). Maneja razonablemente bien las pruebas que fallan intermitentemente. Detecta qué pruebas fallaron y las empuja al principio, por lo que al ejecutar la suite de pruebas nuevamente, las pruebas que fallaron más recientemente se ejecutan primero.

Si GNU parallel adoptara un marco de pruebas real, esos elementos serían importantes.

Dado que muchas pruebas dependen del hardware en el que se ejecutan, estas pruebas fallan cuando se ejecutan en un hardware diferente al para el que se escribió la prueba.

Cuando se corrigen la mayoría de los errores, se agrega una prueba para que no vuelva a aparecer. Sin embargo, a veces es difícil crear el entorno en el que se manifiesta el error, especialmente si el error solo aparece a veces. Uno de los problemas más difíciles fue hacer que una máquina comenzara a usar intercambio sin llevarla al límite.

Tiempo de ejecución mediano

Usar un porcentaje para --timeout hace que GNU parallel calcule el tiempo de ejecución mediano de un trabajo. La mediana es un mejor indicador del tiempo de ejecución esperado que el promedio, porque a menudo habrá valores atípicos que tardarán mucho más que el tiempo de ejecución normal.

Para evitar mantener todos los tiempos de ejecución en memoria, se realizó una implementación de remedian (Rousseeuw et al).

Mensajes de error y advertencias

Mensajes de error como: ERROR, Not found, y 42 no son muy útiles. GNU parallel se esfuerza por...

Diseño de GNU Parallel

If you have encountered an error then it is likely that the error message tells you what is wrong. The error message is usually accompanied by an exit code. If the exit code is 2 then it means that the command line arguments were wrong.

  • ¿Por qué salió mal?
  • ¿Qué se puede hacer al respecto?

Determinar el número de CPU

CPU es un término ambiguo. Puede significar el número de zócalos rellenos (es decir, el número de chips físicos). Puede significar el número de núcleos (es decir, el número de núcleos de cómputo físicos). Puede significar el número de núcleos de hyperthreading (es decir, el número de núcleos virtuales, algunos de los cuales pueden tener hyperthreading).

En ark.intel.com, Intel utiliza los términos *núcleos* e *hilos* para el número de núcleos físicos y el número de núcleos con hyperthreading, respectivamente.

GNU parallel utiliza *CPU* como el número de unidades de cómputo y los términos *zócalos*, *núcleos* e *hilos* para especificar cómo se calcula el número de unidades de cómputo.

Cálculo de la carga

Contrariamente a lo obvio, --load no utiliza la carga promedio. Esto se debe a que la carga promedio aumenta demasiado lentamente. En su lugar, utiliza ps para enumerar el número de hilos en estado corriendo o bloqueado (estado D, O o R). Esto proporciona una carga instantánea.

Dado que el cálculo remoto de la carga puede ser lento, se genera un proceso para ejecutar ps y colocar el resultado en un archivo, que luego se utiliza la próxima vez.

Matar trabajos

GNU parallel mata trabajos. Puede ser debido a --memfree, --halt, o cuando GNU parallel encuentra una condición de la que no puede recuperarse. Cada trabajo se inicia como su propio grupo de procesos. De esta manera, cualquier hijo (o nieto) también será eliminado. El grupo de procesos se elimina con la especificación mencionada en --termseq.

Interfaz SQL

GNU parallel utiliza el DBURL de GNU sql para proporcionar el software de base de datos, nombre de usuario, contraseña, host, puerto, base de datos y tabla en una sola cadena.

El DBURL debe apuntar a un nombre de tabla. La tabla se eliminará y se creará. La razón para no reutilizar una tabla existente es que el usuario puede haber agregado más fuentes de entrada que requerirían más columnas en la tabla. Al anteponer '+' al DBURL, la tabla no se eliminará.

Las columnas de la tabla son similares a joblog con la adición de V1 .. Vn que son valores de las fuentes de entrada, y Stdout y Stderr que son la salida del estándar de salida y del error estándar, respectivamente.

La columna Signal ha sido renombrada a _Signal debido a que Signal es una palabra reservada en MySQL.

Aviso de citación

Para más detalles: Ver https://git.savannah.gnu.org/cgit/parallel.git/tree/doc/citation-notice-faq.txt

Financiar un proyecto de software libre es difícil. GNU parallel no es una excepción. Además, parece que cuanto menos visible es un proyecto, más difícil es obtener financiación. Y la naturaleza de GNU parallel es que nunca será visto por "el tipo con la chequera", sino solo por las personas que realizan el trabajo real.

Este problema ha sido abordado por otros, aunque no se ha encontrado una solución: https://www.slideshare.net/NadiaEghbal/consider-the-maintainer https://www.numfocus.org/blog/why-is-numpy-only-now-getting-funded/

Antes de implementar el aviso de citación, se discutió con los usuarios: https://lists.gnu.org/archive/html/parallel/2013-11/msg00006.html

Tener que dedicar 10 segundos a ejecutar parallel --citation una vez, sin duda no es una solución ideal, pero hasta ahora nadie ha propuesto una solución ideal, ni para financiar GNU parallel ni otro software libre.

Si crees que tienes la solución perfecta, deberías probarla y, si funciona, publicarla en la lista de correo. Sin embargo, es poco probable que se prioricen las ideas que impliquen trabajo y que no se hayan probado.

Ejecutar parallel --citation una sola vez tarda menos de 10 segundos y silenciará el aviso de citación para futuras ejecuciones. Esto es comparable a las herramientas gráficas donde tienes que hacer clic en una casilla que dice "No volver a mostrar". Pero si eso es demasiado problema para ti, ¿por qué no usar una de las alternativas en su lugar? Ver una lista en: man parallel_alternatives.

Dado que la solicitud de citación no es un requisito legal, esto es aceptable bajo GPLv3 y fue aclarado con el propio Richard M. Stallman. Por lo tanto, no cae bajo esto: https://www.gnu.org/licenses/gpl-faq.en.html#RequireCitation

Decisiones históricas

Estas decisiones fueron relevantes para versiones anteriores de GNU parallel, pero no para la versión actual. Se conservan aquí como registro histórico.

--tollef

Puede leer sobre la historia de GNU parallel en https://www.gnu.org/software/parallel/history.html

--tollef se incluyó para hacer que el cambio de GNU parallel fuera compatible con el paralelo de moreutils (que está hecho por Tollef Fog Heen). Esto se hizo para que los usuarios de ese paralelo pudieran portar fácilmente su uso a GNU parallel: simplemente establezca PARALLEL="--tollef" y eso sería todo.

Pero varias distribuciones optaron por hacer --tollef global (poniéndolo en /etc/parallel/config) sin informar a los usuarios, y eso causó mucha confusión cuando las personas probaban los ejemplos de la página man de GNU parallel y estos no funcionaban. Los usuarios se frustraron porque la distribución no les dejó claro que había hecho global --tollef.

Así que para disminuir la frustración y el soporte resultante, --tollef fue obsoleto el 20130222 y eliminado un año después.
