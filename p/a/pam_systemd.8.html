NOMBRE

pam_systemd - Registrar sesiones de usuario en el gestor de inicio de sesión de systemd

SINOPSIS

pam_systemd.so

DESCRIPCIÓN

pam_systemd registra las sesiones de usuario en el gestor de inicio de sesión de systemd systemd-logind.service(8), y por lo tanto en la jerarquía de grupos de control de systemd.

El módulo también aplica varios parámetros de gestión de recursos y de tiempo de ejecución a la nueva sesión, según lo configurado en los Registros de Usuario JSON[1], cuando uno está definido.

Al iniciar sesión, este módulo — en conjunto con systemd-logind.service — asegura lo siguiente:

1. Si aún no existe, el directorio de tiempo de ejecución del usuario /run/user/$UID se crea o se monta como un sistema de archivos "tmpfs" nuevo con cuota aplicada, y su propiedad se cambia al usuario que está iniciando sesión.
2. La variable de entorno $XDG_SESSION_ID se inicializa. Si la auditoría está disponible y pam_loginuid.so se ejecutó antes que este módulo (lo cual es muy recomendable), la variable se inicializa a partir del ID de sesión de auditoría (/proc/self/sessionid). De lo contrario, se utiliza un contador de sesiones independiente.
3. Se crea una nueva unidad de ámbito (scope) de systemd para la sesión. Si esta es la primera sesión concurrente del usuario, se crea automáticamente una unidad de división implícita por usuario debajo de user.slice y el ámbito se coloca en ella. Se inicia una instancia del servicio del sistema user@.service, que ejecuta la instancia del gestor de usuario de systemd.
4. Las variables de entorno "$TZ", "$EMAIL" y "$LANG" se configuran para el usuario, basándose en los datos correspondientes del registro JSON del usuario (si está definido). Además, se importan las variables de entorno explícitamente configuradas en el registro de usuario, y se inicializan la umask, el nivel de nice y los límites de recursos.

Al cerrar sesión, este módulo asegura lo siguiente:

1. Si está habilitado en logind.conf(5) (KillUserProcesses=), se terminan todos los procesos de la sesión. Si finaliza la última sesión concurrente de un usuario, también se terminará la instancia de systemd del usuario, y también su unidad de división de usuario.
2. Si finaliza la última sesión concurrente de un usuario, también se elimina el directorio de tiempo de ejecución del usuario /run/user/$UID y todo su contenido.

Si el sistema no se inició con systemd como sistema init, este módulo no hace nada y devuelve inmediatamente PAM_SUCCESS.

OPCIONES

Se entienden las siguientes opciones:

class=

Toma un argumento de cadena que establece la clase de la sesión. La variable de entorno XDG_SESSION_CLASS (ver abajo) tiene precedencia. Ver sd_session_get_class(3) para una forma de consultar la clase de una sesión. Las siguientes clases de sesión están definidas:

Tabla 1. Clases de Sesión

Nombre Explicación
user Una sesión de usuario interactiva regular. Esta es la clase predeterminada para sesiones para las cuales se conoce una TTY o una pantalla X en el momento de registrar la sesión.
user-early Similar a user pero las sesiones de esta clase no se ordenan después de systemd-user-sessions.service(8), es decir, pueden iniciarse antes de que se permita el establecimiento de sesiones regulares. Esta clase de sesión es la predeterminada para las sesiones del usuario root que de otro modo calificarían para la clase user, ver arriba. (Añadido en v256.)
user-light Similar a user, pero las sesiones de esta clase no invocarán el user@.service(5) del usuario, y por lo tanto, posiblemente no tengan un gestor de servicios del usuario en ejecución. (Añadido en v258.)
user-early-light Similar a user-early, pero las sesiones de esta clase no invocarán el user@.service(5) del usuario, y por lo tanto, posiblemente no tengan un gestor de servicios del usuario en ejecución. (Añadido en v258.)
user-incomplete Similar a user pero para sesiones que aún no están completamente configuradas, es decir, no tienen un directorio personal montado o similar. Esto es utilizado por systemd-homed.service(8) para permitir que los usuarios inicien sesión a través de ssh(1) antes de que se monte su directorio personal, retrasando el montaje hasta que el usuario proporcione la contraseña de desbloqueo. Las sesiones de esta clase se actualizan a la clase regular user una vez que se activa el directorio personal.
greeter Similar a user pero para sesiones que son invocadas efímeramente por un gestor de pantalla y que solicitan al usuario credenciales de inicio de sesión.
lock-screen Similar a user pero para sesiones que son invocadas efímeramente por un gestor de pantalla y que muestran una pantalla de bloqueo que se puede usar para desbloquear cuentas o sesiones de usuario bloqueadas.
background Se utiliza para sesiones en segundo plano, como las invocadas por cron(8) y herramientas similares. Esta es la clase predeterminada para las sesiones para las cuales no se conoce una TTY o una pantalla X en el momento de registrar la sesión.
background-light Similar a background, pero las sesiones de esta clase no invocarán el user@.service(5) del usuario, y por lo tanto, posiblemente no tengan un gestor de servicios del usuario en ejecución. (Añadido en v256.)
manager El servicio user@.service(5) del usuario se registra bajo esta clase de sesión. (Añadido en v256.)
manager-early Similar a manager, pero para el usuario root. Comparar con la situación user vs. user-early. (Añadido en v256.)
none Omite el registro de esta sesión con logind. No se creará ninguna unidad de ámbito de sesión y no se iniciará el gestor de servicios del usuario. (Añadido en v258.)

Añadido en la versión 197.

type=

Toma un argumento de cadena que establece el tipo de sesión. La variable de entorno XDG_SESSION_TYPE (ver abajo) tiene precedencia. Uno de unspecified, tty, x11, wayland, mir, o web. Ver sd_session_get_type(3) para detalles sobre el tipo de sesión.

Añadido en la versión 209.

desktop=

Toma una cadena de identificador única y corta para el entorno de escritorio. La variable de entorno XDG_SESSION_DESKTOP (ver abajo) tiene precedencia. Esto puede usarse para indicar el escritorio de sesión utilizado, donde esto aplica y si esta información está disponible. Por ejemplo: GNOME, o KDE. Se recomienda usar los mismos identificadores y capitalización que para $XDG_CURRENT_DESKTOP, según lo definido por la Especificación de Entrada de Escritorio[2]. (Sin embargo, tenga en cuenta que la opción solo toma un solo elemento, y no una lista separada por dos puntos como $XDG_CURRENT_DESKTOP.) Ver sd_session_get_desktop(3) para más detalles.

Añadido en la versión 240.

area=

Toma un nombre de archivo como parámetro. Si se especifica y el usuario inicia sesión en su cuenta, la variable de entorno $HOME se establecerá en ~/Areas/ seguida de la cadena especificada, pero solo si ese directorio existe. Además, la variable $XDG_AREA se establecerá en el parámetro (sin prefijo).

Esta funcionalidad puede usarse para mantener múltiples directorios personales secundarios separados dentro del directorio personal principal del usuario. Típicamente, el área para iniciar sesión se especifica al iniciar sesión, si la cuenta lo permite (las cuentas proporcionadas por pam_systemd_home(8) lo hacen), pero este parámetro puede usarse para definir un valor predeterminado si no se proporciona.

Tenga en cuenta que esto solo ajusta $HOME durante el inicio de sesión, no afecta al directorio personal del usuario informado de otro modo. Específicamente, esto significa que sshd(8) continuará buscando las claves SSH del usuario solo en el directorio personal principal del usuario, no en ninguna de sus áreas.

OPCIONES

Se puede pasar una lista de cadenas separadas por comas al módulo, cada una de las cuales es una opción de configuración. La lista de opciones se lee desde el archivo de configuración de PAM o desde la línea de comandos del módulo.

area=

Especifica el área de inicio secundaria del usuario para iniciar sesión. Si se proporciona, esto anula el área configurada por defecto allí. Tenga en cuenta también que si el área se especifica explícitamente por el usuario al iniciar sesión, anula ambos. Tenga en cuenta también que establecer este parámetro a una cadena vacía tiene el efecto de deshacer el efecto de cualquier área predeterminada configurada como parte del registro del usuario, es decir, asegurar que el usuario inicie sesión en el directorio principal primario de su cuenta.

Para obtener detalles sobre el concepto de área, consulte pam_systemd_home(8).

Añadido en la versión 258.

default-capability-bounding-set=, default-capability-ambient-set=

Toma una lista de capacidades de proceso separadas por comas (por ejemplo, CAP_WAKE_ALARM, CAP_BLOCK_SUSPEND, ...) para establecer para los procesos de la sesión invocada, si el registro del usuario no codifica conjuntos apropiados de capacidades directamente. Consulte capabilities(7) para obtener detalles sobre el concepto de capacidades. Si no se especifica, el conjunto delimitador predeterminado se deja como está (es decir, generalmente contiene el conjunto completo de capacidades). El conjunto ambiental predeterminado se establece en CAP_WAKE_ALARM para usuarios regulares si la sesión PAM está asociada con un asiento local o si se invoca para el servicio de usuario de systemd user@.service. De lo contrario, se establece por defecto en el conjunto vacío.

Añadido en la versión 254.

debug[=]

Toma un argumento booleano opcional. Si es verdadero o sin argumento, el módulo registrará información de depuración mientras opera.

TIPOS DE MÓDULO PROPORCIONADOS

Solo se proporciona session.

ENTORNO

Las siguientes variables de entorno son inicializadas por el módulo y están disponibles para los procesos de la sesión del usuario:

$XDG_SESSION_ID

Un identificador de sesión corto, adecuado para usar en nombres de archivo. La cadena en sí debe considerarse opaca, aunque a menudo es solo el ID de sesión de auditoría según lo informado por /proc/self/sessionid. Cada ID se asignará solo una vez durante el tiempo de actividad de la máquina. Por lo tanto, puede usarse para etiquetar de forma única archivos u otros recursos de esta sesión. Combine este ID con el identificador de arranque, como lo devuelve sd_id128_get_boot(3), para obtener un identificador globalmente único.

$XDG_RUNTIME_DIR

Ruta a un directorio privado y escribible por el usuario que está vinculado al momento del inicio de sesión del usuario en la máquina. Se crea automáticamente la primera vez que un usuario inicia sesión y se elimina en el último cierre de sesión del usuario. Si un usuario inicia sesión dos veces al mismo tiempo, ambas sesiones verán el mismo $XDG_RUNTIME_DIR y el mismo contenido. Si un usuario inicia sesión una vez, luego cierra la sesión y vuelve a iniciarla, el contenido del directorio se habrá perdido en el medio, pero las aplicaciones no deben depender de este comportamiento y deben poder manejar archivos obsoletos. Para almacenar datos privados de la sesión en este directorio, el usuario debe incluir el valor de $XDG_SESSION_ID en el nombre del archivo. Este directorio se utilizará para objetos de sistema de archivos en tiempo de ejecución, como sockets AF_UNIX, FIFOs, archivos PID y similares. Se garantiza que este directorio es local y ofrece el conjunto de características del sistema de archivos más amplio posible que proporciona el sistema operativo. Para obtener más detalles, consulte la Especificación de directorios base XDG[3]. $XDG_RUNTIME_DIR no se establece si el usuario actual no es el usuario original de la sesión.

$TZ, $EMAIL, $LANG

Si se conoce un registro de usuario JSON para el usuario que inicia sesión, estas variables se inicializan a partir de los datos respectivos del registro.

Añadido en la versión 245.

$SHELL_PROMPT_PREFIX, $SHELL_PROMPT_SUFFIX, $SHELL_WELCOME

Estas variables de entorno se inicializan a partir de las credenciales de servicio "shell.prompt.prefix", "shell.prompt.suffix" y "shell.welcome" si se establecen. Se pasan a los procesos de la sesión invocada, donde se importan en cualquier indicador de shell (específicamente, $SHELL_PROMPT_PREFIX se agrega como prefijo a $PS1, y $SHELL_PROMPT_SUFFIX como sufijo) o se imprimen en pantalla cuando un shell se inicializa por primera vez.

Añadido en la versión 257.

El módulo lee las siguientes variables de entorno y pueden ser utilizadas por el servicio PAM para pasar metadatos al módulo. Si estas variables no están establecidas cuando se invoca el módulo PAM pero se pueden determinar de otra manera, son establecidas por el módulo, de modo que estas variables se inicialicen para la sesión y las aplicaciones si se conocen en absoluto.

$XDG_SESSION_TYPE

El tipo de sesión. Esto puede usarse en lugar de type= en la línea de parámetros del módulo, y generalmente se prefiere.

Añadido en la versión 209.

$XDG_SESSION_CLASS

La clase de sesión. Esto puede usarse en lugar de class= en la línea de parámetros del módulo, y generalmente se prefiere.

Añadido en la versión 209.

$XDG_SESSION_DESKTOP

El identificador del escritorio. Esto puede usarse en lugar de desktop= en la línea de parámetros del módulo, y generalmente se prefiere.

Añadido en la versión 209.

$XDG_SEAT

El nombre del asiento para el que se registrará la sesión, si lo hay.

Añadido en la versión 209.

$XDG_VTNR

El número de VT para el que se registrará la sesión, si lo hay. (Solo se aplica a asientos con un VT disponible, como "seat0")

Añadido en la versión 209.

$XDG_AREA

Si se ha seleccionado un área (directorios de inicio secundarios del usuario, dentro del directorio de inicio principal) para iniciar sesión, esta variable se establece en el nombre del área (sin ningún prefijo de ruta). De lo contrario, no está establecida. Para obtener detalles sobre las áreas, consulte arriba.

Añadido en la versión 258.

Si no se establece, pam_systemd inicializará $XDG_SEAT y $XDG_VTNR basándose en la variable $DISPLAY (si esta última está establecida).

LÍMITES DE SESIÓN

Los módulos PAM anteriores en la pila, es decir, aquellos que vienen antes de pam_systemd.so, pueden establecer límites de alcance de sesión utilizando los objetos de contexto PAM. Los datos para estos objetos se proporcionan como cadenas de C terminadas en NUL y se mapean directamente a las directivas de control de recursos de unidad correspondientes. Tenga en cuenta que estos límites se aplican a las sesiones individuales del usuario, no se aplican a todos los procesos del usuario como un todo combinado. En particular, la instancia de unidad user@.service por usuario, que ejecuta el proceso administrador de systemd --user y sus hijos, y que se rastrea fuera de cualquier sesión, al ser compartida por todas las sesiones del usuario, no está cubierta por estos límites.

Consulte systemd.resource-control(5) para obtener más información sobre los recursos. Además, consulte pam_set_data(3) para obtener información adicional sobre cómo establecer los objetos de contexto.

systemd.memory_max=

Establece MemoryMax= de la unidad.

Añadido en la versión 239.

systemd.tasks_max=

Establece TasksMax= de la unidad.

Añadido en la versión 239.

systemd.cpu_weight=

Establece CPUWeight= de la unidad.

Añadido en la versión 239.

systemd.io_weight=

Establece IOWeight= de la unidad.

Añadido en la versión 239.

systemd.runtime_max_sec=

Establece RuntimeMaxSec= de la unidad.

Añadido en la versión 244.

Ejemplo de datos que pueden ser proporcionados por otro módulo PAM:

pam_set_data(handle, "systemd.memory_max", (void *)"200M", cleanup);
pam_set_data(handle, "systemd.tasks_max",  (void *)"50",   cleanup);
pam_set_data(handle, "systemd.cpu_weight", (void *)"100",  cleanup);
pam_set_data(handle, "systemd.io_weight",  (void *)"340",  cleanup);
pam_set_data(handle, "systemd.runtime_max_sec", (void *)"3600", cleanup);

EJEMPLO

Aquí hay un fragmento de configuración de PAM de ejemplo que permite que las sesiones de los usuarios sean administradas por systemd-logind.service:

#%PAM-1.0
-auth     [success=done authtok_err=bad perm_denied=bad maxtries=bad default=ignore] pam_systemd_home.so
auth      sufficient pam_unix.so
auth      required   pam_deny.so
account   required   pam_nologin.so
-account  [success=done authtok_expired=bad new_authtok_reqd=bad maxtries=bad acct_expired=bad default=ignore] pam_systemd_home.so
account   required   pam_unix.so
-password sufficient pam_systemd_home.so
password  sufficient pam_unix.so sha512 shadow try_first_pass
password  required   pam_deny.so
-session  optional   pam_keyinit.so revoke
-session  optional   pam_loginuid.so
-session  optional   pam_systemd_home.so
-session  optional   pam_systemd.so
session   required   pam_unix.so
