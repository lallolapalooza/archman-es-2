NOMBRE

path_resolution - cómo se resuelve un nombre de ruta a un archivo

DESCRIPCIÓN

Algunas llamadas al sistema de UNIX/Linux tienen como parámetro uno o más nombres de archivo. Un nombre de archivo (o nombre de ruta) se resuelve de la siguiente manera.

Paso 1: inicio del proceso de resolución

Si el nombre de ruta comienza con el carácter '/', el directorio de búsqueda inicial es el directorio raíz del proceso que llama. Un proceso hereda su directorio raíz de su padre. Normalmente, este será el directorio raíz de la jerarquía de archivos. Un proceso puede obtener un directorio raíz diferente mediante la llamada al sistema chroot(2), o puede usar temporalmente un directorio raíz diferente mediante openat2(2) con la bandera RESOLVE_IN_ROOT establecida.

Un proceso puede obtener un espacio de nombres de montaje completamente privado en caso de que él —o uno de sus ancestros— haya sido iniciado por una invocación de la llamada al sistema clone(2) que tuviera la bandera CLONE_NEWNS establecida. Esto maneja la parte '/' del nombre de ruta.

Si el nombre de ruta no comienza con el carácter '/', el directorio de búsqueda inicial del proceso de resolución es el directorio de trabajo actual del proceso —o en el caso de las llamadas al sistema de estilo openat(2), el argumento dfd (o el directorio de trabajo actual si se pasa AT_FDCWD como argumento dfd). El directorio de trabajo actual se hereda del padre y se puede cambiar mediante la llamada al sistema chdir(2).

Los nombres de ruta que comienzan con un carácter '/' se denominan nombres de ruta absolutos. Los nombres de ruta que no comienzan con '/' se denominan nombres de ruta relativos.

Paso 2: recorrido a lo largo de la ruta

Establezca el directorio de búsqueda actual en el directorio de búsqueda inicial. Ahora, para cada componente no final del nombre de ruta, donde un componente es una subcadena delimitada por caracteres '/', este componente se busca en el directorio de búsqueda actual.

Si el proceso no tiene permiso de búsqueda en el directorio de búsqueda actual, se devuelve un error EACCES ("Permiso denegado").

Si el componente no se encuentra, se devuelve un error ENOENT ("No existe tal archivo o directorio").

Si se encuentra el componente, pero no es ni un directorio ni un enlace simbólico, se devuelve un error ENOTDIR ("No es un directorio").

Si se encuentra el componente y es un directorio, establecemos el directorio de búsqueda actual en ese directorio y pasamos al siguiente componente.

Si se encuentra el componente y es un enlace simbólico, primero resolvemos este enlace simbólico (con el directorio de búsqueda actual como directorio de búsqueda inicial). En caso de error, se devuelve ese error. Si el resultado no es un directorio, se devuelve un error ENOTDIR. Si la resolución del enlace simbólico es exitosa y devuelve un directorio, establecemos el directorio de búsqueda actual en ese directorio y pasamos al siguiente componente. Tenga en cuenta que el proceso de resolución aquí puede implicar recursividad si el prefijo ('dirname') de un nombre de ruta contiene un nombre de archivo que es un enlace simbólico que se resuelve a un directorio (donde el componente prefijo de ese directorio puede contener un enlace simbólico, y así sucesivamente). Para proteger al kernel contra desbordamiento de pila, y también para proteger contra denegación de servicio, existen límites en la profundidad máxima de recursividad y en el número máximo de enlaces simbólicos seguidos. Se devuelve un error ELOOP cuando se excede el máximo ("Demasiados niveles de enlaces simbólicos").

Tal como está implementado actualmente en Linux, el número máximo de enlaces simbólicos que se seguirán mientras se resuelve un nombre de ruta es 40. Antes de Linux 2.6.18, el límite en la profundidad de recursividad era 5. A partir de Linux 2.6.18, este límite se elevó a 8. En Linux 4.2, el código de resolución de nombres de ruta del kernel fue rediseñado para eliminar el uso de recursividad, de modo que el único límite que queda es el máximo de 40 resoluciones para todo el nombre de ruta.

La resolución de enlaces simbólicos durante esta etapa puede ser bloqueada mediante openat2(2), con la bandera RESOLVE_NO_SYMLINKS establecida.

Paso 3: encontrar la entrada final

La búsqueda del componente final del nombre de ruta va igual que la de todos los demás componentes, como se describe en el paso anterior, con dos diferencias: (i) el componente final no tiene por qué ser un directorio (al menos en lo que respecta al proceso de resolución de ruta —puede tener que ser un directorio, o un no-directorio, debido a los requisitos de la llamada al sistema específica), y (ii) no es necesariamente un error si el componente no se encuentra —tal vez solo lo estamos creando. Los detalles sobre el tratamiento de la entrada final se describen en las páginas del manual de las llamadas al sistema específicas.

. y ..

Por convención, cada directorio tiene las entradas "." y "..", que se refieren al directorio mismo y a su directorio padre, respectivamente.

El proceso de resolución de ruta asumirá que estas entradas tienen sus significados convencionales, independientemente de si están presentes físicamente en el sistema de archivos.

No se puede subir más allá de la raíz: "/.." es lo mismo que "/".

Puntos de montaje

Después de un comando mount dev path, el nombre de ruta "path" se refiere a la raíz de la jerarquía del sistema de archivos en el dispositivo "dev", y ya no a lo que se refería anteriormente.

Se puede salir de un sistema de archivos montado: "path/.." se refiere al directorio padre de "path", fuera de la jerarquía del sistema de archivos en "dev".

La traversa de puntos de montaje puede ser bloqueada mediante openat2(2), con la bandera RESOLVE_NO_XDEV establecida (aunque tenga en cuenta que esto también restringe la traversa de bind mounts).

Barras finales

Si un nombre de ruta termina en '/', esto fuerza la resolución del componente anterior como en el Paso 2: el componente que precede a la barra existe y se resuelve a un directorio, o nombra un directorio que se creará inmediatamente después de que se resuelva el nombre de ruta. De lo contrario, una barra '/' final se ignora.

Enlace simbólico final

Si el último componente de un nombre de ruta es un enlace simbólico, entonces depende de la llamada al sistema si el archivo al que se hace referencia será el enlace simbólico o el resultado de la resolución de ruta en su contenido. Por ejemplo, la llamada al sistema lstat(2) operará sobre el enlace simbólico, mientras que stat(2) opera sobre el archivo al que apunta el enlace simbólico.

Límite de longitud

Hay una longitud máxima para los nombres de ruta. Si el nombre de ruta (o algún nombre de ruta intermedio obtenido al resolver enlaces simbólicos) es demasiado largo, se devuelve un error ENAMETOOLONG ("Nombre de archivo demasiado largo").

Nombre de ruta vacío

En el UNIX original, el nombre de ruta vacío se refería al directorio actual. Hoy en día, POSIX decreta que un nombre de ruta vacío no debe resolverse con éxito. Linux devuelve ENOENT en este caso.

Permisos

Los bits de permisos de un archivo consisten en tres grupos de tres bits; ver chmod(1) y stat(2). El primer grupo de tres se usa cuando el ID de usuario efectivo del proceso que llama es igual al ID del propietario del archivo. El segundo grupo de tres se usa cuando el ID de grupo del archivo es igual al ID de grupo efectivo del proceso que llama, o es

uno de los IDs de grupo suplementarios del proceso que llama (establecido por setgroups(2)). Cuando ninguno de los dos es válido, se utiliza el tercer grupo.

De los tres bits utilizados, el primer bit determina el permiso de lectura, el segundo el permiso de escritura y el último el permiso de ejecución en caso de archivos normales, o el permiso de búsqueda en caso de directorios.

Linux utiliza el fsuid en lugar del ID de usuario efectivo en las comprobaciones de permisos. Normalmente, el fsuid será igual al ID de usuario efectivo, pero el fsuid puede ser modificado por la llamada al sistema setfsuid(2).

(Aquí "fsuid" significa algo así como "ID de usuario del sistema de archivos". El concepto fue necesario para la implementación de un servidor NFS en el espacio de usuario en un momento en que los procesos podían enviar una señal a un proceso con el mismo ID de usuario efectivo. Ahora está obsoleto. Nadie debería usar setfsuid(2).)

De manera similar, Linux utiliza el fsgid ("ID de grupo del sistema de archivos") en lugar del ID de grupo efectivo. Consulte setfsgid(2).

Ignorar las comprobaciones de permisos: superusuario y capacidades

En un sistema UNIX tradicional, el superusuario (root, ID de usuario 0) es todopoderoso y omite todas las restricciones de permisos al acceder a los archivos.

En Linux, los privilegios de superusuario se dividen en capacidades (ver capabilities(7)). Dos capacidades son relevantes para las comprobaciones de permisos de archivos: CAP_DAC_OVERRIDE y CAP_DAC_READ_SEARCH. (Un proceso tiene estas capacidades si su fsuid es 0.)

La capacidad CAP_DAC_OVERRIDE anula todas las comprobaciones de permisos, pero otorga permiso de ejecución solo cuando se establece al menos uno de los tres bits de permiso de ejecución del archivo.

La capacidad CAP_DAC_READ_SEARCH otorga permisos de lectura y búsqueda en directorios, y permiso de lectura en archivos normales.
