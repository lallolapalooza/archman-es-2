NOMBRE

pam.conf, pam.d - Archivos de configuración de PAM

DESCRIPCIÓN

Cuando se inicia una aplicación que otorga privilegios compatible con PAM, activa su conexión con la API de PAM. Esta activación realiza una serie de tareas, la más importante es la lectura del archivo de configuración: /etc/pam.conf. Alternativamente y de forma preferente, la configuración puede establecerse mediante archivos de configuración individuales ubicados en un directorio pam.d. La presencia de este directorio hará que Linux-PAM ignore /etc/pam.conf.

Estos archivos enumeran los PAMs que realizarán las tareas de autenticación requeridas por este servicio, y el comportamiento apropiado de la API de PAM en caso de que los PAMs individuales fallen.

La sintaxis del archivo de configuración /etc/pam.conf es la siguiente. El archivo está compuesto por una lista de reglas, cada regla se coloca típicamente en una sola línea, pero puede extenderse con un final de línea escapado: `\<LF>'. Los comentarios van precedidos por `#' y se extienden hasta el siguiente final de línea.

El formato de cada regla es una colección de tokens separados por espacios, los tres primeros no distinguen entre mayúsculas y minúsculas:

servicio tipo control ruta_módulo argumentos_módulo

La sintaxis de los archivos contenidos en el directorio /etc/pam.d/ es idéntica excepto por la ausencia de cualquier campo servicio. En este caso, el servicio es el nombre del archivo en el directorio /etc/pam.d/. Este nombre de archivo debe estar en minúsculas.

Una característica importante de PAM es que un número de reglas pueden ser apiladas para combinar los servicios de varios PAMs para una tarea de autenticación dada.

El servicio es típicamente el nombre familiar de la aplicación correspondiente: login y su son buenos ejemplos. El nombre de servicio, other, está reservado para dar reglas por defecto. Solo las líneas que mencionan el servicio actual (o en ausencia de tales, las entradas other) se asociarán con la aplicación-servicio dada.

El tipo es el grupo de gestión al que corresponde la regla. Se utiliza para especificar a cuál de los grupos de gestión se asociará el módulo subsiguiente. Las entradas válidas son:

account

este tipo de módulo realiza gestión de cuentas no basada en autenticación. Se utiliza típicamente para restringir/permitir el acceso a un servicio basado en la hora del día, los recursos del sistema actualmente disponibles (número máximo de usuarios) o quizás la ubicación del usuario solicitante -- solo inicio de sesión 'root' en la consola.

auth

este tipo de módulo proporciona dos aspectos de la autenticación del usuario. Primero, establece que el usuario es quien dice ser, instruyendo a la aplicación para que solicite al usuario una contraseña u otros medios de identificación. Segundo, el módulo puede otorgar membresía de grupo u otros privilegios a través de sus propiedades de concesión de credenciales.

password

este tipo de módulo es necesario para actualizar el token de autenticación asociado con el usuario. Típicamente, hay un módulo para cada tipo de autenticación basado en 'desafío/respuesta' (auth).

session

este tipo de módulo se asocia con la realización de tareas que deben hacerse para el usuario antes/después de que se le pueda conceder el servicio. Tales tareas incluyen el registro de información concerniente a la apertura/cierre de algún intercambio de datos con un usuario, montaje de directorios, etc.

Si el valor del tipo de la lista anterior va precedido por un carácter -, la biblioteca PAM no registrará en el registro del sistema si no es posible cargar el módulo porque falta en el sistema. Esto puede ser útil especialmente para módulos que no siempre están instalados en el sistema y no son necesarios para la autenticación y autorización correctas de la sesión de inicio de sesión.

El tercer campo, control, indica el comportamiento de la API de PAM en caso de que el módulo no logre tener éxito en su tarea de autenticación. Hay dos tipos de sintaxis para este campo de control: la simple tiene una sola palabra clave simple; la más complicada implica una selección entre corchetes de pares valor=acción.

Para la sintaxis simple (histórica), los valores de control válidos son:

required

el fallo de un PAM de este tipo conducirá en última instancia a que la API de PAM devuelva un fallo, pero solo después de que los módulos restantes apilados (para este servicio y tipo) hayan sido invocados.

requisite

igual que required, sin embargo, en caso de que dicho módulo devuelva un fallo, el control se devuelve directamente a la aplicación o a la pila PAM superior. El valor de retorno será el asociado con el primer módulo requerido o requisito que falle. Tenga en cuenta que este indicador puede usarse para proteger contra la posibilidad de que un usuario tenga la oportunidad de ingresar una contraseña a través de un medio no seguro. Es concebible que tal comportamiento pueda informar a un atacante de cuentas válidas en un sistema. Esta posibilidad debe sopesarse frente a las preocupaciones no insignificantes de exponer una contraseña sensible en un entorno hostil.

sufficient

si un módulo de este tipo tiene éxito y ningún módulo required anterior ha fallado, el framework PAM devuelve éxito a la aplicación o a la pila PAM superior inmediatamente sin llamar a ningún módulo adicional en la pila. El fallo de un módulo sufficient se ignora y el procesamiento de la pila de módulos PAM continúa sin verse afectado.

optional

el éxito o fracaso de este módulo solo es importante si es el único módulo en la pila asociado con este servicio+tipo.

include

incluir todas las líneas del tipo dado del archivo de configuración especificado como argumento para este control.

substack

incluir todas las líneas del tipo dado del archivo de configuración especificado como argumento para este control. Esto difiere de include en que la evaluación de las acciones done y die en un substack no provoca el salto del resto de la pila de módulos completa, sino solo del substack. Los saltos en un substack tampoco pueden hacer que la evaluación salte fuera de él, y todo el substack se cuenta como un módulo cuando se realiza el salto en una pila principal. La acción reset restablecerá el estado de una pila de módulos al estado en el que se encontraba al comienzo de la evaluación del substack.

Para la sintaxis más complicada, los valores de control válidos tienen la siguiente forma:

      [valor1=acción1 valor2=acción2 ...]

Donde valorN corresponde al código de retorno de la función invocada en el módulo para el que se define la línea. Se selecciona de uno de estos: success, open_err, symbol_err, service_err, system_err, buf_err, perm_denied, auth_err, cred_insufficient, authinfo_unavail, user_unknown, maxtries, new_authtok_reqd, acct_expired, session_err, cred_unavail, cred_expired, cred_err, no_module_data, conv_err, authtok_err, authtok_recover_err, authtok_lock_busy, authtok_disable_aging, try_again, ignore, abort, authtok_expired, module_unknown, bad_item, conv_again, incomplete y default.

El último de estos, default, implica 'todos los valorN' no mencionados explícitamente. Tenga en cuenta que la lista completa de errores de PAM está disponible en /usr/include/security/_pam_types.h. La acciónN puede tomar una de las siguientes formas:

ignore

cuando se utiliza con una pila de módulos, el estado de retorno del módulo no contribuirá al código de retorno que la aplicación obtiene.

bad

esta acción indica que el código de retorno debe considerarse como indicativo de que el módulo falla. Si este módulo es el primero en la pila en fallar, su valor de estado se utilizará para el de toda la pila. Esta es la acción predeterminada para todos los códigos de retorno.

die

equivalente a bad con el efecto secundario de terminar la pila de módulos y que PAM devuelva inmediatamente a la aplicación.

ok

esto le dice a PAM que el administrador piensa que este código de retorno debe contribuir directamente al código de retorno de toda la pila de módulos. En otras palabras, si el estado anterior de la pila llevara a un retorno de PAM_SUCCESS, el código de retorno del módulo anulará este valor. Tenga en cuenta que si el estado anterior de la pila contiene algún valor que indique un fallo de módulo, este valor 'ok' no se utilizará para anular ese valor.

done

equivalente a ok con el efecto secundario de terminar la pila de módulos y que PAM devuelva inmediatamente a la aplicación, a menos que haya habido un fallo de módulo no ignorado anteriormente.

NOMBRE

pam.d - Linux-PAM configuration file syntax

DESCRIPCIÓN

PAM uses configuration files to determine how applications should use the PAM modules. These files define the sequence of PAM modules to be used for a given service and management group, and how the application should react to the return code of each module.

Historically, PAM used a single configuration file, /etc/pam.conf. This file consisted of lines with the following format:

service  type  control  module-path  module-arguments

However, this approach had a number of drawbacks. For instance, it made it difficult to manage PAM configuration for many services, and it was also more difficult for vendor-supplied PAM modules to be installed and managed.

The PAM system has since been updated to allow for a more flexible configuration using the structure of files in the /etc/pam.d/ directory. In this approach, each service has its own configuration file named after the service.

The syntax of the configuration files consists of lines specifying the type of PAM service management group, the control flag, the module to be used, and any module-specific arguments.

The fields on each line are separated by whitespace.

The type field specifies the management group. The current supported types are:

  • auth: Authentication management. Used to verify the identity of a user.
  • account: Account management. Used to check if the user is allowed to access the service.
  • password: Password management. Used to handle password changes and updates.
  • session: Session management. Used to set up and tear down user sessions, such as mounting home directories or setting resource limits.

The control field specifies how the return code from the module should be handled. The keywords for the control field are:

value

For each possible return code from a module, one can specify an action. This action is one of: ignore, ok, bad, die, restart, reset, jump, or done.
ignore
The return code is ignored, and processing continues with the next module. The final result will be the result of the last module executed, or the default action if no other module is executed.
ok
If the module returns the specified return code, the final result of the module stack is ok, and no further modules are executed. If the module returns any other code, processing continues with the next module.
bad
If the module returns the specified return code, the final result of the module stack is bad, and no further modules are executed. If the module returns any other code, processing continues with the next module.
die
If the module returns the specified return code, the final result of the module stack is bad, and no further modules are executed. The PAM library then returns PAM_ABORT to the application.
restart
If the module returns the specified return code, the module stack is re-executed from the beginning. This is useful for modules that require user interaction, such as password entry.
done
If the module returns the specified return code, processing is terminated and the PAM library returns PAM_SUCCESS to the application.

The special return code default specifies the action to be taken if none of the preceding return codes match the module's return code.

N (an unsigned integer)

jump over the next N modules in the stack. Note that N equal to 0 is not allowed, it would be treated as ignore in such case. The side effect depends on the PAM function call: for pam_authenticate, pam_acct_mgmt, pam_chauthtok, and pam_open_session it is ignore; for pam_setcred and pam_close_session it is one of ignore, ok, or bad depending on the module's return value.

reset

clear all memory of the state of the module stack and start again with the next stacked module.

If a return code's action is not specifically defined via a valueN token, and the default value is not specified, that return code's action defaults to bad.

Each of the four keywords: required; requisite; sufficient; and optional, have an equivalent expression in terms of the [...] syntax. They are as follows:

required

[success=ok new_authtok_reqd=ok ignore=ignore default=bad]

requisite

[success=ok new_authtok_reqd=ok ignore=ignore default=die]

sufficient

[success=done new_authtok_reqd=done default=ignore]

optional

[success=ok new_authtok_reqd=ok default=ignore]

module-path is either the full filename of the PAM to be used by the application (it begins with a '/'), or a relative pathname from the default module location: /lib/security/ or /lib64/security/, depending on the architecture.

module-arguments are a space separated list of tokens that can be used to modify the specific behavior of the given PAM. Such arguments will be documented for each individual module. Note, if you wish to include spaces in an argument, you should surround that argument with square brackets.

    squid auth required pam_mysql.so user=passwd_query passwd=mada \
          db=eminence [query=select user_name from internet_service \
          where user_name='%u' and password=PASSWORD('%p') and \
        service='web_proxy']

When using this convention, you can include `[' characters inside the string, and if you wish to include a `]' character inside the string that will survive the argument parsing, you should use `\]'. In other words:

    [..[..\]..]    -->   ..[..]..

Any line in (one of) the configuration file(s), that is not formatted correctly, will generally tend (erring on the side of caution) to make the authentication process fail. A corresponding error is written to the system log files with a call to syslog(3).

More flexible than the single configuration file is it to configure libpam via the contents of pam.d directories. In this case the directories are filled with files each of which has a filename equal to a service-name (in lower-case): it is the personal configuration file for the named service.

Vendor-supplied PAM configuration files might be installed in the system directory /usr/lib/pam.d/ or a configurable vendor specific directory instead of the machine configuration directory /etc/pam.d/. If no machine configuration file is found, the vendor-supplied file is used. All files in /etc/pam.d/ override files with the same name in other directories.

The syntax of each file in pam.d is similar to that of the /etc/pam.conf file and is made up of lines of the following form:

type  control  module-path  module-arguments

The only difference being that the service-name is not present. The service-name is of course the name of the given configuration file. For example, /etc/pam.d/login contains the configuration for the login service.

ARCHIVOS

/etc/pam.conf

the configuration file

/etc/pam.d

the Linux-PAM configuration directory. Generally, if this directory is present, the /etc/pam.conf file is ignored.

/usr/lib/pam.d

the Linux-PAM vendor configuration directory. Files in /etc/pam.d override files with the same name in this directory.
