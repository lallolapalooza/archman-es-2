readv(2) Manual de llamadas al sistema readv(2)

NOMBRE

readv, writev, preadv, pwritev, preadv2, pwritev2 - leer o escribir datos en múltiples buffers

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/uio.h>
ssize_t readv(int fd, const struct iovec *iov, int iovcnt);
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
ssize_t preadv(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
Requisitos de macro de prueba de características para glibc (ver feature_test_macros(7)):

preadv(), pwritev():

    Desde glibc 2.19:
        _DEFAULT_SOURCE
    glibc 2.19 y anteriores:
        _BSD_SOURCE

DESCRIPCIÓN

La llamada al sistema readv() lee iovcnt buffers del archivo asociado con el descriptor de archivo fd en los buffers descritos por iov ("entrada dispersa").

La llamada al sistema writev() escribe iovcnt buffers de datos descritos por iov en el archivo asociado con el descriptor de archivo fd ("salida agrupada").

El puntero iov apunta a un array de estructuras iovec, descritas en iovec(3type).

La llamada al sistema readv() funciona igual que read(2) excepto que se rellenan múltiples buffers.

La llamada al sistema writev() funciona igual que write(2) excepto que se escriben múltiples buffers.

Los buffers se procesan en el orden del array. Esto significa que readv() rellena completamente iov[0] antes de pasar a iov[1], y así sucesivamente. (Si hay datos insuficientes, entonces no se rellenarán todos los buffers apuntados por iov). De manera similar, writev() escribe el contenido completo de iov[0] antes de pasar a iov[1], y así sucesivamente.

Las transferencias de datos realizadas por readv() y writev() son atómicas: los datos escritos por writev() se escriben como un bloque único que no se mezcla con la salida de escrituras en otros procesos; análogamente, se garantiza que readv() lee un bloque contiguo de datos del archivo, independientemente de las operaciones de lectura realizadas en otros hilos o procesos que tengan descriptores de archivo que hagan referencia a la misma descripción de archivo abierta (ver open(2)).

preadv() y pwritev()

La llamada al sistema preadv() combina la funcionalidad de readv() y pread(2). Realiza la misma tarea que readv(), pero añade un cuarto argumento, offset, que especifica el desplazamiento del archivo en el que se realizará la operación de entrada.

La llamada al sistema pwritev() combina la funcionalidad de writev() y pwrite(2). Realiza la misma tarea que writev(), pero añade un cuarto argumento, offset, que especifica el desplazamiento del archivo en el que se realizará la operación de salida.

El desplazamiento del archivo no se modifica por estas llamadas al sistema. El archivo al que se refiere fd debe ser capaz de buscar.

preadv2() y pwritev2()

Estas llamadas al sistema son similares a las llamadas preadv() y pwritev(), pero añaden un quinto argumento, flags, que modifica el comportamiento por llamada.

A diferencia de preadv() y pwritev(), si el argumento offset es -1, se utiliza y actualiza el desplazamiento actual del archivo.

El argumento flags contiene un OR a nivel de bits de cero o más de las siguientes banderas:

RWF_DSYNC (desde Linux 4.7)
Proporciona un equivalente por escritura de la bandera O_DSYNC de open(2). Esta bandera solo es significativa para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema.
RWF_HIPRI (desde Linux 4.6)
Lectura/escritura de alta prioridad. Permite a los sistemas de archivos basados en bloques utilizar sondeos del dispositivo, lo que proporciona una menor latencia, pero puede usar recursos adicionales. (Actualmente, esta característica solo es utilizable en un descriptor de archivo abierto con la bandera O_DIRECT).
RWF_SYNC (desde Linux 4.7)
Proporciona un equivalente por escritura de la bandera O_SYNC de open(2). Esta bandera solo es significativa para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema.
RWF_NOWAIT (desde Linux 4.14)
No esperar datos que no estén inmediatamente disponibles. Si se especifica esta bandera, la llamada al sistema preadv2() retornará instantáneamente si tuviera que leer datos del almacenamiento subyacente o esperar un bloqueo. Si se leyeron algunos datos, devolverá el número de bytes leídos. Si no se leyeron bytes, devolverá -1 y establecerá errno a EAGAIN (pero ver BUGS). Actualmente, esta bandera solo es significativa para preadv2().
RWF_APPEND (desde Linux 4.16)
Proporciona un equivalente por escritura de la bandera O_APPEND de open(2). Esta bandera solo es significativa para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema. El argumento offset no afecta la operación de escritura; los datos siempre se añaden al final del archivo. Sin embargo, si el argumento offset es -1, se actualiza el desplazamiento actual del archivo.
RWF_NOAPPEND (desde Linux 6.9)
No honrar la bandera O_APPEND de open(2). Esta bandera solo es significativa para pwritev2(). Históricamente, Linux respetaba la bandera O_APPEND si estaba establecida e ignoraba el argumento de desplazamiento, lo cual es un error. Para pwritev2(), el argumento offset se respeta como se espera si la bandera RWF_NOAPPEND está establecida, lo mismo que si la bandera O_APPEND no estuviera establecida.
RWF_ATOMIC (desde Linux 6.11)
Requiere que las escrituras en archivos regulares en sistemas de archivos basados en bloques se emitan con protección contra escrituras rotas. La protección contra escrituras rotas significa que ante una falla de energía o cualquier otra falla de hardware, todos o ninguno de los datos de la escritura se almacenarán, pero nunca una mezcla de datos viejos y nuevos. Esta bandera solo es significativa para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema. La longitud total de escritura debe ser una potencia de 2 y debe tener un tamaño dentro del rango [stx_atomic_write_unit_min, stx_atomic_write_unit_max]. La escritura debe estar en un desplazamiento naturalmente alineado dentro del archivo con respecto a la longitud total de escritura. Por ejemplo, una escritura de 32 KiB en un desplazamiento de archivo de 32 KiB está permitida, sin embargo, una escritura de 32 KiB en un desplazamiento de archivo de 48 KiB no está permitida. El límite superior de iovcnt para pwritev2() viene dado por el valor en stx_atomic_write_segments_max. La protección contra escrituras rotas solo funciona con la bandera O_DIRECT, es decir, las escrituras en búfer no son compatibles. Para garantizar la consistencia de la escritura entre el estado en memoria del archivo y el dispositivo de almacenamiento, se deben especificar O_SYNC o O_DSYNC para open(2). Las mismas garantías de E/S sincronizada que se describen en open(2) se proporcionan cuando se utilizan estas banderas o sus banderas y llamadas al sistema equivalentes (por ejemplo, si se especifica RWF_SYNC para pwritev2()).
RWF_DONTCACHE (desde Linux 6.14)

pwritev2(2) — Arch Linux

NAME

pwritev2(), preadv2(), pwritev(), preadv(), writev(), readv() - I/O vector operation with flags

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

Since Linux 4.6, glibc 2.26:

ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt, off_t offset, unsigned int flags);
ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt, off_t offset, unsigned int flags);

Since Linux 2.6.30, glibc 2.10:

ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt, off_t offset);
ssize_t preadv(int fd, const struct iovec *iov, int iovcnt, off_t offset);

POSIX.1-2001, 4.4BSD, first appeared in 4.2BSD:

ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
ssize_t readv(int fd, const struct iovec *iov, int iovcnt);

DESCRIPTION

The readv() and writev() system calls perform input on or output from a file descriptor, respectively, using scatter-gather with a vector of iovec structures.

The preadv() and pwritev() system calls are the same as readv() and writev() respectively, but they perform their operations at a specified offset within the file, independent of the file descriptor's current seek offset. This is useful for multithreaded applications where threads may need to read from or write to distinct file regions without needing a shared file offset or seeking.

The preadv2() and pwritev2() system calls are the same as preadv() and pwritev() respectively, but they also accept an additional flags argument, which is a bitmask that can be used to modify the behavior of the I/O operation. The following flags are defined:

RWF_HIPRI
Request higher priority for this I/O operation. This is a hint to the kernel that this I/O is more important than normal I/O. The kernel may use this hint to reorder I/O requests, but it is not guaranteed to do so.
RWF_DSYNC
Ensure that all synchronous write operations complete before the pwritev2() or writev() call returns. This is similar to the O_DSYNC flag, but it applies only to the I/O operations performed by this call, not to all subsequent I/O operations on the file descriptor.
RWF_SYNC
Ensure that all synchronous write and metadata update operations complete before the pwritev2() or writev() call returns. This is similar to the O_SYNC flag, but it applies only to the I/O operations performed by this call, not to all subsequent I/O operations on the file descriptor.
RWF_NOWAIT
If the operation would block, return immediately without blocking. This is similar to the O_NONBLOCK flag, but it applies only to this I/O operation, not to all subsequent I/O operations on the file descriptor.
RWF_APPEND
Append data to the end of the file. This is similar to the O_APPEND flag, but it applies only to this I/O operation, not to all subsequent I/O operations on the file descriptor.
RWF_DIRECT
Attempt to perform the I/O operation in direct I/O mode. This means that the I/O will bypass the page cache and go directly to the storage device. This can improve performance for some applications, but it also means that the data will not be cached, so subsequent reads of the same data will be slower.
RWF_ATOMIC
Perform the I/O operation atomically. This means that the entire operation will either succeed or fail. If the operation fails, no partial writes will occur. This flag is only supported for block devices and some file systems. If the file system does not support atomic writes, this flag will be ignored.

Reads or writes to a regular file will prune instantiated page cache content when the operation completes. This is different than normal buffered I/O, where the data usually remains in cache until such time that it gets reclaimed due to memory pressure. If ranges of the read or written I/O were already in cache before this read or write, then those ranges will not be pruned at I/O completion time.

Additionally, any range dirtied by a write operation with RWF_DONTCACHE set will get kicked off for writeback. This is similar to calling sync_file_range(2) with SYNC_FILE_RANGE_WRITE to start writeback on the given range. RWF_DONTCACHE is a hint, or best effort, where no hard guarantees are given on the state of the page cache once the operation completes.
If used on a file system or block device that doesn't support it, it will return -1, and errno will be set to EOPNOTSUPP.

RETURN VALUE

On success, readv(), preadv(), and preadv2() return the number of bytes read; writev(), pwritev(), and pwritev2() return the number of bytes written.

Note that it is not an error for a successful call to transfer fewer bytes than requested (see read(2) and write(2)).

On error, -1 is returned, and errno is set to indicate the error.

ERRORS

The errors are as given for read(2) and write(2). Furthermore, preadv(), preadv2(), pwritev(), and pwritev2() can also fail for the same reasons as lseek(2). Additionally, the following errors are defined:

EINVAL
The sum of the iov_len values overflows an ssize_t value.
EINVAL
If RWF_ATOMIC is specified, the combination of the sum of the iov_len values and the offset value does not comply with the length and offset torn-write protection rules.
EINVAL
The vector count, iovcnt, is less than zero or greater than the permitted maximum. If RWF_ATOMIC is specified, this maximum is given by the stx_atomic_write_segments_max value from statx.
EOPNOTSUPP
RWF_DONTCACHE was set in flags and the file doesn't support it.
EOPNOTSUPP
An unknown flag is specified in flags.

VERSIONS

C library/kernel differences

The raw preadv() and pwritev() system calls have call signatures that differ slightly from that of the corresponding GNU C library wrapper functions shown in the SYNOPSIS. The final argument, offset, is unpacked by the wrapper functions into two arguments in the system calls:

unsigned long pos_l, unsigned long pos

These arguments contain, respectively, the low order and high order 32 bits of offset.

Historical C library/kernel differences

To deal with the fact that IOV_MAX was so low on early versions of Linux, the glibc wrapper functions for readv() and writev() did some extra work if they detected that the underlying kernel system call failed because this limit was exceeded. In the case of readv(), the wrapper function allocated a temporary buffer large enough for all of the items specified by iov, passed that buffer in a call to read(2), copied data from the buffer to the locations specified by the iov_base fields of the elements of iov, and then freed the buffer. The wrapper function for writev() performed the analogous task using a temporary buffer and a call to write(2).

The need for this extra effort in the glibc wrapper functions went away with Linux 2.2 and later. However, glibc continued to provide this behavior until glibc 2.10. Starting with glibc 2.9, the wrapper functions provide this behavior only if the library detects that the system is running a Linux kernel older than Linux 2.6.18 (an arbitrarily selected kernel version). And since glibc 2.20 (which requires a minimum of Linux 2.6.32), the glibc wrapper functions always just directly invoke the system calls.

NOTES

POSIX.1 allows an implementation to place a limit on the number of items that can be passed in iov. An implementation can advertise its limit by defining IOV_MAX in <limits.h> or at run time via the return value from sysconf(_SC_IOV_MAX). On modern Linux systems, the limit is 1024. Back in Linux 2.0 days, this limit was 16.

BUGS

Linux 5.9 and Linux 5.10 have a bug where preadv2() with the RWF_NOWAIT flag may return 0 even when not at end of file.

EXAMPLES

The following code sample demonstrates the use of writev():


char          *str0 = "hello ";
char          *str1 = "world\n";
ssize_t       nwritten;
struct iovec  iov[2];
iov[0].iov_base = str0;
iov[0].iov_len = strlen(str0);
iov[1].iov_base = str1;
iov[1].iov_len = strlen(str1);
nwritten = writev(STDOUT_FILENO, iov, 2);
