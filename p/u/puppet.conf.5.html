Configuración de parámetros

  • Cada uno de estos parámetros se puede especificar en puppet.conf o en la línea de comandos.
  • Puppet Enterprise (PE) y Puppet de código abierto comparten los parámetros de configuración documentados aquí. Sin embargo, los valores predeterminados de PE difieren de los valores predeterminados de código abierto para algunos parámetros, como node_terminus, storeconfigs, always_retry_plugins, disable18n, environment_timeout (cuando Code Manager está habilitado) y el parámetro JRuby de Puppet Server max-active-instances. Para verificar los valores predeterminados de configuración de PE, consulte el archivo puppet.conf o pe-puppet-server.conf después de la instalación.
  • Al usar parámetros booleanos en la línea de comandos, use --setting y --no-setting en lugar de --setting (true|false). (Usar --setting false resulta en "Error: No se pudieron analizar las opciones de la aplicación: argumento innecesario".)
  • Los parámetros se pueden interpolar como $variables en otros parámetros; $environment es especial, ya que Puppet master interpolará el entorno de cada nodo agente en lugar del suyo propio.
  • Los valores múltiples se deben especificar como listas separadas por comas; los directorios múltiples deben separarse con el separador de ruta del sistema (generalmente dos puntos).
  • Los parámetros que representan intervalos de tiempo se deben especificar en formato de duración: un entero seguido inmediatamente por una de las unidades «y» (años de 365 días), «d» (días), «h» (horas), «m» (minutos) o «s» (segundos). La unidad no se puede combinar con otras unidades y, si se omite, se usa segundos como valor predeterminado. Los ejemplos son «3600», que es equivalente a «1h» (una hora), y «1825d», que es equivalente a «5y» (5 años).
  • Si utiliza el parámetro splay, tenga en cuenta que el período que espera cambia cada vez que se reinicia el agente de Puppet.
  • Los parámetros que aceptan un solo archivo o directorio pueden establecer opcionalmente el propietario, el grupo y el modo de su valor: rundir = $vardir/run { owner = puppet, group = puppet, mode = 644 }
  • Los ejecutables de Puppet ignoran cualquier parámetro que no sea relevante para su función.

Consulte la guía de configuración en https://puppet.com/docs/puppet/latest/config_about_settings.html para más detalles.

always_retry_plugins

Afecta cómo almacenamos en caché los intentos de cargar tipos de recursos y características de Puppet. Si es verdadero, las llamadas a Puppet.type.<type>? Puppet.feature.<feature>? siempre intentarán cargar el tipo o la característica (lo que puede ser una operación costosa) a menos que ya se haya cargado correctamente. Esto hace posible que una única ejecución de agente, por ejemplo, instale un paquete que proporcione las capacidades subyacentes para un tipo o característica, y luego cargue ese tipo o característica durante la misma ejecución (incluso si el tipo o la característica se habían probado anteriormente y no estaban disponibles).

Si este parámetro se establece en falso, los tipos y las características solo se verificarán una vez, y si no están disponibles, el resultado negativo se almacenará en caché y se devolverá para todos los intentos posteriores de cargar el tipo o la característica. Este comportamiento es casi siempre apropiado para el servidor y puede resultar en una mejora significativa del rendimiento para tipos y características que se verifican con frecuencia.

Predeterminado: true

autosign

Si (y cómo) firmar automáticamente las solicitudes de certificado. Este parámetro solo es relevante en un Puppet Server que actúa como autoridad de certificación (CA).

Los valores válidos son verdadero (firma automáticamente todas las solicitudes de certificado; no recomendado), falso (deshabilita la firma automática de certificados) o la ruta absoluta a un archivo.

El archivo especificado en este parámetro puede ser un archivo de configuración o un ejecutable de política personalizado. Puppet determinará automáticamente cuál es: si el usuario de Puppet (consulte el parámetro user) puede ejecutar el archivo, se tratará como un ejecutable de política; de lo contrario, se tratará como un archivo de configuración.

Si se configura un ejecutable de política personalizado, el Puppet Server de la CA lo ejecutará cada vez que reciba una CSR. Se le pasará al ejecutable el CN del sujeto de la solicitud como argumento de línea de comandos, y el contenido de la CSR en formato PEM en stdin. Debería salir con un estado de 0 si el certificado debe firmarse automáticamente y distinto de cero si no debe firmarse automáticamente.

Si una solicitud de certificado no se firma automáticamente, persistirá para su revisión. Un usuario administrador puede usar el comando puppetserver ca sign para firmarla manualmente, o puede eliminar la solicitud.

Para obtener información sobre los archivos de configuración de autosign, consulte la guía de archivos de configuración de Puppet en https://puppet.com/docs/puppet/latest/config_file_autosign.html.

•
Predeterminado: $confdir/autosign.conf

certificate_revocation

Si la comprobación de revocación de certificados debe estar habilitada y qué nivel de comprobación se debe realizar.

Cuando la revocación de certificados está habilitada, Puppet espera que el contenido de su CRL sean una o más CRLs codificadas en PEM concatenadas. Cuando se utiliza un paquete de certificados, las CRLs de todas las CAs en la cadena de confianza deben incluirse en el archivo crl. La cadena debe estar ordenada de menor a mayor autoridad, siendo la primera CRL listada para la raíz de la cadena y la última para la CA hoja.

Cuando certificate_revocation se establece en ´true´ o ´chain´, Puppet asegura que cada CA en la cadena de confianza no ha sido revocada por su CA emisora.

Cuando certificate_revocation se establece en ´leaf´, Puppet verifica los certificados contra la lista de revocación de la CA emisora, pero no verifica el estado de revocación de la CA emisora ni de ninguna CA superior dentro de la cadena de confianza.

Cuando certificate_revocation se establece en ´false´, Puppet deshabilita toda la comprobación de revocación de certificados y no intenta descargar la CRL.

•
Default: chain

csr_attributes

Un archivo opcional que contiene atributos personalizados para agregar a las solicitudes de firma de certificados (CSR). Debes asegurarte de que este archivo no exista en tu servidor Puppet CA; si existe, las extensiones de certificado no deseadas pueden filtrarse en los certificados creados con el comando puppetserver ca generate.

Si está presente, este archivo debe ser un hash YAML que contenga una clave custom_attributes y/o una clave extension_requests. El valor de cada clave debe ser un hash, donde cada clave es un OID válido y cada valor es un objeto que se puede convertir a cadena.

Los atributos personalizados pueden ser utilizados por la CA al decidir si firmar el certificado, pero luego se descartan. Los OIDs de los atributos pueden ser cualquier valor OID excepto los atributos CSR estándar (es decir, atributos descritos en RFC 2985 sección 5.4). Esto es útil para incrustar una clave precompartida para ejecutables de políticas de firma automática (ver la configuración autosign), a menudo utilizando el OID 1.2.840.113549.1.9.7 ("contraseña de desafío").

Las solicitudes de extensión se incrustarán permanentemente en el certificado final. Los OIDs de las extensiones deben estar en los arcos OID "ppRegCertExt" (1.3.6.1.4.1.34380.1.1), "ppPrivCertExt" (1.3.6.1.4.1.34380.1.2), o "ppAuthCertExt" (1.3.6.1.4.1.34380.1.3). El arco ppRegCertExt está reservado para cuatro de los datos más comunes para incrustar: pp_uuid (.1), pp_instance_id (.2), pp_image_name (.3) y pp_preshared_key (.4) --- en el archivo YAML, estos pueden ser referidos por sus nombres descriptivos cortos en lugar de su OID completo. El arco ppPrivCertExt no está regulado y puede usarse para extensiones específicas del sitio. El arco ppAuthCert está reservado para dos piezas de datos para incrustar: pp_authorization (.1) y pp_auth_role (.13). Al igual que con ppRegCertExt, en el archivo YAML, estos pueden ser referidos por sus nombres descriptivos cortos en lugar de su OID completo.

Puppet comprueba este ajuste al crear automáticamente un certificado para el agente de Puppet o el servidor de Puppet. Estos pueden ser tanto IP como DNS, y el tipo debe especificarse y seguido de dos puntos. Las entradas sin tipo por defecto serán DNS.

Para poder manejar las solicitudes de agentes en un determinado nombre de host (como "puppet.example.com"), Puppet Server necesita un certificado que demuestre que está permitido utilizar ese nombre; si un servidor muestra un certificado que no incluye su nombre de host, los agentes de Puppet se negarán a confiar en él. Si utilizas un solo nombre de host para el tráfico de Puppet pero lo distribuyes a varios servidores de Puppet, cada uno de esos servidores necesita incluir el nombre de host oficial en su lista de nombres adicionales.

Nota: La lista de nombres alternativos se bloquea cuando se firma el certificado del servidor. Si necesitas cambiar la lista más tarde, no puedes simplemente cambiar este ajuste; también necesitas regenerar el certificado. Para más información sobre ese proceso, consulta la documentación de regeneración de certificados https://puppet.com/docs/puppet/latest/ssl_regenerate_certificates.html.

Para ver todos los nombres alternativos que están utilizando tus servidores, inicia sesión en tu servidor CA y ejecuta puppetserver ca list --all, luego comprueba la salida de (alt names: ...). La mayoría de los nodos agentes NO deberían tener nombres alternativos; los únicos certificados que deberían tenerlos son los nodos de servidor de Puppet en los que quieres que otros agentes confíen.

Si la configuración apunta a un comando ejecutable, los hechos externos confiables se almacenarán en la clave 'external' del hash de hechos confiables. waitforcert

Con qué frecuencia el agente de puppet debe solicitar un certificado firmado.

Al iniciarse por primera vez, el agente de puppet enviará una solicitud de firma de certificado (CSR) al servidor que se indica en la configuración ca_server (generalmente el servidor Puppet principal); esto puede ser auto-firmado, o puede necesitar ser aprobado por un humano, dependiendo de la configuración del servidor CA.

El agente de Puppet no puede aplicar configuraciones hasta que su certificado aprobado esté disponible. Dado que el certificado puede o no estar disponible de inmediato, el agente de Puppet intentará obtenerlo repetidamente en este intervalo. Puedes deshabilitar la espera de certificados especificando un tiempo de 0, o una cantidad máxima de tiempo para esperar en la configuración maxwaitforcert, en cuyo caso el agente de puppet saldrá si no puede obtener un certificado. Esta configuración puede ser un intervalo de tiempo en segundos (30 o 30s), minutos (30m), horas (6h), días (2d) o años (5y).
