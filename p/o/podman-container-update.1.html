NOMBRE

podman-update - Actualizar la configuración de un contenedor dado

SINOPSIS

podman update [opciones] contenedor

podman container update [opciones] contenedor

DESCRIPCIÓN

Actualiza la configuración de un contenedor existente, permitiendo cambios en los límites de recursos y las comprobaciones de estado.

OPCIONES

--blkio-weight=peso

Peso relativo de E/S de bloque. El peso es un valor entre 10 y 1000.

Esta opción no se admite en sistemas sin root cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo de E/S de bloque por dispositivo.

--cpu-period=límite

Establece el período de CPU para el planificador de CPU justo (CFS), que es una duración en microsegundos. Una vez que se agota la cuota de CPU del contenedor, no se programará para ejecutarse hasta que finalice el período actual. El valor predeterminado es 100000 microsegundos.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--cpu-quota=límite

Limita la cuota de CPU del planificador de CPU justo (CFS).

Limita el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso de CPU completo. El límite es un número en microsegundos. Si se proporciona un número, el contenedor puede usar esa cantidad de tiempo de CPU hasta que finalice el período de CPU (controlable a través de --cpu-period).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--cpu-rt-period=microsegundos

Limita el período de tiempo real de CPU en microsegundos.

Limita el uso de CPU de tiempo real del contenedor. Esta opción indica al kernel que restrinja el uso de CPU de tiempo real del contenedor al período especificado.

Esta opción solo se admite en sistemas con root cgroups V1.

--cpu-rt-runtime=microsegundos

Limita el tiempo de ejecución de tiempo real de CPU en microsegundos.

Limita el uso de CPU de tiempo real de los contenedores. Esta opción indica al kernel que limite la cantidad de tiempo que las tareas de tiempo real pueden consumir en un período de CPU dado. Por ejemplo, un período de 1000000us y un tiempo de ejecución de 950000us significa que este contenedor puede consumir el 95% de la CPU disponible y dejar el 5% restante para tareas de prioridad normal.

La suma de todos los tiempos de ejecución entre contenedores no puede superar la cantidad asignada al cgroup padre.

Esta opción solo se admite en sistemas con root cgroups V1.

--cpu-shares, -c=cuotas

Cuotas de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de las cuotas de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso predeterminado es 1024.

La proporción solo se aplica cuando se ejecutan procesos que consumen mucha CPU. Cuando las tareas de un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una cuota de CPU de 1024 y otros dos tienen una configuración de cuota de CPU de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se agrega un cuarto contenedor con una cuota de CPU de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las cuotas de tiempo de CPU se distribuyen en todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de cuotas de CPU:

PID contenedor CPU Cuota de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--cpus=número

Número de CPUs. El valor predeterminado es 0.0, lo que significa sin límite. Esto es un atajo para --cpu-period y --cpu-quota, por lo tanto, la opción no se puede especificar con --cpu-period o --cpu-quota.

En algunos sistemas, cambiar los límites de CPU puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de estos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), use --cpuset-mems=0,1 entonces los procesos en el contenedor solo usarán memoria de los dos primeros nodos de memoria.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--device-read-bps=ruta:tasa

Limita la tasa de lectura (en bytes por segundo) desde un dispositivo (por ejemplo, --device-read-bps=/dev/sda:1mb).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podm

https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin privilegios de cgroups V1.

--device-read-iops=ruta:tasa

Limita la tasa de lectura (en operaciones de E/S por segundo) desde un dispositivo (por ejemplo, --device-read-iops=/dev/sda:1000).

En algunos sistemas, es posible que no se permita a los usuarios que no son root modificar los límites de recursos. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin privilegios de cgroups V1.

--device-write-bps=ruta:tasa

Limita la tasa de escritura (en bytes por segundo) a un dispositivo (por ejemplo, --device-write-bps=/dev/sda:1mb).

En algunos sistemas, es posible que no se permita a los usuarios que no son root modificar los límites de recursos. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin privilegios de cgroups V1.

--device-write-iops=ruta:tasa

Limita la tasa de escritura (en operaciones de E/S por segundo) a un dispositivo (por ejemplo, --device-write-iops=/dev/sda:1000).

En algunos sistemas, es posible que no se permita a los usuarios que no son root modificar los límites de recursos. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin privilegios de cgroups V1.

--env, -e=env

Agrega un valor (por ejemplo, env=valor) al contenedor. Se puede usar varias veces. Si el valor ya existe en el contenedor, se sobrescribe. Para eliminar una variable de entorno del contenedor, utilice la opción --unsetenv.

Tenga en cuenta que las actualizaciones de entorno solo afectan al proceso principal del contenedor después de la próxima vez que se inicie.

--health-cmd="comando" | '["comando", arg1 , ...]'

Establece o modifica un comando de verificación de estado de salud para un contenedor. El comando es un comando que se ejecutará dentro del contenedor y que determina el estado de salud del contenedor. El comando es necesario para que se apliquen otras opciones de verificación de estado de salud. Un valor de none deshabilita las verificaciones de estado de salud existentes.

Se pueden pasar varias opciones en forma de una matriz JSON; de lo contrario, el comando se interpreta como un argumento para /bin/sh -c.

Nota: Se utilizan los valores predeterminados incluso si la verificación de estado de salud está configurada en la imagen.

--health-interval=intervalo

Establece un intervalo para las verificaciones de estado de salud. Un intervalo de disable no configura un temporizador automático. El valor predeterminado es 30s.

Nota: Este parámetro sobrescribirá la configuración de verificación de estado de salud relacionada de la imagen.

El cambio de esta configuración reinicia el temporizador.

--health-log-destination=ruta_directorio

Establece el destino del registro de verificación de estado de salud. Ruta de directorio, local o events_logger (archivo de estado del contenedor de uso local) (Predeterminado: local)

  • local: (predeterminado) Los registros de verificación de estado de salud se almacenan en contenedores overlay. (Por ejemplo: $runroot/healthcheck.log)
  • directory: crea un archivo de registro llamado <ID_contenedor>-healthcheck.log con los registros de verificación de estado de salud en el directorio especificado.
  • events_logger: El registro se escribirá con el mecanismo de registro establecido por events_logger. También guarda el registro en un directorio predeterminado, para el rendimiento en un sistema con una gran cantidad de registros.

Advertencia: Cambiar esta configuración puede provocar la pérdida de registros anteriores.

--health-max-log-count=número de registros almacenados

Establece el número máximo de intentos en el archivo de registro de verificación de estado de salud (el valor '0' significa un número infinito de intentos en el archivo de registro) (Predeterminado: 5 intentos)

--health-max-log-size=tamaño del registro almacenado

Establece la longitud máxima en caracteres del registro de verificación de estado de salud almacenado (el valor "0" significa una longitud de registro infinita) (Predeterminado: 500 caracteres)

--health-on-failure=acción

Acción a tomar una vez que el contenedor cambie a un estado de no saludable. El valor predeterminado es none.

  • none: No tomar ninguna acción.
  • kill: Matar el contenedor.
  • restart: Reiniciar el contenedor. No combine la acción restart con la opción --restart. Cuando se ejecuta dentro de una unidad systemd, considere usar la acción kill o stop en su lugar para aprovechar la política de reinicio de systemd.
  • stop: Detener el contenedor.

--health-retries=reintentos

El número de reintentos permitidos antes de que una verificación de estado de salud se considere no saludable. El valor predeterminado es 3.

Nota: Este parámetro puede sobrescribir la configuración de verificación de estado de salud de la imagen.

--health-start-period=período

El tiempo de inicialización necesario para que un contenedor arranque. El valor se puede expresar en formato de tiempo como 2m3s. El valor predeterminado es 0s.

Nota: El comando de verificación de estado de salud se ejecuta tan pronto como se inicia un contenedor. Si la verificación de estado de salud tiene éxito, el estado de salud del contenedor se actualizará a healthy. Sin embargo, si la verificación de estado de salud falla, el estado de salud permanecerá como starting hasta que la verificación de estado de salud sea exitosa o hasta que expire el tiempo de --health-start-period. Si el comando de verificación de estado de salud falla después de que expire el tiempo de --health-start-period, el estado de salud se actualizará a unhealthy. El comando de verificación de estado de salud se ejecuta periódicamente según el valor de --health-interval.

Nota: Este parámetro sobrescribirá la configuración de verificación de estado de salud relacionada de la imagen.

--health-startup-cmd="comando" | '["comando", arg1 , ...]'

Establece un comando de verificación de estado de salud de inicio para un contenedor. Este comando se ejecuta dentro del contenedor y se utiliza para controlar la verificación de estado de salud regular. Cuando el comando de inicio tiene éxito, comienza la verificación de estado de salud regular y la verificación de estado de salud de inicio cesa. Opcionalmente, si el comando falla durante un número determinado de intentos, el contenedor se reinicia. Se puede utilizar una verificación de estado de salud de inicio para garantizar que los contenedores con un período de inicio prolongado no se marquen como no saludables hasta que se inicien por completo. Las verificaciones de estado de salud de inicio solo se pueden usar cuando también se establece una verificación de estado de salud regular (de la imagen del contenedor o de la opción --health-cmd).

--health-startup-interval=intervalo

Establece un intervalo para la verificación de estado de salud de inicio. Un intervalo de disable no configura un temporizador automático. El valor predeterminado es 30s.

El cambio de esta configuración reinicia el temporizador, dependiendo del estado del contenedor.

--health-startup-retries=reintentos

El número de intentos permitidos antes de que la verificación de estado de salud de inicio reinicie el contenedor. Si se establece en 0, el contenedor nunca se reinicia. El valor predeterminado es 0.

--health-startup-success=reintentos

El número de ejecuciones exitosas requeridas antes de que la verificación de estado de salud de inicio tenga éxito y comience la verificación de estado de salud regular. Un valor de 0 significa que cualquier éxito inicia la verificación de estado de salud regular.

--health-startup-timeout=tiempo_de_espera

El tiempo máximo que tiene el comando de verificación de estado de salud de inicio para completarse antes de que se marque como fallido. El valor se puede expresar en formato de tiempo como 2m3s. El valor predeterminado es 30s.

--health-timeout=tiempo_de_espera

El tiempo máximo permitido para completar la verificación de estado de salud antes de que se considere fallido un intervalo. Al igual que start-period, el valor se puede expresar en formato de tiempo como 1m22s. El valor predeterminado es 30s.

Nota: Un tiempo de espera marca la verificación de estado de salud como fallida. Si el comando de verificación de estado de salud en sí mismo se ejecuta durante más tiempo que el tiempo_de_espera especificado, se le enviará una señal SIGKILL.

Nota: Este parámetro sobrescribirá la configuración de verificación de estado de salud relacionada de la imagen.

--latest, -l

En lugar de proporcionar el nombre o ID del contenedor, utilice el último contenedor creado. Nota: el último contenedor iniciado puede ser de otros usuarios de Podman en la máquina host. (Esta opción no está disponible con el cliente Podman remoto, incluidas las máquinas Mac y Windows (excepto WSL2))

--memory, -m=número[unidad]

Límite de memoria. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Permite restringir la memoria disponible para un contenedor. Si el host admite memoria swap, entonces la configuración de memoria -m puede ser mayor que la RAM física. Si se especifica un límite de 0 (sin usar -m), la memoria del contenedor no se limita. El límite real puede redondearse al múltiplo del tamaño de página del sistema operativo (el valor es muy grande, millones de billones).

Esta opción no es compatible con sistemas sin privilegios de cgroups V1.

--memory-reservation=número[unidad]

Límite suave de memoria. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Después de establecer la reserva de memoria, cuando el sistema detecta contención de memoria o poca memoria, los contenedores se ven obligados a restringir su consumo a su reserva. Por lo tanto, siempre establezca el valor por debajo de --memory, de lo contrario, el límite estricto tendrá precedencia. Por defecto, la reserva de memoria es la misma que el límite de memoria.

NAME

podman-container-update - Update one or more containers

SYNOPSIS

podman container update [options] container ...

DESCRIPTION

The podman container update command updates one or more containers. You can update a container's resource limits.

OPTIONS

Podman container update has the following options, which override those set by the podman create command:

--blkio-weight=weight

Block I/O weight (10-1000). Default weight is 0, and it means preserving the existing relative weight.

--blkio-weight-device=weight

Block I/O weight (device-specific). Format is weight:major:minor. Example: 1000:8:0

--cpu-period=value

Limit the CPU CFS (Completely Fair Scheduler) period. A value is a non-negative integer.

--cpu-quota=value

Limit the CPU CFS (Completely Fair Scheduler) quota. A value is a non-negative integer.

--cpus=value

Number of CPUs. A value is a string representing a floating point number. Example: 1.5, 2, 0.5.

--cpuset-cpus=list

Limit the CPU sets that containers can use. A list is a comma-separated CPU set. Example: 0,1 for the first two CPUs.

--cpuset-mems=list

Limit the memory nodes (NUMA) that containers can use. A list is a comma-separated memory set. Example: 0,1 for the first two memory nodes.

--cpu-shares=value

CPU shares (weight-ratio). A value is a non-negative integer. Default is 1024. See `cpu.shares` man page.

--device-read-bps=rate

Limit read rate for a device. Format is device:rate. Example: /dev/sda:1mb

--device-read-iops=rate

Limit read IOPS for a device. Format is device:rate. Example: /dev/sda:1000

--device-write-bps=rate

Limit write rate for a device. Format is device:rate. Example: /dev/sda:1mb

--device-write-iops=rate

Limit write IOPS for a device. Format is device:rate. Example: /dev/sda:1000

--kernel-memory=limit

Kernel memory limit. A limit can be the same format as memory.

--memory=limit

Memory limit. A limit is a positive number. A unit can be b (bytes), k (kibibytes), m (mebibytes), or g (gibibytes).

--memory-reservation=limit

Memory reservation (soft limit). A limit can be the same format as memory.

This option is not supported on cgroups V1 rootless systems.

--memory-swap=number[unit]

A limit value equal to memory plus swap. A unit can be b (bytes), k (kibibytes), m (mebibytes), or g (gibibytes).

Must be used with the -m (--memory) flag. The argument value must be larger than that of
-m (--memory) By default, it is set to double the value of --memory.

Set number to -1 to enable unlimited swap.

This option is not supported on cgroups V1 rootless systems.

--memory-swappiness=number

Tune a container's memory swappiness behavior. Accepts an integer between 0 and 100.

This flag is only supported on cgroups V1 rootful systems.

--no-healthcheck

Disable any defined healthchecks for container.

--pids-limit=limit

Tune the container's pids limit. Set to -1 to have unlimited pids for the container. The default is 2048 on systems that support "pids" cgroup controller.

--restart=policy

Restart policy to follow when containers exit. Restart policy does not take effect if a container is stopped via the podman kill or podman stop commands.

Valid policy values are:

  • no : Do not restart containers on exit
  • never : Synonym for no; do not restart containers on exit
  • on-failure[:max_retries] : Restart containers when they exit with a non-zero exit code, retrying indefinitely or until the optional max_retries count is hit
  • always : Restart containers when they exit, regardless of status, retrying indefinitely
  • unless-stopped : Identical to always

Podman provides a systemd unit file, podman-restart.service, which restarts containers after a system reboot.

When running containers in systemd services, use the restart functionality provided by systemd. In other words, do not use this option in a container unit, instead set the Restart= systemd directive in the [Service] section. See podman-systemd.unit(5) and systemd.service(5).

--unsetenv=env

Unset environment variables from the container.

Note that the env updates only affect the main container process after the next start.

EXAMPLES

Update a container with a new cpu quota and period:

podman update --cpus=0.5 ctrID

Update the latest container with a new cpu value:

podman update --latest --cpus=1

Update a container with multiple options at ones:

podman update --cpus 5 --cpuset-cpus 0 --cpu-shares 123 --cpuset-mems 0 \  
  --memory 1G --memory-swap 2G --memory-reservation 2G \  
  --blkio-weight-device /dev/sda:123 --blkio-weight 123 \  
  --device-read-bps /dev/sda:10mb --device-write-bps /dev/sda:10mb \  
  --device-read-iops /dev/sda:1000 --device-write-iops /dev/sda:1000 \  
  --pids-limit 123 ctrID
