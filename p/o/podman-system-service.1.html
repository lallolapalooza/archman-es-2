NOMBRE

podman-system-service - Ejecutar un servicio API

SINOPSIS

podman system service [opciones]

DESCRIPCIÓN

El comando podman system service crea un servicio de escucha que responde a las llamadas API de Podman. El comando está disponible en sistemas Linux y generalmente se ejecuta en servicios systemd. El comando no está disponible cuando el comando Podman se ejecuta directamente en un host Windows o macOS o en otras situaciones donde el comando Podman accede a un servicio API remoto de Podman.

La API REST proporcionada por podman system service se divide en dos partes: una capa de compatibilidad que ofrece soporte para la API v1.40 de Docker, y una capa nativa de Podman llamada Libpod. La documentación para esta última está disponible en https://docs.podman.io/en/latest/_static/api.html. Ambas APIs tienen versiones, pero el servidor no rechaza solicitudes con una versión no soportada.

Ejecutar el comando en un servicio systemd

El comando podman system service soporta la activación por socket de systemd. Por lo tanto, cuando el comando se ejecuta en un servicio systemd, el servicio API puede proporcionarse bajo demanda. Si el servicio systemd aún no se está ejecutando, se activará tan pronto como un cliente se conecte al socket de escucha. Systemd ejecuta el comando podman system service. Después de un tiempo de inactividad, definido por la opción --time, el comando termina. Systemd establece el estado del servicio podman.service como inactivo. En este punto, no hay ningún proceso podman system service en ejecución. No se desperdician recursos de cómputo innecesarios. Tan pronto como otro cliente se conecte, systemd activará nuevamente el servicio systemd.

Los archivos de unidad de systemd que declaran el servicio API de Podman para los usuarios son

  • /usr/lib/systemd/user/podman.service
  • /usr/lib/systemd/user/podman.socket

En el archivo podman.socket, la ruta del socket Unix de escucha se define mediante

ListenStream=%t/podman/podman.sock

La ruta contiene el especificador de systemd %t, que systemd expande al valor de la variable de entorno XDG_RUNTIME_DIR (ver especificadores de systemd en la página del manual de systemd.unit(5)).

Además de los servicios de usuario de systemd, también existe un servicio del sistema systemd, podman.service. Ejecuta Podman con privilegios de root y se accede a él desde el socket Unix /run/podman/podman.sock. Ver los archivos de unidad de systemd

  • /usr/lib/systemd/system/podman.service
  • /usr/lib/systemd/system/podman.socket

El comando podman system service no soporta más de un socket de escucha para el servicio API.

Nota: Los archivos de unidad de systemd predeterminados (sistema y usuario) cambian la opción de nivel de registro de error a info. Este cambio proporciona información adicional sobre cada llamada API.

Ejecutar el comando directamente

Para soportar la ejecución de un servicio API sin usar un servicio systemd, el comando también toma un argumento de endpoint opcional para la API en forma de URI. Por ejemplo, unix:///tmp/foobar.sock o tcp://localhost:8080. Si no se proporciona ningún endpoint, se utilizan los valores predeterminados. El endpoint predeterminado para un servicio con privilegios de root es unix:///run/podman/podman.sock y para un servicio sin privilegios de root es unix://$XDG_RUNTIME_DIR/podman/podman.sock (por ejemplo, unix:///run/user/1000/podman/podman.sock)

Acceder al socket Unix desde dentro de un contenedor

Para acceder al servicio API dentro de un contenedor: - montar el socket como un volumen - ejecutar el contenedor con --security-opt label=disable

Seguridad

Tenga en cuenta que la API otorga acceso completo a todas las funcionalidades de Podman, y por lo tanto permite la ejecución arbitraria de código como el usuario que ejecuta la API, sin posibilidad de limitar o auditar este acceso. El modelo de seguridad de la API se basa en el acceso a través de un socket Unix con acceso restringido a través de permisos de archivo estándar, lo que garantiza que solo el usuario que ejecuta el servicio podrá acceder a él. TLS puede utilizarse para proteger este socket exigiendo a los clientes que presenten un certificado firmado por una autoridad certificadora ("CA") de confianza, así como para permitir al cliente verificar la identidad de la API. Recomendamos encarecidamente no hacer que el socket de la API esté disponible a través de la red (es decir, enlazando el servicio a una URL tcp) sin activar TLS mutuo para autenticar al cliente. Incluso el acceso a través de Localhost conlleva riesgos: cualquiera con acceso al sistema podrá acceder a la API. Si se requiere acceso remoto, recomendamos en su lugar reenviar el socket de la API a través de SSH y limitar el acceso en la máquina remota en la mayor medida posible. Si se debe utilizar una URL tcp sin TLS, se recomienda utilizar la opción --cors para mejorar la seguridad.

OPCIONES

--cors

Encabezados CORS para inyectar en la respuesta HTTP. El valor predeterminado es una cadena vacía, lo que deshabilita los encabezados CORS.

--help, -h

Imprime el mensaje de uso.

--time, -t

El tiempo hasta que expire la sesión en segundos. El valor predeterminado es 5 segundos. Un valor de 0 significa que no hay tiempo de espera, por lo tanto, la sesión no expira.

--tls-cert=ruta

Ruta a un archivo PEM que contiene el certificado TLS a presentar a los clientes. También se debe proporcionar --tls-key.

--tls-client-ca=ruta

Ruta a un archivo PEM que contiene el paquete de certificados TLS para validar las conexiones de los clientes. Las conexiones que no presenten ningún certificado o un certificado no firmado por uno de estos certificados serán rechazadas.

--tls-key=ruta

Ruta a un archivo PEM que contiene la clave privada que coincide con --tls-cert. También se debe proporcionar --tls-cert.

El tiempo de espera predeterminado se puede cambiar a través del campo service_timeout=VALUE en containers.conf. Consulte containers.conf(5) para más información.

EJEMPLOS

Iniciar el socket systemd de usuario para un servicio sin privilegios de root.

systemctl --user start podman.socket

Configurar la variable de entorno DOCKER_HOST para que apunte al socket de Podman, de modo que pueda ser utilizado a través de herramientas de API de Docker como docker-compose.

$ export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock
$ docker-compose up

Configurar el socket systemd para que se inicie automáticamente después de los reinicios y se ejecute como el usuario especificado.

systemctl --user enable podman.socket
loginctl enable-linger <USUARIO>

Iniciar el socket systemd para el servicio con privilegios de root.

sudo systemctl start podman.socket

Configurar el socket para que se inicie automáticamente después de los reinicios.

sudo systemctl enable podman.socket

Es posible ejecutar la API sin usar la activación por socket de systemd. En este caso, la API no estará disponible bajo demanda porque el comando permanecerá terminado después de que haya pasado el tiempo de espera de inactividad. Ejecute una API con un tiempo de espera de inactividad de 5 segundos sin usar la activación por socket.

podman system service --time 5

Se utilizó el socket predeterminado, ya que no se proporcionó ningún argumento URI.

Ejecutar un servicio API con una ruta de socket personalizada y sin tiempo de espera:

podman system service --time 0 unix:///var/run/mypodman.sock

Esto inicia el servicio API escuchando en el socket personalizado /var/run/mypodman.sock sin tiempo de espera de inactividad (se ejecuta indefinidamente).
