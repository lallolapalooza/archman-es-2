Solución de problemas

Una lista de problemas y soluciones comunes para Podman

1) Varios problemas - Valida la versión

Un gran número de problemas reportados contra Podman a menudo se descubren que ya están solucionados en versiones más recientes del proyecto. Antes de reportar un problema, por favor verifica la versión que estás ejecutando con podman version y compárala con la última versión documentada en la parte superior de ⟨README.md⟩ de Podman.

Si difieren, por favor actualiza tu versión de PODMAN a la última posible y reintenta tu comando antes de reportar el problema.

2) No se puede usar el montaje de volumen, se obtiene permiso denegado

$ podman run -v ~/mycontent:/content fedora touch /content/file
touch: no se puede crear '/content/file': Permiso denegado

Solución

Esto a veces es causado por SELinux, y a veces por namespaces de usuario.

Sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el sistema operativo.

Para cambiar una etiqueta en el contexto del contenedor, puedes agregar uno de los dos sufijos :z o :Z al montaje del volumen. Estos sufijos le indican a Podman que reetiquete los objetos de archivo en los volúmenes compartidos. La opción z le indica a Podman que dos contenedores comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban contenido. La opción Z le indica a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el contenedor actual puede usar un volumen privado.

$ podman run -v ~/mycontent:/content:Z fedora touch /content/file

Asegúrate de que el contenido sea privado para el contenedor. No reetiquetes directorios y contenido del sistema. Reetiquetar contenido del sistema podría hacer que otros servicios confinados en tu máquina fallen. Para este tipo de contenedores, recomendamos desactivar la separación de SELinux. La opción --security-opt label=disable desactivará la separación de SELinux para el contenedor.

$ podman run --security-opt label=disable -v ~:/home/user fedora touch /home/user/file

En casos donde la imagen del contenedor se ejecuta como un usuario específico, no root, la solución es arreglar el namespace de usuario. Esto incluiría imágenes de contenedor como la imagen de Jupyter Notebook (que se ejecuta como "jovyan") y la imagen de Postgres (que se ejecuta como "postgres"). En cualquier caso, usa el interruptor --userns para mapear namespaces de usuario, la mayoría de las veces usando la opción keep-id.

$ podman run -v "$PWD":/home/jovyan/work --userns=keep-id jupyter/scipy-notebook

3) No existe tal imagen o las claves simples no pueden contener ':'

Al ejecutar un comando podman pull o podman build y no se puede descargar una imagen "común", es probable que el archivo /etc/containers/registries.conf no esté instalado o esté mal configurado.

Síntoma

$ sudo podman build -f Dockerfile
STEP 1: FROM alpine
error building: error creating build container: no such image "alpine" in registry: image not known

o

$ sudo podman pull fedora
error pulling image "fedora": unable to pull fedora: error getting default registries to try: Near line 9 (last key parsed ''): Bare keys cannot contain ':'.

Solución

  • Verifica que el archivo /etc/containers/registries.conf exista. Si no es así, verifica que el paquete containers-common esté instalado.
  • Verifica que las entradas en la lista unqualified-search-registries del archivo /etc/containers/registries.conf sean válidas y accesibles.
•
es decir, unqualified-search-registries = ["registry.fedoraproject.org", "quay.io", "registry.access.redhat.com"]

4) http: el servidor dio una respuesta HTTP a un cliente HTTPS

Al ejecutar un comando de Podman como build, commit, pull o push a un registro, la verificación TLS está activada por defecto. Si no se usa cifrado con esos comandos, este error puede ocurrir.

Síntoma

$ sudo podman push alpine docker://localhost:5000/myalpine:latest
Getting image source signatures
Get https://localhost:5000/v2/: http: el servidor dio una respuesta HTTP a un cliente HTTPS

Solución

Por defecto, la verificación TLS está activada al comunicarse con registros desde Podman. Si el registro no requiere cifrado, los comandos de Podman como build, commit, pull y push fallarán a menos que la verificación TLS se desactive usando la opción --tls-verify. NOTA: No se recomienda en absoluto comunicarse con un registro sin usar verificación TLS.

  • Desactiva la verificación TLS pasando false a la opción tls-verify.
  • Es decir, podman push --tls-verify=false alpine docker://localhost:5000/myalpine:latest

Para una solución global, los usuarios[1] pueden crear el archivo /etc/containers/registries.conf.d/registry-NAME.conf (reemplazando NAME con el nombre de este registro) con el siguiente contenido (reemplazando FULLY.QUALIFIED.NAME.OF.REGISTRY con la dirección de este registro):

[[registry]]
location = "FULLY.QUALIFIED.NAME.OF.REGISTRY"
insecure = true

[1] Si estás usando una Mac / Windows, deberías ejecutar podman machine ssh para iniciar sesión en la máquina de podman antes de agregar la entrada insegura al archivo registry—conf.

Este es un método inseguro y debe usarse con precaución.

5) Los contenedores sin root no pueden hacer ping a los hosts

Al usar el comando ping desde un contenedor sin root, el comando puede fallar debido a la falta de privilegios.

Síntoma

$ podman run --rm fedora ping -W10 -c1 redhat.com
PING redhat.com (209.132.183.105): 56 data bytes
--- redhat.com ping statistics ---
1 packets transmitted, 0 packets received, 100% packet loss

Solución

Lo más probable es que sea necesario habilitar los pings no privilegiados en el host. Asegúrate de que la UID del usuario forme parte del rango en el archivo /proc/sys/net/ipv4/ping_group_range.

Para cambiar su valor, puedes usar algo como:

# sysctl -w "net.ipv4.ping_group_range=0 2000000"

Para que el cambio sea persistente, necesitarás agregar un archivo en /etc/sysctl.d que contenga net.ipv4.ping_group_range=0 $MAX_UID.

6) La compilación se cuelga cuando el Dockerfile contiene el comando useradd

Cuando el Dockerfile contiene un comando como RUN useradd -u 99999000 -g users newuser, la compilación puede colgarse.

Síntoma

Si estás usando un comando useradd dentro de un Dockerfile con una UID/GID grande, creará un archivo disperso grande /var/log/lastlog. Esto puede hacer que la compilación se cuelgue para siempre. El lenguaje Go no soporta archivos dispersos correctamente, lo que puede llevar a la creación de archivos muy grandes.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

5) El archivo lastlog se vuelve demasiado grande

Si el archivo lastlog dentro de tu imagen de contenedor crece demasiado, tu sistema podría quedarse sin espacio en disco.

Solución

Si la entrada en el Dockerfile se veía así: RUN useradd -u 99999000 -g users newuser, entonces agrega el parámetro --no-log-init para cambiarlo a: RUN useradd --no-log-init -u 99999000 -g users newuser. Esta opción le dice a useradd que deje de crear el archivo lastlog.

6) Permiso denegado al ejecutar comandos de Podman

Cuando Podman sin privilegios intenta ejecutar un contenedor en un directorio home no ejecutable, se generará un error de permiso.

Síntoma

Si estás ejecutando Podman o Buildah en un directorio home que está montado como no ejecutable, fallarán con un mensaje como:

$ podman run centos:7
standard_init_linux.go:203: exec user process caused "permission denied"

Solución

Dado que el administrador del sistema configuró tu directorio home como no ejecutable, no se te permitirá ejecutar contenedores desde el almacenamiento en tu directorio home. Es posible solucionar esto especificando manualmente una ruta de almacenamiento de contenedores que no esté en un montaje no ejecutable. Simplemente copia el archivo /etc/containers/storage.conf a ~/.config/containers/ (creando el directorio si es necesario). Especifica un directorio graphroot que no esté en un punto de montaje no ejecutable y al que tengas privilegios de lectura/escritura. También deberás modificar otros campos a directorios escribibles.

Por ejemplo

$ cat ~/.config/containers/storage.conf
[storage]
  driver = "overlay"
  runroot = "/run/user/1000"
  graphroot = "/execdir/myuser/storage"
  [storage.options]
    mount_program = "/bin/fuse-overlayfs"

7) Permiso denegado al ejecutar systemd dentro de un contenedor de Podman

Al ejecutar systemd como PID 1 dentro de un contenedor en una máquina separada por SELinux, necesita escribir en el sistema de archivos cgroup.

Síntoma

Systemd recibe permiso denegado al intentar escribir en el sistema de archivos cgroup, y los mensajes de AVC comienzan a aparecer en el archivo audit.log o en el journal del sistema.

Solución

Las versiones más recientes de Podman (2.0 o superior) admiten la ejecución de contenedores basados en init con etiquetas SELinux diferentes, lo que permite al proceso del contenedor acceder al sistema de archivos cgroup. Esta función requiere container-selinux-2.132 o versiones más recientes.

Antes de Podman 2.0, el booleano SELinux container_manage_cgroup permite a los procesos del contenedor escribir en el sistema de archivos cgroup. Activa este booleano, en sistemas separados por SELinux, para permitir que systemd se ejecute correctamente en el contenedor. Solo haz esto en sistemas que ejecuten versiones antiguas de Podman.

# setsebool -P container_manage_cgroup true

8) Newuidmap ausente al ejecutar comandos de Podman sin privilegios

Podman sin privilegios requiere que los programas newuidmap y newgidmap estén instalados.

Síntoma

Si estás ejecutando Podman o Buildah como un usuario sin privilegios, recibes un error que se queja de un ejecutable newuidmap ausente.

$ podman run -ti fedora sh
command required for rootless mode with multiple IDs: exec: "newuidmap": executable file not found in $PATH

Solución

Instala una versión de shadow-utils que incluya estos ejecutables. Ten en cuenta que para RHEL y CentOS 7, al menos la versión 7.7 debe estar instalada para que el soporte esté disponible.

9) rootless setup user: argumento inválido

Podman sin privilegios requiere que el usuario que lo ejecuta tenga un rango de UID listado en /etc/subuid y /etc/subgid.

Síntoma

Un usuario, ya sea a través de --user o a través de la configuración predeterminada para la imagen, no se mapea dentro del espacio de nombres.

$ podman run --rm -ti --user 1000000 alpine echo hi
Error: container create failed: container_linux.go:344: starting container process caused "setup user: invalid argument"

Solución

Actualiza /etc/subuid y /etc/subgid con campos para usuarios que se vean así:

$ cat /etc/subuid
johndoe:100000:65536
test:165536:65536

El formato de este archivo es NOMBREDEUSUARIO:UID:RANGO

  • nombre de usuario como se lista en /etc/passwd o getpwent.
  • El uid inicial asignado para el usuario.
  • El tamaño del rango de UIDs asignados para el usuario.

Esto significa que a johndoe se le asignan los UIDs 100000-165535 además de su UID estándar en el archivo /etc/passwd.

Debes asegurarte de que cada usuario tenga un rango único de UIDs, ya que los UIDs superpuestos podrían permitir que un usuario ataque a otro. Además, asegúrate de que el rango de UIDs que asignas pueda cubrir todos los UIDs que el contenedor requiere. Por ejemplo, si el contenedor tiene un usuario con UID 10000, asegúrate de tener al menos 10000 subuids, y si el contenedor necesita ejecutarse como un usuario con UID 1000000, asegúrate de tener al menos 1000000 subuids.

También podrías usar el programa usermod para asignar UIDs a un usuario.

Si actualizas el archivo /etc/subuid o /etc/subgid, necesitas detener todos los contenedores en ejecución y matar el proceso de pausa. Esto se hace automáticamente con el comando system migrate, que también se puede usar para detener todos los contenedores y matar el proceso de pausa.

# usermod --add-subuids 200000-201000 --add-subgids 200000-201000 johndoe
# grep johndoe /etc/subuid /etc/subgid
/etc/subuid:johndoe:200000:1001
/etc/subgid:johndoe:200000:1001

10) Cambiar la ubicación de Graphroot conduce a permiso denegado

Cuando cambio la ubicación de almacenamiento de graphroot en storage.conf, la próxima vez que ejecuto Podman, recibo un error como:

# podman run -p 5000:5000 -it centos bash
bash: error while loading shared libraries: /lib64/libc.so.6: cannot apply additional memory protection after relocation: Permission denied

Por ejemplo, el administrador configura un disco de repuesto para montarlo en /src/containers y apunta storage.conf a este directorio.

Síntoma

SELinux bloquea que los contenedores utilicen ubicaciones arbitrarias para el almacenamiento overlay. Estos directorios necesitan ser etiquetados con las mismas etiquetas que si el contenido estuviera bajo /var/lib/containers/storage.

Solución

Informa a SELinux sobre el nuevo almacenamiento de contenedores configurando un registro de equivalencia. Esto le dice a SELinux que etiquete el contenido bajo la nueva ruta como si estuviera almacenado bajo /var/lib/containers/storage.

# semanage fcontext -a -e /var/lib/containers /srv/containers
# restorecon -R -v /srv/containers

El comando semanage anterior le dice a SELinux que configure el etiquetado predeterminado de /srv/containers para que coincida con /var/lib/containers. El comando restorecon le dice a SELinux que aplique las etiquetas al contenido real.

Ahora todo el contenido nuevo creado en estos directorios se creará automáticamente con la etiqueta correcta.

13) Podman inside of a container

When running Podman inside of a container, all of the containers that Podman manages will have their state shown as “created” or “configured” even if they were running or stopped.

Solution

When running Podman inside of a container, you should mount /var/lib/containers/storage as a volume. It is typical not to mount the host version of the directory, but if you wish to share containers with the host, you can do so. If you do mount the host’s /var/lib/containers/storage, you must also mount the host’s /run/libpod and /run/containers/storage directories. If you do not, Podman will detect that temporary files have been cleared and assume that a system restart has taken place. This can cause Podman to reset container states and lose track of running containers.

For running containers on the host from inside a container, we also recommend the Podman remote client ⟨docs/tutorials/remote_client.md⟩, which only requires a single socket to be mounted into the container.

14) Rootless 'podman build' fails EPERM on NFS:

NFS enforces file creation on different UIDs on the server side and does not understand user namespace, which rootless Podman requires. When a container root process like YUM attempts to create a file owned by a different UID, the NFS Server denies the creation. NFS is also a problem for file locks when the storage is on it. Other distributed file systems (for example: Lustre, Spectrum Scale, the General Parallel File System (GPFS)) are also not supported when running in rootless mode as these file systems do not understand user namespace.

Symptom

$ podman build .
ERRO[0014] Error while applying layer: ApplyLayer exit status 1 stdout:  stderr: open /root/.bash_logout: permission denied
error creating build container: Error committing the finished image: error adding layer with blob "sha256:a02a4930cb5d36f3290eb84f4bfa30668ef2e9fe3a1fb73ec015fc58b9958b17": ApplyLayer exit status 1 stdout:  stderr: open /root/.bash_logout: permission denied

Solution

Choose one of the following:
* Set up containers/storage in a different directory, not on an NFS share.
* Create a directory on a local file system.
* Edit ~/.config/containers/containers.conf and point the volume_path option to that local directory. (Copy /usr/share/containers/containers.conf if ~/.config/containers/containers.conf does not exist)
* Otherwise just run Podman as root, via sudo podman

20) Passed-in devices or files can't be accessed in rootless container

As a non-root user, you have group access rights to a device or files that you want to pass into a rootless container with --device=... or --volume=...

Symptom

Any access inside the container is rejected with "Permission denied".

Solution

The runtime uses setgroups(2), hence the process loses all additional groups the non-root user has. Use the --group-add keep-groups flag to pass the user's supplementary group access into the container. Currently only available with the crun OCI runtime.

21) A rootless container running in detached mode is closed at logout

When running a container with a command like podman run --detach httpd as a rootless user, the container is closed upon logout and is not kept running.

Symptom

When logging out of a rootless user session, all containers that were started in detached mode are stopped and are not kept running. As the root user, these same containers would survive the logout and continue running.

Solution

When systemd notes that a session that started a Podman container has exited, it will also stop any containers that have been associated with it. To avoid this, use the following command before logging out: loginctl enable-linger. To later revert the linger functionality, use loginctl disable-linger.

22) Containers default detach keys conflict with shell history navigation

Navegación del historial del shell con Podman

Podman utiliza Ctrl-p, Ctrl-q de forma predeterminada para desconectar de los contenedores en ejecución. Los shells bash y zsh utilizan Ctrl-p de forma predeterminada para mostrar el comando anterior. Esto causa problemas al ejecutar un shell dentro de un contenedor.

Síntoma

Con la combinación de teclas de desconexión predeterminada Ctrl-p, Ctrl-q, la navegación por el historial del shell (probado en bash y zsh) usando Ctrl-p para acceder al comando anterior no mostrará este comando anterior ni nada más. Conmon está esperando un carácter adicional para ver si el usuario desea desconectarse del contenedor. Agregar caracteres adicionales al comando hará que se muestre junto con el carácter adicional. Si el usuario escribe Ctrl-p por segunda vez, el shell mostrará el penúltimo comando.

Solución

La solución a esto es cambiar las claves de desconexión predeterminadas. Por ejemplo, para cambiar los valores predeterminados a Ctrl-q, Ctrl-q, use la opción --detach-keys.

$ podman run -ti --detach-keys ctrl-q,ctrl-q fedora sh

Para que este cambio sea el predeterminado para todos los contenedores, los usuarios pueden modificar el archivo containers.conf. Esto se puede hacer simplemente en su directorio principal, pero agregando las siguientes líneas a su archivo containers.conf:

$ cat >> ~/.config/containers/containers.conf << _eof
[engine]
detach_keys="ctrl-q,ctrl-q"
_eof

Para afectar a los contenedores que se ejecutan como root y a todos los usuarios, modifique los valores predeterminados del sistema en /etc/containers/containers.conf.

23) Contenedor con puertos expuestos no se ejecuta en un pod

Un contenedor con puertos que han sido publicados con la opción --publish o -p no se puede ejecutar dentro de un pod.

Síntoma

$ podman pod create --name srcview -p 127.0.0.1:3434:3434 -p 127.0.0.1:7080:7080 -p 127.0.0.1:3370:3370                        4b2f4611fa2cbd60b3899b936368c2b3f4f0f68bc8e6593416e0ab8ecb0a3f1d
$ podman run --pod srcview --name src-expose -p 3434:3434 -v "${PWD}:/var/opt/localrepo":Z,ro sourcegraph/src-expose:latest serve /var/opt/localrepo
Error: cannot set port bindings on an existing container network namespace

Solución

Esta es una limitación conocida. Si un contenedor se va a ejecutar dentro de un pod, no es necesario publicar el puerto para los contenedores del pod. El puerto solo debe ser publicado por el pod mismo. Las pilas de red del pod actúan como la pila de red en el host: tiene una variedad de contenedores en el pod, y programas en el contenedor, todos compartiendo una única interfaz y dirección IP, y los puertos asociados. Si un contenedor se vincula a un puerto, ningún otro contenedor puede usar ese puerto dentro del pod mientras esté en uso. Los contenedores en el pod también pueden comunicarse a través de localhost al hacer que un contenedor se vincule a localhost en el pod, y otro se conecte a ese puerto.

25) podman run --rootfs link/to//read/only/dir no funciona

Un error como "OCI runtime error" en un sistema de archivos de solo lectura o el error "{image} is not an absolute path or is a symlink" son indicadores frecuentes de este problema. Para más detalles, revise este problema ⟨https://github.com/containers/podman/issues/5895⟩.

Síntoma

Podman sin root requiere que ciertos archivos existan en un sistema de archivos para poder ejecutarse. Podman creará /etc/resolv.conf, /etc/hosts y otros descriptores de archivo en el rootfs para montar volúmenes en ellos.

Solución

Ejecute el contenedor una vez en modo de lectura/escritura, Podman creará todos los FD en el rootfs, y a partir de ese momento podrá ejecutarlo con un rootfs de solo lectura.

$ podman run --rootfs /path/to/rootfs:O ....

26) Ejecutar contenedores con límites de recursos falla con un error de permiso

En algunos sistemas basados en systemd, los usuarios no root no tienen permisos de delegación de límites de recursos. Esto hace que el establecimiento de límites de recursos falle.

Síntoma

Ejecutar un contenedor con opciones de límite de recursos fallará con un error similar al siguiente:

--cpus, --cpu-period, --cpu-quota, --cpu-shares:

Error: OCI runtime error: crun: the requested cgroup controller `cpu` is not available

--cpuset-cpus, --cpuset-mems:

Error: OCI runtime error: crun: the requested cgroup controller `cpuset` is not available

Esto significa que la delegación de límites de recursos no está habilitada para el usuario actual.

Solución

Puede verificar si la delegación de límites de recursos está habilitada ejecutando el siguiente comando:

$ cat "/sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/cgroup.controllers"

La salida de ejemplo podría ser:

memory pids

En el ejemplo anterior, cpu y cpuset no están listados, lo que significa que el usuario actual no tiene permiso para establecer límites de CPU o CPUSET.

[Service]
Delegate=memory pids cpu cpuset

Después de cerrar sesión y volver a iniciarla, debería tener permiso para establecer límites de CPU y CPUSET.

Síntoma

Las reglas del firewall creadas por podman se pierden cuando se recarga el firewall.

Solución

@ranjithrajaram ha creado un hook de systemd para solucionar este problema

1) Para "firewall-cmd --reload", cree un archivo de unidad de systemd con lo siguiente

[Unit]

Wants=dbus.service
After=dbus.service
[Service]
Type=simple
ExecStart=/bin/bash -c '/bin/busctl monitor --system --match "interface=org.fedoraproject.FirewallD1,member=Reloaded" --match "interface=org.fedoraproject.FirewallD1,member=PropertiesChanged" | while read -r line ; do podman network reload --all ; done'
[Install]
WantedBy=default.target

2) Para "systemctl restart firewalld", cree un archivo de unidad de systemd con lo siguiente

[Unit]

Wants=firewalld.service
After=firewalld.service
PartOf=firewalld.service
[Service]
Type=simple
RemainAfterExit=yes
ExecStart=/usr/bin/podman network reload --all
[Install]
WantedBy=default.target

Sin embargo, si usa busctl monitor, no podrá obtener una salida legible por máquina en RHEL 8. Ya que no tiene busctl -j como se menciona aquí por @yrro.

Para RHEL 8, puede usar el siguiente script bash de una sola línea.

Wants=dbus.service
After=dbus.service
Requires=firewalld.service
[Service]

Restart=Always
[Install]
WantedBy=default.target

34) El contenedor crea un archivo que no es propiedad del UID regular del usuario

Después de ejecutar un contenedor con Podman sin privilegios, el usuario no root ve un UID y GID numéricos en lugar de un nombre de usuario y nombre de grupo.

Síntoma

Al listar los permisos de archivos con ls -l en el host, en un directorio que se pasó como --volume /some/dir a podman run, se muestran el UID y GID en lugar del nombre de usuario y nombre de grupo correspondientes. Los números de UID y GID que se muestran provienen de los rangos de UID y GID subordinados del usuario en el sistema host.

Un ejemplo

$ mkdir dir1
$ chmod 777 dir1
$ podman run --rm -v ./dir1:/dir1:Z   
             --user 2003:2003   
             docker.io/library/ubuntu bash -c "touch /dir1/a; chmod 600 /dir1/a"
$ ls -l dir1/a
-rw-------. 1 102002 102002 0 Jan 19 19:35 dir1/a
$ less dir1/a
less: dir1/a: Permiso denegado

Solución

Si desea leer, cambiar el propietario o eliminar dicho archivo, ingrese a un espacio de nombres de usuario. En lugar de ejecutar comandos como less dir1/a o rm dir1/a, debe anteponer al comando podman unshare, es decir, podman unshare less dir1/a o podman unshare rm dir1/a. Para cambiar la propiedad del archivo dir1/a a su UID y GID de usuario regular, ejecute podman unshare chown 0:0 dir1/a. Un archivo que tenga la propiedad 0:0 en el espacio de nombres de usuario es propiedad del usuario regular en el host. Para usar funciones de Bash, como la expansión de variables y la búsqueda de patrones, debe envolver el comando con bash -c, por ejemplo, podman unshare bash -c 'ls $HOME/dir1/a*'.

¿Habría sido posible ejecutar Podman de otra manera para que su usuario regular se convirtiera en el propietario del archivo? Sí, puede usar la opción --userns keep-id:uid=$uid,gid=$gid para cambiar cómo se mapean los UID y GID entre el contenedor y el host. Probemos.

En el ejemplo anterior, ls -l muestra el UID 102002 y el GID 102002. Establezca variables de shell

$ uid_from_ls=102002
$ gid_from_ls=102002

Establezca variables de shell a los UID y GID subordinados más bajos

$ lowest_subuid=$(podman info --format "{{ (index .Host.IDMappings.UIDMap 1).HostID }}")
$ lowest_subgid=$(podman info --format "{{ (index .Host.IDMappings.GIDMap 1).HostID }}")

Calcule el UID y GID dentro del contenedor que se mapean al propietario del archivo creado en el host.

$ uid=$(( $uid_from_ls - $lowest_subuid + 1))
$ gid=$(( $gid_from_ls - $lowest_subgid + 1))

(En el cálculo se asumió que solo hay un rango de subuid y un rango de subgid)

$ echo $uid
2003
$ echo $gid
2003

El cálculo muestra que el UID es 2003 y el GID es 2003 dentro del contenedor. Esto no sorprende, ya que esto es lo que se especificó anteriormente con --user=2003:2003, pero el mismo cálculo podría usarse siempre que se especifique un nombre de usuario o no se use la opción --user.

Ejecute el contenedor nuevamente pero ahora con los UID y GID mapeados

$ mkdir dir1
$ chmod 777 dir1
$ podman run --rm
  -v ./dir1:/dir1:Z   
  --user $uid:$gid   
  --userns keep-id:uid=$uid,gid=$gid   
     docker.io/library/ubuntu bash -c "touch /dir1/a; chmod 600 /dir1/a"
$ id -u
tester
$ id -g
tester
$ ls -l dir1/a
-rw-------. 1 tester tester 0 Jan 19 20:31 dir1/a
$

En este ejemplo, la opción --user especificó un usuario sin privilegios en el contenedor. Como el usuario sin privilegios también podría haberse especificado en la imagen del contenedor, por ejemplo.

$ podman image inspect --format "{{user: {{.User}} }}" IMAGE
user: hpc

el mismo problema también podría ocurrir incluso sin especificar --user.

Otra variante del mismo problema podría ocurrir al usar --user=root:root (el predeterminado), pero donde el usuario root crea archivos no root de alguna manera (por ejemplo, creándolos ellos mismos, o cambiando el UID efectivo a un usuario sin privilegios y luego creando archivos).

37) Sincronización de correcciones de errores para podman-remote o configuraciones que utilizan la API de Podman

Después de actualizar Podman a una versión más reciente, un problema con la versión anterior de Podman todavía se presenta al usar podman-remote.

Síntoma

Al ejecutar comandos remotos de podman con la versión más actualizada de Podman, pueden surgir problemas que se corrigieron en una versión anterior de Podman, ya sea en el lado del cliente de Podman o en el lado del servidor de Podman.

Solución

Al actualizar Podman a una versión particular para las correcciones requeridas, los usuarios a menudo cometen el error de actualizar solo el cliente de Podman. Sin embargo, si una configuración utiliza podman-remote o utiliza un cliente que se comunica con el servidor Podman en una máquina remota a través de la API REST, es necesario actualizar tanto el cliente de Podman como el servidor de Podman que se ejecutan en la máquina remota. Tanto el cliente como el servidor de Podman deben actualizarse a la misma versión.

Ejemplo: si un error particular se corrigió en v4.1.0, entonces el cliente de Podman debe tener la versión v4.1.0 y el servidor de Podman debe tener la versión v4.1.0.

Ejecute Podman sin la bandera --tty (-t).

La bandera --tty (-t) solo debe usarse cuando el programa requiere interacción del usuario en la terminal, por ejemplo, al esperar que el usuario escriba una respuesta a una pregunta.

39) Podman run falla con Error: modo de espacio de nombres no reconocido keep-id:uid=1000,gid=1000 pasado

Podman 4.3.0 introdujo las opciones uid y gid que se pueden pasar a --userns keep-id y que no son reconocidas por versiones anteriores de Podman.

Síntoma

Al usar una versión de Podman anterior a la 4.3.0, las opciones uid y gid no son reconocidas y se genera un error de "modo de espacio de nombres no reconocido".

Ejecute

$ gid=1000

   .Host.IDMappings.UIDMap }}+{{.Size }}{{end }}" ) - 1 ))

   .Host.IDMappings.GIDMap }}+{{.Size }}{{end }}" ) - 1 ))
$ podman run --rm   
  --user $uid:$gid   
  --uidmap 0:1:$uid   
  --uidmap $uid:0:1

  --gidmap $(($gid+1)):$(($gid+1)):$(($subgidSize-$gid))

      1000          0          1
      1001       1001      64536

que utiliza el mismo mapeo de UID y GID que al especificar --userns keep-id:uid=$uid,gid=$gid con Podman 4.3.0 (o superior)

$ gid=1000
$ podman run --rm

  --userns keep-id:uid=$uid,gid=$gid

         0          1       1000

42) Las compilaciones de podman-en-podman que son intensivas en E/S de archivos son muy lentas

Al utilizar el controlador de almacenamiento overlay para realizar una compilación podman anidada dentro de un contenedor en ejecución, las operaciones de E/S de archivos como COPY de una gran cantidad de datos son muy lentas o pueden colgarse por completo.

Síntoma

Utilizando el controlador de almacenamiento overlay por defecto, una línea COPY, ADD o RUN intensiva en E/S en un Containerfile que se ejecuta dentro de otro contenedor es muy lenta o se cuelga por completo al ejecutar una compilación podman dentro del contenedor padre en ejecución.

Solución

Esto podría ser causado por el contenedor hijo que utiliza fuse-overlayfs para escribir en /var/lib/containers/storage. Las escrituras pueden ser lentas con fuse-overlayfs. La solución es usar el sistema de archivos overlay nativo utilizando un directorio local en el sistema host como volumen para /var/lib/containers/storage de la siguiente manera: podman run --privileged --rm -it -v ./nested_storage:/var/lib/containers/storage parent:latest. Asegúrese de que la imagen base de parent:latest en este ejemplo no tenga contenido en /var/lib/containers/storage en la imagen misma para que esto funcione. Una vez que se utiliza el volumen nativo, el contenedor anidado no debería recurrir a fuse-overlayfs para escribir archivos y la compilación anidada se completará mucho más rápido.

Si no tiene acceso al proceso de ejecución padre, como en un entorno de CI, entonces la segunda opción es cambiar el controlador de almacenamiento a vfs en la imagen padre cambiando esta línea en su archivo storage.conf: driver = "vfs". Es posible que tenga que ejecutar podman system reset para que esto tenga efecto. Sabrá que se ha cambiado cuando podman info |grep graphDriverName muestre graphDriverName: vfs. Este método tiene un rendimiento más lento que el método del volumen anterior, pero es significativamente más rápido que fuse-overlayfs

44) sudo podman run --userns=auto falla con Cannot find mappings for user containers

Cuando se invoca podman rootful con --userns=auto, podman necesita seleccionar subrangos de subuids y subgids para el espacio de nombres de usuario del contenedor. Podman rootful asegura que los rangos de subuid y subgid para dichos contenedores no se superpongan, pero ¿cómo puede podman rootful evitar que otras herramientas usen accidentalmente estos IDs?

No es posible bloquear a otras herramientas que se ejecutan como root para que no usen estos IDs, pero tales herramientas normalmente no usarían subuids y subgids que ya han sido asignados a un usuario en /etc/subuid y /etc/subgid.

El nombre de usuario containers en el host tiene una función especial para Podman rootful. Podman rootful utiliza los subuids y subgids del usuario containers al ejecutar contenedores --userns=auto. El usuario containers no necesita estos subuids y subgids porque no se deben iniciar procesos como el usuario containers. En otras palabras, el usuario containers es un usuario especial que solo existe en el sistema para reservar subuids y subgids para podman rootful.

containers es el nombre de usuario por defecto, pero se puede cambiar estableciendo la opción root-auto-userns-user en el archivo /etc/containers/storage.conf

Síntoma

Ejecutar podman rootful con --userns=auto

sudo podman run --rm --userns=auto alpine echo hello

El comando falla con el mensaje de error:

ERRO[0000] Cannot find mappings for user "containers": no subuid ranges found for user "containers" in /etc/subuid
Error: creating container storage: not enough unused IDs in user namespace

Los archivos /etc/subuid y /etc/subgid no tienen líneas que comiencen con containers:

Solución

Agregue rangos de subuid y subgid para el usuario containers en /etc/subuid y /etc/subgid o proporcione dichos rangos con /etc/nsswitch.conf. Para más detalles, vea subid(5).

Los siguientes pasos crean el usuario containers y le asignan rangos grandes de subuid y subgid:

1.

Comprobar los rangos de subuid y subgid del usuario containers $ grep ^containers: /etc/subuid containers:720896:65536 $ grep ^containers: /etc/subgid containers:720896:65536 Por defecto, useradd asigna 65536 subuids y 65536 subgids a un usuario nuevo. Típicamente le gustaría que el grupo reservado fuera más grande que eso. Cuanto mayor sea el tamaño, más contenedores se podrían iniciar con sudo podman run --userns=auto ...

NAME

podman-troubleshooting - A list of common issues and solutions for Podman

DESCRIPTION

This page provides a list of common issues and solutions for Podman.

Troubleshooting

This section describes common issues and their solutions.

1.
Create a directory owned by root sudo mkdir /var/test
2.
Give everyone read access to the directory sudo chmod 755 /var/test
3.
Run ls directly on the host ls /var/test The command succeeds.
4.
Run rootless podman with the directory bind-mounted. Set z as volume option. podman run --rm -v /var/test:/dir:z fedora ls /dir The command fails with the following error message: Error: lsetxattr(label=system_u:object_r:container_file_t:s0) /var/test: operation not permitted The error is expected because the unprivileged user does not have the privileges to modify the SELinux context of the directory /var/test
5.
Repeat the previous command but remove the volume option podman run --rm -v /var/test:/dir fedora ls /dir The command is blocked by SELinux and fails with the following error message: ls: cannot open directory '/dir': Permission denied

Note, access to the bind-mounted directory depends on SELinux rules. For example, bind-mounting the directory /usr/share succeeds even though the user does not have write permissions to the directory. The following command succeeds:

podman run --rm -v /usr/share:/dir fedora ls /dir

Solution

Alternative 1

Use the O flag to mount the directory from the host as a temporary storage using the overlay file system.

podman run --rm -v /var/test:/dir:O fedora ls /dir

Modifications to the mount point are destroyed when the container finishes executing, similar to a tmpfs mount point being unmounted.

The following command succeeds:

podman run --rm -v /var/test:/dir:O fedora touch /dir/file

The command touch creates the file but the file is discarded when the container finishes.

Alternative 2

If the directory /var/test resides on a file system that supports XATTR, set a directory SELinux context that corresponds to the podman volume flag :z

sudo chcon -R system_u:object_r:container_file_t:s0 /var/test

The following command now succeeds

podman run --rm -v /var/test:/dir ls /dir

Alternative 3

Modify the default SELinux context configuration for the directory /var/test with the command

sudo semanage fcontext -a -s system_u -t container_file_t "/var/test(/.*)?"

Change the SElinux contexts recursively for files and directories under /var/test to match the new configuration

sudo restorecon -R -F -v /var/test

Alternative 4

Add the option --security-opt label=disable to disable SELinux for the Podman command.

podman run --rm --security-opt label=disable -v /var/test:/dir fedora ls /dir
