NOMBRE

po4a - framework para traducir documentación y otros materiales

Introducción

po4a (PO para cualquier cosa) facilita el mantenimiento de la traducción de documentación utilizando las herramientas clásicas de gettext. La característica principal de po4a es que desacopla la traducción del contenido de su estructura documental.

Este documento sirve como introducción al proyecto po4a con un enfoque en los usuarios potenciales que estén considerando si usar esta herramienta y en los curiosos que quieran entender por qué las cosas son como son.

¿Por qué po4a?

La filosofía del Software Libre es hacer que la tecnología sea verdaderamente accesible para todos. Pero las licencias no son la única consideración: el software libre sin traducir es inútil para los hablantes no ingleses. Por lo tanto, todavía tenemos trabajo que hacer para que el software esté disponible para todos.

Esta situación es bien entendida por la mayoría de los proyectos y todo el mundo está ahora convencido de la necesidad de traducir todo. Sin embargo, las traducciones reales representan un enorme esfuerzo de muchos individuos, mermado por pequeñas dificultades técnicas.

Afortunadamente, el software de Código Abierto está muy bien traducido utilizando la suite de herramientas gettext. Estas herramientas se utilizan para extraer las cadenas a traducir de un programa y presentar las cadenas a traducir en un formato estandarizado (llamado archivos PO, o catálogos de traducción). Ha surgido un ecosistema completo de herramientas para ayudar a los traductores a traducir estos archivos PO. El resultado es luego utilizado por gettext en tiempo de ejecución para mostrar mensajes traducidos a los usuarios finales.

Sin embargo, en cuanto a la documentación, la situación sigue siendo algo decepcionante. Al principio, traducir documentación puede parecer más fácil que traducir un programa, ya que parecería que solo tienes que copiar el archivo fuente de la documentación y empezar a traducir el contenido. Sin embargo, cuando la documentación original se modifica, hacer un seguimiento de las modificaciones rápidamente se convierte en una pesadilla para los traductores. Si se hace manualmente, esta tarea es desagradable y propensa a errores.

Las traducciones desactualizadas a menudo son peores que ninguna traducción. Los usuarios finales pueden ser engañados por la documentación que describe un comportamiento antiguo del programa. Además, no pueden interactuar directamente con los mantenedores ya que no hablan inglés. Adicionalmente, el mantenedor no puede solucionar el problema ya que no conoce todos los idiomas en los que se traduce su documentación. Estas dificultades, a menudo causadas por una mala herramienta, pueden minar la motivación de los traductores voluntarios, agravando aún más el problema.

El objetivo del proyecto po4a es facilitar el trabajo de los traductores de documentación. En particular, hace que las traducciones de documentación sean *mantenibles*.

La idea es reutilizar y adaptar el enfoque gettext a este campo. Al igual que con gettext, los textos se extraen de sus ubicaciones originales y se presentan a los traductores como catálogos de traducción PO. Los traductores pueden aprovechar las herramientas clásicas de gettext para supervisar el trabajo a realizar, colaborar y organizarse en equipos. po4a luego inyecta las traducciones directamente en la estructura de la documentación para producir archivos fuente traducidos que pueden ser procesados y distribuidos al igual que los archivos en inglés. Cualquier párrafo que no se traduzca se deja en inglés en el documento resultante, asegurando que los usuarios finales nunca vean una traducción desactualizada en la documentación.

Esto automatiza la mayor parte del trabajo pesado del mantenimiento de la traducción. Descubrir los párrafos que necesitan una actualización es muy fácil, y el proceso es completamente automatizado cuando los elementos se reordenan sin modificaciones adicionales. También se pueden usar verificaciones específicas para reducir la posibilidad de errores de formato que resultarían en un documento roto.

Por favor, consulte también el **FAQ** más abajo en este documento para una lista más completa de las ventajas y desventajas de este enfoque.

Formatos soportados

Actualmente, este enfoque se ha implementado con éxito en varios tipos de formatos de texto:

man (parser maduro)
El buen y viejo formato de las páginas de manual, utilizado por tantos programas. El soporte de po4a es muy bienvenido aquí ya que este formato es algo difícil de usar y no muy amigable para los principiantes.

El módulo Locale::Po4a::Man(3pm) también soporta el formato mdoc, utilizado por las páginas man de BSD (que también son bastante comunes en Linux).

AsciiDoc (parser maduro)
Este formato es un formato de marcado ligero destinado a facilitar la creación de documentación. Se utiliza, por ejemplo, para documentar el sistema git. Estas páginas de manual se traducen utilizando po4a.

Ver Locale::Po4a::AsciiDoc para más detalles.

pod (parser maduro)
Este es el formato de documentación en línea de Perl. El lenguaje y sus extensiones se documentan utilizando este formato además de la mayoría de los scripts de Perl existentes. Facilita mantener la documentación cerca del código real al incrustarlos ambos en el mismo archivo. Facilita la vida del programador, pero desafortunadamente, no la del traductor, hasta que se usa po4a.

Ver Locale::Po4a::Pod para más detalles.

sgml (parser maduro)
Incluso si ha sido reemplazado por XML hoy en día, este formato todavía se usa para documentos que son más largos que unas pocas pantallas. Incluso puede usarse para libros completos. Documentos de esta longitud pueden ser muy desafiantes de actualizar. A menudo, **diff** resulta inútil cuando el texto original fue re-indentado después de la actualización. Afortunadamente, po4a puede ayudarte después de ese proceso.

Actualmente, solo se soportan DTD de DebianDoc y DocBook, pero añadir soporte para una nueva es muy fácil. Incluso es posible usar po4a en una DTD SGML desconocida sin cambiar el código proporcionando la información necesaria en la línea de comandos. Ver Locale::Po4a::Sgml(3pm) para más detalles.

TeX / LaTeX (parser maduro)
El formato LaTeX es un formato de documentación importante utilizado en el mundo del Software Libre y para publicaciones.

El módulo Locale::Po4a::LaTeX(3pm) fue probado con la documentación de Python, un libro y algunas presentaciones.

texto (parser maduro)
El formato de texto es el formato base para muchos formatos que incluyen bloques largos de texto, incluyendo Markdown, fortunes, sección de metadatos YAML, debian/changelog y debian/control.

Esto soporta el formato común utilizado en Generadores de Sitios Estáticos, READMEs y otros sistemas de documentación. Ver Locale::Po4a::Text(3pm) para más detalles.

xml y XHMTL (parser probablemente maduro)
El formato XML es un formato base para muchos formatos de documentación.

Actualmente, po4a soporta DTD de DocBook (ver Locale::Po4a::Docbook(3pm) para más detalles) y XHTML.

BibTex (parser probablemente maduro)
El formato BibTex se utiliza junto con LaTeX para formatear listas de referencias (bibliografías).

Ver Locale::Po4a::BibTex para más detalles.

Docbook (parser probablemente maduro)
Un lenguaje de marcado basado en XML que utiliza etiquetas semánticas para describir documentos.

Ver Locale::Po4a:Docbook para más detalles.

Supported formats

Guide XML (probably mature parser)
Un formato de documentación XML. Este módulo se desarrolló específicamente para ayudar con el soporte y mantenimiento de traducciones de la documentación de Gentoo Linux hasta al menos marzo de 2016 (basado en la Wayback Machine). Gentoo desde entonces ha migrado al formato DevBook XML.

Vea Locale::Po4a:Guide para más detalles.

Wml (probably mature parser)
El Lenguaje de Marcado Web, no confunda WML con las cosas de WAP que se usan en los teléfonos móviles. Este módulo depende del módulo Xhtml, que a su vez depende del módulo XmL.

Vea Locale::Po4a::Wml para más detalles.

Yaml (probably mature parser)
Un superconjunto estricto de JSON. YAML se usa a menudo en sistemas o proyectos de configuración. YAML está en el núcleo de Ansible de Red Hat.

Vea Locale::Po4a::Yaml para más detalles.

RubyDoc (probably mature parser)
El formato Ruby Document (RD), originalmente el formato de documentación por defecto para Ruby y proyectos de Ruby antes de convertirse a RDoc en 2002. Aunque aparentemente la versión japonesa del Manual de Referencia de Ruby todavía usa RD.

Vea Locale::Po4a::RubyDoc para más detalles.

Halibut (probably experimental parser)
Un sistema de producción de documentación, con elementos similares a TeX, debiandoc-sgml, TeXinfo y otros, desarrollado por Simon Tatham, el desarrollador de PuTTY.

Vea Locale::Po4a:Halibut para más detalles.

Ini (probably experimental parser)
Formato de archivo de configuración popularizado por MS-DOS.

Vea Locale::Po4a::Ini para más detalles.

texinfo (very highly experimental parser)
Toda la documentación de GNU está escrita en este formato (es incluso uno de los requisitos para convertirse en un proyecto oficial de GNU). El soporte para Locale::Po4a::Texinfo(3pm) en po4a todavía está en sus inicios. Por favor, informe de errores y solicitudes de características.
gemtext (very highly experimental parser)
El formato nativo de texto plano del protocolo Gemini. La extensión ".gmi" se usa comúnmente. El soporte para este módulo en po4a todavía está en su infancia. Si encuentra algo, por favor, envíe un informe de error o una solicitud de característica.
org (very highly experimental parser)
El formato de documento utilizado por el modo Org. El soporte para este módulo en po4a todavía está en su infancia. Si encuentra algo, por favor, envíe un informe de error o una solicitud de característica.
vimhelp (very highly experimental parser)
El formato utilizado para los archivos de ayuda de Vim (y la documentación de algunos plugins de terceros). El soporte para este formato en po4a todavía está en su infancia. Si encuentra algo, por favor, envíe un informe de error o una solicitud de característica.
simplepod (very highly experimental parser)
Similar al pod mencionado anteriormente, este adopta Pod::Simple como su analizador. Dado que se creó recientemente, se esperan algunos errores. Si nota algún comportamiento extraño, por favor háganoslo saber. Eventualmente, este módulo reemplazará a pod.
Others supported formats
Po4a también puede manejar algunos formatos más raros o especializados, como la documentación de opciones de compilación para los kernels de Linux 2.4+ (Locale::Po4a::KernelHelp) o los diagramas producidos por la herramienta dia (Locale::Po4a::Dia). Añadir un nuevo formato suele ser muy fácil y la tarea principal es crear un analizador para su formato de destino. Vea Locale::Po4a::TransTractor(3pm) para más información sobre esto.
Unsupported formats
Desafortunadamente, po4a todavía carece de soporte para varios formatos de documentación. Muchos de ellos serían fáciles de soportar en po4a. Esto incluye formatos que no se usan solo para documentación, como, descripciones de paquetes (deb y rpm), scripts de instalación de paquetes, preguntas, changelogs de paquetes y todos los formatos de archivo especializados utilizados por programas como escenarios de juegos o archivos de recursos de wine.

Usando po4a

La forma más sencilla de usar esta herramienta en su proyecto es escribir un archivo de configuración para el programa po4a, y solo interactuar con este programa. Por favor, consulte su documentación, en po4a(1). El resto de esta sección proporciona más detalles para los usuarios avanzados de po4a que deseen profundizar su comprensión.

Esquema detallado del flujo de trabajo de po4a

Asegúrese de leer po4a(1) antes de esta sección excesivamente detallada para obtener una visión general simplificada del flujo de trabajo de po4a. Vuelva aquí cuando desee obtener la imagen completa y aterradora, con casi todos los detalles.

En el siguiente esquema, master.doc es un nombre de ejemplo para la documentación a traducir; XX.doc es el mismo documento traducido en el idioma XX, mientras que doc.XX.po es el catálogo de traducción para ese documento en el idioma XX. Los autores de la documentación estarán principalmente preocupados por master.doc (que puede ser una página man, un documento XML, un archivo AsciiDoc, etc.); los traductores estarán principalmente preocupados por el archivo PO, mientras que los usuarios finales solo verán el archivo XX.doc.

Las transiciones con corchetes como "[po4a updates po]" representan la ejecución de una herramienta de po4a, mientras que las transiciones con llaves como "{update of master.doc}" representan una modificación manual de los archivos del proyecto.

                                   master.doc
                                       |
                                       V
     +<-----<----+<-----<-----<--------+------->-------->-------+
     :           |                     |                        :
{translation}    |          {update of master.doc}              :
     :           |                     |                        :
   XX.doc        |                     V                        V
 (optional)      |                 master.doc ->-------->------>+
     :           |                   (new)                      |
     V           V                     |                        |
  [po4a-gettextize]   doc.XX.po -->+   |                        |
          |            (old)       |   |                        |
          |              ^         V   V                        |
          |              |   [po4a updates po]                  |
          V              |           |                          V
   translation.pot       ^           V                          |
          |              |        doc.XX.po                     |
          |              |         (fuzzy)                      |
    {translation}        |           |                          |
          |              ^           V                          V
          |              |     {manual editing}                 |
          |              |           |                          |
          V              |           V                          V
      doc.XX.po --->---->+<---<-- doc.XX.po    addendum     master.doc
      (initial)                 (up-to-date)  (optional)   (up-to-date)
          :                          |            |             |

          +----->----->----->------> +            |             |
                                     |            |             |
                                     V            V             V
                                     +------>-----+------<------+
                                                  |
                                                  V
                                     [po4a updates translations]

                                                  V
                                                XX.doc
                                             (up-to-date)

De nuevo, este esquema es excesivamente complicado. Consulte po4a(1) para una visión general simplificada.

La parte izquierda representa cómo po4a-gettextize(1) puede usarse para convertir un proyecto de traducción existente a la infraestructura de po4a. Este script toma un documento original y su contraparte traducida, e intenta construir el archivo PO correspondiente. Dicha conversión manual es bastante engorrosa (vea la documentación de po4a-gettextize(1) para más detalles), pero solo es necesaria una vez para convertir sus traducciones existentes. Si no tiene ninguna traducción que convertir, puede olvidarse de esto y centrarse en la parte derecha del esquema.

En la parte superior derecha, se representa la acción del autor original, actualizando la documentación. La parte media derecha representa las actualizaciones automáticas de los archivos de traducción: el nuevo material se extrae y se compara con la traducción existente. La traducción anterior se utiliza para las partes que no han cambiado, mientras que las partes parcialmente modificadas se conectan a la traducción anterior con un marcador de "borroso" ("fuzzy") que indica que la traducción debe actualizarse. El material nuevo o muy modificado se deja sin traducir.

Luego, el bloque edición manual representa la acción de los traductores, que modifican los archivos PO para proporcionar traducciones a cada cadena y párrafo original. Esto se puede hacer utilizando un editor específico como el GNOME Translation Editor, el Lokalize de KDE o poedit, o utilizando una plataforma de localización en línea como weblate o pootle. El resultado de la traducción es un conjunto de archivos PO, uno por idioma. Por favor, consulte la documentación de gettext para más detalles.

La parte inferior de la figura muestra cómo po4a crea un documento fuente traducido a partir del documento original master.doc y el catálogo de traducción doc.XX.po que fue actualizado por los traductores. La estructura del documento se reutiliza, mientras que el contenido original se reemplaza por su contraparte traducida. Opcionalmente, se puede usar un apéndice para agregar texto adicional a la traducción. Esto se usa a menudo para agregar el nombre del traductor al documento final. Vea más abajo para detalles.

Al invocarse, po4a actualiza tanto los archivos de traducción como los archivos de documentación traducida automáticamente.

Inicio de un nuevo proyecto de traducción

Iniciar un nuevo proyecto de traducción

Si comienzas desde cero, solo tienes que escribir un archivo de configuración para po4a, y ya está. Las plantillas relevantes se crean para los archivos faltantes, permitiendo a tus colaboradores traducir tu proyecto a su idioma. Consulta po4a(1) para un tutorial de inicio rápido y para todos los detalles.

Si tienes una traducción existente, es decir, un archivo de documentación que fue traducido manualmente, puedes integrar su contenido en tu flujo de trabajo de po4a usando po4a-gettextize. Esta tarea es un poco engorrosa (como se describe en la página man de la herramienta), pero una vez que tu proyecto se convierta al flujo de trabajo de po4a, todo se actualizará automáticamente.

Actualizar las traducciones y los documentos

Una vez configurado, invocar po4a es suficiente para actualizar tanto los archivos PO de traducción como los documentos traducidos. Puedes pasar la opción "--no-translations" a po4a para no actualizar las traducciones (actualizando así solo los archivos PO) o "--no-update" para no actualizar los archivos PO (actualizando así solo las traducciones). Esto corresponde aproximadamente a los scripts individuales po4a-updatepo y po4a-translate, que ahora están obsoletos (ver "Por qué los scripts individuales están obsoletos" en el FAQ a continuación).

Usar complementos para añadir texto extra a las traducciones

Añadir texto nuevo a la traducción es probablemente lo único que es más fácil a largo plazo cuando traduces archivos manualmente :). Esto ocurre cuando quieres añadir una sección extra al documento traducido, que no corresponde a ningún contenido del documento original. El caso de uso clásico es dar crédito al equipo de traducción e indicar cómo reportar problemas específicos de la traducción.

Con po4a, tienes que especificar archivos addendum, que conceptualmente se pueden ver como parches aplicados al documento localizado después del procesamiento. Cada complemento debe proporcionarse como un archivo separado, cuyo formato es, sin embargo, muy diferente de los parches clásicos. La primera línea es una línea de encabezado, que define el punto de inserción del complemento (con una sintaxis desafortunadamente críptica -- ver abajo), mientras que el resto del archivo se añade literalmente en la posición determinada.

La línea de encabezado debe comenzar con la cadena PO4A-HEADER:, seguida de una lista de campos clave=valor separados por punto y coma.

Por ejemplo, el siguiente encabezado declara un complemento que debe colocarse al final de la traducción.

PO4A-HEADER: mode=eof

Las cosas son más complejas cuando quieres añadir tu contenido extra en medio del documento. El siguiente encabezado declara un complemento que debe colocarse después de la sección XML que contiene la cadena "About this document" en la traducción.

PO4A-HEADER: position=About this document; mode=after; endboundary=</section>

En la práctica, al intentar aplicar un complemento, po4a busca la primera línea que coincida con el argumento "position" (puede ser una expresión regular). No olvides que po4a considera aquí el documento traducido. Esta documentación está en inglés, pero tu línea probablemente debería leerse así si pretendes que tu complemento se aplique a la traducción francesa del documento.

PO4A-HEADER: position=À propos de ce document; mode=after; endboundary=</section>

Una vez que se encuentra la "position" en el documento de destino, po4a busca la siguiente línea después de la "position" que coincida con el "endboundary" proporcionado. El complemento se añade justo después de esa línea (porque proporcionamos un endboundary, es decir, un límite que termina la sección actual).

El mismo efecto exacto podría obtenerse con el siguiente encabezado, que es equivalente:

PO4A-HEADER: position=About this document; mode=after; beginboundary=<section>

Aquí, po4a busca la primera línea que coincide con "<section>" después de la línea que coincide con "About this document" en la traducción, y añade el complemento antes de esa línea ya que proporcionamos un beginboundary, es decir, un límite que marca el comienzo de la siguiente sección. Así, este encabezado requiere colocar el complemento después de la sección que contiene "About this document", e instruye a po4a que una sección comienza con una línea que contiene la etiqueta "<section>". Esto es equivalente al ejemplo anterior porque lo que realmente quieres es añadir este complemento ya sea después de "</section>" o antes de "<section>".

También puedes establecer el modo de inserción al valor "before", con una semántica similar: combinar "mode=before" con un "endboundary" colocará el complemento justo después del límite que coincide, que es la última línea límite potencial antes de la "position". Combinar "mode=before" con un "beginboundary" colocará el complemento justo antes del límite que coincide, que es la última línea límite potencial antes de la "position".

 Modo   | Tipo de límite | Límite usado           | Punto de inserción comparado con el límite
========|================|========================|=========================================
'before'| 'endboundary'  | último antes de 'pos' | Justo después del límite seleccionado
'before'|'beginboundary' | último antes de 'pos' | Justo antes del límite seleccionado
'after' | 'endboundary'  | primero después de 'pos'| Justo después del límite seleccionado
'after' |'beginboundary' | primero después de 'pos'| Justo antes del límite seleccionado
'eof'   |   (ninguno)    |  n/a                   | Fin del archivo

Pistas y trucos sobre complementos

  • Recuerda que son expresiones regulares. Por ejemplo, si quieres hacer coincidir el final de una sección nroff que termina con la línea ".fi", no uses ".fi" como endboundary, porque coincidirá con "the[ fi]le", lo cual obviamente no es lo que esperas. El endboundary correcto en ese caso es: "^\.fi$".
  • Los espacios en blanco SÍ son importantes en el contenido de la "position" y los límites. Así que las dos siguientes líneas son diferentes. La segunda solo se encontrará si hay suficientes espacios al final en el documento traducido. 
    PO4A-HEADER: position=About this document; mode=after; beginboundary=<section>
PO4A-HEADER: position=About this document ; mode=after; beginboundary=<section>
  • Aunque esta búsqueda de contexto puede considerarse que opera aproximadamente en cada línea del documento traducido, en realidad opera sobre la cadena de datos interna del documento traducido. Esta cadena de datos interna puede ser un texto que abarca un párrafo que contiene múltiples líneas o puede ser una etiqueta XML sola. El punto de inserción exacto del complemento debe estar antes o después de la cadena de datos interna y no puede estar dentro de la cadena de datos interna.
  • Pasa el argumento "-vv" a po4a para entender cómo se añaden los complementos a la traducción. También puede ser útil ejecutar po4a en modo de depuración para ver la cadena de datos interna real cuando tu complemento no se aplica.

Ejemplos de complementos

  • Si quieres añadir algo después de la siguiente sección nroff: 
    .SH "AUTHORS"

    Deberías elegir un enfoque de dos pasos estableciendo mode=after. Luego deberías acotar la búsqueda a la línea después de AUTHORS con el argumento de expresión regular position. Luego, deberías hacer coincidir el comienzo de la siguiente sección (es decir, ^\.SH) con el argumento de expresión regular beginboundary. Es decir:

    PO4A-HEADER:mode=after;position=AUTHORS;beginboundary=\.SH
  • Si quieres añadir algo justo después de una línea dada (por ejemplo, después de la línea "Copyright Big Dude"), usa una position que coincida con esa línea, mode=after y proporciona un beginboundary que coincida con cualquier línea. 
    PO4A-HEADER:mode=after;position=Copyright Big Dude, 2004;beginboundary=^
  • Si quieres añadir algo al final del documento, proporciona una position que coincida con cualquier línea de tu documento (pero solo una línea. Po4a no procederá si no es única), y proporciona un endboundary que no coincida con nada. No uses cadenas simples aquí como "EOF", sino prefiere aquellas que tengan menos probabilidades de estar en tu documento. 
    PO4A-HEADER:mode=after;position=About this document;beginboundary=FakePo4aBoundary

Ejemplo más detallado

Documento original (formato POD):

|=head1 NAME
|
|dummy - a dummy program
|
|=head1 AUTHOR
|
|me

Luego, el siguiente complemento garantizará que una sección (en francés) sobre el traductor se añada al final del archivo (en francés, "TRADUCTEUR" significa "TRANSLATOR", y "moi" significa "me").

|PO4A-HEADER:mode=after;position=AUTEUR;beginboundary=^=head
|
|=head1 TRADUCTEUR
|
|moi
|

Para colocar tu complemento antes del AUTOR, usa el siguiente encabezado:

PO4A-HEADER:mode=after;position=NOM;beginboundary=^=head1

Esto funciona porque la siguiente línea que coincide con el beginboundary "/^=head1/" después de la sección "NAME" (traducida a "NOM" en francés), es la que declara a los autores. Por lo tanto, el complemento se colocará entre ambas secciones. Ten en cuenta que si se añade otra sección entre las secciones NAME y AUTHOR más tarde, po4a colocará erróneamente el complemento antes de la nueva sección.

Para evitar esto, puedes lograr lo mismo usando mode=before:

PO4A-HEADER:mode=before;position=^=head1 AUTEUR

¿Cómo funciona?

NAME

po4a — PO4A documentación flujo de trabajo

Introduction

po4a (PO for anything) is a set of scripts that converts various document formats into a format that can be translated using the gettext tools, and back again.

The main idea is to abstract the translation process from the document format. This means that translators don't need to know about the document format, and don't need to have specific tools to handle it. They just need a PO file editor, and a translator's memory (or equivalent) if they wish to use one.

This manual page explains the po4a workflow, its advantages over other methods, and lists projects that use it.

Why po4a?

Traditionally, translating documentation has been done by copying the original document, translating it, and then re-integrating it. This has several drawbacks:

  • Translators need to know the source format and its tools.
  • It is difficult to automate the process.
  • It is difficult to detect if translations become out of date.
  • It is difficult to manage multiple translations for the same document.

Another approach is to use XML as an intermediate format. This can work, but it has its own set of drawbacks:

  • The XML format can be complex and difficult to manage.
  • Translators might still need to know about the XML format.
  • It is difficult to extract only the translatable strings.

The po4a approach uses the gettext tools, which are widely used for software translation. This approach has several advantages:

  • Translators only need to know about PO files and standard PO file editors.
  • The translation process can be easily automated.
  • It is easy to detect if translations become out of date.
  • It is easy to manage multiple translations.
  • The original document is not modified.

Using po4a

The basic workflow for using po4a is as follows:

  1. Run po4a-gettextize on the source document to extract the translatable strings into a PO file.

  2. Translate the PO file using a standard PO file editor (e.g., poedit, gtranslator, lokalize).

  3. Run po4a-translate on the translated PO file to generate the translated document.

For updating existing translations when the source document has changed, use po4a-updatepo to update the PO file with the new strings, and then re-translate using po4a-translate.

How does it work?

Each supported document format has a corresponding parser that extracts translatable strings and generates a PO file. The translator then edits the PO file. Finally, a writer module takes the translated PO file and the original document, and generates the translated document.

The different parsers and writers are implemented as Perl modules under the Locale::Po4a namespace.

Open-source projects using po4a

Many open-source projects use po4a for their documentation translation, including:

  • Debian documentation
  • KDE documentation
  • GNOME documentation
  • The Perl documentation (pod2text, pod2html, etc.)
  • Python documentation
  • The Wine documentation
  • ...and many more.

FAQ

Q: How does po4a compare to other translation tools?

Several other projects use their own translation workflows. For example:

LaTeX
LaTeX documents can be translated by simply translating the text content. However, this requires translators to be familiar with LaTeX commands and the overall document structure. It is also difficult to automate and detect outdated translations.
DocBook
DocBook is an XML-based format that is well-suited for documentation. Translation tools exist for DocBook, but they often require specific configurations and may not be as widely adopted as gettext tools.
Sphinx
The Sphinx Documentation Project also uses gettext extensively to manage its translations. Unfortunately, it works only for a few text formats, reStructuredText and Markdown, although it is perhaps the only tool that does this managing the whole translation process.

The main advantages of po4a over them are the ease of extra content addition (which is even worse there) and the ability to achieve gettextization.

SUMMARY of the advantages of the gettext based approach

  • The translations are not stored along with the original, which makes it possible to detect if translations become out of date.
  • The translations are stored in separate files from each other, which prevents translators of different languages from interfering, both when submitting their patch and at the file encoding level.
  • It is based internally on gettext (but po4a offers a very simple interface so that you don't need to understand the internals to use it). That way, we don't have to re-invent the wheel, and because of their wide use, we can think that these tools are more or less bug-free.
  • Nothing changed for the end-user (besides the fact that translations will hopefully be better maintained). The resulting documentation file distributed is exactly the same.
  • No need for translators to learn a new file syntax and their favorite PO file editor (like Emacs' PO mode, Lokalize or Gtranslator) will work just fine.
  • gettext offers a simple way to get statistics about what is done, what should be reviewed and updated, and what is still to do. Some examples can be found at those addresses: 
    - https://docs.kde.org/stable5/en/kdesdk/lokalize/project-view.html
- http://www.debian.org/intl/l10n/

But everything isn't perfect, and this approach also has some disadvantages we have to deal with.

  • Addenda are somewhat strange at the first glance.
  • You can't adapt the translated text to your preferences, like splitting a paragraph here, and joining two other ones there. But in some sense, if there is an issue with the original, it should be reported as a bug anyway.
  • Even with an easy interface, it remains a new tool people have to learn.

    One of my dreams would be to integrate somehow po4a to Gtranslator or Lokalize. When a documentation file is opened, the strings are automatically extracted, and a translated file + po file can be written to disk. If we manage to do an MS Word (TM) module (or at least RTF) professional translators may even use it.
