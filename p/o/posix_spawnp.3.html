NOMBRE

posix_spawn, posix_spawnp - crear un proceso

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <spawn.h>
int posix_spawn(pid_t *restrict pid, const char *restrict path,
                const posix_spawn_file_actions_t *restrict file_actions,
                const posix_spawnattr_t *restrict attrp,
                char *const argv[restrict],
                char *const envp[restrict]);
int posix_spawnp(pid_t *restrict pid, const char *restrict file,
                const posix_spawn_file_actions_t *restrict file_actions,
                const posix_spawnattr_t *restrict attrp,
                char *const argv[restrict],
                char *const envp[restrict]);

DESCRIPCIÓN

Las funciones posix_spawn() y posix_spawnp() se utilizan para crear un nuevo proceso hijo que ejecute un archivo especificado. Estas funciones fueron especificadas por POSIX para proporcionar un método estandarizado de creación de nuevos procesos en máquinas que carecen de la capacidad de soportar la llamada al sistema fork(2). Estas máquinas son generalmente sistemas pequeños y embebidos que carecen de soporte de MMU.

Las funciones posix_spawn() y posix_spawnp() proporcionan la funcionalidad de una combinación de fork(2) y exec(3), con algunos pasos opcionales de mantenimiento en el proceso hijo antes del exec(3). Estas funciones no pretenden reemplazar a las llamadas al sistema fork(2) y execve(2). De hecho, solo proporcionan un subconjunto de la funcionalidad que se puede lograr utilizando las llamadas al sistema.

La única diferencia entre posix_spawn() y posix_spawnp() es la forma en que especifican el archivo a ser ejecutado por el proceso hijo. Con posix_spawn(), el archivo ejecutable se especifica como una ruta (que puede ser absoluta o relativa). Con posix_spawnp(), el archivo ejecutable se especifica como un nombre de archivo simple; el sistema busca este archivo en la lista de directorios especificada por PATH (de la misma manera que para execvp(3)). Para el resto de esta página, la discusión se formula en términos de posix_spawn(), entendiendo que posix_spawnp() difiere solo en el punto recién descrito.

Los argumentos restantes para estas dos funciones son los siguientes:

pid
apunta a un búfer que se utiliza para devolver el ID de proceso del nuevo proceso hijo.
file_actions
apunta a un objeto de acciones de archivo de spawn que especifica acciones relacionadas con archivos que se realizarán en el hijo entre los pasos de fork(2) y exec(3). Este objeto se inicializa y se rellena antes de la llamada a posix_spawn() utilizando posix_spawn_file_actions_init(3) y las funciones posix_spawn_file_actions_*().
attrp
apunta a un objeto de atributos que especifica varios atributos del proceso hijo creado. Este objeto se inicializa y se rellena antes de la llamada a posix_spawn() utilizando posix_spawnattr_init(3) y las funciones posix_spawnattr_*().
argv
envp
especifican la lista de argumentos y el entorno para el programa que se ejecuta en el proceso hijo, como para execve(2).

A continuación, las funciones se describen en términos de un proceso de tres pasos: el paso fork(), el paso pre-exec() (ejecutado en el hijo) y el paso exec() (ejecutado en el hijo).

paso fork()

Desde glibc 2.24, la función posix_spawn() comienza llamando a clone(2) con las banderas CLONE_VM y CLONE_VFORK. Implementaciones anteriores utilizan fork(2), o posiblemente vfork(2) (ver más abajo).

El PID del nuevo proceso hijo se coloca en *pid. La función posix_spawn() luego devuelve el control al proceso padre.

Posteriormente, el padre puede usar una de las llamadas al sistema descritas en wait(2) para verificar el estado del proceso hijo. Si el hijo falla en alguno de los pasos de mantenimiento descritos a continuación, o falla al ejecutar el archivo deseado, sale con un estado de 127.

Antes de glibc 2.24, el proceso hijo se crea utilizando vfork(2) en lugar de fork(2) cuando se cumple alguna de las siguientes condiciones:

•
el elemento spawn-flags del objeto de atributos apuntado por attrp contiene la bandera específica de GNU POSIX_SPAWN_USEVFORK; o
•
file_actions es NULL y el elemento spawn-flags del objeto de atributos apuntado por attrp *no* contiene POSIX_SPAWN_SETSIGMASK, POSIX_SPAWN_SETSIGDEF, POSIX_SPAWN_SETSCHEDPARAM, POSIX_SPAWN_SETSCHEDULER, POSIX_SPAWN_SETPGROUP, o POSIX_SPAWN_RESETIDS.

En otras palabras, se utiliza vfork(2) si el llamador lo solicita, o si no hay limpieza esperada en el hijo antes de que exec(3) el archivo solicitado.

paso pre-exec(): mantenimiento

Entre los pasos de fork() y exec(), un proceso hijo puede necesitar realizar un conjunto de acciones de mantenimiento. Las funciones posix_spawn() y posix_spawnp() soportan un conjunto pequeño y bien definido de tareas del sistema que el proceso hijo puede realizar antes de ejecutar el archivo ejecutable. Estas operaciones se controlan mediante el objeto de atributos apuntado por attrp y el objeto de acciones de archivo apuntado por file_actions. En el hijo, el procesamiento se realiza en la siguiente secuencia:

(1)
Se procesan las acciones de atributos del proceso: la máscara de señales, los manejadores por defecto de señales, el algoritmo y los parámetros de planificación, el grupo de procesos y los ID efectivos de usuario y grupo se cambian según lo especificado por el objeto de atributos apuntado por attrp.
(2)
Las acciones de archivo, tal como se especifican en el argumento file_actions, se realizan en el orden en que se especificaron mediante llamadas a las funciones posix_spawn_file_actions_add*().
(3)
Se cierran los descriptores de archivo con la bandera FD_CLOEXEC establecida.

Todos los atributos del proceso en el hijo, aparte de aquellos afectados por los atributos especificados en el objeto apuntado por attrp y las acciones de archivo en el objeto apuntado por file_actions, se verán afectados como si el hijo hubiera sido creado con fork(2) y hubiera ejecutado el programa con execve(2).

Las acciones de atributos del proceso se definen mediante el objeto de atributos apuntado por attrp. La bandera spawn-flags (establecida con posix_spawnattr_setflags(3)) controla las acciones generales que ocurren, y otros atributos en el objeto especifican los valores a usar durante esas acciones.

Los efectos de las banderas que pueden especificarse en spawn-flags son los siguientes:

NAME

posix_spawn, posix_spawnp - create a new process

SYNOPSIS

#include <spawn.h>

int posix_spawn(pid_t *restrict pid, const char *restrict file,
               const posix_spawn_file_actions_t *file_actions,
               const posix_spawnattr_t *restrict attrp,
               char *const argv[restrict],
               char *const envp[restrict]);
int posix_spawnp(pid_t *restrict pid, const char *restrict file,
                const posix_spawn_file_actions_t *file_actions,
                const posix_spawnattr_t *restrict attrp,
                char *const argv[restrict],
                char *const envp[restrict]);

DESCRIPTION

The posix_spawn() function creates a new process (child process). The new process is created by calling a function equivalent to fork(2). After the child process is created, and prior to executing the new program image, a set of actions can be performed in the child process. These actions are specified by the file_actions and attrp arguments.

The file, argv, and envp arguments are used to specify the program to be executed by the child process. file is the path to the executable file. argv is a pointer to a null-terminated array of character pointers, the first of which is conventionally the name of the program being executed. envp is a pointer to a null-terminated array of character pointers, each of which is a string of the form "name=value".

The posix_spawnp() function is similar to posix_spawn(), except that if file contains a slash character (‘/’), then it is assumed to be a path. Otherwise, file is treated as a simple filename and is searched for in the directories specified by the caller's PATH environment variable (see execve(2)).

The behavior of posix_spawn() and posix_spawnp() is determined by the flags in the spawn-flags attribute of the object pointed to by attrp, and by the contents of the objects pointed to by file_actions and attrp.

spawn-flags

If attrp is NULL, then spawn-flags is taken to be 0. The flags are bits that can be set in the spawn-flags attribute of the posix_spawnattr_t object pointed to by attrp. The following flags are defined:

POSIX_SPAWN_SETSIGMASK
If this flag is set, the set of signals blocked in the child process is set to the signal mask specified in the spawn-sigmask attribute of the object pointed to by attrp. If this flag is not set, the child inherits the signal mask of the parent.
POSIX_SPAWN_SETSIGDEF
If this flag is set, the signal dispositions of signals that are not blocked in the child process are set to the disposition specified in the spawn-sigdefault attribute of the object pointed to by attrp. If this flag is not set, the signal dispositions of signals not blocked in the child are inherited from the parent. The default disposition for signals not specified in the spawn-sigdefault attribute, or the treatment when POSIX_SPAWN_SETSIGDEF is not specified, see execve(2).
POSIX_SPAWN_SETSCHEDPARAM
If this flag is set, and the POSIX_SPAWN_SETSCHEDULER flag is not set, then set the scheduling parameters to the parameters specified in the spawn-schedparam attribute of the object pointed to by attrp.
POSIX_SPAWN_SETSCHEDULER
Set the scheduling policy algorithm and parameters of the child, as follows:
•
The scheduling policy is set to the value specified in the spawn-schedpolicy attribute of the object pointed to by attrp.
•
The scheduling parameters are set to the value specified in the spawn-schedparam attribute of the object pointed to by attrp (but see BUGS).

If the POSIX_SPAWN_SETSCHEDPARAM and POSIX_SPAWN_SETSCHEDPOLICY flags are not specified, the child inherits the corresponding scheduling attributes from the parent.

POSIX_SPAWN_RESETIDS
If this flag is set, reset the effective UID and GID to the real UID and GID of the parent process. If this flag is not set, then the child retains the effective UID and GID of the parent. In either case, if the set-user-ID and set-group-ID permission bits are enabled on the executable file, their effect will override the setting of the effective UID and GID (se execve(2)).
POSIX_SPAWN_SETPGROUP
Set the process group to the value specified in the spawn-pgroup attribute of the object pointed to by attrp. If the spawn-pgroup attribute has the value 0, the child's process group ID is made the same as its process ID. If the POSIX_SPAWN_SETPGROUP flag is not set, the child inherits the parent's process group ID.
POSIX_SPAWN_USEVFORK
Since glibc 2.24, this flag has no effect. On older implementations, setting this flag forces the fork() step to use vfork(2) instead of fork(2). The _GNU_SOURCE feature test macro must be defined to obtain the definition of this constant.
POSIX_SPAWN_SETSID (since glibc 2.26)
If this flag is set, the child process shall create a new session and become the session leader. The child process shall also become the process group leader of the new process group in the session (see setsid(2)). The _GNU_SOURCE feature test macro must be defined to obtain the definition of this constant.

If attrp is NULL, then the default behaviors described above for each flag apply.

The file_actions argument specifies a sequence of file operations that are performed in the child process after the general processing described above, and before it performs the exec(3). If file_actions is NULL, then no special action is taken, and standard exec(3) semantics apply—file descriptors open before the exec remain open in the new process, except those for which the FD_CLOEXEC flag has been set. File locks remain in place.

If file_actions is not NULL, then it contains an ordered set of requests to open(2), close(2), and dup2(2) files. These requests are added to the file_actions by posix_spawn_file_actions_addopen(3), posix_spawn_file_actions_addclose(3), and posix_spawn_file_actions_adddup2(3). The requested operations are performed in the order they were added to file_actions.

If any of the housekeeping actions fails (due to bogus values being passed or other reasons why signal handling, process scheduling, process group ID functions, and file descriptor operations might fail), the child process exits with exit value 127.

exec() step

Once the child has successfully forked and performed all requested pre-exec steps, the child runs the requested executable.

The child process takes its environment from the envp argument, which is interpreted as if it had been passed to execve(2). The arguments to the created process come from the argv argument, which is processed as for execve(2).

RETURN VALUE

Upon successful completion, posix_spawn() and posix_spawnp() place the PID of the child process in pid, and return 0. If there is an error during the fork() step, then no child is created, the contents of *pid are unspecified, and these functions return an error number as described below.

Even when these functions return a success status, the child process may still fail for a plethora of reasons related to its pre-exec() initialization. In addition, the exec(3) may fail. In all of these cases, the child process will exit with the exit value of 127.

ERRORS

The posix_spawn() and posix_spawnp() functions fail only in the case where the underlying fork(2), vfork(2), or clone(2) call fails; in these cases, these functions return an error number, which will be one of the errors described for fork(2), vfork(2), or clone(2).

In addition, these functions fail if:

ENOSYS
Function not supported on this system.

STANDARDS

POSIX.1-2008.

HISTORY

glibc 2.2. POSIX.1-2001.

NOTES

The housekeeping activities in the child are controlled by the objects pointed to by attrp (for non-file actions) and file_actions In POSIX parlance, the posix_spawnattr_t and posix_spawn_file_actions_t data types are referred to as objects, and their elements are not specified by name. Portable programs should initialize these objects using only the POSIX-specified functions. (In other words, although these objects may be implemented as structures containing fields, portable programs must avoid dependence on such implementation details.)

According to POSIX, it is unspecified whether fork handlers established with pthread_atfork(3) are called when posix_spawn() is invoked. Since glibc 2.24, the fork handlers are not executed in any case. On older implementations, fork handlers are called only if the child is created using fork(2).

There is no "posix_fspawn" function (i.e., a function that is to posix_spawn() as fexecve(3) is to execve(2)). However, this functionality can be obtained by specifying the path argument as one of the files in the caller's /proc/self/fd directory.

BUGS

POSIX.1 says that when POSIX_SPAWN_SETSCHEDULER is specified in spawn-flags, then the POSIX_SPAWN_SETSCHEDPARAM (if present) is ignored. However, before glibc 2.14, calls to posix_spawn() failed with an error if POSIX_SPAWN_SETSCHEDULER was specified without also specifying POSIX_SPAWN_SETSCHEDPARAM.

EXAMPLES

The program below demonstrates the use of various functions in the POSIX spawn API. The program accepts command-line attributes that can be used to create file actions and attributes objects. The remaining command-line arguments are used as the executable name and command-line arguments of the program that is executed in the child.

In the first run, the date(1) command is executed in the child, and the posix_spawn() call employs no file actions or attributes objects.


$ ./a.out date;
PID of child: 7634
Tue Feb  1 19:47:50 CEST 2011
Child status: exited, status=0

In the next run, the -c command-line option is used to create a file actions object that closes standard output in the child. Consequently, date(1) fails when trying to perform output and exits with a status of 1.


$ ./a.out -c date;
PID of child: 7636
date: write error: Bad file descriptor
Child status: exited, status=1

In the next run, the -s command-line option is used to create an attributes object that specifies that all (blockable) signals in the child should be blocked. Consequently, trying to kill child with the default signal sent by kill(1) (i.e., SIGTERM) fails, because that signal is blocked. Therefore, to kill the child, SIGKILL is necessary (SIGKILL can't be blocked).


$ ./a.out -s sleep 60 &
[1] 7637
$ PID of child: 7638
$ kill 7638;
$ kill -KILL 7638;
$ Child status: killed by signal 9
[1]+  Done                    ./a.out -s sleep 60

When we try to execute a nonexistent command in the child, the exec(3) fails and the child exits with a status of 127.


$ ./a.out xxxxx;
PID of child: 10190
Child status: exited, status=127

NAME

posix_spawnp - spawn a process

LIBRARY

Realtime library (libc, -lrt)

SYNOPSIS

#include <spawn.h>
int posix_spawnp(pid_t *restrict pid, const char *restrict file,
             const posix_spawn_file_actions_t *file_actions,
             const posix_spawnattr_t *restrict attrp,
             char *const argv[restrict], char *const envp[restrict]);

DESCRIPTION

The posix_spawnp() function creates a new process by calling the specified file in the current process image. The new process image is constructed using a call to execve() with the file argument and the argv and envp arguments. The file argument is a string containing a pathname that is used to search for the new process image file if it does not contain a slash character (see execvp(3)).

The posix_spawnp() function is the POSIX.1 standard function for spawning a new process. It is designed to be more flexible than fork() followed by execve(). The posix_spawnp() function is equivalent to calling posix_spawn() with the file argument being searched for in the PATH environment variable.

The posix_spawnp() function is intended to be thread-safe. It is also intended to be used with non-local gotos or longjmps.

The posix_spawnp() function differs from posix_spawn() in that the file argument is searched for in the PATH environment variable if it does not contain a slash character. If file contains a slash character, it is used as the pathname directly.

The posix_spawnp() function takes the following arguments:

pid
A pointer to a pid_t object. If not NULL, this object is set to the process ID of the child process.
file
The name of the file to be executed. This file is searched for in the PATH environment variable if it does not contain a slash character.
file_actions
A pointer to a posix_spawn_file_actions_t object. If this is NULL, the child inherits the file descriptors of the parent. Otherwise, it specifies a set of file descriptor actions to be performed in the child process before the new program is executed. These actions include closing file descriptors, duplicating file descriptors, and opening new file descriptors. See posix_spawn_file_actions_init(3). The object specified by file_actions is not destroyed by the call.
attrp
A pointer to a posix_spawnattr_t object. If this is NULL, the child inherits the attributes of the parent. Otherwise, it specifies a set of attributes for the child process. These attributes include the process group, scheduling policy and priority, signal mask, and signal default actions. See posix_spawnattr_init(3). The object specified by attrp is not destroyed by the call.
argv
A pointer to an array of character pointers, the first element of which is the name of the command to be executed, and the remaining elements are a null-terminated list of arguments to that command. This array is passed to the child process as its argument list.
envp
A pointer to an array of character pointers, each an environment variable assignment string in the format "name=value". This array is passed to the child process as its environment. If envp is NULL, the child inherits the environment of the parent process.

The argument array argv must be terminated by a NULL pointer. The environment array envp must also be terminated by a NULL pointer.

The posix_spawnp() function is essentially a wrapper around the posix_spawn() function. The only difference is that if the file argument does not contain a slash, posix_spawnp() will search the PATH environment variable to locate the executable file, similar to how execvp() works.

The posix_spawnp() function allows for more fine-grained control over the child process creation than the standard fork() and execve() combination. It can be used to control file descriptor inheritance, signal handling, process group, and scheduling attributes of the child process.

RETURN VALUE

On success, posix_spawnp() returns 0. On failure, it returns an error number.

ERRORS

The posix_spawnp() function may fail for any of the reasons that posix_spawn() or posix_spawnve() may fail. In addition, if the file argument does not contain a slash, and the file is not found in the PATH, then posix_spawnp() will fail with ENOENT.

The following errors are specific to posix_spawnp():

EACCES
Search permission is denied for any component of the file pathname, or the requested access permissions are denied for the file. Or, the requested access permissions are denied for the file.
ENOENT
A component of the file pathname does not exist, or file is an empty string, or file does not contain a slash and no executable is found in PATH.

STANDARDS

POSIX.1-2001, POSIX.1-2008.

HISTORY

The posix_spawnp() function first appeared in POSIX.1-2001.

NOTES

The environ variable is a global variable that points to the environment of the calling process. It is used as the default environment for the child process if envp is NULL.

The posix_spawnp() function provides a mechanism for creating new processes that is more efficient than fork() followed by execve() in some scenarios, particularly when the child process needs to inherit specific file descriptors or signal masks from the parent.

The posix_spawnp() function is particularly useful in multithreaded applications where fork() can lead to issues with mutexes and other synchronization primitives. posix_spawn() (and by extension, posix_spawnp()) is designed to be safe to call from within any thread, including those holding locks.

The posix_spawnp() function is not a replacement for fork() in all cases. For example, if the parent process needs to continue executing concurrently with the child, then fork() is still the appropriate choice.

The posix_spawnp() function does not automatically close file descriptors in the child process. If you want to close file descriptors, you must use the file_actions argument and posix_spawn_file_actions_addclose().

The posix_spawnp() function does not automatically set the signal mask for the child process. If you want to set the signal mask, you must use the attrp argument and posix_spawnattr_setsigmask().

BUGS

The posix_spawnp() function is a complex API, and its behavior can be subtle. It is important to consult the POSIX standard and the documentation for your specific system to understand the full implications of its use.

Some implementations may not fully support all features of posix_spawnp().

EXAMPLES

The following example demonstrates how to use posix_spawnp() to spawn a child process that closes its standard output and blocks all signals.

#include <err.h>
#include <errno.h>
#include <spawn.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <wait.h>
char **environ;
int
main(int argc, char *argv[])
{
    pid_t child_pid;
    int s, opt, status;
    sigset_t mask;
    posix_spawnattr_t attr;
    posix_spawnattr_t *attrp;
    posix_spawn_file_actions_t file_actions;
    posix_spawn_file_actions_t *file_actionsp;
    /* Parse command-line options, which can be used to specify an
       attributes object and file actions object for the child.  */
    attrp = NULL;
    file_actionsp = NULL;
    while ((opt = getopt(argc, argv, "sc")) != -1) {
        switch (opt) {
        case 'c':       /* -c: close standard output in child */
            /* Create a file actions object and add a "close"
               action to it.  */
            s = posix_spawn_file_actions_init(&file_actions);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawn_file_actions_init");
            s = posix_spawn_file_actions_addclose(&file_actions,
                                                  STDOUT_FILENO);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawn_file_actions_addclose");
            file_actionsp = &file_actions;
            break;
        case 's':       /* -s: block all signals in child */
            /* Create an attributes object and add a "set signal mask"
               action to it.  */
            s = posix_spawnattr_init(&attr);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawnattr_init");
            s = posix_spawnattr_setflags(&attr, POSIX_SPAWN_SETSIGMASK);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawnattr_setflags");
            sigfillset(&mask);
            s = posix_spawnattr_setsigmask(&attr, &mask);
            if (s != 0)
                errc(EXIT_FAILURE, s, "posix_spawnattr_setsigmask");
            attrp = &attr;
            break;
        }
    }
    if (argv[optind] == NULL) {
        fprintf(stderr, "Usage: %s [-cs] executable [args]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    /* Spawn the child.  The name of the program to execute and the
       command-line arguments are taken from the command-line arguments
       of this program.  The environment of the program execed in the
       child is made the same as the parent's environment.  */
    s = posix_spawnp(&child_pid, argv[optind], file_actionsp, attrp,
                     &argv[optind], environ);
    if (s != 0)
        errc(EXIT_FAILURE, s, "posix_spawn");
    /* Destroy any objects that we created earlier.  */
    if (attrp != NULL) {
        s = posix_spawnattr_destroy(attrp);
        if (s != 0)
            errc(EXIT_FAILURE, s, "posix_spawnattr_destroy");
    }
    if (file_actionsp != NULL) {
        s = posix_spawn_file_actions_destroy(file_actionsp);
        if (s != 0)
            errc(EXIT_FAILURE, s, "posix_spawn_file_actions_destroy");
    }
    printf("PID of child: %jd\n", (intmax_t) child_pid);
    /* Monitor status of the child until it terminates.  */
    do {
        s = waitpid(child_pid, &status, WUNTRACED | WCONTINUED);
        if (s == -1)
            err(EXIT_FAILURE, "waitpid");
        printf("Child status: ");
        if (WIFEXITED(status)) {
            printf("exited, status=%d\n", WEXITSTATUS(status));
        } else if (WIFSIGNALED(status)) {
            printf("killed by signal %d\n", WTERMSIG(status));
        } else if (WIFSTOPPED(status)) {
            printf("stopped by signal %d\n", WSTOPSIG(status));
        } else if (WIFCONTINUED(status)) {
            printf("continued\n");
        }
    } while (!WIFEXITED(status) && !WIFSIGNALED(status));
    exit(EXIT_SUCCESS);
}
