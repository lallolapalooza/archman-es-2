NOMBRE

podman-run - Ejecuta un comando en un nuevo contenedor

SINOPSIS

podman run [opciones] imagen [comando [arg ...]]

podman container run [opciones] imagen [comando [arg ...]]

DESCRIPCIÓN

Ejecuta un proceso en un nuevo contenedor. podman run inicia un proceso con su propio sistema de archivos, su propia red y su propio árbol de procesos aislado. La imagen que inicia el proceso puede definir valores predeterminados relacionados con el proceso que se ejecutará en el contenedor, la red que se expondrá y más, pero podman run otorga el control final al operador o administrador que inicia el contenedor a partir de la imagen. Por esa razón, podman run tiene más opciones que cualquier otro comando de Podman.

Si la imagen aún no está cargada, podman run descargará la imagen y todas sus dependencias de forma similar a como se ejecuta podman pull imagen, antes de iniciar el contenedor a partir de esa imagen.

Se crearán automáticamente varios archivos dentro del contenedor. Estos incluyen /etc/hosts, /etc/hostname y /etc/resolv.conf para gestionar la red. Estos se basarán en la versión del host de los archivos, aunque se pueden personalizar con opciones (por ejemplo, --dns puede anular los servidores DNS del host en el resolv.conf creado). Además, se crea un archivo de entorno del contenedor en cada contenedor para indicar a los programas que se están ejecutando en un contenedor. Este archivo se encuentra en /run/.containerenv (o /var/run/.containerenv para contenedores FreeBSD). Cuando se utiliza la bandera --privileged, el .containerenv contiene pares nombre/valor que indican la versión del motor del contenedor, si el motor se está ejecutando en modo sin privilegios (rootless), el nombre y el ID del contenedor, así como el nombre y el ID de la imagen en la que se basa el contenedor. Nota: /run/.containerenv no se creará cuando se monte un volumen en /run.

Cuando se ejecuta desde un espacio de nombres de red definido por el usuario, se utilizará /etc/netns/NSNAME/resolv.conf si existe, de lo contrario se utilizará /etc/resolv.conf.

La configuración predeterminada se define en containers.conf. La mayoría de la configuración para conexiones remotas utiliza los servidores de containers.conf, excepto cuando se documenta en las páginas del manual.

IMAGEN

La imagen se especifica utilizando el formato transport:ruta. Si no se especifica ningún transporte, el transporte docker (registro de contenedores) se usa por defecto. Para Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), docker es el único transporte permitido.

dir:ruta
Un directorio local existente ruta que almacena el manifiesto, los archivos tar de capas y las firmas como archivos individuales. Este es un formato no estandarizado, útil principalmente para depuración o inspección no invasiva del contenedor.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman run dir:/tmp/fedora echo hello

docker://referencia-docker (Por defecto)
Una referencia de imagen almacenada en un registro de imágenes de contenedores remoto. Ejemplo: "quay.io/podman/stable:latest". La referencia puede incluir una ruta a un registro específico; si no lo hace, se consultan los registros listados en registries.conf para encontrar una imagen coincidente. Por defecto, se utilizan las credenciales de podman login (almacenadas por defecto en ${XDG_RUNTIME_DIR}/containers/auth.json); de lo contrario, se recurre a las credenciales en $HOME/.docker/config.json.

$ podman run registry.fedoraproject.org/fedora:latest echo hello

docker-archive:ruta[:referencia-docker] Una imagen almacenada en el archivo con formato docker save. referencia-docker solo se utiliza al crear dicho archivo y no debe contener un digest.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman run docker-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

docker-daemon:referencia-docker
Una imagen en formato referencia-docker almacenada en el almacenamiento interno del demonio docker. La referencia-docker también puede ser un ID de imagen (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman run docker-daemon:docker.io/library/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

oci-archive:ruta:etiqueta
Una imagen en un directorio que cumple con la "Especificación de diseño de imágenes de contenedores abiertos" en la ruta especificada y se especifica con una etiqueta.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman run oci-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

OPCIONES

--add-host=hostname[;hostname[;...]]:ip

Añade un mapeo personalizado de host a IP al archivo /etc/hosts del contenedor.

La opción toma uno o varios nombres de host separados por punto y coma que se mapearán a una única dirección IPv4 o IPv6, separada por dos puntos. También se puede utilizar para anular las direcciones IP de los nombres de host que Podman añade a /etc/hosts por defecto (consulte también las opciones --name y --hostname). Esta opción se puede especificar múltiples veces para añadir mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede dar el indicador especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede utilizar para conectarse al host. La dirección IP elegida depende de su configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que provocará que Podman falle con un mensaje de error. Puede anular esta dirección IP utilizando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para añadir automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitarlo proporcionando la opción --no-hosts o estableciendo host_containers_internal_ip="none" en containers.conf. Si no se configuró ninguna dirección de host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se ejecuta en una máquina virtual utilizando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven mediante el resolvedor DNS de gvproxy en su lugar.

Podman utilizará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente utilizando la configuración base_hosts_file en containers.conf.

--annotation=clave=valor

Añade una anotación al contenedor. Esta opción se puede establecer múltiples veces.

--arch=ARQUITECTURA

Anula la arquitectura, por defecto la del host, de la imagen a descargar. Por ejemplo, arm. A menos que se anule, las búsquedas posteriores de la misma imagen en el almacenamiento local coincidirán con esta arquitectura, independientemente del host.

--cap-add=capacidad

Añadir capacidades de Linux.

Otorgar capacidades adicionales aumenta los privilegios de los procesos que se ejecutan dentro del contenedor y potencialmente le permite escapar de su confinamiento. Capacidades como CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_MKNOD y CAP_SYS_MODULE son particularmente peligrosas cuando no se usan dentro de un espacio de nombres de usuario. Consulte user_namespaces(7) para una explicación más detallada de la interacción entre los espacios de nombres de usuario y las capacidades.

Antes de añadir cualquier capacidad, revise sus implicaciones de seguridad y asegúrese de que es realmente necesaria para la funcionalidad del contenedor. Consulte capabilities(7) para más información.

--cap-drop=capacidad

Eliminar capacidades de Linux.

--cert-dir=ruta

Utilizar certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. (Por defecto: /etc/containers/certs.d) Para más detalles, consulte containers-certs.d(5). (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2))

--cgroup-conf=CLAVE=VALOR

Al ejecutarse en cgroup v2, especifique el archivo cgroup al que escribir y su valor. Por ejemplo, --cgroup-conf=memory.high=1073741824 establece el límite de memoria.high a 1 GB.

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se crea el cgroup para el contenedor. Si la ruta no es absoluta, se considera relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen ya.

--cgroupns=modo

Establecer el modo de espacio de nombres cgroup para el contenedor.

  • host: usar el espacio de nombres cgroup del host dentro del contenedor.
  • container:id: unirse al espacio de nombres del contenedor especificado.
  • private: crear un nuevo espacio de nombres cgroup.
  • ns:ruta: unirse al espacio de nombres en la ruta especificada.

Si el host utiliza cgroups v1, el valor predeterminado se establece en host. En cgroups v2, el valor predeterminado es private.

--cgroups=cómo

Determina si el contenedor crea cgroups.

El valor predeterminado es enabled.

La opción enabled crea un nuevo cgroup bajo el cgroup-parent. La opción disabled fuerza al contenedor a no crear cgroups, y por lo tanto entra en conflicto con las opciones de cgroup ( --cgroupns y --cgroup-parent). La opción no-conmon deshabilita un nuevo cgroup solo para el proceso conmon. La opción split divide el cgroup actual en dos sub-cgroups: uno para conmon y otro para la carga útil del contenedor. No es posible establecer --cgroup-parent con split.

--chrootdirs=ruta

Ruta a un directorio dentro del contenedor que se trata como un directorio chroot. Cualquier archivo administrado por Podman (por ejemplo, /etc/resolv.conf, /etc/hosts, /etc/hostname) que se monte en el directorio raíz también se montará en esa ubicación. Múltiples directorios se separan con una coma.

--cidfile=archivo

Escribir el ID del contenedor en archivo. El archivo se elimina junto con el contenedor, excepto cuando se utiliza con podman --remote run en contenedores desvinculados.

--conmon-pidfile=archivo

Escribir el PID del proceso conmon en un archivo. Como conmon se ejecuta en un proceso separado de Podman, esto es necesario cuando se utiliza systemd para reiniciar contenedores de Podman. (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2))

--cpu-period=límite

Establecer el período de CPU para el Completely Fair Scheduler (CFS), que es una duración en microsegundos. Una vez que se agota la cuota de CPU del contenedor, no se programará para ejecutarse hasta que termine el período actual. El valor predeterminado es 100000 microsegundos.

En algunos sistemas, es posible que no se permita modificar los límites de recursos para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin privilegios V1 de cgroups.

--cpu-quota=límite

Limitar la cuota de CPU del Completely Fair Scheduler (CFS).

Limitar el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso de CPU completo. El límite es un número en microsegundos. Si se proporciona un número, al contenedor se le permite usar esa cantidad de tiempo de CPU hasta que finalice el período de CPU (controlable mediante --cpu-period).

En algunos sistemas, es posible que no se permita modificar los límites de recursos para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin privilegios V1 de cgroups.

--cpu-rt-period=microsegundos

Limitar el período de tiempo real de CPU en microsegundos.

Limitar el uso de CPU de Tiempo Real del contenedor. Esta opción indica al kernel que restrinja el uso de CPU de Tiempo Real del contenedor al período especificado.

Esta opción solo es compatible con sistemas con privilegios V1 de cgroups.

--cpu-rt-runtime=microsegundos

Limitar el tiempo de ejecución de tiempo real de CPU en microsegundos.

Limitar el uso de CPU de Tiempo Real de los contenedores. Esta opción indica al kernel que limite la cantidad de tiempo que las tareas de Tiempo Real pueden consumir en un período de CPU determinado. Por ejemplo: un período de 1,000,000us y un tiempo de ejecución de 950,000us significa que este contenedor puede consumir el 95% de la CPU disponible y dejar el 5% restante para tareas de prioridad normal.

La suma de todos los tiempos de ejecución entre contenedores no puede exceder la cantidad asignada al cgroup padre.

Esta opción solo es compatible con sistemas con privilegios V1 de cgroups.

--cpu-shares, -c=acciones

Acciones de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de las acciones de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso predeterminado es 1024.

La proporción solo se aplica cuando se ejecutan procesos que consumen mucha CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una cpu-share de 1024 y los otros dos tienen un ajuste de cpu-share de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con una cpu-share de 1024, el primer contenedor solo recibe el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las acciones de tiempo de CPU se distribuyen entre todos los núcleos de CPU. Incluso si un contenedor se limita a menos del 100% del tiempo de CPU, puede utilizar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de acciones de CPU:

PID contenedor CPU Acción de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, es posible que no se permita modificar los límites de recursos para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin privilegios V1 de cgroups.

--creds=[nombredeusuario[:contraseña]]

El [nombredeusuario[:contraseña]] a usar para autenticarse con el registro, si es necesario. Si uno o ambos valores no se proporcionan, aparece un aviso en la línea de comandos y se puede introducir el valor. La contraseña se introduce sin eco.

--decryption-key=clave[:contraseña]

La [clave[:contraseña]] que se utilizará para el descifrado de imágenes. La clave puede apuntar a claves y/o certificados. El descifrado se intenta con todas las claves. Si la clave está protegida por una contraseña, se debe pasar en el argumento y omitirse en caso contrario.

--detach, -d

Modo detached: ejecuta el contenedor en segundo plano e imprime el nuevo ID del contenedor. El valor predeterminado es false.

En cualquier momento, ejecuta podman ps en otra terminal para ver una lista de los contenedores en ejecución. Vuelve a adjuntarte a un contenedor detached con el comando podman attach.

Cuando se adjunta a través del modo tty, se separa del contenedor (y lo deja en ejecución) utilizando una secuencia de teclas configurable. La secuencia predeterminada es ctrl-p,ctrl-q. Especifica la secuencia de teclas usando la opción --detach-keys, o configúrala en el archivo containers.conf: véase containers.conf(5) para más información.

--detach-keys=secuencia

Especifica la secuencia de teclas para separar un contenedor. El formato es un único carácter [a-Z] o uno o más caracteres ctrl-<valor> donde <valor> es uno de: a-z, @, ^, [, , o _. Especificar "" deshabilita esta función. El valor predeterminado es ctrl-p,ctrl-q.

Esta opción también se puede configurar en el archivo containers.conf(5).

--device=dispositivo-host[:dispositivo-contenedor][:permisos]

Añade un dispositivo del host al contenedor. El parámetro opcional permisos se puede usar para especificar permisos del dispositivo combinando r para lectura, w para escritura y m para mknod(2).

Ejemplo: --device=/dev/sdc:/dev/xvdc:rwm.

Nota: si dispositivo-host es un enlace simbólico, primero se resuelve. El contenedor solo almacena los números mayor y menor del dispositivo del host.

Podman puede cargar módulos del kernel necesarios para usar el dispositivo especificado. Los dispositivos para los que Podman carga módulos cuando es necesario son: /dev/fuse.

En modo sin root, el nuevo dispositivo se monta enlazado en el contenedor desde el host en lugar de que Podman lo cree dentro del espacio del contenedor. Como el montaje enlazado conserva su etiqueta SELinux en sistemas SELinux, el contenedor puede recibir un error de permiso al acceder al dispositivo montado. Modifica la configuración de SELinux para permitir que los contenedores usen todas las etiquetas de dispositivos con el siguiente comando:

$ sudo setsebool -P container_use_devices=true

Nota: si el usuario solo tiene derechos de acceso a través de un grupo, acceder al dispositivo desde un contenedor sin root falla. Usa la bandera --group-add keep-groups para pasar el acceso a grupos suplementarios del usuario al contenedor.

--device-cgroup-rule="tipo mayor:menor modo"

Añade una regla a la lista de dispositivos permitidos de cgroup. Se espera que la regla tenga el formato especificado en la documentación del kernel de Linux admin-guide/cgroup-v1/devices: - tipo: a (todos), c (carácter), o b (bloque); - mayor y menor: un número, o * para todos; - modo: una composición de r (lectura), w (escritura) y m (mknod(2)).

--disable-content-trust

Esta es una opción específica de Docker para deshabilitar la verificación de imágenes con un registro de contenedores y no es compatible con Podman. Esta opción es una NOOP (no hace nada) y se proporciona únicamente por compatibilidad de scripts.

--dns=ipaddr

Establecer servidores DNS personalizados.

Esta opción se puede usar para sobrescribir la configuración de DNS que se pasa al contenedor. Normalmente es necesario cuando la configuración de DNS del host no es válida para el contenedor (por ejemplo, 127.0.0.1). Cuando esto ocurre, el flag --dns es necesario en cada ejecución.

--health-cmd="comando" | '["comando", arg1 , ...]'

Establece o modifica un comando de verificación de estado para un contenedor. El comando es un comando que se ejecutará dentro del contenedor y determina el estado de salud del contenedor. El comando es necesario para que se apliquen otras opciones de verificación de estado. Un valor de none deshabilita las verificaciones de estado existentes.

Se pueden pasar múltiples opciones en forma de matriz JSON; de lo contrario, el comando se interpreta como un argumento para /bin/sh -c.

Nota: Los valores predeterminados se utilizan incluso si la verificación de estado está configurada en la imagen.

--health-interval=intervalo

Establece un intervalo para las verificaciones de estado. Un intervalo de disable no configura ningún temporizador automático. El valor predeterminado es 30s.

Nota: Este parámetro sobrescribirá la configuración de verificación de estado relacionada de la imagen.

--health-log-destination=ruta_directorio

Establece el destino del registro de HealthCheck. Ruta del directorio, local o events_logger (uso local del archivo de estado del contenedor) (Predeterminado: local)

  • local: (predeterminado) Los registros de HealthCheck se almacenan en contenedores superpuestos. (Por ejemplo: $runroot/healthcheck.log)
  • directory: crea un archivo de registro llamado <ID-contenedor>-healthcheck.log con los registros de HealthCheck en el directorio especificado.
  • events_logger: El registro se escribirá con el mecanismo de registro establecido por events_logger. También guarda el registro en un directorio predeterminado, para el rendimiento en un sistema con un gran número de registros.

--health-max-log-count=número de registros almacenados

Establece el número máximo de intentos en el archivo de registro de HealthCheck. (el valor '0' significa un número infinito de intentos en el archivo de registro) (Predeterminado: 5 intentos)

Establece la longitud máxima en caracteres del registro de HealthCheck almacenado. ("0" significa una longitud de registro infinita) (Predeterminado: 500 caracteres)

--health-on-failure=acción

Acción a tomar una vez que el contenedor transiciona a un estado no saludable. El valor predeterminado es none.

  • none: No tomar ninguna acción.
  • kill: Matar el contenedor.
  • restart: Reiniciar el contenedor. No combine la acción restart con la bandera --restart. Al ejecutarse dentro de una unidad systemd, considere usar la acción kill o stop para aprovechar la política de reinicio de systemd.
  • stop: Detener el contenedor.

--health-retries=intentos

El número de reintentos permitidos antes de que una verificación de estado se considere no saludable. El valor predeterminado es 3.

Nota: Este parámetro puede sobrescribir la configuración de verificación de estado de la imagen.

--health-start-period=período

El tiempo de inicialización necesario para que un contenedor se inicie. El valor se puede expresar en formato de tiempo como 2m3s. El valor predeterminado es 0s.

Nota: El comando de verificación de estado se ejecuta tan pronto como se inicia un contenedor. Si la verificación de estado es exitosa, el estado de salud del contenedor se actualizará a healthy. Sin embargo, si la verificación de estado falla, el estado de salud permanecerá como starting hasta que la verificación de estado sea exitosa o hasta que transcurra el tiempo --health-start-period. Si el comando de verificación de estado falla después de que el tiempo --health-start-period haya expirado, el estado de salud se actualizará a unhealthy. El comando de verificación de estado se ejecuta periódicamente según el valor de --health-interval.

Nota: Este parámetro sobrescribirá la configuración de verificación de estado relacionada de la imagen.

--health-startup-cmd="comando" | '["comando", arg1 , ...]'

Establece un comando de verificación de estado de inicio para un contenedor. Este comando se ejecuta dentro del contenedor y se utiliza para controlar la verificación de estado regular. Cuando el comando de inicio tiene éxito, comienza la verificación de estado regular y la verificación de estado de inicio cesa. Opcionalmente, si el comando falla durante un número determinado de intentos, el contenedor se reinicia. Se puede utilizar una verificación de estado de inicio para garantizar que los contenedores con un período de inicio extendido no se marquen como no saludables hasta que estén completamente iniciados. Las verificaciones de estado de inicio solo se pueden usar cuando también se establece una verificación de estado regular (de la imagen del contenedor o de la opción --health-cmd).

--health-startup-interval=intervalo

Establece un intervalo para la verificación de estado de inicio. Un intervalo de disable no configura ningún temporizador automático. El valor predeterminado es 30s.

--health-startup-retries=reintentos

El número de intentos permitidos antes de que la verificación de estado de inicio reinicie el contenedor. Si se establece en 0, el contenedor nunca se reinicia. El valor predeterminado es 0.

--health-startup-success=reintentos

El número de ejecuciones exitosas requeridas antes de que la verificación de estado de inicio tenga éxito y comience la verificación de estado regular. Un valor de 0 significa que cualquier éxito inicia la verificación de estado regular. El valor predeterminado es 0.

--health-startup-timeout=tiempo_espera

El tiempo máximo que tiene el comando de verificación de estado de inicio para completarse antes de que se marque como fallido. El valor se puede expresar en formato de tiempo como 2m3s. El valor predeterminado es 30s.

--health-timeout=tiempo_espera

El tiempo máximo permitido para completar la verificación de estado antes de que un intervalo se considere fallido. Al igual que start-period, el valor se puede expresar en formato de tiempo como 1m22s. El valor predeterminado es 30s.

Nota: Un tiempo de espera marca la verificación de estado como fallida. Si el comando de verificación de estado se ejecuta durante más tiempo que el tiempo_espera especificado, recibirá una señal SIGKILL.

Nota: Este parámetro sobrescribirá la configuración de verificación de estado relacionada de la imagen.

--pod=nombre

Ejecuta el contenedor en un pod existente. Podman crea el pod automáticamente si el nombre del pod se antepone con new:. Para crear un pod con opciones más granulares, utiliza el comando podman pod create antes de crear un contenedor. Cuando un contenedor se ejecuta con un pod que tiene un contenedor de infraestructura, el contenedor de infraestructura se inicia primero.

--pod-id-file=archivo

Ejecuta el contenedor en un pod existente y lee el ID del pod del archivo especificado. Cuando un contenedor se ejecuta dentro de un pod que tiene un contenedor de infraestructura, el contenedor de infraestructura se inicia primero.

--preserve-fd=FD1[,FD2,...]

Pasa los descriptores de archivo adicionales especificados en la lista separada por comas al proceso. Se puede especificar varias veces. Esta opción solo es compatible con el runtime OCI crun. Puede ser un riesgo de seguridad usar esta opción con otros runtimes OCI.

(Esta opción no está disponible con el cliente remoto de Podman, incluyendo máquinas Mac y Windows (excluyendo WSL2))

--preserve-fds=N

Pasa N descriptores de archivo adicionales al proceso (además de 0, 1, 2). Los FDs totales son 3+N. (Esta opción no está disponible con el cliente remoto de Podman, incluyendo máquinas Mac y Windows (excluyendo WSL2))

--privileged

Otorga privilegios extendidos a este contenedor. El valor por defecto es false.

Por defecto, los contenedores de Podman no tienen privilegios (=false) y no pueden, por ejemplo, modificar partes del sistema operativo. Esto se debe a que, por defecto, un contenedor solo tiene acceso limitado a los dispositivos. A un contenedor "privilegiado" se le otorga el mismo acceso a los dispositivos que al usuario que lo inicia, con la excepción de las consolas virtuales (/dev/tty\d+) cuando se ejecuta en modo systemd (--systemd=always).

Un contenedor privilegiado desactiva las características de seguridad que aíslan el contenedor del host. Las capacidades descartadas, los dispositivos limitados, los puntos de montaje de solo lectura, la separación de Apparmor/SELinux y los filtros Seccomp se deshabilitan. Debido a las características de seguridad deshabilitadas, el campo privilegiado casi nunca debería establecerse, ya que los contenedores pueden escapar fácilmente de su confinamiento.

Los contenedores que se ejecutan en un espacio de nombres de usuario (por ejemplo, contenedores sin root) no pueden tener más privilegios que el usuario que los inició.

--publish, -p=[[ip:]puertoHost:]puertoContenedor[/protocolo]

Publica uno o un rango de puertos de un contenedor en el host.

Tanto puertoHost como puertoContenedor se pueden especificar como un rango de puertos. Al especificar rangos para ambos, el número de puertos del contenedor en el rango debe coincidir con el número de puertos del host en el rango.

Si la IP del host se establece en 0.0.0.0 o no se establece, el puerto se enlaza a todas las IPs del host.

Por defecto, Podman publica puertos TCP. Para publicar un puerto UDP en su lugar, especifique udp como protocolo. Para publicar puertos TCP y UDP, establezca --publish dos veces, con tcp y udp como protocolos respectivamente. Los contenedores con root también pueden publicar puertos usando el protocolo sctp.

No es obligatorio especificar el puerto del host (por ejemplo, podman run -p 127.0.0.1::80). Si no se hace, al puerto del contenedor se le asigna aleatoriamente un puerto en el host.

Utilice podman port para ver el mapeo real: podman port $CONTENEDOR $PUERTO_CONTENEDOR.

La publicación de puertos solo es compatible con contenedores que utilizan su propio espacio de nombres de red a través de redes bridge, o los modos de red pasta y slirp4netns.

Nota: Si un contenedor se ejecuta dentro de un pod, no es necesario publicar el puerto para los contenedores del pod. El puerto solo debe ser publicado por el propio pod. Las pilas de red del pod actúan como la pila de red del host, lo que significa que una variedad de contenedores en el pod y programas en el contenedor comparten una única interfaz, dirección IP y puertos asociados. Si un contenedor se enlaza a un puerto, ningún otro contenedor puede usar ese puerto dentro del pod mientras esté en uso. Los contenedores del pod también pueden comunicarse a través de localhost al enlazar un contenedor a localhost en el pod y otro conectarse a ese puerto.

--publish-all, -P

Publica todos los puertos expuestos a puertos aleatorios en las interfaces del host. El valor por defecto es false.

Cuando se establece en true, publica todos los puertos expuestos en las interfaces del host. Si el operador usa -P (o -p) entonces Podman hace que el puerto expuesto sea accesible en el host y los puertos estén disponibles para cualquier cliente que pueda alcanzar el host.

Al usar esta opción, Podman enlaza cualquier puerto expuesto a un puerto aleatorio en el host dentro de un rango de puertos efímeros definido en /proc/sys/net/ipv4/ip_local_port_range. Para encontrar el mapeo entre los puertos del host y los puertos expuestos, use podman port.

--pull=politica

Política de descarga de imágenes. El valor por defecto es missing.

  • always: Descarga siempre la imagen y produce un error si la descarga falla.
  • missing: Descarga la imagen solo cuando la imagen no está en el almacenamiento local de contenedores. Produce un error si no se encuentra ninguna imagen y la descarga falla.
  • never: Nunca descarga la imagen, sino que utiliza la del almacenamiento local de contenedores. Produce un error si no se encuentra ninguna imagen.
  • newer: Descarga si la imagen en el registro es más nueva que la del almacenamiento local de contenedores. Una imagen se considera más nueva cuando los hashes son diferentes. Comparar las marcas de tiempo es propenso a errores. Los errores de descarga se suprimen si se encontró una imagen local.

--quiet, -q

--rdt-class=intel-rdt-class-of-service

Rdt-class establece la clase de servicio (CLOS o COS) en la que se ejecutará el contenedor. Basado en la función Cache Allocation Technology (CAT) que forma parte del conjunto de funciones Intel Resource Director Technology (RDT), todos los procesos del contenedor se ejecutarán dentro de la COS pre-configurada, representando una parte de la caché. La COS debe crearse y configurarse utilizando un sistema de archivos pseudo (generalmente montado en /sys/fs/resctrl) que proporciona el controlador del kernel resctrl. Asignar el contenedor a una COS requiere privilegios de root y, por lo tanto, no funciona en un entorno sin root. Actualmente, la función solo es compatible con runc como runtime. Consulte ⟨https://docs.kernel.org/arch/x86/resctrl.html⟩ para más detalles sobre la creación de una COS antes de que un contenedor pueda ser asignado a ella.

--read-only

Monta el sistema de archivos raíz del contenedor como de solo lectura.

Por defecto, los sistemas de archivos raíz de los contenedores son escribibles, lo que permite a los procesos escribir archivos en cualquier lugar. Al especificar la bandera --read-only, el sistema de archivos raíz de los contenedores se monta de solo lectura, lo que prohíbe cualquier escritura.

--read-only-tmpfs

Al ejecutar contenedores con --read-only, monta un tmpfs de lectura/escritura en /dev, /dev/shm, /run, /tmp y /var/tmp. El valor por defecto es true.

--read-only --read-only-tmpfs / /run, /tmp, /var/tmp
true true r/o r/w
true false r/o r/o
false false r/w r/w
false true r/w r/w

Cuando --read-only=true y --read-only-tmpfs=true, se montan tmpfs adicionales en los directorios /tmp, /run y /var/tmp.

Cuando --read-only=true y --read-only-tmpfs=false, /dev y /dev/shm se marcan como Lectura/Escritura y no se montan tmpfs en /tmp, /run y /var/tmp. Los directorios se exponen de la imagen subyacente, lo que significa que son de solo lectura por defecto. Esto hace que el contenedor sea totalmente de solo lectura. No existen directorios escribibles dentro del contenedor. En este modo, los directorios escribibles deben añadirse a través de volúmenes o montajes externos.

Por defecto, cuando --read-only=false, /dev y /dev/shm son de lectura/escritura, y /tmp, /run y /var/tmp son directorios de lectura/escritura de la imagen del contenedor.

--replace

Si ya existe otro contenedor con el mismo nombre, reemplázalo y elimínalo. El valor por defecto es false.

--requires=contenedor

Especifica uno o más requisitos. Un requisito es un contenedor de dependencia que se inicia antes que este contenedor. Los contenedores se pueden especificar por nombre o ID, con múltiples contenedores separados por comas.

--restart=politica

Política de reinicio a seguir cuando los contenedores terminan. La política de reinicio no tiene efecto si un contenedor se detiene mediante los comandos podman kill o podman stop.

Los valores válidos de politica son:

  • no: No reiniciar los contenedores al salir
  • never: Sinónimo de no; no reiniciar los contenedores al salir
  • on-failure[:max_retries]: Reiniciar los contenedores cuando salgan con un código de salida distinto de cero, reintentando indefinidamente o hasta que se alcance el número opcional de reintentos max_retries
  • always: Reiniciar los contenedores cuando salgan, independientemente del estado, reintentando indefinidamente
  • unless-stopped: Idéntico a always

Podman proporciona un archivo de unidad de systemd, podman-restart.service, que reinicia los contenedores después de un reinicio del sistema.

Al ejecutar contenedores en servicios systemd, utilice la funcionalidad de reinicio proporcionada por systemd. En otras palabras, no utilice esta opción en una unidad de contenedor; en su lugar, establezca la directiva Restart= de systemd en la sección [Service]. Consulte podman-systemd.unit(5) y systemd.service(5).

Número de veces que se intentará descargar o subir imágenes entre el registro y el almacenamiento local en caso de fallo. El valor por defecto es 3.

--rm

Elimina automáticamente el contenedor y cualquier volumen anónimo sin nombre asociado al contenedor cuando este sale. El valor predeterminado es false.

--rmi

Después de salir del contenedor, elimina la imagen a menos que otro contenedor la esté utilizando. Implica --rm en el nuevo contenedor. El valor predeterminado es false.

--rootfs

Esto es útil para ejecutar un contenedor sin requerir ninguna gestión de imágenes; se supone que la raíz del sistema de archivos del contenedor es gestionada externamente.

Montajes de Rootfs Superpuestos

El indicador :O indica a Podman que monte el directorio de la ruta de la raíz del sistema de archivos como almacenamiento utilizando el sistema de archivos superpuesto. Los procesos del contenedor pueden modificar el contenido dentro del punto de montaje, que se almacena en el almacenamiento del contenedor en un directorio separado. En términos de superposición, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el contenedor termina de ejecutarse, de forma similar a un punto de montaje tmpfs que se desmonta.

Nota: En sistemas SELinux, la raíz del sistema de archivos necesita la etiqueta correcta, que es por defecto unconfined_u:object_r:container_file_t:s0.

--secret=secret[,opt=opt ...]

Da acceso al contenedor a un secreto. Se puede especificar varias veces.

Un secreto es un bloque de datos sensibles que un contenedor necesita en tiempo de ejecución pero que no se almacena en la imagen ni en el control de versiones, como nombres de usuario y contraseñas, certificados y claves TLS, claves SSH u otras cadenas genéricas o contenido binario importantes (hasta 512 kB de tamaño).

Cuando los secretos se especifican como tipo mount, los secretos se copian y montan en el contenedor cuando se crea uno. Cuando los secretos se especifican como tipo env, el secreto se establece como una variable de entorno dentro del contenedor. Los secretos se escriben en el contenedor en el momento de la creación del contenedor, y la modificación del secreto utilizando los comandos podman secret después de la creación del contenedor afecta al secreto dentro del contenedor.

Los secretos y su almacenamiento se gestionan utilizando el comando podman secret.

Opciones de Secretos

  • type=mount|env : Cómo se expone el secreto al contenedor.
    mount monta el secreto en el contenedor como un archivo.
    env expone el secreto como una variable de entorno.
    Por defecto es mount.
  • target=target : Destino del secreto.
    Para secretos montados, esta es la ruta al secreto dentro del contenedor.
    Si se proporciona una ruta completamente calificada, el secreto se monta en esa ubicación.
    De lo contrario, el secreto se monta en
    /run/secrets/target para contenedores Linux o
    /var/run/secrets/target para contenedores FreeBSD.
    Si no se establece el destino, el secreto se monta en /run/secrets/secretname por defecto.
    Para secretos de entorno, esta es la clave de la variable de entorno. Por defecto es secretname.
  • uid=0 : UID del secreto. Por defecto es 0. Solo tipo de montaje de secreto.
  • gid=0 : GID del secreto. Por defecto es 0. Solo tipo de montaje de secreto.
  • mode=0 : Modo del secreto. Por defecto es 0444. Solo tipo de montaje de secreto.

Ejemplos

Montar en /my/location/mysecret con UID 1:

--secret mysecret,target=/my/location/mysecret,uid=1

Montar en /run/secrets/customtarget con modo 0777:

--secret mysecret,target=customtarget,mode=0777

Crear una variable de entorno de secreto llamada ENVSEC:

--secret mysecret,type=env,target=ENVSEC

--uidmap=[banderas]uid_contenedor:uid_origen[:cantidad]

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo de UID proporcionado. Esta opción entra en conflicto con las opciones --userns y --subuidname. Esta opción proporciona una forma de mapear UID de host a UID de contenedor. Se puede pasar varias veces para mapear diferentes rangos.

Los valores posibles de las banderas opcionales se discuten más abajo en esta página. El valor de cantidad es opcional y se asume que es 1 si no se proporciona.

El valor de uid_origen se basa en el usuario que ejecuta el comando, ya sea un usuario con privilegios (rootful) o sin privilegios (rootless).

  • usuario con privilegios (rootful): [banderas]uid_contenedor:uid_host[:cantidad]
  • usuario sin privilegios (rootless): [banderas]uid_contenedor:uid_intermedio[:cantidad]

Mapeos con privilegios (Rootful)

Cuando podman run es llamado por un usuario privilegiado, la opción --uidmap funciona como un mapeo directo entre los UID del host y los UID del contenedor.

UID del host -> UID del contenedor

La cantidad especifica el número de UID consecutivos que se mapean. Si, por ejemplo, cantidad es 4, el mapeo se ve así:

UID del host UID del contenedor
uid_origen uid_contenedor
uid_origen + 1 uid_contenedor + 1
uid_origen + 2 uid_contenedor + 2
uid_origen + 3 uid_contenedor + 3

Mapeos sin privilegios (Rootless)

Cuando podman run es llamado por un usuario no privilegiado (es decir, ejecutándose sin privilegios), el valor uid_origen se interpreta como un "UID intermedio". En el caso sin privilegios, los UID del host no se mapean directamente a los UID del contenedor. En cambio, el mapeo se realiza a través de dos pasos de mapeo:

UID del host -> UID intermedio -> UID del contenedor

La opción --uidmap solo influye en el segundo paso de mapeo.

El primer paso de mapeo se deriva de Podman a partir del contenido del archivo /etc/subuid y del UID del usuario que llama a Podman.

Primer paso de mapeo:

UID del host UID intermedio
UID del usuario de Podman 0
1er UID subordinado 1
2do UID subordinado 2
3er UID subordinado 3
nth UID subordinado n

Para poder utilizar UID intermedios mayores que cero, el usuario necesita tener UID subordinados configurados en /etc/subuid. Consulte subuid(5).

El segundo paso de mapeo se configura con --uidmap.

Si, por ejemplo, la cantidad es 5, el segundo paso de mapeo se ve así:

UID intermedio UID del contenedor
uid_origen uid_contenedor
uid_origen + 1 uid_contenedor + 1
uid_origen + 2 uid_contenedor + 2
uid_origen + 3 uid_contenedor + 3
uid_origen + 4 uid_contenedor + 4

Al ejecutarse sin privilegios, Podman utiliza todos los rangos configurados en el archivo /etc/subuid.

El ID de usuario actual se mapea a UID=0 en el espacio de nombres de usuario sin privilegios. Cada rango adicional se agrega secuencialmente después:

host espacio de nombres de usuario sin privilegios longitud
$UID 0 1
1 $FIRST_RANGE_ID $FIRST_RANGE_LENGTH
1+$FIRST_RANGE_LENGTH $SECOND_RANGE_ID $SECOND_RANGE_LENGTH

Referenciar un ID de host desde el espacio de nombres padre

Como usuario sin privilegios, el ID de host proporcionado en --uidmap o --gidmap se mapea desde el espacio de nombres intermedio generado por Podman. A veces es deseable referirse directamente al espacio de nombres del host. Es posible hacerlo manualmente ejecutando podman unshare cat /proc/self/gid_map, encontrando el ID de host deseado en la segunda columna de la salida y obteniendo el ID intermedio correspondiente de la primera columna.

Podman puede realizar todo esto precediendo el ID de host en el mapeo con el símbolo @. Por ejemplo, al especificar --gidmap 100000:@2000:1, Podman buscará el ID intermedio que corresponde al ID de host 2000 y mapeará el ID intermedio encontrado al ID de contenedor 100000. El ID de host proporcionado debe haber sido subordinado (de lo contrario, no se habría mapeado al espacio intermedio en primer lugar).

Si la longitud es mayor que uno, por ejemplo con --gidmap 100000:@2000: 2, Podman asignará los IDs del host 2000 y 2001 a 100000 y 100001, respectivamente, independientemente de cómo se defina la asignación intermedia.

Extender asignaciones previas

Algunas modificaciones de asignación pueden ser engorrosas. Por ejemplo, un usuario comienza con una asignación como --gidmap="0:0:65000", que necesita cambiarse de modo que el ID padre 1 se asigne al ID de contenedor 100000 en su lugar, dejando el ID de contenedor 1 sin asignar. El --gidmap correspondiente se convierte en --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

Esta notación se puede simplificar usando el indicador +, que se encarga de romper las asignaciones previas eliminando cualquier asignación conflictiva con la asignación dada. El indicador se introduce antes del ID del contenedor, de la siguiente manera: --gidmap="0:0:65000" --gidmap="+100000:1:1"

Indicador Ejemplo Descripción
+ +100000:1:1 Extender la asignación anterior

Esta notación provoca brechas en la asignación, por lo que puede ser conveniente rellenar esas brechas posteriormente: --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

Un caso de uso específico para este indicador es en el contexto de usuarios sin privilegios (rootless). Un usuario sin privilegios puede especificar asignaciones con el indicador + como en --gidmap="+100000:1:1". Podman luego "rellenará las brechas" comenzando desde cero con todos los IDs intermedios restantes. Esto es conveniente cuando un usuario desea asignar un ID intermedio específico a un ID de contenedor, dejando que Podman asigne el resto de los IDs subordinados a su discreción.

Pasar solo uno de --uidmap o --gidmap

Normalmente, los IDs de usuario y grupo subordinados se asignan simultáneamente, y para cualquier usuario, los IDs de usuario subordinados coinciden con los IDs de grupo subordinados. Para mayor comodidad, si solo se proporciona uno de --uidmap o --gidmap, podman asume que la asignación se refiere tanto a UIDs como a GIDs y aplica la asignación dada a ambos. Si solo uno de los dos valores necesita cambiarse, las asignaciones deben incluir los indicadores u o g para especificar que solo se aplican a UIDs o GIDs y no deben copiarse.

Indicador Ejemplo Descripción
u u20000:2000:1 La asignación solo se aplica a UIDs
g g10000:1000:1 La asignación solo se aplica a GIDs

Por ejemplo, dado el comando

podman run --gidmap "0:0:1000" --gidmap "g2000:2000:1"

Dado que no se proporciona --uidmap, el --gidmap se copia a --uidmap, lo que da un comando equivalente a

podman run --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

El --gidmap "g2000:2000:1" usó el indicador g y, por lo tanto, no se copió a --uidmap.

Asignación sin privilegios de GIDs de host adicionales

Un usuario sin privilegios puede desear asignar un grupo de host específico que ya se ha subordinado dentro de /etc/subgid sin especificar el resto de la asignación.

Esto se puede hacer con --gidmap "+gcontainer_gid:@host_gid"

Donde:

  • El GID del host se proporciona a través del símbolo @
  • La asignación de este GID no se copia a --usermap gracias al indicador g.
  • El resto de los IDs de contenedor se asignarán comenzando desde 0 hasta n, con todos los GIDs subordinados restantes, gracias al indicador +.

Por ejemplo, si un usuario pertenece al grupo 2000 y ese grupo está subordinado a ese usuario (con usermod --add-subgids 2000-2000 $USER), el usuario puede asignar el grupo al contenedor con: --gidmap=+g100000:@2000.

Si esta asignación se combina con la opción --group-add=keep-groups, el proceso en el contenedor pertenecerá al grupo 100000, y los archivos pertenecientes al grupo 2000 en el host aparecerán como propiedad del grupo 100000 dentro del contenedor.

podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

Sin UIDs subordinados

Incluso si un usuario no tiene UIDs subordinados en /etc/subuid, se puede usar --uidmap para asignar el UID normal del usuario a un UID de contenedor ejecutando podman run --uidmap $container_uid:0:1 --user $container_uid ....

Cuando no se utiliza un espacio de nombres de usuario, el UID y el GID utilizados dentro del contenedor y en el host coinciden. Sin embargo, cuando se utilizan espacios de nombres de usuario, el UID y el GID dentro del contenedor pueden corresponder a otro UID y GID en el host. En contenedores sin privilegios (rootless), por ejemplo, siempre se utiliza un espacio de nombres de usuario, y root dentro del contenedor corresponde por defecto al UID y GID del usuario que invoca Podman.

--userns=modo

Establece el modo del espacio de nombres de usuario para el contenedor.

Si no se establece --userns, el valor predeterminado se determina de la siguiente manera. - Si se establece --pod, se ignora --userns y se utiliza el espacio de nombres de usuario del pod. - Si se establece la variable de entorno PODMAN_USERNS, se utiliza su valor. - Si se especifica userns en containers.conf, se utiliza este valor. - De lo contrario, se asume --userns=host.

--userns="" (es decir, una cadena vacía) es un alias de --userns=host.

Esta opción es incompatible con --gidmap, --uidmap, --subuidname y --subgidname.

Asignaciones de claves de --userns para usuarios sin privilegios (rootless):

Clave Usuario del Host Usuario del Contenedor
auto $UID nil (El UID del Usuario del Host no se asigna al contenedor).
host $UID 0 (Cuenta de Usuario predeterminada asignada al usuario root en el contenedor).
keep-id $UID $UID (Asigna la cuenta de usuario al mismo UID dentro del contenedor).
keep-id:uid=200,gid=210 $UID 200:210 (Asigna la cuenta de usuario al UID especificado, valor GID dentro del contenedor).
nomap $UID nil (El UID del Usuario del Host no se asigna al contenedor).

Los valores válidos de modo son:

auto[:OPCIONES,...]: crea automáticamente un espacio de nombres de usuario único.

  • modo con privilegios (rootful): el indicador --userns=auto requiere que el nombre de usuario containers se especifique en los archivos /etc/subuid y /etc/subgid, con un rango no utilizado de IDs de usuario subordinados que Podman puede asignar a los contenedores. Ejemplo: containers:2147483647:2147483648.
  • modo sin privilegios (rootless): se utilizarán los rangos de usuarios de los archivos /etc/subuid y /etc/subgid. Tenga en cuenta que ejecutar un solo contenedor sin usar --userns=auto utilizará el rango completo de UIDs y no permitirá una mayor subdivisión. Consulte subuid(5).

Podman asigna rangos únicos de UIDs y GIDs de los IDs de usuario subordinados de containers. El tamaño de los rangos se basa en el número de UIDs requeridos en la imagen. El número de UIDs y GIDs se puede anular con la opción size.

La opción --userns=keep-id utiliza todos los subuids y subgids del usuario. La opción --userns=nomap utiliza todos los subuids y subgids del usuario excepto el propio ID del usuario. Usar --userns=auto al iniciar nuevos contenedores no funciona mientras existan contenedores que se iniciaron con --userns=nomap o --userns=keep-id sin limitar el tamaño del espacio de nombres de usuario.

Opciones válidas de auto:

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE: para forzar que un GID se incluya en el espacio de nombres de usuario.
  • size=SIZE: para especificar un tamaño explícito para el espacio de nombres de usuario automático. Por ejemplo, --userns=auto:size=8192. Si size no
t especificado, auto estima un tamaño para el espacio de nombres de usuario.
  • uidmapping=UID_CONTENEDOR:UID_HOST:TAMAÑO: para forzar que un mapeo de UID esté presente en el espacio de nombres de usuario.

    • El UID y GID del host en gidmapping y uidmapping pueden prefijarse opcionalmente con el símbolo @. En este caso, podman buscará el ID intermedio correspondiente al ID del host y mapeará el ID intermedio encontrado al ID del contenedor. Para más detalles, ver --uidmap.

    container:id: une el espacio de nombres de usuario del contenedor especificado.

    host o "" (cadena vacía): ejecutar en el espacio de nombres de usuario del llamante. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el host que cualquier otro proceso iniciado por el usuario llamante.

    keep-id: crea un espacio de nombres de usuario donde el UID :GID del usuario actual se mapean a los mismos valores en el contenedor. Para contenedores creados por root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

    Además, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen, a menos que establezca explícitamente --user.

    Opciones válidas para keep-id:

    • uid=UID: anula el UID dentro del contenedor que se utiliza para mapear el usuario actual.
    • gid=GID: anula el GID dentro del contenedor que se utiliza para mapear el usuario actual.
    • size=TAMAÑO: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No soportado cuando se ejecuta como root.

    nomap: crea un espacio de nombres de usuario donde el UID :GID del usuario rootless actual no se mapean en el contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

    ns:namespace: ejecuta el contenedor en el espacio de nombres de usuario existente dado.

    --uts=modo

    Establece el modo del espacio de nombres UTS para el contenedor. Se soportan los siguientes valores:

    • host: utiliza el espacio de nombres UTS del host dentro del contenedor.
    • private: crea un nuevo espacio de nombres para el contenedor (predeterminado).
    • ns:[ruta]: ejecuta el contenedor en el espacio de nombres UTS existente dado.
    • container:[contenedor]: une el espacio de nombres UTS del contenedor especificado.

    --variant=VARIANT

    Utiliza VARIANT en lugar de la variante de arquitectura predeterminada de la imagen del contenedor. Algunas imágenes pueden usar múltiples variantes de las arquitecturas arm, como arm/v5 y arm/v7.

    --volume, -v=[[VOLUMEN-ORIGEN|DIRECTORIO-HOST:]DIRECTORIO-CONTENEDOR[:OPCIONES]]

    Crea un montaje bind. Si se especifica -v /DIRECTORIO-HOST:/DIRECTORIO-CONTENEDOR, Podman monta /DIRECTORIO-HOST del host en /DIRECTORIO-CONTENEDOR en el contenedor Podman. De manera similar, -v VOLUMEN-ORIGEN:/DIRECTORIO-CONTENEDOR monta el volumen con nombre del host en el contenedor. Si no existe dicho volumen con nombre, Podman crea uno. Si no se proporciona origen, el volumen se crea como un volumen con nombre anónimo con un nombre generado aleatoriamente y se elimina cuando el contenedor se elimina mediante la opción --rm o el comando podman rm --volumes.

    (Nota: al usar el cliente remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), los volúmenes se montan desde el servidor remoto, no necesariamente desde la máquina cliente.)

    Las OPCIONES son una lista separada por comas y pueden ser una o más de las siguientes:

    • rw|ro
    • z|Z
    • [O]
    • [U]
    • [no]copy
    • [no]dev
    • [no]exec
    • [no]suid
    • [r]bind
    • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Footnote1⟩
    • idmap[=opciones]

    El DIRECTORIO-CONTENEDOR debe ser una ruta absoluta, como /src/docs. El volumen se monta en el contenedor en este directorio.

    Si se especifica un origen de volumen, debe ser una ruta en el host o el nombre de un volumen con nombre. Se permiten rutas de host absolutas o relativas; las rutas relativas se resuelven en relación con el directorio en el que se ejecuta Podman. Si la fuente no existe, Podman devuelve un error. Los usuarios deben precrear los archivos o directorios de origen.

    Cualquier origen que no comience con un . o / se trata como el nombre de un volumen con nombre. Si no existe un volumen con ese nombre, se crea. Los volúmenes creados con nombres no son anónimos y no son eliminados por la opción --rm ni por el comando podman rm --volumes.

    Especifique múltiples opciones -v para montar uno o más volúmenes en un contenedor.

    Montajes de volumen protegidos contra escritura

    Agregue la opción :ro o :rw para montar un volumen en modo de solo lectura o lectura-escritura, respectivamente. Por defecto, los volúmenes se montan en modo lectura-escritura. Ver ejemplos.

    Cambio de propietario de montajes de volumen

    Cuando un volumen con nombre se monta por primera vez en un contenedor, Podman ajusta automáticamente la propiedad del punto de montaje del volumen durante la inicialización del contenedor. Esta operación de cambio de propietario ocurre bajo las siguientes condiciones:

    • El volumen aún no se ha utilizado (tiene NeedsChown establecido en true)
    • El volumen está vacío o aún no se ha copiado
    • El volumen no está gestionado por un controlador de volumen externo
    • El controlador de volumen no es "image"

    Para volúmenes con montajes idmapped (usando la opción idmap), el cambio de propiedad tiene en cuenta los mapeos del espacio de nombres de usuario del contenedor, pero el volumen idmapped conserva el mapeo UID/GID correcto. Para volúmenes sin idmapping, el punto de montaje se cambia de propietario para que coincida con el usuario y grupo del proceso del contenedor, mapeado al espacio de nombres de usuario del host si la re-mapeo del espacio de nombres de usuario está habilitado.

    Si un contenedor se crea en un nuevo espacio de nombres de usuario, el UID y GID dentro del contenedor pueden corresponder a otro UID y GID en el host.

    El sufijo :U indica a Podman que utilice el UID y GID del host correctos basados en el UID y GID dentro del contenedor, para cambiar recursivamente el propietario y el grupo del volumen de origen. El cambio de propietario recorre el sistema de archivos bajo el volumen y cambia el UID /GID de cada archivo. Si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, retrasando el inicio del contenedor.

    Advertencia: úselo con precaución, ya que esto modifica el sistema de archivos del host.

    Etiquetado de montajes de volumen

    Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el sistema operativo.

    Para cambiar una etiqueta en el contexto del contenedor, agregue uno de los dos sufijos :z o :Z al montaje del volumen. Estos sufijos indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le dice a Podman que dos o más contenedores comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartidas permiten que todos los contenedores lean / escriban contenido. La opción Z le dice a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el contenedor actual puede usar un volumen privado.

    Nota: todos los contenedores dentro de un pod comparten la misma etiqueta SELinux. Esto significa que todos los contenedores dentro de dicho pod pueden leer / escribir volúmenes compartidos en el contenedor creado con :Z en cualquiera de los contenedores. Volver a etiquetar recorre el sistema de archivos bajo el volumen y cambia la etiqueta de cada archivo; si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, retrasando el inicio del contenedor. Si el volumen fue previamente re-etiquetado con la opción z, Podman está optimizado para no re-etiquetar una segunda vez. Si se mueven archivos al volumen, las etiquetas se pueden cambiar manualmente con el comando chcon -Rt container_file_t RUTA.

    Nota: No re-etiquete archivos y directorios del sistema. Re-etiquetar contenido del sistema puede hacer que otros servicios confinados en la máquina fallen. Para este tipo de contenedores, recomendamos deshabilitar la separación de SELinux. La opción --security-opt label=disable deshabilita la separación de SELinux para el contenedor. Por ejemplo, si un usuario quisiera montar su directorio personal completo en un contenedor, necesita deshabilitar la separación de SELinux.

    $ podman run --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

    Montajes de volumen superpuestos

    El indicador :O le dice a Podman que monte el directorio del host como almacenamiento temporal usando el sistema de archivos overlay. Los procesos del contenedor pueden modificar el contenido dentro del punto de montaje, que se almacena en el almacenamiento del contenedor en un directorio separado. En términos de overlay, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el contenedor termina de ejecutarse, similar a como se desmonta un punto de montaje tmpfs.

    Para usuarios avanzados, la opción overlay también admite upperdir y workdir personalizados no volátiles para el montaje overlay. El usuario puede gestionar completamente los upperdir y workdir personalizados, y Podman no los elimina al finalizar el ciclo de vida. Ejemplo: :O,upperdir=/some/upper,workdir=/some/work

    Las ejecuciones posteriores del contenedor ven el contenido original del directorio de origen; los cambios de ejecuciones anteriores del contenedor ya no existen.

    Un caso de uso del montaje overlay es compartir la caché de paquetes del host en el contenedor para acelerar las compilaciones.

    Nota: El indicador O entra en conflicto con otras opciones listadas anteriormente.

    El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor. Normalmente, los contenedores pueden leer / ejecutar container_share_t y pueden leer / escribir container_file_t. Si no se pueden cambiar las etiquetas en un volumen de origen, se debe deshabilitar la separación de contenedores SELinux para que el contenedor funcione.

    No modifique el directorio de origen montado en el contenedor con un montaje overlay, puede causar fallos inesperados. Solo modifique el directorio después de que el contenedor termine de ejecutarse.

    Propagación de montajes

    Por defecto, los volúmenes montados bind son privados. Eso significa que cualquier montaje realizado dentro del contenedor no es visible en el host y viceversa. Se puede cambiar este comportamiento especificando una propiedad de propagación de montaje de volumen. Cuando un volumen está compartido, los montajes realizados bajo ese volumen dentro del contenedor son visibles en el host y

    o viceversa. Crear un volumen esclavo[1] ⟨#Footnote1⟩ habilita la propagación de montaje unidireccional: los montajes realizados en el host bajo ese volumen son visibles dentro del contenedor, pero no al revés.

    Para controlar la propiedad de propagación de montaje de un volumen, se puede usar la bandera de propagación [r]compartido, [r]esclavo, [r]privado o [r]no enlazable. La propiedad de propagación solo se puede especificar para volúmenes enlazados y no para volúmenes internos o volúmenes con nombre. Para que la propagación de montaje funcione, el punto de montaje de origen (el punto de montaje donde está montado el directorio de origen) debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe estar compartido. Y para volúmenes esclavos, el punto de montaje de origen debe ser compartido o esclavo. [1] ⟨#Footnote1⟩

    Para montar recursivamente un volumen y todos sus submontajes en un contenedor, use la opción rbind. Por defecto se usa la opción bind, y los submontajes del directorio de origen no se montan en el contenedor.

    Montar el volumen con una opción copy le indica a podman que copie el contenido del directorio de destino subyacente en volúmenes internos recién creados. La copia solo ocurre en la creación inicial del volumen. El contenido no se copia cuando el volumen se utiliza posteriormente en diferentes contenedores. La opción copy se ignora en los montajes bind y no tiene efecto.

    Montar volúmenes con la opción nosuid significa que los ejecutables SUID en el volumen no pueden ser utilizados por las aplicaciones para cambiar su privilegio. Por defecto, los volúmenes se montan con nosuid.

    Montar el volumen con la opción noexec significa que ningún ejecutable en el volumen puede ser ejecutado dentro del contenedor.

    Montar el volumen con la opción nodev significa que ningún dispositivo en el volumen puede ser utilizado por procesos dentro del contenedor. Por defecto, los volúmenes se montan con nodev.

    Si el HOST-DIR es un punto de montaje, entonces las opciones dev, suid y exec son ignoradas por el kernel.

    Use df HOST-DIR para determinar el montaje de origen, luego use findmnt -o TARGET,PROPAGATION directorio-montaje-origen para determinar las propiedades de propagación del montaje de origen. Si la utilidad findmnt(1) no está disponible, entonces se puede observar la entrada de montaje para el punto de montaje de origen en /proc/self/mountinfo. Observe los "campos opcionales" y vea si se especifican propiedades de propagación. Allí, shared:N significa que el montaje está compartido, master:N significa que el montaje es esclavo, y si no hay nada, el montaje es privado. [1] ⟨#Footnote1⟩

    Para cambiar las propiedades de propagación de un punto de montaje, use el comando mount(8). Por ejemplo, si se desea enlazar el directorio de origen /foo, se puede hacer mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convierte /foo en un punto de montaje compartido. Alternativamente, se pueden cambiar directamente las propiedades de propagación del montaje de origen. Supongamos que / es el montaje de origen para /foo, luego use mount --make-shared / para convertir / en un montaje compartido.

    Nota: si el usuario solo tiene derechos de acceso a través de un grupo, el acceso al volumen desde un contenedor sin privilegios falla.

    Montaje idmapped

    Si se especifica idmap, cree un montaje idmapped al espacio de nombres de usuario de destino en el contenedor. La opción idmap admite un mapeo personalizado que puede ser diferente del espacio de nombres de usuario utilizado por el contenedor. El mapeo se puede especificar después de la opción idmap, así: idmap=uids=0-1-10#10-11-10;gids=0-100-10. Para cada triplete, el primer valor es el inicio de los IDs del sistema de archivos de respaldo que se mapean al segundo valor en el host. La longitud de este mapeo se indica en el tercer valor. Múltiples rangos se separan con #.

    Utilice la opción --group-add keep-groups para pasar el acceso a grupos suplementarios del usuario al contenedor.

    --volumes-from=CONTAINER[:OPTIONS]

    Monta volúmenes del(los) contenedor(es) especificado(s). Se utiliza para compartir volúmenes entre contenedores. Las opciones son una lista separada por comas con los siguientes elementos disponibles:

    • rw|ro
    • z

    Monta volúmenes ya montados de un contenedor de origen en otro contenedor. CONTAINER puede ser un nombre o un ID. Para compartir un volumen, use la opción --volumes-from al ejecutar el contenedor de destino. Los volúmenes se pueden compartir incluso si el contenedor de origen no se está ejecutando.

    Por defecto, Podman monta los volúmenes en el mismo modo (lectura-escritura o solo lectura) en que están montados en el contenedor de origen. Esto se puede cambiar añadiendo una opción ro o rw.

    Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el sistema operativo.

    Para cambiar una etiqueta en el contexto del contenedor, agregue z al montaje del volumen. Este sufijo le dice a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le dice a Podman que dos entidades comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban contenido.

    Si la ubicación del volumen del contenedor de origen se superpone con datos que residen en un contenedor de destino, el volumen ocultará esos datos en el destino.

    --workdir, -w=dir

    Directorio de trabajo dentro del contenedor.

    El directorio de trabajo predeterminado para ejecutar binarios dentro de un contenedor es el directorio raíz (/). El desarrollador de la imagen puede establecer un valor predeterminado diferente con la instrucción WORKDIR. El operador puede anular el directorio de trabajo utilizando la opción -w.

    Estado de salida

    El código de salida de podman run proporciona información sobre por qué el contenedor no se pudo ejecutar o por qué salió. Cuando podman run sale con un código distinto de cero, los códigos de salida siguen el estándar de chroot(1), véase a continuación:

    EJEMPLOS

    Ejecutando contenedor en modo solo lectura

    Durante el desarrollo de imágenes de contenedor, los contenedores a menudo necesitan escribir en el contenido de la imagen. Por ejemplo, instalando paquetes en /usr. En producción, las aplicaciones rara vez necesitan escribir en la imagen. Las aplicaciones de contenedor escriben en volúmenes si necesitan escribir en sistemas de archivos. Las aplicaciones se pueden hacer más seguras ejecutándolas en modo de solo lectura usando el modificador --read-only. Esto protege la imagen del contenedor contra modificaciones. Por defecto, los contenedores de solo lectura pueden escribir datos temporales. Podman monta un tmpfs en /run y /tmp dentro del contenedor.

    $ podman run --read-only -i -t fedora /bin/bash

    Si el contenedor no escribe en ningún sistema de archivos dentro del contenedor, incluido tmpfs, establezca --read-only-tmpfs=false.

    $ podman run --read-only --read-only-tmpfs=false --tmpfs /run -i -t fedora /bin/bash

    Exponiendo librerías compartidas dentro del contenedor como solo lectura usando un glob

    $ podman run --mount type=glob,src=/usr/lib64/libnvidia\*,ro=true -i -t fedora /bin/bash

    Exponiendo mensajes de log del contenedor al log del host

    Enlace de montaje del directorio /dev/log para que los mensajes que se registran en el contenedor aparezcan en el syslog/journal del host.

    $ podman run -v /dev/log:/dev/log -i -t fedora /bin/bash

    Desde dentro del contenedor, pruebe esto enviando un mensaje al log.

    (bash)# logger "Hello from my container"

    Luego salga y verifique el journal.

    (bash)# exit
$ journalctl -b | grep Hello

    Esto lista el mensaje enviado al logger.

    Conectando a uno o más de STDIN, STDOUT, STDERR

    Sin especificar la opción -a, Podman conecta todo (stdin, stdout, stderr). Anule el valor predeterminado especificando -a (stdin, stdout, stderr), como en:

    $ podman run -a stdin -a stdout -i -t fedora /bin/bash

    Compartiendo IPC entre contenedores

    Usando shm_server.c disponible aquí: https://www.cs.cf.ac.uk/Dave/C/node27.html

    Probando el modo --ipc=host:

    El host muestra un segmento de memoria compartida con 7 pids adjuntos, que resulta ser de httpd:

    $ sudo ipcs -m
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status
0x01128e25 0          root       600        1000       7

    Ahora ejecute un contenedor regular, y correctamente NO ve el segmento de memoria compartida del host:

    $ podman run -it shm ipcs -m
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status

    Ejecute un contenedor con la nueva opción --ipc=host, y ahora ve el segmento de memoria compartida del httpd del host:

    $ podman run -it --ipc=host shm ipcs -m
------ Shared Memory Segments --------
clave      shmid      propietario  perms      bytes      nattch     estado
0x01128e25 0          root       600        1000       7

    Probando el modo --ipc=container:id:

    Inicia un contenedor con un programa para crear un segmento de memoria compartida:

    $ podman run -it shm bash
$ sudo shm/shm_server &
$ sudo ipcs -m
------ Segmentos de memoria compartida --------
clave      shmid      propietario  perms      bytes      nattch     estado
0x0000162e 0          root       666        27         1

    Crear un segundo contenedor muestra correctamente que no hay ningún segmento de memoria compartida del primer contenedor:

    $ podman run shm ipcs -m
------ Segmentos de memoria compartida --------
clave      shmid      propietario  perms      bytes      nattch     estado

    Crear un tercer contenedor usando la opción --ipc=container:id, ahora muestra el segmento de memoria compartida del primero:

    $ podman run -it --ipc=container:ed735b2264ac shm ipcs -m
$ sudo ipcs -m
------ Segmentos de memoria compartida --------
clave      shmid      propietario  perms      bytes      nattch     estado
0x0000162e 0          root       666        27         1

    Mapeo de Puertos para Uso Externo

    El puerto expuesto de una aplicación se puede mapear a un puerto del host usando la bandera -p. Por ejemplo, el puerto 80 de httpd se puede mapear al puerto 8080 del host usando lo siguiente:

    $ podman run -p 8080:80 -d -i -t fedora/httpd

    Montaje de Volúmenes Externos

    Para montar un directorio del host como un volumen de contenedor, especifique la ruta absoluta al directorio y la ruta absoluta al directorio del contenedor separadas por dos puntos. Si la fuente es un volumen con nombre mantenido por Podman, se recomienda usar su nombre en lugar de la ruta al volumen. De lo contrario, el volumen se considera huérfano y se elimina con el comando podman volume prune:

    $ podman run -v /var/db:/data1 -i -t fedora bash
$ podman run -v data:/data2 -i -t fedora bash
$ podman run -v /var/cache/dnf:/var/cache/dnf:O -ti fedora dnf -y update

    Si el contenedor necesita un volumen montado escribible por un usuario que no es root dentro del contenedor, use la opción U. Esta opción le dice a Podman que cambie el propietario del volumen de origen para que coincida con el UID y GID predeterminados utilizados dentro del contenedor.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id -v ~/data:/var/lib/mysql:Z,U mariadb

    Alternativamente, si el contenedor necesita un volumen escribible por un usuario que no es root dentro del contenedor, la opción --userns=keep-id permite a los usuarios especificar el UID y GID del usuario que ejecuta Podman a UIDs y GIDs específicos dentro del contenedor. Dado que los procesos que se ejecutan en el contenedor se ejecutan como el UID del usuario, pueden leer/escribir archivos propiedad del usuario.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id:uid=999,gid=999 -v ~/data:/var/lib/mysql:Z mariadb

    Usando las banderas --mount para montar un directorio del host como una carpeta de contenedor, especifique la ruta absoluta al directorio o el nombre del volumen, y la ruta absoluta dentro del directorio del contenedor:

    $ podman run --mount type=bind,src=/var/db,target=/data1 busybox sh
$ podman run --mount type=bind,src=volume-name,target=/data1 busybox sh

    Al usar SELinux, tenga en cuenta que el host no tiene conocimiento de la política SELinux del contenedor. Por lo tanto, en el ejemplo anterior, si la política SELinux está en vigor, el directorio /var/db no es escribible para el contenedor. Ocurre un mensaje de "Permiso denegado" y se agrega un mensaje avc: al syslog del host.

    Para solucionar esto, en el momento de escribir esta página man, se necesita ejecutar el siguiente comando para que se adjunte la etiqueta de tipo de política SELinux adecuada al directorio del host:

    $ chcon -Rt svirt_sandbox_file_t /var/db

    Ahora, escribir en el volumen /data1 en el contenedor está permitido y los cambios se reflejan en el host en /var/db.

    Uso de etiquetado de seguridad alternativo

    Anule el esquema de etiquetado predeterminado para cada contenedor especificando la bandera --security-opt. Por ejemplo, especifique el nivel MCS/MLS, un requisito para sistemas MLS. Especificar el nivel en el siguiente comando permite compartir el mismo contenido entre contenedores.

    podman run --security-opt label=level:s0:c100,c200 -i -t fedora bash

    Un ejemplo de MLS podría ser:

    $ podman run --security-opt label=level:TopSecret -i -t rhel7 bash

    Para deshabilitar el etiquetado de seguridad para este contenedor en lugar de ejecutarlo con la bandera

    --permissive, use el siguiente comando:

    $ podman run --security-opt label=disable -i -t fedora bash

    Refuerce la política de seguridad en los procesos dentro de un contenedor especificando un tipo alternativo para el contenedor. Por ejemplo, ejecute un contenedor al que solo se le permite escuchar en puertos de Apache ejecutando el siguiente comando:

    $ podman run --security-opt label=type:svirt_apache_t -i -t centos bash

    Tenga en cuenta que se debe escribir una política SELinux que defina un tipo svirt_apache_t.

    Para enmascarar rutas adicionales específicas en el contenedor, especifique las rutas separadas por dos puntos usando la opción mask con la bandera --security-opt.

    $ podman run --security-opt mask=/foo/bar:/second/path fedora bash

    Para desenmascarar todas las rutas que están enmascaradas por defecto, establezca la opción unmask en ALL. O para desenmascarar solo rutas específicas, especifique las rutas como se muestra arriba con la opción mask.

    $ podman run --security-opt unmask=ALL fedora bash

    Para desenmascarar todas las rutas que comienzan con /proc, establezca la opción unmask en /proc/*.

    $ podman run --security-opt unmask=/proc/* fedora bash
    $ podman run --security-opt unmask=/foo/bar:/sys/firmware fedora bash

    Establecer el peso del dispositivo mediante la bandera --blkio-weight-device.

    $ podman run -it --blkio-weight-device "/dev/sda:200" ubuntu

    Usar un contenedor podman con entrada de una tubería

    $ echo "asdf" | podman run --rm -i --entrypoint /bin/cat someimage
asdf

    Establecer contenedores separados automáticamente por espacio de nombres de usuario

    # podman run --userns=auto:size=65536 ubi8-micro cat /proc/self/uid_map
0 2147483647      65536
# podman run --userns=auto:size=65536 ubi8-micro cat /proc/self/uid_map
0 2147549183      65536

    Establecer parámetros del kernel con espacios de nombres (Sysctls)

    El --sysctl establece parámetros del kernel con espacios de nombres (sysctls) en el contenedor. Por ejemplo, para habilitar el reenvío de IP en el espacio de nombres de red del contenedor, ejecute este comando:

    $ podman run --sysctl net.ipv4.ip_forward=1 someimage

    Tenga en cuenta que no todos los sysctls tienen espacios de nombres. Podman no soporta el cambio de sysctls dentro de un contenedor que también modifica el sistema host. A medida que el kernel evoluciona, esperamos ver más sysctls con espacios de nombres.

    Consulte la definición de la opción --sysctl anterior para ver la lista actual de sysctls compatibles.

    Establecer mapeo de UID/GID en un nuevo espacio de nombres de usuario

    Ejecutar un contenedor en un nuevo espacio de nombres de usuario requiere un mapeo de los UIDs y GIDs del host.

    $ podman run --uidmap 0:30000:7000 --gidmap 0:30000:7000 fedora echo hello

    Configurar Opciones de Almacenamiento desde la línea de comandos

    Podman permite la configuración del almacenamiento cambiando los valores en el archivo /etc/container/storage.conf o usando opciones globales. Esto muestra cómo usar un almacén de imágenes adicional para una ejecución única de busybox usando opciones globales.

    podman --log-level=debug --storage-opt "additionalimagestore=/tmp/readonly-images" run busybox /bin/sh

    Configurar la zona horaria en un contenedor

    $ podman run --tz=local alpine date
$ podman run --tz=Asia/Shanghai alpine date
$ podman run --tz=US/Eastern alpine date

    Añadir contenedores dependientes

    El primer contenedor, container1, no se inicia inicialmente, pero debe estar en ejecución antes de que se inicie container2. El comando podman run inicia el contenedor automáticamente antes de iniciar container2.

    $ podman create --name container1 -t -i fedora bash
$ podman run --name container2 --requires container1 -t -i fedora bash

    Se pueden requerir múltiples contenedores.

    $ podman create --name container1 -t -i fedora bash
$ podman create --name container2 -t -i fedora bash
$ podman run --name container3 --requires container1,container2 -t -i fedora bash

    Configurar mantener grupos suplementarios para acceder al volumen

    $ podman run -v /var/lib/design:/var/lib/design --group-add keep-groups ubi8

    Configurar el dominio de ejecución para contenedores usando la bandera personality

    $ podman run --name container1 --personality=LINUX32 fedora bash

    Ejecutar un contenedor con rootfs externo montado como overlay

    $ podman run --name container1 --rootfs /path/to/rootfs:O bash

    NAME

    podman-container-run - Run a command in a new container

    SYNOPSIS

    podman container run [-a | --attach] [-d | --detach] [-e | --env] [-p | --publish] [-v | --volume] [--add-host] [--blkio-weight-device] [--cpu-shares] [--cpus] [--entrypoint] [--env-file] [--env-host] [--expose] [--health-cmd] [--health-interval] [--health-retries] [--health-timeout] [--host] [--hostname] [--http-proxy] [--ip] [--kernel-memory] [--label] [--link] [--log-driver] [--mac-address] [--memory] [--memory-swap] [--mount] [--name] [--network] [--no-healthcheck] [--oom-kill-disable] [--pid] [--pull] [--rm] [--rootfs-size] [--security-opt] [--shm-size] [--stop-signal] [--stop-timeout] [--sysctl] [--ulimit] [--userns] [--uts] [--volume-driver] [--volumes-from] [--workdir] <image> [<command>...] [arg ...]

    podman run [-a | --attach] [-d | --detach] [-e | --env] [-p | --publish] [-v | --volume] [--add-host] [--blkio-weight-device] [--cpu-shares] [--cpus] [--entrypoint] [--env-file] [--env-host] [--expose] [--health-cmd] [--health-interval] [--health-retries] [--health-timeout] [--host] [--hostname] [--http-proxy] [--ip] [--kernel-memory] [--label] [--link] [--log-driver] [--mac-address] [--memory] [--memory-swap] [--mount] [--name] [--network] [--no-healthcheck] [--oom-kill-disable] [--pid] [--pull] [--rm] [--rootfs-size] [--security-opt] [--shm-size] [--stop-signal] [--stop-timeout] [--sysctl] [--ulimit] [--userns] [--uts] [--volume-driver] [--volumes-from] [--workdir] <image> [<command>...] [arg ...]

    DESCRIPTION

    Runs a command in a new container. The command is optionally run in a new namespace which is isolated from the host. The new container will have its own filesystem, networking, and process namespace.

    Podman container run is the primary command for running containers. Podman create creates a container but does not run it. podman container start starts an existing container.

    When the container is created, the command specified in the CMD or ENTRYPOINT instruction in the image’s Dockerfile is used. If the ENTRYPOINT is not specified in the image, then the CMD is used as the entrypoint. If neither are specified, then the default command specified in the base image is used. If you specify a command on the podman run command line, it overrides the CMD instruction in the image.

    If the container runs in the foreground, Podman will attach to the container and stream the logs from the container to your terminal. If you detach from the container, Podman will run the container in the background and print the new container’s ID. You can then use podman attach command to attach to the running container, or podman logs to view the logs.

    The container will be automatically removed when it exits if the --rm option is specified.

    IMAGE

    The image argument is the name of the image to use for the container. You can specify the image name in the following formats:

    • name: Retrieves the image from the default registry (e.g., docker.io).
    • name:tag: Retrieves the image with the specified tag from the default registry.
    • registry/name:tag: Retrieves the image from the specified registry.

    If the image is not found locally, Podman will attempt to pull it from the registry configured in /etc/containers/registries.conf.

    If you do not specify a tag, Podman will default to using the latest tag.

    OPTIONS

    -a, --attach
    Attach STDOUT/STDERR to the container. This is the default behavior.
    -d, --detach
    Run container in background and print container ID. If you detach from the container, Podman will run the container in the background and print the new container’s ID. You can then use podman attach command to attach to the running container, or podman logs to view the logs.
    -e, --env
    Give the environment variable value of the container. Pass the environment variable in the following formats: VAR=VAL. You can specify this option multiple times to set multiple environment variables.
    -p, --publish
    Publish a container's port(s) to the host. Pass the port in the following formats:
    • HOSTPORT:CONTAINERPORT
    • IP:HOSTPORT:CONTAINERPORT
    • IP::-CONTAINERPORT
    CONTAINERPORT is the port inside the container. HOSTPORT is the port on the host. If HOSTPORT is not specified, then a random high port on the host is chosen. If IP is not specified, then all network interfaces on the host are used.
    -v, --volume
    Bind mount a volume into the container. Pass the volume in the following formats:
    • HOST-DIR:CONTAINER-DIR
    • HOST-DIR:CONTAINER-DIR:OPTIONS
    • VOLUME-NAME:CONTAINER-DIR
    • VOLUME-NAME:CONTAINER-DIR:OPTIONS
    HOST-DIR is a directory on the host or a named volume. CONTAINER-DIR is the directory in the container. OPTIONS can be ro (read-only) or rw (read-write, default). Named volumes are stored in the Podman host storage area. If HOST-DIR is a relative path, it is interpreted relative to the current working directory.
    --add-host
    Add a hostname mapping to the container’s hosts file. The format is HOST-NAME:IP-ADDRESS.
    --blkio-weight-device
    Block IO Weight (relative weight) in units of 1 to 1000, or if the device weight is 0, it disables block IO contention.
    --cpu-shares
    CPU shares (relative weight). Default is 1024.
    --cpus
    Number of CPUs usable by the container. This is a whole number and defaults to 0 which means unlimited.
    --entrypoint
    Override the default ENTRYPOINT of the image.
    --env-file
    Read environment variables from a file. You can specify this option multiple times to read from multiple files. If a variable is specified multiple times, the last value read will be used.
    --env-host
    Inject the host environment variables into the container. Variables defined in the image or on the command line will override these variables.
    --expose
    Expose a port or a range of ports inside the container. The port can be specified as a port number or a range (e.g., 8080 or 8000-9000). You can specify this option multiple times to expose multiple ports.
    --health-cmd
    The command to run to test the container health.
    --health-interval
    The time interval between checks.
    --health-retries
    The number of retries of the check before the container is considered unhealthy.
    --health-timeout
    The time to wait for the check to complete.
    --host
    Run the container in host mode. This means the container will share the host’s network stack, and host’s process namespace. This is not secure and should only be used when necessary.
    --hostname
    Set the container’s hostname.
    --http-proxy
    Set the proxy environment variables for the container. By default, podman passes the host’s proxy environment variables (http_proxy, https_proxy, ftp_proxy, no_proxy) to the container. This option allows you to override these variables. For example, --http-proxy=false disables the proxy for the container.
    --ip
    Assign a static IP address to the container. This option is only valid if the container is running in a custom network.
    --kernel-memory
    Kernel memory limit.
    --label
    Add metadata to the container. The format is KEY=VALUE.
    --link
    Add link between containers. The format is NAME:ALIAS.
    --log-driver
    Logging driver for the container. Default is json-file.
    --mac-address
    Specify a MAC address for the container.
    --memory
    Memory limit for the container. Can be specified in bytes or with a suffix like b, k, m, g.
    --memory-swap
    Total memory usage limit for the container. This is the sum of memory and swap. Default is unlimited.
    --mount
    Add a mount to the container. The format is type=TYPE,SOURCE=SOURCE,TARGET=TARGET[,OPTIONS]. Supported types are bind, volume, and tmpfs.
    --name
    Assign a name to the container. If a name is not specified, a random name will be generated.
    --network
    Connect container to network(s). See podman-network(5) for more details.
    --no-healthcheck
    Disable healthcheck for the container.
    --oom-kill-disable
    Disable OOM killer for the container.
    --pid
    PID mode for the container. Supported modes are host and container:NAME_or_ID.
    --pull
    Always attempt to pull a newer version of the image. Supported values are always, missing, never. Default is missing.
    --rm
    Automatically remove the container when it exits.
    --rootfs-size
    Set the size of the container root filesystem. Format is SIZE[b|k|m|g].
    --security-opt
    Security option for the container. See podman-container-run(1) for a list of supported options.
    --shm-size
    Size of /dev/shm. Format is SIZE[b|k|m|g].
    --stop-signal
    Signal to send when stopping the container. Default is SIGTERM.
    --stop-timeout
    Time to wait for the container to stop. Default is 10 seconds.
    --sysctl
    Set kernel parameters for the container. Example: --sysctl net.ipv4.ip_forward=1.
    --ulimit
    Ulimit options. Format is TYPE=VALUE[:SOFT[:HARD]].
    --userns
    User namespace to use for the container. Supported values are host, keep-id, and name=NAME.
    --uts
    UTS namespace for the container. Supported values are host and container:NAME_or_ID.
    --volume-driver
    Volume driver for the container. Default is local.
    --volumes-from
    Mount volumes from the specified container(s). The specified containers must be running or stopped.
    --workdir
    Set the working directory for the container.

    Exit Status

    Exit code 0 indicates success, non-zero indicates failure.

    Run a container and attach to it

    Run an alpine container and execute the echo hello world command. The output will be displayed on the terminal.

    $ podman run alpine echo hello world

    Run an alpine container in detached mode. The container ID will be printed to the terminal.

    $ podman run -d alpine sleep 30

    $ podman run -d -p 8080:80 docker.io/nginx

    Rootless Containers

    Podman runs as a non-root user on most systems. This feature requires that a new enough version of shadow-utils be installed. The shadow-utils package must include the newuidmap(1) and newgidmap(1) executables.

    In order for users to run rootless, there must be an entry for their username in /etc/subuid and /etc/subgid which lists the UIDs for their user namespace.

    Rootless Podman works better if the fuse-overlayfs and slirp4netns packages are installed. The fuse-overlayfs package provides a userspace overlay storage driver, otherwise users need to use the vfs storage driver, which can be disk space expensive and less performant than other drivers.

    To enable VPN on the container, slirp4netns or pasta needs to be specified; without either, containers need to be run with the --network=host flag.

    ENVIRONMENT

    Environment variables within containers can be set using multiple different options, in the following order of precedence (later entries override earlier entries):

    • Container image: Any environment variables specified in the container image.
    • --http-proxy: By default, several environment variables are passed in from the host, such as http_proxy and no_proxy. See --http-proxy for details.
    • --env-host: Host environment of the process executing Podman is added.
    • --env-file: Any environment variables specified via env-files. If multiple files are specified, then they override each other in order of entry.
    • --env: Any environment variables specified overrides previous settings.

    Run containers and set the environment ending with a *. The trailing * glob functionality is only active when no value is specified:

    $ export ENV1=a
$ podman run --env 'ENV*' alpine env | grep ENV
ENV1=a
$ podman run --env 'ENV*=b' alpine env | grep ENV
ENV*=b

    CONMON

    When Podman starts a container it actually executes the conmon program, which then executes the OCI Runtime. Conmon is the container monitor. It is a small program whose job is to watch the primary process of the container, and if the container dies, save the exit code. It also holds open the tty of the container, so that it can be attached to later. This is what allows Podman to run in detached mode (backgrounded), so Podman can exit but conmon continues to run. Each container has their own instance of conmon. Conmon waits for the container to exit, gathers and saves the exit code, and then launches a Podman process to complete the container cleanup, by shutting down the network and storage. For more information about conmon, see the conmon(8) man page.
