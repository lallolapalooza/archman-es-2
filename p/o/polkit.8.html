NOMBRE

polkit — Gestor de Autorizaciones

DESCRIPCIÓN GENERAL

polkit proporciona una API de autorización destinada a ser utilizada por programas privilegiados ("MECANISMOS") que ofrecen servicios a programas no privilegiados ("SUJETOS") a menudo a través de algún tipo de mecanismo de comunicación entre procesos. En este escenario, el mecanismo típicamente trata al sujeto como no confiable. Para cada solicitud de un sujeto, el mecanismo necesita determinar si la solicitud está autorizada o si debe rechazar el servicio al sujeto. Utilizando las APIs de polkit, un mecanismo puede descargar esta decisión a una parte confiable: la autoridad polkit.

La autoridad polkit se implementa como un demonio del sistema, polkitd(8), que en sí mismo tiene poco privilegio ya que se ejecuta como el usuario del sistema polkitd. Los mecanismos, sujetos y agentes de autenticación se comunican con la autoridad utilizando el bus de mensajes del sistema.

Además de actuar como autoridad, polkit permite a los usuarios obtener autorización temporal autenticando a un usuario administrativo o al propietario de la sesión a la que pertenece el cliente. Esto es útil para escenarios en los que un mecanismo necesita verificar que el operador del sistema es realmente el usuario o es un usuario administrativo.

ARQUITECTURA DEL SISTEMA

La arquitectura del sistema de polkit se compone de la Autoridad (implementada como un servicio en el bus de mensajes del sistema) y un Agente de Autenticación por sesión de usuario (proporcionado y iniciado por el entorno gráfico del usuario). Las Acciones son definidas por las aplicaciones. Los proveedores, sitios y administradores del sistema pueden controlar la política de autorización a través de las Reglas de Autorización.

AGENTES DE AUTENTICACIÓN

Un agente de autenticación se utiliza para hacer que el usuario de una sesión demuestre que el usuario de la sesión es realmente el usuario (autenticándose como el usuario) o un usuario administrativo (autenticándose como un administrador). Para integrarse bien con el resto de la sesión del usuario (por ejemplo, coincidiendo con el aspecto y la sensación), los agentes de autenticación están diseñados para ser proporcionados por la sesión de usuario que utiliza el usuario. Por ejemplo, un agente de autenticación puede parecerse a esto:

[IMAGEN][4] 
+----------------------------------------------------------+
|                                                          |
|  [Icono] Autenticación requerida                         |
|                                                          |
|          Se requiere autenticación para formatear INTEL  |
|          SSDSA2MH080G1GC (/dev/sda)                      |
|                                                          |
|          Administrador                                   |
|                                                          |
|          Contraseña: [__________________________________]  |
|                                                          |
| [Cancelar]                                [Autenticar] |
+----------------------------------------------------------+

Si el sistema está configurado sin una cuenta de root, puede solicitar la contraseña de un usuario específico designado como usuario administrativo:

[IMAGEN][5] 
+----------------------------------------------------------+
|                                                          |
|  [Icono] Autenticación requerida                         |
|                                                          |
|          Se requiere autenticación para formatear INTEL  |
|          SSDSA2MH080G1GC (/dev/sda)                      |
|                                                          |
|          [Icono] David Zeuthen                           |
|                                                          |
|          Contraseña: [__________________________________]  |
|                                                          |
| [Cancelar]                                [Autenticar] |
+----------------------------------------------------------+

Las aplicaciones que no se ejecutan en un entorno de escritorio (por ejemplo, si se inician desde un inicio de sesión de ssh(1)) pueden no tener un agente de autenticación asociado. Dichas aplicaciones pueden utilizar el tipo PolkitAgentTextListener o la utilidad pkttyagent(1) para que el usuario pueda autenticarse utilizando una interfaz textual.

DECLARANDO ACCIONES

Un mecanismo necesita declarar un conjunto de acciones para poder usar polkit. Las acciones corresponden a operaciones que los clientes pueden solicitar al mecanismo que realice y se definen en archivos XML que el mecanismo instala en el directorio /usr/share/polkit-1/actions.

Las acciones de polkit tienen espacios de nombres y solo pueden contener los caracteres "[A-Z][a-z][0-9].-", por ejemplo, ASCII, dígitos, punto y guion. Cada archivo XML puede contener más de una acción, pero todas las acciones deben estar en el mismo espacio de nombres y el archivo debe nombrarse según el espacio de nombres y tener la extensión .policy.

El archivo XML debe tener la siguiente declaración doctype

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE policyconfig PUBLIC "-//freedesktop//DTD polkit Policy Configuration 1.0//EN"
"http://www.freedesktop.org/software/polkit/policyconfig-1.dtd">

El elemento policyconfig debe estar presente exactamente una vez. Los elementos que se pueden usar dentro de policyconfig incluyen:

vendor

El nombre del proyecto o proveedor que suministra las acciones en el documento XML. Opcional.

vendor_url

Una URL al proyecto o proveedor que suministra las acciones en el documento XML. Opcional.

icon_name

Un icono que representa el proyecto o proveedor que suministra las acciones en el documento XML. El nombre del icono debe cumplir con la Especificación de Nomenclatura de Iconos de Freedesktop.org[6]. Opcional.

action

Un elemento que describe una acción. Cada elemento action debe tener un atributo id que identifique la acción de forma única dentro del espacio de nombres. El valor del atributo id debe seguir las mismas reglas de nomenclatura que los espacios de nombres.

name

Un elemento que describe un nombre para la acción. Este elemento puede contener hasta dos atributos: xml:lang para indicar el idioma del nombre y default para indicar el nombre por defecto si el idioma no está disponible.

description

Un elemento que describe la acción. Este elemento puede contener hasta dos atributos: xml:lang para indicar el idioma de la descripción y default para indicar la descripción por defecto si el idioma no está disponible.

action_scope

Un elemento que indica si la acción es de ámbito local o del sistema. Solo puede ser per_session o per_system. Opcional.

icon_name

Un icono que representa la acción. El nombre del icono debe seguir la Especificación de Nomenclatura de Iconos de Freedesktop.org[6]. Opcional.

menu_path

Un nombre de ruta de menú que puede ser utilizado para mostrar la acción en un menú. Opcional.

menu_path

Un nombre de ruta de menú que puede ser utilizado para mostrar la acción en un menú. Opcional.

allow_active

Un booleano que indica si la acción puede ser autorizada mientras el usuario está activo. Opcional. El valor por defecto es false.

gettext_domain

El dominio gettext que se utilizará para localizar los nombres y descripciones de las acciones. Opcional.

annotate

Un elemento que se puede utilizar para añadir anotaciones a la acción. Este elemento puede contener hasta dos atributos: xml:lang para indicar el idioma de la anotación y default para indicar la anotación por defecto si el idioma no está disponible.

defaults

Un elemento que contiene una lista de elementos default. Cada elemento default contiene un elemento allow_any, allow_inactive o allow_user_managed.

default

Un elemento que especifica una regla por defecto para la acción. Este elemento debe contener uno de los siguientes elementos: allow_any, allow_inactive o allow_user_managed.

allow_any

Un booleano que indica si la acción está permitida para cualquier usuario. Opcional.

allow_inactive

Un booleano que indica si la acción está permitida para usuarios inactivos. Opcional.

allow_user_managed

Un booleano que indica si la acción puede ser gestionada por el usuario. Opcional.

choice

Un elemento que describe una opción para la acción. Cada elemento choice debe tener un atributo id que identifique la opción de forma única dentro de la acción. El valor del atributo id debe seguir las mismas reglas de nomenclatura que las acciones.

text

Un elemento que describe el texto de la opción. Este elemento puede contener hasta dos atributos: xml:lang para indicar el idioma del texto y default para indicar el texto por defecto si el idioma no está disponible.

property

Un elemento que describe una propiedad de la acción. Cada elemento property debe tener un atributo name que identifique la propiedad de forma única dentro de la acción. El valor del atributo name debe seguir las mismas reglas de nomenclatura que las acciones.

type

Un elemento que indica el tipo de la propiedad. Solo puede ser string, int32, uint32, boolean, string-array, int32-array, uint32-array o boolean-array. Obligatorio.

value

Un elemento que especifica el valor de la propiedad. Opcional.

enum

Un elemento que contiene una lista de elementos value que especifican los valores permitidos para la propiedad. Opcional.

Un ejemplo de archivo de acciones se puede encontrar en /usr/share/polkit-1/actions/org.freedesktop.login1.policy.

AUTORIZACIÓN DE ACCIONES

La autorización de acciones se determina mediante un conjunto de reglas que se instalan en los directorios /usr/share/polkit-1/rules.d/, /etc/polkit-1/rules.d/ y /run/polkit-1/rules.d/. Las reglas se escriben en JavaScript y se ejecutan en un motor seguro.

Cada archivo de reglas debe tener la extensión .rules y se ordenará según el nombre del archivo. Las reglas se aplican en el orden en que se aplican y la primera regla que coincida determinará el resultado.

Las reglas tienen acceso a los siguientes objetos:

action

Un objeto que representa la acción que se está autorizando.

subject

Un objeto que representa al sujeto que solicita la acción.

credentials

Un objeto que contiene las credenciales del sujeto.

policy_result

Un objeto que representa el resultado de la autorización.

Las reglas pueden devolver uno de los siguientes valores:

polkit.Result.YES

La acción está permitida.

polkit.Result.NO

La acción está denegada.

polkit.Result.AUTH_ADMIN

Se requiere autenticación de administrador.

polkit.Result.AUTH_SELF

Se requiere autenticación del propio usuario.

polkit.Result.AUTH_ANY

Se requiere autenticación de cualquier usuario.

Un ejemplo de archivo de reglas se puede encontrar en /usr/share/polkit-1/rules.d/00-custom.rules.

DEFINICIONES DE ACCIÓN

Las acciones se definen en archivos XML ubicados en los directorios /usr/share/polkit-1/actions y /etc/polkit-1/actions. Los archivos en /etc/polkit-1/actions anulan los archivos con el mismo nombre en /usr/share/polkit-1/actions. Los archivos de acciones se pueden organizar en subdirectorios.

Las acciones son descriptores para operaciones que requieren privilegios elevados. Por ejemplo, la acción org.freedesktop.policykit.exec describe el acto de ejecutar un programa con privilegios elevados, y la acción org.freedesktop.login-manager.set-password describe el acto de establecer la contraseña de un usuario.

Una acción se define usando el elemento action. El nombre de la acción se especifica usando el atributo id y puede contener solo los caracteres [A-Z][a-z][0-9].-, por ejemplo, ASCII, dígitos, punto e guión. El nombre de la acción debe ser un identificador de objeto D-Bus válido que comienza con un nombre de dominio inverso (por ejemplo, org.freedesktop.policykit).

Los elementos que se pueden usar dentro de action incluyen:

description

Una descripción de la acción legible por humanos, por ejemplo, “Instalar software no firmado”.

message

Un mensaje legible por humanos que se muestra al usuario al solicitar credenciales cuando se necesita autenticación, por ejemplo, “La instalación de software no firmado requiere autenticación”.

defaults

Este elemento se utiliza para especificar autorizaciones implícitas para los clientes. Los elementos que se pueden usar dentro de defaults incluyen:

allow_any

Autorizaciones implícitas que se aplican a cualquier cliente. Opcional.

allow_inactive

Autorizaciones implícitas que se aplican a clientes en sesiones inactivas en consolas locales. Opcional.

allow_active

Autorizaciones implícitas que se aplican a clientes en sesiones activas en consolas locales. Opcional.

Cada uno de los elementos allow_any, allow_inactive y allow_active puede contener los siguientes valores:

no

No autorizado.

yes

Autorizado.

auth_self

Se requiere autenticación por parte del propietario de la sesión de la que se origina el cliente. Tenga en cuenta que esto no es lo suficientemente restrictivo para la mayoría de los usos en sistemas multiusuario; generalmente se recomiendan auth_admin*.

auth_admin

Se requiere autenticación por parte de un usuario administrativo.

auth_self_keep

Al igual que auth_self, pero la autorización se mantiene durante un breve período (por ejemplo, cinco minutos). La advertencia sobre auth_self anterior se aplica de la misma manera.

auth_admin_keep

Al igual que auth_admin, pero la autorización se mantiene durante un breve período (por ejemplo, cinco minutos).

annotate

Se utiliza para anotar una acción con un par clave/valor. La clave se especifica usando el atributo key y el valor se especifica usando el atributo value. Este elemento puede aparecer cero o más veces. Consulte a continuación las anotaciones conocidas.

vendor

Se utiliza para anular el proveedor en una base por acción. Opcional.

vendor_url

Se utiliza para anular la URL del proveedor en una base por acción. Opcional.

icon_name

Se utiliza para anular el nombre del icono en una base por acción. Opcional.

Para la localización, los elementos description y message pueden aparecer varias veces con diferentes atributos xml:lang.

Para enumerar las acciones de polkit instaladas, utilice el comando pkaction(1).

Anotaciones conocidas

El programa pkexec incluido con polkit utiliza la anotación org.freedesktop.policykit.exec.path; consulte la página del manual de pkexec(1) para obtener más detalles.

La anotación org.freedesktop.policykit.imply (su valor es una cadena que contiene una lista de identificadores de acción separados por espacios) se puede utilizar para definir *meta acciones*. La forma en que funciona es que si un sujeto está autorizado para una acción con esta anotación, entonces también está autorizado para cualquier acción especificada por la anotación. Un uso típico de esta anotación es cuando se define una shell de interfaz de usuario con un único botón de bloqueo que debe desbloquear múltiples acciones de distintos mecanismos.

La anotación org.freedesktop.policykit.owner se puede utilizar para definir un conjunto de usuarios que pueden consultar si un cliente está autorizado para realizar esta acción. Si esta anotación no se especifica, entonces solo root puede consultar si un cliente que se ejecuta como otro usuario está autorizado para una acción. El valor de esta anotación es una cadena que contiene una lista de entradas PolkitIdentity separadas por espacios, por ejemplo, “unix-user:42 unix-user:colord”. Un uso típico de esta anotación es para un proceso demonio que se ejecuta como un usuario del sistema en lugar de root.

REGLAS DE AUTORIZACIÓN

polkitd lee los archivos .rules de los siguientes directorios en este orden:

•/etc/polkit-1/rules.d
•/run/polkit-1/rules.d
•/usr/local/share/polkit-1/rules.d
•/usr/share/polkit-1/rules.d

Estos directorios se procesan en orden léxico según el nombre base de cada archivo. Si hay un empate, los archivos en directorios anteriores en la lista se procesan primero. Por ejemplo, para los siguientes cuatro archivos, el orden es:

•/etc/polkit-1/rules.d/10-auth.rules
•/run/polkit-1/rules.d/10-auth.rules
•/usr/local/share/polkit-1/rules.d/10-auth.rules
•/usr/share/polkit-1/rules.d/10-auth.rules

Todos estos directorios son monitoreados, por lo que si se modifica, agrega o elimina un archivo de reglas, las reglas existentes se eliminan y se vuelven a leer y procesar todos los archivos. Los archivos de reglas están escritos en el lenguaje de programación JavaScript[7] y se interconectan con polkitd a través del objeto global polkit (de tipo Polkit).

Si bien el intérprete de JavaScript utilizado en versiones particulares de polkit puede admitir características no estándar (como la palabra clave *let*), las reglas de autorización deben cumplir con ECMA-262 edición 5[8] (en otras palabras, el intérprete de JavaScript utilizado puede cambiar en versiones futuras de polkit).

Las reglas de autorización están destinadas a dos audiencias específicas:

•Administradores del sistema
•Sistemas Operativos / Entornos de propósito especial

y solo a esas audiencias. En particular, las aplicaciones, los mecanismos y los sistemas operativos de propósito general nunca deben incluir reglas de autorización.

El tipo Polkit

Los siguientes métodos están disponibles en el objeto polkit:

void addRule(polkit.Result function(action, subject) {...});

void addAdminRule(string[] function(action, subject) {...});

void log(string message);

string spawn(string[] argv);

El método addRule() se utiliza para agregar una función que puede ser llamada cada vez que se realiza una verificación de autorización para *action* y *subject*. Las funciones se llaman en el orden en que se han agregado hasta que una de las funciones devuelve un valor. Por lo tanto, para agregar una regla de autorización que se procese antes que otras reglas, colóquela en un archivo en /etc/polkit-1/rules.d con un nombre que se ordene antes que otros archivos de reglas, por ejemplo, 00-early-checks.rules. Cada función debería devolver un valor de polkit.Result

polkit.Result = {
    NO              : "no",
    YES             : "yes",
    AUTH_SELF       : "auth_self",
    AUTH_SELF_KEEP  : "auth_self_keep",
    AUTH_ADMIN      : "auth_admin",
    AUTH_ADMIN_KEEP : "auth_admin_keep",
    NOT_HANDLED     : null
};

correspondiente a los valores que se pueden usar como valores predeterminados. Si la función devuelve polkit.Result.NOT_HANDLED, null, undefined o no devuelve ningún valor, se prueba la siguiente función de usuario.

Tenga en cuenta que si se devuelve polkit.Result.AUTH_SELF_KEEP o polkit.Result.AUTH_ADMIN_KEEP, las verificaciones de autorización para el mismo identificador de acción y sujeto tendrán éxito (es decir, devolverán polkit.Result.YES) durante el próximo breve período (por ejemplo, cinco minutos) *incluso* si las variables pasadas junto con la verificación son diferentes. Por lo tanto, si el resultado de una regla de autorización depende de tales variables, no debe usar las constantes *"*_KEEP"* (si se requiere funcionalidad similar, la regla de autorización puede implementar fácilmente autorizaciones temporales utilizando el tipo Date[9] para marcas de tiempo).

El método addAdminRule() se utiliza para agregar una función que puede ser llamada cada vez que se requiere autenticación de administrador. La función se utiliza para especificar qué identidades se pueden utilizar para la autenticación de administrador para la verificación de autorización identificada por *action* y *subject*. Las funciones agregadas se llaman en el orden en que se han agregado hasta que una de las funciones devuelve un valor. Cada función debe devolver una matriz de cadenas donde cada cadena tiene el formato “unix-group:<grupo>”, “unix-netgroup:<netgroup>” o “unix-user:<usuario>”. Si la función devuelve null, undefined o no devuelve ningún valor, se prueba la siguiente función.

No hay garantía de que una función registrada con addRule() o addAdminRule() sea llamada alguna vez; por ejemplo, un archivo de reglas temprano podría registrar una función que siempre devuelve un valor, asegurando así que las funciones agregadas posteriormente nunca se llamen.

Si el código proporcionado por el usuario tarda mucho en ejecutarse, no se lanzará ninguna excepción y el script se cerrará de inmediato (el límite actual es de 15 segundos). Esto se utiliza para detectar scripts que se ejecutan sin control.

El método spawn() inicia un ayudante externo identificado por el vector de argumentos *argv* y espera a que termine. Si ocurre un error o el ayudante no termina normalmente con el código de salida 0, se lanza una excepción. Si el ayudante no termina dentro de los 10 segundos, se cierra. De lo contrario, la *salida estándar* del programa se devuelve como una cadena. El método spawn() debe usarse con moderación, ya que los ayudantes pueden tardar mucho o una cantidad indeterminada de tiempo en completarse y ninguna otra verificación de autorización puede manejarse mientras el ayudante se está ejecutando. Tenga en cuenta que los programas iniciados se ejecutarán como el usuario del sistema *polkitd* sin privilegios.

El método log() escribe el *mensaje* dado en el registrador del sistema prefijado con el nombre del archivo JavaScript y el número de línea. Las entradas del registro se emiten utilizando el indicador LOG_AUTHPRIV, lo que significa que las entradas del registro generalmente terminan en el archivo /var/log/secure. El método log() generalmente solo se usa al depurar reglas. Los tipos Action y Subject tienen métodos toString() adecuados definidos para facilitar el registro, por ejemplo,

polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.policykit.exec")
{ polkit.log("action=" + action); polkit.log("subject=" + subject); } });

producirá lo siguiente cuando el usuario ejecute 'pkexec -u bateman bash -i' desde una shell:

May 24 14:28:50 thinkpad polkitd[32217]: /etc/polkit-1/rules.d/10-test.rules:3: action=[Action id='org.freedesktop.policykit.exec' command_line='/usr/bin/bash -i' program='/usr/bin/bash' user='bateman' user.gecos='Patrick Bateman' user.display='Patrick Bateman (bateman)']
May 24 14:28:50 thinkpad polkitd[32217]: /etc/polkit-1/rules.d/10-test.rules:4: subject=[Subject pid=1352 user='davidz' groups=davidz,wheel, seat='seat0' session='1' local=true active=true]

El tipo Action

El parámetro action pasado a las funciones de usuario es un objeto con información sobre la acción que se está comprobando. Es de tipo Action y tiene el siguiente atributo:

string id

El identificador de la acción, por ejemplo org.freedesktop.policykit.exec.

Los siguientes métodos están disponibles en el tipo Action:

string lookup(string key);

El método lookup() se utiliza para buscar las variables de polkit pasadas desde el mecanismo. Por ejemplo, el mecanismo de pkexec(1) establece la variable program que se puede obtener en JavaScript utilizando la expresión action.lookup("program"). Si no hay ningún valor para la key dada, se devolverá undefined.

Consulte la documentación de cada mecanismo para ver qué variables están disponibles para cada acción.

El tipo Subject

El parámetro subject pasado a las funciones de usuario es un objeto con información sobre el proceso que se está comprobando. Es de tipo Subject y tiene los siguientes atributos

int pid

El ID del proceso.

string user

El nombre de usuario.

string[] groups

Matriz de grupos a los que pertenece el usuario user.

string seat

El asiento al que está asociado el sujeto; en blanco si no está en un asiento local.

string session

La sesión a la que está asociado el sujeto.

string system_unit

La unidad systemd de la que forma parte el proceso del sujeto (si la hay). Tenga en cuenta que solo puede coincidir con unidades del sistema, ya que las unidades de usuario pueden crearse con cualquier nombre sin privilegios (a diferencia de las unidades del sistema que requieren root para crearse). Un proceso que se ejecuta en una unidad de usuario devolverá la unidad de sesión del usuario en este atributo (por ejemplo: user-1000.service).

boolean local

Establecido en true solo si el asiento es local.

boolean no_new_privileges

Establecido solo si system_unit no está vacío, y establecido en true solo si la unidad de servicio systemd referenciada tiene habilitada la configuración NoNewPrivileges=. Esto garantiza que el proceso no pueda obtener nuevos privilegios ejecutando binarios setuid.

boolean active

Establecido en true solo si la sesión está activa.

Los siguientes métodos están disponibles en el tipo Subject:

boolean isInGroup(string groupName);

boolean isInNetGroup(string netGroupName);

El método isInGroup() se puede usar para comprobar si el sujeto está en un grupo dado y isInNetGroup() se puede usar para comprobar si el sujeto está en un netgroup dado.

Ejemplos de Reglas de Autorización

Permitir que todos los usuarios del grupo admin realicen administración de usuarios sin cambiar la política para otros usuarios:

polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.accounts.user-administration" &&
        subject.isInGroup("admin")) {
        return polkit.Result.YES;
    }
});

Definir usuarios administrativos como los usuarios del grupo wheel:

polkit.addAdminRule(function(action, subject) {
    return ["unix-group:wheel"];
});

Prohibir a los usuarios del grupo children cambiar la configuración del nombre de host (es decir, cualquier acción con un identificador que comience por org.freedesktop.hostname1.) y permitir que cualquier otro lo haga después de autenticarse como ellos mismos:

polkit.addRule(function(action, subject) {
    if (action.id.indexOf("org.freedesktop.hostname1.") == 0) {
        if (subject.isInGroup("children")) {
            return polkit.Result.NO;
        } else {
            return polkit.Result.AUTH_SELF_KEEP;
        }
    }
});

Ejecutar un ayudante externo para determinar si el usuario actual puede reiniciar el sistema:

polkit.addRule(function(action, subject) {
    if (action.id.indexOf("org.freedesktop.login1.reboot") == 0) {
        try {
            // user-may-reboot sale con éxito (código de salida 0)
            // solo si el nombre de usuario pasado está autorizado
            polkit.spawn(["/opt/company/bin/user-may-reboot",
                          subject.user]);
            return polkit.Result.YES;
        } catch (error) {
            // No, pero permitir la autenticación de administrador
            return polkit.Result.AUTH_ADMIN;
        }
    }
});

El siguiente ejemplo muestra cómo la decisión de autorización puede depender de las variables pasadas por el mecanismo de pkexec(1):

polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.policykit.exec" &&
        action.lookup("program") == "/usr/bin/cat") {
        return polkit.Result.AUTH_ADMIN;
    }
});

El siguiente ejemplo muestra otro uso de variables pasadas desde el mecanismo. En este caso, el mecanismo es UDisks[10] que define un conjunto de acciones y variables[11] que se utiliza para coincidir:

// Permitir a los usuarios del grupo 'engineers' realizar cualquier operación en
// algunas unidades sin tener que autenticarse
//
polkit.addRule(function(action, subject) {
    if (action.id.indexOf("org.freedesktop.udisks2.") == 0 &&
        action.lookup("drive.vendor") == "SEAGATE" &&
        action.lookup("drive.model") == "ST3300657SS" &&
        subject.isInGroup("engineers")) {
            return polkit.Result.YES;
        }
    }
});

Permitir que todos los procesos que se ejecutan como parte de la unidad del sistema systemd admin.service realicen administración de usuarios, siempre que no puedan obtener nuevos privilegios:

polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.accounts.user-administration" &&
        subject.system_unit == "admin.service" &&
        subject.no_new_privileges) {
        return polkit.Result.YES;
    }
});
