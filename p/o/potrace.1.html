NOMBRE

potrace - transforma mapas de bits en gráficos vectoriales.

SINOPSIS

potrace [opciones] [archivo...]

DESCRIPCIÓN

potrace es una herramienta para trazar mapas de bits, lo que significa transformar un mapa de bits en una imagen escalable y suave. La entrada es un mapa de bits, es decir, una imagen basada en píxeles compuesta únicamente por los dos colores blanco y negro. La salida es SVG, PDF, EPS o uno de varios otros formatos vectoriales. Un uso típico es crear gráficos vectoriales a partir de datos escaneados, como logotipos de empresas o universidades, notas escritas a mano, etc. La imagen resultante no es "dentada" como un mapa de bits, sino suave. Puede renderizarse a cualquier resolución.

potrace puede leer mapas de bits en los siguientes formatos: PBM, PGM, PPM (colectivamente conocidos como PNM, ver pnm(5)), así como BMP (formatos de mapa de bits de Windows y OS/2). La imagen de entrada solo debe utilizar los dos colores, blanco y negro. Si aparecen otros valores de píxel en la entrada, se convertirán a blanco y negro utilizando un método de umbralización simple.

potrace puede producir actualmente los siguientes formatos de salida: SVG, PDF, EPS, PostScript, DXF, GeoJSON, PGM, Gimppath y XFig. Es posible que se añadan más backends en el futuro.

OPCIONES

Se admiten las siguientes opciones. Las dimensiones (argumentos de tipo dim) pueden tener unidades opcionales, por ejemplo, 6.5in, 15cm, 100pt. La unidad predeterminada son las pulgadas (o centímetros, si se configuró en el momento de la compilación, consulte CONFIGURACIÓN EN TIEMPO DE COMPILACIÓN a continuación). Para formatos de salida basados en píxeles como PGM, DXF, GeoJSON y Gimppath, la unidad predeterminada son los píxeles.

Opciones generales:

-h, --help
muestra el mensaje de ayuda y sale.
-v, --version
muestra la información de la versión y sale. Esto también muestra los valores predeterminados que se compilaron en esta versión de potrace.
-l, --license
muestra la información de la licencia y sale.

Opciones de entrada/salida:

archivo
Cada archivo puede contener una imagen de entrada, o varias imágenes concatenadas. Si se proporcionan argumentos de archivo, entonces potrace creará por defecto un archivo de salida por cada nombre de archivo de entrada dado. El nombre del archivo de salida se obtiene del nombre del archivo de entrada cambiando su extensión según el backend elegido. Si cambiar la extensión no es posible porque los nombres de los archivos de entrada y salida serían idénticos, entonces el nombre del archivo de salida se crea añadiendo la extensión "-out" al nombre del archivo de entrada. Si no se proporcionan argumentos de nombre de archivo, entonces potrace actúa como un filtro, leyendo de la entrada estándar y escribiendo en la salida estándar. Se puede dar un nombre de archivo de "-" para especificar la lectura desde la entrada estándar.
-o archivo, --output archivo
escribe la salida a este archivo. Toda la salida se dirige al archivo especificado. Si se utiliza esta opción, entonces los nombres de archivo de entrada múltiples solo están permitidos para backends multipágina (ver TIPOS DE BACKEND a continuación). En este caso, cada archivo de entrada puede contener uno o más mapas de bits, y todos los mapas de bits de todos los archivos de entrada se procesan y la salida se concatena en un solo archivo. Se puede dar un nombre de archivo de "-" para especificar la escritura en la salida estándar.
--
Fin de las opciones. Cualquier argumento restante se interpreta como nombres de archivo. Esto también deshabilita el modo de filtro, incluso si no se dan nombres de archivo. Esto es útil para scripts de shell, porque potrace -- $NOMBRES_DE_ARCHIVO se comportará correctamente incluso con una lista vacía de nombres de archivo. Sin embargo, -- con una lista vacía de nombres de archivo no está permitido en conjunción con la opción -o, ya que esto generaría un documento de cero páginas, lo cual ningún backend permite.

Selección de backend:

Para obtener información general, consulte también TIPOS DE BACKEND a continuación.

-b nombre, --backend nombre
Selecciona el backend por nombre, donde nombre es uno de eps, postscript, ps, pdf, pdfpage, svg, dxf, geojson, pgm, gimppath, xfig. Los nombres de backend se pueden abreviar con un prefijo siempre que sea inequívoco. Los nombres de backend no distinguen entre mayúsculas y minúsculas.
-s, --svg, -b svg, --backend svg
Backend SVG. La salida es un archivo de Gráficos Vectoriales Escalables (SVG). Este es un backend de una sola página, de tamaño variable, basado en dimensiones. Tenga en cuenta que a menos que se proporcione la opción -r, se asume una resolución de 72 ppp para el mapa de bits de entrada.
-b pdf, --backend pdf
Backend PDF. La salida es un archivo en formato PDF (Portable Document Format). Si la entrada consta de varios mapas de bits, cada uno se renderiza en una página separada. Este es un backend multipágina, de tamaño variable, basado en dimensiones.
-b pdfpage, --backend pdfpage
El backend PDFPage es similar al backend PDF, excepto que tiene un tamaño fijo como el backend PostScript.
-e, --eps, -b eps, --backend eps
Backend EPS (predeterminado). La salida es un archivo PostScript encapsulado (EPS). Este es un backend de una sola página, de tamaño variable, basado en dimensiones.
-p, --postscript, -b ps, --backend ps
Backend PostScript. La salida es un archivo PostScript. Este es un backend multipágina, de tamaño fijo, basado en dimensiones. Si la entrada consta de varios mapas de bits, cada uno se renderiza en una página separada.
-b dxf, --backend dxf
Backend DXF. La salida es un archivo en formato Drawing Interchange Format (DXF). En este backend, todas las curvas de Bézier se aproximan mediante arcos circulares a trozos; esto es adecuado para el procesamiento en software CAD o para aplicaciones de mecanizado que utilizan herramientas CNC. Este es un backend de una sola página, de tamaño variable, basado en píxeles. La opción -u no tiene efecto para este backend.
-b geojson, --backend geojson
Backend GeoJSON. La salida es un archivo en el formato utilizado por algunas aplicaciones que procesan datos geográficos. En este backend, todas las curvas de Bézier se aproximan mediante 8 segmentos de línea recta. Este es un backend de una sola página, de tamaño variable, basado en píxeles. La opción -u no tiene efecto para este backend.
-g, --pgm, -b pgm, --backend pgm
Backend PGM. La salida es un archivo portable greymap (PGM). Es un backend conveniente para el suavizado de imágenes de mapa de bits (antialiasing). Este es un backend multipágina, de tamaño variable, basado en píxeles. Si la entrada consta de más de una imagen, las imágenes se concatenan en la salida.
-b gimppath, --backend gimppath
Backend Gimppath. Este backend produce una salida adecuada para ser importada como ruta por el programa GIMP (GNU Image Manipulation Program) (en el diálogo Capas, Canales y Rutas, seleccione Rutas, haga clic derecho y seleccione Importar Ruta). La salida es en realidad un archivo SVG. Las diferencias con el backend SVG son: la opción --opaque no tiene efecto, la opción --flat está siempre activada y las dimensiones se basan en píxeles. Este es un backend de una sola página, de tamaño variable, basado en píxeles.
-b xfig, --backend xfig
Backend XFig. Este es un backend de una sola página, de tamaño fijo, basado en dimensiones. La salida es un archivo en formato XFig. Tenga en cuenta que XFig utiliza X-splines en lugar de curvas de Bézier, por lo que no es posible traducir la salida de potrace al formato XFig con precisión absoluta. Este backend realiza una aproximación razonable utilizando dos puntos de control para cada segmento de curva de Bézier. La opción -u no tiene efecto para este backend, ya que los puntos de control siempre se redondean a la centésima parte más cercana de una pulgada en XFig. La optimización de curvas está deshabilitada. Implica --opaque.

-z política, --turnpolicy política
especifica cómo resolver ambigüedades en la descomposición de la ruta. Debe ser una de las opciones: black, white, right, left, minority, majority, o random. El valor predeterminado es minority. Las políticas de giro se pueden abreviar con un prefijo inequívoco, por ejemplo, se puede especificar min en lugar de minority.
-t n, --turdsize n
suprime pequeñas manchas de hasta este número de píxeles.
-a n, --alphamax n
establece el parámetro de umbral de esquinas. El valor predeterminado es 1. Cuanto menor sea este valor, más esquinas agudas se producirán. Si este parámetro es 0, no se realizará ningún suavizado y la salida será un polígono. Si este parámetro es mayor que 4/3, se suprimen todas las esquinas y la salida es completamente suave.
-n, --longcurve
desactiva la optimización de curvas. Normalmente, **potrace** intenta unir segmentos de curva de Bézier adyacentes cuando es posible. Esta opción deshabilita este comportamiento, lo que resulta en un tamaño de archivo mayor.
-O n, --opttolerance n
establece la tolerancia de optimización de curvas. El valor predeterminado es 0.2. Valores mayores permiten que más segmentos de curva de Bézier consecutivos se unan en un solo segmento, a expensas de la precisión.
-u n, --unit n
establece la cuantificación de la salida. Las coordenadas en la salida se redondean a 1/unidad de píxeles. El valor predeterminado de 10 generalmente produce buenos resultados. Para algunos de los modos de depuración, un valor de 100 proporciona una salida más precisa. Esta opción no tiene efecto para el backend XFig, que siempre rasteriza a 1/1200 de pulgada, ni para el backend DXF. Para el backend GeoJSON, esta opción es solo una sugerencia; el redondeo real puede ser más, pero no menos, preciso que el especificado.
-d n, --debug n
produce salida de depuración del tipo n. Esto tiene diferentes efectos para diferentes backends. Para los backends PostScript/EPS, los valores n=1,2,3 ilustran las etapas intermedias del algoritmo de **potrace**.

Opciones de escalado y colocación:

-P formato, --pagesize formato
para backends de tamaño fijo, establece el tamaño de la página. Se pueden especificar los siguientes formatos: A4, A3, A5, B5, Letter, Legal, Tabloid, Statement, Executive, Folio, Quarto, 10x14. Los nombres de formato no distinguen entre mayúsculas y minúsculas. Además, se acepta un argumento de la forma dimxdim para especificar dimensiones arbitrarias. El tamaño de página predeterminado es Letter (o A4, si se configuró en tiempo de compilación, ver CONFIGURACIÓN EN TIEMPO DE COMPILACIÓN a continuación). Los nombres de formato de página se pueden abreviar con un prefijo siempre que sea inequívoco. Esta opción no tiene efecto para backends de tamaño variable.
-W dim, --width dim
establece el ancho de la imagen de salida (antes de cualquier rotación y márgenes). Si solo se especifica uno de los anchos y altos, el otro se ajustará en consecuencia para preservar la relación de aspecto.
-H dim, --height dim
establece la altura de la imagen de salida. Ver **-W** para más detalles.
-r n[xn], --resolution n[xn]
para backends basados en dimensiones, establece la resolución (en dpi). Una pulgada en la imagen de salida corresponde a esta cantidad de píxeles en la entrada. Tenga en cuenta que un valor mayor resulta en una imagen de salida más pequeña. Es posible especificar resoluciones separadas en las direcciones x e y dando un argumento de la forma nxn. Para backends de tamaño variable, la resolución predeterminada es 72 dpi. Para backends de tamaño fijo, no hay resolución predeterminada; la imagen se escala por defecto para caber en la página. Esta opción no tiene efecto para backends basados en píxeles. Si se especifican **-W** o **-H**, tienen prioridad.
-x n[xn], --scale n[xn]
para backends basados en píxeles, establece el factor de escala. Un valor mayor que 1 amplía la salida, un valor entre 0 y 1 hace que la salida sea más pequeña. El valor predeterminado es 1. Es posible especificar factores de escala separados para las direcciones x e y dando un argumento de la forma nxn. Esta opción no tiene efecto para backends basados en dimensiones. Si se especifican **-W** o **-H**, tienen prioridad.
-S n, --stretch n
establece la relación de aspecto. Un valor mayor que 1 significa que la imagen se estirará en la dirección y. Un valor entre 0 y 1 significa que la imagen se comprimirá en la dirección y.
-A ángulo, --rotate ángulo
establece el ángulo de rotación (en grados). La salida se rotará en sentido contrario a las agujas del reloj en este ángulo. Esto es útil para compensar imágenes que se escanearon no perfectamente rectas.
-M dim, --margin dim
establece los cuatro márgenes. El efecto y el valor predeterminado de esta opción dependen del backend. Para backends de tamaño variable, los márgenes simplemente se agregarán alrededor de la imagen de salida (o se restarán, en caso de márgenes negativos). El margen predeterminado para estos backends es 0. Para backends de tamaño fijo, la configuración de márgenes puede utilizarse para controlar la colocación de la imagen en la página. Si solo se proporciona uno de los márgenes izquierdo y derecho, la imagen se colocará a esta distancia del borde respectivo de la página, y de manera similar para la parte superior e inferior. Si se proporcionan márgenes en lados opuestos, la imagen se escala para que quepa entre estos márgenes, a menos que la escala ya esté determinada explícitamente por una o más de las opciones **-W**, **-H**, **-r** o **-x**. Por defecto, los backends de tamaño fijo utilizan un margen no nulo cuyo ancho depende del tamaño de la página.
-L dim, --leftmargin dim
establece el margen izquierdo. Ver **-M** para más detalles.
-R dim, --rightmargin dim
establece el margen derecho. Ver **-M** para más detalles.
-T dim, --topmargin dim
establece el margen superior. Ver **-M** para más detalles.
-B dim, --bottommargin dim
establece el margen inferior. Ver **-M** para más detalles.
--tight
elimina el espacio en blanco alrededor de la imagen antes de aplicar el escalado y los márgenes. Si se proporciona esta opción, los cálculos del ancho, alto y márgenes se basan en el contorno vectorial real, en lugar de las dimensiones exteriores del píxel de entrada, que es el valor predeterminado. En particular, la opción **--tight** se puede utilizar para eliminar cualquier margen existente de la imagen de entrada. Ver el archivo placement.pdf para una ilustración más detallada.

Opciones de color:

Estas opciones solo son compatibles con ciertos backends. Los backends DXF y GeoJSON no admiten color.

-C #rrggbb, --color #rrggbb
establece el color de primer plano de la imagen de salida. El valor predeterminado es negro.
--fillcolor #rrggbb
establece el color de relleno de la imagen de salida, es decir, el color de las partes "blancas" que están encerradas por partes "negras". El valor predeterminado es dejar estas partes transparentes. Implica **--opaque**. Tenga en cuenta que esta opción establece el color de fondo; para establecer el color de primer plano, use **--color** en su lugar.
--opaque
rellena las partes blancas de la imagen de forma opaca, en lugar de dejarlas transparentes. Esto solo se aplica a las partes blancas interiores, es decir, aquellas que están encerradas dentro de un borde negro. La opacidad está siempre activa para el backend XFig.

Opciones de SVG:

--group
para salida SVG, intenta agrupar rutas relacionadas. Cada ruta se agrupa con todas las rutas que están contenidas dentro de ella, para que puedan moverse como una unidad con un editor SVG. Esto hace que colorear componentes individuales sea un poco más engorroso, y por lo tanto no es el valor predeterminado.
--flat
para salida SVG, coloca toda la imagen en una sola ruta. Esto hace imposible colorear los componentes individualmente, y por lo tanto no es el valor predeterminado. Pero el archivo SVG resultante puede ser importado más fácilmente por algunas aplicaciones como Gimp. De hecho, el backend Gimppath es una variación del backend SVG con la opción **--flat** y escalado basado en píxeles. La opción **--flat** no tiene efecto si se ha seleccionado **--opaque**.

Opciones de PostScript/EPS/PDF:

-c, --cleartext
no comprime la salida. Esta opción deshabilita el uso de filtros de compresión en la salida PostScript y PDF. En el backend PostScript, si se usan **-c** y **-q** juntos, la salida resultante puede ser leída fácilmente por otros programas o incluso por humanos.
-2, --level2
usa compresión PostScript nivel 2 (predeterminado). El tamaño del archivo resultante es aproximadamente un 40% menor que si se usa la opción **-c**.
-3, --level3
usa compresión PostScript nivel 3, si está disponible. Esto da archivos ligeramente más pequeños que usando **-2**, pero los archivos resultantes pueden no imprimirse en impresoras PostScript nivel 2 antiguas. Si el soporte para compresión PostScript nivel 3 se ha deshabilitado en tiempo de compilación, se muestra un mensaje de advertencia y se utiliza compresión nivel 2 en su lugar.
-q, --longcoding
desactiva la codificación numérica optimizada en la salida PostScript. Normalmente, **potrace** utiliza un formato numérico muy compacto para representar curvas de Bézier en PostScript, aprovechando la redundancia existente en los parámetros de la curva. Esta opción deshabilita este comportamiento, resultando en un código más largo, pero

OPTIONS

The following options are available:

General options:

-b backend, --backend backend
generate output in the specified backend format. The available backends are:
  • svg: Scalable Vector Graphics.
  • eps: Encapsulated PostScript.
  • pdf: Portable Document Format.
  • gem: Generic EPS Metafile.
  • ps: PostScript.
  • txt: ASCII art.
  • fig: FIGures.
  • gimppath: GIMP paths.
  • dxf: Drawing Exchange Format.
  • geojson: GeoJSON.
  • pnm: Portable AnyMap format.
-c, --clean
remove adjacent cubic Bezier curves that are collinear. This can make output files smaller and more readable (particularly if the -c option is also used).

PGM options:

-G n, --gamma n
set the gamma value for anti-aliasing (default is 2.2). Most computer displays do not render shades of grey linearly, i.e., a grey value of 0.5 is not displayed as being exactly half-way between black and white. The gamma parameter corrects for this, and therefore leads to nicer looking output. The default value of 2.2 is appropriate for most normal CRT displays.

Frontend options:

-k n, --blacklevel n
set the threshold level for converting input images to bitmaps. The potrace algorithm expects a bitmap, thus all pixels of the input images are converted to black or white before processing begins. Pixels whose brightness is less than n are converted to black, all other pixels to white. Here n is a number between 0 and 1. One case is treated specially: if the input is in an indexed color format with exactly 2 colors, then the blacklevel is ignored and the darker of the two colors is mapped to black.

Note: the method used by potrace for converting greymaps to bitmaps is very crude; much better results can be obtained if a separate program, such as mkbitmap(1), is used for this purpose. In particular, mkbitmap(1), which is distributed with potrace, has the ability to scale and interpolate the image before thresholding, which results in much better preservation of detail.

-i, --invert
invert the input bitmap before processing.

Progress bar options:

--progress
display a progress bar for each bitmap that is processed. This is useful for interactive use. The default behavior is not to show any progress information.
--tty mode
set the terminal mode for progress bar rendering. Possible values are "vt100", which requires a vt100-compatible terminal, and "dumb", which uses only ASCII characters. The default is system dependent.

BACKEND TYPES

Backends can be classified in several ways, which affects the available command line options and their behavior:

Fixed-size or variable-sized:
For fixed-size backends, the size of the page is always the same (for example Letter or A4, as specified at compile time or by the -P option). By default, the image will be centered and scaled to fit the page size. For variable-size backends, the size of the page follows the size of the image. Currently the PostScript (PS), PDFPage, and XFig backends are fixed-size, and the remaining backends are variable-size.
Dimension-based or pixel-based:
In dimension-based backends, distances are measured in physical units such as inches or centimeters. In pixel-based backends, distances are measured in pixel units. The -r option only works for dimension-based backends, and the -x option only works for pixel-based backends. Currently, the DXF, PGM, Gimppath, and GeoJSON backends are pixel-based, and the remaining backends are dimension-based. Currently, all pixel-based backends are variable-sized.
Single-page or multi-page:
Single-page backends can only accept a single image. Multi-page backends can accept multiple images, typically one per page of output. Currently, the PostScript (PS), PDF, PDFPage, and PGM backends are multi-page, and the remaining backends are single-page. Note that multiple input images can be read in two ways: from multiple input files (with the -o option), or from a single input file that holds several concatenated images.

COMPILE TIME CONFIGURATION

Certain aspects of the behavior of potrace can be configured at compile time by passing the following options to the ./configure script.

--disable-zlib
compile potrace without the zlib compression library. This means PostScript level 3 compression will not be available.
--enable-metric
compile potrace with centimeters as the default unit instead of inches.
--enable-a4
compile potrace with A4 as the default page size.

EXIT STATUS

The exit status is 0 on successful completion, 1 if the command line was invalid, and 2 on any other error.
