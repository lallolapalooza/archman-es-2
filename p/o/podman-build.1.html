NOMBRE

podman-build - Construye una imagen de contenedor usando un Containerfile

SINOPSIS

podman build [opciones] [contexto]

podman image build [opciones] [contexto]

DESCRIPCIÓN

podman build construye una imagen usando instrucciones de uno o más Containerfiles o Dockerfiles y un directorio de contexto de compilación especificado. Un Containerfile usa internamente la misma sintaxis que un Dockerfile. Para este documento, un archivo al que se hace referencia como Containerfile puede ser un archivo llamado 'Containerfile' o 'Dockerfile' exclusivamente. Cualquier archivo que tenga una extensión adicional adjunta no será reconocido por podman build . a menos que se utilice la bandera -f para especificar el archivo.

El directorio de contexto de compilación se puede especificar como la URL http(s) de un archivo, un repositorio git o un Containerfile.

Cuando se invoca con -f y una ruta a un Containerfile, sin un directorio de CONTEXTO explícito, Podman utiliza el directorio padre del Containerfile como su contexto de compilación.

Los Containerfiles que terminan con el sufijo ".in" se preprocesan a través de CPP(1). Esto puede ser útil para descomponer los Containerfiles en varias partes reutilizables que se pueden usar a través de la directiva #include de CPP. Los Containerfiles que terminan en .in están restringidos a no tener líneas de comentarios a menos que sean comandos de CPP. Tenga en cuenta que un archivo Containerfile.in todavía puede ser utilizado por otras herramientas al preprocesarlos manualmente a través de cpp -E.

Cuando la URL es un archivo, el contenido de la URL se descarga a una ubicación temporal y se extrae antes de la ejecución.

Cuando la URL es un Containerfile, el Containerfile se descarga a una ubicación temporal.

Cuando un repositorio Git se establece como URL, el repositorio se clona localmente y luego se establece como contexto. Una URL se trata como un repositorio Git si tiene un prefijo git:// o un sufijo .git.

NOTA: podman build utiliza código de origen del proyecto Buildah para construir imágenes de contenedor. Este código de Buildah crea contenedores de Buildah para las opciones RUN en el almacenamiento de contenedores. En ciertas situaciones, cuando podman build falla o los usuarios matan el proceso de podman build, estos contenedores externos pueden dejarse en el almacenamiento de contenedores. Utilice el comando podman ps --all --external para ver estos contenedores.

podman buildx build es un alias de podman build. No todas las características de buildx build están disponibles en Podman. La opción buildx build se proporciona para compatibilidad con scripts.

OPCIONES

--add-host=nombre_host[;nombre_host[;...]]:ip

Agrega un mapeo personalizado de host a IP al archivo /etc/hosts del contenedor.

La opción toma uno o varios nombres de host separados por punto y coma para ser mapeados a una única dirección IPv4 o IPv6, separada por dos puntos. También se puede usar para sobrescribir las direcciones IP de los nombres de host que Podman agrega a /etc/hosts por defecto (ver también las opciones --name y --hostname). Esta opción se puede especificar varias veces para agregar mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede proporcionar el indicador especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de su configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que hará que Podman falle con un mensaje de error. Puede sobrescribir esta dirección IP utilizando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para agregar automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitar eso proporcionando la opción --no-hosts, o configurando host_containers_internal_ip="none" en containers.conf. Si no se configuró ninguna dirección host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se está ejecutando en una máquina virtual usando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven mediante el resolvedor DNS de gvproxy en su lugar.

Podman usará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente utilizando la configuración base_hosts_file en containers.conf.

--all-platforms

En lugar de construir para un conjunto de plataformas especificadas usando la opción --platform, inspecciona las imágenes base de la compilación y construye para todas las plataformas para las que están disponibles. Las etapas que utilizan scratch como punto de partida no se pueden inspeccionar, por lo que al menos una etapa que no sea scratch debe estar presente para que la detección funcione útilmente.

--annotation=anotacion=valor

Agrega una anotación de imagen (por ejemplo, anotacion=valor) a los metadatos de la imagen. Se puede usar varias veces.

Nota: esta información no está presente en los formatos de imagen de Docker, por lo que se descarta al escribir imágenes en formatos de Docker.

--arch=arquitectura

Establece la arquitectura de la imagen a construir, y la de la imagen base a extraer, si la compilación utiliza una, al valor proporcionado en lugar de usar la arquitectura del host de compilación. A menos que se anule, las búsquedas posteriores de la misma imagen en el almacenamiento local coinciden con esta arquitectura, independientemente del host. (Ejemplos: arm, arm64, 386, amd64, ppc64le, s390x)

--authfile=ruta

Ruta del archivo de autenticación. El valor predeterminado es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo es creado por podman login. Si no se encuentra el estado de autorización allí, se verifica $HOME/.docker/config.json, que se establece usando docker login.

Nota: También existe la opción de anular la ruta predeterminada del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

--build-arg=arg=valor

Especifica un argumento de compilación y su valor, que se interpola en las instrucciones leídas de los Containerfiles de la misma manera que las variables de entorno, pero que no se agregan a la lista de variables de entorno en la configuración de la imagen resultante.

--build-arg-file=ruta

Especifica un archivo que contiene líneas de argumentos de compilación del formato arg=valor. El nombre de archivo sugerido es argfile.conf.

Las líneas de comentarios que comienzan con # se ignoran, junto con las líneas en blanco. Todas las demás deben tener el formato arg=valor pasado a --build-arg.

Si se proporcionan varios argumentos a través de las opciones --build-arg-file y --build-arg, los argumentos de compilación se fusionan en todos los archivos y argumentos de línea de comandos proporcionados.

Cualquier archivo proporcionado en una opción --build-arg-file se lee antes que los argumentos suministrados a través de la opción --build-arg.

Cuando un nombre de argumento dado se especifica varias veces, la última instancia es la que se pasa a las compilaciones resultantes. Esto significa que los valores de --build-arg siempre anulan los de un --build-arg-file.

--build-context=nombre=valor

Especifica un contexto de compilación adicional utilizando su nombre corto y su ubicación. Los contextos de compilación adicionales se pueden referenciar de la misma manera que accedemos a diferentes etapas en la instrucción COPY.

Los valores válidos son:

  • Directorio local – por ejemplo, --build-context project2=../ruta/a/project2/src
  • URL HTTP a un archivo tar – por ejemplo, --build-context src=https://example.org/releases/src.tar
  • Imagen de contenedor – especificada con un prefijo container-image://, por ejemplo, --build-context alpine=container-image://al

--created-annotation

Añade una anotación a la imagen (ver también --annotation) a los metadatos de la imagen estableciendo "org.opencontainers.image.created" a la hora actual, o a la marca de fecha especificada para el flag --source-date-epoch o --timestamp, si alguno de ellos fue usado. Si es false, no habrá dicha anotación en la imagen escrita.

Nota: esta información no está presente en los formatos de imagen Docker, por lo que se descarta al escribir imágenes en formatos Docker.

--creds=[usuario[:contraseña]]

El [usuario[:contraseña]] a usar para autenticarse con el registro, si es requerido. Si uno o ambos valores no se suministran, aparece un prompt en la línea de comandos y el valor puede ser introducido. La contraseña se introduce sin eco.

Tenga en cuenta que las credenciales especificadas solo se utilizan para autenticarse con los registros de destino. No se utilizan para espejos o cuando el registro se reescribe (ver containers-registries.conf(5)); para autenticarse con ellos, considere usar un archivo containers-auth.json(5).

--cw=opciones

Produce una imagen adecuada para ser utilizada como carga de trabajo confidencial ejecutándose en un entorno de ejecución confiable (TEE) usando krun (es decir, crun compilado con la característica libkrun habilitada e invocado como krun). En lugar de los contenidos convencionales, el sistema de archivos raíz de la imagen contendrá una imagen de disco cifrada e información de configuración para krun.

El valor para opciones es una lista separada por comas de pares clave=valor, suministrando información de configuración que es necesaria para producir los datos adicionales que se incluirán en la imagen del contenedor.

Las claves reconocidas son:

attestation_url: La ubicación de un servidor de clave/atestación. Si se especifica un valor, el ID de carga de trabajo de la nueva imagen, junto con la frase de contraseña utilizada para cifrar la imagen de disco, se registrará con el servidor, y la ubicación del servidor se almacenará en la imagen del contenedor. En tiempo de ejecución, se espera que krun contacte al servidor para recuperar la frase de contraseña usando el ID de carga de trabajo, que también se almacena en la imagen del contenedor. Si no se especifica un valor, se debe especificar un valor de passphrase.

cpus: El número de CPUs virtuales con los que la imagen espera ejecutarse en tiempo de ejecución. Si no se especifica, se proporcionará un valor predeterminado.

firmware_library: La ubicación de la biblioteca compartida libkrunfw-sev. Si no se especifica, buildah busca su presencia en una serie de ubicaciones codificadas.

memory: La cantidad de memoria con la que la imagen espera ejecutarse en tiempo de ejecución, como un número de megabytes. Si no se especifica, se proporcionará un valor predeterminado.

passphrase: La frase de contraseña a utilizar para cifrar la imagen de disco que se incluirá en la imagen del contenedor. Si no se especifica un valor, pero se especifica un valor de attestation_url, se utilizará una frase de contraseña generada aleatoriamente. Los autores recomiendan establecer una attestation_url pero no una passphrase.

slop: Espacio extra a asignar para la imagen de disco en comparación con el tamaño de los contenidos de la imagen del contenedor, expresado como un porcentaje (..%) o un valor de tamaño (bytes, o unidades mayores si hay sufijos como KB o MB), o una suma de dos o más de tales especificaciones. Si no se especifica, buildah adivina que el 25% más de espacio que los contenidos será suficiente, pero esta opción se proporciona en caso de que su suposición sea incorrecta.

type: El tipo de entorno de ejecución confiable (TEE) para el cual la imagen debe estar marcada para su uso. Los valores aceptados son "SEV" (AMD Secure Encrypted Virtualization - Encrypted State) y "SNP" (AMD Secure Encrypted Virtualization - Secure Nested Paging). Si no se especifica, el valor predeterminado es "SNP".

workload_id: Un identificador de carga de trabajo que se registrará en la imagen del contenedor, para ser utilizado en tiempo de ejecución para recuperar la frase de contraseña que se utilizó para cifrar la imagen de disco. Si no se especifica, se derivará un valor semi-aleatorio del ID de imagen de la imagen base.

Esta opción no se soporta en el cliente remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2).

--decryption-key=clave[:contraseña]

La [clave[:contraseña]] a utilizar para el descifrado de imágenes. La clave puede apuntar a claves y/o certificados. Se intenta el descifrado con todas las claves. Si la clave está protegida por una frase de contraseña, es obligatorio pasarla en el argumento y omitirla en caso contrario.

--device=dispositivo-host[:dispositivo-contenedor][:permisos]

Añade un dispositivo del host al contenedor. El parámetro opcional permisos se puede utilizar para especificar los permisos del dispositivo combinando r para lectura, w para escritura y m para mknod(2).

Ejemplo: --device=/dev/sdc:/dev/xvdc:rwm.

Nota: si dispositivo-host es un enlace simbólico, primero se resuelve. El contenedor solo almacena los números mayor y menor del dispositivo del host.

Entra en conflicto con la bandera similar --timestamp, que

--timestamp=segundos

Establece la marca de tiempo de creación a segundos desde la época para permitir compilaciones deterministas (por defecto es la hora actual). Por defecto, la marca de tiempo creada se cambia y se escribe en el manifiesto de la imagen con cada confirmación, lo que provoca que el hash sha256 de la imagen sea diferente incluso si las fuentes son exactamente las mismas de lo contrario. Cuando se establece --timestamp, la marca de tiempo creada siempre se establece en la hora especificada y, por lo tanto, no se cambia, lo que permite que el hash sha256 de la imagen permanezca igual. Todos los archivos confirmados en las capas de la imagen se crean con la marca de tiempo.

Si la única instrucción en un Containerfile es FROM, esta bandera no tiene ningún efecto.

Modifications to the mount point are destroyed when the **RUN** command finishes executing, similar to a tmpfs mount point. Any subsequent execution of **RUN** commands sees the original source directory content; any changes from previous RUN commands no longer exist. One use case of the **overlay** mount is sharing the package cache from the host into the container to allow speeding up builds. Note: * Overlay mounts are not currently supported in rootless mode. * The **O** flag is not allowed to be specified with the **Z** or **z** flags. This means any mounts done inside containers are not visible on the host and vice versa. This behavior can be changed by specifying a volume mount propagation property. When the mount propagation policy is set to **shared**, any mounts completed inside the container on that volume are visible to both the host and container. When the mount propagation policy is set to **slave**, one-way mount propagation is enabled, and any mounts completed on the host for that volume are visible only inside the container. To control the mount propagation property of a volume, use the **:[r]shared**, **:[r]slave**, or **:[r]private** propagation flag. For mount propagation to work, the source mount point (the mount point where the source directory is mounted) must have the correct propagation properties. For shared volumes, the source mount point must be shared. And for slave volumes, the source mount must be either shared or slave. Construir una imagen usando Containerfiles locales

Construir imagen usando Containerfile con contenido del directorio actual:

$ podman build .

Construir imagen usando Containerfile especificada con contenido del directorio actual:

$ podman build -f Containerfile.simple .

Construir imagen usando Containerfile desde stdin con contenido del directorio actual:

$ cat $HOME/Containerfile | podman build -f - .

Construir imagen usando múltiples Containerfiles con contenido del directorio actual:

$ podman build -f Containerfile.simple -f Containerfile.notsosimple .

Construir imagen con Containerfile especificada con contenido del directorio $HOME. Nota: se aplica **cpp** a Containerfile.in antes de procesarlo como Containerfile:

$ podman build -f Containerfile.in $HOME

Construir imagen con la etiqueta especificada usando Containerfile y contenido del directorio actual:

$ podman build -t imageName .

Construir imagen ignorando la verificación del registro para cualquier imagen extraída a través de Containerfile:

$ podman build --tls-verify=false -t imageName .

Construir imagen con el formato de registro especificado:

$ podman build --runtime-flag log-format=json .

Construir imagen usando modo de depuración para registro:

$ podman build --runtime-flag debug .

Construir imagen usando atributos de registro especificados al extraer imágenes del Containerfile seleccionado:

$ podman build --authfile /tmp/auths/myauths.json --cert-dir $HOME/auth --tls-verify=true --creds=username:password -t imageName -f Containerfile.simple .

Construir imagen usando controles de recursos especificados al ejecutar contenedores durante la construcción:

$ podman build --memory 40m --cpu-period 10000 --cpu-quota 50000 --ulimit nofile=1024:1028 -t imageName .

Construir imagen usando etiquetas SELinux y configuración cgroup especificadas al ejecutar contenedores durante la construcción:

$ podman build --security-opt label=level:s0:c100,c200 --cgroup-parent /path/to/cgroup/parent -t imageName .

Construir imagen con volumen de solo lectura y reetiquetado SELinux montado desde el host en contenedores en ejecución durante la construcción:

$ podman build --volume /home/test:/myvol:ro,Z -t imageName .

Construir imagen con volumen overlay montado desde el host en contenedores en ejecución durante la construcción:

$ podman build -v /var/lib/yum:/var/lib/yum:O -t imageName .

Construir imagen usando capas y luego eliminando contenedores intermedios incluso si la construcción falla.

$ podman build --layers --force-rm -t imageName .

Construir imagen ignorando la caché y no eliminando contenedores intermedios incluso si la construcción tiene éxito:

$ podman build --no-cache --rm=false -t imageName .

Construir imagen usando la red especificada al ejecutar contenedores durante la construcción:

$ podman build --network mynet .

Construir una imagen usando un secreto almacenado en una variable de entorno o archivo llamado **mysecret** para ser utilizado con la instrucción **RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret**:

$ podman build --secret=id=mysecret .

Construir una imagen usando un secreto almacenado en una variable de entorno llamada **MYSECRET** para ser utilizado con la instrucción **RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret**:

$ podman build --secret=id=mysecret,env=MYSECRET .
$ podman build --secret=id=mysecret,src=MYSECRET,type=env .

Construir una imagen usando un secreto almacenado en un archivo llamado **.mysecret** para ser utilizado con la instrucción **RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret**:

$ podman build --secret=id=mysecret,src=.mysecret .
$ podman build --secret=id=mysecret,src=.mysecret,type=file .

Construir una imagen multi-arquitectura usando la opción --manifest (requiere software de emulación)

Construir imagen usando las arquitecturas especificadas y vincular a un único manifiesto al completarse con éxito:

$ podman build --arch arm --manifest myimage /tmp/mysrc
$ podman build --arch amd64 --manifest myimage /tmp/mysrc
$ podman build --arch s390x --manifest myimage /tmp/mysrc

Similarmente, construir usando un solo comando:

$ podman build --platform linux/s390x,linux/ppc64le,linux/amd64 --manifest myimage /tmp/mysrc

Construir imagen usando múltiples arquitecturas especificadas y vincular a un único manifiesto al completarse con éxito:

$ podman build --platform linux/arm64 --platform linux/amd64 --manifest myimage /tmp/mysrc

Construir una imagen usando una URL, repositorio Git o archivo

El directorio de contexto de construcción se puede especificar como una URL a un Containerfile, un repositorio Git o una URL a un archivo. Si la URL es un Containerfile, se descarga a una ubicación temporal y se usa como contexto. Cuando un repositorio Git se establece como la URL, el repositorio se clona localmente a una ubicación temporal y luego se usa como contexto. Por último, si la URL es un archivo, se descarga a una ubicación temporal y se extrae antes de usarse como contexto.

Construir una imagen usando una URL a un Containerfile

Construye una imagen desde un Containerfile descargado en una ubicación temporal que se utiliza como contexto de compilación:

$ podman build https://10.10.10.1/podman/Containerfile

Construir una imagen usando un repositorio de Git

Podman clona el repositorio de GitHub especificado a una ubicación temporal y lo utiliza como contexto. Se utiliza el Containerfile en la raíz del repositorio y solo funciona si el repositorio de GitHub es un repositorio dedicado.

Construye una imagen desde el repositorio de git especificado, descargado en una ubicación temporal utilizada como contexto de compilación:

$ podman build -t hello  https://github.com/containers/PodmanHello.git
$ podman run hello

Nota: GitHub no admite el uso de git:// para realizar la operación clone debido a cambios recientes en sus directrices de seguridad (https://github.blog/2021-09-01-improving-git-protocol-security-github/). Utilice una URL https:// si el repositorio de origen está alojado en GitHub.

Construir una imagen usando una URL a un archivo

Podman recupera el archivo comprimido, lo descomprime y utiliza su contenido como contexto de compilación. El Containerfile en la raíz del archivo y el resto del archivo se utilizan como contexto de compilación. Pasar la opción -f PATH/Containerfile también indica al sistema que busque ese archivo dentro del contenido del archivo.

$ podman build -f dev/Containerfile https://10.10.10.1/podman/context.tar.gz

Nota: los formatos de compresión compatibles son 'xz', 'bzip2', 'gzip' y 'identity' (sin compresión).

Archivos

.containerignore/.dockerignore

Si el archivo .containerignore o .dockerignore existe en el directorio de contexto, podman build lee su contenido. Utilice la opción --ignorefile para anular la ubicación de la ruta de .containerignore. Podman utiliza el contenido para excluir archivos y directorios del directorio de contexto, al ejecutar directivas COPY y ADD en el Containerfile/Dockerfile.

Los archivos .containerignore y .dockerignore utilizan la misma sintaxis; si ambos están en el directorio de contexto, podman build solo utiliza .containerignore.

Los usuarios pueden especificar una serie de globs de shell de Unix en un archivo .containerignore para identificar archivos/directorios a excluir.

Podman admite la cadena comodín especial ** que coincide con cualquier número de directorios (incluido cero). Por ejemplo, */.go excluye todos los archivos que terminan en .go y que se encuentran en todos los directorios.

Archivo .containerignore de ejemplo:

# excluir este contenido para la imagen
*/*.c
**/output*
src

*/*.c Excluye archivos y directorios cuyos nombres terminan en .c en cualquier subdirectorio de nivel superior. Por ejemplo, el archivo fuente include/rootless.c.

**/output* Excluye archivos y directorios que comienzan con output de cualquier directorio.

src Excluye archivos llamados src y el directorio src, así como cualquier contenido dentro de él.

Las líneas que comienzan con ! (signo de exclamación) se pueden utilizar para hacer excepciones a las exclusiones. El siguiente es un ejemplo de archivo .containerignore que utiliza este mecanismo:

*.doc
!Help.doc

Excluye todos los archivos doc excepto Help.doc de la imagen.

Esta funcionalidad es compatible con el manejo de archivos .containerignore descrito aquí: containerignore(5)

registries.conf (/etc/containers/registries.conf)

registries.conf es el archivo de configuración que especifica qué registros de contenedores se consultan al completar nombres de imagen que no incluyen una porción de registro o dominio. Ver containers-registries.conf(5)

Solucion de problemas

archivo sparse lastlog

El uso del comando useradd dentro de un Containerfile con un UID/GID grande crea un archivo sparse grande /var/log/lastlog. Esto puede hacer que la compilación se cuelgue indefinidamente. El lenguaje Go no admite archivos sparse correctamente, lo que puede llevar a la creación de archivos enormes en la imagen del contenedor.

Al utilizar el comando useradd dentro del script de compilación, pase la opción --no-log-init o -l al comando useradd. Esta opción indica a useradd que deje de crear el archivo lastlog.
