NOMBRE

podman-systemd.unit - Unidades systemd que utilizan Podman Quadlet

SINOPSIS

nombre.container, nombre.volume, nombre.network, nombre.kube nombre.image, nombre.build nombre.pod, nombre.artifact

Ruta de búsqueda de unidades rootful de Podman

Los archivos Quadlet para el usuario root se pueden colocar en los siguientes directorios, ordenados por precedencia. Esto significa que los quadlets con nombres duplicados encontrados en /run tienen prioridad sobre los de /etc, así como sobre los de /usr:

Quadlets temporales, generalmente utilizados para pruebas:

•
/run/containers/systemd/

Quadlets definidos por el administrador del sistema:

•
/etc/containers/systemd/

Quadlets definidos por la distribución:

•
/usr/share/containers/systemd/

Ruta de búsqueda de unidades rootless de Podman

Los archivos Quadlet para usuarios no root se pueden colocar en los siguientes directorios:

  • $XDG_RUNTIME_DIR/containers/systemd/
  • $XDG_CONFIG_HOME/containers/systemd/ o ~/.config/containers/systemd/
  • /etc/containers/systemd/users/$(UID)
  • /etc/containers/systemd/users/

Uso de enlaces simbólicos

Quadlet soporta el uso de enlaces simbólicos para la base de las rutas de búsqueda y dentro de ellas.

DESCRIPCIÓN

Podman soporta la creación e inicio de contenedores (y la creación de volúmenes) a través de systemd utilizando un generador de systemd. Estos archivos se leen durante el arranque (y cuando se ejecuta systemctl daemon-reload) y generan archivos de unidad de servicio systemd regulares correspondientes. Se soportan tanto las unidades systemd del sistema como las del usuario. Todas las opciones y tablas disponibles en los archivos de unidad systemd estándar son compatibles. Por ejemplo, las opciones definidas en la tabla [Service] y las tablas [Install] se pasan directamente a systemd y son manejadas por él. Consulte la página del manual systemd.unit(5) para obtener más información.

El generador de Podman lee las rutas de búsqueda anteriores y lee archivos con las extensiones .container .volume, .network, .build, .pod, .kube y .artifact, y para cada archivo genera un archivo .service con nombre similar. Tenga en cuenta que los servicios de proveedor existentes (es decir, en /usr/) se reemplazan si tienen el mismo nombre. Los archivos de unidad generados se pueden iniciar y administrar con systemctl como cualquier otro servicio systemd. systemctl {--user} list-unit-files enumera los archivos de unidad existentes en el sistema.

Los archivos Podman utilizan el mismo formato que los archivos de unidad systemd regulares. Cada tipo de archivo tiene una sección personalizada (por ejemplo, [Container]) que es manejada por Podman, y todas las demás secciones se pasan sin modificaciones, lo que permite el uso de cualquier opción de configuración normal de systemd, como dependencias o límites de cgroup.

Los archivos fuente también admiten drop-ins de la misma manera que lo hace systemd. Para un archivo fuente dado (foo.container), el directorio .d correspondiente (foo.container.d) se buscará en busca de archivos con la extensión .conf, que luego se fusionan en el archivo base en orden alfabético. También se incluirán drop-ins de tipo superior (container.d). Si la unidad contiene guiones ("-") en el nombre (foo-bar-baz.container), entonces también se buscarán los directorios drop-in generados al truncar el nombre después del guion (foo-.container.d y foo-bar-.container.d). Los archivos drop-in con el mismo nombre más abajo en la jerarquía anulan a los de más arriba (foo-bar-baz.container.d/10-override.conf anula foo-bar-.container.d/10-override.conf, que anula foo-.service.d/10-override.conf, que anula container.d/10-override.conf). El formato de estos archivos drop-in es el mismo que el del archivo base. Esto es útil para alterar o agregar configuraciones a una unidad, sin tener que modificar los archivos de unidad.

Para contenedores sin root (rootless), cuando los administradores colocan archivos Quadlet en el directorio /etc/containers/systemd/users, todas las sesiones de usuario ejecutan el Quadlet cuando comienza la sesión de inicio de sesión. Si el administrador coloca un archivo Quadlet en el directorio /etc/containers/systemd/users/${UID}/, entonces solo el usuario con el UID correspondiente ejecuta el Quadlet cuando se inicia la sesión de inicio de sesión. Para los archivos de unidad colocados en subdirectorios dentro de /etc/containers/systemd/user/${UID}/ y las otras rutas de búsqueda de unidades de usuario, Quadlet buscará recursivamente y ejecutará los archivos de unidad presentes en estos subdirectorios.

Tenga en cuenta que las unidades Quadlet no admiten la ejecución como usuario no root definiendo las opciones de systemd User, Group o DynamicUser. Si desea ejecutar un Quadlet sin root, deberá crear el usuario y agregar el archivo de unidad a una de las rutas de búsqueda de unidades sin root anteriores.

Nota: Cuando un Quadlet se está iniciando, Podman a menudo extrae o construye una o más imágenes de contenedor, lo que puede llevar una cantidad considerable de tiempo. Systemd establece por defecto el tiempo de inicio del servicio en 90 segundos, o falla el servicio. Pre-extraer la imagen o extender el tiempo de espera de systemd para el servicio utilizando la opción de servicio TimeoutStartSec puede solucionar el problema. Una advertencia: TimeoutStartSec no está disponible para unidades Type=oneshot. Consulte systemd.service(5) para obtener más información sobre cómo manejar tiempos de inicio prolongados para unidades que no necesitan permanecer activas una vez que su proceso principal ha finalizado.

Agregar el siguiente fragmento a un archivo Quadlet extiende el tiempo de espera de systemd a 15 minutos.

[Service]
TimeoutStartSec=900

Quadlet requiere el uso de cgroup v2, use podman info --format {{.Host.CgroupsVersion}} para verificar en el sistema.

Tipo de servicio

Por defecto, el campo Type de la sección Service del archivo Quadlet no necesita ser establecido. Quadlet lo establecerá en notify para los archivos .container y .kube, forking para los archivos .pod, y oneshot para los archivos .volume, .network, .build, .image y .artifact.

Sin embargo, Type puede establecerse explícitamente en oneshot para los archivos .container y .kube cuando no se espera que se ejecuten contenedores una vez que podman salga.

Al establecer Type=oneshot, se recomienda también establecer RemainAfterExit=yes para evitar que el estado del servicio sea inactive (dead). Sin embargo, al activar un servicio a través de una unidad de temporizador, tener RemainAfterExit=yes deja el trabajo en un estado "started" que impide activaciones posteriores por el temporizador. Para más información, véase la página del manual systemd.service(5).

Ejemplos para tales casos: - Archivo .container con una imagen que sale después de que su entrypoint ha finalizado

•
Archivo .kube que apunta a un archivo Yaml de Kubernetes que no define ningún contenedor. Por ejemplo, solo PVCs

Habilitar archivos de unidad

Los servicios creados por Podman son considerados transitorios por systemd, lo que significa que no tienen las mismas reglas de persistencia que las unidades regulares. En particular, no es posible habilitarlos con systemctl enable para que se habiliten automáticamente en el próximo arranque.

Para compensar esto, el generador aplica manualmente la sección [Install] de los archivos de unidad de definición del contenedor durante la generación, de la misma manera que lo hace systemctl enable cuando se ejecuta posteriormente.

Por ejemplo, para iniciar un contenedor al arrancar, agregue algo como esto al archivo:

[Install]
WantedBy=default.target

Actualmente, solo se admiten las claves Alias, WantedBy, RequiredBy y UpheldBy.

La sección Install puede ser parte del archivo principal, o puede estar en un archivo drop-in separado como se describió anteriormente. Este último permite instalar una unidad no habilitada y luego habilitarla instalando el drop-in.

Plantillas de Quadlets

Los archivos de unidad de Quadlet pueden utilizar la sintaxis de plantillas de systemd, similar a los archivos de unidad de systemd (por ejemplo, basename@.service). En systemd, un nombre de archivo como foo@bar.service se refiere a una instancia de la plantilla foo@.service. Las instancias individuales pueden tener nombres como foo@bar.service, foo@baz.service, etc., todas ellas instanciadas desde un único archivo de plantilla foo@.service. Las instancias individuales también pueden ser diferentes utilizando archivos de drop-in con el nombre de instancia completo.

Quadlets admite esto de dos maneras. En primer lugar, una unidad quadlet con forma de plantilla generará un servicio systemd con forma de plantilla, y el servicio systemd de plantilla se puede utilizar como una plantilla normal. Por ejemplo, foo@.container generará foo@.service y luego podrá ejecutar systemctl start foo@bar.service.

En segundo lugar, si crea un enlace simbólico como foo@instance.container, generará un archivo de plantilla instanciado. Al generar este archivo, quadlet leerá los archivos de drop-in tanto del directorio de la instancia (foo@instance.container.d) como del directorio de la plantilla (foo@.container.d). Esto permite la personalización de instancias individuales.

Los archivos de plantilla instanciados (como foo@bar.container) se pueden habilitar igual que los que no son plantillas. Sin embargo, los que son plantillas (foo@.container) son diferentes, porque necesitan ser instanciados. Si la sección [Install] contiene una clave DefaultInstance=, entonces se habilitará esa instancia, pero si no, no sucederá nada y las opciones solo se utilizarán como predeterminadas para las unidades que se instancien utilizando enlaces simbólicos.

Un ejemplo de archivo de plantilla sleep@.container podría verse así:

[Unit]
Description=Un contenedor durmiente de plantilla
[Container]
Image=quay.io/fedora/fedora
Exec=sleep %i
[Service]
# Reiniciar el servicio cuando termine de dormir
Restart=always
[Install]
WantedBy=multi-user.target
DefaultInstance=100

Si esto está instalado, entonces al arrancar habrá un servicio sleep@100.service ejecutándose que duerme durante 100 segundos. Luego puede hacer algo como systemctl start sleep@50.service para iniciar otra instancia que duerme 50 segundos, o alternativamente otro servicio puede iniciarlo a través de una dependencia como Wants=sleep@50.service.

Además, si ejecuta ln -s sleep@.container sleep@10.container, también tendrá un servicio de 10 segundos durmiendo al arrancar. Y, si desea que esa instancia en particular se ejecute con una imagen diferente, puede crear un archivo de drop-in como sleep@10.container.d/10-image.conf:

[Container]
Image=quay.io/centos/centos

Para admitir especificadores de Systemd, Quadlet no resuelve rutas relativas que comienzan con %. Para resolver dicha ruta, antepóngala con ./.

Por ejemplo, en lugar de EnvironmentFile=%n/env use EnvironmentFile=./%n/env

Depuración de archivos de unidad

Después de colocar el archivo de unidad en una de las rutas de búsqueda de unidades (mencionadas anteriormente), puede iniciarlo con systemctl start {--user}. Si falla con "Failed to start example.service: Unit example.service not found.", entonces es posible que haya utilizado una sintaxis incorrecta o que haya utilizado una opción de una versión más reciente de Podman Quadlet y el generador no haya podido crear un archivo de servicio.

Vea los archivos generados y/o los mensajes de error con:

/usr/lib/systemd/system-generators/podman-system-generator {--user} --dryrun

Alternativamente, muestre solo los errores con:

systemd-analyze {--user} --generators=true verify example.service

Ese comando también realiza comprobaciones adicionales en la unidad de servicio generada. Para obtener detalles, consulte la página del manual de systemd-analyze(1).

Depuración de un conjunto limitado de archivos de unidad

Si desea depurar un conjunto limitado de archivos de unidad, puede copiarlos a un directorio separado y establecer la variable de entorno QUADLET_UNIT_DIRS en este directorio al ejecutar el siguiente comando:

QUADLET_UNIT_DIRS=<Directorio> /usr/lib/systemd/system-generators/podman-system-generator {--user} --dryrun

Esto instruirá a Quadlet a buscar unidades en este directorio en lugar de los comunes y, por lo tanto, limitará la salida solo a las unidades que está depurando.

Dependencias de red implícitas

Quadlet agregará dependencias en network-online.target (como root) o podman-user-wait-network-online.service (como usuario) agregando propiedades After= y Wants= a la unidad. Esto es para asegurar que la red sea accesible si se necesita descargar una imagen y para cuando se inicia el contenedor.

El caso especial podman-user-wait-network-online.service se necesita como usuario porque las unidades de usuario no pueden esperar a las unidades del sistema (root), por lo que network-online.target no hace nada allí y se ignora en su lugar. Dado que esto causó una cantidad significativa de problemas, decidimos solucionar esto con nuestra propia unidad de propósito especial que simplemente verifica si la unidad network-online.target está activa con systemctl is-active network-online.target.

Este comportamiento se puede deshabilitar agregando DefaultDependencies=false en la sección Quadlet. Tenga en cuenta que la sección [Unit] de systemd tiene una opción con el mismo nombre pero un significado diferente.

Dependencia entre unidades Quadlet

Quadlet traducirá automáticamente las dependencias, especificadas en las claves Wants, Requires, Requisite, BindsTo, PartOf, Upholds, Conflicts, Before y After de la sección [Unit], entre diferentes unidades Quadlet.

Por ejemplo, la unidad fedora.container a continuación especifica una dependencia en la unidad basic.container.

[Unit]
After=basic.container
Requires=basic.container
[Container]
Image=registry.fedoraproject.org/fedora:41

Establecer nombres de recursos

Las unidades Quadlet permiten establecer los nombres de los recursos creados (por ejemplo, VolumeName para unidades .volume o PodName para unidades .pod).

Tenga en cuenta que el uso de especificadores de systemd que hacen referencia a la unidad de servicio generada (por ejemplo, $N) rompe la capacidad de Quadlet para vincular entre recursos, ya que se traducen de manera diferente en cada servicio.

Unidades de contenedor [Container]

Las unidades de contenedor se nombran con una extensión .container y contienen una sección [Container] que describe el contenedor que se ejecuta como un servicio. El archivo de servicio resultante contiene una línea como ExecStart=podman run … image-name, y la mayoría de las claves de esta sección controlan las opciones de línea de comandos que se pasan a Podman. Sin embargo, algunas opciones también afectan los detalles de cómo se configura systemd para ejecutar e interactuar con el contenedor.

Por defecto, el contenedor de Podman tiene el mismo nombre que la unidad, pero con un prefijo systemd-, es decir, un archivo $name.container crea una unidad $name.service y un contenedor Podman systemd-$name. La opción ContainerName permite anular este nombre predeterminado con uno proporcionado por el usuario.

Solo hay una clave requerida, Image, que define la imagen del contenedor que ejecuta el servicio.

Descripción de la sección [Container]:

AddCapability=

Añade estas capacidades, además del conjunto de capacidades predeterminado de Podman, al contenedor.

Esta es una lista separada por espacios de capacidades. Esta clave se puede listar varias veces.

Por ejemplo:

AddCapability=CAP_DAC_OVERRIDE CAP_IPC_OWNER

AddDevice=

Añade un nodo de dispositivo desde el host al contenedor. El formato es HOST-DEVICE[:CONTAINER-DEVICE][:PERMISSIONS], donde HOST-DEVICE es la ruta del nodo de dispositivo en el host, CONTAINER-DEVICE es la ruta del nodo de dispositivo en el contenedor y PERMISSIONS es una lista de permisos que combinan 'r' para leer, 'w' para escribir y 'm' para mknod(2). El prefijo - indica a Quadlet que añada el dispositivo solo si existe en el host.

Esta clave se puede listar varias veces.

AddHost=

Añade un mapeo de host a IP a /etc/hosts. El formato es hostname:ip.

Equivalente a la opción --add-host de Podman. Esta clave se puede listar varias veces.

Annotation=

Establece una o más anotaciones OCI en el contenedor. El formato es una lista de elementos clave=valor, similar a Environment.

Esta clave se puede listar varias veces.

AutoUpdate=

Indica si el contenedor se actualizará automáticamente (podman-auto-update(1)). Se admiten los siguientes valores:

  • registry: Requiere una referencia de imagen completamente cualificada (por ejemplo, quay.io/podman/stable:latest) para crear el contenedor. Esta comprobación es necesaria para saber qué imagen comprobar y descargar. Si se utilizó un ID de imagen, Podman no sabe qué imagen comprobar/descargar.
  • local: Indica a Podman que compare la imagen que utiliza un contenedor con la imagen con su nombre sin procesar en el almacenamiento local. Si una imagen se actualiza localmente, Podman simplemente reinicia la unidad systemd que ejecuta el contenedor.

CgroupsMode=

El modo cgroups del contenedor Podman. Equivalente a la opción --cgroups de Podman.

Por defecto, el modo cgroups del contenedor creado por Quadlet es split, lo que difiere del predeterminado (enabled) utilizado por la CLI de Podman.

Si el contenedor se une a un pod (es decir, se especifica Pod=), es posible que desee cambiarlo a no-conmon o enabled para que los límites de recursos de cgroup a nivel de pod surtan efecto.

ContainerName=

El nombre (opcional) del contenedor Podman. Si no se especifica, se utiliza el valor predeterminado de systemd-%N, que es el mismo que el nombre del servicio pero con un prefijo systemd- para evitar conflictos con contenedores gestionados por el usuario.

ContainersConfModule=

Carga el módulo specified containers.conf(5). Equivalente a la opción --module de Podman.

Esta clave se puede listar varias veces.

DNS=

Establece el resolvedor/servidor de nombres DNS con ámbito de red para los contenedores de esta red.

Esta clave se puede listar varias veces.

DNSOption=

Establece opciones DNS personalizadas.

Esta clave se puede listar varias veces.

DNSSearch=

Establece dominios de búsqueda DNS personalizados. Utilice DNSSearch=. para eliminar el dominio de búsqueda.

Esta clave se puede listar varias veces.

DropCapability=

Elimina estas capacidades del conjunto de capacidades predeterminado de Podman, o all para eliminar todas las capacidades.

Esta es una lista separada por espacios de capacidades. Esta clave se puede listar varias veces.

Por ejemplo:

DropCapability=CAP_DAC_OVERRIDE CAP_IPC_OWNER

Entrypoint=

Anula el ENTRYPOINT predeterminado de la imagen. Equivalente a la opción --entrypoint de Podman. Especifique comandos de opción múltiple en forma de una cadena JSON.

Environment=

Establece una variable de entorno en el contenedor. Utiliza el mismo formato que los servicios en systemd y se puede listar varias veces.

EnvironmentFile=

Utiliza un archivo delimitado por líneas para establecer variables de entorno en el contenedor. La ruta puede ser absoluta o relativa a la ubicación del archivo de unidad. Esta clave se puede utilizar varias veces, y el orden se mantiene al pasarlo a podman run.

EnvironmentHost=

Utiliza el entorno del host dentro del contenedor.

Exec=

Argumentos adicionales para el contenedor; esto tiene exactamente el mismo efecto que pasar más argumentos después de una invocación de podman run <image> <arguments>.

El formato es el mismo que para las líneas de comandos de systemd. The format of this is a space separated list of arguments, which can optionally be individually escaped to allow inclusion of whitespace and other control characters.

This key can be listed multiple times.

Set the restart policy for the pod. This is equivalent to the Podman --restart option.

Las unidades de imagen se utilizan para asegurarse de que una imagen de contenedor esté presente en el host. Generan un servicio systemd que se ejecuta y comprueba la existencia de la imagen especificada. Si la imagen no se encuentra, el servicio intenta descargarla.

Este servicio puede ser útil para asegurarse de que las imágenes necesarias estén disponibles antes de que se inicien otros contenedores o servicios.

Las unidades de imagen tienen la extensión .image y contienen una sección [Image] que describe la imagen que se va a descargar.

Las opciones válidas para [Image] se enumeran a continuación:

Opciones de [Image] equivalente a podman pull
Image=quay.io/podman/stable:latest podman pull quay.io/podman/stable:latest
ImageTag=quay.io/podman/stable:latest Imagen completa especificada en la opción Image=
AuthFile=/etc/registry/auth.json --authfile=/etc/registry/auth.json
CertDir=/etc/registry/certs --cert-dir=/etc/registry/certs
GlobalArgs=--log-level=debug --log-level=debug
OS=linux --os=linux
PodmanArgs=--tls-verify=false --tls-verify=false
Policy=always --policy=always
Retry=5 --retry=5
RetryDelay=10s --retry-delay=10s
ServiceName=my-image Establece el nombre del servicio systemd a my-image.service
TLSVerify=false --tls-verify=false
Variant=arm64 --variant=arm64

AuthFile=

Ruta al archivo de autenticación. Equivalente a la opción podman --authfile.

CertDir=

Utiliza certificados en la ruta (*.crt, *.cert, *.key) para conectarte al registro. Equivalente a la opción podman --cert-dir.

GlobalArgs=

Esta clave contiene una lista de argumentos que se pasan directamente entre podman e image en el archivo generado. Se puede utilizar para acceder a funciones de Podman que de otro modo no serían compatibles con el generador. Dado que el generador desconoce las interacciones inesperadas que pueden causar estos argumentos, no se recomienda el uso de esta opción.

El formato es una lista de argumentos separados por espacios, que opcionalmente pueden escaparse individualmente para permitir la inclusión de espacios en blanco y otros caracteres de control.

Esta clave se puede listar varias veces.

Image=

La imagen a descargar. Se recomienda utilizar un nombre de imagen completamente cualificado en lugar de un nombre corto, tanto por razones de rendimiento como de robustez.

El formato del nombre es el mismo que cuando se pasa a podman pull. Por lo tanto, admite el uso de :tag o digests para garantizar la versión específica de la imagen.

ImageTag=

FQIN real de la Image referenciada. Solo tiene sentido cuando la fuente es un archivo o un archivo de directorio.

Por ejemplo, una imagen guardada en un archivo docker-archive con el siguiente comando Podman:

podman image save --format docker-archive --output /tmp/archive-file.tar quay.io/podman/stable:latest

requiere establecer - Image=docker-archive:/tmp/archive-file.tar - ImageTag=quay.io/podman/stable:latest

OS=

Anula el sistema operativo, por defecto el del host, de la imagen que se va a descargar.

Esto es equivalente a la opción podman --os.

PodmanArgs=

Esta clave contiene una lista de argumentos que se pasan directamente al final del comando podman image pull en el archivo generado (justo antes del nombre de la imagen en la línea de comandos). Se puede utilizar para acceder a funciones de Podman que de otro modo no serían compatibles con el generador. Dado que el generador desconoce las interacciones inesperadas que pueden causar estos argumentos, no se recomienda el uso de esta opción.

El formato es una lista de argumentos separados por espacios, que opcionalmente pueden escaparse individualmente para permitir la inclusión de espacios en blanco y otros caracteres de control.

Esta clave se puede listar varias veces.

Policy=

La política de descarga a utilizar al descargar la imagen.

Esto es equivalente a la opción podman --policy.

Retry=

Número de veces que se reintentará la descarga de la imagen cuando ocurra un error HTTP. Equivalente a la opción podman --retry.

RetryDelay=

Retraso entre reintentos. Equivalente a la opción podman --retry-delay.

TLSVerify=

Requiere HTTPS y verificación de certificados al contactar con los registros.

Esto es equivalente a la opción podman --tls-verify.

Variant=

Anula la variante de arquitectura predeterminada de la imagen del contenedor.

Esto es equivalente a la opción podman --variant.

Unidades de artefactos [Artifact]

ADVERTENCIA: Unidad experimental

Esta unidad se considera experimental y aún está en desarrollo. Las entradas, opciones y salidas están sujetas a cambios.

Las unidades de artefactos se nombran con la extensión .artifact y contienen una sección [Artifact] que describe el comando de descarga del artefacto del contenedor. El servicio generado es un comando de un solo uso que garantiza que el artefacto existe en el host, descargándolo si es necesario.

El uso de unidades de artefactos permite que los contenedores dependan de la descarga automática de artefactos. Esto es particularmente útil para gestionar artefactos que los contenedores necesitan montar o acceder. La clave Artifact es obligatoria dentro de la unidad [Artifact].

Las opciones válidas para [Artifact] se enumeran a continuación:

Opciones de [Artifact] equivalente a podman artifact pull
Artifact=quay.io/foobar/artifact:special podman artifact pull quay.io/foobar/artifact:special
AuthFile=/etc/registry/auth.json --authfile=/etc/registry/auth.json
CertDir=/etc/registry/certs --cert-dir=/etc/registry/certs
ContainersConfModule=/etc/nvd.conf --module=/etc/nvd.conf
Creds=username:password --creds=username:password
DecryptionKey=/etc/registry.key --decryption-key=/etc/registry.key
GlobalArgs=--log-level=debug --log-level=debug
PodmanArgs=--pull never --pull never
Quiet=true --quiet
Retry=5 --retry=5
RetryDelay=10s --retry-delay=10s
ServiceName=my-artifact Establece el nombre del servicio systemd a my-artifact.service
TLSVerify=false --tls-verify=false

Artifact=

El artefacto a descargar de un registro a la máquina local. Esta es la única clave requerida para las unidades de artefactos.

Es obligatorio utilizar un nombre de artefacto completamente cualificado en lugar de un nombre corto, tanto por razones de rendimiento como de robustez.

AuthFile=

Ruta al archivo de autenticación.

Esto es equivalente a la opción podman --authfile.

CertDir=

Utiliza certificados en la ruta (*.crt, *.cert, *.key) para conectarte al registro.

Esto es equivalente a la opción podman --cert-dir.

ContainersConfModule=

Carga el módulo specified containers.conf(5). Equivalente a la opción podman --module.

Esta clave se puede listar varias veces.

Creds=

Las credenciales a utilizar al contactar con el registro en el formato [username[:password]].

Esto es equivalente a la opción podman --creds.

DecryptionKey=

La [key[:passphrase]] a utilizar para la descifrado de artefactos.

Esto es equivalente a la opción podman --decryption-key.

GlobalArgs=

Esta clave contiene una lista de argumentos que se pasan directamente entre podman y artifact en el archivo generado. Se puede utilizar para acceder a funciones de Podman que de otro modo no serían compatibles con el generador. Dado que el generador desconoce las interacciones inesperadas que pueden causar estos argumentos, no se recomienda el uso de esta opción.

El formato es una lista de argumentos separados por espacios, que opcionalmente pueden escaparse individualmente para permitir la inclusión de espacios en blanco y otros caracteres de control.

Esta clave se puede listar varias veces.

PodmanArgs=

Esta clave contiene una lista de argumentos que se pasan directamente al final del comando podman artifact pull en el archivo generado (justo antes del nombre del artefacto en la línea de comandos). Se puede utilizar para acceder a funciones de Podman que de otro modo no serían compatibles con el generador. Dado que el generador desconoce las interacciones inesperadas que pueden causar estos argumentos, no se recomienda el uso de esta opción.

El formato es una lista de argumentos separados por espacios, que opcionalmente pueden escaparse individualmente para permitir la inclusión de espacios en blanco y otros caracteres de control.

Esta clave se puede listar varias veces.

Quiet=

Suprime la información de salida al descargar artefactos.

Esto es equivalente a la opción podman --quiet.

Retry=

Número de veces que se reintentará la descarga del artefacto cuando ocurra un error HTTP. Equivalente a la opción podman --retry.

RetryDelay=

Retraso entre reintentos. Equivalente a la opción podman --retry-delay.

ServiceName=

El nombre (opcional) del servicio systemd. Si no se especifica, el valor predeterminado es el mismo nombre que la unidad, pero con un sufijo -artifact, es decir, un archivo $name.artifact crea un servicio systemd $name-artifact.service.

TLSVerify=

Requiere HTTPS y verificación de certificados al contactar con los registros.

Esto es equivalente a la opción podman --tls-verify.

Sección Quadlet [Quadlet]

Alguna configuración específica de quadlet se comparte entre diferentes tipos de unidades. Esos ajustes se pueden configurar en la sección [Quadlet].

Las opciones válidas para [Quadlet] se enumeran a continuación:

Opciones de [Quadlet] Descripción
DefaultDependencies=false Deshabilita las dependencias de red implícitas a la unidad

DefaultDependencies=

Agrega las dependencias de red predeterminadas de Quadlet a la unidad (el valor predeterminado es true).

Cuando se establece en false, Quadlet no agregará una dependencia (After=, Wants=) a network-online.target/podman-user-wait-network-online.service a la unidad generada.

Nota: esta opción se establece en la sección [Quadlet]. La sección systemd [Unit] tiene una opción con el mismo nombre pero con un significado diferente.
