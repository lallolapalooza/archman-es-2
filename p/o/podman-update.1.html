NOMBRE

podman-update - Actualiza la configuración de un contenedor dado

SINOPSIS

podman update [opciones] contenedor

podman container update [opciones] contenedor

DESCRIPCIÓN

Actualiza la configuración de un contenedor existente, permitiendo cambios en los límites de recursos y las comprobaciones de estado (healthchecks).

OPCIONES

--blkio-weight=peso

Peso relativo de Block IO. El peso es un valor entre 10 y 1000.

Esta opción no se soporta en sistemas sin root cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo de Block IO por dispositivo.

--cpu-period=límite

Establece el período de CPU para el Completely Fair Scheduler (CFS), que es una duración en microsegundos. Una vez que la cuota de CPU del contenedor se agota, no se programará para ejecutarse hasta que finalice el período actual. Por defecto es de 100000 microsegundos.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--cpu-quota=límite

Limita la cuota del Completely Fair Scheduler (CFS) de la CPU.

Limita el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso de CPU completo. El límite es un número en microsegundos. Si se proporciona un número, al contenedor se le permite usar esa cantidad de tiempo de CPU hasta que termine el período de CPU (controlable a través de --cpu-period).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--cpu-rt-period=microsegundos

Limita el período de tiempo real de la CPU en microsegundos.

Limita el uso de CPU en tiempo real del contenedor. Esta opción indica al kernel que restrinja el uso de CPU en tiempo real del contenedor al período especificado.

Esta opción solo se soporta en sistemas con root cgroups V1.

--cpu-rt-runtime=microsegundos

Limita el tiempo de ejecución de tiempo real de la CPU en microsegundos.

Limita el uso de CPU en tiempo real de los contenedores. Esta opción indica al kernel que limite la cantidad de tiempo que las tareas de tiempo real pueden consumir en un período de CPU dado. Ej: Un período de 1.000.000 us y un tiempo de ejecución de 950.000 us significa que este contenedor puede consumir el 95% de la CPU disponible y dejar el 5% restante para tareas de prioridad normal.

La suma de todos los tiempos de ejecución entre contenedores no puede exceder la cantidad asignada al cgroup padre.

Esta opción solo se soporta en sistemas con root cgroups V1.

--cpu-shares, -c=cuotas

Cuotas de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de las cuotas de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso por defecto es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas de un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una cuota de CPU de 1024 y otros dos tienen una configuración de cuota de CPU de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con una cuota de CPU de 1024, el primer contenedor solo recibe el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las cuotas de tiempo de CPU se distribuyen entre todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de cuotas de CPU:

PID contenedor CPU Cuota de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--cpus=número

Número de CPUs. El valor por defecto es 0.0, lo que significa que no hay límite. Esto es un atajo para --cpu-period y --cpu-quota, por lo tanto, la opción no se puede especificar con --cpu-period o --cpu-quota.

En algunos sistemas, cambiar los límites de CPU puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--cpuset-cpus=número

CPUs en las cuales permitir la ejecución. Puede especificarse como una lista separada por comas (ej. 0,1), como un rango (ej. 0-3), o cualquier combinación de ellos (ej. 0-3,7,11-15).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los cuales permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), use --cpuset-mems=0,1, entonces los procesos en el contenedor solo usarán memoria de los dos primeros nodos de memoria.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--device-read-bps=ruta:tasa

Límita la tasa de lectura (en bytes por segundo) desde un dispositivo (ej. --device-read-bps=/dev/sda:1mb).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/ma

--device-read-iops=ruta:tasa

Límita la tasa de IOPS (operaciones de entrada/salida por segundo) desde un dispositivo (ej. --device-read-iops=/dev/sda:1000).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--device-write-bps=ruta:tasa

Límita la tasa de escritura (en bytes por segundo) a un dispositivo (ej. --device-write-bps=/dev/sda:1mb).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--device-write-iops=ruta:tasa

Límita la tasa de IOPS (operaciones de entrada/salida por segundo) a un dispositivo (ej. --device-write-iops=/dev/sda:1000).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--kernel-memory, -k=límite

Límite de memoria del kernel.

El límite es un número positivo de bytes, un sufijo de unidad (k, m, g) o unlimited para desactivar el límite. La memoria del kernel incluye memoria para el núcleo, pero no para los datos de los usuarios y el código.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--memory, -m=límite

Límite de memoria.

El límite es un número positivo de bytes, un sufijo de unidad (k, m, g) o unlimited para desactivar el límite. Por defecto, no hay límite.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--memory-reservation=límite

Límite de memoria reservada.

El límite es un número positivo de bytes, un sufijo de unidad (k, m, g) o unlimited para desactivar el límite. Por defecto, no hay límite.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--memory-swap=límite

Límite de memoria swap.

El límite es un número positivo de bytes, un sufijo de unidad (k, m, g) o unlimited para desactivar el límite. Por defecto, no hay límite.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--pids-limit=límite

Límite de PIDs.

El límite es un número positivo de PIDs o -1 para un límite ilimitado.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin root cgroups V1.

--restart=política

Establece la política de reinicio para el contenedor. Las políticas disponibles son: no, on-failure, unless-stopped, y always.

EJEMPLOS

Actualiza un contenedor para limitar su uso de CPU a 2 CPUs:

$ podman update --cpus=2 mycontainer

Actualiza un contenedor para limitar su memoria a 512MB:

$ podman update -m 512m mycontainer

Actualiza un contenedor para permitirle usar un peso de CPU relativo de 2048:

$ podman update -c 2048 mycontainer

Actualiza un contenedor para que tenga un límite de PIDs de 1000:

$ podman update --pids-limit=1000 mycontainer

Actualiza un contenedor para que se reinicie siempre:

$ podman update --restart=always mycontainer

Actualiza un contenedor para que se reinicie solo si falla:

$ podman update --restart=on-failure mycontainer

Actualiza un contenedor para que nunca se reinicie:

$ podman update --restart=no mycontainer

Actualiza un contenedor para que se reinicie a menos que se detenga manualmente:

$ podman update --restart=unless-stopped mycontainer

Elimina el límite de memoria de un contenedor:

$ podman update -m unlimited mycontainer

Elimina el límite de PIDs de un contenedor:

$ podman update --pids-limit=-1 mycontainer

Actualiza un contenedor para establecer la política de reinicio a 'no' y el límite de memoria a '512m':

$ podman update --restart=no -m 512m mycontainer

--env, -e=env

Añade un valor (p. ej. env=valor) al contenedor. Se puede usar múltiples veces. Si el valor ya existe en el contenedor, se sobrescribe. Para eliminar una variable de entorno del contenedor, usa la opción --unsetenv.

Ten en cuenta que las actualizaciones de variables de entorno solo afectan al proceso principal del contenedor después de la próxima vez que se inicie.

--health-cmd="comando" | '["comando", arg1 , ...]'

Establece o modifica un comando de verificación de salud para un contenedor. El comando es un comando que se ejecutará dentro del contenedor y que determina la salud del contenedor. El comando es necesario para que se apliquen otras opciones de verificación de salud. Un valor de none desactiva las verificaciones de salud existentes.

Se pueden pasar múltiples opciones en forma de una matriz JSON; de lo contrario, el comando se interpreta como un argumento para /bin/sh -c.

Nota: Se utilizan los valores predeterminados incluso si la verificación de salud está configurada en la imagen.

--health-interval=intervalo

Establece un intervalo para las verificaciones de salud. Un intervalo de disable (desactivar) resulta en que no se configure un temporizador automático. El valor predeterminado es 30s.

Nota: Este parámetro sobrescribirá la configuración relacionada de verificación de salud de la imagen.

Cambiar esta configuración reinicia el temporizador.

--health-log-destination=ruta_directorio

Establece el destino del registro de verificación de salud. Ruta del directorio, local o events_logger (uso local del archivo de estado del contenedor) (Predeterminado: local)

  • local: (predeterminado) Los registros de verificación de salud se almacenan en contenedores overlay. (Por ejemplo: $runroot/healthcheck.log)
  • directory: crea un archivo de registro llamado <ID_contenedor>-healthcheck.log con los registros de verificación de salud en el directorio especificado.
  • events_logger: El registro se escribirá con el mecanismo de registro establecido por events_logger. También guarda el registro en un directorio predeterminado, para mejorar el rendimiento en un sistema con un gran número de registros.

Advertencia: Cambiar esta configuración puede causar la pérdida de registros anteriores.

--health-max-log-count=número de registros almacenados

Establece el número máximo de intentos en el archivo de registro de verificación de salud. (El valor '0' significa un número infinito de intentos en el archivo de registro) (Predeterminado: 5 intentos)

--health-max-log-size=tamaño de registros almacenados

Establece la longitud máxima en caracteres del registro de verificación de salud almacenado. ("0" significa una longitud de registro infinita) (Predeterminado: 500 caracteres)

--health-on-failure=acción

Acción a tomar una vez que el contenedor transiciona a un estado no saludable. El valor predeterminado es none.

  • none: No hacer nada.
  • kill: Matar el contenedor.
  • restart: Reiniciar el contenedor. No combines la acción restart con la opción --restart. Al ejecutarse dentro de una unidad systemd, considera usar la acción kill o stop en su lugar para aprovechar la política de reinicio de systemd.
  • stop: Detener el contenedor.

--health-retries=reintentos

El número de reintentos permitidos antes de que una verificación de salud se considere no saludable. El valor predeterminado es 3.

Nota: Este parámetro puede sobrescribir la configuración de verificación de salud de la imagen.

--health-start-period=período

El tiempo de inicialización necesario para que un contenedor arranque. El valor se puede expresar en formato de tiempo como 2m3s. El valor predeterminado es 0s.

Nota: El comando de verificación de salud se ejecuta tan pronto como se inicia un contenedor. Si la verificación de salud es exitosa, el estado de salud del contenedor se actualizará a healthy. Sin embargo, si la verificación de salud falla, el estado de salud permanecerá como starting hasta que la verificación de salud sea exitosa o hasta que haya transcurrido el tiempo de --health-start-period. Si el comando de verificación de salud falla después de que haya transcurrido el tiempo de --health-start-period, el estado de salud se actualizará a unhealthy. El comando de verificación de salud se ejecuta periódicamente según el valor de --health-interval.

Nota: Este parámetro sobrescribirá la configuración relacionada de verificación de salud de la imagen.

--health-startup-cmd="comando" | '["comando", arg1 , ...]'

Establece un comando de verificación de salud de inicio para un contenedor. Este comando se ejecuta dentro del contenedor y se utiliza para controlar la verificación de salud regular. Cuando el comando de inicio tiene éxito, comienza la verificación de salud regular y la verificación de salud de inicio cesa. Opcionalmente, si el comando falla durante un número determinado de intentos, el contenedor se reinicia. Se puede utilizar una verificación de salud de inicio para garantizar que los contenedores con un período de inicio prolongado no se marquen como no saludables hasta que se hayan iniciado completamente. Las verificaciones de salud de inicio solo se pueden usar cuando también se establece una verificación de salud regular (de la imagen del contenedor o de la opción --health-cmd).

--health-startup-interval=intervalo

Establece un intervalo para la verificación de salud de inicio. Un intervalo de disable (desactivar) resulta en que no se configure un temporizador automático. El valor predeterminado es 30s.

Cambiar esta configuración reinicia el temporizador, dependiendo del estado del contenedor.

--health-startup-retries=reintentos

El número de intentos permitidos antes de que la verificación de salud de inicio reinicie el contenedor. Si se establece en 0, el contenedor nunca se reinicia. El valor predeterminado es 0.

--health-startup-success=reintentos

El número de ejecuciones exitosas requeridas antes de que la verificación de salud de inicio tenga éxito y comience la verificación de salud regular. Un valor de 0 significa que cualquier éxito inicia la verificación de salud regular.

--health-startup-timeout=tiempo_de_espera

El tiempo máximo que un comando de verificación de salud de inicio tiene para completarse antes de ser marcado como fallido. El valor se puede expresar en formato de tiempo como 2m3s. El valor predeterminado es 30s.

--health-timeout=tiempo_de_espera

El tiempo máximo permitido para completar la verificación de salud antes de que un intervalo se considere fallido. Al igual que start-period, el valor se puede expresar en formato de tiempo como 1m22s. El valor predeterminado es 30s.

Nota: Un tiempo de espera marca la verificación de salud como fallida. Si el comando de verificación de salud se ejecuta más tiempo que el tiempo_de_espera especificado, se le enviará una señal SIGKILL.

Nota: Este parámetro sobrescribirá la configuración relacionada de verificación de salud de la imagen.

--latest, -l

En lugar de proporcionar el nombre o ID del contenedor, utiliza el último contenedor creado. Nota: el último contenedor iniciado puede ser de otros usuarios de Podman en la máquina host. (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2))

--memory, -m=número[unidad]

Límite de memoria. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Permite restringir la memoria disponible para un contenedor. Si el host admite memoria swap, entonces la configuración de memoria -m puede ser mayor que la RAM física. Si se especifica un límite de 0 (sin usar -m), la memoria del contenedor no se limita. El límite real puede redondearse al múltiplo del tamaño de página del sistema operativo (el valor es muy grande, es decir, millones de billones).

Esta opción no se admite en sistemas sin root cgroups V1.

--memory-reservation=número[unidad]

Límite blando de memoria. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Después de establecer la reserva de memoria, cuando el sistema detecta contención de memoria o poca memoria, los contenedores se ven obligados a restringir su consumo a su reserva. Por lo tanto, siempre establece el valor por debajo de --memory, de lo contrario, el límite estricto tiene precedencia. Por defecto, la reserva de memoria es la misma que el límite de memoria.

Esta o

--memory-swap=número[unidad]

Un valor límite igual a la memoria más el swap. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Debe usarse con la opción -m (--memory). El valor del argumento debe ser mayor que el de
-m (--memory). Por defecto, se establece en el doble del valor de --memory.

Establece número en -1 para habilitar el swap ilimitado.

Esta opción no es compatible con sistemas sin root en cgroups V1.

--memory-swappiness=número

Ajusta el comportamiento de swappiness de memoria de un contenedor. Acepta un entero entre 0 y 100.

Esta opción solo es compatible con sistemas con root en cgroups V1.

--no-healthcheck

Deshabilita cualquier healthcheck definido para el contenedor.

--pids-limit=límite

Ajusta el límite de pids del contenedor. Establécelo en -1 para tener pids ilimitados para el contenedor. El valor por defecto es 2048 en sistemas que admiten el controlador cgroup "pids".

--restart=política

Política de reinicio a seguir cuando los contenedores salgan. La política de reinicio no tiene efecto si un contenedor se detiene mediante los comandos podman kill o podman stop.

Los valores válidos para política son:

  • no: No reiniciar contenedores al salir.
  • never: Sinónimo de no; no reiniciar contenedores al salir.
  • on-failure[:max_retries]: Reiniciar contenedores cuando salgan con un código de salida distinto de cero, reintentando indefinidamente o hasta que se alcance el recuento opcional de max_retries.
  • always: Reiniciar contenedores cuando salgan, independientemente del estado, reintentando indefinidamente.
  • unless-stopped: Idéntico a always.

Podman proporciona un archivo de unidad de systemd, podman-restart.service, que reinicia los contenedores después de un reinicio del sistema.

Al ejecutar contenedores en servicios systemd, utiliza la funcionalidad de reinicio proporcionada por systemd. Es decir, no utilices esta opción en una unidad de contenedor, en su lugar establece la directiva Restart= de systemd en la sección [Service]. Consulta podman-systemd.unit(5) y systemd.service(5).

--unsetenv=env

Elimina variables de entorno del contenedor.

Ten en cuenta que las actualizaciones de env solo afectan al proceso principal del contenedor después del próximo inicio.

EJEMPLOS

Actualiza un contenedor con una nueva cuota y período de CPU:

podman update --cpus=0.5 ctrID

Actualiza el último contenedor con un nuevo valor de CPU:

podman update --latest --cpus=1

Actualiza un contenedor con varias opciones a la vez:

podman update --cpus 5 --cpuset-cpus 0 --cpu-shares 123 --cpuset-mems 0 \
  --memory 1G --memory-swap 2G --memory-reservation 2G \
  --blkio-weight-device /dev/sda:123 --blkio-weight 123 \
  --device-read-bps /dev/sda:10mb --device-write-bps /dev/sda:10mb \
  --device-read-iops /dev/sda:1000 --device-write-iops /dev/sda:1000 \
  --pids-limit 123 ctrID
