NOMBRE

podman-build - Construir una imagen de contenedor usando un Containerfile

SINOPSIS

podman build [opciones] [contexto]

podman image build [opciones] [contexto]

DESCRIPCIÓN

podman build Construye una imagen utilizando instrucciones de uno o más Containerfiles o Dockerfiles y un directorio de contexto de compilación especificado. Un Containerfile usa la misma sintaxis que un Dockerfile internamente. Para este documento, un archivo al que se hace referencia como Containerfile puede llamarse 'Containerfile' o 'Dockerfile' exclusivamente. Cualquier archivo que tenga una extensión adicional no será reconocido por podman build . a menos que se utilice la opción -f para especificar el archivo.

El directorio de contexto de compilación se puede especificar como la URL http(s) de un archivo, un repositorio git o un Containerfile.

Cuando se invoca con -f y una ruta a un Containerfile, sin un directorio CONTEXT explícito, Podman utiliza el directorio padre del Containerfile como su contexto de compilación.

Los Containerfiles que terminan con el sufijo ".in" se preprocesan a través de CPP(1). Esto puede ser útil para descomponer Containerfiles en varias partes reutilizables que se pueden usar a través de la directiva #include de CPP. Los Containerfiles que terminan en .in están restringidos a no tener líneas de comentarios a menos que sean comandos CPP. Tenga en cuenta que un archivo Containerfile.in todavía puede ser utilizado por otras herramientas al preprocesarlos manualmente a través de cpp -E.

Cuando la URL es un archivo, el contenido de la URL se descarga a una ubicación temporal y se extrae antes de la ejecución.

Cuando la URL es un Containerfile, el Containerfile se descarga a una ubicación temporal.

Cuando la URL es un repositorio Git, el repositorio se clona localmente y luego se establece como el contexto. Una URL se trata como un repositorio Git si tiene el prefijo git:// o el sufijo .git.

NOTA: podman build utiliza código obtenido del proyecto Buildah para construir imágenes de contenedor. Este código de Buildah crea contenedores de Buildah para las opciones RUN en el almacenamiento de contenedores. En ciertas situaciones, cuando podman build falla o los usuarios matan el proceso podman build, estos contenedores externos pueden quedar en el almacenamiento de contenedores. Utilice el comando podman ps --all --external para ver estos contenedores.

El comando podman buildx build es un alias de podman build. No todas las características de buildx build están disponibles en Podman. La opción buildx build se proporciona para compatibilidad de scripts.

OPCIONES

--add-host=nombre_host[;nombre_host[;...]]:ip

Agrega un mapeo personalizado de host a IP al archivo /etc/hosts del contenedor.

La opción toma uno o más nombres de host separados por punto y coma para ser mapeados a una única dirección IPv4 o IPv6, separados por dos puntos. También se puede utilizar para sobrescribir las direcciones IP de los nombres de host que Podman agrega a /etc/hosts por defecto (ver también las opciones --name y --hostname). Esta opción se puede especificar varias veces para agregar mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede dar el indicador especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de su configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que hará que Podman falle con un mensaje de error. Puede sobrescribir esta dirección IP utilizando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para agregar automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitarlo dando la opción --no-hosts, o configurando host_containers_internal_ip="none" en containers.conf. Si no se configuró una dirección host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se está ejecutando en una máquina virtual usando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven por el resolvedor DNS gvproxy en su lugar.

Podman utilizará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente utilizando la configuración base_hosts_file en containers.conf.

--all-platforms

En lugar de construir para un conjunto de plataformas especificado usando la opción --platform, inspecciona las imágenes base de la compilación y construye para todas las plataformas para las que están disponibles. Las etapas que usan scratch como punto de partida no se pueden inspeccionar, por lo que al menos una etapa que no sea de scratch debe estar presente para que la detección funcione útilmente.

--annotation=anotacion=valor

Agrega una anotación de imagen (por ejemplo, anotacion=valor) a los metadatos de la imagen. Se puede usar múltiples veces.

Nota: esta información no está presente en los formatos de imagen de Docker, por lo que se descarta al escribir imágenes en formatos de Docker.

--arch=arch

Establece la arquitectura de la imagen a construir, y la de la imagen base a descargar, si la compilación utiliza una, al valor proporcionado en lugar de usar la arquitectura del host de compilación. A menos que se sobrescriba, las búsquedas posteriores de la misma imagen en el almacenamiento local coinciden con esta arquitectura, independientemente del host. (Ejemplos: arm, arm64, 386, amd64, ppc64le, s390x)

--authfile=ruta

Ruta del archivo de autenticación. Por defecto es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo es creado por podman login. Si el estado de autorización no se encuentra allí, se verifica $HOME/.docker/config.json, que se establece usando docker login.

Nota: También existe la opción de sobrescribir la ruta por defecto del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

--build-arg=arg=valor

Especifica un argumento de compilación y su valor, que se interpola en las instrucciones leídas de los Containerfiles de la misma manera que las variables de entorno, pero que no se agregan a la lista de variables de entorno en la configuración de la imagen resultante.

--build-arg-file=ruta

Especifica un archivo que contiene líneas de argumentos de compilación de la forma arg=valor. El nombre de archivo sugerido es argfile.conf.

Las líneas de comentarios que comienzan con # se ignoran, al igual que las líneas en blanco. Todas las demás deben tener el formato arg=valor pasado a --build-arg.

Si se proporcionan varios argumentos a través de las opciones --build-arg-file y --build-arg, los argumentos de compilación se fusionan en todos los archivos proporcionados y los argumentos de la línea de comandos.

Cualquier archivo proporcionado en una opción --build-arg-file se lee antes que los argumentos proporcionados a través de la opción --build-arg.

Cuando se especifica un nombre de argumento varias veces, la última instancia es la que se pasa a las compilaciones resultantes. Esto significa que los valores de --build-arg siempre anulan a los de un --build-arg-file.

--build-context=nombre=valor

Especifica un contexto de compilación adicional usando su nombre corto y su ubicación. Los contextos de compilación adicionales se pueden referenciar de la misma manera que accedemos a diferentes etapas en la instrucción COPY.

Los valores válidos son:

  • Directorio local – por ejemplo, --build-context proyecto2=../ruta/a/proyecto2/src
  • URL HTTP a un archivo tar – por ejemplo, --build-context src=https://example.org/releases/src.tar
  • Imagen de contenedor – especificada con un prefijo container-image://, por ejemplo, --build-context alpine=container-imag

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

e://alpine:3.15, (también acepta docker://, docker-image://)

En el lado de Containerfile, haga referencia al contexto de compilación en todos los comandos que aceptan el parámetro “from”. Así es como podría verse:

FROM [nombre]
COPY --from=[nombre] ...
RUN --mount=from=[nombre] …

El valor de [nombre] se compara con el siguiente orden de prioridad:

  • Contexto de compilación nombrado definido con --build-context [nombre]=..
  • Etapa definida con AS [nombre] dentro de Containerfile
  • Imagen [nombre], local o en un registro remoto

--cache-from=imagen

Repositorio a utilizar como posible fuente de caché. Cuando se especifica, Buildah intenta buscar imágenes de caché en el repositorio especificado y intenta descargar imágenes de caché en lugar de ejecutar los pasos de compilación localmente. Buildah solo intenta descargar imágenes previamente cacheadas si se consideran como aciertos de caché válidos.

Utilice la opción --cache-to para poblar un repositorio remoto con contenido de caché.

Ejemplo

# poblar una caché y también consultarla
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Nota: La opción --cache-from se ignora a menos que se especifique --layers.

--cache-to=imagen

Establezca esta opción para especificar un repositorio remoto que se utiliza para almacenar imágenes de caché. Buildah intenta enviar la imagen de caché recién compilada al repositorio remoto.

Nota: Utilice la opción --cache-from para utilizar contenido de caché en un repositorio remoto.

Ejemplo

# poblar una caché y también consultarla
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Nota: La opción --cache-to se ignora a menos que se especifique --layers.

--cache-ttl

Limite el uso de imágenes cacheadas para considerar solo imágenes con marcas de tiempo de creación inferiores a duración. Por ejemplo, si se especifica --cache-ttl=1h, Buildah considera imágenes de caché intermedias que se crean en menos de una hora, y las imágenes de caché intermedias fuera de esta duración se ignoran.

Nota: Establecer --cache-ttl=0 manualmente es equivalente a usar --no-cache en la implementación, ya que esto significa que el usuario no quiere usar caché en absoluto.

--cap-add=CAP_xxx

Al ejecutar instrucciones RUN, ejecute el comando especificado en la instrucción con la capacidad especificada añadida a su conjunto de capacidades. Ciertas capacidades se otorgan por defecto; esta opción se puede usar para añadir más.

--cap-drop=CAP_xxx

Al ejecutar instrucciones RUN, ejecute el comando especificado en la instrucción con la capacidad especificada eliminada de su conjunto de capacidades. Las capacidades CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP y CAP_SETUID se otorgan por defecto; esta opción se puede usar para eliminarlas.

Si una capacidad se especifica tanto para las opciones --cap-add como para --cap-drop, se elimina, independientemente del orden en que se hayan dado las opciones.

--cert-dir=ruta

Utilice los certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. (Predeterminado: /etc/containers/certs.d) Para más detalles, consulte containers-certs.d(5). (Esta opción no está disponible con el cliente Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se crea el cgroup para el contenedor. Si la ruta no es absoluta, la ruta se considera relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen.

--cgroupns=cómo

Establece la configuración para los namespaces de cgroup al manejar instrucciones RUN. El valor configurado puede ser "" (cadena vacía) o "private" para indicar que se crea un nuevo namespace de cgroup, o puede ser "host" para indicar que se reutiliza el namespace de cgroup en el que se está ejecutando buildah.

--compat-volumes

Maneja directorios marcados usando la instrucción VOLUME (tanto en esta compilación como los heredados de imágenes base) de manera que su contenido solo pueda ser modificado por instrucciones ADD y COPY. Cualquier cambio realizado en esas ubicaciones por instrucciones RUN será revertido. Antes de la introducción de esta opción, este comportamiento era el predeterminado, pero ahora está deshabilitado por defecto.

--compress

Esta opción se añade para alinearse con otras CLIs de contenedores. Podman no se comunica con un daemon o un servidor remoto. Por lo tanto, comprimir los datos antes de enviarlos es irrelevante para Podman. (Esta opción no está disponible con el cliente Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--cpp-flag=flags

Establezca indicadores adicionales para pasar al preprocesador C cpp(1). Los Containerfiles que terminan con el sufijo ".in" se preprocesan a través de cpp(1). Esta opción se puede usar para pasar indicadores adicionales a cpp. Nota: También puede establecer CPPFLAGS predeterminados estableciendo la variable de entorno BUILDAH_CPPFLAGS (por ejemplo, export BUILDAH_CPPFLAGS="-DDEBUG").

--cpu-period=límite

Establezca el período de CPU para el planificador Completely Fair Scheduler (CFS), que es una duración en microsegundos. Una vez que la cuota de CPU del contenedor se agota, no se programará para ejecutarse hasta que finalice el período actual. El valor predeterminado es 100000 microsegundos.

En algunos sistemas, el cambio de los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root de cgroups V1.

--cpu-quota=límite

Limite la cuota de CPU del Completely Fair Scheduler (CFS).

Limite el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso completo de CPU. El límite es un número en microsegundos. Si se proporciona un número, el contenedor puede usar esa cantidad de tiempo de CPU hasta que finalice el período de CPU (controlable mediante --cpu-period).

En algunos sistemas, el cambio de los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root de cgroups V1.

--cpu-shares, -c=shares

Comparticiones de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando la ponderación de compartición de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso predeterminado es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía según el número de contenedores que se ejecutan en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una cuota de CPU de 1024 y los otros dos tienen una configuración de cuota de CPU de 512. Cuando los procesos en los tres contenedores intentan utilizar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con una cuota de CPU de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las comparticiones de tiempo de CPU se distribuyen en todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de comparticiones de CPU:

PID contenedor CPU Compartición de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, el cambio de los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root de cgroups V1.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de ellos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, el cambio de los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root de cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), utilice --cpuset-mems=0,1 entonces los procesos en el contenedor solo usan memoria de los dos primeros nodos de memoria.

En algunos sistemas, el cambio de los límites de recursos ma

y no se permite para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se soporta en sistemas sin raíz cgroups V1.

--created-annotation

Añade una anotación a la imagen (ver también --annotation) a los metadatos de la imagen estableciendo "org.opencontainers.image.created" a la hora actual, o a la marca de fecha especificada en el flag --source-date-epoch o --timestamp, si alguno de ellos fue utilizado. Si es false, no habrá tal anotación en la imagen escrita.

Nota: esta información no está presente en los formatos de imagen de Docker, por lo que se descarta al escribir imágenes en formatos de Docker.

--creds=[usuario[:contraseña]]

El [usuario[:contraseña]] a usar para autenticarse con el registro, si es requerido. Si uno o ambos valores no son proporcionados, aparece un prompt en la línea de comandos y el valor puede ser introducido. La contraseña se introduce sin eco.

Tenga en cuenta que las credenciales especificadas solo se usan para autenticarse contra los registros de destino. No se utilizan para espejos o cuando el registro se reescribe (ver containers-registries.conf(5)); para autenticarse contra ellos considere usar un archivo containers-auth.json(5).

--cw=opciones

Produce una imagen adecuada para ser utilizada como una carga de trabajo confidencial ejecutándose en un entorno de ejecución confiable (TEE) usando krun (es decir, crun compilado con la característica libkrun habilitada e invocado como krun). En lugar de los contenidos convencionales, el sistema de archivos raíz de la imagen contendrá una imagen de disco cifrada e información de configuración para krun.

El valor para opciones es una lista separada por comas de pares clave=valor, proporcionando información de configuración que es necesaria para producir los datos adicionales que se incluirán en la imagen del contenedor.

Las claves reconocidas son:

attestation_url: La ubicación de un servidor de claves/atestación. Si se especifica un valor, el ID de carga de trabajo de la nueva imagen, junto con la contraseña utilizada para cifrar la imagen de disco, se registrarán con el servidor, y la ubicación del servidor se almacenará en la imagen del contenedor. En tiempo de ejecución, se espera que krun contacte al servidor para recuperar la contraseña usando el ID de carga de trabajo, que también se almacena en la imagen del contenedor. Si no se especifica ningún valor, se debe especificar un valor de passphrase.

cpus: El número de CPUs virtuales con las que se espera que se ejecute la imagen en tiempo de ejecución. Si no se especifica, se proporcionará un valor predeterminado.

firmware_library: La ubicación de la biblioteca compartida libkrunfw-sev. Si no se especifica, buildah busca su presencia en varias ubicaciones codificadas.

memory: La cantidad de memoria con la que se espera que se ejecute la imagen en tiempo de ejecución, como número de megabytes. Si no se especifica, se proporcionará un valor predeterminado.

passphrase: La contraseña a utilizar para cifrar la imagen de disco que se incluirá en la imagen del contenedor. Si no se especifica ningún valor, pero se especifica un valor de attestation_url, se utilizará una contraseña generada aleatoriamente. Los autores recomiendan establecer una attestation_url pero no una passphrase.

slop: Espacio adicional a asignar para la imagen de disco en comparación con el tamaño de los contenidos de la imagen del contenedor, expresado como un porcentaje (..%) o un valor de tamaño (bytes, o unidades más grandes si hay sufijos como KB o MB), o una suma de dos o más de dichas especificaciones. Si no se especifica, buildah estima que el 25% más de espacio que los contenidos será suficiente, pero esta opción se proporciona en caso de que su estimación sea incorrecta.

type: El tipo de entorno de ejecución confiable (TEE) para el cual la imagen debe ser marcada para su uso. Los valores aceptados son "SEV" (AMD Secure Encrypted Virtualization - Encrypted State) y "SNP" (AMD Secure Encrypted Virtualization - Secure Nested Paging). Si no se especifica, el valor predeterminado es "SNP".

workload_id: Un identificador de carga de trabajo que se registrará en la imagen del contenedor, para ser utilizado en tiempo de ejecución para recuperar la contraseña que se utilizó para cifrar la imagen de disco. Si no se especifica, se derivará un valor semi-aleatorio del ID de imagen de la imagen base.

Esta opción no se soporta en el cliente remoto, incluyendo máquinas Mac y Windows (excluyendo WSL2).

--decryption-key=clave[:contraseña]

La [clave[:contraseña]] a utilizar para el descifrado de imágenes. La clave puede apuntar a claves y/o certificados. El descifrado se intenta con todas las claves. Si la clave está protegida por una contraseña, esta debe ser pasada en el argumento y omitida de lo contrario.

--device=dispositivo-host[:dispositivo-contenedor][:permisos]

Añade un dispositivo host al contenedor. El parámetro opcional permisos se puede usar para especificar los permisos del dispositivo combinando r para leer, w para escribir y m para mknod(2).

Ejemplo: --device=/dev/sdc:/dev/xvdc:rwm.

Nota: si dispositivo-host es un enlace simbólico, primero se resuelve. El contenedor solo almacena los números mayor y menor del dispositivo host.

Podman puede cargar módulos del kernel necesarios para usar el dispositivo especificado. Los dispositivos para los que Podman carga módulos cuando es necesario son: /dev/fuse.

En modo sin raíz, el nuevo dispositivo se monta bind en el contenedor desde el host en lugar de que Podman lo cree dentro del espacio del contenedor. Debido a que el montaje bind conserva su etiqueta SELinux en sistemas SELinux, el contenedor puede obtener un error de permiso al acceder al dispositivo montado. Modifique la configuración de SELinux para permitir que los contenedores usen todas las etiquetas de dispositivos mediante el siguiente comando:

$ sudo setsebool -P container_use_devices=true

Nota: si el usuario solo tiene derechos de acceso a través de un grupo, el acceso al dispositivo desde dentro de un contenedor sin raíz falla. El runtime crun(1) ofrece una solución para esto añadiendo la opción --annotation run.oci.keep_original_groups=1.

--disable-compression, -D

No comprimir las capas del sistema de archivos al construir la imagen a menos que sea requerido por la ubicación donde se está escribiendo la imagen. Esta es la configuración predeterminada, ya que las capas de imagen se comprimen automáticamente cuando se envían a los registros, y las imágenes que se escriben en el almacenamiento local solo necesitan ser descomprimidas de nuevo para ser almacenadas. La compresión se puede forzar en todos los casos especificando --disable-compression=false.

--disable-content-trust

Esta es una opción específica de Docker para deshabilitar la verificación de imágenes a un registro de contenedores y no es soportada por Podman. Esta opción es un NOOP y se proporciona únicamente por compatibilidad de scripts.

--dns=direccionip

Establecer servidores DNS personalizados.

Esta opción se puede usar para anular la configuración DNS que se pasa al contenedor. Típicamente, esto es necesario cuando la configuración DNS del host no es válida para el contenedor (por ejemplo, 127.0.0.1). Cuando este es el caso, el flag --dns es necesario para cada ejecución.

El valor especial none puede ser especificado para deshabilitar la creación de /etc/resolv.conf en el contenedor por Podman. El archivo /etc/resolv.conf en la imagen se usa entonces sin cambios.

En cuanto a las opciones de pasta(1), se proporciona --config-net por defecto, para configurar la red cuando se inicia el contenedor, y también se asume --no-map-gw por defecto, para evitar el acceso directo del contenedor al host utilizando la dirección de la puerta de enlace.   • pasta:--mtu,1500: Especifica un MTU de 1500 bytes para la interfaz tap en el contenedor.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con puerta de enlace 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece el MTU a 1500 bytes, deshabilita NDP, DHCPv6 y soporte DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: lo mismo que lo anterior, pero deja el MTU en 65520 bytes
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto: habilita el reenvío automático de puertos basado en los puertos vinculados observados de ambos lados (host y contenedor)
  • pasta:-T,5201: habilita el reenvío del puerto TCP 5201 del contenedor al host, utilizando la interfaz de bucle invertido en lugar de la interfaz tap para mejorar el rendimiento

--output, -o=opts_salida

La opción --output (o -o) extiende el comportamiento predeterminado de compilar una imagen de contenedor al permitir a los usuarios exportar el contenido de la imagen como archivos en el sistema de archivos local, lo cual puede ser útil para generar binarios locales, generación de código, etc. (Esta opción no está disponible con el cliente Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

El valor de --output es una secuencia de pares clave=valor separados por comas, que definen el tipo y las opciones de salida.

Las claves admitidas son: - dest: Ruta de destino para la salida exportada. El valor válido es una ruta absoluta o relativa, - significa la salida estándar. - type: Define el tipo de salida que se utilizará. Los valores válidos se documentan a continuación.

Los valores de type válidos son: - local: escribe los archivos de compilación resultantes en un directorio en el lado del cliente. - tar: escribe los archivos resultantes como un único archivo tar (.tar).

Si no se especifica ningún tipo, el valor predeterminado es local. Alternativamente, en lugar de una secuencia separada por comas, el valor de --output puede ser solo un destino (en formato dest) (por ejemplo, --output ruta-alguna, --output -) donde --output ruta-alguna se trata como si type=local y --output - se trata como si type=tar.

    documentos cuando la combinación de sus valores "name" y "versionInfo" ya está
    presente. Los documentos se procesan en el orden en que se generan, que es el orden en que se especificaron los comandos que los generan.

El valor del secreto se leerá de una variable de entorno o archivo llamado por la opción "id", o llamado por la opción "src" si se especifica, o de una variable de entorno especificada por la opción "env". --source-date-epoch=segundos

Establece la marca de tiempo "created" para la imagen compilada en este número de segundos desde la época (hora Unix 0, es decir, 00:00:00 UTC del 1 de enero de 1970) (el valor predeterminado es usar el valor establecido en la variable de entorno SOURCE_DATE_EPOCH, o la hora actual si no está establecida).

La marca de tiempo "created" se escribe en la configuración y el manifiesto de la imagen cuando se confirma la imagen, por lo que ejecutar la misma compilación dos veces producirá imágenes con diferentes hashes sha256, incluso si no se realizaron otros cambios en el Containerfile y el contexto de compilación.

Cuando se establece este indicador, un argumento de compilación SOURCE_DATE_EPOCH proporcionará su valor para una etapa en la que se declare.

Cuando se establece este indicador, la marca de tiempo "created" de la configuración de la imagen siempre se establece en la hora especificada, lo que debería permitir la compilación de imágenes idénticas en diferentes momentos utilizando el mismo conjunto de entradas.

Cuando se establece este indicador, la salida escrita según lo especificado en el indicador --output llevará exactamente la marca de tiempo especificada.

Entra en conflicto con el indicador similar --timestamp

, que también establece su tiempo especificado en el contenido de las nuevas capas.

--timestamp=segundos

Establece la marca de tiempo de creación en segundos desde la época para permitir compilaciones deterministas (predeterminado a la hora actual). Por defecto, la marca de tiempo creada se cambia y se escribe en el manifiesto de la imagen con cada commit, lo que hace que el hash sha256 de la imagen sea diferente incluso si las fuentes son exactamente las mismas en otros aspectos. Cuando se establece --timestamp, la marca de tiempo creada siempre se establece en la hora especificada y, por lo tanto, no cambia, lo que permite que el hash sha256 de la imagen permanezca igual. Todos los archivos que se incluyan en las capas de la imagen se crearán con la marca de tiempo.

Si la única instrucción en un Containerfile es FROM, esta bandera no tiene ningún efecto.

--volume, -v=[DIR-HOST:DIR-CONTENEDOR[:OPCIONES]]

Monta un directorio del host en los contenedores al ejecutar instrucciones RUN durante la compilación.

Las OPCIONES son una lista separada por comas y pueden ser una o más de:

  • [rw|ro]
  • [z|Z|O]
  • [U]
  • [[r]shared|[r]slave|[r]private][1] ⟨#Footnote1⟩

El DIR-CONTENEDOR debe ser una ruta absoluta como /src/docs. El DIR-HOST también debe ser una ruta absoluta. Podman monta por enlace (bind-mounts) el DIR-HOST a la ruta especificada al procesar instrucciones RUN.

Puedes especificar múltiples opciones -v para montar uno o más montajes.

Puedes añadir el sufijo :ro o :rw a un volumen para montarlo en modo de solo lectura o lectura/escritura, respectivamente. Por defecto, los volúmenes se montan en modo lectura/escritura. Ver ejemplos.

Cambio de propietario de los montajes de volumen

Por defecto, Podman no cambia el propietario ni el grupo de los directorios de origen de los volúmenes montados. Al ejecutarse utilizando espacios de nombres de usuario, la UID y GID dentro del espacio de nombres pueden

corresponden a otra UID y GID en el host.

El sufijo :U indica a Podman que use la UID y GID del host correctas basadas en la UID y GID dentro del namespace, para cambiar recursivamente el propietario y el grupo del volumen de origen.

Advertencia: Úselo con precaución ya que esto modifica el sistema de archivos del host.

Etiquetado de montajes de volumen

Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. De forma predeterminada, Podman no cambia las etiquetas establecidas por el SO.

Para cambiar una etiqueta en el contexto del contenedor, agregue uno de estos dos sufijos, :z o :Z, al montaje del volumen. Estos sufijos indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le indica a Podman que dos contenedores comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartidas permiten que todos los contenedores lean/escriban el contenido. La opción Z indica a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el contenedor actual puede utilizar un volumen privado.

Nota: No vuelva a etiquetar archivos y directorios del sistema. Volver a etiquetar contenido del sistema podría provocar que otros servicios restringidos en la máquina host fallen. Para estos tipos de contenedores, se recomienda deshabilitar la separación de SELinux. La opción --security-opt label=disable deshabilita la separación de SELinux para el contenedor. Por ejemplo, si un usuario quisiera montar su directorio personal completo en los contenedores de compilación, necesitaría deshabilitar la separación de SELinux.

$ podman build --security-opt label=disable -v $HOME:/home/user .

Montajes de volumen superpuestos

El indicador :O le indica a Podman que monte el directorio del host como almacenamiento temporal utilizando el sistema de archivos Overlay. Los contenedores de comandos RUN pueden modificar el contenido dentro del punto de montaje y se almacena en el almacenamiento del contenedor en un directorio separado. En términos de Overlay FS, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando finaliza la ejecución del comando RUN, de manera similar a un punto de montaje tmpfs.

Cualquier ejecución posterior de comandos RUN ve el contenido original del directorio de origen; los cambios de comandos RUN anteriores ya no existen.

Un caso de uso del montaje overlay es compartir la caché de paquetes del host en el contenedor para acelerar las compilaciones.

Nota:

  • Los montajes Overlay no son compatibles actualmente en modo sin privilegios (rootless).
  • El indicador O no se permite especificar con los indicadores Z o z. El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor. Si no es así, la separación de contenedores de SELinux debe deshabilitarse para que el contenedor funcione.
  • La modificación del directorio montado en el contenedor con un montaje overlay puede causar fallos inesperados. No modifique el directorio hasta que el contenedor termine de ejecutarse.

De forma predeterminada, los volúmenes montados por enlace (bind mounted) son privados. Esto significa que cualquier montaje realizado dentro de los contenedores no será visible en el host y viceversa. Este comportamiento se puede cambiar especificando una propiedad de propagación del montaje de volumen.

Cuando la política de propagación de montaje se establece en shared, cualquier montaje realizado dentro del contenedor en ese volumen será visible tanto para el host como para el contenedor. Cuando la política de propagación de montaje se establece en slave, se habilita la propagación de montaje unidireccional y cualquier montaje realizado en el host para ese volumen solo será visible dentro del contenedor. Para controlar la propiedad de propagación de montaje del volumen, use los indicadores de propagación :[r]shared, :[r]slave o :[r]private. Para que la propagación de montaje funcione, el punto de montaje de origen (el punto de montaje donde se monta el directorio de origen) debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe ser compartido. Y para volúmenes slave, el montaje de origen debe ser compartido o slave. [1] ⟨#Footnote1⟩

Use df <directorio-origen> para determinar el montaje de origen y luego use findmnt -o TARGET,PROPAGATION <directorio-montaje-origen> para determinar las propiedades de propagación del montaje de origen. Si la utilidad findmnt no está disponible, el punto de montaje de origen se puede determinar buscando la entrada de montaje en /proc/self/mountinfo. Busque los campos opcionales y vea si se especifican propiedades de propagación. shared:X significa que el montaje está compartido, master:X significa que el montaje es slave y si no hay nada, significa que el montaje es privado. [1] ⟨#Footnote1⟩

Para cambiar las propiedades de propagación de un punto de montaje, use el comando mount. Por ejemplo, para montar por enlace el directorio de origen /foo, ejecute mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convierte /foo en un punto de montaje shared. Las propiedades de propagación del montaje de origen se pueden cambiar directamente. Por ejemplo, si / es el montaje de origen para /foo, entonces use mount --make-shared / para convertir / en un montaje shared.

podman-image-build(1)

NAME

podman-image-build - Build an image from a Containerfile or Dockerfile

SYNOPSIS

podman image build [options] CONTEXT

podman build [options] CONTEXT

DESCRIPTION

The podman image build command builds an image using instructions from a Containerfile or Dockerfile. The CONTEXT can be a URL to a git repository, a URL to a tarball, or a path to a directory containing a Containerfile/Dockerfile.

The build context is sent to the daemon and the image is built there.

The build process can be configured using various options like setting the build command, specifying a Containerfile, defining build arguments, setting the output format, and more.

OPTIONS

All the options available in docker build are also available in podman image build.

The full set of options is detailed in podman-build(1).

EXAMPLES

Building an image using a URL to a Containerfile

Build image from Containerfile downloaded into temporary location used as the build context:

$ podman build https://10.10.10.1/podman/Containerfile

Building an image using a Git repository

Podman clones the specified GitHub repository to a temporary location and uses it as the context. The Containerfile at the root of the repository is used and it only works if the GitHub repository is a dedicated repository.

Build image from specified git repository downloaded into temporary location used as the build context:

$ podman build -t hello  https://github.com/containers/PodmanHello.git
$ podman run hello

Note: GitHub does not support using git:// for performing clone operation due to recent changes in their security guidance (https://github.blog/2021-09-01-improving-git-protocol-security-github/). Use an https:// URL if the source repository is hosted on GitHub.

Building an image using a URL to an archive

Podman fetches the archive file, decompresses it, and uses its contents as the build context. The Containerfile at the root of the archive and the rest of the archive are used as the context of the build. Passing the -f PATH/Containerfile option as well tells the system to look for that file inside the contents of the archive.

$ podman build -f dev/Containerfile https://10.10.10.1/podman/context.tar.gz

Note: supported compression formats are 'xz', 'bzip2', 'gzip' and 'identity' (no compression).

Files

.containerignore/.dockerignore

If the file .containerignore or .dockerignore exists in the context directory, podman build reads its contents. Use the --ignorefile option to override the .containerignore path location. Podman uses the content to exclude files and directories from the context directory, when executing COPY and ADD directives in the Containerfile/Dockerfile

The .containerignore and .dockerignore files use the same syntax; if both are in the context directory, podman build only uses .containerignore.

Users can specify a series of Unix shell globs in a .containerignore file to identify files/directories to exclude.

Podman supports a special wildcard string ** which matches any number of directories (including zero). For example, */.go excludes all files that end with .go that are found in all directories.

Example .containerignore file:

# exclude this content for image
*/*.c
**/output*
src

*/*.c Excludes files and directories whose names ends with .c in any top level subdirectory. For example, the source file include/rootless.c.

**/output* Excludes files and directories starting with output from any directory.

src Excludes files named src and the directory src as well as any content in it.

Lines starting with ! (exclamation mark) can be used to make exceptions to exclusions. The following is an example .containerignore file that uses this mechanism:

*.doc
!Help.doc

Exclude all doc files except Help.doc from the image.

This functionality is compatible with the handling of .containerignore files described here: containerignore(5)

registries.conf (/etc/containers/registries.conf)

registries.conf is the configuration file which specifies which container registries is consulted when completing image names which do not include a registry or domain portion. See containers-registries.conf(5)

Troubleshooting

lastlog sparse file

Using a useradd command within a Containerfile with a large UID/GID creates a large sparse file /var/log/lastlog. This can cause the build to hang forever. Go language does not support sparse files correctly, which can lead to some huge files being created in the container image.

When using the useradd command within the build script, pass the --no-log-init or -l option to the useradd command. This option tells useradd to stop creating the lastlog file.
