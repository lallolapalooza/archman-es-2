NOMBRE

podman-auto-update - Actualiza automáticamente los contenedores según su política de actualización automática

SINOPSIS

podman auto-update [opciones]

DESCRIPCIÓN

podman auto-update descarga nuevas imágenes de contenedores y reinicia los contenedores configurados para actualizaciones automáticas. Para hacer uso de las actualizaciones automáticas, el contenedor o las cargas de trabajo de Kubernetes deben ejecutarse dentro de una unidad systemd. Después de una actualización exitosa de una imagen, los contenedores que utilizan la imagen se actualizan reiniciando las unidades systemd en las que se ejecutan. Consulte podman-systemd.unit(5) sobre cómo ejecutar Podman bajo systemd.

Para configurar un contenedor para actualizaciones automáticas, debe crearse con la etiqueta io.containers.autoupdate o el campo AutoUpdate en podman-systemd.unit(5) con uno de los siguientes dos valores:

  • registry: Si la etiqueta está presente y configurada como registry, Podman se conecta al registro correspondiente para verificar si la imagen se ha actualizado. La etiqueta image es una alternativa a registry mantenida por compatibilidad con versiones anteriores. Una imagen se considera actualizada si el digest en el almacenamiento local es diferente al de la imagen remota. Si una imagen debe actualizarse, Podman la descarga y reinicia la unidad systemd que ejecuta el contenedor. La política de registro requiere que se utilice una referencia de imagen completamente calificada (por ejemplo, quay.io/podman/stable:latest) para crear el contenedor. Esta aplicación es necesaria para saber qué imagen comprobar y descargar. Si se utilizara un ID de imagen, Podman no sabría qué imagen comprobar/descargar.
  • local: Si la etiqueta de actualización automática está configurada como local, Podman compara el digest de la imagen del contenedor con el del almacenamiento de contenedores local. Si difieren, la imagen local se considera más nueva y la unidad systemd se reinicia.

Actualizaciones Automáticas y YAML de Kubernetes

Podman admite actualizaciones automáticas para cargas de trabajo de Kubernetes. La política de actualización automática se puede configurar directamente a través de podman-systemd.unit(5) o dentro del YAML de Kubernetes con las anotaciones específicas de Podman mencionadas a continuación:

  • io.containers.autoupdate: "registry|local" para aplicar la política de actualización automática a todos los contenedores
  • io.containers.autoupdate/$container: "registry|local" para aplicar la política de actualización automática solo a $container
  • io.containers.sdnotify: "conmon|container" para aplicar la política de sdnotify a todos los contenedores
  • io.containers.sdnotify/$container: "conmon|container" para aplicar la política de sdnotify solo a $container

Por defecto, la política de actualización automática se establece en "disabled", la política de sdnotify se establece en "conmon".

Unidad y Temporizador Systemd

Podman incluye una unidad systemd podman-auto-update.service. Esta unidad se activa diariamente a medianoche por el temporizador systemd podman-auto-update.timer. El temporizador se puede modificar para actualizaciones personalizadas basadas en el tiempo si se desea. La unidad se puede invocar además mediante otras unidades systemd (por ejemplo, a través del árbol de dependencias) o manualmente a través de systemctl start podman-auto-update.service.

OPCIONES

--authfile=ruta

Ruta del archivo de autenticación. El valor predeterminado es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo lo crea podman login. Si no se encuentra el estado de autorización allí, se comprueba $HOME/.docker/config.json, que se establece usando docker login.

Nota: También existe la opción de anular la ruta predeterminada del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

Alternativamente, se puede configurar la etiqueta de contenedor io.containers.autoupdate.authfile. En ese caso, Podman utilizará el valor especificado en la etiqueta.

--dry-run

Verifica la disponibilidad de nuevas imágenes pero no realiza ninguna operación de descarga ni reinicia ningún servicio o contenedor. El campo UPDATED indica la disponibilidad de una nueva imagen con "pending".

--format=formato

Cambia el formato de salida predeterminado. Puede ser de un tipo admitido como 'json' o una plantilla Go. Los marcadores válidos para la plantilla Go se enumeran a continuación:

Marcador Descripción
.Container ID y nombre del contenedor
.ContainerID ID del contenedor
.ContainerName Nombre del contenedor
.Image Nombre de la imagen
.Policy Política de actualización automática del contenedor
.Unit Nombre de la unidad systemd
.Updated Estado de actualización: true, false, failed, pending

--rollback

Si el reinicio de una unidad systemd después de actualizar la imagen ha fallado, revierte al uso de la imagen anterior y reinicia la unidad en otro momento. El valor predeterminado es true.

Tenga en cuenta que la detección de si una unidad systemd ha fallado se realiza mejor mediante el contenedor que envía el mensaje READY a través de SDNOTIFY. De esta manera, el reinicio de la unidad espera hasta haber recibido el mensaje o hasta que se haya agotado un tiempo de espera. Sin eso, reiniciar la unidad systemd puede tener éxito incluso si el contenedor ha fallado poco después.

Para que un contenedor envíe el mensaje READY a través de SDNOTIFY, debe crearse con la opción --sdnotify=container (ver podman-run(1)). La aplicación que se ejecuta dentro del contenedor puede entonces ejecutar systemd-notify --ready cuando esté lista o utilizar las enlaces de sdnotify del lenguaje de programación específico (por ejemplo, sdnotify(3)).

--tls-verify

Requiere HTTPS y verifica certificados al contactar con registros (predeterminado: true). Si se establece explícitamente en true, se utiliza la verificación TLS. Si se establece en false, no se utiliza la verificación TLS. Si no se especifica, se utiliza la verificación TLS a menos que el registro de destino esté listado como un registro inseguro en containers-registries.conf(5)

EJEMPLOS

Crea un archivo Quadlet configurado para actualizaciones automáticas:

$ cat ~/.config/containers/systemd/sleep.container
[Container]
Image=registry.fedoraproject.org/fedora:latest
Exec=sleep infinity
AutoUpdate=registry

Genera un servicio systemd a partir del archivo Quadlet recargando el demonio de usuario de systemd:

$ systemctl --user daemon-reload

Inicia el servicio systemd y asegúrate de que el contenedor se esté ejecutando

$ systemctl --user start sleep.service
$ podman ps
CONTAINER ID  IMAGE                                     COMMAND         CREATED        STATUS        PORTS       NAMES
f8e4759798d4  registry.fedoraproject.org/fedora:latest  sleep infinity  2 seconds ago  Up 2 seconds              systemd-sleep

Verifica si hay una nueva imagen disponible usando --dry-run:

$ podman auto-update --dry-run --format "{{.Image}} {{.Updated}}"
registry.fedoraproject.org/fedora:latest   pending

Actualiza el servicio:

$ podman auto-update
UNIT           CONTAINER                     IMAGE                                     POLICY      UPDATED
sleep.service  f8e4759798d4 (systemd-sleep)  registry.fedoraproject.org/fedora:latest  registry    true
