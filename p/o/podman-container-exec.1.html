podman-exec(1) Manual general de comandos podman-exec(1)

NOMBRE

podman-exec - Ejecutar un comando en un contenedor en ejecución

SINOPSIS

podman exec [opciones] contenedor comando [arg ...]

podman container exec [opciones] contenedor comando [arg ...]

DESCRIPCIÓN

podman exec ejecuta un comando en un contenedor en ejecución.

OPCIONES

--cidfile=archivo

Lee el ID del contenedor de destino desde el archivo especificado.

--detach, -d

Inicia la sesión de ejecución, pero no se adjunta a ella. El comando se ejecuta en segundo plano y la sesión de ejecución se elimina automáticamente cuando finaliza. El comando podman exec imprime el ID de la sesión de ejecución y sale inmediatamente después de que se inicia.

--detach-keys=secuencia

Especifica la secuencia de teclas para desconectar un contenedor. El formato es un solo carácter [a-Z] o uno o más caracteres ctrl-<valor> donde <valor> es uno de: a-z, @, ^, [, , o _. Especificar "" deshabilita esta característica. El valor predeterminado es ctrl-p,ctrl-q.

Esta opción también se puede configurar en el archivo containers.conf(5).

--env, -e=entorno

Establece variables de entorno.

Esta opción permite variables de entorno arbitrarias que están disponibles para el proceso que se lanzará dentro del contenedor. Si se especifica una variable de entorno sin un valor, Podman busca en el entorno del host un valor y establece la variable solo si está configurada en el host. Como caso especial, si se especifica una variable de entorno que termina en * sin un valor, Podman busca en el entorno del host variables que comiencen con el prefijo y agrega esas variables al contenedor.

--env-file=archivo

Lee variables de entorno desde un archivo delimitado por líneas.

--interactive, -i

Cuando se establece en true, hace que stdin esté disponible para el proceso contenido. Si es false, el stdin del proceso contenido está vacío y se cierra inmediatamente.

Si está adjunto, stdin se canaliza al proceso contenido. Si está desconectado, la lectura de stdin se bloqueará hasta que se adjunte más tarde.

Advertencia: Podman consumirá la entrada desde stdin tan pronto como esté disponible, incluso si el proceso contenido no la solicita.

--latest, -l

En lugar de proporcionar el nombre o ID del contenedor, utiliza el último contenedor creado. Nota: el último contenedor iniciado puede ser de otros usuarios de Podman en la máquina host. (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--preserve-fd=FD1[,FD2,...]

Pasa a los descriptores de archivo adicionales especificados en la lista separada por comas al proceso. Se puede especificar varias veces. Esta opción solo se admite con el tiempo de ejecución OCI crun. Usar esta opción con otros tiempos de ejecución OCI puede ser un riesgo de seguridad.

(Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--preserve-fds=N

Pasa N descriptores de archivo adicionales al proceso (además de 0, 1, 2). Los FD totales son 3+N. (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--privileged

Otorga privilegios extendidos a este contenedor. El valor predeterminado es false.

Por defecto, los contenedores de Podman no tienen privilegios (=false) y no pueden, por ejemplo, modificar partes del sistema operativo. Esto se debe a que, por defecto, un contenedor solo tiene permitido un acceso limitado a los dispositivos. A un contenedor "privilegiado" se le otorga el mismo acceso a los dispositivos que al usuario que inicia el contenedor, con la excepción de las consolas virtuales (/dev/tty\d+) cuando se ejecuta en modo systemd (--systemd=always).

Un contenedor privilegiado deshabilita las características de seguridad que aíslan el contenedor del host. Las capacidades descartadas, los dispositivos limitados, los puntos de montaje de solo lectura, la separación de Apparmor/SELinux y los filtros Seccomp se desactivan. Debido a las características de seguridad deshabilitadas, el campo privilegiado casi nunca debe establecerse, ya que los contenedores pueden escapar fácilmente del confinamiento.

Los contenedores que se ejecutan en un espacio de nombres de usuario (por ejemplo, contenedores sin root) no pueden tener más privilegios que el usuario que los inició.

--tty, -t

Asigna un pseudo-TTY. El valor predeterminado es false.

Cuando se establece en true, Podman asigna un pseudo-TTY y se adjunta a la entrada estándar del contenedor. Esto se puede utilizar, por ejemplo, para ejecutar un shell interactivo desechable.

NOTA: El indicador --tty evita la redirección de la salida estándar. Combina STDOUT y STDERR, puede insertar caracteres de control y puede colgar tuberías. Esta opción solo se utiliza cuando se ejecuta interactivamente en una terminal. Al alimentar entrada a Podman, usa solo -i, no -it.

--user, -u=usuario[:grupo]

Establece el nombre de usuario o UID utilizado y, opcionalmente, el nombre de grupo o GID para el comando especificado. Tanto usuario como grupo pueden ser simbólicos o numéricos.

Sin este argumento, el comando se ejecuta como el usuario especificado en la imagen del contenedor. A menos que se anule con un comando USER en el Containerfile o con un valor pasado a esta opción, este usuario generalmente se establece en root por defecto.

Cuando no se utiliza un espacio de nombres de usuario, el UID y el GID utilizados dentro del contenedor y en el host coinciden. Sin embargo, cuando se utilizan espacios de nombres de usuario, el UID y el GID en el contenedor pueden corresponder a otro UID y GID en el host. En los contenedores sin root, por ejemplo, siempre se utiliza un espacio de nombres de usuario, y root en el contenedor corresponde por defecto al UID y GID del usuario que invoca Podman.

--workdir, -w=dir

Directorio de trabajo dentro del contenedor.

El directorio de trabajo predeterminado para ejecutar binarios dentro de un contenedor es el directorio raíz (/). El desarrollador de la imagen puede establecer un valor predeterminado diferente con la instrucción WORKDIR. El operador puede anular el directorio de trabajo utilizando la opción -w.

Estado de salida

El código de salida de podman exec proporciona información sobre por qué el comando dentro del contenedor no se pudo ejecutar o por qué salió. Cuando podman exec sale con un código distinto de cero, los códigos de salida siguen el estándar chroot, ver a continuación:

125 El error es con el propio Podman

$ podman exec --foo ctrID /bin/sh; echo $?
Error: unknown flag: --foo
125

126 El comando contenido no se puede invocar

$ podman exec ctrID /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

127 El comando contenido no se puede encontrar

$ podman exec ctrID foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

Código de salida El código de salida del comando contenido

$ podman exec ctrID /bin/sh -c 'exit 3'; echo $?
3

EJEMPLOS

Ejecutar un comando en el contenedor seleccionado con una entrada estándar y un tty asignado:

$ podman exec -it ctrID ls

Ejecutar un comando con el directorio de trabajo anulado en el contenedor seleccionado con una entrada estándar y un tty asignado:

$ podman exec -it -w /tmp myCtr pwd

Ejecutar un comando como el usuario especificado en el contenedor seleccionado:

$ podman exec --user root ctrID ls

Ejecutar un comando pero no adjuntarse a la sesión de ejecución, dejando el comando ejecutándose en segundo plano:

$ podman exec -d ctrID find /path/to/search -name yourfile
