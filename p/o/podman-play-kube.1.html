podman-kube-play(1) Manual de Comandos Generales podman-kube-play(1)

NOMBRE

podman kube play - Crea contenedores, pods y volúmenes basados en YAML de Kubernetes

SINOPSIS

podman kube play [opciones] archivo.yml|-|https://website.io/archivo.yml

DESCRIPCIÓN

podman kube play lee un archivo estructurado de YAML de Kubernetes. Recrea los contenedores, pods o volúmenes descritos en el YAML. Los contenedores dentro de un pod se inician y se muestra el ID del nuevo Pod o el nombre del nuevo Volumen. Si el archivo YAML se especifica como "-", entonces podman kube play lee el archivo YAML desde la entrada estándar. La entrada también puede ser una URL que apunte a un archivo YAML, como https://podman.io/demo.yml. podman kube play lee el YAML de la URL y crea pods y contenedores a partir de él.

Usando la opción de línea de comandos --down, también es capaz de desmantelar los pods creados por una ejecución previa de podman kube play.

Usando la opción de línea de comandos --replace, desmantela los pods (si los hay) creados por una ejecución previa de podman kube play y recrea los pods con el archivo YAML de Kubernetes.

Idealmente, el archivo de entrada es creado por el comando Podman (ver podman-kube-generate(1)). Esto garantiza una importación fluida y resultados esperados.

Actualmente, los tipos de Kubernetes soportados son:

  • Pod
  • Deployment
  • PersistentVolumeClaim
  • ConfigMap
  • Secret
  • DaemonSet
  • Job

Pods o Deployments de Kubernetes

Solo cinco tipos de volúmenes son soportados por kube play: los tipos de volúmenes hostPath, emptyDir, configMap, persistentVolumeClaim e image.

  • Al usar el tipo de volumen hostPath, solo se admiten los subtipos predeterminado (vacío), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice y BlockDevice. Podman interpreta el valor de la ruta de hostPath como una ruta de archivo si contiene al menos una barra inclinada (forward slash), de lo contrario, Podman trata el valor como el nombre de un volumen con nombre.
  • Al usar un persistentVolumeClaim, el valor de claimName es el nombre del volumen con nombre de Podman.
  • Al usar un volumen emptyDir, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que se elimina el pod.
  • Al usar un volumen configMap, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que se elimina el pod.
  • Al usar un volumen image, Podman crea un volumen de imagen de solo lectura con un subdirectorio vacío (la imagen completa se monta). La imagen ya debe existir localmente. Solo se admite en modo rootful.

Nota: La política de reinicio predeterminada para los contenedores es always. Puede cambiar el valor predeterminado configurando el campo restartPolicy en la especificación.

Nota: Al reproducir un YAML de kube con contenedores init, el contenedor init se crea con el valor de tipo init once. Para cambiar el tipo predeterminado, use la anotación io.podman.annotations.init.container.type para establecer el tipo en always.

Nota: Los tipos de volumen hostPath creados por kube play reciben una etiqueta compartida SELinux (z), los montajes bind no se vuelven a etiquetar (use chcon -t container_file_t -R <directorio>).

Nota: Para establecer los userns de un pod, use la anotación io.podman.annotations.userns en la definición del pod/deployment. Por ejemplo, la anotación io.podman.annotations.userns=keep-id indica a Podman que cree un espacio de nombres de usuario donde la UID:GID del usuario rootless actual se mapea a los mismos valores en el contenedor. Esto se puede anular con la bandera --userns.

Nota: Use la anotación io.podman.annotations.volumes-from para montar volúmenes de un contenedor en otro. Puede montar volúmenes de múltiples contenedores de origen a un contenedor de destino. Los contenedores de origen que pertenecen al mismo pod deben definirse antes que el contenedor de origen en el YAML de kube. El formato de la anotación es io.podman.annotations.volumes-from/contenedorDestino: "contenedorOrigen1:opcionesMontaje1;contenedorOrigen2:opcionesMontaje2".

Nota: Si se usa la etiqueta :latest, Podman intenta extraer la imagen de un registro. Si la imagen se compiló localmente con Podman o Buildah, tiene localhost como dominio, en ese caso, Podman usa la imagen del almacén local incluso si tiene la etiqueta :latest.

Nota: El comando podman play kube es un alias de podman kube play y realiza la misma función.

Nota: El comando podman kube down se puede usar para detener y eliminar pods o contenedores basados en el mismo YAML de Kubernetes usado por podman kube play para crearlos.

Nota: Para personalizar el nombre del contenedor infra creado durante podman kube play, use la anotación io.podman.annotations.infra.name en la definición del pod. Esta anotación se establece automáticamente al generar un YAML de kube a partir de un pod que fue creado con la bandera --infra-name establecida.

Nota: Use la anotación io.podman.annotations.pids-limit/$nombre_ctr para configurar el límite de pids del pod.

Nota: Use la anotación io.podman.annotations.cpuset/$nombre_ctr para restringir la ejecución de un contenedor a un conjunto específico de núcleos de CPU. Esto es equivalente a la opción --cpuset-cpus=número en podman-run(1).

Nota: Use la anotación io.podman.annotations.memory-nodes/$nombre_ctr para restringir las asignaciones de memoria de un contenedor a un conjunto específico de nodos de memoria en sistemas NUMA. Esto es equivalente a la opción --cpuset-mems=nodos en podman-run(1).

PersistentVolumeClaims de Kubernetes

Un PersistentVolumeClaim de Kubernetes representa un volumen con nombre de Podman. Podman solo requiere el nombre del PersistentVolumeClaim para crear un volumen. Las anotaciones de Kubernetes se pueden utilizar para aprovechar las opciones disponibles para los volúmenes de Podman.

  • volume.podman.io/driver
  • volume.podman.io/device
  • volume.podman.io/type
  • volume.podman.io/uid
  • volume.podman.io/gid
  • volume.podman.io/mount-options
  • volume.podman.io/import-source
  • volume.podman.io/image

Use volume.podman.io/import-source para importar el contenido del archivo tarball (.tar, .tar.gz, .tgz, .bzip, .tar.xz, .txz, .tar.zst) especificado en el valor de la anotación al volumen de Podman creado.

Kube play es capaz de construir imágenes sobre la marcha dado el diseño de directorio correcto y los Containerfiles. Esta opción aún no está disponible para clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2). Considere el siguiente extracto de un archivo YAML:

apiVersion: v1
kind: Pod
metadata:
...
spec:
  containers:
  - name: container
    image: foobar
...

Si hay un directorio llamado foobar en el directorio actual con un archivo llamado Containerfile o Dockerfile, Podman kube play compila esa imagen y la nombra foobar. Una estructura de directorio de ejemplo para este ejemplo se ve así:

|- misarchivoskube
    |- miojodejugar.yaml
    |- foobar
         |- Containerfile

La compilación considera foobar como el directorio de contexto para la compilación. Si hay una imagen en el almacenamiento local llamada foobar, la imagen no se compila a menos que se utilice la bandera --build. Use --build=false para deshabilitar completamente las compilaciones.

Kube play soporta selectores de dispositivos CDI (Container Device Interface) para compartir dispositivos del host (por ejemplo, GPUs) con los contenedores. El formato de configuración sigue la gestión de recursos extendidos de Kubernetes:

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: container
    resources:
      limits:
        nvidia.com/gpu=all: 1

Para habilitar el uso compartido de dispositivos del host, análogo al uso de la bandera --device, Podman kube soporta un selector CDI personalizado: podman.io/device=<ruta dispositivo host>.

ConfigMap de Kubernetes

Los ConfigMaps de Kubernetes se pueden referir como una fuente de variables de entorno o volúmenes en Pods o Deployments. Los ConfigMaps no son un objeto independiente en Podman; en su lugar, cuando un contenedor usa un ConfigMap, Podman crea variables de entorno o volúmenes según sea necesario.

Por ejemplo, el siguiente documento YAML define un ConfigMap y luego lo usa en un Pod:

apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: fooba

KUBERNETES OBJECTS

Kubernetes objects can be used to define how Podman will behave when running containers. This behavior is specified in the YAML document using Kubernetes API objects. This document focuses on Podman's support for Kubernetes YAML documents.

Kubernetes ConfigMap

Kubernetes ConfigMap represents a Podman named configuration. The Kubernetes ConfigMap is saved as a whole and may be referred to as a source of environment variables in Pods or Deployments.

For example, the following YAML document defines a ConfigMap and then uses it in a Pod:

kind: ConfigMap
apiVersion: v1
metadata:
  name: foo
data:
  FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    envFrom:
    - configMapRef:
        name: foo
        optional: false

and as a result environment variable FOO is set to bar for container container-1.

Kubernetes Secret

Kubernetes Secret represents a Podman named secret. The Kubernetes Secret is saved as a whole and may be referred to as a source of environment variables or volumes in Pods or Deployments.

For example, the following YAML document defines a Secret and then uses it in a Pod:

kind: Secret
apiVersion: v1
metadata:
  name: foo
data:
  foo: YmFy # base64 for bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    env:
    - name: FOO
      valueFrom:
        secretKeyRef:
          name: foo
          key: foo

and as a result environment variable FOO is set to bar for container container-1.

Automounting Volumes (deprecated)

Note: The automounting annotation is deprecated. Kubernetes has native support for image volumes and that should be used rather than this podman-specific annotation.

An image can be automatically mounted into a container if the annotation io.podman.annotations.kube.image.automount/$ctrname is given. The following rules apply:

  • The image must already exist locally.
  • The image must have at least 1 volume directive.
  • The path given by the volume directive will be mounted from the image into the container. For example, an image with a volume at /test/test_dir will have /test/test_dir in the image mounted to /test/test_dir in the container.
  • Multiple images can be specified. If multiple images have a volume at a specific path, the last image specified trumps.
  • The images are always mounted read-only.
  • Images to mount are defined in the annotation "io.podman.annotations.kube.image.automount/$ctrname" as a semicolon-separated list. They are mounted into a single container in the pod, not the whole pod. The annotation can be specified for additional containers if additional mounts are required.

OPTIONS

--annotation=key=value

Add an annotation to the container or pod. This option can be set multiple times.

Note: For podman kube play, the --annotation flag adds Podman-specific annotations to the containers and pods created by Podman, not to the Kubernetes YAML itself. These annotations can be used to configure Podman-specific features like user namespaces (io.podman.annotations.userns), volumes-from (io.podman.annotations.volumes-from), and other container behaviors.

--authfile=path

Path of the authentication file. Default is ${XDG_RUNTIME_DIR}/containers/auth.json on Linux, and $HOME/.config/containers/auth.json on Windows/macOS. The file is created by podman login. If the authorization state is not found there, $HOME/.docker/config.json is checked, which is set using docker login.

Note: There is also the option to override the default path of the authentication file by setting the REGISTRY_AUTH_FILE environment variable. This can be done with export REGISTRY_AUTH_FILE=path.

--build

Build images even if they are found in the local storage. Use --build=false to completely disable builds. (This option is not available with the remote Podman client)

Note: You can also override the default isolation type by setting the BUILDAH_ISOLATION environment variable. export BUILDAH_ISOLATION=oci. See podman-build.1.md for more information.

--cert-dir=path

Use certificates at path (*.crt, *.cert, *.key) to connect to the registry. (Default: /etc/containers/certs.d) For details, see containers-certs.d(5). (This option is not available with the remote Podman client, including Mac and Windows (excluding WSL2) machines)

--configmap=path

Use Kubernetes configmap YAML at path to provide a source for environment variable values within the containers of the pod. (This option is not available with the remote Podman client)

Note: The --configmap option can be used multiple times or a comma-separated list of paths can be used to pass multiple Kubernetes configmap YAMLs. The YAML file may be in a multi-doc YAML format. But, it must container only configmaps

--context-dir=path

Use path as the build context directory for each image. Requires --build option be true. (This option is not available with the remote Podman client)

--creds=[username[:password]]

The [username[:password]] to use to authenticate with the registry, if required. If one or both values are not supplied, a command line prompt appears and the value can be entered. The password is entered without echo.

Note that the specified credentials are only used to authenticate against target registries. They are not used for mirrors or when the registry gets rewritten (see containers-registries.conf(5)); to authenticate against those consider using a containers-auth.json(5) file.

--force

Tear down the volumes linked to the PersistentVolumeClaims as part of --down

--help, -h

Print usage statement

--ip=IP address

Assign a static ip address to the pod. This option can be specified several times when kube play creates more than one pod. Note: When joining multiple networks use the --network name:ip=<ip> syntax.

--log-driver=driver

Set logging driver for all created containers.

--log-opt=name=value

Logging driver specific options.

Set custom logging configuration. The following *name*s are supported:

path: specify a path to the log file
(e.g. --log-opt path=/var/log/container/mycontainer.json);

max-size: specify a max size of the log file
(e.g. --log-opt max-size=10mb);

tag: specify a custom log tag for the container
(e.g. --log-opt tag="{{.ImageName}}". It supports the same keys as podman inspect --format. This option is currently supported only by the journald log driver.

--mac-address=MAC address

Assign a static mac address to the pod. This option can be specified several times when kube play creates more than one pod. Note: When joining multiple networks use the --network name:mac=<mac> syntax.

--network=mode, --net

Set the network mode for the pod.

Valid mode values are:

•
bridge[:OPTIONS,...]: Create a network stack on the default bridge. This is the default for rootful containers. It is possible to specify these additional options:
  • alias=name: Add network-scoped alias for the container.
  • ip=IPv4: Specify a static IPv4 address for this container.
  • ip6=IPv6: Specify a static IPv6 address for this container.
  • mac=MAC: Specify a static MAC address for this container.
  • interface_name=name: Specify a name for the created network interface inside the container.
  • host_interface_name=name: Specify a name for the created network interface outside the container.
Any other options will be passed through to netavark without validation. This can be useful to pass arguments to netavark plugins.

For example, to set a static ipv4 address and a static mac address, use --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <network name or ID>[:OPTIONS,...]: Connect to a user-defined network; this is the network name or ID from a network created by podman network create. It is possible to specify the same options described under the bridge mode above. Use the --network option multiple times to specify additional networks.
    For backwards compatibility it is also possible to specify comma-separated networks on the first --network argument, however this prevents you from using the options described under the bridge section above.
  • none: Create a network namespace for the container but do not configure network interfaces for it, thus the container has no network connectivity.
  • container:id: Reuse another container's network stack.
  • host: Use the host's network namespace for the container instead of creating an isolated namespace. Warning: This gives the container full access to abstract Unix domain sockets and to TCP/UDP sockets bound to localhost. Since these mechanisms are often used to prevent access to sensitive system services, isolating them from access by external entities, use of this option may be considered a security vulnerability.
  • ns:path: Path to a network namespace to join.
  • private: Create a new namespace for the container. This uses the bridge mode for rootful containers and slirp4netns for rootless ones.
  • slirp4netns[:OPTIONS,...]: use slirp4netns(1) to create a user network stack. It is possible to specify these additional options, they can also be set with network_cmd_options in containers.conf:
  • allow_host_loopback=true|false: Allow slirp4netns to reach the host loopback IP (default is 10.0.2.2 or the second IP from slirp4netns cidr subnet when changed, see the cidr option below). The default is false.
  • mtu=MTU: Specify the MTU to use for this network. (Default is 65520).
  • cidr=CIDR: Specify ip range to use for t
su red. (Predeterminado es 10.0.2.0/24).
  • enable_ipv6=true|false: Habilitar IPv6. El valor predeterminado es true. (Requerido para outbound_addr6).
  • outbound_addr=INTERFACE: Especificar la interfaz de salida a la que se enlaza slirp (solo tráfico ipv4).
  • outbound_addr=IPv4: Especificar la dirección ipv4 de salida a la que se enlaza slirp.
  • outbound_addr6=INTERFACE: Especificar la interfaz de salida a la que se enlaza slirp (solo tráfico ipv6).
  • outbound_addr6=IPv6: Especificar la dirección ipv6 de salida a la que se enlaza slirp.
  • port_handler=rootlesskit: Usar rootlesskit para el reenvío de puertos. Predeterminado.
    Nota: Rootlesskit cambia la dirección IP de origen de los paquetes entrantes a una dirección IP en el espacio de nombres de red del contenedor, generalmente 10.0.2.100. Si la aplicación requiere la dirección IP de origen real, por ejemplo, registros del servidor web, use el manejador de puertos slirp4netns. El manejador de puertos rootlesskit también se utiliza para contenedores sin privilegios cuando se conectan a redes definidas por el usuario.
  • port_handler=slirp4netns: Usar el reenvío de puertos slirp4netns, es más lento que rootlesskit pero conserva la dirección IP de origen correcta. Este manejador de puertos no se puede utilizar para redes definidas por el usuario.
    • •
    pasta[:OPTIONS,...]: usar pasta(1) para crear una pila de red en modo de usuario.
    Este es el valor predeterminado para contenedores sin privilegios y solo es compatible en modo sin privilegios.
    Por defecto, las direcciones y rutas IPv4 e IPv6, así como el nombre de la interfaz del pod, se copian del host. El reenvío de puertos conserva la dirección IP de origen original. Las opciones descritas en pasta(1) se pueden especificar como argumentos separados por comas.
    En términos de opciones de pasta(1), se proporciona --config-net de forma predeterminada, para configurar la red cuando se inicia el contenedor, y también se asume --no-map-gw de forma predeterminada, para evitar el acceso directo desde el contenedor al host utilizando la dirección de puerta de enlace. Este último puede ser anulado pasando --map-gw en las opciones específicas de pasta (a pesar de no ser una opción real de pasta(1)).
    Para una mejor integración con el manejo de DNS, se pasa --dns-forward 169.254.1.1, y esta dirección se agrega a resolv.conf(5) como el primer resolvedor. Es posible pasar --dns-forward explícitamente en caso de que se deba usar una dirección IP diferente. Para que la entrada de hosts host.containers.internal /etc/hosts funcione y permita conexiones al host, se pasa --map-guest-addr 169.254.1.2. Nuevamente, se puede configurar explícitamente para elegir una dirección IP diferente.
    Además, se pasan -t none y -u none si, respectivamente, no se configura ningún reenvío de puertos TCP o UDP del host al contenedor (a través de las opciones --publish de Podman o pasando las opciones -t/-u de pasta directamente), para deshabilitar el reenvío automático de puertos basado en puertos enlazados. De manera similar, se proporcionan -T none y -U none para deshabilitar la misma funcionalidad de contenedor a host.
    Todas las opciones también se pueden configurar en containers.conf(5); consulte la clave pasta_options en la sección de red de ese archivo.
    Algunos ejemplos:
    • pasta:--map-gw: Permite que el contenedor acceda directamente al host utilizando la dirección de la puerta de enlace.
    • pasta:--mtu,1500: Especificar una MTU de 1500 bytes para la interfaz tap en el contenedor.
    • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con puerta de enlace 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece la MTU a 1500 bytes, deshabilita NDP, DHCPv6 y DHCP soporte.
    • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: lo mismo que lo anterior, pero deja la MTU en 65520 bytes.
    • pasta:-t,auto,-u,auto,-T,auto,-U,auto: habilita el reenvío automático de puertos basado en puertos enlazados observados desde ambos lados, host y contenedor
    • pasta:-T,5201: habilita el reenvío del puerto TCP 5201 del contenedor al host, utilizando la interfaz de loopback en lugar de la interfaz tap para mejorar el rendimiento

    Cuando no se especifica ninguna opción de red y el modo de red host no está configurado en el archivo YAML, se crea una nueva pila de red y los pods se adjuntan a ella, lo que permite la comunicación pod a pod.

    --no-hostname

    No crear el archivo /etc/hostname en los contenedores.

    Por defecto, Podman gestiona el archivo /etc/hostname, añadiendo el propio nombre de host del contenedor. Cuando se establece la opción --no-hostname, el archivo /etc/hostname de la imagen se conservará sin modificaciones si existe.

    --no-hosts

    No modificar el archivo /etc/hosts en el pod.

    Podman asume el control del archivo /etc/hosts del pod por defecto y agrega entradas para el nombre del contenedor (ver la opción --name) y el nombre de host (ver la opción --hostname), los hosts internos host.containers.internal y host.docker.internal, así como cualquier nombre de host agregado usando la opción --add-host. Consulte la opción --add-host para obtener más detalles. Al pasar --no-hosts se deshabilita esto, de modo que el archivo /etc/hosts de la imagen se mantiene sin modificar. Lo mismo se puede lograr globalmente estableciendo no_hosts=true en containers.conf.

    Esta opción entra en conflicto con los hosts agregados en el YAML de Kubernetes.

    --no-pod-prefix

    No prefijar el nombre del contenedor con el nombre del pod.

    --publish=[[ip:][hostPort]:]containerPort[/protocol]

    Definir o anular una definición de puerto en el archivo YAML.

    Las listas de puertos en el archivo YAML y la línea de comandos se fusionan. La coincidencia se realiza utilizando el campo containerPort. Si containerPort existe tanto en el archivo YAML como en la opción, esta última tiene prioridad.

    --publish-all

    Establecer esta opción en true expondrá todos los puertos al host, incluso si solo se especifican a través de containerPort en el YAML de K8. En cuanto a qué puerto se expondrá, --publish tiene mayor prioridad que hostPort, que tiene mayor prioridad que containerPort.

    Si se establece en false (que es el valor predeterminado), solo los puertos definidos a través de hostPort o --publish se publicarán en el host.

    --quiet, -q

    Suprimir la información de salida al descargar imágenes.

    --replace

    Detiene los pods creados por una ejecución anterior de kube play y recrea los pods. Esta opción se utiliza para mantener los pods existentes actualizados basándose en el YAML de Kubernetes.

    --seccomp-profile-root=path

    Ruta del directorio para los perfiles seccomp (predeterminado: "/var/lib/kubelet/seccomp"). (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

    --start

    Iniciar el pod después de crearlo, establecido en false para solo crearlo.

    --tls-verify

    Requerir HTTPS y verificar certificados al contactar con los registros (predeterminado: true). Si se establece explícitamente en true, se utiliza la verificación TLS. Si se establece en false, no se utiliza la verificación TLS. Si no se especifica, se utiliza la verificación TLS a menos que el registro de destino esté listado como un registro inseguro en containers-registries.conf(5).

    --userns=mode

    Establecer el modo del espacio de nombres de usuario para el contenedor.

    Si no se establece --userns, el valor predeterminado se determina de la siguiente manera: - Si se establece --pod, se ignora --userns y se utiliza el espacio de nombres de usuario del pod. - Si la variable de entorno PODMAN_USERNS está establecida, se utiliza su valor. - Si se especifica userns en containers.conf, se utiliza este valor. - De lo contrario, se asume --userns=host.

    --userns="" (es decir, una cadena vacía) es un alias para --userns=host.

    Esta opción es incompatible con --gidmap, --uidmap, --subuidname y --subgidname.

    Mapeos de claves de usuario sin privilegios --userns:

    Clave Usuario del Host Usuario del Contenedor
    auto $UID nil (La UID del Usuario del Host no se mapea al contenedor).
    host $UID 0 (Cuenta de Usuario Predeterminada mapeada al usuario root en el contenedor).
    keep-id $UID $UID (Mapear la cuenta de usuario a la misma UID dentro del contenedor).
    keep-id:uid=200,gid=210 $UID 200:210 (Mapear la cuenta de usuario a la UID, valor GID especificado dentro del contenedor).
    nomap $UID nil (La UID del Usuario del Host no se mapea al contenedor).

    Los valores válidos de mode son:

    auto[:OPTIONS,...]: crear automáticamente un espacio de nombres de usuario único.

    • modo con privilegios: El flag --userns=auto requiere que el nombre de usuario containers se especifique en los archivos /etc/subuid y /etc/subgid, con un rango no utilizado de IDs de usuario subordinados que Podman puede asignar. Ejemplo: containers:2147483647:2147483648.
    • modo sin privilegios: Se utilizará el rango de usuarios de los archivos /etc/subuid y /etc/subgid. Tenga en cuenta que ejecutar un solo contenedor sin usar --userns=auto utilizará todo el rango de UIDs y no permitirá una subdivisión adicional. Ver subuid(5).

    Podman asigna rangos únicos de UIDs y GIDs de los IDs de usuario subordinados containers. El tamaño de los rangos se basa en el número de UIDs requeridas en la imagen. El número de UIDs y GIDs se puede anular con la opción size.

    La opción --userns=keep-id utiliza todas las subuids y subgids del usuario. La opción --userns=nomap utiliza todas las subuids y subgids del usuario excepto el ID propio del usuario. Usar --userns=auto al iniciar nuevos contenedores no funciona mientras existan contenedores que se iniciaron con --userns=nomap o --userns=keep-id sin limitar el tamaño del espacio de nombres de usuario.

    auto válido op

    tions:

    • gidmapping=CONTAINER_GID:HOST_GID:SIZE: para forzar un mapeo de GID a estar presente en el espacio de nombres de usuario.
    • size=SIZE: para especificar un tamaño explícito para el espacio de nombres de usuario automático. Por ejemplo, --userns=auto:size=8192. Si no se especifica size, auto estima un tamaño para el espacio de nombres de usuario.
    • uidmapping=CONTAINER_UID:HOST_UID:SIZE: para forzar un mapeo de UID a estar presente en el espacio de nombres de usuario.

    El UID y GID del host en gidmapping y uidmapping pueden ir precedidos opcionalmente por el símbolo @. En ese caso, podman buscará el ID intermedio correspondiente al ID del host y mapeará el ID intermedio encontrado al ID del contenedor. Para más detalles, consulte --uidmap.

    container:id: únete al espacio de nombres de usuario del contenedor especificado.

    host o "" (cadena vacía): ejecuta en el espacio de nombres de usuario del llamante. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el host que cualquier otro proceso iniciado por el usuario llamante.

    keep-id: crea un espacio de nombres de usuario donde el UID:GID del usuario actual se mapea a los mismos valores en el contenedor. Para contenedores creados por root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

    Además, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen, a menos que establezca explícitamente --user.

    Opciones válidas de keep-id:

    • uid=UID: anula el UID dentro del contenedor que se utiliza para mapear al usuario actual.
    • gid=GID: anula el GID dentro del contenedor que se utiliza para mapear al usuario actual.
    • size=SIZE: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No soportado cuando se ejecuta como root.

    nomap: crea un espacio de nombres de usuario donde el UID:GID del usuario rootless actual no se mapea dentro del contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

    ns:namespace: ejecuta el pod en el espacio de nombres de usuario existente dado.

    --wait, -w

    Ejecuta pods y contenedores en primer plano. El valor predeterminado es false.

    En cualquier momento, puede ejecutar podman pod ps en otra terminal para ver una lista de los pods y contenedores en ejecución.

    Cuando se adjunta en modo tty, puede matar los pods y contenedores presionando Ctrl-C o recibiendo cualquier otra señal de interrupción.

    Todos los pods, contenedores y volúmenes creados con podman kube play se eliminan al salir.

    podman-play-kube(1)

    NAME

    podman-play-kube - Play Kubernetes YAML files.

    SYNOPSIS

    podman play kube [options] [kube.yaml ...]

    DESCRIPTION

    The podman play kube command takes Kubernetes YAML files and creates pods, containers, services, and deployments based on the definitions in the files. It is the inverse of the podman generate kube command.

    This command is used to run containerized applications defined in Kubernetes YAML format. It allows users to leverage Kubernetes-style definitions to manage containers without needing a full Kubernetes cluster.

    OPTIONS

    The options available for podman play kube are extensive and allow for fine-grained control over how the Kubernetes YAML is interpreted and applied.

    --cancel
    Cancel a previously started podman play kube command. This option requires the original YAML file used to start the play command.
    --creator-id string
    An optional identifier for the creator of the pod. This can be used for grouping or identifying related resources.
    --dry-run
    Instead of creating containers, print the Kubernetes YAML that would be generated.
    --network string
    Specify the network to attach the containers to. If not specified, a default network will be created.
    --platform string
    Specify the platform for the containers. Supported values are "kubernetes" and "podman". Default is "kubernetes".
    --service-ports
    Expose service ports to the host. By default, ports defined in Kubernetes Services are not exposed.
    -v, --volume string
    Bind mount a volume. The format is <source>:<destination>[:options]. This option can be used multiple times.

    EXAMPLES

    Start containers defined in my-app.yaml:

    - podman play kube my-app.yaml

    Start containers and expose service ports:

    - podman play kube --service-ports my-app.yaml

    Start containers using a specific network:

    - podman play kube --network podman-net my-app.yaml

    Generate Kubernetes YAML from containers defined in my-app.yaml without actually creating containers:

    - podman play kube --dry-run my-app.yaml

    Cancel a previously started play command:

    - podman play kube --cancel my-app.yaml
