NOMBRE

podman-kube-generate - Genera YAML de Kubernetes basado en contenedores, pods o volúmenes

SINOPSIS

podman kube generate [opciones] contenedor... | pod... | volumen...

DESCRIPCIÓN

podman kube generate genera YAML de Kubernetes (especificación v1) a partir de contenedores, pods o volúmenes de Podman. Independientemente de si la entrada es para contenedores o pods, Podman genera la especificación como un Pod por defecto. La entrada puede ser en forma de uno o más nombres o IDs de contenedores, pods o volúmenes.

Contenedores o Pods de Podman

Los volúmenes aparecen en el YAML generado según dos tipos de volúmenes diferentes. Los volúmenes montados en enlace (bind-mounted) se convierten en tipos de volumen hostPath y los volúmenes con nombre se convierten en tipos de volumen persistentVolumeClaim. Los tipos de volumen hostPath generados son de uno de tres subtipos dependiendo del estado de la ruta del host: DirectoryOrCreate cuando no existe ningún archivo o directorio en el host, Directory cuando la ruta del host es un directorio, o File cuando la ruta del host es un archivo. El valor para claimName para un persistentVolumeClaim es el nombre del volumen con nombre registrado en Podman.

Los posibles conflictos de nombres entre volúmenes se evitan utilizando un esquema de nombres estándar para cada tipo de volumen. Los tipos de volumen hostPath se nombran según la ruta en la máquina host, reemplazando las barras inclinadas (`/`) por guiones, excepto las barras inclinadas iniciales y finales. El caso especial de la raíz del sistema de archivos, /, se traduce al nombre root. Además, se añade el sufijo -host al nombre para evitar conflictos de nombres con volúmenes persistentVolumeClaim. Cada tipo de volumen persistentVolumeClaim utiliza el nombre de su volumen con nombre asociado, con el sufijo -pvc.

Tenga en cuenta que si un contenedor init se crea con el tipo once y el pod ha sido iniciado, no aparece en el YAML de kube generado, ya que los contenedores init de tipo once se eliminan después de ejecutarse. Si el pod solo ha sido creado y no iniciado, está en el YAML de kube generado. Los contenedores init creados con el tipo always siempre se generan en el YAML de kube ya que nunca se eliminan, incluso después de completarse.

Nota: Al usar volúmenes y generar un YAML de Kubernetes para un contenedor de podman no privilegiado y sin root en un **sistema con SELinux habilitado**, se debe completar una de las siguientes opciones:
* Añadir la opción "privileged: true" a la especificación del pod
* Añadir type: spc_t bajo securityContext seLinuxOptions en la especificación del pod
* Re-etiquetar el volumen a través del comando de la CLI chcon -t container_file_t -R <directorio>

Una vez completado, los permisos correctos estarán en su lugar para acceder al volumen cuando el pod/contenedor se cree en un clúster de Kubernetes.

Tenga en cuenta que el archivo YAML de Kubernetes generado se puede utilizar para volver a ejecutar el despliegue a través de podman-play-kube(1).

Tenga en cuenta que si el pod que se genera se creó con el indicador --infra-name establecido, entonces el YAML de kube generado tendrá io.podman.annotations.infra.name establecido, donde el valor es el nombre del contenedor infra establecido por el usuario.

Tenga en cuenta que tanto Deployment como DaemonSet solo pueden tener restartPolicy establecido en Always.

Tenga en cuenta que Job solo puede tener restartPolicy establecido en OnFailure o Never. Por defecto, podman lo establece en Never al generar un YAML de kube usando kube generate.

OPCIONES

--filename, -f=nombre_archivo

Salida al archivo especificado en lugar de a STDOUT. Si el archivo ya existe, kube generate se niega a reemplazarlo y devuelve un error.

--podman-only

Añade anotaciones reservadas solo para Podman en el archivo YAML generado (No puede ser utilizado por Kubernetes)

--replicas, -r=contador_de_réplicas

El valor que se establecerá para replicas al generar un tipo Deployment. Nota: esto solo se puede establecer con la opción --type=deployment.

--service, -s

Genera un objeto de servicio de Kubernetes además de los Pods. Se utiliza para generar una especificación de servicio para la salida de Pod correspondiente. En particular, si el objeto tiene enlaces de mapeo de puertos, la especificación del servicio incluye una declaración NodePort para exponer el servicio. Podman asigna un puerto aleatorio en la especificación.

--type, -t=pod | deployment | daemonset | job

El tipo de Kubernetes que se generará en el archivo YAML. Actualmente, las únicas especificaciones de Kubernetes compatibles son Pod, Deployment, Job y DaemonSet. Por defecto, se genera la especificación Pod.

EJEMPLOS

Crear YAML de Pod de Kubernetes para el contenedor especificado.

$ podman kube generate some-mariadb
# Guarda la salida de este archivo y usa kubectl create -f para importar
# en Kubernetes.
#
# Creado con podman-4.8.2
# NOTA: Si generaste este yaml desde un contenedor podman no privilegiado y sin root en un sistema con SELinux
# habilitado, consulta la página del manual de podman generate kube para ver los pasos a seguir para asegurar que tu pod/contenedor
# tenga los permisos correctos para acceder a los volúmenes añadidos.
---
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: "2024-01-09T02:24:55Z"
  labels:
    app: some-mariadb-pod
  name: some-mariadb-pod
spec:
  containers:
  - args:
    - mariadbd
    env:
    - name: MARIADB_ROOT_PASSWORD
      value: x
    image: docker.io/library/mariadb:10.11
    name: some-mariadb
    ports:
    - containerPort: 3306
      hostPort: 34891
    volumeMounts:
    - mountPath: /var/lib/mysql
      name: mariadb_data-pvc
  volumes:
  - name: mariadb_data-pvc
    persistentVolumeClaim:
      claimName: mariadb_data

Crear YAML de Deployment de Kubernetes con 3 réplicas para el contenedor especificado.

$ podman kube generate --type deployment --replicas 3 dep-ct
r
# Guarda la salida de este archivo y usa kubectl create -f para importar
# en Kubernetes.
#
# Creado con podman-4.5.0-dev
apiVersion: apps/v1
kind: Deployment
metadata:
  creationTimestamp: "2023-03-27T20:45:08Z"
  labels:
    app: dep-ctr-pod
  name: dep-ctr-pod-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: dep-ctr-pod
  template:
    metadata:
      annotations:
        io.podman.annotations.ulimit: nofile=524288:524288,nproc=127332:127332
      creationTimestamp: "2023-03-27T20:45:08Z"
      labels:
        app: dep-ctr-pod
      name: dep-ctr-pod
    spec:
      containers:
      - command:
        - top
        image: docker.io/library/alpine:latest
        name: dep-ctr

Crear YAML de Pod de Kubernetes para el contenedor especificado con el directorio del host /home/user/my-data montado en el directorio del contenedor /volume.

$ podman kube generate my-container-with-bind-mounted-data
# Guarda la salida de este archivo y usa kubectl create -f para importar
# en Kubernetes.
#
# Creado con podman-3.1.0-dev
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: "2021-03-18T16:26:08Z"
  labels:
    app: my-container-with-bind-mounted-data
  name: my-container-with-bind-mounted-data
spec:
  containers:
  - command:
    - /bin/sh
    image: docker.io/library/alpine:latest
    name: test-bind-mount
    volumeMounts:
    - mountPath: /volume
      name: home-user-my-data-host
  restartPolicy: Never
  volumes:
  - hostPath:
      path: /home/user/my-data
      type: Directory
    name: home-user-my-data-host

Crear YAML de Pod de Kubernetes para el contenedor especificado con el volumen con nombre priceless-data montado en el directorio del contenedor /volume.

$ podman kube generate my-container-using-priceless-data
