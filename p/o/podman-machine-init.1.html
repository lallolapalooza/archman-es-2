NOMBRE

podman-machine-init - Inicializa una nueva máquina virtual

SINOPSIS

podman machine init [opciones] [nombre]

DESCRIPCIÓN

Inicializa una nueva máquina virtual para Podman.

El nombre de máquina por defecto es podman-machine-default. Si no se especifica un nombre de máquina como argumento, la nueva máquina se llamará podman-machine-default.

Solo sin root.

Podman en MacOS y Windows requiere una máquina virtual. Esto se debe a que los contenedores son Linux: los contenedores no se ejecutan en ningún otro sistema operativo porque la funcionalidad principal de los contenedores está ligada al kernel de Linux. Podman machine debe usarse para administrar máquinas MacOS y Windows, pero puede usarse opcionalmente en Linux.

podman machine init inicializa una nueva máquina virtual Linux donde se ejecutan los contenedores. Se generan automáticamente claves SSH para acceder a la VM y se agregan conexiones de sistema a la cuenta root y a una cuenta de usuario dentro de la VM.

Por defecto, la distribución de la VM es una imagen personalizada basada en Fedora CoreOS enviada a quay.io/podman/machine-os (compilada en https://github.com/containers/podman-machine-os). WSL es una excepción y se basa en una imagen Fedora personalizada.

Para verificar si hay una actualización disponible para el sistema operativo de tu máquina, puedes ejecutar el siguiente comando:

$ podman machine ssh 'sudo rpm-ostree upgrade --check'

Si hay una actualización disponible, puedes volver a ejecutar el comando anterior y eliminar --check y tu sistema operativo se actualizará. Después de actualizar, debes detener e iniciar tu máquina con podman machine stop && podman machine start para que surta efecto.

El mecanismo anterior solo se utiliza para actualizar versiones de parche (Z) de podman. Para actualizar a nuevas versiones principales y secundarias (X.Y) usa el comando podman machine os apply, consulta la documentación allí para obtener más información.

Nota: Actualizar como se describe anteriormente puede provocar desajustes de versión entre Podman en el host y Podman en la máquina. La ejecución de podman info debería revelar las versiones de ambos. Una configuración donde el host de Podman y la máquina no coinciden no está soportada.

Para actualizar la imagen WSL debes ejecutar dnf update dentro, usa el siguiente comando:

$ podman machine ssh dnf update

La configuración por defecto de la máquina Podman se puede establecer a través de la sección [machine] en el archivo containers.conf(5).

OPCIONES

--cpus=número

Número de CPUs.

--disk-size=número

Tamaño del disco para la VM invitada en GiB.

--help

Imprime la declaración de uso.

--ignition-path

Ruta completa del archivo de ignición.

Si se proporciona un archivo de ignición, el archivo se copia al CONF_DIR del usuario y se renombra. Además, no se generan claves SSH ni se establecen conexiones de sistema. Se asume que el usuario realiza estas acciones manualmente o de otra manera.

--image

Registro, ruta o URL completa de una imagen de VM. El objetivo del registro debe tener el formato docker://registro/repositorio/imagen:versión.

Nota: Solo se admitirán las imágenes proporcionadas por podman.

--memory, -m=número

Memoria (en MiB). Nota: 1024MiB = 1GiB.

--now

Inicia la máquina virtual inmediatamente después de que haya sido inicializada.

--playbook

Agrega el playbook de Ansible proporcionado a la máquina y lo ejecuta después del primer arranque.

Nota: El playbook se ejecutará con los mismos privilegios que se otorgan al usuario en la máquina virtual. El playbook proporcionado no puede incluir otros archivos del sistema host, ya que no se copiarán. El uso de la opción --playbook requerirá que la imagen incluya Ansible. La imagen predeterminada proporcionada incluirá Ansible.

--rootful

Si esta máquina prefiere la ejecución de contenedores con root (true) o sin root (false). Esta opción determina la configuración predeterminada de la conexión remota si no existen configuraciones de conexión remota.

El reenvío de la API, si está disponible, sigue esta configuración.

--swap, -s=número

Swap (en MiB). Nota: 1024MiB = 1GiB.

Renderiza un archivo zram-generator.conf con zram-size establecido al valor pasado a --swap

--timezone

Establece la zona horaria para la máquina y los contenedores. Los valores válidos son local o una zona horaria como America/Chicago. Un valor de local, que es el valor predeterminado, significa usar la zona horaria del host de la máquina.

La configuración de zona horaria no se utiliza con WSL. WSL establece automáticamente la zona horaria a la misma que el sistema operativo Windows del host.

--tls-verify

Requiere HTTPS y verifica certificados al contactar registros (predeterminado: true). Si se establece explícitamente en true, se utiliza la verificación TLS. Si se establece en false, no se utiliza la verificación TLS. Si no se especifica, se utiliza la verificación TLS a menos que el registro de destino esté listado como un registro inseguro en containers-registries.conf(5)

--usb=bus=número,devnum=número o vendor=hexadecimal,product=hexadecimal

Asigna un dispositivo USB del host a la VM a través de paso de USB. Solo compatible con máquinas QEMU.

El dispositivo necesita tener los permisos adecuados para ser pasado a la máquina. Esto significa que el dispositivo debe estar bajo tu grupo de usuario.

Ten en cuenta que usar el número de bus y dispositivo es más simple, pero los valores pueden cambiar en cada arranque o cuando se desconecta el dispositivo.

Al especificar un USB usando los ID de vendedor y producto, si más de un dispositivo tiene el mismo ID de vendedor y producto, se asigna el primer dispositivo disponible.

--user-mode-networking

Esta opción solo se puede usar para el proveedor WSL en Windows. En todas las demás plataformas, esta opción se ignora y la red en modo usuario siempre será true allí porque estos proveedores siempre dependen de gvproxy (nuestra herramienta de red en modo usuario para las VMs)

En contraste, el backend de Windows/WSL tiene como valor predeterminado false y sigue la configuración de red WSL estándar. Cambiar esta configuración a true en Windows/WSL informa a Podman que reemplace la configuración de red WSL al iniciar esta instancia de máquina con una distribución de red en modo usuario. Dado que WSL comparte el mismo kernel en todas las distribuciones, todas las demás distribuciones en ejecución reutilizan esta red. Del mismo modo, cuando la última instancia de máquina con la configuración true se detiene, se restaura la configuración de red original.

En algunas configuraciones de VPN, la VPN puede descartar el tráfico de interfaces de red alternativas, incluidos los dispositivos de red de VM. Al habilitar la red en modo usuario, las VPN observan todo el tráfico de la máquina podman como proveniente del host, evitando el problema.

--username

Nombre de usuario a utilizar para ejecutar comandos en la VM remota. El valor predeterminado es core para FCOS y user para Fedora (predeterminado en hosts de Windows). Debe coincidir con el utilizado dentro de la imagen de la VM resultante.

--volume, -v=fuente:destino[:opciones]

Monta un volumen de fuente a destino.

Crea un montaje. Si se especifica /host-dir:/machine-dir como la *fuente:destino*, Podman monta host-dir en el host a machine-dir en la máquina Podman.

Se pueden especificar opciones adicionales como una cadena separada por comas. Las opciones reconocidas son: * ro: montar volumen de solo lectura * rw: montar volumen de lectura/escritura (predeterminado) * security_model=[modelo]: especificar el modelo de seguridad 9p (ver abajo)

Nota: Los siguientes destinos están prohibidos para los volúmenes: /bin, /boot, /dev, /etc, /home, /proc, /root, /run, /sbin, /sys, /tmp, /usr, y /var. Los subdirectorios de estos destinos están permitidos pero los usuarios deben tener cuidado

VOLUMES

--volume, -v mount host directory into the machine's filesystem.

This option can be specified multiple times to mount multiple directories.

The format of the volume is HOST-DIR:CONTAINER-DIR[:OPTIONS]. The CONTAINER-DIR is the path in the virtual machine. The HOST-DIR is the path on the host system. The OPTIONS are comma-separated flags that control how the volume is mounted. Currently, the only supported option is ro for read-only mounts.

By default, volumes are mounted read-write.

On macOS, the default security model is mapped-xattr. This means that symlinks and extended attributes are stored as extended attributes on the host. This is suitable when the host and guest do not need to interoperate on the shared filesystem, but has caveats for actual shared access. Notably, symlinks on the host are not usable on the guest and vice versa. If interoperability is required, then choose none instead. Note that you should not try to mount to important directories as unexpected results may occur.

The 9p security model [determines] https://wiki.qemu.org/Documentation/9psetup#Starting_the_Guest_directly if and how the 9p filesystem translates some filesystem operations before actual storage on the host.

In order to allow symlinks to work, on MacOS the default security model is
none.

The value of mapped-xattr specifies that 9p store symlinks and some file attributes as extended attributes on the host. This is suitable when the host and the guest do not need to interoperate on the shared filesystem, but has caveats for actual shared access; notably, symlinks on the host are not usable on the guest and vice versa. If interoperability is required, then choose none instead, but keep in mind that the guest is not able to do things that the user running the virtual machine cannot do, e.g. create files owned by another user. Using none is almost certainly the best choice for read-only volumes.

Example: -v "$HOME/git:$HOME/git:ro,security_model=none"

Default volume mounts are defined in containers.conf. Unless changed, the default values is $HOME:$HOME.

Note on Windows Subsystem for Linux (WSL) Since all drives are mounted at /mnt on startup by default in WSL, passing --volume is redundant and has no effect. The host home directory for a C: drive will be mounted at /mnt/c/Users/<my username>.

EJEMPLOS

Inicializa la máquina Podman por defecto, descargando el contenido de Internet.

$ podman machine init

Inicializa una máquina Podman para el nombre especificado descargando el contenido de Internet.

$ podman machine init myvm

Inicializa y arranca una nueva máquina Podman en un solo paso.

podman machine init --now

Inicializa la máquina Podman por defecto descargando el contenido de Internet, por defecto en modo rootful. El valor por defecto es rootless.

$ podman machine init --rootful

Inicializa la máquina Podman por defecto, anulando su tamaño de disco de disco, descargando el contenido de Internet.

$ podman machine init --disk-size 50

Inicializa la máquina Podman especificada anulando su tamaño de memoria, descargando el contenido de Internet.

$ podman machine init --memory=1024 myvm

Inicializa la máquina Podman por defecto con el directorio del host /Users montado en la VM en /Users.

$ podman machine init -v /Users:/Users

Inicializa la máquina Podman por defecto con el paso de un dispositivo USB especificado con opciones. Solo compatible con máquinas QEMU.

$ podman machine init --usb vendor=13d3,product=5406

Inicializa la máquina Podman por defecto con el paso de un dispositivo USB especificado con opciones. Solo compatible con máquinas QEMU.

$ podman machine init --usb bus=1,devnum=3
