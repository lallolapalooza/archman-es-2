podman(1) Manual de Comandos Generales podman(1)

NOMBRE

podman - Herramienta simple de gestión de pods, contenedores e imágenes

SINOPSIS

podman [opciones] comando

DESCRIPCIÓN

Podman (Gestor de Pods) es un motor de contenedores completo que es una herramienta simple sin demonio (daemonless). Podman proporciona una línea de comandos comparable a la de Docker-CLI que facilita la transición desde otros motores de contenedores y permite la gestión de pods, contenedores e imágenes. En pocas palabras: alias docker=podman. La mayoría de los comandos de Podman se pueden ejecutar como un usuario normal, sin requerir privilegios adicionales.

Podman utiliza Buildah(1) internamente para crear imágenes de contenedor. Ambas herramientas comparten el almacenamiento de imágenes (no de contenedores), por lo tanto, cada una puede usar o manipular imágenes (pero no contenedores) creadas por la otra.

La configuración predeterminada para las opciones se define en containers.conf. La mayoría de las configuraciones para conexiones remotas utilizan el containers.conf del servidor, excepto cuando se documenta en las páginas del manual.

podman [OPCIONES GLOBALES]

OPCIONES GLOBALES

--cdi-spec-dir=ruta

La ruta del directorio de especificaciones CDI (puede establecerse varias veces). La ruta predeterminada es /etc/cdi.

--cgroup-manager=gestor

El gestor de CGroup a utilizar para los cgroups de los contenedores. Los valores admitidos son cgroupfs o systemd. El valor predeterminado es systemd a menos que se sobrescriba en el archivo containers.conf.

Nota: Establecer esta opción puede causar que ciertos comandos fallen cuando se llaman en contenedores creados previamente por el otro tipo de gestor de CGroup. Nota: El gestor de CGroup no se admite en modo sin privilegios (rootless) cuando se utiliza la Versión 1 de CGroups.

--config

Ubicación del archivo de configuración. Principalmente para compatibilidad con Docker, solo se admiten las partes de autenticación de la configuración.

--conmon

Ruta del binario de conmon (La ruta predeterminada está configurada en containers.conf)

--connection, -c

Conexión a utilizar para podman remoto, incluyendo máquinas Mac y Windows (excluyendo WSL2), (La conexión predeterminada está configurada en containers.conf). Establecer esta opción cambia la opción --remote a true. Las conexiones remotas utilizan el containers.conf local como predeterminado.

--events-backend=tipo

Backend a utilizar para almacenar eventos. Los valores permitidos son file, journald y none. Cuando se especifica file, los eventos se almacenan en <tmpdir>/events/events.log (ver --tmpdir a continuación).

--help, -h

Imprimir el enunciado de uso

--hooks-dir=ruta

Cada archivo *.json en la ruta configura un hook para los contenedores de Podman. Para más detalles sobre la sintaxis de los archivos JSON y la semántica de la inyección de hooks, ver oci-hooks(5). Podman y libpod actualmente admiten los esquemas de hooks 1.0.0 y 0.1.0, aunque el esquema 0.1.0 está obsoleto.

Esta opción puede establecerse varias veces; las rutas de las opciones posteriores tienen mayor precedencia (en oci-hooks(5) se discute la precedencia de directorios).

Para las condiciones de anotación, libpod utiliza cualquier anotación establecida en la configuración OCI generada.

Para las condiciones de montaje de enlace (bind-mount), solo se consideran los montajes solicitados explícitamente por el llamador a través de --volume. Los montajes de enlace que libpod inserta por defecto (por ejemplo, /dev/shm) no se consideran.

Si --hooks-dir no está establecido para los llamadores con privilegios (root), Podman y libpod actualmente tienen como valor predeterminado /usr/share/containers/oci/hooks.d y /etc/containers/oci/hooks.d en orden de precedencia creciente. Se recomienda migrar al establecimiento explícito de --hooks-dir.

Podman y libpod actualmente admiten un estado adicional precreate que se llama antes de la operación create del runtime. A diferencia de las otras etapas, que reciben el estado del contenedor en su entrada estándar, los hooks de precreate reciben la configuración propuesta del runtime en su entrada estándar. Pueden modificar esa configuración como consideren oportuno, y escribir la forma alterada en su salida estándar.

ADVERTENCIA: el hook precreate permite que ocurran cambios potentes, como la adición de montajes adicionales a la configuración del runtime. Ese poder también hace que sea fácil romper cosas. Antes de informar errores de libpod, intente ejecutar un contenedor con los hooks de precreate deshabilitados para ver si el problema se debe a uno de los hooks.

--identity=ruta

Ruta del archivo de identidad ssh. Si el archivo de identidad ha sido cifrado, podman le pedirá al usuario la frase de contraseña. Si no se proporciona ningún archivo de identidad y no se especifica ningún usuario, podman utilizará por defecto al usuario que ejecuta el comando podman. Podman pedirá la contraseña de inicio de sesión en el servidor remoto.

Precedencia en la resolución del valor de identidad:
- valor de la línea de comandos
- variable de entorno CONTAINER_SSHKEY, si se encuentra CONTAINER_HOST
- containers.conf Las conexiones remotas utilizan el containers.conf local como predeterminado.

--imagestore=ruta

Ruta del imagestore donde se almacenan las imágenes. Por defecto, la biblioteca de almacenamiento almacena todas las imágenes en el graphroot, pero si se proporciona un imagestore, la biblioteca de almacenamiento almacenará las imágenes recién descargadas en el imagestore proporcionado y seguirá utilizando el graphroot para todo lo demás. Si el usuario está utilizando el controlador overlay, las imágenes que ya formaban parte del graphroot seguirán siendo accesibles.

Esto anulará la opción imagestore en containers-storage.conf(5), consulte containers-storage.conf(5) para más detalles.

--log-level=nivel

Registrar mensajes en el nivel especificado o superior: debug, info, warn, error, fatal o panic (predeterminado: warn)

--module=ruta

Cargar el módulo containers.conf(5) especificado. Puede ser una ruta absoluta o relativa. Consulte containers.conf(5) para obtener detalles.

Esta opción no es compatible con el cliente remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2). Además, tenga en cuenta que esta opción es una opción a nivel de root y debe especificarse antes de cualquier subcomando de Podman.

--network-cmd-path=ruta

Ruta del comando slirp4netns(1) a utilizar para configurar una red slirp4netns. Si se usa "", el binario se buscará primero utilizando la opción helper_binaries_dir en containers.conf, y segundo utilizando la variable de entorno $PATH. Nota: Esta opción está obsoleta y se eliminará con Podman 6.0. Utilice la opción helper_binaries_dir en containers.conf en su lugar.

--network-config-dir=directorio

Ruta del directorio donde se encuentran los archivos de configuración de red. Para el backend netavark, se utiliza "/etc/containers/networks" como root y "$graphroot/networks" como rootless. Para el backend CNI, el valor predeterminado es "/etc/cni/net.d" como root y "$HOME/.config/cni/net.d" como rootless. CNI está obsoleto y se eliminará en la próxima versión mayor de Podman, la 5.0, en favor de Netavark.

--out=ruta

Redirigir la salida de podman a la ruta especificada sin afectar la salida del contenedor o sus registros. Este parámetro se puede utilizar para capturar la salida de cualquiera de los comandos de podman directamente en un archivo y permitir la supresión de la salida de podman especificando /dev/null como ruta. Para deshabilitar explícitamente el registro del contenedor, se debe usar la opción --log-driver.

--remote, -r

Cuando es verdadero, el acceso al servicio Podman es remoto. El valor predeterminado es falso. La configuración se puede modificar en el archivo containers.conf. Si la variable de entorno CONTAINER_HOST está establecida, la opción --remote tendrá como valor predeterminado true.

--root=valor

Directorio raíz de almacenamiento en el que se almacenan los datos, incluidas las imágenes (predeterminado: "/var/lib/containers/storage" para el UID 0, "$HOME/.local/share/containers/storage" para otros usuarios). Directorio raíz predeterminado configurado en containers-storage.conf(5).

Al anular esta opción, se ignorarán los ajustes de storage-opt en containers-storage.conf(5). El usuario debe especificar opciones adicionales a través del indicador --storage-opt.

--runroot=valor

Directorio de estado de almacenamiento donde se almacena toda la información de estado (predeterminado: "/run/containers/storage" para el UID 0, "/run/user/$UID/run" para otros usuarios). Directorio de estado predeterminado configurado en containers-storage.conf(5).

--runtime=valor

Nombre del runtime OCI especificado en containers.conf o ruta absoluta al binario compatible con OCI utilizado para ejecutar contenedores.

--runtime-flag=flag

Añade indicadores globales para el runtime del contenedor. Para ver los indicadores compatibles, consulte las páginas man del runtime de contenedor seleccionado (runc es el runtime predeterminado, la página man a consultar es runc(8). Cuando la máquina está configurada para cgroup V2, el runtime predeterminado es crun, la página man a consultar es crun(8).).

Los indicadores de runtime predeterminados se pueden añadir en containers.conf.

Nota: No pase el guion inicial -- al indicador. Para pasar el indicador de runc --log-format json a podman build, la opción dada puede ser --runtime-flag log-format=json.

--ssh=valor

Esta opción permite al usuario cambiar el modo ssh, lo que significa que en lugar de usar el modo predeterminado golang, se puede usar --ssh=native para usar el binario ssh instalado y el archivo de configuración declarado en containers.conf.

--storage-driver=valor

Controlador de almacenamiento. El controlador de almacenamiento predeterminado para el UID 0 está configurado en containers-storage.conf(5) en modo sin root), y es vfs para usuarios no root cuando fuse-overlayfs no está disponible. La variable de entorno STORAGE_DRIVER anula el valor predeterminado. El controlador especificado con --storage-driver anula todo.

Al anular esta opción, se ignorarán los ajustes de storage-opt en containers-storage.conf(5). El usuario debe especificar opciones adicionales a través del indicador --storage-opt.

--storage-opt=valor

Especifica una opción del controlador de almacenamiento. Las opciones del controlador de almacenamiento predeterminadas están configuradas en containers-storage.conf(5). La variable de entorno STORAGE_OPTS anula el valor predeterminado. Las opciones especificadas con --storage-opt anulan todo. Especifique --storage-opt="" para que no se utilicen opciones de almacenamiento.

--syslog

Envía información de registro a syslog además de a la consola (predeterminado: false).

En clientes remotos, incluidas las máquinas Mac y Windows (excluido WSL2), el registro se dirige al archivo $HOME/.config/containers/podman.log.

--tls-ca=ruta

Ruta a un archivo PEM que contiene el paquete de autoridad certificadora para verificar el certificado del servidor.

--tls-cert=ruta

Ruta a un archivo PEM que contiene el certificado del cliente TLS para presentar al servidor. También se debe proporcionar --tls-key.

--tls-key=ruta

Ruta a un archivo PEM que contiene la clave privada que coincide con --tls-cert. También se debe proporcionar --tls-cert.

--tmpdir=ruta

Ruta al directorio tmp, para contenido de runtime libpod. Predeterminado: $XDG_RUNTIME_DIR/libpod/tmp en modo sin root y /run/libpod/tmp en modo root.

NOTA: --tmpdir no se utiliza para el almacenamiento temporal de imágenes descargadas. Utilice la variable de entorno TMPDIR para cambiar la ubicación del almacenamiento temporal de las imágenes de contenedor descargadas. Podman utiliza por defecto /var/tmp.

--transient-store

Habilita un modo de almacenamiento transitorio global en el que todos los metadatos del contenedor se almacenan en medios no persistentes (es decir, en la ubicación especificada por --runroot). Este modo permite iniciar contenedores más rápido, así como garantizar un estado fresco al arrancar en caso de apagados incorrectos u otros problemas. Sin embargo, no es compatible con un modelo tradicional en el que los contenedores persisten entre reinicios.

El valor predeterminado para esto está configurado en containers-storage.conf(5).

--url=valor

URL para acceder al servicio Podman (predeterminado desde containers.conf, unix:///run/user/$UID/podman/podman.sock sin root o unix:///run/podman/podman.sock como root). Establecer esta opción cambia la opción --remote a true.

•
CONTAINER_HOST tiene el formato <esquema>://[<usuario[:<contraseña>]@]<host>[:<puerto>][<ruta>]

Detalles:
- esquema es uno de los siguientes:
* ssh (predeterminado): un socket unix(7) local en el host y puerto especificados, accesible a través de SSH
* tcp: una conexión TCP sin cifrar y sin autenticar al host y puerto especificados
* unix: un socket unix(7) local en la ruta especificada, o el predeterminado para el usuario
- usuario tiene como valor predeterminado root o el usuario actual en ejecución (solo ssh)
- contraseña no tiene valor predeterminado (solo ssh)
- host debe ser proporcionado y es la IP o el nombre de la máquina que aloja el servicio Podman (ssh y tcp)
- puerto tiene como valor predeterminado 22 (ssh y tcp)
- ruta tiene como valor predeterminado /run/podman/podman.sock, o /run/user/$UID/podman/podman.sock si se ejecuta sin root (unix), o debe especificarse explícitamente (ssh)

Precedencia de resolución del valor de URL:
- valor de la línea de comandos
- variable de entorno CONTAINER_HOST
- tabla engine.service_destinations en containers.conf, excluyendo el directorio /usr/share/containers
- unix:///run/podman/podman.sock

Las conexiones remotas utilizan el containers.conf local para los valores predeterminados.

Algunos ejemplos de valores de URL en formatos válidos:
- unix:///run/podman/podman.sock
- unix:///run/user/$UID/podman/podman.sock
- ssh://notroot@localhost:22/run/user/$UID/podman/podman.sock
- ssh://root@localhost:22/run/podman/podman.sock
- tcp://localhost:34451
- tcp://127.0.0.1:34451

--version, -v

Imprime la versión

--volumepath=valor

Directorio de volúmenes donde se almacena la información de volúmenes integrados (predeterminado: "/var/lib/containers/storage/volumes" para el UID 0, "$HOME/.local/share/containers/storage/volumes" para otros usuarios). La ruta de volumen predeterminada se puede anular en containers.conf.

Variables de Entorno

Podman puede configurar variables de entorno de la tabla env de [engine] en containers.conf. Estas variables se pueden anular pasando variables de entorno antes de los comandos de podman.

CONTAINERS_CONF

Establece las ubicaciones predeterminadas del archivo containers.conf

CONTAINERS_REGISTRIES_CONF

Establece la ubicación predeterminada del archivo registries.conf.

CONTAINERS_STORAGE_CONF

Establece la ubicación predeterminada del archivo storage.conf.

CONTAINER_CONNECTION

Anula el valor predeterminado de --connection para acceder al servicio Podman. Habilita automáticamente la opción --remote.

CONTAINER_HOST

Establece el valor predeterminado de --url para acceder al servicio Podman. Habilita automáticamente la opción --remote.

CONTAINER_SSHKEY

Establece el valor predeterminado de --identity para la ruta del archivo de clave ssh utilizada para acceder al servicio Podman.

PODMAN_CONNECTIONS_CONF

La ruta al archivo donde se almacenan las conexiones del sistema y las granjas creadas con podman system connection add y podman farm add, por defecto utiliza ~/.config/containers/podman-connections.json.

STORAGE_DRIVER

Establece el valor predeterminado de --storage-driver.

STORAGE_OPTS

Establece el valor predeterminado de --storage-opt.

TMPDIR

Establece la ubicación del almacenamiento temporal de las imágenes de contenedor descargadas. Podman utiliza por defecto /var/tmp.

XDG_CONFIG_HOME

En modo sin root, los archivos de configuración se leen de XDG_CONFIG_HOME cuando se especifica, de lo contrario, en el directorio principal del usuario en $HOME/.config/containers.

XDG_DATA_HOME

En modo sin root, las imágenes se extraen en XDG_DATA_HOME cuando se especifica, de lo contrario, en el directorio principal del usuario en $HOME/.local/share/containers/storage.

XDG_RUNTIME_DIR

En modo sin root, los datos de configuración temporales se almacenan en ${XDG_RUNTIME_DIR}/containers.

Acceso Remoto

El comando Podman se puede utilizar con servicios remotos usando el indicador --remote. Las conexiones se pueden realizar utilizando sockets de dominio de Unix locales, ssh o directamente a sockets tcp. Al especificar el indicador podman --remote, solo se utilizan las opciones globales --url, --identity, --log-level, --connection.

Información de conexión

La información de conexión también se puede gestionar utilizando el archivo containers.conf.

Códigos de salida

El código de salida de podman proporciona información sobre por qué el contenedor no se pudo ejecutar o por qué salió. Cuando los comandos de podman salen con un código distinto de cero, los códigos de salida siguen el estándar de chroot, véase a continuación:

125 El error es de podman en sí mismo

$ podman run --foo busybox; echo $?
Error: unknown flag: --foo
125

126 Se está ejecutando un comando de contenedor y el comando no se puede invocar

$ podman run busybox /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

127 Se está ejecutando un comando de contenedor y el comando no se puede encontrar

$ podman run busybox foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

Código de salida de lo contrario, podman devuelve el código de salida del comando del contenedor

$ podman run busybox /bin/sh -c 'exit 3'; echo $?
3

Archivos de configuración

containers.conf (/usr/share/containers/containers.conf, /etc/containers/containers.conf, $HOME/.config/containers/containers.conf)

Podman tiene valores predeterminados integrados para las opciones de línea de comandos. Estos valores predeterminados se pueden anular utilizando los archivos de configuración containers.conf.

Las distribuciones envían el archivo /usr/share/containers/containers.conf con sus valores predeterminados. Los administradores pueden anular campos en este archivo creando el archivo /etc/containers/containers.conf. Los usuarios pueden modificar aún más los valores predeterminados creando el archivo $HOME/.config/containers/containers.conf. Podman fusiona sus valores predeterminados integrados con los campos especificados de estos archivos, si existen. Los campos especificados en el archivo del usuario anulan el archivo del administrador, que anula el archivo de la distribución, que anula los valores predeterminados integrados.

Podman utiliza valores predeterminados integrados si no se encuentra ningún archivo containers.conf.

Si la variable de entorno CONTAINERS_CONF está establecida, entonces su valor se utiliza para el archivo containers.conf en lugar del predeterminado.

mounts.conf (/usr/share/containers/mounts.conf)

El archivo mounts.conf especifica directorios de montaje de volumen que se montan automáticamente dentro de los contenedores al ejecutar los comandos podman run o podman start. Los administradores pueden anular el archivo predeterminado creando /etc/containers/mounts.conf.

Cuando Podman se ejecuta en modo sin root, el archivo $HOME/.config/containers/mounts.conf anula el predeterminado si existe. Para obtener detalles, consulte containers-mounts.conf(5).

policy.json (/etc/containers/policy.json, $HOME/.config/containers/policy.json)

Los archivos de política de verificación de firmas se utilizan para especificar la política, por ejemplo, claves de confianza, aplicable al decidir si se acepta una imagen, o firmas individuales de esa imagen, como válidas. Para obtener detalles, consulte containers-policy.json(5).

registries.conf (/etc/containers/registries.conf, $HOME/.config/containers/registries.conf)

registries.conf es el archivo de configuración que especifica qué registros de contenedores se consultan al completar nombres de imagen que no incluyen una porción de registro o dominio.

Los usuarios no root de Podman pueden crear el archivo $HOME/.config/containers/registries.conf para que se utilice en lugar de los valores predeterminados del sistema.

Si la variable de entorno CONTAINERS_REGISTRIES_CONF está establecida, entonces su valor se utiliza para el archivo registries.conf en lugar del predeterminado.

storage.conf (/etc/containers/storage.conf, $HOME/.config/containers/storage.conf)

storage.conf es el archivo de configuración de almacenamiento para todas las herramientas que utilizan containers/storage

El archivo de configuración de almacenamiento especifica todas las opciones de almacenamiento de contenedores disponibles para las herramientas que utilizan almacenamiento de contenedores compartido.

Cuando Podman se ejecuta en modo sin root, el archivo $HOME/.config/containers/storage.conf se utiliza en lugar de los valores predeterminados del sistema.

Si la variable de entorno CONTAINERS_STORAGE_CONF está establecida, entonces su valor se utiliza para el archivo storage.conf en lugar del predeterminado.

DESCRIPTION

Podman is a daemonless container engine for developing, managing, and running OCI Containers on Linux Systems. Podman can be used to manage containers, container images, pods, container storage, and registries. Podman can also be used to run containers in rootless mode.

Podman can run containers using different container runtimes. The default is runc, but it can also use crun, or older versions of Docker. In rootless mode, Podman can also use fuse-overlayfs for storage, and slirp4netns or pasta for networking. For more details on Podman's rootless mode see the podman-rootless(7) man page.

GLOBAL OPTIONS

The following options are available on all podman commands:

--help, -h
Print usage statement for the command.
--log-level, -l
Specify the log level to use. Valid options are trace, debug, info, warn, error, fatal, panic, or disabled.
--registries.d
Use a directory of registry config files. The directory may be specified multiple times.
--rootless
Run in rootless mode. Only rootless containers are supported.
--runtime

Specify the container runtime to use. The default is crun. Other valid options are runc.

If the --runtime option is not specified, Podman will check the containers.conf(5) file for a default runtime. If there is no default runtime specified in the configuration file, then Podman will use crun as the default runtime.

--storage-driver

Specify the storage driver to use. The default is overlay. Other valid options are vfs, or zfs.

If the --storage-driver option is not specified, Podman will check the containers.conf(5) file for a default storage driver. If there is no default storage driver specified in the configuration file, then Podman will use overlay as the default storage driver.

--storage-opt
Specify a storage option. This option can be specified multiple times.
--version, -v
Print version information of podman.

Rootless mode

Podman supports running containers in rootless mode, which allows users to run containers without root privileges. This is achieved by using user namespaces and sub-UIDs/sub-GIDs.

To enable rootless mode, the user must have a range of sub-UIDs and sub-GIDs assigned to them. These ranges are defined in the /etc/subuid and /etc/subgid files, respectively.

Containers created by a non-root user are not visible to other users and are not seen or managed by Podman running as root.

It is required to have multiple UIDS/GIDS set for a user. Be sure the user is present in the files /etc/subuid and /etc/subgid.

Execute the following commands to add the ranges to the files

$ sudo usermod --add-subuids 10000-75535 USERNAME
$ sudo usermod --add-subgids 10000-75535 USERNAME

Or just add the content manually.

$ echo USERNAME:10000:65536 >> /etc/subuid
$ echo USERNAME:10000:65536 >> /etc/subgid

See the subuid(5) and subgid(5) man pages for more information.

Note: whitespace in any row of /etc/subuid or /etc/subgid, including trailing blanks, may result in no entry failures.

Images are pulled under XDG_DATA_HOME when specified, otherwise in the home directory of the user under .local/share/containers/storage.

Currently slirp4netns or pasta is required to be installed to create a network device, otherwise rootless containers need to run in the network namespace of the host.

In certain environments like HPC (High Performance Computing), users cannot take advantage of the additional UIDs and GIDs from the /etc/subuid and /etc/subgid systems. However, in this environment, rootless Podman can operate with a single UID. To make this work, set the ignore_chown_errors option in the containers-storage.conf(5) file. This option tells Podman when pulling an image to ignore chown errors when attempting to change a file in a container image to match the non-root UID in the image. This means all files get saved as the user's UID. Note this can cause issues when running the container.

NOTE: Unsupported file systems in rootless mode

The Overlay file system (OverlayFS) is not supported with kernels prior to 5.12.9 in rootless mode. The fuse-overlayfs package is a tool that provides the functionality of OverlayFS in user namespace that allows mounting file systems in rootless environments. It is recommended to install the fuse-overlayfs package. In rootless mode, Podman automatically uses the fuse-overlayfs program as the mount_program if installed, as long as the $HOME/.config/containers/storage.conf file was not previously created. If storage.conf exists in the homedir, add mount_program = "/usr/bin/fuse-overlayfs" under [storage.options.overlay] to enable this feature.

The Network File System (NFS) and other distributed file systems (for example: Lustre, Spectrum Scale, the General Parallel File System (GPFS)) are not supported when running in rootless mode as these file systems do not understand user namespace. However, rootless Podman can make use of an NFS Homedir by modifying the $HOME/.config/containers/storage.conf to have the graphroot option point to a directory stored on local (Non NFS) storage.
