podman-generate-systemd(1) Manual de Comandos Generales podman-generate-systemd(1)

NOMBRE

podman-generate-systemd - [OBSOLETO] Generar archivo(s) de unidad systemd para un contenedor o pod

SINOPSIS

podman generate systemd [opciones] contenedor|pod

DESCRIPCIÓN

OBSOLETO: Nota: podman generate systemd está obsoleto. Recomendamos usar archivos [Quadlet] al ejecutar contenedores o pods Podman bajo systemd. No hay planes para eliminar el comando. Recibirá correcciones urgentes de errores pero no nuevas características.

podman generate systemd crea un archivo de unidad systemd que puede usarse para controlar un contenedor o pod. Por defecto, el comando imprime el contenido de los archivos de unidad en stdout.

Generar archivos de unidad para un pod requiere que el pod se cree con un contenedor infra (ver --infra=true). Un contenedor infra se ejecuta durante toda la vida útil de un pod y, por lo tanto, es necesario para que systemd administre el ciclo de vida de la unidad principal del pod.

  • Nota: Al usar este comando con el cliente remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), coloque las unidades generadas en el sistema remoto. Además, asegúrese de que la variable de entorno XDG_RUNTIME_DIR esté configurada. Si no está configurada, configúrela con export XDG_RUNTIME_DIR=/run/user/$(id -u).
  • Nota: El comando podman run generado contiene una opción --sdnotify con el valor tomado del contenedor. Si el contenedor no tiene ningún valor explícitamente establecido o el valor está establecido en ignore, se usa el valor conmon. La razón para anular el valor predeterminado container es que casi ninguna carga de trabajo de contenedor envía mensajes de notificación. Systemd espera un mensaje de listo que nunca llega, si se usa el valor container para un contenedor que no envía mensajes de notificación. El uso del valor predeterminado podría haber sido involuntario por parte del usuario, por lo tanto, se anula el valor predeterminado.

Integración con Kubernetes

Un YAML de Kubernetes puede ejecutarse en systemd a través de la plantilla systemd podman-kube@.service. El argumento de la plantilla es la ruta al archivo YAML. Dado un archivo workload.yaml en el directorio principal, se puede ejecutar de la siguiente manera:

$ escaped=$(systemd-escape ~/workload.yaml)
$ systemctl --user start podman-kube@$escaped.service
$ systemctl --user is-active podman-kube@$escaped.service
active

OPCIONES

--after=dependency_name

Agregue la opción de unidad systemd After=, que son dependencias de ordenación entre la lista de dependencias y este servicio. Esta opción puede especificarse varias veces.

Las dependencias definidas por el usuario se agregan al archivo de unidad generado, pero las opciones existentes necesarias o definidas por defecto (por ejemplo, online.target) no se eliminan ni se anulan.

--container-prefix=prefix

Establezca el prefijo del nombre de la unidad systemd para los contenedores. El valor predeterminado es container.

--env, -e=env

Establezca variables de entorno en los archivos de unidad systemd.

Si una variable de entorno se especifica sin un valor, Podman comprueba el entorno del host en busca de un valor y establece la variable solo si está configurada en el host. Como caso especial, si una variable de entorno que termina en * se especifica sin un valor, Podman busca en el entorno del host variables que comiencen con el prefijo y agrega esas variables a los archivos de unidad systemd.

--files, -f

Genere archivos en lugar de imprimir en stdout. Los archivos generados se nombran {container,pod}-{ID,name}.service y se colocan en el directorio de trabajo actual.

Nota: En un sistema con SELinux habilitado, los archivos generados heredan contextos del directorio de trabajo actual. Dependiendo de la configuración de SELinux, pueden ser necesarios cambios en los archivos generados usando restorecon, chcon o semanage para permitir que systemd acceda a estos archivos. Alternativamente, use la opción -Z al ejecutar mv o cp.

--format=format

Imprima las unidades creadas en el formato especificado (json). Si se especifica --files, se imprimen las rutas a los archivos creados en lugar del contenido de la unidad.

--name, -n

Use el nombre del contenedor para el inicio, parada y descripción en el archivo de unidad

--new

Esta opción produce archivos de unidad que no esperan que los contenedores y pods existan. En su lugar, se crean nuevos contenedores y pods basándose en sus archivos de configuración. Los archivos de unidad se crean lo mejor posible y pueden necesitar una edición adicional; revise los archivos generados cuidadosamente antes de usarlos en producción.

Tenga en cuenta que --new solo funciona en contenedores y pods creados directamente a través de Podman (es decir, podman [container] {create,run} o podman pod create). No funciona en contenedores o pods creados a través de la API REST o a través de podman kube play. Para podman kube play, use la plantilla systemd podman-kube@.service en su lugar.

--no-header

No genere la cabecera que incluye metadatos como la versión de Podman y la marca de tiempo.

--pod-prefix=prefix

Establezca el prefijo del nombre de la unidad systemd para los pods. El valor predeterminado es pod.

--requires=dependency_name

Establezca la opción Requires= de la unidad systemd. Similar a wants, pero declara una dependencia de requisito más fuerte.

--restart-policy=policy

Establezca la política de reinicio de systemd. La política de reinicio debe ser una de: "no", "on-success", "on-failure", "on-abnormal", "on-watchdog", "on-abort" o "always". La política predeterminada es on-failure a menos que el contenedor se haya creado con una política de reinicio personalizada.

Tenga en cuenta que generar una unidad sin --new en un contenedor con una política de reinicio personalizada puede generar problemas al apagar; systemd intenta detener la unidad mientras Podman intenta reiniciarla. Se recomienda crear el contenedor sin --restart y usar la opción --restart-policy al generar el archivo de unidad.

--restart-sec=time

Establezca el valor de restartsec del servicio systemd. Configura el tiempo de espera antes de reiniciar un servicio (según lo configurado con restart-policy). Toma un valor en segundos.

--separator=separator

Establezca el separador del nombre de la unidad systemd entre el nombre/id de un contenedor/pod y el prefijo. El valor predeterminado es -.

--start-timeout=value

Anule el tiempo de espera de inicio predeterminado para el contenedor con el valor dado en segundos.

--stop-timeout=value

Anule el tiempo de espera de parada predeterminado para el contenedor con el valor dado en segundos.

--template

Agregue especificadores de plantilla para ejecutar varios servicios desde el archivo de unidad systemd.

Tenga en cuenta que si --new no se estableció en true, se establece en true por defecto. Sin embargo, el comando falla si --new se establece explícitamente en false.

--wants=dependency_name

Agregue la opción Wants= de la unidad systemd, de la que este servicio depende (débilmente). Esta opción puede especificarse varias veces. Esta opción no influye en el orden en que se inician o detienen los servicios.

Las dependencias definidas por el usuario se agregan al archivo de unidad generado, pero las opciones existentes necesarias o definidas por defecto (por ejemplo, online.target) no se eliminan ni se anulan.

EJEMPLOS

Generar e imprimir un archivo de unidad systemd para un contenedor

Para generar un archivo de unidad systemd para un contenedor llamado `mycontainer` e imprimirlo en stdout:

$ podman generate systemd mycontainer

Para generar un archivo de unidad systemd para un contenedor llamado `mycontainer` y guardarlo en el directorio actual como `container-mycontainer.service`:

$ podman generate systemd -f mycontainer

Generar un archivo de unidad systemd para un pod

Para generar un archivo de unidad systemd para un pod llamado `mypod` e imprimirlo en stdout:

$ podman generate systemd --pod-prefix=my-custom-pod-prefix mypod

Generar archivos de unidad para múltiples contenedores o pods

Para generar archivos de unidad systemd para todos los contenedores en ejecución:

$ podman generate systemd $(podman ps -q)

Generar nuevos archivos de unidad para contenedores o pods aún no creados

Para generar un archivo de unidad systemd que cree un nuevo contenedor llamado `my-new-container` basado en su configuración (por ejemplo, de un archivo de configuración de Podman existente):

$ podman generate systemd --new my-new-container

Para generar archivos de unidad systemd que creen nuevos contenedores o pods basándose en sus archivos de configuración existentes y guárdelos en el directorio actual:

$ podman generate systemd --new --files $(podman ps -aq)

Especificar dependencias para los archivos de unidad generados

Para generar un archivo de unidad systemd para `mycontainer` que dependa de `another.service` (Wants) y se inicie después de `network-online.target` (After):

$ podman generate systemd --wants=another.service --after=network-online.target mycontainer

Anular la política de reinicio y el retraso de reinicio para los archivos de unidad generados

Para generar un archivo de unidad systemd para `mycontainer` con una política de reinicio de `always` y un retraso de reinicio de 60 segundos:

$ podman generate systemd --restart-policy=always --restart-sec=60 mycontainer

Generar un archivo de unidad para un contenedor nombrado con un separador personalizado

Para generar un archivo de unidad systemd para un contenedor llamado `mycontainer` usando `_` como separador en el nombre de la unidad:

$ podman generate systemd --separator=_ mycontainer

NAME

podman-generate-systemd - Generate systemd unit files for Podman containers and pods

SYNOPSIS

podman generate systemd [options] [container ...]

DESCRIPTION

The podman generate systemd command generates systemd unit files for containers or pods. This allows users to manage containers or pods using systemd.

The generated unit files can be placed in /etc/systemd/system for system-wide services or in $HOME/.config/systemd/user for user services. Once generated and placed in the appropriate directory, the unit files can be managed using the systemctl command.

When generating unit files for containers, the generated unit file uses the container name or ID to start and stop the container. When generating unit files for pods, the generated unit file uses the pod name or ID to start and stop the pod. All containers within the pod are started and stopped when the pod service is started or stopped.

Use the --files option to output the generated unit files to stdout. By default, the generated unit files are not written to disk. If the --files option is used with the --name option, it will output the files named container-<container_name>.service and pod-<pod_name>.service.

Use the --new option to generate unit files that create and remove containers. This is useful for creating containers that are not already created.

OPTIONS

-c, --container-only
Generate systemd unit file only for the container, not for the pod. This option is only valid when generating unit files for containers that are part of a pod.
-d, --container-id-only
Generate a systemd unit file for the container, using the container ID. This option is only valid when generating unit files for containers. When used, the generated unit file will use the container ID to start and stop the container.
-f, --files
Output the generated unit files to stdout. By default, the unit files are not written to disk.
-i, --name
Replace the container name or ID in the generated unit file with the specified name. This option is only valid when generating unit files for containers. This option can be used multiple times to generate unit files for multiple containers.
--new
Generate systemd unit files that create and remove containers. This option is only valid when generating unit files for containers.
-p, --prefix
Specify a prefix for the generated unit files. This option is only valid when generating unit files for containers. The default prefix is container-.
--restart-policy <policy>
Specify the restart policy for the generated unit files. The policy can be always, on-failure, or no. The default policy is no.
-t, --time <seconds>
Specify the timeout in seconds for stopping the container or pod. The default timeout is 10 seconds.

EXAMPLES

Generate systemd unit file for a container

Generate a systemd unit file for a container running nginx with an always restart policy and 1-second timeout to stdout. Note that the RequiresMountsFor option in the Unit section ensures that the container storage for both the GraphRoot and the RunRoot are mounted prior to starting the service. For systems with container storage on disks like iSCSI or other remote block protocols, this ensures that Podman is not executed prior to any necessary storage operations coming online.

$ podman create --name nginx nginx:latest
$ podman generate systemd --restart-policy=always -t 1 nginx

# autogenerated by Podman 1.8.0
# Wed Mar 09 09:46:45 CEST 2020
[Unit]
Description=Podman container-de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6.service
Documentation=man:podman-generate-systemd(1)
Wants=network-online.target
After=network-online.target
RequiresMountsFor=/var/run/container/storage
[Service]
Restart=always
ExecStart=/usr/bin/podman start de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6
ExecStop=/usr/bin/podman stop   
        -t 1 de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6
KillMode=none

[Install]
WantedBy=default.target

Generate systemd unit file for a container with --new flag

The --new flag generates systemd unit files that create and remove containers at service start and stop commands (see ExecStartPre and ExecStopPost service actions). Such unit files are not tied to a single machine and can easily be shared and used on other machines.

$ sudo podman generate systemd --new --files --name bb310a0780ae
# container-busy_moser.service
# autogenerated by Podman 1.8.3
# Fri Apr  3 09:40:47 EDT 2020
[Unit]
Description=Podman container-busy_moser.service
Documentation=man:podman-generate-systemd(1)
Wants=network-online.target
After=network-online.target
RequiresMountsFor=/var/run/container/storage
[Service]
Environment=PODMAN_SYSTEMD_UNIT=%n
Restart=on-failure
ExecStartPre=/bin/rm -f %t/%n-pid %t/%n-cid
ExecStart=/usr/local/bin/podman run   
        --conmon-pidfile %t/%n-pid   
	--cidfile %t/%n-cid   
	--cgroups=no-conmon   
	-d   
	-dit alpine
ExecStop=/usr/local/bin/podman stop   
        --ignore   
        --cidfile %t/%n-cid -t 10
ExecStopPost=/usr/local/bin/podman rm   
        --ignore   
        -f   
	--cidfile %t/%n-cid
PIDFile=%t/%n-pid
KillMode=none
Type=forking
[Install]
WantedBy=default.target

Installation of generated systemd unit files.

Podman-generated unit files include an [Install] section, which carries installation information for the unit. It is used by the enable and disable commands of systemctl(1) during installation.

Once the systemd unit file is generated, install it to /etc/systemd/system to be run by the root user or to $HOME/.config/systemd/user for installing it as a non-root user. Enable the copied unit file or files using systemctl enable.

Note: Copying unit files to /etc/systemd/system and enabling it marks the unit file to be automatically started at boot. And similarly, copying a unit file to $HOME/.config/systemd/user and enabling it marks the unit file to be automatically started on user login.

# Generated systemd files.
$ podman pod create --name systemd-pod
$ podman create --pod systemd-pod alpine top
$ podman generate systemd --files --name systemd-pod
# Copy all the generated files.
$ sudo cp pod-systemd-pod.service container-great_payne.service /etc/systemd/system
$ systemctl enable pod-systemd-pod.service
Created symlink /etc/systemd/system/multi-user.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
Created symlink /etc/systemd/system/default.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
$ systemctl is-enabled pod-systemd-pod.service
enabled

To run the user services placed in $HOME/.config/systemd/user on first login of that user, enable the service with --user flag.

$ systemctl --user enable <.service>

The systemd user instance is killed after the last session for the user is closed. The systemd user instance can be started at boot and kept running even after the user logs out by enabling lingering using

$ loginctl enable-linger <username>

Use systemctl to perform operations on generated installed unit files.

Create and enable systemd unit files for a pod using the above examples as reference and use systemctl to perform operations.

Since systemctl defaults to using the root user, all the changes using the systemctl can be seen by appending sudo to the podman cli commands. To perform systemctl actions as a non-root user use the --user flag when interacting with systemctl.

Note: If the previously created containers or pods are using shared resources, such as ports, make sure to remove them before starting the generated systemd units.

$ systemctl --user start pod-systemd-pod.service
$ podman pod ps

podman-generate-systemd(1)

NAME

podman-generate-systemd - generate systemd unit files for pods or containers

SYNOPSIS

podman generate systemd [--container-prefix=<prefix>] [--name] [--new] [--no-dependencies] [--overwrite] [--pod-prefix=<prefix>] [--separator=<separator>] [--service-unit-dir=<dir>] [-t|--template] [container|pod ...]

DESCRIPTION

The podman generate systemd command generates systemd unit files for one or more containers or pods. The unit files can be used to manage containers or pods with systemd.

By default, podman generate systemd generates unit files for the specified containers or pods. The unit files are named after the containers or pods, with a .service suffix.

The generated unit files can be placed in the systemd unit directory (e.g., /etc/systemd/system/) and then managed with systemd commands like systemctl start, systemctl enable, etc.

OPTIONS

--container-prefix=<prefix>
Set a prefix for generated container unit files. Defaults to "".
--name
Use the container name as the unit name. If not specified, the container ID is used.
--new
Generate systemd unit file for a new container. This means that systemd will create the container. This option is only valid for containers.
--no-dependencies
Do not generate dependencies for the unit files. This means that the containers or pods will not be started or stopped automatically with other units.
--overwrite
Overwrite existing unit files.
--pod-prefix=<prefix>
Set a prefix for generated pod unit files. Defaults to "".
--separator=<separator>
Set a separator for generated unit file names. Defaults to -.
--service-unit-dir=<dir>
Directory where the generated unit files will be placed. Defaults to /etc/systemd/system.
-t, --template
Generate systemd unit file template. This means that the unit file will contain placeholders for values that need to be filled in later.

EXAMPLES


    # Generate systemd unit file for a container named 'mycontainer'
    $ podman generate systemd mycontainer

    # Generate systemd unit files for multiple containers
    $ podman generate systemd container1 container2

    # Generate systemd unit file for a pod named 'mypod'
    $ podman generate systemd --pod-prefix=mypod mypod

    # Generate systemd unit files for all running containers
    $ podman generate systemd $(podman ps -q)

    # Generate systemd unit file template for a container
    $ podman generate systemd --template mycontainer

    # Generate systemd unit file for a container with a custom prefix and separator
    $ podman generate systemd --container-prefix=app --separator=_ mycontainer
