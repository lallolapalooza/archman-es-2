podman-pod-create(1) Manual de Comandos Generales podman-pod-create(1)

NOMBRE

podman-pod-create - Crear un nuevo pod

SINOPSIS

podman pod create [opciones] [nombre]

DESCRIPCIÓN

Crea un pod vacío, o unidad de múltiples contenedores, y lo prepara para añadirle contenedores. El pod puede crearse con un nombre específico. Si no se proporciona un nombre, se generará uno aleatorio. El ID del pod se imprimirá en STDOUT. Luego puedes usar podman create --pod <id_del_pod|nombre_del_pod> ... para añadir contenedores al pod, y podman pod start <id_del_pod|nombre_del_pod> para iniciar el pod.

El operador puede identificar un pod de tres maneras: identificador largo UUID (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”) identificador corto UUID (“f78375b1c487”) Nombre (“jonah”)

Podman genera un UUID para cada pod, y si no se asigna un nombre al contenedor con --name, se genera un nombre de cadena aleatoria para él. Este nombre es útil para identificar un pod.

Nota: Las opciones relacionadas con el límite de recursos funcionan estableciendo los límites explícitamente en el padre cgroup del pod para todos los contenedores que se unan al pod. Un contenedor puede anular los límites de recursos al unirse a un pod. Por ejemplo, si un pod se creó a través de podman pod create --cpus=5, especificar podman container create --pod=<id_del_pod|nombre_del_pod> --cpus=4 hace que el contenedor use el límite menor. Además, los contenedores que especifican su propio cgroup, como --cgroupns=host, NO reciben los recursos cgroup asignados al nivel del pod.

OPCIONES

--add-host=nombre_host[;nombre_host[;...]]:ip

Añade un mapeo personalizado de host a IP al archivo /etc/hosts del pod.

La opción toma uno o varios nombres de host separados por punto y coma para ser mapeados a una única dirección IPv4 o IPv6, separados por dos puntos. También se puede usar para sobrescribir las direcciones IP de los nombres de host que Podman añade a /etc/hosts por defecto (ver también las opciones --name y --hostname). Esta opción se puede especificar varias veces para añadir mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede proporcionar la bandera especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de la configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que provocará que Podman falle con un mensaje de error. Puedes sobrescribir esta dirección IP usando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para añadir automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puedes evitarlo proporcionando la opción --no-hosts, o configurando host_containers_internal_ip="none" en containers.conf. Si no se configuró ninguna dirección host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se ejecuta en una máquina virtual usando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven en su lugar mediante el resolver DNS de gvproxy.

Podman utilizará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente usando la configuración base_hosts_file en containers.conf.

El archivo /etc/hosts se comparte entre todos los contenedores del pod.

--blkio-weight=peso

Peso relativo de entrada/salida de bloques. El peso es un valor entre 10 y 1000.

Esta opción no es compatible con sistemas sin raíz cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo del dispositivo de entrada/salida de bloques.

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se creará el cgroup para el pod. Si la ruta no es absoluta, se considera relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen.

--cpu-shares, -c=cuotas

Cuotas de CPU (peso relativo).

Por defecto, todos los contenedores reciben la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de las cuotas de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso por defecto es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una cuota de cpu de 1024 y otros dos tienen una configuración de cuota de cpu de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con una cuota de cpu de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las cuotas de tiempo de CPU se distribuyen entre todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de cuotas de CPU:

PID contenedor CPU Cuota de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin raíz cgroups V1.

--cpus=cantidad

Establece el número total de CPUs delegadas al pod. El valor por defecto es 0.000, lo que indica que no hay límite en la potencia de cálculo.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de los mismos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin raíz cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), usa --cpuset-mems=0,1 entonces los procesos en el contenedor solo usan memoria de los dos primeros nodos de memoria.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

--detach, -d

Ejecuta el pod en segundo plano y imprime el ID del pod.

--fault-tolerance

Define el comportamiento de tolerancia a fallos para el pod. Si se establece, los contenedores se reiniciarán en caso de fallo.

--gateway=ip

Especifica la dirección IP de la puerta de enlace para el pod.

--help, -h

Imprime un mensaje de uso.

--hostname=nombre_host

Establece el nombre de host para el pod. Si no se especifica, se utiliza el nombre de host generado por defecto.

--infra

Crea un pod de infraestructura con un contenedor de pausa.

Por defecto, todos los contenedores de un pod comparten el mismo espacio de nombres de red. Para que esto sea posible, se necesita un contenedor de pausa que mantenga abierto el espacio de nombres de red. Podman crea automáticamente un contenedor de pausa si no existe uno. Si la opción --infra no está presente, Podman intentará usar un contenedor de pausa existente. Si no hay uno disponible, Podman fallará. La opción --infra=false deshabilita la creación de un contenedor de pausa y se utiliza principalmente para podar la creación de pods de corta duración o cuando la red es gestionada externamente.

--ip=ip

Establece la dirección IP para el pod.

--kernel-memory=limit

Límite de memoria del kernel. El límite es un número entero positivo que representa la cantidad de memoria que puede usar el contenedor. El sufijo de unidad puede ser b (bytes), k (kilobytes), m (megabytes), o g (gigabytes). Si el límite no se establece, no hay límite en la memoria del kernel.

Para más información sobre cómo se calcula el límite de memoria del kernel, consulta la documentación de cgroups.

Esta opción no es compatible con sistemas sin raíz cgroups V1.

--memory, -m=limit

Límite de memoria. El límite es un número entero positivo que representa la cantidad de memoria que puede usar el contenedor. El sufijo de unidad puede ser b (bytes), k (kilobytes), m (megabytes), o g (gigabytes). Si el límite no se establece, no hay límite en la memoria.

Esta opción no es compatible con sistemas sin raíz cgroups V1.

--memory-reservation=limit

Límite de memoria reservada. El límite es un número entero positivo que representa la cantidad de memoria que se garantiza que puede usar el contenedor. El sufijo de unidad puede ser b (bytes), k (kilobytes), m (megabytes), o g (gigabytes).

Esta opción no es compatible con sistemas sin raíz cgroups V1.

--memory-swap=limit

Límite total de memoria (swap). El límite es un número entero positivo que representa la cantidad de memoria y swap que puede usar el contenedor. El sufijo de unidad puede ser b (bytes), k (kilobytes), m (megabytes), o g (gigabytes).

Esta opción no es compatible con sistemas sin raíz cgroups V1.

--name=nombre

Asigna un nombre al pod.

--network=none

No configura una interfaz de red para el pod.

--no-hosts

No añade entradas a /etc/hosts. La opción --add-host entra en conflicto con esta opción y con la opción no_hosts=true en containers.conf.

--notify

Activa las notificaciones de estado para el pod.

--pod-id-file=ruta_archivo

Escribe el ID del pod en el archivo especificado.

--privileged

Otorga capacidades extendidas al pod. Esto otorga al pod acceso completo a todos los dispositivos del host y anula todos los límites de seguridad.

--rootfs-size=limit

Establece el tamaño del sistema de archivos raíz para el pod. El límite es un número entero positivo que representa el tamaño del sistema de archivos raíz. El sufijo de unidad puede ser k (kilobytes), m (megabytes), o g (gigabytes).

--restart=policy

Establece la política de reinicio para el pod. Las políticas admitidas son: `no`, `on-failure`, `always`, `unless-stopped`.

--security-opt=opción

Añade o modifica opciones de seguridad. Las opciones disponibles dependen del tiempo de ejecución.

--sysctl=parámetro

Establece los parámetros sysctl en el pod.

Los parámetros sysctl disponibles dependen del host y de la configuración de seguridad.

--ulimit=ulimit

Establece los límites de recursos ulimit para el pod.

Formato: type=VALUE,soft=VALUE,hard=VALUE.

Los tipos válidos son: `cpu`, `cpu_set`, `fsize`, `memlock`, `msgqueue`, `nice`, `nofile`, `nproc`, `rtprio`, `sem`, `stack`, `nch`, `filtops`, `maxlogins`, `maxfiles`, `core`, `nobits`, `sigpending`, `msgmax`, `shmmax`, `shmmni`, `max_connections`, `max_files`, `max_sockets`, `max_tcp_connections`, `max_udp_sockets`.

Consulte la página del manual de `ulimit(3)` para más información sobre los valores.

--usage-policy=policy

Establece la política de uso de recursos para el pod.

Las políticas admitidas son: `hard` y `best-effort`.

`hard` aplica límites estrictos de recursos. `best-effort` permite que los contenedores usen tantos recursos como sea posible, pero permite que otros contenedores los estrangulen si es necesario.

--version

Imprime la información de la versión de Podman y sal.

EJEMPLOS

Crear un pod llamado mypod:

$ podman pod create --name mypod

Crear un pod con 2 CPUs y 512 MB de memoria:

$ podman pod create --cpus=2 --memory=512m mypod

Crear un pod con un nombre aleatorio y añadirlo al fondo:

$ podman pod create -d

Crear un pod con una política de reinicio en caso de fallo:

$ podman pod create --restart on-failure mypod

Crear un pod con un mapeo de host personalizado:

$ podman pod create --add-host="example.com:10.0.0.5" mypod

Crear un pod con un cgroup padre específico:

$ podman pod create --cgroup-parent=/user.slice/user-1000.slice mypod

Crear un pod con un límite de memoria kernel de 1 GB:

$ podman pod create --kernel-memory=1g mypod

Crear un pod con un nombre de host específico:

$ podman pod create --hostname=host.example.com mypod

Crear un pod sin configurar una interfaz de red:

$ podman pod create --network=none mypod

Crear un pod con opciones de seguridad SELinux:

$ podman pod create --security-opt label=type:container_t mypod

Crear un pod con un límite ulimit de archivos abiertos:

$ podman pod create --ulimit nofile=1024:2048 mypod

Crear un pod con una política de uso de recursos 'hard':

$ podman pod create --usage-policy=hard mypod

--device=dispositivo-host[:dispositivo-container][:permisos]

Añade un dispositivo host al pod. El parámetro opcional de permisos se puede usar para especificar los permisos del dispositivo combinando r para lectura, w para escritura y m para mknod(2).

Ejemplo: --device=/dev/sdc:/dev/xvdc:rwm.

Nota: si dispositivo-host es un enlace simbólico, primero se resuelve. El pod solo almacena los números mayor y menor del dispositivo host.

Podman puede cargar módulos del kernel necesarios para usar el dispositivo especificado. Los dispositivos para los que Podman carga módulos cuando es necesario son: /dev/fuse.

En modo sin raíz, el nuevo dispositivo se monta enlazado en el contenedor desde el host en lugar de que Podman lo cree dentro del espacio del contenedor. Como el montaje enlazado conserva su etiqueta SELinux en sistemas SELinux, el contenedor puede obtener un permiso denegado al acceder al dispositivo montado. Modifique la configuración de SELinux para permitir que los contenedores usen todas las etiquetas de dispositivo con el siguiente comando:

$ sudo setsebool -P container_use_devices=true

Nota: el pod implementa los dispositivos almacenando la configuración inicial pasada por el usuario y recreando el dispositivo en cada contenedor añadido al pod.

Esta opción no es compatible con sistemas sin raíz de cgroups V1.

--device-write-bps=ruta:tasa

Limita la tasa de escritura (en bytes por segundo) a un dispositivo (por ejemplo, --device-write-bps=/dev/sda:1mb).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, véase https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin raíz de cgroups V1.

--dns=direccion-ip

Establece servidores DNS personalizados en el archivo /etc/resolv.conf que se comparte entre todos los contenedores del pod. Se permite una opción especial, "none", que deshabilita la creación de /etc/resolv.conf para el pod.

--dns-option=opcion

Establece opciones DNS personalizadas en el archivo /etc/resolv.conf que se comparte entre todos los contenedores del pod.

--dns-search=dominio

Establece dominios de búsqueda DNS personalizados en el archivo /etc/resolv.conf que se comparte entre todos los contenedores del pod.

--exit-policy=continue | stop

Establece la política de salida del pod cuando el último contenedor sale. Las políticas admitidas son:

Política de Salida Descripción
continue El pod continúa ejecutándose, manteniendo vivo su contenedor de infraestructura, cuando el último contenedor sale. Se usa por defecto.
stop El pod (incluyendo su contenedor de infraestructura) se detiene cuando el último contenedor sale. Se usa en kube play y quadlets.

--gidmap=gid-pod:gid-host:cantidad

Mapa GID para el espacio de nombres de usuario. El uso de esta bandera ejecuta todos los contenedores del pod con el espacio de nombres de usuario habilitado. Entra en conflicto con las banderas --userns y --subgidname.

--gpus=ENTRADA

Dispositivos GPU a añadir al contenedor ('all' para pasar todas las GPUs). Actualmente solo se admiten dispositivos Nvidia.

--help, -h

Imprime el enunciado de uso.

--hostname=nombre

Establece el nombre de host del pod dentro de todos los contenedores.

El nombre de host proporcionado también se añade al archivo /etc/hosts utilizando la dirección IP principal del contenedor (ver también la opción --add-host).

--hosts-file=ruta | none | image

Archivo base para crear el archivo /etc/hosts dentro del contenedor. Debe ser una ruta absoluta a un archivo en el sistema host, o una de las siguientes banderas especiales:
"" Sigue el archivo base de hosts base_hosts_file en la configuración de containers.conf (el valor por defecto)
none No usar un archivo base (es decir, empezar con un archivo vacío)
image Usar el archivo /etc/hosts de la imagen del contenedor como archivo base

--infra

Crea un contenedor de infraestructura y lo asocia al pod. Un contenedor de infraestructura es un contenedor ligero utilizado para coordinar el espacio de nombres del kernel compartido de un pod. Por defecto: true.

--infra-command=comando

El comando que se ejecuta para iniciar el contenedor de infraestructura. Por defecto: "/pause".

--infra-conmon-pidfile=archivo

Escribe el PID del proceso conmon del contenedor de infraestructura en un archivo. Como conmon se ejecuta en un proceso separado de Podman, esto es necesario cuando se usa systemd para gestionar contenedores y pods de Podman.

--infra-image=imagen

La imagen personalizada que se utiliza para el contenedor de infraestructura. A menos que se especifique, Podman construye una imagen local personalizada que no requiere descargar una imagen.

--infra-name=nombre

El nombre que se utiliza para el contenedor de infraestructura del pod.

--ip=ipv4

Especifica una dirección IPv4 estática para el pod, por ejemplo 10.88.64.128. Esta opción solo se puede usar si el pod se une a una única red, es decir, si --network=nombre-red se usa como máximo una vez, y si el pod no se une al espacio de nombres de red de otro contenedor vía --network=container:id. La dirección debe estar dentro del pool de direcciones IP de la red (por defecto 10.88.0.0/16).

Para especificar múltiples direcciones IP estáticas por pod, establezca múltiples redes usando la opción --network con una dirección IP estática especificada para cada una usando el modo ip para esa opción.

--ip6=ipv6

Especifica una dirección IPv6 estática para el pod, por ejemplo fd46:db93:aa76:ac37::10. Esta opción solo se puede usar si el pod se une a una única red, es decir, si --network=nombre-red se usa como máximo una vez, y si el pod no se une al espacio de nombres de red de otro contenedor vía --network=container:id. La dirección debe estar dentro del pool de direcciones IPv6 de la red.

Para especificar múltiples direcciones IPv6 estáticas por pod, establezca múltiples redes usando la opción --network con una dirección IPv6 estática especificada para cada una usando el modo ip6 para esa opción.

--label, -l=clave=valor

Añade metadatos a un pod.

--label-file=archivo

Lee un archivo delimitado por líneas de etiquetas.

--mac-address=direccion

Dirección MAC de la interfaz de red del pod (por ejemplo, 92:d0:c6:0a:29:33). Esta opción solo se puede usar si el pod se une a una única red, es decir, si --network=nombre-red se usa como máximo una vez, y si el pod no se une al espacio de nombres de red de otro contenedor vía --network=container:id.

Recuerde que la dirección MAC en una red Ethernet debe ser única. La dirección de enlace local IPv6 se basa en la dirección MAC del dispositivo según RFC4862.

Para especificar múltiples direcciones MAC estáticas por pod, establezca múltiples redes usando la opción --network con una dirección MAC estática especificada para cada una usando el modo mac para esa opción.

--memory, -m=número[unidad]

Límite de memoria. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Permite que la memoria disponible para un contenedor sea limitada. Si el host admite memoria swap, el ajuste de memoria -m puede ser mayor que la RAM física. Si se especifica un límite de 0 (sin usar -m), la memoria del contenedor no se limita. El límite real puede redondearse al múltiplo del tamaño de página del sistema operativo (el valor es muy grande, es decir, millones de billones).

Esta opción no es compatible con sistemas sin raíz de cgroups V1.

--memory-swap=número[unidad]

Un valor límite igual a memoria más swap. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Debe usarse con la bandera -m (--memory). El valor del argumento debe ser mayor que el de
-m (--memory). Por defecto, se establece en el doble del valor de --memory.

Establezca número en -1 para habilitar swap ilimitado.

Esta opción no es compatible con sistemas sin raíz de cgroups V1.

--name, -n=nombre

Asigna un nombre al pod.

--network=modo, --net

Establece el modo de red para el pod.

Los valores válidos de modo son:

•
bridge[:OPCIONES,...]: Crea una pila de red en el bridge por defecto. Este es el valor por defecto para contenedores rootful. Es posible especificar estas opciones adicionales:
  • alias=nombre: Añade un alias con ámbito de red para el contenedor.
- nombre: --network tipo: cadena descripción: Conecta el contenedor a una red. Las redes disponibles son:
  • bridge: Crea una red de puente en el host y conecta el contenedor a ella. Usa la configuración predeterminada de la red de puente de Podman o especifica las siguientes opciones:
    • ip=IPv4: Especifica una dirección IPv4 estática para este contenedor.
    • ip6=IPv6: Especifica una dirección IPv6 estática para este contenedor.
    • mac=MAC: Especifica una dirección MAC estática para este contenedor.
    • interface_name=nombre: Especifica un nombre para la interfaz de red creada dentro del contenedor.
    • host_interface_name=nombre: Especifica un nombre para la interfaz de red creada fuera del contenedor.
  • <nombre o ID de red>[:OPCIONES,...]: Conéctate a una red definida por el usuario; este es el nombre o ID de una red creada por podman network create. Es posible especificar las mismas opciones descritas en el modo bridge arriba. Usa la opción --network varias veces para especificar redes adicionales.
    Para compatibilidad con versiones anteriores, también es posible especificar redes separadas por comas en el primer argumento --network, sin embargo, esto te impide usar las opciones descritas en la sección de bridge arriba.
  • none: Crea un espacio de nombres de red para el contenedor pero no configura interfaces de red para él, por lo tanto, el contenedor no tiene conectividad de red.
  • container:id: Reutiliza la pila de red de otro contenedor.
  • host: Usa el espacio de nombres de red del host para el contenedor en lugar de crear un espacio de nombres aislado. Advertencia: Esto le da al contenedor acceso completo a los sockets de dominio Unix abstractos y a los sockets TCP/UDP enlazados a localhost. Dado que estos mecanismos se utilizan a menudo para evitar el acceso a servicios sensibles del sistema, aislándolos del acceso de entidades externas, el uso de esta opción puede considerarse una vulnerabilidad de seguridad.
  • ns:ruta: Ruta a un espacio de nombres de red para unirse.
  • private: Crea un nuevo espacio de nombres para el contenedor. Esto utiliza el modo bridge para contenedores con privilegios (rootful) y slirp4netns para los que no los tienen (rootless).
  • slirp4netns[:OPCIONES,...]: usa slirp4netns(1) para crear una pila de red de usuario. Es posible especificar estas opciones adicionales, que también se pueden establecer con network_cmd_options en containers.conf:
    • allow_host_loopback=true|false: Permite a slirp4netns acceder a la IP de loopback del host (por defecto es 10.0.2.2 o la segunda IP del subred CIDR de slirp4netns cuando se cambia, ver la opción cidr abajo). El valor por defecto es false.
    • mtu=MTU: Especifica la MTU a usar para esta red. (Por defecto es 65520).
    • cidr=CIDR: Especifica el rango de IP a usar para esta red. (Por defecto es 10.0.2.0/24).
    • enable_ipv6=true|false: Habilita IPv6. Por defecto es true. (Requerido para outbound_addr6).
    • outbound_addr=INTERFACE: Especifica la interfaz de salida a la que se enlaza slirp (solo tráfico ipv4).
    • outbound_addr=IPv4: Especifica la dirección ipv4 de salida a la que se enlaza slirp.
    • outbound_addr6=INTERFACE: Especifica la interfaz de salida a la que se enlaza slirp (solo tráfico ipv6).
    • outbound_addr6=IPv6: Especifica la dirección ipv6 de salida a la que se enlaza slirp.
    • port_handler=rootlesskit: Usa rootlesskit para el reenvío de puertos. Por defecto.
      Nota: Rootlesskit cambia la dirección IP de origen de los paquetes entrantes a una dirección IP en el espacio de nombres de red del contenedor, generalmente 10.0.2.100. Si la aplicación requiere la dirección IP de origen real, por ejemplo, registros del servidor web, usa el manejador de puertos slirp4netns. El manejador de puertos rootlesskit también se usa para contenedores sin privilegios cuando se conectan a redes definidas por el usuario.
    • port_handler=slirp4netns: Usa el reenvío de puertos slirp4netns, es más lento que rootlesskit pero preserva la dirección IP de origen correcta. Este manejador de puertos no se puede usar para redes definidas por el usuario.
  • pasta[:OPCIONES,...]: usa pasta(1) para crear una pila de red en modo usuario.
    Este es el valor por defecto para contenedores sin privilegios (rootless) y solo se admite en modo sin privilegios.
    Por defecto, las direcciones y rutas IPv4 e IPv6, así como el nombre de la interfaz del pod, se copian del host. El reenvío de puertos preserva la dirección IP de origen original. Las opciones descritas en pasta(1) se pueden especificar como argumentos separados por comas.
    En términos de opciones de pasta(1), se proporciona --config-net por defecto, para configurar la red cuando se inicia el contenedor, y también se asume --no-map-gw por defecto, para evitar el acceso directo desde el contenedor al host utilizando la dirección de gateway. Esto último se puede anular pasando --map-gw en las opciones específicas de pasta (a pesar de no ser una opción real de pasta(1)).
    Para una mejor integración con el manejo de DNS, se pasa --dns-forward 169.254.1.1, y esta dirección se agrega a resolv.conf(5) como el primer resolvedor. Es posible pasar --dns-forward explícitamente en caso de que se deba usar una dirección IP diferente. Para que la entrada host.containers.internal en /etc/hosts funcione y permita conexiones al host, se pasa --map-guest-addr 169.254.1.2. Nuevamente, se puede configurar explícitamente para elegir una dirección IP diferente.
    Además, se pasan -t none y -u none si, respectivamente, no se configura ningún reenvío de puertos TCP o UDP del host al contenedor (a través de --publish de Podman o pasando directamente las opciones -t/-u de pasta), para deshabilitar el reenvío automático de puertos basado en puertos enlazados. De manera similar, se proporcionan -T none y -U none para deshabilitar la misma funcionalidad desde el contenedor al host.
    Todas las opciones también se pueden establecer en containers.conf(5); consulta la clave pasta_options en la sección de red de ese archivo.
    Algunos ejemplos:
    • pasta:--map-gw: Permite que el contenedor acceda directamente al host utilizando la dirección de gateway.
    • pasta:--mtu,1500: Especifica una MTU de 1500 bytes para la interfaz tap en el contenedor.
    • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con gateway 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece la MTU en 1500 bytes, deshabilita NDP, DHCPv6 y el soporte DHCP.
    • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: igual que lo anterior, pero deja la MTU en 65520 bytes
    • pasta:-t,auto,-u,auto,-T,auto,-U,auto: habilita el reenvío automático de puertos basado en los puertos enlazados observados desde los lados del host y del contenedor
    • pasta:-T,5201: habilita el reenvío del puerto TCP 5201 desde el contenedor al host, utilizando la interfaz de loopback en lugar de la interfaz tap para mejorar el rendimiento
Las opciones adicionales se pasarán a netavark sin validación. Esto puede ser útil para pasar argumentos a los plugins de netavark.

Por ejemplo, para establecer una dirección IPv4 estática y una dirección MAC estática, usa --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

Podman is usually run at the user level. When it needs to contact the Podman service, it does so using a Unix socket.

EXAMPLES

Start a pod with two containers, each running a different service:

    $ podman pod create --name mypod --infra=true
    $ podman run --pod mypod --name web -d -p 8080:80 nginx
    $ podman run --pod mypod --name db -d -p 5432:5432 postgres

Start a pod with a container that runs a command and then exits:

    $ podman run --pod mypod alpine echo hello world

Start a pod with a container that runs a command in the foreground:

    $ podman run --pod mypod --tty=true alpine sh

Start a pod with a specific network configuration:

    $ podman pod create --name mypod --network=bridge --subnet=10.10.0.0/24
    $ podman run --pod mypod --name web -d nginx

Start a pod with shared IPC namespace:

    $ podman pod create --name mypod --ipc=shared
    $ podman run --pod mypod --name app1 alpine sleep infinity
    $ podman run --pod mypod --name app2 alpine sh -c "echo foobar > /dev/ipc/foo"

Start a pod with shared network namespace:

    $ podman pod create --name mypod --network=shared
    $ podman run --pod mypod --name web alpine sleep infinity
    $ podman run --pod mypod --name client alpine ping -c 1 web

    Agregue la opción :ro o :rw para montar un volumen en modo de solo lectura o lectura/escritura, respectivamente. Por defecto, los volúmenes se montan en modo lectura/escritura. Ver ejemplos.

    Cambio de propietario de montajes de volumen

    Cuando un volumen con nombre se monta por primera vez en un contenedor, Podman ajusta automáticamente la propiedad del punto de montaje del volumen durante la inicialización del contenedor. Esta operación de cambio de propietario ocurre bajo las siguientes condiciones:

    • El volumen aún no se usó (tiene NeedsChown establecido en true)
    • El volumen está vacío o aún no se ha copiado
    • El volumen no es administrado por un controlador de volumen externo
    • El controlador de volumen no es "image"

    Para volúmenes con montajes idmapped (usando la opción idmap), el cambio de propietario tiene en cuenta las asignaciones del espacio de nombres de usuario del contenedor, pero el volumen idmapped conserva el mapeo UID/GID correcto. Para volúmenes sin idmapping, el punto de montaje se cambia de propietario para que coincida con el usuario y grupo del proceso del contenedor, mapeado al espacio de nombres de usuario del host si la reasignación del espacio de nombres de usuario está habilitada.

    Si se crea un pod en un nuevo espacio de nombres de usuario, el UID y GID en el contenedor pueden corresponder a otro UID y GID en el host.

    El sufijo :U indica a Podman que use el UID y GID correctos del host basados en el UID y GID dentro del pod, para cambiar recursivamente el propietario y el grupo del volumen de origen. El cambio de propietario recorre el sistema de archivos debajo del volumen y cambia el UID/GID de cada archivo. Si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, lo que retrasa el inicio del pod.

    Advertencia: úselo con precaución ya que esto modifica el sistema de archivos del host.

    Etiquetado de montajes de volumen

    Los sistemas de etiquetado como SELinux requieren que se apliquen etiquetas adecuadas al contenido del volumen montado en un pod. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del pod utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el sistema operativo.

    Para cambiar una etiqueta en el contexto del pod, agregue uno de los dos sufijos :z o :Z al montaje del volumen. Estos sufijos indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le dice a Podman que dos o más pods comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban contenido. La opción Z le dice a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el pod actual puede usar un volumen privado.

    Nota: todos los contenedores dentro de un pod comparten la misma etiqueta SELinux. Esto significa que todos los contenedores dentro de dicho pod pueden leer/escribir volúmenes compartidos en el contenedor creados con :Z en cualquiera de los contenedores. Volver a etiquetar recorre el sistema de archivos debajo del volumen y cambia la etiqueta de cada archivo; si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, lo que retrasa el inicio del pod. Si el volumen se volvió a etiquetar previamente con la opción z, Podman está optimizado para no volver a etiquetar por segunda vez. Si los archivos se mueven al volumen, las etiquetas se pueden cambiar manualmente con el comando chcon -Rt container_file_t RUTA.

    Nota: No vuelva a etiquetar archivos y directorios del sistema. Volver a etiquetar contenido del sistema puede hacer que otros servicios confinados en la máquina fallen. Para estos tipos de contenedores, recomendamos deshabilitar la separación de SELinux. La opción --security-opt label=disable deshabilita la separación de SELinux para el pod. Por ejemplo, si un usuario quisiera montar su directorio de inicio completo en un pod, necesita deshabilitar la separación de SELinux.

    $ podman pod create --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

    Montajes de volumen de superposición

    La bandera :O le dice a Podman que monte el directorio del host como almacenamiento temporal usando el sistema de archivos overlay. Los procesos del pod pueden modificar el contenido dentro del punto de montaje, que se almacena en el almacenamiento del contenedor en un directorio separado. En términos de overlay, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el pod termina de ejecutarse, de manera similar a como se desmonta un punto de montaje tmpfs.

    Para usuarios avanzados, la opción overlay también admite upperdir y workdir personalizados no volátiles para el montaje overlay. Los upperdir y workdir personalizados pueden ser administrados completamente por los propios usuarios, y Podman no los elimina al finalizar el ciclo de vida. Ejemplo: :O,upperdir=/some/upper,workdir=/some/work

    Las ejecuciones posteriores del contenedor ven el contenido original del directorio de origen; cualquier cambio de ejecuciones anteriores del pod ya no existe.

    Un caso de uso del montaje overlay es compartir la caché de paquetes del host en el contenedor para acelerar las compilaciones.

    Nota: La bandera O entra en conflicto con otras opciones enumeradas anteriormente.

    El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor de infraestructura del pod. Normalmente, los contenedores pueden leer/ejecutar container_share_t y pueden leer/escribir container_file_t. Si no se pueden cambiar las etiquetas en un volumen de origen, la separación de contenedores SELinux debe deshabilitarse para que el pod o el contenedor de infraestructura funcionen.

    No modifique el directorio de origen montado en el pod con un montaje overlay, puede causar fallos inesperados. Solo modifique el directorio después de que el contenedor termine de ejecutarse.

    Propagación de montajes

    Por defecto, los volúmenes montados por enlace son privados. Eso significa que cualquier montaje realizado dentro del pod no es visible en el host y viceversa. Se puede cambiar este comportamiento especificando una propiedad de propagación de montaje de volumen. Cuando un volumen está compartido, los montajes realizados debajo de ese volumen dentro del pod son visibles en el host y viceversa. Hacer que un volumen sea slave[1] ⟨#Footnote1⟩ permite la propagación de montajes de un solo sentido: los montajes realizados en el host debajo de ese volumen son visibles dentro del contenedor, pero no al revés.

    Para controlar la propiedad de propagación de montaje de un volumen, se puede usar la bandera de propagación [r]shared, [r]slave, [r]private o [r]unbindable. La propiedad de propagación de montaje solo se puede especificar para volúmenes montados por enlace y no para volúmenes internos o volúmenes con nombre. Para que la propagación de montajes funcione, el punto de montaje de origen (el punto de montaje donde se monta el directorio de origen) debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe ser compartido. Y para volúmenes slave, el punto de montaje de origen debe ser compartido o slave. [1] ⟨#Footnote1⟩

    Para montar recursivamente un volumen y todos sus submontajes en un pod, use la opción rbind. Por defecto, se usa la opción bind y los submontajes del directorio de origen no se montan en el pod.

    Montar el volumen con una opción copy le dice a Podman que copie el contenido del directorio de destino subyacente en volúmenes internos recién creados. La copy solo ocurre en la creación inicial del volumen. El contenido no se copia cuando el volumen se utiliza posteriormente en diferentes contenedores. La opción copy se ignora en los montajes bind y no tiene ningún efecto.

    Montar volúmenes con la opción nosuid significa que los ejecutables SUID en el volumen no pueden ser utilizados por las aplicaciones para cambiar sus privilegios. Por defecto, los volúmenes se montan con nosuid.

    Montar el volumen con la opción noexec significa que no se pueden ejecutar ejecutables en el volumen dentro del pod.

    Montar el volumen con la opción nodev significa que los procesos dentro del pod no pueden usar dispositivos en el volumen. Por defecto, los volúmenes se montan con nodev

    b>.

    Si el DIRECTORIO-HOST es un punto de montaje, entonces las opciones dev, suid y exec son ignoradas por el kernel.

    Utilice df DIRECTORIO-HOST para averiguar el punto de montaje de origen, luego utilice findmnt -o TARGET,PROPAGATION directorio-montaje-origen para averiguar las propiedades de propagación del punto de montaje de origen. Si la utilidad findmnt(1) no está disponible, entonces se puede consultar la entrada de montaje para el punto de montaje de origen en /proc/self/mountinfo. Consulte los "campos opcionales" y vea si se especifican propiedades de propagación. En él, shared:N significa que el montaje está compartido, master:N significa que el montaje es esclavo, y si no hay nada, el montaje es privado. [1]

    Para cambiar las propiedades de propagación de un punto de montaje, utilice el comando mount(8). Por ejemplo, si se desea montar por enlace un directorio de origen /foo, se puede hacer mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convierte /foo en un punto de montaje compartido. Alternativamente, se pueden cambiar directamente las propiedades de propagación del montaje de origen. Supongamos que / es el montaje de origen para /foo, entonces utilice mount --make-shared / para convertir / en un montaje compartido.

    Montaje idmapped

    Si se especifica idmap, cree un montaje idmapped en el espacio de nombres de usuario de destino en el contenedor. La opción idmap soporta un mapeo personalizado que puede ser diferente del espacio de nombres de usuario utilizado por el contenedor. El mapeo se puede especificar después de la opción idmap como: idmap=uids=0-1-10#10-11-10;gids=0-100-10. Para cada triplete, el primer valor es el inicio de los ID del sistema de archivos subyacente que se mapean al segundo valor en el host. La longitud de este mapeo se da en el tercer valor. Múltiples rangos se separan con #.

    --volumes-from=CONTAINER[:OPTIONS]

    Monta volúmenes del contenedor(es) especificado(s). Se utiliza para compartir volúmenes entre contenedores y pods. Las opciones son una lista separada por comas con los siguientes elementos disponibles:

    • rw|ro
    • z

    Monta volúmenes ya montados de un contenedor de origen en otro pod. CONTENEDOR puede ser un nombre o un ID. Para compartir un volumen, utilice la opción --volumes-from al ejecutar el contenedor de destino. Los volúmenes se pueden compartir incluso si el contenedor de origen no se está ejecutando.

    Por defecto, Podman monta los volúmenes en el mismo modo (lectura-escritura o solo lectura) en que están montados en el contenedor de origen. Esto se puede cambiar añadiendo una opción ro o rw.

    Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un pod. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el SO.

    Para cambiar una etiqueta en el contexto del pod, añada z al montaje del volumen. Este sufijo indica a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le dice a Podman que dos entidades comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban el contenido.

    Si la ubicación del volumen del contenedor de origen se solapa con datos que residen en un pod de destino, el volumen oculta esos datos en el destino.

    Crear un pod sin contenedor infra.

    $ podman pod create --infra=false

    Crear un pod con nombre y comando de contenedor infra para ejecutar.

    $ podman pod create --infra-command /top toppod

    Crear un pod con puertos publicados en el host.

    $ podman pod create --publish 8443:443

    Crear un pod con la configuración de red especificada.

    $ podman pod create --network slirp4netns:outbound_addr=127.0.0.1,allow_host_loopback=true

    Crear un pod con la red especificada.

    $ podman pod create --network pasta

    Crear un pod en dos redes.

    $ podman pod create --network net1:ip=10.89.1.5 --network net2:ip=10.89.10.10

    Crear un pod con límites compartidos de CPU y memoria para todos los contenedores.

    $ podman pod create --cpus=2 --memory=512m mypod

    Crear un pod con montajes de volumen compartidos accesibles para todos los contenedores.

    $ podman pod create --volume /host/path:/container/path:Z mypod

    Crear un pod con límites de recursos y montajes de volumen compartidos para todos los contenedores.

    $ podman pod create --volume /data:/data:Z --volume /config:/etc/config:ro --cpus=1.5 --memory=1g --cpu-shares=512 mypod

    Crear un pod con acceso compartido a dispositivos y límites de recursos.

    $ podman pod create --device /dev/sda:/dev/sda:rw --cpus=4 --memory=2g --blkio-weight=500 mypod

    Crear un pod con límites de conjunto de CPU compartidos y volúmenes de otro contenedor que se compartirán con todos los contenedores del pod.

    $ podman pod create --cpuset-cpus=0,2 --volumes-from=source-container --memory=1g mypod

    Crear un pod con recursos compartidos y añadirle contenedores.

    $ podman pod create --cpus=2 --memory=1g --volume /data:/data:Z mypod
$ podman create --pod mypod nginx
$ podman create --pod mypod redis
