NOMBRE

podman-create - Crea un nuevo contenedor

SINOPSIS

podman create [opciones] imagen [comando [arg ...]]

podman container create [opciones] imagen [comando [arg ...]]

DESCRIPCIÓN

Crea una capa de contenedor escribible sobre la imagen especificada y la prepara para ejecutar el comando especificado. A continuación, se imprime el ID del contenedor en la salida estándar. Esto es similar a podman run -d, excepto que el contenedor nunca se inicia. Usa el comando podman start contenedor para iniciar el contenedor en cualquier momento.

El estado inicial del contenedor creado con podman create es 'created' (creado).

Las configuraciones por defecto para las banderas se definen en containers.conf. La mayoría de las configuraciones para conexiones remotas utilizan el containers.conf del servidor, excepto cuando se documenta en las páginas man.

IMAGEN

La imagen se especifica utilizando el formato transporte:ruta. Si no se especifica ningún transporte, el transporte docker (registro de contenedores) se usa por defecto. Para Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), docker es el único transporte permitido.

dir:ruta
Un directorio local existente ruta que almacena el manifiesto, los archivos tar de capas y las firmas como archivos individuales. Este es un formato no estandarizado, útil principalmente para depuración o inspección de contenedores no invasiva.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman create dir:/tmp/fedora echo hello

docker://referencia-docker (Por defecto)
Una referencia de imagen almacenada en un registro de imágenes de contenedores remoto. Por ejemplo: "quay.io/podman/stable:latest". La referencia puede incluir una ruta a un registro específico; si no lo hace, se consultan los registros listados en registries.conf para encontrar una imagen coincidente. Por defecto, se utilizan las credenciales de podman login (almacenadas en $XDG_RUNTIME_DIR/containers/auth.json por defecto) para autenticarse; de lo contrario, recurre a las credenciales en $HOME/.docker/config.json.

$ podman create registry.fedoraproject.org/fedora:latest echo hello

docker-archive:ruta[:referencia-docker] Una imagen almacenada en el archivo con formato docker save. referencia-docker solo se usa al crear dicho archivo y no debe contener un digest.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman create docker-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

docker-daemon:referencia-docker
Una imagen en formato referencia-docker almacenada en el almacenamiento interno del daemon de Docker. La referencia-docker también puede ser un ID de imagen (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman create docker-daemon:docker.io/library/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

oci-archive:ruta:etiqueta
Una imagen en un directorio que cumple con la "Open Container Image Layout Specification" en la ruta especificada y especificada con una etiqueta.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman create oci-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

OPCIONES

--add-host=nombre-host[;nombre-host[;...]]:ip

Añade un mapeo personalizado de nombre de host a IP al archivo /etc/hosts del contenedor.

La opción toma uno o varios nombres de host separados por punto y coma para ser mapeados a una única dirección IPv4 o IPv6, separados por dos puntos. También se puede utilizar para sobrescribir las direcciones IP de los nombres de host que Podman añade a /etc/hosts por defecto (ver también las opciones --name y --hostname). Esta opción se puede especificar varias veces para añadir mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede dar el indicador especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de la configuración de red, por lo que no hay garantía de que Podman pueda determinar automáticamente la dirección host-gateway, lo que hará que Podman falle con un mensaje de error. Puede sobrescribir esta dirección IP utilizando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para añadir automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitarlo dando la opción --no-hosts o configurando host_containers_internal_ip="none" en containers.conf. Si no se configuró una dirección host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se ejecuta en una máquina virtual utilizando podman machine (lo que incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven en su lugar mediante el resolvedor DNS de gvproxy.

Podman utilizará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente utilizando la configuración base_hosts_file en containers.conf.

--annotation=clave=valor

Añade una anotación al contenedor. Esta opción se puede establecer varias veces.

--arch=ARQUITECTURA

Sobrescribe la arquitectura, por defecto la del host, de la imagen que se va a descargar. Por ejemplo, arm. A menos que se sobrescriba, las búsquedas posteriores de la misma imagen en el almacenamiento local coinciden con esta arquitectura, independientemente del host.

--attach, -a=stdin | stdout | stderr

Adjunta a STDIN, STDOUT o STDERR.

En modo de primer plano (por defecto cuando no se especifica -d), podman run puede iniciar el proceso en el contenedor y adjuntar la consola a la entrada, salida y error estándar del proceso. Incluso puede simular ser una TTY (que es lo que la mayoría de los ejecutables de línea de comandos esperan) y pasar señales. La opción -a se puede establecer para cada uno de stdin, stdout y stderr.

--authfile=ruta

Ruta del archivo de autenticación. Por defecto es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo es creado por podman login. Si el estado de autorización no se encuentra allí, se consulta $HOME/.docker/config.json, que se establece usando docker login.

Nota: También existe la opción de sobrescribir la ruta por defecto del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

--blkio-weight=peso

Peso relativo de I/O de bloque. El peso es un valor entre 10 y 1000.

Esta opción no es compatible con sistemas sin root cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo del dispositivo de I/O de bloque.

Añade capacidades de Linux.

--cert-dir=ruta

Utiliza certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. (Por defecto: /etc/containers/certs.d) Para más detalles, consulta containers-certs.d(5). (Esta opción no está disponible con el cliente Podman remoto, incluyendo máquinas Mac y Windows (excluyendo WSL2))

--cgroup-conf=CLAVE=VALOR

Al ejecutarse en cgroup v2, especifica el archivo cgroup al que escribir y su valor. Por ejemplo, --cgroup-conf=memory.high=1073741824 establece el límite de memory.high en 1 GB.

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se crea el cgroup para el contenedor. Si la ruta no es absoluta, se considera relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen ya.

--cgroupns=modo

Establece el modo del namespace de cgroup para el contenedor.

  • host: utiliza el namespace de cgroup del host dentro del contenedor.
  • container:id: únete al namespace del contenedor especificado.
  • private: crea un nuevo namespace de cgroup.
  • ns:ruta: únete al namespace en la ruta especificada.

Si el host utiliza cgroups v1, el valor por defecto se establece en host. En cgroups v2, el valor por defecto es private.

--cgroups=cómo

Determina si el contenedor crea cgroups.

El valor por defecto es enabled (habilitado).

La opción enabled crea un nuevo cgroup bajo el cgroup-parent. La opción disabled (deshabilitado) fuerza al contenedor a no crear cgroups, y por lo tanto entra en conflicto con las opciones de cgroup (--cgroupns y --cgroup-parent). La opción no-conmon deshabilita un nuevo cgroup solo para el proceso conmon. La opción split divide el cgroup actual en dos sub-cgroups: uno para conmon y otro para la carga útil del contenedor. No es posible establecer --cgroup-parent con split.

--chrootdirs=ruta

Ruta a un directorio dentro del contenedor que se trata como un directorio chroot. Cualquier archivo gestionado por Podman (por ejemplo, /etc/resolv.conf, /etc/hosts, /etc/hostname) que se monte en el directorio raíz también se montará en esa ubicación. Múltiples directorios se separan con una coma.

--cidfile=archivo

Escribe el ID del contenedor en archivo. El archivo se elimina junto con el contenedor, excepto cuando se utiliza con podman --remote run en contenedores desvinculados.

--conmon-pidfile=archivo

Escribe el PID del proceso conmon en un archivo. Como conmon se ejecuta en un proceso separado de Podman, esto es necesario cuando se utiliza systemd para reiniciar contenedores de Podman. (Esta opción no está disponible con el cliente Podman remoto, incluyendo máquinas Mac y Windows (excluyendo WSL2))

--cpu-period=límite

Establece el período de CPU para el Completely Fair Scheduler (CFS), que es una duración en microsegundos. Una vez que la cuota de CPU del contenedor se agota, no se programará para ejecutarse hasta que finalice el período actual. El valor por defecto es de 100000 microsegundos.

En algunos sistemas, no se permite cambiar los límites de recursos para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpu-quota=límite

Limita la cuota del Completely Fair Scheduler (CFS) de CPU.

Limita el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso de CPU completo. El límite es un número en microsegundos. Si se proporciona un número, el contenedor tiene permitido utilizar esa cantidad de tiempo de CPU hasta que finalice el período de CPU (controlable mediante --cpu-period).

En algunos sistemas, no se permite cambiar los límites de recursos para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpu-rt-period=microsegundos

Limita el período de tiempo real de CPU en microsegundos.

Limita el uso de CPU en tiempo real del contenedor. Esta opción le indica al kernel que restrinja el uso de CPU en tiempo real del contenedor al período especificado.

Esta opción solo es compatible con sistemas con root en cgroups V1.

--cpu-rt-runtime=microsegundos

Limita el tiempo de ejecución en tiempo real de CPU en microsegundos.

Limita el uso de CPU en tiempo real de los contenedores. Esta opción le indica al kernel que limite la cantidad de tiempo que las tareas en tiempo real pueden consumir en un período de CPU dado. Ej: un período de 1.000.000us y un tiempo de ejecución de 950.000us significa que este contenedor puede consumir el 95% de la CPU disponible y dejar el 5% restante para tareas de prioridad normal.

La suma de todos los tiempos de ejecución entre contenedores no puede exceder la cantidad asignada al cgroup padre.

Esta opción solo es compatible con sistemas con root en cgroups V1.

--cpu-shares, -c=shares

Porciones de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de las porciones de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso por defecto es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden utilizar el tiempo de CPU sobrante. La cantidad real de tiempo de CPU varía dependiendo del número de contenedores en ejecución en el sistema.

Por ejemplo, considera tres contenedores, uno tiene una cuota de CPU de 1024 y otros dos tienen una configuración de cuota de CPU de 512. Cuando los procesos en los tres contenedores intentan utilizar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con una cuota de CPU de 1024, el primer contenedor solo recibe el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las porciones de tiempo de CPU se distribuyen entre todos los núcleos de CPU. Incluso si un contenedor se limita a menos del 100% del tiempo de CPU, puede utilizar el 100% de cada núcleo de CPU individual.

Por ejemplo, considera un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de porciones de CPU:

PID contenedor CPU Porción de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, no se permite cambiar los límites de recursos para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpus=número

Número de CPUs. El valor por defecto es 0.0, lo que significa sin límite. Esto es un atajo para --cpu-period y --cpu-quota, por lo tanto la opción no se puede especificar con --cpu-period o --cpu-quota.

En algunos sistemas, no se permite cambiar los límites de CPU para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

CPUs en las cuales permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de estos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, no se permite cambiar los límites de recursos para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los cuales permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), usa --cpuset-mems=0,1 y los procesos en el contenedor solo usarán memoria de los dos primeros nodos de memoria.

En algunos sistemas, no se permite cambiar los límites de recursos para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--creds=[user[:password]]

Username and password for authenticating to a container registry. If only the username is specified, a prompt for the password appears. If neither is specified, Podman attempts to use credentials from containers-auth.json(5) or the container registry, if required. If one or both values are not supplied, a command line prompt appears and the value can be entered. The password is entered without echo.

Note that the specified credentials are only used to authenticate against target registries. They are not used for mirrors or when the registry gets rewritten (see containers-registries.conf(5)); to authenticate against those consider using a containers-auth.json(5) file.

--decryption-key=key[:passphrase]

The [key[:passphrase]] to be used for decryption of images. Key can point to keys and/or certificates. Decryption is tried with all keys. If the key is protected by a passphrase, it is required to be passed in the argument and omitted otherwise.

--device=host-device[:container-device][:permissions]

Add a host device to the container. Optional permissions parameter can be used to specify device permissions by combining r for read, w for write, and m for mknod(2).

Example: --device=/dev/sdc:/dev/xvdc:rwm.

Note: if host-device is a symbolic link then it is resolved first. The container only stores the major and minor numbers of the host device.

Podman may load kernel modules required for using the specified device. The devices that Podman loads modules for when necessary are: /dev/fuse.

In rootless mode, the new device is bind mounted in the container from the host rather than Podman creating it within the container space. Because the bind mount retains its SELinux label on SELinux systems, the container can get permission denied when accessing the mounted device. Modify SELinux settings to allow containers to use all device labels via the following command:

$ sudo setsebool -P container_use_devices=true

Note: if the user only has access rights via a group, accessing the device from inside a rootless container fails. Use the --group-add keep-groups flag to pass the user's supplementary group access into the container.

--device-cgroup-rule="type major:minor mode"

Add a rule to the cgroup allowed devices list. The rule is expected to be in the format specified in the Linux kernel documentation admin-guide/cgroup-v1/devices: - type: a (all), c (char), or b (block); - major and minor: either a number, or * for all; - mode: a composition of r (read), w (write), and m (mknod(2)).

--disable-content-trust

This is a Docker-specific option to disable image verification to a container registry and is not supported by Podman. This option is a NOOP and provided solely for scripting compatibility.

--dns=ipaddr

Set custom DNS servers.

This option can be used to override the DNS configuration passed to the container. Typically this is necessary when the host DNS configuration is invalid for the container (e.g., 127.0.0.1). When this is the case the --dns flag is necessary for every run.

The special value none can be specified to disable creation of /etc/resolv.conf in the container by Podman. The /etc/resolv.conf file in the image is then used without changes.

Note that ipaddr may be added directly to the container's /etc/resolv.conf. This is not guaranteed though. For example, passing a custom network whose dns_enabled is set to true to --network will result in /etc/resolv.conf only referring to the aardvark-dns server. aardvark-dns then forwards to the supplied ipaddr for all non-container name queries.

This option cannot be combined with --network that is set to none or container:id.

--dns-option=option

Set custom DNS options. Invalid if using --dns-option with --network that is set to none or container:id.

--dns-search=domain

Set custom DNS search domains. Invalid if using --dns-search with --network that is set to none or container:id. Use --dns-search=. to remove the search domain.

--entrypoint="command" | '["command", arg1 , ...]'

Override the default ENTRYPOINT from the image.

The ENTRYPOINT of an image is similar to a COMMAND because it specifies what executable to run when the container starts, but it is (purposely) more difficult to override. The ENTRYPOINT gives a container its default nature or behavior. When the ENTRYPOINT is set, the container runs as if it were that binary, complete with default options. More options can be passed in via the COMMAND. But, if a user wants to run something else inside the container, the --entrypoint option allows a new ENTRYPOINT to be specified.

Specify multi option commands in the form of a JSON string.

--env, -e=env

Set environment variables.

This option allows arbitrary environment variables that are available for the process to be launched inside of the container. If an environment variable is specified without a value, Podman checks the host environment for a value and set the variable only if it is set on the host. As a special case, if an environment variable ending in * is specified without a value, Podman searches the host environment for variables starting with the prefix and adds those variables to the container.

See ⟨#environment⟩ note below for precedence and examples.

--env-file=file

Read in a line-delimited file of environment variables.

See ⟨#environment⟩ note below for precedence and examples.

--env-host

Use host environment inside of the container. See Environment note below for precedence. (This option is not available with the remote Podman client, including Mac and Windows (excluding WSL2) machines)

--env-merge=env

Preprocess default environment variables for the containers. For example if image contains environment variable hello=world user can preprocess it using --env-merge hello=${hello}-some so new value is hello=world-some.

Please note that if the environment variable hello is not present in the image, then it'll be replaced by an empty string and so using --env-merge hello=${hello}-some would result in the new value of hello=-some, notice the leading - delimiter.

--expose=port[/protocol]

Expose a port or a range of ports (e.g. --expose=3300-3310). The protocol can be tcp, udp or sctp and if not given tcp is assumed. This option matches the EXPOSE instruction for image builds and has no effect on the actual networking rules unless -P/--publish-all is used to forward to all exposed ports from random host ports. To forward specific ports from the host into the container use the -p/--publish option instead.

Establece o modifica un comando de verificación de estado de salud para un contenedor. El comando es un comando que se ejecutará dentro del contenedor y que determina el estado de salud del contenedor. Se pueden pasar varias opciones en forma de arreglo JSON; de lo contrario, el comando se interpreta como un argumento para /bin/sh -c.

Establece un intervalo para las verificaciones de estado de salud. Un intervalo de disable no configura ningún temporizador automático. El valor predeterminado es 30s.

--health-log-destination=ruta_directorio

Establece el destino del registro de HealthCheck. Ruta de directorio, local o events_logger (estado del contenedor local) (Predeterminado: local)

  • local: (predeterminado) Los registros de HealthCheck se almacenan en contenedores superpuestos. (Por ejemplo: $runroot/healthcheck.log)
  • directory: crea un archivo de registro llamado <ID_contenedor>-healthcheck.log con los registros de HealthCheck en el directorio especificado.
  • events_logger: El registro se escribirá con el mecanismo de registro establecido por events_logger. También guarda el registro en un directorio predeterminado, para optimizar el rendimiento en un sistema con un gran número de registros.

--health-max-log-count=número de registros almacenados

--health-on-failure=acción

Acción a tomar una vez que el contenedor transiciona a un estado no saludable. El valor predeterminado es none.

  • none: No realizar ninguna acción.
  • kill: Matar el contenedor.
  • restart: Reiniciar el contenedor. No combine la acción de restart con la bandera --restart. Al ejecutarse dentro de una unidad systemd, considere usar la acción kill o stop en su lugar para aprovechar la política de reinicio de systemd.
  • stop: Detener el contenedor.

--health-retries=reintentos

El número de reintentos permitidos antes de que una verificación de estado de salud se considere no saludable. El valor predeterminado es 3.

Nota: Este parámetro puede sobrescribir la configuración de verificación de estado de salud de la imagen.

--health-start-period=período

El tiempo de inicialización necesario para que un contenedor se arranque. El valor puede expresarse en formato de tiempo como 2m3s. El valor predeterminado es 0s.

Nota: El comando de verificación de estado de salud se ejecuta tan pronto como se inicia un contenedor; si la verificación de estado de salud tiene éxito, el estado de salud del contenedor se actualizará a healthy. Sin embargo, si la verificación de estado de salud falla, el estado de salud permanecerá como starting hasta que la verificación de estado de salud tenga éxito o hasta que expire el tiempo de --health-start-period. Si el comando de verificación de estado de salud falla después de que expire el tiempo de --health-start-period, el estado de salud se actualizará a unhealthy. El comando de verificación de estado de salud se ejecuta periódicamente según el valor de --health-interval.

Nota: Este parámetro sobrescribirá la configuración relacionada de verificación de estado de salud de la imagen.

--health-startup-cmd="comando" | '["comando", arg1 , ...]'

Establece un comando de verificación de estado de salud de inicio para un contenedor. Este comando se ejecuta dentro del contenedor y se utiliza para controlar la verificación de estado de salud regular. Cuando el comando de inicio tiene éxito, comienza la verificación de estado de salud regular y la verificación de estado de salud de inicio cesa. Opcionalmente, si el comando falla durante un número determinado de intentos, el contenedor se reinicia. Se puede utilizar una verificación de estado de salud de inicio para garantizar que los contenedores con un período de inicio prolongado no se marquen como no saludables hasta que se inicien por completo. Las verificaciones de estado de salud de inicio solo se pueden usar cuando también se establece una verificación de estado de salud regular (de la imagen del contenedor o de la opción --health-cmd).

--health-startup-interval=intervalo

Establece un intervalo para la verificación de estado de salud de inicio. Un intervalo de disable no configura ningún temporizador automático. El valor predeterminado es 30s.

--health-startup-retries=reintentos

El número de intentos permitidos antes de que la verificación de estado de salud de inicio reinicie el contenedor. Si se establece en 0, el contenedor nunca se reinicia. El valor predeterminado es 0.

--health-startup-success=reintentos

El número de ejecuciones exitosas requeridas antes de que la verificación de estado de salud de inicio sea exitosa y comience la verificación de estado de salud regular. Un valor de 0 significa que cualquier éxito inicia la verificación de estado de salud regular.

--health-startup-timeout=tiempo_de_espera

El tiempo máximo que tiene el comando de verificación de estado de salud de inicio para completarse antes de que se marque como fallido. El valor puede expresarse en formato de tiempo como 2m3s. El valor predeterminado es 30s.

--health-timeout=tiempo_de_espera

El tiempo máximo permitido para completar la verificación de estado de salud antes de que un intervalo se considere fallido. Al igual que start-period, el valor puede expresarse en formato de tiempo como 1m22s. El valor predeterminado es 30s.

Nota: Un tiempo de espera marca la verificación de estado de salud como fallida. Si el comando de verificación de estado de salud en sí mismo se ejecuta durante más tiempo que el tiempo_de_espera especificado, se le enviará una señal SIGKILL.

Nota: Este parámetro sobrescribirá la configuración relacionada de verificación de estado de salud de la imagen.

Por lo tanto, siempre establezca el valor por debajo de --memory, de lo contrario, el límite duro tiene prioridad. Por defecto, la reserva de memoria es la misma que el límite de memoria.

Esta opción no se admite en sistemas rootless cgroups V1.

-m (--memory). Por defecto, se establece en el doble del valor de --memory.

Establezca el número en -1 para habilitar el swap ilimitado.

Esta opción no se admite en sistemas rootless cgroups V1.

--memory-swappiness=número

Ajusta el comportamiento de intercambio de memoria de un contenedor. Acepta un entero entre 0 y 100.

--mount=tipo=TIPO,OPCIÓN-ESPECÍFICA-DE-TIPO[,...]

Adjunta un montaje del sistema de archivos al contenedor.

Los TIPO de montaje admitidos actualmente son artifact, bind, devpts, glob, image, ramfs, tmpfs y volume.

Opciones comunes a todos los tipos de montaje:

  • src, source: especificación de origen del montaje para bind, glob y volume. Obligatorio para artifact, bind, glob, image y volume.
  • dst, dest, destination, target: especificación de destino del montaje.

Cuando se especifican globos de origen sin el directorio de destino, los archivos y directorios se montan con su ruta completa dentro del contenedor. Cuando se especifica el destino, los archivos y directorios que coinciden con el globo en el nombre base del archivo en el directorio de destino se montan. La opción type=glob,src=/foo*,destination=/tmp/bar indica a los motores de contenedores que monten los archivos del host que coincidan con /foo* en el directorio /tmp/bar/ del contenedor.

Opciones específicas para type=artifact:

  • digest: Si el origen del artefacto contiene múltiples blobs, se puede especificar un digest para montar solo el blob específico con el digest.
  • title: Si el origen del artefacto contiene múltiples blobs, se puede establecer un título que se compara con la anotación org.opencontainers.image.title.
  • name: Esto se puede usar para sobrescribir el nombre de archivo que utilizamos dentro del contenedor para montar. En un artefacto de blob único, el nombre se usa tal cual si dst es un directorio y, de lo contrario, se ignora. Con un artefacto de múltiples blobs, el nombre se usará con un sufijo de índice <nombre>-x donde x es el índice de capa en el artefacto comenzando desde 0.

El argumento src contiene el nombre del artefacto, que ya debe existir localmente. El argumento dst contiene la ruta de destino, si la ruta en el contenedor es un directorio, el título del blob (anotación org.opencontainers.image.title) se usará como nombre de archivo y se unirá a la ruta.

Si la anotación no existe, se utilizará el digest como nombre de archivo. Esto da como resultado que todos los blobs del artefacto se monten en el contenedor en la ruta especificada.

Sin embargo, si la ruta dst es un archivo existente en el contenedor, el blob se montará directamente sobre él. Esto solo funciona cuando el artefacto contiene un solo blob o cuando se especifican digest o title.

Si la ruta dst no existe previamente en el contenedor, entonces si el artefacto contiene un solo blob, se comporta como el caso de archivo existente y se monta directamente en esa ruta. Si el artefacto tiene más de un blob, funciona como el caso de directorio existente y monta cada blob como archivo dentro de la ruta dst.

Opciones específicas para type=volume:

  • ro, readonly: true o false (predeterminado si no se especifica: false).
  • U, chown: true o false (predeterminado si no se especifica: false). Cambiar recursivamente el propietario y el grupo del volumen de origen según el UID y GID del contenedor.
  • subpath: Montar solo una subruta específica dentro del volumen, en lugar del volumen completo.
  • idmap: Si se especifica, crear un montaje con mapeo de ID al espacio de nombres de usuario de destino en el contenedor. La opción idmap solo es compatible con Podman en modo rootful. El kernel de Linux no permite el uso de sistemas de archivos con mapeo de ID para usuarios no privilegiados. La opción idmap admite un mapeo personalizado que puede ser diferente del espacio de nombres de usuario utilizado por el contenedor. El mapeo se puede especificar después de la opción idmap, por ejemplo: idmap=uids=0-1-10#10-11-10;gids=0-100-10. Para cada tripleta, el primer valor es el inicio de los ID del sistema de archivos subyacente que se mapean al segundo valor en el host. La longitud de este mapeo se indica en el tercer valor. Múltiples rangos se separan con #. Si el mapeo especificado se antepone con un '@', el mapeo se considera relativo al espacio de nombres de usuario del contenedor. El ID del host para el mapeo se cambia para tener en cuenta la posición relativa del usuario del contenedor en el espacio de nombres de usuario del contenedor.

Opciones específicas para type=image:

  • rw, readwrite: true o false (predeterminado si no se especifica: false).
  • subpath: Montar solo una ruta específica dentro de la imagen, en lugar de la imagen completa.

Opciones específicas para bind y glob:

  • ro, readonly: true o false (predeterminado si no se especifica: false).
  • bind-propagation: shared, slave, private, unbindable, rshared, rslave, runbindable, o rprivate (predeterminado).[1] ⟨#Footnote1⟩ Ver también mount(2).
  • bind-nonrecursive: no configurar un montaje bind recursivo. Por defecto es recursivo.
  • relabel: shared, private.
  • idmap: true o false (predeterminado si no se especifica: false). Si es true, crear un montaje con mapeo de ID al espacio de nombres de usuario de destino en el contenedor. La opción idmap solo es compatible con Podman en modo rootful.
  • U, chown: true o false (predeterminado si no se especifica: false). Cambiar recursivamente el propietario y el grupo del volumen de origen según el UID y GID del contenedor.
  • no-dereference: no resolver enlaces simbólicos, sino copiar el origen del enlace al destino del montaje.

Opciones específicas para type=tmpfs y ramfs:

  • ro, readonly: true o false (predeterminado si no se especifica: false).
  • tmpfs-size: Tamaño del montaje tmpfs/ramfs, en bytes. Ilimitado por defecto en Linux.
  • tmpfs-mode: Modo de archivo octal de tmpfs/ramfs (por ejemplo, 700 o 0700).
  • tmpcopyup: Habilitar la copia desde el directorio de la imagen en la misma ubicación a tmpfs/ramfs. Se usa por defecto.
  • noatime: Deshabilitar la actualización de los tiempos de acceso a los archivos cuando se lee el archivo.
  • notmpcopyup: Deshabilitar la copia de archivos de la imagen a tmpfs/ramfs.
  • U, chown: true o false (predeterminado si no se especifica: false). Cambiar recursivamente el propietario y el grupo del volumen de origen según el UID y GID del contenedor.

Opciones específicas para type=devpts:

  • uid: UID numérico del propietario del archivo (predeterminado: 0).
  • gid: GID numérico del propietario del archivo (predeterminado: 0).
  • mode: Máscara de permisos octal para el archivo (predeterminado: 600).
  • max: número máximo de PTY (predeterminado: 1048576).

Ejemplos:

  • type=bind,source=/path/on/host,destination=/path/in/container
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared,U=true
  • type=devpts,destination=/dev/pts
  • type=glob,src=/usr/lib/libfoo*,destination=/usr/lib,ro=true
  • type=image,source=fedora,destination=/fedora-image,rw=true
  • type=ramfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,destination=/path/in/container,noswap
  • type=artifact,src=quay.io/libpod/testartifact:20250206-single,dst=/data
  • type=artifact,src=quay.io/libpod/testartifact:20250206-multi,dst=/data,title=test1
  • type=volume,src=test_vol,dst=/data,subpath=/code/docs

--publish, -p

Publish container's TCP or UDP ports to the host. The format is [ip[:host_port[:container_port]]|container_port[/protocol]]. If container_port is not specified, the port from the container is randomly assigned a port on the host. If host_port is not specified, it defaults to container_port. If ip is not specified, the port is bound on all IPs on the host. If protocol is not specified, it defaults to tcp.

A container port can be published multiple times if they use different protocols (e.g., TCP and UDP). Ports in the range must match the number of host ports in the range.

If the host IP is set to 0.0.0.0 or not set at all, the port is bound on all IPs on the host.

By default, Podman publishes TCP ports. To publish a UDP port instead, give udp as the protocol. To publish both TCP and UDP ports, set --publish twice, with tcp and udp as protocols respectively. Rootful containers can also publish ports using the sctp protocol.

The host port does not have to be specified (e.g. podman run -p 127.0.0.1::80). If it is not, the container port is randomly assigned a port on the host.

Use podman port to see the actual mapping: podman port $CONTAINER $CONTAINERPORT.

Port publishing is only supported for containers utilizing their own network namespace through bridge networks, or the pasta and slirp4netns network modes.

Note: If a container runs within a pod, it is not necessary to publish the port for the containers in the pod. The port must only be published by the pod itself. Pod network stacks act like the network stack on the host - when there are a variety of containers in the pod, and programs in the container, all sharing a single interface and IP address, and associated ports. If one container binds to a port, no other container can use that port within the pod while it is in use. Containers in the pod can also communicate over localhost by having one container bind to localhost in the pod, and another connect to that port.

--publish-all, -P

Publish all exposed ports to random ports on the host interfaces. The default is false.

When set to true, publish all exposed ports to the host interfaces. If the operator uses -P (or -p) then Podman makes the exposed port accessible on the host and the ports are available to any client that can reach the host.

When using this option, Podman binds any exposed port to a random port on the host within an ephemeral port range defined by /proc/sys/net/ipv4/ip_local_port_range. To find the mapping between the host ports and the exposed ports, use podman port.

The :O flag tells Podman to mount the directory from the rootfs path as storage using the overlay file system. --secret=secreto[,opt=opt ...]

Da al contenedor acceso a un secreto. Se puede especificar varias veces.

Un secreto es un bloque de datos sensibles que un contenedor necesita en tiempo de ejecución pero que no se almacena en la imagen ni en el control de versiones, como nombres de usuario y contraseñas, certificados y claves TLS, claves SSH u otras cadenas genéricas o contenido binario importantes (hasta 512 kB de tamaño).

Cuando los secretos se especifican como tipo mount, los secretos se copian y montan en el contenedor cuando se crea un contenedor. Cuando los secretos se especifican como tipo env, el secreto se establece como una variable de entorno dentro del contenedor. Los secretos se escriben en el contenedor en el momento de la creación del contenedor, y la modificación del secreto mediante comandos podman secret después de que se crea el contenedor afecta al secreto dentro del contenedor.

Los secretos y su almacenamiento se gestionan mediante el comando podman secret.

Opciones de secreto

  • type=mount|env : Cómo se expone el secreto al contenedor.
    mount monta el secreto en el contenedor como un archivo.
    env expone el secreto como una variable de entorno.
    Por defecto es mount.
  • target=objetivo : Destino del secreto.
    Para secretos montados, esta es la ruta al secreto dentro del contenedor.
    Si se proporciona una ruta completa, el secreto se monta en esa ubicación.
    De lo contrario, el secreto se monta en
    /run/secrets/objetivo para contenedores Linux o
    /var/run/secrets/objetivo para contenedores FreeBSD.
    Si no se establece el objetivo, el secreto se monta en /run/secrets/nombredelsecreto por defecto.
    Para secretos de entorno, esta es la clave de la variable de entorno. Por defecto es nombredelsecreto.
  • uid=0 : UID del secreto. Por defecto es 0. Solo tipo de montaje de secreto.
  • gid=0 : GID del secreto. Por defecto es 0. Solo tipo de montaje de secreto.
  • mode=0 : Modo del secreto. Por defecto es 0444. Solo tipo de montaje de secreto.

Ejemplos

Montar en /my/location/mysecret con UID 1:

--secret mysecret,target=/my/location/mysecret,uid=1

Montar en /run/secrets/customtarget con modo 0777:

--secret mysecret,target=customtarget,mode=0777

Crear una variable de entorno secreta llamada ENVSEC:

--secret mysecret,type=env,target=ENVSEC

  • label=level:NIVEL: Establece el nivel de la etiqueta para los procesos del contenedor
  • label=filetype:TIPO: Establece el tipo de archivo de la etiqueta para los archivos del contenedor
  • label=disable: Desactiva la separación de etiquetas para el contenedor

Nota: La asignación de etiquetas se puede desactivar para todos los contenedores estableciendo label=false en el archivo containers.conf (/etc/containers/containers.conf o $HOME/.config/containers/containers.conf).

  • label=nested: Permite modificaciones de SELinux dentro del contenedor. Se permite a los contenedores modificar las etiquetas de SELinux en archivos y procesos, siempre que la política de SELinux lo permita. Sin nested, los contenedores ven SELinux como desactivado, incluso cuando está habilitado en el host. Se impide a los contenedores establecer cualquier etiqueta.
  • mask=/ruta/1:/ruta/2: Las rutas a enmascarar separadas por dos puntos. Una ruta enmascarada no se puede acceder dentro del contenedor.
  • no-new-privileges: Desactiva que los procesos del contenedor obtengan privilegios adicionales a través de la llamada al sistema execve(2) (por ejemplo, a través de los bits setuid o setgid, o a través de capacidades de archivo). Los programas que dependen de los bits setuid/setgid establecidos en su ejecutable para cambiar el ID de usuario o grupo ya no pueden hacerlo, y cualquier capacidad de archivo añadida al ejecutable (por ejemplo, a través de setcap) no se añade al conjunto de capacidades permitidas. Para más detalles, consulte: https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined: Desactiva el confinamiento seccomp para el contenedor.
  • seccomp=profile.json: Archivo JSON que se utilizará como filtro seccomp. Tenga en cuenta que la anotación io.podman.annotations.seccomp se establece con el valor especificado, como se muestra en podman inspect.
  • proc-opts=OPCIONES : Lista separada por comas de opciones a utilizar para el montaje de /proc. Más detalles sobre las posibles opciones de montaje se especifican en la página del manual proc(5).
  • unmask=ALL o /ruta/1:/ruta/2, o rutas expandidas por shell (/proc/*): Rutas a desenmascarar separadas por dos puntos. Si se establece en ALL, desenmascara todas las rutas que están enmascaradas o hechas de solo lectura por defecto. Las rutas enmascaradas por defecto son /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, y /sys/fs/selinux, /sys/devices/virtual/powercap. Las rutas por defecto que son de solo lectura son /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

Nota: La asignación de etiquetas se puede desactivar para todos los contenedores estableciendo label=false en el archivo containers.conf(5).

--shm-size=número[unidad]

Tamaño de /dev/shm. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes). Si la unidad se omite, el sistema utiliza bytes. Si el tamaño se omite, el valor por defecto es 64m. Cuando el tamaño es 0, no hay límite en la cantidad de memoria utilizada para IPC por el contenedor. Esta opción entra en conflicto con --ipc=host.

--shm-size-systemd=número[unidad]

Tamaño de los montajes tmpfs específicos de systemd, como /run, /run/lock, /var/log/journal y /tmp. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes). Si la unidad se omite, el sistema utiliza bytes. Si el tamaño se omite, el valor por defecto es 64m. Cuando el tamaño es 0, el uso se limita al 50% de la memoria disponible del host.

--stop-signal=señal

Señal para detener un contenedor. Por defecto es SIGTERM.

--stop-timeout=segundos

Tiempo de espera para detener un contenedor. Por defecto es 10. Las conexiones remotas utilizan el archivo local containers.conf para los valores por defecto.

--subgidname=nombre

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo con nombre en el archivo /etc/subgid. Si se ejecuta sin privilegios (rootless), el usuario necesita tener derecho a usar el mapeo. Consulte subgid(5). Esta bandera entra en conflicto con --userns y --gidmap.

--subuidname=nombre

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo con nombre en el archivo /etc/subuid. Si se ejecuta sin privilegios (rootless), el usuario necesita tener derecho a usar el mapeo. Consulte subuid(5). Esta bandera entra en conflicto con --userns y --uidmap.

--sysctl=nombre=valor

Configura parámetros del kernel con espacios de nombres en tiempo de ejecución.

Para el espacio de nombres IPC, los siguientes sysctls están permitidos:

  • kernel.msgmax
  • kernel.msgmnb
  • kernel.msgmni
  • kernel.sem
  • kernel.shmall
  • kernel.shmmax
  • kernel.shmmni
  • kernel.shm_rmid_forced
  • Sysctls que comienzan con fs.mqueue.*

Nota: si se utiliza la opción --ipc=host, los sysctls anteriores no están permitidos.

Para el espacio de nombres de red, solo los sysctls que comienzan con net.* están permitidos.

Nota: si se utiliza la opción --network=host, los sysctls anteriores no están permitidos.

--systemd=true | false | always

Ejecuta el contenedor en modo systemd. Por defecto es true.

  • true habilita el modo systemd solo cuando el comando ejecutado dentro del contenedor es systemd, /usr/sbin/init, /sbin/init o /usr/local/sbin/init.
  • false deshabilita el modo systemd.
  • always fuerza que el modo systemd esté habilitado.

Ejecutar el contenedor en modo systemd provoca los siguientes cambios:

•
Podman monta sistemas de archivos tmpfs en los siguientes directorios
  • /run
  • /run/lock
  • /tmp
  • /sys/fs/cgroup/systemd (en un sistema cgroup v1)
  • /var/lib/journal
  • Podman establece la señal de parada por defecto en SIGRTMIN+3.
  • Podman establece la variable de entorno container_uuid en el contenedor a los primeros 32 caracteres del ID del contenedor.
  • Podman no monta consolas virtuales (/dev/tty\d+) cuando se ejecuta con --privileged.
  • En cgroup v2, /sys/fs/cgroup se monta como escribible.

Esto permite que systemd se ejecute en un contenedor confinado sin ninguna modificación.

Tenga en cuenta que en sistemas SELinux, systemd intenta escribir en el sistema de archivos cgroup. Se deniega por defecto a los contenedores que escriben en el sistema de archivos cgroup. El booleano container_manage_cgroup debe estar habilitado para permitir esto en un sistema con separación SELinux.

setsebool -P container
_manage_cgroup true

Tiempo máximo que un contenedor puede ejecutarse antes de que conmon le envíe la señal de detención (kill). Por defecto, los contenedores se ejecutan hasta que finalizan o son detenidos por podman stop.

--tls-verify

Requiere HTTPS y verifica los certificados al contactar con los registros (por defecto: true). Si se establece explícitamente en true, se utiliza la verificación TLS. Crea un montaje tmpfs.

Este comando monta un tmpfs en /tmp dentro del contenedor. Las opciones de montaje admitidas son las mismas que las banderas de montaje por defecto de Linux. Si no se especifican opciones, el sistema utiliza las siguientes opciones: rw,noexec,nosuid,nodev.

--tty, -t

Asigna un pseudo-TTY. El valor por defecto es false.

Cuando se establece en true, Podman asigna un pseudo-TTY y se conecta a la entrada estándar del contenedor. Esto se puede usar, por ejemplo, para ejecutar un shell interactivo desechable.

NOTA: La bandera --tty evita la redirección de la salida estándar. Combina STDOUT y STDERR, puede insertar caracteres de control y puede colgar pipes. Esta opción solo se usa cuando se ejecuta interactivamente en una terminal. Al alimentar entrada a Podman, use solo -i, no -it.

Establece la zona horaria en el contenedor. Consulte /usr/share/zoneinfo/ para ver las zonas horarias válidas. Las conexiones remotas utilizan los valores predeterminados de local containers.conf.

--uidmap=[flags]uid_contenedor:uid_origen[:cantidad]

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo de UID proporcionado. Esta opción entra en conflicto con las opciones --userns y --subuidname. Esta opción proporciona una forma de mapear UIDs del host a UIDs del contenedor. Se puede pasar varias veces para mapear diferentes rangos.

Los valores posibles de las banderas opcionales se discuten más adelante en esta página. El valor de cantidad es opcional y se asume que es 1 si no se proporciona.

El valor de uid_origen se basa en el usuario que ejecuta el comando, ya sean usuarios con privilegios (rootful) o sin privilegios (rootless).

  • usuario con privilegios (rootful): [flags]uid_contenedor:uid_host[:cantidad]
  • usuario sin privilegios (rootless): [flags]uid_contenedor:uid_intermedio[:cantidad]

Mapeos con privilegios (Rootful)

Cuando podman create es llamado por un usuario privilegiado, la opción --uidmap funciona como un mapeo directo entre los UIDs del host y los UIDs del contenedor.

UID del host -> UID del contenedor

La cantidad especifica el número de UIDs consecutivos que se mapean. Si, por ejemplo, la cantidad es 4, el mapeo se ve así:

UID del host UID del contenedor
uid_origen uid_contenedor
uid_origen + 1 uid_contenedor + 1
uid_origen + 2 uid_contenedor + 2
uid_origen + 3 uid_contenedor + 3

Mapeos sin privilegios (Rootless)

Cuando podman create es llamado por un usuario sin privilegios (es decir, ejecutándose sin privilegios), el valor uid_origen se interpreta como un "UID intermedio". En el caso sin privilegios, los UIDs del host no se mapean directamente a los UIDs del contenedor. En cambio, el mapeo se realiza en dos pasos:

UID del host -> UID intermedio -> UID del contenedor

La opción --uidmap solo influye en el segundo paso de mapeo.

El primer paso de mapeo se deriva de Podman a partir del contenido del archivo /etc/subuid y del UID del usuario que llama a Podman.

Primer paso de mapeo:

UID del host UID intermedio
UID para el usuario de Podman 0
1er UID subordinado 1
2do UID subordinado 2
3er UID subordinado 3
nth UID subordinado n

Para poder utilizar UIDs intermedios mayores que cero, el usuario necesita tener UIDs subordinados configurados en /etc/subuid. Vea subuid(5).

El segundo paso de mapeo se configura con --uidmap.

Si, por ejemplo, la cantidad es 5, el segundo paso de mapeo se ve así:

UID intermedio UID del contenedor
uid_origen uid_contenedor
uid_origen + 1 uid_contenedor + 1
uid_origen + 2 uid_contenedor + 2
uid_origen + 3 uid_contenedor + 3
uid_origen + 4 uid_contenedor + 4

Al ejecutarse sin privilegios, Podman utiliza todos los rangos configurados en el archivo /etc/subuid.

El ID de usuario actual se mapea a UID=0 en el espacio de nombres de usuario sin privilegios. Cada rango adicional se añade secuencialmente después:

host espacio de nombres de usuario sin privilegios longitud
$UID 0 1
1 $PRIMER_RANGO_ID $PRIMERA_LONGITUD_RANGO
1+$PRIMERA_LONGITUD_RANGO $SEGUNDO_RANGO_ID $SEGUNDA_LONGITUD_RANGO

Referenciar un ID de host desde el espacio de nombres padre

Como usuario sin privilegios, el ID de host proporcionado en --uidmap o --gidmap se mapea desde el espacio de nombres intermedio generado por Podman. A veces es deseable referirse directamente al espacio de nombres del host. Es posible hacerlo manualmente, ejecutando podman unshare cat /proc/self/gid_map, encontrando el ID de host deseado en la segunda columna de la salida y obteniendo el ID intermedio correspondiente de la primera columna.

Podman puede hacer todo esto anteponiendo el ID del host en el mapeo con el símbolo @. Por ejemplo, especificando --gidmap 100000:@2000:1, Podman buscará el ID intermedio que corresponde al ID de host 2000 y mapeará el ID intermedio encontrado al ID de contenedor 100000. El ID de host proporcionado debe haber sido subordinado (de lo contrario, no se habría mapeado al espacio intermedio en primer lugar).

Si la longitud es mayor que uno, por ejemplo con --gidmap 100000:@2000:2, Podman mapeará los IDs de host 2000 y 2001 a 100000 y 100001 respectivamente, sin importar cómo esté definido el mapeo intermedio.

Extender mapeos anteriores

Algunas modificaciones de mapeo pueden ser engorrosas. Por ejemplo, un usuario comienza con un mapeo como --gidmap="0:0:65000", que necesita ser cambiado para que el ID padre 1 se mapee a un ID de contenedor 100000 en su lugar, dejando el ID de contenedor 1 sin asignar. El --gidmap correspondiente se convierte en --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

Esta notación se puede simplificar utilizando la bandera +, que se encarga de romper los mapeos anteriores eliminando cualquier asignación conflictiva con el mapeo dado. La bandera se proporciona antes del ID del contenedor de la siguiente manera: --gidmap="0:0:65000" --gidmap="+100000:1:1"

Bandera Ejemplo Descripción
+ +100000:1:1 Extender el mapeo anterior

Esta notación produce huecos en la asignación, por lo que puede ser conveniente rellenar esos huecos posteriormente: --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

Un caso de uso específico para esta bandera es en el contexto de usuarios sin privilegios. Un usuario sin privilegios puede especificar mapeos con la bandera + como en --gidmap="+100000:1:1". Podman luego "rellenará los huecos" comenzando desde cero con todos los IDs intermedios restantes. Esto es conveniente cuando un usuario quiere mapear un ID intermedio específico a un ID de contenedor, dejando que Podman mapee el resto de los IDs subordinados a su voluntad.

Pasar solo uno de --uidmap o --gidmap

Por lo general, los IDs de usuario y grupo subordinados se asignan simultáneamente, y para cualquier usuario, los IDs de usuario subordinados coinciden con los IDs de grupo subordinados. Para mayor comodidad, si solo se proporciona uno de --uidmap o --gidmap, Podman asume que el mapeo se refiere tanto a UIDs como a GIDs y aplica el mapeo proporcionado a ambos. Si solo necesita cambiar uno de los dos valores, los mapeos deben incluir las banderas u o g para especificar que solo se aplican a UIDs o GIDs y no deben copiarse.

bandera Ejemplo Descripción
u u20000:2000:1 El mapeo solo se aplica a los UIDs
g g10000:1000:1 El mapeo solo se aplica a los GIDs

Por ejemplo, dado el comando

podman create --gidmap "0:0:1000" --gidmap "g2000:2000:1"

Como no se proporciona --uidmap, el --gidmap se copia a --uidmap, dando un comando equivalente a

podman create --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

El --gidmap "g2000:2000:1" utilizó la bandera g y, por lo tanto, no se copió a --uidmap.

Mapeo sin privilegios de GIDs de host adicionales

Un usuario sin privilegios puede desear mapear un grupo de host específico que ya ha sido

--gidmap="+g CONTAINER_GID:@HOST_GID"

Subordina grupos en /etc/subgid sin especificar el resto del mapeo.

Esto se puede hacer con --gidmap "+gcontainer_gid:@host_gid"

Donde:

  • El GID del host se proporciona a través del símbolo @.
  • El mapeo de este GID no se copia a --usermap gracias a la bandera g.
  • El resto de los IDs del contenedor se mapearán comenzando desde 0 hasta n, con todos los GIDs subordinados restantes, gracias a la bandera +.

Por ejemplo, si un usuario pertenece al grupo 2000 y ese grupo está subordinado a ese usuario (con usermod --add-subgids 2000-2000 $USER), el usuario puede mapear el grupo al contenedor con: --gidmap=+g100000:@2000.

Si este mapeo se combina con la opción --group-add=keep-groups, el proceso en el contenedor pertenecerá al grupo 100000, y los archivos que pertenezcan al grupo 2000 en el host aparecerán como propiedad del grupo 100000 dentro del contenedor.

podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

No hay UIDs subordinados

Incluso si un usuario no tiene UIDs subordinados en /etc/subuid, --uidmap se puede usar para mapear el UID normal del usuario a un UID del contenedor ejecutando podman create --uidmap $container_uid:0:1 --user $container_uid ....

Pods

La opción --uidmap no se puede usar junto con la opción --pod ya que no se puede establecer un uidmap a nivel de contenedor cuando se está en un pod.

--ulimit=opción

Opciones de Ulimit. Establece los valores de ulimits dentro del contenedor.

--ulimit con un límite suave y uno duro en el formato =[:]. Por ejemplo:

$ podman run --ulimit nofile=1024:1024 --rm ubi9 ulimit -n 1024

Establezca -1 para el límite suave o duro para establecer el límite al límite máximo del proceso actual. En modo rootful, esto suele ser ilimitado.

Si nofile y nproc no están establecidos, se usará un valor predeterminado de 1048576, a menos que se anule en containers.conf(5). Sin embargo, si el valor predeterminado excede el límite duro para el usuario rootless actual, se aplicará el límite duro actual en su lugar.

Use host para copiar la configuración actual del host.

No use nproc con la bandera ulimit ya que Linux usa nproc para establecer el número máximo de procesos disponibles para un usuario, no para un contenedor.

Use la opción --pids-limit para modificar el control de cgroup para limitar el número de procesos dentro de un contenedor.

--umask=umask

Establece la umask dentro del contenedor. El valor predeterminado es 0022. Las conexiones remotas utilizan el archivo local containers.conf para los valores predeterminados.

--unsetenv=env

Anula las variables de entorno predeterminadas para el contenedor. Las variables de entorno predeterminadas incluyen variables proporcionadas nativamente por Podman, variables de entorno configuradas por la imagen y variables de entorno de containers.conf.

--unsetenv-all

Anula todas las variables de entorno predeterminadas para el contenedor. Las variables de entorno predeterminadas incluyen variables proporcionadas nativamente por Podman, variables de entorno configuradas por la imagen y variables de entorno de containers.conf.

--user, -u=usuario[:grupo]

Establece el nombre de usuario o UID utilizado y, opcionalmente, el nombre de grupo o GID para el comando especificado. Tanto usuario como grupo pueden ser simbólicos o numéricos.

Sin este argumento, el comando se ejecuta como el usuario especificado en la imagen del contenedor. A menos que se anule con un comando USER en el Containerfile o con un valor pasado a esta opción, este usuario generalmente es root por defecto.

Cuando no se utiliza un espacio de nombres de usuario, el UID y el GID utilizados dentro del contenedor y en el host coinciden. Sin embargo, cuando se utilizan espacios de nombres de usuario, el UID y el GID en el contenedor pueden corresponder a otro UID y GID en el host. En contenedores rootless, por ejemplo, siempre se utiliza un espacio de nombres de usuario, y root en el contenedor por defecto corresponde al UID y GID del usuario que invoca Podman.

--userns=modo

Establece el modo del espacio de nombres de usuario para el contenedor.

Si no se establece --userns, el valor predeterminado se determina de la siguiente manera: - Si se establece --pod, se ignora --userns y se utiliza el espacio de nombres de usuario del pod. - Si la variable de entorno PODMAN_USERNS está establecida, se utiliza su valor. - Si se especifica userns en containers.conf, se utiliza ese valor. - De lo contrario, se asume --userns=host.

--userns="" (es decir, una cadena vacía) es un alias de --userns=host.

Esta opción es incompatible con --gidmap, --uidmap, --subuidname y --subgidname.

Mapeos de claves de --userns para usuarios sin privilegios:

Clave Usuario del Host Usuario del Contenedor
auto $UID nil (El UID del Usuario del Host no se mapea al contenedor).
host $UID 0 (Cuenta de Usuario Predeterminada mapeada al usuario root en el contenedor).
keep-id $UID $UID (Mapea la cuenta de usuario al mismo UID dentro del contenedor).
keep-id:uid=200,gid=210 $UID 200:210 (Mapea la cuenta de usuario a los valores UID, GID especificados dentro del contenedor).
nomap $UID nil (El UID del Usuario del Host no se mapea al contenedor).

Los valores válidos de modo son:

auto[:OPCIONES,...]: crea automáticamente un espacio de nombres de usuario único.

  • modo rootful: La bandera --userns=auto requiere que el nombre de usuario containers se especifique en los archivos /etc/subuid y /etc/subgid, con un rango no utilizado de IDs de usuario subordinados que Podman puede asignar a los contenedores. Ejemplo: containers:2147483647:2147483648.
  • modo rootless: Se utilizará el rango de usuarios de los archivos /etc/subuid y /etc/subgid. Tenga en cuenta que ejecutar un solo contenedor sin usar --userns=auto utilizará todo el rango de UIDs y no permitirá subdivisiones adicionales. Ver subuid(5).

Podman asigna rangos únicos de UIDs y GIDs de los IDs de usuario subordinados de containers. El tamaño de los rangos se basa en el número de UIDs requeridos en la imagen. El número de UIDs y GIDs se puede anular con la opción size.

La opción --userns=keep-id utiliza todos los subuids y subgids del usuario. La opción --userns=nomap utiliza todos los subuids y subgids del usuario, excepto el ID propio del usuario. Usar --userns=auto al iniciar nuevos contenedores no funciona mientras existan contenedores que se iniciaron con --userns=nomap o --userns=keep-id sin limitar el tamaño del espacio de nombres del usuario.

Opciones válidas de auto:

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE: para forzar un mapeo de GID a estar presente en el espacio de nombres de usuario.
  • size=SIZE: para especificar un tamaño explícito para el espacio de nombres de usuario automático. Por ejemplo, --userns=auto:size=8192. Si no se especifica size, auto estima un tamaño para el espacio de nombres de usuario.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE: para forzar un mapeo de UID a estar presente en el espacio de nombres de usuario.

El UID y GID del host en gidmapping y uidmapping pueden prefijarse opcionalmente con el símbolo @. En ese caso, podman buscará el ID intermedio correspondiente al ID del host y mapeará el ID intermedio encontrado al ID del contenedor. Para más detalles, consulte --uidmap.

container:id: únete al espacio de nombres de usuario del contenedor especificado.

host o "" (cadena vacía): ejecuta en el espacio de nombres de usuario del llamador. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el host que cualquier otro proceso iniciado por el usuario que llama.

keep-id: crea un espacio de nombres de usuario donde el UID y GID del usuario actual se mapean a los mismos valores en el contenedor. Para contenedores creados por el usuario root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

En adición, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen a menos que establezca explícitamente --user.

Opciones válidas de keep-id:

  • uid=UID: anula el UID dentro del contenedor que se usa para mapear al usuario actual.
  • gid=GID: anula el GID dentro del contenedor que se usa para mapear al usuario actual.
  • size=SIZE: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No soportado cuando se ejecuta como root.

nomap: crea un espacio de nombres de usuario donde el UID y GID del usuario rootless actual no se mapean al contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

Establece el modo del espacio de nombres UTS para el contenedor. Los siguientes valores son compatibles:

  • container:[contenedor]: únete al espacio de nombres UTS del contenedor especificado.

Cambio de propietario de montajes de volumen Cuando un volumen con nombre se monta por primera vez en un contenedor, Podman ajusta automáticamente la propiedad del punto de montaje del volumen durante la inicialización del contenedor. Esta operación de cambio de propietario ocurre bajo las siguientes condiciones: El volumen no se había utilizado antes (tiene establecido en true) El volumen está vacío o aún no se ha copiado. El volumen no está gestionado por un controlador de volumen externo. El controlador de volumen no es "image". Para volúmenes con montajes idmapped (usando la opción ), el cambio de propiedad tiene en cuenta los mapeos del espacio de nombres de usuario del contenedor, pero el volumen idmapped conserva el mapeo UID/GID correcto. Para volúmenes sin idmapping, el punto de montaje se cambia de propietario para que coincida con el usuario y grupo del proceso del contenedor, mapeado al espacio de nombres de usuario del host si el remapeo del espacio de nombres de usuario está habilitado. Si un contenedor se crea en un nuevo espacio de nombres de usuario, el UID y GID en el contenedor pueden corresponder a otro UID y GID en el host. El sufijo indica a Podman que utilice el UID y GID correctos del host basados en el UID y GID dentro del contenedor, para cambiar recursivamente el propietario y el grupo del volumen de origen. El cambio de propietario recorre el sistema de archivos bajo el volumen y cambia el UID/GID en cada archivo. Si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, retrasando el inicio del contenedor. Advertencia: Úselo con precaución ya que esto modifica el sistema de archivos del host.
Etiquetado de montajes de volumen Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el sistema operativo. Para cambiar una etiqueta en el contexto del contenedor, agregue uno de los dos sufijos o al montaje del volumen. Estos sufijos indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción indica a Podman que dos o más contenedores comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartidas permiten que todos los contenedores lean/escriban el contenido. La opción indica a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el contenedor actual puede usar un volumen privado. Nota: todos los contenedores dentro de un pod comparten la misma etiqueta SELinux. Esto significa que todos los contenedores dentro de dicho pod pueden leer/escribir volúmenes compartidos en el contenedor creado con en cualquiera de los contenedores. El reetiquetado recorre el sistema de archivos bajo el volumen y cambia la etiqueta en cada archivo; si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, retrasando el inicio del contenedor. Si el volumen se reetiquetó previamente con la opción , Podman está optimizado para no reetiquetar una segunda vez. Si se mueven archivos al volumen, las etiquetas se pueden cambiar manualmente con el comando chcon -Rt container_file_t PATH. Nota: No reetiquete archivos y directorios del sistema. El reetiquetado de contenido del sistema puede hacer que otros servicios confinados en la máquina fallen. Para estos tipos de contenedores, recomendamos deshabilitar la separación SELinux. La opción deshabilita la separación SELinux para el contenedor. Por ejemplo, si un usuario quisiera montar su directorio de inicio completo en un contenedor, necesita deshabilitar la separación SELinux. $ podman create --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file
Montajes de volumen superpuestos El indicador indica a Podman que monte el directorio del host como almacenamiento temporal utilizando el sistema de archivos overlay. Los procesos del contenedor pueden modificar el contenido dentro del punto de montaje, que se almacena en el almacenamiento del contenedor en un directorio separado. En términos de overlay, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el contenedor termina de ejecutarse, de forma similar a como se desmonta un punto de montaje tmpfs. Para usuarios avanzados, la opción también admite upperdir y workdir personalizados no volátiles para el montaje overlay. Los usuarios pueden gestionar completamente los upperdir y workdir personalizados, y Podman no los elimina al completar el ciclo de vida. Ejemplo Las ejecuciones posteriores del contenedor ven el contenido original del directorio de origen, los cambios de ejecuciones anteriores del contenedor ya no existen. Un caso de uso del montaje overlay es compartir la caché de paquetes del host en el contenedor para acelerar las compilaciones. Nota: El indicador entra en conflicto con otras opciones enumeradas anteriormente. El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor. Normalmente, los contenedores pueden leer/ejecutar container_share_t y pueden leer/escribir container_file_t. Si no se pueden cambiar las etiquetas en un volumen de origen, la separación SELinux del contenedor debe deshabilitarse para que el contenedor funcione. No modifique el directorio de origen montado en el contenedor con un montaje overlay, puede causar fallos inesperados. Solo modifique el directorio después de que el contenedor termine de ejecutarse.
