NOMBRE

podman-create - Crear un nuevo contenedor

SINOPSIS

podman create [opciones] imagen [comando [arg ...]]

podman container create [opciones] imagen [comando [arg ...]]

DESCRIPCIÓN

Crea una capa de contenedor escribible sobre la imagen especificada y la prepara para ejecutar el comando especificado. Luego, la ID del contenedor se imprime en STDOUT. Esto es similar a podman run -d excepto que el contenedor nunca se inicia. Usa el comando podman start contenedor para iniciar el contenedor en cualquier momento.

El estado inicial del contenedor creado con podman create es 'created'.

Los ajustes predeterminados para las opciones se definen en containers.conf. La mayoría de los ajustes para conexiones remotas usan el containers.conf del servidor, excepto cuando se documenta en las páginas del manual.

IMAGEN

La imagen se especifica usando el formato transporte:ruta. Si no se especifica ningún transporte, se usa el transporte docker (registro de contenedores) por defecto. Para Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), docker es el único transporte permitido.

dir:ruta
Un directorio local existente ruta que almacena el manifiesto, los archivos tar de las capas y las firmas como archivos individuales. Este es un formato no estandarizado, útil principalmente para depuración o inspección no invasiva de contenedores.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman create dir:/tmp/fedora echo hello

docker://referencia-docker (Predeterminado)
Una referencia de imagen almacenada en un registro de imágenes de contenedores remoto. Ejemplo: "quay.io/podman/stable:latest". La referencia puede incluir una ruta a un registro específico; si no lo hace, se consultan los registros listados en registries.conf para encontrar una imagen coincidente. Por defecto, se utilizan las credenciales de podman login (almacenadas en $XDG_RUNTIME_DIR/containers/auth.json por defecto) para autenticarse; de lo contrario, recurre a las credenciales en $HOME/.docker/config.json.

$ podman create registry.fedoraproject.org/fedora:latest echo hello

docker-archive:ruta[:referencia-docker] Una imagen almacenada en el archivo con formato docker save. referencia-docker solo se usa al crear dicho archivo y no debe contener un digest.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman create docker-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

docker-daemon:referencia-docker
Una imagen en formato referencia-docker almacenada en el almacenamiento interno del demonio Docker. La referencia-docker también puede ser una ID de imagen (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman create docker-daemon:docker.io/library/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

oci-archive:ruta:etiqueta
Una imagen en un directorio que cumple con la "Especificación de Diseño de Imágenes de Contenedor Abierto" en la ruta especificada y con una etiqueta especificada.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman create oci-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

OPCIONES

--add-host=hostname[;hostname[;...]]:ip

Añade un mapeo personalizado de host a IP al archivo /etc/hosts del contenedor.

La opción toma uno o varios nombres de host separados por punto y coma para ser mapeados a una única dirección IPv4 o IPv6, separados por dos puntos. También se puede usar para sobrescribir las direcciones IP de los nombres de host que Podman añade a /etc/hosts por defecto (ver también las opciones --name y --hostname). Esta opción se puede especificar múltiples veces para añadir mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede proporcionar la bandera especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de su configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que haría que Podman fallara con un mensaje de error. Puede sobrescribir esta dirección IP usando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para añadir automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitarlo proporcionando la opción --no-hosts o estableciendo host_containers_internal_ip="none" en containers.conf. Si no se configuró ninguna dirección host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se está ejecutando en una máquina virtual usando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven en su lugar mediante el resolutor DNS de gvproxy.

Podman usará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente usando la configuración base_hosts_file en containers.conf.

--annotation=clave=valor

Añade una anotación al contenedor. Esta opción se puede establecer múltiples veces.

--arch=ARQUITECTURA

Anula la arquitectura, por defecto la del host, de la imagen que se va a descargar. Por ejemplo, arm. A menos que se anule, las búsquedas posteriores de la misma imagen en el almacenamiento local coincidirán con esta arquitectura, independientemente del host.

--attach, -a=stdin | stdout | stderr

Adjuntar a STDIN, STDOUT o STDERR.

En modo de primer plano (el predeterminado cuando no se especifica -d), podman run puede iniciar el proceso en el contenedor y adjuntar la consola a la entrada, salida y error estándar del proceso. Incluso puede simular ser una TTY (esto es lo que la mayoría de los ejecutables de la línea de comandos esperan) y pasar señales. La opción -a se puede establecer para cada uno de stdin, stdout y stderr.

--authfile=ruta

Ruta del archivo de autenticación. Por defecto es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo es creado por podman login. Si el estado de autorización no se encuentra allí, se revisa $HOME/.docker/config.json, que se establece usando docker login.

Nota: También existe la opción de anular la ruta predeterminada del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

--blkio-weight=peso

Peso relativo de Block IO. El peso es un valor entre 10 y 1000.

Esta opción no es compatible en sistemas sin root con cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo del dispositivo Block IO.

--cap-add=capacidad

Añadir capacidades de Linux.

Otorgar capacidades adicionales aumenta los privilegios de los procesos que se ejecutan dentro del contenedor y potencialmente le permite escapar del confinamiento. --cert-dir=ruta

Utilice los certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. (Por defecto: /etc/containers/certs.d) Para más detalles, consulte containers-certs.d(5). (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--cgroup-conf=CLAVE=VALOR

Cuando se ejecuta en cgroup v2, especifique el archivo cgroup al que escribir y su valor. Por ejemplo, --cgroup-conf=memory.high=1073741824 establece el límite de memory.high en 1 GB.

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se crea el cgroup para el contenedor. Si la ruta no es absoluta, se considera que la ruta es relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen ya.

--cgroupns=modo

Establece el modo de namespace de cgroup para el contenedor.

  • host: usa el namespace de cgroup del host dentro del contenedor.
  • container:id: únete al namespace del contenedor especificado.
  • private: crea un nuevo namespace de cgroup.
  • ns:ruta: únete al namespace en la ruta especificada.

Si el host usa cgroups v1, el valor predeterminado se establece en host. En cgroups v2, el valor predeterminado es private.

--cgroups=cómo

Determina si el contenedor crea cgroups.

El valor predeterminado es enabled.

La opción enabled crea un nuevo cgroup bajo el cgroup-parent. La opción disabled obliga al contenedor a no crear cgroups, y por lo tanto entra en conflicto con las opciones de cgroup ( --cgroupns y --cgroup-parent). La opción no-conmon deshabilita un nuevo cgroup solo para el proceso conmon. La opción split divide el cgroup actual en dos sub-cgroups: uno para conmon y otro para la carga útil del contenedor. No es posible establecer --cgroup-parent con split.

--chrootdirs=ruta

Ruta a un directorio dentro del contenedor que se trata como un directorio de chroot. Cualquier archivo gestionado por Podman (por ejemplo, /etc/resolv.conf, /etc/hosts, /etc/hostname) que se monte en el directorio raíz también se montará en esa ubicación. Múltiples directorios están separados por una coma.

--cidfile=archivo

Escribe el ID del contenedor en archivo. El archivo se elimina junto con el contenedor, excepto cuando se utiliza con podman run --remote en contenedores detenidos.

--conmon-pidfile=archivo

Escribe el PID del proceso conmon en un archivo. Como conmon se ejecuta en un proceso separado de Podman, esto es necesario cuando se utiliza systemd para reiniciar contenedores de Podman. (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--cpu-period=límite

Establece el período de CPU para el planificador Justo (CFS), que es una duración en microsegundos. Una vez que se agota la cuota de CPU del contenedor, no se programará para ejecutarse hasta que finalice el período actual. El valor predeterminado es 100000 microsegundos.

En algunos sistemas, la modificación de los límites de recursos puede no estar permitida para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpu-quota=límite

Limita la cuota de CPU del planificador Justo (CFS).

Limita el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso de CPU completo. El límite es un número en microsegundos. Si se proporciona un número, al contenedor se le permite usar esa cantidad de tiempo de CPU hasta que finalice el período de CPU (controlable a través de --cpu-period).

En algunos sistemas, la modificación de los límites de recursos puede no estar permitida para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpu-rt-period=microsegundos

Limita el período de tiempo real de CPU en microsegundos.

Limita el uso de CPU de tiempo real del contenedor. Esta opción indica al kernel que restrinja el uso de CPU de tiempo real del contenedor al período especificado.

Esta opción solo es compatible con sistemas con root en cgroups V1.

--cpu-rt-runtime=microsegundos

Limita el tiempo de ejecución de tiempo real de CPU en microsegundos.

Limita el uso de CPU de tiempo real de los contenedores. Esta opción indica al kernel que limite la cantidad de tiempo en un período de CPU determinado que las tareas de tiempo real pueden consumir. Por ejemplo, un período de 1.000.000 us y un tiempo de ejecución de 950.000 us significa que este contenedor puede consumir el 95% de la CPU disponible y dejar el 5% restante para tareas de prioridad normal.

La suma de todos los tiempos de ejecución entre contenedores no puede exceder la cantidad asignada al cgroup padre.

Esta opción solo es compatible con sistemas con root en cgroups V1.

--cpu-shares, -c=comparticiones

Comparticiones de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de las comparticiones de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso predeterminado es 1024.

La proporción solo se aplica cuando se ejecutan procesos que consumen mucha CPU. Cuando las tareas de un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una cuota de cpu de 1024 y otros dos tienen una configuración de cuota de cpu de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se agrega un cuarto contenedor con una cuota de cpu de 1024, el primer contenedor solo recibe el 33% de la CPU. Los contenedores restantes reciben el 16,5%, 16,5% y 33% de la CPU.

En un sistema multinúcleo, las comparticiones de tiempo de CPU se distribuyen entre todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de comparticiones de CPU:

PID contenedor CPU Compartición de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, la modificación de los límites de recursos puede no estar permitida para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpus=número

Número de CPUs. El valor predeterminado es 0.0, lo que significa sin límite. Esto es un atajo para --cpu-period y --cpu-quota, por lo tanto, la opción no se puede especificar con --cpu-period o --cpu-quota.

En algunos sistemas, la modificación de los límites de CPU puede no estar permitida para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de estos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, la modificación de los límites de recursos puede no estar permitida para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), utilice --cpuset-mems=0,1 y los procesos del contenedor solo utilizarán memoria de los dos primeros nodos de memoria.

En algunos sistemas, la modificación de los límites de recursos puede no estar permitida para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--creds=[nombre de usuario[:contraseña]]

El [nombre de usuario[:contraseña]] a utilizar t

o autenticarse con el registro, si es necesario. Si no se proporcionan uno o ambos valores, aparece un indicador en la línea de comandos y se puede ingresar el valor. La contraseña se ingresa sin visualización.

Tenga en cuenta que las credenciales especificadas solo se utilizan para autenticarse en los registros de destino. No se utilizan para espejos ni cuando el registro se reescribe (ver containers-registries.conf(5)); para autenticarse en esos casos, considere usar un archivo containers-auth.json(5).

--decryption-key=clave[:contraseña]

La [clave[:contraseña]] que se utilizará para el descifrado de imágenes. La clave puede apuntar a claves y/o certificados. El descifrado se intenta con todas las claves. Si la clave está protegida por una contraseña, se requiere que se pase en el argumento y se omita en caso contrario.

--device=dispositivo-host[:dispositivo-contenedor][:permisos]

Añade un dispositivo del host al contenedor. El parámetro opcional permisos se puede usar para especificar los permisos del dispositivo combinando r para lectura, w para escritura y m para mknod(2).

Ejemplo: --device=/dev/sdc:/dev/xvdc:rwm.

Nota: si dispositivo-host es un enlace simbólico, primero se resuelve. El contenedor solo almacena los números mayor y menor del dispositivo del host.

Podman puede cargar módulos del kernel necesarios para usar el dispositivo especificado. Los dispositivos para los que Podman carga módulos cuando es necesario son: /dev/fuse.

En modo sin root, el nuevo dispositivo se monta en el contenedor desde el host en lugar de que Podman lo cree dentro del espacio del contenedor. Debido a que el montaje bind conserva su etiqueta SELinux en sistemas SELinux, el contenedor puede recibir un error de permiso al acceder al dispositivo montado. Modifique la configuración de SELinux para permitir que los contenedores utilicen todas las etiquetas de dispositivos con el siguiente comando:

$ sudo setsebool -P container_use_devices=true

Nota: si el usuario solo tiene derechos de acceso a través de un grupo, el acceso al dispositivo desde un contenedor sin root falla. Use la bandera --group-add keep-groups para pasar el acceso de grupo suplementario del usuario al contenedor.

--device-cgroup-rule="tipo mayor:menor modo"

Añade una regla a la lista de dispositivos permitidos de cgroup. Se espera que la regla tenga el formato especificado en la documentación del kernel de Linux admin-guide/cgroup-v1/devices: - tipo: a (todos), c (carácter), o b (bloque); - mayor y menor: un número o * para todos; - modo: una composición de r (lectura), w (escritura) y m (mknod(2)).

--disable-content-trust

Esta es una opción específica de Docker para deshabilitar la verificación de imágenes en un registro de contenedores y no es compatible con Podman. Esta opción es un NOOP (no operation) y se proporciona únicamente para compatibilidad de scripts.

--dns=direccion-ip

Establece servidores DNS personalizados.

Esta opción se puede usar para anular la configuración de DNS enviada al contenedor. Normalmente, esto es necesario cuando la configuración de DNS del host no es válida para el contenedor (por ejemplo, 127.0.0.1). En este caso, el flag --dns es necesario para cada ejecución.

Se puede especificar el valor especial none para deshabilitar la creación de /etc/resolv.conf en el contenedor por Podman. Luego, el archivo /etc/resolv.conf en la imagen se usa sin cambios.

Tenga en cuenta que direccion-ip puede añadirse directamente a /etc/resolv.conf del contenedor. Sin embargo, esto no está garantizado. Por ejemplo, pasar una red personalizada cuya dns_enabled esté establecida en true a --network dará como resultado que /etc/resolv.conf solo haga referencia al servidor aardvark-dns. aardvark-dns reenvía a la direccion-ip proporcionada para todas las consultas de nombres no de contenedor.

Esta opción no se puede combinar con --network establecido en none o container:id.

--dns-option=opcion

Establece opciones DNS personalizadas. Inválido si se usa --dns-option con --network establecido en none o container:id.

--dns-search=dominio

Establece dominios de búsqueda DNS personalizados. Inválido si se usa --dns-search con --network establecido en none o container:id. Use --dns-search=. para eliminar el dominio de búsqueda.

--entrypoint="comando" | '["comando", arg1 , ...]"

Anula el ENTRYPOINT predeterminado de la imagen.

El ENTRYPOINT de una imagen es similar a un COMMAND, ya que especifica qué ejecutable ejecutar cuando se inicia el contenedor, pero es (intencionalmente) más difícil de anular. El ENTRYPOINT le da a un contenedor su naturaleza o comportamiento predeterminado. Cuando se establece el ENTRYPOINT, el contenedor se ejecuta como si fuera ese binario, completo con opciones predeterminadas. Se pueden pasar más opciones a través del COMMAND. Pero, si un usuario desea ejecutar algo más dentro del contenedor, la opción --entrypoint permite especificar un nuevo ENTRYPOINT.

Especifique comandos de múltiples opciones en forma de una cadena JSON.

--env, -e=variable-entorno

Establece variables de entorno.

Esta opción permite variables de entorno arbitrarias que están disponibles para el proceso que se va a lanzar dentro del contenedor. Si se especifica una variable de entorno sin valor, Podman busca en el entorno del host un valor y establece la variable solo si está configurada en el host. Como caso especial, si se especifica una variable de entorno que termina en * sin valor, Podman busca en el entorno del host variables que comiencen con el prefijo y agrega esas variables al contenedor.

Ver la nota ⟨#environment⟩ más abajo para conocer la precedencia y los ejemplos.

--env-file=archivo

Lee variables de entorno de un archivo delimitado por líneas.

Ver la nota ⟨#environment⟩ más abajo para conocer la precedencia y los ejemplos.

--env-host

--env-merge=variable-entorno

Establecer la longitud máxima en caracteres del registro de comprobación de estado almacenado. ("0" significa una longitud de registro infinita) (Predeterminado: 500 caracteres)

Acción a tomar una vez que el contenedor cambie a un estado no saludable. El valor predeterminado es none.

  • none: No realizar ninguna acción.
  • kill: Matar el contenedor.
  • restart: Reiniciar el contenedor. No combine la acción de restart con el indicador --restart. Al ejecutarse dentro de una unidad systemd, considere usar la acción kill o stop en su lugar para aprovechar la política de reinicio de systemd.

El número de reintentos permitidos antes de que una comprobación de estado se considere no saludable. El valor predeterminado es 3.

El tiempo de inicialización necesario para que un contenedor se inicie. El valor se puede expresar en formato de tiempo como 2m3s. El valor predeterminado es 0s.

Nota: Este parámetro anulará la configuración relacionada de comprobación de estado de la imagen.

--health-startup-cmd="comando" | '["comando", arg1 , ...]'

Establecer un comando de comprobación de estado de inicio para un contenedor. Este comando se ejecuta dentro del contenedor y se utiliza para controlar la comprobación de estado regular. Cuando el comando de inicio tiene éxito, comienza la comprobación de estado regular y la comprobación de estado de inicio cesa. Opcionalmente, si el comando falla durante un número determinado de intentos, el contenedor se reinicia. Se puede utilizar una comprobación de estado de inicio para garantizar que los contenedores con un período de inicio prolongado no se marquen como no saludables hasta que se inicien por completo. Las comprobaciones de estado de inicio solo se pueden utilizar cuando también se establece una comprobación de estado regular (de la imagen del contenedor o de la opción --health-cmd).

--health-startup-interval=intervalo

Establecer un intervalo para la comprobación de estado de inicio. Un intervalo de disable no configura ningún temporizador automático. El valor predeterminado es 30s.

--health-startup-retries=intentos

El número de intentos permitidos antes de que la comprobación de estado de inicio reinicie el contenedor. Si se establece en 0, el contenedor nunca se reinicia. El valor predeterminado es 0.

--health-startup-success=intentos

El número de ejecuciones exitosas requeridas antes de que la comprobación de estado de inicio tenga éxito y comience la comprobación de estado regular. Un valor de 0 significa que cualquier éxito inicia la comprobación de estado regular. El valor predeterminado es 0.

--health-startup-timeout=tiempo_de_espera

El tiempo máximo que tiene el comando de comprobación de estado de inicio para completarse antes de que se marque como fallido. El valor se puede expresar en un formato de tiempo como 2m3s. El valor predeterminado es 30s.

--health-timeout=tiempo_de_espera

El tiempo máximo permitido para completar la comprobación de estado antes de que se considere fallido un intervalo. Al igual que start-period, el valor se puede expresar en un formato de tiempo como 1m22s. El valor predeterminado es 30s.

Nota: Un tiempo de espera marca la comprobación de estado como fallida. Si el comando de comprobación de estado en sí mismo se ejecuta durante más tiempo que el tiempo_de_espera especificado, se le enviará una señal SIGKILL.

Nota: Este parámetro anulará la configuración relacionada de comprobación de estado de la imagen.

Opciones comunes a todos los tipos de montaje:

  • src, source: especificación de origen del montaje para bind, glob y volume. Obligatorio para artifact, bind, glob, image y volume.
  • dst, dest, destination, target: especificación de destino del montaje.

Cuando se especifica el destino, los archivos y directorios que coinciden con el globo en el nombre de archivo base en el directorio de destino se montan. La opción type=glob,src=/foo*,destination=/tmp/bar indica a los motores de contenedores que monten archivos del host que coincidan con /foo* en el directorio /tmp/bar/ en el contenedor.

--secret=secreto[,opt=opt ...]

Da acceso al contenedor a un secreto. Se puede especificar varias veces.

Un secreto es un bloque de datos sensibles que un contenedor necesita en tiempo de ejecución pero que no se almacena en la imagen ni en el control de versiones de origen, como nombres de usuario y contraseñas, certificados y claves TLS, claves SSH u otras cadenas genéricas o contenido binario importantes (hasta 512 kB de tamaño).

Cuando los secretos se especifican como tipo mount, los secretos se copian y montan en el contenedor cuando se crea un contenedor. Cuando los secretos se especifican como tipo env, el secreto se establece como una variable de entorno dentro del contenedor. Los secretos se escriben en el contenedor en el momento de la creación del contenedor, y modificar el secreto usando comandos podman secret después de que el contenedor se cree afecta al secreto dentro del contenedor.

Los secretos y su almacenamiento se gestionan utilizando el comando podman secret.

Opciones de secreto

  • type=mount|env : Cómo se expone el secreto al contenedor.
    mount monta el secreto en el contenedor como un archivo.
    env expone el secreto como una variable de entorno.
    Por defecto es mount.
  • target=objetivo : Destino del secreto.
    Para secretos montados, esta es la ruta al secreto dentro del contenedor.
    Si se proporciona una ruta completa, el secreto se monta en esa ubicación.
    De lo contrario, el secreto se monta en
    /run/secrets/objetivo para contenedores de Linux o
    /var/run/secrets/objetivo para contenedores de FreeBSD.
    Si el objetivo no está establecido, el secreto se monta en /run/secrets/nombre_secreto por defecto.
    Para secretos env, esta es la clave de la variable de entorno. Por defecto es nombre_secreto.
  • uid=0 : UID del secreto. Por defecto es 0. Solo tipo de montaje de secreto.
  • gid=0 : GID del secreto. Por defecto es 0. Solo tipo de montaje de secreto.
  • mode=0 : Modo del secreto. Por defecto es 0444. Solo tipo de montaje de secreto.

Ejemplos

Montar en /my/location/mysecret con UID 1:

--secret mysecret,target=/my/location/mysecret,uid=1

Montar en /run/secrets/customtarget con modo 0777:

--secret mysecret,target=customtarget,mode=0777

Crear una variable de entorno secreta llamada ENVSEC:

--secret mysecret,type=env,target=ENVSEC

--security-opt=opción

Opciones de seguridad

  • apparmor=unconfined : Desactiva el confinamiento de apparmor para el contenedor
  • apparmor=perfil-alternativo : Establece el perfil de confinamiento de apparmor para el contenedor
  • label=user:USUARIO: Establece el usuario de etiqueta para los procesos del contenedor
  • label=role:ROL: Establece el rol de etiqueta para los procesos del contenedor
  • label=type:TIPO: Establece el tipo de proceso de etiqueta para los procesos del contenedor
  • label=level:NIVEL: Establece el nivel de etiqueta para los procesos del contenedor
  • label=filetype:TIPO: Establece el tipo de archivo de etiqueta para los archivos del contenedor
  • label=disable: Desactiva la separación de etiquetas para el contenedor

Nota: El etiquetado se puede desactivar para todos los contenedores estableciendo label=false en el archivo containers.conf (/etc/containers/containers.conf o $HOME/.config/containers/containers.conf).

  • label=nested: Permite modificaciones de SELinux dentro del contenedor. Se permite a los contenedores modificar etiquetas SELinux en archivos y procesos, siempre que la política SELinux lo permita. Sin nested, los contenedores ven SELinux como deshabilitado, incluso cuando está habilitado en el host. Se impide a los contenedores establecer cualquier etiqueta.
  • mask=/ruta/1:/ruta/2: Las rutas a enmascarar separadas por dos puntos. Una ruta enmascarada no se puede acceder dentro del contenedor.
  • no-new-privileges: Deshabilita que los procesos del contenedor obtengan privilegios adicionales a través de la llamada al sistema execve(2) (por ejemplo, a través de bits setuid o setgid, o a través de capacidades de archivo). Los programas que dependen de los bits setuid/setgid establecidos en su ejecutable para cambiar el ID de usuario o grupo ya no pueden hacerlo, y cualquier capacidad de archivo añadida al ejecutable (por ejemplo, mediante setcap) no se añade al conjunto de capacidades permitidas. Para más detalles, véase: https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined: Desactiva el confinamiento seccomp para el contenedor.
  • seccomp=perfil.json: Archivo JSON que se utilizará como filtro seccomp. Tenga en cuenta que la anotación io.podman.annotations.seccomp se establece con el valor especificado como se muestra en podman inspect.
  • proc-opts=OPCIONES : Lista separada por comas de opciones a utilizar para el montaje /proc. Se especifican más detalles sobre las posibles opciones de montaje en la página del manual proc(5).
  • unmask=ALL o /ruta/1:/ruta/2, o rutas expandidas por shell (/proc/*): Rutas a desenmascarar separadas por dos puntos. Si se establece en ALL, desenmascara todas las rutas que están enmascaradas o hechas de solo lectura por defecto. Las rutas enmascaradas por defecto son /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, y /sys/fs/selinux, /sys/devices/virtual/powercap. Las rutas por defecto que son de solo lectura son /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

Nota: El etiquetado se puede desactivar para todos los contenedores estableciendo label=false en el archivo containers.conf(5).

--shm-size=número[unidad]

Tamaño de /dev/shm. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes). Si se omite la unidad, el sistema utiliza bytes. Si se omite el tamaño, el predeterminado es 64m. Cuando el tamaño es 0, no hay límite en la cantidad de memoria utilizada para IPC por el contenedor. Esta opción entra en conflicto con --ipc=host.

Tamaño de los montajes tmpfs específicos de systemd, como /run, /run/lock, /var/log/journal y /tmp. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes). Si se omite la unidad, el sistema utiliza bytes. Si se omite el tamaño, el predeterminado es 64m. Cuando el tamaño es 0, el uso se limita al 50% de la memoria disponible del host.

--uidmap=[flags]uid_contenedor:uid_origen[:cantidad]

Ejecutar el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo de UID proporcionado. Esta opción entra en conflicto con las opciones --userns y --subuidname. Esta opción proporciona una forma de mapear UIDs del host a UIDs del contenedor. Se puede pasar varias veces para mapear diferentes rangos.

Los valores posibles de flags opcionales se discuten más adelante en esta página. El valor de cantidad es opcional y se asume que es 1 si no se proporciona.

El valor de uid_origen se basa en el usuario que ejecuta el comando, ya sea un usuario rootful o rootless.

  • usuario rootful: [flags]uid_contenedor:uid_host[:cantidad]
  • usuario rootless: [flags]uid_contenedor:uid_intermediario[:cantidad]

Mapeos rootful

Cuando podman create es llamado por un usuario privilegiado, la opción --uidmap funciona como un mapeo directo entre los UIDs del host y los UIDs del contenedor.

UID del host -> UID del contenedor

La cantidad especifica el número de UIDs consecutivos que se mapean. Si, por ejemplo, cantidad es 4, el mapeo se ve así:

UID del host UID del contenedor
uid_origen uid_contenedor
uid_origen + 1 uid_contenedor + 1
uid_origen + 2 uid_contenedor + 2
uid_origen + 3 uid_contenedor + 3

Mapeos rootless

Cuando podman create es llamado por un usuario no privilegiado (es decir, ejecutándose rootless), el valor uid_origen se interpreta como un "UID intermediario". En el caso rootless, los UIDs del host no se mapean directamente a los UIDs del contenedor. En cambio, el mapeo se realiza en dos pasos de mapeo:

UID del host -> UID intermediario -> UID del contenedor

La opción --uidmap solo influye en el segundo paso de mapeo.

El primer paso de mapeo se deriva de Podman a partir del contenido del archivo /etc/subuid y del UID del usuario que llama a Podman.

Primer paso de mapeo:

UID del host UID intermediario
UID para el usuario de Podman 0
1er UID subordinado 1
2do UID subordinado 2
3er UID subordinado 3
n-ésimo UID subordinado n

Para poder utilizar UIDs intermediarios mayores que cero, el usuario necesita tener UIDs subordinados configurados en /etc/subuid. Ver subuid(5).

El segundo paso de mapeo se configura con --uidmap.

Si, por ejemplo, cantidad es 5, el segundo paso de mapeo se ve así:

UID intermediario UID del contenedor
uid_origen uid_contenedor
uid_origen + 1 uid_contenedor + 1
uid_origen + 2 uid_contenedor + 2
uid_origen + 3 uid_contenedor + 3
uid_origen + 4 uid_contenedor + 4

Al ejecutarse como rootless, Podman utiliza todos los rangos configurados en el archivo /etc/subuid.

El ID de usuario actual se mapea a UID=0 en el espacio de nombres de usuario rootless. Cada rango adicional se agrega secuencialmente después:

host espacio de nombres de usuario rootless longitud
$UID 0 1
1 $PRIMER_RANGO_ID $PRIMER_RANGO_LONGITUD
1+$PRIMER_RANGO_LONGITUD $SEGUNDO_RANGO_ID $SEGUNDO_RANGO_LONGITUD

Referenciar un ID de host desde el espacio de nombres padre

Como usuario rootless, el ID de host dado en --uidmap o --gidmap se mapea desde el espacio de nombres intermediario generado por Podman. A veces es deseable referirse directamente al espacio de nombres del host. Es posible hacerlo manualmente, ejecutando podman unshare cat /proc/self/gid_map, encontrando el ID de host deseado en la segunda columna de la salida, y obteniendo el ID intermediario correspondiente de la primera columna.

Podman puede realizar todo esto precediendo el ID de host en el mapeo con el símbolo @. Por ejemplo, al especificar --gidmap 100000:@2000:1, podman buscará el ID intermediario correspondiente al ID de host 2000 y mapeará el ID intermediario encontrado al ID del contenedor 100000. El ID de host dado debe haber sido subordinado (de lo contrario, no se mapearía al espacio intermediario en primer lugar).

Si la longitud es mayor que uno, por ejemplo con --gidmap 100000:@2000:2, Podman mapeará los IDs de host 2000 y 2001 a 100000 y 100001, respectivamente, independientemente de cómo esté definido el mapeo intermediario.

Extender mapeos anteriores

Algunas modificaciones de mapeo pueden ser engorrosas. Por ejemplo, un usuario comienza con un mapeo como --gidmap="0:0:65000", que necesita ser cambiado para que el ID padre 1 se mapee al ID del contenedor 100000 en su lugar, dejando el ID del contenedor 1 sin asignar. El --gidmap correspondiente se convierte en --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

Esta notación se puede simplificar utilizando la bandera +, que se encarga de romper los mapeos anteriores eliminando cualquier asignación conflictiva con el mapeo dado. La bandera se antepone al ID del contenedor de la siguiente manera: --gidmap="0:0:65000" --gidmap="+100000:1:1"

Bandera Ejemplo Descripción
+ +100000:1:1 Extender el mapeo anterior

Esta notación deja huecos en la asignación, por lo que puede ser conveniente rellenarlos posteriormente: --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

Un caso de uso específico para esta bandera es en el contexto de usuarios rootless. Un usuario rootless puede especificar mapeos con la bandera + como en --gidmap="+100000:1:1". Podman luego "rellenará los huecos" a partir de cero con todos los IDs intermediarios restantes. Esto es conveniente cuando un usuario desea mapear un ID intermediario específico a un ID de contenedor, dejando que Podman asigne el resto de los IDs subordinados a su voluntad.

Pasar solo uno de --uidmap o --gidmap

Por lo general, los IDs de usuario y grupo subordinados se asignan simultáneamente, y para cualquier usuario, los IDs de usuario subordinados coinciden con los IDs de grupo subordinados. Por conveniencia, si solo se proporciona uno de --uidmap o --gidmap, podman asume que el mapeo se refiere tanto a UIDs como a GIDs y aplica el mapeo dado a ambos. Si solo se necesita cambiar un valor de los dos, los mapeos deben incluir las banderas u o g para especificar que solo se aplican a UIDs o GIDs y no deben copiarse.

bandera Ejemplo Descripción
u u20000:2000:1 El mapeo solo se aplica a UIDs
g g10000:1000:1 El mapeo solo se aplica a GIDs

Por ejemplo, dado el comando

podman create --gidmap "0:0:1000" --gidmap "g2000:2000:1"

Dado que no se proporciona --uidmap, el --gidmap se copia a --uidmap, dando un comando equivalente a

podman create --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

El --gidmap "g2000:2000:1" utilizó la bandera g y, por lo tanto, no se copió a --uidmap.

Mapeo rootless de GIDs de host adicionales

Un usuario rootless puede desear mapear un grupo de host específico que tiene alr así como la restructuración de sus mapeos de UID/GID en /etc/subuid y /etc/subgid. Si no se especifica un mapeo completo, el UID/GID principal del usuario anfitrión se mapea al UID/GID principal del contenedor, con el resto de los ID de contenedor mapeados a los IDs subordinados que el usuario anfitrión tiene disponibles.

En algunos casos, es posible que desee que su UID/GID principal sea mapeado a un UID/GID específico del contenedor, o que simplemente subordine un UID/GID del anfitrión sin especificar el resto del mapeo.

Esto se puede hacer con --gidmap "+ggid_contenedor:@gid_anfitrión"

Donde:

  • El GID del anfitrión se proporciona a través del símbolo @
  • El mapeo de este GID no se copia a --usermap gracias a la bandera g.
  • El resto de los ID del contenedor se mapearán comenzando desde 0 hasta n, con todos los GID subordinados restantes, gracias a la bandera +.

Por ejemplo, si un usuario pertenece al grupo 2000 y ese grupo está subordinado a ese usuario (con usermod --add-subgids 2000-2000 $USER), el usuario puede mapear el grupo en el contenedor con: --gidmap=+g100000:@2000.

Si este mapeo se combina con la opción --group-add=keep-groups, el proceso en el contenedor pertenecerá al grupo 100000, y los archivos que pertenezcan al grupo 2000 en el anfitrión aparecerán como pertenecientes al grupo 100000 dentro del contenedor.

podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

Sin UIDs subordinados

Incluso si un usuario no tiene UIDs subordinados en /etc/subuid, se puede usar --uidmap para mapear el UID normal del usuario a un UID de contenedor ejecutando podman create --uidmap $uid_contenedor:0:1 --user $uid_contenedor ....

--ulimit=opción

Opciones de ulimit. Establece los valores de ulimits dentro del contenedor.

--ulimit con un límite suave y uno duro en el formato =[:]. Por ejemplo:

$ podman run --ulimit nofile=1024:1024 --rm ubi9 ulimit -n 1024

Establezca -1 para el límite suave o duro para establecer el límite al límite máximo del proceso actual. En modo rootful, esto a menudo es ilimitado.

Use host para copiar la configuración actual del anfitrión.

No use nproc con la bandera ulimit, ya que Linux usa nproc para establecer el número máximo de procesos disponibles para un usuario, no para un contenedor.

Anula las variables de entorno predeterminadas para el contenedor. Las variables de entorno predeterminadas incluyen las variables proporcionadas nativamente por Podman, las variables de entorno configuradas por la imagen y las variables de entorno de containers.conf.

--user, -u=usuario[:grupo]

Establece el nombre de usuario o UID utilizado y, opcionalmente, el nombre de grupo o GID para el comando especificado. Tanto usuario como grupo pueden ser simbólicos o numéricos.

Sin este argumento, el comando se ejecuta como el usuario especificado en la imagen del contenedor. A menos que se anule mediante un comando USER en el Containerfile o por un valor pasado a esta opción, este usuario generalmente es root por defecto.

Cuando no se utiliza un espacio de nombres de usuario, el UID y GID utilizados dentro del contenedor y en el anfitrión coinciden. Sin embargo, cuando se utilizan espacios de nombres de usuario, el UID y GID dentro del contenedor pueden corresponder a otro UID y GID en el anfitrión. En contenedores sin root, por ejemplo, siempre se utiliza un espacio de nombres de usuario, y el root dentro del contenedor corresponde por defecto al UID y GID del usuario que invoca a Podman.

--userns=modo

Establece el modo del espacio de nombres de usuario para el contenedor.

Si no se establece --userns, el valor predeterminado se determina de la siguiente manera. - Si se establece --pod, se ignora --userns y se utiliza el espacio de nombres de usuario del pod. - Si la variable de entorno PODMAN_USERNS está establecida, se utiliza su valor. - Si se especifica userns en containers.conf, se utiliza ese valor. - De lo contrario, se asume --userns=host.

--userns="" (es decir, una cadena vacía) es un alias para --userns=host.

Esta opción es incompatible con --gidmap, --uidmap, --subuidname y --subgidname.

Mapeos de claves de --userns para usuarios sin root:

Clave Usuario Anfitrión Usuario Contenedor
auto $UID nil (El UID del Usuario Anfitrión no se mapea al contenedor).
host $UID 0 (Cuenta de Usuario Predeterminada mapeada al usuario root en el contenedor).
keep-id $UID $UID (Mapea la cuenta de usuario al mismo UID dentro del contenedor).
keep-id:uid=200,gid=210 $UID 200:210 (Mapea la cuenta de usuario al UID, GID especificado dentro del contenedor).
nomap $UID nil (El UID del Usuario Anfitrión no se mapea al contenedor).

Los valores válidos para modo son:

auto[:OPCIONES,...]: crea automáticamente un espacio de nombres de usuario único.

  • modo rootful: La bandera --userns=auto requiere que el nombre de usuario containers se especifique en los archivos /etc/subuid y /etc/subgid, con un rango no utilizado de IDs de usuario subordinados que Podman permite asignar a los contenedores. Ejemplo: containers:2147483647:2147483648.
  • modo sin root: Se utilizará el rango de usuarios de los archivos /etc/subuid y /etc/subgid. Tenga en cuenta que ejecutar un único contenedor sin usar --userns=auto utilizará todo el rango de UIDs y no permitirá una mayor subdivisión. Consulte subuid(5).

Podman asigna rangos únicos de UIDs y GIDs de los IDs de usuario subordinados de containers. El tamaño de los rangos se basa en el número de UIDs requeridos en la imagen. El número de UIDs y GIDs se puede anular con la opción size.

La opción --userns=keep-id utiliza todos los subuids y subgids del usuario. La opción --userns=nomap utiliza todos los subuids y subgids del usuario excepto el ID propio del usuario. Usar --userns=auto al iniciar nuevos contenedores no funciona mientras existan contenedores que se iniciaron con --userns=nomap o --userns=keep-id sin limitar el tamaño del espacio de nombres de usuario.

Opciones válidas para auto:

  • gidmapping=GID_CONTENEDOR:GID_ANFITRIÓN:TAMAÑO: para forzar que un mapeo de GID esté presente en el espacio de nombres de usuario.
  • size=TAMAÑO: para especificar un tamaño explícito para el espacio de nombres de usuario automático. Ej: --userns=auto:size=8192. Si no se especifica size, auto estima un tamaño para el espacio de nombres de usuario.
  • uidmapping=UID_CONTENEDOR:UID_ANFITRIÓN:TAMAÑO: para forzar que un mapeo de UID esté presente en el espacio de nombres de usuario.

El UID y GID del anfitrión en gidmapping y uidmapping pueden prefijarse opcionalmente con el símbolo @. En este caso, podman buscará el ID intermedio correspondiente al ID del anfitrión y mapeará el ID intermedio encontrado al ID del contenedor. Para más detalles, consulte --uidmap.

container:id: únete al espacio de nombres de usuario del contenedor especificado.

host o "" (cadena vacía): ejecuta en el espacio de nombres de usuario del llamador. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el anfitrión que cualquier otro proceso iniciado por el usuario que llama.

keep-id: crea un espacio de nombres de usuario donde el UID:GID del usuario actual se mapean a los mismos valores en el contenedor. Para contenedores creados por root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

En adición, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen a menos que establezca explícitamente --user.

Opciones válidas para keep-id:

  • uid=UID: anula el UID dentro del contenedor al que se mapea el usuario actual.
  • gid=GID: anula el GID dentro del contenedor al que se mapea el usuario actual.
  • size=SIZE: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No se soporta cuando se ejecuta como root.

nomap: crea un espacio de nombres de usuario donde el UID:GID del usuario actual sin root no se mapea al contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

ns:namespace: ejecuta el contenedor en el espacio de nombres de usuario existente dado.

Utiliza VARIANT en lugar de la variante de arquitectura predeterminada de la imagen del contenedor. Algunas imágenes pueden usar múltiples variantes de las arquitecturas arm, como arm/v5 y arm/v7.

--volume, -v=[[VOLUMEN-ORIGEN|DIRECTORIO-ANFITRIÓN:]DIRECTORIO-CONTENEDOR[:OPCIONES]]

Crea un montaje bind. Si se especifica -v /DIRECTORIO-ANFITRIÓN:/DIRECTORIO-CONTENEDOR, Podman monta /DIRECTORIO-ANFITRIÓN desde el anfitrión en /DIRECTORIO-CONTENEDOR en el contenedor de Podman. De manera similar, -v VOLUMEN-ORIGEN:/DIRECTORIO-CONTENEDOR monta el volumen con nombre desde el anfitrión en el contenedor. Si no existe dicho volumen con nombre, Podman crea uno. Si no se proporciona origen, el volumen se crea como un volumen con nombre anónimo con un nombre generado aleatoriamente, y se elimina cuando se elimina el contenedor a través del indicador --rm o el comando po

comando dman rm --volumes.

(Nota: al usar el cliente remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), los volúmenes se montan desde el servidor remoto, no necesariamente desde la máquina cliente).

El OPTIONS es una lista separada por comas y puede ser una o más de las siguientes opciones:

  • rw|ro
  • z|Z
  • [O]
  • [U]
  • [no]copy
  • [no]dev
  • [no]exec
  • [no]suid
  • [r]bind
  • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Footnote1⟩
  • idmap[=options]

El CONTAINER-DIR debe ser una ruta absoluta, como /src/docs. El volumen se monta en el contenedor en este directorio.

Si se especifica una fuente de volumen, debe ser una ruta en el host o el nombre de un volumen con nombre. Las rutas del host pueden ser absolutas o relativas; las rutas relativas se resuelven en relación con el directorio en el que se ejecuta Podman. Si la fuente no existe, Podman devuelve un error. Los usuarios deben pre-crear los archivos o directorios de origen.

Cualquier fuente que no comience con un . o / se trata como el nombre de un volumen con nombre. Si no existe un volumen con ese nombre, se crea. Los volúmenes creados con nombres no son anónimos, y no se eliminan con la opción --rm ni con el comando podman rm --volumes.

Especifique múltiples opciones -v para montar uno o más volúmenes en un contenedor.

Montajes de volumen protegidos contra escritura

Agregue la opción :ro o :rw para montar un volumen en modo de solo lectura o lectura/escritura, respectivamente. De forma predeterminada, los volúmenes se montan en modo lectura/escritura. Ver ejemplos.

Cambio de propietario de montajes de volumen

Cuando un volumen con nombre se monta por primera vez en un contenedor, Podman ajusta automáticamente la propiedad del punto de montaje del volumen durante la inicialización del contenedor. Esta operación de cambio de propietario ocurre bajo las siguientes condiciones:

  • El volumen aún no se ha utilizado (tiene NeedsChown establecido en true)
  • El volumen está vacío o aún no se ha copiado
  • El volumen no está gestionado por un controlador de volumen externo
  • El controlador de volumen no es "image"

Para volúmenes con montajes idmapped (que utilizan la opción idmap), el cambio de propiedad tiene en cuenta las asignaciones del espacio de nombres de usuario del contenedor, pero el volumen idmapped conserva la asignación UID/GID correcta. Para volúmenes sin idmapping, el punto de montaje se cambia de propietario para que coincida con el usuario y grupo del proceso del contenedor, mapeado al espacio de nombres de usuario del host si la reasignación del espacio de nombres de usuario está habilitada.

Si un contenedor se crea en un nuevo espacio de nombres de usuario, el UID y el GID del contenedor pueden corresponder a otro UID y GID en el host.

El sufijo :U indica a Podman que utilice el UID y GID correctos del host basándose en el UID y GID dentro del contenedor, para cambiar recursivamente el propietario y el grupo del volumen de origen. El cambio de propietario recorre el sistema de archivos bajo el volumen y cambia el UID/GID de cada archivo. Si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, lo que retrasa el inicio del contenedor.

Advertencia: úselo con precaución, ya que esto modifica el sistema de archivos del host.

Etiquetado de montajes de volumen

Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. De forma predeterminada, Podman no cambia las etiquetas establecidas por el sistema operativo.

Para cambiar una etiqueta en el contexto del contenedor, agregue uno de los dos sufijos :z o :Z al montaje del volumen. Estos sufijos indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z indica a Podman que dos o más contenedores comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartidas permiten que todos los contenedores lean/escriban contenido. La opción Z indica a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el contenedor actual puede usar un volumen privado.

Nota: todos los contenedores dentro de un pod comparten la misma etiqueta SELinux. Esto significa que todos los contenedores dentro de dicho pod pueden leer/escribir volúmenes compartidos en el contenedor creado con :Z en cualquiera de los contenedores. Volver a etiquetar recorre el sistema de archivos bajo el volumen y cambia la etiqueta de cada archivo; si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, lo que retrasa el inicio del contenedor. Si el volumen se volvió a etiquetar previamente con la opción z, Podman está optimizado para no volver a etiquetar una segunda vez. Si se mueven archivos al volumen, las etiquetas se pueden cambiar manualmente con el comando chcon -Rt container_file_t PATH.

Nota: No vuelva a etiquetar archivos y directorios del sistema. Volver a etiquetar contenido del sistema podría hacer que otros servicios confinados en la máquina fallen. Para este tipo de contenedores, recomendamos deshabilitar la separación de SELinux. La opción --security-opt label=disable deshabilita la separación de SELinux para el contenedor. Por ejemplo, si un usuario quisiera montar su directorio personal completo en un contenedor, necesitaría deshabilitar la separación de SELinux.

$ podman create --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

Montajes de volumen overlay

El indicador :O le dice a Podman que monte el directorio del host como almacenamiento temporal utilizando el sistema de archivos overlay. Los procesos del contenedor pueden modificar el contenido dentro del punto de montaje, que se almacena en el almacenamiento del contenedor en un directorio separado. En términos de overlay, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el contenedor finaliza su ejecución, de forma similar a como se desmonta un punto de montaje tmpfs.

Para usuarios avanzados, la opción overlay también admite upperdir y workdir personalizados no volátiles para el montaje overlay. Los upperdir y workdir personalizados pueden ser gestionados completamente por los propios usuarios, y Podman no los elimina al finalizar el ciclo de vida. Ejemplo: :O,upperdir=/some/upper,workdir=/some/work

Ejecuciones posteriores del contenedor ven el contenido del directorio de origen original; cualquier cambio de ejecuciones de contenedor anteriores ya no existe.

Un caso de uso del montaje overlay es compartir la caché de paquetes del host en el contenedor para acelerar las compilaciones.

Nota: El indicador O entra en conflicto con otras opciones enumeradas anteriormente.

El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor. Por lo general, los contenedores pueden leer/ejecutar container_share_t y pueden leer/escribir container_file_t. Si no se pueden cambiar las etiquetas en un volumen de origen, se debe deshabilitar la separación del contenedor SELinux para que el contenedor funcione.

No modifique el directorio de origen montado en el contenedor con un montaje overlay; puede causar fallos inesperados. Modifique el directorio solo después de que el contenedor termine de ejecutarse.

Propagación de montajes

De forma predeterminada, los volúmenes montados por enlace son privados. Esto significa que cualquier montaje realizado dentro del contenedor no es visible en el host y viceversa. Uno puede cambiar este comportamiento especificando una propiedad de propagación de montaje de volumen. Cuando un volumen está compartido, los montajes realizados dentro del contenedor son visibles en el host y viceversa. Hacer que un volumen sea esclavo[1] ⟨#Footnote1⟩ habilita la propagación de montaje unidireccional: los montajes realizados en el host bajo ese volumen son visibles dentro del contenedor, pero no al revés.

Para controlar la propiedad de propagación de montaje de un volumen, puede utilizar el indicador de propagación [r]shared, [r]slave, [r]private o [r]unbindable. La propiedad de propagación se puede especificar solo para volúmenes montados por enlace y no para volúmenes internos o volúmenes con nombre. Para que la propagación de montaje funcione, el punto de montaje de origen (el punto de montaje donde se monta el directorio de origen) debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe estar compartido. Y para volúmenes esclavos, el punto de montaje de origen debe ser compartido o esclavo. [1] ⟨#Footnote1⟩

Para montar recursivamente un volumen y todos sus submontajes en un contenedor, use la opción rbind. De forma predeterminada, se utiliza la opción bind, y los submontajes del directorio de origen no se montan en el contenedor.

Montar el volumen con una opción copy le dice a Podman que copie el contenido del directorio de destino subyacente en volúmenes internos recién creados. La copia solo ocurre en la creación inicial del volumen. El contenido no se copia cuando el volumen se utiliza posteriormente en contenedores diferentes. La opción copy se ignora en los montajes bind y no tiene ningún efecto.

Montar volúmenes con las opciones nosuid significa que los ejecutables SUID en el volumen no pueden ser utilizados por las aplicaciones para cambiar sus privilegios. De forma predeterminada, los volúmenes se montan con nosuid.

Montar el volumen con la opción noexec significa que no se pueden ejecutar ejecutables en el volumen dentro del contenedor.

Montar el volumen con la opción nodev significa que los procesos dentro del contenedor no pueden utilizar dispositivos en el volumen. De forma predeterminada, los volúmenes se montan con nodev.

Si el HOST-DIR es un punto de montaje, el kernel ignora las opciones dev, suid y exec.

Utilice df HOST-DIR para determinar el montaje de origen, luego utilice findmnt -o TARGET,PROPAGATION source-mount-dir para determinar las propiedades de propagación del montaje de origen. Si la utilidad findmnt(1) no está disponible, entonces se puede consultar la entrada de montaje para el punto de montaje de origen en /proc/self/mountinfo. Mire los "campos opcionales" y vea si se especifican propiedades de propagación. Allí, shared:N significa que el montaje está compartido, master:N significa que el montaje es esclavo, y si no hay nada, el montaje es privado. [1] ⟨#Footnote1⟩

Para cambiar las propiedades de propagación de un punto de montaje, utilice el comando mount(8). Por ejemplo, si uno quiere montar por enlace el directorio de origen /foo, puede hacer mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convierte /foo en un punto de montaje compartido. Alternativamente, se pueden cambiar directamente las propiedades de propagación del montaje de origen. Supongamos que / es el montaje de origen para /foo, entonces use mount --make-shared / para convertir / en un montaje compartido.

Nota: si el usuario solo tiene derechos de acceso a través de un grupo, el acceso al volumen desde un contenedor sin root falla.

Labeling systems like SELinux require that proper labels are placed on volume content mounted into a container. Without a label, the security system might prevent the processes running inside the container from using the content. By default, Podman does not change the labels set by the OS.

EXAMPLES

Create a container using a local image:

$ podman create alpine ls

Create a container using a local image and annotate it:

$ podman create --annotation HELLO=WORLD alpine ls

Create a container using a local image, allocating a pseudo-TTY, keeping stdin open and name it myctr:

  podman create -t -i --name myctr alpine ls

Running a container in a new user namespace requires a mapping of the UIDs and GIDs from the host:

$ podman create --uidmap 0:30000:7000 --gidmap 0:30000:7000 fedora echo hello

Setting automatic user-namespace separated containers:

# podman create --userns=auto:size=65536 ubi8-init

Configure the timezone in a container:

$ podman create --tz=local alpine date
$ podman create --tz=Asia/Shanghai alpine date
$ podman create --tz=US/Eastern alpine date

Ensure the first container (container1) is running before the second container (container2) is started:

$ podman create --name container1 -t -i fedora bash
$ podman create --name container2 --requires container1 -t -i fedora bash
$ podman start --attach container2

Create a container which requires multiple containers:

$ podman create --name container1 -t -i fedora bash
$ podman create --name container2 -t -i fedora bash
$ podman create --name container3 --requires container1,container2 -t -i fedora bash
$ podman start --attach container3

Expose shared libraries inside of container as read-only using a glob:

$ podman create --mount type=glob,src=/usr/lib64/libnvidia\*,ro -i -t fedora /bin/bash

Create a container allowing supplemental groups to have access to the volume:

$ podman create -v /var/lib/design:/var/lib/design --group-add keep-groups ubi8

Configure execution domain for containers using the personality option:

$ podman create --name container1 --personality=LINUX32 fedora bash

Create a container with external rootfs mounted as an overlay:

$ podman create --name container1 --rootfs /path/to/rootfs:O bash

Create a container connected to two networks (called net1 and net2) with a static ip:

$ podman create --network net1:ip=10.89.1.5 --network net2:ip=10.89.10.10 alpine ip addr

Rootless Containers

Podman runs as a non-root user on most systems. This feature requires that a new enough version of shadow-utils be installed. The shadow-utils package must include the newuidmap and newgidmap executables.

In order for users to run rootless, there must be an entry for their username in /etc/subuid and /etc/subgid which lists the UIDs for their user namespace.

Rootless Podman works better if the fuse-overlayfs and slirp4netns packages are installed. The fuse-overlayfs package provides a userspace overlay storage driver, otherwise users need to use the vfs storage driver, which can be disk space expensive and less performant than other drivers.

To enable VPN on the container, slirp4netns or pasta needs to be specified; without either, containers need to be run with the --network=host flag.

ENVIRONMENT

Environment variables within containers can be set using multiple different options: This section describes the precedence.

Precedence order (later entries override earlier entries):

  • --env-host : Host environment of the process executing Podman is added.
  • --http-proxy: By default, several environment variables are passed in from the host, such as http_proxy and no_proxy. See --http-proxy for details.
  • Container image : Any environment variables specified in the container image.
  • --env-file : Any environment variables specified via env-files. If multiple files specified, then they override each other in order of entry.
  • --env : Any environment variables specified overrides previous settings.

Create containers and set the environment ending with a *. The trailing * glob functionality is only active when no value is specified:

$ export ENV1=a
$ podman create --name ctr1 --env 'ENV*' alpine env
$ podman start --attach ctr1 | grep ENV
ENV1=a
$ podman create --name ctr2 --env 'ENV*=b' alpine env
$ podman start --attach ctr2 | grep ENV
ENV*=b

CONMON

When Podman starts a container it actually executes the conmon program, which then executes the OCI Runtime. Conmon is the container monitor. It is a small program whose job is to watch the primary process of the container, and if the container dies, save the exit code. It also holds open the tty of the container, so that it can be attached to later. This is what allows Podman to run in detached mode (backgrounded), so Podman can exit but conmon continues to run. Each container has their own instance of conmon. Conmon waits for the container to exit, gathers and saves the exit code, and then launches a Podman process to complete the container cleanup, by shutting down the network and storage. For more information about conmon, see the conmon(8) man page.
