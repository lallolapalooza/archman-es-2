NOMBRE

podman-pod-clone - Crear una copia de un pod existente

SINOPSIS

podman pod clone [opciones] pod nombre

DESCRIPCIÓN

podman pod clone crea una copia de un pod, recreando la configuración idéntica para el pod y para todos sus contenedores. Los usuarios pueden modificar el nuevo nombre del pod y seleccionar detalles del pod dentro del contenedor de infraestructura

OPCIONES

--blkio-weight=peso

Peso relativo de I/O de bloque. El peso es un valor entre 10 y 1000.

Esta opción no está soportada en sistemas rootless cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo de I/O de bloque por dispositivo.

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se crea el cgroup para el pod. Si la ruta no es absoluta, se considera relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen.

--cpu-shares, -c=participaciones

Participaciones de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de la CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso predeterminado es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU sobrante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una participación de CPU de 1024 y otros dos tienen un ajuste de participación de CPU de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se agrega un cuarto contenedor con una participación de CPU de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las participaciones de tiempo de CPU se distribuyen en todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de participaciones de CPU:

PID contenedor CPU Participación de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no está soportada en sistemas rootless cgroups V1.

--cpus

Establece un número de CPUs para el pod que anula los límites de CPU del pod original. Si no se especifica ninguno, se utilizan los Nano CPUs del pod original.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de ellos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no está soportada en sistemas rootless cgroups V1.

Si no se especifica ninguno, se utiliza el cpuset del pod original.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), use --cpuset-mems=0,1 entonces los procesos en el contenedor solo usan memoria de los dos primeros nodos de memoria.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no está soportada en sistemas rootless cgroups V1.

--destroy

Eliminar el pod original que estamos clonando una vez utilizado para imitar la configuración.

--device=dispositivo-host[:dispositivo-contenedor][:permisos]

Añade un dispositivo host al pod. El permisos opcional parámetro se puede usar para especificar permisos del dispositivo combinando r para leer, w para escribir y m para mknod(2).

Ejemplo: --device=/dev/sdc:/dev/xvdc:rwm.

Nota: si dispositivo-host es un enlace simbólico, primero se resuelve. El pod solo almacena los números mayor y menor del dispositivo host.

Podman puede cargar módulos del kernel necesarios para usar el dispositivo especificado. Los dispositivos para los que Podman carga módulos cuando es necesario son: /dev/fuse.

En modo rootless, el nuevo dispositivo se monta bind en el contenedor desde el host en lugar de que Podman lo cree dentro del espacio del contenedor. Dado que el montaje bind conserva su etiqueta SELinux en sistemas SELinux, el contenedor puede recibir un error de permiso al acceder al dispositivo montado. Modifique la configuración de SELinux para permitir que los contenedores usen todas las etiquetas de dispositivo con el siguiente comando:

$ sudo setsebool -P container_use_devices=true

Nota: el pod implementa dispositivos almacenando la configuración inicial pasada por el usuario y recreando el dispositivo en cada contenedor añadido al pod.

--device-read-bps=ruta:tasa

Limita la tasa de lectura (en bytes por segundo) desde un dispositivo (por ejemplo, --device-read-bps=/dev/sda:1mb).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no está soportada en sistemas rootless cgroups V1.

--device-write-bps=ruta:tasa

Limita la tasa de escritura (en bytes por segundo) a un dispositivo (por ejemplo, --device-write-bps=/dev/sda:1mb).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, ver https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no está soportada en sistemas rootless cgroups V1.

--gidmap=pod_gid:host_gid:cantidad

Mapa GID para el espacio de nombres de usuario. El uso de esta bandera ejecuta todos los contenedores en el pod con el espacio de nombres de usuario habilitado. Entra en conflicto con las banderas --userns y --subgidname.

--gpus=ENTRADA

Dispositivos GPU a añadir al contenedor ('all' para pasar todas las GPUs) Actualmente solo se admiten dispositivos Nvidia.

--help,

-h

Imprime el mensaje de uso.

--hostname=nombre

Establece el nombre de host del pod dentro de todos los contenedores.

El nombre de host proporcionado también se agrega al archivo /etc/hosts utilizando la dirección IP principal del contenedor (consulte también la opción --add-host).

--infra-command=comando

El comando que se ejecuta para iniciar el contenedor de infraestructura. Por defecto: "/pause".

--infra-conmon-pidfile=archivo

Escribe el PID del proceso conmon del contenedor de infraestructura en un archivo. Dado que conmon se ejecuta en un proceso separado de Podman, esto es necesario cuando se utiliza systemd para gestionar contenedores y pods de Podman.

--infra-name=nombre

El nombre que se utiliza para el contenedor de infraestructura del pod.

--label, -l=clave=valor

Agrega metadatos a un pod.

--label-file=archivo

Lee las etiquetas de un archivo delimitado por saltos de línea.

--memory, -m=número[unidad]

Límite de memoria. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Permite limitar la memoria disponible para un contenedor. Si el host admite memoria de intercambio (swap), el ajuste de memoria -m puede ser mayor que la RAM física. Si se especifica un límite de 0 (sin usar -m), la memoria del contenedor no tiene límite. El límite real puede redondearse al múltiplo del tamaño de página del sistema operativo (el valor es muy grande, son millones de billones).

Esta opción no es compatible con sistemas sin root en cgroups V1.

--memory-swap=número[unidad]

Un valor límite igual a la memoria más el intercambio (swap). Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Debe usarse junto con el indicador -m (--memory). El valor del argumento debe ser mayor que el de
-m (--memory). Por defecto, se establece en el doble del valor de --memory.

Establezca el número en -1 para habilitar el intercambio (swap) ilimitado.

Esta opción no es compatible con sistemas sin root en cgroups V1.

--name, -n

Establece un nombre personalizado para el pod clonado. El valor predeterminado si no se especifica es de la sintaxis: <NOMBRE_ORIGINAL>-clone

--pid=pid

Establece el modo PID para el pod. El valor predeterminado es crear un espacio de nombres PID privado para el pod. Requiere que el espacio de nombres PID se comparta a través de --share.

host: usa el espacio de nombres PID del host para el pod
ns: únete al espacio de nombres PID especificado
private: crea un nuevo espacio de nombres para el pod (predeterminado)

--restart=política

Política de reinicio a seguir cuando los contenedores se cierran. La política de reinicio no tiene efecto si un contenedor se detiene mediante los comandos podman kill o podman stop.

Los valores válidos de política son:

  • no: No reiniciar los contenedores al salir.
  • never: Sinónimo de no; no reiniciar los contenedores al salir.
  • on-failure[:max_retries]: Reiniciar los contenedores cuando se cierran con un código de salida distinto de cero, reintentando indefinidamente o hasta que se alcance el número opcional de reintentos max_retries.
  • always: Reiniciar los contenedores al salir, independientemente del estado, reintentando indefinidamente.
  • unless-stopped: Idéntico a always.

Podman proporciona un archivo de unidad de systemd, podman-restart.service, que reinicia los contenedores después de un reinicio del sistema.

Al ejecutar contenedores en servicios de systemd, utilice la funcionalidad de reinicio proporcionada por systemd. En otras palabras, no utilice esta opción en una unidad de contenedor; en su lugar, establezca la directiva Restart= de systemd en la sección [Service]. Consulte podman-systemd.unit(5) y systemd.service(5).

Política de reinicio predeterminada para todos los contenedores de un pod.

--security-opt=opción

Opciones de seguridad

  • apparmor=unconfined: Desactiva la limitación de apparmor para el pod.
  • apparmor=perfil-alternativo: Establece el perfil de limitación de apparmor para el pod.
  • label=user:USUARIO: Establece el usuario de etiqueta para los procesos del pod.
  • label=role:ROL: Establece el rol de etiqueta para los procesos del pod.
  • label=type:TIPO: Establece el tipo de proceso de etiqueta para los procesos del pod.
  • label=level:NIVEL: Establece el nivel de etiqueta para los procesos del pod.
  • label=filetype:TIPO: Establece el tipo de archivo de etiqueta para los archivos del pod.
  • label=disable: Desactiva la separación de etiquetas para el pod.

Nota: El etiquetado se puede desactivar para todos los pods/contenedores estableciendo label=false en el archivo containers.conf (/etc/containers/containers.conf o $HOME/.config/containers/containers.conf).

  • label=nested: Permite modificaciones de SELinux dentro del contenedor. Se permite a los contenedores modificar las etiquetas SELinux en archivos y procesos, siempre que la política SELinux lo permita. Sin nested, los contenedores ven SELinux como deshabilitado, incluso cuando está habilitado en el host. Se impide que los contenedores establezcan cualquier etiqueta.
  • mask=/ruta/1:/ruta/2: Las rutas a enmascarar separadas por dos puntos. Una ruta enmascarada no se puede acceder dentro de los contenedores del pod.
  • no-new-privileges: Desactiva que los procesos del contenedor obtengan privilegios adicionales a través de la llamada al sistema execve(2) (por ejemplo, a través de bits setuid o setgid, o a través de capacidades de archivo). Los programas que dependen de los bits setuid/setgid en su ejecutable para cambiar el ID de usuario o ID de grupo ya no pueden hacerlo, y cualquier capacidad de archivo añadida al ejecutable (por ejemplo, mediante setcap) no se añade al conjunto de capacidades permitidas. Para más detalles, véase: https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined: Desactiva la limitación de seccomp para el pod.
  • seccomp=profile.json: Archivo JSON que se utilizará como filtro seccomp. Tenga en cuenta que la anotación io.podman.annotations.seccomp se establece con el valor especificado, como se muestra en podman inspect.
  • proc-opts=OPCIONES: Lista de opciones separadas por comas para usar en el montaje /proc. Más detalles sobre las posibles opciones de montaje se especifican en la página man de proc(5).
  • unmask=ALL o /ruta/1:/ruta/2, o rutas expandidas por shell (/proc/*): Rutas a desenmascarar separadas por dos puntos. Si se establece en ALL, desenmascara todas las rutas que están enmascaradas o hechas de solo lectura por defecto. Las rutas enmascaradas por defecto son /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware y /sys/fs/selinux, /sys/devices/virtual/powercap. Las rutas que por defecto son de solo lectura son /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

Nota: El etiquetado se puede desactivar para todos los contenedores estableciendo label=false en el archivo containers.conf(5).

--shm-size=número[unidad]

Tamaño de /dev/shm. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes). Si la unidad se omite, el sistema utiliza bytes. Si el tamaño se omite, el valor predeterminado es 64m. Cuando el tamaño es 0, no hay límite en la cantidad de memoria utilizada para IPC por el pod. Esta opción entra en conflicto con --ipc=host.

--shm-size-systemd=número[unidad]

Tamaño de los montajes tmpfs específicos de systemd, como /run, /run/lock, /var/log/journal y /tmp. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes). Si la unidad se omite, el sistema utiliza bytes. Si el tamaño se omite, el valor predeterminado es 64m. Cuando el tamaño es 0, el uso se limita al 50% de la memoria disponible del host.

Ejecuta todos los contenedores del pod en un nuevo espacio de nombres de usuario utilizando el mapeo proporcionado. Esta opción entra en conflicto con las opciones --userns y --subuidname. --userns=modo

Establece el modo del espacio de nombres de usuario.

de for all the containers in a pod. It defaults to the PODMAN_USERNS environment variable. An empty value ("") means user namespaces are disabled.

Rootless user --userns=Key mappings:

Key Host User Container User
"" $UID 0 (Default User account mapped to root user in container.)
host $UID 0 (Default User account mapped to root user in container.)
keep-id $UID $UID (Map user account to same UID within container.)
auto $UID nil (Host User UID is not mapped into container.)
nomap $UID nil (Host User UID is not mapped into container.)

Valid mode values are:

•
auto[:OPTIONS,...]: automatically create a namespace. It is possible to specify these options to auto:
  • gidmapping=CONTAINER_GID:HOST_GID:SIZE to force a GID mapping to be present in the user namespace.
  • size=SIZE: to specify an explicit size for the automatic user namespace. e.g. --userns=auto:size=8192. If size is not specified, auto estimates the size for the user namespace.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE to force a UID mapping to be present in the user namespace.
  • host: run in the user namespace of the caller. The processes running in the container have the same privileges on the host as any other process launched by the calling user (default).
  • keep-id: creates a user namespace where the current rootless user's UID:GID are mapped to the same values in the container. This option is not allowed for containers created by the root user.
  • nomap: creates a user namespace where the current rootless user's UID:GID are not mapped into the container. This option is not allowed for containers created by the root user.

--uts=mode

Set the UTS namespace mode for the pod. The following values are supported:

  • host: use the host's UTS namespace inside the pod.
  • private: create a new namespace for the pod (default).
  • ns:[path]: run the pod in the given existing UTS namespace.

--volume, -v=[[SOURCE-VOLUME|HOST-DIR:]CONTAINER-DIR[:OPTIONS]]

Create a bind mount. If -v /HOST-DIR:/CONTAINER-DIR is specified, Podman bind mounts /HOST-DIR from the host into /CONTAINER-DIR in the Podman container. Similarly, -v SOURCE-VOLUME:/CONTAINER-DIR mounts the named volume from the host into the container. If no such named volume exists, Podman creates one. If no source is given, the volume is created as an anonymously named volume with a randomly generated name, and is removed when the pod is removed via the --rm flag or the podman rm --volumes command.

(Note when using the remote client, including Mac and Windows (excluding WSL2) machines, the volumes are mounted from the remote server, not necessarily the client machine.)

The OPTIONS is a comma-separated list and can be one or more of:

  • rw|ro
  • z|Z
  • [O]
  • [U]
  • [no]copy
  • [no]dev
  • [no]exec
  • [no]suid
  • [r]bind
  • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Footnote1⟩
  • idmap[=options]

The CONTAINER-DIR must be an absolute path such as /src/docs. The volume is mounted into the container at this directory.

If a volume source is specified, it must be a path on the host or the name of a named volume. Host paths are allowed to be absolute or relative; relative paths are resolved relative to the directory Podman is run in. If the source does not exist, Podman returns an error. Users must pre-create the source files or directories.

Any source that does not begin with a . or / is treated as the name of a named volume. If a volume with that name does not exist, it is created. Volumes created with names are not anonymous, and they are not removed by the --rm option and the podman rm --volumes command.

Specify multiple -v options to mount one or more volumes into a pod.

Write Protected Volume Mounts

Add :ro or :rw option to mount a volume in read-only or read-write mode, respectively. By default, the volumes are mounted read-write. See examples.

Chowning Volume Mounts

When a named volume is first mounted to a container, Podman automatically adjusts the ownership of the volume's mount point during container initialization. This chown operation occurs under the following conditions:

  • The volume was not used yet (has NeedsChown set to true)
  • The volume is empty or has not been copied up yet
  • The volume is not managed by an external volume driver
  • The volume driver is not "image"

For volumes with idmapped mounts (using the idmap option), the ownership change takes into account the container's user namespace mappings, but the idmapped volume retains proper UID/GID mapping. For volumes without idmapping, the mount point is chowned to match the container's process user and group, mapped to the host user namespace if user namespace remapping is enabled.

If a pod is created in a new user namespace, the UID and GID in the container may correspond to another UID and GID on the host.

The :U suffix tells Podman to use the correct host UID and GID based on the UID and GID within the pod, to change recursively the owner and group of the source volume. Chowning walks the file system under the volume and changes the UID/GID on each file. If the volume has thousands of inodes, this process takes a long time, delaying the start of the pod.

Warning use with caution since this modifies the host filesystem.

Labeling Volume Mounts

Labeling systems like SELinux require that proper labels are placed on volume content mounted into a pod. Without a label, the security system might prevent the processes running inside the pod from using the content. By default, Podman does not change the labels set by the OS.

To change a label in the pod context, add either of two suffixes :z or :Z to the volume mount. These suffixes tell Podman to relabel file objects on the shared volumes. The z option tells Podman that two or more pods share the volume content. As a result, Podman labels the content with a shared content label. Shared volume labels allow all containers to read/write content. The Z option tells Podman to label the content with a private unshared label. Only the current pod can use a private volume.

Note: all containers within a pod share the same SELinux label. This means all containers within said pod can read/write volumes shared into the container created with the :Z on any one of the containers. Relabeling walks the file system under the volume and changes the label on each file; if the volume has thousands of inodes, this process takes a long time, delaying the start of the pod. If the volume was previously relabeled with the z option, Podman is optimized to not relabel a second time. If files are moved into the volume, then the labels can be manually changed with the chcon -Rt container_file_t PATH command.

Note: Do not relabel system files and directories. Relabeling system content might cause other confined services on the machine to fail. For these types of containers we recommend disabling SELinux separation. The option --security-opt label=disable disables SELinux separation for the pod. For example if a user wanted to volume mount their entire home directory into a pod, they need to disable SELinux separation.

$ podman pod clone --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

Overlay Volume Mounts

The :O flag tells Podman to mount the directory from the host as a temporary storage using the overlay file system. The pod processes can modify content within the mountpoint which is stored in the container storage in a separate directory. In overlay terms, the source directory is the lower, and the container storage directory is the upper. Modifications to the mount point are destroyed when the pod finishes executing, similar to a tmpfs mount point being unmounted.

For advanced users, the overlay option also supports custom non-volatile upperdir and workdir for the overlay mount. Custom upperdir and workdir can be fully managed by the users themselves, and Podman does not remove it on lifecycle completion. Example :O,upperdir=/some/upper,workdir=/some/work

Subsequent executions of the container sees the original source directory content, any changes from previous pod executions no longer exist.

One use case of the overlay mount is sharing the package cache from the host into the container to allow speeding up builds.

Note: The O flag conflicts with other options listed above.

Content mounted into the container is labeled with the private label. On SELinux systems, labels in the source directory must be readable by the pod infra container label. Usually containers can read/execute container_share_t and can read/write container_file_t. If unable to change the labels on a source volume, SELinux container separation must be disabled for the pod or infra container to work.

Do not modify the source directory mounted into the pod with an overlay mount, it can cause unexpected failures. Only modify the directory after the container finishes running.

Mounts propagation

By default, bind-mounted volumes are private. That means any mounts done inside the pod are not visible on the host and vice versa. One can change this behavior by specifying a volume mount propagation property. When a volume is shared, mounts done under that volume inside the pod are visible on host and vice versa. clone a pod

SYNOPSIS

podman pod clone [--authfile=path] [--cert-dir=path] [--cgroup-manager=cgroupfs|systemd] [--cpu-period=value] [--cpu-shares=value] [--cpus=value] [--cpuset-cpus=value] [--cpuset-mems=value] [--destroy] [--gidmap=value] [--group=value] [--help] [--hooks-dir=path] [--http-auth-file=path] [--ip=value] [--kernel-memory=value] [--label=[KEY=VALUE] ... ] [--log-level=value] [--mac-address=value] [--memory=value] [--memory-reservation=value] [--memory-swap=value] [--nameserver=value] [--network=value] [--no-hosts] [--oom-score-adj=value] [--pod-id-file=path] [--preserve-fds=[]] [--privileged] [--pull=value] [--quiet] [--read-only] [--restart=value] [--rm] [--sdnotify=value] [--sysctl=*key=value] [--timeout=value] [--tz=value] [--uidmap=value] [--ulimit=value] [--uts] [--volume=value] [--volumes-from=CONTAINER[:OPTIONS]] [--variant=value] [--version] [--workdir=value] POD [POD...]

DESCRIPTION

Clones one or more specified pods to new pods. This command is useful for creating a new pod with the same configuration as an existing pod. The command allows for modification of certain pod settings during the clone process.

OPTIONS

The options for podman pod clone are the same as the options for podman-pod-create(1), with the addition of the --destroy option.

--destroy

Destroys the source pod after a successful clone. Use this option with caution as it will permanently remove the original pod.

The following options are specific to volume mounting and are relevant when cloning pods that involve volumes:

--volume, -v

Bind mount a volume into the pod. The format is [HOST-DIR:]CONTAINER-DIR[:OPTIONS].

The OPTIONS are a comma-separated list and can be one of the following:

  • bind: This is the default propagation mode for bind mounts. It means that mounts within the source directory are not shared with the container.
  • bind-propagation=MODE: Set the propagation property of a bind mount. MODE can be one of shared, slave, private, or unbindable.
    • shared: Mounts within the source directory are shared with the container, and vice versa.
    • slave: Mounts within the source directory are propagated to the container, but not vice versa.
    • private: Mounts within the source directory are not shared with the container.
    • unbindable: Mounts within the source directory cannot be unmounted.
  • copy: Copy content from the source directory to a new volume. This option is only effective when creating a new internal volume. It is ignored for bind mounts.
  • copy-up: Copy up content from a container to a volume. This option is only effective for containers that are created with the --volume option and not for pods.
  • bind-recursive: Recursively mount a volume and all of its submounts into a pod. This is equivalent to using the rbind option.
  • nonrecursive: Do not recursively mount submounts. This is the default behavior.
  • nosuid: Do not allow SUID or SGID bits to take effect.
  • nodev: Do not allow devices from the source directory to be mounted in the container.
  • noexec: Do not allow executables to be run from the source directory.
  • rw: Mount the volume in read-write mode. This is the default.
  • ro: Mount the volume in read-only mode.
  • z: SELinux label for shared content. This option should be used when multiple containers share the same volume.
  • Z: SELinux label for private content. This option should be used when only one container uses the volume.
  • idmap: Create an idmapped mount to the target user namespace in the container. The idmap option supports a custom mapping that can be different than the user namespace used by the container. The mapping can be specified after the idmap option like: idmap=uids=0-1-10#10-11-10;gids=0-100-10. For each triplet, the first value is the start of the backing file system IDs that are mapped to the second value on the host. The length of this mapping is given in the third value. Multiple ranges are separated with # .

Propagation property can be specified only for bind mounted volumes and not for internal volumes or named volumes. For mount propagation to work, the source mount point (the mount point where source dir is mounted on) must have the right propagation properties. For shared volumes, the source mount point must be shared. And for slave volumes, the source mount point must be either shared or slave. [1]

To recursively mount a volume and all of its submounts into a pod, use the rbind option. By default the bind option is used, and submounts of the source directory is not mounted into the pod.

Mounting the volume with a copy option tells podman to copy content from the underlying destination directory onto newly created internal volumes. The copy only happens on the initial creation of the volume. Content is not copied up when the volume is subsequently used on different containers. The copy option is ignored on bind mounts and has no effect.

Mounting volumes with the nosuid options means that SUID executables on the volume can not be used by applications to change their privilege. By default volumes are mounted with nosuid.

Mounting the volume with the noexec option means that no executables on the volume can be executed within the pod.

Mounting the volume with the nodev option means that no devices on the volume can be used by processes within the pod. By default volumes are mounted with nodev.

If the HOST-DIR is a mount point, then dev, suid, and exec options are ignored by the kernel.

Use df HOST-DIR to figure out the source mount, then use findmnt -o TARGET,PROPAGATION source-mount-dir to figure out propagation properties of source mount. If findmnt(1) utility is not available, then one can look at the mount entry for the source mount point in /proc/self/mountinfo. Look at the "optional fields" and see if any propagation properties are specified. In there, shared:N means the mount is shared, master:N means mount is slave, and if nothing is there, the mount is private. [1]

To change propagation properties of a mount point, use mount(8) command. For example, if one wants to bind mount source directory /foo, one can do mount --bind /foo /foo and mount --make-private --make-shared /foo. This converts /foo into a shared mount point. Alternatively, one can directly change propagation properties of source mount. Say / is source mount for /foo, then use mount --make-shared / to convert / into a shared mount.

Note: if the user only has access rights via a group, accessing the volume from inside a rootless pod fails.

Idmapped mount

If idmap is specified, create an idmapped mount to the target user namespace in the container. The idmap option supports a custom mapping that can be different than the user namespace used by the container. The mapping can be specified after the idmap option like: idmap=uids=0-1-10#10-11-10;gids=0-100-10. For each triplet, the first value is the start of the backing file system IDs that are mapped to the second value on the host. The length of this mapping is given in the third value. Multiple ranges are separated with #.

--volumes-from=CONTAINER[:OPTIONS]

Mount volumes from the specified container(s). Used to share volumes between containers and pods. The options is a comma-separated list with the following available elements:

  • rw|ro
  • z

Mounts already mounted volumes from a source container onto another pod. CONTAINER may be a name or ID. To share a volume, use the --volumes-from option when running the target container. Volumes can be shared even if the source container is not running.

By default, Podman mounts the volumes in the same mode (read-write or read-only) as it is mounted in the source container. This can be changed by adding a ro or rw option.

Labeling systems like SELinux require that proper labels are placed on volume content mounted into a pod. Without a label, the security system might prevent the processes running inside the container from using the content. By default, Podman does not change the labels set by the OS.

To change a label in the pod context, add z to the volume mount. This suffix tells Podman to relabel file objects on the shared volumes. The z option tells Podman that two entities share the volume content. As a result, Podman labels the content with a shared content label. Shared volume labels allow all containers to read/write content.

If the location of the volume from the source container overlaps with data residing on a target pod, then the volume hides that data on the target.

EXAMPLES

Clone the specified pod to a new pod.

# podman pod clone pod-name
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584

Clone the specified pod to a new pod with a new name.

# podman pod clone pod-name --name=cloned-pod
d0cf1f782e2ed67e8c0050ff92df865a039186237a4df24d7acba5b1fa8cc6e7
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584

Clone and remove the specified pod to a new pod, modifying its cpus.

# podman pod clone --destroy --cpus=5 d0cf1
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584

Clone the specified pod to a new named pod.

# podman pod clone 2d4d4fca7219b4437e0d74fcdc272c4f031426a6eacd207372691207079551de new_name
5a9b7851013d326aa4ac4565726765901b3ecc01fcbc0f237bc7fd95588a24f9

Clone a pod with memory limits.

# podman pod clone --memory=1g --memory-swap=2g pod-name
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584

Clone a pod with CPU limits.

# podman pod clone --cpus=2.5 --cpu-shares=1024 pod-name
6b2c73ff8a1982828c9ae2092954bcd59836a131960f7e05221af9df5939c584
