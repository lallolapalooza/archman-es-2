NOMBRE

podman-run - Ejecutar un comando en un nuevo contenedor

SINOPSIS

podman run [opciones] imagen [comando [arg ...]]

podman container run [opciones] imagen [comando [arg ...]]

DESCRIPCIÓN

Ejecuta un proceso en un nuevo contenedor. podman run inicia un proceso con su propio sistema de archivos, su propia red y su propio árbol de procesos aislado. La imagen que inicia el proceso puede definir valores predeterminados relacionados con el proceso que se ejecutará en el contenedor, la red a exponer y más, pero podman run otorga el control final al operador o administrador que inicia el contenedor a partir de la imagen. Por esa razón, podman run tiene más opciones que cualquier otro comando de Podman.

Si la imagen aún no está cargada, podman run descargará la imagen y todas sus dependencias del repositorio, de la misma manera que lo haría ejecutando podman pull imagen, antes de iniciar el contenedor a partir de esa imagen.

Varios archivos se crearán automáticamente dentro del contenedor. Estos incluyen /etc/hosts, /etc/hostname y /etc/resolv.conf para administrar la red. Estos se basarán en la versión del host de los archivos, aunque se pueden personalizar con opciones (por ejemplo, --dns puede anular los servidores DNS del host en el resolv.conf creado). Además, se crea un archivo de entorno del contenedor en cada contenedor para indicar a los programas que se están ejecutando en un contenedor. Este archivo se encuentra en /run/.containerenv (o /var/run/.containerenv para contenedores FreeBSD). Cuando se usa la bandera --privileged, el .containerenv contiene pares nombre/valor que indican la versión del motor del contenedor, si el motor se está ejecutando en modo sin privilegios (rootless), el nombre y ID del contenedor, así como el nombre y ID de la imagen en la que se basa el contenedor. Nota: /run/.containerenv no se creará cuando se monte un volumen en /run.

Cuando se ejecuta desde un espacio de nombres de red definido por el usuario, se utilizará /etc/netns/NSNAME/resolv.conf si existe, de lo contrario se utilizará /etc/resolv.conf.

La configuración predeterminada se define en containers.conf. La mayoría de la configuración para conexiones remotas utiliza el servidor containers.conf, excepto cuando se documenta en las páginas del manual.

IMAGEN

La imagen se especifica usando el formato transporte:ruta. Si no se especifica ningún transporte, el transporte docker (registro de contenedores) se usa por defecto. Para Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), docker es el único transporte permitido.

dir:ruta
Un directorio local existente ruta que almacena el manifiesto, los archivos tar de capas y las firmas como archivos individuales. Este es un formato no estandarizado, útil principalmente para depuración o inspección no invasiva de contenedores.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman run dir:/tmp/fedora echo hello

docker://referencia-docker (Predeterminado)
Una referencia de imagen almacenada en un registro de imágenes de contenedores remoto. Ejemplo: "quay.io/podman/stable:latest". La referencia puede incluir una ruta a un registro específico; si no lo hace, se consultan los registros listados en registries.conf para encontrar una imagen coincidente. Por defecto, se utilizan las credenciales de podman login (almacenadas en ${XDG_RUNTIME_DIR}/containers/auth.json por defecto) para autenticarse; de lo contrario, se recurre a las credenciales en $HOME/.docker/config.json.

$ podman run registry.fedoraproject.org/fedora:latest echo hello

docker-archive:ruta[:referencia-docker] Una imagen almacenada en el archivo con formato docker save. referencia-docker solo se utiliza al crear dicho archivo y no debe contener un resumen (digest).

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman run docker-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

docker-daemon:referencia-docker
Una imagen en formato referencia-docker almacenada en el almacenamiento interno del demonio de Docker. La referencia-docker también puede ser un ID de imagen (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman run docker-daemon:docker.io/library/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

oci-archive:ruta:etiqueta
Una imagen en un directorio que cumple con la "Especificación de diseño de imágenes de contenedor abierto" en la ruta especificada y especificada con una etiqueta.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman run oci-archive:/tmp/fedora echo hello

Nota: En clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2), este transporte no es compatible.

OPCIONES

--add-host=nombre-host[;nombre-host[;...]]:ip

Añade un mapeo personalizado de nombre de host a IP al archivo /etc/hosts del contenedor.

La opción toma uno o varios nombres de host separados por punto y coma que se mapearán a una única dirección IPv4 o IPv6, separada por dos puntos. También se puede utilizar para sobrescribir las direcciones IP de los nombres de host que Podman añade a /etc/hosts por defecto (ver también las opciones --name y --hostname). Esta opción se puede especificar varias veces para añadir mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede dar el indicador especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de su configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que hará que Podman falle con un mensaje de error. Puede sobrescribir esta dirección IP utilizando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para añadir automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitarlo dando la opción --no-hosts, o configurando host_containers_internal_ip="none" en containers.conf. Si no se configuró ninguna dirección host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se está ejecutando en una máquina virtual utilizando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos son resueltos por el resolvedor DNS de gvproxy en su lugar.

Podman usará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente utilizando la configuración base_hosts_file en containers.conf.

--annotation=clave=valor

Añade una anotación al contenedor. Esta opción se puede establecer múltiples veces.

--arch=ARQUITECTURA

Anula la arquitectura, por defecto la del host, de la imagen a descargar. Por ejemplo, arm. A menos que se anule, las búsquedas posteriores de la misma imagen en el almacenamiento local coincidirán con esta arquitectura, independientemente del host.

--attach, -a=stdin | stdout | stderr

Adjuntar a STDIN, STDOUT o STDERR.

En modo de primer plano (el predeterminado cuando no se especifica -d), podman run puede iniciar el proceso en el contenedor y adjuntar la consola a la entrada, salida y error estándar del proceso. Incluso puede simular ser una TTY (que es lo que espera la mayoría de los ejecutables de línea de comandos) y pasar señales. La opción -a se puede establecer para cada uno de stdin, stdout y stderr.

--authfile=ruta

Ruta del archivo de autenticación. El valor predeterminado es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo es creado por podman login. Si el estado de autorización no

t encontrado allí, se comprueba $HOME/.docker/config.json, que se establece mediante docker login.

Nota: También existe la opción de anular la ruta predeterminada del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

--blkio-weight=peso

Peso relativo de Block IO. El peso es un valor entre 10 y 1000.

Esta opción no se admite en sistemas sin privilegios (rootless) con cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo de Block IO por dispositivo.

--cap-add=capacidad

Añadir capacidades de Linux.

Otorgar capacidades adicionales aumenta los privilegios de los procesos que se ejecutan dentro del contenedor y potencialmente le permite escapar de su confinamiento. Capacidades como CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_MKNOD y CAP_SYS_MODULE son particularmente peligrosas cuando no se utilizan dentro de un espacio de nombres de usuario. Consulte user_namespaces(7) para obtener una explicación más detallada de la interacción entre los espacios de nombres de usuario y las capacidades.

Antes de añadir cualquier capacidad, revise sus implicaciones de seguridad y asegúrese de que es realmente necesaria para la funcionalidad del contenedor. Consulte capabilities(7) para obtener más información.

--cap-drop=capacidad

Eliminar capacidades de Linux.

--cert-dir=ruta

Utilice certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. (Predeterminado: /etc/containers/certs.d) Para obtener detalles, consulte containers-certs.d(5). (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2))

--cgroup-conf=CLAVE=VALOR

Al ejecutarse en cgroup v2, especifique el archivo cgroup al que escribir y su valor. Por ejemplo, --cgroup-conf=memory.high=1073741824 establece el límite de memory.high en 1 GB.

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se crea el cgroup para el contenedor. Si la ruta no es absoluta, se considera relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen ya.

--cgroupns=modo

Establece el modo del espacio de nombres cgroup para el contenedor.

  • host: utiliza el espacio de nombres cgroup del host dentro del contenedor.
  • container:id: únete al espacio de nombres del contenedor especificado.
  • private: crea un nuevo espacio de nombres cgroup.
  • ns:ruta: únete al espacio de nombres en la ruta especificada.

Si el host utiliza cgroups v1, el valor predeterminado se establece en host. En cgroups v2, el valor predeterminado es private.

--cgroups=cómo

Determina si el contenedor crea cgroups.

El valor predeterminado es enabled (habilitado).

La opción enabled crea un nuevo cgroup bajo el cgroup-parent. La opción disabled (deshabilitado) obliga al contenedor a no crear cgroups y, por lo tanto, entra en conflicto con las opciones de cgroup (--cgroupns y --cgroup-parent). La opción no-conmon deshabilita un nuevo cgroup solo para el proceso conmon. La opción split (dividir) divide el cgroup actual en dos sub-cgroups: uno para conmon y otro para la carga útil del contenedor. No es posible establecer --cgroup-parent con split.

--chrootdirs=ruta

Ruta a un directorio dentro del contenedor que se trata como un directorio chroot. Cualquier archivo administrado por Podman (por ejemplo, /etc/resolv.conf, /etc/hosts, /etc/hostname) que se monte en el directorio raíz también se montará en esa ubicación. Múltiples directorios se separan con una coma.

--cidfile=archivo

Escribe el ID del contenedor en archivo. El archivo se elimina junto con el contenedor, excepto cuando se utiliza con podman --remote run en contenedores détachés.

--conmon-pidfile=archivo

Escribe el PID del proceso conmon en un archivo. Como conmon se ejecuta en un proceso separado de Podman, esto es necesario cuando se utiliza systemd para reiniciar contenedores de Podman. (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2))

--cpu-period=límite

Establece el período de CPU para el planificador Completely Fair Scheduler (CFS), que es una duración en microsegundos. Una vez que se agota la cuota de CPU del contenedor, no se programará para ejecutarse hasta que finalice el período actual. El valor predeterminado es 100000 microsegundos.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios sin privilegios. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin privilegios (rootless) con cgroups V1.

--cpu-quota=límite

Limita la cuota del planificador Completely Fair Scheduler (CFS) de CPU.

Limita el uso de CPU del contenedor. De forma predeterminada, los contenedores se ejecutan con todos los recursos de CPU. El límite es un número en microsegundos. Si se proporciona un número, al contenedor se le permite usar esa cantidad de tiempo de CPU hasta que finalice el período de CPU (controlable mediante --cpu-period).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios sin privilegios. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin privilegios (rootless) con cgroups V1.

--cpu-rt-period=microsegundos

Limita el período de tiempo real de la CPU en microsegundos.

Limita el uso de la CPU de tiempo real del contenedor. Esta opción indica al kernel que restrinja el uso de la CPU de tiempo real del contenedor al período especificado.

Esta opción solo se admite en sistemas con privilegios (rootful) con cgroups V1.

--cpu-rt-runtime=microsegundos

Limita el tiempo de ejecución de tiempo real de la CPU en microsegundos.

Limita el uso de la CPU de tiempo real de los contenedores. Esta opción indica al kernel que limite la cantidad de tiempo en un período de CPU dado que las tareas de tiempo real pueden consumir. Por ejemplo, un período de 1.000.000 us y un tiempo de ejecución de 950.000 us significa que este contenedor puede consumir el 95% de la CPU disponible y dejar el 5% restante para tareas de prioridad normal.

La suma de todos los tiempos de ejecución entre contenedores no puede superar la cantidad asignada al cgroup padre.

Esta opción solo se admite en sistemas con privilegios (rootful) con cgroups V1.

--cpu-shares, -c=participaciones

Participaciones de CPU (peso relativo).

De forma predeterminada, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de participación de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso predeterminado es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas de un contenedor están inactivas, otros contenedores pueden utilizar el tiempo de CPU sobrante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una participación de CPU de 1024 y otros dos tienen una configuración de participación de CPU de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con una participación de CPU de 1024, el primer contenedor solo recibe el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las participaciones de tiempo de CPU se distribuyen en todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede utilizar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de las participaciones de CPU:

PID contenedor CPU participación de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios sin privilegios. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin privilegios (rootless) con cgroups V1.

--cpus=número

Número de CPUs. El valor predeterminado es 0.0, lo que significa sin límite. Esto es un atajo para --cpu-period y --cpu-quota, por lo tanto, la opción no se puede especificar con --cpu-period o --cpu-quota.

En algunos sistemas, cambiar los límites de CPU puede no estar permitido para usuarios sin privilegios. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin privilegios (rootless) con cgroups V1.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de ellos (por ejemplo, 0-3,7,11-15).

--cpuset-cpu=cpus

CPUs in which to allow execution (0-3, 0,1). Only effective on multi-CPU systems.

If there are four CPUs on the system (0-3), use --cpuset-cpu=0,1 then processes in the container only uses the first two CPUs.

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--cpuset-mems=nodes

Memory nodes (MEMs) in which to allow execution (0-3, 0,1). Only effective on NUMA systems.

If there are four memory nodes on the system (0-3), use --cpuset-mems=0,1 then processes in the container only uses memory from the first two memory nodes.

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--creds=[username[:password]]

The [username[:password]] to use to authenticate with the registry, if required. If one or both values are not supplied, a command line prompt appears and the value can be entered. The password is entered without echo.

Note that the specified credentials are only used to authenticate against target registries. They are not used for mirrors or when the registry gets rewritten (see containers-registries.conf(5)); to authenticate against those consider using a containers-auth.json(5) file.

--decryption-key=key[:passphrase]

The [key[:passphrase]] to be used for decryption of images. Key can point to keys and/or certificates. Decryption is tried with all keys. If the key is protected by a passphrase, it is required to be passed in the argument and omitted otherwise.

--detach, -d

Detached mode: run the container in the background and print the new container ID. The default is false.

At any time run podman ps in the other shell to view a list of the running containers. Reattach to a detached container with podman attach command.

When attached via tty mode, detach from the container (and leave it running) using a configurable key sequence. The default sequence is ctrl-p,ctrl-q. Specify the key sequence using the --detach-keys option, or configure it in the containers.conf file: see containers.conf(5) for more information.

--detach-keys=sequence

Specify the key sequence for detaching a container. Format is a single character [a-Z] or one or more ctrl-<value> characters where <value> is one of: a-z, @, ^, [, , or _. Specifying "" disables this feature. The default is ctrl-p,ctrl-q.

This option can also be set in containers.conf(5) file.

--device=host-device[:container-device][:permissions]

Add a host device to the container. Optional permissions parameter can be used to specify device permissions by combining r for read, w for write, and m for mknod(2).

Example: --device=/dev/sdc:/dev/xvdc:rwm.

Note: if host-device is a symbolic link then it is resolved first. The container only stores the major and minor numbers of the host device.

Podman may load kernel modules required for using the specified device. The devices that Podman loads modules for when necessary are: /dev/fuse.

In rootless mode, the new device is bind mounted in the container from the host rather than Podman creating it within the container space. Because the bind mount retains its SELinux label on SELinux systems, the container can get permission denied when accessing the mounted device. Modify SELinux settings to allow containers to use all device labels via the following command:

$ sudo setsebool -P container_use_devices=true

Note: if the user only has access rights via a group, accessing the device from inside a rootless container fails. Use the --group-add keep-groups flag to pass the user's supplementary group access into the container.

--device-cgroup-rule="type major:minor mode"

Add a rule to the cgroup allowed devices list. The rule is expected to be in the format specified in the Linux kernel documentation admin-guide/cgroup-v1/devices: - type: a (all), c (char), or b (block); - major and minor: either a number, or * for all; - mode: a composition of r (read), w (write), and m (mknod(2)).

--disable-content-trust

This is a Docker-specific option to disable image verification to a container registry and is not supported by Podman. This option is a NOOP and provided solely for scripting compatibility.

--dns=ipaddr

Set custom DNS servers.

This option can be used to override the DNS configuration passed to the container. Typically this is necessary when the host DNS configuration is invalid for the container (e.g., 127.0.0.1). When this is the case the --dns flag is necessary for every run.

The special value none can be specified to disable creation of /etc/resolv.conf in the container by Podman. The /etc/resolv.conf file in the image is then used without changes.

Note that ipaddr may be added directly to the container's /etc/resolv.conf. This is not guaranteed though. For example, passing a custom network whose dns_enabled is set to true to --network will result in /etc/resolv.conf only referring to the aardvark-dns server. aardvark-dns then forwards to the supplied ipaddr for all non-container name queries.

This option cannot be combined with --network that is set to none or container:id.

--dns-option=option

Set custom DNS options. Invalid if using --dns-option with --network that is set to none or container:id.

--dns-search=domain

Set custom DNS search domains. Invalid if using --dns-search with --network that is set to none or container:id. Use --dns-search=. to remove the search domain.

--entrypoint="command" | '["command", arg1 , ...]'

Override the default ENTRYPOINT from the image.

The ENTRYPOINT of an image is similar to a COMMAND because it specifies what executable to run when the container starts, but it is (purposely) more difficult to override. The ENTRYPOINT gives a container its default nature or behavior. When the ENTRYPOINT is set, the container runs as if it were that binary, complete with default options. More options can be passed in via the COMMAND. But, if a user wants to run something else inside the container, the --entrypoint option allows a new ENTRYPOINT to be specified.

Specify multi option commands in the form of a JSON string.

--mount=type=TIPO,OPCIÓN-ESPECÍFICA-DEL-TIPO[,...]

Adjunta un montaje de sistema de archivos al contenedor.

Los TIPO de montaje compatibles actualmente son artifact, bind, devpts, glob, image, ramfs, tmpfs y volume.

Opciones comunes

to all mount types:

  • src, source: mount source spec for bind, glob, and volume. Mandatory for artifact, bind, glob, image and volume.
  • dst, dest, destination, target: mount destination spec.

When source globs are specified without the destination directory, the files and directories are mounted with their complete path within the container. When the destination is specified, the files and directories matching the glob on the base file name on the destination directory are mounted. The option type=glob,src=/foo*,destination=/tmp/bar tells container engines to mount host files matching /foo* to the /tmp/bar/ directory in the container.

Options specific to type=artifact:

  • digest: If the artifact source contains multiple blobs a digest can be specified to only mount the one specific blob with the digest.
  • title: If the artifact source contains multiple blobs a title can be set which is compared against org.opencontainers.image.title annotation.
  • name: This can be used to overwrite the filename we use inside the container for mounting. On a single blob artifact the name is used as is if dst is a directory and otherwise ignored. With a multi blob artifact the name will be used with an index suffix <name>-x where x is the layer index in the artifact starting with 0.

The src argument contains the name of the artifact, which must already exist locally. The dst argument contains the target path, if the path in the container is a directory the blob title (org.opencontainers.image.title annotation) will be used as filename and joined to the path. If the annotation does not exist the digest will be used as filename instead. This results in all blobs of the artifact mounted into the container at the given path.

However, if the dst path is an existing file in the container, then the blob will be mounted directly on it. This only works when the artifact contains a single blob or when either digest or title are specified.

If the dst path does not already exist in the container then if the artifact contains a single blob it behaves like existing file case and mounts directly to that path. If the artifact has more than one blob it works like the existing directory case and mounts each blob as file within the dst path.

Options specific to type=volume:

  • ro, readonly: true or false (default if unspecified: false).
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.
  • subpath: Mount only a specific subpath within the volume, instead of the whole volume.
  • idmap: If specified, create an idmapped mount to the target user namespace in the container. The idmap option is only supported by Podman in rootful mode. The Linux kernel does not allow the use of idmapped file systems for unprivileged users. The idmap option supports a custom mapping that can be different than the user namespace used by the container. The mapping can be specified after the idmap option like: idmap=uids=0-1-10#10-11-10;gids=0-100-10. For each triplet, the first value is the start of the backing file system IDs that are mapped to the second value on the host. The length of this mapping is given in the third value. Multiple ranges are separated with #. If the specified mapping is prepended with a '@', then the mapping is considered relative to the container user namespace. The host ID for the mapping is changed to account for the relative position of the container user in the container user namespace.

Options specific to type=image:

  • rw, readwrite: true or false (default if unspecified: false).
  • subpath: Mount only a specific path within the image, instead of the whole image.

Options specific to bind and glob:

  • ro, readonly: true or false (default if unspecified: false).
  • bind-propagation: shared, slave, private, unbindable, rshared, rslave, runbindable, or rprivate (default).[1] ⟨#Footnote1⟩ See also mount(2).
  • bind-nonrecursive: do not set up a recursive bind mount. By default it is recursive.
  • relabel: shared, private.
  • idmap: true or false (default if unspecified: false). If true, create an idmapped mount to the target user namespace in the container. The idmap option is only supported by Podman in rootful mode.
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.
  • no-dereference: do not dereference symlinks but copy the link source into the mount destination.

Options specific to type=tmpfs and ramfs:

  • ro, readonly: true or false (default if unspecified: false).
  • tmpfs-size: Size of the tmpfs/ramfs mount, in bytes. Unlimited by default in Linux.
  • tmpfs-mode: Octal file mode of the tmpfs/ramfs (e.g. 700 or 0700.).
  • tmpcopyup: Enable copyup from the image directory at the same location to the tmpfs/ramfs. Used by default.
  • noatime: Disable updating file access times when the file is read.
  • notmpcopyup: Disable copying files from the image to the tmpfs/ramfs.
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.

Options specific to type=devpts:

  • uid: numeric UID of the file owner (default: 0).
  • gid: numeric GID of the file owner (default: 0).
  • mode: octal permission mask for the file (default: 600).
  • max: maximum number of PTYs (default: 1048576).

  • type=devpts,destination=/dev/pts
  • type=glob,src=/usr/lib/libfoo*,destination=/usr/lib,ro=true
  • type=image,source=fedora,destination=/fedora-image,rw=true
  • type=ramfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,destination=/path/in/container,noswap

Set the network mode for the container.

Valid mode values are:

•

  • alias=name: Add network-scoped alias for the container.
  • ip=IPv4: Specify a static IPv4 address for this container.
  • ip6=IPv6: Specify a static IPv6 address for this container.
  • mac=MAC: Specify a static MAC address for this container.

Any other options will be passed through to netavark without validation. This can be useful to pass arguments to netavark plugins.

For example, to set a static ipv4 address and a static mac address, use --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <network name or ID>[:OPTIONS,...]: Connect to a user-defined network; this is the network name or ID from a network created by podman network create. It is possible to specify the same options described under the bridge mode above. Use the --network option multiple times to specify additional networks.
    For backwards compatibility it is also possible to specify comma-separated networks on the first --network argument, however this prevents you from using the options described under the bridge section above.
  • none: Create a network namespace for the container but do not configure network interfaces for it, thus the container has no network connectivity.
  • container:id: Reuse another container's network stack.
  • host: Use the host's network namespace for the container instead of creating an isolated namespace. Warning: This gives the container full access to abstract Unix domain sockets and to TCP/UDP sockets bound to localhost. Since these mechanisms are often used to prevent access to sensitive system services, isolating them from access by external entities, use of this option may be considered a security vulnerability.
  • ns:path: Path to a network namespace to join.
  • privado: Crea un nuevo espacio de nombres para el contenedor. Esto utiliza el modo bridge para contenedores con privilegios y slirp4netns para los sin privilegios.
  • slirp4netns[:OPCIONES,...]: utiliza slirp4netns(1) para crear una pila de red de usuario. Es posible especificar estas opciones adicionales, que también se pueden establecer con network_cmd_options en containers.conf:
  • allow_host_loopback=true|false: Permite a slirp4netns acceder a la IP de bucle invertido del host (el valor predeterminado es 10.0.2.2 o la segunda IP de la subred CIDR de slirp4netns cuando se cambia, consulte la opción cidr a continuación). El valor predeterminado es false.
  • mtu=MTU: Especifica la MTU a utilizar para esta red. (El valor predeterminado es 65520).
  • cidr=CIDR: Especifica el rango de IP a utilizar para esta red. (El valor predeterminado es 10.0.2.0/24).
  • enable_ipv6=true|false: Habilita IPv6. El valor predeterminado es true. (Requerido para outbound_addr6).
  • outbound_addr=INTERFACE: Especifica la interfaz de salida a la que se une slirp (solo tráfico ipv4).
  • outbound_addr=IPv4: Especifica la dirección IPv4 de salida a la que se une slirp.
  • outbound_addr6=INTERFACE: Especifica la interfaz de salida a la que se une slirp (solo tráfico ipv6).
  • outbound_addr6=IPv6: Especifica la dirección IPv6 de salida a la que se une slirp.
  • port_handler=rootlesskit: Utiliza rootlesskit para el reenvío de puertos. Predeterminado.
    Nota: Rootlesskit cambia la dirección IP de origen de los paquetes entrantes a una dirección IP en el espacio de nombres de red del contenedor, generalmente 10.0.2.100. El manejador de puertos rootlesskit también se utiliza para contenedores sin privilegios conectados a redes definidas por el usuario.
  • port_handler=slirp4netns: Utiliza el reenvío de puertos slirp4netns, que es más lento que rootlesskit pero conserva la dirección IP de origen correcta. Este manejador de puertos no se puede utilizar para redes definidas por el usuario.
•
pasta[:OPCIONES,...]: utiliza pasta(1) para crear una pila de red en modo de usuario.
Este es el valor predeterminado para contenedores sin privilegios y solo se admite en modo sin privilegios.
Por defecto, las direcciones y rutas IPv4 e IPv6, así como el nombre de la interfaz del pod, se copian del host. El reenvío de puertos conserva la dirección IP de origen original. Las opciones descritas en pasta(1) se pueden especificar como argumentos separados por comas.
En cuanto a las opciones de pasta(1), se proporciona --config-net por defecto, para configurar la red cuando se inicia el contenedor, y también se asume --no-map-gw por defecto, para evitar el acceso directo del contenedor al host utilizando la dirección de la puerta de enlace. Este último puede ser anulado pasando --map-gw en las opciones específicas de pasta (a pesar de no ser una opción real de pasta(1)).
Para una mejor integración con el manejo de DNS, se pasa --dns-forward 169.254.1.1, y esta dirección se añade a resolv.conf(5) como primer resolvedor. Es posible pasar --dns-forward explícitamente en caso de que se deba utilizar una dirección IP diferente. Para que la entrada host.containers.internal en /etc/hosts funcione y permita las conexiones al host, se pasa --map-guest-addr 169.254.1.2. Nuevamente, se puede establecer explícitamente para elegir una dirección IP diferente.
Además, se pasan -t none y -u none si, respectivamente, no se configura ningún reenvío de puertos TCP o UDP del host al contenedor (a través de --publish de Podman o pasando las opciones -t/-u de pasta directamente), para deshabilitar el reenvío automático de puertos basado en puertos enlazados. De manera similar, se proporcionan -T none y -U none para deshabilitar la misma funcionalidad de contenedor a host.
Todas las opciones también se pueden establecer en containers.conf(5); consulte la clave pasta_options en la sección de red de ese archivo.
Algunos ejemplos:
  • pasta:--map-gw: Permite que el contenedor alcance directamente el host utilizando la dirección de la puerta de enlace.
  • pasta:--mtu,1500: Especifica una MTU de 1500 bytes para la interfaz tap en el contenedor.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con puerta de enlace 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece la MTU en 1500 bytes, deshabilita NDP, DHCPv6 y DHCP soporte.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: lo mismo que lo anterior, pero deja la MTU en 65520 bytes.

Cuando los secretos se especifican como tipo mount, los secretos se copian y montan en el contenedor cuando se crea un contenedor. Cuando los secretos se especifican como tipo env, el secreto se establece como una variable de entorno dentro del contenedor. Los secretos se escriben en el contenedor en el momento de la creación del contenedor, y la modificación del secreto utilizando comandos podman secret después de la creación del contenedor afecta al secreto dentro del contenedor.

Los secretos y su almacenamiento se gestionan utilizando el comando podman secret.

Opciones de secreto

  • type=mount|env : Cómo se expone el secreto al contenedor.
    mount monta el secreto en el contenedor como un archivo.
    env expone el secreto como una variable de entorno.
    El valor predeterminado es mount.
  • target=target : Destino del secreto.
    Para secretos montados, esta es la ruta al secreto dentro del contenedor.
    Si se proporciona una ruta completamente calificada, el secreto se montará en esa ubicación.
    De lo contrario, el secreto se montará en
    /run/secrets/target para contenedores Linux o
    /var/run/secrets/target para contenedores FreeBSD.
    Si el destino no está establecido, el secreto se montará en /run/secrets/secretname por defecto.
    Para secretos de entorno, esta es la clave de la variable de entorno. El valor predeterminado es secretname.
  • uid=0 : UID del secreto. El valor predeterminado es 0. Solo tipo de montaje de secreto.
  • gid=0 : GID del secreto. El valor predeterminado es 0. Solo tipo de montaje de secreto.
  • mode=0 : Modo del secreto. El valor predeterminado es 0444. Solo tipo de montaje de secreto.

Ejemplos

Montar en /my/location/mysecret con UID 1:

--secret mysecret,target=/my/location/mysecret,uid=1

Montar en /run/secrets/customtarget con modo 0777:

--secret mysecret,target=customtarget,mode=0777

Crear una variable de entorno secreta llamada ENVSEC:

--secret mysecret,type=env,target=ENVSEC

Opciones de seguridad

  • apparmor=unconfined : Desactivar el confinamiento de apparmor para el contenedor
  • apparmor=alternate-profile : Establecer el perfil de confinamiento de apparmor para el contenedor
  • label=user:USER: Establecer el usuario de etiqueta para los procesos del contenedor
  • label=role:ROLE: Establecer el rol de etiqueta para los procesos del contenedor
  • label=type:TYPE: Establecer el tipo de proceso de etiqueta para los procesos del contenedor
  • label=level:LEVEL: Establecer el nivel de etiqueta para los procesos del contenedor
  • label=filetype:TYPE: Establecer el tipo de archivo de etiqueta para los archivos del contenedor
  • label=disable: Desactivar la separación de etiquetas para el contenedor

Nota: El etiquetado se puede deshabilitar para todos los contenedores estableciendo label=false en el archivo containers.conf (/etc/containers/containers.conf o $HOME/.config/containers/containers.conf).

  • label=nested: Permite modificaciones de SELinux dentro del contenedor. Se permite a los contenedores modificar etiquetas SELinux en archivos y procesos, siempre que la política SELinux lo permita. Sin nested, los contenedores ven SELinux como deshabilitado, incluso cuando está habilitado en el host. Se impide a los contenedores establecer cualquier etiqueta.
  • mask=/path/1:/path/2: Las rutas a enmascarar separadas por dos puntos. Un camino enmascarado no se puede acceder dentro del contenedor.
  • no-new-privileges: Deshabilita que los procesos del contenedor obtengan privilegios adicionales a través de la llamada al sistema execve(2) (por ejemplo, a través de bits setuid o setgid, o a través de capacidades de archivo). Los programas que dependen de los bits setuid/setgid establecidos en su ejecutable para cambiar el ID de usuario o grupo ya no pueden hacerlo, y cualquier capacidad de archivo añadida al ejecutable (por ejemplo, a través de setcap) no se añade al conjunto de capacidades permitidas. Para más detalles, véase: https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined: Desactivar el confinamiento seccomp para el contenedor.
  • seccomp=profile.json: Archivo JSON que se utilizará como filtro seccomp. Tenga en cuenta que la anotación io.podman.annotations.seccomp se establece con el valor especificado como se muestra en podman inspect.
  • proc-opts=OPTIONS : Lista de opciones separadas por comas que se utilizarán para el montaje de /proc. Más detalles sobre las posibles opciones de montaje se especifican en la página de manual proc(5).
  • unmask=ALL o /path/1:/path/2, o rutas expandidas por shell (/proc/*): Rutas a desenmascarar separadas por dos puntos. Si se establece en ALL, desenmascara todas las rutas que están enmascaradas o se hacen de solo lectura por defecto. Las rutas enmascaradas por defecto son /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, y /sys/fs/selinux, /sys/devices/virtual/powercap. Las rutas por defecto que son de solo lectura son /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

Nota: El etiquetado se puede deshabilitar para todos los contenedores estableciendo label=false en el archivo containers.conf(5).

--shm-size=number[unit]

Tamaño de /dev/shm. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes), o g (gibibytes). Si la unidad se omite, el sistema usa bytes. Si el tamaño se omite, el valor predeterminado es 64m. Cuando size es 0, no hay límite en la cantidad de memoria utilizada para IPC por el contenedor. Esta opción entra en conflicto con --ipc=host.

--shm-size-systemd=number[unit]

Tamaño de montajes tmpfs específicos de systemd como /run, /run/lock, /var/log/journal y /tmp. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes), o g (gibibytes). Si la unidad se omite, el sistema usa bytes. Si el tamaño se omite, el valor predeterminado es 64m. Cuando tamaño es 0, el uso se limita al 50% de la memoria disponible del host.

--systemd=true | false | always

Ejecuta el contenedor en modo systemd. El valor predeterminado es true.

  • true habilita el modo systemd solo cuando el comando ejecutado dentro del contenedor es systemd, /usr/sbin/init, /sbin/init o /usr/local/sbin/init.
  • false deshabilita el modo systemd.
  • always fuerza la habilitación del modo systemd.

Ejecutar el contenedor en modo systemd provoca los siguientes cambios:

•
Podman monta sistemas de archivos tmpfs en los siguientes directorios
  • /run
  • /run/lock
  • /tmp
  • /sys/fs/cgroup/systemd (en un sistema cgroup v1)
  • /var/lib/journal
  • Podman establece la señal de detención predeterminada en SIGRTMIN+3.
  • Podman establece la variable de entorno container_uuid en el contenedor con los primeros 32 caracteres del ID del contenedor.
  • Podman no monta consolas virtuales (/dev/tty\d+) cuando se ejecuta con --privileged.
  • En cgroup v2, /sys/fs/cgroup se monta como escribible.

Esto permite que systemd se ejecute en un contenedor confinado sin modificaciones.

Ten en cuenta que en sistemas SELinux, systemd intenta escribir en el sistema de archivos cgroup. Los contenedores que escriben en el sistema de archivos cgroup están denegados por defecto. La opción booleana container_manage_cgroup debe estar habilitada para permitir esto en un sistema separado por SELinux.

setsebool -P container_manage_cgroup true

--uidmap=[flags]uid_contenedor:uid_desde[:cantidad]

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo de UID proporcionado. Esta opción entra en conflicto con las opciones --userns y --subuidname. Esta opción proporciona una forma de mapear UID de host a UID de contenedor. Se puede pasar varias veces para mapear diferentes rangos.

Los valores posibles de flags opcionales se discuten más abajo en esta página. El valor de cantidad es opcional y se asume que es 1 si no se proporciona.

El valor de uid_desde se basa en el usuario que ejecuta el comando, ya sea un usuario con privilegios (rootful) o sin privilegios (rootless).

  • usuario rootful: [flags]uid_contenedor:uid_host[:cantidad]
  • usuario rootless: [flags]uid_contenedor:uid_intermediario[:cantidad]

Mapeos rootful

Cuando el usuario privilegiado llama a podman run, la opción --uidmap funciona como un mapeo directo entre UID de host y UID de contenedor.

UID del host -> UID del contenedor

La cantidad especifica el número de UID consecutivos que se mapean. Si, por ejemplo, cantidad es 4, el mapeo se ve así:

UID del host UID del contenedor
uid_desde uid_contenedor
uid_desde + 1 uid_contenedor + 1
uid_desde + 2 uid_contenedor + 2
uid_desde + 3 uid_contenedor + 3

Mapeos rootless

Cuando un usuario no privilegiado (es decir, ejecutando sin privilegios) llama a podman run, el valor uid_desde se interpreta como un "UID intermedio". En el caso sin privilegios, los UID de host no se mapean directamente a los UID de contenedor. En cambio, el mapeo se realiza a través de dos pasos de mapeo:

UID del host -> UID intermedio -> UID del contenedor

La opción --uidmap solo influye en el segundo paso de mapeo.

El primer paso de mapeo se deriva de Podman a partir del contenido del archivo /etc/subuid y del UID del usuario que llama a Podman.

Primer paso de mapeo:

UID del host UID intermedio
UID del usuario de Podman 0
1er UID subordinado 1
2do UID subordinado 2
3er UID subordinado 3
nth UID subordinado n

Para poder utilizar UID intermedios mayores que cero, el usuario necesita tener UID subordinados configurados en /etc/subuid. Consulta subuid(5).

El segundo paso de mapeo se configura con --uidmap.

Si, por ejemplo, cantidad es 5, el segundo paso de mapeo se ve así:

UID intermedio UID del contenedor
uid_desde uid_contenedor
uid_desde + 1 uid_contenedor + 1
uid_desde + 2 uid_contenedor + 2
uid_desde + 3 uid_contenedor + 3
uid_desde + 4 uid_contenedor + 4

Al ejecutarse sin privilegios, Podman utiliza todos los rangos configurados en el archivo /etc/subuid.

El ID de usuario actual se mapea a UID=0 en el espacio de nombres de usuario sin privilegios. Cada rango adicional se agrega secuencialmente después:

host espacio de nombres de usuario sin privilegios longitud
$UID 0 1
1 $PRIMER_RANGO_ID $PRIMERA_LONGITUD_RANGO
1+$PRIMERA_LONGITUD_RANGO $SEGUNDO_RANGO_ID $SEGUNDA_LONGITUD_RANGO

Referenciando un ID de host desde el espacio de nombres padre

Como usuario sin privilegios, el ID de host dado en --uidmap o --gidmap se mapea desde el espacio de nombres intermedio generado por Podman. A veces es deseable referirse directamente al espacio de nombres del host. Es posible hacerlo manualmente, ejecutando podman unshare cat /proc/self/gid_map, encontrando el ID de host deseado en la segunda columna de la salida y obteniendo el ID intermedio correspondiente de la primera columna.

Podman puede hacer todo esto anteponiendo el ID de host en el mapeo con el símbolo @. Por ejemplo, especificando --gidmap 100000:@2000:1, podman buscará el ID intermedio correspondiente al ID de host 2000 y mapeará el ID intermedio encontrado al ID de contenedor 100000. El ID de host proporcionado debe haber sido subordinado (de lo contrario, no se mapearía al espacio intermedio en primer lugar).

Si la longitud es mayor que uno, por ejemplo, con --gidmap 100000:@2000:2, Podman

man mapeará los ID de host 2000 y 2001 a 100000 y 100001, respectivamente, independientemente de cómo se defina el mapeo intermedio.

Extensión de mapeos anteriores

Algunas modificaciones de mapeo pueden ser engorrosas. Por ejemplo, un usuario comienza con un mapeo como --gidmap="0:0:65000", que necesita ser cambiado de tal manera que el ID padre 1 se mapee a un ID de contenedor 100000 en su lugar, dejando el ID de contenedor 1 sin asignar. El --gidmap correspondiente se convierte en --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

Esta notación se puede simplificar utilizando el indicador +, que se encarga de romper los mapeos anteriores eliminando cualquier asignación conflictiva con el mapeo dado. El indicador se proporciona antes del ID del contenedor, de la siguiente manera: --gidmap="0:0:65000" --gidmap="+100000:1:1"

Indicador Ejemplo Descripción
+ +100000:1:1 Extender el mapeo anterior

Esta notación genera huecos en la asignación, por lo que puede ser conveniente rellenar esos huecos posteriormente: --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

Un caso de uso específico para este indicador es en el contexto de usuarios sin privilegios. Un usuario sin privilegios puede especificar mapeos con el indicador + como en --gidmap="+100000:1:1". Podman luego "rellenará los huecos" comenzando desde cero con todos los IDs intermedios restantes. Esto es conveniente cuando un usuario desea mapear un ID intermedio específico a un ID de contenedor, dejando que Podman mapee el resto de los IDs subordinados a su voluntad.

Pasar solo uno de --uidmap o --gidmap

Por lo general, los IDs de usuario y grupo subordinados se asignan simultáneamente, y para cualquier usuario, los IDs de usuario subordinados coinciden con los IDs de grupo subordinados. Para mayor comodidad, si solo se proporciona uno de --uidmap o --gidmap, podman asume que el mapeo se refiere tanto a UID como a GID y aplica el mapeo dado a ambos. Si solo es necesario cambiar uno de los dos valores, los mapeos deben incluir los indicadores u o g para especificar que solo se aplican a los UID o GID y no deben copiarse.

Indicador Ejemplo Descripción
u u20000:2000:1 El mapeo solo se aplica a los UID
g g10000:1000:1 El mapeo solo se aplica a los GID

Por ejemplo, dado el comando

podman run --gidmap "0:0:1000" --gidmap "g2000:2000:1"

Como no se proporciona --uidmap, el --gidmap se copia a --uidmap, lo que da como resultado un comando equivalente a

podman run --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

El --gidmap "g2000:2000:1" utilizó el indicador g y, por lo tanto, no se copió a --uidmap.

Mapeo sin privilegios de GID de host adicionales

Un usuario sin privilegios puede desear mapear un grupo de host específico que ya ha sido subordinado en /etc/subgid sin especificar el resto del mapeo.

Esto se puede hacer con --gidmap "+ggid_contenedor:@gid_host"

Donde:

  • El GID del host se proporciona a través del símbolo @
  • El mapeo de este GID no se copia a --usermap gracias al indicador g.
  • El resto de los IDs de contenedor se mapearán comenzando desde 0 hasta n, con todos los GID subordinados restantes, gracias al indicador +.

Por ejemplo, si un usuario pertenece al grupo 2000 y ese grupo está subordinado a ese usuario (con usermod --add-subgids 2000-2000 $USER), el usuario puede mapear el grupo al contenedor con: --gidmap=+g100000:@2000.

Si este mapeo se combina con la opción --group-add=keep-groups, el proceso en el contenedor pertenecerá al grupo 100000, y los archivos que pertenezcan al grupo 2000 en el host aparecerán como propiedad del grupo 100000 dentro del contenedor.

podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

Sin UID subordinados

Incluso si un usuario no tiene UID subordinados en /etc/subuid, se puede usar --uidmap para mapear el UID normal del usuario a un UID de contenedor ejecutando podman run --uidmap $uid_contenedor:0:1 --user $uid_contenedor ....

La opción --uidmap no se puede llamar en conjunción con la opción --pod, ya que no se puede establecer un uidmap a nivel de contenedor cuando está en un pod.

--ulimit=opción

Opciones de ulimit. Establece los valores de ulimits dentro del contenedor.

--ulimit con un límite blando y uno duro en el formato =[:]. Por ejemplo:

$ podman run --ulimit nofile=1024:1024 --rm ubi9 ulimit -n 1024

Establezca -1 para el límite blando o duro para establecer el límite al límite máximo del proceso actual. En modo con privilegios, esto a menudo es ilimitado.

Si nofile y nproc no están establecidos, se utilizará un valor predeterminado de 1048576, a menos que se anule en containers.conf(5). Sin embargo, si el valor predeterminado excede el límite duro para el usuario sin privilegios actual, se aplicará el límite duro actual en su lugar.

Use host para copiar la configuración actual del host.

No utilice nproc con el indicador ulimit, ya que Linux utiliza nproc para establecer el número máximo de procesos disponibles para un usuario, no para un contenedor.

Utilice la opción --pids-limit para modificar el control de cgroup para limitar el número de procesos dentro de un contenedor.

--umask=umask

Establece la umask dentro del contenedor. El valor predeterminado es 0022. Las conexiones remotas utilizan el archivo local containers.conf para los valores predeterminados.

--unsetenv=env

Anula las variables de entorno predeterminadas para el contenedor. Las variables de entorno predeterminadas incluyen las proporcionadas nativamente por Podman, las configuradas por la imagen y las del archivo containers.conf.

--unsetenv-all

Anula todas las variables de entorno predeterminadas para el contenedor. Las variables de entorno predeterminadas incluyen las proporcionadas nativamente por Podman, las configuradas por la imagen y las del archivo containers.conf.

--user, -u=usuario[:grupo]

Establece el nombre de usuario o UID utilizado y, opcionalmente, el nombre de grupo o GID para el comando especificado. Tanto usuario como grupo pueden ser simbólicos o numéricos.

Sin este argumento, el comando se ejecuta como el usuario especificado en la imagen del contenedor. A menos que se anule con un comando USER en el Containerfile o con un valor pasado a esta opción, este usuario generalmente se establece en root por defecto.

Cuando no se utiliza un espacio de nombres de usuario, el UID y el GID utilizados dentro del contenedor y en el host coinciden. Cuando se utilizan espacios de nombres de usuario, sin embargo, el UID y el GID dentro del contenedor pueden corresponder a otro UID y GID en el host. En contenedores sin privilegios, por ejemplo, siempre se utiliza un espacio de nombres de usuario, y root dentro del contenedor corresponde por defecto al UID y GID del usuario que invoca Podman.

--userns=modo

Establece el modo de espacio de nombres de usuario para el contenedor.

Si no se establece --userns, el valor predeterminado se determina de la siguiente manera. - Si se establece --pod, se ignora --userns y se utiliza el espacio de nombres de usuario del pod. - Si la variable de entorno PODMAN_USERNS está establecida, se utiliza su valor. - Si userns se especifica en containers.conf, se utiliza este valor. - De lo contrario, se asume --userns=host.

--userns="" (es decir, una cadena vacía) es un alias de --userns=host.

Esta opción es incompatible con --gidmap, --uidmap, --subuidname y --subgidname.

Mapeos de claves --userns para usuarios sin privilegios:

Clave Usuario Host Usuario Contenedor
auto $UID nil (El UID del Usuario Host no se mapea al contenedor.)
host $UID 0 (Cuenta de usuario predeterminada mapeada al usuario root en el contenedor.)
keep-id $UID $UID (Mapea la cuenta de usuario al mismo UID dentro del contenedor.)
keep-id:uid=200,gid=210 $UID 200:210 (Mapea la cuenta de usuario al UID especificado, valor GID dentro del contenedor.)
nomap $UID nil (El UID del Usuario Host no se mapea al contenedor.)

Los valores válidos de modo son:

auto[:OPCIONES,...]: crea automáticamente un espacio de nombres de usuario único.

  • modo con privilegios: El indicador --userns=auto requiere que el nombre de usuario containers se especifique en los archivos /etc/subuid y /etc/subgid, con un rango no utilizado de IDs de usuario subordinados que Podman puede asignar a los contenedores. Ejemplo: containers:2147483647:2147483648.
  • modo sin privilegios: Se utilizarán los rangos de usuarios de los archivos /etc/subuid y /etc/subgid. Tenga en cuenta que al ejecutar un solo contenedor sin usar --userns=auto se utilizará todo el rango de UID y no se permitirá una subdivisión posterior. Consulte subuid(5).

Podman asigna rangos únicos de UID y GID de los IDs de usuario subordinados de containers. El tamaño de los rangos se basa en el número de UID requeridos en la imagen. El número de UID y GID se puede anular con la opción size.

La opción --userns=keep-id utiliza todos los subuids y subgids del usuario. La opción --userns=nomap utiliza todos los subuids y subgids del usuario, excepto el propio ID del usuario. El uso de --userns=auto al iniciar nuevos contenedores no funciona mientras existan contenedores que se iniciaron con --userns=nomap o --userns=keep-id sin limitar el tamaño del espacio de nombres de usuario.

Opciones válidas de auto:

  • gidmapping=GID_CONTENEDOR:GID_HOST:TAMAÑO: para forzar un mapeo GID que esté presente en el espacio de nombres de usuario.
  • size=TAMAÑO: para especificar un tamaño explícito para el espacio de nombres de usuario automático. por ejemplo, --userns=auto:size=8192. Si size no está especificado
especificado, auto estima un tamaño para el espacio de nombres del usuario.
  • uidmapping=UID_CONTENEDOR:UID_HOST:TAMAÑO: para forzar una asignación de UID en el espacio de nombres del usuario.

    • El UID y GID del host en gidmapping y uidmapping pueden prefijarse opcionalmente con el símbolo @. En este caso, podman buscará el ID intermedio correspondiente al ID del host y asignará el ID intermedio encontrado al ID del contenedor. Para más detalles, vea --uidmap.

    container:id: únete al espacio de nombres de usuario del contenedor especificado.

    host o "" (cadena vacía): ejecuta en el espacio de nombres de usuario del llamador. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el host que cualquier otro proceso iniciado por el usuario llamador.

    keep-id: crea un espacio de nombres de usuario donde el UID:GID del usuario actual se mapea a los mismos valores en el contenedor. Para contenedores creados por root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

    Además, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen a menos que establezcas explícitamente --user.

    Opciones válidas para keep-id:

    • uid=UID: anula el UID dentro del contenedor que se utiliza para mapear al usuario actual.
    • gid=GID: anula el GID dentro del contenedor que se utiliza para mapear al usuario actual.
    • size=TAMAÑO: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No soportado al ejecutarse como root.

    nomap: crea un espacio de nombres de usuario donde los UID:GID del usuario rootless actual no se mapean al contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

    ns:namespace: ejecuta el contenedor en el espacio de nombres de usuario existente dado.

    --uts=modo

    Establece el modo del espacio de nombres UTS para el contenedor. Los siguientes valores son soportados:

    • host: utiliza el espacio de nombres UTS del host dentro del contenedor.
    • private: crea un nuevo espacio de nombres para el contenedor (predeterminado).
    • ns:[ruta]: ejecuta el contenedor en el espacio de nombres UTS existente dado.
    • container:[contenedor]: únete al espacio de nombres UTS del contenedor especificado.

    --variant=VARIANT

    Usa VARIANT en lugar de la variante de arquitectura predeterminada de la imagen del contenedor. Algunas imágenes pueden usar múltiples variantes de las arquitecturas arm, como arm/v5 y arm/v7.

    --volume, -v=[[VOLUMEN-ORIGEN|DIR-HOST:]DIR-CONTENEDOR[:OPCIONES]]

    Crea un montaje bind. Si se especifica -v /DIR-HOST:/DIR-CONTENEDOR, Podman monta /DIR-HOST desde el host en /DIR-CONTENEDOR en el contenedor Podman. De manera similar, -v VOLUMEN-ORIGEN:/DIR-CONTENEDOR monta el volumen con nombre desde el host en el contenedor. Si no existe dicho volumen con nombre, Podman crea uno. Si no se proporciona origen, el volumen se crea como un volumen con nombre anónimo y un nombre generado aleatoriamente, y se elimina cuando el contenedor se elimina mediante la bandera --rm o el comando podman rm --volumes.

    (Nota al usar el cliente remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), los volúmenes se montan desde el servidor remoto, no necesariamente desde la máquina cliente).

    Las OPCIONES son una lista separada por comas y pueden ser una o más de:

    • rw|ro
    • z|Z
    • [O]
    • [U]
    • [no]copy
    • [no]dev
    • [no]exec
    • [no]suid
    • [r]bind
    • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Footnote1⟩
    • idmap[=opciones]

    El DIR-CONTENEDOR debe ser una ruta absoluta como /src/docs. El volumen se monta en el contenedor en este directorio.

    Si se especifica un origen de volumen, debe ser una ruta en el host o el nombre de un volumen con nombre. Las rutas del host pueden ser absolutas o relativas; las rutas relativas se resuelven en relación con el directorio en el que se ejecuta Podman. Si el origen no existe, Podman devuelve un error. Los usuarios deben pre-crear los archivos o directorios de origen.

    Cualquier origen que no comience con un . o / se trata como el nombre de un volumen con nombre. Si no existe un volumen con ese nombre, se crea. Los volúmenes creados con nombres no son anónimos y no son eliminados por la opción --rm y el comando podman rm --volumes.

    Especifique múltiples opciones -v para montar uno o más volúmenes en un contenedor.

    Montajes de volumen protegidos contra escritura

    Agregue la opción :ro o :rw para montar un volumen en modo de solo lectura o lectura-escritura, respectivamente. Por defecto, los volúmenes se montan en modo lectura-escritura. Vea los ejemplos.

    Cambio de propietario de montajes de volumen

    Cuando un volumen con nombre se monta por primera vez en un contenedor, Podman ajusta automáticamente la propiedad del punto de montaje del volumen durante la inicialización del contenedor. Esta operación de cambio de propietario ocurre bajo las siguientes condiciones:

    • El volumen aún no se ha utilizado (tiene NeedsChown establecido en true)
    • El volumen está vacío o aún no se ha copiado
    • El volumen no es administrado por un controlador de volumen externo
    • El controlador de volumen no es "image"

    Para volúmenes con montajes idmapped (usando la opción idmap), el cambio de propiedad tiene en cuenta las asignaciones del espacio de nombres de usuario del contenedor, pero el volumen idmapped conserva la asignación UID/GID correcta. Para volúmenes sin idmapping, el punto de montaje se cambia de propietario para que coincida con el usuario y grupo del proceso del contenedor, mapeado al espacio de nombres de usuario del host si el remapeo del espacio de nombres de usuario está habilitado.

    Si un contenedor se crea en un nuevo espacio de nombres de usuario, el UID y GID en el contenedor pueden corresponder a otro UID y GID en el host.

    El sufijo :U le dice a Podman que use el UID y GID correctos del host basados en el UID y GID dentro del contenedor, para cambiar recursivamente el propietario y el grupo del volumen de origen. Chowning recorre el sistema de archivos bajo el volumen y cambia el UID/GID en cada archivo. Si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, retrasando el inicio del contenedor.

    Advertencia: úselo con precaución ya que modifica el sistema de archivos del host.

    Etiquetado de montajes de volumen

    Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el OS.

    Para cambiar una etiqueta en el contexto del contenedor, agregue uno de los dos sufijos :z o :Z al montaje del volumen. Estos sufijos le dicen a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le dice a Podman que dos o más contenedores comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartidas permiten que todos los contenedores lean/escriban contenido. La opción Z le dice a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el contenedor actual puede usar un volumen privado.

    Nota: todos los contenedores dentro de un pod comparten la misma etiqueta SELinux. Esto significa que todos los contenedores dentro de dicho pod pueden leer/escribir volúmenes compartidos en el contenedor creado con :Z en cualquiera de los contenedores. Volver a etiquetar recorre el sistema de archivos bajo el volumen y cambia la etiqueta en cada archivo; si el volumen tiene miles de inodos, este proceso lleva mucho tiempo, retrasando el inicio del contenedor. Si el volumen se volvió a etiquetar previamente con la opción z, Podman está optimizado para no volver a etiquetar por segunda vez. Si se mueven archivos al volumen, las etiquetas se pueden cambiar manualmente con el comando chcon -Rt container_file_t RUTA.

    Nota: No vuelva a etiquetar archivos y directorios del sistema. Volver a etiquetar contenido del sistema podría hacer que otros servicios confinados en la máquina fallen. Para este tipo de contenedores, recomendamos deshabilitar la separación de SELinux. La opción --security-opt label=disable deshabilita la separación de SELinux para el contenedor. Por ejemplo, si un usuario quisiera montar su directorio personal completo en un contenedor, necesita deshabilitar la separación de SELinux.

    $ podman run --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

    Montajes de volumen superpuestos

    La bandera :O le dice a Podman que monte el directorio desde el host como almacenamiento temporal utilizando el sistema de archivos overlay. Los procesos del contenedor pueden modificar el contenido dentro del punto de montaje, que se almacena en el almacenamiento del contenedor en un directorio separado. En términos de overlay, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el contenedor termina de ejecutarse, de forma similar a como se desmonta un punto de montaje tmpfs.

    Para usuarios avanzados, la opción overlay también admite unidades upperdir y workdir personalizadas y no volátiles para el montaje overlay. Las unidades upperdir y workdir personalizadas pueden ser gestionadas completamente por los propios usuarios, y Podman no las elimina al finalizar el ciclo de vida. Ejemplo: :O,upperdir=/alguna/superior,workdir=/alguna/trabajo

    Las ejecuciones subsiguientes del contenedor verán el contenido del directorio de origen original, cualquier cambio de ejecuciones anteriores del contenedor ya no existirá.

    Un caso de uso del montaje overlay es compartir la caché de paquetes del host en el contenedor para acelerar las compilaciones.

    Nota: La bandera O entra en conflicto con otras opciones mencionadas anteriormente.

    El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor. Generalmente los contenedores pueden leer/ejecutar container_share_t y leer/escribir container_file_t. Si no se pueden cambiar las etiquetas en un volumen de origen, se debe deshabilitar la separación del contenedor SELinux para que el contenedor funcione.

    No modifique el directorio de origen montado en el contenedor con un montaje overlay, puede causar fallos inesperados. Solo modifique el directorio después de que el contenedor termine de ejecutarse.

    Propagación de montajes

    Por defecto, los volúmenes montados bind son privados. Esto significa que cualquier montaje realizado dentro del contenedor no es visible en el host y viceversa. Se puede cambiar este comportamiento especificando una propiedad de propagación de montaje de volumen. Cuando un volumen es shared, los montajes realizados bajo ese volumen dentro del contenedor son visibles en el host y viceversa.

    sa. Crear un volumen esclavo[1] ⟨#Footnote1⟩ habilita la propagación de montaje unidireccional: los montajes realizados en el host debajo de ese volumen son visibles dentro del contenedor, pero no al revés.

    Para controlar la propiedad de propagación de montaje de un volumen, se puede utilizar el indicador de propagación [r]compartido, [r]esclavo, [r]privado o el [r]desvinculable. La propiedad de propagación solo se puede especificar para volúmenes montados por enlace (bind mount) y no para volúmenes internos o volúmenes con nombre. Para que la propagación de montaje funcione, el punto de montaje de origen (el punto de montaje donde el directorio de origen está montado) debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe estar compartido. Y para volúmenes esclavos, el punto de montaje de origen debe estar compartido o esclavo. [1] ⟨#Footnote1⟩

    Para montar recursivamente un volumen y todos sus submontajes en un contenedor, utilice la opción rbind. Por defecto se utiliza la opción de enlace (bind), y los submontajes del directorio de origen no se montan en el contenedor.

    Montar el volumen con la opción copiar le indica a Podman que copie el contenido del directorio de destino subyacente a volúmenes internos recién creados. La copia solo ocurre en la creación inicial del volumen. El contenido no se copia cuando el volumen se utiliza posteriormente en diferentes contenedores. La opción copiar se ignora en los montajes por enlace (bind mounts) y no tiene efecto.

    Montar volúmenes con la opción nosuid significa que los ejecutables SUID en el volumen no pueden ser utilizados por las aplicaciones para cambiar sus privilegios. Por defecto, los volúmenes se montan con nosuid.

    Montar el volumen con la opción noexec significa que ningún ejecutable en el volumen puede ser ejecutado dentro del contenedor.

    Montar el volumen con la opción nodev significa que los procesos dentro del contenedor no pueden utilizar ningún dispositivo en el volumen. Por defecto, los volúmenes se montan con nodev.

    Si el DIRECTORIO-HOST es un punto de montaje, entonces el kernel ignora las opciones dev, suid y exec.

    Utilice df DIRECTORIo-HOST para determinar el montaje de origen, luego utilice findmnt -o TARGET,PROPAGATION directorio-montaje-origen para determinar las propiedades de propagación del montaje de origen. Si la utilidad findmnt(1) no está disponible, entonces se puede consultar la entrada de montaje del punto de montaje de origen en /proc/self/mountinfo. Consulte las "opciones opcionales" y vea si se especifican propiedades de propagación. Allí, shared:N significa que el montaje está compartido, master:N significa que el montaje es esclavo, y si no hay nada, el montaje es privado. [1] ⟨#Footnote1⟩

    Para cambiar las propiedades de propagación de un punto de montaje, utilice el comando mount(8). Por ejemplo, si se desea montar por enlace el directorio de origen /foo, se puede hacer mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convierte /foo en un punto de montaje compartido. Alternativamente, se pueden cambiar directamente las propiedades de propagación del montaje de origen. Suponga que / es el montaje de origen para /foo, entonces use mount --make-shared / para convertir / en un montaje compartido.

    Nota: si el usuario solo tiene derechos de acceso a través de un grupo, el acceso al volumen desde dentro de un contenedor sin privilegios falla.

    Montaje con ID mapeados

    Si se especifica idmap, se crea un montaje con ID mapeados al espacio de nombres de usuario de destino en el contenedor. La opción idmap admite un mapeo personalizado que puede ser diferente al espacio de nombres de usuario utilizado por el contenedor. El mapeo se puede especificar después de la opción idmap, como: idmap=uids=0-1-10#10-11-10;gids=0-100-10. Para cada triplete, el primer valor es el inicio de los ID del sistema de archivos de respaldo que se mapean al segundo valor en el host. La longitud de este mapeo se indica en el tercer valor. Múltiples rangos están separados por #.

    Utilice la opción --group-add keep-groups para pasar el acceso a los grupos suplementarios del usuario al contenedor.

    --volumes-from=CONTENEDOR[:OPCIONES]

    Monta volúmenes del o de los contenedores especificados. Se utiliza para compartir volúmenes entre contenedores. Las opciones son una lista separada por comas con los siguientes elementos disponibles:

    • rw|ro
    • z

    Monta volúmenes ya montados de un contenedor de origen en otro contenedor. CONTENEDOR puede ser un nombre o un ID. Para compartir un volumen, utilice la opción --volumes-from al ejecutar el contenedor de destino. Los volúmenes se pueden compartir incluso si el contenedor de origen no se está ejecutando.

    Por defecto, Podman monta los volúmenes en el mismo modo (lectura-escritura o solo lectura) en que están montados en el contenedor de origen. Esto se puede cambiar agregando una opción ro o rw.

    Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el sistema operativo.

    Para cambiar una etiqueta en el contexto del contenedor, agregue z al montaje del volumen. Este sufijo le indica a Podman que dos entidades comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban contenido.

    Si la ubicación del volumen del contenedor de origen se superpone con datos que residen en un contenedor de destino, entonces el volumen oculta esos datos en el destino.

    --workdir, -w=dir

    Directorio de trabajo dentro del contenedor.

    El directorio de trabajo por defecto para ejecutar binarios dentro de un contenedor es el directorio raíz (/). El desarrollador de la imagen puede establecer un valor predeterminado diferente con la instrucción WORKDIR. El operador puede anular el directorio de trabajo utilizando la opción -w.

    Estado de Salida

    El código de salida de podman run proporciona información sobre por qué el contenedor no se pudo ejecutar o por qué salió. Cuando podman run sale con un código distinto de cero, los códigos de salida siguen el estándar de chroot(1), véase a continuación:

    125 El error es de Podman en sí mismo

    $ podman run --foo busybox; echo $?
Error: unknown flag: --foo
125

    126 El comando contenido no se puede invocar

    $ podman run busybox /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

    127 El comando contenido no se puede encontrar

    $ podman run busybox foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

    Código de salida código de salida del comando contenido

    $ podman run busybox /bin/sh -c 'exit 3'; echo $?
3

    EJEMPLOS

    Ejecutar contenedor en modo de solo lectura

    Durante el desarrollo de imágenes de contenedor, los contenedores a menudo necesitan escribir en el contenido de la imagen. Instalando paquetes en /usr, por ejemplo. En producción, las aplicaciones rara vez necesitan escribir en la imagen. Las aplicaciones de contenedor escriben en volúmenes si necesitan escribir en sistemas de archivos. Las aplicaciones se pueden hacer más seguras ejecutándolas en modo de solo lectura utilizando el modificador --read-only. Esto protege la imagen del contenedor de modificaciones. Por defecto, los contenedores de solo lectura pueden escribir en datos temporales. Podman monta un tmpfs en /run y /tmp dentro del contenedor.

    $ podman run --read-only -i -t fedora /bin/bash

    Si el contenedor no escribe en ningún sistema de archivos dentro del contenedor, incluido tmpfs, establezca --read-only-tmpfs=false.

    $ podman run --read-only --read-only-tmpfs=false --tmpfs /run -i -t fedora /bin/bash

    Exponer librerías compartidas dentro del contenedor como solo lectura usando un glob

    $ podman run --mount type=glob,src=/usr/lib64/libnvidia\*,ro=true -i -t fedora /bin/bash

    Exponer mensajes de log del contenedor al log del host

    Montaje por enlace (bind mount) del directorio /dev/log para que los mensajes que se registran en el contenedor aparezcan en el syslog/journal del host.

    $ podman run -v /dev/log:/dev/log -i -t fedora /bin/bash

    Desde dentro del contenedor, pruebe esto enviando un mensaje al log.

    (bash)# logger "Hola desde mi contenedor"

    Luego salga y verifique el journal.

    (bash)# exit
$ journalctl -b | grep Hola

    Esto lista el mensaje enviado al logger.

    Adjuntar a uno o más de STDIN, STDOUT, STDERR

    Sin especificar la opción -a, Podman adjunta todo (stdin, stdout, stderr). Anule el valor predeterminado especificando -a (stdin, stdout, stderr), como en:

    $ podman run -a stdin -a stdout -i -t fedora /bin/bash

    Compartir IPC entre contenedores

    Usando shm_server.c disponible aquí: https://www.cs.cf.ac.uk/Dave/C/node27.html

    Probando el modo --ipc=host:

    El host muestra un segmento de memoria compartida con 7 pids adjuntos, que resulta ser de httpd:

    $ sudo ipcs -m
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status
0x01128e25 0          root       600        1000       7

    Ahora ejecute un contenedor regular, y correctamente NO ve el segmento de memoria compartida del host:

    $ podman run -it shm ipcs -m
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status

    Ejecute un contenedor con la nueva opción --ipc=host, y ahora ve el segmento de memoria compartida del httpd del host:

    $ podman run -it --ipc=host shm ipcs -m
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status
0x01128e25 0          root       600        1000       7

    Probando el modo --ipc=container:id:

    Inicia un contenedor con un programa para crear un segmento de memoria compartida:

    $ podman run -it shm bash
$ sudo shm/shm_server &
$ sudo ipcs -m
------ Segmentos de Memoria Compartida --------
key        shmid      owner      perms      bytes      nattch     status
0x0000162e 0          root       666        27         1

    La creación de un segundo contenedor muestra correctamente que no hay segmento de memoria compartida del primer contenedor:

    $ podman run shm ipcs -m
------ Segmentos de Memoria Compartida --------
key        shmid      owner      perms      bytes      nattch     status

    La creación de un tercer contenedor utilizando la opción --ipc=container:id, ahora muestra el segmento de memoria compartida del primero:

    $ podman run -it --ipc=container:ed735b2264ac shm ipcs -m
$ sudo ipcs -m
------ Segmentos de Memoria Compartida --------
key        shmid      owner      perms      bytes      nattch     status
0x0000162e 0          root       666        27         1

    Mapeo de Puertos para Uso Externo

    El puerto expuesto de una aplicación puede mapearse a un puerto del host utilizando el indicador -p. Por ejemplo, el puerto 80 de httpd puede mapearse al puerto 8080 del host utilizando lo siguiente:

    $ podman run -p 8080:80 -d -i -t fedora/httpd

    Montaje de Volúmenes Externos

    Para montar un directorio del host como un volumen de contenedor, especifique la ruta absoluta del directorio y la ruta absoluta para el directorio del contenedor separadas por dos puntos. Si la fuente es un volumen con nombre mantenido por Podman, se recomienda utilizar su nombre en lugar de la ruta al volumen. De lo contrario, el volumen se considera huérfano y se elimina con el comando podman volume prune:

    $ podman run -v /var/db:/data1 -i -t fedora bash
$ podman run -v data:/data2 -i -t fedora bash
$ podman run -v /var/cache/dnf:/var/cache/dnf:O -ti fedora dnf -y update

    Si el contenedor necesita un volumen montado escribible por un usuario que no sea root dentro del contenedor, utilice la opción U. Esta opción indica a Podman que cambie el propietario del volumen de origen para que coincida con el UID y GID predeterminados utilizados dentro del contenedor.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id -v ~/data:/var/lib/mysql:Z,U mariadb

    Alternativamente, si el contenedor necesita un volumen escribible por un usuario que no sea root dentro del contenedor, la opción --userns=keep-id permite a los usuarios especificar el UID y GID del usuario que ejecuta Podman a UIDs y GIDs específicos dentro del contenedor. Dado que los procesos que se ejecutan en el contenedor se ejecutan como el UID del usuario, pueden leer/escribir archivos propiedad del usuario.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id:uid=999,gid=999 -v ~/data:/var/lib/mysql:Z mariadb

    Usando indicadores --mount para montar un directorio del host como una carpeta de contenedor, especifique la ruta absoluta del directorio o el nombre del volumen, y la ruta absoluta dentro del directorio del contenedor:

    $ podman run --mount type=bind,src=/var/db,target=/data1 busybox sh
$ podman run --mount type=bind,src=volume-name,target=/data1 busybox sh

    Al usar SELinux, tenga en cuenta que el host no tiene conocimiento de la política SELinux del contenedor. Por lo tanto, en el ejemplo anterior, si la política SELinux está activada, el directorio /var/db no es escribible por el contenedor. Se produce un mensaje de "Permiso denegado" y se agrega un mensaje avc: al syslog del host.

    Para solucionar esto, en el momento de escribir esta página man, se debe ejecutar el siguiente comando para que se adjunte la etiqueta de tipo de política SELinux adecuada al directorio del host:

    $ chcon -Rt svirt_sandbox_file_t /var/db

    Ahora, escribir en el volumen /data1 en el contenedor está permitido y los cambios se reflejan en el host en /var/db.

    Uso de Etiquetado de Seguridad Alternativo

    Anule el esquema de etiquetado predeterminado para cada contenedor especificando el indicador --security-opt. Por ejemplo, especifique el nivel MCS/MLS, un requisito para sistemas MLS. Especificar el nivel en el siguiente comando permite compartir el mismo contenido entre contenedores.

    podman run --security-opt label=level:s0:c100,c200 -i -t fedora bash

    Un ejemplo de MLS podría ser:

    $ podman run --security-opt label=level:TopSecret -i -t rhel7 bash

    Para deshabilitar el etiquetado de seguridad para este contenedor en lugar de ejecutarlo con el

    indicador --permissive, use el siguiente comando:

    $ podman run --security-opt label=disable -i -t fedora bash

    Ajuste la política de seguridad en los procesos dentro de un contenedor especificando un tipo alternativo para el contenedor. Por ejemplo, ejecute un contenedor que solo tiene permitido escuchar en puertos de Apache ejecutando el siguiente comando:

    $ podman run --security-opt label=type:svirt_apache_t -i -t centos bash

    Tenga en cuenta que se debe escribir una política SELinux que defina un tipo svirt_apache_t.

    Para enmascarar rutas adicionales específicas en el contenedor, especifique las rutas separadas por dos puntos utilizando la opción mask con el indicador --security-opt.

    $ podman run --security-opt mask=/foo/bar:/second/path fedora bash

    Para desenmascarar todas las rutas que están enmascaradas por defecto, establezca la opción unmask en ALL. O para desenmascarar solo rutas específicas, especifique las rutas como se muestra arriba con la opción mask.

    $ podman run --security-opt unmask=ALL fedora bash

    Para desenmascarar todas las rutas que comienzan con /proc, establezca la opción unmask en /proc/*.

    $ podman run --security-opt unmask=/proc/* fedora bash
    $ podman run --security-opt unmask=/foo/bar:/sys/firmware fedora bash

    $ podman run -it --blkio-weight-device "/dev/sda:200" ubuntu

    Establecimiento de Parámetros del Kernel con Espacios de Nombres (Sysctls)

    El indicador --sysctl establece parámetros del kernel con espacios de nombres (sysctls) en el contenedor. Por ejemplo, para habilitar el reenvío de IP en el espacio de nombres de red del contenedor, ejecute este comando:

    $ podman run --sysctl net.ipv4.ip_forward=1 someimage

    Tenga en cuenta que no todos los sysctls tienen espacios de nombres. Podman no admite el cambio de sysctls dentro de un contenedor que también modifica el sistema host. A medida que el kernel evoluciona, esperamos que más sysctls tengan espacios de nombres.

    Consulte la definición de la opción --sysctl anterior para obtener la lista actual de sysctls admitidos.

    Establecer mapeo UID/GID en un nuevo espacio de nombres de usuario

    Ejecutar un contenedor en un nuevo espacio de nombres de usuario requiere un mapeo de los UIDs y GIDs del host.

    $ podman run --uidmap 0:30000:7000 --gidmap 0:30000:7000 fedora echo hello

    Configuración de Opciones de Almacenamiento desde la Línea de Comandos

    Podman permite la configuración del almacenamiento cambiando los valores en /etc/container/storage.conf o utilizando opciones globales. Esto muestra cómo usar una tienda de imágenes adicional para una ejecución única de busybox utilizando opciones globales.

    podman --log-level=debug --storage-opt "additionalimagestore=/tmp/readonly-images" run busybox /bin/sh

    $ podman run --tz=local alpine date
$ podman run --tz=Asia/Shanghai alpine date
$ podman run --tz=US/Eastern alpine date

    Adición de Contenedores Dependientes

    El primer contenedor, container1, no se inicia inicialmente, pero debe estar en ejecución antes de que comience container2. El comando podman run inicia el contenedor automáticamente antes de iniciar container2.

    $ podman create --name container1 -t -i fedora bash
$ podman run --name container2 --requires container1 -t -i fedora bash

    Se pueden requerir varios contenedores.

    $ podman create --name container1 -t -i fedora bash
$ podman create --name container2 -t -i fedora bash
$ podman run --name container3 --requires container1,container2 -t -i fedora bash

    NAME

    podman-run - Run a container

    SYNOPSIS

    podman run [options] IMAGE [[COMMAND] [ARG...]]

    podman container run [options] IMAGE [[COMMAND] [ARG...]]

    DESCRIPTION

    The podman run command runs a new container from the specified image. Podman can run containers in the background, attach to containers, and to run containers that are based on a different image or Dockerfile. Podman can also run a container with a different command and arguments than the default specified by the image.

    A container is a runnable instance of an image. You can create one or more containers from the same image. For example, a web server image can be used to run multiple containers, each acting as an instance of the web server.

    This command is the of the docker run command.

    IMAGE

    The IMAGE parameter is the name of the image to use for the container. The name can be in the form [registry]/[repository]/[name]:[tag]. If the image is not found locally, Podman attempts to pull it from a registry. If no tag is specified, latest is assumed.

    Rootless Containers

    Podman runs as a non-root user on most systems. This feature requires that a new enough version of shadow-utils be installed. The shadow-utils package must include the newuidmap(1) and newgidmap(1) executables.

    In order for users to run rootless, there must be an entry for their username in /etc/subuid and /etc/subgid which lists the UIDs for their user namespace.

    Rootless Podman works better if the fuse-overlayfs and slirp4netns packages are installed. The fuse-overlayfs package provides a userspace overlay storage driver, otherwise users need to use the vfs storage driver, which can be disk space expensive and less performant than other drivers.

    To enable VPN on the container, slirp4netns or pasta needs to be specified; without either, containers need to be run with the --network=host flag.

    ENVIRONMENT

    Environment variables within containers can be set using multiple different options, in the following order of precedence (later entries override earlier entries):

    • Container image: Any environment variables specified in the container image.
    • --http-proxy: By default, several environment variables are passed in from the host, such as http_proxy and no_proxy. See --http-proxy for details.
    • --env-host: Host environment of the process executing Podman is added.
    • --env-file: Any environment variables specified via env-files. If multiple files are specified, then they override each other in order of entry.
    • --env: Any environment variables specified overrides previous settings.

    Run containers and set the environment ending with a *. The trailing * glob functionality is only active when no value is specified:

    $ export ENV1=a
$ podman run --env 'ENV*' alpine env | grep ENV
ENV1=a
$ podman run --env 'ENV*=b' alpine env | grep ENV
ENV*=b

    CONMON

    When Podman starts a container it actually executes the conmon program, which then executes the OCI Runtime. Conmon is the container monitor. It is a small program whose job is to watch the primary process of the container, and if the container dies, save the exit code. It also holds open the tty of the container, so that it can be attached to later. This is what allows Podman to run in detached mode (backgrounded), so Podman can exit but conmon continues to run. Each container has their own instance of conmon. Conmon waits for the container to exit, gathers and saves the exit code, and then launches a Podman process to complete the container cleanup, by shutting down the network and storage. For more information about conmon, see the conmon(8) man page.
