NAME

podman-farm-build - Build images on farm nodes, then bundle them into a manifest list

SYNOPSIS

podman farm build [options] [context]

DESCRIPTION

podman farm build Builds an image on all nodes in a farm and bundles them up into a manifest list. It executes the podman build command on the nodes in the farm with the given Containerfile. Once the images are built on all the farm nodes, the images will be pushed to the registry given via the --tag flag. Once all the images have been pushed, a manifest list will be created locally and pushed to the registry as well.

The manifest list will contain an image per native architecture type that is present in the farm.

The primary function of this command is to create multi-architecture builds that will be faster than doing it via emulation using podman build --arch --platform.

If no farm is specified, the build will be sent out to all the nodes that podman system connection knows of.

Note: Since the images built are directly pushed to a registry, the user must pass in a full image name using the --tag option in the format registry/repository/imageName[:tag]`.

OPTIONS

--add-host=hostname[;hostname[;...]]:ip

Add a custom host-to-IP mapping to the container's /etc/hosts file.

The option takes one or multiple semicolon-separated hostnames to be mapped to a single IPv4 or IPv6 address, separated by a colon. It can also be used to overwrite the IP addresses of hostnames Podman adds to /etc/hosts by default (also see the --name and --hostname options). This option can be specified multiple times to add additional mappings to /etc/hosts. It conflicts with the --no-hosts option and conflicts with no_hosts=true in containers.conf.

Instead of an IP address, the special flag host-gateway can be given. This resolves to an IP address the container can use to connect to the host. The IP address chosen depends on your network setup, thus there's no guarantee that Podman can determine the host-gateway address automatically, which will then cause Podman to fail with an error message. You can overwrite this IP address using the host_containers_internal_ip option in containers.conf.

The host-gateway address is also used by Podman to automatically add the host.containers.internal and host.docker.internal hostnames to /etc/hosts. You can prevent that by either giving the --no-hosts option, or by setting host_containers_internal_ip="none" in containers.conf. If no host-gateway address was configured manually and Podman fails to determine the IP address automatically, Podman will silently skip adding these internal hostnames to /etc/hosts. If Podman is running in a virtual machine using podman machine (this includes Mac and Windows hosts), Podman will silently skip adding the internal hostnames to /etc/hosts, unless an IP address was configured manually; the internal hostnames are resolved by the gvproxy DNS resolver instead.

Podman will use the /etc/hosts file of the host as a basis by default, i.e. any hostname present in this file will also be present in the /etc/hosts file of the container. A different base file can be configured using the base_hosts_file config in containers.conf.

--annotation=annotation=value

Add an image annotation (e.g. annotation=value) to the image metadata. Can be used multiple times.

Note: this information is not present in Docker image formats, so it is discarded when writing images in Docker formats.

--authfile=path

Path of the authentication file. Default is ${XDG_RUNTIME_DIR}/containers/auth.json on Linux, and $HOME/.config/containers/auth.json on Windows/macOS. The file is created by podman login. If the authorization state is not found there, $HOME/.docker/config.json is checked, which is set using docker login.

Note: There is also the option to override the default path of the authentication file by setting the REGISTRY_AUTH_FILE environment variable. This can be done with export REGISTRY_AUTH_FILE=path.

--build-arg=arg=value

Specifies a build argument and its value, which is interpolated in instructions read from the Containerfiles in the same way that environment variables are, but which are not added to environment variable list in the resulting image's configuration.

--build-arg-file=path

Specifies a file containing lines of build arguments of the form arg=value. The suggested file name is argfile.conf.

Comment lines beginning with # are ignored, along with blank lines. All others must be of the arg=value format passed to --build-arg.

If several arguments are provided via the --build-arg-file and --build-arg options, the build arguments are merged across all of the provided files and command line arguments.

Any file provided in a --build-arg-file option is read before the arguments supplied via the --build-arg option.

When a given argument name is specified several times, the last instance is the one that is passed to the resulting builds. This means --build-arg values always override those in a --build-arg-file.

--build-context=name=value

Specify an additional build context using its short name and its location. Additional build contexts can be referenced in the same manner as we access different stages in COPY instruction.

Valid values are:

  • Local directory – e.g. --build-context project2=../path/to/project2/src
  • HTTP URL to a tarball – e.g. --build-context src=https://example.org/releases/src.tar
  • Container image – specified with a container-image:// prefix, e.g. --build-context alpine=container-image://alpine:3.15, (also accepts docker://, docker-image://)

On the Containerfile side, reference the build context on all commands that accept the “from” parameter. Here’s how that might look:

FROM [name]
COPY --from=[name] ...
RUN --mount=from=[name] …

The value of [name] is matched with the following priority order:

  • Named build context defined with --build-context [name]=..
  • Stage defined with AS [name] inside Containerfile
  • Image [name], either local or in a remote registry

--cache-from=image

Repository to utilize as a potential cache source. When specified, Buildah tries to look for cache images in the specified repository and attempts to pull cache images instead of actually executing the build steps locally. Buildah only attempts to pull previously cached images if they are considered as valid cache hits.

Use the --cache-to option to populate a remote repository with cache content.

Example

# populate a cache and also consult it
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Note: --cache-from option is ignored unless --layers is specified.

--cache-to=image

Set this flag to specify a remote repository that is used to store cache images. Buildah attempts to push newly built cache image to the remote repository.

Note: Use the --cache-from option in order to use cache content in a remote repository.

Example

# populate a cache and also consult it
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Note: --cache-to option is ignored unless --layers is specified.

--cache-ttl

Limit the use of cached images to only consider

images con marcas de tiempo de creación inferiores a duración. Por ejemplo, si se especifica --cache-ttl=1h, Buildah considera las imágenes intermedias de caché creadas en el transcurso de una hora e ignora las imágenes intermedias de caché fuera de esa duración.

Nota: Establecer --cache-ttl=0 manualmente equivale a usar --no-cache en la implementación, ya que esto significa que el usuario no desea utilizar la caché en absoluto.

--cap-add=CAP_xxx

Al ejecutar instrucciones RUN, ejecuta el comando especificado en la instrucción con la capacidad especificada añadida a su conjunto de capacidades. Se otorgan ciertas capacidades por defecto; esta opción se puede utilizar para añadir más.

--cap-drop=CAP_xxx

Al ejecutar instrucciones RUN, ejecuta el comando especificado en la instrucción con la capacidad especificada eliminada de su conjunto de capacidades. Las capacidades CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP y CAP_SETUID se otorgan por defecto; esta opción se puede utilizar para eliminarlas.

Si una capacidad se especifica tanto a la opción --cap-add como a la opción --cap-drop, se elimina, independientemente del orden en que se hayan dado las opciones.

--cert-dir=ruta

Utiliza los certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. (Por defecto: /etc/containers/certs.d) Para más detalles, consulta containers-certs.d(5). (Esta opción no está disponible con el cliente remoto de Podman, incluyendo máquinas Mac y Windows (excluyendo WSL2))

--cgroup-parent=ruta

Ruta a los cgroups bajo los cuales se crea el cgroup para el contenedor. Si la ruta no es absoluta, se considera que la ruta es relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen ya.

--cgroupns=modo

Establece la configuración para los namespaces de cgroup al manejar las instrucciones RUN. El valor configurado puede ser "" (la cadena vacía) o "private" para indicar que se crea un nuevo namespace de cgroup, o puede ser "host" para indicar que se reutiliza el namespace de cgroup en el que se está ejecutando buildah.

--cleanup

Elimina las imágenes creadas de los nodos de granja en caso de éxito (Por defecto: false).

--compat-volumes

Maneja los directorios marcados usando la instrucción VOLUME (tanto en esta compilación como los heredados de las imágenes base) de tal manera que sus contenidos solo puedan ser modificados por las instrucciones ADD y COPY. Cualquier cambio realizado en esas ubicaciones por instrucciones RUN será revertido. Antes de la introducción de esta opción, este comportamiento era el predeterminado, pero ahora está deshabilitado por defecto.

--cpp-flag=flags

Establece flags adicionales para pasar al preprocesador C cpp(1). Los Containerfiles que terminan con el sufijo ".in" se preprocesan a través de cpp(1). Esta opción se puede utilizar para pasar flags adicionales a cpp. Nota: También puedes establecer CPPFLAGS por defecto estableciendo la variable de entorno BUILDAH_CPPFLAGS (por ejemplo, export BUILDAH_CPPFLAGS="-DDEBUG").

--cpu-period=límite

Establece el período de CPU para el Completely Fair Scheduler (CFS), que es una duración en microsegundos. Una vez que la cuota de CPU del contenedor se agota, no se programará para ejecutarse hasta que termine el período actual. El valor por defecto es 100000 microsegundos.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpu-quota=límite

Limita la cuota del Completely Fair Scheduler (CFS) de la CPU.

Limita el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso de CPU completo. El límite es un número en microsegundos. Si se proporciona un número, al contenedor se le permite usar esa cantidad de tiempo de CPU hasta que finalice el período de CPU (controlable a través de --cpu-period).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpu-shares, -c=shares

Shares de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de la participación de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso por defecto es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden utilizar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía dependiendo del número de contenedores en ejecución en el sistema.

Por ejemplo, considera tres contenedores, uno tiene un cpu-share de 1024 y otros dos tienen una configuración de cpu-share de 512. Cuando los procesos en los tres contenedores intentan utilizar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con un cpu-share de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las shares de tiempo de CPU se distribuyen en todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede utilizar el 100% de cada núcleo de CPU individual.

Por ejemplo, considera un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de shares de CPU:

PID contenedor CPU Share de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de estos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo es efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), usa --cpuset-mems=0,1 y entonces los procesos en el contenedor solo usarán memoria de los dos primeros nodos de memoria.

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulta https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no es compatible con sistemas sin root en cgroups V1.

--created-annotation

Añade una anotación de imagen (ver también --annotation) a los metadatos de la imagen estableciendo "org.opencontainers.image.created" a la hora actual, o a la marca de fecha especificada para el flag --source-date-epoch o --timestamp, si alguno de ellos se utilizó. Si es false, no habrá ninguna anotación de este tipo en la imagen escrita.

Nota: esta información no está presente en los formatos de imagen de Docker, por lo que se descarta al escribir imágenes en formatos de Docker.

--creds=[usuario[:contraseña]]

El [usuario[:contraseña]] a utilizar para autenticarse en el registro, si es necesario. Si no se proporcionan uno o ambos valores, aparecerá un prompt de línea de comandos y se podrá introducir el valor. La contraseña se introduce sin eco.

Ten en cuenta que las credenciales especificadas solo se utilizan para autenticarse en los registros de destino. No se utilizan para espejos ni cuando el registro se reescribe (ver containers-registries.conf(5)); para autenticarse contra estos, considera usar un archivo containers-auth.json(5).

--decryption-key=clave[:contraseña]

La [clave[:contraseña]] a utilizar para el descifrado de imágenes. La clave puede apuntar a claves y/o certificados. El descifrado se intenta con todas las claves. Si la clave está protegida por una contraseña, es obligatorio pasarla en el argumento y omitirla en caso contrario.

--pull=política

Política para descargar imágenes. El valor por defecto es missing.

  • always: Descarga siempre la imagen y genera un error si la descarga falla.
  • missing: Solo descarga la imagen cuando no existe en el almacenamiento local de contenedores. Genera un error si no se encuentra ninguna imagen y la descarga falla.
  • never: Nunca descarga la imagen, utiliza la del almacenamiento local de contenedores. Genera un error cuando no se encuentra ninguna imagen.
  • newer: Descarga si la imagen en el registro es más reciente que la del almacenamiento local de contenedores. Una imagen se considera más reciente cuando los resúmenes (digests) son diferentes. Comparar las marcas de tiempo es propenso a errores. Los errores de descarga se suprimen si se encontró una imagen local.

--source-date-epoch=segundos

Establece la marca de tiempo "creado" para la imagen compilada en este número de segundos desde la época (Unix time 0, es decir, 00:00:00 UTC el 1 de enero de 1970) (el valor predeterminado es usar el valor establecido en la variable de entorno SOURCE_DATE_EPOCH, o la hora actual si no está establecida).

La marca de tiempo "creado" se escribe en la configuración y el manifiesto de la imagen cuando la imagen se confirma, por lo que ejecutar la misma compilación dos veces producirá imágenes con diferentes hashes sha256, incluso si no se realizaron otros cambios en el Containerfile y el contexto de compilación.

Cuando se establece esta bandera, un argumento de compilación SOURCE_DATE_EPOCH proporcionará su valor para una etapa en la que se declare.

Cuando se establece esta bandera, la marca de tiempo "creado" de la configuración de la imagen siempre se establece en la hora especificada, lo que debería permitir compilar imágenes idénticas en momentos diferentes utilizando el mismo conjunto de entradas.

Cuando se establece esta bandera, la salida escrita según lo especificado en la bandera **--output** llevará exactamente la marca de tiempo especificada.

Entra en conflicto con la bandera similar **--timestamp**, que también establece la hora especificada en el contenido de las nuevas capas.

Especifica el nombre que se asigna a la imagen resultante si el proceso de compilación se completa con éxito. Si nombreImagen no incluye un nombre de registro, se antepone el nombre de registro localhost al nombre de la imagen.

--target=nombreEtapa

Establece la etapa de compilación de destino a compilar. Al compilar un Containerfile con múltiples etapas de compilación, --target se puede usar para especificar una etapa de compilación intermedia por nombre como etapa final para la imagen resultante. Los comandos posteriores a la etapa de destino se omiten.

--timestamp=segundos

Establece la marca de tiempo de creación en segundos desde la época para permitir compilaciones deterministas (predeterminado a la hora actual). Por defecto, la marca de tiempo de creación se modifica y se escribe en el manifiesto de la imagen con cada confirmación, lo que hace que el hash sha256 de la imagen sea diferente incluso si las fuentes son exactamente las mismas. Cuando se establece --timestamp, la marca de tiempo de creación siempre se establece en la hora especificada y, por lo tanto, no se modifica, lo que permite que el hash sha256 de la imagen permanezca igual. Todos los archivos confirmados en las capas de la imagen se crean con la marca de tiempo.

Si la única instrucción en un Containerfile es FROM, esta bandera no tiene ningún efecto.

--tls-verify

Requiere HTTPS y verifica los certificados al contactar con los registros (predeterminado: **true**). Si se establece explícitamente en **true**, se utiliza la verificación TLS. Si se establece en **false**, no se utiliza la verificación TLS. Si no se especifica, se utiliza la verificación TLS a menos que el registro de destino figure como un registro inseguro en containers-registries.conf(5)

--ulimit=tipo=límite-suave[:límite-duro]

Especifica los límites de recursos a aplicar a los procesos lanzados al procesar instrucciones RUN. Esta opción se puede especificar varias veces. Los tipos de recursos reconocidos incluyen:
"core": tamaño máximo de volcado de núcleo (ulimit -c)
"cpu": tiempo máximo de CPU (ulimit -t)
"data": tamaño máximo del segmento de datos de un proceso (ulimit -d)
"fsize": tamaño máximo de los archivos nuevos (ulimit -f)
"locks": número máximo de bloqueos de archivos (ulimit -x)
"memlock": cantidad máxima de memoria bloqueada (ulimit -l)
"msgqueue": cantidad máxima de datos en colas de mensajes (ulimit -q)
"nice": ajuste de cortesía (nice -n, ulimit -e)
"nofile": número máximo de archivos abiertos (ulimit -n)
"nproc": número máximo de procesos (ulimit -u)
"rss": tamaño máximo de un proceso (ulimit -m)
"rtprio": prioridad máxima de programación en tiempo real (ulimit -r)
"rttime": tiempo máximo de ejecución en tiempo real entre llamadas al sistema bloqueantes
"sigpending": número máximo de señales pendientes (ulimit -i)
"stack": tamaño máximo de la pila (ulimit -s)

--unsetenv=variable

NOMBRE

podman-farm-build - Construye imágenes y listas de manifiestos para una granja de compilación

SINOPSIS

podman farm build [opciones] [build-args...]

DESCRIPCIÓN

Construye imágenes y listas de manifiestos para una granja de compilación. La granja se define en el archivo de configuración de Podman.

Si no se especifica ningún nombre de granja, se utilizará la granja predeterminada definida en el archivo de configuración de Podman.

El comando puede utilizar el archivo Containerfile(5) o containerignore(5) para construir imágenes.

El comando construye imágenes para las plataformas especificadas y crea una lista de manifiestos que puede ser utilizada para desplegar imágenes en diferentes arquitecturas.

Por defecto, las opciones de montaje de volúmenes se establecen en private. Esto significa que cualquier montaje realizado dentro de los contenedores no será visible en el host y viceversa. Este comportamiento se puede cambiar especificando una propiedad de propagación de montaje de volumen.

Cuando la política de propagación de montaje se establece en shared, cualquier montaje realizado dentro del contenedor en ese volumen será visible tanto para el host como para el contenedor. Cuando la política de propagación de montaje se establece en slave, se habilita la propagación de montaje unidireccional y cualquier montaje realizado en el host para ese volumen solo será visible dentro del contenedor. Para controlar la propiedad de propagación de montaje del volumen, utilice los indicadores de propagación :[r]shared, :[r]slave o :[r]private. Para que la propagación de montaje funcione, el punto de montaje de origen (el punto de montaje donde se monta el directorio de origen) debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe estar compartido. Y para volúmenes esclavo, el montaje de origen debe ser compartido o esclavo. [1]

Utilice df <directorio-origen> para determinar el montaje de origen y luego utilice findmnt -o TARGET,PROPAGATION <directorio-montaje-origen> para determinar las propiedades de propagación del montaje de origen; si la utilidad findmnt no está disponible, el punto de montaje de origen se puede determinar buscando la entrada de montaje en /proc/self/mountinfo. Busque los campos opcionales y vea si se especifican propiedades de propagación. shared:X significa que el montaje está compartido, master:X significa que el montaje es esclavo y si no hay nada, significa que el montaje es privado. [1]

Para cambiar las propiedades de propagación de un punto de montaje, utilice el comando mount. Por ejemplo, para montar por enlace el directorio de origen /foo, ejecute mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convierte /foo en un punto de montaje compartido. Las propiedades de propagación del montaje de origen se pueden cambiar directamente. Por ejemplo, si / es el montaje de origen para /foo, entonces utilice mount --make-shared / para convertir / en un montaje compartido.

Las opciones de montaje de volúmenes son una lista separada por comas y pueden ser una o más de las siguientes:

  • [rw|ro]
  • [z|Z|O]
  • [U]
  • [[r]shared|[r]slave|[r]private][1] ⟨#Footnote1⟩

CONTAINER-DIR debe ser una ruta absoluta como /src/docs. HOST-DIR también debe ser una ruta absoluta. Podman monta por enlace HOST-DIR a la ruta especificada al procesar instrucciones RUN.

Puede especificar varias opciones -v para montar uno o más montajes.

Puede añadir el sufijo :ro o :rw a un volumen para montarlo en modo de solo lectura o de lectura/escritura, respectivamente. Por defecto, los volúmenes se montan en modo de lectura/escritura. Ver ejemplos.

Cambio de propietario de los montajes de volumen

Por defecto, Podman no cambia el propietario ni el grupo de los directorios de volumen de origen que se montan. Al ejecutarse utilizando espacios de nombres de usuario, la UID y el GID dentro del espacio de nombres pueden corresponder a otra UID y GID en el host.

El sufijo :U indica a Podman que utilice la UID y el GID correctos del host basándose en la UID y el GID dentro del espacio de nombres, para cambiar recursivamente el propietario y el grupo del volumen de origen.

Advertencia: Úselo con precaución ya que esto modifica el sistema de archivos del host.

Etiquetado de montajes de volumen

Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen que se monta en un contenedor. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. Por defecto, Podman no cambia las etiquetas establecidas por el sistema operativo.

Para cambiar una etiqueta en el contexto del contenedor, añada uno de estos dos sufijos :z o :Z al montaje del volumen. Estos sufijos indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z indica a Podman que dos contenedores comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban el contenido. La opción Z indica a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el contenedor actual puede utilizar un volumen privado.

Nota: No vuelva a etiquetar archivos y directorios del sistema. Volver a etiquetar contenido del sistema puede hacer que otros servicios confinados en la máquina host fallen. Para este tipo de contenedores, se recomienda deshabilitar la separación de SELinux. La opción --security-opt label=disable deshabilita la separación de SELinux para el contenedor. Por ejemplo, si un usuario quisiera montar por volumen todo su directorio de inicio en los contenedores de compilación, necesitaría deshabilitar la separación de SELinux.

$ podman build --security-opt label=disable -v $HOME:/home/user .

Montajes de volumen superpuestos

El indicador :O indica a Podman que monte el directorio del host como almacenamiento temporal utilizando el sistema de archivos Overlay. A los contenedores del comando RUN se les permite modificar el contenido dentro del punto de montaje y se almacena en el almacenamiento del contenedor en un directorio separado. En términos de Overlay FS, el directorio de origen es el inferior y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el comando RUN termina de ejecutarse, de forma similar a un punto de montaje tmpfs.

Cualquier ejecución posterior de comandos RUN verá el contenido original del directorio de origen; los cambios de comandos RUN anteriores ya no existirán.

Un caso de uso del montaje overlay es compartir la caché de paquetes del host en el contenedor para acelerar las compilaciones.

Nota:

  • Los montajes superpuestos no son compatibles actualmente en modo sin raíz.
  • El indicador O no puede especificarse con los indicadores Z o z. El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor. Si no es así, la separación de contenedores de SELinux debe deshabilitarse para que el contenedor funcione.
  • La modificación del directorio del volumen montado en el contenedor con un montaje superpuesto puede causar fallos inesperados. No modifique el directorio hasta que el contenedor termine de ejecutarse.

--build-arg, --buildarg

Elimina todas las imágenes de los nodos de la granja después de ser enviadas al registro.

Nombre del Containerfile(5) a utilizar.
--farm
Nombre de la granja a utilizar.

Nombre y etiqueta de la imagen a crear, en la forma "nombre:etiqueta".

Especifica las plataformas para las que se construirán las imágenes. El valor es una lista separada por comas de las arquitecturas. Por ejemplo, "--platforms arm64,amd64".

EJEMPLOS

Construye una imagen y lista de manifiestos nombradas utilizando un Containerfile especificado con la granja predeterminada:

$ podman farm build --local -t name -f /path/to/containerfile .

Construye una imagen y lista de manifiestos nombradas utilizando la granja especificada:

$ podman farm build --farm myfarm -t name .

Construye una imagen y lista de manifiestos nombradas utilizando la granja especificada, eliminando todas las imágenes de los nodos de la granja después de ser enviadas al registro:

$ podman farm build --farm myfarm --cleanup -t name .

Construye imágenes y listas de manifiestos nombradas para las plataformas especificadas utilizando la granja predeterminada:

$ podman farm build --platforms arm64,amd64 -t name .
