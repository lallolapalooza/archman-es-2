Deficiencias de Podman sin Raíz

La siguiente lista categoriza los problemas y las irregularidades conocidos al ejecutar Podman como un usuario no root. Aunque actualmente funcional, todavía hay una serie de elementos de trabajo que se están considerando para ser añadidos. Estos cambios propuestos se encuentran en diversos grados de diseño y desarrollo.

Los colaboradores son más que bienvenidos a ayudar con este trabajo. Si decide abordar una parte y trabajar en ella, por favor cree un problema en GitHub y asígnelo a usted mismo. Si encuentra algún otro comportamiento inesperado con Podman sin raíz y siente que está justificado, no dude en actualizar este documento.

•
Podman no puede crear contenedores que se enlacen a puertos < 1024.
  • El kernel no permite que los procesos sin CAP_NET_BIND_SERVICE se enlacen a puertos bajos.
  • Puede modificar el sysctl de net.ipv4.ip_unprivileged_port_start para cambiar el puerto más bajo. Por ejemplo, sysctl net.ipv4.ip_unprivileged_port_start=443 permite que los contenedores de Podman sin raíz se enlacen a puertos >= 443.
  • Se puede utilizar un servidor proxy, una regla de firewall del kernel o una herramienta de redirección como redir para redirigir el tráfico de un puerto privilegiado a uno no privilegiado (donde un pod de Podman está enlazado) en un escenario de servidor, donde un usuario tiene acceso a la cuenta root (o el bit setuid en el binario sería un riesgo aceptable), pero quiere ejecutar los contenedores como un usuario no privilegiado para mejorar la seguridad y para un número limitado de puertos predefinidos.
•
A partir de Podman 5.0, pasta es la herramienta de red por defecto. Dado que pasta copia la dirección IP de la interfaz principal, las conexiones a esa IP desde los contenedores no funcionan. Esto significa que, a menos que tenga más de una interfaz, las conexiones entre contenedores no se pueden realizar sin pasar explícitamente una configuración de red de pasta, ya sea en containers.conf o en tiempo de ejecución.
•
Si anteriormente tenía reenvíos de puertos (ej. mediante -p 80:80) a los que otros contenedores podían acceder, puede volver a slirp4netns o utilizar la solución (configurando opciones de pasta con IPs 10.0.2.x) publicada aquí.
  • La documentación "Cómo hacer" es, en el mejor de los casos, irregular.
  • Si /etc/subuid y /etc/subgid no están configurados para un usuario, entonces los comandos de Podman pueden fallar fácilmente.
  • Este puede ser un gran problema en máquinas que utilizan información de contraseña basada en red (FreeIPA, Active Directory, LDAP).
  • Estamos trabajando para obtener soporte para NSSWITCH en los archivos /etc/subuid y /etc/subgid.
•
Sin soporte para cgroup V1
  • cgroup V1 no soporta de forma segura la delegación de cgroup.
  • A partir de Fedora 31, se utiliza por defecto cgroup V2, que tiene soporte completo para la gestión de cgroup sin raíz. Tenga en cuenta que esto requiere que el --cgroup-manager dentro de los contenedores sin raíz utilice systemd, lo que los nuevos contenedores obtendrán por defecto.
•
Algunas opciones de configuración de unidades del sistema no funcionan en el contenedor sin raíz.
  • systemd no aplica varias opciones y los errores se ignoran silenciosamente (por ejemplo, CPUShares, MemoryLimit). Debería funcionar en cgroup V2.
  • El uso de ciertas opciones provocará errores al iniciar el servicio (por ejemplo, PrivateNetwork). Los servicios de systemd que requieren PrivateNetwork pueden funcionar pasando --cap-add SYS_ADMIN, pero las implicaciones de seguridad deben evaluarse cuidadosamente. En la mayoría de los casos, es mejor crear un archivo de anulación (override.conf) que establezca PrivateNetwork=no. Esto también se aplica a los contenedores ejecutados por root.
  • No se pueden compartir imágenes de contenedores con CRI-O u otros usuarios con raíz.
  • Difícil de usar almacenes adicionales para compartir contenido.
  • No funciona en homedirs montados en NFS o sistemas de archivos paralelos (por ejemplo, GPFS).
  • NFS y los sistemas de archivos paralelos aplican la creación de archivos en diferentes UIDs en el lado del servidor y no entienden el Espacio de Nombres de Usuario.
  • Cuando un proceso root del contenedor como YUM intenta crear un archivo propiedad de un UID diferente, NFS Server/GPFS deniega la creación.
•
No funciona con homedirs montados con noexec/nodev.
•
El usuario puede configurar el almacenamiento para que apunte a otros directorios en los que pueda escribir y que no estén montados como noexec/nodev.
•
El soporte para usar overlayfs nativo como usuario no privilegiado solo está disponible para la versión de Podman >= 3.1 en una versión del kernel de Linux >= 5.12, de lo contrario, se puede utilizar el más lento fuse-overlayfs.
•
Algunas distribuciones de Linux (por ejemplo, Ubuntu) han admitido versiones aún más antiguas de Podman y del kernel de Linux modificando el comportamiento normal del kernel de Linux.
  • El único otro controlador soportado es VFS.
  • No se puede usar ping de inmediato.
•
(Se puede solucionar configurando sysctl en el host)
  • Requiere shadow-utils nuevos (no encontrados en distribuciones antiguas como RHEL7/Centos7). Debería corregirse en la versión RHEL7.7).
  • Algunos comandos no funcionan.
•
mount/unmount (en fuse-overlay)
•
Solo funciona si ingresa al espacio de nombres de montaje con `podman unshare`.
  • podman stats (Funciona con soporte para cgroup V2).
  • Checkpoint y Restore (CRIU requiere root).
  • Pause y Unpause (Funciona con soporte para cgroup V2).
•
Los problemas con UIDs más altos pueden causar fallos en la compilación.
•
Si una compilación intenta usar un UID que no está mapeado en el espacio de nombres de usuario para un contenedor, entonces las compilaciones no podrán poner el UID en una imagen.
•
La creación de nodos de dispositivo dentro de un contenedor falla, incluso cuando se ejecuta --privileged.
•
El kernel no permite que los procesos sin privilegios de root (procesos sin CAP_MKNOD) creen nodos de dispositivo. Si un contenedor necesita crear nodos de dispositivo, debe ejecutarse como root.
•
Cuando se usa --net=host con contenedores sin raíz, los `podman exec` subsiguientes a ese contenedor no se unirán al espacio de nombres de red del host porque es propiedad de root.
