PROLOG

Esta página del manual forma parte del Manual del programador de POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual correspondiente de Linux para obtener detalles sobre el comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

posix_spawn, posix_spawnp — crear un proceso (TIEMPO REAL AVANZADO)

SINOPSIS

#include <spawn.h>
int posix_spawn(pid_t *restrict pid, const char *restrict path,
    const posix_spawn_file_actions_t *file_actions,
    const posix_spawnattr_t *restrict attrp,
    char *const argv[restrict], char *const envp[restrict]);
int posix_spawnp(pid_t *restrict pid, const char *restrict file,
    const posix_spawn_file_actions_t *file_actions,
    const posix_spawnattr_t *restrict attrp,
    char *const argv[restrict], char *const envp[restrict]);

DESCRIPCIÓN

Las funciones posix_spawn() y posix_spawnp() crearán un nuevo proceso (proceso hijo) a partir de la imagen de proceso especificada. La nueva imagen de proceso se construirá a partir de un archivo ejecutable regular llamado archivo de imagen de nuevo proceso.

Cuando un programa C se ejecuta como resultado de esta llamada, se entrará en él como una llamada a función del lenguaje C de la siguiente manera:

int main(int argc, char *argv[]);

donde argc es el número de argumentos y argv es un array de punteros a caracteres de los propios argumentos. Además, la siguiente variable:

extern char **environ;

se inicializará como un puntero a un array de punteros a caracteres de las cadenas de entorno.

El argumento argv es un array de punteros a caracteres de cadenas terminadas en nulo. El último miembro de este array será un puntero nulo y no se cuenta en argc. Estas cadenas constituyen la lista de argumentos disponible para la nueva imagen de proceso. El valor en argv[0] debe apuntar a una cadena de nombre de archivo que esté asociada con la imagen de proceso que se está iniciando mediante la función posix_spawn() o posix_spawnp().

El argumento envp es un array de punteros a caracteres de cadenas terminadas en nulo. Estas cadenas constituyen el entorno para la nueva imagen de proceso. El array de entorno está terminado por un puntero nulo.

El número de bytes disponibles para las listas combinadas de argumentos y entorno del proceso hijo es {ARG_MAX}. La implementación especificará en la documentación del sistema (consulte el volumen de Definiciones Base de POSIX.1‐2017, Capítulo 2, Conformidad) si algún sobrecoste de lista, como palabras de longitud, terminadores nulos, punteros o bytes de alineación, se incluye en este total.

El argumento path para posix_spawn() es una ruta que identifica el archivo de imagen del nuevo proceso a ejecutar.

El parámetro file para posix_spawnp() se utilizará para construir una ruta que identifique el archivo de imagen del nuevo proceso. Si el parámetro file contiene un carácter <barra> (‘/’), el parámetro file se utilizará como ruta para el archivo de imagen del nuevo proceso. De lo contrario, el prefijo de ruta para este archivo se obtendrá mediante una búsqueda en los directorios pasados como variable de entorno PATH (consulte el volumen de Definiciones Base de POSIX.1‐2017, Capítulo 8, Variables de entorno). Si esta variable de entorno no está definida, los resultados de la búsqueda son definidos por la implementación.

Si file_actions es un puntero nulo, entonces los descriptores de archivo abiertos en el proceso llamante permanecerán abiertos en el proceso hijo, excepto aquellos cuyo flag de cierre al ejecutar FD_CLOEXEC esté establecido (consulte fcntl()). Para aquellos descriptores de archivo que permanezcan abiertos, el proceso hijo no heredará ningún bloqueo de archivo, pero todos los demás atributos de las descripciones de archivo abiertas correspondientes (consulte fcntl()) permanecerán sin cambios.

Si file_actions no es NULL, entonces los descriptores de archivo abiertos en el proceso hijo serán los abiertos en el proceso llamante, modificados por el objeto de acciones de archivo de creación de procesos apuntado por file_actions y el flag FD_CLOEXEC de cada descriptor de archivo abierto restante después de que se hayan procesado las acciones de archivo de creación de procesos. El orden efectivo de procesamiento de las acciones de archivo de creación de procesos será:

1.
El conjunto de descriptores de archivo abiertos para el proceso hijo será inicialmente el mismo conjunto que está abierto para el proceso llamante. El proceso hijo no heredará ningún bloqueo de archivo, pero todos los demás atributos de las descripciones de archivo abiertas correspondientes (consulte fcntl()) permanecerán sin cambios.
2.
La máscara de señales, las acciones predeterminadas de señales y las ID de usuario y grupo efectivas para el proceso hijo se modificarán según lo especificado en el objeto de atributos referenciado por attrp.
3.
Las acciones de archivo especificadas por el objeto de acciones de archivo de creación de procesos se realizarán en el orden en que se agregaron al objeto de acciones de archivo de creación de procesos.
4.
Se cerrará cualquier descriptor de archivo que tenga su flag FD_CLOEXEC establecido (consulte fcntl()).

Si los descriptores de archivo 0, 1 o 2 se cerraran de otra manera en la imagen del nuevo proceso creada por posix_spawn() o posix_spawnp(), las implementaciones pueden abrir un archivo no especificado para el descriptor de archivo en la nueva imagen de proceso. Si una utilidad estándar o una aplicación que cumpla las normas se ejecuta con el descriptor de archivo 0 no abierto para lectura o con el descriptor de archivo 1 o 2 no abierto para escritura, el entorno en el que se ejecuta la utilidad o aplicación se considerará no conforme, y en consecuencia, la utilidad o aplicación podría no comportarse como se describe en este estándar.

El tipo de objeto de atributos de creación de procesos posix_spawnattr_t se define en <spawn.h>. Contendrá al menos los atributos definidos a continuación.

Si el flag POSIX_SPAWN_SETPGROUP está establecido en los spawn-flags del objeto referenciado por attrp, y el atributo spawn-pgroup del mismo objeto no es cero, entonces el grupo de procesos del hijo será el especificado en el atributo spawn-pgroup del objeto referenciado por attrp.

Como caso especial, si el flag POSIX_SPAWN_SETPGROUP está establecido en los spawn-flags del objeto referenciado por attrp, y el atributo spawn-pgroup del mismo objeto está establecido en cero, entonces el hijo estará en un nuevo grupo de procesos con un ID de grupo de procesos igual a su ID de proceso.

Si el flag POSIX_SPAWN_SETPGROUP no está establecido en los spawn-flags del objeto referenciado por attrp, el nuevo proceso hijo heredará el grupo de procesos del padre.

Si el flag POSIX_SPAWN_SETSCHEDPARAM está establecido en los spawn-flags del objeto referenciado por attrp, pero POSIX_SPAWN_SETSCHEDULER no está establecido, la nueva imagen de proceso tendrá inicialmente la política de planificación del proceso llamante con los parámetros de planificación especificados en el atributo spawn-schedparam del objeto referenciado por attrp.

Si el flag POSIX_SPAWN_SETSCHEDULER está establecido en los spawn-flags del objeto referenciado por attrp (independientemente de la configuración del flag POSIX_SPAWN_SETSCHEDPARAM), la nueva imagen de proceso tendrá inicialmente la política de planificación especificada en el atributo spawn-schedpolicy del objeto referenciado por attrp y los parámetros de planificación especificados en el atributo spawn-schedparam del mismo objeto.

El flag POSIX_SPAWN_RESETIDS en los spawn-flags del objeto referenciado por attrp rige el ID de usuario efectivo del proceso hijo. Si este flag no está establecido, el proceso hijo heredará el ID de usuario efectivo del proceso padre. Si este flag está establecido, el ID de usuario efectivo del proceso hijo se restablecerá al ID de usuario real del padre. En cualquier caso, si el bit de modo set-user-ID del archivo de la nueva imagen de proceso está establecido, el ID de usuario efectivo del proceso hijo se convertirá en el ID del propietario de ese archivo antes de que la nueva imagen de proceso comience a ejecutarse.

El flag POSIX_SPAWN_RESETIDS en los spawn-flags del objeto referenciado por attrp también rige el ID de grupo efectivo del proceso hijo. Si este flag no está establecido, el proceso hijo heredará el ID de grupo efectivo del proceso padre. Si este flag está establecido, el ID de grupo efectivo del proceso hijo se restablecerá al ID de grupo real del padre. En cualquier caso, si el bit de modo set-group-ID del archivo de la nueva imagen de proceso está establecido, el ID de grupo efectivo del proceso hijo se convertirá en el ID de grupo de ese archivo antes de que la nueva imagen de proceso comience a ejecutarse.

DESCRIPCIÓN

La nueva imagen de proceso comienza la ejecución.

Si el flag POSIX_SPAWN_SETSIGMASK está configurado en el atributo spawn-flags del objeto al que se hace referencia con attrp, el proceso hijo tendrá inicialmente la máscara de señales especificada en el atributo spawn-sigmask del objeto al que se hace referencia con attrp.

Si el flag POSIX_SPAWN_SETSIGDEF está configurado en el atributo spawn-flags del objeto al que se hace referencia con attrp, las señales especificadas en el atributo spawn-sigdefault del mismo objeto se establecerán en sus acciones predeterminadas en el proceso hijo. Las señales establecidas para la acción predeterminada en el proceso padre se establecerán para la acción predeterminada en el proceso hijo.

Las señales que se establecen para ser capturadas por el proceso llamador se establecerán en la acción predeterminada en el proceso hijo.

Excepto por SIGCHLD, las señales que se establecen para ser ignoradas por la imagen del proceso llamador se establecerán para ser ignoradas por el proceso hijo, a menos que se especifique lo contrario por el flag POSIX_SPAWN_SETSIGDEF configurado en el atributo spawn-flags del objeto al que se hace referencia con attrp y las señales que se indican en el atributo spawn-sigdefault del objeto al que se hace referencia con attrp.

Si la señal SIGCHLD se establece para ser ignorada por el proceso llamador, no se especifica si la señal SIGCHLD se establecerá para ser ignorada o para la acción predeterminada en el proceso hijo, a menos que se especifique lo contrario por el flag POSIX_SPAWN_SETSIGDEF configurado en el atributo spawn_flags del objeto al que se hace referencia con attrp y la señal SIGCHLD indicada en el atributo spawn_sigdefault del objeto al que se hace referencia con attrp.

Si el valor del puntero attrp es NULL, se utilizan los valores predeterminados.

Todos los atributos del proceso, aparte de aquellos influenciados por los atributos establecidos en el objeto al que se hace referencia con attrp como se especificó anteriormente o por las manipulaciones de descriptores de archivo especificadas en file_actions, aparecerán en la nueva imagen del proceso como si se hubiera llamado a fork() para crear un proceso hijo y luego un miembro de la familia de funciones exec hubiera sido llamado por el proceso hijo para ejecutar la nueva imagen del proceso.

Es definido por la implementación si los manejadores de fork se ejecutan cuando se llama a posix_spawn() o posix_spawnp().

VALOR DE RETORNO

Al completarse con éxito, posix_spawn() y posix_spawnp() devolverán el ID del proceso hijo al proceso padre, en la variable apuntada por un argumento pid no NULL, y devolverán cero como valor de retorno de la función. De lo contrario, no se creará ningún proceso hijo, el valor almacenado en la variable apuntada por un argumento pid no NULL no está especificado y se devolverá un número de error como valor de retorno de la función para indicar el error. Si el argumento pid es un puntero nulo, el ID del proceso hijo no se devuelve al llamador.

ERRORES

Estas funciones pueden fallar si:

EINVAL
El valor especificado por file_actions o attrp es inválido.

Si ocurre este error después de que el proceso llamador retorne con éxito de la función posix_spawn() o posix_spawnp(), el proceso hijo puede salir con el estado de salida 127.

Si posix_spawn() o posix_spawnp() fallan por cualquiera de las razones que harían fallar a fork() o a una de las funciones de la familia exec, se devolverá un valor de error como se describe por fork() y exec, respectivamente (o, si el error ocurre después de que el proceso llamador retorne con éxito, el proceso hijo saldrá con el estado de salida 127).

Si POSIX_SPAWN_SETPGROUP está configurado en el atributo spawn-flags del objeto al que se hace referencia con attrp, y posix_spawn() o posix_spawnp() fallan mientras cambian el grupo de procesos del hijo, se devolverá un valor de error como se describe por setpgid() (o, si el error ocurre después de que el proceso llamador retorne con éxito, el proceso hijo saldrá con el estado de salida 127).

Si POSIX_SPAWN_SETSCHEDPARAM está configurado y POSIX_SPAWN_SETSCHEDULER no está configurado en el atributo spawn-flags del objeto al que se hace referencia con attrp, entonces si posix_spawn() o posix_spawnp() fallan por cualquiera de las razones que harían fallar a sched_setparam(), se devolverá un valor de error como se describe por sched_setparam() (o, si el error ocurre después de que el proceso llamador retorne con éxito, el proceso hijo saldrá con el estado de salida 127).

Si POSIX_SPAWN_SETSCHEDULER está configurado en el atributo spawn-flags del objeto al que se hace referencia con attrp, y si posix_spawn() o posix_spawnp() fallan por cualquiera de las razones que harían fallar a sched_setscheduler(), se devolverá un valor de error como se describe por sched_setscheduler() (o, si el error ocurre después de que el proceso llamador retorne con éxito, el proceso hijo saldrá con el estado de salida 127).

Si el argumento file_actions no es NULL, y especifica alguna acción de close, dup2, o open a realizar, y si posix_spawn() o posix_spawnp() fallan por cualquiera de las razones que harían fallar a close(), dup2(), o open(), se devolverá un valor de error como se describe por close(), dup2(), y open(), respectivamente (o, si el error ocurre después de que el proceso llamador retorne con éxito, el proceso hijo saldrá con el estado de salida 127). Una acción de apertura de archivo puede, por sí misma, resultar en cualquiera de los errores descritos por close() o dup2(), además de aquellos descritos por open().

FUNDAMENTOS DE DISEÑO

La función posix_spawn() y su estrecha relación posix_spawnp() se han introducido para superar las siguientes dificultades percibidas con fork(): la función fork() es difícil o imposible de implementar sin intercambio o traducción de direcciones dinámica.

*
El intercambio es generalmente demasiado lento para un entorno en tiempo real.
*
La traducción de direcciones dinámica no está disponible en todos los lugares donde POSIX podría ser útil.
*
Los procesos son demasiado útiles como para simplemente omitirlos de POSIX cuando debe ejecutarse sin traducción de direcciones u otros servicios de MMU.

Por lo tanto, POSIX necesita primitivas de creación de procesos y ejecución de archivos que puedan implementarse de manera eficiente sin traducción de direcciones u otros servicios de MMU.

La función posix_spawn() se puede implementar como una rutina de biblioteca, pero tanto posix_spawn() como posix_spawnp() están diseñadas como operaciones de kernel. Además, aunque pueden ser un reemplazo eficiente para muchos pares fork()/exec, su objetivo es proporcionar primitivas de creación de procesos útiles para sistemas que tienen dificultades con fork(), no para proporcionar reemplazos directos para fork()/exec.

Esta visión del papel de posix_spawn() y posix_spawnp() influyó en el diseño de su API. No intenta proporcionar la funcionalidad completa de fork()/exec en la que se permiten operaciones arbitrarias especificadas por el usuario de cualquier tipo entre la creación del proceso hijo y la ejecución de la nueva imagen del proceso; cualquier intento de alcanzar ese nivel requeriría proporcionar un lenguaje de programación como parámetro. En cambio, posix_spawn() y posix_spawnp() son primitivas de creación de procesos como el paquete de enlaces del lenguaje Ada POSIX_Process_Primitives Start_Process y Start_Process_Search, y también como las de muchos sistemas operativos que no son sistemas UNIX, pero con algunas adiciones específicas de POSIX.

Para lograr sus objetivos de cobertura, posix_spawn() y posix_spawnp() tienen control de seis tipos de herencia: descriptores de archivo, ID de grupo de procesos, ID de usuario y grupo, máscara de señales, programación y si cada señal ignorada en el padre permanecerá ignorada en el hijo, o se restablecerá a su acción predeterminada en el hijo.

El control de los descriptores de archivo es necesario para permitir que una imagen de proceso hijo escrita de forma independiente acceda a los flujos de datos abiertos por e incluso generados o leídos por el proceso padre sin estar específicamente codificada para saber qué archivos y descriptores de archivo del padre se utilizarán. El control del ID de grupo de procesos es necesario para controlar cómo se relaciona el control de trabajo del proceso hijo con el del padre.

El control de la máscara de señales y la acción predeterminada de señales es suficiente para soportar la implementación de system(). Aunque el soporte para system() no es explícitamente uno de los objetivos para posix_spawn() y posix_spawnp(), se cubre bajo el objetivo de cobertura "al menos el 50%".

La intención es que la herencia normal de descriptores de archivo a través de fork(), el efecto posterior de las acciones de archivo de spawn especificadas, y la herencia normal de descriptores de archivo a través de una de las funciones de la familia exec especifiquen completamente la herencia de descriptores de archivo abiertos. La implementación no necesita tomar decisiones con respecto al conjunto de descriptores de archivo abiertos cuando la imagen del proceso hijo comienza la ejecución, esas decisiones ya han sido tomadas por el llamador y expresadas como el conjunto de descriptores de archivo abiertos y sus flags FD_CLOEXEC en el momento de la llamada y el objeto de acciones de archivo de spawn especificado en la llamada. Se nos ha asegurado que en los casos en que las primitivas de Ada Start_Process de POSIX se han implementado en una biblioteca, este método de control de herencia de descriptores de archivo puede implementarse muy fácilmente.

Podemos identificar varios problemas con posix_spawn() y posix_spawnp(), pero no parece haber una solución que introduzca menos problemas. La modificación del entorno para atributos del proceso hijo no especificables a través de los argumentos attrp o file_actions debe realizarse en el proceso padre, y dado que el padre generalmente quiere guardar su contexto, es más costoso que la funcionalidad similar con fork()/exec. También es complicado modificar el entorno de un proceso multihilo temporalmente, ya que todos los hilos deben acordar cuándo es seguro cambiar el entorno. Sin embargo, este costo solo lo soportan aquellas invocaciones de posix_spawn

NAME

posix_spawn, posix_spawnp - create a new process

SYNOPSIS

#include <spawn.h>

int posix_spawn(pid_t *restrict pid, const char *restrict file,
    const posix_spawn_file_actions_t *file_actions,
    const posix_spawnattr_t *restrict attrp,
    char *const argv[restrict], char *const envp[restrict]);
int posix_spawnp(pid_t *restrict pid, const char *restrict file,
    const posix_spawn_file_actions_t *file_actions,
    const posix_spawnattr_t *restrict attrp,
    char *const argv[restrict], char *const envp[restrict]);

DESCRIPTION

The posix_spawn() and posix_spawnp() functions create a new process. The new process is the child process, and the calling process is the parent process.

The difference between posix_spawn() and posix_spawnp() is the same as the difference between execlp() and execvp(): posix_spawnp() searches the PATH for the specified file.

The child process inherits copies of the parent's file descriptors. The file_actions parameter is a pointer to an object that specifies desired modifications to the child's file descriptor state. These modifications include closing specified file descriptors and duplicating specified file descriptors to other specified file descriptors. If file_actions is NULL, then the child process inherits copies of the parent's file descriptors.

The attrp parameter is a pointer to a structure that specifies process attributes for the child process. These attributes include the child's process group ID, scheduling policy and parameters, and signal handling settings. If attrp is NULL, then the child process inherits the parent's process group ID, scheduling policy, and parameters, and signals that are blocked remain blocked in the child, and signals that are not blocked remain not blocked. The default signal actions are set for all signals that are not blocked.

The child process is created with the command interpreter specified by file. The argv parameter is a pointer to an array of character pointers that is terminated by a NULL pointer. The first element of this array is the name of the command to be executed. The envp parameter is a pointer to an array of character pointers that is terminated by a NULL pointer. Each element of this array is a string of the form "name=value".

If posix_spawn() or posix_spawnp() is successful, the value of the child's process ID is returned in the location referenced by pid, and the function returns 0. If posix_spawn() or posix_spawnp() fails, no child process is created, and the return value is a positive error code.

The posix_spawn() and posix_spawnp() functions are intended to provide a more efficient and flexible way to create processes than the traditional fork() followed by exec() combination.

The posix_spawn() and pos_spawnp() functions are similar to the process creation operations on many non-UNIX operating systems. They are designed to be implementable without special hardware requirements, such as an MMU.

Extensive modifications to the child process environment are discouraged to keep the functions simple and fast. For more complex process creation, the fork() and exec family of functions should be used.

The posix_spawn() and posix_spawnp() functions do not have all the power of fork()/exec(). This is by design. fork() is a very powerful operation, and duplicating its full functionality in a simple, fast function without special hardware requirements is not expected.

The parameter list does not differ between posix_spawn() and posix_spawnp(); posix_spawnp() interprets the second parameter more elaborately than posix_spawn().

The process group inheritance field can be used to join the child process with an existing process group. By assigning a value of zero to the spawn-pgroup attribute of the object referenced by attrp, the setpgid() mechanism will place the child process in a new process group.

Without the posix_spawn() and posix_spawnp() functions, systems without address translation can still use threads to give an abstraction of concurrency. In many cases, thread creation suffices, but it is not always a good substitute. The posix_spawn() and posix_spawnp() functions are considerably ``heavier'' than thread creation. Processes have several important attributes that threads do not. Even without address translation, a process may have base-and-bound memory protection. Each process has a process environment including security attributes and file capabilities, and powerful scheduling attributes. Processes abstract the behavior of non-uniform-memory-architecture multi-processors better than threads, and they are more convenient to use for activities that are not closely linked.

The posix_spawn() and posix_spawnp() functions may not bring support for multiple processes to every configuration. Process creation is not the only piece of operating system support required to support multiple processes. The total cost of support for multiple processes may be quite high in some circumstances. Existing practice shows that support for multiple processes is uncommon and threads are common among ``tiny kernels''. There should, therefore, probably continue to be AEPs for operating systems with only one process.

A library implementation of posix_spawn() or posix_spawnp() may not be able to detect all possible errors before it forks the child process. POSIX.1‐2008 provides for an error indication returned from a child process which could not successfully complete the spawn operation via a special exit status which may be detected using the status value returned by wait(), waitid(), and waitpid().

The stat_val interface and the macros used to interpret it are not well suited to the purpose of returning API errors, but they are the only path available to a library implementation. Thus, an implementation may cause the child process to exit with exit status 127 for any error detected during the spawn process after the posix_spawn() or posix_spawnp() function has successfully returned.

The standard developers had proposed using two additional macros to interpret stat_val. The first, WIFSPAWNFAIL, would have detected a status that indicated that the child exited because of an error detected during the posix_spawn() or posix_spawnp() operations rather than during actual execution of the child process image; the second, WSPAWNERRNO, would have extracted the error value if WIFSPAWNFAIL indicated a failure. Unfortunately, the ballot group strongly opposed this because it would make a library implementation of posix_spawn() or posix_spawnp() dependent on kernel modifications to waitpid() to be able to embed special information in stat_val to indicate a spawn failure.

The 8 bits of child process exit status that are guaranteed by POSIX.1‐2008 to be accessible to the waiting parent process are insufficient to disambiguate a spawn error from any other kind of error that may be returned by an arbitrary process image. No other bits of the exit status are required to be visible in stat_val, so these macros could not be strictly implemented at the library level. Reserving an exit status of 127 for such spawn errors is consistent with the use of this value by system() and popen() to signal failures in these operations that occur after the function has returned but before a shell is able to execute. The exit status of 127 does not uniquely identify this class of error, nor does it provide any detailed information on the nature of the failure. Note that a kernel implementation of posix_spawn() or posix_spawnp() is permitted (and encouraged) to return any possible error as the function value, thus providing more detailed failure information to the parent process.

Thus, no special macros are available to isolate asynchronous posix_spawn() or posix_spawnp() errors. Instead, errors detected by the posix_spawn() or posix_spawnp() operations in the context of the child process before the new process image executes are reported by setting the child's exit status to 127. The calling process may use the WIFEXITED and WEXITSTATUS macros on the stat_val stored by the wait() or waitpid() functions to detect spawn failures to the extent that other status values with which the child process image may exit (before the parent can conclusively determine that the child process image has begun execution) are distinct from exit status 127.

IMPLEMENTATION NOTES

The posix_spawn() and posix_spawnp() functions are intended to be a more efficient alternative to fork() and the exec family of functions. They are designed to be implementable without special hardware requirements, such as an MMU.

Extensive modifications to the child process environment are discouraged to keep the functions simple and fast. For more complex process creation, the fork() and exec family of functions should be used.

The posix_spawn() and posix_spawnp() functions do not have all the power of fork()/exec(). This is to be expected. The fork() function is a wonderfully powerful operation. We do not expect to duplicate its functionality in a simple, fast function with no special hardware requirements. It is worth noting that posix_spawn() and posix_spawnp() are very similar to the process creation operations on many operating systems that are not UNIX systems.

Requirements

The requirements for posix_spawn() and posix_spawnp() are:

*
They must be implementable without an MMU or unusual hardware.
*
They must be compatible with existing POSIX standards.

Additional goals are:

*
They should be efficiently implementable.
*
They should be able to replace at least 50% of typical executions of fork().
*
A system with posix_spawn() and posix_spawnp() and without fork() should be useful, at least for realtime applications.
*
A system with fork() and the exec family should be able to implement posix_spawn() and posix_spawnp() as library routines.

Two-Syntax

POSIX exec has several calling sequences with approximately the same functionality. These appear to be required for compatibility with existing practice. Since the existing practice for the posix_spawn*() functions is otherwise substantially unlike POSIX, we feel that simplicity outweighs compatibility. There are, therefore, only two names for the posix_spawn*() functions.

The parameter list does not differ between posix_spawn() and posix_spawnp(); posix_spawnp() interprets the second parameter more elaborately than posix_spawn().

Compatibility with POSIX.5 (Ada)

The Start_Process and Start_Process_Search procedures from the POSIX_Process_Primitives package from the Ada language binding to POSIX.1 encapsulate fork() and exec functionality in a manner similar to that of posix_spawn() and posix_spawnp(). Originally, in keeping with our simplicity goal, the standard developers had limited the capabilities of posix_spawn() and posix_spawnp() to a subset of the capabilities of Start_Process and Start_Process_Search; certain non-default capabilities were not supported. However, based on suggestions by the ballot group to improve file descriptor mapping or drop it, and on the advice of an Ada Language Bindings working group member, the standard developers decided that posix_spawn() and posix_spawnp() should be sufficiently powerful to implement Start_Process and Start_Process_Search. The rationale is that if the Ada language binding to such a primitive had already been approved as an IEEE standard, there can be little justification for not approving the functionally-equivalent parts of a C binding. The only three capabilities provided by posix_spawn() and posix_spawnp() that are not provided by Start_Process and Start_Process_Search are optionally specifying the child's process group ID, the set of signals to be reset to default signal handling in the child process, and the child's scheduling policy and parameters.

For the Ada language binding for Start_Process to be implemented with posix_spawn(), that binding would need to explicitly pass an empty signal mask and the parent's environment to posix_spawn() whenever the caller of Start_Process allowed these arguments to default, since posix_spawn() does not provide such defaults. The ability of Start_Process to mask user-specified signals during its execution is functionally unique to the Ada language binding and must be dealt with in the binding separately from the call to posix_spawn().

Process Group

The process group inheritance field can be used to join the child process with an existing process group. By assigning a value of zero to the spawn-pgroup attribute of the object referenced by attrp, the setpgid() mechanism will place the child process in a new process group.

Threads

Without the posix_spawn() and posix_spawnp() functions, systems without address translation can still use threads to give an abstraction of concurrency. In many cases, thread creation suffices, but it is not always a good substitute. The posix_spawn() and posix_spawnp() functions are considerably ``heavier'' than thread creation. Processes have several important attributes that threads do not. Even without address translation, a process may have base-and-bound memory protection. Each process has a process environment including security attributes and file capabilities, and powerful scheduling attributes. Processes abstract the behavior of non-uniform-memory-architecture multi-processors better than threads, and they are more convenient to use for activities that are not closely linked.

The posix_spawn() and posix_spawnp() functions may not bring support for multiple processes to every configuration. Process creation is not the only piece of operating system support required to support multiple processes. The total cost of support for multiple processes may be quite high in some circumstances. Existing practice shows that support for multiple processes is uncommon and threads are common among ``tiny kernels''. There should, therefore, probably continue to be AEPs for operating systems with only one process.

Asynchronous Error Notification

A library implementation of posix_spawn() or posix_spawnp() may not be able to detect all possible errors before it forks the child process. POSIX.1‐2008 provides for an error indication returned from a child process which could not successfully complete the spawn operation via a special exit status which may be detected using the status value returned by wait(), waitid(), and waitpid().

The stat_val interface and the macros used to interpret it are not well suited to the purpose of returning API errors, but they are the only path available to a library implementation. Thus, an implementation may cause the child process to exit with exit status 127 for any error detected during the spawn process after the posix_spawn() or posix_spawnp() function has successfully returned.

The standard developers had proposed using two additional macros to interpret stat_val. The first, WIFSPAWNFAIL, would have detected a status that indicated that the child exited because of an error detected during the posix_spawn() or posix_spawnp() operations rather than during actual execution of the child process image; the second, WSPAWNERRNO, would have extracted the error value if WIFSPAWNFAIL indicated a failure. Unfortunately, the ballot group strongly opposed this because it would make a library implementation of posix_spawn() or posix_spawnp() dependent on kernel modifications to waitpid() to be able to embed special information in stat_val to indicate a spawn failure.

The 8 bits of child process exit status that are guaranteed by POSIX.1‐2008 to be accessible to the waiting parent process are insufficient to disambiguate a spawn error from any other kind of error that may be returned by an arbitrary process image. No other bits of the exit status are required to be visible in stat_val, so these macros could not be strictly implemented at the library level. Reserving an exit status of 127 for such spawn errors is consistent with the use of this value by system() and popen() to signal failures in these operations that occur after the function has returned but before a shell is able to execute. The exit status of 127 does not uniquely identify this class of error, nor does it provide any detailed information on the nature of the failure. Note that a kernel implementation of posix_spawn() or posix_spawnp() is permitted (and encouraged) to return any possible error as the function value, thus providing more detailed failure information to the parent process.

Thus, no special macros are available to isolate asynchronous posix_spawn() or posix_spawnp() errors. Instead, errors detected by the posix_spawn() or posix_spawnp() operations in the context of the child process before the new process image executes are reported by setting the child's exit status to 127. The calling process may use the WIFEXITED and WEXITSTATUS macros on the stat_val stored by the wait() or waitpid() functions to detect spawn failures to the extent that other status values with which the child process image may exit (before the parent can conclusively determine that the child process image has begun execution) are distinct from exit status 127.
