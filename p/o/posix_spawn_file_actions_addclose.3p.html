PROLOG

Esta página del manual es parte del Manual del programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

posix_spawn_file_actions_addclose, posix_spawn_file_actions_addopen — añadir acción de cierre o apertura al objeto de acciones de archivo de spawn (ADVANCED REALTIME)

SINOPSIS

#include <spawn.h>
int posix_spawn_file_actions_addclose(posix_spawn_file_actions_t
    *file_actions, int fildes);
int posix_spawn_file_actions_addopen(posix_spawn_file_actions_t
    *restrict file_actions, int fildes,
    const char *restrict path, int oflag, mode_t mode);

DESCRIPCIÓN

Estas funciones añadirán o eliminarán una acción de cierre o apertura a un objeto de acciones de archivo de spawn.

Un objeto de acciones de archivo de spawn es de tipo posix_spawn_file_actions_t (definido en <spawn.h>) y se utiliza para especificar una serie de acciones que serán realizadas por una operación posix_spawn() o posix_spawnp() para llegar al conjunto de descriptores de archivo abiertos para el proceso hijo, dado el conjunto de descriptores de archivo abiertos del proceso padre. POSIX.1‐2008 no define operadores de comparación o asignación para el tipo posix_spawn_file_actions_t.

Un objeto de acciones de archivo de spawn, cuando se pasa a posix_spawn() o posix_spawnp(), especificará cómo el conjunto de descriptores de archivo abiertos en el proceso llamante se transforma en un conjunto de descriptores de archivo potencialmente abiertos para el proceso generado. Esta transformación será como si la secuencia de acciones especificada se hubiera realizado exactamente una vez, en el contexto del proceso generado (antes de la ejecución de la nueva imagen del proceso), en el orden en que las acciones se añadieron al objeto; además, cuando se ejecute la nueva imagen del proceso, se cerrará cualquier descriptor de archivo (de este nuevo conjunto) que tenga establecido el flag FD_CLOEXEC (véase posix_spawn()).

La función posix_spawn_file_actions_addclose() añadirá una acción de cierre al objeto referenciado por file_actions que provocará el cierre del descriptor de archivo fildes (como si se hubiera llamado a close(fildes)) cuando se genere un nuevo proceso utilizando este objeto de acciones de archivo.

La función posix_spawn_file_actions_addopen() añadirá una acción de apertura al objeto referenciado por file_actions que provocará la apertura del archivo denominado por path (como si se hubiera llamado a open(path, oflag, mode), y el descriptor de archivo devuelto, si no es fildes, se hubiera cambiado a fildes) cuando se genere un nuevo proceso utilizando este objeto de acciones de archivo. Si fildes ya era un descriptor de archivo abierto, se cerrará antes de que se abra el nuevo archivo.

La cadena descrita por path será copiada por la función posix_spawn_file_actions_addopen().

VALOR DE RETORNO

Al completarse con éxito, estas funciones devolverán cero; de lo contrario, se devolverá un número de error para indicar el error.

ERRORES

La función posix_spawn_file_actions_addopen() fallará si:

EBADF
El valor especificado por fildes es negativo o mayor o igual que {OPEN_MAX}.

La función posix_spawn_file_actions_addclose() fallará si:

EBADF
El valor especificado por fildes es negativo.

Estas funciones pueden fallar si:

EINVAL
El valor especificado por file_actions es inválido.
ENOMEM
No existe memoria suficiente para añadir al objeto de acciones de archivo de spawn.

No se considerará un error que el argumento fildes pasado a estas funciones especifique un descriptor de archivo para el cual la operación especificada no pudo realizarse en el momento de la llamada. Cualquier error de este tipo se detectará cuando el objeto de acciones de archivo asociado se utilice posteriormente durante una operación posix_spawn() o posix_spawnp().

EJEMPLOS

Ninguno.

USO DE APLICACIÓN

Estas funciones forman parte de la opción Spawn y no tienen por qué estar disponibles en todas las implementaciones.

Las implementaciones pueden utilizar descriptores de archivo que deben heredarse en los procesos hijos para que el proceso hijo siga siendo conforme, como por ejemplo para fines de catálogo de mensajes o rastreo. Por lo tanto, una aplicación que llama a posix_spawn_file_actions_addclose() con un entero arbitrario corre el riesgo de un comportamiento no conforme, y esta función solo puede usarse de forma portable para cerrar valores de descriptores de archivo que la aplicación ha obtenido a través de acciones explícitas, o para los tres descriptores de archivo correspondientes a los flujos de archivo estándar. Para evitar una condición de carrera de fugas de un descriptor de archivo no intencionado en un proceso hijo, una aplicación debería considerar abrir todos los descriptores de archivo con el bit FD_CLOEXEC establecido, a menos que el descriptor de archivo esté destinado a heredarse a través de exec.

RACIÓNALE

Un objeto de acciones de archivo de spawn puede inicializarse para contener una secuencia ordenada de operaciones close(), dup2() y open() que serán utilizadas por posix_spawn() o posix_spawnp() para llegar al conjunto de descriptores de archivo abiertos heredados por el proceso generado a partir del conjunto de descriptores de archivo abiertos en el padre en el momento de la llamada a posix_spawn() o posix_spawnp(). Se había sugerido que las operaciones close() y dup2() por sí solas son suficientes para reorganizar los descriptores de archivo, y que los archivos que necesitan ser abiertos para su uso por el proceso generado pueden ser manejados ya sea teniendo el proceso llamante los abra antes de la llamada a posix_spawn() o posix_spawnp() (y cerrándolos después), o pasando nombres de ruta al proceso generado (en argv) para que pueda abrirlos él mismo. Los desarrolladores del estándar recomiendan que las aplicaciones utilicen uno de estos dos métodos cuando sea práctico, ya que el estado de error detallado de una operación de apertura fallida siempre está disponible para la aplicación de esta manera. Sin embargo, los desarrolladores del estándar sienten que permitir que un objeto de acciones de archivo de spawn especifique operaciones de apertura sigue siendo apropiado porque:

1.
Es consistente con la funcionalidad equivalente de POSIX.5 (Ada).
2.
Soporta el paradigma de redirección de E/S comúnmente empleado por los programas POSIX diseñados para ser invocados desde un shell. Cuando dicho programa es el proceso hijo, puede que no esté diseñado para abrir archivos por sí mismo.
3.
Permite aperturas de archivos que de otro modo podrían fallar o violar los derechos de propiedad/acceso de los archivos si fueran ejecutados por el proceso padre.

Respecto a 2. anterior, nótese que la acción de apertura de archivo de spawn proporciona a posix_spawn() y posix_spawnp() la misma capacidad que los operadores de redirección del shell proporcionan a system(), solo que sin la ejecución intermedia de un shell; por ejemplo:

system ("myprog <file1 3<file2");

Respecto a 3. anterior, nótese que si el proceso llamante necesita abrir uno o más archivos para acceso por el proceso generado, pero tiene descriptores de archivo de repuesto insuficientes, entonces la acción de apertura es necesaria para permitir que la open() ocurra en el contexto del proceso hijo después de que otros descriptores de archivo se hayan cerrado (que deben permanecer abiertos en el padre).

Además, si un padre se ejecuta desde un archivo con un bit de modo "set-user-id" establecido y el flag POSIX_SPAWN_RESETIDS está establecido en los atributos de spawn, un archivo creado dentro del proceso padre tendrá (posiblemente incorrectamente) el ID de usuario efectivo del padre como su propietario, mientras que un archivo creado a través de una acción open() durante posix_spawn() o posix_spawnp() tendrá el padre

posix_spawn_file_actions_addclose

NAME

posix_spawn_file_actions_addclose, posix_spawn_file_actions_addopen, posix_spawn_file_actions_adddup2, posix_spawn_file_actions_addchroot, posix_spawn_file_actions_addchdir, posix_spawn_file_actions_addfchdir, posix_spawn_file_actions_addclosefromfile, posix_spawn_file_actions_addchdir_np, posix_spawn_file_actions_addfchdir_np, posix_spawn_file_actions_addclosefromfile_np, posix_spawn_file_actions_addduplicate - add actions to spawn file actions object

SYNOPSIS

#include <spawn.h>

int posix_spawn_file_actions_addclose(
    posix_spawn_file_actions_t *restrict actions,
    int fildes);
int posix_spawn_file_actions_addopen(
    posix_spawn_file_actions_t *restrict actions,
    int fildes, const char *restrict path, int oflag,
    const struct std_cdev_stat *restrict mode);
int posix_spawn_file_actions_adddup2(
    posix_spawn_file_actions_t *restrict actions,
    int fildes, int newfildes);
int posix_spawn_file_actions_addchroot(
    posix_spawn_file_actions_t *restrict actions,
    const char *restrict path);
int pos_spawn_file_actions_addchdir(
    posix_spawn_file_actions_t *restrict actions,
    const char *restrict path);
int pos_spawn_file_actions_addfchdir(
    posix_spawn_file_actions_t *restrict actions,
    int fildes);
int pos_spawn_file_actions_addclosefromfile(
    posix_spawn_file_actions_t *restrict actions,
    int fildes);
int pos_spawn_file_actions_addchdir_np(
    pos_spawn_file_actions_t *restrict actions,
    const char *restrict path);
int pos_spawn_file_actions_addfchdir_np(
    posix_spawn_file_actions_t *restrict actions,
    int fildes);
int pos_spawn_file_actions_addclosefromfile_np(
    posix_spawn_file_actions_t *restrict actions,
    int fildes);
int pos_spawn_file_actions_addduplicate(
    posix_spawn_file_actions_t *restrict actions,
    int fildes, int newfildes);

DESCRIPTION

The posix_spawn_file_actions_addclose() function adds an operation to the object referenced by actions that will cause the file descriptor fildes to be closed in the child process after a successful call to posix_spawn() or posix_spawnp().

The posix_spawn_file_actions_addopen() function adds an operation to the object referenced by actions that will cause the file described by path to be opened with the specified flags oflag and mode mode in the child process after a successful call to posix_spawn() or posix_spawnp(). The new file descriptor will be assigned to fildes.

The posix_spawn_file_actions_adddup2() function adds an operation to the object referenced by actions that will cause the file descriptor fildes to be duplicated to newfildes in the child process after a successful call to posix_spawn() or posix_spawnp().

The posix_spawn_file_actions_addchroot() function adds an operation to the object referenced by actions that will cause the process's root directory to be changed to path in the child process after a successful call to posix_spawn() or posix_spawnp().

The posix_spawn_file_actions_addchdir() function adds an operation to the object referenced by actions that will cause the process's current working directory to be changed to path in the child process after a successful call to posix_spawn() or posix_spawnp().

The posix_spawn_file_actions_addfchdir() function adds an operation to the object referenced by actions that will cause the process's current working directory to be changed to the directory indicated by the file descriptor fildes in the child process after a successful call to posix_spawn() or posix_spawnp().

The posix_spawn_file_actions_addclosefromfile() function adds an operation to the object referenced by actions that will cause all file descriptors greater than or equal to fildes to be closed in the child process after a successful call to posix_spawn() or posix_spawnp().

The _np variants of these functions are non-portable extensions.

RETURN VALUE

Upon successful completion, these functions shall return 0. Otherwise, they shall return an error number.

ERRORS

The posix_spawn_file_actions_add*() functions may fail if:

[EINVAL]
The value specified by actions is not a valid posix_spawn_file_actions_t object.
[ENOMEM]
Insufficient memory is available to add the specified file action.

The posix_spawn_file_actions_addclose() function may fail if:

[EBADF]
fildes is not a valid open file descriptor. Implementations may also return [EINVAL] if fildes is negative or greater than or equal to {OPEN_MAX}.

The posix_spawn_file_actions_addopen() function may fail if:

[EBADF]
fildes is not a valid open file descriptor. Implementations may also return [EINVAL] if fildes is negative or greater than or equal to {OPEN_MAX}.
[EINVAL]
The path argument is not valid or oflag contains incompatible flags.
[EMFILE]
Too many file descriptors are in use by the calling process.
[ENFILE]
The system-wide limit on the total number of open files has been reached.

The posix_spawn_file_actions_adddup2() function may fail if:

[EBADF]
fildes or newfildes is not a valid open file descriptor. Implementations may also return [EINVAL] if fildes or newfildes is negative or greater than or equal to {OPEN_MAX}.
[EMFILE]
Too many file descriptors are in use by the calling process.
[ENFILE]
The system-wide limit on the total number of open files has been reached.

The posix_spawn_file_actions_addchroot() function may fail if:

[EACCES]
Search permission is denied for any component of the path prefix. The requirement for search permission applies even if the process has write permission to the directory.
[ENAMETOOLONG]
A component of a file name exceeds {NAME_MAX} bytes, or an entire path exceeds {PATH_MAX} bytes.
[ENOENT]
A component of path does not exist, or the path is an empty string.
[ENOTDIR]
A component of path is not a directory.
[EPERM]
The operation requires root privileges.

The posix_spawn_file_actions_addchdir() function may fail if:

[EACCES]
Search permission is denied for any component of the path prefix. The requirement for search permission applies even if the process has write permission to the directory.
[ENAMETOOLONG]
A component of a file name exceeds {NAME_MAX} bytes, or an entire path exceeds {PATH_MAX} bytes.
[ENOENT]
A component of path does not exist, or the path is an empty string.
[ENOTDIR]
A component of path is not a directory.

The posix_spawn_file_actions_addfchdir() function may fail if:

[EBADF]
fildes is not a valid open file descriptor.
[ENOTDIR]
fildes did not refer to a directory.

The posix_spawn_file_actions_addclosefromfile() function may fail if:

[EBADF]
fildes is not a valid open file descriptor. Implementations may also return [EINVAL] if fildes is negative.

EXAMPLES

None.

APPLICATION USAGE

See the RATIONALE section.

RATIONALE

The file descriptor manipulation functions described in this section are intended to provide a flexible way for applications to control which file descriptors are open or closed in a child process created by posix_spawn(). This is particularly useful for security-conscious applications that wish to restrict the resources available to a child process.

The posix_spawn() function preserves the set of open file descriptors from the calling process to the child process, except for those marked close-on-exec. The application can use the file actions functions to modify this default behavior.

For example, an application might want to close all file descriptors except for standard input, output, and error before spawning a child process. This can be achieved by using posix_spawn_file_actions_addclosefromfile() with file descriptor 3 (since file descriptors 0, 1, and 2 are standard input, output, and error, respectively).

It is important to note that the file descriptor mapping in the child process is distinct from the parent process. For instance, if the parent process closes file descriptor 1, this does not affect file descriptor 1 in the child process unless an explicit action is added to close it.

The posix_spawn_file_actions_addclose() function is not required to check whether the file descriptor is less than {OPEN_MAX} because on some implementations {OPEN_MAX} reflects the RLIMIT_NOFILE soft limit and therefore calling setrlimit() to reduce this limit can result in an {OPEN_MAX} value less than or equal to an already open file descriptor. Applications need to be able to close such file descriptors on spawn. On implementations where {OPEN_MAX} does not change, it is recommended that posix_spawn_file_actions_addclose() should return [EBADF] if fildes is greater than or equal to {OPEN_MAX}.

The original design for posix_spawn() included a complex file descriptor mapping array. However, this was deemed too complex for library implementations and potentially problematic for arbitrary reshuffling of file descriptors. The file actions approach, inspired by the Ada Language Bindings, provides a more flexible and manageable solution.

The `_np` variants are non-portable extensions that may offer additional functionality or different error handling, but should be avoided in portable code.

The posix_spawn_file_actions_addopen() function requires a struct std_cdev_stat *mode argument. This structure is typically used to specify file permissions and ownership when creating a new file. However, in the context of posix_spawn(), it is primarily used to pass information about the desired file type and attributes to the child process. The exact contents and interpretation of this structure may vary between implementations.

It's crucial for applications to correctly initialize and destroy the posix_spawn_file_actions_t object using posix_spawn_file_actions_init() and posix_spawn_file_actions_destroy() respectively, to avoid resource leaks or undefined behavior.

The distinction between the real and effective user IDs is important when considering file access. A process running with an effective user ID different from its real user ID may have different file access permissions. When using posix_spawn(), the effective user ID of the parent process determines the access rights for operations that depend on user identity, such as file opening. This means that the parent process, even if it's not the real owner, may successfully open a file that the real user should not have access to, or fail to open a file that the real user should have access to.

File Descriptor Mapping

The standard developers had originally proposed using an array which specified the mapping of child file descriptors back to those of the parent. It was pointed out by the ballot group that it is not possible to reshuffle file descriptors arbitrarily in a library implementation of posix_spawn() or posix_spawnp() without provision for one or more spare file descriptor entries (which simply may not be available). Such an array requires that an implementation develop a complex strategy to achieve the desired mapping without inadvertently closing the wrong file descriptor at the wrong time.

It was noted by a member of the Ada Language Bindings working group that the approved Ada Language Start_Process family of POSIX process primitives use a caller-specified set of file actions to alter the normal fork()/exec semantics for inheritance of file descriptors in a very flexible way, yet no such problems exist because the burden of determining how to achieve the final file descriptor mapping is completely on the application. Furthermore, although the file actions interface appears frightening at first glance, it is actually quite simple to implement in either a library or the kernel.

The posix_spawn_file_actions_addclose() function is not required to check whether the file descriptor is less than {OPEN_MAX} because on some implementations {OPEN_MAX} reflects the RLIMIT_NOFILE soft limit and therefore calling setrlimit() to reduce this limit can result in an {OPEN_MAX} value less than or equal to an already open file descriptor. Applications need to be able to close such file descriptors on spawn. On implementations where {OPEN_MAX} does not change, it is recommended that posix_spawn_file_actions_addclose() should return [EBADF] if fildes is greater than or equal to {OPEN_MAX}.
