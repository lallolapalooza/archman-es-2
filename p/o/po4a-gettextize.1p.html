Paquete: po4a

Licencias: GPL

PO4A-GETTEXTIZE.1P(1) Documentación de Perl contribuida por el usuario PO4A-GETTEXTIZE.1P(1)

NOMBRE

po4a-gettextize - convertir un archivo original (y su traducción) a un archivo PO

SINOPSIS

po4a-gettextize -f fmt -m archivo_maestro.doc -l XX.doc -p XX.po

(XX.po es la salida, todos los demás son entradas)

DESCRIPCIÓN

po4a (PO para cualquier cosa) facilita el mantenimiento de la traducción de documentación utilizando las herramientas clásicas de gettext. La característica principal de po4a es que desacopla la traducción del contenido de su estructura de documento. Consulte la página po4a(7) para una introducción suave a este proyecto.

El script po4a-gettextize le ayuda a convertir sus traducciones existentes previamente en un flujo de trabajo basado en po4a. Esto solo debe hacerse una vez para rescatar una traducción existente al convertir a po4a, no de forma regular después de la conversión de su proyecto. Este tedioso proceso se explica en detalle en la sección 'Conversión de una traducción manual a po4a' a continuación.

Debe proporcionar tanto un archivo maestro (por ejemplo, el original en inglés) como un archivo traducido existente (por ejemplo, un intento de traducción anterior sin po4a). Si proporciona más de un archivo maestro o de traducción, se utilizarán secuencialmente, pero puede ser más fácil convertir cada página o capítulo por separado y luego usar msgmerge para fusionar todos los archivos PO producidos. Como usted prefiera.

Si el documento maestro tiene caracteres no ASCII, el nuevo archivo PO generado estará en UTF-8. Si el documento maestro está completamente en ASCII, el PO generado usará la codificación del documento de entrada traducido.

OPCIONES

-f, --format
Formato de la documentación que desea manejar. Utilice la opción --help-format para ver la lista de formatos disponibles.
-m, --master
Archivo que contiene el documento maestro a traducir. Puede usar esta opción múltiples veces si desea convertir varios documentos.
-M, --master-charset
Juego de caracteres del archivo que contiene el documento a traducir.
-l, --localized
Archivo que contiene el documento localizado (traducido). Si proporcionó múltiples archivos maestros, puede desear proporcionar múltiples archivos localizados usando esta opción más de una vez.
-L, --localized-charset
Juego de caracteres del archivo que contiene el documento localizado.
-p, --po
Archivo donde se debe escribir el catálogo de mensajes. Si no se proporciona, el catálogo de mensajes se escribirá en la salida estándar.
-o, --option
Opción(es) adicional(es) para pasar al plugin de formato. Consulte la documentación de cada plugin para obtener más información sobre las opciones válidas y sus significados. Por ejemplo, podría pasar '-o tablecells' al analizador AsciiDoc, mientras que el analizador de texto aceptaría '-o tabs=split'.
-h, --help
Muestra un breve mensaje de ayuda.
--help-format
Lista los formatos de documentación entendidos por po4a.
-k --keep-temps
Conserva los archivos temporales maestros y de POT localizados creados antes de fusionarlos. Esto puede ser útil para comprender por qué estos archivos se desincronizan, lo que lleva a problemas de conversión. (gettextization)
-V, --version
Muestra la versión del script y sale.
-v, --verbose
Aumenta la verbosidad del programa.
-d, --debug
Muestra información de depuración.
--msgid-bugs-address correo@direccion
Establece la dirección de reporte para los errores de msgid. Por defecto, los archivos POT creados no tienen campos Report-Msgid-Bugs-To.
--copyright-holder cadena
Establece el titular de los derechos de autor en la cabecera del POT. El valor predeterminado es "Free Software Foundation, Inc."
--package-name cadena
Establece el nombre del paquete para la cabecera del POT. El valor predeterminado es "PACKAGE".
--package-version cadena
Establece la versión del paquete para la cabecera del POT. El valor predeterminado es "VERSION".

Conversión de una traducción manual a po4a

po4a-gettextize sincroniza los archivos maestros y localizados para extraer su contenido en un archivo PO. El contenido del archivo maestro proporciona el msgid mientras que el contenido del archivo localizado proporciona el msgstr. Este proceso es algo frágil: se supone que la N-ésima cadena del archivo traducido es la traducción de la N-ésima cadena en el original.

La conversión funciona mejor si se las arregla para recuperar la versión exacta del documento original que se utilizó para la traducción. Aun así, puede que necesite manipular tanto los archivos maestros como los localizados para alinear su estructura si fue modificada por el traductor original, por lo que se recomienda trabajar con copias de los archivos.

Internamente, cada analizador de po4a informa el tipo sintáctico de cada cadena extraída. Así es como se detectan las desincronizaciones durante la conversión. En el ejemplo que se muestra a continuación, es muy poco probable que la cuarta cadena en la traducción (de tipo 'capítulo') sea la traducción de la cuarta cadena en el original (de tipo 'párrafo'). Es más probable que se haya agregado un nuevo párrafo al original, o que se hayan fusionado dos párrafos originales en la traducción.

  Original         Traducción
capítulo           capítulo
  párrafo            párrafo
  párrafo            párrafo
  párrafo          capítulo
capítulo           párrafo
  párrafo            párrafo

po4a-gettextize diagnosticará detalladamente cualquier desincronización estructural. Cuando esto ocurra, debe editar manualmente los archivos para agregar párrafos falsos o eliminar contenido aquí y allá hasta que la estructura de ambos archivos coincida realmente. A continuación, se dan algunos trucos para rescatar la mayor parte de la traducción existente mientras se hace.

Si tiene la suerte de tener una coincidencia perfecta en las estructuras de los archivos tal como están, crear un archivo PO correcto es cuestión de segundos. De lo contrario, pronto entenderá por qué este proceso tiene un nombre tan feo :) Aun así, la conversión suele ser más rápida que traducir todo de nuevo. Convertí la traducción al francés de toda la documentación de Perl en un día a pesar de los muchos problemas de sincronización. Dada la cantidad de texto (2 MB de texto original), reiniciar la traducción sin rescatar primero las traducciones antiguas habría requerido varios meses de trabajo. Además, este trabajo pesado es el precio a pagar para obtener la comodidad de po4a. Una vez convertida, la sincronización entre los documentos maestros y las traducciones siempre será completamente automática.

DESCRIPTION

The po4a-gettextize script is used to convert an existing document and its translation(s) into the PO format used by gettext. This is the first step toward integrating an existing translation workflow into po4a.

It processes two files: the master document and the corresponding translated document. It parses both, tries to identify corresponding translatable strings, and dumps them into a PO file. The PO file is created with the same base name as the master document, but with a .po extension. The current directory is scanned for files matching the pattern *.po to create the PO file. The files are processed in alphabetical order.

The script compares the master document and the translation line by line. It checks for structural integrity first. If the number of paragraphs or other structural elements differ, it considers the documents desynchronized and stops processing.

If the structures match, it extracts translatable strings. These strings are inserted into the PO file as msgid entries. The corresponding translated strings are inserted as msgstr entries. If a translation is missing for a given msgid, the msgstr will be empty.

All entries are marked as fuzzy in the generated PO file to indicate that they require manual verification. This is crucial because the gettextization process might not perfectly align all strings, especially if the original document or translation has undergone significant changes or contains complex formatting.

After the initial run, it is essential to manually review the generated PO file to ensure that the msgid and msgstr pairs are correct. Even if the script completes successfully, subtle errors or misalignments might exist. The script will perform a basic check for undetected disparities and silent errors, as explained below.

Hints and tricks for the gettextization process

The gettextization stops as soon as a desynchronization is detected. When this happens, you need to edit the files as much as needed to re-align the files' structures. po4a-gettextize is rather verbose when things go wrong. It reports the strings that don't match, their positions in the text, and the type of each of them. Moreover, the PO file generated so far is dumped as gettextization.failed.po for further inspection.

Here are some tricks to help you in this tedious process and ensure that you salvage the most of the previous translation:

  • Remove all extra content of the translations, such as the section giving credits to the translators. They should be added separately to po4a as addenda (see po4a(7)).
  • When editing the files to align their structures, prefer editing the translation if possible. Indeed, if the changes to the original are too intrusive, the old and new versions will not be matched during the first po4a run after gettextization (see below). Any unmatched translation will be dumped anyway. That being said, you still want to edit the original document if it's too hard to get the gettextization to proceed otherwise, even if it means that one paragraph of the translation is dumped. The important thing is to get a first PO file to start with.
  • Do not hesitate to kill any original content that would not exist in the translated version. This content will be automatically reintroduced afterward, when synchronizing the PO file with the document.
  • You should probably inform the original author of any structural change in the translation that seems justified. Issues in the original document should reported to the author. Fixing them in your translation only fixes them for a part of the community. Plus, it is impossible to do so when using po4a ;) But you probably want to wait until the end of the conversion to po4a before changing the original files.
  • Sometimes, the paragraph content does match, but not their types. Fixing it is rather format-dependent. In POD and man, it often comes from the fact that one of them contains a line beginning with a white space while the other does not. In those formats, such paragraph cannot be wrapped and thus become a different type. Just remove the space and you are fine. It may also be a typo in the tag name in XML.

    Likewise, two paragraphs may get merged together in POD when the separating line contains some spaces, or when there is no empty line between the =item line and the content of the item.

  • Sometimes, the desynchronization message seems odd because the translation is attached to the wrong original paragraph. It is the sign of an undetected issue earlier in the process. Search for the actual desynchronization point by inspecting the file gettextization.failed.po that was produced, and fix the problem where it really is.
  • Other issues may come from duplicated strings in either the original or translation. Duplicated strings are merged in PO files, with two references. This constitutes a difficulty for the gettextization algorithm, that is a simple one to one pairing between the msgids of both the master and the localized files. It is however believed that recent versions of po4a deal properly with duplicated strings, so you should report any remaining issue that you may encounter.

Reviewing files produced by po4a-gettextize

Any file produced by po4a-gettextize should be manually reviewed, even when the script terminates successfully. You should skim over the PO file, ensuring that the msgid and msgstr actually match. It is not necessary to ensure that the translation is perfectly correct yet, as all entries are marked as fuzzy translations anyway. You only need to check for obvious matching issues because badly matched translations will be dumped in subsequent steps while you want to salvage them.

Fortunately, this step does not require to master the target languages as you only want to recognize similar elements in each msgid and its corresponding msgstr. As a speaker of French, English, and some German myself, I can do this for all European languages at least, even if I cannot say one word of most of these languages. I sometimes manage to detect matching issues in non-Latin languages by looking at string length, phrase structures (does the amount of interrogation marks match?) and other clues, but I prefer when someone else can review those languages.

If you detect a mismatch, edit the original and translation files as if po4a-gettextize reported an error, and try again. Once you have a decent PO file for your previous translation, backup it until you get po4a working correctly.

Running po4a for the first time

The easiest way to setup po4a is to write a po4a.conf configuration file, and use the integrated po4a program (po4a-updatepo and po4a-translate are deprecated). Please check the "CONFIGURATION FILE" Section in po4a(1) documentation for more details.

When po4a runs for the first time, the current version of the master documents will be used to update the PO files containing the old translations that you salvaged through gettextization. This can take quite a long time, because many of the msgids of from the gettextization do not exactly match the elements of the POT file built from the recent master files. This forces gettext to search for the closest one using a costly string proximity algorithm. For example, the first run over the Perl documentation's French translation (5.5 MB PO file) took about 48 hours (yes, two days) while the subsequent ones only take seconds.

Moving your translations to production

After this first run, the PO files are ready to be reviewed by translators. All entries were marked as fuzzy in the PO file by po4a-gettextization, forcing their careful review before use. Translators should take each entry to verify that the salvaged translation actually match the current original text, update the translation on need, and remove the fuzzy markers.

Once enough fuzzy markers are removed, po4a will start generating the translation files on disk, and you're ready to move your translation workflow to production. Some projects find it useful to rely on weblate to coordinate between translators and maintainers, but that's beyond po4a' scope.
