NOMBRE

podman-kube-play - Crea contenedores, pods y volúmenes basados en YAML de Kubernetes

SINOPSIS

podman kube play [opciones] archivo.yml|-|https://sitio.web/archivo.yml

DESCRIPCIÓN

podman kube play lee un archivo estructurado de YAML de Kubernetes. Recrea los contenedores, pods o volúmenes descritos en el YAML. Los contenedores dentro de un pod se inician, y se muestra el ID del nuevo Pod o el nombre del nuevo Volumen. Si el archivo YAML se especifica como "-", entonces podman kube play lee el archivo YAML desde stdin. La entrada también puede ser una URL que apunte a un archivo YAML, como https://podman.io/demo.yml. podman kube play lee el YAML desde la URL y crea pods y contenedores a partir de él.

Utilizando la opción de línea de comandos --down, también es capaz de desmantelar los pods creados por una ejecución anterior de podman kube play.

Utilizando la opción de línea de comandos --replace, desmantela los pods (si los hay) creados por una ejecución anterior de podman kube play y recrea los pods con el archivo YAML de Kubernetes.

Idealmente, el archivo de entrada es creado por el comando Podman (ver podman-kube-generate(1)). Esto garantiza una importación fluida y resultados esperados.

Actualmente, los tipos de Kubernetes soportados son:

  • Pod
  • Deployment
  • PersistentVolumeClaim
  • ConfigMap
  • Secret
  • DaemonSet
  • Job

Pods o Deployments de Kubernetes

Solo cinco tipos de volúmenes son soportados por kube play: los tipos de volumen hostPath, emptyDir, configMap, persistentVolumeClaim e image.

  • Al usar el tipo de volumen hostPath, solo se soportan los subtipos default (empty), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice y BlockDevice. Podman interpreta el valor de la ruta path de hostPath como una ruta de archivo cuando contiene al menos una barra inclinada, de lo contrario Podman trata el valor como el nombre de un volumen nombrado.
  • Al usar un persistentVolumeClaim, el valor de claimName es el nombre para el volumen nombrado de Podman.
  • Al usar un volumen emptyDir, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que se elimina el pod.
  • Al usar un volumen configMap, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que se elimina el pod.
  • Al usar un volumen image, Podman crea un volumen de imagen de solo lectura con una subruta vacía (se monta la imagen completa). La imagen debe existir localmente. Solo se soporta en modo rootful.

Nota: La política de reinicio predeterminada para los contenedores es always. Puede cambiar el valor predeterminado configurando el campo restartPolicy en la especificación.

Nota: Al ejecutar un YAML de kube con contenedores init, el contenedor init se crea con el valor de tipo init once. Para cambiar el tipo predeterminado, use la anotación io.podman.annotations.init.container.type para establecer el tipo a always.

Nota: Los tipos de volumen hostPath creados por kube play reciben una etiqueta compartida SELinux (z), los montajes bind no se re-etiquetan (use chcon -t container_file_t -R <directorio>).

Nota: Para establecer userns de un pod, use la anotación io.podman.annotations.userns en la definición del pod/deployment. Por ejemplo, la anotación io.podman.annotations.userns=keep-id le indica a Podman que cree un espacio de nombres de usuario donde la UID:GID del usuario rootless actual se mapean a los mismos valores en el contenedor. Esto se puede anular con la bandera --userns.

Nota: Use la anotación io.podman.annotations.volumes-from para montar volúmenes de un contenedor en otro. Puede montar volúmenes de múltiples contenedores de origen en un contenedor de destino. Los contenedores de origen que pertenecen al mismo pod deben definirse antes que el contenedor de origen en el archivo YAML de kube. El formato de la anotación es io.podman.annotations.volumes-from/contenedorDestino: "contenedorOrigen1:opcionesMontaje1;contenedorOrigen2:opcionesMontaje2".

Nota: Si se usa la etiqueta :latest, Podman intenta descargar la imagen de un registro. Si la imagen se compiló localmente con Podman o Buildah, tiene localhost como dominio, en ese caso, Podman usa la imagen del almacén local incluso si tiene la etiqueta :latest.

Nota: El comando podman play kube es un alias de podman kube play, y realiza la misma función.

Nota: El comando podman kube down se puede usar para detener y eliminar pods o contenedores basados en el mismo YAML de Kubernetes utilizado por podman kube play para crearlos.

Nota: Para personalizar el nombre del contenedor infra creado durante podman kube play, use la anotación io.podman.annotations.infra.name en la definición del pod. Esta anotación se establece automáticamente al generar un archivo YAML de kube a partir de un pod que se creó con la bandera --infra-name establecida.

Nota: Use la anotación io.podman.annotations.pids-limit/$ctrname para configurar el límite de pids del pod.

Nota: Use la anotación io.podman.annotations.cpuset/$ctrname para restringir la ejecución de un contenedor a un conjunto específico de núcleos de CPU. Esto es equivalente a la opción --cpuset-cpus=número en podman-run(1).

Nota: Use la anotación io.podman.annotations.memory-nodes/$ctrname para restringir las asignaciones de memoria de un contenedor a un conjunto específico de nodos de memoria en sistemas NUMA. Esto es equivalente a la opción --cpuset-mems=nodos en podman-run(1).

PersistentVolumeClaims de Kubernetes

Un PersistentVolumeClaim de Kubernetes representa un volumen nombrado de Podman. Solo el nombre del PersistentVolumeClaim es requerido por Podman para crear un volumen. Las anotaciones de Kubernetes pueden usarse para aprovechar las opciones disponibles para los volúmenes de Podman.

  • volume.podman.io/driver
  • volume.podman.io/device
  • volume.podman.io/type
  • volume.podman.io/uid
  • volume.podman.io/gid
  • volume.podman.io/mount-options
  • volume.podman.io/import-source
  • volume.podman.io/image

Use volume.podman.io/import-source para importar el contenido del archivo tar (.tar, .tar.gz, .tgz, .bzip, .tar.xz, .txz, .tar.zst) especificado en el valor de la anotación al volumen de Podman creado

Kube play es capaz de construir imágenes sobre la marcha dado el diseño de directorio correcto y los Containerfiles. Esta opción aún no está disponible para clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2). Considere el siguiente fragmento de un archivo YAML:

apiVersion: v1
kind: Pod
metadata:
...
spec:
  containers:
  - name: container
    image: foobar
...

Si hay un directorio llamado foobar en el directorio de trabajo actual con un archivo llamado Containerfile o Dockerfile, Podman kube play compila esa imagen y la llama foobar. Un ejemplo de estructura de directorio para este ejemplo se ve así:

|- misArchivosKube
    |- miArchivoPlay.yaml
    |- foobar
         |- Containerfile

La compilación considera foobar como el directorio de contexto para la compilación. Si hay una imagen en el almacenamiento local llamada foobar, la imagen no se compila a menos que se use la bandera --build. Use --build=false para deshabilitar completamente las compilaciones.

Kube play soporta selectores de dispositivos CDI (Container Device Interface) para compartir dispositivos del host (por ejemplo, GPUs) con contenedores. El formato de configuración sigue la gestión de recursos extendidos de Kubernetes:

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: container
    resources:
      limits:
        nvidia.com/gpu=all: 1

Para habilitar el intercambio de dispositivos del host, de forma análoga al uso de la bandera --device, Podman kube soporta un selector CDI personalizado: podman.io/device=<ruta dispositivo host>.

ConfigMap de Kubernetes

Los ConfigMap de Kubernetes pueden ser referenciados como fuente de variables de entorno o volúmenes en Pods o Deployments. Los ConfigMaps no son un objeto independiente en Podman; en su lugar, cuando un contenedor usa un ConfigMap, Podman crea variables de entorno o volúmenes según sea necesario.

Por ejemplo, el siguiente documento YAML define un ConfigMap y luego lo usa en un Pod:

apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: fooba

CONFIGURACIÓN

Las siguientes opciones de configuración se pueden definir en el archivo $HOME/.config/containers/containers.conf o en el archivo de configuración del sistema /etc/containers/containers.conf.

CONFIGURACIÓN YAML

Para usar los servicios de Kubernetes (ConfigMaps y Secrets) como fuente para las variables de entorno de los contenedores:

Kubernetes ConfigMap

Kubernetes ConfigMap representa un ConfigMap con nombre de Podman. El ConfigMap se guarda como un todo y puede ser referenciado como fuente de variables de entorno en Pods o Deployments.

Por ejemplo, el siguiente documento YAML define un ConfigMap y luego lo usa en un Pod:

    kind: ConfigMap
    apiVersion: v1
    metadata:
      name: foo
    data:
      foo: bar
    ---
    apiVersion: v1
    kind: Pod
    metadata:
      name: foobar
    spec:
      containers:
      - name: container-1
        image: foobar
        envFrom:
        - configMapRef:
            name: foo
            optional: false

Y como resultado, la variable de entorno FOO se establece en bar para el contenedor container-1.

Kubernetes Secret

Kubernetes Secret representa un secreto con nombre de Podman. El Kubernetes Secret se guarda como un todo y puede ser referenciado como fuente de variables de entorno o volúmenes en Pods o Deployments.

Por ejemplo, el siguiente documento YAML define un Secret y luego lo usa en un Pod:

    kind: Secret
    apiVersion: v1
    metadata:
      name: foo
    data:
      foo: YmFy # base64 para bar
    ---
    apiVersion: v1
    kind: Pod
    metadata:
      name: foobar
    spec:
      containers:
      - name: container-1
        image: foobar
        env:
        - name: FOO
          valueFrom:
            secretKeyRef:
              name: foo
              key: foo

Y como resultado, la variable de entorno FOO se establece en bar para el contenedor container-1.

Montaje Automático de Volúmenes (obsoleto)

Nota: La anotación de montaje automático está obsoleta. Kubernetes tiene soporte nativo para volúmenes de imágenes y se debe usar en lugar de esta anotación específica de Podman.

Una imagen puede ser montada automáticamente en un contenedor si se proporciona la anotación io.podman.annotations.kube.image.automount/$ctrname. Se aplican las siguientes reglas:

  • La imagen debe existir localmente.
  • La imagen debe tener al menos 1 directiva de volumen.
  • La ruta dada por la directiva de volumen se montará desde la imagen en el contenedor. Por ejemplo, una imagen con un volumen en /test/test_dir tendrá /test/test_dir en la imagen montado en /test/test_dir en el contenedor.
  • Se pueden especificar múltiples imágenes. Si varias imágenes tienen un volumen en una ruta específica, la última imagen especificada prevalece.
  • Las imágenes siempre se montan en modo de solo lectura.
  • Las imágenes a montar se definen en la anotación "io.podman.annotations.kube.image.automount/$ctrname" como una lista separada por punto y coma. Se montan en un solo contenedor en el pod, no en todo el pod. La anotación se puede especificar para contenedores adicionales si se requieren montajes adicionales.

OPCIONES

--annotation=clave=valor

Añadir una anotación al contenedor o pod. Esta opción se puede establecer varias veces.

Nota: Para podman kube play, el flag --annotation añade anotaciones específicas de Podman a los contenedores y pods creados por Podman, no al propio YAML de Kubernetes. Estas anotaciones se pueden usar para configurar características específicas de Podman como espacios de nombres de usuario (io.podman.annotations.userns), volúmenes-desde (io.podman.annotations.volumes-from) y otros comportamientos del contenedor.

--authfile=ruta

Ruta del archivo de autenticación. Por defecto es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo es creado por podman login. Si el estado de autorización no se encuentra allí, se consulta $HOME/.docker/config.json, que se establece usando docker login.

Nota: También existe la opción de anular la ruta por defecto del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

--build

Construir imágenes incluso si se encuentran en el almacenamiento local. Usar --build=false para deshabilitar completamente las construcciones. (Esta opción no está disponible con el cliente remoto de Podman)

Nota: También puedes anular el tipo de aislamiento por defecto estableciendo la variable de entorno BUILDAH_ISOLATION. export BUILDAH_ISOLATION=oci. Ver podman-build.1.md para más información.

--cert-dir=ruta

Usar certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. (Por defecto: /etc/containers/certs.d) Para más detalles, ver containers-certs.d(5). (Esta opción no está disponible con el cliente remoto de Podman, incluyendo máquinas Mac y Windows (excluyendo WSL2))

--configmap=ruta

Usar YAML de ConfigMap de Kubernetes en la ruta para proporcionar una fuente de valores de variables de entorno dentro de los contenedores del pod. (Esta opción no está disponible con el cliente remoto de Podman)

Nota: La opción --configmap puede usarse varias veces o se puede usar una lista de rutas separadas por comas para pasar múltiples YAMLs de ConfigMap de Kubernetes. El archivo YAML puede estar en formato YAML multidocto. Pero, solo debe contener ConfigMaps.

--context-dir=ruta

Usar ruta como el directorio de contexto de construcción para cada imagen. Requiere que la opción --build sea true. (Esta opción no está disponible con el cliente remoto de Podman)

--creds=[usuario[:contraseña]]

El [usuario[:contraseña]] a usar para autenticarse con el registro, si es requerido. Si uno o ambos valores no se proporcionan, aparece un aviso en la línea de comandos y se puede ingresar el valor. La contraseña se ingresa sin eco.

Tenga en cuenta que las credenciales especificadas solo se usan para autenticarse contra los registros de destino. No se usan para espejos ni cuando el registro se reescribe (ver containers-registries.conf(5)); para autenticarse contra estos, considere usar un archivo containers-auth.json(5).

--force

Desmontar los volúmenes enlazados a los PersistentVolumeClaims como parte de --down

--help, -h

Imprimir declaración de uso

--ip=dirección IP

Asignar una dirección IP estática al pod. Esta opción se puede especificar varias veces cuando kube play crea más de un pod. Nota: Al unir múltiples redes, use la sintaxis --network nombre:ip=<ip>.

--log-driver=driver

Establecer el driver de registro para todos los contenedores creados.

--log-opt=nombre=valor

Opciones específicas del driver de registro.

Establecer configuración de registro personalizada. Los siguientes *nombres* son compatibles:

path: especificar una ruta al archivo de registro
(ej. --log-opt path=/var/log/container/mycontainer.json);

max-size: especificar un tamaño máximo del archivo de registro
(ej. --log-opt max-size=10mb);

tag: especificar una etiqueta de registro personalizada para el contenedor
(ej. --log-opt tag="{{.ImageName}}". Soporta las mismas claves que podman inspect --format. Esta opción es actualmente compatible solo con el driver de registro journald.

--mac-address=dirección MAC

Asignar una dirección MAC estática al pod. Esta opción se puede especificar varias veces cuando kube play crea más de un pod. Nota: Al unir múltiples redes, use la sintaxis --network nombre:mac=<mac>.

--network=modo, --net

Establecer el modo de red para el pod.

Los valores válidos de modo son:

•
bridge[:OPCIONES,...]: Crear una pila de red en el bridge por defecto. Este es el valor por defecto para contenedores rootful. Es posible especificar las siguientes opciones adicionales:
  • alias=nombre: Añadir alias con alcance de red para el contenedor.
  • ip=IPv4: Especificar una dirección IPv4 estática para este contenedor.
  • ip6=IPv6: Especificar una dirección IPv6 estática para este contenedor.
  • mac=MAC: Especificar una dirección MAC estática para este contenedor.
  • interface_name=nombre: Especificar un nombre para la interfaz de red creada dentro del contenedor.
  • host_interface_name=nombre: Especificar un nombre para la interfaz de red creada fuera del contenedor.
Cualquier otra opción se pasará a netavark sin validación. Esto puede ser útil para pasar argumentos a plugins de netavark.

Por ejemplo, para establecer una dirección ipv4 estática y una dirección mac estática, use --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nombre o ID de red>[:OPCIONES,...]: Conectar a una red definida por el usuario; este es el nombre o ID de red de una red creada por podman network create. Es posible especificar las mismas opciones descritas en el modo bridge arriba. Use la opción --network varias veces para especificar redes adicionales.
    Para compatibilidad hacia atrás, también es posible especificar redes separadas por comas en el primer argumento de --network, sin embargo, esto le impide usar las opciones descritas en la sección bridge arriba.
  • none: Crear un espacio de nombres de red para el contenedor pero no configurar interfaces de red para él, por lo tanto, el contenedor no tiene conectividad de red.
  • container:id: Reutilizar la pila de red de otro contenedor.
  • host: Usar el espacio de nombres de red del host para el contenedor en lugar de crear un espacio de nombres aislado. Advertencia: Esto da al contenedor acceso completo a sockets Unix abstractos y a sockets TCP/UDP vinculados a localhost. Dado que estos mecanismos se usan a menudo para evitar el acceso a servicios sensibles del sistema, aislando el acceso a entidades externas, el uso de esta opción puede considerarse una vulnerabilidad de seguridad.
  • ns:ruta: Ruta a un espacio de nombres de red para unirse.
  • private: Crear un nuevo espacio de nombres para el contenedor. Esto usa el modo bridge para contenedores rootful y slirp4netns para los rootless.
  • slirp4netns[:OPCIONES,...]: usar slirp4netns(1) para crear una pila de red de usuario. Es posible especificar las siguientes opciones adicionales, que también se pueden establecer con network_cmd_options en containers.conf:
  • allow_host_loopback=true|false: Permitir que slirp4netns acceda a la IP de loopback del host (por defecto es 10.0.2.2 o la segunda IP de la subred CIDR de slirp4netns cuando se cambia, ver la opción cidr abajo). El valor por defecto es false.
  • mtu=MTU: Especificar la MTU a usar para esta red. (Por defecto es 65520).
  • cidr=CIDR: Especificar el rango IP a usar para t
su red. (Predeterminado es 10.0.2.0/24).
  • enable_ipv6=true|false: Habilita IPv6. El valor predeterminado es true. (Requerido para outbound_addr6).
  • outbound_addr=INTERFACE: Especifica la interfaz de salida a la que se vincula slirp (solo tráfico ipv4).
  • outbound_addr=IPv4: Especifica la dirección ipv4 de salida a la que se vincula slirp.
  • outbound_addr6=INTERFACE: Especifica la interfaz de salida a la que se vincula slirp (solo tráfico ipv6).
  • outbound_addr6=IPv6: Especifica la dirección ipv6 de salida a la que se vincula slirp.
  • port_handler=rootlesskit: Usa rootlesskit para reenvío de puertos. Predeterminado.
    Nota: Rootlesskit cambia la dirección IP de origen de los paquetes entrantes a una dirección IP en el espacio de nombres de red del contenedor, generalmente 10.0.2.100. Si la aplicación requiere la dirección IP de origen real, por ejemplo, para registros de servidores web, usa el manejador de puertos slirp4netns. El manejador de puertos rootlesskit también se utiliza para contenedores sin privilegios cuando se conectan a redes definidas por el usuario.
  • port_handler=slirp4netns: Usa el reenvío de puertos slirp4netns, es más lento que rootlesskit pero conserva la dirección IP de origen correcta. Este manejador de puertos no se puede usar para redes definidas por el usuario.
    • •
    pasta[:OPCIONES,...]: usa pasta(1) para crear una pila de red en modo de usuario.
    Este es el valor predeterminado para contenedores sin privilegios y solo se admite en modo sin privilegios.
    Por defecto, se copian las direcciones y rutas IPv4 e IPv6, así como el nombre de la interfaz del pod, del host. El reenvío de puertos conserva la dirección IP de origen original. Las opciones descritas en pasta(1) se pueden especificar como argumentos separados por comas.
    En términos de opciones de pasta(1), se utiliza --config-net por defecto, para configurar la red cuando se inicia el contenedor, y --no-map-gw también se asume por defecto, para evitar el acceso directo desde el contenedor al host utilizando la dirección de la puerta de enlace. Este último puede ser anulado pasando --map-gw en las opciones específicas de pasta (a pesar de no ser una opción real de pasta(1)).
    Para una mejor integración con el manejo de DNS, se pasa --dns-forward 169.254.1.1, y esta dirección se agrega a resolv.conf(5) como el primer resolvedor. Es posible pasar --dns-forward explícitamente en caso de que se deba usar una dirección IP diferente. Para que la entrada host.containers.internal en /etc/hosts funcione y permita conexiones al host, se pasa --map-guest-addr 169.254.1.2. Nuevamente, se puede establecer explícitamente para elegir una dirección IP diferente.
    Además, se pasan -t none y -u none si, respectivamente, no se configura ningún reenvío de puertos TCP o UDP del host al contenedor (a través de --publish de Podman o pasando las opciones -t/-u de pasta directamente), para deshabilitar el reenvío automático de puertos basado en puertos vinculados. De manera similar, se usan -T none y -U none para deshabilitar la misma funcionalidad del contenedor al host.
    Todas las opciones también se pueden configurar en containers.conf(5); consulta la clave pasta_options en la sección de red de ese archivo.
    Algunos ejemplos:
    • pasta:--map-gw: Permite al contenedor alcanzar directamente el host usando la dirección de la puerta de enlace.
    • pasta:--mtu,1500: Especifica una MTU de 1500 bytes para la interfaz tap en el contenedor.
    • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con puerta de enlace 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece la MTU a 1500 bytes, deshabilita NDP, DHCPv6 y DHCP soporte.
    • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: igual que lo anterior, pero deja la MTU en 65520 bytes
    • pasta:-t,auto,-u,auto,-T,auto,-U,auto: habilita el reenvío automático de puertos basado en puertos vinculados observados desde ambos lados del host y del contenedor
    • pasta:-T,5201: habilita el reenvío del puerto TCP 5201 del contenedor al host, utilizando la interfaz de loopback en lugar de la interfaz tap para un mejor rendimiento

    Cuando no se especifica ninguna opción de red y el modo de red de host no está configurado en el archivo YAML, se crea una nueva pila de red y los pods se adjuntan a ella, lo que permite la comunicación pod a pod.

    --no-hostname

    No crea el archivo /etc/hostname en los contenedores.

    Por defecto, Podman gestiona el archivo /etc/hostname, añadiendo el propio nombre de host del contenedor. Cuando se establece la opción --no-hostname, se conservará el archivo /etc/hostname de la imagen sin modificaciones si existe.

    --no-hosts

    No modifica el archivo /etc/hosts en el pod.

    Podman asume el control del archivo /etc/hosts del pod por defecto y agrega entradas para el nombre del contenedor (ver opción --name) y el nombre de host (ver opción --hostname), los hosts internos host.containers.internal y host.docker.internal, así como cualquier nombre de host agregado usando la opción --add-host. Consulta la opción --add-host para obtener detalles. Al pasar --no-hosts se deshabilita esto, de modo que se conserva el archivo /etc/hosts de la imagen sin modificar. Lo mismo se puede lograr globalmente configurando no_hosts=true en containers.conf.

    Esta opción entra en conflicto con los hosts agregados en el YAML de Kubernetes.

    --no-pod-prefix

    No prefijar el nombre del contenedor con el nombre del pod.

    --publish=[[ip:][puerto_host:]puerto_contenedor[/protocolo]]

    Define o anula una definición de puerto en el archivo YAML.

    Las listas de puertos en el archivo YAML y la línea de comandos se fusionan. La coincidencia se realiza utilizando el campo containerPort. Si containerPort existe tanto en el archivo YAML como en la opción, esta última tiene prioridad.

    --publish-all

    Establecer esta opción en true expondrá todos los puertos al host, incluso si solo se especifican a través de containerPort en el YAML de K8. En términos de qué puerto se expondrá, --publish tiene mayor prioridad que hostPort, y mayor prioridad que containerPort.

    Si se establece en false (que es el valor predeterminado), solo los puertos definidos a través de hostPort o --publish se publican en el host.

    --quiet, -q

    Suprimir la información de salida al descargar imágenes

    --replace

    Cierra los pods creados por una ejecución anterior de kube play y recrea los pods. Esta opción se utiliza para mantener actualizados los pods existentes basándose en el YAML de Kubernetes.

    --seccomp-profile-root=ruta

    Ruta del directorio para perfiles seccomp (predeterminado: "/var/lib/kubelet/seccomp"). (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

    --start

    Inicia el pod después de crearlo, se establece en false para solo crearlo.

    --tls-verify

    Requiere HTTPS y verifica certificados al contactar registros (predeterminado: true). Si se establece explícitamente en true, se utiliza la verificación TLS. Si se establece en false, no se utiliza la verificación TLS. Si no se especifica, se utiliza la verificación TLS a menos que el registro de destino esté listado como un registro inseguro en containers-registries.conf(5)

    --userns=modo

    Establece el modo de espacio de nombres de usuario para el contenedor.

    Si no se establece --userns, el valor predeterminado se determina de la siguiente manera. - Si se establece --pod, se ignora --userns y se utiliza el espacio de nombres de usuario del pod. - Si la variable de entorno PODMAN_USERNS está establecida, se usa su valor. - Si se especifica userns en containers.conf, se utiliza este valor. - De lo contrario, se asume --userns=host.

    --userns="" (es decir, una cadena vacía) es un alias para --userns=host.

    Esta opción es incompatible con --gidmap, --uidmap, --subuidname y --subgidname.

    Mapeos de clave de usuario sin privilegios --userns:

    Clave Usuario Host Usuario Contenedor
    auto $UID nil (La UID del usuario host no se mapea al contenedor).
    host $UID 0 (Cuenta de usuario predeterminada mapeada al usuario root en el contenedor).
    keep-id $UID $UID (Mapea la cuenta de usuario a la misma UID dentro del contenedor).
    keep-id:uid=200,gid=210 $UID 200:210 (Mapea la cuenta de usuario a la UID especificada, valor GID dentro del contenedor).
    nomap $UID nil (La UID del usuario host no se mapea al contenedor).

    Los valores válidos de modo son:

    auto[:OPCIONES,...]: crea automáticamente un espacio de nombres de usuario único.

    • modo con privilegios: El indicador --userns=auto requiere que el nombre de usuario containers se especifique en los archivos /etc/subuid y /etc/subgid, con un rango no utilizado de IDs de usuario subordinados que Podman puede asignar a los contenedores. Ejemplo: containers:2147483647:2147483648.
    • modo sin privilegios: Se utilizarán los rangos de usuarios de los archivos /etc/subuid y /etc/subgid. Tenga en cuenta que al ejecutar un solo contenedor sin usar --userns=auto se utilizará todo el rango de UIDs y no se permitirá una subdivisión adicional. Ver subuid(5).

    Podman asigna rangos únicos de UIDs y GIDs de los IDs de usuario subordinados de containers. El tamaño de los rangos se basa en el número de UIDs requeridas en la imagen. El número de UIDs y GIDs puede ser anulado con la opción size.

    La opción --userns=keep-id utiliza todas las subuids y subgids del usuario. La opción --userns=nomap utiliza todas las subuids y subgids del usuario, excepto la ID del propio usuario. Usar --userns=auto al iniciar nuevos contenedores no funciona mientras existan contenedores que se iniciaron con --userns=nomap o --userns=keep-id sin limitar el tamaño del espacio de nombres de usuario.

    Las opciones válidas de auto y el formato de la opción de tamaño son:

    ciones:

    • gidmapping=CONTAINER_GID:HOST_GID:SIZE: para forzar la presencia de un mapeo GID en el espacio de nombres de usuario.
    • size=SIZE: para especificar un tamaño explícito para el espacio de nombres de usuario automático. por ejemplo, --userns=auto:size=8192. Si no se especifica size, auto estima un tamaño para el espacio de nombres de usuario.
    • uidmapping=CONTAINER_UID:HOST_UID:SIZE: para forzar la presencia de un mapeo UID en el espacio de nombres de usuario.

    El UID y GID del host en gidmapping y uidmapping pueden ir precedidos opcionalmente por el símbolo @. En este caso, podman buscará el ID intermedio correspondiente al ID del host y mapeará el ID intermedio encontrado al ID del contenedor. Para más detalles, consulte --uidmap.

    container:id: une el espacio de nombres de usuario del contenedor especificado.

    host o "" (cadena vacía): se ejecuta en el espacio de nombres de usuario del llamador. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el host que cualquier otro proceso iniciado por el usuario llamador.

    keep-id: crea un espacio de nombres de usuario donde el UID:GID del usuario actual se mapean a los mismos valores en el contenedor. Para los contenedores creados por root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

    Además, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen a menos que establezca explícitamente --user.

    Opciones válidas de keep-id:

    • uid=UID: anula el UID dentro del contenedor que se utiliza para mapear al usuario actual.
    • gid=GID: anula el GID dentro del contenedor que se utiliza para mapear al usuario actual.
    • size=SIZE: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No soportado cuando se ejecuta como root.

    nomap: crea un espacio de nombres de usuario donde el UID:GID del usuario sin root actual no se mapean en el contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

    ns:namespace: ejecuta el pod en el espacio de nombres de usuario existente dado.

    --wait, -w

    Ejecuta pods y contenedores en primer plano. El valor predeterminado es false.

    En cualquier momento, puede ejecutar podman pod ps en otra terminal para ver una lista de los pods y contenedores en ejecución.

    Cuando se adjunta en modo tty, puede matar los pods y contenedores presionando Ctrl-C o recibiendo cualquier otra señal de interrupción.

    Todos los pods, contenedores y volúmenes creados con podman kube play se eliminan al salir.

    podman-kube-play(1) — podman

    NAME

    podman-kube-play

    Play Kubernetes YAML files locally

    SYNOPSIS

    podman kube play [options] [YAML file]...

    podman kube play --help

    DESCRIPTION

    The podman kube play command runs Kubernetes YAML files locally. The supported Kubernetes YAMLs are Pod, Deployment, Service, DaemonSet, Job, StatefulSet, and ConfigMap. It converts these Kubernetes objects into Podman containers and other objects.

    This command is intended to provide a way to run Kubernetes YAMLs locally for development and testing purposes.

    The command supports the following Kubernetes objects: Pod, Deployment, Service, DaemonSet, Job, StatefulSet, and ConfigMap. It will ignore objects it does not support.

    OPTIONS

    Podman kube play supports the following options:

    --network

    Set the network mode for the containers. Supported values are bridge, host, none, slirp4netns. The default is bridge.

    --replace

    Replace existing Podman objects with the same name. By default, if an object with the same name already exists, podman kube play will fail.

    --start

    Start the containers after they are created. By default, containers are created but not started.

    --save

    Save the Podman objects to a YAML file. This can be used to inspect the generated Podman objects.

    -h, --help

    Print usage information.

    EXAMPLES

    Run a Kubernetes YAML file locally:

    podman kube play my_pod.yaml

    Run a Kubernetes YAML file locally and start the containers:

    podman kube play --start my_pod.yaml

    Run a Kubernetes YAML file locally and replace existing objects:

    podman kube play --replace my_pod.yaml

    Run a Kubernetes YAML file locally and save the generated Podman objects to a YAML file:

    podman kube play --save my_pod.yaml -o podman_objects.yaml
