DESCRIPCIÓ

N

La herramienta jarsigner tiene dos

propósitos:
•
Firmar archivos Java Archive (JAR)
.
•
Verificar las firmas y
la integridad de los
archivos JAR firmados.

La característica JAR permite empaquetar archivos de clases, imágenes, sonidos y otros datos digitales en un solo archivo para una distribución más rápida y sencilla. Una herramienta llamada jar permite a los desarrolladores producir archivos JAR. (Técnicamente, cualquier archivo ZIP también puede considerarse un archivo JAR, aunque cuando es creado por el comando jar o procesado por el comando jarsigner, los archivos JAR también contienen un archivo META-INF/MANIFEST.MF.

)

Una firma digital es una cadena de bits que se calcula a partir de algunos datos (los datos que se firman) y la clave privada de una entidad (una persona, empresa, etc.). De manera similar a una firma manuscrita, una firma digital tiene muchas características

útiles:
•
Su autenticidad puede ser verificada mediante un cálculo que utiliza la clave pública correspondiente a la clave privada utilizada para generar la
firma.
•
No puede ser falsificada, siempre que la clave privada se mantenga en
secreto.
•
Es una función de los datos firmados y por lo tanto no puede afirmarse que sea la firma de otros datos
también.
•
Los datos firmados no pueden ser modificados.
Si los datos son modificados, entonces la
firma no puede ser verificada como auténtica.

Para generar la firma de una entidad para un archivo, la entidad debe tener primero un par de claves pública/privada asociado con ella y uno o más certificados que autentiquen su clave pública. Un certificado es una declaración firmada digitalmente de una entidad que dice que la clave pública de otra entidad tiene un valor

particular.

El comando jarsigner utiliza la información de clave y certificado de un almacén de claves para generar firmas digitales para archivos JAR. Un almacén de claves es una base de datos de claves privadas y sus cadenas de certificados X.509 asociadas que autentican las claves públicas correspondientes. El comando keytool se utiliza para crear y administrar almacenes de

claves.

El comando jarsigner utiliza la clave privada de una entidad para generar una firma. El archivo JAR firmado contiene, entre otras cosas, una copia del certificado del almacén de claves para la clave pública correspondiente a la clave privada utilizada para firmar el archivo. El comando jarsigner puede verificar la firma digital del archivo JAR firmado utilizando el certificado que contiene (en su archivo de bloque de firma)

.

El comando jarsigner puede generar firmas que incluyan una marca de tiempo que permite a un sistema o desplegador comprobar si el archivo JAR fue firmado mientras el certificado de firma seguía siendo

válido.

Además, las API permiten a las aplicaciones obtener la información de la marca de

tiempo.

En este momento, el comando jarsigner solo puede firmar archivos JAR creados por el comando jar o archivos zip. Los archivos JAR son iguales a los archivos zip, excepto que también tienen un archivo META-INF/MANIFEST.MF. Un archivo META-INF/MANIFEST.MF se crea cuando el comando jarsigner firma un archivo

zip.

El comportamiento predeterminado del comando jarsigner es firmar un archivo JAR o zip. Utilice la opción -verify para verificar un archivo JAR

firmado.

El comando jarsigner también intenta validar el certificado del firmante después de firmar o verificar. Durante la validación, comprueba el estado de revocación de cada certificado en la cadena de certificados del firmante cuando se especifica la opción -revCheck . Si hay un error de validación u otro problema, el comando genera mensajes de advertencia. Si especifica la opción -strict, el comando trata las advertencias graves como errores. Véase Errores y ad

verte
ncias.

ALIAS DEL ALMACÉN DE

CLAVES

Todas las entidades del almacén de claves se acceden con alias

únicos.

Cuando utiliza el comando jarsigner para firmar un archivo JAR, debe especificar el alias de la entrada del almacén de claves que contiene la clave privada necesaria para generar la firma. Si no se especifica un archivo de salida, se sobrescribe el archivo JAR original con el archivo JAR

Los almacenes de claves están protegidos con una contraseña, por lo que la contraseña del almacén debe ser especificada. Se le solicitará cuando no la especifique en

la línea de comandos. De manera similar, las claves privadas están protegidas en un almacén de claves con una contraseña, por lo que la contraseña de la clave
privada debe ser especificada, y se le solicitará la contraseña cuando no la especifique en la línea de comandos y no sea la misma que la contraseña del almacén.

IMPLEMENTACIÓN DEL ALMACÉN DE

CLAVES

La clase KeyStore proporcionada en el paquete java.security suministra una serie de interfaces bien definidas para acceder y modificar la información en un almacén de claves. Puede haber múltiples implementaciones concretas diferentes, donde cada implementación es para un tipo particular de almacén de

claves.

Actualmente, hay dos herramientas de línea de comandos que utilizan implementaciones de almacén de claves (keytool> y jarsign

er).

La implementación de almacén de claves predeterminada es PKCS12. Este es un almacén de claves multiplataforma basado en el Estándar de Sintaxis de Intercambio de Información Personal PKCS12 de RSA. Este estándar está destinado principalmente a almacenar o transportar las claves privadas, los certificados y los secretos diversos de un usuario. Existe otra implementación integrada, proporcionada por Oracle. Implementa el almacén de claves como un archivo con un tipo (formato) de almacén de claves propietario llamado JKS. Protege cada clave privada con su contraseña individual y también protege la integridad de todo el almacén de claves con una (posiblemente diferente)

contraseña.

Las implementaciones de almacén de claves se basan en proveedores, lo que significa que las interfaces de aplicación proporcionadas por la clase KeyStore se implementan en términos de un Service Provider Interface (SPI). Existe una clase abstracta correspondiente KeystoreSpi, también en el paquete java.security, que define los métodos del Service Provider Interface que los proveedores deben implementar. El término proveedor se refiere a un paquete o a un conjunto de paquetes que proporcionan una implementación concreta de un subconjunto de servicios a los que se puede acceder mediante la Java Security API. Para proporcionar una implementación de almacén de claves, los clientes deben implementar un proveedor y proporcionar una implementación de subclase de KeystoreSpi, como se describe en Cómo implementar un proveedor en la Java Cryptography Architecture [https://www.oracle.com/pls/topic/lookup?ctx=en/java/javase/11/tools&id=JSSEC-GUID-2BCFDD85-D533-4E6C-8CE9-29990DEB0190]

.

Las aplicaciones pueden elegir diferentes tipos de implementaciones de almacén de claves de diferentes proveedores, con el método de fábrica getInstance en la clase KeyStore. Un tipo de almacén de claves define el almacenamiento y el formato de datos de la información del almacén de claves y los algoritmos utilizados para proteger las claves privadas en el almacén de claves y la integridad del propio almacén de claves. Las implementaciones de almacén de claves de diferentes tipos no son compatibles entre

sí.

Los comandos jarsigner pueden leer almacenes de claves basados en archivos desde cualquier ubicación que se pueda especificar mediante una URL. Además, estos comandos pueden leer almacenes de claves no basados en archivos, como los proporcionados por MSCAPI en Windows y PKCS11 en todas las

plataformas.

Para los comandos jarsigner y keytool, puede especificar un tipo de almacén de claves en la línea de comandos con la opción -stor

etype.

Si no especifica explícitamente un tipo de almacén de claves, las herramientas eligen una implementación de almacén de claves basándose en el valor de la propiedad keystore.type especificada en el archivo de propiedades de seguridad. El archivo de propiedades de seguridad se llama java.security, y se encuentra en el directorio de propiedades de seguridad del JDK, java.home/conf/security

.

Cada herramienta obtiene el valor keystore.type y luego examina todos los proveedores instalados hasta encontrar uno que implemente almacenes de claves de ese tipo. Luego utiliza la implementación de almacén de claves de ese

proveedor.

La clase KeyStore define un método estático llamado getDefaultType que permite a las aplicaciones recuperar el valor de la propiedad keystore.type. La siguiente línea de código crea una instancia del tipo de almacén de claves predeterminado, como se especifica en la propiedad keystore.

type:

KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType()

;

ARCHIVO DE BLOQUE DE FIRMA

El archivo .SF se firma y la firma se coloca en el archivo de bloque de firma. Este archivo también contiene, codificada en su interior, el certificado o la cadena de certificados del almacén de claves que autentica la clave pública correspondiente a la clave privada utilizada para firmar. El archivo tiene la extensión .DSA, .RSA o .EC, dependiendo del algoritmo de clave utilizado. Consulte la tabla en Algoritmos Soportados.

VERIFICACIÓN DE ARCHIVOS JAR

Una verificación exitosa de un archivo JAR ocurre cuando las firmas son válidas y ninguno de los archivos que estaban en el archivo JAR cuando se generaron las firmas ha cambiado desde entonces. La verificación de archivos JAR implica los siguientes pasos:

1.
Verificar la firma del archivo .SF.

La verificación asegura que la firma almacenada en cada archivo de bloque de firma fue generada usando la clave privada correspondiente a la clave pública cuya certificado (o cadena de certificados) también aparece en el archivo de bloque de firma. También asegura que la firma es una firma válida del archivo de firma (.SF) correspondiente, y por lo tanto, el archivo .SF no ha sido manipulado.

2.
Verificar el resumen (digest) listado en cada entrada del archivo .SF con cada sección correspondiente en el manifiesto.

El archivo .SF incluye por defecto una cabecera que contiene un hash de todo el archivo de manifiesto. Cuando la cabecera está presente, la verificación puede comprobar si el hash en la cabecera coincide o no con el hash del archivo de manifiesto. Si hay una coincidencia, la verificación procede al siguiente paso.

Si no hay coincidencia, se requiere una verificación menos optimizada para asegurar que el hash en cada sección de información de archivo fuente en el archivo .SF sea igual al hash de su sección correspondiente en el archivo de manifiesto. Consulte Archivo de Firma.

Una razón por la cual el hash del archivo de manifiesto que se almacena en la cabecera del archivo .SF podría no coincidir con el hash del archivo de manifiesto actual es que podría contener secciones para archivos recién añadidos después de que el archivo fuera firmado. Por ejemplo, suponga que uno o más archivos fueron añadidos al archivo JAR firmado (usando la herramienta jar) que ya contiene una firma y un archivo .SF. Si el archivo JAR se vuelve a firmar por un firmante diferente, entonces el archivo de manifiesto se modifica (se le añaden secciones para los nuevos archivos por la herramienta jarsigner) y se crea un nuevo archivo .SF, pero el archivo .SF original no se modifica. La verificación todavía se considera exitosa si ninguno de los archivos que estaban en el archivo JAR cuando se generó la firma original ha sido modificado desde entonces. Esto se debe a que los hashes en las secciones que no son cabeceras del archivo .SF coinciden con los hashes de las secciones correspondientes en el archivo de manifiesto.

3.
Leer cada archivo en el archivo JAR que tiene una entrada en el archivo .SF. Mientras se lee, calcular el resumen del archivo y comparar el resultado con el resumen de este archivo en la sección del manifiesto. Los resúmenes deben ser los mismos o la verificación falla.

Si ocurren fallos graves de verificación durante el proceso de verificación, el proceso se detiene y se lanza una excepción de seguridad. El comando jarsigner captura y muestra la excepción.

4.
Comprobar el uso de algoritmos deshabilitados. Consulte Algoritmos Soportados.

Nota:

Debería leer cualquier advertencia adicional (o errores si especificó la opción -strict), así como el contenido del certificado (especificando las opciones -verbose y -certs) para determinar si la firma puede ser confiable.

MÚLTIPLES FIRMAS PARA UN ARCHIVO JAR

Un archivo JAR puede ser firmado por varias personas ejecutando el comando jarsigner en el archivo varias veces y especificando el alias de una persona diferente cada vez, como sigue:


jarsigner myBundle.jar susan
jarsigner myBundle.jar kevin

Cuando un archivo JAR se firma varias veces, hay múltiples archivos .SF y archivos de bloque de firma en el archivo JAR resultante, un par por cada firma. En el ejemplo anterior, el archivo JAR de salida incluye archivos con los siguientes nombres:


SUSAN.SF
SUSAN.RSA
KEVIN.SF
KEVIN.RSA

OPCIONES PARA JARSIGNER

Las siguientes secciones describen las opciones para jarsigner. Tenga en cuenta los siguientes estándares:

•
Todos los nombres de opción van precedidos por un guión (-).
•
Las opciones pueden proporcionarse en cualquier orden.
•
Los elementos que están en cursiva o subrayados (valores de opción) representan los valores reales que deben proporcionarse.
•
Las opciones -storepass, -keypass, -sigfile, -sigalg, -digestalg, -signedjar y las opciones relacionadas con TSA solo son relevantes al firmar un archivo JAR; no son relevantes al verificar un archivo JAR firmado. La opción -keystore es relevante para firmar y verificar un archivo JAR. Además, se especifican alias al firmar y verificar un archivo JAR.
-keystore url
Especifica la URL que indica la ubicación del almacén de claves. Por defecto, es el archivo .keystore en el directorio principal del usuario, según lo determinado por la propiedad del sistema user.home.

Se requiere un almacén de claves al firmar. Debe especificar explícitamente un almacén de claves si el almacén de claves predeterminado no existe o si desea utilizar uno diferente al predeterminado.

No se requiere un almacén de claves al verificar, pero si se especifica uno o existe el predeterminado y también se especificó la opción -verbose, se mostrará información adicional sobre si los certificados utilizados para verificar el archivo JAR están contenidos en ese almacén de claves.

El argumento -keystore puede ser un nombre de archivo y una especificación de ruta en lugar de una URL, en cuyo caso se trata de la misma manera que una URL de archivo, por ejemplo, los siguientes son equivalentes:

•
-keystore rutaYNombreDeArchivo
•
-keystore file:rutaYNombreDeArchivo

Si el proveedor Sun PKCS #11 se configuró en el archivo de propiedades de seguridad java.security (ubicado en el directorio $JAVA_HOME/conf/security del JDK), entonces las herramientas keytool y jarsigner pueden operar en el token PKCS #11 especificando estas opciones:

-keystore NONE -storetype PKCS11

Por ejemplo, el siguiente comando lista el contenido del token PKCS#11 configurado:

keytool -keystore NONE -storetype PKCS11 -list

-storepass [:env | :file] argumento
Especifica la contraseña necesaria para acceder al almacén de claves. Esto solo es necesario al firmar (no al verificar) un archivo JAR. En ese caso, si no se proporciona una opción -storepass en la línea de comandos, se le pedirá al usuario la contraseña.

Si no se especifica el modificador env o file, la contraseña tiene el valor argumento. De lo contrario, la contraseña se recupera de la siguiente manera:

•
env: Recuperar la contraseña de la variable de entorno llamada argumento.
•
file: Recuperar la contraseña del archivo llamado argumento.

<

La contraseña no debe especificarse en la línea de comandos ni en un script a menos que sea para fines de prueba, o si se encuentra en un sistema seguro.

-storetype storetype
Especifica el tipo de almacén de claves que se va a instanciar. El tipo de almacén de claves predeterminado es el que se especifica como valor de la propiedad keystore.type en el archivo de propiedades de seguridad, que es devuelto por el método estático getDefaultType en java.security.KeyStore.

El PIN para un token PKCS #11 también se puede especificar con la opción -storepass. Si no se especifica ninguno, los comandos keytool y jarsigner solicitarán el PIN del token. Si el token tiene una ruta de autenticación protegida (como un lector de PIN dedicado o un lector biométrico), entonces se debe especificar la opción -protected y no se pueden especificar opciones de contraseña.

-keypass [:env | :file] argumento -certchain archivo
Especifica la contraseña utilizada para proteger la clave privada de la entrada del almacén de claves a la que se dirige el alias especificado en la línea de comandos. La contraseña es necesaria al usar jarsigner para firmar un archivo JAR. Si no se proporciona ninguna contraseña en la línea de comandos y la contraseña requerida es diferente de la contraseña del almacén, se le pedirá al usuario que la ingrese.

Si no se especifica el modificador env o file, la contraseña tendrá el valor argumento. De lo contrario, la contraseña se recupera de la siguiente manera:

•
env: Recupera la contraseña de la variable de entorno llamada argumento.
•
file: Recupera la contraseña del archivo llamado argumento.

Nota:

La contraseña no debe especificarse en la línea de comandos ni en un script a menos que sea para fines de prueba, o si se encuentra en un sistema seguro.

-certchain archivo
Especifica la cadena de certificados que se utilizará cuando la cadena de certificados asociada con la clave privada de la entrada del almacén de claves a la que se dirige el alias especificado en la línea de comandos no esté completa. Esto puede ocurrir cuando el almacén de claves se encuentra en un token de hardware donde no hay suficiente capacidad para almacenar una cadena de certificados completa. El archivo puede ser una secuencia de certificados X.509 concatenados, o un bloque de datos con formato PKCS#7, ya sea en formato de codificación binaria o en formato de codificación imprimible (también conocido como codificación Base64) según lo definido por el Estándar de Codificación de Certificados de **Internet RFC 1421** [http://tools.ietf.org/html/rfc1421].
-sigfile archivo
Especifica el nombre base del archivo que se utilizará para los archivos .SF y de bloque de firma generados. Por ejemplo, si el archivo es DUKESIGN, entonces los archivos .SF y de bloque de firma generados se llamarán DUKESIGN.SF y DUKESIGN.RSA, y se colocarán en el directorio META-INF del archivo JAR firmado.

Los caracteres del archivo deben provenir del conjunto a-zA-Z0-9_-. Solo se permiten caracteres de letras, números, guiones bajos y guiones. Todos los caracteres en minúscula se convierten a mayúsculas para los nombres de los archivos .SF y de bloque de firma.

Si no aparece ninguna opción -sigfile en la línea de comandos, entonces el nombre base del archivo para los archivos .SF y de bloque de firma son los primeros 8 caracteres del nombre del alias especificado en la línea de comandos, todos convertidos a mayúsculas. Si el nombre del alias tiene menos de 8 caracteres, se utiliza el nombre completo del alias. Si el nombre del alias contiene caracteres que no son válidos en un nombre de archivo de firma, cada uno de esos caracteres se convierte en un guión bajo (_) para formar el nombre del archivo.

-signedjar archivo
Especifica el nombre del archivo JAR firmado.
-digestalg algoritmo
Especifica el nombre del algoritmo de resumen de mensajes que se utilizará al resumir las entradas de un archivo JAR.

Para obtener una lista de nombres de algoritmos de resumen de mensajes estándar, consulte Nombres de Algoritmos Estándar de Seguridad de Java.

Si no se especifica esta opción, se utiliza SHA256. Debe haber un proveedor instalado estáticamente que proporcione una implementación del algoritmo especificado o el usuario debe especificar uno con las opciones -addprovider o -providerClass; de lo contrario, el comando no se realizará correctamente.

-sigalg algoritmo
Especifica el nombre del algoritmo de firma que se utilizará para firmar el archivo JAR.

Este algoritmo debe ser compatible con la clave privada utilizada para firmar el archivo JAR. Si no se especifica esta opción, se utilizará un algoritmo predeterminado que coincida con la clave privada como se describe en la sección **Algoritmos Soportados**. Debe haber un proveedor instalado estáticamente que proporcione una implementación del algoritmo especificado o debe especificar uno con la opción -addprovider o -providerClass; de lo contrario, el comando no se realizará correctamente.

Para obtener una lista de nombres de algoritmos de resumen de mensajes estándar, consulte Nombres de Algoritmos Estándar de Seguridad de Java.

-verify
Verifica un archivo JAR firmado.
-verbose[:subopciones]
Cuando la opción -verbose aparece en la línea de comandos, indica que jarsigner utilizará el modo detallado al firmar o verificar con las subopciones que determinan cuánta información se muestra. Esto provoca que jarsigner muestre información adicional sobre el progreso de la firma o verificación del JAR. Las subopciones pueden ser all, grouped, o summary.

Si también se especifica la opción -certs, entonces el modo predeterminado (o la subopción all) muestra cada entrada a medida que se procesa, y después de eso, la información del certificado para cada firmante del archivo JAR.

Si se especifican las subopciones -certs y -verbose:grouped, entonces las entradas con la misma información del firmante se agrupan y se muestran juntas con su información de certificado.

Si se especifican las subopciones -certs y -verbose:summary, entonces las entradas con la misma información del firmante se agrupan y se muestran juntas con su información de certificado.

Los detalles de cada entrada se resumen y se muestran como una entrada (y más). Consulte el **Ejemplo de Verificación de un Archivo JAR Firmado** y el **Ejemplo de Verificación con Información de Certificado**.

-certs
Si la opción -certs aparece en la línea de comandos con las opciones -verify y -verbose, entonces la salida incluirá información del certificado para cada firmante del archivo JAR. Esta información incluye el nombre del tipo de certificado (almacenado en el archivo de bloque de firma) que certifica la clave pública del firmante, y si el certificado es un certificado X.509 (una instancia de java.security.cert.X509Certificate), entonces el nombre distinguido del firmante.

También se examina el almacén de claves. Si no se especifica ningún valor de almacén de claves en la línea de comandos, se verifica el archivo de almacén de claves predeterminado (si existe). Si el certificado de clave pública de un firmante coincide con una entrada en el almacén de claves, entonces se muestra el nombre del alias de la entrada del almacén de claves para ese firmante entre paréntesis.

-revCheck
Esta opción habilita la verificación de revocación de certificados al firmar o verificar un archivo JAR. El comando jarsigner intenta establecer conexiones de red para obtener respuestas OCSP y CRLs si la opción -revCheck se especifica en la línea de comandos. Tenga en cuenta que las verificaciones de revocación no están habilitadas a menos que se especifique esta opción.
-tsa url
Si -tsa http://example.tsa.url aparece en la línea de comandos al firmar un archivo JAR, entonces se genera una marca de tiempo para la firma. La URL, http://example.tsa.url, identifica la ubicación de la Autoridad de Sellado de Tiempo (TSA) y anula cualquier URL encontrada con la opción -tsacert. La opción -tsa no requiere que el certificado de clave pública de la TSA esté presente en el almacén de claves.

Para generar la marca de tiempo, jarsigner se comunica con la TSA con el Sello de Tiempo

-tsacert alias
Specifies the timestamping authority (TSA) certificate alias.

When -tsacert alias appears on the command line when signing a JAR file, a timestamp is generated for the signature. The alias identifies the TSA public key certificate in the keystore that is in effect. The entry's certificate is examined for a Subject Information Access extension that contains a URL identifying the location of the TSA.

The TSA public key certificate must be present in the keystore when using the -tsacert option.

-tsacertsha1 sha1hex
Specifies the SHA1 public key hash of the TSA certificate to use for timestamping.
-tsadigestalg algorithm
Specifies the message digest algorithm that is used to generate the message imprint to be sent to the TSA server. If this option isn't specified, SHA-256 will be used.

See Supported Algorithms.

For a list of standard message digest algorithm names, see Java Security Standard Algorithm Names.

-tsapolicyid policyid
Specifies the object identifier (OID) that identifies the policy ID to be sent to the TSA server. If this option isn't specified, no policy ID is sent and the TSA server will choose a default policy ID.

Object identifiers are defined by X.696, which is an ITU Telecommunication Standardization Sector (ITU-T) standard. These identifiers are typically period-separated sets of non-negative digits like 1.2.3.4, for example.

-tsa url
Specifies the URL of the timestamping authority (TSA) server. The TSA server accepts requests for timestamping and returns a timestamp token in response. The timestamp token is digitally signed by the TSA and includes the hash of the data for which the timestamp was requested, the name of the TSA, and the date and time of the request. The Time-Stamp Protocol (TSP) defined in RFC 3161 is used. When successful, the time stamp token returned by the TSA is stored with the signature in the signature block file.
-v
Verify the signature.
-verify
Examines the signature files in the specified JAR file and checks them for validity.
-verbose
Enables extra output during the execution of the command. For example, during the signing process, it prints the names of the entries as they are being signed.
-internalsf
In the past, the signature block file generated when a JAR file was signed included a complete encoded copy of the .SF file (signature file) also generated. This behavior has been changed. To reduce the overall size of the output JAR file, the signature block file by default doesn't contain a copy of the .SF file anymore. If -internalsf appears on the command line, then the old behavior is utilized. This option is useful for testing. In practice, don't use the -internalsf option because it incurs higher overhead.
-sectionsonly
If the -sectionsonly option appears on the command line, then the .SF file (signature file) generated when a JAR file is signed doesn't include a header that contains a hash of the whole manifest file. It contains only the information and hashes related to each individual source file included in the JAR file. See Signature File.

By default, this header is added, as an optimization. When the header is present, whenever the JAR file is verified, the verification can first check to see whether the hash in the header matches the hash of the whole manifest file. When there is a match, verification proceeds to the next step. When there is no match, it is necessary to do a less optimized verification that the hash in each source file information section in the .SF file equals the hash of its corresponding section in the manifest file. See JAR File Verification.

The -sectionsonly option is primarily used for testing. It shouldn't be used other than for testing because using it incurs higher overhead.

-protected
Values can be either true or false. Specify true when a password must be specified through a protected authentication path such as a dedicated PIN reader.
-providerName providerName
If more than one provider was configured in the java.security security properties file, then you can use the -providerName option to target a specific provider instance. The argument to this option is the name of the provider.

For the Oracle PKCS #11 provider, providerName is of the form SunPKCS11-TokenName, where TokenName is the name suffix that the provider instance has been configured with, as detailed in the configuration attributes table. For example, the following command lists the contents of the PKCS #11 keystore provider instance with name suffix SmartCard:

jarsigner -keystore NONE -storetype PKCS11 -providerName SunPKCS11-SmartCard -list

-addprovider name [-providerArg arg]
Adds a security provider by name (such as SunPKCS11) and an optional configure argument. The value of the security provider is the name of a security provider that is defined in a module.

Used with the -providerArg ConfigFilePath option, the keytool and jarsigner tools install the provider dynamically and use ConfigFilePath for the path to the token configuration file. The following example shows a command to list a PKCS #11 keystore when the Oracle PKCS #11 provider wasn't configured in the security properties file.

jarsigner -keystore NONE -storetype PKCS11 -addprovider SunPKCS11 -providerArg /mydir1/mydir2/token.config

-providerClass provider-class-name [-providerArg arg]
Used to specify the name of cryptographic service provider's master class file when the service provider isn't listed in the java.security security properties file. Adds a security provider by fully-qualified class name and an optional configure argument.

Note:

The preferred way to load PKCS11 is by using modules. See -addprovider.

Passes through the specified javaoption string directly to the Java interpreter. The jarsigner command is a wrapper around the interpreter. This option shouldn't contain any spaces. It is useful for adjusting the execution environment or memory usage. For a list of possible interpreter options, type java -h or java -X at the command line.
-strict
During the signing or verifying process, the command may issue warning messages. If you specify this option, the exit code of the tool reflects the severe warning messages that this command found. See Errors and Warnings.
-conf url
Specifies a pre-configured options file. Read the keytool documentation for details. The property keys supported are "jarsigner.all" for all actions, "jarsigner.sign" for signing, and "jarsigner.verify" for verification. jarsigner arguments including the JAR file name and alias name(s) cannot be set in this file.

If the certificate for a signer isn't an X.509 certificate, then
    there is no distinguished name information. In that case, just the
    certificate type and the alias are shown. For example, if the certificate is
    a PGP certificate, and the alias is bob, then
    you would get: PGP, (bob).
