Verificar las firmas y la integridad de los archivos JAR firmados. La característica JAR permite empaquetar archivos de clases, imágenes, sonidos y otros datos digitales en un solo archivo para una distribución más rápida y fácil. Una herramienta llamada jar permite a los desarrolladores producir archivos JAR. (Técnicamente, cualquier archivo zip también puede considerarse un archivo JAR, aunque cuando es creado por el comando jar o procesado por el comando jarsigner, los archivos JAR también contienen

un

Una firma digital es una cadena de bits que se calcula a partir de
algunos datos (los datos que se firman) y la clave privada de una entidad (una persona, empresa, etc.). Similar a una firma manuscrita, una firma digital tiene muchas características útiles:
•
Su autenticidad puede verificarse mediante
un cálculo que utiliza la clave pública correspondiente a la clave privada utilizada para generar la firma.
•
No puede ser falsificada,
asumiendo que la clave privada se mantiene en secreto.
•
Es una función de los datos
firmados y por lo tanto no puede afirmarse que sea la firma de otros datos también.
•

Los datos firmados no pueden ser modificados. Si los datos se modifican, entonces la firma no puede verificarse como

auténtica.

Para generar la firma de una entidad para un archivo, la entidad debe tener primero un par de claves pública/privada asociado con ella y uno o más certificados que autentiquen su clave pública. Un certificado es una declaración firmada digitalmente de una entidad que dice que la clave pública de otra entidad tiene un valor particular. El comando jarsigner usa información de clave y certificado de un almacén de claves para generar firmas digitales para archivos JAR. Un almacén de claves es una base de datos de claves privadas y sus cadenas de certificados X.509 asociadas que autentican las claves públicas correspondientes.

El

comando keytool se usa para crear y administrar almacenes de claves. El comando jarsigner usa la clave privada de una entidad para generar una firma. El archivo JAR firmado contiene, entre otras cosas, una copia del certificado del almacén de claves para la clave pública correspondiente a la clave privada utilizada para firmar el archivo.

El

comando jarsigner puede verificar la firma digital del archivo JAR firmado usando el certificado dentro de él (en su archivo de bloque de firma). E

l

comando jarsigner puede generar firmas que incluyan una marca de tiempo que permite a un sistema o desplegador (incluido Java Plug-in) comprobar si el archivo JAR fue firmado mientras el certificado de firma seguía siendo válido. Además, las API permiten a las aplicaciones obtener la información de la marca de tiempo. En este momento, el comando jarsigner solo puede firmar archivos JAR creados por el comando jar o archivos zip. Los archivos JAR son iguales que los archivos zip, excepto que también tienen un archivo META-INF/MANIFEST.MF. Un archivo META-INF/MANIFEST.MF se crea cuando

el

IMPLEMENTACIÓN DEL ALMACÉN DE

CLAVES

La clase KeyStore proporcionada en el paquete java.security suministra una serie de interfaces bien definidas para acceder y modificar la información en un almacén de claves. Puede tener múltiples implementaciones concretas diferentes, donde cada implementación es para un tipo particular de almacén de

claves.

Actualmente, hay dos herramientas de línea de comandos que usan implementaciones de almacén de claves (keytool y jarsigner), y una herramienta basada en GUI llamada Policy Tool. Como la clase KeyStore está públicamente disponible, los usuarios de JDK pueden escribir aplicaciones de seguridad adicionales que la

usen.

Hay una implementación predeterminada incorporada proporcionada por Oracle que implementa el almacén de claves como un archivo, que usa un tipo de almacén de claves propietario (formato) llamado JKS. La implementación incorporada protege cada clave privada con su contraseña individual y protege la integridad del almacén de claves completo con una (posiblemente diferente)

contraseña.

Las implementaciones de almacenes de claves se basan en proveedores, lo que significa que las interfaces de aplicación suministradas por la clase KeyStore se implementan en términos de una Interfaz de Proveedor de Servicios (SPI). Hay una clase abstracta correspondiente KeystoreSpi, también en el paquete java.security, que define los métodos de la Interfaz de Proveedor de Servicios que los proveedores deben implementar. El término proveedor se refiere a un paquete o un conjunto de paquetes que suministran una implementación concreta de un subconjunto de servicios que pueden ser accedidos por la API de Seguridad de Java. Para proporcionar una implementación de almacén de claves, los clientes deben implementar un proveedor y suministrar una implementación de subclase de KeystoreSpi como se describe en Cómo implementar un proveedor

IMPLEMENTACIONES DE&#x00A0;KEYSTORE

La arquitectura de cifrado de Java proporciona el marco necesario para implementar un proveedor de seguridad que puede proporcionar algoritmos criptográficos y almacenes de claves.

Para obtener más información sobre la implementación de un proveedor de seguridad, consulta la Arquitectura de Cifrado de Java en http://docs.oracle.com/javase/8/docs/technotes/guides/security/crypto/HowToImplAProvider.html

Las aplicaciones pueden elegir diferentes tipos de implementaciones de keystore de diferentes proveedores, con el método fábrica getInstance en la clase KeyStore. Un tipo de keystore define el formato de almacenamiento y datos de la información del keystore y los algoritmos utilizados para proteger las claves privadas en el keystore y la integridad del propio keystore. Las implementaciones de keystore de diferentes tipos no son compatibles.

El comando jarsigner puede leer keystores basados en archivos desde cualquier ubicación que se pueda especificar mediante una URL. Además, el comando puede leer keystores no basados en archivos, como los proporcionados por MSCAPI en Windows y PKCS11 en todas las plataformas.

Para los comandos jarsigner y keytool, puedes especificar un tipo de keystore en la línea de comandos con la opción -storetype. Para Policy Tool, puedes especificar un tipo de keystore con el comando Edit en el menú KeyStore.

Si no especificas explícitamente un tipo de keystore, las herramientas eligen una implementación de keystore basada en el valor de la propiedad keystore.type especificada en el archivo de propiedades de seguridad. El archivo de propiedades de seguridad se llama java.security y reside en el directorio de propiedades de seguridad del JDK, java.home/lib/security, donde java.home es el directorio del entorno de ejecución. El directorio jre en el JDK o el directorio de nivel superior del Entorno de Ejecución Java (JRE).

Cada herramienta obtiene el valor de keystore.type y luego examina todos los proveedores instalados hasta que encuentra uno que implementa keystores de ese tipo. Luego, utiliza la implementación de keystore de ese proveedor.

La clase KeyStore define un método estático llamado getDefaultType que permite a las aplicaciones y applets recuperar el valor de la propiedad keystore.type. La siguiente línea de código crea una instancia del tipo de keystore predeterminado según lo especificado en la propiedad keystore.type:

KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType());

El tipo de keystore predeterminado es jks (el tipo propietario de la implementación de keystore proporcionada por Oracle). Esto se especifica mediante la siguiente línea en el archivo de propiedades de seguridad:

keystore.type=jks

La distinción entre mayúsculas y minúsculas no importa en las designaciones de tipo de keystore. Por ejemplo, JKS es lo mismo que jks.

Para que las herramientas utilicen una implementación de keystore distinta de la predeterminada, cambia esa línea para especificar un tipo de keystore diferente. Por ejemplo, si tienes un paquete de proveedor que suministra una implementación de keystore para un tipo de keystore llamado pkcs12, entonces cambia la línea a la siguiente:

keystore.type=pkcs12

Nota: Si utilizas el paquete de proveedor PKCS 11, consulta "KeyTool" y "JarSigner" en la Guía de Referencia de Java PKCS #11 en http://docs.oracle.com/javase/8/docs/technotes/guides/security/p11guide.html

ALGORITMOS SOPORTADOS

Por defecto, el comando jarsigner firma un archivo JAR utilizando uno de los siguientes algoritmos:

•
Algoritmo de Firma Digital (DSA) con el algoritmo de resumen SHA1
•
Algoritmo RSA con el algoritmo de resumen SHA256
•
Criptografía de Curva Elíptica (EC) con el algoritmo de Firma Digital de Curva Elíptica SHA256 (ECDSA).

Si las claves pública y privada del firmante son claves DSA, entonces jarsigner firma el archivo JAR con el algoritmo SHA1withDSA. Si las claves del firmante son claves RSA, entonces jarsigner intenta firmar el archivo JAR con el algoritmo SHA256withRSA. Si las claves del firmante son claves EC, entonces jarsigner firma el archivo JAR con el algoritmo SHA256withECDSA.

Estos algoritmos de firma predeterminados se pueden anular utilizando la opción -sigalg.

EL ARCHIVO JAR FIRMADO

Cuando se utiliza el comando jarsigner para firmar un archivo JAR, el archivo JAR firmado de salida es exactamente el mismo que el archivo JAR de entrada, excepto que tiene dos archivos adicionales colocados en el directorio META-INF:

•
Un archivo de firma con una extensión .SF
•
Un archivo de bloque de firma con una extensión .DSA, .RSA o .EC

Los nombres base de estos dos archivos provienen del valor de la opción -sigFile. Por ejemplo, cuando la opción es -sigFile MKSIGN, los archivos se llaman MKSIGN.SF y MKSIGN.DSA

Si no aparece ninguna opción -sigfile en la línea de comandos, entonces el nombre base del archivo para los archivos .SF y .DSA son los primeros 8 caracteres del nombre del alias especificado en la línea de comandos, todos convertidos a mayúsculas. Si el nombre del alias tiene menos de 8 caracteres, se utiliza el nombre completo del alias. Si el nombre del alias contiene caracteres no permitidos en un nombre de archivo de firma, cada carácter se convierte en un guion bajo (_) al formar el nombre del archivo. Los caracteres válidos incluyen letras, dígitos, guiones bajos y guiones.

Archivo de Firma

Un archivo de firma (archivo .SF) se parece al archivo manifest que siempre se incluye en un archivo JAR cuando se utiliza el comando jarsigner para firmar el archivo. Para cada archivo fuente incluido en el archivo JAR, el archivo .SF tiene tres líneas, al igual que en el archivo manifest, que enumeran lo siguiente:

•
Nombre del archivo
•
Nombre del algoritmo de resumen (SHA)
•
Valor del resumen SHA

En el archivo manifest, el valor del resumen SHA para cada archivo fuente es el resumen (hash) de los datos binarios en el archivo fuente. En el archivo .SF, el valor del resumen para un archivo fuente especificado es el hash de las tres líneas del archivo manifest correspondientes al archivo fuente.

El archivo de firma, por defecto, incluye una cabecera con un hash de todo el archivo manifest. La cabecera también contiene un hash de la cabecera del manifest. La presencia de la cabecera permite la optimización de la verificación. Consulta Verificación de Archivos JAR.

Archivo de Bloque de Firma

El archivo .SF se firma y la firma se coloca en el archivo de bloque de firma. Este archivo también contiene, codificado en su interior, el certificado o la cadena de certificados del keystore que autentica la clave pública correspondiente a la clave privada utilizada para firmar. El archivo tiene la extensión .DSA, .RSA o .EC, dependiendo del algoritmo de resumen utilizado.

VERIFICACIÓN DE ARCHIVOS JAR

Una verificación exitosa de un archivo JAR se produce cuando las firmas son válidas y ninguno de los archivos que estaban en el archivo JAR cuando se generaron las firmas ha cambiado desde entonces. La verificación de archivos JAR implica los siguientes pasos:

1.
Verifica la firma del archivo .SF.

La verificación asegura que la firma almacenada en cada bloque de firma (.DSA) se generó utilizando la clave privada correspondiente a la clave pública cuya certificado (o cadena de certificados) también aparece en el archivo .DSA. También asegura que la firma es una firma válida del archivo de firma (.SF) correspondiente, y por lo tanto, el archivo .SF no ha sido manipulado.

2.
Verifica el resumen listado en cada entrada del archivo .SF con cada sección correspondiente en el manifest.

El archivo .SF incluye por defecto una cabecera que contiene un hash de todo el archivo manifest. Cuando la cabecera está presente, la verificación puede comprobar si el hash en la cabecera coincide o no con el hash del archivo manifest. Si hay una coincidencia, la verificación continúa al siguiente paso.

Si no hay coincidencia, se requiere una verificación menos optimizada para asegurar que el hash en cada sección de información de archivo fuente en el archivo .SF sea igual al hash de su sección correspondiente en el archivo manifest. Consulta Archivo de Firma.

Una razón por la que el hash del archivo manifest almacenado en la cabecera del archivo .SF podría no coincidir con el hash del archivo manifest actual es que uno o más archivos se agregaron al archivo JAR (con la herramienta jar) después de que se generaran la firma y el archivo .SF. Cuando se utiliza la herramienta jar para agregar archivos, el archivo manifest se modifica agregando secciones para los nuevos archivos, pero el archivo .SF no se modifica. La verificación aún se considera exitosa cuando ninguno de los archivos que estaban en el archivo JAR cuando se generó la firma ha sido modificado desde entonces. Esto ocurre cuando los hashes en las secciones no cabecera del archivo .SF coinciden con los hashes de las secciones correspondientes en el archivo manifest.

Uno de los motivos por los que el hash del archivo manifest que se almacena en el encabezado del archivo .SF podría no ser igual al hash del archivo manifest actual es que uno o más archivos se agregaron al archivo JAR (con la herramienta jar) después de que se generaran la firma y el archivo .SF. Cuando se utiliza la herramienta jar para agregar archivos, el archivo manifest se modifica agregando secciones para los nuevos archivos, pero el archivo .SF no se modifica. La verificación aún se considera exitosa cuando ninguno de los archivos que estaban en el archivo JAR cuando se generó la firma ha sido modificado desde entonces. Esto ocurre cuando los hashes en las secciones no del encabezado del archivo .SF coinciden con los hashes de las secciones correspondientes en el archivo manifest.

3.
Lee cada archivo en el archivo JAR que tiene una entrada en el archivo .SF. Mientras lees, calcula el resumen del archivo y compara el resultado con el resumen de este archivo en la sección del manifest. Los resúmenes deben ser los mismos o la verificación fallará.

Si ocurren fallos de verificación graves durante el proceso de verificación, el proceso se detiene y se lanza una excepción de seguridad. El comando jarsigner captura y muestra la excepción.

NOMBRE

jarsigner

firma y verifica archivos JAR

SINOPSIS

jarsigner [-keystore keystore] [-storepass password] [-storetype type] [-keypass password] [-certchain chain] [-sigfile file] [-signedjar signedjar] [-cvcertsize size] [-internalsf] [-verify] [-verbose] [-debug] [-Joption] [-sigalg digestalg] [-digestalg digestalg] [-providerName name] [-providerClass class[:option]] [-providerArg arg] [-calign align] [-ாளர்க] [-nosigbatch] [-noverify] [-maxMemory size] [-encoding encoding] jar alias [alias ...]

DESCRIPCIÓN

El comando jarsigner se utiliza para firmar archivos JAR con una clave privada. También puede comprobar la validez de una firma en un archivo JAR firmado. La utilidad jarsigner puede operar en archivos JAR que contengan entradas que requieran una verificación de la firma de un único firmante.

El comando jarsigner tiene dos modos: firma y verificación. Cuando se invoca sin la opción -verify, firma el archivo JAR especificado.

Cuando se invoca con la opción -verify, verifica el archivo JAR especificado.

En el modo de firma, el comando jarsigner firma el archivo JAR especificado usando el alias y las contraseñas proporcionados. Si se proporciona la opción -signedjar, el archivo JAR firmado se guardará con el nombre especificado. Si no se proporciona, el archivo JAR de entrada se sobrescribirá con el archivo JAR firmado.

En el modo de verificación, el comando jarsigner comprueba las firmas de las entradas del archivo JAR especificado. Si se proporciona la opción -verbose, se imprime información detallada sobre la verificación. Si se proporciona la opción -certs, se imprime información sobre los certificados utilizados para firmar el archivo JAR.

ERRORES Y ADVERTENCIAS

Cuando se utiliza la opción jarsigner con la opción -strict, los códigos de salida se combinan utilizando el operador OR a nivel de bits. Por ejemplo, si un certificado utilizado para firmar una entrada ha caducado y tiene una extensión KeyUsage que no le permite firmar un archivo, el comando jarsigner sale con el código 12 (=4+8) cuando se especifica la opción -strict.

Nota: Los códigos de salida se reutilizan porque solo los valores de 0 a 255 son legales en los sistemas operativos basados en Unix.

Las siguientes secciones describen los nombres, códigos y descripciones de los errores y advertencias que el comando jarsigner puede emitir.

FALLO

Las razones por las que falla el comando jarsigner incluyen (entre otras) un error de análisis de línea de comandos, la imposibilidad de encontrar un par de claves para firmar el archivo JAR o el fallo de la verificación de un archivo JAR firmado.

fallo
Código 1. Falla la firma o la verificación.

Las advertencias informativas incluyen aquellas que no son errores pero se consideran malas prácticas. No tienen un código.

FIRMAR UN ARCHIVO JAR

Utilice el siguiente comando para firmar bundle.jar con la clave privada de un usuario cuyo alias de almacén de claves es jane en un almacén de claves llamado mystore en el directorio working y nombre el archivo JAR firmado sbundle.jar:

jarsigner -keystore /working/mystore
    -storepass <contraseña del almacén de claves>
    -keypass <contraseña de la clave privada>
    -signedjar sbundle.jar bundle.jar jane

No se especifica ningún -sigfile en el comando anterior, por lo que los archivos .SF y .DSA generados que se colocarán en el archivo JAR firmado tienen nombres predeterminados basados en el nombre del alias. Se llaman JANE.SF y JANE.DSA.

Si desea que se le pida la contraseña del almacén y la contraseña de la clave privada, puede acortar el comando anterior al siguiente:

jarsigner -keystore /working/mystore
    -signedjar sbundle.jar bundle.jar jane

Si el almacén de claves es el almacén de claves predeterminado (.keystore en su directorio de inicio), entonces no necesita especificar un almacén de claves, como se muestra a continuación:

jarsigner -signedjar sbundle.jar bundle.jar jane

Si desea que el archivo JAR firmado sobrescriba el archivo JAR de entrada (bundle.jar), entonces no necesita especificar una opción -signedjar, como se muestra a continuación:

jarsigner bundle.jar jane
