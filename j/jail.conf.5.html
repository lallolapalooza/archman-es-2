JAIL.CONF(5) Configuración de Fail2Ban JAIL.CONF(5)

NOMBRE

jail.conf - configuración para el servidor fail2ban

SINOPSIS

fail2ban.conf fail2ban.d/*.conf fail2ban.local fail2ban.d/*.local

jail.conf jail.d/*.conf jail.local jail.d/*.local

action.d/*.conf action.d/*.local action.d/*.py

filter.d/*.conf filter.d/*.local

DESCRIPCIÓN

Fail2ban tiene cuatro tipos de archivos de configuración:

fail2ban.conf
Configuración global de Fail2Ban (como el registro)
filter.d/*.conf
Filtros que especifican cómo detectar fallos de autenticación
action.d/*.conf
Acciones que definen los comandos para bloquear y desbloquear direcciones IP
jail.conf
Jaulas que definen combinaciones de filtros con acciones.

FORMATO DE LOS ARCHIVOS DE CONFIGURACIÓN

Los archivos *.conf son distribuidos por Fail2Ban. Se recomienda que los archivos *.conf permanezcan sin cambios para facilitar las actualizaciones. Si es necesario, las personalizaciones deben proporcionarse en archivos *.local. Por ejemplo, si desea habilitar la jaula [ssh-iptables-ipset] especificada en jail.conf, cree jail.local que contenga

jail.local
[ssh-iptables-ipset]

enabled = true

En los archivos .local, especifique solo las configuraciones que desea cambiar y el resto de la configuración provendrá del archivo .conf correspondiente, que se analiza primero.

jail.d/ y fail2ban.d/

Además de .local, para el archivo jail.conf o fail2ban.conf puede haber un directorio .d/ correspondiente que contenga archivos .conf adicionales. El orden, por ejemplo, para la configuración de jail sería:

jail.conf
jail.d/*.conf (en orden alfabético)
jail.local
jail.d/*.local (en orden alfabético).

es decir, todos los archivos .local se analizan después de los archivos .conf en el archivo de configuración original y los archivos en el directorio .d. La configuración en el archivo analizado más tarde tiene precedencia sobre entradas idénticas en archivos analizados previamente. Los archivos se ordenan alfabéticamente, por ejemplo,

fail2ban.d/01_custom_log.conf - para usar una ruta de registro diferente

jail.d/01_enable.conf - para habilitar una jaula específica
jail.d/02_custom_port.conf - para cambiar el(los) puerto(s) de una jaula.

Los archivos de configuración tienen secciones, especificadas con [nombre de sección], y pares nombre = valor. Para aquellos elementos de nombre que pueden aceptar múltiples valores, especifique los valores separados por espacios, o en líneas separadas con sangría al principio de la línea antes del segundo valor.

Los archivos de configuración pueden incluir otros archivos de configuración (que definen variables comunes), lo que a menudo se utiliza en Filtros y Acciones. Dichas inclusiones se definen en una sección llamada [INCLUDES]:

antes
indica que el archivo especificado debe analizarse antes del archivo actual.
después
indica que el archivo especificado debe analizarse después del archivo actual.

Usando los mecanismos de "interpolación de cadenas" de Python, se permiten otras definiciones y luego se pueden usar dentro de otras definiciones como %(name)s.

Fail2ban tiene una sintaxis más avanzada (similar a la interpolación extendida de Python). Esta interpolación extendida utiliza %(section/parameter)s para denotar un valor de una sección externa.
Además de la interpolación entre secciones, el valor del parámetro en la sección [DEFAULT] se puede recuperar con %(default/parameter)s.
Fail2ban también admite otra característica llamada %(known/parameter)s (significa la última opción conocida con el nombre parameter). Esta interpolación hace posible extender una expresión regular de filtro o jaula existente en .local (a diferencia de simplemente establecer failregex/ignoreregex que la sobrescribe), por ejemplo

baduseragents = IE|wget|%(my-settings/baduseragents)s
failregex = %(known/failregex)s
            useragent=%(baduseragents)s

Además de la interpolación %(known/parameter)s, que no funciona para parámetros de inicialización de filtros/acciones, se puede usar una etiqueta de interpolación <known/parameter> (significa la última definición de inicialización conocida de filtros o acciones con el nombre parameter). Esta interpolación hace posible extender los parámetros de un filtro o acción existente directamente en la jaula dentro del archivo jail.conf/jail.local sin crear un archivo filter.d/*.local por separado, por ejemplo

# filter.d/test.conf: 
[Init]
test.method = GET
baduseragents = IE|wget
[Definition]
failregex = ^%(__prefix_line)\s+"<test.method>"\s+test\s+regexp\s+-\s+useragent=(?:<baduseragents>)
# jail.local:
[test]
# usa el filtro "test", sobrescribe el método a "POST" y extiende los agentes malos conocidos con "badagent":
filter = test[test.method=POST, baduseragents="badagent|<known/baduseragents>"]

Comentarios: use '#' para líneas de comentario y '; ' (el espacio es importante) para comentarios en línea.

ARCHIVOS DE CONFIGURACIÓN DE FAIL2BAN (fail2ban.conf)

Los elementos que se pueden establecer en la sección [Definition] son:

loglevel
nivel de verbosidad de la salida del registro: CRITICAL, ERROR, WARNING, NOTICE, INFO, DEBUG, TRACEDEBUG, HEAVYDEBUG o valor numérico correspondiente (50-5). Por defecto: INFO (igual a 20)
logtarget
destino del registro: nombre de archivo, SYSLOG, STDERR o STDOUT. Por defecto: STDOUT si no se establece en fail2ban.conf/fail2ban.local
Nota: Si fail2ban se ejecuta como un servicio systemd, para registrar en el diario de systemd, el logtarget podría establecerse en STDOUT
Solo se puede especificar un destino de registro. Si cambia el logtarget del valor predeterminado y está utilizando logrotate, también ajuste o deshabilite la rotación en el archivo de configuración correspondiente (por ejemplo, /etc/logrotate.d/fail2ban en sistemas Debian).
socket
nombre de archivo del socket. Por defecto: /var/run/fail2ban/fail2ban.sock
Esto se utiliza para la comunicación con el demonio servidor de fail2ban. No elimine este archivo cuando Fail2ban esté en ejecución. De lo contrario, no será posible comunicarse con el servidor.
pidfile
nombre de archivo PID. Por defecto: /var/run/fail2ban/fail2ban.pid
Esto se utiliza para almacenar el ID del proceso del servidor fail2ban.
allowipv6
opción para permitir la interfaz IPv6 - auto, sí (on, true, 1) o no (off, false, 0). Por defecto: auto
Este valor se puede utilizar para declarar a fail2ban si se permite IPv6 o no.
dbfile
nombre de archivo de la base de datos. Por defecto: /var/lib/fail2ban/fail2ban.sqlite3
Esto define dónde se almacenan los datos persistentes para fail2ban. Estos datos persistentes permiten que los bloqueos se restablezcan y continúen leyendo los archivos de registro desde la última posición leída cuando fail2ban se reinicia. Un valor de None deshabilita esta función.
dbmaxmatches
Número máximo de coincidencias almacenadas en la base de datos por ticket. Por defecto: 10
Esta opción establece el número máximo de líneas de registro coincidentes que se pueden almacenar por ticket en la base de datos. Esto también afecta a los valores que se pueden resolver a través de las etiquetas <ipmatches> y <ipjailmatches> en las acciones.
dbpurgeage
Edad de purga de la base de datos en segundos. Por defecto: 86400 (24 horas)
Esto establece la edad a la que los bloqueos deben ser purgados de la base de datos.

ARCHIVOS DE CONFIGURACIÓN DE JAULA (jail.conf)

Las siguientes opciones son aplicables a cualquier jaula. Aparecen en una sección que especifica el nombre de la jaula o en la sección [DEFAULT] que define los valores predeterminados que se utilizarán si no se especifican en la sección individual.

filtro
nombre del filtro: nombre del archivo del filtro en /etc/fail2ban/filter.d/ sin la extensión .conf/.local.
Solo se puede especificar un filtro.
ruta_log
nombres de archivo de los registros que se supervisarán, separados por saltos de línea.
Se pueden utilizar comodines (globbing), como paths que contengan * y ? o [0-9], sin embargo, solo se considerarán los archivos que existan al arranque y que coincidan con este patrón de comodín.

La opción opcional 'tail' separada por espacios se puede agregar al final de la ruta para hacer que el archivo de registro se lea desde el final; de lo contrario, la opción predeterminada 'head' lee el archivo desde el principio.

Asegúrese de que syslog o el programa que genera el archivo de registro no esté configurado para comprimir mensajes de registro repetidos a "*último mensaje repetido 5 veces*", de lo contrario, no podrá detectarlo. Esto se llama RepeatedMsgReduction en rsyslog y debe estar en Off.

codificacion_log
codificación de los archivos de registro utilizada para la decodificación. El valor predeterminado "auto" utiliza la configuración regional actual del sistema.
zona_horaria_log
fuerza la zona horaria de las líneas de registro que no tienen una.

Si esta opción no se especifica, las líneas de registro de las cuales no se ha encontrado ninguna zona horaria explícita son interpretadas por fail2ban en su propia zona horaria del sistema, y eso puede ser inapropiado. Si bien la mejor práctica es configurar las aplicaciones supervisadas para que incluyan compensaciones explícitas, esta opción está destinada a manejar casos en los que eso no es posible.

Las zonas horarias compatibles en esta opción son aquellas con compensación fija: Z, UTC[+-]hhmm (también puede usar GMT como alias de UTC).

Esta opción no tiene efecto en las líneas de registro en las que se ha encontrado una zona horaria explícita. Ejemplos:

        zona_horaria_log = UTC
        zona_horaria_log = UTC+0200
        zona_horaria_log = GMT-0100
accion_ban
acción de bloqueo (iptables-multiport por defecto) típicamente especificada en la sección [DEFAULT] para todas las jaulas.
Este parámetro será utilizado por la sustitución estándar de action y puede ser redefinido centralmente en la sección [DEFAULT] dentro de jail.local (para aplicarlo a todas las jaulas a la vez) o por separado en cada jaula, donde se utilizará esta sustitución.
accion_ban_todos_puertos
lo mismo que accion_ban pero para algunas jaulas de "todos_puertos" como "pam-generic" o "recidive" (iptables-allports por defecto).
accion
acción(es) de /etc/fail2ban/action.d/ sin la extensión .conf/.local.
Se pueden pasar argumentos a las acciones para anular los valores predeterminados de la sección [Init] en el archivo de acción. Los argumentos se especifican mediante:

[nombre=valor,nombre2=valor,nombre3="valores,valores"]

Los valores también pueden entrecomillarse (necesario cuando el valor incluye una ","). Se pueden especificar más de una acción (en líneas separadas).
ignorar_propia_ip
valor booleano (predeterminado verdadero) indica que se debe evitar el bloqueo de las propias direcciones IP.
ignorar_ip
lista de IPs que no se deben bloquear. Pueden incluir DNS o máscara CIDR. La opción afecta adicionalmente a ignorar_propia_ip (si es verdadero) y no necesita contener las propias IPs o DNS del host en ejecución.
ignorar_comando
comando que se ejecuta para determinar si la IP candidata actual para el bloqueo (o el ID de fallo para IDs sin procesar) no debería ser bloqueada. Esta opción opera junto con las opciones ignorar_propia_ip y ignorar_ip. Se ejecuta primero, solo si ni ignorar_propia_ip ni ignorar_ip coinciden con los criterios.
La IP no será bloqueada si el comando devuelve éxito (código de salida 0). Al igual que los ARCHIVOS DE ACCIÓN, las etiquetas como <ip> se pueden incluir en el valor de ignorecommand y se sustituirán antes de la ejecución.
cache_ignorar
proporciona parámetros de caché (deshabilitado por defecto) para la comprobación de fallos ignorados (caché del resultado de ignorar_ip, ignorar_propia_ip y ignorar_comando), sintaxis: 
        cache_ignorar = clave="<F-USER>@<ip-host>", max-count=100, max-time=5m
        ignorar_comando = if [ "<F-USER>" = "technical" ] && [ "<ip-host>" = "my-host.example.com" ]; then exit 0; fi;
                        exit 1
Esto almacenará en caché el resultado de ignorar_comando (no lo llamará repetidamente) durante 5 minutos (tiempo de caché) para un máximo de 100 entradas (tamaño de caché), utilizando valores sustituidos como "usuario@host" como claves de caché. Establecer la opción cache_ignorar a un valor vacío deshabilita la caché.
tiempo_ban
duración efectiva del bloqueo (en segundos o formato de abreviatura de tiempo).
tiempo_buscar
intervalo de tiempo (en segundos o formato de abreviatura de tiempo) antes de la hora actual en el que los fallos contarán para un bloqueo.
max_intentos
número de fallos que deben ocurrir en los últimos tiempo_buscar segundos para bloquear la IP.
backend
backend que se utilizará para detectar cambios en la ruta del registro.
Por defecto es "auto", que intentará "pyinotify", "systemd" antes de "polling". Cualquiera de estos puede ser especificado. "pyinotify" solo es válido en sistemas Linux con las bibliotecas Python "pyinotify".
usar_dns
usa DNS para resolver nombres de HOST que aparecen en los registros. Por defecto es "warn", que resolverá nombres de host a IPs, pero también registrará una advertencia. Si está utilizando DNS aquí, podría estar bloqueando las IPs incorrectas debido a la naturaleza asimétrica del DNS inverso (que la aplicación utiliza para escribir el nombre de dominio en el registro) en comparación con el DNS directo que fail2ban utiliza para resolver esto de nuevo a una IP (pero no necesariamente la misma). Idealmente, debería configurar sus aplicaciones para que registren una IP real. Esto se puede establecer en "yes" para evitar advertencias en el registro o "no" para deshabilitar la resolución DNS por completo (ignorando así las entradas donde se registra un nombre de host, no una IP).
prefregex
expresión regular (expresión regular de Python) para analizar una parte común que contiene cada mensaje (ver prefregex en la sección FILTER FILES para detalles).
failregex
expresión regular (expresión regular de Python) que se agregará a las expresiones regulares de fallo del filtro (ver failregex en la sección FILTER FILES para detalles). Si esto es útil para otros que usan su aplicación, comparta su expresión regular con los desarrolladores de fail2ban informando un problema (ver REPORTING BUGS a continuación).
ignoreregex
expresión regular que, si la línea de registro coincide, hará que Fail2Ban no considere esa línea. Esta línea se ignorará incluso si coincide con un failregex de la jaula o con alguno de sus filtros.
max_coincidencias
número máximo de líneas de registro coincidentes que la jaula mantendrá en memoria por ticket. Por defecto, es el mismo valor que max_intentos de la jaula (o el predeterminado). Esta opción también afecta a los valores resolubles a través de la etiqueta <matches> en las acciones.

Backends

Las opciones disponibles se enumeran a continuación.

pyinotify
requiere que pyinotify (un monitor de alteración de archivos) esté instalado. Si pyinotify no está instalado, Fail2ban usará auto.
polling
utiliza un algoritmo de sondeo que no requiere bibliotecas externas.
systemd
utiliza la biblioteca Python de systemd para acceder al journal de systemd. Especificar ruta_log no es válido para este backend y en su lugar utiliza journalmatch de la configuración del filtro asociado a las jaulas. Se pueden pasar varios indicadores específicos de systemd al backend, incluyendo journalpath y journalfiles, para establecer explícitamente la ruta a un directorio o conjunto de archivos. journalflags, que por defecto es 4 y excluye los archivos de sesión de usuario, se puede establecer para incluirlos con journalflags=1, consulte la documentación de python-systemd para otras configuraciones y más detalles. Ejemplos:
backend = systemd[journalpath=/run/log/journal/machine-1]
backend = systemd[journalfiles="/path/to/system.journal, /path/to/user.journal"]
backend = systemd[journalflags=1]

Acciones

Cada jaula se puede configurar con un solo filtro, pero puede tener múltiples acciones. Por defecto, el nombre de una acción es el nombre del archivo de acción, y en el caso de acciones de Python, la extensión del archivo ".py" se elimina.
