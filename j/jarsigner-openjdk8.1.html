VERIFICACIÓN DE ARCHIVOS JAR Una verificación exitosa de un archivo JAR ocurre cuando las firmas son válidas y ninguno de los archivos que estaban en el archivo JAR cuando se generaron las firmas ha cambiado desde entonces. La verificación de un archivo JAR implica los siguientes pasos: 1

. 
Verificar la firma del archivo .SF .

El archivo .SF de forma predeterminada incluye un encabezado que contiene un hash de todo el archivo de manifiesto. Cuando el encabezado está presente, la verificación puede comprobar si el hash en el encabezado coincide con el hash del archivo de manifiesto. Si hay una coincidencia, la verificación continúa con el siguiente paso.

Si no hay coincidencia, se requiere una verificación menos optimizada para asegurar que el hash en cada sección de información de archivo de origen en el archivo.SF es igual al hash de su sección correspondiente en el archivo de manifiesto. -verbose

Cuando la opción -verbose aparece en la línea de comandos, indica el modo detallado, que hace que jarsigner emita información adicional sobre el progreso de la firma o verificación del JAR.
-internalsf

En el pasado, el archivo .DSA (bloque de firma) generado al firmar un archivo JAR incluía una copia codificada completa del archivo .SF (archivo de firma) también generado. Este comportamiento ha sido modificado. Para reducir el tamaño general del archivo JAR de salida, el archivo .DSA por defecto ya no contiene una copia del archivo .SF. Si -internalsf aparece en la línea de comandos, entonces se utiliza el comportamiento anterior. Esta opción es útil para pruebas. En la práctica, no utilice la opción -internalsf porque incurre en una mayor sobrecarga.
-sectionsonly

Si la opción -sectionsonly aparece en la línea de comandos, entonces el archivo .SF (archivo de firma) generado al firmar un archivo JAR no incluye una cabecera que contenga un hash de todo el archivo manifest. Contiene solo la información y los hashes relacionados con cada archivo fuente individual incluido en el archivo JAR. Consulte Archivo de Firma.

Por defecto, esta cabecera se añade como optimización. Cuando la cabecera está presente, siempre que se verifica el archivo JAR, la verificación puede primero comprobar si el hash en la cabecera coincide con el hash de todo el archivo manifest. Cuando hay una coincidencia, la verificación procede al siguiente paso. Cuando no hay coincidencia, es necesario realizar una verificación menos optimizada de que el hash en cada sección de información de archivo fuente en el archivo .SF coincide con el hash de su sección correspondiente en el archivo manifest. Consulte Verificación de Archivos JAR.

La opción -sectionsonly se utiliza principalmente para pruebas. No debe usarse más que para pruebas porque su uso incurre en una mayor sobrecarga.

-protected

Los valores pueden ser true o false. Especifique true cuando una contraseña deba especificarse a través de una ruta de autenticación protegida, como un lector de PIN dedicado.
-providerClass nombre-clase-proveedor

Se utiliza para especificar el nombre del archivo maestro de clase del proveedor de servicios criptográficos cuando el proveedor de servicios no está listado en el archivo de propiedades de seguridad java.security.

Utilizado junto con la opción -providerArg RutaArchivoConfiguracion, las herramientas keytool y jarsigner instalan el proveedor dinámicamente y utilizan RutaArchivoConfiguracion para la ruta del archivo de configuración del token. El siguiente ejemplo muestra un comando para listar un almacén de claves PKCS #11 cuando el proveedor PKCS #11 de Oracle no estaba configurado en el archivo de propiedades de seguridad.

jarsigner -keystore NONE -storetype PKCS11 \
          -providerClass sun.security.pkcs11.SunPKCS11 \
          -providerArg /mi_dir1/mi_dir2/token.config \
          -list
-providerName nombreProveedor

Si se configuraron varios proveedores en el archivo de propiedades de seguridad java.security, entonces puede usar la opción -providerName para dirigirse a una instancia de proveedor específica. El argumento de esta opción es el nombre del proveedor.

Para el proveedor PKCS #11 de Oracle, nombreProveedor tiene el formato SunPKCS11-NombreToken, donde NombreToken es el sufijo de nombre con el que se ha configurado la instancia del proveedor, como se detalla en la tabla de atributos de configuración. Por ejemplo, el siguiente comando lista el contenido de la instancia del proveedor de almacén de claves PKCS #11 con el sufijo de nombre SmartCard:

jarsigner -keystore NONE -storetype PKCS11 \
        -providerName SunPKCS11-SmartCard \
        -list
-Jopcionjava

Pasa la cadena opcionjava especificada directamente al intérprete de Java. El comando jarsigner es un envoltorio alrededor del intérprete. Esta opción no debe contener espacios. Es útil para ajustar el entorno de ejecución o el uso de memoria. Para obtener una lista de posibles opciones del intérprete, escriba java -h o java -X en la línea de comandos.
-tsa url

Si -tsa http://example.tsa.url aparece en la línea de comandos al firmar un archivo JAR, entonces se genera una marca de tiempo para la firma. La URL, http://example.tsa.url, identifica la ubicación de la Autoridad de Sellado de Tiempo (TSA) y anula cualquier URL encontrada con la opción -tsacert. La opción -tsa no requiere que el certificado de clave pública de la TSA esté presente en el almacén de claves.

Para generar la marca de tiempo, jarsigner se comunica con la TSA utilizando el Protocolo de Marca de Tiempo (TSP) definido en la RFC 3161. Cuando tiene éxito, el token de marca de tiempo devuelto por la TSA se almacena con la firma en el archivo del bloque de firma.

-tsacert alias

Cuando -tsacert alias aparece en la línea de comandos al firmar un archivo JAR, se genera una marca de tiempo para la firma. El alias identifica el certificado de clave pública de la TSA en el almacén de claves que está en vigor. Se examina el certificado de la entrada para ver si tiene una extensión de Acceso a la Información del Sujeto que contiene una URL que identifica la ubicación de la TSA.

El certificado de clave pública de la TSA debe estar presente en el almacén de claves al usar la opción -tsacert.

-tsapolicyid idpolitica

Especifica el identificador de objeto (OID) que identifica el ID de política que se enviará al servidor TSA. Si esta opción no se especifica, no se envía ningún ID de política y el servidor TSA elegirá un ID de política predeterminado.

Los identificadores de objeto están definidos por X.696, que es un estándar del Sector de Normalización de Telecomunicaciones de la UIT (UIT-T). Estos identificadores son típicamente conjuntos de dígitos no negativos separados por puntos, como 1.2.3.4, por ejemplo.

-altsigner clase

Esta opción especifica un mecanismo de firma alternativo. El nombre de clase completamente calificado identifica un archivo de clase que extiende la clase abstracta com.sun.jarsigner.ContentSigner. La ruta a este archivo de clase se define mediante la opción -altsignerpath. Si se utiliza la opción -altsigner, entonces el comando jarsigner utiliza el mecanismo de firma proporcionado por la clase especificada. De lo contrario, el comando jarsigner utiliza su mecanismo de firma predeterminado.

Por ejemplo, para usar el mecanismo de firma proporcionado por una clase llamada com.sun.sun.jarsigner.AuthSigner, use la opción jarsigner -altsigner com.sun.jarsigner.AuthSigner.

-altsignerpath listarutasclase

Especifica la ruta al archivo de clase y a cualquier archivo JAR del que dependa. El nombre del archivo de clase se especifica con la opción -altsigner. Si el archivo de clase está en un archivo JAR, entonces esta opción especifica la ruta a ese archivo JAR.

Se puede especificar una ruta absoluta o una ruta relativa al directorio actual. Si listasrutasclase contiene varias rutas o archivos JAR, entonces deben estar separados por dos puntos (:) en Oracle Solaris y por punto y coma (;) en Windows. Esta opción no es necesaria cuando la clase ya está en la ruta de búsqueda.

El siguiente ejemplo muestra cómo especificar la ruta a un archivo JAR que contiene el archivo de clase. Se incluye el nombre del archivo JAR.

-altsignerpath /home/usuario/lib/authsigner.jar

El siguiente ejemplo muestra cómo especificar la ruta al archivo JAR que contiene el archivo de clase. Se omite el nombre del archivo JAR.

-altsignerpath /home/usuario/clases/com/sun/tools/jarsigner/
-strict

Durante el proceso de firma o verificación, el comando puede emitir mensajes de advertencia. Si especifica esta opción, el código de salida de la herramienta reflejará los mensajes de advertencia severos que este comando encontró. Consulte Errores y Advertencias.
-verbose subopciones

Para el proceso de verificación, la opción -verbose toma subopciones para determinar cuánta información se muestra. Si la opción -certs también se especifica, entonces el modo predeterminado (o la subopción all) muestra cada entrada mientras se procesa, y después de eso, la información del certificado para cada firmante del archivo JAR. Si se especifican las subopciones -certs y -verbose:grouped, entonces las entradas con la misma información del firmante se agrupan y se muestran juntas con su información de certificado. Si se especifican -certs y las subopciones -verbose:summary, entonces las entradas con la misma información del firmante se agrupan y se muestran juntas con su información de certificado. Los detalles de cada entrada se resumen y se muestran como una entrada (y más). Consulte Ejemplos.

ERRORES Y ADVERTENCIAS

Durante el proceso de firma o verificación, el comando jarsigner puede emitir varios errores o advertencias.

Si hay un fallo, el comando jarsigner sale con el código 1. Si no hay fallo, pero hay una o más advertencias severas, el comando jarsigner sale con el código 0 cuando la opción -strict *no* se especifica, o sale con el valor OR de los códigos de advertencia cuando se especifica -strict. Si no hay o

```nly informational warnings or no warning at all, the command always exits with code 0.

For example, if a certificate used to sign an entry is expired and has a KeyUsage extension that does not allow it to sign a file, the jarsigner command exits with code 12 (=4+8) when the -strict option is specified.

Note: Exit codes are reused because only the values from 0 to 255 are legal on Unix-based operating systems.

The following sections describes the names, codes, and descriptions of the errors and warnings that the jarsigner command can issue.

FAILURE

Reasons why the jarsigner command fails include (but are not limited to) a command line parsing error, the inability to find a keypair to sign the JAR file, or the verification of a signed JAR fails.

failure
Code 1. The signing or verifying fails.

SEVERE WARNINGS

Note: Severe warnings are reported as errors if you specify the -strict option.

Reasons why the jarsigner command issues a severe warning include the certificate used to sign the JAR file has an error or the signed JAR file has other problems.

hasExpiredCert
Code 4. This jar contains entries whose signer certificate has expired.
notYetValidCert
Code 4. This jar contains entries whose signer certificate is not yet valid.
chainNotValidated
Code 4. This jar contains entries whose certificate chain cannot be correctly validated.
badKeyUsage
Code 8. This jar contains entries whose signer certificate's KeyUsage extension doesn't allow code signing.
badExtendedKeyUsage
Code 8. This jar contains entries whose signer certificate's ExtendedKeyUsage extension doesn't allow code signing.

Code 8. This jar contains entries whose signer certificate's NetscapeCertType extension doesn't allow code signing.

Code 16. This jar contains unsigned entries which have not been integrity-checked.
notSignedByAlias
Code 32. This jar contains signed entries which are not signed by the specified alias(es).
aliasNotInStore
Code 32. This jar contains signed entries that are not signed by alias in this keystore.

INFORMATIONAL WARNINGS

Informational warnings include those that are not errors but regarded as bad practice. They do not have a code.

hasExpiringCert
This jar contains entries whose signer certificate will expire within six months.
noTimestamp
This jar contains signatures that does not include a timestamp. Without a timestamp, users may not be able to validate this JAR file after the signer certificate's expiration date (YYYY-MM-DD) or after any future revocation date.

EXAMPLES

SIGN A JAR FILE

Use the following command to sign bundle.jar with the private key of a user whose keystore alias is jane in a keystore named mystore in the working directory and name the signed JAR file sbundle.jar:

jarsigner -keystore /working/mystore
    -storepass <keystore password>
    -keypass <private key password>
    -signedjar sbundle.jar bundle.jar jane

There is no -sigfile specified in the previous command so the generated .SF and .DSA files to be placed in the signed JAR file have default names based on the alias name. They are named JANE.SF and JANE.DSA.

If you want to be prompted for the store password and the private key password, then you could shorten the previous command to the following:

jarsigner -keystore /working/mystore
    -signedjar sbundle.jar bundle.jar jane

If the keystore is the default keystore (.keystore in your home directory), then you do not need to specify a keystore, as follows:

jarsigner -signedjar sbundle.jar bundle.jar jane

If you want the signed JAR file to overwrite the input JAR file (bundle.jar), then you do not need to specify a -signedjar option, as follows:

jarsigner bundle.jar jane

VERIFY A SIGNED JAR FILE

To verify a signed JAR file to ensure that the signature is valid and the JAR file was not been tampered with, use a command such as the following:

jarsigner -verify sbundle.jar

When the verification is successful, jar verified is displayed. Otherwise, an error message is displayed. You can get more information when you use the -verbose option. A sample use of jarsigner with the-verbose option follows:

jarsigner -verify -verbose sbundle.jar

          1013 Fri Sep 26 16:22:10 PDT 1997 META-INF/JANE.DSA
    smk   2752 Fri Sep 26 16:12:30 PDT 1997 AclEx.class
    smk    849 Fri Sep 26 16:12:46 PDT 1997 test.class

VERIFICATION WITH CERTIFICATE INFORMATION

If you specify the -certs option with the -verify and -verbose options, then the output includes certificate information for each signer of the JAR file. The information includes the certificate type, the signer distinguished name information (when it is an X.509 certificate), and in parentheses, the keystore alias for the signer when the public key certificate in the JAR file matches the one in a keystore entry, for example:

jarsigner -keystore /working/mystore -verify -verbose -certs myTest.jar
           198 Fri Sep 26 16:14:06 PDT 1997 META-INF/MANIFEST.MF
           199 Fri Sep 26 16:22:10 PDT 1997 META-INF/JANE.SF
          1013 Fri Sep 26 16:22:10 PDT 1997 META-INF/JANE.DSA
           208 Fri Sep 26 16:23:30 PDT 1997 META-INF/JAVATEST.SF
          1087 Fri Sep 26 16:23:30 PDT 1997 META-INF/JAVATEST.DSA
    smk   2752 Fri Sep 26 16:12:30 PDT 1997 Tst.class
      X.509, CN=Test Group, OU=Java Software, O=Oracle, L=CUP, S=CA, C=US (javatest)
      X.509, CN=Jane Smith, OU=Java Software, O=Oracle, L=cup, S=ca, C=us (jane)
      s = signature was verified
      m = entry is listed in manifest
      k = at least one certificate was found in keystore
    jar verified.

If the certificate for a signer is not an X.509 certificate, then there is no distinguished name information. In that case, just the certificate type and the alias are shown. For example, if the certificate is a PGP certificate, and the alias is bob, then you would get: PGP, (bob).
