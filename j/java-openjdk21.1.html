USANDO LA VARIABLE DE ENTORNO DEL LANZADOR JDK_JAVA_OPTION

S

JDK_JAVA_OPTIONS antepone su contenido a las opciones analizadas desde la línea de comandos. El contenido de la variable de entorno JDK_JAVA_OPTIONS es una lista de argumentos separados por caracteres en blanco (según lo determinado por isspace()). Estos se anteponen a los argumentos de la línea de comandos pasados al lanzador de java. El requisito de codificación para la variable de entorno es el mismo que el de la línea de comandos de java en el sistema. El contenido de la variable de entorno JDK_JAVA_OPTIONS se trata de la misma manera que lo especificado en la línea de

comandos.

Se pueden usar comillas simples (') o dobles (") para encerrar argumentos que contienen caracteres en blanco. Todo el contenido entre la comilla de apertura y la primera comilla de cierre coincidente se conserva simplemente eliminando el par de comillas. En caso de que no se encuentre una comilla coincidente, el lanzador abortará con un mensaje de error. Los archivos @ son compatibles tal como se especifican en la línea de comandos. Sin embargo, como en los archivos @, el uso de un comodín no es compatible. Para mitigar el posible uso indebido del comportamiento de JDK_JAVA_OPTIONS, las opciones que especifican la clase principal (como -jar) o que hacen que el lanzador de java salga sin ejecutar la clase principal (como -h) no están permitidas en la variable de entorno. Si alguna de estas opciones aparece en la variable de entorno, el lanzador abortará con un mensaje de error. Cuando JDK_JAVA_OPTIONS está establecido, el lanzador imprime un mensaje en stderr como

recordatorio.

Ejemplo

: 

$ export JDK_JAVA_OPTIONS='-g @file1 -Dprop=value @file2 -Dws.prop="white spaces"'
$ java -Xint @file3

es equivalente a la línea de

comandos: 

java -g @file1 -Dprop=value @file2 -Dws.prop="white spaces" -Xint @file3

Reduce el uso de señales del sistema operativo por parte de la JVM. Los "shutdown hooks" (ganchos de apagado) permiten el apagado ordenado de una aplicación Java ejecutando código de limpieza del usuario (como cerrar conexiones de bases de datos) al apagar, incluso si la JVM termina de forma abrupta.
•
No Windows:
•
La JVM captura señales para implementar los "shutdown hooks" en caso de terminación inesperada. La JVM utiliza SIGHUP, SIGINT y SIGTERM para iniciar la ejecución de los "shutdown hooks".
•
Las aplicaciones que integran la JVM con frecuencia necesitan interceptar señales como SIGINT o SIGTERM, lo que puede interferir con los manejadores de señales de la JVM. Windows:
•

•

•

Establece un punto de interrupción al depurar la JVM para detenerse al inicio de la compilación del método especificado.
compileonly
Excluye todos los métodos de la compilación excepto el método especificado. Como alternativa, puede utilizar la opción -XX:CompileOnly, que le permite especificar varios métodos.
dontinline
Evita la inclusión en línea del método especificado.
exclude
Excluye el método especificado de la compilación.
help
Imprime un mensaje de ayuda para la opción -XX:CompileCommand.
inline
Intenta incluir en línea el método especificado.
log
Excluye el registro de compilación (con la opción -XX:+LogCompilation) para todos los métodos excepto el método especificado. Por defecto, el registro se realiza para todos los métodos compilados.
option
Pasa una opción de compilación JIT al método especificado en lugar del último argumento (opción). La opción de compilación se establece al final, después del nombre del método. Por ejemplo, para habilitar la opción BlockLayoutByFrequency para el método append() de la clase StringBuffer, utilice lo siguiente:

-XX:CompileCommand=option,java/lang/StringBuffer.append,BlockLayoutByFrequency

Puede especificar varias opciones de compilación, separadas por comas o espacios.

print
Imprime el código ensamblador generado después de la compilación del método especificado.
quiet
Instruye para no imprimir los comandos de compilación. Por defecto, los comandos que especifica con la opción -XX:CompileCommand se imprimen; por ejemplo, si excluye de la compilación el método indexOf() de la clase String, se imprimirá lo siguiente en la salida estándar:

CompilerOracle: exclude java/lang/String.indexOf

Puede suprimir esto especificando la opción -XX:CompileCommand=quiet antes que otras opciones -XX:CompileCommand.

-XX:CompileCommandFile=nombre_archivo
Establece el archivo desde el que se leen los comandos del compilador JIT. Por defecto, el archivo .hotspot_compiler se utiliza para almacenar los comandos realizados por el compilador JIT.

Cada línea en el archivo de comandos representa un comando, un nombre de clase y un nombre de método para los que se utiliza el comando. Por ejemplo, esta línea imprime el código ensamblador para el método toString() de la clase String:

print java/lang/String toString

Si está utilizando comandos para que el compilador JIT los ejecute en métodos, consulte la opción -XX:CompileCommand.

Especifique cada método con el nombre completo de la clase (incluyendo los paquetes y subpaquetes). Por ejemplo, para compilar solo el método length() de la clase String y el método size() de la clase List, utilice lo siguiente:

-XX:CompileOnly=java/lang/String.length,java/util/List.size

Tenga en cuenta que se especifica el nombre completo de la clase, incluyendo todos los paquetes y subpaquetes separados por una barra (/). -XX:CompileOnly=java.lang.String::length,java.util.List::size

La opción CompileThresholdScaling tiene un valor de punto flotante entre 0 y +Inf y escala los umbrales correspondientes al modo de operación actual (tanto con niveles como sin niveles). Establecer CompileThresholdScaling a un valor inferior a 1.0 da como resultado una compilación más temprana, mientras que los valores superiores a 1.0 retrasan la compilación. JVM OPTIONS

These java options control the behavior of the Java HotSpot Virtual Machine.

-XX:HeapDumpPath=path
Specifies the path and file name of the heap dump file. If this option is not specified, then the heap dump is written to the current directory. The heap dump file is named heapdump<pid>.hprof, where <pid> is the process identifier of the Java VM. Use the jmap command to create a heap dump file. The heap dump is created in the same directory as the executable that is running the Java VM.
Windows: The following example shows how to set the heap dump file to C:/log/java/java_heapdump.log:

-XX:HeapDumpPath=C:/log/java/java_heapdump.log

-XX:LogFile=path
Sets the path and file name where log data is written. By default, the file is created in the current working directory, and it's named hotspot.log.
•
Non-Windows: The following example shows how to set the log file to /var/log/java/hotspot.log:

-XX:LogFile=/var/log/java/hotspot.log

•
Windows: The following example shows how to set the log file to C:/log/java/hotspot.log:

-XX:LogFile=C:/log/java/hotspot.log

-XX:+PrintClassHistogram
Enables printing of a class instance histogram after one of the following events:
•
Non-Windows: Control+\ (SIGQUIT)
•
Windows: Control+C (SIGTERM)

By default, this option is disabled.

Setting this option is equivalent to running the jmap -histo command, or the jcmd pid GC.class_histogram command, where pid is the current Java process identifier.

-XX:+PrintConcurrentLocks
Enables printing of java.util.concurrent locks after one of the following events:
•
Non-Windows: Control+\ (SIGQUIT)
•
Windows: Control+C (SIGTERM)

By default, this option is disabled.

Setting this option is equivalent to running the jstack -l command or the jcmd pid Thread.print -l command, where pid is the current Java process identifier.

-XX:+PrintFlagsRanges
Prints the range specified and allows automatic testing of the values. See Validate Java Virtual Machine Flag Arguments.
-XX:+PerfDataSaveToFile
If enabled, saves jstat binary data when the Java application exits. This binary data is saved in a file named hsperfdata_pid, where pid is the process identifier of the Java application that you ran. Use the jstat command to display the performance data contained in this file as follows:

jstat -class file:///path/hsperfdata_pid

jstat -gc file:///path/hsperfdata_pid

-XX:+UsePerfData
Enables the perfdata feature. This option is enabled by default to allow JVM monitoring and performance testing. Disabling it suppresses the creation of the hsperfdata_userid directories. To disable the perfdata feature, specify -XX:-UsePerfData.

OPCIONES AVANZADAS DE RECOLECCIÓN DE BASURA PARA JAVA

Estas opciones de java controlan cómo se realiza la recolección de basura (GC) en la VM de Java HotSpot.

-XX:+AggressiveHeap
Habilita la optimización del heap de Java. Esto establece varios parámetros para que sean óptimos para trabajos de larga duración con asignación intensiva de memoria, basándose en la configuración del ordenador (RAM y CPU). Por defecto, la opción está deshabilitada y los tamaños del heap se configuran de forma menos agresiva.
-XX:+AlwaysPreTouch
Solicita a la VM que toque cada página del heap de Java después de solicitarla al sistema operativo y antes de entregar memoria a la aplicación. Por defecto, esta opción está deshabilitada y todas las páginas se confirman a medida que la aplicación utiliza el espacio del heap.
-XX:ConcGCThreads=threads
Establece el número de hilos utilizados para la GC concurrente. Establece threads en aproximadamente 1/4 del número de hilos de recolección de basura paralela. El valor predeterminado depende del número de CPUs disponibles para la JVM.

Por ejemplo, para establecer el número de hilos para GC concurrente en 2, especifique la siguiente opción:

-XX:ConcGCThreads=2

-XX:+DisableExplicitGC
Habilita la opción que deshabilita el procesamiento de llamadas al método System.gc(). Esta opción está deshabilitada por defecto, lo que significa que se procesan las llamadas a System.gc(). Si el procesamiento de llamadas a System.gc() está deshabilitado, la JVM todavía realiza GC cuando es necesario.
-XX:+ExplicitGCInvokesConcurrent
Habilita la invocación de GC concurrente mediante la solicitud System.gc(). Esta opción está deshabilitada por defecto y solo se puede habilitar con la opción -XX:+UseG1GC.
-XX:G1AdaptiveIHOPNumInitialSamples=number
Cuando -XX:UseAdaptiveIHOP está habilitado, esta opción establece el número de ciclos de marcado completados utilizados para recopilar muestras hasta que G1 determina adaptativamente el valor óptimo de -XX:InitiatingHeapOccupancyPercent. Antes, G1 utiliza directamente el valor de -XX:InitiatingHeapOccupancyPercent para este propósito. El valor predeterminado es 3.
-XX:G1HeapRegionSize=size
Establece el tamaño de las regiones en las que se subdivide el heap de Java cuando se utiliza el colector garbage-first (G1). El valor es una potencia de 2 y puede oscilar entre 1 MB y 32 MB. El tamaño de región predeterminado se determina de forma ergonómica basándose en el tamaño del heap con un objetivo de aproximadamente 2048 regiones.

El siguiente ejemplo establece el tamaño de las subdivisiones en 16 MB:

-XX:G1HeapRegionSize=16m

-XX:G1HeapWastePercent=percent
Establece el porcentaje del heap que está dispuesto a desperdiciar. La VM de Java HotSpot no inicia el ciclo de recolección de basura mixta cuando el porcentaje recuperable es inferior al porcentaje de desperdicio del heap. El valor predeterminado es 5 por ciento.
-XX:G1MaxNewSizePercent=percent
Establece el porcentaje del tamaño del heap que se utilizará como máximo para el tamaño de la generación joven. El valor predeterminado es el 60 por ciento de su heap de Java.

Esta es una bandera experimental. Esta configuración reemplaza la configuración -XX:DefaultMaxNewGenPercent.

-XX:G1MixedGCCountTarget=number
Establece el número objetivo de recolecciones de basura mixta después de un ciclo de marcado para recolectar regiones antiguas con como máximo G1MixedGCLIveThresholdPercent de datos vivos. El valor predeterminado es 8 recolecciones de basura mixta. El objetivo de las recolecciones mixtas es estar dentro de este número objetivo.
-XX:G1MixedGCLiveThresholdPercent=percent
Establece el umbral de ocupación para que una región antigua se incluya en un ciclo de recolección de basura mixta. La ocupación predeterminada es 85 por ciento.

Esta es una bandera experimental. Esta configuración reemplaza la configuración -XX:G1OldCSetRegionLiveThresholdPercent.

-XX:G1NewSizePercent=percent
Establece el porcentaje del heap que se utilizará como mínimo para el tamaño de la generación joven. El valor predeterminado es el 5 por ciento de su heap de Java.

Esta es una bandera experimental. Esta configuración reemplaza la configuración -XX:DefaultMinNewGenPercent.

-XX:G1OldCSetRegionThresholdPercent=percent
Establece un límite superior en el número de regiones antiguas que se recolectarán durante un ciclo de recolección de basura mixta. El valor predeterminado es el 10 por ciento del heap de Java.
-XX:G1ReservePercent=percent
Establece el porcentaje del heap (0 a 50) que se reserva como un techo falso para reducir la posibilidad de fallo de promoción para el colector G1. Al aumentar o disminuir el porcentaje, asegúrese de ajustar el heap total de Java en la misma cantidad. Por defecto, esta opción se establece en 10%.

El siguiente ejemplo establece el heap reservado en un 20%:

-XX:G1ReservePercent=20

-XX:+G1UseAdaptiveIHOP
Controla el cálculo adaptativo de la ocupación de la generación antigua para iniciar el trabajo de fondo preparándose para una recolección de la generación antigua. Si está habilitado, G1 utiliza -XX:InitiatingHeapOccupancyPercent durante las primeras veces, según lo especificado por el valor de -XX:G1AdaptiveIHOPNumInitialSamples, y después de eso, calcula adaptativamente un nuevo valor óptimo para la ocupación inicial automáticamente. De lo contrario, el proceso de recolección de la generación antigua siempre comienza en la ocupación de la generación antigua determinada por -XX:InitiatingHeapOccupancyPercent.

El valor predeterminado está habilitado.

-XX:InitialHeapSize=size
Establece el tamaño inicial (en bytes) del pool de asignación de memoria. Este valor debe ser 0, o un múltiplo de 1024 y mayor que 1 MB. Agregue la letra k o K para indicar kilobytes, m o M para indicar megabytes, o g o G para indicar gigabytes. El valor predeterminado se selecciona en tiempo de ejecución según la configuración del sistema.

Los siguientes ejemplos muestran cómo establecer el tamaño de la memoria asignada a 6 MB utilizando varias unidades:


-XX:InitialHeapSize=6291456
-XX:InitialHeapSize=6144k
-XX:InitialHeapSize=6m

Si establece esta opción en 0, entonces el tamaño inicial se establece como la suma de los tamaños asignados para la generación antigua y la generación joven. El tamaño del heap para la generación joven se puede establecer utilizando la opción -XX:NewSize. Tenga en cuenta que la opción -Xms establece tanto el tamaño mínimo como el tamaño inicial del heap. Si -Xms aparece después de -XX:InitialHeapSize en la línea de comandos, entonces el tamaño inicial del heap se establece en el valor especificado con -Xms.

-XX:InitialRAMPercentage=percent
Establece la cantidad inicial de memoria que la JVM utilizará para el heap de Java antes de aplicar heurísticas ergonómicas como un porcentaje de la cantidad máxima determinada según se describe en la opción -XX:MaxRAM. El valor predeterminado es 1.5625 por ciento.

El siguiente ejemplo muestra cómo establecer el porcentaje de la cantidad inicial de memoria utilizada para el heap de Java:

-XX:InitialRAMPercentage=5

-XX:InitialSurvivorRatio=ratio
Establece la proporción inicial del espacio de supervivencia utilizado por el colector de basura de rendimiento (que está habilitado por -XX:+UseParall
(opción elGC). El tamaño adaptativo está habilitado por defecto con el recolector de basura de rendimiento utilizando la opción `-XX:+UseParallelGC`, y el espacio de supervivencia se redimensiona según el comportamiento de la aplicación, comenzando con el valor inicial. Si el tamaño adaptativo está deshabilitado (usando la opción `-XX:-UseAdaptiveSizePolicy`), entonces la opción `-XX:SurvivorRatio` debe usarse para establecer el tamaño del espacio de supervivencia durante toda la ejecución de la aplicación.

La siguiente fórmula se puede usar para calcular el tamaño inicial del espacio de supervivencia (S) basado en el tamaño de la generación joven (Y) y la relación inicial del espacio de supervivencia (R):

S=Y/(R+2)

El 2 en la ecuación denota dos espacios de supervivencia. Cuanto mayor sea el valor especificado como relación inicial del espacio de supervivencia, menor será el tamaño inicial del espacio de supervivencia.

Por defecto, la relación inicial del espacio de supervivencia se establece en 8. Si se utiliza el valor por defecto para el tamaño del espacio de la generación joven (2 MB), entonces el tamaño inicial del espacio de supervivencia es de 0.2 MB.

El siguiente ejemplo muestra cómo establecer la relación inicial del espacio de supervivencia a 4:

-XX:InitialSurvivorRatio=4

-XX:InitiatingHeapOccupancyPercent=porcentaje
Establece el porcentaje de ocupación de la generación vieja (0 a 100) en el que comenzar los primeros ciclos de marcado concurrentes para el recolector G1.

Por defecto, el valor inicial se establece en 45%. Un valor de 0 implica ciclos de GC concurrentes ininterrumpidos desde el principio hasta que G1 establezca adaptativamente este valor.

Ver también las opciones `-XX:G1UseAdaptiveIHOP` y `-XX:G1AdaptiveIHOPNumInitialSamples`.

El siguiente ejemplo muestra cómo establecer la ocupación inicial del heap al 75%:

-XX:InitiatingHeapOccupancyPercent=75

-XX:MaxGCPauseMillis=tiempo
Establece un objetivo para el tiempo máximo de pausa de GC (en milisegundos). Este es un objetivo flexible, y la JVM hará todo lo posible para alcanzarlo. El valor especificado no se adapta al tamaño de tu heap. Por defecto, para G1 el objetivo de tiempo máximo de pausa es de 200 milisegundos. Los otros recolectores generacionales no utilizan un objetivo de tiempo de pausa por defecto.

El siguiente ejemplo muestra cómo establecer el tiempo máximo de pausa objetivo a 500 ms:

-XX:MaxGCPauseMillis=500

Añade la letra k o K para indicar kilobytes, m o M para indicar megabytes, o g o G para indicar gigabytes. El valor por defecto se selecciona en tiempo de ejecución basándose en la configuración del sistema. -XX:MaxHeapSize=80m

-XX:MaxHeapFreeRatio=porcentaje

Puede acortar o simplificar el comando java utilizando archivos de argumentos @ para especificar uno o más archivos de texto que contengan argumentos, como opciones y nombres de clase, que se pasan al comando java. Esto le permite crear comandos java de cualquier longitud en cualquier sistema operativo.

En la línea de comandos, use el prefijo arroba (@) para identificar un archivo de argumentos que contiene opciones y nombres de clase de java. Cuando el comando java encuentra un archivo que comienza con arroba (@), expande el contenido de ese archivo en una lista de argumentos tal como se especificarían en la línea de comandos.

El lanzador java expande el contenido del archivo de argumentos hasta que encuentra la opción --disable-@files. Puede usar la opción --disable-@files en cualquier lugar de la línea de comandos, incluso en un archivo de argumentos, para detener la expansión de archivos de argumentos @.

Los siguientes elementos describen la sintaxis de los archivos de argumentos de java:

•
El archivo de argumentos debe contener solo caracteres ASCII o caracteres en la codificación predeterminada del sistema que sea compatible con ASCII, como UTF-8.
•
El tamaño del archivo de argumentos no debe exceder MAXINT (2,147,483,647) bytes.
•
El lanzador no expande comodines presentes dentro de un archivo de argumentos.
•
Use espacios en blanco o caracteres de nueva línea para separar los argumentos incluidos en el archivo.
•
El espacio en blanco incluye un carácter de espacio en blanco, \t, \n, \r y \f.

VALIDAR LOS ARGUMENTOS DE LAS OPCIONES DE LA MÁQUINA VIRTUAL JAVA

Se utilizan los valores proporcionados a todas las opciones de línea de comandos de la Máquina Virtual Java (JVM) para la validación y, si el valor de entrada es inválido o está fuera de rango, se mostrará un mensaje de error apropiado.

Ya sea que se establezcan ergonómicamente, en una línea de comandos, mediante una herramienta de entrada o a través de las API (por ejemplo, clases contenidas en el paquete java.lang.management), se validan los valores proporcionados a todas las opciones de línea de comandos de la Máquina Virtual Java (JVM). La ergonomía se describe en la Guía de optimización de la recolección de basura de la Máquina Virtual HotSpot de la Plataforma Java, Edición Estándar.

Los rangos y las restricciones se validan ya sea cuando se establecen todos los valores de las opciones durante la inicialización de la JVM o cuando se cambia el valor de una opción durante el tiempo de ejecución (por ejemplo, utilizando la herramienta jcmd). La JVM se termina si un valor viola la verificación de rango o restricción y se imprime un mensaje de error apropiado en el flujo de error.

Por ejemplo, si una opción viola una verificación de rango o restricción, la JVM sale con un error:


java -XX:AllocatePrefetchStyle=5 -version
intx AllocatePrefetchStyle=5 is outside the allowed range [ 0 ... 3 ]
Improperly specified VM option 'AllocatePrefetchStyle=5'
Error: Could not create the Java Virtual Machine.
Error: A fatal exception has occurred. Program will exit.

La opción -XX:+PrintFlagsRanges imprime el rango de todas las opciones. Esta opción permite la prueba automática de las opciones mediante los valores proporcionados por los rangos. Para las opciones que tienen rangos especificados, el tipo, el nombre y el rango real se imprimen en la salida.

Por ejemplo,


intx   ThreadStackSize [ 0 ... 9007199254740987 ] {pd product}

Para las opciones que no tienen el rango especificado, los valores no se muestran en la impresión. Por ejemplo:


size_t NewSize         [   ...                  ] {product}

Esto ayuda a identificar las opciones que necesitan ser implementadas. El marco de prueba automática puede omitir aquellas opciones que no tienen valores y no están implementadas.

PÁGINAS GRANDES

Se utilizan páginas grandes, también conocidas como páginas enormes, como páginas de memoria que son significativamente más grandes que el tamaño de página de memoria estándar (que varía según el procesador y el sistema operativo). Las páginas grandes optimizan las Tablas de Búfer de Traducción del procesador.

Una Tabla de Búfer de Traducción (TLB) es una caché de traducción de páginas que contiene las traducciones de direcciones virtuales a físicas utilizadas más recientemente. Una TLB es un recurso escaso del sistema. Una fallo de TLB puede ser costoso porque el procesador debe leer de la tabla de páginas jerárquica, lo que puede requerir múltiples accesos a memoria. Al utilizar un tamaño de página de memoria más grande, una sola entrada de TLB puede representar un rango de memoria mayor. Esto resulta en menos presión sobre una TLB, y las aplicaciones con uso intensivo de memoria pueden tener un mejor rendimiento.

Sin embargo, el uso de páginas grandes puede afectar negativamente el rendimiento del sistema. Por ejemplo, cuando una gran cantidad de memoria es fijada por una aplicación, puede crear una escasez de memoria regular y provocar paginación excesiva en otras aplicaciones y ralentizar todo el sistema. Además, un sistema que ha estado en funcionamiento durante mucho tiempo podría producir fragmentación excesiva, lo que podría imposibilitar la reserva de suficiente memoria de páginas grandes. Cuando esto sucede, el SO o la JVM revierten al uso de páginas regulares.

Linux y Windows admiten páginas grandes.

Soporte de Páginas Grandes para Linux

Linux admite páginas grandes desde la versión 2.6. Para verificar si su entorno admite páginas grandes, intente lo siguiente:


# cat /proc/meminfo | grep Huge
HugePages_Total: 0
HugePages_Free: 0
...
Hugepagesize: 2048 kB

Si la salida contiene elementos prefijados con "Huge", entonces su sistema admite páginas grandes. Los valores pueden variar según el entorno. El campo Hugepagesize muestra el tamaño de página grande predeterminado en su entorno, y los otros campos muestran detalles para páginas grandes de este tamaño. Los kernels más nuevos admiten múltiples tamaños de página grandes. Para listar los tamaños de página admitidos, ejecute esto:


# ls /sys/kernel/mm/hugepages/
hugepages-1048576kB  hugepages-2048kB

El entorno anterior admite páginas grandes de 2 MB y 1 GB, pero deben configurarse para que la JVM pueda usarlas. Al usar páginas grandes y no habilitar páginas grandes transparentes (opción -XX:+UseTransparentHugePages), el número de páginas grandes debe ser preasignado. Por ejemplo, para habilitar 8 GB de memoria para ser respaldada por páginas grandes de 2 MB, inicie sesión como root y ejecute:

Creación de archivo de archivo dinámico de CDS con -XX:+AutoCreateSharedArchiv

e

-XX:+AutoCreateSharedArchive es una forma más conveniente de crear/usar archivos de CDS. A diferencia de los métodos de creación manual de archivos de CDS descritos en la sección anterior, con -XX:+AutoCreateSharedArchive, ya no es necesario tener una ejecución de prueba separada. En su lugar, siempre puede ejecutar la aplicación con el mismo comando de línea y disfrutar automáticamente de los beneficios de

CDS.

java -XX:+AutoCreateSharedArch

ive -XX:SharedArchiveFile=hel
lo.jsa -cp hello.jar Hello

Si el archivo especificado existe y fue creado por la misma versión del JDK, entonces se cargará como un archivo dinámico; de lo contrario, se ignora al inicio de la

VM.

Al salir de la VM, si el archivo especificado no existe, se creará. Si existe pero fue creado con una versión diferente (pero posterior a JDK 19) del JDK, entonces será reemplazado. En ambos casos el archivo estará listo para ser cargado la próxima vez que se lance la JVM con la misma línea de

comando.

Si el archivo especificado existe pero fue creado por una versión del JDK anterior a JDK 19, entonces será ignorado: no se carga al inicio, ni se reemplaza al

salir.

Los desarrolladores deben tener en cuenta que el contenido del archivo de CDS es específico para cada compilación del JDK. Por lo tanto, si cambi

a a una compilación diferente del JDK, -XX:+AutoCreateSharedArchive recreará automáticamente el archivo para que coincida con el JDK. Si tiene
la intención de usar esta función con un archivo existente, debe asegurarse de que el archivo sea creado por al menos la versión 19 del JDK.

Restricciones en la ruta de clases y la ruta de

módulos
•
Ni la ruta de clases (-classpath y -Xbootclasspath/a) ni la ruta de módulos (--module-path) pueden contener directorios no
vacíos.
•
Solo se admiten archivos JAR modulares en --module-path. No se admiten módulos descomprimidos (exploded modules)
.
•
La ruta de clases utilizada en el momento de la creación del archivo debe ser la misma que (o un prefijo de) la ruta de clases utilizada en tiempo de ejecución. (No existe tal requisito para la ruta de módulos.
)
•
El archivo de CDS no se puede cargar si algún archivo JAR en la ruta de clases o la ruta de módulos se modifica después de que se genera el
archivo.
•
Si se especifica alguna de las opciones de la VM --upgrade-module-pa
th, --patch-module o --limit-modules, CDS se deshabilita. Est
o significa que la JVM se ejecutará sin cargar ningún archivo
de CDS. Además, si intenta crear un archivo de CDS con alguna
de estas 3 opciones especificadas, la JVM informará un error.
