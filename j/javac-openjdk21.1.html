NOMBRE

javac - lee declaraciones de Java y las compila en archivos de clase

SINOPSIS

javac [opciones] [archivos-fuente-o-nombres-de-clase]

opciones
Opciones de línea de comandos.
archivos-fuente-o-nombres-de-clase
Archivos fuente a compilar (por ejemplo, Shape.java) o los nombres de clases previamente compiladas para ser procesadas por anotaciones (por ejemplo, geometry.MyShape).

DESCRIPCIÓN

El comando javac lee archivos fuente que contienen declaraciones de módulos, paquetes y tipos escritas en el lenguaje de programación Java, y las compila en archivos de clase que se ejecutan en la Máquina Virtual Java.

El comando javac también puede procesar anotaciones en archivos y clases fuente de Java.

Los archivos fuente deben tener la extensión de nombre de archivo .java. Los archivos de clase tienen la extensión de nombre de archivo .class. Tanto los archivos fuente como los de clase normalmente tienen nombres de archivo que identifican su contenido. Por ejemplo, una clase llamada Shape se declararía en un archivo fuente llamado Shape.java y se compilaría en un archivo de clase llamado Shape.class.

Hay dos formas de especificar archivos fuente a javac:

•
Para un número pequeño de archivos fuente, puedes listar sus nombres de archivo en la línea de comandos.
•
Para un gran número de archivos fuente, puedes usar la opción @nombre_archivo en la línea de comandos para especificar un archivo de argumentos que liste sus nombres de archivo. Consulte Opciones Estándar para ver una descripción de la opción y Archivos de Argumentos de Línea de Comandos para una descripción de los archivos de argumentos de javac.

El orden de los archivos fuente especificados en la línea de comandos o en un archivo de argumentos no es importante. javac compilará los archivos juntos, como un grupo, y resolverá automáticamente cualquier dependencia entre las declaraciones en los diversos archivos fuente.

javac espera que los archivos fuente estén organizados en una o más jerarquías de directorios en el sistema de archivos, descritas en Organización del Código Fuente.

Para compilar un archivo fuente, javac necesita encontrar la declaración de cada clase o interfaz que sea utilizada, extendida o implementada por el código en el archivo fuente. Esto permite a javac verificar que el código tiene derecho a acceder a esas clases e interfaces. En lugar de especificar explícitamente los archivos fuente de esas clases e interfaces, puedes usar opciones de línea de comandos para indicarle a javac dónde buscar sus archivos fuente. Si has compilado esos archivos fuente previamente, puedes usar opciones para indicarle a javac dónde buscar los archivos de clase correspondientes. Las opciones, que todas tienen nombres que terminan en "path", se describen en Opciones Estándar y se detallan más en Configuración de una Compilación y Búsqueda de Declaraciones de Módulos, Paquetes y Tipos.

Por defecto, javac compila cada archivo fuente a un archivo de clase en el mismo directorio que el archivo fuente. Sin embargo, se recomienda especificar un directorio de destino separado con la opción -d.

Las opciones de línea de comandos y las variables de entorno también controlan cómo javac realiza diversas tareas:

•
Compilar código para ejecutarse en versiones anteriores de JDK.
•
Compilar código para ejecutarse bajo un depurador.
•
Verificar problemas de estilo en el código fuente de Java.
•
Verificar problemas en comentarios javadoc (/** ... */).
•
Procesar anotaciones en archivos y clases fuente.
•
Actualizar y parchear módulos en el entorno de compilación.

javac admite Compilación para Versiones Anteriores de la Plataforma y también se puede invocar desde código Java usando una de varias APIs

OPCIONES

javac proporciona opciones estándar y opciones adicionales que son no estándar o para uso avanzado.

Algunas opciones toman uno o más argumentos. Si un argumento contiene espacios u otros caracteres de espacio en blanco, el valor debe ser citado de acuerdo con las convenciones del entorno que se utiliza para invocar javac. Si la opción comienza con un guion simple (-), el argumento debe seguir directamente el nombre de la opción, o estar separado por dos puntos (:) o espacio en blanco, dependiendo de la opción. Si la opción comienza con un doble guion (--), el argumento puede estar separado por espacio en blanco o por un carácter de igual (=) sin espacio adicional. Por ejemplo,


-Anombre="J. Duke"
-proc:only
-d miDirectorio
--module-version 3
--module-version=3

En las siguientes listas de opciones, un argumento de ruta representa una ruta de búsqueda, compuesta por una lista de ubicaciones del sistema de archivos separadas por el carácter separador de ruta de la plataforma (punto y coma ; en Windows, o dos puntos : en otros sistemas). Dependiendo de la opción, las ubicaciones del sistema de archivos pueden ser directorios, archivos JAR o archivos JMOD.

VARIABLES DE ENTORNO

CLASSPATH

Si no se especifica la opción --class-path ni ninguna de sus formas alternativas, la ruta de clases se establecerá de forma predeterminada con el valor de la variable de entorno CLASSPATH, si está definida. Sin embargo, se recomienda que esta variable de entorno no esté configurada y que se utilice la opción --class-path para proporcionar un valor explícito para la ruta de clases cuando sea necesario.

JDK_JAVAC_OPTIONS

El contenido de la variable de entorno JDK_JAVAC_OPTIONS, separado por espacios en blanco ( ) o caracteres de espacio en blanco (\n, \t, \r o \f), se antepone a los argumentos de la línea de comandos pasados a javac como una lista de argumentos.

El requisito de codificación para la variable de entorno es el mismo que para la línea de comandos de javac en el sistema. El contenido de la variable de entorno JDK_JAVAC_OPTIONS se trata de la misma manera que el especificado en la línea de comandos.

Se pueden usar comillas simples (') o dobles (") para encerrar argumentos que contengan caracteres de espacio en blanco. Todo el contenido entre la comilla de apertura y la primera comilla de cierre coincidente se conserva simplemente eliminando el par de comillas. En caso de que no se encuentre una comilla coincidente, el lanzador abortará con un mensaje de error. Se admiten @archivos tal como se especifican en la línea de comandos. Sin embargo, al igual que en @archivos, no se admite el uso de un comodín.

Ejemplos de comillas para argumentos que contienen espacios en blanco:

export JDK_JAVAC_OPTIONS='@"C:\espacios en blanco\archivo_argumentos"'

export JDK_JAVAC_OPTIONS='"@C:\espacios en blanco\archivo_argumentos"'

export JDK_JAVAC_OPTIONS='@C:\"espacios en blanco"\archivo_argumentos'

ARCHIVOS DE ARGUMENTOS DE LÍNEA DE COMANDOS

Un archivo de argumentos puede incluir opciones de línea de comandos y nombres de archivos fuente en cualquier combinación. Los argumentos dentro de un archivo pueden separarse por espacios o caracteres de nueva línea. Si un nombre de archivo contiene espacios incrustados, encierre todo el nombre de archivo entre comillas dobles.

Los nombres de archivo dentro de un archivo de argumentos son relativos al directorio actual, no a la ubicación del archivo de argumentos. No se permiten comodines (*) en estas listas (por ejemplo, para especificar *.java). No se admite el uso de la arroba (@) para interpretar archivos de forma recursiva. Las opciones -J no son compatibles porque se pasan al lanzador, que no admite archivos de argumentos.

Al ejecutar el comando javac, pase la ruta y el nombre de cada archivo de argumentos con el carácter arroba (@) como prefijo. Cuando el comando javac encuentra un argumento que comienza con el carácter arroba (@), expande el contenido de ese archivo en la lista de argumentos.

DISPOSICIÓN DEL CÓDIGO FUENTE

En el lenguaje Java, las clases e interfaces se pueden organizar en paquetes y los paquetes en módulos. javac espera que la disposición física de los archivos fuente en los directorios del sistema de archivos refleje la organización de las clases en paquetes y los paquetes en módulos.

Es una convención ampliamente adoptada que los nombres de módulos y paquetes comiencen con una letra minúscula y que los nombres de clases comiencen con una letra mayúscula.

Disposición del Código Fuente para un Paquete

Cuando las clases e interfaces se organizan en un paquete, el paquete se representa como un directorio y cualquier subpaquete se representa como subdirectorios.

Por ejemplo:

•
El paquete p se representa como un directorio llamado p.
•
El paquete p.q, es decir, el subpaquete q del paquete p, se representa como el subdirectorio q del directorio p. El árbol de directorios que representa el paquete p.q es, por lo tanto, p\q en Windows y p/q en otros sistemas.
•
El paquete p.q.r se representa como el árbol de directorios p\q\r (en Windows) o p/q/r (en otros sistemas).

Dentro de un directorio o subdirectorio, los archivos .java representan clases e interfaces en el paquete o subpaquete correspondiente.

Por ejemplo:

•
La clase X declarada en el paquete p se representa mediante el archivo X.java en el directorio p.
•
La clase Y declarada en el paquete p.q se representa mediante el archivo Y.java en el subdirectorio q del directorio p.
•
La clase Z declarada en el paquete p.q.r se representa mediante el archivo Z.java en el subdirectorio r de p\q (en Windows) o p/q (en otros sistemas).

En algunas situaciones, es conveniente dividir el código en directorios separados, cada uno estructurado como se describe anteriormente, y la lista agregada de directorios especificada a javac.

Disposición del Código Fuente para un Módulo

En el lenguaje Java, un módulo es un conjunto de paquetes diseñados para la reutilización. Además de los archivos .java para clases e interfaces, cada módulo tiene un archivo fuente llamado module-info.java que:

1.
declara el nombre del módulo;
2.
enumera los paquetes exportados por el módulo (para permitir la reutilización por otros módulos);
3.
enumera otros módulos requeridos por el módulo (para reutilizar sus paquetes exportados).

Cuando los paquetes se organizan en un módulo, el módulo se representa mediante uno o más directorios que representan los paquetes del módulo, uno de los cuales contiene el archivo module-info.java. Puede ser conveniente, pero no es obligatorio, utilizar un único directorio, nombrado según el módulo, para contener el archivo module-info.java junto con el árbol de directorios que representa los paquetes del módulo (es decir, la jerarquía de paquetes descrita anteriormente). La disposición exacta del código fuente para un módulo suele venir dictada por las convenciones adoptadas por un entorno de desarrollo (IDE) o un sistema de compilación.

Por ejemplo:

•
El módulo a.b.c puede representarse mediante el directorio a.b.c, en todos los sistemas.
•
La declaración del módulo se representa mediante el archivo module-info.java en el directorio a.b.c.
•
Si el módulo contiene el paquete p.q.r, entonces el directorio a.b.c contiene el árbol de directorios p\q\r (en Windows) o p/q/r (en otros sistemas).

•

El código a compilar puede hacer referencia a tipos en archivos fuente adicionales que no se especifican en la línea de comandos. Si es así, debe colocar esos archivos fuente en la ruta fuente o en la ruta del módulo. Solo puede especificar una de estas opciones: si no está compilando código para un módulo, o si solo está compilando código para un solo módulo, use la ruta fuente; si está compilando código para varios módulos, use la ruta fuente del módulo.

•
Utilice la opción --source-path para especificar las ubicaciones de archivos fuente adicionales que puede leer javac. Las ubicaciones en la ruta fuente deben organizarse en una jerarquía de paquetes. También puede usar una forma alternativa de la opción: -sourcepath.
•
Utilice la opción --module-source-path una o más veces para especificar la ubicación de archivos fuente adicionales en diferentes módulos que puede leer javac, o al compilar archivos fuente en varios módulos. Si desea poder hacer referencia a tipos en archivos fuente adicionales pero no desea que se compilen, utilice la opción -implicit.

Nota: si está compilando código para varios módulos, siempre debe especificar una ruta fuente de módulo, y todos los archivos fuente especificados en la línea de comandos deben estar en uno de los directorios de la ruta fuente del módulo, o en un subdirectorio del mismo.

Si desea incluir módulos adicionales en su compilación, utilice la opción --add-modules. Esto puede ser necesario cuando esté compilando código que no está en un módulo, o que está en un módulo automático, y el código hace referencia a API en los módulos adicionales.

Si desea especificar que se deben considerar paquetes adicionales como requeridos por un módulo, utilice la opción --add-reads. Esto puede ser útil al realizar pruebas de caja blanca; se desaconseja encarecidamente depender del acceso a API internas en el código de producción.

BÚSQUEDA DE DECLARACIONES DE MÓDULOS, PAQUETES Y TIPOS

Para compilar un archivo fuente, el compilador a menudo necesita información sobre un módulo o tipo, pero la declaración no se encuentra en los archivos fuente especificados en la línea de comandos.

javac necesita información de tipos para cada

o clase o interfaz utilizada, extendida o implementada en el archivo fuente. Esto incluye clases e interfaces que no se mencionan explícitamente en el archivo fuente, pero que proporcionan información a través de la herencia.

Por ejemplo, cuando crea una subclase de java.awt.Window, también está utilizando las clases ancestras de Window: java.awt.Container, java.awt.Component y java.lang.Object.

Al compilar código para un módulo, el compilador también necesita tener disponible la declaración de ese módulo.

Una búsqueda exitosa puede producir un archivo de clase, un archivo fuente, o ambos. Si se encuentran ambos, puede utilizar la opción -Xprefer para indicar al compilador cuál utilizar.

Si una búsqueda encuentra y utiliza un archivo fuente, por defecto javac compila ese archivo fuente. Este comportamiento se puede modificar con -implicit.

El compilador podría no descubrir la necesidad de cierta información de tipo hasta después de que finalice el procesamiento de anotaciones. Cuando la información de tipo se encuentra en un archivo fuente y no se especifica ninguna opción -implicit, el compilador emite una advertencia de que el archivo se está compilando sin estar sujeto a procesamiento de anotaciones. Para deshabilitar la advertencia, especifique el archivo en la línea de comandos (para que esté sujeto a procesamiento de anotaciones) o utilice la opción -implicit para especificar si se deben generar archivos de clase para dichos archivos fuente o no.

La forma en que javac localiza las declaraciones de esos tipos depende de si la referencia existe dentro del código de un módulo o no.

Búsqueda en rutas orientadas a paquetes

Al buscar un archivo fuente o de clase en una ruta compuesta por ubicaciones orientadas a paquetes, javac verificará cada ubicación en la ruta secuencialmente para la posible presencia del archivo. La primera aparición de un archivo particular oculta (esconde) cualquier aparición posterior de archivos con el mismo nombre. Este ocultamiento no afecta ninguna búsqueda de archivos con un nombre diferente. Esto puede ser conveniente al buscar archivos fuente, que pueden agruparse en diferentes ubicaciones, como código compartido, código específico de plataforma y código generado. También puede ser útil al inyectar versiones alternativas de un archivo de clase en un paquete, para depuración u otras razones de instrumentación. Pero, también puede ser peligroso, como al colocar versiones incompatibles diferentes de una biblioteca en la ruta de clases.

Búsqueda en rutas orientadas a módulos

Antes de escanear cualquier ruta de módulos para obtener declaraciones de paquetes o tipos, javac escaneará perezosamente las siguientes rutas y ubicaciones para determinar los módulos que se utilizarán en la compilación.

•
La ruta de origen de los módulos (ver la opción --module-source-path)
•
La ruta para módulos actualizables (ver la opción --upgrade-module-path)
•
Los módulos del sistema (ver la opción --system)
•
La ruta de módulos del usuario (ver la opción --module-path)

Para cualquier módulo, la primera aparición del módulo durante el escaneo oculta completamente (esconde) cualquier aparición posterior de un módulo con el mismo nombre. Al localizar los módulos, javac puede determinar los paquetes exportados por el módulo y asociar a cada módulo una ruta orientada a paquetes para el contenido del módulo. Para cualquier módulo compilado previamente, esta ruta típicamente será una única entrada para un directorio o un archivo que proporciona una jerarquía interna similar a un directorio, como un archivo JAR. Por lo tanto, al buscar un tipo que se encuentra en un paquete que se sabe que está exportado por un módulo, javac puede localizar la declaración de forma directa y eficiente.

Búsqueda de la declaración de un módulo

Si el módulo ha sido compilado previamente, la declaración del módulo se encuentra en un archivo llamado module-info.class en la raíz de la jerarquía de paquetes para el contenido del módulo.

Si el módulo es uno de los que se están compilando actualmente, la declaración del módulo será el archivo llamado module-info.class en la raíz de la jerarquía de paquetes para el módulo en el directorio de salida de clases, o el archivo llamado module-info.java en una de las ubicaciones de la ruta de origen o una de las rutas de origen de módulos para el módulo.

Búsqueda de la declaración de un tipo cuando la referencia no está en un módulo

Al buscar un tipo al que se hace referencia en código que no está en un módulo, javac buscará en los siguientes lugares:

•
Las clases de la plataforma (o los tipos en paquetes exportados de los módulos de la plataforma) (Esto es solo para archivos de clase compilados).
•
Tipos en paquetes exportados de cualquier módulo en la ruta de módulos, si corresponde. (Esto es solo para archivos de clase compilados).
•
Tipos en paquetes en la ruta de clases y/o ruta de origen:
•
Si se especifican ambas, javac busca archivos de clase compilados en la ruta de clases y archivos fuente en la ruta de origen.
•
Si se especifica la ruta de clases, pero no la ruta de origen, javac busca tanto archivos de clase compilados como archivos fuente en la ruta de clases.
•
Si no se especifica la ruta de clases, se usa el directorio actual por defecto.

Al buscar un tipo en la ruta de clases y/o ruta de origen, si se encuentran tanto un archivo de clase compilado como un archivo fuente, por defecto se utilizará el archivo modificado más recientemente. Si el archivo fuente es más nuevo, se compilará y puede reemplazar cualquier versión previamente compilada del archivo. Puede utilizar la opción -Xprefer para anular el comportamiento predeterminado.

Búsqueda de la declaración de un tipo cuando la referencia está en un módulo

Al buscar un tipo al que se hace referencia en código dentro de un módulo, javac examinará la declaración del módulo contenedor para determinar si el tipo se encuentra en un paquete que está exportado por otro módulo que es legible por el módulo contenedor. Si es así, javac irá directamente y de forma sencilla a la definición de ese módulo para encontrar la definición del tipo requerido. A menos que el módulo sea otro de los módulos que se están compilando, javac solo buscará archivos de clase compilados. En otras palabras, javac no buscará archivos fuente en módulos de plataforma o módulos en la ruta de módulos.

Si el tipo al que se hace referencia no se encuentra en algún otro módulo legible, javac examinará el módulo que se está compilando para intentar encontrar la declaración del tipo. javac buscará la declaración del tipo de la siguiente manera:

•
Archivos fuente especificados en la línea de comandos o en la ruta de origen o ruta de origen de módulos.
•
Archivos previamente compilados en el directorio de salida.

Jerarquías de directorios

javac generalmente asume que los archivos fuente y los archivos de clase compilados se organizarán en una jerarquía de directorios del sistema de archivos o en un tipo de archivo que admite una jerarquía interna de directorios, como un archivo JAR. Se admiten tres tipos diferentes de jerarquía: una jerarquía de *paquetes*, una jerarquía de *módulos* y una *jerarquía de origen de módulos*.

Si bien javac es bastante flexible con la organización del código fuente, más allá de la expectativa de que el código fuente se organizará en una o varias jerarquías de paquetes, y generalmente puede adaptarse a las organizaciones prescritas por los entornos de desarrollo y las herramientas de compilación, las herramientas de Java en general, y javac y el lanzador de Java en particular, son más estrictas con la organización de los archivos de clase compilados, y se organizarán en jerarquías de paquetes o jerarquías de módulos, según corresponda.

La ubicación de estas jerarquías se especifica a javac mediante opciones de línea de comandos, cuyos nombres suelen terminar en "path", como --source-path o --class-path. También, como regla general, las opciones de ruta cuyos nombres incluyen la palabra módulo, como --module-path, se utilizan para especificar jerarquías de módulos, aunque algunas opciones de ruta relacionadas con módulos permiten especificar una jerarquía de paquetes por módulo. Todas las demás opciones de ruta se utilizan para especificar jerarquías de paquetes.

Jerarquía de paquetes

En una jerarquía de paquetes, los directorios y subdirectorios se utilizan para representar las partes componentes del nombre del paquete, y el archivo fuente o el archivo de clase compilado para un tipo se almacena como un archivo con la extensión .java o .class en el directorio más anidado.

Por ejemplo, en una jerarquía de paquetes, el archivo fuente para una clase com.example.MyClass se almacenará en el archivo com/example/MyClass.java

Jerarquía de módulos

En una jerarquía de módulos, el primer nivel de directorios se nombra para los módulos de la jerarquía; dentro de cada uno de esos directorios, el contenido del módulo se organiza en jerarquías de paquetes.

Por ejemplo, en una jerarquía de módulos, el archivo de clase compilado para un tipo llamado com.example.MyClass en un módulo llamado my.library se almacenará en my.library/com/example/MyClass.class.

Los diversos directorios de salida utilizados por javac (el directorio de salida de clases, el directorio de salida de origen y el directorio de salida de encabezados nativos) se organizarán en una jerarquía de módulos cuando se compilen varios módulos.

Jerarquía de origen de módulos

Aunque el origen de cada módulo individual siempre debe organizarse en una jerarquía de paquetes, puede ser conveniente agrupar esas jerarquías en una jerarquía de origen de módulos. Esto es similar a una jerarquía de módulos, excepto que puede haber directorios intermedios entre el directorio del módulo y el directorio que es la raíz de la jerarquía de paquetes para el código fuente del módulo.

rawtypes
Warns about unchecked operations on raw types. The following statement generates a rawtypes warning:

void countElements(List l) { ... }

The following example does not generate a rawtypes warning:

void countElements(List<?> l) { ... }

List is a raw type. However, List<?> is an unbounded wildcard parameterized type. Because List is a parameterized interface, always specify its type argument. In this example, the List formal argument is specified with an unbounded wildcard (?) as its formal type parameter, which means that the countElements method can accept any instantiation of the List interface.

serial
Warns about missing serialVersionUID definitions on serializable classes. For example:

public class PersistentTime implements Serializable
{
  private Date time;
   public PersistentTime() {
     time = Calendar.getInstance().getTime();
   }
   public Date getTime() {
     return time;
   }
}

The compiler generates the following warning:


warning: [serial] serializable class PersistentTime has no definition of
serialVersionUID

If a serializable class does not explicitly declare a field named serialVersionUID, then the serialization runtime environment calculates a default serialVersionUID value for that class based on various aspects of the class, as described in the Java Object Serialization Specification. However, it's strongly recommended that all serializable classes explicitly declare serialVersionUID values because the default process of computing serialVersionUID values is highly sensitive to class details that can vary depending on compiler implementations. As a result, this might cause an unexpected InvalidClassExceptions during deserialization. To guarantee a consistent serialVersionUID value across different Java compiler implementations, a serializable class must declare an explicit serialVersionUID value.

static
Warns about issues relating to the use of static variables, for example:

class XLintStatic {
    static void m1() { }
    void m2() { this.m1(); }
}

The compiler generates the following warning:


warning: [static] static method should be qualified by type name,
XLintStatic, instead of by an expression

To resolve this issue, you can call the static method m1 as follows:

XLintStatic.m1();

Alternately, you can remove the static keyword from the declaration of the method m1.

this-escape
Warns about constructors leaking this prior to subclass initialization. For example, this class:

public class MyClass {
  public MyClass() {
    System.out.println(this.hashCode());
  }
}

generates the following warning:


MyClass.java:3: warning: [this-escape] possible 'this' escape
                         before subclass is fully initialized
    System.out.println(this.hashCode());
                                    ^

A 'this' escape warning is generated when a constructor does something that might result in a subclass method being invoked before the constructor returns. In such cases the subclass method would be operating on an incompletely initialized instance. In the above example, a subclass of MyClass that overrides hashCode() to incorporate its own fields would likely produce an incorrect result when invoked as shown.

Warnings are only generated if a subclass could exist that is outside of the current module (or package, if no module) being compiled. So, for example, constructors in final and non-public classes do not generate warnings.

try
Warns about issues relating to the use of try blocks, including try-with-resources statements. For example, a warning is generated for the following statement because the resource ac declared in the try block is not used:

try ( AutoCloseable ac = getResource() ) {    // do nothing}
unchecked
Gives more detail for unchecked conversion warnings that are mandated by the Java Language Specification, for example:

List l = new ArrayList<Number>();
List<String> ls = l;       // unchecked warning

During type erasure, the types ArrayList<Number> and List<String> become ArrayList and List, respectively.

The ls command has the parameterized type List<String>. When the List referenced by l is assigned to ls, the compiler generates an unchecked warning. At compile time, the compiler and JVM cannot determine whether l refers to a List<String> type. In this case, l does not refer to a List<String> type. As a result, heap pollution occurs.

A heap pollution situation occurs when the List object l, whose static type is List<Number>, is assigned to another List object, ls, that has a different static type, List<String>. However, the compiler still allows this assignment. It must allow this assignment to preserve backward compatibility with releases of Java SE that do not support generics. Because of type erasure, List<Number> and List<String> both become List. Consequently, the compiler allows the assignment of the object l, which has a raw type of List, to the object ls.

varargs
Warns about unsafe use of variable arguments (varargs) methods, in particular, those that contain non-reifiable arguments, for example:

public class ArrayBuilder {
  public static <T> void addToList (List<T> listArg, T... elements) {
    for (T x : elements) {
      listArg.add(x);
    }
  }
}

A non-reifiable type is a type whose type information is not fully available at runtime.

The compiler generates the following warning for the definition of the method ArrayBuilder.addToList:


warning: [varargs] Possible heap pollution from parameterized vararg type T

When the compiler encounters a varargs method, it translates the varargs formal parameter into an array. However, the Java programming language does not permit the creation of arrays of parameterized types. In the method ArrayBuilder.addToList, the compiler translates the varargs formal parameter T... elements to the formal parameter T[] elements, an array. However, because of type erasure, the compiler converts the varargs formal parameter to Object[] elements. Consequently, there's a possibility of heap pollution.
