JARSIGNER(1) Comandos del JDK JARSIGNER(1)

NOMBRE

jarsigner - firmar y verificar archivos Java Archive (JAR)

SINOPSIS

jarsigner [opciones] archivo-jar alias

jarsigner -verify [opciones] archivo-jar [alias ...]

jarsigner -version

opciones
Las opciones de la línea de comandos. Véase Opciones para jarsigner.
-verify
La opción -verify puede tomar cero o más nombres de alias de almacén de claves después del nombre del archivo JAR. Cuando se especifica la opción -verify , el comando jarsigner comprueba que el certificado utilizado para verificar cada entrada firmada en el archivo JAR coincida con uno de los alias del almacén de claves. Los alias se definen en el almacén de claves especificado por -keystore o en el almacén de claves predeterminado.

Si también especifica la opción -strict y el comando jarsigner detecta advertencias graves, se muestra el mensaje "jar verified, with signer errors" (jar verificado, con errores del firmante).

archivo-jar
El archivo JAR que se va a firmar.

Si también especificó la opción -strict y el comando jarsigner detectó advertencias graves, se muestra el mensaje "jar signed, with signer errors" (jar firmado, con errores del firmante).

alias
Los alias se definen en el almacén de claves especificado por -keystore o en el almacén de claves predeterminado.
-version
La opción -version imprime la versión del programa de jarsigner.

DESCRIPCIÓN

La herramienta jarsigner tiene dos propósitos:

•
Firmar archivos Java Archive (JAR).
•
Verificar las firmas y la integridad de archivos JAR firmados.

La característica JAR permite empaquetar archivos de clases, imágenes, sonidos y otros datos digitales en un solo archivo para una distribución más rápida y sencilla. Una herramienta llamada jar permite a los desarrolladores producir archivos JAR. (Técnicamente, cualquier archivo ZIP también puede considerarse un archivo JAR, aunque cuando es creado por el comando jar o procesado por el comando jarsigner , los archivos JAR también contienen un archivo META-INF/MANIFEST.MF .)

Una firma digital es una cadena de bits que se calcula a partir de algunos datos (los datos que se firman) y la clave privada de una entidad (una persona, una empresa, etc.). De manera similar a una firma manuscrita, una firma digital tiene muchas características útiles:

•
Su autenticidad puede verificarse mediante un cálculo que utiliza la clave pública correspondiente a la clave privada utilizada para generar la firma.
•
No se puede falsificar, siempre que la clave privada se mantenga secreta.
•
Es una función de los datos firmados y, por lo tanto, no puede afirmarse que sea la firma de otros datos también.
•
Los datos firmados no pueden ser modificados. Si los datos se cambian, entonces la firma no puede verificarse como auténtica.

Para generar la firma de una entidad para un archivo, la entidad debe tener primero un par de claves pública/privada asociado con ella y uno o más certificados que autentiquen su clave pública. Un certificado es una declaración firmada digitalmente por una entidad que indica que la clave pública de otra entidad tiene un valor particular.

El comando jarsigner utiliza información de claves y certificados de un almacén de claves para generar firmas digitales para archivos JAR. Un almacén de claves es una base de datos de claves privadas y sus cadenas de certificados X.509 asociadas que autentican las claves públicas correspondientes. El comando keytool se utiliza para crear y administrar almacenes de claves.

El comando jarsigner utiliza la clave privada de una entidad para generar una firma. El archivo JAR firmado contiene, entre otras cosas, una copia del certificado del almacén de claves para la clave pública correspondiente a la clave privada utilizada para firmar el archivo. El comando jarsigner puede verificar la firma digital del archivo JAR firmado utilizando el certificado que contiene (en su archivo de bloque de firma).

El comando jarsigner puede generar firmas que incluyan una marca de tiempo que permite a un sistema o implementador comprobar si el archivo JAR fue firmado mientras el certificado de firma aún era válido.

Además, las API permiten a las aplicaciones obtener la información de la marca de tiempo.

En este momento, el comando jarsigner solo puede firmar archivos JAR creados por el comando jar o archivos zip. Los archivos JAR son iguales a los archivos zip, excepto que también tienen un archivo META-INF/MANIFEST.MF . Un archivo META-INF/MANIFEST.MF se crea cuando el comando jarsigner firma un archivo zip.

El comportamiento predeterminado del comando jarsigner es firmar un archivo JAR o zip. Utilice la opción -verify para verificar un archivo JAR firmado.

El comando jarsigner también intenta validar el certificado del firmante después de firmar o verificar. Durante la validación, comprueba el estado de revocación de cada certificado en la cadena de certificados del firmante cuando se especifica la opción -revCheck . Si hay un error de validación u otro problema, el comando genera mensajes de advertencia. Si especifica la opción -strict , entonces el comando trata las advertencias graves como errores. Véase Errores y advertencias.

ALIAS DEL ALMACÉN DE CLAVES

Todas las entidades del almacén de claves se acceden con alias únicos.

Cuando utiliza el comando jarsigner para firmar un archivo JAR, debe especificar el alias de la entrada del almacén de claves que contiene la clave privada necesaria para generar la firma. Si no se especifica un archivo de salida, sobrescribe el archivo JAR original con el archivo JAR firmado.

Los almacenes de claves están protegidos con una contraseña, por lo que se debe especificar la contraseña del almacén. Se le solicitará si no la especifica en la línea de comandos. De manera similar, las claves privadas están protegidas en un almacén de claves con una contraseña, por lo que se debe especificar la contraseña de la clave privada, y se le solicitará la contraseña cuando no la especifique en la línea de comandos y no sea la misma que la contraseña del almacén.

UBICACIÓN DEL ALMACÉN DE CLAVES

El comando jarsigner tiene una opción -keystore para especificar la URL del almacén de claves a utilizar. El almacén de claves se almacena de forma predeterminada en un archivo llamado .keystore en el directorio de inicio del usuario, según lo determinado por la propiedad del sistema user.home .

Linux y macOS: user.home tiene como valor predeterminado el directorio de inicio del usuario.

El flujo de entrada de la opción -keystore se pasa al método KeyStore.load . Si se especifica NONE como URL, se pasa un flujo nulo al método KeyStore.load . NONE debe especificarse cuando la clase KeyStore no está basada en archivos, por ejemplo, cuando reside en un dispositivo de token de hardware.

IMPLEMENTACIÓN DEL ALMACÉN DE CLAVES

La clase KeyStore proporcionada en el paquete java.security suministra una serie de interfaces bien definidas para acceder y modificar la información en un almacén de claves. Puede haber múltiples implementaciones concretas diferentes, donde cada implementación es para un tipo particular de almacén de claves.

Actualmente, hay dos herramientas de línea de comandos que utilizan implementaciones de almacén de claves (keytool y jarsigner).

La implementación predeterminada del almacén de claves es PKCS12. Este es un almacén de claves multiplataforma basado en el Estándar de Sintaxis de Intercambio de Información Personal RSA PKCS12. Este estándar está diseñado principalmente para almacenar o transportar claves privadas de usuario, certificados y secretos diversos. Existe otra implementación incorporada, proporcionada por Oracle. Implementa el almacén de claves como un archivo con un tipo de almacén de claves (formato) propietario llamado JKS. Protege cada clave privada con su contraseña individual y también protege la integridad de todo el almacén de claves con una contraseña (posiblemente diferente).

Las implementaciones de almacenes de claves se basan en proveedores, lo que significa que las interfaces de aplicación suministradas por la clase KeyStore se implementan en términos de una Interfaz de Proveedor de Servicios (SPI). Existe una clase abstracta correspondiente KeystoreSpi, también en el paquete java.security, que define los métodos de la Interfaz de Proveedor de Servicios que los proveedores deben implementar. El término proveedor se refiere a un paquete o un conjunto de paquetes que suministran una implementación concreta de un subconjunto de servicios a los que se puede acceder mediante la API de seguridad de Java. Para proporcionar una implementación de almacén de claves, los clientes deben implementar un proveedor y suministrar una implementación de subclase KeystoreSpi, como se describe en Cómo implementar un proveedor en la Arquitectura de Criptografía de Java [https://www.oracle.com/pls/topic/lookup?ctx=en/java/javase&id=security_guide_implement_provider_jca].

Las aplicaciones pueden elegir diferentes tipos de implementaciones de almacén de claves de diferentes proveedores, con el método de fábrica getInstance en la clase KeyStore. Un tipo de almacén de claves define el formato de almacenamiento y datos de la información del almacén de claves y los algoritmos utilizados para proteger las claves privadas en el almacén de claves y la integridad del propio almacén de claves. Las implementaciones de almacenes de claves de diferentes tipos no son compatibles.

Los comandos jarsigner pueden leer almacenes de claves basados en archivos desde cualquier ubicación que se pueda especificar mediante una URL. Además, estos comandos pueden leer almacenes de claves no basados en archivos, como los proporcionados por MSCAPI en Windows y PKCS11 en todas las plataformas.

Para los comandos jarsigner y keytool, puede especificar un tipo de almacén de claves en la línea de comandos con la opción -storetype.

Si no especifica explícitamente un tipo de almacén de claves, las herramientas eligen una implementación de almacén de claves basándose en el valor de la propiedad keystore.type especificada en el archivo de propiedades de seguridad. El archivo de propiedades de seguridad se llama java.security y reside en el directorio de propiedades de seguridad del JDK, java.home/conf/security.

Cada herramienta obtiene el valor de keystore.type y luego examina todos los proveedores instalados hasta que encuentra uno que implementa almacenes de claves de ese tipo. Luego utiliza la implementación de almacén de claves de ese proveedor.

La clase KeyStore define un método estático llamado getDefaultType que permite a las aplicaciones recuperar el valor de la propiedad keystore.type. La siguiente línea de código crea una instancia del tipo de almacén de claves predeterminado según lo especificado en la propiedad keystore.type:

KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType());

El tipo de almacén de claves predeterminado es pkcs12, que es un almacén de claves multiplataforma basado en el Estándar de Sintaxis de Intercambio de Información Personal RSA PKCS12. Esto se especifica mediante la siguiente línea en el archivo de propiedades de seguridad:

keystore.type=pkcs12

La capitalización no importa en las designaciones de tipo de almacén de claves. Por ejemplo, JKS es lo mismo que jks.

Para que las herramientas utilicen una implementación de almacén de claves distinta de la predeterminada, puede cambiar esa línea para especificar un tipo de almacén de claves diferente. Por ejemplo, si desea utilizar la implementación de almacén de claves jks de Oracle, cambie la línea a la siguiente:

keystore.type=jks

El comando jarsigner utiliza las propiedades de seguridad jdk.jar.disabledAlgorithms y jdk.security.legacyAlgorithms para determinar qué algoritmos se consideran un riesgo de seguridad. Si el archivo JAR se firmó con algoritmos deshabilitados, se tratará como un archivo JAR sin firmar. Si el archivo JAR se firmó con algoritmos heredados, se tratará como firmado con una advertencia informativa para informar a los usuarios que el algoritmo heredado será deshabilitado en una futura actualización. Para obtener una salida de verificación detallada, incluya -J-Djava.security.debug=jar. Las propiedades de seguridad jdk.jar.disabledAlgorithms y jdk.security.legacyAlgorithms se definen en el archivo java.security (ubicado en el directorio $JAVA_HOME/conf/security del JDK).

Nota:

Para mejorar la seguridad de fábrica, el tamaño de clave y los nombres de los algoritmos de firma predeterminados se actualizan periódicamente a valores más robustos con cada versión del JDK. Si la interoperabilidad con versiones anteriores del JDK es importante, asegúrese de que los valores predeterminados sean compatibles con esas versiones o, alternativamente, utilice la opción -sigalg para anular los valores predeterminados bajo su propio riesgo.

EL ARCHIVO JAR FIRMADO

Cuando se utiliza el comando jarsigner para firmar un archivo JAR, el archivo JAR firmado de salida es exactamente el mismo que el archivo JAR de entrada, excepto que tiene dos archivos adicionales colocados en el directorio META-INF:

•
Un archivo de firma con extensión .SF
•
Un archivo de bloque de firma con extensión .DSA, .RSA o .EC

Los nombres de archivo base para estos dos archivos provienen del valor de la opción -sigfile. Por ejemplo, cuando la opción es -sigfile MKSIGN, los archivos se llaman MKSIGN.SF y MKSIGN.RSA. En este documento, asumimos que el firmante siempre utiliza una clave RSA.

Si no aparece ninguna opción -sigfile en la línea de comandos, el nombre de archivo base para los archivos .SF y de bloque de firma es los primeros 8 caracteres del alias especificado en la línea de comandos, todos convertidos a mayúsculas. Si el nombre del alias tiene menos de 8 caracteres, se utiliza el nombre completo del alias. Si el nombre del alias contiene caracteres no permitidos en un nombre de archivo de firma, cada uno de esos caracteres se convierte en un guion bajo (_) al formar el nombre del archivo. Los caracteres válidos incluyen letras, dígitos, guiones bajos y guiones.

ARCHIVO DE FIRMA

Un archivo de firma (archivo .SF) se parece al archivo de manifiesto que siempre se incluye en un archivo JAR cuando se utiliza el comando jarsigner para firmar el archivo. Para cada archivo fuente incluido en el archivo JAR, el archivo .SF tiene dos líneas, como en el archivo de manifiesto, que enumeran lo siguiente:

•
Nombre del archivo
•
Nombre del algoritmo de resumen (SHA)
•
Valor del resumen SHA

Nota:

El nombre del algoritmo de resumen (SHA) y el valor del resumen SHA están en la misma línea.

En el archivo de manifiesto, el valor del resumen SHA para cada archivo fuente es el resumen (hash) de los datos binarios del archivo fuente. En el archivo .SF, el valor del resumen para un archivo fuente especificado es el hash de las dos líneas del archivo de manifiesto para ese archivo fuente.

El archivo de firma, por defecto, incluye una cabecera con un hash de todo el archivo de manifiesto. La cabecera también contiene un hash de la cabecera del manifiesto. La presencia de la cabecera permite la optimización de la verificación. Consulte Verificación de Archivos JAR.

ARCHIVO DE BLOQUE DE FIRMA

LE'>BLOQUE DE ARCHIVOS DE FIRMA

El archivo .SF está firmado y la firma se coloca en el archivo del bloque de firma. Este archivo también contiene, codificado dentro de él, el certificado o la cadena de certificados del almacén de claves que autentica la clave pública correspondiente a la clave privada usada para firmar. El archivo tiene la extensión .DSA, .RSA, o .EC, dependiendo del algoritmo de clave utilizado. Vea la tabla en Algoritmos admitidos.

VERIFICACIÓN DE ARCHIVOS JAR

Una verificación de archivo JAR es exitosa cuando las firmas son válidas y ninguno de los archivos que estaban en el archivo JAR cuando se generaron las firmas ha cambiado desde entonces. La verificación de archivos JAR implica los siguientes pasos:

1.
Verificar la firma del archivo .SF .

La verificación asegura que la firma almacenada en cada archivo del bloque de firma fue generada usando la clave privada correspondiente a la clave pública cuyo certificado (o cadena de certificados) también aparece en el archivo del bloque de firma. También asegura que la firma es una firma válida del archivo de firma correspondiente (.SF), y por lo tanto el archivo .SF no fue alterado.

2.
Verificar el resumen (digest) listado en cada entrada del archivo .SF con cada sección correspondiente en el manifiesto.

El archivo .SF incluye por defecto un encabezado que contiene un hash del archivo de manifiesto completo. Cuando el encabezado está presente, la verificación puede comprobar si el hash en el encabezado coincide con el hash del archivo de manifiesto. Si hay una coincidencia, entonces la verificación procede al siguiente paso.

Si no hay una coincidencia, entonces se requiere una verificación menos optimizada para asegurar que el hash en cada sección de información de archivo de origen en el archivo .SF es igual al hash de su sección correspondiente en el archivo de manifiesto. Vea Archivo de firma.

Una razón por la que el hash del archivo de manifiesto almacenado en el encabezado del archivo .SF podría no ser igual al hash del archivo de manifiesto actual es que podría contener secciones para archivos añadidos después de que el archivo fue firmado. Por ejemplo, suponga que uno o más archivos fueron añadidos al archivo JAR firmado (usando la herramienta jar ) que ya contiene una firma y un archivo .SF . Si el archivo JAR es firmado de nuevo por un firmante diferente, entonces el archivo de manifiesto es modificado (se le añaden secciones para los nuevos archivos por la herramienta jarsigner ) y un nuevo archivo .SF es creado, pero el archivo .SF original no es modificado. Una verificación todavía se considera exitosa si ninguno de los archivos que estaban en el archivo JAR cuando se generó la firma original han sido cambiados desde entonces. Esto se debe a que los hashes en las secciones que no son de encabezado del archivo .SF son iguales a los hashes de las secciones correspondientes en el archivo de manifiesto.

3.
Leer cada archivo en el archivo JAR que tiene una entrada en el archivo .SF . Mientras se lee, calcular el resumen (digest) del archivo y comparar el resultado con el resumen para este archivo en la sección del manifiesto. Los resúmenes deberían ser iguales o la verificación falla.

Si ocurren fallos de verificación graves durante el proceso de verificación, entonces el proceso se detiene y se lanza una excepción de seguridad. El comando jarsigner captura y muestra la excepción.

4.
Comprobar el uso de algoritmos deshabilitados. Vea Algoritmos admitidos.

Nota:

Debería leer cualquier advertencia adicional (o errores si especificó la opción -strict ), así como el contenido del certificado (especificando las opciones -verbose y -certs ) para determinar si la firma puede ser de confianza.

MÚLTIPLES FIRMAS PARA UN ARCHIVO JAR

Un archivo JAR puede ser firmado por múltiples personas ejecutando el comando jarsigner en el archivo múltiples veces y especificando el alias para una persona diferente cada vez, como sigue:

jarsigner myBundle.jar susan
jarsigner myBundle.jar kevin

Cuando un archivo JAR es firmado múltiples veces, hay múltiples archivos .SF y archivos de bloque de firma en el archivo JAR resultante, un par para cada firma. En el ejemplo anterior, el archivo JAR de salida incluye archivos con los siguientes nombres:

SUSAN.SF
SUSAN.RSA
KEVIN.SF
KEVIN.RSA

OPCIONES PARA JARSIGNER

Las siguientes secciones describen las opciones para jarsigner. Tenga en cuenta los siguientes estándares:

•
Todos los nombres de opciones están precedidos por un signo de guion (-).
•
Las opciones pueden proporcionarse en cualquier orden.
•
Los elementos en cursiva o subrayados (valores de opciones) representan los valores reales que deben proporcionarse.
•
Las opciones -storepass, -keypass, -sigfile, -sigalg, -digestalg, -signedjar, y las opciones relacionadas con TSA solo son relevantes al firmar un archivo JAR; no son relevantes al verificar un archivo JAR firmado. La opción -keystore es relevante para firmar y verificar un archivo JAR. Además, los alias se especifican al firmar y verificar un archivo JAR.
-keystore url
Especifica la URL que indica la ubicación del almacén de claves. Por defecto es el archivo .keystore en el directorio de inicio del usuario, como lo determina la propiedad del sistema user.home .

Un almacén de claves es necesario al firmar. Debe especificar explícitamente un almacén de claves cuando el almacén de claves predeterminado no existe o si desea usar uno diferente al predeterminado.

Un almacén de claves no es necesario al verificar, pero si se especifica uno o el predeterminado existe y también se especificó la opción -verbose , entonces se genera información adicional sobre si alguno de los certificados usados para verificar el archivo JAR está contenido en ese almacén de claves.

El argumento -keystore puede ser un nombre de archivo y una especificación de ruta en lugar de una URL, en cuyo caso se trata igual que un file: URL, por ejemplo, lo siguiente es equivalente:

•
-keystore filePathAndName
•
-keystore file:filePathAndName

Si el proveedor Sun PKCS #11 fue configurado en el archivo de propiedades de seguridad java.security (ubicado en el directorio del JDK $JAVA_HOME/conf/security ), entonces las herramientas keytool y jarsigner pueden operar en el token PKCS #11 especificando estas opciones:

-keystore NONE -storetype PKCS11

Por ejemplo, el siguiente comando lista el contenido del token PKCS#11 configurado:

keytool -keystore NONE -storetype PKCS11 -list

-storepass [:env | :file] argument
Especifica la contraseña que se requiere para acceder al almacén de claves. Esto es necesario solo al firmar (no al verificar) un archivo JAR. En ese caso, si no se proporciona la opción -storepass en la línea de comandos, entonces se le solicita al usuario la contraseña.

Si no se especifica el modificador env o file , entonces la contraseña tiene el valor argument. De lo contrario, la contraseña se recupera de la siguiente manera:

•
env: Recuperar la contraseña de la variable de entorno llamada argument.
•
file: Recuperar la contraseña del archivo llamado argument.

Nota:

La contraseña no debería especificarse en la línea de comandos o en un script a menos que sea con fines de prueba, o esté en un sistema seguro.

OPTIONS

-internalsf
En el pasado, el archivo de bloque de firma generado al firmar un archivo JAR incluía una copia codificada completa del archivo .SF (archivo de firma) también generado. Este comportamiento ha cambiado. Para reducir el tamaño total del archivo JAR de salida, el archivo de bloque de firma no contiene una copia del archivo .SF de forma predeterminada. Si -internalsf aparece en la línea de comandos, se utiliza el comportamiento anterior. Esta opción es útil para pruebas. En la práctica, no utilice la opción -internalsf porque incurre en una mayor sobrecarga.
-sectionsonly
Si la opción -sectionsonly aparece en la línea de comandos, el archivo .SF (archivo de firma) generado al firmar un archivo JAR no incluye una cabecera que contenga un hash de todo el archivo de manifiesto. Contiene solo la información y los hashes relacionados con cada archivo fuente individual incluido en el archivo JAR. Ver Archivo de Firma.

De forma predeterminada, se agrega esta cabecera, como una optimización. Cuando la cabecera está presente, cada vez que se verifica el archivo JAR, la verificación puede primero verificar si el hash en la cabecera coincide con el hash de todo el archivo de manifiesto. Cuando hay una coincidencia, la verificación procede al siguiente paso. Cuando no hay una coincidencia, es necesario realizar una verificación menos optimizada de que el hash en cada sección de información de archivo fuente en el archivo .SF sea igual al hash de su sección correspondiente en el archivo de manifiesto. Ver Verificación de Archivos JAR.

La opción -sectionsonly se utiliza principalmente para pruebas. No debe usarse aparte de para pruebas, ya que su uso incurre en una mayor sobrecarga.

-protected
Los valores pueden ser true o false. Especifique true cuando se debe especificar una contraseña a través de una ruta de autenticación protegida, como un lector de PIN dedicado.
-providerName providerName
Si se configuró más de un proveedor en el archivo de propiedades de seguridad java.security, puede usar la opción -providerName para dirigirse a una instancia de proveedor específica. El argumento de esta opción es el nombre del proveedor.

Para el proveedor Oracle PKCS #11, providerName tiene el formato SunPKCS11-NombreToken, donde NombreToken es el sufijo del nombre con el que se ha configurado la instancia del proveedor, como se detalla en la tabla de atributos de configuración. Por ejemplo, el siguiente comando lista el contenido de la instancia del proveedor del almacén de claves PKCS #11 con el sufijo de nombre SmartCard:

jarsigner -keystore NONE -storetype PKCS11 -providerName SunPKCS11-SmartCard -list

-addprovider nombre [-providerArg arg]
Agrega un proveedor de seguridad por nombre (como SunPKCS11) y un argumento de configuración opcional. El valor del proveedor de seguridad es el nombre de un proveedor de seguridad que está definido en un módulo.

Usado con la opción -providerArg RutaArchivoConfig, las herramientas keytool y jarsigner instalan el proveedor dinámicamente y usan RutaArchivoConfig para la ruta al archivo de configuración del token. El siguiente ejemplo muestra un comando para listar un almacén de claves PKCS #11 cuando el proveedor Oracle PKCS #11 no estaba configurado en el archivo de propiedades de seguridad.

jarsigner -keystore NONE -storetype PKCS11 -addprovider SunPKCS11 -providerArg /midirectorio1/midirectorio2/token.config

-providerClass nombre-clase-proveedor [-providerArg arg]
Se utiliza para especificar el nombre del archivo maestro de la clase del proveedor de servicios criptográficos cuando el proveedor de servicios no está listado en el archivo de propiedades de seguridad java.security. Agrega un proveedor de seguridad por nombre de clase completamente calificado y un argumento de configuración opcional.

ERRORES Y ADVERTENCIAS

Durante el proceso de firma o verificación, el comando jarsigner puede emitir varios errores o advertencias.

Si hay un fallo, el comando jarsigner sale con el código 1. Si no hay fallo, pero hay una o más advertencias graves, el comando jarsigner sale con el código 0 cuando la opción -strict **no** está especificada, o sale con el valor OR de los códigos de advertencia cuando -strict está especificado. Si solo hay advertencias informativas o ninguna advertencia, el comando siempre sale con el código 0.

Por ejemplo, si un certificado utilizado para firmar una entrada ha expirado y tiene una extensión KeyUsage que no le permite firmar un archivo, el comando jarsigner sale con el código 12 (=4+8) cuando se especifica la opción -strict.

Nota: Los códigos de salida se reutilizan porque solo los valores de 0 a 255 son legales en Linux y macOS.

Las siguientes secciones describen los nombres, códigos y descripciones de los errores y advertencias que el comando jarsigner puede emitir.

FALLO

Las razones por las que falla el comando jarsigner incluyen (pero no se limitan a) un error de análisis de línea de comandos, la incapacidad de encontrar un par de claves para firmar el archivo JAR, o falla la verificación de un JAR firmado.

NAME


jarsigner - Sign and verify signed JAR files






SYNOPSIS


jarsigner [options] jar-file alias


jarsigner [options] -verify [-reason] [- ச ] jar-file [ alias... ]


jarsigner -showcerts [- ச ] jar-file [ alias... ]






DESCRIPTION


The jarsigner utility is used to sign applets and applications,
    and to verify signatures on signed JAR files. It can also be used to
    list the signer certificates for a signed JAR file.


When signing a JAR file, you specify a keystore that contains a
    key pair and a certificate chain that will be used to sign the JAR
    file. The key pair is specified by an alias. The certificate chain
    is used to verify the identity of the signer.


When verifying a signed JAR file, you can specify one or more aliases
    to verify the signatures against. If no aliases are specified, then
    all signatures are verified.


The -showcerts option displays the public certificates of the
    signers of the specified JAR file.






KEYSTORE ALIASES


An alias is a name that refers to a private key and its associated
    public-key certificate chain in a keystore.






KEYSTORE LOCATION


The keystore location is specified by the -keystore option. If
    this option is not specified, the default keystore location is
    the user's default keystore, which is typically named
    .keystore in the user's home directory.






KEYSTORE IMPLEMENTATION


The keystore implementation is specified by the -storetype
    option. If this option is not specified, the default keystore type
    is used, which is typically the Java KeyStore (JKS).






SUPPORTED ALGORITHMS


The following signature algorithms are supported:


    
    
  • SHA1withRSA

  • SHA256withRSA
    • 
    
  • SHA512withRSA
    • 
    
  • SHA1withDSA
    • 
    
  • SHA256withDSA
    • 
    
  • SHA512withDSA
    • 
    
  • ECDSA

THE SIGNED JAR FILE


A signed JAR file contains the following additional files:


    
    
  • META-INF/alias.SF
    • 
    
  • META-INF/alias.DSA or META-INF/alias.RSA
    • 
    
  • META-INF/alias.JN
    • 



Where alias is the alias of the signer.






SIGNATURE FILE


The signature file (e.g., META-INF/alias.SF) contains a
    manifest of the JAR file, along with a signature of the manifest.
    The signature file is encoded in Base64 and contains a header
    indicating the digest algorithm used to generate the signature.






SIGNATURE BLOCK FILE


The signature block file (e.g., META-INF/alias.DSA or
    META-INF/alias.RSA) contains the actual digital signature of
    the signature file. It is encoded in Base64 and contains a header
    indicating the signature algorithm used.






SIGNATURE TIME STAMP


A signature timestamp is a timestamp that is cryptographically
    bound to the signature of a JAR file. It is generated by a trusted
    timestamping authority (TSA). The TSA signs the digest of the
    signature block file. The timestamp is typically stored in the
    META-INF/alias.DSA or META-INF/alias.RSA file.


A signature timestamp is used to prove that the JAR file was signed
    before the timestamp expired. This is important for applications that
    rely on the validity of signatures over time.






JAR FILE VERIFICATION


When verifying a signed JAR file, jarsigner checks the
    following:


    
    
  • The signature block file is valid and corresponds to the signature
        file.
    • 
    
  • The signature file is valid and corresponds to the manifest of the
        JAR file.
    • 
    
  • The signer certificate is valid and has not expired.
    • 
    
  • If a timestamp is present, the timestamp is valid and has not
        expired.
    • 







MULTIPLE SIGNATURES FOR A JAR FILE


A JAR file can be signed by multiple signers. In this case, there will
    be multiple signature files and signature block files in the
    META-INF directory. Each signature block file will have a different
    alias.






OPTIONS FOR JARSIGNER



    
-keystore <url>

    
Specifies the location and name of the keystore.

    
-storetype <type>

    
Specifies the type of the keystore.

    
-storepass <password>

    
Specifies the password for the keystore.

    
-keypass <password>

    
Specifies the password for the private key.

    
-signedjar <jar-file>

    
Specifies the name of the signed JAR file to be created.

    
-verify

    
Verifies the signatures of the JAR file.

    
-showcerts

    
Shows the signer certificates of the JAR file.

    
-jarsigner -help

    
Displays help information for the jarsigner command.








ERRORS AND WARNINGS


The following is a list of possible errors and warnings that may be
    displayed when using jarsigner:



    
key associated with alias <alias> does not exist

    
The specified alias does not exist in the keystore.

    
keystore not found

    
The specified keystore location does not exist.

    
keystore password was incorrect

    
The specified keystore password is incorrect.

    
private key password was incorrect

    
The specified private key password is incorrect.

    
unable to find valid certification path to requested target

    
The signer certificate chain is not trusted. This may be because
        the root certificate is not trusted, or because the certificate
        has been revoked.

    
signed JAR has been tampered with, or signature was not originally verified

    
The JAR file has been modified since it was signed, or the
        signature verification failed.








FAILURE


The JAR file is not signed, or the signature is invalid. The JAR file
    is not trusted.






SEVERE WARNINGS


The following are severe warnings that indicate a potential problem
    with the signature:



    
the signer certificate has expired

    
The signer's certificate has expired. The JAR file may no longer
        be trusted.

    
the public key has expired

    
The public key used to sign the JAR file has expired. The JAR file
        may no longer be trusted.

    
the signature has been tampered with

    
The signature of the JAR file has been tampered with. The JAR file
        is not trusted.








INFORMATIONAL WARNINGS


The following are informational warnings that provide additional
    information about the signature:



    
the signer certificate is not before <date>

    
The signer's certificate is not yet valid. The JAR file is not
        trusted until the specified date.

    
the public key is not before <date>

    
The public key used to sign the JAR file is not yet valid. The JAR
        file is not trusted until the specified date.








EXAMPLE OF SIGNING A JAR FILE


The following command signs the JAR file myapp.jar with the alias
    mykey:


jarsigner -keystore mykeystore myapp.jar mykey







EXAMPLE OF VERIFYING A SIGNED JAR FILE


The following command verifies the signatures of the JAR file
    myapp.jar:


jarsigner -verify myapp.jar







EXAMPLE OF VERIFICATION WITH CERTIFICATE INFORMATION


The following command verifies the signatures of the JAR file
    myapp.jar and displays the signer certificate information:


jarsigner -verify -showcerts myapp.jar
