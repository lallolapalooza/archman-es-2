PAQUETE Cada paquete puede tener su propio comentario de documentación, contenido en su propio archivo fuente, que el comando javadoc fusiona en la página de resumen del paquete generada. Normalmente incluye en este comentario cualquier documentación que se aplique a todo el

paquete.

ARCHIVOS DE COMENTARIOS DE PAQUETES

Para crear un archivo de comentarios de paquetes, puedes colocar tus comentarios en uno de los siguientes archivos:

•
El archivo package-info.java puede contener la declaración del paquete, anotaciones de paquete, comentarios de paquete y etiquetas Javadoc. Este archivo es el preferido.
•
El archivo package.html solo contiene comentarios de paquete y etiquetas Javadoc. No contiene anotaciones de paquete.

Un paquete puede tener un solo archivo package.html o un solo archivo package-info.java, pero no ambos. Coloca cualquiera de los archivos en el directorio del paquete dentro del árbol de fuentes, junto con tus archivos de origen.

El Archivo package-info.java

El archivo package-info.java puede contener un comentario de paquete con la siguiente estructura. El comentario se coloca antes de la declaración del paquete.

Nota: Los separadores de comentarios /** y */ deben estar presentes, pero los asteriscos iniciales en las líneas intermedias se pueden omitir.

/**
 * Proporciona las clases necesarias para crear un  
 * applet y las clases que un applet utiliza para 
 * comunicarse con su contexto de applet.
 * <p>
 * El framework de applets involucra dos entidades:
 * el applet y el contexto de applet.
 * Un applet es una ventana incrustable (ver la
 * clase {@link java.awt.Panel}) con algunos métodos
 * adicionales que el contexto de applet puede usar para
 * inicializar, iniciar y detener el applet.
 *
 * @since 1.0
 * @see java.awt
 */
package java.lang.applet;

El archivo package.html es un archivo HTML típico y no incluye una declaración de paquete. El contenido del archivo de comentarios del paquete está escrito en HTML con una excepción. El comentario de documentación no debe incluir los separadores de comentarios /** y */ ni los asteriscos iniciales. Al escribir el comentario, haz que la primera oración sea un resumen sobre el paquete y no pongas un título ni ningún otro texto entre la etiqueta <body> y la primera oración. Puedes incluir etiquetas de paquete. Todas las etiquetas de bloque deben aparecer después de la descripción principal. Si agregas una etiqueta @see en un archivo de comentarios de paquete, entonces debe tener un nombre completamente calificado.

Procesamiento del Archivo de Comentarios

Cuando se ejecuta el comando javadoc, busca el archivo de comentarios del paquete. Si se encuentra el archivo de comentarios del paquete, el comando javadoc hace lo siguiente:

•
Copia el comentario para su procesamiento. Para package.html, el comando javadoc copia todo el contenido entre las etiquetas HTML <body> y </body>. Puedes incluir una sección <head> para colocar una etiqueta <title>, una declaración de copyright del archivo fuente u otra información, pero nada de esto aparecerá en la documentación generada.
•
Procesa las etiquetas del paquete. Ver Etiquetas de Paquete.
•
Inserta el texto procesado al final de la página de resumen del paquete generada. Ver Java Platform, Standard Edition API Specification Overview en http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copia la primera oración del comentario del paquete a la parte superior de la página de resumen del paquete. El comando javadoc también agrega el nombre del paquete y esta primera oración a la lista de paquetes en la página de descripción general. Ver Java Platform, Standard Edition API Specification Overview en http://docs.oracle.com/javase/8/docs/api/overview-summary.html

El final de la oración se determina por las mismas reglas que se usan para el final de la primera oración de las descripciones principales de clases y miembros.

ARCHIVOS DE COMENTARIOS DE DESCRIPCIÓN GENERAL

Cada aplicación o conjunto de paquetes que estés documentando puede tener su propio comentario de documentación de descripción general que se mantiene en su propio archivo fuente, y que el comando javadoc fusiona en la página de descripción general generada. Típicamente incluyes en este comentario cualquier documentación que se aplique a toda la aplicación o conjunto de paquetes.

Puedes nombrar el archivo como quieras, por ejemplo, overview.html, y colocarlo en cualquier lugar. Una ubicación típica es en la parte superior del árbol de fuentes.

Por ejemplo, si los archivos fuente del paquete java.applet están contenidos en el directorio /home/user/src/java/applet, entonces podrías crear un archivo de comentarios de descripción general en /home/user/src/overview.html.

Puedes tener múltiples archivos de comentarios de descripción general para el mismo conjunto de archivos fuente en caso de que quieras ejecutar el comando javadoc varias veces en diferentes conjuntos de paquetes. Por ejemplo, podrías ejecutar el comando javadoc una vez con -private para documentación interna y otra vez sin esa opción para documentación pública. En este caso, podrías describir la documentación como pública o interna en la primera oración de cada archivo de comentarios de descripción general.

El contenido del archivo de comentarios de descripción general es un gran comentario de documentación escrito en HTML. Haz que la primera oración sea un resumen sobre la aplicación o el conjunto de paquetes. No pongas un título ni ningún otro texto entre la etiqueta <body> y la primera oración. Todas las etiquetas, excepto las etiquetas en línea, como la etiqueta {@link}, deben aparecer después de la descripción principal. Si agregas una etiqueta @see, entonces debe tener un nombre completamente calificado.

Cuando ejecutas el comando javadoc, especifica el nombre del archivo de comentarios de descripción general con la opción -overview. El archivo se procesa de manera similar a un archivo de comentarios de paquete. El comando javadoc hace lo siguiente:

•
Copia todo el contenido entre las etiquetas <body> y </body> para su procesamiento.
•
Procesa las etiquetas de descripción general que estén presentes. Ver Etiquetas de Descripción General.
•
Inserta el texto procesado al final de la página de descripción general generada. Ver Java Platform Standard Edition API Specification Overview en http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copia la primera oración del comentario de descripción general a la parte superior de la página de resumen de descripción general.

ARCHIVOS&#x00A0;SIN&#x00A0;PROCESAR

Tus archivos fuente pueden incluir cualquier archivo que quieras que el comando javadoc copie al directorio de destino. Estos archivos generalmente incluyen archivos gráficos, archivos de ejemplo de código fuente y clases de Java, y archivos HTML independientes con mucho contenido que abrumaría el comentario de documentación de un archivo fuente de Java típico.

Para incluir archivos sin procesar, colócalos en un directorio llamado doc-files. El directorio doc-files puede ser un subdirectorio de cualquier directorio de paquete que contenga archivos fuente. Puedes tener un subdirectorio doc-files para cada paquete.

Por ejemplo, si quieres incluir la imagen de un botón en la documentación de la clase java.awt.Button, entonces coloca el archivo de imagen en el directorio /home/user/src/java/awt/doc-files/. No coloques el directorio doc-files en /home/user/src/java/doc-files, porque java no es un paquete. No contiene archivos fuente.

Todos los enlaces a los archivos sin procesar deben incluirse en el código porque el comando javadoc no examina los archivos. El comando javadoc copia el directorio y todo su contenido al destino. El siguiente ejemplo muestra cómo podría verse el enlace en el comentario de documentación de Button.java:

/**
 * Este botón se ve así: 
 * <img src="doc-files/Button.gif">
 */

ARCHIVOS&#x00A0;DE&#x00A0;PRUEBA&#x00A0;Y&#x00A0;PLANTILLA

Puedes almacenar archivos de prueba y plantillas en el árbol de fuentes en el mismo directorio o en un subdirectorio del directorio donde residen los archivos fuente. Para evitar que los archivos de prueba y plantilla sean procesados, ejecuta el comando javadoc y pasa explícitamente nombres de archivos fuente individuales.

Los archivos de prueba son archivos fuente válidos y compilables. Los archivos de plantilla no son archivos fuente válidos y compatibles, pero a menudo tienen el sufijo .java.

Archivos de Prueba

Si quieres que tus archivos de prueba pertenezcan a un paquete sin nombre o a un paquete diferente al paquete en el que se encuentran los archivos fuente, entonces coloca los archivos de prueba en un subdirectorio debajo de los archivos fuente y dale al directorio un nombre inválido. Si colocas los archivos de prueba en el mismo directorio que las fuentes y llamas al comando javadoc con un argumento de línea de comandos que indique su nombre de paquete, entonces los archivos de prueba causarán advertencias o errores. Si los archivos están en un subdirectorio con un nombre inválido, entonces el directorio de archivos de prueba se omitirá y no se emitirán errores ni advertencias. Por ejemplo, para agregar archivos de prueba para archivos fuente en com.package1, colócalos en un subdirectorio con un nombre de paquete inválido. El siguiente nombre de directorio es inválido porque contiene un guion:

com/package1/test-files/

Si tus archivos de prueba contienen comentarios de documentación, entonces puedes configurar una ejecución separada del comando javadoc para producir documentación de archivos de prueba pasando sus nombres de archivos fuente de prueba con comodines, como com/package1/test-files/*.java.

El comando javadoc puede incluir los modificadores public, protected, private, abstract, final, static, transient y volatile, pero no synchronized ni native. Los modificadores synchronized y native se consideran detalles de implementación y no forman parte de la especificación de la

API.

En lugar de depender de la palabra clave synchronized, las APIs deben documentar su semántica de concurrencia en la descripción principal del comentario. Por ejemplo, una descripción podría ser: Una enumeración única no puede ser utilizada por múltiples hilos de forma concurrente. El documento no debe describir cómo lograr estas semánticas. Como otro ejemplo, aunque la opción Hashtable debe ser segura para hilos, no hay razón para especificar que esto se logra sincro

FUENTE

Colocación de los

Los comentarios de documentación solo se reconocen cuando se colocan inmediatamente antes de las declaraciones de clase, interfaz, constructor, método o campo. Los comentarios de documentación colocados en el cuerpo de un método se ignoran. El comando javadoc reconoce solo un comentario de documentación por declaración. Ver Dónde se Pueden Usar las

Partes de los

Comentarios

Un comentario de documentación tiene una descripción principal seguida de una sección de etiquetas. La descripción principal comienza después del delimitador inicial /** y continúa hasta la sección de etiquetas. La sección de etiquetas comienza con la primera etiqueta de bloque, que está definida por el primer carácter @ que comienza una línea (ignorando asteriscos iniciales, espacios en blanco y el separador inicial /**). Es posible tener un comentario con solo una sección de etiquetas y sin descripción principal. La descripción principal no puede continuar después de que comienza la sección de etiquetas. El argumento de una etiqueta puede abarcar múltiples líneas. Puede haber cualquier número de etiquetas, y algunos tipos de etiquetas pueden repetirse mientras que otras no. Por ejemplo, esta etiqueta @see comienza la sección de

etiquetas:

Etiquetas de Bloque y en

Línea

Una etiqueta es una palabra clave especial dentro de un comentario de documentación que el comando javadoc procesa. Hay dos tipos de etiquetas: etiquetas de bloque, que aparecen como una etiqueta @tag (también conocidas como etiquetas independientes), y etiquetas en línea, que aparecen dentro de llaves, como una etiqueta {@tag}. Para ser interpretada, una etiqueta de bloque debe aparecer al comienzo de una línea, ignorando asteriscos iniciales, espacios en blanco y el separador (/**). Esto significa que puede usar el carácter @ en otro lugar del texto y no será interpretado como el inicio de una etiqueta. Si desea comenzar una línea con el carácter @ y que no sea interpretado, use la entidad HTML &. Cada etiqueta de bloque tiene texto asociado, que incluye cualquier texto que sigue a la etiqueta hasta, pero sin incluir, la siguiente etiqueta o el final del comentario de documentación. Este texto asociado puede abarcar múltiples líneas. Se permite e interpreta una etiqueta en línea en cualquier lugar donde se permita texto. El siguiente ejemplo contiene la etiqueta de bloque @deprecated y la etiqueta en línea {@link}. Ver Etiquetas

Javadoc.

Asteriscos

Iniciales

Cuando el comando javadoc analiza un comentario de documentación, los asteriscos iniciales (*) de cada línea se descartan, y los espacios y tabulaciones que preceden a los asteriscos iniciales (*) también se descartan. Si omite el asterisco inicial en una línea, el espacio en blanco inicial ya no se elimina, de modo que puede pegar ejemplos de código directamente en un comentario de documentación dentro de una etiqueta <PRE> con su indentación preservada. La primera oración de cada comentario de documentación debe ser una oración de resumen que contenga una descripción concisa pero completa de la entidad declarada. El comando javadoc copia esta primera oración al resumen del miembro en la parte superior de la página

HTML.

MÉTODOS

El comando javadoc permite la herencia de comentarios de métodos en clases e interfaces para completar texto faltante o para heredar explícitamente comentarios de métodos. Los constructores, campos y clases anidadas no heredan comentarios de

documentación.

Nota: El archivo fuente de un método heredado debe estar en la ruta especificada por la opción -sourcepath para que el comentario de documentación esté disponible para copiar. Ni la clase ni su paquete necesitan pasarse en la línea de comandos. Esto contrasta con la versión 1.3.y versiones anteriores, donde la clase tenía que ser una clase

documentada.

Completar Texto

Faltante

Cuando falta una descripción principal, o una etiqueta @return, @param o @throws en un comentario de método, el comando javadoc copia la descripción principal o el comentario de la etiqueta correspondiente del método que sobrescribe o implementa (si existe). Ver Herencia de Comentarios de

Métodos.

Cuando falta una etiqueta @param para un parámetro particular, el comentario para ese parámetro se copia del método más arriba en la jerarquía de herencia. Cuando falta una etiqueta @throws para una excepción particular, la etiqueta @throws se copia solo cuando esa excepción está

declarada.

Este comportamiento contrasta con la versión 1.3 y anteriores, donde la presencia de cualquier descripción principal o etiqueta impedía que todos los comentarios fueran

heredados.

CLASIFICACIÓN Y HERENCIA DE INTERFACES

La herencia de comentarios ocurre en todos los casos posibles de herencia de clases e interfaces:

•
Cuando un método en una clase reemplaza a un método en una superclase
•
Cuando un método en una interfaz reemplaza a un método en una superinterfaz
•
Cuando un método en una clase implementa un método en una interfaz

En los dos primeros casos, el comando javadoc genera el subtítulo Overrides en la documentación del método que reemplaza. Se incluye un enlace al método que se está reemplazando, independientemente de si el comentario se hereda o no.

En el tercer caso, cuando un método en una clase especificada implementa un método en una interfaz, el comando javadoc genera el subtítulo Specified by en la documentación del método que reemplaza. Se incluye un enlace al método que se está implementando, independientemente de si el comentario se hereda o no.

ALGORITMO DE COMENTARIOS DE MÉTODOS

Si un método no tiene un comentario de documentación, o tiene una etiqueta {@inheritDoc}, entonces el comando javadoc utiliza el siguiente algoritmo para buscar un comentario aplicable. El algoritmo está diseñado para encontrar el comentario de documentación aplicable más específico y dar preferencia a las interfaces sobre las superclases:

1.
Busca en cada interfaz directamente implementada (o extendida) en el orden en que aparecen después de la palabra implements (o extends) en la declaración del método. Utiliza el primer comentario de documentación encontrado para este método.
2.
Si el Paso 1 no encontró un comentario de documentación, entonces aplica recursivamente todo este algoritmo a cada interfaz directamente implementada (o extendida) en el mismo orden en que se examinaron en el Paso 1.
3.
Cuando el Paso 2 no encuentra un comentario de documentación y esta es una clase distinta de la clase Object, pero no una interfaz:
1.
Si la superclase tiene un comentario de documentación para este método, úsalo.
2.
Si el Paso 3a no encontró un comentario de documentación, entonces aplica recursivamente todo este algoritmo a la superclase.

ETIQUETAS DE JAVADOC

El comando javadoc analiza etiquetas especiales cuando se incrustan dentro de un comentario de documentación de Java. Las etiquetas javadoc te permiten autogenerar una API completa y bien formateada a partir de tu código fuente. Las etiquetas comienzan con un signo arroba (@) y distinguen entre mayúsculas y minúsculas. Deben escribirse con las letras mayúsculas y minúsculas como se muestra. Una etiqueta debe comenzar al principio de una línea (después de cualquier espacio inicial y un asterisco opcional), o se trata como texto. Por convención, las etiquetas con el mismo nombre se agrupan. Por ejemplo, agrupa todas las etiquetas @see. Para obtener más información, consulta Dónde se pueden usar las etiquetas.

Las etiquetas tienen los siguientes tipos:

•
Etiquetas de bloque: Coloca las etiquetas de bloque solo en la sección de etiquetas que sigue a la descripción. Las etiquetas de bloque tienen el formato: @tag.
•
Etiquetas en línea: Coloca las etiquetas en línea en cualquier lugar de la descripción principal o en los comentarios de las etiquetas de bloque. Las etiquetas en línea se encierran entre llaves: {@tag}.

Para etiquetas personalizadas, consulta -tag tagname:Xaoptcmf:"taghead". Consulta también Dónde se pueden usar las etiquetas.

DESCRIPCIÓN DE ETIQUETAS

@author nombre-texto
Introducido en JDK 1.0

Agrega una entrada de Autor con el texto de nombre especificado a los documentos generados cuando se usa la opción -author. Un comentario de documentación puede contener múltiples etiquetas @author. Puedes especificar un nombre por etiqueta @author o múltiples nombres por etiqueta. En el primer caso, el comando javadoc inserta una coma (,) y un espacio entre los nombres. En el segundo caso, todo el texto se copia al documento generado sin ser analizado. Por lo tanto, puedes usar múltiples nombres por línea si deseas un separador de nombres localizado que no sea una coma. Consulta @author en Cómo escribir comentarios de documentación para la herramienta Javadoc en http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@author

{@code texto}
Introducido en JDK 1.5

Equivalente a <code>{@literal}</code>.

Muestra texto en fuente de código sin interpretar el texto como marcado HTML o etiquetas Javadoc anidadas. Esto te permite usar corchetes angulares regulares (< y >) en lugar de las entidades HTML (&lt; y &gt;) en los comentarios de documentación, como en los tipos de parámetros (<Object>), desigualdades (3 < 4) o flechas (<-). Por ejemplo, el texto del comentario de documentación {@code A<B>C} se muestra sin cambios en la página HTML generada como A<B>C. Esto significa que <B> no se interpreta como negrita y está en fuente de código. Si deseas la misma funcionalidad sin la fuente de código, usa la etiqueta {@literal}.

@deprecated texto-obsoleto
Introducido en JDK 1.0

Agrega un comentario que indica que esta API ya no debe usarse (incluso si puede seguir funcionando). El comando javadoc mueve el texto-obsoleto antes de la descripción principal, colocándolo en cursiva y precedido por una advertencia en negrita: Deprecated. Esta etiqueta es válida en todos los comentarios de documentación: resumen, paquete, clase, interfaz, constructor, método y campo.

La primera oración del texto obsoleto debe indicar al usuario cuándo se deprecó la API y qué usar como reemplazo. El comando javadoc copia la primera oración a la sección de resumen y al índice. Las oraciones subsiguientes también pueden explicar por qué se deprecó. Debes incluir una etiqueta {@link} (para Javadoc 1.2 o posterior) que apunte a la API de reemplazo.

Usa la etiqueta @deprecated annotation para marcar un elemento del programa como obsoleto. Consulta Cómo y cuándo marcar como obsoleto las APIs en http://docs.oracle.com/javase/8/docs/technotes/guides/javadoc/deprecation/deprecation.html

Consulta también @deprecated en Cómo escribir comentarios de documentación para la herramienta Javadoc en http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@deprecated

{@docRoot}
Introducido en JDK 1.3

Representa la ruta relativa a la raíz del directorio del documento generado (destino) desde cualquier página generada. Esta etiqueta es útil cuando deseas incluir un archivo, como una página de derechos de autor o el logotipo de la empresa, al que deseas hacer referencia desde todas las páginas generadas. Es común enlazar a la página de derechos de autor desde la parte inferior de cada página.

Esta etiqueta {@docRoot} se puede usar tanto en la línea de comandos como en un comentario de documentación. Esta etiqueta es válida en todos los comentarios de documentación: resumen, paquete, clase, interfaz, constructor, método y campo, e incluye la parte de texto de cualquier etiqueta (como las etiquetas @return, @param y @deprecated).

•
En la línea de comandos, donde se definen la cabecera, el pie de página o la parte inferior: javadoc -bottom '<a href="{@docRoot}/copyright.html">Copyright</a>'.

Cuando usas la etiqueta {@docRoot} de esta manera en un archivo de compilación, algunos programas makefile requieren una forma especial de escapar los caracteres de llave {}. Por ejemplo, la versión 5.2 de MAKE de Inprise que se ejecuta en Windows requiere llaves dobles: {{@docRoot}}. También requiere comillas dobles (en lugar de simples) para encerrar los argumentos de opciones como la opción -bottom (omitiendo las comillas alrededor del argumento href).

•
En un comentario de documentación: 
/**
 * Consulta los <a href="{@docRoot}/copyright.html">Derechos de autor</a>.
 */

Esta etiqueta es necesaria porque los documentos generados están en directorios jerárquicos, tan profundos como el número de subpaquetes. La expresión: <a href="{@docRoot}/copyright.html"> se resuelve a <a href="../../copyright.html"> para java/lang/Object.java y <a href="../../../copyright.html"> para java/lang/ref/Reference.java.

@exception nombre-clase descripción
Introducido en JDK 1.0

Idéntica a la etiqueta @throws. Consulta @throws nombre-clase descripción.

{@inheritDoc}
Introducido en JDK 1.4

Hereda (copia) la documentación de la clase heredable o interfaz implementable más cercana al comentario de documentación actual en la ubicación de esta etiqueta. Esto te permite escribir comentarios más generales en la parte superior del árbol de herencia y escribir alrededor del texto copiado.

Esta etiqueta solo es válida en los siguientes lugares en un comentario de documentación:

•
En el bloque de descripción principal de un método. En este caso, la descripción principal se copia de una clase o interfaz superior en la jerarquía.
•
En los argumentos de texto de las etiquetas @return, @param y @throws de un método. En este caso, el texto de la etiqueta se copia de la etiqueta correspondiente superior en la jerarquía.

Consulta Herencia de comentarios de métodos para obtener una descripción de cómo se encuentran los comentarios en la jerarquía de herencia. Ten en cuenta que si esta etiqueta falta, el comentario se hereda o no automáticamente según las reglas descritas en esa sección.

{@link paquete.clase#miembro etiqueta}
Introducido en JDK 1.2

Inserta un enlace en línea con una etiqueta de texto visible que apunta a la documentación del paquete, clase o nombre de miembro especificado de una clase referenciada. Esta etiqueta es válida en todos los comentarios de documentación: resumen, paquete, clase, interfaz, constructor, método y campo, incluida la parte de texto de cualquier etiqueta, como las etiquetas @return, @param y @deprecated. Consulta @link en Cómo escribir comentarios de documentación para la herramienta Javadoc en http://www.oracle.com/tech

• {@link package.class#member label}
This tag is similar to the @see tag. Both tags require the same references and accept the same syntax for package.class#member and label. The main difference is that the {@link} tag generates an inline link rather than placing the link in the See Also section. The {@link} tag begins and ends with braces to separate it from the rest of the inline text. If you need to use the right brace (}) inside the label, then use the HTML entity notation &#125;.

There is no limit to the number of {@link} tags allowed in a sentence. You can use this tag in the main description part of any documentation comment or in the text portion of any tag, such as the @deprecated, @return or @param tags.

For example, here is a comment that refers to the getComponentAt(int, int) method:

Use the {@link #getComponentAt(int, int) getComponentAt} method.

From this code, the standard doclet generates the following HTML (assuming it refers to another class in the same package):

Use the <a href="Component.html#getComponentAt(int, int)">getComponentAt</a> method.

The previous line appears on the web page as:

Use the getComponentAt method.
• {@linkplain package.class#member label}
Introduced in JDK 1.4

Behaves the same as the {@link} tag, except the link label is displayed in plain text rather than code font. Useful when the label is plain text. For example, Refer to {@linkplain add() the overridden method}. displays as: Refer to the overridden method.

• {@literal text}
Introduced in JDK 1.5

Displays text without interpreting the text as HTML markup or nested Javadoc tags. This enables you to use angle brackets (< and >) instead of the HTML entities (&lt; and &gt;) in documentation comments, such as in parameter types (<Object>), inequalities (3 < 4), or arrows (<-). For example, the documentation comment text {@literal A<B>C} displays unchanged in the generated HTML page in your browser, as A<B>C. The <B> is not interpreted as bold (and it is not in code font). If you want the same functionality with the text in code font, then use the {@code} tag.

• @param parameter-name description
Introduced in JDK 1.0

Adds a parameter with the specified parameter-name followed by the specified description to the Parameters section. When writing the documentation comment, you can continue the description onto multiple lines. This tag is valid only in a documentation comment for a method, constructor, or class. See @param in How to Write Doc Comments for the Javadoc Tool at http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@param

The parameter-name can be the name of a parameter in a method or constructor, or the name of a type parameter of a class, method, or constructor. Use angle brackets around this parameter name to specify the use of a type parameter.

Example of a type parameter of a class:

/**
         * @param <E> Type of element stored in a list
         */
        public interface List<E> extends Collection<E> {
        }

Example of a type parameter of a method:

/**
         * @param string  the string to be converted
         * @param type    the type to convert the string to
         * @param <T>     the type of the element
         * @param <V>     the value of the element
         */
        <T, V extends T> V convert(String string, Class<T> type) {
        }
• @return description
Introduced in JDK 1.0

Adds a Returns section with the description text. This text should describe the return type and permissible range of values. This tag is valid only in a documentation comment for a method. See @return in How to Write Doc Comments for the Javadoc Tool at http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@return

• @see reference
Introduced in JDK 1.0

Adds a See Also heading with a link or text entry that points to a reference. A documentation comment can contain any number of @see tags, which are all grouped under the same heading. The @see tag has three variations. The form is the most common. This tag is valid in any documentation comment: overview, package, class, interface, constructor, method, or field. For inserting an inline link within a sentence to a package, class, or member, see {@link}.

Form 1. The @see string tag form adds a text entry for string. No link is generated. The string is a book or other reference to information not available by URL. The javadoc command distinguishes this from the previous cases by searching for a double quotation mark (") as the first character. For example, @see "The Java Programming Language" that generates the following text:

See Also:

"The Java Programming Language"

Form 2. The @see <a href="URL#value">label</a> form adds a link as defined by URL#value. The URL#value parameter is a relative or absolute URL. The javadoc command distinguishes this from other cases by searching for a less-than symbol (<) as the first character. For example, @see <a href="spec.html#section">Java Spec</a> generates the following link:

See Also:

Java Spec

Form 3. The @see package.class#member label form adds a link with a visible text label that points to the documentation for the specified name in the Java Language that is referenced. The label is optional. If the label is omitted, then the name appears instead as visible text, suitably shortened. Use the -noqualifier option to globally remove the package name from this visible text. Use the label when you want the visible text to be different from the autogenerated visible text. See How a Name Appears.

In Java SE 1.2 only, the name but not the label automatically appears in <code> HTML tags. Starting with Java SE 1.2.2, the <code> tag is always included around the visible text, whether or not a label is used.

•
package.class#member is any valid program element name that is referenced, such as a package, class, interface, constructor, method or field name, except that the character ahead of the member name should be a number sign (#). The class represents any top-level or nested class or interface. The member represents any constructor, method, or field (not a nested class or interface). If this name is in the documented classes, then the javadoc command create a link to it. To create links to external referenced classes, use the -link option. Use either of the other two @see tag forms to refer to the documentation of a name that does not belong to a referenced class. See Specify a Name.

Note: External referenced classes are classes that are not passed into the javadoc command on the command line. Links in the generated documentation to external referenced classes are called external references or external links. For example, if you run the javadoc command on only the java.awt package, then any class in java.lang, such as Object, is an external referenced class. Use the -link and -linkoffline options to link to external referenced classes. The source comments of external referenced classes are not available to the javadoc command run.

•
label is optional text that is visible as the link label. The label can contain white space. If label is omitted, then package.class.member appears, suitably shortened relative to the current class and package. See How a Name Appears.
•
A space is the delimiter between package.class#member and label. A space inside parentheses does not indicate the start of a label, so spaces can be used between parameters in a method.

In the following example, an @see tag (in the Character class) refers to the equals method in the String class. The tag includes both arguments: the name String#equals(Object) and the label equals.

/**
         * @see String#equals(Object) equals
         */

        <dd><a href="../../java/lang/String#equals(java.lang.Object)"><code>equals</code></a>
        </dl>

The previous code looks similar to the following in a browser, where the label is the visible link text:

Orden de búsqueda para la etiqueta @see

El comando javadoc procesa una etiqueta @see que aparece en un archivo fuente, archivo de paquete o archivo de vista general. En los dos últimos archivos, debe calificar completamente el nombre que proporciona con la etiqueta @see. En un archivo fuente, puede especificar un nombre que esté completamente calificado o parcialmente calificado.

El siguiente es el orden de búsqueda para la etiqueta @see.

1.
La clase o interfaz actual.
2.
Cualquier clase e interfaz contenedora, buscando primero la más cercana.
3.
Cualquier superclase y superinterfaz, buscando primero la más cercana.
4.
El paquete actual.
5.
Cualquier paquete, clase e interfaz importados, buscando en el orden de la declaración import.

El comando javadoc continúa buscando recursivamente en los elementos 1-3 para cada clase que encuentra hasta que encuentra una coincidencia. Es decir, después de buscar en la clase actual y su clase contenedora E, busca en las superclases de E antes que las clases contenedoras de E. En los elementos 4 y 5, el comando javadoc no busca clases o interfaces dentro de un paquete en ningún orden específico (ese orden depende del compilador particular). En el elemento 5, el comando javadoc busca en java.lang porque este es importado por todos los programas.

Cuando el comando javadoc encuentra una etiqueta @see en un archivo fuente que no está completamente calificado, busca el nombre especificado en el mismo orden en que lo haría el compilador Java, excepto que el comando javadoc no detecta ciertas ambigüedades de espacio de nombres porque asume que el código fuente está libre de estos errores. Este orden de búsqueda se define formalmente en la Especificación del Lenguaje Java. El comando javadoc busca ese nombre a través de todas las clases y paquetes relacionados e importados. En particular, busca en este orden:

1.
La clase o interfaz actual.
2.
Cualquier clase e interfaz contenedora, buscando primero la más cercana.
3.
Cualquier superclase y superinterfaz, buscando primero la más cercana.
4.
El paquete actual.
5.
Cualquier paquete, clase e interfaz importados, buscando en el orden de las declaraciones import.

El comando javadoc no necesariamente busca en las subclases, ni buscará en otros paquetes incluso cuando su documentación se esté generando en la misma ejecución. Por ejemplo, si la etiqueta @see está en la clase java.awt.event.KeyEvent y se refiere a un nombre en el paquete java.awt, entonces el comando javadoc no busca en ese paquete a menos que esa clase lo importe.

Cómo aparece un nombre

Si se omite etiqueta, entonces aparece paquete.clase.miembro. En general, se acorta adecuadamente en relación con la clase y el paquete actuales. Acortado significa que el comando javadoc muestra solo el nombre mínimo necesario. Por ejemplo, si el método String.toUpperCase() contiene referencias a un miembro de la misma clase y a un miembro de una clase diferente, entonces el nombre de la clase se muestra solo en este último caso, como se muestra en la siguiente lista. Use la opción -noqualifier para eliminar globalmente los nombres de paquetes.

Tipo de referencia: la etiqueta @see se refiere a un miembro de la misma clase, mismo paquete
Ejemplo en: @see String#toLowerCase()
Aparece como: toLowerCase() - omite los nombres de paquete y clase

Tipo de referencia: la etiqueta @see se refiere a un miembro de una clase diferente, mismo paquete
Ejemplo en: @see Character#toLowerCase(char)
Aparece como: Character.toLowerCase(char) - omite el nombre del paquete, incluye el nombre de la clase

@serial descripción-campo | include | exclude
Introducido en JDK 1.2

Usado en el comentario de documentación para un campo serializable predeterminado. Consulte Documentar campos y datos serializables para una clase en http://docs.oracle.com/javase/8/docs/platform/serialization/spec/serial-arch.html#5251

Consulte también los Criterios de Oracle para Incluir Clases en la Especificación de Forma Serializada en http://www.oracle.com/technetwork/java/javase/documentation/serialized-criteria-137781.html

Una descripción-campo opcional debe explicar el significado del campo y enumerar los valores aceptables. Cuando sea necesario, la descripción puede abarcar varias líneas. El doclet estándar agrega esta información a la página de forma serializada. Consulte Páginas de referencia cruzada.

Si un campo serializable se agregó a una clase después de que la clase se hiciera serializable, entonces se debe agregar una declaración a su descripción principal para identificar en qué versión se agregó.

Los argumentos include y exclude identifican si una clase o paquete debe incluirse o excluirse de la página de forma serializada. Funcionan de la siguiente manera:

•
Una clase pública o protegida que implementa Serializable se incluye a menos que esa clase (o su paquete) esté marcada con la etiqueta @serial exclude.
•
Una clase privada o package-private que implementa Serializable se excluye a menos que esa clase (o su paquete) esté marcada con la etiqueta @serial include.

Por ejemplo, el paquete javax.swing está marcado con la etiqueta @serialexclude en package.html o package-info.java. La clase pública java.security.BasicPermission está marcada con la etiqueta @serial exclude. La clase package-private java.util.PropertyPermissionCollection está marcada con la etiqueta @serial include.

La etiqueta @serial a nivel de clase anula la etiqueta @serial a nivel de paquete.

@since texto-desde
Introducido en JDK 1.1

Añade un encabezado Since con el valor texto-desde especificado a la documentación generada. El texto no tiene estructura interna especial. Esta etiqueta es válida en cualquier comentario de documentación: resumen, paquete, clase, interfaz, constructor, método o campo. Esta etiqueta significa que este cambio o característica ha existido desde la versión del software especificada por el valor texto-desde, por ejemplo: @since 1.5.

Para el código fuente de la plataforma Java, la etiqueta @since indica la versión de la especificación de la API de la plataforma Java, que no es necesariamente cuándo se añadió el código fuente a la implementación de referencia. Se permiten múltiples etiquetas @since y se tratan como múltiples etiquetas @author. Podrías usar múltiples etiquetas cuando el elemento del programa es utilizado por más de una API.

@throws nombre-de-clasedescripción
Introducido en JDK 1.2

Se comporta igual que la etiqueta @exception. Ver @throws en Cómo Escribir Comentarios de Documentación para la Herramienta Javadoc en http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@exception

La etiqueta @throws añade un subencabezado Throws a la documentación generada, con el nombre-de-clase y el texto de la descripción. El nombre-de-clase es el nombre de la excepción que podría ser lanzada por el método. Esta etiqueta solo es válida en el comentario de documentación de un método o constructor. Si esta clase no está completamente especificada, entonces el comando javadoc usa el orden de búsqueda para buscar esta clase. Múltiples etiquetas @throws pueden ser usadas en un comentario de documentación especificado para las mismas o diferentes excepciones. Ver Orden de Búsqueda para la Etiqueta @see.

Para asegurar que todas las excepciones verificadas sean documentadas, cuando una etiqueta @throws no existe para una excepción en la cláusula throws, el comando javadoc añade esa excepción a la salida HTML (sin descripción) como si hubiera sido documentada con la etiqueta @throws.

La documentación @throws se copia de un método sobrescrito a una subclase solo cuando la excepción se declara explícitamente en el método sobrescrito. Lo mismo aplica para la copia de un método de interfaz a un método implementador. Puedes usar la etiqueta {@inheritDoc} para forzar que la etiqueta @throws herede la documentación.

{@value paquete.clase#campo}
Introducido en JDK 1.4

Muestra los valores de las constantes. Cuando la etiqueta {@value} se usa sin argumento en el comentario de documentación de un campo estático, muestra el valor de esa constante:

Los valores de estas constantes también se muestran en Valores de Campo Constantes en http://docs.oracle.com/javase/8/docs/api/constant-values.html

@version texto-versión
Introducido en JDK 1.0

Añade un subencabezado Version con el valor texto-versión especificado a los documentos generados cuando se usa la opción -version. Esta etiqueta está destinada a contener el número de versión actual del software del que forma parte este código, a diferencia de la etiqueta @since, que contiene el número de versión en la que se introdujo este código. El valor texto-versión no tiene estructura interna especial. Ver @version en Cómo Escribir Comentarios de Documentación para la Herramienta Javadoc en http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@version

Un comentario de documentación puede contener múltiples etiquetas @version. Cuando tenga sentido, puedes especificar un número de versión por etiqueta @version o múltiples números de versión por etiqueta. Por lo tanto, puedes usar múltiples nombres por línea cuando quieras un separador de nombre localizado distinto de una coma.

DÓNDE SE PUEDEN USAR LAS ETIQUETAS

Las siguientes secciones describen dónde se pueden usar las etiquetas. Ten en cuenta que las siguientes etiquetas se pueden usar en todos los comentarios de documentación: @see, @since, @deprecated, {@link}, {@linkplain} y {@docroot}.

ETIQUETAS&#x00A0;DE&#x00A0;RESUMEN

Las etiquetas de resumen son etiquetas que pueden aparecer en el comentario de documentación de la página de resumen (que reside en el archivo fuente típicamente llamado overview.html). De forma similar a cualquier otro comentario de documentación, estas etiquetas deben aparecer después de la descripción principal.

Nota: La etiqueta {@link} tiene un error en los documentos de resumen en Java SE 1.2. El texto aparece correctamente pero no tiene enlace. La etiqueta {@docRoot} no funciona actualmente en documentos de resumen.

Las etiquetas de resumen son las siguientes:

-Xdoclint:(all|none|[-]<grupo>)

Informa advertencias sobre referencias incorrectas, falta de accesibilidad y comentarios Javadoc faltantes, e informa errores de sintaxis Javadoc inválida y etiquetas HTML faltantes.

Esta opción permite que el comando javadoc verifique todos los comentarios de documentación incluidos en la salida generada. Como siempre, puede seleccionar qué elementos incluir en la salida generada con las opciones estándar -public, -protected, -package y -private.

Cuando se habilita -Xdoclint, informa problemas con mensajes similares a los del comando javac. El comando javadoc imprime un mensaje, una copia de la línea de código fuente y un cursor que apunta a la posición exacta donde se detectó el error. Los mensajes pueden ser advertencias o errores, según su gravedad y la probabilidad de que causen un error si la documentación generada se pasa por un validador. Por ejemplo, las referencias incorrectas o los comentarios Javadoc faltantes no hacen que el comando javadoc genere HTML inválido, por lo que estos problemas se informan como advertencias. Los errores de sintaxis o las etiquetas HTML finales faltantes hacen que el comando javadoc genere una salida inválida, por lo que estos problemas se informan como errores.

Por defecto, la opción -Xdoclint está habilitada. Deshabilítela con la opción -Xdoclint:none.

Cambie lo que informa la opción -Xdoclint con las siguientes opciones:

•
-Xdoclint none : deshabilita la opción -Xdoclint
•
-Xdoclintgrupo : habilita las comprobaciones de grupo
•
-Xdoclint all : habilita todos los grupos de comprobaciones
•
-Xdoclint all,-grupo : habilita todas excepto las comprobaciones de grupo

La variable grupo tiene uno de los siguientes valores:

•
accessibility : Comprueba los problemas que detectaría un verificador de accesibilidad (por ejemplo, que no se especifiquen atributos de título o resumen en una etiqueta <table>).
•
html : Detecta problemas de HTML de alto nivel, como colocar elementos de bloque dentro de elementos en línea, o no cerrar elementos que requieren una etiqueta de cierre. Las reglas se derivan de la Especificación HTML 4.01. Este tipo de comprobación permite que el comando javadoc detecte problemas de HTML que muchos navegadores podrían aceptar.
•
missing : Comprueba los comentarios o etiquetas Javadoc faltantes (por ejemplo, un comentario o clase faltante, o una etiqueta @return o similar faltante en un método).
•
reference : Comprueba los problemas relacionados con las referencias a elementos de la API de Java desde etiquetas Javadoc (por ejemplo, elemento no encontrado en @see, o un nombre incorrecto después de @param).
•
syntax : Comprueba problemas de bajo nivel como corchetes angulares no escapados (< y >) y ampersands (&) y etiquetas Javadoc inválidas.

Puede especificar la opción -Xdoclint varias veces para habilitar la opción de verificar errores y advertencias en múltiples categorías. Alternativamente, puede especificar múltiples categorías de error y advertencia utilizando las opciones precedentes. Por ejemplo, utilice cualquiera de los siguientes comandos para verificar los problemas de HTML, sintaxis y accesibilidad en el archivo nombre_archivo.

javadoc -Xdoclint:html -Xdoclint:syntax -Xdoclint:accessibility nombre_archivo
javadoc -Xdoclint:html,syntax,accessibility nombre_archivo

Nota: El comando javadoc no garantiza la completitud de estas comprobaciones. En particular, no es un verificador de cumplimiento HTML completo. El objetivo de la opción -Xdoclint es permitir que el comando javadoc informe la mayoría de los errores comunes.

2. Opciones de la línea de comandos

Esta sección detalla las opciones de la línea de comandos disponibles para el comando javadoc.

-tag tagname

Indica al generador de documentación que incluya el comentario de una etiqueta de nivel de API en la página de documentación que genera. Las etiquetas se definen en la especificación del lenguaje Java. Por defecto, se incluyen las etiquetas: author, deprecated, exception, since, see, serial, throws, version. Cada etiqueta está formateada de una manera específica. Si una etiqueta no tiene un formato específico, entonces el texto se mostrará tal como se ingresó. Para más información, ver Comentarios de documentación aquí.

La opción -tag tagname permite que el programador agregue etiquetas personalizadas o cambie el comportamiento de etiquetas estándar. Para ver un ejemplo, consulte Taglet Overview.

Para omitir una etiqueta estándar de los resultados, use el signo de exclamación (!). Por ejemplo, para omitir la etiqueta author, use: -tag !author.

Para añadir la etiqueta return a la documentación, use -tag return. Para añadir la etiqueta todo, use -tag todo. También puede especificar etiquetas personalizadas. Por ejemplo, si desea documentar el código para fines de depuración y ha creado la etiqueta @bug, puede usar la opción de línea de comandos: -tag bug.

A veces, es necesario incluir los argumentos de una etiqueta. Por ejemplo, la etiqueta @param tiene un argumento (el nombre del parámetro). Para añadir el argumento a la documentación, use el signo de más (+). Por ejemplo, para incluir el argumento de la etiqueta param, use: -tag +param.

Puede especificar un argumento para cada etiqueta. Use una combinación de los caracteres ! y + para definir el comportamiento de la etiqueta. Por ejemplo, para omitir la etiqueta author pero incluir el argumento de la etiqueta param, use: -tag !author +param.

Por defecto, el generador de documentación genera los comentarios de las etiquetas, pero no los argumentos. Sin embargo, si una etiqueta tiene un argumento, se puede indicar a javadoc que genere el argumento usando la opción +tag. Por ejemplo, si usa la etiqueta @param en sus comentarios de documentación, puede hacer que el nombre del parámetro se genere de manera predeterminada mediante el uso de la opción +param.

Una etiqueta puede tener un número arbitrario de argumentos. La etiqueta @param, por ejemplo, tiene dos argumentos: el nombre del parámetro y la descripción del parámetro. Por defecto, la etiqueta @param solo tiene un argumento, el nombre del parámetro. Para incluir ambos argumentos, use -tag +param.

Si desea agregar una etiqueta personalizada a la documentación generada, puede usar la opción -tag. Sin embargo, si la etiqueta personalizada tiene argumentos, debe utilizar la opción -tag junto con el nombre completo de la clase que implementa la etiqueta y el número de argumentos de texto que tiene la etiqueta. La etiqueta también define el comportamiento de la documentación que se genera. La etiqueta acepta dichos argumentos, los procesa y genera la salida. Para documentación extensa con ejemplos de etiquetas, consulte: Taglet Overview en http://docs.oracle.com/javase/8/docs/technotes/guides/javadoc/taglet/overview.html

-taglet overview

La etiqueta -taglet se utiliza para especificar un generador de documentación personalizado (taglet) que se utilizará para generar la documentación de una etiqueta específica. Se debe usar el nombre completamente calificado para el valor de la clase. Esta etiqueta también define el número de argumentos de texto que tiene la etiqueta personalizada. La etiqueta acepta dichos argumentos, los procesa y genera la salida. Para documentación extensa con ejemplos de etiquetas, consulte: Taglet Overview en http://docs.oracle.com/javase/8/docs/technotes/guides/javadoc/taglet/overview.html

Las etiquetas son útiles para etiquetas de bloque o en línea. Pueden tener cualquier número de argumentos e implementar un comportamiento personalizado, como poner el texto en negrita, formatear viñetas, escribir el texto en un archivo o iniciar otros procesos. Las etiquetas solo pueden determinar dónde debe aparecer una etiqueta y en qué forma. Todas las demás decisiones son tomadas por el generador de documentación. Una etiqueta no puede hacer cosas como eliminar un nombre de clase de la lista de clases incluidas. Sin embargo, puede ejecutar efectos secundarios, como imprimir el texto de la etiqueta en un archivo o activar otro proceso. Utilice la opción -tagletpath para especificar la ruta a la etiqueta. El siguiente ejemplo inserta la etiqueta To Do después de Parameters y antes de Throws en las páginas generadas. Alternativamente, puede usar la opción -taglet en lugar de su opción -tag, pero eso podría ser difícil de leer.

-taglet com.sun.tools.doclets.ToDoTaglet
-tagletpath /home/taglets 
-tag return
-tag param
-tag todo
-tag throws
-tag see
-tagletpath tagletpathlist

Especifica las rutas de búsqueda para encontrar los archivos de clase de las etiquetas. La tagletpathlist puede contener múltiples rutas separándolas con dos puntos (:). El comando javadoc busca en todos los subdirectorios de las rutas especificadas.
-docfilesubdirs

Habilita la copia profunda de los directorios doc-files. Los subdirectorios y todo su contenido se copian recursivamente al destino. Por ejemplo, el directorio doc-files/example/images y todo su contenido se copiarían. También hay una opción para excluir subdirectorios.
-excludedocfilessubdir name1:name2

Excluye cualquier subdirectorio de doc-files con los nombres especificados. Esto evita la copia de SCCS y otros subdirectorios de control de código fuente.
-noqualifier all | packagename1:packagename2...

Omite los nombres de paquete calificadores de los nombres de clase en la salida. El argumento de la opción -noqualifier es all (se omiten todos los calificadores de paquete) o una lista de paquetes separados por dos puntos, con comodines, que se eliminarán como calificadores. El nombre del paquete se elimina de los lugares donde aparecen los nombres de clase o interfaz. Consulte Archivos fuente de procesamiento.

El siguiente ejemplo omite todos los calificadores de paquete: -noqualifier all.

El siguiente ejemplo omite los calificadores de los paquetes java.lang y java.io: -noqualifier java.lang:java.io.

El siguiente ejemplo omite los calificadores de paquete que comienzan con java, y los subpaquetes de com.sun, pero no javax: -noqualifier java.*:com.sun.*.

Donde aparecería un calificador de paquete debido al comportamiento anterior, el nombre puede acortarse adecuadamente. Ver Cómo aparece un nombre. Esta regla está en vigor tanto si se utiliza la opción -noqualifier como si no.

-notimestamp

Suprime la marca de tiempo, que está oculta en un comentario HTML en el HTML generado cerca de la parte superior de cada página. La opción -notimestamp es útil cuando desea ejecutar el comando javadoc en dos bases de código y obtener las diferencias entre ellas con diff, ya que evita que las marcas de tiempo causen un diff (que de lo contrario sería un diff en cada página). La marca de tiempo incluye el número de versión del comando javadoc, y actualmente aparece de forma similar a: <!-- Generado por javadoc (build 1.5.0_01) el Jue Apr 02 14:04:52 IST 2009 -->.
-nocomment

Suprime todo el cuerpo del comentario, incluida la descripción principal y todas las etiquetas, y genera solo las declaraciones. Esta opción le permite reutilizar archivos fuente que originalmente estaban destinados a un propósito diferente para que pueda producir documentación HTML esquemática en las primeras etapas de un nuevo proyecto.
-sourcetab tablength

Especifica el número de espacios que utiliza cada tabulación en el código fuente.

ARCHIVOS DE ARGUMENTOS DE LÍNEA DE COMANDOS

Para acortar o simplificar el comando javadoc, puede especificar uno o más archivos que contengan argumentos para el comando javadoc (excepto las opciones -J). Esto le permite crear comandos javadoc de cualquier longitud en cualquier sistema operativo.

Un archivo de argumentos puede incluir opciones de javac y nombres de archivos fuente en cualquier combinación. Los argumentos dentro de un archivo pueden estar separados por espacios o saltos de línea. Si un nombre de archivo contiene espacios incrustados, entonces ponga todo el nombre de archivo entre comillas dobles.

Los nombres de archivo dentro de un archivo de argumentos son relativos al directorio actual, no a la ubicación del archivo de argumentos. Los comodines (*) no están permitidos en estas listas (como para especificar *.java). No se admite el uso del signo arroba (@) para interpretar archivos de forma recursiva. Las opciones -J no son compatibles porque se pasan al lanzador, que no admite archivos de argumentos.

Cuando ejecute el comando javadoc, pase la ruta y el nombre de cada archivo de argumentos con el carácter principal @. Cuando el comando javadoc encuentre un argumento que comience con el signo arroba (@), expandirá el contenido de ese archivo en la lista de argumentos.

NOMBRE


javadoc — generador de documentación de la API de Java






SINOPSIS


javadoc [ opciones ] [ paquetes ] [ archivos_fuente ]






DESCRIPCIÓN


El programa javadoc lee los archivos fuente
    de Java y genera un conjunto de páginas HTML que describen las clases,
    interfaces, tipos anidados y miembros (campos y métodos) de los paquetes
    especificados.


La documentación se genera a partir de los comentarios de la
    documentación incrustados en los archivos fuente de Java. Un comentario de
    documentación comienza con /** y termina con
    */.




COMENTARIOS DE DOCUMENTACION


Los comentarios de documentación se pueden utilizar para documentar
    lo siguiente:


    
  
  • Paquetes
    • 
  
  • Clases
    • 
  
  • Interfaces
    • 
  
  • Miembros (campos y métodos)
    • 
  
  • Constructores
    • 



Los comentarios de documentación se pueden incluir en cualquier
    lugar de un archivo fuente de Java, pero solo se consideran comentarios de
    documentación si preceden inmediatamente a una declaración de nivel de
    paquete, clase, interfaz, campo, método o constructor.






DONDE SE PUEDEN USAR LAS ETIQUETAS


Las etiquetas @param, @return
    y @exception solo se pueden usar en comentarios de
    documentación de métodos y constructores.


La etiqueta @see se puede usar en cualquier
    lugar.


Las etiquetas @author y @version
    solo se pueden usar en comentarios de documentación de nivel de paquete o
    clase.






OPCIONES


Las siguientes opciones se pueden usar con el comando
    javadoc:



  
-classpath ruta

  
Especifica la ruta de búsqueda de archivos de clase y de recursos. Si esta
      opción no se especifica, la ruta de acceso a clases predeterminada será la
      del valor de la variable de entorno CLASSPATH. Si ni CLASSPATH ni la opción
      -classpath se especifican, se utilizará el directorio
      actual. Los directorios se separan con punto y coma (;) en Windows y con
      dos puntos (:) en Solaris.

  
-doctitle cadena_título

  
Especifica el título del documento. El título se coloca en la parte superior
      de cada página generada. El título debe estar entre comillas dobles si
      contiene espacios.

  
-footer cadena_pie

  
Especifica el texto del pie de página. El pie de página se coloca en la
      parte inferior de cada página generada.

  
-header cadena_encabezado

  
Especifica el texto del encabezado. El encabezado se coloca en la parte
      superior de cada página generada.

  
-help

  
Muestra un mensaje de ayuda.

  
-link url

  
Crea un enlace a la documentación de la API de Java en la URL especificada.

  
-linkoffline ruta_paquete url

  
Crea un enlace a la documentación de la API de Java en la URL especificada,
      pero busca los archivos de la API en la ruta de acceso especificada. Esto
      es útil para generar documentación para varias versiones de la API de
      Java.

  
-linksource

  
Crea enlaces a las fuentes de los archivos de clase.

  
-nodeprecated

  
Omite la documentación de los elementos marcados como obsoletos.

  
-nodeprecatedlist

  
No genera una lista de elementos obsoletos.

  
-noindex

  
No genera un índice.

  
-nonavbar

  
No genera una barra de navegación.

  
-noqualifier todos|paquete|corto

  
Especifica cómo eliminar los nombres de paquetes calificados. Los valores
      posibles son all, package o
      short.

  
-notree

  
No genera un árbol de clases.

  
-package

  
Documenta solo los paquetes especificados.

  
-private

  
Muestra todos los miembros privados, incluidos los campos y los métodos
      privados.

  
-protected

  
Muestra solo los miembros protegidos (predeterminado).

  
-public

  
Muestra solo los miembros públicos.

  
-since

  
Incluye información @since en la documentación
      generada.

  
-splitindex

  
Divide el índice en archivos separados por letra.

  
-use

  
Crea páginas de resumen de uso para cada clase e interfaz.

  
-version

  
Incluye información @version en la documentación
      generada.

  
-windowtitle cadena_título_ventana

  
Especifica el título de la ventana del navegador. El título de la ventana se
      muestra en la barra de título del navegador.

NOTAS



  
•

  
Si omite la opción -windowtitle, el comando javadoc copiará el
      título del documento al título de la ventana. El texto de la opción
      -windowtitle es similar a la opción -doctitle, pero sin
      etiquetas HTML para evitar que estas etiquetas aparezcan como texto sin
      formato en el título de la ventana.

  
•

  
Si omite la opción -footer, el comando javadoc copiará el
      texto del encabezado al pie de página.

  
•

  
Otras opciones importantes que podría querer usar, pero que no fueron
      necesarias en el ejemplo anterior, son las opciones -classpath y
      -link.










SOLUCION DE PROBLEMAS GENERAL



  
•

  
El comando javadoc lee solo los archivos que contienen nombres de
      clase válidos. Si el comando javadoc no está leyendo correctamente
      el contenido de un archivo, verifique que los nombres de clase sean
      válidos. Consulte Proceso de Archivos Fuente.

  
•

  
Consulte la FAQ de Javadoc para obtener información sobre errores comunes y
      consejos de solución de problemas en
      http://www.oracle.com/technetwork/java/javase/documentation/index-137483.html








ERRORES Y ADVERTENCIAS


Los mensajes de error y advertencia contienen el nombre del archivo
    y el número de línea de la línea de declaración en lugar de la línea
    específica en el comentario de documentación.


Por ejemplo, este mensaje error: cannot read: Class1.java
    significa que el comando javadoc está intentando cargar
    Class1.java en el directorio actual. El nombre de la clase se
    muestra con su ruta (absoluta o relativa).






ENTORNO



  
CLASSPATH

  
CLASSPATH es la variable de entorno que proporciona la ruta que el
      comando javadoc utiliza para encontrar archivos de clase de usuario.
      Esta variable de entorno se anula con la opción -classpath. Los
      directorios se separan con punto y coma para Windows o con dos puntos para
      Oracle Solaris.
    
Ejemplo de Windows:
        .;C:\clases;C:\home\java\clases

    
Ejemplo de Oracle Solaris:
        .:/home/clases:/usr/local/java/clases.
