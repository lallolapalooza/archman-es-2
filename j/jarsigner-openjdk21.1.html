DESCRIPCIÓ

N

La herramienta jarsigner tiene dos

propósitos:
•
Firmar archivos Java Archive (JAR)
.
•
Verificar las firmas y
la integridad de los
archivos JAR firmados.

La característica JAR permite empaquetar archivos de clases, imágenes, sonidos y otros datos digitales en un solo archivo para una distribución más rápida y fácil. Una herramienta llamada jar permite a los desarrolladores producir archivos JAR. (Técnicamente, cualquier archivo ZIP también puede considerarse un archivo JAR, aunque cuando es creado por el comando jar o procesado por el comando jarsigner, los archivos JAR también contienen un archivo META-INF/MANIFEST.MF.

)

Una firma digital es una cadena de bits que se calcula a partir de algunos datos (los datos que se firman) y la clave privada de una entidad (una persona, una empresa, etc.). De manera similar a una firma manuscrita, una firma digital tiene muchas características

útiles:
•
Su autenticidad puede ser verificada mediante un cálculo que utiliza la clave pública correspondiente a la clave privada utilizada para generar la
firma.
•
No puede ser falsificada, asumiendo que la clave privada se mantiene en
secreto.
•
Es una función de los datos firmados y por lo tanto no puede afirmarse que sea la firma de otros
datos.
•
Los datos firmados no pueden ser modificados
. Si los datos son modificados, entonces la f
irma no puede ser verificada como auténtica.

Para generar la firma de una entidad para un archivo, la entidad debe primero tener un par de claves pública/privada asociado con ella y uno o más certificados que autentiquen su clave pública. Un certificado es una declaración firmada digitalmente de una entidad que dice que la clave pública de otra entidad tiene un valor

particular.

El comando jarsigner utiliza información de claves y certificados de un almacén de claves para generar firmas digitales para archivos JAR. Un almacén de claves es una base de datos de claves privadas y sus cadenas de certificados X.509 asociadas que autentican las claves públicas correspondientes. El comando keytool se utiliza para crear y administrar almacenes de

claves.

El comando jarsigner utiliza la clave privada de una entidad para generar una firma. El archivo JAR firmado contiene, entre otras cosas, una copia del certificado del almacén de claves para la clave pública correspondiente a la clave privada utilizada para firmar el archivo. El comando jarsigner puede verificar la firma digital del archivo JAR firmado utilizando el certificado que contiene (en su archivo de bloque de firma)

.

El comando jarsigner puede generar firmas que incluyan una marca de tiempo que permite a un sistema o desplegador comprobar si el archivo JAR fue firmado mientras el certificado de firma aún era

válido.

Además, las API permiten a las aplicaciones obtener la información de la marca de

tiempo.

En este momento, el comando jarsigner solo puede firmar archivos JAR creados por el comando jar o archivos zip. Los archivos JAR son iguales a los archivos zip, excepto que también tienen un archivo META-INF/MANIFEST.MF. Un archivo META-INF/MANIFEST.MF se crea cuando el comando jarsigner firma un archivo

zip.

El comportamiento predeterminado del comando jarsigner es firmar un archivo JAR o zip. Utilice la opción -verify para verificar un archivo JAR

firmado.

El comando jarsigner también intenta validar el certificado del firmante después de firmar o verificar. Durante la validación, comprueba el estado de revocación de cada certificado en la cadena de certificados del firmante cuando se especifica la opción -revCheck. Si hay un error de validación u otro problema, el comando genera mensajes de advertencia. Si especifica la opción -strict, entonces el comando trata las advertencias graves como errores. CLAVES

Todas las entidades del almacén de claves se acceden con alias

Cuando utiliza el comando jarsigner para firmar un archivo JAR, debe especificar el alias para la entrada del almacén de claves que contiene la clave privada necesaria para generar la firma. Si no se especifica un archivo de salida, sobrescribe el archivo JAR original con el archivo JAR

Los almacenes de claves están protegidos con una contraseña, por lo que se debe especificar la contraseña del almacén. Se le solicitará cuando no la especifique

en la línea de comandos. De manera similar, las claves privadas están protegidas en un almacén de claves con una contraseña, por lo que se debe especificar la c
ontraseña de la clave privada, y se le solicitará la contraseña cuando no la especifique en la línea de comandos y no sea la misma que la contraseña del almacén.

Linux y macOS: user.home por defecto es el directorio de inicio del

El flujo de entrada de la opción -keystore se pasa al método KeyStore.load. Si se especifica NONE como

IMPLEMENTACIÓN DEL ALMACÉN DE

CLAVES

La clase KeyStore proporcionada en el paquete java.security suministra una serie de interfaces bien definidas para acceder y modificar la información en un almacén de claves. Puede haber múltiples implementaciones concretas diferentes, donde cada implementación es para un tipo particular de almacén de

claves.

Actualmente, hay dos herramientas de línea de comandos que utilizan implementaciones de almacén de claves (keytool y jarsigner)

.

La implementación predeterminada del almacén de claves es PKCS12. Este es un almacén de claves multiplataforma basado en el Estándar de Sintaxis de Intercambio de Información Personal PKCS12 de RSA. Este estándar está destinado principalmente a almacenar o transportar las claves privadas, certificados y secretos varios de un usuario. Hay otra implementación integrada, proporcionada por Oracle. Implementa el almacén de claves como un archivo con un tipo de almacén de claves propietario (formato) llamado JKS. Protege cada clave privada con su contraseña individual, y también protege la integridad de todo el almacén de claves con una (posiblemente diferente)

contraseña.

Las implementaciones del almacén de claves se basan en proveedores, lo que significa que las interfaces de aplicación suministradas por la clase KeyStore se implementan en términos de una Interfaz de Proveedor de Servicios (SPI). Hay una clase abstracta correspondiente KeystoreSpi, también en el paquete java.security, que define los métodos de la Interfaz de Proveedor de Servicios que los proveedores deben implementar. El término proveedor se refiere a un paquete o un conjunto de paquetes que suministran una implementación concreta de un subconjunto de servicios a los que se puede acceder mediante la API de Seguridad de Java. Para proporcionar una implementación de almacén de claves, los clientes deben implementar un proveedor y suministrar una implementación de subclase de KeystoreSpi, como se describe en Cómo implementar un proveedor en la Arquitectura de Criptografía de Java [https://www.oracle.com/pls/topic/lookup?ctx=en/java/javase&id=security_guide_implement_provider_jca]

.

Las aplicaciones pueden elegir diferentes tipos de implementaciones de almacén de claves de diferentes proveedores, con el método de fábrica getInstance en la clase KeyStore. Un tipo de almacén de claves define el almacenamiento y el formato de datos de la información del almacén de claves y los algoritmos utilizados para proteger las claves privadas en el almacén de claves y la integridad del propio almacén de claves. Las implementaciones de almacén de claves de diferentes tipos no son compatibles entre

sí.

Los comandos jarsigner pueden leer almacenes de claves basados en archivos desde cualquier ubicación que se pueda especificar usando una URL. Además, estos comandos pueden leer almacenes de claves no basados en archivos, como los proporcionados por MSCAPI en Windows y PKCS11 en todas las

plataformas.

Para los comandos jarsigner y keytool, puede especificar un tipo de almacén de claves en la línea de comandos con la opción

-storetype.

Si no especifica explícitamente un tipo de almacén de claves, las herramientas eligen una implementación de almacén de claves basada en el valor de la propiedad keystore.type especificada en el archivo de propiedades de seguridad. El archivo de propiedades de seguridad se llama java.security y se encuentra en el directorio de propiedades de seguridad del JDK, java.home/conf/security

.

Cada herramienta obtiene el valor de keystore.type y luego examina todos los proveedores instalados hasta que encuentra uno que implemente almacenes de claves de ese tipo. Luego usa la implementación de almacén de claves de ese

proveedor.

La clase KeyStore define un método estático llamado getDefaultType que permite a las aplicaciones recuperar el valor de la propiedad keystore.type. La siguiente línea de código crea una instancia del tipo de almacén de claves predeterminado como se especifica en la propiedad keystore.

type:

KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType()

)
;

seguridad:

The jarsigner utility is used to sign and verify JAR files. Signing a JAR file embeds a digital signature within it, allowing users to verify the identity of the signer and ensuring that the JAR file has not been tampered with since it was signed. Verifying a JAR file checks the validity of these digital signatures.

\n

The verification process involves several steps:

\n
\n
1.
\n
Read the JAR file's manifest file (META-INF/MANIFEST.MF). This file contains a list of all the files in the JAR archive, along with their corresponding message digests (hashes). It also contains a header section that provides information about the manifest itself.
\n
2.
\n
Read the signature file (e.g., META-INF/ALIAS.SF). This file contains the signature for the manifest file. It includes a header section similar to the manifest file and then a section for each file listed in the manifest, containing the message digest of that file as computed by the signer. It's important to note that the .SF file might contain entries for files that were not present in the JAR file when it was originally signed. This can occur if the JAR file is modified and re-signed. However, a verification is still considered successful if none of the files that were present at the time of the original signature have been altered, as the digests in the .SF file will match the digests of the corresponding entries in the manifest file.
\n
\n
\n

A verification is still considered successful if none of the files that were in the JAR file when the original signature was generated have been changed since then. This is because the hashes in the non-header sections of the .SF file equal the hashes of the corresponding sections in the manifest file.

\n
\n
\n
3.
\n
Read each file in the JAR file that has an entry in the .SF file. While reading, compute the file's digest and compare the result with the digest for this file in the manifest section. The digests should be the same or verification fails.
\n
\n
\n

If any serious verification failures occur during the verification process, then the process is stopped and a security exception is thrown. The jarsigner command catches and displays the exception.

\n

4.
\n
Check for disabled algorithm usage. See Supported Algorithms.

NAME

    

        
jarsigner - sign and verify signed JAR files

    





    
SYNOPSIS

    

        
jarsigner [options] jar-file alias
jarsigner [options] -verify jar-file ...

    





    
DESCRIPTION

    

        
The jarsigner utility is used to sign JAR files with a private key and certificate, and to verify signed JAR files. It is part of the Java Development Kit (JDK).

        
When signing a JAR file, jarsigner:

        
    
            
  • Computes digests for all entries in the JAR file.
    • 
            
  • Signs these digests with the specified private key.
    • 
            
  • Creates signature files (.SF and .DSA or .RSA) and a manifest file (META-INF/MANIFEST.MF) containing the digests.
    • 
            
  • Adds these files to the JAR archive.
    • 
            
  • Optionally, obtains a timestamp for the signature from a timestamping authority (TSA).
    • 
        

        
When verifying a signed JAR file, jarsigner:

        
    
            
  • Checks the integrity of the signature files and the manifest.
    • 
            
  • Verifies the signature against the digests of the JAR entries.
    • 
            
  • Verifies the certificate chain of the signer.
    • 
            
  • Optionally, verifies the timestamp.
    • 
        

    





    
KEYSTORE ALIASES

    

        
The alias argument is a name that refers to a private key and its associated public-key certificate chain in a keystore.

    





    
KEYSTORE LOCATION

    

        
By default, jarsigner looks for the keystore in a file named .keystore in the user's home directory. The location can be specified using the -keystore option.

    





    
KEYSTORE IMPLEMENTATION

    

        
The default keystore implementation is the Java KeyStore (JKS). Other implementations can be specified using the -storetype option.

    





    
SUPPORTED ALGORITHMS

    

        
jarsigner supports various signature and digest algorithms, including DSA, RSA, and ECDSA for signatures, and MD5, SHA-1, and SHA-256 for digests.

    





    
THE SIGNED JAR FILE

    

        
A signed JAR file contains additional files in the META-INF directory:

        
    
            
  • MANIFEST.MF: The manifest file, listing all entries and their digests.
    • 
            
  • *.SF: The signature file, containing the digest of the manifest file.
    • 
            
  • *.DSA or *.RSA: The signature block file, containing the digital signature of the signature file.
    • 
        

        
The wildcard character `*` is replaced by the alias of the signer.

    





    
SIGNATURE FILE

    

        
The signature file (e.g., META-INF/alias.SF) contains a hash of the manifest file. It is signed by the private key corresponding to the public key in the signer's certificate.

    





    
SIGNATURE BLOCK FILE

    

        
The signature block file (e.g., META-INF/alias.DSA or META-INF/alias.RSA) contains the actual digital signature of the signature file. It also includes the signer's certificate chain.

    





    
SIGNATURE TIME STAMP

    

        
A timestamp provides evidence that the JAR file was signed at a particular time. This is useful for validating signatures even after the signer's certificate has expired. The timestamp is obtained from a trusted Timestamping Authority (TSA).

    





    
JAR FILE VERIFICATION

    

        
When verifying a JAR file, jarsigner checks the following:

        
    
            
  • The integrity of the signature files and the manifest.
    • 
            
  • The digital signature of the signature file against the manifest's digest.
    • 
            
  • The digital signature of the JAR entries against the digests in the manifest.
    • 
            
  • The validity of the signer's certificate chain, checking against trusted certificates.
    • 
            
  • The validity of the timestamp, if present.
    • 
        

    





    
MULTIPLE SIGNATURES FOR A JAR FILE

    

        
A JAR file can be signed by multiple entities. Each signature is stored in its own set of signature and signature block files within the META-INF directory.

    





    
OPTIONS FOR JARSIGNER

    

        
Common options include:

        

            
-keystore keystore

            
Specifies the location of the keystore.

            
-storetype storetype

            
Specifies the keystore type.

            
-storepass password

            
Specifies the password for the keystore.

            
-keypass password

            
Specifies the password for the private key.

            
-signedjar signedjarfile

            
Specifies the output file for the signed JAR.

            
-tsacert tsacert

            
Specifies the certificate of the TSA.

            
-tsaprobe

            
Probes the TSA to determine supported algorithms.

            
-verify

            
Verifies the signed JAR file.

FAILURE

    

        
The jarsigner utility exits with a non-zero status if an error occurs during signing or verification.

    





    
SEVERE WARNINGS

    

        
Severe warnings indicate potential security risks or problems that could compromise the integrity of the signed JAR file. These include:

        
    
            
  • Signature verification failed.
    • 
            
  • The signer's certificate is invalid (e.g., expired, revoked, or not trusted).
    • 
            
  • The timestamp is invalid or missing.
    • 
            
  • The JAR file has been modified since it was signed.
    • 
        

    





    
INFORMATIONAL WARNINGS

    

        
Informational warnings provide additional details about the signing or verification process, but do not necessarily indicate a security risk. Examples include:

        
    
            
  • The signer's certificate is about to expire.
    • 
            
  • The timestamp has expired, but the signature is still considered valid based on the certificate's validity at the time of signing.
    • 
        

    





    
EXAMPLE OF SIGNING A JAR FILE

    

        
To sign a JAR file named myapp.jar with the alias mykey from the default keystore:

        
jarsigner -keystore ~/.keystore myapp.jar mykey

    





    
EXAMPLE OF VERIFYING A SIGNED JAR FILE

    

        
To verify a signed JAR file named myapp.jar:

        
jarsigner -verify myapp.jar

    





    
EXAMPLE OF VERIFICATION WITH CERTIFICATE INFORMATION

    

        
To verify a signed JAR file and display detailed certificate information:

        
jarsigner -verbose -certs myapp.jar

        
If the certificate for a signer isn't an X.509 certificate, then there is no distinguished name information. In that case, just the certificate type and the alias are shown. For example, if the certificate is a PGP certificate, and the alias is bob, then you would get: PGP, (bob).
