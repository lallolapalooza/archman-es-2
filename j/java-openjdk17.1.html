USANDO LA VARIABLE DE ENTORNO DEL LANZADOR JDK_JAVA_OPTION

S

JDK_JAVA_OPTIONS antepone su contenido a las opciones analizadas desde la línea de comandos. El contenido de la variable de entorno JDK_JAVA_OPTIONS es una lista de argumentos separados por caracteres en blanco (como lo determina isspace()). Estos se anteponen a los argumentos de la línea de comandos pasados al lanzador java. El requisito de codificación para la variable de entorno es el mismo que el de la línea de comandos de java en el sistema. El contenido de la variable de entorno JDK_JAVA_OPTIONS se trata de la misma manera que lo especificado en la línea de

comandos.

Se pueden usar comillas simples (') o dobles (") para encerrar argumentos que contienen caracteres en blanco. Todo el contenido entre la comilla de apertura y la primera comilla de cierre coincidente se conserva simplemente eliminando el par de comillas. En caso de que no se encuentre una comilla coincidente, el lanzador abortará con un mensaje de error. Los archivos @ son soportados tal como se especifican en la línea de comandos. Sin embargo, como en los archivos @, el uso de un comodín no está soportado. Para mitigar el posible uso indebido del comportamiento de JDK_JAVA_OPTIONS, las opciones que especifican la clase principal (como -jar) o que hacen que el lanzador java salga sin ejecutar la clase principal (como -h) no están permitidas en la variable de entorno. Si alguna de estas opciones aparece en la variable de entorno, el lanzador abortará con un mensaje de error. Cuando JDK_JAVA_OPTIONS está establecida, el lanzador imprime un mensaje en stderr como

recordatorio.

Ejemplo

: 

$ export JDK_JAVA_OPTIONS='-g @file1 -Dprop=value @file2 -Dws.prop="white spaces"'
$ java -Xint @file3

es equivalente a la línea de

comandos: 

java -g @file1 -Dprop=value @file2 -Dws.prop="white spaces" -Xint @file3

RESUMEN DE LAS OPCIONES DE

JAVA

El comando java soporta una amplia gama de opciones en las siguientes

categorías:
•
Opciones estándar para Java: Opciones garantizadas para ser soportadas por todas las implementaciones de la Máquina Virtual Java (JVM). Se usan para acciones comunes, como verificar la versión de la JRE, establecer la ruta de clases, habilitar la salida detallada,
etc.
•
Opciones extra para Java: Opciones de propósito general que son específicas de la Máquina Virtual Java HotSpot. No están garantizadas para ser soportadas por todas las implementaciones de JVM, y están sujetas a cambios. Estas opciones comienzan con -X
.

Las opciones avanzadas no se recomiendan para un uso casual. Estas son opciones de desarrollo usadas para ajustar áreas específicas de la operación de la Máquina Virtual Java HotSpot que a menudo tienen requisitos de sistema específicos y pueden requerir acceso privilegiado a parámetros de configuración del sistema. Se proporcionan varios ejemplos de ajuste de rendimiento en Ejemplos de Ajuste de Rendimiento. Estas opciones no están garantizadas para ser soportadas por todas las implementaciones de JVM y están sujetas a cambios. Las opciones avanzadas comienzan con -XX

.
•
Opciones de tiempo de ejecución avanzadas para Java: Controlan el comportamiento en tiempo de ejecución de la Máquina Virtual Java
HotSpot.
•
Opciones avanzadas del compilador JIT para java: Controlan la compilación dinámica just-in-time (JIT) realizada por la Máquina Virtual Java
HotSpot.
•
Opciones de servicio avanzadas para Java: Habilitan la recopilación de información del sistema y la realización de una depuración
extensa.
•
Opciones de recolección de basura avanzadas para Java: Controlan cómo se rea
liza la recolección de basura (G
C) por la Máquina Virtual Java HotSpot

Las opciones booleanas se usan para habilitar una función que está deshabilitada por defecto o para deshabilitar una función que está habilitada por defecto. Tales opciones no requieren un parámetro. Las opciones booleanas -XX se habilitan usando el signo más (-XX:+OptionName) y se deshabilitan usando el signo menos (-XX:-OptionNa

me).

Para las opciones que requieren un argumento, el argumento puede separarse del nombre de la opción por un espacio, un dos puntos (:) o un signo igual (=), o el argumento puede seguir directamente a la opción (la sintaxis exacta difiere para cada opción). Si se espera que especifique el tamaño en bytes, entonces puede usar ningún sufijo, o usar el sufijo k o K para kilobytes (KB), m o M para megabytes (MB), o g o G para gigabytes (GB). Por ejemplo, para establecer el tamaño en 8 GB, puede especificar 8g, 8192m, 8388608k, o 8589934592 como el argumento. Si se espera que especifique el porcentaje, entonces use un número de 0 a 1. Por ejemplo, especifique 0.25 para el

25%.

Las siguientes secciones describene opciones que están obsoletas, en desuso y eliminadas:

•
Opciones de Java en desuso: Aceptadas y actuadas. Se emite una advertencia cuando se utilizan.
•
Opciones de Java obsoletas: Aceptadas pero ignoradas. Se emite una advertencia cuando se utilizan.
•
Opciones de Java eliminadas: Eliminadas. Su uso resulta en un error.

Estas son las opciones más comúnmente utilizadas y compatibles con todas las implementaciones de la JVM.

-agentlib:nombre_libreria[=opciones]
Carga la biblioteca nativa especificada. Después del nombre de la biblioteca, se puede usar una lista de opciones separadas por comas, específicas de la biblioteca.
•
Linux y macOS: Si se especifica la opción -agentlib:foo, la JVM intenta cargar la biblioteca llamada libfoo.so en la ubicación especificada por la variable del sistema LD_LIBRARY_PATH (en macOS, esta variable es DYLD_LIBRARY_PATH).
•
Windows: Si se especifica la opción -agentlib:foo, la JVM intenta cargar la biblioteca llamada foo.dll en la ubicación especificada por la variable del sistema PATH.

El siguiente ejemplo muestra cómo cargar la biblioteca del Protocolo de Depuración de Hilo de Java (JDWP) y escuchar la conexión de socket en el puerto 8000, suspendiendo la JVM antes de que se cargue la clase principal:

-agentlib:jdwp=transport=dt_socket,server=y,address=8000

-agentpath:ruta_completa[=opciones]
Carga la biblioteca nativa especificada por la ruta completa. Esta opción es equivalente a -agentlib pero utiliza la ruta completa y el nombre de archivo de la biblioteca.
--class-path ruta_clases, -classpath ruta_clases o -cp ruta_clases
Una lista separada por punto y coma ( ;) de directorios, archivos JAR y archivos ZIP en los que buscar archivos de clase.

Especificar ruta_clases anula cualquier configuración de la variable de entorno CLASSPATH. Si la opción de ruta de clases no se utiliza y ruta_clases no está configurada, la ruta de clases del usuario consta del directorio actual (.).

Como una conveniencia especial, un elemento de ruta de clases que contiene un nombre base de asterisco (*) se considera equivalente a especificar una lista de todos los archivos en el directorio con la extensión .jar o .JAR. Todos los archivos .jar en el directorio especificado, incluso los ocultos, se incluyen en la lista. Un elemento de ruta de clases que consiste en un asterisco (*) se expande a una lista de todos los archivos jar en el directorio actual. -Xmn tamaño
Establece el tamaño inicial y máximo (en bytes) del heap para la generación joven (nursery) en los recolectores generacionales. Añada la letra k o K para indicar kilobytes, m o M para indicar megabytes, o g o G para indicar gigabytes. La región de generación joven del heap se utiliza para objetos nuevos. La recolección de basura (GC) se realiza en esta región con más frecuencia que en otras. Si el tamaño de la generación joven es demasiado pequeño, se realizan muchas recolecciones de basura menores. Si el tamaño es demasiado grande, solo se realizan recolecciones de basura completas, que pueden tardar mucho tiempo en completarse. Se recomienda no establecer el tamaño de la generación joven para el recolector G1, y mantener el tamaño de la generación joven entre el 25% y el 50% del tamaño total del heap para otros recolectores. Los siguientes ejemplos muestran cómo establecer el tamaño inicial y máximo de la generación joven en 256 MB utilizando varias unidades:

-Xmn256m
-Xmn262144k
-Xmn268435456

En lugar de la opción -Xmn para establecer tanto el tamaño inicial como el máximo del heap para la generación joven, puede utilizar -XX:NewSize para establecer el tamaño inicial y -XX:MaxNewSize para establecer el tamaño máximo.

-Xms tamaño
Establece el tamaño mínimo e inicial (en bytes) del heap. Este valor debe ser un múltiplo de 1024 y mayor que 1 MB. Añada la letra k o K para indicar kilobytes, m o M para indicar megabytes, g o G para indicar gigabytes. Si no establece esta opción, el tamaño inicial se establece como la suma de los tamaños asignados para la generación vieja y la generación joven. El tamaño inicial del heap para la generación joven se puede establecer utilizando la opción -Xmn o la opción -XX:NewSize.

-Xnoclassgc
Deshabilita la recolección de basura (GC) de clases. Esto puede ahorrar algo de tiempo de GC, lo que acorta las interrupciones durante la ejecución de la aplicación. Cuando se especifica -Xnoclassgc al inicio, los objetos de clase en la aplicación se dejan intactos durante la GC y siempre se considerarán vivos. Esto puede resultar en que se ocupe permanentemente más memoria, lo que, si no se utiliza con cuidado, puede provocar una excepción de falta de memoria (out-of-memory).
-Xrs
Reduce el uso de señales del sistema operativo por parte de la JVM. Los ganchos de apagado (shutdown hooks) permiten el apagado ordenado de una aplicación Java ejecutando código de limpieza del usuario (como el cierre de conexiones a bases de datos) al apagar, incluso si la JVM termina abruptamente.
•
Linux y macOS:
•
La JVM captura señales para implementar ganchos de apagado para terminaciones inesperadas. La JVM utiliza SIGHUP, SIGINT y SIGTERM para iniciar la ejecución de los ganchos de apagado.
•
Las aplicaciones que incrustan la JVM a menudo necesitan interceptar señales como SIGINT o SIGTERM, lo que puede provocar interferencias con los manejadores de señales de la JVM. La opción -Xrs está disponible para abordar este problema. Cuando se utiliza -Xrs, la JVM no modifica las máscaras de señal para SIGINT, SIGTERM, SIGHUP y SIGQUIT, y no instala manejadores de señales para estas señales.
•
Windows:
•
La JVM supervisa los eventos de control de la consola para implementar ganchos de apagado para terminaciones inesperadas. Específicamente, la JVM registra un manejador de control de consola que inicia el procesamiento de los ganchos de apagado y devuelve TRUE para CTRL_C_EVENT, CTRL_CLOSE_EVENT, CTRL_LOGOFF_EVENT y CTRL_SHUTDOWN_EVENT.
•
La JVM utiliza un mecanismo similar para implementar la función de volcado de pilas de hilos para fines de depuración. La JVM utiliza CTRL_BREAK_EVENT para realizar volcados de hilos.
•
Si la JVM se ejecuta como un servicio (por ejemplo, como un motor de servlets para un servidor web), puede recibir CTRL_LOGOFF_EVENT pero no debería iniciar el apagado porque el sistema operativo no termina realmente el proceso. Para evitar posibles interferencias como esta, se puede utilizar la opción -Xrs. Cuando se utiliza la opción -Xrs, la JVM no instala un manejador de control de consola, lo que implica que no supervisa ni procesa CTRL_C_EVENT, CTRL_CLOSE_EVENT, CTRL_LOGOFF_EVENT o CTRL_SHUTDOWN_EVENT.

Hay dos consecuencias de especificar -Xrs:

•
Linux y macOS: Los volcados de hilos con SIGQUIT no están disponibles.
•
Windows: Los volcados de hilos con Ctrl + Break no están disponibles.

El código de usuario es responsable de hacer que se ejecuten los ganchos de apagado, por ejemplo, llamando a System.exit() cuando la JVM debe ser terminada.

PÁGINAS

GRANDES

Se usan páginas grandes, también conocidas como páginas enormes, como páginas de memoria que son significativamente más grandes que el tamaño de página de memoria estándar (que varía dependiendo del procesador y el sistema operativo). Las páginas grandes optimizan los búferes de traducción de direcciones (TLB) del

procesador.

Un búfer de traducción de direcciones (TLB) es una caché de traducción de páginas que contiene las traducciones de direcciones virtuales a físicas usadas más recientemente. Un TLB es un recurso escaso del sistema. Un fallo de TLB puede ser costoso porque el procesador debe entonces leer de la tabla de páginas jerárquica, lo que puede requerir múltiples accesos a memoria. Al usar un tamaño de página de memoria más grande, una sola entrada de TLB puede representar un rango de memoria más grande. Esto resulta en menos presión sobre un TLB, y las aplicaciones intensivas en memoria pueden tener un mejor

rendimiento.

Sin embargo, el uso de páginas grandes puede afectar negativamente al sistemarendimiento. Por ejemplo, cuando una gran cantidad de memoria está fijada (pinned) por una aplicación, puede crear una escasez de memoria regular y causar un paginado excesivo en otras aplicaciones y ralentizar todo el sistema. Además, un sistema que ha estado encendido durante mucho tiempo podría producir una fragmentación excesiva, lo que podría hacer imposible reservar suficiente memoria de páginas grandes. Cuando esto sucede, tanto el SO como la JVM recurren a usar páginas

regulares.

Linux y Windows admiten páginas

grandes.

La Compartición de Datos de Clases de la Aplicación (AppCDS) almacena clases usadas por sus aplicaciones en un archivo de archivo (archive). NOMBRE

java - Lanzador de aplicaciones Java

SINOPSIS

java [Java Options] [Application] [Application Options]
java [Java Options] -jar [JAR File] [Application Options]

DESCRIPCIÓN

La utilidad java (lanzador) carga una clase Java y la ejecuta. El lanzador busca una clase predeterminada en un paquete de clases predeterminado y luego busca el método main estático estático de esa clase. El método main debe declararse público, recibir un array de tipo String como argumento y no tener valor de retorno (tipo void).

Una vez que la clase ha sido cargada, se llama al método main. El argumento [Application Options] se pasa al método main en el array de String.

Si el argumento es un nombre de archivo JAR, entonces los argumentos son el nombre del archivo JAR y las opciones de la aplicación. El modo de archivo JAR se especifica con la opción -jar. Esta opción es necesaria para ejecutar un programa Java empaquetado como un archivo JAR. El contenido del archivo JAR está especificado en el archivo META-INF/MANIFEST.MF. Si se especifica el manifiesto, se debe utilizar para localizar la clase inicial.

El lanzador de Java permite especificar opciones de Java antes del nombre de la aplicación o el nombre del archivo JAR. Todas las opciones que comienzan con - se consideran opciones de Java. Todas las demás se pasan directamente al método main de la aplicación.

La siguiente tabla muestra la opción de cómo ejecutar una clase Java desde la línea de comandos:

Y la siguiente tabla muestra la opción de cómo ejecutar una clase Java desde un archivo JAR:

Restricciones en la Ruta de Clases y la Ruta de Módulos

•
Ni la ruta de clases (-classpath y -Xbootclasspath/a) ni la ruta de módulos (--module-path) pueden contener directorios no vacíos.
•
Solo se admiten archivos JAR modulares en --module-path. Los módulos explotados no se admiten.
•
La ruta de clases utilizada en el momento de la creación del archivo debe ser la misma que (o un prefijo de) la ruta de clases utilizada en el momento de la ejecución. (No existe tal requisito para la ruta de módulos.)
•
El archivo CDS no se puede cargar si algún archivo JAR en la ruta de clases o ruta de módulos se modifica después de que se genera el archivo.
•
Si se especifican alguna de las opciones de VM --upgrade-module-path, --patch-module o --limit-modules, CDS se deshabilita. Esto significa que la JVM se ejecutará sin cargar ningún archivo CDS. Además, si intenta crear un archivo CDS con alguna de estas 3 opciones especificadas, la JVM informará un error.
