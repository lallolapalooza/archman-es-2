NOMBRE

jj-rebase - Mover revisiones a diferentes padres

SINOPSIS

jj rebase [-b|--branch] [-s|--source] [-r|--revisions] [-o|--onto] [-A|--insert-after] [-B|--insert-before] [--skip-emptied] [--keep-divergent] [-R|--repository] [--ignore-working-copy] [--ignore-immutable] [--at-operation] [--debug] [--color] [--quiet] [--no-pager] [--config] [--config-file] [-h|--help]

DESCRIPCIÓN

Mover revisiones a diferentes padres

Este comando mueve revisiones a diferentes padres mientras preserva los cambios (diff) en las revisiones.

Hay tres formas diferentes de especificar qué revisiones se deben rebasar:

* `--source/-s` para rebasar una revisión y sus descendientes * `--branch/-b` para rebasar una rama completa, relativa al destino * `--revisions/-r` para rebasar las revisiones especificadas sin sus
descendientes

Si no se especifica ninguna opción, el valor predeterminado es `-b @`.

Hay tres formas diferentes de especificar dónde se deben rebasar las revisiones:

* `--onto/-o` para rebasar las revisiones sobre los destinos especificados * `--insert-after/-A` para rebasar las revisiones sobre los destinos y
para rebasar los descendientes de los destinos sobre las revisiones rebasadas * `--insert-before/-B` para rebasar las revisiones sobre los padres de los destinos y
para rebasar los destinos y sus descendientes sobre las revisiones rebasadas

Consulte las secciones siguientes para obtener detalles sobre las diferentes formas de especificar qué revisiones rebasar y dónde.

Si una revisión de la copia de trabajo es abandonada, se le dará una nueva revisión vacía. Esto es cierto en general; no es específico de este comando.

### Especificar qué revisiones rebasar

Con `--source/-s`, el comando rebasa la revisión especificada y sus descendientes al destino. Por ejemplo, `jj rebase -s M -o O` transformaría su historial de la siguiente manera (las letras seguidas de un apóstrofo son versiones posteriores al rebase):

```text O N' | | | N M' | | | | M O | | => | | | L | L | |/ | | | K | K |/ |/ J J ```

Cada revisión pasada a `-s` se convertirá en un hijo directo del destino, por lo que si en su lugar ejecuta `jj rebase -s M -s N -o O` (o `jj rebase -s 'M|N' -o O`) en el ejemplo anterior, entonces N' sería en su lugar un hijo directo de O.

Con `--branch/-b`, el comando rebasa toda la "rama" que contiene la revisión especificada. Una "rama" es el conjunto de revisiones que incluye:

* la revisión especificada y los ancestros que no son también ancestros del
destino * todos los descendientes de esas revisiones

En otras palabras, `jj rebase -b X -o Y` rebasa revisiones en el conjunto de revisiones `(Y..X)::` (lo que es equivalente a `jj rebase -s 'roots(Y..X)' -o Y` para una sola raíz). Por ejemplo, `jj rebase -b L -o O` o `jj rebase -b M -o O` transformarían su historial de la siguiente manera (porque `L` y `M` están en la misma "rama", relativa al destino):

```text O N' | | | N M' | | | | M | L' | | => |/ | | L K' | |/ | | K O |/ | J J ```

Con `--revisions/-r`, el comando rebasa solo las revisiones especificadas al destino. Cualquier "hueco" que quede se llenará rebajando los descendientes a los padres de las revisiones especificadas. Por ejemplo, `jj rebase -r K -o M` transformaría su historial de la siguiente manera:

```text M K' | | | L M | | => | | K | L' |/ |/ J J ```

Se pueden especificar múltiples revisiones y se preservarán las dependencias (aristas del grafo) dentro del conjunto. Por ejemplo, `jj rebase -r 'K|N' -o O` transformaría su historial de la siguiente manera:

```text O N' | | | N K' | | | | M O | | => | | | L | M' | |/ |/ | K | L' |/ |/ J J ```

`jj rebase -s X` es similar a `jj rebase -r X::` y se comportará igual si X es una sola revisión. Sin embargo, si X es un conjunto de múltiples revisiones, o si pasó múltiples argumentos `-s`, entonces `jj rebase -s` hará que cada una de las revisiones especificadas sea un hijo inmediato del destino, mientras que `jj rebase -r` preservará las dependencias dentro del conjunto.

Tenga en cuenta que puede crear una revisión de fusión repitiendo el argumento `-o`. Por ejemplo, si se da cuenta de que la revisión L en realidad depende de la revisión M para funcionar (además de su padre actual K), puede ejecutar `jj rebase -s L -o K -o M`:

```text M L' | |\ | L M | | => | | | K | K |/ |/ J J ```

### Especificar dónde rebasar las revisiones

Con `--onto/-o`, el comando rebasa las revisiones seleccionadas sobre los destinos. Los descendientes existentes de los destinos no se verán afectados. Consulte la sección anterior para ver ejemplos.

Con `--insert-after/-A`, las revisiones seleccionadas se insertarán después de los destinos. Esto es similar a `-o`, pero si los destinos tienen descendientes existentes, estos se rebasarán sobre las revisiones seleccionadas rebasadas.

Por ejemplo, `jj rebase -r K -A L` reescribirá el historial de la siguiente manera: ```text N N' | | | M | M' |/ |/ L => K' | | | K L |/ | J J ```

El argumento `-A` (y `-B`) también se puede usar para reordenar revisiones. Por ejemplo, `jj rebase -r M -A J` reescribirá el historial de la siguiente manera: ```text M L' | | L K' | => | K M' | | J J ```

Con `--insert-before/-B`, las revisiones seleccionadas se insertarán antes de los destinos. Esto se logra rebajando las revisiones seleccionadas sobre los padres de las revisiones de destino, y luego rebajando las revisiones de destino y sus descendientes sobre las revisiones rebasadas.

Por ejemplo, `jj rebase -r K -B L` reescribirá el historial de la siguiente manera: ```text N N' | | | M | M' |/ |/ L => L' | | | K K' |/ | J J ```

Los argumentos `-A` y `-B` también se pueden combinar, lo que puede ser útil en torno a las fusiones. Por ejemplo, puede usar `jj rebase -r K -A J -B M` para crear una nueva fusión (pero `jj rebase -r M -o L -o K` podría ser más simple en este caso particular): ```text M M' | |\ L L | | => | | | K | K' |/ |/ J J ```

Para insertar un commit dentro de una fusión existente con `jj rebase -r O -A K -B M`: ```text O N' | |\ N | M' |\ | |\ | M | O'| | | => |/ / | L | L | | | | K | K | |/ |/ J J ```

OPCIONES

-b, --branch <REVSETS>
Rebasa toda la rama relativa a los ancestros del destino (se puede repetir)

`jj rebase -b=br -o=dst` es equivalente a `jj rebase '-s=roots(dst..br)' -o=dst`.

Si no se proporciona `-b`, `-s` o `-r`, el valor predeterminado es `-b @`.

-s, --source <REVSETS>
Rebasa la(s) revisión(es) especificada(s) junto con sus árboles de descendientes (se puede repetir)

Cada revisión especificada se convertirá en un hijo directo del(los) destino(s) de la revisión, incluso si algunas de las revisiones de origen son descendientes de otras.

Si no se proporciona `-b`, `-s` o `-r`, el valor predeterminado es `-b @`.

-r, --revisions <REVSETS>
Rebasa las revisiones dadas, rebasando los descendientes sobre el padre de esta revisión

A diferencia de `-s` o `-b`, puede `jj rebase -r` una revisión `A` sobre un descendiente de `A`.

Si no se proporciona `-b`, `-s` o `-r`, el valor predeterminado es `-b @`.

-o, --onto <REVSETS>
La(s) revisión(es) sobre la(s) cual(es) rebasar (se puede repetir para crear un commit de fusión)
-A, --insert-after <REVSETS>
La(s) revisión(es) después de la(s) cual(es) insertar (se puede repetir para crear un commit de fusión)
-B, --insert-before <REVSETS>
La(s) revisión(es) antes de la(s) cual(es) insertar (se puede repetir para crear un commit de fusión)
--skip-emptied
Si es verdadero, cuando el rebase produciría un commit vacío, el commit se abandona. No se abandonará si ya estaba vacío antes del rebase. Nunca abandonará commits de fusión con múltiples padres no vacíos.
--keep-divergent
Mantener commits divergentes al rebasar

Sin esta bandera, los commits divergentes se abandonan durante el rebase si otro commit con el mismo ID de cambio ya está presen

el destino con cambios idénticos.

Esto puede ser útil, por ejemplo, en un prompt de comando, especialmente si tiene otro proceso que confirma la copia de

--at-operation <AT_OPERATIO
N>
Operación en la que cargar el repositorio

Operación en la que cargar el repositorio. Por defecto, Jujutsu carga el repositorio en la operación más reciente, o en la fusión de las operaciones divergentes si las

hay.

Puede usar `--at-op=<operation ID>` para ver cómo era el repositorio en una operación anterior. Por ejemplo, `jj --at-op=<operation ID> st` le mostraría lo que `jj st` habría mostrado cuando la operación indicada hubiera terminado. `--at-op=@` es prácticamente lo mismo que la predeterminada, excepto que las operaciones divergentes nunca se

fusionarán.

Use `jj op log` para encontrar el ID de operación que desea. Cualquier prefijo no ambiguo del ID de operación es

suficiente.

opy`.

zan en la operación anterior. Rara vez hay una razón para hacerlo, pero es posible.
