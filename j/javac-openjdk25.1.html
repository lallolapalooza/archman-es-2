-d directorio
Establece el directorio de destino (o directorio de salida de clases) para archivos de clase. Si una clase forma parte de un paquete, entonces javac coloca el archivo de clase en un subdirectorio que refleja el nombre del módulo (si es apropiado) y el nombre del paquete. El directorio, y cualquier subdirectorio necesario, se crearán si no existen ya.

Si la opción -d no se especifica, entonces javac coloca cada archivo de clase en el mismo directorio que el archivo fuente a partir del cual se generó.

Excepto cuando se compila código para múltiples módulos, el contenido del directorio de salida de clases se organizará en una jerarquía de paquetes. Al compilar código para múltiples módulos, el contenido del directorio de salida se organizará en una jerarquía de módulos, con el contenido de cada módulo en un subdirectorio separado, cada uno organizado como una jerarquía de paquetes.

Nota: Al compilar código para uno o más módulos, el directorio de salida de clases se verificará automáticamente al buscar clases compiladas previamente. Cuando no se compila para módulos, por compatibilidad con versiones anteriores, el directorio *no* se verifica automáticamente en busca de clases compiladas previamente, por lo que se recomienda especificar el directorio de salida de clases como una de las ubicaciones en la ruta de clases del usuario, utilizando la opción --class-path o una de sus formas alternas.

-Xdoclint
Habilita las comprobaciones recomendadas de problemas en los comentarios de documentación.
-Xdoclint:(all|none|[-]group)[/access]
Habilita o deshabilita grupos específicos de comprobaciones en los comentarios de documentación.

group puede tener uno de los siguientes valores: accessibility, html, missing, reference, syntax.

La variable access especifica el nivel de visibilidad mínimo de las clases y miembros que la opción -Xdoclint comprueba. Puede tener uno de los siguientes valores (en orden de más a menos visible): public, protected, package, private.

El nivel access por defecto es private.

Cuando se prefijan con doclint:, los nombres de group y all se pueden usar con @SuppressWarnings para suprimir advertencias sobre comentarios de documentación en partes del código que se están compilando.

Para más información sobre estos grupos de comprobaciones, véase la sección DocLint de la documentación del comando javadoc. La opción -Xdoclint está deshabilitada por defecto en el comando javac.

Por ejemplo, la siguiente opción comprueba clases y miembros (con todos los grupos de comprobaciones) que tienen el nivel de acceso protected y superior (que incluye protected y public):

-Xdoclint:all/protected

La siguiente opción habilita todos los grupos de comprobaciones para todos los niveles de acceso, excepto que no comprobará errores de HTML para clases y miembros que tengan el nivel de acceso package y superior (que incluye package, protected y public):

-Xdoclint:all,-html/package

-Xdoclint/package:[-]packages(,[-]package)*
Habilita o deshabilita comprobaciones en paquetes específicos. Cada package es el nombre calificado de un paquete o un prefijo de nombre de paquete seguido de .*, que se expande a todos los subpaquetes del paquete dado. Cada package puede ir precedido por un guion (-) para deshabilitar las comprobaciones para un paquete o paquetes especificados.

Para más información, véase la sección DocLint de la documentación del comando javadoc.

-Xlint
Habilita todas las advertencias recomendadas. En esta versión, se recomienda habilitar todas las advertencias disponibles.
-Xlint:[-]key(,[-]key)*
Habilita y/o deshabilita categorías de advertencia usando una o más de las claves descritas a continuación, separadas por comas. Las claves all y none habilitan o deshabilitan todas las categorías (respectivamente); otras claves habilitan la categoría correspondiente, o la deshabilitan si va precedida por un guion (-).

Los valores admitidos para key son:

•
all: Habilita todas las categorías de advertencia.
•
auxiliaryclass: Advierte sobre una clase auxiliar que está oculta en un archivo fuente y se utiliza desde otros archivos.
•
cast: Advierte sobre el uso de conversiones (cast) innecesarias.
•
classfile: Advierte sobre problemas relacionados con el contenido del archivo de clase.
•
dangling-doc-comments: Advierte sobre comentarios de documentación extraños o mal colocados cerca del inicio de una declaración.
•
deprecation: Advierte sobre el uso de elementos obsoletos (deprecated).
•
dep-ann: Advierte sobre elementos marcados como obsoletos en javadoc pero sin la anotación @Deprecated.
•
divzero: Advierte sobre la división por la constante entera 0.
•
empty: Advierte sobre una instrucción vacía después de if.
•
exports: Advierte sobre problemas relacionados con las exportaciones de módulos.
•
fallthrough: Advierte sobre el paso de un caso de una instrucción switch al siguiente.
•

Sin embargo, al igual que en los archivos @archivos, el uso de un comodín no es compatible.

Ejemplos de comillas para argumentos que contienen espacios en blanco:

export JDK_JAVAC_OPTIONS='@"C:\espacios en blanco\archivo_args"'

export JDK_JAVAC_OPTIONS='"@C:\espacios en blanco\archivo_args"'

export JDK_JAVAC_OPTIONS='@C:\"espacios en blanco\"\archivo_args'

ARCHIVOS DE ARGUMENTOS DE LA LÍNEA DE COMANDOS

Un archivo de argumentos puede incluir opciones de línea de comandos y nombres de archivos fuente en cualquier combinación. Los argumentos dentro de un archivo pueden separarse por espacios o por saltos de línea. Si un nombre de archivo contiene espacios incrustados, ponga el nombre de archivo completo entre comillas dobles.

Los nombres de archivo dentro de un archivo de argumentos son relativos al directorio actual, no a la ubicación del archivo de argumentos. Los comodines (*) no están permitidos en estas listas (como para especificar *.java). El uso del signo arroba (@) para interpretar archivos recursivamente no es compatible. Las opciones -J no son compatibles porque se pasan al lanzador, que no admite archivos de argumentos.

Al ejecutar el comando javac, pase la ruta y el nombre de cada archivo de argumentos con el carácter de signo arroba (@) como prefijo. Cuando el comando javac encuentra un argumento que comienza con el signo arroba (@), expande el contenido de ese archivo en la lista de argumentos.

DISPOSICIÓN DEL CÓDIGO FUENTE

En el lenguaje Java, las clases e interfaces se pueden organizar en paquetes, y los paquetes se pueden organizar en módulos. javac espera que la disposición física de los archivos fuente en los directorios del sistema de archivos refleje la organización de las clases en paquetes y de los paquetes en módulos.

Es una convención ampliamente adoptada que los nombres de los módulos y paquetes comiencen con una letra minúscula, y que los nombres de las clases comiencen con una letra mayúscula.

Disposición del Código Fuente para un Paquete

Cuando las clases e interfaces se organizan en un paquete, el paquete se representa como un directorio, y cualquier subpaquete se representa como subdirectorios.

Por ejemplo:

•
El paquete p se representa como un directorio llamado p.
•
El paquete p.q —es decir, el subpaquete q del paquete p— se representa como el subdirectorio q del directorio p. Por lo tanto, el árbol de directorios que representa el paquete p.q es p\q en Windows, y p/q en otros sistemas.
•
El paquete p.q.r se representa como el árbol de directorios p\q\r (en Windows) o p/q/r (en otros sistemas).

Dentro de un direc

Structure of Source Code

A Java source file is a text file that contains Java declarations and statements. The name of the file must be the same as the name of the public class or interface declared in the file. The file name must be followed by the .java extension.

For example, if a public class is named MyClass, the source file must be named MyClass.java.

If a source file declares multiple classes or interfaces, or if it declares a public class or interface, then the file name must be the same as the public declaration. For example, if a file contains the public class MyClass, and also contains the declarations of classes HelperClass and AnotherClass, the file must be named MyClass.java.

A Java source file may declare at most one public class or interface. If a source file declares a public class or interface, then the name of the source file must be the same as the name of the public declaration.

A source file may contain zero or more non-public classes and interfaces. If a source file contains only non-public classes and interfaces, then the name of the source file is arbitrary, but must be followed by the .java extension.

Packages are organized in a hierarchy of directories. A package named p is represented by a directory named p. A package named p.q is represented by a subdirectory named q within the directory p. A source file in a package is located in the directory corresponding to the package.

For example:

•
The class X declared in package p is represented by the file X.java in the p directory.
•
The class Y declared in package p.q is represented by the file Y.java in the q subdirectory of directory p.
•
The class Z declared in package p.q.r is represented by the file Z.java in the r subdirectory of p\q (en Windows) o p/q (en otros sistemas).

In some situations, it is convenient to split the code into separate directories, each structured as described above, and the aggregate list of directories specified to javac.

Arrangement of Source Code for a Module

In the Java language, a module is a set of packages designed for reuse. In addition to .java files for classes and interfaces, each module has a source file called module-info.java which:

1.
declares the module's name;
2.
lists the packages exported by the module (to allow reuse by other modules);
3.
lists other modules required by the module (to reuse their exported packages).

When packages are organized into a module, the module is represented by one or more directories representing the packages in the module, one of which contains the module-info.java file. It may be convenient, but it is not required, to use a single directory, named after the module, to contain the module-info.java file alongside the directory tree which represents the packages in the module (i.e., the package hierarchy described above). The exact arrangement of source code for a module is typically dictated by the conventions adopted by a development environment (IDE) or build system.

For example:

•
The module a.b.c may be represented by the directory a.b.c, on all systems.
•
The module's declaration is represented by the file module-info.java in the a.b.c directory.
•
If the module contains package p.q.r, then the a.b.c directory contains the directory tree p\q\r (en Windows) o p/q/r (en otros sistemas).

The development environment may prescribe some directory hierarchy between the directory named for the module and the source files to be read by javac.

For example:

•
The module a.b.c may be represented by the directory a.b.c
•
The module's declaration and the module's packages may be in some subdirectory of a.b.c, such as src\main\java (en Windows) o src/main/java (en otros sistemas).

CONFIGURING A COMPILATION

This section describes how to configure javac to perform a basic compilation.

See Configuring the Module System for additional details for use when compiling for a release of the platform that supports modules.

Source Files

•
Specify the source files to be compiled on the command line.

If there are no compilation errors, the corresponding class files will be placed in the output directory.

Some systems may limit the amount you can put on a command line; to work around those limits, you can use argument files.

When compiling code for modules, you can also specify source files indirectly, by using the --module or -m option.

Output Directory

•
Use the -d option to specify an output directory in which to put the compiled class files.

This will normally be organized in a package hierarchy, unless you are compiling source code from multiple modules, in which case it will be organized as a module hierarchy.

When the compilation has been completed, if you are compiling one or more modules, you can place the output directory on the module path for the Java launcher; otherwise, you can place the place the output directory on the class path for the Java launcher.

Precompiled Code

The code to be compiled may refer to libraries beyond what is provided by the platform. If so, you must place these libraries on the class path or module path. If the library code is not in a module, place it on the class path; if it is in a module, place it on the module path.

•
Use the --class-path option to specify libraries to be placed on the class path. Locations on the class path should be organized in a package hierarchy. You can also use alternate forms of the option: -classpath or -cp.
•
Use the --module-path option to specify libraries to be placed on the module path. Locations on the module path should either be modules or directories of modules. You can also use an alternate form of the option: -p.

See Configuring the Module System for details on how to modify the default configuration of library modules.

Note: the options for the class path and module path are not mutually exclusive, although it is not common to specify the class path when compiling code for one or more modules.

Additional Source Files

The code to be compiled may refer to types in additional source files that are not specified on the command line. If so, you must put those source files on either the source path or module path. You can only specify one of these options: if you are not compiling code for a module, or if you are only compiling code for a single module, use the source path; if you are compiling code for multiple modules, use the module source path.

•
Use the --source-path option to specify the locations of additional source files that may be read by javac. Locations on the source path should be organized in a package hierarchy. You can also use an alternate form of the option: -sourcepath.
•
Use the --module-source-path option one or more times to specify the location of additional source files in different modules that may be read by javac, or when compiling source files in multiple modules. You can either specify the locations for each module individually, or you can organize the source files so that you can specify the locations all together. For more details, see The Module Source Path Option.

If you want to be able to refer to types in additional source files but do not want them to be compiled, use the -implicit option.

Note: if you are compiling code for multiple modules, you must always specify a module source path, and all source files specified on the command line must be in one of the directories on the module source path, or in a subdirectory thereof.

CONFIGURAR EL SISTEMA DE MÓDULOS

Si desea incluir módulos adicionales en su compilación, use la opción --add-modules. Esto puede ser necesario cuando compile código que no está en un módulo, o que está en un módulo automático, y el código hace referencia a la API en los módulos adicionales.

Si desea restringir el conjunto de módulos en su compilación, use la opción --limit-modules. Esto puede ser útil si desea asegurarse de que el código que está compilando sea capaz de ejecutarse en un sistema con un conjunto limitado de módulos instalados.

Si desea romper el encapsulamiento y especificar que se deben considerar paquetes adicionales exportados desde un módulo, use la opción --add-exports. Esto puede ser útil al realizar pruebas de caja blanca; se desaconseja encarecidamente confiar en el acceso a API internas en código de producción.

Si desea especificar que se deben considerar paquetes adicionales requeridos por un módulo, use la opción --add-reads. Esto puede ser útil al realizar pruebas de caja blanca; se desaconseja encarecidamente confiar en el acceso a API internas en código de producción.

Puede aplicar parches de contenido adicional a cualquier módulo usando la opción --patch-module. Consulte [Aplicar parches a un módulo] para obtener más detalles.

BUSCAR DECLARACIONES DE MÓDULOS, PAQUETES Y TIPOS

Para compilar un archivo fuente, el compilador a menudo necesita información sobre un módulo o tipo, pero la declaración no se encuentra en los archivos fuente especificados en la línea de comandos.

javac necesita información de tipos para cada clase o interfaz utilizada, extendida o implementada en el archivo fuente. Esto incluye clases e interfaces no mencionadas explícitamente en el archivo fuente, pero que proporcionan información a través de la herencia.

Por ejemplo, al crear una subclase de java.awt.Window, también está utilizando las clases ancestrales de Window: java.awt.Container, java.awt.Component y java.lang.Object.

Al compilar código para un módulo, el compilador también necesita tener disponible la declaración de ese módulo.

Una búsqueda exitosa puede producir un archivo de clase, un archivo fuente, o ambos. Si se encuentran ambos, puede usar la opción -Xprefer para indicar al compilador cuál usar.

Si una búsqueda encuentra y utiliza un archivo fuente, entonces por defecto javac compila ese archivo fuente. Este comportamiento se puede modificar con -implicit.

Es posible que el compilador no descubra la necesidad de cierta información de tipo hasta después de que finalice el procesamiento de anotaciones. Cuando la información de tipo se encuentra en un archivo fuente y no se especifica ninguna opción -implicit, el compilador emite una advertencia de que el archivo se está compilando sin estar sujeto al procesamiento de anotaciones. Para deshabilitar la advertencia, especifique el archivo en la línea de comandos (para que esté sujeto al procesamiento de anotaciones) o use la opción -implicit para especificar si se deben generar archivos de clase para dichos archivos fuente o no.

La forma en que javac localiza las declaraciones de esos tipos depende de si la referencia existe dentro del código de un módulo o no.

Buscar en rutas orientadas a paquetes

Al buscar un archivo fuente o de clase en una ruta compuesta por ubicaciones orientadas a paquetes, javac verificará cada ubicación en la ruta en orden para la posible presencia del archivo. La primera aparición de un archivo particular oculta cualquier aparición posterior de archivos con el mismo nombre. Este ocultamiento no afecta ninguna búsqueda de archivos con un nombre diferente. Esto puede ser conveniente al buscar archivos fuente, que pueden agruparse en diferentes ubicaciones, como código compartido, código específico de plataforma y código generado. También puede ser útil al inyectar versiones alternativas de un archivo de clase en un paquete, para depuración u otras razones de instrumentación. Pero, también puede ser peligroso, como al poner versiones incompatibles de una biblioteca en la ruta de clases.

Buscar en rutas orientadas a módulos

Antes de escanear cualquier ruta de módulos para obtener declaraciones de paquetes o tipos, javac escaneará perezosamente las siguientes rutas y ubicaciones para determinar los módulos que se utilizarán en la compilación.

•
La ruta de fuentes de módulos (ver la opción --module-source-path)
•
La ruta para módulos actualizables (ver la opción --upgrade-module-path)
•
Los módulos del sistema (ver la opción --system)
•
La ruta de módulos del usuario (ver la opción --module-path)

Para cualquier módulo, la primera aparición del módulo durante el escaneo oculta completamente cualquier aparición posterior de un módulo con el mismo nombre. Al localizar los módulos, javac puede determinar los paquetes exportados por el módulo y asociar a cada módulo una ruta orientada a paquetes para el contenido del módulo. Para cualquier módulo compilado previamente, esta ruta típicamente será una única entrada para un directorio o un archivo que proporciona una jerarquía similar a un directorio interno, como un archivo JAR. Por lo tanto, al buscar un tipo que se encuentra en un paquete conocido por ser exportado por un módulo, javac puede localizar la declaración de forma directa y eficiente.

Buscar la declaración de un módulo

Si el módulo ha sido compilado previamente, la declaración del módulo se encuentra en un archivo llamado module-info.class en la raíz de la jerarquía de paquetes del contenido del módulo.

Si el módulo es uno de los que se están compilando actualmente, la declaración del módulo será el archivo llamado module-info.class en la raíz de la jerarquía de paquetes del módulo en el directorio de salida de clases, o el archivo llamado module-info.java en una de las ubicaciones de la ruta de fuentes o en una de las rutas de fuentes de módulos para el módulo.

Buscar la declaración de un tipo cuando la referencia no está en un módulo

Al buscar un tipo al que se hace referencia en código que no está en un módulo, javac buscará en los siguientes lugares:

•
Las clases de la plataforma (o los tipos en paquetes exportados de los módulos de la plataforma) (Esto es solo para archivos de clase compilados).
•
Tipos en paquetes exportados de cualquier módulo en la ruta de módulos, si corresponde. (Esto es solo para archivos de clase compilados).
•
Tipos en paquetes en la ruta de clases y/o ruta de fuentes:
•
Si se especifican ambas, javac busca archivos de clase compilados en la ruta de clases y archivos fuente en la ruta de fuentes.
•
Si se especifica la ruta de clases, pero no la ruta de fuentes, javac busca archivos de clase compilados y archivos fuente en la ruta de clases.
•
Si no se especifica la ruta de clases, se utiliza el directorio actual por defecto.

Al buscar un tipo en la ruta de clases y/o ruta de fuentes, si se encuentra tanto un archivo de clase compilado como un archivo fuente, por defecto se utilizará el archivo modificado más recientemente. Si el archivo fuente es más nuevo, se compilará y podrá reemplazar cualquier versión previamente compilada del archivo. Puede usar la opción -Xprefer para anular el comportamiento predeterminado.

Al buscar un tipo al que se hace referencia en código de un módulo, javac examinará la declaración del módulo contenedor para determinar si el tipo se encuentra en un paquete que está exportado desde otro módulo que es legible por el módulo contenedor. Si es así,

A menos que el módulo sea otro de los módulos que se están compilando, javac solo buscará archivos de clase compilados. En otras palabras, javac no buscará archivos fuente en módulos de plataforma o módulos en la ruta de módulos.

•
Archivos fuente especificados en la línea de comandos o en la ruta fuente o ruta de fuente del módulo.
•
Archivos previamente compilados en el directorio de salida.

JERARQUÍAS DE DIRECTORIOS

javac generalmente asume que los archivos fuente y los archivos de clase compilados se organizarán en una jerarquía de directorios del sistema de archivos o en un tipo de archivo que admita una jerarquía de directorios interna, como un archivo JAR. Se admiten tres tipos diferentes de jerarquía: una jerarquía de paquetes, una jerarquía de módulos y una jerarquía de fuente de módulo.

Si bien javac es bastante flexible con la organización del código fuente, más allá de la expectativa de que el código fuente se organizará en uno o varias jerarquías de paquetes, y generalmente puede acomodar las organizaciones prescritas por entornos de desarrollo y herramientas de compilación, las herramientas de Java en general, y javac y el lanzador de Java en particular, son más estrictos con la organización de los archivos de clase compilados, y estos se organizarán en jerarquías de paquetes o jerarquías de módulos, según corresponda.

La ubicación de estas jerarquías se especifica a javac con opciones de línea de comandos, cuyos nombres suelen terminar en "path", como --source-path o --class-path. Además, como regla general, las opciones de ruta cuyos nombres incluyen la palabra module, como --module-path, se utilizan para especificar jerarquías de módulos, aunque algunas opciones de ruta relacionadas con módulos permiten especificar una jerarquía de paquetes por módulo. Todas las demás opciones de ruta se utilizan para especificar jerarquías de paquetes.

Jerarquía de paquetes

En una jerarquía de paquetes, los directorios y subdirectorios se utilizan para representar las partes componentes del nombre del paquete, y el archivo fuente o el archivo de clase compilado para un tipo se almacena como un archivo con la extensión .java o .class en el directorio más anidado.

Por ejemplo, en una jerarquía de paquetes, el archivo fuente de una clase com.example.MyClass se almacenará en el archivo com/example/MyClass.java

Jerarquía de módulos

En una jerarquía de módulos, el primer nivel de directorios se nombra según los módulos de la jerarquía; dentro de cada uno de esos directorios, el contenido del módulo se organiza en jerarquías de paquetes.

Por ejemplo, en una jerarquía de módulos, el archivo de clase compilado para un tipo llamado com.example.MyClass en un módulo llamado my.library se almacenará en my.library/com/example/MyClass.class.

Los diversos directorios de salida utilizados por javac (el directorio de salida de clases, el directorio de salida de fuentes y el directorio de salida de encabezados nativos) se organizarán en una jerarquía de módulos cuando se compilen varios módulos.

Jerarquía de fuente de módulos

Aunque el código fuente de cada módulo individual siempre debe organizarse en una jerarquía de paquetes, puede ser conveniente agrupar esas jerarquías en una jerarquía de fuente de módulos. Esto es similar a una jerarquía de módulos, excepto que puede haber directorios intermedios entre el directorio del módulo y el directorio que es la raíz de la jerarquía de paquetes para el código fuente del módulo.

Por ejemplo, en una jerarquía de fuente de módulos, el archivo fuente de un tipo llamado com.example.MyClass en un módulo llamado my.library puede almacenarse en un archivo como my.library/src/main/java/com/example/MyClass.java.

LA OPCIÓN RUTA FUENTE DEL MÓDULO

La opción --module-source-path tiene dos formas: una forma específica del módulo, en la que se proporciona una ruta de paquete para cada módulo que contiene código para compilar, y una forma de patrón de módulo, en la que la ruta fuente para cada módulo se especifica mediante un patrón. La forma específica del módulo es generalmente más simple de usar cuando solo hay un pequeño número de módulos involucrados; la forma de patrón de módulo puede ser más conveniente cuando el número de módulos es grande y los módulos están organizados de manera regular que se puede describir mediante un patrón.

Se pueden proporcionar varias instancias de la opción --module-source-path, cada una utilizando la forma de patrón de módulo o la forma específica del módulo, sujeto a las siguientes limitaciones:

•
la forma de patrón de módulo se puede usar como máximo una vez
•
la forma específica del módulo se puede usar como máximo una vez para cualquier módulo dado

Si se utiliza la forma específica del módulo para algún módulo, la ruta de búsqueda asociada anula cualquier ruta que de otro modo podría haber sido inferida de la forma de patrón de módulo.

Forma específica del módulo

La forma específica del módulo permite proporcionar una ruta de búsqueda explícita para cualquier módulo específico. Esta forma es:

•
--module-source-path nombre-módulo=ruta-archivo (separador-ruta ruta-archivo)*

El carácter separador de ruta es ; en Windows, y : en otros sistemas.

Nota: esto es similar a la forma utilizada para la opción --patch-module.

Forma de patrón de módulo

La forma de patrón de módulo permite una especificación concisa de la ruta fuente del módulo para cualquier número de módulos organizados de manera regular.

•
--module-source-path patrón

El patrón se define mediante las siguientes reglas, que se aplican en orden:

•
El argumento se considera una serie de segmentos separados por el carácter separador de ruta (; en Windows, y : en otros sistemas).
•
Cada segmento que contiene llaves de la forma
cadena1{alt1 ( ,alt2 )* } cadena2

se considera reemplazado por una serie de segmentos formados al "expandir" las llaves:

cadena1 alt1 cadena2
cadena1 alt2 cadena2
y así sucesivamente...

Las llaves pueden anidarse.

Esta regla se aplica para todos los usos de llaves de este tipo.

•
Cada segmento debe tener como máximo un asterisco (*). Si un segmento no contiene un asterisco, se considera como si se le añadieran el carácter separador de archivo y un asterisco.

Para cualquier módulo M, la ruta fuente para ese módulo se forma a partir de la serie de segmentos obtenidos al sustituir el nombre del módulo M por el asterisco en cada segmento.

Nota: en este contexto, el asterisco se utiliza solo como un marcador especial, para denotar la posición en la ruta del nombre del módulo. No debe confundirse con el uso de * como carácter comodín de nombre de archivo, como se encuentra en la mayoría de los sistemas operativos.

APLICANDO PARCHES A MÓDULOS

javac permite aplicar parches a cualquier contenido, ya sea en forma fuente o compilada, en cualquier módulo utilizando la opción --patch-module. Es posible que desee hacer esto para compilar implementaciones alternativas de una clase que se aplicará con parches en tiempo de ejecución a una JVM, o para inyectar clases adicionales en el módulo, como al realizar pruebas.

La forma de la opción es:

•
--patch-module nombre-módulo=ruta-archivo (separador-ruta ruta-archivo )*

El carácter separador de ruta es ; en Windows, y : en otros sistemas. Las rutas proporcionadas para el módulo deben especificar la raíz de una jerarquía de paquetes para el contenido del módulo.

La opción se puede proporcionar como máximo una vez para cualquier módulo dado. Cualquier contenido en la ruta ocultará cualquier contenido con el mismo nombre más adelante en la ruta y en el módulo parcheado.

Al aplicar parches de código fuente a más de un módulo, también se debe usar --module-source-path, para que el directorio de salida se organice en una jerarquía de módulos y sea capaz de contener los archivos de clase compilados para los módulos que se están compilando.

PROCESAMIENTO DE ANOTACIONES

El comando javac proporciona soporte directo para el procesamiento de anotaciones.

La API para procesadores de anotaciones se define en los paquetes javax.annotation.processing y javax.lang.model y sus subpaquetes.

Cómo funciona el procesamiento de anotaciones

Se solicita el procesamiento de anotaciones utilizando una opción para configurar el procesamiento de anotaciones, como -processor, --processor-path, --processor-module-path<

/b> o explícitamente habilitando el procesamiento con las opciones -proc:full o -proc:only. El procesamiento de anotaciones se deshabilita usando la opción -proc:none.

Si se solicita el procesamiento de anotaciones, el compilador busca cualquier procesador de anotaciones que esté disponible.

La ruta de búsqueda se puede especificar con la opción -processorpath. Si no se especifica ninguna ruta, se utiliza la ruta de clases del usuario. Los procesadores se ubican mediante archivos de configuración de proveedores de servicios llamados META-INF/services/javax.annotation.processing.Processor en la ruta de búsqueda. Dichos archivos deben contener los nombres de los procesadores de anotaciones que se utilizarán, listados uno por línea. Alternativamente, los procesadores se pueden especificar explícitamente, utilizando la opción -processor.

Después de escanear los archivos fuente y las clases en la línea de comandos para determinar qué anotaciones están presentes, el compilador consulta a los procesadores para determinar qué anotaciones procesan. Cuando se encuentra una coincidencia, se llama al procesador. Un procesador puede reclamar las anotaciones que procesa, en cuyo caso no se intenta encontrar más procesadores para esas anotaciones. Una vez que todas las anotaciones han sido reclamadas, el compilador no busca procesadores adicionales.

Si algún procesador genera nuevos archivos fuente, se produce otra ronda de procesamiento de anotaciones: Se escanean los archivos fuente recién generados y las anotaciones se procesan como antes. Los procesadores que se llamaron en rondas anteriores también se llamarán en todas las rondas posteriores. Esto continúa hasta que no se generen nuevos archivos fuente.

Después de una ronda en la que no se generan nuevos archivos fuente, los procesadores de anotaciones se llaman una última vez, para darles la oportunidad de completar cualquier trabajo restante. Finalmente, a menos que se utilice la opción -proc:only, el compilador compila los archivos fuente originales y todos los generados.

Si utiliza un procesador de anotaciones que genera archivos fuente adicionales para ser incluidos en la compilación, puede especificar un módulo predeterminado para los nuevos archivos, para su uso cuando tampoco se genera una declaración de módulo. En este caso, utilice la opción --default-module-for-created-files.

Entorno de Compilación y Entorno de Ejecución.

Las declaraciones en archivos fuente y archivos de clase compilados previamente son analizadas por javac en un *entorno de compilación* que es distinto del *entorno de ejecución* utilizado para ejecutar el propio javac. Aunque hay una similitud deliberada entre muchas opciones de javac y opciones de igual nombre para el lanzador de Java, como --class-path, --module-path y demás, es importante entender que, en general, las opciones de javac solo afectan al entorno en el que se compilan los archivos fuente, y no afectan a la operación del propio javac.

La distinción entre el entorno de compilación y el entorno de ejecución es significativa cuando se trata de usar procesadores de anotaciones. Aunque los procesadores de anotaciones procesan elementos (declaraciones) que existen en el entorno de compilación, el propio procesador de anotaciones se ejecuta en el entorno de ejecución. Si un procesador de anotaciones tiene dependencias de bibliotecas que no están en módulos, las bibliotecas se pueden colocar, junto con el propio procesador de anotaciones, en la ruta del procesador. (Consulte la opción --processor-path). Si el procesador de anotaciones y sus dependencias están en módulos, debe usar en su lugar la ruta de módulos del procesador. (Consulte la opción --processor-module-path). Cuando estas son insuficientes, puede ser necesario proporcionar una configuración adicional del entorno de ejecución. Esto se puede hacer de dos maneras:

1.
Si javac se invoca desde la línea de comandos, se pueden pasar opciones al tiempo de ejecución subyacente prefijando la opción con -J.
2.
Puede iniciar una instancia de una Máquina Virtual Java directamente y utilizar opciones de línea de comandos y API para configurar un entorno en el que javac pueda invocarse a través de una de sus APIs.

COMPILACIÓN PARA VERSIONES ANTERIORES DE LA PLATAFORMA

javac puede compilar código que se utilizará en otras versiones de la plataforma, utilizando la opción --release, o las opciones --source/-source y --target/-target, junto con opciones adicionales para especificar las clases de la plataforma.

Dependiendo de la versión de la plataforma deseada, existen algunas restricciones en algunas de las opciones que se pueden utilizar.

•
Al compilar para JDK 8 y versiones anteriores, no puede usar ninguna opción que esté destinada a usarse con el sistema de módulos. Esto incluye todas las siguientes opciones:
•
--module-source-path, --upgrade-module-path, --system, --module-path, --add-modules, --add-exports, --add-opens, --add-reads, --limit-modules, --patch-module

Si usa las opciones --source/-source o --target/-target, también debería configurar las clases de plataforma apropiadas usando la familia de opciones de ruta de clases de arranque (boot class path).

•
Al compilar para JDK 9 y versiones posteriores, no puede usar ninguna opción destinada a configurar la ruta de clases de arranque (boot class path). Esto incluye todas las siguientes opciones:
•
-Xbootclasspath/p:, -Xbootclasspath, -Xbootclasspath/a:, -endorseddirs, -Djava.endorsed.dirs, -extdirs, -Djava.ext.dirs, -profile

Si usa las opciones --source/-source o --target/-target, también debería configurar las clases de plataforma apropiadas usando la opción --system para indicar la ubicación de una versión instalada apropiada de JDK.

Al usar la opción --release, solo se puede utilizar la API documentada soportada para esa versión; no puede usar ninguna opción para romper la encapsulación y acceder a clases internas.

APIS

El compilador javac se puede invocar usando una API de tres maneras diferentes:

La API del Compilador de Java
Esta proporciona la forma más flexible de invocar al compilador, incluida la capacidad de compilar archivos fuente proporcionados en búferes de memoria u otros sistemas de archivos no estándar.
La API ToolProvider
Se puede obtener un ToolProvider para javac llamando a ToolProvider.findFirst("javac"). Esto devuelve un objeto con la funcionalidad equivalente a la herramienta de línea de comandos.

Nota: Esta API no debe confundirse con la API de igual nombre en el paquete javax.tools.

La API Heredada de javac
Esta API se mantiene solo para compatibilidad con versiones anteriores. Todo el código nuevo debe usar la API del Compilador de Java o la API ToolProvider.
