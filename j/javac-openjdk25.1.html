NOMBRE

javac - lee declaraciones Java y las compila en archivos de clase

SINOPSIS

javac [opciones] [archivos-fuente-o-nombres-de-clase]

opciones
Opciones de línea de comandos.
archivos-fuente-o-nombres-de-clase
Archivos fuente que se van a compilar (por ejemplo, Shape.java) o los nombres de clases compiladas previamente que se van a procesar para anotaciones (por ejemplo, geometry.MyShape).

DESCRIPCIÓN

El comando javac lee archivos fuente que contienen declaraciones de módulos, paquetes y tipos escritas en el lenguaje de programación Java, y las compila en archivos de clase que se ejecutan en la Máquina Virtual de Java.

El comando javac también puede procesar anotaciones en archivos fuente de Java y clases.

Los archivos fuente deben tener una extensión de nombre de archivo .java. Los archivos de clase tienen una extensión de nombre de archivo .class. Tanto los archivos fuente como los de clase normalmente tienen nombres de archivo que identifican el contenido. Por ejemplo, una clase llamada Shape se declararía en un archivo fuente llamado Shape.java, y se compilaría en un archivo de clase llamado Shape.class.

Hay dos formas de especificar archivos fuente a javac:

  • Para un número pequeño de archivos fuente, puede listar sus nombres de archivo en la línea de comandos.
  • Para un número grande de archivos fuente, puede usar la opción @nombreDeArchivo en la línea de comandos para especificar un archivo de argumentos que liste sus nombres de archivo. Consulte Opciones estándar para una descripción de la opción y Archivos de argumentos de línea de comandos para una descripción de los archivos de argumentos de javac.

El orden de los archivos fuente especificados en la línea de comandos o en un archivo de argumentos no es importante. javac compilará los archivos juntos, como un grupo, y resolverá automáticamente cualquier dependencia entre las declaraciones en los diversos archivos fuente.

javac espera que los archivos fuente estén organizados en una o más jerarquías de directorios en el sistema de archivos, descritas en Disposición del código fuente.

Para compilar un archivo fuente, javac necesita encontrar la declaración de cada clase o interfaz que sea usada, extendida o implementada por el código en el archivo fuente. Esto permite que javac verifique que el código tiene derecho a acceder a esas clases e interfaces. En lugar de especificar los archivos fuente de esas clases e interfaces explícitamente, puede usar opciones de línea de comandos para indicarle a javac dónde buscar sus archivos fuente. Si ha compilado esos archivos fuente previamente, puede usar opciones para indicarle a javac dónde buscar los archivos de clase correspondientes. Las opciones, que todas tienen nombres que terminan en "path", se describen en Opciones estándar, y se describen con más detalle en Configuración de una compilación y Búsqueda de declaraciones de módulos, paquetes y tipos.

De forma predeterminada, javac compila cada archivo fuente en un archivo de clase en el mismo directorio que el archivo fuente. Sin embargo, se recomienda especificar un directorio de destino separado con la opción -d.

Las opciones de línea de comandos y las variables de entorno también controlan cómo javac realiza diversas tareas:

  • Compilar código para ejecutarse en versiones anteriores del JDK.
  • Compilar código para ejecutarse bajo un depurador.
  • Verificar problemas estilísticos en el código fuente de Java.
  • Verificar problemas en los comentarios de javadoc (/** ... */).
  • Procesar anotaciones en archivos fuente y archivos de clase.
  • Actualizar y parchear módulos en el entorno de tiempo de compilación.

javac admite Compilar para versiones anteriores de la plataforma y también se puede invocar desde código Java usando una de varias API

OPTIONS

javac provides standard options, and extra options that are either non-standard or are for advanced use.

Some options take one or more arguments. If an argument contains spaces or other whitespace characters, the value should be quoted according to the conventions of the environment being used to invoke javac. If the option begins with a single dash (-) the argument should either directly follow the option name, or should be separated with a colon (:) or whitespace, depending on the option. If the option begins with a double dash (--), the argument may be separated either by whitespace or by an equals (=) character with no additional whitespace. For example,

-Aname="J. Duke"
-proc:only
-d myDirectory
--module-version 3
--module-version=3

In the following lists of options, an argument of path represents a search path, composed of a list of file system locations separated by the platform path separator character, (semicolon ; on Windows, or colon : on other systems.) Depending on the option, the file system locations may be directories, JAR files or JMOD files.

Standard Options

@filename
Reads options and file names from a file. To shorten or simplify the javac command, you can specify one or more files that contain arguments to the javac command (except -J options). This lets you to create javac commands of any length on any operating system. See Command-Line Argument Files.
-Akey[=value]
Specifies options to pass to annotation processors. These options are not interpreted by javac directly, but are made available for use by individual processors. The key value should be one or more identifiers separated by a dot (.).
--add-modules module,module
Specifies root modules to resolve in addition to the initial modules, or all modules on the module path if module is ALL-MODULE-PATH.
--boot-class-path path or -bootclasspath path
Overrides the location of the bootstrap class files.
Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details. For JDK 9 or later, see --system.
--class-path path, -classpath path, or -cp path
Specifies where to find user class files and annotation processors. This class path overrides the user class path in the CLASSPATH environment variable.
  • If --class-path, -classpath, or -cp are not specified, then the user class path is the value of the CLASSPATH environment variable, if that is set, or else the current directory.
  • If not compiling code for modules, if the --source-path or -sourcepath` option is not specified, then the user class path is also searched for source files.
  • If the -processorpath option is not specified, then the class path is also searched for annotation processors.
-d directory
Sets the destination directory (or class output directory) for class files. If a class is part of a package, then javac puts the class file in a subdirectory that reflects the module name (if appropriate) and package name. The directory, and any necessary subdirectories, will be created if they do not already exist.
If the -d option is not specified, then javac puts each class file in the same directory as the source file from which it was generated. Except when compiling code for multiple modules, the contents of the class output directory will be organized in a package hierarchy. When compiling code for multiple modules, the contents of the output directory will be organized in a module hierarchy, with the contents of each module in a separate subdirectory, each organized as a package hierarchy. Note: When compiling code for one or more modules, the class output directory will automatically be checked when searching for previously compiled classes. When not compiling for modules, for backwards compatibility, the directory is not automatically checked for previously compiled classes, and so it is recommended to specify the class output directory as one of the locations on the user class path, using the --class-path option or one of its alternate forms.
-deprecation
Shows a description of each use or override of a deprecated member or class. Without the -deprecation option, javac shows a summary of the source files that use or override deprecated members or classes. The -deprecation option is shorthand for -Xlint:deprecation.
--enable-preview
Enables preview language features. Used in conjunction with either -source or --release.
-encoding encoding
Specifies character encoding used by source files, such as EUC-JP and UTF-8. If the -encoding option is not specified, then the platform default converter is used.
-endorseddirs directories
Overrides the location of the endorsed standards path.
Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details.
-extdirs directories
Overrides the location of the installed extensions. directories is a list of directories, separated by the platform path separator (; on Windows, and : otherwise). Each JAR file in the specified directories is searched for class files. All JAR files found become part of the class path.
If you are compiling for a release of the platform that supports the Extension Mechanism, then this option specifies the directories that contain the extension classes. See [Compiling for Other Releases of the Platform]. Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details.
-g
Generates all debugging information, including local variables. By default, only line number and source file information is generated.
-g:[lines, vars, source]
Generates only the kinds of debugging information specified by the comma-separated list of keywords. Valid keywords are:
lines
Line number debugging information.
vars
Local variable debugging information.
source
Source file debugging information.
-g:none
Does not generate debugging information.
-h directory
Specifies where to place generated native header files.
When you specify this option, a native header file is generated for each class that contains native methods or that has one or more constants annotated with the java.lang.annotation.Native annotation. If the class is part of a package, then the compiler puts the native header file in a subdirectory that reflects the module name (if appropriate) and package name. The directory, and any necessary subdirectories, will be created if they do not already exist.
--help, -help or -?
Prints a synopsis of the standard options.
--help-extra or -X
Prints a synopsis of the set of extra options.
--help-lint
Prints the supported keys for the -Xlint option.
-implicit:[none, class]
Specifies whether or not to generate class files for implicitly referenced files:
  • -implicit:class --- Automatically generates class files.
  • -implicit:none --- Suppresses class file generation. If this option is not specified, then the default automatically generates class files. In this case, the compiler issues a warning if any class files are generated when also doing annotation processing. The warning is not issued when the -implicit option is explicitly set. See Searching for Module, Package and Type Declarations.
-Joption
Passes option to the runtime system, where option is one of the Java options described on java command. For example, -J-Xms48m sets the startup memory to 48 MB.
Note: The CLASSPATH environment variable, -classpath option, -bootclasspath option, and -extdirs option do not specify the classes used to run javac. Trying to customize the compiler implementation with these options and variables is risky and often does not accomplish what you want. If you must customize the compiler implementation, then use the -J option to pass options through to the underlying Java launcher.
--limit-modules module,module*
Limits the universe of observable modules.
--module module-name (,module-name)* or -m module-name (,module-name)*
Compiles those source files in the named modules that are newer than the corresponding files in the output directory.
--module-path path or -p path
Specifies where to find application modules.
--module-source-path module-source-path
Specifies where to find source files when compiling code in multiple modules. See The Module Source Path Option.
--module-version version
Specifies the version of modules that are being compiled.
-nowarn
Generate only mandatory warnings.
-parameters
Generates metadata for reflection on method parameters. Stores formal parameter names of constructors and methods in the generated class file so that the method java.lang.reflect.Executable.getParameters from the Reflection API can retrieve them.
-proc:[none, only, full]
Controls whether annotation processing and compilation are done.
  • -proc:none means that compilation takes place without annotation processing
  • -proc:only means that only annotation processing is done, without any subsequent compilation.
  • -proc:full means annotation processing and compilation are done. If this option is not used, annotation processing and compilation are done if at least one other option is used to explicitly configure annotation processing.
-processor class1[,class2,class3...]
Names of the annotation processors to run. This bypasses the default discovery process.
--processor-module-path path
Specifies the module path used for finding annotation processors.
--processor-path path or -processorpath path
Specifies where to find annotation processors. If this option is not used, then the class path is searched for processors.
-profile profile
Checks that the API used is available in the specified profile. This option is deprecated and may be removed in a future release.
Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details.
--release release
Compiles source code according to the rules of the Java programming language for the specified Java SE release, generating class files which target that release. Source code is compiled against the combined Java SE and JDK API for the specified release.
The supported values of release are the current Java SE release and a limited number of previous releases, detailed in the command-line help. For the current release, the Java SE API consists of the java.*, javax.*, and org.* packages that are exported by the Java SE modules in the release; the JDK API consists of the com.* and jdk.* packages that are exported by the JDK modules in the release, plus the javax.* packages that are exported by standard, but non-Java SE, modules in the release. For previous releases, the Java SE API and the JDK API are as defined in that release. Note: When using --release, you cannot also use the --source/-source or --target/-target options. Note: When using --release to specify a release that supports the Java Platform Module System, the --add-exports option cannot be used to enlarge the set of packages exported by the Java SE, JDK, and standard modules in the specified release.
-s directory
Specifies the directory used to place the generated source files. If a class is part of a package, then the compiler puts the source file in a subdirectory that reflects the module name (if appropriate) and package name. The directory, and any necessary subdirectories, will be created if they do not already exist.
Except when compiling code for multiple modules, the contents of the source output directory will be organized in a package hierarchy. When compiling code for multiple modules, the contents of the source output directory will be organized in a module hierarchy, with the contents of each module in a separate subdirectory, each organized as a package hierarchy.
--source release or -source release
Compiles source code according to the rules of the Java programming language for the specified Java SE release. The supported values of release are the current Java SE release and a limited number of previous releases, detailed in the command-line help.
If the option is not specified, the default is to compile source code according to the rules of the Java programming language for the current Java SE release.
--source-path path or -sourcepath path
Specifies where to find source files. Except when compiling multiple modules together, this is the source code path used to search for class or interface definitions.
Note: Classes found through the class path might be recompiled when their source files are also found. See Searching for Module, Package and Type Declarations.
--system jdk | none
Overrides the location of system modules.
--target release or -target release
Generates class files suitable for the specified Java SE release. The supported values of release are the current Java SE release and a limited number of previous releases, detailed in the command-line help.
Note: The target release must be equal to or higher than the source release. (See --source.)
--upgrade-module-path path
Overrides the location of upgradeable modules.
-verbose
Outputs messages about what the compiler is doing. Messages include information about each class loaded and each source file compiled.
--version or -version
Prints version information.
-Werror
Terminates compilation when warnings occur.

-Xdoclint
Enables recommended checks for problems in documentation comments.
-Xdoclint:(all|none|[-]group)[/access]
Enables or disables specific groups of checks in documentation comments.
group can have one of the following values: accessibility, html, missing, reference, syntax. The variable access specifies the minimum visibility level of classes and members that the -Xdoclint option checks. It can have one of the following values (in order of most to least visible): public, protected, package, private. The default access level is private. When prefixed by doclint:, the group names and all can be used with @SuppressWarnings to suppress warnings about documentation comments in parts of the code being compiled. For more information about these groups of checks, see the DocLint section of the javadoc command documentation. The -Xdoclint option is disabled by default in the javac command. For example, the following option checks classes and members (with all groups of checks) that have the access level of protected and higher (which includes protected and public):

-Xdoclint:all/protected

The following option enables all groups of checks for all access levels, except it will not check for HTML errors for classes and members that have the access level of package and higher (which includes package, protected and public):

-Xdoclint:all,-html/package

-Xdoclint/package:[-]packages(,[-]package)*
Enables or disables checks in specific packages. Each package is either the qualified name of a package or a package name prefix followed by .*, which expands to all sub-packages of the given package. Each package can be prefixed with a hyphen (-) to disable checks for a specified package or packages.
For more information, see the DocLint section of the javadoc command documentation.

Enables and/or disables warning categories using the one or more of the keys described below separated by commas. The keys all and none enable or disable all categories (respectively); other keys enable the corresponding category, or disable it if preceded by a hyphen (-).
Supported values for key are:

  • auxiliaryclass: Warns about an auxiliary class that is hidden in a source file, and is used from other files.
  • cast: Warns about the use of unnecessary casts.
  • classfile: Warns about the issues related to classfile contents.
  • dangling-doc-comments: Warns about extra or misplaced documentation comments near the beginning of a declaration.
  • deprecation: Warns about the use of deprecated items.
  • dep-ann: Warns about the items marked as deprecated in javadoc but without the @Deprecated annotation.
  • divzero: Warns about the division by the constant integer 0.
  • empty: Warns about an empty statement after if.
  • exports: Warns about the issues regarding module exports.
  • fallthrough: Warns about the falling through from one case of a switch statement to the next.
  • finally: Warns about finally clauses that do not terminate normally.
  • identity: Warns about use of a value-based class where an identity class is expected
  • incubating: Warns about the use of incubating modules.
  • lossy-conversions: Warns about possible lossy conversions in compound assignment.
  • missing-explicit-ctor: Warns about missing explicit constructors in public and protected classes in exported packages.
  • module: Warns about the module system-related issues.
  • opens: Warns about the issues related to module opens.
  • options: Warns about the issues relating to use of command line options.
  • output-file-clash: Warns if any output file is overwritten during compilation. This can occur, for example, on case-insensitive filesystems.
  • overloads: Warns about the issues related to method overloads.
  • overrides: Warns about the issues related to method overrides.
  • path: Warns about the invalid path elements on the command line.
  • preview: Warns about the use of preview language features.
  • processing: Warns about the issues related to annotation processing.
  • rawtypes: Warns about the use of raw types.
  • removal: Warns about the use of an API that has been marked for removal.
  • restricted: Warns about the use of restricted methods.
  • requires-automatic: Warns developers about the use of automatic modules in requires clauses.
  • requires-transitive-automatic: Warns about automatic modules in requires transitive.
  • serial: Warns about the serializable classes that do not provide a serial version ID. Also warns about access to non-public members from a serializable element.
  • static: Warns about the accessing a static member using an instance.
  • strictfp: Warns about unnecessary use of the strictfp modifier.
  • synchronization: Warns about synchronization attempts on instances of value-based classes. This key is a deprecated alias for identity, which has the same uses and effects. Users are encouraged to use the identity category for all future and existing uses of synchronization.
  • text-blocks: Warns about inconsistent white space characters in text block indentation.
  • this-escape: Warns about constructors leaking this prior to subclass initialization.
  • try: Warns about the issues relating to the use of try blocks (that is, try-with-resources).
  • unchecked: Warns about the unchecked operations.
  • varargs: Warns about the potentially unsafe vararg methods.
  • none: Disables all warning categories. With the exception of all and none, the keys can be used with the @SuppressWarnings annotation to suppress warnings in a part of the source code being compiled. See Examples of Using -Xlint keys.

VARIABLES DE ENTORNO

CLASSPATH

Si la opción --class-path o cualquiera de sus formas alternativas no se especifica, la ruta de clases tomará por defecto el valor de la variable de entorno CLASSPATH si está establecida. Sin embargo, se recomienda que esta variable de entorno no se establezca, y que se use la opción --class-path para proporcionar un valor explícito para la ruta de clases cuando sea necesario.

JDK_JAVAC_OPTIONS

El contenido de la variable de entorno JDK_JAVAC_OPTIONS, separado por espacios en blanco ( ) o caracteres de espacio en blanco (\n, \t, \r, o \f) se antepone a los argumentos de la línea de comandos pasados a javac como una lista de argumentos.

El requisito de codificación para la variable de entorno es el mismo que el de la línea de comandos de javac en el sistema. El contenido de la variable de entorno JDK_JAVAC_OPTIONS se trata de la misma manera que lo especificado en la línea de comandos.

Se pueden usar comillas simples (') o comillas dobles (") para encerrar argumentos que contienen caracteres de espacio en blanco. Todo el contenido entre la comilla de apertura y la primera comilla de cierre coincidente se conserva simplemente eliminando el par de comillas. En caso de que no se encuentre una comilla coincidente, el lanzador abortará con un mensaje de error. Se admiten @archivos tal como se especifican en la línea de comandos. Sin embargo, como en @archivos, no se admite el uso de comodines.

Ejemplos de entrecomillado de argumentos que contienen espacios en blanco:

export JDK_JAVAC_OPTIONS='@"C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='"@C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='@C:\"white spaces"\argfile'

ARCHIVOS DE ARGUMENTOS DE LÍNEA DE COMANDOS

Un archivo de argumentos puede incluir opciones de línea de comandos y nombres de archivos fuente en cualquier combinación. Los argumentos dentro de un archivo pueden estar separados por espacios o caracteres de nueva línea. Si un nombre de archivo contiene espacios incrustados, coloque el nombre completo del archivo entre comillas dobles.

Los nombres de archivo dentro de un archivo de argumentos son relativos al directorio actual, no a la ubicación del archivo de argumentos. No se permiten comodines (*) en estas listas (como para especificar *.java). No se admite el uso del signo arroba (@) para interpretar archivos de forma recursiva. Las opciones -J no son compatibles porque se pasan al lanzador, que no admite archivos de argumentos.

Al ejecutar el comando javac, pase la ruta y el nombre de cada archivo de argumentos con el carácter inicial de signo arroba (@). Cuando el comando javac encuentra un argumento que comienza con el signo arroba (@), expande el contenido de ese archivo en la lista de argumentos.

Ejemplos de uso de javac @nombrearchivo

Archivo de argumentos único
Puede usar un único archivo de argumentos llamado argfile para contener todos los argumentos de javac:

javac @argfile

Este archivo de argumentos podría contener el contenido de ambos archivos mostrados en el siguiente ejemplo Dos archivos de argumentos.
Dos archivos de argumentos
Puede crear dos archivos de argumentos: uno para las opciones de javac y el otro para los nombres de archivos fuente. Tenga en cuenta que las siguientes listas no tienen caracteres de continuación de línea.
Cree un archivo llamado options que contenga lo siguiente: Linux y macOS: 
-d classes
-g
-sourcepath /java/pubs/ws/1.3/src/share/classes
Windows:
-d classes
-g
-sourcepath C:\java\pubs\ws\1.3\src\share\classes
Cree un archivo llamado sources que contenga lo siguiente:
MyClass1.java
MyClass2.java
MyClass3.java
Luego, ejecute el comando javac de la siguiente manera:

javac @options @sources

Archivos de argumentos con rutas
Los archivos de argumentos pueden tener rutas, pero cualquier nombre de archivo dentro de los archivos es relativo al directorio de trabajo actual (no a path1 o path2):

javac @path1/options @path2/sources

ORGANIZACIÓN DEL CÓDIGO FUENTE

En el lenguaje Java, las clases e interfaces se pueden organizar en paquetes, y los paquetes se pueden organizar en módulos. javac espera que la disposición física de los archivos fuente en directorios del sistema de archivos refleje la organización de las clases en paquetes, y de los paquetes en módulos.

Es una convención ampliamente adoptada que los nombres de módulos y los nombres de paquetes comiencen con una letra minúscula, y que los nombres de clases comiencen con una letra mayúscula.

Organización del Código Fuente para un Paquete

Cuando las clases e interfaces se organizan en un paquete, el paquete se representa como un directorio, y cualquier subpaquete se representa como un subdirectorio.

Por ejemplo:

  • El paquete p se representa como un directorio llamado p.
  • El paquete p.q -- es decir, el subpaquete q del paquete p -- se representa como el subdirectorio q del directorio p. El árbol de directorios que representa el paquete p.q es, por lo tanto, p\q en Windows, y p/q en otros sistemas.
  • El paquete p.q.r se representa como el árbol de directorios p\q\r (en Windows) o p/q/r (en otros sistemas).

Dentro de un directorio o subdirectorio, los archivos .java representan clases e interfaces en el paquete o subpaquete correspondiente.

Por ejemplo:

  • La clase X declarada en el paquete p se representa mediante el archivo X.java en el directorio p.
  • La clase Y declarada en el paquete p.q se representa mediante el archivo Y.java en el subdirectorio q del directorio p.
  • La clase Z declarada en el paquete p.q.r se representa mediante el archivo Z.java en el subdirectorio r de p\q (en Windows) o p/q (en otros sistemas).

En algunas situaciones, es conveniente dividir el código en directorios separados, cada uno estructurado como se describe arriba, y la lista agregada de directorios especificada a javac.

Organización del Código Fuente para un Módulo

En el lenguaje Java, un módulo es un conjunto de paquetes diseñados para su reutilización. Además de los archivos .java para clases e interfaces, cada módulo tiene un archivo fuente llamado module-info.java que:

1.
declara el nombre del módulo;
2.
enumera los paquetes exportados por el módulo (para permitir su reutilización por otros módulos);
3.
enumera otros módulos requeridos por el módulo (para reutilizar sus paquetes exportados).

Cuando los paquetes se organizan en un módulo, el módulo se representa mediante uno o más directorios que representan los paquetes en el módulo, uno de los cuales contiene el archivo module-info.java. Puede ser conveniente, pero no es obligatorio, usar un único directorio, nombrado como el módulo, para contener el archivo module-info.java junto con el árbol de directorios que representa los paquetes en el módulo (es decir, la jerarquía de paquetes descrita arriba). La disposición exacta del código fuente para un módulo generalmente está dictada por las convenciones adoptadas por un entorno de desarrollo (IDE) o sistema de compilación.

Por ejemplo:

  • El módulo a.b.c puede representarse mediante el directorio a.b.c, en todos los sistemas.
  • La declaración del módulo se representa mediante el archivo module-info.java en el directorio a.b.c.
  • Si el módulo contiene el paquete p.q.r, entonces el directorio a.b.c contiene el árbol de directorios p\q\r (en Windows) o p/q/r (en otros sistemas).

El entorno de desarrollo puede prescribir alguna jerarquía de directorios entre el directorio nombrado para el módulo y los archivos fuente que serán leídos por javac.

Por ejemplo:

  • El módulo a.b.c puede representarse mediante el directorio a.b.c
  • La declaración del módulo y los paquetes del módulo pueden estar en algún subdirectorio de a.b.c, como src\main\java (en Windows) o src/main/java (en otros sistemas).

CONFIGURAR UNA COMPILACIÓN

Esta sección describe cómo configurar javac para realizar una compilación básica.

Consulte Configurar el sistema de módulos para obtener detalles adicionales que debe usar al compilar para una versión de la plataforma que admite módulos.

Archivos fuente

•
Especifique los archivos fuente que se van a compilar en la línea de comandos.

Si no hay errores de compilación, los archivos de clase correspondientes se colocarán en el directorio de salida.

Algunos sistemas pueden limitar la cantidad que se puede poner en una línea de comandos; para evitar esas limitaciones, puede usar archivos de argumentos.

Al compilar código para módulos, también puede especificar archivos fuente indirectamente, usando la opción --module o -m.

Directorio de salida

•
Use la opción -d para especificar un directorio de salida en el que colocar los archivos de clase compilados.

Normalmente, esto se organizará en una jerarquía de paquetes, a menos que esté compilando código fuente de varios módulos, en cuyo caso se organizará como una jerarquía de módulos.

Cuando la compilación haya finalizado, si está compilando uno o más módulos, puede colocar el directorio de salida en la ruta de módulos para el lanzador de Java; de lo contrario, puede colocar el directorio de salida en la ruta de clases para el lanzador de Java.

Código precompilado

El código que se va a compilar puede hacer referencia a bibliotecas más allá de lo que proporciona la plataforma. Si es así, debe colocar estas bibliotecas en la ruta de clases o en la ruta de módulos. Si el código de la biblioteca no está en un módulo, colóquelo en la ruta de clases; si está en un módulo, colóquelo en la ruta de módulos.

  • Use la opción --class-path para especificar bibliotecas que se colocarán en la ruta de clases. Las ubicaciones en la ruta de clases deben organizarse en una jerarquía de paquetes. También puede usar formas alternativas de la opción: -classpath o -cp.
  • Use la opción --module-path para especificar bibliotecas que se colocarán en la ruta de módulos. Las ubicaciones en la ruta de módulos deben ser módulos o directorios de módulos. También puede usar una forma alternativa de la opción: -p.

Consulte Configurar el sistema de módulos para obtener detalles sobre cómo modificar la configuración predeterminada de los módulos de biblioteca.

Nota: las opciones para la ruta de clases y la ruta de módulos no son mutuamente excluyentes, aunque no es común especificar la ruta de clases al compilar código para uno o más módulos.

Archivos fuente adicionales

El código que se va a compilar puede hacer referencia a tipos en archivos fuente adicionales que no se especifican en la línea de comandos. Si es así, debe colocar esos archivos fuente en la ruta de código fuente o en la ruta de módulos. Solo puede especificar una de estas opciones: si no está compilando código para un módulo, o si solo está compilando código para un único módulo, use la ruta de código fuente; si está compilando código para varios módulos, use la ruta de código fuente de módulos.

  • Use la opción --source-path para especificar las ubicaciones de archivos fuente adicionales que javac puede leer. Las ubicaciones en la ruta de código fuente deben organizarse en una jerarquía de paquetes. También puede usar una forma alternativa de la opción: -sourcepath.
  • Use la opción --module-source-path una o más veces para especificar la ubicación de archivos fuente adicionales en diferentes módulos que javac puede leer, o al compilar archivos fuente en varios módulos. Puede especificar las ubicaciones para cada módulo individualmente, o puede organizar los archivos fuente de modo que pueda especificar las ubicaciones todas juntas. Para obtener más detalles, consulte La opción de ruta de código fuente de módulos.

Si desea poder hacer referencia a tipos en archivos fuente adicionales pero no desea que se compilen, use la opción -implicit.

Nota: si está compilando código para varios módulos, siempre debe especificar una ruta de código fuente de módulos, y todos los archivos fuente especificados en la línea de comandos deben estar en uno de los directorios de la ruta de código fuente de módulos, o en un subdirectorio de esta.

Ejemplo de compilación de varios archivos fuente

Este ejemplo compila los archivos fuente Aloha.java, GutenTag.java, Hello.java y Hi.java en el paquete greetings.

Linux y macOS:

% javac greetings/*.java
% ls greetings
Aloha.class         GutenTag.class      Hello.class         Hi.class
Aloha.java          GutenTag.java       Hello.java          Hi.java

Windows:

C:\>javac greetings\*.java
C:\>dir greetings
Aloha.class         GutenTag.class      Hello.class         Hi.class
Aloha.java          GutenTag.java       Hello.java          Hi.java

Ejemplo de especificación de una ruta de clases de usuario

Después de cambiar uno de los archivos fuente del ejemplo anterior, vuelva a compilarlo:

Linux y macOS:

pwd
/examples
javac greetings/Hi.java

Windows:

C:\>cd
\examples
C:\>javac greetings\Hi.java

Debido a que greetings.Hi hace referencia a otras clases del paquete greetings, el compilador necesita encontrar estas otras clases. El ejemplo anterior funciona porque la ruta de clases de usuario predeterminada es el directorio que contiene el directorio del paquete. Si desea volver a compilar este archivo sin preocuparse por el directorio en el que se encuentra, agregue el directorio examples a la ruta de clases de usuario estableciendo CLASSPATH. Este ejemplo usa la opción -classpath.

Linux y macOS:

javac -classpath /examples /examples/greetings/Hi.java

Windows:

C:\>javac -classpath \examples \examples\greetings\Hi.java

Si cambia greetings.Hi para usar una utilidad de banner, esa utilidad también debe ser accesible a través de la ruta de clases de usuario.

Linux y macOS:

javac -classpath /examples:/lib/Banners.jar \
            /examples/greetings/Hi.java

Windows:

C:\>javac -classpath \examples;\lib\Banners.jar ^
            \examples\greetings\Hi.java

Para ejecutar una clase en el paquete greetings, el programa necesita acceso al paquete greetings y a las clases que usan las clases de greetings.

Linux y macOS:

java -classpath /examples:/lib/Banners.jar greetings.Hi

Windows:

C:\>java -classpath \examples;\lib\Banners.jar greetings.Hi

CONFIGURACIÓN DEL SISTEMA DE MÓDULOS

Si desea incluir módulos adicionales en su compilación, utilice la opción --add-modules. Esto puede ser necesario cuando está compilando código que no está en un módulo, o que está en un módulo automático, y el código hace referencia a la API en los módulos adicionales.

Si desea restringir el conjunto de módulos en su compilación, utilice la opción --limit-modules. Esto puede ser útil si desea asegurarse de que el código que está compilando sea capaz de ejecutarse en un sistema con un conjunto limitado de módulos instalados.

Si desea romper la encapsulación y especificar que paquetes adicionales deben considerarse como exportados desde un módulo, utilice la opción --add-exports. Esto puede ser útil al realizar pruebas de caja blanca; se desaconseja encarecidamente depender del acceso a la API interna en el código de producción.

Si desea especificar que paquetes adicionales deben considerarse como requeridos por un módulo, utilice la opción --add-reads. Esto puede ser útil al realizar pruebas de caja blanca; se desaconseja encarecidamente depender del acceso a la API interna en el código de producción.

Puede aplicar parches con contenido adicional en cualquier módulo utilizando la opción --patch-module. Consulte [Aplicación de parches a un módulo] para obtener más detalles.

BÚSQUEDA DE DECLARACIONES DE MÓDULOS, PAQUETES Y TIPOS

Para compilar un archivo fuente, el compilador a menudo necesita información sobre un módulo o tipo, pero la declaración no está en los archivos fuente especificados en la línea de comandos.

javac necesita información de tipo para cada clase o interfaz utilizada, extendida o implementada en el archivo fuente. Esto incluye clases e interfaces no mencionadas explícitamente en el archivo fuente, pero que proporcionan información a través de la herencia.

Por ejemplo, cuando crea una subclase de java.awt.Window, también está utilizando las clases ancestro de Window: java.awt.Container, java.awt.Component y java.lang.Object.

Al compilar código para un módulo, el compilador también necesita tener disponible la declaración de ese módulo.

Una búsqueda exitosa puede producir un archivo de clase, un archivo fuente o ambos. Si se encuentran ambos, puede usar la opción -Xprefer para indicar al compilador cuál usar.

Si una búsqueda encuentra y utiliza un archivo fuente, entonces por defecto javac compila ese archivo fuente. Este comportamiento se puede alterar con -implicit.

Es posible que el compilador no descubra la necesidad de cierta información de tipo hasta después de que finalice el procesamiento de anotaciones. Cuando la información de tipo se encuentra en un archivo fuente y no se especifica ninguna opción -implicit, el compilador emite una advertencia de que el archivo se está compilando sin estar sujeto al procesamiento de anotaciones. Para deshabilitar la advertencia, especifique el archivo en la línea de comandos (para que esté sujeto al procesamiento de anotaciones) o use la opción -implicit para especificar si se deben generar o no archivos de clase para dichos archivos fuente.

La forma en que javac localiza las declaraciones de esos tipos depende de si la referencia existe dentro del código de un módulo o no.

Búsqueda en Rutas Orientadas a Paquetes

Al buscar un archivo fuente o de clase en una ruta compuesta de ubicaciones orientadas a paquetes, javac verificará cada ubicación en la ruta a su vez para detectar la posible presencia del archivo. La primera aparición de un archivo en particular oculta (sombrea) cualquier aparición posterior de archivos con el mismo nombre. Este sombreado no afecta ninguna búsqueda de archivos con un nombre diferente. Esto puede ser conveniente al buscar archivos fuente, que pueden estar agrupados en diferentes ubicaciones, como código compartido, código específico de la plataforma y código generado. También puede ser útil al inyectar versiones alternativas de un archivo de clase en un paquete, por razones de depuración u otra instrumentación. Pero también puede ser peligroso, como cuando se colocan versiones diferentes e incompatibles de una biblioteca en la ruta de clases.

Búsqueda en Rutas Orientadas a Módulos

Antes de escanear cualquier ruta de módulos en busca de declaraciones de paquetes o tipos, javac escaneará de forma diferida las siguientes rutas y ubicaciones para determinar los módulos que se utilizarán en la compilación.

  • La ruta de origen de módulos (consulte la opción --module-source-path)
  • La ruta para módulos actualizables (consulte la opción --upgrade-module-path)
  • Los módulos del sistema (consulte la opción --system)
  • La ruta de módulos del usuario (consulte la opción --module-path)

Para cualquier módulo, la primera aparición del módulo durante el escaneo oculta completamente (sombrea) cualquier aparición posterior de un módulo con el mismo nombre. Mientras localiza los módulos, javac puede determinar los paquetes exportados por el módulo y asociar con cada módulo una ruta orientada a paquetes para el contenido del módulo. Para cualquier módulo compilado previamente, esta ruta será típicamente una única entrada para un directorio o un archivo que proporciona una jerarquía interna similar a un directorio, como un archivo JAR. Por lo tanto, al buscar un tipo que está en un paquete que se sabe que es exportado por un módulo, javac puede localizar la declaración de forma directa y eficiente.

Búsqueda de la Declaración de un Módulo

Si el módulo se ha compilado previamente, la declaración del módulo se encuentra en un archivo llamado module-info.class en la raíz de la jerarquía de paquetes para el contenido del módulo.

Si el módulo es uno de los que se están compilando actualmente, la declaración del módulo será el archivo llamado module-info.class en la raíz de la jerarquía de paquetes para el módulo en el directorio de salida de clases, o el archivo llamado module-info.java en una de las ubicaciones en la ruta de origen o en la ruta de origen de módulos para el módulo.

Búsqueda de la Declaración de un Tipo Cuando la Referencia no está en un Módulo

Al buscar un tipo al que se hace referencia en código que no está en un módulo, javac buscará en los siguientes lugares:

  • Las clases de la plataforma (o los tipos en paquetes exportados de los módulos de la plataforma) (Esto es solo para archivos de clase compilados).
  • Tipos en paquetes exportados de cualquier módulo en la ruta de módulos, si corresponde. (Esto es solo para archivos de clase compilados).
  • Tipos en paquetes en la ruta de clases y/o ruta de origen:
  • Si se especifican ambas, javac busca archivos de clase compilados en la ruta de clases y archivos fuente en la ruta de origen.
  • Si se especifica la ruta de clases, pero no la ruta de origen, javac busca tanto archivos de clase compilados como archivos fuente en la ruta de clases.
  • Si no se especifica la ruta de clases, su valor predeterminado es el directorio actual.

Al buscar un tipo en la ruta de clases y/o la ruta de origen, si se encuentran tanto un archivo de clase compilado como un archivo fuente, se utilizará por defecto el archivo modificado más recientemente. Si el archivo fuente es más reciente, se compilará y puede anular cualquier versión compilada previamente del archivo. Puede usar la opción -Xprefer para anular el comportamiento predeterminado.

Búsqueda de la Declaración de un Tipo Cuando la Referencia está en un Módulo

Al buscar un tipo al que se hace referencia en código dentro de un módulo, javac examinará la declaración del módulo contenedor para determinar si el tipo está en un paquete que se exporta desde otro módulo que es legible por el módulo contenedor. Si es así, javac simplemente irá de forma directa a la definición de ese módulo para encontrar la definición del tipo requerido. A menos que el módulo sea otro de los módulos que se están compilando, javac solo buscará archivos de clase compilados. En otras palabras, javac no buscará archivos fuente en módulos de la plataforma o módulos en la ruta de módulos.

Si el tipo al que se hace referencia no está en algún otro módulo legible, javac examinará el módulo que se está compilando para intentar encontrar la declaración del tipo. javac buscará la declaración del tipo de la siguiente manera:

  • Archivos fuente especificados en la línea de comandos o en la ruta de origen o ruta de origen de módulos.
  • Archivos compilados previamente en el directorio de salida.

JERARQUÍAS DE DIRECTORIOS

javac generalmente asume que los archivos fuente y los archivos de clase compilados se organizarán en una jerarquía de directorios del sistema de archivos o en un tipo de archivo que admita internamente una jerarquía de directorios, como un archivo JAR. Se admiten tres tipos diferentes de jerarquía: una jerarquía de paquetes, una jerarquía de módulos y una jerarquía de código fuente de módulos.

Aunque javac es bastante flexible respecto a la organización del código fuente, más allá de la expectativa de que el código fuente se organice en una o varias jerarquías de paquetes, y generalmente puede adaptarse a las organizaciones prescritas por los entornos de desarrollo y las herramientas de compilación, las herramientas Java en general, y javac y el lanzador de Java en particular, son más estrictos respecto a la organización de los archivos de clase compilados, y se organizarán en jerarquías de paquetes o jerarquías de módulos, según corresponda.

La ubicación de estas jerarquías se especifica a javac con opciones de línea de comandos, cuyos nombres normalmente terminan en "path", como --source-path o --class-path. Además, como regla general, las opciones de ruta cuyo nombre incluye la palabra module, como --module-path, se utilizan para especificar jerarquías de módulos, aunque algunas opciones de ruta relacionadas con módulos permiten especificar una jerarquía de paquetes por módulo. Todas las demás opciones de ruta se utilizan para especificar jerarquías de paquetes.

Jerarquía de paquetes

En una jerarquía de paquetes, los directorios y subdirectorios se utilizan para representar las partes componentes del nombre del paquete, con el archivo fuente o el archivo de clase compilado de un tipo almacenado como un archivo con una extensión de .java o .class en el directorio más anidado.

Por ejemplo, en una jerarquía de paquetes, el archivo fuente de una clase com.example.MyClass se almacenará en el archivo com/example/MyClass.java

Jerarquía de módulos

En una jerarquía de módulos, el primer nivel de directorios se nombra según los módulos de la jerarquía; dentro de cada uno de esos directorios, el contenido del módulo se organiza en jerarquías de paquetes.

Por ejemplo, en una jerarquía de módulos, el archivo de clase compilado de un tipo llamado com.example.MyClass en un módulo llamado my.library se almacenará en my.library/com/example/MyClass.class.

Los diversos directorios de salida utilizados por javac (el directorio de salida de clases, el directorio de salida de código fuente y el directorio de salida de encabezados nativos) se organizarán todos en una jerarquía de módulos cuando se compilen varios módulos.

Jerarquía de código fuente de módulos

Aunque el código fuente de cada módulo individual siempre debe estar organizado en una jerarquía de paquetes, puede resultar conveniente agrupar esas jerarquías en una jerarquía de código fuente de módulos. Esto es similar a una jerarquía de módulos, excepto que puede haber directorios intermedios entre el directorio del módulo y el directorio que es la raíz de la jerarquía de paquetes para el código fuente del módulo.

Por ejemplo, en una jerarquía de código fuente de módulos, el archivo fuente de un tipo llamado com.example.MyClass en un módulo llamado my.library puede almacenarse en un archivo como my.library/src/main/java/com/example/MyClass.java.

LA OPCIÓN DE RUTA DE ORIGEN DE MÓDULOS

La opción --module-source-path tiene dos formas: una forma específica de módulo, en la que se proporciona una ruta de paquetes para cada módulo que contiene código a compilar, y una forma de patrón de módulo, en la que la ruta de origen para cada módulo se especifica mediante un patrón. La forma específica de módulo suele ser más sencilla de usar cuando solo intervienen un pequeño número de módulos; la forma de patrón de módulo puede ser más conveniente cuando el número de módulos es grande y los módulos están organizados de manera regular que puede describirse mediante un patrón.

Se pueden proporcionar múltiples instancias de la opción --module-source-path, cada una usando la forma de patrón de módulo o la forma específica de módulo, sujeto a las siguientes limitaciones:

  • la forma de patrón de módulo puede usarse como máximo una vez
  • la forma específica de módulo puede usarse como máximo una vez para cualquier módulo dado

Si se usa la forma específica de módulo para algún módulo, la ruta de búsqueda asociada anula cualquier ruta que de otro modo podría haberse inferido de la forma de patrón de módulo.

Forma específica de módulo

La forma específica de módulo permite dar una ruta de búsqueda explícita para cualquier módulo específico. Esta forma es:

•
--module-source-path nombre-de-módulo=ruta-de-archivo (separador-de-ruta ruta-de-archivo)*

El carácter separador de ruta es ; en Windows, y : en caso contrario.

Nota: esto es similar a la forma usada para la opción --patch-module.

Forma de patrón de módulo

La forma de patrón de módulo permite una especificación concisa de la ruta de origen de módulos para cualquier número de módulos organizados de manera regular.

•
--module-source-path patrón

El patrón se define mediante las siguientes reglas, que se aplican en orden:

  • El argumento se considera una serie de segmentos separados por el carácter separador de ruta (; en Windows, y : en caso contrario).
  • Cada segmento que contenga llaves de la forma
cadena1{alt1 ( ,alt2 )* } cadena2

se considera reemplazado por una serie de segmentos formados al "expandir" las llaves:

cadena1 alt1 cadena2
cadena1 alt2 cadena2
y así sucesivamente...

Las llaves pueden estar anidadas.

Esta regla se aplica para todos esos usos de llaves.

•
Cada segmento debe tener como máximo un asterisco (*). Si un segmento no contiene un asterisco, se considera como si se le añadieran el carácter separador de archivos y un asterisco.

Para cualquier módulo M, la ruta de origen para ese módulo se forma a partir de la serie de segmentos obtenidos al sustituir el nombre del módulo M por el asterisco en cada segmento.

Nota: en este contexto, el asterisco se usa solo como un marcador especial, para denotar la posición en la ruta del nombre del módulo. No debe confundirse con el uso de * como carácter comodín de nombre de archivo, como se encuentra en la mayoría de los sistemas operativos.

PARCHEO DE MÓDULOS

javac permite que cualquier contenido, ya sea en forma de código fuente o compilado, se parchee en cualquier módulo usando la opción --patch-module. Es posible que desee hacer esto para compilar implementaciones alternativas de una clase que se parcheará en tiempo de ejecución en una JVM, o para inyectar clases adicionales en el módulo, como al realizar pruebas.

La forma de la opción es:

•
--patch-module nombre-del-módulo=ruta-de-archivo (separador-de-ruta ruta-de-archivo )*

El carácter separador de ruta es ; en Windows, y : en caso contrario. Las rutas proporcionadas para el módulo deben especificar la raíz de una jerarquía de paquetes para el contenido del módulo

La opción puede proporcionarse como máximo una vez para cualquier módulo dado. Cualquier contenido en la ruta ocultará cualquier contenido con el mismo nombre que aparezca más adelante en la ruta y en el módulo parcheado.

Al parchear código fuente en más de un módulo, también debe usarse --module-source-path, para que el directorio de salida esté organizado en una jerarquía de módulos y sea capaz de contener los archivos de clase compilados para los módulos que se están compilando.

PROCESAMIENTO DE ANOTACIONES

El comando javac proporciona soporte directo para el procesamiento de anotaciones.

La API para los procesadores de anotaciones se define en los paquetes y subpaquetes javax.annotation.processing y javax.lang.model.

Cómo funciona el procesamiento de anotaciones

El procesamiento de anotaciones se solicita mediante el uso de una opción para configurar el procesamiento de anotaciones, como -processor, --processor-path, --processor-module-path o habilitando explícitamente el procesamiento con las opciones -proc:full o -proc:only. El procesamiento de anotaciones se deshabilita con la opción -proc:none.

Si se solicita el procesamiento de anotaciones, el compilador busca cualquier procesador de anotaciones que esté disponible.

La ruta de búsqueda se puede especificar con la opción -processorpath. Si no se especifica ninguna ruta, se utiliza la ruta de clases del usuario. Los procesadores se localizan mediante archivos de configuración de proveedores de servicios llamados META-INF/services/javax.annotation.processing.Processor en la ruta de búsqueda. Dichos archivos deben contener los nombres de cualquier procesador de anotaciones que se vaya a utilizar, listados uno por línea. Alternativamente, los procesadores se pueden especificar explícitamente, usando la opción -processor.

Después de escanear los archivos fuente y las clases en la línea de comandos para determinar qué anotaciones están presentes, el compilador consulta a los procesadores para determinar qué anotaciones procesan. Cuando se encuentra una coincidencia, se llama al procesador. Un procesador puede reclamar las anotaciones que procesa, en cuyo caso no se realiza ningún intento adicional de encontrar procesadores para esas anotaciones. Después de que todas las anotaciones son reclamadas, el compilador no busca procesadores adicionales.

Si algún procesador genera nuevos archivos fuente, entonces ocurre otra ronda de procesamiento de anotaciones: cualquier archivo fuente recién generado se escanea y las anotaciones se procesan como antes. Cualquier procesador llamado en rondas anteriores también se llama en todas las rondas posteriores. Esto continúa hasta que no se generen nuevos archivos fuente.

Después de que ocurra una ronda en la que no se generen nuevos archivos fuente, se llama a los procesadores de anotaciones una última vez, para darles la oportunidad de completar cualquier trabajo restante. Finalmente, a menos que se use la opción -proc:only, el compilador compila los archivos fuente originales y todos los generados.

Si utiliza un procesador de anotaciones que genera archivos fuente adicionales para ser incluidos en la compilación, puede especificar un módulo predeterminado que se utilizará para los archivos recién generados, para usarse cuando tampoco se genere una declaración de módulo. En este caso, use la opción --default-module-for-created-files.

Entorno de compilación y entorno de ejecución.

Las declaraciones en los archivos fuente y los archivos de clase compilados previamente son analizados por javac en un entorno de compilación que es distinto del entorno de ejecución utilizado para ejecutar javac en sí mismo. Aunque existe una similitud deliberada entre muchas opciones de javac y opciones con el mismo nombre para el lanzador de Java, como --class-path, --module-path y así sucesivamente, es importante entender que, en general, las opciones de javac solo afectan el entorno en el que se compilan los archivos fuente, y no afectan el funcionamiento de javac en sí mismo.

La distinción entre el entorno de compilación y el entorno de ejecución es significativa cuando se trata del uso de procesadores de anotaciones. Aunque los procesadores de anotaciones procesan elementos (declaraciones) que existen en el entorno de compilación, el procesador de anotaciones en sí mismo se ejecuta en el entorno de ejecución. Si un procesador de anotaciones tiene dependencias de bibliotecas que no están en módulos, las bibliotecas se pueden colocar, junto con el procesador de anotaciones en sí mismo, en la ruta del procesador. (Consulte la opción --processor-path.) Si el procesador de anotaciones y sus dependencias están en módulos, debe usar la ruta de módulos del procesador en su lugar. (Consulte la opción --processor-module-path.) Cuando esas opciones son insuficientes, puede ser necesario proporcionar una configuración adicional del entorno de ejecución. Esto se puede hacer de dos maneras:

1.
Si javac se invoca desde la línea de comandos, las opciones se pueden pasar al entorno de ejecución subyacente prefijando la opción con -J.
2.
Puede iniciar una instancia de una Máquina Virtual Java directamente y usar opciones de línea de comandos y la API para configurar un entorno en el que se pueda invocar javac a través de una de sus API.

COMPILACIÓN PARA VERSIONES ANTERIORES DE LA PLATAFORMA

javac puede compilar código que se va a utilizar en otras versiones de la plataforma, usando la opción --release, o las opciones --source/-source y --target/-target, junto con opciones adicionales para especificar las clases de la plataforma.

Dependiendo de la versión de plataforma deseada, existen algunas restricciones sobre algunas de las opciones que se pueden usar.

•
Al compilar para JDK 8 y versiones anteriores, no puede usar ninguna opción que esté destinada a usarse con el sistema de módulos. Esto incluye todas las siguientes opciones:
•
--module-source-path, --upgrade-module-path, --system, --module-path, --add-modules, --add-exports, --add-opens, --add-reads, --limit-modules, --patch-module

Si usa las opciones --source/-source o --target/-target, también debe establecer las clases de plataforma adecuadas usando la familia de opciones de la ruta de clases de arranque.

•
Al compilar para JDK 9 y versiones posteriores, no puede usar ninguna opción que esté destinada a configurar la ruta de clases de arranque. Esto incluye todas las siguientes opciones:
•
-Xbootclasspath/p:, -Xbootclasspath, -Xbootclasspath/a:, -endorseddirs, -Djava.endorsed.dirs, -extdirs, -Djava.ext.dirs, -profile

Si usa las opciones --source/-source o --target/-target, también debe establecer las clases de plataforma adecuadas usando la opción --system para indicar la ubicación de una versión instalada adecuada de JDK.

Al usar la opción --release, solo se puede usar la API documentada y compatible para esa versión; no puede usar ninguna opción para romper la encapsulación y acceder a clases internas.

APIS

El compilador javac se puede invocar mediante una API de tres formas diferentes:

La API del compilador de Java
Esta proporciona la forma más flexible de invocar el compilador, incluida la capacidad de compilar archivos fuente proporcionados en búferes de memoria u otros sistemas de archivos no estándar.
La API ToolProvider
Se puede obtener un ToolProvider para javac llamando a ToolProvider.findFirst("javac"). Esto devuelve un objeto con la funcionalidad equivalente a la herramienta de línea de comandos.
Nota: Esta API no debe confundirse con la API de nombre similar en el paquete javax.tools.
La API heredada de javac
Esta API se conserva solo por compatibilidad con versiones anteriores. Todo el código nuevo debe usar la API del compilador de Java o la API ToolProvider.

Nota: Todas las demás clases y métodos que se encuentran en un paquete con nombres que comienzan con com.sun.tools.javac (subpaquetes de com.sun.tools.javac) son estrictamente internos y están sujetos a cambios en cualquier momento.

EXAMPLES OF USING -XLINT KEYS

cast
Warns about unnecessary and redundant casts, for example:

String s = (String) "Hello!"

classfile
Warns about issues related to class file contents.
deprecation
Warns about the use of deprecated items. For example:
java.util.Date myDate = new java.util.Date();
int currentDay = myDate.getDay();
The method java.util.Date.getDay has been deprecated since JDK 1.1.
dep-ann
Warns about items that are documented with the @deprecated Javadoc comment, but do not have the @Deprecated annotation, for example:
/**
  * @deprecated As of Java SE 7, replaced by {@link #newMethod()}
  */
public static void deprecatedMethod() { }
public static void newMethod() { }
divzero
Warns about division by the constant integer 0, for example:

int divideByZero = 42 / 0;

empty
Warns about empty statements after ifstatements, for example:
class E {
    void m() {
         if (true) ;
    }
}
fallthrough
Checks the switch blocks for fall-through cases and provides a warning message for any that are found. Fall-through cases are cases in a switch block, other than the last case in the block, whose code does not include a break statement, allowing code execution to fall through from that case to the next case. For example, the code following the case 1 label in this switch block does not end with a break statement:
switch (x) {
case 1:
  System.out.println("1");
  // No break statement here.
case 2:
  System.out.println("2");
}
If the -Xlint:fallthrough option was used when compiling this code, then the compiler emits a warning about possible fall-through into case, with the line number of the case in question.
finally
Warns about finally clauses that cannot be completed normally, for example:
public static int m() {
  try {
     throw new NullPointerException();
  }  catch (NullPointerException e) {
     System.err.println("Caught NullPointerException.");
     return 1;
   } finally {
     return 0;
   }
  }
The compiler generates a warning for the finally block in this example. When the int method is called, it returns a value of 0. A finally block executes when the try block exits. In this example, when control is transferred to the catch block, the int method exits. However, the finally block must execute, so it's executed, even though control was transferred outside the method.
options
Warns about issues that related to the use of command-line options. See Compiling for Earlier Releases of the Platform.
overrides
Warns about issues related to method overrides. For example, consider the following two classes:
public class ClassWithVarargsMethod {
  void varargsMethod(String... s) { }
}
public class ClassWithOverridingMethod extends ClassWithVarargsMethod {
   @Override
   void varargsMethod(String[] s) { }
}
The compiler generates a warning similar to the following:.
warning: [override] varargsMethod(String[]) in ClassWithOverridingMethod
overrides varargsMethod(String...) in ClassWithVarargsMethod; overriding
method is missing '...'
When the compiler encounters a varargs method, it translates the varargs formal parameter into an array. In the method ClassWithVarargsMethod.varargsMethod, the compiler translates the varargs formal parameter String... s to the formal parameter String[] s, an array that matches the formal parameter of the method ClassWithOverridingMethod.varargsMethod. Consequently, this example compiles.
path
Warns about invalid path elements and nonexistent path directories on the command line (with regard to the class path, the source path, and other paths). Such warnings cannot be suppressed with the @SuppressWarnings annotation. For example:
  • Linux and macOS: javac -Xlint:path -classpath /nonexistentpath Example.java
  • Windows: javac -Xlint:path -classpath C:\nonexistentpath Example.java
processing
Warns about issues related to annotation processing. The compiler generates this warning when you have a class that has an annotation, and you use an annotation processor that cannot handle that type of annotation. For example, the following is a simple annotation processor:
Source file AnnoProc.java: 
import java.util.*;
import javax.annotation.processing.*;
import javax.lang.model.*;
import javax.lang.model.element.*;
@SupportedAnnotationTypes("NotAnno")
public class AnnoProc extends AbstractProcessor {
  public boolean process(Set<? extends TypeElement> elems, RoundEnvironment renv){
     return true;
  }
  public SourceVersion getSupportedSourceVersion() {
     return SourceVersion.latest();
   }
}
Source file AnnosWithoutProcessors.java:
@interface Anno { }
@Anno
class AnnosWithoutProcessors { }
The following commands compile the annotation processor AnnoProc, then run this annotation processor against the source file AnnosWithoutProcessors.java:
javac AnnoProc.java
javac -cp . -Xlint:processing -processor AnnoProc -proc:only AnnosWithoutProcessors.java
When the compiler runs the annotation processor against the source file AnnosWithoutProcessors.java, it generates the following warning:
warning: [processing] No processor claimed any of these annotations: Anno
To resolve this issue, you can rename the annotation defined and used in the class AnnosWithoutProcessors from Anno to NotAnno.
rawtypes
Warns about unchecked operations on raw types. The following statement generates a rawtypes warning:

void countElements(List l) { ... }

The following example does not generate a rawtypes warning:

void countElements(List<?> l) { ... }

List is a raw type. However, List<?> is an unbounded wildcard parameterized type. Because List is a parameterized interface, always specify its type argument. In this example, the List formal argument is specified with an unbounded wildcard (?) as its formal type parameter, which means that the countElements method can accept any instantiation of the List interface.
serial
Warns about missing serialVersionUID definitions on serializable classes. For example:
public class PersistentTime implements Serializable
{
  private Date time;
   public PersistentTime() {
     time = Calendar.getInstance().getTime();
   }
   public Date getTime() {
     return time;
   }
}
The compiler generates the following warning:
warning: [serial] serializable class PersistentTime has no definition of
serialVersionUID
If a serializable class does not explicitly declare a field named serialVersionUID, then the serialization runtime environment calculates a default serialVersionUID value for that class based on various aspects of the class, as described in the Java Object Serialization Specification. However, it's strongly recommended that all serializable classes explicitly declare serialVersionUID values because the default process of computing serialVersionUID values is highly sensitive to class details that can vary depending on compiler implementations. As a result, this might cause an unexpected InvalidClassExceptions during deserialization. To guarantee a consistent serialVersionUID value across different Java compiler implementations, a serializable class must declare an explicit serialVersionUID value.
static
Warns about issues relating to the use of static variables, for example:
class XLintStatic {
    static void m1() { }
    void m2() { this.m1(); }
}
The compiler generates the following warning:
warning: [static] static method should be qualified by type name,
XLintStatic, instead of by an expression
To resolve this issue, you can call the static method m1 as follows:

XLintStatic.m1();

Alternately, you can remove the static keyword from the declaration of the method m1.
this-escape
Warns about constructors leaking this prior to subclass initialization. For example, this class:
public class MyClass {
  public MyClass() {
    System.out.println(this.hashCode());
  }
}
generates the following warning:
MyClass.java:3: warning: [this-escape] possible 'this' escape
                         before subclass is fully initialized
    System.out.println(this.hashCode());
                                    ^
A 'this' escape warning is generated when a constructor does something that might result in a subclass method being invoked before the constructor returns. In such cases the subclass method would be operating on an incompletely initialized instance. In the above example, a subclass of MyClass that overrides hashCode() to incorporate its own fields would likely produce an incorrect result when invoked as shown. Warnings are only generated if a subclass could exist that is outside of the current module (or package, if no module) being compiled. So, for example, constructors in final and non-public classes do not generate warnings.
try
Warns about issues relating to the use of try blocks, including try-with-resources statements. For example, a warning is generated for the following statement because the resource ac declared in the try block is not used:
try ( AutoCloseable ac = getResource() ) {    // do nothing}
unchecked
Gives more detail for unchecked conversion warnings that are mandated by the Java Language Specification, for example:
List l = new ArrayList<Number>();
List<String> ls = l;       // unchecked warning
During type erasure, the types ArrayList<Number> and List<String> become ArrayList and List, respectively. The ls command has the parameterized type List<String>. When the List referenced by l is assigned to ls, the compiler generates an unchecked warning. At compile time, the compiler and JVM cannot determine whether l refers to a List<String> type. In this case, l does not refer to a List<String> type. As a result, heap pollution occurs. A heap pollution situation occurs when the List object l, whose static type is List<Number>, is assigned to another List object, ls, that has a different static type, List<String>. However, the compiler still allows this assignment. It must allow this assignment to preserve backward compatibility with releases of Java SE that do not support generics. Because of type erasure, List<Number> and List<String> both become List. Consequently, the compiler allows the assignment of the object l, which has a raw type of List, to the object ls.
varargs
Warns about unsafe use of variable arguments (varargs) methods, in particular, those that contain non-reifiable arguments, for example:
public class ArrayBuilder {
  public static <T> void addToList (List<T> listArg, T... elements) {
    for (T x : elements) {
      listArg.add(x);
    }
  }
}
A non-reifiable type is a type whose type information is not fully available at runtime. The compiler generates the following warning for the definition of the method ArrayBuilder.addToList:
warning: [varargs] Possible heap pollution from parameterized vararg type T
When the compiler encounters a varargs method, it translates the varargs formal parameter into an array. However, the Java programming language does not permit the creation of arrays of parameterized types. In the method ArrayBuilder.addToList, the compiler translates the varargs formal parameter T... elements to the formal parameter T[] elements, an array. However, because of type erasure, the compiler converts the varargs formal parameter to Object[] elements. Consequently, there's a possibility of heap pollution.
