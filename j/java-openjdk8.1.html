DESCRIPCIÓ

N

El comando java inicia una aplicación Java. Lo hace iniciando el Entorno de Ejecución Java (JRE), cargando la clase especificada y llamando al método main() de esa clase. El método debe estar declarado como público (public) y estático (static), no debe devolver ningún valor y debe aceptar un array de String como parámetro. La declaración del método tiene la siguiente

forma: 
public static void
main(Stri
ng[] args)

El comando java se puede usar para iniciar una aplicación JavaFX cargando una clase que tenga un método main() o que extienda de javafx.application.Application. En este último caso, el lanzador construye una instancia de la clase Application, llama a su método init() y luego llama al método start(javafx.stage.Stage)

.

Por defecto, el primer argumento que no es una opción del comando java es el nombre completo (fully qualified) de la clase que se va a llamar. Si se especifica la opción -jar, su argumento es el nombre del archivo JAR que contiene los archivos de clase y de recursos de la aplicación. La clase de inicio debe estar indicada por la cabecera Main-Class del manifiesto en su código

fuente.

El JRE busca la clase de inicio (y otras clases usadas por la aplicación) en tres conjuntos de ubicaciones: la ruta de clases de arranque (bootstrap class path), las extensiones instaladas y la ruta de clases del

usuario.

Los argumentos después del nombre del archivo de clase o del nombre del archivo JAR se pasan al método

mai
n().

Se garantiza que las opciones estándar están soportadas por todas las implementaciones de la Máquina Virtual Java (JVM). Se usan para acciones comunes, como comprobar la versión del JRE, establecer la ruta de clases, habilitar la salida detallada (verbose),

Las opciones no estándar son opciones de propósito general que son específicas de la Máquina Virtual Java HotSpot, por lo que no se garantiza que estén soportadas por todas las implementaciones de la JVM y están sujetas a cambios. Estas opciones comienzan con -X

.

No se recomienda el uso casual de las opciones avanzadas. Son opciones de desarrollador usadas para ajustar áreas específicas de la operación de la Máquina Virtual Java HotSpot que a menudo tienen requisitos de sistema específicos y pueden requerir acceso privilegiado a parámetros de configuración del sistema. Tampoco se garantiza que estén soportadas por todas las implementaciones de la JVM y están sujetas a cambios. Las opciones avanzadas comienzan con -XX

.

Para llevar un registro de las opciones que se han obsoleto o eliminado en la última versión, hay una sección llamada Opciones obsoletas y eliminadas al final del

documento.

Las opciones booleanas se usan para habilitar una función que está deshabilitada por defecto o para deshabilitar una función que está habilitada por defecto. Tales opciones no requieren un parámetro. Las opciones booleanas -XX se habilitan usando el signo más (-XX:+NombreOpción) y se deshabilitan usando el signo menos (-XX:-NombreOpc

ión).

Para las opciones que requieren un argumento, el argumento puede estar separado del nombre de la opción por un espacio, un dos puntos (:) o un signo igual (=), o el argumento puede seguir directamente a la opción (la sintaxis exacta difiere para cada opción). Si se espera que especifique el tamaño en bytes, puede usar ningún sufijo, o usar el sufijo k o K para kilobytes (KB), m o M para megabytes (MB), g o G para gigabytes (GB). Por ejemplo, para establecer el tamaño en 8 GB, puede especificar 8g, 8192m, 8388608k o 8589934592 como el argumento. Si se espera que especifique el porcentaje, use un número de 0 a 1 (por ejemplo, especifique 0.25 para el 25%)

-version:release

Especifica la versión de lanzamiento que se utilizará para ejecutar la aplicación. Si la versión del comando java llamado no cumple con esta especificación y se encuentra una implementación adecuada en el sistema, entonces se utilizará la implementación adecuada.

-X

Muestra la ayuda para todas las opciones -X disponibles.

-Xbatch

Deshabilita la compilación en segundo plano. Por defecto, la JVM compila el método como una tarea en segundo plano, ejecutando el método en modo intérprete hasta que la compilación en segundo plano finaliza. Esta opción es equivalente a -XX:-BackgroundCompilation.

-Xnoclassgc

Deshabilita la recolección de basura (GC) de clases. Esto puede ahorrar tiempo de GC, lo que acorta las interrupciones durante la ejecución de la aplicación.

Cuando especifica -Xnoclassgc al inicio, los objetos de clase en la aplicación permanecerán intactos durante el GC y siempre se considerarán vivos. Esto puede resultar en que se ocupe más memoria de forma permanente, lo que, si no se usa con cuidado, lanzará una excepción de falta de memoria.

-Xprof

-Xrs

Reduce el uso de señales del sistema operativo por parte de la JVM.

Los ganchos de apagado permiten un apagado ordenado de una aplicación Java ejecutando código de limpieza del usuario (como cerrar conexiones de bases de datos) al apagar, incluso si la JVM termina abruptamente.

La JVM captura señales para implementar ganchos de apagado para terminaciones inesperadas. La JVM utiliza SIGHUP, SIGINT y SIGTERM para iniciar la ejecución de los ganchos de apagado.

La JVM utiliza un mecanismo similar para implementar la función de volcado de pilas de hilos con fines de depuración. La JVM utiliza SIGQUIT para realizar volcados de hilos.

Las aplicaciones que integran la JVM con frecuencia necesitan atrapar señales como SIGINT o SIGTERM, lo que puede interferir con los manejadores de señales de la JVM. La opción -Xrs está disponible para abordar este problema. Cuando se utiliza -Xrs, las máscaras de señales para SIGINT, SIGTERM, SIGHUP y SIGQUIT no son modificadas por la JVM, y no se instalan manejadores de señales para estas señales.

Hay dos consecuencias de especificar -Xrs:

•Los volcados de hilos SIGQUIT no están disponibles.
•El código del usuario es responsable de activar los ganchos de apagado, por ejemplo, llamando a System.exit() cuando la JVM deba terminar.

Opciones Avanzadas de Tiempo de Ejecución

Estas opciones controlan el comportamiento en tiempo de ejecución de la VM Java HotSpot.

-XX:+CheckEndorsedAndExtDirs

Habilita la opción para evitar que el comando java ejecute una aplicación Java si utiliza el mecanismo de anulación de estándares respaldados o el mecanismo de extensiones. Esta opción verifica si una aplicación está utilizando uno de estos mecanismos comprobando lo siguiente:
•La
propiedad del sistema java.ext.dirs o java.endorsed.dirs está establecida.
•El directorio lib/endorsed existe y no está vacío.
•El directorio lib/ext contiene archivos JAR distintos de los del JDK.
•El directorio de extensiones específico de la plataforma a nivel de sistema contiene archivos JAR.

-XX:+DisableAttachMechanism

Habilita la opción que deshabilita el mecanismo que permite a las herramientas adjuntarse a la JVM. Por defecto, esta opción está deshabilitada, lo que significa que el mecanismo de adjunción está habilitado y se pueden usar herramientas como jcmd, jstack, jmap y jinfo.

-XX:ErrorFile=nombre_archivo

Especifica la ruta y el nombre del archivo al que se escribirán los datos de error cuando ocurra un error irrecoverable. Por defecto, este archivo se crea en el directorio de trabajo actual y se llama hs_err_pidpid.log, donde pid es el identificador del proceso que causó el error. El siguiente ejemplo muestra cómo establecer el archivo de registro predeterminado (tenga en cuenta que el identificador del proceso se especifica como %p): 
-XX:ErrorFile=./hs_err_pid%p.log
El siguiente ejemplo muestra cómo establecer el registro de errores en /var/log/java/java_error.log: 
-XX:ErrorFile=/var/log/java/java_error.log
Si el archivo no se puede crear en el directorio especificado (debido a espacio insuficiente, problema de permisos u otro problema), el archivo se crea en el directorio temporal del sistema operativo. El directorio temporal es /tmp.

-XX:+FailOverToOldVerifier

Habilita la conmutación automática al antiguo verificador cuando el nuevo verificador de tipos falla. Por defecto, esta opción está deshabilitada y se ignora (es decir, se trata como deshabilitada) para clases con una versión reciente de bytecode. Puede habilitarla para clases con versiones anteriores del bytecode.

-XX:LargePageSizeInBytes=tamaño

En Solaris, establece el tamaño máximo (en bytes) para páginas grandes utilizadas para el heap de Java. El argumento tamaño debe ser una potencia de 2 (2, 4, 8, 16, ...). Agregue la letra k o K para indicar kilobytes, m o M para indicar megabytes, g o G para indicar gigabytes. Por defecto, el tamaño se establece en 0, lo que significa que la JVM elige el tamaño de las páginas grandes automáticamente.

El siguiente ejemplo ilustra cómo establecer el tamaño de página grande en 4 megabytes (MB):

-XX:LargePageSizeInBytes=4m

-XX:MaxDirectMemorySize=tamaño

Establece el tamaño total máximo (en bytes) de las asignaciones de búfer directo de New I/O (el paquete java.nio). Agregue la letra k o K para indicar kilobytes, m o M para indicar megabytes, g o G para indicar gigabytes. Por defecto, el tamaño se establece en 0, lo que significa que la JVM elige el tamaño de las asignaciones de búfer directo de NIO automáticamente.

Los siguientes ejemplos ilustran cómo establecer el tamaño de NIO en 1024 KB en diferentes unidades:

-XX:MaxDirectMemorySize=1m
-XX:MaxDirectMemorySize=1024k
-XX:MaxDirectMemorySize=1048576

-XX:NativeMemoryTracking=modo

Especifica el modo para rastrear el uso de memoria nativa de la JVM. Los posibles argumentos modo para esta opción incluyen los siguientes:

off

No rastrear el uso de memoria nativa de la JVM. Este es el comportamiento predeterminado si no especifica la opción -XX:NativeMemoryTracking.

summary

Rastrear solo el uso de memoria por subsistemas de la JVM, como el heap de Java, la clase, el código y el hilo.

detail

Además de rastrear el uso de memoria por subsistemas de la JVM, rastrear el uso de memoria por cada CallSite individual, cada región de memoria virtual individual y sus regiones confirmadas.

-XX:ObjectAlignmentInBytes=alineación

Establece la alineación de memoria de los objetos Java (en bytes). Por defecto, el valor se establece en 8 bytes. El valor especificado debe ser una potencia de dos y debe estar en el rango de 8 a 256 (inclusive). Esta opción permite el uso de punteros comprimidos con tamaños de heap de Java grandes.

El límite de tamaño del heap en bytes se calcula como:

4GB * ObjectAlignmentInBytes

Nota: A medida que aumenta el valor de alineación, el espacio no utilizado entre objetos también aumentará. Como resultado, es posible que no obtenga ningún beneficio al usar punteros comprimidos con tamaños de heap de Java grandes.

-XX:OnError=cadena

Establece un comando personalizado o una serie de comandos separados por punto y coma para ejecutar cuando ocurra un error irrecoverable. Si la cadena contiene espacios, debe ir entre comillas.

El siguiente ejemplo muestra cómo se puede usar la opción -XX:OnError para ejecutar el comando gcore para crear la imagen del core, y el depurador se inicia para adjuntarse al proceso en caso de un error irrecoverable (el %p designa el proceso actual):

-XX:OnError="gcore %p;dbx - %p"

-XX:OnOutOfMemoryError=cadena

Establece un comando personalizado o una serie de comandos separados por punto y coma para ejecutar cuando se lance por primera vez una excepción OutOfMemoryError. Si la cadena contiene espacios, debe ir entre comillas. Para ver un ejemplo de cadena de comando, consulte la descripción de la opción -XX:OnError.

-XX:+PerfDataSaveToFile

Si está habilitado, guarda los datos binarios de jstat(1) cuando la aplicación Java sale. Estos datos binarios se guardan en un archivo llamado hsperfdata_<pid>, donde <pid> es el identificador del proceso de la aplicación Java que ejecutó. Use jstat para mostrar los datos de rendimiento contenidos en este archivo de la siguiente manera: 
jstat -class file:///<ruta>/hsperfdata_<pid>
jstat -gc file:///<ruta>/hsperfdata_<pid>

Habilita la impresión de las marcas de JVM seleccionadas ergonómicamente que aparecieron en la línea de comandos. Por defecto, esta opción está deshabilitada y las marcas no se imprimen.

-XX:+PrintNMTStatistics

Habilita la impresión de los datos recopilados de rastreo de memoria nativa al salir de la JVM cuando el rastreo de memoria nativa está habilitado (consulte -XX:NativeMemoryTracking). Por defecto, esta opción está deshabilitada y los datos de rastreo de memoria nativa no se imprimen.

-XX:+TraceClassLoadingPreorder

-XX:+TraceClassResolution

Opciones Avanzadas del Compilador JIT

Estas opciones controlan la compilación dinámica justo a tiempo (JIT) realizada por la Java HotSpot VM.

-XX:+AggressiveOpts

Habilita el uso de características de optimización de rendimiento agresivas, que se espera que se conviertan en predeterminadas en futuras versiones. Por defecto, esta opción está deshabilitada y no se utilizan características de rendimiento experimentales.

-XX:AllocateInstancePrefetchLines=líneas

Establece el número de líneas a precargar antes del puntero de asignación de instancias. Por defecto, el número de líneas a precargar se establece en 1: 
-XX:AllocateInstancePrefetchLines=1
Solo la Java HotSpot Server VM soporta esta opción.

-XX:AllocatePrefetchDistance=tamaño

Establece el tamaño (en bytes) de la distancia de prefetch para la asignación de objetos. Se precarga memoria que será escrita con el valor de nuevos objetos hasta esta distancia comenzando desde la dirección del último objeto asignado. Cada hilo Java tiene su propio punto de asignación.

Los valores negativos denotan que la distancia de prefetch se elige en función de la plataforma. Los valores positivos son bytes a precargar. Añada la letra k o K para indicar kilobytes, m o M para indicar megabytes, g o G para indicar gigabytes. El valor predeterminado se establece en -1.

El siguiente ejemplo muestra cómo establecer la distancia de prefetch a 1024 bytes:

-XX:AllocatePrefetchDistance=1024
Solo la Java HotSpot Server VM soporta esta opción.

-XX:AllocatePrefetchInstr=instrucción

Establece la instrucción de prefetch para precargar antes del puntero de asignación. Solo la Java HotSpot Server VM soporta esta opción. Los valores posibles van de 0 a 3. Las instrucciones reales detrás de los valores dependen de la plataforma. Por defecto, la instrucción de prefetch se establece en 0: 
-XX:AllocatePrefetchInstr=0
Solo la Java HotSpot Server VM soporta esta opción.

-XX:AllocatePrefetchLines=líneas

Establece el número de líneas de caché a cargar después de la última asignación de objeto utilizando las instrucciones de prefetch generadas en el código compilado. El valor predeterminado es 1 si el último objeto asignado fue una instancia, y 3 si fue un array.

El siguiente ejemplo muestra cómo establecer el número de líneas de caché cargadas a 5:

-XX:AllocatePrefetchLines=5
Solo la Java HotSpot Server VM soporta esta opción.

-XX:AllocatePrefetchStepSize=tamaño

Establece el tamaño del paso (en bytes) para las instrucciones de prefetch secuenciales. Añada la letra k o K para indicar kilobytes, m o M para indicar megabytes, g o G para indicar gigabytes. Por defecto, el tamaño del paso se establece en 16 bytes: 
-XX:AllocatePrefetchStepSize=16
Solo la Java HotSpot Server VM soporta esta opción.

-XX:AllocatePrefetchStyle=estilo

Establece el estilo de código generado para las instrucciones de prefetch. El argumento estilo es un entero de 0 a 3:

0

No generar instrucciones de prefetch.

1

Ejecutar instrucciones de prefetch después de cada asignación. Este es el parámetro predeterminado.

2

Utilizar el puntero de marca del bloque de asignación local del hilo (TLAB) para determinar cuándo se ejecutan las instrucciones de prefetch.

3

Utilizar la instrucción BIS en SPARC para la prefetch de asignación.

Solo la Java HotSpot Server VM soporta esta opción.

-XX:+BackgroundCompilation

Habilita la compilación en segundo plano. Esta opción está habilitada por defecto. Para deshabilitar la compilación en segundo plano, especifique -XX:-BackgroundCompilation (esto es equivalente a especificar -Xbatch).

-XX:CICompilerCount=hilos

Establece el número de hilos del compilador a utilizar para la compilación. Por defecto, el número de hilos se establece en 2 para la JVM del servidor, en 1 para la JVM del cliente, y escala al número de núcleos si se utiliza compilación en niveles. El siguiente ejemplo muestra cómo establecer el número de hilos a 2: 
-XX:CICompilerCount=2

-XX:CodeCacheMinimumFreeSpace=tamaño

Establece el espacio libre mínimo (en bytes) requerido para la compilación. Añada la letra k o K para indicar kilobytes, m o M para indicar megabytes, g o G para indicar gigabytes. Cuando queda menos del espacio libre mínimo, la compilación se detiene. Por defecto, esta opción se establece en 500 KB. El siguiente ejemplo muestra cómo establecer el espacio libre mínimo a 1024 MB: 
-XX:CodeCacheMinimumFreeSpace=1024m

-XX:CompileCommand=comando,método[,opción]

Especifica un comando a realizar sobre un método. Por ejemplo, para excluir el método indexOf() de la clase String de ser compilado, utilice lo siguiente: 
-XX:CompileCommand=exclude,java/lang/String.indexOf
Tenga en cuenta que se especifica el nombre completo de la clase, incluyendo todos los paquetes y subpaquetes separados por una barra (/). Para facilitar las operaciones de copiar y pegar, también es posible utilizar el formato del nombre del método producido por las opciones -XX:+PrintCompilation y -XX:+LogCompilation: 
-XX:CompileCommand=exclude,java.lang.String::indexOf
Si el método se especifica sin la firma, el comando se aplicará a todos los métodos con el nombre especificado. Sin embargo, también puede especificar la firma del método en el formato de archivo de clase. En este caso, debe encerrar los argumentos entre comillas, ya que de lo contrario el shell tratará el punto y coma como el fin del comando. Por ejemplo, si desea excluir solo el método indexOf(String) de la clase String de ser compilado, utilice lo siguiente: 
-XX:CompileCommand="exclude,java/lang/String.indexOf,(Ljava/lang/String;)I"
También puede utilizar el asterisco (*) como comodín para nombres de clase y método. Por ejemplo, para excluir todos los métodos indexOf() en todas las clases de ser compilados, utilice lo siguiente: 
-XX:CompileCommand=exclude,*.indexOf
Las comas y los puntos son alias de espacios, lo que facilita el paso de comandos del compilador a través de un shell. Puede pasar argumentos a -XX:CompileCommand utilizando espacios como separadores encerrando el argumento entre comillas: 
-XX:CompileCommand="exclude java/lang/String indexOf"
Tenga en cuenta que después de analizar los comandos pasados en la línea de comandos utilizando las opciones -XX:CompileCommand, el compilador JIT lee entonces los comandos del archivo .hotspot_compiler. Puede añadir comandos a este archivo o especificar un archivo diferente utilizando la opción -XX:CompileCommandFile.

Para añadir varios comandos, especifique la opción -XX:CompileCommand varias veces o separe cada argumento con el separador de nueva línea (\n). Los siguientes comandos están disponibles:

break

Establece un punto de interrupción al depurar la JVM para detenerse al principio de la compilación del método especificado.

compileonly

Excluye todos los métodos de la compilación excepto el método especificado. Como alternativa, puede utilizar la opción -XX:CompileOnly, que permite especificar varios métodos.

dontinline

Evita la inlining del método especificado.

exclude

Excluye el método especificado de la compilación.

help

Imprime un mensaje de ayuda para la opción -XX:CompileCommand.

inline

Intenta hacer la inlining del método especificado.

log

Excluye el registro de compilación (con la opción -XX:+LogCompilation) para todos los métodos excepto el método especificado. Por defecto, el registro se realiza para todos los métodos compilados.

option

Este comando se puede utilizar para pasar una opción de compilación JIT al método especificado en lugar del último argumento (opción). La opción de compilación se establece al final, después del nombre del método. Por ejemplo, para habilitar la opción BlockLayoutByFrequency para el método append() de la clase StringBuffer, utilice lo siguiente: 
-XX:CompileCommand=option,java/lang/StringBuffer.append,BlockLayoutByFrequency
Puede especificar varias opciones de compilación, separadas por comas o espacios.

print

Imprime el código ensamblador generado después de la compilación del método especificado.

quiet

No imprime los comandos de compilación. Por defecto, los comandos que especifique con la opción -XX:CompileCommand se imprimen; por ejemplo, si excluye de la compilación el método indexOf() de la clase String, se imprimirá lo siguiente en la salida estándar: 
CompilerOracle: exclude java/lang/String.indexOf

Imprime estadísticas detalladas de deduplicación. Por defecto, esta opción está deshabilitada. Consulte la opción -XX:+UseStringDeduplication.

-XX:+PrintTenuringDistribution

Habilita la impresión de información de edad de tenencia. El siguiente es un ejemplo de la salida: 
Tamaño deseado de superviviente 48286924 bytes, nuevo umbral 10 (máx 10)
- edad 1: 28992024 bytes, 28992024 total
- edad 2: 1366864 bytes, 30358888 total
- edad 3: 1425912 bytes, 31784800 total
...
Los objetos de edad 1 son los supervivientes más jóvenes (se crearon después de la búsqueda anterior, sobrevivieron a la última búsqueda y se movieron del espacio Eden al espacio de supervivientes). Los objetos de edad 2 han sobrevivido a dos búsquedas (durante la segunda búsqueda se copiaron de un espacio de supervivientes al siguiente). Y así sucesivamente.

En el ejemplo anterior, 28 992 024 bytes sobrevivieron a una búsqueda y se copiaron de Eden al espacio de supervivientes, 1 366 864 bytes están ocupados por objetos de edad 2, etc. El tercer valor en cada fila es el tamaño acumulado de objetos de edad n o menos.

Por defecto, esta opción está deshabilitada.

-XX:+ScavengeBeforeFullGC

Habilita la GC de la generación joven antes de cada GC completo. Esta opción está habilitada por defecto. Oracle recomienda que *no* la deshabilite, ya que la búsqueda de la generación joven antes de un GC completo puede reducir el número de objetos alcanzables desde el espacio de generación antigua a los del espacio de generación joven. Para deshabilitar la GC de la generación joven antes de cada GC completo, especifique -XX:-ScavengeBeforeFullGC.

-XX:SoftRefLRUPolicyMSPerMB=tiempo

Establece la cantidad de tiempo (en milisegundos) que un objeto accesible suavemente se mantiene activo en el heap después de la última vez que se hizo referencia a él. El valor predeterminado es un segundo de vida por megabyte libre en el heap. La opción -XX:SoftRefLRUPolicyMSPerMB acepta valores enteros que representan milisegundos por un megabyte del tamaño actual del heap (para Java HotSpot Client VM) o el tamaño máximo posible del heap (para Java HotSpot Server VM). Esta diferencia significa que la VM cliente tiende a descargar referencias suaves en lugar de aumentar el heap, mientras que la VM servidor tiende a aumentar el heap en lugar de descargar referencias suaves. En este último caso, el valor de la opción -Xmx tiene un efecto significativo en la rapidez con la que se recolectan las referencias suaves.

El siguiente ejemplo muestra cómo establecer el valor en 2.5 segundos:

-XX:SoftRefLRUPolicyMSPerMB=2500

-XX:StringDeduplicationAgeThreshold=umbral

Los objetos String que alcanzan la edad especificada se consideran candidatos para la deduplicación. La edad de un objeto es una medida de cuántas veces ha sobrevivido a la recolección de basura. Esto a veces se denomina tenencia; consulte la opción -XX:+PrintTenuringDistribution. Tenga en cuenta que los objetos String que se promocionan a una región de heap antigua antes de alcanzar esta edad siempre se consideran candidatos para la deduplicación. El valor predeterminado para esta opción es 3. Consulte la opción -XX:+UseStringDeduplication.

-XX:SurvivorRatio=relación

Establece la relación entre el tamaño del espacio Eden y el tamaño del espacio de supervivientes. Por defecto, esta opción se establece en 8. El siguiente ejemplo muestra cómo establecer la relación entre el espacio Eden y el espacio de supervivientes en 4: 
-XX:SurvivorRatio=4

-XX:TargetSurvivorRatio=porcentaje

Establece el porcentaje deseado de espacio de supervivientes (0 a 100) utilizado después de la recolección de basura joven. Por defecto, esta opción se establece en 50%.

El siguiente ejemplo muestra cómo establecer la relación objetivo del espacio de supervivientes en 30%:

-XX:TargetSurvivorRatio=30

-XX:TLABSize=tamaño

Establece el tamaño inicial (en bytes) de un búfer de asignación local de hilos (TLAB). Añada la letra k o K para indicar kilobytes, m o M para indicar megabytes, g o G para indicar gigabytes. Si esta opción se establece en 0, entonces la JVM elige el tamaño inicial automáticamente.

El siguiente ejemplo muestra cómo establecer el tamaño inicial del TLAB en 512 KB:

-XX:TLABSize=512k

-XX:+UseAdaptiveSizePolicy

Habilita el uso del dimensionamiento adaptativo de generación. Esta opción está habilitada por defecto. Para deshabilitar el dimensionamiento adaptativo de generación, especifique -XX:-UseAdaptiveSizePolicy y establezca el tamaño del grupo de asignación de memoria explícitamente (consulte la opción -XX:SurvivorRatio).

-XX:+UseCMSInitiatingOccupancyOnly

Habilita el uso del valor de ocupación como el único criterio para iniciar el recolector CMS. Por defecto, esta opción está deshabilitada y se pueden usar otros criterios.

-XX:+UseConcMarkSweepGC

Habilita el uso del recolector de basura CMS para la generación antigua. Oracle recomienda que utilice el recolector de basura CMS cuando los requisitos de latencia de la aplicación no puedan ser cumplidos por el recolector de basura de rendimiento (-XX:+UseParallelGC). El recolector de basura G1 (-XX:+UseG1GC) es otra alternativa.

Por defecto, esta opción está deshabilitada y el recolector se elige automáticamente en función de la configuración de la máquina y el tipo de la JVM. Cuando esta opción está habilitada, la opción -XX:+UseParNewGC se establece automáticamente y no debe deshabilitarla, ya que la siguiente combinación de opciones ha sido obsoleta en JDK 8: -XX:+UseConcMarkSweepGC -XX:-UseParNewGC.

-XX:+UseG1GC

Habilita el uso del recolector de basura garbage-first (G1). Es un recolector de basura de estilo servidor, dirigido a máquinas multiprocesador con una gran cantidad de RAM. Cumple los objetivos de tiempo de pausa de GC con alta probabilidad, manteniendo un buen rendimiento. Se recomienda el recolector G1 para aplicaciones que requieren heaps grandes (tamaños de alrededor de 6 GB o más) con requisitos de latencia de GC limitados (tiempo de pausa estable y predecible por debajo de 0.5 segundos).

Por defecto, esta opción está deshabilitada y el recolector se elige automáticamente en función de la configuración de la máquina y el tipo de la JVM.

-XX:+UseGCOverheadLimit

Habilita el uso de una política que limita la proporción de tiempo dedicado por la JVM a la GC antes de que se lance una excepción OutOfMemoryError. Esta opción está habilitada, por defecto, y el recolector paralelo lanzará un OutOfMemoryError si se dedica más del 98% del tiempo total a la recolección de basura y se recupera menos del 2% del heap. Cuando el heap es pequeño, esta característica se puede utilizar para evitar que las aplicaciones se ejecuten durante largos períodos de tiempo con poco o ningún progreso. Para deshabilitar esta opción, especifique -XX:-UseGCOverheadLimit.

-XX:+UseNUMA

Habilita la optimización del rendimiento de una aplicación en una máquina con arquitectura de memoria no uniforme (NUMA) aumentando el uso de memoria de menor latencia por parte de la aplicación. Por defecto, esta opción está deshabilitada y no se realiza ninguna optimización para NUMA. La opción solo está disponible cuando se utiliza el recolector de basura paralelo (-XX:+UseParallelGC).

-XX:+UseParallelGC

Habilita el uso del recolector de basura paralelo (también conocido como recolector de rendimiento) para mejorar el rendimiento de su aplicación aprovechando múltiples procesadores.

Por defecto, esta opción está deshabilitada y el recolector se elige automáticamente en función de la configuración de la máquina y el tipo de la JVM. Si está habilitada, la opción -XX:+UseParallelOldGC se habilita automáticamente, a menos que la deshabilite explícitamente.

-XX:+UseParallelOldGC

Habilita el uso del recolector de basura paralelo para GCs completos. Por defecto, esta opción está deshabilitada. Habilitarla habilita automáticamente la opción -XX:+UseParallelGC.

-XX:+UseParNewGC

Habilita el uso de hilos paralelos para la recolección en la generación joven. Por defecto, esta opción está deshabilitada. Se habilita automáticamente cuando se establece la opción -XX:+UseConcMarkSweepGC. El uso de la opción -XX:+UseParNewGC sin la opción -XX:+UseConcMarkSweepGC fue obsoleto en JDK 8.

-XX:+UseSerialGC

Habilita el uso del recolector de basura serial. Esta suele ser la mejor opción para aplicaciones pequeñas y sencillas que no requieren ninguna funcionalidad especial de la recolección de basura. Por defecto, esta opción está deshabilitada y el recolector se elige automáticamente en función de la configuración de la máquina y el tipo de la JVM.

-XX:+UseSHM

En Linux, habilita la JVM para usar memoria compartida para configurar páginas grandes.

Para más información, consulte "Páginas grandes".

-XX:+UseStringDeduplication

Habilita la deduplicación de cadenas. Por defecto, esta opción está deshabilitada. Para usar esta opción, debe habilitar el recolector de basura garbage-first (G1). Consulte la opción -XX:+UseG1GC.

La deduplicación de cadenas reduce la huella de memoria de los objetos String en el heap de Java aprovechando el hecho de que muchos objetos String son idénticos. En lugar de que cada objeto String apunte a su propia matriz de caracteres, los objetos String idénticos pueden apuntar y compartir la misma matriz de caracteres.

-XX:+UseTLAB

Habilita el uso de bloques de asignación locales de hilos (TLAB) en el espacio de generación joven. Esta opción está habilitada por defecto. Para deshabilitar el uso de TLAB, especifique -XX:-UseTLAB.

JAVAVM OPTIONS

These are the options that can be used to tune the performance of the JVM. They are divided into the following categories:

  • Garbage collection options.
  • Options for large page support.

GARBAGE COLLECTION OPTIONS

The following options are related to garbage collection.

-XX:+CMSClassUnloadingEnabled

Enables the unloading of classes when using the concurrent mark-sweep (CMS) collector. This option was deprecated in JDK 8 with no replacement.

-XX:+CMSIncrementalMode

Enables the incremental mode for the CMS collector. This option was deprecated in JDK 8 with no replacement, along with other options that start with CMSIncremental.

-XX:CMSIncrementalOffset=percent

Sets the percentage of time (0 to 100) by which the incremental mode duty cycle is shifted to the right within the period between minor collections. This option was deprecated in JDK 8 with no replacement, following the deprecation of the -XX:+CMSIncrementalMode option.

-XX:+CMSIncrementalPacing

Enables automatic adjustment of the incremental mode duty cycle based on statistics collected while the JVM is running. This option was deprecated in JDK 8 with no replacement, following the deprecation of the -XX:+CMSIncrementalMode option.

-XX:CMSIncrementalSafetyFactor=percent

Sets the percentage of time (0 to 100) used to add conservatism when computing the duty cycle. This option was deprecated in JDK 8 with no replacement, following the deprecation of the -XX:+CMSIncrementalMode option.

-XX:CMSInitiatingPermOccupancyFraction=percent

Sets the percentage of the permanent generation occupancy (0 to 100) at which to start a GC. This option was deprecated in JDK 8 with no replacement.

-XX:MaxPermSize=size

Sets the maximum permanent generation space size (in bytes). This option was deprecated in JDK 8, and superseded by the -XX:MaxMetaspaceSize option.

-XX:PermSize=size

Sets the space (in bytes) allocated to the permanent generation that triggers a garbage collection if it is exceeded. This option was deprecated un JDK 8, and superseded by the -XX:MetaspaceSize option.

-XX:+UseSplitVerifier

Enables splitting of the verification process. By default, this option was enabled in the previous releases, and verification was split into two phases: type referencing (performed by the compiler) and type checking (performed by the JVM runtime). This option was deprecated in JDK 8, and verification is now split by default without a way to disable it.

-XX:+UseStringCache

Enables caching of commonly allocated strings. This option was removed from JDK 8 with no replacement.

LARGE PAGES

Also known as huge pages, large pages are memory pages that are significantly larger than the standard memory page size (which varies depending on the processor and operating system). Large pages optimize processor Translation-Lookaside Buffers.

A Translation-Lookaside Buffer (TLB) is a page translation cache that holds the most-recently used virtual-to-physical address translations. TLB is a scarce system resource. A TLB miss can be costly as the processor must then read from the hierarchical page table, which may require multiple memory accesses. By using a larger memory page size, a single TLB entry can represent a larger memory range. There will be less pressure on TLB, and memory-intensive applications may have better performance.

However, large pages page memory can negatively affect system performance. For example, when a large mount of memory is pinned by an application, it may create a shortage of regular memory and cause excessive paging in other applications and slow down the entire system. Also, a system that has been up for a long time could produce excessive fragmentation, which could make it impossible to reserve enough large page memory. When this happens, either the OS or JVM reverts to using regular pages.

Large Pages Support

Solaris and Linux support large pages.

Solaris

Solaris 9 and later include Multiple Page Size Support (MPSS); no additional configuration is necessary. See http://www.oracle.com/technetwork/server-storage/solaris10/overview/solaris9-features-scalability-135663.html.

Linux

The 2.6 kernel supports large pages. Some vendors have backported the code to their 2.4-based releases. To check if your system can support large page memory, try the following:

# cat /proc/meminfo | grep Huge
HugePages_Total: 0
HugePages_Free: 0
Hugepagesize: 2048 kB

If the output shows the three "Huge" variables, then your system can support large page memory but it needs to be configured. If the command prints nothing, then your system does not support large pages. To configure the system to use large page memory, login as root, and then follow these steps:

1.If you are using the option -XX:+UseSHM (instead of -XX:+UseHugeTLBFS), then increase the SHMMAX value. It must be larger than the Java heap size. On a system with 4 GB of physical RAM (or less), the following will make all the memory sharable: 
# echo 4294967295 > /proc/sys/kernel/shmmax
2.If you are using the option -XX:+UseSHM or -XX:+UseHugeTLBFS, then specify the number of large pages. In the following example, 3 GB of a 4 GB system are reserved for large pages (assuming a large page size of 2048kB, then 3 GB = 3 * 1024 MB = 3072 MB = 3072 * 1024 kB = 3145728 kB and 3145728 kB / 2048 kB = 1536): 
# echo 1536 > /proc/sys/vm/nr_hugepages

Note
4 • Note that the values contained in /proc will reset after you reboot your system, so may want to set them in an initialization script (for example, rc.local or sysctl.conf). 4 • If you configure (or resize) the OS kernel parameters /proc/sys/kernel/shmmax or /proc/sys/vm/nr_hugepages, Java processes may allocate large pages for areas in addition to the Java heap. These steps can allocate large pages for the following areas: 4 • Java heap 4 • Code cache 4 • The marking bitmap data structure for the parallel GC Consequently, if you configure the nr_hugepages parameter to the size of the Java heap, then the JVM can fail in allocating the code cache areas on large pages because these areas are quite large in size.
