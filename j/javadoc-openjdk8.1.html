DE PAQUETE

Cada paquete puede tener su propio comentario de documentación, contenido en su propio archivo fuente, que el

comando

javadoc fusiona en la página de resumen del paquete generada. Normalmente, incluyeen este comentario cualquier documentación que se aplique a todo el paquete.

Para crear un archivo de comentarios de paquete, puedes colocar tus comentarios en uno de los siguientes archivos:

•
El archivo package-info.java puede contener la declaración del paquete, anotaciones de paquete, comentarios de paquete y etiquetas Javadoc. Este archivo es el preferido.
•
El archivo package.html contiene solo comentarios de paquete y etiquetas Javadoc. No hay anotaciones de paquete.

Un paquete puede tener un solo archivo package.html o un solo archivo package-info.java, pero no ambos. Coloca cualquiera de los archivos en el directorio del paquete en el árbol de fuentes junto con tus archivos de código fuente.

El Archivo package-info.java

El archivo package-info.java puede contener un comentario de paquete de la siguiente estructura. El comentario se coloca antes de la declaración del paquete.

Nota: Los separadores de comentarios /** y */ deben estar presentes, pero los asteriscos iniciales en las líneas intermedias se pueden omitir.

/**
 * Proporciona las clases necesarias para crear una applet 
 * y las clases que una applet utiliza para comunicarse 
 * con su contexto de applet.
 * <p>
 * El framework de applets involucra dos entidades: la applet 
 * y el contexto de applet. Una applet es una ventana 
 * incrustable (ver la clase {@link java.awt.Panel}) con algunos 
 * métodos adicionales que el contexto de applet puede usar para 
 * inicializar, iniciar y detener la applet.
 *
 * @since 1.0
 * @see java.awt
 */
package java.lang.applet;

El archivo package.html es un archivo HTML típico y no incluye una declaración de paquete. El contenido del archivo de comentarios del paquete está escrito en HTML con una excepción. El comentario de documentación no debe incluir los separadores de comentarios /** y */ ni los asteriscos iniciales. Al escribir el comentario, haz que la primera oración sea un resumen sobre el paquete y no pongas un título ni ningún otro texto entre la etiqueta <body> y la primera oración. Puedes incluir etiquetas de paquete. Todas las etiquetas de bloque deben aparecer después de la descripción principal. Si agregas una etiqueta @see en un archivo de comentarios de paquete, esta debe tener un nombre completamente calificado.

Procesamiento del Archivo de Comentarios

Cuando el comando javadoc se ejecuta, busca el archivo de comentarios del paquete. Si se encuentra el archivo de comentarios del paquete, el comando javadoc hace lo siguiente:

•
Copia el comentario para su procesamiento. Para package.html, el comando javadoc copia todo el contenido entre las etiquetas HTML <body> y </body>. Puedes incluir una sección <head> para poner una etiqueta <title>, una declaración de derechos de autor del archivo fuente u otra información, pero nada de esto aparece en la documentación generada.
•
Procesa las etiquetas de paquete. Ver Etiquetas de Paquete.
•
Inserta el texto procesado al final de la página de resumen del paquete generada. Ver Java Platform, Standard Edition API Specification Overview en http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copia la primera oración del comentario del paquete a la parte superior de la página de resumen del paquete. El comando javadoc también agrega el nombre del paquete y esta primera oración a la lista de paquetes en la página general. Ver Java Platform, Standard Edition API Specification Overview en http://docs.oracle.com/javase/8/docs/api/overview-summary.html

El final de la oración se determina por las mismas reglas que se usan para el final de la primera oración de las descripciones principales de clases y miembros.

ARCHIVOS DE COMENTARIO GENERAL

Cada aplicación o conjunto de paquetes que estés documentando puede tener su propio comentario de documentación general que se mantiene en su propio archivo fuente, que el comando javadoc fusiona en la página general generada. Normalmente, incluyes en este comentario cualquier documentación que se aplique a toda la aplicación o conjunto de paquetes.

Puedes nombrar el archivo como quieras, por ejemplo overview.html, y colocarlo en cualquier lugar. Una ubicación típica es en la parte superior del árbol de fuentes.

Por ejemplo, si los archivos fuente del paquete java.applet están contenidos en el directorio /home/user/src/java/applet, entonces podrías crear un archivo de comentario general en /home/user/src/overview.html.

Puedes tener múltiples archivos de comentario general para el mismo conjunto de archivos fuente en caso de que desees ejecutar el comando javadoc varias veces en diferentes conjuntos de paquetes. Por ejemplo, podrías ejecutar el comando javadoc una vez con -private para documentación interna y otra vez sin esa opción para documentación pública. En este caso, podrías describir la documentación como pública o interna en la primera oración de cada archivo de comentario general.

El contenido del archivo de comentario general es un gran comentario de documentación escrito en HTML. Haz que la primera oración sea un resumen sobre la aplicación o el conjunto de paquetes. No pongas un título ni ningún otro texto entre la etiqueta <body> y la primera oración. Todas las etiquetas, excepto las etiquetas en línea, como una etiqueta {@link}, deben aparecer después de la descripción principal. Si agregas una etiqueta @see, entonces debe tener un nombre completamente calificado.

Cuando ejecutas el comando javadoc, especifica el nombre del archivo de comentario general con la opción -overview. El archivo se procesa de manera similar a la de un archivo de comentarios de paquete. El comando javadoc hace lo siguiente:

•
Copia todo el contenido entre las etiquetas <body> y </body> para su procesamiento.
•
Procesa las etiquetas generales presentes. Ver Etiquetas Generales.
•
Inserta el texto procesado al final de la página general generada. Ver Java Platform Standard Edition API Specification Overview en http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copia la primera oración del comentario general a la parte superior de la página de resumen general.

ARCHIVOS&#x00A0;NO&#x00A0;PROCESADOS

Tus archivos fuente pueden incluir cualquier archivo que desees que el comando javadoc copie al directorio de destino. Estos archivos suelen incluir archivos gráficos, archivos de código fuente y de clase de ejemplo, y archivos HTML independientes con mucho contenido que abrumaría el comentario de documentación de un archivo fuente típico de Java.

Para incluir archivos no procesados, colócalos en un directorio llamado doc-files. El directorio doc-files puede ser un subdirectorio de cualquier directorio de paquete que contenga archivos fuente. Puedes tener un subdirectorio doc-files para cada paquete.

Por ejemplo, si deseas incluir la imagen de un botón en la documentación de la clase java.awt.Button, coloca el archivo de imagen en el directorio /home/user/src/java/awt/doc-files/. No coloques el directorio doc-files en /home/user/src/java/doc-files, porque java no es un paquete. No contiene archivos fuente.

Todos los enlaces a los archivos no procesados deben incluirse en el código porque el comando javadoc no examina los archivos. El comando javadoc copia el directorio y todo su contenido al destino. El siguiente ejemplo muestra cómo podría verse el enlace en el comentario del archivo de documentación de Button.java:

/**
 * Este botón se ve así: 
 * <img src="doc-files/Button.gif">
 */

ARCHIVOS&#x00A0;DE&#x00A0;PRUEBA&#x00A0;Y&#x00A0;PLANTILLA

Puedes almacenar archivos de prueba y plantillas en el árbol de fuentes en el mismo directorio o en un subdirectorio del directorio donde residen los archivos fuente. Para evitar que los archivos de prueba y plantillas se procesen, ejecuta el comando javadoc y pasa explícitamente los nombres de los archivos fuente individuales.

Los archivos de prueba son archivos fuente válidos y compilables. Los archivos de plantilla no son archivos fuente válidos y compatibles, pero a menudo tienen la extensión .java.

Archivos de Prueba

Si quieres que tus archivos de prueba pertenezcan a un paquete sin nombre o a un paquete diferente al que pertenecen los archivos fuente, coloca los archivos de prueba en un subdirectorio debajo de los archivos fuente y dale al directorio un nombre inválido. Si colocas los archivos de prueba en el mismo directorio que las fuentes y llamas al comando javadoc con un argumento de línea de comandos que indica su nombre de paquete, los archivos de prueba causarán advertencias o errores. Si los archivos están en un subdirectorio con un nombre inválido, se omitirá el directorio de los archivos de prueba y no se emitirán errores ni advertencias. Por ejemplo, para agregar archivos de prueba para archivos fuente en com.package1, colócalos en un subdirectorio con un nombre de paquete inválido. El siguiente nombre de directorio es inválido porque contiene un guion:

com/package1/test-files/

Si tus archivos de prueba contienen comentarios de documentación, puedes configurar una ejecución separada del comando javadoc para producir documentación de archivos de prueba pasando sus nombres de archivo fuente de prueba con comodines, como com/package1/test-files/*.java.

ARCHIVOS GENERADOS

Por defecto, el comando javadoc utiliza un doclet estándar que genera documentación en formato HTML. El doclet estándar genera el contenido básico, las referencias cruzadas y las páginas de soporte que se describen aquí. Cada página HTML corresponde a un archivo separado. El comando javadoc genera dos tipos de archivos. El primer tipo se nombra según las clases e interfaces. El segundo tipo contiene guiones (como package-summary.html) para evitar conflictos con el primer tipo de archivo.

•
Una página de clase o interfaz (classname.html) por cada clase o interfaz que se documenta.
•
Una página de paquete (package-summary.html) por cada paquete que se documenta. El comando javadoc incluye cualquier texto HTML proporcionado en un archivo con el nombre package.html o package-info.java en el directorio del paquete del árbol fuente.
•
Una página de resumen (overview-summary.html) para todo el conjunto de paquetes. La página de resumen es la página principal de la documentación generada. El comando javadoc incluye cualquier texto HTML proporcionado en un archivo especificado por la opción -overview. •

Por ejemplo, dada una clase o interfaz A, su página de uso incluye subclases de A, campos declarados como A, métodos que devuelven A, y métodos y constructores con parámetros de tipo A. Para ver la página de uso, vaya al paquete, clase o interfaz y haga clic en el enlace Use en la barra de navegación.

Una página de valores de campos constantes (constant-values.html) para los valores de los campos estáticos.
•

La información de esta página es de interés para los reimplementadores, y no para los desarrolladores que desean utilizar la API. Para acceder a la página de formulario serializado, vaya a cualquier clase serializada y haga clic en Serialized Form en la sección Véase también del comentario de la clase. El doclet estándar genera una página de formulario serializado que enumera cualquier clase (pública o no pública) que implemente Serializable con sus métodos readObject y writeObject, los campos que se serializan y los comentarios de documentación de las etiquetas @serial, @serialField y @serialData. Las clases serializables públicas pueden excluirse marcándolas (o su paquete) con @serial exclude, y las clases serializables private de paquete pueden incluirse marcándolas (o su paquete) con un @serial include. A partir de la versión 1.4, puede generar el formulario serializado completo para clases públicas y privadas ejecutando el comando javadoc sin especificar la opción -private. Consulte Opciones.

La página de índice está internacionalizada para Unicode y se puede generar como un solo archivo o como un archivo separado para cada carácter inicial (por ejemplo, A–Z para inglés).

FRAMES&#x00A0;HTML

El comando javadoc genera el número mínimo de frames (dos o tres) necesarios según los valores pasados al comando. Omite la lista de paquetes cuando se pasa un solo nombre de paquete o archivos fuente que pertenecen a un solo paquete como argumento al comando javadoc. En su lugar, el comando javadoc crea un frame en la columna izquierda que muestra la lista de clases. Cuando se pasan dos o más nombres de paquete, el comando javadoc crea un tercer frame que enumera todos los paquetes y una página de resumen (overview-summary.html). Para omitir los frames, haga clic en el enlace No Frames o acceda al conjunto de páginas desde la página overview-summary.html.

ESTRUCTURA&#x00A0;DE&#x00A0;ARCHIVOS&#x00A0;GENERADOS

Los archivos de clase e interfaz generados se organizan en la misma jerarquía de directorios en la que se organizan los archivos fuente de Java y los archivos de clase. Esta estructura es un directorio por subpaquete.

Por ejemplo, la documentación generada para la clase java.applet.Applet estaría ubicada en java/applet/Applet.html.

La estructura de archivos para el paquete java.applet se muestra a continuación, asumiendo que el directorio de destino se llama apidocs. Todos los archivos que contienen la palabra frame aparecen en los frames superior izquierdo o inferior izquierdo, según se indica. Todos los demás archivos HTML aparecen en el frame derecho.

Los directorios están en negrita. Los asteriscos (*) indican los archivos y directorios que se omiten cuando los argumentos del comando javadoc son nombres de archivos fuente en lugar de nombres de paquetes. Cuando los argumentos son nombres de archivos fuente, se crea una lista de paquetes vacía. El directorio doc-files no se crea en el destino a menos que exista en el árbol fuente. DECLARACIONES DE API GENERADAS

El comando javadoc genera una declaración al comienzo de la descripción de cada clase, interfaz, campo, constructor y método para ese elemento de la API. Por ejemplo, la declaración para la clase Boolean es:

public final class Boolean
extends Object
implements Serializable

La declaración para el método Boolean.valueOf es:

public static Boolean valueOf(String s)

El comando javadoc puede incluir los modificadores public, protected, private, abstract, final, static, transienty volatile, pero no synchronized ni native. Los modificadores synchronized y native se consideran detalles de implementación y no forman parte de la especificación de la API.

En lugar de depender de la palabra clave synchronized, las APIs deben documentar su semántica de concurrencia en la descripción principal del comentario. Por ejemplo, una descripción podría ser: Una enumeración única no puede ser utilizada por múltiples hilos de forma concurrente. El documento no debe describir cómo lograr estas semánticas. Como otro ejemplo, aunque la opción Hashtable debería ser segura para hilos (thread-safe), no hay razón para especificar que se logra sincronizando todos sus métodos exportados. Es mejor reservar el derecho de sincronizar internamente a nivel de "bucket" para una mayor concurrencia.

COMENTARIOS DE DOCUMENTACIÓN

Esta sección describe los comentarios del código fuente y la herencia de comentarios.

COMENTARIOS DEL CÓDIGO FUENTE

Puede incluir comentarios de documentación en el código fuente, antes de las declaraciones de cualquier clase, interfaz, método, constructor o campo. También puede crear comentarios de documentación para cada paquete y otro para la vista general, aunque su sintaxis es ligeramente diferente. Un comentario de documentación consiste en los caracteres entre /** y */ que lo terminan. Se permiten asteriscos al principio de cada línea y se describen más en la siguiente sección. El texto en un comentario puede continuar en múltiples líneas.

/**
 * Este es el formato típico de un comentario de documentación simple
 * que abarca dos líneas.
 */

Para ahorrar espacio puede poner un comentario en una sola línea:

/** Este comentario ocupa solo una línea. */

Colocación de los Comentarios

Los comentarios de documentación solo se reconocen cuando se colocan inmediatamente antes de las declaraciones de clase, interfaz, constructor, método o campo. Los comentarios de documentación colocados en el cuerpo de un método se ignoran. El comando javadoc reconoce solo un comentario de documentación por declaración. Ver Dónde se pueden usar las etiquetas.

Un error común es poner una declaración import entre el comentario de la clase y la declaración de la clase. No ponga una declaración import en esta ubicación porque el comando javadoc ignorará el comentario de la clase.

/**
 * Este es el comentario de la clase para la clase Whatever.
 */
import com.example;   // ERROR - Es importante no poner la declaración import aquí
public class Whatever{ }

Partes de los Comentarios

Un comentario de documentación tiene una descripción principal seguida de una sección de etiquetas. La descripción principal comienza después del delimitador inicial /** y continúa hasta la sección de etiquetas. La sección de etiquetas comienza con la primera etiqueta de bloque, que está definida por el primer carácter @ que comienza una línea (ignorando asteriscos iniciales, espacios en blanco y el separador inicial /**). Es posible tener un comentario con solo una sección de etiquetas y sin descripción principal. La descripción principal no puede continuar después de que comienza la sección de etiquetas. El argumento de una etiqueta puede abarcar múltiples líneas. Puede haber cualquier número de etiquetas, y algunos tipos de etiquetas pueden repetirse mientras que otros no. Por ejemplo, esta etiqueta @see comienza la sección de etiquetas:

/**
 * Esta oración contiene la descripción principal para este comentario de documentación.
 * @see java.lang.Object
 */

Etiquetas de Bloque y en Línea

Una etiqueta es una palabra clave especial dentro de un comentario de documentación que el comando javadoc procesa. Hay dos tipos de etiquetas: etiquetas de bloque, que aparecen como una etiqueta @tag (también conocidas como etiquetas independientes), y etiquetas en línea, que aparecen dentro de llaves, como una etiqueta {@tag} . Para ser interpretada, una etiqueta de bloque debe aparecer al comienzo de una línea, ignorando asteriscos iniciales, espacios en blanco y el separador (/**). Esto significa que puede usar el carácter @ en otro lugar del texto y no será interpretado como el inicio de una etiqueta. Si desea comenzar una línea con el carácter @ y que no sea interpretado, use la entidad HTML &. Cada etiqueta de bloque tiene texto asociado, que incluye cualquier texto que siga a la etiqueta hasta, pero sin incluir, la siguiente etiqueta o el final del comentario de documentación. Este texto asociado puede abarcar múltiples líneas. Se permite e interpreta una etiqueta en línea en cualquier lugar donde se permita texto. El siguiente ejemplo contiene la etiqueta de bloque @deprecated y la etiqueta en línea {@link} . Ver Etiquetas de Javadoc.

/**
 * @deprecated  A partir de JDK 1.1, reemplazado por {@link #setBounds(int,int,int,int)}
 */

Escribir Comentarios en HTML

El texto debe escribirse en HTML con entidades y etiquetas HTML. Puede usar la versión de HTML que su navegador soporte. El doclet estándar genera código compatible con HTML 3.2 en otros lugares (fuera de los comentarios de documentación) con la inclusión de hojas de estilo en cascada y marcos (frames). Se prefiere HTML 4.0 para los archivos generados debido a los conjuntos de marcos.

Por ejemplo, las entidades para el símbolo menor que (<) y el símbolo mayor que (>) deben escribirse como & y &. De manera similar, el símbolo de ampersand (&) debe escribirse como &. La etiqueta HTML de negrita <b> se muestra en el siguiente ejemplo.

/**
 * Este es un comentario <b>doc</b>.
 * @see java.lang.Object
 */

Asteriscos Iniciales

Cuando el comando javadoc analiza un comentario de documentación, los asteriscos iniciales (*) de cada línea se descartan, y los espacios en blanco y tabulaciones que preceden a los asteriscos iniciales (*) también se descartan. Si omite el asterisco inicial en una línea, el espacio en blanco inicial ya no se elimina, de modo que puede pegar ejemplos de código directamente en un comentario de documentación dentro de una etiqueta <PRE> con su indentación preservada. Los espacios son interpretados por los navegadores de manera más uniforme que los tabuladores. La indentación es relativa al margen izquierdo (en lugar del separador /** o la etiqueta <PRE> ).

Primera Oración

La primera oración de cada comentario de documentación debe ser una oración de resumen que contenga una descripción concisa pero completa de la entidad declarada. Esta oración termina en el primer punto seguido de un espacio en blanco, tabulador o terminador de línea, o en la primera etiqueta de bloque. El comando javadoc copia esta primera oración al resumen del miembro en la parte superior de la página HTML.

Declaraciones de Múltiples Campos

La plataforma Java le permite declarar múltiples campos en una sola declaración, pero esta declaración solo puede tener un comentario de documentación que se copia para todos los campos. Si desea comentarios de documentación individuales para cada campo, declare cada campo en una declaración separada. Por ejemplo, el siguiente comentario de documentación no tiene sentido escrito como una única declaración y sería mejor manejarlo como dos declaraciones:

/** 
 * Las distancias horizontal y vertical del punto (x,y)
 */
public int x, y;      // Evitar esto

El comando javadoc genera la siguiente documentación a partir del código anterior:

public int x

Las distancias horizontal y vertical del punto (x, y).

public int y

Las distancias horizontal y vertical del punto (x, y).

Uso de Etiquetas de Encabezado

Al escribir comentarios de documentación para miembros, es mejor no usar etiquetas de encabezado HTML como <H1> y <H2>, porque el comando javadoc crea un documento estructurado completo, y estas etiquetas estructurales podrían interferir con el formato del documento generado. Sin embargo, puede usar estos encabezados en comentarios de clase y paquete para proporcionar su propia estructura.

HERENCIA DE COMENTARIOS DE MÉTODOS

El comando javadoc permite la herencia de comentarios de métodos en clases e interfaces para rellenar texto faltante o para heredar explícitamente comentarios de métodos. Los constructores, campos y clases anidadas no heredan comentarios de documentación.

Nota: El archivo fuente de un método heredado debe estar en la ruta especificada por la opción -sourcepath para que el comentario de documentación esté disponible para copiarse. Ni la clase ni su paquete necesitan ser pasados en la línea de comandos. Esto contrasta con la versión 1.3n y versiones anteriores, donde la clase tenía que ser una clase documentada.

Rellenar Texto Faltante

Cuando falta una descripción principal o una etiqueta @return, @paramo @throws en un comentario de método, el comando javadoc copia la descripción principal o el comentario de la etiqueta correspondiente del método que sobrescribe o implementa (si existe). Ver Herencia de Comentarios de Métodos.

Cuando falta una etiqueta @param para un parámetro particular, el comentario para ese parámetro se copia del método más arriba en la jerarquía de herencia. Cuando falta una etiqueta @throws para una excepción particular, la etiqueta @throws se copia solo cuando esa excepción está declarada.

Este comportamiento contrasta con la versión 1.3 y anteriores, donde la presencia de cualquier descripción principal o etiqueta impedía que todos los comentarios se heredaran.

Ver Etiquetas y Opciones de Javadoc.

Herencia Explícita

Inserte la etiqueta en línea {@inheritDoc} en la descripción principal de un método o en el comentario de una etiqueta @return, @paramo @throws . La descripción principal heredada correspondientecripción o comentario de etiqueta se copia en ese lugar.

HERENCIA DE CLASES E INTERFACES

La herencia de comentarios ocurre en todos los casos posibles de herencia de clases e interfaces:

•
Cuando un método en una clase sobrescribe a un método en una superclase
•
Cuando un método en una interfaz sobrescribe a un método en una superinterfaz
•
Cuando un método en una clase implementa un método en una interfaz

En los dos primeros casos, el comando javadoc genera el subtítulo Sobrescribe en la documentación para el método que sobrescribe. Se incluye un enlace al método que se está sobrescribiendo, independientemente de si el comentario se hereda o no.

En el tercer caso, cuando un método en una clase especificada implementa un método en una interfaz, el comando javadoc genera el subtítulo Especificado por en la documentación para el método que sobrescribe. Se incluye un enlace al método que se está implementando, independientemente de si el comentario se hereda o no.

ALGORITMO DE COMENTARIOS DE MÉTODOS

Si un método no tiene un comentario de documentación, o tiene una etiqueta {@inheritDoc} , entonces el comando javadoc usa el siguiente algoritmo para buscar un comentario aplicable. El algoritmo está diseñado para encontrar el comentario de documentación aplicable más específico y para dar preferencia a las interfaces sobre las superclases:

1.
Buscar en cada interfaz implementada directamente (o extendida) en el orden en que aparecen después de la palabra implements (o extends) en la declaración del método. Usar el primer comentario de documentación encontrado para este método.
2.
Si el Paso 1 no encontró un comentario de documentación, entonces aplicar recursivamente este algoritmo completo a cada interfaz implementada directamente (o extendida) en el mismo orden en que se examinaron en el Paso 1.
3.
Cuando el Paso 2 no encuentra un comentario de documentación y se trata de una clase que no es la clase Object , pero no es una interfaz:
1.
Si la superclase tiene un comentario de documentación para este método, entonces usarlo.
2.
Si el Paso 3a no encontró un comentario de documentación, entonces aplicar recursivamente este algoritmo completo a la superclase.

ETIQUETAS JAVADOC

El comando javadoc analiza etiquetas especiales cuando están incrustadas dentro de un comentario de documentación de Java. Las etiquetas javadoc le permiten autogenerar una API completa y bien formateada a partir de su código fuente. Las etiquetas comienzan con un signo de arroba (@) y distinguen entre mayúsculas y minúsculas. Deben escribirse con las letras mayúsculas y minúsculas como se muestra. Una etiqueta debe comenzar en el inicio de una línea (después de cualquier espacio inicial y un asterisco opcional), o se tratará como texto. Por convención, las etiquetas con el mismo nombre se agrupan juntas. Por ejemplo, poner todas las etiquetas @see juntas. Para más información, ver Dónde se pueden usar las etiquetas.

Las etiquetas tienen los siguientes tipos:

•
Etiquetas de bloque: Colocar etiquetas de bloque solo en la sección de etiquetas que sigue a la descripción. Las etiquetas de bloque tienen la forma: @tag.
•
Etiquetas en línea: Colocar etiquetas en línea en cualquier lugar de la descripción principal o en los comentarios para etiquetas de bloque. Las etiquetas en línea se encierran entre llaves: {@tag}.

Para etiquetas personalizadas, ver -tag tagname:Xaoptcmf:"taghead". Ver también Dónde se pueden usar las etiquetas.

DESCRIPCIONES DE ETIQUETAS

@author nombre-texto
Introducida en JDK 1.0

Añade una entrada de Autor con el texto de nombre especificado a los documentos generados cuando se usa la opción -author . Un comentario de documentación puede contener múltiples etiquetas @author . Puede especificar un nombre por etiqueta @author o múltiples nombres por etiqueta. En el primer caso, el comando javadoc inserta una coma (,) y un espacio entre los nombres. En el segundo caso, el texto completo se copia a el documento generado sin ser analizado. Por lo tanto, puede usar múltiples nombres por línea si desea un separador de nombres localizado diferente a una coma. Ver @author en Cómo escribir comentarios de documentación para la herramienta Javadoc en http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@author

{@code texto}
Introducida en JDK 1.5

Equivalente a <code>{@literal}</code>.

Muestra texto en fuente de código sin interpretar el texto como marcado HTML o etiquetas Javadoc anidadas. Esto le permite usar corchetes angulares normales (< y >) en lugar de las entidades HTML (& y &) en comentarios de documentación, como en tipos de parámetros (<Object>), desigualdades (3 < 4), o flechas (<-). Por ejemplo, el texto del comentario de documentación {@code A<B>C} se muestra en la página HTML generada sin cambios como A<B>C. Esto significa que el <B> no se interpreta como negrita y está en fuente de código. Si desea la misma funcionalidad sin la fuente de código, entonces use la etiqueta {@literal} .

@deprecated texto-deprecado
Introducida en JDK 1.0

Añade un comentario indicando que esta API ya no debe usarse (aunque puede seguir funcionando). El comando javadoc mueve el texto-deprecadoantes de la descripción principal, colocándolo en cursiva y precediéndolo con una advertencia en negrita: Obsoleto. Esta etiqueta es válida en todos los comentarios de documentación: resumen, paquete, clase, interfaz, constructor, método y campo.

La primera oración del texto deprecado debe decir al usuario cuándo se deprecó la API y qué usar como reemplazo. El comando javadoc copia la primera oración a la sección de resumen y al índice. Las oraciones siguientes también pueden explicar por qué se deprecó. Debe incluir una etiqueta {@link} (para Javadoc 1.2 o posterior) que apunte a la API de reemplazo.

Use la etiqueta de anotación @deprecated para deprecar un elemento del programa. Ver Cómo y cuándo deprecar APIs en http://docs.oracle.com/javase/8/docs/technotes/guides/javadoc/deprecation/deprecation.html

Ver también @deprecated en Cómo escribir comentarios de documentación para la herramienta Javadoc en http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@deprecated

{@docRoot}
Introducida en JDK 1.3

Representa la ruta relativa al directorio raíz (destino) del documento generado desde cualquier página generada. Esta etiqueta es útil cuando desea incluir un archivo, como una página de copyright o un logotipo de la empresa, al que desea hacer referencia desde todas las páginas generadas. Es común enlazar a la página de copyright desde el pie de cada página.

Esta etiqueta {@docRoot} puede usarse tanto en la línea de comandos como en un comentario de documentación. Esta etiqueta es válida en todos los comentarios de documentación: resumen, paquete, clase, interfaz, constructor, método y campo, e incluye la porción de texto de cualquier etiqueta (como las etiquetas @return, @param y @deprecated ).

•
En la línea de comandos, donde se definen el encabezado, el pie o la parte inferior: javadoc -bottom '<a href="{@docRoot}/copyright.html">Copyright</a>'.

Cuando usa la etiqueta {@docRoot} de esta manera en un archivo de make, algunos programas makefile requieren una forma especial de escapar los caracteres de llave {} . Por ejemplo, el Inprise MAKE versión 5.2 que se ejecuta en Windows requiere llaves dobles: {{@docRoot}}. También requiere comillas dobles (en lugar de simples) para encerrar los argumentos de opciones como la opción -bottom (con las comillas alrededor del argumento href omitidas).

•
En un comentario de documentación: 
/**
 * Ver el <a href="{@docRoot}/copyright.html">Copyright</a>.
 */

Esta etiqueta es necesaria porque los documentos generados están en directorios jerárquicos, tan profundos como el número de subpaquetes. La expresión: <a href="{@docRoot}/copyright.html"> se resuelve a <a href="../../copyright.html"> para java/lang/Object.java y <a href="../../../copyright.html"> para java/lang/ref/Reference.java.

@exception nombre-de-clase descripción
Introducida en JDK 1.0

Idéntica a la etiqueta @throws . Ver @throws nombre-de-clase descripción.

{@inheritDoc}
Introducida en JDK 1.4

Hereda (copia) documentación de la clase heredable más cercana o de la interfaz implementable en el comentario de documentación actual en la ubicación de esta etiqueta. Esto le permite escribir comentarios más generales más arriba en el árbol de herencia y escribir alrededor del texto copiado.

Esta etiqueta es válida solo en estos lugares de un comentario de documentación:

•
En el bloque de descripción principal de un método. En este caso, la descripción principal se copia de una clase o interfaz más arriba en la jerarquía.
•
En los argumentos de texto de las etiquetas @return, @param, y @throws de un método. En este caso, el texto de la etiqueta se copia de la etiqueta correspondiente más arriba en la jerarquía.

Ver Herencia de comentarios de métodos para una descripción de cómo se encuentran los comentarios en la jerarquía de herencia. Note que si esta etiqueta falta, entonces el comentario se hereda o no se hereda automáticamente según las reglas descritas en esa sección.

{@link paquete.clase#miembro etiqueta}
Introducida en JDK 1.2

Inserta un enlace en línea con una etiqueta de texto visible que apunta a la documentación para el paquete, clase o nombre de miembro especificado de una clase referenciada. Esta etiqueta es válida en todos los comentarios de documentación: resumen, paquete, clase, interfaz, constructor, método y campo, incluyendo la porción de texto de cualquier etiqueta, como las etiquetas @return, @param y @deprecated . Ver @link en Cómo escribir comentarios de documentación para la herramienta Javadoc en

Esta etiqueta es similar a la etiqueta @see. Ambas etiquetas requieren las mismas referencias y aceptan la misma sintaxis para package.class#member y label. La principal diferencia es que la etiqueta {@link} genera un enlace en línea en lugar de colocar el enlace en la sección "See Also". La etiqueta {@link} comienza y termina con llaves para separarla del resto del texto en línea. Si necesita usar la llave derecha (}) dentro de la etiqueta, use la notación de entidad HTML &#125;.

No hay límite en la cantidad de etiquetas {@link} permitidas en una oración. Puede usar esta etiqueta en la parte principal de la descripción de cualquier comentario de documentación o en la parte de texto de cualquier etiqueta, como las etiquetas @deprecated, @return o @param.

Por ejemplo, aquí hay un comentario que se refiere al método getComponentAt(int, int):

Use el método {@link #getComponentAt(int, int) getComponentAt}.

A partir de este código, el doclet estándar genera el siguiente HTML (suponiendo que se refiere a otra clase en el mismo paquete):

Use el método <a href="Component.html#getComponentAt(int, int)">getComponentAt</a>.

La línea anterior aparece en la página web como:

Use el método getComponentAt.
{@linkplain package.class#member label}
Introducido en JDK 1.4

Se comporta igual que la etiqueta {@link}, excepto que la etiqueta del enlace se muestra en texto plano en lugar de fuente de código. Útil cuando la etiqueta es texto plano. Por ejemplo, Consulte {@linkplain add() el método anulado}. se muestra como: Consulte el método anulado.

{@literal text}
Introducido en JDK 1.5

Muestra texto sin interpretar el texto como marcado HTML o etiquetas Javadoc anidadas. Esto le permite usar corchetes angulares (< y >) en lugar de entidades HTML (&lt; y &gt;) en comentarios de documentación, como en tipos de parámetros (<Object>), desigualdades (3 < 4) o flechas (<-). Por ejemplo, el texto del comentario de documentación {@literal A<B>C} se muestra sin cambios en la página HTML generada en su navegador, como A<B>C. El <B> no se interpreta como negrita (y no está en fuente de código). Si desea la misma funcionalidad con el texto en fuente de código, use la etiqueta {@code}.

@param parameter-name description
Introducido en JDK 1.0

Agrega un parámetro con el parameter-name especificado seguido de la descripción especificada a la sección "Parameters". Al escribir el comentario de documentación, puede continuar la descripción en varias líneas. Esta etiqueta solo es válida en un comentario de documentación para un método, constructor o clase. Consulte @param en How to Write Doc Comments for the Javadoc Tool en http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@param

El parameter-name puede ser el nombre de un parámetro en un método o constructor, o el nombre de un parámetro de tipo de una clase, método o constructor. Use corchetes angulares alrededor de este nombre de parámetro para especificar el uso de un parámetro de tipo.

Ejemplo de un parámetro de tipo de una clase:

/**
 * @param <E> Tipo de elemento almacenado en una lista
 */
public interface List<E> extends Collection<E> {
}

Ejemplo de un parámetro de tipo de un método:

/**
 * @param string  la cadena a convertir
 * @param type    el tipo al que convertir la cadena
 * @param <T>     el tipo del elemento
 * @param <V>     el valor del elemento
 */
<T, V extends T> V convert(String string, Class<T> type) {
}
@return description
Introducido en JDK 1.0

Agrega una sección "Returns" con el texto de la descripción. Este texto debe describir el tipo de retorno y el rango de valores permitidos. Esta etiqueta solo es válida en un comentario de documentación para un método. @see reference
Introducido en JDK 1.0

Agrega un encabezado "See Also" con un enlace o una entrada de texto que apunta a una referencia. Un comentario de documentación puede contener cualquier número de etiquetas @see, que se agrupan bajo el mismo encabezado. La etiqueta @see tiene tres variaciones. La forma es la más común. Esta etiqueta es válida en cualquier comentario de documentación: general, paquete, clase, interfaz, constructor, método o campo. Para insertar un enlace en línea dentro de una oración a un paquete, clase o miembro, consulte {@link}.

Forma 1. La forma de etiqueta @see string agrega una entrada de texto para string. No se genera ningún enlace. La cadena es un libro u otra referencia a información no disponible por URL. El comando javadoc distingue esto de los casos anteriores buscando una comilla doble (") como primer carácter. Por ejemplo, @see "The Java Programming Language" que genera el siguiente texto:

See Also:

"The Java Programming Language"

Forma 2. La forma @see <a href="URL#value">label</a> agrega un enlace según lo definido por URL#value. El parámetro URL#value es una URL relativa o absoluta. El comando javadoc distingue esto de otros casos buscando un símbolo menor que (<) como primer carácter. Por ejemplo, @see <a href="spec.html#section">Java Spec</a> genera el siguiente enlace:

See Also:

Java Spec

Forma 3. La forma @see package.class#member label agrega un enlace con una etiqueta de texto visible que apunta a la documentación del nombre especificado en el Lenguaje Java al que se hace referencia. La etiqueta es opcional. Si la etiqueta se omite, entonces el nombre aparece en su lugar como texto visible, convenientemente acortado. Use la opción -noqualifier para eliminar globalmente el nombre del paquete de este texto visible. Use la etiqueta cuando desee que el texto visible sea diferente del texto visible generado automáticamente. Consulte How a Name Appears.

En Java SE 1.2 solamente, el nombre pero no la etiqueta aparece automáticamente en etiquetas HTML <code>. A partir de Java SE 1.2.2, la etiqueta <code> siempre se incluye alrededor del texto visible, ya sea que se use o no una etiqueta.

•
package.class#member es cualquier nombre de elemento de programa válido al que se hace referencia, como un paquete, clase, interfaz, constructor, método o nombre de campo, excepto que el carácter delante del nombre del miembro debe ser un signo de número (#). La clase representa cualquier clase o interfaz de nivel superior o anidada. El miembro representa cualquier constructor, método o campo (no una clase o interfaz anidada). Si este nombre está en las clases documentadas, el comando javadoc crea un enlace a él. Para crear enlaces a clases referenciadas externamente, use la opción -link. Use cualquiera de las otras dos formas de etiqueta @see para referirse a la documentación de un nombre que no pertenece a una clase referenciada. Consulte Specify a Name.

Nota: Las clases referenciadas externamente son clases que no se pasan al comando javadoc en la línea de comandos. Los enlaces en la documentación generada a clases referenciadas externamente se denominan referencias externas o enlaces externos. Por ejemplo, si ejecuta el comando javadoc solo en el paquete java.awt, entonces cualquier clase en java.lang, como Object, es una clase referenciada externamente. Use las opciones -link y -linkoffline para enlazar a clases referenciadas externamente. Los comentarios fuente de las clases referenciadas externamente no están disponibles para la ejecución del comando javadoc.

•

Orden de búsqueda para la etiqueta @see

El javadoc comando procesa una @see etiqueta que aparece en un archivo de origen, un archivo de paquete o un archivo de descripción general. En los dos últimos archivos, debe calificar completamente el nombre que proporciona con la @see etiqueta. En un archivo de origen, puede especificar un nombre que esté calificado completamente o parcialmente.

El siguiente es el orden de búsqueda para la @see etiqueta.

1.
La clase o interfaz actual.
2.
Cualquier clase o interfaz contenedora, buscando primero la más cercana.
3.
Cualquier superclase o superinterfaz, buscando primero la más cercana.
4.
El paquete actual.
5.
Cualquier paquete, clase o interfaz importada, buscando en el orden de la import declaración.

El javadoc comando continúa buscando recursivamente a través de los elementos 1-3 para cada clase que encuentre hasta que encuentre una coincidencia. Es decir, después de buscar a través de la clase actual y su clase contenedora E, busca a través de las superclases de E antes que las clases contenedoras de E. En los elementos 4 y 5, el javadoc comando no busca clases ni interfaces dentro de un paquete en ningún orden especificado (ese orden depende del compilador particular). En el elemento 5, el javadoc comando busca en java.lang porque ese es importado por todos los programas.

Cuando el javadoc comando encuentra una @see etiqueta en un archivo de origen que no está calificado completamente, busca el nombre especificado en el mismo orden en que lo haría el compilador de Java, excepto que el javadoc comando no detecta ciertas ambigüedades de espacio de nombres porque asume que el código fuente está libre de estos errores. Este orden de búsqueda está formalmente definido en la Especificación del Lenguaje Java. El javadoc comando busca ese nombre a través de todas las clases y paquetes relacionados e importados. En particular, busca en este orden:

1.
La clase o interfaz actual.
2.
Cualquier clase o interfaz contenedora, buscando primero la más cercana.
3.
Cualquier superclase o superinterfaz, buscando primero la más cercana.
4.
El paquete actual.
5.
Cualquier paquete, clase o interfaz importada, buscando en el orden de las import declaraciones.

El javadoc comando no busca necesariamente en subclases, ni buscará en otros paquetes incluso cuando su documentación se esté generando en la misma ejecución. Por ejemplo, si la @see etiqueta está en la java.awt.event.KeyEvent clase y se refiere a un nombre en el paquete java.awt, entonces el javadoc comando no busca en ese paquete a menos que esa clase lo importe.

Si label se omite, entonces package.class.member aparece. En general, se acorta adecuadamente con respecto a la clase y el paquete actuales. Acortado significa que el javadoc comando muestra solo el nombre mínimo necesario. Por ejemplo, si el método String.toUpperCase() contiene referencias a un miembro de la misma clase y a un miembro de una clase diferente, entonces el nombre de la clase se muestra solo en el último caso, como se muestra en el siguiente listado. -sourcepath sourcepathlist

Especifica las rutas de búsqueda para encontrar archivos fuente al pasar nombres de paquetes o la opción -subpackages al comando javadoc. Separe múltiples rutas con dos puntos (:). El comando javadoc busca en todos los subdirectorios de las rutas especificadas. Tenga en cuenta que esta opción no solo se utiliza para localizar los archivos fuente que se están documentando, sino también para encontrar archivos fuente que no se están documentando, pero cuyos comentarios son heredados por los archivos fuente que se están documentando.

Puede usar la opción -sourcepath solo al pasar nombres de paquetes al comando javadoc. Esto no localizará archivos fuente pasados al comando javadoc. Para localizar archivos fuente, cambie a ese directorio o incluya la ruta antes de cada archivo, como se muestra en Documentar una o más clases. Si omite -sourcepath, el comando javadoc utiliza la ruta de clases para encontrar los archivos fuente (ver -classpath). La ruta de origen por defecto es el valor de la ruta de clases. Si se omite -classpath y se pasan nombres de paquetes al comando javadoc, el comando javadoc busca en el directorio actual y sus subdirectorios los archivos fuente.

Establezca sourcepathlist en el directorio raíz del árbol de origen del paquete que está documentando.

Por ejemplo, suponga que desea documentar un paquete llamado com.mypackage, cuyos archivos fuente se encuentran en /home/user/src/com/mypackage/*.java. Especifique la ruta de origen en /home/user/src, el directorio que contiene com\mypackage, y luego proporcione el nombre del paquete, como sigue:

javadoc -sourcepath /home/user/src/ com.mypackage

Observe que si concatena el valor de la ruta de origen y el nombre del paquete y cambia el punto por una barra (/), obtendrá la ruta completa del paquete:

/home/user/src/com/mypackage

Para apuntar a dos rutas de origen:

javadoc -sourcepath /home/user1/src:/home/user2/src com.mypackage
-classpath classpathlist

Especifica las rutas donde el comando javadoc busca las clases referenciadas. Estas son las clases documentadas más cualquier clase referenciada por esas clases. Separe múltiples rutas con dos puntos (:). El comando javadoc busca en todos los subdirectorios de las rutas especificadas. Siga las instrucciones en la documentación de la ruta de clases para especificar el valor de classpathlist.

Si omite -sourcepath, el comando javadoc utiliza -classpath para encontrar los archivos fuente y de clase (para compatibilidad con versiones anteriores). Si desea buscar archivos fuente y de clase en rutas separadas, utilice tanto -sourcepath como -classpath.

Por ejemplo, si desea documentar com.mypackage, cuyos archivos fuente residen en el directorio /home/user/src/com/mypackage, y si este paquete depende de una biblioteca en /home/user/lib, entonces utilizaría el siguiente comando:

javadoc -sourcepath /home/user/lib -classpath /home/user/src com.mypackage

Similar a otras herramientas, si no especifica -classpath, el comando javadoc utiliza la variable de entorno CLASSPATH cuando está establecida. Si ninguna de las dos está establecida, el comando javadoc busca clases desde el directorio actual.

Para una descripción detallada de cómo el comando javadoc utiliza -classpath para encontrar clases de usuario en relación con clases de extensión y clases de arranque, consulte Cómo se encuentran las clases en http://docs.oracle.com/javase/8/docs/technotes/tools/findingclasses.html

Un elemento de ruta de clases que contiene un nombre base de * se considera equivalente a especificar una lista de todos los archivos en el directorio con la extensión .jar o .JAR.

Por ejemplo, si el directorio mydir contiene a.jar y b.JAR, entonces el elemento de ruta de clases foo/* se expande a A.jar:b.JAR, excepto que el orden de los archivos JAR no está especificado. Todos los archivos JAR en el directorio especificado, incluidos los archivos ocultos, se incluyen en la lista. Una entrada de ruta de clases que consiste en * se expande a una lista de todos los archivos jar en el directorio actual. La variable de entorno CLASSPATH se expande de manera similar. Cualquier expansión de comodín de ruta de clases ocurre antes de que la Máquina Virtual Java (JVM) se inicie. Ningún programa Java ve comodines sin expandir excepto al consultar el entorno, por ejemplo, llamando a System.getenv("CLASSPATH").

Esta opción es útil al agregar nuevos subpaquetes al código fuente porque se incluyen automáticamente. Cada argumento de paquete es cualquier subpaquete de nivel superior (como java) o paquete completamente calificado (como javax.swing) que no necesita contener archivos fuente. Incluye una página de Uso (Use) para cada clase y paquete documentado. La página describe qué paquetes, clases, métodos, constructores y campos utilizan alguna API de la clase o paquete especificado. Esto documenta solo usos de la API, no la implementación. Cuando un método usa String en su implementación, pero no toma una cadena como argumento ni devuelve una cadena, eso no se considera un uso de String. Para acceder a la página de Uso generada, vaya a la clase o paquete y haga clic en el enlace Uso (Use link) en la barra de navegación.

Al igual que con cualquier etiqueta de bloque, el texto del argumento puede contener etiquetas en línea, que también se interpretan. Colocación de etiquetas: Los argumentos Xaoptcmf determinan dónde en el código fuente se permite colocar la etiqueta y si la etiqueta se puede deshabilitar (usando X). Puede proporcionar a, para permitir la etiqueta en todos los lugares, o cualquier combinación de las otras letras:

X (deshabilitar etiqueta)

a (todas)

o (descripción general)

p (paquetes)

t (tipos, es decir, clases e interfaces)

c (constructores)

m (métodos)

f (campos)

Ejemplos de etiquetas individuales: Un ejemplo de una opción de etiqueta para una etiqueta que se puede usar en cualquier lugar del código fuente es: -tag todo:a:"To Do:".

Si desea que la @todo etiqueta se utilice solo con constructores, métodos y campos, entonces utiliza: -tag todo:cmf:"To Do:".

Observe que el último signo de dos puntos (:) no es un separador de parámetros, sino que es parte del texto del encabezado. Utilizaría cualquiera de las opciones de etiqueta para el código fuente que contenga la @todo etiqueta, como: @todo The documentation for this method needs work.

Dos puntos en los nombres de las etiquetas: Utilice una barra invertida para escapar un signo de dos puntos que desee usar en un nombre de etiqueta. Utilice la -tag ejb\\:bean:a:"EJB Bean:" opción para el siguiente comentario de documentación:

/**
 * @ejb:bean
 */

Verificación ortográfica de los nombres de las etiquetas: Algunos desarrolladores colocan etiquetas personalizadas en el código fuente que no siempre desean generar. En estos casos, es importante enumerar todas las etiquetas que están en el código fuente, habilitando las que desea generar y deshabilitando las que no desea generar. La presencia de X deshabilita la etiqueta, mientras que su ausencia la habilita. Esto proporciona al javadoc comando la información suficiente para saber si una etiqueta que encuentra es desconocida, lo que probablemente es el resultado de un error tipográfico o una falta de ortografía. El javadoc comando imprime una advertencia en estos casos. Puede añadir X a los valores de colocación ya presentes, de modo que cuando desee habilitar la etiqueta, simplemente elimine la X. Por ejemplo, si la @todo etiqueta es una etiqueta que desea suprimir en la salida, entonces utilizaría: -tag todo:Xcmf:"To Do:". Si prefiere mantenerlo simple, utilice esto: -tag todo:X. La sintaxis -tag todo:X funciona incluso cuando la @todo etiqueta está definida por un taglet.

Orden de las etiquetas: El orden de las -tag y -taglet opciones determina el orden en que se generan las etiquetas. Puede mezclar las etiquetas personalizadas con las etiquetas estándar para intercalarlas. Las opciones de etiqueta para las etiquetas estándar son solo marcadores de posición para determinar el orden. Solo aceptan el nombre de la etiqueta estándar. Los subtítulos de las etiquetas estándar no se pueden alterar. Esto se ilustra en el siguiente ejemplo. Si falta la -tag opción, la posición de la -taglet opción determina su orden. Si ambas están presentes, entonces la que aparezca última en la línea de comandos determina su orden. Esto ocurre porque las etiquetas y los taglets se procesan en el orden en que aparecen en la línea de comandos. Por ejemplo, si las -taglet y -tag opciones tienen el nombre todo valor, entonces la que aparezca última en la línea de comandos determina el orden.

Ejemplo de un conjunto completo de etiquetas: Este ejemplo inserta To Do después de Parameters y antes de Throws en la salida. Al usar X, también especifica que la @example etiqueta podría encontrarse en el código fuente y no debe generarse durante esta ejecución. Si utiliza la @argfile etiqueta, puede colocar las etiquetas en líneas separadas en un archivo de argumentos similar a este (no se necesitan caracteres de continuación de línea):

-tag param
-tag return
-tag todo:a:"To Do:"
-tag throws
-tag see
-tag example:X

Cuando el javadoc comando analiza los comentarios de la documentación, cualquier etiqueta que encuentre que no sea una etiqueta estándar ni se haya pasado con las -tag o -taglet opciones se considera desconocida, y se lanza una advertencia.

Las etiquetas estándar se almacenan inicialmente internamente en una lista en su orden predeterminado. Siempre que se utilicen las -tag opciones, esas etiquetas se añaden a esta lista. Las etiquetas estándar se mueven de su posición predeterminada. Por lo tanto, si se omite una -tag opción para una etiqueta estándar, permanece en su posición predeterminada.

Evitación de conflictos: Si desea crear su propio espacio de nombres, puede utilizar una convención de nomenclatura separada por puntos similar a la utilizada para los paquetes: com.mycompany.todo. Oracle continuará creando etiquetas estándar cuyos nombres no contengan puntos. Cualquier etiqueta que cree anulará el comportamiento de una etiqueta con el mismo nombre definida por Oracle. Si crea una @todo etiqueta o taglet, siempre tendrá el mismo comportamiento que usted defina, incluso cuando Oracle cree posteriormente una etiqueta estándar del mismo nombre.

Anotaciones frente a etiquetas Javadoc: En general, si la marcación que desea añadir está destinada a afectar o producir documentación, entonces debe ser una etiqueta Javadoc. De lo contrario, debe ser una anotación. COMMAND-LINE ARGUMENT FILES

To shorten or simplify the javadoc command, you can specify one or more files that contain arguments to the javadoc command (except -J options). This enables you to create javadoc commands of any length on any operating system.

An argument file can include javac options and source file names in any combination. The arguments within a file can be space-separated or newline-separated. If a file name contains embedded spaces, then put the whole file name in double quotation marks.

NOMBRE

javadoc - generar documentación a partir de comentarios de documentación en archivos fuente de Java

SINOPSIS

javadoc [opciones] [paquetes]

DESCRIPCIÓN

El comando javadoc lee los archivos fuente de Java y genera, a partir de los comentarios de documentación, una suite de páginas HTML que describen las clases, interfaces, tipos enumerados, anotaciones y paquetes del programa. La suite de documentos resultante se organiza en paquetes y clases, y se presenta como un conjunto de páginas HTML que se puede ver con un navegador web.

La suite de documentos resultante se organiza en paquetes y clases, y se presenta como un conjunto de páginas HTML que se puede ver con un navegador web.

COMENTARIOS DE DOCUMENTACIÓN

Los comentarios de documentación son comentarios de línea única o múltiple que comienzan con •/** y terminan con */. Se pueden incluir en los archivos fuente de Java que preceden a la declaración de una clase, interfaz, método o campo. Los comentarios de documentación pueden incluir texto descriptivo y etiquetas especiales que comienzan con el signo arroba @.

La primera frase de un comentario de documentación es la primera frase del bloque de resumen. El comando javadoc convierte la primera frase en la descripción de resumen de la página de documentación HTML de la entidad declarada. Las frases subsiguientes (delimitadas por el punto final) se incluyen en el cuerpo principal del comentario.

Las etiquetas especiales incluyen:

@author
Nombre del autor.
@deprecated
Una descripción de cuándo y por qué se marcó un elemento como obsoleto. Esta etiqueta se puede usar con un comentario que incluya un mensaje para indicar la fecha y el motivo de la obsolescencia. El comando javadoc genera una advertencia de obsolescencia para cada elemento marcado como obsoleto.
@exception
Nombre de la clase de excepción y descripción. Se usa para documentar las excepciones que puede lanzar un método.
@param
Nombre del parámetro y descripción. Se usa para documentar los parámetros de un método.
@return
Descripción del valor de retorno. Se usa para documentar el valor de retorno de un método.
@see
Un enlace a otra clase, método o URL. Se usa para crear un enlace en la sección "Ver también".
@since
La versión de Java en la que se introdujo una característica.
@throws
Nombre de la clase de excepción y descripción. Similar a @exception.
@version
Información sobre la versión de la clase o el miembro.

DÓNDE SE PUEDEN USAR LAS ETIQUETAS

•
@author, @deprecated, @since, @version: solo se pueden usar en comentarios de documentación de nivel de clase.
•
@exception, @throws: solo se pueden usar en comentarios de documentación de nivel de método.
•
@param, @return: solo se pueden usar en comentarios de documentación de nivel de método.
•
@see: se puede usar en cualquier lugar.

-classpath ruta
Especifica la ruta de búsqueda para los archivos de clase de entrada y los archivos de recursos. Si no se especifica, se utiliza la variable de entorno CLASSPATH.
-sourcepath ruta
Especifica la ruta de búsqueda para los archivos fuente de Java. Si no se especifica, se utiliza la variable de entorno SOURCEPATH.
-link URL
Crea un enlace a la documentación de Java API externa. Esto permite que las clases referenciadas en la documentación se enlacen a la documentación correspondiente en línea.
-linkoffline ruta-html ruta-jars
Similar a -link, pero se usa para generar documentación sin acceso a la documentación en línea. ruta-html es la ruta al directorio donde se generará la documentación HTML, y ruta-jars es la ruta a los archivos JAR que contienen la documentación de referencia.
-linksource
Genera enlaces desde la documentación a los archivos fuente de Java correspondientes.
-group nombre-grupo paquetes-a-incluir
Agrupa los paquetes en la documentación generada. El argumento nombre-grupo es el nombre del grupo, y paquetes-a-incluir es una lista separada por dos puntos de patrones de paquetes a incluir en ese grupo.
-public, -protected, -package, -private
Especifica el nivel de visibilidad de los elementos que se incluirán en la documentación generada. Por defecto, se incluye solo el nivel -protected.
-help
Muestra un mensaje de ayuda y sale.

NOTAS

•
Si omite la opción -windowtitle, el comando javadoc copia el título del documento al título de la ventana. El texto de la opción -windowtitle es similar a la opción -doctitle, pero sin etiquetas HTML para evitar que esas etiquetas aparezcan como texto sin formato en el título de la ventana.
•
Si omite la opción -footer, el comando javadoc copia el texto del encabezado al pie de página.
•
Otras opciones importantes que podría querer usar, pero que no fueron necesarias en el ejemplo anterior, son las opciones -classpath y -link.

SOLUCIÓN DE PROBLEMAS GENERALES

•
El comando javadoc solo lee archivos que contienen nombres de clase válidos. Si el comando javadoc no está leyendo correctamente el contenido de un archivo, verifique que los nombres de clase sean válidos. Consulte "Procesar archivos fuente".
•
Consulte la FAQ de Javadoc para obtener información sobre errores comunes y consejos para la solución de problemas en http://www.oracle.com/technetwork/java/javase/documentation/index-137483.html

ERRORES Y ADVERTENCIAS

Los mensajes de error y advertencia contienen el nombre del archivo y el número de línea de la línea de declaración en lugar de la línea específica en el comentario de documentación.

Por ejemplo, este mensaje error: cannot read: Class1.java significa que el comando javadoc está intentando cargar Class1.java en el directorio actual. El nombre de la clase se muestra con su ruta (absoluta o relativa).

ENTORNO

CLASSPATH
CLASSPATH es la variable de entorno que proporciona la ruta que el comando javadoc utiliza para encontrar los archivos de clase del usuario. Esta variable de entorno se anula mediante la opción -classpath. Separe los directorios con un punto y coma para Windows o dos puntos para Oracle Solaris.

Ejemplo de Windows: .;C:\classes;C:\home\java\classes

Ejemplo de Oracle Solaris: .:/home/classes:/usr/local/java/classes.
