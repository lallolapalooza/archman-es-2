DESCRIPCIÓ

N

jc convierte a JSON la salida de muchas herramientas CLI, tipos de archivo y cadenas comunes para facilitar su análisis en scripts. jc acepta entrada canalizada desde STDIN y emite una representación JSON de la salida del comando anterior a STDOUT. Alternativamente, se puede usar la sintaxis "mágica" anteponiendo jc al comando que se desea convertir. Las opciones se pueden pasar a jc inmediatamente antes de indicar el comando. (Nota: la sintaxis

"mágica" no admite comandos intern
os del shell ni alias de comandos)

Segmento

:
Se admite el segmentado de líneas utilizando la sintaxis START:STOP similar al segmentado de Python. Esto le permite omitir líneas al principio y/o al final de la entrada STDIN que desea que jc convierta.

START y STOP pueden ser enteros positivos o negativos o estar en blanco, y le permiten especificar cuántas líneas omitir y cuántas líneas procesar. Los segmentos positivos y en blanco son los más eficientes en memoria. Cualquier entero negativo en el segmento usará más

memoria.

Por ejemplo, para omitir la primera y la última línea del siguiente texto, podría expresar el segmento de dos

maneras: 
$ cat table.txt
      ### Queremos omitir este encabezado ###
          col1       col2
          foo        1
          b
ar 2 ### Queremos omitir este pie de página ### $ cat table.txt | jc 1:-1 --asciitable [{"col1":"foo","col2":"
1"},{"col1":"bar","col2":"2"}] $ cat table.txt | jc 1:4 --asciitable [{"col1":"foo","col2":"1"},{"col1":"bar","col2":"2"}]

En este ejemplo 1:-1 y 1:4 los segmentos de líneas proporcionan la misma

salida.

Cuando se usan enteros positivos, la ubicación del índice de STOP es no inclusiva. Los segmentos positivos cuentan desde la primera línea de la entrada hacia el final, empezando en 0 como la primera línea. Los segmentos negativos cuentan desde la última línea hacia el principio, empezando en -1 como la última línea. Esta es también la forma en que funciona la función de segmentado de

Python.

ACUMULACI

ÓN

Algunos analizadores admiten entradas de múltiples elementos y pueden generar un array de resultados en un solo paso. La acumulación funciona para analizadores de cadenas que aceptan una sola línea de entrada. (por ejemplo, url y ip-address) Para ver una lista de analizadores que admiten la opción --slurp, use jc -h

hh.

Por ejemplo, puede enviar un archivo con múltiples direcciones IP (una por línea) a jc con la opción --slurp y se generará un array de

resultados: 
$ cat ip-addresses.txt | jc
--slurp --ip-address [<mú
ltiples objetos de salida>]

La sintaxis mágica para archivos /proc admite automáticamente la acumulación de múltiples archivos (no es necesario usar la opción --slurp). Por ejemplo, puede convertir muchos archivos PID a la

vez: 
$ jc /proc/*/stat
us [<múltiples ob
jetos de salida>]

Cuando se usa la sintaxis mágica /proc y se seleccionan múltiples archivos, se inserta un campo adicional _file en la salida para que sea más fácil determinar a qué archivo se refiere cada objeto de

salida.

Finalmente, la opción --meta-out puede usarse junto con la salida acumulada. En este caso, la salida acumulada se envuelve en un objeto con la siguiente

estructura: 
{
  "result": [<múltiples objetos de salida>],
  "_jc_meta": {
    "parser": "url",
    "timestamp": 1706235558.654576,
    "slice_start": null,
    "slice_end": null,
    "input_list": [
      "http://www.google.com",
      "https://www.apple.com",
      "https://www.microsoft.com"
    ]
  }
}

Con --meta-out, input_list contiene una lista de entradas (cadenas de entrada reales o nombres de archivos /proc) para que pueda identificar qué objeto de salida se relaciona con cada cadena de entrada o nombre de arc

hivo
/proc.

CÓDIGOS DE

SALIDA

Cualquier error fatal dentro de jc generará un código de salida de 100, de lo contrario el código de salida será 0

.

Cuando se usa la sintaxis "mágica" (por ejemplo, jc ifconfig eth0), jc almacenará el código de salida del programa que se está analizando y lo añadirá al código de salida de jc. De esta manera es más fácil determinar si un error provino del programa analizado o de jc

.

Considere los siguientes ejemplos usando ifconfig

:
código de salida de ifconfig = 0, código de salida de jc = 0, código de salida combinado = 0 (sin errores)

código de salida de ifconfig = 1, código de salida de jc = 0, código de salida combinado = 1 (error en

ifconfig)

código de salida de ifconfig = 0, código de salida de jc = 100, código de salida combinado = 100 (error en

jc)

código de salida de ifconfig = 1, código de salida de jc = 100, código de salida combinado = 101 (error tanto en

ifconfig c
omo en jc)

Cuando usa la sintaxis "mágica" también puede recuperar el código de salida del programa llamado usando la opción --meta-out o -M . Esto añadirá un objeto _jc_meta a la salida que incluirá la información del comando mágico, incluyendo el código de

salida.

:

    {
      "type": "timeout",

      "duplicate": false

  ],
  "_jc_meta": {
    "parser": "ping",

ANALIZADORES DE

FLUJO

La mayoría de los analizadores cargan todos los datos de STDIN, los analizan, y luego generan todo el documento JSON serialmente. Hay algunos analizadores de flujo (por ejemplo, ls-s, ping-s, etc.) que comienzan inmediatamente a procesar y generar los datos línea por línea como JSON Lines (también conocido como NDJSON) mientras se reciben de STDIN. Esto puede reducir significativamente la cantidad de memoriaory requerida para analizar grandes cantidades de salida de comandos (por ejemplo, ls -lR /) y a veces puede procesar los datos más rápidamente. Los analizadores de streaming tienen un comportamiento ligeramente diferente al de los analizadores estándar, como se describe a

continuación.
Nota: Los analizadores de streaming no se pueden usar con la sintaxis
"magic"

Ignorando

Errores

Es posible que desee ignorar los errores de análisis al usar analizadores de streaming, ya que estos pueden usarse en canalizaciones de procesamiento de larga duración y los errores pueden romper la tubería. Para ignorar los errores de análisis, use la opción -qq de la CLI. Esto añadirá un objeto _jc_meta a la salida JSON con un atributo success. Si success es true, entonces no hubo problemas al analizar la línea. Si success es false, entonces se encontró un problema de análisis y se añadirán los campos error y line para incluir una breve descripción del error y el contenido de la línea no analizable, respectivamente

:
Línea analizada con éxito con la opción -qq: 
{
  "command_data": "data",
  "_jc_meta": {
    "success": true
  }
}

Línea analizada sin éxito con la opción

-qq: 
{
  "_jc_meta": {
    "success": false,
    "error": "error message",
    "line": "original line data"
}
} Desactivando el Buffer de Salida

La mayoría de los sistemas operativos almacenarán en un buffer la salida que se canaliza de un proceso a otro. El buffer suele ser de alrededor de 4KB. Al ver la salida en la terminal, el buffer del SO no se utiliza, por lo que la salida se muestra inmediatamente en la pantalla. Sin embargo, al canalizar varios procesos juntos, puede parecer que la salida se está colgando cuando los datos de entrada son muy lentos (por ejemplo, ping

): 
$ ping 1.1.1.1 | jc --ping-s | jq
<salida
lenta>

Esto se debe a que el SO activa el buffer de 4KB entre jc y jq en este ejemplo. Para mostrar los datos en la terminal en tiempo real, puede desactivar el buffer con la opción -u (unbuffer) de la

CLI: 
$ ping 1.1.1.1 | jc --ping-s -u | jq
{"type":"reply","pattern":null,"timestamp":null,"bytes":"64",...}
{"type":"reply","pattern":null,"timestamp":null,"bytes":"64",...}
