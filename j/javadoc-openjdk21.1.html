NAME

javadoc - generate HTML pages of API documentation from Java source files

SYNOPSIS

javadoc [options] [packagenames] [sourcefiles] [@files]

options
Specifies command-line options, separated by spaces. See Standard javadoc Options, Extra javadoc Options, Standard Options for the Standard Doclet, and Extra Options for the Standard Doclet.
packagenames
Specifies names of packages that you want to document, separated by spaces, for example java.lang java.lang.reflect java.awt. If you want to also document the subpackages, then use the -subpackages option to specify the packages.

By default, javadoc looks for the specified packages in the current directory and subdirectories. Use the -sourcepath option to specify the list of directories where to look for packages.

sourcefiles
Specifies names of Java source files that you want to document, separated by spaces, for example Class.java Object.java Button.java. By default, javadoc looks for the specified classes in the current directory. However, you can specify the full path to the class file and use wildcard characters, for example /home/src/java/awt/Graphics*.java. You can also specify the path relative to the current directory.
@files
Specifies names of files that contain a list of javadoc tool options, package names, and source file names in any order.

DESCRIPTION

The javadoc tool parses the declarations and documentation comments in a set of Java source files and produces corresponding HTML pages that describe (by default) the public and protected classes, nested and unnamed classes (but not anonymous inner classes), interfaces, constructors, methods, and fields. You can use thejavadoc tool to generate the API documentation or the implementation documentation for a set of source files.

You can run the javadoc tool on entire packages, individual source files, or both. When documenting entire packages, you can use the -subpackages option either to recursively traverse a directory and its subdirectories, or to pass in an explicit list of package names. When you document individual source files, pass in a list of Java source file names.

Conformance

The Standard Doclet does not validate the content of documentation comments for conformance, nor does it attempt to correct any errors in documentation comments. Anyone running javadoc is advised to be aware of the problems that may arise when generating non-conformant output or output containing executable content, such as JavaScript. The Standard Doclet does provide the DocLint feature to help developers detect common problems in documentation comments; but it is also recommended to check the generated output with any appropriate conformance and other checking tools.

For more details on the conformance requirements for HTML5 documents, see Conformance requirements [https://www.w3.org/TR/html5/infrastructure.html#conformance-requirements] in the HTML5 Specification. For more details on security issues related to web pages, see the Open Web Application Security Project (OWASP) [https://www.owasp.org] page.

OPTIONS

javadoc supports command-line options for both the main javadoc tool and the currently selected doclet. The Standard Doclet is used if no other doclet is specified.

GNU-style options (that is, those beginning with --) can use an equal sign (=) instead of whitespace characters to separate the name of an option from its value.

The following options are the core javadoc options that are not equivalent to a corresponding javac option:

-breakiterator
Computes the first sentence with BreakIterator. The first sentence is copied to the package, class, or member summary and to the alphabetic index. The BreakIterator class is used to determine the end of a sentence for all languages except for English.
•
English default sentence-break algorithm --- Stops at a period followed by a space or an HTML block tag, such as <P>.
•
Breakiterator sentence-break algorithm --- Stops at a period, question mark, or exclamation point followed by a space when the next word starts with a capital letter. This is meant to handle most abbreviations (such as "The serial no. is valid", but will not handle "Mr. Smith"). The -breakiterator option doesn't stop at HTML tags or sentences that begin with numbers or symbols. The algorithm stops at the last period in ../filename, even when embedded in an HTML tag.
-doclet class
Generates output by using an alternate doclet. Use the fully qualified name. This doclet defines the content and formats the output. If the -doclet option isn't used, then the javadoc tool uses the standard doclet for generating the default HTML format. This class must contain the start(Root) method. The path to this starting class is defined by the -docletpath option.
-docletpath path
Specifies where to find doclet class files (specified with the -doclet option) and any JAR files it depends on. If the starting class file is in a JAR file, then this option specifies the path to that JAR file. You can specify an absolute path or a path relative to the current directory. If classpathlist contains multiple paths or JAR files, then they should be separated with a colon (:) on Linux and a semi-colon (;) on Windows. This option isn't necessary when the doclet starting class is already in the search path.
-exclude pkglist
Unconditionally, excludes the specified packages and their subpackages from the list formed by -subpackages. It excludes those packages even when they would otherwise be included by some earlier or later -subpackages option.

The following example would include java.io, java.util, and java.math (among others), but would exclude packages rooted at java.net and java.lang. Notice that these examples exclude java.lang.ref, which is a subpackage of java.lang.

•
Linux and macOS:

javadoc -sourcepath /home/user/src -subpackages java -exclude java.net:java.lang
•
Windows:

javadoc -sourcepath \user\src -subpackages java -exclude java.net:java.lang

-locale name
Especifica la configuración regional (locale) que la herramienta javadoc utiliza al generar la documentación. El argumento es el nombre de la configuración regional, como se describe en la documentación de java.util.Locale, por ejemplo, en_US (inglés, Estados Unidos) o en_US_WIN (variante de Windows).

Especificar una configuración regional hace que la herramienta javadoc elija los archivos de recursos de esa configuración regional para mensajes como cadenas en la barra de navegación, encabezados de listas y tablas, contenido del archivo de ayuda, comentarios en el archivo stylesheet.css, y así sucesivamente. También especifica el orden de clasificación para las listas ordenadas alfabéticamente, y el separador de oraciones para determinar el final de la primera oración. La opción -locale no determina la configuración regional del texto del comentario de documentación especificado en los archivos fuente de las clases documentadas.

Las siguientes opciones son proporcionadas por el doclet estándar.

--add-script file
Agrega file como un archivo JavaScript adicional a la documentación generada. Esta opción se puede usar una o más veces para especificar archivos de script adicionales.

Ejemplo de línea de comandos:

javadoc --add-script first_script.js --add-script second_script.js pkg_foo

--add-stylesheet file
Agrega file como un archivo de hoja de estilos adicional a la documentación generada. Esta opción se puede usar una o más veces para especificar hojas de estilos adicionales incluidas en la documentación.

Ejemplo de línea de comandos:


javadoc --add-stylesheet new_stylesheet_1.css --add-stylesheet new_stylesheet_2.css pkg_foo
--allow-script-in-comments
Permite JavaScript en opciones y comentarios.
-author
Incluye el texto @author en la documentación generada.
-bottom html-code
Especifica el texto que se colocará al final de cada archivo de salida. El texto se coloca al final de la página, debajo de la barra de navegación inferior. El texto puede contener etiquetas HTML y espacios en blanco, pero cuando lo hace, el texto debe estar entre comillas. Usa caracteres de escape para cualquier comilla interna dentro del texto.
-charset name
Especifica el conjunto de caracteres HTML para este documento. El nombre debe ser un nombre MIME preferido según el Registro de IANA, Conjuntos de Caracteres [http://www.iana.org/assignments/character-sets].

Por ejemplo:


javadoc -charset "iso-8859-1" mypackage

Este comando inserta la siguiente línea en la sección head de cada página generada:


<meta http-equiv="Content-Type" content="text/html; charset=ISO-8859-1">

La etiqueta meta se describe en el estándar HTML (4197265 y 4137321), Representación de Documentos HTML [http://www.w3.org/TR/REC-html40/charset.html#h-5.2.2].

-d directory
Especifica el directorio de destino donde la herramienta javadoc guarda los archivos HTML generados. Si omites la opción -d, los archivos se guardan en el directorio actual. El valor del directorio puede ser absoluto o relativo al directorio de trabajo actual. El directorio de destino se crea automáticamente cuando se ejecuta la herramienta javadoc.
•
Linux y macOS: Por ejemplo, el siguiente comando genera la documentación para el paquete com.mypackage y guarda los resultados en el directorio /user/doc/:

javadoc -d /user/doc/ com.mypackage
•
Windows: Por ejemplo, el siguiente comando genera la documentación para el paquete com.mypackage y guarda los resultados en el directorio \user\doc\:

javadoc -d \user\doc\ com.mypackage
-docencoding n
Especifica el conjunto de caracteres de los archivos HTML generados. Si no se especifica este encodado, se utiliza el encodado de la plataforma.

Por ejemplo:


javadoc -docencoding UTF-8 com.mypackage

Si la entrada de javadoc está en un conjunto de caracteres diferente del de la plataforma, es posible que necesites especificar el conjunto de caracteres de entrada utilizando la opción -encoding.

-encoding name
Especifica el nombre del conjunto de caracteres de los archivos fuente. Si no se especifica la opción -encoding, se utiliza el encodado predeterminado de la plataforma. La opción -docencoding especifica el conjunto de caracteres de los archivos HTML generados, no el de los archivos de entrada.

Por ejemplo:


javadoc -encoding UTF-8 com.mypackage

Este comando lee los archivos fuente de Java utilizando el conjunto de caracteres UTF-8.

-excludedpackages packagenames
Especifica una lista separada por dos puntos de paquetes que no se deben incluir en la generación de documentación. Los comodines no están permitidos. Por ejemplo:

javadoc -excludedpackages java.util:javax.swing.* com.mypackage

Excluye los paquetes java.util y todos los paquetes que comiencen con javax.swing.

--expand-args file
Lee argumentos adicionales de file y los expande en la línea de comandos. Esto permite pasar opciones largas o listas de archivos de entrada que de otro modo excederían el límite de argumentos de la línea de comandos.

Por ejemplo, si tienes un archivo llamado javadoc.args que contiene:


-d docs -sourcepath src -subpackages com.example

Entonces puedes ejecutar javadoc de la siguiente manera:


javadoc --expand-args javadoc.args

javadoc -footer "<i>My Project</i>" com.mypackage
-group name "nom 1" "nom 2" ...

Los argumentos subsiguientes son los nombres de los paquetes, entre comillas si contienen espacios. La opción -group se puede usar varias veces para diferentes grupos.

Ejemplo:


javadoc -group "Core Packages" java.lang java.util

-link url
Crea enlaces a documentación generada por javadoc existente de clases referenciadas externamente. El argumento url es la URL absoluta o relativa del directorio que contiene la documentación externa generada por javadoc. Puede especificar múltiples opciones -link en una ejecución de la herramienta javadoc especificada para enlazar con múltiples documentos.

Debe haber un archivo package-list o element-list en este directorio url (de lo contrario, use la opción -linkoffline).

Nota: Los archivos package-list y element-list son generados por la herramienta javadoc al generar la documentación de la API y no deben ser modificados por el usuario.

Cuando utiliza la herramienta javadoc para documentar paquetes, utiliza el archivo package-list para determinar los paquetes declarados en una API. Cuando genera documentos de API para módulos, la herramienta javadoc utiliza el archivo element-list para determinar los módulos y paquetes declarados en una API.

La herramienta javadoc lee los nombres del archivo de lista apropiado y luego enlaza con los paquetes o módulos en esa URL.

Cuando se ejecuta la herramienta javadoc, el valor url se copia en los enlaces <A HREF> que se crean. Por lo tanto, url debe ser la URL del directorio y no de un archivo.

Puede usar un enlace absoluto para url para permitir que sus documentos enlacen a un documento en cualquier sitio web, o puede usar un enlace relativo para enlazar solo a una ubicación relativa. Si usa un enlace relativo, entonces el valor que pase debe ser la ruta relativa desde el directorio de destino (especificado con la opción -d) al directorio que contiene los paquetes a los que se enlaza. Cuando especifica un enlace absoluto, generalmente usa un enlace HTTP. Sin embargo, si desea enlazar a un sistema de archivos que no tiene un servidor web, puede usar un enlace de archivo. Use un enlace de archivo solo cuando todos los que quieran acceder a la documentación generada compartan el mismo sistema de archivos. En todos los casos, y en todos los sistemas operativos, use una barra como separador, ya sea que la URL sea absoluta o relativa, y https:, http:, o file: según se especifica en el Memo de URL: Localizadores Uniformes de Recursos [http://www.ietf.org/rfc/rfc1738.txt].

El orden en que se dan las etiquetas en la línea de comandos se utilizará como el orden en que las etiquetas aparecen en la salida generada. Puede incluir etiquetas estándar en el orden dado en la línea de comandos usando la opción -tag sin ubicaciones ni encabezado.

-taglet clase
Especifica el nombre completo de la clase del taglet utilizado para generar la documentación de esa etiqueta. Usa el nombre completo de la clase para el valor clase. Este taglet también define el número de argumentos de texto que tiene la etiqueta personalizada. El taglet acepta esos argumentos, los procesa y genera la salida.

Los taglets son útiles para etiquetas de bloque o en línea. Pueden tener cualquier número de argumentos e implementar un comportamiento personalizado, como poner texto en negrita, formatear viñetas, escribir texto en un archivo o iniciar otros procesos. Los taglets solo pueden determinar dónde debe aparecer una etiqueta y en qué forma. Todas las demás decisiones las toma el doclet. Un taglet no puede hacer cosas como eliminar un nombre de clase de la lista de clases incluidas. Sin embargo, puede ejecutar efectos secundarios, como imprimir el texto de la etiqueta en un archivo o activar otro proceso. Usa la opción -tagletpath para especificar la ruta del taglet. El siguiente ejemplo inserta el taglet To Do después de Parámetros y antes de Throws en las páginas generadas.


-taglet com.sun.tools.doclets.ToDoTaglet
-tagletpath /home/taglets
-tag return
-tag param
-tag todo
-tag throws
-tag see

Alternativamente, puedes usar la opción -taglet en lugar de su opción -tag, pero eso podría ser difícil de leer.

-tagletpath lista-rutas-taglets
Especifica las rutas de búsqueda para encontrar archivos de clase de taglets. La lista-rutas-taglets puede contener múltiples rutas separándolas con el separador de rutas de la plataforma (; en Windows; : en otras plataformas.) La herramienta javadoc busca en todos los subdirectorios de las rutas especificadas.
-top código-html
Especifica el texto que se colocará en la parte superior de cada archivo de salida.
-use
Crea páginas de uso de clases y paquetes. Incluye una página de Uso por cada clase y paquete documentado. La página describe qué paquetes, clases, métodos, constructores y campos utilizan alguna API de la clase o paquete especificado. Dada una clase C, las cosas que usan la clase C incluirían sub-clases de C, campos declarados como C, métodos que devuelven C, y métodos y constructores con parámetros de tipo C. Por ejemplo, puedes ver la página de Uso del tipo String. Dado que el método getName en la clase java.awt.Font devuelve el tipo String, el método getName usa String y por lo tanto el método getName aparece en la página de Uso para String. Esto documenta solo usos de la API, no la implementación. Cuando un método usa String en su implementación, pero no toma una cadena como argumento o devuelve una cadena, eso no se considera un uso de String. Para acceder a la página de Uso generada, ve a la clase o paquete y haz clic en el enlace Uso en la barra de navegación.
-version
Incluye el texto de la versión en la documentación generada. Este texto se omite por defecto. Para averiguar qué versión de la herramienta javadoc estás utilizando, usa la opción -J-version.
-windowtitle título
Especifica el título que se colocará en la etiqueta HTML <title>. El texto especificado en la etiqueta de título aparece en el título de la ventana y en cualquier marcador (favoritos) que alguien cree para esta página. Este título no debe contener ninguna etiqueta HTML porque un navegador no las interpretará correctamente. Usa caracteres de escape en cualquier comilla interna dentro de la etiqueta de título. Si la opción -windowtitle se omite, entonces la herramienta javadoc usa el valor de la opción -doctitle para la opción -windowtitle. Por ejemplo, javadoc -windowtitle "Mi Biblioteca" com.mipaquete.

Opciones adicionales para el Doclet Estándar

Las siguientes son opciones adicionales proporcionadas por el Doclet Estándar y están sujetas a cambios sin previo aviso. Las opciones adicionales se utilizan con menos frecuencia o se consideran avanzadas.

--date fecha-y-hora
Especifica el valor que se utilizará para marcar con fecha las páginas generadas, en formato ISO 8601 [https://www.iso.org/iso-8601-date-and-time-format.html]. El valor especificado debe estar dentro de los 10 años de la fecha y hora actuales. Es un error especificar tanto -notimestamp como --date. Usar un valor específico significa que la documentación generada puede ser parte de una construcción reproducible [https://reproducible-builds.org/]. Si no se proporciona la opción, el valor predeterminado es la fecha y hora actuales. Por ejemplo:

javadoc --date 2022-02-01T17:41:59-08:00 miPaquete
--legal-notices (default|none|directorio)
Especifica la ubicación desde la cual copiar los archivos legales a la documentación generada. Si la opción no se especifica o se usa con el valor default, los archivos se copian desde la ubicación predeterminada. Si el argumento se usa con el valor none, no se copian archivos. Cualquier otro argumento se interpreta como un directorio desde el cual copiar los archivos legales.
--no-frames
Esta opción es un no-op y se conserva solo por compatibilidad hacia atrás.
-Xdoclint
Habilita comprobaciones recomendadas de problemas en comentarios de documentación.

Por defecto, la opción -Xdoclint está habilitada. Deshabilítala con la opción -Xdoclint:none.

Para más detalles, consulta DocLint.

-Xdoclint:bandera,bandera,...
Habilita o deshabilita comprobaciones específicas para diferentes tipos de problemas en los comentarios de documentación.

Cada bandera puede ser all, none, o [-]grupo donde grupo tiene uno de los siguientes valores: accessibility, html, missing, reference, syntax. Para más detalles sobre estos valores, consulta Grupos de DocLint.

Al especificar dos o más banderas, puedes usar una única opción -Xdoclint:..., listando todas las banderas deseadas, o puedes usar múltiples opciones dando una o más banderas en cada opción. Por ejemplo, usa cualquiera de los siguientes comandos para verificar problemas de HTML, sintaxis y accesibilidad en el archivo MyFile.java.


javadoc -Xdoclint:html -Xdoclint:syntax -Xdoclint:accessibility MyFile.java
javadoc -Xdoclint:html,syntax,accessibility MyFile.java

Los siguientes ejemplos ilustran cómo cambiar lo que DocLint informa:

•
-Xdoclint:none --- deshabilita todas las comprobaciones
•
-Xdoclint:grupo --- habilita las comprobaciones de grupo
•
-Xdoclint:all --- habilita todos los grupos de comprobaciones
•
-Xdoclint:all,-grupo --- habilita todas las comprobaciones excepto las del grupo

Para más detalles, consulta DocLint.

-Xdoclint/package:[-]paquetes
Habilita o deshabilita comprobaciones en paquetes específicos. paquetes es una lista de especificadores de paquetes separados por comas. Un especificador de paquete es el nombre calificado de un paquete o un prefijo de nombre de paquete seguido de *, que se expande a todos los subpaquetes del paquete dado. Antepón el especificador del paquete con - para deshabilitar las comprobaciones para los paquetes especificados.

Para más detalles, consulta DocLint.

-Xdocrootparent url
Reemplaza todos los elementos @docRoot seguidos por /.. en los comentarios de documentación con url.

DOCLINT

DocLint proporciona la capacidad de comprobar posibles problemas en los comentarios de documentación. Los problemas pueden informarse como advertencias o errores, dependiendo de su gravedad. Por ejemplo, un comentario faltante puede ser un mal estilo que merece una advertencia, pero un enlace a una declaración Java desconocida es más grave y merece un error. Los problemas se organizan en grupos, y se pueden usar opciones para habilitar o deshabilitar mensajes en uno o más grupos. Dentro del código fuente, los mensajes en uno o más grupos pueden ser suprimidos usando anotaciones @SuppressWarnings.

Cuando se invoca desde javadoc, por defecto DocLint comprueba todos los comentarios que se utilizan en la documentación generada. Por lo tanto, se basa en otras opciones de línea de comandos para determinar qué declaraciones y qué comentarios correspondientes se incluirán. Nota: esto puede significar que incluso los comentarios sobre algunos miembros privados de clases serializables también serán comprobados, si los miembros necesitan ser documentados en la página de Formas Serializadas generada.

En contraste, cuando DocLint se invoca desde javac, DocLint se basa únicamente en las diversas opciones -Xdoclint... para determinar qué comentarios de documentación comprobar.

NAME

javadoc-openjdk21 - javadoc documentation tool

SYNOPSIS

javac [options]
javadoc [options]

This document describes the javadoc documentation generator.

DESCRIPTION

The javadoc tool, also known as the API documentation generator, creates an HTML or other types of document from a set of Java source files. Javadoc is a tool that parses the documentation comments in your Java code and generates documentation in HTML format.

It is a utility built into javac and javadoc that checks the content of documentation comments, as found in source files. In contrast, downstream validation tools can be used to validate the output generated from those documentation comments by javadoc and the Standard Doclet.

The DocLint tool is part of the javadoc command. It checks the content of documentation comments, as found in source files. When you run javadoc, DocLint checks the documentation comments and issues warnings or errors for issues that it finds. You can control DocLint with the -Xdoclint option.

DocLint is not a full HTML compliance checker. The goal is to just report common errors in a convenient manner.

OPTIONS

This command-line option is the same as the -Xdoclint option.

DOCLINT

The -Xdoclint option enables DocLint checks. If no argument is specified, then all checks are enabled. The checks performed by DocLint are organized into groups. The warnings and errors in each group can be enabled or disabled with command-line options, or suppressed with @SuppressWarnings annotations.

The groups are as follows:

•
accessibility --- Checks for issues related to accessibility. For example, no alt attribute specified in an <img> element, or no caption or summary attributes specified in a <table> element.

Issues are reported as errors if a downstream validation tool might be expected to report an error in the files generated by javadoc.

For reference, see the Web Content Accessibility Guidelines [https://www.w3.org/WAI/standards-guidelines/wcag/].

•
html --- Detects common high-level HTML issues. For example, putting block elements inside inline elements, or not closing elements that require an end tag.

Issues are reported as errors if a downstream validation tool might be expected to report an error in the files generated by javadoc.

For reference, see the HTML Living Standard [https://html.spec.whatwg.org/multipage/].

•
missing --- Checks for missing documentation comments or tags. For example, a missing comment on a class declaration, or a missing @param or @return tag in the comment for a method declaration.

Issues related to missing items are typically reported as warnings because they are unlikely to be reported as errors by downstream validation tools that may be used to check the output generated by javadoc.

•
reference --- Checks for issues relating to the references to Java API elements from documentation comment tags. For example, the reference in @see or {@link ...} cannot be found, or a bad name is given for @param or @throws.

Issues are typically reported as errors because while the issue may not cause problems in the generated files, the author has likely made a mistake that will lead to incorrect or unexpected documentation.

•
syntax --- Checks for low-level syntactic issues in documentation comments. For example, unescaped angle brackets (< and >) and ampersands (&) and invalid documentation comment tags.

Issues are typically reported as errors because the issues may lead to incorrect or unexpected documentation.

Suppressing Messages

DocLint checks for and recognizes two strings that may be present in the arguments for an @SuppressWarnings annotation.

•
doclint
•
doclint:LIST

where LIST is a comma-separated list of one or more of accessibility, html, missing, syntax, reference.

The names in LIST are the same group names supported by the command-line -Xdoclint option for javac and javadoc. (This is the same convention honored by the javac -Xlint option and the corresponding names supported by @SuppressWarnings.)

The names in LIST can equivalently be specified in separate arguments of the annotation. For example, the following are equivalent:

•
@SuppressWarnings("doclint:accessibility,missing")
•
@SuppressWarnings("doclint:accessibility", "doclint:missing")

When DocLint detects an issue in a documentation comment, it checks for the presence of @SuppressWarnings on the associated declaration and on all lexically enclosing declarations. The issue will be ignored if any such annotation is found containing the simple string doclint or the longer form doclint:LIST where LIST contains the name of the group for the issue.

Note: as with other uses of @SuppressWarnings, using the annotation on a module or package declaration only affects that declaration; it does not affect the contents of the module or package in other source files.

All messages related to an issue are suppressed by the presence of an appropriate @SuppressWarnings annotation: this includes errors as well as warnings.

Note: It is only possible to suppress messages. If an annotation of @SuppressWarnings("doclint") is given on a top-level declaration, all DocLint messages for that declaration and any enclosed declarations will be suppressed; it is not possible to selectively re-enable messages for issues in enclosed declarations.

Comparison with downstream validation tools

DocLint is a utility built into javac and javadoc that checks the content of documentation comments, as found in source files. In contrast, downstream validation tools can be used to validate the output generated from those documentation comments by javadoc and the Standard Doclet.

Although there is some overlap in functionality, the two mechanisms are different and each has its own strengths and weaknesses.

•
Downstream validation tools can check the end result of any generated documentation, as it will be seen by the end user. This includes content from all sources, including documentation comments, the Standard Doclet itself, user-provided taglets, and content supplied via command-line options. Because such tools are analyzing complete HTML pages, they can do more complete checks than can DocLint. However, when a problem is found in the generated pages, it can be harder to track down exactly where in the build pipeline the problem needs to be fixed.
•
DocLint checks the content of documentation comments, in source files. This makes it very easy to identify the exact position of any issues that may be found. DocLint can also detect some semantic errors in documentation comments that downstream tools cannot detect, such as missing comments, using an @return tag in a method returning void, or an @param tag describing a non-existent parameter. But by its nature, DocLint cannot report on problems such as missing links, or errors in user-provided custom taglets, or problems in the Standard Doclet itself. It also cannot reliably detect errors in documentation comments at the boundaries between content in a documentation comment and content generated by a custom taglet.
