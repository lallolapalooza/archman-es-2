JAVA

El comando java soporta una amplia gama de opciones en las siguientes

categorías:
•
Opciones estándar para Java: Opciones garantizadas para ser soportadas por todas las implementaciones de la Máquina Virtual Java (JVM). Se usan para acciones comunes, como verificar la versión de la JRE, establecer la ruta de clases, habilitar la salida detallada,
etc.
•
Opciones extra para Java: Opciones de propósito general que son específicas de la Máquina Virtual Java HotSpot. No están garantizadas para ser soportadas por todas las implementaciones de la JVM y están sujetas a cambios. Estas opciones comienzan con -X
.

Las opciones avanzadas no se recomiendan para un uso casual. Son opciones de desarrollo para ajustar áreas específicas del funcionamiento de la Máquina Virtual Java HotSpot que a menudo tienen requisitos de sistema específicos y pueden requerir acceso privilegiado a parámetros de configuración del sistema. Se proporcionan varios ejemplos de ajuste de rendimiento en Ejemplos de Ajuste de Rendimiento. Estas opciones no están garantizadas para ser soportadas por todas las implementaciones de la JVM y están sujetas a cambios. Las opciones avanzadas comienzan con -XX

.
•
Opciones de tiempo de ejecución avanzadas para Java: Controlan el comportamiento en tiempo de ejecución de la VM Java
HotSpot.
•
Opciones de compilador JIT avanzadas para java: Controlan la compilación just-in-time (JIT) dinámica realizada por la VM Java
HotSpot.
•
Opciones de servicio avanzadas para Java: Permiten la recopilación de información del sistema y la realización de una depuración
extensa.
•
Opciones de recolección de basura avanzadas para Java: Controlan cóm

de basura (GC) por la Java HotSpot

Las opciones booleanas se usan para habilitar una función que está deshabilitada por defecto o para deshabilitar una función que está habilitada por defecto. Tales opciones no requieren un parámetro. Las opciones booleanas -XX se habilitan usando el signo más (-XX:+OptionName) y se deshabilitan usando el signo menos (-XX:-OptionNa

OPCIONES ESTÁNDAR PARA JAVA

Estas son las opciones más comúnmente utilizadas compatibles con todas las implementaciones de la JVM.

Nota: Para especificar un argumento para una opción larga, puede utilizar --nombre=valor o --nombre valor.

-agentlib:nombrelib[=opciones]
Carga la biblioteca agente nativa especificada. Después del nombre de la biblioteca, se puede utilizar una lista separada por comas de opciones específicas de la biblioteca. Si se especifica la opción -agentlib:foo, la JVM intenta cargar la biblioteca denominada foo utilizando las convenciones de nomenclatura y ubicaciones específicas de la plataforma:
•
Linux y otras plataformas tipo POSIX: La JVM intenta cargar la biblioteca denominada libfoo.so en la ubicación especificada por la variable del sistema LD_LIBRARY_PATH.
•
macOS: La JVM intenta cargar la biblioteca denominada libfoo.dylib en la ubicación especificada por la variable del sistema DYLD_LIBRARY_PATH.
•
Windows: La JVM intenta cargar la biblioteca denominada foo.dll en la ubicación especificada por la variable del sistema PATH.

El siguiente ejemplo muestra cómo cargar la biblioteca del Protocolo de Depuración de Hilo de Java (JDWP) y escuchar la conexión del socket en el puerto 8000, suspendiendo la JVM antes de que se cargue la clase principal:

-agentlib:jdwp=transport=dt_socket,server=y,address=8000

-agentpath:rutacompleta[=opciones]
Carga la biblioteca agente nativa especificada por la ruta absoluta. Esta opción es equivalente a -agentlib pero utiliza la ruta completa y el nombre del archivo de la biblioteca.
--class-path rutadeclases, -classpath rutadeclases, o -cp rutadeclases
Especifica una lista de directorios, archivos JAR y archivos ZIP para buscar archivos de clase.

En Windows, los puntos y coma (;) separan las entidades en esta lista; en otras plataformas es dos puntos (:).

Especificar rutadeclases anula cualquier configuración de la variable de entorno CLASSPATH. Si la opción de ruta de clases no se utiliza y rutadeclases no está configurada, la ruta de clases del usuario consta del directorio actual (.).

Como una conveniencia especial, un elemento de ruta de clases que contiene un nombre base de asterisco (*) se considera equivalente a especificar una lista de todos los archivos en el directorio con la extensión .jar o .JAR. Un programa Java no puede notar la diferencia entre las dos invocaciones. Por ejemplo, si el directorio mydir contiene a.jar y b.JAR, entonces el elemento de ruta de clases mydir/* se expande a A.jar:b.JAR, excepto que el orden de los archivos JAR no está especificado. Todos los archivos .jar en el directorio especificado, incluso los ocultos, se incluyen en la lista. Una entrada de ruta de clases que consiste en un asterisco (*) se expande a una lista de todos los archivos jar en el directorio actual. La variable de entorno CLASSPATH, cuando está definida, se expande de manera similar. Cualquier expansión de comodines de la ruta de clases que ocurre antes de que se inicie la VM de Java. Los programas Java nunca ven comodines que no se expanden, excepto consultando el entorno, como llamando a System.getenv("CLASSPATH").

--disable-@files
Se puede utilizar en cualquier lugar de la línea de comandos, incluso en un archivo de argumentos, para evitar una mayor expansión de @nombrearchivo. Esta opción detiene la expansión de archivos de argumentos con @ después de la opción.
--enable-preview
Permite que las clases dependan de las características de vista previa [https://docs.oracle.com/en/java/javase/12/language/index.html#JSLAN-GUID-5A82FE0E-0CA4-4F1F-B075-564874FE2823] de la versión.
--enable-native-access módulo[,módulo...]
El acceso nativo implica el acceso a código o datos fuera del tiempo de ejecución de Java. Esto es generalmente inseguro y, si se hace incorrectamente, podría bloquear la JVM o resultar en corrupción de memoria. El acceso nativo puede ocurrir como resultado de llamar a un método que es restringido [https://openjdk.org/jeps/454#Safety] o nativo. Esta opción permite que el código en los módulos especificados realice acceso nativo. El acceso nativo que ocurre en un módulo que no ha sido habilitado explícitamente se considera ilegal.

módulo puede ser un nombre de módulo, o ALL-UNNAMED para indicar código en la ruta de clases.

---illegal-native-access=parámetro
Esta opción especifica un modo sobre cómo se maneja el acceso nativo ilegal:

Nota: Esta opción se eliminará en una versión futura.

•
allow: Este modo permite el acceso nativo ilegal en todos los módulos, sin ninguna advertencia.
•
warn: Este modo es idéntico a allow excepto que se emite un mensaje de advertencia para el primer acceso nativo ilegal encontrado en un módulo. Este modo es el predeterminado para el JDK actual, pero cambiará en una versión futura.
•
deny: Este modo deshabilita el acceso nativo ilegal. Es decir, cualquier acceso nativo ilegal causa una IllegalCallerException. Este modo se convertirá en el predeterminado en una versión futura.

Para verificar que su aplicación está lista para una versión futura del JDK, ejecútela con --illegal-native-access=deny junto con las opciones necesarias de --enable-native-access.

--finalization=valor
Controla si la JVM realiza la finalización de objetos. Los valores válidos son "enabled" (habilitado) y "disabled" (deshabilitado). La finalización está habilitada por defecto, por lo que el valor "enabled" no hace nada. El valor "disabled" deshabilita la finalización, de modo que no se invocan finalizadores.
--module-path rutademódulos... o -p rutademódulos
Especifica dónde encontrar los módulos de la aplicación con una lista de elementos de ruta. Los elementos de una ruta de módulos pueden ser una ruta de archivo a un módulo o un directorio que contiene módulos. Cada módulo es un JAR modular o un directorio de módulo expandido.

En Windows, los puntos y coma (;) separan los elementos de ruta en esta lista; en otras plataformas es dos puntos (:).

--upgrade-module-path rutademódulos...
Especifica dónde encontrar los reemplazos de módulos de módulos actualizables en la imagen de tiempo de ejecución con una lista de elementos de ruta. Los elementos de una ruta de módulos pueden ser una ruta de archivo a un módulo o un directorio que contiene módulos. Cada módulo es un JAR modular o un directorio de módulo expandido.

En Windows, los puntos y coma (;) separan los elementos de ruta en esta lista; en otras plataformas es dos puntos (:).

--add-modules módulo[,módulo...]
Especifica los módulos raíz a resolver además del módulo inicial. módulo también puede ser ALL-DEFAULT, ALL-SYSTEM y ALL-MODULE-PATH.
--list-modules
Enumera los módulos observables y luego sale.
-d nombre_módulo o --describe-module nombre_módulo
Describe un módulo especificado y luego sale.
--dry-run
Crea la VM pero no ejecuta el método principal. Esta opción --dry-run puede ser útil para validar las opciones de la línea de comandos, como la configuración del sistema de módulos.
--validate-modules
Valida todos los módulos y sale. Esta opción es útil para encontrar conflictos y otros errores con los módulos en la ruta de módulos.
-D propiedad[=valor]
Establece una propiedad del sistema. Si valor se omite, el valor es una cadena vacía. El uso de -D es equivalente a usar la opción --system-property.

-XX:-CompactStrings
Deshabilita la función Compact Strings. Por defecto, esta opción está habilitada. Cuando esta opción está habilitada, las cadenas de Java que contienen solo caracteres de un solo byte se representan internamente y se almacenan como cadenas de un solo byte por carácter utilizando la codificación ISO-8859-1 / Latin-1. Esto reduce, en un 50%, la cantidad de espacio requerido para cadenas que contienen solo caracteres de un solo byte. Para las cadenas de Java que contienen al menos un carácter multibyte: se representan y almacenan como 2 bytes por carácter utilizando la codificación UTF-16. Deshabilitar la función Compact Strings fuerza el uso de la codificación UTF-16 como representación interna para todas las cadenas de Java.

Los casos en los que puede ser beneficioso deshabilitar Compact Strings incluyen los siguientes:

•
Cuando se sabe que una aplicación asignará predominantemente cadenas de caracteres multibyte.
•
En el caso inesperado en que se observe una regresión de rendimiento al migrar de Java SE 8 a Java SE 9 y un análisis muestre que Compact Strings introduce la regresión.

En ambos escenarios, deshabilitar Compact Strings tiene sentido.

-XX:RTMAbortRatio=relación_aborto
Especifica la relación de aborto de RTM como un porcentaje (%) de todas las transacciones RTM ejecutadas. Si el número de transacciones abortadas supera esta relación, el código compilado se desoptimiza. Esta relación se utiliza cuando la opción -XX:+UseRTMDeopt está habilitada. El valor predeterminado de esta opción es 50. Esto significa que el código compilado se desoptimiza si se abortan el 50% de todas las transacciones.

Especifica el número de veces que se reintentará el código de bloqueo RTM, cuando se aborte o esté ocupado, antes de recurrir al mecanismo de bloqueo normal. El valor predeterminado para esta opción es 5. La opción -XX:+UseRTMLocking debe estar habilitada.

Ajusta automáticamente el bloqueo RTM según la relación de aborto. Esta relación se especifica mediante la opción -XX:RTMAbortRatio. Si el número de transacciones abortadas supera la relación de aborto, el método que contiene el bloqueo se desoptimiza y se recompila con todos los bloqueos como bloqueos normales. Esta opción está deshabilitada por defecto. La opción -XX:+UseRTMLocking debe estar habilitada.
-XX:+UseRTMLocking
Genera código de bloqueo de Memoria Transaccional Restringida (RTM) para todos los bloqueos inflados, con el mecanismo de bloqueo normal como manejador de respaldo. Esta opción está deshabilitada por defecto. Las opciones relacionadas con RTM solo están disponibles en CPUs x86 que soportan las extensiones de sincronización transaccional (TSX).

RTM forma parte de TSX de Intel, que es una extensión del conjunto de instrucciones x86 y facilita la creación de aplicaciones multihilo. RTM introduce las nuevas instrucciones XBEGIN, XABORT, XEND y XTEST. Las instrucciones XBEGIN y XEND encierran un conjunto de instrucciones para ejecutar como una transacción. Si no se encuentra ningún conflicto al ejecutar la transacción, las modificaciones de memoria y registro se confirman juntas en la instrucción XEND. La instrucción XABORT se puede usar para abortar explícitamente una transacción y la instrucción XTEST comprueba si un conjunto de instrucciones se está ejecutando en una transacción.

Un bloqueo en una transacción se infla cuando otro hilo intenta acceder a la misma transacción, bloqueando así el hilo que originalmente no solicitó acceso a la transacción. RTM requiere que se especifique un conjunto de operaciones de respaldo en caso de que una transacción se aborte o falle. Un bloqueo RTM es un bloqueo que se ha delegado al sistema TSX.

RTM mejora el rendimiento para bloqueos altamente disputados con bajo conflicto en una región crítica (que es código al que no deben acceder más de un hilo simultáneamente). RTM también mejora el rendimiento de los bloqueos de grano grueso, que típicamente no funcionan bien en aplicaciones multihilo. (El bloqueo de grano grueso es la estrategia de mantener bloqueos durante largos períodos para minimizar la sobrecarga de tomar y liberar bloqueos, mientras que el bloqueo de grano fino es la estrategia de intentar lograr el máximo paralelismo bloqueando solo cuando es necesario y liberando lo antes posible). Además, para bloqueos ligeramente disputados que son utilizados por diferentes hilos, RTM puede reducir el intercambio de líneas de caché falsas, también conocido como "cache line ping-pong". Esto ocurre cuando varios hilos de diferentes procesadores acceden a diferentes recursos, pero los recursos comparten la misma línea de caché. Como resultado, los procesadores invalidan repetidamente las líneas de caché de otros procesadores, lo que los obliga a leer de la memoria principal en lugar de su caché.

El mecanismo de registro de nivel inferior es una característica del sistema de tiempo de ejecución de Java que se utiliza para registrar información de diagnóstico relacionada con la JVM. El nivel de registro permite controlar el nivel de detalle de los mensajes de registro. La configuración de -Xlog se puede especificar en la línea de comandos de la JVM. La siguiente es una sintaxis básica para la opción -Xlog:

-Xlog[=option][option...]

Donde option puede ser una de las siguientes:

-Xlog:all=info
Registra mensajes de todos los niveles en el nivel info y superiores, y los envía a stdout. La configuración predeterminada para todos los demás mensajes en el nivel warning permanece en vigor.
-Xlog:disable
Desactiva todos los registros, incluidos los avisos y errores.
-Xlog:stdout
Establece el destino de la salida de registro a stdout. Esto no cambia los niveles de registro ni las etiquetas.
-Xlog:stderr
Establece el destino de la salida de registro a stderr.
-Xlog:file=filename
Establece el destino de la salida de registro al archivo especificado por filename.
-Xlog:utctime
Utiliza la hora UTC en las marcas de tiempo de los mensajes de registro. De forma predeterminada, se utiliza la hora local.
-Xlog:uptime
Incluye el tiempo de actividad de la JVM en las marcas de tiempo de los mensajes de registro.
-Xlog:pid
Incluye el ID del proceso de la JVM en los mensajes de registro.
-Xlog:tid
Incluye el ID del hilo de la JVM en los mensajes de registro.
-Xlog:level
Incluye el nivel de registro en los mensajes de registro.
-Xlog:tags
Incluye las etiquetas de los mensajes de registro.
-Xlog:time,uptime,level,tags
Esto es equivalente a usar:

-Xlog:all=info:stdout:uptime,levels,tags

-Xlog:gc
Registra mensajes etiquetados con la etiqueta gc utilizando el nivel info en stdout. La configuración predeterminada para todos los demás mensajes en el nivel warning permanece en vigor.
-Xlog:gc,safepoint
Registra mensajes etiquetados con las etiquetas gc o safepoint, ambos utilizando el nivel info, en stdout, con decoraciones predeterminadas. Los mensajes etiquetados con ambas gc y safepoint no se registrarán.
-Xlog:gc+ref=debug
Registra mensajes etiquetados con ambas etiquetas gc y ref, utilizando el nivel debug en stdout, con decoraciones predeterminadas. Los mensajes etiquetados solo con una de las dos etiquetas no se registrarán.
-Xlog:gc=debug:file=gc.txt:none
Registra mensajes etiquetados con la etiqueta gc utilizando el nivel debug en un archivo llamado gc.txt sin decoraciones. La configuración predeterminada para todos los demás mensajes en el nivel warning sigue vigente.
-Xlog:gc=trace:file=gctrace.txt:uptimemillis,pid:filecount=5,filesize=1024
Registra mensajes etiquetados con la etiqueta gc utilizando el nivel trace en un archivo rotatorio con 5 archivos de 1 MB con el nombre base gctrace.txt y utiliza las decoraciones uptimemillis y pid.

La configuración predeterminada para todos los demás mensajes en el nivel warning sigue vigente.

-Xlog:gc::uptime,tid
Registra mensajes etiquetados con la etiqueta gc utilizando el nivel predeterminado 'info' en la salida predeterminada stdout y utiliza las decoraciones uptime y tid. La configuración predeterminada para todos los demás mensajes en el nivel warning sigue vigente.
-Xlog:gc*=info,safepoint*=off
Registra mensajes etiquetados con al menos gc utilizando el nivel info, pero desactiva el registro de mensajes etiquetados con safepoint. Los mensajes etiquetados con ambas gc y safepoint no se registrarán.
-Xlog:disable -Xlog:safepoint=trace:safepointtrace.txt
Desactiva todos los registros, incluidos los avisos y errores, y luego habilita los mensajes etiquetados con safepoint utilizando el nivel trace en el archivo safepointtrace.txt. La configuración predeterminada no se aplica, porque la línea de comandos comenzó con -Xlog:disable.

Ejemplos de uso complejos de -Xlog

Los siguientes describen algunos ejemplos complejos de uso de la opción -Xlog.

-Xlog:gc+class*=debug
Registra mensajes etiquetados con al menos las etiquetas gc y class utilizando el nivel debug en stdout. La configuración predeterminada para todos los demás mensajes en el nivel warning sigue vigente.
-Xlog:gc+meta*=trace,class*=off:file=gcmetatrace.txt
Registra mensajes etiquetados con al menos las etiquetas gc y meta utilizando el nivel trace en el archivo metatrace.txt, pero desactiva todos los mensajes etiquetados con class. Los mensajes etiquetados con gc, meta y class no se registrarán porque class* está configurado en off. La configuración predeterminada para todos los demás mensajes en el nivel warning está vigente, excepto para aquellos que incluyen class.
-Xlog:gc+meta=trace
Registra mensajes etiquetados exactamente con las etiquetas gc y meta utilizando el nivel trace en stdout. La configuración predeterminada para todos los demás mensajes en el nivel warning sigue vigente.
-Xlog:gc+class+heap*=debug,meta*=warning,threads*=off
Registra mensajes etiquetados con al menos las etiquetas gc, class y heap utilizando el nivel trace en stdout, pero solo registra mensajes etiquetados con meta con el nivel especificado. La configuración predeterminada para todos los demás mensajes en el nivel warning está vigente, excepto para aquellos que incluyen threads.

VALIDACIÓN DE LOS ARGUMENTOS DE LAS BANDERAS DE LA MÁQUINA VIRTUAL JAVA

Utiliza los valores proporcionados a todas las banderas de la línea de comandos de la Máquina Virtual Java (JVM) para su validación y, si el valor de entrada es inválido o está fuera de rango, se mostrará un mensaje de error apropiado.

PÁGINAS GRANDES

Utilizas páginas grandes, también conocidas como páginas enormes, como páginas de memoria que son significativamente más grandes que el tamaño de página de memoria estándar (que varía según el procesador y el sistema operativo). Las páginas grandes optimizan los búferes de traducción de tablas de páginas del procesador.

Un búfer de traducción de tablas de páginas (TLB) es una caché de traducción de páginas que contiene las traducciones de direcciones virtuales a físicas usadas más recientemente. Un TLB es un recurso escaso del sistema. Una falla de TLB puede ser costosa porque el procesador debe leer de la tabla de páginas jerárquica, lo que puede requerir múltiples accesos a memoria. Al usar un tamaño de página de memoria más grande, una sola entrada de TLB puede representar un rango de memoria más grande. Esto resulta en menos presión sobre un TLB, y las aplicaciones intensivas en memoria pueden tener un mejor rendimiento.

Sin embargo, el uso de páginas grandes puede afectar negativamente el rendimiento del sistema. Por ejemplo, cuando una gran cantidad de memoria es fijada por una aplicación, puede crear una escasez de memoria regular y causar paginación excesiva en otras aplicaciones y ralentizar todo el sistema. Además, un sistema que ha estado en funcionamiento durante mucho tiempo podría producir una fragmentación excesiva, lo que podría imposibilitar la reserva de suficiente memoria de página grande. Cuando esto sucede, el SO o la JVM vuelven a usar páginas regulares.

Linux y Windows admiten páginas grandes.

Se utilizan opciones de JVM incompatibles (por ejemplo, ciertas opciones de JVMTI).

Dado que el caché AOT es una característica de optimización, no hay garantía de que sea compatible con todas las opciones posibles de la JVM. Consulte **JEP 483** [https://openjdk.org/jeps/483], sección **Consistencia de entrenamiento y ejecuciones posteriores** para obtener una lista representativa de escenarios que pueden ser incompatibles con el caché AOT.

Estos escenarios suelen implicar la modificación arbitraria de clases con fines de diagnóstico y normalmente no son relevantes para entornos de producción.

Cuando el caché AOT no se puede cargar:

•
Si AOTMode era originalmente auto, la JVM continuará la ejecución sin utilizar el caché AOT. Este es el modo recomendado para entornos de producción, especialmente cuando es posible que no tenga control total de la línea de comandos (por ejemplo, el script de inicio de su aplicación puede permitir a los usuarios inyectar opciones en la línea de comandos). Esto permite que su aplicación funcione correctamente, aunque a veces puede que no se beneficie del caché AOT.
•
Si AOTMode es on, la JVM imprimirá un mensaje de error y saldrá inmediatamente. Este modo solo debe usarse como una ayuda de depuración de "fallo rápido" para verificar si sus opciones de línea de comandos son compatibles con el caché AOT. Una alternativa es ejecutar su aplicación con -XX:AOTMode=auto -Xlog:aot para ver si el caché AOT se puede usar o no.
-XX:+AOTClassLinking
Si esta opción está habilitada, la JVM realizará optimizaciones más avanzadas (como la resolución anticipada de instrucciones invokedynamic) al crear el caché AOT. Como resultado, la aplicación verá mejoras adicionales en el rendimiento de inicio y calentamiento. Sin embargo, un caché AOT creado con esta opción no se puede utilizar cuando se especifican ciertos parámetros de línea de comandos en la fase de Producción. Consulte **JEP 483** [https://openjdk.org/jeps/483] para una discusión detallada de -XX:+AOTClassLinking y sus restricciones.

Cuando se utiliza -XX:AOTMode en la línea de comandos, AOTClassLinking se habilita automáticamente. Para deshabilitarlo, debe pasar explícitamente la opción -XX:-AOTClassLinking.

Cuando -XX:AOTMode no se utiliza en la línea de comandos, AOTClassLinking está deshabilitado por defecto para proporcionar compatibilidad total con opciones CDS tradicionales como `-Xshare:dump.

La primera aparición de la secuencia especial %p en *configfile* y cachefile se reemplaza con el ID del proceso de la JVM lanzada en la línea de comandos, y de manera similar la primera aparición de %t se reemplaza por la marca de tiempo de inicio de la JVM. (Después del reemplazo, no debe haber más ocurrencias de %p o %t, para evitar problemas con subprocesos.) Por ejemplo:

java -XX:AOTConfiguration=foo%p.aotconfig -XX:AOTCacheOutput=foo%p.aot -cp foo.jar Foo

creará dos archivos: foopid123.aotconfig y foopid123.aot, donde 123 es el ID del proceso de la JVM que ha ejecutado la aplicación Foo.

EJEMPLOS DE OPTIMIZACIÓN DE RENDIMIENTO

Puede utilizar las opciones avanzadas de tiempo de ejecución de Java para optimizar el rendimiento de sus aplicaciones.

Optimización para un Mayor Rendimiento

Utilice los siguientes comandos y opciones avanzadas para lograr un rendimiento de mayor rendimiento para su aplicación:

java -server -XX:+UseParallelGC -XX:+UseLargePages -Xmn10g -Xms26g -Xmx26g

Optimización para un Menor Tiempo de Respuesta

Utilice los siguientes comandos y opciones avanzadas para lograr tiempos de respuesta más bajos para su aplicación:

java -XX:+UseG1GC -XX:MaxGCPauseMillis=100

Mantener Pequeño el Heap de Java y Reducir la Huella Dinámica de las Aplicaciones Embebidas

Utilice las siguientes opciones avanzadas de tiempo de ejecución para mantener pequeño el heap de Java y reducir la huella dinámica de las aplicaciones embebidas:

-XX:MaxHeapFreeRatio=10 -XX:MinHeapFreeRatio=5

Nota: Los valores predeterminados para estas dos opciones son 70% y 40% respectivamente. Dado que pueden producirse sacrificios en el rendimiento al utilizar estas configuraciones pequeñas, debe optimizar para una huella pequeña reduciendo estas configuraciones tanto como sea posible sin introducir una degradación inaceptable del rendimiento.
