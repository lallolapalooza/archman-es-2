NOMBRE

jj-fix - Actualiza archivos con correcciones de formato u otros cambios

SINOPSIS

jj fix [-s|--source] [--include-unchanged-files] [-R|--repository] [--ignore-working-copy] [--ignore-immutable] [--at-operation] [--debug] [--color] [--quiet] [--no-pager] [--config] [--config-file] [-h|--help] [ARCHIVOS]

DESCRIPCIÓN

Actualiza archivos con correcciones de formato u otros cambios

El caso de uso principal de este comando es aplicar los resultados de herramientas automáticas de formato de código a revisiones que aún no estén formateadas correctamente. También se puede usar para modificar archivos con otras herramientas como `sed` o `sort`.

### Cómo funciona

Los archivos modificados en las revisiones dadas se actualizarán con cualquier corrección determinada al pasar el contenido de sus archivos a través de las herramientas externas que el usuario haya configurado para esos archivos. Los descendientes también se actualizarán pasando sus versiones de los mismos archivos a través de las mismas herramientas, lo que garantizará que las correcciones no se pierdan. Esto nunca resultará en nuevos conflictos. Los archivos con conflictos existentes se actualizarán en todos los lados del conflicto, lo que puede aumentar o disminuir el número de marcadores de conflicto.

### Configuración

Consulta `jj help -k config` capítulo `Formato de código y otras transformaciones de contenido de archivos` para entender cómo configurar sus herramientas.

### Ejemplo de ejecución

Consideremos la siguiente configuración establecida. Tenemos dos formateadores de código (`clang-format` y `black`), que se aplican a tres extensiones de archivo diferentes (`.cc`, `.h` y `.py`):

```toml [fix.tools.clang-format] command = ["/usr/bin/clang-format", "--assume-filename=$path"] patterns = ["glob:'**/*.cc'",
"glob:'**/*.h'"]

[fix.tools.black] command = ["/usr/bin/black", "-", "--stdin-filename=$path"] patterns = ["glob:'**/*.py'"] ```

Ahora, veamos qué sucedería con el siguiente historial al ejecutar `jj fix`.

```text C (mutable) | Modifica archivo: foo.py | B @ (copia de trabajo - mutable) | Modifica archivo: README.md | A (mutable) | Modifica archivos: src/bar.cc y src/bar.h | X (inmutable) ```

Por defecto, `jj fix` modificará las revisiones que coincidan con el revset `reachable(@, mutable())` (ver `jj help -k revsets`), que corresponde a las revisiones `A`, `B` y `C` aquí.

Las siguientes operaciones ocurrirán entonces:

- Para la revisión `A`, el contenido de esta revisión para los archivos `src/bar.cc` y
`src/bar.h` se proporcionará a `clang-format` y el resultado se usará para
recrear la revisión `A`, que llamaremos `A'`. Todos los demás archivos no
se tocan. - Para la revisión `B`, sucede lo mismo para los archivos `src/bar.cc` y
`src/bar.h`. El contenido de la revisión `B` pasará por `clang-format`. El
archivo `README.md`, como cualquier otro archivo, no se toca ya que ningún
patrón coincide con él. Obtenemos la revisión `B'`. - Para la revisión `C`, `src/bar.cc` y `src/bar.h` pasan por `clang-format`
y el archivo `foo.py` se corrige usando `black`. Cualquier otro archivo no
se toca. Obtenemos la revisión `C'`.

```text C (mutable) /-> C' | src/bar.cc -> clang-format -| | | src/bar.h --> clang-format -| | | foo.py -----> black --------| | | * --------------------------/ | | | B @ (copia de trabajo - mutable) /-> B' @ | src/bar.cc -> clang-format -| | | src/bar.h --> clang-format -| | | * --------------------------| | | | A (mutable) /-> A' | src/bar.cc -> clang-format -| | | src/bar.h --> clang-format -| | | * --------------------------/ | | | X (inmutable) X ```

Las revisiones ahora están todas formateadas correctamente según la configuración.

OPCIONES

-s, --source <REVSETS>
Corrige archivos en la(s) revisión(es) especificada(s) y sus descendientes. Si no se especifican revisiones, esto toma por defecto la configuración `revsets.fix`, o `reachable(@, mutable())` si no está establecida
--include-unchanged-files
Corrige archivos no modificados además de los modificados. Si no se especifican rutas, se corregirán todos los archivos del repositorio
-h, --help
Imprime la ayuda (ver un resumen con '-h')
[ARCHIVOS]
Corrige solo estas rutas

OPCIONES GENERALES

-R, --repository <REPOSITORIO>
Ruta al repositorio sobre el que operar

Por defecto, Jujutsu busca el directorio .jj/ más cercano en un ancestro del directorio de trabajo actual.

--ignore-working-copy
No tomar una instantánea de la copia de trabajo, y no actualizarla

Por defecto, Jujutsu toma una instantánea de la copia de trabajo al inicio de cada comando. La copia de trabajo también se actualiza al final del comando, si el comando modificó el commit de la copia de trabajo (`@`). Si desea evitar tomar una instantánea de la copia de trabajo y ver en su lugar un commit de copia de trabajo posiblemente obsoleto, puede usar `--ignore-working-copy`. Esto puede ser útil, por ejemplo, en una línea de comandos, especialmente si tiene otro proceso que hace commit de la copia de trabajo.

Cargar el repositorio en una operación específica con `--at-operation` implica `--ignore-working-copy`.

--ignore-immutable
Permitir reescribir commits inmutables

Por defecto, Jujutsu evita reescribir commits en el conjunto configurado de commits inmutables. Esta opción deshabilita esa verificación y le permite reescribir cualquier commit excepto el commit raíz.

Esta opción solo afecta la verificación. No afecta al revset `immutable_heads()` ni a la palabra clave de plantilla `immutable`.

--at-operation <AT_OPERATION>
Operación en la que cargar el repositorio

Operación en la que cargar el repositorio. Por defecto, Jujutsu carga el repositorio en la operación más reciente, o en la fusión de las operaciones divergentes si las hay.

Puede usar `--at-op=<ID de operación>` para ver cómo era el repositorio en una operación anterior. Por ejemplo, `jj --at-op=<ID de operación> st` le mostrará lo que `jj st` habría mostrado cuando la operación dada acababa de finalizar. `--at-op=@` es prácticamente lo mismo que el valor predeterminado, excepto que las operaciones divergentes nunca se fusionarán.

Use `jj op log` para encontrar el ID de operación que desea. Cualquier prefijo no ambiguo del ID de operación es suficiente.

Al cargar el repositorio en una operación anterior, se ignorará la copia de trabajo, como si se hubiera especificado `--ignore-working-copy`.

Es posible ejecutar comandos mutantes al cargar el repositorio en una operación anterior. Hacerlo es equivalente a haber ejecutado comandos concurrentes que comienzan en la operación anterior. Rara vez hay una razón para hacerlo, pero es posible.

--debug
Habilita el registro de depuración
--color <WHEN>
Cuándo colorear la salida

[posibles valores: always, never, debug, auto]

--quiet
Silenciar la salida no principal del comando

Por ejemplo, `jj file list` seguirá listando archivos, pero no le dirá si la copia de trabajo se ha tomado una instantánea o si los descendientes se han rebaseado.

Las advertencias y los errores seguirán imprimiéndose.

--no-pager
Deshabilita el paginador
--config <NAME=VALUE>
Opciones de configuración adicionales (se pueden repetir)
