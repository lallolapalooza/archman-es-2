Paquete: wimlib

WIMAPPLY(1) Comandos de usuario WIMAPPLY(1)

NOMBRE

wimapply - Aplicar una imagen WIM

SINOPSIS

wimapply ARCHIVO.WIM [IMAGEN] DESTINO [OPCION...]

DESCRIPCIÓN

wimapply, o equivalentemente wimlib-imagex apply, extrae ( "aplica") una imagen, o todas las imágenes, del archivo de Windows Imaging (WIM) ARCHIVO.WIM.

IMAGEN especifica la imagen en ARCHIVO.WIM a extraer. Puede ser el índice basado en 1 de una imagen, el nombre de una imagen, o la palabra clave "all" para especificar todas las imágenes. Puede ser omitido si ARCHIVO.WIM contiene solo una imagen. Puede usar wiminfo(1) para listar las imágenes contenidas en ARCHIVO.WIM.

DESTINO especifica dónde extraer la(s) imagen(es). Si DESTINO es un directorio, entonces la(s) imagen(es) se extraerán en ese directorio según EXTRACCIÓN DE DIRECTORIO (UNIX) o EXTRACCIÓN DE DIRECTORIO (WINDOWS). Si DESTINO no existe, primero se creará un directorio allí. Alternativamente, si DESTINO especifica un dispositivo de bloques UNIX, entonces la imagen se extraerá en él como se describe en EXTRACCIÓN DE VOLUMEN NTFS (UNIX).

Tenga en cuenta que wimapply está diseñado para extraer, o "aplicar", imágenes WIM completas. Si en su lugar desea extraer solo archivos o directorios específicos de una imagen WIM, use en su lugar wimextract(1).

Si IMAGEN es "all", entonces todas las imágenes en ARCHIVO.WIM se extraerán en subdirectorios de DESTINO con nombres basados en las imágenes, recurriendo al índice de imagen cuando una imagen no tiene nombre o tiene un nombre inusual. Esto aún no es compatible en el modo EXTRACCIÓN DE VOLUMEN NTFS (UNIX).

Si ARCHIVO.WIM es "-", entonces el WIM se lee de la entrada estándar en lugar del disco. Vea WIMS TRANSMISIBLES POR TUBO para más información.

EXTRACCIÓN DE DIRECTORIO (UNIX)

En sistemas tipo UNIX, una imagen WIM puede extraerse en un directorio. Este modo tiene la limitación de que los metadatos NTFS o específicos de Windows no se extraerán. Aunque algunos conceptos como enlaces duros, enlaces simbólicos, marcas de tiempo de último acceso y marcas de tiempo de última modificación se traducirán a sus equivalentes UNIX, otros metadatos se perderán (con advertencias). Notablemente, los siguientes tipos de metadatos *no* se extraerán en este modo:

•
Atributos de archivo de Windows
•
Descriptores de seguridad de Windows (ej. propietarios de archivos y DACLs)
•
Marcas de tiempo de creación de archivos
•
Puntos de reanálisis distintos de enlaces simbólicos y puntos de unión
•
Flujos de datos con nombre
•
Nombres cortos de archivo (también conocidos como nombres 8.3 o nombres DOS).
•
IDs de objeto

Estas mismas limitaciones se aplican a wimextract. Como tal, este modo es más útil en situaciones donde los metadatos NTFS o específicos de Windows no son importantes, por ejemplo, al querer extraer archivos específicos, o al realizar archivado de archivos solo en sistemas tipo UNIX, posiblemente en combinación con --unix-data. Cuando los metadatos específicos de Windows son importantes, entonces se debe usar el modo EXTRACCIÓN DE VOLUMEN NTFS (UNIX), o la versión de Windows de wimlib (ver EXTRACCIÓN DE DIRECTORIO (WINDOWS)).

EXTRACCIÓN DE VOLUMEN NTFS (UNIX)

En sistemas tipo UNIX, DESTINO también puede especificarse como un dispositivo de bloques (ej. /dev/sda3) que contiene un volumen NTFS sin montar. En este modo, wimapply utiliza libntfs-3g para aplicar la imagen WIM especificada al directorio raíz del volumen NTFS. El volumen de destino debe estar vacío, por ejemplo, recién creado por mkntfs(8). En este modo, se extraerán datos y metadatos NTFS y específicos de Windows, incluyendo lo siguiente:

•
Todos los flujos de datos de todos los archivos, excepto los archivos cifrados, incluido el flujo de datos sin nombre, así como todos los flujos de datos con nombre.
•
Puntos de reanálisis, incluidos enlaces simbólicos, puntos de unión y otros puntos de reanálisis.
•
Marcas de tiempo de creación, acceso y modificación de archivos y directorios, utilizando la resolución nativa de NTFS de 100 nanosegundos.
•
Descriptores de seguridad de Windows, incluidos todos los componentes (propietario, grupo, DACL y SACL).
•
Atributos de archivo de Windows
•
Todos los nombres de todos los archivos, incluidos los nombres en el espacio de nombres Win32, el espacio de nombres DOS, el espacio de nombres Win32+DOS y el espacio de nombres POSIX. Esto incluye enlaces duros.
•
IDs de objeto.

Sin embargo, los archivos cifrados no se extraerán.

La restauración de atributos extendidos (EAs) tampoco es compatible en este modo todavía.

A pesar de ello, dado que se restaura casi toda la información de la imagen WIM en este modo, es posible (y totalmente compatible) restaurar una imagen de una instalación real de Windows utilizando wimapply en un sistema tipo UNIX como alternativa a usar wimapply o DISM en Windows. En la sección EJEMPLOS a continuación, hay un ejemplo de aplicación de una imagen desde un archivo "install.wim" tal como se puede encontrar en el medio de instalación de Windows.

Tenga en cuenta que para arrancar Windows (Vista o posterior) desde una imagen "install.wim" aplicada, también necesita marcar la partición como "arrancable" y configurar varios archivos de arranque, como \BOOTMGR y \BOOT\BCD. La última tarea se realiza más fácilmente ejecutando bcdboot.exe desde un sistema Windows en vivo como Windows PE, pero hay otras opciones disponibles.

Finalmente, tenga en cuenta que este modo utiliza libntfs-3g directamente, sin pasar por el controlador ntfs-3g(8). Por lo tanto, no hay soporte especial para aplicar una imagen WIM a un directorio en el que se ha montado un sistema de archivos NTFS utilizando ntfs-3g(8); debe desmontarlo primero. Tampoco hay soporte para aplicar una imagen WIM a algún subdirectorio del volumen NTFS; solo puede aplicarla al directorio raíz.

EXTRACCIÓN DE DIRECTORIO (WINDOWS)

En Windows, wimapply (y wimextract) admiten de forma nativa metadatos NTFS y específicos de Windows. Para obtener los mejores resultados, el directorio de destino debe estar ubicado en un volumen NTFS y el programa debe ejecutarse con privilegios de Administrador; sin embargo, también se admiten sistemas de archivos no NTFS y la ejecución sin privilegios de Administrador, sujetos a limitaciones.

En Windows, wimapply intenta extraer la mayor cantidad de datos y metadatos posible, incluyendo:

•
Todos los flujos de datos de todos los archivos. Esto incluye el contenido de archivo predeterminado, así como flujos de datos con nombre si son soportados por el volumen de destino.
•
Puntos de reanálisis, incluidos enlaces simbólicos, puntos de unión y otros puntos de reanálisis, si son soportados por el volumen de destino. La restauración de enlaces simbólicos requiere privilegios de Administrador. Vea también --rpfix y --norpfix para más detalles sobre cómo se extraen los enlaces simbólicos y puntos de unión absolutos.
•
Marcas de tiempo de creación y modificación de archivos y directorios, a la mayor resolución soportada por el volumen de destino.
•
Descriptores de seguridad, si son soportados por el sistema de archivos y no se especifica --no-acls. Tenga en cuenta que esto, en general, requiere privilegios de Administrador, y puede tener un éxito parcial si el programa se ejecuta sin privilegios de Administrador (ver --strict-acls).
•
Atributos de archivo, incluidos ocultos, comprimidos, cifrados, dispersos, etc., cuando son soportados por el sistema de archivos.
•
Nombres cortos de archivo (también conocidos como nombres 8.3 o nombres DOS).
•
Enlaces duros, si son soportados por el sistema de archivos de destino.
•
IDs de objeto, si son soportados por el sistema de archivos de destino.
•
Atributos extendidos (EAs), si son soportados por el sistema de archivos.

Notas adicionales sobre la extracción de archivos en Windows:

•
wimapply emitirá advertencias si no puede extraer los metadatos y datos exactos de la imagen WIM debido a limitaciones del sistema de archivos de destino.
•
Dado que los archivos cifrados (con FILE_ATTRIBUTE_ENCRYPTED) no se almacenan en texto plano en la imagen WIM, wimapply no puede restaurar archivos cifrados

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

PROBLEMAS

•
Los archivos encriptados no se extraerán si el sistema de archivos de destino no admite la encriptación. Por lo tanto, en dichos sistemas de archivos, los archivos encriptados no se extraerán. Además, incluso si los archivos encriptados se restauran en un sistema de archivos que admite la encriptación, solo serán descifrables si la clave de descifrado está disponible.
•
Los archivos con nombres que no se pueden representar en Windows no se extraerán por defecto; consulta --include-invalid-names.
•
Los archivos con rutas completas de más de 260 caracteres (la llamada MAX_PATH) se extraerán, pero ten en cuenta que dichos archivos serán inaccesibles para la mayoría del software de Windows y es posible que no se puedan eliminar fácilmente.
•
En Windows, a menos que se especifique la opción --no-acls, wimlib intentará restaurar los descriptores de seguridad de los archivos tal como se proporcionan en la imagen WIM. Ten en cuenta que las instalaciones típicas de Windows contienen archivos cuyos descriptores de seguridad no permiten al Administrador eliminarlos. Por lo tanto, dichos archivos no podrán eliminarse, o en algunos casos ni siquiera leerse, después de la extracción, a menos que se procesen con un programa especializado que sepa cómo adquirir los privilegios SE_RESTORE_NAME y/o SE_BACKUP_NAME que permiten anular las listas de control de acceso. Esto no es un error en wimlib, que funciona según lo diseñado para restaurar correctamente los datos que se archivaron, sino un problema con los derechos de acceso que Windows utiliza en ciertos archivos. Pero si solo quieres los datos del archivo y no te importan los descriptores de seguridad, usa --no-acls para omitir la restauración de todos los descriptores de seguridad.
•
Una advertencia similar a la anterior se aplica a los atributos de archivo como Solo lectura, Oculto y Sistema. Por diseño, en Windows wimlib restaurará dichos atributos de archivo; por lo tanto, los archivos extraídos pueden tener esos atributos. Si esto no es lo que deseas, usa la opción --no-attributes.

WIMS DIVIDIDOS

Puedes usar wimapply para aplicar imágenes de un WIM dividido, o wimextract para extraer archivos de un WIM dividido. El argumento WIMFILE debe especificar la primera parte del WIM dividido, mientras que las partes adicionales del WIM dividido deben especificarse en una o más opciones --ref="GLOB". Dado que el globbing está integrado en la opción --ref, normalmente solo es necesaria una opción --ref. Por ejemplo, los nombres de las partes del WIM dividido suelen ser algo como:

mywim.swm
mywim2.swm
mywim3.swm
mywim4.swm
mywim5.swm

Para aplicar la primera imagen de este WIM dividido al directorio "dir", ejecuta:

wimapply mywim.swm 1 dir --ref="mywim*.swm"

WIMS TRANSFERIBLES

wimapply también admite la aplicación de un WIM desde un archivo no buscable, como una tubería, siempre que el WIM se haya capturado en el formato transferible específico de wimlib usando --pipable (consulta wimcapture(1)). Para usar la entrada estándar como WIM, especifica "-" como WIMFILE. Un uso posible de esta característica es aplicar una imagen WIM que se está transmitiendo desde la red. Por ejemplo, para aplicar la primera imagen de un archivo WIM disponible en un servidor HTTP a un volumen NTFS en /dev/sda1, ejecuta algo como:

wget -O - https://myserver/mywim.wim | wimapply - 1 /dev/sda1

Los WIM transferibles también se pueden dividir en varias partes, al igual que los WIM normales. Para aplicar un WIM transferible dividido desde una tubería, las partes deben concatenarse y enviarse todas a la tubería. La primera parte debe enviarse primero, pero las partes restantes pueden enviarse en cualquier orden.

OPCIONES

--check
Antes de aplicar la imagen, verifica la integridad de WIMFILE si tiene información de integridad adicional.
--ref="GLOB"
Glob de archivos de WIMs adicionales o partes de WIM divididos para referenciar recursos. Consulta SPLIT_WIMS. Esta opción se puede especificar varias veces. Nota: GLOB aparece entre comillas porque es interpretado por wimapply y puede necesitar ser citado para protegerlo de la expansión del shell.
--rpfix, --norpfix
Establece si se deben corregir los objetivos de los enlaces simbólicos absolutos (puntos de reanálisis en terminología de Windows) o no. Cuando está habilitado (--rpfix), se asume que los enlaces simbólicos absolutos extraídos que están marcados en la imagen WIM como fijos tienen objetivos absolutos relativos a la raíz de la imagen, y por lo tanto wimapply antepone la ruta absoluta del directorio de extracción a sus objetivos. La intención es que puedas aplicar una imagen que contenga enlaces simbólicos absolutos y que sigan siendo válidos después de haberla aplicado en cualquier ubicación.
El comportamiento por defecto es --rpfix si alguna de las imágenes en WIMFILE ha sido capturada con correcciones de puntos de reanálisis realizadas. De lo contrario, es --norpfix.
Las correcciones de puntos de reanálisis nunca se realizan en el modo de extracción de volúmenes NTFS en sistemas tipo UNIX.
--unix-data
(Solo sistemas tipo UNIX) Restaura metadatos específicos de UNIX y archivos especiales que fueron capturados por wimcapture con la opción --unix-data. Esto incluye: permisos de archivos UNIX estándar (propietario, grupo y modo); nodos de dispositivo, tuberías con nombre y sockets; y atributos extendidos (solo Linux).
--no-acls
No restaurar descriptores de seguridad en archivos y directorios extraídos.
--strict-acls
Fallar inmediatamente si el descriptor de seguridad completo de cualquier archivo o directorio no se puede establecer exactamente como se especifica en el archivo WIM. Si esta opción no se especifica, cuando wimapply en Windows no tiene permiso para establecer un descriptor de seguridad en un archivo extraído, recurre a establecerlo solo parcialmente (por ejemplo, con la SACL omitida), y en el peor de los casos lo omite por completo. Sin embargo, esto solo debería ser un problema cuando se ejecuta wimapply sin derechos de Administrador. Además, en sistemas tipo UNIX, esta bandera también se puede combinar con --unix-data para causar que wimapply emita un error si los permisos UNIX no pueden aplicarse a un archivo extraído.
--no-attributes
No restaurar atributos de archivo de Windows como solo lectura, oculto, etc.
--include-invalid-names
Extraer archivos y directorios con nombres inválidos reemplazando caracteres y agregando un sufijo en lugar de ignorarlos. Exactamente lo que se considera un nombre "inválido" depende de la plataforma.
En sistemas compatibles con POSIX, los nombres de archivo distinguen entre mayúsculas y minúsculas y pueden contener cualquier byte excepto '\0' y '/', por lo que en un sistema compatible con POSIX esta opción solo tendrá efecto en el improbable caso de que la imagen WIM, por alguna razón, tenga un nombre de archivo que contenga uno de estos caracteres.
En Windows, los nombres de archivo no distinguen entre mayúsculas y minúsculas (*), no pueden incluir caracteres de control y no pueden incluir los caracteres '/', '\0', '\', ':', '*', '?', '"', '<', '>' o '|'. Normalmente, los archivos en las imágenes WIM también deberían cumplir estas condiciones. Sin embargo, no está garantizado, y en particular una imagen WIM capturada con wimcapture en un sistema compatible con POSIX podría contener dichos archivos. Por defecto, se ignorarán los nombres inválidos, y si hay múltiples nombres que difieren solo en mayúsculas y minúsculas, se elegirá uno para extraer de forma arbitraria; sin embargo, con --include-invalid-names, todos los nombres se sanitizarán y extraerán de alguna forma.
(*) A menos que la configuración ObCaseInsensitive se haya establecido en 0 en el registro de Windows, en cuyo caso cierto software, incluida la versión de Windows de wimapply, respetará los nombres de archivo sensibles a mayúsculas y minúsculas en NTFS y otros sistemas de archivos compatibles.
--wimboot
Solo Windows: En lugar de extraer los archivos mismos, extrae "archivos puntero" de vuelta al archivo o archivos WIM. Esto puede resultar en ahorros de espacio significativos. Sin embargo, tiene varios costos potenciales, como no poder eliminar los archivos WIM y posiblemente tener un acceso más lento a los archivos. Consulta la documentación de Microsoft sobre "WIMBoot" para obtener más información.
Si existe, se leerá la sección [PrepopulateList] del archivo \Windows\System32\WimBootCompress.ini en la imagen WIM. Los archivos que coincidan con cualquiera de estos patrones se extraerán normalmente, no como archivos "puntero" de WIMBoot. Esto es útil para ciertos archivos que Windows necesita leer al principio del proceso de arranque.
Esta opción solo funciona cuando el programa se ejecuta como Administrador y el volumen de destino es NTFS u otro sistema de archivos que admite puntos de reanálisis.
Además, esta opción funciona mejor cuando se ejecuta en Windows 8.1 Update 1 o posterior, ya que esa es la primera versión de Windows que contiene el controlador de filtro de sistema de archivos superpuesto de Windows ("WOF"). Si se detecta el controlador WOF, wimlib creará los archivos "puntero" de WIMBoot utilizando ioctls documentados proporcionados por WOF.
De lo contrario, si no se detecta el controlador WOF, wimlib creará los puntos de reanálisis y editará manualmente el archivo "\System Volume Information\WimOverlay.dat" en el volumen de destino. Esto es potencialmente propenso a problemas, ya que aunque el código funciona en ciertos casos probados, ninguno de estos formatos de datos está realmente documentado por Microsoft. Antes de sobrescribir este archivo, wimlib guardará la versión anterior en "\System Volume Information\WimOverlay.wimlib_backup", que potencialmente podrías restaurar si lo necesitaras.
De hecho, aún puedes realizar una extracción --wimboot incluso si la imagen WIM no está marcada como "compatible con WIMBoot". Esta opción hace que los archivos extraídos se establezcan como "respaldados externamente" por el archivo WIM. El controlador de Microsoft que implementa esta funcionalidad de "respaldo externo" aparentemente no se preocupa de si las imágenes en el WIM están realmente marcadas como compatibles con WIMBoot. Por lo tanto, la etiqueta "compatible con WIMBoot" (<WIMBOOT> en los datos XML) parece ser solo un marcador de intención. Además, el controlador de Microsoft puede respaldar externamente archivos de WIM que usan fragmentos XPRESS de tamaño 8192

SYNOPSIS

wimapply [OPTIONS] WIMFILE [IMAGENUM] DEST

DESCRIPTION

Apply a WIM image to a directory or partition. The WIM image is specified by WIMFILE. IMAGENUM specifies which image in the WIM to apply; if omitted, the first image is used. DEST specifies the destination directory or partition where the WIM image is to be applied.

The DEST parameter can be a directory path (e.g. "/mnt/windows" or "C:\Windows") or a block device representing a partition (e.g. "/dev/sda2" or "\\.\PhysicalDrive0p2"). When DEST is a block device, it is assumed to be formatted with the NTFS filesystem. The contents of the partition are completely replaced by the WIM image.

When DEST is a directory, it must exist and be empty. The WIM image is extracted into this directory.

DIRECTORY EXTRACTION (UNIX)

If DEST is a directory, it must already exist and should be empty. If it is not empty, wimapply will refuse to proceed. You can create it with mkdir.

NTFS VOLUME EXTRACTION (UNIX)

If DEST is a block device (e.g. "/dev/sda2"), it is assumed that the partition is formatted with NTFS. The existing contents of the partition will be completely destroyed. You might need to create an NTFS filesystem on the partition first using a tool like mkntfs(8).

DIRECTORY EXTRACTION (WINDOWS)

If DEST is a directory, it must already exist and should be empty. If it is not empty, wimapply will refuse to proceed. You can create it using mkdir.

SPLIT WIMS

If WIMFILE is the first part of a split WIM archive (i.e., it has a name like name.swm), then wimapply will automatically look for and apply all subsequent parts of the split WIM archive (name2.swm, name3.swm, etc.) in the same directory.

PIPABLE WIMS

The WIMFILE argument can be specified as - (hyphen) to indicate that the WIM data should be read from standard input. This allows WIM files to be created on-the-fly, for example using a pipe.

Example:

cat win.wim | wimapply - 1 /mnt/destination

OPTIONS

--check
Verify the integrity table of the WIM archive before extracting. This is only useful if the WIM archive contains an integrity table. This option implies --verify.
--confirm
Prompt for confirmation before overwriting any files at the destination. This is only useful when extracting to a directory that is not empty, which is otherwise disallowed. (However, this option is not yet implemented.)
--force
Do not prompt before overwriting files at the destination. This option is only useful when extracting to a directory that is not empty, which is otherwise disallowed. (However, this option is not yet implemented.)
--wimboot
Apply the WIM image in WimBoot mode. This is a special mode intended for use on devices with limited space, such as Windows tablets. In WimBoot mode, files are not directly extracted. Instead, a small stub file is created for each file, which is then used to dynamically reconstruct the file when it is accessed. This option is only supported when applying to an NTFS volume.
--wimboot-chunk-size=SIZE
When used with --wimboot, this option specifies the chunk size to use for the LZX compressed data. The default is 32768. Valid values are 4096, 8192, 16384, and 32768. Note that XPRESS compressed data is always in chunks of 4096 bytes. This option is ignored if the WIM image is not compressed with LZX.
--compact=FORMAT
Windows-only: compress the extracted files using System Compression, when possible. This only works on either Windows 10 or later, or on an older Windows to which Microsoft's wofadk.sys driver has been added. Several different compression formats may be used with System Compression, and one must be specified as FORMAT. The choices are: xpress4k, xpress8k, xpress16k, and lzx.
Exclusions are handled in the same way as with the --wimboot option. That is: if it exists, the [PrepopulateList] section of the file \Windows\System32\WimBootCompress.ini in the WIM image will be read, and files matching any of the patterns in this section will not be compressed. In addition, wimlib has a hardcoded list of files for which it knows, for compatibility with the Windows bootloader, to override the requested compression format.
--recover-data
If a file is corrupted (its stored hash doesn't match its actual hash, or some parts of it can't be decompressed), extract the corrupted file anyway with a warning, rather than aborting with an error. This may be useful to recover data if a WIM archive was corrupted. Note that recovering data is not guaranteed to succeed, as it depends on the type of corruption that occurred.
--threads=NUM
Use NUM threads to decompress and write files in parallel. The default is 1. Setting this to a value greater than 1 may significantly speed up extraction on multi-core systems, but it increases memory usage. This option is ignored when applying a WimBoot image.
--verify
Verify the checksum of every file after it is extracted. This is the default behavior and is equivalent to the /verify option of ImageX.
--no-verify
Do not verify the checksum of extracted files. This may speed up extraction, but it means that data corruption in the WIM archive will not be detected.
--unsafe-compact
Windows-only: This is an alias for --compact=xpress4k. It is provided for compatibility with older versions of wimlib.

NOTES

Data integrity: WIM files include checksums of file data. To detect accidental (non-malicious) data corruption, wimlib calculates the checksum of every file it extracts and issues an error if it does not have the expected value, unless the --recover-data option is given. (This default behavior seems equivalent to the /verify option of ImageX.) In addition, a WIM file can include an integrity table (extra checksums) over the raw data of the entire WIM file. For performance reasons wimlib does not check the integrity table by default, but the --check option can be passed to make it do so.

ESD files: wimlib can extract files from solid-compressed WIMs, or "ESD" (.esd) files, just like from normal WIM (.wim) files. However, Microsoft sometimes distributes ESD files with encrypted segments; wimlib cannot extract such files until they are first decrypted.

Security: wimlib has been carefully written to validate all input and is believed to be secure against some types of attacks which often plague other file archiving programs, e.g. directory traversal attacks (which, as it happens, Microsoft's WIM software is vulnerable to). Important parts of wimlib, e.g. the decompressors, have also been fuzz tested. However, wimlib is not currently designed to protect against some types of denial-of-service (DOS) attacks, e.g. memory exhaustion or "zip bombs".

EXAMPLES

Extract the first image from the Windows PE WIM on the Windows installation media to the directory "boot":

wimapply /mnt/windows/sources/boot.wim 1 boot

On Windows, apply an image of an entire volume, for example from "install.wim" which can be found on the Windows installation media:

wimapply install.wim 1 E:\

Same as above, but running on a UNIX-like system where the corresponding partition is /dev/sda2:

wimapply install.wim 1 /dev/sda2

Note that before running either of the above commands, an NTFS filesystem may need to be created on the partition, for example with format.exe on Windows or mkntfs(8) on UNIX-like systems. For example, on UNIX you might run:

mkntfs /dev/sda2 && wimapply install.wim 1 /dev/sda2

(Of course don't do that if you don't want to destroy all existing data on the partition!)

See SPLIT WIMS and PIPABLE WIMS for examples of applying split and pipable WIMs, respectively.

OPTIONS

Verify the integrity table of the WIM archive before extracting. This is only useful if the WIM archive contains an integrity table. This option implies --verify.
--confirm
Prompt for confirmation before overwriting any files at the destination. This is only useful when extracting to a directory that is not empty, which is otherwise disallowed. (However, this option is not yet implemented.)
--force
Do not prompt before overwriting files at the destination. This option is only useful when extracting to a directory that is not empty, which is otherwise disallowed. (However, this option is not yet implemented.)
--wimboot
Apply the WIM image in WimBoot mode. This is a special mode intended for use on devices with limited space, such as Windows tablets. In WimBoot mode, files are not directly extracted. Instead, a small stub file is created for each file, which is then used to dynamically reconstruct the file when it is accessed. This option is only supported when applying to an NTFS volume.
--wimboot-chunk-size=SIZE
When used with --wimboot, this option specifies the chunk size to use for the LZX compressed data. The default is 32768. Valid values are 4096, 8192, 16384, and 32768. Note that XPRESS compressed data is always in chunks of 4096 bytes. This option is ignored if the WIM image is not compressed with LZX.
--compact=FORMAT
Windows-only: compress the extracted files using System Compression, when possible. This only works on either Windows 10 or later, or on an older Windows to which Microsoft's wofadk.sys driver has been added. Several different compression formats may be used with System Compression, and one must be specified as FORMAT. The choices are: xpress4k, xpress8k, xpress16k, and lzx.
--recover-data
If a file is corrupted (its stored hash doesn't match its actual hash, or some parts of it can't be decompressed), extract the corrupted file anyway with a warning, rather than aborting with an error. This may be useful to recover data if a WIM archive was corrupted. Note that recovering data is not guaranteed to succeed, as it depends on the type of corruption that occurred.
