watchexec(1) Manual de Comandos Generales watchexec(1)

NOMBRE

watchexec - Ejecuta comandos cuando los archivos observados cambian

SINOPSIS

watchexec [--manual] [--completions] [--only-emit-events] [--shell] [-n] [-E|--env] [--no-process-group] [--wrap-process] [--stop-signal] [--stop-timeout] [--delay-run] [--workdir] [--socket] [-o|--on-busy-update] [-r|--restart] [-s|--signal] [--map-signal] [-d|--debounce] [--stdin-quit] [-p|--postpone] [--poll] [--emit-events-to] [-w|--watch] [-W|--watch-non-recursive] [-F|--watch-file] [--no-vcs-ignore] [--no-project-ignore] [--no-global-ignore] [--no-default-ignore] [--no-discover-ignore] [--ignore-nothing] [-e|--exts] [-f|--filter] [--filter-file] [--project-origin] [-j|--filter-prog] [-i|--ignore] [--ignore-file] [--fs-events] [--no-meta] [-v|--verbose]... [--log-file] [--print-events] [-c|--clear] [-N|--notify] [--color] [--timings] [-q|--quiet] [--bell] [-h|--help] [-V|--version] [COMANDO]

DESCRIPCIÓN

Ejecuta comandos cuando los archivos observados cambian.

Monitoriza recursivamente el directorio actual en busca de cambios, ejecutando el comando cuando se detecta un cambio en el sistema de archivos (entre otras fuentes de eventos). Por defecto, watchexec utiliza mecanismos eficientes a nivel de kernel para detectar cambios.

Al iniciar, el comando especificado se ejecuta una vez, y watchexec comienza a monitorizar los cambios.

Ejemplos:

Reconstruir un proyecto cuando cambian los archivos fuente:

$ watchexec make

Observar todos los archivos HTML, CSS y JavaScript en busca de cambios:

$ watchexec -e html,css,js make

Ejecutar pruebas cuando cambian los archivos fuente, limpiando la pantalla cada vez:

$ watchexec -c make test

Iniciar y reiniciar un servidor de node.js:

$ watchexec -r node app.js

Observar los directorios lib y src en busca de cambios, reconstruyendo cada vez:

$ watchexec -w lib -w src make

OPCIONES

--manual
Mostrar la página del manual

Esto muestra la página del manual de Watchexec, si la salida es una terminal y el programa 'man' está disponible. Si no, la página del manual se imprime en stdout en formato ROFF (adecuado para guardarlo en un archivo watchexec.1).

--completions=SHELL
Generar un script de completado de shell

Proporciona un script de completado o configuración para el shell dado. Si Watchexec no se distribuye con completados pregenerados, puedes usar esto para generarlos tú mismo.

Shells soportados: bash, elvish, fish, nu, powershell, zsh.

--only-emit-events
Solo emitir eventos a stdout, no ejecutar comandos.

Esta es una opción de conveniencia para usar Watchexec como un observador de archivos, sin ejecutar ningún comando. Es casi equivalente a usar `cat` como comando, excepto que no generará un nuevo proceso para cada evento.

Esta opción implica `--emit-events-to=json-stdio`; también puedes usar el modo texto especificando `--emit-events-to=stdio`.

-h, --help
Imprimir ayuda (ver un resumen con '-h')
-V, --version
Imprimir versión
[COMANDO]
Comando (programa y argumentos) a ejecutar ante cambios

Se ejecuta cuando los eventos pasan los filtros y el período de debounce (y una vez al inicio a menos que se indique '--postpone'). Si pasas flags al comando, deberías separarlo con -- aunque no es estrictamente necesario.

Ejemplos:

$ watchexec -w src npm run build

$ watchexec -w src -- rsync -a src dest

Ten cuidado al usar globs u otras expansiones del shell en el comando. Tu shell podría expandirlos antes de pasarlos a Watchexec, y los resultados podrían no ser los esperados. Compara:

$ watchexec echo src/*.rs

$ watchexec echo 'src/*.rs'

$ watchexec --shell=none echo 'src/*.rs'

El comportamiento depende del valor de '--shell': para todos excepto 'none', cada parte del comando se une en una sola cadena con un único carácter de espacio ascii, y se pasa al shell como se describe en la ayuda de '--shell'. Para 'none', cada elemento distinto del comando se pasa según la convención execvp(3): el primer argumento es el programa, como ruta o buscado en la variable de entorno 'PATH', el resto son argumentos.

COMANDO

--shell=SHELL
Usar un shell diferente

Por defecto, Watchexec usará '$SHELL' si está definido o un valor por defecto de 'sh' en sistemas Unix-likes, y 'pwsh', 'powershell', o 'cmd' (CMD.EXE) en Windows, dependiendo de qué shell detecte Watchexec que se está ejecutando.

Con esta opción, puedes anular eso y usar un shell diferente, por ejemplo uno con más características o uno que tenga tus alias y funciones personalizadas.

Si el valor contiene espacios, se analiza como una línea de comandos, y la primera palabra se usa como el programa del shell, con el resto como argumentos para el shell.

El comando se ejecuta con el flag '-c' (excepto para 'cmd' en Windows, donde es '/C').

El valor especial 'none' puede usarse para deshabilitar el uso del shell por completo. En ese caso, el comando proporcionado a Watchexec se analizará, siendo la primera palabra el ejecutable y el resto los argumentos, y se ejecutará directamente. Ten en cuenta que este análisis es rudimentario y puede que no funcione como se espera en todos los casos.

Usar 'none' es un poco más eficiente y puede permitir una interpretación más estricta de la entrada, pero también significa que no puedes usar características del shell como globbing, redirección, control de flujo, lógica o pipes.

Ejemplos:

Usar sin shell:

$ watchexec -n -- zsh -x -o shwordsplit scr

Usar con powershell core:

$ watchexec --shell=pwsh -- Test-Connection localhost

Usar con CMD.exe:

$ watchexec --shell=cmd -- dir

Usar con un shell de Unix diferente:

$ watchexec --shell=bash -- 'echo $BASH_VERSION'

Usar con un shell de Unix y opciones:

$ watchexec --shell='zsh -x -o shwordsplit' -- scr

-n
Atajo para '--shell=none'
-E, --env=CLAVE=VALOR
Añadir variables de entorno al comando

Esta es una opción de conveniencia para establecer variables de entorno para el comando, sin establecerlas para el propio proceso de Watchexec.

Usa la sintaxis clave=valor. Se pueden establecer múltiples variables repitiendo la opción.

--no-process-group
No usar un grupo de procesos

Por defecto, Watchexec ejecutará el comando en un grupo de procesos, para que las señales y terminaciones se envíen a todos los procesos del grupo. A veces eso no es lo que quieres, y puedes deshabilitar el comportamiento con esta opción.

Obsoleto, usa '--wrap-process=none' en su lugar.

--wrap-process=MODO [por defecto: group]
Configurar cómo se envuelve el proceso

Por defecto, Watchexec ejecutará el comando en una sesión en Mac, en un grupo de procesos en Unix, y en un Objeto de Trabajo en Windows.

Algunos programas de Unix prefieren ejecutarse en una sesión, mientras que otros no funcionan en un grupo de procesos.

Usa 'group' para usar un grupo de procesos, 'session' para usar una sesión de procesos, y 'none' para ejecutar el comando directamente. En Windows, cualquiera de 'group' o 'session' usará un Objeto de Trabajo.

--stop-signal=SEÑAL
Señal a enviar para detener el comando

Esto se utiliza en los modos 'restart' y 'signal' de '--on-busy-update' (a menos que se proporcione '--signal'). El comportamiento de reinicio consiste en enviar la señal, esperar a que el comando termine y, si no ha terminado después de algún tiempo (ver '--timeout-stop'), terminarlo forzosamente.

El valor predeterminado en unix es "SIGTERM".

La entrada se analiza como un nombre de señal completo (como "SIGTERM"), un nombre de señal corto (como "TERM") o un número de señal (como "15"). Toda la entrada no distingue entre mayúsculas y minúsculas.

En Windows, esta opción es técnicamente compatible, pero solo admite el evento "KILL", ya que Watchexec aún no puede enviar otros eventos. Windows no tiene señales como tales; en su lugar, tiene terminación (aquí llamada "KILL" o "STOP") y eventos "CTRL+C", "CTRL+BREAK" y "CTRL+CLOSE". Para portabilidad, las señales de unix "SIGKILL", "SIGINT", "SIGTERM" y "SIGHUP" se corresponden respectivamente con estas.

--stop-timeout=TIEMPO
Tiempo de espera para que el comando termine limpiamente

Esto se utiliza en el modo 'restart' de '--on-busy-update'. Después de enviar la señal de parada limpia, Watchexec esperará a que el comando termine. Si no ha terminado después de este tiempo, se terminará forzosamente.

Acepta un valor sin unidades en segundos o un valor de lapso de tiempo como "5min 20s". Proporcionar un valor sin unidades está obsoleto y generará una advertencia; será un error en el futuro.

El valor predeterminado es 10 segundos. Establézcalo en 0 para terminar forzosamente el comando inmediatamente.

Esto no tiene ningún efecto práctico en Windows, ya que el comando siempre se termina forzosamente; vea '--stop-signal' para entender por qué.

--delay-run=DURACIÓN
Dormir antes de ejecutar el comando

Esta opción hará que Watchexec duerma durante el tiempo especificado antes de ejecutar el comando, después de detectar un evento. Esto es como usar "sleep 5 && command" en un shell, pero es portable y ligeramente más eficiente.

Acepta un valor sin unidades en segundos o un valor de lapso de tiempo como "2min 5s". Proporcionar un valor sin unidades está obsoleto y generará una advertencia; será un error en el futuro.

--workdir=DIRECTORIO
Establecer el directorio de trabajo

Por defecto, el directorio de trabajo del comando es el directorio de trabajo de Watchexec. Puede cambiarlo con esta opción. Tenga en cuenta que las rutas pueden ser menos intuitivas de usar con esto.

--socket=PUERTO
Proporcionar un socket al comando

Esto implementa el protocolo de paso de sockets de systemd, similar a `systemfd`: los sockets se abren desde el proceso de watchexec y luego se pasan a los comandos que ejecuta. Esto le permite mantener los sockets abiertos y evitar problemas de reutilización de direcciones o pérdida de paquetes.

Esta opción se puede proporcionar varias veces, para abrir múltiples sockets.

El valor puede ser `PUERTO` (abre un socket de escucha TCP en ese puerto), `HOST:PUERTO` (especifica una dirección IP de host; las direcciones IPv6 se pueden especificar `[entre corchetes]`), `TIPO::PUERTO` o `TIPO::HOST:PUERTO` (especifica un tipo de socket, `tcp` / `udp`).

Esta integración solo proporciona soporte básico, si desea más control, debería usar la herramienta `systemfd` de https://github.com/mitsuhiko/systemfd, en la que se basa. La sintaxis aquí y el comportamiento de generación son idénticos a `systemfd`, y tanto watchexec como systemfd son implementaciones compatibles del protocolo de activación de sockets de systemd.

Watchexec _no_ establece la variable `LISTEN_PID` en unix, lo que significa que cualquier proceso hijo de su comando podría enlazarse accidentalmente a los sockets, a menos que las variables `LISTEN_*` se eliminen del entorno.

EVENTOS

-o, --on-busy-update=MODO
Qué hacer al recibir eventos mientras el comando se está ejecutando

El valor predeterminado es 'do-nothing', que ignora los eventos mientras el comando se está ejecutando, de modo que los cambios que ocurren debido al comando se ignoran, como las salidas de compilación. También puede usar 'queue', que ejecutará el comando una vez más cuando termine la ejecución actual si ocurren eventos mientras se está ejecutando, o 'restart', que termina el comando en ejecución y comienza uno nuevo. Finalmente, está 'signal', que solo envía una señal; esto puede ser útil con programas que pueden recargar su configuración sin un reinicio completo.

La señal se puede especificar con la opción '--signal'.

-r, --restart
Reiniciar el proceso si todavía se está ejecutando

Este es un atajo para '--on-busy-update=restart'.

-s, --signal=SEÑAL
Enviar una señal al proceso mientras todavía se está ejecutando

Especifique una señal para enviar al proceso mientras todavía se está ejecutando. Esto implica '--on-busy-update=signal'; de lo contrario, la señal utilizada cuando ese modo es 'restart' se controla mediante '--stop-signal'.

Vea la documentación detallada para '--stop-signal' para la sintaxis.

Las señales no son compatibles con Windows en este momento y siempre se anularán a 'kill'. Vea '--stop-signal' para más información sobre las "señales" de Windows.

--map-signal=SEÑAL:SEÑAL
Traducir señales del sistema operativo a señales a enviar al comando

Toma un par de nombres de señal, separados por dos puntos, como "TERM:INT" para mapear SIGTERM a SIGINT. La primera señal es la que recibe watchexec, y la segunda es la que se envía al comando. La segunda se puede omitir para descartar la primera señal, como "TERM:" para no hacer nada ante SIGTERM.

Si SIGINT o SIGTERM se mapean, entonces ya no cierran Watchexec. Además de dificultar el cierre del propio Watchexec, esto es útil para enviar un Ctrl-C al comando sin terminar también Watchexec y el programa subyacente con él, por ejemplo con "INT:INT".

Esta opción se puede especificar varias veces para mapear múltiples señales.

La sintaxis de señal no distingue entre mayúsculas y minúsculas para nombres cortos (como "TERM", "USR2") y nombres largos (como "SIGKILL", "SIGHUP"). También se admiten números de señal (como "15", "31"). En Windows, las formas "STOP", "CTRL+C" y "CTRL+BREAK" también se admiten para recibir, pero Watchexec aún no puede enviar otras "señales" que no sean un STOP.

-d, --debounce=TIEMPO
Tiempo de espera para nuevos eventos antes de tomar una acción

Cuando se recibe un evento, Watchexec esperará hasta esta cantidad de tiempo antes de manejarlo (como ejecutar el comando). Esto es esencial ya que lo que usted puede percibir como un solo cambio puede emitir muchos eventos, y sin este comportamiento, Watchexec se ejecutaría demasiado a menudo. Además, no es infrecuente que las escrituras de archivos no sean atómicas, y cada escritura puede emitir un evento, por lo que esta es una buena manera de evitar ejecutar un comando mientras un archivo está parcialmente escrito.

Un uso alternativo es establecer un valor alto (como "30min" o más), para ahorrar energía o ancho de banda en tareas intensivas, como un script de copia de seguridad ad hoc. En esos casos de uso, tenga en cuenta que cada evento acumulado se acumulará en la memoria.

Acepta un valor sin unidades en milisegundos o un valor de lapso de tiempo como "5sec 20ms". Proporcionar un valor sin unidades está obsoleto y generará una advertencia; será un error en el futuro.

El valor predeterminado es 50 milisegundos. Establecerlo en 0 es altamente desaconsejable.

--stdin-quit
Salir cuando se cierre la entrada estándar

Esto vigila el descriptor de archivo de entrada estándar para detectar EOF y cierra Watchexec limpiamente cuando se cierra. Esto es utilizado por algunos gestores de procesos para evitar dejar procesos zombis.

-p, --postpone
Esperar hasta el primer cambio antes de ejecutar el comando

Por defecto, Watchexec ejecutará el comando una vez de inmediato. Con esta opción, esperará hasta que se detecte un evento antes de ejecutar el comando como de costumbre.

--poll=INTERVALO
Consultar cambios en el sistema de archivos

Por defecto, y donde esté disponible, Watchexec utiliza las capacidades nativas del sistema operativo para vigilar el sistema de archivos. Esta opción deshabilita eso y en su lugar utiliza un mecanismo de sondeo, que es menos eficiente pero puede solucionar problemas con algunos sistemas de archivos (como unidades de red) o casos extremos.

Opcionalmente, acepta un valor sin unidades en milisegundos o un valor de lapso de tiempo como "2s 500ms", para usar como intervalo de sondeo. Si no se especifica, el valor predeterminado es 30 segundos. Proporcionar un valor sin unidades está obsoleto y generará una advertencia; será un error en el futuro.

Alias: '--force-poll'.

--emit-events-to=MODO
Configurar la emisión de eventos

Watchexec puede emitir información de eventos al ejecutar un comando, que puede ser utilizada por el proceso hijo para apuntar a archivos cambiados específicos.

Una cosa a tener en cuenta es asumir un comportamiento inherente donde solo hay probabilidad. Notablemente, podría parecer que la variable `RENAMED` contiene tanto la ruta original como la nueva ruta renombrada. En versiones anteriores, incluso parecía en algunas plataformas que la original siempre venía antes que la nueva. Sin embargo, nada de esto era cierto. Es imposible de forma fiable y porta

REPORTING DE EVENTOS

-e, --events=MODE
Event reporting mode

Cuando Watchexec recibe un evento del sistema de archivos, genera una serie de datos sobre el evento. La información completa, como si un cambio fue un archivo o una carpeta, es el destino de una operación de renombrado (y no solo el archivo original o el nuevo), si los archivos se crearon, se eliminaron, se modificaron o se renombraron, o si la operación se debió a una solicitud de watcher, una operación de sistema de archivos, una entrada de teclado o un ratón, etc. Es bastante complejo, especialmente cuando se tienen en cuenta los reintentos, los patrones de exclusión, los eventos duplicados, la falta de conocimiento sobre qué ruta de cambio es la vieja o la nueva, los renames parciales pueden aparecer (solo el original, solo el nuevo), los renames desconocidos pueden aparecer (el cambio fue un rename, pero no se sabe si fue el viejo o el nuevo), los eventos de rename pueden dividirse entre dos límites de debounce, y así sucesivamente.

Esta opción controla dónde se emite esa información. Por defecto es 'none', que no emite información de eventos en absoluto. Las otras opciones son 'environment' (obsoleto), 'stdio', 'file', 'json-stdio' y 'json-file'.

Los modos 'stdio' y 'file' son basados en texto: 'stdio' escribe rutas absolutas en la entrada estándar del comando, una por línea, cada una prefijada con `create:`, `remove:`, `rename:`, `modify:` u `other:`, luego cierra el manejador; 'file' escribe lo mismo en un archivo temporal, y su ruta se proporciona con la variable de entorno $WATCHEXEC_EVENTS_FILE.

También hay dos modos JSON, que se basan en objetos JSON y pueden representar el conjunto completo de eventos que Watchexec maneja. Aquí hay un ejemplo de una carpeta que se crea en Linux:

```json
{
"tags": [
{
"kind": "path",
"absolute": "/home/user/your/new-folder",
"filetype": "dir"
},
{
"kind": "fs",
"simple": "create",
"full": "Create(Folder)"
},
{
"kind": "source",
"source": "filesystem",
}
],
"metadata": {
"notify-backend": "inotify"
}
} ```

Los campos son los siguientes:


- `tags`, datos estructurados del evento.
- `tags[].kind`, que puede ser:
* 'path', junto con:
+ `absolute`, una ruta absoluta.
+ `filetype`, un tipo de archivo si se conoce ('dir', 'file', 'symlink', 'other').
* 'fs':
+ `simple`, el tipo de evento "simple" ('access', 'create', 'modify', 'remove' u 'other').
+ `full`, el tipo de evento "completo", que es demasiado complejo para describir aquí completamente, pero se ve como 'General(Precise(Specific))'.
* 'source', junto con:
+ `source`, la fuente del evento ('filesystem', 'keyboard', 'mouse', 'os', 'time', 'internal').
* 'keyboard', junto con:
+ `keycode`. Actualmente solo se admite el valor 'eof'.
* 'process', para eventos causados por procesos:
+ `pid`, el ID del proceso.
* 'signal', para señales enviadas a Watchexec:
+ `signal`, el nombre de la señal normalizada ('hangup', 'interrupt', 'quit', 'terminate', 'user1', 'user2').
* 'completion', para cuando un comando termina:
+ `disposition`, la disposición de salida ('success', 'error', 'signal', 'stop', 'exception', 'continued').
+ `code`, el código de salida, señal, parada o excepción.
- `metadata`, información adicional sobre el evento.

El modo 'json-stdio' emitirá eventos JSON a la entrada estándar del comando, uno por línea, y luego cerrará la entrada estándar. El modo 'json-file' creará un archivo temporal, escribirá los eventos en él y proporcionará la ruta al archivo con la variable de entorno $WATCHEXEC_EVENTS_FILE.

Finalmente, el modo 'environment' fue el predeterminado hasta la versión 2.0. Establece variables de entorno con las rutas de los archivos afectados, para eventos del sistema de archivos:

$WATCHEXEC_COMMON_PATH se establece en la ruta común más larga de todas las variables a continuación, y por lo tanto debe anteponerse a cada ruta para obtener la ruta completa/real. Luego:


- $WATCHEXEC_CREATED_PATH se establece cuando se crearon archivos/carpetas
- $WATCHEXEC_REMOVED_PATH se establece cuando se eliminaron archivos/carpetas
- $WATCHEXEC_RENAMED_PATH se establece cuando se renombraron archivos/carpetas
- $WATCHEXEC_WRITTEN_PATH se establece cuando se modificaron archivos/carpetas
- $WATCHEXEC_META_CHANGED_PATH se establece cuando se modificaron los metadatos de archivos/carpetas
- $WATCHEXEC_OTHERWISE_CHANGED_PATH se establece para cualquier otro tipo de evento de ruta

Múltiples rutas están separadas por el separador de rutas del sistema, ';' en Windows y ':' en unix. Dentro de cada variable, las rutas se deduplican y se ordenan en orden binario (es decir, sin tener en cuenta Unicode ni la configuración regional).

Este es el modo heredado, está obsoleto y se eliminará en el futuro. El entorno es un espacio muy restringido, y además limitado en lo que puede representar de forma útil. Un gran número de archivos provocará que el entorno se trunque, o puede generar un error o bloquear el proceso por completo. El $WATCHEXEC_COMMON_PATH también es poco intuitivo, como lo demuestran las múltiples consultas confusas que han llegado a mi bandeja de entrada a lo largo de los años.

FILTRADO

-w, --watch=RUTA
Observar un archivo o directorio específico

Por defecto, Watchexec observa el directorio actual.

Cuando se observa un solo archivo, a menudo es mejor observar el directorio contenedor en su lugar, y filtrar por el nombre del archivo. Algunos editores pueden reemplazar el archivo con uno nuevo al guardar, y algunas plataformas pueden no detectar eso o cambios posteriores.

Al iniciar, Watchexec resuelve un "origen del proyecto" a partir de las rutas observadas. Consulte la ayuda de '--project-origin' para obtener más información.

Esta opción se puede especificar varias veces para observar múltiples archivos o directorios.

El valor especial '/dev/null', proporcionado como la única ruta observada, hará que Watchexec no observe ninguna ruta. Otras fuentes de eventos (como señales o eventos de teclado) aún pueden ser utilizadas.

-W, --watch-non-recursive=RUTA
Observar un directorio específico, de forma no recursiva

A diferencia de '-w', las carpetas observadas con esta opción no se recorren recursivamente.

Esta opción se puede especificar varias veces para observar múltiples directorios de forma no recursiva.

-F, --watch-file=RUTA
Observar archivos y directorios desde un archivo

Cada línea del archivo se interpretará como si se hubiera proporcionado a '-w'.

Para usos más complejos (como observar de forma no recursiva), utilice la capacidad de archivo de argumentos: cree un archivo que contenga opciones de línea de comandos y páselo a watchexec con `@ruta/al/archivo`.

El valor especial '-' leerá de STDIN; esto es incompatible con '--stdin-quit'.

--no-vcs-ignore
No cargar gitignores

Entre otros archivos de exclusión de VCS, como para Mercurial, Subversion, Bazaar, DARCS, Fossil. Tenga en cuenta que Watchexec detectará cuál de estos está en uso, si alguno, y solo cargará los archivos relevantes. Se consideran tanto los archivos globales (como '~/.gitignore') como los locales (como '.gitignore').

Esta opción es útil si desea observar archivos que son ignorados por Git.

--no-project-ignore
No cargar ignorados del proyecto

Esto deshabilita la carga de archivos de ignorados locales del proyecto, como '.gitignore' o '.ignore' en el proyecto observado. Esto se contrasta con '--no-vcs-ignore', que deshabilita la carga de archivos de ignorados de Git y otros VCS, y con '--no-global-ignore', que deshabilita la carga de archivos de ignorados globales o de usuario, como '~/.gitignore' o '~/.config/watchexec/ignore'.

Archivos de ignorados del proyecto compatibles:


- Git: .gitignore en la raíz del proyecto y directorios hijos, .git/info/exclude, y el archivo al que apunta `core.excludesFile` en .git/config.
- Mercurial: .hgignore en la raíz del proyecto y directorios hijos.
- Bazaar: .bzrignore en la raíz del proyecto.
- Darcs: _darcs/prefs/boring
- Fossil: .fossil-settings/ignore-glob
- Ripgrep/Watchexec/genérico: .ignore en la raíz del proyecto y directorios hijos.

Los archivos de ignorados de VCS (Git, Mercurial, Bazaar, Darcs, Fossil) solo se utilizan si se descubre que el VCS correspondiente está en uso para el proyecto/origen. Por ejemplo, un .bzrignore en un repositorio de Git será descartado.

--no-global-ignore
No cargar ignorados globales

Esto deshabilita la carga de archivos de ignorados globales o de usuario, como '~/.gitignore', '~/.config/watchexec/ignore' o '%APPDATA%\Bazzar\2.0\ignore'. Contrasta con '--no-vcs-ignore' y '--no-project-ignore'.

Archivos de ignorados globales compatibles


- Git (si core.excludesFile está configurado): el archivo en esa ruta
- Git (de lo contrario): el primero encontrado de $XDG_CONFIG_HOME/git/ignore, %APPDATA%/.gitignore, %USERPROFILE%/.gitignore, $HOME/.config/git/ignore, $HOME/.gitignore.
- Bazaar: el primero encontrado de %APPDATA%/Bazzar/2.0/ignore, $HOME/.bazaar/ignore.
- Watchexec: el primero encontrado de $XDG_CONFIG_HOME/watchexec/ignore, %APPDATA%/watchexec/ignore, %USERPROFILE%/.watchexec/ignore, $HOME/.watchexec/ignore.

Al igual que para los archivos del proyecto, los archivos globales de Git y Bazaar solo se utilizarán para el VCS correspondiente tal como se usa en el proyecto.

--no-default-ignore
No usar ignorados predeterminados internos

Watchexec tiene un conjunto de patrones de ignorado predeterminados, como archivos de intercambio de editor, `*.pyc`, `*.pyo`, `.DS_Store`, `.bzr`, `_darcs`, `.fossil-settings`, `.git`, `.hg`, `.pijul`, `.svn`, y archivos de registro de Watchexec.

--no-discover-ignore
No descubrir archivos de ignorados en absoluto

Esto es un atajo para '--no-global-ignore', '--no-vcs-ignore', '--no-project-ignore', pero aún más eficiente, ya que omitirá todos los mecanismos de descubrimiento de ignorados desde el principio.

Tenga en cuenta que los ignorados predeterminados todavía se cargan, consulte '--no-default-ignore'.

OPTIONS

-i, --ignore-nothing
Don't use default ignore file

By default, Watchexec ignores files listed in a `default-ignore` file. This option disables that behaviour.

Note that ignores explicitly loaded via other command line options, such as '--ignore' or '--ignore-file', will still be used.

-e, --exts=EXTENSIONS
Extensiones de nombre de archivo para filtrar

Este es un filtro rápido para emitir solo eventos para archivos con las extensiones dadas. Las extensiones se pueden dar con o sin el punto inicial (por ejemplo, 'js' o '.js'). Se pueden dar múltiples extensiones repitiendo la opción o separándolas con comas.

-f, --filter=PATTERN
Patrones de nombre de archivo para filtrar

Proporcione un patrón de filtro similar a glob y solo se emitirán eventos para archivos que coincidan con el patrón. Se pueden dar varios patrones repitiendo la opción. Los eventos que no provienen de archivos (por ejemplo, señales, eventos de teclado) pasarán sin cambios.

--filter-file=PATH
Archivos para cargar filtros desde

Proporcione una ruta a un archivo que contenga filtros, uno por línea. Las líneas vacías y las líneas que comienzan con '#' se ignoran. Utiliza el mismo formato de patrón que la opción '--filter'.

Esto también se puede usar a través de la variable de entorno $WATCHEXEC_FILTER_FILES.

--project-origin=DIRECTORY
Establecer el origen del proyecto

Watchexec intentará descubrir el "origen" (o "raíz") del proyecto buscando una variedad de marcadores, como archivos o patrones de directorio. Hace todo lo posible, pero a veces se equivoca, y puede anularlo con esta opción.

El origen del proyecto se utiliza para determinar la ruta de ciertos archivos de ignorar, qué VCS se está utilizando, el significado de un '/' inicial en los patrones de filtrado, y quizás más en el futuro.

Cuando se establece, Watchexec tampoco molestará en buscar, lo que puede ser significativamente más rápido.

-j, --filter-prog=EXPRESSION
Programas de filtro.

Proporcione sus propios programas de filtro personalizados en sintaxis jaq (similar a jq). A los programas se les da un evento en el mismo formato que se describe en '--emit-events-to' y deben devolver un booleano. Los programas inválidos harán que watchexec falle al iniciarse; use '-v' para ver los errores de tiempo de ejecución del programa.

Además de la biblioteca estándar de jaq, watchexec agrega algunas definiciones de filtro personalizadas:

- 'path | file_meta' devuelve metadatos del archivo o nulo si el archivo no existe.

- 'path | file_size' devuelve el tamaño del archivo en la ruta, o nulo si no existe.

- 'path | file_read(bytes)' devuelve una cadena con los primeros n bytes del archivo en la ruta. Si el archivo es más pequeño que n bytes, se devuelve todo el archivo. No hay un filtro para leer el archivo completo a la vez para fomentar la limitación de la cantidad de datos leídos y procesados.

- 'string | hash', y 'path | file_hash' devuelven el hash de la cadena o archivo en la ruta. No se garantiza el algoritmo utilizado: trátelo como un valor opaco.

- 'any | kv_store(key)', 'kv_fetch(key)', y 'kv_clear' proporcionan una tienda simple de clave-valor. Los datos se mantienen solo en memoria, no hay persistencia. No se garantiza la consistencia.

- 'any | printout', 'any | printerr', y 'any | log(level)' imprimirán o registrarán cualquier valor en stdout, stderr o el registro (niveles = error, advertencia, información, depuración, rastreo), y pasarán el valor (por lo que '[1] | log("debug") | .[]' producirá un '1' y registrará '[1]').

Todo el filtrado realizado con dichos programas, y especialmente aquellos que usan acceso a kv o al sistema de archivos, es mucho más lento que los otros métodos de filtrado. Si el filtrado es demasiado lento, los eventos se acumularán y detendrán watchexec. Tenga cuidado al diseñar sus filtros.

Si el argumento de esta opción comienza con '@', el resto del argumento se toma como la ruta a un archivo que contiene un programa jaq.

Los programas Jaq se ejecutan en orden, después de todos los demás filtros, y se detienen corto: si un filtro (jaq o no) rechaza un evento, la ejecución se detiene allí y no se ejecutan otros filtros. Además, se detienen después de producir el primer valor, por lo que querrá usar 'any' o 'all' al iterar, de lo contrario, solo se procesará el primer elemento, lo que puede ser bastante confuso.

Encuentre programas aportados por usuarios o envíe los suyos propios y útiles en https://github.com/watchexec/watchexec/discussions/592.

## Ejemplos:

Filtro de ignorar de expresiones regulares en rutas:

'all(.tags[] | select(.kind == "path"); .absolute | test("[.]test[.]js$")) | not'

Pasar cualquier evento que cree un archivo:

'any(.tags[] | select(.kind == "fs"); .simple == "create")'

Pasar eventos que toquen archivos ejecutables:

'any(.tags[] | select(.kind == "path" && .filetype == "file"); .absolute | metadata | .executable)'

Ignorar archivos que comiencen con shebangs:

'any(.tags[] | select(.kind == "path" && .filetype == "file"); .absolute | read(2) == "#!") | not'

-i, --ignore=PATTERN
Patrones de nombre de archivo para filtrar hacia afuera

Proporcione un patrón de filtro similar a glob y los eventos para los archivos que coincidan con el patrón serán excluidos. Se pueden dar varios patrones repitiendo la opción. Los eventos que no provienen de archivos (por ejemplo, señales, eventos de teclado) pasarán sin cambios.

--ignore-file=PATH
Archivos para cargar ignorados desde

Proporcione una ruta a un archivo que contenga ignorados, uno por línea. Las líneas vacías y las líneas que comienzan con '#' se ignoran. Utiliza el mismo formato de patrón que la opción '--ignore'.

Esto también se puede usar a través de la variable de entorno $WATCHEXEC_IGNORE_FILES.

--fs-events=EVENTS
Eventos del sistema de archivos para filtrar

Este es un filtro rápido para emitir solo eventos para los tipos dados de cambios en el sistema de archivos. Elija entre 'access', 'create', 'remove', 'rename', 'modify', 'metadata'. Se pueden dar varios tipos repitiendo la opción o separándolos con comas. Por defecto, son todos los tipos excepto 'access'.

Esto puede aplicar filtrado a nivel del kernel cuando sea posible, lo que puede ser más eficiente, pero puede ser más confuso al leer los registros.

--no-meta
No emitir eventos del sistema de archivos para cambios de metadatos

Este es un atajo para '--fs-events create,remove,rename,modify'. Usarlo junto con la opción '--fs-events' no tiene sentido y no está permitido.

DEBUGGING

-v, --verbose
Establecer el nivel de registro de diagnóstico

Esto habilita el registro de diagnóstico, que es útil para investigar errores u obtener más información sobre filtros defectuosos o eventos "perdidos". Úselo varias veces para aumentar la verbosidad.

Llega hasta '-vvvv'. Al enviar informes de errores, use por defecto un nivel de registro de '-vvv'.

Es posible que desee usarlo con '--log-file' para evitar contaminar su terminal.

Establecer $WATCHEXEC_LOG también funciona y tiene prioridad, pero no se recomienda. Sin embargo, usar $WATCHEXEC_LOG es la única forma de obtener registros de antes de que se analicen estas opciones.

--log-file=PATH
Escribir registros de diagnóstico en un archivo

Esto escribe registros de diagnóstico en un archivo, en lugar de en la terminal, en formato JSON. Si aún no se especificó un nivel de registro, se establecerá en '-vvv'.

Si no se proporciona una ruta, el valor predeterminado es el directorio de trabajo. Tenga en cuenta que con '--ignore-nothing', los eventos de escritura en el registro probablemente serán capturados por Watchexec, lo que provocará un bucle; prefiera establecer una ruta fuera del directorio vigilado.

Si la ruta proporcionada es un directorio, se creará un archivo en ese directorio. El nombre del archivo será la fecha y hora actuales, en el formato 'watchexec.YYYY-MM-DDTHH-MM-SSZ.log'.

--print-events
Imprimir eventos que activan acciones

Esto imprime los eventos que activaron la acción al manejarla (después del debouncing), en un formato legible por humanos. Esto es útil para depurar filtros.

Use '-vvv' en su lugar cuando necesite más información de diagnóstico.

OUTPUT

-c, --clear=MODE
Borrar la pantalla antes de ejecutar el comando

Si esto no borra completamente la pantalla, intente '--clear=reset'.

-N, --notify
Alertar cuando los comandos comienzan y terminan

Con esto, Watchexec emitirá una notificación de escritorio cuando un comando comience y termine, en plataformas compatibles. En plataformas no compatibles, puede no hacer nada en silencio o registrar una advertencia.

--color=MODE [default: auto]
Cuándo usar colores en la terminal

--timings
Imprimir cuánto tiempo tardó en ejecutarse el comando

Esto puede no ser exactamente preciso, ya que incluye algo de sobrecarga del propio Watchexec. Use la utilidad `time`, temporizadores de alta precisión o herramientas de benchmarking para obtener resultados más precisos.

-q, --quiet
No imprimir mensajes de inicio y fin

Por defecto, Watchexec imprimirá un mensaje cuando el comando comience y termine. Esta opción deshabilita este comportamiento, por lo que solo se imprimirán la salida, las advertencias y los errores del comando.
