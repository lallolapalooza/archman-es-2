NOMBRE

waypipe - Un proxy transparente para aplicaciones Wayland

SINOPSIS

waypipe [opciones...] ssh [opciones de ssh] destino comando...

waypipe [opciones...] client
waypipe [opciones...] server -- comando...
waypipe bench
waypipe [--version] [-h, --help]

[opciones...] = [-c, --compress C] [-d, --debug] [-n, --no-gpu] [-o, --oneshot] [-s, --socket S] [--display D] [--drm-node R] [--remote-node R] [--remote-bin R] [--remote-socket S] [--login-shell] [--threads T] [--title-prefix P] [--unlink-socket] [--video V] [--vsock] [--secctx S]

DESCRIPCIÓN

Waypipe es un proxy para clientes Wayland, con el objetivo de admitir comportamiento como ssh -X.

Prefijar un comando ssh ... para convertirlo en waypipe ssh ... ejecutará automáticamente waypipe tanto local como remotamente, y modificará el comando ssh para establecer el reenvío entre las dos instancias de waypipe. La instancia remota actuará como un compositor Wayland, permitiendo que las aplicaciones Wayland que se ejecutan remotamente se muestren localmente.

Cuando se ejecuta como waypipe client, abrirá un socket (por defecto en /tmp/waypipe-client.sock) y se conectará al compositor Wayland local y reenviará todas las aplicaciones Wayland que se vincularon a él a través del socket por una instancia coincidente de waypipe server.

Cuando se ejecuta como waypipe server, ejecutará el comando que sigue en su línea de comandos de invocación, configurará su propio socket de compositor Wayland e intentará conectarse a su socket coincidente de waypipe client (por defecto /tmp/waypipe-server.sock) e intentará reenviar todos los clientes Wayland que se conecten al socket de compositor falso al waypipe client coincidente.

El modo waypipe bench se puede utilizar para estimar qué opciones de compresión producen la menor latencia, para un ancho de banda de conexión y número de hilos dados. Prueba dos imágenes sintéticas, una hecha para ser aproximadamente tan compresible como imágenes que contienen texto, y otra hecha para ser aproximadamente tan compresible como imágenes que contienen fotografías.

OPCIONES

-c C, --compress C

Selecciona el método de compresión aplicado a las transferencias de datos. Las opciones son none (para redes de alto ancho de banda), lz4 (intermedio), zstd (conexión lenta). La compresión por defecto es lz4.† El nivel de compresión se puede elegir añadiendo = seguido de un número. Por ejemplo, si C es zstd=7, waypipe usará compresión Zstd de nivel 7.

† A menos que waypipe se compile sin soporte LZ4, en cuyo caso la compresión por defecto será none.

-d, --debug

Imprime mensajes de registro de depuración.

-h, --help

Muestra el mensaje de ayuda y sale.

-n, --no-gpu

Bloquea protocolos como wayland-drm y linux-dmabuf que requieren acceso a, por ejemplo, nodos de renderizado.

-o, --oneshot

Permite solo una conexión y sale cuando se cierra.

-s S, --socket S

Usa S como ruta para el socket Unix. La ruta del socket por defecto en modo servidor es /tmp/waypipe-server.sock; para modo cliente, es /tmp/waypipe-client.sock; y en modo ssh, S da el prefijo utilizado por el cliente y el servidor para sus rutas de socket. (Las rutas reales de socket en modo ssh añaden un sufijo aleatorio a S.) El prefijo por defecto en modo ssh es /tmp/waypipe.

Cuando se habilita vsock, usa S para especificar un CID y un número de puerto.

--version

Describe brevemente la versión de Waypipe y las características con las que se compiló, luego sale. Características posibles: soporte de compresión LZ4, soporte de compresión ZSTD, capacidad para transferir DMABUF, soporte de compresión de video.

--display D

Para el modo servidor o ssh, proporciona WAYLAND_DISPLAY y deja que waypipe configure su socket de pantalla Wayland para que tenga una ruta coincidente. (Si D no es una ruta absoluta, el socket se creará en la carpeta proporcionada por la variable de entorno XDG_RUNTIME_DIR.)

--drm-node R

Especifica la ruta R al dispositivo drm que esta instancia de waypipe debe usar y (en modo servidor) notifica a las aplicaciones que se conectan.

--remote-node R

En modo ssh, especifica la ruta R al dispositivo drm que la instancia remota de waypipe (ejecutándose en modo servidor) debe usar.

--remote-bin R

En modo ssh, especifica la ruta R al binario waypipe en la computadora remota, o su nombre si está disponible en PATH. Por defecto es waypipe si esta opción no se pasa.

--remote-socket R

En modo ssh, especifica el prefijo utilizado por el waypipe server remoto para su ruta de socket. Esto anula la opción --socket, solo en el lado del servidor.

--login-shell

Solo para modo servidor; si no se está ejecutando ningún comando, abre un shell de inicio de sesión.

--threads T

Establece el número total de hilos (incluido el hilo principal) que una instancia de waypipe creará. Estos hilos se usarán para paralelizar las operaciones de compresión. Esta bandera se pasa a waypipe server cuando se le da a waypipe ssh. La bandera también controla el número de hilos para waypipe bench. El comportamiento por defecto (elegible configurando T a 0) es usar la mitad de hilos que los disponibles en el hardware del ordenador.

--title-prefix P

Antepone P a cualquier título de ventana especificado utilizando el protocolo XDG shell. En modo ssh, el prefijo se aplica solo en el lado del cliente.

--unlink-socket

Solo para modo servidor; al apagarse, elimina el socket Unix al que se conecta waypipe.

--video V

Comprime formatos DMABUF específicos utilizando un códec de video con pérdida. No se admiten formatos opacos, de 10 bits y multiplanares, entre otros. V es una lista separada por comas de opciones para controlar la codificación de video. (Por ejemplo: --video av1,hw.) Las opciones posteriores anulan las anteriores.

none

No usar codificación de video.

h264

Usar video codificado en H.264.

vp9

Usar video codificado en VP9.

av1

Usar video codificado en AV1.

sw, swenc, swdec

Usar codificación o decodificación por software, cuando esté disponible.

hw, hwenc, hwdec

Usar codificación o decodificación por hardware, cuando esté disponible.

bpf=B

Establece la tasa de bits objetivo del codificador de video, en unidades de bits por fotograma. B se puede escribir como un entero o con notación exponencial; por lo tanto, --video=bpf=7.5e5 es equivalente a --video=bpf=750000.

--vsock

Usa vsock en lugar de sockets Unix. Esto se usa cuando waypipe se ejecuta en máquinas virtuales. Con esta opción habilitada, especifica un CID y un número de puerto en S. El CID solo se usa en modo servidor y puede omitirse al conectarse desde una máquina virtual invitada al host.

--secctx S

Habilita el protocolo de contexto de seguridad Wayland (modos cliente o ssh). Especifica un ID de aplicación S que se adjuntará al contexto de seguridad.

--control C
--hwvideo
--allow-tiled

Opciones presentes en versiones anteriores de Waypipe que fueron eliminadas.

EJEMPLO

El siguiente subcomando waypipe ssh intentará ejecutar weston-flower en el servidor exserv, mostrando el resultado en el sistema local.

waypipe ssh usuario@exserv weston-flower

Se puede obtener un comportamiento similar ejecutando explícitamente waypipe y ssh:

waypipe --socket /tmp/socket-client client  &
ssh -R /tmp/socket-server:/tmp/socket-client usuario@exserv \
	waypipe --socket /tmp/socket-server server -- weston-flower

NAME

waypipe - Wayland display server proxy

SYNOPSIS

waypipe [OPTIONS] client [APPLICATION...]
waypipe [OPTIONS] server [APPLICATION...]
waypipe ssh [OPTIONS] [USER@]HOST [COMMAND...]

DESCRIPTION

waypipe is a proxy that allows one to use a Wayland display server on a remote host, or to tunnel connections between local Wayland clients and servers. It supports SSH connections, and also direct TCP and Unix domain socket connections.

When used with SSH, waypipe typically forwards the Wayland display protocol over the SSH connection. The client mode should be run on the local machine, and the server mode on the remote machine.

The server mode will start a Wayland compositor (or connect to an existing one) and accept incoming connections from waypipe clients. The client mode will connect to a waypipe server and forward the Wayland display protocol to a local Wayland compositor.

The ssh subcommand is a convenience wrapper that automates the process of setting up an SSH connection and running the waypipe server on the remote host.

OPTIONS

The following options are available:

--socket=PATH
Use the given Unix domain socket path for communication instead of SSH. This option can be used by both client and server.
-s, --listen=PORT
Listen on the given TCP port for incoming connections. This option is only applicable to the server mode.
-c, --connect=HOST:PORT
Connect to the given TCP host and port. This option is only applicable to the client mode.
--vsock
Use vsock for inter-VM communication. Requires the vsock kernel module to be loaded.
--display=DISPLAY
When running as a server, use the given Wayland display name instead of the default (wayland-0 or wayland-1). This option is also used by the client to specify which Wayland display to connect to.
--no-gpu
Do not use GPU acceleration. This disables dmabuf support and may improve security and compatibility on systems without proper GPU drivers.
--compositor=COMMAND
When running as a server, use the given command to start a Wayland compositor. If not specified, waypipe will try to start weston-simple-dmabuf-egl or weston-launch.
--remote-bin=COMMAND
When using SSH, run the specified command on the remote host instead of the default waypipe server. This can be used to set up environment variables or other pre-launch configurations.
--oneshot
For server mode: exit after the first client disconnects. This is useful for running a single application.
--verbose
Enable verbose output.
-h, --help
Show help message and exit.
-V, --version
Print version information and exit.

EXAMPLE

Run a remote application over SSH:

waypipe ssh user@remote application

Run a local Wayland compositor and connect to it:

waypipe server weston-simple-dmabuf-egl &
waypipe client --display=wayland-0

Run waypipe locally without SSH by specifying matching socket paths. For example:

waypipe --socket /tmp/waypipe.sock client &
waypipe --socket /tmp/waypipe.sock server weston-simple-dmabuf-egl
kill %1
rm /tmp/waypipe.sock

Using transports other than SSH is a bit more complicated. A recipe with ncat to connect to remote from computer local:

    $ waypipe --socket /tmp/waypipe-remote.sock client &
    $ ncat --ssl -lk 12345 --sh-exec 'ncat -U /tmp/waypipe-remote.sock' &
    $ ssh user@remote
    > ncat -lkU /tmp/waypipe-local.sock --sh-exec 'ncat --ssl local 12345' &
    > waypipe --display wayland-local \
                --socket /tmp/waypipe-local.sock server -- sleep inf &
    > WAYLAND_DISPLAY=wayland-local application

Given a certificate file, socat can also provide an encrypted connection (remove 'verify=0' to check certificates):

    $ waypipe --socket /tmp/waypipe-remote.sock client &
    $ socat openssl-listen:12345,reuseaddr,cert=certificate.pem,verify=0,fork \
        unix-connect:/tmp/waypipe-remote.sock
    $ ssh user@remote
    > socat unix-listen:/tmp/waypipe-local.sock,reuseaddr,fork \
        openssl-connect:local:12345,verify=0 &
    > waypipe --socket /tmp/waypipe-local.sock server -- application

Many applications require specific environment variables to use Wayland instead of X11. If ssh isn't configured to support loading ~/.ssh/environment, or to allow specific variables to be set with AcceptEnv/SetEnv, one can run waypipe ssh without a command (and thereby open a login shell), or use env to set the needed variables each time:

waypipe ssh user@host env XDG_SESSION_TYPE=wayland dolphin

In some cases, one may wish to set environment variables for the waypipe server process itself; the above trick with env will not do this, because the env process will be a child of waypipe server, not the other way around. Instead, one can use ~/.ssh/environment, or use the --remote-bin option to change the remote Waypipe instance to a shell script that sets the environment before running the actual waypipe program.

Running waypipe in virtual machines

When running waypipe in virtual machines on the same host it is possible to use vsock for efficient inter-vm communication. The following scenarios are supported:

•
Running applications on host from guest.
host> waypipe --vsock -s 1234 client
guest> waypipe --vsock -s 1234 server weston-terminal
•
Running applications in a guest virtual machine from host.
guest> waypipe --vsock -s 1234 client
host> waypipe --vsock -s 3:1234 server weston-terminal

In this example waypipe server connects to a virtual machine with CID 3 on port 1234.

•
Running applications in a guest virtual machine from other guest virtual machines. When running both client and server in virtual machines it is possble to enable the VMADDR_FLAG_TO_HOST flag for sibling communication by prefixing the CID with an s:
guest> waypipe --vsock -s 1234 client
guest> waypipe --vsock -s s3:1234 server weston-terminal

In this case all packets will be routed to host where they can be forwarded to another virtual machine with a vhost-device-vsock device or some other utility.

ENVIRONMENT

When running as a server, by default WAYLAND_DISPLAY will be set for the invoked process.

If the --oneshot flag is set, waypipe will instead set WAYLAND_SOCKET and inherit an already connected socketpair file descriptor to the invoked (child) process. Some programs open and close a Wayland connection repeatedly as part of their initialization, and will not work correctly with this flag.

EXIT STATUS

waypipe ssh will exit with the exit status code from the remote command, or with return code 1 if there has been an error.

SECURITY

Waypipe does not provide any strong security guarantees, and connecting to untrusted servers is not recommended. It does not filter which Wayland protocols the compositor makes available to the client (with a few exceptions for protocols that require file descriptors which Waypipe cannot yet handle). For example, if a Wayland compositor gives all its clients access to a screenshot or lock-screen protocol, then proxied clients run under Waypipe can also make screenshots or lock the screen.

In general, applications are not well tested against malicious compositors, and compositors are not well tested against malicious clients. Waypipe can connect the two, and may blindly forward denial-of-service and other attacks.

Waypipe itself is written in C and links to compression, graphics, and video libraries; both it and these libraries may have security bugs. Some risk can be avoided by building Waypipe with DMABUF support turned off, or running Waypipe with the --no-gpu flag so that it does not expose graphics libraries.

waypipe ssh has no explicit protections against timing attacks; an observer to the resulting network traffic may, by studying the size and timing of packets, learn information about the user's interaction with a Wayland client proxied through waypipe ssh. For example: a lack of activity suggests the user is not currently using the application, while an intermittant stream of messages from the compositor to the client may indicate mouse movement (or maybe something else: the contents of the messages are protected by ssh.)

The memory used by Waypipe processes may, at a given time, include Wayland messages encoding user input, and the contents of current and recent frames drawn for application windows. Swap should be encrypted to prevent this data from being leaked to disk.

BUGS

File bug reports at: https://gitlab.freedesktop.org/mstoeckl/waypipe/

Common issues

Some programs (gnome-terminal, firefox, kate, among others) have special mechanisms to ensure that only one process is running at a time. Starting those programs under Waypipe while they are running under a different Wayland compositor may silently open a window or tab in the original instance of the program. Such programs may have a command line argument to create a new instance.

The waypipe ssh command requires that the ssh executable supports Unix socket forwarding; this is only supported in OpenSSH since version 6.7 (from 2014), and may require specific configuration. Other implementations of SSH may not be able to forward Unix sockets; see the EXAMPLE section above for how to use non-SSH transports.
