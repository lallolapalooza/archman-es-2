WAIT(1P) Manual de Programador de POSIX WAIT(1P)

PRÓLOGO

Esta página del manual forma parte del Manual del Programador de POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual correspondiente de Linux para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

wait — esperar la finalización del proceso

SINOPSIS

wait [pid...]

DESCRIPCIÓN

Cuando se inicia una lista asíncrona (ver Sección 2.9.3.1, Ejemplos) por el shell, el ID del proceso del último comando de cada elemento de la lista asíncrona será conocido en el entorno de ejecución actual del shell; ver Sección 2.12, Entorno de Ejecución del Shell.

Si se invoca la utilidad wait sin operandos, esperará hasta que todos los IDs de proceso conocidos por el shell invocador hayan terminado y saldrá con un estado de salida cero.

Si se especifican uno o más operandos pid que representan IDs de proceso conocidos, la utilidad wait esperará hasta que todos ellos hayan terminado. Si se especifican uno o más operandos pid que representan IDs de proceso desconocidos, wait los tratará como si fueran IDs de proceso conocidos que salieron con estado de salida 127. El estado de salida devuelto por la utilidad wait será el estado de salida del proceso solicitado por el último operando pid.

Los IDs de proceso conocidos son aplicables solo para las invocaciones de wait en el entorno de ejecución actual del shell.

OPCIONES

Ninguna.

OPERANDOS

Se admitirá el siguiente operando:

pid
Uno de los siguientes:
1.
El entero decimal sin signo del ID de proceso de un comando, para el cual la utilidad debe esperar la terminación.
2.
Un ID de trabajo de control de trabajos (ver el volumen de Definiciones Base de POSIX.1‐2017, Sección 3.204, ID de Trabajo de Control de Trabajos) que identifica a un grupo de procesos en segundo plano al que esperar. La notación de ID de trabajo de control de trabajos solo es aplicable para invocaciones de wait en el entorno de ejecución actual del shell; ver Sección 2.12, Entorno de Ejecución del Shell. El estado de salida de wait se determinará por el último comando del pipeline.
Nota:
El tipo de ID de trabajo de control de trabajos de pid solo está disponible en sistemas que admiten la opción Utilidades de Portabilidad del Usuario.

ENTRADA ESTÁNDAR

No utilizada.

ARCHIVOS DE ENTRADA

Ninguno.

VARIABLES DE ENTORNO

Las siguientes variables de entorno afectarán la ejecución de wait:

LANG
Proporcionar un valor predeterminado para las variables de internacionalización que no están establecidas o están vacías. (Ver el volumen de Definiciones Base de POSIX.1‐2017, Sección 8.2, Variables de Internacionalización para la precedencia de las variables de internacionalización utilizadas para determinar los valores de las categorías de localización).
LC_ALL
Si se establece en un valor de cadena no vacío, anula los valores de todas las demás variables de internacionalización.
LC_CTYPE
Determinar la localización para la interpretación de secuencias de bytes de datos de texto como caracteres (por ejemplo, caracteres de un solo byte frente a multibyte en argumentos).
LC_MESSAGES

Determinar la localización que debería utilizarse para afectar el formato y el contenido de los mensajes de diagnóstico escritos en el error estándar.
NLSPATH
Determinar la ubicación de los catálogos de mensajes para el procesamiento de LC_MESSAGES.

EVENTOS ASINCRÓNICOS

Predeterminado.

SALIDA ESTÁNDAR

No utilizada.

ERROR ESTÁNDAR

El error estándar se utilizará solo para mensajes de diagnóstico.

ARCHIVOS DE SALIDA

Ninguno.

DESCRIPCIÓN EXTENDIDA

Ninguna.

ESTADO DE SALIDA

Si se especificaron uno o más operandos, todos ellos han terminado o no eran conocidos por el shell invocador, y el estado del último operando especificado se conoce, entonces el estado de salida de wait será la información del estado de salida del comando indicado por el último operando especificado. Si el proceso terminó anormalmente debido a la recepción de una señal, el estado de salida será mayor que 128 y será distinto del estado de salida generado por otras señales, pero el valor exacto no está especificado. (Ver la opción kill -l). De lo contrario, la utilidad wait saldrá con uno de los siguientes valores:

    0
La utilidad wait se invocó sin operandos y todos los IDs de proceso conocidos por el shell invocador han terminado.
1‐126
La utilidad wait detectó un error.
  127
El comando identificado por el último operando pid especificado es desconocido.

CONSECUENCIAS DE ERRORES

Predeterminado.

Las siguientes secciones son informativas.

USO DE APLICACIÓN

En la mayoría de las implementaciones, wait es un comando integrado del shell. Si se llama en una subshell o en un entorno de ejecución de utilidad separado, como uno de los siguientes:

(wait)
nohup wait ...
find . -exec wait ... \;

regresa inmediatamente porque no hay IDs de proceso conocidos a la espera en esos entornos.

Las implementaciones históricas de shells interactivos han descartado el estado de salida de los procesos terminados en segundo plano antes de cada prompt del shell. Por lo tanto, el estado de los procesos en segundo plano se perdía generalmente a menos que terminara mientras wait lo esperaba. Esto podía ser un problema grave cuando un trabajo que se esperaba que ejecutara durante mucho tiempo realmente terminaba rápidamente con un error de sintaxis o inicialización porque el estado de salida devuelto era generalmente cero si no se encontraba el ID de proceso solicitado. Este volumen de POSIX.1‐2017 requiere que la implementación mantenga el estado de los trabajos terminados disponible hasta que se solicite el estado, de modo que los scripts como:

j1&
p1=$!
j2&
wait $p1
echo El trabajo 1 salió con estado $?
wait $!
echo El trabajo 2 salió con estado $?

funcionen sin perder el estado en ninguno de los trabajos. Se permite al shell descartar el estado de cualquier proceso si determina que la aplicación no puede obtener el ID del proceso para ese proceso del shell. También se le exige que recuerde solo {CHILD_MAX} número de procesos de esta manera. Dado que la única forma de obtener el ID del proceso del shell es utilizando el parámetro del shell '!', se permite al shell descartar el estado de una lista asíncrona si "$!" no se hizo referencia antes de que se iniciara otra lista asíncrona. (Esto significa que el shell solo tiene que mantener el estado de la última lista asíncrona iniciada si la aplicación no hizo referencia a "$!". wait(1p) — Arch manual pages

PROLOG

This page is a manual page for wait (1p) from the POSIX specification.

NAME

wait

wait for processes to complete

SYNOPSIS

wait [pid...]

DESCRIPTION

The wait utility shall suspend the current shell execution until the exit status of one or more child processes is reported. The standard output and standard error shall be the same as that produced by the corresponding invocation of the system service waitpid().

If no pid arguments are specified, wait shall suspend execution until all child processes for which the calling process is a job control shell have terminated. The exit status of wait shall be the exit status of the last process reported.

If one or more pid arguments are specified, wait shall suspend execution until the child process specified by each pid argument has terminated. The exit status of wait shall be the exit status of the last process specified by a pid argument that terminated.

The wait utility is a built-in POSIX Shell command.

OPTIONS

None.

OPERANDS

The following operand shall be supported:

pid
A decimal integer representing a process ID.

STDIN

Not used.

INPUT FILES

None.

ENVIRONMENT VARIABLES

The following environment variables shall affect the execution of wait:

LANG
Provide default locale settings for the interpretation of the locale categories in the following environment variables.
LC_ALL
Override the locale settings that would be used to interpret LANG.
LC_MESSAGES
Determine the locale that should be used for the format and content of diagnostic messages written by wait.
NLSPATH
Determine the locations of message cataloges for the present locale.

ASYNCHRONOUS EVENTS

By default, wait is not affected by asynchronous events.

STDOUT

None, unless the system service waitpid() produces output.

STDERR

The standard error shall be used for diagnostic messages.

OUTPUT FILES

None.

EXTENDED DESCRIPTION

None.

EXIT STATUS

If pid arguments are specified, the exit status of wait is the exit status of the last specified process to terminate. If no pid arguments are specified, the exit status of wait is the exit status of the last process to terminate. If the process was terminated by a signal, the exit status is 128 plus the signal number.

If an error occurs, wait shall return greater than 128.

CONSEQUENCES OF ERRORS

None.

APPLICATION USAGE

The shell variable"$!" holds the process ID of the most recently executed background pipeline. This can be used to wait for a specific background job. For example:

my_command &
pid=$!
wait $pid

If the shell is a job control shell and the application is not a job control shell, the wait utility with no operands shall suspend the calling shell until all child processes of that shell have terminated. If the shell is not a job control shell, the application does not need to worry about the fact that"$!" was not saved anywhere that the application can retrieve it later, it can use this information to trim the list of saved information. Note also that a successful call to wait with no operands discards the exit status of all asynchronous lists.)

If the exit status of wait is greater than 128, there is no way for the application to know if the waited-for process exited with that value or was killed by a signal. Since most utilities exit with small values, there is seldom any ambiguity. Even in the ambiguous cases, most applications just need to know that the asynchronous job failed; it does not matter whether it detected an error and failed or was killed and did not complete its job normally.

EXAMPLES

Although the exact value used when a process is terminated by a signal is unspecified, if it is known that a signal terminated a process, a script can still reliably determine which signal by using kill as shown by the following script:

sleep 1000&
pid=$!
kill -kill $pid
wait $pid
echo $pid was terminated by a SIG$(kill -l $?) signal.

If the following sequence of commands is run in less than 31 seconds:

sleep 257 | sleep 31 &
jobs -l %%

either of the following commands returns the exit status of the second sleep in the pipeline:

wait <pid of sleep 31>
wait %%

RATIONALE

The description of wait does not refer to the waitpid() function from the System Interfaces volume of POSIX.1‐2017 because that would needlessly overspecify this interface. However, the wording means that wait is required to wait for an explicit process when it is given an argument so that the status information of other processes is not consumed. Historical implementations use the wait() function defined in the System Interfaces volume of POSIX.1‐2017 until wait() returns the requested process ID or finds that the requested process does not exist. Because this means that a shell script could not reliably get the status of all background children if a second background job was ever started before the first job finished, it is recommended that the wait utility use a method such as the functionality provided by the waitpid() function.

The ability to wait for multiple pid operands was adopted from the KornShell.

This new functionality was added because it is needed to determine the exit status of any asynchronous list accurately. The only compatibility problem that this change creates is for a script like

while sleep 60 do
    job& echo Job started $(date) as $!  done

which causes the shell to monitor all of the jobs started until the script terminates or runs out of memory. This would not be a problem if the loop did not reference "$!" or if the script would occasionally wait for jobs it started.
