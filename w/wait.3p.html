WAIT(3P) Manual de Programador POSIX WAIT(3P)

PRÓLOGO

Esta página del manual forma parte del Manual del Programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

wait, waitpid — esperar a que un proceso hijo se detenga o termine

SINOPSIS

#include <sys/wait.h>
pid_t wait(int *stat_loc);
pid_t waitpid(pid_t pid, int *stat_loc, int options);

DESCRIPCIÓN

Las funciones wait() y waitpid() obtendrán información de estado (ver Sección 2.13, Información de Estado) relacionada con uno de los procesos hijos del llamador. La función wait() obtiene información de estado de terminación de proceso de cualquier proceso hijo. La función waitpid() obtiene información de estado de terminación de proceso, y opcionalmente de detención y/o continuación de proceso, de un subconjunto especificado de los procesos hijos.

La función wait() provocará que el hilo llamante se bloquee hasta que la información de estado generada por la terminación de un proceso hijo esté disponible para el hilo, o hasta la entrega de una señal cuya acción sea ejecutar una función de captura de señales o terminar el proceso, o hasta que ocurra un error. Si la información de estado de terminación está disponible antes de la llamada a wait(), el retorno será inmediato. Si la información de estado de terminación está disponible para dos o más procesos hijos, el orden en que se informe su estado no está especificado.

Como se describe en la Sección 2.13, Información de Estado, las funciones wait() y waitpid() consumen la información de estado que obtienen.

El comportamiento cuando varios hilos están bloqueados en wait(), waitid() o waitpid() se describe en la Sección 2.13, Información de Estado.

La función waitpid() será equivalente a wait() si el argumento pid es (pid_t)-1 y el argumento options es 0. De lo contrario, su comportamiento se modificará por los valores de los argumentos pid y options.

El argumento pid especifica un conjunto de procesos hijos para los cuales se solicita el estado. La función waitpid() solo devolverá el estado de un proceso hijo de este conjunto:

*
Si pid es igual a (pid_t)-1, se solicita el estado para cualquier proceso hijo. En este aspecto, waitpid() es entonces equivalente a wait().
*
Si pid es mayor que 0, especifica el ID del proceso de un único proceso hijo para el cual se solicita el estado.
*
Si pid es 0, se solicita el estado para cualquier proceso hijo cuyo ID de grupo de procesos sea igual al del proceso llamante.
*
Si pid es menor que (pid_t)-1, se solicita el estado para cualquier proceso hijo cuyo ID de grupo de procesos sea igual al valor absoluto de pid.

El argumento options se construye a partir de la combinación OR inclusiva a nivel de bits de cero o más de las siguientes banderas, definidas en la cabecera <sys/wait.h>:

WCONTINUED
La función waitpid() informará el estado de cualquier proceso hijo continuado especificado por pid cuyo estado no haya sido informado desde que continuó de una detención de control de trabajos.
WNOHANG
La función waitpid() no suspenderá la ejecución del hilo llamante si el estado no está inmediatamente disponible para uno de los procesos hijos especificados por pid.
WUNTRACED
El estado de cualquier proceso hijo especificado por pid que esté detenido, y cuyo estado aún no haya sido informado desde que se detuvo, también se informará al proceso solicitante.

Si wait() o waitpid() regresan porque el estado de un proceso hijo está disponible, estas funciones devolverán un valor igual al ID del proceso hijo. En este caso, si el valor del argumento stat_loc no es un puntero nulo, se almacenará información en la ubicación apuntada por stat_loc. El valor almacenado en la ubicación apuntada por stat_loc será 0 si y solo si el estado devuelto proviene de un proceso hijo terminado que terminó por uno de los siguientes medios:

1.
El proceso devolvió 0 desde main().
2.
El proceso llamó a _exit() o exit() con un argumento status de 0.
3.
El proceso fue terminado porque el último hilo en el proceso terminó.

Independientemente de su valor, esta información puede ser interpretada usando las siguientes macros, que están definidas en <sys/wait.h> y evalúan a expresiones enteras; el argumento stat_val es el valor entero apuntado por stat_loc.

WIFEXITED(stat_val)

Evalúa a un valor distinto de cero si se devolvió estado para un proceso hijo que terminó normalmente.
WEXITSTATUS(stat_val)

Si el valor de WIFEXITED(stat_val) es distinto de cero, esta macro evalúa a los 8 bits inferiores del argumento status que el proceso hijo pasó a _exit() o exit(), o el valor que el proceso hijo devolvió desde main().
WIFSIGNALED(stat_val)

Evalúa a un valor distinto de cero si se devolvió estado para un proceso hijo que terminó debido a la recepción de una señal que no fue capturada (ver <signal.h>).
WTERMSIG(stat_val)

Si el valor de WIFSIGNALED(stat_val) es distinto de cero, esta macro evalúa al número de la señal que causó la terminación del proceso hijo.
WIFSTOPPED(stat_val)

Evalúa a un valor distinto de cero si se devolvió estado para un proceso hijo que está actualmente detenido.
WSTOPSIG(stat_val)

Si el valor de WIFSTOPPED(stat_val) es distinto de cero, esta macro evalúa al número de la señal que causó la detención del proceso hijo.
WIFCONTINUED(stat_val)

Evalúa a un valor distinto de cero si se devolvió estado para un proceso hijo que ha continuado de una detención de control de trabajos.

Es indeterminado si el valor status devuelto por las llamadas a wait() o waitpid() para procesos creados por posix_spawn() o posix_spawnp() puede indicar un WIFSTOPPED(stat_val) antes de que llamadas posteriores a wait() o waitpid() indiquen un WIFEXITED(stat_val) como resultado de un error detectado antes de que comience la ejecución de la nueva imagen del proceso.

Es indeterminado si el valor status devuelto por las llamadas a wait() o waitpid() para procesos creados por posix_spawn() o posix_spawnp() puede indicar un WIFSIGNALED(stat_val) si se envía una señal al grupo de procesos del padre después de que se llama a posix_spawn() o posix_spawnp().

Si la información apuntada por stat_loc fue almacenada por una llamada a waitpid() que especificó la bandera WUNTRACED y no especificó la bandera WCONTINUED, exactamente una de las macros WIFEXITED(*stat_loc), WIFSIGNALED(*stat_loc) y WIFSTOPPED(*stat_loc) evaluará a un valor distinto de cero.

Si la información apuntada por stat_loc fue almacenada por una llamada a waitpid() que especificó las banderas WUNTRACED y WCONTINUED, exactamente una de las macros WIFEXITED(*stat_loc), WIFSIGNALED(*stat_loc), WIFSTOPPED(*stat_loc) y WIFCONTINUED(*stat_loc) evaluará a un valor distinto de cero.

Si la información apuntada por stat_loc fue almacenada por una llamada a waitpid() que no especificó las banderas WUNTRACED o WCONTINUED, o por una llamada a la función wait(), exactamente una de las macros WIFEXITED(*stat_loc) y WIFSIGNALED(*stat_loc) evaluará a un valor distinto de cero.

>Si la información apuntada por stat_loc fue almacenada por una llamada a waitpid() que no especificó la bandera WUNTRACED y especificó la bandera WCONTINUED, exactamente una de las macros WIFEXITED(*stat_loc), WIFSIGNALED(*stat_loc) y WIFCONTINUED(*stat_loc) deberá evaluarse como un valor distinto de cero.

Si _POSIX_REALTIME_SIGNALS está definido, y la implementación pone en cola la señal SIGCHLD, entonces si wait() o waitpid() retornan porque el estado de un proceso hijo está disponible, cualquier señal SIGCHLD pendiente asociada con el ID del proceso hijo deberá ser descartada. Cualquier otra señal SIGCHLD pendiente permanecerá pendiente.

De lo contrario, si SIGCHLD está bloqueada, si wait() o waitpid() retornan porque el estado de un proceso hijo está disponible, cualquier señal SIGCHLD pendiente deberá ser borrada a menos que el estado de otro proceso hijo esté disponible.

Para todas las demás condiciones, no se especifica si el status del hijo estará disponible cuando se entregue una señal SIGCHLD.

Puede haber circunstancias adicionales definidas por la implementación bajo las cuales wait() o waitpid() informen del status. Esto no deberá ocurrir a menos que el proceso llamador o uno de sus procesos hijos hagan uso explícito de una extensión no estándar. En estos casos, la interpretación del status informado está definida por la implementación.

Si un proceso padre termina sin esperar a que todos sus procesos hijos terminen, los procesos hijos restantes serán asignados a un nuevo ID de proceso padre correspondiente a un proceso del sistema definido por la implementación.

VALOR DE RETORNO

Si wait() o waitpid() retornan porque el estado de un proceso hijo está disponible, estas funciones retornarán un valor igual al ID del proceso del hijo para el cual se informa el status. Si wait() o waitpid() retornan debido a la entrega de una señal al proceso llamador, se retornará -1 y errno se establecerá en [EINTR]. Si waitpid() fue invocado con WNOHANG establecido en options, tiene al menos un proceso hijo especificado por pid para el cual el status no está disponible, y el status no está disponible para ningún proceso especificado por pid, se retorna 0. De lo contrario, se retornará -1, y errno se establecerá para indicar el error.

ERRORES

La función wait() fallará si:

ECHILD
El proceso llamador no tiene procesos hijos no esperados existentes.
EINTR
La función fue interrumpida por una señal. El valor de la ubicación apuntada por stat_loc no está definido.

La función waitpid() fallará si:

ECHILD
El proceso especificado por pid no existe o no es un hijo del proceso llamador, o el grupo de procesos especificado por pid no existe o no tiene ningún miembro que sea hijo del proceso llamador.
EINTR
La función fue interrumpida por una señal. El valor de la ubicación apuntada por stat_loc no está definido.
EINVAL
El argumento options no es válido.

EJEMPLOS

Esperando un Proceso Hijo y luego Comprobando su Estado

El siguiente ejemplo demuestra el uso de waitpid(), fork(), y las macros utilizadas para interpretar el valor de estado retornado por waitpid() (y wait()). El segmento de código crea un proceso hijo que realiza un trabajo no especificado. Mientras tanto, el padre itera realizando llamadas a waitpid() para monitorear el estado del hijo. El bucle termina cuando se detecta la terminación del hijo.

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>
...
pid_t child_pid, wpid;
int status;
child_pid = fork();
if (child_pid == -1) {      /* fork() falló */
    perror("fork");
    exit(EXIT_FAILURE);
}
if (child_pid == 0) {       /* Este es el hijo */
    /* El hijo realiza un trabajo y luego termina */
    ...
} else {                    /* Este es el padre */
    do {
        wpid = waitpid(child_pid, &status, WUNTRACED
#ifdef WCONTINUED       /* No todas las implementaciones soportan esto */
        | WCONTINUED
#endif
        );
        if (wpid == -1) {
            perror("waitpid");
            exit(EXIT_FAILURE);
        }
        if (WIFEXITED(status)) {
            printf("el hijo salió, estado=%d\n", WEXITSTATUS(status));
        } else if (WIFSIGNALED(status)) {
            printf("el hijo fue asesinado (señal %d)\n", WTERMSIG(status));
        } else if (WIFSTOPPED(status)) {
            printf("el hijo se detuvo (señal %d)\n", WSTOPSIG(status));
#ifdef WIFCONTINUED     /* No todas las implementaciones soportan esto */
        } else if (WIFCONTINUED(status)) {
            printf("el hijo continuó\n");
#endif
        } else {    /* Caso no estándar -- puede que nunca ocurra */
            printf("Estado inesperado (0x%x)\n", status);
        }
    } while (!WIFEXITED(status) && !WIFSIGNALED(status));
}

Esperando un Proceso Hijo en un Manejador de Señal para SIGCHLD

El siguiente ejemplo demuestra cómo usar waitpid() en un manejador de señal para SIGCHLD sin pasar -1 como argumento pid. (Ver la sección USO DE LA APLICACIÓN más abajo para las razones por las cuales no se recomienda pasar un pid de -1.) El método utilizado aquí se basa en el comportamiento estándar de waitpid() cuando SIGCHLD está bloqueada. En sistemas históricos no conformes, el estado de algunos procesos hijos podría no ser reportado.

#include <stdlib.h>
#include <stdio.h>
#include <signal.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
#define CHILDREN 10
static void
handle_sigchld(int signum, siginfo_t *sinfo, void *unused)
{
    int sav_errno = errno;
    int status;
    /*
     * Obtener información de estado para el hijo que
     * causó la señal SIGCHLD y escribir su código de salida
     * a la salida estándar.
    */
    if (sinfo->si_code != CLD_EXITED)
    {
        static char msg[] = "código si_code incorrecto\n";
        write(2, msg, sizeof msg - 1);
    }
    else if (waitpid(sinfo->si_pid, &status, 0) == -1)
    {
        static char msg[] = "waitpid() falló\n";
        write(2, msg, sizeof msg - 1);
    }
    else if (!WIFEXITED(status))
    {
        static char msg[] = "WIFEXITED era falso\n";
        write(2, msg, sizeof msg - 1);
    }
    else
    {
        int code = WEXITSTATUS(status);
        char buf[2];
        buf[0] = '0' + code;
        buf[1] = '\n';
        write(1, buf, 2);
    }
    errno = sav_errno;
}
int
main(void)
{
    int i;
    pid_t pid;
    struct sigaction sa;
    sa.sa_flags = SA_SIGINFO;
    sa.sa_sigaction = handle_sigchld;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGCHLD, &sa, NULL) == -1)
    {
        perror("sigaction");
        exit(EXIT_FAILURE);
    }
    for (i = 0; i < CHILDREN; i++)
    {
        switch (pid = fork())
        {
        case -1:
            perror("fork");
            exit(EXIT_FAILURE);
        case 0:
            sleep(2);
            _exit(i);
        }
    }
    /* Esperar todas las señales SIGCHLD, luego terminar con SIGALRM */
    alarm(3);
    for (;;)
        pause();
    return 0; /* NO SE ALCANZA */
}

USO DE LA APLICACIÓN

Las llamadas a wait() recopilarán información sobre cualquier proceso hijo. Esto puede resultar en interacciones con otras interfaces que puedan estar esperando sus propios hijos (como el uso de system()). Por esta y otras razones, se recomienda que las aplicaciones portátiles no usen wait(), sino que usen waitpid(). Por las mismas razones, tampoco se recomienda el uso de waitpid() con un argumento pid de -1, ni el uso de waitid() con el argumento idtype establecido en P_ALL, para aplicaciones portátiles.

Como se especifica en Consecuencias de la Terminación de un Proceso, si el proceso llamador tiene SA_NOCLDWAIT establecido o tiene SIGCHLD establecido en SIG_IGN, entonces la terminación de un proceso hijo no causará que la información de estado esté disponible para un hilo bloqueado en wait(), waitid(), o waitpid(). Por lo tanto, un hilo bloqueado en una de las funciones de espera permanecerá bloqueado a menos que alguna otra condición cause que el hilo reanude la ejecución (como un fallo de [ECHILD] debido a que no quedan hijos en el conjunto de hijos esperados).

JUSTIFICACIÓN

Una llamada a la función wait() o waitpid() solo retorna status sobre un proceso hijo inmediato del proceso llamador; es decir, un hijo que fue producido por una única llamada a fork() (quizás seguida por una exec u otras llamadas a funciones) desde el padre. Si un hijo produce nietos mediante un uso posterior de fork(), ninguno de esos nietos ni ninguno de sus descendientes afecta el comportamiento de un wait() del proceso padre original. Nada en este volumen de POSIX.1‐2017 impide que una implementación proporcione extensiones que permitan a un proceso obtener status de un nieto o cualquier otro proceso, pero un proceso que no utilice tales extensiones debe tener garantizado ver status solo de sus hijos directos.

La función waitpid() se proporciona por tres razones:

1.
Para soportar el control de trabajos
2.
Para permitir una versión no bloqueante de la función wait()
3.
Para permitir que una rutina de biblioteca, como system() o pclose(), espere a sus hijos sin interferir con otros hijos terminados para los cuales el proceso no ha esperado

Las dos primeras de estas facilidades se basan en la función wait3() proporcionada por 4.3 BSD. La función usa el argumento options

ent, que es equivalente a un argumento para wait3(). La bandera WUNTRACED se usa solo en combinación con el control de trabajos en sistemas que lo soportan. Su nombre proviene de 4.3 BSD y se refiere al hecho de que existen dos tipos de procesos detenidos en esa implementación: procesos rastreados a través de la instalación de depuración ptrace() y procesos (no rastreados) detenidos por señales de control de trabajos. Dado que ptrace() no es parte de este volumen de POSIX.1-2017, solo el segundo tipo es relevante. El nombre WUNTRACED se conservó porque su uso es el mismo, aunque el nombre no es intuitivamente significativo en este contexto.

La tercera razón para la función waitpid() es permitir que secciones independientes de un proceso generen y esperen hijos sin interferir entre sí. Por ejemplo, el siguiente problema ocurre al desarrollar un shell portable o un intérprete de comandos:

stream = popen("/bin/true");
(void) system("sleep 100");
(void) pclose(stream);

En todas las implementaciones históricas, el pclose() final no logra recuperar el estado de wait() del popen().

Los valores de estado se recuperan mediante macros, en lugar de proporcionarse como codificaciones de bits específicas, como lo son en la mayoría de las implementaciones históricas (y, por lo tanto, esperadas por los programas existentes). Esto fue necesario para eliminar una limitación en el número de señales que una implementación puede admitir, que era inherente a las codificaciones tradicionales. Este volumen de POSIX.1-2017 sí requiere que un valor de estado cero corresponda a un proceso que llama a _exit(0), ya que esta es la codificación más común esperada por los programas existentes. Algunos nombres de macros se adoptaron de 4.3 BSD.

Estas macros operan sintácticamente sobre un valor entero arbitrario. El comportamiento no está definido a menos que ese valor sea uno almacenado por una llamada exitosa a wait() o waitpid() en la ubicación apuntada por el argumento stat_loc. Una propuesta temprana intentó aclarar esto especificando cada argumento como *stat_loc en lugar de stat_val. Sin embargo, eso no siguió las convenciones de otras especificaciones en este volumen de POSIX.1-2017 o el uso tradicional. También podría haber implicado que el argumento de la macro debe ser literalmente *stat_loc; de hecho, ese valor puede almacenarse o pasarse como argumento a otras funciones antes de ser interpretado por estas macros.

La extensión que afecta a wait() y waitpid() y que es común en las implementaciones históricas es la función ptrace(). Es llamada por un proceso hijo y hace que ese hijo se detenga y devuelva un estado que parece idéntico al estado indicado por WIFSTOPPED. El estado de los hijos de ptrace() se devuelve tradicionalmente independientemente de la bandera WUNTRACED (o por la función wait()). La mayoría de las aplicaciones no necesitan preocuparse por tales extensiones porque tienen control sobre qué extensiones usan ellas o sus hijos. Sin embargo, las aplicaciones, como los intérpretes de comandos, que invocan procesos arbitrarios pueden ver este comportamiento cuando esos procesos arbitrarios abusan de tales extensiones.

Las implementaciones que admiten la creación de archivos de core u otras acciones definidas por la implementación al finalizar algunos procesos proporcionan tradicionalmente un bit en el estado devuelto por wait() para indicar que tales acciones han ocurrido.

Permitir que la familia de funciones wait() descarte una señal SIGCHLD pendiente asociada con un hijo esperado exitosamente, las coloca en la categoría de sigwait() y sigwaitinfo() con respecto a SIGCHLD.

Esta definición permite que las implementaciones traten una señal SIGCHLD pendiente como aceptada por el proceso en wait(), con el mismo significado de "aceptada" que cuando esa palabra se aplica a la familia de funciones sigwait().

Permitir que la familia de funciones wait() se comporte de esta manera permite que una implementación pueda manejar precisamente las señales SIGCHLD.

En particular, una implementación que acepta (descarta) la señal SIGCHLD puede hacer las siguientes garantías independientemente de la profundidad de cola de señales en general (la lista de hijos esperables puede contener la cola SIGCHLD):

1.
Si se establece un manejador de señales SIGCHLD a través de sigaction() sin la bandera SA_RESETHAND, las señales SIGCHLD se pueden contar con precisión; es decir, se entregará o aceptará exactamente una señal SIGCHLD al proceso por cada proceso hijo que termine.
2.
Se puede garantizar que una única llamada a wait() emitida desde un manejador de señales SIGCHLD regrese inmediatamente con información de estado para un proceso hijo.
3.
Cuando se solicita SA_SIGINFO, se puede garantizar que el manejador de señales SIGCHLD reciba un puntero no nulo a una estructura siginfo_t que describe un proceso hijo para el cual una espera a través de waitpid() o waitid() no bloqueará ni fallará.
4.
La función system() no provocará que se llame al manejador de SIGCHLD de un proceso como resultado de la ejecución de fork()/exec dentro de system() porque system() aceptará la señal SIGCHLD cuando realice una waitpid() para su proceso hijo. Este es un comportamiento deseable de system() para que pueda usarse en una biblioteca sin causar efectos secundarios a la aplicación enlazada con la biblioteca.

Una implementación que no permite que la familia de funciones wait() acepte (descarte) una señal SIGCHLD pendiente asociada con un hijo esperado exitosamente, no puede hacer las garantías descritas anteriormente por las siguientes razones:

Garantía #1

Aunque se podría suponer que la cola confiable de todas las señales SIGCHLD generadas por el sistema puede hacer esta garantía, el contraejemplo es el caso de un proceso que bloquea SIGCHLD y realiza un bucle indefinido de operaciones fork()/wait(). Si la implementación admite señales en cola, el sistema eventualmente se quedará sin memoria para la cola. La garantía no se puede hacer porque debe haber algún límite para la profundidad de la cola.
Garantías #2 y #3

Estas no se pueden garantizar a menos que la familia de funciones wait() acepte la señal SIGCHLD. De lo contrario, una llamada a fork()/wait() ejecutada mientras SIGCHLD está bloqueada (como en la función system()) resultará en una invocación del manejador cuando SIGCHLD se desbloquee, después de que el proceso haya desaparecido.
Garantía #4

Aunque es posible hacer esta garantía, system() tendría que establecer el manejador SIGCHLD en SIG_DFL para que la señal SIGCHLD generada por su fork() se descarte (la acción predeterminada de SIGCHLD es ser ignorada), y luego restaurarlo a su configuración anterior. Esto tendría el efecto secundario indeseable de descartar todas las señales SIGCHLD pendientes para el proceso.

    wait(3p)

    NAME

    wait — esperar a que termine un proceso secundario

    SYNOPSIS

    #include <sys/wait.h>

    pid_t wait(int *wstatus");

    pid_t waitpid(pid_t pid, int *wstatus, int options);

    DESCRIPTION

    Las funciones wait() y waitpid() desprenden la información de estado de un proceso secundario hijo terminado. Si algún hijo ha terminado y su estado de terminación está disponible, wait() y waitpid() devuelven el ID de ese proceso hijo. Si el proceso hijo que se espera es un proceso secundario específico, su estado de terminación se almacena en la ubicación apuntada por wstatus.

    wait() espera a que termine cualquier proceso hijo del proceso de llamada. El ID del proceso hijo terminado y el valor devuelto por wait() son los mismos.

    waitpid() espera a que termine un proceso secundario específico o un grupo de procesos.

    • Si pid es mayor que 0, entonces espera solo a ese proceso hijo específico.
    • Si pid es 0, entonces espera a que termine cualquier proceso hijo en el mismo grupo de procesos que el proceso de llamada.
    • Si pid es menor que -1, entonces espera a que termine cualquier proceso hijo cuyo ID de grupo de procesos sea igual en valor absoluto al de pid.
    • Si pid es -1, entonces espera a que termine cualquier proceso hijo.

    El argumento options controla el comportamiento de la llamada a la función de la siguiente manera:

    • WNOHANG: Devuelve inmediatamente si ningún proceso hijo especificado por pid ha terminado.
    • WUNTRACED: Devuelve para hijos que han terminado o que han sido detenidos y no se han reportado todavía.

    Si wstatus es diferente de NULL, entonces el estado de salida del proceso hijo se almacena en la ubicación de memoria apuntada por wstatus. La macro WIFEXITED(wstatus) devuelve un valor verdadero si el proceso hijo terminó normalmente. La macro WEXITSTATUS(wstatus) devuelve el código de salida del proceso hijo. La macro WIFSIGNALED(wstatus) devuelve un valor verdadero si el proceso hijo terminó debido a una señal. La macro WTERMSIG(wstatus) devuelve el número de la señal que causó la terminación del proceso hijo. La macro WIFSTOPPED(wstatus) devuelve un valor verdadero si el proceso hijo fue detenido y no se ha reportado todavía. La macro WSTOPSIG(wstatus) devuelve el número de la señal que detuvo al proceso hijo.

    RETURN VALUE

    En caso de éxito, wait() y waitpid() devuelven el ID del proceso hijo terminado. Si options tiene el valor WNOHANG y ningún proceso hijo ha terminado, devuelven 0. En caso de error, devuelven -1 y establecen errno para indicar el error.

    ERRORS

    ECHILD

    El proceso de llamada no tiene ningún proceso hijo que termine, o el proceso especificado por pid no es un hijo del proceso de llamada.

    EINTR

    La llamada fue interrumpida por una señal.

    EINVAL

    Argumento options inválido.

    EXAMPLES

    Para esperar a cualquier proceso hijo:

    pid_t pid;
int status;

pid = wait(&status);
if (pid == -1) {
    perror("wait");
    exit(EXIT_FAILURE);
}

if (WIFEXITED(status)) {
    printf("Child %d terminated with exit status %d\n", pid, WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("Child %d terminated with signal %d\n", pid, WTERMSIG(status));
}

    Para esperar a un proceso hijo específico:

    pid_t pid;
int status;

pid = waitpid(child_pid, &status, 0);
if (pid == -1) {
    perror("waitpid");
    exit(EXIT_FAILURE);
}

if (WIFEXITED(status)) {
    printf("Child %d terminated with exit status %d\n", pid, WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("Child %d terminated with signal %d\n", pid, WTERMSIG(status));
}
