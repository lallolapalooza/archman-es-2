readv(2) Manual de llamadas al sistema readv(2)

NOMBRE

readv, writev, preadv, pwritev, preadv2, pwritev2 - leer o escribir datos en múltiples búferes

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/uio.h>
ssize_t readv(int fd, const struct iovec *iov, int iovcnt);
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
ssize_t preadv(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
Requisitos de macros de prueba de características para glibc (ver feature_test_macros(7)):

preadv(), pwritev():

    Desde glibc 2.19:
        _DEFAULT_SOURCE
    glibc 2.19 y anteriores:
        _BSD_SOURCE

DESCRIPCIÓN

La llamada al sistema readv() lee iovcnt búferes del archivo asociado con el descriptor de archivo fd en los búferes descritos por iov ("entrada dispersa").

La llamada al sistema writev() escribe iovcnt búferes de datos descritos por iov en el archivo asociado con el descriptor de archivo fd ("salida agrupada").

El puntero iov apunta a un array de estructuras iovec, descritas en iovec(3type).

La llamada al sistema readv() funciona igual que read(2) excepto que se llenan varios búferes.

La llamada al sistema writev() funciona igual que write(2) excepto que se escriben varios búferes.

Los búferes se procesan en orden del array. Esto significa que readv() llena completamente iov[0] antes de proceder a iov[1], y así sucesivamente. (Si hay datos insuficientes, es posible que no se llenen todos los búferes apuntados por iov). De manera similar, writev() escribe el contenido completo de iov[0] antes de proceder a iov[1], y así sucesivamente.

Las transferencias de datos realizadas por readv() y writev() son atómicas: los datos escritos por writev() se escriben como un único bloque que no se mezcla con la salida de escrituras en otros procesos; análogamente, se garantiza que readv() lee un bloque contiguo de datos del archivo, independientemente de las operaciones de lectura realizadas en otros hilos o procesos que tengan descriptores de archivo que hagan referencia a la misma descripción de archivo abierta (ver open(2)).

preadv() y pwritev()

La llamada al sistema preadv() combina la funcionalidad de readv() y pread(2). Realiza la misma tarea que readv(), pero añade un cuarto argumento, offset, que especifica la posición del archivo en la que se realizará la operación de entrada.

La llamada al sistema pwritev() combina la funcionalidad de writev() y pwrite(2). Realiza la misma tarea que writev(), pero añade un cuarto argumento, offset, que especifica la posición del archivo en la que se realizará la operación de salida.

La posición del archivo no se modifica con estas llamadas al sistema. El archivo al que se refiere fd debe ser capaz de buscar.

preadv2() y pwritev2()

Estas llamadas al sistema son similares a las llamadas preadv() y pwritev(), pero añaden un quinto argumento, flags, que modifica el comportamiento por llamada.

A diferencia de preadv() y pwritev(), si el argumento offset es -1, se utiliza la posición actual del archivo y se actualiza.

El argumento flags contiene un OR a nivel de bits de cero o más de las siguientes banderas:

RWF_DSYNC (desde Linux 4.7)
Proporciona un equivalente por escritura de la bandera O_DSYNC de open(2). Esta bandera solo tiene significado para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema.
RWF_HIPRI (desde Linux 4.6)
Lectura/escritura de alta prioridad. Permite que los sistemas de archivos basados en bloques utilicen sondeos del dispositivo, lo que proporciona menor latencia, pero puede consumir recursos adicionales. (Actualmente, esta característica solo se puede utilizar en un descriptor de archivo abierto con la bandera O_DIRECT).
RWF_SYNC (desde Linux 4.7)
Proporciona un equivalente por escritura de la bandera O_SYNC de open(2). Esta bandera solo tiene significado para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema.
RWF_NOWAIT (desde Linux 4.14)
No esperar datos que no estén inmediatamente disponibles. Si se especifica esta bandera, la llamada al sistema preadv2() devolverá instantáneamente si tuviera que leer datos del almacenamiento subyacente o esperar un bloqueo. Si se leyeron algunos datos, devolverá el número de bytes leídos. Si no se leyeron bytes, devolverá -1 y establecerá errno en EAGAIN (pero ver BUGS). Actualmente, esta bandera solo tiene significado para preadv2().
RWF_APPEND (desde Linux 4.16)
Proporciona un equivalente por escritura de la bandera O_APPEND de open(2). Esta bandera solo tiene significado para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema. El argumento offset no afecta a la operación de escritura; los datos siempre se añaden al final del archivo. Sin embargo, si el argumento offset es -1, la posición actual del archivo se actualiza.
RWF_NOAPPEND (desde Linux 6.9)
No honrar la bandera O_APPEND de open(2). Esta bandera solo tiene significado para pwritev2(). Históricamente, Linux honraba la bandera O_APPEND si estaba establecida e ignoraba el argumento offset, lo cual es un error. Para pwritev2(), el argumento offset se honra como se espera si la bandera RWF_NOAPPEND está establecida, igual que si la bandera O_APPEND no estuviera establecida.
RWF_ATOMIC (desde Linux 6.11)
Requiere que las escrituras en archivos regulares en sistemas de archivos basados en bloques se emitan con protección contra escrituras rasgadas. La protección contra escrituras rasgadas significa que, en caso de fallo de alimentación o cualquier otro fallo de hardware, se almacenarán todos los datos de la escritura o ninguno, pero nunca una mezcla de datos antiguos y nuevos. Esta bandera solo tiene significado para pwritev2(), y su efecto se aplica solo al rango de datos escrito por la llamada al sistema. La longitud total de la escritura debe ser una potencia de 2 y debe estar dimensionada en el rango [stx_atomic_write_unit_min, stx_atomic_write_unit_max]. La escritura debe estar en una posición alineada naturalmente dentro del archivo con respecto a la longitud total de la escritura. Por ejemplo, una escritura de 32KiB en una posición de archivo de 32KiB está permitida, sin embargo, una escritura de 32KiB en una posición de archivo de 48KiB no está permitida. El límite superior de iovcnt para pwritev2() se da por el valor en stx_atomic_write_segments_max. La protección contra escrituras rasgadas solo funciona con la bandera O_DIRECT, es decir, las escrituras en búfer no son compatibles. Para garantizar la coherencia desde la escritura entre el estado en memoria de un archivo y el dispositivo de almacenamiento, se deben especificar O_SYNC o O_DSYNC para open(2). Las mismas garantías de E/S sincronizadas descritas en open(2) se proporcionan cuando se utilizan estas banderas o sus banderas y llamadas al sistema equivalentes (por ejemplo, si se especifica RWF_SYNC para pwritev2()).
RWF_DONTCACHE (desde Linux 6.14)

writev(2) — Páginas del manual de Linux

NOMBRE

writev, pwritev, pwritev2 - escribir datos en un descriptor de archivo usando vectores iovec

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/uio.h>
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt, off_t offset);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt, off_t offset, int flags);

DESCRIPCION

Las llamadas al sistema writev(), pwritev() y pwritev2() son la concatenación de múltiples escrituras() en una sola operación. Escriben datos de un arreglo de estructuras iovec, donde cada estructura iovec especifica la dirección y la longitud de un buffer.

writev() escribe los datos de los buffers especificados por iov en el descriptor de archivo fd. El número de estructuras iovec a procesar se especifica en iovcnt.

pwritev() es idéntico a writev() excepto que realiza la operación de escritura en una ubicación especificada por offset en el archivo. No cambia el valor de desplazamiento del archivo.

pwritev2() es idéntico a pwritev() excepto que acepta un argumento adicional flags, que es un campo de bits para controlar el comportamiento de la operación de escritura. Los flags conocidos son:

RWF_APPEND
La escritura se realiza en la posición actual del archivo. Si el descriptor de archivo fue abierto con la bandera O_APPEND, la escritura se realiza al final del archivo. Si el descriptor de archivo no fue abierto con la bandera O_APPEND, la escritura se realiza en la posición actual del archivo. Este flag puede ser útil para la sincronización de escrituras de archivos, ya que garantiza que la escritura tenga lugar en la posición actual, sin importar el valor del desplazamiento de archivo, si el descriptor de archivo fue abierto con la bandera O_APPEND.
RWF_DATACACHE
Este flag sugiere al kernel que evite que los datos escritos permanezcan en la caché de páginas después de que la operación de escritura se complete. Esto puede ser útil para grandes escrituras de archivos donde no se espera que los datos vuelvan a ser leídos pronto, o para prevenir la contaminación de la caché de páginas con datos que solo se escriben una vez.
RWF_DSYNC
Este flag requiere que la operación de escritura sea una escritura síncrona de datos. La operación no se completará hasta que los datos y la información de dirección se hayan escrito en el medio de almacenamiento.
RWF_HIPRI
Este flag sugiere al kernel que priorice la operación de escritura. Esto puede ser útil para aplicaciones que necesitan escribir datos rápidamente, como bases de datos o sistemas de archivos en tiempo real.
RWF_NOWAIT
Este flag indica que la operación de escritura debe ser no bloqueante. Si la escritura no se puede completar inmediatamente, la llamada al sistema regresará inmediatamente con un error EAGAIN.
RWF_SYNC
Este flag requiere que la operación de escritura sea una escritura síncrona. La operación no se completará hasta que los datos y la información de dirección se hayan escrito en el medio de almacenamiento. Esto es similar a RWF_DSYNC, pero también garantiza que los metadatos de la escritura se escriban en el disco.
RWF_DONTCACHE
Las operaciones de lectura o escritura en un archivo regular con la bandera RWF_DONTCACHE establecida podarán el contenido de la caché de páginas instanciado cuando la operación se complete. Esto es diferente a la E/S de búfer normal, donde los datos generalmente permanecen en la caché hasta que se recuperan debido a la presión de memoria. Si rangos de la E/S de lectura o escritura ya estaban en la caché antes de esta lectura o escritura, entonces esos rangos no se podarán en el momento de la finalización de la E/S.
Adicionalmente, cualquier rango ennegrecido por una operación de escritura con RWF_DONTCACHE establecido será enviado para escritura. Esto es similar a llamar a sync_file_range(2) con SYNC_FILE_RANGE_WRITE para iniciar la escritura en el rango dado. RWF_DONTCACHE es una indicación, o mejor esfuerzo, donde no se dan garantías sólidas sobre el estado de la caché de páginas una vez que la operación se completa.
Si se usa en un sistema de archivos o dispositivo de bloques que no lo soporta, devolverá -1, y errno se establecerá en EOPNOTSUPP.

VALOR DE RETORNO

En caso de éxito, readv(), preadv(), y preadv2() devuelven el número de bytes leídos; writev(), pwritev(), y pwritev2() devuelven el número de bytes escritos.

Tenga en cuenta que no es un error para una llamada exitosa transferir menos bytes de los solicitados (ver read(2) y write(2)).

En caso de error, se devuelve -1, y errno se establece para indicar el error.

ERRORES

Los errores son los dados para read(2) y write(2). Además, preadv(), preadv2(), pwritev(), y pwritev2() también pueden fallar por las mismas razones que lseek(2). Adicionalmente, se definen los siguientes errores:

EINVAL
La suma de los valores iov_len se desborda en un valor ssize_t.
EINVAL
Si se especifica RWF_ATOMIC, la combinación de la suma de los valores iov_len y el valor offset no cumple con las reglas de protección contra escrituras fragmentadas de longitud y desplazamiento.
EINVAL
El recuento del vector, iovcnt, es menor que cero o mayor que el máximo permitido. Si se especifica RWF_ATOMIC, este máximo se da por el valor stx_atomic_write_segments_max de statx.
EOPNOTSUPP
Se estableció RWF_DONTCACHE en flags y el archivo no lo soporta.
EOPNOTSUPP
Se especifica un flag desconocido en flags.

VERSIONES

Diferencias biblioteca C/kernel

Las llamadas al sistema preadv() y pwritev() en bruto tienen firmas de llamada que difieren ligeramente de las de las funciones de envoltura correspondientes de la biblioteca C de GNU que se muestran en la SINOPSIS. El argumento final, offset, es desempaquetado por las funciones de envoltura en dos argumentos en las llamadas al sistema:

unsigned long pos_l, unsigned long pos

Estos argumentos contienen, respectivamente, los 32 bits de orden bajo y de orden alto de offset.

Diferencias históricas biblioteca C/kernel

Para hacer frente al hecho de que IOV_MAX era tan bajo en las primeras versiones de Linux, las funciones de envoltura de glibc para readv() y writev() hicieron un trabajo adicional si detectaban que la llamada al sistema subyacente fallaba porque se excedía este límite. En el caso de readv(), la función de envoltura asignó un buffer temporal lo suficientemente grande para todos los elementos especificados por iov, pasó ese buffer en una llamada a read(2), copió datos del buffer a las ubicaciones especificadas por los campos iov_base de los elementos de iov, y luego liberó el buffer. La función de envoltura para writev() realizó la tarea análoga usando un buffer temporal y una llamada a write(2).

La necesidad de este esfuerzo adicional en las funciones de envoltura de glibc desapareció con Linux 2.2 y posteriores. Sin embargo, glibc continuó proporcionando este comportamiento hasta glibc 2.10. A partir de glibc 2.9, las funciones de envoltura solo proporcionan este comportamiento si la biblioteca detecta que el sistema está ejecutando un kernel de Linux anterior a Linux 2.6.18 (una versión de kernel seleccionada arbitrariamente). Y desde glibc 2.20 (que requiere un mínimo de Linux 2.6.32), las funciones de envoltura de glibc siempre invocan directamente las llamadas al sistema.

NOTAS

POSIX.1 permite a una implementación establecer un límite en el número de elementos que se pueden pasar en iov. Una implementación puede anunciar su límite definiendo IOV_MAX en <limits.h> o en tiempo de ejecución a través del valor de retorno de sysconf(_SC_IOV_MAX). En los sistemas modernos de Linux, el límite es 1024. En los días de Linux 2.0, este límite era 16.

BUGS

Linux 5.9 y Linux 5.10 tienen un error donde preadv2() con el flag RWF_NOWAIT puede devolver 0 incluso cuando no está al final del archivo.

EJEMPLOS

El siguiente ejemplo de código demuestra el uso de writev():


char          *str0 = "hello ";
char          *str1 = "world\n";
ssize_t       nwritten;
struct iovec  iov[2];
iov[0].iov_base = str0;
iov[0].iov_len = strlen(str0);
iov[1].iov_base = str1;
iov[1].iov_len = strlen(str1);
nwritten = writev(STDOUT_FILENO, iov, 2);
