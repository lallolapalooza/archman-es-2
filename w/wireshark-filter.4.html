Macros

Es posible definir macros de filtro de visualización. Las macros son nombres que se reemplazan con la expresión asociada, realizando posiblemente sustitución de argumentos. Las expansiones de macros son reemplazos puramente textuales y se realizan recursivamente antes de la compilación. Permiten reemplazar expresiones largas y de uso frecuente con nombres fáciles de usar.

Las macros se definen utilizando la GUI o directamente en el archivo de configuración "dmacros". Por ejemplo, la definición

"addplusone" {$1 + $2 + 1}

crea una macro llamada addplusone que toma dos argumentos y se expande a la expresión dada. Los argumentos en la expresión de reemplazo se proporcionan usando el signo de dólar.

Las macros se invocan como funciones pero precedidas por un signo de dólar (a veces también llamado sigilo):

$addplusone(udp.src_port,udp.dst_port)

resulta en la expresión

{udp.src_port + udp.dst_port + 1}

después de la sustitución de argumentos. Existe una notación alternativa más antigua para invocar macros:

${addplusone:udp.src_port;udp.dst_port}

o

${addplusone;udp.src_port;udp.dst_port}

Ambas formas son equivalentes y se pueden usar indistintamente por preferencia.

Un entero puede expresarse en notación decimal, octal, hexadecimal o binaria, o como una constante de carácter estilo C. Los siguientes siete filtros de visualización son equivalentes:

frame.len > 10
frame.len > 012
frame.len > 0xa
frame.len > 0b1010
frame.len > '\n'
frame.len > '\x0a'
frame.len > '\012'

Los valores booleanos son `true` o `false`. En una expresión de filtro de visualización que prueba el valor de un campo booleano, `true` se expresa como la palabra true (sin distinción de mayúsculas y minúsculas) o cualquier número distinto de cero. `False` se expresa como false (sin distinción de mayúsculas y minúsculas) o el número cero. Por ejemplo, el campo de ruta de origen de un paquete token-ring es booleano. Para encontrar paquetes con ruta de origen, un filtro de visualización sería cualquiera de los siguientes:

tr.sr == 1
tr.sr == true
tr.sr == TRUE

Los paquetes sin ruta de origen se pueden encontrar con:

tr.sr == 0
tr.sr == false
tr.sr == FALSE

Las direcciones Ethernet y las matrices de bytes se representan con dígitos hexadecimales. Los dígitos hexadecimales pueden separarse con dos puntos, puntos o guiones:

eth.dst eq ff:ff:ff:ff:ff:ff
aim.data == 0.1.0.d
fddi.src == aa-aa-aa-aa-aa-aa
echo.data == 7a

Las direcciones IPv4 pueden representarse en notación decimal con puntos o utilizando el nombre de host:

ip.src == 192.168.1.1
ip.dst eq www.mit.edu

Las direcciones IPv4 se pueden comparar con las mismas relaciones lógicas que los números: `eq`, `ne`, `gt`, `ge`, `lt` y `le`. La dirección IPv4 se almacena en orden de host, por lo que no tiene que preocuparse por la endianidad de una dirección IPv4 al usarla en un filtro de visualización.

La notación Classless Inter-Domain Routing (CIDR) se puede utilizar para comprobar si una dirección IPv4 se encuentra en una subred determinada. Por ejemplo, este filtro de visualización encontrará todos los paquetes de la red 129.111:

ip.addr == 129.111.0.0/16

Recuerde, el número después de la barra representa el número de bits utilizados para representar la red. La notación CIDR también se puede usar con nombres de host, como en este ejemplo de búsqueda de direcciones IP en la misma red que 'sneezy' (requiere que 'sneezy' se resuelva a una dirección IP para que el filtro sea válido):

ip.addr eq sneezy/24

La notación CIDR solo se puede usar en direcciones IP o nombres de host, no en nombres de variables. Por lo tanto, un filtro de visualización como "ip.src/24 == ip.dst/24" no es válido (todavía).

Los identificadores de transacción y otros a menudo se representan como enteros de 16 o 32 bits sin signo y se formatean como una cadena hexadecimal con prefijo "0x":

(dhcp.id == 0xfe089c15) || (ip.id == 0x0373)

Las cadenas se encierran entre comillas dobles:

http.request.method == "POST"

Dentro de las comillas dobles, puede usar una barra invertida para incrustar una comilla doble o un byte arbitrario representado en notación octal o hexadecimal.

browser.comment == "Una comilla doble incrustada \""

Uso de hexadecimal para buscar "HEAD":

http.request.method == "\x48EAD"

Uso de octal para buscar "HEAD":

http.request.method == "\110EAD"

Esto significa que debe escapar las barras invertidas con barras invertidas dentro de las comillas dobles.

smb.path contains "\\\\SERVER\\SHARE"

busca `\\SERVER\SHARE` en "smb.path". Esto puede escribirse de manera más conveniente como

smb.path contains r"\\SERVER\SHARE"

Las cadenas literales prefijadas con 'r' se denominan "cadenas raw". Dichas cadenas tratan la barra invertida como un carácter literal. Las comillas dobles aún pueden escaparse con una barra invertida, pero tenga en cuenta que las barras invertidas siempre se conservan en el resultado.

Los valores de fecha y hora se pueden proporcionar en formato ISO 8601 o utilizando un formato heredado de mes-año-hora:

"2020-07-04T12:34:56"
"Sep 26, 2004 23:18:04.954975"

El separador 'T' en ISO 8601 se puede omitir. La zona horaria se puede indicar como "Z" o un desplazamiento de UTC.

Cuando no se utiliza ISO 8601, la zona horaria se puede indicar como las cadenas "UTC", "GMT" o "UT" para UTC o también se puede indicar como un desplazamiento de UTC, además de algunas designaciones norteamericanas y náuticas/militares (consulte la especificación de %z en strptime(3) https://man.netbsd.org/strptime.3). Tenga en cuenta que los nombres arbitrarios de zona horaria no son compatibles.

Si se omite la zona horaria, los valores de fecha y hora se interpretan como hora local.

El operador de slice

Puede tomar una porción (slice) de un campo si el tipo base del campo es una cadena de texto o una matriz de bytes (el tipo base de la mayoría de los campos de direcciones de red son bytes). Por ejemplo, puede filtrar por la porción del proveedor de una dirección ethernet (los primeros tres bytes) de esta manera:

eth.src[0:3] == 00:00:83

Otro ejemplo es:

http.content_type[0:4] == "text"

También puede usar el operador de slice en un nombre de protocolo. El protocolo "frame" puede ser útil, abarcando todos los datos capturados por Wireshark o TShark.

token[0:5] ne 0.0.0.1.1
llc[0] eq aa
frame[100-199] contains "wireshark"

La siguiente sintaxis rige los slices:

[i:j]    i = offset_inicio, j = longitud
[i-j]    i = offset_inicio, j = offset_fin, inclusivo.
[i]      i = offset_inicio, longitud = 1
[:j]     offset_inicio = 0, longitud = j
[i:]     offset_inicio = i, offset_fin = fin_del_campo

Los índices de slice están basados en cero. Los offsets pueden ser negativos, en cuyo caso indican el offset desde el **final** del campo. El último byte del campo está en el offset -1, el penúltimo byte está en el offset -2, y así sucesivamente. Así es como se comprueban los últimos cuatro bytes de una trama:

frame[-4:4] == 0.1.2.3

o

frame[-4:] == 0.1.2.3

Como se mencionó anteriormente, el operador de slice se puede usar en campos de cadena y bytes y producirá respectivamente slices de cadena o de bytes. Los slices de cadena se indexan en los límites de puntos de código UTF-8 (es decir, caracteres internacionalizados), por lo que la siguiente comparación es verdadera:

"touché"[5] == "é"

El ejemplo anterior genera un error porque el compilador rechaza expresiones constantes, pero por lo demás es sintácticamente correcto y ejemplifica el comportamiento de los slices de cadena.

Para obtener un slice de bytes de la misma cadena, se puede usar el operador raw (@):

@"touché"[5-6] == c3:a9

Un slice siempre se puede comparar con una cadena o una secuencia de bytes.

Las rebanadas se pueden combinar.

Puede concatenarlas usando el operador coma:

ftp[1,3-5,9:] == 01:03:04:05:09:0a:0b

Esto concatena el desplazamiento 1, los desplazamientos 3-5, y el desplazamiento 9 hasta el final de los datos ftp.

El operador de capa

Un campo puede ser restringido a una determinada capa en la pila de protocolos usando el operador de capa (#), seguido de un número decimal:

ip.addr#2 == 192.168.30.40

solo coincide con la capa interna (segunda) en el paquete. Las capas usan semántica de apilamiento simple y las capas de protocolo se cuentan secuencialmente a partir de 1. Por ejemplo, en un paquete que contiene dos encabezados IPv4, la dirección de origen externa (primera) se puede comparar con "ip.src#1" y la dirección de origen interna (segunda) se puede comparar con "ip.src#2".

Para rangos más complicados, la misma sintaxis utilizada con las rebanadas es válida:

tcp.port#[2-4]

significa capas número 2, 3 o 4 inclusive. El símbolo de almohadilla es necesario para distinguir un rango de capa de una rebanada.

El operador @

Al prefijar el nombre del campo con un signo arroba (@), la comparación se realiza contra los datos sin procesar del paquete para ese campo.

Una cadena de caracteres debe ser decodificada desde una codificación de origen durante el análisis. Si hay errores de decodificación, la cadena resultante generalmente contendrá caracteres de reemplazo:

browser.comment == "string is ����"

El operador @ permite probar los datos sin procesar y sin decodificar:

@browser.comment == 73:73:72:69:6e:67:20:69:73:20:aa:aa:aa:aa

Las reglas sintácticas para un tipo de campo de bytes se aplican al segundo ejemplo.

El operador de pertenencia

Un campo puede ser verificado para coincidencias contra un conjunto de valores simplemente con el operador de pertenencia. Por ejemplo, puede encontrar tráfico en puertos HTTP/HTTPS comunes con el siguiente filtro:

tcp.port in {80,443,8080}

en contraposición a lo más verboso:

tcp.port == 80 or tcp.port == 443 or tcp.port == 8080

Para encontrar solicitudes HTTP usando los métodos HEAD o GET:

http.request.method in {"HEAD", "GET"}

El conjunto de valores también puede contener rangos:

tcp.port in {443, 4430..4434}
ip.addr in {10.0.0.5 .. 10.0.0.9, 192.168.1.1..192.168.1.9}
frame.time_delta in {10 .. 10.5}

Conversiones implícitas de tipo

Cuando los campos que son secuencias de bytes, incluidos los protocolos, se comparan con literales de cadena (entre comillas dobles) y cadenas sin procesar, los literales se convierten a su representación de bytes usando la codificación UTF-8. (Para ser precisos, se utiliza la secuencia de bytes original, no las formas normalizadas canónicas, por lo que la precompuesta é (U+00E9) y la descompuesta é (U+0065 U+0301) pueden coincidir de manera diferente).

Así, por ejemplo, los siguientes filtros son equivalentes:

tcp.payload contains "GET"
tcp.payload contains 47.45.54

Como se señaló anteriormente, una rebanada también se puede comparar de una forma u otra:

frame[60:2] gt 50.51
frame[60:2] gt "PQ"

Lo inverso no ocurre; los campos similares a cadenas no se convierten implícitamente en arreglos de bytes. (Algunos operadores permiten comparar campos similares a cadenas con literales sin comillas, que luego se tratan como cadenas; esto está obsoleto en general y específicamente prohibido por el operador "matches". Los literales de cadena deben ir entre comillas dobles para mayor claridad).

Un entero hexadecimal que sea 0xff o menos (lo que significa que cabe en un solo byte) puede convertirse implícitamente en una cadena de bytes. Esto no está permitido para enteros hexadecimales de más de un byte, porque entonces se necesitaría especificar la endianidad del entero de varios bytes. Además, esto no está permitido para números decimales u octales, ya que se confundirían con los números hexadecimales que componen los literales de cadena de bytes. Sin embargo, los enteros hexadecimales de un solo byte pueden ser convenientes:

frame[4] == 0xff
frame[1:4] contains 0x02

Un campo entero o booleano que tenga una cadena de valor puede compararse con una de las cadenas que corresponde a un valor. Al igual que con los campos similares a cadenas y las comparaciones, es posible realizar la comparación con un literal sin comillas, aunque esto está obsoleto y no funcionará si el literal contiene un espacio (como en "Modify Bearer Response" anteriormente). Se recomiendan las comillas dobles.

Si existe una correspondencia inversa única del literal de cadena a un valor numérico, la cadena se convierte en ese número y la función de comparación se aplica utilizando reglas aritméticas. Si la correspondencia no es única, entonces se pueden probar las igualdades e desigualdades, pero no las comparaciones ordenadas.

Esto contrasta con las funciones string() y vals(), que convierten el valor del campo a una cadena y aplican comparaciones de cadenas (lexicográficas), además de funcionar con todos los operadores que toman cadenas. Por lo tanto, los siguientes dos filtros dan el mismo resultado:

gtpv2.message_type <= 35
gtpv2.message_type <= "Modify Bearer Response"

mientras que

vals(gtpv2.message_type) <= "Modify Bearer Response"

coincide con todos los mensajes cuyo valor de cadena precede a "Modify Bearer Response" en orden lexicográfico, y

string(gtpv2.message_type) <= "35"

coincide con todos los mensajes tales que el tipo de mensaje precede a "35" en orden lexicográfico, es decir, también coincidiría con "170" (el tipo de mensaje para "Release Access Bearers Request.").

Para los operadores "contains" y "matches", que operan sobre cadenas (o arreglos de bytes en el caso de "contains"), los campos en el lado izquierdo se convierten implícitamente a sus cadenas de valor para la comparación. (Para comparar un campo con un arreglo de bytes, use el operador raw/at (@)).

Operadores bit a bit

También es posible definir pruebas con operaciones bit a bit. Actualmente, se admite el siguiente operador bit a bit:

bitand, bitwise_and, & Bitwise AND

La operación AND bit a bit permite enmascarar bits y verificar si uno o más bits están establecidos. AND bit a bit opera en campos de protocolo enteros y rebanadas.

Al buscar paquetes TCP SYN, puede escribir:

tcp.flags & 0x02

Esa expresión coincidirá con todos los paquetes que contengan un campo "tcp.flags" con el bit 0x02, es decir, el bit SYN, establecido.

Para encontrar direcciones Ethernet unicast administradas localmente, puede usar:

eth.addr[0] & 0x0f == 2

Al usar rebanadas, la máscara de bits debe especificarse como una cadena de bytes, y debe tener el mismo número de bytes que la propia rebanada, como en:

ip[42:2] & 40:ff

Operadores aritméticos

Se admiten expresiones aritméticas con los operadores habituales:

+ Suma
- Resta
* Multiplicación
/ División
% Módulo (resto entero)

Las operaciones aritméticas se pueden realizar en tipos numéricos. Los tipos numéricos son enteros, números de punto flotante y valores de fecha y hora.

Los valores de fecha y hora solo se pueden multiplicar por enteros o números de punto flotante (es decir: escalares) y, además, el multiplicador escalar debe aparecer en el lado derecho de la operación aritmética.

Por ejemplo, es posible filtrar por puertos de destino UDP mayores o iguales a uno respecto al puerto de origen con la expresión:

udp.dstport >= udp.srcport + 1

Es posible agrupar expresiones aritméticas usando llaves (los paréntesis no funcionarán para esto):

tcp.dstport >= 4 * {tcp.srcport + 3}

No confunda este uso de llaves con la pertenencia a conjuntos.

Una peculiaridad desafortunada en la sintaxis del filtro es que el operador de resta debe ir precedido de un espacio en blanco, por lo que "A-B" debe escribirse como "A -B" o "A - B".

Referencias a campos de protocolo

Una variable que utiliza un sigilo con la forma $some.proto.field o ${some.proto.field} se denomina referencia de campo. Una referencia de campo es un valor de campo leído del marco actualmente seleccionado en la GUI. Esto es útil para crear filtros dinámicos como, por ejemplo, marcos de los últimos cinco minutos al marco seleccionado:

frame.time_relative >= ${frame.time_relative} - 300

o más simplemente

frame.time_relative >= $frame.time_relative - 300

Las referencias de campo comparten una notación similar a las macros, pero son elementos sintácticos distintos en el lenguaje de filtros.

Expresiones lógicas

Las pruebas se pueden combinar utilizando expresiones lógicas. Estas también se pueden expresar en sintaxis similar a C o con abreviaturas similares a inglés. La siguiente tabla enumera los operadores lógicos de mayor a menor precedencia:

not, ! NOT lógico (asociativo a la derecha)
and, && AND lógico (asociativo a la izquierda)
xor, ^^ XOR lógico (asociativo a la izquierda)
or,  || OR lógico (asociativo a la izquierda)

La evaluación se realiza siempre de izquierda a derecha. Las expresiones también se pueden agrupar con paréntesis. La expresión "A and B or not C or D and not E or F" se lee:

(A and B) or (not C) or (D and (not E)) or F

Generalmente es mejor ser explícito sobre la agrupación usando paréntesis. Las siguientes son todas expresiones de filtro de visualización válidas:

tcp.port == 80 and ip.src == 192.168.2.1
not llc
http and frame[100-199] contains "w

NAME

wireshark-filter — Wireshark display filter syntax

SYNOPSIS

wireshark -R " filter " [file...]

tshark -R " filter " [file...]

DESCRIPTION

Display filters are used to select which packets to view in Wireshark or tshark. They are similar to capture filters in syntax but are applied after the packets have been captured. This man page describes the syntax of Wireshark display filters.

Display filters use a syntax that allows you to match packets based on protocol fields. The basic syntax is:

protocol.field operator value

For example, to display all TCP packets to port 80, you would use:

tcp.port == 80

To display all IP packets from the address 192.168.1.1, you would use:

ip.src == 192.168.1.1

You can combine multiple filter expressions using logical operators such as "and", "or", and "not".

tcp.port == 80 and ip.src == 192.168.1.1

Parentheses can be used to group expressions.

(tcp.port == 80 or udp.port == 53) and ip.src == 192.168.1.1

FILTER SYNTAX

The display filter syntax is defined by Wireshark's filter engine. It supports a wide range of protocols and fields. The syntax includes:

  • Protocol names (e.g., ip, tcp, http)
  • Field names (e.g., ip.src, tcp.flags, http.request.method)
  • Values can be numbers, strings, or IP addresses.
  • Operators:
    • Comparison: ==, !=, <, <=, >, >=
    • Bitwise: &, |, ^, ~
    • Logical: and, or, not
    • Membership: in, contains, matches (for regular expressions)
  • Parentheses for grouping.

The following examples illustrate some common filter expressions:

ip.addr == 192.168.1.1
tcp.flags.syn == 1
http.request.uri contains "/login"
!(arp or icmp)
frame contains "GET / HTTP/1.0"
ip.src matches "^192\.168\."

Remember that whenever a protocol or field name occurs in an expression, the "exists" operator is implicitly called. The "exists" operator has the highest priority. This means that the first filter expression must be read as "show me the packets for which tcp.port exists and equals 80, and ip.src exists and equals 192.168.2.1". The second filter expression means "show me the packets where not exists llc", or in other words "where llc does not exist" and hence will match all packets that do not contain the llc protocol. The third filter expression includes the constraint that offset 199 in the frame exists, in other words the length of the frame is at least 200.

Because each comparison has an implicit exists test for field values care must be taken when using the display filter to remove noise from the packet trace. If, for example, you want to filter out all IP multicast packets to address 224.1.2.3, then using:

ip.dst ne 224.1.2.3

may be too restrictive. This is the same as writing:

ip.dst and ip.dst ne 224.1.2.3

The filter selects only frames that have the "ip.dst" field. Any other frames, including all non-IP packets, will not be displayed. To display the non-IP packets as well, you can use one of the following two expressions:

not ip.dst or ip.dst ne 224.1.2.3
not ip.dst eq 224.1.2.3

The first filter uses "not ip.dst" to include all non-IP packets and then lets "ip.dst ne 224.1.2.3" filter out the unwanted IP packets. The second filter also negates the implicit existence test and so is a shorter way to write the first.
