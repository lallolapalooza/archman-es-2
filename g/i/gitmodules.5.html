NOMBRE

gitmodules - Definición de propiedades de submodules

SINOPSIS

$GIT_WORK_TREE/.gitmodules

DESCRIPCIÓN

El archivo .gitmodules, ubicado en el directorio raíz de un árbol de trabajo de Git, es un archivo de texto con una sintaxis que coincide con los requisitos de git-config(1).

El archivo contiene una subsección por submodule, y el valor de la subsección es el nombre del submodule. El nombre se establece en la ruta donde se agregó el submodule, a menos que se personalizara con la opción --name de git submodule add. Cada sección de submodule contiene también las siguientes claves requeridas:

submodule.<nombre>.path

Define la ruta, relativa al directorio raíz del árbol de trabajo de Git, donde se espera que se extraiga el submodule. El nombre de la ruta no debe terminar en /. Todas las rutas de submodules deben ser únicas dentro del archivo .gitmodules.

submodule.<nombre>.url

Define una URL desde la cual se puede clonar el repositorio del submodule. Puede ser una URL absoluta lista para pasar a git-clone(1) o (si comienza con ./ o ../) una ubicación relativa al repositorio de origen del superproyecto.

Además, hay una serie de claves opcionales:

submodule.<nombre>.update

Define el procedimiento de actualización predeterminado para el submodule nombrado, es decir, cómo se actualiza el submodule mediante el comando git submodule update en el superproyecto. Esto solo es utilizado por git submodule init para inicializar la variable de configuración del mismo nombre. Los valores permitidos aquí son checkout, rebase, merge o none, pero no !command (por razones de seguridad). Consulte la descripción del comando update en git-submodule(1) para más detalles.

submodule.<nombre>.branch

Un nombre de rama remota para rastrear actualizaciones en el submodule ascendente. Si la opción no se especifica, se utiliza el valor por defecto del HEAD remoto. Se utiliza un valor especial de . para indicar que el nombre de la rama en el submodule debe ser el mismo que el nombre de la rama actual en el repositorio actual. Consulte la documentación de --remote en git-submodule(1) para obtener detalles.

submodule.<nombre>.fetchRecurseSubmodules

Esta opción se puede utilizar para controlar la obtención recursiva de este submodule. Si esta opción también está presente en la entrada del submodule en .git/config del superproyecto, la configuración allí anulará la que se encuentra en .gitmodules. Ambas configuraciones pueden ser anuladas en la línea de comandos utilizando la opción --[no-]recurse-submodules para git fetch y git pull.

submodule.<nombre>.ignore

Define bajo qué circunstancias git status y la familia de diff muestran un submodule como modificado. Los siguientes valores son compatibles:

all

El submodule nunca se considerará modificado (pero aun así aparecerá en la salida de estado y commit cuando haya sido preparado).

dirty

Se ignorarán todos los cambios en el árbol de trabajo del submodule; solo se tendrán en cuenta las diferencias confirmadas entre el HEAD del submodule y su estado registrado en el superproyecto.

untracked

Solo se ignorarán los archivos no rastreados en los submodules. Las diferencias confirmadas y las modificaciones en archivos rastreados se mostrarán.

none

No se ignora ninguna modificación en los submodules; se muestran todas las diferencias confirmadas y las modificaciones en archivos rastreados y no rastreados. Esta es la opción predeterminada.

Si esta opción también está presente en la entrada del submodule en .git/config del superproyecto, la configuración allí anulará la que se encuentra en .gitmodules.

Ambas configuraciones pueden ser anuladas en la línea de comandos utilizando la opción --ignore-submodules. Los comandos git submodule no se ven afectados por esta configuración.

submodule.<nombre>.shallow

Cuando se establece en true, se realizará una clonación de este submodule como una clonación superficial (con una profundidad de historial de 1) a menos que el usuario solicite explícitamente una clonación no superficial.

NOTAS

Git no permite que el archivo .gitmodules dentro de un árbol de trabajo sea un enlace simbólico, y se negará a extraer una entrada de árbol de este tipo. Esto mantiene la coherencia del comportamiento cuando se accede al archivo desde el índice o un árbol en comparación con el sistema de archivos, y ayuda a Git a aplicar de manera confiable las verificaciones de seguridad del contenido del archivo.

EJEMPLOS

Considere el siguiente archivo .gitmodules:

[submodule "libfoo"]
        path = include/foo
        url = git://foo.com/git/lib.git
[submodule "libbar"]
        path = include/bar
        url = git://bar.com/git/lib.git

Esto define dos submodules, libfoo y libbar. Se espera que se extraigan en las rutas include/foo y include/bar, y para ambos submodules se especifica una URL que se puede utilizar para clonar los submodules.
