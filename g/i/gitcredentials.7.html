HELPERS

PERSONALIZADOS

Puede escribir sus propios helpers personalizados para interactuar con cualquier sistema en el que almacene sus

credenciales.

Los helpers de credenciales son programas ejecutados por Git para obtener o guardar credenciales en y desde almacenamiento a largo plazo (donde "a largo plazo" es simplemente más largo que un solo proceso de Git; por ejemplo, las credenciales pueden almacenarse en memoria durante unos minutos, o indefinidamente en disco)

.

Cada helper se especifica mediante una sola cadena en la variable de configuración credential.helper (y otras, ver git-config(1)). Git transforma la cadena en un comando a ejecutar usando estas

reglas:
1.Si la cadena del helper comienza con "!", se considera un fragmento de shell, y todo lo que sigue al "!" se convierte en el
comando.
2.De lo contrario, si la cadena del helper comienza con una ruta absoluta, la cadena del helper literal se convierte en el
comando.
3.De lo contrario, se antepone la cadena "git credential-" a la cadena del helper, y el resultado se convierte en el
comando.

Al comando resultante se le añade un argumento de "operación" (ver más abajo para detalles), y el resultado es ejecutado por el

shell.

Aquí hay algunas especificaciones de

ejemplo: 
# ejecutar "git credential-foo"
[credential]
        helper = foo
# igual que lo anterior, pero pasar un argumento al helper
[credential]
        helper = "foo --bar=baz"
# los argumentos son analizados por el shell, así que use
# comillas de shell si es necesario
[credential]
        helper = "foo --bar='whitespace arg
'" # helper de almacenamiento (desaconsejado) con ubicación personalizada para el archivo db; # use `--file ~/.git-secret.txt`, en lugar de `--file=~/.git-secret.txt`, # para permitir que el shell expanda el tilde al directorio home. [credential] helper = "store --file ~/.git-secret.txt" # también puede usar una
ruta absoluta, que no usará el wrapper de git [credential] helper = "/path/to/my/helper --with-arguments" # o puede especificar su propio fragmento de shell [credential "https://example.com"] username = your_user helper = "!f() { test \"$1\" = get && echo \"password=$(cat $HOME/.secret)\"; }; f"

En general, la regla (3) anterior es la más sencilla para que los usuarios la especifiquen. Los autores de helpers de credenciales deben esforzarse por ayudar a sus usuarios nombrando su programa "git-credential-$NAME", y colocándolo en el $PATH o $GIT_EXEC_PATH durante la instalación, lo que permitirá a un usuario habilitarlo con git config credential.helper $NAME

.

Cuando se ejecuta un helper, se le añadirá un argumento de "operación" a su línea de comandos, que es uno

de:

ge

t
Devuelve una credencial coincidente, si existe
alguna.

stor

e
Almacena la credencial, si es aplicable al
helper.

eras

e
Elimina las credenciales coincidentes, si las hay, del almacenamiento del
helper.

Los detalles de la credenciales se proporcionarán en el flujo de entrada estándar (stdin) del helper. El formato exacto es el mismo que el formato de entrada/salida del git comando de plumbing credential (ver la sección FORMATO DE ENTRADA/SALIDA en git-credential(1) para una especificación detallada)

.

Para una operación get, el helper debe producir una lista de atributos en la salida estándar en el mismo formato (ver git-credential(1) para atributos comunes). Un helper es libre de producir un subconjunto, o incluso ningún valor si no tiene nada útil que proporcionar. Cualquier atributo proporcionado sobrescribirá los que ya son conocidos por el subsistema de credenciales de Git. Los atributos no reconocidos se descartan silenciosamente

.

Aunque es posible sobrescribir todos los atributos, los helpers que se comportan bien deben abstenerse de hacerlo para cualquier atributo que no sea username y

password.

Si un helper produce un atributo quit con un valor de true o 1, no se consultarán más helpers, ni se pedirá nada al usuario (si no se ha proporcionado ninguna credencial, la operación fallará)

.

Del mismo modo, no se consultarán más helpers una vez que se hayan proporcionado tanto el nombre de usuario como la

contraseña.

Para una operación store o erase, la salida del helper se

ignora.

Si un helper no puede realizar la operación solicitada o necesita notificar al usuario de un problema potencial, puede escribir en

stderr.

Si no soporta la operación solicitada (por ejemplo, un store de solo lectura o un generador), debe ignorar silenciosamente la

solicitud.

Si un helper recibe cualquier otra operación, debe ignorar silenciosame

nte la solicitud. Esto deja espacio para que se añadan operaciones futuras
(los helpers más antiguos simplemente ignorarán las nuevas solicitudes).
