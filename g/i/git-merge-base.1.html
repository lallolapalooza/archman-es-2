GIT-MERGE-BASE(1) Manual de Git GIT-MERGE-BASE(1)

NOMBRE

git-merge-base - Encuentra los mejores ancestros comunes posibles para una fusión

SINOPSIS

git merge-base [-a | --all] <commit> <commit>...
git merge-base [-a | --all] --octopus <commit>...
git merge-base --is-ancestor <commit> <commit>
git merge-base --independent <commit>...
git merge-base --fork-point <ref> [<commit>]

DESCRIPCIÓN

git merge-base encuentra el/los mejor(es) ancestro(s) común(es) entre dos commits para usar en una fusión a tres bandas. Un ancestro común es *mejor* que otro ancestro común si el segundo es un ancestro del primero. Un ancestro común que no tiene un ancestro mejor es un *mejor ancestro común*, es decir, una *base de fusión*. Ten en cuenta que puede haber más de una base de fusión para un par de commits.

MODOS DE OPERACIÓN

En el caso especial más común, especificar solo dos commits en la línea de comandos significa calcular la base de fusión entre los dos commits dados.

Más generalmente, entre los dos commits de los que se calculará la base de fusión, uno es especificado por el primer argumento de commit en la línea de comandos; el otro commit es un commit (posiblemente hipotético) que es una fusión de todos los commits restantes en la línea de comandos.

Como consecuencia, la *base de fusión* no está necesariamente contenida en cada uno de los argumentos de commit si se especifican más de dos commits. Esto es diferente de git-show-branch(1) cuando se usa con la opción --merge-base.

--octopus

Calcula los mejores ancestros comunes de todos los commits proporcionados, en preparación para una fusión n-way. Esto imita el comportamiento de git show-branch --merge-base.

--independent

En lugar de imprimir bases de fusión, imprime un subconjunto mínimo de los commits proporcionados con los mismos ancestros. En otras palabras, entre los commits dados, lista aquellos que no se pueden alcanzar desde ningún otro. Esto imita el comportamiento de git show-branch --independent.

--is-ancestor

Comprueba si el primer <commit> es un ancestro del segundo <commit>, y sale con estado 0 si es verdadero, o con estado 1 si no lo es. Los errores se señalan con un estado distinto de cero que no sea 1.

--fork-point

Encuentra el punto en el que una rama (o cualquier historial que conduzca a <commit>) se bifurcó de otra rama (o cualquier referencia) <ref>. Esto no solo busca el ancestro común de los dos commits, sino que también tiene en cuenta el reflog de <ref> para ver si el historial que conduce a <commit> se bifurcó de una encarnación anterior de la rama <ref> (ver la discusión de este modo a continuación).

OPCIONES

-a, --all

Muestra todas las bases de fusión para los commits, en lugar de solo una.

DISCUSIÓN

Dados dos commits A y B, git merge-base A B mostrará un commit que es alcanzable desde ambos A y B a través de la relación padre.

Por ejemplo, con esta topología:

         o---o---o---B
        /
---o---1---o---o---o---A

la base de fusión entre A y B es 1.

Dados tres commits A, B y C, git merge-base A B C calculará la base de fusión entre A y un commit hipotético M, que es una fusión entre B y C. Por ejemplo, con esta topología:

       o---o---o---o---C
      /
     /   o---o---o---B
    /   /
---2---1---o---o---o---A

el resultado de git merge-base A B C es 1. Esto se debe a que la topología equivalente con un commit de fusión M entre B y C es:

       o---o---o---o---o
      /                 \
     /   o---o---o---o---M
    /   /
---2---1---o---o---o---A

y el resultado de git merge-base A M es 1. El commit 2 también es un ancestro común entre A y M, pero 1 es un mejor ancestro común, porque 2 es un ancestro de 1. Por lo tanto, 2 no es una base de fusión.

El resultado de git merge-base --octopus A B C es 2, porque 2 es el mejor ancestro común de todos los commits.

Cuando el historial involucra fusiones entrecruzadas, puede haber más de una *mejor* base común para dos commits. Por ejemplo, con esta topología:

---1---o---A
    \ /
     X
    / \
---2---o---o---B

tanto 1 como 2 son bases de fusión de A y B. Ninguno es mejor que el otro (ambos son *mejores* bases de fusión). Cuando la opción --all no está dada, no se especifica cuál de las mejores se muestra.

Un modismo común para comprobar si es "avance rápido" entre dos commits A y B es (o al menos solía ser) calcular la base de fusión entre A y B, y comprobar si es la misma que A, en cuyo caso, A es un ancestro de B. Verás este modismo utilizado a menudo en scripts antiguos.

A=$(git rev-parse --verify A)
if test "$A" = "$(git merge-base A B)"
then
        ... A es un ancestro de B ...
fi

En git moderno, puedes decirlo de una manera más directa:

if git merge-base --is-ancestor A B
then
        ... A es un ancestro de B ...
fi

en su lugar.

DISCUSIÓN SOBRE EL MODO FORK-POINT

Después de trabajar en la rama topic creada con git switch -c topic origin/master, el historial de la rama de seguimiento remoto origin/master puede haber sido rebobinado y reconstruido, lo que lleva a un historial de esta forma:

                 o---B2
                /
---o---o---B1--o---o---o---B (origin/master)
        \
         B0
          \
           D0---D1---D (topic)

donde origin/master apuntaba anteriormente a los commits B0, B1, B2 y ahora apunta a B, y tu rama topic se inició sobre él cuando origin/master estaba en B0, y construiste tres commits, D0, D1 y D, sobre él. Imagina que ahora quieres reorganizar el trabajo que hiciste en el tema sobre el origin/master actualizado.

En tal caso, git merge-base origin/master topic devolvería el padre de B0 en la imagen de arriba, pero B0^..D *no* es el rango de commits que querrías reproducir sobre B (incluye B0, que no es lo que escribiste; es un commit que el otro lado descartó al mover su punta de B0 a B1).

git merge-base --fork-point origin/master topic está diseñado para ayudar en este caso. Tiene en cuenta no solo B sino también B0, B1 y B2 (es decir, las puntas antiguas de las ramas de seguimiento remoto que su repositorio conoce en su reflog) para ver en qué commit se construyó tu rama topic y encuentra B0, permitiéndote reproducir solo los commits de tu topic, excluyendo los commits que el otro lado descartó más tarde.

Por lo tanto

$ fork_point=$(git merge-base --fork-point origin/master topic)

encontrará B0, y

$ git rebase --onto origin/master $fork_point topic

reproducirá D0, D1 y D sobre B para crear un nuevo historial de esta forma:

                 o---B2
                /
---o---o---B1--o---o---o---B (origin/master)
        \                   \
         B0                  D0'--D1'--D' (topic - actualizado)
          \
           D0---D1---D (topic - antiguo)

Una advertencia es que las entradas de reflog más antiguas en tu repositorio pueden ser expiradas por git gc. Si B0 ya no aparece en el reflog de la rama de seguimiento remoto origin/master, el modo --fork-point obviamente no puede encontrarlo y falla, evitando dar un resultado aleatorio e inútil (como el padre de B0, como lo da el mismo comando sin la opción --fork-point).

Además, la rama de seguimiento remoto con la que usas el modo --fork-point debe ser aquella de la que se bifurcó tu topic en su punta. Si te bifurcaste de un commit anterior a la punta, este modo no funcionará correctamente.
