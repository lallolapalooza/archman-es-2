DESCRIPCIÓ

N

Muestra uno o más objetos (blobs, árboles, etiquetas y commits)

.

Para los commits muestra el mensaje de registro y la diferencia textual. También presenta el commit de fusión en un formato especial producido por git diff-tr

ee --cc.

Para las etiquetas, muestra el mensaje de la etiqueta y los objetos

referenciados.

Para los árboles, muestra los nombres (equivalente a git ls-tree con --name-only)

.

Para blobs simples, muestra el contenido

simple.

Algunas opciones que el comando git log entiende pueden usarse para controlar cómo se muestran los cambios que introduce el

commit.

Esta página de manual

describe solo las opci
ones más utilizadas.

OPCIONE

<objeto>..

Los nombres de los objetos a mostrar (por defecto HEAD). Para una lista más completa de formas de escribir nombres de objetos, vea la sección "SPECIFYING REVISIONS" en gitrevision
s(7).

--pretty[=<formato>], --format=<formato

>
Imprime con formato los contenidos de los registros de commits en un formato dado, donde <formato> puede ser uno de oneline, short, medium, full, fuller, reference, email, raw, format:<cadena> y tformat:<cadena>. Cuando <formato> no es ninguno de los anteriores, y tiene %<marcador de posición> en él, actúa como si se hubiera dado --pretty=tformat:<formato>.

Vea la sección "PRETTY FORMATS" para algunos detalles adicionales de cada formato. Cuando se omite la parte =<formato>, por defecto es medium

.

Nota
puede especificar el formato pretty por defecto en la configuración del repositorio (vea git-conf

1)).

--abbrev-commi

t
En lugar de mostrar el nombre hexadecimal completo de 40 bytes del objeto commit, muestra un prefijo que nombra el objeto de forma única. --abbrev=<n> (que también modifica la salida del diff, si se muestra) puede usarse para especificar la longitud mínima del prefijo.

Esto debería hacer que --pretty=oneline sea mucho más legible par

--no-abbrev-commi

t
Muestra el nombre hexadecimal completo de 40 bytes del objeto commit. Esto anula --abbrev-commit, ya sea explícito o implícito por otras opciones como --oneline. También anula la variable log.abbr
evCommit.

--onelin

e
Este es un atajo para --pretty=oneline --abbrev-commit usados
juntos.

--encoding=<codificación

>
Los objetos commit registran la codificación de caracteres utilizada para el mensaje de registro en su cabecera de codificación; esta opción puede usarse para decirle al comando que recodifique el mensaje de registro del commit en la codificación preferida por el usuario. Para comandos de fontanería (no plumbing) esto por defecto es UTF-8. Tenga en cuenta que si un objeto afirma estar codificado en X y estamos saliendo en X, saldremos el objeto literalmente; esto significa que secuencias inválidas en el commit original pueden copiarse a la salida. Del mismo modo, si iconv(3) falla al convertir el commit, saldremos silenciosamente el objeto original
literalmente.

--expand-tabs=<n>, --expand-tabs, --no-expand-tab

s
Realiza una expansión de tabulaciones (reemplaza cada tabulador con suficientes espacios para llenar hasta la siguiente columna de visualización que sea múltiplo de <n>) en el mensaje de registro antes de mostrarlo en la salida. --expand-tabs es un atajo para --expand-tabs=8, y --no-expand-tabs es un atajo para --expand-tabs=0, que desactiva la expansión de tabulaciones.

Por defecto, las tabulaciones se expanden en los formatos pretty que indentan el mensaje de registro con 4 espacios (es decir, medium, que es el valor por defecto, full, y full

er
).

--notes[=<ref

>]
Muestra las notas (vea git-notes(1)) que anotan el commit, al mostrar el mensaje de registro del commit. Esto es el valor por defecto para los comandos git log, git show y git whatchanged cuando no se ha dado ninguna opción --pretty, --format, o --oneline en la línea de comandos.

Por defecto, las notas mostradas provienen de las refs de notas listadas en las variables core.notesRef y notes.displayRef (o las correspondientes anulaciones por variables de entorno). Vea git-config(1) para más

detalles.

Con un argumento opcional <ref>, usa la ref para encontrar las notas a mostrar. La ref puede especificar el nombre completo de la ref cuando comienza con refs/notes/; cuando comienza con notes/, refs/ y en otro caso refs/notes/ se antepone para formar el nombre completo de la

ref.

Múltiples opciones --notes pueden combinarse para controlar qué notas se están mostrando. Ejemplos: "--notes=foo" mostrará solo notas de refs/notes/foo; "--notes=foo --notes" mostrará tanto notas de "refs/notes/foo

" como de la(s) ref(
s) de notas por defecto.

--no-note

s
No muestra notas. Esto anula la opción --notes anterior, al restablecer la lista de refs de notas de las que se muestran notas. Las opciones se analizan en el orden dado en la línea de comandos, así que por ejemplo "--notes --notes=foo --no-notes --notes=bar" solo mostrará notas de refs/notes/bar
.

--show-notes-by-defaul

t
Muestra las notas por defecto a menos que se den opciones para mostrar notas
específicas.

--show-notes[=<ref>], --standard-notes, --no-standard-note

s
Estas opciones están obsoletas. Use en su lugar las opciones --notes/--no-notes ante
riores.

--show-signatur

Comprueba la validez de un objeto commit firmado pasando la firma a gpg --verify y mue

Al igual que email, pero las líneas en el mensaje de commit que comienzan con "From " (precedidas por cero o más ">") se citan con ">" para que no se confundan con el inicio de un nuevo commit.

•raw

El formato raw muestra el commit completo exactamente como está almacenado en el objeto de commit. Notablemente, los hashes se muestran completos, independientemente de si se utilizan --abbrev o --no-abbrev, y la información de *parents* muestra los commits padre reales, sin tener en cuenta injertos o simplificación del historial. Tenga en cuenta que este formato afecta la forma en que se muestran los commits, pero no la forma en que se muestra la diferencia, por ejemplo, con git log --raw. Para obtener nombres de objetos completos en un formato de diferencia crudo, use --no-abbrev.

•format:<format-string>

El formato format:<format-string> le permite especificar qué información desea mostrar. Funciona un poco como el formato printf, con la notable excepción de que obtiene un salto de línea con %n en lugar de \n.

Por ejemplo, format:"El autor de %h fue %an, %ar%nEl título fue >>%s<<%n" mostraría algo como esto:

El autor de fe6e0ee fue Junio C Hamano, hace 23 horas
El título fue >>t4119: test autocomputing -p<n> para entrada de diferencia tradicional.<<

%<(<n>[,(trunc|ltrunc|mtrunc)])

hace que el siguiente marcador de posición ocupe al menos N columnas de ancho, rellenando con espacios a la derecha si es necesario. Opcionalmente, trunca (con puntos suspensivos ..) a la izquierda (ltrunc) ..ft, en el medio (mtrunc) mi..le, o al final (trunc) rig.., si la salida es más larga que <n> columnas. Nota 1: que truncar solo funciona correctamente con <n> >= 2. Nota 2: los espacios alrededor de los valores <n> y <m> (ver más abajo) son opcionales. Nota 3: Los emojis y otros caracteres anchos ocuparán dos columnas de visualización, lo que puede exceder los límites de las columnas. Nota 4: las marcas de caracteres descompuestos combinados pueden colocarse incorrectamente en los límites de relleno.

hace que el siguiente marcador de posición ocupe al menos hasta la columna de visualización <m>, rellenando con espacios a la derecha si es necesario. Use valores negativos de <m> para posiciones de columna medidas desde el borde derecho de la ventana de la terminal.

DISCUSIÓ

N

Git es hasta cierto punto agnóstico en cuanto a la codificación de

caracteres.
•El contenido de los objetos blob son secuencias de bytes sin interpretar. No hay traducción de codificación a nivel
central.
•Los nombres de ruta están codificados en la forma C de normalización UTF-8. Esto se aplica a los objetos árbol, el archivo índice, los nombres de referencia, así como a los nombres de ruta en argumentos de la línea de comandos, variables de entorno y archivos de configuración (.git/config (ver git-config(1)), gitignore(5), gitattributes(5) y gitmodules(5)).

Tenga en cuenta que Git a nivel central trata los nombres de ruta simplemente como secuencias de bytes que no son NUL, no hay conversiones de codificación de nombres de ruta (excepto en Mac y Windows). Por lo tanto, el uso de nombres

de ruta que no son ASCII funcionará en su mayoría incluso en plataformas y sistemas de archivos que usan codificaciones ASCII extendidas heredadas. Sin embargo, los repositorios creados en tales sistemas no funcionarán correctame
nte en sistemas basados en UTF-8 (por ejemplo, Linux, Mac, Windows) y viceversa. Además, muchas herramientas basadas en Git simplemente asumen que los nombres de ruta son UTF-8 y fallarán al mostrar correctamente otras codificaciones.
•Los mensajes de registro de commits suelen estar codificados en UTF-8, pero también se admiten otras codificaciones ASCII extendidas. Esto incluye ISO-8859-x, CP125x y muchas otras, pero no UTF-16/32, EBCDIC y codificaciones multibyte CJK (GBK, Shift-JIS, Big5, EUC-x, CP9xx etc.)
.

Aunque animamos a que los mensajes de registro de commits estén codificados en UTF-8, tanto el núcleo como Git Porcelain están diseñados para no forzar UTF-8 en proyectos. Si todos los participantes de un proyecto en particular encuentran más conveniente usar codificaciones heredadas, Git no lo prohíbe. Sin embargo, hay algunas cosas a tener en

cuenta.
1.git commit y git commit-tree emiten una advertencia si el mensaje de registro de commit que se les da no parece una cadena UTF-8 válida, a menos que diga explícitamente que su proyecto usa una codificación heredada. La forma de decir esto es tener i18n.commitEncoding en el archivo .git/config, así: 
[i18n]
commitEncodin
g = ISO-8859-1

Los objetos commit creados con la configuración anterior registran el valor de i18n.commitEncoding en su encabezado encoding. Esto es para ayudar a otras personas que los miren más adelante. La fal

ta de este encabezado implica que el mensaje
de registro de commit está codificado en UTF-8.
2.git log, git show, git blame y compañía miran el encabezado encoding de un objeto commit, e intentan recodificar el mensaje de registro en UTF-8 a menos que se especifique lo contrario. Puede especificar la codificación de salida deseada con i18n.logOutputEncoding en el archivo .git/config, así: 
[i18n]
logOutputEncodi
ng = ISO-8859-1

Si no tiene esta variable de configuración, se usa el valor de i18n.commitEncod

ing en s
u lugar.

Tenga en cuenta que elegimos deliberadamente no recodificar el mensaje de registr

o de commit cuando se hace un commit para forzar UTF-8 a nivel de objeto comm
it, porque recodificar a UTF-8 no es necesariamente una operación reversible.
