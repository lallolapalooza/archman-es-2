DESCRIPCIÓ

N

Crea, desempaqueta y manipula archivos "bundle". Los bundles se utilizan para la transferencia "sin conexión" de objetos de Git sin un "servidor" activo en el otro extremo de la conexión de

red.

Se pueden usar para crear copias de seguridad incrementales y completas de un repositorio (véase el ejemplo de "copia de seguridad completa" en "EJEMPLOS"), y para transmitir el estado de las referencias de un repositorio a otro (véase el segundo ejemplo)

.

Los comandos de Git que obtienen o de otro modo "leen" a través de protocolos como ssh:// y https:// también pueden operar sobre archivos bundle. Es posible git-clone(1) un nuevo repositorio desde un bundle, usar git-fetch(1) para obtener de uno, y listar las referencias que contiene con git-ls-remote(1). No existe soporte correspondiente para "escribir", es decir, un git push hacia un bu

ndle no est
á soportado.

FORMATO DEL

BUNDLE

Los bundles son archivos .pack (véase git-pack-objects(1)) con una cabecera que indica qué referencias contiene el

bundle.

Al igual que el propio formato de archivo empaquetado, los bundles pueden ser autocontenidos o crearse usando exclusiones. Véase la sección "PRERREQUISITOS DE OBJETOS" más

abajo.

Los bundles creados usando exclusiones de revisión son "paquetes delgados" creados usando la opción --thin de git-pack-objects(1), y desempaquetados usando la opción --fix-thin de git-index-pa

ck(1).

No existe una opción para crear un "paquete grueso" al usar exclusiones de revisión, y los usuarios no deberían preocuparse por la diferencia. Al usar "paquetes delgados", los bundles creados usando exclusiones son más pequeños en tamaño. El hecho de que sean "delgados" por debajo se menciona aquí simplemente como una curiosidad, y como referencia a otra

documentación.

Véase gitformat-bundle(5) para más detalles y la discusión de "paquete delgado" en gitformat-pack(5) p

ara más
detalles.

OPCIONE

S

create [options] <file> <git-rev-list-args

>
Se usa para crear un bundle llamado file. Esto requiere los argumentos <git-rev-list-args> para definir el contenido del bundle. options contiene las opciones específicas del subcomando git bundle create. Si file es -, el bundle se escribe en
stdout.

verify

<file>
Se usa para comprobar que un archivo bundle es válido y se aplicará limpiamente al repositorio actual. Esto incluye comprobaciones sobre el propio formato del bundle, así como comprobar que los commits de prerrequisito existen y están totalmente enlazados en el repositorio actual. Luego, git bundle imprime una lista de commits faltantes, si los hay. Finalmente, se imprime información sobre capacidades adicionales, como "object filter". Véase "Capabilities" en gitformat-bundle(5) para más información. El código de salida es cero para éxito, pero será distinto de cero si el archivo bundle no es válido. Si file es -, el bundle se lee de
stdin.

list-heads

<file>
Lista las referencias definidas en el bundle. Si va seguido de una lista de referencias, solo se imprimen las referencias que coincidan con las dadas. Si file es -, el bundle se lee de
stdin.

unbundle

<file>
Pasa los objetos del bundle a git index-pack para su almacenamiento en el repositorio, luego imprime los nombres de todas las referencias definidas. Si se da una lista de referencias, solo se imprimen las referencias que coincidan con las de la lista. Este comando es realmente de fontanería, destinado a ser llamado solo por git fetch. Si file es -, el bundle se lee de
stdin.

<git-rev-list-args

>
Una lista de argumentos, aceptables por git rev-parse y git rev-list (y que contiene una referencia con nombre, véase ESPECIFICAR REFERENCIAS más abajo), que especifica los objetos y referencias específicos a transportar. Por ejemplo, master~10..master hace que la referencia master actual se empaquete junto con todos los objetos añadidos desde su commit ancestro número 10. No hay un límite explícito al número de referencias y objetos que pueden
empaquetarse.

[<refname>...

]
Una lista de referencias usada para limitar las referencias reportadas como disponibles. Esto es principalmente de uso para git fetch, que espera recibir solo las referencias solicitadas y no necesariamente todo lo que hay en el paquete (en este caso, git bundle actúa como git fetch-
pack).

--progres

s
El estado de progreso se reporta en el flujo de error estándar por defecto cuando está conectado a una terminal, a menos que se especifique -q. Esta bandera fuerza el estado de progreso incluso si el flujo de error estándar no está dirigido a una
terminal.

--version=<version

>
Especifica la versión del bundle. La versión 2 es el formato más antiguo y solo puede usarse con repositorios SHA-1; la versión 3 más nueva contiene capacidades que permiten extensiones. El valor por defecto es el formato soportado más antiguo, basado en el algoritmo de hash en
uso.

-q,

--quiet
Esta bandera hace que el coma
ndo no reporte su progreso en
el flujo de error estándar.

ESPECIFICAR

REFERENCIAS

Las revisiones deben ir acompañadas de nombres de referencia para ser empaquetadas en un bundle. Alternativamente --all puede usarse para empaquetar todas las

referencias.

Se pueden empaquetar más de una referencia, y se puede especificar más de un conjunto de objetos de prerrequisito. Los objetos empaquetados son aquellos no contenidos en la unión de los

prerrequisitos.

El comando git bundle create resuelve los nombres de referencia por usted usando las mismas reglas que git rev-parse --abbrev-ref=loose. Cada prerrequisito puede especificarse explícitamente (por ejemplo, ^master~10), o implícitamente (por ejemplo, master~10..master, --since=10.days.ago maste

r).

Todos estos casos simples están bien (asumiendo que tenemos una rama "master" y "next")

: 
$ git bundle create master.bundle master
$ echo master | git bundle create m
aster.bundle --stdin $ git bundle create master-and-next.bundle master next $
(echo master; echo next) | git bundle create master-and-next.bundle --stdin

Y también estos (y los mismos pero omitiendo los ejemplos con --stdin )

: 
$ git bundle create recent-master.bundle mas
ter~10..master $ git bundle create recent-u
pdates.bundle master~10..master next~5..next

Un nombre de revisión o un rango cuyo lado derecho no pueda resolverse a una referencia no es

aceptado: 
$ git bundle create HEAD.bundle $(git rev-parse H
EAD) fatal: Refusing to create empty bundle. $ gi
t bundle create master-yesterday.bundle master~10.
.master~5 fatal: Refusing to create empty bundle.

PRERREQUISITOS DE

OBJETOS

Al crear bundles es posible crear un bundle autocontenido que puede desempaquetarse en un repositorio sin historia común, así como proporcionar revisiones negativas para excluir objetos necesarios en las partes anteriores de la

historia.

Al proporcionar una revisión como new a git bundle create se creará un archivo bundle que contiene todos los objetos alcanzables desde la revisión new. Ese bundle puede desempaquetarse en cualquier repositorio para obtener una historia completa que lleve a la revisión new

: 
$ git bundle
create ful
l.bundle new

Un rango de revisiones como old..new producirá un archivo bundle que requerirá que la revisión old (y cualquier objeto alcanzable desde ella) exista para que el bundle pueda ser "desempaquetado&quot;

-able: 
$ git bundle
create full.bu
ndle old..new

Un paquete autónomo sin ningún prerrequisito puede extraerse en cualquier lugar, incluso en un repositorio vacío, o ser clonado desde (es decir, new, pero no old..new

).

Está bien errar por el lado de la precaución, haciendo que el archivo del paquete contenga objetos que ya están en el destino, ya que estos se ignoran al desempaquetar en el

destino.

Si desea proporcionar el mismo conjunto de refs que un clon directo desde el repositorio de origen obtendría, use --branches --tags para los <git-rev-list

-args>.

El comando git bundle verify se puede usar para comprobar si su repositorio

de destino tiene los commits de prerreq
uisito requeridos para un paquete.

EJEMPLO

S

Discutiremos dos

casos:
1.Tomar una copia de seguridad completa de un
repositorio
2.Transferir el historial de un repositorio a otra máquina cuando las dos máquinas no tienen conexión
directa

Primero consideremos una copia de seguridad completa del repositorio. El siguiente comando tomará una copia de seguridad completa del repositorio en el sentido de que todas las refs se incluyen en el

paquete: 
$ git bundle
create backup
.bundle --all

Pero tenga en cuenta de nuevo que esto es solo para las refs, es decir, solo incluirá refs y commits alcanzables desde esas refs. No incluirá otro estado local, como el contenido del índice, el árbol de trabajo, el stash, la configuración por repositorio, los hooks,

etc.

Puede recuperar ese repositorio más tarde usando, por ejemplo, git-clone

(1): 
$ git clone ba
ckup.bundle <
new directory>

Para el siguiente ejemplo, suponga que desea transferir el historial de un repositorio R1 en la máquina A a otro repositorio R2 en la máquina B. Por cualquier razón, la conexión directa entre A y B no está permitida, pero podemos mover datos de A a B a través de algún mecanismo (CD, correo electrónico, etc.). Queremos actualizar R2 con el desarrollo hecho en la rama master en

R1.

Para iniciar el proceso, puede primero crear un paquete que no tenga ningún prerrequisito. Puede usar una etiqueta para recordar hasta qué commit procesó por última vez, para facilitar la actualización posterior del otro repositorio con un paquete

incremental: 
machineA$ cd R1
machineA$ git bund
le create file.bundle master machin
eA$ git tag -f lastR2bundle master

Luego transfiere file.bundle a la máquina de destino B. Debido a que este paquete no requiere ningún objeto existente para extraerse, puede crear un nuevo repositorio en la máquina B clonando desde

él: 
machineB$ git clone
-b master /home/me
/tmp/file.bundle R2

Esto definirá un remoto llamado "origin" en el repositorio resultante que le permite hacer fetch y pull desde el paquete. El archivo $GIT_DIR/config en R2 tendrá una entrada como

esta: 
[remote "origin"]
    url = /home/me/tmp/file.bundle
    fetch = refs/heads/*:refs/remotes/origin
/
*

Para actualizar el repositorio resultante mine.git, puede hacer fetch o pull después de reemplazar el paquete almacenado en /home/me/tmp/file.bundle con actualizaciones

incrementales.

Después de trabajar un poco más en el repositorio original, puede crear un paquete incremental para actualizar el otro

repositorio: 
machineA$ cd R1
machineA$ git bundle cr
eate file.bundle lastR2bundle..master m
achineA$ git tag -f lastR2bundle master

Luego transfiere el paquete a la otra máquina para reemplazar /home/me/tmp/file.bundle, y haz pull desde

él. 
machineB$ c
d R2 machine
B$ git pull

Si sabe hasta qué commit el repositorio de destino previsto debe tener los objetos necesarios, puede usar ese conocimiento para especificar los prerrequisitos, dando un punto de corte para limitar las revisiones y objetos que van en el paquete resultante. El ejemplo anterior usó la etiqueta lastR2bundle para este propósito, pero puede usar cualquier otra opción que le daría al comando git-log(1). Aquí hay más

ejemplos:

Puede usar una etiqueta que esté presente en

ambos: 
$ git bundle c
reate mybundle
v1.0.0..master

Puede usar un prerrequisito basado en

tiempo: 
$ git bundle crea
te mybundle --sin
ce=10.days master

Puede usar el número de

commits: 
$ git bundle
create mybund
le -10 master

Puede ejecutar git-bundle verify para ver si puede extraer de un paquete que se creó con un

prerrequisito: 
$ git bun
dle verify
mybundle

Esto listará qué commits debe tener para poder extraer del paquete y dará un error si no los

tiene.

Un paquete desde el punto de vista del repositorio de destino es simplemente como un repositorio normal desde el que hace fetch o pull. Puede, por ejemplo, mapear referencias al hacer

fetch: 
$ git fetch
mybundle mas
ter:localRef

También puede ver qué referencias

ofrece: 
$ git
ls-rem
ote my
bundle

DISCUSIÓ

N

Una forma ingenua de hacer una copia de seguridad completa de un repositorio es usar algo con el efecto de cp -r <repo> <destination>. Esto se desaconseja ya que el repositorio podría escribirse durante la operación de copia. A su vez, algunos archivos en <destination> podrían

corromperse.

Por eso se recomienda usar las herramientas de Git para hacer copias de seguridad de repositorios, ya sea con este comando o con, por ejemplo, git-clone(1). Pero tenga en cuenta que estas herramientas no le ayudarán a respaldar el estado que no sean refs y commits. En otras palabras, no le ayudarán a respaldar el contenido del índice, el árbol de trabajo, el stash, la configuración por repositorio, los hooks,

etc.

Véase también gitfaq(7), sección "TRANSFERS" para una discusión de los prob

lemas asociados con la sincroniza
ción de archivos entre sistemas.
