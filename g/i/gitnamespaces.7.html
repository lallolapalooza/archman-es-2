NOMBRE

gitnamespaces - Namespaces de Git

SINOPSIS

GIT_NAMESPACE=<namespace> git upload-pack
GIT_NAMESPACE=<namespace> git receive-pack

DESCRIPCIÓN

Git soporta la división de las referencias (refs) de un único repositorio en múltiples namespaces, cada uno con sus propias ramas, etiquetas (tags) y HEAD. Git puede exponer cada namespace como un repositorio independiente para hacer pull y push, mientras comparte el almacén de objetos y expone todas las referencias a operaciones como git-gc(1).

Almacenar múltiples repositorios como namespaces de un único repositorio evita almacenar copias duplicadas de los mismos objetos, como cuando se almacenan múltiples ramas del mismo código fuente. El mecanismo de alternativos proporciona soporte similar para evitar duplicados, pero los alternativos no previenen la duplicación entre objetos nuevos añadidos a los repositorios sin mantenimiento continuo, mientras que los namespaces sí lo hacen.

Para especificar un namespace, establezca la variable de entorno GIT_NAMESPACE al namespace. Para cada namespace de refs, Git almacena las refs correspondientes en un directorio bajo refs/namespaces/. Por ejemplo, GIT_NAMESPACE=foo almacenará las refs bajo refs/namespaces/foo/. También puede especificar namespaces a través de la opción --namespace de git(1).

Tenga en cuenta que los namespaces que incluyen un / se expandirán a una jerarquía de namespaces; por ejemplo, GIT_NAMESPACE=foo/bar almacenará las refs bajo refs/namespaces/foo/refs/namespaces/bar/. Esto hace que las rutas en GIT_NAMESPACE se comporten jerárquicamente, de modo que clonar con GIT_NAMESPACE=foo/bar produce el mismo resultado que clonar con GIT_NAMESPACE=foo y clonar desde ese repositorio con GIT_NAMESPACE=bar. También evita ambigüedades con rutas de namespace extrañas como foo/refs/heads/, que de otro modo podrían generar conflictos de directorios/archivos dentro del directorio refs.

git-upload-pack(1) y git-receive-pack(1) reescriben los nombres de las refs según lo especificado por GIT_NAMESPACE. git-upload-pack y git-receive-pack ignorarán todas las referencias fuera del namespace especificado.

El servidor HTTP inteligente, git-http-backend(1), pasará GIT_NAMESPACE a los programas backend; consulte git-http-backend(1) para ver ejemplos de configuración para exponer namespaces de repositorios como repositorios.

Para una prueba local sencilla, puede usar git-remote-ext(1):

git clone ext::'git --namespace=foo %s /tmp/prefixed.git'

SEGURIDAD

Los protocolos de fetch y push no están diseñados para evitar que un lado robe datos del otro repositorio que no se pretendía compartir. Si tiene datos privados que necesita proteger de un par malintencionado, su mejor opción es almacenarlos en otro repositorio. Esto se aplica tanto a clientes como a servidores. En particular, los namespaces en un servidor no son efectivos para el control de acceso de lectura; solo debe conceder acceso de lectura a un namespace a clientes en los que confiaría para acceso de lectura a todo el repositorio.

Los vectores de ataque conocidos son los siguientes:

1.La víctima envía líneas "have" anunciando los IDs de los objetos que tiene y que no están explícitamente destinados a ser compartidos, pero que pueden usarse para optimizar la transferencia si el par también los tiene. El atacante elige un ID de objeto X para robar y envía una ref a X, pero no se le requiere enviar el contenido de X porque la víctima ya lo tiene. Ahora la víctima cree que el atacante tiene X y le envía el contenido de X más tarde. (Este ataque es más directo para que un cliente lo realice en un servidor, creando una ref a X en el namespace al que el cliente tiene acceso y luego obteniéndola. La forma más probable para que un servidor lo realice en un cliente es "fusionar" X en una rama pública y esperar que el usuario realice trabajo adicional en esta rama y la envíe de vuelta al servidor sin notar la fusión).

2.Al igual que en el punto 1, el atacante elige un ID de objeto X para robar. La víctima envía un objeto Y que el atacante ya tiene, y el atacante afirma falsamente tener X y no Y, por lo que la víctima envía Y como un delta contra X. El delta revela regiones de X que son similares a Y al atacante.
