REGISTRANDO ESTADO DE

GIT

Ahora, queremos ir a la siguiente etapa en Git, que es tomar los archivos que Git conoce en el índice, y registrarlos como un árbol real. Lo hacemos en dos fases: crear un objeto árbol, y registrar ese objeto árbol como un objeto commit junto con una explicación de de qué se trataba el árbol, junto con información de cómo llegamos a ese

Crear un objeto árbol es trivial, y se hace con git write-tree. No hay opciones ni otra entrada: git write-tree tomará el estado actual del índice, y escribirá un objeto que describe todo ese índice. Sin embargo — normalmente nunca usarías git write-tree por sí solo, porque normalmente siempre registras un árbol en un objeto commit usando el comando git commit-tree. A diferencia de git diff-files, que mostraba la diferencia entre el archivo índice y el árbol de trabajo, git diff-index muestra las diferencias entre un árbol registrado y ya sea el archivo índice o el árbol de trabajo. En otras palabras, git diff-index quiere un árbol contra el cual hacer diff, y antes de que hiciéramos el commit, no podíamos hacer eso, porque no teníamos nada contra lo que hacer

diff.

Pero ahora podemos

-p HEAD

Ahora estamos comparando el árbol de trabajo no contra el archivo índice, sino contra el árbol que acabamos de escribir. Simplemente ocurre que esos dos son obviamente los mismos, así que obtenemos el mismo

resultado.

De nuevo, porque esta es una operación común, también puedes simplemente abreviarla

con

HEAD

En otras palabras, git diff-index normalmente compara un árbol contra el árbol de trabajo, pero cuando se le da el indicador --cached, se le dice que en su lugar compare solo contra los contenidos de la caché del índice, e ignore completamente el estado actual del árbol de trabajo. Como acabamos de escribir el archivo índice en HEAD, hacer git diff-index --cached -p HEAD debería por lo tanto devolver un conjunto vacío de diferencias, y eso es exactamente lo que

hace.

Nota

git diff-index realmente siempre usa el índice para sus comparaciones, y decir que compara un árbol contra el árbol de trabajo es por lo tanto no estrictamente preciso. En particular, la lista de archivos a comparar (los "metadatos") siempre proviene del archivo índice, independientemente de si se usa el indicador --cached o no. El indicador --cached realmente solo determina si los contenidos del archivo a comparar provienen del árbol de trabajo o

no.

Esto no es difícil de entender, tan pronto como te das cuenta de que Git simplemente nunca conoce (o le importa) sobre archivos que no se le han dicho explícitamente. Git nunca irá buscando archivos para comparar, espera que tú le

digas cuáles son los archivo

Sin embargo, nuestro siguiente paso es registrar el cambio que hicimos, y de nuevo, para entender qué está pasando, ten en cuenta la diferencia entre "contenidos del árbol de trabajo", "archivo índice" y "árbol registrado". Tenemos cambios en el árbol de trabajo que queremos registrar, y siempre tenemos que trabajar a través del archivo índice, así que lo primero que necesitamos hacer es actualizar la caché del

índice:

Observa qué pasa con las diferentes versiones de git diff-* aquí. Después de que hayamos actualizado hello en el índice, git diff-files -p ahora no muestra diferencias, pero git diff-index -p HEAD todavía muestra que el estado actual es diferente del estado que registramos. De hecho, ahora git diff-index muestra la misma diferencia ya sea que usemos el indicador --cached o no, ya que ahora el índice es coherente con el árbol de

trabajo.

ETIQUETANDO UNA

VERSIÓN

En Git, hay dos tipos de etiquetas, una "ligera", y una "etiqueta

anotada".

Una etiqueta "ligera" técnicamente no es más que una rama, excepto que la ponemos en el subdirectorio .git/refs/tags/ en lugar de llamarla un head. Así que la forma más simple de etiqueta no implica nada más

que 
$ git t
ag my-fi
rst-tag

que simplemente escribe el HEAD actual en el archivo .git/refs/tags/my-first-tag, después de lo cual puedes usar este nombre simbólico para ese estado particular. Puedes, por ejemplo,

hacer 
$ git di
ff my-f
irst-tag

para comparar tu estado actual contra esa etiqueta, lo cual en este punto obviamente será un diff vacío, pero si continúas desarrollando y confirmando cosas, puedes usar tu etiqueta como un "punto de anclaje" para ver qué ha cambiado desde que la

etiquetaste.

Una "etiqueta anotada" es en realidad un objeto Git real, y contiene no solo un puntero al estado que quieres etiquetar, sino también un pequeño nombre de etiqueta y mensaje, junto con opcionalmente una firma PGP que dice que sí, realmente hiciste esa etiqueta. Creas estas etiquetas anotadas con el indicador -a o -s de git t

ag: 
$ git t
ag -s <t
agname>

lo que firmará el HEAD actual (pero también puedes darle otro argumento que especifique la cosa a etiquetar, por ejemplo, podrías haber etiquetado el punto actual de mybranch usando git tag <tagname> mybranc

h).

Normalmente solo haces etiquetas firmadas para versiones principales o cosas así, mientras que las etiquetas ligeras

son útiles para cualquier marcado que quieras hacer — cada vez que decidas que quieres recordar un cierto punto, sim
plemente crea una etiqueta privada para él, y tendrás un nombre simbólico agradable para el estado en ese punto.

COPIANDO

REPOSITORIOS

Los repositorios de Git normalmente son totalmente autosuficientes y reubicables. A diferencia de CVS, por ejemplo, no hay una noción separada de "repositorio" y "árbol de trabajo". Un repositorio de Git normalmente es el árbol de trabajo, con la información local de Git oculta en el subdirectorio .git. No hay nada más. Lo que ves es lo que

tienes.

Nota

Puedes decirle a Git que separe la información interna de Git del directorio que rastrea, pero lo ignoraremos por ahora: no es cómo funcio

nan los proyectos normales, y realmente solo está destinado a usos especiales. Así que el modelo mental de "la información de Git siempre está
ligada directamente al árbol de trabajo que describe" puede no ser técnicamente 100% preciso, pero es un buen modelo para todo uso normal.

Esto tiene dos

implicaciones:
•si te aburres del repositorio del tutorial que creaste (o has cometido un error y quieres empezar de nuevo), puedes simplemente hacer

Ten en cuenta que cuando hayas movido o copiado un repositorio de Git, tu archivo índice de Git (que almacena en caché varios datos, notablemente la información de "stat" de los archivos involucrados) probablemente necesitará ser actualizado. Al copiar un repositorio remoto, querrás al menos actualizar la caché del índice cuando hagas esto, y especialmente con los repositorios de otras personas a menudo querrás asegurarte de que la caché del índice esté en algún estado conocido (no sabes lo que han hecho y aún no han confirmado), así que usualmente precederás al git update-index con

TRABAJAR CON OTRAS PERSONAS, ESTILO DE REPOSITORIO COMPARTIDO

Si vienes de un entorno CVS, el estilo de cooperación sugerido en la sección anterior puede serte nuevo. No tienes que preocuparte. Git soporta el estilo de cooperación de "repositorio público compartido" con el que probablemente estés más familiarizado.

Consulta gitcvs-migration(7) para más detalles.

AGRUPAR TU TRABAJO

Es probable que estés trabajando en más de una cosa a la vez. Es fácil gestionar esas tareas más o menos independientes utilizando ramas con Git.

Ya hemos visto cómo funcionan las ramas anteriormente, con el ejemplo de "diversión y trabajo" utilizando dos ramas. La idea es la misma si hay más de dos ramas. Digamos que empezaste desde la cabeza de "master", y tienes algo de código nuevo en la rama "master", y dos correcciones independientes en las ramas "commit-fix" y "diff-fix":

$ git show-branch
! [commit-fix] Fix commit message normalization.
 ! [diff-fix] Fix rename detection.
  * [master] Release candidate #1
---
 +  [diff-fix] Fix rename detection.
 +  [diff-fix~1] Better common substring algorithm.
+   [commit-fix] Fix commit message normalization.
  * [master] Release candidate #1
++* [diff-fix~2] Pretty-print messages.

Ambas correcciones están bien probadas, y en este punto, quieres fusionar ambas. Podrías fusionar primero diff-fix y luego commit-fix, así:

$ git merge -m "Merge fix in diff-fix" diff-fix
$ git merge -m "Merge fix in commit-fix" commit-fix

Lo que resultaría en:

$ git show-branch
! [commit-fix] Fix commit message normalization.
 ! [diff-fix] Fix rename detection.
  * [master] Merge fix in commit-fix
---
  - [master] Merge fix in commit-fix
+ * [commit-fix] Fix commit message normalization.
  - [master~1] Merge fix in diff-fix
 +* [diff-fix] Fix rename detection.
 +* [diff-fix~1] Better common substring algorithm.
  * [master~2] Release candidate #1
++* [master~3] Pretty-print messages.

Sin embargo, no hay ninguna razón particular para fusionar una rama primero y la otra después, cuando lo que tienes es un conjunto de cambios verdaderamente independientes (si el orden importara, entonces no son independientes por definición). En su lugar, podrías fusionar esas dos ramas en la rama actual a la vez. Primero, vamos a deshacer lo que acabamos de hacer y empezar de nuevo. Querríamos obtener la rama master antes de estas dos fusiones, reiniciándola a master~2:

$ git reset --hard master~2

Puedes asegurarte de que git show-branch coincida con el estado anterior a esas dos git merge que acabas de hacer. Luego, en lugar de ejecutar dos comandos git merge seguidos, fusionarías esas dos cabezas de rama (esto se conoce como hacer un Octopus):

$ git merge commit-fix diff-fix
$ git show-branch
! [commit-fix] Fix commit message normalization.
 ! [diff-fix] Fix rename detection.
  * [master] Octopus merge of branches 'diff-fix' and 'commit-fix'
---
  - [master] Octopus merge of branches 'diff-fix' and 'commit-fix'
+ * [commit-fix] Fix commit message normalization.
 +* [diff-fix] Fix rename detection.
 +* [diff-fix~1] Better common substring algorithm.
  * [master~1] Release candidate #1
++* [master~2] Pretty-print messages.

Ten en cuenta que no deberías hacer un Octopus solo porque puedes. Un octopus es algo válido de hacer y a menudo facilita la visualización del historial de commits si estás fusionando más de dos cambios independientes a la vez. Sin embargo, si tienes conflictos de fusión con alguna de las ramas que estás fusionando y necesitas resolverlos manualmente, eso es una indicación de que el desarrollo ocurrido en esas ramas no eran realmente independientes después de todo, y deberías fusionar de dos en dos, documentando cómo resolviste los conflictos y la razón por la que preferiste los cambios realizados en un lado sobre el otro. De lo contrario, haría el historial del proyecto más difícil de seguir, no más fácil.
