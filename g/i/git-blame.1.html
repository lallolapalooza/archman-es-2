git-blame - Muestra qué revisió

n y autor modificaron por últi
ma vez cada línea de un archivo

SINOPSI

S 
git blame [-c] [-b] [-l] [--root] [-t] [-f] [-n] [-s] [-e] [-p] [-w] [--incremental]
            [-L <rango>] [-S <archivo-revisiones>] [-M] [-C] [-C] [-C] [--since=<fecha>]
            [--ignore-re
v <rev>] [--ignore-revs-file <archivo>] [--color-lines] [--color-by-age] [--progress]

DESCRIPCIÓ

N

Anota cada línea en el archivo dado con información de la revisión que modificó la línea por última vez. Opcionalmente, comienza a anotar desde la revisión

dada.

Cuando se especifica una o más veces, -L restringe la anotación a las líneas

solicitadas.

El origen de las líneas se sigue automáticamente a través de renombres de archivos completos (actualmente no hay opción para desactivar el seguimiento de renombres). Para seguir líneas movidas de un archivo a otro, o para seguir líneas que fueron copiadas y pegadas de otro archivo, etc., vea las opciones -C y -M

.

El informe no le dice nada sobre las líneas que han sido eliminadas o reemplazadas; necesita usar una herramienta como git diff o la interfaz "pickaxe" mencionada brevemente en el siguiente

párrafo.

Además de soportar la anotación de archivos, Git también soporta la búsqueda en el historial de desarrollo de cuándo un fragmento de código apareció en un cambio. Esto hace posible rastrear cuándo un fragmento de código fue añadido a un archivo, movido o copiado entre archivos, y finalmente eliminado o reemplazado. Funciona buscando una cadena de texto en el diff. Un pequeño ejemplo de la interfaz pickaxe que busca blame_usage

: 
$ git log --pretty=oneline -S'blame_usage'
50
40f17eba15504bad66b14a645bddd9b015ebb7 blame
-S <archivo-ancestry> ea4c7f9bf69e781dd0cd88
d2bccb2bf5cc15c9a7 git-blame: Hacer la salida

-M[<num>

]
Detecta líneas movidas o copiadas dentro de un archivo. Cuando un commit mueve o copia un bloque de líneas (por ejemplo, el archivo original tiene A y luego B, y el commit lo cambia a B y luego A), el algoritmo de blame tradicional nota solo la mitad del movimiento y típicamente atribuye las líneas que fueron movidas hacia arriba (es decir, B) al padre y asigna la culpa de las líneas que fueron movidas hacia abajo (es decir, A) al commit hijo. Con esta opción, ambos grupos de líneas se culpan al padre ejecutando pasadas adicionales de inspección.

<num> es opcional pero es el límite inferior en el número de caracteres alfa

numéricos que Git debe detectar como movidos/copiados dentro de un archivo
para asociar esas líneas con el commit padre. El valor predeterminado es 20.

-C[<num>

]
Además de -M, detecta líneas movidas o copiadas desde otros archivos que fueron modificados en el mismo commit. Esto es útil cuando reorganiza su programa y mueve código alrededor entre archivos. Cuando esta opción se da dos veces, el comando además busca copias de otros archivos en el commit que crea el archivo. Cuando esta opción se da tres veces, el comando además busca copias de otros archivos en cualquier commit.

<num> es opcional pero es el límite inferior en el número de caracteres alfanuméricos que Git debe detectar como movidos/copiados entre archivos para asociar esas líneas con el commit padre.ommit. Y el valor por defecto es 40. Si se proporcionan más de una opción -C, el argumento <num> de la última -C tendr

Esta opción puede especificarse varias veces para ignorar más de una revisión. EL FORMATO POR

DEFECTO

Cuando no se especifica la opción --porcelain ni la opción --incremental, git blame producirá una anotación para cada línea

con:
•el nombre abreviado del objeto para el commit del que provino la
línea;
•el identificador del autor (por defecto el nombre del autor y la fecha, a menos que se especifique -s o -e);
y
•el número de
línea

antes del c

ontenido d
e la línea.

EL FORMATO

PORCELAIN

En este formato, cada línea se emite después de un encabezado; el encabezado tiene como mínimo la primera línea que

tiene:
•el SHA-1 de 40 bytes del commit al que se atribuye la
línea;
•el número de línea de la línea en el archivo
original;
•el número de línea de la línea en el archivo
final;
•en una línea que inicia un grupo de líneas de un commit diferente al anterior, el número de líneas en este grupo. En las líneas siguientes este campo está
ausente.

A esta línea de encabezado le sigue la siguiente información al menos una vez para cada

commit:
•el nombre del autor ("author"), el correo electrónico ("author-mail"), la hora ("author-time") y la zona horaria ("author-tz"); de manera similar para el
committer.
•el nombre de archivo en el commit al que se atribuye la
línea.
•la primera línea del mensaje del registro del commit ("summary")
.

El contenido de la línea real se emite después del encabezado anterior, precedido por un TAB. Esto es para permitir añadir más elementos de encabezado más

adelante.

El formato porcelain generalmente suprime la información del commit que ya se ha visto. Por ejemplo, dos líneas que se le atribuyen la culpa al mismo commit se mostrarán ambas, pero los detalles de ese commit se mostrarán solo una vez. La información que es específica de líneas individuales no se agrupará, como las revisiones a marcar como ignored o unblamable. Esto es más eficiente, pero puede requerir que el lector mantenga más estado. La opción --line-porcelain puede usarse para emitir la información completa del commit para cada línea, permitiendo un uso más sencillo (pero menos eficiente)

como: 
# contar el número de líneas atrib
uidas a cada autor git blame --lin
e-porcelain file | sed -n 's/^autho
r //p' | sort | uniq -c | sort -rn

ESPECIFICAR

RANGOS

A diferencia de git blame y git annotate en versiones anteriores de git, el alcance de la anotación puede limitarse tanto a rangos de líneas como a rangos de revisiones. La opción -L, que limita la anotación a un rango de líneas, puede especificarse varias

veces.

Cuando esté interesado en encontrar el origen de las líneas 40-60 del archivo foo, puede usar la opción -L así (significan lo mismo — ambas piden 21 líneas empezando en la línea 40)

: 
git blame -L 40
,60 foo git blam
e -L 40,+21 foo

También puede usar una expresión regular para especificar el rango de

líneas: 
git blame -L
'/^sub hello
{/,/^}$/' foo

lo que limita la anotación al cuerpo de la subrutina

hello.

Cuando no le interesen los cambios más antiguos que la versión v2.6.18, o cambios más antiguos que 3 semanas, puede usar especificadores de rango de revisiones similares a git rev-l

ist: 
git blame v2.6.18..
-- foo git blame --
since=3.weeks -- foo

Cuando se usan especificadores de rango de revisiones para limitar la anotación, las líneas que no han cambiado desde el límite del rango (ya sea el commit v2.6.18 o el commit más reciente que tenga más de 3 semanas de antigüedad en el ejemplo anterior) se le atribuye la culpa a ese commit límite del

rango.

Una forma particularmente útil es ver si un archivo añadido tiene líneas creadas por copiar y pegar de archivos existentes. A veces esto indica que el desarrollador estaba siendo descuidado y no refactorizó el código adecuadamente. Puede primero encontrar el commit que introdujo el archivo

con: 
git log --diff-
filter=A --pret
ty=short -- foo

y luego anotar el cambio entre el commit y sus padres, usando la notación commit^!

: 
git blame
-C -C -f
$commit
^! -- foo

SALIDA

INCREMENTAL

Cuando se llama con la opción --incremental, el comando emite el resultado a medida que se construye. La salida generalmente hablará sobre las líneas tocadas por commits más recientes primero (es decir, las líneas se anotarán fuera de orden) y está destinada a ser usada por visores

interactivos.

El formato de salida es similar al formato Porcelain, pero no contiene las líneas reales del archivo que se está

anotando.
1.Cada entrada de blame siempre comienza con una línea de: 
<40-byte-hex-sha1>
<sourceline> <resu
ltline> <num-lines>

Los números d

e línea se cue
ntan desde 1.
2.La primera vez que un commit aparece en el flujo, se imprimen varios otros información sobre él con una etiqueta de una palabra al principio de cada línea describiendo la información adicional del commit (autor, correo electrónico, committer, fechas, resumen, etc.)
.
3.A diferencia del formato Porcelain, la información del nombre de archivo se da siempre y termina la entrada: 
"filename" <whitespace-quoted-filename-goes-her
e
>

y por lo tanto es realmente bastante fácil de analizar para algún analizador orientado a líneas y palabras (lo cual debería ser bastante natural para la mayoría de los lenguajes de scripting)

.

Nota
Para las personas que hacen análisis: para hacerlo más robusto, simplemente ignore cualquier línea entre la primer
a y la última ("<sha1>" y las líneas "filename") donde no reconozca las palabras de etiqueta (o no le importe esa
en particular) al principio de las líneas de "información extendida". De esa manera, si alguna vez se añade info
rmación (como la codificación del commit o comentarios extendidos del commit), un visor de blame no se preocupará.
