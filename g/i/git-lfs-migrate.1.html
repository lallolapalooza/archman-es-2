NOMBRE

git-lfs-migrate - Migrar historial hacia o desde Git LFS

SINOPSIS

git lfs migrate <modo> [opciones] [--] [rama ...]

DESCRIPCIÓN

Convierte archivos en un repositorio Git hacia o desde punteros Git LFS, o resume los tamaños de archivo de Git por tipo de archivo. El modo import convierte archivos de Git (es decir, blobs) a Git LFS, mientras que el modo export hace lo inverso, y el modo info proporciona un resumen informativo que puede ser útil para decidir qué archivos importar o exportar.

En todos los modos, por defecto git lfs migrate opera solo en la rama actualmente extraída, y solo en archivos (de cualquier tamaño y tipo) añadidos en commits que no existen en ningún remoto. Hay múltiples opciones disponibles para anular estos valores predeterminados.

Al convertir archivos hacia o desde Git LFS, el comando git lfs migrate solo realizará cambios en tu repositorio y copia de trabajo local, nunca en los remotos. Esto es intencional ya que los modos import y export son generalmente "destructivos" en el sentido de que reescriben tu historial de Git, cambiando commits y generando nuevos SHAs de commit. (La excepción es el sub-modo import "sin reescritura"; ver IMPORTAR SIN REESCRIBIR HISTORIAL para detalles).

Por lo tanto, siempre debes confirmar o ocultar primero cualquier trabajo no confirmado antes de usar los modos import o export, y luego validar el resultado de la migración antes de enviar los cambios a tus remotos, por ejemplo, ejecutando el modo info y examinando tu historial de commits reescrito.

Una vez que estés satisfecho con los cambios, deberás forzar el envío del nuevo historial de Git de cualquier rama reescrita a todos tus remotos. Este es un paso que debe tomarse con cuidado, ya que estarás alterando el historial de Git en tus remotos.

Para examinar o modificar archivos en ramas distintas a la actualmente extraída, se pueden especificar referencias de rama directamente, o proporcionarlas en una o más opciones --include-ref. También se pueden excluir prefijándolas con ^ o proporcionándolas en opciones --exclude-ref. Usa la opción --everything para especificar que todas las referencias deben ser examinadas, incluyendo todas las referencias remotas. Ver INCLUIR Y EXCLUIR REFERENCIAS para detalles.

Para los modos info e import, se consideran todos los tipos de archivo por defecto; si bien es útil en el modo info, esto a menudo no es deseable al importar, por lo que normalmente se deben especificar patrones de nombres de archivo (pathspecs) o la opción --fixup en ese caso. (Se requiere al menos un pathspec de inclusión para el modo export.) Los pathspecs se pueden definir usando las opciones --include y --exclude (-I y -X como abreviatura), como se describe en INCLUIR Y EXCLUIR.

Dado que el uso típico de Git LFS depende del seguimiento de tipos de archivo específicos utilizando patrones de nombres de archivo definidos en archivos .gitattributes, el comando git lfs migrate examinará, creará y modificará archivos .gitattributes según sea necesario. A los archivos .gitattributes siempre se les asignará el modo de permisos de lectura/escritura predeterminado (es decir, sin permisos de ejecución). Cualquier enlace simbólico con ese nombre provocará que la migración se detenga prematuramente.

El modo import (ver IMPORTAR) convertirá los objetos de Git de los tipos de archivo especificados (por ejemplo, con --include) a punteros Git LFS, y añadirá entradas para esos tipos de archivo a los archivos .gitattributes, creando esos archivos si no existen. El resultado debe ser como si se hubieran ejecutado comandos git lfs track en los puntos de tu historial de Git correspondientes a donde aparece por primera vez cada tipo de archivo convertido. La excepción es si se da la opción --fixup, en cuyo caso el modo import solo examinará los archivos .gitattributes existentes y luego convertirá los objetos de Git que deberían ser rastreados por Git LFS pero que aún no lo son.

El modo export (ver EXPORTAR) funciona como la operación inversa al modo import, convirtiendo cualquier puntero Git LFS que coincida con los tipos de archivo especificados con --include, que debe ser dado al menos una vez. Nota que las entradas de .gitattributes no se eliminarán, ni tampoco los archivos; en cambio, el modo export inserta entradas de "no rastrear" similares a las creadas por el comando git lfs untrack. La opción --remote está disponible en el modo export para especificar el remoto desde el cual se deben obtener los objetos Git LFS si no existen en la caché de objetos Git LFS local; si no se proporciona, se usa origin por defecto.

El modo info (ver INFO) resume por tipo de archivo (es decir, por extensión de nombre de archivo) el número total y el tamaño de los archivos en un repositorio. Nota que, al igual que los otros dos modos, por defecto el modo info opera solo en la rama actualmente extraída y solo en commits que no existen en ningún remoto, por lo que para obtener un resumen de todo el repositorio en todas las ramas, usa la opción --everything. Si los objetos ya han sido convertidos a punteros Git LFS, entonces por defecto el tamaño de los objetos referenciados se totaliza y se informa por separado. También puedes optar por ignorarlos usando --pointers=ignore o tratarlos como archivos usando --pointers=no-follow. (Esta última opción es similar a cómo los punteros Git LFS existentes eran manejados por el modo info en versiones anteriores de Git LFS).

Al usar la opción --everything, ten en cuenta que significa que se considerarán todos los commits alcanzables desde todas las refs (locales y remotas), pero no necesariamente todos los tipos de archivo. Los modos import e info consideran todos los tipos de archivo por defecto, aunque las opciones --include y --exclude restringen este comportamiento.

Mientras que la opción --everything significa que se considerarán todos los commits alcanzables desde cualquier ref para la migración, después de la migración solo se actualizarán las refs locales, incluso cuando se especifica --everything. Esto asegura que las refs remotas permanezcan sincronizadas con sus remotos. En otras palabras, se actualizará refs/heads/foo con la opción --everything, pero refs/remotes/origin/foo no, por lo que permanece sincronizada con el remoto hasta que se ejecute git push origin foo. Después de verificar que los resultados de una migración con --everything son satisfactorios, puede ser conveniente enviar todas las ramas locales a tus remotos usando la opción --all de git push.

A menos que se proporcione la opción --skip-fetch, git lfs migrate siempre comienza obteniendo listas actualizadas de refs de todos los remotos devueltos por git remote, pero como se mencionó anteriormente, después de realizar cambios en tu historial de Git al convertir objetos, nunca enviará automáticamente esos cambios a tus remotos.

MODOS

info

Muestra información sobre el tamaño del repositorio. Ver INFO.

import

Convierte objetos de Git a punteros Git LFS. Ver IMPORTAR e IMPORTAR SIN REESCRIBIR HISTORIAL.

export

Convierte punteros Git LFS a objetos de Git. Ver EXPORTAR.

Ver INCLUIR Y EXCLUIR.

--include-ref=<nombre_ref>

Ver INCLUIR Y EXCLUIR REFERENCIAS.<

--exclude-ref=<refname>

Ver REFERENCIAS DE INCLUSIÓN Y EXCLUSIÓN.

--skip-fetch


Asume que el conjunto conocido de referencias remotas está completo y no debe actualizarse al determinar el conjunto de commits "no enviados" a migrar. No tiene efecto cuando se combina con --include-ref o --exclude-ref.

--everything

Ver REFERENCIAS DE INCLUSIÓN Y EXCLUSIÓN.

Nota: Las referencias de Git distinguen entre mayúsculas y minúsculas ("case-sensitive") en todas las plataformas en el modo "packed from" (ver git-pack-refs(1)). En sistemas de archivos "no sensibles a mayúsculas y minúsculas" (case-insensitive), por ejemplo, NTFS en Windows o APFS por defecto en macOS, git-lfs-migrate(1) solo migraría la primera referencia si dos o más referencias son iguales excepto por las mayúsculas/minúsculas de las letras.

--yes

Asume una respuesta sí a cualquier pregunta, permitiendo el uso no interactivo. Actualmente, la única pregunta de este tipo es la que pregunta si se deben sobrescribir (destruir) los cambios en la copia de trabajo. Por lo tanto, especificar esta opción puede causar pérdida de datos si no se tiene cuidado.

[rama ...]

Migra solo el conjunto de ramas listadas. Si no se proporciona, git-lfs-migrate(1) migrará la rama que esté actualmente seleccionada.

Las referencias que comiencen con ^ serán excluidas, mientras que las ramas que no comiencen con ^ serán incluidas.

Si se proporcionan --include-ref o --exclude-ref, la rama seleccionada no se añadirá, pero las ramas proporcionadas explícitamente sí se añadirán.

INFO

El modo info resume los tamaños de los archivos de objetos presentes en el historial de Git. Soporta todas las opciones principales de migrate y estas adicionales:

--above=<tamaño>

Solo cuenta los archivos cuyo tamaño individual esté por encima del tamaño dado. El tamaño puede especificarse como un número de bytes o un número seguido de una unidad de almacenamiento, por ejemplo, "1b", "20 MB", "3 TiB", etc.

Si un conjunto de archivos que comparten una extensión común no tiene ningún archivo en ese conjunto cuyo tamaño individual esté por encima del --above dado, no se mostrará ninguna entrada para ese conjunto.

--top=<n>

Solo muestra las primeras n entradas, ordenadas por la cantidad total de archivos que coinciden con el specifier de ruta dado. Por defecto, se muestran solo las primeras 5 entradas. Cuando se encuentran objetos Git LFS existentes, se emite una línea adicional separada de "Objetos LFS" además de las primeras n entradas, a menos que la opción --pointers se utilice para cambiar este comportamiento.

--unit=<unidad>

Formatea el número de bytes en cada entrada como una cantidad de la unidad de almacenamiento proporcionada. Las unidades válidas incluyen: * b, kib, mib, gib, tib, pib - para unidades de almacenamiento IEC * b, kb, mb, gb, tb, pb - para unidades de almacenamiento SI

Si no se especifica una --unit, se elige la unidad más grande que pueda contener el número de bytes contados como una cantidad entera.

--pointers=[follow|no-follow|ignore]

Trata los punteros Git LFS existentes en el historial de acuerdo con una de las tres alternativas. En el caso predeterminado follow, si se encuentran punteros, se emite un elemento de línea adicional y separado de "Objetos LFS" que resume el número total y el tamaño de los objetos Git LFS a los que se hace referencia mediante punteros. En el caso ignore, los punteros se ignoran simplemente, mientras que el caso no-follow replica el comportamiento del modo info en versiones anteriores de Git LFS y trata los punteros que encuentra como si fueran archivos normales, por lo que los totales de salida solo incluyen el contenido de los punteros, no el contenido de los objetos a los que se refieren.

--fixup

Infiere filtros --include y --exclude por commit basándose en los archivos .gitattributes del repositorio. En la práctica, esta opción cuenta cualquier ruta de archivo que deba ser rastreada por Git LFS según el(los) archivo(s) .gitattributes del repositorio, pero que aún no sean punteros. Los archivos .gitattributes no se informan, a diferencia de la salida normal del modo info. Esta opción es incompatible con los filtros --include y --exclude proporcionados explícitamente y con cualquier configuración de --pointers que no sea ignore, por lo tanto, --fixup implica --pointers=ignore si no se establece explícitamente.

El formato de la salida muestra el patrón del nombre del archivo, el tamaño total de los objetos de archivo (excluyendo aquellos por debajo del umbral --above, si se definió uno), y la relación entre el número de archivos por encima del umbral y el número total de archivos; esta relación también se muestra como un porcentaje. Por ejemplo:

*.gif               93 MB   9480/10504 archivos  90%
*.png               14 MB    1732/1877 archivos  92%

Por defecto, solo se muestran las cinco mejores entradas, pero --top permite que se emitan más o menos según se desee.

IMPORT

El modo import migra los objetos presentes en el historial de Git a archivos puntero rastreados y almacenados con Git LFS. Soporta todas las opciones principales de migrate y estas adicionales:

--verbose

Imprime el OID del commit y el nombre del archivo de los archivos migrados en STDOUT.

--above=<tamaño>

Solo migra los archivos cuyo tamaño individual sea superior al tamaño dado. El tamaño puede especificarse como un número de bytes o un número seguido de una unidad de almacenamiento, por ejemplo, "1b", "20 MB", "3 TiB", etc. Esta opción no se puede usar con las opciones --include, --exclude y --fixup.

--object-map=<ruta>

Escribe en ruta un archivo con el mapeo de cada commit reescrito. El formato del archivo es CSV con este patrón: SHA-ANTIGUO,SHA-NUEVO

--no-rewrite

Migra objetos a Git LFS en un nuevo commit sin reescribir el historial de Git. Tenga en cuenta que cuando se utiliza esta opción, el comando migrate import esperará una lista de argumentos diferente, estarán disponibles opciones especializadas y las opciones principales de migrate se ignorarán. Ver IMPORTAR SIN REESCRIBIR HISTORIAL.

--fixup

Infiere filtros --include y --exclude por commit basándose en los archivos .gitattributes del repositorio. En la práctica, esta opción importa cualquier ruta de archivo que deba ser rastreada por Git LFS según el(los) archivo(s) .gitattributes del repositorio, pero que aún no sean punteros. Esta opción es incompatible con los filtros --include y --exclude proporcionados explícitamente.

Si no se proporciona --no-rewrite y se dan --include o --exclude (-I, -X, respectivamente), el archivo .gitattributes se modificará para incluir cualquier nuevo patrón de ruta de archivo según lo indicado por esas banderas.

Si no se proporciona --no-rewrite y no se dan ninguna de esas banderas, el archivo gitattributes se modificará de forma incremental para incluir las nuevas extensiones de ruta de archivo a medida que se reescriben en el historial.

IMPORTAR SIN REESCRIBIR HISTORIAL

El modo import tiene un submódo especial activado por la bandera --no-rewrite. Este submódo migrará objetos a punteros como en el modo base import, pero lo hará en un nuevo commit sin reescribir el historial de Git. Al usar este submódo, las opciones principales de migrate, como --include-ref, serán ignoradas, al igual que las del modo base import. El comando migrate también tomará una lista de argumentos diferente. Como resultado de estos cambios, --no-rewrite solo operará en la rama actual; cualquier otra rama interesada deberá fusionar el commit generado.

El submódo --no-rewrite soporta las siguientes opciones y argumentos:

-m <mensaje>, --message=<mensaje>

Especifica un mensaje de commit para el commit recién creado.

[archivo ...]

La lista de archivos a importar. Estos archivos deben ser rastreados por patrones especificados en el archivo gitattributes.

Si se proporciona --message, el nuevo commit se creará con el mensaje proporcionado. Si no se proporciona ningún mensaje, se generará un mensaje de commit basado en los argumentos de archivo.

NAME

git-lfs-migrate - Migrate existing Git history to or from Git LFS

SYNOPSIS

git lfs migrate import [options] [paths...]
git lfs migrate export [options] [paths...]

DESCRIPTION

This command rewrites Git history. It can be used to convert existing Git history to use Git LFS, or to convert Git LFS objects back to regular Git blobs.

This command is destructive! Use it with care, and know that the history will be rewritten and SHA1s of commits will change.

It is strongly recommended that you backup your repository before using this command.

You can perform a dry run of the import with git lfs migrate info. This command will show you what files would be converted, without actually touching your history.

MODES

import

Convert Git blobs to Git LFS pointers. In this mode, git-lfs-migrate will find files matching the specified patterns and convert them to Git LFS objects. Files that are already Git LFS objects will be skipped unless the --force flag is used.

export

Convert Git LFS pointers back to Git blobs. In this mode, git-lfs-migrate will find Git LFS objects matching the specified patterns and convert them back to regular Git blobs.

The export mode requires at least one --include pathspec. Git LFS objects that are not found locally will be downloaded from the Git remote specified with --remote (defaults to origin).

OPTIONS

--everything

Rewrite all local refs, including branches and tags. By default, only the current branch is rewritten.

--include-ref=pattern

Rewrite only the refs matching the given pattern. This option may be specified more than once.

--exclude-ref=pattern

Do not rewrite refs matching the given pattern. This option may be specified more than once.

--include=pattern

Convert files matching the given pattern. This option may be specified more than once, and patterns may be comma-separated.

For example, to convert all .png and .jpg files, use:

    --include="*.png,*.jpg"

This option is required for the export mode.

--exclude=pattern

Do not convert files matching the given pattern. This option may be specified more than once, and patterns may be comma-separated.

--above=size

Convert files larger than the specified size. Size can be specified in bytes, or with a suffix of KB, MB, or GB.

For example, to convert all files larger than 100MB:

    --above=100MB
--below=size

Convert files smaller than the specified size. This option is rarely useful, but can be used in conjunction with --above to convert files within a specific size range.

--force

When importing, convert files even if they are already Git LFS objects. When exporting, convert files even if they are not Git LFS objects (this would be unusual).

--no-rewrite

Do not rewrite local history. Instead, create a new commit at the tip of the current branch with the specified files converted to Git LFS objects. This is useful for converting files in a repository without rewriting the entire history.

The --no-rewrite option does not apply to the export mode.

-m, --message=msg

When using --no-rewrite, use the specified commit message for the new commit.

--remote=name

When exporting, download missing Git LFS objects from the specified remote. Defaults to origin.

--pointers=mode

Specifies how to handle Git LFS pointers in the repository. Possible modes are:

only

Only convert Git LFS objects that are already in the repository.

ignore

Ignore any Git LFS objects that are already in the repository.

scan

Scan for Git LFS objects and convert them if they match the --include patterns. This is the default behavior for import mode.

--top=n

When importing, only consider the top n files by size. When exporting, only consider the top n Git LFS objects by size.

--skip-smudge

When exporting, do not download Git LFS objects that are not already present locally. This means that if a Git LFS object is not found, it will not be converted back to a blob, and will be left as a pointer.

The export mode requires at minimum a pattern provided with the --include argument to specify which files to export. Files matching the --include patterns will be removed from Git LFS, while files matching the --exclude patterns will retain their Git LFS status. The export command will modify the .gitattributes to set/unset any filepath patterns as given by those flags.

INCLUDE AND EXCLUDE

You can specify that git lfs migrate should only convert files whose pathspec matches the --include glob patterns and does not match the --exclude glob patterns, either to reduce total migration time or to only migrate part of your repo. Multiple patterns may be given using commas as delimiters.

Pattern matching is done so as to be functionally equivalent to the pattern matching format of .gitattributes. In addition to simple file extension matches (e.g., .gif) patterns may also specify directory paths, in which case the path/* format may be used to match recursively.

Note that this form of pattern matching for the --include and --exclude options used by the git lfs migrate command is unique among the suite of git lfs commands. Other commands which also take these options, such as git lfs ls-files, use the gitignore(5) form of pattern matching instead.

INCLUDE AND EXCLUDE REFERENCES

You can specify that git lfs migrate should only convert files added in commits reachable from certain references, namely those defined using one or more --include-ref options, and should ignore files in commits reachable from references defined in --exclude-ref options.

        D---E---F
       /         \
  A---B------C    refs/heads/my-feature
   \          \
    \          refs/heads/main
     \
      refs/remotes/origin/main

In the above configuration, the following commits are reachable by each ref:

refs/heads/main:           C, B, A
refs/heads/my-feature:     F, E, D, B, A
refs/remote/origin/main:   A

The following git lfs migrate options would, therefore, include commits F, E, D, C, and B, but exclude commit A:

  --include-ref=refs/heads/my-feature
  --include-ref=refs/heads/main
  --exclude-ref=refs/remotes/origin/main

The presence of flag --everything indicates that all commits reachable from all local and remote references should be migrated (but note that the remote refs themselves will not be updated).

EXAMPLES

Migrate unpushed commits

A common use case for the migrate command is to convert large Git objects to LFS before pushing your commits. By default, it only scans commits that don’t exist on any remote, so long as the repository is non-bare.

First, run git lfs migrate info to list the file types taking up the most space in your repository:

$ git lfs migrate info
Fetching remote refs: ..., done
Sorting commits: ..., done
Examining commits: 100% (1/1), done
*.mp3   284 MB    1/1 files(s)  100%
*.pdf   42 MB     8/8 files(s)  100%
*.psd   9.8 MB  15/15 files(s)  100%
*.ipynb 6.9 MB    6/6 files(s)  100%
*.csv   5.8 MB    2/2 files(s)  100%

Now, you can run git lfs migrate import to convert some file types to LFS:

$ git lfs migrate import --include="*.mp3,*.psd"
Fetching remote refs: ..., done
Sorting commits: ..., done
Rewriting commits: 100% (1/1), done
  main  d2b959babd099fe70da1c1512e2475e8a24de163 -> 136e706bf1ae79643915c134e17a6c933fd53c61
Updating refs: ..., done

If after conversion you find that some files in your working directory have been replaced with Git LFS pointers, this is normal, and the working copies of these files can be repopulated with their full expected contents by using git lfs checkout.

Migrate local history

You can also migrate the entire history of your repository:

# Check for large files and existing Git LFS objects in your local main branch
$ git lfs migrate info --include-ref=main
# Check for large files and existing Git LFS objects in every branch
$ git lfs migrate info --everything
# Check for large files in every branch, ignoring any existing Git LFS objects,
# and listing the top 100 or fewer results
$ git lfs migrate info --everything --pointers=ignore --top=100

The same flags will work in import mode:

# Convert all zip files in your main branch
$ git lfs migrate import --include-ref=main --include="*.zip"
# Convert all zip files in every local branch
$ git lfs migrate import --everything --include="*.zip"
# Convert all files over 100K in every local branch
$ git lfs migrate import --everything --above=100Kb

Note: This will require a force-push to any existing Git remotes. Using the --all option when force-pushing may be convenient if many local refs were updated, e.g., after importing to Git LFS with the --everything option.

Migrate without rewriting local history

You can also migrate files without modifying the existing history of your repository. Note that in the examples below, files in subdirectories are not included because they are not explicitly specified.

Without a specified commit message:

$ git lfs migrate import --no-rewrite test.zip *.mp3 *.psd

With a specified commit message:

$ git lfs migrate import --no-rewrite \
  -m "Import test.zip, .mp3, .psd files in root of repo" \
  test.zip *.mp3 *.psd

Migrate from Git LFS

If you no longer wish to use Git LFS for some or all of your files, you can use the export mode to convert Git LFS objects into regular Git blobs again.

The export mode requires at least one --include pathspec, and will download any objects not found locally from your origin Git remote, or from the Git remote you specify with the --remote option.

# Convert all zip Git LFS objects to files in your main branch
$ git lfs migrate export --include-ref=main --include="*.zip"
# Convert all zip Git LFS objects to files in every local branch,
# fetching any object data not cached locally from the my-remote Git remote
$ git lfs migrate export --everything --include="*.zip" --remote=my-remote
# Convert all Git LFS objects to files in every local branch
$ git lfs migrate export --everything --include="*"

Note: This will require a force-push to any existing Git remotes. Using the --all option when force-pushing may be convenient if many local refs were updated, e.g., after exporting from Git LFS with the --everything option.
