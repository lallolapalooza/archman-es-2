NOMBRE

git-revise - Actualizar, dividir y reorganizar commits de git de forma eficiente

SINOPSIS

git revise [<opciones>] [<objetivo>]

DESCRIPCIÓN

git revise es un subcomando de git(1) para actualizar, dividir y reorganizar commits de forma eficiente. Está fuertemente inspirado en git-rebase(1), pero intenta ser más eficiente y ergonómico para flujos de trabajo orientados a pilas de parches.

Por defecto, git revise aplicará los cambios staged a <objetivo>, actualizando HEAD para apuntar a la historia revisada. También soporta la división de commits y la reescritura de mensajes de commit.

A diferencia de git-rebase(1), git revise evita modificar el estado del directorio de trabajo y del índice, realizando todas las fusiones en memoria, y solo escribiéndolas cuando es necesario. Esto le permite ser significativamente más rápido en grandes bases de código y evitar la invalidación de compilaciones.

Si se especifican --autosquash o --interactive, el argumento <objetivo> puede omitirse o darse como el valor especial :option:--root. Si se omite, git revise considerará un rango de commits no publicados en la rama actual. Si se da como :option:--root, se considerarán todos los commits, incluido el commit raíz.

OPCIONES

Opciones generales

-a, --all
Añadir cambios a archivos rastreados antes de revisar.
-p, --patch
Añadir interactivamente fragmentos del árbol de trabajo antes de revisar.
--no-index
Ignorar cambios staged en el índice.
--reauthor
Restablecer el autor del commit de destino al usuario actual.
--ref <gitref>
Rama de trabajo a actualizar; por defecto es HEAD.
-S, --gpg-sign, --no-gpg-sign
Firmar commits con GPG. Anula tanto la configuración de git commit.gpgSign como la de revise.gpgSign.

Modos principales de operación

-i, --interactive
En lugar de aplicar cambios staged a <objetivo>, editar una lista de tareas de acciones a realizar en los commits después de <objetivo>. Véase MODO INTERACTIVO.
--autosquash, --no-autosquash
En lugar de aplicar directamente los cambios staged a <objetivo>, realizar automáticamente acciones de fixup o squash marcadas con fixup! o squash! entre <objetivo> y el HEAD actual. Para más información sobre lo que hacen estas acciones, véase MODO INTERACTIVO.

Estos commits se crean normalmente con git commit --fixup=<commit> o git commit --squash=<commit>, y se identifican con el objetivo mediante la primera línea de su mensaje de commit.

Esta opción se puede combinar con --interactive para modificar las tareas generadas antes de que se ejecuten.

Si la opción --autosquash está habilitada por defecto mediante una variable de configuración, la opción --no-autosquash se puede utilizar para anular y deshabilitar esta configuración. Véase CONFIGURACIÓN.

-c, --cut
Seleccionar interactivamente fragmentos de <objetivo>. Los fragmentos elegidos se dividen en un segundo commit inmediatamente después del objetivo.

Una vez completada la división, se editan los mensajes de ambos commits.

Consulte la sección "Modo Interactivo" de git-add(1) para aprender a operar en este modo.

-e, --edit
Después de aplicar los cambios staged, editar el mensaje del commit de <objetivo>.

Esta opción se puede combinar con --interactive para permitir la edición de mensajes de commit dentro de la lista de tareas. Para más información, véase MODO INTERACTIVO.

-m <msg>, --message <msg>
Usar el <msg> dado como el nuevo mensaje de commit para <objetivo>. Si se dan varias opciones -m, sus valores se concatenan como párrafos separados.
--version
Imprimir información de la versión y salir.

CONFIGURACIÓN

La configuración se gestiona mediante git-config(1).

revise.autoSquash
Si se establece en true, implica --autosquash siempre que se especifique --interactive. Anulado por --no-autosquash. Por defecto es false. Si no está configurado, se utiliza el valor de rebase.autoSquash en su lugar.
revise.gpgSign
Si se establece en true, firma los nuevos commits con GPG; por defecto es false. Esta configuración anula la configuración original de git commit.gpgSign y puede ser anulada por las opciones de línea de comandos --gpg-sign y --no-gpg-sign.

RESOLUCIÓN DE CONFLICTOS

Cuando se encuentra un conflicto, git revise intentará resolverlo automáticamente utilizando los mecanismos estándar de git. Si la resolución automática falla, se le pedirá al usuario que los resuelva manualmente.

Actualmente no hay soporte para usar git-mergetool(1) para resolver conflictos.

No se intenta detectar renombrados de archivos o directorios. git revise puede producir resultados subóptimos en caso de renombrados. Utilice el modo interactivo de git-rebase(1) cuando el seguimiento de renombrados sea importante.

NOTAS

Una ejecución exitosa de git revise añadirá una única entrada al reflog, permitiendo deshacerla con git reset @{1}. Los comandos de git revise fallidos dejarán su repositorio en gran medida sin modificar.

No se permiten commits de fusión entre el commit de destino y HEAD, ya que no se soporta la reescritura de los mismos.

Consulte git-rebase(1) para obtener más información sobre las implicaciones de modificar el historial en un repositorio que se comparte.

MODO INTERACTIVO

git revise soporta un modo interactivo inspirado en el modo interactivo de git-rebase(1).

Este modo se inicia con el último commit que desea conservar "tal cual":

git revise -i <commit-después-de-este>

El objetivo especial --root está disponible para revisar todo hasta el commit raíz:

git revise -i --root

Se iniciará un editor con los commits de su rama actual después del commit especificado. Si el índice tiene algún cambio staged pero no commiteado, también aparecerá una entrada de <git index>.
