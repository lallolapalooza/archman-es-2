DESCRIPCIÓ

N

git-annex permite gestionar archivos con git, sin verificar el contenido de los archivos dentro de git. Aunque esto pueda parecer paradójico, es útil cuando se tratan archivos más grandes de los que git puede manejar fácilmente en la actualidad, ya sea debido a limitaciones en la memoria, el tiempo de cálculo de sumas de comprobación o el espacio en

disco.

Incluso sin seguimiento del contenido de los archivos, poder gestionar archivos con git, mover archivos y eliminarlos con árboles de directorios versionados, y usar ramas y clonaciones distribuidas, son todas razones muy prácticas para usar git. Y los archivos anexados pueden coexistir en el mismo repositorio git con archivos versionados regularmente, lo cual es conveniente para mantener documentos, Makefiles, etc., que están asociados con archivos anexados pero que se benefician del control total de

revisiones.

Cuando un archivo es anexado, su contenido se mueve a un almacén de clave-valor, y se crea un enlace simbólico que apunta al contenido. Estos

enlaces simbólicos se verifican en git y se versionan como archivos normales. Puedes moverlos, eliminarlos, etc. Enviar a otro repositori
o git hará que git-annex allí se entere del archivo anexado, y se puede usar para recuperar su contenido desde el almacén de clave-valor.

CONFIGURACIÓN

Al igual que otros comandos de git, git-annex se configura a través de .git/config. Estas configuraciones, así como las configuraciones relevantes de git, son las que git-annex utiliza.

(Algunas de estas configuraciones también se pueden establecer, en todos los clones del repositorio, usando git-annex-config. Ver su página man para una lista.)

annex.uuid
Un UUID único para este repositorio (establecido automáticamente).
annex.backend
Nombre del backend de clave-valor predeterminado a usar al agregar nuevos archivos al repositorio. Ver git-annex-backends(1) para información sobre los backends disponibles.
Esto se anula mediante la configuración annex.backend en los archivos .gitattributes, y mediante la opción --backend.
(Anteriormente se llamaba annex.backends, y ese seguirá siendo utilizado si está establecido.)
annex.securehashesonly
Establecer a true para indicar que el repositorio solo debe usar hashes criptográficamente seguros (SHA2, SHA3) y no hashes inseguros (MD5, SHA1) para el contenido.
Cuando esto está establecido, no se permitirá agregar el contenido de los archivos que utilizan hashes criptográficamente inseguros al repositorio.
Además, git-annex fsck se quejará de cualquier archivo presente en el repositorio que utilice hashes inseguros. Y, git-annex import --no-content se negará a importar archivos de remotos especiales que usen hashes inseguros.
Para configurar el comportamiento en nuevos clones del repositorio, esto se puede establecer usando git-annex-config.
annex.maxextensionlength
Longitud máxima, en bytes, de lo que se considera una extensión de nombre de archivo. Esto se usa al agregar un archivo a un backend que preserva las extensiones de nombre de archivo, y también al generar una rama de vista.
La longitud predeterminada es 4, lo que permite extensiones como "jpeg". El punto antes de la extensión no se cuenta como parte de su longitud.
annex.maxextensions
Número máximo de extensiones de nombre de archivo a preservar al usar un backend que preserva extensiones de nombre de archivo, y también al generar una rama de vista.
El valor predeterminado es 2, lo que permite extensiones compuestas como ".tar.gz". Cuando se establece en 1, solo preservará la última extensión, por ejemplo, ".gz".
annex.diskreserve
Cantidad de espacio en disco a reservar. Se verifica el espacio en disco al transferir contenido anexo para evitar quedarse sin él, y se puede reservar espacio libre adicional a través de esta opción, para dejar espacio para otros datos (como logs de commits de git). Se puede especificar con cualquier unidad comúnmente utilizada, por ejemplo, "0.5 gb", "500M", o "100 KiloBytes"
La reserva predeterminada es de 100 megabytes.
annex.fullybalancedthreshhold
Configura el porcentaje de ocupación que debe tener un repositorio para que la expresión de contenido preferido "fullybalanced" lo considere lleno. El valor predeterminado es 90.
annex.skipunknown
Establecer a true para que comandos como "git-annex get" omitan silenciosamente los elementos que se listan en la línea de comandos, pero no están registrados en git.
Establecer a false para que sea un error que comandos como "git-annex get" se les pida operar en archivos que no están registrados en git. (Este es el valor predeterminado en versiones recientes de git-annex.)
Tenga en cuenta que, cuando annex.skipunknown es false, un comando como "git-annex get ." fallará si ningún archivo en el directorio actual está registrado en git. Comandos como "git-annex get foo/" fallarán si ningún archivo en el directorio está registrado en git, pero si al menos un archivo lo está, ignorará otros archivos que no lo estén. Todo esto es igual que el comportamiento de "git-ls-files --error-unmatch".
Tenga en cuenta también que git-annex omite los archivos que están registrados en git, pero no son archivos anexados; esta configuración no afecta a eso.
annex.largefiles
Se utiliza para configurar qué archivos son lo suficientemente grandes como para agregarse al anexo. Es una expresión que coincide con los archivos grandes, por ejemplo "include=*.mp3 or largerthan=500kb" Ver git-annex-matching-expression(1) para detalles sobre la sintaxis.
Anula cualquier atributo annex.largefiles en los archivos .gitattributes.
Para configurar un annex.largefiles predeterminado para todos los clones del repositorio, esto se puede establecer en git-annex-config(1).
Esto configura el comportamiento tanto de git-annex como de git al agregar archivos al repositorio. Por defecto, git-annex add agrega todos los archivos al anexo (excepto los archivos ocultos y los archivos en directorios ocultos), y git add agrega archivos a git (a menos que se hayan agregado al anexo previamente). Cuando se configura annex.largefiles, tanto git annex add como git add agregarán los archivos grandes coincidentes al anexo, y los otros archivos a git.
Otros comandos de git-annex también respetan annex.largefiles, incluyendo git annex import, git annex addurl, git annex importfeed, git annex assist, y el git-annex assistant.
annex.dotfiles
Normalmente, los archivos ocultos y los archivos dentro de directorios ocultos se asumen como archivos de configuración como .gitignore, cuyo contenido siempre debe formar parte del repositorio git, por lo que no se agregarán al anexo. Establecer annex.dotfiles a true hará que estos archivos se agreguen al anexo igual que cualquier otro archivo.
Para anexionar solo algunos archivos ocultos, establezca esto y configure annex.largefiles para que coincida con los que desea. Por ejemplo, para coincidir solo con archivos ocultos que terminen en ".big"

git config annex.dotfiles true
Para configurar un annex.dotfiles predeterminado para todos los clones del repositorio, esto se puede establecer en git-annex-config(1).

remote.<name>.annex-verify, annex.verify
Por defecto, git-annex verificará las sumas de verificación de los objetos descargados desde remotos. Si confías en un remoto y no deseas la sobrecarga de estas sumas de verificación, puedes establecer esto en false.
Ten en cuenta que incluso cuando esto se establece en false, git-annex realiza verificaciones en algunos casos extremos, donde es probable que un objeto se haya descargado incorrectamente, o cuando sea necesario por seguridad.
remote.<name>.annex-fastcopy, annex.fastcopy
Establecer en "true" para optimizar la copia de archivos hacia/desde un remoto.
Establecer esto permite que cp utilice la llamada al sistema copy_file_range. (Cuando el comando cp lo soporte). El beneficio depende del sistema de archivos. Por ejemplo, en NFS, esto puede permitir una copia del lado del servidor. En ext4, esto evita cierta sobrecarga de transferencia de memoria, pero el archivo aún necesita ser copiado. No hay beneficio en btrfs, ya que git-annex realiza la vinculación CoW equivalente y rápida en btrfs por defecto.
Esto aportará poco para mejorar la velocidad de copia cuando git-annex necesita leer el archivo copiado para verificarlo. Por lo tanto, para una velocidad máxima, además de establecer esta opción, establece remote.<name>.annex-verify o annex.verify en false.
Actualmente, establecer esto impide reanudar copias interrumpidas donde quedaron. Una copia interrumpida se ejecutará nuevamente desde el principio.
remote.<name>.annex-tracking-branch
Esto es para usar con remotos especiales que admiten exportaciones e importaciones.
Cuando se establece en, por ejemplo, "master", esto le dice a git-annex que deseas que el remoto especial rastree esa rama.
Cuando se establece en, por ejemplo, "master:subdir", el remoto especial rastrea solo el subdirectorio de esa rama.
Establecer esto habilita otros comandos para trabajar con estos remotos especiales: git-annex pull importará cambios del remoto y los fusionará en la rama de seguimiento de anexos. Y git-annex push exportará cambios al remoto. Los comandos de nivel superior git-annex sync --content y git-annex assist importan y exportan.

remote.<name>.annexUrl
Se puede usar para especificar una URL diferente a la regular remote.<name>.url para que git-annex acceda al remoto. Similar a pushUrl utilizado por git-push.
Cuando esto se establece en una URL annex+http o annex+https, esa URL se utiliza solo para operaciones de git-annex, y remote.<name>.url se utiliza para operaciones git. Esto permite usar git-annex-p2phttp para servir un repositorio git-annex a través de http.
Cuando esto y remote.<name>.url contienen el mismo nombre de host, y esta es una URL annex+http(s), y esa es también una URL http(s), git-annex asume que se pueden usar el mismo nombre de usuario y contraseña para ambas URL. remote.<name>.annex-stalldetection, annex.stalldetection
Configurar esto permite detectar transferencias estancadas o demasiado lentas, y manejarlas, para que en lugar de quedarse atascado, git-annex cancele la operación estancada. La transferencia se considerará fallida, por lo que las configuraciones como annex.retry controlarán lo que hace a continuación.
El valor predeterminado es detectar automáticamente cuándo las transferencias probablemente se han estancado, y sugerir la configuración de esto, pero no cancelar las operaciones estancadas. Para que esto funcione, un remoto necesita actualizar su progreso de manera consistente. Los remotos que no lo hagan no tendrán detección automática de estancamiento. Y puede pasar un tiempo para que git-annex decida que un remoto está realmente estancado cuando se utiliza la detección automática de estancamiento, ya que necesita ser conservador sobre lo que parece un estancamiento.
Establecer en "false" para evitar todos los intentos de detección de estancamiento.
Para detectar
y cancelar transferencias detenidas, configúralo con un valor en el formato "<cantidad>/<periododetiempo>" que especifica cuántos datos git-annex debería esperar ver fluyendo, como mínimo, durante un período de tiempo determinado.
Por ejemplo, para detectar bloqueos totales donde no se han transferido datos después de 30 segundos: git config annex.stalldetection "1KB/30s"
O, si tienes un remoto en una unidad USB que normalmente es capaz de varios megabytes por segundo, pero tiene sectores defectuosos donde se atasca durante mucho tiempo, podrías usar: git config remote.usbdrive.annex-stalldetection "1MB/1m"
Algunos remotos no informan sobre el progreso de la transferencia y los bloqueos no pueden detectarse al usarlos.
Algunos remotos solo informan sobre el progreso de la transferencia ocasionalmente, por ejemplo, después de cada fragmento. Para evitar tiempos de espera falsos en tal situación, si la primera actualización de progreso tarda más en llegar que el período de tiempo configurado, la detección de bloqueo se ajustará automáticamente para usar un período de tiempo más largo. Por ejemplo, si la primera actualización de progreso llega después de 10 minutos, pero annex.stalldetection es "1MB/1m", se tratará como, por ejemplo, "30MB/30m".
La configuración de la detección de bloqueo puede hacer que git-annex utilice más recursos. Para poder cancelar bloqueos, git-annex tiene que ejecutar las transferencias en procesos separados (uno por trabajo concurrente). Por lo tanto, puede necesitar abrir más conexiones a un remoto de lo habitual, o la comunicación con esos procesos puede hacer que sea un poco más lento.

gitattributes

El backend clave-valor usado al añadir un nuevo archivo al annex se puede configurar por tipo de archivo a través de archivos .gitattributes. En el archivo, el atributo annex.backend se puede establecer al nombre del backend a usar. (Vea git-annex-backends(1) para información sobre los backends disponibles.) Por ejemplo, así es como usar el backend WORM por defecto, pero el backend SHA256E para archivos

ogg:


* annex.backend=WORM
*.ogg annex.

backend=SHA256E

Hay un atributo annex.largefiles, que se usa para configurar qué archivos son lo suficientemente grandes como para ser añadidos al annex. Dado que los atributos no pueden contener espacios, es difícil de usar para configuraciones de annex.largefiles más complejas. Establecer annex.largefiles en git-annex-config(1) es una forma más fácil de configurarlo en todos los clones del repositorio. Vea git-annex-matching-expression(1) para detalles sobre la

sintaxis.

Las configuraciones numcopies y mincopies también se pueden configurar por tipo de archivo a través de los atributos annex.numcopies y annex.mincopies en archivos .gitattributes. Esto anula otras configuraciones. Por ejemplo, esto hace que se necesiten dos copias para archivos wav y 3 copias para archivos

flac:


*.wav annex.numcopies=2
*.flac annex.

numcopies=3

Estas configuraciones son respetadas por git-annex siempre que esté operando en un archivo que coincida. Sin embargo, al usar --all, --unused, o --key para especificar claves sobre las que operar, git-annex está operando en claves y no en archivos, por lo que no respetará las configuraciones de .gitattributes. Por esta razón, los comandos git annex numcopies y git annex mincopies son útiles para configurar un valor predeterminado

global.

Tenga en cuenta también que al usar vistas, solo el archivo .gita

ttributes de nivel superior se conserva en la vista, por lo que
otras configuraciones en otros archivos no tendrán ningún efecto.
