NOMBRE

git-fast-import - Backend para importadores rápidos de datos de Git

SINOPSIS

frontend | git fast-import [<opciones>]

DESCRIPCIÓN

Este programa normalmente no es lo que el usuario final quiere ejecutar directamente. La mayoría de los usuarios finales quieren usar uno de los programas frontend existentes, que analiza un tipo específico de fuente externa y alimenta el contenido almacenado allí a git fast-import.

fast-import lee un flujo mixto de comandos y datos desde la entrada estándar y escribe uno o más archivos de paquete directamente en el repositorio actual. Cuando se recibe EOF en la entrada estándar, fast import escribe las referencias de rama y etiqueta actualizadas, actualizando completamente el repositorio actual con los datos recién importados.

El backend fast-import en sí mismo puede importar en un repositorio vacío (uno que ya haya sido inicializado por git init) o actualizar incrementalmente un repositorio existente poblado. Si se admiten importaciones incrementales desde una fuente externa particular depende del programa frontend en uso.

OPCIONES

--force

Forzar la actualización de ramas existentes modificadas, incluso si hacer así causaría que se pierdan commits (ya que el nuevo commit no contiene el commit antiguo).

--quiet

Deshabilitar la salida mostrada por --stats, haciendo que fast-import normalmente esté silencioso cuando tiene éxito. Sin embargo, si el flujo de importación tiene directivas destinadas a mostrar salida al usuario (por ejemplo, progress ), los mensajes correspondientes seguirán mostrándose.

--stats

Mostrar algunas estadísticas básicas sobre los objetos que fast-import ha creado, los archivos de paquete en los que fueron almacenados y la memoria usada por fast-import durante esta ejecución. Mostrar esta salida es actualmente el valor predeterminado, pero puede deshabilitarse con --quiet.

--allow-unsafe-features

Muchas opciones de línea de comandos pueden proporcionarse como parte del flujo fast-import en sí mismo usando los comandos feature o option . Sin embargo, algunas de estas opciones son inseguras (por ejemplo, permitir a fast-import acceder al sistema de archivos fuera del repositorio). Estas opciones están deshabilitadas por defecto, pero pueden permitirse proporcionando esta opción en la línea de comandos. Esto actualmente afecta solo a los comandos de característica export-marks, import-marksy import-marks-if-exists .

¡Solo habilite esta opción si confía en el programa que genera el flujo fast-import! Esta opción se habilita automáticamente para los asistentes remotos que usan la capacidad import , ya que ya se les confía para ejecutar su propio código.

--signed-tags=(verbatim|warn-verbatim|warn-strip|strip|abort)

Especificar cómo manejar etiquetas firmadas. Se comporta de la misma manera que la misma opción en git-fast-export(1), excepto que el valor predeterminado es verbatim (en lugar de abort).

--signed-commits=(verbatim|warn-verbatim|warn-strip|strip|abort)

Especificar cómo manejar commits firmados. Se comporta de la misma manera que la misma opción en git-fast-export(1), excepto que el valor predeterminado es verbatim (en lugar de abort).

Opciones para Frontends

--cat-blob-fd=<fd>

Escribir las respuestas a las consultas get-mark, cat-bloby ls en el descriptor de archivo <fd> en lugar de stdout. Permite que la salida progress destinada al usuario final se separe de otras salidas.

--date-format=<fmt>

Especificar el tipo de fechas que el frontend proporcionará a fast-import dentro de los comandos author, committer y tagger . Vea "Formatos de Fecha" más abajo para detalles sobre qué formatos son soportados y su sintaxis.

--done

Terminar con error si no hay un comando done al final del flujo. Esta opción puede ser útil para detectar errores que causan que el frontend termine antes de haber comenzado a escribir un flujo.

Ubicaciones de los Archivos de Marcas

--export-marks=<file>

Vuelca la tabla interna de marcas a <file> cuando se completa. Las marcas se escriben una por línea como :markid SHA-1. Los frontends pueden usar este archivo para validar importaciones después de que se han completado, o para guardar la tabla de marcas a través de ejecuciones incrementales. Como <file> solo se abre y trunca en el punto de control (o finalización), la misma ruta puede darse de forma segura también a --import-marks.

--import-marks=<file>

Antes de procesar cualquier entrada, cargar las marcas especificadas en <file>. El archivo de entrada debe existir, debe ser legible y debe usar el mismo formato que produce --export-marks. Se pueden proporcionar múltiples opciones para importar más de un conjunto de marcas. Si una marca está definida con valores diferentes, el último archivo gana.

--import-marks-if-exists=<file>

Como --import-marks pero en lugar de generar un error, omite silenciosamente el archivo si no existe.

--relative-marks, --no-relative-marks

Después de especificar --relative-marks, las rutas especificadas con --import-marks= y --export-marks= son relativas a un directorio interno en el repositorio actual. En git-fast-import esto significa que las rutas son relativas al directorio .git/info/fast-import. Sin embargo, otros importadores pueden usar una ubicación diferente.

Las marcas relativas y no relativas pueden combinarse intercalando --(no-)-relative-marks con las opciones --(import|export)-marks=.

Reescritura de Submódulos

--rewrite-submodules-from=<name>:<file>, --rewrite-submodules-to=<name>:<file>

Reescribir los IDs de objeto para el submódulo especificado por <name> desde los valores usados en el archivo from <file> a los usados en el archivo to <file>. Las marcas from deberían haber sido creadas por git fast-export, y las marcas to deberían haber sido creadas por git fast-import al importar ese mismo submódulo.

<name> puede ser cualquier cadena arbitraria que no contenga un carácter de dos puntos, pero se debe usar el mismo valor con ambas opciones al especificar marcas correspondientes. Se pueden especificar múltiples submódulos con valores diferentes para <name>. Es un error no usar estas opciones en pares correspondientes.

Estas opciones son principalmente útiles al convertir un repositorio de un algoritmo de hash a otro; sin ellas, fast-import fallará si encuentra un submódulo porque no tiene forma de escribir el ID de objeto en el nuevo algoritmo de hash.

Ajuste de Rendimiento y Compresión

--active-branches=<n>

Número máximo de ramas para mantener activas a la vez. Vea "Utilización de Memoria" más abajo para detalles. El valor predeterminado es 5.

--big-file-threshold=<n>

Tamaño máximo de un blob para el que fast-import intentará crear un delta, expresado en bytes. El valor predeterminado es 512m (512 MiB). Algunos importadores pueden desear reducir esto en sistemas con memoria limitada.

--depth=<n>

Profundidad máxima de delta, para la deltificación de blobs y árboles. El valor predeterminado es 50.

--export-pack-edges=<file>

Después de crear un archivo de paquete, imprimir una línea de datos en <file> listando el nombre de archivo del archivo de paquete y el último commit en cada rama que fue escrita en ese archivo de paquete. Esta información puede ser útil después de importar proyectos cuyo conjunto total de objetos excede el límite de 4 GiB del archivo de paquete, ya que estos commits pueden usarse como puntos de borde durante las llamadas a git pack-objects.

--max-pack-size=<n>

Tamaño máximo de cada archivo de paquete de salida. El valor predeterminado es ilimitado.

fastimport.unpackLimit

Vea git-config(1)

RENDIMIENTO

El diseño de fast-import le permite importar proyectos grandes con un mínimo de uso de memoria y tiempo de procesamiento. Asumiendo que el frontend es capaz de seguir el ritmo de fast-import y alimentarlo con un flujo constante de datos, los tiempos de importación para proyectos que contienen 10+ años de historia y que contienen 100.000+ commits individuales se completan generalmente en solo 1-2 horas con hardware bastante modesto (~2.000 USD en 2007).

La mayoría de los cuellos de botella parecen estar en el acceso a datos de origen extranjeros (la fuente simplemente no puede extraer revisiones lo suficientemente rápido) o en la E/S de disco (fast-import escribe tan rápido como el disco lo permite). Las importaciones se ejecutarán más rápido si los datos de origen se almacenan en una unidad diferente a la del repositorio Git de destino (debido a una menor contención de E/S).

COSTO DE DESARROLLO

Un frontend típico para fast-import tiende a pesar aproximadamente 200 líneas de código Perl/Python/Ruby. La mayoría de los desarrolladores han podido crear importadores funcionales en solo un par de horas, incluso si es su primera exposición a fast-import, y a veces incluso a Git. Esta es una situación ideal, dado que la mayoría de las herramientas de conversión son desechables (se usan una vez y nunca se vuelven a mirar).

OPERACIÓN PARALELA

Al igual que git push o git fetch, las importaciones manejadas por fast-import son seguras para ejecutarse junto con invocaciones paralelas de git repack -a -d o git gc, o cualquier otra operación de Git (incluyendo git prune, ya que los objetos sueltos nunca son utilizados por fast-import).

fast-import no bloquea las referencias de ramas o etiquetas que está importando activamente. Después de la importación, durante su fase de actualización de referencias, fast-import prueba cada referencia de rama existente para verificar que la actualización sea una actualización de avance rápido (el commit almacenado en la referencia está contenido en el nuevo historial del commit que se va a escribir). Si la actualización no es una actualización de avance rápido, fast-import omitirá la actualización de esa referencia y en su lugar mostrará un mensaje de advertencia. fast-import siempre intentará actualizar todas las referencias de rama, y no se detiene ante el primer fallo.

Las actualizaciones de rama se pueden forzar con --force, pero se recomienda que esto solo se use en un repositorio que de lo contrario esté tranquilo. Usar --force no es necesario para una importación inicial en un repositorio vacío.

DISCUSIÓN TÉCNICA

fast-import rastrea un conjunto de ramas en memoria. Cualquier rama puede ser creada o modificada en cualquier momento durante el proceso de importación enviando un comando commit en el flujo de entrada. Este diseño permite que un programa frontend procese un número ilimitado de ramas simultáneamente, generando commits en el orden en que están disponibles a partir de los datos de origen. También simplifica considerablemente los programas frontend.

fast-import no usa ni altera el directorio de trabajo actual, ni ningún archivo dentro de él. (Sin embargo, sí actualiza el repositorio Git actual, según lo referenciado por GIT_DIR). Por lo tanto, un frontend de importación puede usar el directorio de trabajo para sus propios propósitos, como extraer revisiones de archivos del origen extranjero. Esta ignorancia del directorio de trabajo también permite que fast-import se ejecute muy rápido, ya que no necesita realizar ninguna operación costosa de actualización de archivos al cambiar entre ramas.

FORMATO DE ENTRADA

Con la excepción de los datos de archivo sin procesar (que Git no interpreta), el formato de entrada de fast-import está basado en texto (ASCII). Este formato basado en texto simplifica el desarrollo y la depuración de programas frontend, especialmente cuando se utiliza un lenguaje de alto nivel como Perl, Python o Ruby.

fast-import es muy estricto con su entrada. Donde decimos SP a continuación, nos referimos a exactamente un espacio. Asimismo, LF significa un (y solo un) salto de línea y HT un (y solo un) tabulador horizontal. Suministrar caracteres de espacio en blanco adicionales causará resultados inesperados, como nombres de rama o nombres de archivo con espacios iniciales o finales en su nombre, o la terminación temprana de fast-import cuando encuentre entrada inesperada.

Comentarios de flujo

Para ayudar en la depuración de frontends, fast-import ignora cualquier línea que comience con # (signo de almohadilla/hash ASCII) hasta e incluyendo el final de línea LF. Una línea de comentario puede contener cualquier secuencia de bytes que no contenga un LF y, por lo tanto, puede usarse para incluir información de depuración detallada que pueda ser específica del frontend y útil al inspeccionar un flujo de datos de fast-import.

Formatos de fecha

Se admiten los siguientes formatos de fecha. Un frontend debe seleccionar el formato que utilizará para esta importación pasando el nombre del formato en la opción de línea de comandos --date-format=<fmt>.

raw

Este es el formato nativo de Git y es <tiempo> SP <offutc>. También es el formato predeterminado de fast-import, si no se especificó --date-format.

El tiempo del evento se especifica mediante <tiempo> como el número de segundos desde la época UNIX (medianoche, 1 de enero de 1970, UTC) y se escribe como un entero decimal ASCII.

El desplazamiento local se especifica mediante <offutc> como un desplazamiento positivo o negativo de UTC. Por ejemplo, EST (que está 5 horas detrás de UTC) se expresaría en <tz> como "-0500", mientras que UTC es "+0000". El desplazamiento local no afecta a <tiempo>; se utiliza solo como una advertencia para ayudar a las rutinas de formato a mostrar la marca de tiempo.

Si el desplazamiento local no está disponible en el material de origen, use "+0000", o el desplazamiento local más común. Por ejemplo, muchas organizaciones tienen un repositorio CVS que solo ha sido accedido por usuarios que se encuentran en la misma ubicación y zona horaria. En este caso, se podría suponer un desplazamiento razonable de UTC.

A diferencia del formato rfc2822, este formato es muy estricto. Cualquier variación en el formato hará que fast-import rechace el valor, y también se pueden realizar algunas verificaciones de validez en los valores numéricos.

raw-permissive

Esto es lo mismo que raw excepto que no se realizan verificaciones de validez en la época numérica y el desplazamiento local. Esto puede ser útil al intentar filtrar o importar un historial existente con, por ejemplo, valores de zona horaria erróneos.

rfc2822

Este es el formato de fecha estándar descrito por RFC 2822.

Un valor de ejemplo es "Tue Feb 6 11:22:18 2007 -0500". El analizador de Git es preciso, pero un poco flexible. Es el mismo analizador que utiliza git am al aplicar parches recibidos por correo electrónico.

Algunas cadenas malformadas pueden ser aceptadas como fechas válidas. En algunos de estos casos, Git aún podrá obtener la fecha correcta de la cadena malformada. También hay algunos tipos de cadenas malformadas que Git analizará incorrectamente, y aun así las considerará válidas. Las cadenas seriamente malformadas serán rechazadas.

A diferencia del formato raw anterior, la información de zona horaria/desplazamiento UTC contenida en una cadena de fecha RFC 2822 se utiliza para ajustar el valor de la fecha a UTC antes del almacenamiento. Por lo tanto, es importante que esta información sea lo más precisa posible.

Si el material de origen utiliza fechas estilo RFC 2822, el frontend debería permitir que fast-import maneje el análisis y la conversión (en lugar de intentar hacerlo por sí mismo), ya que el analizador de Git ha sido bien probado en la práctica.

Los frontends deberían preferir el formato raw si el material de origen ya utiliza formato de época UNIX, puede ser persuadido para dar fechas en ese formato, o su formato es fácilmente convertible a él, ya que no hay ambigüedad en el análisis.

now

Utiliza siempre la hora y la zona horaria actuales. El literal now debe suministrarse siempre para <cuándo>.

Este es un formato de juguete. La hora y la zona horaria actuales de este sistema se copian siempre en la cadena de identidad en el momento en que está siendo creada por fast-import. No hay forma de especificar una hora o zona horaria diferente.

Este formato en particular se proporciona ya que es corto de implementar y puede ser útil para un proceso que desea crear un nuevo commit en este momento, sin necesidad de usar un directorio de trabajo o git update-index.

Si se utilizan comandos author y committer separados en un commit, las marcas de tiempo pueden no coincidir, ya que el reloj del sistema se consultará dos veces (una para cada comando). La única forma de garantizar que la información de identidad del autor y del committer tenga la misma marca de tiempo es omitir author (copiando así del committer) o usar un formato de fecha que no sea now.

Comandos

fast-import acepta varios comandos para actualizar el repositorio actual y controlar el proceso de importación actual. Una discusión más detallada (con ejemplos) de cada comando sigue más adelante.

commit

Crea una nueva rama o actualiza una rama existente creando un nuevo commit y actualizando la rama para que apunte al commit recién creado.

tag

Crea un objeto de etiqueta anotada a partir de un commit o rama existente. Las etiquetas ligeras no son compatibles con este comando, ya que no se recomiendan para registrar puntos significativos en el tiempo.

reset

Restablece una rama existente (o una nueva rama) a una revisión específica. Este comando debe usarse para cambiar una rama a una revisión específica sin hacer un commit en ella.

blob

Convierte datos de archivo sin procesar en un blob, para su uso futuro en un comando commit. Este comando es opcional y no es necesario para realizar una importación.

alias

Registra que una marca se refiere a un objeto dado sin crear primero ningún objeto nuevo. El uso de --import-marks y la referencia a marcas faltantes harán que fast-import falle, por lo que los alias pueden proporcionar una forma de establecer commits que de otro modo serían podados a un valor válido (por ejemplo, el ancestro válido más cercano no podado).

checkpoint

Fuerza a fast-import a cerrar el packfile actual, generar su checksum SHA-1 e índice únicos, y comenzar un nuevo packfile. Este comando es opcional y no es necesario para realizar una importación.

progress

Hace que fast-import repita toda la línea en su propia salida estándar. Este comando es opcional y no es necesario para realizar una importación.

done

Marca el final del flujo. Este comando es opcional a menos que se haya solicitado la función done utilizando la opción de línea de comandos --done o el comando feature done.

get-mark

data

Suministra datos sin procesar (para usar como contenido de blob/archivo, mensajes de commit o mensajes de etiquetas anotadas) a fast-import. Los datos se pueden suministrar utilizando un recuento exacto de bytes o delimitados por una línea de terminación. Los frontends reales destinados a conversiones de calidad de producción siempre deben usar el formato de recuento exacto de bytes, ya que es más robusto y tiene un mejor rendimiento. Formato de recuento exacto de bytes

El frontend debe especificar el número de bytes de datos. 
        'data' SP <count> LF
        <raw> LF?

donde <count> es el número exacto de bytes que aparecen dentro de <raw>. El valor de <count> se expresa como un entero decimal ASCII. El LF a cada lado de <raw> no está incluido en <count> y no se incluirá en los datos importados.

El LF después de <raw> es opcional (antes era obligatorio) pero recomendado. Incluirlo siempre facilita la depuración de un flujo de fast-import, ya que el siguiente comando siempre comienza en la columna 0 de la siguiente línea, incluso si <raw> no terminó con un LF.

        <raw> LF

        LF?

donde <delim> es la cadena delimitadora elegida. checkpoint

Fuerza a fast-import a cerrar el packfile actual, iniciar uno nuevo, y guardar todas las referencias de rama, etiquetas y marcas actuales.

        'checkpoint' LF
        LF?

Tenga en cuenta que fast-import cambia automáticamente los packfiles cuando el packfile actual alcanza --max-pack-size, o 4 GiB, el límite que sea menor. Durante un cambio automático de packfile, fast-import no actualiza las referencias de rama, las etiquetas ni las marcas.

Como un checkpoint puede requerir una cantidad significativa de tiempo de CPU y E/S de disco (para calcular la suma de verificación SHA-1 general del pack, generar el archivo de índice correspondiente y actualizar las referencias) puede tomar fácilmente varios minutos para que un solo comando checkpoint se complete.

Los frontends pueden optar por emitir puntos de control durante importaciones extremadamente grandes y de larga duración, o cuando necesitan permitir que otro proceso de Git acceda a una rama. Sin embargo, dado que un repositorio de Subversion de 30 GiB puede cargarse en Git a través de fast-import en aproximadamente 3 horas, es posible que los puntos de control explícitos no sean necesarios.

El LF después del comando es opcional (antes era obligatorio).

CAÍDAS

Si se proporciona una entrada no válida a fast-import, este terminará con un estado de salida distinto de cero y creará un informe de caída en el nivel superior del repositorio de Git en el que estaba importando. Los informes de caída contienen una instantánea del estado interno de fast-import, así como los comandos más recientes que condujeron a la

caída.

Todos los comandos recientes (incluyendo comentarios de flujo, cambios de archivos y comandos de progreso) se muestran en el historial de comandos dentro del informe de caída, pero los datos de archivo sin procesar y los mensajes de commit se excluyen del informe de caída. Esta exclusión ahorra espacio en el archivo de informe y reduce la cantidad de almacenamiento intermedio que fast-import debe realizar durante la

ejecución.

Después de escribir un informe de caída, fast-import cerrará el archivo de paquete actual y exportará la tabla de marcas. Esto permite al desarrollador del frontend inspeccionar el estado del repositorio y reanudar la importación desde el punto donde se produjo la caída. Las ramas y etiquetas modificadas no se actualizan durante una caída, ya que la importación no se completó con éxito. La información de ramas y etiquetas se puede encontrar en el informe de caída y debe aplicarse manualmente

si se necesita la actualización.

REPORT

CONSEJOS Y

TRUCOS

Los siguientes consejos y trucos se han recopilado de varios usuarios de fast-import y se ofrecen aquí como

sugerencias.

Use una marca por commitAl hacer una conversación de repositorio, use una marca única por commit ( mark : <n>) y proporcione la opción --export-marks en la línea de comandos. fast-import volcará un archivo que lista cada marca y el SHA-1 del objeto de Git que le corresponde. Si el frontend puede vincular las marcas de vuelta al repositorio de origen, es fácil verificar la precisión y completitud de la importación comparando cada commit de Git con la revisión de origen correspondiente

.

Viniendo de un sistema como Perforce o Subversion, esto debería ser

bastante simple, ya que la marca de fast-import también puede ser el
número de changeset de Perforce o el número de revisión de Subversion.

Salte libremente entre

ramas

No se moleste en intentar optimizar el frontend para ceñirse a una rama a la vez durante una importación. Aunque hacerlo podría ser ligeramente más rápido para fast-import, tiende a aumentar considerablemente la complejidad del código del

frontend.

El LRU de ramas incorporado en fast-import tiende a comportarse muy bien, y

el costo de activar una rama inactiva es tan bajo que moverse entre ramas
no tiene prácticamente ningún impacto en el rendimiento de la importación.

Manejo de

renombrados

Al importar un archivo o directorio renombrado, simplemente elimine el nombre(es) antiguo

(s) y modifique el nombre(es) nuevo(s) durante el commit correspondiente. Git realiza la
detección de renombrados después del hecho, en lugar de explícitamente durante un commit.

Usar ramas de corrección de etiquetas

Algunos otros sistemas SCM permiten al usuario crear una etiqueta a partir de múltiples archivos que no provienen del mismo commit/changeset. O crear etiquetas que son un subconjunto de los archivos disponibles en el repositorio.

Importar estas etiquetas tal cual en Git es imposible sin hacer al menos un commit que “corrija” los archivos para que coincidan con el contenido de la etiqueta. Usa el comando reset de fast-import para restablecer una rama ficticia fuera de tu espacio normal de ramas hasta el commit base de la etiqueta, luego haz uno o más commits de corrección de archivos, y finalmente etiqueta la rama ficticia.

Por ejemplo, dado que todas las ramas normales se almacenan bajo refs/heads/ nombra la rama de corrección de la etiqueta TAG_FIXUP. De esta manera es imposible que la rama de corrección usada por el importador tenga conflictos de espacio de nombres con ramas reales importadas desde el origen (el nombre TAG_FIXUP no es refs/heads/TAG_FIXUP).

Al hacer commits de correcciones, considera usar merge para conectar el/los commit(s) que proporcionan las revisiones de archivos a la rama de corrección. Hacer esto permitirá a herramientas como git blame rastrear a través del historial real de commits y anotar adecuadamente los archivos de origen.

Después de que fast-import termine, el frontend necesitará ejecutar rm .git/TAG_FIXUP para eliminar la rama ficticia.

Importar ahora, reempaquetar después

Tan pronto como fast-import complete, el repositorio Git es completamente válido y listo para usar. Típicamente esto toma solo un tiempo muy corto, incluso para proyectos considerablemente grandes (100,000+ commits).

Sin embargo, reempaquetar el repositorio es necesario para mejorar la localidad de datos y el rendimiento de acceso. También puede tomar horas en proyectos extremadamente grandes (especialmente si se usa -f y un parámetro --window grande). Dado que reempaquetar es seguro de ejecutar junto con lectores y escritores, ejecuta el reempaquetado en segundo plano y déjalo terminar cuando termine. ¡No hay razón para esperar para explorar tu nuevo proyecto Git!

Si eliges esperar al reempaquetado, no intentes ejecutar benchmarks o pruebas de rendimiento hasta que el reempaquetado se complete. fast-import genera packfiles subóptimos que simplemente nunca se ven en situaciones de uso real.

Reempaquetar datos históricos

Si estás reempaquetando datos importados muy antiguos (p. ej., más antiguos que el último año), considera gastar algo de tiempo extra de CPU y proporcionar --window=50 (o más alto) cuando ejecutes git repack. Esto tomará más tiempo, pero también producirá un packfile más pequeño. Solo necesitas esforzarte una vez, y todos los que usen tu proyecto se beneficiarán del repositorio más pequeño.

Incluir algunos mensajes de progreso

De vez en cuando haz que tu frontend emita un mensaje progress a fast-import. El contenido de los mensajes es completamente de forma libre, así que una sugerencia sería imprimir el mes y año actuales cada vez que la fecha del commit actual se mueve al siguiente mes. Tus usuarios se sentirán mejor sabiendo cuánto del flujo de datos ha sido procesado.

OPTIMIZACIÓN DE PACKFILE

Al empaquetar un blob, fast-import siempre intenta hacer delta contra el último blob escrito. A menos que el frontend lo organice específicamente, esto probablemente no será una versión anterior del mismo archivo, así que el delta generado no será el más pequeño posible. El packfile resultante estará comprimido, pero no será óptimo.

Los frontends que tienen acceso eficiente a todas las revisiones de un solo archivo (por ejemplo, leyendo un archivo RCS/CVS ,v) pueden optar por proporcionar todas las revisiones de ese archivo como una secuencia de comandos blob consecutivos. Esto permite a fast-import hacer delta entre las diferentes revisiones del archivo, ahorrando espacio en el packfile final. Las marcas (marks) pueden usarse para identificar posteriormente revisiones individuales de archivos durante una secuencia de comandos commit .

El/los packfile(s) creados por fast-import no fomentan buenos patrones de acceso a disco. Esto se debe a que fast-import escribe los datos en el orden en que los recibe de la entrada estándar, mientras que Git típicamente organiza los datos dentro de los packfiles para que los datos más recientes (punta actual) aparezcan antes de los datos históricos. Git también agrupa los commits, acelerando el recorrido de revisiones a través de una mejor localidad de caché.

Por esta razón se recomienda encarecidamente que los usuarios reempaqueten el repositorio con git repack -a -d después de que fast-import complete, permitiendo a Git reorganizar los packfiles para un acceso a datos más rápido. Si los deltas de blobs son subóptimos (ver arriba), entonces añadir también la opción -f para forzar el recálculo de todos los deltas puede reducir significativamente el tamaño del packfile final (un 30-50% más pequeño puede ser bastante típico).

En lugar de ejecutar git repack también puedes ejecutar git gc --aggressive, lo cual también optimizará otras cosas después de una importación (p. ej., empaquetar refs sueltas). Como se indica en la sección "AGGRESSIVE" en git-gc(1) la opción --aggressive encontrará nuevos deltas con la opción -f de git-repack(1). Por las razones elaboradas arriba, usar --aggressive después de un fast-import es uno de los pocos casos donde se sabe que vale la pena.

UTILIZACIÓN DE MEMORIA

Hay una serie de factores que afectan cuánta memoria fast-import requiere para realizar una importación. Como las secciones críticas de Git central, fast-import usa sus propios asignadores de memoria para amortizar cualquier sobrecosto asociado con malloc. En la práctica, fast-import tiende a amortizar cualquier sobrecosto de malloc a 0, debido a su uso de asignaciones de bloques grandes.

por objeto

fast-import mantiene una estructura en memoria para cada objeto escrito en esta ejecución. En un sistema de 32 bits la estructura es de 32 bytes, en un sistema de 64 bits la estructura es de 40 bytes (debido a los tamaños de puntero más grandes). Los objetos en la tabla no se liberan hasta que fast-import termina. Importar 2 millones de objetos en un sistema de 32 bits requerirá aproximadamente 64 MiB de memoria.

La tabla de objetos es en realidad una hashtable indexada por el nombre del objeto (el SHA-1 único). Esta configuración de almacenamiento permite a fast-import reutilizar un objeto existente o ya escrito y evitar escribir duplicados en el packfile de salida. Los blobs duplicados son sorprendentemente comunes en una importación, típicamente debido a fusiones de ramas en el origen.

por marca (mark)

Las marcas se almacenan en un array disperso, usando 1 puntero (4 bytes u 8 bytes, dependiendo del tamaño del puntero) por marca. Aunque el array es disperso, se anima encarecidamente a los frontends a usar marcas entre 1 y n, donde n es el número total de marcas requeridas para esta importación.

por rama

Las ramas se clasifican como activas e inactivas. El uso de memoria de las dos clases es significativamente diferente.

Las ramas inactivas se almacenan en una estructura que usa 96 o 120 bytes (sistemas de 32 bits o 64 bits, respectivamente), más la longitud del nombre de la rama (típicamente menos de 200 bytes), por rama. fast-import manejará fácilmente hasta 10,000 ramas inactivas en menos de 2 MiB de memoria.

Las ramas activas tienen la misma sobrecarga que las ramas inactivas, pero también contienen copias de cada árbol que ha sido modificado recientemente en esa rama. Si el subárbol include no ha sido modificado desde que la rama se activó, su contenido no se cargará en memoria, pero si el subárbol src ha sido modificado por un commit desde que la rama se activó, entonces su contenido se cargará en memoria.

Dado que las ramas activas almacenan metadatos sobre los archivos contenidos en esa rama, su tamaño de almacenamiento en memoria puede crecer a un tamaño considerable (ver abajo).

fast-import mueve automáticamente las ramas activas a estado inactivo basándose en un simple algoritmo de uso menos reciente (LRU). La cadena LRU se actualiza en cada comando commit . El número máximo de ramas activas puede aumentarse o disminuirse en la línea de comandos con --active-branches=.

por árbol activo

Los árboles (también conocidos como directorios) usan solo 12 bytes de memoria además de la memoria requerida por sus entradas (ver “por archivo activo” abajo). El costo de un árbol es virtualmente 0, ya que su sobrecosto se amortiza sobre las entradas individuales de archivos.

por entrada de archivo activo

Los archivos (y punteros a subárboles) dentro de árboles activos requieren 52 u 64 bytes (plataformas de 32/64 bits) por entrada. Para conservar espacio, los nombres de archivos y árboles se agrupan en una tabla de cadenas común, permitiendo que el nombre de archivo “Makefile” use solo 16 bytes (después de incluir la sobrecosto de la cabecera de la cadena) sin importar cuántas veces ocurra dentro del proyecto.

El LRU de ramas activas, junto con el agrupamiento de nombres de archivo en cadenas y la carga diferida de subárboles, permite a fast-import importar eficientemente proyectos con 2,000+ ramas y 45,114+ archivos en una huella de memoria muy limitada (menos de 2.7 MiB por rama activa).

SEÑALES

Enviar SIGUSR1 al proceso git fast-import termina el packfile actual temprano, simulando un comando checkpoint . El operador impaciente puede usar esta facilidad para echar un vistazo a los objetos y refs de una importación en curso, al costo de algo de tiempo de ejecución adicional y peor compresión.

CONFIGURACIÓN

Todo lo que hay debajo de esta línea en esta sección se incluye selectivamente de la documentación de git-config(1) . El contenido es el mismo que el que se encuentra allí:

fastimport.unpackLimit

Si el número de objetos importados por git-fast-import(1) está por debajo de este límite, entonces los objetos serán desempaquetados en archivos de objetos sueltos. Sin embargo, si el número de objetos importados es igual o supera este límite, entonces el paquete se almacenará como un pack. Almacenar el paquete de un fast-import puede hacer que la operación de importación se complete más rápidoter, especialmente en sistemas de archivos lentos. Si no se establece, se utiliza el valor de transfer.unpackLimit en su lugar.
