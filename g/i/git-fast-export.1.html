DESCRIPCIÓ

N

Este programa vuelca las revisiones dadas en una forma adecuada para ser canalizada hacia git fast-im

port.

Puede usarse como un reemplazo legible para humanos de un bundle (véase git-bundle(1)), o como un formato que puede editarse antes de ser alimentado a git fast-import para realizar reescrituras de historial (una capacidad en la que se basan herramientas como git filt

er-re
po).

OPCIONE

S

--progress=<n

>
Inserta sentencias de progreso cada <n> objetos, para ser mostradas por git fast-import durante la
importación.

--signed-tags=(verbatim|warn-verbatim|warn-strip|strip|abort

)
Especifica cómo manejar etiquetas firmadas. Dado que cualquier transformación después de la exportación (o durante la exportación, como excluir revisiones) puede cambiar los hashes que se firman, las firmas pueden volverse inválidas.

Al pedir abort (que es el valor por defecto), este programa morirá al encontrar una etiqueta firmada. Con strip, las etiquetas se harán sin firmar silenciosamente, con warn-strip se harán sin firmar pero se mostrará una advertencia, con verbatim, se exportarán silenciosamente y con warn-verbatim (o warn, un sinónimo obsoleto), se exportarán, pero verás una advertencia. verbatim y warn-verbatim solo deben usarse si sabes que no se realizará ninguna transformación que afecte a las etiquetas o a cualquier commit en s

u historial por parte de ti o de fast-export o fast-import, o si
no te importa que la etiqueta resultante tenga una firma inválida.

--signed-commits=(verbatim|warn-verbatim|warn-strip|strip|abort

)
Especifica cómo manejar commits firmados. Se comporta exactamente igual que --signed-tags, pero para commits. El valor por defecto es strip, que es igual al comportamiento de versiones anteriores de este comando sin esta opción.

Cuando se exporta, una firma comienza

con:

gpgsig <git-hash-algo> <signature-format

>

donde <git-hash-algo> es el hash del objeto de Git, es decir "sha1" o "sha256", y <signature-format> es el tipo de firma, es decir "openpgp", "x509", "ssh" o

"unknown".

Por ejemplo, una firma OpenPGP en un commit SHA-1 comienza con gpgsig sha1 openpgp, mientras que una firma SSH en un commit SHA-256 comienza con gpgsig sha256 ssh

.

Aunque se exportan todas las firmas de un commit, un importador puede elegir aceptar solo algunas de ellas. Por ejemplo git-fast-import(1) actualmente almacena como máximo una firma por algoritmo hash de Git en cada

commit.

Nota
Esto es altamente experimental y el forma
to del flujo de datos puede cambiar en el
futuro sin garantías de compatibilidad.

--tag-of-filtered-object=(abort|drop|rewrite

)
Especifica cómo manejar etiquetas cuyo objeto etiquetado es filtrado. Dado que las revisiones y los archivos a exportar pueden limitarse por ruta, los objetos etiquetados pueden filtrarse completamente.

Al pedir abort (que es el valor por defecto), este programa morirá al encontrar una etiqueta así. Con drop se omitirán dichas etiquetas de la salida. Con rewrite, si el objeto etiquetado es un commit, se reescribirá la etiqueta para que etiquete un commit ancestro (mediante reescritura de padres; véase git-rev-

list(
1)).

-M,

-C
Realiza detección de movimientos y/o copias, como se describe en la página del manual de git-diff(1), y la usa para generar comandos de renombrado y copia en el volcado de salida.

Ten en cuenta que versiones anteriores de est

e comando no se quejaban y producían resul
tados incorrectos si le dabas estas opciones.

--export-marks=<archivo

>
Vuelca la tabla de marcas interna a <archivo> cuando esté completa. Las marcas se escriben una por línea como :markid SHA-1. Solo se vuelcan las marcas para revisiones; las marcas para blobs se ignoran. Los backends pueden usar este archivo para validar importaciones después de que se hayan completado, o para guardar la tabla de marcas entre ejecuciones incrementales. Como <archivo> solo se abre y trunca al completarse, la misma ruta también puede darse de forma segura a --import-marks. El archivo no se escribirá si no se ha marcado/exportado ningún objeto
nuevo.

--import-marks=<archivo

>
Antes de procesar cualquier entrada, carga las marcas especificadas en <archivo>. El archivo de entrada debe existir, debe ser legible y debe usar el mismo formato que el producido por
--export-marks.

--mark-tag

s
Además de etiquetar blobs y commits con identificadores de marca, también etiqueta etiquetas. Esto es útil en combinación con --export-marks y --import-marks, y también es útil (y necesario) para la exportación de etiquetas anidadas. No perjudica a otros casos y debería ser el valor por defecto, pero muchos frontends de fast-import no están preparados para aceptar etiquetas con identificadores de marca.

Cualquier commit (o etiqueta) que ya haya sido marcado no será exportado de nuevo. Si

el backend usa un archivo --import-marks similar, esto permite la exportación bidire
ccional incremental del repositorio manteniendo las marcas iguales entre ejecuciones.

--fake-missing-tagge

r
Algunos repositorios antiguos tienen etiquetas sin tagger. El protocolo fast-import era bastante estricto con eso y no lo permitía. Así que se falsifica un tagger para poder hacer fast-import de la
salida.

--use-done-featur

e
Inicia el flujo con una estanza feature done y lo termina con un comando d
one.

--no-dat

a
Omite la salida de objetos blob y en su lugar hace referencia a blobs a través de su hash SHA-1 original. Esto es útil al reescribir la estructura de directorios o el historial de un repositorio sin tocar el contenido de archivos individuales. Ten en cuenta que el flujo resultante solo puede ser usado por un repositorio que ya contenga los objetos
necesarios.

--full-tre

e
Esta opción hará que fast-export emita una directiva "deleteall" para cada commit seguida de una lista completa de todos los archivos en el commit (en lugar de solo listar los archivos que son diferentes del primer padre del commit)
.

--anonymiz

e
Anonimiza el contenido del repositorio mientras aún conserva la forma del historial y el árbol almacenado. Véase la sección sobre ANONIMIZACIÓN más
abajo.

--anonymize-map=<desde>[:<hasta>

]
Convierte el token <desde> a <hasta> en la salida anonimizada. Si <hasta> se omite, mapea <desde> a sí mismo (es decir, no lo anonimiza). Véase la sección sobre ANONIMIZACIÓN más
abajo.

--reference-excluded-parent

s
Por defecto, ejecutar un comando como git fast-export master~5..master no incluirá el commit master~5 y hará que master~4 ya no tenga master~5 como padre (aunque tanto el antiguo master~4 como el nuevo master~4 tendrán todos los mismos archivos). Usa --reference-excluded-parents para que en su lugar el flujo haga referencia a commits en el rango excluido del historial por su sha1sum. Ten en cuenta que el flujo resultante solo puede ser usado por un repositorio que ya contenga los commits padre
necesarios.

--show-original-id

s
Añade una directiva extra a la salida para commits y blobs, original-oid <SHA1SUM>. Aunque dichas directivas serán probablemente ignoradas por importadores como git-fast-import, puede ser útil para filtros intermedios (p. ej., para reescribir mensajes de commit que hacen referencia a commits antiguos, o para eliminar blobs por id)
.

--reencode=(yes|no|abort

)
Especifica cómo manejar la cabecera de codificación en objetos commit. Al pedir abort (que es el valor por defecto), este programa morirá al encontrar un objeto commit así. Con yes, el mensaje del commit se recodificará a UTF-8. Con no, se preservará la codificación
original.

--refspe

c
Aplica el refspec especificado a cada ref exportado. Se pueden especificar
varios.

[<argumentos de git-rev-list>...

]
Una lista de argumentos, aceptables por git rev-parse y git rev-list, que especifica los objetos y referencias específicos a exportar. Por ejemplo, master~10..master hace que la referencia master actual se exporte junto con todos los objetos añadidos desde su commit ancestro número 10 y (a menos que se use la opción --reference-excluded-parents se especifican) todos
los archivos comunes a
master~9 y master~10.

EJEMPLO

S 
$ git fast-export --al
l | (cd /empty/reposito
ry && git fast-import)

Esto exportará el repositorio completo y lo importará en el repositorio vacío existente. Excepto por la recodificación de los commits que no están en UTF-8, sería un espejo uno a

uno. 
$ git fast-export master~5..master |
sed "s|refs/heads/master|refs/h
eads/other|" | git fast-import

Esto crea una nueva rama llamada other a partir de master~5..master (es decir, si master tiene un historial lineal, tomará los últimos 5 commits)

.

Ten en cuenta que esto asume que ninguno de los blobs y mensajes de commit referenciados por ese rango de revisiones contiene la cadena refs/heads/maste

r
.

ANONIMIZACIÓ

N

Si se proporciona la opción --anonymize, git intentará eliminar toda la información identificativa del repositorio mientras retiene suficiente del árbol y los patrones de historial originales para reproducir algunos errores. El objetivo es que un error de git que se encuentre en un repositorio privado persista en el repositorio anonimizado, y que este último pueda compartirse con los desarrolladores de git para ayudar a resolver el

error.

Con esta opción, git reemplazará todos los nombres de refs, rutas, contenidos de blobs, mensajes de commit y etiquetas, nombres y direcciones de correo electrónico en la salida con datos anonimizados. Dos instancias de la misma cadena serán reemplazadas de manera equivalente (por ejemplo, dos commits con el mismo autor tendrán el mismo autor anonimizado en la salida, pero no se parecerán en nada a la cadena del autor original). La relación entre commits, ramas y etiquetas se conserva, así como las marcas de tiempo de los commits (pero los mensajes de commit y los nombres de refs no se parecen en nada a los originales). La composición relativa del árbol se conserva (por ejemplo, si tienes un árbol raíz con 10 archivos y 3 árboles, la salida también los tendrá), pero sus nombres y el contenido de los archivos serán

reemplazados.

Si crees que has encontrado un error de git, puedes comenzar exportando un flujo anonimizado del repositorio

completo: 
$ git fast-expor
t --anonymize --
all >anon-stream

Luego confirma que el error persiste en un repositorio creado a partir de ese flujo (muchos errores no lo harán, ya que realmente dependen del contenido exacto del repositorio)

: 
$ git init anon-repo
$ cd anon-repo
$ git fast-import <../anon-stream
$ ... prueba tu error .
.
.

Si el repositorio anonimizado muestra el error, podría valer la pena compartir anon-stream junto con un informe de errores normal. Ten en cuenta que el flujo anonimizado se comprime muy bien, por lo que se recomienda comprimirlo con gzip. Si quieres examinar el flujo para ver que no contiene ningún dato privado, puedes revisarlo directamente antes de enviarlo. También podrías

intentar: 
$ perl -pe 's/\d+
/X/g' <anon-stream
| sort -u | less

que muestra todas las líneas únicas (con los números convertidos a "X", para colapsar "User 0", "User 1", etc. en "User X"). Esto produce una salida mucho más pequeña, y normalmente es fácil confirmar rápidamente que no hay datos privados en el

flujo.

Reproducir algunos errores puede requerir referenciar commits o rutas particulares, lo cual se vuelve desafiante después de que los nombres de refs y las rutas han sido anonimizados. Puedes pedir que un token particular se deje tal cual o se mapee a un nuevo valor. Por ejemplo, si tienes un error que se reproduce con git rev-list sensitive -- secret.c, puedes

ejecutar: 
$ git fast-export --anonymize --all \
--anonymize-map=sensitive:foo \ --a
nonymize-map=secret.c:bar.c \ >stream

Después de importar el flujo, puedes ejecutar git rev-list foo -- bar.c en el repositorio

anonimizado.

Ten en cuenta que las rutas y los nombres de refs se dividen en tokens en los límites de las barras inclinadas. El comando de arriba anonimizaría subdir/secret.c como algo como path123/bar.c; luego podrías buscar bar.c en el repositorio anonimizado para determinar el nombre de ruta

final.

Para hacer más sencillo referenciar el nombre de ruta final, puedes mapear cada componente de la ruta; así que si también anonimizas subdir a publicdir, entonces el nombre de ruta final sería publicdi

r/ba
r.c.

LIMITACIONE

S

Dado que git fast-import no puede etiquetar árboles, no podrás exportar el repositorio linux.git c

ompletamente, ya que contiene una etiqueta
que referencia un árbol en lugar de un commit.
