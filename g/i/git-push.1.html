GIT-PUSH(1) Manual de Git GIT-PUSH(1)

NOMBRE

git-push - Actualiza referencias remotas junto con los objetos asociados

SINOPSIS

git push [--all | --branches | --mirror | --tags] [--follow-tags] [--atomic] [-n | --dry-run] [--receive-pack=<git-receive-pack>]
           [--repo=<repositorio>] [-f | --force] [-d | --delete] [--prune] [-q | --quiet] [-v | --verbose]
           [-u | --set-upstream] [-o <cadena> | --push-option=<cadena>]
           [--[no-]signed|--signed=(true|false|if-asked)]
           [--force-with-lease[=<refname>:<expect>]] [--force-if-includes]]
           [--no-verify] [<repositorio> [<refspec>...]]

DESCRIPCIÓN

Actualiza una o más ramas, etiquetas u otras referencias en un repositorio remoto desde tu repositorio local, y envía todos los datos necesarios que aún no están en el repositorio remoto.

La forma más sencilla de hacer push es git push <remoto> <rama>. git push origin main enviará la rama local main a la rama main en el remoto llamado origin.

El argumento <repositorio> por defecto es el upstream de la rama actual, o origin si no hay un upstream configurado.

Para decidir qué ramas, etiquetas u otras referencias enviar, Git utiliza (en orden de precedencia):

1.Los argumentos <refspec> (por ejemplo main en git push origin main) o las opciones --all, --mirror o --tags
2.La configuración remote.*.push para el repositorio al que se está enviando
3.La configuración push.default. El valor por defecto es push.default=simple, que enviará a una rama con el mismo nombre que la rama actual. Consulte la sección CONFIGURACIÓN para obtener más información sobre push.default.

git push puede fallar si no has configurado un upstream para la rama actual, dependiendo de lo que se haya configurado en push.default. Consulte la sección RAMAS UPSTREAM para obtener más información sobre cómo configurar y usar los upstreams.

Puedes hacer que sucedan cosas interesantes en un repositorio cada vez que haces push en él, configurando hooks allí. Consulte la documentación de git-receive-pack(1).

OPCIONES

<repositorio>

El repositorio "remoto" que es el destino de una operación de push. Este parámetro puede ser una URL (ver la sección URLS DE GIT abajo) o el nombre de un remoto (ver la sección REMOTOS abajo).

<refspec>...

Especifica qué ref de destino actualizar con qué objeto fuente.

El formato para un refspec es [+]<src>[:<dst>], por ejemplo main, main:other, o HEAD^:refs/heads/main.

El <src> suele ser el nombre de la rama local que se va a enviar, pero puede ser cualquier "expresión SHA-1" arbitraria (ver gitrevisions(7)).

El <dst> determina qué ref actualizar en el lado remoto. Debe ser el nombre de una rama, etiqueta u otra ref, no una expresión arbitraria.

El + es opcional y hace lo mismo que --force.

Puedes escribir un refspec utilizando la forma expandida completa (por ejemplo refs/heads/main:refs/heads/main) que especifica la fuente y el destino exactos, o con una forma más corta (por ejemplo main o main:other). Aquí están las reglas sobre cómo se expanden los refspecs, así como varias otras formas especiales de refspec:

•<src> sin un :<dst> significa actualizar la misma ref que <src>, a menos que la configuración remote.<repositorio>.push especifique un <dst> diferente. Por ejemplo, si main es una rama, entonces el refspec main se expande a main:refs/heads/main.
•Si <dst> se refiere inequívocamente a una ref en el remoto <repositorio>, expándela a esa ref. Por ejemplo, si v1.0 es una etiqueta en el remoto, entonces HEAD:v1.0 se expande a HEAD:refs/tags/v1.0.
•Si <src> se resuelve a una ref que comienza con refs/heads/ o refs/tags/, entonces prepón eso a <dst>. Por ejemplo, si main es una rama, entonces main:other se expande a main:refs/heads/other
•El refspec especial : (o +: para permitir actualizaciones no directas) indica a Git que envíe ramas "coincidentes": por cada rama que existe en el lado local, el lado remoto se actualiza si una rama del mismo nombre ya existe en el lado remoto.
•<src> puede contener un * para indicar una coincidencia de patrón simple. Esto funciona como un glob que coincide con cualquier ref que coincida con el patrón. Debe haber solo un * tanto en <src> como en <dst>. Mapeará refs al destino reemplazando el * con el contenido coincidente de la fuente. Por ejemplo, refs/heads/*:refs/heads/* enviará todas las ramas.
•Un refspec que comienza con ^ es un refspec negativo. Esto especifica refs a excluir. Una ref se considerará coincidente si coincide con al menos un refspec positivo y no coincide con ningún refspec negativo. Los refspecs negativos pueden ser refspecs de patrón. Solo deben contener un <src>. Tampoco se admiten nombres hexadecimales de objetos escritos de forma completa. Por ejemplo, git push origin 'refs/heads/*' '^refs/heads/dev-*' enviará todas las ramas excepto aquellas que comiencen con dev-
•Si <src> está vacío, elimina la ref <dst> del repositorio remoto. Por ejemplo, git push origin :dev eliminará la rama dev.
•tag <tag> se expande a refs/tags/<tag>:refs/tags/<tag>. Esto es técnicamente una sintaxis especial para git push y no un refspec, ya que en git push origin tag v1.0 los argumentos tag y v1.0 son separados.
•Si el refspec no se puede expandir de forma inequívoca, genera un error indicando lo que se intentó, y dependiendo de la configuración advice.pushUnqualifiedRefname (ver git-config(1)) sugiere a qué espacio de nombres refs/ podrías haber querido enviar.

No todas las actualizaciones están permitidas: ver REGLAS DE PUSH abajo para los detalles.

--all, --branches

Envía todas las ramas (es decir, refs bajo refs/heads/); no se puede usar con otros <refspec>.

--prune

Elimina las ramas remotas que no tienen una contraparte local. Por ejemplo, una rama remota tmp se eliminará si una rama local con el mismo nombre ya no existe. Esto también respeta los refspecs, por ejemplo git push --prune remote refs/heads/*:refs/tmp/* se asegurará de que refs/tmp/foo remoto se elimine si refs/heads/foo no existe.

--mirror

En lugar de nombrar cada ref a enviar, especifica que todas las refs bajo refs/ (que incluye pero no se limita a refs/heads/, refs/remotes/ y refs/tags/) se reflejen en el repositorio remoto. Las refs locales recién creadas se enviarán al extremo remoto, las refs locales actualizadas se forzarán en el extremo remoto y las refs eliminadas se eliminarán del extremo remoto. Esto es lo predeterminado si la opción de configuración remote.<remote>.mirror está establecida.

-n, --dry-run

Haz todo excepto enviar realmente las actualizaciones.

--porcelain

Produce una salida legible por máquina. La línea de estado de salida para cada ref estará separada por tabulaciones y se enviará a stdout en lugar de stderr. Se darán los nombres simbólicos completos de las refs.

-d, --delete

Todas las refs listadas se eliminan del repositorio remoto. Esto es lo mismo que prefijar todas las refs con dos puntos.

--tags

Todas las refs bajo refs/tags se envían, además de los refspecs listados explícitamente en la línea de comandos.

--follow-tags

Envía todas las refs que se enviarían sin esta opción, y también envía etiquetas anotadas en refs/tags que faltan en el remoto pero que apuntan a un commit-ish que es alcanzable desde las refs que se están enviando. Esto también se puede especificar con la variable de configuración push.followTags. Para más información, ver push.followTags en git-config(1).

--atomic

Asegura que todas las referencias se actualicen como una única transacción atómica. Si falla alguna actualización, ninguna se realiza. Las actualizaciones atómicas se envían como operaciones independientes y se ejecutan en ese orden.

--receive-pack=<git-receive-pack>

Es el comando que el lado remoto ejecutará para recibir el push. Normalmente no se necesita especificar.

--repo=<repositorio>

En lugar de usar la configuración de remoto, especifica el repositorio que se está enviando directamente con el argumento <repositorio>. Esto se utiliza para sobrescribir la configuración del remoto o para el uso en scripts.

-f, --force

Forzar la actualización de una rama remota, incluso si resulta en una actualización no directa. Esto es peligroso y puede llevar a la pérdida del historial. Úsalo con precaución.

--prune-tags

Elimina las etiquetas del repositorio remoto si ya no existen localmente. Esto se combina con otras operaciones de push, pero solo afecta a las etiquetas.

-q, --quiet

Suprime el mensaje de progreso y la salida detallada.

-v, --verbose

Activa la salida detallada.

-u, --set-upstream

Para cada rama enviada, configura la rama remota como el upstream de la rama local. Esto se utiliza para facilitar futuras operaciones de push y pull.

-o <cadena>, --push-option=<cadena>

Especifica una opción que se pasará al proceso de recepción del remoto. La opción puede usarse múltiples veces. Las opciones disponibles dependen del remoto.

--signed[=(true|false|if-asked)]

Indica si las actualizaciones de ref deben ser firmadas. Si se establece en true, Git intentará firmar las actualizaciones. Si se establece en false, Git no las firmará. Si se establece en if-asked, Git las firmará solo si se le solicita explícitamente (por ejemplo, mediante una variable de entorno).

--force-with-lease[=<refname>:<expect>]

Forzar la actualización de una rama remota solo si el ref en el remoto coincide con lo esperado. Si no se especifica <refname> o <expect>, el comportamiento predeterminado es verificar que el ref remoto no haya sido actualizado desde la última vez que se consultó. Esto ayuda a prevenir sobrescribir accidentalmente el trabajo de otros.

--force-if-includes

Permite un push forzado si los commits que se envían incluyen los commits que se esperaban para el ref.

--no-verify

Salta la ejecución de los hooks pre-push. Esto debe usarse con precaución ya que los hooks pre-push pueden contener validaciones importantes.

CONFIGURACIÓN

git-push tiene varias opciones de configuración que pueden afectar su comportamiento:

remote.<nombre>.push

Permite especificar un refspec por defecto para un remoto específico. Si se establece, se utilizará en lugar de push.default. Por ejemplo, para enviar todas las ramas locales a la rama correspondiente en el remoto `origin`, puedes usar: 
$ git config remote.origin.push refs/heads/*:refs/heads/*

push.default

Determina qué ramas se envían cuando no se especifica un refspec. Los valores posibles son:
  • simple: Envía solo la rama actual si tiene el mismo nombre que la rama remota correspondiente.

  • upstream: Envía solo la rama actual a su upstream.

  • current: Envía la rama actual a una rama con el mismo nombre en el remoto.

  • matching: Envía todas las ramas locales que tienen una rama coincidente en el remoto.
El valor por defecto es simple.

push.followTags

Si se establece en `true`, todas las etiquetas anotadas que apuntan a commits alcanzables por las refs que se envían también se enviarán.

push.autoSetupRemote

Si se establece en `true`, git push -u configurará automáticamente la rama remota como upstream para la rama local actual, incluso si no se especifica un nombre de rama.

EJEMPLOS

Para enviar la rama actual a su upstream:

$ git push

Para enviar la rama `main` al remoto `origin`:

$ git push origin main

Para enviar la rama `main` al remoto `origin` y configurarla como upstream:

$ git push -u origin main

Para enviar todas las ramas y etiquetas:

$ git push --all --tags

Para eliminar la rama `feature/old-stuff` del remoto `origin`:

$ git push origin --delete feature/old-stuff

Para enviar la rama `develop` al remoto `origin`, pero solo si el ref remoto `origin/develop` coincide con el commit local `HEAD`:

$ git push --force-with-lease origin develop

REGLAS DE PUSH

Por defecto, Git solo permite actualizaciones directas (fast-forward) para las ramas. Esto significa que el commit de destino debe ser un descendiente del commit actual. Si esto no es posible, el push fallará.

Se pueden especificar reglas de push para permitir o denegar ciertos tipos de actualizaciones. Estas reglas se pueden configurar en el archivo `.git/config` del repositorio local o en el archivo `config` del repositorio remoto.

Las reglas de push se definen utilizando la directiva `push.rule` en la sección `[branch "<nombre_rama>"]` o `[remote "<nombre_remoto>"]`.

Por ejemplo, para permitir actualizaciones no directas en la rama `main` del remoto `origin`, puedes añadir lo siguiente a tu `.git/config`:

[remote "origin"]
    push = +refs/heads/main:refs/heads/main

El prefijo `+` indica que se permiten actualizaciones no directas.

También puedes configurar reglas de push que prohíban explícitamente ciertos tipos de actualizaciones. Consulta la documentación de Git para obtener más detalles sobre las reglas de push.

GIT URLS

El parámetro <repository> puede ser una URL. Las URLs pueden estar en varios formatos:

Local:

    /path/to/repository
    file:///path/to/repository

Remoto (SSH):

    user@host.xz:/path/to/repository
    ssh://user@host.xz[:port]/path/to/repository

Remoto (HTTP/HTTPS):

    http://host.xz[:port]/path/to/repository.git
    https://host.xz[:port]/path/to/repository.git

Remoto (Git Protocol):

    git://host.xz[:port]/path/to/repository.git

REMOTES

Los remotos se configuran en el archivo `.git/config` bajo la sección `[remote "<nombre_remoto>"]`. Por ejemplo:

[remote "origin"]
    url = git@github.com:user/repo.git
    fetch = +refs/heads/*:refs/remotes/origin/*

Puedes gestionar tus remotos con `git remote`.

UPSTREAM BRANCHES

El concepto de upstream branch es fundamental para `git push`. Un upstream branch es una rama remota que se configura como el punto de seguimiento para una rama local.

Cuando ejecutas `git push -u`, configuras la rama remota como el upstream de tu rama local. Esto te permite usar `git push` sin argumentos y `git pull` sabrá dónde enviar o de dónde recibir las actualizaciones.

Puedes ver las relaciones de upstream con `git branch -vv`.

--signed, --no-signed, --signed=(true|false|if-asked)

Firma la solicitud de envío con GPG para actualizar las referencias en el lado receptor, para permitir su comprobación por los hooks y/o su registro. Si es false o --no-signed, no se intentará firmar. Si es true o --signed, el envío fallará si el servidor no soporta envíos firmados. Si se establece en if-asked, firmará solo si el servidor soporta envíos firmados. El envío también fallará si la llamada real a gpg --sign falla. Consulte git-receive-pack(1) para obtener detalles sobre el extremo receptor.

--atomic, --no-atomic

Utiliza una transacción atómica en el lado remoto si está disponible. Se actualizan todas las referencias o, en caso de error, no se actualiza ninguna. Si el servidor no soporta envíos atómicos, el envío fallará.

-o <opción>, --push-option=<opción>

Transmite la cadena dada al servidor, que la pasa al hook pre-receive y post-receive. La cadena dada no debe contener caracteres NUL ni LF. Cuando se proporcionan varias opciones --push-option=<opción>, todas se envían al otro lado en el orden especificado en la línea de comandos. Cuando no se proporciona ninguna opción --push-option=<opción> desde la línea de comandos, se utilizan los valores de la variable de configuración push.pushOption en su lugar.

--receive-pack=<git-receive-pack>, --exec=<git-receive-pack>

Ruta del programa git-receive-pack en el extremo remoto. A veces es útil al enviar a un repositorio remoto a través de ssh, y no se tiene el programa en un directorio de la $PATH predeterminada.

--force-with-lease, --no-force-with-lease, --force-with-lease=<nombre-ref>, --force-with-lease=<nombre-ref>:<esperado>

Normalmente, "git push" se niega a actualizar una referencia remota que no es un antecesor de la referencia local utilizada para sobrescribirla.

Esta opción anula esta restricción si el valor actual de la referencia remota es el valor esperado. "git push" falla de lo contrario.

Imagine que tiene que reorganizar lo que ya ha publicado. Tendrá que eludir la regla de "debe ser avance rápido" para reemplazar el historial que publicó originalmente con el historial reorganizado. Si alguien más se basó en su historial original mientras usted reorganizaba, la punta de la rama remota puede avanzar con su commit, y enviar ciegamente con --force perderá su trabajo.

Esta opción le permite indicar que espera que el historial que está actualizando sea el que reorganizó y quiere reemplazar. Si la referencia remota todavía apunta al commit que especificó, puede estar seguro de que nadie más hizo nada con la referencia. Es como tomar una "concesión" sobre la referencia sin bloquearla explícitamente, y la referencia remota se actualiza solo si la "concesión" sigue siendo válida.

--force-with-lease solo, sin especificar los detalles, protegerá todas las referencias remotas que vayan a ser actualizadas, exigiendo que su valor actual sea el mismo que el de la rama de seguimiento remoto que tenemos para ellas.

--force-with-lease=<nombre-ref>, sin especificar el valor esperado, protegerá la referencia nombrada (solo), si va a ser actualizada, exigiendo que su valor actual sea el mismo que el de la rama de seguimiento remoto que tenemos para ella.

--force-with-lease=<nombre-ref>:<esperado> protegerá la referencia nombrada (solo), si va a ser actualizada, exigiendo que su valor actual sea el mismo que el valor especificado <esperado> (que puede ser diferente de la rama de seguimiento remoto que tenemos para nombre-ref, o es posible que ni siquiera tengamos una rama de seguimiento remoto cuando se usa esta forma). Si <esperado> es una cadena vacía, entonces la referencia nombrada no debe existir aún.

Tenga en cuenta que todas las formas que no son --force-with-lease=<nombre-ref>:<esperado> que especifican explícitamente el valor actual esperado de la referencia todavía son experimentales y sus semánticas pueden cambiar a medida que ganamos experiencia con esta característica.

"--no-force-with-lease" cancelará todas las --force-with-lease anteriores en la línea de comandos.

Nota general sobre seguridad: suministrar esta opción sin un valor esperado, es decir, como --force-with-lease o --force-with-lease=<nombre-ref> interactúa muy mal con cualquier cosa que ejecute implícitamente git fetch en el remoto que se está enviando en segundo plano, por ejemplo, git fetch origin en su repositorio en un cronjob.

La protección que ofrece sobre --force es asegurar que los cambios posteriores en los que su trabajo no se basó no se sobrescriban, pero esto se derrota trivialmente si algún proceso en segundo plano está actualizando las referencias en segundo plano. No tenemos nada más que la información de seguimiento remoto como heurística para las referencias que se espera que haya visto y que esté dispuesto a sobrescribir.

Si su editor o algún otro sistema está ejecutando git fetch en segundo plano para usted, una forma de mitigar esto es simplemente configurar otro remoto:

git remote add origin-push $(git config remote.origin.url)
git fetch origin-push

Ahora, cuando el proceso en segundo plano ejecute git fetch origin, las referencias en origin-push no se actualizarán, y por lo tanto comandos como:

git push --force-with-lease origin-push

Fallarán a menos que ejecute manualmente git fetch origin-push. Este método, por supuesto, es completamente derrotado por algo que ejecuta git fetch --all, en cuyo caso necesitaría deshabilitarlo o hacer algo más tedioso como:

git fetch              # actualizar 'master' desde el remoto
git tag base master    # marcar nuestro punto base
git rebase -i master   # reescribir algunos commits
git push --force-with-lease=master:base master:master

Es decir, crear una etiqueta base para las versiones del código fuente que haya visto y esté dispuesto a sobrescribir, luego reescribir el historial y, finalmente, forzar el envío de los cambios a master si la versión remota todavía está en base, independientemente de cómo se haya actualizado su remotes/origin/master local en segundo plano.

Alternativamente, especificar --force-if-includes como una opción auxiliar junto con --force-with-lease[=<nombre-ref>] (es decir, sin indicar en qué commit exacto debe apuntar la referencia en el lado remoto, o qué referencias en el lado remoto están siendo protegidas) en el momento de "push" verificará si las actualizaciones de las referencias de seguimiento remoto que pueden haber sido actualizadas implícitamente en segundo plano se integran localmente antes de permitir una actualización forzada.

-f, --force

Normalmente, git push se negará a actualizar una rama que no es un antecesor del commit que se está enviando.

Esta opción deshabilita esa comprobación, las demás comprobaciones de seguridad en REGLAS DE ENVÍO más abajo, y las comprobaciones de --force-with-lease. Puede causar que el repositorio remoto pierda commits; úsela con cuidado.

Tenga en cuenta que --force se aplica a todas las referencias que se envían, por lo tanto, usarlo con push.default establecido en matching o con múltiples destinos de envío configurados con remote.*.push puede sobrescribir referencias distintas de la rama actual (incluidas referencias locales que están estrictamente detrás de su contraparte remota). Para forzar un envío solo a una rama, use un + delante del refspec a enviar (por ejemplo, git push origin +master para forzar un envío a la rama master). Consulte la sección <refspec>... más arriba para obtener detalles.

--force-if-includes, --no-force-if-includes

Forza una actualización solo si la punta de la referencia de seguimiento remoto se ha integrado localmente.

Esta opción habilita una comprobación que verifica si la punta de la referencia de seguimiento remoto es alcanzable desde una de las entradas del "reflog" de la rama local basada en ella para una reescritura. La comprobación garantiza que todas las actualizaciones del remoto se hayan incorporado localmente, rechazando la actualización forzada si no es así.

Si la opción se pasa sin especificar --force-with-lease, o se especifica junto con --force-with-lease=<nombre-ref>:<esperado>, es una "no-operación".

Especificar --no-force-if-includes deshabilita este comportamiento.

--repo=<repositorio>

Esta opción es equivalente al argumento <repositorio>. Si se especifican ambos, el argumento de la línea de comandos tiene prioridad.

-u, --set-upstream

Para cada rama que esté actualizada o se haya enviado correctamente, agregue una referencia remota (de seguimiento), utilizada por git-pull sin argumentos y otros comandos. Para más información, consulte branch.<nombre>.merge en git-config(1).

--thin, --no-thin

Estas opciones se pasan a git-send-pack(1). Una transferencia delgada reduce significativamente la cantidad de datos enviados cuando el remitente y el receptor comparten muchos de los mismos objetos en común. El valor predeterminado es --thin.

-q, --quiet

Suprime toda la salida, incluida la lista de referencias actualizadas, a menos que ocurra un error. El progreso no se informa al flujo de error estándar.

-v, --verbose

Ejecutar de forma detallada.

--progress

El estado de progreso se informa en el flujo de error estándar por defecto cuando está conectado a una terminal, a menos que se especifique -q. Esta bandera fuerza el estado de progreso incluso si el flujo de error estándar no está dirigido a una terminal.

--no-recurse-submodules, --recurse-submodules=check|on-demand|only|no

Puede usarse para asegurarse de que todos los commits de submódulos utilizados por las revisiones que se van a enviar estén disponibles en una rama de seguimiento remoto. Si se usa check, Git verificará que todos los commits de submódulos que cambiaron en las revisiones a enviar estén disponibles en al menos un remoto del submódulo. Si faltan commits, el envío se abortará y saldrá con un estado distinto de cero. Si se usa on-demand, se enviarán todos los submódulos que cambiaron en las revisiones a enviar. Si on-demand no pudo enviar todas las revisiones necesarias, también se abortará y saldrá con un estado distinto de cero. Si se usa only, se enviarán todos los submódulos mientras que el superproyecto quedará sin enviar. Un valor de no o el uso de --no-recurse-submodules puede usarse para anular la variable de configuración push.recurseSubmodules cuando no se requiere recursión de submódulos.

Al usar on-demand o only, si un submódulo tiene una configuración de "push.recurseSubmodules={on-demand,only}" o "submodule.recurse", recursión adicional.

SEGURIDA

D

Los protocolos fetch y push no están diseñados para evitar que una de las partes robe datos del otro repositorio que no pretendían ser compartidos. Si tienes datos privados que necesitas proteger de un par malicioso, tu mejor opción es almacenarlos en otro repositorio. Esto aplica tanto a clientes como a servidores. En particular, los espacios de nombres en un servidor no son efectivos para el control de acceso de lectura; solo deberías conceder acceso de lectura a un espacio de nombres a clientes en los que confiarías con acceso de lectura a todo el

repositorio.

Los vectores de ataque conocidos son los

siguientes:
1.La víctima envía líneas "have" anunciando los IDs de objetos que tiene que no están destinados explícitamente a ser compartidos pero que pueden usarse para optimizar la transferencia si el par también los tiene. El atacante elige un ID de objeto X para robar y envía una referencia a X, pero no está obligado a enviar el contenido de X porque la víctima ya lo tiene. Ahora la víctima cree que el atacante tiene X, y envía el contenido de X de vuelta al atacante más tarde. (Este ataque es más sencillo de realizar para un cliente en un servidor, al crear una referencia a X en el espacio de nombres al que el cliente tiene acceso y luego hacer fetch de él. La forma más probable para que un servidor lo realice en un cliente es "fusionar" X en una rama pública y esperar que el usuario haga trabajo adicional en esta rama y la empuje de vuelta al servidor sin notar la fusión.
)
2.Como en #1, el atacante elige un ID de objeto X para robar. La víctima envía un objeto Y que
el atacante ya tiene, y el atacante afirma falsamente tener X y no Y, por lo que la víctima env
ía Y como un delta contra X. El delta revela regiones de X que son similares a Y al atacante.

Además, este modo no es adecuado para empujar a un repositorio central compartido, ya que otras personas pueden añadir nuevas ramas allí, o actualizar la punta de ramas existentes fuera de tu

control.
