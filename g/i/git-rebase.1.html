GIT-REBASE(1) Manual de Git GIT-REBASE(1)

NOMBRE

git-rebase - Reaplicar commits sobre otro punto de partida

SINOPSIS

git rebase [-i | --interactive] [<opciones>] [--exec <comando>]
        [--onto <nuevo-punto-partida> | --keep-base] [<upstream> [<rama>]]
git rebase [-i | --interactive] [<opciones>] [--exec <comando>] [--onto <nuevo-punto-partida>]
        --root [<rama>]
git rebase (--continue|--skip|--abort|--quit|--edit-todo|--show-current-patch)

DESCRIPCIÓN

Transplanta una serie de commits a un punto de partida diferente. También puedes usar git rebase para reordenar o combinar commits: consulta MODO INTERACTIVO a continuación para saber cómo hacerlo.

Por ejemplo, imagina que has estado trabajando en la rama topic en este historial, y quieres "ponerte al día" con el trabajo realizado en la rama master.

          A---B---C topic
         /
    D---E---F---G master

Quieres trasplantar los commits que hiciste en topic desde que se separó de master (es decir, A, B y C), sobre el master actual. Puedes hacer esto ejecutando git rebase master mientras la rama topic está seleccionada. Si quieres hacer rebase de topic mientras estás en otra rama, git rebase master topic es un atajo para git checkout topic && git rebase master.

                  A'--B'--C' topic
                 /
    D---E---F---G master

Si hay un conflicto de fusión durante este proceso, git rebase se detendrá en el primer commit problemático y dejará marcadores de conflicto. Si esto sucede, puedes hacer una de estas cosas:

1.Resuelve el conflicto. Puedes usar git diff para encontrar los marcadores (<<<<<<) y hacer ediciones para resolver el conflicto. Para cada archivo que edites, necesitas indicarle a Git que el conflicto se ha resuelto. Puedes marcar el conflicto como resuelto con git add <nombre-archivo>. Después de resolver todos los conflictos, puedes continuar el proceso de rebase con 
git rebase --continue
2.Detén el git rebase y devuelve tu rama a su estado original con 
git rebase --abort
3.Omite el commit que causó el conflicto de fusión con 
git rebase --skip

Si no especificas un <upstream> sobre el cual hacer rebase, se usarán las opciones upstream configuradas en branch.<nombre>.remote y branch.<nombre>.merge (ver git-config(1) para más detalles) y se asumirá la opción --fork-point. Si actualmente no estás en ninguna rama o si la rama actual no tiene un upstream configurado, el rebase fallará.

Aquí hay una descripción simplificada de lo que hace git rebase <upstream>:

1.Haz una lista de todos los commits en tu rama actual desde que se separó de <upstream> que no tienen un commit equivalente en <upstream>.
2.Selecciona <upstream> con el equivalente a git checkout --detach <upstream>.
3.Vuelve a aplicar los commits, uno por uno, en orden. Esto es similar a ejecutar git cherry-pick <commit> para cada commit. Consulta REBASING MERGES para ver cómo se manejan las fusiones.
4.Actualiza tu rama para que apunte al commit final con el equivalente a git checkout -B <rama>.

Nota

Al iniciar el rebase, ORIG_HEAD se establece para apuntar al commit en la punta de la rama a ser rebasada. Sin embargo, ORIG_HEAD no está garantizado que siga apuntando a ese commit al final del rebase si otros comandos que cambian ORIG_HEAD (como git reset) se usan durante el rebase. La punta de rama anterior, sin embargo, es accesible usando el reflog de la rama actual (es decir, @{1}, ver gitrevisions(7).

TRASPLANTANDO UNA RAMA DE TEMA CON --ONTO

Aquí se explica cómo trasplantar una rama de tema basada en una rama a otra, para simular que bifurcaste la rama de tema de la última rama, usando rebase --onto.

Primero, asumamos que tu topic se basa en la rama next. Por ejemplo, una característica desarrollada en topic depende de alguna funcionalidad que se encuentra en next.

    o---o---o---o---o  master
         \
          o---o---o---o---o  next
                           \
                            o---o---o  topic

Queremos hacer que topic se bifurque de la rama master; por ejemplo, porque la funcionalidad en la que se basa topic se fusionó en la rama más estable master. Queremos que nuestro árbol se vea así:

    o---o---o---o---o  master
        |            \
        |             o'--o'--o'  topic
         \
          o---o---o---o---o  next

Podemos conseguir esto usando el siguiente comando:

git rebase --onto master next topic

Otro ejemplo de la opción --onto es hacer rebase de parte de una rama. Si tenemos la siguiente situación:

                            H---I---J topicB
                           /
                  E---F---G  topicA
                 /
    A---B---C---D  master

entonces el comando

git rebase --onto master topicA topicB

resultaría en:

                 H'--I'--J'  topicB
                /
                | E---F---G  topicA
                |/
    A---B---C---D  master

Esto es útil cuando topicB no depende de topicA.

También se puede eliminar un rango de commits con rebase. Si tenemos la siguiente situación:

    E---F---G---H---I---J  topicA

entonces el comando

git rebase --onto topicA~5 topicA~3 topicA

resultaría en la eliminación de los commits F y G:

    E---H'---I'---J'  topicA

Esto es útil si F y G tenían algún defecto, o no deberían formar parte de topicA. Ten en cuenta que el argumento para --onto y el parámetro <upstream> pueden ser cualquier commit válido.

OPCIONES DE MODO

Las opciones en esta sección no se pueden usar con ninguna otra opción, incluido no usarlas entre sí:

--continue

Reinicia el proceso de rebase después de haber resuelto un conflicto de fusión.

--skip

Reinicia el proceso de rebase omitiendo el parche actual.

--abort

Aborta la operación de rebase y restablece HEAD a la rama original. Si se proporcionó <rama> cuando se inició la operación de rebase, entonces HEAD se restablecerá a <rama>. De lo contrario, HEAD se restablecerá a donde estaba cuando se inició la operación de rebase.

--quit

Aborta la operación de rebase pero HEAD no se restablece a la rama original. El índice y el árbol de trabajo también se dejan sin cambios como resultado. Si se creó una entrada temporal de stash usando --autostash, se guardará en la lista de stash.

--edit-todo

Edita la lista de tareas pendientes durante un rebase interactivo.

--show-current-patch

Muestra el parche actual en un rebase interactivo o cuando el rebase se detiene debido a conflictos. Esto es el equivalente a git show REBASE_HEAD.

OPCIONES

--onto <nuevo-punto-partida>

Punto de partida sobre el cual crear los nuevos commits. Si la opción --onto no se especifica, el punto de partida es <upstream>. Puede ser cualquier commit válido, y no solo un nombre de rama existente.

Como caso especial, puedes usar "A...B" como atajo para la base de fusión de A y B si hay exactamente una base de fusión. Puedes omitir como máximo uno de A y B, en cuyo caso se usa HEAD por defecto.

--keep-bas

e
Establece el punto de inicio en el que crear los nuevos commits como la base de fusión de <upstream> y <branch>. Ejecutar git rebase --keep-base <upstream> <branch> es equivalente a ejecutar git rebase --reapply-cherry-picks --no-fork-point --onto <upstream>...<branch> <upstream> <branch>.

Esta opción es útil en el caso en que se está desarrollando una característica sobre una rama upstream. Mientras se trabaja en la característica, la rama upstream puede avanzar y puede que no sea la mejor idea seguir haciendo rebase sobre la rama upstream, sino mantener el commit base tal como está. Como el commit base no cambia, esta opción implica --reapply-cherry-picks para evitar perder

commits.

Aunque tanto esta opción como --fork-point encuentran la base de fusión entre <upstream> y <branch>, esta opción usa la base de fusión como el punto de inicio en el que se crearán los nuevos commits, mientras que --fork-point usa la base de fusión para determinar el conjunto de commits que serán

rebaseados.

--no-keep-empty,

--keep-empty
No mantener los commits que empiezan vacíos antes del rebase (es decir, que no cambian nada de su padre) en el resultado. El comportamiento por defecto es mantener los commits que empiezan vacíos, ya que crear tales commits requiere pasar la --allow-empty flag de anulación a git commit, lo que significa que un usuario está creando intencionalmente tal commit y por lo tanto quiere mantenerlo.

El uso de esta bandera probablemente será raro, ya que puede deshacerse de los commits que empiezan vacíos simplemente iniciando un rebase interactivo y eliminando las líneas correspondientes a los commits que no desea. Esta bandera existe como un acceso directo conveniente, como para los casos en que herramientas externas generan muchos commits vacíos y desea que todos sean

eliminados.

Para los commits que no empiezan vacíos pero se vuelven vacíos después del rebase, vea la --empty ban

dera.

--reapply-cherry-picks, --no-reapply-cherry-pick

s
Reaplicar todos los cherry-picks limpios de cualquier commit upstream en lugar de descartarlos preventivamente. (Si estos commits se vuelven vacíos después del rebase, porque contienen un subconjunto de cambios ya upstream, el comportamiento hacia ellos está controlado por la --empty bandera.)

En ausencia de --keep-base (o si se da --no-reapply-cherry-picks), estos commits serán descartados automáticamente. Debido a que esto requiere leer todos los commits upstream, esto puede ser costoso en repositorios con un gran número de commits upstream que necesitan ser leídos. Al usar el backend de fusión, se emitirán advertencias por cada commit descartado (a menos que se dé --quiet). También se emitirá un consejo a menos que advice.skippedCherryPicks se establezca en false (vea git-config(1))

.

--reapply-cherry-picks permite a rebase prescindir de leer todos los commits upstream, mejorando potencialmente el

rendimiento.

--fork-point,

--no-fork-point
Usar el reflog para encontrar un mejor ancestro común entre <upstream> y <branch> al calcular qué commits han sido introducidos por <branch>.

Cuando --fork-point está activo, fork_point se usará en lugar de <upstream> para calcular el conjunto de commits a rebasear, donde fork_point es el resultado del comando git merge-base --fork-point <upstream> <branch> (vea git-merge-base(1)). Si fork_point termina siendo vacío, se usará <upstream> como

alternativa.

Si se da <upstream> o --keep-base> en la línea de comandos, entonces el comportamiento por defecto es --no-fork-point, de lo contrario el comportamiento por defecto es --fork-point. Vea también rebase.forkpoint en git-confi

g(1).

rama.
