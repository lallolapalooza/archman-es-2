NOMBRE

git-annex-export - exportar un árbol de archivos a un remoto especial

SINOPSIS

git annex export treeish --to remoto

DESCRIPCIÓN

Utiliza este comando para exportar un árbol de archivos de un repositorio git-annex.

Normalmente los archivos se almacenan en un remoto especial de git-annex nombrado por sus claves. Eso es ideal para el almacenamiento fiable de datos, pero tus nombres de archivo quedan ofuscados. Exportar replica el árbol al remoto especial tal cual.

Para usar esto, tienes que configurar un remoto especial con exporttree=yes cuando lo inicializas con git-annex-initremote(1).

El treeish a exportar puede ser el nombre de una rama de git, o una etiqueta, o cualquier otro treeish aceptado por git, incluyendo por ejemplo master:subdir para exportar solo un subdirectorio de una rama.

Cuando el remoto tiene una expresión de contenido preferido configurada por git-annex-wanted(1), el treeish se filtra a través de ella, excluyendo los archivos anexados que no desea que se exporten allí. (Ten en cuenta que las cosas en la expresión como "include=" coinciden relativamente a la parte superior del treeish que se está exportando.)

Cualquier archivo en el treeish que esté almacenado en git también se exportará al remoto especial.

Las exportaciones repetidas se realizan de manera eficiente, comparando el árbol antiguo y el nuevo, y transfiriendo solo los archivos cambiados, y renombrando archivos según sea necesario.

Las exportaciones pueden interrumpirse y reanudarse. Sin embargo, los archivos parcialmente subidos se reiniciarán desde el principio en la mayoría de los casos.

Una vez que el contenido se ha exportado a un remoto, comandos como git annex get pueden descargar contenido desde allí igual que desde otros remotos. Sin embargo, dado que una exportación no es una tienda de clave/valor, git-annex tiene que realizar más verificación del contenido descargado de una exportación. Algunos tipos de claves, que no se basan en sumas de verificación, no pueden descargarse de una exportación. Y, git-annex nunca confiará en una exportación para retener el contenido de una clave.

Sin embargo, algunos remotos especiales, notablemente S3, admiten el seguimiento de versiones antiguas de archivos almacenados en ellos. Si un remoto especial está configurado para hacer eso, se puede usar como una tienda de clave/valor y las limitaciones en el párrafo anterior no se aplican. Ten en cuenta que eliminar contenido de dicho remoto no está soportado. Consulta la documentación individual de los remotos especiales para obtener detalles sobre cómo habilitar dicho versionado.

Comandos como git annex push también se pueden usar para exportar una rama a un remoto especial, actualizando el remoto especial cada vez que la rama cambie. Para hacer esto, necesitas configurar "remote.<nombre>.annex-tracking-branch" para decirle qué rama rastrear. Por ejemplo:


git config remote.myremote.annex-tracking-branch master
git annex push myremote

Puedes combinar el uso de git annex export para enviar cambios a un remoto especial con git annex import para obtener cambios desde un remoto especial. Cuando un archivo en un remoto especial ha sido modificado por software que no sea git-annex, exportarlo allí no sobrescribirá el archivo modificado, y la exportación no tendrá éxito. Puedes resolver este conflicto usando git annex import.

(Algunos tipos de remotos especiales como S3 con versionado pueden permitir en su lugar que una exportación sobrescriba el archivo modificado; entonces git annex import creará una secuencia de commits que incluye el archivo modificado, por lo que la modificación sobrescrita no se pierde.)

OPCIONES

--to=remoto
Especifica el remoto especial al que exportar.
--from=remoto
Cuando el contenido de un archivo no está disponible en el repositorio local, esta opción permite descargarlo de otro remoto y enviarlo al remoto de destino. El archivo se almacenará temporalmente en el disco local, pero nunca entrará en el repositorio local.
Esta opción se puede repetir varias veces.
Es posible usar --from con el mismo remoto que --to. Si el árbol contiene varios archivos con el mismo contenido, y el remoto al que se exporta ya contiene una copia del contenido, esto permite hacer una copia descargando el contenido de él.
--tracking
Esta es una forma obsoleta de establecer "remote.<nombre>.annex-tracking-branch". En lugar de usar esta opción, deberías configurar el git tú mismo.
--fast
Esto configura una exportación de un árbol, pero evita cualquier carga costosa de archivos al remoto. Más tarde puedes ejecutar git annex push para cargar los archivos a la exportación.
--jobs=N -JN
Exporta varios archivos en paralelo. Esto puede ser más rápido. Por ejemplo: -J4
Establecer esto a "cpus" ejecutará un trabajo por núcleo de CPU.
--json
Habilita la salida JSON. Esto está destinado a ser analizado por programas que usan git-annex. Cada línea de salida es un objeto JSON.
--json-progress
Incluye objetos de progreso en la salida JSON.
--json-error-messages
Los mensajes que normalmente se emitirían al error estándar se incluyen en el JSON en su lugar.
También se pueden usar las opciones comunes de git-annex(1).

EJEMPLO


git annex initremote myremote type=directory directory=/mnt/myremote \
exporttree=yes encryption=none
git annex export master --to myremote

Después de eso, /mnt/myremote contendrá el mismo árbol de archivos que la rama master.


git mv myfile subdir/myfile
git commit -m renombrado
git annex export master --to myremote

Eso actualiza /mnt/myremote para reflejar el archivo renombrado.


git annex export master:subdir --to myremote

Eso actualiza /mnt/myremote, para contener solo los archivos del directorio "subdir" de la rama master.

CONFLICTOS DE EXPORTACIÓN

Si dos repositorios git-annex diferentes están exportando árboles diferentes al mismo remoto especial, es posible que ocurra un conflicto de exportación. Esto deja al remoto especial con algunos archivos de un árbol y algunos archivos del otro. Los archivos en el remoto especial pueden tener contenido completamente incorrecto también.

No es posible que git-annex detecte cuándo hacer una exportación resultará en un conflicto de exportación. La mejor manera de evitar conflictos de exportación es exportar siempre a un remoto especial desde un único repositorio, o tener una regla sobre el árbol que se exporta al remoto especial. Por ejemplo, si siempre exportas origin/master después de enviar a origin, entonces no puede ocurrir un conflicto de exportación.

Un conflicto de exportación solo se puede detectar después de que los dos repositorios git que lo produjeron se sincronicen. Entonces, la próxima vez que ejecutes git annex export, detectará el conflicto de exportación y lo resolverá.
