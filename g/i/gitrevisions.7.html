GITREVISIONS(7) Manual de Git GITREVISIONS(7)

NOMBRE

gitrevisions - Especificar revisiones y rangos para Git

SINTAXIS

gitrevisions

DESCRIPCIÓN

Muchos comandos de Git toman parámetros de revisión como argumentos. Dependiendo del comando, denotan un commit específico o, para comandos que recorren el grafo de revisiones (como git-log(1)), todos los commits que son alcanzables desde ese commit. Para comandos que recorren el grafo de revisiones, también se puede especificar explícitamente un rango de revisiones.

Además, algunos comandos de Git (como git-show(1) y git-push(1)) también pueden tomar parámetros de revisión que denotan objetos distintos de commits, por ejemplo, blobs ("archivos") o árboles ("directorios de archivos").

ESPECIFICAR REVISIONES

Un parámetro de revisión <rev> típicamente, pero no necesariamente, nombra un objeto commit. Utiliza lo que se llama una sintaxis de SHA-1 extendido. Aquí hay varias formas de escribir nombres de objetos. Los que se enumeran cerca del final de esta lista nombran árboles y blobs contenidos en un commit.


Nota

Este documento muestra la sintaxis "cruda" tal como la ve Git. El shell y otras interfaces de usuario podrían requerir comillas adicionales para proteger caracteres especiales y evitar la división de palabras.

<sha1>, por ejemplo, dae86e1950b1277e545cee180551750029cfe735, dae86e

El nombre completo del objeto SHA-1 (cadena hexadecimal de 40 bytes), o una subcadena inicial que sea única en el repositorio. Por ejemplo, dae86e1950b1277e545cee180551750029cfe735 y dae86e nombran el mismo objeto commit si no hay ningún otro objeto en tu repositorio cuyo nombre de objeto comience con dae86e.

<salida_describe>, por ejemplo, v1.7.4.2-679-g3bee7fb

Salida de git describe; es decir, una etiqueta más cercana, seguida opcionalmente por un guión y un número de commits, seguido por un guión, una g y un nombre de objeto abreviado.

<nombre_ref>, por ejemplo, master, heads/master, refs/heads/master

Un nombre simbólico de ref. Por ejemplo, master típicamente significa el objeto commit referenciado por refs/heads/master. Si tienes tanto heads/master como tags/master, puedes decir explícitamente heads/master para indicarle a Git cuál quieres. Cuando es ambiguo, un <nombre_ref> se desambigua tomando la primera coincidencia en las siguientes reglas:
1. Si existe $GIT_DIR/<nombre_ref>, eso es lo que quieres (esto suele ser útil solo para HEAD, FETCH_HEAD, ORIG_HEAD, MERGE_HEAD, REBASE_HEAD, REVERT_HEAD, CHERRY_PICK_HEAD, BISECT_HEAD y AUTO_MERGE);
2. de lo contrario, refs/<nombre_ref> si existe;
3. de lo contrario, refs/tags/<nombre_ref> si existe;
4. de lo contrario, refs/heads/<nombre_ref> si existe;
5. de lo contrario, refs/remotes/<nombre_ref> si existe;
6. de lo contrario, refs/remotes/<nombre_ref>/HEAD si existe.

HEAD

nombra el commit en el que basaste los cambios en el árbol de trabajo.

FETCH_HEAD

registra la rama de la que obtuviste los datos de un repositorio remoto con tu última invocación de git fetch.

ORIG_HEAD

es creada por comandos que mueven tu HEAD de manera drástica (git am, git merge, git rebase, git reset), para registrar la posición del HEAD antes de su operación, para que puedas cambiar fácilmente la punta de la rama de vuelta al estado anterior a su ejecución.

MERGE_HEAD

registra el commit (o commits) que estás fusionando en tu rama cuando ejecutas git merge.

REBASE_HEAD

durante un rebase, registra el commit en el que la operación se detiene actualmente, ya sea por conflictos o por un comando edit en un rebase interactivo.

REVERT_HEAD

registra el commit que estás revirtiendo cuando ejecutas git revert.

CHERRY_PICK_HEAD

registra el commit que estás aplicando selectivamente (cherry-picking) cuando ejecutas git cherry-pick.

BISECT_HEAD

registra el commit actual a probar cuando ejecutas git bisect --no-checkout.

AUTO_MERGE

registra un objeto de árbol que corresponde al estado que la estrategia de fusión ort escribió en el árbol de trabajo cuando una operación de fusión resultó en conflictos.

Ten en cuenta que cualquiera de los casos refs/* anteriores puede provenir del directorio $GIT_DIR/refs o del archivo $GIT_DIR/packed-refs. Si bien la codificación del nombre de ref no está especificada, se prefiere UTF-8, ya que parte del procesamiento de salida puede asumir que los nombres de ref están en UTF-8.

@

@ solo es un atajo para HEAD.

[<nombre_ref>]@{<fecha>}, por ejemplo, master@{ayer}, HEAD@{hace 5 minutos}

Una ref seguida del sufijo @ con una especificación de fecha encerrada entre llaves (por ejemplo, {ayer}, {hace 1 mes 2 semanas 3 días 1 hora 1 segundo} o {1979-02-26 18:30:00}) especifica el valor de la ref en un momento anterior. Este sufijo solo se puede usar inmediatamente después de un nombre de ref, y la ref debe tener un registro existente ($GIT_DIR/logs/<ref>). Ten en cuenta que esto busca el estado de tu ref local en un momento dado; por ejemplo, lo que había en tu rama master local la semana pasada. Si deseas ver commits realizados durante ciertos períodos, consulta --since y --until.

<nombre_ref>@{<n>}, por ejemplo, master@{1}

Una ref seguida del sufijo @ con una especificación ordinal encerrada entre llaves (por ejemplo, {1}, {15}) especifica el n-ésimo valor anterior de esa ref. Por ejemplo, master@{1} es el valor anterior inmediato de master, mientras que master@{5} es el quinto valor anterior de master. Este sufijo solo se puede usar inmediatamente después de un nombre de ref, y la ref debe tener un registro existente ($GIT_DIR/logs/<nombre_ref>).

@{<n>}, por ejemplo, @{1}

Puedes usar la construcción @ con una parte de ref vacía para acceder a una entrada del reflog de la rama actual. Por ejemplo, si estás en la rama blabla, entonces @{1} significa lo mismo que blabla@{1}.

@{-<n>}, por ejemplo, @{-1}

La construcción @{-<n>} significa la n-ésima rama/commit que se consultó antes que el actual.

[<nombre_rama>]@{upstream}, por ejemplo, master@{upstream}, @{u}

Una rama B puede configurarse para construirse sobre una rama X (configurada con branch.<nombre>.merge) en un remoto R (configurada con la rama X tomada del remoto R, típicamente encontrada en refs/remotes/R/X.

[<nombre_rama>]@{push}, por ejemplo, master@{push}, @{push}

El sufijo @{push} informa la rama "a dónde empujaríamos" si se ejecutara git push mientras se tuviera la rama nombre_rama consultada (o el HEAD actual si no se especifica un nombre de rama). Al igual que para @{upstream}, informamos la rama de seguimiento remoto que corresponde a esa rama en el remoto.

Aquí hay un ejemplo para hacerlo más claro:

$ git config push.default current
$ git config remote.pushdefault myfork
$ git switch -c mybranch origin/master
$ git rev-parse --symbolic-full-name @{upstream}
refs/remotes/origin/master
$ git rev-parse --symbolic-full-name @{push}
refs/remotes/myfork/mybranch

Observa en el ejemplo que configuramos un flujo de trabajo triangular, donde extraemos de una ubicación y empujamos a otra. En un flujo de trabajo no triangular, @{push} es lo mismo que @{upstream}, y no es necesario.

Este sufijo también se acepta cuando está escrito en mayúsculas, y significa lo mismo sin importar la capitalización.

;^0 significa el propio commit y se usa cuando <rev> es el nombre de objeto de un objeto tag que se refiere a un objeto commit.

<rev>~[<n>], por ejemplo HEAD~,

master~3
Un sufijo ~ a un parámetro de revisión significa el primer padre de ese objeto commit. Un sufijo ~<n> a un parámetro de revisión significa el objeto commit que es el ancestro de generación <n> del objeto commit nombrado, siguiendo solo los primeros padres. Es decir, <rev>~3 es equivalente a <rev>^^^ que es equivalente a <rev>^1^1^1. Véase más abajo una ilustración del uso de esta
forma.

<rev>^{<type>}, por ejemplo v0.99.

8^{commit}
Un sufijo ^ seguido de un nombre de tipo de objeto encerrado en un par de llaves significa desreferenciar el objeto en <rev> recursivamente hasta que se encuentre un objeto de tipo <type> o el objeto ya no pueda ser desreferenciado (en cuyo caso, error). Por ejemplo, si <rev> es un commit-ish, <rev>^{commit} describe el objeto commit correspondiente. De manera similar, si <rev> es un tree-ish, <rev>^{tree} describe el objeto tree correspondiente. <rev>^0 es una abreviatura de <rev>^{commit}.

<rev>^{object} se puede usar para asegurarse de que <rev> nombra un objeto que existe, sin requerir que <rev> sea un tag, y sin desreferenciar <rev>; porque un tag ya es un objeto, no tiene que ser desreferenciado ni una sola vez para llegar a un

objeto.

<rev>^{tag} se puede usar para asegurar que <rev> identifica un

objeto tag
existente.

<rev>^{}, por ejemplo v0.99.

8^{}
Un sufijo ^ seguido de un par de llaves vacío significa que el objeto podría ser un tag, y desreferenciar el tag recursivamente hasta que se encuentre un objeto que no sea un
tag.

<rev>^{/<texto>}, por ejemplo HEAD^{/fix nasty

bug}
Un sufijo ^ a un parámetro de revisión, seguido de un par de llaves que contiene un texto que comienza con una barra inclinada, es lo mismo que la :/fix nasty bug sintaxis de abajo excepto que devuelve el commit coincidente más reciente que es alcanzable desde el <rev> antes ^
.

:/<texto>, por ejemplo :/fix nasty

bug
Dos puntos, seguido de una barra inclinada, seguido de un texto, nombra un commit cuyo mensaje de commit coincide con la expresión regular especificada. Este nombre devuelve el commit coincidente más reciente que es alcanzable desde cualquier ref, incluyendo HEAD. La expresión regular puede coincidir con cualquier parte del mensaje de commit. Para coincidir con mensajes que comienzan con una cadena, se puede usar, por ejemplo, :/^foo. La secuencia especial :/! está reservada para modificadores de lo que se coincide. :/!-foo realiza una coincidencia negativa, mientras que :/!!foo coincide con un carácter ! literal, seguido de foo. Cualquier otra secuencia que comience con :/! está reservada por ahora. Dependiendo del texto dado, las reglas de división de palabras del shell podrían requerir comillas
adicionales.

<rev>:<ruta>, por ejemplo HEAD:README, master:.

/README
Un sufijo : seguido de una ruta nombra el blob o tree en la ruta dada en el objeto tree-ish nombrado por la parte antes de los dos puntos. Una ruta que comienza con ./ o ../ es relativa al directorio de trabajo actual. La ruta dada se convertirá para ser relativa al directorio raíz del árbol de trabajo. Esto es más útil para abordar un blob o tree desde un commit o tree que tiene la misma estructura de árbol que el árbol de
trabajo.

:[<n>:]<ruta>, por ejemplo :0:README, :

README
Dos puntos, opcionalmente seguidos de un número de etapa (0 a 3) y dos puntos, seguidos de una ruta, nombra un objeto blob en el índice en la ruta dada. Un número de etapa faltante (y los dos puntos que lo siguen) nombra una entrada de etapa 0. Durante una fusión, la etapa 1 es el ancestro común, la etapa 2 es la versión de la rama destino (típicamente la rama actual), y la etapa 3 es la versión de la rama que se está
fusionando.

ESPECIFICANDO

RANGOS

Los comandos de recorrido de historial como git log operan en un conjunto de commits, no solo en un solo

commit.

Para estos comandos, especificar una sola revisión, usando la notación descrita en la sección anterior, significa el conjunto de commits alcanzables desde el commit

dado.

Especificar varias revisiones significa el conjunto de commits alcanzables desde cualquiera de los commits

dados.

El conjunto alcanzable de un commit es el propio commit y los commits en su cadena de

ascendencia.

Hay varias notaciones para especificar un conjunto de commits conectados (llamado un "rango de revisión"), ilustrado a

continuación.

Commits

Exclusiones

^<rev> (caret)

Notación
Para excluir commits alcanzables desde un commit, se usa un prefijo ^ notación. Por ejemplo ^r1 r2 significa commits alcanzables desde r2 pero excluye los que son alcanzables desde r1 (es decir, r1 y sus
ances
tros).

Notaciones de Rango con

Puntos

La .. (dos puntos) Notación de

Rango
La ^r1 r2 operación de conjunto aparece tan a menudo que hay una abreviatura para ella. Cuando tienes dos commits r1 y r2 (nombrados según la sintaxis explicada en ESPECIFICANDO REVISIONES arriba), puedes pedir commits que son alcanzables desde r2 excluyendo aquellos que son alcanzables desde r1 por ^r1 r2 y se puede escribir como r1..r
2.

La ... (tres puntos) Notación de Diferencia

Simétrica
Una notación similar r1...r2 se llama diferencia simétrica de r1 y r2 y se define como r1 r2 --not $(git merge-base --all r1 r2). Es el conjunto de commits que son alcanzables desde cualquiera de r1 (lado izquierdo) o r2 (lado derecho) pero no desde
ambos.

En estas dos notaciones abreviadas, puedes omitir un extremo y dejar que por defecto sea HEAD. Por ejemplo, origin.. es una abreviatura de origin..HEAD y pregunta "¿Qué hice desde que me bifurqué de la rama origin?" De manera similar, ..origin es una abreviatura de HEAD..origin y pregunta "¿Qué hizo el origin desde que me bifurqué de él?" Ten en cuenta que .. significaría HEAD..HEAD que es un rango vacío que es tanto alcanzable como inalcanzable desde

HEAD.

Los comandos que están específicamente diseñados para tomar dos rangos distintos (por ejemplo, "git range-diff R1 R2" para comparar dos rangos) existen, pero son excepciones. A menos que se indique lo contrario, todos los comandos "git" que operan en un conjunto de commits trabajan en un solo rango de revisión. En otras palabras, escribir dos "notaciones de rango con dos puntos" una al lado de la otra, por

ejemplo, 
$ git log A..B C.

Otras <rev>^ Abreviaturas de

Padre

Exist otras tres abreviaturas, particularmente útiles para commits de fusión, para nombrar un conjunto que está formado por un commit y sus commits

padre.

La r1^@ notación significa todos los padres de r1

.

La r1^! notación incluye el commit r1 pero excluye todos sus padres. Por sí misma, esta notación denota el único commit r1

.

La <rev>^-[<n>] notación incluye <rev> pero excluye el padre <n> (es decir, una abreviatura para <rev>^<n>..<rev>), con <n> = 1 si no se da. Esto es típicamente útil para commits de fusión donde puedes simplemente pasar <commit>^- para obtener todos los commits en la rama que se fusionó en el commit de fusión <commit> (incluyendo <commit> mismo)

.

Mientras que <rev>^<n> se trataba de especificar un solo padre de commit, estas tres notaciones también consideran sus padres. Por ejemplo puedes decir HEAD^2^@, sin embargo no puedes decir HEAD
