GIT-CHERRY(1) Manual de Git GIT-CHERRY(1)

NOMBRE

git-cherry - Encontrar commits que aún no se han aplicado al upstream

SINOPSIS

git cherry [-v] [<upstream> [<head> [<limit>]]]

DESCRIPCIÓN

Determina si hay commits en <head>..<upstream> que sean equivalentes a los del rango <limit>..<head>.

La prueba de equivalencia se basa en la diferencia, después de eliminar espacios en blanco y números de línea. git-cherry, por lo tanto, detecta cuándo se han "copiado" commits mediante git-cherry-pick(1), git-am(1) o git-rebase(1).

Muestra el SHA1 de cada commit en <limit>..<head>, prefijado con - para commits que tienen un equivalente en <upstream>, y + para commits que no lo tienen.

OPCIONES

-v

Muestra los temas de los commits junto a los SHA1s.

<upstream>

Rama upstream para buscar commits equivalentes. Por defecto, es la rama upstream de HEAD.

<head>

Rama de trabajo; por defecto, es HEAD.

<limit>

No informar sobre commits hasta (e incluyendo) el límite.

EJEMPLOS

Flujos de trabajo de parches

git-cherry se usa frecuentemente en flujos de trabajo basados en parches (ver gitworkflows(7)) para determinar si una serie de parches ha sido aplicada por el mantenedor principal. En un flujo de trabajo así, podrías crear y enviar una rama temática como esta:

$ git checkout -b tema origin/master
# trabajar y crear algunos commits
$ git format-patch origin/master
$ git send-email ... 00*

Más tarde, puedes ver si tus cambios han sido aplicados diciendo (todavía en tema):

$ git fetch  # actualizar tu noción de origin/master
$ git cherry -v

Ejemplo concreto

En una situación donde el tema consistía en tres commits, y el mantenedor aplicó dos de ellos, la situación podría parecerse a:

$ git log --graph --oneline --decorate --boundary origin/master...tema
* 7654321 (origin/master) commit principal del upstream
[... omitir otros commits ...]
* cccc111 cherry-pick de C
* aaaa111 cherry-pick de A
[... omitir mucho más que ha ocurrido ...]
| * cccc000 (tema) commit C
| * bbbb000 commit B
| * aaaa000 commit A
|/
o 1234567 punto de ramificación

En tales casos, git-cherry muestra un resumen conciso de lo que aún necesita ser aplicado:

$ git cherry origin/master tema
- cccc000... commit C
+ bbbb000... commit B
- aaaa000... commit A

Aquí vemos que los commits A y C (marcados con -) pueden ser eliminados de tu rama tema cuando la rebases sobre origin/master, mientras que el commit B (marcado con +) aún necesita ser conservado para ser enviado para su aplicación en origin/master.

Usando un límite

El <limit> opcional es útil en casos donde tu tema se basa en otro trabajo que no está en el upstream. Ampliando el ejemplo anterior, esto podría verse así:

$ git log --graph --oneline --decorate --boundary origin/master...tema
* 7654321 (origin/master) commit principal del upstream
[... omitir otros commits ...]
* cccc111 cherry-pick de C
* aaaa111 cherry-pick de A
[... omitir mucho más que ha ocurrido ...]
| * cccc000 (tema) commit C
| * bbbb000 commit B
| * aaaa000 commit A
| * 0000fff (base) cosas F no publicadas
[... omitir ...]
| * 0000aaa cosas A no publicadas
|/
o 1234567 merge-base entre upstream y tema

Especificando base como el límite, puedes evitar listar commits entre base y tema:

$ git cherry origin/master tema base
- cccc000... commit C
+ bbbb000... commit B
- aaaa000... commit A
