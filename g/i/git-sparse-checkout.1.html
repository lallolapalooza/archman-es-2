DESCRIPCIÓ

N

Este comando se utiliza para crear comprobaciones dispersas (sparse checkouts), que cambian el árbol de trabajo para que en lugar de tener todos los archivos rastreados presentes, solo tenga un subconjunto de esos archivos. También puede cambiar qué subconjunto de archivos está presente, o deshacer y volver a tener todos los archivos rastreados presentes en la copia de

trabajo.

El subconjunto de archivos se elige proporcionando una lista de directorios en modo cono (el predeterminado), o proporcionando una lista de patrones en modo

no-cono.

Cuando se está en una comprobación dispersa (sparse-checkout), otros comandos de Git se comportan de manera un poco diferente. Por ejemplo, cambiar de rama no actualizará las rutas fuera de los directorios/patrones de la comprobación dispersa, y git commit -a no registrará como eliminadas las rutas fuera de los directorios/patrones de la comprobación

dispersa.

Para asegurar que ajustar la configuración de la comprobación dispersa dentro de un árbol de trabajo no altere la configuración de la comprobación dispersa en otros árboles de trabajo, el subcomando set actualizará la configuración de tu repositorio para usar configuración específica del árbol de trabajo si aún no está presente. La dispersión definida por los argumentos al subcomando set se almacena en el archivo de comprobación dispersa específico del árbol de trabajo. Ver git-worktree(1) y la documentación de extensions.worktreeConfig en git-config(1) para más

detalles.

Cuando se proporciona la opción --stdin, los directorios o patrones se leen de la entrada estándar como una lista delimitada por saltos de línea en lugar de desde los

argumentos.

Por defecto, la lista de entrada se considera una lista de directorios, coincidiendo con la salida de git ls-tree -d --name-only. Esto incluye interpretar los nombres de ruta que comienzan con comillas dobles (") como cadenas entre comillas al estilo C. Ten en cuenta que todos los archivos bajo los directorios especificados (a cualquier profundidad) se incluirán en la comprobación dispersa, así como los archivos que son hermanos del directorio dado o de cualquiera de sus ancestros (ver CONJUNTO DE PATRONES EN MODO CONO más abajo para más detalles). En el pasado, esto no era el predeterminado, y --cone necesitaba ser especificado o core.sparseCheckoutCone necesitaba ser

activado.

Cuando se pasa --no-cone, la lista de entrada se considera una lista de patrones. Este modo tiene una serie de desventajas, incluyendo no funcionar con algunas opciones como --sparse-index. Como se explica en la sección "Problemas del modo no-cono" más abajo, no recomendamos

usarlo.

Usa la opción --[no-]sparse-index para usar un índice disperso (el predeterminado es no usarlo). Un índice disperso reduce el tamaño del índice para alinearse más estrechamente con tu definición de comprobación dispersa. Esto puede tener ventajas de rendimiento significativas para comandos como git status o git add. Esta función sigue siendo experimental. Algunos comandos podrían ser más lentos con un índice disperso hasta que estén correctamente integrados con la

función.

ADVERTENCIA: Usar un índice disperso requiere modificar el índice de una manera que no es completamente entendida por herramientas externas. Si tienes problemas con esta compatibilidad, ejecuta git sparse-checkout init --no-sparse-index para reescribir tu índice para que no sea disperso. Las versiones antiguas de Git no entenderán la extens

ión de índice de entradas de directorio disperso y podrían fa
llar al interactuar con tu repositorio hasta que se desactive.

Un archivo se considera para eliminación si está contenido dentro de un directorio rastreado que está fuera de la definición de comprobación dispersa.

Algunos casos especiales, como conflictos de fusión o archivos modificados fuera de la definición de comprobación dispersa, podrían llevar a mantener archivos que de otro modo serían eliminados. Resuelve conflictos, prepara modificaciones, y usa git sparse-checkout reapply en conjunto con git sparse-checkout clean para resolver estos

t
Comando obsoleto que se comporta como set sin rutas especificadas. Puede ser eliminado en el futuro.

Históricamente, set no manejaba todas las configuraciones necesarias, lo que significaba que tanto init como set tenían que ser llamados. Invocar ambos significaba que el paso init primero eliminaría casi todos los archivos rastreados (y en modo cono, también los archivos ignorados), luego el paso set añadiría de vuelta muchos de los archivos rastreados (pero no los ignorados). Además de los archivos perdidos, el rendimiento y la interfaz de usuario de esta combinación eran

pobres.

También, históricamente, init no inicializaría realmente el archivo de comprobación dispersa si ya existía. Esto significaba que era posible volver a una comprobación dispersa sin recordar qué rutas pasar a un set o add posterior. Sin embargo, las opciones --cone y --sparse-index no se recordarían a través del comando disable, por lo que la fácil restauración de llamar a un simple init disminuyó

en ut
ilidad.

INTERNOS — CHECKOUT DISPERSO (SPARSE

CHECKOUT)

El "checkout disperso" permite poblar el directorio de trabajo de forma dispersa. Utiliza el bit skip-worktree (véase git-update-index(1)) para decirle a Git si un archivo en el directorio de trabajo merece ser examinado. Si el bit skip-worktree está activado y el archivo no está presente en el árbol de trabajo, entonces su ausencia se ignora. Git evitará poblar el contenido de esos archivos, lo que hace que un checkout disperso sea útil cuando se trabaja en un repositorio con muchos archivos, pero solo unos pocos son importantes para el usuario

actual.

El archivo $GIT_DIR/info/sparse-checkout se utiliza para definir el mapa de bits de referencia skip-worktree. Cuando Git actualiza el directorio de trabajo, actualiza los bi

ts skip-worktree en el índice basándose en este archivo. Los archivos que coincidan
con los patrones en el archivo aparecerán en el directorio de trabajo, y el resto no.

INTERNOS — PROBLEMAS DEL MODO NO

CONO

El archivo $GIT_DIR/info/sparse-checkout poblado por los subcomandos set y add se define como un conjunto de patrones (uno por línea) usando la misma sintaxis que los archivos .gitignore. En modo cono, estos patrones están restringidos a coincidir con directorios (y los usuarios solo necesitan proporcionar o ver nombres de directorios), mientras que en modo no cono se permite cualquier patrone estilo gitignore. El uso de los patrones completos estilo gitignore en modo no cono tiene varias

deficiencias:
•Fundamentalmente, hace que varios procesos de actualización del árbol de trabajo (pull, merge, rebase, switch, reset, checkout, etc.) requieran O(N*M) coincidencias de patrones, donde N es el número de patrones y M es el número de rutas en el índice. Esto escala
mal.
•Evitar el problema de escala debe hacerse limitando el número de patrones mediante la especificación del nombre del directorio inicial o
glob.
•Pasar globs en la línea de comandos es propenso a errores ya que los usuarios pueden olvidar de entrecomillar el glob, causando que la shell lo expanda en todos los archivos coincidentes y los pase todos individualmente a sparse-checkout set/add. Aunque esto también podría ser un problema con, por ejemplo, "git grep — *.c", los errores con grep/log/status aparecen en la salida inmediata. Con sparse-checkout, el error se registra en el momento en que se ejecuta el comando sparse-checkout y podría no ser problemático hasta que el usuario más tarde cambie de rama o rebase o fusione, poniendo así un retraso entre el error del usuario y cuando tenga la oportunidad de detectarlo/notarlo
.
•Relacionado con el punto anterior, sparse-checkout tiene un subcomando add pero no un subcomando remove. Incluso si se añadiera un subcomando remove, deshacer un glob sin comillas accidentalmente corre el riesgo de "eliminar demasiado", ya que puede eliminar entradas que habían sido incluidas antes del add
accidental.
•El modo no cono usa patrones estilo gitignore para seleccionar qué incluir (con la excepción de los patrones negados), mientras que los archivos .gitignore usan patrones estilo gitignore para seleccionar qué excluir (con la excepción de los patrones negados). La documentación sobre patrones estilo gitignore normalmente no habla en términos de coincidencia o no coincidencia, sino sobre lo que el usuario quiere "excluir". Esto puede causar confusión para los usuarios que intentan aprender cómo especificar patrones de sparse-checkout para obtener su comportamiento
deseado.
•Cada otro subcomando de git que quiere proporcionar "coincidencia de patrones de ruta especial" de algún tipo usa pathspecs, pero el modo no cono para sparse-checkout usa patrones gitignore, lo que se siente
inconsistente.
•Tiene casos límite donde el comportamiento "correcto" no está claro. Dos ejemplos:

Primero, dos usuarios están en un subdirectorio, y el primero

El usuario que escribió el primer comando probablemente es consciente de que los argumentos de set/add deben ser patrones en modo no cono, y probablemente no estaría contento con tal transliteración. Sin embargo, muchos patrones estilo gitignore son solo rutas, que podría ser lo que el usuario que escribió el segundo comando estaba pensando, y estaría molesto si su argumento no se

Algunas ideas para añadir acoplamiento entre clones parciales y checkouts dispersos solo son prácticas con un conjunto más restringido de rutas
también.

Por todas estas razones, el modo

INTERNOS — MANEJO DEL MODO

CONO

El "modo cono", que es el predeterminado, le permite especificar solo qué directorios incluir. Para cualquier directorio especificado, todas las rutas bajo ese directorio se incluirán, y cualquier ruta inmediatamente bajo los directorios iniciales (incluido el directorio de nivel superior) también se incluirá. Así, si especificó el directorio Documentation/technical/ entonces su checkout disperso

contendría:
•todos los archivos en el directorio de nivel
superior
•todos los archivos inmediatamente bajo
Documentation/
•todos los archivos a cualquier profundidad bajo Documentation/technical
/

También, en modo cono, incluso si no se especifican directorios, los archivos del directorio de nivel superior se

incluirán.

Al cambiar los patrones de sparse-checkout en modo cono, Git inspeccionará cada directorio rastreado que no esté dentro del cono de sparse-checkout para ver si contiene algún archivo no rastreado. Si todos esos archivos son ignorados debido a los patrones .gitignore, entonces el directorio será eliminado. Si alguno de los archivos no rastreados dentro de ese directorio no es ignorado, entonces no ocurrirán eliminaciones dentro de ese directorio y aparecerá un mensaje de advertencia. Si estos archivos son importantes, entonces restablezca su definición de sparse-checkout para que se incluyan, use git add y git commit para almacenarlos, luego elimine manualmente los archivos restantes para asegurar que Git pueda comportarse de manera

óptima.

Véase también la sección "Internos — Conjunto de Patrones de Cono" para aprender cómo se transforman los directorios internamente en un subconjunto del Conjunto Completo de Patrones de

sparse-checkout
.

INTERNOS — CONJUNTO COMPLETO DE

PATRONES

El conjunto completo de patrones permite coincidencias de patrones arbitrarias y reglas de inclusión/exclusión complicadas. Estos pueden resultar en O(N*M) coincidencias de patrones al actualizar el índice, donde N es el número de patrones y M es el número de rutas en el índice. Para combatir este problema de rendimiento, se permite un conjunto de patrones más restringido cuando core.sparseCheckoutCone está

habilitado.

El archivo sparse-checkout usa la misma sintaxis que los archivos .gitignore ; véase gitignore(5) para detalles. Aquí, sin embargo, los patrones se usan normalmente para seleccionar qué archivos incluir en lugar de qué archivos excluir. (Sin embargo, puede ser un poco confuso ya que los patrones estilo gitignore tienen negaciones definidas por patrones que comienzan con un !, así que también puede seleccionar archivos para no incluir.

)
