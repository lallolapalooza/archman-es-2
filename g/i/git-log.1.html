NOMBRE

git-log - Muestra los registros de commits

SINOPSIS

git log [<opciones>] [<rango-de-revisiones>] [[--] <ruta>...

DESCRIPCIÓN

Muestra los registros de commits.

Lista los commits que son alcanzables siguiendo los enlaces padre desde los commits dados, pero excluye los commits que son alcanzables desde los que se dan con un ^ delante. La salida se da en orden cronológico inverso por defecto.

Puedes pensar en esto como una operación de conjuntos. Los commits alcanzables desde cualquiera de los commits dados en la línea de comandos forman un conjunto, y luego los commits alcanzables desde cualquiera de los que se dan con ^ delante se restan de ese conjunto. Los commits restantes son lo que sale en la salida del comando. Se pueden usar varias otras opciones y parámetros de ruta para limitar aún más el resultado.

Así, el siguiente comando:

$ git log foo bar ^baz

significa "listar todos los commits que son alcanzables desde foo o bar, pero no desde baz".

Una notación especial "<commit1>..<commit2>" puede ser usada como un atajo para "^<commit1> <commit2>". Por ejemplo, cualquiera de los siguientes pueden ser usados indistintamente:

$ git log origin..HEAD
$ git log HEAD ^origin

Otra notación especial es "<commit1>...<commit2>" que es útil para las fusiones. El conjunto resultante de commits es la diferencia simétrica entre los dos operandos. Los siguientes dos comandos son equivalentes:

$ git log A B --not $(git merge-base --all A B)
$ git log A...B

El comando toma opciones aplicables al comando git-rev-list(1) para controlar qué se muestra y cómo, y opciones aplicables al comando git-diff(1) para controlar cómo se muestran los cambios que introduce cada commit.

OPCIONES

--follow

Continúa listando el historial de un archivo más allá de los renombres (solo funciona para un solo archivo).

--no-decorate, --decorate[=(short|full|auto|no)]

Imprime los nombres de refs de cualquier commit que se muestre. Los valores posibles son: 
`short`;; los prefijos de nombres de ref `refs/heads/`, `refs/tags/` y
        `refs/remotes/` no se imprimen.
`full`;; se imprime el nombre de ref completo (incluyendo prefijo).
`auto`:: si la salida va a una terminal, los nombres de ref
        se muestran como si se hubiera dado `short`, de lo contrario no se
        muestran nombres de ref.

La opción --decorate es un atajo para --decorate=short. Por defecto, usa el valor de configuración de log.decorate si está configurado, de lo contrario, auto.

--decorate-refs=<patrón>, --decorate-refs-exclude=<patrón>

Para cada referencia candidata, no la uses para decorar si coincide con alguno de los parámetros <patrón> dados a --decorate-refs-exclude o si no coincide con ninguno de los parámetros <patrón> dados a --decorate-refs. La opción de configuración log.excludeDecoration permite excluir refs de las decoraciones, pero un patrón explícito de --decorate-refs anulará una coincidencia en log.excludeDecoration.

Si no se dan estas opciones o configuraciones, entonces las referencias se usan como decoración si coinciden con HEAD, refs/heads/, refs/remotes/, refs/stash/, o refs/tags/.

--clear-decorations

Cuando se especifica, esta opción borra todas las opciones anteriores de --decorate-refs o --decorate-refs-exclude y relaja el filtro de decoración predeterminado para incluir todas las referencias. Se asume esta opción si el valor de configuración log.initialDecorationSet está configurado como all.

--source

Imprime el nombre de ref dado en la línea de comandos por el cual se alcanzó cada commit.

--mailmap, --no-mailmap, --use-mailmap, --no-use-mailmap

Usa el archivo mailmap para mapear nombres y direcciones de correo electrónico de autores y committer a nombres y direcciones de correo electrónico canónicos. Ver git-shortlog(1).

--full-diff

Sin esta bandera, git log -p <ruta>... muestra commits que tocan las rutas especificadas, y diffs sobre las mismas rutas especificadas. Con esto, se muestra el diff completo para commits que tocan las rutas especificadas; esto significa que "<ruta>..." limita solo los commits, y no limita el diff para esos commits.

Ten en cuenta que esto afecta a todos los tipos de salida basados en diff, por ejemplo, los producidos por --stat, etc.

--log-size

Incluye una línea log size <número> en la salida para cada commit, donde <número> es la longitud del mensaje de ese commit en bytes. Pensado para acelerar herramientas que leen mensajes de log de la salida de git log permitiéndoles asignar espacio por adelantado.

-L<inicio>,<fin>:<archivo>, -L:<nombre-función>:<archivo>

Rastrea la evolución del rango de líneas dado por <inicio>,<fin>, o por la expresión regular del nombre de función <nombre-función>, dentro del <archivo>. No puedes dar limitadores de ruta. Actualmente está limitado a un recorrido que comienza desde una única revisión, es decir, solo puedes dar cero o un argumento de revisión positivo, y <inicio> y <fin> (o <nombre-función>) deben existir en la revisión de inicio. Puedes especificar esta opción más de una vez. Implica --patch. La salida de parche se puede suprimir usando --no-patch, pero otros formatos de diff (específicamente --raw, --numstat, --shortstat, --dirstat, --summary, --name-only, --name-status, --check) actualmente no están implementados.

<inicio> y <fin> pueden tomar una de las siguientes formas:

•<número>

Si <inicio> o <fin> es un número, especifica un número de línea absoluto (las líneas se cuentan a partir de 1).

•/<regex>/

Esta forma usará la primera línea que coincida con la <regex> POSIX dada. Si <inicio> es una regex, buscará desde el final del rango -L anterior, si existe, de lo contrario desde el inicio del archivo. Si <inicio> es ^/<regex>/, buscará desde el inicio del archivo. Si <fin> es una regex, buscará comenzando en la línea dada por <inicio>.

•+<desplazamiento> o -<desplazamiento>

Esto solo es válido para <fin> y especificará un número de líneas antes o después de la línea dada por <inicio>.

Si se da :<nombre-función> en lugar de <inicio> y <fin>, es una expresión regular que denota el rango desde la primera línea de función que coincide con <nombre-función>, hasta la siguiente línea de función. :<nombre-función> busca desde el final del rango -L anterior, si existe, de lo contrario desde el inicio del archivo. ^:<nombre-función> busca desde el inicio del archivo. Los nombres de función se determinan de la misma manera que git diff determina las cabeceras de los hunks de parche (ver Definición de una cabecera de hunk personalizada en gitattributes(5)).

<rango-de-revisiones>

Muestra solo commits en el rango de revisiones especificado. Cuando no se especifica <rango-de-revisiones>, por defecto es HEAD (es decir, todo el historial que lleva al commit actual). origin..HEAD especifica todos los commits alcanzables desde el commit actual (es decir, HEAD), pero no desde origin. Para una lista completa de formas de escribir <rango-de-revisiones>, consulta la sección Especificación de Rangos de gitrevisions(7).

[--] <ruta>...

Muestra solo los commits que son suficientes para explicar cómo llegaron a ser los archivos que coinciden con las rutas especificadas. Ver Simplificación del Historial más abajo para más detalles y otros modos de simplificación.

Orden de confirmación

Por defecto, las confirmaciones se muestran en orden cronológico inverso.

--date-order

No muestra los padres antes de que todos sus hijos sean mostrados, pero por lo demás muestra las confirmaciones en orden de marca de tiempo de confirmación.

--author-date-order

No muestra los padres antes de que todos sus hijos sean mostrados, pero por lo demás muestra las confirmaciones en orden de marca de tiempo del autor.

--topo-order

No muestra los padres antes de que todos sus hijos sean mostrados, y evita mostrar confirmaciones de varias líneas de historial mezcladas.

Por ejemplo, en un historial de confirmaciones como este:

    ---1----2----4----7
        \              \
         3----5----6----8---

Donde los números denotan el orden de las marcas de tiempo de confirmación, git rev-list y similares con --date-order muestran las confirmaciones en orden de marca de tiempo: 8 7 6 5 4 3 2 1.

Con --topo-order, mostrarían 8 6 5 3 7 4 2 1 (o 8 7 4 2 6 5 3 1); algunas confirmaciones más antiguas se muestran antes que las más nuevas para evitar mostrar las confirmaciones de dos pistas de desarrollo paralelas mezcladas.

--reverse

Saca las confirmaciones elegidas para mostrar (ver la sección Limitación de confirmaciones anterior) en orden inverso. No se puede combinar con --walk-reflogs.

Recorrido de objetos

Estas opciones están dirigidas principalmente al empaquetado de repositorios Git.

--no-walk[=(sorted|unsorted)]

The default output format is --date=iso. The date is shown in --date=default format when the timezone is not specified. When the timezone is specified, it is used to display the date and time.

The supported pseudo-timezones are:

Like --date=default, but the date format is ISO 8601 like format. E.g. 2007-03-15 10:00:00 -0700.

rfc

Like --date=default, but the date format is RFC 2822 like format. E.g. Thu, 15 Mar 2007 10:00:00 -0700.

short

Like --date=default, but the date format is short. E.g. 15 Mar 10:00.

raw

The number of seconds since the beginning of 1970 (deprecat- ed).

relative

Like --date=default, but the date format is relative to the current time. E.g. 2 hours ago.

default

The default format is based on ctime(3) output. It shows a single line with three-letter day of the week, three-letter month, day-of-month, hour-minute-seconds in "HH:MM:SS" format, followed by 4-digit year, plus timezone information, unless the local time zone is used, e.g. Thu Jan 1 00:00:00 1970 +0000.

Like --date=default, but use the local timezone instead of UTC.

human

Like --date=relative, but the date format is human-readable. E.g. 2 hours ago.

Allows you to specify your own date format string, which uses the same syntax as the date format string described by strftime(3) and shown by the system date command. See strftime(3) for details. Same as format:<format>, but the date is shown in the local timezone.

•raw

The raw format shows the entire commit exactly as stored in the commit object. Notably, the hashes are displayed in full, regardless of whether --abbrev or --no-abbrev are used, and parents information show the true parent commits, without taking grafts or history simplification into account. Note that this format affects the way commits are displayed, but not the way the diff is shown e.g. with git log --raw. To get full object names in a raw diff format, use --no-abbrev.

•tformat:

El formato tformat: funciona exactamente igual que format:, excepto que proporciona semántica de "terminador" en lugar de semántica de "separador". En otras palabras, a cada commit se le añade el carácter terminador del mensaje (normalmente un salto de línea), en lugar de colocar un separador entre las entradas. 3.Le sigue una cabecera de dos líneas de archivo de origen/archivo de destino: 
--- a/file
+++ b/file

Similar a la cabecera de dos líneas para el formato de diferencia unificada tradicional, /dev/null se usa para indicar archivos creados o eliminados.

Sin embargo, si se proporciona la opción --combined-all-paths, en lugar de una cabecera de dos líneas de origen/destino, obtendrá una cabecera de N+1 líneas de origen/destino, donde N es el número de padres en el commit de fusión:

--- a/file
--- a/file
--- a/file
+++ b/file

Este formato extendido puede ser útil si la detección de renombramiento o copia está activa, para permitirle ver el nombre original del archivo en diferentes padres.

4.El formato de la cabecera del fragmento se modifica para evitar que las personas lo alimenten accidentalmente a patch -p1. El formato de diferencia combinada se creó para la revisión de los cambios de commit de fusión, y no estaba destinado a ser aplicado. El cambio es similar al cambio en la cabecera extendida index: 
@@@ <rango-de-archivo-de-origen> <rango-de-archivo-de-origen> <rango-de-archivo-de-destino> @@@

Hay (número de padres + 1) caracteres @ en la cabecera del fragmento para el formato de diferencia combinada.

A diferencia del formato de diferencia unificada tradicional, que muestra dos archivos A y B con una sola columna que tiene un prefijo - (menos — aparece en A pero se elimina en B), + (más — falta en A pero se agrega a B), o " " (espacio — sin cambios), este formato compara dos o más archivos file1, file2,... con un archivo X, y muestra cómo X difiere de cada uno de fileN. Una columna por cada uno de fileN se antepone a la línea de salida para indicar cómo la línea de X difiere de ella.

Un carácter - en la columna N significa que la línea aparece en fileN pero no aparece en el resultado. Un carácter + en la columna N significa que la línea aparece en el resultado, y fileN no tiene esa línea (en otras palabras, la línea se agregó, desde el punto de vista de ese padre).

En la salida del ejemplo anterior, la firma de la función se cambió en ambos archivos (por lo tanto, dos eliminaciones - de file1 y file2, más ++ para indicar que una línea agregada no aparece en ninguno de file1 ni file2). Además, otras ocho líneas son iguales a las de file1 pero no aparecen en file2 (por lo tanto, prefijadas con +).

Cuando es mostrado por git diff-tree -c, compara los padres de un commit de fusión con el resultado de la fusión (es decir, file1..fileN son los padres). Cuando es mostrado por git diff-files -c, compara los dos padres de fusión sin resolver con el archivo del árbol de trabajo (es decir, file1 es la etapa 2, también conocida como "nuestra versión", file2 es la etapa 3, también conocida como "su versión").

Mostrar los cambios durante las últimas dos semanas en el archivo gitk. El -- es necesario para evitar confusiones con la rama llamada gitk

Mostrar los commits que están en la rama "test" pero aún no en la rama "release", junto con la lista de rutas que cada commit modifica.

Muestra los commits que cambiaron builtin/rev-list.c, incluyendo aquellos commits que ocurrieron antes de que el archivo recibiera su nombre actual.

git log --branches --not --remotes=origin

Muestra todos los commits que están en cualquiera de las ramas locales pero no en ninguna de las ramas de seguimiento remoto para origin (lo que tienes que origin no tiene).

Muestra todos los commits que están en master local pero no en ninguna rama master de repositorio remoto.

git log -p -m --first-parent

Muestra el historial incluyendo diferencias de cambios, pero solo desde la perspectiva de la "rama principal", omitiendo los commits que vienen de ramas fusionadas, y mostrando diferencias completas de los cambios introducidos por las fusiones. Muestra cómo evolucionó la función main() en el archivo main.c con el tiempo.

git log -3

Limita el número de commits a mostrar a 3.

DISCUSIÓN

Git es hasta cierto punto agnóstico a la codificación de caracteres.

•El contenido de los objetos blob son secuencias de bytes no interpretadas. No hay traducción de codificación a nivel central.
•Los nombres de ruta están codificados en la forma C de normalización UTF-8. Esto se aplica a los objetos de árbol, el archivo de índice, los nombres de ref, así como a los nombres de ruta en los argumentos de la línea de comandos, variables de entorno y archivos de configuración (.git/config (ver git-config(1)), gitignore(5), gitattributes(5) y gitmodules(5)).

Tenga en cuenta que Git a nivel central trata los nombres de ruta simplemente como secuencias de bytes que no son NUL, no hay conversiones de codificación de nombres de ruta (excepto en Mac y Windows). Por lo tanto, usar nombres de ruta no ASCII funcionará en su mayoría incluso en plataformas y sistemas de archivos que utilizan codificaciones de ASCII extendido heredadas. Sin embargo, los repositorios creados en tales sistemas no funcionarán correctamente en sistemas basados en UTF-8 (por ejemplo, Linux, Mac, Windows) y viceversa. Además, muchas herramientas basadas en Git simplemente asumen que los nombres de ruta son UTF-8 y fallarán al mostrar otras codificaciones correctamente.
