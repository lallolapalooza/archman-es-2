NOMBRE

gitprotocol-v2 - Protocolo de alambre de Git, versión 2

SINOPSIS

<protocolo-de-transferencia>

DESCRIPCIÓN

Este documento presenta una especificación para una versión 2 del protocolo de alambre de Git. El protocolo v2 mejorará el v1 de las siguientes maneras:

•En lugar de múltiples nombres de servicio, se admitirán múltiples comandos en un único servicio
•Extensible fácilmente ya que las capacidades se mueven a su propia sección del protocolo, ya no estarán ocultas detrás de un byte NUL y limitadas por el tamaño de una línea de paquete (pkt-line)
•Separar otra información oculta detrás de bytes NUL (por ejemplo, la cadena del agente como una capacidad y los symrefs se pueden solicitar usando ls-refs)
•El anuncio de referencias se omitirá a menos que se solicite explícitamente
•Comando ls-refs para solicitar explícitamente algunas referencias
•Diseñado teniendo en cuenta http y stateless-rpc. Con semántica de vaciado (flush) clara, el ayudante remoto http puede actuar simplemente como un proxy

En el protocolo v2, la comunicación está orientada a comandos. Al contactar inicialmente a un servidor, se anunciará una lista de capacidades. Algunas de estas capacidades serán comandos que un cliente puede solicitar que se ejecuten. Una vez que un comando ha completado, un cliente puede reutilizar la conexión y solicitar que se ejecuten otros comandos.

ENMARCADO DE LÍNEA DE PAQUETE (PACKET-LINE FRAMING)

Toda la comunicación se realiza utilizando el enmarcado de línea de paquete (packet-line framing), al igual que en la v1. Consulte gitprotocol-pack(5) y gitprotocol-common(5) para obtener más información.

En el protocolo v2, estos paquetes especiales tendrán las siguientes semánticas:

•0000 Paquete de vaciado (flush-pkt) - indica el final de un mensaje
•0001 Paquete delimitador (delim-pkt) - separa secciones de un mensaje
•0002 Paquete de fin de respuesta (response-end-pkt) - indica el final de una respuesta para conexiones sin estado (stateless)

SOLICITUD INICIAL DEL CLIENTE

En general, un cliente puede solicitar hablar el protocolo v2 enviando version=2 a través del canal lateral respectivo para el transporte que se está utilizando, lo que finalmente establece GIT_PROTOCOL. Se puede encontrar más información en gitprotocol-pack(5) y gitprotocol-http(5), así como la definición de GIT_PROTOCOL en git(1). En todos los casos, la respuesta del servidor es el anuncio de capacidades.

Transporte Git

Al utilizar el transporte git://, puede solicitar usar el protocolo v2 enviando "version=2" como un parámetro adicional:

003egit-upload-pack /project.git\0host=myserver.com\0\0version=2\0

Transporte SSH y Archivo

Al utilizar el transporte ssh:// o file://, la variable de entorno GIT_PROTOCOL debe establecerse explícitamente para incluir "version=2". Es posible que el servidor deba configurarse para permitir que esta variable de entorno se pase.

Transporte HTTP

Al utilizar el transporte http:// o https://, un cliente realiza una solicitud "smart" de info/refs como se describe en gitprotocol-http(5) y solicita que se use la v2 proporcionando "version=2" en la cabecera Git-Protocol.

C: GET $GIT_URL/info/refs?service=git-upload-pack HTTP/1.0
C: Git-Protocol: version=2

Un servidor v2 respondería:

S: 200 OK
S: <Algunas cabeceras>
S: ...
S:
S: 000eversion 2\n
S: <anuncio-de-capacidades>

Las solicitudes posteriores se realizan directamente al servicio $GIT_URL/git-upload-pack. (Esto funciona igual para git-receive-pack).

Utiliza la opción --http-backend-info-refs de git-upload-pack(1).

Es posible que el servidor deba configurarse para pasar el contenido de esta cabecera a través de la variable GIT_PROTOCOL. Consulte la discusión en git-http-backend(1).

ANUNCIO DE CAPACIDADES

Un servidor que decide comunicarse (basándose en una solicitud de un cliente) utilizando la versión 2 del protocolo, notifica al cliente enviando una cadena de versión en su respuesta inicial seguida de un anuncio de sus capacidades. Cada capacidad es una clave con un valor opcional. Los clientes deben ignorar todas las claves desconocidas. La semántica de los valores desconocidos se deja a la definición de cada clave. Algunas capacidades describirán comandos que el cliente puede solicitar que se ejecuten.

anuncio-capacidades = version-protocolo
                      lista-capacidades
                      paquete-vaciado
version-protocolo = PKT-LINE("version 2" LF)
lista-capacidades = *capacidad
capacidad = PKT-LINE(clave[=valor] LF)
clave = 1*(ALPHA | DIGIT | "-_")
valor = 1*(ALPHA | DIGIT | " -_.,?\/{}[]()<>!@#$%^&*+=:;")

SOLICITUD DE COMANDO

Después de recibir el anuncio de capacidades, un cliente puede emitir una solicitud para seleccionar el comando que desea con las capacidades o argumentos que desee. Luego hay una sección opcional donde el cliente puede proporcionar cualquier parámetro o consulta específica del comando. Solo se puede solicitar un comando a la vez.

solicitud = solicitud-vacia | solicitud-comando
solicitud-vacia = paquete-vaciado
solicitud-comando = comando
                    lista-capacidades
                    paquete-delimitador
                    argumentos-comando
                    paquete-vaciado
comando = PKT-LINE("command=" clave LF)
argumentos-comando = *argumento-especifico-comando
argumentos-especificos-comando son argumentos enmarcados en líneas de
paquete definidos por cada comando individual.

El servidor comprobará entonces que la solicitud del cliente conste de un comando válido, así como de capacidades válidas que fueron anunciadas. Si la solicitud es válida, el servidor ejecutará el comando. El servidor DEBE esperar hasta haber recibido la solicitud completa del cliente antes de emitir una respuesta. El formato de la respuesta está determinado por el comando que se está ejecutando, pero en todos los casos un paquete-vaciado indica el final de la respuesta.

Cuando un comando ha finalizado, y el cliente ha recibido la respuesta completa del servidor, un cliente puede solicitar que se ejecute otro comando o puede terminar la conexión. Un cliente puede opcionalmente enviar una solicitud vacía que consista solo en un paquete-vaciado para indicar que no se realizarán más solicitudes.

CAPACIDADES

Hay dos tipos diferentes de capacidades: capacidades normales, que pueden usarse para transmitir información o alterar el comportamiento de una solicitud, y comandos, que son las acciones principales que un cliente desea realizar (fetch, push, etc.).

El protocolo versión 2 no tiene estado (stateless) por defecto. Esto significa que todos los comandos solo deben durar una sola ronda y no tener estado desde la perspectiva del lado del servidor, a menos que el cliente haya solicitado una capacidad que indique que el servidor debe mantener el estado. Los clientes NO DEBEN requerir la gestión de estado en el lado del servidor para funcionar correctamente. Esto permite un balanceo de carga simple de ida y vuelta (round-robin) en el lado del servidor, sin tener que preocuparse por la gestión de estado.

agente

El servidor puede anunciar la capacidad agent con el valor X (en la forma agent=X) para notificar al cliente que el servidor está ejecutando la versión X. El cliente puede opcionalmente enviar su propia cadena de agente incluyendo la capacidad agent con un valor Y (en la forma agent=Y) en su solicitud al servidor (pero NO DEBE hacerlo si

el servidor no anunció la capacidad del agente). Las X y Y cadenas pueden contener cualquier carácter ASCII imprimible excepto espacio (es decir, el rango de bytes 33 ⟨ x ⟨ 126), y son típicamente de la forma "paquete/versión-os" (por ejemplo, "git/1.8.3.1-Linux") donde os es el nombre del sistema operativo (por ejemplo, "Linux"). X y Y se pueden configurar usando la variable de entorno GIT_USER_AGENT y esta tiene prioridad. La os se recupera usando el campo sysname de la llamada al sistema uname(2) o su equivalente. Las cadenas de agente son puramente informativas con fines de estadística y depurac

ión, y NO DEBEN usarse para asumir programáticamente la presencia o ausencia de características particulares.

PROTOCOL NEGOTIATION


When a client connects to a server, it first sends a list of its
    capabilities, ending with a flush-pkt. The server then responds with a list
    of its capabilities, also ending with a flush-pkt. The client then chooses
    the intersection of capabilities and sends the capabilities it wants to use,
    ending with a flush-pkt. The server responds with the final list of
    capabilities that will be used in the session, ending with a flush-pkt.

DATA TRANSFER


The server may respond with a packfile. The packfile is sent in
    sections, with each section preceded by a section header.




acknowledgments section
    * This section is only included if the client has sent 'multi-ack'
      or 'multi-ack-detailed' capabilities. Otherwise, the server
      will omit acknowledgments and respond with a 'ready' line
      (thus requiring the server to send a packfile), the
      acknowledgments sections MUST be omitted from the server's
      response.




• Always begins with the section header
    "acknowledgments"


• The server will respond with "NAK" if
    none of the object ids sent as have lines were common.


• The server will respond with "ACK <obj-id>" for all
    of the object ids sent as have lines which are common.


• A response cannot have both "ACK" lines
    as well as a "NAK" line.


• The server will respond with a "ready"
    line indicating that the server has found an acceptable common base and is
    ready to make and send a packfile (which will be found in the packfile section
    of the same response)


• If the server has found a suitable cut point and
    has decided to send a "ready" line, then the server can decide to
    (as an optimization) omit any "ACK" lines it would have sent during
    its response. This is because the server will have already determined the
    objects it plans to send to the client and no further negotiation is needed.



shallow-info section
    * If the client has requested a shallow fetch/clone, a shallow
      client requests a fetch or the server is shallow then the
      server's response may include a shallow-info section. The
      shallow-info section will be included if (due to one of the
      above conditions) the server needs to inform the client of any
      shallow boundaries or adjustments to the clients already
      existing shallow boundaries.






• Always begins with the section header
    "shallow-info"


• If a positive depth is requested, the server will
    compute the set of commits which are no deeper than the desired depth.


• The server sends a "shallow <obj-id>"
    line for each commit whose parents will not be sent in the following
    packfile.


• The server sends an "unshallow <obj-id>"
    line for each commit which the client has indicated is shallow, but is no
    longer shallow as a result of the fetch (due to its parents being sent in the
    following packfile).


• The server MUST NOT send any
    "unshallow" lines for anything which the client has not indicated
    was shallow as a part of its request.



wanted-refs section
    * This section is only included if the client has requested a
      ref using a 'want-ref' line and if a packfile section is also
      included in the response.






• Always begins with the section header
    "wanted-refs".


• The server will send a ref listing
    ("<oid> <refname>") for each reference requested using
    want-ref lines.


• The server MUST NOT send any refs which were not
    requested using want-ref lines.



packfile-uris section
    * This section is only included if the client sent
      'packfile-uris' and the server has at least one such URI to
      send.






• Always begins with the section header
    "packfile-uris".


• For each URI the server sends, it sends a hash of
    the pack’s contents (as output by git index-pack) followed by the
    URI.


• The hashes are 40 hex characters long. When Git
    upgrades to a new hash algorithm, this might need to be updated. (It should
    match whatever index-pack outputs after "pack\t" or
    "keep\t".



packfile section
    * This section is only included if the client has sent 'want'
      lines in its request and either requested that no more
      negotiation be done by sending 'done' or if the server has
      decided it has found a sufficient cut point to produce a
      packfile.






• Always begins with the section header
    "packfile"


• The transmission of the packfile begins
    immediately after the section header


• The data transfer of the packfile is always
    multiplexed, using the same semantics of the side-band-64k capability
    from protocol version 1. This means that each packet, during the packfile data
    stream, is made up of a leading 4-byte pkt-line length (typical of the
    pkt-line format), followed by a 1-byte stream code, followed by the actual
    data.

The server can advertise the object-format capability with
    a value X (in the form object-format=X) to notify the client

The server may advertise a session ID that can be used to identify

Session IDs should be unique to a given process. They must fit

    session ID should not rely on this fact.

bundle-uri


If the bundle-uri capability is advertised, the server
    supports the ‘bundle-uri’ command.


The capability is currently advertised with no value (i.e. not
    "bundle-uri=somevalue"), a value may be added in the future for
    supporting command-wide extensions. Clients MUST ignore any unknown
    capability values and proceed with the 'bundle-uri` dialog they support.


The bundle-uri command is intended to be issued before
    fetch to get URIs to bundle files (see git-bundle(1)) to
    "seed" and inform the subsequent fetch command.


The client CAN issue bundle-uri before or after any other
    valid command. To be useful to clients it’s expected that
    it’ll be issued after an ls-refs and before fetch, but
    CAN be issued at any time in the dialog.


DISCUSSION of bundle-uri
  






The intent of the feature is optimize for server resource
    consumption in the common case by changing the common case of fetching a
    very large PACK during git-clone(1) into a smaller incremental
    fetch.


It also allows servers to achieve better caching in combination
    with an uploadpack.packObjectsHook (see git-config(1)).


By having new clones or fetches be a more predictable and common
    negotiation against the tips of recently produces *.bundle file(s). Servers
    might even pre-generate the results of such negotiations for the
    uploadpack.packObjectsHook as new pushes come in.


One way that servers could take advantage of these bundles is that
    the server would anticipate that fresh clones will download a known bundle,
    followed by catching up to the current state of the repository using ref
    tips found in that bundle (or bundles).




PROTOCOL for bundle-uri
  






A bundle-uri request takes no arguments, and as noted above
    does not currently advertise a capability value. Both may be added in the
    future.


When the client issues a command=bundle-uri request, the
    response is a list of key-value pairs provided as packet lines with value
    <key>=<value>. Each <key>
    should be interpreted as a config key from the bundle.* namespace to
    construct a list of bundles. These keys are grouped by a
    bundle.<id>. subsection, where each key corresponding to
    a given <id> contributes attributes to the bundle defined by
    that <id>. See git-config(1) for the specific details of
    these keys and how the Git client will interpret their values.


Clients MUST parse the line according to the above format, lines
    that do not conform to the format SHOULD be discarded. The user MAY be
    warned in such a case.

GIT PROTOCOL V2

gitprotocol-v2.5

NAME

gitprotocol

SYNOPSIS

git protocol v2

DESCRIPTION

The git protocol uses a network protocol to transfer Git objects and refs between repositories. This document describes version 2 of the protocol.

The protocol is stateless, meaning that each request/response cycle is independent. This allows for easier implementation and resilience against network interruptions.

The protocol is extensible, allowing for new features and capabilities to be added in the future.

PACKET-LINE FRAMING

The protocol uses packet-line framing to delimit messages. Each packet is prefixed by a 4-digit hexadecimal length, including the length of the prefix itself. A length of 0000 indicates the end of the stream.

For example, a packet with 100 bytes of data would be prefixed with 0064 (hexadecimal for 100). The total packet size would be 104 bytes.

INITIAL CLIENT REQUEST

The client initiates the connection by sending a request to the server. The request consists of the desired Git command (e.g., fetch, push) followed by a list of capabilities the client supports.

The server responds with a list of capabilities it supports, followed by the references and objects available.

CAPABILITY ADVERTISEMENT

Both the client and server advertise their supported capabilities during the initial handshake. This allows them to negotiate the features they will use during the session.

Capabilities are represented as key-value pairs, where the key is the capability name and the value is an optional parameter.

COMMAND REQUEST

After the initial handshake, the client sends a command request to the server. The command specifies the operation to perform (e.g., fetch, push) and any relevant arguments.

The server processes the command and responds with the requested data or status information.

CAPABILITIES

multi_ack
Supports multiple acknowledgments during a push operation, allowing for more efficient data transfer.
of_0
Indicates that the server supports the older version 0 of the protocol. This is used for backward compatibility.
push_options
Supports custom options for push operations, allowing for more control over the push process.
report_status
The server reports the status of a push operation after each ref, rather than waiting until the end. This allows the client to abort the push early if an error occurs.
report_status_v2
A more detailed version of report_status, providing more information about the push operation.
side_band
Allows for data to be sent on separate channels during a push operation, such as progress information or error messages.
side_band_64k
A variation of side_band that uses larger packets (64KB) for more efficient data transfer.
thin_pack
Supports sending a "thin" packfile, which contains only the objects that are missing from the receiving repository. This reduces the amount of data transferred.
unreferenced
Allows the server to advertise unreferenced objects, which are objects that are not reachable from any ref. This can be useful for garbage collection.
upload_archive
Supports uploading an archive of the repository, allowing for easier backups or distribution.
v2
Indicates that the server supports version 2 of the Git protocol.
agent=git/
The client is using the git command-line client.
async
The server supports asynchronous operations, allowing for faster response times.
no-progress
The client does not want to receive progress information during the operation.
promisor-remote
This capability is used when a server acts as a "promisor" for other remotes. It indicates that the server can fetch objects from other remotes on behalf of the client. This would require the server to omit in its response the objects available on the better-connected remotes that the client has accepted. This hasn’t been implemented yet though. So for now this "promisor-remote" capability is useful only when the server advertises some promisor remotes it already uses to borrow objects from.
