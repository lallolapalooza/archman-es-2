Sobre

Reetiquetado

¿Qué deberías hacer cuando etiquetas un commit incorrecto y quieres

reetiquetarlo?

Si nunca has publicado nada, simplemente reetiquétalo. Usa -f para reemplazar el antiguo. Y ya

está.

Pero si has publicado cosas (o otros podrían leer tu repositorio directamente), entonces otros ya habrán visto la etiqueta antigua. En ese caso puedes hacer una de dos

cosas:
1.Lo sensato. Admite que te equivocaste y usa un nombre diferente. Otros ya han visto un nombre de etiqueta, y si mantienes el mismo nombre, puedes estar en la situación de que dos personas tengan ambas "versión X", pero en realidad tienen "X" diferentes. Así que simplemente llámala "X.1" y ya
está.
2.Lo insensato. Realmente quieres llamar a la nueva versión "X" también, aunque otros ya hayan visto la antigua. Así que simplemente usa git tag -f de nuevo, como si no hubieras publicado la
antigua.

Sin embargo, Git no (y no debería) cambia etiquetas a espaldas de los usuarios. Así que si alguien ya obtuvo la etiqueta antigua, hacer un git pull en tu árbol no debería simplemente hacer que sobrescriban la

antigua.

Si alguien obtuvo una etiqueta de lanzamiento de ti, no puedes simplemente cambiar la etiqueta por ellos actualizando la tuya. Este es un gran problema de seguridad, ya que la gente DEBE poder confiar en sus nombres de etiqueta. Si realmente quieres hacer la cosa insensata, simplemente tienes que confesarlo y decirle a la gente que te equivocaste. Puedes hacer eso haciendo un anuncio muy público

diciendo: 
Vale, me equivoqué, y publiqué una versión anterior etiquetada como X. Luego
arreglé algo y reetiqueté el árbol *arreglado* como X de nuevo.
Si obtuviste la etiqueta equ
ivocada y quieres la nueva, por favor elimina la antigua y obtén la nueva haciendo: git tag -d X git fetch origin tag X para obtener mi etiqueta actuali
zada. Puedes probar qué etiqueta tienes haciendo git rev-parse X que debería devolver 0123456789abcdef.. si tienes la nueva versión. Lo siento por las molestias.

¿Esto parece un poco complicado? Debería serlo. No hay forma de que fuera correcto simplemente "arreglarlo" automáticam

ente. La gente necesita saber que su
s etiquetas podrían haber sido cambiadas.

Sobre Seguimiento

automático

Si estás siguiendo el árbol de otra persona, es muy probable que estés usando ramas de seguimiento remoto (por ejemplo, refs/remotes/origin/master). Normalmente quieres las etiquetas del otro

extremo.

Por otro lado, si estás haciendo fetch porque quieres una fusión puntual con alguien más, normalmente no quieres obtener etiquetas de ahí. Esto ocurre con más frecuencia para personas cerca de la parte superior pero no se limita a ellas. Mortales comunes al hacer pull entre sí no necesariamente quieren obtener automáticamente etiquetas de puntos de anclaje privados de la otra

persona.

A menudo, los mensajes de "por favor haz pull" en la lista de correo solo proporcionan dos piezas de información: una URL de repositorio y un nombre de rama; esto está diseñado para ser fácil de cortar y pegar al final de una git fetch línea de

comandos: 
Linus, por favor haz pull de
        git://git..../proj.git master
para obtener las siguientes actualizaciones.
.
.

se convierte

en: 
$ git pull gi
t://git..../pr
oj.git master

En tal caso, no quieres seguir automáticamente las etiquetas de la otra

persona.

Un aspecto importante de Git es su naturaleza distribuida, lo que en gran medida significa que no hay un "upstream" o "downstream" inherente en el sistema. A primera vista, el ejemplo anterior podría parecer indicar que el espacio de nombres de etiquetas es propiedad de la gente de mayor jerarquía y que las etiquetas solo fluyen hacia abajo, pero no es el caso. Solo muestra que el patrón de uso determina quién está interesado en las etiquetas de

quién.

Un pull puntual es una señal de que un historial de commits ahora cruza el límite entre un círculo de personas (por ejemplo, "personas que están principalmente interesadas en la parte de red del kernel") que pueden tener su propio conjunto de etiquetas (por ejemplo, "esta es la tercera candidata a lanzamiento del grupo de red para ser propuesta para consumo general con la versión 2.6.21 ") a otro círculo de personas (por ejemplo, "personas que integran varias mejoras de subsistemas"). Estas últimas normalmente no están interesadas en las etiquetas detalladas usadas internamente en el primer grupo (eso es lo que significa "interno"). Por eso es deseable no seguir etiquetas automáticamente en este

caso.

Es muy posible que entre la gente de red, quieran intercambiar las etiquetas internas de su grupo, pero en

ese flujo de trabajo es muy probable que estén siguiendo el progreso de los demás teniendo ramas de
seguimiento remoto. De nuevo, la heurística para seguir automáticamente tales etiquetas es una cosa buena.

FECHA

Las variables de entorno GIT_AUTHOR_DATE y GIT_COMMITTER_DATE admiten los siguientes formatos de

fecha:

Formato interno de

Git
Es <marca_de_tiempo_unix> <desfase_de_zona_horaria>, donde <marca_de_tiempo_unix> es el número de segundos desde la época UNIX. <desfase_de_zona_horaria> es un desfase positivo o negativo desde UTC. Por ejemplo CET (que está 1 hora por delante de UTC) es +0100
.

RFC

2822
El formato de fecha estándar descrito por RFC 2822, por ejemplo Thu, 07 Apr 2005 22:13:13 +0200
.

ISO

8601
Hora y fecha especificadas por el estándar ISO 8601, por ejemplo 2005-04-07T22:13:13. El analizador acepta un espacio en lugar del carácter T también. Las partes fraccionarias de un segundo se ignorarán, por ejemplo 2005-04-07T22:13:13.019 se tratará como 2005-04-07T22:13:13.

Nota
Además, la parte de la fecha se acepta en los siguientes formatos: AAAA.MM.DD, MM/DD/AAAA y DD.M
