GIE(1) PROY GIE(1)

NOMBRE

gie - El entorno de investigación de integridad geoespacial

SÍNTAXIS

gie [ -hovql [ args ] ] archivo[s]

DESCRIPCIÓN

gie, el entorno de investigación de integridad geoespacial, es un entorno de pruebas de regresión para la biblioteca de transformación de PROJ. Su objetivo principal de diseño es poder realizar pruebas de regresión de código que forman parte de PROJ, sin requerir ningún otro tipo de herramienta que el mismo compilador C ya empleado para compilar la biblioteca.

-h, --help
Imprimir información de uso
-o <archivo>, --output <archivo>
Especificar el nombre del archivo de salida
-v, --verbose
Verbo: Proporcionar información informativa no esencial. Repetir -v para mayor detalle (por ejemplo, -vv)
-q, --quiet
Silencioso: Lo opuesto al modo verbo. En modo silencioso ni siquiera se reportan errores. La única interacción es a través del código de retorno (0 en éxito, no-cero indica el número de pruebas FALLADAS)
-l, --list
Listar los códigos de error del sistema interno de PROJ
--version
Imprimir el número de versión

Las pruebas para gie se definen en archivos de texto simples. Generalmente con la extensión .gie. Las pruebas para gie se escriben en el lenguaje de comandos propiamente hecho para gie. La funcionalidad básica del lenguaje de comandos gie se implementa a través de solo 3 verbos de comando: operation, que define la operación de PROJ a probar, accept, que define la coordenada de entrada a leer, y expect, que define el resultado a esperar.

Un archivo de prueba de ejemplo para gie que utiliza los tres comandos básicos anteriores se parece a:

<gie>
--------------------------------------------
Salida de prueba de la proyección UTM
--------------------------------------------
operation  +proj=utm  +zone=32  +ellps=GRS80
--------------------------------------------
accept     12  55
expect     691_875.632_14   6_098_907.825_05
</gie>

El análisis de un archivo gie comienza en <gie> y termina cuando se alcanza </gie>. Cualquier cosa antes de <gie> y después de </gie> no se considera. Los casos de prueba se crean definiendo una operation que accept una coordenada de entrada y expect una coordenada de salida.

Como las pruebas de gie están envueltas en las etiquetas <gie>/</gie>, también es posible añadir casos de prueba a archivos init personalizados. Las pruebas serán ignoradas por PROJ al leer el archivo init con +init y gie ignora cualquier cosa no envuelta en <gie>/</gie>.

Las pruebas de gie se definen por un conjunto de comandos como operation, accept y expect en el ejemplo anterior. Juntos, los comandos constituyen el lenguaje de comandos gie. Cualquier línea en un archivo gie que no comience con un comando se ignora. En el ejemplo anterior se ve cómo esto se puede utilizar para añadir comentarios y estilos a los archivos de prueba gie con el fin de hacerlos más legibles y también documentando qué es el propósito de las diversas pruebas.

A continuación se explica en detalle el lenguaje de comandos gie.

EJEMPLOS

1.
Ejecutar todas las pruebas en un archivo con toda la información de depuración activada
gie -vvvv corner-cases.gie
2.
Ejecutar todas las pruebas en varios archivos
gie foo bar

Lenguaje de comandos GIE

operation <+args>
Definir una operación de PROJ a probar. Ejemplo:
operation proj=utm zone=32 ellps=GRS80
# prueba de función 4D
accept    12 55 0 0
expect    691875.63214  6098907.82501  0  0
# prueba de función 2D
accept    12 56
expect    687071.4391   6210141.3267
accept <x y [z [t]]>
Definir la coordenada de entrada a leer. Toma la coordenada de prueba. La coordenada puede definirse mediante 2, 3 o 4 valores, donde los primeros dos valores son los componentes x- y y-, el tercero es el componente z- y el cuarto es el componente de tiempo. El número de componentes en la coordenada determina qué versión de la operación se prueba (2D, 3D o 4D). Se pueden aceptar muchas coordenadas para una operation. Para cada accept se necesita un expect acompañante.

Nota que gie acepta el guion bajo (_) como un separador de miles. No es obligatorio (de hecho, es completamente ignorado por la rutina de entrada), pero mejora significativamente la legibilidad de las cadenas de números muy largos típicamente requeridos en coordenadas proyectadas.

Véase operation para un ejemplo.

expect <x y [z [t]]> | <código de error>
Definir la coordenada esperada que será devuelta por la coordenada aceptada pasando a través de una operación. La coordenada esperada puede definirse mediante 2, 3 o 4 componentes, de manera similar a accept. Se pueden esperar muchas coordenadas para una operation. Para cada expect se necesita un accept acompañante.

Véase operation para un ejemplo.

Además de esperar una coordenada, también es posible esperar un código de error de PROJ en caso de que no se pueda crear una operación. Esto es útil cuando se prueban que los errores se capturan y se manejan correctamente. A continuación se muestra un ejemplo de esa prueba que verifica que el operador de tubería falla correctamente cuando se construye una tubería no invertible.

operation   proj=pipeline step
            proj=urm5 n=0.5 inv
expect      failure pjd_err_malformed_pipeline

Véase gie --list para una lista de códigos de error que se pueden esperar.

tolerance <tolerancia>
El comando tolerance controla cuánto pueden desviarse las coordenadas aceptadas de la coordenada esperada. Esto es útil para probar que una operación cumple con un umbral de tolerancia numérica determinada. Algunas operaciones se esperan que sean precisas dentro de milímetros mientras que otras pueden ser precisas solo dentro de unos pocos metros. tolerance debe
operation       proj=merc
# prueba de coordenada devuelta por ``echo 12 55 | proj +proj=merc``
tolerance       1 cm
accept          12 55
expect          1335833.89 7326837.72
# prueba de que la misma coordenada con un falso esteing de 50 m determinado
# por ``echo 12 55 |proj +proj=merc +x_0=50`` sigue estando dentro de una
# tolerancia de 100 m de la coordenada no alterada de proj=merc
tolerance       100 m
accept          12 55
expect          1335883.89  7326837.72

La tolerancia predeterminada es 0.5 mm. Véase proj -lu para una lista de unidades posibles.

roundtrip <n> <tolerancia>
Realizar una prueba de ida y vuelta de una operación. roundtrip necesita un comando operation y un comando accept para funcionar. La coordenada aceptada se pasa a la operación primero en su modo directo, luego la salida de la operación directa se pasa de nuevo a la operación inversa. Este procedimiento se realiza n veces. Si la coordenada resultante está dentro de la tolerancia establecida de la coordenada inicial, la prueba se aprueba.

Ejemplo con el predeterminado de 100 iteraciones and la tolerancia predeterminada:

operation       proj=merc
accept          12 55
roundtrip

Ejemplo con conteo y tolerancia predeterminada:

operation       proj=merc
accept          12 55
roundtrip       10000

Ejemplo con conteo y tolerancia:

operation       proj=merc
accept          12 55
roundtrip       10000 5 mm
direction <direction>
El comando direction especifica en qué dirección se realiza una operación. Esto puede ser forward o inverse. Un ejemplo de esto se ve a continuación, donde se comprueba que un pipeline de transformación simétrico devuelve los mismos resultados en ambas direcciones.
operation proj=pipeline zone=32 step
          proj=utm  ellps=GRS80 step
          proj=utm  ellps=GRS80 inv
tolerance 0.1 mm
accept 12 55 0 0
expect 12 55 0 0
# Ahora la dirección inversa (sigue siendo el mismo resultado: el pipeline es simétrico)
direction inverse
expect 12 55 0 0

La dirección predeterminada es "forward".

ignore <error code>
Esto es especialmente útil en casos de prueba que dependen de una cuadrícula cuya disponibilidad no está garantizada. A continuación se muestra un ejemplo de esa situación.
operation proj=hgridshift +grids=nzgd2kgrid0005.gsb ellps=GRS80
tolerance 1 mm
ignore    pjd_err_failed_to_load_grid
accept    172.999892181021551 -45.001620431954613
expect    173                 -45

Vea gie --list para obtener una lista de códigos de error que pueden ser ignorados.

require_grid <grid_name>
Comprueba la disponibilidad de la cuadrícula <grid_name>. Si no se encuentra, entonces todos los pares accept/expect hasta la siguiente operation serán omitidos. require_grid puede repetirse varias veces para especificar varias cuyas presencias son requeridas.
echo <text>
Añade texto definido por el usuario al flujo de salida. Vea el ejemplo a continuación.
<gie>
echo ** Mercator projection tests **
operation +proj=merc
accept  0   0
expect  0   0
</gie>

que devuelve

-------------------------------------------------------------------------------
Reading file 'test.gie'
** Mercator projection test **
-------------------------------------------------------------------------------
total:  1 tests succeeded,  0 tests skipped,  0 tests failed.
-------------------------------------------------------------------------------
skip
Omite cualquier prueba después de la primera aparición de skip. En el ejemplo siguiente solo se realizará la primera prueba. La segunda prueba se omite. Esta función es principalmente relevante para la depuración al escribir nuevos casos de prueba.
<gie>
operation proj=merc
accept  0   0
expect  0   0
skip
accept  0   1
expect  0   110579.9
</gie>

MODO ESTRICTO

Añadido en la versión 7.1.

Se puede usar una variante más estricta de la sintaxis normal de gie envolviendo los comandos de gie entre <gie-strict> y </gie-strict>. En modo estricto, las líneas de comentario deben comenzar con un carácter almohadilla. Los comandos desconocidos se considerarán un error. Un comando aún puede dividirse en varias líneas, pero las líneas intermedias deben terminar con el carácter de espacio seguido de una barra invertida para marcar la continuación.

<gie-strict>
# Esto es un comentario. La siguiente línea con múltiples caracteres repetidos también
-------------------------------------------------
# Un comando en varias líneas debe usar la continuación " \"
operation proj=hgridshift +grids=nzgd2kgrid0005.gsb \
          ellps=GRS80
tolerance 1 mm
ignore    pjd_err_failed_to_load_grid
accept    172.999892181021551 -45.001620431954613
expect    173                 -45
</gie-strict>

ANTECEDENTES

Más importante que ser un acrónimo para "Geospatial Integrity Investigation Environment", gie también eran las iniciales, el id de usuario y la dirección de correo electrónico de USGS de Gerald Ian Evenden (1935--2016), el visionario geoespacial, quien, ya en la década de 1980, comenzó lo que se convertiría en el PROJ de hoy.

La clara visión de Gerald era que las proyecciones de mapas son solo funciones especiales. Algunas de ellas son bastante complejas, la mayoría son de dos variables, pero todas son solo funciones especiales, y no particularmente más especiales que sin(), cos(), tan(), y hypot() ya disponibles en la biblioteca estándar de C.

Y por lo tanto, según Gerald, no deberían ser particularmente más difíciles de usar, para un programador, que las sin()'s, tan()'s y hypot()'s tan fácilmente disponibles.

La ingeniosidad de Gerald también se mostró en la implementación de la visión, donde ideó un sistema integral, aunque simple, de pares clave-valor para parametrizar una proyección de mapa, y la altamente flexible struct PJ , que almacena versiones compiladas en tiempo de ejecución de esos pares clave-valor, haciendo así que una llamada a una función de proyección de mapa, pj_fwd(PJ, point), sea tan fácil como una llamada a una función tradicional como hypot(x,y).

Aunque hoy en día podemos tener sistemas de metadatos más formalmente bien definidos (el más prominente es la representación OGC WKT2), nada se acerca a ser tan fácilmente legible ("compatible con humanos") como el sistema de pares clave-valor de Gerald. Este sistema en particular, y el sistema PROJ en general, fue el gran regalo de Gerald para cualquiera que usara y/o se comunicara sobre geodatos.

Es solo razonable nombrar a un programa, que vigila la integridad del sistema PROJ, en honor a Gerald.

Así que en honor, y con suerte también en el espíritu, de Gerald Ian Evenden (1935--2016), este es el Entorno de Investigación de Integridad Geoespacial.
