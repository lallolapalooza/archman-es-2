DESCRIPCIÓ

N

En las tres primeras formas, copia entradas de <tree-ish> al índice. En la última forma, establece la cabeza de la rama actual (HEAD) en <commit>, modificando opcionalmente el índice y el árbol de trabajo para que coincidan. El <tree-ish>/<commit> por defecto es HEAD en todas las

formas.

git reset [-q] [<tree-ish>] [--] <pathspec>..., git reset [-q] [--pathspec-from-file=<file> [--pathspec-file-nul]] [<tree-i

sh>]
Estas formas restablecen las entradas del índice para todas las rutas que coincidan con <pathspec> a su estado en <tree-ish>. (No afecta al árbol de trabajo ni a la rama actual.)

Esto significa que git reset <pathspec> es lo opuesto a git add <pathspec>. Este comando es equivalente a git restore [--source=<tree-ish>] --staged <pathspec>...

.

Después de ejecutar git reset <pathspec> para actualizar la entrada del índice, puedes usar git-restore(1) para extraer el contenido del índice al árbol de trabajo. Alternativamente, usando git-restore(1) y especificando un commit con --source, puedes copiar el contenido de una ruta de un

commit al índice y al árbol d
e trabajo de una sola vez.

git reset (--patch | -p) [<tree-ish>] [--] [<pathspec>...

]
Selecciona interactivamente los trozos en la diferencia entre el índice y <tree-ish> (por defecto HEAD). Los trozos elegidos se aplican en reversa al índice.

Esto significa que git reset -p es lo opuesto de git add -p, es decir, puedes usarlo para restablecer selectivamente trozos. Consulta la sección "Modo interactivo" de git-add(1) para aprender a operar el modo -

-pat

git reset [<mode>] [<commi

t>]
Esta forma restablece la cabeza de la rama actual a <commit> y posiblemente actualiza el índice (restableciéndolo al árbol de <commit>) y el árbol de trabajo dependiendo de <mode>. Antes de la operación, ORIG_HEAD se establece en la punta de la rama actual. Si <mode> se omite, por defecto es --mixed. El <mode> debe ser uno de los siguientes:

--sof

t
No toca el archivo de índice ni el árbol de trabajo en absoluto (pero restablece la cabeza a <commit>, igual que todos los modos). Esto deja todos tus archivos modificados como "Cambios a ser confirmados", como git status lo
pondría.

--mixe

d
Restablece el índice pero no el árbol de trabajo (es decir, los archivos modificados se conservan pero no se marcan para confirmar) e informa de lo que no se ha actualizado. Esta es la acción por defecto.

Si se especifica -N, las rutas eliminadas se marcan como intención-de-añadir (ver git-ad

d(1
)).

--har

d
Restablece el índice y el árbol de trabajo. Cualquier cambio en archivos rastreados en el árbol de trabajo desde <commit> se descartan. Cualquier archivo o directorio no rastreado que estorbe la escritura de archivos rastreados simplemente se
elimina.

--merg

e
Restablece el índice y actualiza los archivos en el árbol de trabajo que son diferentes entre <commit> y HEAD, pero conserva aquellos que son diferentes entre el índice y el árbol de trabajo (es decir, que tienen cambios que no se han añadido). Si un archivo que es diferente entre <commit> y el índice tiene cambios sin preparar, se aborta el reset.

En otras palabras, --merge hace algo como git read-tree -u -m <commit>, pero lleva adelante la

s entradas de índ
ice no fusionadas.

--kee

p
Restablece las entradas del índice y actualiza los archivos en el árbol de trabajo que son diferentes entre <commit> y HEAD. Si un archivo que es diferente entre <commit> y HEAD tiene cambios locales, se aborta el
reset.

--recurse-submodules, --no-recurse-submodule

s
Cuando se actualiza el árbol de trabajo, usar ‘--recurse-submodules` también restablecerá recursivamente el árbol de trabajo de todos los submódulos activos según el commit registrado en el superproyecto, estableciendo también el HEAD de los submódulos para qu

git reset --merge está destinado a usarse al restablecer desde una fusión en conflicto. Cualquier operación de fusión garantiza que el archivo del árbol de trabajo involucrado en la fusión no tiene un cambio local con respecto al índice antes de que comience, y que escribe el resultado en el árbol de trabajo. Entonces, si vemos alguna diferencia entre el índice y el destino y también entre el índice y el árbol de trabajo, entonces significa que no estamos restableciendo desde un estado que una operación de fusión dejó después de fallar con un conflicto. Es por eso que no permitimos la opción --merge en este

caso.

git reset --keep está destinado a usarse al eliminar algunos de los últimos commits en la rama actual mientras se mantienen los cambios en el árbol de trabajo. Si pudiera haber conflictos entre los cambios en el commit que queremos eliminar y los cambios en el árbol de trabajo que queremos mantener, el restablecimiento no está permitido. Por eso no está permitido si hay cambios tanto entre el árbol de trabajo y HEAD, como entre HEAD y el destino. Por seguridad, también no está permitido cuando hay entradas sin

fusionar.
