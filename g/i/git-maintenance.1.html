TROUBLESHOOTIN

G

The git maintenance command is designed to simplify the repository maintenance patterns while minimizing user wait time during Git commands. A variety of configuration options are available to allow customizing this process. The default maintenance options focus on operations that complete quickly, even on large

repositories.

Users may find some cases where scheduled maintenance tasks do not run as frequently as intended. Each git maintenance run command takes a lock on the repository’s object database, and this prevents other concurrent git maintenance run commands from running on the same repository. Without this safeguard, competing processes could leave the repository in an unpredictable

state.

The background maintenance schedule runs git maintenance run processes on an hourly basis. Each run executes the "hourly" tasks. At midnight, that process also executes the "daily" tasks. At midnight on the first day of the week, that process also executes the "weekly" tasks. A single process iterates over each registered repository, performing the scheduled tasks for that frequency. The processes are scheduled to a random minute of the hour per client to spread out the load that multiple clients might generate (e.g. from prefetching). Depending on the number of registered repositories and their sizes, this process may take longer than an hour. In this case, multiple git maintenance run commands may run on the same repository at the same time, colliding on the object database lock. This results in one of the two tasks not

running.

If you find that some maintenance windows are taking longer than one hour to complete, then consider reducing the complexity of your maintenance tasks. For example, the gc task is much slower than the incremental-repack task. However, this comes at a cost of a slightly larger object database. Consider moving more expensive tasks to be run less

frequently.

Expert users may consider scheduling their own maintenance tasks using a different schedule than is available through git maintenance start and Git configuration options. These users should be aware of the object database lock and how concurrent git maintenance run commands behave. Further, the git gc command should not be combined with git maintenance run commands. git gc modifies the object database but does not take the lock in the same way as git maintenance run. If possible, use git maintenance run --task=gc instead of git gc

.

The following sections describe the mechanisms put in place to run background maintenance by git maintenance start and how

to custom
ize them.

BACKGROUND MAINTENANCE ON POSIX

SYSTEMS

The standard mechanism for scheduling background tasks on POSIX systems is cron(8). This tool executes commands based on a given schedule. The current list of user-scheduled tasks can be found by running crontab -l. The schedule written by git maintenance start is similar to

this: 
# BEGIN GIT MAINTENANCE SCHEDULE
# The following schedule was created by Git
# Any edits made in this region might be
# replaced in the future by a Git command.
0 1-23 * * * "/<path>/gi
t" --exec-path="/<path>" for-each-repo --config=maintenance.repo maintenance run --schedule=hourly 0 0 * * 1-6 "/<path>/git" --exec-path="/<path>" for-each-repo --config=maintenance.rep
o maintenance run --schedule=daily 0 0 * * 0 "/<path>/git" --exec-path="/<path>" for-each-repo --config=maintenance.repo maintenance run --schedule=weekly # END GIT MAINTENANCE SCHEDULE

The comments are used as a region to mark the schedule as written by Git. Any modifications within this region will be completely deleted by git maintenance stop or overwritten by git maintenance start

.

The crontab entry specifies the full path of the git executable to ensure that the executed git command is the same one with which git maintenance start was issued independent of PATH. If the same user runs git maintenance start with multiple Git executables, then only the latest executable is

used.

These commands use git for-each-repo --config=maintenance.repo to run git maintenance run --schedule=<frequency> on each repository listed in the multi-valued maintenance.repo config option. These are typically loaded from the user-specific global config. The git maintenance process then determines which maintenance tasks are configured to run on each repository with each <frequency> using the maintenance.<task>.schedule config options. These values are loaded from the global or repository config

values.

If the config values are insufficient to achieve your desired background maintenance schedule, then you can create your own schedule. If you run crontab -e, then an editor will load with your user-specific cron schedule. In that editor, you can add your own schedule lines. You could start by adapting the default schedule listed earlier, or you could read the crontab(5) documentation for advanced scheduling techniques. Please do use the full path and --exec-path techniques from the default schedule to ensure

you are executing the correct
binaries in your schedule.

BACKGROUND MAINTENANCE ON LINUX SYSTEMD

SYSTEMS

While Linux supports cron, depending on the distribution, cron may be an optional package not necessarily installed. On modern Linux distributions, systemd timers are superseding

it.

If user systemd timers are available, they will be used as a replacement of cron

.

In this case, git maintenance start will create user systemd timer units and start the timers. The current list of user-scheduled tasks can be found by running systemctl --user list-timers. The timers written by git maintenance start are similar to

One timer is registered for each --schedule=<frequency>

option.

The definition of the systemd units can be inspected in the following

BACKGROUND MAINTENANCE ON MACOS

SYSTEMS

While macOS technically supports cron, using crontab -e requires elevated privileges and the executed process does not have a full user context. Without a full user context, Git and its credential helpers cannot access stored credentials, so some maintenance tasks are not

functional.

Instead, git maintenance start interacts with the launchctl tool, which is the recommended way to schedule timed jobs in macOS. Scheduling maintenance through git maintenance (start|stop) requires some launchctl features available

BACKGROUND MAINTENANCE ON MACOS SYSTEMS

Solo en macOS 10.11 o posterior.

Sus tareas programadas específicas del usuario se almacenan como archivos .plist con formato XML en ~/Library/LaunchAgents/. Puede ver las tareas registradas actualmente usando el siguiente comando:

$ ls ~/Library/LaunchAgents/org.git-scm.git*
org.git-scm.git.daily.plist
org.git-scm.git.hourly.plist
org.git-scm.git.weekly.plist

Se registra una tarea por cada opción --schedule=<frecuencia>. Para inspeccionar cómo el formato XML describe cada programación, abra uno de estos archivos .plist en un editor e inspeccione el elemento <array> que sigue al elemento <key>StartCalendarInterval</key>.

git maintenance start sobrescribirá estos archivos y volverá a registrar las tareas con launchctl, por lo que cualquier personalización debe hacerse creando sus propios archivos .plist con nombres distintos. De manera similar, el comando git maintenance stop anulará el registro de las tareas con launchctl y eliminará los archivos .plist.

Para crear personalizaciones más avanzadas de sus tareas en segundo plano, consulte launchctl.plist(5) para obtener más información.

BACKGROUND MAINTENANCE ON WINDOWS SYSTEMS

Windows no admite cron y en su lugar tiene su propio sistema para programar tareas en segundo plano. El comando git maintenance start utiliza el comando schtasks para enviar tareas a este sistema. Puede inspeccionar todas las tareas en segundo plano utilizando la aplicación Programador de tareas. Las tareas agregadas por Git tienen nombres del tipo Git Maintenance (<frecuencia>). La GUI del Programador de tareas tiene formas de inspeccionar estas tareas, pero también puede exportar las tareas a archivos XML y ver los detalles allí.

Tenga en cuenta que dado que Git es una aplicación de consola, estas tareas en segundo plano crean una ventana de consola visible para el usuario actual. Esto se puede cambiar manualmente seleccionando la opción "Ejecutar esté el usuario conectado o no" en el Programador de tareas. Este cambio requiere la entrada de una contraseña, por lo que git maintenance start no la selecciona por defecto.

Si desea personalizar las tareas en segundo plano, cambie el nombre de las tareas para que las futuras llamadas a git maintenance (start|stop) no sobrescriban sus tareas personalizadas.

CONFIGURACIÓN

Todo lo que está debajo de esta línea en esta sección se incluye selectivamente de la documentación de git-config(1). El contenido es el mismo que el que se encuentra allí:

maintenance.auto

Esta opción de configuración booleana controla si algunos comandos ejecutan git maintenance run --auto después de realizar su trabajo normal. Por defecto es true.

maintenance.autoDetach

Muchos comandos de Git activan el mantenimiento automático después de haber escrito datos en el repositorio. Esta opción de configuración booleana controla si este mantenimiento automático debe ocurrir en primer plano o si el proceso de mantenimiento debe separarse y continuar ejecutándose en segundo plano.

Si no está establecido, se utiliza el valor de gc.autoDetach como respaldo. Por defecto es true si ambos no están establecidos, lo que significa que el proceso de mantenimiento se separará.

maintenance.strategy

Esta opción de configuración de cadena proporciona una manera de especificar una de las pocas estrategias recomendadas para el mantenimiento del repositorio. Esto afecta a las tareas que se ejecutan durante git maintenance run, siempre que no se proporcione ningún argumento --task=<tarea>. Esta configuración impacta el mantenimiento manual, el mantenimiento automático y el mantenimiento programado. Las tareas que se ejecutan pueden ser diferentes dependiendo del tipo de mantenimiento.

La estrategia de mantenimiento se puede ajustar aún más estableciendo maintenance.<tarea>.enabled y maintenance.<tarea>.schedule. Si se establecen, estos valores se utilizan en lugar de los valores predeterminados proporcionados por maintenance.strategy.

Las estrategias posibles son:

•none: Esta estrategia implica que no se ejecuta ninguna tarea. Esta es la estrategia predeterminada para el mantenimiento programado.
•gc: Esta estrategia ejecuta la tarea gc. Esta es la estrategia predeterminada para el mantenimiento manual.
•geometric: Esta estrategia realiza el empaquetado geométrico de los archivos de paquete y mantiene las estructuras de datos auxiliares actualizadas. La estrategia expira los datos en el reflog y elimina los árboles de trabajo que ya no se pueden ubicar. Cuando la estrategia de empaquetado geométrico decidiría hacer un empaquetado de todo en uno, entonces la estrategia genera un archivo de fragmentos para todos los objetos inalcanzables. Los objetos que ya forman parte de un archivo de fragmentos se expirarán.

Esta estrategia de empaquetado es un reemplazo completo para la estrategia gc y se recomienda para repositorios grandes. * incremental: Esta configuración optimiza la realización de pequeñas actividades de mantenimiento que no eliminan ningún dato. Esto no programa la tarea gc, sino que ejecuta las tareas prefetch y commit-graph cada hora, las tareas loose-objects e incremental-repack diariamente, y la tarea pack-refs semanalmente. El mantenimiento manual del repositorio utiliza la tarea gc.

maintenance.<task>.enabled

Esta opción de configuración booleana controla si la tarea de mantenimiento con el nombre <task> se ejecuta cuando no se especifica ninguna opción --task para git maintenance run. Estos valores de configuración se ignoran si existe una opción --task. Por defecto, solo maintenance.gc.enabled es true.

maintenance.<task>.schedule

Esta opción de configuración controla si la <task> dada se ejecuta o no durante un comando git maintenance run --schedule=<frecuencia>. El valor debe ser "hourly", "daily" o "weekly".

maintenance.commit-graph.auto

Esta opción de configuración entera controla con qué frecuencia se debe ejecutar la tarea commit-graph como parte de git maintenance run --auto. Si es cero, entonces la tarea commit-graph no se ejecutará con la opción --auto. Un valor negativo forzará la ejecución de la tarea cada vez. De lo contrario, un valor positivo implica que el comando se ejecutará cuando el número de commits alcanzables que no están en el archivo de grafo de commits sea al menos el valor de maintenance.commit-graph.auto. El valor predeterminado es 100.

maintenance.loose-objects.auto

Esta opción de configuración entera controla con qué frecuencia se debe ejecutar la tarea loose-objects como parte de git maintenance run --auto. Si es cero, entonces la tarea loose-objects no se ejecutará con la opción --auto. Un valor negativo forzará la ejecución de la tarea cada vez. De lo contrario, un valor positivo implica que el comando se ejecutará cuando el número de objetos sueltos sea al menos el valor de maintenance.loose-objects.auto. El valor predeterminado es 100.

maintenance.loose-objects.batchSize

Esta opción de configuración entera controla el número máximo de objetos sueltos escritos en un archivo de paquete durante la tarea loose-objects. El valor predeterminado es cincuenta mil. Use el valor 0 para indicar sin límite.

maintenance.incremental-repack.auto

Esta opción de configuración entera controla con qué frecuencia se debe ejecutar la tarea incremental-repack como parte de git maintenance run --auto. Si es cero, entonces la tarea incremental-repack no se ejecutará con la opción --auto. Un valor negativo forzará la ejecución de la tarea cada vez. De lo contrario, un valor positivo implica que el comando se ejecutará cuando el número de archivos de paquete que no están en el índice multipack sea al menos el valor de maintenance.incremental-repack.auto. El valor predeterminado es 10.

maintenance.geometric-repack.auto

Esta opción de configuración entera controla con qué frecuencia se debe ejecutar la tarea geometric-repack como parte de git maintenance run --auto. Si es cero, entonces la tarea geometric-repack no se ejecutará con la opción --auto. Un valor negativo forzará la ejecución de la tarea cada vez. De lo contrario, un valor positivo implica que el comando se ejecutará ya sea cuando haya archivos de paquete que necesiten fusionarse para mantener la progresión geométrica, o cuando haya al menos esta cantidad de objetos sueltos que se escribirían en un nuevo archivo de paquete. El valor predeterminado es 100.

maintenance.geometric-repack.splitFactor

Esta opción de configuración entera controla el factor utilizado para la secuencia geométrica. Consulte la opción --geometric= en git-repack(1) para más detalles. Por defecto es 2.

maintenance.reflog-expire.auto

Esta opción de configuración entera controla con qué frecuencia se debe ejecutar la tarea reflog-expire como parte de git maintenance run --auto. Si es cero, entonces la tarea reflog-expire no se ejecutará con la opción --auto. Un valor negativo forzará la ejecución de la tarea cada vez. De lo contrario, un valor positivo implica que el comando se ejecutará cuando el número de entradas de reflog expiradas en el reflog de "HEAD" sea al menos el valor de maintenance.loose-objects.auto. El valor predeterminado es 100.

maintenance.rerere-gc.auto

Esta opción de configuración entera controla con qué frecuencia se debe ejecutar la tarea rerere-gc como parte de git maintenance run --auto. Si es cero, entonces la tarea rerere-gc no se ejecutará con la opción --auto. Un valor negativo forzará la ejecución de la tarea cada vez. De lo contrario, cualquier valor positivo implica que el comando se ejecutará cuando el directorio "rr-cache" exista y tenga al menos una entrada, independientemente de si está obsoleta o no. Esta heurística puede refinarse en el futuro. El valor predeterminado es 1.

maintenance.worktree-prune.auto

Esta opción de configuración entera controla con qué frecuencia se debe ejecutar la tarea worktree-prune como parte de git maintenance run --auto. Si es cero, entonces la tarea worktree-prune no se ejecutará con la opción --auto. Un valor negativo forzará la ejecución de la tarea cada vez. De lo contrario, un valor positivo implica que el comando se ejecutará cuando el número de árboles de trabajo que se pueden podar exceda el valor. El valor predeterminado es 1.
