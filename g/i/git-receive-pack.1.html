NOMBRE

git-receive-pack - Recibe lo que se envía al repositorio

SINOPSIS

git receive-pack <git-dir>

DESCRIPCIÓN

Invocado por git send-pack y actualiza el repositorio con la información proporcionada por el extremo remoto.

Este comando normalmente no es invocado directamente por el usuario final. La interfaz de usuario para el protocolo está en el lado de git send-pack , y el par de programas está destinado a usarse para enviar actualizaciones a un repositorio remoto. Para las operaciones de extracción (pull), consulte git-fetch-pack(1).

El comando permite la creación y el avance rápido (fast-forward) de referencias sha1 (heads/tags) en el extremo remoto (estrictamente hablando, es el extremo local donde git-receive-pack se ejecuta, pero para el usuario que está en el extremo send-pack, está actualizando el remoto. ¿Confundido?)

Hay otros ejemplos del mundo real sobre el uso de los ganchos (hooks) update y post-update en el directorio Documentation/howto.

git-receive-pack respeta la opción de configuración receive.denyNonFastForwards, que le indica si se deben denegar las actualizaciones a una referencia si no son avances rápidos.

Hay disponibles otras opciones de configuración receive.* para ajustar su comportamiento, consulte git-config(1).

OPCIONES

<git-dir>

El repositorio con el que sincronizar.

--http-backend-info-refs

Usado por git-http-backend(1) para servir peticiones $GIT_URL/info/refs?service=git-receive-pack. Véase --http-backend-info-refs en git-upload-pack(1).

--skip-connectivity-check

Omite las comprobaciones de conectividad que validan la existencia de todos los objetos en el cierre transitivo de objetos alcanzables. Esta opción está destinada a los operadores de servidores que quieren implementar su propia validación de conectividad de objetos fuera de Git. Esto es útil en aquellos casos donde el lado del servidor conoce información adicional sobre cómo se está usando Git y por lo tanto puede confiar en ciertas garantías para calcular la conectividad de objetos de manera más eficiente de lo que Git mismo puede hacer. El uso de esta opción sin un mecanismo externo fiable para asegurar la conectividad completa de objetos alcanzables arriesga corromper el repositorio y no debería usarse en el caso general.

GANCHO (HOOK) PRE-RECEIVE

Antes de que se actualice cualquier referencia, si el archivo $GIT_DIR/hooks/pre-receive existe y es ejecutable, será invocado una vez sin parámetros. La entrada estándar del gancho tendrá una línea por cada referencia a actualizar:

sha1-antiguo ESPACIO sha1-nuevo ESPACIO nombre-referencia LF

El valor del nombre-referencia es relativo a $GIT_DIR; p. ej. para la cabecera master esto es "refs/heads/master". Los dos valores sha1 antes de cada nombre-referencia son los nombres de objeto para el nombre-referencia antes y después de la actualización. Las referencias a crear tendrán sha1-antiguo igual a 0{40}, mientras que las referencias a eliminar tendrán sha1-nuevo igual a 0{40}, de lo contrario sha1-antiguo y sha1-nuevo deben ser objetos válidos en el repositorio.

Al aceptar un envío (push) firmado (véase git-push(1)), el certificado de envío firmado se almacena en un blob y una variable de entorno GIT_PUSH_CERT puede consultarse para obtener su nombre de objeto. Véase la descripción del gancho post-receive para un ejemplo. Además, el certificado se verifica usando GPG y el resultado se exporta con las siguientes variables de entorno:

GIT_PUSH_CERT_SIGNER

El nombre y la dirección de correo electrónico del propietario de la clave que firmó el certificado de envío.

GIT_PUSH_CERT_KEY

El ID de la clave GPG de la clave que firmó el certificado de envío.

GIT_PUSH_CERT_STATUS

El estado de la verificación GPG del certificado de envío, usando el mismo mnemotécnico que se usa en el formato %G? de la familia de comandos git log (véase git-log(1)).

GIT_PUSH_CERT_NONCE

La cadena de nonce (número usado una sola vez) que el proceso pidió al firmante incluir en el certificado de envío. Si esto no coincide con el valor registrado en el encabezado "nonce" en el certificado de envío, puede indicar que el certificado es uno válido que se está reproduciendo desde una sesión separada de "git push".

GIT_PUSH_CERT_NONCE_STATUS

UNSOLICITED

"git push --signed" envió un nonce cuando no le pedimos que enviara uno.

MISSING

"git push --signed" no envió ningún encabezado nonce.

BAD

"git push --signed" envió un nonce falso.

OK

"git push --signed" envió el nonce que le pedimos que enviara.

SLOP

"git push --signed" envió un nonce diferente de lo que le pedimos ahora, pero en una sesión anterior. Véase la variable de entorno GIT_PUSH_CERT_NONCE_SLOP .

GIT_PUSH_CERT_NONCE_SLOP

"git push --signed" envió un nonce diferente de lo que le pedimos ahora, pero en una sesión diferente cuyo tiempo de inicio difiere en este número de segundos de la sesión actual. Solo tiene sentido cuando GIT_PUSH_CERT_NONCE_STATUS dice SLOP. Lea también sobre la variable receive.certNonceSlop en git-config(1).

Este gancho se llama antes de que se actualice cualquier nombre-referencia y antes de que se realicen las comprobaciones de avance rápido.

Si el gancho pre-receive termina con un estado de salida distinto de cero, no se realizarán actualizaciones, y los ganchos update, post-receive y post-update tampoco serán invocados. Esto puede ser útil para salir rápidamente si la actualización no va a ser soportada.

Véase las notas sobre el entorno de cuarentena más abajo.

GANCHO (HOOK) UPDATE

Antes de que se actualice cada referencia, si el archivo $GIT_DIR/hooks/update existe y es ejecutable, se invoca una vez por referencia, con tres parámetros:

$GIT_DIR/hooks/update nombre-referencia sha1-antiguo sha1-nuevo

El parámetro nombre-referencia es relativo a $GIT_DIR; p. ej. para la cabecera master esto es "refs/heads/master". Los dos argumentos sha1 son los nombres de objeto para el nombre-referencia antes y después de la actualización. Tenga en cuenta que el gancho se llama antes de que se actualice el nombre-referencia, así que o bien sha1-antiguo es 0{40} (lo que significa que aún no existe tal referencia), o debería coincidir con lo que está registrado en nombre-referencia.

El gancho debería terminar con un estado distinto de cero si quiere desallow la actualización de la referencia nombrada. De lo contrario debería terminar con cero.

La ejecución exitosa (un estado de salida cero) de este gancho no asegura que la referencia realmente será actualizada, es solo un prerrequisito. Como tal, no es una buena idea enviar notificaciones (p. ej. correo electrónico) desde este gancho. Considere usar el gancho post-receive en su lugar.

GANCHO (HOOK) POST-RECEIVE

Después de que todas las referencias hayan sido actualizadas (o se haya intentado actualizarlas), si alguna actualización de referencia fue exitosa, y si el archivo $GIT_DIR/hooks/post-receive existe y es ejecutable, será invocado una vez sin parámetros. La entrada estándar del gancho tendrá una línea por cada referencia actualizada exitosamente:

sha1-antiguo ESPACIO sha1-nuevo ESPACIO nombre-referencia LF

El valor del nombre-referencia es relativo a $GIT_DIR; p. ej. para la cabecera master esto es "refs/heads/master". Los dos valores sha1 antes de cada nombre-referencia son los nombres de objeto para el nombre-referencia antes y después de la actualización. Las referencias que fueron creadas tendrán sha1-antiguo igual a 0{40}, mientras que las referencias que fueron eliminadas tendrán sha1-nuevo igual a 0{40}, de lo contrario sha1-antiguo y sha1-nuevo deben ser objetos válidos en el repositorio.

Las variables de entorno GIT_PUSH_CERT* pueden ser inspeccionadas, tal como en el gancho pre-receive , después de aceptar un envío firmado.

Usando este gancho, es fácil generar correos describiendo las actualizaciones al repositorio. NAME


git-receive-pack - Update refs locally accepting \"push\" from another repository






SYNOPSIS


git receive-pack <directory>






DESCRIPTION


This command is called by git-push to update references
    in the receiving repository. It reads ref updates from standard input in
    the same format as git-send-pack and writes the ref advertisement
    back to standard output. It is usually not called directly by the user.


The command takes one argument, the path to the repository
    directory to be updated.


The command exits with a non-zero status if the push failed.


When a push is made to a repository that is served via a
    transport protocol like SSH, the remote side runs git-receive-pack
    in the repository directory. This command handles the incoming data,
    validates the requested updates, and updates the references in the repository
    after running hooks.


The git-receive-pack command handles the following hooks:



    
    
    
  • pre-receive hook
    • 
    
  • update hook
    • 
    
  • post-receive hook
    • 
    
  • post-update hook
    • 
    








OPTIONS


This command does not take any options.






PRE-RECEIVE HOOK


This hook is invoked before any refs are updated. It is given a list
    of refs that are about to be updated, their old values, and their new values,
    all read from standard input.




old-sha1 new-sha1 ref-name
old-sha1 new-sha1 ref-name
...





If the hook program exits with a non-zero status, then none of the
    refs are updated. This hook is suitable for validating the requested updates
    or performing checks before anything is changed in the repository. Note that
    the objects being pushed are not yet available in the main object store of
    the repository when this hook is invoked; they are staged in a temporary
    \"quarantine\" directory.


If the hook program exits successfully (status 0), then the
    updates are applied to the repository.


The standard output of the hook program is ignored.


The hook program receives the arguments <old-sha1>
    <new-sha1> <ref-name> on standard input. For example:




0000000000000000000000000000000000000000 f416468f03c346455a6365d06c09971c280b4447 refs/heads/main
a1b2c3d4a1b2c3d4a1b2c3d4a1b2c3d4a1b2c3d4 refs/heads/main




When a ref is deleted, the new sha1 is all zeros (the zero
    sha1).






UPDATE HOOK


This hook is invoked once for each ref that is updated. It is given
    the ref name and its old and new values as command-line arguments.




$GIT_DIR/hooks/update <old-sha1> <new-sha1> <ref-name>




If the hook program exits with a non-zero status, then that specific
    ref update is rejected, but other refs specified in the same push operation
    might still be updated. This hook is suitable for enforcing policies on
    individual refs.


The standard output of the hook program is ignored.


As with the pre-receive hook, the objects being pushed
    are not yet available in the main object store.


The pre-receive hook is generally preferred over the
    update hook because it allows the entire push operation to be rejected
    atomically if any of the refs fail validation. However, the update hook
    allows for finer-grained control, permitting some refs to be updated while
    rejecting others within the same push.






POST-RECEIVE HOOK


This hook is invoked after all refs have been updated. It receives
    no arguments, but it receives the list of refs that were updated (along with
    their old and new values) on standard input, in the same format as the
    pre-receive hook.




old-sha1 new-sha1 ref-name
old-sha1 new-sha1 ref-name
...





This hook is suitable for performing repository-wide tasks that
    depend on the updates having been completed, such as sending out notifications
    or triggering build processes. The objects are available in the repository's
    object store at this point.


The exit code of this hook is ignored.


Example script that sends an email for each updated ref:




#!/bin/sh
# receive hook
while read oldrev newrev refname
do
        if test "$oldrev" = 0000000000000000000000000000000000000000
        then
                # New reference
                echo "New ref: $refname $newrev"
        else
                # Update to existing reference
                echo "Updating ref: $refname $oldrev..$newrev"
        fi
done | mail -s "Repository update" user@example.com
exit 0




In addition to the standard refs, this hook may also receive
    information about signed push certificates. If a signed push certificate
    was presented by the client and validated (meaning its signature was
    verified and its nonce matched the expected value), the certificate itself
    will be available as a blob object, and its SHA-1 hash will be passed to the
    post-receive hook as an extra argument. The signer's identity and
    the nonce will also be available in environment variables.




#!/bin/sh
# post-receive hook

# Check if we received a signed push certificate
if test -n "${GIT_PUSH_CERT_SIGNER-}"
then
        # The certificate blob is referenced by $GIT_PUSH_CERT
        # The signer's identity is in $GIT_PUSH_CERT_SIGNER
        # The expected nonce is in $GIT_PUSH_NONCE
        # The status of the validation is in $GIT_PUSH_CERT_STATUS
        # (G=good, B=bad, U=unknown)

        # Report valid signed pushes
        if test "$GIT_PUSH_CERT_STATUS" = G
        then
                echo "Received signed push from $GIT_PUSH_CERT_SIGNER."
                echo "Nonce: $GIT_PUSH_NONCE"
                # You can inspect the certificate using:
                # git cat-file blob $GIT_PUSH_CERT
        fi
fi

# Process normal ref updates
while read oval nval ref
do
        # Skip the certificate ref if it was pushed
        if test "$ref" = "$GIT_PUSH_CERT"
        then
                continue
        fi

        # Report new commits
        if test "$oval" = "0000000000000000000000000000000000000000"
        then
                echo "New commits on $ref:"
                git rev-list --pretty "$nval"
        else
                echo "New commits on $ref:"
                git rev-list --pretty "$nval" "^$oval"
        fi |
        mail -s "Changes to ref $ref" commit-list@mydomain
done
# log signed push certificate, if any
if test -n "${GIT_PUSH_CERT-}" && test ${GIT_PUSH_CERT_STATUS} = G
then
        (
                echo expected nonce is ${GIT_PUSH_NONCE}
                git cat-file blob ${GIT_PUSH_CERT}
        ) | mail -s "push certificate from $GIT_PUSH_CERT_SIGNER" push-log@mydomain
fi
exit 0








POST-UPDATE HOOK


After all other processing, if at least one ref was updated, and
    if $GIT_DIR/hooks/post-update file exists and is executable, then
    post-update will be called with the list of refs that have been updated.
    This can be used to implement any repository wide cleanup tasks.


The exit code from this hook invocation is ignored; the only thing
    left for git-receive-pack to do at that point is to exit itself
    anyway.


This hook can be used, for example, to run git
    update-server-info if the repository is packed and is served via a
    dumb transport.




#!/bin/sh
exec git update-server-info








QUARANTINE ENVIRONMENT


When receive-pack takes in objects, they are placed into a
    temporary "quarantine" directory within the
    $GIT_DIR/objects directory and migrated into the main object store
    only after the pre-receive hook has completed. If the push fails
    before then, the temporary directory is removed entirely.


This has a few user-visible effects and caveats:


 1.Pushes which fail due to problems with the incoming
    pack, missing objects, or due to the pre-receive hook will not leave
    any on-disk data. This is usually helpful to prevent repeated failed pushes
    from filling up your disk, but can make debugging more challenging.


 2.Any objects created by the pre-receive hook
    will be created in the quarantine directory (and migrated only if it
    succeeds).


 3.The pre-receive hook MUST NOT update any refs
    to point to quarantined objects. Other programs accessing the repository will
    not be able to see the objects (and if the pre-receive hook fails, those refs
    would become corrupted). For safety, any ref updates from within
    pre-receive are automatically rejected.
