NOMBRE

gitprotocol-common - Cosas comunes a varios protocolos

SINOPSIS

<protocolo-de-transmisión>

DESCRIPCIÓN

Este documento define las cosas comunes a varios protocolos de transmisión y formatos de archivo utilizados en Git.

NOTACIÓN ABNF

Se utiliza la notación ABNF descrita por RFC 5234 dentro de los documentos de protocolo, excepto que se utilizan las siguientes reglas básicas de reemplazo:

  HEXDIG    =  DIGIT / "a" / "b" / "c" / "d" / "e" / "f"

También definimos las siguientes reglas comunes:

  NUL       =  %x00
  zero-id   =  40*"0"
  obj-id    =  40*(HEXDIGIT)
  refname  =  "HEAD"
  refname /=  "refs/" <ver discusión abajo>

Un nombre de ref (refname) es una cadena de octetos jerárquica que comienza con "refs/" y no viola las reglas de validación del comando git-check-ref-format. Más específicamente, ellos:

1.Pueden incluir la barra / para agrupamiento jerárquico (directorio), pero ningún componente separado por barras puede comenzar con un punto ..
2.Deben contener al menos una /. Esto fuerza la presencia de una categoría como heads/, tags/, etc., pero los nombres reales no están restringidos.
3.No pueden tener dos puntos consecutivos .. en ningún lugar.
4.No pueden tener caracteres de control ASCII (es decir, bytes cuyos valores son menores que \040, o \177 DEL), espacio, tilde ~, circunflejo ^, dos puntos :, signo de interrogación ?, asterisco *, o corchete de apertura [ en ningún lugar.
5.No pueden terminar con una barra / o un punto ..
6.No pueden terminar con la secuencia .lock.
7.No pueden contener una secuencia @{.
8.No pueden contener una \\.

FORMATO PKT-LINE

Gran parte (pero no toda) la carga útil se describe en torno a las pkt-lines.

Una pkt-line es una cadena binaria de longitud variable. Los primeros cuatro bytes de la línea, el pkt-len, indican la longitud total de la línea, en hexadecimal. El pkt-len incluye los 4 bytes utilizados para contener la representación hexadecimal de la longitud.

Una pkt-line PUEDE contener datos binarios, por lo que los implementadores DEBEN asegurarse de que las rutinas de análisis/formateo de pkt-line sean limpias en 8 bits.

Una línea no binaria DEBERÍA estar terminada por un LF, que si está presente DEBE incluirse en la longitud total. Los receptores DEBEN tratar las pkt-lines con datos no binarios de la misma manera, ya sea que contengan o no el LF final (eliminando el LF si está presente y no quejándose cuando falta).

La longitud máxima del componente de datos de una pkt-line es de 65516 bytes. Las implementaciones NO DEBEN enviar pkt-lines cuya longitud exceda los 65520 (65516 bytes de carga útil + 4 bytes de datos de longitud).

Las implementaciones NO DEBERÍAN enviar una pkt-line vacía ("0004").

Una pkt-line con un campo de longitud de 0 ("0000"), llamada flush-pkt, es un caso especial y DEBE manejarse de manera diferente a una pkt-line vacía ("0004").

  pkt-line     =  data-pkt / flush-pkt
  data-pkt     =  pkt-len pkt-payload
  pkt-len      =  4*(HEXDIG)
  pkt-payload  =  (pkt-len - 4)*(OCTET)
  flush-pkt    = "0000"

Ejemplos (como cadenas estilo C):

  pkt-line          valor real
  ---------------------------------
  "0006a\n"         "a\n"
  "0005a"           "a"
  "000bfoobar\n"    "foobar\n"
  "0004"            ""
