GIT-SEND-PACK(1) Manual de Git GIT-SEND-PACK(1)

NOMBRE

git-send-pack - Envía objetos a través del protocolo Git a otro repositorio

SINOPSIS

git send-pack [--mirror] [--dry-run] [--force]
                [--receive-pack=<git-receive-pack>]
                [--verbose] [--thin] [--atomic]
                [--[no-]signed | --signed=(true|false|if-asked)]
                [<host>:]<directorio> (--all | <ref>...)

DESCRIPCIÓN

Normalmente, deberías usar git push, que es un envoltorio de nivel superior de este comando, en su lugar. Consulta git-push(1).

Invoca git-receive-pack en un repositorio posiblemente remoto y lo actualiza desde el repositorio actual, enviando las refs nombradas.

OPCIONES

--receive-pack=<git-receive-pack>

Ruta al programa git-receive-pack en el extremo remoto. A veces es útil al enviar a un repositorio remoto a través de ssh, y no tienes el programa en un directorio de la $PATH predeterminada.

--exec=<git-receive-pack>

Igual que --receive-pack=<git-receive-pack>.

--all

En lugar de especificar explícitamente qué refs actualizar, actualiza todas las cabeceras que existen localmente.

--stdin

Toma la lista de refs de la entrada estándar, una por línea. Si hay refs especificadas en la línea de comandos además de esta opción, las refs de la entrada estándar se procesan después de las de la línea de comandos.

Si se especifica --stateless-rpc junto con esta opción, la lista de refs debe estar en formato de paquetes (pkt-line). Cada ref debe estar en un paquete separado, y la lista debe terminar con un paquete de cierre.

--dry-run

Haz todo excepto enviar las actualizaciones realmente.

--force

Normalmente, el comando se niega a actualizar una ref remota que no sea un antepasado de la ref local utilizada para sobrescribirla. Esta bandera deshabilita la verificación. Esto significa que el repositorio remoto puede perder commits; úsala con cuidado.

--verbose

Ejecutar detalladamente.

--thin

Envía un paquete "delgado", que registra objetos en forma deltificada basándose en objetos no incluidos en el paquete para reducir el tráfico de red.

--atomic

Utiliza una transacción atómica para actualizar las refs. Si alguna de las refs falla al actualizarse, todo el envío fallará sin cambiar ninguna ref.

--signed, --no-signed, --signed=(true|false|if-asked)

Firma GPG la solicitud de envío para actualizar refs en el lado receptor, para permitir que sea verificada por los hooks y/o registrada. Si es false o --no-signed, no se intentará firmar. Si es true o --signed, el envío fallará si el servidor no admite envíos firmados. Si se establece en if-asked, firma si y solo si el servidor admite envíos firmados. El envío también fallará si la llamada real a gpg --sign falla. Consulta git-receive-pack(1) para más detalles en el extremo receptor.

--push-option=<cadena>

Pasa la cadena especificada como una opción de envío para que sea consumida por los hooks en el lado del servidor. Si el servidor no admite opciones de envío, genera un error. Consulta git-push(1) y githooks(5) para más detalles.

<host>

Un host remoto para alojar el repositorio. Cuando se especifica esta parte, git-receive-pack se invoca a través de ssh.

<directorio>

El repositorio a actualizar.

<ref>...

Las refs remotas a actualizar.

ESPECIFICANDO LAS REFS

Hay tres formas de especificar qué refs actualizar en el extremo remoto.

Con la bandera --all, todas las refs que existen localmente se transfieren al lado remoto. No puedes especificar ninguna <ref> si usas esta bandera.

Sin --all y sin ninguna <ref>, se actualizan las cabeceras que existen tanto en el lado local como en el lado remoto.

Cuando se especifican explícitamente una o más <ref> (ya sea en la línea de comandos o a través de --stdin), puede ser un patrón único o un par de dichos patrones separados por dos puntos ":" (esto significa que un nombre de ref no puede tener dos puntos en él). Un patrón único <nombre> es solo una abreviatura para <nombre>:<nombre>.

Cada par de patrones consta del lado de origen (antes de los dos puntos) y el lado de destino (después de los dos puntos). La ref que se va a enviar se determina encontrando una coincidencia que coincida con el lado de origen, y dónde se envía se determina usando el lado de destino. Las reglas utilizadas para hacer coincidir una ref son las mismas reglas utilizadas por git rev-parse para resolver un nombre de ref simbólico. Consulta git-rev-parse(1).

•Es un error si <src> no coincide exactamente con una de las refs locales.
•Es un error si <dst> coincide con más de una ref remota.
•Si <dst> no coincide con ninguna ref remota,
•tiene que empezar con "refs/"; <dst> se utiliza como destino literalmente en este caso.
•<src> == <dst> y la ref que coincidió con <src> no debe existir en el conjunto de refs remotas; la ref que coincidió con <src> localmente se utiliza como nombre del destino.

Sin --force, la ref <src> se almacena en el remoto solo si <dst> no existe, o <dst> es un subconjunto propio (es decir, un antepasado) de <src>. Esta verificación, conocida como la verificación de "fast-forward", se realiza para evitar sobrescribir accidentalmente la ref remota y perder los commits de otras personas de allí.

Con --force, la verificación de fast-forward se deshabilita para todas las refs.

Opcionalmente, un parámetro <ref> puede ir precedido por un signo más + para deshabilitar la verificación de fast-forward solo en esa ref.
