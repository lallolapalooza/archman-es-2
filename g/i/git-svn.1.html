DESCRIPCIÓ

N

git svn es un conducto simple para conjuntos de cambios entre Subversion y Git. Proporciona un flujo bidireccional de cambios entre un repositorio Subversion y uno de

Git.

git svn puede rastrear un repositorio Subversion estándar, siguiendo el diseño común "trunk/branches/tags", con la opción --stdlayout. También puede seguir ramas y etiquetas en cualquier diseño con las opciones -T/-t/-b (ver opciones de init más abajo, y también el comando clone)

.

Una vez que se está rastreando un repositorio Subversion (con cualquiera de los métodos anteriores), el repositorio de Git puede actualizarse desde Subversion con el comando fetch y Subversion puede actualizarse desde Git con el comando

dcom
mit.

Esto permite especificar un prefijo que se antepone a los nombres de los remotos si se especifican trunk/branches/tags. El prefijo no incluye automáticamente una barra final, así que asegúrese de incluir una en el argumento si eso es lo que desea. Establecer un prefijo (con una barra final) se recomienda encarecidamente en cualquier caso, ya que sus refs de seguimiento de SVN se ubicarán entonces en "refs/remotes/$prefix/", lo cual es compatible con el diseño de refs de seguimiento de remotos de Git (refs/remotes/$remote/). Establecer un prefijo también es útil si desea rastrear múltiples proyectos que comparten un repositorio común. Por defecto, el prefijo se establece a origin/.

Nota
Antes de Git v2.0, el prefijo por defecto era "" (sin prefijo). Esto significaba que las refs de seguimiento de SVN se colocaban en "refs/remotes/*", lo cual es incompatible con cómo se organizan las refs de seguimiento de remotos de Git. Si aún desea el valor por defecto anterior, puede obtenerlo pasando --prefix "" en la línea de comandos (--prefix="" puede no funcionar si el

REBASE VS.

PULL/MERGE

Prefiera usar git svn rebase o git rebase, más bien que git pull o git merge para sincronizar commits no integrados con una rama git svn. Hacer esto mantendrá el historial de commits no integrados lineal con respecto al repositorio SVN upstream y permitirá el uso del subcomando preferido git svn dcommit para empujar commits no integrados de vuelta a

SVN.

Originalmente, git svn recomendaba que los desarrolladores hicieran pull o merge desde la rama git svn. Esto era porque el autor favorecía git svn set-tree B para hacer commit de un solo head en lugar de la notación git svn set-tree A..B para hacer commit de múltiples commits. El uso de git pull o git merge con git svn set-tree A..B causará que el historial no lineal se aplane al hacer commit en SVN y esto puede l

levar a que los commits de fusión reviertan
inesperadamente commits previos en SVN.

SEGUIMIENTO DE

FUSIONES

Aunque git svn puede rastrear el historial de copias (incluyendo ramas y etiquetas) para repositorios que adoptan un diseño estándar, aún no puede representar el historial de fusiones que ocurrieron dentro de git hacia

los usuarios upstream de SVN. Por lo tanto se aconseja a los usuarios que mantengan el historial lo más linea
l posible dentro de Git para facilitar la compatibilidad con SVN (vea la sección de ADVERTENCIAS más abajo).

MANEJO DE RAMAS

SVN

Si git svn está configurado para obtener ramas (y --follow-branches está en efecto), a veces crea múltiples ramas Git para una rama SVN, donde las ramas adicionales tienen nombres de la forma branchname@nnn (con nnn un número de revisión de SVN). Estas ramas adicionales se crean si git svn no puede encontrar un commit padre para el primer commit en una rama SVN, para conectar la rama al historial de las otras

ramas.

Normalmente, el primer commit en una rama SVN consiste en una operación de copia. git svn leerá este commit para obtener la revisión de SVN desde la que se creó la rama. Luego intentará encontrar el commit de Git que corresponde a esta revisión de SVN, y usarlo como padre de la rama. Sin embargo, es posible que no haya un commit de Git adecuado para servir como padre. Esto sucederá, entre otras razones, si la rama SVN es una copia de una revisión que no fue obtenida por git svn (p. ej. porque es una revisión antigua que fue omitida con --revision), o si en SVN se copió un directorio que no está rastreado por git svn (como una rama que no está rastreada en absoluto, o un subdirectorio de una rama rastreada). En estos casos, git svn creará igualmente una rama de Git, pero en lugar de usar un commit de Git existente como padre de la rama, leerá el historial de SVN del directorio desde el que se copió la rama y creará los commits de Git correspondientes. Esto se indica con el mensaje "Initializing parent: <branchname>

".

Además, creará una rama especial llamada <branchname>@<SVN-Revision>, donde <SVN-Revision> es el número de revisión de SVN desde la que se copió la rama. Esta rama apuntará al commit padre recién creado de la rama. Si en SVN la rama fue eliminada y luego recreada desde una versión diferente, habrá múltiples ramas así con un @

.

Ten en cuenta que esto puede significar que se creen múltiples commits de Git para una sola revisión de

SVN.

Un ejemplo: en un repositorio SVN con una estructura estándar trunk/tags/branches, se crea un directorio trunk/sub en la r.100. En la r.200, trunk/sub se ramifica copiándolo a branches/. git svn clone -s creará entonces una rama sub. También creará nuevos commits de Git para la r.100 hasta la r.199 y los usará como el historial de la rama sub. Así que habrá dos commits de Git para cada revisión de la r.100 a la r.199 (uno que contiene trunk/, otro que contiene trunk/sub/). Finalmente, creará una rama sub@200 apuntando al nuevo commit padre de la rama sub (es decir, el commit p

ara la r.200 y
trunk/sub/).

ADVERTENCI

AS

Por simplicidad y para interoperar con Subversion, se recomienda que todos los usuarios de git svn clonen, hagan fetch y dcommit directamente desde el servidor SVN, y eviten todas las operaciones de git clone/pull/merge/push entre repositorios y ramas de Git. El método recomendado para intercambiar código entre ramas de Git y usuarios es git format-patch y git am, o simplemente hacer 'dcommit’ al repositorio

SVN.

Ejecutar git merge o git pull NO se recomienda en una rama de la que planees hacer dcommit, porque los usuarios de Subversion no pueden ver ninguna fusión (merge) que hayas hecho. Además, si haces merge o pull desde una rama de Git que es un espejo de una rama de SVN, dcommit podría hacer commit en la rama

equivocada.

Si haces merge, ten en cuenta la siguiente regla: git svn dcommit intentará hacer commit encima del commit de SVN nombrado

en 
git log --grep=
^git-svn-id: --
first-parent -1

Por lo tanto, debes asegurarte de que el commit más reciente de la rama a la que quieres hacer dcommit sea el primer padre de la fusión (merge). De lo contrario se producirá el caos, especialmente si el primer padre es un commit más antiguo en la misma rama de

SVN.

git clone no clona ramas bajo la jerarquía refs/remotes/ ni ningún metadato de git svn, ni la configuración. Así que los repositorios creados y gestionados usando git svn deberían usar rsync para clonar, si se va a clonar en

absoluto.

Dado que dcommit usa rebase internamente, cualquier rama de Git a la que hagas git push antes de hacer dcommit requerirá forzar una sobrescritura de la referencia existente en el repositorio remoto. Esto generalmente se considera una mala práctica, consulta la documentación de git-push(1) para más

detalles.

No uses la opción --amend de git-commit(1) en un cambio que ya hayas hecho dcommit. Se considera mala práctica hacer --amend a commits que ya has subido a un repositorio remoto para otros usuarios, y dcommit con SVN es análogo a

eso.

Al clonar un repositorio SVN, si no se usa ninguna de las opciones para describir la estructura del repositorio (--trunk, --tags, --branches, --stdlayout), git svn clone creará un repositorio Git con un historial completamente lineal, donde las ramas y etiquetas aparecen como directorios separados en la copia de trabajo. Aunque esta es la forma más fácil de obtener una copia de un repositorio completo, para proyectos con muchas ramas llevará a una copia de trabajo muchas veces mayor que solo el trunk. Por lo tanto, para proyectos que usan la estructura de directorios estándar (trunk/branches/tags), se recomienda clonar con la opción --stdlayout. Si el proyecto usa una estructura no estándar, y/o si no se necesitan ramas y etiquetas, es más fácil clonar solo un directorio (típicamente trunk), sin dar ninguna opción de estructura del repositorio. Si se necesita el historial completo con ramas y etiquetas, se deben usar las opciones --trunk / --branches / --tags

.

Al usar múltiples --branches o --tags, git svn no maneja automáticamente colisiones de nombres (por ejemplo, si dos ramas de rutas diferentes tienen el mismo nombre, o si una rama y una etiqueta tienen el mismo nombre). En estos casos, usa init para configurar tu repositorio Git y luego, antes de tu primer fetch, edita el archivo $GIT_DIR/config para que las ramas y etiquetas estén asociadas a espacios de nombres diferentes. Por

ejemplo: 
branches = stable/*:refs/remotes/svn/stable/*
branches = debug/*:refs/remotes/svn/debu
g
/

        branches = branches/release_*:refs/remotes/project-a/branches/release_*
        branches = branches/re*se:refs/remotes/project-a/branches/*
