DESCRIPCIÓ

N

Dado uno o más commits existentes, revierte los cambios que los parches relacionados introducen y registra algunos nuevos commits que los registran. Esto requiere que tu árbol de trabajo esté limpio (sin modificaciones desde el commit HEAD)

.

Nota: git revert se usa para registrar algunos nuevos commits para revertir el efecto de algunos commits anteriores (a menudo solo uno defectuoso). Si quieres descartar todos los cambios sin confirmar en tu directorio de trabajo, deberías ver git-reset(1), particularmente la opción --hard. Si quieres extraer archivos específicos tal como estaban en otro commit, deberías ver git-restore(1), específicamente la opción --source. Ten cuidado con estas alternativas ya que ambas descartarán cambios sin confirmar en tu directorio de

trabajo.

Ver "Reset, restore y revert" en git(1) para las diferenc

ias entre los
tres comandos.

OPCIONE

S

<commit>..

.
Commits a revertir. Para una lista más completa de formas de escribir nombres de commits, ver gitrevisions(7). También se pueden dar conjuntos de commits pero no se hace ninguna traversión por defecto, ver git-rev-list(1) y su opción --no
-walk.

-e,

--edit
Con esta opción, git revert te permitirá editar el mensaje del commit antes de confirmar la reversión. Esto es lo predeterminado si ejecutas el comando desde una
terminal.

-m parent-number, --mainline

parent-number
Normalmente no puedes revertir un merge porque no sabes qué lado del merge debe considerarse la línea principal. Esta opción especifica el número de padre (empezando desde 1) de la línea principal y permite a revert invertir el cambio relativo al padre especificado.

Revertir un commit de merge declara que nunca querrás los cambios de árbol que trajo el merge. Como resultado, los merges posteriores solo traerán cambios de árbol introducidos por commits que no sean ancestros del merge revertido previamente. Esto puede o no ser lo que

quieras.

Ver el revert-a-faulty-merge How-

To[1] para má
s detalles.

--no-edi

t
Con esta opción, git revert no iniciará el editor de mensajes de
commit.

--cleanup=<mode

>
Esta opción determina cómo se limpiará el mensaje del commit antes de pasarlo al mecanismo de confirmación. Ver git-commit(1) para más detalles. En particular, si el <mode> recibe el valor scissors, scissors se añadirá a MERGE_MSG antes de pasarse en el caso de un
conflicto.

-n,

--no-commit
Normalmente el comando crea automáticamente algunos commits con mensajes de registro que indican qué commits fueron revertidos. Esta bandera aplica los cambios necesarios para revertir los commits nombrados a tu árbol de trabajo y al índice, pero no hace los commits. Además, cuando se usa esta opción, tu índice no tiene que coincidir con el commit HEAD. La reversión se hace contra el estado inicial de tu índice.

Esto es útil al revertir el

efecto de más de un commit
a tu índice en una fila.

-S[<keyid>], --gpg-sign[=<keyid>],

--no-gpg-sign
Firmar commits con GPG. El argumento keyid es opcional y por defecto es la identidad del confirmador; si se especifica, debe pegarse a la opción sin espacio. --no-gpg-sign es útil para contrarrestar tanto la variable de configuración commit.gpgSign como un --gpg-sign an
terior.

-s,

--signoff
Añadir un remate Signed-off-by al final del mensaje del commit. Ver la opción signoff en git-commit(1) para más
información.

--strategy=<strategy

>
Usar la estrategia de merge dada. Solo debe usarse una vez. Ver la sección MERGE STRATEGIES en git-merge(1) para
detalles.

-X<option>, --strategy-option=<option

>
Pasar la opción específica de la estrategia de merge a la estrategia de merge. Ver git-merge(1) para
detalles.

--rerere-autoupdate, --no-rerere-autoupdat

e
Después de que el mecanismo rerere reutilice una resolución registrada en el conflicto actual para actualizar los archivos en el árbol de trabajo, permitirle también actualizar el índice con el resultado de la resolución. --no-rerere-autoupdate es una buena manera de verificar dos veces lo que rerere hizo y detectar posibles fusiones incorrectas, antes de confirmar el resultado en el índice con un git add separ
ado.

--referenc

e
En lugar de comenzar el cuerpo del mensaje de registro con "This reverts <full-object-name-of-the-commit-being-reverted>.", referirse al commit usando el formato "--pretty=reference" (cf. git-log(1)). La variable de configuración revert.reference puede
usarse para habilitar
esta opción por defecto.

e

EJEMPLO

S

git revert HEAD~

3
Revertir los cambios especificados por el cuarto commit desde el final en HEAD y crear un nuevo commit con los cambios
revertidos.

git revert -n master~5..master~

2
Revertir los cambios hechos por los commits desde el quinto commit desde el final en master (
incluido) hasta el tercer commit desde el final en master (incluido), pero no crear ningún c
ommit con los cambios revertidos. La reversión solo modifica el árbol de trabajo y el índice.

DISCUSIÓ

N

Aunque git crea automáticamente un mensaje de commit básico, es fuertemente recomendado explicar por qué se está revirtiendo el commit original. Además, revertir repetidamente reversiones resultará en líneas de asunto cada vez más engorrosas, por ejemplo Reapply "Reapply "<original-subject>"". Por favor, consi

dera reformular estas para
que sean más cortas y únicas.
