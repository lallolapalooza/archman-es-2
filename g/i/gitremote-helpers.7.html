DESCRIPCIÓ

N

Los programas auxiliares remotos normalmente no son utilizados directamente por los usuarios finales, sino que son invocados por Git cuando necesita interactuar con repositorios remotos que Git no soporta de forma nativa. Un auxiliar determinado implementará un subconjunto de las capacidades documentadas aquí. Cuando Git necesita interactuar con un repositorio usando un auxiliar remoto, lanza el auxiliar como un proceso independiente, envía comandos a la entrada estándar del auxiliar y espera resultados de la salida estándar del auxiliar. Debido a que un auxiliar remoto se ejecuta como un proceso independiente de Git, no es necesario volver a vincular Git para añadir un nuevo auxiliar, ni es necesario vincular el auxiliar con la implementación de

Git.

Todo auxiliar debe soportar el comando "capabilities", que Git utiliza para determinar qué otros comandos aceptará el auxiliar. Esos otros comandos pueden usarse para descubrir y actualizar referencias remotas, transportar objetos entre la base de datos de objetos y el repositorio remoto, y actualizar el almacén de objetos

local.

Git viene con una familia de auxiliares remotos "curl", que manejan varios protocolos de transporte, como git-remote-http, git-remote-https, git-remote-ftp y git-remote-ftps. Implementan las capacidades fetch, option, y pu

sh
.

INVOCACIÓ

N

Los programas auxiliares remotos se invocan con uno o (opcionalmente) dos argumentos. El primer argumento especifica un repositorio remoto como en Git; es el nombre de un remoto configurado o una URL. El segundo argumento especifica una URL; usualmente tiene la forma <transport>://<address>, pero cualquier cadena arbitraria es posible. La variable de entorno GIT_DIR está configurada para el auxiliar remoto y puede usarse para determinar dónde almacenar datos adicionales o desde qué directorio invocar comandos auxiliares de

Git.

Cuando Git encuentra una URL de la forma <transport>://<address>, donde <transport> es un protocolo que no puede manejar de forma nativa, invoca automáticamente git remote-<transport> con la URL completa como segundo argumento. Si tal URL se encuentra directamente en la línea de comandos, el primer argumento es el mismo que el segundo, y si se encuentra en un remoto configurado, el primer argumento es el nombre de ese

remoto.

Una URL de la forma <transport>::<address> instruye explícitamente a Git para invocar git remote-<transport> con <address> como segundo argumento. Si tal URL se encuentra directamente en la línea de comandos, el primer argumento es <address>, y si se encuentra en un remoto configurado, el primer argumento es el nombre de ese

remoto.

Adicionalmente, cuando un remoto configurado tiene remote.<name>.vcs establecido a <transport>, Git invoca explícitamente git remote-<transport> con <name> como primer argumento. Si está establecido, el segundo argumento es remote.<name>.url; de lo contrario, e

l segundo argum

DESCRIPTION

This document describes the protocol used by Git to communicate with remote helpers.

A remote helper is an executable that Git can invoke to handle access to a remote repository. For example, Git ships with git-remote-ext(1) which allows Git to fetch from and push to repositories accessible via a command. Git also ships with git-remote-fd(1) which is used by Git to communicate with the remote repository when it is in another Git process.

Remote helpers are invoked by Git, and they communicate with Git via stdin/stdout. Git writes commands to the helper’s stdin, and the helper writes responses to its stdout. The helper may write messages to stderr which will be displayed to the user.

The protocol is line-based. Git writes a command line to the helper’s stdin, and the helper must respond with a line of output. Some commands may require the helper to write multiple lines of output, or to write data after the command line. Git will signal the end of output by closing the pipe.

INVOCATION

When Git needs to communicate with a remote helper, it invokes the helper as a subcommand. For example, if you run git fetch on a repository configured to use the git-daemon remote helper, Git will execute:

git remote-daemon user@host:path

The remote name is omitted, and the arguments to the helper are the remaining arguments from the original Git command line, except that the remote URL is usually passed as the first argument.

If the remote helper is designed to handle multiple commands (e.g., fetch and push), it must be able to determine which command Git wants to run. This is done by Git writing the command name as the first line on stdin. For example, if Git wants to fetch, it writes:

git-fetch

and if it wants to push, it writes:

git-push

The helper must respond with a line indicating its capabilities, e.g.:

capabilities^{git-upload-pack,git-receive-pack}

This line lists the commands that the helper supports, separated by commas.

Note that the actual commands are optional. If a helper does not implement a command that Git asks it to run, Git will assume that the command failed.

INPUT FORMAT

The input Git sends to the helper is a sequence of commands, each followed by zero or more arguments and/or data.

A command is given as a single line of text. Arguments are space separated. Data is sent after the command line, terminated by EOF.

The following commands are defined:

git-fetch remote
Fetch refs from remote. The default refspec is to fetch all refs. This command requires the helper to write a list of refs that are available on the remote, followed by the objects associated with those refs. The refs are listed one per line, each line starting with the object name, followed by a space, and then the ref name. If the ref is annotated, the ref name is followed by a space and the tag object name. If the ref is tagged, the ref name is followed by a space and the tag object name. The list of refs is terminated by a blank line. After the refs are listed, the helper sends the objects associated with those refs, followed by the usual Git protocol handshake. This command may also be passed the option progress true capability. In this case, the helper should print progress information to stderr.
git-push remote
Push refs to remote. The command is followed by a list of refs to push, one per line. Each line starts with the source ref, followed by a space, and then the destination ref. The source ref is the object name of the ref to push, and the destination ref is the name of the ref on the remote.

When a file transfer is performed, the helper writes the name of the file to stdout, followed by the contents of the file. The file name is given in a format that is suitable for use with the Git internals (e.g., .git/objects/pack/pack-*.git). The transfer is terminated by EOF.

The helper may write additional information to stderr. This information is displayed to the user.

If a partial download is detected, the helper may write the name of the partial download file to stdout. If <path>.temp exists, then Git assumes that the .temp file is a partial download from a previous attempt and will resume the download from that position.

If a fatal error occurs, the program writes the error message to stderr and exits. The caller should expect that a suitable error message has been printed if the child closes the connection without completing a valid response for the current command.

Additional commands may be supported, as may be determined from capabilities reported by the helper.

REF LIST ATTRIBUTES

The list command produces a list of refs in which each ref may be followed by a list of attributes. The following ref list attributes are defined.

unchanged

This ref is unchanged since the last import or fetch, although the helper cannot necessarily determine what value that produced.

REF LIST KEYWORDS

The list command may produce a list of key-value pairs. The following keys are defined.

object-format

The refs are using the given hash algorithm. This keyword is only used if the server and client both support the object-format extension.

OPTIONS

The following options are defined and (under suitable circumstances) set by Git if the remote helper has the option capability.

option verbosity <n>

Changes the verbosity of messages displayed by the helper. A value of 0 for <n> means that processes operate quietly, and the helper produces only error output. 1 is the default level of verbosity, and higher values of <n> correspond to the number of -v flags passed on the command line.

option progress {true|false}

Enables (or disables) progress messages displayed by the transport helper during a command.

option depth <depth>

Deepens the history of a shallow repository.

option deepen-since <timestamp>

Deepens the history of a shallow repository based on time.

option deepen-not <ref>

Deepens the history of a shallow repository excluding ref. Multiple options add up.

option deepen-relative {true|false}

Deepens the history of a shallow repository relative to current boundary. Only valid when used with "option depth".

option followtags {true|false}

If enabled the helper should automatically fetch annotated tag objects if the object the tag points at was transferred during the fetch command. If the tag is not fetched by the helper a second fetch command will usually be sent to ask for the tag specifically. Some helpers may be able to use this option to avoid a second network connection.

option dry-run {true|false}

If true, pretend the operation completed successfully, but don’t actually change any repository data. For most helpers this only applies to the push, if supported.

option servpath <c-style-quoted-path>

Sets service path (--upload-pack, --receive-pack etc.) for next connect. Remote helper may support this option, but must not rely on this option being set before connect request occurs.

option check-connectivity {true|false}

Request the helper to check connectivity of a clone.

option force {true|false}

Request the helper to perform a force update. Defaults to false.

option cloning {true|false}

Notify the helper this is a clone request (i.e. the current repository is guaranteed empty).

option update-shallow {true|false}

Allow to extend .git/shallow if the new refs require it.

option pushcert {true|false}

GPG sign pushes.

option push-option <string>

Transmit <string> as a push option. As the push option must not contain LF or NUL characters, the string is not encoded.

option from-promisor {true|false}

Indicate that these objects are being fetched from a promisor.

option no-dependents {true|false}

Indicate that only the objects wanted need to be fetched, not their dependents.

option atomic {true|false}

When pushing, request the remote server to update refs in a single atomic transaction. If successful, all refs will be updated, or none will. If the remote side does not support this capability, the push will fail.

option object-format true

Indicate that the caller wants hash algorithm information to be passed back from the remote. This mode is used when fetching refs.
