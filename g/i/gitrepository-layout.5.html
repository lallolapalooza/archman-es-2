GITREPOSITORY-LAYOUT(5) Manual de Git GITREPOSITORY-LAYOUT(5)

NOMBRE

gitrepository-layout - Diseño del Repositorio de Git

SINOPSIS

$GIT_DIR/*

DESCRIPCIÓN

Un repositorio de Git tiene dos sabores diferentes:

•un directorio .git en la raíz del árbol de trabajo;
•un directorio <proyecto>.git que es un repositorio bare (es decir, sin su propio árbol de trabajo), que se utiliza típicamente para intercambiar historiales con otros al hacer push hacia él y fetch desde él.

Nota: También puedes tener un archivo de texto plano .git en la raíz de tu árbol de trabajo, que contiene gitdir: <ruta> para apuntar al directorio real que tiene el repositorio. Este mecanismo se llama gitfile y generalmente se gestiona a través de los comandos git submodule y git worktree. Se utiliza a menudo para un árbol de trabajo de un checkout de submódulo, para permitirte en el superproyecto contenedor hacer git checkout de una rama que no tiene el submódulo. El checkout tiene que eliminar todo el árbol de trabajo del submódulo, sin perder el repositorio del submódulo.

Estas cosas pueden existir en un repositorio de Git.

objects

Almacén de objetos asociado con este repositorio. Normalmente, un almacén de objetos es autosuficiente (es decir, todos los objetos a los que se hace referencia desde un objeto encontrado en él también se encuentran en él), pero hay algunas maneras de violar esto.
1.Podrías tener un repositorio incompleto pero localmente usable creando un clon superficial. Ver git-clone(1).
2.Podrías estar utilizando los mecanismos objects/info/alternates o $GIT_ALTERNATE_OBJECT_DIRECTORIES para tomar prestados objetos de otros almacenes de objetos. Un repositorio con este tipo de almacén de objetos incompleto no es adecuado para ser publicado para su uso con transportes tontos (dumb transports), pero por lo demás está bien mientras objects/info/alternates apunte a los almacenes de objetos de los que toma prestado.

Este directorio se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/objects" en su lugar.

objects/[0-9a-f][0-9a-f]

Un objeto recién creado se almacena en su propio archivo. Los objetos se extienden sobre 256 subdirectorios utilizando los dos primeros caracteres del nombre del objeto sha1 para mantener el número de entradas de directorio en objects manejable. Los objetos encontrados aquí a menudo se llaman objetos descomprimidos (o sueltos).

objects/pack

Los paquetes (archivos que almacenan muchos objetos en forma comprimida, junto con archivos índice para permitir el acceso aleatorio) se encuentran en este directorio.

objects/info

Información adicional sobre el almacén de objetos se registra en este directorio.

objects/info/packs

Este archivo sirve para ayudar a los transportes tontos a descubrir qué paquetes están disponibles en este almacén de objetos. Siempre que se añade o elimina un paquete, se debe ejecutar git update-server-info para mantener este archivo actualizado si el repositorio se publica para transportes tontos. git repack lo hace por defecto.

objects/info/alternates

Este archivo registra rutas a almacenes de objetos alternativos de los que este almacén de objetos toma prestados objetos, un nombre de ruta por línea. Ten en cuenta que no solo las herramientas nativas de Git lo usan localmente, sino que el recuperador HTTP también intenta usarlo de forma remota; esto generalmente funcionará si tienes rutas relativas (relativas a la base de datos de objetos, no al repositorio!) en tu archivo de alternativos, pero no funcionará si usas rutas absolutas a menos que la ruta absoluta en el sistema de archivos y la URL web sean las mismas. Ver también objects/info/http-alternates.

objects/info/http-alternates

Este archivo registra URLs de almacenes de objetos alternativos de los que este almacén de objetos toma prestados objetos, para ser utilizados cuando el repositorio se recupera a través de HTTP.

refs

Las referencias se almacenan en subdirectorios de este directorio. El comando git prune sabe que debe preservar los objetos alcanzables desde las referencias encontradas en este directorio y sus subdirectorios. Este directorio se ignora (excepto refs/bisect, refs/rewritten y refs/worktree) si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/refs" en su lugar.

refs/heads/nombre

registra los objetos commit de la punta del árbol de la rama nombre

refs/tags/nombre

registra cualquier nombre de objeto (no necesariamente un objeto commit, o un objeto tag que apunte a un objeto commit).

refs/remotes/nombre

registra los objetos commit de la punta del árbol de las ramas copiadas de un repositorio remoto.

refs/replace/<obj-sha1>

registra el SHA-1 del objeto que reemplaza a <obj-sha1>. Esto es similar a info/grafts y es utilizado y mantenido internamente por git-replace(1). Dichas referencias se pueden intercambiar entre repositorios, mientras que los grafts no.

packed-refs

registra la misma información que refs/heads/, refs/tags/, y similares en una forma más eficiente. Ver git-pack-refs(1). Este archivo se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/packed-refs" en su lugar.

HEAD

Una referencia simbólica (symref, ver glosario) al espacio de nombres refs/heads/ que describe la rama activa actualmente. No significa mucho si el repositorio no está asociado con ningún árbol de trabajo (es decir, un repositorio bare), pero un repositorio Git válido debe tener el archivo HEAD; algunas porcelanas pueden usarlo para adivinar la rama "predeterminada" del repositorio (generalmente master). Es legal si la rama nombrada nombre no existe (todavía). En algunas configuraciones heredadas, es un enlace simbólico en lugar de una referencia simbólica que apunta a la rama actual.

HEAD también puede registrar directamente un commit específico, en lugar de ser una referencia simbólica que apunta a la rama actual. Tal estado a menudo se llama HEAD desconectado. Ver git-checkout(1) para más detalles.

config

Archivo de configuración específico del repositorio. Este archivo se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/config" en su lugar.

config.worktree

Archivo de configuración específico del directorio de trabajo para el directorio de trabajo principal en una configuración de múltiples directorios de trabajo (ver git-worktree(1)).

branches

Una forma obsoleta de almacenar nombres cortos a usar para especificar una URL para git fetch, git pull y git push. Se puede almacenar un archivo como branches/<nombre> y luego nombre se puede dar a estos comandos en lugar del argumento repositorio. Ver la sección REMOTES en git-fetch(1) para más detalles. Este mecanismo es obsoleto y es poco probable que se encuentre en repositorios modernos. Este directorio se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/branches" en su lugar.

Git dejará de leer los remotos de este directorio en Git 3.0.

hooks

Los hooks son scripts de personalización utilizados por varios comandos de Git. Un puñado de hooks de ejemplo se instalan cuando se ejecuta git init, pero todos ellos están deshabilitados por defecto. Para habilitarlos, la sufijo .sample tiene que ser eliminado del nombre del archivo renombrándolo. Lee githooks(5) para más detalles sobre cada hook. Este directorio se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/hooks" en su lugar.

common

Cuando se utilizan múltiples árboles de trabajo, la mayoría de los archivos en $GIT_DIR son por árbol de trabajo con unas pocas excepciones conocidas. Todos los archivos bajo common se compartirán entre todos los árboles de trabajo.

index

El archivo índice actual para el repositorio. Normalmente no se encuentra en un repositorio bare.

sharedindex.<SHA-1>

La parte del índice compartido, a ser referenciada por $GIT_DIR/index y otros archivos temporales de índice. Solo válido en modo de índice dividido.

info

Información adicional sobre el repositorio se registra en este directorio. Este directorio se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/info" en su lugar.

info/refs

Este archivo ayuda a los transportes tontos a descubrir qué referencias están disponibles en este repositorio. Si el repositorio se publica para transportes tontos, este archivo debe ser regenerado por git update-server-info cada vez que se crea o modifica una etiqueta o rama. Esto se hace normalmente desde el hook hooks/update, w
que es ejecutado por el git-receive-pack comando cuando usted git push al repositorio.

info/grafts

Este archivo registra información de ascendencia falsa de las confirmaciones, para fingir que el conjunto de padres que una confirmación tiene es diferente de cómo la confirmación fue realmente creada. Un registro por línea describe una confirmación y sus padres falsos listando sus nombres de objetos hexadecimales de 40 bytes separados por un espacio y terminados por un salto de línea.

Tenga en cuenta que el mecanismo de injertos está obsoleto y puede causar problemas al transferir objetos entre repositorios; vea git-replace(1) para un sistema más flexible y robusto para hacer lo mismo.

info/exclude

Este archivo, por convención entre los Porcelains, almacena la lista de patrones de exclusión. .gitignore es el archivo de exclusión por directorio. git status, git add, git rm y git clean lo miran pero los comandos centrales de Git no lo miran. Vea también: gitignore(5).

info/attributes

Define qué atributos asignar a una ruta, similar a los archivos .gitattributes por directorio. Vea también: gitattributes(5).

info/sparse-checkout

Este archivo almacena patrones de verificación dispersa. Vea también: git-read-tree(1).

remotes

Almacena abreviaturas para URL y nombres de referencias predeterminados para usar al interactuar con repositorios remotos a través de los comandos git fetch, git pull y git push . Vea la sección REMOTES en git-fetch(1) para más detalles. Este mecanismo es antiguo y no es probable que se encuentre en repositorios modernos. Este directorio se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/remotes" en su lugar.

Git dejará de leer los remotos de este directorio en Git 3.0.

logs

Los registros de los cambios realizados en las referencias se almacenan en este directorio. Vea git-update-ref(1) para más información. Este directorio se ignora (excepto logs/HEAD) si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/logs" en su lugar.

logs/refs/heads/nombre

Registra todos los cambios realizados en la punta de la rama llamada nombre.

logs/refs/tags/nombre

Registra todos los cambios realizados en la etiqueta llamada nombre.

shallow

Esto es similar a info/grafts pero es usado internamente y mantenido por el mecanismo de clonación superficial. Vea la opción --depth de git-clone(1) y git-fetch(1). Este archivo se ignora si $GIT_COMMON_DIR está establecido y se usará "$GIT_COMMON_DIR/shallow" en su lugar.

commondir

Si este archivo existe, $GIT_COMMON_DIR (vea git(1)) se establecerá en la ruta especificada en este archivo si no está explícitamente establecido. Si la ruta especificada es relativa, es relativa a $GIT_DIR. El repositorio con commondir está incompleto sin el repositorio al que apunta "commondir".

modules

Contiene los git-repositories de los submódulos.

worktrees

Contiene datos administrativos para los árboles de trabajo vinculados. Cada subdirectorio contiene la parte relacionada con el árbol de trabajo de un árbol de trabajo vinculado. Este directorio se ignora si $GIT_COMMON_DIR está establecido, en cuyo caso se usará "$GIT_COMMON_DIR/worktrees" en su lugar.

worktrees/<id>/gitdir

Un archivo de texto que contiene la ruta absoluta de vuelta al archivo .git que apunta aquí. Esto se usa para verificar si el repositorio vinculado ha sido eliminado manualmente y no hay necesidad de mantener este directorio más. El mtime de este archivo debe actualizarse cada vez que se accede al repositorio vinculado.

worktrees/<id>/locked

Si este archivo existe, el árbol de trabajo vinculado puede estar en un dispositivo portátil y no estar disponible. La presencia de este archivo evita que worktrees/<id> sea podado ya sea automáticamente o manualmente por git worktree prune. El archivo puede contener una cadena que explique por qué el repositorio está bloqueado.

worktrees/<id>/config.worktree

Archivo de configuración específico del directorio de trabajo.

VERSIONES DE FORMATO DE REPOSITORIO DE GIT

Cada repositorio git está marcado con una versión numérica en la clave core.repositoryformatversion de su archivo config . Esta versión especifica las reglas para operar sobre los datos del repositorio en disco. Una implementación de git que no entienda una versión particular anunciada por un repositorio en disco NO DEBE operar en ese repositorio; hacerlo arriesga no solo producir resultados incorrectos, sino realmente perder datos.

Debido a esta regla, los incrementos de versión deben mantenerse al mínimo absoluto. En su lugar, generalmente preferimos estas estrategias:

•incrementar los números de versión de formato de archivos de datos individuales (por ejemplo, índice, archivos de paquete, etc.). Esto restringe las incompatibilidades solo a esos archivos.
•introducir nuevos datos que se degradan con elegancia cuando son usados por clientes más antiguos (por ejemplo, los archivos de mapa de bits de paquete son ignorados por clientes más antiguos, que simplemente no se aprovechan de la optimización que proporcionan).

Un incremento de versión de formato de todo el repositorio solo debe ser parte de un cambio que no pueda ser versionado independientemente. Por ejemplo, si uno cambiara las reglas de alcanzabilidad de los objetos, o las reglas para bloquear referencias, eso requeriría un incremento de la versión de formato del repositorio.

Tenga en cuenta que esto se aplica solo al acceso directo al contenido en disco del repositorio. Un cliente más antiguo que solo entienda el formato 0 aún puede conectarse vía git:// a un repositorio que usa el formato 1, siempre que el proceso del servidor entienda el formato 1.

La estrategia preferida para implementar un incremento de versión (ya sea de todo el repositorio o de un solo archivo) es enseñar a git a leer el nuevo formato, y permitir escribir el nuevo formato con un interruptor de configuración o una opción de línea de comando (para experimentación o para aquellos a quienes no les importa la compatibilidad con versiones anteriores de git). Luego, después de un largo período para que la capacidad de lectura se vuelva común, podemos cambiar a escribir el nuevo formato por defecto.

Las versiones de formato actualmente definidas son:

Versión 0

Este es el formato definido por la versión inicial de git, incluyendo pero no limitado al formato del directorio del repositorio, el archivo de configuración del repositorio, y el almacenamiento de objetos y referencias. Especificar el comportamiento completo de git está fuera del alcance de este documento.

Versión 1

Este formato es idéntico a la versión 0, con las siguientes excepciones:

1.Al leer la variable core.repositoryformatversion , una implementación de git que soporte la versión 1 DEBE también leer cualquier clave de configuración encontrada en la sección extensions del archivo de configuración.
2.Si un repositorio de versión 1 especifica cualquier clave extensions.* que el git en ejecución no ha implementado, la operación NO DEBE proceder. De manera similar, si el valor de cualquier clave conocida no es entendido por la implementación, la operación NO DEBE proceder.

Tenga en cuenta que si no se especifican extensiones en el archivo de configuración, entonces core.repositoryformatversion DEBERÍA establecerse en 0 (establecerlo en 1 no proporciona ningún beneficio, y hace que el repositorio sea incompatible con implementaciones más antiguas de git).

Las extensiones definidas se dan en la sección extensions.* de git-config(1). Cualquier implementación que desee definir una nueva extensión debe hacer una nota allí, para reclamar el nombre.
