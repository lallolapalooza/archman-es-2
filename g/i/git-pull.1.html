Integra cambios de un repositorio remoto en la rama

Primero, git pull ejecuta git fetch con los mismos argumentos (excluyendo las opciones de fusión) para obtener las ramas remotas. Luego decide qué rama remota integrar: si ejecutas git pull sin argumentos, por defecto se usa la rama ascendente (upstream) de la rama actual. Después integra esa rama en la rama

1.git pull --ff-only solo hará actualizaciones "fast-forward": falla si tu rama local ha divergido de la rama remota. Esta es la opción por

2.git pull --rebase ejecuta git rebas

3.git pull --no-rebase ejecuta git merge

4.git pull --squash ejecuta git merge --squas

También puedes establecer las opciones de configuración pull.rebase, pull.squash, o pull.ff con tu comportamiento

Si hay un conflicto de fusión durante la fusión o el rebase que no quieres manejar, puedes abortarlo de forma segura con git merge --abort o git --rebase abo

<refspec>

Especifica qué refs recuperar y qué refs locales actualizar. Cuando no aparecen <refspec>s en la línea de comandos, se leen las refs a recuperar de las variables remote.<repositorio>.fetch en su lugar (ver la sección "RAMAS DE SEGUIMIENTO REMOTO CONFIGURADAS" en git-fetch(1)).

El formato de un parámetro <refspec> es un signo más opcional +, seguido de la fuente <src>, seguido de dos puntos :, seguido del destino <dst>. Los dos puntos se pueden omitir cuando <dst> está vacío. <src> es típicamente una ref, o un patrón glob con un único * que se utiliza para hacer coincidir un conjunto de refs, pero también puede ser un nombre de objeto hexadecimal completamente escrito.

Un <refspec> puede contener un * en su <src> para indicar una coincidencia de patrón simple. Dicho refspec funciona como un glob que coincide con cualquier ref con el patrón. Un patrón <refspec> debe tener uno y solo un * tanto en el <src> como en el <dst>. Mapeará las refs al destino reemplazando el * con el contenido coincidente de la fuente.

Si un refspec va precedido de ^, se interpretará como un refspec negativo. En lugar de especificar qué refs recuperar o qué refs locales actualizar, dicho refspec especificará refs a excluir. Una ref se considerará coincidente si coincide al menos con un refspec positivo y no coincide con ningún refspec negativo. Los refspecs negativos pueden ser útiles para restringir el alcance de un refspec de patrón para que no incluya refs específicas. Los refspecs negativos pueden ser refspecs de patrón. Sin embargo, solo pueden contener un <src> y no especifican un <dst>. Tampoco se admiten nombres de objeto hexadecimal completamente escritos.

tag <tag> significa lo mismo que refs/tags/<tag>:refs/tags/<tag>; solicita la recuperación de todo hasta la etiqueta dada.

Se recupera la ref remota que coincide con <src>, y si <dst> no es una cadena vacía, se intenta actualizar la ref local que coincide con ella.

Si esa actualización está permitida sin --force depende del espacio de nombres de la ref al que se recupera, del tipo de objeto que se recupera y de si la actualización se considera un avance rápido. En general, las mismas reglas se aplican para la recuperación que para el envío, ver la sección <refspec>... de git-push(1) para saber cuáles son. Las excepciones a esas reglas particulares de git fetch se anotan abajo.

Hasta la versión 2.20 de Git, y a diferencia de cuando se envía con git-push(1), cualquier actualización de refs/tags/* se aceptaba sin + en el refspec (o --force). Al recuperar, considerábamos promiscuamente todas las actualizaciones de etiquetas de un remoto como recuperaciones forzadas. Desde la versión 2.20 de Git, la recuperación para actualizar refs/tags/* funciona de la misma manera que al enviar. Es decir, cualquier actualización será rechazada sin + en el refspec (o --force).

A diferencia de cuando se envía con git-push(1), cualquier actualización fuera de refs/{tags,heads}/* se aceptará sin + en el refspec (o --force), ya sea cambiando, por ejemplo, un objeto de árbol por uno de bloque, o un commit por otro commit que no tenga el commit anterior como ancestro, etc.

A diferencia de cuando se envía con git-push(1), no existe configuración que modifique estas reglas, ni nada parecido a un hook pre-fetch análogo al hook pre-receive.

Al igual que al enviar con git-push(1), todas las reglas descritas anteriormente sobre lo que no está permitido como actualización se pueden anular añadiendo un signo + opcional al principio de un refspec (o usando la opción de línea de comandos --force). La única excepción es que ninguna cantidad de forzado hará que el espacio de nombres refs/heads/* acepte un objeto que no sea un commit.


Nota
Cuando la rama remota que deseas recuperar se sabe que se rebobina y se rehace regularmente, se espera que su nueva punta no sea descendiente de su punta anterior (tal como está almacenada en tu rama de seguimiento remoto la última vez que recuperaste). Querrás usar el signo + para indicar que se necesitarán actualizaciones no rápidas para dichas ramas. No hay forma de determinar o declarar que una rama estará disponible en un repositorio con este comportamiento; el usuario que la extrae simplemente debe saber que este es el patrón de uso esperado para una rama.

Nota
Existe una diferencia entre listar múltiples <refspec> directamente en la línea de comandos de git pull y tener múltiples entradas remote.<repositorio>.fetch en tu configuración para un <repositorio> y ejecutar un comando git pull sin ningún parámetro explícito de <refspec>. Los <refspec> listados explícitamente en la línea de comandos siempre se fusionan en la rama actual después de la recuperación. En otras palabras, si listas más de un ref remoto, git pull creará una fusión Octopus. Por otro lado, si no listas ningún parámetro explícito de <refspec> en la línea de comandos, git pull recuperará todos los <refspec> que encuentre en la configuración remote.<repositorio>.fetch y fusionará solo el primer <refspec> encontrado en la rama actual. Esto se debe a que realizar una fusión Octopus a partir de refs remotas rara vez se hace, mientras que llevar un registro de múltiples puntas remotas de una vez recuperando más de una suele ser útil.

En general, las URLs contienen información sobre el protocolo de transporte, la dirección del servidor remoto y la ruta al repositorio. Dependiendo del protocolo de transporte, parte de esta información puede estar ausente.

resolve

Solo puede resolver dos cabezas (es decir, la rama actual y otra rama de la que extrajo) utilizando un algoritmo de fusión de 3 vías. Intenta detectar cuidadosamente las ambigüedades de fusión entrecruzada. No maneja renombramientos.

octopus

Resuelve casos con más de dos cabezas, pero se niega a realizar una fusión compleja que requiera resolución manual. Está diseñado principalmente para agrupar cabezas de ramas temáticas. Esta es la estrategia de fusión predeterminada al extraer o fusionar más de una rama.

ours

Resuelve cualquier número de cabezas, pero el árbol resultante de la fusión es siempre el de la cabeza de la rama actual, ignorando efectivamente todos los cambios de todas las demás ramas. Está diseñado para suplantar historiales de desarrollo antiguos de ramas laterales. Tenga en cuenta que esto es diferente de la opción -Xours para la estrategia de fusión ort.

subtree

Esta es una estrategia ort modificada. Al fusionar árboles A y B, si B corresponde a un subárbol de A, B se ajusta primero para que coincida con la estructura del árbol de A, en lugar de leer los árboles al mismo nivel. Este ajuste también se realiza en el árbol antecesor común.

Con las estrategias que utilizan fusión de 3 vías (incluida la predeterminada, ort), si se realiza un cambio en ambas ramas, pero luego se revierte en una de las ramas, ese cambio estará presente en el resultado fusionado; a algunas personas les resulta confuso este comportamiento. Ocurre porque solo se consideran las cabezas y la base de fusión al realizar una fusión, no los commits individuales. Por lo tanto, el algoritmo de fusión considera el cambio revertido como ningún cambio y sustituye la versión modificada en su lugar.

COMPORTAMIENTO PREDETERMINADO

A menudo, las personas usan git pull sin dar ningún parámetro. Tradicionalmente, esto ha sido equivalente a decir git pull origin. Sin embargo, cuando la configuración branch.<nombre>.remote está presente mientras se está en la rama <nombre>, ese valor se usa en lugar de origin.

Para determinar qué URL se debe usar para extraer, se consulta el valor de la configuración remote.<origin>.url y, si no existe tal variable, se utiliza el valor de la línea URL: en $GIT_DIR/remotes/<origin>.

Para determinar qué ramas remotas extraer (y opcionalmente almacenar en las ramas de seguimiento remoto) cuando se ejecuta el comando sin ningún refspec en la línea de comandos, se consultan los valores de la variable de configuración remote.<origin>.fetch y, si no hay ninguno, se consulta $GIT_DIR/remotes/<origin> y se utilizan sus líneas Pull:. Además de los formatos de refspec descritos en la sección OPCIONES, puede tener un refspec de globbing que se vea así:

refs/heads/*:refs/remotes/origin/*

Un refspec de globbing debe tener una RHS no vacía (es decir, debe almacenar lo que se extrajo en ramas de seguimiento remoto), y su LHS y RHS deben terminar en /*. Lo anterior especifica que todas las ramas remotas se rastrean utilizando ramas de seguimiento remoto en la jerarquía refs/remotes/origin/ bajo el mismo nombre.

La regla para determinar qué rama remota fusionar después de extraer es un poco complicada, para no romper la compatibilidad hacia atrás.

Si se especificaron refspecs explícitos en la línea de comandos de git pull, todos se fusionan.

Cuando no se especificó ningún refspec en la línea de comandos, git pull utiliza el refspec de la configuración o $GIT_DIR/remotes/<origin>. En tales casos, se aplican las siguientes reglas:

1.Si existe la configuración branch.<nombre>.merge para la rama actual <nombre>, ese es el nombre de la rama en el sitio remoto que se fusiona.
2.Si el refspec es de tipo globbing, no se fusiona nada.
3.De lo contrario, se fusiona la rama remota del primer refspec.

EJEMPLOS

•Actualiza las ramas de seguimiento remoto para el repositorio del que clonaste, y luego fusiona una de ellas en tu rama actual: 
$ git pull
$ git pull origin

Normalmente, la rama que se fusiona es la HEAD del repositorio remoto, pero la elección está determinada por las opciones branch.<nombre>.remote y branch.<nombre>.merge; consulte git-config(1) para obtener detalles.

•Fusiona la rama remota next en la rama actual: 
$ git pull origin next

Esto deja una copia temporal de next en FETCH_HEAD y actualiza la rama de seguimiento remoto origin/next. Lo mismo se puede hacer invocando fetch y merge:

$ git fetch origin
$ git merge origin/next

Si intentó una extracción que resultó en conflictos complejos y quisiera comenzar de nuevo, puede recuperarse con git reset.

SEGURIDAD

Los protocolos de extracción (fetch) y envío (push) no están diseñados para evitar que un lado robe datos del otro repositorio que no se pretendía compartir. Si tiene datos privados que necesita proteger de un par malicioso, su mejor opción es almacenarlos en otro repositorio. Esto se aplica tanto a clientes como a servidores. En particular, los espacios de nombres en un servidor no son efectivos para el control de acceso de lectura; solo debe otorgar acceso de lectura a un espacio de nombres a clientes en los que confiaría con acceso de lectura a todo el repositorio.

Los vectores de ataque conocidos son los siguientes:

1.La víctima envía líneas "have" anunciando los IDs de los objetos que tiene y que no están explícitamente destinados a ser compartidos, pero que pueden usarse para optimizar la transferencia si el par también los tiene. El atacante elige un objeto X para robar y envía una ref a X, pero no se le exige enviar el contenido de X porque la víctima ya lo tiene. Ahora la víctima cree que el atacante tiene X, y más tarde le envía el contenido de X al atacante. (Este ataque es más directo para que un cliente lo realice en un servidor, creando una ref a X en el espacio de nombres al que el cliente tiene acceso y luego extrayéndola. La forma más probable para que un servidor lo realice en un cliente es "fusionar" X en una rama pública y esperar que el usuario realice trabajo adicional en esta rama y la envíe de vuelta al servidor sin notar la fusión).
2.Como en el punto 1, el atacante elige un objeto X para robar. La víctima envía un objeto Y que el atacante ya tiene, y el atacante afirma falsamente tener X y no Y, por lo que la víctima envía Y como un delta contra X. El delta revela al atacante regiones de X que son similares a Y.

ERRORES

El uso de --recurse-submodules solo puede extraer nuevos commits en submódulos ya extraídos en este momento. Cuando, por ejemplo, el upstream agregó un nuevo submódulo en los commits recién extraídos del superproyecto, el submódulo en sí no se puede extraer, lo que imposibilita extraer ese submódulo más tarde sin tener que realizar una extracción nuevamente. Se espera que esto se corrija en una futura versión de Git.
