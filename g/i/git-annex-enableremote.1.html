NOMBRE

git-annex-enableremote - habilita git-annex para usar un remoto

SINOPSIS

git annex enableremote nombre|uuid|desc [param=valor ...]

DESCRIPCIÓN

Habilita el uso de un remoto existente en el repositorio actual, que fue configurado previamente por git annex initremote ejecutado en otro clon del repositorio.

Al habilitar un remoto, especifique el mismo nombre utilizado cuando se configuró originalmente ese remoto con git annex initremote. Ejecute git annex enableremote sin ningún nombre para obtener una lista de nombres de remotos. O puede especificar el uuid o la descripción del remoto.

Algunos tipos de remotos especiales necesitan que se especifiquen parámetros cada vez que se habilitan. Por ejemplo, el remoto especial de directorio requiere un parámetro directory= cada vez. El comando le pedirá los parámetros requeridos que falten.

Este comando también se puede usar para modificar la configuración de un remoto especial existente, especificando nuevos valores para los parámetros que generalmente se establecen al usar initremote. (Sin embargo, algunas configuraciones, como el esquema de cifrado, no se pueden cambiar una vez que se ha creado un remoto especial).

Las claves GPG con las que se cifra un remoto especial cifrado pueden cambiarse utilizando los parámetros keyid+= y keyid-=. Estos añaden y eliminan respectivamente claves de la lista. Sin embargo, tenga en cuenta que eliminar una clave NO necesariamente evita que el propietario de la clave acceda a los datos en el remoto especial cifrado (lo cual es imposible por diseño, a menos que se elimine el remoto).

Un caso de uso de keyid-= es reemplazar una clave revocada con una nueva clave:


git annex enableremote mys3 keyid-=clave_revocada keyid+=clave_nueva

Además, tenga en cuenta que para los remotos especiales cifrados que utilizan cifrado de clave pública simple (encryption=pubkey), añadir o eliminar una clave NO tiene efecto en los archivos que ya se han copiado al remoto. Por lo tanto, el uso de keyid+= y keyid-= con dichos remotos debe hacerse con cuidado y tiene poco sentido, excepto en casos como el ejemplo de la clave revocada anterior.

Si se cansa de habilitar manualmente un remoto especial en cada nuevo clon, puede pasar "autoenable=true". Entonces, cuando se ejecute git-annex-init(1) en un nuevo clon, intentará habilitar el remoto especial. Por supuesto, esto funciona mejor cuando el remoto especial no necesita nada especial para habilitarse.

(Este comando también se puede usar para habilitar un remoto git que git-annex ha descubierto que no funcionaba antes y renunció a usar, estableciendo remote.<nombre>.annex-ignore.)

OPCIONES

--with-url
Esto configura el remoto con una URL "annex::", que permite a git enviar y recibir de él, utilizando git-remote-annex.
--json
Habilita la salida JSON. Esto está destinado a ser analizado por programas que utilizan git-annex.
--json-error-messages
Los mensajes que normalmente se enviarían a la salida de error estándar se incluyen en el JSON.
Ademá, se pueden utilizar las opciones-comunes-de-git-annex(1).
