DESCRIPCIÓ

N

Cada repositorio tiene una configuración de contenido preferido, que especifica el contenido que el repositorio desea tener presente. Estas configuraciones se pueden definir usando git annex vicfg o git annex wanted. Se usan por la opción --auto, por git annex sync --content, por clústeres y por el asistente de

git-annex.

Mientras que el contenido preferido expresa una preferencia, puede ser anulado simplemente usando git annex drop. Por otro lado, las configuraciones de contenido requerido se aplican; git annex drop se negará a eliminar un archivo si hacerlo violaría sus configuraciones de contenido requerido. El contenido requerido de un repositorio se puede configurar usando git annex vicfg o git annex

requ
ired.

SINTAXI

S

Las expresiones de contenido preferido usan una sintaxis similar a la de git-annex-matching-options(1), sin los guiones. Por

ejemplo:


exclude=archive/* and (include=*.mp3 or smallerthan=1mb

)

La idea es que escribas una expresión contra la cual se comparan los archivos. Si un archivo coincide, el repositorio desea almacenar su contenido. Si no coincide, el repositorio desea eliminar su contenido (si hay suficientes copias en otros lugares para permitir eliminarlo)

.

Una expresión de contenido preferi

do vacía se trata igual que c
ontenido preferido no configurado.

Coincide con archivos a incluir, o

Mientras que las opciones de línea de comandos --include=glob y --exclude=glob coinciden con archivos relativos al directorio actual, las expresiones de contenido preferido coinciden con archivos relativos a la raíz del repositorio
git.
Un glob es algo como foo.* o b?r. Los globs también pueden contener clases de caracteres, como foo[Bb]ar, así como clases de caracteres POSIX adicionales como [[:space:]]. Lo cual es útil, ya que un glob en una expresión de contenido preferido no puede contener espacios. Consulta la página man glob(7) para más información sobre
globs.
Por ejemplo, supón que pones archivos en directorios de archivo cuando terminas con ellos. Entonces podrías configurar tu portátil para preferir no conservar esos archivos, así: exclude=*/archiv
e/*
Cuando un subdirectorio se está exportando o importando a un remoto especial (consulta git-annex-export(1) y git-annex-import(1)), estos coinciden relativos a la raíz del
subdirectorio.
Ten en cuenta que, cuando un comando se ejecuta con la opción --all, o en un repositorio desnudo, no hay nombre de archivo asociado con un objeto annexed, y por lo tanto "include=" y "exclude=" no
coincidirán.

Coincide solo con archivos que git-annex cree que tienen el número especificado de copias, o más. Ten en cuenta que no verifica remotos para confirmar que las copias todavía
existen.
Para decidir si el contenido debe ser eliminado, git-annex evalúa la expresión de contenido preferido bajo la suposición de que el contenido ha *ya* sido eliminado. Si el contenido no se desearía entonces, la eliminación puede realizarse. Así, por ejemplo, copies=2 en una expresión de contenido preferido permite que el contenido sea eliminado solo cuando hay actualmente 3 copias de él, incluyendo el repositorio del cual se está eliminando. Esto es diferente a ejecutar git annex drop --copies=2, que eliminará archivos que actualmente tienen 2
copias.

standa
rd
git-annex viene con algunas expresiones de contenido preferido integradas, que pueden usarse con repositorios que están en algunos grupos estándar como "client" y
"transfer".
Cuando un repositorio está exactamente en uno de esos grupos, puedes usar la palabra clave "standard" en su expresión de contenido preferido, para coincidir con cualquier contenido con el que coincida la expresión del
grupo.
La mayoría de las veces, toda la expresión de contenido preferido es simplemente "standard". Pero puedes hacer cosas más complicadas, por ejemplo: standard or include=otherdi
r/*
groupwant
ed
La palabra clave "groupwanted" puede usarse para referirse a una expresión de contenido preferido que está asociada con un grupo, siempre que haya exactamente una expresión así entre los grupos en los que está un repositorio. Esto es como la palabra clave "standard", pero puedes configurar las expresiones de contenido preferido usando git annex group
wanted.
Al escribir una expresión de contenido preferido groupwanted, puedes usar todas las palabras clave documentadas aquí, incluyendo "standard". (Pero no "groupwanted".
)
Por ejemplo, para hacer una variante de la expresión de contenido preferido estándar de cliente que no quiere archivos en el directorio "out", podrías ejecutar: git annex groupwanted client "standard and
exclude=out/*"
Luego, los repositorios que están en el grupo client y tienen su expresión de contenido preferido configurada a "groupwanted" usarán esa, mientras que otros repositorios client que tienen su expresión de contenido preferido configurada a "standard" usarán la expresión
estándar.
O, podrías hacer un nuevo grupo, con tu propia expresión de contenido preferido personalizada ajustada a tus necesidades, y cada repositorio que pongas en este grupo y hagas que su contenido preferido sea "groupwanted" la
usará.
Por ejemplo, el grupo archive solo quiere archivar 1 copia de cada archivo, distribuida entre todos los repositorios del grupo. Así es como configurar un grupo llamado redundantarchive, que en cambio quiere contener 3 copias de cada
archivo:

git annex groupwanted redundantarchive "not (copies=redundantarchive:3)"
for repo in foo bar baz; do
git annex group $repo redundantarchive
git annex wanted $repo groupwanted

Coincide solo con claves que git annex unused ha determinado que están sin
usar.
Esto está relacionado con la opción --unused. Sin embargo, poner unused en una expresión de contenido preferido no hace que git-annex considere esas claves sin usar. Así que cuando git-annex solo está verificando expresiones de contenido preferido contra archivos en el repositorio (que obviamente están en uso), unused en una expresión de contenido preferido no coincidirá con
nada.
Entonces, ¿cuándo es útil en una expresión de contenido
preferido?
Usando git annex sync --content --all operará con todos los archivos, incluyendo los sin usar, y tomará unused en las expresiones de contenido preferido en
cuenta.
El asistente de git-annex escanea periódicamente archivos sin usar, y los mueve a algún repositorio cuya expresión de contenido preferido diga que los quiere. (O, si annex.expireunused está configurado, puede simplemente eliminarlos.
)
balanced=groupname[:number|:
lackingcopies]
Hace que el contenido esté equilibrado uniformemente entre los repositorios del
grupo.
El número es el número de repositorios del grupo que querrán cada archivo. Cuando no se especifica, el valor por defecto es
1.
Por ejemplo, "balanced=backup:2", cuando hay 3 miembros del grupo backup, hará que cada repositorio de backup quiera 2/3 partes de los
archivos.
Usar "lackingcopies" en lugar de un número hace que cada archivo se equilibre entre tantos repositorios del grupo como sean necesarios para satisfacer su configuración numcopies. Por ejemplo, "balanced=backup:lackingcopies", cuando numcopies es 3 y hay 1 otra copia, se comportará igual que "balanced=backup:
2".
Para que el equilibrio funcione, cada repositorio del grupo debe tener su contenido preferido configurado a la misma expresión. Usar groupwanted es una buena manera de
hacerlo.
Los tamaños de los archivos no se tienen en cuenta, así que es posible que un repositorio obtenga archivos más grandes de lo habitual y por lo tanto se llene antes que los otros repositorios. Pero los archivos solo son deseados por repositorios que tienen suficiente espacio libre para contenerlos. Así que una vez que un repositorio está lleno, los repositorios restantes tendrán cualquier archivo adicional equilibrado entre ellos. Para que git-annex sepa cuándo un repositorio está lleno, debes usar git-annex-maxsize(1) para especificar el tamaño de cada repositorio en el
grupo.
Esto generalmente evita mover archivos entre repositorios, incluso si eso significa que las cosas no están óptimamente equilibradas. Algunas de las formas en que puede desequilibrarse incluyen agregar un nuevo repositorio al grupo, o que un archivo se copie a más repositorios del grupo que el número especificado, o que algunos de los repositorios se
llenen.
Ejecutar comandos de git-annex con la opción --rebalance hará que esta expresión en cambio se comporte como la expresión fullybalanced, lo que hará que los repositorios quieran mover archivos alrededor según sea necesario para lograr un equilibrio
completo.
Usar esto en una expresión de contenido preferido hace que git-annex necesite hacer algo de trabajo adicional para llevar la cuenta de cuán llenos están los repositorios. Generalmente eso no afectará mucho el rendimiento. Sin embargo, la primera vez que git-annex procesa esta expresión en un repositorio git dado, necesitará calcular los tamaños de todos los repositorios, lo cual puede ser lento cuando hay muchos archivos. Cuando esto hace que git-annex haga mucho trabajo, mostrará "(calculating repository sizes)
".
Ten en cuenta que not balanced no es algo razonable de usar en una expresión de contenido preferido por las mismas razones que not pres
ent.

Por ejemplo, fullybalanced=foo:3, cuando el grupo foo tiene 5 repositorios, dos al 50% llenos y tres al 99% llenos, hará que algo de contenido se mueva de los repositorios llenos a los otros. Mover contenido así es costoso, pero permite que nuevos archivos continúen almacenándose en el número especificado de

sizebalanced=groupname[:number|:
lackingcopies]
Distribuye contenido entre los repositorios del grupo, manteniendo los repositorios proporcionalmente
llenos.
El número es el número de repositorios del grupo que querrán cada archivo. Cuando no se especifica, el valor por defecto es
1.
Para que esto funcione, debes usar git-annex-maxsize(1) para especificar el tamaño de cada repositorio en el grupo. Cuando el maxsize de un repositorio no ha sido especificado, no querrá ningún
archivo.
Por ejemplo, si un repositorio en el grupo tiene un tamaño máximo de 100 gb con 60 gb usados, y otro tiene un tamaño máximo de 50 gb con 25 gb usados, el más pequeño querrá archivos (que quepan en él), y el más grande no querrá ningún archivo (que quepa en el más pequeño) hasta que el más pequeño esté igualmente
lleno.
Ten en cuenta que, una vez que un repositorio contiene un archivo, continuará queriéndolo, incluso si está más lleno que otros repositorios. Esto es para evitar el movimiento innecesario de
archivos.
Es más probable que se desequilibre que la expresión balanced=, porque git-annex no siempre tiene un conocimiento consistente de cuán llenos están los repositorios. Considera por ejemplo si un portátil y un escritorio están cada uno enviando un nuevo archivo al grupo. Ambos escogerán el repositorio que esté menos lleno, pero eso significa que ambos archivos van al mismo repositorio, cuando una mejor solución podría haber sido enviar el archivo más pequeño a un repositorio diferente. Al usar balanced= en la misma situación, es menos probable que un repositorio quiera ambos
archivos.

PRUEBA

S

Para comprobar en la línea de comandos qué archivos coinciden con la configuración de contenido preferido de un repositorio, puedes usar las opciones --want-get y

--want-drop.

Por ejemplo, git annex find --want-get --not --in . encontrará todos los archivos que git annex get --auto querrá obtener, y git annex find --want-drop --in . encontrará todos los archivos que git annex drop --auto querrá

descartar.

La opción --explain se puede usar para entender por qué una expresión compleja de contenido preferido coincide o no coincide. La expresión se mostrará, con cada término seguido de "[TRUE]" o "[FALSE]" para indicar el valor. Los términos irrelevantes se omitirán de la explicación, por ejemplo "exclude=* and copies=1" se mostrará como "exclu

de=*[F
ALSE]"
