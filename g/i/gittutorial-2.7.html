GITTUTORIAL-2(7) Manual de Git GITTUTORIAL-2(7)

NOMBRE

gittutorial-2 - Una introducción tutorial a Git: parte dos

SINOPSIS

git *

DESCRIPCIÓN

Deberías haber trabajado a través de gittutorial(7) antes de leer este tutorial.

El objetivo de este tutorial es introducir dos piezas fundamentales de la arquitectura de Git: la base de datos de objetos y el archivo índice, y proporcionar al lector todo lo necesario para entender el resto de la documentación de Git.

LA BASE DE DATOS DE OBJETOS DE GIT

Comencemos un nuevo proyecto y creemos una pequeña cantidad de historial:

$ mkdir test-project
$ cd test-project
$ git init
Initialized empty Git repository in .git/
$ echo 'hello world' > file.txt
$ git add .
$ git commit -a -m "initial commit"
[master (root-commit) 54196cc] initial commit
 1 file changed, 1 insertion(+)
 create mode 100644 file.txt
$ echo 'hello world!' >file.txt
$ git commit -a -m "add emphasis"
[master c4d59f3] add emphasis
 1 file changed, 1 insertion(+), 1 deletion(-)

¿Cuáles son los 7 dígitos hexadecimales con los que Git respondió al commit?

Vimos en la parte uno del tutorial que los commits tienen nombres como este. Resulta que cada objeto en el historial de Git se almacena bajo un nombre hexadecimal de 40 dígitos. Ese nombre es el hash SHA-1 del contenido del objeto; entre otras cosas, esto asegura que Git nunca almacenará los mismos datos dos veces (ya que los datos idénticos reciben un nombre SHA-1 idéntico), y que el contenido de un objeto de Git nunca cambiará (ya que eso cambiaría el nombre del objeto también). Las cadenas hexadecimales de 7 caracteres aquí son simplemente la abreviatura de tales cadenas de 40 caracteres. Las abreviaturas pueden usarse en todas partes donde se puedan usar las cadenas de 40 caracteres, siempre que sean inequívocas.

Se espera que el contenido del objeto commit que creaste siguiendo el ejemplo anterior genere un hash SHA-1 diferente al mostrado arriba, porque el objeto commit registra el momento en que fue creado y el nombre de la persona que realizó el commit.

Podemos preguntarle a Git sobre este objeto en particular con el comando cat-file . No copies los 40 dígitos hexadecimales de este ejemplo, sino usa los de tu propia versión. Ten en cuenta que puedes abreviarlo a solo unos pocos caracteres para ahorrarte escribir los 40 dígitos hexadecimales:

$ git cat-file -t 54196cc2
commit
$ git cat-file commit 54196cc2
tree 92b8b694ffb1675e5975148e1121810081dbdffe
author J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
committer J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
initial commit

Un árbol (tree) puede referirse a uno o más objetos "blob", cada uno correspondiente a un archivo. Además, un árbol también puede referirse a otros objetos árbol, creando así una jerarquía de directorios. Puedes examinar el contenido de cualquier árbol usando ls-tree (recuerda que una porción inicial lo suficientemente larga del SHA-1 también funcionará):

$ git ls-tree 92b8b694
100644 blob 3b18e512dba79e4c8300dd08aeb37f8e728b8dad    file.txt

Así vemos que este árbol tiene un archivo en él. El hash SHA-1 es una referencia a los datos de ese archivo:

$ git cat-file -t 3b18e512
blob

Un "blob" es simplemente datos de archivo, que también podemos examinar con cat-file:

$ git cat-file blob 3b18e512
hello world

Ten en cuenta que estos son los datos antiguos del archivo; por lo tanto, el objeto que Git nombró en su respuesta al árbol inicial era un árbol con una instantánea del estado del directorio que fue registrado por el primer commit.

Todos estos objetos se almacenan bajo sus nombres SHA-1 dentro del directorio de Git:

$ find .git/objects/
.git/objects/
.git/objects/pack
.git/objects/info
.git/objects/3b
.git/objects/3b/18e512dba79e4c8300dd08aeb37f8e728b8dad
.git/objects/92
.git/objects/92/b8b694ffb1675e5975148e1121810081dbdffe
.git/objects/54
.git/objects/54/196cc2703dc165cbd373a65a4dcf22d50ae7f7
.git/objects/a0
.git/objects/a0/423896973644771497bdc03eb99d5281615b51
.git/objects/d0
.git/objects/d0/492b368b66bdabf2ac1fd8c92b39d3db916e59
.git/objects/c4
.git/objects/c4/d59f390b9cfd4318117afde11d601c1085f241

y el contenido de estos archivos es solo los datos comprimidos más un encabezado que identifica su longitud y su tipo. El tipo es un blob, un árbol, un commit o una etiqueta (tag).

El commit más fácil de encontrar es el commit HEAD, que podemos encontrar desde .git/HEAD:

$ cat .git/HEAD
ref: refs/heads/master

Como puedes ver, esto nos dice en qué rama estamos actualmente, y nos lo dice nombrando un archivo bajo el directorio .git, el cual contiene un nombre SHA-1 que se refiere a un objeto commit, el cual podemos examinar con cat-file:

$ cat .git/refs/heads/master
c4d59f390b9cfd4318117afde11d601c1085f241
$ git cat-file -t c4d59f39
commit
$ git cat-file commit c4d59f39
tree d0492b368b66bdabf2ac1fd8c92b39d3db916e59
parent 54196cc2703dc165cbd373a65a4dcf22d50ae7f7
author J. Bruce Fields <bfields@puzzle.fieldses.org> 1143418702 -0500
committer J. Bruce Fields <bfields@puzzle.fieldses.org> 1143418702 -0500
add emphasis

El objeto "tree" aquí se refiere al nuevo estado del árbol:

$ git ls-tree d0492b36
100644 blob a0423896973644771497bdc03eb99d5281615b51    file.txt
$ git cat-file blob a0423896
hello world!

y el objeto "parent" se refiere al commit anterior:

$ git cat-file commit 54196cc2
tree 92b8b694ffb1675e5975148e1121810081dbdffe
author J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
committer J. Bruce Fields <bfields@puzzle.fieldses.org> 1143414668 -0500
initial commit

El objeto árbol es el árbol que examinamos primero, y este commit es inusual en que carece de cualquier padre.

La mayoría de los commits tienen solo un padre, pero también es común que un commit tenga múltiples padres. En ese caso, el commit representa una fusión (merge), con las referencias a los padres apuntando a las cabeceras de las ramas fusionadas.

Además de blobs, árboles y commits, el único tipo restante de objeto es una "etiqueta" (tag), la cual no discutiremos aquí; consulta git-tag(1) para más detalles.

Así que ahora sabemos cómo Git usa la base de datos de objetos para representar el historial de un proyecto:

•Los objetos "commit" se refieren a objetos "tree" que representan la instantánea de un árbol de directorios en un punto particular del historial, y se refieren a commits "padre" para mostrar cómo están conectados en el historial del proyecto.
•Los objetos "tree" representan el estado de un directorio único, asociando nombres de directorio a objetos "blob" que contienen datos de archivos y objetos "tree" que contienen información de subdirectorios.
•Los objetos "blob" contienen datos de archivos sin ninguna otra estructura.
•Las referencias a objetos commit en la cabecera de cada rama se almacenan en archivos bajo .git/refs/heads/.
•El nombre de la rama actual se almacena en .git/HEAD.

Ten en cuenta, por cierto, que muchos comandos toman un árbol como argumento. Pero como podemos ver arriba, un árbol puede referenciarse de muchas maneras diferentes: por el nombre SHA-1 de ese árbol, por el nombre de un commit que se refiere al árbol, por el nombre de una rama cuya cabecera se refiere a ese árbol, etc.—y la mayoría de tales comandos pueden aceptar cualquiera de estos nombres.

En las sinopsis de comandos, la palabra "tree-ish" se usa a veces para designar tal argumento.

EL ARCHIVO ÍNDICE

La herramienta principal que hemos estado usando para crear commits es git-commit -a, la cual crea un commit incluyendo cada cambio que has hecho en tu árbol de trabajo. Pero, ¿qué pasa si quieres hacer commit de cambios solo en ciertos archivos? ¿O solo de ciertos cambios en ciertos archivos?

Si miramos la manera en que se crean los commits internamente, veremos que hay formas más flexibles de crear commits.

Continuando con nuestro test-project, modifiquemos file.txt de nuevo:

$ echo "hello world, again" >>file.txt

pero esta vez, en lugar de hacer el commit inmediatamente, tomemos un paso intermedio y pidamos diffs por el camino para llevar un registro de lo que está pasando:

$




git diff








NAME


git-diff - show changes between commits, commit and working tree, etc






SYNOPSIS


git diff [options] [pathspec…]


git diff [options] <commit> [<commit> [<path>…]]


git diff [<commit>…] -- [pathspec…]


git diff --cached [commit…] -- [pathspec…]


git diff --check [commit…] -- [pathspec…]






DESCRIPTION


This command shows the differences between the commit histories, the
    index, and the working tree.


It can be used in several ways:


    
    
  • git diff: Without any options, show the differences
        between the index and the working tree.
    • 
    
  • git diff --index: Show the differences between the
        index and the last commit.
    • 
    
  • git diff HEAD: Show the differences between the
        working tree and the last commit.
    • 
    
  • git diff <commit>: Show the differences between
        the named commit and the working tree.
    • 
    
  • git diff <commit> <commit>: Show the
        differences between the two named commits.
    • 
    
  • git diff --cached <commit>: Show the
        differences between the index and the named commit.
    • 
    
  • git diff --cached: Show the differences between
        the index and the last commit.
    • 



The output format is a patch, a list of differences between two
    files.


When comparing two branches, the default behavior is to show the
    differences between the tip of the current branch and the tip of the other
    branch. When comparing a branch with itself, nothing is shown.


The command can also be used to show the differences between two
    arbitrary files in the working tree.


The command can be used to show the differences between two arbitrary
    files in the working tree, as well as between a file in the working tree and
    its version in the index, or between a file in the index and its version in
    the last commit.






THE GIT OBJECT DATABASE


Git stores all its data as objects in the object database. These
    objects are of four types: blobs, trees, commits, and tags.


Blobs store file contents. Trees store the contents of directories.
    Commits store metadata and a pointer to a tree. Tags point to other objects.


When you modify a file, Git creates a new blob object for the new
    content. It then updates the tree object that points to the file, and then
    updates the commit object that points to the tree.


The index file is a staging area for new commits. It is a list of
    files that will be included in the next commit, along with their contents.
    When you use git add, you are adding a file to the index. When
    you use git commit, you are creating a new commit based on the
    contents of the index.






THE INDEX FILE


The index file is a crucial part of Git's workflow. It acts as a
    staging area, holding information about the next commit you intend to make.
    It is not just a list of files, but a more complex data structure that Git
    uses to track changes.


Let's illustrate with an example:




$ echo "hello world!" > file.txt
$ git add file.txt
$ git diff




The output of git diff is empty because there are no
    differences between the working directory and the index. The file has been
    added to the index, but not yet committed.


Now, let's add a new line to the file:




$ echo "hello world, again" >> file.txt
$ git diff




The output shows the difference between the working directory and the
    index:




diff --git a/file.txt b/file.txt
index a042389..513feba 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1,2 @@
 hello world!
+hello world, again




When you run git add file.txt again, it updates the
    index to reflect the changes in the working directory:




$ git add file.txt
$ git diff




The last diff is empty, but no new commits have been made, and the
    head still doesn’t contain the new line:




$ git diff HEAD
diff --git a/file.txt b/file.txt
index a042389..513feba 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1,2 @@
 hello world!
+hello world, again




So git diff is comparing against something other than the
    head. The thing that it’s comparing against is actually the index
    file, which is stored in .git/index in a binary format, but whose contents
    we can examine with ls-files:




$ git ls-files --stage
100644 513feba2e53ebbd2532419ded848ba19de88ba00 0       file.txt
$ git cat-file -t 513feba2
blob
$ git cat-file blob 513feba2
hello world!
hello world, again




So what our git add did was store a new blob and then put a
    reference to it in the index file. If we modify the file again, we’ll
    see that the new modifications are reflected in the git diff
  output:




$ echo 'again?' >>file.txt
$ git diff
index 513feba..ba3da7b 100644
--- a/file.txt
+++ b/file.txt
@@ -1,2 +1,3 @@
 hello world!
 hello world, again
+again?




With the right arguments, git diff can also show us the
    difference between the working directory and the last commit, or between the
    index and the last commit:




$ git diff HEAD
diff --git a/file.txt b/file.txt
index a042389..ba3da7b 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1,3 @@
 hello world!
+hello world, again
+again?
$ git diff --cached
diff --git a/file.txt b/file.txt
index a042389..513feba 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1,2 @@
 hello world!
+hello world, again




At any time, we can create a new commit using git commit
    (without the "-a" option), and verify that the state committed
    only includes the changes stored in the index file, not the additional
    change that is still only in our working tree:




$ git commit -m "repeat"
$ git diff HEAD
diff --git a/file.txt b/file.txt
index 513feba..ba3da7b 100644
--- a/file.txt
+++ b/file.txt
@@ -1,2 +1,3 @@
 hello world!
 hello world, again
+again?




So by default git commit uses the index to create the
    commit, not the working tree; the "-a" option to commit tells it
    to first update the index with all changes in the working tree.


Finally, it’s worth looking at the effect of git add
    on the index file:




$ echo "goodbye, world" >closing.txt
$ git add closing.txt




The effect of the git add was to add one entry to the index
    file:




$ git ls-files --stage
100644 8b9743b20d4b15be3955fc8d5cd2b09cd2336138 0       closing.txt
100644 513feba2e53ebbd2532419ded848ba19de88ba00 0       file.txt




And, as you can see with cat-file, this new entry refers to the
    current contents of the file:




$ git cat-file blob 8b9743b2
goodbye, world




The "status" command is a useful way to get a quick
    summary of the situation:




$ git status
On branch master
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        new file:   closing.txt
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   file.txt




Since the current state of closing.txt is cached in the index
    file, it is listed as "Changes to be committed". Since file.txt
    has changes in the working directory that aren’t reflected in the
    index, it is marked "changed but not updated". At this point,
    running "git commit" would create a commit that added closing.txt
    (with its new contents), but that didn't modify file.txt.


Also, note that a bare git diff shows the changes to
    file.txt, but not the addition of closing.txt, because the version of
    closing.txt in the index file is identical to the one in the working
    directory.


In addition to being the staging area for new commits, the index
    file is also populated from the object database when checking out a branch,
    and is used to hold the trees involved in a merge operation. See
    gitcore-tutorial(7) and the relevant man pages for details.






WHAT NEXT?


At this point you should know everything necessary to read the man
    pages for any of the git commands; one good place to start would be with the
    commands mentioned in giteveryday(7). You should be able to find any
    unknown jargon in gitglossary(7).


The Git User’s Manual[1] provides a more
    comprehensive introduction to Git.


gitcvs-migration(7) explains how to import a CVS repository
    into Git, and shows how to use Git in a CVS-like way.


For some interesting examples of Git use, see the
    howtos[2].


For Git developers, gitcore-tutorial(7) goes into detail on
    the lower-level Git mechanisms involved in, for example, creating a new
    commit.
