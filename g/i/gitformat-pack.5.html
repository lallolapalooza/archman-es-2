DESCRIPCIÓ

N

El formato de paquete de Git es la forma en que Git almacena la mayoría de los datos principales de su repositorio. A lo largo de la vida de un repositorio, los objetos sueltos (si los hay) y los paquetes más pequeños se consolidan en paquete(s) más grandes. Vea git-gc(1) y git-pack-obje

cts(1).

El formato de paquete también se usa a través de la red, véase por ejemplo gitprotocol-v2(5), así como ser parte de otros formatos de contenedor en el caso de gitformat-

bundl
e(5).

SUMAS DE VERIFICACIÓN E IDENTIFICADORES DE

OBJETOS

En un repositorio que usa el SHA-1 tradicional, las sumas de verificación del paquete, las sumas de verificación del índice y los identificadores de objetos (nombres de objetos) mencionados a continuación se calculan todos usando SHA-1. De manera similar, en los repositorios SHA-256, estos valores se calculan usando

SHA-256.

Las sumas de verificación CRC32 se calculan siempre sobre el objeto empaquetado completo,

incluyendo el encabezado (tipo y longitud de n bytes); el nombre u offset del objeto base
, si lo hay; y el objeto comprimido completo. El algoritmo CRC32 utilizado es el de zlib.

Codificación de

objetos

A diferencia de los objetos sueltos, los objetos empaquetados no tienen un prefijo que contenga el tipo, el tamaño y un byte NUL. Estos no son necesarios porque pueden determinarse por el tipo y longitud de n bytes que preceden a los datos y por lo tanto se omiten de los datos comprimidos y con

delta.

El cálculo del identificador del objeto todav

ía usa este prefijo reconstruyéndolo des
de el tipo y la longitud según sea necesario.

Codificación de

tamaño

Este documento usa la siguiente "codificación de tamaño" de enteros no negativos: De cada byte, los siete bits menos significativos se usan para formar el entero resultante. Mientras el bit más significativo sea 1, este proceso continúa; el byte con MSB 0 proporciona los últimos siete bits. Los fragmentos de siete bits se concatenan. Los valores posteriores son más

significativos.

Esta codificación de tamaño no debe confundirse con la "codificación de offset", que también se usa en este

documento.

Al codificar el tamaño de un objeto sin delta en un paquete, el tamaño es el del

objeto sin comprimir. Para los objetos con delta, es el tamaño del delta sin comp
rimir. El nombre u offset del objeto base no se incluye en el cálculo del tamaño.

Representación con

delta

Conceptualmente solo hay cuatro tipos de objetos: commit, tree, tag y blob. Sin embargo, para ahorrar espacio, un objeto podría almacenarse como un "delta" de otro objeto "base". A estas representaciones se les asignan los nuevos tipos ofs-delta y ref-delta, que solo son válidos en un archivo de

paquete.

Tanto ofs-delta como ref-delta almacenan el "delta" a aplicar a otro objeto (llamado objeto base) para reconstruir el objeto. La diferencia entre ellos es que ref-delta codifica directamente el nombre del objeto base. Si el objeto base está en el mismo paquete, ofs-delta codifica el offset del objeto base en el paquete en su

lugar.

El objeto base también podría tener delta si está en el mismo paquete. Ref-delta también puede referirse a un objeto fuera del paquete (es decir, el llamado "paquete delgado"). Sin embargo, cuando se almacena en disco, el paquete debe ser autosuficiente para evitar dependencias

cíclicas.

Los datos delta comienzan con el tamaño del objeto base y el tamaño del objeto a reconstruir. Estos tamaños se codifican usando la codificación de tamaño de arriba. El resto de los datos delta es una secuencia de instrucciones para reconstruir el objeto desde el objeto base. Si el objeto base tiene delta, primero debe convertirse a forma canónica. Cada instrucción añade más y más datos al objeto objetivo hasta que esté completo. Hasta ahora hay dos instrucciones soportadas: una para copiar un rango de bytes del objeto fuente y otra para insertar nuevos datos incrustados en la instrucción

misma.

Cada instrucción tiene longitud variable. El tipo de instrucción se determina por el séptimo bit del primer octeto. Los siguientes diagramas siguen la convención en RFC 1951 (formato de datos comprimidos Deflate)

•Una tabla de fan-out de 256 entradas, igual que la v1.

•Una tabla de valores CRC32 de 4 bytes de los datos de objeto empaquetados. Esto es nuevo en la v2 para que los datos comprimidos se puedan copiar directamente de un paquete a otro durante la reorganización sin corrupción de datos no detectada.
•Una tabla de valores de desplazamiento de 4 bytes (en orden de red). Estos suelen ser desplazamientos de archivo de paquete de 31 bits, pero los desplazamientos grandes se codifican como un índice en la siguiente tabla con el bit ms activado.
•Una tabla de entradas de desplazamiento de 8 bytes (vacía para archivos de paquete menores a 2 GiB). Los archivos de paquete se organizan con objetos muy utilizados hacia el frente, por lo que la mayoría de las referencias de objetos no necesitarán hacer referencia a esta tabla.

Todos los números de 4 bytes están en orden de byte de red.

ARCHIVOS MULTI-PACK-INDEX (MIDX) TIENEN EL SIGUIENTE FORMATO:

Los archivos multi-pack-index hacen referencia a múltiples archivos de paquete y objetos sueltos.

Para permitir extensiones que añadan datos extra al MIDX, organizamos el cuerpo en "trozos" (chunks) y proporcionamos una tabla de búsqueda al principio del cuerpo. La cabecera incluye ciertos valores de longitud, como el número de paquetes, el número de archivos MIDX base, las longitudes y tipos de hash.

Todos los números de 4 bytes están en orden de red.
