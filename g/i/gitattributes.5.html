DESCRIPCIÓ

N

Un archivo gitattributes es un archivo de texto simple que asigna atributos a nombres de

ruta.

Cada línea en un archivo gitattributes tiene la

forma: 
patrón atributo1 atributo2 .
.
.

Es decir, un patrón seguido de una lista de atributos, separados por espacios en blanco. Los espacios en blanco iniciales y finales se ignoran. Las líneas que comienzan con # se ignoran. Los patrones que comienzan con comillas dobles están citados al estilo C. Cuando el patrón coincide con la ruta en cuestión, los atributos listados en la línea se asignan a la

ruta.

Cada atributo puede estar en uno de estos estados para una ruta

dada:

Establec

ido
La ruta tiene el atributo con el valor especial "true"; esto se especifica listando solo el nombre del atributo en la lista de
atributos.

No

establecido
La ruta tiene el atributo con el valor especial "false"; esto se especifica listando el nombre del atributo precedido de un guion - en la lista de
atributos.

Establecido a un

valor
La ruta tiene el atributo con el valor de cadena especificado; esto se especifica listando el nombre del atributo seguido de un signo igual = y su valor en la lista de
atributos.

No

especificado
Ningún patrón coincide con la ruta, y nada indica si la ruta tiene o no el atributo, el atributo de la ruta se dice que está No
especificado.

Cuando más de un patrón coincide con la ruta, una línea posterior anula una línea anterior. Esta anulación se hace por

atributo.

Las reglas por las que el patrón coincide con las rutas son las mismas que en archivos .gitignore (ver gitignore(5)), con algunas

excepciones:
•los patrones negativos están
prohibidos
•los patrones que coinciden con un directorio no coinciden recursivamente con las rutas dentro de ese directorio (por lo que usar la sintaxis de barra final ruta/ es inútil en un archivo de atributos; usa ruta/** en su
lugar)

Al decidir qué atributos se asignan a una ruta, Git consulta el archivo $GIT_DIR/info/attributes (que tiene la mayor precedencia), el archivo .gitattributes en el mismo directorio que la ruta en cuestión, y sus directorios superiores hasta la raíz del árbol de trabajo (cuanto más lejos esté el directorio que contiene .gitattributes de la ruta en cuestión, menor será su precedencia). Finalmente, se consideran los archivos globales y de sistema (tienen la menor precedencia)

.

Cuando el archivo .gitattributes falta en el árbol de trabajo, se usa la ruta en el índice como respaldo. Durante el proceso de checkout, se usa .gitattributes en el índice y luego el archivo en el árbol de trabajo se usa como

respaldo.

Si deseas afectar solo a un repositorio único (es decir, asignar atributos a archivos que son particulares para el flujo de trabajo de un usuario para ese repositorio), entonces los atributos deben colocarse en el archivo $GIT_DIR/info/attributes. Los atributos que deben ser controlados por versiones y distribuidos a otros repositorios (es decir, atributos de interés para todos los usuarios) deben ir en archivos .gitattributes. Los atributos que deben afectar a todos los repositorios de un usuario único deben colocarse en un archivo especificado por la opción de configuración core.attributesFile (ver git-config(1)). Su valor por defecto es $XDG_CONFIG_HOME/git/attributes. Si $XDG_CONFIG_HOME no está establecido o está vacío, se usa $HOME/.config/git/attributes en su lugar. Los atributos para todos los usuarios de un sistema deben colocarse en el archivo $(prefix)/etc/gitattributes

.

A veces necesitarías anular la configuración de un atributo para una ruta al estado No especificado. Esto se puede hacer listando el nombre de el atributo precedido de un signo de exclamación

!
.

EFECTO

S

Ciertas operaciones de Git pueden verse influidas por la asignación de atributos particulares a una ruta. Actualmente, las siguientes operaciones son conscientes de los

atributos.

Checkout y

checkin

Estos atributos afectan cómo el contenido almacenado en el repositorio se copia a los archivos del árbol de trabajo cuando se ejecutan comandos como git switch, git checkout y git merge. También afectan cómo Git almacena el contenido que preparas en el árbol de trabajo en el repositorio al hacer git add y git com

mit.

text

Este atributo marca la ruta como un archivo de texto, lo que habilita la conversión de fin de línea: cuando un archivo que coincide se añade al índice, los finales de línea del archivo se normalizan a LF en el índice. A la inversa, cuando el archivo se copia del índice al directorio de trabajo, sus finales de línea pueden convertirse de LF a CRLF dependiendo del atributo eol, la configuración de Git y la plataforma (ver la explicación de eol más abajo)

.

Establec

ido
Establecer el atributo text en una ruta habilita la conversión de fin de línea en el checkin y checkout como se describió arriba. Los finales de línea se normalizan a LF en el índice cada vez que el archivo se registra, incluso si el archivo se añadió previamente a Git con finales de línea
CRLF.

No

establecido
No establecer el atributo text en una ruta le dice a Git que no intente ninguna conversión de fin de línea al hacer checkin o
checkout.

Establecido a valor de cadena

"auto"
Cuando text se establece en "auto", Git decide por sí mismo si el archivo es de texto o binario. Si es de texto y el archivo no estaba ya en Git con finales CRLF, los finales de línea se convierten al hacer checkin y checkout como se describió arriba. De lo contrario, no se hace ninguna conversión al hacer checkin o
checkout.

No

especificado
Si el atributo text no está especificado, Git usa la variable de configuración core.autocrlf para determinar si el archivo debe ser
convertido.

Cualquier otro valor hace que Git actúe como si text hubiera quedado

sin es
pecificar.

eol

Este atributo marca una ruta para usar un estilo de fin de línea específico en el árbol de trabajo cuando se hace checkout. Solo tiene efecto si text o text=auto está establecido (ver arriba), pero especificar eol establece automáticamente text si text estaba sin

especificar.

Establecido a valor de cadena

"crlf"
Esta configuración convierte los finales de línea del archivo en el directorio de trabajo a CRLF cuando el archivo se hace
checkout.

Establecido a valor de cadena

"lf"
Esta configuración usa los mismos finales de línea en el directorio de trabajo que en el índice cuando el archivo se hace
checkout.

No

especificado
Si el atributo eol no está especificado para un archivo, sus finales de línea en el directorio de trabajo se determinan por la variable de configuración core.autocrlf o core.eol (ver las definiciones de esas opciones en git-config(1)). Si text está establecido pero ninguna de esas variables lo está, el valor por defecto es eol=crlf en Windows y eol=lf en todas las
demás pl
ataformas.

Compatibilidad hacia atrás con el atributo crlf

Por compatibilidad hacia atrás, el atributo crlf se interpreta de la siguiente

manera: 
crlf
text -crlf
-text crlf=i
nput eol=lf

Conversión de fin de línea

Aunque Git normalmente deja el contenido de los archivos sin cambios, se puede configurar para normalizar los finales de línea a LF en el repositorio y,

Opcionalmente, para convertirlos a CRLF cuando los archivos son extraídos.

Si simplemente desea tener finales de línea CRLF en su directorio de trabajo independientemente del repositorio con el que esté trabajando, puede establecer la variable de configuración "core.autocrlf" sin usar atributos.

[core]
        autocrlf = true

Esto no fuerza la normalización de archivos de texto, pero asegura que los archivos de texto que introduce en el repositorio tengan sus finales de línea normalizados a LF cuando se añaden, y que los archivos que ya están normalizados en el repositorio permanezcan normalizados.

Si desea asegurarse de que los archivos de texto que cualquier contribuidor introduzca en el repositorio tengan sus finales de línea normalizados, puede establecer el atributo text en "auto" para *todos* los archivos.

*       text=auto

Los atributos permiten un control granular sobre cómo se convierten los finales de línea. Aquí hay un ejemplo que hará que Git normalice los archivos .txt, .vcproj y .sh, asegurará que los archivos .vcproj tengan CRLF y los archivos .sh tengan LF en el directorio de trabajo, y evitará que los archivos .jpg sean normalizados independientemente de su contenido.

*               text=auto
*.txt           text
*.vcproj        text eol=crlf
*.sh            text eol=lf
*.jpg           -text

Nota

Cuando la conversión text=auto está habilitada en un proyecto multiplataforma utilizando push y pull a un repositorio central, los archivos de texto que contienen CRLF deben ser normalizados.

Desde un directorio de trabajo limpio:

$ echo "* text=auto" >.gitattributes
$ git add --renormalize .
$ git status        # Muestra los archivos que serán normalizados
$ git commit -m "Introducir normalización de fin de línea"

Si algunos archivos que no deberían ser normalizados aparecen en git status, desactive su atributo text antes de ejecutar git add -u.

manual.pdf      -text

Por el contrario, los archivos de texto que Git no detecta pueden tener la normalización habilitada manualmente.

weirdchars.txt  text

Si core.safecrlf está establecido en "true" o "warn", Git verifica si la conversión es reversible para la configuración actual de core.autocrlf. Para "true", Git rechaza conversiones irreversibles; para "warn", Git solo imprime una advertencia pero acepta una conversión irreversible. Los disparadores de seguridad evitan que dichas conversiones se realicen en los archivos del árbol de trabajo, pero hay algunas excepciones. A pesar de que...

•git add en sí mismo no toca los archivos en el árbol de trabajo, el próximo checkout sí lo haría, por lo que los disparadores de seguridad se activan;
•git apply para actualizar un archivo de texto con un parche sí toca los archivos en el árbol de trabajo, pero la operación trata sobre archivos de texto y la conversión de CRLF trata de corregir las inconsistencias de los finales de línea, por lo que la seguridad no se activa;
•git diff en sí mismo no toca los archivos en el árbol de trabajo, a menudo se ejecuta para inspeccionar los cambios que se pretenden añadir posteriormente con git add. Para detectar potenciales problemas de forma temprana, los disparadores de seguridad se activan.

working-tree-encoding

Git reconoce los archivos codificados en ASCII o en uno de sus superconjuntos (por ejemplo, UTF-8, ISO-8859-1, ...) como archivos de texto. Los archivos codificados en otras codificaciones (por ejemplo, UTF-16) se interpretan como binarios y, en consecuencia, las herramientas de procesamiento de texto integradas en Git (por ejemplo, git diff), así como la mayoría de los frontales web de Git, no visualizan el contenido de estos archivos por defecto.

En estos casos, puede indicar a Git la codificación de un archivo en el directorio de trabajo con el atributo working-tree-encoding. Si se añade un archivo con este atributo a Git, entonces Git re-codifica el contenido de la codificación especificada a UTF-8. Finalmente, Git almacena el contenido codificado en UTF-8 en su estructura de datos interna (llamada "el índice"). Al extraer, el contenido se re-codifica de nuevo a la codificación especificada.

Tenga en cuenta que el uso del atributo working-tree-encoding puede tener varias trampas:

•Implementaciones alternativas de Git (por ejemplo, JGit o libgit2) y versiones antiguas de Git (a partir de marzo de 2018) no soportan el atributo working-tree-encoding. Si decide usar el atributo working-tree-encoding en su repositorio, se recomienda encarecidamente asegurarse de que todos los clientes que trabajen con el repositorio lo soporten.

Por ejemplo, los archivos de recursos de Microsoft Visual Studio (*.rc) o los archivos de script de PowerShell (*.ps1) a veces están codificados en UTF-16. Si declara *.ps1 como archivos en UTF-16 y añade foo.ps1 con un cliente Git que tiene habilitado working-tree-encoding, entonces foo.ps1 se almacenará como UTF-8 internamente. Un cliente sin soporte para working-tree-encoding extraerá foo.ps1 como un archivo codificado en UTF-8. Esto generalmente causará problemas a los usuarios de este archivo.

Si un cliente Git que no soporta el atributo working-tree-encoding añade un archivo nuevo bar.ps1, entonces bar.ps1 se almacenará "tal cual" internamente (en este ejemplo, probablemente como UTF-16). Un cliente con soporte para working-tree-encoding interpretará el contenido interno como UTF-8 e intentará convertirlo a UTF-16 al extraer. Esa operación fallará y provocará un error.

•La re-codificación de contenido a codificaciones no UTF puede causar errores ya que la conversión podría no ser segura para el ciclo de ida y vuelta UTF-8. Si sospecha que su codificación no es segura para el ciclo de ida y vuelta, añádala a core.checkRoundtripEncoding para que Git verifique la codificación de ciclo de ida y vuelta (ver git-config(1)). SHIFT-JIS (conjunto de caracteres japonés) es conocido por tener problemas de ciclo de ida y vuelta con UTF-8 y se verifica por defecto.
•La re-codificación de contenido requiere recursos que pueden ralentizar ciertas operaciones de Git (por ejemplo, git checkout o git add).

Utilice el atributo working-tree-encoding solo si no puede almacenar un archivo en codificación UTF-8 y si desea que Git pueda procesar el contenido como texto.

Como ejemplo, utilice los siguientes atributos si sus archivos *.ps1 están codificados en UTF-16 con marca de orden de bytes (BOM) y desea que Git realice conversiones automáticas de finales de línea según su plataforma.

*.ps1           text working-tree-encoding=UTF-16

Utilice los siguientes atributos si sus archivos *.ps1 están codificados en UTF-16 little endian sin BOM y desea que Git utilice finales de línea de Windows en el directorio de trabajo (use UTF-16LE-BOM en lugar de UTF-16LE si desea UTF-16 little endian con BOM). Tenga en cuenta que se recomienda encarecidamente definir explícitamente los finales de línea con eol si se utiliza el atributo working-tree-encoding para evitar ambigüedades.

*.ps1           text working-tree-encoding=UTF-16LE eol=crlf

Puede obtener una lista de todas las codificaciones disponibles en su plataforma con el siguiente comando:

iconv --list

Si no conoce la codificación de un archivo, puede usar el comando file para adivinar la codificación:

file foo.ps1

ident

Cuando el atributo ident se establece para una ruta, Git reemplaza $Id$ en el objeto blob con $Id:, seguido del nombre del objeto blob hexadecimal de 40 caracteres, seguido de un signo de dólar $ al extraer. Cualquier secuencia de bytes que comience con $Id: y termine con $ en el archivo del árbol de trabajo se reemplaza con $Id$ al registrar.

filter

Se puede establecer un atributo filter con un valor de cadena que nombra un controlador de filtro especificado en la configuración.

Un controlador de filtro consta de un comando clean y un comando smudge, cualquiera de los cuales puede dejarse sin especificar. Al extraer, cuando se especifica el comando smudge, el comando recibe el objeto blob de su entrada estándar, y su salida estándar se utiliza para actualizar el archivo del árbol de trabajo. De manera similar, el comando clean se utiliza para convertir el contenido del archivo del árbol de trabajo al registrar. Por defecto, estos comandos procesan un solo blob y terminan. Si se utiliza un filtro de proceso de larga ejecución en lugar de filtros clean y/o smudge, entonces Git puede procesar todos los blobs con una sola invocación de comando de filtro durante toda la vida de un único comando de Git, por ejemplo, git add --all. Si se configura un filtro de proceso de larga ejecución, entonces siempre tiene prioridad sobre un filtro de blob único configurado. Consulte la sección a continuación para la descripción del protocolo utilizado para comunicarse con un filtro de proceso.

Un uso del filtrado de contenido es masajear el contenido a una forma que sea más conveniente para la plataforma, el sistema de archivos y el usuario. Para este modo de operación, la frase clave aquí es "más conveniente" y no "convertir algo inutilizable en utilizable". En otras palabras, la intención es que si alguien desactiva la definición del controlador de filtro, o no tiene el programa de filtro apropiado, el proyecto aún debería ser utilizable.

Otro uso del filtrado de contenido es almacenar contenido que no se puede usar directamente en el repositorio (por ejemplo, un UUID que hace referencia al contenido real almacenado fuera de Git, o contenido cifrado) y convertirlo a una forma utilizable al extraer (por ejemplo, descargar el contenido externo o descifrar el contenido cifrado).

Estos dos filtros se comportan de manera diferente, y por defecto, un filtro se considera el primero, masajear el contenido a una forma más conveniente. Una definición de controlador de filtro faltante en la configuración, o un controlador de filtro que sale con un estado distinto de cero, no es un error sino que hace que el filtro sea un no-op passthrough.

Puede declarar que un filtro convierte un contenido que por sí mismo es inutilizable en un contenido utilizable estableciendo la variable de configuración filter.<driver>.required en true.

Nota: Siempre que se cambie el filtro clean, el repositorio debe ser renormalizado: $ git add --renormalize .

Por ejemplo, en .gitattributes, asignaría el atributo filter para rutas.

*.c     filter=indent

Luego definiría una configuración "filter.indent.clean" y "filter.indent.smudge" en su .git/config para especificar un par de comandos para modificar el contenido de los programas C cuando los archivos fuente se registran (se ejecuta "clean") y se extraen (no se realiza ningún cambio porque el comando es "cat").

[filter "indent"]
        clean = indent
        smudge = cat

Para obtener los mejores resultados, clean no debería alterar su salida si se ejecuta dos veces ("clean→clean" debería

sería equivalente a "limpio"), y múltiples comandos de mancha no deberían alterar la salida de limpio ("mancha → mancha → limpio" debería ser equivalente a "limpio"). Ver la sección sobre fusiones más abajo.

El filtro "indent" se comporta bien en este aspecto: no modificará la entrada que ya está correctamente indentada. En este caso, la ausencia de un filtro de mancha significa que el filtro de limpieza *debe* aceptar su propia salida sin modificarla.

Si un filtro *debe* tener éxito para hacer que los contenidos almacenados sean utilizables, puedes declarar que el filtro es requerido, en la configuración:

[filter "crypt"]
        clean = openssl enc ...
        smudge = openssl enc -d ...
        required

La secuencia "%f" en la línea de comandos del filtro se reemplaza con el nombre del archivo en el que el filtro está trabajando. Un filtro puede usar esto en la sustitución de palabras clave. Por ejemplo:

[filter "p4"]
        clean = git-p4-filter --clean %f
        smudge = git-p4-filter --smudge %f

Ten en cuenta que "%f" es el nombre de la ruta que se está procesando. Dependiendo de la versión que se esté filtrando, el archivo correspondiente en disco puede no existir o puede tener contenidos diferentes. Por lo tanto, los comandos de mancha y limpieza no deben intentar acceder al archivo en disco, sino solo actuar como filtros en el contenido que se les proporciona a través de la entrada estándar.

Proceso de filtro de larga duración

Si el comando del filtro (un valor de cadena) se define a través de filter.<driver>.process, entonces Git puede procesar todos los blobs con una única invocación del filtro durante toda la vida de un único comando Git. Esto se logra utilizando el protocolo de proceso de larga duración (descrito en Documentation/technical/long-running-process-protocol.adoc).

Cuando Git encuentra el primer archivo que necesita ser limpiado o manchado, inicia el filtro y realiza el apretón de manos. En el apretón de manos, el mensaje de bienvenida enviado por Git es "git-filter-client", solo se soporta la versión 2 y las capacidades soportadas son "clean", "smudge" y "delay".

Después, Git envía una lista de pares "clave=valor" terminada con un paquete de flush. La lista contendrá al menos el comando del filtro (basado en las capacidades soportadas) y la ruta del archivo a filtrar relativa a la raíz del repositorio. Justo después del paquete de flush, Git envía el contenido dividido en cero o más paquetes pkt-line y un paquete de flush para terminar el contenido. Por favor, ten en cuenta que el filtro no debe enviar ninguna respuesta antes de recibir el contenido y el paquete de flush final. También ten en cuenta que el "valor" de un par "clave=valor" puede contener el carácter "=" mientras que la clave nunca contendría ese carácter.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> 0000
packet:          git> CONTENT
packet:          git> 0000

Se espera que el filtro responda con una lista de pares "clave=valor" terminada con un paquete de flush. Si el filtro no experimenta problemas, la lista debe contener un estado "success". Justo después de estos paquetes, se espera que el filtro envíe el contenido en cero o más paquetes pkt-line y un paquete de flush al final. Finalmente, se espera una segunda lista de pares "clave=valor" terminada con un paquete de flush. El filtro puede cambiar el estado en la segunda lista o mantener el estado tal cual con una lista vacía. Ten en cuenta que la lista vacía debe terminar con un paquete de flush independientemente.

packet:          git< status=success
packet:          git< 0000
packet:          git< SMUDGED_CONTENT
packet:          git< 0000
packet:          git< 0000  # ¡lista vacía, mantener "status=success" sin cambios!

Si el contenido resultante está vacío, se espera que el filtro responda con un estado "success" y un paquete de flush para señalar el contenido vacío.

packet:          git< status=success
packet:          git< 0000
packet:          git< 0000  # ¡contenido vacío!
packet:          git< 0000  # ¡lista vacía, mantener "status=success" sin cambios!

En caso de que el filtro no pueda o no quiera procesar el contenido, se espera que responda con un estado "error".

packet:          git< status=error
packet:          git< 0000

Si el filtro experimenta un error durante el procesamiento, puede enviar el estado "error" después de que el contenido haya sido enviado (parcial o completamente).

packet:          git< status=success
packet:          git< 0000
packet:          git< HALF_WRITTEN_ERRONEOUS_CONTENT
packet:          git< 0000
packet:          git< status=error
packet:          git< 0000

En caso de que el filtro no pueda o no quiera procesar el contenido, así como cualquier contenido futuro durante la vida del proceso Git, se espera que responda con un estado "abort" en cualquier punto del protocolo.

packet:          git< status=abort
packet:          git< 0000

Git no detiene ni reinicia el proceso del filtro en caso de que se establezca el estado "error"/"abort". Sin embargo, Git establece su código de salida de acuerdo con el flag filter.<driver>.required, simulando el comportamiento del mecanismo filter.<driver>.clean / filter.<driver>.smudge.

Si el filtro muere durante la comunicación o no cumple con el protocolo, entonces Git detendrá el proceso del filtro y lo reiniciará con el siguiente archivo que necesite ser procesado. Dependiendo del flag filter.<driver>.required, Git interpretará eso como un error.

Retraso

Si el filtro soporta la capacidad "delay", entonces Git puede enviar el flag "can-delay" después del comando del filtro y la ruta. Este flag indica que el filtro puede retrasar el filtrado del blob actual (por ejemplo, para compensar latencias de red) respondiendo sin contenido pero con el estado "delayed" y un paquete de flush.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> can-delay=1
packet:          git> 0000
packet:          git> CONTENT
packet:          git> 0000
packet:          git< status=delayed
packet:          git< 0000

Si el filtro soporta la capacidad "delay", entonces debe soportar el comando "list_available_blobs". Si Git envía este comando, entonces se espera que el filtro devuelva una lista de rutas que representan blobs que han sido retrasados anteriormente y ahora están disponibles. La lista debe ser terminada con un paquete de flush seguido de un estado "success" que también está terminado con un paquete de flush. Si aún no hay blobs para las rutas retrasadas disponibles, entonces se espera que el filtro bloquee la respuesta hasta que al menos un blob esté disponible. El filtro puede indicarle a Git que ya no tiene blobs retrasados enviando una lista vacía. Tan pronto como el filtro responde con una lista vacía, Git deja de preguntar. Todos los blobs que Git no ha recibido hasta este punto se consideran faltantes y resultarán en un error.

packet:          git> command=list_available_blobs
packet:          git> 0000
packet:          git< pathname=path/testfile.dat
packet:          git< pathname=path/otherfile.dat
packet:          git< 0000
packet:          git< status=success
packet:          git< 0000

Interacción entre atributos de registro/extracción

En la ruta de código de registro, el archivo del área de trabajo se convierte primero con el controlador filter (si se especifica y se define el controlador correspondiente), luego el resultado se procesa con ident (si se especifica), y luego finalmente con text (de nuevo, si se especifica y es aplicable).

En la ruta de código de extracción, el contenido del blob se convierte primero con text, y luego ident y se alimenta a filter.

Fusión de ramas con atributos de registro/extracción diferentes

Si has agregado atributos a un archivo que causan que el formato canónico del repositorio para ese archivo cambie, como agregar un filtro limpio/manchado o atributos de texto/eol/ident, fusionar cualquier cosa donde el atributo no esté presente normalmente causaría conflictos de fusión.

Para prevenir estos conflictos de fusión innecesarios, Git puede ser instruido para ejecutar una extracción y registro virtual de las tres etapas de cada archivo que necesita una fusión de contenido de tres vías, estableciendo la variable de configuración merge.renormalize. Esto previene que los cambios causados por la conversión de registro provoquen conflictos de fusión espurios cuando un archivo convertido se fusiona con un archivo no convertido.

Mientras que una "mancha → limpio" resulte en la misma salida que una "limpio", incluso en archivos que ya están manchados, esta estrategia resolverá automáticamente todos los conflictos relacionados con filtros. Los filtros que no actúen de esta manera pueden causar conflictos de fusión adicionales que deben ser resueltos manualmente.

2.Luego examina .gitattributes (que está en el directorio padre), y encuentra que la primera línea coincide, pero el archivo t/.gitattributes ya decidió cómo los atributos merge, foo y bar deberían darse a esta ruta, por lo que deja foo y bar desestablecidos. El atributo baz está
establecido.
3.Finalmente examina $GIT_DIR/info/attributes. Este archivo se usa para anular la configuración dentro del árbol. La primera línea coincide, y foo está establecido, bar se revierte al estado no especificado, y baz está
desestablecido.
