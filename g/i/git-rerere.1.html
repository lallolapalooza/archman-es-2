NOMBRE

git-rerere - Reutiliza la resolución grabada de fusiones conflictivas

SINOPSIS

git rerere [clear | forget <pathspec>... | diff | status | remaining | gc]

DESCRIPCIÓN

En un flujo de trabajo que emplea ramas de tema relativamente duraderas, el desarrollador a veces necesita resolver los mismos conflictos una y otra vez hasta que las ramas de tema estén terminadas (ya sea fusionadas en la rama de "lanzamiento" o enviadas y aceptadas upstream).

Este comando ayuda al desarrollador en este proceso grabando los resultados de la fusión automática conflictiva y los resultados de resolución manual correspondientes en la fusión manual inicial, y aplicando resoluciones manuales previamente grabadas a sus resultados de fusión automática correspondientes.


Nota

Necesitas establecer la variable de configuración rerere.enabled para habilitar este comando.

COMANDOS

Normalmente, git rerere se ejecuta sin argumentos o intervención del usuario. Sin embargo, tiene varios comandos que le permiten interactuar con su estado de trabajo.

clear

Restablece los metadatos utilizados por rerere si se va a abortar una resolución de fusión. La llamada a git am [--skip|--abort] o git rebase [--skip|--abort] invocará automáticamente este comando.

forget <pathspec>

Restablece las resoluciones de conflictos que rerere ha grabado para el conflicto actual en <pathspec>.

diff

Muestra las diferencias del estado actual de la resolución. Es útil para rastrear lo que ha cambiado mientras el usuario está resolviendo conflictos. Los argumentos adicionales se pasan directamente al comando diff del sistema instalado en PATH.

status

Imprime las rutas con conflictos cuya resolución de fusión rerere grabará.

remaining

Imprime las rutas con conflictos que no han sido resueltos automáticamente por rerere. Esto incluye rutas cuyas resoluciones no pueden ser rastreadas por rerere, como submódulos conflictivos.

gc

Poda los registros de fusiones conflictivas que ocurrieron hace mucho tiempo. Por defecto, se podan los conflictos no resueltos de más de 15 días y los conflictos resueltos de más de 60 días. Estos valores predeterminados se controlan a través de las variables de configuración gc.rerereUnresolved y gc.rerereResolved respectivamente.

DISCUSIÓN

Cuando tu rama de tema modifica un área superpuesta que tu rama principal (o upstream) tocó desde que tu rama de tema se bifurcó de ella, puede que quieras probarla con la última versión de master, incluso antes de que tu rama de tema esté lista para ser enviada upstream:

              o---*---o---o tema
             /
    o---o---o---*---o---o---o master

Para una prueba así, necesitas fusionar master y tema de alguna manera. Una forma de hacerlo es tirar de master en la rama de tema:

        $ git switch topic
        $ git merge master
              o---*---o---+ tema
             /           /
    o---o---o---*---o---o---o master

Los commits marcados con * tocan la misma área en el mismo archivo; necesitas resolver los conflictos al crear el commit marcado con +. Luego puedes probar el resultado para asegurarte de que tu trabajo en progreso todavía funciona con lo que está en el último master.

Después de esta fusión de prueba, hay dos maneras de continuar tu trabajo en el tema. La más fácil es construir sobre el commit de fusión de prueba +, y cuando tu tema esté finalmente listo, fusionarlo a master, y/o pedir al upstream que tire de ti. Para entonces, sin embargo, master o el upstream podrían haber avanzado desde la fusión de prueba +, en cuyo caso el grafo de commits final se vería así:

        $ git switch topic
        $ git merge master
        $ ... trabajar en ambas ramas topic y master
        $ git switch master
        $ git merge topic
              o---*---o---+---o---o topic
             /           /         \
    o---o---o---*---o---o---o---o---+ master

Sin embargo, cuando tu rama de tema es de larga duración, tu rama de tema terminaría teniendo muchos de estos commits de "Merge desde master", que desordenarían innecesariamente el historial de desarrollo. Los lectores de la lista de correo del kernel de Linux pueden recordar que Linus se quejó de fusiones de prueba tan frecuentes cuando un mantenedor de subsistema pidió que se extrajera de una rama llena de "fusiones inútiles".

Como alternativa, para mantener la rama de tema limpia de fusiones de prueba, podrías eliminar la fusión de prueba y seguir construyendo sobre la punta antes de la fusión de prueba:

        $ git switch topic
        $ git merge master
        $ git reset --hard HEAD^ ;# revertir la fusión de prueba
        $ ... trabajar en ambas ramas topic y master
        $ git switch master
        $ git merge topic
              o---*---o-------o---o topic
             /
    o---o---o---*---o---o---o---o   master

Esto dejaría solo un commit de fusión cuando tu rama de tema esté finalmente lista y fusionada en la rama master. Esta fusión requeriría que resolvieras el conflicto, introducido por los commits marcados con *. Sin embargo, este conflicto es a menudo el mismo conflicto que resolviste cuando creaste la fusión de prueba que eliminaste. git rerere te ayuda a resolver esta fusión conflictiva final utilizando la información de tu resolución manual anterior.

Ejecutar el comando git rerere inmediatamente después de una fusión automática conflictiva graba los archivos del árbol de trabajo conflictivo, con los marcadores de conflicto habituales <<<<<<<, =======, y >>>>>>> en ellos. Más tarde, después de haber terminado de resolver los conflictos, ejecutar git rerere de nuevo grabará el estado resuelto de estos archivos. Supongamos que hiciste esto cuando creaste la fusión de prueba de master en la rama de tema.

La próxima vez, después de ver la misma fusión automática conflictiva, ejecutar git rerere realizará una fusión de tres vías entre la fusión automática conflictiva anterior, la resolución manual anterior y la fusión automática conflictiva actual. Si esta fusión de tres vías se resuelve limpiamente, el resultado se escribe en el archivo de tu árbol de trabajo, así que no tienes que resolverlo manualmente. Ten en cuenta que git rerere deja el índice intacto, por lo que todavía necesitas hacer las comprobaciones finales con git diff (o git diff -c) y git add cuando estés satisfecho.

Como medida de conveniencia, git merge invoca automáticamente git rerere al salir con una fusión automática fallida y git rerere graba la resolución manual cuando es un nuevo conflicto, o reutiliza la resolución manual anterior cuando no lo es. git commit también invoca git rerere al confirmar un resultado de fusión. Lo que esto significa es que no tienes que hacer nada especial tú mismo (además de habilitar la variable de configuración rerere.enabled).

En nuestro ejemplo, cuando haces la fusión de prueba, se graba la resolución manual, y se reutilizará cuando hagas la fusión real más tarde con la rama master y la rama topic actualizadas, siempre que la resolución grabada siga siendo aplicable.

La información que git rerere graba también se utiliza al ejecutar git rebase. Después de eliminar la fusión de prueba y continuar el desarrollo en la rama de tema:

              o---*---o-------o---o topic
             /
    o---o---o---*---o---o---o---o   master
        $ git rebase master topic
                                  o---*---o-------o---o topic
                                 /
    o---o---o---*---o---o---o---o   master

podrías ejecutar git rebase master topic, para ponerte al día antes de que tu tema esté listo para ser enviado upstream. Esto resultaría en caer de nuevo a una fusión de tres vías, y conflictuaría de la misma manera que la fusión de prueba que resolviste antes. git rerere será ejecutado por git rebase para ayudarte a resolver este conflicto.

[NOTA] git rerere se basa en los marcadores de conflicto en el archivo para detectar el conflicto. Si el archivo ya contiene líneas que parecen iguales a las líneas con marcadores de conflicto, git rerere puede fallar al grabar una resolución de conflicto. Para solucionar esto, se puede usar la configuración conflict-marker-size en gitattributes(5).

git - the information manager from hell

NAME

git - the information manager from hell

SYNOPSIS

git [git-options] [sub-command] [sub-command-options]

DESCRIPTION

Git is a fast, scalable, distributed revision control system with an unusually rich command set that provides both high-level operations and low-level control. It was originally designed, written, and is still maintained by Linus Torvalds (creator of Linux, the most widely used open source operating system kernel) for helping manage the development of the Linux kernel. Git is designed for speed and efficiency, with all operations either local or designed to be fast. It is particularly well suited for distributed development environments where a project has multiple contributors working concurrently.

COMMANDS

The following is a list of the most commonly used git commands. For a complete list, see git help -a.

git help
Show help for a given command.
git init
Create an empty Git repository or reinitialize an existing one.
git clone
Clone a repository into a new directory.
git add
Add file contents to the index.
git rm
Remove files from the working tree and from the index.
git mv
Move or rename a file, a directory, or a symlink.
git status
Show the working tree status.
git diff
Show changes between commits, commit and working tree, etc.
git log
Show commit logs.
git commit
Record changes to the repository.
git reset
Reset current HEAD to the specified state.
git checkout
Switch branches or restore working tree files.
git branch
List, create, or delete branches.
git merge
Join two or more development histories together.
git rebase
Reapply commits on top of another base tip.
git tag
Give a commit a human-readable name, often used to mark for a release point (e.g., v1.0).
git fetch
Download objects and refs from another repository.
git pull
Fetch from and integrate with another repository or a local branch.
git push
Update remote refs along with associated objects.
git remote
Manage set of tracked repositories.
git config
Get and set repository or global options.

DISCUSSION

This manual page is a high-level overview of the git command. For detailed information about a specific command, use git help <command>.
