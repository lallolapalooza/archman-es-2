NOMBRE

git-p4 - Importar desde y enviar a repositorios de Perforce

SINOPSIS

git p4 clone [<opciones-de-sincronización>] [<opciones-de-clonación>] <ruta-del-depósito-p4>...
git p4 sync [<opciones-de-sincronización>] [<ruta-del-depósito-p4>...]
git p4 rebase
git p4 submit [<opciones-de-envío>] [<nombre-de-la-rama-principal>]

DESCRIPCIÓN

Este comando proporciona una forma de interactuar con repositorios p4 usando Git.

Cree un nuevo repositorio Git a partir de un repositorio p4 existente usando git p4 clone, dándole una o más rutas de depósito p4. Incorpore nuevos commits de cambios de p4 con git p4 sync. El comando sync también se usa para incluir nuevas ramas de otras rutas de depósito p4. Envíe cambios de Git de vuelta a p4 usando git p4 submit. El comando git p4 rebase realiza una sincronización y hace un rebase de la rama actual sobre la rama remota de p4 actualizada.

EJEMPLOS

•Clonar un repositorio: 
$ git p4 clone //depot/path/project
•Hacer algo de trabajo en el repositorio Git recién creado: 
$ cd project
$ vi foo.h
$ git commit -a -m "edited foo.h"
•Actualizar el repositorio Git con cambios recientes de p4, haciendo un rebase de su trabajo encima: 
$ git p4 rebase
•Enviar sus commits de vuelta a p4: 
$ git p4 submit

COMANDOS

Clonar

Generalmente, git p4 clone se usa para crear un nuevo directorio Git a partir de un repositorio p4 existente:

$ git p4 clone //depot/path/project

Esto:

1.Crea un repositorio Git vacío en un subdirectorio llamado project.
2.Importa el contenido completo de la revisión más reciente desde la ruta de depósito p4 dada en un solo commit en la rama de Git refs/remotes/p4/master.
3.Crea una rama local, master desde esta remota y la hace checkout.

Para reproducir todo el historial de p4 en Git, use el modificador @all en la ruta del depósito:

$ git p4 clone //depot/path/project@all

Sincronizar

A medida que el desarrollo continúa en el repositorio p4, esos cambios pueden ser incluidos en el repositorio Git usando:

$ git p4 sync

Este comando encuentra nuevos cambios en p4 y los importa como commits de Git.

Los repositorios p4 pueden ser añadidos a un repositorio Git existente usando git p4 sync también:

$ mkdir repo-git
$ cd repo-git
$ git init
$ git p4 sync //path/in/your/perforce/depot

Esto importa el depósito especificado en refs/remotes/p4/master en un repositorio Git existente. La opción --branch puede usarse para especificar una rama diferente a usar para el contenido de p4.

Si un repositorio Git incluye ramas refs/remotes/origin/p4, estas serán obtenidas y consultadas primero durante un git p4 sync. Dado que importar directamente desde p4 es considerablemente más lento que obtener cambios de un remoto de Git, esto puede ser útil en un entorno con múltiples desarrolladores.

Si hay múltiples ramas, hacer un git p4 sync usará automáticamente el algoritmo de "DETECCIÓN DE RAMAS" para intentar particionar los nuevos cambios en la rama correcta. Esto puede ser anulado con la opción --branch para especificar una sola rama a actualizar.

Rebase

Un patrón de trabajo común es obtener los últimos cambios del depósito p4 y fusionarlos con cambios locales sin confirmar. A menudo, el repositorio p4 es la ubicación definitiva para todo el código, por lo que un flujo de trabajo de rebase tiene sentido. Este comando hace git p4 sync seguido de git rebase para mover los commits locales encima de los cambios de p4 actualizados.

$ git p4 rebase

Enviar

Enviar cambios de un repositorio Git de vuelta al repositorio p4 requiere un espacio de trabajo de cliente p4 separado. Este debe ser especificado usando la variable de entorno P4CLIENT o la variable de configuración de Git git-p4.client. El cliente p4 debe existir, pero la raíz del cliente será creada y poblada si no existe ya.

Para enviar todos los cambios que están en la rama de Git actual pero no en la rama p4/master , use:

$ git p4 submit

Para especificar una rama diferente a la actual, use:

$ git p4 submit topicbranch

Para especificar un solo commit o un rango de commits, use:

$ git p4 submit --commit <sha1>
$ git p4 submit --commit <sha1..sha1>

La referencia ascendente es generalmente refs/remotes/p4/master, pero puede ser anulada usando la opción de línea de comandos --origin= .

Los cambios de p4 serán creados como el usuario que invoca git p4 submit. La opción --preserve-user hará que la propiedad sea modificada de acuerdo con el autor del commit de Git. Esta opción requiere privilegios de administrador en p4, que pueden ser otorgados usando p4 protect.

Para guardar cambios en un estante (shelve) en lugar de enviarlos, use --shelve y --update-shelve:

$ git p4 submit --shelve
$ git p4 submit --update-shelve 1234 --update-shelve 2345

Unshelve

Unshelving tomará una lista de cambios de P4 guardada en un estante, y producirá el commit de git equivalente en la rama refs/remotes/p4-unshelved/<lista-de-cambios>.

El commit de git es creado relativo a la revisión de origen actual (HEAD por defecto). Se crea un commit padre basado en el origen, y luego el commit de unshelve es creado basado en ese.

La revisión de origen puede ser cambiada con la opción "--origin".

Si la rama de destino en refs/remotes/p4-unshelved ya existe, la antigua será renombrada.

$ git p4 sync
$ git p4 unshelve 12345
$ git show p4-unshelved/12345
<enviar más cambios vía p4 a los mismos archivos>
$ git p4 unshelve 12345
<rechaza hacer unshelve hasta que git esté de nuevo en sincronía con p4>

Opciones generales

Todos los comandos excepto clone aceptan estas opciones.

Opciones de sincronización

Estas opciones pueden usarse en el clone inicial así como en operaciones posteriores de sync .

--branch <ref>

Importar cambios en <ref> en lugar de refs/remotes/p4/master. Si <ref> empieza con refs/, se usa tal cual. De lo contrario, si no empieza con p4/, se añade ese prefijo.

Por defecto, un <ref> que no empieza con refs/ es tratado como el nombre de una rama de seguimiento remoto (bajo refs/remotes/). Este comportamiento puede ser modificado usando la opción --import-local.

El <ref> por defecto es "master".

Este ejemplo importa un nuevo remoto "p4/proj2" en un repositorio Git existente:

    $ git init
    $ git p4 sync --branch=refs/remotes/p4/proj2 //depot/proj2

--detect-branches

Usar el algoritmo de detección de ramas para encontrar nuevas rutas en p4. Está documentado más abajo en "DETECCIÓN DE RAMAS".

--changesfile <archivo>

Importar exactamente los números de cambio de p4 listados en archivo, uno por línea. Normalmente, git p4 inspecciona el estado actual del repositorio p4 y detecta los cambios que debe importar.

--silent

No imprimir ninguna información de progreso.

git-p4.skipSubmitNote

By default, git p4 submit will add a note to the submitted changelist, stating that it was created from Git. Set this to "true" to disable this behaviour.

EXTENSIONS

git-p4 can be extended to support other version control systems beyond Perforce. This is done via extensions. Currently, only Git LFS is supported. See the documentation for EXTENSIONS(7) for more details.

EXAMPLES

Clone from p4 to git:

git p4 clone //depot/path/to/repo@all

Sync from p4 to an existing git repo:

git p4 sync

Submit from git to p4:

git p4 submit

GIT

Part of the git suite.

Variables para submit

git-p4.detectRenames

Detecta renombrados. Ver git-diff(1). Puede ser true, false, o una puntuación como la esperada por git diff -M.

git-p4.detectCopies

Detecta copias. Ver git-diff(1). Puede ser true, false, o una puntuación como la esperada por git diff -C.

git-p4.detectCopiesHarder

Detecta copias de forma más exhaustiva. Ver git-diff(1). Un booleano.

git-p4.preserveUser

Al hacer submit, reasigna los cambios para reflejar el autor de Git, independientemente de quién invoque git p4 submit.

git-p4.allowMissingP4Users

Cuando preserveUser es true, git p4 normalmente falla si no puede encontrar un usuario en el mapa de usuarios de p4. Esta configuración envía el cambio de todos modos.

git-p4.skipSubmitEdit

El proceso de submit invoca el editor antes de que cada cambio de p4 sea enviado. Si esta configuración es true, sin embargo, el paso de edición se omite.

git-p4.skipSubmitEditCheck

Después de editar el mensaje de cambio de p4, git p4 se asegura de que la descripción realmente se cambió comprobando la hora de modificación del archivo. Esta opción deshabilita esa prueba.

git-p4.allowSubmit

Por defecto, cualquier rama puede usarse como fuente para una operación git p4 submit. Esta variable de configuración, si está establecida, permite solo las ramas nombradas para ser usadas como fuentes de submit. Los nombres de rama deben ser los nombres cortos (sin "refs/heads/"), y deben separarse por comas (","), sin espacios.

git-p4.skipUserNameCheck

Si el usuario que ejecuta git p4 submit no existe en el mapa de usuarios de p4, git p4 sale. Esta opción se puede usar para forzar el envío independientemente.

git-p4.attemptRCSCleanup

Si está habilitado, git p4 submit intentará limpiar palabras clave RCS ($Header$, etc.). Estas de lo contrario causarían conflictos de fusión y impedirían que el submit se realizara. Esta opción debe considerarse experimental en este momento.

git-p4.exportLabels

Exporta etiquetas de Git a etiquetas de p4, como por --export-labels.

git-p4.labelExportRegexp

Solo las etiquetas de p4 que coincidan con esta expresión regular se exportarán. El valor predeterminado es [a-zA-Z0-9_\-.]+$.

git-p4.conflict

Especifica el comportamiento de submit cuando se encuentra un conflicto con p4, como por --conflict. El comportamiento predeterminado es ask.

git-p4.disableRebase

No hacer rebase del árbol contra p4/master después de un submit.

git-p4.disableP4Sync

No sincronizar p4/master con Perforce después de un submit. Implica git-p4.disableRebase.

DETALLES DE IMPLEMENTACIÓN

•Los cambios de p4 se importan usando Git fast-import.
•Clonar o sincronizar no requiere un cliente p4; los contenidos de los archivos se recopilan usando p4 print.
•Enviar requiere un cliente p4, que no está en la misma ubicación que el repositorio Git. Los parches se aplican, uno a la vez, a este cliente p4 y se envían desde allí.
•Cada commit importado por git p4 tiene una línea al final del mensaje de registro que indica la ubicación del depósito p4 y el número de cambio. Esta línea es utilizada por operaciones posteriores de git p4 sync para saber qué cambios de p4 son nuevos.
