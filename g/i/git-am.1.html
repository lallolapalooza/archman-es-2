--show-current-patch[=(diff|raw)]

Muestra el mensaje en el que git am se ha detenido debido a conflictos. Si se especifica raw, muestra el contenido sin procesar del mensaje de correo electrónico; si se especifica diff, muestra solo la parte del diff. El valor predeterminado es raw.

--allow-empty

Después de un fallo al aplicar un parche en un mensaje de correo electrónico de entrada que carece de parche, crea un commit vacío con el contenido del mensaje de correo electrónico como su mensaje de registro.

DISCUSIÓN

El nombre del autor del commit se toma de la línea "From: " del mensaje, y la fecha del autor del commit se toma de la línea "Date: " del mensaje. La línea "Subject: " se utiliza como título del commit, después de eliminar el prefijo común "[PATCH <cualquier cosa>]". Se supone que la línea "Subject: " describe de forma concisa de qué trata el commit en una sola línea de texto.

Las líneas "From: ", "Date: " y "Subject: " que inician el cuerpo anulan los valores correspondientes del nombre del autor y el título del commit tomados de las cabeceras.

El mensaje del commit se forma con el título tomado de "Subject: ", una línea en blanco y el cuerpo del mensaje hasta donde comienza el parche. Los espacios en blanco excesivos al final de cada línea se eliminan automáticamente.

Se espera que el parche esté en línea, siguiendo directamente el mensaje. Cualquier línea que tenga el formato:

• tres guiones y fin de línea, o
• una línea que comience con "diff -", o
• una línea que comience con "Index: "

se toma como el comienzo de un parche, y el mensaje de registro del commit se termina antes de la primera aparición de dicha línea.

Al invocar git am inicialmente, le proporciona los nombres de los buzones de correo a procesar. Al ver el primer parche que no se aplica, se interrumpe en el medio. Puede recuperarse de esto de una de dos maneras:

1.saltar el parche actual volviendo a ejecutar el comando con la opción --skip.
2.resolver manualmente el conflicto en el directorio de trabajo y actualizar el índice para llevarlo a un estado que debería haber producido el parche. Luego, ejecutar el comando con la opción --continue.

El comando se niega a procesar nuevos buzones de correo hasta que la operación actual haya finalizado, por lo que si decide empezar de nuevo desde cero, ejecute git am --abort antes de ejecutar el comando con los nombres de los buzones de correo.

Antes de que se apliquen los parches, ORIG_HEAD se establece en la punta de la rama actual. Esto es útil si tiene problemas con varios commits, como ejecutar git am en la rama incorrecta o un error en los commits que es más fácil de corregir cambiando el buzón de correo (por ejemplo, errores en las líneas "From:").

HOOKS

Este comando puede ejecutar los hooks applypatch-msg, pre-applypatch y post-applypatch. Consulte githooks(5) para obtener más información.

CONFIGURACIÓN

Todo lo que está debajo de esta línea en esta sección se incluye selectivamente de la documentación de git-config(1). El contenido es el mismo que el que se encuentra allí:

am.keepcr

Si es verdadero, git-am llamará a git-mailsplit para parches en formato mbox con el parámetro --keep-cr. En este caso, git-mailsplit no eliminará \r de las líneas que terminan con \r\n. Se puede anular proporcionando --no-keep-cr desde la línea de comandos. Consulte git-am(1), git-mailsplit(1).

am.threeWay

Por defecto, git am fallará si el parche no se aplica limpiamente. Cuando se establece en verdadero, esta configuración indica a git am que recurra a la fusión de 3 vías si el parche registra la identidad de los blobs a los que se supone que debe aplicarse y tenemos esos blobs disponibles localmente (equivalente a proporcionar la opción --3way desde la línea de comandos). El valor predeterminado es false. Consulte git-am(1).
