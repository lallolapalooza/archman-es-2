GIT-FILTER-BRANCH(1) Manual de Git GIT-FILTER-BRANCH(1)

NOMBRE

git-filter-branch - Reescribe ramas

SINOPSIS

git filter-branch [--setup <comando>] [--subdirectory-filter <directorio>]
        [--env-filter <comando>] [--tree-filter <comando>]
        [--index-filter <comando>] [--parent-filter <comando>]
        [--msg-filter <comando>] [--commit-filter <comando>]
        [--tag-name-filter <comando>] [--prune-empty]
        [--original <espacio-de-nombres>] [-d <directorio>] [-f | --force]
        [--state-branch <rama>] [--] [<opciones-de-rev-list>...]

ADVERTENCIA

git filter-branch tiene una plétora de trampas que pueden producir alteraciones no obvias de la reescritura de historial pretendida (y puede dejarte con poco tiempo para investigar tales problemas ya que tiene un rendimiento tan abismal). Estos problemas de seguridad y rendimiento no pueden corregirse de forma compatible con versiones anteriores y como tal, su uso no se recomienda. Por favor, usa una herramienta alternativa de filtrado de historial como git filter-repo[1]. Si aún necesitas usar git filter-branch, por favor lee cuidadosamente la sección llamada "SEGURIDAD" (y la sección llamada "RENDIMIENTO") para conocer las minas terrestres de filter-branch, y luego evita vigilante tantos de los peligros listados allí como sea razonablemente posible.

DESCRIPCIÓN

Te permite reescribir el historial de revisiones de Git reescribiendo las ramas mencionadas en las <opciones-de-rev-list>, aplicando filtros personalizados en cada revisión. Esos filtros pueden modificar cada árbol (por ejemplo, eliminando un archivo o ejecutando una reescritura perl en todos los archivos) o información sobre cada commit. De lo contrario, toda la información (incluyendo los tiempos de commit originales o información de fusión) será preservada.

El comando solo reescribirá las referencias positivas mencionadas en la línea de comandos (por ejemplo, si pasas a..b, solo b será reescrita). Si no especificas ningún filtro, los commits serán re-commiteados sin ningún cambio, lo cual normalmente no tendría efecto. Sin embargo, esto puede ser útil en el futuro para compensar algunos bugs de Git o similares, por lo tanto tal uso está permitido.

NOTA: Este comando honra el archivo .git/info/grafts y las referencias en el espacio de nombres refs/replace/ . Si tienes algún graft o referencias de reemplazo definidos, ejecutar este comando los hará permanentes.

ADVERTENCIA! El historial reescrito tendrá nombres de objetos diferentes para todos los objetos y no convergerá con la rama original. No podrás empujar y distribuir fácilmente la rama reescrita encima de la rama original. Por favor, no uses este comando si no conoces todas las implicaciones, y evita usarlo de todos modos, si un simple commit único bastaría para arreglar tu problema. (Consulta la sección "RECUPERÁNDOSE DE UN REBASE UPSTREAM" en git-rebase(1) para más información sobre reescribir historial publicado.)

Verifica siempre que la versión reescrita sea correcta: Las referencias originales, si son diferentes de las reescritas, serán almacenadas en el espacio de nombres refs/original/.

Ten en cuenta que ya que esta operación es muy costosa en E/S, podría ser una buena idea redirigir el directorio temporal fuera del disco con la opción -d , por ejemplo, en tmpfs. Se reporta que la aceleración es muy notable.

Filtros

Los filtros se aplican en el orden listado a continuación. El argumento <comando> siempre se evalúa en el contexto del shell usando el comando eval (con la notable excepción del filtro de commit, por razones técnicas). Antes de eso, la variable de entorno $GIT_COMMIT se establecerá para contener el id del commit que se está reescribiendo. También, GIT_AUTHOR_NAME, GIT_AUTHOR_EMAIL, GIT_AUTHOR_DATE, GIT_COMMITTER_NAME, GIT_COMMITTER_EMAIL, y GIT_COMMITTER_DATE se toman del commit actual y se exportan al entorno, para afectar las identidades del autor y committer del commit de reemplazo creado por git-commit-tree(1) después de que los filtros se hayan ejecutado.

Si cualquier evaluación de <comando> devuelve un estado de salida distinto de cero, toda la operación será abortada.

Una función map está disponible que toma un argumento "id sha1 original" y emite un "id sha1 reescrito" si el commit ya ha sido reescrito, y "id sha1 original" de lo contrario; la función map puede devolver varios ids en líneas separadas si tu filtro de commit emitió múltiples commits.

OPCIONES

--setup <comando>

Esto no es un filtro real ejecutado para cada commit sino una configuración única justo antes del bucle. Por lo tanto, aún no se han definido variables específicas del commit. Las funciones o variables definidas aquí pueden ser usadas o modificadas en los siguientes pasos de filtro excepto el filtro de commit, por razones técnicas.

--subdirectory-filter <directorio>

Solo mira el historial que toca el subdirectorio dado. El resultado contendrá ese directorio (y solo ese) como su raíz del proyecto. Implica la sección llamada "Remapear a ancestro".

--env-filter <comando>

Este filtro puede usarse si solo necesitas modificar el entorno en el que se realizará el commit. Específicamente, podrías querer reescribir las variables de entorno de nombre/email/fecha del autor/committer (consulta git-commit-tree(1) para detalles).

--tree-filter <comando>

Este es el filtro para reescribir el árbol y su contenido. El argumento se evalúa en el shell con el directorio de trabajo establecido en la raíz del árbol verificado. El nuevo árbol se usa tal cual (los archivos nuevos se añaden automáticamente, los archivos desaparecidos se eliminan automáticamente - ni los archivos .gitignore ni ninguna otra regla de ignorar TIENEN NINGÚN EFECTO!).

--index-filter <comando>

Este es el filtro para reescribir el índice. Es similar al filtro de árbol pero no verifica el árbol, lo que lo hace mucho más rápido. Usado frecuentemente con git rm --cached --ignore-unmatch ..., consulta EJEMPLOS abajo. Para casos complicados, consulta git-update-index(1).

--parent-filter <comando>

Este es el filtro para reescribir la lista de padres del commit. Recibirá la cadena de padres en stdin y debe emitir la nueva cadena de padres en stdout. La cadena de padres está en el formato descrito en git-commit-tree(1): vacía para el commit inicial, "-p padre" para un commit normal y "-p padre1 -p padre2 -p padre3 ..." para un commit de fusión.

--msg-filter <comando>

Este es el filtro para reescribir los mensajes de commit. El argumento se evalúa en el shell con el mensaje de commit original en la entrada estándar; su salida estándar se usa como el nuevo mensaje de commit.

--commit-filter <comando>

Este es el filtro para realizar el commit. Si este filtro se especifica, será llamado en lugar del comando git commit-tree , con argumentos de la forma "<ID_DE_ÁRBOL> [(-p <ID_DE_COMMIT_PADRE>)...]" y el mensaje de log en stdin. Se espera que el id del commit esté en stdout.

Como una extensión especial, el filtro de commit puede emitir múltiples ids de commit; en ese caso, los hijos reescritos del commit original tendrán todos ellos como padres.

Puedes usar la función conveniente map en este filtro, y otras funciones convenientes también. Por ejemplo, llamar skip_commit "$@" omitirá el commit actual (¡pero no sus cambios! Si quieres eso, usa git rebase en su lugar).

También puedes usar git_commit_non_empty_tree "$@" en lugar de git commit-tree "$@" si no deseas conservar commits con un solo padre que no hacen ningún cambio al árbol.

--tag-name-filter <comando>

Este es el filtro para reescribir nombres de etiquetas. Cuando se pasa, será llamado para cada ref de etiqueta que apunte a un objeto reescrito (o a un objeto de etiqueta que apunte a un objeto reescrito). El nombre de etiqueta original se pasa vía la entrada estándar, y se espera el nuevo nombre de etiqueta en la salida estándar.

Las etiquetas originales no se eliminan, pero pueden ser sobrescritas; usa "--tag-name-filter cat" para simplemente actualizar las etiquetas. En este caso, ten mucho cuidado y asegúrate de tener las etiquetas antiguas respaldadas en caso de que la conversión haya fallado.

Reescritura casi correcta de etiquetas objetos está soportado. Si la etiqueta tiene un mensaje adjunto, se creará un nuevo objeto de etiqueta con el mismo mensaje, autor y marca de tiempo. Si la etiqueta tiene una firma adjunta, la firma será eliminada. Por definición es imposible pre

servar firmas. La razón por la que esto es "casi" correcto, es porque idealmente, si la etiqueta no cambió (apunta al mismo objeto, tiene el mismo nombre, etc.), debería conservar cualquier firma. Ese no es el caso, las firmas serán siempre elimin
adas, comprador a la vista. Tampoco hay soporte para cambiar el autor o la marca de tiempo (o el mensaje de la etiqueta por ese motivo). Las etiquetas que apuntan a otras etiquetas serán reescritas para apuntar al commit subyacente. --prune-empty

RENDIMIENTO

El rendimiento de git-filter-branch es glacialmente lento; su diseño hace imposible que una implementación compatible con versiones anteriores sea rápida:

•Al editar archivos, git-filter-branch por diseño hace checkout de cada y todos los commits tal como existían en el repositorio original. Si tu repositorio tiene 10^5 archivos y 10^5 commits, pero cada commit solo modifica cinco archivos, entonces git-filter-branch te hará hacer 10^10 modificaciones, a pesar de tener solo (como máximo) 5*10^5 blobs únicos.
•Si intentas hacer trampa e intentas hacer que git-filter-branch solo trabaje en archivos modificados en un commit, entonces dos cosas suceden
•te encuentras con problemas con eliminaciones siempre que el usuario simplemente esté intentando renombrar archivos (porque intentar eliminar archivos que no existen parece ser una operación sin efecto; se requiere algo de astucia para remapear eliminaciones a través de renombrados de archivos cuando los renombrados ocurren a través de shell arbitrario proporcionado por el usuario)
•incluso si tienes éxito con la astucia de remapear-eliminaciones-para-renombrados, técnicamente aún violas la compatibilidad con versiones anteriores porque a los usuarios se les permite filtrar archivos de maneras que dependen de la topología de los commits en lugar de filtrar únicamente basándose en el contenido de los archivos o sus nombres (aunque esto no se ha observado en la práctica).
•Incluso si no necesitas editar archivos pero solo quieres, por ejemplo, renombrar o remover algunos y así evitar hacer checkout de cada archivo (es decir, puedes usar --index-filter), aún estás pasando fragmentos de shell para tus filtros. Esto significa que para cada commit, tienes que tener un repositorio git preparado donde esos filtros puedan ejecutarse. Eso es una configuración significativa.
•Además, varios archivos adicionales son creados o actualizados por commit por git-filter-branch. Algunos de estos son para soportar las funciones de conveniencia proporcionadas por git-filter-branch (como map()), mientras que otros son para mantener el seguimiento del estado interno (pero podrían haber sido también accedidos por filtros de usuario; una de las pruebas de regresión de git-filter-branch lo hace). Esto esencialmente equivale a usar el sistema de archivos como un mecanismo de IPC entre git-filter-branch y los filtros proporcionados por el usuario. Los discos tienden a ser un mecanismo de IPC lento, y escribir estos archivos también representa efectivamente un punto de sincronización forzado entre procesos separados que alcanzamos con cada commit.
•Los comandos de shell proporcionados por el usuario probablemente involucrarán una canalización (pipeline) de comandos, resultando en la creación de muchos procesos por commit. Crear y ejecutar otro proceso toma una cantidad de tiempo que varía ampliamente entre sistemas operativos, pero en cualquier plataforma es muy lento en comparación con invocar una función.
•git-filter-branch en sí mismo está escrito en shell, lo cual es algo lento. Este es el único problema de rendimiento que podría arreglarse de forma compatible con versiones anteriores, pero comparado con los problemas anteriores que son intrínsecos al diseño de git-filter-branch, el lenguaje de la herramienta en sí es un problema relativamente menor.
•Nota lateral: Desafortunadamente, la gente tiende a fijarse en el aspecto de estar-escrito-en-shell y periódicamente pregunta si git-filter-branch podría ser reescrito en otro lenguaje para arreglar los problemas de rendimiento. No solo eso ignora los problemas intrínsecos más grandes con el diseño, ayudaría menos de lo que esperarías: si git-filter-branch en sí no fuera shell, entonces las funciones de conveniencia (map(), skip_commit(), etc) y el --setup argumento ya no podrían ejecutarse una sola vez al principio del programa, sino que en su lugar necesitarían ser anteponidos a cada filtro de usuario (y así re-ejecutarse con cada commit).

La git filter-repo[1] herramienta es una alternativa a git-filter-branch que no sufre de estos problemas de rendimiento o de los problemas de seguridad (mencionados más abajo). Para aquellos con herramientas existentes que dependen de git-filter-branch, git filter-repo también proporciona filter-lamely[2], un reemplazo directo de git-filter-branch (con algunas advertencias). Aunque filter-lamely sufre de todos los mismos problemas de seguridad que git-filter-branch, al menos alivia un poco los problemas de rendimiento.

SEGURIDAD

git-filter-branch está lleno de trampas resultando en varias formas de corromper fácilmente repositorios o terminar con un desastre peor que el que empezaste:

•Alguien puede tener un conjunto de "filtros que funcionan y están probados" que documenta o proporciona a un compañero de trabajo, quien entonces los ejecuta en un sistema operativo diferente donde los mismos comandos no funcionan/no están probados (algunos ejemplos en el manual de git-filter-branch también se ven afectados por esto). Las diferencias entre el entorno de usuario BSD y GNU pueden doler mucho. Con suerte, se arrojan mensajes de error. Pero igualmente probablemente, los comandos o bien no hacen el filtrado solicitado, o corrompen silenciosamente haciendo algún cambio no deseado. El cambio no deseado puede afectar solo a unos pocos commits, así que no es necesariamente obvio tampoco. (El hecho de que los problemas no sean necesariamente obvios significa que es probable que pasen desapercibidos hasta que el historial reescrito se haya estado usando por bastante tiempo, momento en el que es realmente difícil justificar otro día de bandera para otra reescritura.)
•Los nombres de archivo con espacios a menudo son manejados incorrectamente por fragmentos de shell ya que causan problemas para las canalizaciones de shell. No todo el mundo está familiarizado con find -print0, xargs -0, git-ls-files -z, etc. Incluso la gente que está familiarizada con estos puede asumir que tales banderas no son relevantes porque alguien más renombró cualquier archivo de ese tipo en su repositorio antes de que la persona haciendo el filtrado se uniera al proyecto. Y a menudo, incluso aquellos familiarizados con el manejo de argumentos con espacios pueden no hacerlo simplemente porque no están en la mentalidad de pensar en todo lo que podría salir mal.
•Los nombres de archivo no-ascii pueden ser removidos silenciosamente a pesar de estar en un directorio deseado. Mantener solo las rutas deseadas a menudo se hace usando canalizaciones como git ls-files | grep -v ^WANTED_DIR/ | xargs git rm. ls-files solo comillará los nombres de archivo si es necesario, así que la gente puede no notar que uno de los archivos no coincidió con la expresión regular (al menos no hasta que sea demasiado tarde). Sí, alguien que conoce core.quotePath puede evitar esto (a menos que tengan otros caracteres especiales como \t, \n, o "), y la gente que usa ls-files -z con algo que no sea grep puede evitar esto, pero eso no significa que lo harán.
•De manera similar, al mover archivos de un lado a otro, se puede encontrar que nombres de archivo con caracteres no-ascii o especiales terminan en un directorio diferente, uno que incluye un carácter de comilla doble. (Esto técnicamente es el mismo problema de arriba con el comillado, pero quizás una manera diferente e interesante en que puede y ha manifestado como un problema.)
•Es demasiado fácil mezclar accidentalmente el historial viejo y el nuevo. Todavía es posible con cualquier herramienta, pero git-filter-branch casi lo invita. Con suerte, la única desventaja es que los usuarios se frustran porque no saben cómo reducir su repositorio y remover lo viejo. Si no tienen suerte, mezclan el historial viejo y el nuevo y terminan con múltiples "copias" de cada commit, algunas de las cuales tienen archivos no deseados o sensibles y otras que no. Esto surge de múltiples maneras diferentes:
•el valor por defecto de hacer solo una reescritura parcial del historial (--all no es el valor por defecto y pocos ejemplos lo muestran)
•el hecho de que no haya una limpieza automática post-ejecución
•el hecho de que --tag-name-filter (cuando se usa para renombrar etiquetas) no remueve las etiquetas viejas sino que solo añade nuevas con el nuevo nombre
•el hecho de que se proporciona poca información educativa para informar a los usuarios de las ramificaciones de una reescritura y cómo evitar mezclar el historial viejo y el nuevo. Por ejemplo, esta página del manual discute cómo los usuarios necesitan entender que necesitan hacer rebase de sus cambios para todas sus ramas sobre el nuevo historial (o eliminar y volver a clonar), pero eso es solo una de múltiples preocupaciones a considerar. Ver la sección "DISCUSIÓN" de la página del manual de git filter-repo para más detalles.
•Las etiquetas anotadas pueden ser convertidas accidentalmente a etiquetas ligeras, debido a cualquiera de dos problemas:
•Alguien puede hacer una reescritura de historial, darse cuenta de que la cagó, restaurar desde las copias de seguridad en refs/original/, y luego rehacer su comando de git-filter-branch. (La copia de seguridad en refs/original/ no es una copia de seguridad real; desreferencia las etiquetas primero.)
•Ejecutar git-filter-branch con --tags o --all en tus <rev-list-options>. Para retener las etiquetas anotadas como anotadas, debes usar --tag-name-filter (y no debes haber restaurado desde refs/original/ en una reescritura previamente arruinada).
•Cualquier mensaje de commit que especifique una codificación será corrompido por la reescritura; git-filter-branch ignora la codificación, toma los bytes originales, y los alimenta a commit-tree sin decirle la codificación correcta. (Esto sucede tanto si se usa --msg-filter como si no.)
•Los mensajes de commit (incluso si todos son UTF-8) por defecto se corrompen al no ser actualizados — cualquier referencia a otros hashes de commit en los mensajes de commit ahora referenciarán commits que ya no existen.
•No hay facilidades para ayudar a los usuarios a encontrar qué basura no deseada deberían eliminar, lo que significa que es mucho más probable que tengan limpiezas incompletas o parciales que a veces resultan en confusión y gente perdiendo tiempo intentando entender. (Por ejemplo, la gente tiende a buscar archivos grandes para eliminar en lugar de directorios grandes o extensiones, y una vez que lo hacen, entonces más tarde la gente usando el nuevo repositorio que está revisando el historial notará un directorio de artefactos de compilación que tiene algunos archivos pero no otros, o una caché de dependencias (node_modules o similar) que no podría haber funcionado nunca ya que le faltan algunos archivos.)
•Si --prune-empty no se especifica, entonces el proceso de filtrado puede crear hordas de commits vacíos confusos
•Si --prune-empty se especifica, entonces los commits vacíos colocados intencionalmente antes de la operación de filtrado también son podados en lugar de podar solo los commits que se volvieron vacíos debido a las reglas de filtrado.
•Si --prune-empty se especifica, a veces los commits vacíos se dejan pasar y quedan alrededor (un bug algo raro, pero sucede...)
•Un problema menor, pero los usuarios que tienen como objetivo actualizar todos los nombres y correos electrónicos en un repositorio pueden llevó a `--env-filter` que solo actualizará autores y commmitters, omitiendo los taggers.
•Si el usuario proporciona un `--tag-name-filter` que mapea múltiples etiquetas al mismo nombre, no se proporciona advertencia ni error; `git-filter-branch` simplemente sobrescribe cada etiqueta en un orden predefinido no documentado, resultando en una sola etiqueta al final. (Una prueba de regresión de `git-filter-branch` requiere este comportamiento sorprendente).

Además, el bajo rendimiento de `git-filter-branch` a menudo conduce a problemas de seguridad:

•Elaborar el fragmento de shell correcto para filtrar lo que deseas a veces es difícil a menos que solo estés haciendo una modificación trivial, como eliminar un par de archivos. Desafortunadamente, las personas a menudo aprenden si el fragmento es correcto o incorrecto al probarlo, pero la corrección o incorrección puede variar según las circunstancias especiales (espacios en nombres de archivos, nombres de archivos no ASCII, nombres o correos electrónicos de autor extraños, zonas horarias inválidas, presencia de injertos u objetos de reemplazo, etc.), lo que significa que pueden tener que esperar mucho tiempo, encontrar un error y luego reiniciar. El rendimiento de `git-filter-branch` es tan malo que este ciclo es doloroso, reduciendo el tiempo disponible para volver a verificar cuidadosamente (por no mencionar lo que le hace a la paciencia de la persona que realiza la reescritura, incluso si técnicamente tiene más tiempo disponible). Este problema se agrava porque los errores de filtros rotos pueden no mostrarse durante mucho tiempo y/o perderse en un mar de salida. Peor aún, los filtros rotos a menudo solo resultan en reescrituras incorrectas y silenciosas.
•Para colmo, incluso cuando los usuarios finalmente encuentran comandos que funcionan, naturalmente quieren compartirlos. Pero es posible que no se den cuenta de que su repositorio no tenía algunos casos especiales que sí tiene el de otra persona. Entonces, cuando otra persona con un repositorio diferente ejecuta los mismos comandos, se encuentra con los problemas anteriores. O, el usuario simplemente ejecuta comandos que realmente fueron revisados para casos especiales, pero los ejecuta en un sistema operativo diferente donde no funcionan, como se mencionó anteriormente.
