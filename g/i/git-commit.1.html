EJEMPLO

S

Al registrar tu propio trabajo, el contenido de los archivos modificados en tu árbol de trabajo se almacena temporalmente en un área de preparación llamada el "índice" con git add. Un archivo puede ser revertido, solo en el índice pero no en el árbol de trabajo, al de la última confirmación con git restore --staged <file>, que revierte efectivamente git add e impide que los cambios en este archivo participen en la siguiente confirmación. Después de construir el estado a confirmar incrementalmente con estos comandos, git commit (sin ningún parámetro de nombre de ruta) se usa para registrar lo que se ha preparado hasta ahora. Esta es la forma más básica del comando. Un

ejemplo: 
$ edit hello.c
$ git
rm goodbye.c $ git add
hello.c $ git commit

En lugar de preparar archivos después de cada cambio individual, puedes decirle a git commit que note los cambios en los archivos cuyo contenido está rastreado en tu árbol de trabajo y haga el git add y git rm correspondiente por ti. Es decir, este ejemplo hace lo mismo que el ejemplo anterior si no hay ningún otro cambio en tu árbol de

trabajo: 
$ edit hello.c
$ rm goodbye.c
$ git commit -a

El comando git commit -a primero mira tu árbol de trabajo, nota que has modificado hello.c y eliminado goodbye.c, y realiza el git add y git rm necesarios por

ti.

Después de preparar cambios en muchos archivos, puedes alterar el orden en que se registran los cambios, dando nombres de ruta a git commit. Cuando se dan nombres de ruta, el comando hace una confirmación que solo registra los cambios hechos a las rutas

nombradas: 
$ edit hello.c hello.h
$ git
add hello.c hello.h $ edit M
akefile $ git commit Makefile

Esto hace una confirmación que registra la modificación a Makefile. Los cambios preparados para hello.c y hello.h no se incluyen en la confirmación resultante. Sin embargo, sus cambios no se pierden — siguen preparados y simplemente se retienen. Después de la secuencia anterior, si

haces: 
$ gi
t co
mmit

esta segunda confirmación registraría los cambios a hello.c y hello.h como se

esperaba.

Después de una fusión (iniciada por git merge o git pull) se detiene debido a conflictos, las rutas fusionadas limpiamente ya están preparadas para ser confirmadas por ti, y las rutas que entraron en conflicto se dejan en estado sin fusionar. Tendrías que primero comprobar qué rutas están en conflicto con git status y después de arreglarlas manualmente en tu árbol de trabajo, prepararías el resultado como de costumbre con git add

: 
$ git status | grep unmerg
ed unmerged: hello.c $ edit
hello.c $ git add hello.c

Después de resolver los conflictos y preparar el resultado, git ls-files -u dejaría de mencionar la ruta en conflicto. Cuando termines, ejecuta git commit para finalmente registrar la

fusión: 
$ gi
t co
mmit

Al igual que en el caso de registrar tus propios cambios, puedes usar la opción -a para ahorrar tecleo. Una diferencia es que durante una resolución de fusión, no puedes usar git commit con nombres de ruta para alterar el orden en que se confirman los cambios, porque la fusión debe registrarse como una sola confirmación. De hecho, el comando se niega a ejecutarse cuando se le dan nombres de ruta (pero consulta la opción

Formato interno de

Git
Es <unix-timestamp> <time-zone-offset>, donde <unix-timestamp> es el número de segundos desde la época UNIX. <time-zone-offset> es un desplazamiento positivo o negativo desde UTC. Por ejemplo CET (que está 1 hora por delante de UTC) es +0100

DISCUSIÓ

N

Aunque no es obligatorio, es una buena idea comenzar el mensaje de confirmación con una sola línea corta (no más de 50 caracteres) que resuma el cambio, seguida de una línea en blanco y luego una descripción más detallada. El texto hasta la primera línea en blanco en un mensaje de confirmación se trata como el título de la confirmación, y ese título se usa en todo Git. Por ejemplo, git-format-patch(1) convierte una confirmación en correo electrónico, y usa el título en la línea Asunto y el resto de la confirmación en el

cuerpo.

Git es hasta cierto punto agnóstico a la codificación de

caracteres.
•El contenido de los objetos blob son secuencias de bytes sin interpretar. No hay traducción de codificación a nivel del
núcleo.
•Los nombres de ruta se codifican en la forma de normalización UTF-8 C. Esto se aplica a los objetos árbol, el archivo índice, los nombres de ref, así como los nombres de ruta en argumentos de línea de comandos, variables de entorno y archivos de configuración (.git/config (consulta git-config(1)), gitignore(5), gitattributes(5) y gitmodules(5)).

Ten en cuenta que Git a nivel del núcleo trata los nombres de ruta simplemente como secuencias de bytes no-NUL, no hay conversiones de codificación de nombres de ruta (excepto en Mac y Windows). Por lo tanto, el uso de nombre

s de ruta no-ASCII funcionará en su mayoría incluso en plataformas y sistemas de archivos que usan codificaciones ASCII extendidas heredadas. Sin embargo, los repositorios creados en tales sistemas no funcionarán correctamente
en sistemas basados en UTF-8 (p. ej. Linux, Mac, Windows) y viceversa. Además, muchas herramientas basadas en Git simplemente asumen que los nombres de ruta son UTF-8 y fallarán al mostrar otras codificaciones correctamente.
•Los mensajes de registro de confirmación se codifican típicamente en UTF-8, pero también se soportan otras codificaciones ASCII extendidas. Esto incluye ISO-8859-x, CP125x y muchas otras, pero no UTF-16/32, EBCDIC y codificaciones multibyte CJK (GBK, Shift-JIS, Big5, EUC-x, CP9xx etc.)
.

Aunque animamos a que los mensajes de registro de confirmación se codifiquen en UTF-8, tanto el núcleo como Git Porcelain están diseñados para no forzar UTF-8 en proyectos. cuenta.
