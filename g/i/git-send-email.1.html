--smtp-encryption=<cifrado>

Especifica la forma en que comienza el cifrado para la conexión SMTP. Los valores válidos son ssl y tls. Cualquier otro valor revertirá al SMTP plano (sin cifrar), que usa el puerto 25 por defecto. A pesar de los nombres, ambos valores utilizarán la misma versión más reciente de TLS, pero por razones históricas tienen estos nombres. ssl se refiere al cifrado "implícito" (a veces llamado SMTPS), que utiliza el puerto 465 por defecto. tls se refiere al cifrado "explícito" (a menudo conocido como STARTTLS), que utiliza el puerto 25 por defecto. Otros puertos pueden ser utilizados por el servidor SMTP, que no son los predeterminados. Un puerto alternativo común para tls y sin cifrar es el 587. Debe consultar la documentación de su proveedor o la configuración de su servidor para asegurarse de su caso particular. El valor por defecto es el valor de sendemail.smtpEncryption.

--smtp-domain=<FQDN>

Especifica el Nombre de Dominio Completamente Calificado (FQDN) utilizado en el comando HELO/EHLO al servidor SMTP. Algunos servidores requieren que el FQDN coincida con su dirección IP. Si no se establece, git send-email intenta determinar su FQDN automáticamente. El valor por defecto es el valor de sendemail.smtpDomain.

--smtp-auth=<mecanismos>

Lista separada por espacios en blanco de mecanismos SMTP-AUTH permitidos. Esta configuración fuerza el uso exclusivo de los mecanismos listados. Ejemplo: 
$ git send-email --smtp-auth="PLAIN LOGIN GSSAPI" ...

Si al menos uno de los mecanismos especificados coincide con los anunciados por el servidor SMTP y si es compatible con la biblioteca SASL utilizada, se utiliza el mecanismo para la autenticación. Si no se especifica ni sendemail.smtpAuth ni --smtp-auth, se pueden utilizar todos los mecanismos soportados por la biblioteca SASL. El valor especial none puede especificarse para deshabilitar completamente la autenticación independientemente de --smtp-user.

--smtp-pass[=<contraseña>]

Contraseña para SMTP-AUTH. El argumento es opcional: si no se especifica ningún argumento, se utiliza la cadena vacía como contraseña. El valor por defecto es el valor de sendemail.smtpPass, sin embargo --smtp-pass siempre anula este valor.

Además, las contraseñas no necesitan especificarse en archivos de configuración o en la línea de comandos. Si se ha especificado un nombre de usuario (con --smtp-user o sendemail.smtpUser), pero no se ha especificado ninguna contraseña (con --smtp-pass o sendemail.smtpPass), entonces se obtiene una contraseña utilizando git-credential(1).

--no-smtp-auth

Deshabilita la autenticación SMTP. Abreviatura de --smtp-auth=none.

--smtp-server=<host>

Si se establece, especifica el servidor SMTP de salida a utilizar (por ejemplo, smtp.example.com o una dirección IP directa). Si no se especifica, y si --sendmail-cmd también está sin especificar, el valor por defecto es buscar sendmail en /usr/sbin, /usr/lib y $PATH si dicho programa está disponible, recurriendo a localhost en caso contrario.

Por compatibilidad con versiones anteriores, esta opción también puede especificar la ruta completa de un programa similar a sendmail; el programa debe soportar la opción -i. Este método no admite el paso de argumentos ni el uso de nombres de comandos simples. Para esos casos de uso, considere usar --sendmail-cmd en su lugar.

--smtp-server-port=<puerto>

Especifica un puerto diferente del puerto por defecto (los servidores SMTP suelen escuchar en el puerto smtp 25, pero también pueden escuchar en el puerto de envío 587, o en el puerto común de SSL smtp 465); también se aceptan nombres de puertos simbólicos (por ejemplo, submission en lugar de 587). El puerto también se puede configurar con la variable de configuración sendemail.smtpServerPort.

--smtp-server-option=<opción>

Si se establece, especifica la opción del servidor SMTP de salida a utilizar. El valor por defecto se puede especificar mediante la opción de configuración sendemail.smtpServerOption.

La opción --smtp-server-option debe repetirse para cada opción que desee pasar al servidor. Del mismo modo, se deben utilizar líneas diferentes en los archivos de configuración para cada opción.

--smtp-ssl

Alias obsoleto para --smtp-encryption ssl.

--smtp-ssl-cert-path

Ruta a un almacén de certificados CA de confianza para la validación de certificados SSL/TLS SMTP (ya sea un directorio que ha sido procesado por c_rehash, o un solo archivo que contiene uno o más certificados en formato PEM concatenados: consulte la descripción de las opciones -CAfile <archivo> y -CApath <dir> de https://docs.openssl.org/master/man1/openssl-verify/ [la página del manual de verify(1) de OpenSSL] para más información sobre estos). Establézcalo a una cadena vacía para deshabilitar la validación del certificado. Por defecto, es el valor de la variable de configuración sendemail.smtpSSLCertPath, si está establecida, o el valor por defecto compilado en la biblioteca SSL subyacente en caso contrario (que debería ser la mejor opción en la mayoría de las plataformas).

--smtp-user=<usuario>

Nombre de usuario para SMTP-AUTH. Por defecto es el valor de sendemail.smtpUser; si no se especifica un nombre de usuario (con --smtp-user o sendemail.smtpUser), no se intentará la autenticación.

--smtp-debug=(0|1)

Habilita (1) o deshabilita (0) la salida de depuración. Si está habilitada, se imprimirán los comandos y respuestas SMTP. Útil para depurar problemas de conexión TLS y autenticación.

--imap-sent-folder=<carpeta>

Algunos proveedores de correo electrónico (por ejemplo, iCloud) no envían una copia de los correos electrónicos enviados usando SMTP a la carpeta Sent o similar en su buzón. Utilice esta opción para usar git imap-send para enviar una copia de los correos electrónicos a la carpeta especificada con esta opción. Puede ejecutar git imap-send --list para obtener una lista de nombres de carpetas válidos, incluido el nombre correcto de la carpeta Sent en su buzón. También puede utilizar esta opción para enviar correos electrónicos a una carpeta IMAP dedicada de su elección.

Esta función requiere configurar git imap-send. Consulte git-imap-send(1) para obtener instrucciones.

--use-imap-only, --no-use-imap-only

Si esto está establecido, todos los correos electrónicos solo se copiarán en la carpeta IMAP especificada con --imap-sent-folder o sendemail.imapSentFolder y no se enviarán a los destinatarios. Útil si solo desea crear un borrador de los correos electrónicos y utilizar otro cliente de correo para enviarlos. Si se deshabilita con --no-use-imap-only, los correos electrónicos se enviarán como de costumbre. Deshabilitado por defecto, pero la variable de configuración sendemail.useImapOnly se puede utilizar para habilitarlo.

+ Esta función requiere configurar git imap-send. Consulte git-imap-send(1) para obtener instrucciones.

--batch-size=<num>

Algunos servidores de correo electrónico (por ejemplo, smtp.163.com) limitan el número de correos electrónicos que se pueden enviar por sesión (conexión) y esto provocará un error al enviar muchos mensajes. Con esta opción, send-email se desconectará después de enviar <num> mensajes y esperará unos segundos (ver --relogin-delay) y se reconectará, para solucionar tal limitación. Es posible que desee utilizar alguna forma de ayudante de credenciales para evitar tener que volver a escribir su contraseña cada vez que esto ocurra. Por defecto, es la variable de configuración sendemail.smtpBatchSize.

--relogin-delay=<int>

Espera <int> segundos antes de reconectar al servidor SMTP. Se utiliza junto con la opción --batch-size. Por defecto, es la variable de configuración sendemail.smtpReloginDelay.

Automatizar

--no-to, --no-cc, --no-bcc

Borra cualquier lista de direcciones To:, Cc:, Bcc: establecida previamente a través de la configuración.

--no-identity

Borra el valor previamente leído de sendemail.identity establecido a través de la configuración, si lo hubiera.

--to-cmd=<comando>

Especifica un comando a ejecutar por cada archivo de parche que debería generar entradas To: específicas del archivo de parche. La salida de este comando debe ser una única dirección de correo electrónico por línea. Por defecto, es el valor de la configuración sendemail.toCmd.

--cc-cmd=<comando>

Especifica un comando a ejecutar por cada archivo de parche que debería generar entradas Cc: específicas del archivo de parche. La salida de este comando debe ser una única dirección de correo electrónico por línea. Por defecto, es el valor de la configuración sendemail.ccCmd.

--header-cmd=<comando>

Especifica un comando que se ejecuta una vez por cada mensaje saliente y genera líneas de encabezado estilo RFC 2822 para insertarlas en ellos. Cuando la variable de configuración sendemail.headerCmd está establecida, su valor siempre se utiliza. Cuando se proporciona --header-cmd en la línea de comandos, su valor tiene prioridad sobre la variable de configuración sendemail.headerCmd.

--no-header-cmd

Deshabilita cualquier comando de encabezado en uso.

--chain-reply-to, --no-chain-reply-to

Si esto está establecido, cada correo electrónico se enviará como respuesta al correo electrónico anterior enviado. Si se deshabilita con --no-chain-reply-to, todos los correos electrónicos después del primero se enviarán como respuesta al primer correo electrónico enviado. Al usar esto, se recomienda que el primer archivo proporcionado sea una visión general de toda la serie de parches. Deshabilitado por defecto, pero la variable de configuración sendemail.chainReplyTo se puede utilizar para habilitarlo.

--identity=<identidad>

Una identidad de configuración. Cuando se proporciona, hace que los valores de la subsección sendemail.<identidad> tengan prioridad sobre los valores de la sección sendemail. La identidad por defecto es el valor de sendemail.identity.

--signed-off-by-cc, --no-signed-off-by-cc

Si esto está establecido, añade correos electrónicos encontrados en el sufijo Signed-off-by o en las líneas Cc: a la lista de cc. Por defecto, es el valor de la configuración sendemail.signedOffByCc; si no se especifica, por defecto es --signed-off-by-cc.

--cc-cover, --no-cc-cover

Si esto está establecido, los correos electrónicos encontrados en los encabezados Cc: del primer parche de la serie (típicamente la carta de presentación) se añaden a la lista de cc para cada conjunto de correos electrónicos. Por defecto, es el valor de la configuración sendemail.ccCover; si no se especifica, por defecto es --no-cc-cover.

--to-cover, --no-to-cover

Si esto está establecido, los correos electrónicos encontrados en los encabezados To: del primer parche de la serie (típicamente la carta de presentación) se añaden a la lista de destinatarios para cada conjunto de correos electrónicos. Por defecto, es el valor de la configuración sendemail.toCover; si no se especifica, por defecto es --no-to-cover.

--suppress-cc=<categoría>

•author evitará incluir al autor del parche.
•self evitará incluir al remitente.
•cc evitará incluir a cualquiera mencionado en líneas Cc en el encabezado del parche excepto a uno mismo (utilice self para eso).
•bodycc evitará incluir a cualquiera mencionado en líneas Cc en el cuerpo del parche (mensaje de confirmación) excepto a uno mismo (utilice self para eso).
•sob evitará incluir a cualquiera mencionado en los trailers Signed-off-by excepto a uno mismo (utilice self para eso).
•misc-by evitará incluir a cualquiera mencionado en líneas Acked-by, Reviewed-by, Tested-by y otras líneas "-by" en el cuerpo del parche, excepto Signed-off-by (utilice sob para eso).
•cccmd evitará ejecutar el --cc-cmd.
•body es equivalente a sob + bodycc + misc-by.
•all suprimirá todos los valores de auto cc.

El valor por defecto es el valor de sendemail.suppressCc de configuración ; si no está especificado, el valor por defecto es self si --suppress-from está especificado, así como body si --no-signed-off-cc está especificado.

--suppress-from, --no-suppress-from

Si esto está establecido, no se añade la dirección From: a la lista Cc: . El valor por defecto es el valor de sendemail.suppressFrom de configuración; si no está especificado, el valor por defecto es --no-suppress-from.

--thread, --no-thread

Si esto está establecido, se añadirán las cabeceras In-Reply-To y References a cada correo electrónico enviado. Si cada correo se refiere al correo electrónico anterior (deep threading según la terminología de git format-patch ) o al primer correo electrónico (shallow threading) está gobernado por --[no-]chain-reply-to.

Si se deshabilita con --no-thread, esas cabeceras no se añadirán (a menos que se especifique con --in-reply-to). El valor por defecto es el valor de la configuración sendemail.thread ; si no está especificado, el valor por defecto es --thread.

Corresponde al usuario asegurarse de que no exista ya una cabecera In-Reply-To cuando se le pide a git send-email que la añada (teniendo especialmente en cuenta que git format-patch puede configurarse para hacer el threading él mismo). El no hacerlo puede no producir el resultado esperado en el MUA del destinatario.

--mailmap, --no-mailmap

Usar el archivo mailmap (ver gitmailmap(5)) para mapear todas las direcciones a su nombre real canónico y dirección de correo electrónico. Se pueden proporcionar datos adicionales de mailmap específicos de git send-email utilizando los valores de configuración sendemail.mailmap.file o sendemail.mailmap.blob . El valor por defecto es sendemail.mailmap.

Administración

--confirm=<mode>

Confirmar justo antes de enviar:
•always siempre confirmará antes de enviar.
•never nunca confirmará antes de enviar.
•cc confirmará antes de enviar cuando send-email haya añadido automáticamente direcciones del parche a la lista Cc.
•compose confirmará antes de enviar el primer mensaje al usar --compose.
•auto es equivalente a cc + compose.

El valor por defecto es el valor de sendemail.confirm de configuración ; si no está especificado, el valor por defecto es auto a menos que se hayan especificado alguna de las opciones de supresión, en cuyo caso el valor por defecto es compose.

--dry-run

Hacer todo excepto enviar realmente los correos electrónicos.

--format-patch, --no-format-patch

Cuando un argumento pueda entenderse tanto como una referencia como un nombre de archivo, elegir entenderlo como un argumento de format-patch (--format-patch) o como un nombre de archivo (--no-format-patch). Por defecto, cuando ocurre tal conflicto, git send-email fallará.

--quiet

Hacer que git send-email sea menos detallado. Debería emitirse solo una línea por correo electrónico.

--validate, --no-validate

Realizar comprobaciones de integridad en los parches. Actualmente, la validación significa lo siguiente:
•Invocar el hook sendemail-validate si está presente (ver githooks(5)).
•Advertir sobre parches que contengan líneas de más de 998 caracteres a menos que se use una codificación de transferencia adecuada (auto, base64o quoted-printable); esto se debe a los límites de SMTP descritos en https://www.ietf.org/rfc/rfc5322.txt.

El valor por defecto es el valor de sendemail.validate; si no está establecido, el valor por defecto es --validate.

--force

Enviar correos electrónicos incluso si las comprobaciones de seguridad lo impedirían.

Información

--dump-aliases

En lugar de la operación normal, volcar los nombres de alias abreviados de los archivos de alias configurados, uno por línea en orden alfabético. Tenga en cuenta que esto solo incluye el nombre del alias y no sus direcciones de correo electrónico expandidas. Ver sendemail.aliasesFile para más información sobre los alias.

--translate-aliases

En lugar de la operación normal, leer de la entrada estándar e interpretar cada línea como un alias de correo electrónico. Traducirlo de acuerdo con los archivos de alias configurados. Emitir cada nombre y dirección de correo electrónico traducidos a la salida estándar, uno por línea. Ver sendemail.aliasFile para más información sobre los alias.

CONFIGURACIÓN

Todo lo que hay debajo de esta línea en esta sección se incluye selectivamente de la documentación de git-config(1) . El contenido es el mismo que el que se encuentra allí:

sendemail.identity

Una identidad de configuración. Cuando se proporciona, hace que los valores en la subsección sendemail.<identity> tengan prioridad sobre los valores en la sección sendemail . La identidad por defecto es el valor de sendemail.identity.

sendemail.smtpEncryption

Ver git-send-email(1) para la descripción. Tenga en cuenta que esta configuración no está sujeta al mecanismo de identity .

sendemail.smtpSSLCertPath

Ruta a los ca-certificates (ya sea un directorio o un solo archivo). Establézcalo a una cadena vacía para deshabilitar la verificación de certificados.

sendemail.<identity>.*

Versiones específicas de la identidad de los parámetros sendemail.* que se encuentran más abajo, teniendo prioridad sobre estos cuando se selecciona esta identidad, ya sea a través de la línea de comandos o de sendemail.identity.

sendemail.multiEdit

Si true (por defecto), se iniciará una única instancia del editor para editar los archivos que tenga que editar (parches cuando se usa --annotate y el resumen cuando se usa --compose ). Si false, los archivos se editarán uno tras otro, iniciando un nuevo editor cada vez.

sendemail.confirm

Establece el valor por defecto de si confirmar antes de enviar. Debe ser uno de always, never, cc, composeo auto. Ver --confirm en la documentación de git-send-email(1) para el significado de estos valores.

sendemail.mailmap

Si true, hace que git-send-email(1) asuma --mailmap, de lo contrario asume --no-mailmap. False por defecto.

sendemail.mailmap.file

La ubicación de un archivo mailmap de ampliación específico de git-send-email(1) . El mailmap por defecto y mailmap.file se cargan primero. Por lo tanto, las entradas en este archivo tienen prioridad sobre las entradas en las ubicaciones por defecto del mailmap. Ver gitmailmap(5).

sendemail.mailmap.blob

Como sendemail.mailmap.file, pero considere el valor como una referencia a un blob en el repositorio. Las entradas en sendemail.mailmap.file tienen prioridad sobre las entradas aquí. Ver gitmailmap(5).

sendemail.aliasesFile

Para evitar escribir direcciones de correo electrónico largas, apunte esto a uno o más archivos de alias de correo electrónico. También debe proporcionar sendemail.aliasFileType.

sendemail.aliasFileType

Formato de los archivos especificados en sendemail.aliasesFile. Debe ser uno de mutt, mailrc, pine, elm, gnuso sendmail.

Cómo es un archivo de alias en cada formato se puede encontrar en la documentación del programa de correo electrónico del mismo nombre. Las diferencias y limitaciones de los formatos estándar se describen a continuación:

sendmail

•No se admiten alias entrecomillados ni direcciones entrecomilladas: se ignoran las líneas que contienen un símbolo ".
•No se admite la redirección a un archivo (/path/name) o a una tubería (|command
).•No se admite la inclusión de archivos ( :include:/path/name
).

•Se imprimen advertencias en la salida de error estándar para cualquier construcción explícitamente no admitida, y para cualquier otra línea que no sea reconocida por el analizador.

Estas variables de configuración proporcionan todas un valor por defecto para las opciones de la línea de comandos de git-send-email(1) . Ver su documentación para los detalles.

sendemail.outlookidfix

Si true, hace que git-send-email(1) asuma --outlook-id-fix, y si false asume --no-outlook-id-fix. Si no está especificado, se comportará de la misma manera que si no se especifica --outlook-id-fix .div>

sendemail.signedOffCc (obsoleto)

Alias obsoleto de sendemail.signedOffByCc.

sendemail.smtpBatchSize

Número de mensajes a enviar por conexión, después de lo cual se producirá un nuevo inicio de sesión. Si el valor es 0 o indefinido, se envían todos los mensajes en una sola conexión. Véase también la opción --batch-size de git-send-email(1).

sendemail.smtpReloginDelay

Segundos de espera antes de reconectarse al servidor SMTP. Véase también la opción --relogin-delay de git-send-email(1).

sendemail.forbidSendmailVariables

Para evitar errores de configuración comunes, git-send-email(1) se abortará con una advertencia si existen opciones de configuración para sendmail . Establezca esta variable para omitir la comprobación.

EJEMPLOS DE SERVIDORES SMTP

Usar Gmail como servidor SMTP

Para usar git send-email para enviar sus parches a través del servidor SMTP de Gmail, edite ~/.gitconfig para especificar la configuración de su cuenta:

[sendemail]
        smtpEncryption = ssl
        smtpServer = smtp.gmail.com
        smtpUser = su-nombre@gmail.com
        smtpServerPort = 465

Gmail no permite usar su contraseña habitual con git send-email. Si tiene configurada la autenticación multifactor en su cuenta de Gmail, puede generar una contraseña específica de la aplicación para usar con git send-email. Visite https://security.google.com/settings/security/apppasswords para crearla.

Alternativamente, en lugar de usar una contraseña específica de la aplicación, puede usar la autenticación OAuth2.0 con Gmail. OAuth2.0 es más seguro que las contraseñas específicas de la aplicación y funciona independientemente de si tiene configurada la autenticación multifactor. OAUTHBEARER y XOAUTH2 son mecanismos comunes utilizados para este tipo de autenticación. Gmail admite ambos. Como ejemplo, si desea usar OAUTHBEARER, edite su archivo ~/.gitconfig y añada smtpAuth = OAUTHBEARER a la configuración de su cuenta:

[sendemail]
        smtpEncryption = ssl
        smtpServer = smtp.gmail.com
        smtpUser = su-nombre@gmail.com
        smtpServerPort = 465
        smtpAuth = OAUTHBEARER

Otra alternativa es usar una herramienta desarrollada por Google conocida como sendgmail[1] para enviar correos electrónicos usando git send-email.

Usar Microsoft Outlook como servidor SMTP

A diferencia de Gmail, Microsoft Outlook ya no admite contraseñas específicas de la aplicación. Por lo tanto, debe usarse la autenticación OAuth2.0 con Outlook. Además, solo admite el mecanismo de autenticación XOAUTH2 .

Edite ~/.gitconfig para especificar la configuración de su cuenta para Outlook y usar su servidor SMTP con git send-email:

[sendemail]
        smtpEncryption = tls
        smtpServer = smtp.office365.com
        smtpUser = su-nombre@outlook.com
        smtpServerPort = 587
        smtpAuth = XOAUTH2

ENVÍO DE PARCHES

Una vez que sus commits estén listos para enviarse a la lista de correo, ejecute los siguientes comandos:

$ git format-patch --cover-letter -M origin/master -o outgoing/
$ edit outgoing/0000-*
$ git send-email outgoing/*

La primera vez que lo ejecute, se le pedirán sus credenciales. Introduzca la contraseña específica de la aplicación o su contraseña habitual, según corresponda.

Si tiene configurado un ayudante de credenciales (véase git-credential(1)), la contraseña se guardará en el almacén de credenciales, por lo que no tendrá que escribirla la próxima vez.

Si está usando la autenticación OAuth2.0, necesita usar un token de acceso en lugar de una contraseña cuando se le solicite. Hay varios generadores de tokens OAuth2.0 disponibles en línea. También hay ayudantes de credenciales mantenidos por la comunidad disponibles:

•git-credential-gmail[2] (multiplataforma, ayudante dedicado para autenticar cuentas de Gmail)
•git-credential-outlook[2] (multiplataforma, ayudante dedicado para autenticar cuentas de Microsoft Outlook)
•git-credential-yahoo[2] (multiplataforma, ayudante dedicado para autenticar cuentas de Yahoo)
•git-credential-aol[2] (multiplataforma, ayudante dedicado para autenticar cuentas de AOL)

También puede consultar gitcredentials(7) para más ayudantes de autenticación basados en OAuth.

Proton Mail no proporciona un servidor SMTP para enviar correos electrónicos. Si es un cliente de pago de Proton Mail, puede usar Proton Mail Bridge[3] oficialmente proporcionado por Proton Mail para crear un servidor SMTP local para enviar correos electrónicos. Tanto para usuarios gratuitos como de pago, se pueden usar proyectos mantenidos por la comunidad como git-protonmail[2].

Nota: se requieren los siguientes módulos Perl principales que pueden instalarse con su distribución de Perl:

MIME::Base64[4], MIME::QuotedPrint[5], Net::Domain[6] y Net::SMTP[7].

También se requieren estos módulos Perl adicionales:

Authen::SASL[8] y Mail::Address[9].

Aprovechando la opción sendmailCmd de git send-email

Además de enviar correos electrónicos a través de un servidor SMTP, git send-email también puede enviar correos electrónicos a través de cualquier aplicación que admita comandos similares a sendmail. Puede leer la documentación de --sendmail-cmd=<command> arriba para más información. Esta capacidad puede ser muy útil si desea usar otra aplicación como cliente SMTP para git send-email, o si su proveedor de correo electrónico usa APIs propietarias en lugar de SMTP para enviar correos electrónicos.

Como ejemplo, veamos cómo configurar msmtp[10], un cliente SMTP popular que se encuentra en muchas distribuciones de Linux. Edite ~/.gitconfig para indicar a git-send-email que lo use para enviar correos electrónicos.

[sendemail]
        sendmailCmd = /usr/bin/msmtp # Cambie esto por la ruta donde esté instalado msmtp

Enlaces a algunos de estos ayudantes mantenidos por la comunidad:

•msmtp[10] (cliente SMTP popular con muchas funciones, disponible para Linux y macOS)
•git-protonmail[2] (cliente multiplataforma que puede enviar correos electrónicos usando la API de ProtonMail)
•git-msgraph[2] (cliente multiplataforma que puede enviar correos electrónicos usando la API de Microsoft Graph)

    git-send-email - Enviar parches de Git por correo electrónico

    NOMBRE

    git-send-email - Enviar parches de Git por correo electrónico

    SINOPSIS

    git send-email [ -o | --output= <archivo> ] [ --to= <destinatario> ] [ --cc= <destinatario> ] [ --bcc= <destinatario> ] [ --subject= <asunto> ] [ --in-reply-to= <mensaje> ] [ --thread= <mensaje> ] [ --cover-letter ] [ --numbered ] [ --email-cmd= <comando> ] [ --annotate ] [ --compose ] [ --dry-run ] [ --from= <remitente> ] [ --signed ] [ --signed-by= <clave> ] [ --suppress-from ] [ --suppress-to ] [ --suppress-cc ] [ --suppress-bcc ] [ --validate ] [ --chain-reply-to ] [ --no-chain-reply-to ] [ --smtp-auth= <método> ] [ --smtp-server= <servidor> ] [ --smtp-user= <usuario> ] [ --smtp-password= <contraseña> ] [ --smtp-ssl | --smtp-use-starttls ] [ --compose-abort= <cadena> ] [ --compose-list= <archivo> ] [ --attach= <archivo> ] [ --suppress-message-id ] [ --utf8 ] [ --no-utf8 ] [ --no-plain-text ] [ --message-id-format= <formato> ] [ -v | --verbose ] [ --help ] [ --man ] [ --version ] <rev_inicial>.. <rev_final> -- [ <archivo_parche>... ]

    git send-email [ --alias= <alias> ] [ --dump-aliases ] [ --alias-file= <archivo> ] <opciones>

    git send-email [ --dump-config ] <opciones>

    DESCRIPCIÓN

    git send-email es una utilidad para enviar parches de Git a través de correo electrónico. Fue diseñado para trabajar con listas de correo, pero se puede usar para enviar correos electrónicos a cualquier destinatario. El programa genera correos electrónicos en formato de parche, listos para ser enviados.

    Si no se especifican las revisiones inicial y final, o si se especifica 'HEAD', el programa intenta adivinar la revisión inicial y final basándose en los parches enviados previamente (en caso de que se hayan enviado parches con el mismo asunto o con el mismo ID de mensaje).

    Los parches se pueden crear usando git-format-patch.

    El programa lee las revisiones desde la línea de comandos. Las revisiones se pueden especificar como un rango (p. ej., v1.0..v2.0) o como una sola revisión. Si se especifica un solo commit, solo se enviará ese commit.

    Si el archivo ".git//.git-send-email.cfg" existe, git send-email leerá las opciones de configuración desde ese archivo.

    El contenido del correo electrónico se genera a partir de los commits especificados. Si el commit tiene un cuerpo (body), se incluirá en el correo electrónico. Si el commit tiene metadatos (como un autor o una fecha), se incluirán también.

    El asunto del correo electrónico se genera automáticamente a partir del asunto del commit. Se puede modificar con la opción --subject.

    Las direcciones de destinatarios se pueden especificar con las opciones --to, --cc y --bcc.

    Si se utiliza la opción --cover-letter, se generará una carta de presentación adicional antes de los parches.

    Si se utiliza la opción --numbered, los parches se numerarán secuencialmente.

    La opción --email-cmd permite especificar un comando externo para enviar el correo electrónico (por ejemplo, sendmail).

    Las opciones relacionadas con SMTP ( --smtp-server, --smtp-user, --smtp-password, --smtp-ssl, --smtp-use-starttls) permiten configurar la conexión a un servidor SMTP para enviar los correos electrónicos directamente.

    La opción --validate realiza una validación del correo electrónico sin enviarlo.

    La opción --compose permite editar el contenido del correo electrónico antes de enviarlo.

    La opción --attach permite adjuntar archivos al correo electrónico.

    La opción --message-id-format permite personalizar el formato del ID del mensaje.

    La opción --utf8 habilita el soporte para caracteres UTF-8 en el contenido del correo electrónico.

    OPCIONES

    --output=<archivo>, -o <archivo>
    Escribe el correo electrónico generado en el archivo especificado en lugar de enviarlo.
    --to=<destinatario>
    Establece la dirección del destinatario principal. Se puede especificar múltiples veces.
    --cc=<destinatario>
    Establece la dirección de copia carbón (CC). Se puede especificar múltiples veces.
    --bcc=<destinatario>
    Establece la dirección de copia carbón oculta (BCC). Se puede especificar múltiples veces.
    --subject=<asunto>
    Establece el asunto del correo electrónico.
    --in-reply-to=<mensaje>
    Establece el encabezado In-Reply-To. Útil para responder a hilos existentes.
    --thread=<mensaje>
    Establece el encabezado Thread-Topic. Útil para mantener el hilo de la conversación.
    --cover-letter
    Genera una carta de presentación antes de los parches. La carta de presentación se basa en la descripción del commit de Git.
    --numbered
    Numera los parches secuencialmente.
    --email-cmd=<comando>
    Utiliza el comando especificado para enviar el correo electrónico. Por ejemplo, --email-cmd=sendmail.
    --annotate
    Abre un editor para añadir anotaciones a cada parche.
    --compose
    Abre un editor para modificar el cuerpo de cada correo electrónico antes de enviarlo.
    --dry-run
    Muestra lo que se enviaría, pero no envía realmente los correos electrónicos.
    --from=<remitente>
    Establece la dirección del remitente.
    --signed
    Firma los correos electrónicos con GPG.
    --signed-by=<clave>
    Firma los correos electrónicos con la clave GPG especificada.
    --suppress-from
    Suprime el encabezado From.
    --suppress-to
    Suprime el encabezado To.
    --suppress-cc
    Suprime el encabezado Cc.
    --suppress-bcc
    Suprime el encabezado Bcc.
    --validate
    Valida el formato de los correos electrónicos sin enviarlos.
    --chain-reply-to
    Habilita la cadena de respuestas.
    --no-chain-reply-to
    Deshabilita la cadena de respuestas.
    --smtp-auth=<método>
    Establece el método de autenticación SMTP (p. ej., login, plain).
    --smtp-server=<servidor>
    Establece el servidor SMTP a utilizar.
    --smtp-user=<usuario>
    Establece el nombre de usuario para la autenticación SMTP.
    --smtp-password=<contraseña>
    Establece la contraseña para la autenticación SMTP.
    --smtp-ssl
    Utiliza SSL para la conexión SMTP.
    --smtp-use-starttls
    Utiliza STARTTLS para la conexión SMTP.
    --compose-abort=<cadena>
    Si la cadena especificada se encuentra en el cuerpo del correo electrónico durante la composición, la operación se abortará.
    --compose-list=<archivo>
    Especifica un archivo que contiene una lista de direcciones de correo electrónico a las que enviar el correo.
    --attach=<archivo>
    Adjunta el archivo especificado al correo electrónico. Se puede usar varias veces.
    --suppress-message-id
    No añade el encabezado Message-ID.
    --utf8
    Habilita el soporte para caracteres UTF-8 en el contenido del correo electrónico.
    --no-utf8
    Deshabilita el soporte para caracteres UTF-8.
    --no-plain-text
    No genera la versión en texto plano del correo electrónico.
    --message-id-format=<formato>
    Especifica el formato del encabezado Message-ID.
    -v, --verbose
    Aumenta la verbosidad de la salida.
    --help
    Muestra un mensaje de ayuda y sale.
    --man
    Muestra esta página de manual y sale.
    --version
    Muestra información sobre la versión y sale.
    --alias=<alias>
    Utiliza las opciones de alias especificadas.
    --dump-aliases
    Muestra todos los alias disponibles y sale.
    --alias-file=<archivo>
    Especifica un archivo para cargar alias adicionales.
    --dump-config
    Muestra la configuración actual y sale.

    EJEMPLOS

    Enviar los parches desde el commit v1.0 hasta HEAD a la lista de correo devel@lists.example.com: 

    $ git send-email --to="devel@lists.example.com" v1.0..HEAD

    Enviar el último commit como un borrador a su propio correo electrónico: 

    $ git send-email --to="me@example.com" --output=draft.eml HEAD

    Enviar parches con una carta de presentación y numerados: 

    $ git send-email --cover-letter --numbered --to="devel@lists.example.com" v1.0..HEAD

    Enviar parches a través de un servidor SMTP con autenticación: 

    $ git send-email --smtp-server=smtp.example.com --smtp-user=myuser --smtp-password=mypass --to="devel@lists.example.com" v1.0..HEAD

    EJEMPLOS DE SERVIDORES SMTP

    Aquí hay algunos ejemplos de configuraciones SMTP:

    • Gmail: smtp.gmail.com:587 --smtp-use-starttls --smtp-user=your_email@gmail.com --smtp-password=your_app_password
    • Outlook.com: smtp.office365.com:587 --smtp-use-starttls --smtp-user=your_email@outlook.com --smtp-password=your_app_password
    • Yahoo Mail: smtp.mail.yahoo.com:587 --smtp-use-starttls --smtp-user=your_email@yahoo.com --smtp-password=your_app_password

    Nota: Para Gmail y Yahoo, es posible que necesites generar contraseñas de aplicación en lugar de usar tu contraseña normal.

    ENVÍO DE PARCHES

    Para enviar parches, generalmente seguirás estos pasos:

    1. Crea tus parches usando git format-patch. Por ejemplo: git format-patch -o "parches/" HEAD~3..HEAD
    2. Envía los parches usando git send-email, especificando los destinatarios y opcionalmente otras opciones: git send-email --to="lista@ejemplo.com" parches/*.patch

    Si estás enviando una serie de parches que continúan un hilo anterior, considera usar las opciones --in-reply-to y --thread para mantener el contexto.
