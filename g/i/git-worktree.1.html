NOMBRE

git-worktree - Gestionar múltiples árboles de trabajo

SINOPSIS

git worktree add [-f] [--detach] [--checkout] [--lock [--reason <string>]]
                 [--orphan] [(-b | -B) <new-branch>] <path> [<commit-ish>]
git worktree list [-v | --porcelain [-z]]
git worktree lock [--reason <string>] <worktree>
git worktree move <worktree> <new-path>
git worktree prune [-n] [-v] [--expire <expire>]
git worktree remove [-f] <worktree>
git worktree repair [<path>...]
git worktree unlock <worktree>

DESCRIPCIÓN

Gestiona múltiples árboles de trabajo (working trees) asociados al mismo repositorio.

Un repositorio de Git puede soportar múltiples árboles de trabajo, permitiéndote extraer (checkout) más de una rama a la vez. Con git worktree add, se asocia un nuevo árbol de trabajo al repositorio, junto con metadatos adicionales que diferencian ese árbol de trabajo de otros en el mismo repositorio. El árbol de trabajo, junto con estos metadatos, se denomina "worktree".

Este nuevo worktree se llama "linked worktree" (árbol de trabajo enlazado) en contraposición al "main worktree" (árbol de trabajo principal) preparado por git-init(1) o git-clone(1). Un repositorio tiene un árbol de trabajo principal (si no es un repositorio "bare") y cero o más árboles de trabajo enlazados. Cuando hayas terminado con un árbol de trabajo enlazado, elimínalo con git worktree remove.

En su forma más simple, git worktree add <path> crea automáticamente una nueva rama cuyo nombre es el componente final de <path>, lo cual es conveniente si planeas trabajar en un nuevo tema. Por ejemplo, git worktree add ../hotfix crea una nueva rama hotfix y la extrae en la ruta ../hotfix. Para trabajar en una rama existente en un nuevo worktree, usa git worktree add <path> <branch>. Por otro lado, si solo planeas hacer algunos cambios experimentales o realizar pruebas sin afectar el desarrollo existente, a menudo es conveniente crear un worktree "desechable" (throwaway) que no esté asociado a ninguna rama. Por ejemplo, git worktree add -d <path> crea un nuevo worktree con un HEAD desvinculado (detached) en el mismo commit que la rama actual.

Si un árbol de trabajo se elimina sin usar git worktree remove, sus archivos administrativos asociados, que residen en el repositorio (ver "DETALLES" a continuación), se eliminarán eventualmente de forma automática (ver gc.worktreePruneExpire en git-config(1)), o puedes ejecutar git worktree prune en el worktree principal o en cualquier worktree enlazado para limpiar cualquier archivo administrativo obsoleto.

Si el árbol de trabajo de un worktree enlazado está almacenado en un dispositivo portátil o una unidad de red que no siempre está montada, puedes evitar que sus archivos administrativos se eliminen ejecutando el comando git worktree lock, especificando opcionalmente --reason para explicar por qué está bloqueado el worktree.

COMANDOS

add <path> [<commit-ish>]

Crea un worktree en <path> y extrae <commit-ish> en él. El nuevo worktree se enlaza al repositorio actual, compartiendo todo excepto los archivos específicos del worktree como HEAD, index, etc. Como conveniencia, <commit-ish> puede ser un guion simple ("-"), que es sinónimo de @{-1}.

Si <commit-ish> es un nombre de rama (llamémosla <branch>) y no se encuentra, y ni -b ni -B ni --detach se utilizan, pero sí existe una rama de seguimiento en exactamente un remoto (llamémoslo <remote>) con un nombre coincidente, se considerará equivalente a:

$ git worktree add --track -b <branch> <path> <remote>/<branch>

Si la rama existe en múltiples remotos y uno de ellos es nombrado por la variable de configuración checkout.defaultRemote, usaremos ese para desambiguar, incluso si <branch> no es único entre todos los remotos. Establece por ejemplo checkout.defaultRemote=origin para siempre extraer ramas remotas de ahí si <branch> es ambiguo pero existe en el remoto origin. Ver también checkout.defaultRemote en git-config(1).

Si <commit-ish> se omite y no se usan ni -b ni -B ni --detach, entonces, como conveniencia, el nuevo worktree se asocia con una rama (llamémosla <branch>) nombrada a partir de $(basename <path>). Si <branch> no existe, se crea automáticamente una nueva rama basada en HEAD como si se hubiera dado -b <branch>. Si <branch> existe, se extraerá en el nuevo worktree, si no está extraída en ningún otro lugar, de lo contrario, el comando se negará a crear el worktree (a menos que se use --force).

Si <commit-ish> se omite, no se usa --detach ni --orphan, y no hay ramas locales válidas (o ramas remotas si se especifica --guess-remote), entonces, como conveniencia, el nuevo worktree se asocia con una nueva rama no nacida (unborn branch) llamada <branch> (después de $(basename <path>) si no se usa ni -b ni -B) como si se hubiera pasado --orphan al comando. En caso de que el repositorio tenga un remoto y se use --guess-remote, pero no existan ramas remotas ni locales, el comando fallará con una advertencia recordando al usuario que primero debe hacer fetch de su remoto (o anularlo usando -f/--force).

list

Lista detalles de cada worktree. El worktree principal se lista primero, seguido de cada uno de los worktrees enlazados. Los detalles de la salida incluyen si el worktree está "bare" (vacío/sin directorios de trabajo), la revisión actualmente extraída, la rama actualmente extraída (o "detached HEAD" si no hay ninguna), "locked" (bloqueado) si el worktree está bloqueado, "prunable" (eliminable) si el worktree puede ser eliminado por el comando prune.

lock

Si un worktree está en un dispositivo portátil o unidad de red que no siempre está montada, bloquéalo para evitar que sus archivos administrativos se eliminen automáticamente. Esto también evita que se mueva o elimine. Opcionalmente, especifica una razón para el bloqueo con --reason.

move

Mueve un worktree a una nueva ubicación. Ten en cuenta que el worktree principal o los worktrees enlazados que contienen submódulos no se pueden mover con este comando. (Sin embargo, el comando git worktree repair puede restablecer la conexión con los worktrees enlazados si mueves el worktree principal manualmente).

prune

Limpia la información de worktree en $GIT_DIR/worktrees.

remove

Elimina un worktree. Solo se pueden eliminar worktrees limpios (sin archivos no rastreados y sin modificaciones en archivos rastreados). Los worktrees sucios o aquellos con submódulos se pueden eliminar con --force. El worktree principal no se puede eliminar.

repair [<path>...]

Repara los archivos administrativos de los worktrees, si es posible, si se han corrompido o desactualizado debido a factores externos.

Por ejemplo, si el worktree principal (o repositorio "bare") se mueve, los worktrees enlazados no podrán localizarlo. Ejecutar repair en el worktree principal restablecerá la conexión desde los worktrees enlazados de vuelta al worktree principal.

De manera similar, si el árbol de trabajo de un worktree enlazado se mueve sin usar git worktree move, el worktree principal (o repositorio "bare") no podrá localizarlo. Ejecutar repair dentro del worktree recientemente movido restablecerá la conexión. Si se mueven múltiples worktrees enlazados, ejecutar repair desde cualquier worktree especificando la nueva ruta <path> de cada árbol, restablecerá la conexión a todas las rutas especificadas.

Si tanto el worktree principal como los worktrees enlazados se han movido o copiado manualmente, entonces ejecutar repair en el worktree principal y especificar el nuevo <path> de cada worktree enlazado reestablecerá la conexión a todos los worktrees enlazados especificados.

unlock

Elimina un bloqueo de un worktree.

OPCIONES

-f, --force

Al usar add, permite la creación de un nuevo worktree incluso si hay ramas existentes que no se pueden extraer limpiamente.

Al usar remove, permite eliminar un worktree incluso si tiene archivos no rastreados o modificaciones sin hacer commit.

--checkout

Al usar add, extrae la rama o commit especificado en el nuevo worktree. Esta es la operación predeterminada.

--detach

Al usar add, extrae el commit especificado en modo desvinculado (detached HEAD) en el nuevo worktree.

-b <new-branch>

Al usar add, crea una nueva rama llamada <new-branch> y la extrae. Si se especifica un <commit-ish>, la nueva rama se basará en ese commit. Si se omite <commit-ish>, la rama se basará en HEAD.

-B <new-branch>

Al usar add, crea una nueva rama llamada <new-branch> y la extrae. Si la rama ya existe, se restablece (reset) para que apunte a <commit-ish> (o a HEAD si se omite).

--track

Al usar add y -b, crea la rama local especificada con seguimiento de la rama remota especificada. Si se omite la rama remota, se intentará desambiguar basándose en la configuración (ver la descripción de add).

--orphan

Al usar add, crea una nueva rama que no tiene historial de commits. Esto es útil para iniciar un nuevo proyecto o para agregar un nuevo repositorio a Git sin vincularlo a un historial existente.

--lock [--reason <string>]

Al usar add, crea un nuevo worktree bloqueado. Esto evita que sus archivos administrativos se eliminen automáticamente. La opción --reason permite especificar un texto explicativo para el bloqueo.

-v, --verbose

Al usar list, muestra información más detallada sobre cada worktree, incluyendo la ruta completa del directorio de trabajo y el estado de los archivos de índice.

--porcelain [-z]

Al usar list, produce una salida formateada para ser procesada por scripts. La opción -z termina las entradas con un byte nulo en lugar de un salto de línea, lo que permite manejar nombres de ramas o rutas que contienen saltos de línea.

-n, --dry-run

Al usar prune, solo muestra qué worktrees se eliminarían, pero no los elimina realmente.

--expire <expire>

Al usar prune, elimina solo los worktrees que no se han accedido o modificado en el período especificado por <expire>. El formato de <expire> es el mismo que el utilizado por la opción `--expire` del comando `git gc`.

DETALLES

Los metadatos de los worktrees enlazados se almacenan en el directorio del repositorio Git principal, dentro de un subdirectorio llamado worktrees. Cada worktree enlazado tiene su propio subdirectorio dentro de $GIT_DIR/worktrees, que contiene información como el archivo HEAD, el archivo de índice y otros archivos necesarios para el funcionamiento del worktree.

El archivo $GIT_DIR/worktrees/<name>/gitdir en un worktree enlazado contiene la ruta absoluta al directorio del repositorio Git principal.

El archivo $GIT_DIR/worktrees/<name>/HEAD contiene la referencia (ref) a la rama o commit que está actualmente extraído en ese worktree.

Cuando se utiliza el comando git worktree prune, se buscan en el directorio $GIT_DIR/worktrees los worktrees cuyos directorios de trabajo asociados ya no existen o están inaccesibles. Si un worktree enlazado no se ha accedido o modificado en el período definido por la configuración `gc.worktreePruneExpire`, se considera obsoleto y se elimina su información administrativa del repositorio principal.

Si un worktree está bloqueado con git worktree lock, se añade una marca especial en sus metadatos para evitar que prune lo elimine. El bloqueo se puede eliminar con git worktree unlock.

La operación git worktree repair intenta corregir los enlaces entre el repositorio principal y los worktrees enlazados si alguno de ellos ha sido movido o copiado sin usar los comandos de Git. Busca archivos de configuración como gitdir en los worktrees enlazados y actualiza las rutas si es necesario.

COMMANDS

add [ -b <new-branch> | -B <new-branch> ] [ --track | --no-track ] [ -f | --force ] [ -d | --detach ] [ --orphan ] [ --checkout | --no-checkout ] [ --guess-remote | --no-guess-remote ] [ --relative-paths | --no-relative-paths ] [ --lock ] [ -q | --quiet ] [<commit-ish>] [<path>]

Create a new worktree named <path> by checking out <commit-ish> (defaults to HEAD). The new worktree is created under the repository’s $GIT_DIR/worktrees directory. See "DETAILS" for more information.

If <commit-ish> is a branch name or a tag name, then the new worktree starts from that commit. If it is a SHA-1, then it starts from that commit.

If <commit-ish> is omitted, it defaults to HEAD. Use -b or -B to create a new branch starting from <commit-ish>.

Use --orphan to create a new worktree with an unborn branch. The index and the worktree are empty.

By default, the new worktree's branch is set up to track the corresponding upstream branch if <commit-ish> is a remote-tracking branch. Use --track or --no-track to override this.

Use --lock to keep the worktree locked after creation. This is useful if you want to avoid accidentally pruning it.

Use --checkout / --no-checkout to control whether the branch is checked out.

Use --guess-remote to automatically set up tracking information if there is exactly one remote tracking branch with the same name as the new worktree's basename.

Use --relative-paths to use relative paths in the `.git` file.

list [ --porcelain [-z] ] [ -v | --verbose ] [ --expire <time> ]

List all the worktrees associated with the current repository. By default, it shows the path, the branch being tracked, the source commit and the reason why the worktree is locked (if any). Use -v to see additional information about the relative path, the gitdir, the working tree name, and the amount of data that will be freed by pruning.

With --porcelain, output is guaranteed to be stable across versions and insensitive to user configuration. Combine with -z to terminate lines with NUL characters, which is safer for parsing.

With --expire, annotate missing worktrees as prunable if they are older than the given time.

remove [ -f | --force ] [--ignore-unmatch] [<worktree>...]

Remove the specified worktree(s). By default, this command refuses to remove an unclean worktree (i.e. one with modifications). Use -f to force removal. If the worktree was locked, use -f twice.

prune [ -n | --dry-run ] [ -v | --verbose ] [ --expire <time> ]

Remove worktree directories associated with missing directories from the filesystem. They are removed from the index and the filesystem.

Use -n to see which worktrees would be removed without actually removing them.

Use -v to report all removals.

Use --expire to only prune worktrees that have not been used for the specified amount of time.

lock [ --reason <string> ] [<worktree>...]

Lock the specified worktree(s). A locked worktree cannot be removed or pruned. Use unlock to remove the lock. This is useful to prevent accidental pruning of a worktree that is in use, but not actively being worked on.

Use --reason to provide a reason for the lock, which will be displayed by list.

unlock [<worktree>...]

Unlock the specified worktree(s). This allows them to be pruned or removed again.

OPTIONS

-f, --force

By default, add refuses to create a new worktree when <commit-ish> is a branch name and is already checked out by another worktree, or if <path> is already assigned to some worktree but is missing (for instance, if <path> was deleted manually). This option overrides these safeguards. To add a missing but locked worktree path, specify --force twice.

move refuses to move a locked worktree unless --force is specified twice. If the destination is already assigned to some other worktree but is missing (for instance, if <new-path> was deleted manually), then --force allows the move to proceed; use --force twice if the destination is locked.

remove refuses to remove an unclean worktree unless --force is used. To remove a locked worktree, specify --force twice.

-b <new-branch>, -B <new-branch>

With add, create a new branch named <new-branch> starting at <commit-ish>, and check out <new-branch> into the new worktree. If <commit-ish> is omitted, it defaults to HEAD. By default, -b refuses to create a new branch if it already exists. -B overrides this safeguard, resetting <new-branch> to <commit-ish>.

-d, --detach

With add, detach HEAD in the new worktree. See "DETACHED HEAD" in git-checkout(1).

--checkout, --no-checkout

By default, add checks out <commit-ish>, however, --no-checkout can be used to suppress checkout in order to make customizations, such as configuring sparse-checkout. See "Sparse checkout" in git-read-tree(1).

--guess-remote, --no-guess-remote

With worktree add <path>, without <commit-ish>, instead of creating a new branch from HEAD, if there exists a tracking branch in exactly one remote matching the basename of <path>, base the new branch on the remote-tracking branch, and mark the remote-tracking branch as "upstream" from the new branch.

This can also be set up as the default behaviour by using the worktree.guessRemote config option.

--relative-paths, --no-relative-paths

Link worktrees using relative paths or absolute paths (default). Overrides the worktree.useRelativePaths config option, see git-config(1).

With repair, the linking files will be updated if there’s an absolute/relative mismatch, even if the links are correct.

--track, --no-track

When creating a new branch, if <commit-ish> is a branch, mark it as "upstream" from the new branch. This is the default if <commit-ish> is a remote-tracking branch. See --track in git-branch(1) for details.

--lock

Keep the worktree locked after creation. This is the equivalent of git worktree lock after git worktree add, but without a race condition.

-n, --dry-run

With prune, do not remove anything; just report what it would remove.

--orphan

With add, make the new worktree and index empty, associating the worktree with a new unborn branch named <new-branch>.

--porcelain

With list, output in an easy-to-parse format for scripts. This format will remain stable across Git versions and regardless of user configuration. It is recommended to combine this with -z. See below for details.

-z

Terminate each line with a NUL rather than a newline when --porcelain is specified with list. This makes it possible to parse the output when a worktree path contains a newline character.

-q, --quiet

With add, suppress feedback messages.

-v, --verbose

With prune, report all removals.

With list, output additional information about worktrees (see below).

--expire <time>

With prune, only expire unused worktrees older than <time>.

With list, annotate missing worktrees as prunable if they are older than <time>.

--reason <string>

With lock or with add --lock, an explanation why the worktree is locked.

<worktree>

Worktrees can be identified by path, either relative or absolute.

If the last path components in the worktree’s path is unique among worktrees, it can be used to identify a worktree. For example if you only have two worktrees, at /abc/def/ghi and /abc/def/ggg, then ghi or def/ghi is enough to point to the former worktree.

REFS

When using multiple worktrees, some refs are shared between all worktrees, but others are specific to an individual worktree. One example is HEAD, which is different for each worktree. This section is about the sharing rules and how to access refs of one worktree from another.

In general, all pseudo refs are per-worktree and all refs starting with refs/ are shared. Pseudo refs are ones like HEAD which are directly under $GIT_DIR instead of inside $GIT_DIR/refs. There are exceptions, however: refs inside refs/bisect, refs/worktree and refs/rewritten are not shared.

Refs that are per-worktree can still be accessed from another worktree via two special paths, main-worktree and worktrees. The former gives access to per-worktree refs of the main worktree, while the latter to all linked worktrees.

For example, main-worktree/HEAD or main-worktree/refs/bisect/good resolve to the same value as the main worktree’s HEAD and refs/bisect/good respectively. Similarly, worktrees/foo/HEAD or worktrees/bar/refs/bisect/bad are the same as $GIT_COMMON_DIR/worktrees/foo/HEAD and $GIT_COMMON_DIR/worktrees/bar/refs/bisect/bad.

To access refs, it’s best not to look inside $GIT_DIR directly. Instead use commands such as git-rev-parse(1) or git-update-ref(1) which will handle refs correctly.

CONFIGURATION FILE

By default, the repository config file is shared across all worktrees. If the config variables core.bare or core.worktree are present in the common config file and extensions.worktreeConfig is disabled, then they will be applied to the main worktree only.

In order to have worktree-specific configuration, you can turn on the worktreeConfig extension, e.g.:

$ git config extensions.worktreeConfig true

In this mode, specific configuration stays in the path pointed by git rev-parse --git-path config.worktree. You can add or update configuration in this file with git config --worktree. Older Git versions will refuse to access repositories with this extension.

Note that in this file, the exception for core.bare and core.worktree is gone. If they exist in $GIT_DIR/config, you must move them to the config.worktree of the main worktree. You may also take this opportunity to review and move other configuration that you do not want to share to all worktrees:

•core.worktree should never be shared.
•core.bare should not be shared if the value is core.bare=true.
•core.sparseCheckout should not be shared, unless you are sure you always use sparse checkout for all worktrees.

See the documentation of extensions.worktreeConfig in git-config(1) for more details.

DETAILS

Each linked worktree has a private sub-directory in the repository’s $GIT_DIR/worktrees directory. The private sub-directory’s name is usually the base name of the linked worktree’s path, possibly appended with a number to make it unique. For example, when $GIT_DIR=/path/main/.git the command git worktree add /path/other/test-next next creates the linked worktree in /path/other/test-next and also creates a $GIT_DIR/worktrees/test-next directory (or $GIT_DIR/worktrees/test-next1 if test-next is already taken).

Within a linked worktree, $GIT_DIR is set to point to this private directory (e.g. /path/main/.git/worktrees/test-next in the example) and $GIT_COMMON_DIR is set to point back to the main worktree’s $GIT_DIR (e.g. /path/main/.git). These settings are made in a .git file located at the top directory of the linked worktree.

Path resolution via git rev-parse --git-path uses either $GIT_DIR or $GIT_COMMON_DIR depending on the path. For example, in the linked worktree git rev-parse --git-path HEAD returns /path/main/.git/worktrees/test-next/HEAD (not /path/other/test-next/.git/HEAD or /path/main/.git/HEAD) while git rev-parse --git-path refs/heads/master uses $GIT_COMMON_DIR and returns /path/main/.git/refs/heads/master, since refs are shared across all worktrees, except refs/bisect, refs/worktree and refs/rewritten.

See gitrepository-layout(5) for more information. The rule of thumb is do not make any assumption about whether a path is shared or not, and use commands like git-rev-parse(1) and git-update-ref(1) to access and update refs.
