Debes poner tu nombre personal, generalmente una forma que use un nombre de pila y un apellido. Por ejemplo, el mantenedor actual de Git usa "Junio C Hamano". Esta será la porción del nombre que se almacena en cada commit que hagas.

¿Qué hace realmente http.postBu

ffer?
Esta opción cambia el tamaño del búfer que Git usa al hacer push de datos a un remoto a través de HTTP o HTTPS. Si los datos son más grandes que este tamaño, libcurl, que maneja el soporte HTTP para Git, usará codificación de transferencia por trozos (chunked) ya que no se conoce de antemano cuál será el tamaño de los datos que se harán push.

Dejar este valor en el tamaño por defecto está bien, a menos que sepas que ya sea el servidor remoto o un proxy intermedio no soportan HTTP/1.1 (que introdujo la codificación de transferencia por trozos) o se sabe que falla con datos por trozos. Esto se sugiere a menudo (erróneamente) como una solución para problemas genéricos de push, pero como casi todos los servidores y proxies soportan al menos HTTP/1.1, aumentar este valor usualmente no resuelve la mayoría de los problemas de push. Un servidor o proxy que no soportara correctamente HTTP/1.1 y la codificación de transferencia por trozos no sería muy útil en Internet hoy en día, ya que rompería mucho

tráfico.

Ten en cuenta que aumentar este valor incrementará la memoria usada en cada push relevante que Git haga so

bre HTTP o HTTPS, ya que se asigna el búfer completo independientemente de si se usa todo o no. Por lo tan
to, es mejor dejarlo en el valor por defecto a menos que estés seguro de necesitar un valor diferente.

¿Cómo configuro un editor

diferente?
Si no has especificado un editor específicamente para Git, por defecto usará el editor que has configurado usando las variables de entorno VISUAL o EDITOR, o si ninguna de las dos está especificada, el valor por defecto del sistema (que usualmente es vi). Dado que algunas personas encuentran vi difícil de usar o prefieren un editor diferente, puede ser deseable cambiar el editor usado.

Si quieres configurar un editor general para la mayoría de los programas que necesiten uno, puedes editar la configuración de tu shell (por ejemplo, ~/.bashrc o ~/.zshenv) para que contenga una línea que establezca la variable de entorno EDITOR o VISUAL a un valor apropiado. Ten en cuenta que en todos los casos, el valor del editor se pasará al shell, así que cualquier argumento que contenga espacios debe estar apropiadamente entrecomillado. ¿Cómo especifico mis credenciales al hacer push sobre

HTTP?
La forma más fácil de hacer esto es usar un asistente de credenciales a través de la configuración credential.helper. La mayoría de los sistemas proveen una opción estándar para integrarse con el gestor de credenciales del sistema. Por ejemplo, Git for Windows provee el gestor de credenciales wincred, macOS tiene el gestor de credenciales osxkeychain, y los sistemas Unix con un entorno de escritorio estándar pueden usar el gestor de credenciales libsecret. Todos estos almacenan las credenciales en un almacén encriptado para mantener seguras tus contraseñas o tokens.

Además, puedes usar el gestor de credenciales store que almacena en un archivo en tu directorio de inicio, o el gestor de credenciales cache, que no almacena tus credenciales permanentemente, pero te evita que te pregunten por ellas durante un cierto período de

tiempo.

También puedes simplemente introducir tu contraseña cuando se te pregunte. Aunque es posible coloc

¿Cómo uso múltiples cuentas con el mismo proveedor de alojamiento usando

SSH?
Con la mayoría de los proveedores de alojamiento que soportan SSH, un solo par de claves identifica de manera única a un usuario. Por lo tanto, para usar múltiples cuentas, es necesario crear un par de claves para cada cuenta. Si estás usando una versión de OpenSSH razonablemente moderna, puedes crear un nuevo par de claves con algo como ssh-keygen -t ed25519 -f ~/.ssh/id_committer. Luego puedes registrar la clave pública (en este caso, ~/.ssh/id_committer.pub; nota el .pub) con el proveedor de alojamiento.

La mayoría de los proveedores de alojamiento usan una sola cuenta SSH para hacer push; es decir, todos los usuarios hacen push a la cuenta git (por ejemplo, git@git.example.org). Si ese es el caso para tu proveedor, puedes configurar múltiples alias en SSH para dejar claro qué par de claves usar. Por ejemplo, podrías escribir algo como lo siguiente en ~/.ssh/config, sustituyendo el archivo de clave privada

        User git

        IdentityFile ~/.ssh/id_author
        IdentitiesOnly yes
# This is the account for committer on git.example.org.
Host example_committer
        HostName git.example.org
        User git
        # Este es el par de claves registrado para el co

¿Cómo sincronizo un árbol de trabajo entre

sistemas?
Primero, decide si quieres hacer esto en absoluto. Git funciona mejor cuando haces push o pull de tu trabajo usando los comandos típicos git push y git fetch y no está diseñado para compartir un árbol de trabajo entre sistemas. Esto es potencialmente arriesgado y en algunos casos puede causar la corrupción del repositorio o la pérdida de datos.

Generalmente, hacerlo hará que git status necesite releer cada archivo en el árbol de trabajo. Adicionalmente, el modelo de seguridad de Git no permite compartir un árbol de trabajo entre usuarios no confiables, por lo que solo es seguro sincronizar un árbol de trabajo si solo será utilizado por un único usuario en todas las

máquinas.

Es importante no usar un servicio de sincronización en la nube para sincronizar ninguna parte de un repositorio Git, ya que esto puede causar corrupción, como objetos faltantes, archivos cambiados o añadidos, referencias rotas y una amplia variedad de otros problemas. Estos servicios tienden a sincronizar archivo por archivo de forma continua y no entienden la estructura de un repositorio Git. Esto es especialmente malo si sincronizan el repositorio en medio de una actualización, ya que es muy probable que cause actualizaciones incompletas o parciales y por lo tanto pérdida de

datos.

Un ejemplo del tipo de corrupción que puede ocurrir es conflictos sobre el estado de las referencias, de modo que ambos lados terminen con commits diferentes en una rama que el otro no tiene. Esto puede resultar en que objetos importantes se queden sin referencia y posiblemente sean podados por git gc, causando pérdida de

datos.

Por lo tanto, es mejor hacer push de tu trabajo a otro sistema o a un servidor central usando el mecanismo normal de push y pull. Sin embargo, esto no siempre preserva datos importantes, como los stashes, por lo que algunas personas prefieren compartir un árbol de trabajo entre

sistemas.

Si haces esto, el enfoque recomendado es usar rsync -a --delete-after (idealmente con una conexión cifrada como con ssh) en la raíz del repositorio. Debes asegurar varias cosas cuando hagas

esto:
•Si tienes worktrees adicionales o un directorio de Git separado, deben sincronizarse al mismo tiempo que el árbol de trabajo principal y el
repositorio.
•Estás cómodo con que el directorio de destino sea una copia exacta del directorio de origen, eliminando cualquier dato qu
e ya esté allí.
•El repositorio (incluyendo todos los worktrees y el directorio de Git) está en un estado de reposo durante la duración de la transferencia (es decir, no se están realizando operaciones de ningún tipo en él, incluyendo operaciones en segundo plano como git gc y operaciones invocadas por tu editor).

Ten en cuenta que incluso con estas recomendaciones, sincronizar de esta manera tiene algún riesgo ya que evita la comprobación de integridad normal de Git para los repositorios, por lo que se recomienda tener copias de seguridad. También podrías querer hacer un git fsck para verificar la integridad

de tus datos en
el sistema d
e destino despué
s de sincronizar.

PROBLEMAS

COMUNES

He cometido un error en el último commit. ¿Cómo lo

cambio?
Puedes hacer el cambio apropiado en tu árbol de trabajo, ejecutar git add <file> o git rm <file>, según corresponda, para prepararlo, y luego git commit --amend. Tu cambio será incluido en el commit, y se te pedirá que edites el mensaje del commit de nuevo; si deseas usar el mensaje original literalmente, puedes usar la opción --no-edit con git commit además, o simplemente guardar y salir cuando tu editor se
abra.

He hecho un cambio con un error y ha sido incluido en la rama principal. ¿Cómo debería

deshacerlo?
La forma habitual de tratar esto es usar git revert. Esto preserva el historial de que el cambio original se hizo y fue una contribución valiosa, pero también introduce un nuevo commit que deshace esos cambios porque el original tenía un problema. El mensaje del commit del revert indica el commit que fue revertido y usualmente se edita para incluir una explicación de por qué se hizo el
revert.

¿Cómo ignoro cambios en un archivo

rastreado?
Git no proporciona una forma de hacer esto. La razón es que si Git necesita sobrescribir este archivo, como durante un checkout, no sabe si los cambios en el archivo son valiosos y deben conservarse, o si son irrelevantes y pueden ser destruidos de forma segura. Por lo tanto, tiene que tomar la ruta segura y siempre preservarlos.

Es tentador intentar usar ciertas características de git update-index, a saber, los bits assume-unchanged y skip-worktree, pero estos no funcionan correctamente para este propósito y no deberían usarse de esta

manera.

Si tu objetivo es modificar un archivo de configuración, a menudo puede ser útil tener un archivo versionado en el repositorio que sea una plantilla o un conjunto de valores predeterminados que luego puedan copiarse junto a él y modificarse según corresponda. Este segundo archivo, modificado, usualmente se ignora para evitar que se versione

accidentalmente
.

Le pedí a Git que ignorara varios archivos, pero aún están

rastreados
Un archivo gitignore asegura que cierto(s) archivo(s) que no están rastreados por Git permanezcan sin rastrear. Sin embargo, a veces archivos particulares pueden haber sido rastreados antes de añadirlos al .gitignore, por lo que siguen siendo rastreados. Para dejar de rastrear e ignorar archivos/patrones, usa git rm --cached <file/pattern> y añade un patrón al .gitignore que coincida con el <file>. Ver gitignore(5) para
detalles.

¿Cómo sé si quiero hacer un fetch o un

pull?
Un fetch almacena una copia de los últimos cambios del repositorio remoto, sin modificar el árbol de trabajo o la rama actual. Puedes luego a tu ritmo inspeccionar, fusionar, hacer rebase encima de, o ignorar los cambios upstream. Un pull consiste en un fetch seguido inmediatamente por una fusión o rebase. Ver git-pull
(1).

¿Puedo usar un proxy con

Git?
Sí, Git soporta el uso de proxies. Git respeta las variables de entorno estándar http_proxy, https_proxy, y no_proxy comúnmente usadas en Unix, y también puede configurarse con http.proxy y opciones similares para HTTPS (ver git-config(1)). Las http.proxy y opciones relacionadas pueden personalizarse por patrón de URL. Adicionalmente, Git puede en teoría funcionar normalmente con proxies transparentes que existan en la red.

Para SSH, Git puede soportar un proxy usando el ProxyCommand de OpenSSH. Las herramientas comúnmente usadas incluyen netcat y socat. Sin embargo, deben configurarse para no salir al ver EOF en la entrada estándar, lo que usualmente significa que netcat requerirá -q y socat requerirá un tiempo de espera con algo como -t 10. Esto es necesario porque la forma en que el servidor SSH de Git sabe que no se harán más peticiones es un EOF en la entrada estándar, pero cuando eso sucede, el servidor puede no haber procesado aún la petición final, por lo que soltar la conexión en ese punto interrumpiría esa

petición.

Un ejemplo de entrada de configuración en ~/.ssh/config con un proxy HTTP podría verse

así: 
Host git.example.org
    User git
ProxyCommand socat -t 10 - PROXY:pr
oxy.example.org:%h:%p,proxyport=8080

Ten en cuenta que en todos los casos, para que Git funcione correctamente, el proxy debe ser completamente transparente. El proxy no puede modificar, manipular, o almacen

ar en búfer la conexión de ninguna manera, o Git casi con certeza fallará en funcionar. Ten en cuenta que muchos proxies, incluyendo muchos middleboxes TLS, programa
s de antivirus y firewall de Windows distintos de Windows Defender y Windows Firewall, y proxies de filtrado no cumplen este estándar, y como resultado terminan
rompiendo Git. Debido a los muchos reportes de problemas y su pobre historial de seguridad, recomendamos en contra del uso de estas clases de software y dispositivos.

FUSIÓN Y

REBASE

¿Qué tipo de problemas pueden ocurrir al fusionar ramas de vida larga con squash

merges?
En general, hay una variedad de problemas que pueden ocurrir al usar squash merges para fusionar dos ramas múltiples veces. Estos pueden incluir ver commits extra en la salida de git log, con una GUI, o al usar la notación ... para expresar un rango, así como la posibilidad de necesitar resolver conflictos de nuevo y de nuevo.

Cuando Git hace una fusión normal entre dos ramas, considera exactamente tres puntos: las dos ramas y un tercer commit, llamado el base de fusión, que es usualmente el ancestro común de los commits. El resultado de la fusión es la suma de los cambios entre la base de fusión y cada cabeza. Cuando fusionas dos ramas con un commit de fusión regular, esto resulta en un nuevo commit que terminará siendo una base de fusión cuando se fusionen de nuevo, porque ahora hay un nuevo ancestro común. Git no tiene que considerar cambios que ocurrieron antes de la base de fusión, por lo que no tienes que resolver de nuevo ningún conflicto que resolviste

antes.

Cuando realizas un squash merge, no se crea un commit de fusión; en su lugar, los cambios de un lado se aplican como un commit regular al otro lado. Esto significa que la base de fusión para estas ramas no habrá cambiado, y así cuando Git vaya a realizar su próxima fusión, considerará todos los cambios que consideró la última vez más los nuevos cambios. Eso significa que cualquier conflicto puede necesitar ser resuelto de nuevo. De manera similar, cualquier cosa que use la notación ... en git diff, git log, o una GUI resultará en mostrar todos los cambios desde la base de fusión

original.

Como consecuencia, si quieres fusionar dos r

amas de vida larga repetidamente, es mej
or siempre usar un commit de fusión regular.

Si hago un cambio en dos ramas pero lo revierto en una, ¿por qué la fusión de esas ramas incluye el

cambio?
Por defecto, cuando Git hace una fusión, usa una estrategia llamada la estrategia ort, que hace una sofisticada fusión de tres vías. En tal caso, cuando Git realiza la fusión, considera exactamente tres puntos: las dos cabezas y un tercer punto, llamado el base de fusión, que es usualmente el ancestro común de esos commits. Git no considera la historia o los commits individuales que han ocurrido en esas ramas en absoluto.

Como resultado, si ambos lados tienen un cambio y un lado ha revertido ese cambio, el resultado es incluir el cambio. Esto se debe a que el código ha cambiado en un lado y no hay un cambio neto en el otro, y en este escenario, Git adopta el cambio.

Si esto es un problema para usted, puede hacer un rebase en su lugar, haciendo un rebase de la rama con la reversión sobre la otra rama. Un rebase en este escenario revertirá el cambio, porque un rebase aplica cada commit individual, incluida la reversión. Tenga en cuenta que los rebases reescriben el historial, por lo que debe evitar hacer rebase de ramas publicadas a menos que esté seguro de que se siente cómodo con eso. Consulte la sección de NOTAS en git-rebase(1) para más detalles.

HOOKS

¿Cómo uso hooks para evitar que los usuarios hagan ciertos cambios?

El único lugar seguro para hacer estos cambios es en el repositorio remoto (es decir, el servidor Git), generalmente en el hook pre-receive o en un sistema de integración continua (CI). Estas son las ubicaciones en las que la política se puede aplicar de manera efectiva.

Es común intentar usar hooks pre-commit (o, para mensajes de commit, hooks commit-msg) para verificar estas cosas, lo cual es genial si estás trabajando como desarrollador individual y quieres que las herramientas te ayuden. Sin embargo, usar hooks en una máquina de desarrollador no es efectivo como control de políticas porque un usuario puede omitir estos hooks con --no-verify sin ser notado (entre otras formas). Git asume que el usuario tiene el control de sus repositorios locales y no intenta prevenir esto ni delatar al usuario.

Además, algunos usuarios avanzados encuentran que los hooks pre-commit son un impedimento para flujos de trabajo que usan commits temporales para preparar trabajo en progreso o que crean commits de corrección (fixup commits), por lo que es mejor enviar este tipo de verificaciones al servidor de todos modos.

PROBLEMAS TRANSVERSALES

Estoy en Windows y mis archivos de texto se detectan como binarios.

Git funciona mejor cuando almacenas archivos de texto como UTF-8. Muchos programas en Windows admiten UTF-8, pero algunos no y solo usan el formato UTF-16 little-endian, que Git detecta como binario. Si no puedes usar UTF-8 con tus programas, puedes especificar una codificación de árbol de trabajo (working tree encoding) que indique con qué codificación deben extraerse los archivos, mientras sigues almacenando estos archivos como UTF-8 en el repositorio. Esto permite que herramientas como git-diff(1) funcionen como se espera, al tiempo que permite que tus herramientas funcionen.

Para hacerlo, puedes especificar un patrón de gitattributes(5) con el atributo working-tree-encoding. Por ejemplo, el siguiente patrón establece que todos los archivos C usen UTF-16LE-BOM, que es una codificación común en Windows:

*.c     working-tree-encoding=UTF-16LE-BOM

Necesitarás ejecutar git add --renormalize para que esto tenga efecto. Ten en cuenta que si estás haciendo estos cambios en un proyecto que se usa en varias plataformas, probablemente querrás hacerlo en un archivo de configuración por usuario o en el de $GIT_DIR/info/attributes, ya que hacerlo en un archivo .gitattributes en el repositorio se aplicará a todos los usuarios del repositorio.

Consulta la siguiente entrada para obtener información sobre la normalización de saltos de línea, y consulta gitattributes(5) para más información sobre archivos de atributos.

Estoy en Windows y git diff muestra mis archivos con un ^M al final.

Por defecto, Git espera que los archivos se almacenen con saltos de línea de Unix. Como tal, el retorno de carro (^M) que es parte de un salto de línea de Windows se muestra porque se considera espacio en blanco final. Git, por defecto, solo muestra los espacios en blanco finales en líneas nuevas, no en las existentes.

Puedes almacenar los archivos en el repositorio con saltos de línea de Unix y convertirlos automáticamente a los saltos de línea de tu plataforma. Para hacer eso, establece la opción de configuración core.eol a native y consulta la pregunta sobre los ajustes de almacenamiento recomendados para obtener información sobre cómo configurar archivos como texto o binarios.

También puedes controlar este comportamiento con la configuración core.whitespace si no deseas eliminar los retornos de carro de tus saltos de línea.

¿Por qué tengo un archivo que siempre se modifica?

Internamente, Git siempre almacena los nombres de archivo como secuencias de bytes y no realiza ninguna codificación ni plegado de mayúsculas/minúsculas. Sin embargo, Windows y macOS por defecto realizan plegado de mayúsculas/minúsculas en los nombres de archivo. Como resultado, es posible terminar con múltiples archivos o directorios cuyos nombres solo difieren en mayúsculas/minúsculas. Git puede manejar esto sin problemas, pero el sistema de archivos solo puede almacenar uno de estos archivos, por lo que cuando Git lee el otro archivo para ver su contenido, parece modificado.

Es mejor eliminar uno de los archivos de modo que solo quede uno. Puedes hacerlo con comandos como los siguientes (asumiendo dos archivos AFile.txt y afile.txt) en un árbol de trabajo limpio:

$ git rm --cached AFile.txt
$ git commit -m 'Eliminar archivos en conflicto por mayúsculas/minúsculas'
$ git checkout .

Esto evita tocar el disco, pero elimina el archivo adicional. Su proyecto puede preferir adoptar una convención de nombres, como nombres en minúsculas, para evitar que este problema vuelva a ocurrir; dicha convención puede verificarse utilizando un hook pre-receive o como parte de un sistema de integración continua (CI).

También es posible que los archivos modificados perpetuamente ocurran en cualquier plataforma si se está utilizando un filtro smudge o clean en su sistema pero un archivo fue previamente commiteado sin ejecutar el filtro smudge o clean. Para solucionar esto, ejecute lo siguiente en un árbol de trabajo limpio:

$ git add --renormalize .

¿Cuál es la forma recomendada de almacenar archivos en Git?

Aunque Git puede almacenar y manejar cualquier archivo de cualquier tipo, hay algunas configuraciones que funcionan mejor que otras. En general, recomendamos que los archivos de texto se almacenen en UTF-8 sin marca de orden de bytes (BOM) con finales LF (estilo Unix). También recomendamos el uso de UTF-8 (de nuevo, sin BOM) en los mensajes de commit. Estas son las configuraciones que funcionan mejor en todas las plataformas y con herramientas como git diff y git merge.

Además, si tienes una opción entre formatos de almacenamiento basados en texto o no basados en texto, recomendamos almacenar los archivos en formato de texto y, si es necesario, transformarlos al otro formato. Por ejemplo, un volcado SQL basado en texto con un registro por línea funcionará mucho mejor para diff y merge que un archivo de base de datos real. De manera similar, los formatos basados en texto como Markdown y AsciiDoc funcionarán mejor que los formatos binarios como Microsoft Word y PDF.

De manera similar, generalmente no se recomienda almacenar dependencias binarias (por ejemplo, bibliotecas compartidas o archivos JAR) o productos de compilación en el repositorio. Las dependencias y los productos de compilación se almacenan mejor en un servidor de artefactos o paquetes con solo referencias, URLs y hashes almacenados en el repositorio.

También recomendamos establecer un archivo gitattributes(5) para marcar explícitamente qué archivos son de texto y cuáles son binarios. Si quieres que Git adivine, puedes establecer el atributo text=auto.

Con los archivos de texto, Git generalmente se asegurará de que se utilicen finales LF en el repositorio. Las variables de configuración core.autocrlf y core.eol especifican qué convención de finales de línea se sigue cuando se extrae cualquier archivo de texto. También puedes usar el atributo eol (por ejemplo, eol=crlf) para anular qué archivos reciben qué tratamiento de finales de línea.

Por ejemplo, generalmente los archivos de shell deben tener finales LF y los archivos batch deben tener finales CRLF, por lo que lo siguiente podría ser apropiado en algunos proyectos:

# Por defecto, adivina.
*       text=auto
# Marca todos los archivos C como texto.
*.c     text
# Asegura que todos los archivos de shell tengan finales LF y todos los archivos batch tengan finales CRLF
# en el árbol de trabajo y ambos tengan LF en el repositorio.
*.sh text eol=lf
*.bat text eol=crlf
# Marca todos los archivos JPEG como binarios.
*.jpg   binary

Estas configuraciones ayudan a las herramientas a elegir el formato correcto para la salida, como parches, y resultan en archivos extraídos con los finales de línea apropiados para la plataforma.
