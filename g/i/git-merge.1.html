GIT-MERGE(1) Git Manual GIT-MERGE(1)

NOMBRE

git-merge - Unir dos o más historiales de desarrollo

SINOPSIS

git merge [-n] [--stat] [--compact-summary] [--no-commit] [--squash] [--[no-]edit]
        [--no-verify] [-s <strategy>] [-X <strategy-option>] [-S[<keyid>]]
        [--[no-]allow-unrelated-histories]
        [--[no-]rerere-autoupdate] [-m <msg>] [-F <file>]
        [--into-name <branch>] [<commit>...]
git merge (--continue | --abort | --quit)

DESCRIPCIÓN

Incorpora los cambios de los commits nombrados (desde el momento en que sus historiales divergieron de la rama actual) en la rama actual. Este comando es usado por git pull para incorporar cambios de otro repositorio y puede usarse manualmente para fusionar cambios de una rama en otra.

Suponga que existe el siguiente historial y la rama actual es master:

          A---B---C topic
         /
    D---E---F---G master

Entonces git merge topic reproducirá los cambios realizados en la rama topic desde que divergió de master (es decir, E) hasta su commit actual (C) sobre master, y registrará el resultado en un nuevo commit junto con los nombres de los dos commits padre y un mensaje de registro del usuario que describe los cambios. Antes de la operación, ORIG_HEAD se establece en la punta de la rama actual (G).

          A---B---C topic
         /         \
    D---E---F---G---H master

Una fusión se detiene si hay un conflicto que no puede resolverse automáticamente o si se proporcionó --no-commit al iniciar la fusión. En ese momento puede ejecutar git merge --abort o git merge --continue.

git merge --abort abortará el proceso de fusión e intentará reconstruir el estado previo a la fusión. Sin embargo, si había cambios sin confirmar cuando comenzó la fusión (y especialmente si esos cambios se modificaron posteriormente después de iniciar la fusión), git merge --abort en algunos casos no podrá reconstruir los cambios originales (previos a la fusión). Por lo tanto:


Advertencia

Se desaconseja ejecutar git merge con cambios sin confirmar no triviales: aunque es posible, puede dejarlo en un estado del que es difícil salir en caso de conflicto.

OPTIONS

--commit, --no-commit

Perform the merge and commit the result. This option can be used to override --no-commit.

With --no-commit perform the merge and stop just before creating a merge commit, to give the user a chance to inspect and further tweak the merge result before committing.

Note that fast-forward updates do not create a merge commit and therefore there is no way to stop those merges with --no-commit. Thus, if you want to ensure your branch is not changed or updated by the merge command, use --no-ff with --no-commit.

--edit, -e, --no-edit

Invoke an editor before committing successful mechanical merge to further edit the auto-generated merge message, so that the user can explain and justify the merge. The --no-edit option can be used to accept the auto-generated message (this is generally discouraged). The --edit (or -e) option is still useful if you are giving a draft message with the -m option from the command line and want to edit it in the editor.

Older scripts may depend on the historical behaviour of not allowing the user to edit the merge log message. They will see an editor opened when they run git merge. To make it easier to adjust such scripts to the updated behaviour, the environment variable GIT_MERGE_AUTOEDIT can be set to no at the beginning of them.

--cleanup=<mode>

This option determines how the merge message will be cleaned up before committing. See git-commit(1) for more details. In addition, if the <mode> is given a value of scissors, scissors will be appended to MERGE_MSG before being passed on to the commit machinery in the case of a merge conflict.

--ff, --no-ff, --ff-only

Specifies how a merge is handled when the merged-in history is already a descendant of the current history. --ff is the default unless merging an annotated (and possibly signed) tag that is not stored in its natural place in the refs/tags/ hierarchy, in which case --no-ff is assumed.

With --ff, when possible resolve the merge as a fast-forward (only update the branch pointer to match the merged branch; do not create a merge commit). When not possible (when the merged-in history is not a descendant of the current history), create a merge commit.

With --no-ff, create a merge commit in all cases, even when the merge could instead be resolved as a fast-forward.

With --ff-only, resolve the merge as a fast-forward when possible. When not possible, refuse to merge and exit with a non-zero status.

-S[<key-id>], --gpg-sign[=<key-id>], --no-gpg-sign

GPG-sign the resulting merge commit. The <key-id> argument is optional and defaults to the committer identity; if specified, it must be stuck to the option without a space. --no-gpg-sign is useful to countermand both commit.gpgSign configuration variable, and earlier --gpg-sign.

--log[=<n>], --no-log

In addition to branch names, populate the log message with one-line descriptions from at most <n> actual commits that are being merged. See also git-fmt-merge-msg(1).

With --no-log do not list one-line descriptions from the actual commits being merged.

--signoff, --no-signoff

Add a Signed-off-by trailer by the committer at the end of the commit log message. The meaning of a signoff depends on the project to which you’re committing. For example, it may certify that the committer has the rights to submit the work under the project’s license or agrees to some contributor representation, such as a Developer Certificate of Origin. (See https://developercertificate.org for the one used by the Linux kernel and Git projects.) Consult the documentation or leadership of the project to which you’re contributing to understand how the signoffs are used in that project.

The --no-signoff option can be used to countermand an earlier --signoff option on the command line.

Git does not (and will not) have a configuration variable to enable the --signoff command line option by default; see the commit.signoff entry in gitfaq(7) for more details.

--stat, -n, --no-stat

Show a diffstat at the end of the merge. The diffstat is also controlled by the configuration option merge.stat.

With -n or --no-stat do not show a diffstat at the end of the merge.

--compact-summary

Show a compact-summary at the end of the merge.

--squash, --no-squash

Produce the working tree and index state as if a real merge happened (except for the merge information), but do not actually make a commit, move the HEAD, or record $GIT_DIR/MERGE_HEAD (to cause the next git commit command to create a merge commit). This allows you to create a single commit on top of the current branch whose effect is the same as merging another branch (or more in case of an octopus).

With --no-squash perform the merge and commit the result. This option can be used to override --squash.

With --squash, --commit is not allowed, and will fail.

--verify, --no-verify

By default, the pre-merge and commit-msg hooks are run. When --no-verify is given, these are bypassed. See also githooks(5).

-s <strategy>, --strategy=<strategy>

Use the given merge strategy; can be supplied more than once to specify them in the order they should be tried. If there is no -s option, a built-in list of strategies is used instead (ort when merging a single head, octopus otherwise).

-X <option>, --strategy-option=<option>

Pass merge strategy specific option through to the merge strategy.

--verify-signatures, --no-verify-signatures

Verify that the tip commit of the side branch being merged is signed with a valid key, i.e. a key that has a valid uid: in the default trust model, this means the signing key has been signed by a trusted key. If the tip commit of the side branch is not signed with a valid key, the merge is aborted.

--summary, --no-summary

Synonyms to --stat and --no-stat; these are deprecated and will be removed in the future.

-q, --quiet

Operate quietly. Implies --no-progress.

-v, --verbose

Be verbose.

--progress, --no-progress

Turn progress on/off explicitly. If neither is specified, progress is shown if standard error is connected to a terminal. Note that not all merge strategies may support progress reporting.

--autostash, --no-autostash

Automatically create a temporary stash entry before the operation begins, record it in the ref MERGE_AUTOSTASH and apply it after the operation ends. This means that you can run the operation on a dirty worktree. However, use with care: the final stash application after a successful merge might result in non-trivial conflicts.

--allow-unrelated-histories

By default, git merge command refuses to merge histories that do not share a common ancestor. This option can be used to override this safety when merging histories of two projects that started their lives independently. As that is a very rare occasion, no configuration variable to enable this by default exists or will be added.

-m <msg>

Set the commit message to be used for the merge commit (in case one is created).

If --log is specified, a shortlog of the commits being merged will be appended to the specified message.

The git fmt-merge-msg command can be used to give a good default for automated git merge invocations. The automated message can include the branch description.

--into-name <branch>

Prepare the default merge message as if merging to the branch <branch>, instead of the name of the real branch to which the merge is made.

-F <file>, --file=<file>

Read the commit message to be used for the merge commit (in case one is created).

If --log is specified, a shortlog of the commits being merged will be appended to the specified message.

--rerere-autoupdate, --no-rerere-autoupdate

After the rerere mechanism reuses a recorded resolution on the current conflict to update the files in the working tree, allow it to also update the index with the result of resolution. --no-rerere-autoupdate is a good way to double-check what git-rerere(1) did and catch potential mismerges, before committing the result to the index with a separate git-add(1).

--overwrite-ignore, --no-overwrite-ignore

Silently overwrite ignored files from the merge result. This is the default behavior. Use --no-overwrite-ignore to abort.

--abort

Abort the current conflict resolution process, and try to reconstruct the pre-merge state. If an autostash entry is present, apply it to the worktree.

If there were uncommitted worktree changes present when the merge started, git merge --abort will in some cases be unable to reconstruct these changes. It is therefore recommended to always commit or stash your changes before running git merge.

git merge --abort is equivalent to git reset --merge when MERGE_HEAD is present unless MERGE_AUTOSTASH is also present in which case git merge --abort applies the stash entry to the worktree whereas git reset --merge will save the stashed changes in the stash list.

--quit

Forget about the current merge in progress. Leave the index and the working tree as-is. If MERGE_AUTOSTASH is present, the stash entry will be saved to the stash list.

--continue

After a git merge stops due to conflicts you can conclude the merge by running git merge --continue (see "HOW TO RESOLVE CONFLICTS" section below).

<commit>...

Commits, usually other branch heads, to merge into our branch. Specifying more than one commit will create a merge with more than two parents (affectionately called an Octopus merge).

If no commit is given from the command line, merge the remote-tracking branches that the current branch is configured to use as its upstream. See also the configuration section of this manual page.

When FETCH_HEAD (and no other commit) is specified, the branches recorded in the .git/FETCH_HEAD file by the previous invocation of git fetch for merging are merged to the current branch.

COMPROBACIONES PREVIAS A LA FUSIÓN

Antes de aplicar cambios externos, deberías tener tu propio trabajo en buen estado y confirmado localmente, para que no sea sobrescrito si hay conflictos. Véase también git-stash(1). git pull y git merge se detendrán sin hacer nada cuando los cambios locales no confirmados se solapen con archivos que git pull/git merge puedan necesitar actualizar.

Para evitar registrar cambios no relacionados en el commit de fusión, git pull y git merge también abortarán si hay cambios registrados en el índice respecto al commit HEAD. (Pueden existir excepciones especiales y limitadas a esta regla dependiendo de qué estrategia de fusión se esté usando, pero, por lo general, el índice debe coincidir con HEAD.)

Si todos los commits nombrados ya son ancestros de HEAD, git merge terminará anticipadamente con el mensaje "Already up to date."

FUSIÓN RÁPIDA (FAST-FORWARD)

A menudo, la cabeza de la rama actual es un ancestro del commit nombrado. Este es el caso más común, especialmente cuando se invoca desde git pull: estás siguiendo un repositorio upstream, no has realizado cambios locales y ahora quieres actualizar a una revisión upstream más reciente. En este caso, no se necesita un nuevo commit para almacenar el historial combinado; en su lugar, el HEAD (junto con el índice) se actualiza para apuntar al commit nombrado, sin crear un commit de fusión adicional.

Este comportamiento se puede suprimir con la opción --no-ff.

VERDADERA FUSIÓN

Excepto en una fusión de avance rápido (ver arriba), las ramas que se van a fusionar deben estar unidas por un commit de fusión que tenga a ambas como sus padres.

Se confirma una versión fusionada que reconcilia los cambios de todas las ramas que se van a fusionar, y su HEAD, el índice y el árbol de trabajo se actualizan a ella. Es posible tener modificaciones en el árbol de trabajo siempre que no se superpongan; la actualización las preservará.

Cuando no es obvio cómo reconciliar los cambios, ocurre lo siguiente:

1.El puntero HEAD permanece igual.
2.La referencia MERGE_HEAD se establece para apuntar a la otra cabeza de rama.
3.Las rutas que se fusionaron limpiamente se actualizan tanto en el archivo de índice como en su árbol de trabajo.
4.Para las rutas en conflicto, el archivo de índice registra hasta tres versiones: la etapa 1 almacena la versión del ancestro común, la etapa 2 de HEAD, y la etapa 3 de MERGE_HEAD (puede inspeccionar las etapas con git ls-files -u). Los archivos del árbol de trabajo contienen el resultado de la operación de fusión; es decir, resultados de fusión de 3 vías con los familiares marcadores de conflicto <<< === >>>.
5.Se escribe una referencia llamada AUTO_MERGE, que apunta a un árbol correspondiente al contenido actual del árbol de trabajo (incluyendo marcadores de conflicto para conflictos textuales). Tenga en cuenta que esta referencia solo se escribe cuando se usa la estrategia de fusión ort (la predeterminada).
6.No se realizan otros cambios. En particular, las modificaciones locales que tenía antes de comenzar la fusión permanecerán igual y las entradas del índice para ellas permanecen como estaban, es decir, coincidiendo con HEAD.

Si intentó una fusión que resultó en conflictos complejos y quiere empezar de nuevo, puede recuperarse con git merge --abort.

FUSIÓN DE ETIQUETAS

Al fusionar una etiqueta anotada (y posiblemente firmada), Git siempre crea un commit de fusión incluso si es posible una fusión fast-forward, y la plantilla del mensaje del commit se prepara con el mensaje de la etiqueta. Además, si la etiqueta está firmada, la verificación de la firma se informa como un comentario en la plantilla del mensaje. Véase también git-tag(1).

Cuando solo quieres integrarte con el trabajo que conduce al commit que resulta estar etiquetado, por ejemplo, sincronizar con un punto de lanzamiento upstream, puede que no quieras crear un commit de fusión innecesario.

En tal caso, puedes "desenvolver" la etiqueta tú mismo antes de pasársela a git merge, o pasar --ff-only cuando no tengas ningún trabajo propio. Por ejemplo

git fetch origin
git merge v1.2.3^0
git merge --ff-only v1.2.3

CÓMO SE PRESENTAN LOS CONFLICTOS

Durante una fusión, los archivos del árbol de trabajo se actualizan para reflejar el resultado de la fusión. Entre los cambios realizados a la versión del ancestro común, los que no se superponen (es decir, usted cambió un área del archivo mientras el otro lado dejó esa área intacta, o viceversa) se incorporan literalmente en el resultado final. Sin embargo, cuando ambos lados hicieron cambios en la misma área, Git no puede elegir uno u otro al azar, y le pide que lo resuelva dejando lo que ambos lados hicieron en esa área.

De forma predeterminada, Git usa el mismo estilo que el utilizado por el programa "merge" de la suite RCS para presentar dicho fragmento en conflicto, así:

Here are lines that are either unchanged from the common
ancestor, or cleanly resolved because only one side changed,
or cleanly resolved because both sides changed the same way.
<<<<<<< yours:sample.txt
Conflict resolution is hard;
let's go shopping.
=======
Git makes conflict resolution easy.
>>>>>>> theirs:sample.txt
And here is another line that is cleanly resolved or unmodified.

El área donde ocurrió un par de cambios en conflicto está marcada con los marcadores <<<<<<<, ======= y >>>>>>>. La parte anterior a ======= es típicamente su lado, y la parte posterior es típicamente el lado de ellos.

El formato predeterminado no muestra lo que decía el original en el área en conflicto. No puede saber cuántas líneas se eliminaron y reemplazaron con el comentario de Barbie en su lado. Lo único que puede saber es que su lado quiere decir que es difícil y que preferiría irse de compras, mientras que el otro lado quiere afirmar que es fácil.

Se puede usar un estilo alternativo estableciendo la variable de configuración merge.conflictStyle en diff3 o zdiff3. En el estilo diff3, el conflicto anterior puede verse así:

Here are lines that are either unchanged from the common
ancestor, or cleanly resolved because only one side changed,
<<<<<<< yours:sample.txt
or cleanly resolved because both sides changed the same way.
Conflict resolution is hard;
let's go shopping.
||||||| base:sample.txt
or cleanly resolved because both sides changed identically.
Conflict resolution is hard.
=======
or cleanly resolved because both sides changed the same way.
Git makes conflict resolution easy.
>>>>>>> theirs:sample.txt
And here is another line that is cleanly resolved or unmodified.

mientras que en el estilo zdiff3, puede verse así:

Here are lines that are either unchanged from the common
ancestor, or cleanly resolved because only one side changed,
or cleanly resolved because both sides changed the same way.
<<<<<<< yours:sample.txt
Conflict resolution is hard;
let's go shopping.
||||||| base:sample.txt
or cleanly resolved because both sides changed identically.
Conflict resolution is hard.
=======
Git makes conflict resolution easy.
>>>>>>> theirs:sample.txt
And here is another line that is cleanly resolved or unmodified.

Además de los marcadores <<<<<<<, ======= y >>>>>>>, usa otro marcador ||||||| seguido del texto original. Puede ver que el original simplemente afirmaba un hecho, y su lado simplemente cedió ante esa afirmación y se rindió, mientras que el otro lado intentó tener una actitud más positiva. A veces puede llegar a una mejor resolución viendo el original.

CÓMO RESOLVER CONFLICTOS

Después de ver un conflicto, puedes hacer dos cosas:

•Decidir no fusionar. Las únicas limpiezas que necesitas son restablecer el archivo de índice al commit HEAD para revertir 2. y limpiar los cambios del árbol de trabajo realizados por 2. y 3.; git merge --abort se puede usar para esto.
•Resolver los conflictos. Git marcará los conflictos en el árbol de trabajo. Edita los archivos para dejarlos en forma y git add para agregarlos al índice. Usa git commit o git merge --continue para cerrar el trato. El último comando verifica si hay una fusión (interrumpida) en progreso antes de llamar a git commit.

Puedes trabajar a través del conflicto con varias herramientas:

•Usa una herramienta de fusión. git mergetool para lanzar una herramienta gráfica de fusión que trabajará a través de la fusión contigo.
•Mira los diffs. git diff mostrará un diff de tres vías, resaltando los cambios tanto de las versiones HEAD como MERGE_HEAD. git diff AUTO_MERGE mostrará qué cambios has hecho hasta ahora para resolver conflictos textuales.
•Mira los diffs de cada rama. git log --merge -p <ruta> mostrará los diffs primero para la versión HEAD y luego la versión MERGE_HEAD.
•Mira los originales. git show :1:nombrearchivo muestra el ancestro común, git show :2:nombrearchivo muestra la versión HEAD, y git show :3:nombrearchivo muestra la versión MERGE_HEAD.

EJEMPLOS

•Fusionar las ramas fixes y enhancements sobre la rama actual, realizando una fusión octopus: 
$ git merge fixes enhancements
•Fusionar la rama obsolete en la rama actual, usando la estrategia de fusión ours: 
$ git merge -s ours obsolete
•Fusionar la rama maint en la rama actual, pero no crear un nuevo commit automáticamente: 
$ git merge --no-commit maint

Esto se puede usar cuando quieres incluir cambios adicionales en la fusión, o quieres escribir tu propio mensaje de commit de fusión.

Deberías abstenerte de abusar de esta opción para introducir cambios sustanciales en un commit de fusión. Pequeños ajustes como actualizar el nombre de la versión/lanzamiento serían aceptables.

ESTRATEGIAS DE FUSIÓN

El mecanismo de fusión (los comandos git merge y git pull) permite elegir las estrategias de fusión del backend con la opción -s. Algunas estrategias también pueden tomar sus propias opciones, que se pueden pasar dando argumentos -X<opción> a git merge y/o git pull.

ort

Esta es la estrategia de fusión predeterminada al hacer pull o fusionar una rama. Esta estrategia solo puede resolver dos cabezas usando un algoritmo de fusión de 3 vías. Cuando hay más de un ancestro común que se puede usar para la fusión de 3 vías, crea un árbol fusionado de los ancestros comunes y usa ese como árbol de referencia para la fusión de 3 vías. Se ha informado que esto da como resultado menos conflictos de fusión sin causar fusiones erróneas según pruebas realizadas en confirmaciones de fusión reales tomadas del historial de desarrollo del kernel de Linux 2.6. Además, esta estrategia puede detectar y manejar fusiones que involucran renombrados. No hace uso de copias detectadas. El nombre de este algoritmo es un acrónimo ("Ostensibly Recursive’s Twin", el gemelo de lo ostensiblemente recursivo) y proviene del hecho de que fue escrito como reemplazo del algoritmo predeterminado anterior, recursive.

En el caso de que la ruta sea un submódulo, si la confirmación del submódulo usada en un lado de la fusión es descendiente de la confirmación del submódulo usada en el otro lado de la fusión, Git intenta avanzar rápidamente hacia el descendiente. De lo contrario, Git tratará este caso como un conflicto, sugiriendo como resolución una confirmación de submódulo que sea descendiente de las conflictivas, si existe.

La estrategia ort puede tomar las siguientes opciones:

ours

Esta opción fuerza que los fragmentos en conflicto se resuelvan automáticamente de forma limpia favoreciendo nuestra versión. Los cambios del otro árbol que no entran en conflicto con nuestro lado se reflejan en el resultado de la fusión. Para un archivo binario, todo el contenido se toma de nuestro lado.

Esto no debe confundirse con la estrategia de fusión ours, que ni siquiera mira lo que contiene el otro árbol. Descarta todo lo que hizo el otro árbol, declarando que nuestro historial contiene todo lo que sucedió en él.

theirs

Esto es lo opuesto a ours; tenga en cuenta que, a diferencia de ours, no existe una estrategia de fusión theirs con la que confundir esta opción de fusión.

ignore-space-change, ignore-all-space, ignore-space-at-eol, ignore-cr-at-eol

Trata las líneas con el tipo indicado de cambio de espacio en blanco como sin cambios para efectos de una fusión de tres vías. Los cambios de espacio en blanco mezclados con otros cambios en una línea no se ignoran. Véase también git-diff(1) -b, -w, --ignore-space-at-eol y --ignore-cr-at-eol.
•Si su versión solo introduce cambios de espacio en blanco en una línea, se usa nuestra versión;
•Si nuestra versión introduce cambios de espacio en blanco pero su versión incluye un cambio sustancial, se usa su versión;
•De lo contrario, la fusión procede de la manera habitual.

renormalize

Esto ejecuta una comprobación y registro virtuales de las tres etapas de cualquier archivo que necesite una fusión de tres vías. Esta opción está pensada para usarse al fusionar ramas con diferentes filtros de limpieza o reglas de normalización de fin de línea. Véase "Merging branches with differing checkin/checkout attributes" en gitattributes(5) para más detalles.

no-renormalize

Desactiva la opción renormalize. Esto anula la variable de configuración merge.renormalize.

find-renames[=<n>]

Activa la detección de renombrados, estableciendo opcionalmente el umbral de similitud. Esta es la opción predeterminada. Esto anula la variable de configuración merge.renames. Véase también git-diff(1) --find-renames.

rename-threshold=<n>

Sinónimo obsoleto de find-renames=<n>.

no-renames

Desactiva la detección de renombrados. Esto anula la variable de configuración merge.renames. Véase también git-diff(1) --no-renames.

histogram

Sinónimo obsoleto de diff-algorithm=histogram.

patience

Sinónimo obsoleto de diff-algorithm=patience.

diff-algorithm=(histogram|minimal|myers|patience)

Usa un algoritmo de diferencias diferente durante la fusión, lo que puede ayudar a evitar fusiones erróneas que ocurren debido a líneas coincidentes poco importantes (como llaves de funciones distintas). Véase también git-diff(1) --diff-algorithm. Tenga en cuenta que ort usa por defecto diff-algorithm=histogram, mientras que las diferencias regulares actualmente usan por defecto la configuración diff.algorithm.

subtree[=<ruta>]

Esta opción es una forma más avanzada de la estrategia subtree, donde la estrategia hace una suposición sobre cómo se deben desplazar dos árboles para coincidir entre sí al fusionar. En cambio, la ruta especificada se antepone (o se elimina del principio) para hacer que la forma de los dos árboles coincida.

recursive

Ahora es un sinónimo de ort. Fue una implementación alternativa hasta la v2.49.0, pero se redirigió para significar ort en la v2.50.0. La estrategia recursiva anterior fue la estrategia predeterminada para resolver dos cabezas desde Git v0.99.9k hasta la v2.33.0.

resolve

Esto solo puede resolver dos cabezas (es decir, la rama actual y otra rama de la que hizo pull) usando un algoritmo de fusión de 3 vías. Intenta detectar cuidadosamente ambigüedades de fusión entrecruzadas. No maneja renombrados.

octopus

Esto resuelve casos con más de dos cabezas, pero se niega a hacer una fusión compleja que necesite resolución manual. Está pensado principalmente para usarse al agrupar cabezas de ramas de temas. Esta es la estrategia de fusión predeterminada al hacer pull o fusionar más de una rama.

ours

Esto resuelve cualquier número de cabezas, pero el árbol resultante de la fusión es siempre el de la cabeza de la rama actual, ignorando efectivamente todos los cambios de todas las demás ramas. Está pensado para usarse para reemplazar el historial de desarrollo antiguo de ramas secundarias. Tenga en cuenta que esto es diferente de la opción -Xours de la estrategia de fusión ort.

subtree

Esta es una estrategia ort modificada. Al fusionar los árboles A y B, si B corresponde a un subárbol de A, B se ajusta primero para coincidir con la estructura de árbol de A, en lugar de leer los árboles en el mismo nivel. Este ajuste también se hace al árbol ancestro común.

Con las estrategias que usan fusión de 3 vías (incluida la predeterminada, ort), si se hace un cambio en ambas ramas, pero luego se revierte en una de las ramas, ese cambio estará presente en el resultado fusionado; algunas personas encuentran confuso este comportamiento. Ocurre porque solo se consideran las cabezas y la base de fusión al realizar una fusión, no las confirmaciones individuales. Por lo tanto, el algoritmo de fusión considera el cambio revertido como ningún cambio en absoluto, y sustituye la versión cambiada en su lugar.

CONFIGURATION

branch.<name>.mergeOptions

Sets default options for merging into branch <name>. The syntax and supported options are the same as those of git merge, but option values containing whitespace characters are currently not supported.

Everything above this line in this section isn’t included from the git-config(1) documentation. The content that follows is the same as what’s found there:

merge.conflictStyle

Specify the style in which conflicted hunks are written out to working tree files upon merge. The default is "merge", which shows a <<<<<<< conflict marker, changes made by one side, a ======= marker, changes made by the other side, and then a >>>>>>> marker. An alternate style, "diff3", adds a ||||||| marker and the original text before the ======= marker. The "merge" style tends to produce smaller conflict regions than diff3, both because of the exclusion of the original text, and because when a subset of lines match on the two sides, they are just pulled out of the conflict region. Another alternate style, "zdiff3", is similar to diff3 but removes matching lines on the two sides from the conflict region when those matching lines appear near either the beginning or end of a conflict region.

merge.defaultToUpstream

If merge is called without any commit argument, merge the upstream branches configured for the current branch by using their last observed values stored in their remote-tracking branches. The values of the branch.<current branch>.merge that name the branches at the remote named by branch.<current-branch>.remote are consulted, and then they are mapped via remote.<remote>.fetch to their corresponding remote-tracking branches, and the tips of these tracking branches are merged. Defaults to true.

merge.ff

By default, Git does not create an extra merge commit when merging a commit that is a descendant of the current commit. Instead, the tip of the current branch is fast-forwarded. When set to false, this variable tells Git to create an extra merge commit in such a case (equivalent to giving the --no-ff option from the command line). When set to only, only such fast-forward merges are allowed (equivalent to giving the --ff-only option from the command line).

merge.verifySignatures

If true, this is equivalent to the --verify-signatures command line option. See git-merge(1) for details.

merge.branchdesc

In addition to branch names, populate the log message with the branch description text associated with them. Defaults to false.

merge.log

In addition to branch names, populate the log message with at most the specified number of one-line descriptions from the actual commits that are being merged. Defaults to false, and true is a synonym for 20.

merge.suppressDest

By adding a glob that matches the names of integration branches to this multi-valued configuration variable, the default merge message computed for merges into these integration branches will omit "into <branch-name>" from its title.

An element with an empty value can be used to clear the list of globs accumulated from previous configuration entries. When there is no merge.suppressDest variable defined, the default value of master is used for backward compatibility.

merge.renameLimit

The number of files to consider in the exhaustive portion of rename detection during a merge. If not specified, defaults to the value of diff.renameLimit. If neither merge.renameLimit nor diff.renameLimit are specified, currently defaults to 7000. This setting has no effect if rename detection is turned off.

merge.renames

Whether Git detects renames. If set to false, rename detection is disabled. If set to true, basic rename detection is enabled. Defaults to the value of diff.renames.

merge.directoryRenames

Whether Git detects directory renames, affecting what happens at merge time to new files added to a directory on one side of history when that directory was renamed on the other side of history. Possible values are:

false

Directory rename detection is disabled, meaning that such new files will be left behind in the old directory.

true

Directory rename detection is enabled, meaning that such new files will be moved into the new directory.

conflict

A conflict will be reported for such paths.

If merge.renames is false, merge.directoryRenames is ignored and treated as false. Defaults to conflict.

merge.renormalize

Tell Git that canonical representation of files in the repository has changed over time (e.g. earlier commits record text files with CRLF line endings, but recent ones use LF line endings). In such a repository, for each file where a three-way content merge is needed, Git can convert the data recorded in commits to a canonical form before performing a merge to reduce unnecessary conflicts. For more information, see section "Merging branches with differing checkin/checkout attributes" in gitattributes(5).

merge.stat

What, if anything, to print between ORIG_HEAD and the merge result at the end of the merge. Possible values are:

false

Show nothing.

true

Show git diff --diffstat --summary ORIG_HEAD.

compact

Show git diff --compact-summary ORIG_HEAD.

but any unrecognised value (e.g., a value added by a future version of Git) is taken as true instead of triggering an error. Defaults to true.

merge.autoStash

When set to true, automatically create a temporary stash entry before the operation begins, and apply it after the operation ends. This means that you can run merge on a dirty worktree. However, use with care: the final stash application after a successful merge might result in non-trivial conflicts. This option can be overridden by the --no-autostash and --autostash options of git-merge(1). Defaults to false.
