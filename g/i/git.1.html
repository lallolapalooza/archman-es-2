Restablecer, restaurar y

revertir

Hay tres comandos con nombres similares: git reset, git restore y git revert

.
•git-revert(1) se trata de hacer un nuevo commit que revierte los cambios realizados por otros
commits.
•git-restore(1) se trata de restaurar archivos en el árbol de trabajo desde el índice u otro commit. Este comando no actualiza tu rama. El comando también puede usarse para restaurar archivos en el índice desde otro
commit.
•git-reset(1) se trata de actualizar tu rama, moviendo la punta para añadir o eliminar commits de la rama. Esta operación cambia el historial de commits.

git reset también puede usarse para restaurar el índice, superponiéndose con git res

t
o
re

COMANDOS DE NIVEL BAJO

(FONTANERÍA)

Aunque Git incluye su propia capa de porcelana, sus comandos de nivel bajo son suficientes para soportar el desarrollo de porcelanas alternativas. Los desarrolladores de tales porcelanas podrían empezar leyendo sobre git-update-index(1) y git-read-tr

ee(1).

La interfaz (entrada, salida, conjunto de opciones y la semántica) de estos comandos de nivel bajo está destinada a ser mucho más estable que la de los comandos de nivel Porcelana, porque estos comandos son principalmente para uso en scripts. La interfaz de los comandos de Porcelana, por otro lado, está sujeta a cambios para mejorar la experiencia del usuario

final.

La siguiente descripción divide los comandos de nivel bajo en comandos que manipulan objetos (en el repositorio, el índice y el árbol de trabajo), comandos que interrogan y comparan objetos, y comandos que mueven objetos y referencias entre

repositorios.

Varios comandos de Git prestan atención a las variables de entorno y cambian su comportamiento. Esta debería ser una lista de rutas absolutas separadas por dos puntos. Si está definida, es una lista de directorios en los que Git no debería hacer chdir hacia arriba mientras busca un directorio de repositorio (útil para excluir directorios de red de carga lenta). GIT_TRACE2_SOCKET

Define the path to the Unix domain socket to which Git will send trace messages. The socket type can be either stream or dgram. It is specified as follows: 

GIT_TRACE2_SOCKET=<socket-type>:]<absolute-pathname>

Por ejemplo:

GIT_TRACE2_SOCKET=stream:/path/to/my/git-trace.sock

Git intentará abrir la ruta como un Socket de Dominio Unix. El tipo de socket puede ser stream o dgram.

Anular la variable, o establecerla a vacía, "0" o "false" (sin distinción de mayúsculas y minúsculas) deshabilita los mensajes de rastreo.

Ver la documentación de Trace2[2] para detalles completos.

GIT_TRACE2_EVENT

Esta configuración escribe un formato basado en JSON que se adapta a la interpretación de máquinas. Ver GIT_TRACE2 para opciones de salida de rastreo disponibles y la documentación de Trace2[2] para detalles completos.

GIT_TRACE2_PERF

Además de los mensajes basados en texto disponibles en GIT_TRACE2, esta configuración escribe un formato basado en columnas para entender las regiones anidadas. Ver GIT_TRACE2 para opciones de salida de rastreo disponibles y la documentación de Trace2[2] para detalles completos.

GIT_TRACE_REDACT

Por defecto, cuando se activa el rastreo, Git redacta los valores de las cookies, la cabecera "Authorization:", la cabecera "Proxy-Authorization:" y las URIs de los packfiles. Establecer esta variable de entorno booleana a false para prevenir esta redacción.

GIT_NO_REPLACE_OBJECTS

Establecer y exportar esta variable de entorno le dice a Git que ignore las referencias de reemplazo y no reemplace los objetos de Git.

GIT_LITERAL_PATHSPECS

Establecer esta variable de entorno booleana a true hará que Git trate todos los pathspecs literalmente, en lugar de como patrones glob. Por ejemplo, ejecutar GIT_LITERAL_PATHSPECS=1 git log -- '*.c' buscará commits que toquen la ruta *.c, no cualquier ruta que coincida con el glob *.c. Podrías querer esto si estás alimentando rutas literales a Git (por ejemplo, rutas dadas previamente por git ls-tree, salida diff --raw, etc).

GIT_GLOB_PATHSPECS

Establecer esta variable de entorno booleana a true hará que Git trate todos los pathspecs como patrones glob (también conocido como magia "glob").

GIT_NOGLOB_PATHSPECS

Establecer esta variable de entorno booleana a true hará que Git trate todos los pathspecs como literales (también conocido como magia "literal").

GIT_ICASE_PATHSPECS

Establecer esta variable de entorno booleana a true hará que Git trate todos los pathspecs como insensible a mayúsculas y minúsculas.

GIT_NO_LAZY_FETCH

Establecer esta variable de entorno booleana a true le dice a Git que no obtenga perezosamente objetos faltantes del remoto promotor bajo demanda.

GIT_REFLOG_ACTION

Cuando se actualiza una referencia, se crean entradas de reflog para rastrear la razón por la cual se actualizó la referencia (que típicamente es el nombre del comando de alto nivel que actualizó la referencia), además de los valores antiguos y nuevos de la referencia. Un comando de Porcelana scriptado puede usar la función auxiliar set_reflog_action en git-sh-setup para establecer su nombre a esta variable cuando se invoca como comando de nivel superior por el usuario final, para que se registre en el cuerpo del reflog.

GIT_REF_PARANOIA

Si esta variable de entorno booleana se establece a false, ignora referencias rotas o mal nombradas al iterar sobre listas de referencias. Normalmente Git intentará incluir cualquier referencia de este tipo, lo que puede hacer que algunas operaciones fallen. Esto es usualmente preferible, ya que las operaciones potencialmente destructivas (por ejemplo, git-prune(1)) es mejor que aborten en lugar de ignorar referencias rotas (y por lo tanto considerar que la historia a la que apuntan no vale la pena guardarla). El valor por defecto es 1 (es decir, ser paranoico sobre la detección y aborto de todas las operaciones). Normalmente no necesitarás establecer esto a 0, pero puede ser útil al intentar recuperar datos de un repositorio corrupto.

GIT_COMMIT_GRAPH_PARANOIA

Al cargar un objeto de commit del commit-graph, Git realiza una verificación de existencia del objeto en la base de datos de objetos. Esto se hace para evitar problemas con commit-graphs obsoletos que contienen referencias a commits ya eliminados, pero tiene una penalización de rendimiento.

El valor por defecto es "false", que deshabilita el comportamiento mencionado anteriormente. Establecer esto a "true" habilita la verificación de existencia para que los commits obsoletos nunca sean devueltos desde el commit-graph a costa de rendimiento.

GIT_ALLOW_PROTOCOL

Si se establece a una lista de protocolos separada por dos puntos, compórtate como si protocol.allow estuviera configurado a never, y cada uno de los protocolos listados tuviera protocol.<name>.allow configurado a always (sobrescribiendo cualquier configuración existente). Ver la descripción de protocol.allow en git-config(1) para más detalles.

GIT_PROTOCOL_FROM_USER

Establecer esta variable de entorno booleana a false para prevenir protocolos usados por fetch/push/clone que están configurados al estado user. Esto es útil para restringir la inicialización recursiva de submódulos desde un repositorio no confiable o para programas que alimentan URLs potencialmente no confiables a comandos de git. Ver git-config(1) para más detalles.

GIT_PROTOCOL

Solo para uso interno. Usado en el apretón de manos del protocolo de cable. Contiene una lista separada por dos puntos : de claves con valores opcionales <clave>[=<valor>]. La presencia de claves y valores desconocidos debe ser ignorada.

Nota que los servidores pueden necesitar ser configurados para permitir que esta variable pase sobre algunos transportes. Será propagada automáticamente al acceder a repositorios locales (es decir, file:// o una ruta del sistema de archivos), así como sobre el protocolo git://. Para git-sobre-http, debería funcionar automáticamente en la mayoría de las configuraciones, pero ver la discusión en git-http-backend(1). Para git-sobre-ssh, el servidor ssh puede necesitar ser configurado para permitir a los clientes pasar esta variable (por ejemplo, usando AcceptEnv GIT_PROTOCOL con OpenSSH).

Esta configuración es opcional. Si la variable no es propagada, entonces los clientes recurrirán al protocolo original "v0" (pero pueden perderse algunas mejoras de rendimiento o características). Esta variable actualmente solo afecta a clones y fetches; aún no se usa para pushes (pero puede serlo en el futuro).

GIT_OPTIONAL_LOCKS

Si esta variable de entorno booleana se establece a false, Git completará cualquier operación solicitada sin realizar ninguna sub-operación opcional que requiera tomar un bloqueo. Por ejemplo, esto evitará que git status actualice el índice como efecto secundario. Esto es útil para procesos que se ejecutan en segundo plano y que no desean causar contención de bloqueos con otras operaciones en el repositorio. Por defecto es 1.

GIT_REDIRECT_STDIN, GIT_REDIRECT_STDOUT, GIT_REDIRECT_STDERR

Solo para Windows: permite redirigir los manejadores de entrada/salida/error estándar a rutas especificadas por las variables de entorno. Esto es particularmente útil en aplicaciones multihilo donde la forma canónica de pasar manejadores estándar a través de CreateProcess() no es una opción porque requeriría que los manejadores estuvieran marcados como heredables (y en consecuencia todos los procesos generados los heredarían, posiblemente bloqueando operaciones normales de Git). El caso de uso principal previsto es usar pipes con nombre para la comunicación (por ejemplo, \\.\pipe\my-git-stdin-123).

Se soportan dos valores especiales: off simplemente cerrará el manejador estándar correspondiente, y si GIT_REDIRECT_STDERR es 2>&1, la salida de error estándar se redirigirá al mismo manejador que la salida estándar.

GIT_PRINT_SHA1_ELLIPSIS (obsoleto)

Si se establece a yes, imprime puntos suspensivos después de un valor SHA-1 (abreviado). Esto afecta las indicaciones de HEADs desconectados (git-checkout(1)) y la salida diff cruda (git-diff(1)). Imprimir puntos suspensivos en los casos mencionados ya no se considera adecuado y es probable que el soporte para ello se elimine en el futuro previsible (junto con la variable).

GIT_ADVICE

Si se establece a 0, entonces deshabilita todos los mensajes de consejo. Estos mensajes están destinados a proporcionar pistas a los usuarios humanos que pueden ayudarles a salir de situaciones problemáticas o a aprovechar nuevas características. Los usuarios pueden deshabilitar mensajes individuales usando las claves de configuración advice.*. Estos mensajes pueden ser disruptivos para las herramientas que ejecutan procesos de Git, por lo que esta variable está disponible para deshabilitar los mensajes. (La opción global --no-advice también está disponible, pero las versiones antiguas de Git pueden fallar cuando esta opción no se entiende. La variable de entorno será ignorada por las versiones de Git que no la entienden).

DISCUSION

Más detalles sobre lo siguiente está disponible en el capítulo de conceptos de Git del manual del usuario[3] y gitcore-tutorial(7).

Un proyecto Git normalmente consiste en un directorio de trabajo con un subdirectorio ".git" en el nivel superior. El directorio .git contiene, entre otras cosas, una base de datos de objetos comprimida que representa el historial completo del proyecto, un archivo "índice" que vincula ese historial con el contenido actual del árbol de trabajo, y punteros nombrados en ese historial como etiquetas y cabezas de rama.

La base de datos de objetos contiene objetos de tres tipos principales: blobs, que contienen datos de archivos; árboles, que apuntan a blobs y otros árboles para construir jerarquías de directorios; y commits, cada uno de los cuales referencia un único árbol y algunos commits padres.

El commit, equivalente a lo que otros sistemas llaman un "changeset" o "versión", representa un paso en el historial del proyecto, y cada padre representa un paso inmediatamente anterior. Los commits con más de un padre representan fusiones de líneas de desarrollo independientes.

Todos los objetos son nombrados por el hash SHA-1 de su contenido, normalmente escrito como una cadena de 40 dígitos hexadecimales. Tales nombres son globalmente únicos. Todo el historial que conduce a un commit puede ser validado firmando solo ese commit. Se proporciona un cuarto tipo de objeto, la etiqueta, para este propósito.

Cuando se crean por primera vez, los objetos se almacenan en archivos individuales, pero por eficiencia pueden ser comprimidos posteriormente en "archivos de paquete".

Punteros nombrados llamados referencias marcan puntos interesantes en el historial. Una referencia puede contener el nombre SHA-1 de un objeto o el nombre de otra referencia (esta última se llama "referencia simbólica"). Las referencias con nombres que comienzan con refs/head/ contienen el nombre SHA-1 del commit más reciente (o "cabeza") de una rama en desarrollo. INDEX

The index file is initialized with a list of all paths and, for each path, a blob object and a set of attributes. The blob object represents the contents of the file as of the head of the current branch. The attributes (last modified time, size, etc.) are taken from the corresponding file in the working tree. Subsequent changes to the working tree can be found by comparing these attributes. The index may be updated with new content, and new commits may be created from the content stored in the index.

The index is also capable of storing multiple entries (called "stages") for a given pathname. These stages are used to hold the various unmerged version of a file when a merge is in progress.

SEGURIDAD

Algunas opciones de configuración y archivos hook pueden hacer que Git ejecute comandos shell arbitrarios. Dado que la configuración y los hooks no se copian usando git clone, generalmente es seguro clonar repositorios remotos con contenido no confiable, inspeccionarlos con git log, etc.

Sin embargo, no es seguro ejecutar comandos Git en un directorio .git (o en el árbol de trabajo que lo rodea) cuando ese directorio .git proviene de una fuente no confiable. Los comandos en su configuración y hooks se ejecutan de la manera habitual.

Por defecto, Git se negará a ejecutarse cuando el repositorio sea propiedad de alguien que no sea el usuario que ejecuta el comando. Ver la entrada para safe.directory en git-config(1). Si bien esto puede ayudar a protegerlo en un entorno multiusuario, tenga en cuenta que también puede adquirir repositorios no confiables que le pertenezcan (por ejemplo, si extrae un archivo zip o tarball de una fuente no confiable). En tales casos, tendría que "sanitizar" el repositorio no confiable primero.

Si tiene un directorio .git no confiable, primero debe clonarlo con git clone --no-local para obtener una copia limpia. Git restringe el conjunto de opciones y hooks que serán ejecutados por upload-pack, que maneja el lado del servidor de un clone o fetch, pero tenga en cuenta que la superficie de ataque contra upload-pack es grande, por lo que esto conlleva cierto riesgo. Lo más seguro es servir el repositorio como un usuario sin privilegios (ya sea a través de git-daemon(1), ssh, o usando otras herramientas para cambiar IDs de usuario). Ver la discusión en la sección SECURITY de git-upload-pack(1).
