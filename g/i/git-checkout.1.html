GIT-CHECKOUT(1) Manual de Git GIT-CHECKOUT(1)

NOMBRE

git-checkout - Cambiar de rama o restaurar archivos del árbol de trabajo

SINOPSIS

git checkout [-q] [-f] [-m] [<branch>]
git checkout [-q] [-f] [-m] --detach [<branch>]
git checkout [-q] [-f] [-m] [--detach] <commit>
git checkout [-q] [-f] [-m] [[-b|-B|--orphan] <new-branch>] [<start-point>]
git checkout <tree-ish> [--] <pathspec>...
git checkout <tree-ish> --pathspec-from-file=<file> [--pathspec-file-nul]
git checkout [-f|--ours|--theirs|-m|--conflict=<style>] [--] <pathspec>...
git checkout [-f|--ours|--theirs|-m|--conflict=<style>] --pathspec-from-file=<file> [--pathspec-file-nul]
git checkout (-p|--patch) [<tree-ish>] [--] [<pathspec>...]

DESCRIPCIÓN

git checkout tiene dos modos principales:

1.Cambiar de rama, con git checkout <branch>
2.Restaurar una versión diferente de un archivo, por ejemplo con git checkout <commit> <filename> o git checkout <filename>

Véase DESAMBIGUACIÓN DE ARGUMENTOS más abajo para ver cómo Git decide cuál hacer.

git checkout [<branch>]

Cambia a <branch>. Esto establece la rama actual a <branch> y actualiza los archivos en tu directorio de trabajo. El checkout fallará si hay cambios sin confirmar en cualquier archivo donde <branch> y tu commit actual tengan contenido diferente. Los cambios sin confirmar se conservarán de lo contrario.

Si <branch> no se encuentra pero existe una rama de seguimiento en exactamente un remoto (llamémoslo <remote>) con un nombre coincidente y --no-guess no se especifica, se trata como equivalente a

$ git checkout -b <branch> --track <remote>/<branch>

Ejecutar git checkout sin especificar una rama no tiene efecto excepto imprimir la información de seguimiento de la rama actual.

git checkout -b <new-branch> [<start-point>]

Crea una nueva rama llamada <new-branch>, iníciala en <start-point> (por defecto el commit actual), y haz checkout de la nueva rama. Puedes usar las opciones --track o --no-track para establecer la información de seguimiento upstream de la rama.

Esto fallará si hay un error al hacer checkout de <new-branch>, por ejemplo si hacer checkout del <start-point> commit sobrescribiría tus cambios sin confirmar.

git checkout -B <branch> [<start-point>]

Igual que -b, excepto que si la rama ya existe, restablece <branch> al punto de inicio en lugar de fallar.

git checkout --detach [<branch>], git checkout [--detach] <commit>

Igual que git checkout <branch>, excepto que en lugar de apuntar HEAD a la rama, apunta HEAD al ID del commit. Véase la sección "HEAD DESPRENDIDO" más abajo para más información.

Omitir <branch> desprende HEAD en la punta de la rama actual.

git checkout <tree-ish> [--] <pathspec>..., git checkout <tree-ish> --pathspec-from-file=<file> [--pathspec-file-nul]

Reemplaza los archivos y/o directorios especificados con la versión del commit o árbol dado y añádelos al índice (también conocido como "área de preparación").

Por ejemplo, git checkout main file.txt reemplazará file.txt con la versión de main.

git checkout [-f|--ours|--theirs|-m|--conflict=<style>] [--] <pathspec>..., git checkout [-f|--ours|--theirs|-m|--conflict=<style>] --pathspec-from-file=<file> [--pathspec-file-nul]

Reemplaza los archivos y/o directorios especificados con la versión del índice.

Por ejemplo, si haces checkout de un commit, editas file.txt, y luego decides que esos cambios fueron un error, git checkout file.txt descartará cualquier cambio sin preparar en file.txt.

Esto fallará si el archivo tiene un conflicto de fusión y aún no has ejecutado git add file.txt (o algo equivalente) para marcarlo como resuelto. Puedes usar -f para ignorar los archivos sin fusionar en lugar de fallar, usar --ours o --theirs para reemplazarlos con la versión de un lado específico de la fusión, o usar -m para reemplazarlos con el resultado de la fusión conflictiva original.

git checkout (-p|--patch) [<tree-ish>] [--] [<pathspec>...]

Esto es similar a los dos modos anteriores, pero te permite usar la interfaz interactiva para mostrar la salida del "diff" y elegir qué bloques usar en el resultado. Véase más abajo la descripción de la opción --patch .

OPCIONES

-q, --quiet

Silencioso, suprime los mensajes de retroalimentación.

--progress, --no-progress

El estado de progreso se informa en el flujo de error estándar por defecto cuando está conectado a una terminal, a menos que --quiet se especifique. Este indicador habilita el informe de progreso incluso si no está conectado a una terminal, independientemente de --quiet.

-f, --force

Al cambiar de rama, procede incluso si el índice o el árbol de trabajo difiere de HEAD, e incluso si hay archivos sin seguimiento en el camino. Esto se usa para descartar cambios locales y cualquier archivo o directorio sin seguimiento que esté en el camino.

Al hacer checkout de rutas desde el índice, no falla con entradas sin fusionar; en su lugar, las entradas sin fusionar se ignoran.

--ours, --theirs

Al hacer checkout de rutas desde el índice, haz checkout de la etapa #2 (ours) o #3 (theirs) para rutas sin fusionar.

Ten en cuenta que durante git rebase y git pull --rebase, ours y theirs pueden aparecer intercambiados; --ours da la versión de la rama sobre la que se están reasentando los cambios, mientras que --theirs da la versión de la rama que contiene tu trabajo que se está reasentando.

Esto se debe a que rebase se usa en un flujo de trabajo que trata el historial en el remoto como el canónico compartido, y trata el trabajo hecho en la rama que estás reasentando como el trabajo de terceros a integrar, y tú estás asumiendo temporalmente el rol de guardián del historial canónico durante el rebase. Como guardián del historial canónico, necesitas ver el historial del remoto como ours (es decir, "nuestro historial canónico compartido"), mientras que lo que hiciste en tu rama lateral como theirs (es decir, "el trabajo de un colaborador encima de él").

-b <new-branch>

Crea una nueva rama llamada <new-branch>, iníciala en <start-point>, y haz checkout de la rama resultante; véase git-branch(1) para más detalles.

-B <new-branch>

Igual que -b, excepto que si la rama ya existe, restablece <branch> al punto de inicio en lugar de fallar.

-t, --track[=(direct|inherit)]

Al crear una nueva rama, configura la configuración de "upstream". Véase --track en git-branch(1) para más detalles. Como conveniencia, --track sin -b implica la creación de una rama.

Esto nos indicaría usar hack como rama local al ramificar desde origin/hack (o remotes/origin/hack , o incluso refs/remotes/origin/hack ). Si el nombre dado no tiene barra, o la deducción anterior resulta en un nombre vacío, la deducción se aborta. . DETAC

HEAD

HEAD normalmente se refiere a una rama con nombre (por ejemplo, master). Mientras tanto, cada rama se refiere a un commit específico. Echemos un vistazo a un repositorio con tres commits, uno de ellos etiquetado y con la rama master seleccionada:

           HEAD (se refiere a la rama 'master')
            |
            v
a---b---c  rama 'master' (se refiere al commit 'c')
    ^
    |
  etiqueta 'v2.0' (se refiere al commit 'b')

Cuando se crea un commit en este estado, la rama se actualiza para referirse al nuevo commit. Específicamente, git commit crea un nuevo commit d, cuyo padre es el commit c, y luego actualiza la rama master para que se refiera al nuevo commit d. HEAD aún se refiere a la rama master y, por lo tanto, indirectamente ahora se refiere al commit d:

$ editar; git add; git commit
               HEAD (se refiere a la rama 'master')
                |
                v
a---b---c---d  rama 'master' (se refiere al commit 'd')
    ^
    |
  etiqueta 'v2.0' (se refiere al commit 'b')

A veces es útil poder seleccionar un commit que no está en la punta de ninguna rama con nombre, o incluso crear un nuevo commit que no sea referenciado por una rama con nombre. Veamos qué sucede cuando seleccionamos el commit b (aquí mostramos dos formas en que esto puede hacerse):

$ git checkout v2.0  # o
$ git checkout master^^
   HEAD (se refiere al commit 'b')
    |
    v
a---b---c---d  rama 'master' (se refiere al commit 'd')
    ^
    |
  etiqueta 'v2.0' (se refiere al commit 'b')

Observe que independientemente del comando de checkout que usemos, HEAD ahora se refiere directamente al commit b. Esto se conoce como estado de HEAD desvinculado. Significa simplemente que HEAD se refiere a un commit específico, en lugar de referirse a una rama con nombre. Veamos qué sucede cuando creamos un commit:

$ editar; git add; git commit
     HEAD (se refiere al commit 'e')
      |
      v
      e
     /
a---b---c---d  rama 'master' (se refiere al commit 'd')
    ^
    |
  etiqueta 'v2.0' (se refiere al commit 'b')

Ahora hay un nuevo commit e, pero solo es referenciado por HEAD. Por supuesto, podemos agregar aún otro commit en este estado:

$ editar; git add; git commit
         HEAD (se refiere al commit 'f')
          |
          v
      e---f
     /
a---b---c---d  rama 'master' (se refiere al commit 'd')
    ^
    |
  etiqueta 'v2.0' (se refiere al commit 'b')

De hecho, podemos realizar todas las operaciones normales de Git. Pero, veamos qué sucede cuando luego seleccionamos master:

$ git checkout master
               HEAD (se refiere a la rama 'master')
      e---f     |
     /          v
a---b---c---d  rama 'master' (se refiere al commit 'd')
    ^
    |
  etiqueta 'v2.0' (se refiere al commit 'b')

Es importante darse cuenta de que en este punto nada se refiere al commit f. Eventualmente, el commit f (y por extensión el commit e) será eliminado por el proceso de recolección de basura de Git, a menos que creemos una referencia antes de que eso suceda. Si aún no nos hemos alejado del commit f, cualquiera de estas opciones creará una referencia a él:

$ git checkout -b foo  # o "git switch -c foo"  (1)
$ git branch foo                                 (2)
$ git tag foo                                    (3)
1. crea una nueva rama foo, que se refiere al commit f, y luego actualiza HEAD para que se refiera a la rama foo. En otras palabras, ya no estaremos en el estado de HEAD desvinculado después de este comando.
2. similarmente crea una nueva rama foo, que se refiere al commit f, pero deja HEAD desvinculado.
3. crea una nueva etiqueta foo, que se refiere al commit f, dejando HEAD desvinculado.

Si nos hemos alejado del commit f, entonces debemos primero recuperar su nombre de objeto (típicamente usando git reflog), y luego podemos crear una referencia a él. Por ejemplo, para ver los últimos dos commits a los que HEAD se refirió, podemos usar cualquiera de estos comandos:

$ git reflog -2 HEAD # o
$ git log -g -2 HEAD

DESAMBIGUACIÓN DE ARGUMENTOS

Cuando ejecuta git checkout <algo>, Git intenta adivinar si <algo> está destinado a ser una rama, un commit o un conjunto de archivos, y luego cambia a esa rama o commit, o restaura los archivos especificados.

Si hay alguna ambigüedad, Git tratará <algo> como una rama o commit, pero puede usar el doble guion -- para forzar a Git a tratar el parámetro como una lista de archivos y/o directorios, de esta manera:

git checkout -- archivo.txt

EJEMPLOS

1. Rutas

La siguiente secuencia selecciona la rama master, revierte Makefile a dos revisiones atrás, elimina hello.c por error y lo recupera del índice.

$ git checkout master             (1)
$ git checkout master~2 Makefile  (2)
$ rm -f hello.c
$ git checkout hello.c            (3)
1. cambiar de rama
2. tomar un archivo de otro commit
3. restaurar hello.c desde el índice

Si desea extraer todos los archivos fuente C del índice, puede decir

$ git checkout -- '*.c'

Observe las comillas alrededor de *.c. El archivo hello.c también se extraerá, aunque ya no esté en el árbol de trabajo, porque el globbing de archivos se usa para coincidir con las entradas en el índice (no en el árbol de trabajo por el shell).

Si tiene una rama desafortunada llamada hello.c, este paso se confundiría como una instrucción para cambiar a esa rama. Debería escribir en su lugar:

$ git checkout -- hello.c

2. Fusionar

Después de trabajar en la rama incorrecta, cambiar a la rama correcta se haría usando:

$ git checkout mytopic

Sin embargo, su rama "incorrecta" y la rama correcta mytopic pueden diferir en archivos que ha modificado localmente, en cuyo caso el checkout anterior fallaría así:

$ git checkout mytopic
error: Tienes cambios locales en 'frotz'; no cambies de rama.

Puede dar la bandera -m al comando, que intentaría una fusión de tres vías:

$ git checkout -m mytopic
Auto-fusionando frotz

Después de esta fusión de tres vías, las modificaciones locales *no* se registran en su archivo de índice, por lo que git diff le mostraría qué cambios realizó desde la punta de la nueva rama.

3. Conflicto de fusión

Cuando ocurre un conflicto de fusión al cambiar de rama con la opción -m, vería algo como esto:

$ git checkout -m mytopic
Auto-fusionando frotz
ERROR: Conflicto de fusión en frotz
fatal: el programa de fusión falló

En este punto, git diff muestra los cambios fusionados limpiamente como en el ejemplo anterior, así como los cambios en los archivos en conflicto. Edite y resuelva el conflicto y márquelo como resuelto con git add como de costumbre:

$ editar frotz
$ git add frotz

CONFIGURACIÓN

Todo lo que sigue a continuación en esta sección se incluye selectivamente de la documentación de git-config(1). El contenido es el mismo que el que se encuentra allí:

checkout.defaultRemote

Cuando ejecuta git checkout <algo> o git switch <algo> y solo tiene un remoto, puede recurrir implícitamente a la selección y seguimiento de, por ejemplo, origin/<algo>. Esto deja de funcionar tan pronto como tenga más de un remoto con una referencia <algo>. Esta configuración permite establecer el nombre de un remoto preferido que siempre debe prevalecer cuando se trata de desambiguación. El caso de uso típico es establecer esto en origin.

Actualmente, esto es utilizado por git-switch(1) y git-checkout(1) cuando git checkout <algo> o git switch <algo> seleccionará la rama <algo> en otro remoto, y por git-worktree(1) cuando git worktree add se refiere a una rama remota. Esta configuración podría usarse para otros comandos similares a checkout o funcionalidades en el futuro.

checkout.guess

Proporciona el valor predeterminado para la opción --guess o --no-guess en git checkout y git switch. Ver git-switch(1) y git-checkout(1).

checkout.workers

El número de trabajadores paralelos a utilizar al actualizar el árbol de trabajo. El valor predeterminado es uno, es decir, ejecución secuencial. Si se establece en un valor menor que uno, Git utilizará tantos trabajadores como el número de núcleos lógicos disponibles. Esta configuración y checkout.thresholdForParallelism afectan a todos los comandos que realizan el checkout. Por ejemplo: checkout, clone, reset, sparse-checkout, etc.

Nota
El checkout paralelo generalmente ofrece un mejor rendimiento para repositorios ubicados en SSD o a través de NFS. Para repositorios en discos giratorios y/o máquinas con un pequeño número de núcleos, el checkout secuencial predeterminado a menudo funciona mejor. El tamaño y el nivel de compresión de un repositorio también podrían influir en qué tan bien funciona la versión paralela.

checkout.thresholdForParallelism

Al ejecutar el checkout paralelo con un número pequeño de archivos, el costo de la generación de subprocesos y la comunicación entre procesos podría
superan las ganancias de paralelización. Este ajuste le permite definir el número mínimo de archivos para los cuales se debe intentar la comprobación (checkout) en paralelo. El valor predeterminado es 100.
