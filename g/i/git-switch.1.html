GIT-SWITCH(1) Manual de Git GIT-SWITCH(1)

NOMBRE

git-switch - Cambiar de rama

SINOPSIS

git switch [<opciones>]--no-guess] <rama>
git switch [<opciones>] --detach [<punto-inicio>]
git switch [<opciones>] (-c|-C) <rama-nueva> [<punto-inicio>]
git switch [<opciones>] --orphan <rama-nueva>

DESCRIPCIÓN

Cambia a una rama especificada. El árbol de trabajo y el índice se actualizan para que coincidan con la rama. Todos los commits nuevos se añadirán a la punta de esta rama.

Opcionalmente, se puede crear una nueva rama con -c, -C, automáticamente desde una rama remota con el mismo nombre (véase --guess), o desvincular el árbol de trabajo de cualquier rama con --detach, junto con el cambio.

Cambiar de rama no requiere un índice y un árbol de trabajo limpios (es decir, sin diferencias en comparación con HEAD). Sin embargo, la operación se aborta si la operación conduce a la pérdida de cambios locales, a menos que se indique lo contrario con --discard-changes o --merge.

OPCIONES

<rama>

Rama a la que cambiar.

<rama-nueva>

Nombre de la nueva rama.

<punto-inicio>

El punto de inicio para la nueva rama. Especificar un <punto-inicio> le permite crear una rama basada en algún otro punto de la historia que no sea donde HEAD apunta actualmente. (O, en el caso de --detach, le permite inspeccionar y desvincularse de algún otro punto.)

Puede usar la sintaxis @{-<N>} para referirse a la <N>-ésima última rama/commit a la que se cambió usando la operación git switch o git checkout . También puede especificar - , que es sinónimo de @{-1}. Esto se usa a menudo para cambiar rápidamente entre dos ramas, o para deshacer un cambio de rama por error.

Como caso especial, puede usar <rev-a>...<rev-b> como un atajo para la base de fusión de <rev-a> y <rev-b> si hay exactamente una base de fusión. Puede omitir como máximo uno de <rev-a> y <rev-b>, en cuyo caso por defecto es HEAD.

-c <rama-nueva>, --create <rama-nueva>

Crea una nueva rama llamada <rama-nueva> que comienza en <punto-inicio> antes de cambiar a la rama. Este es el equivalente transaccional de 
$ git branch <rama-nueva>
$ git switch <rama-nueva>

es decir, la rama no se restablece/crea a menos que git switch sea exitoso (por ejemplo, cuando la rama está en uso en otro árbol de trabajo, no solo la rama actual permanece igual, sino que la rama tampoco se restablece al punto de inicio).

-C <rama-nueva>, --force-create <rama-nueva>

Similar a --create excepto que si <rama-nueva> ya existe, se restablecerá a <punto-inicio>. Este es un atajo conveniente para: 
$ git branch -f _<rama-nueva>_
$ git switch _<rama-nueva>_

-d, --detach

Cambia a un commit para inspección y experimentos desechables. Véase la sección "HEAD DESVINCULADO" en git-checkout(1) para más detalles.

--guess, --no-guess

Si <rama> no se encuentra pero existe una rama de seguimiento en exactamente un remoto (llamémoslo <remoto>) con un nombre coincidente, se trata como equivalente a 
$ git switch -c <rama> --track <remoto>/<rama>

Si la rama existe en varios remotos y uno de ellos es nombrado por la variable de configuración checkout.defaultRemote , usaremos ese para los propósitos de desambiguación, incluso si <rama> no es única en todos los remotos. Establézcala, por ejemplo, en checkout.defaultRemote=origin para siempre hacer checkout de ramas remotas desde allí si <rama> es ambigua pero existe en el remoto origin . Véase también checkout.defaultRemote en git-config(1).

--guess es el comportamiento por defecto. Use --no-guess para desactivarlo.

El comportamiento por defecto se puede establecer a través de la variable de configuración checkout.guess .

-f, --force

Un alias para --discard-changes.

--discard-changes

Proceder incluso si el índice o el árbol de trabajo difiere de HEAD. Tanto el índice como el árbol de trabajo se restauran para que coincidan con el objetivo del cambio. Si se especifica --recurse-submodules , el contenido de los submódulos también se restaura para que coincida con el objetivo del cambio. Esto se usa para descartar cambios locales.

-m, --merge

Si tiene modificaciones locales en uno o más archivos que son diferentes entre la rama actual y la rama a la que está cambiando, el comando se niega a cambiar de rama para preservar sus modificaciones en contexto. Sin embargo, con esta opción, se realiza una fusión de tres vías entre la rama actual, el contenido de su árbol de trabajo y la nueva rama, y estará en la nueva rama.

Cuando ocurre un conflicto de fusión, las entradas del índice para las rutas en conflicto se dejan sin fusionar, y necesita resolver los conflictos y marcar las rutas resueltas con git add (o git rm si la fusión debe resultar en la eliminación de la ruta).

--conflict=<estilo>

Igual que la opción --merge anterior, pero cambia la forma en que se presentan los fragmentos en conflicto, anulando la variable de configuración merge.conflictStyle . Los valores posibles son merge (por defecto), diff3y zdiff3.

-q, --quiet

Silencioso, suprime los mensajes de retroalimentación.

--progress, --no-progress

El estado de progreso se informa en el flujo de error estándar por defecto cuando está conectado a una terminal, a menos que se especifique --quiet . Esta bandera habilita el informe de progreso incluso si no está conectado a una terminal, independientemente de --quiet.

-t, --track[ (direct|inherit)]

Al crear una nueva rama, configura la configuración de "upstream". -c está implícito. Véase --track en git-branch(1) para más detalles.

Si no se da la opción -c , el nombre de la nueva rama se derivará de la rama de seguimiento remota, mirando la parte local del refspec configurado para el remoto correspondiente, y luego eliminando la parte inicial hasta el "*". Esto nos diría usar hack como rama local al ramificar desde origin/hack (o remotes/origin/hack, o incluso refs/remotes/origin/hack). Si el nombre dado no tiene barra, o el resultado de la adivinación anterior es un nombre vacío, la adivinación se aborta. Puede dar explícitamente un nombre con -c en tal caso.

--no-track

No configura la configuración de "upstream", incluso si la variable de configuración branch.autoSetupMerge es verdadera.

--orphan <rama-nueva>

Crea una nueva rama no nacida, llamada <rama-nueva>. Todos los archivos rastreados se eliminan.

--ignore-other-worktrees

git switch se niega cuando la referencia deseada ya está hecha checkout por otro árbol de trabajo. Esta opción hace que haga checkout de la referencia de todos modos. En otras palabras, la referencia puede ser mantenida por más de un árbol de trabajo.

--recurse-submodules, --no-recurse-submodules

Usar --recurse-submodules actualizará el contenido de todos los submódulos activos de acuerdo con el commit registrado en el superproyecto. Si no se usa nada (o --no-recurse-submodules), los árboles de trabajo de los submódulos no se actualizarán. Igual que git-submodule(1), esto desvinculará el HEAD de los submódulos.

EJEMPLOS

El siguiente comando cambia a la rama "master":

$ git switch master

Después de trabajar en la rama equivocada, cambiar a la rama correctanch se haría usando:

$ git switch mytopic

Sin embargo, tu rama "incorrecta" y la rama correcta "mytopic" pueden diferir en archivos que has modificado localmente, en cuyo caso el cambio anterior fallaría así:

$ git switch mytopic
error: You have local changes to 'frotz'; not switching branches.

Puedes dar el -m bandera al comando, que intentaría una fusión de tres vías:

$ git switch -m mytopic
Auto-merging frotz

Después de esta fusión de tres vías, las modificaciones locales están no registradas en tu archivo índice, por lo tanto git diff te mostraría qué cambios hiciste desde la punta de la nueva rama.

Para volver a la rama anterior antes de la que cambiamos a mytopic (es decir, la rama "master"):

$ git switch -

Puedes crear una nueva rama desde cualquier commit. Por ejemplo, cambia a "HEAD~3" y crea la rama "fixup":

$ git switch -c fixup HEAD~3
Switched to a new branch 'fixup'

Si quieres iniciar una nueva rama desde una rama remota con el mismo nombre:

$ git switch new-topic
Branch `new-topic` set up to track remote branch `new-topic` from `origin`
Switched to a new branch `new-topic`

Para hacer checkout del commit HEAD~3 para inspección temporal o experimento sin crear una nueva rama:

$ git switch --detach HEAD~3
HEAD is now at 9fc9555312 Merge branch 'cc/shared-index-permbits'

Si resulta que lo que has hecho vale la pena conservar, siempre puedes crear un nuevo nombre para ello (sin cambiar de rama):

$ git switch -c good-surprises

CONFIGURACIÓN

Todo lo que hay debajo de esta línea en esta sección se incluye selectivamente de la git-config(1) documentación. El contenido es el mismo que lo que se encuentra allí:

checkout.defaultRemote

Cuando ejecutas git checkout <something> o git switch <something> y solo tienes un remoto, puede caer implícitamente en hacer checkout y rastrear por ejemplo origin/<something>. Esto deja de funcionar tan pronto como tienes más de un remoto con una referencia <something> . Esta configuración permite establecer el nombre de un remoto preferido que siempre debe ganar cuando se trata de desambiguación. El caso de uso típico es establecer esto a origin.

Actualmente esto es usado por git-switch(1) y git-checkout(1) cuando git checkout <something> o git switch <something> hará checkout de la rama <something> en otro remoto, y por git-worktree(1) cuando git worktree add se refiere a una rama remota. Esta configuración podría usarse para otros comandos o funcionalidades similares al checkout en el futuro.

checkout.guess

Proporciona el valor por defecto para la --guess o --no-guess opción en git checkout y git switch. Ver git-switch(1) y git-checkout(1).

checkout.workers

El número de trabajadores paralelos a usar al actualizar el árbol de trabajo. El valor por defecto es uno, es decir, ejecución secuencial. Si se establece a un valor menor que uno, Git usará tantos trabajadores como el número de núcleos lógicos disponibles. Esta configuración y checkout.thresholdForParallelism afectan a todos los comandos que realizan checkout. Por ejemplo, checkout, clone, reset, sparse-checkout, etc.

Nota
El checkout paralelo generalmente ofrece un mejor rendimiento para repositorios ubicados en SSDs o a través de NFS. Para repositorios en discos magnéticos y/o máquinas con un pequeño número de núcleos, el checkout secuencial por defecto a menudo rinde mejor. El tamaño y el nivel de compresión de un repositorio también pueden influir en qué tan bien rinde la versión paralela.

checkout.thresholdForParallelism

Al ejecutar checkout paralelo con un pequeño número de archivos, el costo de generación de subprocesos y comunicación entre procesos podría superar las ganancias de la paralelización. Esta configuración te permite definir el número mínimo de archivos para los cuales se debe intentar el checkout paralelo. El valor por defecto es 100.
