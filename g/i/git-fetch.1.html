DESCRIPCIÓ

N

Obtiene ramas y/o etiquetas (colectivamente, "refs") de uno o más otros repositorios, junto con los objetos necesarios para completar sus historiales. Las ramas de seguimiento remoto se actualizan (véase la descripción de <refspec> más abajo para conocer las formas de controlar este comportamiento)

.

De forma predeterminada, cualquier etiqueta que apunte a los historiales que se están obteniendo también se obtiene; el efecto es obtener etiquetas que apuntan a ramas en las que estás interesado. Este comportamiento predeterminado se puede cambiar usando las opciones --tags o --no-tags o configurando remote.<name>.tagOpt. Usando un refspec que obtenga etiquetas explícitamente, puedes obtener también etiquetas que no apunten a ramas en las que estés

interesado.

git fetch puede obtener de un único repositorio con nombre o URL, o de varios repositorios a la vez si se proporciona <grupo> y existe una entrada remotes.<group> en el archivo de configuración. (Véase git-config(1))

.

Cuando no se especifica un remoto, por defecto se usará el remoto origin a menos que haya una rama ascendente configurada para la rama

actual.

Los nombres de las referencias que se obtienen, junto con los nombres de los objetos a los que apuntan, se escriben en .git/FETCH_HEAD. Esta información puede ser usada por scripts u otros comandos de git, como git-pu

ll(
1).

<repository

El repositorio "remoto" que es la fuente de una operación de obtención o tirón. Este parámetro puede ser una URL (ver la sección GIT URLS más abajo) o el nombre de un remoto (ver la sección REMOTES más abajo)

Un nombre que se refiere a una lista de repositorios como el valor de remotes.<group> en el archivo de configuración. (Ver git-config(1))

<refspec

>
Especifica qué refs obtener y qué refs locales actualizar. Cuando no aparecen <refspec>s en la línea de comandos, las refs a obtener se leen de remote.<repository>.fetch en su lugar (ver RAMAS DE SEGUIMIENTO REMOTO CONFIGURADAS más abajo).

El formato de un parámetro <refspec> es un más + opcional, seguido de la fuente <src>, seguido de dos puntos :, seguido del destino <dst>. Los dos puntos se pueden omitir cuando <dst> es vacío. <src> es típicamente una ref, o un patrón glob con un único * que se usa para coincidir con un conjunto de refs, pero también puede ser un nombre de objeto hexadecimal completamente

escrito.

Un <refspec> puede contener un * en su <src> para indicar una coincidencia de patrón simple. Tal refspec funciona como un glob que coincide con cualquier ref con el patrón. Un <refspec> de patrón debe tener uno y solo un * tanto en el <src> como en el <dst>. Mapeará refs al destino reemplazando el * con el contenido coincidente de la

fuente.

Si un refspec tiene el prefijo ^, se interpretará como un refspec negativo. En lugar de especificar qué refs obtener o qué refs locales actualizar, tal refspec especificará refs a excluir. Una ref se considerará que coincide si coincide con al menos un refspec positivo, y no coincide con ningún refspec negativo. Los refspecs negativos pueden ser útiles para restringir el alcance de un refspec de patrón para que no incluya refs específicas. Los refspecs negativos pueden ser ellos mismos refspecs de patrón. Sin embargo, solo pueden contener un <src> y no especifican un <dst>. Los nombres de objeto hexadecimales completamente escritos tampoco están

soportados.

tag <tag> significa lo mismo que refs/tags/<tag>:refs/tags/<tag>; solicita obtener todo hasta la etiqueta

dada.

La ref remota que coincide con <src> se obtiene, y si <dst> no es una cadena vacía, se intenta actualizar la ref local que coincide con

ella.

Si esa actualización se permite sin --force depende del espacio de nombres de la ref a la que se está obteniendo, el tipo de objeto que se está obteniendo, y si la actualización se considera un fast-forward. Generalmente, las mismas reglas se aplican para obtener como para hacer push, ver la sección <refspec>... de git-push(1) para saber cuáles son. Las excepciones a esas reglas particulares para git fetch se anotan más

abajo.

Hasta la versión 2.20 de Git, y a diferencia de cuando se hace push con git-push(1), cualquier actualización a refs/tags/* se aceptaba sin un + en el refspec (o --force). Al obtener, considerábamos promiscuamente que todas las actualizaciones de etiquetas de un remoto eran obtenciones forzadas. Desde la versión 2.20 de Git, obtener para actualizar refs/tags/* funciona de la misma manera que al hacer push. Es decir, cualquier actualización se rechazará sin un + en el refspec (o --forc

e).

A diferencia de cuando se hace push con git-push(1), cualquier actualización fuera de refs/{tags,heads}/* se aceptará sin un + en el refspec (o --force), ya sea que se esté cambiando, por ejemplo, un objeto árbol por un blob, o un commit por otro commit que no tiene el commit anterior como ancestro,

etc.

A diferencia de cuando se hace push con h.1.en'>git-push(1), no existe ninguna configuración que modifique estas reglas, ni nada parecido a un hook pre-fetch análogo al hook pre-receive.

Al igual que al hacer push con git-push(1), todas las reglas descritas anteriormente sobre lo que no está permitido como actualización pueden anularse añadiendo un signo + opcional al principio de una refspec (o usando la opción de línea de comandos --force). La única excepción es que ninguna cantidad de fuerza hará que el espacio de nombres refs/heads/* acepte un objeto que no sea un commit.


Nota
Cuando se sabe que la rama remota que se desea obtener se rebobina y se rebase regularmente, se espera que su nueva punta no sea descendiente de su punta anterior (tal como se almacena en su rama de seguimiento remoto la última vez que se obtuvo). Querrá usar el signo + para indicar que se necesitarán actualizaciones no fast-forward para dichas ramas. No hay forma de determinar o declarar que una rama estará disponible en un repositorio con este comportamiento; el usuario que extrae simplemente debe saber que este es el patrón de uso esperado para una rama.

--stdin

Lee las refspecs, una por línea, desde stdin además de las proporcionadas como argumentos. El formato "tag <nombre>" no es compatible.

URLS DE GIT

En general, las URL contienen información sobre el protocolo de transporte, la dirección del servidor remoto y la ruta al repositorio. Dependiendo del protocolo de transporte, parte de esta información puede estar ausente.

Git soporta los protocolos ssh, git, http y https (además, ftp y ftps se pueden usar para obtener, pero esto es ineficiente y está obsoleto; no los use).

El transporte nativo (es decir, la URL git://) no realiza ninguna autenticación y debe usarse con precaución en redes no seguras.

Se pueden usar las siguientes sintaxis con ellos:

•ssh://[<usuario>@]<host>[:<puerto>]/<ruta-al-repositorio-git>
•git://<host>[:<puerto>]/<ruta-al-repositorio-git>
•http[s]://<host>[:<puerto>]/<ruta-al-repositorio-git>
•ftp[s]://<host>[:<puerto>]/<ruta-al-repositorio-git>

También se puede usar una sintaxis alternativa similar a scp con el protocolo ssh:

•[<usuario>@]<host>:/<ruta-al-repositorio-git>

Esta sintaxis solo se reconoce si no hay barras antes de los dos puntos. Esto ayuda a diferenciar una ruta local que contiene dos puntos. Por ejemplo, la ruta local foo:bar podría especificarse como una ruta absoluta o como ./foo:bar para evitar ser malinterpretada como una URL ssh.

Los protocolos ssh y git admiten además la expansión de ~<nombredeusuario>:

•ssh://[<usuario>@]<host>[:<puerto>]/~<usuario>/<ruta-al-repositorio-git>
•git://<host>[:<puerto>]/~<usuario>/<ruta-al-repositorio-git>
•[<usuario>@]<host>:~<usuario>/<ruta-al-repositorio-git>

Para repositorios locales, también soportados de forma nativa por Git, se pueden usar las siguientes sintaxis:

•/ruta/al/repositorio.git/
•file:///ruta/al/repositorio.git/

Estas dos sintaxis son en su mayoría equivalentes, excepto al clonar, donde la primera implica la opción --local. Consulte git-clone(1) para obtener detalles.

git clone, git fetch y git pull, pero no git push, también aceptarán un archivo bundle adecuado. Consulte git-bundle(1).

Cuando Git no sabe cómo manejar un determinado protocolo de transporte, intenta usar el ayudante de remotos remote-<transporte>, si existe. Para solicitar explícitamente un ayudante de remotos, se puede usar la siguiente sintaxis:

•<transporte>::<direccion>

donde <direccion> puede ser una ruta, un servidor y una ruta, o una cadena arbitraria similar a una URL reconocida por el ayudante de remotos específico que se está invocando. Consulte gitremote-helpers(7) para obtener detalles.

Si hay un gran número de repositorios remotos con nombres similares y desea utilizar un formato diferente para ellos (de manera que las URL que utilice se reescriban en URL que funcionen), puede crear una sección de configuración del tipo:

        [url "<base-url-real>"]
                insteadOf = <base-url-otra>

Por ejemplo, con esto:

        [url "git://git.host.xz/"]
                insteadOf = host.xz:/path/to/
                insteadOf = work:

Una URL como "work:repo.git" o como "host.xz:/path/al/repo.git" se reescribirá en cualquier contexto que acepte una URL para ser "git://git.host.xz/repo.git".

Si desea reescribir URL solo para push, puede crear una sección de configuración del tipo:

        [url "<base-url-real>"]
                pushInsteadOf = <base-url-otra>

Por ejemplo, con esto:

        [url "ssh://example.org/"]
                pushInsteadOf = git://example.org/

una URL como "git://example.org/ruta/al/repo.git" se reescribirá a "ssh://example.org/ruta/al/repo.git" para los push, pero los pull seguirán usando la URL original.

REMOTE

El nombre de uno de los siguientes puede usarse en lugar de una URL como argumento <repositorio>:

•un remoto en el archivo de configuración de Git: $GIT_DIR/config,
•un archivo en el directorio $GIT_DIR/remotes, o
•un archivo en el directorio $GIT_DIR/branches.

Todos estos también le permiten omitir la refspec de la línea de comandos porque cada uno contiene una refspec que git usará por defecto.

Remoto nombrado en el archivo de configuración

Puede optar por proporcionar el nombre de un remoto que haya configurado previamente usando git-remote(1), git-config(1) o incluso mediante una edición manual del archivo $GIT_DIR/config. La URL de este remoto se utilizará para acceder al repositorio. La refspec de este remoto se utilizará por defecto cuando no proporcione una refspec en la línea de comandos. La entrada en el archivo de configuración aparecería así:

        [remote "<nombre>"]
                url = <URL>
                pushurl = <pushurl>
                push = <refspec>
                fetch = <refspec>

El <pushurl> se utiliza solo para los push. Es opcional y por defecto es <URL>. El push a un remoto afecta a todos los pushurls definidos o a todas las urls definidas si no se definen pushurls. Sin embargo, fetch solo obtendrá de la primera url definida si se definen múltiples urls.

Archivo nombrado en $GIT_DIR/remotes

Puede optar por proporcionar el nombre de un archivo en $GIT_DIR/remotes. La URL en este archivo se utilizará para acceder al repositorio. La refspec en este archivo se utilizará por defecto cuando no proporcione una refspec en la línea de comandos. Este archivo debe tener el siguiente formato:

        URL: uno de los formatos de URL anteriores
        Push: <refspec>
        Pull: <refspec>

Las líneas Push: son utilizadas por git push y las líneas Pull: son utilizadas por git pull y git fetch. Se pueden especificar múltiples líneas Push: y Pull: para mapeos de ramas adicionales.

Archivo nombrado en $GIT_DIR/branches

Puede optar por proporcionar el nombre de un archivo en $GIT_DIR/branches. La URL en este archivo se utilizará para acceder al repositorio. Este archivo debe tener el siguiente formato:

        <URL>#<head>

<URL> es obligatorio; #<head> es opcional.

Dependiendo de la operación, git utilizará una de las siguientes refspecs, si no proporciona una en la línea de comandos. <rama> es el nombre de este archivo en $GIT_DIR/branches y <head> por defecto es master.

git fetch usa:

        refs/heads/<head>:refs/heads/<rama>

git push usa:

        HEAD:refs/heads/<head>

RAMAS REMOTAS

Las ramas en Git pueden tener opcionalmente una rama remota upstream. Git utiliza por defecto la rama upstream para las operaciones remotas, por ejemplo:

•Es el valor por defecto para git pull o git fetch sin argumentos.
•Es el valor por defecto para git push sin argumentos, con algunas excepciones. Por ejemplo, puede usar la opción branch.<nombre>.pushRemote para hacer push a un remoto diferente al que hace pull, y por defecto con push.default=simple la rama upstream que configure debe tener el mismo nombre.
•Varios comandos, incluyendo git checkout y git status, le mostrarán cuántos commits se han añadido a su rama actual y a la rama upstream desde que se bifurcó de ella, por ejemplo "Su rama y origin/main han divergido, y tienen 2 y 3 commits diferentes cada una respectivamente".

El upstream se almacena en .git/config, en los campos "remote" y "merge". Por ejemplo, si el upstream de main es origin/main:

[branch "main"]
   remote = origin
   merge = refs/heads/main

Puede configurar explícitamente una rama upstream con git push --set-upstream <remote> <branch>, pero Git a menudo configurará automáticamente el upstream por ti, por

ejemplo:
•Cuando clonas un repositorio, Git configurará automáticamente el upstream para la rama
predeterminada.
•Si tienes la opción de configuración push.autoSetupRemote establecida, git push configurará automáticamente el upstream la primera vez que hagas push de una
rama.
•Al hacer checkout de una rama de seguimiento remoto con git checkout <branch> se creará automáticamente una rama local con ese nombre y se establecerá el upstream a la rama remota.
Nota

Las ramas upstream a veces se denominan "información de seguimiento", como en "establecer la información de seguimiento de la rama".

POD

A

Git tiene una disposición predeterminada de conservar los datos a menos que se descarten explícitamente; esto se extiende a mantener referencias locales a ramas en remotos que han eliminado esas ramas ellos

mismos.

Si se acumulan, estas referencias obsoletas podrían empeorar el rendimiento en repositorios grandes y activos con mucho cambio de ramas y, por ejemplo, hacer que la salida de comandos como git branch -a --contains <commit> sea innecesariamente verbosa, así como afectar a cualquier otra cosa que trabaje con el conjunto completo de referencias

conocidas.

Estas referencias de seguimiento remoto pueden eliminarse de una vez con cualquiera de los

siguientes: 
# Mientras se obtiene
$ git fetch
--prune <name> # Solo podar, no
obtener $ git remote prune <name>

Para podar referencias como parte de tu flujo de trabajo normal sin necesidad de recordar ejecutar eso, establece fetch.prune globalmente, o remote.<name>.prune por remoto en la configuración. Ver git-confi

g(1).

Aquí es donde las cosas se vuelven complicadas y más específicas. La función de poda no se preocupa realmente por las ramas, sino que podará referencias locales ←→ remotas como una función del refspec del remoto (ver <refspec> y RAMAS DE SEGUIMIENTO REMOTO CONFIGURADAS arriba)

.

Por lo tanto, si el refspec para el remoto incluye, por ejemplo, refs/tags/*:refs/tags/*, o ejecutas manualmente, por ejemplo, git fetch --prune <name> "refs/tags/*:refs/tags/*", no serán ramas de seguimiento remoto obsoletas las que se eliminen, sino cualquier etiqueta local que no exista en el

remoto.

Esto puede no ser lo que esperas, es decir, quieres podar el remoto <name>, pero también obtener explícitamente sus etiquetas, de modo que cuando obtengas de él elimines todas tus etiquetas locales, la mayoría de las cuales pueden no haber provenido del remoto <name> en primer

lugar.

Así que ten cuidado al usar esto con un refspec como refs/tags/*:refs/tags/*, o cualquier otro refspec que pueda mapear referencias de múltiples remotos al mismo espacio de nombres

local.

Dado que mantenerse al día con tanto las ramas como las etiquetas en el remoto es un caso de uso común, se puede proporcionar la opción --prune-tags junto con --prune para podar etiquetas locales que no existen en el remoto y forzar la actualización de aquellas que difieren. La poda de etiquetas también se puede habilitar con fetch.pruneTags o remote.<name>.pruneTags en la configuración. Ver git-confi

g(1).

La opción --prune-tags es equivalente a tener refs/tags/*:refs/tags/* declarado en los refspecs del remoto. Esto puede llevar a algunas interacciones aparentemente

extrañas: 
# Ambos obtienen etiquetas
$ git fetch --
no-tags origin 'refs/tags/*:refs/tags/*'
$ git fetch --no-tags --prune-tags origin

La razón por la que no produce un error cuando se proporciona sin --prune o sus versiones de configuración es por flexibilidad de las versiones configuradas, y para mantener un mapeo 1=1 entre lo que hacen los indicadores de la línea de comandos y lo que hacen las versiones de

configuración.

Es razonable, por ejemplo, configurar fetch.pruneTags=true en ~/.gitconfig para tener las etiquetas podadas siempre que se ejecute git fetch --prune, sin hacer que cada invocación de git fetch sin --prune sea un

error.

Podar etiquetas con --prune-tags también funciona al obtener una URL en lugar de un remoto con nombre. Todos estos podarán las etiquetas que no se encuentren en

origin: 
$ git fetch origin --prune --prune-tags
$ git fetch
origin --prune 'refs/tags/*:refs/tags/*' $ git fet
ch <url-of-origin> --prune --prune-tags $ git fetc
h <url-of-origin> --prune 'refs/tags/*:refs/tags/*'
