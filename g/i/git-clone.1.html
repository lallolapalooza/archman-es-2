GIT-CLONE(1) Manual de Git GIT-CLONE(1)

NOMBRE

git-clone - Clonar un repositorio en un nuevo directorio

SINOPSIS

git clone [--template=<directorio-plantilla>]
          [-l] [-s] [--no-hardlinks] [-q] [-n] [--bare] [--mirror]
          [-o <nombre>] [-b <nombre>] [-u <upload-pack>] [--reference <repositorio>]
          [--dissociate] [--separate-git-dir <dir-git>]
          [--depth <profundidad>] [--[no-]single-branch] [--[no-]tags]
          [--recurse-submodules[=<ruta-patron>]] [--[no-]shallow-submodules]
          [--[no-]remote-submodules] [--jobs <n>] [--sparse] [--[no-]reject-shallow]
          [--filter=<espec-filtro> [--also-filter-submodules]] [--] <repositorio>
          [<directorio>]

DESCRIPCIÓN

Clona un repositorio en un directorio recién creado, crea ramas de seguimiento remoto para cada rama en el repositorio clonado (visibles usando git branch --remotes), y crea y descarga una rama inicial que se bifurca de la rama actualmente activa del repositorio clonado.

Después de clonar, un simple git fetch sin argumentos actualizará todas las ramas de seguimiento remoto, y un git pull sin argumentos además fusionará la rama maestra remota en la rama maestra actual, si existe (esto no es cierto cuando se da --single-branch; ver más abajo).

Esta configuración predeterminada se logra creando referencias a las cabeceras de rama remotas bajo refs/remotes/origin y inicializando las variables de configuración remote.origin.url y remote.origin.fetch.

OPCIONES

-l, --local

Cuando el repositorio a clonar está en una máquina local, esta bandera omite el mecanismo de transporte normal "consciente de Git" y clona el repositorio haciendo una copia de HEAD y todo lo que está bajo los directorios objects y refs. Los archivos bajo el directorio .git/objects/ se enlazan físicamente para ahorrar espacio cuando sea posible.

Si el repositorio se especifica como una ruta local (por ejemplo, /ruta/a/repo), este es el valor predeterminado, y --local es esencialmente una operación nula. Si el repositorio se especifica como una URL, esta bandera se ignora (y nunca usamos las optimizaciones locales). Especificar --no-local anulará el valor predeterminado cuando se proporcione /ruta/a/repo, utilizando el transporte Git normal en su lugar.

Si $GIT_DIR/objects del repositorio tiene enlaces simbólicos o es un enlace simbólico, la clonación fallará. Esta es una medida de seguridad para prevenir la copia no intencionada de archivos al seguir los enlaces simbólicos.

Esta opción no funciona con repositorios propiedad de otros usuarios por razones de seguridad, y se debe especificar --no-local para que la clonación tenga éxito.

NOTA: esta operación puede entrar en competencia con modificaciones concurrentes del repositorio de origen, similar a ejecutar cp -r <origen> <destino> mientras se modifica <origen>.

--no-hardlinks

Fuerza el proceso de clonación desde un repositorio en el sistema de archivos local a copiar los archivos bajo el directorio .git/objects en lugar de usar enlaces físicos. Esto puede ser deseable si está intentando hacer una copia de seguridad de su repositorio.

-s, --shared

Cuando el repositorio a clonar está en la máquina local, en lugar de usar enlaces físicos, configura automáticamente .git/objects/info/alternates para compartir los objetos con el repositorio de origen. El repositorio resultante comienza sin ningún objeto propio.

NOTA: esta es una operación potencialmente peligrosa; no la use a menos que entienda lo que hace. Si clona su repositorio usando esta opción y luego elimina ramas (o utiliza cualquier otro comando de Git que haga que cualquier commit existente no sea referenciado) en el repositorio de origen, algunos objetos pueden volverse no referenciados (o colgarse). Estos objetos pueden ser eliminados por operaciones normales de Git (como git commit) que llaman automáticamente a git maintenance run --auto. (Ver git-maintenance(1)). Si estos objetos se eliminan y eran referenciados por el repositorio clonado, entonces el repositorio clonado se corromperá.

Tenga en cuenta que ejecutar git repack sin la opción --local en un repositorio clonado con --shared copiará los objetos del repositorio de origen en un paquete en el repositorio clonado, eliminando el ahorro de espacio en disco de clone --shared. Sin embargo, es seguro ejecutar git gc, que utiliza la opción --local por defecto.

Si desea romper la dependencia de un repositorio clonado con --shared en su repositorio de origen, simplemente puede ejecutar git repack -a para copiar todos los objetos del repositorio de origen en un paquete en el repositorio clonado.

--reference[-if-able] <repositorio>

Si el repositorio de referencia <repositorio> está en la máquina local, configura automáticamente .git/objects/info/alternates para obtener objetos del repositorio de referencia <repositorio>. El uso de un repositorio ya existente como alternativo requerirá menos objetos para ser copiados del repositorio que se está clonando, reduciendo los costos de red y almacenamiento local. Al usar --reference-if-able, un directorio no existente se omite con una advertencia en lugar de abortar la clonación.

NOTA: ver la NOTA para la opción --shared, y también la opción --dissociate.

--dissociate

Toma prestados los objetos de los repositorios de referencia especificados con las opciones --reference solo para reducir la transferencia de red, y deja de tomarlos prestados después de que se crea una clonación realizando las copias locales necesarias de los objetos prestados. Esta opción también se puede usar al clonar localmente desde un repositorio que ya toma prestados objetos de otro repositorio; el nuevo repositorio tomará prestados objetos del mismo repositorio, y esta opción se puede usar para detener el préstamo.

-q, --quiet

Operar en silencio. El progreso no se informa al flujo de error estándar.

-v, --verbose

Ejecutar de forma verbosa. No afecta el informe del estado de progreso al flujo de error estándar.

--progress

El estado de progreso se informa en el flujo de error estándar por defecto cuando está conectado a una terminal, a menos que se especifique --quiet. Esta bandera fuerza el estado de progreso incluso si el flujo de error estándar no está dirigido a una terminal.

--server-option=<opcion>

Transmite la cadena dada al servidor al comunicarse utilizando el protocolo versión 2. La cadena dada no debe contener un carácter NUL o LF. El manejo de las opciones del servidor por parte del servidor, incluidas las desconocidas, es específico del servidor. Cuando se dan múltiples --server-option=<opcion>, todas se envían al otro lado en el orden en que aparecen en la línea de comandos. Cuando no se proporciona ninguna --server-option=<opcion> desde la línea de comandos, se utilizan los valores de la variable de configuración remote.<nombre>.serverOption.

-n, --no-checkout

No se realiza ningún checkout de HEAD después de que la clonación se completa.

--[no-]reject-shallow

Falla si el repositorio de origen es un repositorio superficial. La variable de configuración clone.rejectShallow se puede utilizar para especificar el valor predeterminado.

--bare

Crea un repositorio Git *desnudo* (bare). Es decir, en lugar de crear <directorio> y colocar los archivos administrativos en <directorio>/.git, se crea el propio <directorio> como el $GIT_DIR. Esto obviamente implica --no-checkout porque no hay dónde hacer checkout del árbol de trabajo. Además, las cabeceras de rama en el remoto se copian directamente a las cabeceras de rama locales correspondientes, sin mapearlas a refs/remotes/origin/. Cuando se utiliza esta opción, ni las ramas de seguimiento remoto ni las variables de configuración relacionadas se crean.

--mirror

Crea un repositorio *desnudo* y además configura el repositorio para que todas las ramas y etiquetas remotas se reflejen exactamente como en el repositorio remoto. En particular, cualquier rama o etiqueta eliminada en el remoto será eliminada en el clonado y cualquier rama nueva en el remoto se creará en el clonado.

--filter=<espec-filtro>

Utiliza un filtro de contenido para reducir la cantidad de datos descargados. Ver git-sparse-checkout(1) para obtener más información sobre el formato de las especificaciones de filtro.

--also-filter-submodules

Cuando se clona un repositorio que contiene submódulos, aplique el mismo filtro de contenido a los submódulos que se aplican al repositorio principal.

--recurse-submodules[=<ruta-patron>]

Por defecto, los submódulos no se clonan. Cuando esta opción se especifica, se clonan automáticamente los submódulos que se encuentran en el repositorio clonado. Esto se hace recursivamente, es decir, los submódulos de los submódulos también se clonan.

Si se proporciona un <ruta-patron>, solo se incluirán los submódulos que coincidan con las rutas especificadas.

--jobs <n>

Número de procesos paralelos a usar cuando se clonan submódulos.

--shallow-submodules

Los submódulos se clonan superficialmente.

--no-remote-submodules

No clonar submódulos que están configurados para ser remotos.

--template=<directorio-plantilla>

Especifica un directorio de plantilla. Los objetos del repositorio de plantilla se copiarán en el nuevo repositorio de Git. Sin embargo, el contenido del árbol de trabajo no se copiará. Esto se puede usar para configurar un nuevo repositorio con una estructura de directorios común, ganchos de Git pre-escritos, etc. El valor predeterminado es $GIT_TEMPLATE_DIR si está configurado, o el archivo especificado por la variable de configuración init.templateDir.

--separate-git-dir <dir-git>

En lugar de colocar el directorio .git dentro del directorio de destino, se creará el directorio <dir-git> y se colocará el contenido del directorio .git allí. Esto es útil para mantener los repositorios de Git centralizados o para crear repositorios virtuales.

--depth <profundidad>

Crea un *clon superficial* (shallow clone), que tiene un historial de solo <profundidad> commits. Los repositorios superficiales son útiles para descargar solo los cambios más recientes, ya que se descargan menos datos. La profundidad puede ser una cadena de números positivos (ej. --depth 10) o puede ser "history" para clonar sin ningún commit de historial.

Cuando se usa con la opción --shallow-since o --shallow-exclude, la profundidad se determina automáticamente.

Si se usa con --unshallow, se descargará el historial completo.

--shallow-since=<fecha>

Crea un clon superficial con todos los commits desde la fecha especificada.

--shallow-exclude=<rev>

Crea un clon superficial excluyendo todos los commits anteriores al commit especificado.

--single-branch

Clona solo la rama remota de la que se está haciendo checkout. Por defecto, se clonan todas las ramas remotas.

--no-tags

No clonar ninguna etiqueta. Por defecto, todas las etiquetas en el repositorio remoto se clonan.

--sparse

Emplea un checkout disperso, con solo los archivos del directorio raíz presentes inicialmente. El comando git-sparse-checkout(1) puede utilizarse posteriormente para añadir o eliminar archivos del árbol de trabajo.

--

Separa los argumentos de la línea de comandos que se pasan a git de los argumentos que se pasan a la aplicación externa (por ejemplo, ssh).

<repositorio>

El repositorio remoto que se va a clonar. Puede ser una URL (por ejemplo, https://github.com/git/git.git) o una ruta local (por ejemplo, /git/repo/.git).

<directorio>

El nombre del nuevo directorio en el que se clonará el repositorio. Si no se proporciona, se crea un directorio con el mismo nombre que el repositorio remoto (el último componente de la ruta del repositorio).

EJEMPLOS

Clonar el repositorio de Git desde la URL proporcionada en un nuevo directorio llamado `my-git`: 
$ git clone https://github.com/git/git.git my-git

Clonar el repositorio de Git desde la URL proporcionada en el directorio actual, que se llamará `git`: 
$ git clone https://github.com/git/git.git

Clonar el repositorio de Git desde la URL proporcionada, pero solo obtener los últimos 10 commits: 
$ git clone --depth 10 https://github.com/git/git.git

Clonar el repositorio de Git desde la URL proporcionada, pero sin hacer checkout de la rama principal: 
$ git clone --no-checkout https://github.com/git/git.git

Clonar el repositorio de Git desde la URL proporcionada, sin clonar ninguna etiqueta: 
$ git clone --no-tags https://github.com/git/git.git

Clonar el repositorio de Git desde la URL proporcionada, solo la rama `develop`: 
$ git clone --branch develop --single-branch https://github.com/git/git.git

Clonar el repositorio de Git desde la URL proporcionada, utilizando el repositorio local `../my-repo` como alternativa para ahorrar ancho de banda: 
$ git clone --reference ../my-repo https://github.com/git/git.git

Clonar el repositorio de Git desde la URL proporcionada, creando un repositorio desnudo (bare) en el directorio `my-git.git`: 
$ git clone --bare https://github.com/git/git.git my-git.git

Clonar el repositorio de Git desde la URL proporcionada, utilizando un filtro de contenido para descargar solo los objetos necesarios para la rama `main`: 
$ git clone --filter=blob:none --single-branch --branch main https://github.com/git/git.git

--filter=<especificación-filtro>

Utiliza la función de clonación parcial y solicita al servidor que envíe un subconjunto de objetos alcanzables según un filtro de objetos dado. Al usar --filter, se utiliza la <especificación-filtro> proporcionada para el filtro de clonación parcial. Por ejemplo, --filter=blob:none filtrará todos los blobs (contenidos de archivos) hasta que Git los necesite. Además, --filter=blob:limit=<tamaño> filtrará todos los blobs de tamaño igual o superior a <tamaño>. Para más detalles sobre las especificaciones de filtros, consulta la opción --filter en git-rev-list(1).

--also-filter-submodules

Aplica también el filtro de clonación parcial a los submodules del repositorio. Requiere --filter y --recurse-submodules. Esto se puede activar por defecto estableciendo la opción de configuración clone.filterSubmodules.

--mirror

Configura un espejo del repositorio de origen. Esto implica --bare. En comparación con --bare, --mirror no solo mapea las ramas locales del origen a ramas locales del destino, sino que mapea todos los refs (incluyendo ramas de seguimiento remoto, notas, etc.) y configura una refspec que garantiza que todos estos refs sean sobrescritos por un git remote update en el repositorio de destino.

-o <nombre>, --origin <nombre>

En lugar de usar el nombre de remoto origin para hacer seguimiento del repositorio upstream, usa <nombre>. Anula clone.defaultRemoteName de la configuración.

-b <nombre>, --branch <nombre>

En lugar de apuntar el HEAD recién creado a la rama a la que apunta el HEAD del repositorio clonado, apunta a la rama <nombre> en su lugar. En un repositorio no bare, esta será la rama que se verificará. --branch también puede tomar etiquetas y desacopla el HEAD en ese commit en el repositorio resultante.

--revision=<rev>

Crea un nuevo repositorio y descarga el historial que lleva a la revisión dada <rev> (y nada más), sin crear ninguna rama de seguimiento remoto, ni ninguna rama local, y desacopla el HEAD a <rev>. El argumento puede ser un nombre de ref (por ejemplo, refs/heads/main o refs/tags/v1.0) que se resuelve en un commit, o un nombre de objeto hexadecimal. Esta opción es incompatible con --branch y --mirror.

-u <upload-pack>, --upload-pack <upload-pack>

Cuando se especifica y el repositorio a clonar se accede vía ssh, esto especifica una ruta no predeterminada para el comando que se ejecuta en el extremo remoto.

--template=<directorio-plantilla>

Especifica el directorio desde el cual se usarán las plantillas; (ver la sección "DIRECTORIO DE PLANTILLAS" de git-init(1)).

-c <clave>=<valor>, --config <clave>=<valor>

Establece una variable de configuración en el repositorio recién creado; esto tiene efecto inmediatamente después de que el repositorio sea inicializado, pero antes de que se descargue el historial remoto o se verifiquen los archivos. La <clave> está en el mismo formato que se espera en git-config(1) (por ejemplo, core.eol=true). Si se proporcionan múltiples valores para la misma clave, cada valor se escribirá en el archivo de configuración. Esto permite, por ejemplo, añadir refspecs de fetch adicionales al remoto 'origin'.

Debido a limitaciones de la implementación actual, algunas variables de configuración no surten efecto hasta después del fetch y checkout inicial. Las variables de configuración que se sabe que no surten efecto son: remote.<nombre>.mirror y remote.<nombre>.tagOpt. Usa las opciones correspondientes --mirror y --no-tags en su lugar.

--depth <profundidad>

Crea un clon *shallow* con un historial truncado al número especificado de commits. Implica --single-branch a menos que se indique --no-single-branch para descargar los historiales cerca de las puntas de todas las ramas. Si deseas clonar submodules de forma shallow, también pasa --shallow-submodules.

--shallow-since=<fecha>

Crea un clon shallow con un historial posterior a la fecha especificada.

--shallow-exclude=<ref>

Crea un clon shallow con un historial, excluyendo los commits alcanzables desde una rama o etiqueta remota especificada. Esta opción se puede especificar varias veces.

--single-branch, --no-single-branch

Clona solo el historial que lleva a la punta de una única rama, ya sea especificada por la opción --branch o la rama principal a la que apunta el HEAD del remoto. Futuros fetches en el repositorio resultante solo actualizarán la rama de seguimiento remoto para la rama para la cual se usó esta opción durante la clonación inicial. Si el HEAD en el remoto no apuntaba a ninguna rama cuando se hizo la clonación con --single-branch, no se crea ninguna rama de seguimiento remoto.

--tags, --no-tags

Controla si se clonan las etiquetas o no. Cuando se indica --no-tags, la opción se volverá permanente estableciendo la configuración remote.<remoto>.tagOpt=--no-tags. Esto asegura que futuros git pull y git fetch no seguirán ninguna etiqueta. Fetchs de etiquetas explícitos posteriores seguirán funcionando (ver git-fetch(1)).

Por defecto, las etiquetas se clonan y pasar --tags es típicamente una operación nula, a menos que cancele un --no-tags anterior.

Se puede usar en conjunción con --single-branch para clonar y mantener una rama sin referencias aparte de una única rama clonada. Esto es útil, por ejemplo, para mantener clones mínimos de la rama por defecto de algún repositorio para indexación de búsqueda.

--recurse-submodules[=<pathspec>]

Después de que el clon sea creado, inicializa y clona los submodules dentro basándose en el <pathspec> proporcionado. Si no se proporciona =<pathspec>, se inicializan y clonan todos los submodules. Esta opción puede ser dada múltiples veces para pathspecs que consisten en múltiples entradas. El clon resultante tiene submodule.active configurado al pathspec proporcionado, o "." (lo que significa todos los submodules) si no se proporciona pathspec.

Los submodules se inicializan y clonan usando su configuración predeterminada. Esto es equivalente a ejecutar git submodule update --init --recursive <pathspec> inmediatamente después de que el clon finalice. Esta opción se ignora si el repositorio clonado no tiene un árbol de trabajo/checkout (es decir, si se da alguna de las opciones --no-checkout/-n, --bare, o --mirror)

--shallow-submodules, --no-shallow-submodules

Todos los submodules que se clonen serán shallow con una profundidad de 1.

--remote-submodules, --no-remote-submodules

Todos los submodules que se clonen usarán el estado de la rama de seguimiento remoto del submodule para actualizar el submodule, en lugar del SHA-1 registrado en el superproyecto. Equivalente a pasar --remote a git submodule update.

--separate-git-dir=<git-dir>

En lugar de colocar el repositorio clonado donde debería estar, colócalo en el directorio especificado y luego crea un enlace simbólico agnóstico al sistema de archivos de Git hacia allí. El resultado es que el repositorio de Git puede separarse del árbol de trabajo.

--ref-format=<formato-ref>

Especifica el formato de almacenamiento de refs dado para el repositorio. Los valores válidos son:
•files para archivos sueltos con refs empaquetados. Este es el valor predeterminado.
•reftable para el formato reftable. Este formato es experimental y sus internos están sujetos a cambios.

-j <n>, --jobs <n>

El número de submodules que se obtienen simultáneamente. El valor predeterminado es la opción submodule.fetchJobs.

<repositorio>

El <repositorio> (posiblemente remoto) desde el cual clonar. Consulta la sección URLS DE GIT a continuación para más información sobre cómo especificar repositorios.

<directorio>

El nombre de un nuevo directorio en el cual clonar. La parte "humanesca" del repositorio de origen se utiliza si no se proporciona un <directorio> explícitamente (repo para /path/to/repo.git y foo para host.xz:foo/.git). Clonar en un directorio existente solo está permitido si el directorio está vacío.

--bundle-uri=<uri>

Antes de obtener del remoto, obtén un bundle desde la <uri> dada y desempaqueta los datos en el repositorio local. Los refs en el bundle se almacenarán bajo el espacio de nombres oculto refs/bundle/*. Esta opción es incompatible con --depth, --shallow-since y --shallow-exclude.

URLS DE GIT

En general, las URLs contienen información sobre el protocolo de transporte, la dirección del servidor remoto y la ruta al repositorio. Dependiendo del protocolo de transporte, parte de esta información puede estar ausente.

Git soporta los protocolos ssh, git, http, y https (además, ftp y ftps pueden usarse para obtener, pero esto es ineficiente y obsoleto; no los uses).

El transporte nativo (es decir, URL git://) no realiza autenticación y debe usarse con precaución en redes no seguras.

Se pueden usar las siguientes sintaxis con ellos:

•ssh://[<usuario>@]<host>[:<puerto>]/<ruta-al-repositorio-git>
•git://<host>[:<puerto>]/<ruta-al-repositorio-git>
•http[s]://<host>[:<puerto>]/<ruta-al-repositorio-git>
•ftp[s]://<host>[:<puerto>]/<ruta-al-repositorio-git>

También se puede usar una sintaxis alternativa similar a scp con el protocolo ssh:

•[<usuario>@]<host>:/<ruta-al-repositorio-git>

Esta sintaxis solo se reconoce si no hay barras antes de los dos puntos iniciales. Esto ayuda a diferenciar una ruta local de una remota.

at contiene dos puntos. Por ejemplo, la ruta local foo:bar podría especificarse como una ruta absoluta o ./foo:bar para evitar que se interprete como una url ssh.

Los protocolos ssh y git además soportan la expansión de ~<username> :

•ssh://[<user>@]<host>[:<port>]/~<user>/<path-to-git-repo>
•git://<host>[:<port>]/~<user>/<path-to-git-repo>
•[<user>@]<host>:~<user>/<path-to-git-repo>

Para los repositorios locales, también soportados nativamente por Git, pueden usarse las siguientes sintaxis:

•/path/to/repo.git/
•file:///path/to/repo.git/

Estas dos sintaxis son mayormente equivalentes, excepto que la primera implica la opción --local .

git clone, git fetch y git pull, pero no git push, también aceptarán un archivo bundle adecuado. Véase git-bundle(1).

Cuando Git no sabe cómo manejar un cierto protocolo de transporte, intenta usar el helper remoto remote-<transport> , si existe. Para solicitar explícitamente un helper remoto, puede usarse la siguiente sintaxis:

•<transport>::<address>

donde <address> puede ser una ruta, un servidor y una ruta, o una cadena similar a una URL reconocida por el helper remoto específico que se invoca. Véase gitremote-helpers(7) para más detalles.

Si hay un gran número de repositorios remotos con nombres similares y desea usar un formato diferente para ellos (de modo que las URLs que use se reescriban en URLs que funcionen), puede crear una sección de configuración de la forma:

        [url "<actual-url-base>"]
                insteadOf = <other-url-base>

Por ejemplo, con esto:

        [url "git://git.host.xz/"]
                insteadOf = host.xz:/path/to/
                insteadOf = work:

una URL como "work:repo.git" o como "host.xz:/path/to/repo.git" será reescrita en cualquier contexto que tome una URL para ser "git://git.host.xz/repo.git".

Si desea reescribir URLs solo para push, puede crear una sección de configuración de la forma:

        [url "<actual-url-base>"]
                pushInsteadOf = <other-url-base>

Por ejemplo, con esto:

        [url "ssh://example.org/"]
                pushInsteadOf = git://example.org/

una URL como "git://example.org/path/to/repo.git" será reescrita a "ssh://example.org/path/to/repo.git" para los pushes, pero los pulls seguirán usando la URL original.

EJEMPLOS

•Clonar desde el upstream: 
$ git clone git://git.kernel.org/pub/scm/.../linux.git my-linux
$ cd my-linux
$ make
•Hacer un clon local que toma prestado del directorio actual, sin hacer checkout de nada: 
$ git clone -l -s -n . ../copy
$ cd ../copy
$ git show-branch
•Clonar desde el upstream mientras se toma prestado de un directorio local existente: 
$ git clone --reference /git/linux.git \
        git://git.kernel.org/pub/scm/.../linux.git \
        my-linux
$ cd my-linux
•Crear un repositorio bare para publicar sus cambios al público: 
$ git clone --bare -l /home/proj/.git /pub/scm/proj.git
•Clonar un repositorio local de otro usuario: 
$ git clone --no-local /home/otheruser/proj.git /pub/scm/proj.git

CONFIGURACIÓN

Todo lo que hay debajo de esta línea en esta sección se incluye selectivamente desde la documentación de git-config(1) . El contenido es el mismo que el que se encuentra allí:

init.templateDir

Especifica el directorio desde el cual se copiarán las plantillas. (Véase la sección "DIRECTORIO DE PLANTILLAS" de git-init(1).)

init.defaultBranch

Permite anular el nombre de la rama predeterminado, por ejemplo, al inicializar un nuevo repositorio.

init.defaultObjectFormat

Permite anular el formato de objeto predeterminado para nuevos repositorios. Véase --object-format= en git-init(1). Tanto la opción de la línea de comandos como la variable de entorno GIT_DEFAULT_HASH tienen prioridad sobre esta configuración.

init.defaultRefFormat

Permite anular el formato de almacenamiento de referencias predeterminado para nuevos repositorios. Véase --ref-format= en git-init(1). Tanto la opción de la línea de comandos como la variable de entorno GIT_DEFAULT_REF_FORMAT tienen prioridad sobre esta configuración.

clone.defaultRemoteName

El nombre del remoto a crear al clonar un repositorio. Por defecto es origin. Puede anularse pasando la opción de la línea de comandos --origin .

clone.rejectShallow

Rechaza clonar un repositorio si es uno poco profundo (shallow); esto puede anularse pasando la opción --reject-shallow en la línea de comandos.

clone.filterSubmodules

Si se proporciona un filtro de clonado parcial (véase --filter en git-rev-list(1)) y se usa --recurse-submodules , también se aplica el filtro a los submódulos.
