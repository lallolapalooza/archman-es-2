Ejecutar

bisect

Si tiene un script que puede decir si el código fuente actual es bueno o malo, puede hacer bisect emitiendo el

comando: 
$ git bisect
run my_scri
pt arguments

Tenga en cuenta que el script (my_script en el ejemplo anterior) debe salir con el código 0 si el código fuente actual es bueno/antiguo, y salir con un código entre 1 y 127 (inclusive), excepto 125, si el código fuente actual es

malo/nuevo.

Cualquier otro código de salida abortará el proceso de bisect. Debe tenerse en cuenta que un programa que termina mediante exit(-1) deja $? = 255, (vea la página de manual de exit(3)), ya que el valor se trunca con & 0377

.

El código de salida especial 125 debe usarse cuando el código fuente actual no se puede probar. Si el script sale con este código, la revisión actual será omitida (vea git bisect skip arriba). Se eligió 125 como el valor más alto razonable a usar para este propósito, porque 126 y 127 son usados por los shells POSIX para señalar un estado de error específico (127 es para comando no encontrado, 126 es para comando encontrado pero no ejecutable; estos detalles no importan, ya que son errores normales en el script, en lo que a bisect run se refiere)

.

A menudo puede encontrar que durante una sesión de bisect desea tener modificaciones temporales (por ejemplo, s/#define DEBUG 0/#define DEBUG 1/ en un archivo de cabecera, o "la revisión que no tiene este commit necesita este parche aplicado para sortear otro problema en el que esta bisección no está interesada") aplicadas a la revisión que se está

probando.

Para lidiar con tal situación, después de que el git bisect interno encuentre la siguiente revisión a probar, el script puede aplicar el parche antes de compilar, ejecutar la prueba real, y después decidir si la revisión (posiblemente con el parche necesario) pasó la prueba y luego rebobinar el árbol al estado prístino. Finalmente, el script debe salir con el estado de la prueba real para dejar que el git bisect run command loop determine

el resultado ev
entual de la se
sión de bisect.

--no-checkou

t
No hacer checkout del nuevo árbol de trabajo en cada iteración del proceso de bisección. En su lugar, solo actualizar la referencia llamada BISECT_HEAD para que apunte al commit que debe ser probado.

Esta opción puede ser útil cuando la prueba que realizaría en cada paso no requiere un árbol con

checkout.

Si el repositorio es desnudo, se asume --n

o-che
ckout.

--first-paren

t
Seguir solo el commit del primer padre al encontrar un commit de fusión.

Al detectar regresiones introducidas a través de la fusión de una rama, el commit de fusión será identificado como la introducción del error y sus ancestros serán

ignorados.

Esta opción es particularmente útil para ev

itar falsos positivos cuando una rama f
usionada contenía commits rotos o no compila
bles, pero la fusión en sí estaba bien.
