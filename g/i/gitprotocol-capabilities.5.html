GITPROTOCOL-CAPABILITIES(5) Manual de Git GITPROTOCOL-CAPABILITIES(5)

NOMBRE

gitprotocol-capabilities - Capacidades del protocolo v0 y v1

SINOPSIS

<protocolo-sobre-el-cable>

DESCRIPCIÓN


Nota

este documento describe las capacidades para las versiones 0 y 1 del protocolo pack. Para la versión 2, por favor consulte el documento gitprotocol-v2(5).

Los servidores DEBERÍAN admitir todas las capacidades definidas en este documento.

En la primera línea de la respuesta inicial del servidor de receive-pack y upload-pack, la primera referencia va seguida de un byte NUL y luego una lista de capacidades del servidor separadas por espacios. Estas permiten al servidor declarar lo que puede y no puede admitir al cliente.

El cliente enviará entonces una lista de capacidades separada por espacios que desea que estén en vigor. El cliente NO DEBE solicitar capacidades que el servidor no haya dicho que admite.

El servidor DEBE diagnosticar y abortar si se enviaron capacidades que no comprende. El servidor NO DEBE ignorar las capacidades que el cliente solicitó y que el servidor anunció. Como consecuencia de estas reglas, el servidor NO DEBE anunciar capacidades que no comprende.

Las capacidades atomic, report-status, report-status-v2, delete-refs, quiet y push-cert son enviadas y reconocidas por el proceso receive-pack (push al servidor).

Las capacidades ofs-delta y side-band-64k son enviadas y reconocidas por ambos protocolos, upload-pack y receive-pack. Las capacidades agent y session-id pueden ser enviadas opcionalmente en ambos protocolos.

Todas las demás capacidades solo son reconocidas por el proceso upload-pack (fetch desde el servidor).

MULTI_ACK

La capacidad multi_ack permite al servidor devolver "ACK obj-id continue" tan pronto como encuentre un commit que pueda utilizar como base común, entre lo que el cliente quiere y lo que el cliente tiene.

Al enviar esto temprano, el servidor puede potencialmente evitar que el cliente camine más por esa rama particular del historial del repositorio del cliente. El cliente aún puede necesitar caminar por otras ramas, enviando líneas de "have" para ellas, hasta que el servidor tenga un corte completo a través del DAG, o el cliente haya dicho "done".

Sin multi_ack, un cliente envía líneas de "have" en --date-order hasta que el servidor encuentre una base común. Eso significa que el cliente enviará líneas de "have" que el servidor ya sabe que son comunes, porque se solapan en el tiempo con otra rama en la que el servidor aún no ha encontrado una base común.

Por ejemplo, supongamos que el cliente tiene commits en mayúsculas que el servidor no tiene y el servidor tiene commits en minúsculas que el cliente no tiene, como en el siguiente diagrama:

   +---- u ---------------------- x
  /              +----- y
 /              /
a -- b -- c -- d -- E -- F
   \
    +--- Q -- R -- S

Si el cliente quiere x,y y empieza diciendo "have F,S", el servidor no sabe qué es F,S. Eventualmente el cliente dice "have d" y el servidor envía "ACK d continue" para que el cliente sepa dejar de caminar por esa línea (así que no envíes c-b-a), pero aún no ha terminado, necesita una base para x. El cliente sigue con S-R-Q, hasta que se alcanza a, en cuyo punto el servidor tiene una base clara y todo termina.

Sin multi_ack, el cliente habría enviado esa cadena c-b-a de todos modos, intercalada con S-R-Q.

MULTI_ACK_DETAILED

Esta es una extensión de multi_ack que permite al cliente comprender mejor el estado en memoria del servidor. Consulte la sección "Negociación de Packfile" de gitprotocol-pack(5) para más información.

NO-DONE

Esta capacidad solo debe usarse con el protocolo HTTP inteligente. Si multi_ack_detailed y no-done están presentes, entonces el remitente es libre de enviar inmediatamente un pack después de su primer mensaje "ACK obj-id ready".

Sin no-done en el protocolo HTTP inteligente, la sesión del servidor terminaría y el cliente tendría que hacer otro viaje para enviar "done" antes de que el servidor pueda enviar el pack. no-done elimina la última ronda y, por lo tanto, reduce ligeramente la latencia.

THIN-PACK

Un pack delgado es aquel con deltas que hacen referencia a objetos base no contenidos dentro del pack (pero que se sabe que existen en el extremo receptor). Esto puede reducir significativamente el tráfico de red, pero requiere que el extremo receptor sepa cómo "espesar" estos packs añadiendo las bases faltantes al pack.

El servidor upload-pack anuncia thin-pack cuando puede generar y enviar un pack delgado. Un cliente solicita la capacidad thin-pack cuando entiende cómo "espesarlo", notificando al servidor que puede recibir dicho pack. Un cliente NO DEBE solicitar la capacidad thin-pack si no puede convertir un pack delgado en un pack autocontenido.

Receive-pack, por otro lado, se asume por defecto que puede manejar packs delgados, pero puede pedirle al cliente que no use la función anunciando la capacidad no-thin. Un cliente NO DEBE enviar un pack delgado si el servidor anuncia la capacidad no-thin.

Las razones de esta asimetría son históricas. El programa receive-pack no existió hasta después de la invención de los packs delgados, por lo que históricamente la implementación de referencia de receive-pack siempre entendió los packs delgados. Agregar no-thin más tarde permitió a receive-pack deshabilitar la función de manera compatible con versiones anteriores.

SIDE-BAND, SIDE-BAND-64K

Esta capacidad significa que el servidor puede enviar, y el cliente puede entender, informes de progreso y información de errores multiplexados intercalados con el propio packfile.

Estas dos opciones son mutuamente excluyentes. Un cliente moderno siempre favorece side-band-64k.

Cualquiera de los modos indica que los datos del packfile se transmitirán divididos en paquetes de hasta 1000 bytes en el caso de side_band, o 65520 bytes en el caso de side_band_64k. Cada paquete consiste en una longitud de paquete de 4 bytes al principio, indicando cuántos datos hay en el paquete, seguida de un código de flujo de 1 byte y luego los datos reales.

El código de flujo puede ser uno de:

1 - datos del pack
2 - mensajes de progreso
3 - mensaje de error fatal justo antes de que se aborte el flujo

La capacidad "side-band-64k" surgió como una forma para que los clientes más nuevos que pueden manejar paquetes mucho más grandes soliciten paquetes que están casi llenos, manteniendo la compatibilidad con versiones anteriores para los clientes más antiguos.

Además, con side-band y sus mensajes de hasta 1000 bytes, en realidad son 999 bytes de carga útil y 1 byte para el código de flujo. Con side-band-64k, lo mismo, tienes hasta 65519 bytes de datos y 1 byte para el código de flujo.

El cliente DEBE enviar solo uno de "side-band" y "side-band-64k". El servidor DEBE diagnosticarlo como un error si el cliente solicita ambos.

OFS-DELTA

El servidor puede enviar, y el cliente puede entender, PACKv2 con deltas que hacen referencia a su base por posición en el pack en lugar de por un obj-id. Es decir, pueden enviar/leer OBJ_OFS_DELTA (también conocido como tipo 6) en un packfile.

AGENT

El servidor puede enviar opcionalmente una capacidad de la forma agent=X para notificar al cliente que el servidor está ejecutando la versión X. El cliente puede opcionalmente devolver su propia cadena de agente respondiendo con una capacidad agent=Y (pero NO DEBE hacerlo si el servidor no mencionó la capacidad agent). Las cadenas X e Y pueden contener cualquier carácter ASCII imprimible excepto espacio (es decir, el rango de bytes 32 < x < 127), y típicamente tienen el formato "paquete/versión" (por ejemplo, "git/1.8.3.1"). Las cadenas de agente son puramente informativas para fines estadísticos y de depuración, y NO DEBEN usarse para asumir programáticamente la presencia o ausencia de características particulares.

FORMATO-DE-OBJETO

Esta capacidad, que toma un algoritmo de hash como argumento, indica que el servidor soporta los algoritmos de hash dados. Puede enviarse varias veces; si es así, el primero dado es el que se usa en la publicación de las referencias.

Cuando la proporciona el cliente, indica que tiene la intención de usar el algoritmo de hash dado para comunicarse. El algoritmo proporcionado debe ser uno que el servidor soporte.

Si esta capacidad no se proporciona, se asume que el único algoritmo soportado es SHA-1.

SYMREF

Esta capacidad parametrizada se usa para informar al receptor qué referencia simbólica apunta a qué referencia; por ejemplo, "symref=HEAD:refs/heads/master" le dice al receptor que HEAD apunta a master. Esta capacidad puede repetirse para representar múltiples referencias simbólicas.

Los servidores DEBERÍAN incluir esta capacidad para la referencia simbólica HEAD si es una de las referencias que se están enviando.

Los clientes PUEDEN usar los parámetros de esta capacidad para seleccionar la rama inicial adecuada al clonar un repositorio.

SHALLOW

Esta capacidad añade los comandos "deepen", "shallow" y "unshallow" al protocolo fetch-pack/upload-pack para que los clientes puedan solicitar clones superficiales.

DEEPEN-SINCE

Esta capacidad añade el comando "deepen-since" al protocolo fetch-pack/upload-pack para que el cliente pueda solicitar clones superficiales que se cortan en un tiempo específico, en lugar de por profundidad. Internamente es equivalente a hacer "rev-list --max-age=<timestamp>" en el lado del servidor. "deepen-since" no puede usarse con "deepen".

DEEPEN-NOT

Esta capacidad añade el comando "deepen-not" al protocolo fetch-pack/upload-pack para que el cliente pueda solicitar clones superficiales que se cortan en una revisión específica, en lugar de por profundidad. Internamente es equivalente a hacer "rev-list --not <rev>" en el lado del servidor. "deepen-not" no puede usarse con "deepen", pero puede usarse con "deepen-since".

DEEPEN-RELATIVE

Si el cliente solicita esta capacidad, la semántica del comando "deepen" cambia. El argumento "depth" es la profundidad desde el límite superficial actual, en lugar de la profundidad desde las referencias remotas.

NO-PROGRESS

El cliente se inició con "git clone -q" o algo similar, y no quiere el canal lateral 2. Básicamente el cliente solo dice "No deseo recibir el flujo 2 en el canal lateral, así que no me lo envíes, y si lo hiciste, lo descartaré de todos modos". Sin embargo, el canal lateral 3 todavía se usa para respuestas de error.

INCLUDE-TAG

La include-tag capacidad se trata de enviar etiquetas anotadas si estamos enviando los objetos a los que apuntan. Si empaquetamos un objeto para el cliente, y un objeto de etiqueta apunta exactamente a ese objeto, empaquetamos también el objeto de etiqueta. En general, esto permite a un cliente obtener todas las nuevas etiquetas anotadas cuando obtiene una rama, en una sola conexión de red.

Los clientes PUEDEN siempre enviar include-tag, codificándolo en duro en una solicitud cuando el servidor publica esta capacidad. La decisión de un cliente para solicitar include-tag solo tiene que ver con los deseos del cliente para los datos de las etiquetas, independientemente de si un servidor ha publicado objetos en el espacio de nombres refs/tags/*.

Los servidores DEBEN empaquetar las etiquetas si su referente está empaquetado y el cliente ha solicitado include-tags.

Los clientes DEBEN estar preparados para el caso en que un servidor ha ignorado include-tag y no ha enviado realmente etiquetas en el paquete. En tales casos, el cliente DEBERÍA emitir una obtención posterior para adquirir las etiquetas que include-tag habría dado al cliente de otro modo.

El servidor DEBERÍA enviar include-tag, si lo soporta, independientemente de si hay etiquetas disponibles o no.

REPORT-STATUS

El proceso receive-pack puede recibir una report-status capacidad, que le dice que el cliente quiere un informe de lo que sucedió después de la subida de un archivo de paquete y la actualización de referencias. Si el cliente que hace push solicita esta capacidad, después de desempaquetar y actualizar las referencias, el servidor responderá con si el archivo de paquete se desempaquetó correctamente y si cada referencia se actualizó correctamente. Si alguna de esas no fue exitosa, enviará un mensaje de error. Véase gitprotocol-pack(5) para ejemplos de mensajes.

REPORT-STATUS-V2

La capacidad report-status-v2 extiende la capacidad report-status añadiendo nuevas directivas "option" para soportar referencias reescritas por el hook "proc-receive". El hook "proc-receive" puede manejar un comando para una pseudo-referencia que puede crear o actualizar una referencia con un nombre, new-oid y old-oid diferentes. Mientras que la capacidad report-status no puede informar para tal caso. Véase gitprotocol-pack(5) para detalles.

DELETE-REFS

Si el servidor devuelve la delete-refs capacidad, significa que es capaz de aceptar un valor de id cero como el valor objetivo de una actualización de referencia. No es devuelta por el cliente, simplemente informa al cliente que se le pueden enviar valores de id cero para borrar referencias.

QUIET

Si el servidor receive-pack publica la quiet capacidad, es capaz de silenciar la salida de progreso legible para humanos que de otro modo podría mostrarse al procesar el paquete recibido. Un cliente send-pack debería responder con la quiet capacidad para suprimir el informe de progreso del lado del servidor si el informe de progreso local también está siendo suprimido (por ejemplo, mediante push -q, o si stderr no va a un tty).

ATOMIC

Si el servidor envía la atomic capacidad, es capaz de aceptar pushes atómicos. Si el cliente que hace push solicita esta capacidad, el servidor actualizará las referencias en una transacción atómica. O todas las referencias se actualizan o ninguna.

PUSH-OPTIONS

Si el servidor envía la push-options capacidad, es capaz de aceptar opciones de push después de que se hayan enviado los comandos de actualización, pero antes de que se transmita el archivo de paquete. Si el cliente que hace push solicita esta capacidad, el servidor pasará las opciones a los hooks pre-receive y post-receive que procesan esta solicitud de push.

ALLOW-TIP-SHA1-IN-WANT

Si el servidor upload-pack publica esta capacidad, fetch-pack puede enviar líneas "want" con nombres de objetos que existen en el servidor pero no son publicados por upload-pack. Por razones históricas, el nombre de esta capacidad contiene "sha1". Los nombres de objetos siempre se dan usando el formato de objeto negociado a través de la capacidad object-format .

ALLOW-REACHABLE-SHA1-IN-WANT

Si el servidor upload-pack publica esta capacidad, fetch-pack puede enviar líneas "want" con nombres de objetos que existen en el servidor pero no son publicados por upload-pack. Por razones históricas, el nombre de esta capacidad contiene "sha1". Los nombres de objetos siempre se dan usando el formato de objeto negociado a través de la capacidad object-format .

PUSH-CERT=<NONCE>

El servidor receive-pack que publica esta capacidad está dispuesto a aceptar un certificado de push firmado, y pide que el <nonce> sea incluido en el certificado de push. Un cliente send-pack NO DEBE enviar un paquete push-cert a menos que el servidor receive-pack publique esta capacidad.

FILTER

Si el servidor upload-pack publica la filter capacidad, fetch-pack puede enviar comandos "filter" para solicitar un clon parcial o una obtención parcial y solicitar que el servidor omita varios objetos del archivo de paquete.

SESSION-ID=<SESSION-ID>

El servidor puede publicar un ID de sesión que puede usarse para identificar este proceso a través de múltiples solicitudes. El cliente también puede publicar su propio ID de sesión de vuelta al servidor.

Los ID de sesión deberían ser únicos para un proceso dado. Deben caber dentro de una línea de paquete, y no deben contener caracteres no imprimibles o de espacio en blanco. La implementación actual usa ID de sesión trace2 (véase api-trace2[1] para detalles), pero esto puede cambiar y los usuarios del ID de sesión no deberían depender de este hecho.
