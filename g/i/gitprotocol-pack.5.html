GITPROTOCOL-PACK(5) Manual de Git GITPROTOCOL-PACK(5)

NOMBRE

gitprotocol-pack - Cómo se transfieren los paquetes a través de la red

SINOPSIS

<protocolo-a-traves-de-la-red>

DESCRIPCIÓN

Git soporta la transferencia de datos en archivos de paquete a través de los transportes ssh://, git://, http:// y file://. Existen dos conjuntos de protocolos, uno para enviar datos desde un cliente a un servidor y otro para obtener datos desde un servidor a un cliente. Los tres transportes (ssh, git, file) utilizan el mismo protocolo para transferir datos. http está documentado en gitprotocol-http(5).

Los procesos invocados en la implementación canónica de Git son upload-pack en el lado del servidor y fetch-pack en el lado del cliente para obtener datos; luego receive-pack en el servidor y send-pack en el cliente para enviar datos. El protocolo funciona para que un servidor le diga a un cliente qué hay actualmente en el servidor, y luego que los dos negocien la menor cantidad de datos a enviar para actualizar completamente a uno u otro.

FORMATO PKT-LINE

Las descripciones a continuación se basan en el formato pkt-line descrito en gitprotocol-common(5). Cuando la gramática indica PKT-LINE(...), a menos que se indique lo contrario, se aplican las reglas habituales de pkt-line LF: el remitente DEBERÍA incluir un LF, pero el receptor NO DEBE quejarse si no está presente.

Un paquete de error es un pkt-line especial que contiene una cadena de error.

  línea-error    =  PKT-LINE("ERR" SP texto-explicación)

A lo largo del protocolo, donde se espera PKT-LINE(...), se PUEDE enviar un paquete de error. Una vez que este paquete es enviado por un cliente o un servidor, el proceso de transferencia de datos definido en este protocolo se termina.

TRANSPORTES

Hay tres transportes a través de los cuales se inicia el protocolo de archivo de paquetes. El transporte Git es un servidor simple y no autenticado que toma el comando (casi siempre upload-pack, aunque los servidores Git pueden configurarse para ser globalmente escribibles, en cuyo caso también se permite la iniciación de receive-pack) con el que el cliente desea comunicarse y lo ejecuta, conectándolo al proceso solicitante.

En el transporte SSH, el cliente simplemente ejecuta el proceso upload-pack o receive-pack en el servidor a través del protocolo SSH y luego se comunica con ese proceso invocado a través de la conexión SSH.

El transporte file:// ejecuta el proceso upload-pack o receive-pack localmente y se comunica con él a través de una tubería.

PARÁMETROS ADICIONALES

El protocolo proporciona un mecanismo mediante el cual los clientes pueden enviar información adicional en su primer mensaje al servidor. Estos se denominan "Parámetros Adicionales", y son compatibles con los protocolos Git, SSH y HTTP.

Cada Parámetro Adicional tiene el formato de <clave>=<valor> o <clave>.

Los servidores que reciben dichos Parámetros Adicionales DEBEN ignorar todas las claves no reconocidas. Actualmente, el único Parámetro Adicional reconocido es "version" con un valor de 1 o 2. Consulte gitprotocol-v2(5) para obtener más información sobre el protocolo versión 2.

TRANSPORTE GIT

El transporte Git comienza enviando el comando y el repositorio en la red utilizando el formato pkt-line, seguido de un byte NUL y un parámetro de nombre de host, terminado con un byte NUL.

0033git-upload-pack /project.git\0host=myserver.com\0

El transporte puede enviar Parámetros Adicionales agregando un byte NUL adicional y luego agregando una o más cadenas terminadas en NUL:

003egit-upload-pack /project.git\0host=myserver.com\0\0version=1\0
git-proto-request = request-command SP pathname NUL
                    [ host-parameter NUL ] [ NUL extra-parameters ]
request-command   = "git-upload-pack" / "git-receive-pack" /
                    "git-upload-archive"   ; sensible a mayúsculas y minúsculas
pathname          = *( %x01-ff ) ; excluye NUL
host-parameter    = "host=" hostname [ ":" port ]
extra-parameters  = 1*extra-parameter
extra-parameter   = 1*( %x01-ff ) NUL

host-parameter se utiliza para la virtualización de nombres basada en git-daemon. Consulte la opción --interpolated-path de git daemon, con los caracteres de formato %H/%CH.

Básicamente, lo que el cliente Git está haciendo para conectarse a un proceso upload-pack en el lado del servidor a través del protocolo Git es esto:

$ echo -e -n \
  "003agit-upload-pack /schacon/gitbook.git\0host=example.com\0" |
  nc -v example.com 9418

TRANSPORTE SSH

Iniciar los procesos upload-pack o receive-pack a través de SSH es ejecutar el binario en el servidor mediante la ejecución remota de SSH. Es básicamente equivalente a ejecutar esto:

$ ssh git.example.com "git-upload-pack '/project.git'"

Para que un servidor admita el envío y la recepción de Git para un usuario determinado a través de SSH, ese usuario debe poder ejecutar uno o ambos de esos comandos a través del shell SSH que se le proporciona al iniciar sesión. En algunos sistemas, el acceso a ese shell se limita a solo poder ejecutar esos dos comandos, o incluso solo uno de ellos.

En una URI en formato ssh://, es absoluto en la URI, por lo que la / después del nombre del host (o número de puerto) se envía como argumento, que luego es leído por el git-upload-pack remoto exactamente como está, por lo que efectivamente es una ruta absoluta en el sistema de archivos remoto.

   git clone ssh://user@example.com/project.git
                |
                v
ssh user@example.com "git-upload-pack '/project.git'"

En una URI en formato "user@host:path", es relativo al directorio de inicio del usuario, ya que el cliente Git ejecutará:

   git clone user@example.com:project.git
                  |
                  v
ssh user@example.com "git-upload-pack 'project.git'"

La excepción es si se usa un ~, en cuyo caso lo ejecutamos sin la / inicial.

   ssh://user@example.com/~alice/project.git,
                  |
                  v
ssh user@example.com "git-upload-pack '~alice/project.git'"

Dependiendo del valor de la variable de configuración protocol.version, Git puede intentar enviar Parámetros Adicionales como una cadena separada por dos puntos en la variable de entorno GIT_PROTOCOL. Esto solo se hace si la variable de configuración ssh.variant indica que el comando ssh admite el paso de variables de entorno como argumento.

Algunas cosas a tener en cuenta aquí:

•El "nombre del comando" está escrito con guion (por ejemplo, git-upload-pack), pero esto puede ser anulado por el cliente;
•La ruta del repositorio siempre está entre comillas simples.

OBTENIENDO DATOS DE UN SERVIDOR

Cuando un repositorio Git quiere obtener datos que tiene un segundo repositorio, el primero puede obtener del segundo. Esta operación determina qué datos tiene el servidor que el cliente no tiene, y luego transmite esos datos al cliente en formato de archivo de paquete.

NEGOCIACIÓN DE ARCHIVO DE

PAQUETES

Después del descubrimiento de referencias y capacidades, el cliente puede decidir terminar la conexión enviando un flush-pkt, indicando al servidor que ahora puede terminar correctamente y desconectarse, cuando no necesita ningún dato de paquete. Esto puede ocurrir con el comando ls-remote, y también puede ocurrir cuando el cliente ya está

actualizado.

De lo contrario, entra en la fase de negociación, donde el cliente y el servidor determinan el archivo de paquete mínimo necesario para la transferencia, diciendo al servidor qué objetos quiere, sus objetos superficiales (si los hay), y la profundidad máxima de commits que quiere (si la hay). El cliente también enviará una lista de las capacidades que quiere que estén activas, de entre las que el servidor dijo que podía hacer con la primera línea w

ant. 
  upload-request    =  want-list
                       *shallow-line
                       *1depth-request
                       [filter-request]
                       flush-pkt
  want-list         =  first-want
*additional-want shallow-line = PKT-LINE("shallow" SP obj-id) depth-request = PKT-LINE("deepen" SP depth) / PKT-LINE("deepen-since" SP timestamp) / PKT-LINE(
"deepen-not" SP ref) first-want = PKT-LINE("want" SP obj-id SP capability-list) additional-want = PKT-LINE("want" SP obj-id) depth = 1*DIGIT filter-request = PKT-LINE("filter" SP filter-spec)

Los clientes DEBEN enviar todos los obj-ids que quieren de la fase de descubrimiento de referencias como líneas want. Los clientes DEBEN enviar al menos un comando want en el cuerpo de la solicitud. Los clientes NO DEBEN mencionar un obj-id en un comando want que no apareció en la respuesta obtenida a través del descubrimiento de

refs.

El cliente DEBE escribir todos los obj-ids de los que solo tiene copias superficiales (lo que significa que no tiene los padres de un commit) como líneas shallow para que el servidor sea consciente de las limitaciones del historial del

cliente.

El cliente ahora envía la profundidad máxima del historial de commits que quiere para esta transacción, que es el número de commits que quiere desde la punta del historial, si los hay, como una línea deepen. Una profundidad de 0 es lo mismo que no hacer una solicitud de profundidad. El cliente no quiere recibir ningún commit más allá de esta profundidad, ni quiere objetos necesarios solo para completar esos commits. Los commits cuyos padres no se reciben como resultado se definen como superficiales y se marcan como tales en el servidor. Esta información se envía de vuelta al cliente en el siguiente

paso.

El cliente puede solicitar opcionalmente que pack-objects omita varios objetos del archivo de paquete usando una de varias técnicas de filtrado. Estas están destinadas a su uso con operaciones de clonado parcial y obtención parcial. Un objeto que no cumple un valor de filter-spec se omite a menos que se solicite explícitamente en una línea want. Consulte rev-list para posibles valores de

filter-spec.

Una vez que todos los want's y 'shallow's (y opcionalmente 'deepen) se han transferido, los clientes DEBEN enviar un flush-pkt, para decirle al lado del servidor que ha terminado de enviar la

lista.

De lo contrario, si el cliente envió una solicitud de profundidad positiva, el servidor determinará qué commits serán superficiales y cuáles no y enviará esta información al cliente. Si el cliente no solicitó una profundidad positiva, este paso se

omite. 
  shallow-update   =  *shallow-line
                      *unshallow-lin

Si el cliente ha solicitado una profundidad positiva, el servidor calculará el conjunto de commits que no son más profundos que la profundidad deseada. El conjunto de commits comienza en los wants del

cliente.

El servidor escribe líneas shallow para cada commit cuyos padres no se enviarán como resultado. El servidor escribe una línea unshallow para cada commit que el cliente ha indicado que es superficial, pero que ya no es superficial a la profundidad actualmente solicitada (es decir, sus padres ahora se enviarán). El servidor NO DEBE marcar como no superficial nada que el cliente no haya indicado que era

superficial.

Ahora el cliente enviará una lista de los obj-ids que tiene usando líneas have, para que el servidor pueda hacer un archivo de paquete que solo contenga los objetos que el cliente necesita. En modo multi_ack, la implementación canónica enviará hasta 32 de estas a la vez, y luego enviará un flush-pkt. La implementación canónica saltará y enviará las siguientes 32 inmediatamente, para que siempre haya un bloque de 32 "en vuelo en el cable" a la

vez.

cliente.

•el servidor responderá con ACK obj-id continue para cualquier commit

•una vez que el servidor haya encontrado un commit base común aceptable y esté listo para hacer un archivo de paquete, hará ACK ciegamente a todos los obj-ids have de vuelta al

•el servidor luego enviará un NAK y luego esperará otra respuesta del cliente - ya sea un done u otra lista de líneas h

En modo multi_ack_detailed

•el servidor diferenciará los ACK donde está señalando que está listo para enviar datos con líneas ACK obj-id ready, y señalará los commits comunes identificados con líneas ACK obj-id common

Sin multi_ack ni multi_ack_detailed

•upload-pack envía "ACK obj-id" en el primer objeto común que encuentra. Después de eso no dice nada hasta que el cliente le da un
"done".
•upload-pack envía "NAK" en un flush-pkt si aún no se ha encontrado ningún objeto común. Si se ha encontrado uno, y por lo tanto ya se envió un ACK, permanece en silencio en el

Después de que el cliente haya recibido suficientes respuestas ACK para que pueda determinar que el servidor tiene suficiente información para enviar un archivo de paquete eficiente (en la implementación canónica, esto se determina cuando ha recibido suficientes ACKs para poder colorear todo lo que queda en la cola --date-order como común con el servidor, o la cola --date-order está vacía), o el cliente determina que quiere rendirse (en la implementación canónica, esto se determina cuando el cliente envía 256 líneas have sin que el servidor haga ACK a ninguna de ellas - lo que significa que no hay nada en común y el servidor debería simplemente enviar todos sus objetos), entonces el cliente enviará un comando done. El comando done le señala al servidor que el cliente está listo para recibir los datos de su archivo de

paquete.

Sin embargo, el límite de 256 solo se activa en la implementación canónica del cliente si hemos recibido al menos un "ACK %s continue" durante una ronda anterior. Esto ayuda a asegurar que al menos un ancestro común se encuentre antes de rendirnos por

completo.

Una vez que se lee la línea done del cliente, el servidor enviará ya sea un ACK obj-id final o enviará un NAK. obj-id es el nombre del último commit determinado como común. El servidor solo envía ACK después de done si hay al menos una base común y multi_ack o multi_ack_detailed está habilitado. El servidor siempre envía NAK después de done si no se ha encontrado ninguna base

común.

En lugar de ACK o NAK, el servidor puede enviar un mensaje de error (por ejemplo, si no reconoce un objeto en una línea want recibida del cliente)

.

PACKFILE

DATOS

Ahora que el cliente y el servidor han terminado la negociación sobre cuál es la cantidad mínima de datos que necesita enviarse al cliente, el servidor construirá y enviará los datos requeridos en formato de

packfile.

Ver gitformat-pack(5) para ver cómo es realmente el packfile en

sí.

Si side-band o side-band-64k han sido especificadas por el cliente, el servidor enviará los datos del packfile

multiplexados.

Cada paquete comienza con la longitud de la línea de paquete de la cantidad de datos que sigue, seguido de un solo byte que especifica el canal lateral por el que llegan los datos

siguientes.

En modo side-band, enviará hasta 999 bytes de datos más 1 código de control, para un total de hasta 1000 bytes en un pkt-line. En modo side-band-64k enviará hasta 65519 bytes de datos más 1 código de control, para un total de hasta 65520 bytes en un

pkt-line.

El byte del canal lateral será un 1, 2 o un 3. El canal lateral 1 contendrá datos del packfile, el canal lateral 2 se usará para información de progreso que el cliente generalmente imprimirá en stderr y el canal lateral 3 se usa para información de

error.

Si no se especificó la capacidad side-band, el servidor transmitirá

el packfile comple
to sin multiplexar.

EMPUJAR DATOS A UN

SERVIDOR

Empujar datos a un servidor invocará el proceso receive-pack en el servidor, lo que permitirá al cliente decirle qué referencias debe actualizar y luego enviar todos los datos que el servidor necesitará para qu

e esas nuevas referencias estén completas. Una vez que todos los datos son recibidos y
validados, el servidor actualizará sus referencias a lo que el cliente especificó.

AUTENTICACIÓ

N

El protocolo en sí no contiene mecanismos de autenticación. Eso debe ser manejado por el transporte, como SSH, antes de que el proceso receive-pack sea invocado. Si receive-pack está configurado sobre el transporte Git, esos repositorios serán escribibles por

cualquiera que pueda acceder a ese puerto (
9418), ya que ese transporte no está autenticado.

DESCUBRIMIENTO DE

REFERENCIAS

La fase de descubrimiento de referencias se hace casi de la misma manera que en el protocolo de obtención. Cada obj-id y nombre de referencia en el servidor se envía en formato de línea de paquete al cliente, seguido de un flush-pkt. La única diferencia real es que el listado de capacidades es diferente - los únicos valores posibles son report-status, report-status-v2, delete-refs, ofs-delta, atomic y push-option

s
.

El servidor recibirá el packfile, lo desempaquetará, luego validará cada referencia que está siendo actualizada que no haya cambiad

o mientras la solicitud estaba siendo procesada (el obj-id sigue siendo el mismo que el old-id), y ejecutará cualquier hook de
actualización para asegurarse de que la actualización es aceptable. Si todo eso está bien, el servidor actualizará las referencias.

CERTIFICADO DE

EMPUJE

Un certificado de empuje comienza con un conjunto de líneas de encabezado. Después del encabezado y una línea vacía, siguen los comandos del protocolo, uno por línea. Nótese que el LF final en los PKT-LINE de push-cert no es opcional; debe estar

presente.

Actualmente, están definidos los siguientes campos de

encabezado:

pusher i

dent
Identifica la clave GPG en formato "Nombre Legible <email@address[1]>
".

pushee

url
La URL del repositorio (anonimizada, si la URL contiene material de autenticación) a la que el usuario que ejecutó git push pretendía
empujar.

nonce n

once
La cadena nonce que el repositorio receptor pidió al usuario que empujaba incluir en el certificado, para prevenir ataques de
repetición.

Las líneas de firma GPG son una firma separada para el contenido registrado en el certi

ficado de empuje antes de que comience el bloque de firma. La firma separada se usa para
certificar que los comandos fueron dados por el empujador, quien debe ser el firmante.

REPORTE DE

ESTADO

Después de recibir los datos del pack del emisor, el receptor envía un reporte si la capacidad report-status o report-status-v2 está en efecto. Es un listado corto de lo que sucedió en esa actualización. Primero listará el estado del desempaquetado del packfile como unpack ok o unpack [error]. Luego listará el estado para cada una de las referencias que intentó actualizar. Cada línea es o bien ok [refname] si la actualización fue exitosa, o ng [refname] [error] si la actualización no lo

fue. 
  report-status     = unpack-status
                      1*(command-status)
                      flush-pkt
  unpack-status     = PKT-LINE
("unpack" SP unpack-result) unpack-result = "ok" / error-msg command-status = command-ok / command-fail command-ok =
PKT-LINE("ok" SP refname) command-fail = PKT-LINE("ng" SP refname SP error-msg) error-msg = 1*(OCTET) ; donde no es "ok"

La capacidad report-status-v2 extiende el protocolo agregando nuevas líneas de opción para soportar el reporte de referencias reescritas por el hook proc-receive. El hook proc-receive puede manejar un comando para una pseudoreferencia que puede crear o actualizar una o más referencias, y cada referencia puede tener un nombre diferente, un new-oid diferente, y un old-oid

diferente. 
  report-status-v2  = unpack-status
                      1*(command-status-v2)
                      flush-pkt
  unpack-status     = PKT-LINE("unpack" SP unpack-result)
  unpack-result     = "ok" / error-msg
  command-status-v2 = command-ok-v2 / command-fail
  command-ok-v2     = command-ok
                      *option-line
  command-ok        = PKT-LINE("ok" SP refname)
  command-fail      = PKT-LINE("ng" SP refname SP error-msg)
  error-msg         = 1*(OCTET) ; donde no es "ok"
  option-line       = *1(option-refname)
                      *1(option-old-oid)
                      *1(option-new-oid)
                      *1(option-forced-update)
  option-refname    = PKT-LINE("option" SP "refname" SP refname)
  option-old-oid    = PKT-LINE("option" SP "old-oid" SP obj-id)
  option-new-oid    = PKT-LINE("option" SP "new-oid" SP obj-id)
  option-force      = PKT-LINE("option" SP
"forced-update"
)

Las actualizaciones pueden ser fallidas por varias razones. La referencia puede haber cambiado desde que la fase de descubrimiento de referencias fue enviada originalmente, lo que significa que alguien empujó en el intermedio. La referencia que se está empujando podría ser una referencia de avance no rápido y los hooks de actualización o la configuración podrían estar configurados para no permitir eso, etc. Además, algunas referencias pueden ser actualizadas mientras otras pueden ser

rechazadas.
