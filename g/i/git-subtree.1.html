GIT-SUBTREE(1) Manual de Git GIT-SUBTREE(1)

NOMBRE

git-subtree - Fusiona subárboles juntos y divide el repositorio en subárboles

SINOPSIS

git subtree [<opciones>] -P <prefijo> [-S[<keyid>]] add <commit-local>
git subtree [<opciones>] -P <prefijo> [-S[<keyid>]] add <repositorio> <referencia-remota>
git subtree [<opciones>] -P <prefijo> [-S[<keyid>]] merge <commit-local> [<repositorio>]
git subtree [<opciones>] -P <prefijo> [-S[<keyid>]] split [<commit-local>]
git subtree [<opciones>] -P <prefijo> [-S[<keyid>]] pull <repositorio> <referencia-remota>
git subtree [<opciones>] -P <prefijo> [-S[<keyid>]] push <repositorio> <refspec>

DESCRIPCIÓN

Los subárboles permiten incluir subproyectos dentro de un subdirectorio del proyecto principal, incluyendo opcionalmente todo el historial del subproyecto.

Por ejemplo, podrías incluir el código fuente de una biblioteca como un subdirectorio de tu aplicación.

Los subárboles no deben confundirse con los submódulos, que se utilizan para la misma tarea. A diferencia de los submódulos, los subárboles no necesitan ninguna construcción especial (como archivos .gitmodules o gitlinks) en tu repositorio, y no obligan a los usuarios finales de tu repositorio a hacer nada especial ni a entender cómo funcionan los subárboles. Un subárbol es solo un subdirectorio en el que puedes hacer commits, ramas y fusiones como quieras.

Tampoco deben confundirse con el uso de la estrategia de fusión subtree. La principal diferencia es que, además de fusionar el otro proyecto como un subdirectorio, también puedes extraer todo el historial de un subdirectorio de tu proyecto y convertirlo en un proyecto independiente. A diferencia de la estrategia de fusión subtree, puedes alternar entre estas dos operaciones. Si la biblioteca independiente se actualiza, puedes fusionar automáticamente los cambios en tu proyecto; si actualizas la biblioteca dentro de tu proyecto, puedes "dividir" los cambios de nuevo y fusionarlos de vuelta al proyecto de la biblioteca.

Por ejemplo, si una biblioteca que creaste para una aplicación resulta ser útil en otro lugar, puedes extraer todo su historial y publicarlo como su propio repositorio git, sin mezclar accidentalmente el historial de tu proyecto de aplicación.


Consejo

Para mantener limpios tus mensajes de commit, recomendamos que las personas dividan sus commits entre los subárboles y el proyecto principal lo más posible. Es decir, si haces un cambio que afecta tanto a la biblioteca como a la aplicación principal, hazlo en dos partes. De esta manera, cuando dividas los commits de la biblioteca más tarde, sus descripciones seguirán teniendo sentido. Pero si esto no es importante para ti, no es necesario. git subtree simplemente omitirá las partes no relacionadas con la biblioteca del commit cuando lo divida en el subproyecto más tarde.

COMANDOS

add <commit-local>, add <repositorio> <referencia-remota>

Crea el subárbol <prefijo> importando su contenido desde el <commit-local> dado o desde el <repositorio> y <referencia-remota>. Se crea automáticamente un nuevo commit, uniendo el historial del proyecto importado con el tuyo. Con --squash, importa solo un commit del subproyecto, en lugar de todo su historial.

merge <commit-local> [<repositorio>]

Fusiona los cambios recientes hasta <commit-local> en el subárbol <prefijo>. Al igual que con git merge normal, esto no elimina tus propios cambios locales; solo fusiona esos cambios en el último <commit-local>. Con --squash, crea solo un commit que contiene todos los cambios, en lugar de fusionar todo el historial.

Si usas --squash, la dirección de la fusión no siempre tiene que ser hacia adelante; puedes usar este comando para retroceder en el tiempo de v2.5 a v2.4, por ejemplo. Si tu fusión introduce un conflicto, puedes resolverlo de las maneras habituales.

Cuando usas --squash, y la fusión anterior con --squash fusionó una etiqueta anotada del repositorio del subárbol, esa etiqueta debe estar disponible localmente. Si se proporciona <repositorio>, una etiqueta faltante se obtendrá automáticamente de ese repositorio.

split [<commit-local>] [<repositorio>]

Extrae un nuevo historial de proyecto sintético del historial del subárbol <prefijo> de <commit-local>, o de HEAD si no se proporciona <commit-local>. El nuevo historial incluye solo los commits (incluidas las fusiones) que afectaron a <prefijo>, y cada uno de esos commits ahora tiene el contenido de <prefijo> en la raíz del proyecto en lugar de en un subdirectorio. Por lo tanto, el historial recién creado es adecuado para exportarlo como un repositorio git separado.

Después de dividir con éxito, se imprime un único ID de commit en stdout. Esto corresponde al HEAD del árbol recién creado, que puedes manipular como quieras.

Las divisiones repetidas del mismo historial garantizan ser idénticas (es decir, producir los mismos IDs de commit) siempre que la configuración pasada a split (como --annotate) sea la misma. Debido a esto, si agregas nuevos commits y luego vuelves a dividir, los nuevos commits se adjuntarán como commits encima del historial que generaste la última vez, por lo que git merge y comandos similares funcionarán como se espera.

Cuando una fusión anterior con --squash fusionó una etiqueta anotada del repositorio del subárbol, esa etiqueta debe estar disponible localmente. Si se proporciona <repositorio>, una etiqueta faltante se obtendrá automáticamente de ese repositorio.

pull <repositorio> <referencia-remota>

Exactamente igual que merge, pero es análogo a git pull en que recupera la referencia dada del repositorio remoto especificado.

push <repositorio> [+][<commit-local>:]<referencia-remota>

Realiza un split usando el subárbol <prefijo> de <commit-local> y luego realiza un git push para enviar el resultado al <repositorio> y <referencia-remota>. Esto se puede usar para enviar tu subárbol a diferentes ramas del repositorio remoto. Al igual que con split, si no se proporciona <commit-local>, se utiliza HEAD. El signo + inicial opcional se ignora.

OPCIONES PARA TODOS LOS COMANDOS

-q, --quiet

Suprime mensajes de salida innecesarios en stderr.

-d, --debug

Produce mensajes de salida aún más innecesarios en stderr.

-P <prefijo>, --prefix=<prefijo>

Especifica la ruta en el repositorio del subárbol que deseas manipular. Esta opción es obligatoria para todos los comandos.

-S[<keyid>], --gpg-sign[=<keyid>], --no-gpg-sign

Firma commits con GPG. El argumento keyid es opcional y por defecto es la identidad del que confirma; --no-gpg-sign es útil para contrarrestar una opción --gpg-sign dada anteriormente en la línea de comandos.

OPCIONES PARA ADD Y MERGE (TAMBIÉN: PULL, SPLIT --REJOIN, Y PUSH --REJOIN)

Estas opciones para add y merge también pueden ser dadas a pull (que envuelve merge), split --rejoin (que envuelve add o merge según corresponda), y push --rejoin (que envuelve split --rejoin).

--squash

En lugar de fusionar todo el historial del proyecto del subárbol, produce solo un commit que contiene todas las diferencias que deseas fusionar, y luego fusiona ese nuevo commit en tu proyecto.

Usar esta opción ayuda a reducir el desorden del log. Las personas rara vez quieren ver cada cambio que ocurrió entre la v1.0 y la v1.1 de la biblioteca que están usando, ya que ninguna de las versiones intermedias se incluyó nunca en su aplicación.

Usar --squash también ayuda a evitar problemas cuando el mismo subproyecto se incluye varias veces en el mismo proyecto, o se elimina y se vuelve a añadir. En ese caso, de todos modos no tiene sentido combinar los historiales, ya que no está claro qué parte del historial pertenece a qué subárbol.

Además, con --squash, puedes alternar entre diferentes versiones de un subárbol, en lugar de estrictamente hacia adelante. git subtree merge --squash siempre ajusta el subárbol para que coincida con el commit exactamente especificado, incluso si llegar a ese commit requeriría deshacer algunos cambios que se agregaron anteriormente.

Ya sea que uses --squash

git-subtree(1) — Arch Linux Manual Pages

NAME

git-subtree - Maintain sub-repositories as sub-projects

SYNOPSIS

git subtree add [<options>] <repository> [<ref>]

git subtree merge [<options>] <commit>

git subtree split [<options>] [<commit>]

git subtree push [<options>] <repository> [<ref>]

git subtree pull [<options>] <repository> [<ref>]

DESCRIPTION

git subtree allows you to manage sub-projects as sub-repositories within your main project.

COMMANDS

The following commands are available:

add
Adds a subtree repository. This is equivalent to a subtree pull, except that it also adds the remote repository to your configuration.
merge
Merges changes from the subtree into your main project. This is useful for pulling updates from the sub-project into your main project.
split
Splits out a subtree into its own repository. This is useful for pushing changes from your main project back to the sub-project.
push
Pushes changes from your main project to the subtree repository. This is a wrapper around split that also pushes the resulting commits to the specified remote repository.
pull
Pulls changes from the subtree repository into your main project. This is a wrapper around merge that also fetches from the specified remote repository.

OPTIONS FOR ALL COMMANDS

-P <prefix>, --prefix=<prefix>

Specify the root directory of the subtree. This option is required for all commands except split.

--squash

When adding or merging a subtree, squash all the commits from the sub-project into a single commit in your main project. This helps to keep the main project's history clean.

--annotate=<annotation>

When splitting a subtree, add <annotation> as a prefix to each commit message. This can help to differentiate the commits from the sub-project from the commits in your main project.

-m <message>, --message=<message>

Specify <message> as the commit message for the merge commit.

OPTIONS FOR SPLIT (ALSO: PUSH)

These options for split may also be given to push (which wraps split).

--annotate=<annotation>

When generating synthetic history, add <annotation> as a prefix to each commit message. Since we’re creating new commits with the same commit message, but possibly different content, from the original commits, this can help to differentiate them and avoid confusion.

Whenever you split, you need to use the same <annotation>, or else you don’t have a guarantee that the new re-created history will be identical to the old one. That will prevent merging from working correctly. git subtree tries to make it work anyway, particularly if you use --rejoin, but it may not always be effective.

-b <branch>, --branch=<branch>

After generating the synthetic history, create a new branch called <branch> that contains the new history. This is suitable for immediate pushing upstream. <branch> must not already exist.

--ignore-joins

If you use --rejoin, git subtree attempts to optimize its history reconstruction to generate only the new commits since the last --rejoin. --ignore-joins disables this behavior, forcing it to regenerate the entire history. In a large project, this can take a long time.

--onto=<onto>

If your subtree was originally imported using something other than git subtree, its history may not match what git subtree is expecting. In that case, you can specify the commit ID <onto> that corresponds to the first revision of the subproject’s history that was imported into your project, and git subtree will attempt to build its history from there.

If you used git subtree add, you should never need this option.

--rejoin

After splitting, merge the newly created synthetic history back into your main project. That way, future splits can search only the part of history that has been added since the most recent --rejoin.

If your split commits end up merged into the upstream subproject, and then you want to get the latest upstream version, this will allow git’s merge algorithm to more intelligently avoid conflicts (since it knows these synthetic commits are already part of the upstream repository).

Unfortunately, using this option results in git log showing an extra copy of every new commit that was created (the original, and the synthetic one).

If you do all your merges with --squash, make sure you also use --squash when you split --rejoin.

EXAMPLE 1. ADD COMMAND

Let’s assume that you have a local repository that you would like to add an external vendor library to. In this case we will add the git-subtree repository as a subdirectory of your already existing git-extensions repository in ~/git-extensions/:

$ git subtree add --prefix=git-subtree --squash \
        git://github.com/apenwarr/git-subtree.git master

master needs to be a valid remote ref and can be a different branch name

You can omit the --squash flag, but doing so will increase the number of commits that are included in your local repository.

We now have a ~/git-extensions/git-subtree directory containing code from the master branch of git://github.com/apenwarr/git-subtree.git in our git-extensions repository.

EXAMPLE 2. EXTRACT A SUBTREE USING COMMIT, MERGE AND PULL

Let’s use the repository for the git source code as an example. First, get your own copy of the git.git repository:

$ git clone git://git.kernel.org/pub/scm/git/git.git test-git
$ cd test-git

gitweb (commit 1130ef3) was merged into git as of commit 0a8f4f0, after which it was no longer maintained separately. But imagine it had been maintained separately, and we wanted to extract git’s changes to gitweb since that time, to share with the upstream. You could do this:

$ git subtree split --prefix=gitweb --annotate='(split) ' \
        0a8f4f0^.. --onto=1130ef3 --rejoin \
        --branch gitweb-latest
$ gitk gitweb-latest
$ git push git@github.com:whatever/gitweb.git gitweb-latest:master

(We use 0a8f4f0^.. because that means "all the changes from 0a8f4f0 to the current version, including 0a8f4f0 itself.")

If gitweb had originally been merged using git subtree add (or a previous split had already been done with --rejoin specified) then you can do all your splits without having to remember any weird commit IDs:

$ git subtree split --prefix=gitweb --annotate='(split) ' --rejoin \
        --branch gitweb-latest2

And you can merge changes back in from the upstream project just as easily:

$ git subtree pull --prefix=gitweb \
        git@github.com:whatever/gitweb.git master

Or, using --squash, you can actually rewind to an earlier version of gitweb:

$ git subtree merge --prefix=gitweb --squash gitweb-latest~10

Then make some changes:

$ date >gitweb/myfile
$ git add gitweb/myfile
$ git commit -m 'created myfile'

And fast forward again:

$ git subtree merge --prefix=gitweb --squash gitweb-latest

And notice that your change is still intact:

$ ls -l gitweb/myfile

And you can split it out and look at your changes versus the standard gitweb:

git log gitweb-latest..$(git subtree split --prefix=gitweb)

EXAMPLE 3. EXTRACT A SUBTREE USING A BRANCH

Suppose you have a source directory with many files and subdirectories, and you want to extract the lib directory to its own git project. Here’s a short way to do it:

First, make the new repository wherever you want:

$ <go to the new location>
$ git init --bare

Back in your original directory:

$ git subtree split --prefix=lib --annotate="(split)" -b split

Then push the new branch onto the new empty repository:

$ git push <new-repo> split:master
