NOMBRE

git-read-tree - Lee información de árbol en el índice

SINOPSIS

git read-tree [(-m [--trivial] [--aggressive] | --reset | --prefix=<prefijo>)
                [-u | -i]] [--index-output=<archivo>] [--no-sparse-checkout]
                (--empty | <árbol-ish1> [<árbol-ish2> [<árbol-ish3>]])

DESCRIPCIÓN

Lee la información del árbol dada por <árbol-ish> en el índice, pero no actualiza realmente ninguno de los archivos que "almacena en caché". (véase: git-checkout-index(1))

Opcionalmente, puede fusionar un árbol en el índice, realizar una fusión de avance rápido (es decir, de 2 vías), o una fusión de 3 vías, con el -m indicador. Cuando se usa con -m, el -u indicador hace que también actualice los archivos en el árbol de trabajo con el resultado de la fusión.

Solo se realizan fusiones triviales por git read-tree en sí mismo. Solo las rutas en conflicto estarán en un estado sin fusionar cuando git read-tree regrese.

OPCIONES

-m

Realizar una fusión, no solo una lectura. El comando se negará a ejecutarse si su archivo de índice tiene entradas sin fusionar, lo que indica que no ha terminado una fusión anterior que comenzó.

--reset

Igual que -m, excepto que las entradas sin fusionar se descartan en lugar de fallar. Cuando se usa con -u, las actualizaciones que resulten en la pérdida de cambios en el árbol de trabajo o archivos o directorios sin seguimiento no abortarán la operación.

-u

Después de una fusión exitosa, actualizar los archivos en el árbol de trabajo con el resultado de la fusión.

-i

Generalmente una fusión requiere que el archivo de índice y los archivos en el árbol de trabajo estén actualizados con el commit actual de cabecera, para no perder cambios locales. Este indicador desactiva la comprobación con el árbol de trabajo y está destinado a usarse al crear una fusión de árboles que no están directamente relacionados con el estado actual del árbol de trabajo en un archivo de índice temporal.

-n, --dry-run

Comprobar si el comando daría error, sin actualizar el índice o los archivos en el árbol de trabajo realmente.

-v

Mostrar el progreso de la extracción de archivos.

--trivial

Restringir la fusión de tres vías por git read-tree para que ocurra solo si no se requiere fusión a nivel de archivo, en lugar de resolver la fusión para casos triviales y dejar los archivos en conflicto sin resolver en el índice.

--aggressive

Generalmente una fusión de tres vías por git read-tree resuelve la fusión para casos realmente triviales y deja otros casos sin resolver en el índice, para que las porcelanas puedan implementar diferentes políticas de fusión. Este indicador hace que el comando resuelva unos casos más internamente:
•cuando un lado elimina una ruta y el otro lado deja la ruta sin modificar. La resolución es eliminar esa ruta.
•cuando ambos lados eliminan una ruta. La resolución es eliminar esa ruta.
•cuando ambos lados añaden una ruta de forma idéntica. La resolución es añadir esa ruta.

--prefix=<prefijo>

Mantener el contenido actual del índice, y leer el contenido del árbol-ish nombrado bajo el directorio en <prefijo>. El comando se negará a sobrescribir entradas que ya existían en el archivo de índice original.

--index-output=<archivo>

En lugar de escribir los resultados en $GIT_INDEX_FILE, escribir el índice resultante en el archivo nombrado. Mientras el comando está operando, el archivo de índice original se bloquea con el mismo mecanismo que de costumbre. El archivo debe permitir ser renombrado con rename(2) desde un archivo temporal que se crea junto al archivo de índice habitual; típicamente esto significa que debe estar en el mismo sistema de archivos que el archivo de índice mismo, y usted necesita permiso de escritura en los directorios donde se encuentran el archivo de índice y el archivo de salida del índice.

--recurse-submodules, --no-recurse-submodules

Usar --recurse-submodules actualizará el contenido de todos los submódulos activos de acuerdo con el commit registrado en el superproyecto llamando a read-tree recursivamente, también configurando el HEAD de los submódulos para que esté desprendido en ese commit.

--no-sparse-checkout

Desactivar el soporte de checkout disperso incluso si core.sparseCheckout es verdadero.

--empty

En lugar de leer objeto(s) de árbol en el índice, simplemente vaciarlo.

-q, --quiet

Silencioso, suprime los mensajes de retroalimentación.

<árbol-ish#>

El id del(los) objeto(s) de árbol a leer/fusionar.

FUSIÓN

Si -m está especificado, git read-tree puede realizar 3 tipos de fusión, una fusión de árbol único si solo se da 1 árbol, una fusión de avance rápido con 2 árboles, o una fusión de 3 vías si se proporcionan 3 o más árboles.

Fusión de Árbol Único

Si solo se especifica 1 árbol, git read-tree opera como si el usuario no hubiera especificado -m, excepto que si el índice original tiene una entrada para un nombre de ruta dado, y el contenido de la ruta coincide con el árbol que se está leyendo, se usa la información de stat del índice. (En otras palabras, los stat() del índice tienen precedencia sobre los del árbol fusionado).

Eso significa que si hace un git read-tree -m <nuevoárbol> seguido de un git checkout-index -f -u -a, el git checkout-index solo extrae lo que realmente cambió.

Esto se usa para evitar falsos positivos innecesarios cuando git diff-files se ejecuta después de git read-tree.

Fusión de Dos Árboles

Típicamente, esto se invoca como git read-tree -m $H $M, donde $H es el commit de cabecera del repositorio actual, y $M es la cabecera de un árbol externo, que simplemente está por delante de $H (es decir, estamos en una situación de avance rápido).

Cuando se especifican dos árboles, el usuario le está diciendo a git read-tree lo siguiente:

1.El índice actual y el árbol de trabajo se derivan de $H, pero el usuario puede tener cambios locales en ellos desde $H.
2.El usuario quiere avanzar rápidamente a $M.

En este caso, el git read-tree -m $H $M comando se asegura de que ningún cambio local se pierda como resultado de esta "fusión". Aquí están las reglas de "mantener hacia adelante", donde "I" denota el índice, "limpio" significa que el índice y el árbol de trabajo coinciden, y "existe"/"nada" se refieren a la presencia de una ruta en el commit especificado:

        I                   H        M        Resultado
       -------------------------------------------------------
     0  nada               nada     nada     (no ocurre)
     1  nada               nada     existe   usar M
     2  nada               existe   nada     eliminar ruta del índice
     3  nada               existe   existe,  usar M si "checkout inicial",
                                     H == M   mantener índice de lo contrario
                                     existe,  fallar
                                     H != M
        limpio I==H  I==M
       ------------------
     4  sí    N/A   N/A     nada     nada     mantener índice
     5  no    N/A   N/A     nada     nada     mantener índice
     6  sí    N/A   sí      nada     existe   mantener índice
     7  no    N/A   sí      nada     existe   mantener índice
     8  sí    N/A   no      nada     existe   fallar
     9  no    N/A   no      nada     existe   fallar
     10 sí    sí    N/A     existe   nada     eliminar ruta del índice
     11 no    sí    N/A     existe   nada     fallar
     12 sí    no    N/A     existe   nada     fallar
     13 no    no    N/A     existe   nada     fallar
        limpio (H==M)
       ------
     14 sí                  existe   existe   mantener índice
     15 no                  existe   existe   mantener índice
        limpio I==H  I==M (H!=M)
       ------------------
     16 sí    no    no      existe   existe   fallar
     17 no    no    no      existe   existe   fallar
     18 sí    no    sí      existe   existe   mantener índice
     19 no    no    sí      existe   existe   mantener índice
     20 sí    sí    no      existe   existe   usar M
     21 no    sí    no      existe   existe   fallar

En todos los casos de "mantener índice", la entrada del índice permanece como en el archivo de índice original. Si la entrada no está actualizada, git read-tree mantiene la copia en el árbol de trabajo intacta cuando

NOMBRE

git-read-tree - Lee datos de un árbol en el índice

SINOPSIS

git read-tree --prefix=<prefix>/ [<options>] <tree-ish>
git read-tree [--prefix=<prefix>/] [<options>] <old-tree> <new-tree>
git read-tree --prefix=<prefix>/ --index-output=<file> [<options>] <tree-ish>

DESCRIPCIÓN

Lee el contenido de un árbol (un commit o una referencia a un árbol) y lo usa para poblar el índice de Git.

El índice es un área intermedia entre el repositorio y el árbol de trabajo. Normalmente, solo hay una entrada para cada archivo, que representa el estado de ese archivo en la rama actual.

Cuando se utiliza la opción -m (--merge), se realiza una fusión de tres vías. Esto requiere tres árboles: el árbol común ancestral y las dos ramas que se están fusionando. El índice resultante contendrá entradas para archivos conflictivos en diferentes "etapas" (stages).

  • Etapa 1: Contiene el árbol ancestral común.

  • Etapa 2: Contiene el árbol de la rama actual (la que se está fusionando).

  • Etapa 3: Contiene el árbol de la otra rama (la que se fusiona en la actual).

Después de una fusión de tres vías, el índice puede contener entradas en estas etapas 1, 2 y 3. El comando git write-tree no escribirá un árbol si todavía hay entradas en etapas distintas de 0 (que representa el resultado fusionado y final).

La opción -u (--update-index) actualiza el árbol de trabajo para que coincida con el índice después de leer el árbol. Esto se usa a menudo en el contexto de fusiones y descarte de cambios.

ESPECIFICANDO ÁRBOLES

Los árboles se especifican mediante un objeto de Git que puede ser un hash SHA-1, una etiqueta, una rama o cualquier otra referencia a un commit o árbol.

OPCIONES

Además de las opciones estándar de Git, git read-tree acepta las siguientes:

-m, --merge

Realiza una fusión de tres vías. El índice contendrá las tres versiones de los archivos (ancestral, actual, otra). Ver la sección 3-Way Merge para más detalles.

-u, --update-index

Actualiza el árbol de trabajo para que coincida con el índice después de leer el árbol. Los archivos que ya existían y no se han modificado se conservarán. Los archivos que solo existían en el árbol leído se añadirán al árbol de trabajo. Los archivos que solo existían en el índice se eliminarán del árbol de trabajo.

--index-output=<file>

En lugar de actualizar el índice actual, escribe el resultado en el archivo especificado.

--prefix=<prefix>/

Lee el árbol y lo aplica dentro del subdirectorio especificado por <prefix>. Esto es útil para insertar contenido de un árbol en una parte específica de otro.

--trivial

En el modo de fusión -m, solo realiza fusiones triviales. Si encuentra un conflicto, se detiene y no actualiza el índice.

--verify

Verifica que los árboles proporcionados sean válidos antes de proceder. Si alguno no es válido, falla.

--temp

Utiliza un índice temporal en lugar de actualizar el índice actual. Esto es útil si necesitas realizar varias operaciones de lectura de árbol sin afectar el índice principal hasta que estés listo.

-q, --quiet

Suprime la mayoría de los mensajes informativos. Útil en scripts.

FUSIÓN DE DOS ÁRBOLES

Cuando se llama a git read-tree con dos árboles (<old-tree> <new-tree>) y la opción -u, se realiza una fusión de dos árboles. Esto es útil para actualizar el árbol de trabajo basándose en cambios de otra rama, sin realizar una fusión completa de tres vías.

El índice se poblará con el contenido del <new-tree>. Luego, se comparará con el árbol de trabajo. Los archivos que se han modificado en el árbol de trabajo pero no en el <new-tree> se marcarán como "modificados localmente" y no se sobrescribirán. Los archivos que se han modificado en el <new-tree> pero no en el árbol de trabajo se actualizarán. Los archivos que se han añadido o eliminado en el <new-tree> se reflejarán en el árbol de trabajo.

Cuando esta forma de git read-tree retorna exitosamente, puedes ver qué "cambios locales" realizaste se conservaron ejecutando git diff-index --cached $M. Ten en cuenta que esto no coincide necesariamente con lo que git diff-index --cached $H habría producido antes de dicha fusión de dos árboles. Esto se debe a los casos 18 y 19: si ya tenías los cambios en $M (por ejemplo, quizás los recogiste por correo electrónico en formato de parche), git diff-index --cached $H te habría informado del cambio antes de esta fusión, pero no aparecería en la salida de git diff-index --cached $M después de la fusión de dos árboles.

El caso 3 es un poco complicado y necesita explicación. El resultado de esta regla lógicamente debería ser eliminar la ruta si el usuario marcó para la eliminación de la ruta y luego cambió a una nueva rama. Sin embargo, eso impediría la salida inicial, por lo que la regla se modifica para usar M (nuevo árbol) solo cuando el contenido del índice está vacío. De lo contrario, la eliminación de la ruta se mantiene siempre que $H y $M sean iguales.

FUSIÓN DE TRES VÍAS

Cada entrada del "índice" tiene dos bits de estado de "etapa". La etapa 0 es la normal, y es la única que verías en cualquier tipo de uso normal.

Sin embargo, cuando usas git read-tree con tres árboles, la "etapa" comienza en 1.

Esto significa que puedes hacer:

$ git read-tree -m <tree1> <tree2> <tree3>

Y terminarás con un índice con todas las entradas de <tree1> en "etapa1", todas las entradas de <tree2> en "etapa2" y todas las entradas de <tree3> en "etapa3". Al realizar una fusión de otra rama en la rama actual, usamos el árbol ancestro común como <tree1>, la cabeza de la rama actual como <tree2>, y la cabeza de la otra rama como <tree3>.

Además, git read-tree tiene una lógica de caso especial que dice: si ve un archivo que coincide en todos los aspectos en los siguientes estados, se "colapsa" de nuevo a "etapa0":

•Las etapas 2 y 3 son iguales; toma una o la otra (no hace diferencia - el mismo trabajo se ha hecho en nuestra rama en la etapa 2 y en su rama en la etapa 3)
•Las etapas 1 y 2 son iguales y la etapa 3 es diferente; toma la etapa 3 (nuestra rama en la etapa 2 no hizo nada desde el ancestro en la etapa 1 mientras que su rama en la etapa 3 trabajó en ello)
•Las etapas 1 y 3 son iguales y la etapa 2 es diferente; toma la etapa 2 (hicimos algo mientras ellos no hicieron nada)

El comando git write-tree se niega a escribir un árbol sin sentido, y se quejará de entradas sin fusionar si ve una sola entrada que no sea la etapa 0.

De acuerdo, todo esto suena como una colección de reglas totalmente sin sentido, pero en realidad es exactamente lo que quieres para hacer una fusión rápida. Las diferentes etapas representan el "árbol de resultado" (etapa 0, también conocido como "fusionado"), el árbol original (etapa 1, también conocido como "orig"), y los dos árboles que estás tratando de fusionar (etapas 2 y 3 respectivamente).

El orden de las etapas 1, 2 y 3 (por lo tanto, el orden de los tres argumentos de línea de comandos <tree-ish>) es significativo cuando inicias una fusión de 3 vías con un archivo de índice que ya está poblado. Aquí hay un resumen de cómo funciona el algoritmo:

•Si un archivo existe en formato idéntico en los tres árboles, colapsará automáticamente al estado "fusionado" por git read-tree.
•Un archivo que tenga *cualquier* diferencia en los tres árboles permanecerá como entradas separadas en el índice. Depende de la "política de porcelana" determinar cómo eliminar las etapas no 0, e insertar una versión fusionada.
•El archivo de índice se guarda y restaura con toda esta información, por lo que puedes fusionar cosas incrementalmente, pero mientras tenga entradas en las etapas 1/2/3 (es decir, "entradas sin fusionar"), no puedes escribir el resultado. Así que ahora el algoritmo de fusión termina siendo realmente simple:
•Recorre el índice en orden, e ignora todas las entradas de la etapa 0, ya que ya se han procesado.
•Si encuentras una "etapa1", pero ninguna "etapa2" o "etapa3" correspondiente, sabes que ha sido eliminada de ambos árboles (solo existía en el árbol original), y eliminas esa entrada.
•Si encuentras una "etapa2" y "etapa3" correspondientes, eliminas una de ellas y conviertes la otra en una entrada de "etapa0". Elimina cualquier entrada "etapa1" correspondiente si también existe. .. todas las reglas triviales normales ..

Normalmente usarías git merge-index con el suministro de git merge-one-file para hacer este último paso. El script actualiza los archivos en el árbol de trabajo a medida que fusiona cada ruta y al final de una fusión exitosa.

Cuando inicias una fusión de 3 vías con un archivo de índice que ya está poblado, se asume que representa el estado de los archivos en tu árbol de trabajo, e incluso puedes tener archivos con cambios no registrados en el archivo de índice. Se asume además que este estado se ha "derivado" del árbol de etapa 2. La fusión de 3 vías se niega a ejecutarse si encuentra una entrada en el archivo de índice original que no coincide con la etapa 2.

Esto se hace para evitar que pierdas tu trabajo en progreso, y mezclar tus cambios aleatorios en un commit de fusión no relacionado. Para ilustrar, supongamos que comienzas desde lo que se ha commiteado por última vez en tu repositorio:

$ JC=$(git rev-parse --verify "HEAD^0")
$ git checkout-index -f -u -a $JC

Haces ediciones aleatorias, sin ejecutar git update-index. Y luego notas que la punta de tu árbol "upstream" ha avanzado desde que tiraste de él:

$ git fetch git://.... linus
$ LT=$(git rev-parse FETCH_HEAD)

Tu árbol de trabajo todavía se basa en tu HEAD ($JC), pero tienes algunas ediciones desde entonces. La fusión de tres vías asegura que no hayas añadido ni modificado entradas de índice desde $JC, y si no lo has hecho, hace lo correcto. Así que con la siguiente secuencia:

$ git read-tree -m -u $(git merge-base $JC $LT) $JC $LT
$ git merge-index git-merge-one-file -a
$ echo "Merge with Linus" | \
  git commit-tree $(git write-tree) -p $JC -p $LT

Lo que commitearías es una fusión pura entre $JC y $LT sin tus cambios en progreso, y tu árbol de trabajo se actualizaría al resultado de la fusión.

Sin embargo, si tienes cambios locales en el árbol de trabajo que serían sobrescritos por esta fusión, git read-tree se negará a ejecutarse para evitar que tus cambios se pierdan.

En otras palabras, no hay necesidad de preocuparse por lo que existe solo en el árbol de trabajo. Cuando tienes cambios locales en una parte del proyecto que no está involucrada en la fusión, tus cambios no interfieren con la fusión y se conservan intactos. Cuando sí interfieren, la fusión ni siquiera comienza (git read-tree se queja en voz alta y falla sin modificar nada). En tal caso, puedes simplemente continuar haciendo lo que estabas haciendo, e cuando tu árbol de trabajo esté listo (es decir, hayas terminado tu trabajo en progreso), intenta la fusión de nuevo.

CHECKOUT DISPERSO

Nota: Las capacidades skip-worktree en git-update-index(1) y read-tree precedieron la introducción de git-sparse-checkout(1). Se anima a los usuarios a utilizar el comando sparse-checkout en lugar de estos comandos de fontanería para necesidades relacionadas con sparse-checkout/skip-worktree. Sin embargo, la información a continuación puede ser útil para los usuarios que intentan comprender el estilo de patrón utilizado en el modo no cono del comando sparse-checkout.

El "checkout disperso" permite poblar el directorio de trabajo de forma dispersa. Utiliza el bit skip-worktree (ver git-update-index(1)) para decirle a Git si un archivo en el directorio de trabajo merece ser revisado.

git read-tree y otros comandos basados en fusión (git merge, git checkout...) pueden ayudar a mantener el mapa de bits skip-worktree y la actualización del directorio de trabajo. $GIT_DIR/info/sparse-checkout se utiliza para definir el mapa de bits de referencia skip-worktree. Cuando git read-tree necesita actualizar el directorio de trabajo, restablece el bit skip-worktree en el índice basándose en este archivo, que utiliza la misma sintaxis que los archivos .gitignore. Si una entrada coincide con un patrón en este archivo, o la entrada corresponde a un archivo presente en el árbol de trabajo, entonces skip-worktree no se establecerá en esa entrada. De lo contrario, se establecerá skip-worktree.

Luego compara el nuevo valor de skip-worktree con el anterior. Si skip-worktree pasa de establecido a no establecido, añadirá el archivo correspondiente de nuevo. Si pasa de no establecido a establecido, ese archivo será eliminado.

Mientras que $GIT_DIR/info/sparse-checkout se utiliza normalmente para especificar qué archivos están dentro, también puedes especificar qué archivos *no* están dentro, utilizando patrones de negación. Por ejemplo, para eliminar el archivo unwanted:
