GIT-RANGE-DIFF(1) Manual de Git GIT-RANGE-DIFF(1)

NOMBRE

git-range-diff - Compara dos rangos de commits (por ejemplo, dos versiones de una rama)

SINOPSIS

git range-diff [--color=[<cuándo>]] [--no-color] [<opciones-diff>]
        [--no-dual-color] [--creation-factor=<factor>]
        [--left-only | --right-only] [--diff-merges=<formato>]
        [--remerge-diff]
        ( <rango1> <rango2> | <rev1>...<rev2> | <base> <rev1> <rev2> )
        [[--] <ruta>...]

DESCRIPCIÓN

Este comando muestra las diferencias entre dos versiones de una serie de parches, o más generalmente, dos rangos de commits (ignorando los commits de fusión).

En presencia de argumentos <ruta>, estos rangos de commits se limitan correspondientemente.

Para ello, primero encuentra pares de commits de ambos rangos de commits que se corresponden entre sí. Se dice que dos commits se corresponden cuando la diferencia entre sus parches (es decir, la información del autor, el mensaje del commit y la diferencia del commit) es razonablemente pequeña en comparación con el tamaño de los parches. Consulte ``Algoritmo`` a continuación para obtener más detalles.

Finalmente, la lista de commits coincidentes se muestra en el orden del segundo rango de commits, y los commits no coincidentes se insertan justo después de que se hayan mostrado todos sus antecesores.

Hay tres formas de especificar los rangos de commits:

•<rango1> <rango2>: Cualquiera de los rangos de commits puede tener el formato <base>..<rev>, <rev>^! o <rev>^-<n>. Consulte ESPECIFICACIÓN DE RANGOS en gitrevisions(7) para más detalles.
•<rev1>...<rev2>. Esto es equivalente a <rev2>..<rev1> <rev1>..<rev2>.
•<base> <rev1> <rev2>: Esto es equivalente a <base>..<rev1> <base>..<rev2>.

OPCIONES

--no-dual-color

Cuando las diferencias de commits difieren, ‘git range-diff` recrea el coloreado de las diferencias originales y añade marcadores de diferencia externos -/+ con el fondo en rojo/verde para que sea más fácil ver, por ejemplo, cuándo hubo un cambio en las líneas exactas que se añadieron.

Además, las líneas de diferencia de commits que solo están presentes en el primer rango de commits se muestran "atenuadas" (esto se puede anular usando la configuración color.diff.<slot> donde <slot> es uno de contextDimmed, oldDimmed y newDimmed), y las líneas de diferencia de commits que solo están presentes en el segundo rango de commits se muestran en negrita (lo que se puede anular usando la configuración color.diff.<slot> con <slot> siendo uno de contextBold, oldBold o newBold).

Esto se conoce como "coloreado dual" para range-diff. Use --no-dual-color para volver a colorear todas las líneas según los marcadores de diferencia externos (e ignorar completamente la diferencia interna en lo que respecta al color).

--creation-factor=<porcentaje>

Establece el factor de corrección del coste de creación/eliminación a <porcentaje>. El valor predeterminado es 60. Pruebe un valor mayor si git range-diff considera erróneamente un cambio grande como una reescritura total (eliminación de un commit y adición de otro), y un valor menor en el caso inverso. Consulte la sección ``Algoritmo`` para obtener una explicación de por qué esto es necesario.

--left-only

Suprime los commits que faltan en el primer rango especificado (o el rango "izquierdo" cuando se usa el formato <rev1>...<rev2>).

--right-only

Suprime los commits que faltan en el segundo rango especificado (o el rango "derecho" cuando se usa el formato <rev1>...<rev2>).

--diff-merges=<formato>

En lugar de ignorar los commits de fusión, genera diferencias para ellos utilizando la opción correspondiente --diff-merges=<formato> de git-log(1), e inclúyelos en la comparación.

Nota: En el caso común, el modo remerge será el más natural de usar, ya que muestra solo la diferencia sobre lo que la maquinaria de fusión de git habría producido. En otras palabras, si un commit de fusión es el resultado de una git merge sin conflictos, el modo remerge lo representará con una diferencia vacía.

--remerge-diff

Opción de conveniencia, equivalente a --diff-merges=remerge.

--notes[=<ref>], --no-notes

Esta bandera se pasa al programa git log (consulte git-log(1)) que genera los parches.

<rango1> <rango2>

Compara los commits especificados por los dos rangos, donde <rango1> se considera una versión anterior de <rango2>.

<rev1>...<rev2>

Equivalente a pasar <rev2>..<rev1> <rev1>..<rev2>.

<base> <rev1> <rev2>

Equivalente a pasar <base>..<rev1> <base>..<rev2>. Tenga en cuenta que <base> no necesita ser el punto exacto de bifurcación de las ramas. Ejemplo: después de hacer rebase en una rama mi-tema, git range-diff mi-tema@{u} mi-tema@{1} mi-tema mostraría las diferencias introducidas por el rebase.

git range-diff también acepta las opciones de diff regulares (consulte git-diff(1)), en particular las opciones --color=[<cuándo>] y --no-color. Estas opciones se utilizan al generar la "diferencia entre parches", es decir, para comparar el autor, el mensaje del commit y la diferencia de los commits antiguos/nuevos correspondientes. Actualmente no hay forma de ajustar la mayoría de las opciones de diff que se pasan a git log al generar esos parches.

ESTABILIDAD DE LA SALIDA

La salida del comando range-diff está sujeta a cambios. Está pensada para ser una salida de porcelana legible por humanos, no algo que pueda usarse entre versiones de Git para obtener un range-diff textualmente estable (en contraposición a algo como la opción --stable de git-patch-id(1)). Tampoco existe un equivalente de git-apply(1) para range-diff, la salida no está pensada para ser legible por máquinas.

Esto es particularmente cierto al pasar opciones de diff. Actualmente algunas opciones como --stat pueden, como efecto emergente, producir una salida que es bastante inútil en el contexto de range-diff. Las versiones futuras de range-diff pueden aprender a interpretar dichas opciones de una manera específica para range-diff (por ejemplo, para que --stat produzca una salida legible que resuma cómo cambió la estadística de diferencias).

CONFIGURACIÓN

Este comando utiliza la configuración diff.color.* y pager.range-diff (esta última está habilitada por defecto). Consulte git-config(1).

EJEMPLOS

Cuando un rebase requirió la resolución de conflictos de fusión, compare los cambios introducidos por el rebase inmediatamente después usando:

$ git range-diff @{u} @{1} @

Cuando la salida va a una terminal, se codifica por colores de forma predeterminada, igual que la salida regular de git diff. Además, la primera línea (añadir un commit) es verde, la última línea (borrar un commit) es roja, la segunda línea (con una coincidencia perfecta) es amarilla como el encabezado del commit de la salida de git show, y la tercera línea colorea el commit antiguo en rojo, el nuevo en verde y el resto como el encabezado del commit de git show.

Un diff de diffs codificado por colores de forma ingenua es en realidad un poco difícil de leer, ya que colorea las líneas enteras de rojo o verde. La línea que añadió "What is unexpected" en el commit antiguo, por ejemplo, está completamente en rojo, incluso si la intención del commit antiguo era añadir algo.

Para ayudar con eso, range usa el modo --dual-color de forma predeterminada. En este modo, el diff de diffs conservará los colores originales del diff, y antepondrá a las líneas marcadores -/+ que tienen su fondo en rojo o verde, para hacer más obvio que describen cómo cambió el diff en sí mismo.

ALGORITMO

La idea general es esta: generamos una matriz de costes entre los commits en ambos rangos de commits, y luego resolvemos la asignación de menor coste.

La matriz de costes se rellena así: para cada par de commits, se generan ambos diffs y se genera el "diff de diffs", con 3 líneas de contexto, y luego el número de líneas de ese diff se usa como coste.

Para evitar falsos positivos (por ejemplo, cuando un parche ha sido eliminado, y un parche no relacionado ha sido añadido entre dos iteraciones de la misma serie de parches), la matriz de costes se extiende para permitir eso, añadiendo entradas de coste fijo para borrados/añadidos completos.

Ejemplo: Sean los commits 1--2 la primera iteración de una serie de parches y A--C la segunda iteración. Asumamos que A es un cherry-pick de 2, y C es un cherry-pick de 1 pero con una pequeña modificación (digamos, un error tipográfico corregido). Visualicemos los commits como un grafo bipartito:

    1            A
    2            B
                 C

Estamos buscando una explicación "mejor" de la nueva serie en términos de la antigua. Podemos representar una "explicación" como una arista en el grafo:

    1            A
               /
    2 --------'  B
                 C

Esta explicación es "gratuita" porque no hubo cambio. De manera similar, C podría ser explicado usando 1, pero eso tiene algún coste c>0 debido a la modificación:

    1 ----.      A
          |    /
    2 ----+---'  B
          |
          `----- C
          c>0

En términos matemáticos, lo que estamos buscando es algún tipo de emparejamiento bipartito de coste mínimo; `1` se empareja con C a algún coste, etc. El grafo subyacente es de hecho un grafo bipartito completo; el coste que asociamos a cada arista es el tamaño del diff entre los parches de los dos commits. Para explicar también commits nuevos, introducimos nodos ficticios en ambos lados:

    1 ----.      A
          |    /
    2 ----+---'  B
          |
          o     `----- C
          c>0
    o            o
    o            o

El coste de una arista o--C es el tamaño del diff de C, modificado por un factor de ajuste que debería ser menor que el 100%. El coste de una arista o--o es gratuito. El factor de ajuste es necesario porque incluso si 1 y C no tienen nada en común, aún pueden compartir algunas líneas vacías y tal, posiblemente haciendo la asignación 1--C, o--o ligeramente más barata que 1--o, o--C incluso si 1 y C no tienen nada en común. Con el factor de ajuste requerimos una parte común mucho mayor para considerar que los parches corresponden.

El tiempo total necesario para computar este algoritmo es el tiempo necesario para computar n+m diffs de commits y luego n*m diffs de parches, más el tiempo necesario para computar la asignación de menor coste entre n y m diffs. Git usa una implementación del algoritmo de Jonker-Volgenant para resolver el problema de asignación, que tiene complejidad de tiempo cúbica. El emparejamiento encontrado en este caso se verá así:

    1 ----.      A
          |    /
    2 ----+---'  B
       .--+-----'
    o -'  `----- C
          c>0
    o ---------- o
    o ---------- o
