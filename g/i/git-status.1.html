ACTUALIZACIÓN EN SEGUNDO

PLANO

Por defecto, git status actualizará automáticamente el índice, actualizando la información de estadísticas almacenada desde el árbol de trabajo y escribiendo el resultado. Escribir el índice actualizado es una optimización que no es estrictamente necesaria (status calcula los valores por sí mismo, pero escribirlos es solo para ahorrar a los programas posteriores repetir nuestro cálculo). Cuando status se ejecuta en segundo plano, el bloqueo (lock) mantenido durante la escritura puede entrar en conflicto con otros procesos simultáneos, provocando que fallen. Los scripts que ejecuten status en segundo plano deberían considerar usar git --no-optional-locks status (consulte git(1) para m

ás deta
lles).

ARCHIVOS SIN RASTREAR Y

RENDIMIENTO

git status puede ser muy lento en árboles de trabajo grandes si/necesita buscar archivos y directorios sin rastrear. Hay muchas opciones de configuración disponibles para acelerar esto, ya sea evitando el trabajo o utilizando los resultados almacenados de comandos de Git anteriores. No hay un conjunto único de ajustes óptimos adecuado para todos. Listaremos un resumen de las opciones relevantes para ayudarle, pero antes de entrar en la lista, es posible que desee ejecutar git status de nuevo, porque su configuración puede estar almacenando ya los resultados de git status, por lo que podría ser más rápido en ejecuciones

posteriores.
•La bandera --untracked-files=no o la configuración status.showUntrackedFiles=no (consulte arriba para ambas): indican que git status no debe informar de archivos sin rastrear. Esta es la opción más rápida. git status no listará los archivos sin rastrear, así que debe tener cuidado de recordar si crea algún archivo nuevo y añadirlo manualmente con git add
.
•advice.statusUoption=false (consulte git-config(1)): establecer esta variable en false desactiva el mensaje de advertencia dado cuando la enumeración de archivos sin rastrear tarda más de 2 segundos. En un proyecto grande, puede tardar más y el usuario puede haber aceptado ya el compromiso (por ejemplo, usar "-uno" puede no ser una opción aceptable para el usuario), en cuyo caso, no tiene sentido emitir el mensaje de advertencia, y en tal caso, desactivar la advertencia puede ser lo
mejor.
•core.untrackedCache=true (consulte git-update-index(1)): habilita la función de caché de sin rastrear y solo busca directorios que han sido modificados desde el git status anterior. Git recuerda el conjunto de archivos sin rastrear dentro de cada directorio y asume que si un directorio no ha sido modificado, entonces el conjunto de archivos sin rastrear dentro de él no ha cambiado. Esto es mucho más rápido que enumerar el contenido de cada directorio, pero aún no es sin coste, porque Git todavía tiene que buscar el conjunto de directorios modificados. La caché de sin rastrear se almacena en el archivo .git/index. El coste reducido de buscar archivos sin rastrear se compensa ligeramente por el tamaño aumentado del índice y el coste de mantenerlo actualizado. Ese tiempo de búsqueda reducido generalmente vale la pena por el tamaño
adicional.
•core.untrackedCache=true y core.fsmonitor=true o core.fsmonitor=<ruta-al-comando-hook> (consulte git-update-index(1)): habilita tanto la caché de sin rastrear como la función FSMonitor, y solo busca directorios que han sido modificados desde el anterior git status. Esto es más rápido que usar solo la caché de sin rastrear porque Git también puede evitar buscar directorios modificados. Git solo tiene que enumerar el conjunto exacto de directorios que han cambiado recientemente. Aunque la función FSMonitor puede ser habilitada sin la caché de sin rastrear, los beneficios se reducen enormemente en ese
caso.

Tenga en cuenta que después de activar la caché de sin rastrear y/o la función FSMonitor puede tomar unos cuantos git status para que las distintas cachés se calienten an

tes de ver tiempos de comand
o mejorados. Esto es normal.
