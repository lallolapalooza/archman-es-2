NAME

gitsubmodules — the Git submodule facilities

SYNOPSIS

git submodule status [-q|--quiet] [-m|--measured] [-d|--debug] [...])
git submodule init [-f|--force] [--] [...])
git submodule update [-f|--force] [--init] [--recursive] [--jobs <N>] [--filter] [...])
git submodule add [-f|--force] [-o|--off] [-i|--init] [-N|--no-checkout] [--resolve <method>] [--] <repository> [<path>])
git submodule deinit [-f|--force] [--all] [--] [...])
git submodule rm [-f|--force] [--cached] [--ignore-unmatch] [--] [...])
git submodule set-url [--] <path> [<newurl>])
git submodule set- submodule.recurse [--] [<newval>])

DESCRIPTION

Submodules allow you to embed one Git repository within another. This is useful for many reasons:

  • To include a dependency project that is developed independently.

  • To allow a project to have sub-projects that are developed by different teams.

  • To allow a project to depend on external code that is not hosted on the same server.

A submodule is a Git repository embedded inside the main repository. The main repository does not store the submodule content directly; instead, it stores a reference (a commit hash) to the submodule repository.

The submodules are defined in the .gitmodules file. This file is part of the main repository and describes how to clone and update the submodule repositories.

THE CONFIGURATION OF SUBMODULES

The .gitmodules file is a text file where each section defines a submodule. The section header is of the form [submodule "<name>"], where <name> is the path relative to the main repository where the submodule will be cloned.

The following keys are supported within a submodule section:

url
The URL of the submodule repository. This is the only mandatory field.
active
A boolean or a pathspec that controls whether the submodule is considered active. See ACTIVE SUBMODULES below.
ignore
A boolean or a pathspec that controls how Git should behave when it detects changes in the submodule directory. See git-submodule(1) for details. The default value is untracked. Other values are dirty, all, and none.
path
This field is no longer used. The submodule name is derived from the section header.
branch
A specific branch name to checkout when the submodule is initialized or updated. If this is not specified, the submodule will be checked out at the commit recorded in the superproject.
tag
A specific tag name to checkout when the submodule is initialized or updated. If this is not specified, the submodule will be checked out at the commit recorded in the superproject.

FORMS

The .gitmodules file can contain multiple sections defining submodules. The following is an example of a .gitmodules file:

[submodule "lib/foo"]
  url = https://example.org/foo.git
  active = true
  branch = main
[submodule "lib/bar"]
  url = https://example.org/bar.git
  branch = v1.0
[submodule "lib/baz"]
  url = https://example.org/baz.git
  active = false

In this example:

  • The submodule at lib/foo is always active. When the superproject is checked out, the submodule will be checked out at the commit recorded in the superproject, or if the branch is set, it will be checked out at the tip of the main branch.

  • The submodule at lib/bar is active by default (since active is not specified and defaults to true). When the superproject is checked out, the submodule will be checked out at the commit recorded in the superproject, or if the branch is set, it will be checked out at the tip of the v1.0 branch.

  • The submodule at lib/baz is explicitly inactive. It will not be checked out by default.

Note that the url field is optional if the submodule is inactive. It is only needed if the submodule is active.

ACTIVE SUBMODULES

The active flag in .gitmodules can be set to true or false to explicitly enable or disable a submodule. If the active flag is not present, the submodule is considered active by default.

The active flag can also take a pathspec, which allows for more flexible control over which submodules are active. Pathspecs can be used to enable submodules based on their path, or to exclude specific submodules from being active.

When multiple active flags are specified in the .gitmodules file, they are evaluated in order. The first matching rule determines whether the submodule is active or not.

The following precedence rules apply:

  1. A submodule is active if submodule.<name>.active is set to true in the configuration file.
  2. A submodule is inactive if submodule.<name>.active is set to false in the configuration file.
  3. A submodule is active if it matches a pathspec in submodule.active.
  4. A submodule is inactive if it matches a pathspec in submodule.active that is prefixed with :(exclude).

Here is an example that illustrates these rules:

[submodule "foo"]
  active = true
  url = https://example.org/foo
[submodule "bar"]
  url = https://example.org/bar
[submodule "baz"]
  url = https://example.org/baz
[submodule "bob"]
  ignore = true
[submodule]
  active = b*
  active = :(exclude) baz

In this configuration:

  • foo is active due to its own active = true setting (rule 1).

  • bar and baz are active due to the active = b* pathspec (rule 3). This pathspec matches any submodule whose name starts with "b".

  • Even though baz matches active = b*, it is then excluded by the subsequent rule active = :(exclude) baz (rule 4). Therefore, baz is inactive.

  • bob is active due to the active = b* pathspec (rule 3).

Therefore, submodules foo, bar, and bob are active, while baz is inactive.

Note that (3) is a historical artefact and will be ignored if the (1) and (2) specify that the submodule is not active. In other words, if we have a submodule.<name>.active set to false or if the submodule’s path is excluded in the pathspec in submodule.active, the url doesn’t matter whether it is present or not. This is illustrated in the example that follows.

[submodule "foo"]
  active = true
  url = https://example.org/foo
[submodule "bar"]
  url = https://example.org/bar
[submodule "baz"]
  url = https://example.org/baz
[submodule "bob"]
  ignore = true
[submodule]
  active = b*
  active = :(exclude) baz

In here all submodules except baz (foo, bar, bob) are active. foo due to its own active flag and all the others due to the submodule active pathspec, which specifies that any submodule starting with b except baz are also active, regardless of the presence of the .url field.

WORKFLOW FOR A THIRD PARTY LIBRARY

# Add a submodule
git submodule add <URL> <path>
# Occasionally update the submodule to a new version:
git -C <path> checkout <new-version>
git add <path>
git commit -m "update submodule to new version"
# See the list of submodules in a superproject
git submodule status
# See FORMS on removing submodules

WORKFLOW FOR AN ARTIFICIALLY SPLIT REPO

# Enable recursion for relevant commands, such that
# regular commands recurse into submodules by default
git config --global submodule.recurse true
# Unlike most other commands below, clone still needs
# its own recurse flag:
git clone --recurse <URL> <directory>
cd <directory>
# Get to know the code:
git grep foo
git ls-files --recurse-submodules

Note

git ls-files also requires its own --recurse-submodules flag.

# Get new code
git fetch
git pull --rebase
# Change worktree
git checkout
git reset

IMPLEMENTATION DETAILS

When cloning or pulling a repository containing submodules the submodules will not be checked out by default; you can instruct clone to recurse into submodules. The init and update subcommands of git submodule will maintain submodules checked out and at an appropriate revision in your working tree. Alternatively you can set submodule.recurse to have checkout recurse into submodules (note that submodule.recurse also affects other Git commands, see git-config(1) for a complete list).
