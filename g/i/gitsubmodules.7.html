DESCRIPCIÓ

N

Un submódulo es un repositorio incrustado dentro de otro repositorio. El submódulo tiene su propio historial; el repositorio en el que está incrustado se denomina

superproyecto.

En el sistema de archivos, un submódulo generalmente (pero no siempre - ver FORMAS más abajo) consiste en (i) un directorio Git ubicado bajo el directorio $GIT_DIR/modules/ de su superproyecto, (ii) un directorio de trabajo dentro del directorio de trabajo del superproyecto, y un archivo .git en la raíz del directorio de trabajo del submódulo que apunta a (i)

.

Asumiendo que el submódulo tiene un directorio Git en $GIT_DIR/modules/foo/ y un directorio de trabajo en path/to/bar/, el superproyecto rastrea el submódulo a través de una entrada gitlink en el árbol en path/to/bar y una entrada en su archivo .gitmodules (ver gitmodules(5)) de la forma submodule.foo.path = path/to/bar

.

La entrada gitlink contiene el nombre del objeto del commit que el superproyecto espera que tenga el directorio de trabajo del

submódulo.

La sección submodule.foo.* en el archivo .gitmodules da pistas adicionales a la capa porcelain de Git. Por ejemplo, la configuración submodule.foo.url especifica dónde obtener el

submódulo.

Los submódulos se pueden utilizar para al menos dos casos de uso

diferentes:
1.Usar otro proyecto mientras se mantiene un historial independiente. Los submódulos permiten contener el árbol de trabajo de otro proyecto dentro de tu propio árbol de trabajo mientras se mantienen los historiales de ambos proyectos separados. Además, ya que los submódulos están fijados a una versión arbitraria, el otro proyecto puede desarrollarse de forma independiente sin afectar al superproyecto, permitiendo al superproyecto fijarse a nuevas versiones solo cuando se
desee.
2.Dividir un proyecto (lógicamente único) en múltiples repositorios y volver a unirlos. Esto se puede usar para superar las limitaciones actuales de la implementación de Git para tener un acceso más detallado:
•Tamaño del repositorio Git: En su forma actual Git escala mal para repositorios grandes que contienen contenido que no está comprimido por el cálculo de delta entre árboles. Por ejemplo, puedes usar submódulos para contener grandes recursos binarios y estos repositorios se pueden clonar de forma superficial para que no tengas un gran historial
localmente.
•Tamaño de transferencia: En su forma actual Git requiere el árbol de trabajo completo presente. No permite la transferencia de árboles parciales en fetch o clone. Si el proyecto en el que trabajas consiste en múltiples repositorios unidos como submódulos en un superproyecto, puedes evitar obtener los árboles de trabajo de los repositorios en los que no estás
interesado.
•Control de acceso: Al restringir el acceso
de los usuarios a los submódulos, esto se
puede usar para implementar políticas de l
ectura/escritura para diferentes usuarios.

LA CONFIGURACIÓN DE

SUBMÓDULOS

Las operaciones de submódulo se pueden configurar usando los siguientes mecanismos (de mayor a menor precedencia)

:
•La línea de comandos para aquellos comandos que soportan tomar submódulos como parte de sus especificaciones de ruta. La mayoría de los comandos tienen un indicador booleano --recurse-submodules que especifica si recursar en los submódulos. Ejemplos son grep y checkout. Algunos comandos toman enums, como fetch y push, donde puedes especificar cómo se ven afectados los
submódulos.
•La configuración dentro del submódulo. Esto incluye $GIT_DIR/config en el submódulo, pero también configuraciones en el árbol como archivos .gitattributes o .gitignore que especifican el comportamiento de los comandos dentro del submódulo.

Por ejemplo, un efecto del archivo .gitignore del submódulo se observaría cuando ejecutas git status --ignore-submodules=none en el superproyecto. Esto recopila información del directorio de trabajo del submódulo ejecutando status en el submódulo mientras se presta atención al archivo .gitignore del

submódulo.

El archivo $GIT_DIR/config del submódulo entraría en juego al ejecutar git push --recurse-submodules=check en el superproyecto, ya que esto comprobaría si el submódulo tiene cambios no publicados en ningún remoto. Los remotos se configuran en el submódulo como de costumbre en el archivo $GIT_DIR

/con
fig.
•El archivo de configuración $GIT_DIR/config en el superproyecto. Git solo recursa en submódulos activos (ver la sección "SUBMÓDULOS ACTIVOS" más abajo).

Si el submódulo aún no está inicializado, entonces la config

uración dentro del submódulo aún no existe, por lo que dó
nde obtener el submódulo se configura aquí, por ejemplo.
•El archivo .gitmodules dentro del superproyecto. Un proyecto generalmente usa este archivo para sugerir valores predeterminados para la colección upstream de repositorios para el mapeo que se requiere entre el nombre de un submódulo y su ruta.

Este archivo sirve principalmente como el mapeo entre el nombre y la ruta de los submódulos en el superproyecto, de modo que se pueda localizar el directorio Git del

submódulo.

Si el submódulo nunca ha sido inicializado, este e

FORMA

S

Los submódulos pueden tomar las siguientes

formas:
•La forma básica descrita en DESCRIPCIÓN con un directorio Git, un directorio de trabajo, un gitlink, y una entrad
a
.gitmodules. •Submódulo de "forma antigua": Un directorio de trabajo con un directorio .git incrustado, y el rastreo gitlink y la entrada .gitmodules en el superproyecto. Esto se encuentra típicamente en repositorios generados usando versiones anteriores de Git.

Es posible construir estos repositorios de forma antigua

manualmente.

Al desinicializar o eliminar (ver más abajo), el directorio Git del submódulo se mueve automáticamente a $GIT_DIR/modules/<name>/ del supe

rproy
ecto.
•Submódulo desinicializado: Un gitlink, y una entrada .gitmodules, pero sin directorio de trabajo del submódulo. El directorio Git del submódulo puede estar allí ya que después de desinicializar el directorio Git se conserva. El directorio que se supone que debe ser el directorio de trabajo está vacío en su lugar.

Un submódulo se puede desinicializar ejecutando git submodule deinit. Además de vaciar el directorio de trabajo, este comando solo modifica el archivo $GIT_DIR/config del superproyecto, por lo que el historial del superproyecto no se ve afectado. Esto se puede deshacer usando git submodule in

it
.
•Submódulo eliminado: Un submódulo se puede eliminar ejecutando git rm <submodule-path> && git commit. Esto se puede deshacer usando git revert.

La eliminación elimina los datos de rastreo del superproyecto, que son tanto la entrada gitlink como la sección en el archivo .gitmodules. El directorio de trabajo del submódulo se elimina del sistema de archivos, pero el directorio Git se conserva para hacer posible hacer checkout de commits pasados sin requerir obtener de otro

repositorio.

Para eliminar completamente un submódulo, elimina manualmente $GIT_DIR/modules/<name>/

.
