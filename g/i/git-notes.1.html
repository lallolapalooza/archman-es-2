NAME

git-notes(1) — Añade o inspecciona notas de objetos

SYNOPSIS

git notes [list [<objeto>]]
git notes add [-f] [--allow-empty] [--[no-]separator | --separator=<salto-párrafo>] [--[no-]stripspace] [-F <archivo> | -m <mensaje> | (-c | -C) <objeto>] [-e] [<objeto>]
git notes copy [-f] ( --stdin | <objeto-origen> [<objeto-destino>] )
git notes append [--allow-empty] [--[no-]separator | --separator=<salto-párrafo>] [--[no-]stripspace] [-F <archivo> | -m <mensaje> | (-c | -C) <objeto>] [-e] [<objeto>]
git notes edit [--allow-empty] [<objeto>] [--[no-]stripspace]
git notes show [<objeto>]
git notes merge [-v | -q] [-s <estrategia> ] <ref-notas>
git notes merge --commit [-v | -q]
git notes merge --abort [-v | -q]
git notes remove [--ignore-missing] [--stdin] [<objeto>...]
git notes prune [-n] [-v]
git notes get-ref

DESCRIPTION

Añade, elimina o lee notas adjuntas a objetos, sin modificar los objetos mismos.

Por defecto, las notas se guardan y leen de refs/notes/commits, pero este valor por defecto puede ser anulado. Consulta las secciones OPCIONES, CONFIGURACIÓN y ENTORNO más abajo. Si este ref no existe, se creará silenciosamente cuando se necesite para almacenar una nota.

Un uso típico de las notas es complementar un mensaje de commit sin cambiar el commit en sí. Las notas pueden ser mostradas por git log junto con el mensaje de commit original. Para distinguir estas notas del mensaje almacenado en el objeto de commit, las notas están indentadas como el mensaje, después de una línea sin indentación que dice "Notes (<refname>):" (o "Notes:" para refs/notes/commits).

Las notas también pueden añadirse a parches preparados con git format-patch usando la opción --notes. Dichas notas se añaden como un comentario del parche después de una línea separadora de tres guiones.

Para cambiar qué notas son mostradas por git log, consulta la discusión sobre notes.displayRef en CONFIGURACIÓN.

Consulta la configuración notes.rewrite.<comando> para una forma de transportar notas a través de comandos que reescriben commits.

SUBCOMMANDS

list

Lista el objeto de notas para un objeto dado. Si no se proporciona ningún objeto, muestra una lista de todos los objetos de notas y los objetos que anotan (en el formato "<objeto-nota> <objeto-anotado>"). Este es el subcomando por defecto si no se proporciona ningún subcomando.

add

Añade notas para un objeto dado (por defecto HEAD). Aborta si el objeto ya tiene notas (usa -f para sobrescribir notas existentes). Sin embargo, si estás usando add interactivamente (usando un editor para proporcionar el contenido de las notas), entonces en lugar de abortar, las notas existentes se abrirán en el editor (como el subcomando edit). Si especificas múltiples -m y -F, se insertará una línea en blanco entre los mensajes. Usa la opción --separator para insertar otros delimitadores. Puedes usar -e para editar y refinar interactivamente los mensajes suministrados por las opciones -m y -F (usando un editor) antes de añadir la nota.

copy

Copia las notas del primer objeto al segundo objeto (por defecto HEAD). Aborta si el segundo objeto ya tiene notas, o si el primer objeto no tiene ninguna (usa -f para sobrescribir notas existentes en el segundo objeto). Este subcomando es equivalente a: git notes add [-f] -C $(git notes list <objeto-origen>) <objeto-destino>

En modo --stdin, toma líneas en el formato

<objeto-origen> ESP <objeto-destino> [ ESP <resto> ] LF

en la entrada estándar, y copia las notas de cada <objeto-origen> a su correspondiente <objeto-destino>. (El opcional <resto> se ignora para que el comando pueda leer la entrada dada al hook post-rewrite).

--stdin no puede combinarse con nombres de objeto dados en la línea de comandos.

append

Añade nuevos mensajes dados por las opciones -m o -F a una nota existente, o los añade como una nueva nota si no existe, para el objeto (por defecto HEAD). Al añadir a una nota existente, se añade una línea en blanco antes de cada nuevo mensaje como separador de párrafos. El separador se puede personalizar con la opción --separator. Edita las notas a añadir dadas por las opciones -m y -F con -e interactivamente (usando un editor) antes de añadir la nota.

edit

Edita las notas para un objeto dado (por defecto HEAD).

show

Muestra las notas para un objeto dado (por defecto HEAD).

merge

Fusiona el ref de notas dado en el ref de notas actual. Esto intentará fusionar los cambios realizados por el ref de notas dado ("remoto") desde la base de fusión (si existe) en el ref de notas actual ("local").

Si surgen conflictos y no se proporciona una estrategia para resolver automáticamente las notas en conflicto (consulta la sección "ESTRATEGIAS DE FUSIÓN DE NOTAS"), se utiliza el resolver manual. Este resolver extrae las notas en conflicto en un espacio de trabajo especial (.git/NOTES_MERGE_WORKTREE) e instruye al usuario para que resuelva manualmente los conflictos allí. Cuando termine, el usuario puede finalizar la fusión con git notes merge --commit, o abortar la fusión con git notes merge --abort.

remove

Elimina las notas para los objetos dados (por defecto HEAD). Al proporcionar cero o un objeto desde la línea de comandos, esto es equivalente a especificar un mensaje de nota vacío al subcomando edit.

En modo --stdin, también elimina los nombres de objeto dados en la entrada estándar. En otras palabras, --stdin puede combinarse con nombres de objeto de la línea de comandos.

prune

Elimina todas las notas para objetos inexistentes/no alcanzables.

get-ref

Imprime el ref de notas actual. Esto proporciona una forma fácil de recuperar el ref de notas actual (por ejemplo, desde scripts).

OPTIONS

-f, --force

Al añadir notas a un objeto que ya tiene notas, sobrescribe las notas existentes (en lugar de abortar).

-m <mensaje>, --message=<mensaje>

Usa el mensaje de nota dado (en lugar de pedirlo). Si se dan múltiples opciones -m, sus valores se concatenan como párrafos separados.

-F <archivo>, --file=<archivo>

Toma el mensaje de nota del archivo dado. Usa - para leer el mensaje de nota de la entrada estándar.

-C <objeto>, --reuse-message=<objeto>

Toma el objeto blob dado (por ejemplo, otra nota) como mensaje de nota. (Usa git notes copy <objeto> en su lugar para copiar notas entre objetos.) Implica --no-stripspace ya que el comportamiento por defecto es copiar el mensaje literalmente.

-c <objeto>, --reedit-message=<objeto>

Similar a -C, pero con -c se invoca el editor, para que el usuario pueda editar más el mensaje de nota.

--allow-empty

Permite almacenar un objeto de nota vacío. El comportamiento por defecto es eliminar automáticamente las notas vacías.

--separator=<salto-párrafo>, --separator, --no-separator

Especifica una cadena utilizada como separador de párrafos personalizado (se añade una nueva línea al final según sea necesario). Si --no-separator

>, no se añadirán separadores entre párrafos. Por defecto, una línea en blanco.

--stripspace, --no-stripspace

Limpia los espacios en blanco. Específicamente (véase git-stripspace(1)):
•elimina los espacios en blanco al final de todas las líneas
•contrae múltiples líneas vacías consecutivas en una sola línea vacía
•elimina las líneas vacías del principio y del final de la entrada
•añade un \n faltante a la última línea si es necesario.

--stripspace es el comportamiento por defecto, excepto para -C/--reuse-message. Sin embargo, tenga en cuenta que esto depende del orden de las opciones similares. Por ejemplo, para -C <object> -m<message>, --stripspace se utilizará porque el valor por defecto de -m anula el -Canterior. Esta es una limitación conocida que puede corregirse en el futuro.

--ref=<ref>

Manipula el árbol de notas en <ref>. Esto anula la variable de entorno GIT_NOTES_REF y la configuración core.notesRef . La referencia especifica el nombre completo de la referencia cuando comienza con refs/notes/; cuando comienza con notes/, refs/ y, en caso contrario, refs/notes/ se anteponen para formar el nombre completo de la referencia.

--ignore-missing

No considerar un error solicitar la eliminación de notas de un objeto que no tiene notas adjuntas.

--stdin

Válido solo para remove y copy. Véanse los subcomandos respectivos.

-n, --dry-run

No elimina nada; solo informa de los nombres de los objetos cuyas notas serían eliminadas.

-s <strategy>, --strategy=<strategy>

Al fusionar notas, resuelve los conflictos de notas utilizando la estrategia dada. Se reconocen las siguientes estrategias: manual (por defecto), ours, theirs, union y cat_sort_uniq. Esta opción anula la configuración notes.mergeStrategy . Véase la sección "ESTRATEGIAS DE FUSIÓN DE NOTAS" más abajo para más información sobre cada estrategia de fusión de notas.

--commit

Finaliza una git notes mergeen curso. Utilice esta opción cuando haya resuelto los conflictos que git notes merge almacenó en .git/NOTES_MERGE_WORKTREE. Esto enmienda la confirmación de fusión parcial creada por git notes merge (almacenada en .git/NOTES_MERGE_PARTIAL) añadiendo las notas en .git/NOTES_MERGE_WORKTREE. La referencia de notas almacenada en el symref .git/NOTES_MERGE_REF se actualiza a la confirmación resultante.

--abort

Aborta/restablece una git notes mergeen curso, es decir, una fusión de notas con conflictos. Esto simplemente elimina todos los archivos relacionados con la fusión de notas.

-q, --quiet

Al fusionar notas, opera de forma silenciosa.

-v, --verbose

Al fusionar notas, sé más detallado. Al podar notas, informa de todos los nombres de los objetos cuyas notas son eliminadas.

DISCUSIÓN

Las notas de confirmación son blobs que contienen información adicional sobre un objeto (normalmente información para complementar el mensaje de una confirmación). Estos blobs se toman de las referencias de notas. Una referencia de notas es normalmente una rama que contiene "archivos" cuyas rutas son los nombres de los objetos para los objetos que describen, con algunos separadores de directorio incluidos por razones de rendimiento [1].

Cada cambio en las notas crea una nueva confirmación en la referencia de notas especificada. Por lo tanto, puede inspeccionar el historial de las notas invocando, por ejemplo, git log -p notes/commits. Actualmente, el mensaje de la confirmación solo registra qué operación desencadenó la actualización, y la autoría de la confirmación se determina según las reglas habituales (véase git-commit(1)). Estos detalles pueden cambiar en el futuro.

También está permitido que una referencia de notas apunte directamente a un objeto árbol, en cuyo caso el historial de las notas puede leerse con git log -p -g <refname>.

ESTRATEGIAS DE FUSIÓN DE NOTAS

La estrategia de fusión de notas por defecto es manual, que extrae las notas en conflicto en un árbol de trabajo especial para resolver los conflictos de notas (.git/NOTES_MERGE_WORKTREE), e instruye al usuario para que resuelva los conflictos en ese árbol de trabajo. Cuando termine, el usuario puede finalizar la fusión con git notes merge --commit, o abortar la fusión con git notes merge --abort.

Los usuarios pueden seleccionar una estrategia de fusión automatizada de entre las siguientes utilizando la opción -s/--strategy o configurando notes.mergeStrategy adecuadamente:

ours resuelve automáticamente los conflictos de notas a favor de la versión local (es decir, la referencia de notas actual).

theirs resuelve automáticamente los conflictos de notas a favor de la versión remota (es decir, la referencia de notas dada que se fusiona en la referencia de notas actual).

union resuelve automáticamente los conflictos de notas concatenando las versiones local y remota.

cat_sort_uniq es similar a union, pero además de concatenar las versiones local y remota, esta estrategia también ordena las líneas resultantes y elimina las líneas duplicadas del resultado. Esto es equivalente a aplicar el pipeline de shell "cat | sort | uniq" a las versiones local y remota. Esta estrategia es útil si las notas siguen un formato basado en líneas donde se quiere evitar líneas duplicadas en el resultado de la fusión. Nótese que si la versión local o la remota contienen líneas duplicadas antes de la fusión, estas también serán eliminadas por esta estrategia de fusión de notas.

EJEMPLOS

Puede usar las notas para añadir anotaciones con información que no estaba disponible en el momento en que se escribió una confirmación.

$ git notes add -m 'Tested-by: Johannes Sixt <j6t@kdbg.org>' 72a144e2
$ git show -s 72a144e
[...]
    Signed-off-by: Junio C Hamano <gitster@pobox.com>
Notes:
    Tested-by: Johannes Sixt <j6t@kdbg.org>

En principio, una nota es un blob regular de Git, y se acepta cualquier tipo de formato (o ausencia de formato). Puede crear notas de forma segura para binarios a partir de archivos arbitrarios utilizando git hash-object:

$ cc *.c
$ blob=$(git hash-object -w a.out)
$ git notes --ref=built add --allow-empty -C "$blob" HEAD

(No puede simplemente usar git notes --ref=built add -F a.out HEAD porque eso no es seguro para binarios). Por supuesto, no tiene mucho sentido mostrar notas que no son de formato de texto con git log, así que si usa tales notas, probablemente necesitará escribir algunas herramientas de propósito especial para hacer algo útil con ellas.

CONFIGURACIÓN

core.notesRef

Referencia de notas a leer y manipular en lugar de refs/notes/commits. Debe ser un nombre de referencia sin abreviar. Esta configuración puede ser anulada a través del entorno y la línea de comandos.

Todo lo que hay por encima de esta línea en esta sección no está incluido desde la documentación de git-config(1) . El contenido que sigue es el mismo que el que se encuentra allí:

notes.mergeStrategy

Qué estrategia de fusión elegir por defecto al resolver conflictos de notas. Debe ser una de manual, ours, theirs, union, o cat_sort_uniq. Por defecto es manual. Véase la sección "ESTRATEGIAS DE FUSIÓN DE NOTAS" de git-notes(1) para más información sobre cada estrategia.

Esta configuración puede ser anulada pasando la opción --strategy a git-notes(1).

notes.<name>.mergeStrategy

Qué estrategia de fusión elegir al hacer una fusión de notas en refs/notes/<name>. Esto anula la configuración más general notes.mergeStrategy. Véase la sección "ESTRATEGIAS DE FUSIÓN DE NOTAS" en git-notes(1) para más información sobre las estrategias disponibles.

notes.displayRef

Qué referencia (o referencias, si se especifica un patrón glob o más de una vez), además del conjunto por defecto establecido por core.notesRef o GIT_NOTES_REF, leer las notas de al mostrar los mensajes de confirmación con la familia de comandos git log .

Esta configuración puede ser anulada con la variable de entorno GIT_NOTES_DISPLAY_REF , que debe ser una lista de referencias o patrones glob separados por dos puntos.

Se emitirá una advertencia para las referencias que no existan, pero un patrón glob que no coincida con ninguna referencia se ignora silenciosamente.

Esta configuración puede ser deshabilitada con la opción --no-notes de la familia de comandos git-log(1) , o con la opción --notes=<ref> aceptada por esos comandos.

El valor efectivo de core.notesRef (posiblemente anulado por GIT_NOTES_REF) también se añade implícitamente a la lista de referencias a mostrar.

notes.rewrite.<command>

Al reescribir confirmaciones con <command> (actualmente amend o rebase), si esta variable es false, git no copiará las notas de la confirmación original a la reescrita. Por defecto es true. Véase también notes.rewriteRef más abajo.

Esta configuración puede ser anulada con la variable de entorno GIT_NOTES_REWRITE_REF , que debe ser una lista de referencias o patrones glob separados por dos puntos.

notes.rewriteMode

Al copiar notas durante una reescritura (véase la opción notes.rewrite.<command> ), determina qué hacer si la confirmación de destino ya tiene una nota. Debe ser una de overwrite, concatenate, cat_sort_uniq, o ignore. Por defecto es concatenate.

Esta configuración puede ser anulada con la variable de entorno GIT_NOTES_REWRITE_MODE .

notes.rewriteRef

Al copiar notas durante una reescritura, especifica la referencia (totalmente calificada) cuyas notas deben ser copiadas. Puede ser un patrón glob, en cuyo caso se copiarán las notas en todas las referencias que coincidan. También puede especificar esta configuración varias veces.

No tiene un valor por defecto; debe configurar esta variable para habilitar la reescritura de notas. Establézcala en refs/notes/commits para activar la reescritura de las notas de commit predeterminadas.

Puede ser anulado con la variable de entorno GIT_NOTES_REWRITE_REF . Consulte notes.rewrite.<command> arriba para una descripción más detallada de su formato.

ENTORNO

GIT_NOTES_REF

Qué referencia manipular para las notas, en lugar de refs/notes/commits. Esto anula la configuración core.notesRef .

GIT_NOTES_DISPLAY_REF

Lista de referencias o patrones globales delimitados por dos puntos que indican qué referencias, además de la predeterminada de core.notesRef o GIT_NOTES_REF, leer para las notas al mostrar los mensajes de commit. Esto anula la configuración notes.displayRef .

Se emitirá una advertencia para las referencias que no existan, pero un patrón global que no coincida con ninguna referencia será ignorado silenciosamente.

GIT_NOTES_REWRITE_MODE

Al copiar notas durante una reescritura, qué hacer si el commit de destino ya tiene una nota. Debe ser uno de overwrite, concatenate, cat_sort_uniqo ignore. Esto anula la configuración core.rewriteMode .

GIT_NOTES_REWRITE_REF

Al reescribir commits, qué notas copiar del commit original al commit reescrito. Debe ser una lista de referencias o patrones globales delimitados por dos puntos.

Si no está definida en el entorno, la lista de notas a copiar depende de la configuración notes.rewrite.<command> y notes.rewriteRef .
