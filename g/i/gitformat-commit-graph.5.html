GITFORMAT-COMMIT-GRAPH(5) Manual de Git GITFORMAT-COMMIT-GRAPH(5)

NOMBRE

gitformat-commit-graph - formato del grafo de commits de Git

SINOPSIS

$GIT_DIR/objects/info/commit-graph
$GIT_DIR/objects/info/commit-graphs/*

DESCRIPCIÓN

El grafo de commits de Git almacena una lista de OIDs de commits y metadatos asociados, incluyendo:

•El número de generación del commit.
•El OID del árbol raíz.
•La fecha del commit.
•Los padres del commit, almacenados mediante referencias posicionales dentro del archivo del grafo.
•El filtro de Bloom del commit que contiene las rutas modificadas entre el commit y su primer padre, si se solicita.

Estas referencias posicionales se almacenan como enteros sin signo de 32 bits correspondientes a la posición del array dentro de la lista de OIDs de commits. Debido a algunas constantes especiales que usamos para rastrear padres, podemos almacenar como máximo (1 << 30) + (1 << 29) + (1 << 28) - 1 (aproximadamente 1.8 mil millones) de commits.

LOS ARCHIVOS DEL GRAFO DE COMMITS TIENEN EL SIGUIENTE FORMATO:

Para permitir extensiones que añadan datos adicionales al grafo, organizamos el cuerpo en "trozos" (chunks) y proporcionamos una tabla de búsqueda binaria al principio del cuerpo. La cabecera incluye ciertos valores, como el número de trozos y el tipo de hash.

Todos los números de varios bytes están en orden de bytes de red.

CABECERA:

Firma de 4 bytes:
    La firma es: {'C', 'G', 'P', 'H'}
Número de versión de 1 byte:
    Actualmente, la única versión válida es 1.
Versión de Hash de 1 byte
    Inferimos la longitud del hash (H) a partir de este valor:
      1 => SHA-1
      2 => SHA-256
    Si el tipo de hash no coincide con el algoritmo de hash del repositorio,
    se debe ignorar el archivo commit-graph y mostrar una advertencia al
    usuario.
Número (C) de "trozos" de 1 byte
Número (B) de grafos base de 1 byte
    Inferimos la longitud (H*B) del trozo de Grafos Base
    a partir de este valor.

TABLA DE BÚSQUEDA DE TROZOS:

(C + 1) * 12 bytes que listan la tabla de contenido de los trozos:
    Los primeros 4 bytes describen el ID del trozo. El valor 0 es una etiqueta
    de terminación. Los otros 8 bytes proporcionan el desplazamiento de
    bytes en el archivo actual para que comience el trozo. (Los trozos están
    ordenados contiguamente en el archivo, por lo que puedes inferir la
    longitud usando la posición del siguiente trozo si es necesario.) Cada
    ID de trozo aparece como máximo una vez.
La TABLA DE BÚSQUEDA DE TROZOS coincide con la tabla de contenido del
formato de archivo basado en trozos, ver linkgit:gitformat-chunk[5]
Los datos restantes en el cuerpo se describen trozo a trozo, y estos
trozos pueden darse en cualquier orden. Los trozos son obligatorios a menos
que se especifique lo contrario.

DATOS DE TROZOS:

Abanico de OIDs (ID: {O, I, D, F}) (256 * 4 bytes) 

La i-ésima entrada, F[i], almacena el número de OIDs con el primer
byte menor o igual a i. Por lo tanto, F[255] almacena el número total
de commits (N).

Búsqueda de OIDs (ID: {O, I, D, L}) (N * H bytes) 

Los OIDs de todos los commits en el grafo, ordenados en orden
ascendente.

Datos del Commit (ID: {C, D, A, T }) (N * (H + 16) bytes)

•Los primeros H bytes son para el OID del árbol raíz.
•Los siguientes 8 bytes son para las posiciones de los dos primeros padres del i-ésimo commit. Almacena el valor 0x70000000 si no hay padre en esa posición. Si hay más de dos padres, el segundo valor tiene su bit más significativo activado y los otros bits almacenan una posición de array en el trozo de Lista de Aristas Extra.
•Los siguientes 8 bytes almacenan el nivel topológico (número de generación v1) del commit y la hora del commit en segundos desde EPOCH. El número de generación utiliza los 30 bits superiores de los primeros 4 bytes, mientras que la hora del commit utiliza los 32 bits de los segundos 4 bytes, junto con los 2 bits inferiores del byte más bajo, almacenando el bit 33 y 34 de la hora del commit.

Datos de Generación (ID: {G, D, A, 2 }) (N * 4 bytes) [Opcional]

•Esta lista de valores de 4 bytes almacena los desplazamientos de fecha de commit corregidos para los commits, ordenados de la misma manera que el trozo de datos del commit.
•Si el desplazamiento de fecha de commit corregido no se puede almacenar dentro de 31 bits, el valor tiene su bit más significativo activado y los otros bits almacenan la posición del desplazamiento de fecha de commit corregido en el trozo de Desbordamiento de Datos de Generación.
•El trozo de Datos de Generación solo está presente cuando el archivo commit-graph es escrito por versiones compatibles de Git y, en caso de cadenas de grafos de commits divididas, la capa superior también tiene el trozo de Datos de Generación.

Desbordamiento de Datos de Generación (ID: {G, D, O, 2 }) [Opcional]

•Esta lista de valores de 8 bytes almacena los desplazamientos de fecha de commit corregidos para los commits cuyos desplazamientos de fecha de commit corregidos no se pueden almacenar dentro de 31 bits.
•El trozo de Desbordamiento de Datos de Generación solo está presente cuando el trozo de Datos de Generación está presente y al menos un desplazamiento de fecha de commit corregido no se puede almacenar dentro de 31 bits.

Lista de Aristas Extra (ID: {E, D, G, E}) [Opcional] 

Esta lista de valores de 4 bytes almacena el segundo hasta el n-ésimo
padre para todas las fusiones de pulpo (octopus merges). El valor del
segundo padre en los datos del commit almacena una posición de array dentro
de esta lista junto con el bit más significativo activado. Comenzando en
esa posición de array, itera a través de esta lista de posiciones de commit
para los padres hasta llegar a un valor con el bit más significativo
activado. Los otros bits corresponden a la posición del último padre.

Índice del Filtro de Bloom (ID: {B, I, D, X}) (N * 4 bytes) [Opcional]

•La i-ésima entrada, BIDX[i], almacena el número de bytes en todos los filtros de Bloom desde el commit 0 hasta el commit i (inclusive) en orden lexicográfico. El filtro de Bloom para el i-ésimo commit abarca desde BIDX[i-1] hasta BIDX[i] (más la longitud de la cabecera), donde BIDX[-1] es 0.
•El trozo BIDX se ignora si el trozo BDAT no está presente.

Datos del Filtro de Bloom (ID: {B, D, A, T}) [Opcional]

•Comienza con una cabecera que consta de tres enteros sin signo de 32 bits:
•La versión del algoritmo de hash que se está utilizando. Actualmente admitimos el valor 2, que corresponde a la versión de 32 bits del hash murmur3 implementado exactamente como se describe en https://en.wikipedia.org/wiki/MurmurHash#Algorithm y la técnica de doble hash utilizando las semillas 0x293ae76f y 0x7e646e2 como se describe en https://doi.org/10.1007/978-3-540-30494-4_26 "Bloom Filters in Probabilistic Verification". Los filtros de Bloom de versión 1 tienen un error que aparece cuando char es con signo y el repositorio tiene nombres de ruta que tienen caracteres >= 0x80; Git admite leerlos y escribirlos, pero esta capacidad se eliminará en una futura versión de Git.
•El número de veces que se hashea una ruta y, por lo tanto, el número de posiciones de bits que determinan acumulativamente si un archivo está presente en el commit.
•El número mínimo de bits b por entrada en el filtro de Bloom. Si el filtro contiene n entradas, entonces el tamaño del filtro es el número mínimo de palabras de 64 bits que contienen n*b bits.
•El resto del trozo es la concatenación de todos los filtros de Bloom calculados para los commits en orden lexicográfico.
•Nota: Los commits sin cambios o con más de 512 cambios tienen filtros de Bloom de longitud uno, con todos los bits establecidos en cero o uno respectivamente.
•El trozo BDAT está presente si y solo si BIDX está presente.

HISTÓRICAS:

iar los identificadores, las versiones más nuevas de Git ignorarán silenciosamente esos fr
agmentos antiguos y escribirán la nueva información sin confiar en los datos incorrectos.
