NOMBRE

gitprotocol-http - Protocolos basados en HTTP de Git

SINOPSIS

<protocolo_sobre_la_red>

DESCRIPCIÓN

Git soporta dos protocolos de transferencia basados en HTTP. Un protocolo "tonto" que solo requiere un servidor HTTP estándar en el extremo servidor de la conexión, y un protocolo "inteligente" que requiere un CGI (o módulo de servidor) que entienda Git. Este documento describe ambos protocolos.

Como característica de diseño, los clientes inteligentes pueden mejorar automáticamente las URL del protocolo "tonto" a URL inteligentes. Esto permite que todos los usuarios tengan la misma URL publicada, y los pares seleccionan automáticamente el transporte más eficiente disponible para ellos.

FORMATO DE URL

Las URL para repositorios de Git accedidos por HTTP utilizan la sintaxis estándar de URL HTTP documentada por RFC 1738, por lo que tienen la forma:

http://<host>:<puerto>/<ruta>?<parte_de_búsqueda>

Dentro de esta documentación, el marcador de posición $GIT_URL representará la URL del repositorio http:// introducida por el usuario final.

Los servidores DEBERÍAN manejar todas las solicitudes a ubicaciones que coincidan con $GIT_URL, ya que tanto los protocolos HTTP "inteligente" como "tonto" utilizados por Git operan añadiendo componentes de ruta adicionales al final de la cadena $GIT_URL suministrada por el usuario.

Un ejemplo de un cliente tonto solicitando un objeto suelto:

$GIT_URL:     http://example.com:8080/git/repo.git
Solicitud URL:  http://example.com:8080/git/repo.git/objects/d0/49f6c27a2244e12041955e262a404c7faba355

Un ejemplo de una solicitud inteligente a una puerta de enlace que lo captura todo:

$GIT_URL:     http://example.com/daemon.cgi?svc=git&q=
Solicitud URL:  http://example.com/daemon.cgi?svc=git&q=/info/refs&service=git-receive-pack

Un ejemplo de una solicitud a un submódulo:

$GIT_URL:     http://example.com/git/repo.git/path/submodule.git
Solicitud URL:  http://example.com/git/repo.git/path/submodule.git/info/refs

Los clientes DEBEN eliminar una barra inclinada final (/), si está presente, de la cadena $GIT_URL suministrada por el usuario para evitar que aparezcan tokens de ruta vacíos (//) en cualquier URL enviada a un servidor. Los clientes compatibles DEBEN expandir $GIT_URL/info/refs como foo/info/refs y no como foo//info/refs.

AUTENTICACIÓN

Se utiliza la autenticación HTTP estándar si se requiere autenticación para acceder a un repositorio, y PUEDE ser configurada y forzada por el software del servidor HTTP.

Debido a que los repositorios de Git son accedidos por componentes de ruta estándar, los administradores de servidores PUEDEN usar permisos basados en directorios dentro de su servidor HTTP para controlar el acceso al repositorio.

Los clientes DEBERÍAN admitir la autenticación Básica según lo descrito por RFC 2617. Los servidores DEBERÍAN admitir la autenticación Básica confiando en el servidor HTTP ubicado frente al software del servidor de Git.

Los servidores NO DEBERÍAN requerir cookies HTTP para fines de autenticación o control de acceso.

Los clientes y servidores PUEDEN admitir otras formas comunes de autenticación basada en HTTP, como la autenticación Digest.

SSL

Los clientes y servidores DEBERÍAN admitir SSL, particularmente para proteger contraseñas al confiar en la autenticación HTTP Básica.

ESTADO DE SESIÓN

El protocolo Git sobre HTTP (muy parecido a HTTP en sí) es sin estado desde la perspectiva del lado del servidor HTTP. Todo el estado DEBE ser retenido y gestionado por el proceso cliente. Esto permite un balanceo de carga simple de round-robin en el lado del servidor, sin necesidad de preocuparse por la gestión del estado.

Los clientes NO DEBEN requerir gestión de estado en el lado del servidor para funcionar correctamente.

Los servidores NO DEBEN requerir cookies HTTP para funcionar correctamente. Los clientes PUEDEN almacenar y reenviar cookies HTTP durante el procesamiento de solicitudes según lo descrito por RFC 2616 (HTTP/1.1). Los servidores DEBERÍAN ignorar cualquier cookie enviada por un cliente.

PROCESAMIENTO GENERAL DE SOLICITUDES

Excepto donde se indique, se debe asumir todo el comportamiento estándar de HTTP tanto por el cliente como por el servidor. Esto incluye (pero no se limita a):

Si no hay un repositorio en $GIT_URL, o el recurso al que apunta una ubicación que coincide con $GIT_URL no existe, el servidor NO DEBE responder con una respuesta 200 OK. Un servidor DEBERÍA responder con 404 Not Found, 410 Gone, o cualquier otro código de estado HTTP adecuado que no implique que el recurso existe como se solicitó.

Si hay un repositorio en $GIT_URL, pero el acceso no está actualmente permitido, el servidor DEBE responder con el código de estado HTTP 403 Forbidden.

Los servidores DEBERÍAN admitir tanto HTTP 1.0 como HTTP 1.1. Los servidores DEBERÍAN admitir codificación por fragmentos para cuerpos de solicitud y respuesta.

Los clientes DEBERÍAN admitir tanto HTTP 1.0 como HTTP 1.1. Los clientes DEBERÍAN admitir codificación por fragmentos para cuerpos de solicitud y respuesta.

Los servidores PUEDEN devolver encabezados ETag y/o Last-Modified.

Los clientes PUEDEN revalidar entidades cacheadas incluyendo encabezados de solicitud If-Modified-Since y/o If-None-Match.

Los servidores PUEDEN devolver 304 Not Modified si los encabezados relevantes aparecen en la solicitud y la entidad no ha cambiado. Los clientes DEBEN tratar 304 Not Modified idéntico a 200 OK reutilizando la entidad cacheada.

Los clientes PUEDEN reutilizar una entidad cacheada sin revalidación si los encabezados Cache-Control y/o Expires lo permiten. Los clientes y servidores DEBEN seguir RFC 2616 para controles de caché.

DESCUBRIMIENTO DE REFERENCIAS

Todos los clientes HTTP DEBEN comenzar un intercambio de `fetch` o `push` descubriendo las referencias disponibles en el repositorio remoto.

Clientes Tontos

Los clientes HTTP que solo admiten el protocolo "tonto" DEBEN descubrir las referencias realizando una solicitud del archivo especial info/refs del repositorio.

Los clientes HTTP tontos DEBEN realizar una solicitud GET a $GIT_URL/info/refs, sin ningún parámetro de búsqueda/consulta.

C: GET $GIT_URL/info/refs HTTP/1.0
S: 200 OK
S:
S: 95dcfa3633004da0049d3d0fa03f80589cbcaf31  refs/heads/maint
S: d049f6c27a2244e12041955e262a404c7faba355  refs/heads/master
S: 2cb58b79488a98d2721cea644875a8dd0026b115  refs/tags/v1.0
S: a3c2e2402b99163d1d59756e5f207ae21cccba4c  refs/tags/v1.0^{}

El Content-Type de la entidad info/refs devuelta DEBERÍA ser text/plain; charset=utf-8, pero PUEDE ser cualquier tipo de contenido. Los clientes NO DEBEN intentar validar el Content-Type devuelto. Los servidores tontos NO DEBEN devolver un tipo de respuesta que comience con application/x-git-.

Se PUEDEN devolver encabezados Cache-Control para deshabilitar el almacenamiento en caché de la entidad devuelta.

Al examinar la respuesta, los clientes DEBERÍAN examinar solo el código de estado HTTP. Las respuestas válidas son 200 OK o 304 Not Modified.

El contenido devuelto es un archivo de texto formateado en UNIX que describe cada ref y su valor conocido. El archivo DEBERÍA estar ordenado por nombre según el orden de ubicación C. El archivo NO DEBERÍA incluir la ref predeterminada llamada HEAD.

info_refs   =  *( ref_record )
ref_record  =  any_ref / peeled_ref
any_ref     =  obj-id HTAB refname LF
peeled_ref  =  obj-id HTAB refname LF
               obj-id HTAB refname "^{}" LF

Clientes Inteligentes

Los clientes HTTP que admiten el protocolo "inteligente" (o ambos protocolos, el "inteligente" y el "tonto") DEBEN descubrir las referencias realizando una solicitud parametrizada al archivo info/refs del repositorio.

La solicitud DEBE contener exactamente un parámetro de consulta, service=$nombre_servicio, donde $nombre_servicio DEBE ser el nombre del servicio al que el cliente desea contactar para completar la operación. La solicitud NO DEBE contener parámetros de consulta adicionales.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

indent"> 
C: GET $GIT_URL/info/refs?service=git-upload-pack HTTP/1.0

respuesta del servidor simple:

S: 200 OK
S:
S: 95dcfa3633004da0049d3d0fa03f80589cbcaf31  refs/heads/maint
S: d049f6c27a2244e12041955e262a404c7faba355  refs/heads/master

respuesta del servidor inteligente:

S: 200 OK
S: Content-Type: application/x-git-upload-pack-advertisement
S: Cache-Control: no-cache
S:
S: 001e# service=git-upload-pack\n
S: 0000
S: 004895dcfa3633004da0049d3d0fa03f80589cbcaf31 refs/heads/maint\0multi_ack\n
S: 003fd049f6c27a2244e12041955e262a404c7faba355 refs/heads/master\n
S: 003c2cb58b79488a98d2721cea644875a8dd0026b115 refs/tags/v1.0\n
S: 003fa3c2e2402b99163d1d59756e5f207ae21cccba4c refs/tags/v1.0^{}\n
S: 0000

El cliente puede enviar Parámetros Adicionales (ver gitprotocol-pack(5)) como una cadena separada por dos puntos en la cabecera Git-Protocol.

Usa la --http-backend-info-refs opción para git-upload-pack(1).

Respuesta del Servidor Simple

Los servidores simples DEBEN responder con el formato de respuesta de servidor simple.

Ver la sección anterior bajo clientes simples para una descripción más detallada de la respuesta del servidor simple.

Respuesta del Servidor Inteligente

Si el servidor no reconoce el nombre del servicio solicitado, o el nombre del servicio solicitado ha sido deshabilitado por el administrador del servidor, el servidor DEBE responder con el 403 Forbidden código de estado HTTP.

De lo contrario, los servidores inteligentes DEBEN responder con el formato de respuesta de servidor inteligente para el nombre del servicio solicitado.

Las cabeceras Cache-Control DEBERÍAN usarse para deshabilitar el almacenamiento en caché de la entidad devuelta.

El Content-Type DEBE ser application/x-$servicename-advertisement. Los clientes DEBERÍAN volver al protocolo simple si se devuelve otro tipo de contenido. Al volver al protocolo simple, los clientes NO DEBERÍAN hacer una solicitud adicional a $GIT_URL/info/refs, sino que DEBERÍAN usar la respuesta que ya tienen en mano. Los clientes NO DEBEN continuar si no soportan el protocolo simple.

Los clientes DEBEN validar que el código de estado sea 200 OK o 304 Not Modified.

Los clientes DEBEN validar que los primeros cinco bytes de la entidad de respuesta coincidan con la expresión regular ^[0-9a-f]{4}#. Si esta prueba falla, los clientes NO DEBEN continuar.

Los clientes DEBEN analizar toda la respuesta como una secuencia de registros pkt-line.

Los clientes DEBEN verificar que el primer pkt-line sea # service=$servicename. Los servidores DEBEN establecer $servicename como el valor del parámetro de solicitud. Los servidores DEBERÍAN incluir un LF al final de esta línea. Los clientes DEBEN ignorar un LF al final de la línea.

Los servidores DEBEN terminar la respuesta con el marcador mágico 0000 de fin de pkt-line.

La respuesta devuelta es un flujo pkt-line que describe cada ref y su valor conocido. El flujo DEBERÍAN estar ordenado por nombre según la ordenación de la configuración regional C. El flujo DEBERÍA incluir la ref por defecto llamada HEAD como la primera ref. El flujo DEBE incluir declaraciones de capacidades detrás de un NUL en la primera ref.

La respuesta devuelta contiene "version 1" si "version=1" fue enviado como un Parámetro Adicional.

smart_reply     =  PKT-LINE("# service=$servicename" LF)
                   "0000"
                   *1("version 1")
                   ref_list
                   "0000"
ref_list        =  empty_list / non_empty_list
empty_list      =  PKT-LINE(zero-id SP "capabilities^{}" NUL cap-list LF)
non_empty_list  =  PKT-LINE(obj-id SP name NUL cap_list LF)
                   *ref_record
cap-list        =  capability *(SP capability)
capability      =  1*(LC_ALPHA / DIGIT / "-" / "_")
LC_ALPHA        =  %x61-7A
ref_record      =  any_ref / peeled_ref
any_ref         =  PKT-LINE(obj-id SP name LF)
peeled_ref      =  PKT-LINE(obj-id SP name LF)
                   PKT-LINE(obj-id SP name "^{}" LF

SERVICIO INTELIGENTE GIT-UPLOAD-PACK

Este servicio lee del repositorio apuntado por $GIT_URL.

Los clientes DEBEN primero realizar el descubrimiento de refs con $GIT_URL/info/refs?service=git-upload-pack.

C: POST $GIT_URL/git-upload-pack HTTP/1.0
C: Content-Type: application/x-git-upload-pack-request
C:
C: 0032want 0a53e9ddeaddad63ad106860237bbf53411d11a7\n
C: 0032have 441b40d833fdfa93eb2908e52742248faf0ee993\n
C: 0000
S: 200 OK
S: Content-Type: application/x-git-upload-pack-result
S: Cache-Control: no-cache
S:
S: ....ACK %s, continue
S: ....NAK

Los clientes NO DEBEN reutilizar ni revalidar una respuesta en caché. Los servidores DEBEN incluir cabeceras Cache-Control suficientes para prevenir el almacenamiento en caché de la respuesta.

Los servidores DEBERÍAN soportar todas las capacidades definidas aquí.

Los clientes DEBEN enviar al menos un comando "want" en el cuerpo de la solicitud. Los clientes NO DEBEN referenciar un id en un comando "want" que no apareció en la respuesta obtenida a través del descubrimiento de refs a menos que el servidor anuncie la capacidad allow-tip-sha1-in-want o allow-reachable-sha1-in-want.

compute_request   =  want_list
                     have_list
                     request_end
request_end       =  "0000" / "done"
want_list         =  PKT-LINE(want SP cap_list LF)
                     *(want_pkt)
want_pkt          =  PKT-LINE(want LF)
want              =  "want" SP id
cap_list          =  capability *(SP capability)
have_list         =  *PKT-LINE("have" SP id LF)

El Algoritmo de Negociación

El cálculo para seleccionar el paquete mínimo procede como sigue (C = cliente, S = servidor):

paso de inicialización:

C: Usar el descubrimiento de refs para obtener las refs anunciadas.

C: Colocar cualquier objeto visto en el conjunto advertised.

C: Construir un conjunto vacío, common, para contener los objetos que se determina posteriormente que están en ambos extremos.

C: Construir un conjunto, want, de los objetos de advertised que el cliente quiere obtener, basado en lo que vio durante el descubrimiento de refs.

C: Iniciar una cola, c_pending, ordenada por tiempo de commit (sacando el más nuevo primero). Añadir todas las refs del cliente. Cuando se saca un commit de la cola, sus padres DEBERÍAN insertarse automáticamente de vuelta. Los commits SOLO DEBEN entrar en la cola una vez.

un paso de cálculo:

C: Enviar una solicitud a $GIT_URL/git-upload-pack :

C: 0032want <want-#1>...............................
C: 0032want <want-#2>...............................
....
C: 0032have <common-#1>.............................
C: 0032have <common-#2>.............................
....
C: 0032have <have-#1>...............................
C: 0032have <have-#2>...............................
....
C: 0000

El flujo está organizado en "comandos", con cada comando apareciendo por sí mismo en un pkt-line. Dentro de una línea de comando, el texto que precede al primer espacio es el nombre del comando, y el resto de la línea hasta el primer LF es el valor. Las líneas de comando se terminan con un LF como el último byte del valor del pkt-line.

Los comandos DEBEN aparecer en el siguiente orden, si aparecen en el flujo de solicitud:

•"want"
•"have"

El flujo se termina con un pkt-line de vaciado (0000).

Un comando "want" o "have" individual DEBE tener un nombre de objeto con formato hexadecimal como su valor. Múltiples nombres de objetos DEBEN enviarse enviando múltiples comandos. Los nombres de objetos DEBEN darse usando el formato de objeto negociado a través de la capacidad object-format (SHA-1 por defecto).

La lista have se crea sacando los primeros 32 commits de c_pending. Se pueden proporcionar menos si c_pending se vacía.

Si el cliente ha enviado 256 commits "have" y aún no ha recibido uno de esos de vuelta de s_common, o el cliente ha vaciado c_pending DEBERÍA incluir un comando "done" para hacer saber al servidor que no procederá:

C: 0009done

S: Analizar la solicitud git-upload-pack:

Verificar que todos los objetos en want sean directamente alcanzables desde refs.

El servidor PUEDE retroceder a través del historial o a través del reflog para permitir solicitudes ligeramente obsoletas.

Si no se reciben objetos "want", enviar un error: TODO: Definir error si no se solicitan líneas "want".

Si algún objeto "want" no es alcanzable, enviar un error: TODO: Definir error si se solicita un "want" inválido.

Crear una lista vacía, s_common.

Si se envió "have":

Recorrer los objetos en el orden proporcionado por el cliente.

Para cada objeto, si el servidor tiene el objeto alcanzable desde una ref, añadirlo a s_common. Si un commit se añade a s_common, no añadir ningún ancestro, incluso si también aparecen en have.

S: Enviar la respuesta git-upload-pack:

Si el servidor ha encontrado un conjunto cerrado de objetos para empaquetar o la solicitud termina con "done", responde con el paquete. TODO: Documentar la respuesta basada en paquete

SERVICIO INTELIGENTE GIT-RECEIVE-PACK

Este servicio lee fdel repositorio apuntado por $GIT_URL.

Los clientes DEBEN realizar primero el descubrimiento de referencias con $GIT_URL/info/refs?service=git-receive-pack.

C: POST $GIT_URL/git-receive-pack HTTP/1.0
C: Content-Type: application/x-git-receive-pack-request
C:
C: ....0a53e9ddeaddad63ad106860237bbf53411d11a7 441b40d833fdfa93eb2908e52742248faf0ee993 refs/heads/maint\0 report-status
C: 0000
C: PACK....
S: 200 OK
S: Content-Type: application/x-git-receive-pack-result
S: Cache-Control: no-cache
S:
S: ....

Los clientes NO DEBEN reutilizar ni revalidar una respuesta en caché. Los servidores DEBEN incluir cabeceras Cache-Control suficientes para evitar el almacenamiento en caché de la respuesta.

Los servidores DEBERÍAN soportar todas las capacidades definidas aquí.

Los clientes DEBEN enviar al menos un comando en el cuerpo de la solicitud. Dentro de la sección de comandos del cuerpo de la solicitud, los clientes DEBERÍAN enviar el id obtenido a través del descubrimiento de referencias como old_id.

update_request  =  command_list
                   "PACK" <binary-data>
command_list    =  PKT-LINE(command NUL cap_list LF)
                   *(command_pkt)
command_pkt     =  PKT-LINE(command LF)
cap_list        =  *(SP capability) SP
command         =  create / delete / update
create          =  zero-id SP new_id SP name
delete          =  old_id SP zero-id SP name
update          =  old_id SP new_id SP name
