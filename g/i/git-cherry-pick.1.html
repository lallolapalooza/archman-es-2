GIT-CHERRY-PICK(1) Manual de Git GIT-CHERRY-PICK(1)

NOMBRE

git-cherry-pick - Aplica los cambios introducidos por algunos commits existentes

SINOPSIS

git cherry-pick [--edit] [-n] [-m <número-de-padre>] [-s] [-x] [--ff]
                  [-S[<id-de-clave>]] <commit>...
git cherry-pick (--continue | --skip | --abort | --quit)

DESCRIPCIÓN

Dado uno o más commits existentes, aplica el cambio que cada uno introduce, registrando un nuevo commit por cada uno. Esto requiere que tu árbol de trabajo esté limpio (sin modificaciones desde el commit HEAD).

Cuando no es obvio cómo aplicar un cambio, ocurre lo siguiente:

1.La rama actual y el puntero HEAD permanecen en el último commit realizado con éxito.
2.La referencia CHERRY_PICK_HEAD se establece para apuntar al commit que introdujo el cambio que es difícil de aplicar.
3.Las rutas en las que el cambio se aplicó limpiamente se actualizan tanto en el archivo de índice como en tu árbol de trabajo.
4.Para las rutas en conflicto, el archivo de índice registra hasta tres versiones, como se describe en la sección "FUSIÓN VERDADERA" de git-merge(1). Los archivos del árbol de trabajo incluirán una descripción del conflicto delimitada por los marcadores de conflicto habituales <<<<<<<< y >>>>>>>.
5.No se realizan otras modificaciones.

Consulta git-merge(1) para obtener algunas pistas sobre cómo resolver tales conflictos.

OPCIONES

<commit>...

Commits a cherry-pick. Para una lista más completa de formas de escribir commits, consulta gitrevisions(7). Se pueden pasar conjuntos de commits, pero no se realiza ninguna traversión de forma predeterminada, como si se hubiera especificado la opción --no-walk , consulta git-rev-list(1). Ten en cuenta que especificar un rango pasará todos los argumentos <commit>... a un solo recorrido de revisiones (consulta un ejemplo posterior que usa maint master..next).

-e, --edit

Con esta opción, git cherry-pick te permitirá editar el mensaje del commit antes de hacer el commit.

--cleanup=<modo>

Esta opción determina cómo se limpiará el mensaje del commit antes de pasarlo al mecanismo de commits. Consulta git-commit(1) para más detalles. En particular, si el <modo> tiene el valor scissors, se añadirá "scissors" al final de MERGE_MSG antes de pasarlo en el caso de un conflicto.

-x

Al registrar el commit, añade una línea que dice "(cherry picked from commit ...)" al mensaje del commit original para indicar desde qué commit se hizo cherry-pick de este cambio. Esto se hace solo para cherry picks sin conflictos. No uses esta opción si estás haciendo cherry-pick desde tu rama privada porque la información es inútil para el destinatario. Si por otro lado estás haciendo cherry-pick entre dos ramas visibles públicamente (por ejemplo, trasladando una corrección a una rama de mantenimiento para una versión antigua desde una rama de desarrollo), añadir esta información puede ser útil.

-r

Antes, el comando hacía por defecto lo que hace -x descrito arriba, y -r servía para desactivarlo. Ahora el comportamiento predeterminado es no hacer -x , así que esta opción no tiene efecto.

-m <número-de-padre>, --mainline <número-de-padre>

Normalmente no puedes hacer cherry-pick de una fusión (merge) porque no sabes qué lado de la fusión debe considerarse la línea principal. Esta opción especifica el número de padre (empezando desde 1) de la línea principal y permite a cherry-pick reproducir el cambio relativo al padre especificado.

-n, --no-commit

Normalmente el comando crea automáticamente una secuencia de commits. Esta bandera aplica los cambios necesarios para hacer cherry-pick de cada commit nombrado a tu árbol de trabajo y al índice, sin hacer ningún commit. Además, cuando se usa esta opción, tu índice no tiene que coincidir con el commit HEAD. El cherry-pick se realiza contra el estado inicial de tu índice.

Esto es útil cuando se hace cherry-pick del efecto de más de un commit a tu índice de forma consecutiva.

-s, --signoff

Añade un rótulo Signed-off-by al final del mensaje del commit. Consulta la opción signoff en git-commit(1) para más información.

-S[<id-de-clave>], --gpg-sign[=<id-de-clave>], --no-gpg-sign

Firma los commits con GPG. El argumento id-de-clave es opcional y por defecto es la identidad del committer; si se especifica, debe pegarse a la opción sin espacio. --no-gpg-sign es útil para contrarrestar tanto la variable de configuración commit.gpgSign como una --gpg-signanterior.

--ff

Si el HEAD actual es el mismo que el padre del commit al que se le hace cherry-pick, se realizará un avance rápido (fast forward) a este commit.

--allow-empty

Por defecto, hacer cherry-pick de un commit vacío fallará, indicando que se requiere una invocación explícita de git commit --allow-empty . Esta opción anula ese comportamiento, permitiendo que los commits vacíos se conserven automáticamente en un cherry-pick. Ten en cuenta que cuando "--ff" está en vigor, los commits vacíos que cumplen el requisito de "avance rápido" se conservarán incluso sin esta opción. Ten en cuenta también que el uso de esta opción solo conserva los commits que estaban inicialmente vacíos (es decir, el commit registraba el mismo árbol que su padre). Los commits que se vuelven vacíos debido a un commit anterior harán fallar el cherry-pick. Para forzar la inclusión de esos commits, usa --empty=keep.

--allow-empty-message

Por defecto, hacer cherry-pick de un commit con un mensaje vacío fallará. Esta opción anula ese comportamiento, permitiendo hacer cherry-pick de commits con mensajes vacíos.

--empty=(drop|keep|stop)

Cómo manejar los commits que se están haciendo cherry-pick y que son redundantes con los cambios ya presentes en el historial actual.

drop

El commit será descartado.

keep

El commit será conservado. Implica --allow-empty.

stop

El cherry-pick se detendrá cuando el commit se aplique, permitiéndote examinar el commit. Este es el comportamiento predeterminado.

Ten en cuenta que --empty=drop y --empty=stop solo especifican cómo manejar un commit que no estaba inicialmente vacío, sino que se volvió vacío debido a un commit anterior. Los commits que estaban inicialmente vacíos seguirán haciendo fallar el cherry-pick a menos que se especifique --empty=keep o --allow-empty .

--keep-redundant-commits

Sinónimo obsoleto de --empty=keep.

--strategy=<estrategia>

Usa la estrategia de fusión (merge) dada. Solo debe usarse una vez. Consulta la sección ESTRATEGIAS DE FUSIÓN en git-merge(1) para detalles.

-X<opción>, --strategy-option=<opción>

Pasa la opción específica de la estrategia de fusión a la estrategia de fusión. Consulta git-merge(1) para detalles.

--rerere-autoupdate, --no-rerere-autoupdate

Después de que el mecanismo rerere reutilice una resolución registrada en el conflicto actual para actualizar los archivos en el árbol de trabajo, permítele también actualizar el índice con el resultado de la resolución. --no-rerere-autoupdate es una buena manera de verificar lo que rerere hizo y detectar posibles fusiones incorrectas, antes de confirmar el resultado en el índice con un git addseparado.

SUBCOMANDOS DEL SECUENCIADOR

--continue

Continúa la operación en progreso usando la información en .git/sequencer. Se puede usar para continuar después de resolver conflictos en un cherry-pick o revert fallido.

--skip

Omite el commit actual y continúa con el resto de la secuencia.

--quit

Olvida la operación en progreso actual. Se puede usar para limpiar el estado del secuenciador después de un cherry-pick o revert fallido.

--abort

Cancela la operación y vuelve al estado anterior a la secuencia.

EJEMPLOS

git cherry-pick master

Aplica el cambio introducido por el commit en la punta de la rama master y crea un nuevo commit con este cambio.

git cherry-pick ..master, git cherry-pick ^HEAD master

Aplica los cambios introducidos por todos los commits que son ancestros de master pero no de HEAD para producir nuevos commits.

git cherry-pick maint next ^master, git cherry-pick maint master..next

Aplica los cambios introducidos por todos los commits que son ancestros de maint o next, pero no de master ni de ninguno de sus ancestros. Ten en cuenta que esto último no significa maint y todo lo que hay entre master y next; específicamente, maint no se usará si está incluido en master.

git cherry-pick master~4 master~2

Aplica los cambios introducidos por el quinto y el tercer último commit apuntados por master y crea 2 nuevos commits con estos cambios.

git cherry-pick -n master~1 next

Aplica al árbol de trabajo y al índice los cambios introducidos por el segundo último commit apuntado por master y por el último commit apuntado por next, pero no crea ningún commit con estos cambios.

git cherry-pick --ff ..next

Si el historial es lineal y HEAD es un ancestro de next, actualiza el árbol de trabajo y avanza el puntero HEAD para que coincida con next. De lo contrario, aplica los cambios introducidos por esos commits que están en next pero no en HEAD a la rama actual, creando un nuevo commit para cada nuevo cambio.

git rev-list --reverse master -- README | git cherry-pick -n --stdin

Aplica los cambios introducidos por todos los commits en la rama master que tocaron README al árbol de trabajo y al índice, de modo que el resultado pueda ser inspeccionado y convertido en un único nuevo commit si es adecuado.

La siguiente secuencia intenta aplicar un parche de forma retroactiva, se detiene porque el código al que se aplica el parche ha cambiado demasiado, y luego lo intenta de nuevo, esta vez con más cuidado para hacer coincidir las líneas de contexto.

$ git cherry-pick topic^             (1)
$ git diff                           (2)
$ git cherry-pick --abort            (3)
$ git cherry-pick -Xpatience topic^  (4)
1. aplica el cambio que sería mostrado por git show topic^. En este ejemplo, el parche no se aplica limpiamente, así que se escribe información sobre el conflicto en el índice y el árbol de trabajo y no resulta ningún commit nuevo.
2. resume los cambios a reconciliar
3. cancela el cherry-pick. En otras palabras, vuelve al estado previo al cherry-pick, preservando cualquier modificación local que tuvieras en el árbol de trabajo.
4. intenta aplicar el cambio introducido por topic^ de nuevo, dedicando tiempo extra para evitar errores basados en la coincidencia incorrecta de líneas de contexto.
