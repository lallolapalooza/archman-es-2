NOMBRE

git-diff - Muestra cambios entre commits, commit y árbol de trabajo, etc

SINOPSIS

git diff [<opciones>] [<commit>] [--] [<ruta>...]
git diff [<opciones>] --cached [--merge-base] [<commit>] [--] [<ruta>...]
git diff [<opciones>] [--merge-base] <commit> [<commit>...] <commit> [--] [<ruta>...]
git diff [<opciones>] <commit>...<commit> [--] [<ruta>...]
git diff [<opciones>] <blob> <blob>
git diff [<opciones>] --no-index [--] <ruta> <ruta> [<ruta-especificación>...]

DESCRIPCIÓN

Muestra los cambios entre el árbol de trabajo y el índice o un árbol, cambios entre el índice y un árbol, cambios entre dos árboles, cambios resultantes de una fusión, cambios entre dos objetos blob, o cambios entre dos archivos en disco.

git diff [<opciones>] [--] [<ruta>...]

Esta forma es para ver los cambios que has realizado en relación con el índice (área de preparación para el próximo commit). En otras palabras, las diferencias son lo que podrías decirle a Git que agregue al índice pero aún no lo has hecho. Puedes preparar estos cambios usando git-add(1).

git diff [<opciones>] --no-index [--] <ruta> <ruta> [<ruta-especificación>...]

Esta forma es para comparar las dos rutas dadas en el sistema de archivos. Puedes omitir la opción --no-index cuando ejecutas el comando en un árbol de trabajo controlado por Git y al menos una de las rutas apunta fuera del árbol de trabajo, o cuando ejecutas el comando fuera de un árbol de trabajo controlado por Git. Esta forma implica --exit-code. Si ambas rutas apuntan a directorios, se pueden proporcionar rutas adicionales. Estas limitarán los archivos incluidos en la diferencia. Todas estas rutas especificadas deben ser relativas ya que se aplican a ambos lados de la diferencia.

git diff [<opciones>] --cached [--merge-base] [<commit>] [--] [<ruta>...]

Esta forma es para ver los cambios que has preparado para el próximo commit en relación con el <commit> nombrado. Típicamente querrás una comparación con el último commit, así que si no das <commit>, por defecto será HEAD. Si HEAD no existe (por ejemplo, ramas no nacidas) y no se proporciona <commit>, muestra todos los cambios preparados. --staged es un sinónimo de --cached.

Si se da --merge-base, en lugar de usar <commit>, usa la base de fusión de <commit> y HEAD. git diff --cached --merge-base A es equivalente a git diff --cached $(git merge-base A HEAD).

git diff [<opciones>] [--merge-base] <commit> [--] [<ruta>...]

Esta forma es para ver los cambios que tienes en tu árbol de trabajo en relación con el <commit> nombrado. Puedes usar HEAD para compararlo con el último commit, o un nombre de rama para comparar con la punta de una rama diferente.

Si se da --merge-base, en lugar de usar <commit>, usa la base de fusión de <commit> y HEAD. git diff --merge-base A es equivalente a git diff $(git merge-base A HEAD).

git diff [<opciones>] [--merge-base] <commit> <commit> [--] [<ruta>...]

Esto es para ver los cambios entre dos <commit> arbitrarios.

Si se da --merge-base, usa la base de fusión de los dos commits para el lado "antes". git diff --merge-base A B es equivalente a git diff $(git merge-base A B) B.

git diff [<opciones>] <commit> <commit>...<commit> [--] [<ruta>...]

Esta forma es para ver los resultados de un commit de fusión. El primer <commit> listado debe ser la fusión en sí; los siguientes dos o más commits deben ser sus padres. Formas convenientes de producir el conjunto deseado de revisiones son usar los sufijos @ y ^!. Si A es un commit de fusión, entonces git diff A A^@, git diff A^! y git show A dan la misma diferencia combinada.

git diff [<opciones>] <commit>..<commit> [--] [<ruta>...]

Esto es sinónimo de la forma anterior (sin el ..) para ver los cambios entre dos <commit> arbitrarios. Si se omite <commit> en un lado, tendrá el mismo efecto que usar HEAD.

git diff [<opciones>] <commit>...<commit> [--] [<ruta>...]

Esta forma es para ver los cambios en la rama que contiene y hasta el segundo <commit>, comenzando en un ancestro común de ambos <commit>. git diff A...B es equivalente a git diff $(git merge-base A B) B. Puedes omitir cualquiera de los <commit>, lo que tendrá el mismo efecto que usar HEAD.

Por si acaso estás haciendo algo exótico, debe notarse que todos los <commit> en la descripción anterior, excepto en el caso de --merge-base y en las dos últimas formas que usan notaciones .. no significan un rango como se define en la sección "ESPECIFICACIÓN DE RANGOS" en gitrevisions(7).

git diff [<opciones>] <blob> <blob>

Esta forma es para ver las diferencias entre los contenidos crudos de dos objetos blob.

OPCIONES

-p, -u, --patch

Generar parche (ver la sección llamada “GENERAR TEXTO DE PARCHE CON -P”). Este es el valor predeterminado.

-s, --no-patch

Suprimir toda salida de la maquinaria de diff. Útil para comandos como git show que muestran el parche por defecto para silenciar su salida, o para cancelar el efecto de opciones como --patch, --stat anteriores en la línea de comandos en un alias.

-U<n>, --unified=<n>

Generar diffs con <n> líneas de contexto en lugar de las tres habituales. Implica --patch.

--output=<archivo>

Salida a un archivo específico en lugar de stdout.

--output-indicator-new=<car>, --output-indicator-old=<car>, --output-indicator-context=<car>

Especificar el carácter utilizado para indicar líneas nuevas, antiguas o de contexto en el parche generado. Normalmente son +, - y ' ' respectivamente.

--raw

Generar la diferencia en formato crudo.

--patch-with-raw

Sinónimo de -p --raw.

--indent-heuristic

Habilitar la heurística que desplaza los límites de los fragmentos de diff para hacer los parches más fáciles de leer. Este es el valor predeterminado.

ault.

--no-indent-heuristic

Desactivar la heurística de indentación.

--minimal

Dedicar tiempo extra para asegurarse de que se produce la menor diferencia posible.

--patience

Generar una diferencia utilizando el algoritmo de "paciencia".

--histogram

Generar una diferencia utilizando el algoritmo de "histograma".

--anchored=<texto>

Generar una diferencia utilizando el algoritmo de "diferencia anclada".

Esta opción puede especificarse varias veces.

Si una línea existe tanto en el origen como en el destino, solo existe una vez y comienza con <texto>, este algoritmo intenta evitar que aparezca como una eliminación o adición en la salida. Utiliza internamente el algoritmo de "diferencia de paciencia".

--diff-algorithm=(patience|minimal|histogram|myers)

Elegir un algoritmo de diferencia. Las variantes son las siguientes:

default, myers

El algoritmo básico de diferencia voraz. Actualmente, este es el predeterminado.

minimal

Dedicar tiempo extra para asegurarse de que se produce la menor diferencia posible.

patience

Utilizar el algoritmo de "diferencia de paciencia" al generar parches.

histogram

Este algoritmo extiende el algoritmo de paciencia para "soportar elementos comunes de baja ocurrencia".

Por ejemplo, si configuraste la variable diff.algorithm a un valor no predeterminado y quieres usar el predeterminado, entonces tienes que usar la opción --diff-algorithm=default.

--stat[=<ancho>[,<ancho-nombre>[,<conteo>]]]

Generar un diffstat. Por defecto, se utilizará todo el espacio necesario para la parte del nombre de archivo y el resto para la parte del gráfico. El ancho máximo tiene como valor predeterminado el ancho de la terminal, o 80 columnas si no está conectada a una terminal, y puede ser anulado por <ancho>. El ancho de la parte del nombre de archivo puede limitarse proporcionando otro ancho <ancho-nombre> después de una coma o estableciendo diff.statNameWidth=<ancho-nombre>. El ancho de la parte del gráfico puede limitarse utilizando --stat-graph-width=<ancho-gráfico> o estableciendo diff.statGraphWidth=<ancho-gráfico>. El uso de --stat o --stat-graph-width afecta a todos los comandos que generan un gráfico de estadísticas, mientras que el establecimiento de diff.statNameWidth o diff.statGraphWidth no afecta a git format-patch. Proporcionando un tercer parámetro <conteo>, puede limitar la salida a las primeras <conteo> líneas, seguidas de ... si hay más.

Estos parámetros también se pueden establecer individualmente con --stat-width=<ancho>, --stat-name-width=<ancho-nombre> y --stat-count=<conteo>.

--compact-summary

Mostrar un resumen condensado de información de cabecera extendida, como creaciones o eliminaciones de archivos ("nuevo" o "gone", opcionalmente +l si es un enlace simbólico) y cambios de modo (+x o -x para añadir o eliminar el bit ejecutable respectivamente) en el diffstat. La información se coloca entre la parte del nombre de archivo y la parte del gráfico. Implica --stat.

--numstat

Similar a --stat, pero muestra el número de líneas añadidas y eliminadas en notación decimal y el nombre de la ruta sin abreviar, para hacerlo más amigable para las máquinas. Para archivos binarios, muestra dos - en lugar de decir 0 0.

--shortstat

Mostrar solo la última línea del formato --stat que contiene el número total de archivos modificados, así como el número de líneas añadidas y eliminadas.

-X [<parametro>,...], --dirstat[=<parametro>,...]

Mostrar la distribución de la cantidad relativa de cambios para cada subdirectorio. El comportamiento de --dirstat se puede personalizar pasándole una lista de parámetros separados por comas. Los valores predeterminados se controlan mediante la variable de configuración diff.dirstat (ver git-config(1)). Las siguientes parámetros están disponibles:

changes

Calcular los números de dirstat contando las líneas que se han eliminado de la fuente o añadido al destino. Esto ignora la cantidad de movimientos de código puros dentro de un archivo. En otras palabras, reorganizar líneas en un archivo no se cuenta tanto como otros cambios. Este es el comportamiento predeterminado cuando no se proporciona ningún parámetro.

lines

Calcular los números de dirstat realizando el análisis regular basado en líneas y sumando los recuentos de líneas eliminadas/añadidas. (Para archivos binarios, se cuentan fragmentos de 64 bytes en su lugar, ya que los archivos binarios no tienen un concepto natural de líneas). Este es un comportamiento de --dirstat más costoso que el comportamiento de changes, pero cuenta las líneas reorganizadas dentro de un archivo tanto como otros cambios. La salida resultante es coherente con lo que se obtiene de las otras opciones de --*stat.

files

Calcular los números de dirstat contando el número de archivos cambiados. Cada archivo cambiado cuenta por igual en el análisis de dirstat. Este es el comportamiento de --dirstat computacionalmente más barato, ya que no tiene que mirar el contenido del archivo en absoluto.

cumulative

Contar los cambios en un subdirectorio también para el directorio padre. Tenga en cuenta que al usar cumulative, la suma de los porcentajes reportados puede exceder el 100%. El comportamiento predeterminado (no acumulativo) se puede especificar con el parámetro noncumulative.

<limite>

Un parámetro entero especifica un porcentaje de corte (3% por defecto). Los directorios que contribuyen menos del porcentaje especificado al total de cambios no se muestran en la salida.

Ejemplo: Lo siguiente contará los archivos cambiados, ignorando los directorios con menos del 10% del total de archivos cambiados, y acumulando los recuentos de subdirectorios en los directorios padres: --dirstat=files,10,cumulative.

--cumulative

Sinónimo de --dirstat=cumulative.

--dirstat-by-file[=<parametro>,...]

Sinónimo de --dirstat=files,<parametro>,....

--summary

Mostrar un resumen condensado de información de cabecera extendida, como creaciones, renombramientos y cambios de modo.

--patch-with-stat

Sinónimo de -p --stat.

-z

Cuando se ha especificado --raw, --numstat, --name-only o --name-status, no se modifican los nombres de archivo y se utilizan NULs como terminadores de campo de salida.

Sin esta opción, los nombres de archivo con caracteres "inusuales" se citan como se explica para la variable de configuración core.quotePath (ver git-config(1)).

--name-only

Mostrar solo el nombre de cada archivo modificado en el árbol de post-imagen. Los nombres de archivo a menudo se codifican en UTF-8. Para obtener más información, consulte la discusión sobre codificación en la página del manual de git-log(1).

--name-status

Mostrar solo el nombre (o nombres) y el estado de cada archivo modificado. Consulte la descripción de la opción --diff-filter para saber qué significan las letras de estado. Al igual que con --name-only, los nombres de archivo a menudo se codifican en UTF-8.

--submodule[=<formato>]

Especificar cómo se muestran las diferencias en los submodules. Al especificar --submodule=short se utiliza el formato short. Este formato solo muestra los nombres de los commits al principio y al final del rango. Cuando se especifica --submodule o --submodule=log, se utiliza el formato log. Este formato enumera los commits en el rango como lo hace el resumen de git-submodule(1). Cuando se especifica --submodule=diff, se utiliza el formato diff. Este formato muestra una diferencia en línea de los cambios en el contenido del submodule entre el rango de commits. El valor predeterminado es diff.submodule o el formato short si la opción de configuración no está establecida.

--color[=<cuándo>]

Mostrar diferencia con color. --color (es decir, sin =<cuándo>) es lo mismo que --color=always. <cuándo> puede ser uno de always, never o auto. Puede cambiarse mediante la configuración de los ajustes color.ui y color.diff.

--no-color

Desactivar la diferencia con color. Esto se puede utilizar para anular la configuración. Es lo mismo que --color=never.

--color-moved[=<modo>]

Las líneas de código movidas se colorean de forma diferente. Puede cambiarse mediante la configuración de diff.colorMoved. El <modo> tiene como valor predeterminado no si no se proporciona la opción y zebra si se proporciona la opción sin modo. El modo debe ser uno de los siguientes:

no

Las líneas movidas no se resaltan.

default

Es un sinónimo de zebra. Esto puede cambiar a un modo más sensato en el futuro.

plain

Cualquier línea que se añade en una ubicación y se eliminó en otra ubicación se coloreará con color.diff.newMoved. De manera similar, se utilizará color.diff.oldMoved para las líneas eliminadas que se añaden en otro lugar de la diferencia. Este modo detecta cualquier línea movida, pero no es muy útil en una revisión para determinar si un bloque de código se movió sin permutación.

blocks

Los bloques de texto movido de al menos 20 caracteres alfanuméricos se detectan de forma voraz. Los bloques detectados se pintan utilizando el color color.diff.(old|new)Moved. No se pueden distinguir bloques adyacentes.

zebra

Los bloques de texto movido se detectan como en el modo blocks. Los bloques se pintan utilizando el color color.diff.(old|new)Moved o color.diff.(old|new)MovedAlternative. El cambio entre los dos colores indica que se ha detectado un nuevo bloque.

dimmed-zebra

Similar a zebra, pero se realiza un atenuado adicional de partes no interesantes del código movido. Las líneas límite de dos bloques adyacentes se consideran interesantes, el resto no. dimmed_zebra es un sinónimo obsoleto.

-S<cadena>

Busca diferencias que cambien el número de ocurrencias de la <cadena> especificada (es decir, adición/eliminación) en un archivo. Diseñado para el uso del script.

Es útil cuando buscas un bloque de código exacto (como una estructura), y quieres conocer el historial de ese bloque desde que nació: usa la función iterativamente para alimentar el bloque interesante en la preimage de vuelta a -S, y sigue hasta que obtengas la primerísima versión del bloque.

Los archivos binarios también se buscan.

-G<expresionregular>

Busca diferencias cuyo texto del parche contenga líneas añadidas/eliminadas que coincidan con la <expresionregular>.

Para ilustrar la diferencia entre -S<expresionregular> --pickaxe-regex y -G<expresionregular>, considera un commit con el siguiente diff en el mismo archivo:

+    return frotz(nitfol, two->ptr, 1, 0);
...
-    hit = frotz(nitfol, mf2.ptr, 1, 0);

Mientras que git log -G"frotz\(nitfol" mostrará este commit, git log -S"frotz\(nitfol" --pickaxe-regex no lo hará (porque el número de ocurrencias de esa cadena no cambió).

A menos que se proporcione --text, los parches de archivos binarios sin un filtro de textconv serán ignorados.

Consulta la entrada pickaxe en gitdiffcore(7) para más información.

--find-object=<idobjeto>

Busca diferencias que cambien el número de ocurrencias del objeto especificado. Similar a -S, solo que el argumento es diferente en que no busca una cadena específica sino un ID de objeto específico.

El objeto puede ser un blob o un commit de submódulo. Implica la opción -t en git-log para también encontrar árboles.

--pickaxe-all

Cuando -S o -G encuentran un cambio, muestra todos los cambios en ese conjunto de cambios, no solo los archivos que contienen el cambio en <cadena>.

--pickaxe-regex

Trata la <cadena> dada a -S como una expresión regular POSIX extendida para coincidir.

-O<archivoorden>

Controla el orden en que aparecen los archivos en la salida. Esto anula la variable de configuración diff.orderFile (ver git-config(1)). Para cancelar diff.orderFile, usa -O/dev/null.

El orden de salida está determinado por el orden de los patrones glob en <archivoorden>. Todos los archivos con rutas que coinciden con el primer patrón se muestran primero, todos los archivos con rutas que coinciden con el segundo patrón (pero no el primero) se muestran a continuación, y así sucesivamente. Todos los archivos con rutas que no coinciden con ningún patrón se muestran al final, como si hubiera un patrón implícito de coincidencia universal al final del archivo. Si varias rutas tienen el mismo rango (coinciden con el mismo patrón pero no con patrones anteriores), su orden de salida relativo entre sí es el orden normal.

<archivoorden> se analiza de la siguiente manera:

•Las líneas en blanco se ignoran, por lo que se pueden usar como separadores para legibilidad.
•Las líneas que comienzan con una almohadilla ("#") se ignoran, por lo que se pueden usar para comentarios. Agrega una barra invertida ("\") al principio del patrón si comienza con una almohadilla.
•Cada otra línea contiene un solo patrón.

Los patrones tienen la misma sintaxis y semántica que los patrones utilizados para fnmatch(3) sin el flag FNM_PATHNAME, excepto que una ruta también coincide con un patrón si eliminar cualquier número de los componentes finales de la ruta coincide con el patrón. Por ejemplo, el patrón "foo*bar" coincide con "fooasdfbar" y "foo/bar/baz/asdf" pero no con "foobarx".

Cualquier comando que genere diffs puede usar la opción -c o --cc para producir un diff combinado al mostrar una fusión. Este es el formato predeterminado al mostrar fusiones con git-diff(1) o git-show(1). Tenga en cuenta que también puede dar la opción adecuada --diff-merges a cualquiera de estos comandos para forzar la generación de diffs en un formato específico.

2.Está seguido por una o más líneas de cabecera extendida (este ejemplo muestra una fusión con dos padres):

La línea mode <mode>,<mode>..<mode> aparece solo si al menos uno de los <mode> es diferente de los demás. Las cabeceras extendidas con información sobre el movimiento de contenido detectado (renombrados y detección de copias) están diseñadas para funcionar con el diff de dos <tree-ish> y no son utilizadas por el formato de diff combinado.

3.Está seguido por una cabecera de dos líneas de archivo de origen/archivo de destino: 
--- a/file

Similar a la cabecera de dos líneas para el formato de diff unificado tradicional, /dev/null se usa para señalar archivos creados o eliminados.

Sin embargo, si se proporciona la opción --combined-all-paths, en lugar de un archivo de origen/archivo de destino de dos líneas, obtendrá una cabecera de archivo de origen/archivo de destino de N+1 líneas, donde N es el número de padres en la confirmación de fusión:

4.El formato de la cabecera del fragmento se modifica para evitar que la gente lo alimente accidentalmente a patch -p1. El formato de diff combinado se creó para la revisión de los cambios de confirmación de fusión, y no estaba destinado a ser aplicado. El cambio es similar al cambio en la cabecera extendida index: 
@@@ <from-file-range> <from-file-range> <to-file-range> @@@

Hay (número de padres + 1) caracteres @ en la cabecera del fragmento para el formato de diff combinado.

A diferencia del formato de diff unificado tradicional, que muestra dos archivos A y B con una sola columna que tiene un prefijo - (menos — aparece en A pero se elimina en B), + (más — falta en A pero se añade a B), o " " (espacio — sin cambios), este formato compara dos o más archivos file1, file2,... con un archivo X, y muestra cómo X difiere de cada uno de los fileN. Una columna por cada fileN se antepone a la línea de salida para indicar cómo la línea de X difiere de ella.

Un carácter - en la columna N significa que la línea aparece en fileN pero no aparece en el resultado. Un carácter + en la columna N significa que la línea aparece en el resultado, y fileN no tiene esa línea (en otras palabras, la línea se añadió, desde el punto de vista de ese padre).

En la salida del ejemplo anterior, la firma de la función se cambió en ambos archivos (de ahí dos eliminaciones - de ambos file1 y file2, más ++ para indicar que una línea añadida no aparece en ninguno de los file1 o file2). Además, otras ocho líneas son las mismas de file1 pero no aparecen en file2 (de ahí prefijadas con +).

Cuando es mostrado por git diff-tree -c, compara los padres de una confirmación de fusión con el resultado de la fusión (es decir, file1..fileN son los padres). Cuando es mostrado por git diff-files -c, compara los dos padres de fusión sin resolver con el archivo del árbol de trabajo (es decir, file1 es la etapa 2, también conocida como "nuestra versión", file2 es la etapa 3, también conocida como "su versión").

OTROS FORMATOS DE DIFF

La opción --summary describe los archivos recién añadidos, eliminados, renombrados y copiados. La opción --stat añade un gráfico de diffstat(1) a la salida. Estas opciones se pueden combinar con otras opciones, como -p, y están destinadas al consumo humano.

Al mostrar un cambio que involucra un renombrado o una copia, la salida de --stat formatea los nombres de archivo de forma compacta combinando el prefijo y sufijo comunes de los nombres de archivo. Por ejemplo, un cambio que mueve arch/i386/Makefile a arch/x86/Makefile mientras modifica 4 líneas se mostrará así:

arch/{i386 => x86}/Makefile    |   4 +--

La opción --numstat proporciona información de diffstat(1) pero está diseñada para un consumo más fácil por máquinas. Una entrada en la salida de --numstat se ve así:

1       2       README
3       1       arch/{i386 => x86}/Makefile

Es decir, de izquierda a derecha:

1.el número de líneas añadidas;
2.una tabulación;
3.el número de líneas eliminadas;
4.una tabulación;
5.nombre de archivo (posiblemente con información de renombrado/copia);
6.una nueva línea.

Cuando la opción de salida -z está activa, la salida se formatea de esta manera:

1       2       README NUL
3       1       NUL arch/i386/Makefile NUL arch/x86/Makefile NUL

Eso es:

1.el número de líneas añadidas;
2.una tabulación;
3.el número de líneas eliminadas;
4.una tabulación;
5.un NUL (solo existe si se renombró/copió);
6.nombre de archivo en la preimagen;
7.un NUL (solo existe si se renombró/copió);
8.nombre de archivo en la postimagen (solo existe si se renombró/copió);
9.un NUL.

El NUL adicional antes de la ruta de la preimagen en el caso de renombrado es para permitir que los scripts que leen la salida sepan si el registro actual que se está leyendo es un registro de ruta única o un registro de renombrado/copia sin tener que leer por adelantado. Después de leer las líneas añadidas y eliminadas, leer hasta el NUL produciría el nombre de archivo, pero si este es NUL, el registro mostrará dos rutas.

Varias formas de comprobar su árbol de trabajo

$ git diff            (1)
$ git diff --cached   (2)
$ git diff HEAD       (3)
$ git diff AUTO_MERGE (4)
1. Cambios en el árbol de trabajo aún no preparados para la próxima confirmación.
2. Cambios entre el índice y su última confirmación; lo que estaría confirmando si ejecuta git commit sin la opción -a.
3. Cambios en el árbol de trabajo desde su última confirmación; lo que estaría confirmando si ejecuta git commit -a
4. Cambios en el árbol de trabajo que ha realizado para resolver conflictos textuales hasta el momento.

Comparando con confirmaciones arbitrarias

$ git diff test            (1)
$ git diff HEAD -- ./test  (2)
$ git diff HEAD^ HEAD      (3)
1. En lugar de usar la punta de la rama actual, compare con la punta de la rama "test".
2. En lugar de comparar con la punta de la rama "test", compare con la punta de la rama actual, pero limite la comparación al archivo "test".
3. Compare la versión antes de la última confirmación y la última confirmación.

Comparando ramas

$ git diff topic master    (1)
$ git diff topic..master   (2)
$ git diff topic...master  (3)
1. Cambios entre las puntas de las ramas topic y master.
2. Igual que el anterior.
3. Cambios ocurridos en la rama master desde que la rama topic se inició a partir de ella.
