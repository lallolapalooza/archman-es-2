GITFORMAT-CHUNK(5) Manual de Git GITFORMAT-CHUNK(5)

NOMBRE

gitformat-chunk - Formatos de archivo basados en fragmentos

SINOPSIS

Utilizado por gitformat-commit-graph(5) y el formato "MIDX" (ver la documentación del formato de paquetes en gitformat-pack(5)).

DESCRIPCIÓN

Algunos formatos de archivo en Git utilizan un concepto común de "fragmentos" para describir secciones del archivo. Esto permite el acceso estructurado a un archivo grande escaneando una pequeña "tabla de contenido" para los datos restantes. Este formato común es utilizado por los archivos commit-graph y multi-pack-index. Consulte el formato multi-pack-index en gitformat-pack(5) y el formato commit-graph en gitformat-commit-graph(5) para ver cómo utilizan los fragmentos para describir datos estructurados.

Un formato de archivo basado en fragmentos comienza con información de cabecera personalizada para ese formato. Esa cabecera debe incluir suficiente información para identificar el tipo de archivo, la versión del formato y el número de fragmentos en el archivo. A partir de esta información, ese archivo puede determinar el inicio de la región basada en fragmentos.

La región basada en fragmentos comienza con una tabla de contenido que describe dónde comienzan y terminan cada fragmento. Esto consiste en (C+1) filas de 12 bytes cada una, donde C es el número de fragmentos. Considere la siguiente tabla:

| ID del fragmento (4 bytes) | Desplazamiento del fragmento (8 bytes) |
|--------------------------|---------------------------------------|
| ID[0]                    | OFFSET[0]                             |
| ...                      | ...                                   |
| ID[C]                    | OFFSET[C]                             |
| 0x0000                   | OFFSET[C+1]                           |

Cada fila consta de un identificador de fragmento (ID) de 4 bytes y un desplazamiento de 8 bytes. Cada entero se almacena en orden de bytes de red (network-byte order).

El identificador de fragmento ID[i] es una etiqueta para los datos almacenados dentro de este archivo desde OFFSET[i] (inclusive) hasta OFFSET[i+1] (exclusive). Por lo tanto, el tamaño del i-ésimo fragmento es igual a la diferencia entre `OFFSET[i+1] y OFFSET[i]. Esto requiere que los datos del fragmento aparezcan de forma contigua en el mismo orden que la tabla de contenido.

La entrada final en la tabla de contenido debe ser cuatro bytes cero. Esto confirma que la tabla de contenido está terminando y proporciona el desplazamiento para el final de los datos basados en fragmentos.

Nota: El formato basado en fragmentos espera que el archivo contenga *al menos* un hash final después de OFFSET[C+1].

Las funciones para trabajar con formatos de archivo basados en fragmentos se declaran en chunk-format.h. El uso de estos métodos proporciona verificaciones adicionales que ayudan a los desarrolladores al crear nuevos formatos de archivo.

ESCRIBIR FORMATOS DE ARCHIVO BASADOS EN FRAGMENTOS

Para escribir un formato de archivo basado en fragmentos, cree un struct chunkfile llamando a init_chunkfile() y pase un puntero a struct hashfile. El llamante es responsable de abrir el hashfile y escribir la información de cabecera para que el formato de archivo sea identificable antes de que comience el formato basado en fragmentos.

Luego, llame a add_chunk() para cada fragmento que se pretenda escribir. Esto rellena el chunkfile con información sobre el orden y el tamaño de cada fragmento a escribir. Proporcione un puntero a función chunk_write_fn para realizar la escritura de los datos del fragmento cuando se solicite.

Llame a write_chunkfile() para escribir la tabla de contenido en el hashfile seguido de cada uno de los fragmentos. Esto verificará que cada fragmento escribió la cantidad esperada de datos para que la tabla de contenido sea correcta.

Finalmente, llame a free_chunkfile() para liberar los datos de struct chunkfile. El llamante es responsable de finalizar el hashfile escribiendo el hash final y cerrando el archivo.

LEER FORMATOS DE ARCHIVO BASADOS EN FRAGMENTOS

Para leer un formato de archivo basado en fragmentos, el archivo debe abrirse como una región mapeada en memoria. La API de formato de fragmentos espera que todo el archivo esté mapeado como una región de memoria contigua.

Inicialice un puntero a struct chunkfile con init_chunkfile(NULL).

Después de leer la información de cabecera desde el principio del archivo, incluido el recuento de fragmentos, llame a read_table_of_contents() para rellenar el struct chunkfile con la lista de fragmentos, sus desplazamientos y sus tamaños.

Extraiga la información de datos para cada fragmento utilizando pair_chunk() o read_chunk():

•pair_chunk() asigna un puntero dado con la ubicación dentro del archivo mapeado en memoria correspondiente al desplazamiento de ese fragmento. Si el fragmento no existe, el puntero no se modifica.
•read_chunk() toma un puntero a función chunk_read_fn y lo llama con la información inicial de puntero y tamaño apropiada. La función no se llama si el fragmento no existe. Utilice este método para leer fragmentos si necesita realizar un análisis inmediato o si necesita ejecutar lógica basada en el tamaño del fragmento.

Después de llamar a estos métodos, llame a free_chunkfile() para liberar los datos de struct chunkfile. Esto no cerrará la región mapeada en memoria. Se espera que los llamantes posean esos datos durante el tiempo que se necesiten los punteros dentro de la región.

EJEMPLOS

Estos formatos de archivo utilizan la API de formato de fragmentos y pueden servir como ejemplos para formatos futuros:

•commit-graph: vea write_commit_graph_file() y parse_commit_graph() en commit-graph.c para ver cómo se utiliza la API de formato de fragmentos para escribir y analizar el formato de archivo commit-graph documentado en el formato de archivo commit-graph en gitformat-commit-graph(5).
•multi-pack-index: vea write_midx_internal() y load_multi_pack_index() en midx.c para ver cómo se utiliza la API de formato de fragmentos para escribir y analizar el formato de archivo multi-pack-index documentado en la sección del formato de archivo multi-pack-index de gitformat-pack(5).
