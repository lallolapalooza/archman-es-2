GIT-RESTORE(1) Manual de Git GIT-RESTORE(1)

NOMBRE

git-restore - Restaura archivos del árbol de trabajo

SINOPSIS

git restore [<opciones>] [--source=<árbol>] [--staged] [--worktree] [--] <especificación de ruta>...
git restore [<opciones>] [--source=<árbol>] [--staged] [--worktree] --pathspec-from-file=<archivo> [--pathspec-file-nul]
git restore (-p|--patch) [<opciones>] [--source=<árbol>] [--staged] [--worktree] [--] [<especificación de ruta>...]

DESCRIPCIÓN

Restaura las rutas especificadas en el árbol de trabajo con algunos contenidos de una fuente de restauración. Si una ruta está rastreada pero no existe en la fuente de restauración, se eliminará para que coincida con la fuente.

El comando también puede usarse para restaurar el contenido del índice con --staged, o restaurar tanto el árbol de trabajo como el índice con --staged --worktree.

De forma predeterminada, si se proporciona --staged , los contenidos se restauran desde HEAD, de lo contrario desde el índice. Usa --source para restaurar desde un commit diferente.

Consulta "Reset, restore y revert" en git(1) para las diferencias entre los tres comandos.

OPCIONES

-s <árbol>, --source=<árbol>

Restaura los archivos del árbol de trabajo con el contenido del árbol dado. Es común especificar el árbol fuente nombrando un commit, rama o etiqueta asociada con él.

Si no se especifica, los contenidos se restauran desde HEAD si se proporciona --staged , de lo contrario desde el índice.

Como caso especial, puedes usar "<rev-A>...<rev-B>" como un atajo para la base de fusión de <rev-A> y <rev-B> si hay exactamente una base de fusión. Puedes omitir al menos uno de <rev-A>_ y <rev-B>, en cuyo caso por defecto es HEAD.

-p, --patch

Selecciona interactivamente los fragmentos en la diferencia entre la fuente de restauración y la ubicación de restauración. Consulta la sección "Modo interactivo" de git-add(1) para aprender a operar el modo --patch .

-U<n>, --unified=<n>

Genera diferencias con <n> líneas de contexto. Por defecto es diff.context o 3 si la opción de configuración no está definida.

--inter-hunk-context=<n>

Muestra el contexto entre fragmentos de diferencia, hasta el número especificado de <número> líneas, fusionando así los fragmentos que están cerca unos de otros. Por defecto es diff.interHunkContext o 0 si la opción de configuración no está definida.

-W, --worktree, -S, --staged

Especifica la ubicación de restauración. Si no se especifica ninguna opción, por defecto se restaura el árbol de trabajo. Especificar --staged solo restaurará el índice. Especificar ambos restaura ambos.

-q, --quiet

Silencioso, suprime los mensajes de retroalimentación. Implica --no-progress.

--progress, --no-progress

El estado de progreso se informa en el flujo de error estándar por defecto cuando está conectado a una terminal, a menos que se especifique --quiet . Esta bandera habilita el informe de progreso incluso si no está conectado a una terminal, independientemente de --quiet.

--ours, --theirs

Al restaurar archivos en el árbol de trabajo desde el índice, usa la etapa #2 (ours) o #3 (theirs) para rutas no fusionadas. Esta opción no puede usarse al verificar rutas desde un árbol-ish (es decir, con la --source opción).

Ten en cuenta que durante git rebase y git pull --rebase, ours y theirs pueden aparecer intercambiados. Consulta la explicación de las mismas opciones en git-checkout(1) para más detalles.

-m, --merge

Al restaurar archivos en el árbol de trabajo desde el índice, recrea la fusión conflictiva en las rutas no fusionadas. Esta opción no puede usarse al verificar rutas desde un árbol-ish (es decir, con la --source opción).

--conflict=<estilo>

Igual que la opción --merge anterior, pero cambia la forma en que se presentan los fragmentos conflictivos, anulando la variable de configuración merge.conflictStyle . Los valores posibles son merge (predeterminado), diff3, y zdiff3.

--ignore-unmerged

Al restaurar archivos en el árbol de trabajo desde el índice, no aborta la operación si hay entradas no fusionadas y no se especifica --ours, --theirs, --merge o --conflict . Las rutas no fusionadas en el árbol de trabajo se dejan intactas.

--ignore-skip-worktree-bits

En el modo de verificación dispersa (sparse checkout), el comportamiento predeterminado es solo actualizar las entradas que coinciden con <especificación de ruta> y los patrones dispersos en $GIT_DIR/info/sparse-checkout. Esta opción ignora los patrones dispersos y restaura incondicionalmente cualquier archivo en <especificación de ruta>.

--recurse-submodules, --no-recurse-submodules

Si <especificación de ruta> nombra un submódulo activo y la ubicación de restauración incluye el árbol de trabajo, el submódulo solo se actualizará si se proporciona esta opción, en cuyo caso su árbol de trabajo será restaurado al commit registrado en el superproyecto, y cualquier modificación local será sobrescrita. Si no se usa nada (o --no-recurse-submodules), los árboles de trabajo de los submódulos no serán actualizados. Al igual que git-checkout(1), esto desvinculará el HEAD del submódulo.

--overlay, --no-overlay

En el modo overlay, nunca se eliminan archivos al restaurar. En el modo no-overlay, se eliminan los archivos rastreados que no aparecen en el <árbol> de --source=<árbol>, para hacer que coincidan exactamente con el <árbol> . El modo predeterminado es no-overlay.

--pathspec-from-file=<archivo>

La especificación de ruta se pasa en el <archivo> en lugar de los argumentos de la línea de comandos. Si el <archivo> es exactamente - entonces se usa la entrada estándar. Los elementos de la especificación de ruta se separan por LF o CR/LF. Los elementos de la especificación de ruta pueden estar entrecomillados como se explica para la variable de configuración core.quotePath (consulta git-config(1)). Consulta también --pathspec-file-nul y la opción global --literal-pathspecs.

--pathspec-file-nul

Solo tiene sentido con --pathspec-from-file. Los elementos de la especificación de ruta se separan con el carácter NUL y todos los demás caracteres se toman literalmente (incluyendo saltos de línea y comillas).

--

No interpretar más argumentos como opciones.

<especificación de ruta>...

Limita las rutas afectadas por la operación.

Para más detalles, consulta la entrada pathspec en gitglossary(7).

EJEMPLOS

La siguiente secuencia cambia a la rama master , revierte el Makefile a dos revisiones atrás, borra hello.c por error, y lo recupera desde el índice.

$ git switch master
$ git restore --source master~2 Makefile  (1)
$ rm -f hello.c
$ git restore hello.c                     (2)
1. tomar un archivo de otro commit
2. restaurar hello.c desde el índice

Si quieres restaurar todos los archivos fuente C para que coincidan con la versión en el índice, puedes decir

$ git restore '*.c'

Observa las comillas alrededor de *.c. El archivo hello.c también será restaurado, aunque ya no esté en el árbol de trabajo, porque el comodín de archivos se usa para hacer coincidir entradas en el índice (no en el árbol de trabajo por el shell).

Para restaurar todos los archivos en el directorio actual

$ git restore .

o para restaurar todos los archivos del árbol de trabajo con la magia de la especificación de ruta top (consulta gitglossary(7))

$ git restore :/

Para restaurar un archivo en el índice para que coincida con la versión en HEAD (esto es lo mismo que usar git-reset(1))

$ git restore --staged hello.c

o puedes restaurar tanto el índice como el árbol de trabajo (esto es lo mismo que usar git-checkout(1))

$ git restore --source=HEAD --staged --worktree hello.c

o la forma corta, que es más práctica pero menos legible:

$ git restore -s@ -SW hello.c
