N

genhtml crea una vista HTML de los datos de cobertura encontrados en archivos de traza geninfo y lcov que se encuentran mediante patrones de coincidencia glob (glob-match pattern(s)) tracefile_pattern. Véase el manual geninfo(1) para una descripción del formato del archivo de

traza.


Las características

incluyen:
  • Comparación de cobertura diferencial contra datos de cobertura de referencia
    • (baseline)
  • Anotación de informes con
    • información de fecha y pro

Los conceptos básicos de la cobertura diferencial y el agrupamiento por fecha/propietario se describen en el artículo disponible en https://arxiv.org/abs/2008.

Cobertura

diferencial

La cobertura diferencial compara dos versiones del código fuente - la versión de referencia (baseline) y la versión actual - y los resultados de cobertura de cada una para segmentar el código en

categorías.

Para crear un informe de cobertura diferencial, genhtml

requiere
1
.
uno o más archivos de referencia (baseline-files) especificados mediante --baseline-file,
y
2
.
un archivo de parche en formato unificado especificado usando --diff-fil
e

Tanto tracefile_pattern como baseline-file se tratan como patrones glob que coinciden con uno o más

archivos.

La diferencia en la cobertura entre el conjunto de archivos de traza (tracefiles) y archivos de referencia (baseline-files) se clasifica línea por línea en categorías basadas en cambios en 2

aspectos:
1
.
Resultados de cobertura de pruebas: una línea de código puede estar probada (1), no probada (0), o sin usar (#). Una línea sin usar es una línea de código fuente que no tiene datos de cobertura asociados, por ejemplo debido a una sentencia #ifdef deshabilitada.
2
.
Cambios en el código fuente: una línea puede estar sin cambios, añadida (+ =>), o eliminada (=> -). Tenga en cuenta que el formato de archivo de diferencias (diff-file) usado por genhtml informa de los cambios en las líneas como la eliminación de la línea antigua y la adición de la nueva línea.

A continuación se muestran las 12 categorías resultantes, ordenadas por prioridad (asumiendo que el código no probado es más interesante que el código probado, y que el código nuevo es más interesante que el código antiguo)

:
UNC
Código nuevo sin cubrir (Uncovered New Code, + => 0): el código añadido recientemente no está probado.

LB

C
Cobertura de referencia perdida (Lost Baseline Coverage, 1 => 0): el código sin cambios ya no está probado.

UI

C
Código incluido sin cubrir (Uncovered Included Code, # => 0): el código previamente sin usar no está probado.

UB

C
Código de referencia sin cubrir (Uncovered Baseline Code, 0 => 0): el código sin cambios no estaba probado antes, y no está probado ahora.

GB

C
Cobertura de referencia ganada (Gained Baseline Coverage, 0 => 1): el código sin cambios está probado ahora.

GI

C
Cobertura incluida ganada (Gained Included Coverage, # => 1): el código previamente sin usar está probado ahora.

GN

C
Cobertura nueva ganada (Gained New Coverage, + => 1): el código añadido recientemente está probado.

CB

C
Código de referencia cubierto (Covered Baseline Code, 1 => 1): el código sin cambios estaba probado antes y sigue estando probado.

EU

B
Referencia sin cubrir excluida (Excluded Uncovered Baseline, 0 => #): el código previamente sin probar ahora está sin usar.

EC

B
Referencia cubierta excluida (Excluded Covered Baseline, 1 => #): el código previamente probado ahora está sin usar.

DU

B
Referencia sin cubrir eliminada (Deleted Uncovered Baseline, 0 => -): el código previamente sin probar ha sido eliminado.

Nota: Debido a que estas líneas no están representa

das en la versión actual del código fuente, solo s

DC

B
Referencia cubierta eliminada (Deleted Covered Baseline, 1 => -): el código previamente probado ha sido eliminado.

Nota: Debido a que estas líneas no están representadas en la versión actual del código fuente, solo se representan en la tabla resumen de clasificación.

El informe de cobertura diferencial colorea las regiones categorizadas en la vista del código fuente usando colores únicos para cada una. Puede usar la opción --simplified-colors para usar en su lugar un color p

Agrupamiento por fecha y

propietario

El agrupamiento por fecha (date binning) anota los informes de cobertura con información de la antigüedad del último cambio para distinguir el código añadido o modificado recientemente que no ha sido probado del código más antiguo, presumiblemente estable, que tampoco está probado. El agrupamiento por propietario (owner binning) añade una anotación que identifica al autor de los

cambios.

Tanto el informe de antigüedad como el de propiedad pueden usarse para mejorar los esfuerzos del equipo para mantener una buena disciplina de cobertura, destacando las deficiencias de cobertura en el código modificado recientemente, incluso en ausencia de datos de cobertura de referencia (baseline)

.

Para habilitar el agrupamiento por fecha y propietario, debe usarse la opción --annotate-script para especificar un script que proporcione información de antigüedad y propiedad de las líneas de código

fuente.

Para cada línea de código fuente, la antigüedad (age) ies el intervalo desde la fecha de modificación más reciente y el propietario es la identidad de usuario responsable del cambio más reciente en esa

línea.

Los totales generales de cobertura de líneas y los recuentos para cada una de las 12 categorías de clasificación se recopilan para cada uno de los rangos de edad especificados (ver la opción --date-bi

ns, más
abajo).

Consideraciones

adicionales

Si se usa la opción --criteria-script, genhtml usará el script referenciado para determinar si sus criterios de cobertura se han cumplido - y devolverá un estado distinto de cero e imprimirá un mensaje si los criterios no se

cumplen.

La opción --version-script se usa para verificar que se muestran las versiones del código fuente las mismas/compatibles que las que se usaron para capturar los datos de cobertura, así como para verificar que se usó el mismo código fuente para capturar la información de coberturase fusionará y para verificar que la versión de origen utilizada para las operaciones de filtrado es compatible con la versión utilizada para generar los

datos.

Los archivos de salida HTML se crean en el directorio de trabajo actual a menos que se utilice la opción --output-directory. Si tracefile o baseline-file terminan en ".gz", se asume que están comprimidos con GZIP y se utilizará la herramienta gunzip para descomprimirlos de forma

transparente.

Tenga en cuenta que todos los archivos de código fuente deben estar presentes y ser legibles en la ubicación exacta del sistema de archivos en la que se compiló, y todas las referencias de ruta en los archivos de datos de entrada ".info" y "diff" deben coincidir exactamente (es decir, coincidencia exacta de cadena)

.

Además, los scripts --version-script, --annotate-script y --criteria-script utilizan las mismas cadenas de ruta. Sin embargo, consulte las opciones --substitute y --resolve-script para un mecanismo de ajuste de las rutas extraídas para que coincidan con su estructura de origen y/o de control de

revisiones.

Puede utilizar la opción de configuración check_exisitence_before_callback para indicar a la herramienta que compruebe que el archivo existe antes de llamar a la devolución de llamada --version-script o --annotate-script. Consulte el manual lcovrc(5) para
