gettimeofday(2) Manual de Llamadas al Sistema gettimeofday(2)

NOMBRE

gettimeofday, settimeofday - obtener / establecer la hora

BIBLIOTECA

Biblioteca C estándar (libc,-lc)

SINOPSIS

#include <sys/time.h>
[[obsoleto]]
int gettimeofday(struct timeval *restrict tv,
                 struct timezone *_Nullable restrict tz);
[[obsoleto]]
int settimeofday(const struct timeval *tv,
                 const struct timezone *_Nullable tz);
Requisitos de la macro de prueba de características para glibc (ver feature_test_macros(7)):

settimeofday():

    Desde glibc 2.19:
        _DEFAULT_SOURCE
    glibc 2.19 y anteriores:
        _BSD_SOURCE

DESCRIPCIÓN

Las funciones gettimeofday() y settimeofday() pueden obtener y establecer la hora, así como una zona horaria.

El tv argumento es un struct timeval (como se especifica en <sys/time.h>):


struct timeval {
    time_t      tv_sec;     /* segundos */
    suseconds_t tv_usec;    /* microsegundos */
};

y proporciona el número de segundos y microsegundos desde la Época (ver time(2)).

El tz argumento es un struct timezone:


struct timezone {
    int tz_minuteswest;     /* minutos al oeste de Greenwich */
    int tz_dsttime;         /* tipo de corrección de horario de verano */
};

Si tv o tz es NULL, la estructura correspondiente no se establece ni se devuelve. (Sin embargo, se producirán advertencias de compilación si tv es NULL.)

El uso de la estructura timezone está obsoleto; el tz argumento normalmente debería especificarse como NULL. Ver VERSIONES.

En Linux, existen algunas semánticas peculiares de "reloj deformado" asociadas con la settimeofdayllamada al sistema si en la primera llamada (después del arranque) que tiene un argumento no nulo tz , el tv argumento es NULL y el tz_minuteswest campo es distinto de cero. (El tz_dsttime campo debería ser cero en este caso.) En tal caso se asume que el reloj CMOS está en hora local, y que debe incrementarse en esta cantidad para obtener la hora UTC del sistema. Sin duda, es una mala idea usar esta característica.

VALOR DE RETORNO

gettimeofday() y settimeofday() devuelven 0 para éxito. En caso de error, se devuelve -1 y errno se establece para indicar el error.

ERRORES

EFAULT
Uno de tv o tz apuntaba fuera del espacio de direcciones accesible.
EINVAL
(settimeofday()): timezone es inválido.
EINVAL
(settimeofday()): tv.tv_sec es negativo o tv.tv_usec está fuera del rango [0, 999,999].
EINVAL (desde Linux 4.3)
(settimeofday()): Se intentó establecer la hora en un valor menor que el valor actual del reloj CLOCK_MONOTONIC (ver clock_gettime(2)).
EPERM
El proceso que llama no tiene privilegios suficientes para llamar a settimeofday(); en Linux se requiere la capacidad CAP_SYS_TIME .

VERSIONES

Diferencias entre la biblioteca C y el núcleo

En algunas arquitecturas, se proporciona una implementación de gettimeofday() en el vdso(7).

El núcleo acepta NULL tanto para tv como para tz. El argumento de zona horaria es ignorado por glibc y musl, y no se pasa al ni desde el núcleo. Bionic de Android pasa el argumento de zona horaria al y desde el núcleo, pero Android no actualiza la zona horaria del núcleo basándose en la zona horaria del dispositivo en Configuración, por lo que la zona horaria del núcleo es típicamente UTC.

ESTÁNDARES

Ninguno.

HISTORIA

SVr4, 4.3BSD. POSIX.1-2001 describió gettimeofday() pero no settimeofday(). POSIX.1-2008 marcó gettimeofday() como obsoleto, recomendando el uso de clock_gettime(2) en su lugar. Del mismo modo, clock_settime(2) debería usarse en lugar de settimeofday(). POSIX.1-2024 eliminó gettimeofday().

Tradicionalmente, los campos de struct timeval eran de tipo long.

El campo tz_dsttime

En un núcleo que no sea Linux, con glibc, el tz_dsttime campo de struct timezone se establecerá en un valor distinto de cero por gettimeofday() si la zona horaria actual ha tenido o tendrá alguna vez aplicada una regla de horario de verano. En este sentido, refleja exactamente el significado de daylight(3) para la zona actual. En Linux, con glibc, el establecimiento del tz_dsttime campo de struct timezone nunca ha sido utilizado por settimeofday() o gettimeofday(). Por lo tanto, lo siguiente es puramente de interés histórico.

En sistemas antiguos, el campo tz_dsttime contiene una constante simbólica (los valores se dan a continuación) que indica en qué parte del año está en vigor el Horario de Verano. (Nota: este valor es constante a lo largo del año: no indica que el horario de verano esté en vigor, solo selecciona un algoritmo.) Los algoritmos de horario de verano definidos son los siguientes:


DST_NONE     /* sin horario de verano */
DST_USA      /* horario de verano estilo EE. UU. */
DST_AUST     /* horario de verano estilo australiano */
DST_WET      /* horario de verano de Europa Occidental */
DST_MET      /* horario de verano de Europa Central */
DST_EET      /* horario de verano de Europa Oriental */
DST_CAN      /* Canadá */
DST_GB       /* Gran Bretaña e Irlanda */
DST_RUM      /* Rumanía */
DST_TUR      /* Turquía */
DST_AUSTALT  /* estilo australiano con cambio en 1986 */

Por supuesto, resultó que el período en el que está en vigor el Horario de Verano no puede ser dado por un simple algoritmo, uno por país; de hecho, este período está determinado por decisiones políticas impredecibles. Por lo tanto, este método de representar zonas horarias ha sido abandonado.

NOTAS

La hora devuelta por gettimeofday() está afectada por saltos discontinuos en la hora del sistema (p. ej., si el administrador del sistema cambia manualmente la hora del sistema). Si necesita un reloj monótonamente creciente, ver clock_gettime(2).

Las macros para operar en estructuras timeval se describen en timeradd(3).
