-b [ --backlog ] arg (=32)
Número de conexiones en espera para escuchar.

Número de descriptores de archivo permitidos para el proceso (las conexiones totales serán ligeramente menores). El valor predeterminado es el máximo permitido para el usuario.
-h [ --help ]
Imprime este menú de ayuda.
-j [ --job-retries ] arg (=0)
Número de intentos para ejecutar el trabajo antes de que el servidor de trabajos lo elimine. Esto es útil para asegurar que un trabajo defectuoso no bloquee todos los trabajadores disponibles. El valor predeterminado no tiene límite.
-l [ --log-file ] arg
Archivo de registro donde escribir errores e información. Habilitar esta opción también fuerza la habilitación del primer nivel de verbosidad.

Archivo donde se escribirá el ID del proceso.
-r [ --protocol ] arg
Cargar módulo de protocolo.

Asignar trabajo en orden de ronda por conexión de trabajador. El valor predeterminado es asignar trabajo en el orden de las funciones agregadas por el trabajador.
-q [ --queue-type ] arg
Tipo de cola persistente a utilizar.
-t [ --threads ] arg (=4)
Número de hilos de E/S a utilizar. Predeterminado=4.
-u [ --user ] arg
Cambiar al usuario indicado después del inicio.
-v [ --verbose ] arg (=v)
Establecer el nivel de verbosidad. El valor predeterminado es ERROR. Acepta FATAL, ALERT, CRITICAL, ERROR, WARNING, NOTICE, INFO y DEBUG.
-V [ --version ]
Mostrar la versión de gearmand y salir.
-w [ --worker-wakeup ] arg (=0)
Número de trabajadores a despertar por cada trabajo recibido. El valor predeterminado es despertar a todos los trabajadores disponibles.
--keepalive
Habilitar keepalive en los sockets.
--keepalive-idle arg (=-1)
Si keepalive está habilitado, establezca el valor para TCP_KEEPIDLE para sistemas que lo soporten. Un valor de -1 significa que el sistema no lo soporta o se produjo un error al intentar recuperar el valor predeterminado.
--keepalive-interval arg (=-1)
Si keepalive está habilitado, establezca el valor para TCP_KEEPINTVL para sistemas que lo soporten. Un valor de -1 significa que el sistema no lo soporta o se produjo un error al intentar recuperar el valor predeterminado.
--keepalive-count arg (=-1)
Si keepalive está habilitado, establezca el valor para TCP_KEEPCNT para sistemas que lo soporten. Un valor de -1 significa que el sistema no lo soporta o se produjo un error al intentar recuperar el valor predeterminado.

DESCRIPCIÓN

Gearman proporciona un marco de aplicación genérico para delegar trabajo a otras máquinas o procesos que son más adecuados para realizar el trabajo. Permite realizar trabajo en paralelo, equilibrar la carga de procesamiento y llamar a funciones entre lenguajes. Se puede utilizar en una variedad de aplicaciones, desde sitios web de alta disponibilidad hasta el transporte de eventos de replicación de bases de datos. En otras palabras, es el sistema nervioso de cómo se comunica el procesamiento distribuido. Algunos puntos fuertes de Gearman

:
  • Código abierto - ¡Es gratis! (en ambos significados de la palabra) Gearman tiene una comunidad de código abierto activa con la que es fácil involucrarse si necesitas ayuda o quieres
    • contribuir.
  • Multilenguaje - Hay interfaces para varios lenguajes, y esta lista está creciendo. También tienes la opción de escribir aplicaciones heterogéneas con clientes que envían trabajo en un lenguaje y trabajadores que realizan ese trabajo en
    • otro.
  • Flexible - No estás atado a ningún patrón de diseño específico. Puedes montar rápidamente aplicaciones distribuidas usando cualquier modelo que elijas, una de esas opciones siendo
    • Map/Reduce.
  • Rápido - Gearman tiene un protocolo e interfaz simples con un nuevo servidor optimizado en C para minimizar la sobrecarga de tu
    • aplicación.
  • Incrustable - Dado que Gearman es rápido y ligero, es ideal para aplicaciones de todos los tamaños. También es fácil de introducir en aplicaciones existentes con una sobrecarga
    • mínima.
  • Sin punto único de fallo - Gearma
    • n no solo puede ayudar a escalar
sistemas, sino que puede hacerlo
de una manera tolerante a fallos.

Modelo de

Hilos

La opción -t de gearmand te permite especificar múltiples hilos de E/S, esto está habilitado por defecto. Actualmente hay tres tipos de hilos en el servidor de

trabajos:

Hilo de escucha y gestión - solo uno Hilo de E/S - puede haber muchos Hilo de procesamiento - solo

uno

Cuando no se da la opción -t o se da -t 0, los tres tipos de hilos ocurren dentro de un solo hilo. Cuando se da -t 1, hay un hilo para escucha/gestión y un hilo para E/S y procesamiento. Cuando se da -t 2, hay un hilo para cada tipo de hilo anterior. Para todos los valores de la opción -t por encima de 2, se crean más hilos de

E/S.

El hilo de escucha y gestión es principalmente responsable de aceptar nuevas conexiones y asignar esas conexiones a un hilo de E/S (si hay muchos). También coordina el inicio y apagado dentro del servidor. Este hilo tendrá una instancia de libevent para gestionar eventos de socket y señales en un pipe interno. Este pipe se usa para despertar al hilo o para coordinar el

apagado.

El hilo de E/S es responsable de realizar las llamadas al sistema de lectura y escritura en los sockets y el análisis inicial de paquetes. Una vez que el paquete ha sido analizado, se pone en una cola asíncrona para el hilo de procesamiento (cada hilo tiene su propia cola, por lo que hay muy poca contención). Cada hilo de E/S tiene su propia instancia de libevent para gestionar eventos de socket y señales en un pipe interno, como el hilo de

escucha.

El hilo de procesamiento no debería tener llamadas al sistema dentro de él (excepto el ocasional brk() para más memoria), y gestiona las diversas listas y tablas hash utilizadas para rastrear claves únicas, manejadores de trabajos, funciones y colas de trabajos. Todos los paquetes que necesitan ser enviados de vuelta a las conexiones se ponen en una cola asíncrona para el hilo de E/S. El hilo de E/S los recogerá y los enviará de vuelta a través del socket conectado. Todos los paquetes fluyen a través del hilo de procesamiento ya que contiene la información necesaria para procesar los paquetes. Esto se debe a la naturaleza compleja de las diversas listas y tablas hash. Si múltiples hilos los modificaran, la sobrecarga de bloqueo probablemente causaría un peor rendimiento que tenerlo en un solo hilo (y también complicaría el código). En el futuro, más trabajo puede ser empujado a los hilos de E/S, y el hilo de procesamiento puede retener una funcionalidad mínima para gestionar esas tablas y listas. Hasta ahora esto no ha sido un cuello de botella significativo, una máquina Intel de 16 núcleos es capaz de procesar hasta 50k trabajos por

segundo.

Colas

Persistentes

Dentro del servidor de trabajos de Gearman, todas las colas de trabajos se almacenan en memoria. Esto significa que si un servidor se reinicia o se bloquea con trabajos pendientes, se perderán y nunca serán ejecutados por un trabajador. Se añadieron colas persistentes para permitir que los trabajos en segundo plano se almacenen en una cola externa duradera para que puedan sobrevivir entre reinicios y bloqueos del servidor. La cola persistente solo está habilitada para los trabajos en segundo plano porque los trabajos en primer plano tienen un cliente adjunto. Si un servidor de trabajos desaparece, el cliente puede detectarlo y reiniciar el trabajo en primer plano en otro lugar (o reportar un error de vuelta al llamador original). Los trabajos en segundo plano, por otro lado, no tienen un cliente adjunto y simplemente se espera que se ejecuten cuando se

envían.

La cola persistente funciona llamando a una función de retorno de llamada del módulo justo antes de poner un nuevo trabajo en la cola interna de trabajos pendientes para ser ejecutados. Esto permite al módulo almacenar el trabajo a punto de ser ejecutado de alguna manera persistente para que pueda ser reproducido más tarde durante un reinicio. Una vez que es almacenado a través del módulo, el trabajo se pone en la cola activa ejecutable, despertando a los trabajadores disponibles si es necesario. Una vez que el trabajo ha sido completado exitosamente por un trabajador, se llama a otra función de retorno de llamada del módulo para notificar al módulo que el trabajo está hecho y puede ser eliminado. Si un servidor de trabajos se bloquea o se reinicia entre estas dos llamadas para un trabajo, los trabajos se recargan durante el siguiente inicio del servidor de trabajos. Cuando el servidor de trabajos arranca, llamará a una función de retorno de llamada de reproducción en el módulo para proporcionar una lista de todos los trabajos que no estaban completos. Esto se usa para poblar la cola de memoria interna de trabajos a ejecutar. Una vez que esta reproducción está completa, el servidor de trabajos termina su inicialización y los trabajos ahora son ejecutables una vez que los trabajadores se conectan (la cola debería estar en el mismo estado que cuando se bloqueó). Estos trabajos se eliminan de la cola persistente cuando se completan como de normal. NOTA: Eliminar trabajos del almacenamiento de la cola persistente no los eliminará de la cola en memoria mientras el servidor está en

ejecución.

Las colas se implementan usando una interfaz modular, por lo que es fácil añadir nuevos almacenes de datos para la cola

persistente.

Un módulo de cola persistente se habilita pasando la opción -q o –queue-type a gearmand. Ejecuta gearma

nd –help para ver qué módulos de cola están soportados en tu sistema. Si te faltan opciones para uno q
ue te gustaría usar, necesitarás instalar cualquier dependencia y luego recompilar el paquete gearmand.
