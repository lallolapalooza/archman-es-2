DESCRIPCIÓ

N

La función getrlimit() debe obtener, y la función setrlimit() debe establecer, límites en el consumo de una variedad de

recursos.

Cada llamada a getrlimit() o a setrlimit() identifica un recurso específico sobre el que operar, así como un límite de recurso. Un límite de recurso está representado por una estructura rlimit. El miembro rlim_cur especifica el límite actual o suave y el miembro rlim_max especifica el límite máximo o duro. Los límites suaves pueden ser cambiados por un proceso a cualquier valor que sea menor o igual al límite duro. Un proceso puede (irreversiblemente) reducir su límite duro a cualquier valor que sea mayor o igual al límite suave. Solo un proceso con los privilegios adecuados puede aumentar un límite duro. Tanto los límites duros como los suaves pueden ser cambiados en una sola llamada a setrlimit() sujeto a las restricciones descritas

arriba.

El valor RLIM_INFINITY, definido en <sys/resource.h>, debe considerarse mayor que cualquier otro valor de límite. Si una llamada a getrlimit() devuelve RLIM_INFINITY para un recurso, significa que la implementación no debe hacer cumplir límites sobre ese recurso. Especificar RLIM_INFINITY como cualquier valor de límite de recurso en una llamada exitosa a setrlimit() debe inhibir el cumplimiento de ese límite de

recurso.

Los siguientes recursos están

definidos:
RLIMIT_CO
RE
Este es el tamaño máximo de un archivo core, en bytes, que puede ser creado por un proceso. Un límite de 0 debe prevenir la creación de un archivo core. Si este límite es excedido, la escritura de un archivo core debe terminar en este
tamaño.
RLIMIT_C
PU
Esta es la cantidad máxima de tiempo de CPU, en segundos, usada por un proceso. Si este límite es excedido, se debe generar SIGXCPU para el proceso. Si el proceso está capturando o ignorando SIGXCPU, o si todos los hilos que pertenecen a ese proceso están bloqueando SIGXCPU, el comportamiento no está
especificado.
RLIMIT_DA
TA
Este es el tamaño máximo de un segmento de datos del proceso, en bytes. Si este límite es excedido, la función malloc() debe fallar con errno establecido a [ENOME
M].
RLIMIT_FSI
ZE
Este es el tamaño máximo de un archivo, en bytes, que puede ser creado por un proceso. Si una operación de escritura o truncado causaría que este límite sea excedido, se debe generar SIGXFSZ para el hilo. Si el hilo está bloqueando, o el proceso está capturando o ignorando SIGXFSZ, los intentos continuos de aumentar el tamaño de un archivo desde el fin de archivo más allá del límite deben fallar con errno establecido a [EFBI
G].
RLIMIT_NOFI
LE
Este es un número uno mayor que el valor máximo que el sistema puede asignar a un descriptor recién creado. Si este límite es excedido, las funciones que asignan un descriptor de archivo deben fallar con errno establecido a [EMFILE]. Este límite constriñe el número de descriptores de archivo que un proceso puede
asignar.
RLIMIT_STA
CK
Este es el tamaño máximo de la pila del hilo inicial, en bytes. La implementación no hace crecer automáticamente la pila más allá de este límite. Si este límite es excedido, se debe generar SIGSEGV para el hilo. Si el hilo está bloqueando SIGSEGV, o el proceso está ignorando o capturando SIGSEGV y no ha hecho arreglos para usar una pila alterna, la disposición de SIGSEGV debe establecerse a SIG_DFL antes de que sea
generado.
RLIMIT_
AS
Este es el tamaño máximo de la memoria disponible total del proceso, en bytes. Si este límite es excedido, las funciones malloc() y mmap() deben fallar con errno establecido a [ENOMEM]. En adición, el crecimiento automático de
la pila falla con los efec
tos delineados arriba.

Cuando se usa la función getrlimit(), si un límite de recurso puede ser representado correctamente en un objeto de tipo rlim_t, entonces su representación es devuelta; de lo contrario, si el valor del límite de recurso es igual al del límite duro guardado correspondiente, el valor devuelto debe ser RLIM_SAVED_MAX; de lo contrario, el valor devuelto debe ser

RLIM_SAVED_CUR.

Cuando se usa la función setrlimit(), si el nuevo límite solicitado es RLIM_INFINITY, el nuevo límite debe ser ``sin límite''; de lo contrario, si el nuevo límite solicitado es RLIM_SAVED_MAX, el nuevo límite debe ser el límite duro guardado correspondiente; de lo contrario, si el nuevo límite solicitado es RLIM_SAVED_CUR, el nuevo límite debe ser el límite suave guardado correspondiente; de lo contrario, el nuevo límite debe ser el valor solicitado. En adición, si el límite guardado correspondiente puede ser representado correctamente en un objeto de tipo rlim_t entonces debe ser sobrescrito con el nuevo

límite.

El resultado de establecer un límite a RLIM_SAVED_MAX o RLIM_SAVED_CUR no está especificado a menos que una llamada previa a getrlimit() haya devuelto ese valor como el límite suave o duro para el límite de recurso correspondiente

.

La determinación de si un límite puede ser correctamente representado en un objeto de tipo rlim_t está definida por la implementación. Por ejemplo, algunas implementaciones permiten un límite cuyo valor es mayor que RLIM_INFINITY y otras

no.

La familia de funciones exec debe causar que

los límites de recurso
s sean guardados.

APLICACIONES

Si un proceso intenta establecer el límite duro o suave para RLIMIT_NOFILE a menos que el valor de {_POSIX_OPEN_MAX} de <limits.h>, puede ocurrir un comportamiento

inesperado.

Si un proceso intenta establecer el límite duro o suave para

RLIMIT_NOFILE a menos que el descriptor de archivo abierto más
alto actual +1, puede ocurrir un comportamiento inesperado.

JUSTIFICACIÓ

N

Debe notarse que RLIMIT_STACK aplica ``al menos'' a la pila del hilo inicial en el pro

ceso, y no a la suma de todas las pilas en el proceso, ya que eso sería muy restrictivo
a menos que el valor sea tan grande que no proporcione ningún valor con un solo hilo.
