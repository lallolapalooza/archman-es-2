The gl_get_line() function returns a pointer to the line entered by the user, or NULL on error or at the end of the input. The returned pointer is part of the specified gl resource object, and thus should not be free'd by the caller, or assumed to be unchanging from one call to the next. When reading from a user at a terminal, there will always be a newline character at the end of the returned line. When standard input is being taken from a pipe or a file, there will similarly be a newline unless the input line was too long to store in the internal buffer. In the latter case you should call gl_get_line() again to read the rest of the line. Note that this behavior makes gl_get_line() similar to fgets(). FUENTES ALTERNATIVAS DE

CONFIGURACIÓN

Como se mencionó anteriormente, de forma predeterminada los usuarios tienen la opción de configurar el comportamiento de gl_get_line() a través de un archivo de configuración llamado .teclarc en sus directorios de inicio. El hecho de que todas las aplicaciones compartan este mismo archivo de configuración es tanto una ventaja como una desventaja. En la mayoría de los casos es una ventaja, ya que fomenta la uniformidad y libera al usuario de tener que configurar cada aplicación por separado. En algunas aplicaciones, sin embargo, este único medio de configuración es un problema. Esto es particularmente cierto en software embebido, donde no hay un sistema de archivos del cual leer un archivo de configuración, y también en aplicaciones donde se necesita una elección radicalmente diferente de asignaciones de teclas para emular una interfaz de teclado heredada. Para atender estos casos, la siguiente función permite a la aplicación controlar de dónde se leen los datos de

configuración. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Permite que los comandos de configuración que normalmente se leerían del archivo ~/.teclarc de un usuario, se lean desde cualquiera o ninguno de: una cadena, un archivo de configuración específico de la aplicación, y/o un archivo de configuración específico del usuario. Si esta función se llama antes de la primera llamada a gl_get_line(), el comportamiento predeterminado de leer ~/.teclarc en la primera llamada a gl_get_line() se deshabilita, por lo que toda la configuración debe lograrse usando las fuentes de configuración especificadas con esta

función.

Si app_string != NULL, entonces se interpreta como una cadena que contiene uno o más comandos de configuración, separados entre sí en la cadena por caracteres de salto de línea incrustados. Si app_file != NULL entonces se interpreta como el nombre de ruta completo de un archivo de configuración específico de la aplicación. Si user_file != NULL entonces se interpreta como el nombre de ruta completo de un archivo de configuración específico del usuario, como ~/.teclarc. Por ejemplo, en la siguiente

llamada, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")
;

Luego intenta leer comandos de configuración de todo el sistema desde un archivo opcional llamado /usr/share/myapp/teclarc, y finalmente lee comandos de configuración específicos del usuario desde un archivo .teclarc opcional en el directorio de inicio del usuario. Note que los argumentos se listan en orden ascendente de prioridad, con el contenido de app_string siendo potencialmente sobreescrito por comandos en app_file, y los comandos en app_file siendo potencialmente sobreescritos por comandos en user_file

PERSONALIZADO

Si en su aplicación desea que el completado con TAB complete otras cosas además de o en lugar de nombres de archivo, puede organizarlo registrando una función de retorno de completado alternativa, mediante una llamada a la función gl_customize_co

El argumento data proporciona una manera para que su aplicación pase información arbitraria y específica de la aplicación a la función de retorno. Esto se pasa a la función de retorno cada vez que se la llama. Podría, por ejemplo, apuntar a la tabla de símbolos de la que se deben buscar los completados posibles. El argumento match_fn especifica la función de retorno a llamar. El tipo de función CplMatchFn está definido en libtecla.h, al igual que una macro CPL_MATCH_FN() que puede usar para declarar y establecer prototipos de funciones de retorno. La declaración y las responsabilidades de las funciones de retorno se describen en profundidad en la página de manual de cpl_complete_word(3)

.

En resumen, la función de retorno es responsable de buscar hacia atrás en la línea de entrada, desde el punto en el que el usuario pulsó TAB, para encontrar el inicio de la palabra que se está completando. Luego debe buscar completados posibles de esta palabra y registrarlos uno por uno en el objeto WordCompletion que se le pasa como argumento, llamando a la función cpl_add_completion(). Si la función de retorno desea proporcionar completado de nombres de archivo además de sus propios completados específicos, tiene la opción de llamar ella misma a la función de retorno de completado de nombres de archivo incorporada. Esto también está documentado en la página de manual de cpl_complete_word(3)

.

Tenga en cuenta que si desea que gl_get_line() devuelva la línea de entrada actual cuando se haya realizado un completado exitoso, puede organizarlo cuando llame a cpl_add_completion(), haciendo que el último carácter del sufijo de continuación sea un carácter de nueva línea. Si hace esto, la línea de entrada se actualizará para mostrar el completado, junto con cualquier sufijo de continuación hasta el carácter de nueva línea, y luego gl_get_line() devolverá esta línea de

entrada.

Si, por alguna razón, su función de retorno necesita escribir algo en la terminal, debe llamar a gl_normal_io() antes de hacerlo. Esto iniciará una nueva línea después de la línea de entrada que se está editando actualmente, restablecerá la E/S normal de la terminal y le dirá a gl_get_line() que la línea de entrada necesitará

ser redibujada cuando la f
unción de retorno regrese.

Esto se logra usando la función gl_completion_action()

  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,

Los argumentos data y match_fn se describen como en la página de manual de cpl_complete_word, y especifican la función de retorno que debe invocarse para identificar los completados posibles. El argumento list_only determina si la acción que se está definiendo debe intentar completar la palabra tanto como sea posible en la línea de entrada antes de mostrar cualquier completado ambiguo posible, o si debe simplemente mostrar la lista de completados posibles sin tocar la línea de entrada. La primera opción se selecciona especificando un valor de 0, y la segunda especificando un valor de 1. El argumento name especifica el nombre con el que los archivos de configuración y las futuras invocaciones de esta función deben referirse a la acción. Este debe ser el nombre de una acción de completado existente que se va a cambiar, o un nombre nuevo sin usar para una acción nueva. Finalmente, el argumento keyseq especifica la secuencia de teclas predeterminada para enlazar a la acción. Si esto es NULL, no se enlazará ninguna nueva secuencia de teclas a la

acción.

Tenga cuidado de que para que el usuario pueda cambiar la secuencia de teclas que está enlazada a las acciones que se instalan de esta manera, cuando llame a gl_completion_action() para instalar una acción determinada por primera vez, debe hacerlo entre la llamada a new_GetLine() y la primera llamada a gl_get_line(). Esto se debe a que las reglas dictadas por varios modos, como el modo vi frente al modo emacs, el modo sin eco, y el modo de inserción frente al modo de sobrescritura etc, hacen que sea demasiado compleo para un desarrollador de aplicaciones escribir una acción de edición conforme, así como restringen cambios futuros en los internos de gl_get_line(). consideración.

Si la función de acción desea escribir texto en la terminal, sin que esto se mezcle con el texto mostrado de la línea de entrada, o leer de la terminal sin tener que manejar la E/S cruda de la terminal, entonces antes de realizar cualquiera de estas operaciones, debe suspender temporalmente la edición de línea llamando a la función gl_normal_io(). Esta función vacía cualquier salida pendiente a la terminal, mueve el cursor al inicio de la línea que sigue a la última línea de terminal de la línea de entrada, y luego restaura la terminal a un estado que es adecuado para su uso con las instalaciones stdio de C. Después de haber llamado a esta función, la acción puede leer de y escribir a la terminal sin temor de crear un desorden. No es necesario que la función de acción restaure el entorno de edición original antes de regresar. Esto se hace automáticamente por gl_get_line() después de que la función de acción regrese.                    a gl_return_status() devolverá
                   GLR_TIMEOUT. Tenga en cuenta que si la
                   aplicación necesita que errno siempre tenga
                   un valor significativo cuando
                   gl_get_line() devuelva NULL,
                   la función de callback debe establecer
                   errno adecuadamente.
  GLTO_REFRESH  -  Redibujar la línea de entrada, luego continuar
                   esperando entrada. Debería devolver
                   este valor si su callback escribió en el
                   terminal sin haber llamado primero a
                   gl_normal_io(gl).
  GLTO_CONTINUE -  En el modo normal de E/S bloqueante, continuar
                   esperando entrada, sin redibujar la
                   línea de entrada del usuario.
                   En el modo de E/S de servidor no bloqueante (vea
                   gl_io_mode(3)), hacer que gl_get_line()
                   actúe como si la E/S se bloqueara. Esto significa
                   que gl_get_line() devolverá inmediatamente NULL, y una llamada posterior
                   a gl_return_status() devolverá
                   GLR_BLOCKED

Tenga en cuenta que antes de llamar a la callback, gl_get_line() bloquea la mayoría de las señales, y deja instalados sus propios manejadores de señal, así que si necesita capturar una señal en particular, necesitará tanto instalar temporalmente su propio manejador de señal, como desbloquear la señal. Asegúrese de volver a bloquear la señal (si originalmente estaba bloqueada) y reinstalar el manejador de señal original, si lo hay, antes de

regresar.

Si la función de callback necesita leer o escribir en el terminal, idealmente debería llamar primero a gl_normal_io(gl) para suspender temporalmente la edición de línea. Esto restaurará el terminal a modo canónico, de E/S bloqueante, y moverá el cursor al inicio de una nueva línea de terminal. Más tarde, cuando la callback regrese, gl_get_line() notará que gl_normal_io() fue llamada, redisplayará la línea de entrada y reanudará la edición. Tenga en cuenta que en este caso los valores de retorno, GLTO_REFRESH y GLTO_CONTINUE son

equivalentes.

Para soportar casos donde la función de callback llama a una función de terceros que ocasional e impredeciblemente escribe en el terminal, la conversión automática de "0 a "0 se reactiva antes de que se llame a la función de callback. Si la callback sabe que la función de terceros escribió en el terminal, debería entonces devolver el valor de retorno GLTO_REFRESH, para decirle a gl_get_line() que redibuje la línea de

entrada.

Tenga en cuenta que aunque el argumento de tiempo de espera incluye un componente de nanosegundos, pocos relojes de computadora tienen actualmente resoluciones más finas que unos pocos milisegundos, así que pedir menos de unos pocos milisegundos es equivalente a solicitar cero segundos en muchos sistemas. Si esto fuera un problema, debería basar su selección de tiempo de espera en la resolución real del reloj del host (ej. llamando a sysconf(_SC_CLK_TCK))

.

en es

Por defecto, la función gl_get_line() intercepta un número de señales. continuación.

MANEJO FIABLE DE

SEÑALES

El manejo de señales es sorprendentemente difícil de hacer de forma fiable sin condiciones de carrera. En gl_get_line() se ha tenido mucho cuidado para permitir que las aplicaciones realicen un manejo fiable de señales alrededor de gl_get_line(). Esta sección explica cómo hacer uso de

esto.

Como ejemplo de los problemas que pueden surgir si la aplicación no está escrita correctamente, imagine que su aplicación tiene un manejador de señal SIGINT que establece un indicador global. Ahora suponga que la aplicación prueba este indicador justo antes de invocar gl_get_line(). Si una señal SIGINT resulta ser recibida en la pequeña ventana de tiempo entre la sentencia que prueba el valor de este indicador, y la sentencia que llama a gl_get_line(), entonces gl_get_line() no verá la señal, y no será interrumpido. Como resultado, la aplicación no podrá responder a la señal hasta que el usuario termine de ingresar la línea de entrada y gl_get_line() regrese. Dependiendo de la aplicación, esto podría o no ser un desastre, pero al menos confundiría al

usuario.

La forma de evitar tales problemas es hacer lo

siguiente.

1. Si es necesario, use la función gl_trap_signal() para
configurar gl_get_line() para que aborte cuando se capturen
señales

importantes.

2. Configure gl_get_line() de modo que si alguna de las
señales que captura está bloqueada cuando
se llama a gl_get_line(), se desbloqueen
automáticamente durante los momentos en que gl_get_line() está
esperando E/S. Esto se puede hacer ya sea
por señal, llamando a la
función gl_trap_signal(), y especificando el
atributo GLS_UNBLOCK de la señal, o globalmente llamando a la
función gl_catch_bloc

ked(). 
     void gl_catch_blocked(GetLine *gl)
;


Esta función simplemente agrega el atributo GLS_UNBLOCK
a todas las señales que actualmente está configurada para
atrapar

.

3. Justo antes de llamar a gl_get_line(), bloquee la entrega
de todas las señales que gl_get_line() está
configurada para atrapar. Esto se puede hacer usando la función POSIX
sigprocmask() en conjunto con la
función gl_list_signals()

. 
      int gl_list_signals(GetLine *gl, sigset_t *set)
;


Esta función devuelve el conjunto de señales que está
actualmente configurada para capturar en el argumento set,
que está en la forma requerida por sigprocma

sk().

4. En el ejemplo, ahora se probaría el indicador global que
establece el manejador de señales, sabiendo que ahora no hay
peligro de que este indicador se establezca de nuevo hasta que
gl_get_line() desbloquee sus señales mientras realiza
E/S

.

5. Eventualmente gl_get_line() regresa, ya sea porque
se capturó una señal, ocurrió un error, o el usuario
terminó de ingresar su línea de

entrada.

6. Ahora se verificaría el indicador de señal global de nuevo, y si
está establecido, se respondería a él, y se pondría el indicador a

cero.

7. Use sigprocmask() para desbloquear las señales que fueron
bloqueadas en el paso

3.

La misma técnica se puede usar alrededor de ciertas funciones POSIX conscientes de señales, como sigsetjmp() y sigsuspend(), y en particular, la primera de estas dos funciones se puede usar en conjunto con siglongjmp() para implementar un manejo de señales libre de condiciones de carrera alrededor de otras llamadas al sistema de larga duración. La forma de hacer esto se explica a continuación, mostrando cómo gl_get_line() logra atrapar señales de forma fiable alrededor de llamadas a funciones como read() y select() sin condiciones de

carrera.

La primera cosa que gl_get_line() hace, siempre que es llamada, es usar la función POSIX sigprocmask() para bloquear la entrega de todas las señales que actualmente está configurada para capturar. Esto es redundante si la aplicación ya las ha bloqueado, pero no hace ningún daño. Deshace este paso justo antes de

regresar.

Siempre que gl_get_line() necesite llamar a read() o select() para esperar entrada del usuario, primero llama a la función POSIX sigsetjmp(), asegurándose de especificar un valor distinto de cero para su argumento savesigs. La razón de este último argumento se aclarará en

breve.

Si sigsetjmp() devuelve cero, gl_get_line() luego hace lo

siguiente. 
a. Usa la función POSIX sigaction() para registrar
   un manejador de señales temporal para todas las señales que
   está configurada para capturar. Este manejador de señales hace dos
   cosas.
   1. Registra el número de la señal que fue recibida
      en una variable de ámbito de archivo.
   2. Luego llama a la función POSIX siglongjmp()
      usando el búfer que fue pasado a
      sigsetjmp() como su primer argumento, y
      un valor distinto de cero como su segundo argumento.
   Cuando este manejador de señales está registrado, el miembro sa_mask
   del argumento struct sigaction act de la
   llamada a sigaction() está configurado para contener todas
   de las señales que gl_get_line() está capturando. Esto
   asegura que solo una señal será capturada a la vez por
   nuestro manejador de señales, lo que a su vez asegura que múltiples
   instancias de nuestro manejador de señales no se interfieran entre sí.
b. Ahora que el manejador de señales ha sido configurado,
   gl_get_line() desbloquea todas las señales que
   está configurada para capturar.
c. Luego llama a las llamadas al sistema read() o select() para esperar entrada del teclado.
d. Si esta llamada al sistema regresa (es decir, no se recibe ninguna señal),
   gl_get_line() bloquea la entrega de las señales de
   interés de nuevo.
e. Luego restablece los manejadores de señales que fueron
   desplazados por el que acababa de
instalarse.

Alternativamente, si sigsetjmp() devuelve un valor distinto de cero, esto significa que una de las señales atrapadas fue capturada mientras se ejecutaban los pasos anteriores. Cuando esto ocurre, gl_get_line() hace lo

siguiente.

Primero, tenga en cuenta que cuando una llamada a siglongjmp() hace que sigsetjmp() retorne, siempre que el argumento savesigs de sigsetjmp() fuera distinto de cero, como se especificó anteriormente, la máscara de proceso de señales se restaura a cómo estaba cuando se llamó a sigsetjmp(). Esta es la diferencia importante entre sigsetjmp() y el antiguo y problemático setjmp(), y es el ingrediente esencial que hace posible evitar condiciones de carrera en el manejo de señales. Debido a esto, se garantiza que todas las señales que bloqueamos antes de llamar a sigsetjmp() estén bloqueadas de nuevo tan pronto como se capture cualquier señal. Las siguientes sentencias, que se ejecutan a continuación, se garantiza que se ejecutarán sin que se capturen más

señales.

1. Si así lo indica gl_get_line() la configuración
de atributos de la señal que fue capturada,
gl_get_line() restaura los atributos del terminal a
el estado que tenían cuando se llamó a gl_get_line(). Esto es particularmente importante para las señales que
suspenden o terminan el proceso, ya que de lo contrario el
terminal quedaría en un estado inutilizable.
2. A continuación, restablece los manejadores de señales de la

aplicación.

3. Luego usa la

función

raise() de la biblioteca estándar de C para reenviar a la aplicación la señal que
fue capturada.
3. A continuación, desbloquea la entrega de la señal que acabamos

de

enviar. Esto resulta en que la señal que fue enviada
recientemente
a través de raise(), sea capturada por el manejador de señales
original de la aplicación, que ahora puede manejarla como
considere

oportuno.

4. Si el manejador de señales retorna (es decir, no termina
el proceso), gl_get_line() bloquea la entrega de la
señal anterior de

nuevo.

5. Luego deshace cualquier acción realizada en el primero de los
pasos anteriores, y vuelve a mostrar la línea, si la configuración de la señal
lo

requiere.

6. gl_get_line() luego reanuda el intento de
leer un carácter, o se aborta, dependiendo de la
configuración de la señal que fue

capturada.

Lo que los pasos anteriores hacen en esencia es tomar señales entregadas de forma asíncrona y manejarlas de forma síncrona, una a la vez, en un punto del código donde gl_get_line() tiene control

total sobre s
u entorno.

EL TAMAÑO DEL

TERMINAL

En la mayoría de los sistemas, la combinación de la ioctl TIOCGWINSZ y la señal SIGWINCH se utiliza para mantener una idea precisa del tamaño del terminal. El tamaño del terminal se consulta cada vez que se llama a gl_get_line() y siempre que se recibe una señal

SIGWINCH.

En los pocos sistemas donde este mecanismo no está disponible, al inicio, new_GetLine() primero busca las variables de entorno LINES y COLUMNS. Si no se encuentran, o contienen valores inutilizables, entonces si está disponible una base de datos de información del terminal como terminfo o termcap, se busca el tamaño por defecto del terminal en esta base de datos. Si esto también falla para proporcionar el tamaño del terminal, se usa un tamaño por defecto de 80 columnas por 24

líneas.

Incluso en sistemas que sí soportan ioctl(TIOCGWINSZ), si el terminal está en el otro extremo de una línea serie, el controlador del terminal generalmente no tiene forma de detectar cuándo ocurre un redimensionamiento ni de consultar cuál es el tamaño actual. En tales casos, no se envía ningún SIGWINCH al proceso, y las dimensiones devueltas por ioctl(TIOCGWINSZ) no son correctas. La única manera de manejar tales instancias es proporcionar una forma para que el usuario ingrese un comando que le diga al sistema remoto cuál es el nuevo tamaño. Este comando entonces llamaría a la función gl_set_term_size() para informar a gl_get_line() sobre el cambio de

tamaño. 
  int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Los argumentos ncolumn y nline se utilizan para especificar las nuevas dimensiones del terminal, y no deben ser menores que 1. En sistemas que sí soportan ioctl(TIOCGWINSZ), esta función primero llama a ioctl(TIOCSWINSZ) para informar al controlador del terminal sobre el cambio en el tamaño. CONSULTAS DE UN SOLO

CARÁCTER

Usar gl_get_line() para consultar al usuario para una respuesta de un solo carácter, es inconveniente para el usuario, ya que debe presionar la tecla intro o retorno antes de que el carácter que escribió sea devuelto al programa. Por lo tanto, la función gl_query_char() ha sido proporcionada para consultas de un solo carácter como

esta. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Esta función muestra el prompt especificado al comienzo de una nueva línea, y espera a que el usuario escriba un carácter. Cuando el usuario escribe un carácter, gl_query_char() lo muestra a la derecha del prompt, inicia una nueva línea, y luego devuelve el carácter al programa llamante. El valor de retorno de la función es el carácter que fue escrito. Si la lectura tuvo que ser abortada por alguna razón, se devuelve EOF en su lugar. En el último caso, la aplicación puede llamar a la previamente documentada gl_return_status(), para averiguar qué salió mal. Esto podría, por ejemplo, haber sido la recepción de una señal, o el temporizador opcional de inactividad

activándose.

Si el usuario simplemente presiona intro, el valor del argumento defchar se sustituye. Esto significa que cuando el usuario presiona ya sea nueva línea o retorno, el carácter especificado en defchar, se muestra después del prompt, como si el usuario lo hubiera escrito, así como ser devuelto a la aplicación llamante. Si tal reemplazo no es importante, simplemente pase '0 como el valor de defchar

.

Si el carácter ingresado es un carácter no imprimible, se muestra simbólicamente. Por ejemplo, control-A se muestra como ^A, y los caracteres más allá de 127 se muestran en octal, precedidos por una barra

invertida.

Al igual que con gl_get_line(), el eco del carácter ingresado puede ser desactivado usando la función gl_echo_mode()

.

Si el proceso llamante es suspendido mientras espera a que el usuario escriba su respuesta, el cursor se mueve a la línea siguiente a la línea del prompt, luego cuando el proceso se reanuda, el prompt se vuelve a mostrar, y gl_query_char() reanuda la espera de que el usuario escriba un

carácter.

Tenga en cuenta que en el modo de servidor no bloqueante, (vea gl_io_mode(3)), si una línea de entrada incompleta está en proceso de ser leída cuando se llama a gl_query_char(), la línea de entrada parcial se descarta, y se borra del terminal, antes de que se muestre el nuevo prompt. La siguiente llamada a gl_get_line() por lo tanto come

nzará a editar
una nueva línea.

CRUDOS

Mientras que la función gl_query_char() pide visiblemente al usuario un carácter, y muestra lo que escribió, la función gl_read_char() lee un carácter del usuario, sin escribir nada en el terminal, o perturbar alguna línea de entrada incompletamente ingresada. Esto significa que puede ser llamada no solo desde entre llamadas a gl_get_line(), sino también desde funciones de retorno que la aplicación ha registrado para ser llamadas por gl_get_li

ne(). 
  int gl_read_char(GetLine *gl)
;

En caso de éxito, el valor de retorno de gl_read_char() es el carácter que fue leído. En caso de fallo, se devuelve EOF, y la función gl_return_status() puede ser llamada para averiguar qué salió mal. Las posibilidades incluyen el temporizador opcional de inactividad activándose, la recepción de una señal que está configurada para abortar gl_get_line(), o el bloqueo de E/S del terminal, cuando se está en el modo de E/S de servidor no

bloqueante.

Tenga en cuenta que ciertas teclas del teclado, como las teclas de función y las teclas de cursor, usualmente generan al menos 3 caracteres cada una, por lo que una sola llamada a gl_read_char() no gl_limit_history(3) — Arch Linux man pages

NAME

gl_limit_history, gl_erase_terminal, gl_display_text, gl_replace_prompt - limited history size, clearing the terminal, displaying text dynamically, customizing prompts

SYNOPSIS

#include <tecla.h>

int
gl_limit_history(GetLine *gl, size_t max_entries);

void
gl_erase_terminal(GetLine *gl);

int
gl_display_text(GetLine *gl, int indentation,
                const char *prefix,
                const char *suffix, int fill_char,
                int def_width, int start,
                const char *string);

void
gl_replace_prompt(GetLine *gl, const char *prompt);

DESCRIPTION

The gl_limit_history() function limits the number of entries that can be stored in the history list associated with gl to max_entries.

The gl_erase_terminal() function clears the terminal screen.

The gl_display_text() function is used to display paragraphs of text.

The gl_replace_prompt() function is used to change the prompt displayed by gl_get_line().

AN EXAMPLE

The following example demonstrates the use of these functions:

  #include <stdio.h>
  #include <tecla.h>

  int main(void) {
    GetLine *gl;
    const char *prompt = "Type something: ";
    char *line;

    gl = gl_new(prompt);
    if (gl == NULL) {
      perror("gl_new");
      return 1;
    }

    gl_limit_history(gl, 10); // Limit history to 10 entries
    gl_replace_prompt(gl, "New prompt: "); // Change the prompt

    gl_display_text(gl, 4, NULL, NULL, ' ', 80, 0,
                    "This is a sample text that will be displayed on the screen.");

    line = gl_get_line(gl);
    if (line) {
      printf("You entered: %s\n", line);
      free(line);
    }

    gl_destroy(gl);
    return 0;
  }

THE FUNCTIONS USED IN THE EXAMPLE

gl_new(3): Creates a new GetLine object.

gl_limit_history(3): Limits the number of history entries.

gl_replace_prompt(3): Replaces the current prompt with a new one.

gl_display_text(3): Displays text on the terminal.

gl_get_line(3): Reads a line of input from the user.

gl_destroy(3): Destroys a GetLine object.

THE RETURN STATUS OF GL_GET_LINE

The gl_get_line() function returns a pointer to a string containing the line read, or NULL if an error occurred or the user signaled an end-of-file. The returned string should be freed by the caller using free(3).

OPTIONAL PROMPT FORMATTING

The prompt string can contain special formatting sequences understood by gl_get_line(). For example, \%u will be replaced by the current username, and \%h by the hostname.

ALTERNATE CONFIGURATION SOURCES

In addition to the ~/.teclarc file, the GetLine module can also be configured using environment variables. For example, the TECLA_CONFIG_FILE environment variable can be used to specify an alternative configuration file.

CUSTOMIZED WORD COMPLETION

The word completion functionality of libtecla can be customized by providing your own completion functions. This is done by calling gl_install_completion() with a pointer to your completion function.

ADDING COMPLETION ACTIONS

You can add custom actions to be performed when a completion is selected. This is done by calling gl_add_completion_action() with a pointer to your action function.

DEFINING CUSTOM ACTIONS

Custom actions are functions that take a pointer to the GetLine object and a string representing the selected completion as arguments. They can be used to perform any desired action, such as inserting text into the input line or executing a command.

HISTORY FILES

By default, the history is not saved to a file. You can enable history file support by calling gl_set_history_file() with the desired filename.

MULTIPLE HISTORY LISTS

You can maintain multiple independent history lists by creating separate GetLine objects. Each object will have its own history list.

DISPLAYING HISTORY

The history list can be displayed by pressing the up or down arrow keys. You can also programmatically retrieve the history entries using gl_get_history_entry().

LOOKING UP HISTORY

You can search the history list for entries matching a given string using gl_lookup_history().

MANUAL HISTORY ARCHIVAL

You can manually save the current history list to a file using gl_write_history(), and load it back using gl_read_history().

MISCELLANEOUS HISTORY CONFIGURATION

Other history-related functions include gl_clear_history() to clear the history list, and gl_get_history_size() to get the current number of entries.

QUERYING HISTORY INFORMATION

You can query information about the history list, such as the maximum number of entries allowed using gl_get_history_limit(), and the current number of entries using gl_get_history_size().

CHANGING TERMINALS

If your program needs to interact with multiple terminals, you can change the terminal associated with a GetLine object using gl_set_terminal().

EXTERNAL EVENT HANDLING

In non-blocking server-I/O mode, libtecla can be integrated with an external event loop. The function gl_check_events() can be used to check for pending events and process them.

SETTING AN INACTIVITY TIMEOUT

You can set an inactivity timeout for input operations using gl_set_timeout(). If no input is received within the specified timeout period, gl_get_line() will return NULL.

SIGNAL HANDLING DEFAULTS

libtecla installs default signal handlers for common signals like SIGINT and SIGQUIT to ensure graceful termination and cleanup. These defaults can be modified or disabled.

CUSTOMIZED SIGNAL HANDLING

You can install your own signal handlers by calling gl_install_signal_handler(). This allows you to define custom behavior when specific signals are received.

RELIABLE SIGNAL HANDLING

For more robust signal handling, especially in multi-threaded applications, consider using the reentrant versions of the library functions and ensuring your signal handlers are safe for use in signal contexts.

THE TERMINAL SIZE

The terminal size (width and height) is automatically detected and updated. You can query the current terminal width using gl_get_terminal_width().

HIDING WHAT YOU TYPE

To hide user input, for example when entering passwords, you can call gl_set_echo() with a value of 0.

SINGLE CHARACTER QUERIES

The function gl_get_char() can be used to read a single character from the input, without waiting for a newline. This function also respects the echo setting.

  int gl_get_char(GetLine *gl);

Note that this function may not be sufficient to identify such keystrokes.

CLEARING THE TERMINAL

The calling program can clear the terminal by calling gl_erase_terminal(). In non-blocking server-I/O mode, this function also arranges for the current input line to be redrawn from scratch when gl_get_line() is next called.

  int gl_erase_terminal(GetLine *gl);

DISPLAYING TEXT DYNAMICALLY

Between calls to gl_get_line(), the gl_display_text() function provides a convenient way to display paragraphs of text, left-justified and split over one or more terminal lines according to the constraints of the current width of the terminal. Examples of the use of this function may be found in the demo programs, where it is used to display introductions. In those examples the advanced use of optional prefixes, suffixes and filled lines to draw a box around the text is also illustrated.

  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string);

If gl isn't currently connected to a terminal, for example if the output of a program that uses gl_get_line() is being piped to another program or redirected to a file, then the value of the def_width parameter is used as the terminal width.

The indentation argument specifies the number of characters to use to indent each line of ouput. The fill_char argument specifies the character that will be used to perform this indentation.

The prefix argument can either be NULL, or be a string to place at the beginning of each new line (after any indentation). Similarly, the suffix argument can either be NULL, or be a string to place at the end of each line. The suffix is placed flush against the right edge of the terminal, and any space between its first character and the last word on that line is filled with the character specified via the fill_char argument. Normally the fill-character is a space.

The start argument tells gl_display_text() how many characters have already been written to the current terminal line, and thus tells it the starting column index of the cursor. Since the return value of gl_display_text() is the ending column index of the cursor, by passing the return value of one call to the start argument of the next call, a paragraph that is broken between more than one string can be composed by calling gl_display_text() for each successive portion of the paragraph. Note that literal newline characters are necessary at the end of each paragraph to force a new line to be started.

On error, gl_display_text() returns -1.

CALLBACK FUNCTION FACILITIES

Unless otherwise stated, callback functions, such as tab completion callbacks and event callbacks should not call any functions in this module. The following functions, however, are designed specifically to be used by callback functions.

Calling the gl_replace_prompt() function from a callback tells gl_get_line() to display a different prompt when the callback returns. Except in non-blocking server mode, it has no effect if used between calls to gl_get_line(). In non-blocking server mode (see the gl_io_mode(3) man page, when used between two calls to gl_get_line() that are operating on the same input line, the current input line will be re-drawn with the new prompt on the following call to gl_get_line().

  void gl_replace_prompt(GetLine *gl, const char *prompt);

INTERNATIONAL CHARACTER SETS

Since libtecla version 1.4.0, gl_get_line() has been 8-bit clean. This means that all 8-bit characters that are printable in the user's current locale are now displayed verbatim and included in the returned input line. Assuming that the calling program correctly contains a call like the following,

  setlocale(LC_CTYPE, "");

then the current locale is determined by the first of the environment variables LC_CTYPE, LC_ALL, and LANG, that is found to contain a valid locale name. If none of these variables are defined, or the program neglects to call setlocale, then the default C locale is used, which is US 7-bit ASCII. On most unix-like platforms, you can get a list of valid locales by typing the command:

  locale -a

at the shell prompt. Further documentation on how the user can make use of this to enter international characters can be found in the tecla(7) man page.

THREAD SAFETY

In a multi-threaded program, you should use the libtecla_r.a version of the library. This uses reentrant versions of system functions, where available. Unfortunately neither terminfo nor termcap were designed to be reentrant, so you can't safely use the functions of the getline module in multiple threads (you can use the separate file-expansion and word-completion modules in multiple threads, see the corresponding man pages for details). However due to the use of POSIX reentrant functions for looking up home directories etc, it is safe to use this module from a single thread of a multi-threaded program, provided that your other threads don't use any termcap or terminfo functions.
