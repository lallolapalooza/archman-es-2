función gl_get_line() es parte de la biblioteca tecla (véase la página man libtecla(3)). Si el usuario está escribiendo en un terminal, cada llamada le solicita una línea de entrada, y luego proporciona instalaciones de edición interactivas, similares a las del shell tcsh de unix. Además de la edición de línea de comandos simple, admite el recuerdo de líneas de comandos introducidas previamente, la completación con TAB de nombres de archivos y la expansión en línea de comodines de nombres de archivos. La documentación de las características de edición de línea de comandos a nivel de usuario y de todas las opciones de configuración del usuario se puede encontrar en la página man tecla(7). Esta página man se ocupa de la documentación para programadores interesados en usar esta biblioteca en su aplicación. UN E

La función gl_get_line() puede ser llamada cualquier número de veces para leer entrada del usuario. El argumento gl debe haber sido previamente devuelto por una llamada a new_GetLine(). El argumento prompt debe ser una cadena normal terminada en NUL, especificando el prompt a presentar al usuario. Por defecto los prompts se muestran literalmente, pero si se habilitan con la función gl_prompt_style() (véase más adelante), los prompts pueden contener directivas para subrayar, cambiar a y de fuentes en negrita, o activar y desactivar el

resaltado.

Si desea especificar los contenidos iniciales de la línea, para que el usuario la edite, pase la cadena deseada a través del argumento start_line. Luego puede especificar en qué carácter de esta línea se posiciona inicialmente el cursord over, utilizando el argumento start_pos. Este debe ser -1 si desea que el cursor siga al último carácter de la línea de inicio. Si no desea pre-cargar la línea de esta manera, envíe start_line como NULL y establezca start_pos en -1. Tenga en cuenta que el puntero de línea devuelto por una llamada a gl_get_line() puede pasarse a la siguiente llamada a gl_get_line() a través de start_line. Esto permite que la aplicación tome la última línea introducida y, si contiene un error, la presente nuevamente al usuario para volver a editarla, con el cursor inicialmente posicionado donde se encontró el error.

La función gl_get_line() devuelve un puntero a la línea introducida por el usuario, o NULL en caso de error o al final de la entrada. El puntero devuelto es parte del objeto de recurso gl especificado y, por lo tanto, el llamador no debe liberarlo ni asumir que es inmutable de una llamada a la siguiente. Al leer de un usuario en una terminal, siempre habrá un carácter de nueva línea al final de la línea devuelta. Cuando la entrada estándar se toma de una tubería o un archivo, similarmente habrá una nueva línea a menos que la línea de entrada fuera demasiado larga para almacenarla en el búfer interno. En este último caso, debe llamar a gl_get_line() nuevamente para leer el resto de la línea. Tenga en cuenta que este comportamiento hace que gl_get_line() sea similar a fgets(). De hecho, cuando stdin no está conectado a una terminal, gl_get_line() simplemente llama a fgets().

FUENTES DE CONFIGURACION ALTERNATIVAS

Como se mencionó anteriormente, por defecto los usuarios tienen la opción de configurar el comportamiento de gl_get_line() a través de un archivo de configuración llamado .teclarc en sus directorios personales. El hecho de que todas las aplicaciones compartan este mismo archivo de configuración es una ventaja y una desventaja. En la mayoría de los casos es una ventaja, ya que fomenta la uniformidad y libera al usuario de tener que configurar cada aplicación por separado. Sin embargo, en algunas aplicaciones, este único medio de configuración es un problema. Esto es particularmente cierto en el software embebido, donde no hay un sistema de archivos para leer un archivo de configuración, y también en aplicaciones donde se necesita una elección radicalmente diferente de enlaces de teclas para emular una interfaz de teclado heredada. Para atender tales casos, la siguiente función permite a la aplicación controlar de dónde se leen las informaciones de configuración.

  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file);

Permite que los comandos de configuración que normalmente se leerían del archivo ~/.teclarc del usuario, se lean de cualquiera o ninguna de las siguientes opciones: una cadena, un archivo de configuración específico de la aplicación y/o un archivo de configuración específico del usuario. Si esta función se llama antes de la primera llamada a gl_get_line(), el comportamiento predeterminado de leer ~/.teclarc en la primera llamada a gl_get_line() se deshabilita, por lo que toda la configuración debe lograrse utilizando las fuentes de configuración especificadas con esta función.

Si app_string != NULL, entonces se interpreta como una cadena que contiene uno o más comandos de configuración, separados entre sí en la cadena por caracteres de nueva línea incrustados. Si app_file != NULL, entonces se interpreta como la ruta completa de un archivo de configuración específico de la aplicación. Si user_file != NULL, entonces se interpreta como la ruta completa de un archivo de configuración específico del usuario, como ~/.teclarc. Por ejemplo, en la siguiente llamada,

  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc");

el argumento app_string hace que la aplicación llamante comience en modo de edición vi, en lugar del modo emacs predeterminado, y desactiva el uso de la campana de la terminal por parte de la biblioteca. Luego intenta leer comandos de configuración a nivel de sistema de un archivo opcional llamado /usr/share/myapp/teclarc, y finalmente lee comandos de configuración específicos del usuario de un archivo .teclarc opcional en el directorio personal del usuario. Tenga en cuenta que los argumentos se enumeran en orden ascendente de prioridad, y el contenido de app_string puede ser anulado por comandos en app_file, y los comandos en app_file pueden ser anulados por comandos en user_file.

Puede llamar a esta función tantas veces como sea necesario, y los resultados serán acumulativos, pero tenga en cuenta que las copias de los nombres de archivo especificados a través de la argumento ap

p_file y user_file se registran internamente para su uso posterior por la función de enlace de teclas read-init-files, así que si planea llamar a esta función varias veces, asegúrese de que la última llamada especifique los nombres de archivo que desea volver a leer cuando el usuario solicite que los archivos de configuración se

relean.

     versátil, implica asumir algunas

RELIABLE SIGNAL HANDLING

Signal handling is surprisingly hard to do reliably without race conditions. In gl_get_line(), a lot of care has been taken to allow applications to perform reliable signal handling around gl_get_line(). This section explains how to make use of this.

As an example of the problems that can arise if the application isn't written correctly, imagine that one's application has a SIGINT signal handler that sets a global flag. Now suppose that the application tests this flag just before invoking gl_get_line(). If a SIGINT signal happens to be received in the small window of time between the statement that tests the value of this flag, and the statement that calls gl_get_line(), then gl_get_line() will not see the signal, and will not be interrupted. As a result, the application won't be able to respond to the signal until the user gets around to finishing entering the input line and gl_get_line() returns. Depending on the application, this might or might not be a disaster, but at the very least it would puzzle the user.

The way to avoid such problems is to do the following.

1. If needed, use the gl_trap_signal() function to configure gl_get_line() to abort when important signals are caught.

2. Configure gl_get_line() such that if any of the signals that it catches are blocked when gl_get_line() is called, they will be unblocked automatically during times when gl_get_line() is waiting for I/O. This can be done either on a per signal basis, by calling the gl_trap_signal() function, and specifying the GLS_UNBLOCK attribute of the signal, or globally by calling the gl_catch_blocked() function.

     void gl_catch_blocked(GetLine *gl);

This function simply adds the GLS_UNBLOCK attribute to all of the signals that it is currently configured to trap.

3. Just before calling gl_get_line(), block delivery of all of the signals that gl_get_line() is configured to trap. This can be done using the POSIX sigprocmask() function in conjunction with the gl_list_signals() function.

      int gl_list_signals(GetLine *gl, sigset_t *set);

This function returns the set of signals that it is currently configured to catch in the set argument, which is in the form required by sigprocmask().

4. In the example, one would now test the global flag that the signal handler sets, knowing that there is now no danger of this flag being set again until gl_get_line() unblocks its signals while performing I/O.

5. Eventually gl_get_line() returns, either because a signal was caught, an error occurred, or the user finished entering their input line.

6. Now one would check the global signal flag again, and if it is set, respond to it, and zero the flag.

7. Use sigprocmask() to unblock the signals that were blocked in step 3.

The same technique can be used around certain POSIX signal-aware functions, such as sigsetjmp() and sigsuspend(), and in particular, the former of these two functions can be used in conjunction with siglongjmp() to implement race-condition free signal handling around other long-running system calls. The way to do this is explained next, by showing how gl_get_line() manages to reliably trap signals around calls to functions like read() and select() without race conditions.

The first thing that gl_get_line() does, whenever it is called, is to use the POSIX sigprocmask() function to block the delivery of all of the signals that it is currently configured to catch. This is redundant if the application has already blocked them, but it does no harm. It undoes this step just before returning.

Whenever gl_get_line() needs to call read() or select() to wait for input from the user, it first calls the POSIX sigsetjmp() function, being sure to specify a non-zero value for its savesigs argument. The reason for the latter argument will become clear shortly.

If sigsetjmp() returns zero, gl_get_line() then does the following.

a. It uses the POSIX sigaction() function to register
   a temporary signal handler to all of the signals that it
   is configured to catch. This signal handler does two
   things.
   1. It records the number of the signal that was received
      in a file-scope variable.
   2. It then calls the POSIX siglongjmp()
      function using the buffer that was passed to
      sigsetjmp() for its first argument, and
      a non-zero value for its second argument.
   When this signal handler is registered, the sa_mask
   member of the struct sigaction act argument of the
   call to sigaction() is configured to contain all of
   the signals that gl_get_line() is catching. This
   ensures that only one signal will be caught at once by
   our signal handler, which in turn ensures that multiple
   instances of our signal handler don't tread on each
   other's toes.
b. Now that the signal handler has been set up,
   gl_get_line() unblocks all of the signals that it
   is configured to catch.
c. It then calls the read() or select() system

d. If this system call returns (ie. no signal is received),
   gl_get_line() blocks delivery of the signals of
   interest again.
e. It then reinstates the signal handlers that were
   displaced by the one that was just installed.

Entre las llamadas a gl_get_line(), la función gl_display_text() proporciona una manera conveniente de mostrar párrafos de texto, justificados a la izquierda y divididos en una o más líneas de la terminal de acuerdo con las restricciones del ancho actual de la terminal. terminal.

El argumento indentation especifica el número de caracteres a usar para sangrar cada línea de salida. El argumento fill_char especifica el carácter que se usará para realizar esta

El argumento prefix puede ser NULL, o una cadena de texto a colocar al comienzo de cada nueva línea (después de cualquier sangría). De manera similar, el argumento suffix puede ser NULL, o una cadena de texto a colocar al final de cada línea. espacio.

Desde la versión 1.4.0 de libtecla, gl_get_line() ha sido compatible con 8 bits. Esto significa que todos los caracteres de 8 bits que son imprimibles en el locale actual del usuario ahora se muestran literalmente y se incluyen en la línea de entrada devuelta. HILOS

En un programa multi-hilo, debe usar la versión libtecla_r.a de la biblioteca. Esta usa versiones reentrantes de las funciones del sistema, cuando están disponibles. Desafortunadamente, ni terminfo ni termcap fueron diseñados para ser reentrantes, por lo q

ue no puede usar de forma segura las funciones del módulo getline en múltiples hilos (puede usar los módulos separados de expansión de archivos y completado de palabras en múltiples hilos, vea las páginas de manual correspondientes para más detalles). Sin
