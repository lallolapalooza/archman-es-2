GL_GET_LINE

The gl_get_line() function reads a line of input from the user. A line is terminated by the carriage return key. The line is returned as a null-terminated string. The user may edit the line before terminating it by using the standard editing functions provided by the library. Optionally, the application can specify a prompt string to be displayed to the user before the line is read.

  char *gl_get_line(GetLine *gl, const char *prompt);

The gl argument is a pointer to the GetLine resource object that was returned by the gl_init() function. The prompt argument is a pointer to a null-terminated string, which is displayed to the user. If prompt is NULL, no prompt is displayed. The application can specify a line to be pre-loaded into the input buffer by passing a non-NULL value for start_line and an integer for start_pos. If start_line is a pointer to a valid line string, and start_pos is a valid character offset into that string, then the string will be loaded into the input buffer and the cursor will be positioned at that offset. If start_pos is -1, then the cursor will be positioned at the end of the line. If you don't wish to preload the line, send start_line as NULL, and set start_pos to -1. Note that the line pointer returned by one call to gl_get_line() can be passed back to the next call to gl_get_line() via the start_line. This allows the application to take the last entered line, and if it contains an error, to then present it back to the user for re-editing, with the cursor initially positioned where the error was encountered.

The gl_get_line() function returns a pointer to the line entered by the user, or NULL on error or at the end of the input. The returned pointer is part of the specified gl resource object, and thus should not be free'd by the caller, or assumed to be unchanging from one call to the next. When reading from a user at a terminal, there will always be a newline character at the end of the returned line. When standard input is being taken from a pipe or a file, there will similarly be a newline unless the input line was too long to store in the internal buffer. In the latter case you should call gl_get_line() again to read the rest of the line. Note that this behavior makes gl_get_line() similar to fgets(). In fact when stdin isn't connected to a terminal,gl_get_line() just calls fgets().

FUENTES DE CONFIGURACIÓN ALTERNATIVAS

As mentioned above, by default users have the option of configuring the behavior of gl_get_line() via a configuration file called .teclarc in their home directories. The fact that all applications share this same configuration file is both an advantage and a disadvantage. In most cases it is an advantage, since it encourages uniformity, and frees the user from having to configure each application separately. In some applications, however, this single means of configuration is a problem. This is particularly true of embedded software, where there's no filesystem to read a configuration file from, and also in applications where a radically different choice of keybindings is needed to emulate a legacy keyboard interface. To cater for such cases, the following function allows the application to control where configuration information is read from.

  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file);

It allows the configuration commands that would normally be read from a user's ~/.teclarc file, to be read from any or none of, a string, an application specific configuration file, and/or a user-specific configuration file. If this function is called before the first call to gl_get_line(), the default behavior of reading ~/.teclarc on the first call to gl_get_line() is disabled, so all configuration must be achieved using the configuration sources specified with this function.

If app_string != NULL, then it is interpreted as a string containing one or more configuration commands, separated from each other in the string by embedded newline characters. If app_file != NULL then it is interpreted as the full pathname of an application-specific configuration file. If user_file != NULL then it is interpreted as the full pathname of a user-specific configuration file, such as ~/.teclarc. For example, in the following call,

  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc");

the app_string argument causes the calling application to start in vi edit-mode, instead of the default emacs mode, and turns off the use of the terminal bell by the library. It then attempts to read system-wide configuration commands from an optional file called /usr/share/myapp/teclarc, then finally reads user-specific configuration commands from an optional .teclarc file in the user's home directory. Note that the arguments are listed in ascending order of priority, with the contents of app_string being potentially overriden by commands in app_file, and commands in app_file potentially being overriden by commands in user_file.

You can call this function as many times as needed, the results being cumulative, but note that copies of any filenames specified via the

los argumentos app_file y user_file se registran internamente para su uso posterior por parte de la función de enlace de teclas read-init-files, así que si planea llamar a esta función varias veces, asegúrese de que la última llamada especifique los nombres de archivo que desea volver a leer cuando el usuario solicite que los archivos de configuración se

relean.

entrada.

DEFINIENDO ACCIONES

PERSONALIZADAS

Aunque las acciones de enlace de teclas incorporadas son suficientes para las necesidades de la mayoría de las aplicaciones, ocasionalmente una aplicación especializada puede necesitar definir una o más acciones personalizadas, vinculadas a secuencias de teclas específicas de la aplicación. Por ejemplo, una aplicación de ventas se beneficiaría de tener una secuencia de teclas que mostrara el nombre de la pieza que correspondiera a un número de pieza que precede al cursor. Tal característica está claramente fuera del alcance de las funciones de acción incorporadas. Así que para tales casos especiales, se proporciona la función gl_register_action()

. 
  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq)
;

Esta función permite a la aplicación registrar una función externa, fn, que a partir de entonces se llamará cada vez que se introduzca la secuencia de teclas especificada, keyseq, por parte del usuario, o cuando el usuario introduzca cualquier otra secuencia de teclas que el usuario vincule posteriormente al nombre de acción especificado, name, en su archivo de configuración. El argumento data puede ser un puntero a cualquier cosa que la aplicación desee que se pase a la función de acción, fn, cada vez que se invoque esa

función.

La función de acción, fn, debe declararse utilizando la siguiente macro, que está definida en libtecl

a.h. 
  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char
*line)

Los argumentos gl y data son aquellos que se pasaron previamente a gl_register_action() cuando se registró la función de acción. El argumento count es un argumento numérico que el usuario tiene la opción de introducir utilizando la acción de argumento numérico, antes de invocar la acción. Si el usuario no introduce un número, entonces el argumento count se establece en 1. Nominalmente, este argumento se interpreta como un conteo de repetición, lo que significa que la acción debe repetirse esa cantidad de veces. En la práctica, sin embargo, para algunas acciones un conteo de repetición tiene poco sentido. En tales casos, las acciones pueden simplemente ignorar el argumento count o usar su valor para un propósito

diferente.

Se pasa una copia de la línea de entrada actual en el argumento de solo lectura line. La posición actual del cursor dentro de esta cadena se indica mediante el índice contenido en el argumento curpos. Tenga en cuenta que no se permite la manipulación directa de la línea de entrada y la posición del cursor. Esto se debe a que las reglas dictadas por varios modos, como el modo vi frente al modo emacs, el modo sin eco, y el modo de inserción frente al modo de sobrescritura, etc., hacen que sea demasiado compleo para un programador de aplicaciones escribir una acción de edición conforme, así como restringen cambios futuros en los internos de gl_get_line(). Una solución potencial a este dilema sería permitir a la función de acción editar la línea utilizando las acciones de edición existentes. Esto está actualmente bajo

consideración.

Si la función de acción desea escribir texto en la terminal, sin que esto se mezcle con el texto mostrado de la línea de entrada, o leer de la terminal sin tener que manejar la E/S cruda de la terminal, entonces antes de realizar cualquiera de estas operaciones, debe suspender temporalmente la edición de línea llamando a la función gl_normal_io(). Esta función vacía cualquier salida pendiente a la terminal, mueve el cursor al inicio de la línea que sigue a la última línea de terminal de la línea de entrada, y luego restaura la terminal a un estado que es adecuado para su uso con las instalaciones de stdio de C. Lo último incluye cosas como restaurar la asignación normal de \n a \r\n, y, cuando está en modo servidor, restaurar la forma normal de bloqueo de la E/S de la terminal. Después de haber llamado a esta función, la acción puede leer de y escribir en la terminal sin temor de crear un desorden. No es necesario que la función de acción restaure el entorno de edición original antes de regresar. Esto lo hace automáticamente gl_get_line() después de que la función de acción regrese. Lo siguiente es un ejemplo sencillo de una función de acción que escribe la frase "Hello world" en una nueva línea de terminal después de la línea que se está editando. Cuando esta función regresa, la línea de entrada se redibuja en la línea que sigue a la línea "Hello world", y la edición de línea se

Esto les permite reasociar la acción a una secuencia de teclas alternativa. entrada.

ignora en

FIABLE

El manejo de señales es sorprendentemente difícil de hacer de forma fiable sin condiciones de carrera. En gl_get_line() se ha tenido mucho cuidado para permitir que las aplicaciones realicen un manejo de señales fiable alrededor de gl_get_line(). Esta sección explica cómo hacer uso de

esto.

Como ejemplo de los problemas que pueden surgir si la aplicación no está escrita correctamente, imagine que su aplicación tiene un manejador de señales SIGINT que establece un indicador global. Ahora suponga que la aplicación prueba este indicador justo antes de invocar gl_get_line(). Si una señal SIGINT resulta recibida en la pequeña ventana de tiempo entre la sentencia que prueba el valor de este indicador y la sentencia que llama a gl_get_line(), entonces gl_get_line() no verá la señal y no será interrumpida. Como resultado, la aplicación no podrá responder a la señal hasta que el usuario termine de ingresar la línea de entrada y gl_get_line() regrese. Dependiendo de la aplicación, esto podría o no ser un desastre, pero al menos confundiría al

usuario.

siguiente.

señales

importantes.

breve.

   instancias de nuestro manejador de señales no interfieran entre sí.

Una de las señales que se estaba capturando fue detectada mientras los pasos anteriores se estaban ejecutando. Cuando esto sucede, gl_get_line() hace lo siguiente.

Primero, tenga en cuenta que cuando una llamada a siglongjmp() hace que sigsetjmp() retorne, siempre que el argumento savesigs de sigsetjmp() no fuera cero, como se especificó anteriormente, la máscara de proceso de señales se restaura a cómo estaba cuando se llamó a sigsetjmp(). Esta es la diferencia importante entre sigsetjmp() y la antigua y problemática setjmp(), y es el ingrediente esencial que hace posible evitar las condiciones de carrera en el manejo de señales. Debido a esto, se garantiza que todas las señales que bloqueamos antes de llamar a sigsetjmp() vuelven a estar bloqueadas tan pronto como se captura alguna señal. Las siguientes sentencias, que se ejecutan entonces, se garantiza que se ejecutan sin capturar ninguna señal adicional.

1. Si se indica por los atributos de configuración de
gl_get_line() de la señal que se capturó,
gl_get_line() restaura los atributos de la terminal al
estado que tenían cuando se llamó a
gl_get_line(). Esto es particularmente importante para las señales que
suspenden o terminan el proceso, ya que de lo contrario la
terminal quedaría en un estado inutilizable.

2. Luego, reinstala los manejadores de señales de la aplicación.

3. Luego utiliza la función raise() de la biblioteca estándar de C
para reenviar la señal capturada a la aplicación.

3. A continuación, desbloquea la entrega de la señal que acabamos de
enviar. Esto da como resultado que la señal que se acaba de enviar
a través de raise() sea capturada por el manejador de señales original
de la aplicación, que ahora puede manejarla como considere oportuno.

4. Si el manejador de señales retorna (es decir, no termina
el proceso), gl_get_line() vuelve a bloquear la entrega de la
señal anterior.

5. Luego deshace cualquier acción realizada en el primer paso
de los anteriores, y redibuja la línea, si la configuración de la señal
así lo requiere.

6. gl_get_line() reanuda el intento de leer un carácter o
aborta, dependiendo de la configuración de la señal capturada.

Lo que hacen los pasos anteriores en esencia es tomar señales entregadas asíncronamente y manejarlas síncronamente, una a la vez, en un punto del código donde gl_get_line() tiene control total sobre su entorno.

EL TAMAÑO DE LA TERMINAL

En la mayoría de los sistemas, la combinación del ioctl TIOCGWINSZ y la señal SIGWINCH se utiliza para mantener una idea precisa del tamaño de la terminal. El tamaño de la terminal se consulta cada vez que se llama a gl_get_line() y cada vez que se recibe una señal SIGWINCH.

En los pocos sistemas donde este mecanismo no está disponible, al inicio new_GetLine() primero busca las variables de entorno LINES y COLUMNS. Si estas no se encuentran, o contienen valores inútiles, entonces si una base de datos de información de terminal como terminfo o termcap está disponible, se busca el tamaño predeterminado de la terminal en esta base de datos. Si esto también falla en proporcionar el tamaño de la terminal, se utiliza un tamaño predeterminado de 80 columnas por 24 líneas.

Incluso en sistemas que admiten ioctl(TIOCGWINSZ), si la terminal está en el otro extremo de una línea serial, el controlador de terminal generalmente no tiene forma de detectar cuándo ocurre un redimensionamiento o de consultar cuál es el tamaño actual. En tales casos, no se envía SIGWINCH al proceso y las dimensiones devueltas por ioctl(TIOCGWINSZ) no son correctas. La única forma de manejar tales instancias es proporcionar una manera para que el usuario ingrese un comando que le diga al sistema remoto cuál es el nuevo tamaño. Este comando luego llamaría a la función gl_set_term_size() para informar a gl_get_line() sobre el cambio de tamaño.

  int gl_set_term_size(GetLine *gl, int ncolumn, int nline);

Los argumentos ncolumn y nline se utilizan para especificar las nuevas dimensiones de la terminal y no deben ser menores que 1. En sistemas que admiten ioctl(TIOCGWINSZ), esta función llama primero a ioctl(TIOCSWINSZ) para informar al controlador de terminal sobre el cambio de tamaño. En modo de servidor de E/S no bloqueante, si se está ingresando una línea actualmente, la línea de entrada se redibuja para adaptarse al tamaño cambiado. Finalmente, los nuevos valores se registran en gl para su uso futuro por gl_get_line().

La función gl_terminal_size() le permite consultar el tamaño actual de la terminal e instalar un tamaño de respaldo alternativo para casos en los que el tamaño no está disponible. Tenga en cuenta que el tamaño de la terminal no estará disponible si se lee desde una tubería o un archivo, por lo que los valores predeterminados pueden ser importantes incluso en sistemas que admiten formas de conocer el tamaño de la terminal.

  typedef struct {
    int nline;        /* La terminal tiene nline líneas */
    int ncolumn;      /* La terminal tiene ncolumn columnas */
  } GlTerminalSize;
  GlTerminalSize gl_terminal_size(GetLine *gl,
                                  int def_ncolumn,
                                  int def_nline);

Esta función primero actualiza las dimensiones de terminal de respaldo de gl_get_line(), luego registra sus hallazgos en el valor de retorno.

def_ncolumn y def_nline especifican el número predeterminado de columnas y líneas de terminal a usar si el tamaño de la terminal no se puede determinar a través de ioctl(TIOCGWINSZ) o variables de entorno.

OCULTAR LO QUE ESCRIBES

Al ingresar información confidencial, como contraseñas, es mejor no tener el texto que se está ingresando reflejado en la terminal. Además, dicho texto no debe registrarse en la lista de historial, ya que alguien que encuentre su terminal desatendida podría recordarlo, o alguien que husmee en sus directorios podría verlo en su archivo de historial. Teniendo esto en cuenta, la función gl_echo_mode() le permite activar y desactivar la visualización y el archivo de cualquier texto que se ingrese posteriormente en las llamadas a gl_get_line().

  int gl_echo_mode(GetLine *gl, int enable);

El argumento enable especifica si el texto ingresado debe ser visible o no. Si es 0, entonces las líneas ingresadas posteriormente no serán visibles en la terminal y no se registrarán en la lista de historial. Si es 1, entonces las líneas de entrada posteriores se mostrarán a medida que se ingresan y, siempre que el historial no se haya deshabilitado mediante una llamada a gl_toggle_history(), también se archivarán en la lista de historial. Finalmente, si el argumento enable es -1, el modo de eco se deja sin cambios, lo que le permite consultar de forma no destructiva la configuración actual a través del valor de retorno. En todos los casos, el valor de retorno de la función es 0 si el eco se deshabilitó antes de llamar a la función, y 1 si estaba habilitado.

Cuando el eco está desactivado, tenga en cuenta que aunque la finalización con tabulador completará invisiblemente su prefijo tanto como sea posible, las completaciones ambiguas no se mostrarán.

CONSULTAS DE UN SOLO CARÁCTER

Usar gl_get_line() para solicitar al usuario una respuesta de un solo carácter es inconveniente para el usuario, ya que debe presionar la tecla enter o return antes de que el carácter que escribió sea devuelto al programa. Por lo tanto, la función gl_query_char() se ha proporcionado para consultas de un solo carácter como esta.

  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar);

Esta función muestra el prompt especificado al inicio de una nueva línea y espera a que el usuario escriba un carácter. Cuando el usuario escribe un carácter, gl_query_char() lo muestra a la derecha del prompt, inicia una nueva línea y luego devuelve el carácter al programa que llama. El valor de retorno de la función es el carácter que se escribió. Si la lectura tuvo que abortarse por alguna razón, se devuelve EOF en su lugar. En este último caso, la aplicación puede llamar a gl_return_status(), documentado previamente, para averiguar qué salió mal. Esto podría haber sido, por ejemplo, la recepción de una señal, o la expiración del temporizador de inactividad opcional.

Si el usuario simplemente presiona enter, se sustituye el valor del argumento defchar. Esto significa que cuando el usuario presiona newline o return, el carácter especificado en defchar se muestra después del prompt, como si el usuario lo hubiera escrito, y también se devuelve a la aplicación que llama. Si tal reemplazo no es importante, simplemente pase '0 como valor de defchar.

Si el carácter ingresado es un carácter no imprimible, se muestra simbólicamente. Por ejemplo, control-A se muestra como ^A, y los caracteres mayores que 127 se muestran en octal, precedidos por una barra invertida.

Al igual que con gl_get_line(), el eco del carácter ingresado se puede deshabilitar usando la función gl_echo_mode().

Si el proceso que llama se suspende mientras espera que el usuario escriba su respuesta, el cursor se mueve a la línea siguiente a la línea del prompt, luego cuando el proceso se reanuda, se vuelve a mostrar el prompt y gl_query_char() reanuda la espera a que el usuario escriba un carácter.

Tenga en cuenta que en el modo de servidor no bloqueante (ver gl_io_mode(3)), si una línea de entrada incompleta está en proceso de lectura cuando se llama a gl_query_char(), la línea de entrada parcial se descarta y se borra de la terminal antes de mostrar el nuevo prompt. La próxima llamada a gl_get_line() comenzará a editar una nueva línea.

LECTURA DE CARACTERES EN BRUTO

Mientras que la función gl_query_char() muestra visiblemente un prompt al usuario para obtener un carácter y muestra lo que escribió, la función gl_read_char() lee un carácter de señal del usuario, sin escribir nada en la terminal ni perturbar ninguna línea de entrada incompleta. Esto significa que se puede llamar no solo desde entre llamadas a gl_get_line(), sino también desde funciones de devolución de llamada que la aplicación ha registrado para ser llamadas por gl_get_line().

  int gl_read_char(GetLine *gl);

En caso de éxito, el valor de retorno de gl_read_char() es el carácter leído. En caso de fallo, se devuelve EOF y se puede llamar a la función gl_return_status() para averiguar qué salió mal. Las posibilidades incluyen la expiración del temporizador de inactividad opcional, la recepción de una señal configurada para abortar gl_get_line(), o un bloqueo de E/S de terminal, cuando está en modo de servidor de E/S no bloqueante.

Desde la versión 1.4.0 de libtecla, gl_get_line() ha sido 8-bit limpio. Esto significa que todos los caracteres de 8 bits que son imprimibles en la configuración regional actual del usuario ahora se muestran literalmente y se incluyen en la línea de entrada devuelta. SEGURIDAD DE

HILOS

En un programa multi-hilo, debe usar la versión libtecla_r.a de la biblioteca. Esta usa versiones reentrantes de las funciones del sistema, donde están disponibles. Desafortunadamente, ni terminfo ni termcap fueron diseñados para ser reentrantes, por lo

que no puede usar de forma segura las funciones del módulo getline en múltiples hilos (puede usar los módulos separados de expansión de archivos y completado de palabras en múltiples hilos, vea las páginas de manuales correspondientes para más detalles).
Sin embargo, debido al uso de funciones reentrantes POSIX para buscar directorios de inicio de sesión, etc., es seguro usar este módulo desde un solo hilo de un programa multi-hilo, siempre que sus otros hilos no usen ninguna función termcap o terminfo.
