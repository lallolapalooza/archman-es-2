DESCRIPCIÓ

N

La función gl_get_line(), que se documenta por separado en la página del manual gl_get_line(3), admite dos modos de E/S diferentes. Estos se seleccionan llamando a la función gl_io_mode()

. 
  int gl_io_mode(GetLine *gl, GlIOMode mode)
;

El argumento mode de esta función especifica el nuevo modo de E/S, y debe ser uno de los

siguientes. 
  GL_NORMAL_MODE   -  Selecciona el modo de E/S bloqueante normal.
                      En este modo gl_get_line()
                      no retorna hasta que ocurre un error o el usuario termina de introducir una nueva línea. Este modo es el foco de la página del manual gl_get_line(3).
  GL_SERVER_MODE   -  Selecciona el modo de E/S de servidor no bloqueante.
                      En este modo, ya que se utiliza E/S de terminal no bloqueante, la introducción de cada nueva línea de entrada normalmente requiere muchas llamadas a gl_get_line() desde un bucle de eventos externo impulsado por E/S.
                      Este modo es el foco de esta página del
manual.

Los objetos GetLine recién creados comienzan en modo de E/S normal, por lo que para cambiar al modo de servidor no bloqueante se requiere una llamada inicial a gl_io_

mode
().

MODO DE E/S DE

SERVIDOR

En el modo de E/S de servidor no bloqueante, la aplicación debe tener un bucle de eventos que llame a gl_get_line() siempre que el descriptor de archivo del terminal pueda realizar el tipo de E/S que gl_get_line() está esperando. Para determinar qué tipo de E/S gl_get_line() está esperando, la aplicación llama a la función gl_pending_io()

. 
  GlPendingIO gl_pending_io(GetLine *gl)
;

El valor de retorno de esta función es uno de los siguientes dos valores

enumerados. 
  GLP_READ    -  gl_get_line() está esperando para escribir un carácter en el terminal.
  GLP_WRITE   -  gl_get_line() está esperando para leer un carácter del
teclado.

Si la aplicación está utilizando ya sea la select() o poll() llamadas al sistema para vigilar la E/S en un grupo de descriptores de archivo, entonces debe llamar a la función gl_pending_io() antes de cada llamada a estas funciones para ver qué dirección de E/S debe decirles que vigilen, y configurar sus argumentos en consecuencia. En el caso de la llamada al sistema select(), esto significa usar la macro FD_SET() para añadir el descriptor de archivo del terminal ya sea al conjunto de descriptores de archivo a vigilar por legibilidad, o al conjunto a vigilar por

escribibilidad.

Como en el modo de E/S normal, el valor de retorno de gl_get_line() es ya sea un puntero a una línea de entrada completada, o NULL. Sin embargo, mientras que en el modo de E/S normal un valor de retorno NULL siempre significa que ocurrió un error, en el modo de servidor no bloqueante, NULL también se retorna cuando gl_get_line() no puede leer o escribir en el terminal sin bloquearse. Así que en el modo de servidor no bloqueante, para determinar cuándo un valor de retorno NULL significa que ocurrió un error o no, es necesario llamar a la función gl_return_status(). Si esta función retorna el valor enumerado GLR_BLOCKED, como se documenta en la página del manual gl_get_line(3), esto significa que gl_get_line() está esperando E/S, y no ha ocurrido ningún

error.

Cuando gl_get_line() retorna NULL y gl_return_status() indica que esto se debe a E/S de terminal bloqueada, la aplicación debe llamar a gl_get_line() de nuevo cuando el tipo de E/S reportado por gl_pending_io() se vuelva posible. Los argumentos prompt, start_line y start_pos de gl_get_line() se ignorarán en estas llamadas. Si necesita cambiar el prompt de la línea que se está editando actualmente, entonces puede llamar a la función gl_replace_prompt() (documentada en la página del manual gl_get_line(3)) entre llamadas a gl_get_

lin
e().

RENDIRSE DEL

TERMINAL

Una complicación que es única al modo de servidor no bloqueante es que requiere que el terminal se deje en modo crudo entre llamadas a gl_get_line(). Si no fuera el caso, el bucle de eventos externo no sería capaz de detectar pulsaciones de teclas individuales, y la edición básica de línea implementada por el controlador del terminal entraría en conflicto con la edición proporcionada por gl_get_line(). Lo que esto significa es que cada vez que el terminal necesita ser usado para otras cosas que no sean introducir una nueva línea de entrada con gl_get_line(), necesita ser restaurado a un estado utilizable. En particular, siempre que el proceso sea suspendido o terminado, el terminal debe ser devuelto a un estado normal. Si esto no se hace, entonces dependiendo de las características del shell que se usó para invocar el programa, el usuario puede terminar con un terminal colgado. Para este fin, la función gl_normal_io() se proporciona para cambiar el terminal de vuelta al estado en el que estaba cuando se estableció el modo crudo por última

vez. 
  int gl_normal_io(GetLine *gl)
;

Lo que hace esta función es primero vaciar cualquier salida pendiente al terminal, luego mover el cursor al inicio de la línea del terminal que sigue al final de la línea de entrada introducida incompletamente. En este punto es seguro suspender o terminar el proceso, y es seguro para la aplicación leer y escribir en el terminal. Para reanudar la introducción de la línea de entrada, la aplicación debe llamar a la función gl_raw_io()

. 
  int gl_raw_io(GetLine *gl)
;

Esta función inicia una nueva línea, vuelve a mostrar la línea de entrada parcialmente completada (si la hay), restaura la posición del cursor dentro de esta línea a donde estaba cuando se llamó a gl_normal_io(), luego cambia de vuelta al modo de terminal crudo no bloqueante listo para continuar la introducción de la línea de entrada cuando gl_get_line() sea llamado la próxima

vez.

Note que en el modo de servidor no bloqueante, si gl_get_line() es llamado después de una llamada a gl_normal_io(), sin una llamada intermedia a gl_raw_io(), gl_get_line() llamará a gl_raw_mode() por sí mismo, y el terminal permanecerá en este modo cuando gl_get_line

() re
torne.

MANEJO DE

SEÑALES

En la sección anterior se señaló que en el modo de servidor no bloqueante, el terminal debe ser restaurado a un estado sensato siempre que se reciba una señal que suspenda o termine el proceso. En el modo de E/S normal, esto se hace por usted por gl_get_line(), pero en el modo de servidor no bloqueante, ya que el terminal se deja en modo crudo entre llamadas a gl_get_line(), este manejo de señales debe ser hecho por la aplicación. Ya que hay muchas señales que pueden suspender o terminar un proceso, así como otras señales que son importantes para gl_get_line(), como la señal SIGWINCH, que le dice cuándo el tamaño del terminal ha cambiado, la función gl_tty_signals() se proporciona para instalar manejadores de señales para todas las señales

pertinentes. 
  int gl_tty_signals(void (*term_handler)(int),
                     void (*susp_handler)(int),
                     void (*cont_handler)(int),
                     void (*size_handler)(int))
;

Lo que hace esto es usar la lista interna de señales de gl_get_line() para asignar manejadores de señales especificados a grupos de señales. Los argumentos de esta función son los

siguientes. 
  term_handler  -  Este es el manejador de señales que debe usarse para atrapar señales que por defecto terminan cualquier proceso que las reciba (ej. SIGINT o SIGTERM).
  susp_handler  -  Este es el manejador de señales que debe usarse para atrapar señales que por defecto suspenden cualquier proceso que las reciba (ej. SIGTSTP o SIGTTOU).
  cont_handler  -  Este es el manejador de señales que debe usarse para atrapar señales que usualmente se envían cuando un proceso se reanuda después de ser
                   suspendido (normalmente SIGCONT). Tenga cuidado de que no hay nada que impida a un usuario enviar una de estas señales en otros momentos.
                   size_handler  -  Este manejador de señales se utiliza para atrapar
                   señales que se envían a los procesos cuando
                   sus terminales de control son redimensionados
                   por el usuario (por ejemplo, SIGWINCH)
.

Todos estos argumentos pueden ser el mismo, si así se desea, y puede especificar SIG_IGN (ignorar esta señal) o SIG_DFL (usar el manejador de señal predeterminado proporcionado por el sistema) en lugar de una función donde sea pertinente. En particular, rara vez es útil atrapar SIGCONT, por lo que el argumento cont_handler normalmente será SIG_DFL o SIG_IGN

.

La función gl_tty_signals() usa la función POSIX sigaction() para instalar estos manejadores de señales, y se asegura de usar el miembro sa_mask de cada estructura sigaction para asegurar que solo una de estas señales se entregue alguna vez a la vez. Esto protege contra que diferentes instancias de estos manejadores de señales intenten simultáneamente escribir en datos globales comunes, como un búfer sigsetjmp() compartido o un indicador de señal

recibida.

Los manejadores de señales que son instalados por esta función deberían llamar a la función gl_handle_signal()

. 
  void gl_handle_signal(int signo, GetLine *gl, int ngl)
;

El argumento signo le indica a esta función a qué señal se le está pidiendo que responda, y el argumento gl debería ser un puntero al primer elemento de un arreglo de ngl objetos GetLine. Si su aplicación solo tiene uno de estos objetos, simplemente pase su puntero como el argumento gl y especifique ngl como 1

.

Dependiendo de la señal que se esté manejando, esta función hace cosas

diferentes.

Señales de redimensionamiento de terminal

(SIGWINCH)

Si la señal indica que la terminal fue redimensionada, entonces organiza que la próxima llamada a gl_get_line() le pida a la terminal por su nuevo tamaño y redibuje la línea de entrada en consecuencia. Para que gl_get_line() sea llamada lo antes posible para hacer esto, gl_handle_signal() también organiza que la próxima llamada a gl_pending_io() devuelva GLP_WRITE. Así que si la aplicación espera E/S en select() o poll(), entonces la aplicación necesita asegurarse de que estas funciones ser

án abortadas de manera confiable cuando u
na señal sea atrapada y manejada por
la aplicación. Más sobre esto más abajo.

Señales de terminación de

proceso.

Si la señal que fue atrapada es una de aquellas que por defecto termina cualquier proceso que la recibe, entonces gl_handle_signal() hace los siguientes

pasos.

1. Primero bloquea la entrega de todas las señales que pueden ser
bloqueadas (es decir, SIGKILL y SIGSTOP no pueden ser

bloqueadas)

2. Luego llama a gl_normal_io() para cada uno de los ngl

3. Luego establece el manejador de la señal a su disposición predeterminada de
terminación del

proceso.

4. Luego reenvía al proceso la señal que fue

atrapada.

5. Finalmente desbloquea la entrega de esta señal, lo que
resulta en la

terminación
del proceso.

Señales de suspensión de

proceso.

Si la disposición predeterminada de la señal es suspender el proceso, se ejecutan los mismos pasos que para las señales de terminación de proceso, excepto que cuando el proceso es reanudado más tarde, gl_handle_signal() continúa, y hace los siguientes

6. Vuelve a bloquear la entrega de la

señal.

7. Restablece el manejador de la señal a aquel
que fue desplazado cuando se sustituyó su disposición

8. Para cualquiera de los objetos GetLine que estaban en modo crudo cuando
gl_handle_signal() fue llamada, gl_handle_signal() luego

esas

terminales.

Note que el proceso es suspendido o terminado usando la señal original que fue atrapada, en lugar de usar las señales inatrapables SIGSTOP y SIGKILL. Esto es importante, porque cuando un proceso es suspendido o terminado, el padre del proceso puede desear usar el valor de estado devuelto por la llamada al sistema wait() para averiguar qué señal fue responsable. En particular, la mayoría de los shells usan esta información para imprimir un mensaje correspondiente en la terminal. Los usuarios estarían justamente confundidos si cuando su proceso recibió una señal SIGPIPE, el programa respondiera enviándose a sí mismo una señal SIGKILL, y el shell luego imprimi

INTERRUMPIENDO EL BUCLE DE

EVENTOS

Si una señal es atrapada y manejada cuando el bucle de eventos de la aplicación está esperando en select() o poll(), estas funciones serán abortadas con errno establecido a EINTR. Cuando esto sucede, el bucle de eventos debería llamar a gl_pending_io(), antes de llamar a select() o poll() de nuevo. Luego debería organizar que select() o poll() espere por el tipo de E/S que esto reporta. Esto es necesario, porque cualquier manejador de señales que llame a gl_handle_signal(), cambiará frecuentemente el tipo de E/S por el que gl_get_line() está

esperando.

Desafortunadamente, si una señal llega entre las sentencias que configuran los argumentos de select() o poll() y las llamadas a estas funciones, entonces la señal no será vista por estas funciones, que luego no serán abortadas. Si estas funciones están esperando la entrada del teclado del usuario cuando la señal es recibida, y el manejador de señales organiza redibujar la línea de entrada para acomodar un redimensionamiento de la terminal o la reanudación del proceso, entonces este redisplay se retrasará hasta que el usuario presione la siguiente tecla. Aparte de confundir al usuario, esto claramente no es un problema serio. Sin embargo, hay una manera, aunque complicada, de evitar completamente esta condición de carrera. RENUNCIAR A LA TERMINAL

En el modo de E/S de servidor no bloqueante, a menudo no deseará que la aplicación se bloquee indefinidamente esperando la entrada del usuario. Una forma de evitarlo es programar explícitamente su uso con un bucle de eventos externo, tal como se describe en la sección SERVER I/O MODE. Sin embargo, para manejar el caso de que su programa tenga que salir de gl_get_line() de forma inmediata (por ejemplo, para responder a una señal), debe llamar a gl_raw_io(3) antes de realizar cualquier otra cosa que requiera el uso de la terminal. Si devuelve GLR_BLOCKED, o GLR_SIGNAL, o si llama a gl_get_line(3) y quiere salir inmediatamente, llame a gl_abandon_line(3). Por ejemplo:

  int ret;
  if ((ret = gl_get_line(gl, prompt, &line)) != 0) {
    if (ret == GLR_SIGNAL) {
      if (signal_caught == SIGINT) {
        gl_abandon_line(gl);
        goto next_iteration;
      }
    }
    ...
  }

MANEJO DE SEÑALES

En el modo de E/S de servidor no bloqueante, la biblioteca tecla solo responderá a las señales si se lo indica explícitamente. Por defecto, la biblioteca ignorará todas las señales. La función gl_trap_signal(3) se utiliza para indicar a la biblioteca que intercepte una señal específica.

Al llamar a gl_get_line(3), la biblioteca comprobará si se ha recibido alguna de las señales que se le ha indicado que intercepte. Si es así, la biblioteca devolverá GLR_SIGNAL, y el gl_return_status(3) devolverá el número de la señal recibida. La biblioteca también llama a su manejador de señales (si se ha proporcionado alguno) y se lo pasa como argumento a su manejador.

La función gl_handle_signal(3) se puede utilizar para registrar un manejador de señales. Su firma es:

  void gl_handle_signal(GetLine *gl, int sig, void (*handler)(int));

El manejador de señales proporcionado se adjuntará a la señal especificada, y la biblioteca también registrará su propio manejador de señales. Cuando se reciba la señal, el manejador de la biblioteca se ejecutará primero y luego llamará al manejador proporcionado por el usuario.

Señales de terminación de proceso.

Las señales de terminación de proceso, como SIGINT, SIGTERM y SIGHUP, normalmente terminan la aplicación. Sin embargo, en el modo de E/S de servidor no bloqueante, si la biblioteca está configurada para manejar estas señales (consulte gl_trap_signal(3)), la biblioteca devolverá GLR_SIGNAL y el gl_return_status(3) devolverá el número de la señal. La aplicación puede entonces decidir cómo responder, ya sea terminando la aplicación o realizando alguna otra acción.

Señales de suspensión de proceso.

Las señales de suspensión de proceso, como SIGTSTP, SIGSTOP y SIGTTIN, suspenden la aplicación. Si la biblioteca está configurada para manejar estas señales, la biblioteca devolverá GLR_SIGNAL y el gl_return_status(3) devolverá el número de la señal. La aplicación puede entonces decidir si reanuda el proceso o realiza alguna otra acción.

INTERRUPCIÓN DEL BUCLE DE EVENTOS

En aplicaciones de servidor, a menudo es deseable poder salir del bucle de eventos principal de forma controlada, por ejemplo, en respuesta a una señal de interrupción del usuario (SIGINT). La biblioteca tecla proporciona un mecanismo para hacer esto en el modo de E/S de servidor no bloqueante.

Cuando gl_get_line() se ejecuta en modo no bloqueante, devolverá GLR_SIGNAL si se recibe una señal que la biblioteca está configurada para manejar (consulte gl_trap_signal(3)). En este caso, la llamada posterior a gl_return_status() devolverá el número de la señal recibida.

Para interrumpir el bucle de eventos y salir de gl_get_line() de forma limpia, puede implementar un manejador de señales que llame a gl_abandon_line(). Esto hará que gl_get_line() descarte la línea actual, imprima un nuevo prompt y comience a aceptar una nueva entrada.

Por ejemplo, si desea salir de gl_get_line() en respuesta a SIGINT:

  static GetLine *my_gl;
  static void sigint_handler(int sig) {
    gl_abandon_line(my_gl);
  }

  void setup_signal_handling(GetLine *gl) {
    my_gl = gl;
    gl_handle_signal(gl, SIGINT, sigint_handler);
  }

En su bucle de eventos principal, después de una llamada a gl_get_line() que devuelve GLR_SIGNAL con SIGINT, puede salir del bucle si es necesario.

SEÑALES INTERCEPTADAS POR GL_GET_LINE

La función gl_get_line() puede configurarse para interceptar un conjunto específico de señales en el modo de E/S de servidor no bloqueante. Esto se hace usando la función gl_trap_signal(3).

Cuando se intercepta una señal, gl_get_line() devolverá el valor GLR_SIGNAL. La función gl_return_status() devolverá entonces el número de la señal que fue interceptada. Si se ha proporcionado un manejador de señales personalizado usando gl_handle_signal(3), este se llamará también.

La forma de usar esto es llamar primero a gl_trap_signal(3) para especificar las señales que desea interceptar. Por ejemplo, para interceptar SIGINT y SIGTERM:

  gl_trap_signal(gl, SIGINT);
  gl_trap_signal(gl, SIGTERM);

Luego, en el bucle principal de su aplicación, después de llamar a gl_get_line(), verifique el valor de retorno. Si es GLR_SIGNAL, puede usar gl_return_status() para obtener el número de la señal y actuar en consecuencia. Si la señal es SIGINT, a menudo querrá abortar la entrada de la línea actual llamando a gl_abandon_line(3).

Es importante tener en cuenta que gl_get_line() solo interceptará las señales que se le indiquen explícitamente. Otras señales serán manejadas por los manejadores de señales predeterminados del sistema. Además, si está usando su propio bucle de eventos con select(2) o poll(2), gl_get_line() solo comprobará las señales después de que haya transcurrido un tiempo de espera (consulte USING TIMEOUTS TO POLL).

Para las señales que no se quieren interceptar explícitamente, siga el procedimiento estándar de manejo de señales de POSIX, usando sigaction(2) para registrar un manejador que realice las acciones adecuadas. Tenga en cuenta que si su manejador de señales modifica estructuras de datos compartidas con gl_get_line(), debe tomar las precauciones adecuadas para evitar condiciones de carrera, como bloquear las señales mientras se accede a las estructuras de datos compartidas.

Las funciones gl_normal_io(3), gl_raw_io(3), gl_handle_signal(3) y gl_abandon_line(3) son seguras para ser llamadas desde manejadores de señales, siempre que se sigan ciertas reglas, como se describe en la sección SIGNAL SAFE FUNCTIONS.

ABORTAR ENTRADA DE LÍNEA

A menudo, en lugar de permitir que termine el proceso, las aplicaciones responden a la señal de interrupción del usuario SIGINT abortando la línea de entrada actual. La forma de hacerlo en el modo de E/S de servidor no bloqueante es no llamar a gl_handle_signal() cuando se captura esta señal, sino llamar a gl_abandon_line().

  void gl_abandon_line(GetLine *gl);

Esta función se encarga de que, cuando se llame a gl_get_line() la próxima vez, primero vacíe cualquier salida pendiente en la terminal, luego descarte la línea de entrada actual, imprima un nuevo prompt en la siguiente línea y finalmente comience a aceptar la entrada de una nueva línea de entrada del usuario.

FUNCIONES SEGURAS PARA SEÑALES

Siempre que se sigan ciertas reglas, las siguientes funciones pueden haber sido escritas para ser llamadas de forma segura desde manejadores de señales. Otras funciones de esta biblioteca no deben ser llamadas desde manejadores de señales.

  gl_normal_io()
  gl_raw_io()
  gl_handle_signal()
  gl_abandon_line()

Para que esto sea cierto, todos los manejadores de señales que llaman a estas funciones deben registrarse de tal manera que solo pueda ejecutarse una instancia de cualquiera de ellas a la vez. La forma de hacer esto es usar la función POSIX sigaction() para registrar todos los manejadores de señales, y al hacerlo, usar el miembro sa_mask de la estructura sigaction correspondiente, para indicar que todas las señales cuyos manejadores invocan las funciones anteriores deben ser bloqueadas cuando se esté manejando la señal actual. Esto evita que dos manejadores de señales operen en un objeto GetLine al mismo tiempo.

Para evitar que los manejadores de señales accedan a un objeto GetLine mientras gl_get_line() o cualquiera de sus funciones públicas asociadas están operando sobre él, todas las funciones públicas asociadas con gl_get_line(), incluida la propia gl_get_line(), bloquean temporalmente la entrega de señales cuando acceden a objetos GetLine. Tenga en cuenta que las únicas señales que bloquean son las señales que gl_get_line() está configurado actualmente para capturar, así que asegúrese de que si llama a alguna de las funciones anteriores desde manejadores de señales, las señales a las que están asignados estos manejadores estén configuradas para ser capturadas por gl_get_line() (consulte gl_trap_signal()).

USO DE TIEMPOS DE ESPERA PARA SONDEO

Si en lugar de usar select() o poll() para esperar E/S, su aplicación solo necesita salir de gl_get_line() periódicamente para hacer brevemente otra cosa antes de volver a aceptar la entrada del usuario, esto se puede hacer en el modo de servidor no bloqueante utilizando la función gl_inactivity_timeout() (consulte gl_get_line(3)), para especificar que una función de devolución de llamada que devuelve GLTO_CONTINUE debe ser llamada siempre que gl_get_line() haya estado esperando E/S durante más tiempo que una cantidad de tiempo especificada.

Cuando se activa esta devolución de llamada, gl_get_line() devolverá NULL, y una llamada posterior a gl_return_status() devolverá GLR_BLOCKED.

Tenga en cuenta que gl_get_line() no devolverá hasta que el usuario no haya tecleado una tecla durante el intervalo especificado, por lo que si el intervalo es largo y el usuario sigue tecleando, gl_get_line() puede no devolver durante un tiempo. En otras palabras, no hay garantía de que devuelva en el tiempo especificado.

EL PROGRAMA DEMO DE SERVIDOR

El programa demo3 que se distribuye con la biblioteca, proporciona un ejemplo funcional de cómo utilizar el modo de E/S de servidor no bloqueante en un programa real. En lo que respecta al usuario, este programa opera de forma idéntica al programa demo principal (llamado demo), excepto que mientras el programa demo principal utiliza el modo de E/S bloqueante normal, demo3 utiliza E/S no bloqueante y un bucle de eventos externo. El código fuente se puede encontrar en demo3.c, y los comentarios en él explican los diversos pasos.
