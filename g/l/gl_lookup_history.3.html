DESCRIPCIÓN

La función gl_get_line() forma parte de la biblioteca tecla (ver la página del manual libtecla(3)). Si el usuario está escribiendo en una terminal, cada llamada le solicita una línea de entrada, luego proporciona instalaciones de edición interactivas, similares a las del shell tcsh de Unix. Además de la edición simple de la línea de comandos, admite la recuperación de líneas de comandos ingresadas previamente, la compleción con TAB de nombres de archivo y la expansión de nombres de archivo con comodines en línea. La documentación de las características de edición de línea de comandos a nivel de usuario y de todas las opciones de configuración del usuario, se puede encontrar en la página del manual tecla(7). Esta página del manual se centra en la documentación para programadores interesados en usar esta biblioteca en sus aplicaciones.

UN EJEMPLO

El siguiente muestra un ejemplo completo de cómo usar la función gl_get_line() para obtener entrada del usuario:

  #include <stdio.h>
  #include <locale.h>
  #include <libtecla.h>
  int main(int argc, char *argv[])
  { 
    char *line;    /* La línea que escribió el usuario */
    GetLine *gl;   /* El objeto de recursos de gl_get_line() */
    setlocale(LC_CTYPE, ""); /* Adoptar la elección del usuario */
                             /* de conjunto de caracteres. */
    gl = new_GetLine(1024, 2048);
    if(!gl)
      return 1;
    while((line=gl_get_line(gl, "$ ", NULL, -1)) != NULL &&
           strcmp(line, "exit\n") != 0)
      printf("Escribiste: %s\n", line);
    gl = del_GetLine(gl);
    return 0;
  }

En el ejemplo, primero se crean los recursos necesarios para la función gl_get_line() llamando a new_GetLine(). Esto asigna la memoria utilizada en llamadas posteriores a la función gl_get_line(), incluido el búfer de historial para registrar las líneas ingresadas previamente. Luego se leen una o más líneas del usuario, hasta que ocurra un error o el usuario escriba exit. Luego, finalmente, los recursos que fueron asignados por new_GetLine(), se devuelven al sistema llamando a del_GetLine(). Tenga en cuenta el uso del valor de retorno NULL de del_GetLine() para hacer que gl sea NULL. Esta es una medida de precaución. Si el programa posteriormente intenta pasar gl a gl_get_line(), dicha función se quejará y devolverá un error, en lugar de intentar usar el objeto de recurso eliminado.

LAS FUNCIONES UTILIZADAS EN EL EJEMPLO

Las descripciones de las funciones utilizadas en el ejemplo son las siguientes:

  GetLine *new_GetLine(size_t linelen, size_t histlen)

Esta función crea los recursos utilizados por la función gl_get_line() y devuelve un puntero opaco al objeto que los contiene. La longitud máxima de una línea de entrada se especifica a través del argumento linelen, y el número de bytes a asignar para almacenar líneas de historial se establece mediante el argumento histlen. Las líneas de historial se almacenan una detrás de otra en un único búfer de este tamaño. Tenga en cuenta que esto significa que el número de líneas de historial que se pueden almacenar en cualquier momento, depende de las longitudes de las líneas individuales. Si desea establecer un límite superior en el número de líneas que se pueden almacenar, consulte la función gl_limit_history() descrita más adelante. Si no desea historial en absoluto, especifique histlen como cero, y no se asignará ningún búfer de historial.

En caso de error, se imprime un mensaje en stderr y se devuelve NULL.

  GetLine *del_GetLine(GetLine *gl)

Esta función elimina los recursos que fueron devueltos por una llamada previa a new_GetLine(). Siempre devuelve NULL (es decir, un objeto eliminado). No hace nada si el argumento gl es NULL.

  char *gl_get_line(GetLine *gl, const char *prompt,
                   const char *start_line, int start_pos);

La función gl_get_line() se puede llamar cualquier número de veces para leer la entrada del usuario. El argumento gl debe haber sido devuelto previamente por una llamada a new_GetLine(). El argumento prompt debe ser una cadena normal terminada en NUL, que especifica el prompt que se le presentará al usuario. Por defecto, los prompts se muestran literalmente, pero si se habilitan con la función gl_prompt_style() (ver más adelante), los prompts pueden contener directivas para hacer subrayado, cambiar a y desde fuentes en negrita, o activar y desactivar el resaltado.

Si desea especificar el contenido inicial de la línea, para que el usuario lo edite, pase la cadena deseada a través del argumento start_line. Luego puede especificar en qué carácter de esta línea está inicialmente posicionado el cursor

FUENTES DE CONFIGURACIÓN

ALTERNATIVAS

Como se mencionó anteriormente, por defecto los usuarios tienen la opción de configurar el comportamiento de gl_get_line() a través de un archivo de configuración llamado .teclarc en sus directorios de inicio. El hecho de que todas las aplicaciones compartan este mismo archivo de configuración es tanto una ventaja como una desventaja. En la mayoría de los casos es una ventaja, ya que fomenta la uniformidad y libera al usuario de tener que configurar cada aplicación por separado. En algunas aplicaciones, sin embargo, este único medio de configuración es un problema. Esto es particularmente cierto para el software embebido, donde no hay un sistema de archivos del cual leer un archivo de configuración, y también en aplicaciones donde se necesita una elección radicalmente diferente de asignaciones de teclas para emular una interfaz de teclado heredada. Para atender a estos casos, la siguiente función permite a la aplicación controlar de dónde se lee la información de

configuración. 
  int gl_configure_getline(GetLine *gl,
                           const char *app_string,
                           const char *app_file,
                           const char *user_file)
;

Permite que los comandos de configuración que normalmente se leerían del archivo ~/.teclarc de un usuario, se lean de cualquiera o ninguno de: una cadena, un archivo de configuración específico de la aplicación y/o un archivo de configuración específico del usuario. Si esta función se llama antes de la primera llamada a gl_get_line(), el comportamiento por defecto de leer ~/.teclarc en la primera llamada a gl_get_line() se desactiva, por lo que toda la configuración debe lograrse utilizando las fuentes de configuración especificadas con esta

función.

Si app_string != NULL, entonces se interpreta como una cadena que contiene uno o más comandos de configuración, separados entre sí en la cadena por caracteres de salto de línea incrustados. Si app_file != NULL entonces se interpreta como la ruta de acceso completa de un archivo de configuración específico de la aplicación. Si user_file != NULL entonces se interpreta como la ruta de acceso completa de un archivo de configuración específico del usuario, como ~/.teclarc. Por ejemplo, en la siguiente

llamada, 
  gl_configure_getline(gl, "edit-mode vi \n nobeep",
                           "/usr/share/myapp/teclarc",
                           "~/.teclarc")

el argumento app_string hace que la aplicación llamante comience en el modo de edición vi, en lugar del modo emacs por defecto, y desactiva el uso de la campana de la terminal por parte de la biblioteca. Luego intenta leer comandos de configuración de todo el sistema desde un archivo opcional llamado /usr/share/myapp/teclarc, y finalmente lee comandos de configuración específicos del usuario desde un archivo .teclarc opcional en el directorio de inicio del usuario. Tenga en cuenta que los argumentos se listan en orden ascendente de prioridad, con el contenido de app_string siendo potencialmente anulado por comandos en app_file, y los comandos en app_file potencialmente siendo anulados por comandos en user_file

CUSTOMIZED KEY BINDINGS

In addition to specifying that the contents of a file should be used to initialize the key bindings, you can also specify that one or more files be used to initialize the argument list. This is achieved by making calls to the gl_read_init_file() function.

  int gl_read_init_file(GetLine *gl, const char *pp_file,
                        const char *user_file);

The pp_file and user_file arguments are recorded internally for subsequent use by the read-init-files key-binding function, so if you plan to call this function multiple times, be sure that the last call specifies the filenames that you want re-read when the user requests that the configuration files be re-read.

Individual key sequences can also be bound and unbound using the gl_bind_keyseq() function.

  int gl_bind_keyseq(GetLine *gl, GlKeyOrigin origin,
                     const char *keyseq,
                     const char *action);

The origin argument specifies the priority of the binding, according to who it is being established for, and must be one of the following two values.

  GL_USER_KEY   -   The user requested this key-binding.
  GL_APP_KEY    -   This is a default binding set by the
                    application.

When both user and application bindings for a given key-sequence have been specified, the user binding takes precedence. The application's binding is subsequently reinstated if the user's binding is later unbound via either another to this function, or a call to gl_configure_getline().

The keyseq argument specifies the key-sequence to be bound or unbound, and is expressed in the same way as in a ~/.teclarc configuration file. The action argument must either be a string containing the name of the action to bind the key-sequence to, or it must be NULL or "" to unbind the key-sequence.

CUSTOMIZED WORD COMPLETION

If in your application, you would like to have TAB completion complete other things in addition to or instead of filenames, you can arrange this by registering an alternate completion callback function, via a call to the gl_customize_completion() function.

  int gl_customize_completion(GetLine *gl, void *data,
                              CplMatchFn *match_fn);

The data argument provides a way for your application to pass arbitrary, application-specific information to the callback function. This is passed to the callback every time that it is called. It might for example, point to the symbol table from which possible completions are to be sought. The match_fn argument specifies the callback function to be called. The CplMatchFn function type is defined in libtecla.h, as is a CPL_MATCH_FN() macro that you can use to declare and prototype callback functions. The declaration and responsibilities of callback functions are described in depth in the cpl_complete_word(3) man page.

In brief, the callback function is responsible for looking backwards in the input line, back from the point at which the user pressed TAB, to find the start of the word being completed. It then must lookup possible completions of this word, and record them one by one in the WordCompletion object that is passed to it as an argument, by calling the cpl_add_completion() function. If the callback function wishes to provide filename completion in addition to its own specific completions, it has the option of itself calling the builtin file-name completion callback. This also, is documented in the cpl_complete_word(3) man page.

Note that if you would like gl_get_line() to return the current input line when a successful completion is been made, you can arrange this when you call cpl_add_completion(), by making the last character of the continuation suffix a newline character. If you do this, the input line will be updated to display the completion, together with any contiuation suffix up to the newline character, then gl_get_line() will return this input line.

If, for some reason, your callback function needs to write something to the terminal, it must call gl_normal_io() before doing so. This will start a new line after the input line that is currently being edited, reinstate normal terminal I/O, and tell gl_get_line() that the input line will need to be redrawn when the callback returns.

ADDING COMPLETION ACTIONS

In the previous section the ability to customize the behavior of the only default completion action, complete-word, was described. In this section the ability to install additional action functions, so that different types of word completion can be bound to different key-sequences, is described. This is achieved by using the gl_completion_action() function.

  int gl_completion_action(GetLine *gl,
                           void *data, CplMatchFn *match_fn,
                           int list_only, const char *name,
                           const char *keyseq);

The data and match_fn arguments are as described in the cpl_complete_word man page, and specify the callback function that should be invoked to identify possible completions. The list_only argument determines whether the action that is being defined should attempt to complete the word as far as possible in the input line before displaying any possible ambiguous completions, or whether it should simply display the list of possible completions without touching the input line. The former option is selected by specifying a value of 0, and the latter by specifying a value of 1. The name argument specifies the name by which configuration files and future invokations of this function should refer to the action. This must either be the name of an existing completion action to be changed, or be a new unused name for a new action. Finally, the keyseq argument specifies the default key-sequence to bind the action to. If this is NULL, no new keysequence will be bound to the action.

Beware that in order for the user to be able to change the key-sequence that is bound to actions that are installed in this manner, when you call gl_completion_action() to install a given action for the first time, you should do this between calling new_GetLine() and the first call to gl_get_line(). Otherwise, when the user's configuration file is read on the first call to gl_get_line(), the name of the your additional action won't be known, and any reference to it in the configuration file will generate an error.

As discussed for gl_customize_completion(), if your callback function, for some reason, needs to write anything to the terminal, it must call gl_normal_io() before doing so.

DEFINING CUSTOM ACTIONS

Although the built-in key-binding actions are sufficient for the needs of most applications, occasionally a specialized application may need to define one or more custom actions, bound to application-specific key-sequences. For example, a sales application would benefit from having a key-sequence that displayed the part name that corresponded to a part number preceding the cursor. Such a feature is clearly beyond the scope of the built-in action functions. So for such special cases, the gl_register_action() function is provided.

  int gl_register_action(GetLine *gl, void *data,
			 GlActionFn *fn, const char *name,
			 const char *keyseq);

This function lets the application register an external function, fn, that will thereafter be called whenever either the specified key-sequence, keyseq, is entered by the user, or the user enters any other key-sequence that the user subsequently binds to the specified action name, name, in their configuration file. The data argument can be a pointer to anything that the application wishes to have passed to the action function, fn, whenever that function is invoked.

The action function, fn, should be declared using the following macro, which is defined in libtecla.h.

  #define GL_ACTION_FN(fn) GlAfterAction (fn)(GetLine *gl, \
              void *data, int count, size_t curpos, \
              const char *line)

The gl and data arguments are those that were previously passed to gl_register_action() when the action function was registered. The count argument is a numeric argument which the user has the option of entering using the digit-argument action, before invoking the action. If the user doesn't enter a number, then the count argument is set to 1. Nominally this argument is interpreted as a repeat count, meaning that the action should be repeated that many times. In practice however, for some actions a repeat count makes little sense. In such cases, actions can either simply ignore the count argument, or use its value for a different purpose.

A copy of the current input line is passed in the read-only line argument. The current cursor position within this string is given by the index contained in the curpos argument. Note that direct manipulation of the input line and the cursor position is not permitted. This is because the rules dicated by various modes, such as vi mode versus emacs mode, no-echo mode, and insert mode versus overstrike mode etc, make it too complex for an application writer to write a conforming editing action, as well as constrain future changes to the internals of gl_get_line(). A potential solution to this dilema would be to allow the action function to edit the line using the existing editing actions. This is currently under consideration.

If the action function wishes to write text to the terminal, without this getting mixed up with the displayed text of the input line, or read from the terminal without having to handle raw terminal I/O, then before doing either of these operations, it must temporarily suspend line editing by calling the gl_normal_io() function. This function flushes any pending output to the terminal, moves the cursor to the start of the line that follows the last terminal line of the input line, then restores the terminal to a state that is suitable for use with the C stdio facilities. The latter includes such things as restoring the normal mapping of \n to \r\n, and, when in server mode, restoring the normal blocking form of terminal I/O. Having called this function, the action function can read from and write to the terminal without the fear of creating a mess. It isn't necessary for the action function to restore the original editing environment before it returns. This is done automatically by gl_get_line() after the action function returns. The following is a simple example of an action function which writes the sentence "Hello world" on a new terminal line after the line being edited. When this function returns, the input line is redrawn on the line that follows the "Hello world" line, and line editing resumes.

  {
    if(gl_n
ormal_io(gl)) /* Temporarily suspend editing */ return GLA_ABORT; printf("Hello world\n"); return GLA_CONTINUE; }

     versátil, implica asumir algunas

  GLTO_CONTINUE -  En el modo de E/S de bloqueo normal, continuar
                   esperando la entrada, sin redibujar la línea
                   de entrada del usuario.
                   En el modo de E/S de servidor no bloqueante (ver
                   gl_io_mode(3)), hacer que gl_get_line()
                   actúe como si la E/S estuviera bloqueada. Esto
                   significa que gl_get_line() devolverá
                   inmediatamente NULL, y una llamada
                   posterior a gl_return_status() devolverá
                   GLR_BLOCKED.


Tenga en cuenta que antes de llamar a la función de devolución de
    llamada, gl_get_line() bloquea la mayoría de las señales y deja sus
    propios manejadores de señales instalados, por lo que si necesita capturar
    una señal particular, deberá instalar temporalmente su propio manejador de
    señales y desbloquear la señal. Asegúrese de volver a bloquear la señal
    (si estaba bloqueada originalmente) y restablecer el manejador de señales
    original, si lo hay, antes de regresar.


Si la función de devolución de llamada necesita leer o escribir en
    el terminal, idealmente debería llamar primero a
    gl_normal_io(gl) para suspender temporalmente la edición de la línea.
    Esto restaurará el terminal al modo canónico y de E/S bloqueante, y moverá
    el cursor al inicio de una nueva línea del terminal. Más tarde, cuando la
    función de devolución de llamada regrese, gl_get_line() notará que
    se llamó a gl_normal_io(), redibujará la línea de entrada y reanudará
    la edición. Tenga en cuenta que en este caso los valores de retorno,
    GLTO_REFRESH y GLTO_CONTINUE son equivalentes.


Para admitir casos en los que la función de devolución de llamada
    llama a una función de terceros que ocasionalmente y de forma impredecible
    escribe en el terminal, la conversión automática de "0 a
    "0 se vuelve a habilitar antes de llamar a la función de
    devolución de llamada. Si la llamada sabe que la función de terceros
    escribió en el terminal, debería devolver el valor de retorno
    GLTO_REFRESH, para indicar a gl_get_line() que redibuje la
    línea de entrada.


Tenga en cuenta que aunque el argumento de tiempo de espera incluye
    un componente de nanosegundos, pocos relojes de computadora tienen actualmente
    resoluciones más finas que unos pocos milisegundos, por lo que solicitar menos
    de unos pocos milisegundos equivale a solicitar cero segundos en muchos
    sistemas. Si esto fuera un problema, debería basar su selección de tiempo de
    espera en la resolución real del reloj del host (por ejemplo, llamando a
    sysconf(_SC_CLK_TCK)).


Para desactivar los tiempos de espera, simplemente llame a
    gl_inactivity_timeout() con un argumento callback de
    0. El argumento data se ignora en este caso.






VALORES PREDETERMINADOS DE MANEJO DE SEÑALES


Por defecto, la función gl_get_line() intercepta varias
    señales. Esto es particularmente importante para las señales que terminarían
    el proceso por defecto, ya que el terminal debe restaurarse a un estado
    utilizable antes de que esto ocurra. En esta sección, se describen las
    señales que son capturadas por defecto y cómo gl_get_line() responde
    a ellas. El cambio de estos valores predeterminados es el tema de la siguiente
    sección.


Cuando se capturan el siguiente subconjunto de señales,
    gl_get_line() primero restaura la configuración del terminal y el
    manejo de señales a cómo estaban antes de que se llamara a
    gl_get_line(), reenvía la señal, para permitir que los manejadores de
    señales de la aplicación que llama la manejen, y luego, si el proceso todavía
    existe, gl_get_line() devuelve NULL y establece errno
    como se especifica a continuación.


 SIGINT  -  Esta señal es generada tanto por la tecla de
            interrupción del teclado (generalmente ^C), como
            por la tecla de interrupción del teclado.
            errno=EINTR
 SIGHUP  -  Esta señal es generada cuando sale el terminal
            de control.
            errno=ENOTTY
 SIGPIPE -  Esta señal es generada cuando un programa intenta
            escribir en una tubería cuyo extremo remoto no está
            siendo leído por ningún proceso. Esto puede ocurrir,
            por ejemplo, si ha llamado a
            gl_change_terminal() para redirigir la salida
            a una tubería oculta bajo un pseudo terminal.
            errno=EPIPE
 SIGQUIT -  Esta señal es generada por la tecla de salida del
            teclado (generalmente ^\).
            errno=EINTR
 SIGABRT -  Esta señal es generada por la función estándar C,
            abort(). Por defecto, termina el proceso y genera un
            volcado del núcleo.
            errno=EINTR
 SIGTERM -  Esta es la señal por defecto que el comando kill
            de UN*X envía a los procesos.
            errno=EINTR


Tenga en cuenta que en el caso de todas las señales anteriores, POSIX
    establece que por defecto el proceso se termina, con la adición de un volcado
    del núcleo en el caso de la señal SIGQUIT. En otras palabras, si la
    aplicación que llama no anula el manejador por defecto proporcionando su
    propio manejador de señales, la recepción de la señal correspondiente
    terminará la aplicación antes de que gl_get_line() regrese.


Si gl_get_line() aborta con errno establecido en EINTR, puede averiguar
    qué señal provocó el aborto llamando a la siguiente función.


  int gl_last_signal(const GetLine *gl);


Esto devuelve el código numérico (por ejemplo, SIGINT) de la
    última señal recibida durante la llamada más reciente a
    gl_get_line(), o -1 si no se recibieron señales.


En sistemas que lo soportan, cuando se recibe una señal SIGWINCH
    (cambio de ventana), gl_get_line() consulta el terminal para conocer su
    nuevo tamaño, redibuja la línea de entrada actual para acomodar el nuevo
    tamaño, y luego regresa a esperar la entrada del teclado del usuario. A
    diferencia de otras señales, esta señal no se reenvía a la aplicación.


Finalmente, las siguientes señales hacen que gl_get_line()
    restaure primero el entorno del terminal y de las señales a cómo era antes
    de llamar a gl_get_line(), luego reenvíe la señal a la aplicación. Si
    el proceso todavía existe después de que se entregue la señal, entonces
    gl_get_line() restablece sus propios manejadores de señales, cambia el
    terminal de nuevo a modo raw, redibuja la línea de entrada y vuelve a esperar
    la entrada del terminal del usuario.


 SIGCONT    -  Esta señal se genera cuando se reanuda un
               proceso suspendido.
 SIGPOLL    -  En sistemas SVR4, esta señal notifica al
               proceso un evento de E/S asíncrono. Tenga en
               cuenta que bajo 4.3+BSD, SIGIO y SIGPOLL son
               lo mismo. En otros sistemas, SIGIO es ignorado
               por defecto, por lo que gl_get_line() no
               lo captura por defecto.
 SIGPWR     -  Esta señal se genera cuando ocurre una falla de
               energía (presumiblemente cuando el sistema está en
               un UPS).
 SIGALRM    -  Esta señal se genera cuando expira un temporizador.
 SIGUSR1    -  Una señal específica de la aplicación.
 SIGUSR2    -  Otra señal específica de la aplicación.
 SIGVTALRM  -  Esta señal se genera cuando expira un temporizador
               virtual (ver man setitimer(2)).
 SIGXCPU    -  Esta señal se genera cuando un proceso excede su
               límite de tiempo de CPU blando.
 SIGXFSZ    -  Esta señal se genera cuando un proceso excede su
               límite de tamaño de archivo blando.
 SIGTSTP    -  Esta señal es generada por la tecla de suspensión
               del terminal, que suele ser ^Z, o la tecla de
               suspensión retardada del terminal, que suele ser
               ^Y.
 SIGTTIN    -  Esta señal se genera si el programa intenta leer
               del terminal mientras el programa se está
               ejecutando en segundo plano.
 SIGTTOU    -  Esta señal se genera si el programa intenta escribir
               en el terminal mientras el programa se está
               ejecutando en segundo plano.


Obviamente, no todas las señales anteriores son compatibles en todos
    los sistemas, por lo que el código para admitirlas se compila condicionalmente
    en la biblioteca tecla.


Tenga en cuenta que si SIGKILL o SIGPOLL, que por
    definición no pueden ser capturados, o cualquiera de las señales de excepción
    generadas por hardware, como SIGSEGV, SIGBUS y SIGFPE,
    se reciben y no se manejan mientras gl_get_line() tiene el terminal en
    modo raw, el programa terminará sin que el terminal se restaure a un estado
    utilizable. En la práctica, los shells de control de trabajos suelen restablecer
    la configuración del terminal cuando un proceso cede el control del terminal,
    por lo que esto solo es un problema con shells más antiguos.

MANEJO DE SEÑALES

FIABLE

El manejo de señales es sorprendentemente difícil de hacer de forma fiable sin condiciones de carrera. En gl_get_line() se ha tenido mucho cuidado para permitir que las aplicaciones realicen un manejo de señales fiable alrededor de gl_get_line(). Esta sección explica cómo hacer uso de

esto.

Como ejemplo de los problemas que pueden surgir si la aplicación no está escrita correctamente, imagine que su aplicación tiene un manejador de señales SIGINT que establece un indicador global. Ahora suponga que la aplicación prueba este indicador justo antes de invocar gl_get_line(). Si una señal SIGINT llega a ser recibida en la pequeña ventana de tiempo entre la sentencia que prueba el valor de este indicador y la sentencia que llama a gl_get_line(), entonces gl_get_line() no verá la señal y no será interrumpido. Como resultado, la aplicación no podrá responder a la señal hasta que el usuario termine de ingresar la línea de entrada y gl_get_line() regrese. Dependiendo de la aplicación, esto podría o no ser un desastre, pero al menos confundiría al

usuario.

La forma de evitar tales problemas es hacer lo

siguiente.

1. Si es necesario, use la función gl_trap_signal() para
configurar gl_get_line() para que aborte cuando se
capturen señales

importantes.

2. Configure gl_get_line() de modo que si alguna de las
señales que captura está bloqueada cuando se
llama a gl_get_line(), se desbloqueen
automáticamente durante los momentos en que gl_get_line() está
esperando E/S. Esto se puede hacer ya sea
por señal, llamando a la
función gl_trap_signal() y especificando el
atributo GLS_UNBLOCK de la señal, o globalmente
llamando a la función gl_catch_blocked()

. 
     void gl_catch_blocked(GetLine *gl)
;


Esta función simplemente agrega el atributo GLS_UNBLOCK
a todas las señales que actualmente está configurada para
capturar

.

3. Justo antes de llamar a gl_get_line(), bloquee la entrega
de todas las señales que gl_get_line() está
configurada para capturar. Esto se puede hacer usando la función POSIX
sigprocmask() en conjunto con la
función gl_list_signals()

. 
      int gl_list_signals(GetLine *gl, sigset_t *set)
;


Esta función devuelve el conjunto de señales que está
actualmente configurada para capturar en el argumento set,
que está en la forma requerida por sigprocma

sk().

4. En el ejemplo, ahora se probaría el indicador global que
el manejador de señales establece, sabiendo que ahora no hay
peligro de que este indicador se establezca de nuevo hasta que
gl_get_line() desbloquee sus señales mientras realiza
E/S

.

5. Eventualmente gl_get_line() regresa, ya sea porque
se capturó una señal, ocurrió un error, o el usuario
terminó de ingresar su línea de

entrada.

6. Ahora se verificaría el indicador global de señales de nuevo, y si
está establecido, se respondería a él, y se pondría el indicador a

cero.

7. Use sigprocmask() para desbloquear las señales que fueron
bloqueadas en el paso

3.

La misma técnica se puede usar alrededor de ciertas funciones POSIX conscientes de señales, como sigsetjmp() y sigsuspend(), y en particular, la primera de estas dos funciones se puede usar en conjunto con siglongjmp() para implementar un manejo de señales libre de condiciones de carrera alrededor de otras llamadas al sistema de larga ejecución. La forma de hacer esto se explica a continuación, mostrando cómo gl_get_line() logra capturar señales de forma fiable alrededor de llamadas a funciones como read() y select() sin condiciones de

carrera.

Lo primero que gl_get_line() hace, siempre que se la llama, es usar la función POSIX sigprocmask() para bloquear la entrega de todas las señales que actualmente está configurada para capturar. Esto es redundante si la aplicación ya las ha bloqueado, pero no causa ningún daño. Deshace este paso justo antes de

regresar.

Siempre que gl_get_line() necesite llamar a read() o select() para esperar la entrada del usuario, primero llama a la función POSIX sigsetjmp(), asegurándose de especificar un valor distinto de cero para su argumento savesigs. La razón de este último argumento se aclarará en

breve.

Si sigsetjmp() devuelve cero, gl_get_line() luego hace lo

siguiente. 
a. Usa la función POSIX sigaction() para registrar
   un manejador de señales temporal para todas las señales que
   está configurada para capturar. Este manejador de señales hace dos
   cosas.
   1. Registra el número de la señal que fue recibida
      en una variable de ámbito de archivo.
   2. Luego llama a la función POSIX siglongjmp()
      usando el búfer que se pasó a
      sigsetjmp() como su primer argumento, y
      un valor distinto de cero para su segundo argumento.
   Cuando este manejador de señales está registrado, el miembro sa_mask
   del argumento struct sigaction act de la
   llamada a sigaction() está configurado para contener todas
   las señales que gl_get_line() está capturando. Esto
   asegura que solo una señal sea capturada a la vez por
   nuestro manejador de señales, lo que a su vez asegura que múltiples
   instancias de nuestro manejador de señales no se interfieran entre sí.
b. Ahora que el manejador de señales ha sido configurado,
   gl_get_line() desbloquea todas las señales que
   está configurada para capturar.
c. Luego llama a las llamadas al sistema read() o select() para esperar la entrada del teclado.
d. Si esta llamada al sistema regresa (es decir, no se recibe ninguna
   señal),
   gl_get_line() bloquea de nuevo la entrega de las señales de
   interés.
e. Luego reinstaura los manejadores de señales que fueron
   desplazados por el que se acaba de
instalar.

Alternativamente, si sigsetjmp() devuelve un valor distinto de cero, esto significa que una de las señales que se estaban atrapando fue capturada mientras se ejecutaban los pasos anteriores. Cuando esto ocurre, gl_get_line() hace lo

siguiente.

Primero, tenga en cuenta que cuando una llamada a siglongjmp() hace que sigsetjmp() retorne, siempre que el argumento savesigs de sigsetjmp() fuera distinto de cero, como se especificó anteriormente, la máscara de proceso de la señal se restaura a cómo estaba cuando sigsetjmp() fue llamado. Esta es la diferencia importante entre sigsetjmp() y el antiguo y problemático setjmp(), y es el ingrediente esencial que hace posible evitar condiciones de carrera en el manejo de señales. Debido a esto, se garantiza que todas las señales que bloqueamos antes de llamar a sigsetjmp() estén bloqueadas de nuevo tan pronto como se capture cualquier señal. Las siguientes declaraciones, que se ejecutan a continuación, se garantiza que se ejecutarán sin que se capturen más

señales.

1. Si así lo indica la configuración de gl_get_line()
de los atributos de la señal que fue capturada,
gl_get_line() restaura los atributos del terminal a
el estado que tenían cuando gl_get_line() fue
llamado. Esto es particularmente importante para las señales que
suspenden o terminan el proceso, ya que de lo contrario el
terminal quedaría en un estado

inutilizable.

2. Luego, restablece los manejadores de señales de la

aplicación.

3. Luego usa la función raise()
de la biblioteca estándar de C para reenviar a la aplicación la señal que
fue

capturada.

3. A continuación, desbloquea la entrega de la señal que acabamos de
enviar. Esto resulta en que la señal que acababa de ser enviada
a través de raise(), sea capturada por el manejador de señales
original de la aplicación, que ahora puede manejarla como
considere

oportuno.

4. Si el manejador de señales retorna (es decir, no termina
el proceso), gl_get_line() bloquea la entrega de la
señal anterior de

nuevo.

5. Luego deshace cualquier acción realizada en el primero de los
pasos anteriores, y vuelve a mostrar la línea, si la configuración de la señal
lo

requiere.

6. gl_get_line() luego reanuda el intento de
leer un carácter, o se aborta, dependiendo de la
configuración de la señal que fue

capturada.

Lo que los pasos anteriores hacen en esencia es tomar señales entregadas de forma asíncrona y manejarlas de forma síncrona, una a la vez, en un punto del código donde gl_get_line() tiene control

total sobre s
u entorno.

EL TAMAÑO DEL

TERMINAL

En la mayoría de los sistemas, la combinación de la ioctl TIOCGWINSZ y la señal SIGWINCH se utiliza para mantener una idea precisa del tamaño del terminal. El tamaño del terminal se consulta nuevamente cada vez que se llama a gl_get_line() y siempre que se recibe una señal SIGWINCH

.

En los pocos sistemas donde este mecanismo no está disponible, al inicio new_GetLine() primero busca las variables de entorno LINES y COLUMNS. Si no se encuentran, o contienen valores inutilizables, entonces si está disponible una base de datos de información del terminal como terminfo o termcap, se busca el tamaño predeterminado del terminal en esta base de datos. Si esto también falla en proporcionar el tamaño del terminal, se usa un tamaño predeterminado de 80 columnas por 24

líneas.

Incluso en sistemas que sí soportan ioctl(TIOCGWINSZ), si el terminal está en el otro extremo de una línea serie, el controlador del terminal generalmente no tiene forma de detectar cuándo ocurre un redimensionamiento ni de consultar cuál es el tamaño actual. En tales casos, no se envía ningún SIGWINCH al proceso, y las dimensiones devueltas por ioctl(TIOCGWINSZ) no son correctas. La única forma de manejar tales instancias es proporcionar una manera para que el usuario introduzca un comando que le diga al sistema remoto cuál es el nuevo tamaño. Este comando entonces llamaría a la función gl_set_term_size() para informar a gl_get_line() sobre el cambio de

tamaño. 
  int gl_set_term_size(GetLine *gl, int ncolumn, int nline)
;

Los argumentos ncolumn y nline se utilizan para especificar las nuevas dimensiones del terminal, y no deben ser menores que 1. Tenga en cuenta que el tamaño del terminal no estará disponible si se lee desde una tubería o un archivo, por lo que los valores predeterminados pueden ser importantes incluso en sistemas que sí soportan formas de averiguar el tamaño del

OCULTANDO LO QUE

ESCRIBES

Al introducir información sensible, como contraseñas, es mejor no tener el texto que está introduciendo reflejado en el terminal. Además, dicho texto no debería registrarse en la lista de historial, ya que alguien que encuentre su terminal desatendida podría recuperarlo, o alguien que esté husmeando en sus directorios podría verlo en su archivo de historial. Teniendo esto en cuenta, la función gl_echo_mode() le permite activar y desactivar la visualización y el archivo de cualquier texto que se introduzca posteriormente en las llamadas a gl_get_li

ne(). 
  int gl_echo_mode(GetLine *gl, int enable)
;

El argumento enable especifica si el texto introducido debe ser visible o no. Si es 0, entonces las líneas introducidas posteriormente no serán visibles en el terminal, y no se registrarán en la lista de historial. Si es 1, entonces las líneas de entrada posteriores se mostrarán a medida que se introduzcan, y siempre que el historial no se haya desactivado a través de una llamada a gl_toggle_history(), también se archivarán en la lista de historial. Finalmente, si el argumento enable es -1, entonces el modo de eco se deja sin cambios, lo que le permite consultar de forma no destructiva la configuración actual a través del valor de retorno. En todos los casos, el valor de retorno de la función es 0 si el eco estaba desactivado antes de que se llamara a la función, y 1 si estaba

activado.

Cuando el eco está desactivado, tenga en cuenta que aunque la fin

alización con tabulador completará su prefijo de forma invisible l
o más lejos posible, las finalizaciones ambiguas no se mostrarán.

CONSULTAS DE UN SOLO

CARÁCTER

Usar gl_get_line() para consultar al usuario para una respuesta de un solo carácter es inconveniente para el usuario, ya que debe presionar la tecla intro o retorno antes de que el carácter que escribió sea devuelto al programa. Por lo tanto, se ha proporcionado la función gl_query_char() para consultas de un solo carácter como

esta. 
  int gl_query_char(GetLine *gl, const char *prompt,
                    char defchar)
;

Esta función muestra el prompt especificado al comienzo de una nueva línea, y espera a que el usuario escriba un carácter. Cuando el usuario escribe un carácter, gl_query_char() lo muestra a la derecha del prompt, inicia una nueva línea, y luego devuelve el carácter al programa que lo llamó. El valor de retorno de la función es el carácter que fue escrito. Si la lectura tuvo que abortarse por alguna razón, se devuelve EOF en su lugar. En el último caso, la aplicación puede llamar a la función previamente documentada gl_return_status(), para averiguar qué salió mal. Esto podría, por ejemplo, haber sido la recepción de una señal, o el temporizador opcional de inactividad

activándose.

Si el usuario simplemente presiona intro, se sustituye el valor del argumento defchar. Esto significa que cuando el usuario presiona retorno de línea o retorno, el carácter especificado en defchar, se muestra después del prompt, como si el usuario lo hubiera escrito, así como ser devuelto a la aplicación que lo llamó. Si tal reemplazo no es importante, simplemente pase '0 como el valor de defchar

.

Si el carácter introducido es un carácter no imprimible, se muestra simbólicamente. Por ejemplo, control-A se muestra como ^A, y los caracteres más allá de 127 se muestran en octal, precedidos por una barra

invertida.

Al igual que con gl_get_line(), el eco del carácter introducido puede desactivarse usando la función gl_echo_mode()

.

Si el proceso que llama se suspende mientras espera a que el usuario escriba su respuesta, el cursor se mueve a la línea siguiente a la línea del prompt, luego, cuando el proceso se reanuda, el prompt se vuelve a mostrar, y gl_query_char() reanuda la espera de que el usuario escriba un

carácter.

Tenga en cuenta que en el modo de servidor no bloqueante, (vea gl_io_mode(3)), si una línea de entrada incompleta está en proceso de lectura cuando se llama a gl_query_char(), la línea de entrada parcial se descarta y se borra del terminal, antes de que se muestre el nuevo prompt. La siguiente llamada a gl_get_line() comenzará por lo

tanto a editar
una nueva línea.

LEYENDO CARACTERES

CRUDOS

Mientras que la función gl_query_char() solicita visiblemente al usuario un carácter, y muestra lo que escribió, la función gl_read_char() lee un carácter de señal del usuario, sin escribir nada en el terminal, o perturbar alguna línea de entrada incompleta. Esto significa que puede ser llamada no solo entre llamadas a gl_get_line(), sino también desde funciones de retorno de llamada que la aplicación ha registrado para ser llamadas por gl_get_li

ne(). 
  int gl_read_char(GetLine *gl)
;

En caso de éxito, el valor de retorno de gl_read_char() es el carácter que fue leído. En caso de fallo, se devuelve EOF, y la función gl_return_status() puede ser llamada para averiguar qué salió mal. Las posibilidades incluyen el temporizador opcional de inactividad activándose, la recepción de una señal que está configurada para abortar gl_get_line(), o el bloqueo de E/S del terminal, cuando se está en el modo de E/S de servidor no

bloqueante.

Tenga en cuenta que ciertas teclas del teclado, como las teclas de función y las teclas de cursor, usualmente generan al menos 3 caracteres cada una, por lo que una sola llamada a gl_read_char() probablemente nono sería suficiente pa

ra identificar tales
pulsaciones de teclas.

MOSTRANDO TEXTO

DINÁMICAMENTE

Entre las llamadas a gl_get_line(), la función gl_display_text() proporciona una manera conveniente de mostrar párrafos de texto, alineados a la izquierda y divididos en una o más líneas de la terminal de acuerdo con las restricciones del ancho actual de la terminal. Ejemplos del uso de esta función se pueden encontrar en los programas de demostración, donde se utiliza para mostrar introducciones. En esos ejemplos también se ilustra el uso avanzado de prefijos opcionales, sufijos y líneas rellenas para dibujar un cuadro alrededor del

texto. 
  int gl_display_text(GetLine *gl, int indentation,
                      const char *prefix,
                      const char *suffix, int fill_char,
                      int def_width, int start,
                      const char *string)
;

Si gl no está actualmente conectado a una terminal, por ejemplo si la salida de un programa que usa gl_get_line() se está redirigiendo a otro programa o a un archivo, entonces se utiliza el valor del parámetro def_width como el ancho de la

terminal.

El argumento indentation especifica el número de caracteres a usar para sangrar cada línea de salida. El argumento fill_char especifica el carácter que se usará para realizar esta

sangría.

El argumento prefix puede ser NULL, o una cadena de texto a colocar al comienzo de cada línea nueva (después de cualquier sangría). De manera similar, el argumento suffix puede ser NULL, o una cadena de texto a colocar al final de cada línea. El sufijo se coloca al ras contra el borde derecho de la terminal, y cualquier espacio entre su primer carácter y la última palabra de esa línea se rellena con el carácter especificado a través del argumento fill_char. Normalmente, el carácter de relleno es un

espacio.

El argumento start le indica a gl_display_text() cuántos caracteres ya se han escrito en la línea de la terminal actual, y por lo tanto le indica el índice de columna inicial del cursor. Dado que el valor de retorno de gl_display_text() es el índice de columna final del cursor, al pasar el valor de retorno de una llamada al argumento start de la siguiente llamada, se puede componer un párrafo que está dividido entre más de una cadena llamando a gl_display_text() para cada porción sucesiva del párrafo. Tenga en cuenta que los caracteres de salto de línea literales son necesarios al final de cada párrafo para forzar el inicio de una nueva

línea.

JUEGOS DE CARACTERES

INTERNACIONALES

Desde la versión 1.4.0 de libtecla, gl_get_line() ha sido compatible con 8 bits. Esto significa que todos los caracteres de 8 bits que son imprimibles en la configuración regional actual del usuario ahora se muestran literalmente y se incluyen en la línea de entrada devuelta. Asumiendo que el programa que llama contiene correctamente una llamada como la

siguiente, 
  setlocale(LC_CTYPE, "")
;

entonces la configuración regional actual se determina por la primera de las variables de entorno LC_CTYPE, LC_ALL y LANG que se encuentre que contiene un nombre de configuración regional válido. Si ninguna de estas variables está definida, o el programa omite llamar a setlocale, entonces se usa la configuración regional C predeterminada, que es ASCII de 7 bits de EE. UU. En la mayoría de las plataformas tipo unix, puede obtener una lista de configuraciones regionales válidas escribiendo el

comando: 
  locale
-a

en el símbolo del sistema. Puede encontrar más documentación sobre cómo el usuario puede hacer uso de esto para introducir caracteres internacionales en la página del man

ual te
cla(7).

SEGURIDAD EN

HILOS

En un programa multihilo, debe usar la versión libtecla_r.a de la biblioteca. Esta usa versiones reentrantes de las funciones del sistema, cuando están disponibles. Desafortunadamente, ni terminfo ni termcap fueron diseñados para ser reentrantes, por lo q

ue no puede usar de forma segura las funciones del módulo getline en múltiples hilos (puede usar los módulos separados de expansión de archivos y completado de palabras en múltiples hilos, vea las páginas de manual correspondientes para más detalles). Sin
embargo, debido al uso de funciones reentrantes de POSIX para buscar directorios de inicio de sesión, etc., es seguro usar este módulo desde un solo hilo de un programa multihilo, siempre que sus otros hilos no usen ninguna función de termcap o terminfo.
