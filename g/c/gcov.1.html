DESCRIPCIÓNgcoves un programa de pruebas de cobertura. Úselo en conjunto con GCC para analizar sus programas y ayudar a crear código más eficiente y de ejecución más rápida, y para descubrir partes no probadas de su programa. Puede usar
gcovcomo una herramienta de perfilado para ayudar a descubrir dónde sus esfuerzos de optimización afectarán mejor a su código. También puede usargcov junto con la otra herramienta de perfilado,
gprof, para evaluar qué partes de su código usan la mayor cantidad de tiempo de cómputo.Las herramientas de perfilado le ayudan a analizar el rendimiento de su código. Usando un perfilador como
gcovo gprof, puede obtener algunas estadísticas básicas de rendimiento, como:
con qué frecuencia se ejecuta cada línea de códigoqué líneas de código se ejecutan realmente cuánto tiempo de cómputo usa cada sección de códigoUna vez que sepa estas cosas sobre cómo funciona su código cuando está compilado, puede examinar cada módulo para ver qué módulos deberían ser optimizados.
gcovle ayuda a determinar dónde trabajar en optimización.Los desarrolladores de software también usan las pruebas de cobertura en conjunto con suites de pruebas, para asegurarse de que el software sea realmente lo suficientemente bueno para una versión. Las suites de pruebas pueden verificar que un programa funciona como se espera; un programa de cobertura prueba para ver cuánto del programa es ejercitado por la suite de pruebas. Los desarrolladores pueden entonces determinar qué tipos de casos de prueba necesitan ser añadidos a las suites de pruebas para crear tanto mejores pruebas como un mejor producto final. Debería compilar su código sin optimización si planea usar

acumula estadísticas por línea (a la resolución más baja), funciona mejor con un estilo de programación que coloca solo una sentencia en cada línea. -d
--display-progress
Muestra el progreso en la salida estándar.
-f
--function-summaries
Genera resúmenes para cada función además del resumen a nivel de archivo.
--include regex
Incluye funciones que coincidan con regex. Esta opción hace que gcov solo informe sobre las funciones que coincidan con la expresión regular extendida regex. Esta opción puede combinarse con --exclude. Si una función coincide tanto con las inclusiones como con las exclusiones, se aplica la última inclusión/exclusión. Por defecto gcov informa sobre todas las funciones, pero si se usa --include , solo se informará sobre las funciones que coincidan con la inclusión.
--exclude regex
Excluye funciones que coincidan con regex. Esta opción hace que gcov no informe sobre las funciones que coincidan con la expresión regular extendida regex. Esta opción puede combinarse con --include. Si una función coincide tanto con las inclusiones como con las exclusiones, se aplica la última inclusión/exclusión. Por defecto gcov informa sobre todas las funciones, y si se usa --exclude , se omitirán las funciones que coincidan con ella.
-h
--help
Muestra información de ayuda sobre el uso de gcov (en la salida estándar) y termina sin realizar ningún procesamiento adicional.
-j
--json-format
Genera el archivo gcov en un formato intermedio JSON fácil de analizar que no requiere el código fuente para su generación. El archivo JSON está comprimido con el algoritmo de compresión gzip y los archivos tienen la extensión .gcov.json.gz .

La estructura del JSON es la siguiente:

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Los campos del elemento raíz tienen la siguiente semántica:

  • current_working_directory: directorio de trabajo donde se compiló la unidad de compilación
  • data_file: nombre del archivo de datos (GCDA)
  • format_version: versión semántica del formato

    Cambios en la versión 2:

*
calls: se añade información sobre las llamadas a funciones
*
gcc_version: versión del compilador GCC

Cada file tiene la siguiente forma:

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Los campos del elemento file tienen la siguiente semántica:

*
file_name: nombre del archivo fuente

Cada function tiene la siguiente forma:

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Los campos del elemento function tienen la siguiente semántica:

  • blocks: número de bloques que hay en la función
  • blocks_executed: número de bloques ejecutados de la función
  • demangled_name: nombre desenmascarado de la función
  • end_column: columna en el archivo fuente donde termina la función
  • end_line: línea en el archivo fuente donde termina la función
  • execution_count: número de ejecuciones de la función
  • name: nombre de la función
  • start_column: columna en el archivo fuente donde comienza la función
  • start_line: línea en el archivo fuente donde comienza la función

Tenga en cuenta que los números de línea y de columna comienzan en 1. En la implementación actual, start_line y start_column no incluyen los parámetros de plantilla ni el tipo de retorno inicial, pero es probable que esto se corrija en el futuro.

Cada line tiene la siguiente forma:

{
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

Las ramas y las llamadas solo están presentes con la opción -b . Los campos del elemento line tienen la siguiente semántica:

  • block_ids: IDs de los bloques básicos que pertenecen a la línea
  • count: número de ejecuciones de la línea
  • line_number: número de línea
  • unexecuted_block: indicador de si la línea contiene un bloque no ejecutado (no todas las sentencias de la línea se ejecutan)
  • function_name: nombre de una función a la que esta line pertenece (para una línea con sentencias en línea puede no estar establecido)

Cada branch tiene la siguiente forma:

{
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

Los campos del elemento branch tienen la siguiente semántica:

  • count: número de ejecuciones de la rama
  • fallthrough: true cuando la rama es una rama de flujo continuo (fall through)
  • throw: true cuando la rama es una rama excepcional
  • isource_block_id: ID del bloque básico donde ocurre esta rama
  • destination_block_id: ID del bloque básico al que salta esta rama

Cada call tiene la siguiente forma:

{
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

Los campos del elemento call tienen la siguiente semántica:

  • returned: número de veces que una llamada a función ha retornado (el recuento de llamadas es igual a line::count)
  • isource_block_id: ID del bloque básico donde ocurre esta llamada
  • destination_block_id: ID del bloque básico al que continúa esta llamada después del retorno

Cada condition tiene la siguiente forma:

{
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

Los campos del elemento condition tienen la siguiente semántica:

  • count: número de resultados de condiciones en esta expresión
  • covered: número de resultados de condiciones cubiertos en esta expresión
  • not_covered_true: términos, por índice, que no se han visto como verdaderos en esta expresión
  • not_covered_false: términos, por índice, que no se han visto como falsos en esta expresión
-H
--human-readable
Escribe los recuentos en un formato legible para humanos (como 24.6k).
-k
--use-colors
Usa colores para las líneas de código que tienen cobertura cero. Usamos el color rojo para las líneas no excepcionales y el cian para las excepcionales. Se usan los mismos colores para los bloques básicos con la opción -a .
-l
--long-file-names
Crea nombres de archivo largos para los archivos fuente incluidos. Por ejemplo, si el archivo de cabecera x.h contiene código y fue incluido en el archivo a.c, entonces al ejecutar gcov sobre el archivo a.c se producirá un archivo de salida llamado a.c##x.h.gcov en lugar de x.h.gcov. Esto puede ser útil si x.h está incluido en múltiples archivos fuente y desea ver las contribuciones individuales. Si usa la opción -p , tanto los nombres de los archivos que incluyen como los incluidos serán rutas completas.
-m
--demangled-names
Muestra nombres de función desenmascarados en la salida. Por defecto, se muestran los nombres de función enmascarados.
-M
--filter-on-demangled
Hace que --include y --exclude coincidan con los nombres desenmascarados. Esto solo afecta a la coincidencia y no implica --demangled-names, pero se puede combinar con él de forma segura.
-n
--no-output
No crea el archivo de salida gcov .
-o directory|file
--object-directory directory

Especifica el directorio que contiene los archivos de datos de gcov, o la ruta del archivo objeto. Los archivos de datos .gcnoy .gcda se buscan usando esta opción. Si se especifica un directorio, los archivos de datos están en ese directorio y se nombran según el nombre del archivo de entrada, sin su extensión. Si se especifica un archivo aquí, los archivos de datos se nombran según ese archivo, sin su extensión.
-p
--preserve-paths
Preserva la información completa de la ruta en los nombres de los archivos .gcov generados. Sin esta opción, solo se usa el componente del nombre del archivo. Con esta opción, se usan todos los directorios, con los caracteres / traducidos a caracteres #, los componentes de directorio . eliminados y los componentes .. irremovibles renombrados a ^. Esto es útil si los archivos de código fuente están en varios directorios diferentes.
-q
--use-hotness-colors
Emite salida coloreada tipo perf para líneas activas. La leyenda de la escala de colores se imprime al principio del archivo de salida.
-r
--relative-only
Solo emite información sobre archivos de código fuente con un nombre de ruta relativo (después de la eliminación del prefijo de código fuente). Las rutas absolutas suelen ser archivos de encabezado del sistema y la cobertura de cualquier función insertada allí normalmente no es interesante.
-s directorio
--source-prefix directorio
Un prefijo para los nombres de archivos de código fuente que se eliminará al generar los archivos de cobertura de salida. Esta opción es útil cuando se compila en un directorio separado y no se desea la ruta al directorio de código fuente al determinar los nombres de los archivos de salida. Tenga en cuenta que esta detección de prefijo se aplica antes de determinar si el archivo de código fuente es absoluto.
-t
--stdout
Salida al flujo de salida estándar en lugar de a archivos de salida.
-u
--unconditional-branches
Cuando se proporcionan probabilidades de rama, incluye las de ramas incondicionales. Las ramas incondicionales normalmente no son interesantes.
-v
--version
Muestra el número de versión de gcov (en la salida estándar) y sale sin realizar ningún procesamiento adicional.
-w
--verbose
Imprime información detallada relacionada con bloques básicos y arcos.
-x
--hash-filenames
Al usar --preserve-paths, gcov utiliza la ruta completa de los archivos de código fuente para crear un nombre de archivo de salida. Esto puede generar nombres de archivo largos que pueden exceder los límites del sistema de archivos. Esta opción crea nombres del tipo archivo-fuente##md5.gcov, donde el componente archivo-fuente es la parte final del nombre del archivo y el componente md5 se calcula a partir del nombre completo modificado que se habría utilizado de lo contrario. La opción es una alternativa a --preserve-paths en sistemas que tienen un límite de sistema de archivos.

gcov debe ejecutarse con el directorio actual igual al que tenía cuando invocó al compilador. De lo contrario, no podrá localizar los archivos de código fuente. gcov produce archivos llamados nombre-modificado.gcov en el directorio actual. Estos contienen la información de cobertura del archivo de código fuente al que corresponden. Se produce un archivo .gcov por cada archivo de código fuente (o de encabezado) que contiene código, y que fue compilado para producir los archivos de datos. La parte nombre-modificado del nombre del archivo de salida suele ser simplemente el nombre del archivo de código fuente, pero puede ser algo más complicado si se dan las opciones -l o -p. Consulte esas opciones para obtener detalles.

Si invoca gcov con varios archivos de entrada, las contribuciones de cada archivo de entrada se suman. Normalmente, lo invocaría con la misma lista de archivos que la vinculación final de su ejecutable.

Los archivos .gcov contienen campos separados por : junto con el código fuente del programa. El formato es

<contador_ejecuciones>:<numero_linea>:<texto_linea_fuente>

Información adicional de bloques puede seguir a cada línea, cuando se solicita mediante una opción de línea de comandos. El contador_ejecuciones es - para las líneas que no contienen código. Las líneas no ejecutadas se marcan con ##### o =====, dependiendo de si son alcanzables por rutas no excepcionales o solo por rutas excepcionales como los manejadores de excepciones de C++, respectivamente. Dada la opción -a, los bloques no ejecutados se marcan con $$$$$ o %%%%%, dependiendo de si un bloque básico es alcanzable a través de rutas no excepcionales o excepcionales. Los bloques básicos ejecutados que tienen una declaración con un contador_ejecuciones cero terminan con el carácter * y se colorean con color magenta con la opción -k. Esta funcionalidad no es compatible en Ada.

Tenga en cuenta que GCC puede eliminar completamente los cuerpos de las funciones que no son necesarias, por ejemplo, si se insertan en todas partes. Dichas funciones se marcan con -, lo que puede ser confuso. Use las opciones -fkeep-inline-functions y -fkeep-static-functions para conservar estas funciones y permitir que gcov muestre correctamente su contador_ejecuciones.

Algunas líneas de información al principio tienen el numero_linea cero. Estas líneas de preámbulo tienen el formato

-:0:<etiqueta>:<valor>

El orden y el número de estas líneas de preámbulo se aumentarán a medida que progrese el desarrollo de gcov; no confíe en que permanezcan sin cambios. Use etiqueta para localizar una línea de preámbulo particular.

La información adicional de bloques tiene el formato

<etiqueta> <información>

La información es legible por humanos, pero está diseñada para ser lo suficientemente simple como para ser analizada por máquinas.

Al imprimir porcentajes, 0% y 100% solo se imprimen cuando los valores son exactamente 0% y 100%, respectivamente. Otros valores que convencionalmente se redondearían a 0% o 100% se imprimen en su lugar como el valor no límite más cercano.

Al usar gcov, primero debe compilar su programa con la opción especial de GCC --coverage. Esto le indica al compilador que genere información adicional necesaria para gcov (básicamente un grafo de flujo del programa) y también incluye código adicional en los archivos objeto para generar la información de perfilado adicional necesaria para gcov. Estos archivos adicionales se colocan en el directorio donde se encuentra el archivo objeto.

Al ejecutar el programa, se generará una salida de perfilado. Por cada archivo de código fuente compilado con -fprofile-arcs, se colocará un archivo .gcda complementario en el directorio del archivo objeto.

Ejecutar gcov con los nombres de archivo de código fuente de su programa como argumentos ahora producirá una lista del código junto con la frecuencia de ejecución para cada línea. Por ejemplo, si su programa se llama tmp.cpp, esto es lo que verá cuando utilice la funcionalidad básica de gcov:

$ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m
File 'tmp.cpp'
Lines executed:92.86% of 14
Creating 'tmp.cpp.gcov'

Para cada función, se imprime una línea mostrando cuántas veces se llama la función, cuántas veces retorna y qué porcentaje de los bloques de la función fueron ejecutados.

Para cada bloque básico, se imprime una línea después de la última línea del bloque básico describiendo la ramificación o llamada que termina el bloque básico. Puede haber múltiples ramificaciones y llamadas listadas para una sola línea de origen si hay múltiples bloques básicos que terminan en esa línea. En este caso, las ramificaciones y llamadas se les asigna un número. No hay una manera simple de mapear estas ramificaciones y llamadas de vuelta a las construcciones de origen. En general, sin embargo, la ramificación o llamada con el número más bajo corresponderá a la construcción más a la izquierda en la línea de origen.

Para una ramificación, si fue ejecutada al menos una vez, se imprimirá un porcentaje indicando el número de veces que la ramificación fue tomada dividido por el número de veces que la ramificación fue ejecutada. De lo contrario, se imprime el mensaje "never executed".

Para una llamada, si fue ejecutada al menos una vez, se imprimirá un porcentaje indicando el número de veces que la llamada retornó dividido por el número de veces que la llamada fue ejecutada. Esto generalmente será 100%, pero puede ser menos para funciones que llaman "exit" o "longjmp", y por lo tanto pueden no retornar cada vez que son llamadas.

Los conteos de ejecución son acumulativos. Si el programa de ejemplo se ejecutara de nuevo sin eliminar el .gcda archivo, el conteo para el número de veces que cada línea en el origen fue ejecutada se agregaría a los resultados de la(s) ejecución(es) anterior(es). Esto es potencialmente útil de varias maneras. Por ejemplo, podría usarse parao acumular datos a lo largo de varias ejecuciones del programa como parte de una suite de verificación de pruebas, o para proporcionar información a largo plazo más precisa sobre un gran número de ejecuciones del programa.

Los datos en los .gcda archivos se guardan inmediatamente antes de que el programa salga. Para cada archivo de origen compilado con -fprofile-arcs, el código de perfilado primero intenta leer un archivo .gcda existente; si el archivo no coincide con el ejecutable (número diferente de recuentos de bloques básicos) ignorará el contenido del archivo. Luego añade los nuevos recuentos de ejecución y finalmente escribe los datos en el archivo.

Puede informar sobre un subconjunto de funciones utilizando --include y --exclude. Uso de gcov con la Optimización de GCC

Si planea usar gcov para ayudar a optimizar su código, debe primero compilar su programa con una opción especial de GCC --coverage. Aparte de eso, puede usar cualquier otra opción de GCC; pero si quiere demostrar que cada línea de su programa fue ejecutada, no debe compilar con optimización al mismo tiempo. En algunas máquinas, el optimizador puede eliminar algunas líneas de código simples combinándolas con otras líneas. Por ejemplo, código como este:

if (a != b)
  c = 1;
else
  c = 0;

puede compilarse en una sola instrucción en algunas máquinas. En este caso, no hay manera para gcov de calcular recuentos de ejecución separados para cada línea porque no hay código separado para cada línea. Por lo tanto, la gcov salida se ve así si compiló el programa con optimización:

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

La salida muestra que este bloque de código, combinado por la optimización, se ejecutó 100 veces. En un sentido este resultado es correcto, porque solo había una instrucción que representaba estas cuatro líneas. Sin embargo, la salida no indica cuántas veces el resultado fue 0 y cuántas veces el resultado fue 1.

Las funciones en línea pueden crear recuentos de líneas inesperados. Los recuentos de líneas se muestran para el código fuente de la función en línea, pero lo que se muestra depende de dónde se inserta la función en línea, o si no se inserta en línea en absoluto.

Si la función no se inserta en línea, el compilador debe emitir una copia fuera de línea de la función, en cualquier archivo de objeto que la necesite. Si fileA.o y fileB.o ambos contienen cuerpos fuera de línea de una función en línea particular, también contendrán ambos los recuentos de cobertura para esa función. Cuando fileA.o y fileB.o se enlazan juntos, el enlazador, en muchos sistemas, seleccionará uno de esos cuerpos fuera de línea para todas las llamadas a esa función, y eliminará o ignorará el otro. Desafortunadamente, no eliminará los contadores de cobertura para el cuerpo de función no utilizado. Por lo tanto, cuando se instrumenta, todas las usos de esa función excepto uno mostrarán recuentos cero.

Si la función se inserta en línea en varios lugares, la estructura de bloques en cada ubicación podría no ser la misma. Por ejemplo, una condición podría ahora ser calculable en tiempo de compilación en algunas instancias. Debido a que la cobertura de todos los usos de la función en línea se mostrará para las mismas líneas de código fuente, los recuentos de línea en sí podrían parecer inconsistentes.

Las aplicaciones de larga duración pueden usar las instalaciones "__gcov_reset" y "__gcov_dump" para restringir la recopilación de perfiles a la región de interés del programa. Llamar a "__gcov_reset(void)" borrará todos los contadores de perfil en tiempo de ejecución a cero, y llamar a "__gcov_dump(void)" hará que la información de perfil recopilada en ese punto se vuelque a los archivos de salida .gcda . Las aplicaciones instrumentadas usan un destructor estático con prioridad 99 para invocar la función "__gcov_dump" . Así "__gcov_dump" se ejecuta después de todos los destructores estáticos definidos por el usuario, así como los manejadores registrados con "atexit".

Si un ejecutable carga un objeto compartido dinámico a través de la funcionalidad dlopen, -Wl,--dynamic-list-data es necesario para volcar todos los datos de perfil.

La biblioteca de tiempo de ejecución de perfilado informa varios errores relacionados con la manipulación de perfiles y el guardado de perfiles. Los errores se imprimen en la salida de error estándar o en el archivo GCOV_ERROR_FILE , si se usa la variable de entorno. Para terminar inmediatamente después de que ocurra un error, establezca la variable de entorno GCOV_EXIT_AT_ERROR . Eso puede ayudar a los usuarios a encontrar conflictos de perfil que conducen a un perfil engañoso.
