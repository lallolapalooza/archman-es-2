NOMBRE

GC_malloc, GC_malloc_atomic, GC_free, GC_realloc, GC_enable_incremental, GC_register_finalizer, GC_malloc_ignore_off_page, GC_malloc_atomic_ignore_off_page, GC_set_warn_proc - Reemplazo de malloc con recolección de basura

SINOPSIS

#include <gc/gc.h>
void * GC_malloc(size_t size);
void * GC_malloc_atomic(size_t size);
void GC_free(void *ptr);
void * GC_realloc(void *ptr, size_t size);
void GC_enable_incremental(void);
void * GC_malloc_ignore_off_page(size_t size);
void * GC_malloc_atomic_ignore_off_page(size_t size);
void GC_set_warn_proc(void (*proc)(char *, GC_word));

cc ... -lgc

DESCRIPCIÓN

GC_malloc y GC_free son reemplazos "plug-in" para malloc y free estándar. Sin embargo, GC_malloc intentará reclamar espacio inaccesible automáticamente invocando un recolector de basura conservador en puntos apropiados. El recolector recorre todas las estructuras de datos accesibles siguiendo punteros desde los registros de la máquina, la pila, los segmentos de datos y bss. Las estructuras inaccesibles serán reclamadas. Una palabra de máquina se considera un puntero válido si es una dirección dentro de un objeto asignado por GC_malloc o funciones similares.

En la mayoría de los casos, es preferible llamar a las macros GC_MALLOC, GC_FREE, etc. en lugar de llamar directamente a GC_malloc y funciones similares. Esto permite que las versiones de depuración de las rutinas sean sustituidas definiendo GC_DEBUG antes de incluir gc.h.

Consulte la documentación en los archivos de inclusión gc_cpp.h y gc_allocator.h, así como el archivo gcinterface.md en la distribución, para una interfaz alternativa específica de C++ al recolector de basura. Tenga en cuenta que los programas C++ generalmente deben tener cuidado de asegurarse de que toda la memoria asignada (ya sea a través de new, malloc o asignadores STL) que pueda apuntar a memoria recolectada por basura esté ella misma recolectada por basura, o al menos rastreada por el recolector.

A diferencia de las implementaciones estándar de malloc, GC_malloc borra el almacenamiento recién asignado. GC_malloc_atomic no lo hace. Además, informa al recolector que el objeto resultante nunca contendrá punteros y, por lo tanto, no debe ser escaneado por el recolector.

GC_free se puede usar para desasignar objetos, pero su uso es opcional y generalmente desaconsejado. GC_realloc tiene las semánticas estándar de realloc. Conserva la ausencia de punteros. GC_register_finalizer permite el registro de funciones que se invocan cuando un objeto se vuelve inaccesible.

El recolector de basura intenta evitar asignar memoria en ubicaciones que ya parecen estar referenciadas antes de la asignación. (Tales "punteros" aparentes son generalmente enteros grandes y similares que simplemente parecen una dirección.) Esto puede dificultar la asignación de objetos muy grandes. Un intento de hacerlo puede generar una advertencia.

GC_malloc_ignore_off_page y GC_malloc_atomic_ignore_off_page informan al recolector que el código del cliente siempre mantendrá un puntero cerca del inicio (es decir, dentro del primer bloque de montón) del objeto, y que los punteros más allá de eso pueden ser ignorados por el recolector. Esto hace que sea mucho más fácil para el recolector colocar objetos grandes. Se recomiendan para la asignación de objetos grandes. (Se deben asignar de esta manera los objetos que se espera que sean mayores de ~100 KB).

También es posible usar el recolector para encontrar fugas de almacenamiento en programas que se ejecutarán con malloc/free estándar. El recolector se puede compilar para operación segura en hilos. A diferencia del malloc estándar, es seguro llamar a malloc después de que una llamada anterior a malloc fuera interrumpida por una señal, siempre que la llamada original a malloc no se reanude.

El recolector puede, en raras ocasiones, producir mensajes de advertencia. En máquinas UNIX, estos aparecen en stderr. Los mensajes de advertencia se pueden filtrar, redirigir o ignorar con GC_set_warn_proc. Esto se recomienda para código de producción. Consulte gc.h para obtener detalles.

El código completamente portable debe llamar a GC_INIT desde el hilo primordial del programa principal antes de realizar cualquier otra llamada a GC. En la mayoría de las plataformas, esto no hace nada y el recolector se inicializa en el primer uso. En algunas plataformas, la inicialización explícita es necesaria. Y nunca puede hacer daño.

Las versiones de depuración de muchas de las rutinas anteriores se proporcionan como macros. Sus nombres son idénticos a los anteriores, pero consisten en letras mayúsculas. Si GC_DEBUG se define antes de incluir gc.h, estas rutinas realizan comprobaciones adicionales y permiten que la versión del recolector que detecta fugas produzca una salida ligeramente más útil. Sin GC_DEBUG definido, se comportan exactamente igual que las versiones en minúsculas.

En algunas máquinas, la recolección se realizará de forma incremental después de una llamada a GC_enable_incremental. Esto puede escribir temporalmente protegiendo páginas en el montón. Consulte el archivo README para obtener más información sobre cómo esto interactúa con las llamadas al sistema que escriben en el montón.

Otras instalaciones no discutidas aquí incluyen instalaciones limitadas para admitir la recolección incremental en máquinas sin el soporte de VM apropiado, disposiciones para proporcionar información de diseño de objetos más explícita al recolector de basura, soporte más directo para punteros "débiles", soporte para recolecciones de basura "abortables" durante el tiempo de inactividad, etc.
