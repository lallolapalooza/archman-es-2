NOMBRE

guestfs-security - seguridad de libguestfs

DESCRIPCIÓN

Esta página del manual discute las implicaciones de seguridad de usar libguestfs, particularmente con huéspedes o imágenes de disco no confiables o maliciosas.

REPORTE DE PROBLEMAS DE SEGURIDAD

Si desea informar privadamente de un problema de seguridad, por favor siga el procedimiento de seguridad de Red Hat en https://access.redhat.com/security/team/contact

Si el problema de seguridad no es tan grave, simplemente puede registrar un error (ver "ERRORES" más abajo), o enviar un correo electrónico a nuestra lista de correo (https://lists.libguestfs.org). No es necesario suscribirse a la lista de correo para enviar un correo electrónico, pero habrá un retraso mientras el mensaje es moderado.

PROBLEMAS GENERALES

Seguridad al montar sistemas de archivos

Nunca debe montar un sistema de archivos de invitado no confiable directamente en su kernel anfitrión (por ejemplo, usando loopback o kpartx).

Cuando monta un sistema de archivos, los errores en el sistema de archivos del kernel (VFS) pueden ser escalados a exploits por atacantes que crean un sistema de archivos malicioso. Estos exploits son muy graves por dos razones. Primero, hay muchísimos drivers de sistemas de archivos en el kernel, y muchos de ellos se usan con poca frecuencia y no se les ha prestado mucha atención por parte de los desarrolladores. El espacio de usuario de Linux ayuda a los posibles atacantes detectando el tipo de sistema de archivos y eligiendo automáticamente el driver VFS correcto, incluso si ese tipo de sistema de archivos es inesperado. Segundo, un exploit a nivel de kernel es como un exploit de root local (peor en algunos aspectos), dando acceso inmediato y total al sistema hasta el nivel de hardware.

Estos exploits pueden estar presentes en el kernel durante mucho tiempo (https://lwn.net/Articles/538898/).

Libguestfs proporciona un enfoque en capas para protegerlo de exploits:

  sistema de archivos no confiable
--------------------------------------
  kernel del appliance
--------------------------------------
  proceso qemu ejecutándose como no root
--------------------------------------
  sVirt [si usa libvirt + SELinux]
--------------------------------------
  kernel anfitrión

Ejecutamos un kernel de Linux dentro de una máquina virtual qemu, generalmente ejecutándose como un usuario no root. El atacante tendría que escribir un sistema de archivos que primero explotara el kernel, y luego explotara la virtualización qemu (por ejemplo, un driver qemu defectuoso) o el protocolo libguestfs, y finalmente, para ser tan grave como el exploit del kernel anfitrión, tendría que escalar sus privilegios a root. Adicionalmente, si usa el backend libvirt y SELinux, sVirt se usa para confinar el proceso qemu. Esta escalada múltiple, realizada por una pieza estática de datos, se considera extremadamente difícil de lograr, aunque nunca decimos 'nunca' sobre problemas de seguridad.

Los llamadores también pueden reducir la superficie de ataque forzando el tipo de sistema de archivos al montar (use "guestfs_mount_vfs" en guestfs(3)).

Consideraciones generales de seguridad

Tenga cuidado con cualquier archivo o dato que descargue de un invitado (por "descargar" nos referimos no solo al comando "guestfs_download" en guestfs(3) sino a cualquier comando que lea archivos, nombres de archivo, directorios o cualquier otra cosa de una imagen de disco). Un atacante podría manipular los datos para engañar a su programa para que haga algo incorrecto. Considere casos como:

  • que los datos (archivo, etc.) no estén presentes
  • que estén presentes pero vacíos
  • que sean mucho más grandes de lo normal
  • que contengan datos arbitrarios de 8 bits
  • que estén en una codificación de caracteres inesperada
  • que contengan homóglifos.

Seguridad del protocolo

El protocolo está diseñado para ser seguro, basándose en RFC 4506 (XDR) con un tamaño de mensaje superior definido. Sin embargo, un programa que usa libguestfs también debe tener cuidado; por ejemplo, puede escribir un programa que descargue un binario de una imagen de disco y lo ejecute localmente, y ninguna cantidad de seguridad de protocolo lo salvará de las consecuencias.

Seguridad de la inspección

Partes de la API de inspección (ver "INSPECCIÓN" en guestfs(3)) devuelven cadenas no confiables directamente del invitado, y estas podrían contener cualquier dato de 8 bits. Los llamadores deben tener cuidado de escaparlas antes de imprimirlas en un archivo estructurado (por ejemplo, use escapado HTML si crea una página web).

La configuración del invitado puede ser alterada de maneras inusuales por el administrador de la máquina virtual, y puede no reflejar la realidad (particularmente para invitados no confiables o activamente maliciosos). Por ejemplo, analizamos el nombre de host a partir de archivos de configuración como /etc/sysconfig/network que encontramos en el invitado, pero el administrador del invitado puede manipular fácilmente estos archivos para proporcionar el nombre de host incorrecto.

La API de inspección analiza la configuración del invitado utilizando dos bibliotecas externas: Augeas (configuración de Linux) y hivex (Registro de Windows). Ambas están diseñadas para ser robustas frente a datos maliciosos, aunque los ataques de denegación de servicio todavía son posibles, por ejemplo, con archivos de configuración excesivamente grandes.

Ejecución de comandos de invitado no confiables

Sea muy cauteloso al ejecutar comandos del invitado. Al ejecutar un comando en el invitado, está dando tiempo de CPU a un binario que no controla, bajo la misma cuenta de usuario que la biblioteca, aunque envuelto en la virtualización qemu. Puede encontrar más información y alternativas en "EJECUCIÓN DE COMANDOS" en guestfs(3).

PROBLEMAS HISTÓRICOS DE SEGURIDAD EN LIBGUESTFS

CVE-2010-3851

https://bugzilla.redhat.com/642934

Este error de seguridad concierne a la detección automática del formato de disco que qemu realiza en las imágenes de disco.

Una imagen de disco raw son solo los bytes crudos, no hay cabecera. Otras imágenes de disco como qcow2 contienen una cabecera especial. Qemu maneja esto buscando una de las cabeceras conocidas, y si no encuentra ninguna, asume que la imagen de disco debe ser raw.

Esto permite que un invitado al que se le ha dado una imagen de disco raw escriba alguna otra cabecera. En el próximo arranque (o cuando la imagen de disco es accedida por libguestfs), qemu haría la autodetección y pensaría que el formato de la imagen de disco era, por ejemplo, qcow2 basándose en la cabecera escrita por el invitado.

Esto en sí mismo no sería un problema, pero qcow2 ofrece muchas características, una de las cuales es permitir que una imagen de disco se refiera a otra imagen (llamada "imagen de disco de respaldo"). Lo hace colocando la ruta a la imagen de respaldo en la cabecera qcow2. Esta ruta no se valida y podría apuntar a cualquier archivo del anfitrión (por ejemplo, "/etc/passwd"). La imagen de respaldo se expone a través de "agujeros" en la imagen de disco qcow2, que por supuesto está completamente bajo el control del atacante.

En libguestfs esto es bastante difícil de explotar excepto bajo dos circunstancias:

1.
Ha habilitado la red o ha abierto el disco en modo de escritura.
2.
También está ejecutando código no confiable desde el invitado (ver "EJECUCIÓN DE COMANDOS" en guestfs(3)).

La forma de evitar esto es especificar el formato de disco esperado al agregar discos (la opción opcional "format" a "guestfs_add_drive_opts" en guestfs(3)). Siempre debería hacer esto si el disco es de formato raw, y también es una buena idea para otros casos. (Ver también "FORMATOS DE IMAGEN DE DISCO" en guestfs(3)).

CVE-2011-4127

https://bugzilla.redhat.com/752375

Este es un error en el kernel que permitía a los huéspedes sobrescribir partes de los discos del host a las que normalmente no deberían tener acceso.

Es suficiente con actualizar libguestfs a cualquier versión ≥ 1.16 que contenga un cambio que mitigue el problema.

CVE-2012-2690

https://bugzilla.redhat.com/831117

Versiones antiguas tanto de virt-edit como del "edit" comando de guestfish creaban un archivo nuevo que contenía los cambios pero no establecían los permisos, etc. del archivo nuevo para que coincidieran con los del antiguo. El resultado de esto era que si editaba un archivo sensible desde el punto de vista de la seguridad como /etc/shadow entonces quedaría legible por todos después de la edición.

Es suficiente con actualizar libguestfs a cualquier versión ≥ 1.16.

CVE-2013-2124

https://bugzilla.redhat.com/968306

Este error de seguridad era una falla en la inspección donde un huésped no confiable usando un archivo especialmente manipulado en el sistema operativo del huésped podía causar una doble liberación (double-free) en la biblioteca C (denegación de servicio).

Es suficiente con actualizar libguestfs a una versión que no sea vulnerable: libguestfs ≥ 1.20.8, ≥ 1.22.2 o ≥ 1.23.2.

CVE-2013-4419

https://bugzilla.redhat.com/1016960

Al usar las opciones guestfish(1) --remote o guestfish --listen , guestfish creaba un socket en una ubicación conocida (/tmp/.guestfish-$UID/socket-$PID).

La ubicación tiene que ser conocida para que ambos extremos puedan comunicarse. Sin embargo, no se realizaba ninguna comprobación de que el directorio contenedor (/tmp/.guestfish-$UID) fuera propiedad del usuario. Así, otro usuario podía crear este directorio y potencialmente secuestrar sockets propiedad del cliente o servidor guestfish de otro usuario.

Es suficiente con actualizar libguestfs a una versión que no sea vulnerable: libguestfs ≥ 1.20.12, ≥ 1.22.7 o ≥ 1.24.

Denegación de servicio al inspeccionar imágenes de disco con volúmenes btrfs corruptos

Era posible hacer fallar a libguestfs (y a los programas que usan libguestfs como biblioteca) presentando una imagen de disco que contuviera un volumen btrfs corrupto.

Esto fue causado por una desreferencia de puntero NULL que causaba una denegación de servicio, y no se cree que sea explotable en mayor medida.

Vea el commit d70ceb4cbea165c960710576efac5a5716055486 para la corrección. Esta corrección está incluida en las ramas estables de libguestfs ≥ 1.26.0, ≥ 1.24.6 y ≥ 1.22.8, y también en RHEL ≥ 7.0. Las versiones anteriores de libguestfs no son vulnerables.

CVE-2014-0191

Libguestfs usaba previamente APIs inseguras de libxml2 para analizar XML de libvirt. Estas APIs permitían por defecto que se realizaran conexiones de red cuando se presentaban ciertos documentos XML. Usando un documento XML malformado también era posible agotar toda la CPU, la memoria o los descriptores de archivo en la máquina.

Dado que el XML de libvirt proviene de una fuente confiable ( el demonio de libvirt) no se cree que esto haya podido ser explotable.

Esto fue corregido en libguestfs ≥ 1.27.9 y la corrección fue trasladada a versiones estables ≥ 1.26.2, ≥ 1.24.9, ≥ 1.22.10 y ≥ 1.20.13.

Shellshock (bash CVE-2014-6271)

Este error de bash afecta indirectamente a libguestfs. Para más información vea: https://www.redhat.com/archives/libguestfs/2014-September/msg00252.html

CVE-2014-8484

CVE-2014-8485

Estos dos errores en binutils afectan al programa GNU strings(1) , y por lo tanto a "guestfs_strings" en guestfs(3) y "guestfs_strings_e" en guestfs(3) APIs en libguestfs. Ejecutar strings sobre un archivo no confiable podría causar la ejecución de código arbitrario (confinado al appliance de libguestfs).

En libguestfs ≥ 1.29.5 y ≥ 1.28.3, libguestfs usa la opción "strings" -a para evitar el análisis BFD del archivo.

CVE-2015-5745

https://bugzilla.redhat.com/show_bug.cgi?id=1251157

Esta no es una vulnerabilidad en libguestfs, pero como siempre le damos un puerto virtio-serial a cada huésped (ya que así es como ocurre la comunicación huésped-host), es posible una escalada desde el appliance al proceso qemu del host. Esto podría afectarle si:

  • su programa libguestfs ejecuta programas no confiables fuera del huésped (usando "guestfs_sh" en guestfs(3) etc.), o
  • se encontró otra vulnerabilidad en (por ejemplo) el código del sistema de archivos del kernel que permitiera a un sistema de archivos malformado tomar el control del appliance.

Si usa sVirt para confinar a qemu, eso frustraría algunos ataques.

Permisos de .ssh y .ssh/authorized_keys

https://bugzilla.redhat.com/1260778

Las herramientas virt-customize(1), virt-sysprep(1) y virt-builder(1) tienen una opción --ssh-inject para inyectar una clave SSH en imágenes de disco de máquinas virtuales. Pueden crear un directorio ~user/.ssh y un archivo ~user/.ssh/authorized_keys en el huésped para hacer esto.

En libguestfs < 1.31.5 y libguestfs < 1.30.2, el nuevo directorio y archivo obtendrían el modo 0755 y el modo 0644 respectivamente. Sin embargo, estos permisos (especialmente para ~user/.ssh) son más amplios que los permisos que usa OpenSSH. En la libguestfs actual, el directorio y el archivo se crean con el modo 0700 y el modo 0600.

CVE-2015-8869

https://bugzilla.redhat.com/CVE-2015-8869

Esta vulnerabilidad en OCaml podría afectar a las herramientas virt escritas en el lenguaje de programación OCaml. Afecta solo a plataformas de 64 bits. Debido a que este error afecta a la generación de código, es difícil predecir qué software específico podría verse afectado, y por lo tanto nuestra recomendación es que recompile libguestfs usando una versión del compilador de OCaml donde este error haya sido corregido (o pida a su distribución de Linux que haga lo mismo).

CVE-2017-5208, CVE-2017-5331, CVE-2017-5332, CVE-2017-5333, CVE-2017-6009, CVE-2017-6010, CVE-2017-6011

Múltiples vulnerabilidades en el wrestool(1) programa en el paquete "icoutils" pueden ser explotadas para la ejecución de código local en el host.

Cuando la inspección de libguestfs (vea "Inspección de seguridad" arriba) detecta un huésped Windows XP o Windows 7 y se le pide encontrar un icono asociado para el huésped, descargará un archivo no confiable del huésped y ejecutará "wrestool -x" sobre ese archivo. Esto puede llevar a la ejecución de código local en el host. Cualquier imagen de disco o huésped puede ser manipulado para parecer un huésped Windows a la inspección de libguestfs, así que el hecho de que no tenga huéspedes Windows no le ayuda.

Cualquier programa que llame a la API de libguestfs "guestfs_inspect_get_icon" podría ser vulnerable. Esto incluye a virt-inspector(1) y virt-manager(1).

La solución es actualizar a la versión no vulnerable de icoutils (al menos 0.31.1).

CVE-2017-7244, CVE-2017-7245, CVE-2017-7246

Múltiples vulnerabilidades en PCRE podrían ser explotadas para hacer fallar libguestfs (es decir, causar una denegación de servicio) al realizar la inspección de una máquina virtual no confiable.

La solución es actualizar a una versión de PCRE con estos errores corregidos (versión upstream ≥ 8.41).

CVE-2018-11806

Vulnerabilidades que afectan al networking de usuario de qemu (SLIRP) permiten que una imagen de sistema de archivos maliciosa tome el control de qemu y desde allí ataque al host.

Esto afecta a libguestfs cuando el backend está configurado en "direct" y el networking está habilitado.

El backend direct es el predeterminado upstream, pero no en algunas distribuciones downstream de Linux incluyendo Fedora, Red Hat Enterprise Linux y CentOS. También podría haber sido seleccionado si usted configuró la variable de entorno "LIBGUESTFS_BACKEND=direct" o llamó a "guestfs_set_backend (g, "direct")".

El networking es habilitado automáticamente por algunas herramientas (por ejemplo virt-builder(1)), o se habilita si su código llamó a "guestfs_set_network (g, 1)" (lo cual no es el predeterminado).

El backend libvirt no está afectado.

La solución es actualizar qemu a una versión que contenga la corrección (vea guestfs-security(1) — libguestfs

NAME

guestfs-security

reporting security problems with libguestfs

DESCRIPTION

This page explains how to report security problems found in the libguestfs library. It also lists historical security issues that have affected libguestfs.

REPORTING SECURITY PROBLEMS

To report a security problem, please use the private security mailing list: "security at libguestfs.org". Do NOT report security problems on the public mailing list or bug tracker.

When reporting a security problem, please include the following information:

  • The version of libguestfs affected.
  • The operating system and version you are using.
  • A clear and concise description of the vulnerability.
  • Steps to reproduce the vulnerability.
  • Any relevant logs or error messages.
  • A proof of concept (if available).

We will acknowledge your report within 2 business days and will work with you to address the issue.

GENERAL ISSUES

If you have a question or find a bug that is not security-related, please use the public mailing list:

https://lists.nongnu.org/mailman/listinfo/libguestfs

You can also check the bug tracker:

https://bugzilla.redhat.com/buglist.cgi?component=libguestfs&product=Virtualization+Tools

This section lists some historical security issues that have affected libguestfs.

CVE-2018-10701

https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2018-10701 https://lists.gnu.org/archive/html/qemu-devel/2018-05/msg01012.html.

CVE-2022-2211

https://bugzilla.redhat.com/CVE-2022-2211

La función "get_keys" en libguestfs-common/options/keys.c recopila esas opciones de --key de la línea de comandos en un nuevo array que coinciden con un dispositivo de bloque particular que se está descifrando para inspección. La función tiene la intención de dimensionar el array de resultados de tal manera que potencialmente todas las opciones de --key, más un elemento terminador "NULL", quepan en él. El código utiliza erróneamente la macro "MIN" en lugar de "MAX" y, por lo tanto, solo se asigna un elemento antes del terminador "NULL".

Pasar exactamente dos opciones de --key ID:... en la línea de comandos para el dispositivo de bloque cifrado "ID" hace que "get_keys" sobrescriba el terminador "NULL", lo que lleva a una lectura fuera de límites en "decrypt_mountables", archivo libguestfs-common/options/decrypt.c.

Pasar más de dos opciones de --key ID:... en la línea de comandos para el dispositivo de bloque cifrado "ID" hace que la propia función "get_keys" realice escrituras fuera de límites. El síntoma más común es un bloqueo con "SIGSEGV" más adelante.

Este problema afecta, en términos generales, a todas las utilidades basadas en libguestfs que aceptan --key, a saber: "guestfish", "guestmount", "virt-cat", "virt-customize", "virt-diff", "virt-edit", "virt-get-kernel", "virt-inspector", "virt-log", "virt-ls", "virt-sparsify", "virt-sysprep", "virt-tail", "virt-v2v".
