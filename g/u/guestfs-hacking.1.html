EL CÓDIGO

FUENTE

El código fuente de libguestfs se encuentra en el repositorio de github https://github.com/libguestfs/libguestf

s

Grandes cantidades de código de plantilla en libguestfs (RPC, enlaces, documentación) se generan. Esto significa que muchos archivos fuente parecerán faltar en una comprobación directa de git. Tienes que ejecutar el generador ("./configure && make -C generator") para crear esos

archivos.

Libguestfs utiliza un sistema de compilación basado en autotools, siendo los archivos principales configure.ac y Makefile.am. Ver "EL SISTEMA DE

COMPILACIÓN".

El subdirectorio generator contiene el generador, además de archivos que describen la API. El subdirectorio lib contiene el código fuente de la biblioteca. Los subdirectorios appliance y daemon contienen el código fuente para el código que construye el appliance y el código que se ejecuta en el appliance, respectivamente. Otros directorios se describen en la sección "SUBDIRECTORIOS DEL CÓDIGO FUENTE" más

abajo.

Aparte del hecho de que todos los puntos de entrada de la API pasan por algo de código generado, la biblioteca es sencilla. (De hecho, incluso el código generado está diseñado para ser legible, y debería leerse como código ordinario). Algunas acciones se ejecutan completamente en la biblioteca, y están escritas como funciones C en archivos bajo lib. Otras se reenvían al demonio donde (después de algo de serialización RPC generada) aparecen como funciones C en archivos bajo daemon

.

Para compilar desde el código fuente, lee primero el guestfs-build

ing(1).

EL SISTEMA DE

CONSTRUCCIÓN

Libguestfs utiliza el sistema de construcción GNU autotools (autoconf, automake, libtool)

.

El script ./configure se genera a partir de configure.ac y m4/guestfs-*.m4. La mayor parte del script configure está dividida en muchos archivos de macros m4 por tema, por ejemplo m4/guestfs-daemon.m4 trata sobre las dependencias del

demonio.

La tarea del Makefile.am de nivel superior es principalmente listar los subdirectorios ("SUBDIRS") en el orden en que deben ser

compilados.

common-rules.mk se incluye en cada Makefile.am (nivel superior y subdirectorios). subdir-rules.mk se incluye solo en los archivos Makefile.am de los

subdirectorios.

Hay muchos objetivos de make. Use este comando para listarlos

API

Debido a que grandes cantidades de código de plantilla en libguestfs son generados, esto facilita la extensión de la API de

libguestfs.

Para añadir una nueva acción de API hay dos

cambios:
1
.
Necesita añadir una descripción de la llamada (nombre, parámetros, tipo de retorno, pruebas, documentación) a generator/actions_*.ml y posiblemente generator/proc_nr.ml.

Hay dos tipos de acción de API, dependiendo de si la llamada pasa al demonio en el dispositivo o es atendida enteramente por la biblioteca (ver "ARQUITECTURA" en guestfs-internals(1)). "guestfs_sync" en guestfs(3) es un ejemplo de lo primero, ya que la sincronización se hace en el dispositivo. "guestfs_set_trace" en guestfs(3) es un ejemplo de lo segundo, ya que un indicador de rastreo se mantiene en el manejo y todo el rastreo se hace en el lado de la

biblioteca.

La mayoría de las nuevas acciones son del primer tipo, y se añaden a la lista "daemon_functions". Cada función tiene un número de procedimiento único utilizado en el protocolo RPC que se asigna a esa acción cuando publicamos libguestfs y no puede ser reutilizado. Tome el último número de procedimiento e

incrémentelo.

Para las acciones solo de biblioteca del segundo tipo, añada a la lista "non_daemon_functions". Dado que estas funciones son atendidas por la biblioteca y no viajan por el mecanismo RPC al demonio, estas funciones no necesitan un número de procedimiento, y por lo tanto el número de procedimiento se establece en -1

.
2
.
Implemente la acción (en C):

Para las acciones del demonio, implemente la función "do_<name>" en el directorio "da

emon/".

Para las acciones de la biblioteca, implemente la función "guestfs_impl_<name>" en el directorio "

lib/".

En cualquier caso, use

otra función como ejempl
o de qué hacer.
3
.
Como alternativa al paso 2: Desde libguestfs 1.38, las acciones del demonio pueden ser implementadas en OCaml. Tiene que establecer la bandera "impl = OCaml ..." en el generador. Eche un vistazo a daemon/file.ml p
ara un
ejemplo.

Después de hacer estos cambios, use "make" para

compilar.

Tenga en cuenta que no necesita implementar el RPC, los enlaces de lenguaje, las páginas de manual ni nada más. Todo se genera automáticamente a partir de la descripción

OCaml.

PRUEBAS DE LA API

Las pruebas de la API "guestfs_command" se encuentran en el directorio tests/c-api.

Para ejecutar las pruebas, configure el paquete, luego ejecute "make check".

Cada prueba es un programa C separado. La mayoría de las pruebas ejecutan un único comando de guestfs y comprueban el valor de retorno, la salida estándar y el error estándar. Algunas pruebas más complejas crean una imagen de disco, la montan, crean archivos en ella, la desmontan, y luego la inspeccionan.

Hay varias formas de controlar la ejecución de pruebas:

  • "make check" ejecuta todas las pruebas.
  • "make check-valgrind" ejecuta las pruebas bajo Valgrind.
  • "make check-valgrind-local-guests" ejecuta las pruebas bajo Valgrind usando invitados locales de libvirt.
  • "make check-direct" ejecuta todas las pruebas usando el backend de appliance predeterminado.
  • "make check-valgrind-direct" ejecuta las pruebas bajo Valgrind usando el backend de appliance predeterminado.

Puede controlar qué pruebas se ejecutan estableciendo las variables de entorno TESTS y SKIP. Por ejemplo, para ejecutar sólo la prueba 3:

make check TESTS=test-guestfs-command.3

Para omitir la prueba 3:

make check SKIP=test-guestfs-command.3

Puede ver una lista de todas las pruebas ejecutadas y sus resultados en el archivo tests/c-api/results.log.

Algunas pruebas sólo están diseñadas para ejecutarse en determinadas configuraciones de libguestfs. Por ejemplo, algunas pruebas usan comandos que pueden no funcionar en todas las variaciones de libguestfs. Una prueba con el prerrequisito de "Siempre" significa que se ejecutará incondicionalmente.

Además, los empaquetadores pueden omitir pruebas individuales estableciendo variables de entorno antes de ejecutar "make check".

SKIP_TEST_<CMD>_<NUM>=1

ej: "SKIP_TEST_COMMAND_3=1" omite la prueba #3 de "guestfs_command" en guestfs(3).

o:

SKIP_TEST_<CMD>=1

ej: "SKIP_TEST_ZEROFREE=1" omite todas las pruebas de "guestfs_zerofree" en guestfs(3).

Los empaquetadores pueden ejecutar sólo ciertas pruebas estableciendo, por ejemplo:

TEST_ONLY="vfs_type zerofree"

Consulte tests/c-api/tests.c para obtener más detalles sobre cómo funcionan estas variables de entorno.

Depuración de nuevas APIs

Pruebe que las nuevas acciones funcionen antes de enviarlas.

Puede usar guestfish para probar nuevos comandos.

La depuración del demonio es un problema porque se ejecuta dentro de un entorno mínimo. Sin embargo, puede imprimir mensajes en stderr dentro del demonio, y aparecerán si usa "guestfish -v".

AÑADIR UNA NUEVA LIGADURA DE IDIOMA

Todas las ligaduras de idiomas deben ser generadas por el generador (consulte el subdirectorio generator).

Aún no hay documentación para esto. Le sugerimos que consulte una ligadura existente, por ejemplo, generator/ocaml.ml o generator/perl.ml.

Añadir pruebas para ligaduras de idiomas

Las ligaduras de idiomas deben venir con pruebas. Anteriormente, las pruebas de ligaduras de idiomas eran bastante ad hoc, pero hemos estado intentando formalizar el conjunto de pruebas que cada ligadura de idioma debería utilizar.

Actualmente, sólo las ligaduras OCaml y Perl implementan el conjunto completo de pruebas, y las ligaduras OCaml son las canónicas, por lo que debería emular lo que hacen las pruebas OCaml.

Este es el esquema de numeración utilizado por las pruebas:

- 000+ pruebas básicas:

  010  carga de la biblioteca
  020  crear
  030  flags de creación
  040  crear múltiples handles
  050  prueba de configuración y obtención de propiedades de configuración
  060  cierre explícito
  065  cierre implícito (en lenguajes con recolección de basura)
  070  argumentos opcionales
  080  versión
  090  valores de retorno

- 100  lanzamiento, creación de particiones y LVs y sistemas de archivos

- 400+ eventos:

  410  evento de cierre
  420  mensajes de log
  430  mensajes de progreso

- 800+ pruebas de regresión (específicas del idioma)

- 900+ cualquier otra prueba personalizada para el idioma

Para ahorrar tiempo al ejecutar las pruebas, sólo 100, 430, 800+, 900+ deberían lanzar el handle.

FORMATEO DEL CÓDIGO

Nuestro código fuente C generalmente se adhiere a algunas convenciones básicas de formato de código. La base de código existente no es totalmente consistente en este aspecto, pero preferimos que el código contribuido tenga un formato similar. En resumen, use espacios, no TABs, para la indentación, use 2 espacios por cada nivel de indentación y, aparte de eso, siga el estilo K&R.

Si usa Emacs, agregue lo siguiente a uno de sus archivos de inicio (por ejemplo, ~/.emacs) para ayudar a asegurar que la indentación sea correcta:

;;; En libguestfs, indentar con espacios en todas partes (no TABs).
;;; Excepciones: modos Makefile y ChangeLog.
(add-hook 'find-file-hook
    '(lambda () (if (and buffer-file-name
                         (string-match "/libguestfs\\>"
                             (buffer-file-name))
                         (not (string-equal mode-name "Change Log"))
                         (not (string-equal mode-name "Makefile")))
                    (setq indent-tabs-mode nil))))

;;; Al editar fuentes C en libguestfs, usar este estilo.
(defun libguestfs-c-mode ()
  "Modo C con valores predeterminados ajustados para usar con libguestfs."
  (interactive)
  (c-set-style "K&R")
  (setq c-indent-level 2)
  (setq c-basic-offset 2))
(add-hook 'c-mode-hook
          '(lambda () (if (string-match "/libguestfs\\>"
                              (buffer-file-name))
                          (libguestfs-c-mode))))

Los objetivos útiles son:

"make check"

Esto se implementa utilizando el objetivo regular de automake "TESTS". Consulte la documentación de automake para obtener detalles.

"make check-valgrind"
Ejecuta un subconjunto de la suite de pruebas bajo valgrind.

Ver "VALGRIND" abajo.

"make check-valgrind-local-guests"
Ejecuta un subconjunto de la suite de pruebas bajo valgrind usando invitados de libvirt instalados localmente (sólo lectura).
"make check-direct"
Ejecuta todas las pruebas usando el backend de appliance predeterminado. Esto sólo tiene algún efecto si se seleccionó un backend no predeterminado usando "./configure --with-default-backend=..."
"make check-valgrind-direct"
Ejecuta un subconjunto de la suite de pruebas bajo valgrind usando el backend de appliance predeterminado.
"make check-with-upstream-qemu"
Ejecuta todas las pruebas usando un binario local de qemu. Busca el binario de qemu en QEMUDIR (por defecto $HOME/d/qemu), pero puedes establecerlo a otro directorio en la línea de comandos, por ejemplo: 
make check-with-upstream-qemu QEMUDIR=/usr/src/qemu
"make check-with-upstream-libvirt"
Ejecuta todas las pruebas usando un libvirt local. Esto sólo tiene algún efecto si se seleccionó el backend de libvirt usando "./configure --with-default-backend=libvirt"

Busca libvirt en LIBVIRTDIR (por defecto $HOME/d/libvirt), pero puedes establecerlo a otro directorio en la línea de comandos, por ejemplo:

make check-with-upstream-libvirt LIBVIRTDIR=/usr/src/libvirt
"make check-slow"
Ejecuta algunas pruebas lentas/de larga duración que no se ejecutan por defecto.

Para marcar una prueba como lenta/de larga duración:

  • Agrégala a la lista de "TESTS" en el Makefile.am, igual que una prueba normal.
  • Modifica la prueba para que compruebe si la variable de entorno "SLOW=1" está establecida, y si no está establecida, la omite (es decir, retorna con código de salida 77). Si usas tests/functions.sh, puedes llamar a la función "slow_test" para esto.
  • Agrega una variable "SLOW_TESTS" al Makefile.am listando las pruebas lentas.
  • Agrega una regla al Makefile.am: 
    check-slow:
  $(MAKE) check TESTS="$(SLOW_TESTS)" SLOW=1
"sudo make check-root"
Ejecuta algunas pruebas que requieren privilegios de root. Se supone que estas son seguras, pero ten cuidado. Tienes que ejecutar esto como root (por ejemplo, usando explícitamente sudo(8)).

Para marcar una prueba como que requiere root:

  • Agrégala a la lista de "TESTS" en el Makefile.am, igual que una prueba normal.
  • Modifica la prueba para que compruebe si euid == 0, y si no está establecida, la omite (es decir, retorna con código de salida 77). Si usas tests/functions.sh, puedes llamar a la función "root_test" para esto.
  • Agrega una variable "ROOT_TESTS" al Makefile.am listando las pruebas de root.
  • Agrega una regla al Makefile.am: 
    check-root:
  $(MAKE) check TESTS="$(ROOT_TESTS)"
"make check-all"
Equivalente a ejecutar todas las reglas "make check*" excepto "check-root".
"make check-release"
Ejecuta un subconjunto de reglas "make check*" que son requeridas para pasar antes de que un tarball pueda ser liberado. Actualmente esto es:
  • check
  • check-valgrind
  • check-direct
  • check-valgrind-direct
  • check-slow
"make installcheck"
Ejecuta "make check" en la copia instalada de libguestfs.

La versión de libguestfs instalada que se está probando, y la versión del árbol de fuentes de libguestfs deben ser la misma.

Haz:

./configure
make clean ||:
make
make installcheck

VALGRIND

Cuando ejecutas "make check-valgrind", busca cualquier Makefile.am en el árbol que tenga un objetivo "check-valgrind:" y lo ejecuta.

Escribir el Makefile.am y las pruebas correctamente para usar valgrind y trabajar con las pruebas paralelas de automake es sutil.

CÓMO SE COMPILAN Y ENLAZAN LOS PROGRAMAS OCAML

Principalmente esta sección es "cómo hacemos que automake y ocamlopt funcionen juntos" ya que los programas OCaml en sí mismos son fáciles de compilar.

Automake no tiene soporte nativo para programas OCaml, ni ocamlc ni ocamlopt. Lo que hacemos en su lugar es tratar los programas OCaml como programas C que resulta que contienen estos "otros objetos" ("DEPENDENCIES" en jerga de automake) que resulta que son los objetos OCaml. Esto funciona porque los programas OCaml suelen tener archivos C para enlaces nativos, etc.

Así, un programa típico se describe solo con sus fuentes C:

virt_customize_SOURCES = ... crypt-c.c perl_edit-c.c

Para programas que no tienen fuentes C explícitas, creamos un archivo vacío *dummy.c* y lo listamos en su lugar:

virt_resize_SOURCES = dummy.c

Los objetos OCaml que contienen la mayor parte del código se listan como dependencias de automake (también se pueden listar otras dependencias):

virt_customize_DEPENDENCIES = ... customize_main.cmx

La única otra cosa especial que necesitamos hacer es proporcionar un comando de enlace personalizado. Esto es necesario porque automake no ensamblará el comando ocamlopt, la lista de objetos y las bibliotecas "-cclib" en el orden correcto de lo contrario.

virt_customize_LINK = \
    $(top_builddir)/ocaml-link.sh -cclib '-lutils' -- ...

Las reglas reales, que puedes examinar en *customize/Makefile.am*, son un poco más complicadas que esto porque tienen que manejar:

  • Compilación para código byte o código nativo.
  • Las reglas de patrón necesarias para compilar las fuentes OCaml a objetos.

    Estas ahora se mantienen en *subdir-rules.mk* en el nivel superior, que se incluye en cada subdirectorio *Makefile.am*.

  • Añadir archivos fuente OCaml a "EXTRA_DIST".

    Automake no es consciente de la lista completa de fuentes para un binario, por lo que no las añadirá todas automáticamente.

sobrescrito.

Archivo lib/proto.c


Este es el código utilizado para enviar y recibir mensajes RPC y (para ciertos tipos de mensajes) para realizar transferencias de archivos. Este código es impulsado por las acciones generadas (lib/actions-*.c). Hay cinco casos diferentes a considerar:



  
1.

  
Una función no demonio (por ejemplo, "guestfs_set_verbose" en
      guestfs(3)). No hay RPC involucrado en absoluto, todo se maneja dentro de la biblioteca.

  
2.

  
Un RPC simple (por ejemplo, "guestfs_mount" en guestfs(3)). Escribimos la solicitud, luego leemos la respuesta. La secuencia de llamadas es:
        
guestfs_int_send
guestfs_int_recv


  

  
3.

  
Un RPC con parámetros "FileIn" (por ejemplo,
      "guestfs_upload" en guestfs(3)). Escribimos la solicitud,
      luego escribimos los archivos, luego leemos la respuesta. La secuencia de llamadas es:
        
guestfs_int_send
guestfs_int_send_file  (posiblemente varias veces)
guestfs_int_recv


  

  
4.

  
Un RPC con parámetros "FileOut" (por ejemplo,
      "guestfs_download" en guestfs(3)). Escribimos la solicitud,
      luego leemos la respuesta, luego leemos los archivos. La secuencia de llamadas es:
        
guestfs_int_send
guestfs_int_recv
guestfs_int_recv_file  (posiblemente varias veces)


  

  
5.

  
Parámetros "FileIn" y
      "FileOut". No hay llamadas como esta en la API actual, pero se implementarían como una combinación de los casos 3 y 4.

Mini-biblioteca para escribir líneas de comando de qemu y archivos de configuración de qemu.

Existen algunas deficiencias en el modelo utilizado para las opciones de qemu que no están claras hasta que intentas convertir las opciones en un archivo de configuración. Sin embargo, si intentáramos modelar las opciones con más detalle, esta biblioteca sería muy difícil de usar e incompatible con versiones anteriores de qemu. Esperamos que el modelo actual sea un buen compromiso.

Como referencia, aquí están los problemas:

  • Hay inconsistencia en qemu entre las opciones y el archivo de configuración, por ejemplo, "-smp 4" se convierte en:

  • En "-opt key=value,..." la "key" es en realidad un especificador de árbol/arreglo. La forma en que funciona esto es complicada pero se insinúa aquí: http://git.qemu.org/?p=qemu.git;a=blob;f=util/keyval.c;h=93d5db6b590427e412dfb172f1c406d6dd8958c1;hb=HEAD
