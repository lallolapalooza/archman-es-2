La biblioteca, vinculada al programa principal, crea el proceso hijo y por lo tanto el appliance en la

función "guestfs_launch" de

guestf

s(3) [
[24]].

Dentro del appliance hay un núcleo Linux y una pila completa de herramientas de espacio de usuario (como programas LVM y ext2) y un pequeño demonio de control llamado "guestfsd". La biblioteca se comunica con "guestfsd" usando llamadas a procedimiento remoto (RPC). Existe una correspondencia mayormente uno a uno entre las llamadas a la API de libguestfs y las llamadas RPC al demonio. Por último, la(s) imagen(es) de disco se adjuntan al proceso qemu, el cual traduce el acceso a dispositivos por parte del núcleo

Linux del appliance en accesos a la imagen.

Un malentendido común es que el appliance "es" la máquina virtual. Aunque la imagen de disco a la que se ha conectado podría ser también usada por alguna máquina virtual, libguestfs no lo sabe ni le importa. (Pero a usted le importará si tanto el proceso qemu de libguestfs como su máquina virtual están intentando actualizar la imagen de disco al mismo tiempo, ya que esto normalmente resulta en una corrupción masiva del

disco)
.

MÁQUINA DE

ESTADOS

libguestfs usa una máquina de estados para modelar el proceso hijo: | guestfs_create / guestfs_create_flags | | ____V_____ / \ | CONFIG | \__________/ ^ ^ \ | \ \ guestfs_launch | _\__V______ | / \ | | LAUNCHING | | \___________/ | / | guestfs_launch | / __|____V / \ | READY |

\________/ 
Las transiciones normales son (1) CONFIG (cuando se crea el manejador,
    pero no hay proceso hijo), (2) LAUNCHING (cuando el proceso hijo se está
    iniciando), (3) READY, lo que significa que el appliance está activo, se pueden emitir
    acciones al proceso hijo y este las puede llevar a
cabo.

El huésped puede ser terminado por "guestfs_kill_subprocess" en guestfs(3

)

, o puede morir de forma asíncrona en cualquier momento (p. ej. debido a algún error interno), y eso causa que el estado vuelva a

CONFIG.

Los comandos de configu

ración para qemu como
"guestfs_set_path" en

guestfs(3

)

solo se pueden emitir cuando se está en el estado

CONFIG. 
               La API ofrece una única llamada que va de CONFIG a través de LAUNCHING a
    READY. "guestfs_launch"
en

guestfs(3

)

se bloquea hasta que el proceso hijo está READY para aceptar comandos (o hasta que haya algún fallo o tiempo de espera agotado). "guestfs_launch" en guestfs(3

)

mueve internamente el estado de CONFIG a LAUNCHING mientras se está ejecutando. Las acciones de la API como "guestfs_mount"

en

guestfs(3) solo se pueden emitir cuando se está en el estado READY. Estas llamadas a la API se bloquean esperando a que el comando se lleve a cabo. No hay versiones no bloqueantes, y no hay forma de emitir más de un comando por manejador al mismo tiempo. Finalmente, el proceso hijo envía mensajes asíncronos de vuelta al programa principal, como mensajes de registro del kernel. Puede registrar una función de retorno de llamada para recibir estos

mensajes.

Le champ de longueur totale permet au

Par conséquent, la longueur totale est limitée à "GUESTFS_MESSAGE_MAX" octets (actuellement 4 Mo), ce qui signifie que la taille effective de toute requête est limitée à une valeur inférieure à cette taille. Un masque de bits dans l'en-tête indique quels arguments facultatifs sont significatifs. Le morceau final a

il n'y a pas de fonctions qui ont plus d'un paramètre FileIn. Cependant, cela est (théoriquement) supporté, en envoyant la séquence de morceaux pour chaque paramètre FileIn l'une après l'autre (de gauche à droite). La bibliothèque (l'expéditeur) et

le

démon (le récepteur) peuvent annuler le transfert. La bibliothèque le fait en envoyant un morceau avec un drapeau spécial défini pour indiquer l'annulation. Lorsque le démon voit cela, il annule tout le RPC, n'envoie [[70]] aucune réponse, et revient à la lecture de la requête suivante. Le démon peut aussi

annuler.

Il le fait en écrivant un mot spécial "GUESTFS_CANCEL_FLAG" dans la socket. La bibliothèque écoute cela pendant le transfert, et si elle le reçoit, elle annulera le transfert (elle envoie un morceau d'annulation). Le mot spécial est choisi de telle sorte que même si l'annulation se produit juste à la fin du transfert (après que la bibliothèque a fini d'écrire et a commencé à écouter la réponse), le drapeau d'annulation "spurious" ne sera pas confondu avec le message de réponse. Ce protocole permet le transfert de fichiers de

taille

arbitraire (pas de limite 32 bits), et aussi de fichiers dont la taille n'est pas connue à l'avance (par ex. à partir de tuyaux (pipes) ou de sockets). Cependant, les morceaux sont plutôt petits ( "GUESTFS_MAX_CHUNK_SIZE"), de sorte que ni la bibliothèque ni le démon n'ont besoin de conserver beaucoup de données en

mémoire.
