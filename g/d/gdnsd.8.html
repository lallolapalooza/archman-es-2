DESCRIPCIÓ

N

gdnsd es un demonio DNS autoritativo

muy rápido, liger
o y ampliable.

CONFIGURACIÓN

BÁSICA

El archivo de configuración principal es el archivo llamado config en el directorio de

configuración.

Ten en cuenta que el archivo de configuración no tiene que existir para un inicio exitoso. Sin un archivo de configuración, gdnsd cargará todas las zonas en el directorio de zonas (por defecto "/etc/gdnsd/zones/") y escuchará en el puerto 53 de 0.0.0.0 y "::" usando la configu

ración pred
eterminada.

COMANDOS
-
c
Establece el directorio de configuración, por defecto es /etc/gdnsd. El directorio de zonas es el subdirectorio zones/ del directorio de
configuración.
-
D
Habilita la salida de registro de nivel de depuración adicional según
corresponda.
-
l
Envía la salida de registro a syslog en lugar de a stderr por defecto. Esto se activa implícitamente por la acción "daemonize" y también se recomienda al ejecutar como servicio systemd, para capturar la información de
prioridad.
-
S
Fuerza la opción de configuración "zones_strict_data" a true para esta invocación, independientemente de la configuración en el archivo de configuración. Esto es mayormente útil para la validación durante la opción "checkconf
".
-
R
Modo de reemplazo para "start" y "daemonize":

Normalmente, si otra instancia del servidor tiene el socket de control del servidor bloqueado, un intento de "start" o "daemonize" fallará. Con esta bandera activada, el nuevo servidor se conectará al antiguo a través de su socket de control e intentará una toma de control elegante y sin tiempo de inactividad de las operaciones. Esto permite que tanto cambios de código como de configuración se realicen sin perder solicitudes en la mayoría de los casos y es, en general, bastante transparente. Consulta la documentación de gdnsdctl(8) sobre "replace" para más información, ya q

ue esa es la interfaz preferida
para esta funcionalidad.
-
i
Modo idempotente para "start" y "daemonize":

Normalmente, si otra instancia del servidor tiene el socket de control del servidor bloqueado, un intento de "start" o "daemonize" fallará. Con esta bandera activada, si

otra instancia ya está en ejec
ución, esta instancia
informará de éxito y saldrá c
on estado cero inmediatamente.

Verifica la validez del archivo de configuración y los archivos de zona, estableciendo el estado de salida adecuadamente (0 para éxito). El mismo código se ejecuta implícitamente durante el inicio; checkconf simplemente sale en el último punto antes de que se deban tomar acciones reales de tiempo de ejecución, como la adquisición de
sockets.

Inicia gdnsd como un proceso en primer plano de servidor DNS en tiempo de ejecución, emitiendo la salida de registro a

daemoni

Inicia gdnsd como un proceso de demonio en segundo plano desprendido en una nueva sesión, con PID 1 (init) como padre, emitiendo la salida de registro directamente a syslog. El
proceso inicial en primer plano no emitirá ninguna salida en la terminal si tiene éxito, pero esperará a que el demonio en segundo plano complete las operaciones de ini

Cualquier otra opción de línea de comandos se tratará como inválida, lo que resultará en la visualización de un texto de ayuda corto en STDERR y la salida con un estado de salida distinto de cero. Esto incluye cosas como el omnipresente --help y --ver

sio
n.

PRIVILEGIO

S

Este servicio no presta atención a, ni intenta comprobar o modificar, nada sobre el entorno de seguridad en tiempo de ejecución o el conjunto de privilegios, o si está o no ejecutándose como "root", ni intenta ninguna acción que comúnmente requeriría privilegios de "root", como alterar sus propios límites de memlock o elevar su propia prioridad de proceso. La única excepción es que el código asume ciegamente que el enlace de sus puertos de escucha DNS, que por defecto están en el rango privilegiado, simplemente

funcionará.

Se espera que todas estas cosas sean gestionadas por mecanismos externos: ya sea un sistema init similar a systemd qu

e pueda hacerlo todo de forma declarativa, o una combinación de herramientas en un script de inicio para un sist
ema init tradicional que se encargue de los ajustes privilegiados necesarios y/o de la jaula de seguridad / ACL, etc.

COMPATIBILIDAD CON

SYSTEMD

Cuando se ejecuta como servicio systemd, se debe usar "start" en lugar de "daemonize", se debe usar la bandera "-l" y el tipo debe establecerse a "Type=notify" con "NotifyAccess=all". Estas últimas opciones harán que systemd establezca $NOTIFY_SOCKET para el demonio, y el demonio a su vez lo usará para enviar una notificación de preparación cuando haya terminado con las tareas de inicio iniciales y esté listo para atender solicitudes. Se debe usar "gdnsdctl -l stop" para el comando "Exec

Stop=".

El árbol de código fuente contiene un archivo de un

idad de systemd de ejemplo con valores predeterm
inados razonables para un despliegue en producción.

ARCHIVOS DE ZONA -

RFC1035

El directorio para los archivos de zona estándar RFC1035 (el backend de datos de zona por defecto) es el subdirectorio llamado zones/ en el directorio de configuración, por lo que el valor por defecto sería /etc/gdnsd/zones/

.

Los archivos de zona RFC1035 son el formato de archivo de zona tradicional que uno usa típicamente con, por ejemplo, BIND. Para más información sobre el formato interno y el procesamiento de estos archivos, consulta gdnsd.zonefile(5). Esta sección trata sobre cómo se gestiona el directorio en

sí.

Todos los archivos en el directorio de zonas se consideran archivos de zona. En general, debe haber exactamente un archivo por zona, y el nombre de archivo debe coincidir con el nombre de la zona. Los nombres de archivo que comienzan con "." se ignoran. Todos los archivos de zona deben ser archivos regulares (a diferencia de directorios, enlaces simbólicos, sockets, etc)

.

Para mejor soportar el caso especial de las zonas de delegación in-addr.arpa sin clase estilo RFC 2137 (que contienen barras diagonales), cualquier símbolo "@" en el nombre de archivo se traducirá a una barra diagonal ("/") al transformar un nombre de archivo en su nombre de zona correspondiente

.

Por razones similares, si tu servidor está destinado a servir la raíz del DNS, el nombre de archivo para la zona raíz debe ser el nombre de archivo especial ROOT_ZONE, en lugar del nombre de archivo literal imposible .. Debido a que los servidores autoritativos no pueden servir doso dominios que tienen una relación padre<->hijo correctamente, un servidor raíz no puede servir ninguna otra zona, por lo que este sería el único archivo de

zona.

Se reconocen las secuencias de escape estándar de archivos de zona DNS dentro de los nombres de archivo (por ejemplo, "\." para un punto dentro de una etiqueta, o "\NNN" donde NNN es un entero decimal en el rango 0 - 255), si por alguna razón necesita un carácter extraño en su nombre de

zona.

Los puntos finales en los nombres de archivos de zona se ignoran; por ejemplo, example.com y example.com. son funcionalmente

equivalentes.

Las zonas duplicadas (por ejemplo, tener ambas representaciones anteriores de "example.com" presentes en el directorio de zonas y/o agregar un mapeo de mayúsculas/minúsculas diferente como EXample.Com) son

ilegales.

Las subzonas (por ejemplo, tener archivos de zona tanto para "example.com" como para "subz.example.com")

también son
ilegales.

ARCHIVOS DE ZONA -

RECARGA

"gdnsdctl reload-zones" desencadena la recarga de todos los datos de zona. La operación de recarga se realiza en un hilo separado del servidor principal y no interrumpe el flujo de solicitudes

DNS.

"gdnsdctl" esperará a que el servidor complete la operación de carga e informará el éxito o el fallo de la transacción de recarga a través de stdout y su estado de salida del

proceso.

Si ocurre algún fallo durante la operación de recarga, toda la transacció

n de recarga se descarta sin ningún efecto sobre los datos de ejecución anteri
ores que aún se están utilizando para responder a las consultas en curso.

ARCHIVO DE ESTADO DE ADMINISTRACIÓN - //lib/gdnsd/admin_stat

e

Este archivo es la entrada para las anulaciones de estado administrativo que afectan las decisiones de resolución de los plugins. La intención de este archivo es permitir decisiones administrativas humanas explícitas para anular temporalmente los estados que afectan la toma de decisiones de los plugins en cuestiones de conmutación por error y/o distribución geográfica. Un archivo inexistente se trata igual que un archivo vacío. El archivo se monitorea en tiempo de ejecución en busca de cambios, y cualquier estado anulado encontrado se aplica rápidamente. Se espera que el archivo persista a través de reinicios y reinicios del demonio para preservar la intención del administrador a través de estos

eventos.

Se asume una comprensión básica de cómo funcionan tanto los plugins de monitoreo como los de resolución en gdnsd (vea gdnsd.config(5)). Este archivo se analiza como una estructura de datos hash vscf (nuevamente, vea gdnsd.config(5) para detalles más profundos de ese formato). Las claves son los nombres de recursos monitoreados o virtuales, y los valores son valores de estado forzados (opcionalmente con valores TTL monitoreados también). Las claves también pueden ser comodines usando la sintaxis de glob de shell que afectan a múltiples

recursos.

Para recursos monitoreados normales, la forma típica de una clave sería "THING/service_type", donde "THING" es la dirección monitoreada o el valor CNAME y "service_type" es el service_type configurado para monitorear esa dirección o valor CNAME por uno o más plugins de resolución. La parte del valor toma la forma de "STATE[/TTL]", donde "STATE" es "UP" o "DOWN" y la parte TTL es una anulación opcional del TTL

monitoreado.

El orden de las líneas en el archivo es importante; se procesan y aplican en orden de manera que las líneas posteriores pueden anular las acciones de las líneas anteriores. Esto es especialmente útil para hacer excepciones a coincidencias de

glob.

Ejemplo

: 
//lib/gdnsd/admin_state:
    2001:db8::2:123/my_http_check => DOWN # bajar un res+stype específico
    foo.example.com./extmon_ping => UP # subir un res+stype específico
    192.0.2.1/* => DOWN # bajar todos los service_types para esta dirección
    */xmpp => UP/30 # subir todos los recursos monitoreados por xmpp con TTL 30 ...
    192.0.2.2/xmpp => DOWN # ... excepto
este

Algunos plugins de resolución también pueden registrar recursos virtuales (que no son monitoreados por ningún "service_type") únicamente con el propósito de la anulación administrativa de la toma de decisiones. Actualmente los plugins geoip y metafo hacen esto para sus "datacenters", y las claves que crean toman la forma de "plugin_name/resname/dcname" para forzar el estado de un centro de datos a nivel de recurso específico. El plugin geoip también soporta claves de la forma "plugin_name/mapname/dcname" para forzar el estado de un centro de datos a nivel de mapa específico. Estas forzaciones anulan el estado agregado que se pasa hacia arriba a geoip/metafo desde los plugins por centro de datos (por ejemplo, multifo o weighted monitoreando varias direcciones en un centro de datos), y en el caso de geoip, el estado forzado más específico por recurso anulará cualquier estado forzado por

mapa.

Ejemplo

: 
//lib/gdnsd/admin_state:
    geoip/map3/dc-us => DOWN # bajar dc-us en el mapa geoip map3
    */dc-jp => DOWN # bajar todos los centros de datos llamados dc-jp para geoip y metafo
    metafo/res_www/dc-jp => UP # excepción a lo
anterior

Todas las claves monitoreadas y virtuales disponibles que pueden ser igualadas en este archivo, así como sus estados monitoreados y/o forzados actuales, son visibles en la salida de "gdnsdctl state

s" en for
mato JSON.

Cuando se inicia mediante "start", el manejo de "SIGHUP" se deja en los valores predeterminados, lo que normalmente resultará en una terminación no limpia del proceso al ser

principal.

SALIDA

Un estado de salida de cero indica éxito, cualquier otro indica

fallo.

Para "daemonize", el estado de salida del proceso inicial en primer plano indicará si el demonio en segundo plano se lanzó

exitosamente.

Para "start", el proceso inicial en primer plano es el demonio, y el estado de salida reflejará apropiadamente la señal de terminación incluso en un ca

so de apagado limpio, o será cero si se apagó li
