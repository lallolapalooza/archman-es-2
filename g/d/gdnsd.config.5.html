tcp_timeo
ut
Entero en segundos, predeterminado 37, mínimo 5, máximo 1800.

Esto determina el tiempo de espera por inactividad del lado del cliente para las conexiones TCP, que es enviado por el servidor a los clientes aplicables que soportan mecanismos de señalización como RFC 7828 EDNS TCP Keepalive o RFC 8490 DNS Stateful Operations

(DSO).

Existe un tiempo de espera correspondiente del lado del servidor que determina cuándo gdnsd abandonará a un cliente que considera delincuente (uno que mantiene una conexión abierta demasiado tiempo sin respetar ningún tiempo de espera por inactividad del lado del cliente señalado). El tiempo de espera del lado del servidor es el doble del tiempo de espera del cliente (lo que equivale a un predeterminado de 74, mínimo 10, máximo

3600).

Ten en cuenta que en el caso común/típico de clientes y conexiones bien portados, en un servidor Linux (donde usamos TCP_DEFER_ACCEPT) o un servidor BSD que soporte los filtros de aceptación "dnsready" o "dataready", cuando llega una nueva conexión recibimos inmediatamente la primera solicitud y devolvemos la respuesta sin ninguna oportunidad para retrasos que cuenten como tiempo de inactividad, sin volver a entrar en el bucle de eventos general donde se procesa el tiempo de inactividad o donde podrían llegar otras nuevas

conexiones.

La inactividad de un cliente solo se restablece después de que complete cada transacción completa (nos envía una solicitud completa, y nuestra respuesta completa llega al menos al búfer de escritura local). La incapacidad de escribir inmediatamente una respuesta completa en los búferes TCP locales del servidor (generalmente porque el cliente tiene una ventana de recepción demasiado pequeña y/o no está haciendo ACK a varias respuestas anteriores) causa la terminación inmediata de la conexión. Las conexiones de clientes bien portados que no se atascan a mitad de una transacción solo se convierten en conexiones inactivas (sujetas a terminación por inactividad) durante los períodos de inactividad entre transacciones después de su primera transacción, y para los clientes no tan bien portados, el temporizador de inactividad ayuda a controlar el impacto de patrones similares a ataques de lectura/escritura

lentos.

El servidor enviará información de edns TCP keepalive a los clientes con todas las respuestas donde sea legal (la solicitud usó EDNS sobre TCP, y DSO aún no se ha establecido). El valor de tiempo de espera se enviará con el valor fijo que está configurado aquí hasta que el servidor comience a apagarse, momento en el cual se envía el valor cero en tales respuestas en un intento de que los clientes cierren

limpiamente.

Los clientes que establezcan DSO a través del Keepalive TLV recibirán el mismo tiempo de espera del lado del cliente enviado a ellos como el tiempo de espera de inactividad de DSO, con el intervalo de KeepAlive de DSO establecido en Infinite (esto significa que no pedimos al cliente que envíe nunca pings de keepalive artificiales, y nuestro tiempo de espera del lado del cliente se aplica al intervalo entre las transacciones de solicitudes DNS reales en la sesión). Los clientes DSO también recibirán información mejor y más oportuna cuando el servidor se esté apagando o siendo reemplazado (podemos enviar mensajes unidireccionales DSO inmediatos hacia ellos pidiéndoles que cierren su sesión de forma

elegante)

Booleano, predeterminado false. Esta opción TCP solo se soporta dentro de las opciones por dirección de una dirección de escucha específica en la forma hash de la opción "listen", no como una opción

PELIGRO - Exponer el socket de control a través de TCP es peligroso. El código del servidor del socket de control no está diseñado para ser robusto contra tráfico de ataque arbitrario, y no tiene ninguna autenticación ni cifrado. Entero, por defecto 2, mínimo 1, máximo 1024. Cuando los archivos de zona estándar RFC1035 se (re)cargan, hasta este número de hilos efímeros se generarán en paralelo para ayudar a cargarlos y analizarlos más rápido.

La forma en que se divide el trabajo entre los hilos es relativamente ingenua: a medida que se escanea el directorio de zonas en el sistema de archivos en busca de nombres de archivo de zona, los nombres se dividen uniformemente en N listas de trabajo separadas (una por hilo), y luego se generan todos los hilos y trabajan en sus propias listas fijas en paralelo, con el empalme final de los datos de zona en el árbol raíz ocurriendo serialmente en el hilo principal de zonas a medida que cada hilo de trabajo termina. En el caso de que el recuento total de archivos de zona sea menor que el número de hilos configurado, los hilos excedentes no se

generan.

Esta estrategia simple tiende a funcionar bien para grandes cantidades de archivos de zona donde los costos de análisis por archivo de zona son aproximadamente uniformes, pero en los casos en que una minoría de archivos de zona tardan mucho más en analizarse que otros, no siempre dará como resultado un resultado muy "justo" (algunos hilos pueden ejecutarse mucho más tiempo que

otros).

Tenga en cuenta que en general, mejorar el rendimiento de E/S de la lectura d

Booleano, por defecto falso. En la transmisión, los registros "TXT" se codifican como fragmentos discretos de hasta 255 caracteres por fragmento. Las RFC relevantes declaran que múltiples fragmentos deben ser tratados por los clientes como si estuvieran concatenados. Es decir, no debería hacer ninguna diferencia para un cliente si los datos "TXT" se envían como dos fragmentos de 16 bytes o un fragmento de 32 bytes.

Ordinariamente, puede especificar fragmento(s) de un registro "TXT" en los archivos de zona de gdnsd como una cadena de cualquier tamaño hasta la longitud legal (en la práctica, justo por debajo de 16K), y gdnsd dividirá automáticamente los datos en fragmentos de 255 bytes para la transmisión sobre el protocolo DNS correctamente. Si elige dividir manualmente su registro TXT en múltiples cadenas en el archivo de zona, gdnsd también respeta estos límites e intentará fusionarlos en fragmentos más grandes cuando sea

posible.

Si establece esta opción en verdadero, el comportamiento de división automática está deshabilitado, y cualquier cadena de caracteres única especificada en un archivo de zona como parte de un registro "TXT" que sea mayor de 255

bytes se considerará
un error de sintaxis.

RFC 7873 (edns-client-subnet) en realidad lo recomienda para al menos respuestas diferenciadas por subred, porque de lo contrario es ambiguo a cuál de los múltiples registros de la sección de respuestas se aplica el alcance de la subred, y las cachés inevitablemente tienen que adoptar un punto de vista pesimista y fragmentar las entradas de la caché por subred sin sentido. También se adhiere al principio general de respuestas mínimas que seguimos en otros lugares (las cachés pueden tener el destino almacenado en caché de todos modos), y ayuda a minimizar los tamaños de respuesta (reduce la reflexión, y es especialmente útil para DNSSEC en el

futuro).

Además, si este fuera el comportamiento fijo del servidor, en lugar de configurable, simplificaría significativamente el código y haría las búsquedas más eficientes (estas mejoras no se obtienen con la versión opcional experimental)

RFC 2308 también aborda este tema, y el resumen allí es que los recursivos pueden distinguir nuestras respuestas incompletas de las respuestas negativas reales de "No Data" sobre el siguiente nombre en la cadena por el hecho de que no emitimos un registro SOA en la sección de

autoridad.

SERVICE_TYPE

S

service_types se usa en conjunto con ciertos plugins de gdnsd. Si no está usando uno de estos plugins, puede ignorar esta sección de forma segura y omitirla de su

configuración.

El hash service_types contiene definiciones genéricas de cómo monitorear un tipo de servicio dado, independientemente de cualquier dirección o nombre de host específico para ese

servicio.

Hay dos service_types triviales definidos internamente como los nombres "up" y "down", que no realizan monitoreo real y simplemente establecen el estado monitoreado permanentemente en "UP" o "DOWN". "up" es el service_type predeterminado cuando no se especifica ningún

service_type.

Dentro de la definición de un service_type hay varios parámetros genéricos relacionados con el tiempo y el anti-flap, así como parámetros específicos del plugin que varían según el

plugin.

Un tipo de servicio, sin embargo, no especifica un nombre o dirección para una instancia específica de un servicio. Esos ocurrirían por dirección en la configuración de un plugin de resolución más abajo en la sección "plugins", y la configuración del plugin haría referencia a un tipo de servicio nombrado para usar al monitorear dicha

dirección.

Un servicio monitoreado a través de estos mecanismos siempre está en el estado "UP" o "DOWN" en tiempo de ejecución desde una perspectiva de monitoreo. El estado "UP" se mantiene frente a fallos intermitentes o aislados hasta que se superan los umbrales anti-flap y el estado pasa a "DOWN"

.

Cualquier servicio monitoreado para plugins también tiene su estado reportado junto con el informe de estadísticas estándar de gdnsd, servido por el servidor HTTP integrado (el puerto predeterminado es 3506)

.

SINTAXIS DE BAJO

NIVEL

En el nivel más bajo, la sintaxis de los archivos de configuración de gdnsd se asemeja aproximadamente a una estructura de datos Perl anónima (usando sintaxis de referencia). Hay tres tipos de datos básicos para los valores: hashes ordenados (arreglos asociativos que mapean claves a valores), arreglos ordenados de valores y cadenas simples. Los hashes y arreglos se pueden anidar a una profundidad arbitraria. En general, el espacio en blanco es opcional. Los comentarios de una sola línea tanto en estilo de shell ("#") como de archivo de zona DNS (";") están permitidos. Se extienden hasta el final de la línea actual y son considerados como espacio en blanco por el

analizador.

Un hash está rodeado por llaves ("{" y "}"). Las claves se separan de sus valores por "=>" o "=" (a tu discreción estilística). Las claves del hash siguen las mismas reglas que los valores de cadena simples. Los valores del hash pueden ser cadenas simples, arreglos o hashes. Los pares clave/valor pueden tener opcionalmente una coma final para mayor claridad estilística y

separación.

Un arreglo está rodeado por corchetes ("[" y "]"). Los valores pueden ser cadenas simples, arreglos o hashes. Los valores pueden tener opcionalmente una coma final para

estilo.

Las cadenas (y por lo tanto las claves) se pueden escribir tanto en forma cotada como no cotada. En la forma cotada, la cadena está rodeada por comillas dobles ("""), y puede contener cualquier valor de byte literal (incluso binario/utf-8, o NUL) excepto """ o "\". Esos dos caracteres deben escaparse con "\", es decir "\"" y "\\"

.

En la forma no cotada, no hay comillas circundantes, y el conjunto permitido de caracteres sin escapar está más restringido. Los siguientes no están permitidos: "][}{;#,"=\" (es decir, corchetes, llaves, punto y coma, almohadillas, comas, comillas dobles, signos de igual y barras invertidas). Adicionalmente, el primer carácter no puede ser un "$" (signo de dólar)

.

Ambas formas usan las mismas reglas de escape, que son las mismas reglas de escape estándar de RFC usadas en los archivos de zona. Los escapes siempre comienzan con "\". "\" seguido de cualquier byte único que no sea un dígito (0 - 9) se interpreta como ese byte. "\" seguido de exactamente 3 dígitos interpreta esos dígitos como el valor entero decimal sin signo del byte deseado (el valor de 3 dígitos no puede exceder 255

).

analizado:

"white space"

NAME

gdnsd.config - gdnsd configuration file syntax

SYNOPSIS

gdnsd configuration files are written in a syntax similar to Perl's Data::Dumper, or Python dictionaries. They consist of key/value pairs, which may be nested.

# A simple configuration file
options = {
    listen = [ 192.0.2.1, 192.0.2.2 ]
}
zones = {
    example.com = {
        type = master
        file = "zones/example.com.zone"
    }
    test.net = {
        type = slave
        master = 192.0.2.1
        key = "somekeyid"
    }
}

DESCRIPTION

Configuration data is loaded from the directory specified by the -C command line option (defaulting to /etc/gdnsd/). The main configuration file is gdnsd.conf.

The configuration file syntax is a superset of JSON, and is very similar to Perl's Data::Dumper output, or Python dictionaries. It can be thought of as nested hashes and arrays.

Keys are typically simple identifiers (like options, zones, listen, etc.). They may be quoted using double quotes, and may contain almost any character. If a key contains spaces, punctuation, or other special characters, it must be quoted.

Values can be one of the following:

A scalar value
A string, integer, or boolean. These are generally unquoted, unless they contain spaces or special characters, or could be misinterpreted as other syntax elements. See "LOW-LEVEL SYNTAX" below.
An array
A list of values, enclosed in square brackets []. Elements are separated by commas.
A hash
A set of key/value pairs, enclosed in curly braces {}. Keys and values are separated by equals signs (=), or fat arrows (=>). Pairs are separated by commas.

Commentary is supported using C-style block comments (/* ... */) and C++-style line comments (// ...).

OPTIONS HASH

The top-level configuration file must contain exactly one hash, which is typically named options. The contents of this hash control the behaviour of the gdnsd daemon itself.

SERVICE_TYPES

The configuration file may also contain definitions of service types. These are hashes at the top level, keyed by the name of the service type (e.g. zones, access_list, acl, etc.).

PLUGINS

The configuration file may also contain definitions of plugins. These are hashes at the top level, keyed by the name of the plugin (e.g. geoip, extmon, etc.).

LOW-LEVEL SYNTAX

The syntax described above is the high-level syntax used in gdnsd configuration files. Beneath this, there is a lower-level syntax which is primarily used internally, or when generating configuration data programmatically. This low-level syntax is described here for completeness.

The low-level syntax accepts a stream of tokens, which can be structured as follows:

scalar
A sequence of characters, possibly including numbers, letters, and symbols. May be quoted with double quotes ("), in which case all characters are permitted. Unquoted scalars are terminated by whitespace, or by any character which has special meaning in the grammar (e.g. =, ,, {, }, [, ], $, and whitespace).
array
A sequence of scalars or nested arrays, enclosed in square brackets []. Elements may be separated by commas, but the commas are optional. e.g.: [ foo bar baz ] is equivalent to [ foo, bar, baz ].
hash
A sequence of key/value pairs, enclosed in curly braces {}. Keys and values are separated by either = or =>. Pairs are separated by commas, though the commas are optional. e.g.: { key1 value1 key2 => value2 } is equivalent to { key1 = value1, key2 => value2 }.

Within the high-level syntax, strings are delimited by double quotes ("), and may contain escape sequences like \n, \t, \\, and \".

The high-level syntax also allows the use of arrays where a single value is expected. For example, if a configuration value expects a single IP address, you could provide 192.0.2.1, or you could provide the array [ 192.0.2.1 ]. The parser will treat the array as if it contained only that single value.

This is only valid for the primary gdnsd configuration file, not for any includefiles (see below).

As a general rule, anywhere the higher-level syntax allows an array of values, you can substitute a single value. The code will treat it as if it were an array of length 1.

When we refer in other sections above to a value as being an "Integer" (or other specific scalar type), we're referring to constraints on the content of the character string value. All scalar values are character strings. "Boolean" values are characters strings which have the value "true" or "false", in any mix of upper or lower case.

The following 3 example configuration files are identical in their parsed meanings, and should clarify anything miscommunicated above:

Example 1 (simple and clean):

options = {
  listen = [ 192.0.2.1, 192.0.2.2 ],
}

Example 2 (fat arrows, no commas, some arbitrary quoting):

"options" => {
  listen => [ 192.0.2.1 192.0.2.2 ]
}

Example 3 (compressed and ugly):

options={listen=[192.0.2.1 192.0.2.2]}

INCLUDING OTHER FILES

vscf now has a mechanism for config includefiles. The syntax is

$include{dir/file} # single file must exist
$include{dir/*}   # not ok if no matching files
$include{dir}     # ok if no files in dir

where the path can use the same kinds of escaping and/or double-quoting as normal scalar string data. Whitespace between the path and the surrounding brackets is optional. Whitespace between $include and the following "{" is not allowed. If the path is relative (does not begin with /), it is interpreted as relative to the directory containing the parent file. Includes can nest other includes to arbitrary depth.

The path is normally treated as a glob, allowing the inclusion of multiple files. When used as a glob, there must be at least one match - it will be an error if there are no matching files. However, if "path" is not a glob and names an existing directory explicitly, it will be treated like it was a glob of all files within that directory by appending "/*", and it will not be an error if there are no files within that directory (no matches for the glob).

Keep in mind that at the top level of any given vscf file (even include files), the file must syntactically be either an implicit hash or an explicit, square-bracket-bounded, array.

The include statement can be used in two distinct contexts within the syntax structure of a config file:

Value Context
The include statement can replace any whole value (that is, the right hand side of a hash map entry or a member of an array) with its own contents, which are either a hash or an array. Note that there is no mechanism for flattening an include-file's array into the parent array (the whole included array would be a single array item within the parent array). Also, including multiple files in a single statement (directory name or glob pattern) are not allowed in value context. Examples: 
main config:
  options => { listen => $include{foo} }
foo:
  [ 127.0.0.1, 127.0.0.2 ]
main config:
  plugins => $include{ "bar" }
bar:
  geoip => { ... }
  extmon => { ... }
Hash-Merge Context
The include statement can also appear in a hash where a key would normally be expected. In this case, the included file must be in hash (rather than array) form at the top level, and its contents are merged into the parent hash. The merge is shallow, and conflicting keys are not allowed. Example: 
main config:
  options => { ... },
  plugins => {
      extmon => { ... },
      $include{geoip.cfg},
      $include{plugins.d},
  }
geoip.cfg:
  geoip => { ... }
plugins.d/foo:
  weighted => { ... }
  simplefo => { ... }
plugins.d/bar:
  metafo => { ... }
