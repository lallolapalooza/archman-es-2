NOMBRE

gdnsd-plugin-simplefo - plugin de gdnsd para conmutación por error simple de dirección primaria->secundaria

SINOPSIS

Fragmento de configuración de ejemplo de gdnsd que utiliza este plugin:

plugins => {
  simplefo => {
    service_types => [ www ],
    pubwww => {
      primary => 192.0.2.1
      secondary => 192.0.2.100
    }
    www6 => {
      primary => 2001:DB8::1
      secondary => 2001:DB8::100
    }
    mixed => {
      service_types => [ www, xmpp ]
      addrs_v4 => {
        primary => 192.0.2.1
        secondary => 192.0.2.100
      }
      addrs_v6 => {
        service_types => up
        primary => 2001:DB8::1
        secondary => 2001:DB8::100
      }
    }
  }
}

Registros de recursos (RR) de archivo de zona de ejemplo:

www 180 DYNA simplefo!pubwww
www6 180 DYNA simplefo!www6
mix 180 DYNA simplefo!mixed

DESCRIPCIÓN

gdnsd-plugin-simplefo está diseñado para realizar una conmutación por error simple activo/pasivo entre una dirección primaria y una secundaria. El estado de las direcciones se comprueba con la monitorización estándar de "service_types" de gdnsd. Si necesita más que una lista simple de conmutación por error de dos direcciones, el plugin "metafo" es más apropiado.

CONFIGURACIÓN DEL PLUGIN DE NIVEL SUPERIOR

En el nivel superior de la sección de configuración del plugin, se admite el parámetro especial "service_types". Estos establecen los "service_types" predeterminados por recurso para todos los recursos. El valor predeterminado "service_types" es "[ up ]", que simplemente los establece todos en "UP" estáticamente.

El resto de las entradas de hash en el nivel superior son los nombres de los recursos que usted define. Cada recurso recibe su propia sección de configuración de hash para contener información de direcciones específica del recurso.

CONFIGURACIÓN DEL RECURSO

Dentro de un recurso, "service_types" se admite nuevamente, para establecer el tipo(s) de servicio monitorizado(s) para este recurso específico.

Si se define "addrs_v4", debe ser un hash que contenga dos claves: "primary" y "secondary", cada una de las cuales tiene un valor de dirección de cadena IPv4.

De manera similar, si se define "addrs_v6", debe ser un hash que contenga dos claves: "primary" y "secondary", cada una de las cuales tiene un valor de dirección de cadena IPv6.

Si no se define ninguna de estas dos subsecciones, debe definir un solo par de direcciones "primary" y "secondary" para todo el recurso. Estas pueden ser de cualquier familia de direcciones, siempre que ambas sean de la misma familia.

Cuando se utilizan "addrs_v4" y/o "addrs_v6", "service_types" también se puede anular dentro de cada uno, para un comportamiento diferente por familia de direcciones (por ejemplo, forzar que un protocolo esté siempre activo/inactivo).

MECÁNICA OPERACIONAL

Para cada familia de direcciones para la que haya proporcionado datos, se aplica la siguiente lógica de forma independiente:

  • Primero, se obtiene el peor estado monitorizado de todas las comprobaciones de "service_types" para la dirección primaria. Si este estado es "UP", se utiliza la dirección primaria.
  • Si la dirección primaria estaba "DOWN", se comprueba la dirección secundaria: Si la secundaria está "UP", se utilizará. Si la secundaria también está "DOWN", entonces se utilizará la primaria.
  • En cualquier caso que no sea que la primaria esté exactamente "UP", el TTL de la respuesta RR-set del archivo de zona se reducirá a la mitad para ambas familias de direcciones.

Si tanto "primary" como "secondary" estaban "DOWN" para **cualquiera** de las familias de direcciones, este plugin señalará un fallo total del recurso a cualquier módulo upstream (geoip o metafo). La reducción del TTL solo ocurre una vez para todos los RR de dirección, incluso si ambas familias tenían una primaria no "UP".
