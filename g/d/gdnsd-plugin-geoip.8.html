NOMBRE

gdnsd-plugin-geoip - meta-plugin de gdnsd para GSLB + failover a través de las bases de datos GeoIP2 de MaxMind

SINOPSIS

Archivo de configuración mínimo de gdnsd que utiliza este plugin:

plugins => { geoip => {
  maps => {
    my_prod_map => {
      geoip2_db => GeoIP2-City.mmdb,
      datacenters => [dc-03, dc-02, dc-01, dc-fail],
      map => {
          EU => {
              DE => [dc-03, dc-01, dc-fail],
              CH => [dc-01, dc-03, dc-fail]
          },
          NA => { MX => [dc-02, dc-fail] }
      }
    },
    my_auto_map => {
      geoip2_db => GeoIP2-Country.mmdb,
      datacenters => [dc1, dc2],
      auto_dc_coords => {
         dc1 => [ 38.9, -77 ],
         dc2 => [ 50.1, 8.7 ],
      }
    }
  },
  resources => {
    prod_www => {
      map => my_prod_map
      service_types => up
      dcmap => {
        dc-01 => 192.0.2.1,
        dc-02 => { lb01 => 192.0.2.2, lb02 => 192.0.2.3 },
        dc-03 => [ 192.0.2.4, 192.0.2.5, 192.0.2.6 ],
        dc-fail => last.resort.cname.example.net.
      }
    }
    corp_www => {
      map => my_auto_map
      dcmap => {
        dc1 => 192.0.2.100,
        dc2 => 192.0.2.101
      }
    }
  }
}}

Registros de zona de ejemplo en la zona example.com:

www      600 DYNA geoip!prod_www
www-dc01 600 DYNA geoip!prod_www/dc-01
www.corp 600 DYNA geoip!corp_www

DESCRIPCIÓN

gdnsd-plugin-geoip utiliza las bases de datos binarias GeoIP2 de MaxMind para mapear resultados de direcciones y CNAME basados en la geografía y la disponibilidad del servicio monitoreado. Soporta completamente IPv6 y el estándar emergente edns-client-subnet. Si una solicitud contiene la opción edns-client-subnet con una máscara de red de origen mayor que cero, se utilizará la información de edns-client-subnet en lugar de la IP de origen de la solicitud (la IP de la caché que consulta).

Soporta las bases de datos en formato GeoIP2, que típicamente terminan en .mmdb. No soporta las bases de datos en formato GeoIP1 (que típicamente terminan en .dat).

También se puede utilizar sin ninguna base de datos GeoIP, en cuyo caso la única entrada de mapeo de red proviene de los datos de configuración "nets" o de un archivo externo "nets", que mapea explícitamente subredes a listas de centros de datos.

Este plugin puede operar en un modo automático basado en la distancia (utilizando la información de coordenadas de una base de datos de nivel de Ciudad). También puede operar sin coordenadas y depender del usuario para configurar un mapa jerárquico de mapeos en cascada predeterminados de ubicación de usuario a centro de datos, comenzando en el nivel de continente.

Los dos modos también se pueden mezclar de manera efectiva en los límites geográficos.

Para cada "map" que definas (que mapea códigos de ubicación geográfica a listas ordenadas de tus ubicaciones de centros de datos), este plugin fusiona todas las subredes GeoIP sin procesar en los supernets más grandes posibles que contienen respuestas idénticas en tu configuración. Estos, a su vez, se utilizan para establecer máscaras de alcance de edns-client-subnet más grandes de las que se obtendrían simplemente devolviendo resultados GeoIP sin procesar.

PLUGIN_METAFO

La documentación de gdnsd-plugin-metafo(8) es lectura obligatoria para entender la documentación del plugin geoip aquí. El plugin geoip es un superconjunto exacto del plugin metafo, y reutiliza casi todo el código fuente del plugin metafo. Metafo realiza failover a lo largo de una única lista global y ordenada de centros de datos. Lo que plugin_geoip añade sobre la funcionalidad de metafo es la capacidad de que el orden de la lista de failover de centros de datos se vuelva dinámico por solicitud, basándose en pistas geográficas derivadas de la dirección de red del cliente.

UBICACIONES DE ARCHIVOS

La configuración de este plugin puede hacer referencia a varios archivos de configuración y/o datos externos. Por defecto, todos los archivos referenciados en la configuración de este plugin se cargan desde el subdirectorio geoip del directorio de configuración del demonio (por defecto /etc/gdnsd). Puedes cargar desde otras ubicaciones especificando rutas de archivo absolutas.

CONFIGURACIÓN - NIVEL SUPERIOR

El nivel superior de la configuración del plugin geoip (es decir, "plugins => { geoip => { ... } }") soporta solo tres claves explícitas. Una es la opción opcional "undefined_datacenters_ok".

Las otras dos son obligatorias y se detallan en las siguientes dos secciones: "maps" y "resources". La sección "maps" define uno o más mapeos nombrados de información geográfica de las bases de datos binarias GeoIP a subconjuntos ordenados de nombres de centros de datos. La sección "resources" define uno o más recursos nombrados, cada uno de los cuales hace referencia a uno de los mapas nombrados y resuelve nombres de centros de datos a conjuntos específicos de direcciones o CNAMEs.

Cualquier otra clave presente en este nivel se heredará dentro de cada hash por recurso dentro de la estrofa "resources", actuando como valores predeterminados por recurso para cualquier cosa que no esté definida explícitamente allí.

"undefined_datacenters_ok = false"

Booleano, predeterminado: false. Si se establece en true, se permite que los recursos geoip dejen algunos de los centros de datos especificados en su "map" sin definir en su "dcmap" a nivel de recurso. Por ejemplo, un mapa M podría definir 3 centros de datos llamados A, B y C, pero un recurso que use el mapa M podría solo definir direcciones de resultado para los centros de datos B y C en su "dcmap". Esto de lo contrario sería un error de configuración grave.

!!! PELIGRO !!! - Establecer este valor en true es una buena forma de autolesionarse si no se tiene mucho cuidado con cómo se configuran los mapas y los recursos entre sí, especialmente en el "Modo Automático de Ciudad". Los mapas se calculan sin ningún conocimiento de los recursos que los utilizan. Si una red o ubicación específica se mapea a una lista de centros de datos que no contiene ninguno de los centros de datos definidos para un recurso dado, los resultados de las consultas en tiempo de ejecución para ese recurso desde esa ubicación o red serán el conjunto vacío (ningún registro de respuesta en absoluto). Esto es casi seguro que sucederá en el "Modo Automático de Ciudad" si el número de centros de datos no definidos en un recurso es mayor o igual que el "auto_dc_limit" del mapa.

CONFIGURACIÓN - MAPAS

Todas las claves de configuración a nivel de "maps" son los nombres de los mapas que elijas definir. Un mapa, conceptualmente, es un mapeo entre geografía y/o topología de red a subconjuntos de centros de datos ordenados variables. El valor de cada mapa nombrado debe ser un hash, y las siguientes claves de configuración se aplican dentro:

"geoip2_db = GeoIP2-City.mmdb"

Cadena, nombre de archivo, opcional. Este es el nombre de archivo de una base de datos en formato GeoIP2 de MaxMind. Debe contener el modelo de datos de Ciudad o País. Aquí no se hace distinción para la versión de IP, y es normal que estas bases de datos contengan datos de IPv4 e IPv6 juntos. Si falta uno u otro, los clientes que usan esa familia de direcciones obtendrán los valores predeterminados.

"datacenters = [ uno, dos, tres, ... ]"

Arreglo de cadenas, obligatorio. Este es el conjunto total de nombres de centros de datos utilizados por este mapa. Debes definir al menos un nombre de centro de datos (aunque 2 o más serían infinitamente más útiles). En este momento, hay un límite máximo de 254 nombres de centros de datos por mapa, aunque esto podría aumentarse si alguien lo requiere. El orden especificado aquí es el orden de resultado predeterminado de respaldo en varios casos predeterminados (por ejemplo, si no se proporciona ninguna lista predeterminada de mapas explícita de nivel superior).

"map = { ... }"

Hash, opcional. Este es el mapeo principal de la geografía a los centros de datos. Los pares clave-valor dentro de este hash son: el código geográfico (como clave) y una lista de nombres de centros de datos (como valor). La clave geográfica puede ser un código de continente (por ejemplo, EU, NA, AS, AF, OC, SA) o un código de país ISO 3166-1 alpha-2 (por ejemplo, US, DE, GB, JP). Los códigos de país tienen prioridad sobre los códigos de continente. Por ejemplo, si tienes una entrada para EU y otra para DE, la entrada para DE se aplicará a las solicitudes de Alemania, mientras que la entrada para EU se aplicará a solicitudes de Europa no cubiertas por una entrada de país más específica.

El valor asociado con cada clave geográfica debe ser una lista de nombres de centros de datos. Esta lista es la lista de preferencia de centros de datos a utilizar para solicitudes provenientes de la ubicación geográfica especificada. El orden es importante y debe ser un subconjunto de los nombres de centros de datos definidos en el nivel superior "datacenters" clave para este mapa.

El plugin cargará y mantendrá listas de subredes IP para las ubicaciones geográficas configuradas que coincidan con la información de la base de datos GeoIP2. Los resultados se fusionarán en el supernet más grande posible que contenga todas las subredes que se mapean a la misma lista de centros de datos. Por ejemplo, si la base de datos GeoIP2 dice que 1.2.3.0/24 y 1.2.3.128/25 pertenecen a la misma lista de centros de datos, estas se fusionarán en 1.2.3.0/24. La máscara de subred de cliente (CSM) utilizada en las respuestas edns-client-subnet se basará en el tamaño del supernet más grande resultante.

Tenga en cuenta que el plugin GeoIP2 no sabe de antemano qué Centros de Datos estarán definidos en la sección de Recursos. Por lo tanto, la lista de centros de datos proporcionada aquí solo se utiliza para determinar la subred IP de la que el plugin GeoIP construirá su respuesta. La validación de si los centros de datos resultantes son válidos para un recurso dado solo ocurre en tiempo de ejecución.

"auto_dc_coords = { ... }"

Hash, opcional. Si se proporciona, esto habilita el modo "City Auto Mode". La clave debe ser el nombre de un centro de datos de la lista "datacenters", y el valor debe ser un arreglo de punto flotante de dos elementos que representan la latitud y longitud de ese centro de datos. El plugin utiliza la base de datos GeoIP2-City.mmdb para obtener las coordenadas de la ubicación solicitante y luego calcula la distancia a cada uno de los centros de datos definidos en "auto_dc_coords". La lista de centros de datos resultante es simplemente una lista de sus centros de datos, ordenada de más cercano a más lejano. Se pueden mezclar bases de datos de Ciudad y País; en este caso, el plugin intentará utilizar los datos de Ciudad si están disponibles, y los datos de País en caso contrario.

Se espera que la base de datos GeoIP2_db esté configurada en este mapa. Si no es así, no se pueden determinar las coordenadas del cliente y este modo se degradará silenciosamente a un modo sin coordenadas, pero con una lista de centros de datos predeterminada basada en la lista global de centros de datos.

Esta característica puede ser muy útil para un GSLB de "último recurso". Por ejemplo, si la mayoría de tus usuarios están en América del Norte, pero solo tienes un centro de datos en Europa, y quieres que tus usuarios de América del Norte apunten allí, puedes hacerlo simplemente usando la lista ordenada de centros de datos global predeterminada del mapa. Si tienes un centro de datos de respaldo que está geográficamente muy lejos de todos los demás, puedes añadirlo al final de la lista.

El plugin GeoIP2 también puede devolver rangos de coordenadas para la ubicación de la solicitud. Si es así, el plugin es lo suficientemente inteligente como para utilizar el centro de datos que esté más cerca del centro de ese rango.

En el modo automático, un parámetro opcional auto_dc_limit puede ser proporcionado. Si se proporciona, limitará el número de centros de datos para ser devueltos.

"nets = { ... }"

Hash, opcional. Permite configurar el mapeo de subredes IP a centros de datos sin usar una base de datos GeoIP2. Las claves son las definiciones de subredes IP (por ejemplo, 192.0.2.0/24), y los valores son listas de nombres de centros de datos, como se describe para la clave "map". Esto puede ser útil para mapear rangos de direcciones IP privadas (RFC1918) o para complementar la información de GeoIP2 con sus propios datos personalizados.

CONFIGURACIÓN - RECURSOS

La sección "resources" define los servicios individuales que se expondrán a través de este plugin. Cada clave en esta sección es el nombre de un recurso (que se utiliza en los registros de zona), y el valor es un hash que describe el recurso.

"map = map_name"

Cadena, requerida. El nombre del mapa definido en la sección "maps" que se utilizará para este recurso.

"service_types = list_of_types"

Arreglo de cadenas, opcional. Utilizado principalmente para definir qué tipos de servicio (por ejemplo, up, http_200, tcp_connect) se utilizarán para determinar la disponibilidad de los centros de datos. Si no se proporciona, se utiliza el valor predeterminado up.

"dcmap = { ... }"

Hash, requerida. Este es el mapeo real de los nombres de los centros de datos a las direcciones IP o CNAMEs. Las claves son los nombres de los centros de datos (que deben ser un subconjunto de los nombres definidos en la sección "datacenters" del mapa referenciado), y los valores son las direcciones IP, CNAMEs o hashes de balanceadores de carga.

El plugin geoip soporta la definición de resultados para el centro de datos last_resort. Si una solicitud de un cliente no coincide con ninguna de las subredes definidas en el mapa, o si la ubicación de la solicitud no se encuentra en la base de datos GeoIP2, se utilizarán los resultados definidos para last_resort si existen. Si no existen, y la opción undefined_datacenters_ok no está habilitada, la solicitud se responderá con un error SERVFAIL.

EJEMPLOS DE ENTRADAS DE ARCHIVO DE ZONA

Para el archivo de configuración de ejemplo anterior:

www      600 DYNA geoip!prod_www
www-dc01 600 DYNA geoip!prod_www/dc-01
www.corp 600 DYNA geoip!corp_www

La primera entrada, www, generará respuestas basadas en la ubicación del cliente, utilizando el mapa my_prod_map. Si el cliente está en Europa (DE o CH) o Norteamérica (MX), se devolverán las direcciones IP/CNAMEs correspondientes de la sección dcmap de prod_www, en el orden especificado por el mapa.

La segunda entrada, www-dc01, es un ejemplo de cómo podrías forzar a un cliente a ir a un centro de datos específico, independientemente de su ubicación geográfica. En este caso, se devolverán directamente los resultados para dc-01.

La tercera entrada, www.corp, utiliza el mapa my_auto_map. En este caso, los centros de datos se ordenarán por distancia calculada desde la ubicación del cliente hasta los centros de datos dc1 y dc2.

"nets = { ... }

Hash clave-valor, opcional (vea más abajo para la forma alternativa). Si se especifica, el contenido debe ser pares clave-valor de "network/netmask" mapeado a un nombre de centro de datos (o a un arreglo de nombres de centros de datos). Cualquier mapeo de red a centro de datos especificado aquí anulará los mapeos determinados vía GeoIP. Tenga en cuenta que es ilegal especificar redes en los subespacios similares a IPv4 de IPv6 distintos de v4compat, pero es legal especificar redes IPv4 reales (que se tratan de manera idéntica a v4compat). Vea la sección sobre Direcciones Compatibles con IPv4 más adelante en este documento para más detalles. El orden de las redes no es importante; siempre se ordenarán e insertarán de manera que una entrada que sea una subred de otra entrada no sea obliterada por la supernet

padre. 
nets => {
    10.0.0.0/8 => [ dc1, dc2 ],
    192.0.2.128/25 => dc3
    2001:DB8::/32 => [ dc4, dc5, dc6 ],
}

En el caso de que una entrada sea una subred de otra con una lista de centros de datos (dclist) diferente, las entradas se fusionan correctamente de modo que la supernet rodee a la subre

d. En el caso de una entrada duplicada exacta (o efectiva, después de fusionar subredes más pequeñas) con una dclist diferente, es arbitrario cuál "gana" y se emite una advertencia
sobre la condición. Si le preocupa este caso, debería sanitizar sus datos de nets de antemano con una herramienta externa y/o buscar el mensaje de advertencia en las salidas de registro.

"nets =

nets_file_name"

Ruta de archivo de cadena de texto, opcional. Una variante de lo anterior, pero el contenido del hash clave-valor se carga desde el archivo

externo con nombre. Esto facilita la vida a herramientas y scripts externos que generan grandes conjuntos de entradas de nets (p. ej., a partir d
e datos BGP). El archivo se monitoreará para detectar cambios y se recargará en tiempo de ejecución, muy similar a las bases de datos GeoIP.

"map = { ... }

"

Hash clave-valor, opcional. Este es el corazón de un mapa con nombre que usa GeoIP: el propio mapa, que mapea lugares a listas ordenadas de centros de datos. Requiere que "geoip2_db" también se especifique, y no tiene sentido sin

él.

Este es un hash clave-valor anidado. En cada nivel, las claves son códigos de ubicación (continente, país, región/subdivisión o información de ciudad, dependiendo de la profundidad), y los valores son o bien un arreglo ordenado de centros de datos (p. ej., "[" dc03, dc01, dc04 ]"), o un sub-hash que contiene un nivel más profundo de distinción. En cada capa, una clave especial llamada "default" está disponible, que establece el valor predeterminado para todo dentro del ámbito actual. El predeterminado de nivel superior mismo tiene como predeterminado la lista ordenada de "datacenters" en el caso normal. Si toda la estrofa "map" falta o está vacía, simplemente obtendrá el comportamiento predeterminado de "default". Un arreglo de centros de datos también puede estar vacío, lo que implica que esta ubicación está mapeada para no recibir datos de respuesta (el servidor aún responderá a la consulta,

y no emitirá un NXDOMAIN. Simplemente será una respuesta NODATA/NOERROR como la que obtendría si no
hubiera registros de este tipo, pero pudiera haber registros de otros tipos para el mismo nombre).

Jerarquía de Datos de Ubicación

GeoIP2

El nivel superior de la jerarquía del mapa está compuesto por los siete códigos de continente de MaxMind: "AF" para África, "AS" para Asia, "NA" para América del Norte, "SA" para América del Sur, "EU" para Europa, "OC" para Oceanía, y "AN" para la Antártida. El siguiente nivel es el código de país de 2 letras ISO

3166-1.

A partir de aquí hay una serie de niveles de Subdivisión, cuyo número varía para diferentes entradas de bases de datos de red. En EE. UU., por ejemplo, solo hay un nivel de datos de subdivisión para los estados de EE. UU. En la República Checa hay dos niveles de subdivisión: primero en 14 regiones, y luego en 91 distritos. Las subdivisiones se especifican todas utilizando directamente sus códigos ISO

3166-2.

Después de todos los niveles de subdivisión, el nivel final es el nivel de Ciudad. Los nombres de las ciudades están todos en el juego de caracteres UTF-8. Actualmente este complemento solo usa los nombres de ciudades en inglés de la base de datos, aunque otros idiomas pueden estar disponibles dependiendo de la base de

datos.

Como respuesta pragmática a los problemas que pueden surgir con múltiples capas de subdivisión, el mapa busca automáticamente más profundamente en los datos de la base de datos cuando no se encuentra una coincidencia en el mapa en un nivel dado de la jerarquía del mapa por debajo del nivel de País. Esto significa que puede omitir cualquier nivel de detalle de Subdivisión en su mapa que no le resulte

relevante.

Por ejemplo, esto apunta a la subdivisión de consejo regional de Nueva Zelanda de Otago sin especificar explícitamente la subdivisión circundante de la Isla

Sur: 
{ OC => { NZ => { OTA => [...] } }
}

Como otro ejemplo, esto funciona correctamente para apuntar a la ciudad de París sin importar qué capas de subdivisiones se encuentren entre ella y

FR: 
{ EU => { FR => { Paris => [...] }
}
}

CONFIGURACIÓN - MAPAS - MODO AUTOMÁTICO DE

CIUDAD

"City-auto-mode" es un modo especial de operación que mapea automáticamente el mundo a sus centros de datos basándose en cálculos de coordenadas, de modo que no tenga que construir manualmente un jerárquico complejo "map". Todavía se puede mezclar con "map" por supuesto, permitiéndole usar el modo automático solo para áreas geográficas seleccionadas si lo desea (o deshabilitarlo para áreas seleccionadas especificando listas manuales). El parámetro clave es "auto_dc_coords", que habilita el modo automático de ciudad. Esto requiere una base de datos GeoIP2 a nivel de Ciudad; las de País no contienen información de

coordenadas.
"auto_dc_coords = { ...
}"
Hash clave-valor, opcional. Si se especifica esta opción, el modo de operación básico de todo el mapa cambia a "city-auto-mode". El contenido del hash es una clave para cada centro de datos nombrado en "datacenters", con sus valores establecidos en un arreglo de "[lat, lon]" en unidades de grados decimales. Cuando el modo automático de ciudad se habilita con esto, ocurren los siguientes cambios de validación de configuración respecto al modo predeterminado de mapeo estático: las bases de datos GeoIP2 cargadas deben ser bases de datos a nivel de Ciudad, y la palabra clave especial "auto" se convierte en una "lista de centros de datos" legal en la estrofa "map".

Con el modo automático de ciudad habilitado, el "default" de nivel superior del mapa tiene como predeterminado "auto", pero puede ser anulado con una lista manual. Para cualquier ubicación que se mapee a "auto", las coordenadas especificadas aquí en "auto_dc_coords" se compararán con las coordenadas de la(s) base(s) de datos a nivel de Ciudad para determinar una lista de centros de datos ordenada por distancia

automáticamente.

Si omite uno o más centros de datos definidos de la lista de coordenadas en "auto_dc_coords", esos centros de datos no se usarán en los resultados automáticos, pero seguirán estando disponibles para uso manual a través de "map" y/o entradas d

e "n
ets".
"auto_dc_limit
= N"
Entero sin signo, opcional, por defecto 3. Cuando el modo automático de ciudad está en vigor, este es el límite superior de longitud para las listas generadas automáticamente. 3 es un valor predeterminado razonable incluso si tiene un conjunto considerablemente más largo de centros de datos, ya que esto proporc
iona uno principal así como dos de respaldo. Aumentar esto a un número grande en presencia de una lista larga de centros de datos hará que el conjunto de listas únicas de centros de datos de resultados aumente rápidamente, y así reducir la optimización de la base de datos de resultados final para fines de
edns-client-subnet. Realmente no vale la pena aumentar este valor en casi ningún caso, a menos que realmente necesite manejar más de 3 centros de datos aleatorios fuera de línea al mismo tiempo y aún hacer que los clientes fallen en otro lugar. El valor cero se trata como ilimitado (altamente no recomendado).

Bajo el modo automático de ciudad, cuando el predeterminado de nivel superior es (explícita o implícitamente) "auto", todavía existe un ordenamiento estático de respaldo que es toda la lista ordenada de "datacenters", que es el predeterminado estático normal "default" cuando no se está en el modo automático de ciudad. Este respaldo se usa cuando no hay información de ubicación disponible en absoluto (p. ej., cliente IPv6 vs base de datos GeoIP IPv4, Proxies Anónimos,

etc)
.

CONFIGURACIÓN - RECURSOS

La

configuración a nivel de recurso dentro de la sección "resources" es casi idéntica a la configuración de recursos del plugin metafo, con todos los mismos comportamientos básicos sobre la síntesis o la referencia directa de la configuración de otros plugins por centro de datos. Una

diferencia

es que el arreglo "datacenters" por recurso de metafo es reemplazado por "map => mapname", que referencia uno de los mapas definidos en la sección "maps", descrita en detalle anteriormente. El conjunto de centros de datos definidos en la sección "dcmap" debe coincidir con el conjunto total de centros de datos definidos por el mapa referenciado, a menos que "undefined_datacenters_ok" esté establecido en "true" (vea las

advertencias

y la documentación anteriores). El indicador "skip_first" también puede establecerse por recurso, y es mucho más útil con el plugin geoip que con el plugin metafo básico. Si se establece este indicador, el primer centro de datos en la lista de conmutación por error para una búsqueda determinada será omitido, lo que permite la definición de un recur

so de "segunda opción" usando la misma definición básica de mapa que la primera opción. En este caso, la primera opción original *nunca* es una respuesta posible, y el resto de l
a lógica (p. ej., omitir centros de datos marcados como caídos) procede normalmente con la lista restante. Si la entrada del mapa y/o la definición del recurso ya han reducido el

número efectivo de centros

de

datos a uno, el indicador notiene efecto. INTERACCIÓN CON EL META-PLUGIN Ambos meta-plugins ( "metafo" y "geoip") pueden referenciar sus propios recursos así como los del otro mediante una referencia directa dentro de un "dcmap", siempre que un recurso no se refiera directamente a sí mismo. Esto permite configuraciones de superposición de plugins como geoip -> metafo -> weighted, o

metafo

-> geoip -> multifo, o incluso metafo -> metafo -> simplefo, etc. Tenga en cuenta que una vez que comience a usar referencias entre meta-plugins, podría crear un bucle de referencias. gdnsd actualmente no detecta ni previene dichos bucles, y causarán un fallo total en tiempo de

ejecución

cuando se consulten, probablemente al agotar el espacio de pila durante la recursión. Adicionalmente, "geoip" puede sintetizar configuración para recursos de "metafo", pero lo contrario

no se c
umple;

"metafo" no puede

sintetizar

configuración para recursos de "geoip". Direcciones compatibles con IPv4 Este plugin conoce seis formas diferentes y relativamente triviales de mapear direcciones IPv4 dentro del espacio de direcciones IPv6. Se muestran a continuación con el

detalle 
     que importa para este plugin, con
    "NNNN:NNNN" en lugar de los bytes de la dirección IPv4
    copiados:
::0000:NNNN:NNNN/96   # RFC 4291 - v4compat (obsoleto)
     ::ffff:NNNN:NNNN/96   # RFC 4291 - v4mapped
::ffff:0000:NNNN:NNNN/96   # RFC 2765 - SIIT (obsoleto)
   64:ff9b::NNNN:NNNN/96   # RFC 6052 - Prefijo de conocimiento general
2001:0000:X:NNNN:NNNN/32   # RFC 4380 - Teredo (los bits IPv4 están invertidos)
       2002:NNNN:NNNN::/16 # RFC 3056 - 6to4
(en el caso de Teredo anterior,
"X"

representa algunos bytes variables distintos de cero que ocupan los 64 bits centrales de la dirección). Todas las bases de datos de búsqueda internas de este plugin son bases de datos IPv6, y cualquier información similar a IPv4 se almacena siempre en el espacio v4compat dentro de estas bases de datos. Al realizar búsquedas en tiempo de ejecución, todas las demás direcciones similares a v4 (direcciones IPv4 en bruto, v4mapped, SIIT, WKP, Teredo y 6to4) se convierten a la representación IPv6 v4compat canónica antes de consultar las bases de datos internas. Las otras representaciones (v4mapped, SIIT,

WKP,

Teredo, 6to4) son Undefined internamente, y nunca serán referenciadas en el momento de la búsqueda debido a la conversión v4compat mencionada anteriormente. La sección "nets" no permite especificar entradas en los cinco espacios IPv6 similares a v4 no definidos (los que no son v4compat). Especifique esas redes como redes IPv4 normales o redes v4compat en su lugar. Las entradas legítimas de "nets" de IPv6 que resulten ser una superneta de cualquier espacio similar a v4 *no* afectarán indebidamente a las

búsquedas

similares a v4. No hay diferencia funcional entre las formas v4compat y v4 nativas en "nets", p. ej. "192.0.2.0/24" y "::C000:0200

/120" son completamente idénticas. Las bases de datos GeoIP que son nativamente solo IPv4 cargan todos sus datos únicamente en el espacio v4com
pat. Para las bases de datos GeoIP IPv6 normales, por defecto cargamos directamente el espacio v4compat (donde MaxMind almacena los datos IPv4

en sus bases de datos IPv6)

,

pero ignoramos los espacios v4mapped/SIIT/Teredo/6to4 (algunos de los cuales están vacíos en las bases de datos

de 
MaxMind, y algunos de los cuales
    simplemente aliasan el espacio v4compat).
