NOMBRE

gdnsd-plugin-metafo - plugin de gdnsd para el meta-failover de direcciones

SINOPSIS

Ejemplo mínimo de archivo de configuración de gdnsd que utiliza este plugin:

plugins => {
  metafo => {
    resources => {
      prod_www => {
        datacenters => [ dc-01, dc-02, dc-03 ]
        dcmap => {
          dc-01 => 192.0.2.1
          dc-02 => { lb01 => 192.0.2.2, lb02 => 192.0.2.3 }
          dc-03 => [ 192.0.2.4, 192.0.2.5, 192.0.2.6 ]
        }
      },
      prod_foo => {
        datacenters => [ dc-01, dc-02, dc-bk ]
        dcmap => {
          dc-01 => { lb01 => 192.0.1.1, lb02 => 192.0.1.2 }
          dc-02 => [ 192.0.5.1, 192.0.5.2, 192.0.5.3 ]
          dc-bk => fallback.static.cname.example.org.
        }
      }
    }
  }
}

Ejemplo de RRs de archivo de zona en la zona example.com:

www      600 DYNA metafo!prod_www
www-dc01 600 DYNA metafo!prod_www/dc-01
foo      700 DYNC metafo!prod_foo

DESCRIPCIÓN

gdnsd-plugin-metafo es un meta-plugin. Realiza un failover de direcciones estático-ordenado entre múltiples "datacenters" (que pueden o no corresponder con centros de datos reales, es solo una etiqueta conveniente). Cada centro de datos se define en términos de otros plugins como "multifo", "weighted", etc, como se describe a continuación.

CONFIGURACIÓN - NIVEL SUPERIOR

El nivel superior de la configuración del plugin metafo (es decir, "plugins => { metafo => { ... } }") soporta solo una clave fija y requerida, "resources", cuyo valor debe ser un hash. El contenido de "resources" es una clave por recurso nombrado, con el valor definiendo ese recurso. Cualquier otra clave presente en el nivel superior se heredará hacia abajo dentro de cada hash por recurso dentro de la sección

"resources" , actuando como valores predeterminados por recurso para cualquier cosa no definida explícitamente allí, como se explica a continuación. CONFIGURACIÓN - RECURSOS

Todas las claves dentro de la sección de recursos representan recursos nombrados, que pueden ser referenciados por

RRs "DYNA" en archivos de zona (por ejemplo, "www DYNA metafo!resource_name"). El valor de cada recurso debe ser un hash clave-valor que configure el recurso en sí. Ejemplo estructural ligero:

plugins => {
  metafo => {
    resources => { resA => { ... }, resB => { ... } }
  }
}

Dentro de un recurso, solo hay tres claves específicamente significativas:

"datacenters = [ A, B, C, ... ]"
Array de nombres de centros de datos, requerido. Este es el conjunto de etiquetas de nombres de centros de datos utilizados para este recurso, en el orden en que serán comprobados para el failover.
"dcmap = { ... }"
Hash, requerido. El "dcmap" es un hash clave-valor donde las claves deben ser exactamente la lista de centros de datos definidos en la lista "datacenters" de este recurso, y los valores definen la configuración de dirección de cada centro de datos. Otro ejemplo estructural mínimo hasta este nivel: 
plugins => {
  metafo => {
    resources => {
      resA => {
        datacenters => [ dc01, dc02 ],
        dcmap => {
          dc01 => ???
          dc02 => ???
        }
      }
    }
  }
}

Hay varias formas que los valores por centro de datos ("???" arriba) pueden tomar, documentadas en la siguiente sección.

"skip_first = true"
Si esta bandera de configuración booleana está activada, el código del resolutor omitirá el primer centro de datos al resolver este recurso. Esto es principalmente útil en el contexto del plugin geoip, y se discute con más detalle allí.

Cualquier clave que no sea "datacenters" ni "dcmap" a nivel por recurso sirve como valores predeterminados heredados para cada configuración por centro de datos dentro de "dcmap".

RESOLUCIÓN POR CENTRO DE DATOS

El valor de los centros de datos dentro de la sección "dcmap" de un recurso puede tomar varias formas. Es importante entender que en su mayor parte, plugin_metafo no se ocupa de este nivel de resultados en sí mismo, sino que en su lugar delega el trabajo en este ámbito a otros plugins. Estos sub-plugins, a su vez, también notifican a metafo del fallo completo en su nivel, que es la información que metafo utiliza para saber que debe hacer failover al siguiente centro de datos en la lista.

La forma más directa y obvia de hacer esto es con una referencia directa de la forma "%plugin!resource", como se muestra aquí:

plugins => {
  metafo => {
    resources => {
      resA => {
        datacenters => [ dc1, dc2 ],
        dcmap => {
          dc1 => %multifo!res_mfo1
          dc2 => %multifo!res_mfo2
        }
      }
    }
  }
  multifo => {
    res_mfo1 => { lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
    res_mfo2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
  }
}

Sin embargo, para simplificar la vida en los casos simples, plugin_metafo puede sintetizar la configuración del plugin de nivel inferior a partir de un hash, así:

plugins => {
  metafo => {
    resources => {
      resA => {
        datacenters => [ dc1, dc2 ],
        dcmap => {
          dc1 => { plugin => multifo, lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
          dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
          # lo de arriba se trata efectivamente como:
          # dc1 => %multifo!metafo_resA_dc1
          # dc2 => %multifo!metafo_resA_dc2
        }
      }
    }
  }
  # lo de abajo no existe en su archivo de configuración, pero es lo que plugin_metafo
  #   sintetiza para soportar lo de arriba:
  #multifo => {
  #  metafo_resA_dc1 => { lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
  #  metafo_resA_dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
  #}
}

Dentro de un hash como el de arriba, la clave especial "plugin" será eliminada internamente y utilizada para nombrar el plugin para el que sintetizamos la configuración. "plugin" tiene como valor predeterminado "multifo" si no se especifica. Nótese que "plugin" también podría ser especificado a nivel de recurso (justo dentro de la sección "resA" ) para cambiar el valor predeterminado para todas las entradas "dcmap" en un recurso, y también podría ser especificado en el ámbito más externo (justo dentro de la sección "metafo" ) para cambiar el valor predeterminado para todos los recursos.

El "plugin" heredado hacia abajo también es el valor predeterminado para la forma de referencia directa "%plugin!resource" discutida anteriormente. Con el nombre de plugin predeterminado correcto, puede acortarse a simplemente "!resource".

El mismo esquema de herencia clave-valor (nivel superior -> nivel por recurso -> nivel por centro de datos) también puede ser utilizado para cualquier otro parámetro en configuraciones de recursos sintetizados específicas para el(los) plugin(s) por centro de datos que esté utilizando. Un ejemplo común sería el parámetro "service_types" que tienen la mayoría de los plugins que soportan resultados de direcciones monitorizadas. Nótese que estos otros valores (por ejemplo, service_types) solo se aplicarían a recursos sintetizados, no a referencias directas como "%multifo!foo", que deben ser configurados completamente por separado dentro de la configuración de ese plugin.

Hay otras tres posibles formas abreviadas para los centros de datos: una dirección directa única, un array de direcciones, o un nombre de host CNAME único. Si se especifica una dirección IP única o un array de direcciones IP, plugin_metafo sintetizará un hash a partir de ellas con el plugin forzado a "multifo" (ya que no puede conocer la sintaxis de los hashes para todos los demás plugins, que puede diferir), y les dará etiquetas de dirección 1, 2, etc.

Si el valor para un centro de datos es un nombre de host CNAME único, no se utiliza ningún sub-plugin, y ese resultado CNAME se devuelve directamente. Nótese gdnsd-plugin-metafo(8) — gdnsd 3.8.2

NAME

gdnsd-plugin-metafo - metadata-driven load balancer

SYNOPSIS

A plugin which implements a number of load-balancing algorithms, driven by a metadata configuration file.

DESCRIPTION

This plugin is intended to be used as a backend for gdnsd's name-server configuration, to provide load-balanced IP addresses.

Its configuration is a nested hash-table structure that can be built up from several sources. The plugin itself is named metafo, and it can be configured within the global plugins hash, or within the resources hash, or within a resource's per-datacenter configuration.

CONFIGURATION - TOP-LEVEL

The top-level configuration is a hash-table, in which the keys are the names of the resources that this plugin will manage. For each resource name, the value is another hash-table containing the configuration for that resource.

The configuration hash for a resource may contain the following keys:

plugin: The name of the plugin to use for this resource. This defaults to metafo. This is useful if you want to use other plugins (e.g. simplefo) to provide addresses for one of your metadata-driven resources.

service_types: A list of strings, specifying which service types this resource is for. The default value is ["up"]. See gdnsd.config(5) for more information on service types.

datacenters: A list of strings, specifying the names of the datacenters where this resource is deployed. These names are arbitrary, but are used to construct the per-datacenter resource names described below.

dcmap: A hash-table mapping datacenter names (which must be included in the datacenters list) to configurations for that datacenter. The configuration for a datacenter can be one of the following:

A hash-table mapping arbitrary keys (e.g. load balancer names) to IP addresses, load balancer names, or references to other resources.
A resource reference, e.g. %simplefo!foo.
A negated resource reference, e.g. !bar. This will cause the resource to be omitted from the output for this datacenter.
A list of IP addresses, load balancer names, or resource references.
A single IP address, load balancer name, or resource reference.

CONFIGURATION - RESOURCES

Within a datacenter's configuration hash, you may specify:

plugin: Override the plugin for this datacenter.
service_types: Override the service_types for this datacenter.
arbitrary keys:
These are mapped to values, which can be IP addresses, resource references, or other hash tables. This is useful for specifying named load balancers within a datacenter.

The example below shows a variety of configurations. Note that resources defined directly in the top-level plugins hash are typically configured with a default service_types of ["up"], whereas resources synthesized by other plugins (like metafo) inherit the service_types from the parent resource.

It is important to note that if any subplugin's configuration is capable of returning CNAME data, then the resource in question must be configured to use "DYNC" RRs, not "DYNA" RRs.

A much more complete example, showing off most of the features above:

plugins => {
  metafo => {
    plugin => multifo # change default for all resources
    service_types => [ bar ] # default service_types for synthesized below
    resources => {
      resA => {
        plugin => multifo # change default for this resource
        service_types => [foo, bar] # services types for synthesized below:
        datacenters => [ dc1, dc2, dc3, dc4, dc5, dc6, dc7, dc8 ],
        dcmap => {
          dc1 => { plugin => multifo, lb01 => 192.0.2.1, lb02 => 192.0.2.3 }
          dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113 }
          dc3 => %simplefo!foo
          dc4 => { plugin => simplefo, primary => 192.0.2.100, secondary => 192.0.2.101 }
          dc5 => !bar
          dc6 => 192.0.2.150
          dc7 => [ 192.0.2.180, 192.0.2.181 ]
          dc8 => last.resort.example.com.
        }
      }
    }
  }
  # below, commented-out sections show configuration synthesized
  #   by plugin_metafo, whereas the rest are direct-references that
  #   had to be manually specified here:
  multifo => {
    # metafo_resA_dc1 => { lb01 => 192.0.2.1, lb02 => 192.0.2.3, service_types => [foo, bar] }
    # metafo_resA_dc2 => { lb01 => 192.0.2.111, lb02 => 192.0.2.113, service_types => [foo, bar] }
    bar => { asd => 192.0.2.77, xyz => 192.0.2.88 }
    # metafo_resA_dc6 => { 1 => 192.0.2.150, service_types => [foo, bar] }
    # metafo_resA_dc7 => { 1 => 192.0.2.180, 2 => 192.0.2.181, service_types => [foo, bar] }
  }
  simplefo => {
    foo => { primary => 192.0.2.80, secondary => 192.0.2.81 }
    # metafo_resA_dc4 => { primary => 192.0.2.100, secondary => 192.0.2.101, service_types => [foo, bar] }
  }
}

Note in the example above that "%multifo!bar" and "%simplefo!foo" would have had their default "service_types = up" rather than the one specified at the metafo level, because they were not synthesized. It would be up to you to keep all of the service_types in sync when using direct references.

PER-DATACENTER RESOLUTION

Any resource with such an entry can only be used with "DYNC" RRs, and not "DYNA" RRs (as is the case if any subplugin's configuration is capable of returning CNAME data).

SYNTHETIC PER-DATACENTER RESOURCES

This plugin will synthesize additional, per-datacenter resource names from your configuration. They are named as "resname/dcname". For example, if you define a metafo resource named "prodwww" with the datacenter list "[ pri, sec ]", the resource names "prodwww/pri" and "prodwww/sec" will be sythesized and can be used in zonefile records, e.g.:

www-backup 300 DYNA metafo!prodwww/sec

When used, these per-datacenter synthetic resource names cause a given lookup to skip the normal failover process and directly return results from that particular datacenter.
