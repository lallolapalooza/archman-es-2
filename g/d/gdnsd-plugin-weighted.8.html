NOMBRE

gdnsd-plugin-weighted - plugin de gdnsd que implementa registros "weighted"

SINOPSIS

Ejemplo de configuración de plugin:

plugins => {
  weighted => {
    multi = false # por defecto
    service_types = up
    up_thresh => 0.5 # por defecto
    corpwww => {
      lb01 = [ lb01.example.org., 99 ]
      lb02 = [ lb02.example.org., 15 ]
      lb03 = [ lb03.example.org., 1 ]
    }
    frontwww6 => {
      service_types = up
      multi = true
      wwwhost01 = [ 2001:db8::123, 4 ]
      wwwhost02 = [ 2001:db8::456, 1 ]
      wwwhost03 = [ 2001:db8::789, 2 ]
    }
    pubwww => {
      service_types = [ web_check, foo ]
      up_thresh => 0.01,
      pubhost01 = [ 192.0.2.1, 44 ]
      pubhost02 = [ 192.0.2.2, 11 ]
      pubhost03 = [ 192.0.2.3, 11 ]
      pubhost04 = [ 192.0.2.4, 11 ]
    }
    cdnwww => {
      service_types = web_check
      datacenter1 => {
        d1-lb1 = [ 127.0.0.1, 2 ]
        d1-lb2 = [ 127.0.0.2, 2 ]
      }
      datacenter2 => {
        d2-lb1 = [ 127.0.0.3, 2 ]
        d2-lb2 = [ 127.0.0.4, 2 ]
        d2-lb3 = [ 127.0.0.5, 1 ]
      }
    }
    mixed => {
      multi => false,
      addrs_v4 => {
        lb1 = [ 127.0.0.3, 2 ]
        lb2 = [ 127.0.0.4, 2 ]
      }
      addrs_v6 => {
        multi => true
        www6set1 = {
          lb01 => [ 2001:db8::123, 4 ]
          lb02 => [ 2001:db8::456, 1 ]
        }
        www6set2 = {
          lb01 => [ 2001:db8::789, 4 ]
          lb02 => [ 2001:db8::ABC, 1 ]
        }
      }
    }
    cn => {
      service_types = my_cn_check
      foo = [ lb01.example.org., 99 ]
      bar = [ lb02.example.org., 15 ]
    }
  }
}

RR de zona que hacen referencia a lo anterior, en example.com:

www.corp   300 DYNC weighted!corpwww
www6.front 300 DYNA weighted!frontwww6
www        300 DYNC weighted!pubwww
cdn        300 DYNA weighted!cdnwww
mixed-a    300 DYNA weighted!mixed
cnames     300 DYNC weighted!cn

DESCRIPCIÓN

gdnsd-plugin-weighted se puede utilizar para devolver uno (o un subconjunto) de varios registros de direcciones, o uno de varios registros CNAME basados en probabilidades ponderadas dinámicas.

CONFIGURACIÓN - NIVEL SUPERIOR

En el nivel superior, hay tres claves de parámetro especiales: "service_types", "up_thresh" y "multi". "multi" se ignora para recursos basados en CNAME. Todas estas claves se heredan y pueden ser anuladas en los niveles por recurso y por familia de direcciones.

"service_types" establece cómo se supervisan las direcciones o CNAME aplicables. El valor por defecto "service_types" de nivel superior es "up", que es un tipo de servicio integrado proporcionado por gdnsd. Para obtener más información sobre cómo configurar tipos de servicio no predeterminados, consulte la documentación principal de gdnsd.config(5).

"multi" es un booleano que puede ser "true" o "false", y por defecto es "false". "multi" controla el comportamiento del algoritmo para seleccionar direcciones de resultado, que se discute en detalle más adelante.

"up_thresh" define una fracción de punto flotante de los pesos de dirección sumados en el rango "(0.0 - 1.0]", con un valor por defecto de 0.5, y se utiliza para influir en el comportamiento de fallo/conmutación por error.

Aparte de esos tres, el resto de las claves de nivel superior son los nombres de sus recursos, y sus valores son la configuración de cada recurso.

CONFIGURACIÓN - POR RECURSO

Dentro de la configuración de un recurso determinado, de nuevo los tres parámetros relacionados con la dirección "services_types", "multi" y "up_thresh" pueden especificarse para anular su configuración por recurso.

Hay dos modos de configuración básicos dentro de un recurso:

1) Subcláusulas de dirección explícitas por familia. En este modo, el recurso contiene una o más de las claves "addrs_v4" y "addrs_v6". Normalmente se usarían ambas juntas, ya que es más simple usar la segunda opción al configurar una sola familia de direcciones.

El contenido de cada subcláusula configura los RR de respuesta del tipo de dirección dado para este recurso, y los 3 parámetros de comportamiento "service_types", "multi" y "up_thresh" pueden ser anulados también por familia de direcciones.

2) Detección automática de nivel superior de una sola familia de direcciones o CNAMEs. En este modo, puede configurar el nivel superior de un recurso con entradas directas, siempre que coincidan con un conjunto de un solo tipo: todas las direcciones IPv4, todas las direcciones IPv6 o todos los CNAMEs, y el tipo se detectará automáticamente.

Los recursos que contienen listas ponderadas de CNAMEs en lugar de direcciones solo se pueden usar con registros "DYNC" en los archivos de zona, mientras que los que contienen solo direcciones se pueden usar en registros "DYNC" o "DYNA".

CONFIGURACIÓN - CNAMEs

Al configurar CNAMEs, el valor de cada elemento debe ser "[ CNAME, PESO ]", y el recurso será útil para registros de zona "DYNC", resolviendo a un registro CNAME ponderado en las respuestas. El algoritmo de selección basado en pesos y resultados de monitorización es como se documenta a continuación para direcciones en EL CASO ÚNICO NO AGRUPADO, ya que los grupos de CNAMEs no se pueden configurar, y la opción "multi" no es válida para ellos.

Los datos de CNAME deben estar completamente calificados (terminar en "."), y un "DYNC" no se puede utilizar para emitir un CNAME que apunte dentro de la misma zona que contenía el "DYNC".

CONFIGURACIÓN - DIRECCIONES

Con la excepción de que "addrs_v4" y "addrs_v6" deben contener solo direcciones de la familia correcta (o en el caso de detección automática de nivel superior, las entradas de nivel superior deben ser todas de la misma familia), las dos subcláusulas se comportan de manera idéntica. Cuando ambas están presentes, ambas se utilizan en cada respuesta "DYNA" (ya que gdnsd siempre incluye registros de familia opuesta en la sección Adicional de consultas A/AAAA).

Dentro de cada tipo de familia de direcciones, hay dos dimensiones binarias diferentes (multi -> true/false, y agrupado vs no agrupado) en las que se basan la configuración y el comportamiento, lo que lleva a cuatro casos posibles: único no agrupado, múltiple no agrupado, único agrupado y múltiple agrupado. Cada uno se discutirá en detalle a continuación:

EL CASO ÚNICO NO AGRUPADO

Este es el caso más simple. El código detecta este caso cuando ve que "multi" es falso (el valor por defecto), y que los valores de las claves son matrices en lugar de sub-hashes. Cada clave de hash es una etiqueta de dirección, y cada valor es una matriz de "[ IPADDR, PESO ]".

Al responder a una consulta en este caso, primero los pesos se convierten en pesos dinámicos. El peso dinámico de una dirección es su peso configurado si el estado monitorizado es "UP", o cero si el estado monitorizado es "DOWN". Los pesos dinámicos se suman para producir un total de peso dinámico, y luego se elige una única dirección para responder del conjunto, con cada dirección teniendo las probabilidades "peso_dinámico_dir / peso_total_dinámico".

Sin embargo, si el "peso_total_dinámico" es menor que "ceil(umbral_subida * peso_total_configurado)", entonces el

dinámica los pesos se restablecen todos a sus valores completos configurados de modo que las probabilidades de respuesta sean las mismas que si todos estuvieran "UP", y el fallo a nivel de recurso se señala a cualquier meta-plugin de capa superior (por ejemplo, metafo o geoip) cuando corresponda.

Ejemplo (X podría ser un recurso completo, o una sección addrs_v4):

X => {
  multi => false # por defecto
  # las probabilidades asumen que ninguna dirección está caída:
  lb01 => [ 192.0.2.1, 45 ] # 25% de probabilidad (45/180)
  lb02 => [ 192.0.2.1, 60 ] # 33% de probabilidad (60/180)
  lb03 => [ 192.0.2.1, 75 ] # 42% de probabilidad (75/180)
}

EL CASO MULTI SIN AGRUPAR

Este caso se detecta cuando, (como arriba) los valores de las claves son matrices de "[ IPADDR, WEIGHT]", pero el parámetro "multi" es verdadero. El cambio con respecto al comportamiento anterior es principalmente que en cada respuesta se pueden devolver múltiples direcciones del conjunto ponderado. Se encuentra el "máximo", en lugar de la suma, de los pesos dinámicos (de nuevo, cero para direcciones caídas, peso configurado en caso contrario), y la probabilidad de inclusión de cada dirección en el conjunto de respuesta es "addr_dyanmic_weight / max_dynamic_weight".

Esto significa que todas las direcciones que no estén"DOWN" y que compartan el valor de peso dinámico máximo del grupo siempre se incluirán, mientras que otras se incluirán opcionalmente dependiendo de las probabilidades. Siempre se devuelve al menos una dirección (porque lógicamente, al menos una dirección tiene el peso máximo, dándole un 100% de probabilidad), y a veces se devolverá el conjunto completo que no esté"DOWN" .

"up_thresh" se comporta como en el caso anterior: Si la suma de los valores de peso dinámico es menor que "ceil(up_thresh * total_configured_weight)", entonces todos los pesos dinámicos se establecen en sus valores configurados y el conjunto de resultados se calcula como si todos estuvieran "UP", señalando al mismo tiempo el fallo a nivel de recurso a los meta-plugins superiores (geoip o metafo).

Ejemplo:

X => {
  multi => true
  # las probabilidades asumen que ninguna dirección está caída:
  lb01 => [ 192.0.2.1, 45 ] # 75% de probabilidad (45/60)
  lb02 => [ 192.0.2.1, 60 ] # 100% de probabilidad (60/60)
  lb03 => [ 192.0.2.1, 60 ] # 100% de probabilidad (60/60)
  # conjuntos de resultados posibles en general:
  # lb01,lb02,lb03 -> 75%
  # lb02,lb03 -> 25%
}

EL CASO ÚNICO AGRUPADO

Los casos agrupados se detectan cuando los valores de las claves son sub-hashes en el nivel exterior en lugar de matrices de "[ IPADDR, WEIGHT]". En el caso agrupado, primero el conjunto se divide en grupos con nombre, y luego dentro de cada grupo las direcciones individuales se configuran como "addrlabel => [ IPADDR, WEIGHT ]".

Ejemplo:

X => {
  group1 => {
    lb01 => [ 192.0.2.1, 10 ]
    lb02 => [ 192.0.2.1, 20 ]
    lb03 => [ 192.0.2.1, 30 ]
  }
  group2 => {
    lb01 => [ 192.0.2.7, 10 ]
    lb02 => [ 192.0.2.8, 20 ]
    lb03 => [ 192.0.2.9, 30 ]
  }
}

El caso único agrupado, por supuesto, ocurre cuando la configuración es como se muestra arriba, y el parámetro "multi" es "false" (el valor por defecto).

En el modo único agrupado, esencialmente los grupos se ponderan entre sí de manera similar al caso único para direcciones sin agrupar, resultando en la elección de un solo grupo del conjunto de grupos. Luego las direcciones dentro del grupo elegido se ponderan entre sí en estilo multi, devolviendo potencialmente más de una dirección del grupo elegido.

Específicamente, la probabilidad de que cada grupo sea el único grupo elegido es "group_dyn_weight / total_dyn_weight", donde el peso dinámico del grupo es la suma de los pesos dinámicos dentro de él ("DOWN" las direcciones son cero), y el peso dinámico total es la suma dinámica de todos los grupos. Luego dentro de cada grupo, la probabilidad de que cada dirección se incluya en el conjunto de respuesta multi es "addr_dyn_weight / group_max_dyn_weight".

"up_thresh" opera sobre todos los grupos en su conjunto, y si la suma que no es"DOWN" de todos los pesos en todos los grupos no cumple el estándar de "ceil(up_thresh * total_sum_configured_weight)", entonces todas las direcciones se tratarán como si estuvieran "UP" a efectos de selección, y el fallo a nivel de recurso se señalará hacia arriba.

EL CASO MULTI AGRUPADO

Probablemente puedas inferir el comportamiento de este leyendo sobre los tres casos anteriores. La diferencia con el caso único agrupado anterior es que los comportamientos multi-verso-único están invertidos. Se eligen múltiples grupos basándose en el peso dinámico máximo entre los grupos, y se devuelve una única dirección ponderada del subconjunto dentro de cada grupo elegido. Todos los detalles anteriores se aplican lógicamente de la manera que esperarías, ya que estos cuatro casos comparten internamente el mismo código y lógica, simplemente aplican diferentes partes de él a diferentes subconjuntos del problema.

NOTAS GENERALES SOBRE LOS CASOS DE MODO DE DIRECCIÓN ANTERIORES

Ten en cuenta que cada vez que la selección múltiple está en efecto en una capa (la capa superior cuando multi es verdadero, o dentro de un grupo cuando multi es falso), el recuento mínimo de elementos elegidos será el recuento de elementos que comparten el peso máximo dentro del conjunto. Por ejemplo, un conjunto de elementos con pesos "30, 30, 30, 20, 20" siempre elegirá al menos 3/5 de los elementos (porque los primeros tres tienen un 100% de probabilidad de inclusión), y el conjunto total de respuesta oscilará hasta los 5 elementos con alguna probabilidad.

Un ejemplo de caso de uso práctico para el único agrupado:

Dividir los grupos en límites de subred en modo único agrupado da como resultado que un paquete de respuesta único nunca mezcle subredes. Esto permitiría que tu balanceo basado en DNS derrote ciertas formas de interferencia en la Selección de Dirección de Destino a nivel de cliente, devolviendo aún múltiples direcciones por respuesta (todas de una misma subred).

Un caso de uso práctico para el multi agrupado:

Supongamos que tienes un conjunto grande de direcciones que se pueden agrupar lógicamente en subconjuntos que tienen algún riesgo de fallo compartido (por ejemplo, subparticiones de un centro de datos que comparten infraestructura). Con el comportamiento multi agrupado, los clientes obtendrán hasta N (recuento de grupos) direcciones en una respuesta round-robin, pero un conjunto de respuesta determinado nunca contendrá dos direcciones del mismo grupo/subconjunto. Esto maximiza la probabilidad de que el cliente pueda cambiar con éxito a otra dirección de la lista cuando su selección principal falla, ya que el conjunto total en cada respuesta no comparte ningún modo de fallo por subconjunto.

LÍMITES

Todos los pesos deben ser valores enteros positivos mayores que cero y menores que 2^20 (1048576).

Hay un límite de 64 direcciones, grupos de direcciones o cnames en el nivel superior de un recurso (o por familia de direcciones en los casos addrs_v4/addrs_v6), y un límite de 64 direcciones dentro de cada grupo de direcciones en los modos agrupados.

    NOMBRE

    gdnsd-plugin-weighted - plugin de carga de peso para gdnsd

    SINOPSIS

    Este es un plugin de gdnsd que permite la selección de registros DNS basada en el peso asignado a cada uno. Los registros con un peso mayor tienen una probabilidad mayor de ser seleccionados.

    DETALLES

    El plugin weighted se utiliza para configurar registros DNS donde se desea una distribución no uniforme de las consultas entre múltiples direcciones IP o destinos.

    Cuando se configura un registro con este plugin, se le asigna un peso a cada uno de los destinos disponibles. Gdnsd, al recibir una consulta para este registro, seleccionará un destino basado en las probabilidades derivadas de estos pesos.

    La sintaxis para la configuración dentro del archivo de configuración de gdnsd (normalmente /etc/gdnsd/gdnsd.conf) sería similar a:

    plugin: weighted
config:
  record_name:
    A:
      - ip: 192.168.1.10
        weight: 10
      - ip: 192.168.1.11
        weight: 5
      - ip: 192.168.1.12
        weight: 5
    AAAA:
      - ip: "2001:db8::1"
        weight: 10
      - ip: "2001:db8::2"
        weight: 5

    En este ejemplo, para el registro record_name, la dirección IP 192.168.1.10 tiene una probabilidad del 50% de ser seleccionada (10 de 20), mientras que las otras dos tienen una probabilidad del 25% cada una.

    CASOS DE MODO DE DIRECCIÓN

    Este plugin es particularmente útil en escenarios donde se desea:

    • Distribución de carga: Dirigir más tráfico a servidores más potentes o con mayor capacidad.
    • Despliegues escalonados (Blue/Green deployments): Enviar un pequeño porcentaje de tráfico a una nueva versión de un servicio para pruebas antes de migrar completamente.
    • Redundancia con prioridad: Favorecer un servidor primario sobre uno secundario.

    NOTAS GENERALES SOBRE LOS CASOS DE MODO DE DIRECCIÓN ANTERIORES

    La implementación del plugin weighted se basa en un algoritmo de selección probabilística que asegura que, a largo plazo, el tráfico se distribuya de acuerdo con los pesos definidos. La selección se realiza para cada consulta individualmente.

    LÍMITES

    No hay límites inherentes en cuanto al número de registros que pueden ser configurados con este plugin, ni en la cantidad de destinos por registro. Sin embargo, los límites prácticos estarán determinados por los recursos del sistema (memoria, CPU) y las capacidades de gdnsd.

    Los pesos deben ser enteros positivos. Un peso de cero o negativo no es válido y podría causar un error de configuración.
