DESCRIPCIÓ

N

gpsd es un demonio monitor que recopila información de GPS, radios de GPS diferencial, o receptores AIS conectados a la máquina anfitriona. Se espera que cada GPS, radio DGPS, o receptor AIS esté directamente conectado al anfitrión a través de un dispositivo serie USB o RS232C. El dispositivo serie puede especificarse a gpsd al inicio, o puede establecerse mediante un comando enviado por un socket de control local (p. ej., por un script de conexión USB). Dado un dispositivo GPS por cualquiera de los dos medios, gpsd descubre la velocidad de puerto y el protocolo correctos para

él.

gpsd debería poder consultar cualquier GPS que hable ya sea el protocolo textual estándar NMEA 0183, o los (diferentes) dialectos NMEA extendidos usados por MTK-3301, iTrax, Motorola OnCore, Sony CXD2951, Ashtech/Thales y algunos otros dispositivos. También puede interpretar los protocolos binarios usados por los dispositivos EverMore, Garmin, Javad, Navcom, Rockwell/Zodiac, SiRF, Trimble y u-blox. Bajo Linux puede leer paquetes NMEA2000 a través del socket CAN del kernel. Puede leer información de rumbo y actitud de las brújulas digitales TNT

Revolution.

Los formatos de informe GPS soportados por su binario de gpsd pueden diferir dependiendo de cómo fue compilado; las versiones de propósito general soportan muchas, pero puede construirse con subconjuntos de protocolos reducidos hasta un solo protocolo para su uso en entornos restringidos. Para una lista de los protocolos GPS soportados por su binario, véase la salida de gpsd

-l

gpsd oculta efectivamente las diferencias entre los tipos de GPS que soporta. También conoce y usa comandos que ajustan estos GPS para menor latencia. Usando gpsd como intermediario, las aplicaciones evitan la contención por los dispositivos

serie.

gpsd puede usar correcciones de GPS diferencial de una radio DGPS o a través de la red, desde una estación terrestre que ejecute un servidor DGPSIP o un transmisor Ntrip que informe datos RTCM-104; esto puede reducir los errores de posición. Cuando gpsd abre un dispositivo serie que emite RTCM-104, automáticamente reconoce esto y usa el dispositivo como fuente de corrección para todos los GPS conectados que acepten correcciones RTCM (esto depende del tipo de GPS; no todos los GPS tienen la capacidad de firmware para aceptar paquetes de corrección RTCM)

.

Las aplicaciones cliente típicamente se comunican con gpsd a través de un puerto TCP/IP, puerto 2947 por defecto. Se soportan conexion

es IPv4 e IPv6 y un cliente puede con
ectarse a través de cualquiera de las dos.

GESTIÓN DE DISPOSITIVOS

GPS

gpsd mantiene una lista interna de dispositivos GPS (el "conjunto de dispositivos"). Si especifica dispositivos en la línea de comandos, la lista se inicializa con esas rutas; de lo contrario, la lista comienza vacía. Los comandos para añadir y quitar rutas de dispositivos GPS de la lista de dispositivos del demonio deben escribirse en un socket de dominio Unix local que solo será accesible para programas que se ejecuten como root. Este socket de control se ubicará donde lo especifique la opción

-F.

Un dispositivo también puede ser eliminado del conjunto si GPSD obtiene una lectura de longitud cero de él. Esta condición de fin de archivo indica que el dispositivo ha sido

desconectado.

Cuando gpsd se instala junto con scripts de notificación de conexión (hotplug) funcionales que le envían comandos de adición de dispositivos a través del socket de control, gpsd no debería requerir ninguna configuración ni acción del usuario para encontrar dispositivos de conexión (hotplug)

.

Enviar SIGHUP a un gpsd en ejecución lo fuerza a cerrar todos los GPS y todas las conexiones de clientes. Luego intentará reconectarse a cualquier GPS en su lista de dispositivos y reanudará la escucha de conexiones de clientes. Esto puede ser útil si su GPS entra en un estado bloqueado o confundido pero puede ser reiniciado suavemente bajando

DTR.

Cuando

CONTROL SOCKET

gpsd is called with no initial devices (thus, expecting devices to be passed to it by notifications to the control socket), and reaches a state where there are no devices connected and no subscribers after some devices have been seen, it shuts down gracefully. It is expected that future device hotplug events will reactivate it.

To point gpsd at a device that may be a GPS, write to the control socket a plus sign ('+') followed by the device name followed by LF or CR-LF. Thus, to point the daemon at /dev/foo. send "+/dev/foo\n". To tell the daemon that a device has been disconnected and is no longer available, send a minus sign ('-') followed by the device name followed by LF or CR-LF. Thus, to remove /dev/foo from the search list, send "-/dev/foo\n".

To send a control string to a specified device, write to the control socket a '!', followed by the device name, followed by '=', followed by the control string.

To send a binary control string to a specified device, write to the control socket a '&', followed by the device name, followed by '=', followed by the control string in paired hex digits.

Your client may await a response, which will be a line beginning with either "OK" or "ERROR". An ERROR response to an 'add' command means the device did not emit data recognizable as GPS packets, an ERROR response to a remove command means the specified device was not in gpsd's device pool. An ERROR response to a '!' command means the daemon did not recognize the devicename specified.

The control socket is intended for use by hotplug scripts and other device-discovery services. This control channel is separate from the public gpsd service port, and only locally accessible, in order to prevent remote denial-of-service and spoofing attacks.

ACCURACY

The base User Estimated Range Error (UERE) of GPSes is 8 meters or less at 66% confidence, 15 meters or less at 95% confidence. Actual horizontal error will be UERE times a dilution factor dependent on current satellite position. Altitude determination is more sensitive to variability in ionospheric signal lag than latitude/longitude is, and is also subject to errors in the estimation of local mean sea level, base error is 12 meters at 66% confidence, 23 meters at 95% confidence. Again, this will be multiplied by a vertical dilution of precision (VDOP) dependent on satellite geometry, and VDOP is typically larger than HDOP. Users should not rely on GPS altitude for life-critical tasks such as landing an airplane.

These errors are intrinsic to the design and physics of the GPS system. gpsd does its internal computations at sufficient accuracy that it will add no measurable position error of its own.

DGPS correction may reduce UERE, provided you are within about 100 miles (160 km) of a DGPS ground station from which you are receiving corrections.

On a 4800bps connection, the time latency of fixes provided by gpsd will be one second or less 95% of the time. Most of this lag is due to the fact that GPSes normally emit fixes once per second, thus expected latency is 0.5sec. On the personal-computer hardware available in 2005 and later, computation lag induced by gpsd will be negligible, on the order of a millisecond. Nevertheless, latency can introduce significant errors for vehicles in motion, at 50 km/h (31 mi/h) of speed over ground, 1 second of lag corresponds to 13.8 meters change in position between updates.

The time reporting of the GPS system itself has an intrinsic accuracy limit of 14 nanoseconds, but this can only be approximated by specialized receivers using that send the high-accuracy PPS (Pulse-Per-Second) over RS232 to cue a clock crystal. Most GPS receivers only report time to a precision of 0.01s or 0.001s, and with no accuracy guarantees below 1sec.

If your GPS uses a SiRF chipset at firmware level 231, reported UTC time may be off by the difference between whatever default leap-second offset has been compiled in and whatever leap-second correction is currently applicable, from startup until complete subframe information is received. Firmware levels 232 and up don’t have this problem. You may run gpsd at debug level 4 to see the chipset type and firmware revision level.

There are exactly two circumstances under which gpsd relies on the host-system clock:

In the GPS broadcast signal, GPS time is represented using a week number that rolls over after 2^10 or 2^13 weeks (about 19.6 years, or 157 years), depending on the spacecraft. Receivers are required to disambiguate this to the correct date, but may have difficulty due to not knowing time to within half this interval, or may have bugs. Users have reported incorrect dates which appear to be due to this issue. gpsd uses the startup time of the daemon detect and compensate for rollovers while it is running, but otherwise reports the date as it is reported by the receiver without attempting to correct it.

If you are using an NMEA-only GPS (that is, not using SiRF or Garmin or Zodiac binary mode), gpsd relies on the system clock to tell it the current century. If the system clock returns an invalid value near zero, and the GPS does not emit GPZDA at the start of its update cycle (which most consumer-grade NMEA GPSes do not) then the century part of the dates gpsd delivers may be wrong. Additionally, near the century turnover, a range of dates as wide in seconds as the accuracy of your system clock may be referred to the wrong century.

USE WITH NTP

gpsd can provide reference clock information to ntpd or chronyd, to keep the system clock synchronized to the time provided by the GPS receiver.

On Linux, gpsd includes support for interpreting the PPS pulses emitted at the start of every clock second on the carrier-detect lines of some serial GPSes, this pulse can be used to update NTP at much higher accuracy than message time provides. You can determine whether your GPS emits this pulse by running at -D 5 and watching for carrier-detect state change messages in the logfile. In addition, if your kernel provides the RFC 2783 kernel PPS API then gpsd will use that for extra accuracy.

gpsd communicates with ntpd using shared memory segments (SHMs). The SHMs are numbered SHM(0) to SHM(7). and have a name (key) of NTP0 to NTP7. The first local time source on the command line may use NTP0 and NTP1. The second may use NTP2 and NTP3, etc.

You can see the output of gpsd to ntpd in real time with the ntpshmmon command.

Other daemons, such as ptp4l may also be using the same SHMs to talk to ntpd.

Detailed instructions for using GPSD to set up a high-quality time service can be found among the documentation on the GPSD website.

USE WITH D-BUS

On operating systems that support D-BUS, gpsd can be built to broadcast GPS fixes to D-BUS-aware applications. As D-BUS is still at a pre-1.0 stage, we will not attempt to document this interface here. Read the gpsd source code to learn more.

SECURITY AND PERMISSIONS ISSUES

gpsd, if given the -G flag, will listen for connections from any reachable host, and then disclose the current position. Before using the -G flag, consider whether you consider your computer’s location to be sensitive data to be kept private or something that you wish to publish.

gpsd must start up as root in order to open the NTPD shared-memory segment, open its logfile, and create its local control socket. Note that starting gpsd with sudo is not the same as starting as root. Before doing any processing of GPS data, it tries to drop root privileges by setting its UID to "nobody" (or another configured userid) and its group ID to the group of the initial GPS passed on the command line — or, if that device doesn’t exist, to the group of /dev/ttyS0.

Privilege-dropping is a hedge against the possibility that carefully crafted data, either presented from a client socket or from a subverted serial device posing as a GPS, could be used to induce misbehavior in the internals of gpsd. It ensures that any such compromises cannot be used for privilege elevation to root.

The assumption behind gpsd's particular behavior is that all the tty devices to which a GPS might be connected are owned by the same non-root group and allow group read/write, though the group may vary because of distribution-specific or local administrative practice. If this assumption is false, gpsd may not be able to open GPS devices in order to read them (such failures will be logged).

In order to fend off inadvertent denial-of-service attacks by port scanners (not to mention deliberate ones), gpsd will time out inactive client connections. Before the client has issued a command that requests a channel assignment, a short timeout (60 seconds) applies. There is no timeout for clients in watcher or raw modes; rather, gpsd drops these clients if they fail to read data long enough for the outbound socket write buffer to fill. Clients with an assigned device in polling mode are subject to a longer timeout (15 minutes).

LIMITACIONE

S

Si múltiples emisores NMEA envían frases RMC, GLL y GGA al mismo dispositivo serie (posible con un adaptador RS422 conectado a algunos sistemas de navegación marítima), una respuesta 'TPV' puede mezclar una altitud de la GGA de un dispositivo con la latitud/longitud de la RMC/GLL de otro después de que la segunda frase haya

llegado.

gpsd puede cambiar la configuración de control de su GPS (como la frecuencia de emisión de diversas frases o paquetes) y no restaurar la configuración original al salir. Esto es resultado de deficiencias en NMEA y los protocolos binarios de GPS de los proveedores, que a menudo no dan a los clientes ninguna forma de consultar los valores de la configuración de control para poder restaurarlos más

tarde.

Algunos receptores no reportan cifras VDOP/TDOP/GDOP y estimaciones de error asociadas. En ese caso, pueden ser calculadas por gpsd en su lugar. Este cálculo no coincide exactamente con lo que los chips hacen internamente, lo que incluye un cierto ponderado de satélites usando parámetros gpsd no puede

ver.

El autobaudeo en los GPS Trimble puede tardar hasta 20 segundos, o más, si la velocidad del dispositivo no coincide con la velocidad del GPS. Use la opción -s para evitar retrasos de

autobaudeo.

La generación de estimaciones de error de posición (eph, epv, epd, eps, epc) a partir de los datos incompletos devueltos por los protocolos de reporte de GPS implica tanto mucho arte matemático oscuro como suposiciones frágiles dependientes del dispositivo. Este código ha sido propenso a errores en el pasado y los problemas pueden seguir ocultándose

allí.

La decodificación AIVDM de los tipos 16-17, 22-23 y 25-26 no está

verificada.

GPSD actualmente reconoce completamente solo el nivel 2.1 de RTCM2 (tipos de mensaje 1, 3, 4, 5, 6, 7, 9, 16). Los tipos de mensaje 13, 14 y 31 de la versión 2.3 son reconocidos y reportados. Los tipos de mensaje 8, 10-12, 15-27, 28-30 (indefinidos), 31-37, 38-58 (indefinidos) y 60-63 aún no están

soportados.

La lógica del decodificador ISGPS usada para RTCM2 y subtramas es lo suficientemente enrevesada como para confundir a algunos optimizadores de compiladores, notablemente en GCC 3.x con -O2, generando código

defectuoso.

Los dispositivos destinados a usar PPS para cronometraje de alta precisión pueden fallar si se especifican después del inicio mediante un comando de socket de control, a diferencia de en la línea de comandos original del demonio. Los privilegios de root se eliminan temprano, y algunas variantes de Unix los requieren para establecer la disciplina de línea PPS. Bajo Linux, la capacidad POSIX para establecer la disciplina de línea se mantiene, pero otras plataformas no pueden usar este

código.

Los dispositivos GPS USB a menudo no se identifican a sí mismos a través del subsistema USB; típicamente se presentan como la clase 00h (indefinida) o clase FFh (específica del proveedor) de adaptadores USB a serie. Debido a esto, los scripts de hotplug de Linux deben decirle a gpsd que huela datos de cada adaptador USB a serie que se active y se sepa que es de un tipo usado en GPS. A ningún dispositivo de este tipo se le envían cadenas de configuración hasta después de que haya sido identificado como un GPS, y gpsd nunca abre un dispositivo que está abierto por otro proceso. Pero hay una pequeña ventana para que los dispositivos no-GPS no se abran; si la aplicación que los quiere

pierde una carrera con GPSD, su apertura de dispositivo fallará y tendrá que reintentar
se después de que GPSD huela el dispositivo (normalmente menos de un segundo después).

APLICABLES

Los estándares oficiales del protocolo NMEA para NMEA0183 y NMEA2000 están disponibles en la National Marine Electronics Association, pero son propietarios y caros; los mantenedores de gpsd han hecho un punto de no mirarlos. El sitio web del proyecto GPSD enlaza a varios documentos que recopilan información divulgada públicamente sobre el

protocolo.

gpsd analiza las siguientes frases NMEA: RMC, GGA, GLL, GSA, GSV, VTG, ZDA, GBS, HDT, DBT, GST. Las reconoce con el prefijo normal de ID de emisor GP, o con el prefijo GN usado por GLONASS, o con el prefijo II emitido por los sistemas de navegación marítima Seahawk Autohelm, o con el prefijo IN emitido por algunas unidades Garmin, o con el prefijo EC emitido por unidades ECDIS, o con el prefijo SD emitido por sondadores de profundidad, o con los prefijos HC y TI emitidos por algunos equipos Airmar. Reconoce algunas extensiones de proveedor: el PGRME emitido por algunos modelos de GPS Garmin, el PTNTHTM emitido por brújulas digitales True North, el PMTK omitido por algunos GPS de San Jose Navigation, y las frases PASHR emitidas por algunos GPS

Ashtech.

Tenga en cuenta que gpsd JSON devuelve grados decimales puros, no el formato híbrido de grado/minuto descrito en el estándar

NMEA.

Las correcciones de GPS diferencial se transmiten mediante los protocolos RTCM. El estándar aplicable para RTCM-104 V2 es RTCM Recommended Standards for Differential GNSS (Global Navigation Satellite) Service RTCM Paper 136-2001/SC 104-STD. El estándar aplicable para RTCM-104 V3 es RTCM Standard 10403.1 for Differential GNSS Services - Version 3 RTCM Paper 177-2006-SC104-STD. Las instrucciones de pedido para los estándares RTCM son accesibles desde el sitio web de la Radio Technical Commission for Maritime Services bajo

"Publications".

AIS está definido por la Recomendación ITU M.1371, Technical Characteristics for a Universal Shipborne Automatic Identification System Using Time Division Multiple Access. El formato AIVDM/AIVDO entendido por este programa está definido por IEC-PAS 61162-100, Maritime navigation and radiocommunication equipment and systems. Una descripción más accesible de ambos se puede encontrar en AIVDM/AIVDO Protocol Decoding, en la página de referencias del sitio web del proyecto

GPSD.

Los datos de subtrama están definidos por IS-GPS-200, GLOBAL POSITIONING SYSTEM WING (GPSW) SYSTEMS ENGINEERING & INTEGRATION, INTERFACE SPECIFICATION IS-GPS-200. El formato entendido por este programa está definido en la Sección 20 (Apéndice II)
