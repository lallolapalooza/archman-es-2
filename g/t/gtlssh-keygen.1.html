DESCRIPCIÓ

N

El programa gtlssh-keygen se utiliza para facilitar el manejo de claves para

gtlssh.

Generalmente, cuando comienza a usar gtlssh en un sistema,

ejecutaría


gtlssh-keygen

keygen

y este creará las claves para usted. Debería hacer lo mismo en cualquier sistema de destino al que desee iniciar sesión con gtlssh. Luego copie el archivo default.crt de su directorio $HOME/.gtlssh al directorio $HOME/.gtlssh/allowed_certs del destino. Después

ejecute


gtlssh

rehash

en el sistema de destino para generar los hashes. Después de eso, debería poder iniciar sesión sin

contraseña.

Cuando necesite regenerar sus claves,

ejecute


gtlssh-keygen

keygen

nuevamente. Le pedirá confirmación para reemplazarlas. Si reemplaza las claves, las antiguas se guardarán con un ".1" añadido al nombre del archivo. Una vez que reemplace las claves, deberá enviar las nuevas claves a todos sus destinos. Puede

ejecutar


gtlssh-keygen pushcert destino1 [destino2 [...]

]

para actualizar las claves en todos esos destinos. Usará

las credenciales antiguas (con el ".1" añadido) pa
ra hacerlo, por lo que debería funcionar fácilmente.

DIFERENCIAS CON

SSH

A diferencia de ssh, las claves ssl tienen tiempos de vida. Por defecto, gtlssh crea claves con un tiempo de vida de 1 año, aunque puede cambiar esto. Aunque esto es un poco molesto, es una buena idea reemplazar sus claves periódicamente, por lo que podría considerarse algo

bueno.

gtlssh le permite crear claves para destinos específicos y usarlas automáticamente. Suponga, por ejemplo, que desea usar una clave diferente para iniciar sesión en el destino abc.my.domain. Haría lo

siguiente:


gtlssh-keygen keygen abc.my.

domain

y esto creará una clave y un certificado en el directorio .gtlssh/keycerts con los nombres abc.my.domain.crt y abc.my.domain.key. Necesitaría copiar ese certificado (no el default.crt) a su destino remoto. gtlssh vería que esas claves están ahí y las usaría automáticamente cuando inicie sesión en abc.my.domain. El comando pushcert también entiende esto y manejará el envío de las claves adecuadas cuando envíe a abc.my.

domain.

También puede añadir puertos a la generación de claves, y s

olo las usará si se conecta al destino específico en e
l puerto específico. Esto podría ser útil para ser2net.

TRUCOS PARA

WINDOWS

gtlsshd funcionará en Windows, y funcionará de cierta manera sin contraseña, pero ciertas cosas no funcionarán ya que el inicio de sesión no tiene credenciales almacenadas, y no puede crear un token vinculado para inicios de sesión de administrador, por lo que no puede realizar tareas de

administrador.

Para solucionar este problema y permitir aún los inicios de sesión con certificados, puede usar el comando storepw de gtlssh-k

eygen para almacenar su contraseña en su directorio .gtlssh. Esto no es ideal, pero sus claves privadas están ahí de todos
modos, así que no es un gran problema. Los administradores de su sistema podrán ver su contraseña, así que tenga cuidado.

son:
keygen [-p <puerto>]
[nombre_de_host]
Configuración del directorio base (si aún no está configurado) y creación de claves. Si no se especifica nada, crea la clave predeterminada en <basedir>/default.key y <basedir>/default.crt. De lo contrario, crea claves en la forma <keydir>/<host>[,<puerto>].key y <keydir>/<host>[,<puerto>].
crt.
set
up
Igual que keygen, pero no acepta opciones y crea solo el certificado
predeterminado.
rehash [directorio [directorio [...
]]]
La biblioteca openssl que usa gtlssh requiere que los certificados en una biblioteca estén hasheados para poder encontrarlos. Este comando vuelve a hacer los hashes en los directorios indicados. Si no se especifica ningún directorio, vuelve a hashear <basedir>/allowed_certs y <basedir>/server_certs.

Tenga en cuenta que si añade claves a estos directorios, debe volver a hashearlas o no

funcionarán.

rehash eliminará automáticamente cualqui

er certificado
que haya caducado.
addallow [-i] <nombre_de_host>
<archivo>
Añade el archivo indicado como certificado público permitido para el nombre de host indicado. Instalará este archivo en el directorio <basedir>/allowed_certs con el nombre "nombre_de_host.crt". También volverá a hashear el directorio. Si se especifica -i, la entrada proviene de stdin y el archivo no es necesario ni se usa. Si el archivo de destino ya existe, lo renombrará a "nombre_de_host.crt.1.
crt".
pushcert [-n <nombre> ] [-p <puerto>] <nombre_de_host> [[-p <puerto>] <nombre_de_host> [.
..]]
Coloca el certificado local para el host indicado en el host remoto para que pueda usarse para iniciar sesión. Usa credenciales antiguas (credenciales con .1 añadido al nombre, según keygen) si están ahí. Esto es útil si ha actualizado su certificado y necesita enviar uno nuevo a algunos hosts remotos. Encuentra el nombre del certificado como se describe en el comando keygen. Si existen credenciales antiguas, usará esas para conectarse con gtlssh y enviar el certificado. De lo contrario, usará credenciales predeterminadas y esperará lo mejor, probablemente solo útil si se aceptan contraseñas. Esto solo funciona un keygen hacia atrás; si ha ejecutado el comando keygen dos veces para el host, necesitará transferir el certificado manualmente. Por defecto, la credencial en el host remoto se llama como la salida de 'hostname -f' en la máquina local, -n anula
esto.

Crea claves para el servidor, generalmente en /etc/gtlssh/gtlsshd.key y /etc/gtlssh/gtlsshd.crt. Generalmente debe ser root para hacer esto. Úselo para la configuración inicial de gtlsshd.

Si especifica un nombre de clave, el nombre común usado para la clave será "<keyname>.<hostname>" por defecto, a menos que lo establezcas con --commonname. Si no especificas un nombre de clave (por defecto gtlsshd), el nombre común es solo el nombre de host. Esto evita el siguiente problema.

NOTA: Si ejecutas múltiples servidores en el mismo sistema, debes tener un nombre común diferente para cada uno. Algunas versiones de openssl mirarán otro certificado con el mismo nombre común como parte de la misma cadena de certificados y obtendrás un

fallo:


authority and subject key identifier

mismatch

Así que si, por ejemplo, estás ejecutando ser2net y gtlsshd en el mismo sistema, deben tener nombres comunes

diferentes.

En Windows, debes eliminar todos los permisos del archivo de clave excepto para SYSTEM y Administrator. Si gtlssh no se ejecuta, esto es lo primero que debes verificar. (Puedes obtener una consola SYSTEM como se describe a continuación y ejecutar "gtlssh -d" y te dará un error, esto es útil para depurar.) El programa aún no hace esto por defecto, desafortunadamente. Tendrás que configurar el archivo como SYSTEM para hacer esto. El procedimiento

"explorer".

Ve al archivo de clave en el

explorador, haz clic derecho
sobre él y elige Pro
