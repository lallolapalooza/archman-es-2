NOMBRE

zshcalsys - sistema de calendario de zsh

DESCRIPCIÓN

El shell se suministra con una serie de funciones para reemplazar y mejorar el programa tradicional de Unix calendar, que advierte al usuario de eventos inminentes o futuros, cuyos detalles se almacenan en un archivo de texto (típicamente calendar en el directorio de inicio del usuario). La versión proporcionada aquí incluye un mecanismo para alertar al usuario cuando un evento está programado.

Además, se proporcionan las funciones age, before y after que se pueden usar en un calificador de glob; permiten seleccionar archivos basándose en sus tiempos de modificación.

Se describe primero el formato del archivo calendar y las fechas utilizadas allí y en la función age, y luego las funciones que se pueden llamar para examinar y modificar el archivo calendar.

Las funciones aquí dependen de la disponibilidad del módulo zsh/datetime que generalmente se instala con el shell. La función de biblioteca strptime() debe estar disponible; está presente en la mayoría de los sistemas operativos recientes.

FORMATO DE ARCHIVO Y FECHAS

Formato del Archivo de Calendario

El archivo de calendario es por defecto ~/calendar. Esto se puede configurar con el estilo calendar-file, consulte la sección ESTILOS más abajo. El formato básico consiste en una serie de líneas separadas, sin sangría, cada una incluyendo una fecha y especificación de hora seguida de una descripción del evento.

Se admiten varias mejoras a este formato, basadas en la sintaxis del modo calendario de Emacs. Una línea con sangría indica una línea de continuación que amplía la descripción del evento de la línea anterior (tenga en cuenta que la fecha no se puede continuar de esta manera). Se ignora un ampersand inicial (&) por compatibilidad.

Una línea con sangría en la que el primer carácter que no es de espacio en blanco es # no se muestra con la entrada del calendario, pero todavía se escanea en busca de información. Esto se puede utilizar para ocultar información útil para el sistema de calendario pero no para el usuario, como el identificador único utilizado por calendar_add.

No se admite la extensión de Emacs de que una fecha sin descripción pueda referirse a un número de eventos sucesivos en diferentes momentos.

A menos que el estilo done-file se haya modificado, los eventos que se hayan procesado se añaden al archivo con el mismo nombre que el archivo de calendario con el sufijo .done, por lo tanto, ~/calendar.done por defecto.

A continuación se muestra un ejemplo.

Formato de Fecha

El formato de la fecha y la hora está diseñado para permitir flexibilidad sin admitir ambigüedad. (Las palabras `fecha' y `hora' se usan ambas en la documentación a continuación; excepto donde se indique específicamente, esto implica una cadena que puede incluir tanto una fecha como una especificación de hora). Tenga en cuenta que no hay soporte de localización; los nombres de meses y días deben estar en inglés y los caracteres separadores son fijos. La coincidencia no distingue entre mayúsculas y minúsculas, y solo las tres primeras letras de los nombres son significativas, aunque como caso especial una forma que comienza con "month" no coincide con "Monday". Además, las zonas horarias no se manejan; se asume que todas las horas son locales.

Se recomienda que, en lugar de explorar las complejidades del sistema, los usuarios encuentren un formato de fecha que les sea natural y se atiengan a él. Esto evitará efectos inesperados. Se deben tener en cuenta varios hechos clave.

•
En particular, observe la confusión entre mes/día/año y día/mes/año cuando el mes es numérico; estos formatos deben evitarse en la medida de lo posible. Hay muchas alternativas disponibles.
•
El año debe proporcionarse completo para evitar confusiones, y solo se coinciden años entre 1900 y 2099 inclusive.

Los siguientes ofrecen algunos ejemplos obvios; los usuarios que encuentren aquí un formato que les guste y no esté sujeto a las variaciones de estilo pueden omitir la descripción completa. Como las fechas y las horas se comparan por separado (incluso si la hora puede estar incrustada en la fecha), cualquier formato de fecha puede mezclarse con cualquier formato para la hora del día, siempre que los separadores sean claros (espacios en blanco, dos puntos, comas).

2007/04/03 13:13
2007/04/03:13:13
2007/04/03 1:13 pm
3 de abril de 2007, 13:13
Abril 3, 2007 1:13 p.m.
Abr 3, 2007 13:13
Mar 03 Abr 13:13:00 2007
13:13 2007/abr/3

A continuación se detallan las reglas.

Las horas se analizan y extraen antes que las fechas. Deben usar dos puntos para separar horas y minutos, aunque se permite un punto antes de los segundos si están presentes. Esto limita los formatos de hora a los siguientes:

•
HH:MM[:SS[.FFFFF]] [am|pm|a.m.|p.m.]
•
HH:MM.SS[.FFFFF] [am|pm|a.m.|p.m.]

Aquí, los corchetes indican elementos opcionales, posiblemente con alternativas. Se reconocen fracciones de segundo pero se ignoran. Para horas absolutas (el formato normal requerido por el archivo calendar y las funciones age, before y after), la fecha es obligatoria pero la hora del día no lo es; la hora devuelta es al inicio del día. Se permite una variación: si están presentes a.m. o p.m. o una de sus variantes, se permite una hora sin minutos, por ejemplo, 3 p.m..

Las zonas horarias no se manejan, aunque si se detecta una después de una especificación de hora, se eliminará para permitir el análisis de una fecha circundante. Esto solo ocurre si el formato de la zona horaria no es demasiado inusual. Los siguientes son ejemplos de formas que se entienden:

+0100
GMT
GMT-7
CET+1CDT

Cualquier parte de la zona horaria que no sea numérica debe tener exactamente tres letras mayúsculas en el nombre.

Las fechas sufren la ambigüedad entre DD/MM/AAAA y MM/DD/AAAA. Se recomienda evitar esta forma con fechas puramente numéricas, pero el uso de ordinales, por ejemplo, 3rd/04/2007, resolverá la ambigüedad ya que el ordinal siempre se interpreta como el día del mes. Los años deben tener cuatro dígitos (y los dos primeros deben ser 19 o 20); 03/04/08 no se reconoce. Otros números pueden tener ceros iniciales, pero no son obligatorios. Se manejan los siguientes:

•
AAAA/MM/DD
•
AAAA-MM-DD
•
AAAA/MNM/DD
•
AAAA-MNM-DD
•
DD[th|st|rd] MNM[,] [ AAAA ]
•
MNM DD[th|st|rd][,] [ AAAA ]
•
DD[th|st|rd]/MM[,] AAAA
•
DD[th|st|rd]/MM/AAAA
•
MM/DD[th|st|rd][,] AAAA
•
MM/DD[th|st|rd]/AAAA

Aquí, MNM es al menos las tres primeras letras del nombre de un mes, coincidiendo sin distinción entre mayúsculas y minúsculas. El resto del nombre del mes puede aparecer pero su contenido es irrelevante, por lo que janissary, febrile, martial, apricot, maybe, junta, etc. se manejan felizmente.

Donde el año se muestra como opcional, se asume el año actual. Solo hay dos casos de este tipo, el formato Jun 20 o 14 de septiembre (los dos únicos formatos que ocurren comúnmente, aparte de un "the" en algunas formas del inglés, que actualmente no se admite). Tales fechas se volverán ambigüas en el futuro, por lo que idealmente deberían evitarse.

Las horas pueden seguir a las fechas con dos puntos, por ejemplo, 1965/07/12:09:45; esto es para proporcionar un formato sin espacios en blanco. Se permiten una coma y espacios en blanco, por ejemplo, 1965/07/12, 09:45. Actualmente el orden de estos separadores no se verifica, por lo que también se coincidirán formatos ilógicos como 1965/07/12, : ,09:45. DATE FORMATS

This section describes the formats used to specify dates and times. There are three distinct types:

  • The standard format used by many date and time utilities.
  • The relative time format used for calculations.
  • The format used within calendar files.

Note that in all cases, day names and month names are recognised in English only, and are case-insensitive.

Standard Format

This is the format most commonly used in the C library's strptime(3) function, and is the default format if no other is specified. The following are examples:

2006-08-18 17:00:48
18 Aug 06 17:00
Fri, 18 Aug 2006 5:00PM

When used in contexts where only a date is expected, the time part may be omitted, in which case it is assumed to be midnight at the start of the date. When used in contexts where only a time is expected, the date part may be omitted, in which case it is assumed to be today.

The time zone is generally ignored, but if it is specified and the time is not otherwise specified, the time is assumed to be local.

Note that the time is embedded in the date.

Relative Time Format

Days of the week are not normally scanned, but will be ignored if they occur at the start of the date pattern only. However, in contexts where it is useful to specify dates relative to today, days of the week with no other date specification may be given. The day is assumed to be either today or within the past week. Likewise, the words yesterday, today and tomorrow are handled. All matches are case-insensitive. Hence if today is Monday, then Sunday is equivalent to yesterday, Monday is equivalent to today, but Tuesday gives a date six days ago. This is not generally useful within the calendar file. Dates in this format may be combined with a time specification; for example Tomorrow, 8 p.m..

For example, the standard date format:

Fri Aug 18 17:00:48 BST 2006

is handled by matching HH:MM:SS and removing it together with the matched (but unused) time zone. This leaves the following:

Fri Aug 18 2006

Fri is ignored and the rest is matched according to the standard rules.

Relative Time Format

In certain places relative times are handled. Here, a date is not allowed; instead a combination of various supported periods are allowed, together with an optional time. The periods must be in order from most to least significant.

In some cases, a more accurate calculation is possible when there is an anchor date: offsets of months or years pick the correct day, rather than being rounded, and it is possible to pick a particular day in a month as `(1st Friday)', etc., as described in more detail below.

Anchors are available in the following cases. If one or two times are passed to the function calendar, the start time acts an anchor for the end time when the end time is relative (even if the start time is implicit). When examining calendar files, the scheduled event being examined anchors the warning time when it is given explicitly by means of the WARN keyword; likewise, the scheduled event anchors a repetition period when given by the RPT keyword, so that specifications such as RPT 2 months, 3rd Thursday are handled properly. Finally, the -R argument to calendar_scandate directly provides an anchor for relative calculations.

The periods handled, with possible abbreviations are:

Years
years, yrs, ys, year, yr, y, yearly. A year is 365.25 days unless there is an anchor.
Months
months, mons, mnths, mths, month, mon, mnth, mth, monthly. Note that m, ms, mn, mns are ambiguous and are not handled. A month is a period of 30 days rather than a calendar month unless there is an anchor.
Weeks
weeks, wks, ws, week, wk, w, weekly
Days
days, dys, ds, day, dy, d, daily
Hours
hours, hrs, hs, hour, hr, h, hourly
Minutes
minutes, mins, minute, min, but not m, ms, mn or mns
Seconds
seconds, secs, ss, second, sec, s

Spaces between the numbers are optional, but are required between items, although a comma may be used (with or without spaces).

The forms yearly to hourly allow the number to be omitted; it is assumed to be 1. For example, 1 d and daily are equivalent. Note that using those forms with plurals is confusing; 2 yearly is the same as 2 years, not twice yearly, so it is recommended they only be used without numbers.

When an anchor time is present, there is an extension to handle regular events in the form of the nth someday of the month. Such a specification must occur immediately after any year and month specification, but before any time of day, and must be in the form n(th|st|rd) day, for example 1st Tuesday or 3rd Monday. As in other places, days are matched case insensitively, must be in English, and only the first three letters are significant except that a form beginning `month' does not match `Monday'. No attempt is made to sanitize the resulting date; attempts to squeeze too many occurrences into a month will push the day into the next month (but in the obvious fashion, retaining the correct day of the week).

Here are some examples:

30 years 3 months 4 days 3:42:41
14 days 5 hours
Monthly, 3rd Thursday
4d,10hr

Example

Here is an example calendar file. It uses a consistent date format, as recommended above.

Feb 1, 2006 14:30 Pointless bureaucratic meeting
Mar 27, 2006 11:00 Mutual recrimination and finger pointing
  Bring water pistol and waterproofs
Mar 31, 2006 14:00 Very serious managerial pontification
  # UID 12C7878A9A50
Apr 10, 2006 13:30 Even more pointless blame assignment exercise WARN 30 mins
May 18, 2006 16:00 Regular moaning session RPT monthly, 3rd Thursday

The second entry has a continuation line. The third entry has a continuation line that will not be shown when the entry is displayed, but the unique identifier will be used by the calendar_add function when updating the event. The fourth entry will produce a warning 30 minutes before the event (to allow you to equip yourself appropriately). The fifth entry repeats after a month on the 3rd Thursday, i.e. June 15, 2006, at the same time.

USER FUNCTIONS

This section describes functions that are designed to be called directly by the user. The first part describes those functions associated with the user's calendar; the second part describes the use in glob qualifiers.

Calendar system functions

calendar [ -abdDsv ] [ -C calfile ] [ -n num ] [ -S showprog ]
[ [ start ] end ]
calendar -r [ -abdDrsv ] [ -C calfile ] [ -n num ] [ -S showprog ]
[ start ]
Show events in the calendar.

With no arguments, show events from the start of today until the end of the next working day after today. In other words, if today is Friday, Saturday, or Sunday, show up to the end of the following Monday, otherwise show today and tomorrow.

If end is given, show events from the start of today up to the time and date given, which is in the format described in the previous section. Note that if this is a date the time is assumed to be midnight at the start of the date, so that effectively this shows all events before the given date.

end may start with a +, in which case the remainder of the specification is a relative time format as described in the previous section indicating the range of time from the start time that is to be included.

If start is also given, show events starting from that time and date. The word now can be used to indicate the current time.

To implement an alert when events are due, include calendar -s in your ~/.zshrc file.

Options:

-a
Show all items in the calendar, regardless of the start and end.
-b
Brief: don't display continuation lines (i.e. indented lines following the line with the date/time), just the first line.
-B lines
Brief: display at most the first lines lines of the calendar entry. `-B 1' is equivalent to `-b'.
-C calfile
Explicitly specify a calendar file instead of the value of the calendar-file style or the default ~/calendar.
-d
Move any events that have passed from the calendar file to the "done" file, as given by the done-file style or the default which is the calendar file with .done appended. This option is implied by the -s option.
-D
Turns off the option -d, even if the -s option is also present.
-n num, -num
Show at least num events, if present in the calendar file, regardless of the start and end.
-r
Show all the remaining options in the calendar, ignoring the given end time. The start time is respected; any argument given is treated as a start time.
-s
Use the shell's sched command to schedule a timed event that will warn the user when an event is due. Note that the sched command only runs if the shell is at an interactive prompt; a foreground task blocks the scheduled task from running until it is finished.

The timed event usually runs the programme calendar_show to show the event, as described in the section UTILITY FUNCTIONS below.

By default, a warning of the event is shown five minutes before it is due. The warning period can be configured by the style warn-time or for a single calendar entry by including WARN reltime in the first line of the entry, where reltime is one of the usual relative time formats.

A repeated event may be indicated by including RPT reldate in the first line of the entry. After the scheduled event

ha sido mostrado, se volverá a ingresar en el archivo del calendario en un momento reldate después del evento existente. Tenga en cuenta que este es actualmente el único uso que se le da al contador de repeticiones, por lo que no es posible consultar el horario para una recurrencia de un evento en el calendario hasta que el evento anterior haya pasado.

Si se usa RPT, también es posible especificar que ciertas recurrencias de un evento se reprogramen o cancelen. Esto se hace con la palabra clave OCCURRENCE, seguida de espacios en blanco y la fecha y hora de la ocurrencia en la secuencia regular, seguida de espacios en blanco y la fecha y hora del evento reprogramado o la cadena exacta CANCELLED. En este caso, la fecha y hora deben estar exactamente en el formato de "fecha con hora local" utilizado por el tipo MIME text/calendar (RFC 2445), <YYYY><MM><DD>T<hh><mm><ss> (tenga en cuenta la presencia del carácter literal T). La primera palabra (la recurrencia regular) puede ser algo diferente de una fecha/hora correcta para indicar que el evento es adicional a la secuencia normal; una convención que conserva la apariencia de formato es XXXXXXXXTXXXXXX.

Además, es útil registrar la próxima recurrencia regular (ya que la fecha mostrada puede ser para un evento reprogramado, por lo que no se puede usar para calcular la secuencia regular). Esto se especifica mediante RECURRENCE y una hora o fecha en el mismo formato. calendar_add agrega tal indicación cuando encuentra un evento recurrente que no incluye una, basándose en la fecha/hora del titular.

Si se utiliza calendar_add para actualizar ocurrencias, la palabra clave UID descrita allí debe estar presente tanto en la entrada existente como en la ocurrencia agregada para identificar las secuencias de eventos recurrentes.

Por ejemplo,

jueves 6 de mayo de 2010 11:00 Charla informal RPT 1 semana
  # RECURRENCE 20100506T110000
  # OCCURRENCE 20100513T110000 20100513T120000
  # OCCURRENCE 20100520T110000 CANCELLED

El evento que ocurre a las 11:00 del 13 de mayo de 2010 se reprograma una hora más tarde. El evento que ocurre una semana después se cancela. Las ocurrencias se dan en una línea de continuación que comienza con un carácter #, por lo que normalmente no se mostrarán como parte del evento. Como en otros lugares, no se tiene en cuenta la zona horaria con las horas. Después de que ocurra el siguiente evento, la fecha/hora del titular será `jueves 13 de mayo de 2010 12:00' mientras que la fecha/hora de RECURRENCE será `20100513T110000' (tenga en cuenta que los eventos cancelados y movidos no se tienen en cuenta en RECURRENCE, que registra cuál es la próxima recurrencia regular, pero se tienen en cuenta en la fecha/hora del titular).

Es seguro ejecutar calendar -s para reprogramar un evento existente (si el archivo del calendario ha cambiado, por ejemplo), y también para tenerlo ejecutándose en múltiples instancias del shell, ya que el archivo del calendario está bloqueado cuando está en uso.

Por defecto, los eventos expirados se mueven al archivo "hecho"; consulte la opción -d. Use -D para evitar esto.

-S showprog
Especifica explícitamente un programa para ser utilizado para mostrar eventos en lugar del valor del estilo show-prog o el valor predeterminado calendar_show.
-v
Verboso: muestra más información sobre las etapas de procesamiento. Esto es útil para confirmar que la función ha analizado correctamente las fechas en el archivo del calendario.
calendar_add [ -BL ] evento ...
Agrega un evento único al calendario en la ubicación apropiada. El evento puede contener múltiples líneas, como se describe en la sección `Formato del archivo de calendario' anterior. Usar esta función asegura que el archivo del calendario se ordene por fecha y hora. También toma arreglos especiales para bloquear el archivo mientras se modifica. El calendario antiguo se deja en un archivo con el sufijo .old.

La opción -B indica que la copia de seguridad del archivo del calendario será manejada por el llamador y no debe ser realizada por calendar_add. La opción -L indica que calendar_add no necesita bloquear el archivo del calendario, ya que ya está bloqueado. Estas opciones normalmente no serán necesarias para los usuarios.

Si el estilo reformat-date es verdadero, la fecha y hora de la nueva entrada se reescribirán en el formato de fecha estándar: consulte las descripciones de este estilo y el estilo date-format.

La función puede usar un identificador único almacenado con cada evento para asegurar que las actualizaciones de eventos existentes se traten correctamente. La entrada debe contener la palabra UID, seguida de espacios en blanco, seguida de una palabra que consista completamente en dígitos hexadecimales de longitud arbitraria (todos los dígitos son significativos, incluidos los ceros iniciales). Como la UID no es directamente útil para el usuario, es conveniente ocultarla en una línea de continuación indentada que comience con un #, por ejemplo:

31 de agosto de 2007 09:30  Celebrar el fin de las vacaciones
  # UID 045B78A0

La segunda línea no será mostrada por la función calendar.

Es posible especificar la palabra clave RPT seguida de CANCELLED en lugar de un tiempo relativo. Esto provoca que cualquier evento o serie de eventos que coincida sea cancelado (el evento original no tiene que estar marcado como recurrente para ser cancelado por este método). Se requiere una UID para hacer coincidir un evento existente en el calendario.

calendar_add intentará gestionar las recurrencias y ocurrencias de eventos que se repiten según lo descrito para la programación de eventos por calendar -s arriba. Para reprogramar o cancelar un solo evento, calendar_add debe ser llamado con una entrada que incluya la UID correcta, pero que *no* incluya la palabra clave RPT, ya que esto se toma como que la entrada se aplica a una serie de eventos que se repiten y, por lo tanto, reemplaza toda la información existente. Cada ocurrencia reprogramada o cancelada debe tener una palabra clave OCCURRENCE en la entrada pasada a calendar_add, que se fusionará en el archivo del calendario. Cualquier referencia existente a la ocurrencia se reemplaza. Una ocurrencia que no se refiere a un evento existente válido se agrega como una ocurrencia única a la misma entrada del calendario.

calendar_edit
Esto llama al editor del usuario para editar el archivo del calendario. Si hay argumentos, se toman como el editor a usar (el nombre del archivo se agrega a los comandos); de lo contrario, el editor se da mediante la variable VISUAL, si está establecida, o la variable EDITOR.

Si el programador del calendario estaba en ejecución, entonces después de editar el archivo, se llama a calendar -s para actualizarlo.

Esta función bloquea el sistema de calendario durante la edición. Por lo tanto, debe usarse para editar el archivo del calendario si existe la posibilidad de que ocurra un evento del calendario mientras tanto. Tenga en cuenta que esto puede hacer que otro shell con funciones de calendario habilitadas se cuelgue esperando un bloqueo, por lo que es necesario salir del editor lo antes posible.

calendar_parse entrada-calendario
Esta es la función interna que analiza las partes de una entrada de calendario, que se pasa como único argumento. La función devuelve el estado 1 si el argumento no pudo ser analizado como una entrada de calendario y el estado 2 si se pasó un número incorrecto de argumentos; también establece el parámetro reply a un array asociativo vacío. De lo contrario, devuelve el estado 0 y establece los elementos del array asociativo reply de la siguiente manera:
time
La hora como una cadena de dígitos en las mismas unidades que $EPOCHSECONDS
schedtime
La hora programada regularmente. Esto puede diferir de la hora real del evento time si se trata de un evento recurrente y la próxima ocurrencia ha sido reprogramada. Entonces time indica la hora real y schedtime la hora de la recurrencia regular antes de la modificación.
text1
El texto de la línea sin incluir la fecha y hora del evento, pero incluyendo cualquier palabra clave y valor WARN o RPT.
warntime
Cualquier hora de advertencia dada por la palabra clave WARN como una cadena de dígitos que contiene la hora a la que advertir en las mismas unidades que $EPOCHSECONDS. (Tenga en cuenta que esta es una hora absoluta, no la hora relativa pasada.) No se establece si no se encontraron palabras clave y valores WARN.
warnstr
La cadena cruda que coincide después de la palabra clave WARN, de lo contrario se desestablece.
rpttime
Cualquier hora de recurrencia dada por la palabra clave RPT como una cadena de dígitos que contiene la hora de la recurrencia en las mismas unidades que $EPOCHSECONDS. (Tenga en cuenta que esta es una hora absoluta.) No se establece si no se encontraron palabras clave y valores RPT.
schedrpttime
La próxima ocurrencia programada regularmente de un evento recurrente antes de la modificación. Esto puede diferir de rpttime, que es la hora real del evento que puede haber sido reprogramado de la hora regular.
rptstr
La cadena cruda que coincide después de la palabra clave RPT, de lo contrario se desestablece.
text2
El texto de la línea después de la eliminación de la fecha y cualquier palabra clave y valor.
calendar_showdate [ -r ] [ -f fmt ] espec-fecha ...
La espec-fecha dada se interpreta y se imprime la fecha y hora correspondientes. Si la espec-fecha inicial comienza con un + o - se trata como relativa a la hora actual; las espec-fechas después de la primera se tratan como relativas a la fecha calculada hasta el momento y un + inicial es opcional en ese caso. Esto permite usar el sistema como una calculadora de fechas. Por ejemplo, calendar_showdate '+1 mes, primer viernes' muestra la fecha del primer viernes del próximo mes.

Con la opción -r no se imprime nada, pero el valor de la fecha y hora en segundos desde la época se almacena en el parámetro REPLY.

Con la opción -f fmt la fecha/hora dada

El formato de conversión se pasa a strftime; consulte las notas sobre el estilo date-format a continuación.

Para evitar ambigüedades con especificaciones de fecha relativas negativas, las opciones deben aparecer como palabras separadas; en otras palabras, -r y -f no deben combinarse en la misma palabra.

calendar_sort
Ordena el archivo del calendario por fecha y hora. El calendario antiguo se deja en un archivo con el sufijo .old.

Calificadores Glob

age
La función age puede cargarse automáticamente y usarse por separado del sistema de calendario, aunque utiliza la función calendar_scandate para el formato de fecha. Requiere la utilidad incorporada zsh/stat, pero solo utiliza la utilidad incorporada zstat.

age selecciona archivos que tienen una fecha de modificación dada para usar como calificador de glob. El formato de la fecha es el mismo que el entendido por el sistema de calendario, descrito en la sección FORMATOS DE ARCHIVOS Y FECHAS anterior.

La función puede tomar uno o dos argumentos, que pueden proporcionarse directamente como comando o argumentos, o por separado como parámetros del shell.

print *(e:age 2006/10/04 2006/10/09:)

El ejemplo anterior coincide con todos los archivos modificados entre el inicio de esas fechas. El segundo argumento alternativamente puede ser un tiempo relativo introducido por un +:

print *(e:age 2006/10/04 +5d:)

El ejemplo anterior es equivalente al ejemplo anterior.

Además del uso especial de los días de la semana, today y yesterday, se pueden especificar tiempos sin fecha; estos se aplican a hoy. Obviamente, tales usos se vuelven problemáticos alrededor de la medianoche.

print *(e-age 12:00 13:30-)

El ejemplo anterior muestra archivos modificados entre las 12:00 y las 13:00 de hoy.

print *(e:age 2006/10/04:)

El ejemplo anterior coincide con todos los archivos modificados en esa fecha. Si se omite el segundo argumento, se toma como exactamente 24 horas después del primer argumento (incluso si el primer argumento contiene una hora).

print *(e-age 2006/10/04:10:15 2006/10/04:10:45-)

El ejemplo anterior proporciona horas. Tenga en cuenta que los espacios en blanco dentro de la especificación de hora y fecha deben entrecomillarse para garantizar que age reciba los argumentos correctos, de ahí el uso de dos puntos adicionales para separar la fecha y la hora.

AGEREF=2006/10/04:10:15
AGEREF2=2006/10/04:10:45
print *(+age)

Esto muestra el mismo ejemplo anterior utilizando otra forma de pasar argumentos. Las fechas y horas en los parámetros AGEREF y AGEREF2 permanecen en vigor hasta que se desestablecen, pero se anularán si se pasa algún argumento como argumento explícito a age. Cualquier argumento explícito hace que ambos parámetros se ignoren.

En lugar de una fecha y hora explícitas, es posible utilizar la fecha de modificación de un archivo como fecha y hora para cualquiera de los argumentos introduciendo el nombre del archivo con dos puntos:

print *(e-age :file1-)

coincide con todos los archivos creados el mismo día (24 horas a partir de la medianoche) que file1.

print *(e-age :file1 :file2-)

coincide con todos los archivos modificados no antes de file1 y no después de file2; la precisión aquí es hasta el segundo más cercano.

after
before
Las funciones after y before son versiones más simples de age que toman solo un argumento. El argumento se analiza de forma similar a un argumento de age; si no se proporciona, se consulta la variable AGEREF. Como sugieren los nombres de las funciones, un archivo coincide si su fecha de modificación es posterior o anterior a la hora y fecha especificadas. Si solo se proporciona una hora, la fecha es hoy.

Los dos ejemplos siguientes son, por lo tanto, equivalentes:

print *(e-after 12:00-)
print *(e-after today:12:00-)

ESTILOS

El mecanismo de estilo de zsh que utiliza el comando zstyle se describe en zshmodules(1). Este es el mismo mecanismo utilizado en el sistema de completado.

Los estilos siguientes se examinan en el contexto :datetime:función:, por ejemplo :datetime:calendar:.

calendar-file
La ubicación del calendario principal. El valor predeterminado es ~/calendar.
date-format
Una cadena de formato strftime (consulte strftime(3)) con las extensiones de zsh que proporcionan varios números sin cero inicial o espacio si el número es de un solo dígito, como se describe para el formato de indicación %D{cadena} en la sección EXPANSIÓN DE SECUENCIAS DE INDICACIÓN en zshmisc(1).

Esto se utiliza para mostrar fechas en calendar, tanto para admitir la opción -v como al agregar eventos recurrentes de nuevo al archivo del calendario, y en calendar_showdate como formato de salida final.

Si el estilo no está establecido, el valor predeterminado utilizado es similar al formato estándar del sistema tal como lo produce el comando date (también conocido como formato `ctime'): `%a %b %d %H:%M:%S %Z %Y'.

done-file
La ubicación del archivo al que se agregan los eventos que han pasado. El valor predeterminado es la ubicación del archivo del calendario con el sufijo .done. El estilo puede establecerse como una cadena vacía en cuyo caso no se mantendrá un archivo de "hecho".
reformat-date
Booleano, utilizado por calendar_add. Si es verdadero, la fecha y hora de las nuevas entradas agregadas al calendario se reformatearán al formato dado por el estilo date-format o su valor predeterminado. Solo se reformatean la fecha y hora del evento en sí; cualquier fecha y hora subsidiaria, como las asociadas con los tiempos de repetición y advertencia, se dejan sin cambios.
show-prog
El programa ejecutado por calendar para mostrar eventos. Se le pasarán la hora de inicio y la hora de fin de los eventos solicitados en segundos desde la época seguida del texto del evento. Tenga en cuenta que calendar -s utiliza una hora de inicio y una hora de fin iguales para indicar alertas para eventos específicos.

El valor predeterminado es la función calendar_show.

warn-time
La hora antes de un evento en la que se mostrará una advertencia, si la primera línea del evento no incluye el texto EVENT reltime. El valor predeterminado es 5 minutos.

FUNCIONES UTILITARIAS

calendar_lockfiles
Intenta bloquear los archivos dados en el argumento. Para prevenir problemas con el bloqueo de archivos en red, esto se hace de forma ad hoc intentando crear un enlace simbólico al archivo con el nombre archivo.lockfile. No se utilizan otras funciones a nivel de sistema para el bloqueo, es decir, el archivo puede ser accedido y modificado por cualquier utilidad que no utilice este mecanismo. En particular, el usuario no tiene impedimento para editar el archivo del calendario al mismo tiempo a menos que se utilice calendar_edit.

Se realizan tres intentos de bloquear el archivo antes de desistir. Si el módulo zsh/zselect está disponible, los tiempos de los intentos se alteran para que múltiples instancias de la función que llama tengan pocas probabilidades de reintentar al mismo tiempo.

Los archivos bloqueados se agregan al array lockfiles, que debe ser local al llamador.

Si todos los archivos se bloquearon con éxito, se devuelve el estado cero, de lo contrario, el estado uno.

Esta función puede utilizarse como una función general de bloqueo de archivos, aunque esto solo funcionará si solo se utiliza este mecanismo para bloquear archivos.

calendar_read
Este es un backend utilizado por varias otras funciones para analizar el archivo del calendario, que se pasa como único argumento. El array calendar_entries se establece con la lista de eventos del archivo; no se realiza ninguna poda excepto que se eliminan los ampersands del principio de la línea. Cada entrada puede contener varias líneas.
calendar_scandate
Esta es una función genérica para analizar fechas y horas que puede usarse por separado del sistema de calendario. El argumento es una especificación de fecha u hora como se describe en la sección FORMATOS DE ARCHIVOS Y FECHAS anterior. El parámetro REPLY se establece con el número de segundos desde la época correspondiente a esa fecha u hora. Por defecto, la fecha y hora pueden aparecer en cualquier lugar dentro del argumento dado.

Devuelve el estado cero si la fecha y hora se analizaron correctamente, de lo contrario, devuelve uno.

Opciones:

-a
La fecha y hora están ancladas al principio del argumento; no coincidirán si hay texto precedente.
-A
La fecha y hora están ancladas tanto al principio como al final del argumento; no coincidirán si hay algún otro texto en el argumento.
-d
Habilita la salida de depuración adicional.
-m
Menos. Cuando también se da -R anchor_time, el tiempo relativo se calcula hacia atrás desde anchor_time.
-r
El argumento pasado se analizará como un tiempo relativo.
-R anchor_time
El argumento pasado se analizará como un tiempo relativo. El tiempo es relativo a anchor_time, un tiempo en segundos desde la época, y el valor devuelto es el tiempo absoluto correspondiente a avanzar anchor_time por el tiempo relativo dado. Esto permite que las duraciones de los meses se tengan en cuenta correctamente. Si el día final no existe en el mes dado, se da el último día del mes final. Por ejemplo,

NAME

zshcalsys - Zsh calendar system

DESCRIPTION

This utility provides a basic calendar and scheduling facility. It is implemented as a set of zsh functions and is loaded using the command %Z. The basic functionality is available by default, and additional functionality can be loaded using the following arguments to %Z:

-c
Load the command line completion support for the calendar system.

-e
Load the editor support for the calendar system. This allows you to edit the calendar file using your preferred editor (specified by the VISUAL or EDITOR environment variables).

-h
Load the history support for the calendar system. This allows you to access past calendar events.

-s
Load the scheduled events support for the calendar system. This allows you to schedule events and receive reminders.

-t
Load the time tracking support for the calendar system. This allows you to track time spent on different tasks.

FILE AND DATE FORMATS

The calendar data is stored in a file named ~/.calendar. The format of this file is a series of lines, each representing an event. Each line has the following format:

timestamp description

The timestamp is the number of seconds since the epoch. The description is a string describing the event.

The calendar system also supports relative date and time specifications. These are parsed by the zsh/datetime module. Some examples include:

date
If the anchor time is during 31st January 2007 and the relative time is 1 month, the final time is the same time of day during 28th February 2007.
-s
In addition to setting REPLY, set REPLY2 to the remainder of the argument after the date and time have been stripped. This is empty if the option -A was given.
-t
Allow a time with no date specification. The date is assumed to be today. The behaviour is unspecified if the iron tongue of midnight is tolling twelve.

USER FUNCTIONS

The following functions are available to the user:

calendar_add
Add an event to the calendar.
calendar_list
List events in the calendar.
calendar_show
Show a specific event in the calendar.
calendar_edit
Edit the calendar file.
calendar_delete
Delete an event from the calendar.
calendar_lockfiles
Manage lock files for the calendar system.

The calendar_show function is used by default to display events. It accepts a start time and end time for events, both in epoch seconds, and an event description.

The event is always printed to standard output. If the command line editor is active (which will usually be the case) the command line will be redisplayed after the output.

If the parameter DISPLAY is set and the start and end times are the same (indicating a scheduled event), the function uses the command xmessage to display a window with the event details.

STYLES

The calendar system supports the following styles:

calendar:display_func
The function used by default to display events. It accepts a start time and end time for events, both in epoch seconds, and an event description.
calendar:editor
The editor command used to edit the calendar file.
calendar:default_editor
The default editor command used if calendar:editor is not set.

UTILITY FUNCTIONS

The following utility functions are used internally by the calendar system:

calendar_parse_date
Parses a date and time string and returns the epoch seconds.
calendar_format_date
Formats epoch seconds into a human-readable date and time string.
calendar_read_events
Reads events from the calendar file.
calendar_write_events
Writes events to the calendar file.

BUGS

As the system is based entirely on shell functions (with a little support from the zsh/datetime module) the mechanisms used are not as robust as those provided by a dedicated calendar utility. Consequently the user should not rely on the shell for vital alerts.

There is no calendar_delete function.

There is no localization support for dates and times, nor any support for the use of time zones.

Relative periods of months and years do not take into account the variable number of days.

The calendar_show function is currently hardwired to use xmessage for displaying alerts on X Window System displays. This should be configurable and ideally integrate better with the desktop.

calendar_lockfiles hangs the shell while waiting for a lock on a file. If called from a scheduled task, it should instead reschedule the event that caused it.
