ZSHCOMPSYS(1) Manual de Comandos Generales ZSHCOMPSYS(1)

NOMBRE

zshcompsys - sistema de completado de zsh

DESCRIPCIÓN

Esto describe el código de shell para el sistema de completado `nuevo', denominado compsys. Está escrito en funciones de shell basadas en las características descritas en zshcompwid(1).

Las características son contextuales, sensibles al punto en el que se inicia el completado. Ya se proporcionan muchos completados. Por esta razón, un usuario puede realizar una gran cantidad de tareas sin conocer ningún detalle más allá de cómo inicializar el sistema, lo cual se describe a continuación en INICIALIZACIÓN.

El contexto que decide qué completado se va a realizar puede ser

•
una posición de argumento u opción: estos describen la posición en la línea de comandos en la que se solicita el completado. Por ejemplo, `primer argumento de rmdir, la palabra que se está completando nombra un directorio';
•
un contexto especial, que denota un elemento en la sintaxis del shell. Por ejemplo, `una palabra en posición de comando' o `un subíndice de matriz'.

Una especificación de contexto completa contiene otros elementos, como describiremos.

Además de los nombres de comandos y contextos, el sistema emplea dos conceptos más: estilos y etiquetas. Estos proporcionan formas para que el usuario configure el comportamiento del sistema.

Las etiquetas juegan un doble papel. Sirven como un sistema de clasificación para las coincidencias, indicando típicamente una clase de objeto que el usuario puede necesitar distinguir. Por ejemplo, al completar argumentos del comando ls, el usuario puede preferir probar archivos antes que directorios, por lo que ambos son etiquetas. También aparecen como el elemento más a la derecha en una especificación de contexto.

Los estilos modifican varias operaciones del sistema de completado, como el formato de salida, pero también qué tipos de completadores se utilizan (y en qué orden), o qué etiquetas se examinan. Los estilos pueden aceptar argumentos y se manipulan utilizando el comando zstyle descrito en zshmodules(1).

En resumen, las etiquetas describen qué son los objetos de completado, y el estilo cómo deben completarse. En varios puntos de la ejecución, el sistema de completado comprueba qué estilos y/o etiquetas están definidos para el contexto actual, y utiliza eso para modificar su comportamiento. La descripción completa del manejo de contextos, que determina cómo las etiquetas y otros elementos del contexto influyen en el comportamiento de los estilos, se describe a continuación en CONFIGURACIÓN DEL SISTEMA DE COMPLETADO.

Cuando se solicita un completado, se llama a una función de despacho; consulte la descripción de _main_complete en la lista de funciones de control a continuación. Este despachador decide qué función debe llamarse para producir los completados y la llama. El resultado se pasa a uno o más completadores, funciones que implementan estrategias de completado individuales: completado simple, corrección de errores, completado con corrección de errores, selección de menú, etc.

Más generalmente, las funciones de shell contenidas en el sistema de completado son de dos tipos:

•
aquellas que comienzan con `comp' deben llamarse directamente; hay pocas de estas;
•
aquellas que comienzan con `_' son llamadas por el código de completado. Las funciones de shell de este conjunto, que implementan el comportamiento de completado y pueden estar enlazadas a pulsaciones de teclas, se denominan `widgets'. Estos proliferan a medida que se requieren nuevos completados.

INICIALIZACIÓN

Si el sistema se instaló completamente, debería ser suficiente llamar a la función de shell compinit desde su archivo de inicialización; consulte la siguiente sección. Sin embargo, la función compinstall puede ser ejecutada por un usuario para configurar varios aspectos del sistema de completado.

Normalmente, compinstall insertará código en .zshrc, aunque si este no es escribible, lo guardará en otro archivo y le dirá la ubicación de ese archivo. Tenga en cuenta que depende de usted asegurarse de que las líneas añadidas a .zshrc se ejecuten realmente; puede, por ejemplo, necesitar moverlas a una posición anterior en el archivo si .zshrc generalmente retorna temprano. Mientras las mantenga todas juntas (incluidas las líneas de comentarios al principio y al final), puede volver a ejecutar compinstall y localizará y modificará correctamente estas líneas. Tenga en cuenta, sin embargo, que cualquier código que agregue a esta sección manualmente es probable que se pierda si vuelve a ejecutar compinstall, aunque las líneas que usan el comando `zstyle' deberían manejarse sin problemas.

El nuevo código entrará en vigor la próxima vez que inicie el shell, o ejecute .zshrc manualmente; también hay una opción para que surtan efecto inmediatamente. Sin embargo, si compinstall ha eliminado definiciones, necesitará reiniciar el shell para ver los cambios.

Para ejecutar compinstall deberá asegurarse de que se encuentra en un directorio mencionado en su parámetro fpath, lo cual debería ser ya el caso si zsh se configuró correctamente, siempre que sus archivos de inicio no eliminen los directorios apropiados de fpath. Luego debe ser cargado automáticamente (`autoload -U compinstall' es recomendado). Puede abortar la instalación en cualquier momento en que se le solicite información, y su .zshrc no se alterará en absoluto; los cambios solo tienen lugar al final, donde se le pide específicamente confirmación.

Uso de compinit

Esta sección describe el uso de compinit para inicializar el completado para la sesión actual cuando se llama directamente; si ha ejecutado compinstall, se llamará automáticamente desde su .zshrc.

Para inicializar el sistema, la función compinit debe estar en un directorio mencionado en el parámetro fpath, y debe ser cargada automáticamente (`autoload -U compinit' es recomendado), y luego ejecutada simplemente como `compinit'. Esto definirá algunas funciones de utilidad, organizará que todas las funciones de shell necesarias se carguen automáticamente y luego redefinirá todos los widgets que realizan completado para usar el nuevo sistema. Si usa el widget menu-select, que es parte del módulo zsh/complist, debe asegurarse de que ese módulo se cargue antes de la llamada a compinit para que ese widget también se redefina. Si los estilos de completado (ver más abajo) están configurados para realizar expansión además de completado por defecto, y la tecla TAB está enlazada a expand-or-complete, compinit la reenlazará a complete-word; esto es necesario para usar la forma correcta de expansión.

Si necesita usar los comandos de completado originales, aún puede enlazar teclas a los widgets antiguos poniendo un `.' delante del nombre del widget, por ejemplo `.expand-or-complete'.

Para acelerar la ejecución de compinit, se le puede hacer producir una configuración volcada que se leerá en invocaciones futuras; esto es lo predeterminado, pero se puede desactivar llamando a compinit con la opción -D. El archivo volcado es .zcompdump en el mismo directorio que los archivos de inicio (es decir, $ZDOTDIR o $HOME); alternativamente, se puede dar un nombre de archivo explícito con `compinit -d nombrearchivo'. La siguiente invocación de compinit leerá el archivo volcado en lugar de realizar una inicialización completa.

Si el número de archivos de completado cambia, compinit lo reconocerá y producirá un nuevo archivo volcado. Sin embargo, si el nombre de una función o los argumentos en la primera línea de una función #compdef (como se describe a continuación) cambian, es más fácil eliminar el archivo volcado manualmente para que compinit lo recree la próxima vez que se ejecute. La comprobación realizada para ver si hay nuevas funciones se puede omitir dando la opción -C. En este caso, el archivo volcado solo se creará si no existe uno ya.

El volcado es realizado en realidad por otra función, compdump, pero solo necesitará ejecutarla usted mismo si cambia la configuración (por ejemplo, usando compdef) y luego desea volcar la nueva. El nombre del archivo antiguo volcado se recordará para este propósito.

Si el parámetro _compdir está establecido, compinit lo utiliza como un directorio donde se pueden encontrar funciones de completado; esto solo es necesario si no están ya en la ruta de búsqueda de funciones.

Por razones de seguridad, compinit también comprueba si el sistema de completado utilizará archivos que no son propiedad de root o del usuario actual, o archivos en directorios que son escribibles por todos o por grupo, o que no son propiedad de root o del usuario actual. Si se encuentran dichos archivos o directorios, compinit preguntará si el sistema de completado debe usarse realmente. Para evitar estas pruebas y hacer que todos los archivos encontrados se utilicen sin preguntar, use la opción -u

, y para hacer que compinit ignore silenciosamente todos los archivos y directorios inseguros, usa la opción -i. Esta verificación de seguridad se omite por completo cuando se proporciona la opción -C, siempre que exista el volcado. La verificación de seguridad se puede reintentar en cualquier momento ejecutando la función compaudit. Esta es la misma verificación que utiliza compinit, pero cuando se ejecuta directamente, los cambios en fpath se realizan localmente para la función, de modo que no persistan. Los directorios que se verificarán se pueden pasar como argumentos; si no se proporcionan, compaudit utiliza fpath y _compdir para encontrar directorios del sistema de completado, agregando los que faltan a fpath según sea necesario. Para forzar una verificación de exactamente los directorios actualmente nombrados en fpath, establezca _compdir a una cadena vacía antes de llamar a compaudit o compinit. La función bashcompinit proporciona compatibilidad con el sistema de completado programable de bash. Cuando se ejecuta, definirá las funciones compgen y complete, que corresponden a los comandos incorporados de bash con los mismos nombres. Luego será posible utilizar especificaciones de completado y funciones escritas para bash.

Archivos cargados automáticamente

La convención para las funciones cargadas automáticamente utilizadas en el completado es que comienzan con un guión bajo; como ya se mencionó, el parámetro fpath/FPATH debe contener el directorio en el que están almacenados. Si zsh se instaló correctamente en su sistema, entonces fpath/FPATH contiene automáticamente los directorios requeridos para las funciones estándar. Para instalaciones incompletas, si compinit no encuentra suficientes archivos que comiencen con un guión bajo (menos de veinte) en la ruta de búsqueda, intentará encontrar más agregando el directorio _compdir a la ruta de búsqueda. Si ese directorio tiene un subdirectorio llamado Base, se agregarán todos los subdirectorios a la ruta. Además, si el subdirectorio Base tiene un subdirectorio llamado Core, compinit agregará todos los subdirectorios de los subdirectorios a la ruta: esto permite que las funciones tengan el mismo formato que en la distribución fuente de zsh. Cuando se ejecuta compinit, busca en todos los archivos accesibles a través de fpath/FPATH y lee la primera línea de cada uno de ellos. Esta línea debe contener una de las etiquetas descritas a continuación. Los archivos cuya primera línea no comience con una de estas etiquetas no se consideran parte del sistema de completado y no se tratarán de forma especial. Las etiquetas son:
#compdef nombre ... [ -{p|P} patrón ... [ -N nombre ... ]]
El archivo se hará cargable automáticamente y la función definida en él se llamará al completar nombres, cada uno de los cuales es el nombre de un comando cuyos argumentos se completarán o uno de varios contextos especiales con el formato -contexto- descrito a continuación.

Cada nombre también puede tener el formato `cmd=servicio'. Al completar el comando cmd, la función se comporta típicamente como si se estuviera completando el comando (o contexto especial) servicio en su lugar. Esto proporciona una forma de alterar el comportamiento de las funciones que pueden realizar muchas completaciones diferentes. Se implementa estableciendo el parámetro $service al llamar a la función; la función puede optar por interpretarlo como desee, y las funciones más simples probablemente lo ignorarán.

Si la línea #compdef contiene una de las opciones -p o -P, las palabras siguientes se toman como patrones. La función se llamará cuando se intente completar un comando o contexto que coincida con uno de los patrones. Las opciones -p y -P se utilizan para especificar patrones que se probarán antes o después de otras completaciones, respectivamente. Por lo tanto, -P se puede utilizar para especificar acciones predeterminadas.

La opción -N se utiliza después de una lista que sigue a -p o -P; especifica que las palabras restantes ya no definen patrones. Es posible alternar entre las tres opciones tantas veces como sea necesario.

#compdef -k estilo secuencia-de-teclas ...
Esta opción crea un widget que se comporta como el widget incorporado estilo y lo vincula a las secuencias-de-teclas dadas, si las hay. El estilo debe ser uno de los widgets incorporados que realizan completado, a saber, complete-word, delete-char-or-list, expand-or-complete, expand-or-complete-prefix, list-choices, menu-complete, menu-expand-or-complete o reverse-menu-complete. Si el módulo zsh/complist está cargado (ver zshmodules(1)), el widget menu-select también está disponible.

Cuando se escribe una de las secuencias-de-teclas, la función en el archivo se invocará para generar las coincidencias. Tenga en cuenta que una tecla no se volverá a vincular si ya lo estaba (es decir, estaba vinculada a algo que no fuera undefined-key). El widget creado tiene el mismo nombre que el archivo y se puede vincular a otras teclas utilizando bindkey como de costumbre.

#compdef -K nombre-widget estilo secuencia [ nombre estilo secuencia ... ]
Esto es similar a -k excepto que solo se puede dar un argumento de secuencia-de-teclas por cada par nombre-widget estilo. Sin embargo, el conjunto completo de tres argumentos puede repetirse con un conjunto diferente de argumentos. Tenga en cuenta en particular que el nombre-widget debe ser distinto en cada conjunto. Si no comienza con `_', se agregará. El nombre-widget no debe chocar con el nombre de ningún widget existente: los nombres basados en el nombre de la función son los más útiles. Por ejemplo,
#compdef -K _foo_complete complete-word "^X^C" \ 
  _foo_list list-choices "^X^D"

(todo en una línea) define un widget _foo_complete para el completado, vinculado a `^X^C', y un widget _foo_list para la lista, vinculado a `^X^D'.

#autoload [ opciones ]
Las funciones con la etiqueta #autoload se marcan para carga automática pero no se tratan de forma especial. Típicamente, se llamarán desde dentro de una de las funciones de completado. Cualquier opciones suministrada se pasará al comando incorporado autoload; un uso típico es +X para forzar la carga inmediata de la función. Tenga en cuenta que las banderas -U y -z siempre se agregan implícitamente.

El # es parte del nombre de la etiqueta y no se permite espacio en blanco después de él. Las etiquetas #compdef utilizan la función compdef descrita a continuación; la principal diferencia es que el nombre de la función se suministra implícitamente.

Los contextos especiales para los que se pueden definir funciones de completado son:

-array-value-
El lado derecho de una asignación de arreglo (`nombre=(...)')
-assign-parameter-
El nombre de un parámetro en una asignación, es decir, en el lado izquierdo de un `='
-brace-parameter-
El nombre de una expansión de parámetro dentro de llaves (`${...}')
-command-
Una palabra en posición de comando
-condition-
Una palabra dentro de una condición (`[[...]]')
-default-
Cualquier palabra para la que no se defina otro completado
-equal-
Una palabra que comience con un signo igual
-first-
Esto se prueba antes que cualquier otra función de completado. La función llamada puede establecer el parámetro _compskip a uno de varios valores: all: no se intentará ningún completado adicional; una cadena que contenga el subcadena patterns: no se llamarán funciones de completado de patrones; una cadena que contenga default: la función para el contexto `-default-' no se llamará, pero se llamarán las funciones definidas para los comandos.
-math-
Dentro de contextos matemáticos, como `((...))'
-parameter-
El nombre de una expansión de parámetro (`$...')
-redirect-
La palabra después de un operador de redirección.
-subscript-
El contenido de un subíndice de parámetro.
-tilde-
Después de una tilde inicial (`~'), pero antes de la primera barra en la palabra.
-value-
En el lado derecho de una asignación.

Se proporcionan implementaciones predeterminadas para cada uno de estos contextos. En la mayoría de los casos, el contexto -contexto- se implementa mediante una función correspondiente _contexto, por ejemplo, el contexto `-tilde-' y la función `_tilde').

Los contextos -redirect- y -value- permiten información adicional específica del contexto. (Internamente, esto es manejado por las funciones de cada contexto que llaman a la función _dispatch.) La información adicional se agrega separada por comas.

Para el contexto -redirect-, la información adicional tiene el formato `-redirect-,op,comando', donde op es el operador de redirección y comando es el nombre del comando en la línea. Si aún no hay un comando en la línea, el campo comando estará vacío.

Para el contexto -value-, el formato es `-value-,nombre,comando', donde nombre es el nombre del parámetro en el lado izquierdo de la asignación. En el caso de elementos de un array asociativo, por ejemplo `assoc=(key <TAB>', nombre se expande a `nombre-clave'. En ciertos contextos especiales, como al completar después de `make CFLAGS=', la parte comando da el nombre del comando, aquí make; de lo contrario, está vacío.

No es necesario definir completados totalmente específicos, ya que las funciones proporcionadas intentarán generar completados reemplazando progresivamente los elementos con `-default-'. Funciones de complemento

El sistema de complementos de Zsh utiliza una gran cantidad de funciones para realizar el trabajo de ofrecer complementos. Estas funciones se invocan de diversas maneras. La principal es la función incorporada compdef.

compdef se puede utilizar para asociar una función de complemento existente con uno o más comandos o contextos. Los comandos pueden ser nombres de comandos simples, o el nombre de un comando seguido por un guión y un subcomando, por ejemplo, `cvs-add'.

Los contextos se dan como cadenas separadas por dos puntos, por ejemplo, `:completion:*:*:*:*:*'. El primer campo, `:completion:', indica que se trata de un contexto de complemento. El segundo campo, si se utiliza una función con nombre para realizar el complemento, contendrá el nombre de la función (por ejemplo, `predict'). El tercer campo, el `completer', es la función que controla el proceso de complemento, por ejemplo, `complete' para la mayoría de los complementos, `complete-command' para los nombres de comandos, `complete-variable' para los nombres de variables y así sucesivamente. Los campos cuarto y quinto indican el comando actual y el argumento que se está complementando. El campo final es una etiqueta que distingue entre los tipos de complementos que se pueden generar en un contexto determinado.

La compdef busca las funciones en el orden que se indica a continuación. El primer argumento a `compdef' es la función que se utilizará para realizar el complemento, y el resto de los argumentos especifican el contexto. Los contextos se prueban en el orden siguiente:

  • Si se proporciona un argumento de comando, éste se utiliza primero. Por ejemplo, si se invoca `compdef _foo foo', la función `_foo' se utiliza para el comando `foo'. Si el comando tiene subcomandos, como `cvs add', entonces la llamada `compdef _foo-add cvs-add' se utilizará para los argumentos de `cvs add'.

  • Si no se proporciona un argumento de comando, se prueban las siguientes formas genéricas en orden, hasta que se encuentra una función para manejar el contexto.

    Por ejemplo, la llamada

    compdef _foo `-command-,-default-,-default-,-default-,-default-`

    indica que la función `_foo' debe utilizarse para los comandos para los que no se ha definido ninguna función de complemento específica. Esto normalmente se maneja mediante la función `_command' misma.

    De manera similar, las llamadas

    compdef _foo `-argument-,-default-,-default-,-default-`
    compdef _foo `-tag-,foo,-default-,-default-,-default-`
    compdef _foo `-tag-,-default-,-default-,-default-`
    compdef _foo `-value-,foo,-default-,-default-`
    compdef _foo `-value-,-default-,-default-`

    hacen que la función `_foo' proporcione complementos para los argumentos de los comandos, los valores de los argumentos con una etiqueta dada, los argumentos con una etiqueta dada, los valores de los argumentos con una etiqueta dada y los valores de los argumentos, respectivamente. La lista completa de contextos disponibles se puede encontrar en la página man de Zsh para `zshcompsys(1)'.

    Los argumentos también pueden tener la forma `-pattern-', que se utilizará para encontrar coincidencias con el patrón del argumento del comando actual. Por ejemplo:

    compdef '_files -g "*.log"' '-redirect-,2>,-default-'

    complementa archivos que coinciden con `*.log' después de `2> <TAB>' para cualquier comando sin un manejador más específico definido.

    Además:

    compdef _foo -value-,-default-,-default-

    especifica que `_foo' proporciona complementos para los valores de los parámetros para los que no se ha definido ninguna función especial. Esto generalmente lo maneja la propia función `_value'.

    Las mismas reglas de búsqueda se utilizan al buscar estilos (como se describe a continuación); por ejemplo

    zstyle ':completion:*:*:-redirect-,2>,*:*' file-patterns '*.log'

    es otra forma de hacer que el complemento después de `2> <TAB>' complemente archivos que coinciden con `*.log'.

Funciones

La siguiente función está definida por compinit y puede ser llamada directamente.

compdef [ -ane ] función nombre ... [ -{p|P} patrón ... [ -N nombre ...]]
compdef -d nombre ...
compdef -k [ -an ] función estilo secuencia-de-teclas [ secuencia-de-teclas ... ]
compdef -K [ -an ] función nombre estilo clave-sec [ nombre estilo seq ... ]
La primera forma define la función a llamar para el complemento en los contextos dados, como se describe para la etiqueta #compdef anterior.

Alternativamente, todos los argumentos pueden tener la forma `cmd=servicio'. Aquí servicio ya debería haber sido definido por líneas `cmd1=servicio' en archivos #compdef, como se describe anteriormente. El argumento para cmd se complementará de la misma manera que servicio.

El argumento función alternativamente puede ser una cadena que contenga casi cualquier código de shell. Si la cadena contiene un signo igual, lo anterior tendrá prioridad. La opción -e se puede usar para especificar que el primer argumento debe ser evaluado como código de shell incluso si contiene un signo igual. La cadena se ejecutará utilizando el comando incorporado eval para generar complementos. Esto proporciona una forma de evitar tener que definir una nueva función de complemento. Por ejemplo, para completar archivos que terminan en `.h' como argumentos del comando foo:

compdef '_files -g "*.h"' foo

La opción -n evita que se sobrescriban los complementos ya definidos para el comando o contexto.

La opción -d elimina cualquier complemento definido para el comando o los contextos listados.

Los nombres también pueden contener las opciones -p, -P y -N como se describe para la etiqueta #compdef. El efecto en la lista de argumentos es idéntico, cambiando entre definiciones de patrones que se prueban inicialmente, patrones que se prueban finalmente, y comandos y contextos normales.

El parámetro $_compskip puede ser establecido por cualquier función definida para un contexto de patrón. Si se establece a un valor que contiene la subcadena `patterns', ninguna de las funciones de patrón será llamada; si se establece a un valor que contiene la subcadena `all', ninguna otra función será llamada. Establecer $_compskip de esta manera es de particular utilidad cuando se usa la opción -p, ya que de lo contrario el despachador pasará a funciones adicionales (probablemente la predeterminada) después de llamar a la función de contexto de patrón, lo que puede distorsionar la visualización de las posibilidades de complemento si no se maneja correctamente.

La forma con -k define un widget con el mismo nombre que la función que se llamará para cada una de las secuencia-de-teclas; esto es similar a la etiqueta #compdef -k. La función debe generar los complementos necesarios y de lo contrario se comportará como el widget incorporado cuyo nombre se da como argumento estilo. Los widgets utilizables para esto son: complete-word, delete-char-or-list, expand-or-complete, expand-or-complete-prefix, list-choices, menu-complete, menu-expand-or-complete y reverse-menu-complete, así como menu-select si se carga el módulo zsh/complist. La opción -n evita que la tecla se vincule si ya está vinculada a algo distinto de undefined-key.

La forma con -K es similar y define múltiples widgets basados en la misma función, cada uno de los cuales requiere el conjunto de tres argumentos nombre, estilo y secuencia-de-teclas, donde los dos últimos son como para -k y el primero debe ser un nombre de widget único que comience con un guión bajo.

Donde sea aplicable, la opción -a hace que la función sea cargable automáticamente, equivalente a autoload -U función.

La función compdef se puede utilizar para asociar funciones de complemento existentes con nuevos comandos. Por ejemplo,

compdef _pids foo

utiliza la función `_pids' para completar IDs de proceso para el comando `foo'.

Tenga en cuenta también la función `_gnu_generic' descrita a continuación, que se puede utilizar para completar opciones para comandos que entienden la opción `--help'.

CONFIGURACIÓN DEL SISTEMA DE COMPLEMENTOS

Esta sección ofrece una breve descripción general de cómo funciona el sistema de complementos y, a continuación, más detalles sobre cómo los usuarios pueden configurar cómo y cuándo se generan las coincidencias.

Visión general

Cuando se intenta realizar un complemento en algún lugar de la línea de comandos, el sistema de complementos comienza a construir el contexto. El contexto representa todo lo que el shell sabe sobre el significado de la línea de comandos y la importancia de la posición del cursor. Esto tiene en cuenta una serie de cosas, incluido el nombre del comando (como `grep' o `zsh') y las opciones a las que la palabra actual puede ser un argumento (como la opción `-o' de zsh, que toma una opción de shell como argumento).

El contexto comienza siendo muy genérico ("estamos comenzando un complemento") y se vuelve más específico a medida que se aprende más ("la palabra actual está en una posición que suele ser un nombre de comando" o "la palabra actual podría ser un nombre de variable", etc.). Por lo tanto, el contexto variará durante la misma llamada al sistema de complementos.

Esta información de contexto se condensa en una cadena que consta de varios campos separados por dos puntos, denominada simplemente `el contexto' en el resto de la documentación. Tenga en cuenta que un usuario del sistema de complementos rara vez necesita componer una cadena de contexto, a menos que, por ejemplo, se esté escribiendo una nueva función para realizar complementos para un nuevo comando. Lo que un usuario puede necesitar hacer es componer un patrón de estilo, que se compara con un contexto cuando es necesario para buscar opciones sensibles al contexto que configuran el sistema de complementos.

Los siguientes párrafos explican cómo se compone un contexto dentro del conjunto de funciones de complemento. A continuación se discute cómo se definen los estilos. Los estilos determinan, por ejemplo, cómo se generan las coincidencias, de manera similar a las opciones de shell pero con mucho más control. Se definen con el comando incorporado zstyle (ver zshmodules(1)).

La cadena de contexto siempre consta de un conjunto fijo de campos, separados por dos puntos y con un dos puntos inicial antes del primero. Los campos que aún no se conocen se dejan vacíos, pero los dos puntos circundantes aparecen de todos modos. Los campos están siempre en el orden :completion:función:complementador:comando:argumento:etiqueta. Estos tienen el siguiente significado:

•
La cadena literal completion, indicando que este estilo es utilizado por el sistema de complementos. Esto distingue el contexto de los utilizados por, por ejemplo, los widgets zle y las funciones ZFTP.
•
La función, si el complemento se llama desde un widget con nombre en lugar de a través del sistema de complementos normal. Típicamente esto está en blanco, pero es establecido por widgets especiales como predict-on y las diversas funciones en el directorio Widget de la distribución con el nombre de esa función, a menudo en una forma abreviada.
•
El complementador activo actualmente, el nombre de la función sin el guión bajo inicial y con otros guiones bajos convertidos a guiones. Un `complementador' tiene el control general sobre cómo se debe realizar el complemento; `complete' es el más simple, pero existen otros complementadores para realizar tareas relacionadas como la corrección, o para modificar el comportamiento de un complementador posterior. Ver la sección `Funciones de control' a continuación para más información.
•
El comando o un -contexto- especial, tal como aparece después de la etiqueta #compdef o la función compdef. Las funciones de complemento para comandos que tienen subcomandos generalmente modifican este campo para contener el nombre del comando seguido de un guión y el subcomando. Por ejemplo, la función de complemento para el comando cvs establece este campo a cvs-add al complementar argumentos para el subcomando add.
•
El argumento; esto indica qué argumento de la línea de comandos o de opción se está complementando. Para los argumentos de comandos, esto generalmente toma la forma argumento-n, donde n es el número del argumento, y para los argumentos de las opciones la forma opción-opt-n donde n es el número del argumento para la opción opt. Sin embargo, esto solo es así si la línea de comandos se analiza con opciones y argumentos de estilo UNIX estándar, por lo que muchos complementos no establecen esto.
•
La etiqueta. Como se describió anteriormente, las etiquetas se utilizan para discriminar entre los tipos de coincidencias que una función de complemento puede generar en un contexto determinado. Cualquier función de complemento puede usar cualquier nombre de etiqueta que desee, pero se enumera una lista de las más comunes a continuación.

Luego, el complementador agrega el elemento complementador. El complemento contextual agrega las opciones comando y argumento. zstyle

allows the user to set styles which control the behaviour of the completion system. The styles are accessed by zstyle builtin command. The first argument to zstyle is a context name, and the remaining arguments are style values.

The context names are strings like :completion:function:completer:command:argument:tag. The fields are separated by colons (:). The first field is always completion.

The function field is the name of the completion function. If the completion function is not determined, it is left empty. This is the case for the special completion function :completion::complete:files, which is used when no completion function has been explicitly requested. It is also the case for the special function :completion::complete:dvips:option-o-1:files, which says that normal completion was attempted as the first argument to the option -o of the command dvips:

dvips -o ...

and the completion function will generate filenames.

Usually completion will be tried for all possible tags in an order given by the completion function. However, this can be altered by using the tag-order style. Completion is then restricted to the list of given tags in the given order.

The _complete_help bindable command shows all the contexts and tags available for completion at a particular point. This provides an easy way of finding information for tag-order and other styles. It is described in the section `Bindable Commands' below.

When looking up styles the completion system uses full context names, including the tag. Looking up the value of a style therefore consists of two things: the context, which is matched to the most specific (best fitting) pattern, and the name of the style itself, which must be matched exactly. The following examples demonstrate that patterns may be loosely defined for styles that apply broadly, or as tightly defined as desired for styles that apply in narrower circumstances.

For example, many completion functions can generate matches in a simple and a verbose form and use the verbose style to decide which form should be used. To make all such functions use the verbose form, put

zstyle ':completion:*' verbose yes

in a startup file (probably .zshrc). This gives the verbose style the value yes in every context inside the completion system, unless that context has a more specific definition. It is best to avoid giving the pattern as `*' in case the style has some meaning outside the completion system.

Many such general purpose styles can be configured simply by using the compinstall function.

A more specific example of the use of the verbose style is by the completion for the kill builtin. If the style is set, the builtin lists full job texts and process command lines; otherwise it shows the bare job numbers and PIDs. To turn the style off for this use only:

zstyle ':completion:*:*:kill:*:*' verbose no

For even more control, the style can use one of the tags `jobs' or `processes'. To turn off verbose display only for jobs:

zstyle ':completion:*:*:kill:*:jobs' verbose no

The -e option to zstyle even allows completion function code to appear as the argument to a style; this requires some understanding of the internals of completion functions (see see zshcompwid(1))). For example,

zstyle -e ':completion:*' hosts 'reply=($myhosts)'

This forces the value of the hosts style to be read from the variable myhosts each time a host name is needed; this is useful if the value of myhosts can change dynamically. For another useful example, see the example in the description of the file-list style below. This form can be slow and should be avoided for commonly examined styles such as menu and list-rows-first.

Note that the order in which styles are defined does not matter; the style mechanism uses the most specific possible match for a particular style to determine the set of values. Strings are preferred over patterns (for example, `:completion::complete:::foo' is more specific than `:completion::complete:::*'), and longer patterns are preferred over the pattern `*'. See zmodules(1) for details.

Context patterns that use something other than a wildcard (*) to match the middle parts of the context -- the completer, command, and argument in :completion:function:completer:command:argument:tag -- should include all six colons (:) explicitly. Without this, a pattern such as :completion:*:foo:* could match foo against a component other than the intended one (for example, against completer when a match against command was intended).

Style names like those of tags are arbitrary and depend on the completion function. However, the following two sections list some of the most common tags and styles.

Estilos Estándar

Tenga en cuenta que los valores de varios de estos estilos representan valores booleanos. Cualquiera de las cadenas `true', `on', `yes' y `1' puede usarse para el valor `true' y cualquiera de las cadenas `false', `off', `no' y `0' para el valor `false'. El comportamiento para cualquier otro valor no está definido, excepto donde se menciona explícitamente. El valor predeterminado puede ser `true' o `false' si el estilo no está definido.

Algunos de estos estilos se prueban primero para cada etiqueta posible correspondiente a un tipo de coincidencia, y si no se encuentra ningún estilo, para la etiqueta default. Los estilos más notables de este tipo son menu, list-colors y los estilos que controlan la lista de completado, como list-packed y last-prompt. Al probarse para la etiqueta default, solo se establecerá el campo function del contexto, de modo que un estilo que use la etiqueta default normalmente se definirá siguiendo estas líneas:

zstyle ':completion:*:default' menu ...
accept-exact
Se prueba para la etiqueta default además de las etiquetas válidas para el contexto actual. Si se establece en `true' y alguna de las coincidencias de prueba es idéntica a la cadena en la línea de comandos, esta coincidencia se aceptará inmediatamente (incluso si de otro modo se consideraría ambigua).

Al completar rutas (donde la etiqueta utilizada es `paths'), este estilo acepta cualquier número de patrones como valor además de los valores booleanos. Las rutas que coinciden con uno de estos patrones se aceptarán inmediatamente, incluso si la línea de comandos contiene más componentes de ruta parcialmente escritos y estos no coinciden con ningún archivo en el directorio aceptado.

Este estilo también es utilizado por el completador _expand para decidir si las palabras que comienzan con una tilde o una expansión de parámetro deben expandirse. Por ejemplo, si hay parámetros foo y foobar, la cadena `$foo' solo se expandirá si accept-exact se establece en `true'; de lo contrario, se permitirá que el sistema de completado expanda $foo a $foobar. Si el estilo se establece en `continue', _expand agregará la expansión como una coincidencia y también se permitirá que el sistema de completado continúe.

accept-exact-dirs
Se utiliza para completar nombres de archivo. A diferencia de accept-exact, es booleano. Por defecto, la completación de nombres de archivo examina todos los componentes de una ruta para ver si hay completados de ese componente, incluso si el componente coincide con un directorio existente. Por ejemplo, al completar después de /usr/bin/, la función examina posibles completados para /usr.

Cuando este estilo es `true', cualquier prefijo de una ruta que coincida con un directorio existente se acepta sin ningún intento de completarlo más. Por lo tanto, en el ejemplo dado, la ruta /usr/bin/ se acepta inmediatamente y se intenta la completación en ese directorio.

Este estilo también es útil al completar después de directorios que aparecen mágicamente cuando se hace referencia a ellos, como los directorios .zfs de ZFS o los directorios .snapshot de NetApp. Cuando el estilo está configurado, el shell no verifica la existencia del directorio dentro del directorio padre.

Si desea inhibir este comportamiento por completo, establezca el estilo path-completion (ver más abajo) en `false'.

add-space
Este estilo es utilizado por el completador _expand. Si es `true' (el valor predeterminado), se insertará un espacio después de todas las palabras resultantes de la expansión, o una barra en el caso de nombres de directorio. Si el valor es `file', el completador solo agregará un espacio a los nombres de archivos existentes. Tanto un booleano `true' como el valor `file' pueden combinarse con `subst', en cuyo caso el completador no agregará un espacio a las palabras generadas a partir de la expansión de una sustitución de la forma `$(...)' o `${...}'.

El completador _prefix utiliza este estilo como un valor booleano simple para decidir si se debe insertar un espacio antes del sufijo.

ambiguous
Esto se aplica al completar componentes no finales de rutas de nombres de archivo, en otras palabras, aquellos con una barra al final. Si está configurado, el cursor se deja después del primer componente ambiguo, incluso si el completado de menú está en uso. El estilo siempre se prueba con la etiqueta paths.
assign-list
Al completar después de un signo igual que se está tratando como una asignación, el sistema de completado normalmente completa solo un nombre de archivo. En algunos casos, el valor puede ser una lista de nombres de archivo separados por dos puntos, como con PATH y parámetros similares. Este estilo se puede establecer en una lista de patrones que coinciden con los nombres de dichos parámetros.

El valor predeterminado es completar listas cuando la palabra en la línea ya contiene dos puntos.

auto-description
Si está configurado, el valor de este estilo se utilizará como la descripción de las opciones que no son
descritas por las funciones de completado, pero que tienen exactamente un argumento. La secuencia `%d' en el valor se reemplazará por la descripción de este argumento. Dependiendo de las preferencias personales, puede ser útil establecer este estilo a algo como `especificar: %d'. Tenga en cuenta que esto puede no funcionar para algunos comandos.
evitar-completer
Esto es utilizado por el completer _all_matches para decidir si la cadena que consiste en todas las coincidencias debe añadirse a la lista que se está generando actualmente. Su valor es una lista de nombres de completers. Si alguno de ellos es el nombre del completer que generó las coincidencias en este completado, la cadena no se añadirá.

El valor predeterminado para este estilo es `_expand _old_list _correct _approximate', es decir, contiene los completers para los cuales una cadena con todas las coincidencias casi nunca será deseada.

ruta-caché
Este estilo define la ruta donde se almacenan los archivos de caché que contienen datos de completado volcado. Por defecto es `$ZDOTDIR/.zcompcache', o `$HOME/.zcompcache' si $ZDOTDIR no está definido. La caché de completado no se usará a menos que el estilo usar-caché esté configurado.
política-caché
Este estilo define la función que se utilizará para determinar si una caché necesita ser reconstruida. Consulte la sección sobre la función _cache_invalid a continuación.
llamar-comando
Este estilo se utiliza en la función para comandos como make y ant donde llamar al comando directamente para generar coincidencias sufre problemas como ser lento o, como en el caso de make, puede potencialmente causar la ejecución de acciones en el makefile. Si se establece en `true', se llama al comando para generar coincidencias. El valor predeterminado de este estilo es `false'.
comando
En muchos lugares, las funciones de completado necesitan llamar a comandos externos para generar la lista de completados. Este estilo se puede usar para anular el comando que se llama en algunos de estos casos. Los elementos del valor se unen con espacios para formar una línea de comandos para ejecutar. El valor también puede comenzar con un guion, en cuyo caso el comando habitual se agregará al final; esto es más útil para poner `builtin' o `command' delante para asegurarse de que se llama la versión apropiada de un comando, por ejemplo, para evitar llamar a una función de shell con el mismo nombre que un comando externo.

Como ejemplo, la función de completado para identificadores de proceso utiliza este estilo con la etiqueta procesos para generar los identificadores a completar y la lista de procesos a mostrar (si el estilo verbose es `true'). La lista producida por el comando debe parecerse a la salida del comando ps. La primera línea no se muestra, pero se busca la cadena `PID' (o `pid') para encontrar la posición de los identificadores de proceso en las siguientes líneas. Si la línea no contiene `PID', los primeros números de cada una de las otras líneas se toman como los identificadores de proceso a completar.

Tenga en cuenta que la función de completado generalmente tiene que llamar al comando especificado para cada intento de generar la lista de completado. Por lo tanto, se debe tener cuidado al especificar solo comandos que tardan poco tiempo en ejecutarse y, en particular, evitar aquellos que pueden no terminar nunca.

ruta-comando
Esta es una lista de directorios en los que buscar comandos para completar. El valor predeterminado para este estilo es el valor del parámetro especial path.
comandos
Esto es utilizado por la función que completa subcomandos para los scripts de inicialización del sistema (que residen en /etc/init.d o en algún lugar no demasiado lejos de allí). Sus valores proporcionan los comandos predeterminados a completar para aquellos comandos para los cuales la función de completado no puede encontrarlos automáticamente. El valor predeterminado para este estilo son las dos cadenas `start' y `stop'.
completar
Esto es utilizado por la función _expand_alias cuando se invoca como un comando enlazable. Si se establece en `true' y la palabra en la línea de comandos no es el nombre de un alias, se completarán los nombres de alias coincidentes.
completar-opciones
Esto es utilizado por el completer para cd, chdir y pushd. Para estos comandos se utiliza un - para introducir una entrada de pila de directorios y la completación de estos es mucho más común que la completación de opciones. Por lo tanto, a menos que el valor de este estilo sea `true', las opciones no se completarán, incluso después de un - inicial. Si es `true', las opciones se completarán después de un - inicial, a menos que haya un -- anterior en la línea de comandos.
completer
Las cadenas proporcionadas como valor de este estilo especifican los nombres de las funciones completer a utilizar. Las funciones completer disponibles se describen en la sección 'Funciones de Control' a continuación.

Cada cadena puede ser el nombre de una función completer o una cadena del tipo `función:nombre'. En el primer caso, el campo completer del contexto contendrá el nombre del completer sin el subrayado inicial y con todos los demás subrayados reemplazados por guiones. En el segundo caso, función es el nombre del completer a llamar, pero el contexto contendrá el nombre definido por el usuario en el campo completer del contexto. Si el nombre comienza con un guion, la cadena para el contexto se construirá a partir del nombre de la función completer como en el primer caso, con el nombre añadido al final. Por ejemplo:

zstyle ':completion:*' completer _complete _complete:-foo

Aquí, el completado llamará a la completer _complete dos veces, una vez usando `complete' y otra vez usando `complete-foo' en el campo completer del contexto. Normalmente, usar el mismo completer más de una vez solo tiene sentido cuando se usa con el formato `función:nombre', porque de lo contrario el nombre del contexto será el mismo en todas las llamadas al completer; las posibles excepciones a esta regla son los completers _ignored y _prefix.

El valor predeterminado para este estilo es `_complete _ignored': solo se realizará el completado, primero usando el estilo patrones-ignorados y el array $fignore, y luego sin ignorar coincidencias.

condición
Este estilo es utilizado por la función completer _list para decidir si la inserción de coincidencias debe retrasarse incondicionalmente. El valor predeterminado es `true'.
delimitadores
Este estilo se utiliza al agregar un delimitador para usar con modificadores de historial o calificadores de glob que tienen argumentos delimitados. Es un array de delimitadores preferidos para agregar. Se prefieren los caracteres no especiales, ya que de lo contrario el sistema de completado puede confundirse. La lista predeterminada es :, +, /, -, %. La lista puede estar vacía para forzar la escritura de un delimitador.
deshabilitado
Si esto se establece en `true', el completer _expand_alias y el comando enlazable intentarán expandir también alias deshabilitados. El valor predeterminado es `false'.
dominios
Una lista de nombres de dominios de red para completar. Si esto no está configurado, los nombres de dominio se tomarán del archivo /etc/resolv.conf.
entorno
El estilo de entorno se utiliza al completar para `sudo'. Se establece en un array de asignaciones `VAR=valor' que se exportarán al entorno local antes de que se invoque el completado para el comando objetivo.
zstyle ':completion:*:sudo::' environ \
  PATH="/sbin:/usr/sbin:$PATH" HOME="/root"
expandir
Este estilo se utiliza al completar cadenas que constan de varias partes, como nombres de ruta.

Si uno de sus valores es la cadena `prefijo', la palabra parcialmente escrita en la línea se expandirá tanto como sea posible, incluso si las partes finales no se pueden completar.

Si uno de sus valores es la cadena `sufijo', también se agregarán los nombres coincidentes para los componentes posteriores al primer componente ambiguo. Esto significa que la cadena resultante es la cadena desambiguada más larga posible. Sin embargo, la completación de menú se puede utilizar para recorrer todas las coincidencias.

extra-verboso
Si se establece, la lista de completado es más detallada a costa de una probable disminución de la velocidad de completado. El rendimiento del completado se verá afectado si este estilo se establece en `true'.
falso
Este estilo se puede establecer para cualquier contexto de completado. Especifica cadenas adicionales que siempre se completarán en ese contexto. La forma de cada cadena es `valor:descripción'; los dos puntos y la descripción pueden omitirse, pero cualquier dos puntos literal en valor debe escaparse con una barra invertida. Cualquier descripción proporcionada se muestra junto con el valor en las listas de completado.

Es importante usar un contexto suficientemente restrictivo al especificar cadenas falsas. Tenga en cuenta que los estilos ficheros-falsos y parametros-falsos proporcionan funcionalidades adicionales al completar archivos o parámetros.

falso-siempre
Esto funciona de manera idéntica al estilo falso, excepto que el estilo patrones-ignorados no se aplica a él. Esto permite anular un conjunto de coincidencias por completo estableciendo los patrones ignorados en `*'.

Lo siguiente muestra una forma de complementar cualquier etiqueta con datos arbitrarios, pero haciendo que se comporte como una etiqueta separada para fines de visualización. En este ejemplo, utilizamos las características del estilo orden-etiquetas para dividir la etiqueta directorios-nombrados en dos al realizar el completado con el completer estándar completar para argumentos de cd. La etiqueta directorios-nombrados-normal se comporta como de costumbre, pero la etiqueta directorios-nombrados-mio c contiene un conjunto fijo de directorios. Esto tiene el efecto de añadir el grupo de coincidencias `directorios extra' con las completaciones dadas.

zstyle ':completion::complete:cd:*' tag-order \ 
  'named-directories:-mine:extra\ directories
  named-directories:-normal:named\ directories *'
zstyle ':completion::complete:cd:*:named-directories-mine' \ 
  fake-always mydir1 mydir2
zstyle ':completion::complete:cd:*:named-directories-mine' \ 
  ignored-patterns '*'
fake-files
Este estilo se utiliza al completar archivos y se busca sin una etiqueta. Sus valores son del tipo `dir:nombres...'. Esto añadirá los nombres (cadenas separadas por espacios) como coincidencias posibles al completar en el directorio dir, incluso si no existen realmente tales archivos. El directorio puede ser un patrón; los caracteres de patrón o los dos puntos en dir deben escaparse con una barra invertida para ser tratados literalmente.

Esto puede ser útil en sistemas que soportan sistemas de archivos especiales cuyos nombres de ruta de nivel superior no se pueden listar o generar con patrones glob (pero ver accept-exact-dirs para una forma más general de tratar este problema). También se puede usar para directorios en los que no se tiene permiso de lectura.

La forma de patrón se puede usar para añadir una entrada 'mágica' determinada a todos los directorios de un sistema de archivos particular.

fake-parameters
Esto es utilizado por la función de completación para nombres de parámetros. Sus valores son nombres de parámetros que aún no se han establecido pero que deben completarse de todos modos. Cada nombre también puede ir seguido de dos puntos y una cadena que especifica el tipo del parámetro (como `scalar', `array' o `integer'). Si se proporciona el tipo, el nombre solo se completará si se requieren parámetros de ese tipo en el contexto particular. Los nombres para los que no se especifica tipo se completarán siempre.
file-list
Este estilo controla si los archivos completados utilizando el mecanismo incorporado estándar se listarán con una lista larga similar a ls -l. Tenga en cuenta que esta característica utiliza el módulo del shell zsh/stat para obtener información de archivos; esto carga el comando incorporado stat que reemplazará cualquier ejecutable stat externo. Para evitar esto, el siguiente código puede incluirse en un archivo de inicialización:
zmodload -i zsh/stat
disable stat

El estilo se puede establecer en un valor 'verdadero' (o 'all'), o uno de los valores 'insert' o 'list', que indica que los archivos se listarán en formato largo en todas las circunstancias, o al intentar insertar un nombre de archivo, o al listar nombres de archivo sin intentar insertar uno.

De forma más general, el valor puede ser una matriz de cualquiera de los valores anteriores, seguido opcionalmente por =num. Si num está presente, indica el número máximo de coincidencias para las que se utilizará el estilo de listado largo. Por ejemplo,

zstyle ':completion:*' file-list list=20 insert=10

especifica que el formato largo se utilizará al listar hasta 20 archivos o al insertar un archivo con hasta 10 coincidencias (suponiendo que se vaya a mostrar un listado, por ejemplo, en una completación ambigua), de lo contrario se utilizará el formato corto.

zstyle -e ':completion:*' file-list \ 
       '(( ${+NUMERIC} )) && reply=(true)'

especifica que el formato largo se utilizará siempre que se proporcione un argumento numérico, de lo contrario, el formato corto.

file-patterns
Esto es utilizado por la función estándar para completar nombres de archivo, _files. Si el estilo no está establecido, se ofrecen hasta tres etiquetas: `globbed-files', `directories' y `all-files', dependiendo de los tipos de archivos esperados por la llamada a _files. Las dos primeras (`globbed-files' y `directories') se ofrecen normalmente juntas para facilitar la completación de archivos en subdirectorios.

El estilo file-patterns proporciona alternativas a las etiquetas predeterminadas, que no se utilizan. Su valor consiste en elementos del tipo `patrón:etiqueta'; cada cadena puede contener cualquier número de tales especificaciones separadas por espacios.

El patrón es un patrón que se utilizará para generar nombres de archivo. Cualquier ocurrencia de la secuencia `%p' se reemplaza por cualquier patrón que pase la función que llama a _files. Los dos puntos en el patrón deben ir precedidos por una barra invertida para distinguirlos de los dos puntos antes de la etiqueta. Si se necesita más de un patrón, los patrones se pueden dar entre llaves, separados por comas.

Las etiquetas de todas las cadenas del valor serán ofrecidas por _files y utilizadas al buscar otros estilos. Cualquier etiqueta en la misma palabra se ofrecerá al mismo tiempo y antes que las palabras posteriores. Si no se da `:etiqueta', se utilizará la etiqueta `files'.

La etiqueta también puede ir seguida de dos puntos opcionales y una descripción, que se utilizará para el `%d' en el valor del estilo format (si está establecido) en lugar de la descripción predeterminada proporcionada por la función de completación. La inclusión de una descripción también da precedencia a las opciones asociadas, como para la agrupación de completaciones, por lo que se puede usar donde los archivos deban separarse.

Por ejemplo, para hacer que el comando rm complete primero solo nombres de archivos objeto y luego nombres de todos los archivos si no hay un archivo objeto coincidente:

zstyle ':completion:*:*:rm:*:*' file-patterns \ 
    '*.o:object-files' '%p:all-files'

Para alterar el comportamiento predeterminado de la completación de archivos: ofrecer archivos que coincidan con un patrón y directorios en el primer intento, luego todos los archivos -- para ofrecer solo archivos coincidentes en el primer intento, luego directorios y finalmente todos los archivos:

zstyle ':completion:*' file-patterns \ 
    '%p:globbed-files' '*(-/):directories' '*:all-files'

Esto funciona incluso donde no hay un patrón especial: _files coincide con todos los archivos usando el patrón `*' en el primer paso y se detiene cuando ve este patrón. Tenga en cuenta también que nunca intentará un patrón más de una vez para un solo intento de completación.

Para separar los directorios en un grupo distinto de los archivos pero aún así completarlos en el primer intento, se debe proporcionar una descripción. Tenga en cuenta que los directorios deben excluirse explícitamente de los globbed-files porque `*' coincidirá con los directorios. Para la agrupación, también es necesario establecer el estilo group-name.

zstyle ':completion:*' file-patterns \ 
    '%p(^-/):globbed-files *(-/):directories:location'

Durante la ejecución de las funciones de completación, la opción EXTENDED_GLOB está en vigor, por lo que los caracteres `#', `~' y `^' tienen significados especiales en los patrones.

file-sort
La función estándar de completación de nombres de archivo utiliza este estilo sin una etiqueta para determinar en qué orden se deben listar los nombres; la completación por menú recorrerá en el mismo orden. Los valores posibles son: `size' para ordenar por el tamaño del archivo; `links' para ordenar por el número de enlaces al archivo; `modification' (o `time' o `date') para ordenar por la hora de la última modificación; `access' para ordenar por la hora del último acceso; y `inode' (o `change') para ordenar por la hora del último cambio de inodo. Si el estilo se establece en cualquier otro valor, o no está establecido, los archivos se ordenarán alfabéticamente por nombre. Si el valor contiene la cadena `reverse', la ordenación se realiza en orden opuesto. Si el valor contiene la cadena `follow', las marcas de tiempo se asocian con los destinos de los enlaces simbólicos; la predeterminada es utilizar las marcas de tiempo de los propios enlaces.
file-split-chars
Un conjunto de caracteres que hará que *todas* las completaciones de archivos para el contexto dado se dividan en el punto donde ocurra cualquiera de los caracteres. Un uso típico es establecer el estilo en :; entonces todo hasta e incluyendo el último : en la cadena hasta ahora se ignora al completar archivos. Como esto es bastante drástico, generalmente es preferible actualizar las funciones de completación para contextos donde este comportamiento sea útil.
filter
El plugin ldap de la completación de direcciones de correo electrónico (ver _email_addresses) utiliza este estilo para especificar los atributos a comparar al filtrar entradas. Por ejemplo, si el estilo se establece en `sn', la comparación se realiza contra los apellidos. Se utiliza el filtrado LDAP estándar, por lo que se omite la coincidencia de completación normal. Si este estilo no está establecido, el plugin LDAP se omite. Es posible que también necesite establecer el estilo command para especificar cómo conectarse a su servidor LDAP.
force-list
Esto fuerza a que se muestre una lista de completaciones en cualquier punto donde se realice un listado, incluso en casos donde la lista normalmente se suprimiría. Por ejemplo, normalmente la lista solo se muestra si hay al menos dos coincidencias diferentes. Al establecer este estilo en `always', la lista siempre se mostrará, incluso si solo hay una coincidencia que se aceptará inmediatamente. El estilo también se puede establecer en un número. En este caso, la lista se mostrará si hay al menos ese número de coincidencias, incluso si todas insertaran la misma cadena.

Este estilo se prueba para la etiqueta predeterminada, así como para cada etiqueta válida para la completación actual. Por lo tanto, el listado se puede forzar solo para ciertos tipos de coincidencias.

format
Si esto se establece para la etiqueta descriptions, su valor se utiliza como una cadena para mostrar encima de las coincidencias en las listas de completación. La secuencia `%d' en esta cadena se reemplazará con una breve descripción de qué son estas coincidencias. Esta cadena también puede contener las secuencias de atributos de salida entendidas por compadd -X (ver zshcompwid(1)).

El estilo se prueba con cada etiqueta válida para la completación actual antes de probarse para la etiqueta descriptions. Por lo tanto, se pueden definir diferentes cadenas de formato para diferentes tipos de coincidencias.

Tenga en cuenta también que algunas funciones de completación definen secuencias `%' adicionales. Estas se describen para las funciones de completación que las utilizan.
