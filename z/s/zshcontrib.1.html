NOMBRE

zshcontrib - contribuciones de usuarios a zsh

DESCRIPCIÓN

La distribución fuente de Zsh incluye una serie de elementos contribuidos por la comunidad de usuarios. Estos no son intrínsecamente parte del shell y algunos pueden no estar disponibles en todas las instalaciones de zsh. Los más significativos se documentan aquí. Para documentación sobre otros elementos contribuidos, como funciones de shell, busque comentarios en los archivos fuente de las funciones.

UTILIDADES

Acceso a Ayuda En-Línea

La secuencia de teclas ESC h normalmente está enlazada por ZLE para ejecutar el widget run-help (ver zshzle(1)). Esto invoca al comando run-help con la palabra del comando de la línea de entrada actual como su argumento. Por defecto, run-help es un alias del comando man, por lo que a menudo falla cuando la palabra del comando es un builtin del shell o una función definida por el usuario. Al redefinir el alias run-help, se puede mejorar la ayuda en línea proporcionada por el shell.

La utilidad helpfiles, que se encuentra en el directorio Util de la distribución, es un programa Perl que se puede utilizar para procesar el manual de zsh y producir un archivo de ayuda separado para cada builtin del shell y para muchas otras características del shell. La función cargable automáticamente run-help, que se encuentra en Functions/Misc, busca estos archivos de ayuda y realiza varias otras comprobaciones para producir la ayuda más completa posible para el comando.

Los archivos de ayuda se instalan por defecto en un subdirectorio de /usr/share/zsh o /usr/local/share/zsh.

Para crear sus propios archivos de ayuda con helpfiles, elija o cree un directorio donde residirán los archivos de ayuda de cada comando. Por ejemplo, podría elegir ~/zsh_help. Si descomprimió la distribución de zsh en su directorio personal, usaría los comandos:

mkdir ~/zsh_help
perl ~/zsh-5.9/Util/helpfiles ~/zsh_help

El parámetro HELPDIR le dice a run-help dónde buscar los archivos de ayuda. Cuando no está configurado, utiliza la ruta de instalación predeterminada. Para usar su propio conjunto de archivos de ayuda, configure esto en la ruta apropiada en uno de sus archivos de inicio:

HELPDIR=~/zsh_help

Para usar la función run-help, necesita agregar líneas como las siguientes a su archivo .zshrc o equivalente:

unalias run-help
autoload run-help

Tenga en cuenta que para que `autoload run-help' funcione, el archivo run-help debe estar en uno de los directorios nombrados en su matriz fpath (ver zshparam(1)). Esto ya debería ser así si tiene una instalación estándar de zsh; si no es así, copie Functions/Misc/run-help a un directorio apropiado.

Recompilación de Funciones

Si edita frecuentemente sus funciones de zsh, o actualiza periódicamente su instalación de zsh para seguir los últimos desarrollos, puede que los resúmenes de funciones compilados con el builtin zcompile estén frecuentemente desactualizados con respecto a los archivos fuente de las funciones. Esto normalmente no es un problema, ya que zsh siempre busca el archivo más nuevo al cargar una función, pero puede causar un inicio del shell y una carga de funciones más lentos. Además, si un archivo de resumen se usa explícitamente como un elemento de fpath, zsh no verificará si alguno de sus archivos fuente ha cambiado.

La función cargable automáticamente zrecompile, que se encuentra en Functions/Misc, se puede usar para mantener actualizados los resúmenes de funciones.

zrecompile [ -qt ] [ nombre ... ]
zrecompile [ -qt ] -p arg ... [ -- arg ... ]
Esto intenta encontrar archivos *.zwc y recompilarlos automáticamente si al menos uno de los archivos originales es más nuevo que el archivo compilado. Esto solo funciona si los nombres almacenados en los archivos compilados son rutas completas o son relativas al directorio que contiene el archivo .zwc.

En la primera forma, cada nombre es el nombre de un archivo compilado o un directorio que contiene archivos *.zwc que deben ser verificados. Si no se proporcionan argumentos, se utilizan los directorios y los archivos *.zwc en fpath.

Cuando se proporciona -t, no se realiza ninguna compilación, pero se establece un estado de retorno de cero (verdadero) si hay archivos que necesitan ser recompilados y cero (falso) en caso contrario. La opción -q silencia la salida detallada que describe lo que está haciendo zrecompile.

Sin la opción -t, el estado de retorno es cero si todos los archivos que necesitaban recompilación pudieron ser compilados y cero si la compilación para al menos uno de los archivos falló.

Si se proporciona la opción -p, los args se interpretan como uno o más conjuntos de argumentos para zcompile, separados por `--'. Por ejemplo:

zrecompile -p \ 
           -R ~/.zshrc -- \ 
           -M ~/.zcompdump -- \ 
           ~/zsh/comp.zwc ~/zsh/Completion/*/_*

Esto compila ~/.zshrc en ~/.zshrc.zwc si este no existe o si es más antiguo que ~/.zshrc. El archivo compilado se marcará para lectura en lugar de mapeo. Lo mismo se hace para ~/.zcompdump y ~/.zcompdump.zwc, pero este archivo compilado se marcará para mapeo. La última línea recrea el archivo ~/zsh/comp.zwc si alguno de los archivos que coinciden con el patrón dado es más nuevo que él.

Sin la opción -p, zrecompile no crea resúmenes de funciones que no existan previamente, ni agrega nuevas funciones al resumen.

El siguiente bucle de shell es un ejemplo de un método para crear resúmenes de funciones para todas las funciones en su fpath, asumiendo que tiene permisos de escritura en los directorios:

for ((i=1; i <= $#fpath; ++i)); do
  dir=$fpath[i]
  zwc=${dir:t}.zwc
  if [[ $dir == (.|..) || $dir == (.|..)/* ]]; then
    continue
  fi
  files=($dir/*(N-.))
  if [[ -w $dir:h && -n $files ]]; then
    files=(${${(M)files%/*/*}#/})
    if ( cd $dir:h &&
         zrecompile -p -U -z $zwc $files ); then
      fpath[i]=$fpath[i].zwc
    fi
  fi
done

Las opciones -U y -z son apropiadas para funciones en la instalación predeterminada de fpath de zsh; puede que necesite usar opciones diferentes para sus directorios de funciones personales.

Una vez que se han creado los resúmenes y se ha modificado su fpath para referirse a ellos, puede mantenerlos actualizados ejecutando zrecompile sin argumentos.

Definición de Teclado

La gran cantidad de combinaciones posibles de teclados, estaciones de trabajo, terminales, emuladores y sistemas de ventanas hace imposible que zsh tenga enlaces de teclas incorporados para cada situación. La utilidad zkbd, que se encuentra en Functions/Misc, puede ayudarle a crear rápidamente enlaces de teclas para su configuración.

Ejecute zkbd ya sea como una función cargable automáticamente, o como un script de shell:

zsh -f ~/zsh-5.9/Functions/Misc/zkbd

Cuando ejecuta zkbd, primero le pide que introduzca el tipo de su terminal; si el predeterminado que ofrece es correcto, simplemente pulse enter. Luego le pide que pulse una serie de teclas diferentes para determinar características de su teclado y terminal; zkbd le advierte si encuentra algo fuera de lo común, como una tecla de Borrar que no envíe ni ^H ni ^?.

Las pulsaciones de teclas leídas por zkbd se registran como una definición para un array asociativo llamado key, escrito en un archivo en el subdirectorio .zkbd dentro de su directorio HOME o ZDOTDIR. El nombre del archivo se compone de los parámetros TERM, VENDOR y OSTYPE, unidos por guiones.

Puede leer este archivo en su .zshrc u otro archivo de inicio con los comandos `source' o `.', luego referenciar el parámetro key en comandos bindkey, así:

source ${ZDOTDIR:-$HOME}/.zkbd/$TERM-$VENDOR-$OSTYPE
[[ -n ${key[Left]} ]] && bindkey "${key[Left]}" backward-char
[[ -n ${key[Right]} ]] && bindkey "${key[Right]}" forward-char
# etc.

Dumping Shell State

Occasionally, you may encounter a problem that appears to be a bug in the shell, particularly if you are using a beta version of zsh or a development release. Usually, it is sufficient to send a description of the problem to one of the zsh mailing lists (see zsh(1)). However, sometimes one of the zsh developers will need to recreate your environment to track down the problem.

The script named reporter, found in the Util directory of the distribution, is provided for this purpose. (It is also possible to autoload reporter, but reporter is not installed in fpath by default.) This script outputs a detailed dump of the shell state in the form of another script that can be read with `zsh -f' to recreate that state.

To use reporter, read the script into your shell with the `.' command and redirect the output into a file:

. ~/zsh-5.9/Util/reporter > zsh.report

You should check the zsh.report file for any sensitive information, such as passwords, and remove them manually before sending the script to the developers. Also, as the output can be voluminous, it is best to wait for the developers to request this information before sending it.

You can also use reporter to dump only a subset of the shell state. This is sometimes useful for creating startup files for the first time. Most of the output from reporter is far more detailed than is usually necessary for a startup file, but the states aliases, options, and zstyles may be useful because they include only changes from the defaults. The bindings state may be useful if you have created any keymaps of your own, because reporter arranges to dump the keymap creation commands as well as the bindings for every keymap.

As is usual with automated tools, if you create a startup file with reporter, you should edit the results to remove unnecessary commands. Note that if you are using the new completion system, you should *not* dump the functions state to your startup files with reporter; use the compdump function instead (see zshcompsys(1)).

reporter [ state ... ]
Prints the indicated subset of the current shell state to standard output. The state arguments can be one or more of the following:
all
Outputs everything listed below.
aliases
Outputs alias definitions.
bindings
Outputs ZLE key maps and bindings.
completion
Outputs old-style compctl commands. New completion is covered by functions and zstyles.
functions
Outputs autoloads and function definitions.
limits
Outputs limit commands.
options
Outputs setopt commands.
styles
Same as zstyles.
variables
Outputs shell parameter assignments, plus export commands for any environment variables.
zstyles
Outputs zstyle commands.

If the state is omitted, all is assumed.

With the exception of `all', every state can be abbreviated by any prefix, even a single letter; thus a is the same as aliases, z is the same as zstyles, etc.

Manipulating Hook Functions

add-zsh-hook [ -L | -dD ] [ -Uzk ] hook function
Several functions are special to the shell, as described in the section SPECIAL FUNCTIONS (see zshmisc(1)), in that they are automatically called at specific points during shell execution. Each has an associated array consisting of names of functions to be called at the same point; these are so-called `hook functions'. The shell function add-zsh-hook provides a simple way of adding or removing functions from the array.

hook is one of chpwd, periodic, precmd, preexec, zshaddhistory, zshexit, or zsh_directory_name, the special functions in question. Note that zsh_directory_name is called in a different way from the other functions, but may still be manipulated as a hook.

function is the name of an ordinary shell function. If no options are given, this will be added to the array of functions to be executed in the given context. Functions are invoked in the order they were added.

If the option -L is given, the current values for the hook arrays are listed with typeset.

If the option -d is given, the function is removed from the array of functions to be executed.

If the option -D is given, the function is treated as a pattern, and any matching names of functions are removed from the array of functions to be executed.

The options -U, -z, and -k are passed as arguments to autoload for function. For functions contributed with zsh, the options -Uz are appropriate.

add-zle-hook-widget [ -L | -dD ] [ -Uzk ] hook widgetname
Several widget names are special to the line editor, as described in the section Special Widgets (see zshzle(1)), in that they are automatically called at specific points during editing. Unlike function hooks, these do not use a predefined array of other names to call at the same point; the shell function add-zle-hook-widget maintains a similar array and arranges for the special widget to invoke those additional widgets.

hook is one of isearch-exit, isearch-update, line-pre-redraw, line-init, line-finish, history-line-set, or keymap-select, corresponding to each of the special widgets zle-isearch-exit, etc. The special widget names are also accepted as the hook argument.

widgetname is the name of a ZLE widget. If no options are given, this is added to the array of widgets to be invoked in the given hook context. Widgets are invoked in the order they were added, with

zle widgetname -Nw -f "nolast" -- "$@"

Note that this means that the `WIDGET' special parameter tracks the widgetname when the widget function is called, rather than tracking the name of the corresponding special hook widget.

If the option -d is given, the widgetname is removed from the array of widgets to be executed.

If the option -D is given, the widgetname is treated as a pattern, and any matching names of widgets are removed from the array.

If widgetname does not name an existing widget when added to the array, it is assumed that a shell function also named widgetname is intended to provide the implementation of the widget. This name is therefore marked for autoloading, and the options -U, -z, and -k are passed as arguments to autoload, as with add-zsh-hook. The widget is also created with `zle -N widgetname' to cause the corresponding function to be loaded the first time the hook is called.

The arrays of widgetname are currently maintained in zstyle contexts, one for each hook context, with a style of `widgets'. If the -L option is given, this set of styles is listed with `zstyle -L'. This implementation may change, and the special widgets that refer to the styles are created only if add-zle-hook-widget is called to add at least one widget. Therefore, if this function is used for any hooks, then all hooks should be managed only via this function.

REMEMBERING RECENT DIRECTORIES

The function cdr allows you to change the working directory to a previous working directory from a list maintained automatically. It is similar in concept to the directory stack controlled by the pushd, popd, and dirs builtins, but it is more configurable. As it stores all entries in files, it is maintained across sessions and (by default) between terminal emulators in the current session. Duplicates are automatically removed, so that the list reflects the single most recent use of each directory.

Note that the pushd directory stack is not actually modified or used by cdr unless you configure it to do so as described in the configuration section below.

Installation

The system works by means of a hook function that is called every time the directory changes. To install the system, autoload the required functions and use the add-zsh-hook function described above:

autoload -Uz chpwd_recent_dirs cdr add-zsh-hook
add-zsh-hook chpwd chpwd_recent_dirs

Now, every time you change directories interactively, no matter which command you use, the directory to which you change will be remembered in most-recent-first order.

CDR(1)

cambia de directorio usando una lista de directorios usados recientemente

Sinopsis

cdr [n]

cdr [-l|-r|-e|-p [-P] pattern]

Descripción

El comando cdr (change recent directory) cambia el directorio actual a uno de los directorios utilizados recientemente. La lista de directorios recientes se mantiene en un archivo, de forma que sobrevive a través de las sesiones del shell.

Si se proporciona un argumento numérico, cdr cambia al directorio correspondiente de la lista. El índice 1 se refiere al directorio inmediatamente anterior; el directorio actual se recuerda pero no se ofrece como destino. Tenga en cuenta que si tiene varias ventanas abiertas, 1 puede referirse a un directorio cambiado en otra ventana; puede evitar esto teniendo archivos por terminal para almacenar el directorio, como se describe para el estilo recent-dirs-file a continuación.

Si establece el estilo recent-dirs-default descrito a continuación, cdr se comportará igual que cd si se le da un argumento no numérico o más de un argumento. La lista de directorios recientes se actualiza de todos modos al cambiar de directorio.

Si se omite el argumento, se asume 1. Esto es similar al comportamiento de pushd de intercambiar los dos directorios más recientes en la pila.

La completación para el argumento de cdr está disponible si se ha ejecutado compinit; se recomienda la selección de menú, usando:

zstyle ':completion:*:*:cdr:*:*' menu selection

para permitirle ciclar a través de directorios recientes; el orden se conserva, por lo que la primera opción es el directorio más reciente antes del actual. El estilo detallado también se recomienda para asegurar que se muestre el directorio; este estilo está activado por defecto, por lo que no se requiere ninguna acción a menos que lo haya cambiado.

Opciones

El comportamiento de cdr puede modificarse por las siguientes opciones.

-l
enumera los números y los directorios correspondientes en forma abreviada (es decir, con la sustitución de ~ aplicada de nuevo), uno por línea. Los directorios aquí no están entre comillas (esto solo sería un problema si un nombre de directorio contuviera un salto de línea). Esto es utilizado por el sistema de completación.
-r
establece la variable reply al conjunto actual de directorios. No se imprime nada y el directorio no se cambia.
-e
le permite editar la lista de directorios, uno por línea. La lista puede editase en la medida que desee; no se realiza ninguna comprobación de validez. La completación está disponible. No se necesitan comillas (excepto para saltos de línea, donde en cualquier caso no tengo simpatía); los directorios están en forma no abreviada y contienen una ruta absoluta, es decir, comienzan con /. Normalmente, la primera entrada debe dejarse como el directorio actual.
-p 'patrón'
Elimina cualquier elemento de la lista de directorios que coincida con el patrón de glob extendido dado; el patrón debe estar entre comillas para evitar la expansión inmediata en la línea de comandos. El patrón se compara con cada nombre de archivo completamente expandido en la lista; la cadena completa debe coincidir, por lo que se necesitan comodines al final (por ejemplo, '*elimíname*') para eliminar entradas con una subcadena dada.

Si la salida es a una terminal, la función imprimirá la nueva lista después de eliminar y solicitará confirmación al usuario. Este paso de salida y confirmación se puede omitir usando -P en lugar de -p.

Configuración

La configuración se realiza mediante el mecanismo de estilos que debería ser familiar para la completación; si no, consulte la descripción del comando zstyle en zshmodules(1). El contexto para establecer estilos debe ser ':chpwd:*' en caso de que el significado del contexto se amplíe en el futuro, por ejemplo:

zstyle ':chpwd:*' recent-dirs-max 0

establece el valor del estilo recent-dirs-max a 0. En la práctica, el nombre del estilo es lo suficientemente específico como para que un contexto de '*' esté bien.

Una excepción es recent-dirs-insert, que es utilizado exclusivamente por el sistema de completación y, por lo tanto, tiene el contexto habitual del sistema de completación (':completion:*' si no se necesita nada más específico), aunque de nuevo '*' debería estar bien en la práctica.

recent-dirs-default
Si es verdadero, y el comando está esperando un índice de directorio reciente, y bien hay más de un argumento o el argumento no es un entero, entonces pasa a "cd". Esto permite a los perezosos usar solo un comando para cambiar de directorio. La completación también reconoce esto; consulte recent-dirs-insert para controlar la completación cuando esta opción está en uso.
recent-dirs-file
El archivo donde se guarda la lista de directorios. El valor por defecto es ${ZDOTDIR:-$HOME}/.chpwd-recent-dirs, es decir, está en su directorio de inicio a menos que haya establecido la variable ZDOTDIR para que apunte a otro lugar. Los nombres de los directorios se guardan en formato de comillas $'...', por lo que cada línea del archivo puede suministrarse directamente al shell como argumento.

El valor de este estilo puede ser un array. En este caso, el primer archivo de la lista se utilizará siempre para guardar directorios, mientras que cualquier otro archivo permanecerá sin cambios. Al leer la lista de directorios recientes, si hay menos que el número máximo de entradas en el primer archivo, el contenido de los archivos posteriores del array se añadirá eliminando duplicados de la lista mostrada. El contenido de los dos archivos no se ordena conjuntamente, es decir, todas las entradas del primer archivo se muestran primero. El valor especial + puede aparecer en la lista para indicar que el archivo por defecto debe leerse en ese momento. Esto permite efectos como el siguiente:

zstyle ':chpwd:*' recent-dirs-file \ 
~/.chpwd-recent-dirs-${TTY##*/} +

Los directorios recientes se leen de un archivo numerado según la terminal. Si hay suficientes entradas, la lista se complementa desde el archivo por defecto.

Es posible usar zstyle -e para hacer que el directorio sea configurable en tiempo de ejecución:

zstyle -e ':chpwd:*' recent-dirs-file pick-recent-dirs-file
pick-recent-dirs-file() {
  if [[ $PWD = ~/text/writing(|/*) ]]; then
    reply=(~/.chpwd-recent-dirs-writing)
  else
    reply=(+)
  fi
}

En este ejemplo, si el directorio actual es ~/text/writing o un directorio debajo de él, entonces se usa un archivo especial para guardar directorios recientes, de lo contrario se usa el por defecto.

recent-dirs-insert
Usado por la completación. Si recent-dirs-default es verdadero, entonces establecer esto a true hace que el directorio real, en lugar de su índice, se inserte en la línea de comandos; esto tiene el mismo efecto que usar el índice correspondiente, pero hace que el historial sea más claro y la línea más fácil de editar. Con esta configuración, si parte de un argumento ya se ha escrito, se realiza la completación normal de directorio en lugar de la completación de directorio reciente; esto se debe a que se espera que la completación de directorio reciente se haga ciclando a través de las entradas en modo menú.

Si el valor del estilo es always, entonces solo se completarán los directorios recientes; en ese caso, use el comando cd cuando desee completar otros directorios.

Si el valor es fallback, se intentarán primero los directorios recientes, luego se realizará la completación normal de directorios si la completación de directorios recientes no encontró una coincidencia.

Finalmente, si el valor es both, se presentarán ambos conjuntos de completaciones; el mecanismo de etiquetas habitual se puede utilizar para distinguir los resultados, con los directorios recientes etiquetados como recent-dirs. Tenga en cuenta que los directorios recientes insertados se abrevian con nombres de directorio cuando corresponda.

recent-dirs-max
El número máximo de directorios a guardar en el archivo. Si esto es cero o negativo, no hay máximo. El valor por defecto es 20. Tenga en cuenta que esto incluye el directorio actual, que no se ofrece, por lo que el número más alto de directorios que se le ofrecerán es uno menos que el máximo.
recent-dirs-prune
Este estilo es un array que determina qué directorios deben (o no deben) añadirse a la lista reciente. Los elementos del array pueden incluir:
parent
Elimina ancestros (más precisamente, ancestros) de la lista reciente. Si está presente, cambiar directamente hacia abajo por cualquier número de directorios hace que el directorio actual se sobrescriba. Por ejemplo, cambiar de ~pws a ~pws/some/other/dir hace que ~pws no quede en la pila de directorios recientes. Esto solo se aplica a cambios directos a directorios descendientes; los directorios anteriores en la lista no se eliminan. Por ejemplo, cambiar de ~pws/yet/another a ~pws/some/other/dir no hace que ~pws se elimine.
pattern:patrón
Proporciona un patrón de zsh para los directorios que no deben añadirse a la lista reciente (si aún no están allí). Este elemento se puede repetir para añadir diferentes patrones. Por ejemplo, 'pattern:/tmp(|/*)' impide que /tmp o sus descendientes se añadan. La opción EXTENDED_GLOB siempre está activada para estos patrones.
recent-dirs-pushd
Si se establece en verdadero, cdr usará pushd en lugar de cd para cambiar el directorio, de modo que el directorio se guarde en la pila de directorios. Como la pila de directorios está completamente separada de la lista de archivos guardados por el mecanismo utilizado en este archivo, no hay una razón obvia para hacer esto.

Uso con nomenclatura de directorios dinámica

Es posible referirse a directorios recientes utilizando la sintaxis de nombres de directorios dinámicos utilizando la función proporcionada zsh_directory_name_cdr como gancho:

autoload -Uz add-zsh-hook
add-zsh-hook -Uz zsh_directory_name zsh_directory_name_cdr

Cuando esto se hace, ~[1] se referirá al directorio más reciente distinto de $PWD, y así sucesivamente. La completación después de ~[... también funciona.

Detalles del manejo de directorios

Esta sección es para los curiosos o confundidos; la mayoría de los usuarios no necesitarán esta información.

Los directorios recientes se guardan en un archivo inmediatamente y, por lo tanto, se conservan entre sesiones. Tenga en cuenta que actualmente no se aplica bloqueo de archivos: la lista se actualiza inmediatamente en comandos interactivos y en ningún otro lugar (a diferencia del historial), y se asume que solo cambiará de directorio en una ventana.

to-do-list-vim do-at-once. This is not safe on shared accounts, but in any case the system has limited utility when someone else is changing to a different set of directories behind your back.

To make this a little safer, only directory changes instituted from the command line, either directly or indirectly through shell function calls (but not through subshells, evals, traps, completion functions and the like) are saved. Shell functions should use cd -q or pushd -q to avoid side effects if the change to the directory is to be invisible at the command line. See the contents of the function chpwd_recent_dirs for more details.

REFERENCIAS DINÁMICAS ABREVIADAS A DIRECTORIOS

El sistema de nombres de directorios dinámicos se describe en la subsección Directorios con nombre dinámico de la sección Expansión de nombres de archivo en zshexpn(1). En este, una referencia a ~[...] se expande mediante una función encontrada a través del mecanismo de hooks.

La función contribuida zsh_directory_name_generic proporciona un sistema que permite al usuario referirse a directorios con solo una cantidad limitada de código nuevo. Admite las tres interfaces estándar para la denominación de directorios: convertir de un nombre a un directorio, convertir en la dirección inversa para encontrar un nombre corto y completar nombres.

La característica principal de esta función es una sintaxis similar a la de las rutas, que combina abreviaturas en varios niveles separados por ":". Como ejemplo, ~[g:p:s] podría especificar:

g
El directorio de nivel superior para tu área de git. Este primer componente debe coincidir, o la función devolverá indicando que se debe intentar otra función hook de nombre de directorio.
p
El nombre de un proyecto dentro de tu área de git.
s
El área de origen dentro de ese proyecto. Esto te permite colapsar referencias a jerarquías largas a una forma muy compacta, particularmente si las jerarquías son similares en diferentes áreas del disco.

Los componentes del nombre pueden completarse: si se muestra una descripción en la parte superior de la lista de completaciones, incluye la ruta a la que se expanden los componentes anteriores, mientras que la descripción de una completación individual muestra el segmento de ruta que agregaría. No se necesita configuración adicional para esto, ya que el sistema de completación es consciente del mecanismo de nombres de directorios dinámicos.

Uso

Para usar la función, primero define una función wrapper para tu caso específico. Asumiremos que se va a cargar automáticamente (autoload). Esto puede tener cualquier nombre, pero nos referiremos a ella como zdn_mywrapper. Esta función wrapper definirá varias variables y luego llamará a esta función con los mismos argumentos que recibe la función wrapper. Esta configuración se describe a continuación.

Luego, haz que el wrapper se ejecute como un hook de zsh_directory_name:

autoload -Uz add-zsh-hook zsh_directory_name_generic zdn_mywrapper
add-zsh-hook -U zsh_directory_name zdn_mywrapper

Configuración

La función wrapper debe definir un array asociativo local zdn_top. Alternativamente, esto se puede configurar con un estilo llamado mapping. El contexto del estilo es :zdn:nombre-wrapper donde nombre-wrapper es la función que llama a zsh_directory_name_generic; por ejemplo:

zstyle :zdn:zdn_mywrapper: mapping zdn_mywrapper_top

Las claves de este array asociativo corresponden al primer componente del nombre. Los valores son directorios coincidentes. Pueden tener un sufijo opcional con una barra seguida de dos puntos y el nombre de una variable en el mismo formato para dar el siguiente componente. (La barra antes de los dos puntos es para desambiguar el caso en que se necesiten dos puntos en la ruta para una unidad. De lo contrario, no hay sintaxis para escapar esto, por lo que los componentes de ruta cuyos nombres comienzan con dos puntos no son admitidos). Un componente especial :default: especifica una variable en la forma /:var (la sección de ruta se ignora y generalmente está vacía) que se usará para el siguiente componente si no se proporciona ninguna variable para la ruta. Las variables a las que se hace referencia dentro de zdn_top tienen el mismo formato que zdn_top mismo, pero contienen rutas relativas.

Por ejemplo,

local -A zdn_top=(
  g   ~/git
  ga  ~/alternate/git
  gs  /scratch/$USER/git/:second2
  :default: /:second1
)

Esto especifica el comportamiento de un directorio al que se hace referencia como ~[g:...] o ~[ga:...] o ~[gs:...]. Los componentes de ruta posteriores son opcionales; en ese caso, ~[g] se expande a ~/git, y así sucesivamente. gs se expande a /scratch/$USER/git y utiliza el array asociativo second2 para coincidir con el segundo componente; g y ga usan el array asociativo second1 para coincidir con el segundo componente.

Al expandir un nombre a un directorio, si el primer componente no es g, ga o gs, no es un error; la función simplemente devuelve 1 para que se pueda intentar una función hook posterior. Sin embargo, la coincidencia del primer componente compromete a la función, por lo que si un componente posterior no coincide, se imprime un error (aunque esto aún no impide que se ejecuten hooks posteriores).

Para los componentes posteriores al primero, se espera una ruta relativa, pero tenga en cuenta que aún pueden aparecer varios niveles. Aquí hay un ejemplo de second1:

local -A second1=(
  p   myproject
  s   somproject
  os  otherproject/subproject/:third
)

La ruta encontrada desde zdn_top se extiende con el directorio coincidente, por lo que ~[g:p] se convierte en ~/git/myproject. La barra entre ellos se agrega automáticamente (no es posible que un componente posterior modifique el nombre de un directorio ya coincidente). Solo os especifica una variable para un tercer componente, y no hay :default:, por lo que es un error usar un nombre como ~[g:p:x] o ~[ga:s:y] porque no hay dónde buscar x o y.

Los arrays asociativos deben ser visibles dentro de esta función; por lo tanto, la función genérica utiliza nombres de variables internos que comienzan con _zdn_ para evitar conflictos. Tenga en cuenta que la variable reply debe pasarse de vuelta al shell, por lo que no debe ser local en la función que llama.

La función no verifica si los directorios ensamblados por componente realmente existen; esto permite que el sistema funcione en sistemas de archivos montados automáticamente. El error del comando que intenta usar un directorio inexistente debería ser suficiente para indicar el problema.

Ejemplo completo

Aquí tienes una definición completa ficticia pero utilizable y cargable automáticamente de la función de ejemplo definida por el código anterior. Así, ~[gs:p:s] se expande a /scratch/$USER/git/myscratchproject/top/srcdir (con $USER también expandido).

local -A zdn_top=(
  g   ~/git
  ga  ~/alternate/git
  gs  /scratch/$USER/git/:second2
  :default: /:second1
)
local -A second1=(
  p   myproject
  s   somproject
  os  otherproject/subproject/:third
)
local -A second2=(
  p   myscratchproject
  s   somescratchproject
)
local -A third=(
  s   top/srcdir
  d   top/documentation
)
# autoload no es necesario si hiciste esto al inicializar...
autoload -Uz zsh_directory_name_generic
zsh_directory_name_generic "$@

También es posible utilizar arrays asociativos globales, adecuadamente nombrados, y establecer el estilo para el contexto de tu función wrapper para referirse a esto. Entonces tu código de configuración contendría lo siguiente:

typeset -A zdn_mywrapper_top=(...)
# ... y así sucesivamente para otros arrays asociativos ...
zstyle ':zdn:zdn_mywrapper:' mapping zdn_mywrapper_top
autoload -Uz add-zsh-hook zsh_directory_name_generic zdn_mywrapper
add-zsh-hook -U zsh_directory_name zdn_mywrapper

Y la función zdn_mywrapper contendría solo lo siguiente:

zsh_directory_name_generic "$@"

Inicio Rápido

Para que esta función funcione rápidamente (incluyendo colores), puedes hacer lo siguiente (asumiendo que cargaste vcs_info correctamente - ver arriba):

zstyle ':vcs_info:*' actionformats \ 
    '%F{5}(%f%s%F{5})%F{3}-%F{5}[%F{2}%b%F{3}|%F{1}%a%F{5}]%f '
zstyle ':vcs_info:*' formats       \ 
    '%F{5}(%f%s%F{5})%F{3}-%F{5}[%F{2}%b%F{5}]%f '
zstyle ':vcs_info:(sv[nk]|bzr):*' branchformat '%b%F{1}:%F{3}%r'
precmd () { vcs_info }
PS1='%F{5}[%F{2}%n%F{5}] %F{3}%3~ ${vcs_info_msg_0_}%f%# '

Obviamente, las dos últimas líneas están ahí para demostración. Necesitas llamar a vcs_info desde tu función precmd. Una vez hecho esto, necesitas un '${vcs_info_msg_0_}' *entre comillas simples* en tu prompt.

Para poder usar '${vcs_info_msg_0_}' directamente en tu prompt de esta manera, necesitarás tener la opción PROMPT_SUBST habilitada.

Eso significa que la detección de estos sistemas se omite *completamente*. No se pierde tiempo.

Configuración

La función vcs_info se puede configurar a través de zstyle.

Primero, el contexto en el que estamos trabajando:

:vcs_info:cadena-vcs:contexto-usuario:nombre-raiz-repo
cadena-vcs
es uno de: git, git-svn, git-p4, hg, hg-git, hg-hgsubversion, hg-hgsvn, darcs, bzr, cdv, mtn, svn, cvs, svk, tla, p4 o fossil. A esto le sigue `.quilt-modo-quilt' en modo Quilt (ver Soporte de Quilt para detalles) y `+nombre-gancho' mientras los ganchos están activos (ver Ganchos en vcs_info para detalles).

Actualmente, los ganchos en modo quilt no agregan la información `.quilt-modo-quilt'. Esto puede cambiar en el futuro.

contexto-usuario
es una cadena configurable libremente, asignable por el usuario como primer argumento a vcs_info (ver su descripción abajo).
nombre-raiz-repo
es el nombre de un repositorio en el que deseas que coincida un estilo. Por lo tanto, si deseas una configuración específica para /usr/src/zsh, siendo este un checkout de CVS, puedes establecer nombre-raiz-repo a zsh para que así sea.

Hay tres valores especiales para cadena-vcs: El primero se llama -init-, que está en efecto mientras no se haya tomado una decisión sobre qué backend de VCS usar. El segundo es -preinit-; se usa *antes* de ejecutar vcs_info, al inicializar las variables de exportación de datos. El tercer valor especial es formats y es utilizado por vcs_info_lastmsg para buscar sus estilos.

El valor inicial de nombre-raiz-repo es -all- y se reemplaza con el nombre real, tan pronto como se conozca. Solo usa esta parte del contexto para definir los estilos formats, actionformats o branchformat, ya que está garantizado que nombre-raiz-repo se configura correctamente solo para estos. Para todos los demás estilos, simplemente usa '*' en su lugar.

Hay dos valores predefinidos para contexto-usuario:

default
el que se usa si no se especifica ninguno
command
usado por vcs_info_lastmsg para buscar sus estilos

Puedes, por supuesto, usar ':vcs_info:*' para que coincida con todos los VCS en todos los contextos de usuario a la vez.

Esta es una descripción de todos los estilos que se buscan.

formats
Una lista de formatos, usada cuando actionformats no se usa (que es la mayor parte del tiempo).
actionformats
Una lista de formatos, usada si hay una acción especial en curso en tu repositorio actual; como un rebase interactivo o un conflicto de fusión.
branchformat
Algunos backends reemplazan %b en los estilos formats y actionformats anteriores, no solo con un nombre de rama sino también con un número de revisión. Este estilo te permite modificar cómo debe verse esa cadena.
nvcsformats
Estos "formatos" se establecen cuando no hemos detectado un sistema de control de versiones para el directorio actual o vcs_info fue deshabilitado. Esto es útil si quieres que vcs_info tome el control completo de la generación de tu prompt. Harías algo como PS1='${vcs_info_msg_0_}' para lograrlo.
hgrevformat
hg usa tanto un hash como un número de revisión para referenciar un cambio específico en un repositorio. Con este estilo puedes formatear la cadena de revisión (ver branchformat) para incluir uno o ambos. Solo es útil cuando get-revision es verdadero. Nota, la identificación de revisión completa de 40 caracteres no está disponible (excepto al usar la opción use-simple) porque ejecutar hg más de una vez por prompt es demasiado lento; puedes personalizar este comportamiento usando ganchos.
max-exports
Define el número máximo de variables vcs_info_msg_*_ que vcs_info establecerá.
enable
Una lista de backends que deseas usar. Verificado en el contexto -init-. Si esta lista contiene un elemento llamado NONE, ningún backend se utiliza y vcs_info no hará nada. Si esta lista contiene ALL, vcs_info usará todos los backends conocidos. Solo con ALL en enable tendrá algún efecto el estilo disable. ALL y NONE no distinguen mayúsculas de minúsculas.
disable
Una lista de VCS que no deseas que vcs_info pruebe para repositorios (verificado también en el contexto -init-). Solo se usa si enable contiene ALL.
disable-patterns
Una lista de patrones que se verifican contra $PWD. Si un patrón coincide, vcs_info se deshabilitará. Este estilo se verifica en el contexto :vcs_info:-init-:*:-all-.

Por ejemplo, si ~/.zsh es un directorio bajo control de versiones, en el cual no deseas que vcs_info esté activo, haz:

zstyle ':vcs_info:*' disable-patterns "${(b)HOME}/.zsh(|/*)"
use-quilt
Si está habilitado, el código de soporte de quilt está activo en modo `addon'. Ver Soporte de Quilt para detalles.
quilt-standalone
Si está habilitado, se intenta la detección en modo `standalone' si no hay un VCS activo en un directorio dado. Ver Soporte de Quilt para detalles.
quilt-patch-dir
Sobrescribe el valor de la variable de entorno $QUILT_PATCHES. Ver Soporte de Quilt para detalles.
quiltcommand
Cuando se llama a quilt en el soporte de quilt, el valor de este estilo se utiliza como el nombre del comando.
check-for-changes
Si está habilitado, este estilo hace que las secuencias de escape de formato %c y %u muestren cuándo el directorio de trabajo tiene cambios no confirmados. Las cadenas mostradas por estas secuencias de escape se pueden controlar a través de los estilos stagedstr y unstagedstr. Los únicos backends que actualmente soportan esta opción son git, hg, y bzr (estos dos últimos solo soportan no confirmados).

Para que este estilo se evalúe con el backend hg, el estilo get-revision debe estar establecido y el estilo use-simple debe estar desestablecido. Este último es el predeterminado; el primero no lo es.

Con el backend bzr, los *checkouts ligeros* solo honran este estilo si el estilo use-server está establecido.

Nota, las acciones tomadas si este estilo está habilitado son potencialmente costosas (es decir, pueden ser lentas, dependiendo de cuán grande sea el repositorio actual). Por lo tanto, está deshabilitado por defecto.

check-for-staged-changes
Este estilo es
como check-for-changes, pero nunca verifica los archivos del árbol de trabajo, solo los metadatos en el directorio .${vcs}. Por lo tanto, este estilo inicializa solo la secuencia de escape %c (con stagedstr) pero no la secuencia de escape %u. Este estilo es más rápido que check-for-changes.

En el backend git, este estilo verifica los cambios en el índice. Otros backends no implementan actualmente este estilo.

Este estilo está deshabilitado por defecto.

stagedstr
Esta cadena se utilizará en la secuencia de escape %c si hay cambios preparados en el repositorio.
unstagedstr
Esta cadena se utilizará en la secuencia de escape %u si hay cambios no preparados en el repositorio.
command
Este estilo hace que vcs_info utilice la cadena proporcionada como comando para usar como binario del VCS. Tenga en cuenta que configurar esto en ':vcs_info:*' no es una buena idea.

Si el valor de este estilo está vacío (que es el valor por defecto), el nombre del binario utilizado es el nombre del backend en uso (por ejemplo, se utiliza svn en un repositorio svn).

La parte repo-root-name en el contexto es siempre -all- por defecto cuando se busca este estilo.

Por ejemplo, este estilo se puede utilizar para usar binarios de directorios de instalación no predeterminados. Suponga que git está instalado en /usr/bin pero su administrador del sistema instaló una versión más reciente en /usr/local/bin. En lugar de cambiar el orden de su parámetro $PATH, puede hacer esto:

zstyle ':vcs_info:git:*:-all-' command /usr/local/bin/git
use-server
Esto lo utiliza el backend Perforce (p4) para decidir si debe contactar al servidor Perforce para averiguar si un directorio es gestionado por Perforce. Esta es la única forma confiable de hacerlo, pero corre el riesgo de una demora si no se puede encontrar el nombre del servidor. Si no se puede contactar al servidor (más específicamente, el par host:port que describe el servidor), su nombre se coloca en la matriz asociativa vcs_info_p4_dead_servers y no se vuelve a contactar durante la sesión hasta que se elimine manualmente. Si no establece este estilo, el backend p4 solo es utilizable si ha establecido la variable de entorno P4CONFIG en un nombre de archivo y tiene archivos correspondientes en los directorios raíz de cada cliente Perforce. Consulte los comentarios en la función VCS_INFO_detect_p4 para obtener más detalles.

El backend Bazaar (bzr) utiliza esto para permitir el contacto con el servidor sobre clonas ligeras, consulte el estilo check-for-changes.

use-simple
Si hay dos formas diferentes de recopilar información, puede seleccionar la más simple estableciendo este estilo en verdadero; el valor por defecto es utilizar el código no tan simple, que potencialmente es mucho más lento, pero podría ser más preciso en todos los casos posibles. Este estilo es utilizado por los backends bzr, hg y git. En el caso de hg, invocará el programa externo hexdump para analizar el archivo de caché binario dirstate; este método no devolverá el número de revisión local.
get-revision
Si se establece en verdadero, vcs_info se esfuerza por determinar la revisión del árbol de trabajo de un repositorio (actualmente para los backends git y hg, donde este tipo de información no siempre es vital). Para git, el valor hash del commit actualmente seleccionado está disponible a través de la expansión %i. Con hg, el número de revisión local y el hash global correspondiente están disponibles a través de %i.
get-mq
Si se establece en verdadero, el backend hg buscará un directorio de parches de Mercurial Queue (mq). La información estará disponible a través del reemplazo `%m'.
get-bookmarks
Si se establece en verdadero, el backend hg intentará obtener una lista de los marcadores actuales. Estarán disponibles a través del reemplazo `%m'.

El valor por defecto es generar una lista separada por comas de todos los nombres de marcadores que se refieren a la revisión actualmente seleccionada. Si un marcador está activo, su nombre se sufija con un asterisco y se coloca primero en la lista.

use-prompt-escapes
Determina si asumimos que la cadena ensamblada de vcs_info incluye secuencias de escape de prompt. (Usado por vcs_info_lastmsg.)
debug

En los formats y actionformats normales, se realizan los siguientes reemplazos:

%s
El VCS en uso (git, hg, svn, etc.).
%b
Información sobre la rama actual.
%a
Un identificador que describe la acción. Solo tiene sentido en actionformats.
%i
El número de revisión o identificador actual. Para hg, el estilo hgrevformat puede usarse para personalizar la salida.
%c
La cadena del estilo stagedstr si hay cambios preparados en el repositorio.
%u
La cadena del estilo unstagedstr si hay cambios no preparados en el repositorio.
%R
El directorio base del repositorio.
%r
El nombre del repositorio. Si %R es /foo/bar/repoXY, %r es repoXY.
%S
Un subdirectorio dentro de un repositorio. Si $PWD es /foo/bar/repoXY/beer/tasty, %S es beer/tasty.
%m
Un reemplazo de "miscelánea". Queda a discreción del backend decidir a qué se expande este reemplazo.

Los backends hg y git utilizan esta expansión para mostrar información de parches. hg obtiene información de parches de las extensiones mq; git de operaciones rebase y cherry-pick en progreso y de la extensión stgit. Los estilos patch-format y nopatch-format controlan la cadena generada. El primero se usa cuando se ha aplicado al menos un parche de la cola de parches, y el último en caso contrario.

El backend hg muestra información de marcadores en esta expansión (además de la información de mq). Consulte los estilos get-mq y get-bookmarks. Ambos o

Si ambos estilos están habilitados, ambas cadenas resultantes se mostrarán separadas por un punto y coma (que actualmente no se puede personalizar).

%Q

Consulte Soporte de Quilt a continuación para obtener más detalles.

%b
El nombre de la rama. Para hg, el nombre de la rama puede incluir un nombre de tema.
%r
El número de revisión actual o el estilo hgrevformat para hg.

El número de revisión local actual.
%h
El identificador de revisión global actual.

En patch-format y nopatch-format se realizan estos reemplazos:

%p
El nombre del parche aplicado de nivel superior; puede ser anulado por el hook applied-string.
%u
El número de parches no aplicados; puede ser anulado por el hook unapplied-string.
%n
El número de parches aplicados.
%c
El número de parches no aplicados.
%a
El número total de parches (%a = %n + %c).
%g
Los nombres de los guards de mq activos (backend hg).
%G
El número de guards de mq activos (backend hg).

No todos los backends de VCS tienen que admitir todos los reemplazos. Para nvcsformats no se realiza ningún reemplazo, es solo una cadena.

Rarezas

Si desea utilizar la expansión de prompt %b (negrita apagada) en formats, que expande %b en sí, use %%b. Esto hará que la expansión de vcs_info reemplace %%b por %b, de modo que el mecanismo de expansión de prompt de zsh pueda manejarlo. De manera similar, para pasar %b desde branchformat, use %%%%b. Lamentamos este inconveniente, pero no se puede evitar fácilmente. Afortunadamente, no nos topamos con muchas expansiones de prompt y esto solo necesita hacerse para esas.

Cuando uno de los hooks gen-applied-string, gen-unapplied-string y set-patch-format está definido, la aplicación del escape de % (`foo=${foo//'%'/%%}') a los valores interpolados para su uso en el prompt es responsabilidad de esos hooks (conjuntamente); cuando ninguno de esos hooks está definido, vcs_info maneja el escape por sí mismo. Lamentamos este acoplamiento, pero fue necesario por compatibilidad con versiones anteriores.

Soporte de Quilt

Quilt no es un sistema de control de versiones, por lo tanto, no está implementado como un backend. Puede ayudar a realizar un seguimiento de una serie de parches. La gente lo usa para mantener un conjunto de cambios que desean usar sobre paquetes de software (lo que está estrechamente integrado en el proceso de compilación de paquetes; el proyecto Debian hace esto para una gran cantidad de paquetes). Quilt también puede ayudar a los desarrolladores individuales a realizar un seguimiento de sus propios parches sobre sistemas de control de versiones reales.

La integración de vcs_info intenta admitir ambas formas de usar quilt teniendo dos modos de operación ligeramente diferentes: modo `addon' y modo `standalone').

La integración de Quilt está desactivada por defecto; para habilitarla, establezca el estilo use-quilt y agregue %Q a su estilo formats o actionformats:

zstyle ':vcs_info:*' use-quilt true

Los estilos buscados en el código de soporte de Quilt incluyen `.quilt-quilt-mode' en la parte de vcs-string del contexto, donde quilt-mode es addon o standalone. Ejemplo: :vcs_info:git.quilt-addon:default:nombre-raíz-repo.

Para que el modo `addon' se active, vcs_info debe haber detectado previamente un sistema de control de versiones real que controle el directorio. Si ese es el caso, se debe encontrar un directorio que contenga los parches de quilt. Ese directorio es configurable a través de la variable de entorno `QUILT_PATCHES'. Si esa variable existe, se usa su valor; de lo contrario, se asume el valor `patches'. El valor de $QUILT_PATCHES puede ser anulado usando el estilo `quilt-patch-dir'. (Nota: puede usar vcs_info para mantener correcto el valor de $QUILT_PATCHES todo el tiempo a través del hook post-quilt).

Cuando se encuentra el directorio en cuestión, se asume que quilt está activo. Para recopilar más información, vcs_info busca un directorio llamado `.pc'; Quilt usa ese directorio para rastrear su estado actual. Si este directorio no existe, sabemos que quilt no ha hecho nada al directorio de trabajo (es decir, aún no se han aplicado parches).

Si se aplican parches, vcs_info intentará averiguar cuáles. Si desea saber qué parches de una serie aún no se han aplicado, necesita activar el estilo get-unapplied en el contexto apropiado.

vcs_info permite un control muy detallado sobre cómo se presenta la información recopilada (consulte las secciones Configuración y Hooks en vcs_info), todo lo cual se documenta a continuación. Tenga en cuenta que existen varios otros sistemas de seguimiento de parches que funcionan sobre un cierto sistema de control de versiones (como stgit para git, o mq para hg); la configuración para sistemas como esos generalmente se configura de la misma manera que el soporte de quilt.

Si el soporte de quilt está funcionando en modo `addon', la cadena producida está disponible como un reemplazo de formato simple (%Q para ser precisos), que se puede usar en formats y actionformats; consulte a continuación para obtener más detalles).

Si, por otro lado, el código de soporte está funcionando en modo `standalone', vcs_info pretenderá como si quilt fuera un sistema de control de versiones real. Esto significa que el identificador del sistema de control de versiones (que de otro modo sería algo como `svn' o `cvs') se establecerá en `-quilt-'. Esto tiene implicaciones en el contexto de estilo utilizado donde este identificador es el segundo elemento. vcs_info habrá completado un valor adecuado para el directorio raíz del "repositorio" y la cadena que contiene la información sobre el estado de quilt estará disponible como el reemplazo `misc' (y %Q para compatibilidad con el modo `addon').

Lo que queda por discutir es cómo se detecta el modo `standalone'. La detección en sí es una serie de búsquedas de directorios. Puede tener esta detección habilitada todo el tiempo en todos los directorios que no estén bajo control de versiones. Si sabe que solo hay un conjunto limitado de árboles donde le gustaría que vcs_info intentara buscar Quilt en modo `standalone' para minimizar la cantidad de búsqueda en cada llamada a vcs_info, hay varias formas de hacerlo:

Esencialmente, la detección del modo `standalone' está controlada por un estilo llamado `quilt-standalone'. Es un estilo de cadena y su valor puede tener diferentes efectos. Los valores más simples son: `always' para ejecutar la detección cada vez que se ejecuta vcs_info, y `never' para desactivar la detección por completo.

Si el valor de quilt-standalone es algo más, se interpreta de manera diferente. Si el valor es el nombre de una variable escalar, se verifica el valor de esa variable y ese valor se utiliza de la misma manera `always'/`never' que se describió anteriormente.

Si el valor de quilt-standalone es un array, los elementos de ese array se utilizan como nombres de directorio bajo los cuales desea que la detección esté activa.

Si quilt-standalone es un array asociativo, las claves se toman como nombres de directorio bajo los cuales desea que la detección esté activa, pero solo si el valor correspondiente es la cadena `true'.

Por último, pero no menos importante, si el valor de quilt-standalone es el nombre de una función, la función se llama sin argumentos y el valor de retorno decide si la detección debe estar activa. Un valor de retorno `0' es verdadero; un valor de retorno distinto de cero se interpreta como falso.

Tenga en cuenta que si existe una función y una variable con el nombre quilt-standalone, la función tendrá prioridad.

Este hook se utiliza cuando la funcionalidad de quilt de vcs_info está activa en modo "addon" (quilt utilizado sobre un sistema de control de versiones real). Se activa justo antes de que se realice cualquier acción específica de quilt.

set-patch-format
Este hook se utiliza para controlar algunas de las expansiones posibles en los estilos patch-format y nopatch-format con sistemas de colas de parches como quilt, mqueue y similares.

Este hook se utiliza en los backends git, hg y quilt.

El hook permite controlar la expansión %p (${hook_com[applied]}) y %u (${hook_com[unapplied]}) en todos los backends que utilizan el hook. Con el backend mercurial, además de eso se puede controlar la expansión %g (${hook_com[guards]}).

Si ret se establece a un valor distinto de cero, la cadena en ${hook_com[patch-replace]} se utilizará sin cambios en lugar de un formato expandido de patch-format o nopatch-format.

Este hook, junto con los hooks gen-applied-string o gen-unapplied-string si están definidos, es responsable de escapar con % el valor final de patch-format para su uso en el prompt. (Ver la sección Oddities.)

El backend quilt pasa a este hook las entradas ${hook_com[quilt-patches-dir]} y, si se ha determinado, ${hook_com[quilt-pc-dir]}.

set-message
Se llama cada vez antes de que se establezca un mensaje `vcs_info_msg_N_'. Toma dos argumentos; el primero es el `N' en el nombre de la variable del mensaje, el segundo es el configurado actualmente formats o actionformats.

Hay una serie de claves `hook_com' que se utilizan aquí: `action', `branch', `base', `base-name', `subdir', `staged', `unstaged', `revision', `misc', `vcs' y una entrada `miscN' para cada campo de datos específico del backend (N comenzando desde cero). Se establecen a los valores calculados hasta el momento por vcs_info y cualquier cambio se utilizará directamente cuando se realice el reemplazo real.

Dado que este hook se activa varias veces (una vez por cada formats o actionformats configurado), cada una de las claves `hook_com' mencionadas anteriormente (excepto las entradas miscN) tiene una contraparte `_orig', por lo que incluso si ha cambiado un valor a su gusto, aún puede obtener el valor original en la siguiente ejecución. Cambiar los valores `_orig' probablemente no sea una buena idea.

Si ret se establece a un valor distinto de cero, la cadena en ${hook_com[message]} se utilizará sin cambios como mensaje por vcs_info.

Ejemplos

No usar vcs_info en absoluto (aunque esté en tu prompt):

zstyle ':vcs_info:*' enable NONE

Deshabilitar los backends para bzr y svk:

zstyle ':vcs_info:*' disable bzr svk

Deshabilitar todo *excepto* bzr y svk:

zstyle ':vcs_info:*' enable bzr svk

Proporcionar formatos especiales para git:

zstyle ':vcs_info:git:*' formats       ' GIT, BABY! [%b]'
zstyle ':vcs_info:git:*' actionformats ' GIT ACTION! [%b|%a]'

Todas las expansiones %x en todo tipo de formatos (formats, actionformats, branchformat, etc.) se realizan utilizando el comando incorporado `zformat' del módulo `zsh/zutil'. Eso significa que puedes hacer con estos elementos %x todo lo que zformat soporta. En particular, si quieres que algo muy largo tenga un ancho fijo, como un hash en un formato de rama mercurial, puedes hacer esto: %12.12i. Eso reducirá el hash de 40 caracteres a sus 12 caracteres iniciales. La forma es en realidad `%min.maxx'. Hay más posibilidades. Consulta la sección `The zsh/zutil Module' en zshmodules(1) para más detalles.

Usar el backend bzr más rápido

zstyle ':vcs_info:bzr:*' use-simple true

Si usas use-simple, por favor informa si hace `lo correcto[tm]`.

Mostrar el número de revisión en amarillo para bzr y svn:

zstyle ':vcs_info:(svn|bzr):*' \ 
       branchformat '%b%%F{yellow}:%r'

El doble signo de porcentaje se explica en la sección Oddities.

Alternativamente, se pueden usar directamente los códigos de color:

zstyle ':vcs_info:(svn|bzr):*' \ 
       branchformat '%b%{'${fg[yellow]}'%}:%r'

Normalmente, cuando una variable se interpola en una cadena de formato, la variable debe escaparse con %. En este ejemplo, omitimos eso porque asumimos que el valor de ${fg[yellow]} no contiene ningún signo de %.

Asegúrate de encerrar los códigos de color en %{...%} si quieres usar la cadena proporcionada por vcs_info en los prompts.

Así es como se imprime la información de VCS como un comando (no en un prompt):

vcsi() { vcs_info interactive; vcs_info_lastmsg }

De esta manera, incluso puedes definir diferentes formatos para la salida a través de vcs_info_lastmsg en el espacio de nombres ':vcs_info:*:interactive:*'.

Ahora, como prometimos, algo de código que usa hooks: digamos que te gustaría reemplazar la cadena `svn' por `subversion' en el reemplazo de %s de formats de vcs_info.

Primero, le diremos a vcs_info que llame a una función al poblar las variables de mensaje con la información recopilada:

zstyle ':vcs_info:*+set-message:*' hooks svn2subversion

No sucede nada. Lo cual es razonable, ya que aún no hemos definido la función real. Para ver qué está tratando de hacer el subsistema de hooks, habilita el estilo `debug':

zstyle ':vcs_info:*+*:*' debug true

Eso debería darte una idea de lo que está sucediendo. Específicamente, la función que buscamos es `+vi-svn2subversion'. Nota el prefijo `+vi-'. Así que todo está en orden, tal como se documenta. Cuando hayas terminado de revisar la salida de depuración, desactívala de nuevo:

zstyle ':vcs_info:*+*:*' debug false

Ahora, definamos la función:


function +vi-svn2subversion() {
    [[ ${hook_com[vcs_orig]} == svn ]] && hook_com[vcs]=subversion
}

Lo suficientemente simple. Y podría haber sido aún más simple, si solo hubiéramos registrado nuestra función en un contexto menos genérico. Si lo hacemos solo en el contexto del backend `svn', no necesitamos probar cuál es el backend activo:

zstyle ':vcs_info:svn+set-message:*' hooks svn2subversion

function +vi-svn2subversion() {
    hook_com[vcs]=subversion
}

Y finalmente un ejemplo un poco más elaborado, que utiliza un hook para crear una cadena de marcadores personalizada para el backend hg.

De nuevo, empezamos registrando una función:

zstyle ':vcs_info:hg+gen-hg-bookmark-string:*' hooks hgbookmarks

Y luego definimos la función `+vi-hgbookmarks':


function +vi-hgbookmarks() {
    # El valor predeterminado es conectar todos los nombres de marcadores por
    # comas. Esto mezcla un poco las cosas.
    # Imagina que hay un tipo de marcadores que es
    # especial para ti. Digamos, porque es *tu* trabajo.
    # Esos marcadores siempre se ven así: "sh/*"
    # (porque tus iniciales son sh, por ejemplo).
    # Esto hace que la cadena de marcadores use solo esos
    # marcadores. Si hay más de uno, concatena
    # usandocomas.
    # Los marcadores devueltos por `hg' están disponibles en
    # los parámetros posicionales de la función.
    local s="${(Mj:,:)@:#sh/*}"
    # Ahora, la comunicación con el código que llama
    # a las funciones del hook se realiza a través del hash
    # hook_com[]. La clave en la que busca el hook `gen-hg-bookmark-string'
    # es `hg-bookmark-string'. Así que:
    hook_com[hg-bookmark-string]=$s
    # Y para señalar que queremos usar la cadena que
    # acabamos de generar, establecemos la variable especial `ret' a
    # algo distinto de cero predeterminado:
    ret=1
    return 0
}

Algunos ejemplos más largos y fragmentos de código que podrían ser útiles están disponibles en el archivo de ejemplos ubicado en Misc/vcs_info-examples en el directorio fuente de Zsh.

promptinit

Selección de Tema

Usa el comando prompt para seleccionar tu tema preferido. Este comando puede ser añadido a tu .zshrc después de la llamada a promptinit para iniciar zsh con un tema ya seleccionado.

prompt [ -c | -l ]
prompt [ -p | -h ] [ tema ... ]
prompt [ -s ] tema [ arg ... ]
Establece o examina el tema del prompt. Sin opciones y con un argumento tema, el tema con ese nombre se establece como el tema actual. Los temas disponibles se determinan en tiempo de ejecución; usa la opción -l para ver una lista. El tema especial `random' selecciona al azar uno de los temas disponibles y establece tu prompt a ese.

En algunos casos, el tema puede ser modificado por uno o más argumentos, que deben proporcionarse después del nombre del tema. Consulta la ayuda de cada tema para obtener descripciones de estos argumentos.

Opciones:

-c
Muestra el tema actualmente seleccionado y sus parámetros, si los hay.
-l
Lista todos los temas de prompt disponibles.
-p
Previsualiza el tema nombrado por tema, o todos los temas si no se proporciona tema.
-h
Muestra la ayuda para el tema nombrado por tema, o para la función prompt si no se proporciona tema.
-s
Establece tema como el tema actual y guarda el estado.
prompt_tema_setup
Cada tema disponible tiene una función de configuración que es llamada por la función prompt para instalar ese tema. Esta función puede definir otras funciones según sea necesario para mantener el prompt, incluyendo funciones utilizadas para previsualizar el prompt o proporcionar ayuda para su uso. Normalmente no deberías llamar directamente a la función de configuración de un tema.

Temas de Utilidad

prompt off
El tema `off' establece todas las variables del prompt a valores mínimos sin efectos especiales.
prompt default
El tema `default' establece todas las variables del prompt al mismo estado que si un zsh interactivo se iniciara sin archivos de inicialización.
prompt restore
El tema especial `restore' borra todas las configuraciones de tema y restablece las variables del prompt a su estado anterior a la primera vez que se ejecutó la función `prompt', siempre que cada tema haya definido correctamente su limpieza (ver más abajo).

Ten en cuenta que puedes deshacer `prompt off' y `prompt default' con `prompt restore', pero una segunda restauración no deshace la primera.

Escribiendo Temas

El primer paso para añadir tu propio tema es elegir un nombre para él y crear un archivo `prompt_nombre_setup' en un directorio de tu fpath, como ~/myfns en el ejemplo anterior. El archivo debe contener como mínimo asignaciones para las variables del prompt que tu tema desea modificar. Por convención, los temas usan PS1, PS2, RPS1, etc., en lugar de los más largos PROMPT y RPROMPT.

El archivo se carga automáticamente como una función en el contexto del shell actual, por lo que puede contener cualquier comando necesario para personalizar tu tema, incluyendo la definición de funciones adicionales. Para facilitar algunas tareas complejas, tu función de configuración también puede hacer cualquiera de lo siguiente:

Asignar prompt_opts
El array prompt_opts puede ser asignado con cualquiera de "bang", "cr", "percent", "sp", y/o "subst" como valores. Los setopts correspondientes (promptbang, etc.) se activan, todos los demás opciones relacionadas con el prompt se desactivan. El array prompt_opts conserva los setopts incluso más allá del ámbito de localoptions, si tu función lo necesita.
Modificar hooks
Se recomienda el uso de add-zsh-hook y add-zle-hook-widget (ver la sección Manipulación de Funciones Hook más arriba). Todos los hooks que siguen el patrón de nombres prompt_tema_hook se eliminan automáticamente cuando el tema del prompt cambia o se deshabilita.
Declarar limpieza
Si tu función realiza algún otro cambio que deba deshacerse cuando el tema se desactive, tu función de configuración puede llamar a
prompt_cleanup comando

donde comando debe estar correctamente entrecomillado. Si tu tema se desactiva o es reemplazado por otro, comando se ejecuta con eval. Puedes declarar más de un hook de limpieza.

Definir previsualización
Define o carga automáticamente una función prompt_nombre_preview para mostrar una versión simulada de tu prompt. Un simple previsualizador predeterminado es definido por promptinit para los temas que no definen el suyo propio. Esta función de previsualización es llamada por `prompt -p'.
Proporcionar ayuda
Define o carga automáticamente una función prompt_nombre_help para mostrar documentación o texto de ayuda para tu tema. Esta función de ayuda es llamada por `prompt -h'.

FUNCIONES ZLE

Widgets

Todas estas funciones implementan widgets ZLE definidos por el usuario (ver zshzle(1)) que pueden ser enlazados a secuencias de teclas en shells interactivos. Para usarlos, tu .zshrc debería contener líneas de la forma

autoload función
zle -N función

seguido de un comando bindkey apropiado para asociar la función con una secuencia de teclas. Se describen enlaces sugeridos a continuación.

funciones de palabra estilo bash
Si buscas funciones para implementar el movimiento sobre y edición de palabras al estilo de bash, donde solo los caracteres alfanuméricos se consideran caracteres de palabra, puedes usar las funciones descritas en la siguiente sección. Lo siguiente es suficiente:
autoload -U select-word-style
select-word-style bash
forward-word-match, backward-word-match
kill-word-match, backward-kill-word-match
transpose-words-match, capitalize-word-match
up-case-word-match, down-case-word-match
delete-whole-word-match, select-word-match
select-word-style, match-word-context, match-words-by-style
Las primeras ocho funciones `-match' son reemplazos directos de los widgets incorporados sin el sufijo. Por defecto, se comportan de manera similar. Sin embargo, mediante el uso de estilos y la función select-word-style, la forma en que se emparejan las palabras puede alterarse. select-word-match está destinado a ser utilizado como un objeto de texto en modo vi, pero con estilos de palabra personalizados. A modo de comparación, los widgets descritos en zshzle(1) bajo Objetos de Texto utilizan definiciones fijas de palabras, compatibles con el editor vim.

La forma más sencilla de configurar las funciones es usar select-word-style, que puede ser llamado como una función normal con el argumento apropiado, o invocado como un widget definido por el usuario que preguntará por el primer carácter del estilo de palabra a utilizar. La primera vez que se invoque, las primeras ocho funciones -match reemplazarán automáticamente las versiones incorporadas, por lo que no necesitan ser cargadas explícitamente.

Los estilos de palabra disponibles son los siguientes. Solo se examina el primer carácter.

bash
Los caracteres de palabra son solo caracteres alfanuméricos.
normal
Como en la operación normal del shell: los caracteres de palabra son caracteres alfanuméricos más cualquier carácter presente en la cadena dada por el parámetro $WORDCHARS.
shell
Las palabras son argumentos de comandos de shell completos, posiblemente incluyendo cadenas entrecomilladas completas, o cualquier token especial para el shell.
whitespace
Las palabras son cualquier conjunto de caracteres delimitados por espacios en blanco.
default
Restablece la configuración predeterminada; esto suele ser lo mismo que `normal'.

Todos los estilos excepto `default' pueden ser introducidos como un carácter en mayúscula, lo que tiene el mismo efecto pero con la coincidencia de subpalabras activada. En este caso, las palabras con caracteres en mayúscula se tratan de forma especial: cada secuencia separada de caracteres en mayúscula, o un carácter en mayúscula seguido de cualquier número de otros caracteres, se considera una palabra. El estilo subword-range puede proporcionar un rango de caracteres alternativo al predeterminado `[:upper:]'; el valor del estilo se trata como el contenido de un patrón `[...]' (ten en cuenta que los corchetes exteriores no deben proporcionarse, solo los que rodean rangos con nombre).

Se puede obtener un mayor control utilizando el comando zstyle, como se describe en zshmodules(1). Cada estilo se busca en el contexto :zle:widget donde widget es el nombre del widget definido por el usuario, no el nombre de la función que lo implementa, por lo que en el caso de las definiciones proporcionadas por select-word-style los contextos apropiados son :zle:forward-word, y así sucesivamente. La función select-word-style siempre define estilos para el contexto `:zle:*' que pueden ser anulados por patrones más específicos (más largos) así como contextos explícitos.

El estilo word-style especifica

normal
Utiliza las reglas estándar del shell, es decir, alfanuméricos y $WORDCHARS, a menos que se anulen con los estilos word-chars o word-class.
specified
Similar a normal, pero *solo* los caracteres especificados, y no los alfanuméricos, se consideran caracteres de palabra.
unspecified
La negación de especificado. Los caracteres dados son aquellos que *no* serán considerados parte de una palabra.
shell
Las palabras se obtienen utilizando las reglas sintácticas para generar argumentos de comandos de shell. Además, los tokens especiales que nunca son argumentos de comando, como `()', también se tratan como palabras.
whitespace
Las palabras son cadenas de caracteres delimitadas por espacios en blanco.

Las tres primeras de estas reglas suelen utilizar $WORDCHARS, pero el valor del parámetro puede ser anulado por el estilo word-chars, que funciona exactamente de la misma manera que $WORDCHARS. Además, el estilo word-class utiliza la sintaxis de clases de caracteres para agrupar caracteres y tiene precedencia sobre word-chars si ambos están establecidos. El estilo word-class no incluye los corchetes circundantes de la clase de caracteres; por ejemplo, `-:[:alnum:]' es una word-class válida para incluir todos los alfanuméricos más los caracteres `-' y `:'. Tenga cuidado al incluir `]', `^' y `-', ya que son especiales dentro de las clases de caracteres.

word-style también puede tener `-subword` añadido a su valor para activar la coincidencia de subpalabras, como se describe anteriormente.

El estilo skip-chars es principalmente útil para transpose-words y funciones similares. Si está establecido, proporciona un recuento de caracteres a partir de la posición del cursor que no se considerarán parte de la palabra y se tratarán como espacios, independientemente de lo que sean en realidad. Por ejemplo, si

zstyle ':zle:transpose-words' skip-chars 1

se ha establecido, y se llama a transpose-words-match con el cursor en la *X* de foo*X***bar, donde *X* puede ser cualquier carácter, entonces la expresión resultante es bar*X***foo.

Se puede obtener un control más detallado estableciendo el estilo word-context a una matriz de pares de entradas. Cada par de entradas consiste en un *patrón* y un *subcontexto*. El argumento de shell en el que se encuentra el cursor se compara con cada *patrón* en orden hasta que uno coincide; si lo hace, el contexto se amplía con dos puntos y el *subcontexto* correspondiente. Tenga en cuenta que la prueba se realiza contra la palabra original en la línea, sin eliminar las comillas. Se realiza un manejo especial entre palabras: se examina el contexto actual y si contiene la cadena between, la palabra se establece en un solo espacio; si no, si contiene la cadena back, se considera la palabra antes del cursor; si no, se considera la palabra después del cursor. Algunos ejemplos se proporcionan a continuación.

El estilo skip-whitespace-first solo se utiliza con el widget forward-word. Si está establecido en verdadero, entonces forward-word omite cualquier carácter no de palabra, seguido de cualquier carácter no de palabra: esto es similar al comportamiento de otros widgets orientados a palabras, y también al utilizado por otros editores, sin embargo difiere del comportamiento estándar de zsh. Al utilizar select-word-style, el widget se establece en el contexto :zle:* a true si el estilo de palabra es bash y false en caso contrario. Puede ser anulado estableciéndolo en el contexto más específico :zle:forward-word*.

Es posible crear widgets con comportamiento específico definiendo un nuevo widget implementado por la función genérica apropiada, y luego estableciendo un estilo para el contexto del widget específico. Por ejemplo, lo siguiente define un widget backward-kill-space-word utilizando backward-kill-word-match, el widget genérico que implementa el comportamiento de backward-kill-word, y asegura que el nuevo widget siempre implementa el comportamiento delimitado por espacios.

zle -N backward-kill-space-word backward-kill-word-match
zstyle :zle:backward-kill-space-word word-style space

El widget backward-kill-space-word ahora puede enlazarse a una tecla.

Aquí hay algunos ejemplos adicionales del uso de los estilos, tomados de la interfaz simplificada en select-word-style:

zstyle ':zle:*' word-style standard
zstyle ':zle:*' word-chars ''

Implementa el manejo de palabras al estilo bash para todos los widgets, es decir, solo los alfanuméricos son caracteres de palabra; equivalente a establecer el parámetro WORDCHARS vacío para el contexto dado.

style ':zle:*kill*' word-style space

Utiliza palabras delimitadas por espacios para los widgets con la palabra `kill' en el nombre. Ni los estilos word-chars ni word-class se utilizan en este caso.

Aquí hay algunos ejemplos del uso del estilo word-context para extender el contexto.

zstyle ':zle:*' word-context \
       "*/*" filename "[[:space:]]" whitespace
zstyle ':zle:transpose-words:whitespace' word-style shell
zstyle ':zle:transpose-words:filename' word-style normal
zstyle ':zle:transpose-words:filename' word-chars ''

Esto proporciona dos formas diferentes de usar transpose-words dependiendo de si el cursor está en un espacio en blanco entre palabras o en un nombre de archivo, aquí cualquier palabra que contenga un /. En un espacio en blanco, se transpondrán argumentos completos según las reglas estándar del shell. En un nombre de archivo, solo se transpondrán los alfanuméricos. En otros lugares, las palabras se transpondrán utilizando el estilo predeterminado para :zle:transpose-words.

La coincidencia de palabras y todo el manejo de la configuración de zstyle se implementa en realidad mediante la función match-words-by-style. Esto se puede utilizar para crear nuevos widgets definidos por el usuario. La función que llama debe establecer el parámetro local curcontext a :zle:widget, crear el parámetro local matched_words y llamar a match-words-by-style sin argumentos. Al regresar, matched_words se establecerá en una matriz con los elementos: (1) el inicio de la línea (2) la palabra antes del cursor (3) cualquier carácter no de palabra entre esa palabra y el cursor (4) cualquier carácter no de palabra en la posición del cursor más cualquier carácter no de palabra restante antes de la siguiente palabra, incluidos todos los caracteres especificados por el estilo skip-chars, (5) la palabra en o después del cursor (6) cualquier carácter no de palabra después de esa palabra (7) el resto de la línea. Cualquiera de los elementos puede ser una cadena vacía; la función que llama debe probar esto para decidir si puede realizar su función.

Si la variable matched_words es definida por el llamante a match-words-by-style como una matriz asociativa (local -A matched_words), entonces los siete valores dados anteriormente deben recuperarse de ella como elementos llamados start, word-before-cursor, ws-before-cursor, ws-after-cursor, word-after-cursor, ws-after-word y end. Además, el elemento is-word-start es 1 si el cursor está en el inicio de una palabra o subpalabra, o en un espacio en blanco antes de ella (los casos se pueden distinguir probando el elemento ws-after-cursor) y 0 en caso contrario. Se recomienda esta forma para compatibilidad futura.

Es posible pasar opciones con argumentos a match-words-by-style para anular el uso de estilos. Las opciones son:

-w
word-style
-s
skip-chars
-c
word-class
-C
word-chars
-r
subword-range

Por ejemplo, match-words-by-style -w shell -c 0 puede usarse para extraer el argumento de comando alrededor del cursor.

El estilo word-context es implementado por la función match-word-context. Normalmente no debería ser necesario llamarla directamente.

bracketed-paste-magic
El widget bracketed-paste (ver la subsección `Misceláneo' en zshzle(1)) inserta el texto pegado literalmente en el búfer del editor en lugar de interpretarlo como pulsaciones de teclas. Esto deshabilita algunos usos comunes donde el widget de auto-inserción se reemplaza para realizar algún procesamiento adicional. Un ejemplo es el widget contribuido url-quote-magic descrito a continuación.

El widget bracketed-paste-magic está destinado a reemplazar a bracketed-paste con un envoltorio que re-habilita estas acciones de auto-inserción, y otras acciones según lo seleccionado por zstyles. Por lo tanto, este widget se instala con

autoload -Uz bracketed-paste-magic
zle -N bracketed-paste bracketed-paste-magic

Además de habilitar cierto procesamiento de widgets, bracketed-paste-magic intenta replicar bracketed-paste tan fielmente como sea posible.

Los siguientes zstyles se pueden establecer para controlar el procesamiento del texto pegado. Todos se buscan en el contexto `:bracketed-paste-magic'.

active-widgets
Una lista de patrones que coinciden con nombres de widgets que deben ser activados durante el pegado. Todas las demás secuencias de teclas se procesan como self-insert-unmeta. El valor predeterminado es `self-*' por lo que los widgets definidos por el usuario con ese prefijo están activos junto con el self-insert incorporado.

Si este estilo no está establecido (explícitamente eliminado) o está establecido en un valor vacío, ningún widget está activo y el texto pegado se inserta literalmente. Si el valor incluye `undefined-key', las secuencias desconocidas se descartan del texto pegado.

inactive-keys
Lo inverso de active-widgets, una lista de secuencias de teclas que siempre utilizan self-insert-unmeta incluso cuando están enlazadas a un widget activo. Tenga en cuenta que esta es una lista de secuencias de teclas literales, no de patrones.
paste-init
Una lista de nombres de funciones, llamadas en contexto de widget (pero no como widgets). Las funciones se llaman en orden hasta que una de ellas devuelve un estado distinto de cero. El parámetro `PASTED' contiene el estado inicial del texto pegado. Toda la demás Z
paste-init
A list of function names called in order until one returns non-zero. These functions are called before the pasted text has been processed by the active-widgets, but after it has been copied into `PASTED'. ZLE parameters such as `BUFFER' have their normal values and side-effects, and full history is available, so for example paste-init functions may move words from BUFFER into PASTED to make those words visible to the active-widgets.

A non-zero return from a paste-init function does not prevent the paste itself from proceeding.

Loading bracketed-paste-magic defines backward-extend-paste, a helper function for use in paste-init.

zstyle :bracketed-paste-magic paste-init \
       backward-extend-paste

When a paste would insert into the middle of a word or append text to a word already on the line, backward-extend-paste moves the prefix from LBUFFER into PASTED so that the active-widgets see the full word so far. This may be useful with url-quote-magic.

paste-finish
Another list of function names called in order until one returns non-zero. These functions are called after the pasted text has been processed by the active-widgets, but before it is inserted into `BUFFER'. ZLE parameters have their normal values and side-effects.

A non-zero return from a paste-finish function does not prevent the paste itself from proceeding.

Loading bracketed-paste-magic also defines quote-paste, a helper function for use in paste-finish.

zstyle :bracketed-paste-magic paste-finish \
       quote-paste
zstyle :bracketed-paste-magic:finish quote-style \
       qqq

When the pasted text is inserted into BUFFER, it is quoted per the quote-style value. To forcibly turn off the built-in numeric prefix quoting of bracketed-paste, use:

zstyle :bracketed-paste-magic:finish quote-style \
       none

Important: During active-widgets processing of the paste (after paste-init and before paste-finish), BUFFER starts empty and history is restricted, so cursor motions, etc., may not pass outside of the pasted content. Text assigned to BUFFER by the active widgets is copied back into PASTED before paste-finish.

copy-earlier-word
This widget works like a combination of insert-last-word and copy-prev-shell-word. Repeated invocations of the widget retrieve earlier words on the relevant history line. With a numeric argument N, insert the Nth word from the history line; N may be negative to count from the end of the line.

If insert-last-word has been used to retrieve the last word on a previous history line, repeated invocations will replace that word with earlier words from the same line.

Otherwise, the widget applies to words on the line currently being edited. The widget style can be set to the name of another widget that should be called to retrieve words. This widget must accept the same three arguments as insert-last-word.

cycle-completion-positions
After inserting an unambiguous string into the command line, the new function based completion system may know about multiple places in this string where characters are missing or differ from at least one of the possible matches. It will then place the cursor on the position it considers to be the most interesting one, i.e. the one where one can disambiguate between as many matches as possible with as little typing as possible.

This widget allows the cursor to be easily moved to the other interesting spots. It can be invoked repeatedly to cycle between all positions reported by the completion system.

delete-whole-word-match
This is another function which works like the -match functions described immediately above, i.e. using styles to decide the word boundaries. However, it is not a replacement for any existing function.

The basic behaviour is to delete the word around the cursor. There is no numeric argument handling; only the single word around the cursor is considered. If the widget contains the string kill, the removed text will be placed in the cutbuffer for future yanking. This can be obtained by defining kill-whole-word-match as follows:

zle -N kill-whole-word-match delete-whole-word-match

and then binding the widget kill-whole-word-match.

up-line-or-beginning-search, down-line-or-beginning-search
These widgets are similar to the builtin functions up-line-or-search and down-line-or-search: if in a multiline buffer they move up or down within the buffer, otherwise they search for a history line matching the start of the current line. In this case, however, they search for a line which matches the current line up to the current cursor position, in the manner of history-beginning-search-backward and -forward, rather than the first word on the line.
edit-command-line
Edit the command line using your visual editor, as in ksh.
bindkey -M vicmd v edit-command-line

The editor to be used can also be specified using the editor style in the context of the widget. It is specified as an array of command and arguments:

zstyle :zle:edit-command-line editor gvim -f
expand-absolute-path
Expand the file name under the cursor to an absolute path, resolving symbolic links. Where possible, the initial path segment is turned into a named directory or reference to a user's home directory.
history-search-end
This function implements the widgets history-beginning-search-backward-end and history-beginning-search-forward-end. These commands work by first calling the corresponding builtin widget (see `History Control' in zshzle(1)) and then moving the cursor to the end of the line. The original cursor position is remembered and restored before calling the builtin widget a second time, so that the same search is repeated to look farther through the history.

Although you autoload only one function, the commands to use it are slightly different because it implements two widgets.

zle -N history-beginning-search-backward-end \
       history-search-end
zle -N history-beginning-search-forward-end \
       history-search-end
bindkey '\e^P' history-beginning-search-backward-end
bindkey '\e^N' history-beginning-search-forward-end
history-beginning-search-menu
This function implements yet another form of history searching. The text before the cursor is used to select lines from the history, as for history-beginning-search-backward except that all matches are shown in a numbered menu. Typing the appropriate digits inserts the full history line. Note that leading zeroes must be typed (they are only shown when necessary for removing ambiguity). The entire history is searched; there is no distinction between forwards and backwards.

With a numeric argument, the search is not anchored to the start of the line; the string typed by the use may appear anywhere in the line in the history.

If the widget name contains `-end' the cursor is moved to the end of the line inserted. If the widget name contains `-space' any space in the text typed is treated as a wildcard and can match anything (hence a leading space is equivalent to giving a numeric argument). Both forms can be combined, for example:

zle -N history-beginning-search-menu-space-end \
       history-beginning-search-menu
history-pattern-search
The function history-pattern-search implements widgets which prompt for a pattern with which to search the history backwards or forwards. The pattern is in the usual zsh format, however the first character may be ^ to anchor the search to the start of the line, and the last character may be $ to anchor the search to the end of the line. If the search was not anchored to the end of the line the cursor is positioned just after the pattern found.

The commands to create bindable widgets are similar to those in the example immediately above:

autoload -U history-pattern-search
zle -N history-pattern-search-backward history-pattern-search
zle -N history-pattern-search-forward history-pattern-search
incarg
Typing the keystrokes for this widget with the cursor placed on or to the left of an integer causes that integer to be incremented by one. With a numeric argument, the number is incremented by the amount of the argument (decremented if the numeric argument is negative). The shell parameter incarg may be set to change the default increment to something other than one.
bindkey '^X+' incarg
incremental-complete-word
This allows incremental completion of a word. After starting this command, a list of completion choices can be shown after every character you type, which you can delete with ^H or DEL. Pressing return accepts the completion so far and returns you to normal editing (that is, the command line is not immediately executed). You can hit TAB to do normal completion, ^G to abort back to the state when you started, and ^D to list the matches.

This works only with the new function based completion system.

bindkey '^Xi' incremental-complete-word
insert-composed-char
Esta función permite componer caracteres que no se encuentran en el teclado para insertarlos en la línea de comandos. El comando va seguido de dos teclas que corresponden a caracteres ASCII (no hay indicaciones). Para caracteres acentuados, las dos teclas son un carácter base seguido de un código para el acento, mientras que para otros caracteres especiales las dos caracteres juntas forman una mnemotecnia para el carácter a insertar. Los códigos de dos caracteres son un subconjunto de los dados por RFC 1345 (ver por ejemplo http://www.faqs.org/rfcs/rfc1345.html).

La función puede ir seguida opcionalmente por hasta dos caracteres que reemplazan uno o ambos caracteres leídos del teclado; si se suministran ambos caracteres, no se lee ninguna entrada. Por ejemplo, insert-composed-char a: se puede usar dentro de un widget para insertar una "a" con diéresis en la línea de comandos. Esto tiene la ventaja sobre el uso de un carácter literal de ser más portable.

Para obtener mejores resultados, zsh debería haber sido compilado con soporte para caracteres multibyte (configurado con --enable-multibyte); sin embargo, la función funciona para el rango limitado de caracteres disponibles en conjuntos de caracteres de un solo byte como ISO-8859-1.

El carácter se convierte a la representación local y se inserta en la línea de comandos en la posición del cursor. (La conversión se realiza dentro del shell, utilizando las facilidades que proporcione la biblioteca C). Con un argumento numérico, el carácter y su código se previsualizan en la línea de estado.

La función puede ejecutarse fuera de zle, en cuyo caso imprime el carácter (junto con un salto de línea) en la salida estándar. La entrada todavía se lee de las pulsaciones de teclas.

Ver insert-unicode-char para una forma alternativa de insertar caracteres Unicode usando su número de carácter hexadecimal.

El conjunto de caracteres acentuados es razonablemente completo hasta el carácter Unicode U+0180, el conjunto de caracteres especiales es menos completo. Sin embargo, es muy esporádico a partir de ese punto. Añadir nuevos caracteres es fácil, sin embargo; ver la función define-composed-chars. Por favor, envíe cualquier adición a zsh-workers@zsh.org.

narrow-to-region-invisible
Reduce el área editable del búfer a la región entre el cursor y la marca, que pueden estar en cualquier orden. La región no puede estar vacía.

narrow-to-region puede usarse como un widget o llamarse como una función desde un widget definido por el usuario; por defecto, el texto fuera del área editable permanece visible. Se realiza una recursive-edit y luego se restaura el estado de ampliación original. Hay varias opciones y argumentos disponibles cuando se llama como función.

Las opciones -p pretext y -P posttext pueden usarse para reemplazar el texto antes y después de la visualización durante la duración de la función; una o ambas pueden ser una cadena vacía.

Si también se da la opción -n, pretext o posttext solo se insertarán si hay texto antes o después de la región respectivamente que se hará invisible.

Se pueden proporcionar dos argumentos numéricos que se utilizarán en lugar de las posiciones del cursor y la marca.

La opción -S statepm se usa para reducir según las otras opciones mientras se guarda el estado original en el parámetro con nombre statepm, mientras que la opción -R statepm se usa para restaurar el estado desde el parámetro; tenga en cuenta que en ambos casos se requiere el nombre del parámetro. En el segundo caso, otras opciones y argumentos son irrelevantes. Cuando se utiliza este método, no se realiza una recursive-edit; el widget de llamada debe llamar a esta función con la opción -S, realizar su propia edición en la línea de comandos o pasar el control al usuario a través de `zle recursive-edit', luego llamar a esta función con la opción -R. El argumento statepm debe ser un nombre adecuado para un parámetro ordinario, excepto que los parámetros que comienzan con el prefijo _ntr_ están reservados para su uso dentro de narrow-to-region. Típicamente, el parámetro será local a la función de llamada.

Las opciones -l lbufvar y -r rbufvar pueden usarse para especificar parámetros donde el widget almacenará el texto resultante de la operación. El parámetro lbufvar contendrá LBUFFER y rbufvar contendrá RBUFFER. Ninguna de estas dos opciones puede usarse con -S o -R.

narrow-to-region-invisible es un widget simple que llama a narrow-to-region con argumentos que reemplazan cualquier texto fuera de la región con `...'. No toma ningún argumento.

La pantalla se restaura (y el widget regresa) en cualquier comando de zle que normalmente haría que la línea se aceptara o abortara. Por lo tanto, se requiere un comando adicional de este tipo para aceptar o abortar la línea actual.

El estado de retorno de ambos widgets es cero si la línea fue aceptada, de lo contrario, es distinto de cero.

Aquí hay un ejemplo trivial de un widget que utiliza esta característica.

local state
narrow-to-region -p $'Editing restricted region\n' \
  -P '' -S state
zle recursive-edit
narrow-to-region -R state

Este conjunto de funciones implementa la escritura predictiva utilizando la búsqueda en el historial. Después de predict-on, al escribir caracteres, el editor busca hacia atrás en el historial la primera línea que comienza con lo que ha escrito hasta ahora. ZLE Widgets

bind-and-execute
This widget is analogous to `bind-key' except that it also executes the widget referred to by the key. This is useful for testing widgets, and for binding a key to execute a widget that has been modified by `zmod'.

For example, to test the `self-insert' widget after it has been modified by `zmod', one might use:

zle bind-and-execute self-insert

This will then bind the key `self-insert' to execute `self-insert', which is, of course, the modified version.

edit-command-line
This widget offers a different way of editing the command line. Instead of using the standard ZLE widgets, it runs an external editor (specified by the environment variable VISUAL or EDITOR, falling back to `vi' if neither is set).

The current command line is written to a temporary file, and the editor is invoked on that file. When the editor exits, the contents of the file are read back into the command line. If the editor exits with a status of zero, the command line is updated; otherwise, it is left unchanged.

If the editor is invoked with a numeric argument, the command line is not updated if the editor exits with a non-zero status.

expand-or-complete
This widget is intended to be bound to the tab key. It tries to complete the current word. If this fails, it tries to expand the word using globbing or history expansion.

The behaviour of this widget can be controlled by the following styles, looked up in the context `:expand-or-complete':

complete-with-ignore
If set to a true value, completion will ignore any files or directories that start with a period (`.'). The default is false.
expand-glob
If set to a true value, glob expansion will be attempted if completion fails. The default is true.
expand-history
If set to a true value, history expansion will be attempted if glob expansion fails. The default is true.
full-line-with-glob
If set to a true value, and glob expansion is attempted, the entire line will be expanded, not just the current word. The default is false.
menu-complete
If set to a true value, completion will enter menu completion mode. This allows cycling through possible completions using a key binding (usually TAB again). The default is false.
pop-menu-completion
If set to a true value, menu completion will pop down when a completion is inserted. The default is false.
history-incremental-search-backward
This widget performs an incremental search backwards through the history list. As you type characters, the widget moves backward through the history list, finding the most recent command that starts with the characters you have typed so far. If you type a character that does not match the start of any previous command, the widget will beep.

The search can be controlled by the following styles, looked up in the context `:history-incremental-search-backward':

history-search-lines
If set to a true value, the search will consider all lines in the history. Otherwise, it will only consider lines starting from the current line.
history-search-fixed
If set to a true value, the search string will be fixed once a match is found. This means that further characters typed will be appended to the current match, rather than starting a new search. The default is false.

The widget can be customized by binding the following keys:

accept-and-infer-next-history
Accept the current match and infer the next history entry.
history-search-next
Continue the search for the next match.
history-search-previous
Continue the search for the previous match.
insert-last-word
This widget inserts the last word from the previous command line. If the previous command line was empty, or contained no words, the widget does nothing.

A numeric argument is used to specify which word to insert. For example, a numeric argument of 2 would insert the second-to-last word.

kill-whole-line
This widget kills (i.e., deletes and yanks) the entire current line.

This is similar to the `kill-line' widget, except that it operates on the entire line, regardless of the cursor position.

magic-delete-backward-word
This widget deletes the characters preceding the cursor up to the beginning of the current word. It is similar to `backward-delete-word', but it also deletes any leading whitespace preceding the word.

The definition of a "word" and "whitespace" can be customized using the `zstyle' command. The context is `:magic-delete-backward-word'.

word-chars
A string containing characters that constitute a word. Defaults to `[:alnum:]_'.
whitespace-chars
A string containing characters that constitute whitespace. Defaults to `[:space:]'.
match-and-insert-edit
This widget tries to match the current word against a list of possible completions. If a match is found, the word is replaced by the completion, and the cursor is moved to the end of the completed word. If no match is found, the widget does nothing.

The list of possible completions is determined by the `match' style, looked up in the context `:match-and-insert-edit'. The default list includes all files in the current directory.

This widget is the opposite of `menu-complete'. It moves backward through the list of possible completions. It is useful for correcting mistakes made when using `menu-complete'.
move-over-space
This widget moves the cursor forward to the next non-space character. If the cursor is already at a non-space character, it moves to the next non-space character after that.

This widget is similar to `history-search-backward' but instead of searching for a specific string, it moves to the previous history line that contains the current word. A numeric argument can be used to specify which occurrence of the word to jump to.

pipe-region-backward
This widget is similar to `vi-pipe' but operates on the region before the cursor. It prompts for an external command, pipes the text before the cursor to the command, and replaces the text with the command's output. If a numeric argument is given, it specifies the number of lines to pipe.
print-last-command
This widget prints the last command executed in the current shell session. It is useful for recalling commands that you may have forgotten.
quote-line
This widget quotes the entire current command line, preventing it from being interpreted by the shell. This is useful when you want to paste a command line into the shell without executing it immediately.
read-from-minibuffer
This widget reads a string from the minibuffer and inserts it into the current buffer at the cursor position. The string can be anything, including shell commands, variable assignments, etc.

The prompt for the minibuffer can be customized using the `prompt' style, looked up in the context `:read-from-minibuffer'.

replace-macro-or-string
This widget is used to replace occurrences of a given string or regular expression with another string. It is similar to the `replace-string' and `replace-pattern' widgets, but it can also be used to replace macros.

The widget prompts for the string or pattern to search for, and then for the replacement string. It then replaces all occurrences of the search string or pattern with the replacement string.

The `replace-string' widget shows the previous replacement above the prompt, so long as there was one during the current session; if the source string is empty, that replacement will be repeated without the widget prompting for a replacement string.

For example, starting from the line:

print This line contains fan and fond

and invoking replace-pattern with the source string `f(?)n' and the replacement string `c\1r' produces the not very useful line:

print This line contains car and cord

The range of the replacement string can be limited by using the narrow-to-region-invisible widget. One limitation of the current version is that undo will cycle through changes to the replacement and source strings before undoing the replacement itself.

send-invisible
This is similar to read-from-minibuffer in that it may be called as a function from a widget or as a widget of its own, and interactively reads input from the keyboard. However, the input being typed is concealed and a string of asterisks (`*') is shown instead. The value is saved in the parameter $INVISIBLE to which a reference is inserted into the editing buffer at the restored cursor position. If the read was aborted by a keyboard break (typically ^G) or another escape from editing such as push-line, $INVISIBLE is set to empty and the original buffer is restored unchanged.

If one argument is supplied to the function it is taken as a prompt, otherwise `Non-echoed text: ' is used (as in emacs). If a second and third argument are supplied they are used to begin and end the reference to $INVISIBLE that is inserted into the buffer. The default is to open with ${, then INVISIBLE, and close with }, but many other effects are possible.

smart-insert-last-word
This function may replace the insert-last-word widget, like so:
zle -N insert-last-word smart-insert-last-word

With a numeric argument, or when passed command line arguments in a call from another widget, it behaves like insert-last-word, except that words in comments are ignored when INTERACTIVE_COMMENTS is set.

Otherwise, the rightmost ``interesting'' word from the previous command is found and inserted. The default definition of ``interesting'' is that the word contains at least one alphabetic character, slash, or backslash. This definition may be overridden by use of the match style. The context used to look up the style is the widget name, so usually the context is :insert-last-word. However, you can bind this function to different widgets to use different patterns:

zle -N insert-last-assignment smart-insert-last-word
zstyle :insert-last-assignment match '[[:alpha:]][][[:alnum:]]#=*'
bindkey '\e=' insert-last-assignment

If no interesting word is found and the auto-previous style is set to a true value, the search continues upward through the history. When auto-previous is unset or false (the default), the widget must be invoked repeatedly in order to search earlier history lines.

transpose-lines
Only useful with a multi-line editing buffer; the lines here are lines within the current on-screen buffer, not history lines. The effect is similar to the function of the same name in Emacs.

Transpose the current line with the previous line and move the cursor to the start of the next line. Repeating this (which can be done by providing a positive numeric argument) has the effect of moving the line above the cursor down by a number of lines.

With a negative numeric argument, requires two lines above the cursor. These two lines are transposed and the cursor moved to the start of the previous line. Using a numeric argument less than -1 has the effect of moving the line above the cursor up by minus that number of lines.

url-quote-magic
This widget replaces the built-in self-insert to make it easier to type URLs as command line arguments. As you type, the input character is analyzed and, if it may need quoting, the current word is checked for a URI scheme. If one is found and the current word is not already in quotes, a backslash is inserted before the input character.

Styles to control quoting behavior:

url-metas
This style is looked up in the context `:url-quote-magic:scheme' (where scheme is that of the current URL, e.g. "ftp"). The value is a string listing the characters to be treated as globbing metacharacters when appearing in a URL using that scheme. The default is to quote all zsh extended globbing characters, excluding '<' and '>' but including braces (as in brace expansion). See also url-seps.
url-seps
Like url-metas, but lists characters that should be considered command separators, redirections, history references, etc. The default is to quote the standard set of shell separators, excluding those that overlap with the extended globbing characters, but including '<' and '>' and the first character of $histchars.
url-globbers
This style is looked up in the context `:url-quote-magic'. The values form a list of command names that are expected to do their own globbing on the URL string. This implies that they are aliased to use the `noglob' modifier. When the first word on the line matches one of the values and the URL refers to a local file (see url-local-schema), only the url-seps characters are quoted; the url-metas are left alone, allowing them to affect command-line parsing, completion, etc. The default values are a literal `noglob' plus (when the zsh/parameter module is available) any commands aliased to the helper function `urlglobber' or its alias `globurl'.
url-local-schema
This style is always looked up in the context `:urlglobber', even though it is used by both url-quote-magic and urlglobber. The values form a list of URI schema that should be treated as referring to local files by their real local path names, as opposed to files which are specified relative to a web-server-defined document root. The defaults are "ftp" and "file".
url-other-schema
Like url-local-schema, but lists all other URI schema upon which urlglobber and url-quote-magic should act. If the URI on the command line does not have a scheme appearing either in this list or in url-local-schema, it is not magically quoted. The default values are "http", "https", and "ftp". When a scheme appears both here and in url-local-schema, it is quoted differently depending on whether the command name appears in url-globbers.

Loading url-quote-magic also defines a helper function `urlglobber' and aliases `globurl' to `noglob urlglobber'. This function takes a local URL apart, attempts to pattern-match the local file portion of the URL path, and then puts the results back into URL format again.

vi-pipe
This function reads a movement command from the keyboard and then prompts for an external command. The part of the buffer covered by the movement is piped to the external command and then replaced by the command's output. If the movement command is bound to vi-pipe, the current line is used.

The function serves as an example for reading a vi movement command from within a user-defined widget.

which-command
This function is a drop-in replacement for the builtin widget which-command. It has enhanced behaviour, in that it correctly detects whether or not the command word needs to be expanded as an alias; if so, it continues tracing the command word from the expanded alias until it reaches the command that will be executed.

The style whence is available in the context :zle:$WIDGET; this may be set to an array to give the command and options that will be used to investigate the command word found. The default is whence -c.

zcalc-auto-insert
This function is useful together with the zcalc function described in the section `Mathematical Functions'. It should be bound to a key representing a binary operator such as `+', `-', `*' or `/'. When running in zcalc, if the key occurs at the start of the line or immediately following an open parenthesis, the text "ans " is inserted before the representation of the key itself. This allows easy use of the answer from the previous calculation in the current line. The text to be inserted before the symbol typed can be modified by setting the variable ZCALC_AUTO_INSERT_PREFIX.

Hence, for example, typing `+12' followed by return adds 12 to the previous result.

If zcalc is in RPN mode (-r option) the effect of this binding is automatically suppressed as operators alone on a line are meaningful.

When not in zcalc, the key simply inserts the symbol itself.

argument-buffer
Contiene los argumentos de la línea de comandos actual, divididos por espacios en blanco. Por ejemplo, si la línea de comandos es ls -l /tmp, argument-buffer contendrá ("ls" "-l" "/tmp").

Si la opción KSH_ARRAYS está activada, los índices de la matriz comienzan en 0. De lo contrario, comienzan en 1.

La matriz contiene todas las partes de la línea en orden, comenzando con cualquier espacio en blanco antes del primer argumento y terminando con cualquier espacio en blanco después del último argumento. Por lo tanto (siempre que la opción KSH_ARRAYS no esté activada) los espacios en blanco se dan por índices impares en la matriz y los argumentos por índices pares. Tenga en cuenta que no se elimina el escape de comillas; unir todos los elementos de argument-buffer en orden garantiza la producción de la línea original.

El parámetro REPLY se establece en el índice de la palabra en argument-buffer que contiene el carácter después del cursor, donde el primer elemento tiene índice 1. El parámetro REPLY2 se establece en el índice del carácter debajo del cursor en esa palabra, donde el primer carácter tiene índice 1.

Por lo tanto, argument-buffer, REPLY y REPLY2 deben hacerse locales a la función contenedora.

Consulte la función modify-current-argument, descrita a continuación, para ver un ejemplo de cómo llamar a esta función.

modify-current-argument [ expr-usando-$ARG | func ]
Esta función proporciona un método sencillo para permitir que los widgets definidos por el usuario modifiquen el argumento de la línea de comandos debajo del cursor (o inmediatamente a la izquierda del cursor si el cursor está entre argumentos).

El argumento puede ser una expresión que, al evaluarse, opera sobre el parámetro del shell ARG, que se habrá establecido al argumento de la línea de comandos debajo del cursor. La expresión debe estar adecuadamente entrecomillada para evitar que se evalúe demasiado pronto.

Alternativamente, si el argumento no contiene la cadena ARG, se asume que es una función del shell, a la que se pasa el argumento actual de la línea de comandos como único argumento. La función debe establecer la variable REPLY con el nuevo valor para el argumento de la línea de comandos. Si la función devuelve un estado distinto de cero, también lo hace la función que la llama.

Por ejemplo, un widget definido por el usuario que contenga el siguiente código convierte los caracteres del argumento debajo del cursor a mayúsculas:

modify-current-argument '${(U)ARG}'

Lo siguiente elimina cualquier comilla del palabra actual (ya sean barras invertidas o uno de los estilos de comillas), y lo reemplaza con comillas simples en todas partes:

modify-current-argument '${(qq)${(Q)ARG}}'

Lo siguiente realiza la expansión de directorios en el argumento de la línea de comandos y lo reemplaza por la ruta absoluta:

expand-dir() {
  REPLY=${~1}
  REPLY=${REPLY:a}
}
modify-current-argument expand-dir

En la práctica, la función expand-dir probablemente no se definiría dentro del widget donde se llama a modify-current-argument.

Estilos

El comportamiento de varios de los widgets anteriores se puede controlar mediante el uso del mecanismo zstyle. En particular, los widgets que interactúan con el sistema de completado pasan su contexto a cualquier completado que invoquen.

break-keys
Este estilo es utilizado por el widget incremental-complete-word. Su valor debe ser un patrón, y todas las teclas que coincidan con este patrón harán que el widget detenga la completación incremental sin que la tecla tenga ningún efecto adicional. Al igual que todos los estilos utilizados directamente por incremental-complete-word, este estilo se busca utilizando el contexto `:incremental'.
completer
Los widgets incremental-complete-word e insert-and-predict establecen su nombre de contexto de nivel superior antes de llamar al completado. Esto permite definir diferentes conjuntos de funciones completadoras para el completado normal y para estos widgets. Por ejemplo, para utilizar completado, aproximación y corrección para el completado normal, completado y corrección para el completado incremental y solo completado para la predicción, se podría usar:
zstyle ':completion:*' completer \ 
        _complete _correct _approximate
zstyle ':completion:incremental:*' completer \ 
        _complete _correct
zstyle ':completion:predict:*' completer \ 
        _complete

Es una buena idea restringir los completadores utilizados en la predicción, ya que pueden invocarse automáticamente al escribir. Los completadores _list y _menu nunca deben usarse con predicción. Los completadores _approximate, _correct, _expand y _match pueden usarse, pero tenga en cuenta que pueden cambiar caracteres en cualquier lugar de la palabra detrás del cursor, por lo que debe observar atentamente que el resultado sea lo que pretendía.

cursor
El widget insert-and-predict utiliza este estilo, en el contexto `:predict', para decidir dónde colocar el cursor después de que se haya intentado el completado. Los valores son:
complete
El cursor se deja donde estaba cuando finalizó el completado, pero solo si está después de un carácter igual al que acaba de insertar el usuario. Si está después de otro carácter, este valor es el mismo que `key'.
key
El cursor se deja después de la n-ésima ocurrencia del carácter recién insertado, donde n es el número de veces que ese carácter apareció en la palabra antes de que se intentara el completado. En resumen, esto tiene el efecto de dejar el cursor después del carácter recién escrito, incluso si el código de completado determinó que no se necesitan insertar otros caracteres en esa posición.

Cualquier otro valor para este estilo deja incondicionalmente el cursor en la posición donde lo dejó el código de completado.

list
Al usar el widget incremental-complete-word, este estilo indica si las coincidencias deben mostrarse en cada pulsación de tecla (si caben en la pantalla). Utilice el prefijo de contexto `:completion:incremental'.

El widget insert-and-predict utiliza este estilo para decidir si se debe mostrar el completado, incluso si solo hay una posible completación. Esto se hace si el valor de este estilo es la cadena always. En este caso, el contexto es `:predict' (no `:completion:predict').

match
Este estilo es utilizado por smart-insert-last-word para proporcionar un patrón (usando sintaxis completa de EXTENDED_GLOB) que coincide con una palabra interesante. El contexto es el nombre del widget al que smart-insert-last-word está enlazado (ver arriba). El comportamiento predeterminado de smart-insert-last-word es equivalente a:
zstyle :insert-last-word match '*[[:alpha:]/\\]*'

Sin embargo, es posible que desee incluir palabras que contengan espacios:

zstyle :insert-last-word match '*[[:alpha:][:space:]/\\]*'

O incluir números siempre que la palabra tenga al menos dos caracteres de longitud:

zstyle :insert-last-word match '*([[:digit:]]?|[[:alpha:]/\\])*'

El ejemplo anterior provoca la inclusión de redirecciones como "2>".

prompt
El widget incremental-complete-word muestra el valor de este estilo en la línea de estado durante la completación incremental. El valor de la cadena puede contener cualquiera de las siguientes subcadenas de la misma manera que los parámetros PS1 y otros prompts:
%c
Reemplazado por el nombre de la función completadora que generó las coincidencias (sin el guion bajo inicial).
%l
Cuando el estilo list está configurado, se reemplaza por `...' si la lista de coincidencias es demasiado larga para caber en la pantalla y con una cadena vacía en caso contrario. Si el estilo list es `false' o no está configurado, `%l' siempre se elimina.
%n
Reemplazado por el número de coincidencias generadas.
%s
Reemplazado por `-no match-', `-no prefix-' o una cadena vacía si no hay ninguna completación que coincida con la palabra en la línea, si las coincidencias no tienen un prefijo común distinto de la palabra en la línea, o si existe tal prefijo común, respectivamente.
%u
Reemplazado por la parte no ambigua de todas las coincidencias, si existe alguna, y si es diferente de la palabra en la línea.

Al igual que `break-keys', esto utiliza el contexto `:incremental'.

stop-keys
Este estilo es utilizado por el widget incremental-complete-word. Su valor se trata de forma similar al del estilo break-keys (y utiliza el mismo contexto: `:incremental'). Sin embargo, en este caso, todas las teclas que coincidan con el patrón dado como su valor detendrán la completación incremental y luego ejecutarán su función habitual.
toggle
Este estilo booleano es utilizado por predict-on y sus widgets relacionados en el contexto `:predict'. Si se establece en uno de los valores estándar `true', la escritura predictiva se desactiva automáticamente en situaciones donde es poco probable que sea útil, como al editar un buffer multilínea o después de moverse a la mitad de una línea y luego eliminar un carácter. El valor predeterminado es dejar la predicción activada hasta una llamada explícita a predict-off.
verbose
Este estilo booleano es utilizado por predict-on y sus widgets relacionados en el contexto `:predict'. Si se establece en uno de los valores estándar `true', estos widgets muestran un mensaje debajo del prompt cuando se alterna el estado predictivo. Esto es más útil en combinación con el estilo toggle. El valor predeterminado no muestra estos mensajes.
widget
Este estilo es similar al estilo command: Para las funciones de widget que utilizan zle para llamar a otros widgets, este estilo a veces se puede utilizar para anular el widget que se llama. El contexto para este estilo es el nombre del widget que llama (no el nombre de la función que llama, ya que una función puede estar enlazada a múltiples nombres de widget).
zstyle :copy-earlier-word widget smart-insert-last-word

Verifique la documentación del widget o función de llamada para determinar si se utiliza el estilo widget.

MANEJO DE EXCEPCIONES

Se proporcionan dos funciones para permitir que zsh ofrezca manejo de excepciones de una forma que debería resultar familiar de otros lenguajes.

throw excepción
La función throw lanza la excepción nombrada. El nombre es una cadena arbitraria y solo es utilizada por las funciones throw y catch. Una excepción se trata en la mayoría de los casos igual que un error de shell, es decir, una excepción no manejada hará que el shell aborte todo el procesamiento en una función o script y regrese al nivel superior en un shell interactivo.
catch patrón-excepcion
La función catch devuelve el estado cero si se lanzó una excepción y el patrón patrón-excepcion coincide con su nombre. De lo contrario, devuelve el estado 1. patrón-excepcion es un patrón de shell estándar, respetando la configuración actual de la opción EXTENDED_GLOB. También se define un alias catch para evitar que el argumento de la función coincida con nombres de archivo, por lo que los patrones se pueden usar sin comillas. Tenga en cuenta que como las excepciones no son fundamentalmente diferentes de otros errores de shell, es posible capturar errores de shell utilizando una cadena vacía como nombre de excepción. La variable de shell CAUGHT es establecida por catch con el nombre de la excepción capturada. Es posible volver a lanzar una excepción llamando nuevamente a la función throw una vez que una excepción ha sido capturada.

Las funciones están diseñadas para usarse junto con la construcción always descrita en zshmisc(1). Esto es importante ya que solo esta construcción proporciona el soporte requerido para las excepciones. Un ejemplo típico es el siguiente.

{
  # Bloque "try"
  # ... código anidado aquí llama a "throw MyExcept"
} always {
  # Bloque "always"
  if catch MyExcept; then
    print "Capturada excepción MyExcept"
  elif catch ''; then
    print "Capturado un error de shell. Propagando..."
    throw ''
  fi
  # Otras excepciones no se manejan pero pueden ser capturadas más arriba
  # en la pila de llamadas.
}

Si se deben capturar todas las excepciones, el siguiente modismo puede ser preferible.

{
  # ... código anidado aquí lanza una excepción
} always {
  if catch *; then
    case $CAUGHT in
      (MyExcept)
      print "Capturada mi propia excepción"
      ;;
      (*)
      print "Capturada otra excepción"
      ;;
    esac
  fi
}

En común con el manejo de excepciones en otros lenguajes, la excepción puede ser lanzada por código profundamente anidado dentro del bloque `try'. Sin embargo, tenga en cuenta que debe ser lanzada dentro del shell actual, no en un subshell creado para un pipeline, una construcción de shell actual entre paréntesis, o alguna forma de sustitución de comando o proceso.

El sistema utiliza internamente la variable de shell EXCEPTION para registrar el nombre de la excepción entre el lanzamiento y la captura. Una desventaja de este esquema es que si la excepción no se maneja, la variable EXCEPTION permanece establecida y puede ser reconocida incorrectamente como el nombre de una excepción si posteriormente ocurre un error de shell. Agregar unset EXCEPTION al inicio de la capa más externa de cualquier código que utilice manejo de excepciones eliminará este problema.

FUNCIONES MIME

Hay tres funciones disponibles para proporcionar manejo de archivos reconocidos por extensión, por ejemplo, para distribuir un archivo text.ps cuando se ejecuta como un comando a un visor apropiado.

zsh-mime-setup [ -fv ] [ -l [ sufijo ... ] ]
zsh-mime-handler [ -l ] comando argumento ...
Estas dos funciones utilizan los archivos ~/.mime.types y /etc/mime.types, que asocian tipos y extensiones, así como los archivos ~/.mailcap y /etc/mailcap, que asocian tipos y los programas que los manejan. Estos se proporcionan en muchos sistemas con las Extensiones de Correo de Internet Multimedia.

Para habilitar el sistema, la función zsh-mime-setup debe ser cargada automáticamente y ejecutada. Esto permite que los archivos con extensiones sean tratados como ejecutables; dichos archivos serán completados por el sistema de completado de funciones. La función zsh-mime-handler no debería necesitar ser llamada por el usuario.

El sistema funciona configurando alias de sufijo con `alias -s'. Los alias de sufijo ya instalados por el usuario no serán sobrescritos.

Para sufijos definidos en minúsculas, las variantes en mayúsculas también se manejarán automáticamente (por ejemplo, PDF se maneja automáticamente si se define el manejo para el sufijo pdf), pero no al revés.

Las llamadas repetidas a zsh-mime-setup no anulan el mapeo existente entre sufijos y archivos ejecutables a menos que se proporcione la opción -f. Tenga en cuenta, sin embargo, que esto no anula los alias de sufijo existentes asignados a manejadores distintos de zsh-mime-handler.

Llamar a zsh-mime-setup con la opción -l lista los mapeos existentes sin alterarlos. Los sufijos a listar (que pueden contener caracteres de patrón que deben ser citados para su interpretación inmediata en la línea de comandos) pueden proporcionarse como argumentos adicionales, de lo contrario, se listan todos los sufijos.

Llamar a zsh-mime-setup con la opción -v muestra una salida detallada durante la operación de configuración.

El sistema respeta las banderas mailcap needsterminal y copiousoutput; consulte mailcap(4) o mailcap(5) (el nombre de la página man varía según la plataforma).

Las funciones utilizan los siguientes estilos, que se definen con el comando incorporado zstyle (consulte zshmodules(1)). Deben definirse antes de ejecutar zsh-mime-setup. Todos los contextos utilizados comienzan con :mime:, con componentes adicionales en algunos casos. Se recomienda que se agregue un * final (adecuadamente citado) a los patrones de estilo en caso de que el sistema se extienda en el futuro. Algunos ejemplos se dan a continuación.

Para archivos que tienen múltiples sufijos, por ejemplo, .pdf.gz, donde el contexto incluye el sufijo, se buscará comenzando con el sufijo más largo posible hasta encontrar una coincidencia para el estilo. Por ejemplo, si .pdf.gz produce una coincidencia para el manejador, se usará ese; de lo contrario, se usará el manejador para .gz. Tenga en cuenta que, debido a la forma en que funcionan los alias de sufijo, siempre se requiere que haya un manejador para el sufijo más corto posible, por lo que en este ejemplo .pdf.gz solo se puede manejar si .gz también se maneja (aunque no necesariamente de la misma manera). Alternativamente, si no se necesita manejo para .gz por sí solo, simplemente agregar el comando

alias -s gz=zsh-mime-handler

al código de inicialización es suficiente; .gz no se manejará por sí solo, pero puede ser en combinación con otros sufijos.

current-shell
Si este estilo booleano es verdadero, el manejador de mailcap para el contexto en cuestión se ejecuta utilizando el incorporado eval en lugar de iniciar un nuevo proceso sh. Esto es más eficiente, pero puede no funcionar en los casos ocasionales en los que el manejador de mailcap utiliza sintaxis estricta POSIX.
disown
Si este estilo booleano es verdadero, los manejadores de mailcap iniciados en segundo plano serán desvinculados, es decir, no estarán sujetos al control de trabajos dentro del shell padre. Dichos manejadores casi siempre producen sus propias ventanas, por lo que el único efecto secundario perjudicial probable de establecer el estilo es que se vuelve más difícil matar trabajos desde dentro del shell.
execute-as-is
Este estilo proporciona una lista de patrones para que coincidan con los archivos pasados para ejecución con un programa manejador. Si el archivo coincide con el patrón, toda la línea de comandos se ejecuta en su forma actual, sin manejador. Esto es útil para archivos que podrían tener sufijos pero que, no obstante, son ejecutables por derecho propio. Si el estilo no está establecido, se utiliza el patrón *(*) *(/); por lo tanto, los archivos ejecutables se ejecutan directamente y no se pasan a un manejador, y la opción AUTO_CD puede usarse para cambiar a directorios que casualmente tengan sufijos MIME.
execute-never
Este estilo es útil en combinación con execute-as-is. Se establece con un array de patrones que corresponden a rutas completas de archivos que nunca deben tratarse como ejecutables, incluso si el archivo pasado al manejador MIME coincide con execute-as-is. Esto es útil para sistemas de archivos que no manejan el permiso de ejecución o que contienen ejecutables de otro sistema operativo. Por ejemplo, si /mnt/windows es un montaje de Windows, entonces
zstyle ':mime:*' execute-never '/mnt/windows/*'

asegurará que cualquier archivo encontrado en esa área se ejecute como tipos MIME incluso si son ejecutables. Como muestra este ejemplo, el nombre completo del archivo coincide con el patrón, independientemente de cómo se pasó el archivo al manejador. El archivo se resuelve a una ruta completa utilizando el modificador :P descrito en la subsección `Modificadores' en zshexpn(1); esto significa que los enlaces simbólicos se resuelven siempre que sea posible, de modo que los enlaces a otros sistemas de archivos se comporten de la manera correcta.

file-path
Se utiliza si el estilo find-file-in-path es verdadero para el mismo contexto. Se establece con un array de directorios que se utilizan para buscar el archivo a manejar; el valor predeterminado es la ruta de comandos dada por el parámetro especial path. Se respeta la opción de shell PATH_DIRS; si esta está establecida, se buscará la ruta apropiada incluso si el nombre del archivo a manejar tal como aparece en la línea de comandos contiene un `/'. El contexto completo es :mime:.sufijo:, como se describe para el estilo handler.
find-file-in-path
Si está establecido, permite que los archivos cuyos nombres no contienen rutas absolutas se busquen en la ruta de comandos o en la ruta especificada por el estilo file-path. Si el archivo no se encuentra en la ruta, se busca localmente (independientemente de si el curren
t directorio se encuentra en la ruta); si no se encuentra localmente, el manejador abortará a menos que se establezca el estilo handle-nonexistent. Los archivos que se encuentran en la ruta se prueban como se describe para el estilo execute-as-is. El contexto completo es :mime:.sufijo:, como se describe para el estilo handler.
flags
Define flags para acompañar a un manejador; el contexto es el mismo que para el estilo handler, y el formato es el mismo que para las flags en mailcap.
handle-nonexistent
Por defecto, los argumentos que no corresponden a archivos no se pasan al manejador MIME para evitar que intercepte comandos que se encuentran en la ruta y que casualmente tienen sufijos. Este estilo puede establecerse a un array de patrones glob extendidos para los argumentos que se pasarán al manejador incluso si no existen. Si no se establece explícitamente, por defecto es [[:alpha:]]#:/*, lo que permite que las URLs se pasen al manejador MIME aunque no existan en ese formato en el sistema de archivos. El contexto completo es :mime:.sufijo:, como se describe para el estilo handler.
handler
Especifica un manejador para un sufijo; el sufijo se da por el contexto como :mime:.sufijo:, y el formato del manejador es exactamente el de mailcap. Tenga en cuenta en particular el `.' y el dos puntos final para distinguir este uso del contexto. Esto anula cualquier manejador especificado por los archivos mailcap. Si el manejador requiere una terminal, el estilo flags debe establecerse para incluir la palabra needsterminal, o si la salida se va a mostrar a través de un paginador (pero no si el manejador es en sí mismo un paginador), debe incluir copiousoutput.
mailcap
Una lista de archivos en el formato de ~/.mailcap y /etc/mailcap para ser leídos durante la configuración, reemplazando la lista por defecto que consiste en esos dos archivos. El contexto es :mime:. Un + en la lista se reemplazará por los archivos por defecto.
mailcap-priorities
Este estilo se utiliza para resolver múltiples entradas mailcap para el mismo tipo MIME. Consiste en un array de los siguientes elementos, en orden descendente de prioridad; las entradas posteriores se utilizarán si las entradas anteriores no pueden resolver las entradas que se comparan. Si ninguna de las pruebas resuelve las entradas, se conserva la primera entrada encontrada.
files
El orden de los archivos (entradas en el estilo mailcap) leídos. Los archivos anteriores tienen preferencia. (Tenga en cuenta que esto no resuelve las entradas en el mismo archivo).
priority
La flag de prioridad de la entrada mailcap. La prioridad es un entero de 0 a 9, siendo el valor por defecto 5.
flags
La prueba dada por la opción mailcap-prio-flags se utiliza para resolver las entradas.
place
Las entradas posteriores tienen preferencia; como las entradas están estrictamente ordenadas, esta prueba siempre tiene éxito.

Tenga en cuenta que como este estilo se maneja durante la inicialización, el contexto es siempre :mime:, sin discriminación por sufijo.

mailcap-prio-flags
Este estilo se utiliza cuando la palabra clave flags se encuentra en la lista de pruebas especificadas por el estilo mailcap-priorities. Debe establecerse a una lista de patrones, cada uno de los cuales se prueba contra las flags especificadas en la entrada mailcap (en otras palabras, los conjuntos de asignaciones encontrados con algunas entradas en el archivo mailcap). Los patrones anteriores en la lista tienen preferencia sobre los posteriores, y los patrones coincidentes tienen preferencia sobre los no coincidentes.
mime-types
Una lista de archivos en el formato de ~/.mime.types y /etc/mime.types para ser leídos durante la configuración, reemplazando la lista por defecto que consiste en esos dos archivos. El contexto es :mime:. Un + en la lista se reemplazará por los archivos por defecto.
never-background
Si se establece este estilo booleano, el manejador para el contexto dado se ejecuta siempre en primer plano, incluso si las flags proporcionadas en la entrada mailcap sugieren que no es necesario (por ejemplo, no requiere una terminal).
pager
Si se establece, se utilizará en lugar de $PAGER o more para manejar sufijos donde la flag copiousoutput está establecida. El contexto es el mismo que para handler, es decir, :mime:.sufijo: para manejar un archivo con el sufijo dado.

Ejemplos:

zstyle ':mime:*' mailcap ~/.mailcap /usr/local/etc/mailcap
zstyle ':mime:.txt:' handler less %s
zstyle ':mime:.txt:' flags needsterminal

Cuando zsh-mime-setup se ejecute posteriormente, buscará entradas mailcap en los dos archivos dados. Los archivos con sufijo .txt se manejarán ejecutando `less archivo.txt'. La flag needsterminal se establece para indicar que este programa debe ejecutarse conectado a una terminal.

Como hay varios pasos para despachar un comando, se debe comprobar lo siguiente si al intentar ejecutar un archivo por extensión .ext no se produce el efecto esperado.

El comando `alias -s ext' debería mostrar `ps=zsh-mime-handler'. Si muestra algo más, ya se ha instalado otro alias de sufijo y no se ha sobrescrito. Si no muestra nada, no se ha instalado ningún manejador: esto se debe probablemente a que no se encontró ningún manejador en la combinación .mime.types y mailcap para archivos .ext. En ese caso, se debe agregar un manejo adecuado a ~/.mime.types y mailcap.

Si la extensión es manejada por zsh-mime-handler pero el archivo no se abre correctamente, o el manejador definido para el tipo es incorrecto, o las flags asociadas a él son inapropiadas. Ejecutar zsh-mime-setup -l mostrará el manejador y, si los hay, las flags. Un %s en el manejador se reemplaza por el archivo (adecuadamente entre comillas si es necesario). Verifique que el programa manejador listado lista y puede ser ejecutado de la manera mostrada. Verifique también que las flags needsterminal o copiousoutput estén establecidas si el manejador necesita ser ejecutado bajo una terminal; la segunda flag se utiliza si la salida debe enviarse a un paginador. Un ejemplo de una entrada mailcap adecuada para dicho programa es:

text/html; /usr/bin/lynx '%s'; needsterminal

Ejecutar `zsh-mime-handler -l línea de comando' imprime la línea de comando que se ejecutaría, simplificada para eliminar el efecto de cualquier flag, y entre comillas para que la salida pueda ser ejecutada como una línea de comando zsh completa. Esto es utilizado por el sistema de completado para decidir cómo completar después de un archivo manejado por zsh-mime-setup.

pick-web-browser
Esta función es independiente de las dos funciones MIME descritas anteriormente y puede asignarse directamente a un sufijo:
autoload -U pick-web-browser
alias -s html=pick-web-browser

Se proporciona como un front-end inteligente para despachar un navegador web. Puede ejecutarse como una función o un script de shell. El estado 255 se devuelve si no se pudo iniciar ningún navegador.

Varios estilos están disponibles para personalizar la elección de navegadores:

browser-style
El valor del estilo es un array que da preferencias en orden decreciente para el tipo de navegador a usar. Los valores de los elementos pueden ser
running
Utiliza un navegador GUI que ya está en ejecución cuando hay una pantalla X Window disponible. Los navegadores listados en el estilo x-browsers se prueban en orden hasta que se encuentra uno; si se encuentra, el archivo se mostrará en ese navegador, por lo que el usuario puede necesitar verificar si ha aparecido. Si no se encuentra un navegador en ejecución, no se inicia. Se asume que los navegadores distintos de Firefox, Opera y Konqueror entienden la sintaxis de Mozilla para abrir una URL de forma remota.
x
Inicia un nuevo navegador GUI cuando hay una pantalla X Window disponible. Busca la disponibilidad de uno de los navegadores listados en el estilo x-browsers e inicia el primero que se encuentra. No se realiza ninguna comprobación de si ya hay un navegador en ejecución.

Inicia un navegador basado en terminal. Busca la disponibilidad de uno de los navegadores listados en el estilo tty-browsers e inicia el primero que se encuentra.

Si el estilo no está establecido, se utiliza el valor por defecto running x tty.

x-browsers
Un array en orden decreciente de preferencia de navegadores a usar cuando se ejecuta bajo el sistema de ventanas X. El array consiste en el nombre del comando bajo el cual iniciar el navegador. Se buscan en el contexto :mime: (que puede extenderse en el futuro, por lo que se recomienda agregar `*'). Por ejemplo,

tty-browsers
Un array similar a x-browsers, excepto que proporciona navegadores a usar cuando no hay una pantalla X Window disponible. El valor por defecto es elinks links lynx.
command
Si está establecido, este estilo se utiliza para seleccionar el comando que se usa para abrir una página para un navegador. La secuencia de escape %b en el valor del estilo se reemplazará por el navegador, mientras que %u se reemplazará por la URL. FUNCIONES MATEMÁTICAS

zcalc [ -erf ] [ expresión ... ]
Una calculadora razonablemente potente basada en la facilidad de evaluación aritmética de zsh. La sintaxis es similar a la de las fórmulas en la mayoría de los lenguajes de programación; consulte la sección `Evaluación aritmética' en zshmisc(1) para obtener detalles.

Los no programadores deben tener en cuenta que, al igual que en muchos otros lenguajes de programación, las expresiones que solo involucran enteros (ya sean constantes sin un `.', variables que contienen dichas constantes como cadenas de texto, o variables declaradas como enteros) se evalúan por defecto utilizando aritmética de enteros, que no es como opera una calculadora de escritorio común. Para forzar la operación de punto flotante, pase la opción -f; véanse más notas a continuación.

Si el archivo ~/.zcalcrc existe, se cargará dentro de la función una vez que se configure y esté a punto de procesar la línea de comandos. Esto se puede usar, por ejemplo, para establecer opciones del shell; emulate -L zsh y setopt extendedglob están en vigor en este momento. Cualquier fallo al cargar el archivo si existe se trata como fatal. Al igual que con otros archivos de inicialización, el directorio $ZDOTDIR se utiliza en lugar de $HOME si está establecido.

La biblioteca matemática zsh/mathfunc se cargará si está disponible; consulte la sección `El módulo zsh/mathfunc' en zshmodules(1). Las funciones matemáticas corresponden a las bibliotecas del sistema sin procesar, por lo que las funciones trigonométricas se evalúan utilizando radianes, y así sucesivamente.

Cada línea introducida se evalúa como una expresión. El prompt muestra un número, que corresponde a un parámetro posicional donde se almacena el resultado de ese cálculo. Por ejemplo, el resultado del cálculo en la línea precedida por `4> ' está disponible como $4. El último valor calculado está disponible como ans. Se dispone de edición completa de línea de comandos, incluido el historial de cálculos anteriores; el historial se guarda en el archivo ~/.zcalc_history. Para salir, introduzca una línea en blanco o escriba `:q` por sí solo (`q' está permitido por compatibilidad histórica).

Una línea que termina con una barra invertida se trata de la misma manera que en la edición de línea de comandos: se elimina la barra invertida, la función solicita más entrada (el prompt se precede de `...' para indicarlo), y las líneas se combinan en una para obtener el resultado final. Además, si la entrada hasta el momento contiene más paréntesis de apertura que de cierre, zcalc solicitará más entrada.

Si se proporcionan argumentos a zcalc al inicio, se utilizan para inicializar los primeros parámetros posicionales. Se da una indicación visual de esto cuando la calculadora se inicia.

Se proporcionan las constantes PI (3.14159...) y E (2.71828...). Es posible la asignación de parámetros, pero tenga en cuenta que todos los parámetros se colocarán en el espacio de nombres global a menos que se utilice el comando especial :local. La función crea variables locales cuyos nombres comienzan con _, por lo que los usuarios deben evitar hacerlo. Las variables ans (la última respuesta) y stack (la pila en modo RPN) se pueden referenciar directamente; stack es un arreglo pero sus elementos son numéricos. Varias otras variables especiales se utilizan localmente con su significado estándar, por ejemplo compcontext, match, mbegin, mend, psvar.

La base de salida se puede inicializar pasando la opción `-#base', por ejemplo `zcalc -#16' (la `#' puede tener que ser entre comillas, dependiendo de las opciones de globbing establecidas).

Si la opción `-e' está establecida, la función se ejecuta de forma no interactiva: los argumentos se tratan como expresiones a evaluar como si se introdujeran interactivamente línea por línea.

Si la opción `-f' está establecida, todos los números se tratan como punto flotante, por lo que, por ejemplo, la expresión `3/4' se evalúa como 0.75 en lugar de 0. Las opciones deben aparecer en palabras separadas.

Si la opción `-r' está establecida, se entra en modo RPN (Notación Polaca Inversa). Esto tiene varias propiedades adicionales:

Pila
Los valores evaluados se mantienen en una pila; esto está contenido en un arreglo llamado stack con el valor más reciente en ${stack[1]}.
Operadores y funciones
Si la línea introducida coincide con un operador (+, -, *, /, **, ^, | o &) o una función suministrada por la biblioteca zsh/mathfunc, se extraen uno o más elementos de la parte inferior de la pila para usarlos como argumento o argumentos. Los elementos superiores de la pila (menos recientes) se utilizan como argumentos anteriores. El resultado se introduce luego en ${stack[1]}.
Expresiones
Otras expresiones se evalúan normalmente, se imprimen y se añaden a la pila como valores numéricos. La sintaxis dentro de las expresiones en una sola línea es la aritmética normal del shell (no RPN).
Listado de pila
Si un entero sigue a la opción -r sin espacio, entonces en cada evaluación se imprimen tantos elementos de la pila, donde estén disponibles, en lugar de solo el resultado más reciente. Por lo tanto, por ejemplo, zcalc -r4 muestra $stack[4] a $stack[1] cada vez que se imprimen resultados.
Duplicación: =
El pseudo-operador = hace que el elemento más reciente de la pila se duplique en la pila.
pop
La pseudo-función pop hace que se extraiga el elemento más reciente de la pila. Un `>' por sí solo tiene el mismo efecto.
>identificador
La expresión > seguida (sin espacio) de un identificador de shell hace que se extraiga el elemento más reciente de la pila y se asigne a la variable con ese nombre. La variable es local a la función zcalc.
<identificador
La expresión < seguida (sin espacio) de un identificador de shell hace que el valor de la variable con ese nombre se inserte en la pila. identificador puede ser un entero, en cuyo caso el resultado anterior con ese número (como se muestra antes del > en el prompt estándar de zcalc) se coloca en la pila.
Intercambio: xy
La pseudo-función xy hace que se intercambien los dos elementos más recientes de la pila. `<>' tiene el mismo efecto.

El prompt es configurable a través del parámetro ZCALCPROMPT, que experimenta la expansión de prompt estándar. El índice de la entrada actual se almacena localmente en el primer elemento del arreglo psvar, al que se puede hacer referencia en ZCALCPROMPT como `%1v'. El prompt predeterminado es `%1v> '.

La variable ZCALC_ACTIVE se establece dentro de la función y puede ser probada por funciones anidadas; tiene el valor rpn si el modo RPN está activo, de lo contrario 1.

Hay unos pocos comandos especiales disponibles; estos se introducen con dos puntos. Por compatibilidad hacia atrás, los dos puntos pueden omitirse para ciertos comandos. La compleción está disponible si se ha ejecutado compinit.

La precisión de la salida se puede especificar dentro de zcalc con comandos especiales familiares de muchas calculadoras.

:norm
El formato de salida predeterminado. Corresponde a la especificación %g de printf. Típicamente muestra seis dígitos decimales.
:sci dígitos
Notación científica, que corresponde al formato de salida %g de printf con la precisión dada por dígitos. Esto produce notación de punto fijo o exponencial dependiendo del valor de salida.
:fix dígitos
Notación de punto fijo, que corresponde al formato de salida %f de printf con la precisión dada por dígitos.
:eng dígitos
Notación exponencial, que corresponde al formato de salida %E de printf con la precisión dada por dígitos.
:raw
Salida sin procesar: esta es la forma predeterminada de la salida de una evaluación matemática. Puede mostrar más precisión de la que el número posee realmente.

Otros comandos especiales:

:!línea...
Ejecuta línea... como una línea de comando normal del shell. Tenga en cuenta que se ejecuta en el contexto de la función, es decir, con variables locales. El espacio es opcional después de :!.
:local arg ...
Declara variables locales a la función. Se pueden usar otras variables, pero se tomarán del ámbito global o se colocarán en él.
:function nombre [ cuerpo ]
Define una función matemática o (sin cuerpo) la elimina. :function puede abreviarse a :func o simplemente :f. El nombre puede contener los mismos caracteres que un nombre de función de shell. La función se define utilizando zmathfuncdef, véase más abajo.

Tenga en cuenta que zcalc se encarga de todas las comillas. Por lo tanto, por ejemplo:

:f cube $1 \* $1 \* $1

define una función para elevar al cubo el único argumento. Las funciones definidas de esta manera, o de hecho cualquier función definida directa o indirectamente usando functions -M, están disponibles para ejecutarlas escribiendo solo el nombre en la línea en modo RPN; esto extrae el número apropiado de argumentos de la pila para pasarlos a la función, es decir, 1 en el caso de la función de ejemplo cube. Si hay argumentos opcionales, solo se proporcionan los argumentos obligatorios de esta manera.

[#base]
Esto no es un comando especial, sino parte de la sintaxis aritmética normal; sin embargo, cuando esta forma aparece en una línea por sí sola, la base de salida predeterminada se establece en base. Use, por ejemplo, `[#16]' para mostrar la salida hexadecimal precedida de una indicación de la base, o `[##16]' solo para mostrar el número sin procesar en la base dada. Las bases en sí siempre se especifican en decimal. `[#]' restaura el formato de salida normal. Tenga en cuenta que establecer una base de salida suprime la salida de punto flotante; use `[#]' para volver a la operación normal.
$var
Imprime el valor de var literalmente; no afecta al cálculo. Para usar el valor de var, omita el `$' inicial.

Consulte los comentarios en la función para obtener algunos consejos adicionales.

sum(argumento, ...)
zmathfunc
La función zmathfunc define las tres funciones matemáticas min, max y sum. Las funciones min y max toman uno o más argumentos. La función sum toma cero o más argumentos. Los argumentos pueden ser de diferentes tipos (enteros y flotantes).

No debe confundirse con el módulo zsh/mathfunc, descrito en la sección `El módulo zsh/mathfunc' en zshmodules(1).

Una interfaz conveniente para functions -M.

Con dos argumentos, define una función matemática llamada función_matemática que se puede usar en cualquier forma de evaluación aritmética. cuerpo es una expresión matemática para implementar la función. Puede contener referencias a parámetros posicionales $1, $2, ... para referirse a parámetros obligatorios y ${1:-valor_predeterminado} ... para referirse a parámetros opcionales. Tenga en cuenta que las formas deben cumplirse estrictamente para que la función calcule el número correcto de argumentos. La implementación se mantiene en una función de shell llamada zsh_math_func_función_matemática; por lo general, el usuario no necesitará referirse directamente a la función de shell. Sin argumentos, lista todas las funciones función_matemática en un formato adecuado para restaurar la definición. Las funciones no han sido necesariamente definidas por zmathfuncdef.

FUNCIONES DE CONFIGURACIÓN DEL USUARIO

El módulo zsh/newuser viene con una función para ayudar en la configuración de opciones del shell para nuevos usuarios. Si el módulo está instalado, esta función también se puede ejecutar manualmente. Está disponible incluso si el comportamiento predeterminado del módulo, es decir, ejecutar la función para un nuevo usuario que inicia sesión sin archivos de inicio, está inhibido.

zsh-newuser-install [ -f ]
La función presenta al usuario varias opciones para personalizar sus scripts de inicialización. Actualmente solo se maneja ~/.zshrc. Se utiliza $ZDOTDIR/.zshrc en su lugar si se establece el parámetro ZDOTDIR; esto proporciona una forma para que el usuario configure un archivo sin alterar un .zshrc existente.

Por defecto, la función sale inmediatamente si encuentra alguno de los archivos .zshenv, .zprofile, .zshrc o .zlogin en el directorio apropiado. La opción -f es necesaria para forzar a la función a continuar. Tenga en cuenta que esto puede ocurrir incluso si el propio .zshrc no existe.

Tal como está configurada actualmente, la función saldrá inmediatamente si el usuario tiene privilegios de root; este comportamiento no puede ser anulado.

Una vez activada, se supone que el comportamiento de la función es autoexplicativo. Hay menús que permiten al usuario alterar el valor de opciones y parámetros. Siempre se agradecen sugerencias de mejora.

Cuando el script sale, al usuario se le da la oportunidad de guardar el nuevo archivo o no; los cambios no son irreversibles hasta este punto. Sin embargo, el script se cuida de restringir los cambios en el archivo solo a un grupo marcado por las líneas `# Líneas configuradas por zsh-newuser-install' y `# Fin de las líneas configuradas por zsh-newuser-install'. Además, la versión anterior de .zshrc se guarda en un archivo con el sufijo .zni adjunto.

Si la función edita un .zshrc existente, depende del usuario asegurarse de que los cambios realizados surtan efecto. Por ejemplo, si el control generalmente regresa temprano desde el .zshrc existente, las líneas no se ejecutarán; o un archivo de inicialización posterior puede anular opciones o parámetros, etc. La función en sí misma no intenta detectar tales conflictos.

zmv

La función zmv se utiliza para renombrar un conjunto de archivos de acuerdo con un patrón de expansión de glob y una regla de sustitución.

La sintaxis es:

zmv [options] pattern replacement

donde pattern es un patrón de glob que describe los archivos que desea renombrar, y replacement es una cadena que especifica el nuevo nombre. Las partes del patrón que coinciden con expansiones de glob (por ejemplo, `*', `?', `[...]') se pueden referenciar en replacement usando la notación de sustitución de parámetros de shell, como ${1}, ${2}, etc. Si se usa la opción -w, las partes comodín coincidirán con los delimitadores de palabra y si se usa -W, el nombre de archivo completo se pasa a la variable $f.

Ejemplos:

zmv -v 'old_dir/*.txt' 'new_dir/$1.txt'

Renombra todos los archivos .txt en old_dir a new_dir, manteniendo el mismo nombre base. Por ejemplo, `old_dir/foo.txt' se convertiría en `new_dir/foo.txt'.

zmv -v '(*) (*)' '$1_$2'

Si tiene archivos llamados `a b' y `c d', esta orden los renombrará a `a_b' y `c_d', respectivamente.

zmv -v 'image-*.jpg' 'img-$(printf "%03d" $1).jpg'

Si tiene archivos como `image-1.jpg', `image-2.jpg', etc., esto los renombrará a `img-001.jpg', `img-002.jpg', etc.

zmv -v -- '**/(*).old' '$1'

Elimina la extensión `.old' de los archivos recursivamente. El `--' es importante aquí si el nombre del archivo comienza con un guion. Esto podría potencialmente sobrescribir archivos existentes (ver opción -f).

zmv -v 'old_dir/(*)' 'new_dir/$1'

Mueve todos los archivos y directorios de `old_dir' a `new_dir'. Tenga en cuenta que si `new_dir' ya existe, los archivos se moverán dentro de él. Si `new_dir' no existe, se creará.

zmv -v '(*)' '$1.bak'

Agrega la extensión `.bak' a todos los archivos en el directorio actual. Tenga en cuenta que esto incluirá `zmv' mismo si se ejecuta como un script, lo que podría ser un problema. También podría sobrescribir archivos existentes (ver opción -f).

zmv -v '(*~*.txt)' '$1.old'

Agrega la extensión `.old' a todos los archivos excepto a los que terminan en `.txt'.

zmv -v '*.jpg' '${f:r}.png'

Cambia la extensión de todos los archivos `.jpg' a `.png'. La parte ${f:r} significa la extensión del nombre de archivo eliminada.

zmv -v 'my.old.stuff.txt' 'my.new.stuff.txt'

El patrón siempre se trata como un patrón EXTENDED_GLOB. Cualquier archivo cuyo nombre no cambie por la sustitución simplemente se ignora. Cualquier error (una sustitución resultó en una cadena vacía, dos sustituciones dieron el mismo resultado, el destino era un archivo regular existente y -f no se dio) causa que toda la función se aborte sin hacer nada.

Además del reemplazo de patrones, la variable $f puede ser referenciada en el segundo argumento (reemplazo). Esto hace posible usar la sustitución de variables para alterar el argumento; ver los ejemplos a continuación.

Opciones:

-f
Forzar la sobrescritura de archivos de destino. Actualmente no se pasa al comando mv/cp/ln debido a las peculiaridades de las implementaciones (pero puedes usar -o-f para hacer eso).
-i
Interactivo: muestra cada línea que se va a ejecutar y pregunta al usuario si la debe ejecutar. `Y' o `y' la ejecutará, cualquier otra cosa la omitirá. Tenga en cuenta que solo necesita escribir un carácter.
-n
No ejecutar: imprime lo que sucedería, pero no lo haga.
-q
Desactivar calificadores de glob desnudos: ahora asumido por defecto, por lo que esto no tiene efecto.
-Q
Forzar calificadores de glob desnudos. No active esto a menos que esté realmente usando calificadores de glob en un patrón.
-s
Simbólico, pasado a ln; solo funciona con -L.
-v
Verboso: imprime cada comando a medida que se ejecuta.
-w
Selecciona las partes comodín del patrón, como se describió anteriormente, y agrega implícitamente paréntesis para referirse a ellas.
-W
Igual que -w, con la adición de convertir comodines en el patrón de reemplazo en referencias secuenciales de ${1} .. ${N}.
-C
-L
-M
Forzar cp, ln o mv, respectivamente, independientemente del nombre de la función.
-p programa
Llama a programa en lugar de cp, ln o mv. Haga lo que haga, debería al menos entender la forma `programa -- nombreantiguo nombrenuevo' donde nombreantiguo y nombrenuevo son nombres de archivo generados por zmv. programa se dividirá en palabras, por lo que podría ser, por ejemplo, el nombre de una herramienta de archivo más un subcomando de copia o renombrado.
-P programa
Como -p programa, excepto que programa no acepta un `--' posterior para indicar el final de las opciones. En este caso, los nombres de archivo deben estar ya en un formato sensato para el programa en cuestión.
-o cadenadeopciones
La cadenadeopciones se divide en palabras y se pasa verbatim al comando cp, ln o mv llamado para realizar el trabajo. Probablemente debería comenzar con un `-'.

Más ejemplos:

zmv -v '(* *)' '${1// /_}'

Para cualquier archivo en el directorio actual con al menos un espacio en el nombre, reemplace cada espacio por un guion bajo y muestre los comandos ejecutados.

zmv -v '* *' '${f// /_}'

Esto hace exactamente lo mismo al referirse al nombre de archivo almacenado en $f.

Para obtener ejemplos más completos y otros detalles de implementación, consulte el archivo fuente de zmv, generalmente ubicado en uno de los directorios nombrados en su fpath, o en Functions/Misc/zmv en la distribución de zsh.

zrecompile

zrecompile
Ver `Recompiling Functions' arriba.

zstyle+

zstyle+ contexto estilo valor [ + subcontexto estilo valor ... ]
Esto hace que la definición de estilos sea un poco más simple al usar un único `+' como token especial que le permite agregar un nombre de contexto al nombre de contexto utilizado anteriormente. De esta manera:
zstyle+ ':foo:bar' estilo1 valor1 \ 
       +':baz'     estilo2 valor2 \ 
       +':frob'    estilo3 valor3

Esto define estilo1 con valor1 para el contexto :foo:bar como de costumbre, pero también define estilo2 con valor2 para el contexto :foo:bar:baz y estilo3 con valor3 para :foo:bar:frob. Cualquier subcontexto puede ser la cadena vacía para reutilizar el primer contexto sin cambios.

Estilos

insert-tab
La función zed *establece* este estilo en el contexto `:completion:zed:*' para desactivar la compleción cuando se escribe TAB al principio de una línea. Puede anular esto estableciendo su propio valor para este contexto y estilo.
pager
La función nslookup busca este estilo en el contexto `:nslookup' para determinar el programa utilizado para mostrar la salida que no cabe en una sola pantalla.
prompt
rprompt
La función nslookup busca este estilo en el contexto `:nslookup' para establecer el prompt y el prompt del lado derecho, respectivamente. Se pueden usar las expansiones habituales para los parámetros PS1 y RPS1 (consulte EXPANSION OF PROMPT SEQUENCES en zshmisc(1)).
