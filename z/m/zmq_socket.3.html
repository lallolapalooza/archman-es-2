Paquete: zeromq

Licencias: MPL2

ZMQ_SOCKET(3) Manual de 0MQ ZMQ_SOCKET(3)

NOMBRE

zmq_socket - crear un socket 0MQ

SINOPSIS

void *zmq_socket (void *context, int type);

DESCRIPCIÓN

La función zmq_socket() creará un socket 0MQ dentro del context especificado y devolverá un manejador opaco al socket recién creado. El argumento type especifica el tipo de socket, que determina la semántica de la comunicación a través del socket.

El socket recién creado está inicialmente sin enlazar y no está asociado a ningún punto final. Para establecer un flujo de mensajes, primero se debe conectar un socket a al menos un punto final con zmq_connect(3), o se deben crear al menos un punto final para aceptar conexiones entrantes con zmq_bind(3).

Diferencias clave con los sockets convencionales. En general, los sockets convencionales presentan una interfaz síncrona ya sea a flujos de bytes fiables orientados a la conexión (SOCK_STREAM), o a datagramas no fiables sin conexión (SOCK_DGRAM). En comparación, los sockets 0MQ presentan una abstracción de una cola de mensajes asíncrona, con la semántica de cola exacta dependiendo del tipo de socket en uso. Donde los sockets convencionales transfieren flujos de bytes o datagramas discretos, los sockets 0MQ transfieren mensajes discretos.

El hecho de que los sockets 0MQ sean asíncronos significa que los tiempos de configuración y desmantelamiento de la conexión física, reconexión y entrega efectiva son transparentes para el usuario y organizados por 0MQ. Además, los mensajes pueden ser enviados en cola en caso de que un par no esté disponible para recibirlos.

Los sockets convencionales solo permiten relaciones estrictas de uno a uno (dos pares), de muchos a uno (muchos clientes, un servidor), o en algunos casos de uno a muchos (multidifusión). Con la excepción de ZMQ_PAIR y ZMQ_CHANNEL, los sockets 0MQ pueden conectarse a múltiples puntos finales usando zmq_connect(), mientras aceptan simultáneamente conexiones entrantes de múltiples puntos finales enlazados al socket usando zmq_bind(), permitiendo así relaciones de muchos a muchos.

Seguridad de hilos. 0MQ tiene tipos de socket seguros para hilos y otros que no lo son. Las aplicaciones NO DEBEN usar un socket que no sea seguro para hilos desde múltiples hilos bajo ninguna circunstancia. Hacerlo resulta en un comportamiento indefinido.

Los siguientes son los sockets seguros para hilos: * ZMQ_CLIENT * ZMQ_SERVER * ZMQ_DISH * ZMQ_RADIO * ZMQ_SCATTER * ZMQ_GATHER * ZMQ_PEER * ZMQ_CHANNEL

Tipos de socket. Las siguientes secciones presentan los tipos de socket definidos por 0MQ, agrupados por el patrón de mensajería general que se construye a partir de tipos de socket relacionados.

Patrón cliente-servidor

El patrón cliente-servidor se utiliza para permitir que un único servidor ZMQ_SERVER hable con uno o más clientes ZMQ_CLIENT. El cliente siempre inicia la conversación, después de lo cual cualquiera de los pares puede enviar mensajes asíncronamente al otro.

El patrón cliente-servidor está formalmente definido por http://rfc.zeromq.org/spec:41.


Nota

Cliente-servidor todavía está en fase de borrador.

ZMQ_CLIENT

Un socket ZMQ_CLIENT habla con un socket ZMQ_SERVER. Cualquiera de los pares puede conectarse, aunque el modelo habitual y recomendado es enlazar el ZMQ_SERVER y conectar el ZMQ_CLIENT.

Si el socket ZMQ_CLIENT ha establecido una conexión, zmq_send(3) aceptará mensajes, los pondrá en cola y los enviará tan rápido como la red lo permita. El límite del búfer de salida se define por la marca de agua alta para el socket. Si el búfer de salida está lleno, o, para transportes orientados a la conexión, si la opción ZMQ_IMMEDIATE está establecida y no hay un par conectado, zmq_send(3) se bloqueará. El socket ZMQ_CLIENT no descartará mensajes.

Cuando un socket ZMQ_CLIENT está conectado a múltiples sockets ZMQ_SERVER, los mensajes salientes se distribuyen entre los pares conectados de forma rotatoria. Del mismo modo, el socket ZMQ_CLIENT recibe mensajes de forma justa de cada par conectado. Este uso solo tiene sentido para protocolos sin estado.

Los sockets ZMQ_CLIENT son seguros para hilos y pueden usarse desde múltiples hilos al mismo tiempo. Tenga en cuenta que las respuestas de un socket ZMQ_SERVER irán al primer hilo cliente que llame a zmq_msg_recv(3). Si necesita que las respuestas vuelvan al hilo original, use un socket ZMQ_CLIENT por hilo.


Nota

Los sockets ZMQ_CLIENT son seguros para hilos. No aceptan la opción ZMQ_SNDMORE en envíos ni ZMQ_RCVMORE en recepciones. Esto los limita a datos de una sola parte. La intención es extender la API para permitir la dispersión/recolección de datos multipartes.

ZMQ_SERVER

Un socket ZMQ_SERVER habla con un conjunto de sockets ZMQ_CLIENT. Un socket ZMQ_SERVER solo puede responder a un mensaje entrante: el par ZMQ_CLIENT siempre debe iniciar una conversación.

Cada mensaje recibido tiene un routing_id que es un entero sin signo de 32 bits. La aplicación puede obtenerlo con zmq_msg_routing_id(3). Para enviar un mensaje a un par ZMQ_CLIENT dado, la aplicación debe establecer el routing_id del par en el mensaje, usando zmq_msg_set_routing_id(3).

Si el routing_id no se especifica, o no se refiere a un par cliente conectado, la llamada de envío fallará con EHOSTUNREACH. Si el búfer de salida para el par cliente está lleno, la llamada de envío se bloqueará, a menos que se use ZMQ_DONTWAIT en el envío, en cuyo caso fallará con EAGAIN. El socket ZMQ_SERVER no descartará mensajes en ningún caso.


Nota

Los sockets ZMQ_SERVER son seguros para hilos. No aceptan la opción ZMQ_SNDMORE en envíos ni ZMQ_RCVMORE en recepciones. Esto los limita a datos de una sola parte. La intención es extender la API para permitir la dispersión/recolección de datos multipartes.

Patrón radio-dish

El patrón radio-dish se utiliza para la distribución de uno a muchos de datos desde un único publisher a múltiples subscribers en modo fan-out.

Radio-dish utiliza grupos (frente a temas de Pub-sub), los sockets Dish pueden unirse a un grupo y cada mensaje enviado por los sockets Radio pertenece a un grupo.

Radio-dish pattern

The radio-dish pattern is used for one-to-many distribution of data from a single publisher to multiple subscribers. This pattern is similar to the publish-subscribe pattern, but allows subscribers to subscribe to a subset of the published data via group prefix matching of PubSub).


Note

Radio-dish is still in draft phase.

ZMQ_RADIO

A socket of type ZMQ_RADIO is used by a publisher to distribute data. Each message belong to a group, a group is specified with zmq_msg_set_group(3). Messages are distributed to all members of a group. The zmq_recv(3) function is not implemented for this socket type.

When a ZMQ_RADIO socket enters the mute state due to having reached the high water mark for a subscriber, then any messages that would be sent to the subscriber in question shall instead be dropped until the mute state ends. The zmq_send() function shall never block for this socket type.


Note

ZMQ_RADIO sockets are threadsafe. They do not accept the ZMQ_SNDMORE option on sends. This limits them to single part data.

ZMQ_DISH

A socket of type ZMQ_DISH is used by a subscriber to subscribe to groups distributed by a radio. Initially a ZMQ_DISH socket is not subscribed to any groups, use zmq_join(3) to join a group. To get the group the message belong to call zmq_msg_group(3). The zmq_send() function is not implemented for this socket type.

ZMQ_DISH sockets are threadsafe. They do not accept ZMQ_RCVMORE on receives. This limits them to single part data.

Publish-subscribe pattern

The publish-subscribe pattern is used for one-to-many distribution of data from a single publisher to multiple subscribers in a fan out fashion.

The publish-subscribe pattern is formally defined by http://rfc.zeromq.org/spec:29.

ZMQ_PUB

A socket of type ZMQ_PUB is used by a publisher to distribute data. Messages sent are distributed in a fan out fashion to all connected peers. The zmq_recv(3) function is not implemented for this socket type.

When a ZMQ_PUB socket enters the mute state due to having reached the high water mark for a subscriber, then any messages that would be sent to the subscriber in question shall instead be dropped until the mute state ends. The zmq_send() function shall never block for this socket type.

Pipeline pattern

The pipeline pattern is used for distributing data to nodes arranged in a pipeline. Data always flows down the pipeline, and each stage of the pipeline is connected to at least one node. When a pipeline stage is connected to multiple nodes data is round-robined among all connected nodes.

The pipeline pattern is formally defined by http://rfc.zeromq.org/spec:30.

ZMQ_PUSH

A socket of type ZMQ_PUSH is used by a pipeline node to send messages to downstream pipeline nodes. Messages are round-robined to all connected downstream nodes. The zmq_recv() function is not implemented for this socket type.

When a ZMQ_PUSH socket enters the mute state due to having reached the high water mark for all downstream nodes, or, for connection-oriented transports, if the ZMQ_IMMEDIATE option is set and there are no downstream nodes at all, then any zmq_send(3) operations on the socket shall block until the mute state ends or at least one downstream node becomes available for sending; messages are not discarded.

Un socket de tipo ZMQ_PULL es utilizado por un nodo de pipeline para recibir mensajes de nodos de pipeline anteriores. Los mensajes se distribuyen de forma justa (fair-queued) entre todos los nodos conectados anteriores. La función zmq_send() no está implementada para este tipo de socket.

Patrón Scatter-gather

El patrón scatter-gather es la versión segura para hilos del patrón de pipeline.
El patrón scatter-gather se utiliza para distribuir datos a _nodos_ organizados en
un pipeline. Los datos siempre fluyen hacia abajo en el pipeline, y cada etapa del pipeline
está conectada al menos a un _nodo_. Cuando una etapa del pipeline está conectada a múltiples
_nodos_, los datos se distribuyen por turnos (round-robin) entre todos los _nodos_ conectados.
ZMQ_SCATTER
^^^^^^^^
Un socket de tipo 'ZMQ_SCATTER' es utilizado por un _nodo_ de scatter-gather para enviar mensajes
a _nodos_ de scatter-gather posteriores. Los mensajes se distribuyen por turnos (round-robin) a todos los _nodos_ conectados
posteriores. La función _zmq_recv()_ no está implementada para este
tipo de socket.
Cuando un socket 'ZMQ_SCATTER' entra en el estado de 'silencio' debido a haber alcanzado la marca de agua alta (high water mark) para todos los _nodos_ posteriores, o, para transportes orientados a conexión, si la opción ZMQ_IMMEDIATE está establecida y no hay _nodos_ posteriores en absoluto,
entonces cualquier operación zmq_send[3] en el socket se bloqueará hasta que el estado de silencio termine o al menos un _nodo_ posterior esté disponible para enviar; los mensajes no se descartan.
NOTA: Los sockets 'ZMQ_SCATTER' son seguros para hilos. No aceptan ZMQ_RCVMORE en las recepciones.
Esto los limita a datos de una sola parte.

Patrón de par exclusivo

El patrón de par exclusivo se utiliza para conectar un par a exactamente otro par. Este patrón se utiliza para la comunicación entre hilos a través del transporte inproc.

El patrón de par exclusivo está formalmente definido por http://rfc.zeromq.org/spec:31.

ZMQ_PAIR

Un socket de tipo ZMQ_PAIR solo puede conectarse a un único par en un momento dado. No se realiza ningún enrutamiento ni filtrado de mensajes en los mensajes enviados a través de un socket ZMQ_PAIR.

Cuando un socket ZMQ_PAIR entra en el estado de silencio debido a haber alcanzado la marca de agua alta para el par conectado, o, para transportes orientados a conexión, si la opción ZMQ_IMMEDIATE está establecida y no hay ningún par conectado, entonces cualquier operación zmq_send(3) en el socket se bloqueará hasta que el par esté disponible para enviar; los mensajes no se descartan.

Si bien los sockets ZMQ_PAIR pueden usarse sobre transportes distintos de zmq_inproc(7), su incapacidad para reconectarse automáticamente, junto con el hecho de que las nuevas conexiones entrantes se terminarán mientras existan conexiones anteriores (incluidas las que están en estado de cierre), los hace inadecuados para TCP en la mayoría de los casos.


Nota

Los sockets ZMQ_PAIR están diseñados para la comunicación entre hilos a través del transporte zmq_inproc(7) y no implementan funcionalidades como la reconexión automática.

Patrón peer-to-peer

El patrón peer-to-peer se utiliza para conectar un par a múltiples pares. Los pares pueden conectarse y enlazarse, y mezclar ambos con el mismo socket. El patrón peer-to-peer es útil para construir redes peer-to-peer (por ejemplo, zyre, bitcoin, torrent) donde un par puede aceptar conexiones de otros pares o conectarse a ellos.


Nota

Peer-to-peer todavía está en fase de borrador.

ZMQ_PEER

Un socket ZMQ_PEER se comunica con un conjunto de sockets ZMQ_PEER.

Para conectarse y obtener el routing_id del par, utilice zmq_connect_peer(3).

Cada mensaje recibido tiene un routing_id que es un entero sin signo de 32 bits. La aplicación puede obtenerlo con zmq_msg_routing_id(3).

Para enviar un mensaje a un par ZMQ_PEER dado, la aplicación debe establecer el routing_id del par en el mensaje, utilizando zmq_msg_set_routing_id(3).

Si el routing_id no se especifica, o no se refiere a un par cliente conectado, la llamada de envío fallará con EHOSTUNREACH. Si el buffer de salida para el par está lleno, la llamada de envío se bloqueará, a menos que se use ZMQ_DONTWAIT en el envío, en cuyo caso fallará con EAGAIN. El socket ZMQ_PEER no descartará mensajes en ningún caso.


Nota

Los sockets ZMQ_PEER son seguros para hilos. No aceptan la opción ZMQ_SNDMORE en los envíos ni ZMQ_RCVMORE en las recepciones. Esto los limita a datos de una sola parte.

Patrón Nativo

El patrón nativo se utiliza para comunicarse con pares TCP y permite solicitudes y respuestas asíncronas en cualquier dirección.

ZMQ_STREAM

Un socket de tipo ZMQ_STREAM se utiliza para enviar y recibir datos TCP de un par que no es 0MQ, cuando se utiliza el transporte tcp://. Un socket ZMQ_STREAM puede actuar como cliente y/o servidor, enviando y/o recibiendo datos TCP de forma asíncrona.

Al recibir datos TCP, un socket ZMQ_STREAM antepondrá una parte del mensaje que contiene el routing id del par de origen al mensaje antes de pasarlo a la aplicación. Los mensajes recibidos se distribuyen de forma justa (fair-queued) entre todos los pares conectados.

Al enviar datos TCP, un socket ZMQ_STREAM eliminará la primera parte del mensaje y la utilizará para determinar el routing id del par al que se enrutará el mensaje, y los mensajes no enrutables provocarán un error EHOSTUNREACH o EAGAIN.

ZMQ_STREAM SOCKET

A socket of type ZMQ_STREAM is a special-purpose socket type designed for implementing arbitrary protocols on top of ZeroMQ. A ZMQ_STREAM socket acts like a pair of connected ZMQ_REQ and ZMQ_REP sockets. It is a duplex socket, allowing you to send and receive data without regard to the pattern. You can connect to a server, use the zmq_getsockopt call with the ZMQ_ROUTING_ID option to fetch the socket routing id, and then fetch the socket routing id using the zmq_getsockopt call with the ZMQ_ROUTING_ID option.

To close a specific connection, send the routing id frame followed by a zero-length message (see EXAMPLE section).

When a connection is made, a zero-length message will be received by the application. Similarly, when the peer disconnects (or the connection is lost), a zero-length message will be received by the application.

You must send one routing id frame followed by one data frame. The ZMQ_SNDMORE flag is required for routing id frames but is ignored on data frames.

Request-reply pattern

The request-reply pattern is used for sending requests from a ZMQ_REQ client to one or more ZMQ_REP services, and receiving subsequent replies to each request sent.

The request-reply pattern is formally defined by http://rfc.zeromq.org/spec:28.

ZMQ_REQ

A socket of type ZMQ_REQ is used by a client to send requests to and receive replies from a service. This socket type allows only an alternating sequence of zmq_send(request) and subsequent zmq_recv(reply) calls. Each request sent is round-robined among all services, and each reply received is matched with the last issued request.

For connection-oriented transports, If the ZMQ_IMMEDIATE option is set and there is no service available, then any send operation on the socket shall block until at least one service becomes available. The REQ socket shall not discard messages.

ZMQ_REP

A socket of type ZMQ_REP is used by a service to receive requests from and send replies to a client. This socket type allows only an alternating sequence of zmq_recv(request) and subsequent zmq_send(reply) calls. Each request received is fair-queued from among all clients, and each reply sent is routed to the client that issued the last request. If the original requester does not exist any more the reply is silently discarded.

ZMQ_DEALER

A socket of type ZMQ_DEALER is an advanced pattern used for extending request/reply sockets. Each message sent is round-robined among all connected peers, and each message received is fair-queued from all connected peers.

When a ZMQ_DEALER socket enters the mute state due to having reached the high water mark for all peers, or, for connection-oriented transports, if the ZMQ_IMMEDIATE option is set and there are no peers at all, then any zmq_send(3) operations on the socket shall block until the mute state ends or at least one peer becomes available for sending; messages are not discarded.

When a ZMQ_DEALER socket is connected to a ZMQ_REP socket each message sent must consist of an empty message part, the delimiter, followed by one or more body parts.

Direction Bidirectional

ZMQ_ROUTER

A socket of type ZMQ_ROUTER is an advanced socket type used for extending request/reply sockets. When receiving messages a ZMQ_ROUTER socket shall prepend a message part containing the routing id of the originating peer to the message before passing it to the application. Messages received are fair-queued from among all connected peers. When sending messages a ZMQ_ROUTER socket shall remove the first part of the message and use it to determine the _routing id _ of the peer the message shall be routed to. If the peer does not exist anymore, or has never existed, the message shall be silently discarded. However, if ZMQ_ROUTER_MANDATORY socket option is set to 1, the socket shall fail with EHOSTUNREACH in both cases.

When a ZMQ_ROUTER socket enters the mute state due to having reached the high water mark for all peers, then any messages sent to the socket shall be dropped until the mute state ends. Likewise, any messages routed to a peer for which the individual high water mark has been reached shall also be dropped. If, ZMQ_ROUTER_MANDATORY is set to 1, the socket shall block or return EAGAIN in both cases.

When a ZMQ_ROUTER socket has ZMQ_ROUTER_MANDATORY flag set to 1, the socket shall generate ZMQ_POLLIN events upon reception of messages from one or more peers. Likewise, the socket shall generate ZMQ_POLLOUT events when at least one message can be sent to one or more peers.

When a ZMQ_REQ socket is connected to a ZMQ_ROUTER socket, in addition to the routing id of the originating peer each message received shall contain an empty delimiter message part. Hence, the entire structure of each received message as seen by the application becomes: one or more routing id parts, delimiter part, one or more body parts. When sending replies to a ZMQ_REQ socket the application must include the delimiter part.

Direction Bidirectional

Outgoing routing strategy See text
Incoming routing strategy Fair-queued
Action in mute state Drop (see text)

RETURN VALUE

The zmq_socket() function shall return an opaque handle to the newly created socket if successful. Otherwise, it shall return NULL and set errno to one of the values defined below.

ERRORS

EINVAL

The requested socket type is invalid.

EFAULT

The provided context is invalid.

EMFILE

The limit on the total number of open 0MQ sockets has been reached.

ETERM

The context specified was shutdown or terminated.

NAME

zmq_socket, zmq_close, zmq_ctx_destroy, zmq_ctx_new, zmq_ctx_term, zmq_ctx_shutdown, zmq_ctx_recv, zmq_ctx_send - 0MQ socket and context management

SYNOPSIS

#include <zmq.h>
void *zmq_socket (void *context, int type);
int zmq_close (void *s);
int zmq_ctx_destroy (void *context);
void *zmq_ctx_new (void);
int zmq_ctx_term (void *context);
int zmq_ctx_shutdown (void *context);
int zmq_ctx_recv (void *context, int timeout);
int zmq_ctx_send (void *context, int timeout);

DESCRIPTION

The zmq_socket function shall create a new 0MQ socket of the specified type within the supplied context. The context is a pointer to the 0MQ execution context returned by a prior call to zmq_ctx_new. The type argument specifies the socket type.

The following socket types are available:

zmq_req
The 0MQ REQ socket type is used by a client to send requests to and receive replies from a 0MQ service.
zmq_rep
The 0MQ REP socket type is used by a service to receive requests from and send replies to a 0MQ client.
zmq_router
The 0MQ ROUTER socket type is a generic server socket that can receive messages from any client and send replies to specific clients. It supports advanced messaging patterns, like routing and load balancing.
zmq_dealer
The 0MQ DEALER socket type is a generic client socket that can send messages to any server and receive replies from any server. It supports advanced messaging patterns, like routing and load balancing.
zmq_push
The 0MQ PUSH socket type is used by a high-speed, asynchronous message queue.
zmq_pull
The 0MQ PULL socket type is used to receive messages from a PUSH socket.
zmq_pub
The 0MQ PUB socket type is used to publish messages to a group of subscribers.
zmq_sub
The 0MQ SUB socket type is used to subscribe to messages published by a PUB socket.
zmq_pair
The 0MQ PAIR socket type is used to create exclusive connections between two sockets.
zmq_stream
The 0MQ STREAM socket type is used to establish persistent connections between two sockets.

The zmq_close function shall close the specified socket s. Any messages remaining in the socket shall be discarded. Closing a socket invalidates any zmq_msg_t objects previously received from it. If a message was received using zmq_msg_recv and has not yet been processed by zmq_msg_close, the application must call zmq_msg_close on it before calling zmq_close on the socket.

The zmq_ctx_new function shall create a new 0MQ execution context. The context is a container for all sockets and other 0MQ objects. The application must create at least one context before creating any sockets.

The zmq_ctx_destroy function shall destroy the specified 0MQ context. All sockets within the context shall be closed automatically. Any messages remaining in any socket shall be discarded. The behaviour is undefined if the context is destroyed while there are still active operations in progress.

The zmq_ctx_term function shall terminate the specified 0MQ context. All sockets within the context shall be closed automatically. Any messages remaining in any socket shall be discarded. The behaviour is undefined if the context is terminated while there are still active operations in progress.

The zmq_ctx_shutdown function shall initiate an orderly shutdown of the specified 0MQ context. This function is a non-blocking call and returns immediately. It can be used to initiate a shutdown of the context from another thread.

The zmq_ctx_recv and zmq_ctx_send functions shall block until the specified timeout expires or until the context is shut down. They return the number of messages received or sent, respectively, or -1 if an error occurred. These functions are useful for performing context-level operations such as shutting down the context gracefully.

RETURN VALUE

The zmq_socket function shall return a pointer to the newly created socket if the call was successful. Otherwise, it shall return NULL and set errno to an appropriate value.

The zmq_close, zmq_ctx_destroy, zmq_ctx_term, zmq_ctx_shutdown, zmq_ctx_recv, and zmq_ctx_send functions shall return 0 if the call was successful. Otherwise, they shall return -1 and set errno to an appropriate value.

The zmq_ctx_new function shall return a pointer to the newly created context if the call was successful. Otherwise, it shall return NULL and set errno to an appropriate value.

ERRORS

The zmq_socket function shall fail if:

EAGAIN
The requested socket type is not supported by the current 0MQ version.
EINVAL
The provided context is invalid, or the specified type is not a valid socket type.
ENOTSOCK
The provided context is not a valid 0MQ context.
EMFILE
The process has reached the maximum number of file descriptors allowed by the operating system.
ENFILE
The system has reached the maximum number of open sockets allowed.

The zmq_close function shall fail if:

EBADF
The provided socket s is invalid.

The zmq_ctx_destroy and zmq_ctx_term functions shall fail if:

EINVAL
The provided context is invalid.

The zmq_ctx_new function shall fail if:

ENOMEM
The system is unable to allocate sufficient memory to create the context.

The zmq_ctx_recv and zmq_ctx_send functions shall fail if:

EINVAL
The provided context is invalid.
ETIME
The specified timeout expired before the operation could be completed.
ETERM
The context has been terminated.

EXAMPLE

Example demonstrating the use of zmq_socket, zmq_send, and zmq_recv:

/*
 * Get HTTP request; routing id frame and then request
 */
routing_id_size = zmq_recv (socket, routing_id, 256, 0);
assert (routing_id_size > 0);
do {
        raw_size = zmq_recv (socket, raw, 256, 0);
        assert (raw_size >= 0);
} while (raw_size == 256);
/* Prepares the response */
char http_response [] =
        "HTTP/1.0 200 OK\r\n"
        "Content-Type: text/plain\r\n"
        "\r\n"
        "Hello, World!";
/* Sends the routing id frame followed by the response */
zmq_send (socket, routing_id, routing_id_size, ZMQ_SNDMORE);
zmq_send (socket, http_response, strlen (http_response), 0);
/* Closes the connection by sending the routing id frame followed by a zero response */
zmq_send (socket, routing_id, routing_id_size, ZMQ_SNDMORE);
zmq_send (socket, 0, 0, 0);
}
zmq_close (socket);
zmq_ctx_destroy (ctx);
