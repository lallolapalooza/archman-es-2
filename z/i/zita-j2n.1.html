ZITA-J2N(1) Manual de Comandos Generales ZITA-J2N(1)

NOMBRE

zita-j2n, zita-n2j - Clientes Jack para transportar audio multicanal a través de una red local.

SINOPSIS

zita-j2n [ opciones ] direccion-ip puerto-ip
zita-n2j [ opciones ] direccion-ip puerto-ip
zita-j2n [ opciones ] direccion-ip puerto-ip interfaz
zita-n2j [ opciones ] direccion-ip puerto-ip interfaz

DESCRIPCIÓN

General

Las aplicaciones zita-j2n (remitente) y zita-n2j (receptor) permiten intercambiar hasta 64 canales de flujos de audio sin comprimir de calidad completa entre dos o más sistemas que ejecutan el servidor de audio Jack. El remitente y el receptor (o receptores) pueden tener su propia frecuencia de muestreo y tamaño de período, y no se asume ninguna sincronización de reloj de palabra entre ellos. El receptor utiliza remuestreo adaptativo para convertir los flujos de audio a su frecuencia de muestreo local.

No existe una relación maestro/esclavo entre el remitente y el receptor (o receptores). Este es un objetivo de diseño explícito. En todos los aspectos, el resultado neto de usar zita-njbridge es similar a tener conexiones de audio analógicas entre las tarjetas de sonido de los sistemas que lo utilizan. Nada que un remitente pueda hacer afectará al receptor (o receptores), aparte de que las señales de audio estén disponibles o vuelvan a estar en silencio si no hay remitente. Los Xruns o ciclos omitidos no afectarán la sincronización o el remuestreo. El funcionamiento libre de Jack en cualquiera de los extremos suspenderá temporalmente la operación.

Zita-njbridge se puede utilizar de dos maneras: uno a uno, o uno a muchos. Se admiten tanto IPv4 como IPv6.

Para una configuración uno a uno, se debe usar la primera forma de los comandos mostrados arriba. El protocolo utilizado es UDP y la dirección IP requerida tanto para el remitente como para el receptor es la del receptor. Se puede usar un nombre de host en lugar de direcciones IP numéricas; esto se buscará utilizando getaddrinfo().

Para una configuración uno a muchos, se debe usar la segunda forma. El argumento de direccion-ip debe ser una dirección de multidifusión válida, y el argumento obligatorio de interfaz selecciona la interfaz de red a utilizar.

Longitud del filtro del remuestreador.

El receptor utiliza la biblioteca zita-resampler para remuestrear las señales a su tasa local. La longitud del filtro de paso bajo multifase utilizado como parte del algoritmo de remuestreo determina el ancho de banda de audio y agrega latencia. También puede tener un impacto significativo en la carga de la CPU si se reciben muchos canales.

Zita-njbridge seleccionará una longitud de filtro basada en la menor de las frecuencias de muestreo del remitente y el receptor. Para frecuencias de muestreo de 44.1 kHz y superiores, el valor elegido resultará en una atenuación de no más de 0.1 dB hasta 20 kHz. La opción --filt permite anular la configuración automática, pero normalmente no será necesario.

Problemas de latencia.

Al conectar dos sistemas Jack con períodos no sincronizados, la latencia adicional mínima en condiciones de peor caso es la suma de los dos tiempos de período. Latencia adicional significa cualquier latencia requerida para que la conexión funcione sin interrupción. La latencia de ida y vuelta desde una entrada analógica ideal (cero latencia adicional) en el remitente hasta una salida analógica ideal (ídem) en el receptor será el doble de este valor. Condiciones de peor caso significa que tanto el remitente como el receptor pueden ejecutarse en momentos arbitrarios dentro de sus respectivos períodos.

Zita-njbridge está diseñado para proporcionar una latencia adicional definida y constante. El valor objetivo es la suma de los dos períodos, más el retraso de remuestreo, más cualquier búfer adicional especificado por el usuario. La latencia real será este valor más el retraso promedio de la red. Este último es desconocido, por lo que no hay forma de compensarlo. Esto sería posible utilizando un canal de retorno o alguna forma de sincronizar los relojes de los dos sistemas, que luego podrían usarse para medir el retraso promedio de la red. La versión actual de zita-njbridge no proporciona esto, ya que está pensada para su uso en una red local. Una red Ethernet Gigabit dedicada o con poca carga puede proporcionar retrasos de red típicos muy inferiores a un milisegundo.

La opción --buff de zita-n2j agrega el número especificado de milisegundos a la latencia objetivo. El valor predeterminado es 10 ms, lo cual es más que suficiente en una red local Gigabit moderadamente cargada. Esto se puede establecer en cero, por ejemplo, cuando se sabe que el remitente siempre se ejecutará cerca del inicio de su período Jack y la fluctuación del retraso de la red es menor que este período.

Si hay alguna fluctuación del retraso de la red superior a 10 ms, será necesario aumentar el tiempo de búfer adicional para evitar la interrupción ocasional de los flujos de audio recibidos.

La latencia no depende de cuándo se ejecuta exactamente el remitente dentro de su período Jack. Esto es similar a la reproducción en una tarjeta de sonido: cuando las muestras de reproducción se escriben mucho antes de que deban hacerlo, esto no reduce la latencia, los datos simplemente se almacenan en búfer hasta el final del período. En el caso de zita-njbridge, el tiempo restante está disponible para el retraso de la red. Por eso, cuando el remitente solo tiene poca carga y el retraso de la red es pequeño, es posible usar --buff 0 en los receptores.

Uso en redes de área amplia o inalámbricas.

La implementación actual está diseñada para usarse en redes locales que proporcionan una entrega de paquetes más o menos confiable, con retrasos bajos o moderados. La pérdida ocasional de paquetes no afectará la sincronización o el remuestreo, pero se ignorarán las muestras que lleguen desordenadas (ya habrán sido reemplazadas por silencio antes). El búfer adicional (usando la opción --buff) permitirá una señal ininterrumpida en presencia de fluctuación del retraso, a costa de latencia adicional. Zita-njbridge puede ser utilizable en conexiones de internet de larga distancia, pero tenga en cuenta que no fue diseñado para ello.

El rendimiento en redes inalámbricas es puramente una cuestión de azar. De nuevo, zita-njbridge no está diseñado para dicho uso.

OPCIONES

Opciones comunes

--help

Imprime el resumen de la línea de comandos y las opciones.
--jname nombre

Selecciona el nombre del cliente Jack. El valor predeterminado es 'zita-j2n' o 'zita-n2j'.
--jserv servidor

Selecciona el servidor Jack al que conectarse.
--ipv4
--ipv6
Utiliza solo el tipo de dirección IP especificado.

Opciones de zita-j2n

--chan canales

El número de canales a transmitir, el valor predeterminado es 2 canales.
--16bit

Envía audio como muestras de enteros con signo de 16 bits.
--24bit

Envía audio como muestras de enteros con signo de 24 bits. Este es el formato predeterminado.
--float

Envía audio como muestras de punto flotante de 32 bits (formato interno de Jack).
--mtu MTU

Informa a zita-j2n de la MTU de la ruta, lo que le permite usar paquetes de hasta ese tamaño. El valor predeterminado es 1500. Tenga en cuenta que los valores grandes de MTU en una red compartida pueden aumentar la fluctuación del retraso de la red.
--hops saltos

Establece el número máximo de saltos para paquetes de multidifusión. El valor predeterminado es uno, es decir, la multidifusión es solo a la red local.

Opciones de zita-n2j

--chan lista

Una lista de números de canales en orden ascendente y separados por comas o guiones (este último indica un rango). Los números de canal comienzan en 1. Solo los canales solicitados serán remuestreados y tendrán un puerto Jack correspondiente. Canales no proporcionados por el remitente

NAME

zita-j2n — JACK client to send audio data to NetJack

SYNOPSIS

zita-j2n [-h] [-d] [-p port] [-f file] [-c channels] [-b buffertime] [-l latency] [-t timeout] [-r rate] [-s samplerate] [-n name] [-i interface] [-a address]

DESCRIPTION

zita-j2n is a JACK client that sends audio data to the NetJack remote client. It opens a network connection to the remote client, and transfers audio data from the JACK input ports to the network socket.

It is designed to provide low latency audio streaming over a network. For best results, use a wired Ethernet connection and ensure that the two machines are on the same subnet and have low network latency between them.

zita-n2j is the companion client that receives the audio data from the network and makes it available to the JACK server.

OPTIONS

-a address

The IP address or hostname of the remote NetJack server. If not specified, it defaults to the first command line argument.
-b buffertime

Set the network buffer size in milliseconds. The default is 10 ms. This value affects latency and stability. A larger value may improve stability on unreliable networks, but increases latency.
-c channels

Set the number of audio channels to transmit. The default is 2. This must match the number of channels on the remote NetJack client.
-d

Enable debug mode. This will print more verbose output to the console.
-f file

Load configuration from a file. The file format is INI-style, with sections for [zita-j2n] and [jack]. Options are the same as the command line options.
-h

Print a help message and exit.
-i interface

Specify the network interface to use for sending data. This is useful if you have multiple network interfaces.
-l latency

Set the target latency in milliseconds. The default is 10 ms. This value is used to determine the buffer sizes for the JACK server and the network connection. Smaller values will result in lower latency but may be less stable.
-n name

Set the JACK client name. The default is "zita-j2n".
-p port

Set the network port to use for sending data. The default is 57120. This must match the port used by the remote NetJack client.
-r rate

Set the resampling rate. The default is 0, which means no resampling is performed. If a non-zero value is specified, audio data will be resampled to this rate. This is useful if the JACK server and the remote NetJack client are running at different sample rates.
-s samplerate

Set the JACK server sample rate. The default is taken from the JACK server. This option is usually not needed.
-t timeout

Set the network connection timeout in milliseconds. The default is 1000 ms. If the connection is not established within this time, zita-j2n will exit.

EXAMPLE

Send audio to a remote NetJack server at 192.168.1.100 on port 57120 with a target latency of 5ms:

zita-j2n -l 5 -a 192.168.1.100 -p 57120
