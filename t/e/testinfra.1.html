EMPEZAR RÁPIDO

Instala testinfra usando pip:

$ pip install pytest-testinfra
# o instala la versión de desarrollo
$ pip install 'git+https://github.com/pytest-dev/pytest-testinfra@main#egg=pytest-testinfra'

Escribe tu primer archivo de pruebas en test_myinfra.py:

def test_passwd_file(host):
    passwd = host.file("/etc/passwd")
    assert passwd.contains("root")
    assert passwd.user == "root"
    assert passwd.group == "root"
    assert passwd.mode == 0o644
def test_nginx_is_installed(host):
    nginx = host.package("nginx")
    assert nginx.is_installed
    assert nginx.version.startswith("1.2")
def test_nginx_running_and_enabled(host):
    nginx = host.service("nginx")
    assert nginx.is_running
    assert nginx.is_enabled

Backends de Conexión

Testinfra viene con varios backends de conexión para la ejecución remota de comandos.

Al instalar, debes seleccionar los backends que requieras como extras para asegurar que las dependencias de Python se satisfacen (ten en cuenta que es posible que aún se requieran varias herramientas empaquetadas por el sistema). Por ejemplo:

$ pip install pytest-testinfra[ansible,salt]

Para todos los backends, los comandos se pueden ejecutar como superusuario con la opción --sudo o como un usuario específico con la opción --sudo-user.

Especificación General de Host

El parámetro --hosts en Testinfra se utiliza para especificar los hosts de destino para las pruebas.

Puedes especificar múltiples hosts separando cada destino con una coma, lo que te permite ejecutar pruebas utilizando diferentes backends en diferentes entornos o máquinas.

El usuario, la contraseña y el puerto son campos opcionales, lo que proporciona flexibilidad según tus requisitos de autenticación y conexión.

Por favor, lee también los detalles de los backends individuales, ya que la especificación del host se maneja de manera ligeramente diferente entre los backends.

Sintaxis:

--hosts=<backend>://<usuario>:<contraseña>@<host>:<puerto>

Componentes:

  • <backend>: tipo de backend a utilizar (por ejemplo, ssh, docker, paramiko, local)
  • <usuario>: nombre de usuario para la autenticación (opcional)
  • <contraseña>: contraseña para la autenticación (opcional)
  • <host>: nombre de host o dirección IP de destino
  • <puerto>: número de puerto de destino (opcional)

Los caracteres especiales (por ejemplo, ":") en los campos de usuario y contraseña deben ser codificados como porcentaje según RFC 3986. Esto se puede hacer usando urllib.parse.quote() en Python.

Por ejemplo:

import urllib.parse
usuario = urllib.parse.quote('usuario:nombre')
contraseña = urllib.parse.quote('c@ntr:seña')
host = 'nombredehost'
puerto = 22
especificacion_host = f"ssh://{usuario}:{contraseña}@{host}:{puerto}"
print(especificacion_host)

Esto asegurará que cualquier carácter especial se codifique correctamente, haciendo que la cadena de conexión sea válida.

Backend SSH con Especificación Completa:

local

Este es el backend predeterminado cuando no se proporcionan hosts (ya sea a través de --hosts o en módulos). Los comandos se ejecutan localmente en un subproceso bajo el usuario actual:

Puedes proporcionar un archivo ssh-config alternativo:

$ pytest --hosts='docker://[usuario@]id_contenedor_o_nombre'

Consulta también el ejemplo *Test Docker images*.

podman

$ pytest --hosts='podman://[usuario@]id_contenedor_o_nombre'

ssh

Este es un backend SSH puro que utiliza el comando ssh. Ejemplo:

$ pytest --hosts='ssh://servidor'
$ pytest --ssh-config=/ruta/a/ssh_config --hosts='ssh://servidor'
$ pytest --ssh-identity-file=/ruta/a/clave --hosts='ssh://servidor'
$ pytest --hosts='ssh://servidor?timeout=60&controlpersist=120'
$ pytest --hosts='ssh://servidor' --ssh-extra-args='-o StrictHostKeyChecking=no'

Por defecto, el tiempo de espera se establece en 10 segundos y ControlPersist en 60 segundos. Puedes deshabilitar la conexión persistente pasando controlpersist=0 a las opciones.

salt

$ pytest --hosts='salt://*'
$ pytest --hosts='salt://minion1,salt://minion2'
$ pytest --hosts='salt://web*'
$ pytest --hosts='salt://G@os:Debian'

Testinfra utilizará el canal de conexión de salt para ejecutar comandos.

ansible

Los inventarios de Ansible pueden usarse para describir qué hosts debe usar Testinfra y cómo conectarlos, utilizando el backend Ansible de Testinfra.

Para usar el backend Ansible, antepón la opción --hosts con ansible://, por ejemplo:

$ pytest --hosts='ansible://all' # prueba todos los hosts del inventario
$ pytest --hosts='ansible://host1,ansible://host2'
$ pytest --hosts='ansible://web*'

Se puede especificar un inventario con la opción --ansible-inventory, de lo contrario, se usa el predeterminado (/etc/ansible/hosts).

El valor ansible_connection en tu inventario se usará para determinar qué backend usar para hosts individuales: local, ssh, paramiko y docker son valores soportados. Otras conexiones (o si estás usando la opción --force-ansible) resultarán en que testinfra ejecute todos los comandos a través de Ansible mismo, lo cual es sustancialmente más lento que los otros backends:

$ pytest --force-ansible --hosts='ansible://all'
$ pytest --hosts='ansible://host?force_ansible=True'

Por defecto, el backend de conexión Ansible intentará primero usar ansible_ssh_private_key_file y ansible_private_key_file para autenticarse, luego recurrirá a ansible_user con las variables ansible_ssh_pass (ambas son necesarias), antes de recurrir finalmente a la configuración SSH de tu propio host.

Este comportamiento puede ser anulado especificando la opción --ssh-identity-file o la opción --ssh-config

Finalmente, estas variables de entorno son compatibles y se pasarán a su correspondiente variable de ansible (Ver documentación de Ansible):

  • ANSIBLE_REMOTE_USER
  • ANSIBLE_SSH_EXTRA_ARGS
  • ANSIBLE_SSH_COMMON_ARGS
  • ANSIBLE_REMOTE_PORT
  • ANSIBLE_BECOME_USER
  • ANSIBLE_BECOME

$ pytest --hosts=

testinfra

Testinfra provides a set of built-in test modules that can be used to implement checks on remote or local systems.

This module enables you to use Testinfra from your pytest tests.

Backends

Testinfra can connect to hosts using a variety of backends. The backend is specified using the --hosts command line option.

ansible

The ansible backend can be used to test remote hosts managed by Ansible. It uses the ansible command and support connecting to a given host and using a given inventory file: 

# will use the default ansible configuration
$ pytest --hosts='ansible://server1'
# specify the inventory file
$ pytest --hosts='ansible://server1?ansible_inventory=/etc/ansible/hosts'
# specify an ansible vault password file
$ pytest --hosts='ansible://server1?ansible_password_file=/etc/ansible/vault.key'
# you can specify vault password file with vault password (not recommended)
$ pytest --hosts='ansible://server1?ansible_vault_password=yourpassword'
# specify a connection user
$ pytest --hosts='ansible://server1?ansible_user=myuser'
# specify ssh key file
$ pytest --hosts='ansible://server1?ansible_private_key_file=/path/to/key.pem'
# specify ansible args
$ pytest --hosts='ansible://server1?ansible_args=--ssh-common-args=\"-o StrictHostKeyChecking=no\"'
# run adhoc command
$ pytest --hosts='ansible://server1?ansible_module=ping'
# test host in remote machine via ssh, using ansible
$ pytest --hosts='ansible://server1,ansible://server2?ansible_inventory=/path/to/inventory'
# use ansible.cfg
$ pytest --hosts='ansible://server1?ansible_connection=local&ansible_cfg=/path/to/ansible.cfg'

docker

The docker backend can be used to test containers running in Docker. It uses the docker exec command and support connecting to a given container name within a pod: 

# will use the default docker client
$ pytest --hosts='docker://container-id'
# specify docker host
$ pytest --hosts='docker://container-id?docker_host=ssh://user@host'
# test multiple containers
$ pytest --hosts='docker://container-id-1,docker://container-id-2?docker_host=ssh://user@host'

Example using docker-compose: 

$ COMPOSE_FILE=docker-compose.yml pytest --hosts='docker://my-service'

kubectl

The kubectl backend can be used to test containers running in Kubernetes. It uses the kubectl exec command and support connecting to a given pod name and namespace: 

$ pytest --hosts='winrm://Administrator:Password@127.0.0.1'
$ pytest --hosts='winrm://vagrant@127.0.0.1:2200?no_ssl=true&no_verify_ssl=true'

pywinrm's default read and operation timeout can be overridden using query arguments read_timeout_sec and operation_timeout_sec:

Ansible

clase Ansible(module_name, module_args=None, check=True)
Ejecuta funciones de módulos de Ansible

Este módulo solo está disponible con el backend de conexión ansible.

Los argumentos de Ansible que no están relacionados con el inventario o la conexión de Ansible (ambos gestionados por testinfra) también se aceptan a través de argumentos de palabras clave:

  • become_method str sudo, su, doas, etc.
  • become_user str conviértete en este usuario.
  • diff bool: al cambiar archivos y plantillas (pequeños), muestra las diferencias en esos archivos.
  • extra_vars dict serializado a una cadena JSON, pasado a Ansible.
  • one_line bool: condensa la salida.
  • user str conéctate como este usuario.
  • verbose int nivel de verbosidad

API

API de conexión

Puedes usar testinfra fuera de pytest. Puedes obtener dinámicamente una instancia de host y llamar a funciones o acceder a miembros de los módulos respectivos:

>>> import testinfra
>>> host = testinfra.get_host("paramiko://root@server:2222", sudo=True)
>>> host.file("/etc/shadow").mode == 0o640
True

Por ejemplo, podrías hacer una prueba para comparar dos archivos en dos servidores diferentes:

# MAL: Si la prueba falla en nginx, python no se prueba
def test_packages(host):
    for name, version in (
        ("nginx", "1.6"),
        ("python", "2.7"),
    ):
        pkg = host.package(name)
        assert pkg.is_installed
        assert pkg.version.startswith(version)

# $ pytest -v test.py
# [...]
# test.py::test_package[local-nginx-1.6] PASSED
# test.py::test_package[local-python-2.7] PASSED
# [...]
import pytest
@pytest.mark.parametrize("name,version", [
    ("nginx", "1.6"),
    ("python", "2.7"),
])
def test_packages(host, name, version):
    pkg = host.package(name)
    assert pkg.is_installed
    assert pkg.version.startswith(version)

Integración con KitchenCI

KitchenCI (también conocido como Test Kitchen) puede usar testinfra a través de su verificador (verifier) shell. Añade lo siguiente a tu .kitchen.yml, esto requiere instalar adicionalmente paramiko (en tu máquina host, no en la VM gestionada por kitchen)

verifier:
  name: shell
  command: pytest --hosts="paramiko://${KITCHEN_USERNAME}@${KITCHEN_HOSTNAME}:${KITCHEN_PORT}?ssh_identity_file=${KITCHEN_SSH_KEY}" --junit-xml "junit-${KITCHEN_INSTANCE}.xml" "test/integration/${KITCHEN_SUITE}"

Prueba de imágenes Docker

Docker es una forma práctica de probar tu código de infraestructura. Esta receta muestra cómo construir y ejecutar contenedores Docker con Testinfra sobrecargando el fixture host.

import pytest
import subprocess
import testinfra
# scope='session' usa el mismo contenedor para todas las pruebas;
# scope='function' usa un nuevo contenedor por cada función de prueba.
@pytest.fixture(scope='session')
def host(request):
    # construye el Dockerfile local ./Dockerfile
    subprocess.check_call(['docker', 'build', '-t', 'myimage', '.'])
    # ejecuta un contenedor
    docker_id = subprocess.check_output(
        ['docker', 'run', '-d', 'myimage']).decode().strip()
    # devuelve una conexión de testinfra al contenedor
    yield testinfra.get_host("docker://" + docker_id)
    # al final de la suite de pruebas, destruye el contenedor
    subprocess.check_call(['docker', 'rm', '-f', docker_id])
def test_myimage(host):
    # 'host' ahora se enlaza al contenedor
    assert host.check_output('myapp -v') == 'Myapp 1.0'
