INFORMACIÓN GENERAL

El proyecto TURN Server contiene el código fuente de un servidor TURN y una biblioteca de mensajería para clientes TURN. También incluye algunos programas adicionales para fines de prueba solamente.

Consulte el archivo INSTALL para ver las instrucciones de compilación.

Después de la compilación, tendrá las siguientes imágenes binarias:

1.
turnserver: Relé de TURN Server. La imagen binaria compilada del programa TURN Server se encuentra en el subdirectorio bin/.
2.
turnadmin: Herramienta de administración de TURN. Consulte README.turnadmin y la página del manual de turnadmin.
3.
turnutils_uclient. Consulte README.turnutils y la página del manual de turnutils.
4.
turnutils_peer. Consulte README.turnutils y la página del manual de turnutils.
5.
turnutils_stunclient. Consulte README.turnutils y la página del manual de turnutils.
6.
turnutils_rfc5769check. Consulte README.turnutils y la página del manual de turnutils.

En el subdirectorio "examples/scripts", encontrará ejemplos de líneas de comando para ejecutar los programas. Los scripts están diseñados para ejecutarse desde el subdirectorio examples/, por ejemplo:

$ cd examples $ ./scripts/secure_relay.sh

SYSTEMD

Si la biblioteca de desarrollo de systemd está disponible, notificará a systemd sobre el estado del servidor.

EJECUTANDO EL SERVIDOR TURN

Para ejecutar el servidor coturn como un demonio, utilice:

  $ turnserver -o
Tenga en cuenta que si realiza algún cambio en el archivo de configuración, el servidor deberá reiniciarse.

Nota sobre las opciones: turnserver tiene nombres de opción largos y cortos para la mayoría de las opciones. Algunas opciones solo tienen forma larga, otras solo tienen forma corta. Su sintaxis es algo diferente; si se requiere un argumento:

La forma corta debe usarse de la siguiente manera (por ejemplo):

  $ turnserver -L 12.34.56.78
La forma larga equivalente debe usar el carácter "=": 
  $ turnserver --listening-ip=12.34.56.78
Si se trata de una opción de tipo bandera (no se requiere argumento), su uso es el mismo, por ejemplo: 
 $ turnserver -a
es equivalente a: 
 $ turnserver --lt-cred-mech

=====================================

NOMBRE

turnserver - implementación de un servidor de retransmisión TURN.

SINOPSIS

$ turnserver [-n | -c <archivo-config> ] [banderas] [ --userdb=<archivo-db-usuarios> | --psql-userdb=<cadena-conexion-db> | --mysql-userdb=<cadena-conexion-db> | --mongo-userdb=<cadena-conexion-db> | --redis-userdb=<cadena-conexion-db> ] [-z | --no-auth | -a | --lt-cred-mech ] [opciones]
$ turnserver -h

DESCRIPCIÓN

Configuración del archivo:

-n
No usar archivo de configuración, utilizar solo parámetros de línea de comandos.
-c
Nombre del archivo de configuración (por defecto - turnserver.conf). El formato del archivo de configuración se puede ver en el archivo de ejemplo examples/etc/turnserver.conf proporcionado. Los nombres largos de las opciones se utilizan como nombres de elementos de configuración en el archivo. Si no se proporciona una ruta absoluta, el archivo se buscará en los siguientes directorios:
  • directorio actual
  • directorio actual subdirectorio etc/
  • nivel superior del directorio etc/
  • /etc/
  • /usr/local/etc/
  • directorio de instalación /etc

Configuración de la base de datos de usuarios:

-b, --db, --userdb
Nombre del archivo de base de datos SQLite para usuarios (por defecto - /var/db/turndb o /usr/local/var/db/turndb o /var/lib/turn/turndb).
-e, --psql-userdb
Cadena de conexión a la base de datos PostgreSQL para usuarios. Esta base de datos se puede utilizar para el mecanismo de credenciales a largo plazo y puede almacenar el valor secreto para la autenticación programada basada en secretos en la API REST de TURN. El formato de la cadena de conexión es el siguiente:

"host=<host> dbname=<nombre-db> user=<usuario-db> password=<contraseña-usuario-db> connect_timeout=<segundos>" (para Postgres 8.x o superior).

O:

"postgresql://usuario:contraseña@nombre-host:puerto/nombre-base-datos" (para Postgres 9.x o superior).

Consulte el archivo INSTALL para obtener más explicaciones y ejemplos.

Además, consulte http://www.PostgreSQL.org para ver la documentación completa de PostgreSQL.

-M, --mysql-userdb
Cadena de conexión a la base de datos MySQL o MariaDB para usuarios. Esta base de datos se puede utilizar para el mecanismo de credenciales a largo plazo y puede almacenar el valor secreto para la autenticación programada basada en secretos en la API REST de TURN. El formato de la cadena de conexión es el siguiente:

"host=<host> dbname=<nombre-db> user=<usuario-db> password=<contraseña-usuario-db> connect_timeout=<segundos> read_timeout=<segundos>"

Consulte el archivo INSTALL para obtener más explicaciones y ejemplos.

Además, consulte http://www.mysql.org o http://mariadb.org para ver la documentación completa de MySQL.

Parámetros opcionales de la cadena de conexión para comunicaciones seguras (SSL): ca, capath, cert, key, cipher (consulte http://dev.mysql.com/doc/refman/5.1/en/ssl-options.html para ver la descripción de las opciones del comando).

--secret-key-file
Esta es la ruta del archivo que contiene la clave secreta de cifrado AES al usar el cifrado de contraseña de MySQL. Si desea utilizar la contraseña en formato cifrado en la cadena de conexión de MySQL, establezca en esta opción la ruta del archivo de la clave secreta. La clave que se utiliza para cifrar la contraseña de MySQL. Advertencia: Si se establece esta opción, la contraseña de MySQL debe estar en formato cifrado en la opción "mysql-userdb". ¡Si desea utilizar la contraseña en texto plano, no establezca esta opción!
-J, --mongo-userdb
Cadena de conexión a la base de datos MongoDB para usuarios. Esta base de datos se puede utilizar para el mecanismo de credenciales a largo plazo y puede almacenar el valor secreto para la autenticación programada basada en secretos en la API REST de TURN. El formato de la cadena de conexión es el siguiente:

"mongodb://usuario:contraseña@host:puerto/base-datos?opciones"

Consulte el archivo INSTALL para obtener más explicaciones y ejemplos.

Además, consulte http://docs.mongodb.org/manual/ para ver la documentación completa de MongoDB.

-N, --redis-userdb
Cadena de conexión a la base de datos Redis para usuarios. Esta base de datos se puede utilizar para el mecanismo de credenciales a largo plazo y puede almacenar el valor secreto para la autenticación programada basada en secretos en la API REST de TURN. El formato de la cadena de conexión es el siguiente:

"ip=<direccion-ip> dbname=<numero-db> password=<contraseña-db> connect_timeout=<segundos>"

Consulte el archivo INSTALL para obtener más explicaciones y ejemplos.

Además, consulte http://redis.io para ver la documentación completa de Redis.

Banderas:

-v, --verbose
Modo detallado moderado.
-V, --Verbose
Modo muy detallado, muy molesto y no recomendado.
-o, --daemon
Ejecutar el servidor como un demonio.

--no-software-attribute Modo de producción: ocultar la versión del software.

<
b>-f, --fingerprint
Utiliza huellas digitales en los mensajes TURN. Si una solicitud entrante contiene una huella digital, el servidor TURN siempre agregará huellas digitales a los mensajes de esta sesión, independientemente de la configuración por servidor.
-a, --lt-cred-mech
Utiliza el mecanismo de credenciales a largo plazo (este es el que necesitas para el uso de WebRTC).
-z, --no-auth
No utilices ningún mecanismo de credenciales, permite el acceso anónimo. Lo opuesto a las opciones -a y -A. Esta es la opción predeterminada cuando no se establecen opciones relacionadas con la autenticación. De forma predeterminada, no se utiliza ningún mecanismo de credenciales; se permite a cualquier usuario.
--use-auth-secret
Indicador de la API REST de TURN. Indicador que establece una opción especial de autorización de WebRTC basada en un secreto de autenticación. El propósito de esta función es soportar la "API REST del Servidor TURN" como se describe en la sección API REST de TURN a continuación. Esta opción utiliza la marca de tiempo como parte del nombre de usuario combinado: usercombo -> "timestamp:username", usuario de turn -> usercombo, contraseña de turn -> base64(hmac(buffer_entrada = usercombo, clave = secretocompartido)). Esto permite que las credenciales de TURN se contabilicen para un ID de usuario específico. Si no tienes un ID adecuado, se puede usar la marca de tiempo sola. Esta opción simplemente activa la autenticación basada en secretos. El valor real del secreto se define ya sea por la opción static-auth-secret, o se puede encontrar en la tabla turn_secret en la base de datos.
--oauth
Soporta autenticación oAuth, como en el RFC 7635 de STUN/TURN de terceros.
--dh566
Utiliza una clave TLS DH predefinida de 566 bits. El tamaño predeterminado de la clave es 2066.
--dh1066
Utiliza una clave TLS DH predefinida de 1066 bits. El tamaño predeterminado de la clave es 2066.
--tlsv1
Establece TLSv1 como la versión mínima de protocolo compatible.
--tlsv1_1
Establece TLSv1.1 como la versión mínima de protocolo compatible.
--no-tlsv1_2
Establece TLSv1_3 como la versión mínima de protocolo compatible.
--no-udp
No iniciar oyentes de clientes UDP.
--no-tcp
No iniciar oyentes de clientes TCP.
--no-tls
No iniciar oyentes de clientes TLS.
--no-dtls
No iniciar oyentes de clientes DTLS.
--no-udp-relay
No permitir puntos finales de retransmisión UDP definidos en RFC 5766, utilizar solo puntos finales de retransmisión TCP como se define en RFC 6062.
--no-tcp-relay
No permitir puntos finales de retransmisión TCP definidos en RFC 6062, utilizar solo puntos finales de retransmisión UDP como se define en RFC 5766.
--no-stdout-log
Indicador para evitar mensajes de registro en la salida estándar. De forma predeterminada, todos los mensajes de registro van tanto a la salida estándar como al archivo de registro configurado. Con esta opción, todo irá solo al archivo de registro (a menos que el propio archivo de registro sea la salida estándar).
--syslog
Con este indicador, todos los registros se redirigirán al registro del sistema (syslog).
--simple-log
Este indicador significa que no se utilizará rotación de archivos de registro, y el nombre del archivo de registro se construirá tal cual, sin el sufijo PID y fecha. Esta opción se puede usar, por ejemplo, junto con la herramienta logrotate.
--new-log-timestamp
Habilita la marca de tiempo completa ISO-8601 en todos los registros.
--new-log-timestamp-format
<formato> Establece el formato de la marca de tiempo (en formato strftime(1))
--log-binding
Registra la solicitud de enlace STUN. Actualmente está deshabilitado por defecto para evitar ataques de denegación de servicio.
--secure-stun
Requiere autenticación de la solicitud de enlace STUN. De forma predeterminada, se permite a los clientes acceso anónimo a la funcionalidad de enlace STUN.
-S, --stun-only
Ejecutar solo como servidor STUN, se ignorarán todas las solicitudes TURN. Opción para suprimir la funcionalidad TURN, solo se procesarán las solicitudes STUN.
--no-stun
Ejecutar solo como servidor TURN, se ignorarán todas las solicitudes STUN. Opción para suprimir la funcionalidad STUN, solo se procesarán las solicitudes TURN.
--allow-loopback-peers
Permite pares en las direcciones de bucle invertido (127.x.x.x y ::1). Permítelo solo para pruebas en un entorno de desarrollo. En producción, agrega una posible vulnerabilidad de seguridad, y por lo tanto, por razones de seguridad, no se permite su uso junto con una contraseña CLI vacía.
--no-multicast-peers
No permite pares en direcciones de multidifusión conocidas (224.0.0.0 y superior, y FFXX:*).
--mobility
Soporte de especificaciones de movilidad con ICE (MICE).
--no-cli
Desactiva el soporte CLI. Por defecto, siempre está activado. Ver también las opciones --cli-ip y --cli-port.
--server-relay
Retransmisión del servidor. OPCIÓN NO ESTÁNDAR Y PELIGROSA. Solo para aquellas aplicaciones en las que queremos ejecutar aplicaciones de servidor en los puntos finales de retransmisión. Esta opción elimina la verificación de permisos de IP en los paquetes entrantes a los puntos finales de retransmisión. Ver http://tools.ietf.org/search/rfc5766#section-17.2.3 .
--udp-self-balance
(recomendado solo para Linux más antiguos) Balancea automáticamente el tráfico UDP entre servidores auxiliares (si están configurados). El balanceo de carga utiliza el mecanismo ALTERNATE_SERVER. El cliente TURN debe soportar la respuesta 300 ALTERNATE_SERVER para esta funcionalidad.
--check-origin-consistency
El indicador que establece la verificación de consistencia de origen: a lo largo de la sesión, todas las solicitudes deben tener el mismo valor principal del atributo ORIGIN (si el ORIGIN fue utilizado inicialmente por la sesión).
--prometheus
Habilita métricas de prometheus. Por defecto está deshabilitado. Escuchará en el puerto 9641 bajo la ruta /metrics, y la ruta / en este puerto también se puede usar como verificación de estado.
--prometheus-username-labels
Habilita el etiquetado de métricas de tráfico de prometheus con nombres de usuario de cliente. El etiquetado con nombres de usuario de cliente está deshabilitado por defecto, ya que puede causar fugas de memoria cuando se utiliza autenticación con nombres de usuario efímeros (por ejemplo, API REST de TURN).
--prometheus-port
Puerto del oyente de Prometheus (Predeterminado: 9641).
-h
Ayuda.

Opciones con valores:

--stale-nonce[=<valor>]
Utiliza seguridad adicional con un valor de nonce que tiene una vida útil limitada, en segundos (predeterminado 600 segundos). Establécelo en 0 para una vida útil ilimitada del nonce.
--max-allocate-lifetime
Establece el valor máximo para la vida útil de la asignación. Predeterminado a 3600 segundos.
--channel-lifetime
Establece la vida útil para el enlace de canal, predeterminado a 600 segundos. Este valor NO DEBE cambiarse para fines de producción.
--permission-lifetime
Establece el valor para la vida útil del permiso. Predeterminado a 300 segundos. Esto NO DEBE cambiarse para fines de producción.
-d, --listening-device
Dispositivo de interfaz del oyente. (NO RECOMENDADO. Funcionalidad opcional, solo Linux). El proceso turnserver debe tener privilegios de root para enlazar el punto final del oyente a un dispositivo. Si turnserver debe ejecutarse como un proceso sin privilegios de root, entonces simplemente no uses esta configuración.
-L, --listening-ip
Dirección IP del oyente del servidor de retransmisión. Se pueden especificar varios oyentes, por ejemplo: -L ip1 -L ip2 -L ip3. Si no se especifican IP(s), entonces se utilizarán todas las IPs del sistema IPv4 e IPv6 para escuchar. Las mismas IP(s) se pueden utilizar como IP(s) de escucha y de retransmisión.
-p, --listening-port
Puerto del oyente TURN para oyentes UDP y TCP (Predeterminado: 3478). Nota: en realidad, las sesiones TLS y DTLS pueden conectarse también a los puertos TCP y UDP "sin cifrar", si se permite por configuración.
--tls-listening-port
Puerto del oyente TURN para oyentes TLS y DTLS (Predeterminado: 5349). Nota: en realidad, las sesiones TCP y UDP "sin cifrar" pueden conectarse también a los puertos TLS y DTLS, si se permite por configuración. El servidor TURN reconoce "automáticamente" el tipo de tráfico. En realidad, dos puntos finales de escucha (el "sin cifrar" y el "tls") son equivalentes en términos de funcionalidad; pero mantenemos ambos puntos finales para satisfacer las especificaciones RFC 5766. Para conexiones TCP seguras, actualmente versiones TLS 1.2, 1.3. Para conexiones UDP seguras, soportamos DTLS versión 1.
--alt-listening-port
Puerto de escucha alternativo para oyentes UDP y TCP; el valor predeterminado (o cero) significa "puerto de escucha más uno". Esto es necesario para STUN CHANGE_REQUEST, en el sentido de RFC 5780 o en el antiguo sentido RFC 3489, para NAT
behavior discovery). El Servidor TURN soporta CHANGE_REQUEST solo si se inicia con más de una dirección IP de escucha de la misma familia (IPv4 o IPv6). CHANGE_REQUEST solo es compatible con el protocolo UDP; otros protocolos solo escuchan en ese punto final para "simetría".
--alt-tls-listening-port
Puerto de escucha alternativo para los protocolos TLS y DTLS. El valor por defecto (o cero) significa "puerto de escucha TLS más uno".
--tcp-proxy-port
Admite conexiones de un balanceador de carga TCP en este puerto. El balanceador de carga debe usar el protocolo proxy binario. (https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt)
--aux-server
Punto final de escucha auxiliar del servidor STUN/TURN. Los servidores Aux tienen funcionalidad STUN y TURN casi completa. Las (menores) limitaciones son:
1)
Los servidores auxiliares no tienen puertos alternativos y no admiten la funcionalidad de STUN RFC 5780 (CHANGE REQUEST).
2)
Los servidores auxiliares tampoco devuelven nunca la respuesta ALTERNATIVE-SERVER.

Los formatos válidos son 1.2.3.4:5555 para IPv4 y [1:2::3:4]:5555 para IPv6. Puede haber varias opciones aux-server, cada una se usará para escuchar las solicitudes del cliente.

-i, --relay-device
Dispositivo de interfaz de retransmisión para sockets de retransmisión (NO RECOMENDADO. Opcional, solo Linux).
-E, --relay-ip
Dirección de retransmisión (la dirección IP local que se usará para retransmitir los paquetes al par). Se pueden usar varias direcciones de retransmisión: -E ip1 -E ip2 -E ip3 Las mismas direcciones IP pueden usarse como direcciones IP de escucha y de retransmisión. Si no se especifican direcciones IP de retransmisión, el turnserver aplicará la política predeterminada: decidirá por sí mismo qué direcciones de retransmisión se utilizarán, y siempre usará la dirección IP del socket del cliente como dirección IP de retransmisión de la sesión TURN (si la dirección IP de retransmisión solicitada es de la misma familia que la del socket del cliente).
-X, --external-ip
Mapeo de dirección pública/privada del Servidor TURN, si el servidor está detrás de un NAT. En esa situación, si se utiliza un -X en la forma "-X <ip>" entonces esa ip se informará como dirección IP de retransmisión de todas las asignaciones. Este escenario solo funciona en un caso simple cuando se utiliza una única dirección de retransmisión, y no se requiere ninguna funcionalidad CHANGE_REQUEST. Esa única dirección de retransmisión debe ser mapeada por NAT a la IP "externa". El valor "external-ip", si no está vacío, se devuelve en el campo XOR-RELAYED-ADDRESS. Para esa IP "externa", el NAT debe reenviar los puertos directamente (el puerto retransmitido 12345 debe mapearse siempre al mismo puerto "externo" 12345). En un caso más complejo, cuando hay más de una dirección IP involucrada, esta opción debe usarse varias veces, cada entrada debe tener la forma "-X <ip-publica/ip-privada>", para mapear todas las direcciones involucradas. La funcionalidad de descubrimiento NAT de STUN CHANGE_REQUEST (RFC5780 o RFC3489) funcionará correctamente, si las direcciones están mapeadas adecuadamente, incluso cuando el propio servidor TURN está detrás de un NAT. Por defecto, este valor está vacío y no se usa ningún mapeo de direcciones.
-m, --relay-threads
Número de hilos de retransmisión para manejar las conexiones establecidas (además del hilo de autenticación y el hilo de escucha). Si se establece explícitamente en 0, la aplicación ejecuta el proceso de retransmisión en un solo hilo, en el mismo hilo que el proceso de escucha (el hilo de autenticación seguirá siendo un hilo separado). Si no se establece, se empleará un algoritmo óptimo predeterminado (dependiente del SO). En sistemas Linux más antiguos (anteriores a Linux kernel 3.9), el número de hilos UDP es siempre un hilo por punto final de escucha de red, a menos que se establezca "-m 0" o "-m 1".
--min-port
Límite inferior del rango de puertos UDP para la asignación de puntos finales de retransmisión. El valor predeterminado es 49152, según RFC 5766.
--max-port
Límite superior del rango de puertos UDP para la asignación de puntos finales de retransmisión. El valor predeterminado es 65535, según RFC 5766.
-u, --user
Credenciales de usuario para el mecanismo de seguridad a largo plazo, en formato separado por dos puntos: nombre de usuario:clave. Se pueden usar varias cuentas de usuario en la línea de comandos. La clave es la contraseña del usuario o la clave generada por el comando turnadmin. En este último caso, la clave debe ir precedida por los símbolos 0x. La clave se calcula sobre el nombre de usuario, el dominio (realm) del usuario y la contraseña del usuario. Esta configuración no se puede usar con la API REST de TURN.
-r, --realm
El dominio (realm) predeterminado que se utilizará para los usuarios cuando no se encuentre ninguna relación origen/dominio explícita en la base de datos, o si el servidor TURN no está utilizando ninguna base de datos (solo la configuración de línea de comandos y el archivo userdb). Debe usarse con el mecanismo de credenciales a largo plazo o con la API REST de TURN.
-C, --rest-api-separator
Este es el símbolo (carácter) separador de marca de tiempo/nombre de usuario en la API REST de TURN. El valor predeterminado es :.
-q, --user-quota
Cuota de asignaciones por usuario: cuántas asignaciones concurrentes puede crear un usuario. Esta opción también se puede establecer a través de la base de datos, para un dominio (realm) particular.
-Q, --total-quota
Cuota total de asignaciones: límite global de asignaciones concurrentes. Esta opción también se puede establecer a través de la base de datos, para un dominio (realm) particular.
-s, --max-bps
Bytes por segundo máximos que una sesión TURN puede manejar (los flujos de red de entrada y salida se tratan por separado). Cualquier cosa por encima de este límite se eliminará o se suprimirá temporalmente (dentro de los límites de búfer disponibles). Esta opción también se puede establecer a través de la base de datos, para un dominio (realm) particular.
-B, --bps-capacity
Capacidad máxima del servidor. Bytes por segundo totales que el servidor TURN puede asignar para las sesiones, combinados (los flujos de red de entrada y salida se tratan por separado).
--static-auth-secret
Valor secreto de autenticación estático (una cadena) solo para la API REST de TURN. Si no se establece, el servidor turn intentará usar el valor dinámico en la tabla turn_secret de la base de datos de usuarios (si está presente). El valor almacenado en la base de datos se puede cambiar sobre la marcha por un programa separado, por eso el otro modo es dinámico. Se pueden usar múltiples secretos compartidos (tanto en la base de datos como de forma "estática").
--no-auth-pings
Deshabilita las comprobaciones periódicas de estado a las tablas de secretos de autenticación 'dinámicos'.
--no-dynamic-ip-list
No utilizar la lista dinámica de IPs permitidas/denegadas.
--no-dynamic-realms
No utilizar la asignación y las opciones dinámicas de dominios (realms).
--server-name
Nombre del servidor utilizado para fines de autenticación oAuth. El valor predeterminado es el nombre del dominio (realm).
--cert
Archivo de certificado, formato PEM. Se aplican las mismas reglas de búsqueda de archivos que para el archivo de configuración. Si se especifican las opciones --no-tls y --no-dtls, este parámetro no es necesario. El valor predeterminado es turn_server_cert.pem.
--pkey
Archivo de clave privada, formato PEM. Se aplican las mismas reglas de búsqueda de archivos que para el archivo de configuración. Si se especifican las opciones --no-tls y --no-dtls, este parámetro no es necesario. El valor predeterminado es turn_server_pkey.pem.
--pkey-pwd
Si el archivo de clave privada está cifrado, esta es la contraseña que se debe usar.
--cipher-list
Lista de cifrados OpenSSL permitidos para conexiones TLS/DTLS. El valor predeterminado es "DEFAULT" para versiones TLS/DTLS hasta TLSv1.2/DTLSv1.2, y los conjuntos de cifrado predeterminados de la biblioteca para TLSv1.3.
--CA-file
Archivo CA en formato OpenSSL. Obliga al servidor TURN a verificar los certificados SSL del cliente. Por defecto, no se establece ningún CA y no se realiza ninguna verificación del certificado del cliente.
--ec-curve-name

TURN REST API

En WebRTC, el navegador obtiene la información de conexión de TURN del servidor web. Esta información es confidencial, ya que contiene las credenciales necesarias de TURN. Como estas credenciales se transmiten a través de redes públicas, existe una posible brecha de seguridad.

Si tenemos que transmitir información valiosa a través de la red pública, esta información debe tener una vida útil limitada. De este modo, la persona que obtenga esta información sin permiso solo podrá causar un daño limitado.

Así es como surgió la idea de la API REST de TURN: credenciales de TURN con tiempo limitado. Este mecanismo de seguridad se basa en el mecanismo de credenciales a largo plazo. La idea principal de la API REST es que el servidor web proporciona las credenciales al cliente, pero estas credenciales solo pueden ser utilizadas por un tiempo limitado por una aplicación que tiene que crear una conexión de servidor TURN.

El mecanismo de credenciales a largo plazo ("clásico") (LTCM) se describe aquí:

http://tools.ietf.org/html/rfc5389#section-10.2

http://tools.ietf.org/html/rfc5389#section-15.4

Para la autenticación, cada usuario debe conocer dos cosas: el nombre de usuario y la contraseña. Opcionalmente, el usuario debe proporcionar el valor ORIGIN, para que el servidor pueda determinar el reino que se utilizará para el usuario. Los valores nonce y realm son proporcionados por el servidor TURN. Pero LTCM no dice nada sobre la naturaleza y la persistencia del nombre de usuario y la contraseña; y esto es utilizado por la API REST.

En la API REST de TURN, no hay contraseñas persistentes para los usuarios. Un usuario solo tiene el nombre de usuario. La contraseña es siempre temporal y es generada por el servidor web bajo demanda, cuando el usuario accede a la página WebRTC. Y, de hecho, el nombre de usuario también se proporciona al usuario solo para una sesión temporal de un solo uso.

El usuario temporal se genera como:

temporary-username="timestamp" + ":" + "username"

donde username es el nombre de usuario persistente, y el formato timestamp son solo segundos desde 1970, el mismo valor que devuelve la función time(NULL).

La contraseña temporal se obtiene como la función HMAC-SHA1 sobre el nombre de usuario temporal, con un secreto compartido como clave HMAC, y luego el resultado se codifica:

temporary-password = base64_encode(hmac-sha1(shared-secret, temporary-username))

Tanto el servidor TURN como el servidor web conocen el mismo secreto compartido. Cómo se distribuye el secreto compartido entre las entidades involucradas se deja a los detalles de implementación de WebRTC, esto está fuera del alcance de la API REST de TURN.

Por lo tanto, se utiliza una marca de tiempo para el cálculo de la contraseña temporal, y esta marca de tiempo se puede recuperar del nombre de usuario temporal. Esta información es valiosa, pero solo temporal, mientras la marca de tiempo no haya expirado. Sin conocer el secreto compartido, no se puede generar una nueva contraseña temporal.

Todo esto está formalmente descrito en el documento de la API REST de TURN de Justin Uberti, que se puede obtener siguiendo el enlace "TURN REST API" en la página del proyecto TURN Server https://github.com/coturn/coturn/.

Una vez que la aplicación cliente (navegador) obtiene el nombre de usuario y la contraseña temporales, el resto es simplemente el mecanismo de credenciales a largo plazo "clásico". Para los desarrolladores, lo describiremos paso a paso a continuación:

  • un nuevo cliente TURN envía una solicitud de comando al servidor TURN. Opcionalmente, agrega el campo ORIGIN.
  • el servidor TURN ve que es un nuevo cliente y el mensaje no está autenticado.
  • el servidor TURN genera una cadena nonce aleatoria y devuelve el error 401 al cliente, con nonce y realm incluidos. Si el campo ORIGIN estaba presente en la solicitud del cliente, puede afectar el valor del realm que el servidor elige para el cliente.
  • el cliente ve el error 401 y extrae dos valores de la respuesta de error: el nonce y el realm.
  • el cliente usa el nombre de usuario, el realm y la contraseña para producir una clave:
         key = MD5(username ":" realm ":" SASLprep(password))
(SASLprep se describe aquí: http://tools.ietf.org/html/rfc4013)
  • el cliente forma una nueva solicitud, agrega nombre de usuario, realm y nonce a la solicitud. Luego, el cliente calcula y agrega el campo de integridad a la solicitud. Esta es la parte más complicada del proceso y se describe al final de la sección 15.4: http://tools.ietf.org/html/rfc5389#section-15.4
  • el cliente, opcionalmente, agrega el campo fingerprint. Este también puede ser un procedimiento complicado, descrito en la sección 15.5 del mismo documento. WebRTC generalmente usa mensajes TURN con fingerprint.
  • el servidor TURN recibe la solicitud, lee el nombre de usuario.
  • luego el servidor TURN verifica que el nonce y el realm en la solicitud sean válidos.
  • luego el servidor TURN calcula la clave.
  • luego el servidor TURN calcula el campo de integridad.
  • luego el servidor TURN compara el campo de integridad calculado con el recibido; deben ser iguales. Si los campos de integridad difieren, la solicitud es rechazada.

En comunicaciones posteriores, el cliente puede seguir la misma secuencia, pero para optimización, generalmente el cliente, al tener ya información sobre el realm y el nonce, precalcula la cadena de integridad para cada solicitud, de modo que la respuesta de error 401 se vuelve innecesaria. El servidor TURN puede usar la opción "--stale-nonce" para seguridad adicional: en algún momento, el nonce expira y el cliente obtendrá una respuesta de error 438 con el nuevo nonce, y el cliente tendrá que empezar a usar el nuevo nonce.

En comunicaciones posteriores, el servidor y el cliente siempre asumirán la misma contraseña: la contraseña original se convierte en un parámetro de sesión y nunca expira. Por lo tanto, la contraseña no cambia mientras la sesión sea válida y no haya expirado. Así, si la sesión se mantiene correctamente, puede durar para siempre, incluso si la contraseña del usuario ya ha sido cambiada (en la base de datos). La sesión simplemente está utilizando la contraseña antigua. Una vez que la sesión se desconecta, el cliente tendrá que usar la nueva contraseña para volver a conectarse (si la contraseña ha sido cambiada).

Se proporciona un ejemplo de cómo el secreto compartido se genera cada hora por el servidor TURN y luego se suministra al servidor web, de forma remota, en los ejemplos de scripts/restapi/shared_secret_maintainer.pl.

Algo muy importante es que el nonce debe ser totalmente aleatorio y diferente para diferentes clientes y diferentes sesiones.

BASES DE DATOS

Para la base de datos de usuarios, el turnserver tiene las siguientes opciones:

1)
Los usuarios se pueden configurar en la línea de comandos, con múltiples opciones -u o --user. Obviamente, solo se pueden configurar pocos usuarios de esa manera, y sus credenciales son fijas durante la vida útil del proceso turnserver.
2)
Los usuarios se pueden almacenar en una base de datos SQLite. El archivo de base de datos SQLite predeterminado es /var/db/turndb o /usr/local/var/db/turndb o /var/lib/turn/turndb.
3)
Los usuarios se pueden almacenar en una base de datos PostgreSQL, si el turnserver se compiló con soporte para PostgreSQL. Cada vez que turnserver verifica las credenciales del usuario, lee la base de datos (de forma asíncrona, por supuesto, para que el flujo actual de paquetes no se retrase de ninguna manera), por lo que cualquier cambio en el contenido de la base de datos es inmediatamente visible por el turnserver. Esta es la forma si necesita la mejor escalabilidad. El esquema para la base de datos se puede encontrar en el archivo schema.sql. Para credenciales a largo plazo, debe configurar las "claves" para los usuarios; las "claves" son generadas por la utilidad turnadmin. Para la generación de claves, necesita el nombre de usuario, la contraseña y el realm. Todos los usuarios en la base de datos deben usar el mismo valor de realm; si más adelante decide cambiar el nombre del realm, tendrá que volver a generar todas las claves de usuario (lo que se puede hacer en un script por lotes). Vea el archivo turndb/testsqldbsetup.sql como ejemplo.
4)
Lo mismo ocurre con la base de datos MySQL. El mismo archivo de esquema es aplicable. Las mismas consideraciones son aplicables.
5)
Lo mismo ocurre con la base de datos Redis, pero la base de datos Redis tiene un esquema diferente; se puede encontrar (en forma de explicación) en schema.userdb.redis. Además, en Redis puede almacenar tanto "claves" como contraseñas abiertas (para credenciales a largo plazo); la opción de "contraseña abierta" es menos segura pero más conveniente para entornos de baja seguridad. Vea el archivo turndb/testredisdbsetup.sh como ejemplo.
6)
Si se utiliza una base de datos, los usuarios se pueden dividir en múltiples realms independientes. Cada realm se puede administrar por separado, y cada realm puede tener su propio conjunto de usuarios y sus propias opciones de rendimiento (max-bps, user-quota, total-quota).
7)
Si utiliza MongoDB, la base de datos se configurará automáticamente.
8)
Por supuesto, el turnserver se puede utilizar en modo no seguro, cuando se permite a los usuarios establecer sesiones de forma anónima. Pero en la mayoría de los casos (como WebRTC) eso no funcionará.

Para la base de datos de estado y estadísticas, hay dos opciones:

1)
La opción más sencilla es no usarla. No establezca la opción --redis-statsdb, y esta funcionalidad simplemente se ignorará.
2)
Si elige usarla, establezca la opción --redis-statsdb. Puede ser la misma base de datos que en la opción --redis-userdb, o puede ser una base de datos diferente. Puede que desee utilizar una base de datos diferente por motivos de seguridad o conveniencia. Además, puede utilizar diferentes sistemas de gestión de bases de datos para la base de datos de usuarios y para la base de datos de estado y estadísticas. Por ejemplo, puede utilizar MySQL como base de datos de usuarios y Redis para las estadísticas. O puede utilizar Redis para ambos.

Por lo tanto, tenemos 6 opciones para la gestión de usuarios y 2 opciones para la gestión de estadísticas. Estas dos son totalmente independientes. Por lo tanto, tiene un total de 6 * 2 = 12 formas de manejar información persistente, elija cualquiera para su conveniencia.

No tiene que manejar la información de la base de datos "manualmente": el programa turnadmin puede encargarse de todo por usted. Para PostgreSQL y MySQL, solo tendrá que crear una base de datos vacía con el script SQL schema.sql. Con

INFORMACIÓN GENERAL

El servidor TURN es un programa de código abierto que implementa el protocolo TURN (Traversal Using Relays around NAT), definido en RFC 5766, y varios protocolos relacionados como STUN (RFC 5389) y TURN-TCP extension (RFC 6062).

El servidor TURN permite que los hosts detrás de un NAT o un firewall puedan comunicarse entre sí estableciendo un relé en un servidor público.

SYSTEMD

Si está utilizando un sistema que se inicia con systemd, puede usar el archivo de servicio systemd proporcionado para administrar el servidor TURN. Los archivos de servicio se encuentran en /usr/lib/systemd/system/turnserver.service y /usr/lib/systemd/system/turnadmin.service.

Para iniciar el servidor TURN al arrancar, ejecute:

    # systemctl enable turnserver.service

Para iniciar el servidor TURN ahora, ejecute:

    # systemctl start turnserver.service

Puede verificar el estado del servidor TURN con:

    # systemctl status turnserver.service

Las opciones de configuración para el servidor TURN se encuentran en el archivo /etc/turnserver.conf.

EJECUCIÓN DEL SERVIDOR TURN

El servidor TURN se puede iniciar de varias maneras, dependiendo de cómo se haya instalado y configurado el sistema.

Si utiliza la gestión de usuarios proporcionada por el servidor TURN, no necesita hacer nada adicional, simplemente ejecute turnadmin y establecerá los usuarios por usted (consulte los manuales de turnadmin). Si está utilizando SQLite, entonces turnserver o turnadmin inicializarán la base de datos vacía por usted al iniciarse. El proceso de instalación del servidor TURN crea una base de datos SQLite vacía inicializada en la ubicación predeterminada (/var/db/turndb o /usr/local/var/db/turndb o /var/lib/turn/turndb, dependiendo del sistema).

EQUILIBRIO DE CARGA Y AJUSTE DE RENDIMIENTO

Para el equilibrio de carga, puede ejecutar varios servidores TURN y utilizar un equilibrador de carga externo (por ejemplo, HAProxy, Nginx) para distribuir las conexiones entrantes entre ellos. Los servidores TURN deben configurarse para que compartan la misma base de datos de usuarios y realms para permitir una gestión coherente de las credenciales.

El ajuste de rendimiento implica la optimización de la configuración del servidor TURN, como el número de hilos de trabajo, el tamaño de los búferes de red y la configuración de la base de datos. También puede ser necesario ajustar la configuración del sistema operativo, como los límites de descriptores de archivos y la configuración de la pila de red.

=

USO DE WEBRTC

El servidor TURN es fundamental para el funcionamiento de WebRTC en muchos escenarios de red, especialmente cuando los clientes están detrás de NAT o firewalls que impiden la comunicación directa de par a par. WebRTC utiliza TURN para retransmitir el tráfico de medios (audio y video) cuando no se puede establecer un camino directo.

Para utilizar TURN con WebRTC, las aplicaciones deben configurarse con la dirección IP y el puerto del servidor TURN, así como las credenciales de autenticación (nombre de usuario y contraseña) que el servidor TURN puede verificar. El servidor TURN permite que los clientes establezcan una sesión de retransmisión y les asigna direcciones IP y puertos de retransmisión para el tráfico de medios.

=

API REST DE TURN

El servidor TURN proporciona una interfaz de administración basada en RESTful a través de HTTP/HTTPS. Esta API permite la gestión programática de la configuración del servidor, incluidos realms, usuarios y cuotas. También se puede utilizar para obtener estadísticas de rendimiento y estado del servidor.

Para habilitar la API REST, debe configurarla en el archivo turnserver.conf, especificando los puertos para HTTP y/o HTTPS, así como la configuración de autenticación para acceder a la API.

=

BASES DE DATOS

El servidor TURN puede utilizar diferentes sistemas de bases de datos para almacenar información de configuración, como realms y usuarios. Las opciones comunes incluyen:

  • SQLite: Una base de datos ligera y autónoma, adecuada para instalaciones más pequeñas o de un solo servidor. El servidor TURN puede inicializar automáticamente una base de datos SQLite si no existe.

  • MySQL/MariaDB: Bases de datos relacionales más robustas, adecuadas para entornos de producción más grandes y distribuidos. Requiere la configuración de un servidor de base de datos separado y la creación de tablas específicas para TURN.

  • PostgreSQL: Otra opción de base de datos relacional potente y de código abierto, con características similares a MySQL/MariaDB.

  • Redis: Una base de datos en memoria, utilizada a menudo para configuraciones de alta disponibilidad y escalabilidad. Puede almacenar credenciales de usuario y otra información de configuración para un acceso rápido.

La elección de la base de datos depende de los requisitos de escalabilidad, rendimiento y complejidad de la implementación.

ALPN

El servidor admite las ALPN (Application-Layer Protocol Negotiation) "stun.turn" y "stun.nat-discovery". Si el servidor recibe un mensaje TLS/DTLS ClientHello que contiene una o ambas de esas ALPN, el servidor elige la primera etiqueta stun.* y la envía de vuelta (en el ServerHello) en el campo de extensión ALPN. Si no se encuentra ninguna etiqueta stun.*, el servidor no incluye la información ALPN en el ServerHello.

BIBLIOTECAS

En el subdirectorio lib/, el proceso de compilación creará la biblioteca de mensajería del cliente TURN. En el subdirectorio include/, se colocarán los archivos de inclusión necesarios. El wrapper C++ para la funcionalidad de mensajería se encuentra en el archivo de cabecera TurnMsgLib.h. Un ejemplo de código C++ se puede encontrar en el archivo stunclient.c.

DOCUMENTACIÓN

Después de la instalación, ejecute el comando:

    $ man turnserver

o en el directorio raíz del proyecto:

    $ man -M man turnserver

para ver la página man.

En el subdirectorio docs/html del árbol de archivo original, encontrará la referencia de la biblioteca cliente. Después de la instalación, se colocará en PREFIX/share/doc/turnserver/html.

REGISTROS

Cuando el Servidor TURN se inicia, intenta crear un archivo de registro turn_<pid>.log en los siguientes directorios:

  • /var/log
  • /log/
  • /var/tmp
  • /tmp
  • directorio actual

Si todos los intentos fallaron (debido a la configuración de permisos del sistema), todos los mensajes de registro se envían solo a la salida estándar del proceso.

Este comportamiento se puede controlar mediante las opciones --log-file, --syslog y --no-stdout-log.

=

INTERFAZ DE GESTIÓN HTTPS

El proceso turnserver proporciona acceso web HTTPS como interfaz de estadísticas y gestión básica. El turnserver escucha las conexiones de administración HTTPS entrantes en los mismos puertos que el oyente principal TURN/STUN. Las páginas de administración web son básicas y autoexplicativas.

Para activar la interfaz HTTPS, la tabla de la base de datos admin_user debe poblarse con la(s) cuenta(s) de usuario administrador. Un usuario administrador puede ser un superusuario (si no está asignado a un reino particular) o un usuario restringido (si está asignado a un reino). Los usuarios administradores restringidos solo pueden realizar acciones limitadas dentro de sus reinos correspondientes.

=

TELNET CLI

El proceso turnserver proporciona acceso CLI de telnet como interfaz de estadísticas y gestión básica. De forma predeterminada, el turnserver inicia un oyente CLI de telnet en la IP 127.0.0.1 y el puerto 5766. Esto se puede cambiar mediante las opciones de línea de comandos del proceso turnserver (consulte las opciones --cli-ip y --cli-port). La lista completa de comandos CLI de telnet se proporciona en la salida del comando "help" en la CLI de telnet.

=

CLÚSTERES

El Servidor TURN puede formar parte de una instalación en clúster. Sin embargo, para admitir la funcionalidad de "puerto par" (pares de flujos RTP/RTCP), las solicitudes del cliente de una IP particular deben entregarse a la misma instancia del Servidor TURN, por lo que requiere cierto ajuste en la configuración de red para el clúster. La razón es que los puntos finales de retransmisión RTP y RTCP deben asignarse en la misma IP de retransmisión. Sería posible diseñar un esquema con reenvío de solicitudes a nivel de aplicación (y es posible que lo hagamos más adelante), pero afectaría al rendimiento.

turnserver(8)

NOMBRE

turnserver - Servidor TURN (Transport Relay and NAT traversal)

DESCRIPCIÓN

El servidor TURN (Transport Relay and NAT traversal), especificado en RFC 5766, permite que los peers conecten a través de dispositivos NAT o firewalls que bloquean el tráfico directo de UDP o TCP. El servidor TURN actúa como un relé para el tráfico de los peers.

Este servidor implementa el protocolo TURN como se define en RFC 5766 y también soporta el protocolo STUN (Simple Traversal of UDP Through NAT), especificado en RFC 5389.

OPCIONES

El servidor TURN se inicia con la siguiente sintaxis:

turnserver [opciones]

Las siguientes opciones están disponibles:

-v, --version
Muestra la versión del servidor TURN y sale.
-h, --help
Muestra un mensaje de ayuda y sale.
-c CONFIG_FILE, --config=CONFIG_FILE
Especifica el archivo de configuración a utilizar. Si no se especifica, se intenta cargar /etc/turnserver.conf.

ARCHIVO DE CONFIGURACIÓN

El archivo de configuración contiene directivas para configurar el comportamiento del servidor TURN. Algunas directivas comunes incluyen:

listening-ip
La dirección IP en la que el servidor TURN escuchará las conexiones entrantes.
listening-port
El puerto en el que el servidor TURN escuchará las conexiones entrantes.
relay-ip
La dirección IP que se utilizará para el reenvío de tráfico.
realm
El realm utilizado para la autenticación.
credentials
El archivo que contiene los nombres de usuario y contraseñas para la autenticación.
tls-cert
El archivo del certificado TLS para conexiones seguras.
tls-key
El archivo de la clave privada TLS para conexiones seguras.

ALPN

El servidor TURN soporta ALPN (Application-Layer Protocol Negotiation) para la negociación de protocolos sobre TLS, incluyendo turn y stun.

LIBRERÍAS

El servidor TURN utiliza varias librerías para su funcionamiento, incluyendo libevent, openssl, y libsrtp.

DOCUMENTACIÓN

La documentación completa sobre la configuración y el uso del servidor TURN se puede encontrar en el archivo turnserver.conf y en la página man.

REGISTROS

El servidor TURN registra información sobre su actividad en archivos de registro. La ubicación y el nivel de detalle de los registros se pueden configurar en el archivo de configuración.

INTERFAZ DE GESTIÓN HTTPS

El servidor TURN puede exponer una interfaz de gestión basada en HTTPS para monitorizar y administrar el servidor de forma remota.

CLI TELNET

Se puede acceder a una interfaz de línea de comandos (CLI) a través de Telnet para interactuar con el servidor TURN, obtener información de estado y ejecutar comandos administrativos.

CLÚSTERES

El servidor TURN puede configurarse para ejecutarse en modo clúster, lo que permite una mayor escalabilidad y redundancia.

ARCHIVOS

/etc/turnserver.conf
Archivo de configuración por defecto del servidor TURN.
/var/log/turnserver.log
Archivo de registro por defecto del servidor TURN.

DIRECTORIOS

No hay directorios específicos asociados con el servidor TURN más allá de los utilizados para almacenar archivos de configuración, registros y certificados.

ESTÁNDARES

El servidor TURN implementa los siguientes estándares:

  • RFC 5766: Traversal Using Relays around NAT (TURN): Extended Methods and Traversal.
  • RFC 5389: Session Traversal Utilities for NAT (STUN).
  • RFC 5705: Signaling Transport (T14) - TURN Extension.

TURN RFC 5766

La implementación del protocolo TURN sigue estrictamente las especificaciones definidas en RFC 5766, incluyendo el manejo de peticiones, la asignación de direcciones y puertos, y el reenvío de tráfico.
