PRÓLOGO

Esta página del manual forma parte del Manual del programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para obtener detalles sobre el comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

timer_create — crear un temporizador por proceso

SINOPSIS

#include <signal.h>
#include <time.h>
int timer_create(clockid_t clockid, struct sigevent *restrict evp,
    timer_t *restrict timerid);

DESCRIPCIÓN

La función timer_create() creará un temporizador por proceso utilizando el reloj especificado, clock_id, como base de temporización. La función timer_create() devolverá, en la ubicación referenciada por timerid, un ID de temporizador de tipo timer_t utilizado para identificar el temporizador en las solicitudes de temporizador. Este ID de temporizador será único dentro del proceso que llama hasta que el temporizador sea eliminado. El reloj particular, clock_id, se define en <time.h>. El temporizador cuyo ID se devuelve estará en estado desarmado al regresar de timer_create().

El argumento evp, si no es NULL, apunta a una estructura sigevent. Esta estructura, asignada por la aplicación, define la notificación asíncrona que ocurrirá según se especifica en la Sección 2.4.1, Generación y entrega de señales cuando el temporizador expire. Si el argumento evp es NULL, el efecto es como si el argumento evp apuntara a una estructura sigevent con el miembro sigev_notify teniendo el valor SIGEV_SIGNAL, el miembro sigev_signo teniendo un número de señal predeterminado y el miembro sigev_value teniendo el valor del ID del temporizador.

Cada implementación definirá un conjunto de relojes que pueden ser utilizados como bases de temporización para temporizadores por proceso. Todas las implementaciones admitirán un clock_id de CLOCK_REALTIME. Si la opción Reloj Monótono se admite, las implementaciones admitirán un clock_id de CLOCK_MONOTONIC.

Los temporizadores por proceso no serán heredados por un proceso hijo a través de un fork() y serán desarmados y eliminados por un exec.

Si se define _POSIX_CPUTIME, las implementaciones admitirán valores de clock_id que representen el reloj de tiempo de CPU del proceso que llama.

Si se define _POSIX_THREAD_CPUTIME, las implementaciones admitirán valores de clock_id que representen el reloj de tiempo de CPU del hilo que llama.

Es una decisión de la implementación si una función timer_create() tendrá éxito si el valor definido por clock_id corresponde al reloj de tiempo de CPU de un proceso o hilo diferente del proceso o hilo que invoca la función.

Si evp->sigev_notify es SIGEV_THREAD y sev->sigev_notify_attributes no es NULL, si el atributo al que apunta sev->sigev_notify_attributes tiene una dirección de pila de hilo especificada por una llamada a pthread_attr_setstack(), los resultados no están especificados si la señal se genera más de una vez.

VALOR DE RETORNO

Si la llamada tiene éxito, timer_create() devolverá cero y actualizará la ubicación referenciada por timerid a un timer_t, que puede pasarse a las llamadas de temporizador por proceso. Si ocurre un error, la función devolverá un valor de -1 y establecerá errno para indicar el error. El valor de timerid no está definido si ocurre un error.

ERRORES

La función timer_create() fallará si:

EAGAIN
Al sistema le faltan recursos suficientes de cola de señales para atender la solicitud.
EAGAIN
El proceso que llama ya ha creado todos los temporizadores que le están permitidos por esta implementación.
EINVAL
El ID del reloj especificado no está definido.
ENOTSUP
La implementación no admite la creación de un temporizador asociado al reloj de tiempo de CPU especificado por clock_id y asociado a un proceso o hilo diferente del proceso o hilo que invoca timer_create().

Las siguientes secciones son informativas.

EJEMPLOS

Ninguno.

USO DE LA APLICACIÓN

Si se crea un temporizador con evp->sigev_sigev_notify establecido en SIGEV_THREAD y el atributo al que apunta evp->sigev_notify_attributes tiene una dirección de pila de hilo especificada por una llamada a pthread_attr_setstack(), la memoria dedicada como pila de hilo no se puede recuperar. La razón de esto es que los hilos creados en respuesta a una expiración de temporizador se crean desvinculados, o de una manera no especificada si el detachstate del atributo del hilo es PTHREAD_CREATE_JOINABLE. En ningún caso es válido llamar a pthread_join(), lo que hace imposible determinar la vida útil del hilo creado y, por lo tanto, la memoria de la pila no se puede reutilizar.

FUNDAMENTO

Exceso de temporizador periódico y asignación de recursos

Las instalaciones de temporizador especificadas pueden entregar señales en tiempo real (es decir, señales en cola) en implementaciones que admiten esta opción. Dado que las aplicaciones en tiempo real no pueden permitirse perder notificaciones de eventos asíncronos, como expiraciones de temporizadores o finalizaciones de E/S asíncronas, se debe garantizar que existan suficientes recursos para entregar la señal cuando ocurra el evento. En general, esto no es un problema porque hay una correspondencia uno a uno entre una solicitud y la generación posterior de una señal. Si la solicitud no puede asignar los recursos de entrega de señales, puede fallar la llamada con un error [EAGAIN].

Los temporizadores periódicos son un caso especial. Una sola solicitud puede generar un número no especificado de señales. Esto no es un problema si el proceso solicitante puede atender las señales tan rápido como se generan, haciendo así que los recursos de entrega de señales estén disponibles para la entrega de señales posteriores de expiración de temporizadores periódicos. Pero, en general, esto no se puede asegurar: el procesamiento de las señales de temporizadores periódicos puede "excederse"; es decir, expiraciones de temporizadores periódicos posteriores pueden ocurrir antes de que se entregue la señal pendiente actualmente.

Además, para las señales, de acuerdo con el estándar POSIX.1-1990, si se generan ocurrencias subsiguientes de una señal pendiente, es una decisión de la implementación si se entrega una señal por cada ocurrencia. Esto no es adecuado para algunas aplicaciones en tiempo real. Por lo tanto, se requiere un mecanismo para permitir a las aplicaciones detectar cuántas expiraciones de temporizador se retrasaron sin requerir una cantidad indefinida de recursos del sistema para almacenar las expiraciones retrasadas.

Las instalaciones especificadas proporcionan un contador de excesos. El contador de excesos se define como el número de expiraciones adicionales del temporizador que ocurrieron entre el momento en que se generó una señal de expiración del temporizador y el momento en que se entregó la señal. La función de captura de señales, si le preocupa el exceso, puede recuperar este contador al entrar. Con este método, un temporizador periódico solo necesita un "recurso de cola de señales" que se pueda asignar en el momento de la llamada a la función timer_create().

Se define una función para recuperar el contador de excesos para que una aplicación no necesite asignar almacenamiento estático para contener el contador, y una implementación no necesite actualizar este almacenamiento de forma asíncrona en las expiraciones del temporizador. Pero, para algunas aplicaciones periódicas de alta frecuencia, la sobrecarga de una llamada al sistema adicional en cada expiración del temporizador puede ser prohibitiva. Las funciones, tal como se definen, permiten a una implementación mantener el contador de excesos en el espacio de usuario, asociado con el timerid. La función timer_getoverrun() puede implementarse como una macro que utiliza el argumento timerid (que puede ser simplemente un puntero a una estructura del espacio de usuario que contiene el contador) para localizar el contador de excesos sin sobrecarga de llamada al sistema. Otras implementaciones, menos preocupadas por esta clase de aplicaciones, pueden evitar la actualización asíncrona de uso

timer_create(3p) — Arch Linux

NAME

timer_create - create a per-process timer

SYNOPSIS

            #include <time.h>

            int timer_create(clockid_t clockid,
                struct sigevent *restrict evp, timer_t *restrict timerid);

DESCRIPTION

The timer_create() function creates a timer. The timer is associated with the specified clockid. The clockid parameter should be the ID of a realtime clock, as defined in clock_getres(). The timer is initially disarmed.

The evp parameter points to a structure that defines how the calling thread shall be notified upon timer expiration. If evp is NULL, the calling thread is implicitly created with the same signal disposition as the creating thread, and the signal posted is SIGALRM.

If evp is not NULL, it points to a sigevent structure. The sigevent structure shall be defined as follows:

    struct sigevent {
        int sigev_notify;
        union sigval sigval;
        int sigev_signo;
        void (*sigev_notify_function)(sigval_t);
        void *sigev_notify_attributes;
    };

The sigev_notify member specifies the notification mechanism to be used on timer expiration and can have the following values:

SIGEV_NONE
No notification is generated. This is useful for querying timer values.
SIGEV_SIGNAL
A signal is generated. The sigev_signo member specifies the signal number to be generated. The signal is generated in the context of the thread that created the timer. The signal shall be generated for the thread that has the timer armed (see timer_settime()).
SIGEV_THREAD
A thread is created to execute the function pointed to by sigev_notify_function. The sigev_notify_attributes member is used to set thread attributes for the new thread. If it is NULL, a default set of thread attributes is used. The function is invoked with the value in sigval passed as the argument.

The sigval member is a union that contains the value to be passed to the signal handler or thread function. If sigev_notify is SIGEV_SIGNAL, the signal is queued with the signal number sigev_signo, and sigval is sent as the value of the si_value field in the siginfo_t structure (see sigaction()). If sigev_notify is SIGEV_THREAD, sigval is passed as the argument to sigev_notify_function.

If sigev_notify is SIGEV_SIGNAL, the sigev_signo member specifies the signal number to be sent. The default signal number is SIGALRM.

The sigev_notify_function member specifies the function to be called when the timer expires, and is only used when sigev_notify is SIGEV_THREAD.

The sigev_notify_attributes member specifies attributes for the thread created by SIGEV_THREAD.

Upon successful completion, the timerid parameter points to the timer ID associated with the newly created timer. This timer ID is used in subsequent calls to timer_settime(), timer_gettime(), and timer_delete().

RETURN VALUE

Upon successful completion, timer_create() shall return 0 and the timer ID is stored in the location pointed to by timerid. Otherwise, it shall return the corresponding error number.

ERRORS

EAGAIN
All timer ID values are currently in use.
EINVAL
The value of clockid is not a supported realtime clock ID or is invalid. The value of sigev_notify is invalid. The value of sigev_signo is not a valid signal number or is restricted. If sigev_notify is SIGEV_THREAD, the value of sigev_notify_attributes is invalid.
ENOMEM
Insufficient memory or timer resources are available.
ENOSYS
The timer_create() function is not supported by the system.

EXAMPLES

None.

APPLICATION USAGE

The timer_create() function is part of the Realtime Extensions option. Applications should check the return value of sysconf(_SC_TIMERS) to determine if timer functions are available on the system.

RATIONALE

The sigevent structure allows an application to specify the type of notification and the associated data. This provides flexibility in how timers are used. The use of SIGEV_THREAD allows timer notifications to be handled in a separate thread, avoiding potential deadlocks or priority inversion issues that can occur when using signals.

The sigval union allows applications to pass arbitrary data (either an integer or a pointer) to the signal handler or thread function. This is useful for associating timer expirations with specific application data structures or events.

The timer_create() function supports different clock types, allowing applications to choose the clock that best suits their needs. For example, CLOCK_REALTIME represents the system-wide real-time clock, while CLOCK_MONOTONIC represents a clock that cannot be set backward.

The option to specify an application-defined value in the sigevent structure, rather than always sending the timer ID, was chosen to align with existing practices on some non-POSIX realtime systems. This allows applications to directly pass relevant context information to the signal handler or thread function without requiring a lookup in the handler. For instance, the application can pass a pointer to a data structure that contains all necessary information for the handler to process the timer expiration.

The timer_ids are dynamically allocated by the system. When using SIGEV_SIGNAL, the system sends the timer ID as part of the siginfo_t structure's si_value field. This allows the signal handler to identify which timer expired without needing to maintain a separate mapping of signal handlers to timer IDs. However, if the application wishes to associate a constant or a pointer to application-specific data with the timer, it can use the sigval field of the sigevent structure.

The ability to create a timer associated with a specific clock (clockid) provides flexibility. For example, an application might want to use a monotonic clock for measuring elapsed time, independent of system time changes. The extension requires that clockid be a realtime clock, as defined in clock_getres().

The sigev_notify_attributes parameter for SIGEV_THREAD allows for fine-grained control over the newly created thread, such as setting its stack size or scheduling policy. This can be important for realtime applications where thread priorities and resource allocation need careful management.

The RATIONALE section discusses the design choices for the sigevent structure and its members, including the flexibility it offers to applications in handling timer expirations. The goal was to provide a powerful yet reasonably simple interface for timer management, accommodating various application needs without sacrificing performance or adding undue complexity. The choice of passing application-specific data via sigval allows handlers to directly access context, avoiding the overhead of searching for timer information, which would be necessary if only the timer ID were provided.

The text specifies that timer_ids are dynamically allocated. This implies that applications cannot pre-allocate timer IDs and must rely on the system to provide them upon timer creation. This approach simplifies resource management for the application, as it doesn't need to worry about managing a pool of timer IDs itself.

The text also mentions that the sigev_notify mechanism using SIGEV_THREAD invokes a function. This function is executed in a separate thread, which is created by the system. The default behavior for the thread is defined by the implementation, but the sigev_notify_attributes allow customization. This separation of concerns is beneficial for avoiding blocking the main application thread or other critical threads during signal processing.

The discussion on SIGEV_SIGNAL highlights that the signal is posted to the thread that created the timer. This is a crucial detail for understanding signal delivery in threaded environments. The system ensures that the signal is delivered to the correct thread, preventing potential issues with signal masks or thread-specific signal handling.

The rationale behind the sigevent structure and its members is to provide a flexible mechanism for timer notifications. The ability to specify SIGEV_NONE, SIGEV_SIGNAL, or SIGEV_THREAD allows developers to choose the most appropriate method for their application's needs. For instance, SIGEV_NONE can be used for periodic polling of timer status, while SIGEV_SIGNAL and SIGEV_THREAD are used for event-driven notifications. The flexibility extends to passing data through sigval, enabling context-specific actions upon timer expiration without requiring the handler to perform additional lookups. This design choice aims to balance power and simplicity, ensuring that timers can be effectively used in a wide range of applications, from simple event notifications to complex real-time control systems.

The text contrasts the provided mechanism with an alternative where only the timer ID is sent, necessitating extra work in the signal handler to map the ID back to application data. The chosen approach of allowing direct specification of an application-defined value (integer or pointer) in the sigevent structure streamlines this process. This is particularly beneficial when multiple timers are in use, as it avoids the need for complex lookups or shared data structures to correlate timer IDs with their associated contexts.

The sigevent structure's sigval field allows the passing of an integer or a pointer. This flexibility is key for integrating timers into existing application designs. For example, a pointer can be used to pass the address of a specific object or data structure that needs to be accessed or updated when the timer expires. This avoids the need for global variables or complex synchronization mechanisms to share context between the timer creation point and the notification handler. The design prioritizes efficiency and ease of use for common realtime programming patterns.

The rationale emphasizes that the explicit specification of an application-specific datum in the sigevent structure, as opposed to always sending the timer ID, was chosen based on existing practice. This means that developers coming from systems with similar timer interfaces will find this approach familiar. It also suggests that this method is considered more efficient or convenient for typical use cases, as it reduces the need for additional system calls or data lookups within the signal handler or the thread created for notification. The ability to pass a value directly with the notification reduces the overhead associated with identifying the source of the timer event.

The text mentions that timer_ids are dynamically allocated by timer_create(). This implies that applications cannot pre-allocate timer IDs. When a timer expires and SIGEV_SIGNAL is used, the system sends the timer ID as part of the siginfo_t structure's si_value field. This allows the signal handler to directly obtain the timer ID. However, if the application needs to associate a constant or a pointer to application-defined data with the timer, it can use the sigval field of the sigevent structure during timer creation.

The design allows for either passing the timer ID or an application-specific value. If the application passes an application-specific value (integer or pointer) in the sigevent structure, that value is delivered to the handler. If the application chooses not to specify anything in sigevent (by passing NULL), the default behavior is to send SIGALRM. In the case of SIGEV_SIGNAL, the system delivers the timer ID in the si_value.sival_int field. This provides a good balance between flexibility and simplicity. The choice of passing the timer ID by default when evp is NULL simplifies basic timer usage, while the ability to provide a custom sigevent structure allows for more complex scenarios. The system maintains the count in a system structure at the cost of the extra system call to obtain it.

Timer Expiration Signal Parameters

The Realtime Signals Extension option supports an application-specific datum that is delivered to the extended signal handler. This value is explicitly specified by the application, along with the signal number to be delivered, in a sigevent structure. The type of the application-defined value can be either an integer constant or a pointer. This explicit specification of the value, as opposed to always sending the timer ID, was selected based on existing practice.

It is common practice for realtime applications (on non-POSIX systems or realtime extended POSIX systems) to use the parameters of event handlers as the case label of a switch statement or as a pointer to an application-defined data structure. Since timer_ids are dynamically allocated by the timer_create() function, they can be used for neither of these functions without additional application overhead in the signal handler; for example, to search an array of saved timer IDs to associate the ID with a constant or application data structure.
