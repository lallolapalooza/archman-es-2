tpm2_policypcr(1) Manual de Comandos Generales tpm2_policypcr(1)

NOMBRE

tpm2_policypcr(1) - Crea una política que incluye valores de PCR específicos.

SINOPSIS

tpm2_policypcr [OPCIONES]

DESCRIPCIÓN

tpm2_policypcr(1) - Genera un evento de política de PCR con el TPM. Un evento de política de PCR crea una política vinculada a valores de PCR específicos y es útil dentro de políticas más grandes construidas usando policyor y policyauthorize eventos. Consulte tpm2_policyor(1) y tpm2_policyauthorize(1) respectivamente para sus usos. Los datos de PCR incorporados en la política se pueden especificar de una de las 3 maneras: 1. Un archivo que contiene una lista concatenada de valores de PCR como en la salida de tpm2_pcrread. 2. Requerir que los valores de PCR se lean del TPM al no especificar una entrada de archivo de PCR. 3. El resumen (digest) de todos los valores de PCR especificados directamente como un argumento.

OPCIONES

•
-L, --policy=ARCHIVO:

Archivo donde guardar el resumen de la política.

•
-f, --pcr=ARCHIVO:

Ruta o nombre opcional del archivo que contiene los valores de PCR esperados para el índice especificado. Por defecto, se leen los PCRs actuales según la lista establecida.

•
-l, --pcr-list=PCR:

La lista de bancos de PCR y los identificadores de los PCRs seleccionados para cada banco. Se pueden especificar valores de sellado hacia adelante (forward sealing).

•
-S, --session=ARCHIVO:

El archivo de sesión de política generado a través de la opción -S de tpm2_startauthsession(1).

•
ARGUMENTO: El resumen (digest) calculado de todos los valores de PCR especificados como un stream de bytes hexadecimal. Ej: openssl dgst -sha256 -binary pcr.bin | xxd -p -c 32

Referencias

Formato del Objeto de Contexto

El tipo de un objeto de contexto, ya sea un manejador (handle) o un nombre de archivo, se determina según la siguiente lógica *en orden*:

•
Si el argumento es una ruta de archivo, entonces el archivo se carga como un objeto transitorio del TPM restaurado.
•
Si el argumento es una coincidencia *de prefijo* con uno de:
•
owner: la jerarquía del propietario
•
platform: la jerarquía de la plataforma
•
endorsement: la jerarquía de respaldo (endorsement)
•
lockout: el objeto persistente de control de bloqueo
•
Si el argumento se puede cargar como un número, se tratará como un manejador (handle), por ejemplo, 0x81010013 y se usará directamente. _OBJECT_.

Formato de Autorización

La autorización para el uso de un objeto en TPM2.0 puede venir en 3 formas diferentes: 1. Contraseña 2. HMAC 3. Sesiones

NOTA: "Las autorizaciones por defecto son la CONTRASEÑA VACÍA cuando no se especifican".

Contraseñas

Las contraseñas se interpretan en las siguientes formas a continuación utilizando prefijos identificadores.

Nota: Por defecto, las contraseñas se asumen en forma de cadena cuando no tienen prefijo.

Cadena

Una contraseña en formato de cadena, especificada con el prefijo "str:" o su ausencia (cadena raw sin prefijo) no se interpreta y se utiliza directamente para la autorización.

Ejemplos

foobar
str:foobar

Cadena Hexadecimal

Una contraseña en formato de cadena hexadecimal, especificada con el prefijo "hex:", se convierte de forma hexadecimal a un formato de array de bytes, permitiendo así contraseñas con caracteres no imprimibles y/o no amigables para la terminal.

Ejemplo

hex:1122334455667788

Archivo

Una contraseña basada en archivo, especificada por el prefijo "file:", debe ser la ruta de un archivo que contenga la contraseña a leer por la herramienta o un "-" para usar stdin. Almacenar contraseñas en archivos previene fugas de información; las contraseñas pasadas como opciones pueden ser leídas de la lista de procesos o de funciones comunes del historial del shell.

Ejemplos

# para usar stdin y ser preguntado
file:-
# para usar un archivo de una ruta
file:ruta/al/archivo/contraseña
# para hacer eco de una contraseña vía stdin:
echo foobar | tpm2_tool -p file:-
# para usar una cadena de bash (here-string) vía stdin:
tpm2_tool -p file:- <<< foobar

Sesiones

Al usar una sesión de política para autorizar el uso de un objeto, prefije el argumento de la opción con la palabra clave *session*. Luego indique una ruta a un archivo de sesión que fue creado con tpm2_startauthsession(1). Opcionalmente, si la sesión requiere que se envíe un valor de autorización con el manejador de sesión (por ejemplo, contraseña de política), agregue un "+" y una cadena como se describe en la sección de Contraseñas.

Ejemplos

Para usar un archivo de contexto de sesión llamado *session.ctx*.

session:session.ctx

Para usar un archivo de contexto de sesión llamado *session.ctx* **Y** enviar el valor de autorización mypassword.

session:session.ctx+mypassword

Para usar un archivo de contexto de sesión llamado *session.ctx* **Y** enviar el valor de autorización HEX 0x11223344.

session:session.ctx+hex:11223344

Autorizaciones de PCR

Puedes satisfacer una política de PCR usando el prefijo "pcr:" y el minilenguaje de PCR. El minilenguaje de PCR es el siguiente: <especificador-pcr>=<archivo-pcr-raw>

El especificador de PCR está documentado en la sección "Especificadores de banco de PCR".

El archivo-pcr-raw es un argumento opcional que contiene la salida del contenido crudo del PCR tal como lo devuelve tpm2_pcrread(1).

Especificadores de banco de PCR

Ejemplos

Para satisfacer una política de PCR de sha256 en los bancos 0, 1, 2 y 3, use un especificador de:

pcr:sha256:0,1,2,3

especificando *AUTH*.

Especificadores de Banco de PCR

Las listas de selección de Banco de PCR siguen la siguiente especificación:

<BANCO>:<PCR>[,<PCR>] o <BANCO>:all

Se pueden separar varios bancos con '+'.

Por ejemplo:

sha1:3,4+sha256:all

seleccionará los PCRs 3 y 4 del banco SHA1 y todos los PCRs (0 a 23) del banco SHA256.

Ciertos comandos admiten la especificación de valores de sellado hacia adelante (forward sealing) también:

sha1:0,1=da39a3ee5

NAME

tpm2_pcrread - read the PCRs values from the TPM

SYNOPSIS

tpm2_pcrread [OPTIONS] [pcrs ...]

DESCRIPTION

The tpm2_pcrread command is used to read the Platform Configuration Registers (PCRs) values from the TPM. The PCRs are registers in the TPM that can be extended with data but not directly written to or cleared. This allows for the measurement of platform state.

The command can read all PCRs or specific PCRs as specified by the user.

PCR SELECTION

The PCRs to be read can be specified using the pcrs argument. The format for specifying PCRs is a comma-separated list of PCR indices, optionally preceded by a hash algorithm name and colon. If no hash algorithm is specified, the default hash algorithm of the TPM will be used.

Examples:

  • 0,1,2,3: Reads PCRs 0, 1, 2, and 3 using the TPM's default hash algorithm.
  • sha1:0,1,2,3: Reads PCRs 0, 1, 2, and 3 using the SHA1 hash algorithm.
  • sha256:4,5: Reads PCRs 4 and 5 using the SHA256 hash algorithm.
  • all: Reads all PCRs supported by the TPM for the default hash algorithm.
  • all:sha256: Reads all PCRs supported by the TPM for the SHA256 hash algorithm.

The output is a dictionary of PCRs. Each PCR is represented as a key-value pair, where the key is the PCR index and the value is its digest in hexadecimal format. The digest length will match the bank size of the specified hash algorithm.

If no pcrs are specified, all PCRs will be read using the TPM's default hash algorithm.

The output format can be controlled using the --format option, which accepts json or hex. The default format is hex, which prints the digest in hexadecimal.

OPTIONS

•
-o, --output output file for the PCR values. Default to stdout.
•
-f, --format [hex|json] Specify the output format. Default is hex.
•
-P, --password password for the TPM.
•
-Q, --quiet quiet mode.
•
-T, --tcti TCTI context configuration string.
•
--caching-policy PCR caching policy. It is a comma separated list of PCR selections. The tool will use these PCR selections to ensure that the PCR values used are not stale. The format is the same as PCR selections.
•
--caching-policy-file PCR caching policy file. Same format as --caching-policy.

A PCR selection string specifies a list of PCRs to read, along with an optional hash algorithm. For example, sha1:0,1,2,3 specifies PCRs 0, 1, 2, and 3 to be read using the SHA1 hash algorithm. If the algorithm is omitted, the TPM's default hash algorithm is used.

Example usage of PCR selections:

•
To read PCRs 0, 1, and 2 using the TPM's default hash algorithm: tpm2_pcrread 0,1,2
•
To read PCRs 0, 1, and 2 using the SHA256 algorithm: tpm2_pcrread sha256:0,1,2
•
To read all PCRs using the SHA1 algorithm: tpm2_pcrread all:sha1
•
To read all PCRs using the TPM's default hash algorithm: tpm2_pcrread all

The --caching-policy option allows you to specify PCRs that should be checked for changes before reading the current PCR values. This can help prevent using stale PCR values in certain scenarios. For example, --caching-policy sha256:0,1,2,3 would ensure that PCRs 0-3 have not changed since the last time they were read. This option can be specified multiple times to include multiple PCR selections.

The --caching-policy-file option allows you to load the PCR selections from a file. Each line in the file should contain a valid PCR selection string.

Digest lengths must match the bank size. An optional 0x prefix will be stripped off.

Note

PCR Selections allow for up to 5 hash to pcr selection mappings. This is a limitation in design in the single call to the tpm to get the pcr values. PCR.

TCTI Configuration

The TCTI or “Transmission Interface” is the communication mechanism with the TPM. TCTIs can be changed for communication with TPMs across different mediums.

To control the TCTI, the tools respect:

1.
The command line option -T or --tcti
2.
The environment variable: TPM2TOOLS_TCTI.

Note: The command line option always overrides the environment variable.

The current known TCTIs are:

•
tabrmd - The resource manager, called tabrmd. Note that tabrmd and abrmd as a tcti name are synonymous.
•
mssim - Typically used for communicating to the TPM software simulator.
•
device - Used when talking directly to a TPM device file.
•
none - Do not initalize a connection with the TPM. Some tools allow for off-tpm options and thus support not using a TCTI. Tools that do not support it will error when attempted to be used without a TCTI connection. Does not support ANY options and MUST BE presented as the exact text of “none”.

The arguments to either the command line option or the environment variable are in the form:

<tcti-name>:<tcti-option-config>

Specifying an empty string for either the <tcti-name> or <tcti-option-config> results in the default being used for that portion respectively.

TCTI Defaults

When a TCTI is not specified, the default TCTI is searched for using dlopen(3) semantics. The tools will search for tabrmd, device and mssim TCTIs IN THAT ORDER and USE THE FIRST ONE FOUND. You can query what TCTI will be chosen as the default by using the -v option to print the version information. The “default-tcti” key-value pair will indicate which of the aforementioned TCTIs is the default.

Custom TCTIs

Any TCTI that implements the dynamic TCTI interface can be loaded. The tools internally use dlopen(3), and the raw tcti-name value is used for the lookup. Thus, this could be a path to the shared library, or a library name as understood by dlopen(3) semantics.

TCTI OPTIONS

This collection of options are used to configure the various known TCTI modules available:

•
device: For the device TCTI, the TPM character device file for use by the device TCTI can be specified. The default is /dev/tpm0.

Example: -T device:/dev/tpm0 or export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: For the mssim TCTI, the domain name or IP address and port number used by the simulator can be specified. The default are 127.0.0.1 and 2321.

Example: -T mssim:host=localhost,port=2321 or export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,' character. Each key and value string are separated by a `=' character.
•
TCTI abrmd supports two keys:
1.
`bus_name' : The name of the tabrmd service on the bus (a string).
2.
`bus_type' : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

\--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules.

EXAMPLES

Starts a trial session, builds a PCR policy and uses that policy in the creation of an object. Then, it uses a policy session to unseal some data stored in the object.

Step 1: create a policy

tpm2_createprimary -C e -g sha256 -G ecc -c primary.ctx
tpm2_pcrread -o pcr.dat "sha1:0,1,2,3"
tpm2_startauthsession -S session.dat
tpm2_policypcr -S session.dat -l "sha1:0,1,2,3" -f pcr.dat -L policy.dat
tpm2_flushcontext session.dat

Step 2: create an object using that policy

tpm2_create -Q -u key.pub -r key.priv -C primary.ctx -L policy.dat \
-i- <<< "12345678"
tpm2_load -C primary.ctx -u key.pub -r key.priv -n unseal.key.name \
-c unseal.key.ctx

Step 3: Satisfy the policy

tpm2_startauthsession --policy-session -S session.dat
tpm2_policypcr -S session.dat -l "sha1:0,1,2,3" -f pcr.dat -L policy.dat

Step 4: Use the policy

tpm2_unseal -psession:session.dat -c unseal.key.ctx
12345678
tpm2_flushcontext session.dat

Limitations

It expects a session to be already established via tpm2_startauthsession(1) and requires one of the following:

•
direct device access
•
extended session support with tpm2-abrmd.

Without it, most resource managers will not save session state between command invocations.
