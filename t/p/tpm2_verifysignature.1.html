tpm2_verifysignature(1) Manual de Comandos Generales tpm2_verifysignature(1)

NOMBRE

tpm2_verifysignature(1) - Valida una firma usando el TPM.

SINOPSIS

tpm2_verifysignature [OPCIONES]

DESCRIPCIÓN

tpm2_verifysignature(1) - Utiliza las claves cargadas para validar una firma sobre un mensaje con el resumen del mensaje pasado al TPM. Si la comprobación de la firma tiene éxito, el TPM producirá un TPMT_TK_VERIFIED. De lo contrario, el TPM devolverá TPM_RC_SIGNATURE. Si el objeto hace referencia a una clave asimétrica, solo se necesita cargar la parte pública de la clave. Si el objeto hace referencia a una clave simétrica, se deben cargar tanto la parte pública como la privada.

OPCIONES

•
-c, --key-context=OBJETO:

Objeto de contexto para el contexto de clave utilizado en la operación. Puede ser un archivo o un número de identificador. Consulte la sección “Formato del Objeto de Contexto”.

•
-g, --hash-algorithm=ALGORITMO:

El algoritmo de hash utilizado para digerir el mensaje. Los algoritmos deben seguir los “estándares de formato”, consulte la sección “Especificadores de Algoritmos”. Además, consulte la sección “Algoritmos de Hash Soportados” para obtener una lista de los algoritmos de hash soportados.

•
-m, --message=ARCHIVO:

El archivo del mensaje, que contiene el contenido a digerir.

•
-d, --digest=ARCHIVO:

El archivo de hash de entrada, que contiene el hash del mensaje. Si se selecciona esta opción, no es necesario especificar las opciones de mensaje (-m) y algoritmo (-g).

•
-s, --signature=ARCHIVO:

El archivo de firma de entrada de la firma a validar.

•
-f, --scheme=ESQUEMA:

El esquema de firma que se utilizó para firmar el mensaje. Esta opción solo debe especificarse si la firma proviene de un estándar no *tss*, como openssl. Consulte “Especificadores de formato de firma” para más detalles. El formato *tss* contiene los metadatos de firma necesarios para entender su esquema de firma.

Los esquemas de firma deben seguir los “estándares de formato”, consulte la sección “Especificadores de Algoritmos”.

•
--format=ESQUEMA:

Obsoleto. Igual que --scheme.

•
-t, --ticket=ARCHIVO:

El archivo de ticket para registrar la estructura de validación.

Referencias

Formato del Objeto de Contexto

El tipo de un objeto de contexto, ya sea un identificador o un nombre de archivo, se determina según la siguiente lógica, *en orden*:

•
Si el argumento es una ruta de archivo, entonces el archivo se carga como un objeto transitorio del TPM restaurado.
•
Si el argumento es una coincidencia de *prefijo* en uno de:
•
owner: la jerarquía del propietario
•
platform: la jerarquía de la plataforma
•
endorsement: la jerarquía de respaldo
•
lockout: el objeto persistente de control de bloqueo
•
Si el argumento puede cargarse como un número, se tratará como un identificador, por ejemplo, 0x81010013 y se usará directamente.*OBJETO*.

Especificadores Complejos

Los objetos, cuando se especifican para su creación por el TPM, tienen numerosos algoritmos para poblar en los datos públicos. Cosas como el tipo, esquema y detalles asimétricos, tamaño de clave, etc. A continuación se muestra el formato general para especificar estos datos: <tipo>:<esquema>:<detalles-simétricos>

Especificadores de Tipo

Esta parte del especificador de algoritmo complejo es obligatoria. El esquema y los detalles simétricos restantes se establecerán por defecto según el tipo especificado y el tipo del objeto que se esté creando.

•
aes - AES por defecto: aes128
•
aes128<modo> - AES de 128 bits con modo opcional (ctr|ofb|cbc|cfb|ecb). Si no se especifica el modo, por defecto es null.
•
aes192<modo> - Igual que aes128<modo>, excepto por un tamaño de clave de 192 bits.
•
aes256<modo> - Igual que aes128<modo>, excepto por un tamaño de clave de 256 bits.
•
sm4 - SM4 por defecto: sm4128
•
sm4128 o sm4_128 <modo> - SM4 de 128 bits con modo opcional (ctr|ofb|cbc|cfb|ecb).

CRYPTO SPECIFIERS

These command line options are used to specify the cryptographic algorithms used by the tools. These specifiers are a combination of the key types and the cryptographic operations.

The list below follows the format of how the specifiers are formed:

    <key-type>:<symmetric-details>
    <key-type>:<scheme-details>
    <key-type>:<scheme-details>:<symmetric-details>

Where:

•
key-type - The type of asymmetric key to create. Defaults to rsa2048.
•
symmetric-details - Optional, defaults to null. Specifies the symmetric algorithm and mode. If not specified, defaults to aes128cfb.
•
scheme-details - Optional, defaults to null. Specifies the signing or encryption scheme. If not specified, defaults to null.

Key Type Specifiers

Key types can be specified using the following options:

•
rsa - Default RSA: rsa2048
•
rsa1024 - RSA with 1024 bit keysize.
•
rsa2048 - RSA with 2048 bit keysize.
•
rsa3072 - RSA with 3072 bit keysize.
•
rsa4096 - RSA with 4096 bit keysize.
•
ecc - Elliptical Curve, defaults to ecc256.
•
ecc192 or ecc_nist_p192 - 192 bit ECC NIST curve
•
ecc224 or ecc_nist_p224 - 224 bit ECC NIST curve
•
ecc256 or ecc_nist_p256 - 256 bit ECC NIST curve
•
ecc384 or ecc_nist_p384 - 384 bit ECC NIST curve
•
ecc521 or ecc_nist_p521 - 521 bit ECC NIST curve
•
ecc_sm2 or ecc_sm2_p256 - 256 bit SM2 curve

Scheme Specifiers

Next, is an optional field, it can be skipped.

Schemes are usually Signing Schemes or Asymmetric Encryption Schemes. Most signing schemes take a hash algorithm directly following the signing scheme. If the hash algorithm is missing, it defaults to sha256. Some take no arguments, and some take multiple arguments.

Hash Optional Scheme Specifiers

These scheme specifiers are followed by a dash and a valid hash algorithm, For example: oaep-sha256.

•
oaep
•
ecdh
•
rsassa
•
rsapss
•
ecdsa
•
ecschnorr
•
sm2

Multiple Option Scheme Specifiers

This scheme specifier is followed by a count (max size UINT16) then followed by a dash(-) and a valid hash algorithm. * ecdaa For example, ecdaa4-sha256. If no count is specified, it defaults to 4.

No Option Scheme Specifiers

This scheme specifier takes NO arguments. * rsaes

Symmetric Details Specifiers

This field is optional, and defaults based on the type of object being created and it’s attributes. Generally, any valid Symmetric specifier from the Type Specifiers list should work. If not specified, an asymmetric objects symmetric details defaults to aes128cfb.

Examples

Create an rsa2048 key with an rsaes asymmetric encryption scheme

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Create an ecc256 key with an ecdaa signing scheme with a count of 4 and sha384 hash

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv cryptographic algorithms ALGORITHM.

TCTI Configuration

The TCTI or “Transmission Interface” is the communication mechanism with the TPM. TCTIs can be changed for communication with TPMs across different mediums.

To control the TCTI, the tools respect:

1.
The command line option -T or --tcti
2.
The environment variable: TPM2TOOLS_TCTI.

Note: The command line option always overrides the environment variable.

The current known TCTIs are:

•
tabrmd - The resource manager, called tabrmd. Note that tabrmd and abrmd as a tcti name are synonymous.
•
mssim - Typically used for communicating to the TPM software simulator.
•
device - Used when talking directly to a TPM device file.
•
none - Do not initalize a connection with the TPM. Some tools allow for off-tpm options and thus support not using a TCTI. Tools that do not support it will error when attempted to be used without a TCTI connection. Does not support ANY options and MUST BE presented as the exact text of “none”.

The arguments to either the command line option or the environment variable are in the form:

<tcti-name>:<tcti-option-config>

Specifying an empty string for either the <tcti-name> or <tcti-option-config> results in the default being used for that portion respectively.

TCTI Defaults

When a TCTI is not specified, the default TCTI is searched for using dlopen(3) semantics. The tools will search for tabrmd, device and mssim TCTIs IN THAT ORDER and USE THE FIRST ONE FOUND. You can query what TCTI will be chosen as the default by using the -v option to print the version information. The “default-tcti” key-value pair will indicate which of the aforementioned TCTIs is the default.

Custom TCTIs

Any TCTI that implements the dynamic TCTI interface can be loaded. The tools internally use dlopen(3), and the raw tcti-name value is used for the lookup. Thus, this could be a path to the shared library, or a library name as understood by dlopen(3) semantics.

TCTI OPTIONS

This collection of options are used to configure the various known TCTI modules available:

•
device: For the device TCTI, the TPM character device file for use by the device TCTI can be specified. The default is /dev/tpm0.

Example: -T device:/dev/tpm0 or export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: For the mssim TCTI, the domain name or IP address and port number used by the simulator can be specified. The default are 127.0.0.1 and 2321.

Example: -T mssim:host=localhost,port=2321 or export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,' character. Each key and value string are separated by a `=' character.
•
TCTI abrmd supports two keys:
1.
`bus_name' : The name of the tabrmd service on the bus (a string).
2.
`bus_type' : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

\--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules.

tpm2_verifysignature(1) — tpm2-tools

NAME

tpm2_verifysignature 1

SYNOPSIS

tpm2_verifysignature [OPTIONS] [ARGUMENT...]

DESCRIPTION

Verify a signature using a TPM.

This command allows the verification of a digital signature over data, using a key previously loaded into the TPM or created by the TPM.

The TPM can be used for cryptographic operations and as a secure environment to store keys. The tpm2_verifysignature tool utilizes the TPM to perform the signature verification operation.

The tool expects the message digest to be provided as an argument. The digest can be computed by the tool itself, or provided by the user.

The digest size should match the hash algorithm specified.

Public Key

The public key associated with the private key used to sign the message must be provided to the TPM. This can be done via a public key context file (created with tpm2_create or tpm2_createexternal) or by providing a file containing the public key.

OPTIONS

Context Object Format

The tool accepts a context object that references a key.

-c, --context=KEY
specifies the context object of the key used for verification. The key can be referenced via a handle or a path to a context file.

Algorithm Specifiers

Specifies the algorithm parameters for the operation.

-g, --hash-algorithm=ALG
specifies the hash algorithm used to digest the message. Supported values are: sha1, sha256, sha384, sha512, sm3.
-f, --format=FMT
specifies the signature format. Supported values are: tss (default) and plain.
-s, --signature=SIG
specifies the file containing the signature to be verified.
--scheme=SCHEME
specifies the signature scheme. Supported values are: rsass, rsapkass, ecsdarss, ecdkwss, hmac.

COMMON OPTIONS

Common options such as controlling the output format, verbosity, and connection settings.

-Q, --quiet
suppresses the output on stdout.
-V, --version
prints the version number of the tool.
-h, --help
prints the help message and exits.

TCTI Configuration

Specify the Tagged Command Transmission Interface (TCTI) used to communicate with the TPM.

-I, --tcti=name:device
specifies the TCTI to use. The format is typically name:device. For example, mssim:host=localhost,port=6443 or device:lib=libtss.so,dev=/dev/tpm0.

TCTI OPTIONS

Options specific to the selected TCTI.

--tcti-opt=option
specifies an option for the TCTI. This option can be used multiple times.

Signature Format Specifiers

Format selection for the signature output file. tss (the default) will output a binary blob according to the TPM 2.0 specification and any potential compiler padding. The option plain will output the plain signature data as defined by the used cryptographic algorithm.

EXAMPLES

Sign and verify with the TPM using the endorsement hierarchy 

tpm2_createprimary -C e -c primary.ctx
tpm2_create -G rsa -u rsa.pub -r rsa.priv -C primary.ctx
tpm2_load -C primary.ctx -u rsa.pub -r rsa.priv -c rsa.ctx
echo "my message > message.dat
tpm2_sign -c rsa.ctx -g sha256 -s sig.rssa message.dat
tpm2_verifysignature -c rsa.ctx -g sha256 -m message.dat -s sig.rssa

Sign with openssl and verify with the TPM 

# Generate an ECC key
openssl ecparam -name prime256v1 -genkey -noout -out private.ecc.pem
openssl ec -in private.ecc.pem -out public.ecc.pem -pubout
# Generate a hash to sign (OSSL needs the hash of the message)
echo "data to sign" > data.in.raw
sha256sum data.in.raw | awk '{ print "000000 " $1 }' | \
xxd -r -c 32 > data.in.digest
# Load the private key for signing
tpm2_loadexternal -Q -G ecc -r private.ecc.pem -c key.ctx
# Sign in the TPM and verify with OSSL
tpm2_sign -Q -c key.ctx -g sha256 -d data.in.digest -f plain -s data.out.signed
openssl dgst -verify public.ecc.pem -keyform pem -sha256 \
-signature data.out.signed data.in.raw
# Sign with openssl and verify with TPM
openssl dgst -sha256 -sign private.ecc.pem -out data.out.signed data.in.raw
tpm2_verifysignature -Q -c key.ctx -g sha256 -m data.in.raw -f ecdsa \
-s data.out.signed
