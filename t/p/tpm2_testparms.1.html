NOMBRE

tpm2_testparms(1) - Verifica que el conjunto de algoritmos especificado es compatible con TPM

SINOPSIS

tpm2_testparms [OPCIONES] [ARGUMENTO]

DESCRIPCIÓN

tpm2_testparms(1) - Comprueba que el conjunto especificado por ALG_SPEC está disponible para su uso según ALGORITMO.

Los algoritmos deben seguir las "normas de formato", véase la sección "Especificadores de Algoritmos".

Además, véase la sección "Esquemas de Firma Soportados" para obtener una lista de algoritmos hash soportados.

OPCIONES

Esta herramienta no acepta opciones específicas de la herramienta.

Configuración TCTI

El TCTI o "Interfaz de Transmisión" es el mecanismo de comunicación con el TPM. Los TCTI se pueden cambiar para la comunicación con TPMs a través de diferentes medios.

Para controlar el TCTI, las herramientas respetan:

1.
La opción de línea de comandos -T o --tcti
2.
La variable de entorno: TPM2TOOLS_TCTI.

Nota: La opción de línea de comandos siempre tiene prioridad sobre la variable de entorno.

Los TCTI conocidos actualmente son:

•
tabrmd - El gestor de recursos, llamado tabrmd. Tenga en cuenta que tabrmd y abrmd como nombre de tcti son sinónimos.
•
mssim - Típicamente utilizado para comunicarse con el simulador de software de TPM.
•
device - Utilizado al hablar directamente con el archivo del dispositivo TPM.
•
none - No inicializar una conexión con el TPM. Algunas herramientas permiten opciones fuera de tpm y, por lo tanto, soportan no usar un TCTI. Las herramientas que no lo soportan generarán un error cuando se intente usar sin una conexión TCTI. No soporta NINGUNA opción y DEBE presentarse como el texto exacto de "none".

Los argumentos para la opción de línea de comandos o la variable de entorno tienen el formato:

<nombre-tcti>:<config-opciones-tcti>

Especificar una cadena vacía para el <nombre-tcti> o la <config-opciones-tcti> resulta en el uso del valor predeterminado para esa porción respectivamente.

Valores Predeterminados TCTI

Cuando no se especifica un TCTI, se busca el TCTI predeterminado utilizando la semántica de dlopen(3). Las herramientas buscarán los TCTI tabrmd, device y mssim EN ESE ORDEN y USARÁN EL PRIMERO ENCONTRADO. Puede consultar qué TCTI se elegirá como predeterminado usando la opción -v para mostrar la información de versión. El par clave-valor "default-tcti" indicará cuál de los TCTI mencionados es el predeterminado.

TCTIs Personalizados

Cualquier TCTI que implemente la interfaz TCTI dinámica puede ser cargado. Las herramientas internamente usan dlopen(3), y el valor bruto del nombre-tcti se usa para la búsqueda. Por lo tanto, esto podría ser una ruta a la biblioteca compartida, o un nombre de biblioteca según lo entiende la semántica de dlopen(3).

OPCIONES TCTI

Esta colección de opciones se utilizan para configurar los diversos módulos TCTI conocidos disponibles:

•
device: Para el TCTI de dispositivo, se puede especificar el archivo del dispositivo de caracteres TPM a usar por el TCTI de dispositivo. El valor predeterminado es /dev/tpm0.

Ejemplo: -T device:/dev/tpm0 o export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: Para el TCTI mssim, se puede especificar el nombre de dominio o la dirección IP y el número de puerto utilizados por el simulador. Los valores predeterminados son 127.0.0.1 y 2321.

Ejemplo: -T mssim:host=localhost,port=2321 o export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: Para el TCTI abrmd, el formato de la cadena de configuración es una serie de pares clave-valor simples separados por un carácter ','. Cada clave y valor se separan por un carácter '='.
•
TCTI abrmd soporta dos claves:
1.
`bus_name' : El nombre del servicio tabrmd en el bus (una cadena).
2.
`bus_type' : El tipo de la instancia de dbus (una cadena) limitada a `session' y `system'.

Especifica el nombre del TCTI tabrmd y una cadena de configuración de bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Especifica el TCTI predeterminado (abrmd) y una cadena de configuración de bus_type=session:

\--tcti:bus_type=session

NOTA: abrmd y tabrmd son sinónimos. los diversos módulos TCTI conocidos.

Especificadores de Algoritmos

Las opciones que aceptan algoritmos soportan "nombres amigables".

Hay dos clases principales de cadenas de especificación de algoritmos, simples y complejas. Solo ciertos algoritmos serán aceptados por el TPM, basándose en el uso y las condiciones.

Especificadores simples

Estas son cadenas sin datos de especificación adicionales. Al crear objetos, las partes no especificadas de un objeto se asumen como predeterminadas. Puede encontrar la lista de "Especificadores Simples" conocidos a continuación.

NAME

tpm2_algparse - parse algorithm specifiers

SYNOPSIS

tpm2_algparse [OPTIONS] [ALGORITHM...];
tpm2_testparms [OPTIONS] [ALGORITHM...];

DESCRIPTION

The tpm2_algparse and tpm2_testparms utilities parse TPM2 algorithm specifiers. The primary difference is that tpm2_algparse prints out the parsed structure while tpm2_testparms tests whether the algorithm specifier is valid.

An algorithm specifier is used for specifying cryptographic algorithms to the TPM2. These specifiers are often used for object creation, key generation, and other cryptographic operations. The specifier is a string composed of different parts separated by colons (:) or dashes (-).

The general format for specifying algorithms is:

<type>[:<scheme>[:<symmetric-details>]]

Where:

type
This is the primary algorithm type (e.g., aes, ecc, rsa). This field is required.
scheme
This is a secondary algorithm specification that often relates to how the primary type is used (e.g., signing, encryption, hashing). This field is optional.
symmetric-details
This field provides specific details for symmetric algorithms, such as key size and mode (e.g., aes128ctr, sm4128cbc).

The order and presence of these fields can vary based on the algorithm type.

Complex Specifiers

Objects, when specified for creation by the TPM, have numerous algorithms to populate in the public data. Things like type, scheme and asymmetric details, key size, etc. Below is the general format for specifying this data: <type>:<scheme>:<symmetric-details>

Type Specifiers

This portion of the complex algorithm specifier is required. The remaining scheme and symmetric details will default based on the type specified and the type of the object being created.

•
aes - Default AES: aes128
•
aes128<mode> - 128 bit AES with optional mode (ctr|ofb|cbc|cfb|ecb). If mode is not specified, defaults to null.
•
aes192<mode> - Same as aes128<mode>, except for a 192 bit key size.
•
aes256<mode> - Same as aes128<mode>, except for a 256 bit key size.
•
sm4 - Default SM4: sm4128
•
sm4128 or sm4_128 <mode> - 128 bit SM4 with optional mode (ctr|ofb|cbc|cfb|ecb). If mode is not specified, defaults to null.
•
ecc - Elliptical Curve, defaults to ecc256.
•
ecc192 or ecc_nist_p192 - 192 bit ECC NIST curve
•
ecc224 or ecc_nist_p224 - 224 bit ECC NIST curve
•
ecc256 or ecc_nist_p256 - 256 bit ECC NIST curve
•
ecc384 or ecc_nist_p384 - 384 bit ECC NIST curve
•
ecc521 or ecc_nist_p521 - 521 bit ECC NIST curve
•
ecc_sm2 or ecc_sm2_p256 - 256 bit SM2 curve
•
rsa - Default RSA: rsa2048
•
rsa1024 - RSA with 1024 bit keysize.
•
rsa2048 - RSA with 2048 bit keysize.
•
rsa3072 - RSA with 3072 bit keysize.
•
rsa4096 - RSA with 4096 bit keysize.

Scheme Specifiers

Next, is an optional field, it can be skipped.

Schemes are usually Signing Schemes or Asymmetric Encryption Schemes. Most signing schemes take a hash algorithm directly following the signing scheme. If the hash algorithm is missing, it defaults to sha256. Some take no arguments, and some take multiple arguments.

Hash Optional Scheme Specifiers

These scheme specifiers are followed by a dash and a valid hash algorithm, For example: oaep-sha256.

Multiple Option Scheme Specifiers

This scheme specifier is followed by a count (max size UINT16) then followed by a dash(-) and a valid hash algorithm. * ecdaa For example, ecdaa4-sha256. If no count is specified, it defaults to 4.

No Option Scheme Specifiers

This scheme specifier takes NO arguments. * rsaes

Symmetric Details Specifiers

This field is optional, and defaults based on the type of object being created and it’s attributes. Generally, any valid Symmetric specifier from the Type Specifiers list should work. If not specified, an asymmetric objects symmetric details defaults to aes128cfb.

Examples

Create an rsa2048 key with an rsaes asymmetric encryption scheme

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Create an ecc256 key with an ecdaa signing scheme with a count of 4 and sha384 hash

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv cryptographic algorithms ALGORITHM.

Signature Format Specifiers

Format selection for the signature output file. tss (the default) will output a binary blob according to the TPM 2.0 specification and any potential compiler padding. The option plain will output the plain signature data as defined by the used cryptographic algorithm.

EXAMPLES

Check whether if “rsa” is supported

tpm2_testparms rsa

Check that ECDSA using P-256 with AES-128 CTR mode is available

tpm2_testparms ecc256:ecdsa:aes128ctr

NAME
tpm2_testparms - Test TPM2 Parameters
SYNOPSIS
tpm2_testparms [OPTIONS]
tpm2_testparms [OPTIONS] --yaml-file <yaml file>
tpm2_testparms [OPTIONS] --config-file <config file>
DESCRIPTION

The tpm2_testparms utility is used to test and validate TPM2 configuration parameters. It can read parameters from a YAML file or a configuration file, or it can read parameters from the command line.

The tool is useful for ensuring that the parameters provided to other TPM2 tools are valid and correctly formatted. It performs checks on various aspects of TPM2 configuration, including TCTI settings, algorithm specifiers, and signature formats.

OPTIONS

This utility accepts the following options:

  • --yaml-file <yaml file>: Specifies a YAML file containing TPM2 parameters.
  • --config-file <config file>: Specifies a configuration file containing TPM2 parameters.
  • -h, --help: Prints a help message and exits.
  • -v, --version: Prints version information and exits.
COMMON OPTIONS

The following options are common to most tpm2 utilities:

  • -I <TCTI>, --tcti <TCTI>: Specifies the TPM Communication and Test Interface (TCTI). See the tpm2_tools.conf(5) man page for details on the TCTI format.
  • -C <context file>, --context <context file>: Specifies a TPM context file.
  • -Q, --quiet: Suppress verbose output.
  • -V, --verbose: Enable verbose output.
  • -T, --tpm-device <device node>: The TPM device node path. Defaults to /dev/tpm0.
TCTI Configuration

The TCTI specifies how the TPM2 tools communicate with the TPM device. Common TCTIs include:

  • device: Direct access to the TPM device (e.g., /dev/tpm0).
  • mssim: Communication with a TPM simulator.
  • socket: Communication over a network socket.

The exact format and options for each TCTI are described in the tpm2_tools.conf(5) man page.

TCTI OPTIONS

Depending on the selected TCTI, additional options may be required. For example, when using the socket TCTI, you will need to specify the host and port.

Refer to the tpm2_tools.conf(5) man page for a comprehensive list of TCTI options.

Algorithm Specifiers

tpm2_testparms validates algorithm specifiers. These typically refer to cryptographic algorithms like RSA, ECC, SHA, etc. The tool checks if the specified algorithms are supported by the TPM and are correctly formatted.

Signature Format Specifiers

This utility also validates signature format specifiers. This ensures that the format of signatures generated or verified by the TPM is consistent and correct, adhering to standards like PKCS#1 or ECDSA.

EXAMPLES

Test parameters from a YAML file:

$ tpm2_testparms --yaml-file my_tpm_params.yaml

Test parameters from a configuration file:

$ tpm2_testparms --config-file tpm2_tools.conf

Test with a specific TCTI and TPM device:

$ tpm2_testparms -I device:/dev/tpm0 -T /dev/tpm0
                                    
Returns

Returns 0 if the parameters are valid, and a non-zero value otherwise.
