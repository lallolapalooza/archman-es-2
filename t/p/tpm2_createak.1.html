NOMBRE

tpm2_createak(1) - Genera una clave de atestación con el algoritmo dado bajo la jerarquía de aprobación.

SINOPSIS

tpm2_createak [OPCIONES]

DESCRIPCIÓN

tpm2_createak(1) - Genera una clave de atestación (AK) con el algoritmo especificado bajo la jerarquía de aprobación. El contexto de la clave de atestación se especifica a través de -c.

La herramienta produce una representación YAML del nombre de la clave cargada, por ejemplo:

loaded-key:
  name: 000bac149518baa05540a0678bd9b624f8a98d042e46c60f4d098ba394d36fc49268

OPCIONES

•
-P, --eh-auth=AUTH:

El valor de autorización para la jerarquía de aprobación.

•
-p, --ak-auth=AUTH

El valor de autorización para el objeto de clave de atestación creado.

•
-C, --ek-context=OBJECT:

El objeto de clave de aprobación (EK).

•
-c, --ak-context=FILE:

La ruta del archivo donde se guardará el contexto del objeto de la clave de atestación.

•
-G, --key-algorithm=ALGORITHM:

Especifica el algoritmo de la clave de atestación. Admite:

•
ecc - Una clave NIST_P256 por defecto. Se pueden seleccionar curvas alternativas utilizando especificadores de algoritmo (por ejemplo, ecc384 o ecc_nist_p384).
•
rsa - Una clave RSA2048.
•
keyedhash - clave hmac.
•
-g, --hash-algorithm=ALGORITHM:

Especifica el algoritmo de hash utilizado para firmar.

•
-s, --signing-algorithm=ALGORITHM:

El algoritmo de firma.

•
-u, --public=FILE:

El archivo donde se guardará la porción pública de la clave de atestación.

•
-n, --ak-name=FILE:

El archivo donde se guardará el nombre de la clave de atestación, opcional.

•
-r, --private=FILE:

El archivo de salida que contiene la porción sensible del objeto, opcional. # Detalles de Protección

Los objetos que pueden moverse fuera del TPM deben ser protegidos (confidencialidad e integridad). Por ejemplo, los objetos transitorios requieren que los datos protegidos por el TPM (clave o material de sellado) se almacenen fuera del TPM. Esto se ve en herramientas como tpm2_create(1), donde la opción -r produce estos datos protegidos. Este blob contiene las porciones sensibles del objeto. Las porciones sensibles del objeto están protegidas por el objeto padre, utilizando los detalles de cifrado simétrico del padre para cifrar los datos sensibles y realizar un HMAC.

Los detalles profundos se pueden encontrar en las secciones 23 de:

•
https://trustedcomputinggroup.org/wp-content/uploads/TPM-Rev-2.0-Part-1-Architecture-01.38.pdf

Notablemente, la Figura 20 es relevante, aunque se refiera específicamente a blobs de duplicación, el proceso es idéntico.

Si la salida es de tpm2_duplicate(1), la salida será ligeramente diferente, como se describe completamente en la sección 23.

•
-f, --format:

Selección de formato para el archivo de salida de clave pública. `tss' (el valor por defecto) producirá un blob binario según la Especificación TPM 2.0. `pem' producirá una clave pública codificada en PEM compatible con OpenSSL. `der' producirá una clave pública codificada en DER compatible con OpenSSL. `tpmt' producirá un blob binario de la estructura TPMT_PUBLIC referenciada en las especificaciones TPM 2.0.

Selección de formato para el archivo de salida de firma.

•
-q, --ak-qualified-name=FILE:

El nombre cualificado del objeto de clave de atestación. El nombre cualificado es el nombre cualificado del objeto padre (el EK en esta instancia) y el nombre del objeto en sí. Por lo tanto, el nombre cualificado de un objeto sirve para vincularlo a sus padres.

Referencias

Formato del Objeto de Contexto

El tipo de un objeto de contexto, ya sea un manejador o un nombre de archivo, se determina según la siguiente lógica *en orden*:

•
Si el argumento es una ruta de archivo, entonces se carga el archivo como un objeto transitorio de TPM restaurado.
•
Si el argumento coincide con un *prefijo* de uno de:
•
owner: la jerarquía de propietario
•
platform: la jerarquía de plataforma
•
endorsement: la jerarquía de aprobación
•
lockout: el objeto persistente de control de bloqueo
•
Si el argumento se puede cargar como un número, se tratará como un manejador, por ejemplo, 0x81010013 y se utilizará directamente._OBJETO_.

Formato de Autorización

La autorización para el uso de un objeto en TPM2.0 puede venir en 3 formas diferentes: 1. Contraseña 2. HMAC 3. Sesiones

NOTA: "Las autorizaciones son por defecto la **CONTRASEÑA VACÍA** cuando no se especifican".

Contraseñas

Las contraseñas se interpretan en las siguientes formas utilizando identificadores de prefijo.

Nota: Por defecto, las contraseñas se asumen en forma de cadena cuando no tienen prefijo.

Cadena

Una contraseña en formato de cadena, especificada con el prefijo "str:" o su ausencia (cadena cruda sin prefijo) no se interpreta y se usa directamente para la autorización.

Ejemplos

foobar
str:foobar

Cadena hexadecimal

Una contraseña en formato de cadena hexadecimal, especificada con el prefijo "hex:", se convierte de forma hexadecimal a una forma de array de bytes, permitiendo así contraseñas con caracteres no imprimibles y/o poco amigables con la terminal.

Ejemplo

hex:1122334455667788

Archivo

Una contraseña basada en archivo, especificada por el prefijo "file:", debe ser la ruta de un archivo que contenga la contraseña que será leída por la herramienta, o un "-" para usar la entrada estándar. Almacenar contraseñas en archivos evita la fuga de información; las contraseñas pasadas como opciones pueden ser leídas de la lista de procesos o de las funciones comunes del historial del shell.

Ejemplos

# para usar entrada estándar y solicitarla
file:-
# para usar un archivo de una ruta
file:ruta/al/archivo/de/contraseña
# para enviar una contraseña vía entrada estándar:
echo foobar | tpm2_tool -p file:-
# para usar una cadena de bash vía entrada estándar:
tpm2_tool -p file:- <<< foobar

Sesiones de Política

Al utilizar una sesión de política para autorizar el uso de un objeto, prefije el argumento de la opción con la palabra clave session. Luego, indique una ruta a un archivo de sesión que se creó con tpm2_startauthsession(1). Opcionalmente, si la sesión requiere un valor de autenticación que se envíe con el identificador de sesión (por ejemplo, contraseña de política), agregue un + y una cadena como se describe en la sección Contraseñas.

Ejemplos

Para usar un archivo de contexto de sesión llamado session.ctx.

session:session.ctx

Para usar un archivo de contexto de sesión llamado session.ctx Y enviar el valor de autenticación mypassword.

session:session.ctx+mypassword

Para usar un archivo de contexto de sesión llamado session.ctx Y enviar el valor de autenticación HEX 0x11223344.

session:session.ctx+hex:11223344

Autorizaciones de PCR

Puede satisfacer una política de PCR utilizando el prefijo “pcr:” y el minilenguaje de PCR. El minilenguaje de PCR es el siguiente: <pcr-spec>=<archivo-pcr-crudo>

La especificación de PCR está documentada en la sección “Especificadores de bancos de PCR”.

El archivo-pcr-crudo es un argumento opcional que contiene la salida de los contenidos de PCR crudos tal como los devuelve tpm2_pcrread(1).

Especificadores de bancos de PCR

Ejemplos

Para satisfacer una política de PCR de sha256 en los bancos 0, 1, 2 y 3 use un especificador de:

pcr:sha256:0,1,2,3

especificando AUTH.

Especificadores Complejos

Los objetos, cuando se especifican para su creación por el TPM, tienen numerosos algoritmos para poblar en los datos públicos. Cosas como el tipo, el esquema y los detalles asimétricos, el tamaño de la clave, etc. A continuación se muestra el formato general para especificar estos datos: <tipo>:<esquema>:<detalles-simétricos>

Especificadores de Tipo

Esta parte del especificador de algoritmo complejo es obligatoria. El resto de los detalles del esquema y simétricos se establecerán por defecto según el tipo especificado y el tipo del objeto que se está creando.

•
aes - AES predeterminado: aes128
•
aes128<modo> - AES de 128 bits con modo opcional (ctr|ofb|cbc|cfb|ecb). Si no se especifica el modo, se establece por defecto en null.
•
aes192<modo> - Igual que aes128<modo>, excepto por un tamaño de clave de 192 bits.
•
aes256<modo> - Igual que aes128<modo>, excepto por un tamaño de clave de 256 bits.
•
sm4 - SM4 predeterminado: sm4128
•
sm4128 o sm4_128 <modo> - SM4 de 128 bits con modo opcional (ctr|ofb|cbc|cfb|ecb). Si no se especifica el modo, se establece por defecto en null.
•
ecc - Curva Elíptica, por defecto es ecc256.
•
ecc192 o ecc_nist_p192 - Curva NIST ECC de 192 bits
•
ecc224 o ecc_nist_p224 - Curva NIST ECC de 224 bits
•
ecc256 o ecc_nist_p256 - Curva NIST ECC de 256 bits
•
ecc384 o ecc_nist_p384 - Curva NIST ECC de 384 bits
•
ecc521 o ecc_nist_p521 - Curva NIST ECC de 521 bits
•
ecc_sm2 o ecc_sm2_p256 - Curva SM2 de 256 bits
•
rsa - RSA predeterminado: rsa2048
•
rsa1024 - RSA con tamaño de clave de 1024 bits.
•
rsa2048 - RSA con tamaño de clave de 2048 bits.
•
rsa3072 - RSA con tamaño de clave de 3072 bits.
•
rsa4096 - RSA con tamaño de clave de 4096 bits.

Especificadores de Esquema

A continuación, hay un campo opcional, se puede omitir.

Los esquemas son generalmente Esquemas de Firma o Cifrado Asimétrico. La mayoría de los esquemas de firma toman un algoritmo hash directamente después del esquema de firma. Si falta el algoritmo hash, se establece por defecto en sha256. Algunos no toman argumentos y otros toman múltiples argumentos.

Especificadores de Esquema Opcional de Hash

Especificadores de Esquema con Múltiples Opciones

Este especificador de esquema va seguido de un recuento (tamaño máximo UINT16) y luego seguido de un guion (-) y un algoritmo hash válido. * ecdaa Por ejemplo, ecdaa4-sha256. Si no se especifica el recuento, se establece por defecto en 4.

Especificadores de Esquema Sin Opciones

Este especificador de esquema NO toma argumentos. * rsaes

Especificadores de Detalles Simétricos

Este campo es opcional y se establece por defecto según el tipo de objeto que se está creando y sus atributos. En general, cualquier especificador Simétrico válido de la lista de Especificadores de Tipo debería funcionar. Si no se especifica, los detalles simétricos de los objetos asimétricos se establecen por defecto en aes128cfb.

Ejemplos

Crear una clave rsa2048 con un esquema de cifrado asimétrico rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Crear una clave ecc256 con un esquema de firma ecdaa con un recuento de 4 y hash sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algoritmos criptográficos ALGORITMO.

DESCRIPTION

The tpm2_createek and tpm2_createak utilities are used to create primary, endorsement and attestation keys. These keys are typically created under the primary or endorsement hierarchy.

tpm2_createek generates a primary key that is unique to the platform. This key is often referred to as the Endorsement Key (EK) and is usually used for platform identification and attestation.

tpm2_createak generates an Attestation Key (AK). AKs are used to attest to the platform's state. They are typically created under an EK or a primary seed.

The tpm2_createpolicy* utilities are used to create TPM policies. Policies are sequences of commands that must be successfully executed by the TPM to satisfy an authorization policy. These commands are typically used with functions like tpm2_policyauthorize, tpm2_policydupin, tpm2_policysecret, etc.

Context Object Format

The context object is a data structure that contains TPM objects, such as keys or policy sessions. The context object is serialized to a file and can be loaded back into the TPM. The context object format is specified using the -f, --format option. The available formats are:

pki: PKI format.
pem: PEM format.
pkcs1: PKCS#1 format.
pkcs8: PKCS#8 format.
sec: Security format.
any: Let the tool decide the best format.

Authorization Formatting

The authorization value can be specified in several formats. The default format is a string password. The available formats are:

string: A plain text password.
hex: A hexadecimal string.
file: A file containing the password.

Algorithm Specifiers

The algorithm specifier can be specified in several formats. The default is `any`. The available formats are:

rsa: RSA algorithm.
ecc: Elliptic Curve Cryptography algorithm.
any: Let the tool decide the best algorithm.

Signature Format Specifiers

The signature format specifier can be specified in several formats. The default is `any`. The available formats are:

pkcs1: PKCS#1 signature format.
ems2: EMSA2 signature format.
any: Let the tool decide the best format.

TCTI Configuration

The TCTI or “Transmission Interface” is the communication mechanism with the TPM. TCTIs can be changed for communication with TPMs across different mediums.

To control the TCTI, the tools respect:

1.
The command line option -T or --tcti
2.
The environment variable: TPM2TOOLS_TCTI.

Note: The command line option always overrides the environment variable.

The current known TCTIs are:

tabrmd - The resource manager, called tabrmd. Note that tabrmd and abrmd as a tcti name are synonymous.
mssim - Typically used for communicating to the TPM software simulator.
device - Used when talking directly to a TPM device file.
none - Do not initalize a connection with the TPM. Some tools allow for off-tpm options and thus support not using a TCTI. Tools that do not support it will error when attempted to be used without a TCTI connection. Does not support ANY options and MUST BE presented as the exact text of “none”.

The arguments to either the command line option or the environment variable are in the form:

<tcti-name>:<tcti-option-config>

Specifying an empty string for either the <tcti-name> or <tcti-option-config> results in the default being used for that portion respectively.

TCTI Defaults

When a TCTI is not specified, the default TCTI is searched for using dlopen(3) semantics. The tools will search for tabrmd, device and mssim TCTIs IN THAT ORDER and USE THE FIRST ONE FOUND. You can query what TCTI will be chosen as the default by using the -v option to print the version information. The “default-tcti” key-value pair will indicate which of the aforementioned TCTIs is the default.

Custom TCTIs

Any TCTI that implements the dynamic TCTI interface can be loaded. The tools internally use dlopen(3), and the raw tcti-name value is used for the lookup. Thus, this could be a path to the shared library, or a library name as understood by dlopen(3) semantics.

TCTI OPTIONS

This collection of options are used to configure the various known TCTI modules available:

device: For the device TCTI, the TPM character device file for use by the device TCTI can be specified. The default is /dev/tpm0.

Example: -T device:/dev/tpm0 or export TPM2TOOLS_TCTI=“device:/dev/tpm0”

mssim: For the mssim TCTI, the domain name or IP address and port number used by the simulator can be specified. The default are 127.0.0.1 and 2321.

Example: -T mssim:host=localhost,port=2321 or export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

abrmd: For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,' character. Each key and value string are separated by a `=' character.
TCTI abrmd supports two keys:
1.
`bus_name' : The name of the tabrmd service on the bus (a string).
2.
`bus_type' : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

\--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules.
