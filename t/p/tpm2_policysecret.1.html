tpm2_policysecret(1) Manual de Comandos Generales tpm2_policysecret(1)

NOMBRE

tpm2_policysecret(1) - Vincula la autorización de un objeto a la de un objeto existente.

SINOPSIS

tpm2_policysecret [OPCIONES] [ARGUMENTO]

DESCRIPCIÓN

tpm2_policysecret(1) - Vincula la autorización de un objeto a la de un objeto existente sin necesidad de exponer el secreto existente hasta el momento de uso del objeto.

OPCIONES

•
-c, --object-context=OBJETO:

Un especificador de objeto de contexto de un objeto transitorio/permanente/persistente. Puede ser una ruta de archivo de un blob de contexto de objeto o un identificador de handle cargado/persistente/permanente. Consulte la sección "Formato del Objeto de Contexto". Como argumento, toma el valor de autorización del objeto TPM asociado, un guion (-) puede usarse para leer el valor de autorización desde stdin. El argumento sigue los "estándares de formato de autorización", consulte la sección "Formato de Autorización".

•
-S, --session=ARCHIVO:

Archivo de sesión de política generado mediante la opción -S de tpm2_startauthsession(1).

•
-L, --policy=ARCHIVO:

Archivo donde se guardará el digest de la política.

•
-t, --expiration=NUMERO_NATURAL:

Establece el tiempo de expiración de la política en segundos. En ausencia de nonceTPM, el tiempo de expiración es el valor de tiempo de espera de la política. Si el valor de expiración es 0, la política no tiene límite de tiempo para la autorización.

•
--ticket=ARCHIVO:

Archivo donde se registrará la estructura del ticket de autorización.

•
--timeout=ARCHIVO:

Ruta del archivo donde se registrará la estructura de tiempo de espera devuelta.

•
-x, --nonce-tpm:

Habilita la comparación del nonceTPM de la sesión actual para asegurar que la validez de la autorización de la política se limita a la sesión actual.

•
-q, --qualification=CADENA_HEX_O_ARCHIVO:

Opcional, los datos de calificación de la política que el firmante puede optar por incluir en la firma. Puede ser una cadena hexadecimal o una ruta.

•
--cphash=ARCHIVO

Ruta del archivo donde se registrará el hash de los parámetros del comando. Esto se denomina comúnmente cpHash. NOTA: Cuando se selecciona esta opción, la herramienta no ejecutará realmente el comando, simplemente devolverá un cpHash para ser utilizado en una auditoría o en un policycphash.

•
ARGUMENTO el argumento de la línea de comandos especifica la AUTH que se establecerá para el objeto especificado con -c.

Referencias

Formato del Objeto de Contexto

El tipo de un objeto de contexto, ya sea un handle o un nombre de archivo, se determina según la siguiente lógica *en orden*:

•
Si el argumento es una ruta de archivo, entonces el archivo se carga como un objeto transitorio de TPM restaurado.
•
Si el argumento es una coincidencia de *prefijo* en uno de:
•
owner: la jerarquía de propietario
•
platform: la jerarquía de plataforma
•
endorsement: la jerarquía de respaldo
•
lockout: el objeto persistente de control de bloqueo
•
Si el argumento puede cargarse como un número, se tratará como un handle, por ejemplo, 0x81010013 y se usará directamente._OBJETO_.

Formato de Autorización

La autorización para usar un objeto en TPM2.0 puede venir en 3 formas diferentes: 1. Contraseña 2. HMAC 3. Sesiones

NOTA: "Las autorizaciones por defecto son la CONTRASEÑA VACÍA cuando no se especifican".

Contraseñas

Las contraseñas se interpretan en las siguientes formas a continuación utilizando prefijos.

Nota: Por defecto, las contraseñas se asumen en formato de cadena cuando no tienen prefijo.

Cadena

Una contraseña en cadena, especificada por el prefijo "str:" o su ausencia (cadena sin prefijo) no se interpreta y se utiliza directamente para la autorización.

Ejemplos

foobar
str:foobar

Cadena hexadecimal

Una contraseña en cadena hexadecimal, especificada por el prefijo "hex:", se convierte de forma hexadecimal a forma de array de bytes, permitiendo así contraseñas con caracteres no imprimibles y/o poco amigables para la terminal.

Ejemplo

hex:1122334455667788

Archivo

Una contraseña basada en archivo, especificada por el prefijo "file:", debe ser la ruta de un archivo que contenga la contraseña a leer por la herramienta o un "-" para usar stdin. Almacenar contraseñas en archivos evita la fuga de información, las contraseñas pasadas como opciones pueden ser leídas de la lista de procesos o de características comunes del historial del shell.

Ejemplos

# para usar stdin y ser preguntado
file:-
# para usar un archivo desde una ruta
file:ruta/al/archivo/de/contraseña
# para hacer eco de una contraseña vía stdin:
echo foobar | tpm2_tool -p file:-
# para usar una cadena aquí de bash vía stdin:
tpm2_tool -p file:- <<< foobar

Sesiones

Al usar una sesión de política para autorizar el uso de un objeto, prefije el argumento de la opción con la palabra clave session. Luego, indique una ruta a un archivo de sesión que se creó con tpm2_startauthsession(1). Opcionalmente, si la sesión requiere un valor de autorización para ser enviado con el handle de la sesión (por ejemplo, contraseña de política), agregue un "+" y una cadena como se describe en la sección Contraseñas.

Ejemplos

Para usar un archivo de contexto de sesión llamado session.ctx.

session:session.ctx

Para usar un archivo de contexto de sesión llamado session.ctx Y enviar el valor de autorización mypassword.

session:session.ctx+mypassword

Para usar un archivo de contexto de sesión llamado session.ctx Y enviar el valor de autorización HEX 0x11223344.

session:session.ctx+hex:11223344

Autorizaciones PCR

Puede satisfacer una política PCR usando el prefijo "pcr:" y el minilenguaje PCR. El minilenguaje PCR es el siguiente: <especificador-pcr>=<archivo-pcr-crudo>

El especificador PCR se documenta en la sección "Especificadores de bancos PCR".

El archivo-pcr-crudo es un argumento opcional que contiene la salida del contenido crudo del PCR.

NAME

\n

\ntpm2_policycp - policy command to satisfy the
\ntpm2_policycp(1) command

\n
\n
\n

SYNOPSIS

\n

tpm2_policycp [-h|--help ] [-v|--version ] [-T|--tcti tcti-name] [-T|--tcti <tcti-name>:<tcti-option>] [-Q|--quiet ] [-S|--session session] [-P|--policy-auth auth] [-L|--policy-file policy] [-l|--policy-log log] [-c|--parent-ctx context] [-o|--ops ops] [-u|--update policy-digest]

\n
\n

DESCRIPTION

\n

The tpm2_policycp command is used to create a policy digest that can be used to represent\na policy that is satisfied when a specific PCR value is calculated. The PCR value is specified\nby the PCR bank specifier argument.

\n

This policy digest can be used for various commands, such as:

\n
    \n
  • tpm2_create: To create objects that have this policy attached.
    • \n
  • tpm2_seal: To seal data with this policy attached.
    • \n
  • tpm2_policyauthorize: To specify this policy as a prerequisite for a policy authorization.
    • \n
\n

The PCR bank specifier is a string that describes the PCR bank and the PCRs within that bank.

\n
\n

PCR BANK SPECIFIERS

\n

The PCR bank specifier has the following format:

\n

pcr:<hash-alg>:<pcr-banks>

\n

Where:

\n
    \n
  • <hash-alg> is the hash algorithm used for the PCR bank (e.g., sha1, sha256, sha384, sha512, sm3_256).
    • \n
  • <pcr-banks> is a comma-separated list of PCR indexes within the specified hash algorithm bank.
    • \n
\n

For example, to specify PCRs 0, 1, 2, and 3 of the SHA256 bank, you would use:

\n

pcr:sha256:0,1,2,3

\n

This is equivalent to the PCR values returned by\ntpm2_pcrread(1).

\n

PCR bank specifiers

\n
\n
\n

Examples

\n

To satisfy a PCR policy of sha256 on banks 0, 1, 2 and 3 use a\nspecifier of:

\n
\n
\n
\n
pcr:sha256:0,1,2,3\n

TCTI Configuration

\n

The TCTI or “Transmission Interface” is the\ncommunication mechanism with the TPM. TCTIs can be changed for communication\nwith TPMs across different mediums.

\n

To control the TCTI, the tools respect:

\n
\n
1.
\n
The command line option -T or --tcti
\n
2.
\n
The environment variable: TPM2TOOLS_TCTI.
\n
\n

Note: The command line option always overrides the\nenvironment variable.

\n

The current known TCTIs are:

\n
\n
•
\n
tabrmd - The resource manager, called\ntabrmd. Note that tabrmd and abrmd as a tcti name are synonymous.
\n
•
\n
mssim - Typically used for communicating to the TPM software\nsimulator.
\n
•
\n
device - Used when talking directly to a TPM device file.
\n
•
\n
none - Do not initalize a connection with the TPM. Some tools allow for\noff-tpm options and thus support not using a TCTI. Tools that do not\nsupport it will error when attempted to be used without a TCTI connection.\nDoes not support ANY options and MUST BE presented as the\nexact text of “none”.
\n
\n

The arguments to either the command line option or the environment\nvariable are in the form:

\n

<tcti-name>:<tcti-option-config>

\n

Specifying an empty string for either the\n<tcti-name> or\n<tcti-option-config> results in the default\nbeing used for that portion respectively.

\n
\n

TCTI Defaults

\n

When a TCTI is not specified, the default TCTI is searched for\nusing dlopen(3) semantics. The tools will search for tabrmd,\ndevice and mssim TCTIs IN THAT ORDER and USE THE\nFIRST ONE FOUND. You can query what TCTI will be chosen as the\ndefault by using the -v option to print the version information. The\n“default-tcti” key-value pair will indicate which of the\naforementioned TCTIs is the default.

\n
\n
\n

Custom TCTIs

\n

Any TCTI that implements the dynamic TCTI interface can be loaded.\nThe tools internally use dlopen(3), and the raw tcti-name\nvalue is used for the lookup. Thus, this could be a path to the shared\nlibrary, or a library name as understood by dlopen(3) semantics.

\n
\n
\n

EXAMPLES

\n

Associate auth value of a sealing object to the owner hierarchy\npassword. * Start a trial auth session and run tpm2_policysecret(1)\nto create policy that can only be satisfied if owner hierarchy auth value is\nsupplied. * Start a real policy session and provide the owner hierarchy auth\nvalue. * Provide the session input where in the policysecret for owner\nhierarchy auth was satisfied to the unseal tool. * If the policy was\nsatisfied unsealing should succeed.

\n

\n
\n
\n
