NOMBRE

tpm2_ecdhkeygen(1) - Crea una clave efímera y la utiliza para generar el valor secreto compartido utilizando los parámetros de una clave pública ECC.

SINOPSIS

tpm2_ecdhkeygen [OPCIONES]

DESCRIPCIÓN

tpm2_ecdhkeygen(1) - Crea una clave efímera y la utiliza para generar el valor secreto compartido utilizando los parámetros de una clave pública ECC.

OPCIONES

•
-c, --context=ARCHIVO:

Objeto de contexto que apunta a la clave pública ECC. Puede ser un archivo o un número de manejador. Ver la sección "Formato del Objeto de Contexto".

•
-u, --public=ARCHIVO:

Punto Q de la ECC de salida.

•
-o, --output=ARCHIVO

Especifica la ruta del archivo para guardar el secreto ECDH calculado o el punto Z.

•
--cphash=ARCHIVO

Ruta del archivo para registrar el hash de los parámetros del comando. Esto se denomina comúnmente cpHash. NOTA: Cuando se selecciona esta opción, la herramienta no ejecutará realmente el comando, simplemente devolverá un cpHash.

Especificadores complejos

Los objetos, cuando se especifican para su creación por el TPM, tienen numerosos algoritmos para poblar en los datos públicos. Cosas como el tipo, el esquema y los detalles asimétricos, el tamaño de la clave, etc. A continuación se muestra el formato general para especificar estos datos: <tipo>:<esquema>:<detalles-simétricos>

Especificadores de tipo

Esta parte del especificador de algoritmo complejo es obligatoria. El esquema restante y los detalles simétricos se establecerán por defecto basándose en el tipo especificado y el tipo del objeto que se está creando.

•
aes - AES por defecto: aes128
•
aes128<modo> - AES de 128 bits con modo opcional (ctr|ofb|cbc|cfb|ecb). Si no se especifica el modo, el valor predeterminado es null.
•
aes192<modo> - Igual que aes128<modo>, excepto por un tamaño de clave de 192 bits.
•
aes256<modo> - Igual que aes128<modo>, excepto por un tamaño de clave de 256 bits.
•
sm4 - SM4 por defecto: sm4128
•
sm4128 o sm4_128 <modo> - SM4 de 128 bits con modo opcional (ctr|ofb|cbc|cfb|ecb). Si no se especifica el modo, el valor predeterminado es null.
•
ecc - Curva elíptica, por defecto es ecc256.
•
ecc192 o ecc_nist_p192 - Curva NIST ECC de 192 bits
•
ecc224 o ecc_nist_p224 - Curva NIST ECC de 224 bits
•
ecc256 o ecc_nist_p256 - Curva NIST ECC de 256 bits
•
ecc384 o ecc_nist_p384 - Curva NIST ECC de 384 bits
•
ecc521 o ecc_nist_p521 - Curva NIST ECC de 521 bits
•
ecc_sm2 o ecc_sm2_p256 - Curva SM2 de 256 bits
•
rsa - RSA por defecto: rsa2048
•
rsa1024 - RSA con tamaño de clave de 1024 bits.
•
rsa2048 - RSA con tamaño de clave de 2048 bits.
•
rsa3072 - RSA con tamaño de clave de 3072 bits.
•
rsa4096 - RSA con tamaño de clave de 4096 bits.

Especificadores de esquema

A continuación, hay un campo opcional, se puede omitir.

Los esquemas suelen ser Esquemas de Firma o Esquemas de Cifrado Asimétrico. La mayoría de los esquemas de firma toman un algoritmo de hash directamente después del esquema de firma. Si falta el algoritmo de hash, se establece por defecto en sha256. Algunos no toman argumentos y otros toman múltiples argumentos.

Por defecto, el esquema es null.

EJEMPLO

Para realizar un intercambio de claves ECDH con una clave pública ECC:

tpm2_ecdhkeygen -c o . -u o u.bin -o o secret.bin

Aquí:

  • -c o . lee el objeto de contexto de la entrada estándar.
  • -u o u.bin escribe la clave pública ECC efímera generada en el archivo u.bin.
  • -o o secret.bin escribe el secreto ECDH compartido calculado en el archivo secret.bin.

Para realizar un intercambio de claves ECDH con un par de claves almacenado en el TPM:

tpm2_ecdhkeygen -c <solicitud> -u o u.bin -o o secret.bin

Donde <solicitud> es un archivo que contiene un objeto de contexto que apunta a la clave pública del par de claves.

NAME

tpm2_create - create primary or object

SYNOPSIS

tpm2_create [-h|--help=[man|no-man]] [-v|--version] [-V|--verbose] [-Q|--quiet] [-Z|--enable-errata] [-R|--autoflush] [-T|--tcti=<tcti-name>[:<tcti-option-config>]] [-c <context-file>] [-f] [-g <hash-algorithm>] [-l <policy-digest>] [-L <policy-file>] [-P <password>] [-p <password>] [-r <private-file>] [-u <public-file>] [-U <policy-file>] [-a <attributes>] [-I <policy-file>] [-d <data-file>] [-G <symmetric-details-specifiers>] [-i <input-file>]

DESCRIPTION

The tpm2_create command is used to create a primary key or an object key (e.g. endorsement key, storage key, Attestation Key) under a specified parent key context. It will output the created objects public and private key data to separate files.

The primary key will be created when the parent handle is the TPM_RH_OWNER, TPM_RH_ENDORSEMENT, or TPM_RH_PLATFORM.

For the creation of a primary key, the “creation data” field will be populated by the algorithm digest of the created key's parent. The “parent public key” will be an empty structure.

For the creation of an object key, the “creation data” field will be populated by the algorithm digest of the parent. The “parent public key” field will be populated with the parent key’s public key structure.

The object created can be persisted to disk by providing values for the -u and -r flags. The object can be loaded back into the TPM by using the tpm2_load command.

Context Management

The TPM supports the concept of context management. It allows for the context of a TPM object, such as a key, to be saved to disk and then later reloaded.

In the case of tpm2_create, the parent object specified by the -c flag is loaded from a file. This file may represent a primary key, or a key previously created and saved via tpm2_create and tpm2_load.

If the -R or --autoflush option is used, the transient object representing the parent key will be flushed from the TPM once the command has completed. If the parent context is loaded from a file, the file will be deleted.

Key Creation and Policies

When creating an object key, policies can be attached to the object which can restrict its usage. The flags available are:

-l, --policy-digest=<policy-digest>
Specifies the policy digest for the object. The policy digest is calculated by applying a hash algorithm to a policy tree. The hash algorithm is specified using the -g flag.
-L, --policy-file=<policy-file>
Specifies a policy tree file for the object. The policy tree is used to generate the policy digest. This option is used in conjunction with -g.
-U, --policy-auth-file=<policy-file>
Specifies a policy tree file for the object authorization value. The policy tree is used to generate the policy digest. This option is used in conjunction with -g.
-I, --policy-ticket-file=<policy-file>
Specifies a policy tree file for the object's ticket. The policy tree is used to generate the policy digest. This option is used in conjunction with -g.
-d, --creation-data-file=<data-file>
Specifies a file containing the creation data for the object. This is used to ensure that the object was created with specific data, typically used to prevent replay attacks.

OPTIONS

-c, --parent-context=<context-file>
The parent object to create the new object under. This can be a primary key or any other object. The context is loaded from the specified file.
-f, --force
Overwrite the output files if they already exist.
-g, --hash-algorithm=<hash-algorithm>
The hash algorithm to use for the creation data and policy digest. The default is sha1.
-l, --policy-digest=<policy-digest>
The policy digest to attach to the object. This is a hex string of the policy digest.
-L, --policy-file=<policy-file>
The file containing the policy digest digest structure.
-P, --parent-password=<password>
The password for the parent object. This is used to authorize the creation of the new object.
-p, --object-password=<password>
The password for the newly created object. This password will be required to sign or decrypt with the object.
-r, --private-file=<private-file>
The file to write the private key data to.
-u, --public-file=<public-file>
The file to write the public key data to.
-U, --policy-auth-file=<policy-file>
The file containing the policy digest digest structure for the parent authorization value.
-a, --attributes=<attributes>
The attributes for the created object. These attributes control the usage and properties of the object. Attributes are specified as a list of keywords separated by colons. For example: fixed,persistent,encrypted.
-I, --policy-ticket-file=<policy-file>
The file containing the policy digest digest structure for the parent ticket value.
-d, --creation-data-file=<data-file>
The file containing the creation data for the object. This data is used to ensure the integrity of the object's creation process.
-G, --symmetric-details-specifiers=<symmetric-details-specifiers>
Specifies the symmetric encryption details for the object. This is used for object types that utilize symmetric encryption, such as those created with certain key types.
-i, --input-file=<input-file>
The file containing the data to be encrypted or signed by the object. This is typically used when creating an object for encryption or signing purposes.

Algorithm Specifiers

The -G option, when used to specify asymmetric key details, can take a variety of specifiers. These specifiers are used to define the type and properties of the asymmetric key being generated. The general format is <key-type>[:<usage>].

Key Types:

  • rsa1024, rsa2048, rsa3072, rsa4096: RSA keys of specified bit lengths.
  • ecc256, ecc384, ecc521: ECC keys using NIST curves of specified bit lengths.

Usage Specifiers (optional, appended after a colon):

  • rsaes: RSA Key Encapsulation Mechanism (KEM) for encryption.
  • rsassa:sha1, rsassa:sha256, rsassa:sha384, rsassa:sha512: RSA Signature Scheme with Appendix (SSA) for signing, specifying the hash algorithm.
  • ecdsa:sha1, ecdsa:sha256, ecdsa:sha384, ecdsa:sha512: ECDSA signature scheme, specifying the hash algorithm.
  • ecdaa:<count>-<hash>: Elliptic Curve Directly Accessible Authentication (DAA) signature scheme. Requires a count (e.g., 4) and a hash algorithm (e.g., sha256). Example: ecdaa4-sha256.
  • hmac: For HMAC keys.
  • tpm2b:maxBuffer: For keys that can store TPM2B_MAX_BUFFER size data.

Note: The hash algorithms supported depend on the TPM version and configuration.

Symmetric Details Specifiers

This field is optional, and defaults based on the type of object being created and it’s attributes. Generally, any valid Symmetric specifier from the Type Specifiers list should work. If not specified, an asymmetric objects symmetric details defaults to aes128cfb.

Examples

Create an rsa2048 key with an rsaes asymmetric encryption scheme

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Create an ecc256 key with an ecdaa signing scheme with a count of 4 and sha384 hash

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv cryptographic algorithms ALGORITHM.

TCTI Configuration

The TCTI or “Transmission Interface” is the communication mechanism with the TPM. TCTIs can be changed for communication with TPMs across different mediums.

To control the TCTI, the tools respect:

1.
The command line option -T or --tcti
2.
The environment variable: TPM2TOOLS_TCTI.

Note: The command line option always overrides the environment variable.

The current known TCTIs are:

•
tabrmd - The resource manager, called tabrmd. Note that tabrmd and abrmd as a tcti name are synonymous.
•
mssim - Typically used for communicating to the TPM software simulator.
•
device - Used when talking directly to a TPM device file.
•
none - Do not initalize a connection with the TPM. Some tools allow for off-tpm options and thus support not using a TCTI. Tools that do not support it will error when attempted to be used without a TCTI connection. Does not support ANY options and MUST BE presented as the exact text of “none”.

The arguments to either the command line option or the environment variable are in the form:

<tcti-name>:<tcti-option-config>

Specifying an empty string for either the <tcti-name> or <tcti-option-config> results in the default being used for that portion respectively.

TCTI Defaults

When a TCTI is not specified, the default TCTI is searched for using dlopen(3) semantics. The tools will search for tabrmd, device and mssim TCTIs IN THAT ORDER and USE THE FIRST ONE FOUND. You can query what TCTI will be chosen as the default by using the -v option to print the version information. The “default-tcti” key-value pair will indicate which of the aforementioned TCTIs is the default.

Custom TCTIs

Any TCTI that implements the dynamic TCTI interface can be loaded. The tools internally use dlopen(3), and the raw tcti-name value is used for the lookup. Thus, this could be a path to the shared library, or a library name as understood by dlopen(3) semantics.

TCTI OPTIONS

This collection of options are used to configure the various known TCTI modules available:

•
device: For the device TCTI, the TPM character device file for use by the device TCTI can be specified. The default is /dev/tpm0.

Example: -T device:/dev/tpm0 or export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: For the mssim TCTI, the domain name or IP address and port number used by the simulator can be specified. The default are 127.0.0.1 and 2321.

Example: -T mssim:host=localhost,port=2321 or export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,' character. Each key and value string are separated by a `=' character.
•
TCTI abrmd supports two keys:
1.
`bus_name' : The name of the tabrmd service on the bus (a string).
2.
`bus_type' : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

\--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules.
