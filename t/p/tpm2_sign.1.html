tpm2_sign(1) Manual de Comandos Generales tpm2_sign(1)

NOMBRE

tpm2_sign(1) - Firma un hash o mensaje usando el TPM.

SINOPSIS

tpm2_sign [OPCIONES] [ARGUMENTO]

DESCRIPCIÓN

tpm2_sign(1) - Genera la firma de un mensaje especificado o su digest usando la clave de firma simétrica o asimétrica especificada.

Al firmar un mensaje, la utilidad tpm2_sign primero calcula el digest del mensaje de forma similar al comando tpm2_hash. También genera un ticket de validación bajo las jerarquías TPM2_RH_NULL o TPM2_RH_OWNER, respectivamente, para claves de firma sin restricciones o restringidas.

Si bien firmar mensajes es una provisión en esta herramienta, se recomienda usar primero la herramienta tpm2_hash y pasar el digest y el ticket de validación.

NOTA: Si la clave de firma es una clave de firma restringida, entonces la validación y el digest deben proporcionarse a través de la entrada -t. El ticket indica que el TPM realizó el hash del mensaje.

OPCIONES

•
-c, --key-context=OBJETO:

Objeto de contexto que apunta a la clave utilizada para firmar. Ya sea un archivo o un número de manejador. Consulte la sección "Formato del Objeto de Contexto".

•
-p, --auth_AUTH_:

Valor de autorización opcional para usar la clave especificada con -c. Los valores de autorización deben seguir los "estándares de formato de autorización", consulte la sección "Formato de Autorización".

•
-g, --hash-algorithm=ALGORITMO:

El algoritmo de hash utilizado para digerir el mensaje. Los algoritmos deben seguir los "estándares de formato", consulte la sección "Especificadores de Algoritmos". Consulte también la sección "Algoritmos de Hash Soportados" para obtener una lista de los algoritmos de hash soportados.

•
-s, --scheme=ALGORITMO:

El esquema de firma utilizado para firmar el mensaje. Opcional.

Los esquemas de firma deben seguir los "estándares de formato", consulte la sección "Especificadores de Algoritmos".

Si se especifica, el esquema de firma debe coincidir con el tipo de clave. Si se deja sin especificar, se utilizará un esquema de firma predeterminado para el tipo de clave.

•
-d, --digest:

Indica que ARCHIVO es un archivo que contiene el digest del mensaje. Cuando se especifican esta opción y -t, se genera una advertencia y el ticket de validación (-t) se ignora. No puede usar esta opción para firmar un digest contra una clave de firma restringida.

•
-t, --ticket=ARCHIVO:

El archivo de ticket, que contiene la estructura de validación, opcional.

•
-o, --signature=ARCHIVO:

El archivo de firma, registra la estructura de firma.

•
-f, --format=FORMATO:

Selección del formato para el archivo de salida de la firma. Consulte la sección "Especificadores de Formato de Firma".

•
--cphash=ARCHIVO

Ruta del archivo para registrar el hash de los parámetros del comando. Esto se denomina comúnmente cpHash. NOTA: Cuando se selecciona esta opción, la herramienta no ejecutará el comando, simplemente devolverá un cpHash.

•
--commit-index=NUMERO_NATURAL

El valor del contador de commit para determinar el índice de la clave a utilizar en un esquema de firma ECDAA. El valor del contador por defecto es 0.

•
ARGUMENTO El argumento de línea de comandos especifica los datos del archivo para firmar.

Referencias

Formato del Objeto de Contexto

El tipo de un objeto de contexto, ya sea un manejador o un nombre de archivo, se determina según la siguiente lógica *en orden*:

•
Si el argumento es una ruta de archivo, entonces el archivo se carga como un objeto transitorio TPM restaurado.
•
Si el argumento es una coincidencia de *prefijo* en uno de:
•
owner: la jerarquía del propietario
•
platform: la jerarquía de la plataforma
•
endorsement: la jerarquía de aprobación
•
lockout: el objeto persistente de control de bloqueo
•
Si el argumento se puede cargar como un número, se tratará como un manejador, por ejemplo, 0x81010013 y se usará directamente.*OBJETO*.

Formato de Autorización

La autorización para el uso de un objeto en TPM2.0 puede venir en 3 formas diferentes: 1. Contraseña 2. HMAC 3. Sesiones

NOTA: "Las autorizaciones son por defecto **VACÍAS** cuando no se especifican".

Contraseñas

Las contraseñas se interpretan en las siguientes formas usando identificadores de prefijo.

Nota: Por defecto, las contraseñas se asumen en formato de cadena cuando no tienen prefijo.

Cadena

Una contraseña de cadena, especificada con el prefijo "str:" o su ausencia (cadena sin prefijo) no se interpreta y se usa directamente para la autorización.

Ejemplos

foobar
str:foobar

Cadena hexadecimal

Una contraseña en formato de cadena hexadecimal, especificada con el prefijo "hex:", se convierte de un formato hexadecimal a un formato de array de bytes, lo que permite contraseñas con caracteres no imprimibles y/o no amigables para la terminal.

Ejemplo

hex:1122334455667788

Archivo

Una contraseña basada en archivo, especificada con el prefijo "file:" debe ser la ruta de un archivo que contenga la contraseña a leer por la herramienta o un "-" para usar stdin. Almacenar contraseñas en archivos evita la fuga de información, las contraseñas pasadas como opciones pueden ser leídas de la lista de procesos o de las funciones comunes del historial del shell.

Ejemplos

# para usar stdin y ser preguntado
file:-
# para usar un archivo desde una ruta
file:ruta/a/archivo/contraseña
# para enviar una contraseña vía stdin:
echo foobar | tpm2_tool -p file:-
# para usar una cadena aquí de bash vía stdin:
tpm2_tool -p file:- <<< foobar

Sesiones

Al usar una sesión de política para autorizar el uso de un objeto, prefije el argumento de la opción con la palabra clave session. Luego, indique una ruta a un archivo de sesión que fue creado con tpm2_startauthsession(1). Opcionalmente, si la sesión requiere un valor de autorización que se envíe con el manejador de sesión (por ejemplo, contraseña de política), agregue un + y una cadena como se describe en la sección Contraseñas.

Ejemplos

Para usar un archivo de contexto de sesión llamado session.ctx.

session:session.ctx

Para usar un archivo de contexto de sesión llamado session.ctx **Y**

Authorization Policies

Authorization policies are a way to specify which methods are allowed to authorize the TPM, or a specific object, or both. Authorization policies are a comma separated list of authorization policy specifiers.

Password authorization

To use a password authorization policy, use the password: prefix. This requires the user to provide the password for the object or TPM.

To use a password authorization policy using a password file called mypassword.txt:

password:mypassword.txt

To use a password authorization policy using a password string of mypassword:

password:mypassword

Session context file authorization

To use a session context file, use the session: prefix. This will load the session context from the specified file.

To use a session context file called session.ctx and send the password authvalue mypassword.

session:session.ctx+mypassword

To use a session context file called session.ctx AND send the HEX authvalue 0x11223344.

session:session.ctx+hex:11223344

PCR Authorizations

You can satisfy a PCR policy using the “pcr:” prefix and the PCR minilanguage. The PCR minilanguage is as follows: <pcr-spec>=<raw-pcr-file>

The PCR spec is documented in in the section “PCR bank specifiers”.

The raw-pcr-file is an optional argument that contains the output of the raw PCR contents as returned by tpm2_pcrread(1).

PCR bank specifiers

Examples

To satisfy a PCR policy of sha256 on banks 0, 1, 2 and 3 use a specifier of:

pcr:sha256:0,1,2,3

specifying AUTH.

Complex Specifiers

Objects, when specified for creation by the TPM, have numerous algorithms to populate in the public data. Things like type, scheme and asymmetric details, key size, etc. Below is the general format for specifying this data: <type>:<scheme>:<symmetric-details>

Type Specifiers

This portion of the complex algorithm specifier is required. The remaining scheme and symmetric details will default based on the type specified and the type of the object being created.

•
aes - Default AES: aes128
•
aes128<mode> - 128 bit AES with optional mode (ctr|ofb|cbc|cfb|ecb). If mode is not specified, defaults to null.
•
aes192<mode> - Same as aes128<mode>, except for a 192 bit key size.
•
aes256<mode> - Same as aes128<mode>, except for a 256 bit key size.
•
sm4 - Default SM4: sm4128
•
sm4128 or sm4_128 <mode> - 128 bit SM4 with optional mode (ctr|ofb|cbc|cfb|ecb). If mode is not specified, defaults to null.
•
ecc - Elliptical Curve, defaults to ecc256.
•
ecc192 or ecc_nist_p192 - 192 bit ECC NIST curve
•
ecc224 or ecc_nist_p224 - 224 bit ECC NIST curve
•
ecc256 or ecc_nist_p256 - 256 bit ECC NIST curve
•
ecc384 or ecc_nist_p384 - 384 bit ECC NIST curve
•
ecc521 or ecc_nist_p521 - 521 bit ECC NIST curve
•
ecc_sm2 or ecc_sm2_p256 - 256 bit SM2 curve
•
rsa - Default RSA: rsa2048
•
rsa1024 - RSA with 1024 bit keysize.
•
rsa2048 - RSA with 2048 bit keysize.
•
rsa3072 - RSA with 3072 bit keysize.
•
rsa4096 - RSA with 4096 bit keysize.

Scheme Specifiers

Next, is an optional field, it can be skipped.

Schemes are usually Signing Schemes or Asymmetric Encryption Schemes. Most signing schemes take a hash algorithm directly following the signing scheme. If the hash algorithm is missing, it defaults to sha256. Some take no arguments, and some take multiple arguments.

Hash Optional Scheme Specifiers

These scheme specifiers are followed by a dash and a valid hash algorithm, For example: oaep-sha256.

•
oaep
•
ecdh

rsassa

Multiple Option Scheme Specifiers

This scheme specifier is followed by a count (max size UINT16) then followed by a dash(-) and a valid hash algorithm. * ecdaa For example, ecdaa4-sha256. If no count is specified, it defaults to 4.

No Option Scheme Specifiers

This scheme specifier takes NO arguments. * rsaes

Symmetric Details Specifiers

This field is optional, and defaults based on the type of object being created and it’s attributes. Generally, any valid Symmetric specifier from the Type Specifiers list should work. If not specified, an asymmetric objects symmetric details defaults to aes128cfb.

Examples

Create an rsa2048 key with an rsaes asymmetric encryption scheme

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Create an ecc256 key with an ecdaa signing scheme with a count of 4 and sha384 hash

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv cryptographic algorithms ALGORITHM.
