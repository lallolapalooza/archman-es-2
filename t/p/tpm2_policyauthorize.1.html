tpm2_policyauthorize(1) Manual de Comandos Generales tpm2_policyauthorize(1)

NOMBRE

tpm2_policyauthorize(1) - Permite políticas mutables enlazándolas a una autoridad de firma.

SINOPSIS

tpm2_policyauthorize [OPCIONES]

DESCRIPCIÓN

tpm2_policyauthorize(1) - Este comando permite que las políticas cambien asociando la política a una autoridad de firma y permitiendo que el contenido de la política cambie.

1.
Si la sesión de entrada es una sesión de prueba, esta herramienta genera un resumen de política que asocia el nombre de la clave pública de una autoridad de firma con la política que se está autorizando.
2.
Si la sesión de entrada es una sesión de política real, tpm2_policyauthorize(1) busca un ticket de verificación del TPM para atestiguar que el TPM ha verificado la firma en el resumen de política antes de autorizar la política en el resumen de política.

OPCIONES

•
-L, --policy=ARCHIVO:

Archivo donde guardar el resumen de política.

•
-S, --session=ARCHIVO:

Archivo de sesión de política generado a través de la opción -S de tpm2_startauthsession(1).

•
-i, --input=ARCHIVO:

El resumen de política que debe ser autorizado.

•
-q, --qualification=ARCHIVO_O_HEX:

Los datos de calificación de política firmados junto con el resumen de política de entrada. Estos son datos únicos que el firmante puede optar por incluir en la firma y pueden ser una ruta o una cadena hexadecimal.

•
-n, --name=ARCHIVO:

Archivo que contiene el nombre de la clave pública de verificación. Esto vincula el resumen de política final con un firmante. Se puede obtener con tpm2_readpublic(1)

•
-t, --ticket=ARCHIVO:

Archivo de ticket para registrar la estructura de validación. Esto se genera con tpm2_verifysignature(1).

•
--cphash=ARCHIVO

Ruta del archivo para registrar el hash de los parámetros del comando. Esto se denomina comúnmente cpHash. NOTA: Cuando se selecciona esta opción, la herramienta no ejecutará el comando, simplemente devolverá un cpHash.

Configuración TCTI

El TCTI o "Interfaz de Transmisión" es el mecanismo de comunicación con el TPM. Los TCTI se pueden cambiar para comunicarse con TPMs a través de diferentes medios.

Para controlar el TCTI, las herramientas respetan:

1.
La opción de línea de comandos -T o --tcti
2.
La variable de entorno: TPM2TOOLS_TCTI.

Nota: La opción de línea de comandos siempre anula la variable de entorno.

Los TCTI conocidos actualmente son:

•
tabrmd - El gestor de recursos, llamado tabrmd. Tenga en cuenta que tabrmd y abrmd como nombre de tcti son sinónimos.
•
mssim - Típicamente utilizado para comunicarse con el simulador de software del TPM.
•
device - Se utiliza al hablar directamente con el archivo del dispositivo TPM.
•
none - No inicializar una conexión con el TPM. Algunas herramientas permiten opciones fuera del TPM y, por lo tanto, admiten no usar un TCTI. Las herramientas que no lo soportan generarán un error cuando se intenten usar sin una conexión TCTI. No admite *NINGUNA* opción y *DEBE* presentarse como el texto exacto de "none".

Los argumentos para la opción de línea de comandos o la variable de entorno tienen el formato:

<nombre-tcti>:<config-opciones-tcti>

Especificar una cadena vacía para <nombre-tcti> o <config-opciones-tcti> resulta en el uso del valor predeterminado para esa parte respectivamente.

Valores predeterminados de TCTI

Cuando no se especifica un TCTI, se busca el TCTI predeterminado utilizando la semántica de dlopen(3). Las herramientas buscarán los TCTI *tabrmd*, *device* y *mssim* **EN ESE ORDEN** y **USARÁN EL PRIMERO QUE ENCUENTREN**. Puede consultar qué TCTI se elegirá como predeterminado usando la opción -v para imprimir la información de la versión. El par clave-valor "default-tcti" indicará cuál de los TCTI mencionados es el predeterminado.

TCTIs personalizados

Cualquier TCTI que implemente la interfaz TCTI dinámica se puede cargar. Las herramientas utilizan internamente dlopen(3), y el valor bruto *tcti-name* se utiliza para la búsqueda. Por lo tanto, esto podría ser una ruta a la biblioteca compartida, o un nombre de biblioteca tal como lo entiende la semántica de dlopen(3).

OPCIONES TCTI

Esta colección de opciones se utilizan para configurar los diversos módulos TCTI conocidos disponibles:

•
device: Para el TCTI de dispositivo, se puede especificar el archivo de dispositivo de caracteres del TPM para que lo use el TCTI de dispositivo. El valor predeterminado es /dev/tpm0.

Ejemplo: -T device:/dev/tpm0 o export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: Para el TCTI mssim, se puede especificar el nombre de dominio o la dirección IP y el número de puerto utilizados por el simulador. Los valores predeterminados son 127.0.0.1 y 2321.

Ejemplo: -T mssim:host=localhost,port=2321 o export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

tpm2_policyauthorize(1) - tpm2-tools

NAME

tpm2_policyauthorize — authorize a policy session with a signature

SYNOPSIS

tpm2_policyauthorize [OPTIONS] [-S session] [-L policy] [-n name] [-t] [-i] [-f]

DESCRIPTION

The tpm2_policyauthorize command is used to authorize a policy session using a signature. This command is typically used in conjunction with other policy commands to establish complex authorization schemes. It allows a policy to be authorized by a signature that was created by a specific key (identified by name).

The tool allows for setting up a policy that requires a valid signature from a designated signing authority. This can be used for various purposes, such as creating objects that can only be managed or unsealed if a specific policy, verified by a signature, is met.

OPTIONS

The command supports the following options:

-S, --session=session
The policy session context. This can be a file path to a session context or a session string like "session:0x0". If not specified, the command will attempt to use the default session if one exists.
-L, --policy=policy
Path to the policy file digest. If not specified, the policy digest is computed from the inputs and session.
-n, --name=name
The name of the public key context. This is used to verify the signature. The name should correspond to the public key used to sign the policy.
-t, --ticket=ticket
Path to the authorization ticket. The ticket is generated by tpm2_verifysignature(1) and is used to link the signature verification to the policy authorization.
-i, --input=input
Path to the policy digest file that is to be authorized. If not specified, the digest is computed from the session.
-f, --format=format
The format of the policy digest. Can be one of:
fs: The input is a file name.
tpm: The input is a TPM-generated digest.
This option is often inferred from the policy computation.

COMMON OPTIONS

These options are common to most TPM2 tools.

-h, --help
Print the help message.
-V, --version
Print version information.
-v, --verbose
Enable verbose output.
-d, --debug
Enable debug output.

TCTI Configuration

The TPM Communication Transport Interface (TCTI) specifies how the tools communicate with the TPM. The default TCTI is usually configured at build time. However, it can be overridden using the TPM2TOOLS_TCTI environment variable or the --tcti option.

export TPM2TOOLS_TCTI="mssim:host=localhost,port=2321";
•
abrmd: For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,' character. Each key and value string are separated by a `=' character.
•
TCTI abrmd supports two keys:
1.
`bus_name' : The name of the tabrmd service on the bus (a string).
2.
`bus_type' : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules.

EXAMPLES

Starts a trial session, builds a PCR policy. This PCR policy digest is then an input to the tpm2_policyauthorize(1) along with policy qualifier data and a signer public. The resultant policy digest is then used in creation of objects.

Subsequently when the PCR change and so does the PCR policy digest, the actual policy digest from the tpm2_policyauthorize(1) used in creation of the object will not change. At runtime the new PCR policy needs to be satisfied along with verification of the signature on the PCR policy digest using tpm2_policyauthorize(1)

Create a signing authority

openssl genrsa -out signing_key_private.pem 2048
openssl rsa -in signing_key_private.pem -out signing_key_public.pem -pubout
tpm2_loadexternal -G rsa -C o -u signing_key_public.pem -c signing_key.ctx -n signing_key.name

Create the authorize policy digest

tpm2_startauthsession -S session.ctx
tpm2_policyauthorize -S session.ctx -L authorized.policy -n signing_key.name
tpm2_flushcontext session.ctx

Create a policy to be authorized like a PCR policy

tpm2_pcrread -opcr0.sha256 sha256:0
tpm2_startauthsession -S session.ctx
tpm2_policypcr -S session.ctx -l sha256:0 -f pcr0.sha256 -L pcr.policy_desired
tpm2_flushcontext session.ctx

Sign the policy

openssl dgst -sha256 -sign signing_key_private.pem -out pcr.signature pcr.policy_desired

Create a TPM object like a sealing object with the authorized policy based authentication

tpm2_createprimary -C o -g sha256 -G rsa -c prim.ctx
tpm2_create -g sha256 -u sealing_pubkey.pub -r sealing_prikey.pub -i- -C prim.ctx -L authorized.policy <<< "secret to seal"

Verify the desired policy digest comes from the signing authority, read the actual value of PCR and check that read policy and desired policy are equal.

tpm2_verifysignature -c signing_key.ctx -g sha256 -m  pcr.policy_desired -s pcr.signature -t verification.tkt -f rsassa
tpm2_startauthsession \--policy-session -S session.ctx
tpm2_policypcr -S session.ctx -l sha256:0 -L pcr.policy_read
tpm2_policyauthorize -S session.ctx -L authorized.policy -i pcr.policy_desired -n signing_key.name -t verification.tkt
tpm2_load -C prim.ctx -u sealing_pubkey.pub -r sealing_prikey.pub -c sealing_key.ctx
unsealed=$(tpm2_unseal -p"session:session.ctx" -c sealing_key.ctx)
echo $unsealed
tpm2_flushcontext session.ctx

Returns

Tools can return any of the following codes:

•
0 - Success.
•
1 - General non-specific error.
•
2 - Options handling error.
•
3 - Authentication error.
•
4 - TCTI related error.
•
5 - Non supported scheme. Applicable to tpm2_testparams.

Limitations

It expects a session to be already established via tpm2_startauthsession(1) and requires one of the following:

•
direct device access
•
extended session support with tpm2-abrmd.

Without it, most resource managers will not save session state between command invocations.
