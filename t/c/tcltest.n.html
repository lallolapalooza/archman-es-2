DESCRIPCIÓN

El paquete tcltest proporciona varios comandos de utilidad útiles en la construcción de conjuntos de pruebas para código instrumentado que se ejecutará mediante la evaluación de comandos Tcl. Notablemente, los comandos integrados de la propia biblioteca Tcl son probados por un conjunto de pruebas que utiliza el paquete tcltest.

Todos los comandos proporcionados por el paquete tcltest están definidos y exportados desde el espacio de nombres ::tcltest, como se indica en la SINOPSIS anterior. En las siguientes secciones, todos los comandos se describirán por sus nombres simples, en aras de la brevedad.

El comando central de tcltest es test, que define y ejecuta una prueba. Probar con test implica la evaluación de un script Tcl y la comparación del resultado con un resultado esperado, según se configure y controle mediante una serie de opciones. Varios comandos más proporcionados por tcltest gobiernan la configuración de test y la recolección de muchos comandos test en conjuntos de pruebas.

Vea CREACIÓN DE CONJUNTOS DE PRUEBAS CON TCLTEST a continuación para obtener un ejemplo extendido de cómo utilizar los comandos de tcltest para producir conjuntos de pruebas para su código habilitado para Tcl.

COMANDOS

test nombre descripción ?-opción valor?
Define y posiblemente ejecuta una prueba con el nombre nombre y la descripción descripción. El nombre y la descripción de una prueba se utilizan en los mensajes informados por test durante la prueba, según se configure con las opciones de tcltest. Los argumentos restantes opción valor para test definen la prueba, incluyendo los scripts a ejecutar, las condiciones bajo las cuales ejecutarlos, el resultado esperado y los medios por los cuales los resultados esperados y reales deben compararse. Consulte PRUEBAS a continuación para una descripción completa de las opciones válidas y cómo definen una prueba. El comando test devuelve una cadena vacía.
test nombre descripción ?restricciones? cuerpo resultado
Esta forma de test se proporciona para soportar conjuntos de pruebas escritos para la versión 1 del paquete tcltest, y también una interfaz más simple para un uso común. Es lo mismo que “test nombre descripción -constraints restricciones -body cuerpo -result resultado”. Todas las demás opciones para test toman sus valores predeterminados. Cuando restricciones se omite, esta forma de test se puede distinguir de la primera porque todas las opciones comienzan con “-”.
loadTestedCommands
Evalúa en el contexto del llamador el script especificado por configure -load o configure -loadfile. Devuelve el resultado de esa evaluación de script, incluyendo cualquier error que genere el script. Use este comando y las opciones de configuración relacionadas para proporcionar los comandos a probar al intérprete que ejecuta el conjunto de pruebas.
makeFile contenido nombre ?directorio?
Crea un archivo llamado nombre relativo al directorio directorio y escribe contenido en ese archivo usando la codificación encoding system. Si contenido no termina con una nueva línea, se agregará una nueva línea para que el archivo llamado nombre termine con una nueva línea. Debido a que se utiliza la codificación del sistema, este comando solo es adecuado para crear archivos de texto. El archivo será eliminado por la próxima evaluación de cleanupTests, a menos que sea eliminado primero por removeFile. El valor predeterminado de directorio es el directorio configure -tmpdir. Devuelve la ruta completa del archivo creado. Use este comando para crear cualquier archivo de texto requerido por una prueba con el contenido necesario.
removeFile nombre ?directorio?
Fuerza la eliminación del archivo referenciado por nombre. Este nombre de archivo debe ser relativo a directorio. El valor predeterminado de directorio es el directorio configure -tmpdir. Devuelve una cadena vacía. Use este comando para eliminar archivos creados por makeFile.
makeDirectory nombre ?directorio?
Crea un directorio llamado nombre relativo al directorio directorio. El directorio será eliminado por la próxima evaluación de cleanupTests, a menos que sea eliminado primero por removeDirectory. El valor predeterminado de directorio es el directorio configure -tmpdir. Devuelve la ruta completa del directorio creado. Use este comando para crear cualquier directorio que deba existir según una prueba.
removeDirectory nombre ?directorio?
Fuerza la eliminación del directorio referenciado por nombre. Este directorio debe ser relativo a directorio. El valor predeterminado de directorio es el directorio configure -tmpdir. Devuelve una cadena vacía. Use este comando para eliminar cualquier directorio creado por makeDirectory.
viewFile archivo ?directorio?
Devuelve el contenido de archivo, excepto cualquier nueva línea final, tal como lo devolvería read -nonewline. Este nombre de archivo debe ser relativo a directorio. El valor predeterminado de directorio es el directorio configure -tmpdir. Use este comando como una forma conveniente de convertir el contenido de un archivo generado por una prueba en el resultado de esa prueba para compararlo con un resultado esperado. El contenido del archivo se lee utilizando la codificación del sistema, por lo que su utilidad se limita a archivos de texto.
cleanupTests
Destinado a limpiar y resumir después de que se hayan ejecutado varias pruebas. Típicamente se llama una vez por archivo de prueba, al final del archivo después de que se hayan completado todas las pruebas. Para una mayor efectividad, asegúrese de que cleanupTests se evalúe incluso si ocurre un error anteriormente en la evaluación del archivo de prueba.

Imprime estadísticas sobre las pruebas ejecutadas y elimina los archivos que fueron creados por makeDirectory y makeFile desde la última cleanupTests. Los nombres de archivos y directorios en el directorio configure -tmpdir creados desde la última cleanupTests, pero no creados por makeFile o makeDirectory se imprimen en outputChannel. Este comando también restaura el entorno de shell original, como se describe en la variable global env.

COMANDOS DE CONFIGURACIÓN

configure
Devuelve la lista de opciones configurables compatibles con tcltest. Consulte OPCIONES CONFIGURABLES a continuación para obtener la lista completa de opciones, sus valores válidos y su efecto en las operaciones de tcltest.
configure opción
Devuelve el valor actual de la opción configurable admitida opción. Genera un error si la opción no es una opción configurable admitida.
configure opción valor ?-opción valor ...?
Establece el valor de cada opción configurable opción al valor correspondiente valor, en orden. Genera un error si una opción no es una opción configurable admitida, o si el valor no es un valor válido para la opción correspondiente, o si no se proporciona un valor. Cuando se genera un error, la operación de configure se detiene y los argumentos opción valor posteriores no se procesan.

Si la variable de entorno ::env(TCLTEST_OPTIONS) existe cuando se carga el paquete tcltest (mediante package require tcltest), su valor se toma como una lista de argumentos para pasar a configure. Esto permite que los valores predeterminados de las opciones de configuración se establezcan mediante el entorno.

customMatch modo script
Registra modo como un nuevo valor legal de la opción -match para test. Cuando se pasa la opción -match modo a test, el script script se evaluará para comparar el resultado real de evaluar el cuerpo de la prueba con el resultado esperado. Para realizar la comparación, el script se completa con dos palabras adicionales, el resultado esperado y el resultado real, y el script completado se evalúa en el espacio de nombres global. Se espera que el script completado devuelva un valor booleano que indique si los resultados coinciden o no. Los modos de comparación integrados de test son exact, glob y regexp.
testConstraint restricción ?booleano?
Establece o devuelve el valor booleano asociado con la restricción con nombre. Consulte RESTRICCIONES DE PRUEBAS a continuación para obtener más información.
interpreter ?nombreEjecutable?
Establece o devuelve el nombre del ejecutable que exec ejecutará runAllTests para ejecutar cada archivo de prueba cuando configure -singleproc sea falso. El valor predeterminado para interpreter es el nombre del programa que se está ejecutando actualmente, tal como lo devuelve info nameofexecutable.
outputChannel ?idCanal?
Establece o devuelve el ID del canal de salida. Por defecto es stdout. Cualquier prueba que imprima salida relacionada con la prueba debe enviar esa salida a outputChannel en lugar de permitir que esa salida sea stdout por defecto.
errorChannel ?idCanal?
Establece o devuelve el ID del canal de error. Por defecto es stderr. Cualquier prueba que imprima mensajes de error debe enviar esa salida a errorChannel en lugar de imprimir directamente en stderr.

OTROS COMANDOS

Los comandos restantes proporcionados por tcltest tienen mejores alternativas proporcionadas por tcltest o por el propio Tcl. Se conservan para admitir suites de pruebas existentes, pero deben evitarse en código nuevo.

test nombre descripción listaOpciones
Esta forma de test se proporcionó para permitir pasar muchas opciones que abarcan varias líneas a test como un único argumento entrecomillado por llaves, en lugar de necesitar entrecomillar con barra invertida los saltos de línea entre argumentos de test. Se espera que el argumento listaOpciones sea una lista con un número par de elementos que representen argumentos de opción y valor para pasar a test. Sin embargo, estos valores no se pasan directamente, como en las formas alternativas de switch. En cambio, esta forma hace un intento desafortunado de anular las reglas de sustitución de Tcl realizando sustituciones en algunos de los elementos de la lista como un intento de implementar una interpretación de "haz lo que quiero" de un "bloque" entre llaves. El resultado es casi imposible de documentar claramente y, por esa razón, no se recomienda esta forma. Consulte los ejemplos en CREACIÓN DE SUITES DE PRUEBAS CON TCLTEST a continuación para ver que esta forma realmente no es necesaria para evitar saltos de línea entrecomillados con barra invertida. Si insiste en usar esta forma, examine el código fuente de tcltest si desea conocer los detalles de la sustitución, o simplemente encierre el tercer argumento hasta el último para test entre llaves y espere lo mejor.
workingDirectory ?nombreDirectorio?
Establece o devuelve el directorio de trabajo actual mientras se ejecuta la suite de pruebas. El valor predeterminado para workingDirectory es el directorio en el que se inició la suite de pruebas. Los comandos Tcl cd y pwd son reemplazos suficientes.
normalizeMsg mensaje
Devuelve el resultado de eliminar los saltos de línea "adicionales" de mensaje, donde "adicional" es bastante impreciso. Tcl ofrece muchos comandos de procesamiento de cadenas para modificar cadenas como desee, y customMatch permite la comparación flexible de resultados reales y esperados.
normalizePath varRuta
Resuelve los enlaces simbólicos en una ruta, creando así una ruta sin redirección interna. Se asume que varRuta es absoluta. varRuta se modifica en su lugar. El comando Tcl file normalize es un reemplazo suficiente.
bytestring cadena
Construye una cadena que consiste en la secuencia de bytes solicitada, en oposición a una cadena de caracteres UTF-8 correctamente formados utilizando el valor proporcionado en cadena. Esto permite al probador crear cadenas denormalizadas o mal formadas para pasarlas a procedimientos C que se supone que aceptan cadenas con tipos NULL incrustados y confirmar que un resultado de cadena tiene un cierto patrón de bytes. Esto es exactamente equivalente al comando Tcl encoding convertfrom identity. Esta función está obsoleta.

PRUEBAS

El comando test es el corazón del paquete tcltest. Su función esencial es

para evaluar un script de Tcl y comparar el resultado con un resultado esperado. Las opciones de test definen el script de prueba, el entorno en el que se evaluará, el resultado esperado y cómo comparar el resultado real con el resultado esperado. Algunas opciones de configuración de tcltest también influyen en cómo opera test.

Las opciones válidas para test se resumen:

test nombre descripción
        ?-constraints listaClaves|expresión?
        ?-setup scriptConfiguración?
        ?-body scriptPrueba?
        ?-cleanup scriptLimpieza?
        ?-result respuestaEsperada?
        ?-output salidaEsperada?
        ?-errorOutput errorEsperado?
        ?-returnCodes listaCódigos?
        ?-errorCode códigoErrorEsperado?
        ?-match modo?

El nombre puede ser cualquier cadena. Es convencional elegir un nombre según el patrón:

objetivo-numMayor.numMenor

Para pruebas de caja blanca (regresión), el objetivo debe ser el nombre de la función C o el procedimiento Tcl que se está probando. Para pruebas de caja negra, el objetivo debe ser el nombre de la característica que se está probando. Algunas convenciones exigen que los nombres de las pruebas de caja negra tengan el sufijo _bb. Las pruebas relacionadas deben compartir un número mayor. A medida que evoluciona un conjunto de pruebas, es mejor que el mismo nombre de prueba continúe correspondiendo a la misma prueba, de modo que siga teniendo sentido decir cosas como "La prueba foo-1.3 pasó en todas las versiones hasta la 3.4, pero comenzó a fallar en la versión 3.5".

Durante la evaluación de test, el nombre se comparará con las listas de patrones de coincidencia de cadenas devueltas por configure -match y configure -skip. La prueba se ejecutará solo si el nombre coincide con alguno de los patrones de configure -match y no coincide con ninguno de los patrones de configure -skip.

La descripción debe ser una breve descripción textual de la prueba. La descripción se incluye en la salida producida por la prueba, típicamente en los mensajes de fallo de la prueba. Los buenos valores de descripción deben explicar brevemente el propósito de la prueba a los usuarios de un conjunto de pruebas. El nombre de una función Tcl o C que se está probando debe incluirse en la descripción para las pruebas de regresión. Si el caso de prueba existe para reproducir un error, incluya el ID del error en la descripción.

Los atributos válidos y sus valores asociados son:

-constraints listaClaves|expresión
El atributo opcional -constraints puede ser una lista de una o más palabras clave o una expresión. Si el valor de -constraints es una lista de palabras clave, cada una de estas palabras clave debe ser el nombre de una restricción definida por una llamada a testConstraint. Si alguna de las restricciones listadas es falsa o no existe, la prueba se omite. Si el valor de -constraints es una expresión, se evalúa esa expresión. Si la expresión se evalúa como verdadera, entonces se ejecuta la prueba. Tenga en cuenta que la forma de expresión de -constraints puede interferir con la operación de configure -constraints y configure -limitconstraints, y no se recomienda. Se deben agregar restricciones apropiadas a cualquier prueba que no deba ejecutarse siempre. Es decir, la evaluación condicional de una prueba debe realizarse mediante la opción -constraints, no mediante la evaluación condicional de test. De esta manera, el conjunto de pruebas siempre informa el mismo número de pruebas, aunque el número de pruebas omitidas pueda cambiar según el entorno de prueba. El valor predeterminado es una lista vacía. Consulte RESTRICCIONES DE PRUEBA a continuación para obtener una lista de restricciones integradas y información sobre cómo agregar sus propias restricciones.
-setup script
El atributo opcional -setup indica un script que se ejecutará antes del script indicado por el atributo -body. Si la evaluación del script genera un error, la prueba fallará. El valor predeterminado es un script vacío.
-body script
El atributo -body indica el script a ejecutar para llevar a cabo la prueba, que debe devolver un resultado que pueda verificarse en busca de corrección. Si la evaluación del script genera un error, la prueba fallará (a menos que se use la opción -returnCodes para indicar que se espera un error). El valor predeterminado es un script vacío.
-cleanup script
El atributo opcional -cleanup indica un script que se ejecutará después del script indicado por el atributo -body. Si la evaluación del script genera un error, la prueba fallará. El valor predeterminado es un script vacío.
-match modo
El atributo -match determina cómo se comparan las respuestas esperadas proporcionadas por -result, -output y -errorOutput. Los valores válidos para modo son regexp, glob, exact y cualquier valor registrado por una llamada previa a customMatch. El valor predeterminado es exact.
-result valorEsperado
El atributo -result proporciona el valorEsperado contra el cual se comparará el valor de retorno del script. El valor predeterminado es una cadena vacía.
-output valorEsperado
El atributo -output proporciona el valorEsperado contra el cual se comparará cualquier salida enviada a stdout o outputChannel durante la evaluación del script. Tenga en cuenta que solo la salida impresa usando el comando global puts se utiliza para la comparación. Si no se especifica -output, la salida enviada a stdout y outputChannel no se procesa para la comparación.
-errorOutput valorEsperado
El atributo -errorOutput proporciona el valorEsperado contra el cual se comparará cualquier salida enviada a stderr o errorChannel durante la evaluación del script. Tenga en cuenta que solo la salida impresa usando el comando global puts se utiliza para la comparación. Si no se especifica -errorOutput, la salida enviada a stderr y errorChannel no se procesa para la comparación.
-returnCodes listaCódigosEsperados
El atributo opcional -returnCodes proporciona listaCódigosEsperados, una lista de códigos de retorno que pueden ser aceptados de la evaluación del script -body. Si la evaluación del script -body devuelve un código que no está en la listaCódigosEsperados, la prueba falla. Todos los códigos de retorno conocidos por return, en forma numérica y simbólica, incluidos los códigos de retorno extendidos, son elementos aceptables en la listaCódigosEsperados. El valor predeterminado es "ok return".
-errorCode códigoErrorEsperado
El atributo opcional -errorCode proporciona códigoErrorEsperado, un patrón glob que debe coincidir con el código de error informado de la evaluación del script -body. Si la evaluación del script -body devuelve un código que no coincide con códigoErrorEsperado, la prueba falla. El valor predeterminado es "*". Si -returnCodes no incluye error, se establece en error.

Para tener éxito, una prueba debe evaluar correctamente sus scripts -setup, -body y -cleanup. El código de retorno del script -body y su resultado deben coincidir con los valores esperados y, si se especifica, la salida y los datos de error de la prueba deben coincidir con los valores esperados de -output y -errorOutput. Si alguna de estas condiciones no se cumple, la prueba falla. Tenga en cuenta que todos los scripts se evalúan en el contexto del llamador de test.

Mientras test se llame con sintaxis válida y valores legales para todos los atributos, no generará un error. Los fallos de prueba se informan en su lugar como salida escrita en outputChannel. En la operación predeterminada, una prueba exitosa no produce ninguna salida. Los mensajes de salida producidos por test están controlados por la opción configure -verbose, como se describe en OPCIONES CONFIGURABLES a continuación. Cualquier salida producida por los propios scripts de prueba debe producirse utilizando puts a outputChannel o errorChannel, para que los usuarios del conjunto de pruebas puedan capturar fácilmente la salida con las opciones configure -outfile y configure -errfile, y para que los atributos -output y -errorOutput funcionen correctamente.

RESTRICCIONES DE PRUEBA

Las restricciones se utilizan para determinar si una prueba debe omitirse o no. Cada restricción tiene un nombre, que puede ser cualquier cadena, y un valor booleano. Cada test tiene un valor -constraints que es una lista de nombres de restricciones. Hay dos modos de control de restricciones. La mayor parte del tiempo, se utiliza el modo predeterminado, indicado por la configuración de configure -limitconstraints en falso. La prueba se ejecutará solo si todas las restricciones de la lista son verdaderas. Por lo tanto, la opción -constraints de test es una forma simbólica conveniente para definir cualquier condición requerida para que la prueba sea posible o significativa. Por ejemplo, un test con -constraints unix solo se ejecutará si la restricción unix es verdadera, lo que indica que el conjunto de pruebas se está ejecutando en una plataforma Unix.

Cada test debe incluir las -constraints necesarias para limitarlo a ejecutarse solo donde sea apropiado. Varias restricciones están predefinidas en el paquete tcltest, que se enumeran a continuación. El registro de restricciones definidas por el usuario se realiza mediante el comando testConstraint. Las restricciones definidas por el usuario pueden aparecer dentro de un archivo de prueba, o dentro del script especificado por las opciones configure -load o configure -loadfile.

win
Esta prueba solo se puede ejecutar en cualquier plataforma Windows.

CONSTRAINTS

The tcltest system allows tests to be tagged with constraints. These constraints can be used to control which tests are run. The system comes with a default set of constraints; new constraints can be added and used by calling the constraint command. The following is a list of the default constraints:

unix
This test can only be run on a Unix platform.
win
This test can only be run on a Windows platform.
mac
This test can only be run on a Mac platform.
unixOrWin
This test can only be run on a Unix or Windows platform.
macOrWin
This test can only be run on a Mac or Windows platform.
macOrUnix
This test can only be run on a Mac or Unix platform.
tempNotWin
This test can not be run on Windows. This flag is used to temporarily disable a test.
tempNotMac
This test can not be run on a Mac. This flag is used to temporarily disable a test.
unixCrash
This test crashes if it is run on Unix. This flag is used to temporarily disable a test.
winCrash
This test crashes if it is run on Windows. This flag is used to temporarily disable a test.
macCrash
This test crashes if it is run on a Mac. This flag is used to temporarily disable a test.
emptyTest
This test is empty, and so not worth running, but it remains as a place-holder for a test to be written in the future. This constraint has value false to cause tests to be skipped unless the user specifies otherwise.
knownBug
This test is known to fail and the bug is not yet fixed. This constraint has value false to cause tests to be skipped unless the user specifies otherwise.
nonPortable
This test can only be run in some known development environment. Some tests are inherently non-portable because they depend on things like word length, file system configuration, window manager, etc. This constraint has value false to cause tests to be skipped unless the user specifies otherwise.
userInteraction
This test requires interaction from the user. This constraint has value false to causes tests to be skipped unless the user specifies otherwise.
interactive
This test can only be run in if the interpreter is in interactive mode (when the global tcl_interactive variable is set to 1).
nonBlockFiles
This test can only be run if platform supports setting files into nonblocking mode.
asyncPipeClose
This test can only be run if platform supports async flush and async close on a pipe.
unixExecs
This test can only be run if this machine has Unix-style commands cat, echo, sh, wc, rm, sleep, fgrep, ps, chmod, and mkdir available.
hasIsoLocale
This test can only be run if can switch to an ISO locale.
root
This test can only run if Unix user is root.
notRoot
This test can only run if Unix user is not root.
eformat
This test can only run if app has a working version of sprintf with respect to the “e” format of floating-point numbers.
stdio
This test can only be run if interpreter can be opened as a pipe.

The alternative mode of constraint control is enabled by setting configure -limitconstraints to true. With that configuration setting, all existing constraints other than those in the constraint list returned by configure -constraints are set to false. When the value of configure -constraints is set, all those constraints are set to true. The effect is that when both options configure -constraints and configure -limitconstraints are in use, only those tests including only constraints from the configure -constraints list are run; all others are skipped. For example, one might set up a configuration with

configure -constraints knownBug \
          -limitconstraints true \
          -verbose pass

to run exactly those tests that exercise known bugs, and discover whether any of them pass, indicating the bug had been fixed.

RUNNING ALL TESTS

The single command runAllTests is evaluated to run an entire test suite, spanning many files and directories. The configuration options of tcltest control the precise operations. The runAllTests command begins by printing a summary of its configuration to outputChannel.

Test files to be evaluated are sought in the directory configure -testdir. The list of files in that directory that match any of the patterns in configure -file and match none of the patterns in configure -notfile is generated and sorted. Then each file will be evaluated in turn. If configure -singleproc is true, then each file will be sourced in the caller's context. If it is false, then a copy of interpreter will be exec'd to evaluate each file. The multi-process operation is useful when testing can cause errors so severe that a process terminates. Although such an error may terminate a child process evaluating one file, the main process can continue with the rest of the test suite. In multi-process operation, the configuration of tcltest in the main process is passed to the child processes as command line arguments, with the exception of configure -outfile. The runAllTests command in the main process collects all output from the child processes and collates their results into one main report. Any reports of individual test failures, or messages requested by a configure -verbose setting are passed directly on to outputChannel by the main process.

After evaluating all selected test files, a summary of the results is printed to outputChannel. The summary includes the total number of tests evaluated, broken down into those skipped, those passed, and those failed. The summary also notes the number of files evaluated, and the names of any files with failing tests or errors. A list of the constraints that caused tests to be skipped, and the number of tests skipped for each is also printed. Also, messages are printed if it appears that evaluation of a test file has caused any temporary files to be left behind in configure -tmpdir.

Having completed and summarized all selected test files, runAllTests then recursively acts on subdirectories of configure -testdir. All subdirectories that match any of the patterns in configure -relateddir and do not match any of the patterns in configure -asidefromdir are examined. If a file named all.tcl is found in such a directory, it will be sourced in the caller's context. Whether or not an examined directory contains an all.tcl file, its subdirectories are also scanned against the configure -relateddir and configure -asidefromdir patterns. In this way, many directories in a directory tree can have all their test files evaluated by a single runAllTests command.

CONFIGURABLE OPTIONS

The configure command is used to set and query the configurable options of tcltest. The valid options are:

-singleproc boolean
Controls whether or not runAllTests spawns a child process for each test file. No spawning when boolean is true. Default value is false.
-debug level
Sets the debug level to level, an integer value indicating how much debugging information should be printed to stdout. Note that debug messages always go to stdout, independent of the value of configure -outfile. Default value is 0. Levels are defined as:
0
Do not display any debug information.
1
Display information regarding whether a test is skipped because it does not match any of the tests that were specified using by configure -match (userSpecifiedNonMatch) or matches any of the tests specified by configure -skip (userSpecifiedSkip). Also print warnings about possible lack of cleanup or balance in test files. Also print warnings about any re-use of test names.
2
Display the flag array parsed by the command line processor, the contents of the global env array, and all user-defined variables that exist in the current namespace as they are used.
3
Display information regarding what individual procs in the test harness doing.
-verbose level
Sets the type of output verbosity desired to level, a list of zero or more of the elements body, pass, skip, start, error, line, msec and usec. Default value is “body error”. Levels are defined as:
body (b)
Display the body of failed tests
pass (p)
Print output when a test passes
skip (s)
Print output when a test is skipped
start (t)
Print output whenever a test starts
error (e)
Print errorInfo and errorCode, if they exist, when a test return code does not match its expected return code
line (l)
Print source file line information of failed tests
msec (m)
Imprime el tiempo de ejecución de cada prueba en milisegundos
usec (u)
Imprime el tiempo de ejecución de cada prueba en microsegundos

Tenga en cuenta que los niveles de verbosidad msec y usec se proporcionan solo como medidas indicativas. No abordan el problema de la repetición, que debe considerarse en pruebas de rendimiento o benchmarks. Para utilizar estos niveles de verbosidad y rastrear exhaustivamente las degradaciones de rendimiento, considere envolver los cuerpos de sus pruebas con comandos time.

Las abreviaturas de una sola letra mencionadas anteriormente también se reconocen, de modo que “configure -verbose pt” es lo mismo que “configure -verbose {pass start}”.

-preservecore nivel
Establece el nivel de preservación del núcleo en nivel. Este nivel determina qué tan estrictas son las comprobaciones de los archivos del núcleo. El valor predeterminado es 0. Los niveles se definen como:
0
Sin comprobación: no compruebe los archivos del núcleo al final de cada comando de prueba, pero sí compruebe si existen en runAllTests después de que se hayan evaluado todos los archivos de prueba.
1
También compruebe los archivos del núcleo al final de cada comando test.
2
Compruebe los archivos del núcleo en todos los momentos descritos anteriormente y guarde una copia de cada archivo del núcleo producido en configure -tmpdir.
-limitconstraints booleano
Establece el modo en que test respeta las restricciones descritas en TESTS anteriormente. El valor predeterminado es falso.
-constraints lista
Establece todas las restricciones en lista a verdadero. También se utiliza en combinación con configure -limitconstraints true para controlar un modo de restricción alternativo, como se describe en TESTS anteriormente. El valor predeterminado es una lista vacía.
-tmpdir directorio
Establece el directorio temporal que será utilizado por makeFile, makeDirectory, viewFile, removeFile y removeDirectory como el directorio predeterminado donde se deben crear los archivos y directorios temporales creados por los archivos de prueba. El valor predeterminado es workingDirectory.
-testdir directorio
Establece el directorio en el que runAllTests busca archivos de prueba y subdirectorios. El valor predeterminado es workingDirectory.
-file listaPatrones
Establece la lista de patrones utilizada por runAllTests para determinar qué archivos de prueba evaluar. El valor predeterminado es “*.test”.
-notfile listaPatrones
Establece la lista de patrones utilizada por runAllTests para determinar qué archivos de prueba omitir. El valor predeterminado es “l.*.test”, de modo que se omitan los archivos de bloqueo SCCS.
-relateddir listaPatrones
Establece la lista de patrones utilizada por runAllTests para determinar qué subdirectorios buscar un archivo all.tcl. El valor predeterminado es “*”.
-asidefromdir listaPatrones
Establece la lista de patrones utilizada por runAllTests para determinar qué subdirectorios omitir al buscar un archivo all.tcl. El valor predeterminado es una lista vacía.
-match listaPatrones
Establece la lista de patrones utilizada por test para determinar si una prueba debe ejecutarse. El valor predeterminado es “*”.
-skip listaPatrones
Establece la lista de patrones utilizada por test para determinar si una prueba debe omitirse. El valor predeterminado es una lista vacía.
-load script
Establece un script que será evaluado por loadTestedCommands. El valor predeterminado es un script vacío.
-loadfile nombreArchivo
Establece el nombre del archivo desde el cual leer un script que será evaluado por loadTestedCommands. Esta es una alternativa a -load. No se pueden usar juntos.
-outfile nombreArchivo
Establece el archivo al que se escribirá toda la salida producida por tcltest. Se abrirá un archivo llamado nombreArchivo para escritura, y el canal resultante se establecerá como el valor de outputChannel.
-errfile nombreArchivo
Establece el archivo al que se escribirá toda la salida de error producida por tcltest. Se abrirá un archivo llamado nombreArchivo para escritura, y el canal resultante se establecerá como el valor de errorChannel.

CREACIÓN DE CONJUNTOS DE PRUEBAS CON TCLTEST

El elemento fundamental de un conjunto de pruebas es el comando individual test. Comenzamos con varios ejemplos.

[1]
Prueba de un script que retorna normalmente.
test example-1.0 {retorno normal} {
    format %s value
} value
[2]
Prueba de un script que requiere configuración y limpieza de contexto. Tenga en cuenta el estilo de llaves y sangría que evita cualquier necesidad de continuación de línea.
test example-1.1 {existencia de archivo de prueba} -setup {
    set file [makeFile {} test]
} -body {
    file exists $file
} -cleanup {
    removeFile test
} -result 1
[3]
Prueba de un script que genera un error.
test example-1.2 {retorno de error} -body {
    error message
} -returnCodes error -result message
[4]
Prueba con una restricción.
test example-1.3 {el usuario posee los archivos creados} -constraints {
    unix
} -setup {
    set file [makeFile {} test]
} -body {
    file attributes $file -owner
} -cleanup {
    removeFile test
} -result $::tcl_platform(user)

En el siguiente nivel superior de organización, varios comandos test se agrupan en un solo archivo de prueba. Los archivos de prueba deben tener nombres con la extensión “.test”, porque ese es el patrón predeterminado que utiliza runAllTests para encontrar archivos de prueba. Es una buena regla general tener un archivo de prueba por cada archivo de código fuente de su proyecto. Es una buena práctica editar el archivo de prueba y el archivo de código fuente juntos, manteniendo las pruebas sincronizadas con los cambios de código.

La mayor parte del código en el archivo de prueba deben ser los comandos test. Utilice restricciones para omitir pruebas, en lugar de evaluación condicional de test.

[5]
Sistema recomendado para escribir pruebas condicionales, utilizando restricciones para proteger:
testConstraint X [expr $myRequirement]
test goodConditionalTest {} X {
    # cuerpo
} result
[6]
Sistema desaconsejado para escribir pruebas condicionales, utilizando if para proteger:
if $myRequirement {
    test badConditionalTest {} {
        #cuerpo
    } result
}

Utilice las opciones -setup y -cleanup para establecer y liberar todos los requisitos de contexto del cuerpo de la prueba. No haga que las pruebas dependan de pruebas anteriores en el archivo. Esas pruebas anteriores podrían omitirse. Si varias pruebas consecutivas requieren el mismo contexto, los scripts de configuración y limpieza apropiados pueden almacenarse en variables para pasarlas a las opciones -setup y -cleanup de cada prueba. Esta es una mejor solución que realizar la configuración fuera de los comandos test, porque la configuración solo se realizará si es necesario, y cualquier error durante la configuración se informará, y no hará que el archivo de prueba se aborte.

Un archivo de prueba debe poder combinarse con otros archivos de prueba y no interferir con ellos, incluso cuando configure -singleproc 1 hace que todos los archivos se evalúen en un intérprete común. Una forma sencilla de lograr esto es que sus pruebas definan todos sus comandos y variables en un espacio de nombres que se elimina cuando finaliza la evaluación del archivo de prueba. Un buen espacio de nombres para usar es un espacio de nombres hijo test del espacio de nombres del módulo que está probando.

Un archivo de prueba también debe poder ser evaluado directamente como un script, sin depender de ser llamado por un runAllTests principal. Esto significa que cada archivo de prueba debe procesar los argumentos de la línea de comandos para brindar al probador todo el control de configuración que proporciona tcltest.

Después de todas las tests en un archivo de prueba, se debe llamar al comando cleanupTests.

[7]
Aquí hay un esquema de un archivo de prueba de ejemplo que ilustra esos puntos:
package require tcltest 2.5
eval ::tcltest::configure $argv
package require example
namespace eval ::example::test {
    namespace import ::tcltest::*
    testConstraint X [expr {...}]
    variable SETUP {#código de configuración común}
    variable CLEANUP {#código de limpieza común}
    test example-1 {} -setup $SETUP -body {
        # Primera prueba
    } -cleanup $CLEANUP -result {...}
    test example-2 {} -constraints X -setup $SETUP -body {
        # Segunda prueba; con restricción
    } -cleanup $CLEANUP -result {...}
    test example-3 {} {
        # Tercera prueba; no requiere contexto
    } {...}
    cleanupTests
}
namespace delete ::example::test

El siguiente nivel de organización es un conjunto de pruebas completo, compuesto por varios archivos de prueba. Se utiliza un script para controlar todo el conjunto. La función básica de este script es llamar a runAllTests después de realizar cualquier configuración necesaria. Este script generalmente se llama all.tcl porque ese es el nombre predeterminado utilizado por runAllTests al combinar varios conjuntos de pruebas en una sola ejecución de prueba.

[8]
Aquí hay un esquema de un script principal de conjunto de pruebas de ejemplo:
package require Tcl 8.6
package require tcltest 2.5
package require example
::tcltest::configure -testdir \
        [file dirname [file normalize [info script]]]
eval ::tcltest

NAME


tcltest — A Tcl module for building and running test suites






SYNOPSIS


package require Tcltest ?2.5?
test name ?-global? ?-disabled? ?-skip reason? ?-body script? ?-setup script? ?-cleanup script? ?-returnCode code? ?-error ?string?? ?-output ?string?? ?-errorOutput ?string??

DESCRIPTION


The tcltest package is a module for Tcl that
    provides facilities for building and running test suites. It provides a
    command, test, for defining individual tests and
    commands for running and cleaning up tests.


The primary goal of tcltest is to provide
    a standardized way to test Tcl code. It allows tests to be defined with
    setup and cleanup procedures, and it supports the specification of expected
    return codes, output, and error messages.






COMMANDS

Configures the test harness. This command can be used to set
        various options that affect how tests are run. Some common options
        include:

        
    
        
            
  • -name name: Set the name of the test suite.
    • 
            
  • -file file: Specify a file containing test
              definitions.
    • 
            
  • -returnCode code: Set the default return code
              for tests.
    • 
            
  • -output ?string?: Set the expected standard
              output for tests.
    • 
            
  • -errorOutput ?string?: Set the expected
              standard error output for tests.
    • 
            
  • -matchGlob glob: Only run tests whose names
              match the glob pattern.
    • 
            
  • -noMatchGlob glob: Do not run tests whose
              names match the glob pattern.
    • 
            
  • -runGlob glob: Only run tests whose names
              match the glob pattern. (Same as -matchGlob).
    • 
            
  • -skipGlob glob: Skip tests whose names match
              the glob pattern.
    • 
            
  • -disabledGlob glob: Mark tests whose names
              match the glob pattern as disabled.
    •

eval configure $::argv

TESTS


Tests are defined using the test command.
    Each test is given a unique name. The test command can
    take a -body script, which is the code that will be
    executed when the test is run. Optional -setup and
    -cleanup scripts can be provided to perform actions
    before and after the test body executes, respectively.


Tests can also be configured to expect specific outcomes, such as
    a particular return code (-returnCode), standard
    output (-output), or standard error output
    (-errorOutput). If the actual outcome of the test
    does not match the expected outcome, the test is marked as failed.


Tests can also be marked as disabled (-disabled)
    or skipped (-skip reason). Disabled tests are not
    run at all, while skipped tests are not run but are reported as skipped with
    a reason.






CONFIGURABLE OPTIONS


The behavior of the tcltest package can be
    modified using the configure command. Options such as
    -matchGlob, -skipGlob, and
    -disabledGlob allow for flexible selection and
    filtering of tests based on their names. This is particularly useful when
    dealing with large test suites.


The configure command can also set default
    values for return codes, output, and error output, which can simplify the
    definition of individual tests.

To create a test suite using tcltest, you
    typically:


    
    
  1.

    package require Tcltest
      
    
      
    
    
    2.

    configure {*}$::argv
      
    
      
    
    
    3. 
    
  3. 
      
    Define individual tests using the test
          command:
    
      
    
      
    test myTest.1 {

    reporting of test results. It typically outputs a summary indicating the

A typical test script might look like this:

# Configure the test harness with command line arguments

# Define a simple test
test simple.add {
    set a 10
    set b 20
    expr {$a + $b}
} -returnCode ok -result 30

test simple.error {
    error "This is an expected error"
} -returnCode error -error {This is an expected error}

# Run all tests and report results
runAllTests

# Clean up
cleanupTests

exit [expr {[llength [::tcltest::getFailures]] > 0}]





When this script is run, tcltest will
    execute the tests defined. If ok and results in 30) and
    error
    and generates the expected error message), the test suite will be considered
    successful.


The arguments passed to tcltest can be
    used to control which tests are run. For example, running the script with
    tclsh your_test_script.tcl myTest.1 will only run the
    test named The command runAllTests will evaluate
    ::tcltest::configure if it has not already been
    evaluated. The evaluation will use the contents of the global variable
    ::argv. So, if you are using the default behaviour of
    tcltest, you do not need to explicitly call
    ::tcltest::configure.


However, it is recommended that new test files include
    eval ::tcltest::configure $::argv or
    ::tcltest::configure {*}$::argv to explicitly
    establish a configuration from command line arguments.


Running the tests with arguments like
    tclsh your_test_script.tcl -matchGlob *add will only execute tests whose names match the glob
    pattern *add.

    all tests have been defined using the test command.

COMPATIBILITY

A number of commands and variables in the ::tcltest namespace provided by earlier releases of tcltest have not been documented here. They are no longer part of the supported public interface of tcltest and should not be used in new test suites. However, to continue to support existing test suites written to the older interface specifications, many of those deprecated commands and variables still work as before. For example, in many circumstances, configure will be automatically called shortly after package require tcltest 2.1 succeeds with arguments from the variable ::argv. This is to support test suites that depend on the old behavior that tcltest was automatically configured from command line arguments. New test files should not depend on this, but should explicitly include

eval ::tcltest::configure $::argv

or

::tcltest::configure {*}$::argv

to establish a configuration from command line arguments.

KNOWN ISSUES

There are two known issues related to nested evaluations of test. The first issue relates to the stack level in which test scripts are executed. Tests nested within other tests may be executed at the same stack level as the outermost test. For example, in the following code:

test level-1.1 {level 1} {
    -body {
        test level-2.1 {level 2} {
        }
    }
}

any script executed in level-2.1 may be executed at the same stack level as the script defined for level-1.1.

In addition, while two tests have been run, results will only be reported by cleanupTests for tests at the same level as test level-1.1. However, test results for all tests run prior to level-1.1 will be available when test level-2.1 runs. What this means is that if you try to access the test results for test level-2.1, it will may say that “m” tests have run, “n” tests have been skipped, “o” tests have passed and “p” tests have failed, where “m”, “n”, “o”, and “p” refer to tests that were run at the same test level as test level-1.1.

Implementation of output and error comparison in the test command depends on usage of puts in your application code. Output is intercepted by redefining the global puts command while the defined test script is being run. Errors thrown by C procedures or printed directly from C applications will not be caught by the test command. Therefore, usage of the -output and -errorOutput options to test is useful only for pure Tcl applications that use puts to produce output.
