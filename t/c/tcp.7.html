tcp(7) Manual de Información Miscelánea tcp(7)

NOMBRE

tcp - Protocolo TCP

SINOPSIS

#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>
tcp_socket = socket(AF_INET, SOCK_STREAM, 0);

DESCRIPCIÓN

Esta es una implementación del protocolo TCP definido en RFC 793, RFC 1122 y RFC 2001 con las extensiones NewReno y SACK. Proporciona una conexión fiable, orientada a flujo y full-duplex entre dos sockets sobre ip(7), para ambas versiones v4 y v6. TCP garantiza que los datos llegan en orden y retransmite los paquetes perdidos. Genera y verifica una suma de verificación por paquete para detectar errores de transmisión. TCP no preserva los límites de los registros.

Un socket TCP recién creado no tiene dirección local ni remota y no está completamente especificado. Para crear una conexión TCP saliente, use connect(2) para establecer una conexión con otro socket TCP. Para recibir nuevas conexiones entrantes, primero bind(2) el socket a una dirección y puerto local y luego llame a listen(2) para poner el socket en estado de escucha. Después de eso, se puede aceptar un nuevo socket para cada conexión entrante usando accept(2). Un socket en el que se ha llamado con éxito a accept(2) o connect(2) está completamente especificado y puede transmitir datos. No se pueden transmitir datos en sockets en escucha o que aún no estén conectados.

Linux soporta las extensiones TCP de alto rendimiento RFC 1323. Estas incluyen Protección contra Números de Secuencia Envueltos (PAWS), Escalado de Ventana y Marcas de Tiempo. El escalado de ventana permite el uso de ventanas TCP grandes (> 64 kB) para soportar enlaces con alta latencia o ancho de banda. Para utilizarlas, se deben aumentar los tamaños de los búferes de envío y recepción. Se pueden configurar globalmente con los archivos /proc/sys/net/ipv4/tcp_wmem y /proc/sys/net/ipv4/tcp_rmem, o en sockets individuales utilizando las opciones de socket SO_SNDBUF y SO_RCVBUF con la llamada setsockopt(2).

Los tamaños máximos de los búferes de socket declarados a través de los mecanismos SO_SNDBUF y SO_RCVBUF están limitados por los valores en los archivos /proc/sys/net/core/rmem_max y /proc/sys/net/core/wmem_max. Tenga en cuenta que TCP en realidad asigna el doble del tamaño del búfer solicitado en la llamada setsockopt(2), y por lo tanto, una llamada posterior a getsockopt(2) no devolverá el mismo tamaño de búfer que se solicitó en la llamada setsockopt(2). TCP utiliza el espacio adicional para fines administrativos y estructuras internas del kernel, y los valores de los archivos /proc reflejan los tamaños más grandes en comparación con las ventanas TCP reales. En conexiones individuales, el tamaño del búfer del socket debe establecerse antes de las llamadas listen(2) o connect(2) para que tenga efecto. Consulte socket(7) para obtener más información.

TCP soporta datos urgentes. Los datos urgentes se utilizan para señalar al receptor que un mensaje importante forma parte del flujo de datos y que debe procesarse lo antes posible. Para enviar datos urgentes, especifique la opción MSG_OOB a send(2). Cuando se reciben datos urgentes, el kernel envía una señal SIGURG al proceso o grupo de procesos que ha sido establecido como el "propietario" del socket utilizando las ioctls SIOCSPGRP o FIOSETOWN (o la operación F_SETOWN de fcntl(2) especificada por POSIX.1). Cuando la opción de socket SO_OOBINLINE está habilitada, los datos urgentes se colocan en el flujo de datos normal (un programa puede verificar su ubicación utilizando la ioctl SIOCATMARK descrita a continuación), de lo contrario, solo se pueden recibir cuando se establece el indicador MSG_OOB para recv(2) o recvmsg(2).

Cuando hay datos fuera de banda, select(2) indica el descriptor de archivo como que tiene una condición excepcional y poll(2) indica un evento POLLPRI.

Linux 2.4 introdujo una serie de cambios para mejorar el rendimiento y la escalabilidad, así como una funcionalidad mejorada. Algunas de estas características incluyen soporte para sendfile(2) de copia cero, Notificación Explícita de Congestión, nueva gestión de sockets TIME_WAIT, opciones de socket keep-alive y soporte para extensiones Duplicate SACK.

Formatos de dirección

TCP se basa en IP (ver ip(7)). Los formatos de dirección definidos por ip(7) se aplican a TCP. TCP solo soporta comunicación punto a punto; no se admite la difusión ni la multidifusión.

Interfaces de /proc

La configuración de los parámetros TCP a nivel de sistema se puede acceder a través de los archivos en el directorio /proc/sys/net/ipv4/. Además, la mayoría de las interfaces /proc de IP también se aplican a TCP; consulte ip(7). Las variables descritas como Booleanas toman un valor entero, con un valor distinto de cero ("verdadero") que significa que la opción correspondiente está habilitada, y un valor cero ("falso") que significa que la opción está deshabilitada.

tcp_abc (Entero; por defecto: 0; Linux 2.6.15 a Linux 3.8)
Controla la Apropiada Cuenta de Bytes (ABC), definida en RFC 3465. ABC es una forma de aumentar la ventana de congestión (cwnd) más lentamente en respuesta a acuses de recibo parciales. Los valores posibles son:
0
aumentar cwnd una vez por acuse de recibo (sin ABC)
1
aumentar cwnd una vez por acuse de recibo de segmento de tamaño completo
2
permitir aumentar cwnd en dos si el acuse de recibo es de dos segmentos para compensar los acuses de recibo retrasados.
tcp_abort_on_overflow (Booleano; por defecto: deshabilitado; desde Linux 2.4)
Habilita el restablecimiento de conexiones si el servicio de escucha es demasiado lento e incapaz de mantenerse al día y aceptarlas. Significa que si se produjo un desbordamiento debido a una ráfaga, la conexión se recuperará. Habilite esta opción *solo* si está realmente seguro de que el demonio de escucha no puede ajustarse para aceptar conexiones más rápido. Habilitar esta opción puede perjudicar a los clientes de su servidor.
tcp_adv_win_scale (entero; por defecto: 2; desde Linux 2.4)
Cuenta la sobrecarga de almacenamiento en búfer como bytes/2^tcp_adv_win_scale, si tcp_adv_win_scale es mayor que 0; o bytes-bytes/2^(-tcp_adv_win_scale), si tcp_adv_win_scale es menor o igual a cero.
El espacio del búfer de recepción del socket se comparte entre la aplicación y el kernel. TCP mantiene parte del búfer como la ventana TCP, que es el tamaño de la ventana de recepción anunciada al otro extremo. El resto del espacio se utiliza como búfer de la "aplicación", utilizado para aislar la red de las latencias de programación y aplicación. El valor por defecto de tcp_adv_win_scale de 2 implica que el espacio utilizado para el búfer de la aplicación es una cuarta parte del total.
tcp_allowed_congestion_control (Cadena; por defecto: ver texto; desde Linux 2.4.20)
Muestra/establece las opciones de algoritmo de control de congestión disponibles para procesos no privilegiados (ver la descripción de la opción de socket TCP_CONGESTION). Los elementos de la lista están separados por espacios en blanco y terminan con un carácter de nueva línea. La lista es un subconjunto de las que se encuentran en tcp_available_congestion_control. El valor por defecto para esta lista es "reno" más la configuración por defecto de tcp_congestion_control.
tcp_autocorking (Booleano; por defecto: habilitado; desde Linux 3.14)
Si esta opción está habilitada, el kernel intenta agrupar pequeños

La coalescencia se realiza si al menos un paquete anterior para el flujo está esperando en las colas de Qdisc o en la cola de transmisión del dispositivo. tcp_available_congestion_control (Cadena; solo lectura; desde Linux 2.4.20)
Muestra una lista de los algoritmos de control de congestión que están registrados. Los elementos de la lista están separados por espacios en blanco y terminados por un carácter de nueva línea. Esta lista es un conjunto limitante para la lista en tcp_allowed_congestion_control. Puede haber más algoritmos de control de congestión disponibles como módulos, pero no cargados.
tcp_app_win (entero; predeterminado: 31; desde Linux 2.4)
Esta variable define cuántos bytes de la ventana TCP se reservan para la sobrecarga del búfer.
Se reservan como máximo (ventana/2^tcp_app_win, mss) bytes en la ventana para el búfer de la aplicación. Un valor de 0 implica que no se reserva ninguna cantidad.
tcp_base_mss (Entero; predeterminado: 512; desde Linux 2.6.17)
El valor inicial de search_low a ser utilizado por la capa de paquetización para el descubrimiento de MTU de ruta (sondeo de MTU). Si el sondeo de MTU está habilitado, este es el MSS inicial utilizado por la conexión.
tcp_bic (Booleano; predeterminado: deshabilitado; Linux 2.4.27/2.6.6 a Linux 2.6.13)
Habilita el algoritmo de control de congestión TCP BIC. BIC-TCP es un cambio solo del lado del emisor que garantiza equidad lineal de RTT bajo ventanas grandes, ofreciendo escalabilidad y amigabilidad TCP acotada. El protocolo combina dos esquemas llamados aumento aditivo y aumento por búsqueda binaria. Cuando la ventana de congestión es grande, el aumento aditivo con un incremento grande garantiza equidad lineal de RTT, así como buena escalabilidad. Bajo ventanas de congestión pequeñas, el aumento por búsqueda binaria proporciona amigabilidad TCP.
tcp_bic_low_window (entero; predeterminado: 14; Linux 2.4.27/2.6.6 a Linux 2.6.13)
Establece la ventana umbral (en paquetes) donde BIC TCP comienza a ajustar la ventana de congestión. Por debajo de este umbral, BIC TCP se comporta igual que el TCP Reno predeterminado.
tcp_bic_fast_convergence (Booleano; predeterminado: habilitado; Linux 2.4.27/2.6.6 a Linux 2.6.13)
Fuerza a BIC TCP a responder más rápidamente a los cambios en la ventana de congestión. Permite que dos flujos que comparten la misma conexión converjan más rápidamente.
tcp_congestion_control (Cadena; predeterminado: ver texto; desde Linux 2.4.13)
Establece el algoritmo de control de congestión predeterminado que se utilizará para nuevas conexiones. El algoritmo "reno" siempre está disponible, pero pueden haber opciones adicionales disponibles según la configuración del kernel. El valor predeterminado para este archivo se establece como parte de la configuración del kernel.
tcp_dma_copybreak (entero; predeterminado: 4096; desde Linux 2.6.24)
Límite inferior, en bytes, del tamaño de las lecturas de socket que se descargarán a un motor de copia DMA, si hay uno presente en el sistema y el kernel fue configurado con la opción CONFIG_NET_DMA.
tcp_dsack (Booleano; predeterminado: habilitado; desde Linux 2.4)
Habilita el soporte de TCP Duplicate SACK (DSACK) según RFC 2883.
tcp_fastopen (Máscara de bits; predeterminado: 0x1; desde Linux 3.7)
Habilita el soporte de Fast Open según RFC 7413. El indicador se utiliza como un mapa de bits con los siguientes valores:
0x1
Habilita el soporte de Fast Open del lado del cliente
0x2
Habilita el soporte de Fast Open del lado del servidor
0x4
Permite que el lado del cliente transmita datos en SYN sin la opción Fast Open
0x200
Permite que el lado del servidor acepte datos SYN sin la opción Fast Open
0x400
Habilita Fast Open en todos los escuchadores sin la opción de socket TCP_FASTOPEN
tcp_fastopen_key (desde Linux 3.7)
Establece la clave del lado del servidor RFC 7413 Fast Open para generar la cookie de Fast Open cuando el soporte de Fast Open del lado del servidor está habilitado.
tcp_ecn (Entero; predeterminado: ver abajo; desde Linux 2.4)
Habilita la Notificación Explícita de Congestión (ECN) según RFC 3168.
Este archivo puede tener uno de los siguientes valores:
0
Deshabilita ECN. Ni inicia ni acepta ECN. Este era el valor predeterminado hasta Linux 2.6.30 inclusive.
1
Habilita ECN cuando es solicitado por conexiones entrantes y también solicita ECN en intentos de conexión salientes.
2
Habilita ECN cuando es solicitado por conexiones entrantes, pero no solicita ECN en conexiones salientes. Este valor es compatible y es el predeterminado, desde Linux 2.6.31.
Cuando está habilitado, la conectividad con algunos destinos podría verse afectada debido a middle boxes más antiguos y que se comportan mal en el camino, lo que provoca la caída de las conexiones. Sin embargo, para facilitar y fomentar la implementación con la opción 1, y para solucionar problemas de equipos defectuosos, se ha introducido la opción tcp_ecn_fallback.
tcp_ecn_fallback (Booleano; predeterminado: habilitado; desde Linux 4.1)
Habilita el fallback de la Sección 6.1.1.1 de RFC 3168. Cuando está habilitado, los SYNs salientes con configuración ECN que expiran dentro del tiempo de espera normal de retransmisión de SYN se volverán a enviar con CWR y ECE despejados.
tcp_fack (Booleano; predeterminado: habilitado; desde Linux 2.2)
Habilita el soporte de TCP Forward Acknowledgement (FACK).
tcp_fin_timeout (entero; predeterminado: 60; desde Linux 2.2)
Esto especifica cuántos segundos esperar un paquete FIN final antes de que el socket se cierre forzosamente. Esto es una violación estricta de la especificación TCP, pero es necesario para prevenir ataques de denegación de servicio. En Linux 2.2, el valor predeterminado era 180.
tcp_frto (entero; predeterminado: ver abajo; desde Linux 2.4.21/2.6)
Habilita F-RTO, un algoritmo de recuperación mejorado para tiempos de espera de retransmisión TCP (RTO). Es particularmente beneficioso en entornos inalámbricos donde la pérdida de paquetes se debe típicamente a interferencia de radio aleatoria en lugar de congestión del enrutador intermedio. Ver RFC 4138 para más detalles.
Este archivo puede tener uno de los siguientes valores:
0
Deshabilitado. Este era el valor predeterminado hasta Linux 2.6.23 inclusive.
1
Se habilita la versión básica del algoritmo F-RTO.
2
Habilita F-RTO mejorado con SACK si el flujo utiliza SACK. La versión básica también se puede usar cuando se utiliza SACK, aunque en ese caso existen escenarios donde F-RTO interactúa mal con el conteo de paquetes del flujo TCP habilitado para SACK. Este valor es el predeterminado desde Linux 2.6.24.
Antes de Linux 2.6.22, este parámetro era un valor booleano, que solo admitía los valores 0 y 1 anteriores.
tcp_frto_response (entero; predeterminado: 0; desde Linux 2.6.22)
Cuando F-RTO ha detectado que un tiempo de espera de retransmisión TCP fue espurio (es decir, se habría evitado el tiempo de espera si TCP hubiera establecido un tiempo de espera de retransmisión más largo), TCP tiene varias opciones sobre qué hacer a continuación. Los valores posibles son:
0
Basado en reducción a la mitad de la tasa; una respuesta suave y conservadora, resulta en una ventana de congestión (cwnd) y umbral de inicio lento (ssthresh) reducidos a la mitad después de un RTT.
1
Respuesta muy conservadora; no recomendada porque, aunque válida, interactúa mal con el resto de TCP de Linux; reduce a la mitad cwnd y ssthresh inmediatamente.
2
Respuesta agresiva; deshace las medidas de control de congestión que ahora se sabe que son innecesarias (ignorando la posibilidad de una retransmisión perdida que requeriría que TCP sea más cauteloso); cwnd y ssthresh se restauran a los valores anteriores al tiempo de espera.
tcp_keepalive_intvl (entero; predeterminado: 75; desde Linux 2.4)
El número de segundos entre las sondas keep-alive de TCP.
tcp_keepalive_probes (entero; predeterminado: 9; desde Linux 2.2)
El número máximo de sondas keep-alive de TCP a enviar antes de rendirse y matar la conexión si no se obtiene respuesta del otro extremo.
tcp_keepalive_time (entero; predeterminado: 7200; desde Linux 2.2)
El número de segundos que una conexión debe estar inactiva antes de que TCP comience a enviar sondas keep-alive. Las sondas keep-alive solo se envían cuando la opción de socket SO_KEEPALIVE está habilitada. El valor predeterminado es 7200 segundos (2 horas). Una conexión inactiva se termina después de aproximadamente 11 minutos adicionales (9 sondas separadas por un intervalo de 75 segundos) cuando keep-alive está habilitado.
Tenga en cuenta que los mecanismos de seguimiento de conexión subyacentes y los tiempos de espera de la aplicación pueden ser mucho más cortos.
tcp_low_latency (Booleano; predeterminado: deshabilitado; desde Linux 2.4.21/2.6; obsoleto desde Linux 4.14)
Si está habilitado, la pila TCP toma decisiones que prefieren menor latencia en lugar de mayor rendimiento. Si esta opción está deshabilitada, entonces se prefiere un mayor rendimiento. Un ejemplo de aplicación donde se debería cambiar este valor predeterminado sería un clúster de computación Beowulf. Desde Linux 4.14, este archivo todavía existe, pero su valor se ignora.
tcp_max_orphans (entero; predeterminado: ver abajo; desde Linux 2.4)
El número máximo de sockets TCP huérfanos (no adjuntos a ningún manejador de archivos de usuario) permitidos en el sistema. Cuando se excede este número, la conexión huérfana se reinicia y se imprime una advertencia. Este límite solo existe para prevenir ataques simples de denegación de servicio. No se recomienda reducir este límite. Las condiciones de red pueden requerir que aumente el número de huérfanos permitidos, pero tenga en cuenta que cada huérfano puede consumir hasta ~64 kB de memoria no paginable. El valor inicial predeterminado se establece igual al parámetro del kernel NR_FILE. Este valor predeterminado inicial se ajusta según la memoria del sistema.
tcp_max_syn_backlog (entero; predeterminado: ver abajo; desde Linux 2.2)
El número máximo de solicitudes de conexión en cola que aún no han recibido una confirmación del cliente que se conecta. Si se excede este número, el kernel comenzará a descartar solicitudes. El valor predeterminado de 256 se incrementa a 1024 cuando la memoria presente en el sistema es adecuada o mayor (>= 128 MB), y se reduce a 128 para aquellos sistemas con muy poca memoria (<= 32 MB).
Antes de Linux 2.6.20, se recomendaba que si esto necesitaba aumentarse por encima de 1024, se modificara el tamaño de la tabla hash SYNACK (TCP_SYNQ_HSIZE) en include/net/tcp.h para mantener

TCP_SYNQ_HSIZE * 16 <= tcp_max_syn_backlog

y se recompilara el kernel. En Linux 2.6.20, se eliminó el tamaño fijo TCP_SYNQ_HSIZE en favor del dimensionamiento dinámico.
tcp_max_tw_buckets (entero; predeterminado: ver abajo; desde Linux 2.4)
El número máximo de sockets en estado TIME_WAIT permitidos en el sistema. Este límite solo existe para prevenir ataques simples de denegación de servicio. El valor predeterminado de NR_FILE*2 se ajusta según la memoria del sistema. Si se excede este número, el socket se cierra y se imprime una advertencia.
tcp_moderate_rcvbuf (booleano; predeterminado: habilitado; desde Linux 2.4.17/2.6.7)
Si está habilitado, TCP realiza la sintonización automática del búfer de recepción, intentando ajustar automáticamente el tamaño del búfer (no mayor que tcp_rmem[2]) para que coincida con el tamaño requerido por la ruta para un rendimiento completo.
tcp_mem (desde Linux 2.4)
Este es un vector de 3 enteros: [bajo, presión, alto]. Estos límites, medidos en unidades del tamaño de página del sistema, son utilizados por TCP para rastrear su uso de memoria. Los valores predeterminados se calculan en el momento del arranque según la cantidad de memoria disponible. (TCP solo puede usar memoria baja para esto, que está limitada a alrededor de 900 megabytes en sistemas de 32 bits. Los sistemas de 64 bits no sufren esta limitación).
bajo
TCP no regula su asignación de memoria cuando el número de páginas que ha asignado globalmente está por debajo de este número.
presión
Cuando la cantidad de memoria asignada por TCP excede este número de páginas, TCP modera su consumo de memoria. Se sale de este estado de presión de memoria una vez que el número de páginas asignadas cae por debajo de la marca baja.
alto
El número máximo de páginas, globalmente, que TCP asignará. Este valor anula cualquier otro límite impuesto por el kernel.
tcp_mtu_probing (entero; predeterminado: 0; desde Linux 2.6.17)
Este parámetro controla el descubrimiento de MTU de ruta de la capa de paquetización de TCP. Los siguientes valores pueden asignarse al archivo:
0
Deshabilitado
1
Deshabilitado por defecto, habilitado cuando se detecta un agujero negro ICMP
2
Siempre habilitado, utiliza MSS inicial de tcp_base_mss.
tcp_no_metrics_save (booleano; predeterminado: deshabilitado; desde Linux 2.6.6)
Por defecto, TCP guarda varias métricas de conexión en la caché de ruta cuando la conexión se cierra, para que las conexiones que se establezcan en un futuro cercano puedan utilizarlas para establecer condiciones iniciales. Normalmente, esto aumenta el rendimiento general, pero a veces puede causar una degradación del rendimiento. Si tcp_no_metrics_save está habilitado, TCP no almacenará métricas en caché al cerrar conexiones.
tcp_orphan_retries (entero; predeterminado: 8; desde Linux 2.4)
El número máximo de intentos realizados para sondear el otro extremo de una conexión que ha sido cerrada por nuestro extremo.
tcp_reordering (entero; predeterminado: 3; desde Linux 2.4)
El máximo que un paquete puede estar desordenado en un flujo de paquetes TCP sin que TCP asuma pérdida de paquetes y entre en inicio lento. No es aconsejable cambiar este número. Esta es una métrica de detección de desorden de paquetes diseñada para minimizar retrocesos y retransmisiones innecesarias provocadas por el desorden de paquetes en una conexión.
tcp_retrans_collapse (booleano; predeterminado: habilitado; desde Linux 2.2)
Intenta enviar paquetes de tamaño completo durante la retransmisión.
tcp_retries1 (entero; predeterminado: 3; desde Linux 2.2)
El número de veces que TCP intentará retransmitir un paquete en una conexión establecida normalmente, sin el esfuerzo adicional de involucrar a las capas de red. Una vez que superamos este número de retransmisiones, primero hacemos que la capa de red actualice la ruta si es posible antes de cada nueva retransmisión. El valor predeterminado es el mínimo especificado por RFC de 3.
tcp_retries2 (entero; predeterminado: 15; desde Linux 2.2)
El número máximo de veces que se retransmite un paquete TCP en estado establecido antes de rendirse. El valor predeterminado es 15, lo que corresponde a una duración de aproximadamente entre 13 y 30 minutos, dependiendo del tiempo de espera de retransmisión. El mínimo especificado por RFC 1122 de 100 segundos se considera típicamente demasiado corto.
tcp_rfc1337 (booleano; predeterminado: deshabilitado; desde Linux 2.2)
Habilita el comportamiento de TCP conforme a RFC 1337. Cuando está deshabilitado, si se recibe un RST en estado TIME_WAIT, cerramos el socket inmediatamente sin esperar el final del período TIME_WAIT.
tcp_rmem (desde Linux 2.4)
Este es un vector de 3 enteros: [min, default, max]. Estos parámetros son utilizados por TCP para regular los tamaños del búfer de recepción. TCP ajusta dinámicamente el tamaño del búfer de recepción desde los valores predeterminados que se enumeran a continuación, dentro del rango de estos valores, según la memoria disponible en el sistema.
min
tamaño mínimo del búfer de recepción utilizado por cada socket TCP. El valor predeterminado es el tamaño de página del sistema. (En Linux 2.4, el valor predeterminado es 4 kB, reducido a PAGE_SIZE bytes en sistemas con poca memoria). Se utiliza para garantizar que en modo de presión de memoria, las asignaciones por debajo de este tamaño aún tengan éxito. Esto no se utiliza para limitar el tamaño del búfer de recepción declarado usando SO_RCVBUF en un socket.
default
el tamaño predeterminado del búfer de recepción para un socket TCP. Este valor anula el tamaño del búfer predeterminado inicial del net.core.rmem_default global genérico definido para todos los protocolos. El valor predeterminado es 87380 bytes. (En Linux 2.4, este se reducirá a 43689 en sistemas con poca memoria). Si se desean tamaños de búfer de recepción más grandes, este valor debe aumentarse (para afectar a todos los sockets). Para emplear ventanas TCP más grandes, se debe habilitar net.ipv4.tcp_window_scaling (predeterminado).
max
el tamaño máximo del búfer de recepción utilizado por cada socket TCP. Este valor no anula el net.core.rmem_max global. Esto no se utiliza para limitar el tamaño del búfer de recepción declarado usando SO_RCVBUF en un socket. El valor predeterminado se calcula utilizando la fórmula

max(87380, min(4 MB, tcp_mem[1]*PAGE_SIZE/128))

(En Linux 2.4, el valor predeterminado es 87380*2 bytes, reducido a 87380 en sistemas con poca memoria).
tcp_sack (booleano; predeterminado: habilitado; desde Linux 2.2)
Habilita los reconocimientos selectivos TCP de RFC 2018.
tcp_slow_start_after_idle (booleano; predeterminado: habilitado; desde Linux 2.6.18)
Si está habilitado, proporciona el comportamiento de RFC 2861 y agota el tiempo de espera de la ventana de congestión después de un período inactivo. Un período inactivo se define como el RTO actual (tiempo de espera de retransmisión). Si está deshabilitado, la ventana de congestión no agota el tiempo de espera después de un período inactivo.
tcp_stdurg (booleano; predeterminado: deshabilitado; desde Linux 2.2)
Si esta opción está habilitada, se utiliza la interpretación de RFC 1122 del campo de puntero urgente de TCP. Según esta interpretación, el puntero urgente apunta al último byte de datos urgentes. Si esta opción está deshabilitada, se utiliza la interpretación compatible con BSD del puntero urgente: el puntero urgente apunta al primer byte después de los datos urgentes. Habilitar esta opción puede provocar problemas de interoperabilidad.
tcp_syn_retries (entero; predeterminado: 6; desde Linux 2.2)
El número máximo de veces que se retransmitirán los SYN iniciales para un intento de conexión TCP activo. Este valor no debe ser superior a 255. El valor predeterminado es 6, lo que corresponde a reintentos durante aproximadamente 127 segundos. Antes de Linux 3.7, el valor predeterminado era 5, que (junto con el cálculo basado en otros parámetros del kernel) correspondía a aproximadamente 180 segundos.
tcp_synack_retries (entero; predeterminado: 5; desde Linux 2.2)
El número máximo de veces que
se retransmitirá. Este número no debe ser superior a 255.
tcp_syncookies (entero; predeterminado: 1; desde Linux 2.2)
Habilita syncookies TCP. El kernel debe compilarse con CONFIG_SYN_COOKIES. La función syncookies intenta proteger un socket de un ataque de inundación SYN. Esto debe usarse como último recurso, si acaso. Esto es una violación del protocolo TCP y entra en conflicto con otras áreas de TCP como las extensiones TCP. Puede causar problemas para clientes y retransmisores. No se recomienda como mecanismo de ajuste para servidores con mucha carga para ayudar con condiciones de sobrecarga o configuración incorrecta. Para alternativas recomendadas, consulte tcp_max_syn_backlog, tcp_synack_retries y tcp_abort_on_overflow. Establézcalo en uno de los siguientes valores:
0
Deshabilita syncookies TCP.
1
Envía syncookies cuando la cola de backlog syn de un socket se desborda.
2
(desde Linux 3.12) Envía syncookies incondicionalmente. Esto puede ser útil para pruebas de red.
tcp_timestamps (entero; predeterminado: 1; desde Linux 2.2)
Establézcalo en uno de los siguientes valores para habilitar o deshabilitar las marcas de tiempo TCP de RFC 1323:
0
Deshabilita las marcas de tiempo.
1
Habilita las marcas de tiempo según lo definido en RFC1323 y utiliza un desplazamiento aleatorio para cada conexión en lugar de solo usar la hora actual.
2
Al igual que el valor 1, pero sin desplazamientos aleatorios. Establecer tcp_timestamps en este valor tiene sentido desde Linux 4.10.
tcp_tso_win_divisor (entero; predeterminado: 3; desde Linux 2.6.9)
Este parámetro controla qué porcentaje de la ventana de congestión puede ser consumido por un único paquete de descarga de segmentación TCP (TSO). El ajuste de este parámetro es un compromiso entre la ráfaga y la construcción de paquetes TSO más grandes.
tcp_tw_recycle (booleano; predeterminado: deshabilitado; Linux 2.4 a Linux 4.11)
Habilita el reciclaje rápido de sockets TIME_WAIT. No se recomienda habilitar esta opción ya que la IP remota puede no utilizar marcas de tiempo monótonamente crecientes (dispositivos detrás de NAT, dispositivos con desplazamientos de marca de tiempo por conexión). Consulte RFC 1323 (PAWS) y RFC 6191.
tcp_tw_reuse (booleano; predeterminado: deshabilitado; desde Linux 2.4.19/2.6)
Permite reutilizar sockets TIME_WAIT para nuevas conexiones cuando es seguro desde el punto de vista del protocolo. No debe modificarse sin el consejo o la solicitud de expertos técnicos.
tcp_vegas_cong_avoid (booleano; predeterminado: deshabilitado; Linux 2.2 a Linux 2.6.13)
Habilita el algoritmo de evitación de congestión TCP Vegas. TCP Vegas es un cambio solo en el lado del emisor para TCP que anticipa la aparición de congestión mediante la estimación del ancho de banda. TCP Vegas ajusta la tasa de envío modificando la ventana de congestión. TCP Vegas debería proporcionar menos pérdida de paquetes, pero no es tan agresivo como TCP Reno.
tcp_westwood (booleano; predeterminado: deshabilitado; Linux 2.4.26/2.6.3 a Linux 2.6.13)
Habilita el algoritmo de control de congestión TCP Westwood+. TCP Westwood+ es una modificación solo en el lado del emisor de la pila de protocolos TCP Reno que optimiza el rendimiento del control de congestión TCP. Se basa en la estimación del ancho de banda de extremo a extremo para establecer la ventana de congestión y el umbral de inicio lento después de un episodio de congestión. Utilizando esta estimación, TCP Westwood+ establece adaptativamente un umbral de inicio lento y una ventana de congestión que tiene en cuenta el ancho de banda utilizado en el momento en que se experimenta la congestión. TCP Westwood+ aumenta significativamente la equidad con respecto a TCP Reno en redes cableadas y el rendimiento en enlaces inalámbricos.
tcp_window_scaling (booleano; predeterminado: habilitado; desde Linux 2.2)
Habilita el escalado de ventana TCP RFC 1323. Esta función permite el uso de una ventana grande (> 64 kB) en una conexión TCP, si el otro extremo la soporta. Normalmente, el campo de longitud de ventana de 16 bits en la cabecera TCP limita el tamaño de la ventana a menos de 64 kB. Si se desean ventanas más grandes, las aplicaciones pueden aumentar el tamaño de sus búferes de socket y se empleará la opción de escalado de ventana. Si tcp_window_scaling está deshabilitado, TCP no negociará el uso del escalado de ventana con el otro extremo durante el establecimiento de la conexión.
tcp_wmem (desde Linux 2.4)
Este es un vector de 3 enteros: [min, default, max]. Estos parámetros son utilizados por TCP para regular los tamaños de los búferes de envío. TCP ajusta dinámicamente el tamaño del búfer de envío desde los valores predeterminados que se enumeran a continuación, dentro del rango de estos valores, según la memoria disponible.
min
Tamaño mínimo del búfer de envío utilizado por cada socket TCP. El valor predeterminado es el tamaño de página del sistema. (En Linux 2.4, el valor predeterminado es 4 kB). Este valor se utiliza para garantizar que en modo de presión de memoria, las asignaciones por debajo de este tamaño sigan teniendo éxito. Esto no se utiliza para limitar el tamaño de búfer de envío declarado usando SO_SNDBUF en un socket.
default
El tamaño predeterminado del búfer de envío para un socket TCP. Este valor sobrescribe el tamaño de búfer predeterminado inicial del global genérico /proc/sys/net/core/wmem_default definido para todos los protocolos. El valor predeterminado es 16 kB. Si se desean tamaños de búfer de envío más grandes, este valor debe aumentarse (para afectar a todos los sockets). Para emplear búferes TCP grandes, el valor de /proc/sys/net/ipv4/tcp_window_scaling debe establecerse en un valor distinto de cero (predeterminado).
max
El tamaño máximo del búfer de envío utilizado por cada socket TCP. Este valor no anula el valor en /proc/sys/net/core/wmem_max. Esto no se utiliza para limitar el tamaño del búfer de envío declarado usando SO_SNDBUF en un socket. El valor predeterminado se calcula usando la fórmula

max(65536, min(4 MB, tcp_mem[1]*PAGE_SIZE/128))

(En Linux 2.4, el valor predeterminado es 128 kB, reducido a 64 kB dependiendo de los sistemas con poca memoria).
tcp_workaround_signed_windows (booleano; predeterminado: deshabilitado; desde Linux 2.6.26)
Si está habilitado, asume que la no recepción de una opción de escalado de ventana significa que el TCP remoto está roto y trata la ventana como una cantidad con signo. Si está deshabilitado, asume que el TCP remoto no está roto incluso si no recibimos una opción de escalado de ventana de él.

Opciones de socket

Para establecer u obtener una opción de socket TCP, llame a getsockopt(2) para leer o setsockopt(2) para escribir la opción con el argumento de nivel de opción establecido en IPPROTO_TCP. A menos que se indique lo contrario, optval es un puntero a un int. Además, la mayoría de las opciones de socket IPPROTO_IP son válidas en sockets TCP. Para más información, consulte ip(7).

A continuación se presenta una lista de opciones de socket específicas de TCP. Para obtener detalles de algunas otras opciones de socket que también son aplicables a sockets TCP, consulte socket(7).

TCP_CONGESTION (desde Linux 2.6.13)
El argumento para esta opción es una cadena. Esta opción permite al llamador establecer el algoritmo de control de congestión TCP a utilizar, por socket. Los procesos no privilegiados están restringidos a elegir uno de los algoritmos en tcp_allowed_congestion_control (descrito anteriormente). Los procesos privilegiados (CAP_NET_ADMIN) pueden elegir entre cualquiera de los algoritmos de control de congestión disponibles (consulte la descripción de tcp_available_congestion_control anterior).
TCP_CORK (desde Linux 2.2)
Si está activada, no envía paquetes parciales. Todos los paquetes parciales en cola se envían cuando la opción se desactiva de nuevo. Esto es útil para anteponer cabeceras antes de llamar a sendfile(2), o para optimización de rendimiento. Como implementado actualmente, hay un límite de 200 milisegundos en el tiempo que la salida se corcha por TCP_CORK. Si se alcanza este límite, los datos en cola se transmiten automáticamente. Esta opción se puede combinar con TCP_NODELAY solo desde Linux 2.5.71. Esta opción no debe utilizarse en código destinado a ser portátil.
TCP_DEFER_ACCEPT (desde Linux 2.4)
Permite que un oyente se despierte solo cuando llegan datos al socket. Toma un valor entero (segundos), esto puede limitar el número máximo de intentos que TCP hará para completar la conexión. Esta opción no debe utilizarse en código destinado a ser portátil.
TCP_INFO (desde Linux 2.4)
Se utiliza para recopilar información sobre este socket. El kernel devuelve una struct tcp_info como se define en el archivo /usr/include/linux/tcp.h. Esta opción no debe utilizarse en código destinado a ser portátil.
TCP_KEEPCNT (desde Linux 2.4)
El número máximo de sondeos keepalive que TCP debe enviar antes de descartar la conexión. Esta opción no debe utilizarse en código destinado a ser portátil.
TCP_KEEPIDLE (desde Linux 2.4)
El tiempo (en segundos) que la conexión debe permanecer inactiva antes de que TCP comience a enviar sondeos keepalive, si la opción de socket SO_KEEPALIVE se ha establecido en este socket. Esta opción no debe utilizarse en código destinado a ser portátil.
TCP_KEEPINTVL (desde Linux 2.4)
El tiempo (en segundos) entre sondeos keepalive individuales. Esta opción no debe utilizarse en código destinado a ser portátil.
TCP_LINGER2 (desde Linux 2.4)
TCP_FINCNT
El tiempo de vida de los sockets en estado FIN_WAIT2 huérfanos. Esta opción se puede utilizar para anular la configuración global del sistema en el archivo /proc/sys/net/ipv4/tcp_fin_timeout para este socket. Esto no debe confundirse con la opción de nivel de socket(7) SO_LINGER. Esta opción no debe usarse en código destinado a ser portátil.
TCP_MAXSEG
El tamaño máximo de segmento para los paquetes TCP salientes. En Linux 2.2 y anteriores, y en Linux 2.6.28 y posteriores, si esta opción se establece antes del establecimiento de la conexión, también cambia el valor de MSS anunciado al otro extremo en el paquete inicial. Los valores mayores que la MTU de la interfaz (eventual) no tienen efecto. TCP también impondrá sus límites mínimos y máximos sobre el valor proporcionado.
TCP_NODELAY
Si se establece, deshabilita el algoritmo de Nagle. Esto significa que los segmentos se envían siempre lo más rápido posible, incluso si solo hay una pequeña cantidad de datos. Cuando no se establece, los datos se almacenan en búfer hasta que hay una cantidad suficiente para enviar, evitando así el envío frecuente de paquetes pequeños, lo que resulta en una pobre utilización de la red. Esta opción es anulada por TCP_CORK; sin embargo, establecer esta opción fuerza un vaciado explícito de la salida pendiente, incluso si TCP_CORK está actualmente establecido.
TCP_QUICKACK (desde Linux 2.4.4)
Habilita el modo quickack si se establece o deshabilita el modo quickack si se borra. En modo quickack, los acuses de recibo se envían inmediatamente, en lugar de retrasarse si es necesario de acuerdo con la operación normal de TCP. Esta bandera no es permanente, solo permite un cambio hacia o desde el modo quickack. La operación posterior del protocolo TCP volverá a entrar/salir del modo quickack dependiendo del procesamiento interno del protocolo y de factores como la ocurrencia de tiempos de espera de acuse de recibo retrasado y transferencia de datos. Esta opción no debe usarse en código destinado a ser portátil.
TCP_SYNCNT (desde Linux 2.4)
Establece el número de retransmisiones de SYN que TCP debe enviar antes de abortar el intento de conexión. No puede exceder de 255. Esta opción no debe usarse en código destinado a ser portátil.
TCP_SAVE_SYN (desde Linux 4.3)
Guarda el contenido del paquete SYN entrante del socket de escucha hasta que se lea con TCP_SAVED_SYN una vez. Podría establecerse antes o después de la llamada a listen(2).
TCP_SAVED_SYN (desde Linux 4.3)
Lee el contenido del paquete SYN guardado por TCP_SAVE_SYN. Las cabeceras SYN guardadas se liberan después de la primera llamada. Los datos devueltos en TCP_SAVED_SYN son cabeceras de red (IPv4/IPv6) y TCP.
TCP_USER_TIMEOUT (desde Linux 2.6.37)
Esta opción toma un argumento de tipo unsigned int. Cuando el valor es mayor que 0, especifica la cantidad máxima de tiempo en milisegundos que los datos transmitidos pueden permanecer sin acuse de recibo, o los datos en búfer pueden permanecer sin transmitir (debido a una ventana de tamaño cero) antes de que TCP cierre forzosamente la conexión correspondiente y devuelva ETIMEDOUT a la aplicación. Si el valor de la opción se especifica como 0, TCP utilizará el valor predeterminado del sistema.
Aumentar los tiempos de espera del usuario permite que una conexión TCP sobreviva a períodos extendidos sin conectividad de extremo a extremo. Disminuir los tiempos de espera del usuario permite a las aplicaciones "fallar rápido", si así lo desean. De lo contrario, la falla puede tardar hasta 20 minutos con los valores predeterminados actuales del sistema en un entorno WAN normal.
Esta opción se puede establecer en cualquier estado de una conexión TCP, pero es efectiva solo durante los estados sincronizados de una conexión (ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING y LAST-ACK). Además, cuando se usa con la opción de keepalive de TCP (SO_KEEPALIVE), TCP_USER_TIMEOUT anulará keepalive para determinar cuándo cerrar una conexión debido a un error de keepalive.
La opción no tiene efecto sobre cuándo TCP retransmite un paquete, ni sobre cuándo se envía una sonda de keepalive.
Esta opción, como muchas otras, será heredada por el socket devuelto por accept(2), si se estableció en el socket de escucha.
Se pueden encontrar más detalles sobre la característica de tiempo de espera del usuario en RFC 793 y RFC 5482 ("TCP User Timeout Option").
TCP_WINDOW_CLAMP (desde Linux 2.4)
Limita el tamaño de la ventana anunciada a este valor. El kernel impone un tamaño mínimo de SOCK_MIN_RCVBUF/2. Esta opción no debe usarse en código destinado a ser portátil.
TCP_FASTOPEN (desde Linux 3.6)
Esta opción habilita Fast Open (RFC 7413) en el socket del oyente. El valor especifica la longitud máxima de SYNs pendientes (similar al argumento backlog en listen(2)). Una vez habilitado, el socket del oyente otorga la cookie de TCP Fast Open en un SYN entrante con la opción TCP Fast Open.
Más importante aún, acepta los datos en SYN con una cookie Fast Open válida y responde SYN-ACK reconociendo tanto los datos como la secuencia SYN. accept(2) devuelve un socket disponible para lectura y escritura cuando el handshake aún no se ha completado. Por lo tanto, el intercambio de datos puede comenzar antes de que se complete el handshake. Esta opción requiere habilitar la soporte del lado del servidor en sysctl net.ipv4.tcp_fastopen (ver arriba). Para el soporte del lado del cliente de TCP Fast Open, consulte send(2) MSG_FASTOPEN o TCP_FASTOPEN_CONNECT a continuación.
TCP_FASTOPEN_CONNECT (desde Linux 4.11)
Esta opción habilita una forma alternativa de realizar Fast Open en el lado activo (cliente). Cuando esta opción está habilitada, connect(2) se comportará de manera diferente según si una cookie de Fast Open está disponible para el destino.
Si no hay una cookie disponible (es decir, primer contacto con el destino), connect(2) se comporta como de costumbre enviando un SYN inmediatamente, excepto que el SYN incluiría una opción de cookie Fast Open vacía para solicitar una cookie.
Si hay una cookie disponible, connect(2) devolverá 0 inmediatamente, pero la transmisión del SYN se pospondrá. Una llamada posterior a write(2) o sendmsg(2) activará un SYN con datos más cookie en la opción Fast Open. En otras palabras, la operación de conexión real se pospondrá hasta que se proporcionen datos.
Nota: Si bien esta opción está diseñada para mayor comodidad, habilitarla cambia los comportamientos y ciertas llamadas al sistema pueden establecer diferentes valores de errno. Con la cookie presente, write(2) o sendmsg(2) debe llamarse inmediatamente después de connect(2) para enviar SYN+datos para completar 3WHS y establecer la conexión. Llamar a read(2) inmediatamente después de connect(2) sin write(2) hará que el socket bloqueante se bloquee para siempre.
La aplicación debe establecer la opción de socket TCP_FASTOPEN_CONNECT antes de llamar a write(2) o sendmsg(2), o llamar a write(2) o sendmsg(2) con la bandera MSG_FASTOPEN directamente, en lugar de ambas en la misma conexión.
Aquí está el flujo de llamadas típico con esta nueva opción:

s = socket();
setsockopt(s, IPPROTO_TCP, TCP_FASTOPEN_CONNECT, 1, ...);
connect(s);
write(s);  /* write() siempre debe seguir a connect()
            * para activar el envío de SYN.  */
read(s)/write(s);
/* ... */
close(s);

API de Sockets

TCP proporciona un soporte limitado para datos fuera de banda, en forma de (un solo byte de) datos urgentes. En Linux, esto significa que si el otro extremo envía datos urgentes más nuevos, los datos urgentes antiguos se insertan como datos normales en el flujo (incluso cuando SO_OOBINLINE no está establecido). Esto difiere de las pilas basadas en BSD.

Linux utiliza la interpretación compatible con BSD del campo del puntero urgente por defecto. Esto viola RFC 1122, pero es necesario para la interoperabilidad con otras pilas. Se puede cambiar a través de /proc/sys/net/ipv4/tcp_stdurg.

Es posible examinar los datos fuera de banda utilizando el flag MSG_PEEK de recv(2).

Desde Linux 2.4, Linux admite el uso de MSG_TRUNC en el argumento flags de recv(2) (y recvmsg(2)). Este flag hace que los bytes de datos recibidos se descarten, en lugar de pasarlos a un búfer proporcionado por el llamador. Desde Linux 2.4.4, MSG_TRUNC también tiene este efecto cuando se usa junto con MSG_OOB para recibir datos fuera de banda.

Ioctls

Las siguientes llamadas ioctl(2) devuelven información en value. La sintaxis correcta es:

int value;
error = ioctl(tcp_socket, ioctl_type, &value);

ioctl_type es uno de los siguientes:

SIOCINQ
Devuelve la cantidad de datos en cola sin leer en el búfer de recepción. El socket no debe estar en estado LISTEN, de lo contrario se devuelve un error (EINVAL). SIOCINQ está definido en <linux/sockios.h>. Alternativamente, puede usar el sinónimo FIONREAD, definido en <sys/ioctl.h>.
SIOCATMARK
Devuelve verdadero (es decir, value no es cero) si el flujo de datos entrante está en la marca urgente.
Si la opción de socket SO_OOBINLINE está establecida, y SIOCATMARK devuelve verdadero, entonces la próxima lectura del socket devolverá los datos urgentes. Si la opción de socket SO_OOBINLINE no está establecida, y SIOCATMARK devuelve verdadero, entonces la próxima lectura del socket devolverá los bytes que siguen a la urgencia.
tcp(7) — Arch Linux man pages

NAME

tcp - Transmission Control Protocol

SYNOPSIS

#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

tcp_socket = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);

DESCRIPTION

The TCP protocol is a connection-oriented, reliable, byte-stream protocol that is used for the transfer of data between applications.

TCP supports the following socket options. These can be obtained with getsockopt(2) and set with setsockopt(2).

TCP_NODELAY
Enable/disable Nagle's algorithm. This option takes an integer value. The default is false (Nagle's algorithm is enabled). If set to true, the user is telling the protocol implementation that it may send small amounts of data at any time. This will disable the Nagle algorithm and may result in a larger number of small packets being sent. This is useful for applications that require low latency (e.g., interactive games). Setting this option to true may harm throughput. This option is not supported for listening sockets.
TCP_MAXSEG
Set or receive the maximum segment size (MSS). This option takes an integer value. This is the largest amount of data, in bytes, that TCP will send in a single segment. The kernel will automatically determine the MSS based on the MTU of the underlying path. This option can be used to manually set the MSS, for example, to reduce the size of the packets being sent. Note that the kernel may still override this value based on network conditions.
TCP_CORK
Enable/disable the corking of TCP sends. This option takes an integer value. The default is false (disabled). When enabled (set to true), the kernel will try to collect all data sent via write(2) calls into a single segment, delaying sending the segment until either the buffer is full, the socket is closed, or TCP_NODELAY is enabled. This can be useful for protocols that send multiple small pieces of data that logically belong together. See sendfile(2) for more details.
TCP_KEEPIDLE
The TCP_KEEPIDLE option defines the time in seconds the connection must be idle before TCP probes the connection by sending keepalive messages. An idle connection is one on which no data has been received from the other end for TCP_KEEPIDLE seconds. This option expects an integer value.
TCP_KEEPINTVL
The TCP_KEEPINTVL option defines the interval in seconds between keepalive probes if the other end does not acknowledge them. This option expects an integer value.
TCP_KEEPCNT
The TCP_KEEPCNT option defines the number of unacknowledged keepalive probes that may be sent before the connection is considered dead. This option expects an integer value.
TCP_SYNCNT
The TCP_SYNCNT option defines the number of times the TCP initial connection probe (SYN) will be retransmitted. This option expects an integer value.
TCP_TIME_WAIT2_ABORT_LIMIT
This option controls the maximum number of TCP connections in TIME_WAIT state. If this limit is reached, new connections may be aborted. This option expects an integer value.
TCP_USER_TIMEOUT
This option controls the maximum amount of time in milliseconds that a TCP connection can remain in the ESTABLISHED state without any data transfer. If this timeout is reached, the connection is considered dead and TCP will send an RST to the other side. This option expects an integer value.
TCP_CONGESTION
Set the congestion control algorithm. This option takes a string value representing the name of the congestion control algorithm (e.g., "reno", "cubic", "bbr").
TCP_MD5SIG
Enable TCP MD5 Signature verification (RFC 2385). This option takes a structure value that specifies the authentication key. The key must be provided as a null-terminated string.
TCP_QUICKACK
Enable/disable the quick acknowledgement mode. When enabled (set to true), TCP will immediately acknowledge received data, even if it is not yet processed by the application. This can improve performance in high-latency networks.
TCP_DEFER_ACCEPT
Enable/disable the defer accept mode for listening sockets. When enabled (set to true), the server will not accept incoming connections until data has been received from the client. This can help protect against certain types of denial-of-service attacks. This option is only valid on listening sockets.
TCP_WINDOW_CLAMP
Clamp the receive window size to a specified maximum value. This option is useful for preventing excessive memory usage in high-bandwidth, high-latency networks.
TCP_INFO
Retrieve TCP connection information. This option returns a structure containing various statistics about the TCP connection, such as the congestion window size, round-trip time, and retransmission count.
TCP_QUICKRST
Enable/disable the quick reset mode. When enabled (set to true), TCP will send an RST packet immediately upon receiving data on a closed connection, rather than waiting for a timeout. This can help to quickly terminate connections that are no longer needed.
TCP_FASTOPEN
Enable/disable TCP Fast Open. Fast Open allows clients to send data in the initial SYN packet, reducing latency for subsequent connections. This option takes an integer value that specifies the maximum number of Fast Open connections to allow.
TCP_RECV_BUF_QUEUE_MAX_SIZE
Set the maximum size of the receive buffer queue. This option takes an integer value.
TCP_SEND_BUF_QUEUE_MAX_SIZE
Set the maximum size of the send buffer queue. This option takes an integer value.
SIOCATMARK
Check if the read pointer is at the urgent mark. This ioctl returns a non-zero value if the read pointer is at the urgent mark, and zero otherwise. This is useful for applications that need to handle urgent data. Note that to actually read the urgent data requires the recv(MSG_OOB) flag).
Note that a read never reads across the urgent mark. If an application is informed of the presence of urgent data via select(2) (using the exceptfds argument) or through delivery of a SIGURG signal, then it can advance up to the mark using a loop which repeatedly tests SIOCATMARK and performs a read (requesting any number of bytes) as long as SIOCATMARK returns false.
SIOCOUTQ
Returns the amount of unsent data in the socket send queue. The socket must not be in LISTEN state, otherwise an error (EINVAL) is returned. SIOCOUTQ is defined in <linux/sockios.h>. Alternatively, you can use the synonymous TIOCOUTQ, defined in <sys/ioctl.h>.

Error handling

When a network error occurs, TCP tries to resend the packet. If it doesn't succeed after some time, either ETIMEDOUT or the last received error on this connection is reported.

Some applications require a quicker error notification. This can be enabled with the IPPROTO_IP level IP_RECVERR socket option. When this option is enabled, all incoming errors are immediately passed to the user program. Use this option with care — it makes TCP less tolerant to routing changes and other normal network conditions.

ERRORS

EAFNOTSUPPORT
Passed socket address type in sin_family was not AF_INET.
EPIPE
The other end closed the socket unexpectedly or a read is executed on a shut down socket.
ETIMEDOUT
The other end didn't acknowledge retransmitted data after some time.

Any errors defined for ip(7) or the generic socket layer may also be returned for TCP.

VERSIONS

Support for Explicit Congestion Notification, zero-copy sendfile(2), reordering support and some SACK extensions (DSACK) were introduced in Linux 2.4. Support for forward acknowledgement (FACK), TIME_WAIT recycling, and per-connection keepalive socket options were introduced in Linux 2.3.
