NOMBRE

tc-stab - Manipulaciones genéricas de tablas de tamaño

SINOPSIS

tc qdisc add ... stab
[ mtu BYTES ] [ tsize SLOTS ]
[ mpu BYTES ] [ overhead BYTES ]
[ linklayer { adsl | atm | ethernet } ] ...

OPCIONES

Para la descripción de BYTES, consulte la sección UNITS de tc(8).

mtu

tamaño máximo de paquete para el cual creamos la tabla de tamaño, se asume 2048 si no se especifica explícitamente
tsize

tamaño de tabla requerido, se asume 512 si no se especifica explícitamente
mpu

tamaño mínimo de paquete utilizado en los cálculos
overhead

sobrecarga por paquete (puede ser negativa) utilizada en los cálculos
linklayer

especificación de capa de enlace requerida.

DESCRIPCIÓN

Las tablas de tamaño permiten la manipulación de los tamaños de paquete, tal como son vistos por el marco completo del planificador (por supuesto, el tamaño real del paquete permanece igual). El tamaño de paquete ajustado se calcula una sola vez, cuando una qdisc encola el paquete. La primera cola raíz lo inicializa al tamaño real del paquete.

Cada qdisc puede usar una tabla de tamaño diferente, pero el tamaño ajustado se almacena en un área compartida por toda la jerarquía de qdiscs adjuntas a la interfaz. El efecto es que si tiene una configuración así, la última qdisc con un stab en una cadena "gana". Por ejemplo, considere HFSC con un pfifo simple adjunto a una de sus clases hoja. Si esa qdisc pfifo tiene definido un stab, anulará las longitudes calculadas durante la encolación de HFSC; y a su vez, cada vez que HFSC intente desencolar un paquete, usará un tamaño potencialmente inválido en sus cálculos. Las configuraciones normales generalmente incluirán un stab definido solo en la qdisc raíz, pero la anulación adicional proporciona flexibilidad extra para configuraciones menos usuales.

La tabla de tamaño inicial es calculada por la herramienta tc utilizando los parámetros mtu y tsize. El algoritmo establece el tamaño de cada ranura a la potencia de 2 más pequeña, de modo que el mtu completo sea cubierto por la tabla de tamaño. Ni tsize ni mtu tienen que ser potencias de 2, por lo que la tabla de tamaño generalmente soportará más de lo requerido por mtu.

Por ejemplo, con mtu = 1500 y tsize = 128, se creará una tabla con 128 ranuras, donde la ranura 0 corresponderá a tamaños 0-16, la ranura 1 a 17 - 32, ..., la ranura 127 a 2033 - 2048. Los tamaños asignados a cada ranura dependen del parámetro linklayer.

El cálculo de Stab también es seguro para un caso inusual, cuando un tamaño asignado a una ranura sería mayor que 2^16-1 (aunque perderá precisión).

Durante la parte del kernel del ajuste del tamaño del paquete, se añadirá overhead al tamaño original, y luego se calculará la ranura. Si el tamaño causara un desbordamiento, se utilizarán más de 1 ranura para obtener el tamaño final. Esto, por supuesto, afectará la precisión, pero es solo una protección contra situaciones inusuales.

Actualmente hay dos métodos para crear los valores almacenados en la tabla de tamaño: ethernet y atm (adsl):

ethernet

Esto es básicamente una correspondencia 1 a 1, así que siguiendo nuestro ejemplo anterior (ignorando mpu por un momento) la ranura 0 tendría 8, la ranura 1 tendría 16 y así sucesivamente, hasta la ranura 127 con 2048. Tenga en cuenta que se debe especificar mpu > 0, y las ranuras que obtendrían menos que el especificado por mpu obtendrán mpu en su lugar. Si no especifica mpu, la tabla de tamaño no se creará en absoluto (no haría ninguna diferencia), aunque cualquier valor de overhead será respetado durante los cálculos.
atm, adsl

La capa de enlace ATM consta de celdas de 53 bytes, donde cada una proporciona 48 bytes para datos útiles. Además, todas las celdas deben ser utilizadas completamente, por lo que la última se rellena si es necesario.

Cuando se calcula la tabla de tamaño, se asigna a una ranura el tamaño ajustado que encaja correctamente en la menor cantidad de celdas. Por ejemplo, un paquete de 100 bytes requiere tres cargas útiles de 48 bytes, por lo que el tamaño final requeriría 3 celdas ATM, 159 bytes.

Para las tablas de tamaño ATM, ranuras de 16 bytes son perfectamente suficientes. Los valores predeterminados de mtu y tsize crean ranuras de 4 bytes.

SOBRECARGAS TÍPICAS

Los siguientes valores son típicos para diferentes escenarios adsl (basados en [1] y [2]):

basado en LLC:
PPPoA - 14 (PPP - 2, ATM - 12)
PPPoE - 40+ (PPPoE - 8, ATM - 18, ethernet 14, posiblemente FCS - 4+relleno)
Bridged - 32 (ATM - 18, ethernet 14, posiblemente FCS - 4+relleno)
IPoA - 16 (ATM - 16)
basado en VC Mux:
PPPoA - 10 (PPP - 2, ATM - 8)
PPPoE - 32+ (PPPoE - 8, ATM - 10, ethernet 14, posiblemente FCS - 4+relleno)
Bridged - 24+ (ATM - 10, ethernet 14, posiblemente FCS - 4+relleno)
IPoA - 8 (ATM - 8)

Hay algunas cosas importantes con respecto a las sobrecargas anteriores:

  • IPoA en caso LLC requiere SNAP, en lugar de LLC-NLPID (ver rfc2684) - esta es la razón por la que en realidad ocupa más espacio que PPPoA.
  • En casos raros, FCS puede ser preservado en protocolos que incluyen tramas Ethernet (Bridged y PPPoE). En tal situación, también se debe incluir cualquier relleno específico de Ethernet que garantice un tamaño de trama de 64 bytes (ver RFC2684). En otras palabras, también garantiza que cualquier paquete que envíe ocupará un mínimo de 2 celdas atm. Debería configurar mpu en consecuencia.
  • Cuando se consulta la tabla de tamaño, y está modelando el tráfico para otro módem/enrutador, ya se agregará una cabecera Ethernet (sin relleno) a la longitud inicial del paquete. Debería compensar eso restando 14 de las sobrecargas anteriores en este caso. Si está modelando directamente en el enrutador (por ejemplo, con un módem USB speedtouch), está utilizando una interfaz ppp cruda sin capa 2 subyacente, por lo que no se agregará nada.

    Para explicaciones más detalladas, consulte [1] y [2].

CONSIDERACIONES PARA TARJETAS ETHERNET

A menudo se olvida que las tarjetas de red modernas (incluso las baratas en placas base de escritorio) y/o sus controladores a menudo admiten diferentes mecanismos de descarga. En el contexto de la modelación de tráfico, 'tso' y 'gso' pueden causar efectos indeseables, debido a que los segmentos TCP masivos se consideran durante la modelación de tráfico (incluidos los cálculos de stab). Para interfaces de enlace ascendente lentas, es bueno usar ethtool para desactivar las funciones de descarga.

NAME

tc-stab - traffic control stability primitives

SYNOPSIS

tc [ OPTIONS ] filter ...

tc [ OPTIONS ] class ...

tc [ OPTIONS ] qdisc ...

OPTIONS

None

DESCRIPTION

The tc-stab program is a traffic control stability primitive. It is used to configure traffic control policies on network interfaces.

The tc-stab program is a part of the iproute2 suite of network configuration tools.

TYPICAL OVERHEADS

The overhead of using tc-stab is minimal. The program itself is small and efficient, and the traffic control policies it configures have a negligible impact on network performance.

ETHERNET CARDS CONSIDERATIONS

When configuring traffic control policies on Ethernet cards, it is important to consider the capabilities of the card. Some cards may have hardware support for certain traffic control features, while others may not. It is important to consult the documentation for your Ethernet card to determine its capabilities.
