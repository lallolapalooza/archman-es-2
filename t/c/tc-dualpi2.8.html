NOMBRE

DUALPI2 - Controlador Proporcional Integral (PI) de Doble Cola AQM - Mejorado con un cuadrado

SINOPSIS


tc qdisc ... dualpi2
[ limit PAQUETES ]
[ memlimit BYTES ]
[ coupling_factor NUMERO ]
[ step_thresh TIEMPO|PAQUETES ]
[ min_qlen_step PAQUETES ]
[ drop_on_overload | overflow ]
[ drop_enqueue | drop_dequeue ]
[ l4s_ect | any_ect ]
[ classic_protection PORCENTAJE ]
[ max_rtt TIEMPO [ typical_rtt TIEMPO ]]
[ target TIEMPO ]
[ tupdate TIEMPO ]
[ alpha float ]
[ beta float ]
[ split_gso | no_split_gso ]

DESCRIPCIÓN

DUALPI2 AQM es una combinación del DUALQ Coupled-AQM con un AQM base PI2. El AQM PI2 (cuyos detalles se pueden encontrar en el artículo citado a continuación) es a su vez una extensión y una simplificación del AQM PIE. PI2 hace innecesarias muchas heurísticas de PIE, al mismo tiempo que es capaz de controlar controles de congestión escalables como TCP-Prague. Con PI2, tanto Reno/Cubic se pueden usar en paralelo con Prague, manteniendo la equidad de ventanas. DUALQ proporciona separación de latencia entre flujos de baja latencia Prague y flujos Reno/Cubic que necesitan una cola más grande. Los principales objetivos de diseño son:

  • Soporte para control de congestión L4S - Baja Pérdida, Baja Latencia y Escalable
  • Opción DualQ para separar el tráfico L4S en una cola de baja latencia (cola L), sin perjudicar el tráfico restante que se programa en la cola clásica (cola C) debido al acoplamiento de la congestión
  • Estrategias de sobrecarga configurables
  • Uso del tiempo de permanencia para estimar de forma fiable el retraso de la cola
  • Implementación sencilla
  • Estabilidad garantizada y rápida capacidad de respuesta

Los parámetros detallados de PI2 (alpha, beta y tupdate) de DualPI2 son difíciles de ajustar correctamente y normalmente dan malos resultados si simplemente se intentan o se adivinan. Estos parámetros deben calcularse para formar un conjunto coherente con un objetivo típico en mente. DualPI2 tiene un conjunto de parámetros predeterminados que se pueden usar para Internet en general, donde el RTT máximo es de alrededor de 100 ms y el RTT típico es de alrededor de 15 ms. Se recomienda encarecidamente utilizar los parámetros auxiliares max_rtt y typical_rtt (o target) si su implementación se desvía de los objetivos anteriores (por ejemplo, en un centro de datos). Estos auxiliares se utilizan para proporcionar los parámetros PI2 teóricamente óptimos (alpha, beta y tupdate) para esos objetivos, y que se pueden utilizar como base para ajustes adicionales, experimentación y pruebas si se desea.

ALGORITMO

DUALPI2 está diseñado para proporcionar baja pérdida y baja latencia al tráfico L4S, sin perjudicar el tráfico clásico. Cada intervalo de actualización, se calcula una nueva probabilidad base interna basada en el retraso de la cola. La probabilidad base se actualiza con una delta basada en la diferencia entre el retraso de cola actual y el retraso target, y el crecimiento de la cola en comparación con el retraso de cola durante el intervalo tupdate anterior. El factor de ganancia integral alpha se utiliza para corregir lo suficientemente lento cualquier error persistente de cola a la demora objetivo especificada por el usuario, mientras que el factor de ganancia proporcional beta se utiliza para compensar rápidamente los cambios en la cola (crecimiento o decrecimiento).

La probabilidad base actualizada se utiliza como entrada para decidir marcar y descartar paquetes. DUALPI2 escala la probabilidad calculada para cada una de las dos colas en consecuencia. Para la cola L, la probabilidad se multiplica por un coupling_factor, mientras que para la cola C, se eleva al cuadrado para compensar la ecuación de tasa de raíz cuadrada de Reno/Cubic. El identificador ECT ( l4s_ect|any_ect ) se utiliza para clasificar el tráfico en las respectivas colas.

Si DUALPI2 AQM ha detectado sobrecarga (cuando se envía tráfico excesivo no sensible), puede señalar congestión utilizando únicamente drop, independientemente del campo ECN, o alternativamente limitar la probabilidad de descarte y dejar que la cola crezca y eventualmente overflow (como tail-drop).

Se pueden encontrar detalles adicionales en el RFC citado a continuación.

PARÁMETROS

limit PAQUETES
Limita el número de paquetes que se pueden encolar. Los paquetes entrantes serán descartados una vez que se alcance este límite. Este límite es común para la cola L y la cola C. Por defecto es 10000 paquetes. Esto equivale a unos 125 ms de retraso en un enlace de 1 Gbps.
memlimit BYTES
Limita la cantidad total de memoria que se puede utilizar. Los paquetes entrantes serán descartados una vez que se alcance este límite de memoria. Este límite de memoria es común para la cola L y la cola C. Por defecto es 10000 * MTU de la interfaz en bytes.
coupling_factor NUMERO
Establece el factor de tasa de acoplamiento entre Clásico y L4S. Por defecto es 2
l4s_ect|any_ect
Configura el clasificador ECT. Los paquetes cuya codepoint ECT coincida con esto se envían a la cola L, donde reciben un marcado escalable. Por defecto es l4s_ect, es decir, el identificador L4S ECT(1). Establecer esto en any_ect hace que todos los paquetes cuyo campo ECN no sea cero se envíen a la cola L. Esto permite la compatibilidad con versiones anteriores, por ejemplo, DCTCP. Tenga en cuenta que DCTCP solo debe usarse para tráfico dentro del centro de datos con RTTs muy bajos y objetivos de retraso AQM mayores que esos RTTs, separado del tráfico de Internet (incluso si es un CC compatible con Prague), ya que no admite todos los requisitos de Prague que aseguran que un control de congestión pueda funcionar bien con el rango de RTTs en Internet.
step_thresh TIEMPO | PAQUETES
Establece el umbral de paso para la cola L. Esto hará que los paquetes con un tiempo de permanencia que exceda el umbral sean marcados siempre. Este valor se puede especificar usando unidades de tiempo (es decir, us, ms, s), o en paquetes (p, pkt, packet(s)). Se asume que un valor sin unidades está en tiempo (us). Si define el paso en paquetes, asegúrese de deshabilitar GRO en las interfaces de entrada. Por defecto es 1ms
min_qlen_step PAQUETES
Los paquetes entrantes encolados en la cola L pueden aplicar el umbral de paso cuando la longitud de la cola L excede este valor. Por defecto es 0 paquetes. Esto significa que cada paquete encolado en la cola L con un tiempo de permanencia que excede el umbral de paso será marcado.
drop_on_overload | overflow
Controla la estrategia de sobrecarga. drop_on_overload preserva el retraso en la cola L descartando en ambas colas en caso de sobrecarga. overflow sacrifica el retraso para evitar pérdidas, lo que finalmente resulta en un comportamiento de taildrop una vez que se alcanza el limit. Por defecto es drop_on_overload
drop_enqueue | drop_dequeue
Decide cuándo se descartan o marcan los paquetes basados en PI. El marcado L4S basado en step_thresh siempre se realiza en la salida. Por defecto es drop_dequeue
classic_protection PORCENTAJE
Protege la cola C del tráfico no sensible en la cola L. Esto limita el retraso máximo de programación en la cola C a ser (100 - PORCENTAJE) veces mayor que el de la cola L. Por defecto es 10
typical_rtt TIEMPO
max_rtt TIEMPO
Especifica el tiempo de ida y vuelta (RTT) máximo y/o el RTT típico del tráfico que será controlado por DUALPI2. Estos valores se especifican utilizando unidades de tiempo (es decir, us, ms, s). Se asume que un valor sin unidades está en us. Si no se especifica max_rtt o typical_rtt, el valor faltante se calculará a partir de la siguiente relación: max_rtt = typical_rtt * 6. Si se proporciona alguno de estos parámetros, se utilizará para calcular automáticamente valores adecuados para alpha, beta, target, y tupdate, según la relación del apéndice A.1 en el RFC de la IETF citado a continuación, para lograr un control estable. En consecuencia, esos valores derivados anularán sus eventuales valores proporcionados por el usuario.

El rango de operación predeterminado del qdisc utiliza max_rtt = 100ms y typical_rtt = 15ms , que es adecuado para controlar el tráfico de Internet.
target TIME
Establece el retraso de cola esperado. Por defecto es 15 ms. Un valor sin unidades se asume en microsegundos.
tupdate TIME
Establece la frecuencia con la que se calcula la probabilidad de caída del sistema. Por defecto es 16 ms. Un valor sin unidades se asume en microsegundos. Este valor debe ser menor que un tercio del RTT máximo soportado.
alpha float
beta float
Establece alpha y beta, los factores de ganancia integral y proporcional en Hz para el controlador PI. Estos pueden calcularse basándose en la teoría de control. Los valores por defecto son 0.16 y 3.2 Hz, que proporcionan un control estable para RTTs de hasta 100ms con tupdate de 16ms. Ten en cuenta que, a diferencia de PIE, estos son los factores de ganancia reales sin escalar. Si no se proporcionan, se derivarán automáticamente de typical_rtt y max_rtt , si uno de ellos o ambos se proporcionan.
split_gso | no_split_gso
Decide cómo manejar los paquetes agregados. Ya sea tratar el agregado como un paquete único (por lo tanto, todos comparten el mismo destino con respecto a las marcas y caídas) con no_split_gso , intercambiando algo de latencia final por uso de CPU, o tratar cada paquete individualmente (es decir, dividirlos) con split_gso para habilitar el marcado/descenso de paquetes de grano fino para controlar las latencias de cola. Por defecto es split_gso

EJEMPLOS

Configurando DUALPI2 para Internet con parámetros predeterminados:
# sudo tc qdisc add dev eth0 root dualpi2

Configurando DUALPI2 para centros de datos con DCTCP heredado usando ECT(0):
# sudo tc qdisc add dev eth0 root dualpi2 any_ect

FILTROS

Este qdisc se puede utilizar junto con tc-filters. Más precisamente, honrará los filtros que "roban paquetes", así como aceptará otros esquemas de clasificación.

Paquetes cuya prioridad/classid estén establecidos a
1 se pondrán en cola en la cola L, junto con el tráfico L4S, y por lo tanto estarán sujetos a una mayor probabilidad de marcado (o caídas si se marcan como no-ECT).
Paquetes cuya prioridad/classid estén establecidos a
2 también se pondrán en cola en la cola L, pero nunca se descartarán si son no-ECT (a menos que el qdisc esté lleno y, por lo tanto, recurra a taildrop).
Finalmente, todos los demás classid/prioridad se mapean a la cola C.
