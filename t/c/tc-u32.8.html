NOMBRE

u32 - filtro de control de tráfico universal de 32 bits

DESCRIPCIÓN

El filtro Universal/Ugly de 32 bits (u32) permite hacer coincidir campos de bits arbitrarios en el paquete. Debido a que descompone todo en valores, máscaras y desplazamientos, es igualmente potente y difícil de usar. Afortunadamente, existen muchas directivas que abstraen, lo que permite definir reglas a un nivel superior y, por lo tanto, libera al usuario de tener que manipular bits y máscaras en muchos casos.

Hay dos modos generales de invocación: el primer modo crea un nuevo filtro para delegar paquetes a diferentes destinos. Aparte de los obvios, como clasificar el paquete especificando un ID_CLASE o llamando a una acción, se puede enlazar un filtro a otro (o incluso a una lista de ellos), organizando efectivamente los filtros en una jerarquía similar a un árbol.

Típicamente, la delegación de filtros se realiza mediante una tabla hash, lo que lleva al segundo modo de invocación: simplemente sirve para configurar estas tablas hash. Los filtros pueden seleccionar una tabla hash y proporcionar un selector de clave a partir del cual se calculará un hash y se utilizará como clave para buscar el "cubo" de la tabla que contiene filtros para un procesamiento posterior. Esto es útil si se utiliza un gran número de filtros, ya que la sobrecarga de realizar la operación hash y la búsqueda en la tabla se vuelve insignificante en ese caso. Usar tablas hash con u32 implica básicamente el siguiente patrón:

(1)
Crear una nueva tabla hash, especificando su tamaño usando el parámetro divisor y, idealmente, un manejador por el cual se pueda identificar la tabla. Si este último no se proporciona, el kernel elige uno por sí mismo, que debe ser adivinado más tarde.
(2)
Crear filtros que se enlazan a la tabla creada en el punto (1) usando el parámetro link y definiendo los datos del paquete que el kernel utilizará para calcular la clave hash.
(3)
Añadir filtros a los cubos en la tabla hash del punto (1). Para evitar tener que saber exactamente cómo el kernel crea la clave hash, existe el parámetro sample, que proporciona datos de muestra para hacer hash y, por lo tanto, definir el cubo de la tabla al que se debe añadir el filtro.

De hecho, incluso si no se solicita explícitamente, u32 crea una tabla hash por cada prioridad con la que se añade un filtro. Sin embargo, el tamaño de la tabla es 1, por lo que en realidad es simplemente una lista enlazada.

VALORES

Las opciones y selectores requieren que los valores se especifiquen en un formato específico, que a menudo no es intuitivo. Por lo tanto, a los terminales de la SINOPSIS se les han dado nombres descriptivos para indicar el formato requerido y/o el valor numérico máximo permitido: Los prefijos u32, u16 y u8 indican valores sin signo de cuatro, dos y un byte respectivamente. Por ejemplo, u16 indica un valor de dos bytes en el rango de 0 a 65535 (0xFFFF) inclusive. Un prefijo int indica un valor con signo de cuatro bytes. Una parte central de _hex_ indica que el valor se analiza en formato hexadecimal. De lo contrario, la base del valor se detecta automáticamente, es decir, los valores prefijados con 0x se consideran hexadecimales, un 0 inicial indica formato octal y formato decimal en caso contrario. Hay algunos valores con formato especial también: direccion_ip y mascara_red están en formato de cuádruple punto como es habitual para las direcciones IPv4. Una direccion_ip6 se especifica en formato hexadecimal común, separado por dos puntos. Finalmente, longitud_prefijo es un valor entero decimal sin signo en el rango de 0 a la anchura de bits de la dirección (32 para IPv4 y 128 para IPv6).

A veces los valores deben ser divisibles por un número determinado. En ese caso se eligió un nombre de la forma N*valor, indicando que valor debe ser divisible por N. O al revés: el valor resultante debe ser un múltiplo de N.

OPCIONES

U32 reconoce las siguientes opciones:

handle MANEJADOR
El manejador se utiliza para referenciar un filtro y, por lo tanto, debe ser único. Consta de un identificador de tabla hash htid y, opcionalmente, hash (que identifica el cubo de la tabla hash) y nodo. Todos estos valores se analizan como números hexadecimales sin signo de 12 bits ( htid y nodo) u 8 bits ( hash). Alternativamente, se puede especificar un solo número hexadecimal de 32 bits que contenga los tres campos de bits concatenados. A diferencia de los campos en sí, debe ir prefijado por 0x.
offset DESPLAZAMIENTO
Establece un desplazamiento que define dónde se aplican las coincidencias de los filtros subsiguientes. Por lo tanto, esta opción solo es útil cuando se combina con link o con una combinación de ht y sample. El desplazamiento se puede dar explícitamente usando la palabra clave plus, o extraer de los datos del paquete con at. Es posible manipular este último usando las palabras clave mask y/o shift. Por defecto, este desplazamiento se registra pero no se aplica implícitamente. Solo se utiliza para sustituir la declaración nexthdr+. Sin embargo, usar la palabra clave eat invierte este comportamiento: el desplazamiento se aplica siempre, y nexthdr+ volverá a cero.
hashkey CLAVE_HASH
Especifica qué datos del paquete se utilizarán para calcular una clave hash para la búsqueda en el cubo. El kernel ajusta el valor de acuerdo con el tamaño de la tabla hash. Para que esto funcione, se debe proporcionar la opción link.
classid ID_CLASE

OPCIONES

class CLASSID
The filter matches if packet belongs to the given CLASSID. This is used for classification of packets and is mutually exclusive with all other options except handle.
handle VALUE
Used to identify a filter. If a filter is added to a hash table, this VALUE denotes the hash table's identifier. Otherwise it is the filter's identifier and used to refer to it later.
protocol PROTOCOL
The filter matches only packets of the given PROTOCOL. Recognised protocols are: all, ip, ipv6, ip6, encap, ah, esp, all, tc, mpls, ether, vlan, mmpdu, pppoe, ppp, ipip, icmp, igmp, tcp, udp, udplite, sctp, dccp, icmpv6, mh, ah, esp, hopopt, etc.
priority VALUE
Assigns a priority to the filter. Lower values mean higher priority. This is used when multiple filters are attached to the same parent qdisc and dictates the order in which they are consulted.
parent QdiscID
Attach filter to the given qdisc. In case the qdisc has multiple classes (like Class Based Queuing), the class needs to be specified as well.
divisor u32_value
Especifica un valor de módulo. Se utiliza al crear tablas hash para definir su tamaño o para declarar una sample para calcular las claves de las tablas hash. Debe ser una potencia de dos con un exponente no mayor de ocho.
order u32_value
Un valor para ordenar los filtros, en orden ascendente. Entra en conflicto con handle, que cumple el mismo propósito.
sample SELECTOR
Se utiliza junto con ht para especificar a qué cubo agregar este filtro. Esto permite evitar tener que saber exactamente cómo calcula el kernel los hashes. El divisor adicional tiene un valor predeterminado de 256, por lo que debe proporcionarse para tablas hash de diferente tamaño.
link HANDLE
Delega paquetes coincidentes a filtros en una tabla hash. HANDLE se utiliza para especificar solo la tabla hash, por lo que solo se puede proporcionar htid, y se deben omitir hash y nodeid. Por predeterminado, se utilizará el número de cubo 0 y se puede anular con la opción hashkey.
indev ifname
Filtra por la interfaz de entrada del paquete. Obviamente, solo funciona para tráfico reenviado.
skip_sw
No procesar el filtro por software. Si el hardware no tiene soporte de descarga para este filtro, o la descarga de TC no está habilitada para la interfaz, la operación fallará.
skip_hw
No procesar el filtro por hardware.
help
Imprime un breve texto de ayuda sobre las opciones posibles.

SELECTORES

Básicamente, el único selector real es u32 . Todos los demás simplemente proporcionan una sintaxis de nivel superior y se traducen internamente a u32 .

u32 VAL_MASK_32
u16 VAL_MASK_16
u8 VAL_MASK_8
Compara los datos del paquete con un valor dado. El nombre del selector define la longitud de la muestra a extraer (32 bits para u32, 16 bits para u16 y 8 bits para u8). Antes de comparar, la muestra se aplica un AND binario con la máscara dada. De esta manera, los bits no interesantes se pueden borrar antes de la comparación. La posición de la muestra se define por el desplazamiento especificado en AT.
ip IP
ip6 IP6
Asume que el paquete comienza con una cabecera IPv4 ( ip) o IPv6 ( ip6). IP/IP6 permite comparar varios campos de cabecera:
src ADDR
dst ADDR
Compara los campos de Dirección de Origen o Destino con el valor de ADDR. Las palabras reservadas default, any y all efectivamente coinciden con cualquier dirección. De lo contrario, se espera una dirección IP del protocolo particular, opcionalmente seguida de una longitud de prefijo para coincidir con subredes completas. En el caso de IPv4, también se puede proporcionar una máscara de red.
dsfield VAL_MASK_8
Solo IPv4. Compara el campo DSCP/ECN de la cabecera del paquete. Sinónimos de esto son tos y precedence.
ihl VAL_MASK_8
Solo IPv4. Compara el campo Longitud de la Cabecera de Internet. Tenga en cuenta que la unidad del valor es de 32 bits, por lo que para comparar un paquete con una cabecera de 24 bytes, u8_value debe ser 6.
protocol VAL_MASK_8
Compara el valor del campo Protocolo (IPv4) o Siguiente Cabecera (IPv6), por ejemplo, 6 para TCP.
icmp_type VAL_MASK_8
icmp_code VAL_MASK_8
Asume un protocolo de siguiente cabecera icmp o ipv6-icmp y compara los valores de los campos Tipo o Código. Esto es peligroso, ya que el código asume un tamaño mínimo de cabecera para IPv4 y la ausencia de cabeceras de extensión para IPv6.
sport VAL_MASK_16
dport VAL_MASK_16
Compara puertos de origen o destino de capa cuatro. Esto también es peligroso, ya que asume la presencia de un protocolo de capa cuatro adecuado (que tiene campos de Puerto de Origen y Destino justo al principio de la cabecera y de 16 bits de tamaño). También se asume un tamaño mínimo de cabecera para IPv4 y la ausencia de cabeceras de extensión IPv6.
nofrag
firstfrag
df
mf
Solo IPv4, comprueba ciertos flags y valores de desplazamiento de fragmento. Coincide si el paquete no es un fragmento (nofrag), es el primer fragmento de un paquete fragmentado (firstfrag), si los bits de No Fragmentar (df) o Más Fragmentos (mf) están establecidos.
priority VAL_MASK_8
Solo IPv6. Compara el campo Clase de Tráfico de la cabecera, que tiene el mismo propósito y semántica que el campo ToS de IPv4 desde RFC 3168: los seis bits superiores son DSCP, los dos inferiores ECN.
flowlabel VAL_MASK_32
Solo IPv6. Compara el valor del campo Etiqueta de Flujo. Tenga en cuenta que la Etiqueta de Flujo en sí misma solo tiene 20 bytes de longitud, que son los menos significativos aquí. Los 12 bytes superiores restantes coinciden con los campos Versión y Clase de Tráfico.
tcp TCPUDP
udp TCPUDP
Compara campos de la siguiente cabecera de protocolo TCP o UDP. Los valores posibles para TCPDUP son:
src VAL_MASK_16
Compara el valor del campo Puerto de Origen.
dst VALMASK_16
Compara el valor del campo Puerto de Destino.
icmp ICMP
Compara campos de la siguiente cabecera de protocolo ICMP. Los valores posibles para ICMP son:
type VAL_MASK_8
Compara el campo Tipo ICMP.
code VAL_MASK_8
Compara el campo Código ICMP.
mark VAL_MASK_32
Compara el valor de fwmark de netfilter.
ether ETHER
Compara campos de la cabecera ethernet. Los valores posibles para ETHER son:
src ether_address AT
dst ether_address AT
Compara la dirección ethernet de origen o destino. Esto es peligroso: asume que hay una cabecera ethernet al principio del paquete. Esto probablemente llevará a resultados inesperados si se utiliza con interfaces de capa tres como, por ejemplo, tun o ppp.

EJEMPLOS

tc filter add dev eth0 parent 999:0 prio 99 protocol ip u32 \
        match ip src 192.168.8.0/24 classid 1:1

Esto adjunta un filtro a la qdisc identificada por 999:0. Su prioridad es 99, lo que afecta el orden en que se consultan múltiples filtros adjuntos al mismo parent (cuanto menor sea, antes). El filtro maneja paquetes de tipo protocol ip, y matchea si la dirección de origen de la cabecera IP está dentro de la subred 192.168.8.0/24. Los paquetes coincidentes se clasifican en la clase 1.1. El efecto de este comando podría ser sorprendente a primera vista:

filter parent 1: protocol ip pref 99 u32
filter parent 1: protocol ip pref 99 u32 \
        fh 800: ht divisor 1
filter parent 1: protocol ip pref 99 u32 \
        fh 800::800 order 2048 key ht 800 bkt 0 flowid 1:1 \
        match c0a80800/ffffff00 at 12

Así, al padre 1: se le asigna un nuevo filtro u32, que contiene una tabla hash de tamaño 1 (como indica el divisor). La ID de la tabla es 800. La tercera línea muestra el filtro real que se agregó anteriormente: se encuentra en la tabla 800 y el cubo 0, clasifica los paquetes en la ID de clase 1:1 y compara los tres bytes superiores del valor de cuatro bytes en el desplazamiento 12 a ser 0xc0a808, que es 192, 168 y 8.

Ahora algo más complicado, como crear una tabla hash personalizada:

tc filter add dev eth0 prio 99 handle 1: u32 divisor 256

Esto crea una tabla de tamaño 256 con el handle 1: en la prioridad 99. El efecto es el siguiente:

filter parent 1: protocol all pref 99 u32
filter parent 1: protocol all pref 99 u32 fh 1: ht divisor 256
filter parent 1: protocol all pref 99 u32 fh 800: ht divisor 1

Así, junto con la tabla hash solicitada (handle 1:), el kernel ha creado su propia tabla de tamaño 1 para contener otros filtros de la misma prioridad.

El siguiente paso es crear un filtro que se enlace a la tabla hash creada:

tc filter add dev eth0 parent 1: prio 1 u32 \
        link 1: hashkey mask 0x0000ff00 at 12 \
        match ip src 192.168.0.0/16

Al filtro se le da una prioridad menor que a la tabla hash en sí, por lo que u32 la consulta antes de recorrer manualmente la tabla hash. Las opciones link y hashkey determinan a qué tabla y cubo redirigir. En este caso, la clave hash debe construirse a partir del segundo byte en el desplazamiento 12, que corr

Responde al tercer byte del campo de dirección de origen de un paquete IP. Junto con la sentencia match, esto mapea efectivamente todas las redes de clase C por debajo de 192.168.0.0/16 a diferentes cubetas de la tabla hash.

Se pueden crear filtros para ciertas subredes de la siguiente manera:

tc filter add dev eth0 parent 1: prio 99 u32 \
        ht 1: sample u32 0x00000800 0x0000ff00 at 12 \
        match ip src 192.168.8.0/24 classid 1:1

La cubeta se define usando la opción sample: En este caso, el segundo byte en el desplazamiento 12 debe ser exactamente 0x08. En este caso, el ID de cubeta resultante es obviamente 8, pero tan pronto como sample selecciona una cantidad de datos que podría exceder el divisor, habría que conocer el algoritmo interno del kernel para deducir la cubeta de destino. La sentencia match de este filtro es redundante en este caso, ya que la entropía para la clave hash no excede el tamaño de la tabla y, por lo tanto, no pueden ocurrir colisiones. De lo contrario, es necesario evitar la coincidencia de paquetes no deseados.

La coincidencia de campos de capa superior es problemática ya que la longitud de la cabecera IPv4 es variable y IPv6 admite cabeceras de extensión que afectan al desplazamiento de la cabecera de capa superior. Para superar esto, existe la posibilidad de especificar nexthdr+ al dar un desplazamiento, y para facilitar las cosas, existen las coincidencias tcp y udp que utilizan nexthdr+ implícitamente. Sin embargo, este desplazamiento debe calcularse de antemano, y la única forma de lograrlo es hacerlo en un filtro separado que luego se vincula al filtro que desea usarlo. Aquí hay un ejemplo de cómo hacerlo:

tc filter add dev eth0 parent 1:0 protocol ip handle 1: \
        u32 divisor 1
tc filter add dev eth0 parent 1:0 protocol ip \
        u32 ht 1: \
        match tcp src 22 FFFF \
        classid 1:2
tc filter add dev eth0 parent 1:0 protocol ip \
        u32 ht 800: \
        match ip protocol 6 FF \
        match u16 0 1fff at 6 \
        offset at 0 mask 0f00 shift 6 \
        link 1:

Esto es lo que se hace: En la primera llamada, se crea una tabla hash de tamaño de un solo elemento para que haya un lugar donde mantener el filtro vinculado y un identificador conocido (1:) para referirse a él. La segunda llamada agrega el filtro real, que empuja los paquetes con el puerto de origen TCP 22 a la clase 1:2. Usando ht, se mueve a la tabla hash creada por la primera llamada. La tercera llamada hace la magia real: Coincide con paquetes IPv4 con el protocolo de capa siguiente 6 (TCP), solo si es el primer fragmento (generalmente TCP establece el bit DF, pero si no lo hace y el paquete está fragmentado, solo el primero contiene la cabecera TCP), y luego establece el desplazamiento basado en el campo IHL de la cabecera IP (desplazar a la derecha en 6 elimina el desplazamiento del campo y al mismo tiempo convierte el valor a unidades de bytes). Finalmente, usando link, se hace referencia a la tabla hash de la primera llamada que contiene el filtro de la segunda llamada.
