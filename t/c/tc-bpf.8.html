NOMBRE

BPF - Classificador y acciones BPF programables para disciplinas de cola de entrada/salida

SINOPSIS

Clasificador (filtro) o acción eBPF:

tc filter ... bpf [ archivo-objeto OBJ_FILE ] [ sección NOMBRE_CLS ] [ exportar ARCHIVO_UDS ] [ verbose ] [ accion-directa | ad ] [ skip_hw | skip_sw ] [ police ESPEC_POLICE ] [ acción ESPEC_ACCION ] [ classid CLASSID ]
tc action ... bpf [ archivo-objeto OBJ_FILE ] [ sección NOMBRE_CLS ] [ exportar ARCHIVO_UDS ] [ verbose ]

Clasificador (filtro) o acción cBPF:

tc filter ... bpf [ archivo-bytecode ARCHIVO_BPF | bytecode BYTECODE_BPF ] [ police ESPEC_POLICE ] [ acción ESPEC_ACCION ] [ classid CLASSID ]
tc action ... bpf [ archivo-bytecode ARCHIVO_BPF | bytecode BYTECODE_BPF ]

DESCRIPCIÓN

Extended Berkeley Packet Filter ( eBPF ) y classic Berkeley Packet Filter (originalmente conocido como BPF, para una mejor distinción referido como cBPF aquí) están ambos disponibles como clasificadores y acciones completamente programables y altamente eficientes. Ambos ofrecen un conjunto mínimo de instrucciones para implementar pequeños programas que pueden ser cargados de forma segura en el kernel y, por lo tanto, ejecutados en una pequeña máquina virtual desde el espacio del kernel. Un verificador dentro del kernel garantiza que un programa especificado siempre termina y no falla ni filtra datos del kernel.

En Linux, generalmente se considera que eBPF es el sucesor de cBPF. El kernel internamente transforma las expresiones cBPF en expresiones eBPF y ejecuta estas últimas. La ejecución de estos puede realizarse en un intérprete o, en tiempo de configuración, pueden ser compilados justo a tiempo (JIT) para ejecutarse como código máquina nativo.

Actualmente, el compilador JIT de eBPF está disponible para las siguientes arquitecturas:

  • x86_64 (desde Linux 3.18)
  • arm64 (desde Linux 3.18)
  • s390 (desde Linux 4.1)
  • ppc64 (desde Linux 4.8)
  • sparc64 (desde Linux 4.12)
  • mips64 (desde Linux 4.13)
  • arm32 (desde Linux 4.14)
  • x86_32 (desde Linux 4.18)

Mientras que las siguientes arquitecturas tienen cBPF, pero aún no han cambiado a soporte JIT de eBPF:

  • ppc32
  • sparc32
  • mips32

El conjunto de instrucciones de eBPF tiene principios subyacentes similares al conjunto de instrucciones de cBPF, sin embargo, está modelado más cerca de la arquitectura subyacente para imitar mejor los conjuntos de instrucciones nativos con el objetivo de lograr un mejor rendimiento en tiempo de ejecución. Está diseñado para ser JIT'eado con un mapeo uno a uno, lo que también puede abrir la posibilidad para que los compiladores generen código eBPF optimizado a través de un backend de eBPF que funciona casi tan rápido como el código compilado nativamente. Dado que LLVM proporciona un backend de eBPF de este tipo, los programas eBPF pueden, por lo tanto, programarse fácilmente en un subconjunto del lenguaje C. Además de eso, la infraestructura de eBPF también viene con una construcción llamada "mapas". Los mapas eBPF son almacenes de clave/valor que se comparten entre múltiples programas eBPF, pero también entre programas eBPF y aplicaciones de espacio de usuario.

Para el subsistema de control de tráfico, los clasificadores y acciones que se pueden adjuntar a qdiscs de entrada y salida pueden escribirse en eBPF o cBPF. La ventaja sobre otros clasificadores y acciones es que eBPF/cBPF proporciona el marco genérico, mientras que los usuarios pueden implementar sus casos de uso altamente especializados de manera eficiente. Esto significa que el clasificador o acción escrito de esta manera no sufrirá una acumulación de características y, por lo tanto, podrá ejecutar su tarea de manera altamente eficiente. Permite la clasificación no lineal e incluso la fusión de la parte de acción en la clasificación. Combinado con estructuras de datos eficientes de mapas eBPF, el espacio de usuario puede introducir nuevas políticas como classids en el kernel sin recargar un clasificador, o puede recopilar estadísticas que se introducen en un mapa y usar otro para el balanceo de carga dinámico del tráfico basado en la carga determinada, solo por dar algunos ejemplos.

PARÁMETROS

archivo-objeto

apunta a un archivo objeto que tiene un formato ejecutable y enlazable (ELF) y contiene opcodes eBPF y definiciones de mapas eBPF. La infraestructura del compilador LLVM con clang(1) como front-end de lenguaje C es un proyecto que admite la emisión de archivos objeto eBPF que se pueden pasar al clasificador eBPF (más detalles en la sección EJEMPLOS). Esta opción es obligatoria cuando se va a cargar un clasificador o acción eBPF.

sección

es el nombre de la sección ELF del archivo objeto, donde reside el clasificador o acción eBPF. Por defecto, el nombre de la sección para el clasificador se llama "classifier", y para la acción "action". Dado que un solo archivo objeto puede contener múltiples clasificadores y acciones, se debe especificar el nombre de la sección correspondiente si difiere de los predeterminados.

exportar

apunta a un archivo de socket de dominio Unix. En caso de que el archivo objeto eBPF también contenga una sección llamada "maps" con especificaciones de mapas eBPF, entonces los descriptores de archivo de mapa pueden ser entregados a través del socket de dominio Unix a un "agente" eBPF que gestiona todos los descriptores después de la vida útil de tc. Esto puede ser alguna aplicación de terceros que implemente la contraparte IPC para la importación, que los utiliza para llamar a la llamada del sistema bpf(2) para leer o actualizar datos de mapas eBPF desde el espacio de usuario, por ejemplo, con fines de monitoreo o para enviar nuevas políticas.

verbose

si se establece, mostrará la salida del verificador eBPF, incluso si la carga del programa eBPF fue exitosa. Por defecto, solo en caso de error, se emite el registro del verificador al usuario.

accion-directa | ad

instruye al clasificador eBPF para que no invoque acciones TC externas, sino que utilice los códigos de retorno de acciones TC ( TC_ACT_OK, TC_ACT_SHOT, etc.) para los clasificadores.

skip_hw | skip_sw

banderas de control de descarga de hardware. Por defecto, TC intentará descargar filtros a hardware si es posible. skip_hw deshabilita explícitamente el intento de descarga. skip_sw fuerza la descarga y deshabilita la ejecución del programa eBPF en el kernel. Si la descarga de hardware no es posible y esta bandera se estableció, el kernel informará un error y el filtro no se instalará en absoluto.

police

es un parámetro opcional para un clasificador eBPF/cBPF que especifica una policía en tc(1) que se adjunta al clasificador, por ejemplo, en un qdisc de entrada.

acción

es un parámetro opcional para un clasificador eBPF/cBPF que especifica una acción posterior en tc(1) que se adjunta a un clasificador.

classid

flowid

proporciona el identificador de clase de control de tráfico predeterminado para este clasificador eBPF/cBPF. El identificador de clase predeterminado también puede ser sobrescrito por el código de retorno del programa eBPF/cBPF. Un código de retorno predeterminado de -1 especifica que se debe utilizar el identificador de clase predeterminado proporcionado aquí. Un código de retorno del programa eBPF/cBPF de 0 implica que no se produjo ninguna coincidencia, y un código de retorno distinto de estos dos anulará el classid predeterminado. Esto permite una clasificación no lineal eficiente con un solo programa eBPF/cBPF en lugar de tener múltiples programas individuales para varias clases de identificadores que necesitarían volver a analizar el contenido del paquete.

bytecode

es el código de bytes CPython para un clasificador/acción cBPF.

archivo-bytecode

es un archivo que contiene el código de bytes CPython para un clasificador/acción cBPF.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

OPTIONS

bytecode

se está utilizando para cargar solo el clasificador y las acciones cBPF. El código de bytes cBPF se pasa directamente como una cadena de texto en la forma de 's,c t f k,c t f k,c t f k,...' , donde s denota el número de tuplas de 4 elementos subsiguientes. Una de esas tuplas de 4 elementos consta de decimales c t f k , donde c representa el código de operación cBPF, t el objetivo de desplazamiento de salto verdadero, f el objetivo de desplazamiento de salto falso y k la constante/literal inmediata. Hay varias herramientas que generan código en este formato cargable, por ejemplo, bpf_asm que se incluye con el árbol de código fuente del kernel de Linux en tools/net/ , por lo que ciertamente no se espera hackearlo a mano. La opción bytecode o bytecode-file es obligatoria cuando se va a cargar un clasificador o acción cBPF.

bytecode-file

también se utiliza para cargar un clasificador o acción cBPF. Es efectivamente lo mismo que bytecode solo que el código de bytes cBPF no se pasa directamente a través de la línea de comandos, sino que reside en un archivo de texto.

EJEMPLOS

HERRAMIENTAS eBPF

Un ejemplo completo que incluye código de agente eBPF se puede encontrar dentro del paquete fuente de iproute2 en: examples/bpf/

Como requisitos previos, el kernel debe tener habilitada la llamada al sistema eBPF, a saber, bpf(2) y debe incluir los módulos del kernel cls_bpf y act_bpf para el subsistema de control de tráfico. Para habilitar el soporte eBPF/eBPF JIT, dependiendo de cuál de los dos soporta la arquitectura dada:


echo 1 > /proc/sys/net/core/bpf_jit_enable

Un archivo C restringido dado puede compilarse a través de LLVM como:


clang -O2 -emit-llvm -c bpf.c -o - | llc -march=bpf -filetype=obj -o bpf.o

La invocación del compilador aún podría simplificarse en el futuro, por lo que, por ahora, es muy útil crear un alias para esta construcción de una forma u otra, por ejemplo: 

__bcc() {
        clang -O2 -emit-llvm -c $1 -o - | \
        llc -march=bpf -filetype=obj -o "`basename $1 .c`.o"
}
alias bcc=__bcc

Una unidad mínima e independiente, que coincide con todo el tráfico con el classid predeterminado (código de retorno de -1), se ve así:


#include <linux/bpf.h>
#ifndef __section
# define __section(x)  __attribute__((section(x), used))
#endif
__section("classifier") int cls_main(struct __sk_buff *skb)
{
        return -1;
}
char __license[] __section("license") = "GPL";

Se pueden encontrar más ejemplos más abajo en la subsección PROGRAMACIÓN eBPF, ya que el enfoque aquí estará en las herramientas.

Puede haber varias otras secciones, por ejemplo, también para acciones. Por lo tanto, un archivo objeto en eBPF puede contener múltiples puntos de entrada. Sin embargo, siempre se debe especificar un punto de entrada específico al configurar con tc. Una licencia debe formar parte del código C restringido y la sintaxis de la cadena de licencia es la misma que con los módulos del kernel de Linux. El kernel se reserva el derecho de que algunas funciones auxiliares de eBPF solo puedan estar restringidas a licencias compatibles con GPL, y por lo tanto pueden rechazar la carga de un programa en el kernel cuando ocurre una falta de coincidencia de licencia de este tipo.

Agregar un clasificador eBPF desde un archivo objeto que contiene un clasificador en la sección ELF predeterminada es trivial (tenga en cuenta que en lugar de "object-file" también se pueden usar atajos como "obj"):


bcc bpf.c
tc filter add dev em1 parent 1: bpf obj bpf.o flowid 1:1

En caso de que el clasificador resida en la sección ELF "mycls", entonces se debe invocar el mismo comando como:


tc filter add dev em1 parent 1: bpf obj bpf.o sec mycls flowid 1:1

Volcar la configuración del clasificador le dirá la ubicación del clasificador, en otras palabras, que proviene del archivo objeto "bpf.o" bajo la sección "mycls":


tc filter show dev em1
filter parent 1: protocol all pref 49152 bpf
filter parent 1: protocol all pref 49152 bpf handle 0x1 flowid 1:1 bpf.o:[mycls]

El mismo programa también se puede instalar en el lado qdisc de entrada en lugar de salida...


tc qdisc add dev em1 handle ffff: ingress
tc filter add dev em1 parent ffff: bpf obj bpf.o sec mycls flowid ffff:1

... y nuevamente volcado desde allí:


tc filter show dev em1 parent ffff:
filter protocol all pref 49152 bpf
filter protocol all pref 49152 bpf handle 0x1 flowid ffff:1 bpf.o:[mycls]

Adjuntar un clasificador y una acción en la entrada tiene la restricción de que no tiene una disciplina de cola subyacente real. Lo que la entrada puede hacer es clasificar, manipular, redirigir o descartar paquetes. Cuando se requiere cola en el lado de entrada, la entrada debe redirigir los paquetes al dispositivo ifb, de lo contrario, se puede utilizar la aplicación de políticas. Además, la entrada se puede utilizar para tener un punto de descarte temprano de paquetes no deseados antes de que lleguen a las capas superiores de la pila de red, realizar contabilidad de red con mapas eBPF que podrían compartirse con la salida, o tener un punto de manipulación y/o redirección temprano a diferentes dispositivos de red.

Se pueden colocar múltiples acciones y clasificadores eBPF en un solo archivo objeto dentro de varias secciones. En ese caso, se deben proporcionar nombres de sección no predeterminados, que es el caso para ambas acciones en este ejemplo:


tc filter add dev em1 parent 1: bpf obj bpf.o flowid 1:1 \

action bpf obj bpf.o sec action-mark \
action bpf obj bpf.o sec action-rand ok

La ventaja de esto es que el clasificador y las dos acciones pueden compartir mapas eBPF entre sí, si están implementados en los programas.

Para acceder a los mapas eBPF desde el espacio de usuario más allá de la vida útil de configuración de tc(8) , la propiedad se puede transferir a un agente eBPF a través de sockets de dominio Unix. Hay dos posibilidades para implementar esto:

1) Implementación de un propio agente eBPF que se encarga de configurar el socket de dominio Unix e implementar el protocolo que dicta tc(8) . Un ejemplo de código de esto se puede encontrar dentro del paquete fuente de iproute2 en: examples/bpf/

2) Use tc exec para transferir los descriptores de archivo de mapa eBPF a través de un socket de dominio Unix, y generar una aplicación como sh(1) . La ventaja de este enfoque es que tc colocará los descriptores de archivo en el entorno y así los hará disponibles al igual que los descriptores de archivo de entrada estándar, salida estándar y error estándar, lo que significa que, en caso de que las aplicaciones de usuario se ejecuten desde este shell propietario de fd, pueden terminar y reiniciarse sin perder los descriptores de archivo de mapa eBPF. Ejemplo de invocación con la combinación anterior de clasificador y acción:


tc exec bpf imp /tmp/bpf
tc filter add dev em1 parent 1: bpf obj bpf.o exp /tmp/bpf flowid 1:1 \

action bpf obj bpf.o sec action-mark \
action bpf obj bpf.o sec action-rand ok

Suponiendo que los mapas eBPF se comparten con el clasificador y las acciones, es suficiente exportarlos una vez, por ejemplo, desde el comando del clasificador o la acción. tc configurará todos los descriptores de archivo de mapa eBPF en el momento en que se analice el archivo objeto por primera vez.

Cuando se ha generado un shell, el entorno tendrá un par de variables relacionadas con eBPF. BPF_NUM_MAPS proporciona el número total de mapas que se han transferido a través del socket de dominio Unix. El valor de BPF_MAP<X> es el número de descriptor de archivo al que se puede acceder en las aplicaciones del agente eBPF, en otras palabras, se puede utilizar directamente como valor del descriptor de archivo para la llamada al sistema bpf(2) para recuperar o modificar valores de mapa eBPF. <X> denota el identificador del mapa eBPF. Corresponde al miembro id de struct bpf_elf_map de la especificación del mapa eBPF de tc.

El entorno en este ejemplo se ve así:


sh# env | grep BPF
    BPF_NUM_MAPS=3
    BPF_MAP1=6
    BPF_MAP0=5
    BPF_MAP2=7
sh# ls -la /proc/self/fd
    [...]
    lrwx------. 1 root root 64 Apr 14 16:46 5 -> anon_inode:bpf-map
    lrwx------. 1 root root 64 Apr 14 16:46 6 -> anon_inode:bpf-map
    lrwx------. 1 root root 64 Apr 14 16:46 7 -> anon_inode:bpf-map
sh# my_bpf_agent

Los agentes eBPF son muy útiles, ya que pueden pre-poblar mapas eBPF desde el espacio de usuario, monitorear estadísticas a través de mapas y, basándose en esa retroalimentación, por ejemplo, reescribir classids en valores de mapa eBPF en tiempo de ejecución. Dado que los agentes eBPF se implementan como aplicaciones normales, también pueden recibir dinámicamente políticas de control de tráfico de controladores externos y así enviarlas a los mapas eBPF para adaptarse dinámicamente a las condiciones de la red. Además, los mapas eBPF también se pueden compartir con otros tipos de programas eBPF (por ejemplo, trazado), por lo que se puede implementar una combinación muy potente.

PROGRAMACIÓN eBPF

Los clasificadores y acciones eBPF se implementan en sintaxis C restringida (en el futuro, podría haber interfaces de lenguaje nuevas y adicionales admitidas).

El archivo de cabecera linux/bpf.h proporciona funciones auxiliares eBPF que pueden ser llamadas desde un programa eBPF. Esta página man solo proporcionará dos ejemplos mínimos e independientes; consulte examples/bpf del paquete fuente de iproute2 para ver un ejemplo completo de disector de flujo que demuestre mejor algunas de las posibilidades con eBPF.

Códigos de retorno de clasificador de 32 bits admitidos desde el programa C y sus significados:
0 , denota una falta de coincidencia
-1 , denota el classid predeterminado configurado desde la línea de comandos


else, todo lo demás anulará el classid predeterminado para proporcionar una facilidad para la coincidencia no lineal.

Códigos de retorno de acción de 32 bits admitidos desde el programa C y sus significados (linux/pkt_cls.h):
TC_ACT_OK (0), terminará el pipeline de procesamiento de paquetes y permitirá que el paquete continúe.
TC_ACT_SHOT (2), terminará el pipeline de procesamiento de paquetes y descartará el paquete.
TC_ACT_UNSPEC (-1), usará la acción predeterminada configurada desde tc (similar a devolver -1 desde un clasificador).
TC_ACT_PIPE (3), iterará a la siguiente acción, si está disponible.
TC_ACT_RECLASSIFY (1), terminará el pipeline de procesamiento de paquetes y comenzará la clasificación desde el principio.
else, todo lo demás es un código de retorno no especificado.

Los códigos de retorno tanto del clasificador como de la acción son compatibles en programas eBPF y cBPF.

Para demostrar la sintaxis restringida de C, se proporciona un ejemplo mínimo de clasificador de juguete, que asume que los paquetes de egreso, por ejemplo, originados en un contenedor, han sido previamente marcados en el intervalo [0, 255]. El programa mantiene estadísticas sobre diferentes marcas para el espacio de usuario y mapea el classid al qdisc raíz con la propia marca como manejador secundario:


#include <stdint.h>
#include <asm/types.h>
#include <linux/bpf.h>
#include <linux/pkt_sched.h>
#include "helpers.h"
struct tuple {
        long packets;
        long bytes;
};
#define BPF_MAP_ID_STATS        1 /* ID del mapa del agente */
#define BPF_MAX_MARK            256
struct bpf_elf_map __section("maps") map_stats = {
        .type           =       BPF_MAP_TYPE_ARRAY,
        .id             =       BPF_MAP_ID_STATS,
        .size_key       =       sizeof(uint32_t),
        .size_value     =       sizeof(struct tuple),
        .max_elem       =       BPF_MAX_MARK,
        .pinning        =       PIN_GLOBAL_NS,
};
static inline void cls_update_stats(const struct __sk_buff *skb,
                                    uint32_t mark)
{
        struct tuple *tu;
        tu = bpf_map_lookup_elem(&map_stats, &mark);
        if (likely(tu)) {
                __sync_fetch_and_add(&tu->packets, 1);
                __sync_fetch_and_add(&tu->bytes, skb->len);
        }
}
__section("cls") int cls_main(struct __sk_buff *skb)
{
        uint32_t mark = skb->mark;
        if (unlikely(mark >= BPF_MAX_MARK))
                return 0;
        cls_update_stats(skb, mark);
        return TC_H_MAKE(TC_H_ROOT, mark);
}
char __license[] __section("license") = "GPL";

Otro pequeño ejemplo es un redirigidor de puertos que desmultiplexa el puerto de destino 80 en el intervalo [8080, 8087] dirigido por RSS, que luego se puede adjuntar al qdisc de ingreso. El ejercicio de agregar la contraparte de egreso y el soporte IPv6 se deja al lector:


#include <asm/types.h>
#include <asm/byteorder.h>
#include <linux/bpf.h>
#include <linux/filter.h>
#include <linux/in.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/tcp.h>
#include "helpers.h"
static inline void set_tcp_dport(struct __sk_buff *skb, int nh_off,
                                 __u16 old_port, __u16 new_port)
{
        bpf_l4_csum_replace(skb, nh_off + offsetof(struct tcphdr, check),
                            old_port, new_port, sizeof(new_port));
        bpf_skb_store_bytes(skb, nh_off + offsetof(struct tcphdr, dest),
                            &new_port, sizeof(new_port), 0);
}
static inline int lb_do_ipv4(struct __sk_buff *skb, int nh_off)
{
        __u16 dport, dport_new = 8080, off;
        __u8 ip_proto, ip_vl;
        ip_proto = load_byte(skb, nh_off +
                             offsetof(struct iphdr, protocol));
        if (ip_proto != IPPROTO_TCP)
                return 0;
        ip_vl = load_byte(skb, nh_off);
        if (likely(ip_vl == 0x45))
                nh_off += sizeof(struct iphdr);
        else
                nh_off += (ip_vl & 0xF) << 2;
        dport = load_half(skb, nh_off + offsetof(struct tcphdr, dest));
        if (dport != 80)
                return 0;
        off = skb->queue_mapping & 7;
        set_tcp_dport(skb, nh_off - BPF_LL_OFF, __constant_htons(80),
                      __cpu_to_be16(dport_new + off));
        return -1;
}
__section("lb") int lb_main(struct __sk_buff *skb)
{
        int ret = 0, nh_off = BPF_LL_OFF + ETH_HLEN;
        if (likely(skb->protocol == __constant_htons(ETH_P_IP)))
                ret = lb_do_ipv4(skb, nh_off);
        return ret;
}
char __license[] __section("license") = "GPL";

static void *(*bpf_map_lookup_elem)(void *map, void *key) =
      (void *) BPF_FUNC_map_lookup_elem;
/* Algunas intrínsecas BPF utilizadas. */
unsigned long long load_byte(void *skb, unsigned long long off)
    asm ("llvm.bpf.load.byte");
unsigned long long load_half(void *skb, unsigned long long off)
    asm ("llvm.bpf.load.half");

Como mejor práctica, recomendamos tener un solo clasificador eBPF cargado en tc y realizar todas las coincidencias y manipulaciones necesarias desde allí en lugar de una lista de clasificadores individuales y acciones separadas. Solo un clasificador adaptado para un caso de uso dado será el más eficiente de ejecutar.

DEPURACIÓN DE eBPF

Tanto los comandos filter como action de tc para bpf admiten un parámetro opcional verbose que se puede utilizar para inspeccionar el registro del verificador de eBPF. Se vuelca por defecto en caso de error.

En caso de que el compilador JIT de eBPF/cBPF se haya habilitado, también se puede instruir para que emita una salida de depuración de la imagen de código de operación resultante en el registro del kernel, que se puede leer a través de dmesg(1):


echo 2 > /proc/sys/net/core/bpf_jit_enable

El árbol de origen del kernel de Linux envía adicionalmente en tools/net/ una pequeña utilidad llamada bpf_jit_disasm que lee el volcado de la imagen de código de operación del registro del kernel y muestra el desensamblado resultante:


bpf_jit_disasm -o

Aparte de eso, el kernel de Linux también contiene un extenso conjunto de pruebas eBPF/cBPF llamado test_bpf. Al ...


modprobe test_bpf

... realiza una diversidad de casos de prueba y vuelca los resultados en el registro del kernel que se pueden inspeccionar con dmesg(1). Los resultados pueden diferir dependiendo de si el compilador JIT está habilitado o no. En caso de fallar las pruebas, el módulo no se cargará. En tales casos, le instamos a que presente un informe de error a los autores del JIT relacionados, a las listas de correo del kernel de Linux y de redes.

cBPF

Aunque generalmente recomendamos cambiar a la implementación de clasificadores y acciones eBPF, por completitud, unas pocas palabras sobre cómo programar en cBPF se perderán aquí.

Del mismo modo, el interruptor bpf_jit_enable se puede habilitar como se mencionó anteriormente. Herramientas como bpf_jit_disasm también son independientes de si se está cargando código eBPF o cBPF.

A diferencia de eBPF, los clasificadores y acciones no se implementan en C restringido, sino en un lenguaje mínimo similar a ensamblador o con la ayuda de otras herramientas.

La interfaz bruta con tc toma directamente los códigos de operación. Por ejemplo, el clasificador más mínimo que coincide con cada paquete resultando en el classid predeterminado de 1:1 se ve así:


tc filter add dev em1 parent 1: bpf bytecode '1,6 0 0 4294967295,' flowid 1:1

El primer decimal de la secuencia de bytecode denota el número de tuplas de 4 de códigos de operación cBPF subsiguientes. Como se mencionó, tal tupla de 4 consiste en los decimales c t f k, donde c representa el código de operación cBPF, t el objetivo de desplazamiento de salto verdadero, f el objetivo de desplazamiento de salto falso y k la constante/literal inmediata. Aquí, esto denota un retorno incondicional del programa con un valor inmediato de -1.

Por lo tanto, para la clasificación de egreso, Willem de Bruijn implementó una herramienta auxiliar mínima independiente bajo la Licencia Pública General de GNU versión 2 para la extensión BPF de iptables(8), que abusa del compilador cBPF interno de libpcap, su código derivado aquí para su uso con tc(8):


#include <pcap.h>
#include <stdio.h>
int main(int argc, char **argv)
{
        struct bpf_program prog;
        struct bpf_insn *ins;
        int i, ret, dlt = DLT_RAW;
        if (argc < 2 || argc > 3)
                return 1;
        if (argc == 3) {
                dlt = pcap_datalink_name_to_val(argv[1]);
                if (dlt == -1)
                        return 1;
        }
        ret = pcap_compile_nopcap(-1, dlt, &prog, argv[argc - 1],
                                  1, PCAP_NETMASK_UNKNOWN);
        if (ret)
                return 1;
        printf("%d,", prog.bf_len);
        ins = prog.bf_insns;
        for (i = 0; i < prog.bf_len - 1; ++ins, ++i)
                printf("%u %u %u %u,", ins->code,
                       ins->jt, ins->jf, ins->k);
        printf("%u %u %u %u",
               ins->code, ins->jt, ins->jf, ins->k);
        pcap_freecode(&prog);
        return 0;
}

Dado este pequeño generador, cualquier expresión de filtro de tcpdump(8) se puede abusar como un clasificador donde una coincidencia resultará en el classid predeterminado:


bpftool EN10MB 'tcp[tcpflags] & tcp-syn != 0' > /var/bpf/tcp-syn
tc filter add dev em1 parent 1: bpf bytecode-file /var/bpf/tcp-syn flowid 1:1

Básicamente, un generador tan mínimo es equivalente a:


tcpdump -iem1 -ddd 'tcp[tcpflags] & tcp-syn != 0' | tr '  ',' > /var/bpf/tcp-syn

Dado que libpcap no admite todas las extensiones cBPF específicas de Linux en su compilador, el kernel de Linux también envía

s bajo tools/net/ un ensamblador BPF minimal llamado bpf_asm para proporcionar control total. Para obtener una sintaxis y semántica detalladas sobre la implementación de dichos programas manualmente, consulte las referencias en LECTURA ADICIONAL .

Ejemplo trivial de juguete en bpf_asm para clasificar paquetes IPv4/TCP , guardado en un archivo de texto llamado foobar :


ldh [12]
jne #0x800, drop
ldb [23]
jneq #6, drop
ret #-1
drop: ret #0

De manera similar, dicho clasificador se puede cargar como:


bpf_asm foobar > /var/bpf/tcp-syn
tc filter add dev em1 parent 1: bpf bytecode-file /var/bpf/tcp-syn flowid 1:1

Para los clasificadores BPF, el kernel de Linux proporciona adicionalmente en tools/net/ un pequeño depurador BPF llamado bpf_dbg , que puede ser utilizado para probar un clasificador contra archivos pcap, depurar paso a paso o agregar varios puntos de interrupción en el programa clasificador y volcar el contenido de los registros durante el tiempo de ejecución.

La implementación de una acción en BPF clásico es bastante limitada en el sentido de que no se admite la manipulación de paquetes. Por lo tanto, generalmente se recomienda cambiar a eBPF, siempre que sea posible.
