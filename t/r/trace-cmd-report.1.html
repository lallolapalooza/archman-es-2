NOMBRE

trace-cmd-report - mostrar en ASCII un rastreo creado por trace-cmd record

SINOPSIS

trace-cmd report [OPCIONES] [archivo-entrada [archivo-entrada ...]]

DESCRIPCIÓN

El comando trace-cmd(1) report generará un informe legible por humanos de un rastreo creado por trace-cmd record.

OPCIONES

-i archivo-entrada

Por defecto, trace-cmd report leerá el archivo trace.dat. Pero la opción -i abrirá el archivo-entrada especificado en su lugar. Tenga en cuenta que el archivo de entrada también puede especificarse como el último elemento en la línea de comandos.

-e

Esto muestra el orden de bytes (endianness) del archivo. trace-cmd report es lo suficientemente inteligente como para poder leer archivos big-endian en máquinas little-endian, y viceversa.

-f

Esto muestra la lista de todas las funciones que se han mapeado en el archivo trace.dat. Tenga en cuenta que esta lista puede contener funciones que no aparecen en el rastreo, ya que es la lista de mapeos para traducir direcciones de funciones a nombres de funciones.

-P

Esto muestra la lista de datos de "trace_printk()". Los puntos de datos brutos del rastreo apuntan a punteros estáticos en el kernel. Esto debe almacenarse en el archivo trace.dat.

-E

Esto lista los posibles eventos en el archivo (pero esta lista no es necesariamente la lista de eventos en el archivo).

--events

Esto mostrará los formatos de eventos que se almacenan en el archivo trace.dat.

--event regex

Esto imprimirá eventos que coincidan con la expresión regular dada. Si se especifica dos puntos, los caracteres anteriores a los dos puntos se utilizarán para coincidir con el sistema y los caracteres posteriores a los dos puntos coincidirán con el evento. 
trace-cmd report --event sys:read
Lo anterior solo coincidirá con eventos donde el nombre del sistema contenga
"sys" y el nombre del evento contenga "read".
trace-cmd report --event read
Lo anterior coincidirá con todos los eventos que contengan "read" en su
nombre. También puede listar todos los eventos de un sistema que contenga
"read".

--check-events

Esto analizará las cadenas de formato de eventos que se almacenan en el archivo trace.dat y devolverá si los formatos se pueden analizar correctamente. Cargará plugins a menos que se especifique -N.

-t

Imprime la marca de tiempo completa. Las marcas de tiempo en el archivo de datos generalmente se registran hasta nanosegundos. Pero la visualización predeterminada de la marca de tiempo es solo hasta microsegundos. Para ver la marca de tiempo completa, agregue la opción -t.

-F filtro

Agrega un filtro para limitar qué eventos se muestran. Los filtros definidos después de un archivo de entrada (especificado con -i) solo se aplican a ese archivo de entrada. Los filtros proporcionados antes de cualquier archivo de entrada se consideran globales y se aplican a todos los archivos de entrada. 
El formato del filtro es:
    <eventos> ':' <filtro>
    <eventos> = SISTEMA'/'EVENTO  | SISTEMA | EVENTO | <eventos> ',' <eventos>
    <filtro> = CAMPO_EVENTO <op> <valor> | <filtro> '&&' <filtro> |
               <filtro> '||' <filtro> | '(' <filtro> ')' | '!' <filtro>
    <op> = '==' | '!=' | '>=' | '<=' | '>' | '<' | '&' | '|' | '^' |
           '+' | '-' | '*' | '/' | '%'
    <valor> = NUM | CADENA | CAMPO_EVENTO
SISTEMA es el nombre del sistema en el que filtrar. Si se omite EVENTO,
entonces se aplica a todos los eventos bajo el SISTEMA. Si solo se usa una
cadena sin el '/' para delimitar entre SISTEMA y EVENTO, entonces el filtro
se aplicará a todos los sistemas y eventos que coincidan con la cadena dada.
Los espacios en blanco se ignoran, de modo que "sched:next_pid==123" es equivalente a
"sched : next_pid == 123".
CADENA se define con comillas simples o dobles (la comilla simple debe
terminar con comilla simple, y la doble con doble). Los espacios en blanco
dentro de las comillas no se ignoran.
La representación de un SISTEMA o EVENTO también puede ser una expresión
regular según lo definido por 'regcomp(3)'.
CAMPO_EVENTO es el nombre del campo de un evento que se está filtrando. Si
el evento no contiene el CAMPO_EVENTO, esa parte de la ecuación se considerará
falsa.
    -F 'sched : bogus == 1 || common_pid == 2'
El "bogus == 1" siempre se evaluará como FALSO porque ningún evento tiene
un campo llamado "bogus", pero el "common_pid == 2" aún se evaluará
ya que todos los eventos tienen el campo "common_pid". Se mostrarán
todos los eventos "sched" que fueron rastreados por el proceso con el
PID de 2.
Nota: el CAMPO_EVENTO es el nombre del campo como se muestra en el formato de
los eventos (como se muestra con *--events*), y no lo que se encuentra en la
salida. Si la salida muestra "ID:foo" pero el campo al que pertenece
"foo" se llamó "name" en el formato del evento, entonces se debe usar
"name" en el filtro. Lo mismo ocurre con los valores. Si el valor que se muestra
se convierte a un símbolo de cadena, el filtro verifica el valor original y no
el valor mostrado. Por ejemplo, para filtrar todas las tareas que estaban en
estado de ejecución en un cambio de contexto:
    -F 'sched/sched_switch : prev_state==0'
Aunque la salida muestra 'R', tener 'prev_stat=="R"' no funcionará.
Nota: También puedes especificar 'COMM' como CAMPO_EVENTO. Esto usará el
nombre de la tarea (o comm) del registro para comparar. Por ejemplo, para
filtrar todas las tareas "trace-cmd":
    -F '.*:COMM != "trace-cmd"'

-I

No imprime eventos donde se establece la bandera de latencia de interrupción (hardirq). Esto filtrará la mayoría de los eventos que provienen del contexto de interrupción. Tenga en cuenta que puede no filtrar funciones rastreadas que están en contexto de interrupción pero fueron llamadas antes de que se estableciera la bandera de "interrupción" del kernel.

-S

No imprime eventos donde se establece la bandera de latencia de interrupción (softirq). Esto filtrará la mayoría de los eventos que provienen del contexto de interrupción suave.

-v

Esto hace que los siguientes filtros de -F filtren los eventos coincidentes.
    -v -F 'sched/sched_switch : prev_state == 0'
No mostrará ningún evento sched_switch que tenga un prev_state de 0.
Eliminar *-v* solo imprimirá esos eventos.

-T

Prueba los filtros de -F. Después de procesar una cadena de filtro, el filtro resultante se mostrará para cada evento. Esto es útil para usar un filtro para más de un evento donde un campo puede no existir en todos los eventos. También se puede usar para asegurarse de que no haya nombres de campos de eventos mal escritos, ya que simplemente se ignorarán. -T se ignora si no se especifica -F.

-V

Muestra mensajes detallados (ver --verbose pero solo para los números)

-L

Esto no cargará plugins a nivel de sistema. Carga "solo locales". Es decir, lo que encuentra en el directorio ~/.trace-cmd/plugins.

-N

Esto no cargará ningún plugin.

-n evento-re

Esto hará que todos los eventos que coincidan con la opción ignoren cualquier manejador registrado (por los plugins) para imprimir el evento. Se imprimirá el evento normal en su lugar. El evento-re es una expresión regular según lo definido por regcomp(3).

--profile

Con la opción --profile, "trace-cmd report" procesará todos los eventos primero y luego generará un formato que muestra dónde han pasado el tiempo las tareas en el kernel, así como dónde están más bloqueadas y dónde están las latencias de activación. 
Vea trace-cmd-profile(1) para más detalles y ejemplos.

-G

Establece eventos de interrupción (suave y dura) como globales (asociados a la CPU en lugar de a las tareas). Solo funciona para --profile.

-H event-hooks

Añade coincidencia de eventos personalizada

g para conectar dos eventos juntos. 
Ver trace-cmd-profile(1) para el formato.

-R

Esto mostrará los eventos en formato "crudo" (raw). Es decir, ignorará el formato de impresión del evento y simplemente imprimirá el contenido de cada campo.

-r event-re

Esto hará que todos los eventos que coincidan con la opción impriman sus campos crudos. El event-re es una expresión regular tal como se define en regcomp(3).

-l

Esto añade un formato de "salida de latencia". Información sobre interrupciones deshabilitadas, soft irq deshabilitadas, la bandera "need_resched" establecida, el contador de preemption y el bloqueo del kernel (big kernel lock) se registran con cada evento. Pero la visualización por defecto no muestra esta información. Esta opción mostrará esta información con 6 caracteres. Cuando uno de los campos es cero o N/A se muestra un '.'.
      <idle>-0       0d.h1. 106467.859747: function:             ktime_get <-- tick_check_idle
El 0d.h1. denota esta información.
Comienza con un número. Este representa el número de CPU en el que ocurrió el
  evento.
El segundo carácter es uno de los siguientes:
'd' - Interrupciones deshabilitadas
'.' - Interrupciones habilitadas
'X' - Tiene banderas que aún no son conocidas por trace-cmd
El tercer carácter es la bandera "need rescheduling".
'N' - Se establece una planificación para que tenga lugar
'.' - No hay planificación establecida
El cuarto carácter representa el contexto en el que se encontraba el evento
  cuando se disparó
'h' - Contexto de interrupción dura (hard interrupt context)
's' - Contexto de interrupción suave (soft interrupt context)
'H' - Contexto de interrupción dura que interrumpió una interrupción suave
'.' - Contexto normal
Lo siguiente es un número (debería ser menor que 10), que representa la
  profundidad de preemption (el número de veces que se llama a
  preempt_disable() sin preempt_enable()). '.' significa que la preemption
  está habilitada.
En algunos sistemas, puede existir "migrate disable" (deshabilitación de
  migración), en cuyo caso se mostrará un número para ello, o '.' que significa
  que la migración está habilitada.
Si lockdep está habilitado en el sistema, entonces el número representa la
  profundidad de los bloqueos que se mantienen cuando se disparó el evento. '.'
  significa que no se mantienen bloqueos.

-w

Si tanto los eventos sched_switch como sched_wakeup están habilitados, esta opción informará la latencia entre el momento en que la tarea fue despertada por primera vez y el momento en que fue programada.

-q

Silencia advertencias no críticas.

-O

Pasa opciones a los plugins de trace-cmd que están cargados. 
-O plugin:var=value
El 'plugin:' y '=value' son opcionales. El valor puede omitirse para opciones
  booleanas. Si se omite el 'plugin:', se establecerá cualquier variable que
  coincida en todos los plugins.
Ejemplo:  -O fgraph:tailprint

--cpu <lista de cpu>

Lista de CPUs, separadas por "," o ":", utilizada para filtrar los eventos. Se puede especificar un rango de CPUs utilizando la notación "cpuX-cpuY", donde todas las CPUs en el rango entre cpuX y cpuY se incluirán en la lista. El orden de las CPUs en la lista debe ser de menor a mayor. 
Ejemplo:  "--cpu 0,3" - mostrar eventos de CPUs 0 y 3
          "--cpu 2-4" - mostrar eventos de CPUs 2, 3 y 4

--cpus

Lista las CPUs que tienen datos en el archivo de traza y sale.

--first-event

Muestra la marca de tiempo del primer evento de todas las CPUs que tienen datos.

--last-event

Muestra la marca de tiempo del último evento de todas las CPUs que tienen datos.

--stat

Si el archivo trace.dat registró las estadísticas finales (salidas al final de la grabación), la opción --stat puede usarse para recuperarlas.

--uname

Si el archivo trace.dat registró uname durante la ejecución, esto recuperará esa información.

--version

Si el archivo trace.dat registró la versión del ejecutable utilizado para crearlo, informará esa versión.

--ts-offset offset

Añade (o resta si es negativo) un desplazamiento a todas las marcas de tiempo del archivo de datos especificado previamente con -i. Esto es útil para fusionar y ordenar múltiples archivos trace.dat donde se conoce la diferencia en la marca de tiempo. Por ejemplo, si se realiza una traza en una máquina virtual invitada y otra traza en el host. Si la marca de tiempo del host está 1000 unidades por delante de la invitada, se puede hacer lo siguiente: 
trace-cmd report -i host.dat --ts-offset -1000 -i guest.dat
Esto restará 1000 unidades de marca de tiempo a todos los eventos del host
  mientras se fusionan con los eventos de guest.dat. Tenga en cuenta que las
  unidades son las unidades crudas registradas en la traza. Si las unidades son
  nanosegundos, la adición (o sustracción) del desplazamiento serán nanosegundos,
  incluso si las unidades mostradas son microsegundos.

--ts2secs HZ

Convierte la fuente de reloj actual en una salida de segundos (resolución en nanosegundos). Al usar relojes como x86-tsc, si se conoce la frecuencia, al proporcionar la frecuencia del reloj, esto convertirá el tiempo a segundos. 
Esta opción afecta a cualquier archivo trace.dat proporcionado con *-i* que le
  preceda. Si esta opción aparece antes que cualquier opción *-i*, entonces ese
  valor se convierte en el valor por defecto para todos los demás archivos
  trace.dat. Si aparece otra opción --ts2secs después de un archivo trace.dat
  con *-i*, entonces esa opción anulará el valor por defecto.
Ejemplo: En una máquina de 3.4 GHz
trace-cmd record -p function -C x86-tsc
trace-cmd report --ts2ns 3400000000
El informe convertirá las marcas de tiempo de ciclos en una visualización de
  segundos legible. La resolución de visualización por defecto es microsegundos,
  a menos que se utilice *-t*.
El valor de --ts-offset debe seguir estando en las unidades de marca de tiempo
  crudas, incluso con esta opción. El desplazamiento también se convertirá.

--ts-diff

Muestra las diferencias de tiempo entre eventos. La diferencia aparecerá entre paréntesis justo después de la marca de tiempo.

--ts-check

Asegura que ninguna marca de tiempo retroceda, y si lo hace, imprime un mensaje de advertencia al respecto.

--nodate

Ignora la conversión de las marcas de tiempo a la fecha establecida por la opción --date de trace-cmd record(3).

--raw-ts

Muestra marcas de tiempo crudas, sin ninguna corrección.

--align-ts

Muestra las marcas de tiempo alineadas con el primer evento.

--verbose[=nivel]

Establece el nivel de registro. Los niveles de registro soportados son "none", "crit", "err", "warn", "info", "debug", "all" o sus identificadores "0", "1", "2", "3", "4", "5", "6". Establecer el nivel de registro a un valor específico habilita todos los registros de ese nivel y de todos los niveles anteriores. El nivel por defecto será "info" si no se especifica uno. 
Ejemplo: habilitar todos los registros críticos, de error y de advertencia
trace-cmd report --verbose=warning

Es lo mismo que se explica en la opción -l. Donde la primera posición es:

'.' - significa interrupciones y bottom halves habilitadas
'd' - significa interrupciones y bottom halves deshabilitadas

La segunda posición:

'N' - significa que la bandera "NEED_RESCHED" está establecida y el kernel debe
      intentar programar lo antes posible.

ElTercera posición:

' . ' - En contexto normal/programable
's' - En contexto de interrupción suave
'h' - En contexto de interrupción dura
'H' - En contexto de interrupción dura que interrumpió una interrupción suave

La cuarta posición es la profundidad del contador de preempción:

'pass:[.]' - preempción habilitada
'#' - la profundidad de la preempción deshabilitada (anidada)

La quinta columna es el contador de migración deshabilitada:

' . ' - migración habilitada
'#' - la profundidad de la migración deshabilitada (anidada)

trace-cmd-report(1)

NAME

trace-cmd-report - reports the statistics of the recorded trace

SYNOPSIS

trace-cmd report [options]

DESCRIPTION

The trace-cmd(1) utility is a front-end for the kernel's trace capabilities (ftrace). The trace-cmd-record(1) command records the trace data into a file. The trace-cmd-report(1) command reads that file and displays the statistics of the trace. This includes scheduling events, system calls, function timings, etc., depending on what was enabled when the trace was recorded.

When a profile is given, trace-cmd-report will filter the events and only show information related to that profile. This is useful for analyzing specific types of events, like scheduling delays or Real Time task behavior.

The default output includes:

  • Wakeup events: Shows when a task was woken up and by which event.
  • Context switches: Shows when a task switched from running to sleeping or vice-versa.
  • Latency analysis: For scheduling events, it calculates the latency between a task being woken up and actually running.

The output format can vary depending on the options used during recording and reporting. Common information includes:

  • PID-Name [CPU]: Process ID, task name, and CPU core number.
  • Timestamp: Time of the event.
  • Event Type: The specific ftrace event (e.g., sched_wakeup, sched_switch).
  • Details: Additional information about the event, such as the task that was woken up, the CPU involved, or the latency.

The output can be quite verbose, especially for long traces. Filtering options can help to narrow down the information.

OPTIONS

The options available for trace-cmd-report(1) are extensive and can be used to filter and format the output. Some common ones include:

-n, --no-callgraph
Do not print the callgraph for events that have one.
-g, --callgraph
Print the callgraph for events.
-s, --sched
Show scheduling statistics.
-l, --latency
Show latency statistics for scheduling events.
-m, --max-latency
Show maximum latency statistics.
-f, --functions
Show function tracer statistics.
-i, --irq
Show interrupt handler statistics.
-p, --profile <profile_name>
Filter the report to show only events related to the specified profile.
-a, --all
Show all events, even those not explicitly enabled.
-o, --output <file>
Write the report to the specified file instead of stdout.
-d, --debug
Enable debug output.
-v, --verbose
Increase verbosity.

EXAMPLES

Report the default statistics from the recorded trace:

# trace-cmd report

Report scheduling statistics, including latency:

# trace-cmd report -s -l

Report the maximum latency statistics:

# trace-cmd report -m

Report statistics for Real Time (RT) tasks using a profile:

# trace-cmd record -p "sched_wakeup* sched_switch*" --profile rt_tasks
# trace-cmd report --profile rt_tasks
