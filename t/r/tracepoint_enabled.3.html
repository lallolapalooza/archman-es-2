DESCRIPCIÓN

El Linux Trace Toolkit: next generation es un paquete de software de código abierto utilizado para el trazado correlacionado del kernel de Linux, aplicaciones de usuario y bibliotecas de usuario.

LTTng-UST es el componente de trazado en el espacio de usuario del proyecto LTTng. Es un port a espacio de usuario de las capacidades de trazado de baja sobrecarga del trazador del kernel de Linux LTTng. La biblioteca liblttng-ust se utiliza para trazar aplicaciones y bibliotecas de usuario.


Nota

Esta página del manual trata sobre la biblioteca liblttng-ust. El proyecto LTTng-UST también proporciona paquetes Java y Python para trazar aplicaciones escritas en esos lenguajes. Cómo instrumentar y trazar aplicaciones Java y Python se documenta en la documentación en línea de LTTng http://lttng.org/docs/.

Hay tres formas de usar liblttng-ust:

•Usando la API de lttng_ust_tracef(3), que es similar a printf(3).
•Usando la API de lttng_ust_tracelog(3), que es lttng_ust_tracef(3) con un parámetro de nivel de registro.
•Definiendo tus propios puntos de traza. Ver la sección Creación de un proveedor de puntos de traza a continuación.

Compatibilidad con APIs anteriores

Desde LTTng-UST 2.13, la definición LTTNG_UST_COMPAT_API_VERSION controla qué APIs de LTTng-UST están disponibles (compiladas):

No definida

Todas las APIs están disponibles.

N (0 o entero positivo)

La versión de la API N, y todas las APIs existentes siguientes, están disponibles. Las APIs anteriores no están disponibles (no compiladas).

Creación de un proveedor de puntos de traza

Crear un proveedor de puntos de traza es el primer paso para usar liblttng-ust. Los siguientes pasos son:

•Instrumentar tu aplicación con llamadas a lttng_ust_tracepoint()
•Construir tu aplicación con soporte LTTng-UST, ya estáticamente o dinámicamente.

Un proveedor de tracepoint es un objeto compilado que contiene las sondas de eventos correspondientes a las definiciones de tracepoint personalizadas. Un proveedor de tracepoint contiene, entre otras cosas, el código para obtener el tamaño de un evento y serializarlo.

Para crear un proveedor de tracepoint, comience con la siguiente plantilla de encabezado de proveedor de tracepoint:

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * Aquí se utilizan LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), y `LTTNG_UST_TRACEPOINT_ENUM()`.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

En esta plantilla, el proveedor de tracepoint se llama my_provider (definición de LTTNG_UST_TRACEPOINT_PROVIDER). El archivo debe tener el nombre de la definición de LTTNG_UST_TRACEPOINT_INCLUDE (tp.h en este caso). Entre #include <lttng/tracepoint.h> y #endif van las invocaciones de las macros LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL() y LTTNG_UST_TRACEPOINT_ENUM().


Nota

Puede evitar escribir el prólogo y el epílogo repetitivos en el archivo de plantilla anterior utilizando la herramienta lttng-gen-tp(1) incluida con LTTng-UST.

El archivo de encabezado del proveedor de tracepoint debe incluirse en un archivo fuente que se vea así:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Juntos, esos dos archivos (llamémoslos tp.h y tp.c) forman las fuentes del proveedor de tracepoint, listos para ser compilados.

Puede crear varios proveedores de tracepoint para usarlos en una única aplicación, pero cada uno debe tener su propio archivo de encabezado.

Uso de LTTNG_UST_TRACEPOINT_EVENT()

La macro LTTNG_UST_TRACEPOINT_EVENT() se utiliza en un archivo de encabezado de proveedor de plantilla (consulte la sección Creación de un proveedor de tracepoint anterior) para definir tracepoints LTTng-UST.

La plantilla de uso de LTTNG_UST_TRACEPOINT_EVENT() es la siguiente:

LTTNG_UST_TRACEPOINT_EVENT(
    /* Nombre del proveedor de tracepoint */
    my_provider,
    /* Nombre del tracepoint/evento */
    my_tracepoint,
    /* Lista de argumentos del tracepoint (entrada) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Lista de campos del evento eventual (salida) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La macro LTTNG_UST_TP_ARGS() contiene los argumentos de entrada del tracepoint. Esos argumentos se pueden usar en las expresiones de los argumentos de los campos de salida definidos en LTTNG_UST_TP_FIELDS().

El formato de los parámetros de LTTNG_UST_TP_ARGS() es: tipo C, luego nombre del argumento; repita según sea necesario, hasta diez veces. Por ejemplo:

LTTNG_UST_TP_ARGS(
    int, my_int,
    const char *, my_string,
    FILE *, my_file,
    double, my_float,
    struct my_data *, my_data
)

La macro LTTNG_UST_TP_FIELDS() contiene los campos de salida del tracepoint, es decir, los datos reales que se pueden registrar en la carga útil de un evento emitido por este tracepoint.

La macro LTTNG_UST_TP_FIELDS() contiene una lista de macros lttng_ust_field_*() NO separadas por comas. Las macros disponibles se documentan en la sección de macros de tipos de campo Disponibles lttng_ust_field_*() a continuación.

lttng-ust-tracers - LTTng User Space Tracer macros

DESCRIPTION

LTTng-UST (Linux Trace Toolkit next Generation - User Space Tracer) is a tracing framework for user space applications. It allows developers to instrument their code and collect detailed execution traces.

This man page describes the C macros provided by LTTng-UST to define and emit tracepoints.

Creating a tracepoint provider

A tracepoint provider is a name given to a set of tracepoints. It is mandatory to declare a provider before defining any tracepoint belonging to it.

The LTTNG_UST_TRACEPOINT_PROVIDER() macro is used for this:

#define LTTNG_UST_TRACEPOINT_PROVIDER provider_name

provider_name must be a valid C identifier. All tracepoint definitions following this macro will belong to the specified provider until another LTTNG_UST_TRACEPOINT_PROVIDER() macro is encountered.

It is recommended to define the tracepoint provider name in a header file, and then include this header file in every C source file where you intend to define or use tracepoints from this provider.

Example:

/* my_provider.h */
#ifndef MY_PROVIDER_H
#define MY_PROVIDER_H
#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#include <lttng/tracepoint.h>
#endif /* MY_PROVIDER_H */

Defining tracepoints

Tracepoints are defined using either LTTNG_UST_TRACEPOINT_EVENT(), or the combination of LTTNG_UST_TRACEPOINT_EVENT_CLASS() and LTTNG_UST_TRACEPOINT_EVENT_INSTANCE().

LTTNG_UST_TRACEPOINT_EVENT() usage

This macro defines a new tracepoint event. It takes the following parameters:

LTTNG_UST_TRACEPOINT_EVENT(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

my_provider: The name of the tracepoint provider.

my_tracepoint: The name of the tracepoint event.

LTTNG_UST_TP_ARGS(...) defines the input arguments of the tracepoint. These arguments are passed by the tracer application when it calls the tracepoint. Each argument must be declared with its type and name, like a normal C function parameter.

LTTNG_UST_TP_FIELDS(...) defines the fields of the trace event that will be generated. These fields represent the data that will be recorded in the trace buffer. Each field must be declared with its type and name. The fields can be initialized using the values of the input arguments defined in LTTNG_UST_TP_ARGS().

See the EXAMPLE section below for a complete example.

Fields

Fields are declared using the following macros within LTTNG_UST_TP_FIELDS():

  • lttng_ust_field_integer(type, name, value);

    Records an integer field. type can be one of unsigned int, int, unsigned long, long, unsigned long long, long long. value is an expression that evaluates to the field's value.

  • lttng_ust_field_string(name, value);

    Records a null-terminated string field. value must be a pointer to a null-terminated string (char *).

  • lttng_ust_field_float(name, value);

    Records a single-precision floating point field. value is an expression that evaluates to the field's value.

  • lttng_ust_field_double(name, value);

    Records a double-precision floating point field. value is an expression that evaluates to the field's value.

  • lttng_ust_field_array(type, name, value, size);

    Records an array field. type is the type of the array elements (e.g. unsigned char, int). value is a pointer to the array. size is the number of elements in the array.

  • lttng_ust_field_enum(name, value);

    Records an enumeration field. value is an expression that evaluates to the integer value of the enumerated field. The mapping between integer values and their string representations is defined elsewhere using the LTTNG_UST_TRACEPOINT_ENUM() macro.

Note that the integer types for array elements are limited to C primitive types.

LTTNG_UST_TRACEPOINT_ENUM() usage

An enumeration field is a list of mappings between an integers, or a range of integers, and strings (sometimes called labels or enumerators). Enumeration fields can be used to have a more compact trace when the possible values for a field are limited.

An enumeration field is defined with the LTTNG_UST_TRACEPOINT_ENUM() macro:

LTTNG_UST_TRACEPOINT_ENUM(
    /* Tracepoint provider name */
    my_provider,
    /* Enumeration name (unique in the whole tracepoint provider) */
    my_enum,
    /* Enumeration mappings */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contains a list of enumeration mappings, NOT separated by commas. Two macros can be used in the LTTNG_UST_TP_ENUM_VALUES(): lttng_ust_field_enum_value() and lttng_ust_field_enum_range().

lttng_ust_field_enum_value() is a single value mapping:

lttng_ust_field_enum_value(label, value)

This macro maps the given label string to the value value.

lttng_ust_field_enum_range() is a range mapping:

lttng_ust_field_enum_range(label, start, end)

This macro maps the given label string to the range of integers from start to end, inclusively. Range mappings may overlap, but the behaviour is implementation-defined: each trace reader handles overlapping ranges as it wishes.

See the EXAMPLE section below for a complete example.

LTTNG_UST_TRACEPOINT_EVENT_CLASS() usage

A tracepoint class is a class of tracepoints sharing the same field types and names. A tracepoint instance is one instance of such a declared tracepoint class, with its own event name.

LTTng-UST creates one event serialization function per tracepoint class. Using LTTNG_UST_TRACEPOINT_EVENT() creates one tracepoint class per tracepoint definition, whereas using LTTNG_UST_TRACEPOINT_EVENT_CLASS() and LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() creates one tracepoint class, and one or more tracepoint instances of this class. In other words, many tracepoints can reuse the same serialization code. Reusing the same code, when possible, can reduce cache pollution, thus improve performance.

The LTTNG_UST_TRACEPOINT_EVENT_CLASS() macro accepts the same parameters as the LTTNG_UST_TRACEPOINT_EVENT() macro, except that instead of an event name, its second parameter is the tracepoint class name:

#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Tracepoint class provider name */
    my_provider,
    /* Tracepoint class name */
    my_tracepoint_class,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Once the tracepoint class is defined, you can create as many tracepoint instances as needed:

#define LTTNG_UST_TRACEPOINT_PROVIDER natality
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Name of the tracepoint class provider */
    my_provider,
    /* Tracepoint class name */
    my_tracepoint_class,
    /* Name of the local (instance) tracepoint provider */
    natality,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

As you can see, the LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() does not contain the LTTNG_UST_TP_FIELDS() macro, because they are defined at the LTTNG_UST_TRACEPOINT_EVENT_CLASS() level.

Note that the LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() macro requires two provider names:

•The name of the tracepoint class provider (my_provider in the example above).

This is the same as the first argument of the LTTNG_UST_TRACEPOINT_EVENT_CLASS() expansion to refer to.

•The name of the local, or instance, provider (natality in the example above).

This is the provider name which becomes the prefix part of the name of the events which such a tracepoint creates.

Instrumenting your application

Once the tracepoint provider is created (see the Creating a tracepoint provider section above), you can instrument your application with the defined tracepoints thanks to the lttng_ust_tracepoint() macro:

#define lttng_ust_tracepoint(prov_name, t_name, ...)

With:

prov_name

Tracepoint provider name.

t_name

Tracepoint/event name.

...

Tracepoint arguments, if any.

Make sure to include the tracepoint provider header file anywhere you use lttng_ust_tracepoint() for this provider.


Note

Even though LTTng-UST supports lttng_ust_tracepoint() call site duplicates having the same provider and tracepoint names, it is recommended to use a provider/tracepoint name pair only once within the application source code to help map events back to their call sites when analyzing the trace.

Sometimes, arguments to the tracepoint are expensive to compute (take call stack, for example). To avoid the computation when the tracepoint is disabled, you can use the lttng_ust_tracepoint_enabled() and lttng_ust_do_tracepoint() macros:

#define lttng_ust_tracepoint_enabled(prov_name, t_name)
#define lttng_ust_do_tracepoint(prov_name, t_name, ...)

lttng_ust_tracepoint_enabled() returns a non-zero value if the tracepoint named t_name from the provider named prov_name is enabled at run time.

lttng_ust_do_tracepoint() is like lttng_ust_tracepoint(), except that it doesn’t check if the tracepoint is enabled. Using lttng_ust_tracepoint() with lttng_ust_tracepoint_enabled() is dangerous since lttng_ust_tracepoint() also contains the lttng_ust_tracepoint_enabled() check, thus a race condition is possible in this situation:

if (lttng_ust_tracepoint_enabled(my_provider, my_tracepoint)) {
    stuff = prepare_stuff();
}
lttng_ust_tracepoint(my_provider, my_tracepoint, stuff);

If the tracepoint is enabled after the condition, then stuff is not prepared: the emitted event will either contain wrong data, or the whole application could crash (segmentation fault, for example).


Note

Neither lttng_ust_tracepoint_enabled() nor lttng_ust_do_tracepoint() have a STAP_PROBEV() call, so if you need it, you should emit this call yourself.

Tracing C/C++ runtime events

LTTng-UST provides macros to trace C/C++ runtime events such as memory allocations, function entry/exit, etc. These macros are meant to be used in conjunction with the runtime library initialization/deinitialization routines.

Memory allocation tracing

To trace memory allocations (malloc, calloc, realloc, free), you need to:

  • Include the tracing header file defining the tracepoints: 
    #define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#include <lttng/tracepoint.h>
  • Declare the memory allocation tracepoints. You can use the default provider name `lttng_ust` for this: 
    LTTNG_UST_TRACEPOINT_MEMORY_ALLOC(lttng_ust, malloc);
LTTNG_UST_TRACEPOINT_MEMORY_ALLOC(lttng_ust, calloc);
LTTNG_UST_TRACEPOINT_MEMORY_ALLOC(lttng_ust, realloc);
LTTNG_UST_TRACEPOINT_MEMORY_FREE(lttng_ust, free);
  • Initialize and finalize the tracing library: 
    lttng_ust_runtime_init();
/* ... your application code ... */
lttng_ust_runtime_finalize();

Note that the memory allocation tracepoint definitions are not tied to a specific provider name. You can use any provider name you want when declaring them.

The default provider name `lttng_ust` is used internally by lttng-ust to define its own runtime events. You can use this name for your own tracepoints as well. However, it is recommended to use a dedicated provider name for your application's tracepoints to avoid potential name collisions.

Function entry/exit tracing

To trace function entry and exit, you can use the following macros:

  • LTTNG_UST_TRACEPOINT_FUNCTION(): Traces the entry into a function. 
    LTTNG_UST_TRACEPOINT_FUNCTION(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_function_entry,
    /* Function name (string) */
    "my_function"
)
  • LTTNG_UST_TRACEPOINT_FUNCTION_RETURN(): Traces the exit from a function. 
    LTTNG_UST_TRACEPOINT_FUNCTION_RETURN(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_function_exit,
    /* Function name (string) */
    "my_function"
)

These macros automatically generate the necessary fields (function name, return address, etc.) to record the event. You typically use them at the beginning and end of your functions:

#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#include <lttng/tracepoint.h>

void my_function(int arg) {
    LTTNG_UST_TRACEPOINT_FUNCTION(my_provider, my_function_entry, "my_function");
    /* ... function body ... */
    LTTNG_UST_TRACEPOINT_FUNCTION_RETURN(my_provider, my_function_exit, "my_function");
}

Note that the function name provided to these macros should match across the entry and exit tracepoints for a given function.

EXAMPLE

Here is a complete example of how to define and use tracepoints:

/*
 * File: my_provider.h
 */
#ifndef MY_PROVIDER_H
#define MY_PROVIDER_H
#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#include <lttng/tracepoint.h>

/* Tracepoint class definition */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    my_provider,      /* Provider name */
    my_class,         /* Tracepoint class name */
    LTTNG_UST_TP_ARGS(
        int magic,
        const char *msg
    ),
    LTTNG_UST_TP_FIELDS(
        lttng_ust_field_integer(int, magic_field, magic);
        lttng_ust_field_string(msg_field, msg);
        lttng_ust_field_integer(int, status, 0); /* Default status */
    )
);

/* Tracepoint instance definition */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    my_provider,      /* Tracepoint class provider name */
    my_class,         /* Tracepoint class name */
    my_provider,      /* Local provider name */
    my_event,         /* Tracepoint event name */
    LTTNG_UST_TP_ARGS(
        int magic,
        const char *msg
    )
);

/* Another tracepoint instance using the same class */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    my_provider,      /* Tracepoint class provider name */
    my_class,         /* Tracepoint class name */
    another_provider, /* Local provider name */
    another_event,    /* Tracepoint event name */
    LTTNG_UST_TP_ARGS(
        int magic,
        const char *msg
    )
);

/* Enumeration definition */
LTTNG_UST_TRACEPOINT_ENUM(
    my_provider,
    my_status_enum,
    LTTNG_UST_TP_ENUM_VALUES(
        lttng_ust_field_enum_value(success, 0);
        lttng_ust_field_enum_value(failure, 1);
        lttng_ust_field_enum_range(pending, 2, 5);
    )
);

/* Tracepoint using the enumeration field */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    my_provider,
    my_class_with_enum,
    LTTNG_UST_TP_ARGS(
        int state
    ),
    LTTNG_UST_TP_FIELDS(
        lttng_ust_field_enum(state_field, state);
    )
);

LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    my_provider,
    my_class_with_enum,
    my_provider,
    enum_event,
    LTTNG_UST_TP_ARGS(
        int state
    )
);

/* Assigning a log level */
LTTNG_UST_TRACEPOINT_LOGLEVEL(
    my_provider,
    my_event,
    LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
);

#endif /* MY_PROVIDER_H */

/*
 * File: main.c
 */
#include "my_provider.h"
#include <stdio.h>

int main() {
    int magic_num = 42;
    const char *message = "Hello LTTng!";
    int state_code = 3; /* Corresponds to 'pending' */

    /* Emit the tracepoint event */
    lttng_ust_tracepoint(my_provider, my_event, magic_num, message);

    /* Emit the tracepoint event with a different provider */
    lttng_ust_tracepoint(another_provider, another_event, magic_num, message);

    /* Emit the tracepoint using the enumeration */
    lttng_ust_tracepoint(my_provider, enum_event, state_code);

    /* Example using enabled/do macros to avoid computation */
    if (lttng_ust_tracepoint_enabled(my_provider, my_event)) {
        printf("Tracepoint my_provider:my_event is enabled.\n");
        /* Prepare expensive data only if tracepoint is enabled */
        magic_num = 123;
        message = "Expensive data prepared.";
    }
    /* This call will always happen, but arguments are only prepared if needed */
    lttng_ust_do_tracepoint(my_provider, my_event, magic_num, message);


    return 0;
}

En este caso, qué constructores y destructores de C++ exactos no serán rastreados dependerá del orden de inicialización dentro de cada unidad de traducción y entre todas las unidades de traducción cuando se enlazan juntas.

Enlace estático del proveedor de puntos de traza

Con el método de enlace estático, los proveedores de puntos de traza compilados se copian en la aplicación de destino.

Define la macro LTTNG_UST_TRACEPOINT_DEFINE debajo de la definición de LTTNG_UST_TRACEPOINT_CREATE_PROBES en el código fuente del proveedor de puntos de traza:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Crea el archivo objeto del proveedor de puntos de traza:

$ cc -c -I. tp.c

Nota

Aunque una aplicación instrumentada con puntos de traza LTTng-UST puede compilarse con un compilador C++, las sondas de puntos de traza deben compilarse con un compilador C.

En este punto, puedes archivar este archivo objeto del proveedor de puntos de traza, posiblemente con otros archivos objeto de tu aplicación o con otros archivos objeto de proveedores de puntos de traza, como una biblioteca estática:

$ ar rc tp.a tp.o

El uso de una biblioteca estática tiene la ventaja de centralizar los objetos del proveedor de puntos de traza para que puedan ser compartidos entre múltiples aplicaciones. De esta manera, cuando se modifica el proveedor de puntos de traza, los cambios en el código fuente no tienen que ser parcheados en el árbol de código fuente de cada aplicación. Las aplicaciones necesitan ser relinkeadas después de cada cambio, pero no necesitan ser recompiladas de otra manera (a menos que la API del proveedor de puntos de traza cambie).

Luego, enlaza tu aplicación con este archivo objeto (o con la biblioteca estática que lo contiene) y con liblttng-ust y libdl (libc en un sistema BSD):

$ cc -o app tp.o app.o -llttng-ust -ldl

Carga dinámica del proveedor de puntos de traza

El segundo enfoque para empaquetar el proveedor de puntos de traza es usar el cargador dinámico: la biblioteca y sus funciones miembro se buscan explícitamente, se cargan en tiempo de ejecución.

En este escenario, el proveedor de puntos de traza se compila como un objeto compartido.

El proceso para crear el objeto compartido del proveedor de puntos de traza es muy similar al del método de enlace estático, excepto que:

•Dado que el proveedor de puntos de traza no forma parte de la aplicación, LTTNG_UST_TRACEPOINT_DEFINE debe definirse, para cada proveedor de puntos de traza, en exactamente un archivo fuente de la aplicación.
•LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE debe definirse junto a LTTNG_UST_TRACEPOINT_DEFINE.

En cuanto a LTTNG_UST_TRACEPOINT_DEFINE y LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la práctica recomendada es usar un archivo fuente C separado en tu aplicación para definirlos, y luego incluir los archivos de cabecera del proveedor de puntos de traza después. Por ejemplo, como tp-define.c:

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

El archivo objeto del proveedor de puntos de traza utilizado para crear la biblioteca compartida se construye como en el método de enlace estático, pero con la opción -fpic:

$ cc -c -fpic -I. tp.c

Luego se enlaza como una biblioteca compartida de esta manera:

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Este objeto compartido del proveedor de puntos de traza no se enlaza con la aplicación de usuario: debe cargarse manualmente. Es por eso que la aplicación se construye sin mención de este proveedor de puntos de traza, pero aún necesita libdl:

$ cc -o app app.o tp-define.o -ldl

Hay dos formas de cargar dinámicamente el objeto compartido del proveedor de puntos de traza:

•Cargarlo manualmente desde la aplicación usando dlopen(3).
•Hacer que el cargador dinámico lo cargue con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Si la aplicación no carga dinámicamente el objeto compartido del proveedor de puntos de traza usando uno de los métodos anteriores, el rastreo se deshabilita para esta aplicación, y los eventos no se listan en la salida de lttng-list(1).

Ten en cuenta que no es seguro usar dlclose(3) en un objeto compartido de proveedor de puntos de traza que se está utilizando activamente para rastrear, debido a la falta de conteo de referencias de LTTng-UST al objeto compartido.

Por ejemplo, enlazar estáticamente un proveedor de puntos de traza a un objeto compartido que será cargado dinámicamente por una aplicación (un plugin, por ejemplo) no es seguro: el objeto compartido, que contiene el proveedor de puntos de traza, podría ser cerrado dinámicamente (dlclose(3)) en cualquier momento por la aplicación.

Para instrumentar un objeto compartido, haz una de las siguientes opciones:

•Enlaza estáticamente el proveedor de puntos de traza a la aplicación, o
•Compila el proveedor de puntos de traza como un objeto compartido (siguiendo el procedimiento mostrado en esta sección), y cárgalo previamente cuando se necesite rastrear usando la variable de entorno LD_PRELOAD.

Uso de LTTng-UST con demonios

Se necesita un cuidado adicional al usar liblttng-ust con aplicaciones demonio que llaman a fork(2), clone(2), o rfork(2) de BSD sin una llamada posterior a la familia de llamadas al sistema exec(3). La biblioteca liblttng-ust-fork.so necesita ser precargada antes de iniciar la aplicación con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Para usar liblttng-ust con una aplicación demonio que cierra descriptores de archivo que no fueron abiertos por ella, precarga la biblioteca liblttng-ust-fd.so antes de iniciar la aplicación. Los casos de uso típicos incluyen demonios que cierran todos los descriptores de archivo después de fork(2), y aplicaciones defectuosas que realizan "dobles cierres".

Detectar si LTTng-UST está cargado

Para detectar si liblttng-ust está cargado desde una aplicación:

1.Define el símbolo débil lttng_ust_loaded globalmente: 
int lttng_ust_loaded __attribute__((weak));

Este símbolo débil es establecido por el constructor de liblttng-ust.

2.Prueba lttng_ust_loaded donde sea necesario: 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST está cargado */
} else {
    /* LTTng-UST NO está cargado */
}
/* ... */

VARIABLES DE ENTORNO

LTTNG_HOME

Directorio de inicio alternativo del usuario. Esta variable es útil cuando el usuario que ejecuta la aplicación instrumentada tiene un directorio de inicio no escribible. Esta ruta es donde se encuentran los sockets Unix para la comunicación con el demonio de sesión por usuario.

LTTNG_UST_ABORT_ON_CRITICAL

Si está configurada, aborta la aplicación instrumentada en un mensaje de error crítico.

LTTNG_UST_ALLOW_BLOCKING

Si está configurada, permite a la aplicación reintentar el trazado de eventos cuando no hay espacio para el registro del evento en el sub-búfer, bloqueando efectivamente la aplicación hasta que se libere espacio o se alcance el tiempo de espera configurado.

Para permitir que una aplicación se bloquee durante el trazado, también debes especificar un tiempo de espera de bloqueo cuando creas un canal con la opción --blocking-timeout del comando lttng-enable-channel(1).

Esta opción puede ser útil en cargas de trabajo que generan un rendimiento de datos de trazas muy grande, donde bloquear la aplicación es un compromiso aceptable para evitar descartar registros de eventos.


Advertencia
Configurar esta variable de entorno puede afectar significativamente los tiempos de la aplicación.

LTTNG_UST_APP_PATH

Ruta del directorio donde se espera que el demonio de sesión LTTng coloque los siguientes archivos para recibir solicitudes de conexión de aplicaciones instrumentadas:
•El socket Unix de registro de la aplicación.
•Los archivos de memoria compartida de "espera" para despertar a las aplicaciones instrumentadas que esperan a que se inicie un demonio de sesión.
•El archivo de puerto del agente.

Este archivo contiene el puerto TCP al que los agentes deben conectarse para habilitar el trazado LTTng.

Este directorio debe existir cuando inicies la aplicación para que se habilite el trazado LTTng.

Cuando LTTNG_UST_APP_PATH está configurado, liblttng-ust:

•Solo considera esta ruta para conectarse a un demonio de sesión.
•No se conectará a demonios de sesión raíz y/o de usuario como de costumbre.

Consulta la variable de entorno correspondiente LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Ruta al objeto compartido que actúa como plugin de anulación de reloj. Un ejemplo de dicho plugin se puede encontrar en la documentación de LTTng-UST bajo examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

VARIABLES DE ENTORNO

LTTNG_UST_DEBUG

Si se establece, habilita la salida de depuración y error de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Ruta al objeto compartido que actúa como el plugin de reemplazo de getcpu(). Un ejemplo de dicho plugin se puede encontrar en la documentación de LTTng-UST bajo examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si se establece, anula la política utilizada para poblar las páginas de memoria compartida dentro de la aplicación.

Los valores posibles son:

none (por defecto)

No pre-poblar ninguna página: tomar fallos menores en el primer acceso mientras se traza.

cpu_possible

Pre-poblar páginas para todas las CPUs posibles en el sistema, como se muestra en /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Tiempo de espera para el comando del demonio de sesión de registration done antes de proceder a ejecutar el programa principal (milisegundos).

El valor 0 significa no esperar. El valor -1 significa esperar para siempre. Se recomienda establecer esta variable de entorno a 0 para aplicaciones con restricciones de tiempo en el tiempo de inicio del proceso.

Por defecto: 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si se establece, evita que liblttng-ust realice un volcado de estado de la dirección base (ver la sección Vuelto de estado de LTTng-UST arriba).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si se establece, evita que liblttng-ust realice un volcado de estado del nombre de proceso (ver la sección Vuelto de estado de LTTng-UST arriba).
