NOMBRE

transchan - API del manejador de comandos de transformaciones de canal

SINOPSIS

prefijoCmd opción ?arg arg ...?

DESCRIPCIÓN

El manejador a nivel de Tcl para una transformación de canal debe ser un comando con subcomandos (denominado un conjunto a pesar de no implicar que deba crearse con namespace ensemble create; este mecanismo no está vinculado a namespace ensemble de ninguna manera). Tenga en cuenta que prefijoCmd es lo que se especificó en la llamada a chan push, y puede constar de varios argumentos; esto se expandirá a varias palabras en lugar del prefijo.

De todos los subcomandos posibles, el manejador *debe* admitir initialize y finalize. Las transformaciones para canales escribibles también deben admitir write, y las transformaciones para canales legibles también deben admitir read.

Tenga en cuenta que en las descripciones a continuación, prefijoCmd puede ser más de una palabra, y manejador es el valor devuelto por la llamada a chan push utilizada para crear la transformación.

SUBCOMANDOS GENÉRICOS

Los siguientes subcomandos son relevantes para todos los tipos de canales.

prefijoCmd clear manejador
Este subcomando opcional se llama para indicar a la transformación que se deben borrar los datos almacenados en búferes internos (entrantes o salientes). Se llama cuando se realiza un chan seek en el canal que se está transformando.
prefijoCmd finalize manejador
Este subcomando obligatorio se llama por última vez para el manejador dado, y luego nunca más, y existe para permitir la limpieza de cualquier estructura de datos a nivel de Tcl asociada con la transformación. *¡Advertencia!* Se ignorarán todos los errores generados por este subcomando. No se garantiza que se llame si se elimina el intérprete.
prefijoCmd initialize manejador modo
Este subcomando obligatorio se llama por primera vez, y luego nunca más (para el manejador dado). Su responsabilidad es inicializar todas las partes de la transformación a nivel de Tcl. El modo es una lista que contiene cualquiera de read y write.
write
implica que el canal es escribible.
read
implica que el canal es legible.

El valor de retorno del subcomando debe ser una lista que contenga los nombres de todos los subcomandos admitidos por este manejador. Cualquier error generado por el subcomando evitará la creación de la transformación. El error generado aparecerá como un error generado por chan push.

SUBCOMANDOS RELACIONADOS CON LA LECTURA

Estos subcomandos se utilizan para manejar transformaciones aplicadas a canales legibles; aunque estrictamente read es opcional, debe ser admitido si alguno de los otros lo es o el canal se hará no legible.

prefijoCmd drain manejador
Este subcomando opcional se llama cada vez que los datos en el búfer de entrada (es decir, de lectura) de la transformación deben forzarse hacia arriba, es decir, hacia el usuario o el script. El resultado devuelto por el método se toma como los datos *binarios* para empujar hacia arriba al nivel superior a esta transformación (el lector o una transformación de nivel superior).

En otras palabras, cuando se llama a este método, la transformación no puede seguir posponiendo la operación de transformación real y debe transformar todos los datos que esperan en sus búferes de lectura internos y devolver el resultado de esa acción.

prefijoCmd limit? manejador
Este subcomando opcional se llama para permitir que el motor de E/S de Tcl determine cuántos datos debe leer por adelantado. Si está presente, debe devolver un número entero mayor que cero que indique cuántos bytes por adelantado se deben leer, o un número entero menor que cero para indicar que el motor de E/S puede leer tantos datos por adelantado como desee.
prefijoCmd read manejador búfer
Este subcomando, que debe estar presente si la transformación va a funcionar con canales legibles, se llama cada vez que el canal base, o una transformación por debajo de esta transformación, empuja datos hacia arriba. El búfer contiene los datos binarios que nos han sido proporcionados desde abajo. La responsabilidad de este subcomando es realmente transformar los datos. El resultado devuelto por el subcomando se toma como los datos binarios para empujar más arriba a la transformación por encima de esta transformación. Este también puede ser el usuario o el script que originalmente leyó del canal.

Tenga en cuenta que se permite que el resultado esté vacío, o incluso sea menor que los datos que recibimos; la transformación no está obligada a transformar todo lo que se le da ahora mismo. Se le permite almacenar los datos entrantes en búferes internos y posponer la transformación real hasta que tenga más datos.

SUBCOMANDOS RELACIONADOS CON LA ESCRITURA

Estos subcomandos se utilizan para manejar transformaciones aplicadas a canales escribibles; aunque estrictamente write es opcional, debe ser admitido si alguno de los otros lo es o el canal se hará no escribible.

prefijoCmd flush manejador
Este subcomando opcional se llama cada vez que los datos en el búfer de 'escritura' de la transformación deben forzarse hacia abajo, es decir, hacia el canal base. El resultado devuelto por el subcomando se toma como los datos binarios para escribir en la transformación debajo de la transformación actual. Este también puede ser el canal base.

En otras palabras, cuando se llama a este subcomando, la transformación no puede seguir posponiendo la operación de transformación real y debe transformar todos los datos que esperan en sus búferes de escritura internos y devolver el resultado de esa acción.

prefijoCmd write manejador búfer
Este subcomando, que debe estar presente si la transformación va a funcionar con canales escribibles, se llama cada vez que el usuario, o una transformación por encima de esta transformación, escribe datos hacia abajo. El búfer contiene los datos binarios que se nos han escrito. La responsabilidad de este subcomando es realmente transformar los datos.

El resultado devuelto por el subcomando se toma como los datos binarios para escribir en la transformación debajo de esta transformación. Este también puede ser el canal base. Tenga en cuenta que se permite que el resultado esté vacío, o sea menor que los datos que obtuvimos; la transformación no está obligada a transformar todo lo que se le escribió ahora mismo. Se le permite almacenar estos datos en búferes internos y posponer la transformación real hasta que tenga más datos.
