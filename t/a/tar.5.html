TAR(5) Manual de formatos de archivo TAR(5)

NOMBRE

tar — formato de archivos de cinta de archivo

DESCRIPCIÓN

El formato de archivo tar recopila cualquier número de archivos, directorios y otros objetos del sistema de archivos (enlaces simbólicos, nodos de dispositivos, etc.) en un único flujo de bytes. El formato se diseñó originalmente para ser utilizado con unidades de cinta que operan con bloques de tamaño fijo, pero se utiliza ampliamente como un mecanismo general de empaquetado.

Formato General

Un archivo tar consta de una serie de registros de 512 bytes. Cada objeto del sistema de archivos requiere un registro de cabecera que almacena metadatos básicos (nombre de ruta, propietario, permisos, etc.) y cero o más registros que contienen datos del archivo. El final del archivo se indica mediante dos registros que consisten enteramente en bytes cero.

Para compatibilidad con unidades de cinta que utilizan tamaños de bloque fijos, los programas que leen o escriben archivos tar siempre leen o escriben un número fijo de registros con cada operación de E/S. Estos "bloques" son siempre un múltiplo del tamaño del registro. El tamaño máximo de bloque admitido por las primeras implementaciones era de 10240 bytes o 20 registros. Este sigue siendo el valor predeterminado para la mayoría de las implementaciones, aunque los tamaños de bloque de 1MiB (2048 registros) o mayores se utilizan comúnmente con unidades de cinta modernas de alta velocidad. (Nota: los términos "bloque" y "registro" aquí no son totalmente estándar; este documento sigue la convención establecida por John Gilmore al documentar pdtar).

Formato de Archivo Estilo Antiguo

El formato de archivo tar original se ha ampliado muchas veces para incluir información adicional que varios implementadores consideraron necesaria. Esta sección describe la variante implementada por el comando tar incluido en UNIX AT&T Versión 7, que parece ser la versión más antigua de uso general del programa tar.

El registro de cabecera para un archivo tar de estilo antiguo consta de lo siguiente:

struct header_old_tar {
	char name[100];
	char mode[8];
	char uid[8];
	char gid[8];
	char size[12];
	char mtime[12];
	char checksum[8];
	char linkflag[1];
	char linkname[100];
	char pad[255];
};
Todos los bytes no utilizados en el registro de cabecera se rellenan con ceros.
name
Nombre de ruta, almacenado como una cadena terminada en nulo. Las primeras implementaciones de tar solo almacenaban archivos regulares (incluidos los enlaces duros a esos archivos). Una convención temprana común utilizaba un carácter "/" al final para indicar un nombre de directorio, permitiendo que los permisos del directorio y la información del propietario se archiven y restauren.
mode
Modo de archivo, almacenado como un número octal en ASCII.
uid, gid
ID de usuario y ID de grupo del propietario, como números octales en ASCII.
size
Tamaño del archivo, como número octal en ASCII. Solo para archivos regulares, esto indica la cantidad de datos que siguen a la cabecera. En particular, este campo fue ignorado por las primeras implementaciones de tar al extraer enlaces duros. Los escritores modernos siempre deben almacenar una longitud cero para las entradas de enlaces duros.
mtime
Tiempo de modificación del archivo, como número octal en ASCII. Esto indica el número de segundos desde el inicio de la época, 00:00:00 UTC del 1 de enero de 1970. Tenga en cuenta que se deben evitar los valores negativos aquí, ya que se manejan de manera inconsistente.
checksum
Suma de comprobación de la cabecera, almacenada como un número octal en ASCII. Para calcular la suma de comprobación, establezca el campo de suma de comprobación en todos los espacios, luego sume todos los bytes de la cabecera utilizando aritmética sin signo. Este campo debe almacenarse como seis dígitos octales seguidos de un carácter nulo y un espacio. Tenga en cuenta que muchas implementaciones tempranas de tar utilizaron aritmética con signo para el campo de suma de comprobación, lo que puede causar problemas de interoperabilidad al transferir archivos entre sistemas. Los lectores modernos robustos calculan la suma de comprobación de ambas maneras y aceptan la cabecera si cualquiera de los cálculos coincide.
linkflag, linkname
Para preservar los enlaces duros y conservar cinta, un archivo con múltiples enlaces solo se escribe en el archivo la primera vez que se encuentra. La próxima vez que se encuentre, el linkflag se establece en un carácter ASCII '1' y el campo linkname contiene el primer nombre bajo el cual aparece este archivo. (Tenga en cuenta que los archivos regulares tienen un valor nulo en el campo linkflag).

Las primeras implementaciones de tar variaron en cómo terminaban estos campos. El comando tar en UNIX AT&T Versión 7 utilizó las siguientes convenciones (esto también se documenta en los manuales de BSD tempranos): el nombre de ruta debe estar terminado en nulo; los campos modo, uid y gid deben terminar en un espacio y un byte nulo; los campos de tamaño y mtime deben terminar en un espacio; la suma de comprobación está terminada por un nulo y un espacio. Las primeras implementaciones rellenaban los campos numéricos con espacios iniciales. Esta parece haber sido una práctica común hasta que se publicó el estándar IEEE Std 1003.1-1988 ("POSIX.1"). Para una máxima portabilidad, las implementaciones modernas deben rellenar los campos numéricos con ceros iniciales.

Archivos Previos a POSIX

Un borrador temprano de IEEE Std 1003.1-1988 ("POSIX.1") sirvió de base para el programa pdtar de John Gilmore y muchas implementaciones de sistemas de finales de los 80 y principios de los 90. Estos archivos generalmente siguen el formato ustar de POSIX descrito a continuación con las siguientes variaciones:

  • El valor mágico consta de los cinco caracteres "ustar" seguidos de un espacio. El campo de versión contiene un carácter de espacio seguido de un nulo.
  • Los campos numéricos generalmente se rellenan con espacios iniciales (no ceros iniciales como se recomienda en el estándar final).
  • El campo de prefijo a menudo no se utiliza, lo que limita los nombres de ruta a los 100 caracteres de los archivos de estilo antiguo.

Archivos ustar POSIX

IEEE Std 1003.1-1988 ("POSIX.1") definió un formato de archivo tar estándar para ser leído y escrito por implementaciones conformes de tar(1). Este formato a menudo se denomina formato "ustar", por el valor mágico utilizado en la cabecera. (El nombre es un acrónimo de "Unix Standard TAR"). Extiende el formato histórico con nuevos campos:

struct header_posix_ustar {
	char name[100];
	char mode[8];
	char uid[8];
	char gid[8];
	char size[12];
	char mtime[12];
	char checksum[8];
	char typeflag[1];
	char linkname[100];
	char magic[6];
	char version[2];
	char uname[32];
	char gname[32];
	char devmajor[8];
	char devminor[8];
	char prefix[155];
	char pad[12];
};
typeflag
Tipo de entrada. POSIX amplió el campo anterior linkflag con varios valores de tipo nuevos:
“0”
Archivo regular. NUL debe tratarse como un sinónimo, para fines de compatibilidad.
“1”
Enlace duro.
“2”
Enlace simbólico.
“3”
Nodo de dispositivo de carácter.
“4”
Nodo de dispositivo de bloque.
“5”
Directorio.
“6”
Nodo FIFO.
“7”
Reservado.
Otro
Una implementación conforme a POSIX debe tratar cualquier valor typeflag no reconocido como un archivo regular. En particular, los escritores deben asegurarse de que todas las entradas tengan un nombre de archivo válido para que puedan ser restauradas por lectores que no admitan la extensión correspondiente. Las letras mayúsculas "A" a "Z" están reservadas para extensiones personalizadas. Tenga en cuenta que los sockets y las entradas de "whiteout" no son archivables.
Cabe señalar que el campo size, en particular, tiene diferentes significados según el tipo. Para archivos regulares, por supuesto, indica la cantidad de datos que siguen a la cabecera. Para directorios, puede usarse para indicar el tamaño total de todos

Formato Ustar

El formato ustar (tar unificado) se define en la Norma IEEE Std 1003.1-1990. Se basa en el formato de cabecera original de tar, pero agrega campos y restricciones para mejorar la portabilidad.

name
El nombre del archivo, codificado como ASCII con terminación NUL. Los nombres deben ser compatibles con el sistema de archivos de destino. El formato estándar solo permite nombres de archivo de hasta 100 bytes. Los directorios deben terminar con una barra inclinada (/).
mode
Los permisos del archivo y el tipo de archivo. Los permisos se almacenan como un número octal de 12 dígitos, con un carácter NUL de terminación. Los valores de tipo de archivo también se almacenan aquí.
uid, gid
El ID numérico del usuario y del grupo propietario, almacenado como un número octal de 6 dígitos con un carácter de espacio o NUL de terminación.
size
El tamaño del archivo en bytes, almacenado como un número octal de 11 dígitos con un carácter de espacio o NUL de terminación. Este campo solo se usa para archivos regulares.
mtime
La hora de la última modificación del archivo, almacenada como un número octal de 11 dígitos de segundos desde la época (Epoch), con un carácter de espacio o NUL de terminación. Para los archivos regulares, este campo debe estar establecido.
chksum
La suma de verificación del encabezado, almacenada como un número octal de 6 dígitos con dos caracteres de espacio de terminación. Este campo se utiliza para verificar la integridad del encabezado. Se calcula sumando los valores de los bytes del encabezado, tratando los bytes del campo chksum como si fueran espacios.
typeflag
El tipo de archivo. Los valores comunes incluyen:
  • �: Archivo regular.
  • /: Enlace simbólico.
  • 0 o �: Archivo regular.
  • 1: Enlace simbólico.
  • 2: Archivo de dispositivo de caracteres.
  • 3: Archivo de dispositivo de bloques.
  • 4: Directorio.
  • 5: Archivo FIFO (tubería con nombre).
  • 6: Archivo de socket.

Este campo debe ser un solo carácter ASCII. Para los archivos regulares, este campo puede contener el byte NUL, que es el valor predeterminado para los archivos de sistemas que preasignan espacio en el directorio. Para todos los demás tipos, debe ser establecido a cero por los escritores e ignorado por los lectores.

linkname
El nombre del archivo al que apunta un enlace simbólico. Este campo es solo para enlaces simbólicos.
magic
Contiene el valor mágico "ustar" seguido de un byte NUL para indicar que este es un archivo estándar POSIX. El cumplimiento total requiere que los campos uname y gname estén correctamente establecidos.
version
Versión. Debe ser "00" (dos copias del dígito cero ASCII) para archivos estándar POSIX.
uname, gname
Nombres de usuario y grupo, como cadenas ASCII terminadas en NUL. Estos deben usarse preferentemente sobre los valores uid/gid cuando estén establecidos y los nombres correspondientes existan en el sistema.
devmajor, devminor
Números mayor y menor para la entrada del dispositivo de caracteres o de bloques.
name, prefix
Si la ruta del archivo es demasiado larga para caber en los 100 bytes proporcionados por el formato estándar, puede dividirse en cualquier carácter / con la primera porción yendo al campo prefix. Si el campo prefix no está vacío, el lector antepondrá el valor del prefijo y un carácter / al campo de nombre regular para obtener la ruta completa del archivo. El estándar no requiere un carácter / final en los nombres de directorio, aunque la mayoría de las implementaciones todavía lo incluyen por razones de compatibilidad.

Tenga en cuenta que todos los bytes no utilizados deben establecerse en NUL.

La terminación de campo se especifica de manera ligeramente diferente por POSIX que por implementaciones anteriores. Los campos magic, uname y gname deben tener un NUL final. Los campos pathname, linkname y prefix deben tener un NUL final a menos que llenen todo el campo. (En particular, es posible almacenar una ruta de archivo de 256 caracteres si ocurre que tiene una / como el 156º carácter). POSIX requiere que los campos numéricos se rellenen con ceros por delante, y requiere que se terminen con caracteres de espacio o NUL.

Actualmente, la mayoría de las implementaciones de tar cumplen con el formato ustar, extendiéndolo ocasionalmente al agregar nuevos campos al área en blanco al final del registro de encabezado.

Extensiones Numéricas

Ha habido varios intentos de extender el rango de tamaños o tiempos admitidos modificando cómo se almacenan los números en el encabezado.

Una extensión obvia para aumentar el tamaño de los archivos es eliminar los caracteres de terminación de los diversos campos numéricos. Por ejemplo, el estándar solo permite que el campo de tamaño contenga 11 dígitos octales, reservando el duodécimo byte para un carácter NUL final. Permitir 12 dígitos octales permite tamaños de archivo de hasta 64 GB.

Otra extensión, utilizada por GNU tar, star y otras implementaciones más nuevas de tar, permite números binarios en los campos numéricos estándar. Esto se indica estableciendo el bit más alto del primer byte. El resto del campo se trata como un valor con complemento a dos con signo. Esto permite valores de 95 bits para los campos de longitud y tiempo, y valores de 63 bits para los números uid, gid y de dispositivo. En particular, esto proporciona una forma consistente de manejar valores de tiempo negativos. GNU tar admite esta extensión para los campos length, mtime, ctime y atime. El programa star de Joerg Schilling y la biblioteca libarchive admiten esta extensión para todos los campos numéricos. Tenga en cuenta que esta extensión está en gran medida obsoleta por el registro de atributos extendidos proporcionado por el formato de intercambio pax.

Otra extensión temprana de GNU permitía valores base-64 en lugar de octales. Esta extensión fue de corta duración y ya no es compatible con ninguna implementación.

Formato de Intercambio Pax

Hay muchos atributos que no se pueden almacenar de forma portable en un archivo ustar POSIX. IEEE Std 1003.1-2001 (“POSIX.1”) definió un “formato de intercambio pax” que utiliza dos nuevos tipos de entradas para contener metadatos en formato de texto que se aplican a las entradas siguientes. Tenga en cuenta que un archivo con formato de intercambio pax es un archivo ustar en todos los aspectos. Los nuevos datos se almacenan en entradas de archivo compatibles con ustar que usan el typeflag “x” o “g”. En particular, las implementaciones más antiguas que no admiten completamente estas extensiones extraerán los metadatos en archivos regulares, donde los metadatos pueden examinarse según sea necesario.

Una entrada en un archivo con formato de intercambio pax consta de una o dos entradas ustar estándar, cada una con su propio encabezado y datos. La primera entrada opcional almacena los atributos extendidos para la entrada siguiente. Esta primera entrada opcional tiene un typeflag "x" y un campo size que indica el tamaño total de los atributos extendidos. Los atributos extendidos en sí mismos se almacenan como una serie de líneas en formato de texto codificadas en la codificación portable UTF-8. Cada línea consta de un número decimal, un espacio, una cadena de clave, un signo igual, una cadena de valor y una nueva línea. El número decimal indica la longitud de toda la línea, incluido el campo de longitud inicial y la nueva línea final. Un ejemplo de dicho campo es:

25 ctime=1084839148.1212\n
Las claves en minúsculas son claves estándar. Los proveedores pueden agregar sus propias claves anteponiéndoles un nombre de proveedor en mayúsculas y un punto. Tenga en cuenta que, a diferencia del encabezado histórico, los valores numéricos se almacenan usando decimal, no octal. A continuación se describe un conjunto de claves comunes:
atime, ctime, mtime
Tiempos de acceso al archivo, cambio de inodo y modificación. Estos campos pueden ser negativos o incluir un punto decimal y un valor fraccional.
hdrcharset
El conjunto de caracteres utilizado por los valores de extensión pax. Por defecto, todos los valores textuales en los atributos extendidos pax se asumen en UTF-8, incluidos los nombres de ruta, nombres de usuario y nombres de grupo. En algunos casos, no es posible traducir las convenciones locales a UTF-8. Si esta clave está presente y el valor es la cadena ASCII de seis caracteres "BINARY", entonces se asume que todos los valores textuales están en una codificación multibyte dependiente de la plataforma. Tenga en cuenta que solo hay dos valores válidos para esta clave: "BINARY" o "ISO-IR 10646 2000 UTF-8". El estándar no permite otros valores, y este último valor generalmente no debe usarse ya que es el valor predeterminado cuando esta clave no se especifica. En particular, esta bandera no debe usarse como un mecanismo general para permitir que los nombres de archivo se almacenen en codificaciones arbitrarias.
uname, uid, gname, gid
Nombre de usuario, nombre de grupo y valores numéricos UID y GID. El nombre de usuario y el nombre de grupo almacenados aquí están codificados en UTF8 y, por lo tanto, pueden incluir caracteres no ASCII. Los campos UID y GID pueden ser de longitud arbitraria.
linkpath
La ruta completa del archivo enlazado. Tenga en cuenta que está codificado en UTF8 y, por lo tanto, puede incluir caracteres no ASCII.
path
El nombre completo de la entrada. Tenga en cuenta que está codificado en UTF8 y, por lo tanto, puede incluir caracteres no ASCII.
realtime.*, security.*
Estas claves están reservadas y pueden usarse para estandarización futura.
size
El tamaño del archivo. Tenga en cuenta que no hay límite de longitud en este campo, lo que permite que los archivos conformes almacenen archivos mucho más grandes que el límite histórico de 8 GB.
SCHILY.*
Atributos específicos del proveedor utilizados por la implementación star de Joerg Schilling.
SCHILY.acl.access, SCHILY.acl.default, SCHILY.acl.ace
Almacena las ACL de acceso, predeterminadas y NFSv4 como cadenas de texto en un formato que es una extensión del formato especificado por POSIX.1e borrador 17. En particular, cada especificación de acceso de usuario o grupo puede incluir un campo adicional separado por dos puntos con el UID o GID numérico. Esto permite restaurar las ACL en sistemas que pueden no tener información completa de usuario o grupo disponible (como cuando los servicios NIS/YP o LDAP no están temporalmente disponibles).
SCHILY.devminor, SCHILY.devmajor
Los números menor y mayor completos para los nodos de dispositivo.
SCHILY.fflags
Las banderas del archivo.
SCHILY.realsize
El tamaño completo del archivo en disco. XXX explicar? XXX
SCHILY.dev, SCHILY.ino, SCHILY.nlinks
El número de dispositivo, número de inodo y recuento de enlaces para la entrada. En particular, tenga en cuenta que un archivo con formato de intercambio pax que utiliza las extensiones SCHILY.* de Joerg Schilling puede almacenar todos los datos de struct stat.
LIBARCHIVE.*
Atributos específicos del proveedor utilizados por la biblioteca libarchive y los programas que la utilizan.
LIBARCHIVE.creationtime
La hora en que se creó el archivo. (Esto no debe confundirse con el atributo POSIX "ctime", que se refiere a la hora en que se modificaron por última vez los metadatos del archivo).
LIBARCHIVE.xattr.namespace.key
Libarchive almacena atributos extendidos al estilo POSIX.1e utilizando claves de este formato.

Formato de intercambio PAX

El formato de intercambio PAX (paxctl(1) y pax(1)) es una extensión del formato ustar que aborda varias de las deficiencias del formato ustar. Permite que las entradas de cabecera sean de longitud arbitraria y admite el almacenamiento de atributos que no están definidos en el formato ustar.

El formato PAX se basa en un sistema de cabeceras de longitud variable. Los archivos de cinta se componen de una secuencia de registros de cabecera de longitud fija (a menudo 512 bytes) seguidos de registros de datos. El registro de cabecera de longitud fija contiene la información estándar de la cabecera ustar, pero con algunas variaciones. Los campos que no se utilizan en el formato ustar estándar se utilizan para otros fines. Para las entradas de datos, el campo size en la cabecera estándar indica el tamaño de los datos que siguen. Cualquier información adicional se almacena en registros de cabecera adicionales que preceden a la cabecera estándar.

x
Este es el formato de entrada de cabecera extendida más común. La entrada de cabecera x precede a una entrada de datos regular. La entrada de datos consiste en una secuencia de pares de clave/valor. La clave es un nombre de atributo, y el valor es el valor de ese atributo. Los pares clave/valor están separados por un carácter de nueva línea. El valor de esta clave es el atributo extendido codificado en base 64. XXX Detallar el formato base-64 aquí XXX
VENDOR.*
XXX documentar otras extensiones específicas del proveedor XXX

Cualquier valor almacenado en un atributo extendido anula los valores correspondientes en la cabecera de tar normal. Tenga en cuenta que los lectores compatibles deben ignorar los campos normales cuando se anulan. Esto es importante, ya que se sabe que los archiveros existentes almacenan valores no conformes en los campos de cabecera estándar en esta situación. No hay límites de longitud para ninguno de estos campos. En particular, los campos numéricos pueden ser arbitrariamente grandes. Todos los campos de texto están codificados en UTF8. Los escritores compatibles solo deben almacenar caracteres ASCII portátiles de 7 bits en la cabecera ustar estándar y utilizar atributos extendidos siempre que un valor de texto contenga caracteres que no sean ASCII.

Además de la entrada x descrita anteriormente, el formato de intercambio PAX también admite una entrada g. La entrada g es idéntica en formato, pero especifica atributos que sirven como valores predeterminados para todas las entradas de archivo subsiguientes. La entrada g no se usa ampliamente.

Además de las nuevas entradas x y g, el formato de intercambio PAX tiene algunas otras variaciones menores con respecto al formato ustar anterior. La más problemática es que se permite que los enlaces duros tengan datos que los sigan. Esto permite a los lectores restaurar cualquier enlace duro a un archivo sin tener que rebobinar el archivo para encontrar una entrada anterior. Sin embargo, crea complicaciones para los lectores robustos, ya que ya no está claro si deben ignorar el campo de tamaño para las entradas de enlaces duros.

Archivos GNU Tar

El programa GNU tar comenzó con un formato pre-POSIX similar al descrito anteriormente y lo ha ampliado utilizando varios mecanismos diferentes: Añadió nuevos campos al espacio vacío de la cabecera (algunos de los cuales fueron utilizados más tarde por POSIX para fines conflictivos); permitió que la cabecera se continuara en varios registros; y definió nuevas entradas que modifican las entradas siguientes (similar en principio a la entrada x descrita anteriormente, pero cada entrada especial de GNU es de un solo propósito, a diferencia de la entrada de propósito general x). Como resultado, los archivos GNU tar no son compatibles con POSIX, aunque los lectores compatibles con POSIX más flexibles pueden extraer la mayoría de los archivos GNU tar con éxito.

struct header_gnu_tar {
	char name[100];
	char mode[8];
	char uid[8];
	char gid[8];
	char size[12];
	char mtime[12];
	char checksum[8];
	char typeflag[1];
	char linkname[100];
	char magic[6];
	char version[2];
	char uname[32];
	char gname[32];
	char devmajor[8];
	char devminor[8];
	char atime[12];
	char ctime[12];
	char offset[12];
	char longnames[4];
	char unused[1];
	struct {
		char offset[12];
		char numbytes[12];
	} sparse[4];
	char isextended[1];
	char realsize[12];
	char pad[17];
};
typeflag
GNU tar utiliza los siguientes tipos de entrada especiales, además de los definidos por POSIX:
7
GNU tar trata los registros de tipo "7" de forma idéntica a los registros de tipo "0", excepto en un oscuro RTOS donde se utilizan para indicar la preasignación de un archivo contiguo en disco.
D
Esto indica una entrada de directorio. A diferencia del tipoflag "5" estándar de POSIX, la cabecera va seguida de registros de datos que enumeran los nombres de los archivos de este directorio. Cada nombre va precedido de una "Y" ASCII si el archivo se almacena en este archivo o de una "N" si el archivo no se almacena en este archivo. Cada nombre se termina con un nulo, y un nulo adicional marca el final de la lista de nombres. El propósito de esta entrada es soportar copias de seguridad incrementales; un programa que restaura desde dicho archivo puede desear eliminar archivos en disco que no existían en el directorio cuando se creó el archivo.

Tenga en cuenta que el tipoflag "D" viola específicamente POSIX, que requiere que los typeflags no reconocidos se restauren como archivos normales. En este caso, restaurar la entrada "D" como un archivo podría interferir con la posterior creación del directorio del mismo nombre.

K
Los datos de esta entrada son un enlace largo para la siguiente entrada regular.
L
Los datos de esta entrada son una ruta larga para la siguiente entrada regular.
M
Esta es una continuación del último archivo del volumen anterior. Los archivos multivolumen de GNU garantizan que cada volumen comience con una cabecera de entrada válida. Para asegurar esto, un archivo puede dividirse, con parte almacenada al final de un volumen y parte almacenada al principio del siguiente volumen. El tipoflag "M" indica que esta entrada continúa un archivo existente. Dichas entradas solo pueden ocurrir como la primera o segunda entrada en un archivo (la última solo si la primera entrada es una etiqueta de volumen). El campo size especifica el tamaño de esta entrada. El campo offset en los bytes 369-380 especifica el desplazamiento donde comienza este fragmento de archivo. El campo realsize especifica el tamaño total del archivo (que debe ser igual a size más offset). Al extraer, GNU tar verifica que el nombre del archivo de cabecera sea el esperado, que el desplazamiento de la cabecera esté en la secuencia correcta y que la suma de offset y size sea igual a realsize.
N
Los registros de tipo "N" ya no son generados por GNU tar. Contenían una lista de archivos que debían renombrarse o enlazarse simbólicamente después de la extracción; esto se usó originalmente para admitir nombres largos. El contenido de este registro es una descripción de texto de las operaciones a realizar, en el formato "Rename %s to %s\n" o "Symlink %s to %s\n"; en cualquier caso, ambos nombres de archivo están escapados utilizando la sintaxis C de K&R. Debido a preocupaciones de seguridad, los registros "N" ahora generalmente se ignoran al leer archivos.
S
Este es un archivo regular "sparse" (disperso). Los archivos dispersos se almacenan como una serie de fragmentos. La cabecera contiene una lista de pares de desplazamiento/longitud de fragmentos. Si se requieren más de cuatro entradas de este tipo, la cabecera se extiende según sea necesario con registros de extensión de cabecera "extra" (un formato anterior que ya no se utiliza) o extensiones "sparse".
V
El campo name debe interpretarse como el nombre de una cabecera de cinta/volumen. Esta entrada generalmente debe ignorarse en la extracción.
magic
El campo magic contiene los cinco caracteres "ustar" seguidos de un espacio. Tenga en cuenta que los archivos ustar POSIX tienen un carácter nulo al final.
version
El campo version contiene un carácter de espacio seguido de un nulo. Tenga en cuenta que los archivos ustar POSIX utilizan dos copias del dígito ASCII "0".
atime, ctime
El tiempo en que se accedió por última vez al archivo y el tiempo del último cambio de información del archivo, almacenados en octal como con mtime.
longnames
Este campo aparentemente ya no se utiliza.
Sparse offset / numbytes
Cada estructura de este tipo especifica un único fragmento de un archivo disperso. Los dos campos almacenan valores como números octales. Los fragmentos se rellenan cada uno hasta un múltiplo de 512 bytes en el archivo. En la extracción, la lista de fragmentos se recopila de la cabecera (incluidas las cabeceras de extensión), y luego los datos se leen y se escriben en el archivo en los desplazamientos apropiados.
isextended
Si este campo está configurado en un valor distinto de cero, la cabecera irá seguida de registros adicionales de "cabecera dispersa". Cada registro de este tipo contiene información sobre hasta 21 bloques dispersos adicionales, como se muestra aquí: 
struct gnu_sparse_header {
	struct {
		char offset[12];
		char numbytes[12];
	} sparse[21];
	char    isextended[1];
	char    padding[7];
};
realsize
Una representación binaria del tamaño completo del archivo, con un rango mucho mayor que el tamaño de archivo POSIX. En particular, con archivos de tipo M, la entrada actual es solo una parte del archivo. En ese caso, el campo de tamaño POSIX indicará el tamaño de esta entrada; el campo realsize indicará el tamaño total del archivo.

Archivos GNU tar pax

GNU tar 1.14 (XXX verificar esto XXX) y versiones posteriores escribirán archivos en formato de intercambio pax cuando especifique la opción --posix. Este formato sigue de cerca el formato de intercambio pax, utilizando algunas etiquetas SCHILY e introduciendo nuevas palabras clave para almacenar información de archivos dispersos. Ha habido tres iteraciones del soporte de archivos dispersos, denominadas "0.0", "0.1" y "1.0".

GNU.sparse.numblocks, GNU.sparse.offset, GNU.sparse.numbytes, GNU.sparse.size
El formato "0.0" utilizó un atributo inicial GNU.sparse.numblocks para indicar el número de bloques en el archivo, un par de GNU.sparse.offset y GNU.sparse.numbytes para indicar el desplazamiento y el tamaño de cada bloque, y un único GNU.sparse.size para indicar el tamaño completo del archivo. Esto no es lo mismo que el tamaño en la cabecera tar, ya que este último valor no incluye el tamaño de los agujeros. Este formato requería que se mantuviera el orden de los atributos y dependía de que los lectores aceptaran apariciones múltiples de los mismos nombres de atributos, lo cual no está permitido oficialmente por los estándares.
