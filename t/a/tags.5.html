Propuesta para un formato de archivo tags extendido de Vi

Versión: 0.06 BORRADOR
Fecha: 8 Feb 1998
Autor: Bram Moolenaar <Bram at vim.org> y Darren Hiebert <dhiebert at users.sourceforge.net>

Introducción

El formato del archivo "tags", tal como lo usan Vi y muchos de sus descendientes, tiene capacidades limitadas.

Se desea esta funcionalidad adicional:

1.
Tags estáticos o locales. El alcance de estos tags es el archivo donde se definen. El mismo tag puede aparecer en varios archivos, sin ser realmente un duplicado.
2.
Tags duplicados. Permitir que el mismo tag ocurra más de una vez. Pueden estar ubicados en un archivo diferente y/o tener un comando diferente.
3.
Soporte para C++. Un tag no solo se especifica por su nombre, sino también por el contexto (el nombre de la clase).
4.
Extensión futura. Cuando se desee aún más funcionalidad adicional, debe ser posible añadirla más tarde, sin romper programas que no la soporten.

De la propuesta al estándar

Para convertir esta propuesta en un estándar para los archivos tags, necesita ser soportada por la mayoría de las personas que trabajan en versiones de Vi, ctags, etc. Actualmente este estándar es soportado por:

Compatibilidad hacia atrás

Un archivo tags generado con el nuevo formato debería seguir siendo utilizable por Vi. Esto hace posible distribuir archivos tags que sean utilizables por todas las versiones y descendientes de Vi.

Esto restringe el formato a lo que Vi puede manejar. El formato es:

1.
El archivo tags es una lista de líneas, cada línea en el formato:
{nombre_tag}<Tab>{archivo_tag}<Tab>{direccion_tag}
{nombre_tag}
Cualquier identificador, que no contenga espacios en blanco.

EXCEPCIÓN: Universal Ctags viola este punto de la propuesta; el nombre_tag puede contener espacios. Sin embargo, los tabuladores no están permitidos.

<Tab>
Exactamente un carácter TAB (aunque muchas versiones de Vi pueden manejar cualquier cantidad de espacios en blanco).
{archivo_tag}
El nombre del archivo donde {nombre_tag} está definido, relativo al directorio actual (¿o ubicación del archivo tags?).
{direccion_tag}
Cualquier comando Ex. Cuando se ejecuta, se comporta como si 'magic' no estuviera activado.
2.
El archivo tags está ordenado por {nombre_tag}. Esto permite una búsqueda binaria en el archivo.
3.
Se permiten tags duplicados, pero cuál se usa realmente es impredecible (debido a la búsqueda binaria).

La mejor manera de añadir texto adicional a la línea para la nueva funcionalidad, sin romperla para Vi, es poner un comentario en la {direccion_tag}. Esto da la libertad de usar cualquier texto, y debería funcionar en cualquier implementación tradicional de Vi.

Por ejemplo, cuando el archivo tags antiguo contiene:

main    main.c  /^main(argc, argv)$/
DEBUG   defines.c       89

Las nuevas líneas pueden ser:

main    main.c  /^main(argc, argv)$/;"cualquier texto adicional
DEBUG   defines.c       89;"cualquier texto adicional

Nótese que el ';' es requerido para poner el cursor en la línea correcta, y luego el '"' es reconocido como el inicio de un comentario.

Para las versiones de Vi compatibles con Posix, esto NO funcionará, ya que solo se reconoce un número de línea o un comando de búsqueda. Espero que Posix pueda ser ajustado. Nvi sufre de esto.

Seguridad

Vi permite el uso de cualquier comando Ex en un archivo tags. Esto tiene el potencial de una fuga de seguridad tipo caballo de Troya.

La propuesta es permitir solo comandos Ex que posicionen el cursor en un solo archivo. Otros comandos, como editar otro archivo, salir del editor, cambiar un archivo o escribir un archivo, no están permitidos. Por lo tanto, es lógico llamar al comando tagaddress.

Específicamente, estos dos comandos Ex están permitidos:

•
Un número de línea decimal:
89
•
Un comando de búsqueda. Es un patrón de expresión regular, como lo usa Vi, encerrado entre // o ?? :
/^int c;$/
?main()?

Hay dos combinaciones posibles:

•
Concatenación de lo anterior, con ';' en medio. El significado es que se usa el primer número de línea o comando de búsqueda, el cursor se posiciona en esa línea, y luego se usa el segundo comando de búsqueda (un número de línea no sería útil). Esto se puede hacer varias veces. Esto es útil cuando la información en una sola línea no es única, y la búsqueda necesita comenzar en una línea especificada.
/struct xyz {/;/int count;/
389;/struct foo/;/char *s;/
•
Se puede añadir un comentario final, comenzando con ';"' (dos caracteres: punto y coma y comillas dobles). Esto se usa a continuación.
89;" foo bar

Esto podría extenderse en el futuro. Lo que actualmente falta es una forma de posicionar el cursor en una columna determinada.

Objetivos

Ahora hay que definir el uso del texto del comentario. Lo siguiente es el objetivo:

1.
Mantener el texto corto, porque:
  • La longitud de línea que Vi puede manejar está limitada a 512 caracteres.
  • Los archivos tags pueden contener miles de tags. He visto archivos tags de varios Mbytes.
  • Más texto hace que la búsqueda sea más lenta.
2.
Mantener el texto legible, porque:
  • A menudo es necesario comprobar la salida de un nuevo programa ctags.
  • Ser capaz de editar el archivo manualmente.
  • Facilitar la escritura de un programa para producir o

EXCEPTIONS IN UNIVERSAL CTags

The following text is describing the exceptions in Universal Ctags. The reader should be aware that the file format described above is the one used by Exuberant Ctags, which is also used by Universal Ctags. However, Universal Ctags implements the following extensions.

•
The tagname field may contain whitespace characters. However, it may not contain the TAB character.
•
The tagfile field may contain whitespace characters. However, it may not contain the TAB character.
•
For tagname and tagfile, the following escape sequences are supported:
  • \a BEL (0x07).
  • \b BS (0x08).
  • \f FF (0x0c).
  • \n NL (0x0a).
  • \r CR (0x0d).
  • \t TAB (0x09).
  • \v VT (0x0b).
  • \\ A single backslash.
  • \x followed by two hexadecimal digits, representing the character with that value. For example, \x09 is a TAB.
•
The following escape sequences are supported in the tagaddress field:
  • \a BEL (0x07).
  • \b BS (0x08).
  • \f FF (0x0c).
  • \n NL (0x0a).
  • \r CR (0x0d).
  • \t TAB (0x09).
  • \v VT (0x0b).
  • \\ A single backslash.
  • \x followed by two hexadecimal digits, representing the character with that value. For example, \x09 is a TAB.
•
The following escape sequences are supported in the tagfield values:
  • \a BEL (0x07).
  • \b BS (0x08).
  • \f FF (0x0c).
  • \n NL (0x0a).
  • \r CR (0x0d).
  • \t TAB (0x09).
  • \v VT (0x0b).
  • \\ A single backslash.
  • \x followed by two hexadecimal digits, representing the character with that value. For example, \x09 is a TAB.
•
The tagname field may begin with a space or a literal ! character. In this case, the space or ! is represented as \x20 or \x21, respectively. This is done to distinguish pseudo-tags from regular tags when the tag file is sorted.
•
When the tagfile field contains whitespace characters, and the tag file is generated on a non-Windows system, the backslash character \ is converted to a forward slash /. On Windows systems, the backslash is left unchanged.

FORMAT

A tags file contains a list of tags, where each tag is on a line. The format of each line is:

{tagname}<Tab>{tagfile}<Tab>{tagaddress}

where:

{tagname}
The name of the tag. This is an identifier, and should not contain whitespace characters, except for the exceptions noted above for Universal Ctags.
<Tab>
Exactly one TAB character (ASCII 0x09). This is used to separate the fields.
{tagfile}
The name of the file in which the tag is defined. This is a pathname, and may be relative or absolute. The exceptions noted above for Universal Ctags apply.
{tagaddress}
An Ex command that will find the tag within the {tagfile}. This is typically a search pattern (e.g., /pattern/) or a line number.

Optionally, a line may contain additional information in the form of tag fields:

{tagname}<Tab>{tagfile}<Tab>{tagaddress}[;"<Tab>{tagfield}..]
;"
This sequence marks the end of the {tagaddress} and the beginning of the tag fields. The double quote character makes the rest of the line a comment to the vi editor.
{tagfield}
A tag field consists of a name, followed by a colon, followed by a value. For example: kind:function.

The following tag fields are recognized:

FIELD-NAME DESCRIPTION
arity The number of arguments for a function tag.
class The name of the class for which this tag is a member or method.
enum The name of the enumeration in which this tag is an enumerator.
file Indicates that the tag is static (local) to the specified file. If the value is empty, the tag file itself is used.
function The name of the function in which this tag is defined. This is useful for local variables and functions. If functions are nested (e.g., in Pascal), the function names are concatenated, separated by '/', forming a path.
kind The kind of tag. The value depends on the language. For C and C++, the following kinds are recommended:
c
class name
d
define (from #define XXX)
e
enumerator
f
function or method name
F
file name
g
enumeration name
m
member (of structure or class data)
p
function prototype
s
structure name
t
typedef
u
union name
v
variable
If this field is omitted, the kind of tag is undefined.
struct The name of the struct in which this tag is a member.
union The name of the union in which this tag is a member.

These fields are mostly intended for C and C++. When tag programs are written for other languages, this list should be extended to include language-specific field names. This will help users be independent of the tag program used.

If the "kind:" field is omitted, the tag kind is considered undefined. The "kind" tag field itself may be omitted if the tag is a function. In this case, the tag kind is assumed to be 'f'.

Value conversions:

  • A literal TAB character in a value is represented as \t.
  • A literal carriage return (CR) is represented as \r.
  • A literal newline (NL) is represented as \n.
  • A literal backslash character is represented as \\.
  • Other characters in the range 0x01 to 0x1F, and 0x7F, are converted to \x followed by two hexadecimal digits.

Note that on MS-DOS systems, backslashes are used as path separators. Therefore, file names containing backslashes must have them doubled. For example, c:\vim\file.c would be represented as c:\\vim\\file.c.

Universal Ctags adds support for the following escape sequences in tag field values:

  • \a BEL (0x07).
  • \b BS (0x08).
  • \v VT (0x0b).
  • \f FF (0x0c).

If a tag field appears twice in a tag line, only the last one is used.

Examples:

asdf    sub.cc  /^asdf()$/;"    new_field:some\svalue   file:
foo_t   sub.h   /^typedef foo_t$/;"     kind:t
func3   sub.p   /^func3()$/;"   function:/func1/func2   file:
getflag sub.c   /^getflag(arg)$/;"      kind:f  file:
inc     sub.cc  /^inc()$/;"     file: class:PipeBuf

The name of the "kind:" field can be omitted. This is to reduce the size of the tags file by about 15%. A program reading the tags file can recognize the "kind:" field by the missing ':'. Examples:

foo_t   sub.h   /^typedef foo_t$/;"     t
getflag sub.c   /^getflag(arg)$/;"      f       file:

The format of the tags file.

Name

tags — the format of the tags file

DESCRIPTION

This section describes the format of a tags file that is used by many programming tools to locate identifiers in source code.

A tags file is a text file that contains lines of text. Each line represents a tag, which is an identifier (like a function name, a variable name, a class name, etc.) that has been found in a source code file. The format of a line is:

{tagname} <Tab> {tagfile} <Tab> {tagaddress}

{tagname} is the name of the identifier.

{tagfile} is the name of the source code file in which the identifier was found.

{tagaddress} specifies the location of the identifier within the source code file. There are two forms:

/{pattern}/
/{line-number}/

Where {pattern} is a regular expression that matches the identifier, and {line-number} is the number of the line in the file where the identifier is found. The tag address forms are equivalent if the regular expression matches only one line. Some tools may support only one of the forms.

Note that characters like newline, carriage return, form feed, and tab are represented by the escape sequences \n, \r, \f, and \t, respectively. Other characters that have special meaning in regular expressions, or characters that cannot be represented in the current locale, are represented by an octal escape sequence of the form \ddd.

This description is a variant of the original Vi tags file format. It is compatible with the format described in the Exuberant Ctags manual. See "Proposal for extended Vi tags file format" below for the full specification.

Special lines starting with the sequence "!_TAG_" are used to store additional information about the tag file itself, such as its format version, whether it is sorted, and information about the program that generated it. These lines are ignored by basic tag parsers but are useful for more advanced tools. Examples include:

Tag lines providing information about the content of the tag file:

!_TAG_FILE_FORMAT   {version-number}        /optional comment/
!_TAG_FILE_SORTED   {0|1}                   /0=unsorted, 1=sorted/

The {version-number} used in the tag file format line reserves the value of "1" for tag files complying with the original UNIX vi/ctags format, and reserves the value "2" for tag files complying with this proposal. This value may be used to determine if the extended features described in this proposal are present.

Tag lines providing information about the program used to generate the tag file, and provided solely for documentation purposes:

!_TAG_PROGRAM_AUTHOR        {author-name}   /{email-address}/
!_TAG_PROGRAM_NAME  {program-name}  /optional comment/
!_TAG_PROGRAM_URL   {URL}   /optional comment/
!_TAG_PROGRAM_VERSION       {version-id}    /optional comment/

Lines starting with "!_TAG_" are known as pseudo-tags. They are semantically different from regular tags but use the same format. The escape sequences and illegal character handling described in the "Proposal" section also apply to pseudo-tags.

Proposal for extended Vi tags file format

This section describes an extension to the original Vi tags file format, designed to provide more flexibility and information. It is intended to be compatible with existing tools while enabling new features.

Key features of the extended format include:

1.
{tagname} may contain spaces and several escape sequences. This is necessary for parsing documents like Tex and reStructuredText, or for liberal languages such as JavaScript. Specific rules for conversion and escape sequences are defined to ensure proper handling.
2.
{tagfile} may contain spaces and several escape sequences, provided that backslashes (\) are not used as filename separators. On UNIX-like systems, forward slashes (/) are used. On MS Windows, Universal Ctags converts backslashes to forward slashes by default. Pseudo-tags are used to indicate whether this condition is satisfied.
3.
The "name" part of {tagfield} in a tag generated by Universal Ctags may contain numeric characters, but the first character must be alphabetic.

Additionally, pseudo-tags are introduced to convey meta-information:

!_TAG_FILE_FORMAT {version-number}
Specifies the version of the tag file format. Version 1 is for the original UNIX vi/ctags format, and version 2 is for this extended proposal. This allows tools to detect support for extended features.
!_TAG_FILE_SORTED {0|1}
Indicates whether the tag file is sorted (1) or unsorted (0). This can help optimize searching.
!_TAG_PROGRAM_AUTHOR {author-name} /{email-address}/
Provides the name and email address of the program's author.
!_TAG_PROGRAM_NAME {program-name} /optional comment/
Specifies the name of the program used to generate the tags file.
!_TAG_PROGRAM_URL {URL} /optional comment/
Provides a URL for the program that generated the tags file.
!_TAG_PROGRAM_VERSION {version-id} /optional comment/
Indicates the version of the program used to generate the tags file.

Pseudo-tags use the same format as regular tags: {tagname}<Tab>{tagfile}<Tab>{tagaddress}. Escape sequences and illegal character handling also apply.

The use of "!_TAG_" prefix for pseudo-tags is recommended to ensure they are sorted near the beginning of the tag file. Tools should be capable of skipping over unknown pseudo-tags.

Exceptions in Universal Ctags

Universal Ctags implements this proposal with certain exceptions to maintain compatibility and handle specific cases.

Exceptions

1.
{tagname} in Universal Ctags generated files may include spaces and various escape sequences, particularly for formats like Tex, reStructuredText, and languages like JavaScript. Refer to the "Proposal" section for details on conversion and escape sequence handling.
2.
{tagfile} may contain spaces and escape sequences if backslashes (\) are not used as filename separators. Universal Ctags handles this by converting backslashes to forward slashes on MS Windows and using pseudo-tags to indicate the filename separator convention.
3.
The "name" part of {tagfield} in Universal Ctags output may contain numeric characters, but must begin with an alphabetic character.

Compatible output and weakness

The default output format of Universal Ctags (using the --output-format=u-ctags option) includes these exceptions. An alternative format, --output-format=e-ctags, mimics the Exuberant Ctags output without extensions. However, the e-ctags format may discard tag entries whose names contain spaces or tab characters. The TAG_OUTPUT_MODE pseudo-tag indicates which format is being used.
