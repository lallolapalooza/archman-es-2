NAME

thread - Extension for script access to Tcl threading

SYNOPSIS

package require Thread ?2.8?

DESCRIPTION

The thread extension creates threads that contain Tcl interpreters, and it lets you send scripts to those threads for evaluation. Additionally, it provides script-level access to basic thread synchronization primitives, like mutexes and condition variables.

COMMANDS

This section describes commands for creating and destroying threads and sending scripts to threads for evaluation.

thread::create ?-joinable? ?-preserved? ?script?
This command creates a thread that contains a Tcl interpreter. The Tcl interpreter either evaluates the optional script, if specified, or it waits in the event loop for scripts that arrive via the thread::send command. Both of them would take place simultaneously with the return of command thread::create to the caller thread. Neither the caller is waiting for the finishing of optional script, nor the result, if any, of the script is returned to the caller. The result of thread::create is the ID of the thread. This is the opaque handle which identifies the newly created thread for all other package commands. The handle of the thread goes out of scope automatically when thread is marked for exit (see the thread::release command below).

If the optional script argument contains the thread::wait command the thread will enter into the event loop. If such command is not found in the script the thread will run the script to the end and exit. In that case, the handle may be safely ignored since it refers to a thread which does not exists any more at the time when the command returns.

Using flag -joinable it is possible to create a joinable thread, i.e. one upon whose exit can be waited upon by using thread::join command. Note that failure to join a thread created with -joinable flag results in resource and memory leaks.

Threads created by the thread::create cannot be destroyed forcefully. Consequently, there is no corresponding thread destroy command. A thread may only be released using the thread::release and if its internal reference count drops to zero, the thread is marked for exit. This kicks the thread out of the event loop servicing and the thread continues to execute commands passed in the script argument, following the thread::wait command. If this was the last command in the script, as usually the case, the thread will exit.

It is possible to create a situation in which it may be impossible to terminate the thread, for example by putting some endless loop after the thread::wait or entering the event loop again by doing an vwait-type of command. In such cases, the thread may never exit. This is considered to be a bad practice and should be avoided if possible. This is best illustrated by the example below:

    # You should never do ...
    set tid [thread::create {
        package require Http
        thread::wait
        vwait forever ; # <-- this!
    }]
The thread created in the above example will never be able to exit. After it has been released with the last matching thread::release call, the thread will jump out of the thread::wait and continue to execute commands following. It will enter vwait command and wait endlessly for events. There is no way one can terminate such thread, so you wouldn't want to do this!

Each newly created has its internal reference counter set to 0 (zero), i.e. it is unreserved. This counter gets incremented by a call to thread::preserve and decremented by a call to thread::release command. These two commands implement simple but effective thread reservation system and offer predictable and controllable thread termination capabilities. It is however possible to create initially preserved threads by using flag -preserved of the thread::create command. Threads created with this flag have the initial value of the reference counter of 1 (one), and are thus initially marked reserved.

thread::preserve ?id?
This command increments the thread reference counter. Each call to this command increments the reference counter by one (1). Command returns the value of the reference counter after the increment. If called with the optional thread id, the command preserves the given thread. Otherwise the current thread is preserved.

With reference counting, one can implement controlled access to a shared Tcl thread. By incrementing the reference counter, the caller signalizes that he/she wishes to use the thread for a longer period of time. By decrementing the counter, caller signalizes that he/she has finished using the thread.

thread::release ?-wait? ?id?
This command decrements the thread reference counter. Each call to this command decrements the reference counter by one (1). If called with the optional thread id, the command releases the given thread. Otherwise, the current thread is released. Command returns the value of the reference counter after the decrement. When the reference counter reaches zero (0), the target thread is marked for termination. You should not reference the thread after the thread::release command returns zero or negative integer. The handle of the thread goes out of scope and should not be used any more. Any following reference to the same thread handle will result in Tcl error.

Optional flag -wait instructs the caller thread to wait for the target thread to exit, if the effect of the command would result in termination of the target thread, i.e. if the return result would be zero (0). Without the flag, the caller thread does not wait for the target thread to exit. Care must be taken when using the -wait, since this may block the caller thread indefinitely. This option has been implemented for some special uses of the extension and is deprecated for regular use. Regular users should create joinable threads by using the -joinable option of the thread::create command and the thread::join to wait for thread to exit.

thread::id
Returns the id of the current thread.
thread::errorproc ?procname?
Specifies a Tcl procedure to be called in the current thread when an error occurs in any other thread that has been instructed to send scripts to the current thread. If procname is specified, it is registered as the error handler procedure. If procname is omitted, the command returns the currently registered error handler procedure name. If no error handler procedure has been specified, it returns an empty string.

The error handler procedure will be called with two arguments: the thread id of the thread that sent the script and the error message. The procedure is called asynchronously, meaning that it is executed when the main loop of the thread comes to servicing the event queue.

thread::cancel ?-unwind? id ?result?
This command cancels a running script in the thread specified by id. If the optional flag -unwind is given, the script execution is terminated by unwinding the call stack. If the script is not running or does not exist, the command returns an empty string. Otherwise, it returns the result of the cancelled script. The result argument can be used to specify the return value of the cancelled script. If not specified, the default return value is an empty string.

Unwinding the call stack is a dangerous operation and should be used with caution. It may lead to resource leaks or other unexpected behavior if not used properly.

thread::unwind
This command forces the current thread to unwind its call stack and exit. It should be used with extreme caution as it may lead to resource leaks or other unexpected behavior. It is generally recommended to use thread::exit instead.
thread::exit ?status?
This command causes the current thread to exit. If the optional status argument is provided, it is returned as the exit status of the thread. Otherwise, the exit status is an empty string. The thread must not be joinable. If it is, an error is raised.
thread::names
Returns a list of the IDs of all currently existing threads.
thread::exists id
Returns 1 if a thread with the given id exists, and 0 otherwise.
thread::send ?-async? ?-head? id script ?varname?
This command sends the script to be evaluated in the thread specified by id. The script is evaluated asynchronously by default. If the -async flag is not specified, the command waits for the script to complete and returns its result. The -head flag causes the script to be placed at the front of the message queue for the target thread, ensuring it is processed before any previously sent scripts.

If varname is specified, the result of the script evaluation will be stored in the global variable named varname in the calling thread. If varname is not specified, the result is returned directly by the thread::send command.

The command returns an empty string if the target thread does not exist or if the -async flag is used.

thread::broadcast script
This command sends the script to be evaluated in all other existing threads (except the current one). The script is evaluated asynchronously in each target thread. This command returns an empty string.
thread::wait
This command makes the current thread enter the event loop and wait for incoming events (e.g., scripts sent via thread::send). This command blocks until the thread is terminated or receives a command that breaks out of the event loop. It is typically used in conjunction with thread::create to keep a thread alive and responsive.
thread::eval ?-lock mutex? arg ?arg ...?
This command evaluates the Tcl script formed by concatenating the arguments arg. It is similar to the Tcl eval command, but it can optionally acquire a mutex before evaluating the script. If the -lock option is specified, the command first acquires the lock on the given mutex, evaluates the script, and then releases the lock. This is useful for protecting shared resources from concurrent access by multiple threads.
thread::join id
This command waits for the thread specified by id to terminate. The thread must have been created with the -joinable flag. If the thread has already terminated, the command returns immediately. The return value of the terminated thread is returned by this command. If the thread was not created as joinable, an error is raised.
thread::configure id ?option? ?value? ?...?
This command allows configuring various aspects of a thread. Currently, it only supports setting or getting the error handler procedure for a thread using the -errorproc option. For example, `thread::configure $tid -errorproc myErrorHandler` sets `myErrorHandler` as the error handler for thread `$tid`. `thread::configure $tid -errorproc` retrieves the current error handler.
thread::transfer id channel
Transfers ownership of the channel channel to the thread specified by id. The target thread must be running and waiting in the event loop (e.g., after calling thread::wait). After the transfer, the channel can only be accessed from the target thread. Returns the channel name. An error is raised if the target thread does not exist or is not ready to accept the channel.
thread::detach channel
Removes the channel channel from the event loop of the current thread. The channel is no longer accessible from this thread. This is typically used before transferring a channel to another thread or when a channel is no longer needed.
thread::attach channel
Attaches the channel channel to the event loop of the current thread. This allows the current thread to process events related to the channel. This is the default behavior for channels created within a thread.

Synchronization Primitives

The following commands provide access to synchronization primitives for inter-thread communication.

thread::mutex
Creates, destroys, locks, and unlocks mutexes.
thread::mutex create ?-recursive?
Creates a new mutex and returns its handle. The optional -recursive flag allows the same thread to lock the mutex multiple times.
thread::mutex destroy mutex
Destroys the specified mutex. The mutex must not be locked.
thread::mutex lock mutex
Acquires a lock on the specified mutex. If the mutex is already locked by another thread, this command blocks until the mutex is available.
thread::mutex unlock mutex
Releases the lock on the specified mutex. If the mutex is not locked by the current thread, an error is raised.
thread::rwmutex
Creates, destroys, locks, and unlocks read-write mutexes. Read-write mutexes allow multiple threads to acquire a read lock simultaneously, but only one thread can acquire a write lock, which excludes all other read and write locks.
thread::rwmutex create
Creates a new read-write mutex and returns its handle.
thread::rwmutex destroy mutex
Destroys the specified read-write mutex. The mutex must not be locked.
thread::rwmutex rlock mutex
Acquires a read lock on the specified read-write mutex. Blocks if a write lock is held by another thread.
thread::rwmutex wlock mutex
Acquires a write lock on the specified read-write mutex. Blocks if any read or write lock is held by another thread.
thread::rwmutex unlock mutex
Releases the lock (read or write) on the specified read-write mutex.
thread::cond
Creates, destroys, notifies, and waits on condition variables. Condition variables are used to signal events between threads, typically in conjunction with mutexes.
thread::cond create
Creates a new condition variable and returns its handle.
thread::cond destroy cond
Destroys the specified condition variable.
thread::cond notify cond
Wakes up one thread that is waiting on the specified condition variable.
thread::cond wait cond mutex ?ms?
Waits on the specified condition variable. The associated mutex is unlocked while waiting and re-locked before returning. The optional ms argument specifies a timeout in milliseconds. If the timeout expires, the command returns 0; otherwise, it returns 1.

EXAMPLE

The following example demonstrates basic usage of the thread extension:

    # Create a new thread that waits for commands
    set tid [thread::create {
        thread::wait
    }]

    # Send a script to the new thread for evaluation
    thread::send $tid {
        puts "Hello from thread $tid!"
        set result [expr {2 + 2}]
    } result_var

    # Wait for the result to be available in the main thread
    vwait result_var

    # Print the result
    puts "The result from thread $tid is: $result_var"

    # Clean up the thread
    thread::release $tid

thread::id
Este comando devuelve el ID del hilo actual.
thread::errorproc ?nombreproc?
Este comando establece un manejador para los errores que ocurren en scripts enviados asincrónicamente, usando la bandera -async del comando thread::send, a otros hilos. Si no se especifica ningún manejador, se devuelve el manejador actual. Una cadena vacía restablece el manejador a su valor predeterminado (no especificado). Un error no capturado en un hilo provoca que se envíe un mensaje de error al canal de error estándar. Este esquema de informe predeterminado se puede cambiar registrando un procedimiento que se llama para informar el error. El nombreproc se llama en el intérprete que invocó el comando thread::errorproc. El nombreproc se llama de esta manera:
    mi_procedimiento_error id_hilo informacion_error
thread::cancel ?-unwind? id ?resultado?
Este comando requiere la versión 8.6 o superior de Tcl.

Cancela el script que se está evaluando en el hilo dado por el parámetro id. Sin el modificador -unwind, la pila de evaluación del intérprete se desenrolla hasta que se encuentra un comando catch envolvente o no quedan más invocaciones del intérprete en la pila de llamadas. Con el modificador -unwind, la pila de evaluación del intérprete se desenrolla sin tener en cuenta ningún comando catch intermedio hasta que no quedan más invocaciones del intérprete en la pila de llamadas. Si resultado está presente, se utilizará como mensaje de error; de lo contrario, se utilizará un mensaje de error predeterminado.

thread::unwind
El uso de este comando está obsoleto en favor de un sistema de reserva de hilos más avanzado implementado con los comandos thread::preserve y thread::release. El soporte para el comando thread::unwind desaparecerá en alguna futura versión principal de la extensión.

Este comando detiene un comando thread::wait anterior. La ejecución del script pasado a un hilo recién creado continuará desde el comando thread::wait. Si thread::wait fue el último comando en el script, el hilo saldrá. El comando devuelve un resultado vacío pero puede desencadenar un error de Tcl con el mensaje "el hilo de destino murió" en algunas situaciones.

thread::exit ?estado?
El uso de este comando está obsoleto en favor de un sistema de reserva de hilos más avanzado implementado con los comandos thread::preserve y thread::release. El soporte para el comando thread::exit desaparecerá en alguna futura versión principal de la extensión.

Este comando fuerza a un hilo atascado en el comando thread::wait a salir incondicionalmente. El estado de salida del hilo por defecto es 666 y se puede especificar usando el argumento opcional estado. Se garantiza que la ejecución del comando thread::exit dejará la memoria del programa en un estado inconsistente, producirá fugas de memoria y afectará de otra manera a otros subsistemas de la aplicación Tcl de forma impredecible. El comando devuelve un resultado vacío pero puede desencadenar un error de Tcl con el mensaje "el hilo de destino murió" en algunas situaciones.

thread::names
Este comando devuelve una lista de IDs de hilos. Estos son solo para hilos que se han creado a través del comando thread::create. Si su aplicación crea otros hilos a nivel C, no son informados por este comando.
thread::exists id
Devuelve verdadero (1) si el hilo dado por el parámetro id existe, falso (0) en caso contrario. Esto se aplica solo a los hilos que se han creado a través del comando thread::create.
thread::send ?-async? ?-head? id script ?nombrevar?
Este comando pasa un script a otro hilo y, opcionalmente, espera el resultado. Si se especifica la bandera -async, el comando no espera el resultado y devuelve una cadena vacía. El hilo de destino debe ingresar a su bucle de eventos para recibir scripts enviados a través de este comando. Esto se hace por defecto para los hilos creados sin un script de inicio. Los hilos pueden ingresar al bucle de eventos explícitamente llamando a thread::wait o a cualquier otro comando Tcl/Tk relevante, como update, vwait, etc.

El nombrevar opcional especifica el nombre de la variable donde almacenar el resultado del script. Sin la bandera -async, el comando devuelve el código de evaluación, de forma similar al comando estándar Tcl catch. Si, sin embargo, se especifica la bandera -async, el comando devuelve inmediatamente y el llamador puede posteriormente hacer vwait sobre ?nombrevar? para obtener el resultado del script pasado.

    set t1 [thread::create]
    set t2 [thread::create]
    thread::send -async $t1 "set a 1" resultado
    thread::send -async $t2 "set b 2" resultado
    for {set i 0} {$i < 2} {incr i} {
        vwait resultado
    }
En el ejemplo anterior, se enviaron trabajos a dos hilos y ambos fueron instruidos para señalar la misma variable "resultado" en el hilo llamador. El llamador ingresó al bucle de eventos dos veces para obtener ambos resultados. Tenga en cuenta, sin embargo, que el orden de los resultados recibidos puede variar, dependiendo de la carga actual del sistema, el tipo de trabajo realizado, etc.

Muchos hilos pueden enviar simultáneamente scripts al hilo de destino para su ejecución. Todos ellos se ingresan en la cola de eventos del hilo de destino y se ejecutan de forma FIFO, mezclados con otros eventos opcionales pendientes en la cola de eventos del hilo de destino. Usando el modificador opcional ?-head?, los scripts publicados en la cola de eventos del hilo pueden colocarse en la cabeza, en lugar de en la cola, siendo ejecutados así de forma LIFO.

thread::broadcast script
Este comando pasa un script a todos los hilos creados por el paquete para su ejecución. No espera respuesta de ninguno de los hilos.
thread::wait
Esto ingresa al bucle de eventos para que un hilo pueda recibir mensajes del comando thread::send. Este comando solo debe usarse dentro del script pasado a thread::create. Debe ser el último comando en el script. Si no es así, el hilo que sale continuará ejecutando las líneas del script después de thread::wait, lo cual generalmente no es lo que usted desea y/o espera.
    set t1 [thread::create {
        #
        # Hacer algún trabajo de inicialización aquí
        #
        thread::wait ; # Entrar al bucle de eventos
    }]
thread::eval ?-lock mutex? arg ?arg ...?
Este comando concatena los argumentos pasados y evalúa el script resultante bajo protección de mutex. Si no se especifica ningún mutex usando el argumento opcional ?-lock mutex?, se utiliza el mutex estático interno.
thread::join id
Este comando espera a que el hilo con el ID id termine y luego devuelve su código de salida. Se devolverán errores para los hilos que no se puedan unir o que ya hayan sido esperados por otro hilo. Tras la unión, el manejador del hilo ha salido de ámbito y no debe usarse más.
thread::configure id ?opción? ?valor? ?...?
Este comando configura varios aspectos de bajo nivel del hilo con ID id de manera similar a como el comando estándar Tcl fconfigure configura algunas opciones de canal Tcl. Las opciones actualmente admitidas son: -eventmark y -unwindonerror.

Cuando se proporciona -eventmark con un valor mayor que 0 (cero), ese valor es el número máximo de scripts publicados asincrónicamente que pueden estar pendientes para el hilo. thread::send -async se bloquea hasta que el número de scripts pendientes en el bucle de eventos cae por debajo del valor -eventmark.

Cuando se proporciona -unwindonerror con un valor de true, un resultado de error en un script hace que el hilo se desenrolle, haciéndolo no disponible para evaluar scripts adicionales.

thread::transfer id canal
Esto mueve el canal especificado del hilo e intérprete actual al intérprete principal del hilo con el ID dado id. Después de la mudanza, el intérprete actual ya no tiene acceso al canal, pero el intérprete principal del hilo de destino podrá usarlo a partir de entonces. El comando espera hasta que el otro hilo haya incorporado el canal. Debido a esto, es posible bloquear los hilos participantes al ordenar al otro, a través de un thread::send síncrono, transferir un canal a nosotros. Esto se extiende fácilmente a bucles más largos de hilos que esperan mutuamente. Otras restricciones: el canal en cuestión no debe ser compartido entre múltiples intérpretes que se ejecutan en el hilo de envío. Esto excluye automáticamente los canales especiales para entrada, salida y error estándar.

Debido a la implementación interna del núcleo de Tcl y la restricción en la transferencia de canales compartidos, se deben tomar medidas adicionales al transferir canales de socket creados al aceptar la conexión a partir de los procedimientos de devolución de llamada de los comandos socket:

    socket -server _Aceptar 2200
    proc _Aceptar {s ipaddr puerto} {
        after idle [list Aceptar $s $ipaddr $puerto]
    }
    proc Aceptar {s ipaddr puerto} {
        set tid [thread::create]
        thread::transfer $tid $s
    }
thread::detach canal
Esto desvincula el canal especificado del hilo e intérprete actual. Después de eso, el intérprete actual ya no tiene acceso al canal. El canal está en estado de espera hasta que otro hilo (o el mismo) vincule el canal nuevamente con thread::attach. Restricciones: las mismas que para la transferencia de canales compartidos con el comando thread::transfer.
thread::attach canal
Esto
s adjunta el channel previamente desvinculado en el hilo/intérprete actual. Para canales ya existentes, el comando no hace nada, es decir, no es un error adjuntar el mismo canal más de una vez. La primera operación realizará la operación, mientras que todas las operaciones subsiguientes simplemente no harán nada. El comando lanza un error si el channel no se encuentra en la lista de canales desvinculados y/o en el intérprete actual.
thread::mutex
Los mutex son los primitivos de sincronización de hilos más comunes. Se utilizan para sincronizar el acceso de dos o más hilos a uno o más recursos compartidos. Este comando proporciona acceso a nivel de script a mutex exclusivos y/o recursivos. Los mutex exclusivos solo pueden ser bloqueados una vez por un hilo, mientras que los mutex recursivos pueden ser bloqueados muchas veces por el mismo hilo. Para los mutex recursivos, el número de operaciones de bloqueo y desbloqueo debe coincidir, de lo contrario, el mutex nunca se liberará, lo que provocaría diversas situaciones de interbloqueo.

Se debe tener cuidado al usar mutex en un programa multihilo. El uso inadecuado de mutex puede provocar diversas situaciones de interbloqueo, especialmente al usar mutex exclusivos.

El comando thread::mutex admite los siguientes subcomandos y opciones:

thread::mutex create ?-recursive?
Crea el mutex y devuelve su identificador opaco. Este identificador debe usarse para cualquier referencia futura al mutex recién creado. Si no se especificó el argumento opcional ?-recursive?, el comando crea el mutex exclusivo. Con el argumento ?-recursive?, el comando crea un mutex recursivo.
thread::mutex destroy mutex
Destruye el mutex. El mutex debe estar en estado desbloqueado antes del intento de destrucción. Si el mutex está bloqueado, el comando lanzará un error de Tcl.
thread::mutex lock mutex
Bloquea el mutex. El bloqueo del mutex exclusivo puede lanzar un error de Tcl si se intenta bloquear el mismo mutex dos veces desde el mismo hilo. Si la lógica de su programa le obliga a bloquear el mismo mutex una o más veces desde el mismo hilo (esto puede ocurrir en invocaciones de procedimientos recursivos), debería considerar el uso de mutex recursivos.
thread::mutex unlock mutex
Desbloquea el mutex para que otro hilo pueda bloquearlo de nuevo. El intento de desbloquear un mutex ya desbloqueado lanzará un error de Tcl.
thread::rwmutex
Este comando crea mutex de muchos-lectores/un-escritor. Los mutex de lector/escritor le permiten serializar el acceso a un recurso compartido de manera más óptima. En situaciones donde un recurso compartido se lee principalmente y se modifica raramente, podría obtener un rendimiento adicional utilizando mutex de lector/escritor en lugar de mutex exclusivos o recursivos.

Para leer el recurso, el hilo debe obtener un bloqueo de lectura en el recurso. El bloqueo de lectura no es exclusivo, lo que significa que más de un hilo puede obtener un bloqueo de lectura del mismo recurso, sin esperar a otros lectores. Para modificar el recurso, sin embargo, un hilo debe obtener un bloqueo de escritura exclusivo. Este bloqueo bloquea efectivamente a todos los hilos de obtener el bloqueo de lectura mientras el recurso está siendo modificado por el hilo escritor. Solo después de que se libere el bloqueo de escritura, el recurso podrá bloquearse para lectura nuevamente.

El comando thread::rwmutex admite los siguientes subcomandos y opciones:

thread::rwmutex create
Crea el mutex de lector/escritor y devuelve su identificador opaco. Este identificador debe usarse para cualquier referencia futura al mutex recién creado.
thread::rwmutex destroy mutex
Destruye el mutex de lector/escritor. Si el mutex ya está bloqueado, el intento de destruirlo lanzará un error de Tcl.
thread::rwmutex rlock mutex
Bloquea el mutex para lectura. Más de un hilo puede bloquear para lectura el mismo mutex al mismo tiempo.
thread::rwmutex wlock mutex
Bloquea el mutex para escritura. Solo un hilo puede bloquear para escritura el mismo mutex al mismo tiempo. El intento de bloquear para escritura el mismo mutex dos veces desde el mismo hilo lanzará un error de Tcl.
thread::rwmutex unlock mutex
Desbloquea el mutex para que otro hilo pueda bloquearlo de nuevo. El intento de desbloquear un mutex ya desbloqueado lanzará un error de Tcl.
thread::cond
Este comando proporciona acceso a nivel de script a variables de condición. Una variable de condición crea un entorno seguro para que el programa evalúe una condición, duerma en ella cuando sea falsa y se despierte cuando pueda haberse vuelto verdadera. Una variable de condición siempre se usa en conjunción con un mutex exclusivo. Si intenta usar otro tipo de mutex en conjunción con la variable de condición, se lanzará un error de Tcl.

El comando admite los siguientes subcomandos y opciones:

thread::cond create
Crea la variable de condición y devuelve su identificador opaco. Este identificador debe usarse para cualquier referencia futura a la variable de condición recién creada.
thread::cond destroy cond
Destruye la variable de condición cond. Se debe tener extremo cuidado de que nadie esté utilizando (es decir, esperando) la variable de condición, de lo contrario, pueden ocurrir errores inesperados.
thread::cond notify cond
Despierta a todos los hilos que esperan en la variable de condición cond.
thread::cond wait cond mutex ?ms?
Este comando se utiliza para suspender la ejecución del programa hasta que la variable de condición cond haya sido señalizada o hasta que expire el temporizador opcional. El mutex exclusivo debe estar bloqueado por el hilo que llama al ingresar a este comando. Si el mutex no está bloqueado, se lanzará un error de Tcl. Mientras espera en cond, el comando libera mutex. Antes de devolver el control al hilo que llama, el comando vuelve a adquirir el mutex. El desbloqueo del mutex y la espera en la variable de condición cond se realizan de forma atómica.

La opción de comando ms, si se proporciona, debe ser un entero que especifique el intervalo de tiempo en milisegundos que el comando espera ser señalizado. De lo contrario, el comando espera la notificación de condición para siempre.

En programas multihilo, hay muchas situaciones en las que un hilo tiene que esperar a que ocurra algún evento hasta que se le permita continuar. Esto generalmente se logra probando repetidamente una condición bajo protección de mutex y esperando en la variable de condición hasta que la condición sea verdadera:

    set mutex [thread::mutex create]
    set cond  [thread::cond  create]
    thread::mutex lock $mutex
    while {<some_condition_is_true>} {
        thread::cond wait $cond $mutex
    }
    # Hacer algo de trabajo bajo protección de mutex
    thread::mutex unlock $mutex
La prueba repetida de la condición es necesaria ya que la variable de condición puede ser señalizada sin que la condición haya cambiado realmente (despertares de hilo espurios, por ejemplo).

DISCUSIÓN

El modelo de hilos fundamental en Tcl es que puede haber uno o más intérpretes de Tcl por hilo, pero cada intérprete de Tcl solo debe ser utilizado por un único hilo que lo creó. Una abstracción de "memoria compartida" es difícil de proporcionar en Tcl porque Tcl hace suposiciones sobre la propiedad de variables y datos. Por lo tanto, esta extensión admite una forma simple de subprocesos donde el hilo principal puede administrar varios hilos de fondo o "trabajadores". Por ejemplo, un servidor basado en eventos puede pasar solicitudes a hilos de trabajadores y luego esperar respuestas de los hilos de trabajadores o nuevas solicitudes de clientes. Todo pasa a través del bucle de eventos común de Tcl, por lo que la mensajería entre hilos funciona de forma natural con E/S basada en eventos, vwait en variables, etc. Para la transferencia de información a granel, es posible mover canales entre los hilos.

Para scripts multihilo avanzados, también se admite el acceso a nivel de script a dos primitivas de sincronización básicas, mutex y variables de condición.

thread(n)

NAME
thread - A thread is a path of execution within a process.

SYNOPSIS
thread

DESCRIPTION
A thread is a path of execution within a process. Threads are sometimes called lightweight processes. Threads within the same process share the same address space. This means that threads can share global variables, static variables, and heap memory. However, each thread has its own stack, registers, and thread-local storage.

Threads are created using the pthread_create() function. Threads are terminated using the pthread_exit() function or by returning from the thread's start routine. Threads can be joined using the pthread_join() function.

Threads are used to improve the performance of applications by allowing them to perform multiple tasks concurrently. For example, a web server can use threads to handle multiple client requests simultaneously. A GUI application can use threads to keep the user interface responsive while performing long-running tasks in the background.

COMMANDS
This manual page does not describe any commands.

DISCUSSION
Threads are a powerful tool for concurrent programming, but they also introduce complexity. Race conditions and deadlocks are common problems that can arise when working with threads. It is important to carefully design and implement multithreaded programs to avoid these issues.
