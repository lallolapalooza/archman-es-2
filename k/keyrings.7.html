keyrings - instalación

de gestión y retención
de claves en el núcleo

DESCRIPCIÓ

N

La instalación de gestión de claves de Linux es principalmente una forma para que varios componentes del núcleo retengan o almacenen en caché datos de seguridad, claves de autenticación, claves de cifrado y otros datos en el

núcleo.

Se proporcionan interfaces de llamadas al sistema para que los programas en espacio de usuario puedan gestionar esos objetos y también usar la instalación para sus propios fines; ver add_key(2), request_key(2) y keyctl(

2).

Se proporciona una biblioteca y algunas utilidades de espacio de usuario para permitir el acceso a la instalación. Ver keyctl(1), keyctl(3) y keyutils(7) para más

información.

Clave

s

Una clave tiene los siguientes

atributos:
Número de serie
(ID)
Este es un identificador entero único por el cual se hace referencia a una clave en las llamadas al sistema. El número de serie a veces se denomina sinónimamente como el ID de la clave. Programáticamente, los números de serie de las claves se representan utilizando el tipo key_serial_

El tipo de una clave define qué tipo de datos se pueden a

Hay varios tipos de propósito general disponible

Descripción
(nombre)
La descripción de la clave es una cadena imprimible que se utiliza como término de búsqueda para la clave (en conjunto con el tipo de clave) así como como nombre de visualización. Durante las búsquedas, la descripción puede coincidir parcialmente o coincidir
exactamente.
Carga útil
(datos)
La carga útil es el contenido real de una clave. Esto generalmente se establece cuando se crea una clave, pero es posible que el núcleo realice una llamada al espacio de usuario para finalizar la instanciación de una clave si esa clave no era conocida por el núcleo cuando se solicitó. Para más detalles, ver request_
key

La carga útil de una clave se puede leer y actu

Derechos de
acceso
Al igual que los archivos, cada clave tiene un ID de usuario propietario, un ID de grupo propietario y una etiqueta de seguridad. Cada clave también tiene un conjunto de permisos, aunque hay más que para un archivo UNIX normal, y hay una categoría adicional (poseedor) además del habitual usuario, grupo y otros (ver Posesión,
más ab

Tenga en cuenta que las claves están controladas por cuotas, ya qu

suario propietario especifica a quién se le debe debitar la cuota.
Tiempo de
expiración
A cada clave se le puede establecer un tiempo de expiración. Cuando se alcanza ese tiempo, la clave se marca como expirada y los accesos a ella fallan con el error EKEYEXPIRED. Si no se elimina, actualiza o reemplaza, entonces, después de una cantidad de tiempo establecida, una clave expirada se elimina automáticamente (se recoge la basura) junto con todos los enlaces a ella, y los intentos de acceder a la clave fallan con el error ENOKE
Y.

La carga útil para las claves de este tipo es un blob de datos arbitrarios de hasta 32,767

La descripción de una clave "logon" debe comenzar con un prefijo no vacío delimitado por dos puntos cuyo propósito es identificar el servicio al que pertenece la clave. (Tenga en cuenta que esto difiere de las claves del tipo "user", donde la inclusión de un prefij

Llavero

s

Como se mencionó anteriormente, los llaveros son un tipo especial de clave que contienen enlaces a otras claves (que pueden incluir otros llaveros). Las claves pueden ser enlazadas por múltiples llaveros. Los llaveros pueden considerarse análogos a directorios UNIX donde cada directorio contiene un conjunto de enlaces duros a

archivos.

Se pueden aplicar varias operaciones (llamadas al sistema) solo a

Una clave puede ser añadida a un llavero por llamadas al sistema que crean claves. Esto evita que la nueva clave sea eliminada inmediatamente cuando la llamada al sistema libera su última referencia a la
clave.
Enlaza
ndo
Se puede añadir un enlace a un llavero apuntando a una clave que ya es conocida, siempre que esto no cree un ciclo
autorreferencial.
Desenlaza
ndo
Se puede eliminar un enlace de un llavero. Cuando se elimina el último enlace a una clave, esa clave será programada para su eliminación por el recolector de
basura.
Limpian
do
Se pueden eliminar todos los enlaces de un
llavero.
Buscan
do
Un llavero puede considerarse la raíz de un árbol o subárbol en el que los ll
averos forman las ramas y los no llaveros las hojas. Este árbol puede ser bu
scado para encontrar una clave que coincida con un tipo y descripción particulares.

Ver keyctl_clear(3), keyctl_link(3), keyctl_search(3), y keyctl_unlink(3) par

Anclaje de

claves

Para evitar que una clave sea recolectada por el recolector de basura, debe ser anclada para mantener su recuento de referencias elevado cuando no está en uso activo por el

kernel.

Los llaveros se utilizan para anclar otras claves: cada enlace es una referencia a una clave. Ten en cuenta que los llaveros en sí mismos son solo claves y también están sujetos al mismo requisito de anclaje para evitar que sean recolectados por el recolector de

basura.

El kernel pone a disposición una serie de llaveros ancla. Ten en cuenta que algunos de estos llaveros solo se crearán cuando se acceda a ellos por primera

vez.
Llaveros de
proceso
Las credenciales del proceso en sí mismas hacen referencia a llaveros con semá
nticas específicas. Estos llaveros están fijados mientras exista el conj
unto de credenciales, lo que generalmente es mientras exista el proceso.
Hay tres llaveros con diferentes reglas de herencia/compartición: el session-keyring(7) (heredado y compartido por todos los procesos hijos), el process-keyring(7) (compartido por todos los hilos en un proceso) y el thread-keyring(7) (específico de un hilo en particular)
.
Como alternativa a usar los IDs reales de los llaveros, en llamadas a add_key(2), keyctl(2), y request_key(2), los valores especiales de llavero KEY_SPEC_SESSION_KEYRING, KEY_SPEC_PROCESS_KEYRING, y KEY_SPEC_THREAD_KEYRING pueden usarse para referirse
a las instancias propias de
l llamador de estos llaveros.
Llaveros de
usuario
Cada UID conocido por el kernel tiene un registro que contiene dos llaveros: el user-keyring(7) y el user-session-keyring(7). Estos existen
mientras exista el regi

Como alternativa a usar los IDs reales de los llaveros, en llamadas a add_key(2), keyctl(2), y request_key(2), los valores especiales de llavero KEY_SPEC_USER_KEYRING y KEY_SPEC_USER_SESSION_KEYRING pueden usarse para referirse a las instancias propias del llamador de estos
llaveros.
Un enlace al llavero de usuario se coloca en un nuevo llavero de sesión por pam_keyinit(8) cuando se inicia un
a nueva sesión de
inicio de sesión.
Llaveros
persistentes
Existe un persistent-keyring(7) disponible para cada UID conocido por el sistema. Puede persistir más allá de la vida del registro UID mencionado anteriormente, pero tiene un tiempo de expiración establecido de modo que se limpia automáticamente después de un tiempo determinado. El llavero persistente permite, por ejemplo, que los scripts de cron(8) usen credenciales que quedan en el
llavero persistente después d

Ten en cuenta que el tiempo de expiración de

Hay llaveros especiales propiedad del kernel que pueden anclar claves para propósitos especiales. Un ejemplo de esto es el llavero del sistema utilizado para mantener clave

Posesió

n

El concepto de posesión es importante para entender el modelo de seguridad de los llaveros. Si un hilo posee una clave se determina por las siguientes

reglas:
(1
)
Cualquier clave o llavero que no otorgue permiso de búsqueda al llamador se ignora en todas las siguientes
reglas.
(2
)
Un hilo posee su session-keyring(7), process-keyring(7), y thread-keyring(7) directamente porque esos llaveros son referenciados por sus
credenciales.
(3
)
Si un llavero es poseído, entonces cualquier clave a la que enlace también es
poseída.
(4
)
Si cualquier clave a la que un llavero enlace es en sí misma un llavero, entonces la regla (3) se aplica
recursivamente.
(5
)
Si un proceso es llamado desde el kernel para instanciar una clave (ver request_key(2)), entonces también posee los llaveros del solic
itante como en la regla (1
) como si fuera el solicitante.

Ten en cuenta que la posesión no es una propiedad fundamental de una clave, sino que debe calcularse cada vez que se necesita la

clave.

La posesión está diseñada para permitir que los programas con ID de usuario establecido (setuid) ejecutados desde, digamos, un shell de un usuario accedan a las claves del usuario. Otorgar permisos al poseedor de la clave mientras se le niegan al propietario de la clave y al grupo permite la prevención de acceso a claves en función de la coincidencia de UID y

GID.

Cuando crea el llavero de sesión, pam_keyinit(8) agrega un enlace al user-keyring(7), haciendo que el llavero de usuario

y todo lo que contien
e sea poseído por defecto.

Búsqueda de

claves

Una de las características clave de la instalación de gestión de claves de Linux es la capacidad de encontrar una clave que un proceso está reteniendo. El system call request_key(2) es el punto principal de acceso para las aplicaciones de espacio de usuario para encontrar una clave. (Internamente, el kernel tiene algo similar disponible para que lo usen los componentes internos que hacen uso de claves.

)

El algoritmo de búsqueda funciona de la siguiente

manera:
(1
)
Los llaveros del proceso se buscan en el siguiente orden: el thread-keyring(7) si existe, el process-keyring(7) si existe, y luego ya sea el session-keyring(7) si existe o el user-session-keyring(7) si ese
existe.
(2
)
Si el llamador era un proceso que fue invocado por el mecanismo de upcall de request_key(2), entonces los llaveros del llamador original de request_key(2) también serán
buscados.
(3
)
La búsqueda de un árbol de llaveros se realiza en orden de amplitud (breadth-first): primero se busca una coincidencia en cada llavero, luego se buscan los llaveros a los que ese llavero hace
referencia.
(4
)
Si se encuentra una llave coincidente que es válida, la búsqueda termina y se devuelve esa
llave.
(5
)
Si se encuentra una llave coincidente que tiene un estado de error adjunto, se anota ese estado de error y la búsqueda
continúa.
(6
)
Si no se encuentra ninguna llave coincidente válida, se devuelve el primer estado de error anotado; de lo contrario, se devuelve un error
ENOK
EY.

También es posible buscar en un llavero específico, en cuyo caso solo se aplican los pasos (3) a (6)

.

Consulte request_key(2) y keyctl_search(3) pa

ra más in
formación.

Creación de llaves bajo

demanda

Si no se puede encontrar una llave, request_key(2) creará una nueva llave si se le proporciona un argumento callout_info, y luego realizará una llamada (upcall) al espacio de usuario para instanciar la llave. Esto permite crear llaves según sea

necesario.

Normalmente, esto implicará que el núcleo cree un nuevo proceso que ejecute el programa request-key(8), el cual a su vez ejecutará el manejador (handler) apropiado basándose en su

configuración.

Al manejador se le pasa una llave de autorización especial que le permite a él y solo a él instanciar la nueva llave. Esto también se utiliza para permitir que las búsquedas realizadas por el programa manejador busquen también en los llaveros del

solicitante.

Consulte request_key(2), keyctl_assume_authority(3), keyctl_instantiate(3), keyctl_negate(3), keyctl_reject(3), request-key(8) y request-key.conf(5)

para más in
formación.

Usuario

s

La instalación de gestión de llaves de Linux tiene una serie de usuarios y usos, pero no se limita a los que ya

existen.

Los usuarios en el núcleo de esta instalación

incluyen:
Sistemas de archivos de red -
DNS
El núcleo utiliza el mecanismo de llamada (upcall) proporcionado por las llaves para llamar al espacio de usuario para realizar búsquedas DNS y luego almacenar en caché los
resultados.
AF_RXRPC y kAFS -
Autenticación
El protocolo de red AF_RXRPC y el sistema de archivos AFS en el núcleo utilizan llaves para almacenar el ticket necesario para realizar tráfico asegurado o cifrado. Luego, estos son buscados por las operaciones de red en AF_RXRPC y por las operaciones de sistema de archivos en
kAFS.
NFS - Mapeo de ID de
usuario
El sistema de archivos NFS utiliza llaves para almacenar mapeos de IDs de usuario externos a IDs de usuario
locales.
CIFS -
Contraseña
El sistema de archivos CIFS utiliza llaves para almacenar contraseñas para acceder a recursos compartidos
remotos.
Verificación de
módulos
El proceso de compilación del núcleo puede configur
arse para firmar criptográficamente los módulos. Esa
firma se verifica luego cuando se carga un módulo.

Los usuarios en el espacio de usuario de esta instalación

incluyen:
Almacenamiento de llaves
Kerberos
La instalación MIT Kerberos 5 (libkrb5) puede utilizar llaves para almacenar tokens de autenticación que pueden configurarse para limpiarse automáticamente un tiempo establecido después de que el usuario los use por última vez, pero hasta entonces permite que permanezcan después de que el usuario haya cerrado sesión para que los scripts d

NAME


keyrings — controlizzazione delle chiavi del kernel






DESCRIPTION


Il sottosistema di controllo delle chiavi del kernel Linux fornisce
    un modo per archiviare oggetti di dati sensibili (come chiavi crittografiche,
    password e certificati) in modo sicuro nel kernel e di accedervi tramite un
    insieme di interfacce di sistema.


Il sottosistema delle chiavi ha quattro tipi principali di oggetti:


    
  
  • key: L'oggetto fondamentale che contiene un payload
      di dati e alcune metadati.
    • 
  
  • keyring: Un contenitore speciale che può contenere
      altri oggetti key o keyring.
      I keyring sono organizzati in una gerarchia.
    • 
  
  • key type: Un'astrazione che definisce come viene
      creato, serializzato e deserializzato un particolare tipo di chiave.
    • 
  
  • key operation: Un'operazione che può essere
      eseguita su un oggetto chiave, ad esempio la crittografia o la
      decrittografia.
    • 



Ogni processo utente ha un insieme di keyring associati:


    
  
  • session keyring: Associato alla sessione utente.
      Viene creato all'accesso e distrutto al disconnessione.
    • 
  
  • process keyring: Associato a un processo. Può
      essere creato su richiesta.
    • 
  
  • thread keyring: Associato a un thread. Può essere
      creato su richiesta.
    • 
  
  • user keyring: Associato a un ID utente. Viene
      creato la prima volta che un processo con quell'ID utente richiede un
      keyring utente.
    • 
  
  • persistent keyring: Un keyring speciale che può
      sopravvivere ai riavvii del sistema.
    • 



I keyring sono organizzati in una gerarchia. Quando viene richiesta
    una chiave, il kernel cerca prima nel keyring del thread, poi nel keyring
    del processo, poi nel keyring della sessione e infine nel keyring dell'utente.
    Se la chiave non viene trovata, il kernel può invocare un programma
    di "richiesta chiave" per creare o recuperare la chiave.


I file in /proc/sys/kernel/keys/ consentono
    di controllare il comportamento del sottosistema delle chiavi:


106/20000
1000:    11 11/11 10/200 271/20000




  
uid

  
L'ID utente.

  
usage

  
Questo è un conteggio di utilizzo interno al kernel per la struttura del
      kernel utilizzata per registrare gli utenti chiave.

  
nkeys/nikeys

  
Il numero totale di chiavi possedute dall'utente e il numero di tali chiavi
      che sono state instantiate.

  
qnkeys/maxkeys

  
Il numero di chiavi possedute dall'utente e il numero massimo di chiavi che
      l'utente può possedere.

  
qnbytes/maxbytes

  
Il numero di byte consumati nei payload delle chiavi possedute da questo
      utente e il limite superiore sul numero di byte nei payload delle chiavi per
      quell'utente.





  
/proc/sys/kernel/keys/gc_delay (dal Linux 2.6.32)

  
Il valore in questo file specifica l'intervallo, in secondi, dopo il quale
      le chiavi revocate e scadute verranno sottoposte a garbage collection. Lo
      scopo di avere tale intervallo è di avere una finestra temporale in cui lo
      spazio utente possa vedere un errore (rispettivamente EKEYREVOKED e
      EKEYEXPIRED) che indica cosa è successo alla chiave.





  

  
Il valore predefinito in questo file è 300 (cioè, 5 minuti).





  
/proc/sys/kernel/keys/persistent_keyring_expiry (dal Linux
    3.13)

  
Questo file definisce un intervallo, in secondi, a cui il timer di scadenza
      del keyring persistente viene resettato ogni volta che il keyring viene
      acceduto (tramite keyctl_get_persistent(3)
      o l'operazione keyctl(2) KEYCTL_GET_PERSISTENT).





  

  
Il valore predefinito in questo file è 259200 (cioè, 3 giorni).




I seguenti file (che sono scrivibili da processi privilegiati)
    vengono utilizzati per applicare quote sul numero di chiavi e sul numero di
    byte di dati che possono essere memorizzati nei payload delle chiavi:



  
/proc/sys/kernel/keys/maxbytes (dal Linux 2.6.26)

  
Questo è il numero massimo di byte di dati che un utente non root può
      detenere nei payload delle chiavi possedute dall'utente.





  

  
Il valore predefinito in questo file è 20.000.





  
/proc/sys/kernel/keys/maxkeys (dal Linux 2.6.26)

  
Questo è il numero massimo di chiavi che un utente non root può possedere.





  

  
Il valore predefinito in questo file è 200.





  
/proc/sys/kernel/keys/root_maxbytes (dal Linux 2.6.26)

  
Questo è il numero massimo di byte di dati che l'utente root (UID 0 nello
      spazio dei nomi dell'utente root) può detenere nei payload delle chiavi
      possedute da root.





  

  
Il valore predefinito in questo file è 25.000.000 (20.000 prima di Linux
      3.17).





  
/proc/sys/kernel/keys/root_maxkeys (dal Linux 2.6.26)

  
Questo è il numero massimo di chiavi che l'utente root (UID 0 nello spazio
      dei nomi dell'utente root) può possedere.





  

  
Il valore predefinito in questo file è 1.000.000 (200 prima di Linux
      3.17).




Per quanto riguarda i keyring, si noti che ogni collegamento in
    un keyring consuma 4 byte del payload del keyring.
