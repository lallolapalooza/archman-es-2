ksu(1)

Paquete: krb5

Licencias: custom

KSU(1) MIT Kerberos KSU(1)

NOMBRE

ksu - superusuario Kerberizado

SINOPSIS

ksu [ usuario_destino ] [ -n nombre_principal_destino ] [ -c nombre_caché_origen ] [ -k ] [ -r tiempo ] [ -p | -P] [ -f | -F] [ -l duración ] [ -z | Z ] [ -q ] [ -e comando [ argumentos ... ] ] [ -a [ argumentos ... ] ]

REQUISITOS

Debe tener Kerberos versión 5 instalado para compilar ksu. Debe tener un servidor Kerberos versión 5 en ejecución para usar ksu.

DESCRIPCIÓN

ksu es una versión Kerberizada del programa su que tiene dos misiones: una es cambiar de forma segura el ID de usuario real y efectivo al del usuario destino, y la otra es crear un nuevo contexto de seguridad.

NOTA:

Para mayor claridad, todas las referencias y atributos del usuario que invoca el programa comenzarán con "origen" (por ejemplo, "usuario de origen", "caché de origen", etc.).

Igualmente, todas las referencias y atributos de la cuenta destino comenzarán con "destino".

AUTENTICACIÓN

Para cumplir la primera misión, ksu opera en dos fases: autenticación y autorización. La resolución del nombre de principal destino es el primer paso en la autenticación. El usuario puede especificar su nombre de principal con la opción -n (por ejemplo, -n jqpublic@USC.EDU) o se asignará un nombre de principal predeterminado utilizando una heurística descrita en la sección OPCIONES (ver opción -n). El nombre de usuario destino debe ser el primer argumento de ksu; si no se especifica, root es el predeterminado. Si se especifica ., el usuario destino será el usuario de origen (por ejemplo, ksu .). Si el usuario de origen es root o el usuario destino es el usuario de origen, no se realiza ninguna autenticación ni autorización. De lo contrario, ksu busca un ticket Kerberos apropiado en la caché de origen.

El ticket puede ser para el servidor final o un ticket de concesión de ticket (TGT) para el reino del principal destino. Si el ticket para el servidor final ya está en la caché, se descifra y verifica. Si no está en la caché pero el TGT sí, el TGT se utiliza para obtener el ticket para el servidor final. Luego se verifica el ticket del servidor final. Si ninguno de los tickets está en la caché, pero ksu está compilado con la definición GET_TGT_VIA_PASSWD, se le pedirá al usuario una contraseña Kerberos que luego se usará para obtener un TGT. Si el usuario ha iniciado sesión de forma remota y no tiene un canal seguro, la contraseña puede quedar expuesta. Si ninguno de los tickets está en la caché y GET_TGT_VIA_PASSWD no está definido, la autenticación falla.

AUTORIZACIÓN

Esta sección describe la autorización del usuario de origen cuando ksu se invoca sin la opción -e. Para una descripción de la opción -e, consulte la sección OPCIONES.

Tras una autenticación exitosa, ksu verifica si el principal destino está autorizado para acceder a la cuenta destino. En el directorio de inicio del usuario destino, ksu intenta acceder a dos archivos de autorización: .k5login(5) y .k5users. En el archivo .k5login, cada línea contiene el nombre de un principal que está autorizado para acceder a la cuenta.

Por ejemplo:

jqpublic@USC.EDU
jqpublic/secure@USC.EDU
jqpublic/admin@USC.EDU

El formato de .k5users es el mismo, excepto que el nombre del principal puede ir seguido de una lista de comandos que el principal está autorizado a ejecutar (ver la opción -e en la sección OPCIONES para más detalles).

Por lo tanto, si el nombre del principal destino se encuentra en el archivo .k5login, el usuario de origen está autorizado para acceder a la cuenta destino. De lo contrario, ksu busca en el archivo .k5users. Si se encuentra el nombre del principal destino sin comandos finales o seguido solo por *, entonces el usuario de origen está autorizado. Si existen .k5login o .k5users, pero no existe una entrada apropiada para el principal destino, se deniega el acceso. Si no existen ninguno de los archivos, se concederá al principal acceso a la cuenta según las reglas de mapeo aname->lname. De lo contrario, la autorización falla.

EJECUCIÓN DEL SHELL DESTINO

Tras una autenticación y autorización exitosas, ksu procede de manera similar a su. El entorno no se modifica con la excepción de las variables USER, HOME y SHELL. Si el usuario destino no es root, USER se establece al nombre de usuario destino. De lo contrario, USER permanece sin cambios. Tanto HOME como SHELL se establecen a los valores predeterminados del inicio de sesión destino. Además, la variable de entorno KRB5CCNAME se establece al nombre de la caché destino. El ID de usuario real y efectivo se cambia al del usuario destino. Luego se invoca el shell del usuario destino (el nombre del shell se especifica en el archivo de contraseñas). Al finalizar el shell, ksu elimina la caché destino (a menos que ksu se invoque con la opción -k). Esto se implementa primero haciendo un fork y luego un exec, en lugar de solo un exec, como hace su.

CREACIÓN DE UN NUEVO CONTEXTO DE SEGURIDAD

ksu se puede utilizar para crear un nuevo contexto de seguridad para el programa destino (ya sea el shell destino o un comando especificado a través de la opción -e). El programa destino hereda un conjunto de credenciales del usuario de origen. Por defecto, este conjunto incluye todas las credenciales de la caché de origen más cualquier credencial adicional obtenida durante la autenticación. El usuario de origen puede limitar las credenciales de este conjunto utilizando la opción -z o -Z. -z restringe la copia de tickets de la caché de origen a la caché destino solo a los tickets donde el cliente == el nombre del principal destino. La opción -Z proporciona al usuario destino una nueva caché destino (sin credenciales en la caché). Tenga en cuenta que por razones de seguridad, cuando el usuario de origen es root y el usuario destino no es root, la opción -z es el modo de operación predeterminado.

Si bien no se realiza ninguna autenticación si el usuario de origen es root o es el mismo que el usuario destino, aún se pueden obtener tickets adicionales para la caché destino. Si se especifica -n y no se pueden copiar credenciales a la caché destino, se le pide al usuario de origen una contraseña Kerberos (a menos que se especifique -Z o GET_TGT_VIA_PASSWD esté indefinido). Si tiene éxito, se obtiene un TGT del servidor Kerberos y se almacena en la caché destino. De lo contrario, si no se proporciona contraseña (el usuario presiona Enter), ksu continúa en modo de operación normal (la caché destino no contendrá el TGT deseado). Si se escribe la contraseña incorrecta, ksu falla.

NOTA:

Durante la autenticación, solo los tickets que se pudieron obtener sin proporcionar una contraseña se almacenan en caché en la caché de origen.

OPCIONES

-n nombre_principal_destino
Especifica un nombre de principal Kerberos destino. Se utiliza en las fases de autenticación y autorización de ksu.

Si ksu se invoca sin -n, se asigna un nombre de principal predeterminado a través de la siguiente heurística:

•
Caso 1: el usuario de origen no es root.

Si el usuario destino es el usuario de origen, el nombre de principal predeterminado se establece al principal predeterminado de la caché de origen. Si la caché no existe, el nombre de principal predeterminado se establece a usuario_destino@reino_local. Si los usuarios de origen y destino son diferentes y ni ~usuario_destino/.k5users ni ~usuario_destino/.k5login existen, el nombre de principal predeterminado es nombre_de_usuario_destino@reino_local. De lo contrario, comenzando por el primer principal listado a continuación, ksu verifica si el principal está autorizado para acceder a la cuenta destino y si hay un ticket legítimo para ese principal en la caché de origen. Si ambas condiciones se cumplen, ese principal se convierte en el principal destino predeterminado, de lo contrario, se pasa al siguiente principal.

a.
principal predeterminado de la caché de origen
b.
usuario_destino@reino_local

>
c.
usuario_origen@dominio_local

Si a-c falla, intente con cualquier principal para el cual exista un ticket en la caché de origen y que esté autorizado para acceder a la cuenta de destino. Si eso falla, seleccione el primer principal autorizado para acceder a la cuenta de destino de la lista anterior. Si ninguno está autorizado y ksu está configurado con PRINC_LOOK_AHEAD activado, seleccione el principal predeterminado de la siguiente manera:

Para cada candidato en la lista anterior, seleccione un principal autorizado que tenga el mismo nombre de dominio y cuya primera parte del nombre de principal sea igual al prefijo del candidato. Por ejemplo, si el candidato a) es jqpublic@ISI.EDU y jqpublic/secure@ISI.EDU está autorizado para acceder a la cuenta de destino, entonces el principal predeterminado se establece en jqpublic/secure@ISI.EDU.

•
Caso 2: el usuario de origen es root.

Si el usuario de destino no es root, el nombre del principal predeterminado es usuario_destino@dominio_local. De lo contrario, si la caché de origen existe, el nombre del principal predeterminado se establece en el principal predeterminado de la caché de origen. Si la caché de origen no existe, el nombre del principal predeterminado se establece en root\@dominio_local.

-c nombre_caché_origen

Especifique el nombre de la caché de origen (por ejemplo, -c FILE:/tmp/mi_cache). Si no se utiliza la opción -c, el nombre se obtiene de la variable de entorno KRB5CCNAME. Si KRB5CCNAME no está definida, el nombre de la caché de origen se establece en krb5cc_<uid_origen>. El nombre de la caché de destino se establece automáticamente en krb5cc_<uid_destino>.(gen_sym()), donde gen_sym genera un número nuevo tal que la caché resultante no exista previamente. Por ejemplo: 
krb5cc_1984.2
-k
No elimine la caché de destino al finalizar el shell de destino o un comando (comando -e). Sin -k, ksu elimina la caché de destino.
-z
Restrinja la copia de tickets de la caché de origen a la caché de destino solo a los tickets donde el cliente == el nombre del principal de destino. Utilice la opción -n si desea tickets para algo más que el principal predeterminado. Tenga en cuenta que la opción -z es mutuamente excluyente con la opción -Z.
-Z
No copie ningún ticket de la caché de origen a la caché de destino. Simplemente cree una nueva caché de destino, donde el nombre del principal predeterminado de la caché se inicialice al nombre del principal de destino. Tenga en cuenta que la opción -Z es mutuamente excluyente con la opción -z.
-q
Suprima la impresión de mensajes de estado.

Opciones de ticket de concesión de tickets:

-l vida_util -r tiempo -p -P -f -F
Las opciones de ticket de concesión de tickets solo se aplican al caso en que no haya tickets apropiados en la caché para autenticar al usuario de origen. En este caso, si ksu está configurado para solicitar a los usuarios una contraseña de Kerberos (se define GET_TGT_VIA_PASSWD), se utilizarán las opciones de ticket de concesión de tickets especificadas al obtener un ticket de concesión de tickets del servidor Kerberos.
-l vida_util
(cadena de duración.) Especifica la vida útil que se solicitará para el ticket; si esta opción no se especifica, se utilizará la vida útil predeterminada del ticket (12 horas).
-r tiempo
(cadena de duración.) Especifica que se debe solicitar la opción renovable para el ticket y especifica la vida útil total deseada del ticket.
-p
especifica que se debe solicitar la opción proxiable para el ticket.
-P
especifica que la opción proxiable no se solicitará para el ticket, incluso si la configuración predeterminada es solicitar tickets proxiables.
-f
la opción especifica que se debe solicitar la opción reenviable para el ticket.
-F
la opción especifica que la opción reenviable no se solicitará para el ticket, incluso si la configuración predeterminada es solicitar tickets reenviables.
-e comando [argumentos ...]
ksu procede exactamente de la misma manera que si se hubiera invocado sin la opción -e, excepto que en lugar de ejecutar el shell de destino, ksu ejecuta el comando especificado. Ejemplo de uso:
ksu bob -e ls -lag

El algoritmo de autorización para -e es el siguiente:

Si el usuario de origen es root o el usuario de origen == usuario de destino, no se realiza ninguna autorización y se ejecuta el comando. Si el ID de usuario de origen != 0 y el archivo ~usuario_destino/.k5users no existe, la autorización falla. De lo contrario, el archivo ~usuario_destino/.k5users debe tener una entrada apropiada para que el principal de destino sea autorizado.

El formato del archivo .k5users:

Una entrada de principal por línea que puede ir seguida de una lista de comandos que el principal está autorizado a ejecutar. Un nombre de principal seguido de un * significa que el usuario está autorizado a ejecutar cualquier comando. Por lo tanto, en el siguiente ejemplo:

jqpublic@USC.EDU ls mail /local/kerberos/klist
jqpublic/secure@USC.EDU *
jqpublic/admin@USC.EDU

jqpublic@USC.EDU solo está autorizado a ejecutar los comandos ls, mail y klist. jqpublic/secure@USC.EDU está autorizado a ejecutar cualquier comando. jqpublic/admin@USC.EDU no está autorizado a ejecutar ningún comando. Tenga en cuenta que jqpublic/admin@USC.EDU está autorizado a ejecutar el shell de destino (ksu normal, sin la opción -e), pero jqpublic@USC.EDU no lo está.

Los comandos listados después del nombre del principal deben ser nombres de ruta completos o solo el nombre del programa. En el segundo caso, CMD_PATH, que especifica la ubicación de los programas autorizados, debe definirse en el momento de la compilación de ksu. ¿Qué comando se ejecuta?

Si el usuario de origen es root o el usuario de destino es el usuario de origen o el usuario está autorizado a ejecutar cualquier comando (entrada *), entonces el comando puede ser una ruta completa o relativa que conduzca al programa de destino. De lo contrario, el usuario debe especificar una ruta completa o solo el nombre del programa.

-a argumentos
Especifique los argumentos que se pasarán al shell de destino. Tenga en cuenta que todas las banderas y parámetros que sigan a -a se pasarán al shell, por lo tanto, todas las opciones destinadas a ksu deben preceder a -a.

La opción -a se puede utilizar para simular la opción -e si se utiliza de la siguiente manera:

-a -c [comando [argumentos]].

-c es interpretado por el c-shell para ejecutar el comando.

INSTRUCCIONES DE INSTALACIÓN

ksu se puede compilar con los siguientes cuatro indicadores:

GET_TGT_VIA_PASSWD
En caso de que no se encuentren tickets apropiados en la caché de origen, se le pedirá al usuario una contraseña de Kerberos. La contraseña se utiliza luego para obtener un ticket de concesión de tickets del servidor Kerberos. El peligro de configurar ksu con esta macro es que si el usuario de origen está conectado remotamente y no tiene un canal seguro, la contraseña puede quedar expuesta.
PRINC_LOOK_AHEAD
Durante la resolución del nombre de principal predeterminado, PRINC_LOOK_AHEAD permite a ksu encontrar nombres de principales en el archivo .k5users como se describe en la sección OPCIONES (ver opción -n ).
CMD_PATH
Especifica una lista de directorios que contienen programas que los usuarios están autorizados a ejecutar (a través del archivo .k5users).
HAVE_GETUSERSHELL
Si el usuario de origen no es root, ksu insiste en que el shell del usuario de destino que se invoca sea un shell "legal". Se llama a getusershell(3) para obtener los nombres de los shells "legales". Tenga en cuenta que el shell del usuario de destino se obtiene del archivo passwd.

Configuración de ejemplo:

KSU_OPTS = -DGET_TGT_VIA_PASSWD -DPRINC_LOOK_AHEAD -DCMD_PATH='"/bin /usr/ucb /local/bin"

ksu debe ser propiedad de root y tener activado el bit set user id.

ksu intenta obtener un ticket para el servidor final al igual que telnet y rlogin con Kerberos. Por lo tanto, debe haber una entrada para el servidor en la base de datos de Kerberos (por ejemplo, host/nii.isi.edu@ISI.EDU). El archivo keytab debe estar en una ubicación apropiada.

EFECTOS SECUNDARIOS

ksu elimina todos los tickets caducados de la caché de origen.
