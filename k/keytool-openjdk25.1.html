DESCRIPCIÓ

N

El comando keytool es una utilidad de gestión de claves y certificados. Permite a los usuarios administrar sus propios pares de claves pública/privada y los certificados asociados para su uso en la autoautenticación (donde un usuario se autentica a sí mismo ante otros usuarios y servicios) o en servicios de integridad y autenticación de datos, mediante el uso de firmas digitales. El comando keytool también permite a los usuarios almacenar en caché las claves públicas (en forma de certificados) de sus pares de

comunicación.

Un certificado es una declaración firmada digitalmente por una entidad (persona, empresa, etc.), que indica que la clave pública (y alguna otra información) de alguna otra entidad tiene un valor particular. Cuando los datos se firman digitalmente, la firma puede verificarse para comprobar la integridad y autenticidad de los datos. Integridad significa que los datos no han sido modificados ni manipulados, y autenticidad significa que los datos provienen del individuo que afirma haberlos creado y

firmado.

El comando keytool también permite a los usuarios administrar claves secretas y frases de contraseña utilizadas en el cifrado y descifrado simétrico (Estándar de Cifrado de Datos). También puede mostrar otra información relacionada con la

seguridad.

El comando keytool almacena las claves y los certificados en un almacén de

claves.

El comando keytool utiliza las propiedades de seguridad jdk.certpath.disabledAlgorithms y jdk.security.legacyAlgorithms para determinar qué algoritmos se consideran un riesgo de seguridad. Emite advertencias cuando se utilizan algoritmos deshabilitados o heredados. Las propiedades de seguridad jdk.certpath.disabledAlgorithms y jdk.security.legacyAlgorithms están definidas en el archivo java.security (ubicado en el directorio $JAVA_HOME/conf/s

ecurity d
el JDK).

Utilice el comando -genkeypair para generar un par de claves (una clave pública y la clave privada asociada). Cuando no se especifica la opción -signer, la clave pública se envuelve en un certificado autofirmado X.509 v3 y se almacena como una cadena de certificados de un solo elemento. Cuando se especifica la opción -signer, se genera un nuevo certificado y lo firma el firmante designado, y se almacena como una cadena de certificados de múltiples elementos (que contiene el propio certificado generado y la cadena de certificados del firmante). La cadena de certificados y la clave privada se almacenan en una nueva entrada del almacén de claves identificada por su

alias.

El valor -keyalg especifica el algoritmo que se debe usar para generar el par de claves. El valor -keysize especifica el tamaño de cada clave que se va a generar. El valor -groupname especifica el grupo con nombre (por ejemplo, el nombre estándar o predefinido de una Curva Elíptica) de la clave que se va a

generar.

El comando keytool puede importar certificados X.509 v1, v2 y v3, y cadenas de certificados con formato PKCS#7 que constan de certificados de ese tipo. Los datos a importar deben proporcionarse ya sea en formato de codificación binaria o en formato de codificación imprimible (también conocido como codificación Base64) como lo define el estándar de Internet RFC 1421. En el último caso, la codificación debe estar delimitada al principio por una cadena que comienza con -----BEGIN, y delimitada al final por una cadena que comienza con -----END

.

Importa un certificado por dos razones: para añadirlo a la lista de certificados de confianza e importar una respuesta de certificado recibida de una autoridad de certificación (CA) como resultado de enviar una Solicitud de Firma de Certificado (CSR) a esa CA. ificado.

En este caso, el alias no debería existir ya en el almacén de claves. Si el alias ya existe, el comando keytool muestra un error porque ya existe un certificado de confianza para ese alias, y no importa el certificado. KEYTOOL KEYSTORE MANAGEMENT

keytool is a key and certificate management utility that facilitates the integrity and authenticity of information exchanged between clients and servers.

It supports the following functions:

•
Creating and managing a private/public key pair.
•
Generating a Certificate Signing Request (CSR) to submit to a Certificate Authority (CA).
•
Importing and exporting a certificate and certificate chain.
•
Importing a certificate that authenticates the public key of a CA.
•
Generating an SSL certificate for an SSL server.

A keystore is a protected collection of entries, where each entry contains a secret key, a certificate, or a trusted certificate. The keytool utility can be used to manage the following types of keystores:

•

JKS keystore

The default keystore type. JKS is a Java Key Store that is proprietary to Oracle.

•

PKCS12 keystore

A widely used keystore type that is an industry standard.

See keytool(1) for a detailed description of the keytool command, its options, and usage.

The following options are common to many keytool commands:

alias
The alias for the entry in the keystore. Each entry in a keystore is identified by an alias.
keystore
The name of the keystore file. If this option is not specified, keytool uses the default keystore, which is typically located in the user's home directory as ~/.keystore.
storepass
The password for the keystore. This password is required to access or modify the keystore.
keypass
The password for the private key within the keystore. This password is required to access or modify the private key.
file
The name of the file from which to read or write data, such as a certificate or a certificate request.
dname
The Distinguished Name (DN) of the entity associated with the key pair. The DN consists of attribute-value pairs, such as cn=Common Name, ou=Organizational Unit, o=Organization, c=Country.
keyalg
The name of the public-digest algorithm (such as RSA or DSA) used to generate the key pair.
keysize
The length of the key in bits.
validity
The number of days for which the generated certificate will be valid.

The following options are used when dealing with certificates:

certreq
Generates a certificate signing request (CSR).
exportcert
Exports a certificate that authenticates a public key.
importcert
Imports a certificate or a certificate chain.
printcert
Displays information about a certificate.
gencertificate
Generates a certificate.

CAUTION:

Users should be aware that some combinations of extensions (and other certificate fields) may not conform to the Internet standard. See Certificate Conformance Warning.

GENERATING THE KEY PAIR

Create a keystore and then generate the key pair.

You can enter the command as a single line such as the following:

keytool -genkeypair -dname "cn=myname, ou=mygroup, o=mycompany, c=mycountry" -alias business -keyalg rsa -keypass password -keystore /working/mykeystore -storepass password -validity 180

The command creates the keystore named mykeystore in the working directory (provided it doesn't already exist), and assigns it the password specified by -keypass. It generates a public/private key pair for the entity whose distinguished name is myname, mygroup, mycompany, and a two-letter country code of mycountry. It uses the RSA key generation algorithm to create the keys; both are 3072 bits.

The command uses the default SHA384withRSA signature algorithm to create a self-signed certificate that includes the public key and the distinguished name information. The certificate is valid for 180 days, and is associated with the private key in a keystore entry referred to by -alias business. The private key is assigned the password specified by -keypass.

The command is significantly shorter when the option defaults are accepted. In this case, only -keyalg is required, and the defaults are used for unspecified options that have default values. You are prompted for any required values. You could have the following:

keytool -genkeypair -keyalg rsa

In this case, a keystore entry with the alias mykey is created, with a newly generated key pair and a certificate that is valid for 90 days. This entry is placed in your home directory in a keystore named .keystore . .keystore is created if it doesn't already exist. You are prompted for the distinguished name information, the keystore password, and the private key password.

Note:

The rest of the examples assume that you responded to the prompts with values equal to those specified in the first -genkeypair command. For example, a distinguished name of cn=myname, ou=mygroup, o=mycompany, c=mycountry.

REQUESTING A SIGNED CERTIFICATE FROM A CA

Note:

Generating the key pair created a self-signed certificate; however, a certificate is more likely to be trusted by others when it is signed by a CA.

To get a CA signature, complete the following process:

1.
Generate a CSR:

keytool -certreq -file myname.csr

This creates a CSR for the entity identified by the default alias mykey and puts the request in the file named myname.csr.

2.
Submit myname.csr to a CA, such as DigiCert.

The CA authenticates you, the requestor (usually offline), and returns a certificate, signed by them, authenticating your public key. In some cases, the CA returns a chain of certificates, each one authenticating the public key of the signer of the previous certificate in the chain.

IMPORTING A CERTIFICATE FOR THE CA

To import a certificate for the CA, complete the following process:

1.
Before you import the certificate reply from a CA, you need one or more trusted certificates either in your keystore or in the cacerts keystore file. See -importcert in Commands.
•
If the certificate reply is a certificate chain, then you need the top certificate of the chain. The root CA certificate that authenticates the public key of the CA.
•
If the certificate reply is a single certificate, then you need a certificate for the issuing CA (the one that signed it). If that certificate isn't self-signed, then you need a certificate for its signer, and so on, up to a self-signed root CA certificate.

The cacerts keystore ships with a set of root certificates issued by the CAs of the Oracle Java Root Certificate program [https://www.oracle.com/java/technologies/javase/carootcertsprogram.html]. If you request a signed certificate from a CA, and a certificate authenticating that CA's public key hasn't been added to cacerts, then you must import a certificate from that CA as a trusted certificate.

A certificate from a CA is usually self-signed or signed by another CA. If it is signed by another CA, you need a certificate that authenticates that CA's public key.

For example, you have obtained a X.cer file from a company that is a CA and the file is supposed to be a self-signed certificate that authenticates that CA's public key. Before you import it as a trusted certificate, you should ensure that the certificate is valid by:

1.
Viewing it with the keytool -printcert command or the keytool -importcert command without using the -noprompt option. Make sure that the displayed certificate fingerprints match the expected fingerprints.
2.
Calling the person who sent the certificate, and comparing the fingerprints that you see with the ones that they show or that a secure public key repository shows.

Only when the fingerprints are equal is it assured that the certificate wasn't replaced in transit with somebody else's certificate (such as an attacker's certificate). If such an attack takes place, and you didn't check the certificate before you imported it, then you would be trusting anything that the attacker signed.

2.
Replace the self-signed certificate with a certificate chain, where each certificate in the chain authenticates the public key of the signer of the previous certificate in the chain, up to a root CA.

If you trust that the certificate is valid, then you can add it to your keystore by entering the following command:

keytool -importcert -alias alias -file *X*.cer`

This command creates a trusted certificate entry in the keystore from the data in the CA certificate file and assigns the values of the alias to the entry.

IMPORTING THE CERTIFICATE REPLY FROM THE CA

After you import a certificate that authenticates the public key of the CA that you submitted your certificate signing request to (or there is already such a certificate in the cacerts file), you can import the certificate reply and replace your self-signed certificate with a certificate chain.

The certificate chain is one of the following:

•
Returned by the CA when the CA reply is a chain.
•
Constructed when the CA reply is a single certificate. This certificate chain is constructed by using the certificate reply and trusted certificates available either in the keystore where you import the reply or in the cacerts keystore file.

For example, if you sent your certificate signing request to DigiCert, then you can import their reply by entering the following command:

Note:

In this example, the returned certificate is named DCmyname.cer.

keytool -importcert -trustcacerts -file DCmyname.cer

EXPORTING A CERTIFICATE THAT AUTHENTICATES THE PUBLIC KEY

Note:

If you used the jarsigner command to sign a Java Archive (JAR) file, then clients that use the file will want to authenticate your signature.

One way that clients can authenticate you is by importing your public key certificate into their keystore as a trusted entry. You can then export the certificate and supply it to your clients.

For example:

1.
Copy your certificate to a file named myname.cer by entering the following command:

Note:

In this example, the entry has an alias of myname.

keytool -exportcert -alias myname -file myname.cer

This command copies the certificate associated with the alias myname from the default keystore to the file myname.cer in the current directory.

2.
Give the myname.cer file to your clients.

Your clients can then import this certificate into their keystore as a trusted certificate.

GENERATING CERTIFICATES FOR AN SSL SERVER

To generate certificates for an SSL server, you need to perform the following tasks:

1.
Generate the key pair and the self-signed certificate:

keytool -genkeypair -dname "cn=server_hostname, ou=mygroup, o=mycompany, c=mycountry" -alias server-alias -keyalg rsa -keypass server_password -keystore server.keystore -storepass store_password -validity 365

This command generates a key pair and a self-signed certificate for the SSL server, identified by its hostname server_hostname. The certificate is valid for 365 days and is stored in the file server.keystore.

2.
Generate a certificate signing request (CSR):

keytool -certreq -alias server-alias -file server.csr

This command generates a CSR for the server's key pair, which should be sent to a CA for signing.

3.
After receiving the signed certificate from the CA (e.g., server_signed.cer), import it into the keystore:

keytool -importcert -alias server-alias -file server_signed.cer -keystore server.keystore

This command replaces the self-signed certificate with the CA-signed certificate.

The keystore server.keystore now contains the server's private key and the CA-signed certificate, which can be used for SSL/TLS communication.

Certificado
Un certificado (o certificado de clave pública) es una declaración firmada digitalmente de una entidad (el emisor), que indica que la clave pública y alguna otra información de otra entidad (el sujeto) tienen algún valor específico. Los siguientes términos están relacionados con los certificados:
•
Claves Públicas: Son números asociados con una entidad particular y están destinados a ser conocidos por todos los que necesiten tener interacciones de confianza con esa entidad. Las claves públicas se utilizan para verificar firmas.
•
Firmado Digitalmente: Si algunos datos están firmados digitalmente, entonces se almacenan con la identidad de una entidad y una firma que demuestra que esa entidad conoce los datos. Los datos se vuelven inalterables al firmarlos con la clave privada de la entidad.
•
Identidad: Una forma conocida de dirigirse a una entidad. En algunos sistemas, la identidad es la clave pública, y en otros puede ser cualquier cosa, desde un UID de Oracle Solaris hasta una dirección de correo electrónico o un nombre distinguido X.509.
•
Firma: Una firma se calcula sobre algunos datos utilizando la clave privada de una entidad. El firmante, que en el caso de un certificado también se conoce como el emisor.
•
Claves Privadas: Son números, cada uno de los cuales debe ser conocido solo por la entidad particular cuya clave privada es (es decir, se supone que debe mantenerse en secreto). Las claves privadas y públicas existen en pares en todos los sistemas de criptografía de clave pública (también denominados sistemas de criptografía de clave pública). En un sistema de criptografía de clave pública típico, como DSA, una clave privada corresponde exactamente a una clave pública. Las claves privadas se utilizan para calcular firmas.
•
Entidad: Una entidad es una persona, organización, programa, computadora, negocio, banco o algo más en lo que se confía hasta cierto punto.

La criptografía de clave pública requiere acceso a las claves públicas de los usuarios. En un entorno de red a gran escala, es imposible garantizar que se hayan establecido relaciones previas entre las entidades que se comunican o que exista un repositorio de confianza con todas las claves públicas utilizadas. Los certificados se inventaron como una solución a este problema de distribución de claves públicas. Ahora una Autoridad de Certificación (CA) puede actuar como un tercero de confianza. Las CA son entidades como empresas en las que se confía para firmar (emitir) certificados para otras entidades. Se asume que las CA solo crean certificados válidos y confiables porque están vinculadas por acuerdos legales. Hay muchas Autoridades de Certificación públicas, como DigiCert, Comodo, Entrust, etc.

También puede ejecutar su propia Autoridad de Certificación utilizando productos como Microsoft Certificate Server o el producto Entrust CA para su organización. Con el comando keytool, es posible mostrar, importar y exportar certificados. También es posible generar certificados autofirmados.

El comando keytool actualmente maneja certificados X.509.

Certificados X.509
El estándar X.509 define qué información puede ir en un certificado y describe cómo escribirla (el formato de los datos). Todos los datos de un certificado se codifican con dos estándares relacionados llamados ASN.1/DER. Abstract Syntax Notation 1 describe los datos. Las Reglas de Codificación Definida describen una única forma de almacenar y transferir esos datos.

Todos los certificados X.509 tienen los siguientes datos, además de la firma:

•
Versión: Esto identifica qué versión del estándar X.509 se aplica a este certificado, lo que afecta a la información que se puede especificar en él. Hasta ahora, se han definido tres versiones. El comando keytool puede importar y exportar certificados v1, v2 y v3. Genera certificados v3.
•
La versión X.509 1 ha estado disponible desde 1988, está ampliamente desplegada y es la más genérica.
•
La versión X.509 2 introdujo el concepto de identificadores únicos de sujeto y emisor para manejar la posibilidad de reutilización de nombres de sujeto o emisor con el tiempo. La mayoría de los documentos de perfil de certificado recomiendan firmemente que los nombres no se reutilicen y que los certificados no utilicen identificadores únicos. Los certificados de versión 2 no se utilizan ampliamente.
•
La versión X.509 3 es la más reciente (1996) y admite la noción de extensiones donde cualquiera puede definir una extensión e incluirla en el certificado. Algunas extensiones comunes son: KeyUsage (limita el uso de las claves a fines particulares como firma-solo) y AlternativeNames (permite asociar otras identidades a esta clave pública, por ejemplo, nombres DNS, direcciones de correo electrónico, direcciones IP). Las extensiones se pueden marcar como críticas para indicar que la extensión debe verificarse y aplicarse o utilizarse. Por ejemplo, si un certificado tiene la extensión KeyUsage marcada como crítica y establecida en keyCertSign, entonces cuando este certificado se presente durante la comunicación SSL, debe ser rechazado porque la extensión del certificado indica que la clave privada asociada solo debe usarse para firmar certificados y no para uso SSL.
•
Número de serie: La entidad que creó el certificado es responsable de asignarle un número de serie para distinguirlo de otros certificados que emite. Esta información se utiliza de numerosas maneras. Por ejemplo, cuando se revoca un certificado, su número de serie se coloca en una Lista de Revocación de Certificados (CRL).
•
Identificador del algoritmo de firma: Esto identifica el algoritmo utilizado por la CA para firmar el certificado.
•
Nombre del emisor: El Nombre Distinguido X.500 de la entidad que firmó el certificado. Típicamente es una CA. Usar este certificado implica confiar en la entidad que firmó este certificado. En algunos casos, como los certificados raíz o de nivel superior de CA, el emisor firma su propio certificado.
•
Período de validez: Cada certificado solo es válido por un tiempo limitado. Este período se describe mediante una fecha y hora de inicio y una fecha y hora de fin, y puede ser tan corto como unos pocos segundos o casi un siglo. El período de validez elegido depende de varios factores, como la fuerza de la clave privada utilizada para firmar el certificado, o la cantidad que uno está dispuesto a pagar por un certificado. Este es el período esperado durante el cual las entidades pueden confiar en el valor público, cuando la clave privada asociada no se ha visto comprometida.
•
Nombre del sujeto: El nombre de la entidad cuya clave pública identifica el certificado. Este nombre utiliza el estándar X.500, por lo que está destinado a ser único en Internet. Este es el Nombre Distinguido (DN) X.500 de la entidad. Por ejemplo,

CN=Java Duke, OU=Java Software Division, O=Oracle Corporation, C=US

Estos se refieren al nombre común (CN), unidad organizativa (OU), organización (O) y país (C) del sujeto.

•
Información de clave pública del sujeto: Esta es la clave pública de la entidad que se está nombrando con un identificador de algoritmo que especifica a qué sistema de criptografía de clave pública pertenece esta clave y cualquier parámetro de clave asociado.
Cadenas de Certificados
El comando keytool puede crear y administrar entradas de clave de almacén de claves que cada una contiene una clave privada y una cadena de certificados asociada. El primer certificado de la cadena contiene la clave pública que corresponde a la clave privada.

Cuando se generan las claves por primera vez, la cadena generalmente comienza conteniendo un solo elemento, un certificado autofirmado. Consulte -genkeypair en Comandos. Un certificado autofirmado es aquel para el cual el emisor (firmante) es el mismo que el sujeto. El sujeto es la entidad cuya clave pública está siendo autenticada por el certificado. Cuando se llama al comando -genkeypair para generar un nuevo par de claves pública/privada, también envuelve la clave pública en un certificado autofirmado (a menos que se especifique la opción -signer).

Más tarde, después de que se generó una Solicitud de Firma de Certificado (CSR) con el comando -certreq y se envió a una Autoridad de Certificación (CA), la respuesta de la CA se importa con -importcert, y el certificado autofirmado es reemplazado por una cadena de certificados. Al final de la cadena está el certificado (respuesta) emitido por la CA que autentica la clave pública del sujeto. El siguiente certificado en la cadena es uno que autentica la clave pública de la CA.

En muchos casos, este es un certificado autofirmado, que es un certificado de la CA que autentica su propia clave pública, y es el último certificado de la cadena. En otros casos, la CA puede devolver una cadena de certificados. En este caso, el certificado inferior de la cadena es el mismo (un certificado firmado por la CA, que autentica la clave pública de la entrada de clave), pero el segundo certificado de la cadena es un certificado firmado por una CA diferente que autentica la clave pública de la CA a la que envió la CSR. La

El siguiente certificado en la cadena es un certificado que autentica la clave de la segunda CA, y así sucesivamente, hasta llegar a un certificado raíz autofirmado. Cada certificado en la cadena (después del primero) autentica la clave pública del firmante del certificado anterior en la cadena.

Muchas CA solo devuelven el certificado emitido, sin la cadena de soporte, especialmente cuando hay una jerarquía plana (sin CAs intermedias). En este caso, la cadena de certificados debe establecerse a partir de la información de certificados de confianza ya almacenada en el almacén de claves.

Un formato de respuesta diferente (definido por el estándar PKCS #7) incluye la cadena de certificados de soporte además del certificado emitido. Ambos formatos de respuesta pueden ser manejados por el comando keytool.

El certificado raíz (de nivel superior) de la CA está autofirmado. Sin embargo, la confianza en la clave pública de la raíz no proviene del certificado raíz en sí, sino de otras fuentes como un periódico. Esto se debe a que cualquiera podría generar un certificado autofirmado con el nombre distintivo de, por ejemplo, la CA raíz DigiCert. La clave pública de la CA raíz es ampliamente conocida. La única razón por la que se almacena en un certificado es porque este es el formato entendido por la mayoría de las herramientas, por lo que el certificado en este caso solo se utiliza como un vehículo para transportar la clave pública de la CA raíz. Antes de agregar el certificado de la CA raíz a su almacén de claves, debe verlo con la opción -printcert y comparar la huella digital mostrada con la huella digital conocida obtenida de un periódico, la página web de la CA raíz, etc.

•

Estándar de Codificación de Certificados RFC 1421 de Internet
Los certificados a menudo se almacenan utilizando el formato de codificación imprimible definido por el estándar RFC 1421 de Internet, en lugar de su codificación binaria. Este formato de certificado, también conocido como codificación Base64, facilita la exportación de certificados a otras aplicaciones por correo electrónico o a través de algún otro mecanismo.

Los certificados leídos por los comandos -importcert y -printcert pueden estar en este formato o codificados en binario. El comando -exportcert por defecto produce un certificado en codificación binaria, pero producirá un certificado en el formato de codificación imprimible cuando se especifique la opción -rfc.

El comando -list por defecto imprime la huella digital SHA-256 de un certificado. Si se especifica la opción -v, entonces el certificado se imprime en formato legible por humanos. Si se especifica la opción -rfc, entonces el certificado se emite en el formato de codificación imprimible.

En su formato de codificación imprimible, el certificado codificado está delimitado al principio y al final por el siguiente texto:

-----BEGIN CERTIFICATE-----
aquí va el certificado codificado.
-----END CERTIFICATE-----
Nombres Distintivos X.500
Los Nombres Distintivos X.500 se utilizan para identificar entidades, como las que se nombran en los campos subject (sujeto) e issuer (emisor) de los certificados X.509. El comando keytool admite las siguientes subpartes:
•
commonName: El nombre común de una persona, como Susan Jones.
•
organizationUnit: El nombre de la pequeña organización (como departamento o división). Por ejemplo, Compras.
•
localityName: El nombre de la localidad (ciudad), por ejemplo, Palo Alto.
•
stateName: El nombre del estado o provincia, por ejemplo, California.
•
country: Código de país de dos letras, por ejemplo, CH.

Cuando proporcione una cadena de nombre distintivo como valor de una opción -dname, como para el comando -genkeypair, la cadena debe estar en el siguiente formato:

CN=cName, OU=orgUnit, O=org, L=city, S=state, C=countryCode

Todos los siguientes elementos representan valores reales y las palabras clave anteriores son abreviaturas de los siguientes:

CN=commonName
OU=organizationUnit
O=organizationName
L=localityName
S=stateName
C=country

Una cadena de nombre distintivo de ejemplo es:

CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino, S=California, C=US

Un comando de ejemplo que utiliza dicha cadena es:

keytool -genkeypair -dname "CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino, S=California, C=US" -alias mark -keyalg rsa

La capitalización no importa para las abreviaturas de las palabras clave. Por ejemplo, CN, cn y Cn se tratan de la misma manera.

El orden importa; cada subcomponente debe aparecer en el orden designado. Sin embargo, no es necesario tener todos los subcomponentes. Puede utilizar un subconjunto, por ejemplo:

CN=Smith, OU=Java, O=Oracle, C=US

Si un valor de cadena de nombre distintivo contiene una coma, entonces la coma debe ser escapada por un carácter de barra invertida (\) cuando especifique la cadena en una línea de comandos, como en:

cn=Jack, ou=Java\, Product Development, o=Oracle, c=US

Nunca es necesario especificar una cadena de nombre distintivo en una línea de comandos. Cuando se necesita el nombre distintivo para un comando, pero no se proporciona en la línea de comandos, se le pide al usuario cada uno de los subcomponentes. En este caso, no es necesario escapar una coma con una barra invertida (\).

Si se produjera un ataque de este tipo y no verificara el certificado antes de importarlo, entonces confiaría en cualquier cosa que firmara el atacante, por ejemplo, un archivo JAR con archivos de clase maliciosos dentro.

Nota:

No es necesario ejecutar un comando -printcert antes de importar un certificado. Esto se debe a que antes de añadir un certificado a la lista de certificados de confianza en el almacén de claves, el comando -importcert imprime la información del certificado y le pide que la verifique. A continuación, puede detener la operación de importación. Sin embargo, esto solo se puede hacer cuando se llama al comando -importcert sin la opción -noprompt. Si se especifica la opción -noprompt, no hay interacción con el usuario.

ADVERTENCIA SOBRE CONTRASEÑAS

La mayoría de los comandos que operan en un almacén de claves requieren la contraseña del almacén. Algunos comandos requieren una contraseña de clave privada/secreta. Las contraseñas se pueden especificar en la línea de comandos con las opciones -storepass y -keypass. Sin embargo, una contraseña no debe especificarse en una línea de comandos o en un script a menos que sea para pruebas, o si se encuentra en un sistema seguro. Cuando no especifica una opción de contraseña requerida en una línea de comandos, se le solicita.

ADVERTENCIA SOBRE CONFORMIDAD DEL CERTIFICADO

Perfil de certificado y lista de revocación de certificados (CRL) de Internet X.509 Public Key Infrastructure [https://tools.ietf.org/rfc/rfc5280.txt] definió un perfil para los certificados X.509 conformes, que incluye qué valores y combinaciones de valores son válidos para los campos y extensiones de los certificados.

El comando keytool no aplica todas estas reglas, por lo que puede generar certificados que no se ajustan al estándar, como certificados autofirmados que se utilizarían para fines de prueba internos. Los certificados que no se ajustan al estándar pueden ser rechazados por el JDK u otras aplicaciones. Los usuarios deben asegurarse de proporcionar las opciones correctas para -dname, -ext, etc.

IMPORTAR UN NUEVO CERTIFICADO DE CONFIANZA

Antes de añadir el certificado al almacén de claves, el comando keytool lo verifica intentando construir una cadena de confianza desde ese certificado hasta un certificado autofirmado (perteneciente a una CA raíz), utilizando los certificados de confianza que ya están disponibles en el almacén de claves.

Si se especificó la opción -trustcacerts, se consideran certificados adicionales para la cadena de confianza, a saber, los certificados de un archivo llamado cacerts.

Si el comando keytool no logra establecer una ruta de confianza desde el certificado a importar hasta un certificado autofirmado (ya sea desde el almacén de claves o el archivo cacerts), entonces se imprime la información del certificado y se le pide al usuario que la verifique comparando las huellas digitales del certificado mostrado con las huellas digitales obtenidas de alguna otra fuente de información (confiable), que podría ser el propietario del certificado. Tenga mucho cuidado para asegurarse de que el certificado es válido antes de importarlo como certificado de confianza. El usuario tiene entonces la opción de detener la operación de importación. Si se especifica la opción -noprompt, no hay interacción con el usuario.

IMPORTAR UNA RESPUESTA DE CERTIFICADO

Al importar una respuesta de certificado, esta se valida con certificados de confianza del almacén de claves y, opcionalmente, con los certificados configurados en el archivo de almacén de claves cacerts cuando se especifica la opción -trustcacerts.

Los métodos para determinar si la respuesta del certificado es confiable son los siguientes:

•
Si la respuesta es un único certificado X.509, el comando keytool intenta establecer una cadena de confianza, comenzando por la respuesta del certificado y terminando en un certificado autofirmado (perteneciente a una CA raíz). La respuesta del certificado y la jerarquía de certificados se utilizan para autenticar la respuesta del certificado de la nueva cadena de alias de certificados. Si no se puede establecer una cadena de confianza, la respuesta del certificado no se importa. En este caso, el comando keytool no imprime el certificado ni solicita al usuario que lo verifique, ya que es muy difícil para un usuario determinar la autenticidad de la respuesta del certificado.
•
Si la respuesta es una cadena de certificados en formato PKCS #7 o una secuencia de certificados X.509, la cadena se ordena con el certificado del usuario primero, seguido de cero o más certificados de CA. Si la cadena termina con un certificado de CA raíz autofirmado y se especificó la opción -trustcacerts, el comando keytool intenta que coincida con alguno de los certificados de confianza en el almacén de claves o en el archivo de almacén de claves cacerts. Si la cadena no termina con un certificado de CA raíz autofirmado y se especificó la opción -trustcacerts, el comando keytool intenta encontrar uno de los certificados de confianza en el almacén de claves o en el archivo de almacén de claves cacerts y añadirlo al final de la cadena. Si no se encuentra el certificado y no se especifica la opción -noprompt, se imprime la información del último certificado de la cadena y se le pide al usuario que la verifique.

Si la clave pública en la respuesta del certificado coincide con la clave pública del usuario ya almacenada con alias, la antigua cadena de certificados se reemplaza por la nueva cadena de certificados en la respuesta. La antigua cadena solo se puede reemplazar con una keypass válida, por lo que se proporciona la contraseña que protege la clave privada de la entrada. Si no se proporciona ninguna contraseña y la contraseña de la clave privada es diferente de la contraseña del almacén de claves, se le solicita al usuario.

Este comando se llamaba -import en versiones anteriores. Este nombre antiguo todavía es compatible en esta versión. Se prefiere el nuevo nombre, -importcert.
