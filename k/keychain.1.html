NOMBRE

keychain - Gestor para ssh-agent, gpg-agent y claves privadas. Compatible con sistemas POSIX.

SINOPSIS

keychain [ -hklQqV ] [ --clear --confhost --confallhosts --debug --extended --gpg2 --help --ignore-missing --list --noask --nocolor --nogui --noinherit --nolock --quick --quiet --ssh-allow-forwarded --ssh-allow-gpg --ssh-rm --ssh-spawn-gpg --systemd --version ] [ --ssh-agent-socket ruta ] [ --dir nombre_directorio ] [ --host nombre ] [ --lockwait segundos ] [ --stop cuál ] [ --timeout minutos ] [ --wipe cuál ] [ claves... ]

INTRODUCCIÓN

Keychain ayuda a gestionar claves SSH y GPG de forma cómoda y segura. Actúa como una interfaz para "ssh-agent" y "ssh-add", pero te permite tener fácilmente un único proceso "ssh-agent" de larga duración por sistema, en lugar de la norma de un "ssh-agent" por sesión de inicio de sesión.

Esto reduce drásticamente el número de veces que necesitas introducir tu frase de contraseña. Con "keychain", solo necesitas introducir una frase de contraseña una vez cada vez que se reinicie tu máquina local. Keychain también facilita que los trabajos cron remotos se "conecten" de forma segura a un proceso "ssh-agent" en ejecución, permitiendo que tus scripts aprovechen los inicios de sesión basados en claves.

Keychain también soporta GnuPG 2.1 y posteriores, e iniciará automáticamente gpg-agent si se referencian claves GPG en la línea de comandos, y se asegurará de que estas credenciales se almacenen en caché en memoria y estén disponibles para su uso.

Página oficial del proyecto: https://github.com/danielrobbins/keychain.

COMPATIBILIDAD

Keychain soporta la mayoría de los sistemas operativos tipo UNIX y limita intencionadamente su alcance a implementaciones modernas y ampliamente desplegadas de OpenSSH y GnuPG.

  • Versión mínima de OpenSSH: 7.3

    OpenSSH 7.3 (lanzado el 2016-08-01) introdujo la opción "-G" (volcado de configuración) utilizada por Keychain para expandir claves extendidas "host:" y la característica "--confallhosts". Dado que esta opción es fundamental para el descubrimiento de claves moderno, Keychain tiene como objetivo oficial OpenSSH 7.3 o superior. Versiones anteriores (>=6.5) pueden parecer funcionar para uso básico (cargando claves explícitamente nombradas) pero no forman parte de la matriz de pruebas soportada.

    Los tipos de claves soportadas bajo la línea base 7.3+ incluyen RSA, ECDSA y Ed25519 (Ed25519 apareció por primera vez en OpenSSH 6.5). Las claves DSA han sido deshabilitadas por defecto upstream desde OpenSSH 7.0; Keychain aún las listará o cargará si están explícitamente habilitadas y presentes, pero se consideran heredadas.

    Características aprovechadas de OpenSSH:

    ssh -V            (detección de implementación)
ssh -nG host      (expansión de configuración para claves extendidas host:)
ssh-agent -s      (salida de entorno compatible con Bourne; siempre forzado)
ssh-agent -t      (vida útil predeterminada de la clave al iniciar)
ssh-agent -a ruta (ruta de socket explícita cuando se solicita)
ssh-add -l/-L     (listar huellas dactilares / claves públicas)
ssh-add -d/-D     (eliminar una / eliminar todas las claves)
ssh-add -c        (modo de confirmación)
ssh-add -t        (anulación de vida útil por clave)
ssh-keygen -l -f  (extracción de huella dactilar, maneja SHA256 y MD5 heredado)
Sockets de agente reenviados (opcionalmente adoptados con --ssh-allow-forwarded)
  • GnuPG / gpg-agent

    Se requiere GnuPG 2.1 o posterior para la integración con gpg-agent. Keychain utiliza "gpg-connect-agent" "GETINFO nombre_socket" y "GETINFO ssh_nombre_socket" para detectar, adoptar o (opcionalmente) iniciar gpg-agent cuando actúa como agente SSH a través de "--ssh-allow-gpg" o "--ssh-spawn-gpg". Versiones anteriores de GnuPG (2.0.x) carecían de soporte fiable para el almacenamiento de claves SSH y no están soportadas.

  • Shells

    El script Keychain en sí requiere un shell compatible con POSIX / Bourne. Genera archivos pid para shells Bourne ("...-sh"), csh/tcsh ("...-csh") y fish ("...-fish"). Internamente Keychain ahora consume siempre la salida canónica Bourne de ssh-agent (forzada con "-s") y deriva los otros formatos de shell. Bash, ksh y zsh consumen los archivos pid Bourne.

    Keychain está soportado oficialmente en Git Bash (MSYS2) para Windows, incluyendo el manejo adecuado de rutas y nombres de usuario de estilo Windows que contienen espacios.

    Los archivos pid de csh/tcsh y fish siguen siendo soportados para compatibilidad con versiones anteriores. Son candidatos a ser deprecados: se anunciará una advertencia sobre la eliminación planificada al menos dos versiones menores antes de cualquier cambio.

  • Espacios en HOME y rutas

    Keychain 2.9.7+ maneja correctamente los directorios de inicio y las rutas de claves privadas que contienen espacios. Todas las variables de ruta en los archivos pid (SSH_AUTH_SOCK) se citan para garantizar un análisis correcto por parte de los shells. La implementación utiliza un enfoque robusto que evalúa la salida de ssh-agent en un subshell para extraer variables de entorno directamente, en lugar de un análisis de cadenas frágil. Esto garantiza la compatibilidad incluso si el formato de salida de ssh-agent cambia. La detección de propiedad de archivos utiliza el formato de salida de `ls` definido por POSIX con lógica para analizar correctamente nombres de usuario que contienen espacios.

  • Heredado / Otras implementaciones SSH

    SunSSH (que se encuentra en versiones antiguas de Oracle Solaris) todavía puede funcionar; se conservan rutas de código para la detección de SunSSH pero no se prueban activamente. Están programadas para revisión y posible eliminación después de tres futuras versiones menores, a menos que la retroalimentación de la comunidad solicite su retención.

    La implementación comercial histórica ssh.com y su agente ya no son objetivos. Si se detectan, el comportamiento puede recurrir a una carga de claves más simple; las características avanzadas (confirmación, análisis de huellas dactilares modernas, expansión de host) no están garantizadas. Informar de dicho uso a través de Problemas de GitHub ayudará a dar forma a cualquier decisión de soporte futuro.

  • Entorno de usuario Systemd

    En sistemas con systemd --user, Keychain puede inyectar "SSH_AUTH_SOCK" (y opcionalmente "SSH_AGENT_PID") a través de "--systemd" para una mayor disponibilidad en la sesión.

Resumen: Un entorno soportado es OpenSSH >= 7.3 más (opcionalmente) GnuPG >= 2.1, ejecutándose bajo cualquier SO moderno similar a UNIX con un shell POSIX. Versiones anteriores o implementaciones SSH no listadas pueden funcionar para escenarios básicos pero están fuera del alcance oficial.

CICLO DE VIDA

Típicamente, configuras keychain para que se ejecute cuando inicias sesión por primera vez en un sistema. Si estás usando Bourne shell o bash, crearás un archivo ~/.profile o ~/.bash_profile e incluirás la siguiente línea:

eval "$(keychain --eval id_rsa)"

Keychain iniciará ssh-agent si aún no hay uno en ejecución. Keychain luego comprueba para asegurarse de que tus claves privadas (en este ejemplo, "id_rsa") estén cargadas en el agente. Si no lo están, se te pedirá cualquier frase de contraseña necesaria para descifrarlas, para que se almacenen en caché en memoria y estén disponibles para su uso.

Además de mostrar una salida amigable para el usuario en tu terminal, keychain también mostrará variables de entorno importantes de ssh-agent, que el "$() " (también puedes usar "` `" ) captura, y el "eval" evalúa, estableciendo estas variables en tu shell actual.

Estas variables de entorno de ssh-agent también se escriben en ~/.keychain/${HOSTNAME}-sh, para que los inicios de sesión posteriores y los shells no interactivos como los trabajos cron puedan obtener el archivo para acceder al ssh-agent en ejecución y realizar conexiones SSH sin contraseña utilizando las claves privadas almacenadas en caché, incluso cuando no estés presente.

RESUMEN DEL ALGORITMO

Cuando se ejecuta el script keychain, primero intentará encontrar un ssh-agent en ejecución.

Fase 1: pidfile: Para hacer esto, primero buscará un pidfile existente. Si existe uno, se inspeccionará y se utilizará para encontrar un agente en ejecución, en concordancia con las opciones de línea de comandos especificadas. Si este proceso tiene éxito, se encuentra un agente "generado por keychain" y este proceso se completa. De lo contrario, continuamos con el siguiente paso.
Fase 2: entorno: Si el pidfile de keychain no arrojó un agente en ejecución, keychain examina las variables de entorno definidas en el entorno actual. Este paso se omitirá si se especifica la opción --noinherit. Si se encuentra un agente que está en concordancia con las opciones de línea de comandos especificadas, se considera "heredado" por keychain, y el proceso se completa. De lo contrario, continuamos con el siguiente paso.
Fase 3: generación de agente: En ausencia de encontrar un agente generado por keychain o uno existente que pueda ser adoptado, keychain generará un nuevo ssh-agent, o un nuevo gpg-agent si se especifica --ssh-spawn-gpg y gpg-agent está disponible.
Fase Final: actualización del pidfile: Además, los pidfiles se actualizarán para reflejar el agente generado por keychain o el agente "heredado". Un agente "heredado", una vez escrito en el pidfile, se considera ahora "adoptado".
Excepción de actualización del pidfile: Si se especificó la opción --ssh-allow-forwarded, y se encontró un socket SSH reenviado -- que se identifica como un socket SSH válido definido en una variable "SSH_AUTH_SOCK", que no tiene asociado un "SSH_AGENT_PID" válido también definido en el entorno y se determina además que no es el socket de ningún gpg-agent en ejecución -- entonces este agente simplemente se utilizará, pero no se persistirá en ningún pidfile. Esto se debe a que este socket suministrado por SSH desaparecerá cuando termine la conexión SSH subyacente, y por lo tanto no se puede confiar en que esté disponible de forma persistente.

EL CORTO-CIRCUITO RÁPIDO

Cuando se especifica la opción --quick, se ejecutará un algoritmo especial antes del algoritmo principal de detección de agentes que se enumera arriba. Un pidfile, si existe, se evaluará según la Fase 1 del algoritmo principal. Si se encuentra un agente válido en ejecución, se le consultará sobre las claves válidas. Si al menos una clave válida está cargada en el agente, el inicio rápido se considera exitoso, y keychain omitirá el algoritmo regular de inicio de agente, y utilizará este agente encontrado.

RESUMEN Y RAZONAMIENTO

El algoritmo de detección e inicio de ssh-agent de keychain es algo sofisticado por una razón. Hay una intención detrás de su comportamiento.

El algoritmo ha sido diseñado específicamente para preferir un agente generado por keychain, o previamente adoptado, si ese agente está actualmente disponible. Esto es intencional, porque otro software del sistema podría generar procesos ssh-agent y/o gpg-agent, y queremos que keychain no sea forzado a usar estos nuevos agentes que pueden aparecer repentinamente en el entorno de forma inesperada cuando se inician nuevas sesiones de escritorio y en otras circunstancias. Si keychain es demasiado "sugestionable", perderá el rastro del agente que actualmente tiene claves válidas, lo que puede resultar en solicitudes innecesarias de contraseñas y confusión general.

OPCIONES

--absolute
Esta opción se puede usar con la opción --dir, si desea especificar un directorio no predeterminado para almacenar los pidfiles (el valor predeterminado es ~/.keychain). Cuando se usa esta opción, el script no agrega automáticamente /.keychain a la ruta, lo que le permite usar cualquier nombre de directorio arbitrario para almacenar los pidfiles. Tenga en cuenta que Keychain 2.9.3 agrega algunas verificaciones de seguridad adicionales relacionadas con los permisos de directorios y archivos: usted debe tener propiedad exclusiva de cualquier directorio que keychain use para almacenar pidfiles, o keychain se abortará.
--clear
Cuando se especifica, esta opción agrega un paso inicial antes de agregar cualquier clave a los agentes, limpiando todas las claves/contraseñas almacenadas en caché existentes. Esto está destinado a usarse junto con keychain --eval para garantizar que solo se carguen las claves especificadas, y que keychain asuma que usted es un intruso hasta que se demuestre lo contrario y fuerce a todos los inicios de sesión interactivos a especificar contraseñas válidas. Esta opción aumenta la seguridad y aún permite que sus trabajos cron usen sus claves SSH cuando no ha iniciado sesión.
--confallhosts
Además de cualquier clave especificada en la línea de comandos, esta opción le dirá a keychain que busque en ~/.ssh/config todas las claves privadas referenciadas en todas las líneas de "IdentityFile", y cargue todas las claves para todos los hosts.
--confirm
Las claves están sujetas a confirmación interactiva por el programa SSH_ASKPASS antes de ser utilizadas para la autenticación. Ver la opción -c para ssh-add(1).
--debug
Keychain 2.9.0 introduce la opción --debug, que generará información adicional relacionada con cómo Keychain realiza su proceso de selección de agente. Específicamente, mostrará cuándo se rechaza un SSH_AUTH_SOCK porque está siendo proporcionado por gpg-agent -- y esto no está permitido debido a la ausencia de la opción --ssh-allow-gpg, o cuándo se rechaza porque parece provenir de una conexión SSH reenviada, y no se proporcionó --ssh-allow-forwarded.
--dir nombre_directorio
Esta opción le permite usar un directorio diferente a $HOME/.keychain para almacenar los pidfiles. Tenga en cuenta que Keychain 2.9.3 agrega algunas verificaciones de seguridad adicionales relacionadas con los permisos de directorios y archivos: usted debe tener propiedad exclusiva de cualquier directorio que keychain use para almacenar pidfiles, o el script se abortará. Consulte también la opción --absolute.
--env nombre_archivo
Después de analizar las opciones, keychain cargará configuraciones de entorno adicionales desde "nombre_archivo". Por defecto, si no se proporciona "--env", entonces keychain intentará cargar desde ~/.keychain/[nombre_host]-{c}sh o, alternativamente, ~/.keychain/env. El propósito de este archivo es anular configuraciones como PATH, en caso de que ssh se almacene en un lugar no estándar.
--eval
Keychain imprimirá líneas para ser evaluadas en el shell en stdout. Respeta la variable de entorno SHELL para determinar si se espera salida de Bourne shell o C shell.
--extended
Esto habilita el procesamiento de claves de línea de comandos extendido con más funciones, y es un reemplazo para la antigua opción "--confhost". Cuando se especifica, cada clave especificada en la línea de comandos debe tener un prefijo para categorizarla explícitamente. Las claves SSH deben tener un prefijo de "sshk:" seguido inmediatamente por la ruta o el nombre de la clave (la parte después de "sshk:" se procesa igual que una clave SSH sin la opción "--extended"). Las claves GPG deben estar en el formato "gpgk:" seguido inmediatamente por la huella digital de 8 o 16 caracteres. Si se especifica "host:<nombre_host>", entonces Keychain extraerá la configuración SSH para el nombre de host especificado, obtendrá todas las opciones de identityfile (claves privadas) especificadas, y estas claves se incluirán en el conjunto de claves a cargar por keychain. Esto permite especificar juntas múltiples claves de múltiples tipos, incluidas claves SSH por host, lo que no era posible con "--confhost".
--gpg2
Esta opción cambia las llamadas predeterminadas a gpg para usar gpg2 en su lugar para admitir distribuciones como Ubuntu que tienen tanto gpg como gpg2.
-h --help
Muestra ayuda que se parece notablemente a esta página de manual. A partir de la versión 2.6.10, la ayuda se envía a stdout para que pueda ser fácilmente canalizada a un paginador.
--host nombre
Establece un nombre de host alternativo para la creación de pidfiles.
--ignore-missing
No advertir si algunas claves en la línea de comandos no se encuentran. Esto es útil para situaciones en las que tiene un .bash_profile compartido, pero sus claves pueden no estar disponibles en todas las máquinas donde se ejecuta keychain.
-l --list
Lista las firmas de todas las claves SSH activas y sale, similar a "ssh-add -l".
-L --list-fp
Lista las huellas digitales de todas las claves SSH activas y sale, similar a "ssh-add -L".
--lockwait segundos
Cuánto tiempo esperar a que el bloqueo esté disponible. Predeterminado a 5 segundos. Especifique un valor de cero o más. Si el bloqueo no se puede adquirir dentro del número especificado de segundos, entonces este proceso de keychain adquirirá forzosamente el bloqueo.
--noask
Esta opción le dice a keychain que haga todo lo que normalmente hace (asegurarse de que ssh-agent esté en ejecución, configurar los archivos ~/.keychain/[nombre_host]-{c}sh) excepto que no le pedirá que agregue ninguna de las claves que especificó si aún no se han agregado a ssh-agent.
--nocolor
Deshabilita el resaltado de color para terminales no compatibles con ANSI.
