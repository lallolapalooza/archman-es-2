NOMBRE

kadm5.acl - archivo ACL de Kerberos

DESCRIPCIÓN

El demonio kadmind(8) de Kerberos utiliza un archivo de Lista de Control de Acceso (ACL) para gestionar los derechos de acceso a la base de datos de Kerberos. Para las operaciones que afectan a los principales, el archivo ACL también controla qué principales pueden operar sobre qué otros principales.

La ubicación predeterminada del archivo ACL de Kerberos es /var/lib/krb5kdc/kadm5.acl, a menos que se anule mediante la variable acl_file en kdc.conf(5).

SINTAXIS

Las líneas vacías y las líneas que comienzan con el signo de almohadilla (#) se ignoran. Las líneas que contienen entradas ACL tienen el formato:

principal  permisos  [principal_objetivo  [restricciones] ]

NOTA:

El orden de las líneas en el archivo ACL es importante. La primera entrada coincidente controlará el acceso de un principal actor sobre un principal objetivo.
principal
(Nombre de principal de Kerberos parcial o completamente calificado.) Especifica el principal cuyos permisos se establecerán.

Cada componente del nombre puede ser comodín utilizando el carácter *.

permisos
Especifica qué operaciones pueden o no realizarse por un principal que coincida con una entrada determinada. Esta es una cadena de uno o más de los siguientes caracteres de la lista o sus contrapartes en mayúsculas. Si el carácter está en mayúsculas, la operación está prohibida. Si el carácter está en minúsculas, la operación está permitida.
a [Pro]híbe la adición de principales o políticas
c [Pro]híbe el cambio de contraseñas para los principales
d [Pro]híbe la eliminación de principales o políticas
e [Pro]híbe la extracción de claves de principal
i [Pro]híbe las consultas sobre principales o políticas
l [Pro]híbe la lista de todos los principales o políticas
m [Pro]híbe la modificación de principales o políticas
p [Pro]híbe la propagación de la base de datos de principales (utilizado en incr_db_prop)
s [Pro]híbe el establecimiento explícito de la clave para un principal
x Abreviatura de admcilsp. Todos los privilegios (excepto e)
* Igual que x.

NOTA:

El privilegio de extracción no está incluido en el privilegio comodín; debe asignarse explícitamente. Este privilegio permite al usuario extraer claves de la base de datos y debe manejarse con gran cuidado para evitar la divulgación de claves importantes como las de los principales kadmin/* o krbtgt/*. El atributo de principal lockdown_keys se puede usar para evitar la extracción de claves de principales específicos independientemente del privilegio otorgado.
principal_objetivo
(Opcional. Nombre de principal de Kerberos parcial o completamente calificado.) Especifica el principal sobre el cual se pueden aplicar los permisos. Cada componente del nombre puede ser comodín utilizando el carácter *.

principal_objetivo también puede incluir retroreferencias a principal, en las cuales *número coincide con el comodín correspondiente en principal.

restricciones
(Opcional) Una cadena de indicadores. Las restricciones permitidas son:
{+|-}nombre_indicador
el indicador se fuerza al valor indicado. Los indicadores permitidos son los mismos que los de la variable default_principal_flags en kdc.conf(5).
-clearpolicy
la política se fuerza a estar vacía.
-policy pol
la política se fuerza a ser pol.
-{expire, pwexpire, maxlife, maxrenewlife} tiempo
(cadena getdate) el valor asociado se forzará a ser MIN(tiempo, valor solicitado).

Los indicadores anteriores actúan como restricciones en cualquier operación de adición o modificación que esté permitida debido a esa línea ACL.

ADVERTENCIA:

Si se modifica el archivo ACL de kadmind, el demonio kadmind necesita ser reiniciado para que los cambios surtan efecto.

EJEMPLO

Aquí hay un ejemplo de un archivo kadm5.acl:

*/admin@ATHENA.MIT.EDU    *                               # línea 1
joeadmin@ATHENA.MIT.EDU   ADMCIL                          # línea 2
joeadmin/*@ATHENA.MIT.EDU i   */root@ATHENA.MIT.EDU       # línea 3
*/root@ATHENA.MIT.EDU     ci  *1@ATHENA.MIT.EDU           # línea 4
*/root@ATHENA.MIT.EDU     l   *                           # línea 5
sms@ATHENA.MIT.EDU        x   * -maxlife 9h -postdateable # línea 6

(línea 1) Cualquier principal en el dominio ATHENA.MIT.EDU con una instancia admin tiene todos los privilegios administrativos excepto la extracción de claves.

(líneas 1-3) El usuario joeadmin tiene todos los permisos excepto la extracción de claves con su instancia admin, joeadmin/admin@ATHENA.MIT.EDU (coincide con la línea 1). No tiene ningún permiso en absoluto con su instancia nula, joeadmin@ATHENA.MIT.EDU (coincide con la línea 2). Sus instancias root y otras no admin, no nulas (por ejemplo, extra o dbadmin) tienen permisos de consulta sobre cualquier principal que tenga la instancia root (coincide con la línea 3).

(línea 4) Cualquier principal root en ATHENA.MIT.EDU puede consultar o cambiar la contraseña de su instancia nula, pero no de ninguna otra instancia nula. (Aquí, *1 denota una retroreferencia al componente que coincide con el primer comodín en el principal actor).

(línea 5) Cualquier principal root en ATHENA.MIT.EDU puede generar la lista de principales en la base de datos y la lista de políticas en la base de datos. Esta línea está separada de la línea 4, ya que el permiso de lista solo se puede otorgar globalmente, no a principales objetivos específicos.

(línea 6) Finalmente, el principal del Sistema de Gestión de Servicios sms@ATHENA.MIT.EDU tiene todos los permisos excepto la extracción de claves, pero cualquier principal que cree o modifique no podrá obtener tickets postdateables o tickets con una vida útil superior a 9 horas.

COMPORTAMIENTO DEL MÓDULO

El ACL de kadmind

kadm5.acl(5)

NAME

kadm5.acl - Kerberos 5 administration daemon ACL file format

DESCRIPTION

The Kerberos 5 administration daemon, kadmind, can optionally use an Access Control List (ACL) file to control which principals are allowed to perform administrative operations on principals and policies in the Kerberos realm.

The ACL file is a text file that contains a series of entries, each on a single line. Each entry specifies a principal or a glob pattern for principals and the operations they are allowed to perform.

The ACL file is processed in order from top to bottom. The first matching entry for a principal determines the allowed operations. If no entry matches, the principal is denied all operations.

SYNTAX

Each line in the ACL file has the following format:

principal_expression    privileges

principal_expression
This can be a full Kerberos principal name (e.g., user/admin@REALM), a glob pattern (e.g., */admin@REALM), or the special keyword * to match any principal.
privileges
A space-separated list of privileges granted to the principal. The following privileges are recognized:
a
Allow principal to administrate other principals.
c
Allow principal to change passwords.
i
Allow principal to list principals.
p
Allow principal to purge principals.
l
Allow principal to look up principals.
m
Allow principal to modify principals.
s
Allow principal to select principals.
x
Allow principal to delete principals.
R
Allow principal to rename principals.
K
Allow principal to load keys.
A
Allow principal to administrate policies.
C
Allow principal to change policy passwords.
I
Allow principal to list policies.
M
Allow principal to modify policies.
S
Allow principal to select policies.
X
Allow principal to delete policies.

Comments can be added to lines by starting the comment with a # character. Lines starting with # are ignored.

EXAMPLE

The following is an example kadm5.acl file:

# Allow the user 'admin/admin' to perform all administrative operations
*/admin@REALM        a c i p l m s x R K A C I M S X

# Allow any user in the 'sysadmin' group to change passwords and list principals
sysadmin/*@REALM     c i

# Allow the principal 'service/server@REALM' to list principals
service/server@REALM i

MODULE BEHAVIOR

The ACL file module can coexist with other authorization modules in release 1.16 and later, as configured in the kadm5_auth section of krb5.conf(5). The ACL file will positively authorize operations according to the rules above, but will never authoritatively deny an operation, so other modules can authorize operations in addition to those authorized by the ACL file.

To operate without an ACL file, set the acl_file variable in kdc.conf(5) to the empty string with acl_file = "".
