NOMBRE

kubeadm join - Ejecutar esto en cualquier máquina que desee unirse a un clúster existente

SINOPSIS

kubeadm join [OPCIONES]

DESCRIPCIÓN

Al unirse a un clúster inicializado con kubeadm, necesitamos establecer confianza bidireccional. Esto se divide en descubrimiento (para que el Nodo confíe en el Plano de Control de Kubernetes) y arranque TLS (para que el Plano de Control de Kubernetes confíe en el Nodo).

Hay 2 esquemas principales para el descubrimiento. El primero es usar un token compartido junto con la dirección IP del servidor de API. El segundo es proporcionar un archivo: un subconjunto del archivo kubeconfig estándar. El archivo de descubrimiento/kubeconfig admite token, plugins de autenticación de cliente-go ("exec"), "tokenFile" y "authProvider". Este archivo puede ser un archivo local o descargarse a través de una URL HTTPS. Las formas son kubeadm join --discovery-token abcdef.1234567890abcdef 1.2.3.4:6443, kubeadm join --discovery-file ruta/a/archivo.conf, o kubeadm join --discovery-file https://url/file.conf. Solo se puede usar una forma. Si la información de descubrimiento se carga desde una URL, se debe usar HTTPS. Además, en ese caso se utiliza el paquete de CA instalado en el host para verificar la conexión.

Si utiliza un token compartido para el descubrimiento, también debe pasar el flag --discovery-token-ca-cert-hash para validar la clave pública de la autoridad raíz de certificados (CA) presentada por el Plano de Control de Kubernetes. El valor de este flag se especifica como ":", donde el tipo de hash admitido es "sha256". El hash se calcula sobre los bytes del objeto Subject Public Key Info (SPKI) (como en RFC7469). Este valor está disponible en la salida de "kubeadm init" o puede calcularse utilizando herramientas estándar. El flag --discovery-token-ca-cert-hash puede repetirse varias veces para permitir más de una clave pública.

Si no conoce el hash de la clave pública de la CA de antemano, puede pasar el flag --discovery-token-unsafe-skip-ca-verification para deshabilitar esta verificación. Esto debilita el modelo de seguridad de kubeadm ya que otros nodos pueden suplantar potencialmente al Plano de Control de Kubernetes.

El mecanismo de arranque TLS también se impulsa a través de un token compartido. Se utiliza para autenticarse temporalmente con el Plano de Control de Kubernetes para enviar una solicitud de firma de certificado (CSR) para un par de claves creado localmente. Por defecto, kubeadm configurará el Plano de Control de Kubernetes para aprobar automáticamente estas solicitudes de firma. Este token se pasa con el flag --tls-bootstrap-token abcdef.1234567890abcdef.

A menudo, el mismo token se usa para ambas partes. En este caso, se puede usar el flag --token en lugar de especificar cada token individualmente.

El comando "join [api-server-endpoint]" ejecuta las siguientes fases:

preflight              Ejecutar comprobaciones previas al arranque de join
control-plane-prepare  Preparar la máquina para servir un plano de control
  /download-certs        Descargar certificados compartidos entre nodos del plano de control desde el Secret de kubeadm-certs
  /certs                 Generar los certificados para los nuevos componentes del plano de control
  /kubeconfig            Generar el kubeconfig para los nuevos componentes del plano de control
  /control-plane         Generar los manifiestos para los nuevos componentes del plano de control
kubelet-start          Escribir la configuración de kubelet, certificados y (re)iniciar el kubelet
control-plane-join     Unir una máquina como instancia de plano de control
  /etcd                  Agregar un nuevo miembro local de etcd
  /mark-control-plane    Marcar un nodo como plano de control
wait-control-plane     Esperar a que se inicie el plano de control

OPCIONES

--apiserver-advertise-address="" Si el nodo debe alojar una nueva instancia de plano de control, la dirección IP que el Servidor de API anunciará que está escuchando. Si no se establece, se utilizará la interfaz de red predeterminada.

--apiserver-bind-port=6443 Si el nodo debe alojar una nueva instancia de plano de control, el puerto al que se enlazará el Servidor de API.

--certificate-key="" Use esta clave para descifrar los secretos de certificados cargados por init. La clave de certificado es una cadena codificada en hexadecimal que es una clave AES de 32 bytes.

--config="" Ruta a un archivo de configuración de kubeadm.

--control-plane=false Crear una nueva instancia de plano de control en este nodo

--cri-socket="" Ruta al socket CRI para conectar. Si está vacío, kubeadm intentará autodetectar este valor; use esta opción solo si tiene más de un CRI instalado o si tiene un socket CRI no estándar.

--discovery-file="" Para el descubrimiento basado en archivos, un archivo o URL desde el cual cargar la información del clúster.

--discovery-token="" Para el descubrimiento basado en tokens, el token utilizado para validar la información del clúster obtenida del servidor de API.

--discovery-token-ca-cert-hash=[] Para el descubrimiento basado en tokens, validar que la clave pública raíz de la CA coincide con este hash (formato: ":").

--discovery-token-unsafe-skip-ca-verification=false Para el descubrimiento basado en tokens, permitir unirse sin la fijación de --discovery-token-ca-cert-hash.

--dry-run=false No aplicar ningún cambio; solo mostrar lo que se haría.

--ignore-preflight-errors=[] Una lista de comprobaciones cuyos errores se mostrarán como advertencias. Ejemplo: 'IsPrivilegedUser,Swap'. El valor 'all' ignora los errores de todas las comprobaciones.

--node-name="" Especificar el nombre del nodo.

--patches="" Ruta a un directorio que contiene archivos llamados "target[suffix][+patchtype].extension". Por ejemplo, "kube-apiserver0+merge.yaml" o simplemente "etcd.json". "target" puede ser uno de "kube-apiserver", "kube-controller-manager", "kube-scheduler", "etcd", "kubeletconfiguration", "corednsdeployment". "patchtype" puede ser uno de "strategic", "merge" o "json" y coinciden con los formatos de parche compatibles con kubectl. El "patchtype" predeterminado es "strategic". "extension" debe ser "json" o "yaml". "suffix" es una cadena opcional que se puede utilizar para determinar qué parches se aplican primero alfanuméricamente.

--skip-phases=[] Lista de fases a omitir

--tls-bootstrap-token="" Especificar el token utilizado para autenticarse temporalmente con el Plano de Control de Kubernetes mientras se une el nodo.

--token="" Usar este token tanto para discovery-token como para tls-bootstrap-token cuando esos valores no se proporcionan.

OPCIONES HEREDADAS DE COMANDOS PADRE

--rootfs="" La ruta al sistema de archivos raíz del host 'real'. Esto hará que kubeadm haga chroot a la ruta proporcionada.

--version=false --version, --version=raw imprime información de versión y sale; --version=vX.Y.Z... establece la versión informada
