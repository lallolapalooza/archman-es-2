NOMBRE

keepalived.conf - archivo de configuración para Keepalived

Nota:

Esta documentación DEBE considerarse la fuente de información DEFINITIVA para configurar Keepalived. Esta documentación es compatible y mantenida por el Equipo Central de Keepalived.

DESCRIPCIÓN

keepalived.conf es el archivo de configuración que describe todas las palabras clave de Keepalived. Las palabras clave se colocan en jerarquías de bloques y subbloques, cada capa delimitada por pares de '{' y '}'.

Los comentarios comienzan con '#' o '!' hasta el final de la línea y pueden comenzar en cualquier parte de una línea.

La palabra clave 'include' y sus variantes permiten la inclusión de otros archivos de configuración desde el archivo de configuración principal, o desde archivos incluidos posteriormente.

El formato de la directiva include es:

include NOMBRE_ARCHIVO

NOMBRE_ARCHIVO puede ser una ruta completa o relativa, y puede incluir comodines, incluidas expresiones de llaves al estilo csh como "{foo/{,cat,dog},bar}" si glob() las soporta.

Después de abrir un archivo incluido, el directorio actual se establece en el directorio del propio archivo, por lo que cualquier ruta relativa incluida desde un archivo es relativa al directorio del propio archivo que lo incluye.

Las variantes de include agregan verificaciones de inclusión adicionales al nivel actual de include_check (ver abajo). Las variantes son:


includer NOMBRE_ARCHIVO - igual que include_check readable
includem NOMBRE_ARCHIVO - igual que include_check match
includew NOMBRE_ARCHIVO - igual que include_check wildcard_match
includeb NOMBRE_ARCHIVO - igual que include_check brace_match
includea NOMBRE_ARCHIVO - todas las verificaciones de include_check

NOTA: Si la función glob() de libc no soporta GLOB_ALTDIRFUNC (por ejemplo, Musl libc como en Alpine Linux, etc.), entonces solo includea, includer y includew de las opciones anteriores funcionarán.

¿Por qué queremos permitir errores? Supongamos que una configuración tiene archivos opcionales en /etc/keepalived/conf.d, entonces se podría especificar include_/etc/keepalived/conf.d/*, pero no debería generar un error si no hay archivos en el directorio; en este caso, se debe usar includer. De lo contrario, es sensato usar includea.

El manejo de 'include' no funcionará si la línea 'include' utiliza configuración condicional o sustitución de parámetros, ya que la detección de las palabras clave 'include' se realiza antes del procesamiento de la configuración condicional y la sustitución de parámetros.

La palabra clave básica include se conserva por compatibilidad con versiones anteriores, ya que no produce errores de configuración si los archivos no se pudieron abrir, etc.

SINTAXIS DE PARÁMETROS

<BOOL> es uno de on|off|true|false|yes|no
<TIMER> es un valor de tiempo en segundos, incluidos segundos fraccionarios, por ejemplo, 2.71828 o 3; la resolución del temporizador es de microsegundos.

SCRIPTS

Hay tres clases de scripts que se pueden configurar para ser ejecutados.

(a) Scripts de notificación que se ejecutan cuando una instancia de vrrp o un grupo de vrrp cambian de estado, o cuando un quórum de servidor virtual cambia entre activo y no activo.

(b) Scripts de seguimiento de vrrp que harán que las instancias de vrrp se caigan si salen con un estado de salida distinto de cero, o si se especifica un peso, sumarán o restarán el peso a la prioridad de esa instancia de vrrp.

(c) Scripts varios de verificación LVS que harán que un servidor real se configure como inactivo si salen con un estado distinto de cero.

Por defecto, los scripts serán ejecutados por el usuario keepalived_script si ese usuario existe, o si no, por root, pero para cada script se puede especificar el usuario/grupo bajo el cual se ejecutará.

Existen implicaciones de seguridad significativas si los scripts se ejecutan con privilegios de root, especialmente si los scripts son modificables o reemplazables por un usuario que no sea root. En consecuencia, se realizan comprobaciones de seguridad al inicio para garantizar que, si un script es ejecutado por root, no pueda ser modificado o reemplazado por un usuario que no sea root.

Todos los scripts deben escribirse de manera que terminen al recibir una señal SIGTERM. Los scripts recibirán SIGTERM si su proceso padre termina, o si es un script cuya salida keepalived está esperando y ha tardado demasiado en ejecutarse.

Cadenas entre comillas

Las cadenas entre comillas se especifican entre caracteres " o ' y las cadenas se delimitan por espacios en blanco. En los ejemplos siguientes, los caracteres ´ no forman parte de las cadenas y no deben especificarse:

´abcd" efg h jkl "mnop´
será la única cadena: 
´abcd efg h jkl mnop´
mientras que:

´abcd "efg h jkl" mnop´

serán las tres cadenas:

´abcd´, ´efg h jkl´ y ´mnop´
es decir, los caracteres " y ' se eliminan y se conserva cualquier espacio en blanco intermedio.
Las cadenas entre comillas también pueden tener caracteres de escape, como en el shell. \a, \b, \E, \f,
\n, \r, \t, \v, \nnn y \xXX (donde nnn son hasta 3 dígitos octales y XX son hasta dos dígitos hex) y \cC (que produce la versión de control del carácter C) son
todos compatibles. \C para cualquier otro carácter C se trata simplemente como una versión escapada de
el carácter C, por lo que \\ es un carácter \ y \" será un carácter ", pero no iniciará ni terminará una cadena entre comillas.
Para especificar scripts con parámetros, los espacios sin comillas separarán los parámetros.
Si se requiere que un parámetro contenga un espacio, debe estar entre comillas simples ('). Por ejemplo

$SG_NAME=SG1
$INST=low
$USER=user
notify_master "/etc/keepalived/notify_event.sh ' espacios\\x20f\x69le ' '\"s p a c e \"' ${SG_NAME}.$INST master" $USER group

especifica un script notify_master /etc/keepalived/notify_event.sh que se ejecutará como usuario:grupo con los parámetros

´ espacios\x20fichero ´, ´"e s p a c i o "´, ´SG1.low´ y ´master´

ANALIZADOR DE CONFIGURACIÓN

Tradicionalmente, el analizador del archivo de configuración no ha sido uno de los puntos fuertes de keepalived. Se han realizado muchos esfuerzos para corregir esto, incluso si no es el objetivo principal del proyecto.

El archivo de configuración de Keepalived se articula en torno a un conjunto de bloques de configuración. Cada bloque se centra y apunta a una característica específica de la familia de demonios. Estas características son:

CONFIGURACIÓN GLOBAL

CONFIGURACIÓN DE BFD

CONFIGURACIÓN DE VRRPD

CONFIGURACIÓN DE LVS

To avoid having to frequently run a track_script to monitor the existance of processes (often haproxy or nginx), vrrp_track_process can monitor whether other processes are running.

One difference from pgrep is track_process doesn't do a regular expression match of the command string, but does an exact match. 'pgrep ssh' will match an sshd process, this track_process will not (it is equivalent to pgrep "^ssh$").

If full_command is used (equivalent to pgrep -f), /proc/PID/cmdline is used, but any updates to cmdline will not be detected (a process shouldn't normally change it, although it is possible with great care, for example systemd).

Prior to Linux v3.2 track_process will not support detection of changes to a process name, since the kernel did not notify changes of process name prior to 3.2. Most processes do not change their process name, but, for example, firefox forks processes that change their process name to "Web Content". The process name referred to here is the contents of /proc/PID/comm.

Quorum is the number of matching processes that must be run for an OK status.

Delay might be useful if it anticipated that a process may be reloaded (stopped and restarted), and it isn't desired to down and up a vrrp instance.

A positive weight means that an OK status will add <weight> to the priority of all VRRP instances which monitor it. On the opposite, a negative weight will be subtracted from the initial priority in case of insufficient processes.

If the vrrp instance or sync group is not the address owner and the result is between -253 and 253, the result will be added to the initial priority of the VRRP instance (a negative value will reduce the priority), although the effective priority will be limited to the range [1,254].

If a vrrp instance using a track_process is a member of a sync group, unless sync_group_tracking_weight is set on the group weight 0 must be set. Likewise, if the vrrp instance is the address owner, weight 0 must also be set.

Rational for not using pgrep/pidof/killall and the likes:

Every time pgrep or its equivalent is run, it iterates though the /proc/[1-9][0-9]* directories, and opens the status and cmdline pseudo files in each directory. The cmdline pseudo file is mapped to the process's address space, and so if that part of the process is swapped out, it will have to be fetched from the swap space. pgrep etc also include zombie processes whereas keepalived does not, since they aren't running.

This implementation only iterates though /proc/[1-9][0-9]*/ directories at start up, and it won't even read the cmdline pseudo files if 'full_command' is not specified for any of the vrrp_track_process entries. After startup, it uses the process_events kernel <-> userspace connector to receive notification of process changes. If full_command is specified for any track_process instance, the cmdline pseudo file will have to be read upon notification of the creation of the new process, but at that time it is very unlikely that it will have already been swapped out.

On a busy system with a high number of process creations/terminations, using a track_script with pgrep/pidof/killall may be more efficient, although those processes are inefficient compared to the minimum that keepalived needs.

Using pgrep etc on a system that is swapping can have a significant detrimental impact on the performance of the system, due to having to fetch swapped memory from the swap space, thereby causing additional swapping.

bloque.

Si los valores globales vrrp_garp_interval y/o vrrp_gna_interval están configurados, cualquier interfaz que no esté especificada en un garp_group heredará la configuración global de forma individual por

interfaz. 
La sintaxis para garp_group es:
garp_group {
    # Establece el intervalo entre ARP gratuitos (en segundos, resolución en microsegundos)
    garp_interval <DECIMAL>
    # Establece el intervalo por defecto entre NA no solicitados (en segundos, resolución en microsegundos)
    gna_interval <DECIMAL>
    # La interfaz física a la que se aplican los intervalos
    interface <STRING>
    # Una lista de interfaces sobre las que se agregan los retardos.
    interfaces {
        <STRING>
        <STRING>
        ...
    }
}

Instancia(s)

VRRP

Una Instancia VRRP es la característica clave del protocolo VRRP. Define y configura el comportamiento de VRRP para ejecutarse en una interfaz específica. Cada Instancia VRRP está relacionada con una interfaz

única. 
La sintaxis para vrrp_instance es:
vrrp_instance <STRING> {
    # Estado inicial, MASTER|BACKUP
    # Si la prioridad es 255, la instancia hará la transición inmediatamente
    # a MASTER si se especifica el estado MASTER; de lo contrario, la instancia
    # esperará entre 3 y 4 intervalos de anuncio antes de poder hacer la transición,
    # dependiendo de la prioridad.
    state MASTER
    # interfaz para inside_network, vinculada por vrrp.
    # Nota: si se usa unicast, la interfaz puede omitirse siempre que
    #   las direcciones unicast no sean direcciones link-local de IPv6 (esto es
    #   necesario, por ejemplo, si se usa enrutamiento asimétrico).
    #   Si se omite la interfaz, todas las VIP y eVIP deben especificar
    #   la interfaz en la que se configurarán, de lo contrario se añadirán
    #   a la interfaz por defecto.
    interface eth0
    # Si se usa unicast sin especificar una interfaz, se puede especificar el VRF en
    # el que operar.
    vrf  VRF_IF
    # Usar MAC virtual de VRRP (macvlan).
    # El macvlan se creará en la interfaz configurada para
    # la instancia VRRP, y las VIP y eVIP de la familia de direcciones
    # coincidente que no especifiquen una interfaz diferente se configurarán
    # en el macvlan.
    # Los anuncios VRRP también se enviarán y recibirán en la interfaz
    # macvlan, a menos que se configure vmac_xmit_base.
    # NOTA: Si sysctl net.ipv4.conf.all.rp_filter está configurado,
    # y esta vrrp_instance es una instancia IPv4, usar
    # esta opción hará que las interfaces individuales se
    # actualicen al mayor de su configuración actual y
    # all.rp_filter, al igual que default.rp_filter, y all.rp_filter
    # se establecerá en 0.
    # La configuración original se restaura al terminar.
    # NOTA 2: Si se usa use_vmac con pares unicast,
    # vmac_xmit_base debe establecerse.
    # La dirección MAC se puede especificar con solo 5 octetos, en cuyo caso
    # se usará el virtual_router_id como último octeto.
    # Si se especifica netlink_notify_msg, cuando keepalived crea una interfaz macvlan
    # forzará el envío de un mensaje netlink para la interfaz base
    # ya que el kernel no envía uno, incluso si la promiscuidad de la interfaz base
    # ha sido actualizada.
    # Por defecto, la VMAC se crea en el mismo grupo de enlace que la interfaz padre.
    # Especificar group GROUP_ID (donde GROUP_ID es un número de grupo válido, o un
    # nombre en /etc/iproute2/group) creará la interfaz en el grupo especificado.
    # Se puede especificar la opción name si desea usar un nombre de interfaz "group".
    use_vmac [[nombre] <VMAC_INTERFACE_NAME>] [MAC_ADDRESS] [netlink_notify_msg] [group GROUP_ID]
    # use_vmac_addr se usa para crear interfaces VMAC (macvlan) para
    # cada interfaz que es usada por un VIP o eVIP donde la interfaz
    # no es la misma que la interfaz en la que está configurada la instancia
    # VRRP o la familia de direcciones del eVIP no coincide con la de la
    # instancia VRRP. Alternativamente, se puede especificar use_vmac contra cada
    # VIP/eVIP que especifique una interfaz (dev).
    # NOTA: si se especifica use_vmac y un eVIP no es de la misma familia de
    # direcciones que la instancia vrrp, a menos que se especifique use_vmac_addr, o
    # se especifique use_vmac para el eVIP, el eVIP se configurará en
    # la VMAC de la instancia vrrp, que tendrá la dirección MAC incorrecta para
    # la familia de direcciones del eVIP.
    use_vmac_addr
    # Enviar/Recibir mensajes VRRP desde la interfaz base en lugar de
    # la interfaz VMAC
    vmac_xmit_base
    # Usar interfaz IPVLAN. keepalived creará una interfaz ipvlan en modo L2
    # sobre la interfaz especificada.
    # Para instancias IPv4, se requiere una dirección IP, para IPv6
    # la dirección es opcional, en cuyo caso se usará la dirección
    # de enlace local.
    # Los indicadores de modo tienen como valor predeterminado bridge. NOTA: los indicadores de modo deben ser los
    # mismos para todos los ipvlans en la misma interfaz subyacente.
    # Es más seguro configurar un nombre de interfaz, en caso de que keepalived se cierre
    # y se reinicie, en cuyo caso podrá encontrar de forma más fiable una interfaz creada
    # previamente.
    # Se puede especificar la opción name si desea usar un nombre que causaría
    # un error de análisis (p. ej. "bridge").
    # Para una descripción de la opción group, consulte use_vmac.
    use_ipvlan [[nombre] <INTERFACE_NAME>] [IP_ADDRESS] [bridge|private|vepa] [group GROUP_ID]
    # forzar a la instancia a usar IPv6 (esta opción está obsoleta desde que
    # las direcciones IP virtuales determinan si se usa IPv4 o IPv6).
    native_ipv6
    # Ignorar fallos de la interfaz VRRP (predeterminado sin configurar).
    # Nota: al usar IPv6, poner la interfaz administrativamente inactiva, p. ej.
    #   'ip link set IF down' hará que por defecto todas las direcciones IPv6 sean
    #   eliminadas de la interfaz, y en consecuencia la instancia VRRP irá
    #   al estado de fallo debido a la eliminación de las direcciones. Establecer sysctl
    #   net.ipv6.conf.IF.keep_addr_on_down a 1 permitirá que las direcciones que no son de enlace local
    #   permanezcan cuando la interfaz esté inactiva.
    dont_track_primary
    # opcional, monitorizar también estas.
    # ir al estado FAULT si alguna de estas se cae si no está ponderada.
    # Cuando se especifica un peso en track_interface, en lugar de poner la instancia vrrp
    # en el estado FAULT en caso de fallo, su prioridad se
    # incrementará por el peso cuando la interfaz esté activa (para pesos positivos),
    # o se decrementará por el valor absoluto del peso cuando la interfaz esté inactiva
    # (para pesos negativos), a menos que se especifique reverse, en cuyo caso la
    # dirección de ajuste de la prioridad se invierte.
    # El peso debe estar comprendido entre -253 y +253 inclusive.
    # 0 es el comportamiento predeterminado, lo que significa que un fallo implica un
    # estado FAULT. La práctica común es usar pesos positivos para contar un
    # número limitado de servicios buenos de modo que el servidor con el mayor recuento
    # se convierta en maestro. Los pesos negativos son mejores para contar fallos inesperados
    # entre un gran número de interfaces, ya que no se saturará incluso con un gran
    # número de interfaces. Use reverse para aumentar la prioridad si una interfaz está inactiva
    track_interface {
        eth0
        eth1
        eth2 weight <-253..253> [reverse]
         ...
    }
    # añadir un script de seguimiento a la interfaz
    # (<SCRIPT_NAME> es el nombre de la entrada vrrp_script)
    # El mismo principio que track_interface se puede aplicar a las entradas track_script,
    # excepto que un peso no especificado significa que se usará el peso predeterminado declarado en
    # el script (que a su vez tiene 0 como valor predeterminado).
    # reverse causa que la dirección de ajuste de la prioridad se invierta.
    track_script {
        <SCRIPT_NAME>
        <SCRIPT_NAME> weight <-253..253> [reverse|noreverse]
    }
    # Archivos cuyo estado monitorizamos, el valor se añade a la prioridad efectiva.
    # <STRING> es el nombre de un track_file
    track_file {
        <STRING>
        <STRING>
        <STRING> weight <-254..254> [reverse|noreverse]
        ...
    }
    # Los pesos positivos se añaden/restan cuando el proceso está en ejecución,
    # los pesos negativos se restan/añaden cuando no está en ejecución.
    # Si se especifica reverse, la suma/resta se invierte.
    # <STRING> es el nombre de un vrrp_track_process
    # weight tiene como valor predeterminado el peso configurado en vrrp_track_process
    track_process {
        <STRING>
        <STRING> weight <-254..254> [reverse|noreverse]
        ...
    }
    # Instancias BFD que monitorizamos, el valor se añade a la prioridad efectiva,
    # a menos que se especifique reverse, en cuyo caso el valor se resta.
    # Los pesos positivos se suman/restan cuando la instancia bfd está activa,
    # los pesos negativos se restan/añaden cuando la instancia bfd está inactiva.
    # <STRING> es el nombre de una instancia BFD
    track_bfd {
        <STRING>
        <STRING>
        <STRING> weight <INTEGER: -253..253> [reverse|noreverse]
        ...
    }
    # La IP predeterminada para vincular vrrpd es la IP principal
    # de la interfaz. Si desea ocultar la ubicación de vrrpd,
    # use esta IP como src_addr para paquetes vrrp multicast o unicast.
    # (ya que es multicast, vrrpd recibirá el paquete de respuesta
    # sin importar qué src_addr se use).
    # opcional
    mcast_src_ip <IPADDR>
    unicast_src_ip <IPADDR>
    # especificar una dirección multicast alternativa a usar como destino
    # de los anuncios VRRP y para escuchar anuncios. Tenga en cuenta, si está usando
    # múltiples instancias VRRP con VMACs y diferentes direcciones multicast
    # y el mismo VRID, tendrá que especificar direcciones MAC alternativas
    # para al menos todas las VMACs excepto una.
    # Las direcciones multicast IPv6 deben ser de enlace local, es decir, comenzar con ffX2:
    # Usar diferentes direcciones multicast con IPv6 en la misma interfaz sin
    # usar VMACs solo es compatible si el kernel soporta IPV6_MULTICAST_ALL
    # (desde Linux v4.20).
    mcast_dst_ip <MULTICAST_IPADDR>
    # si la src_ip configurada no existe o se elimina, poner la
    # instancia en estado de fallo
    track_src_ip
    # Versión VRRP a ejecutar en la interfaz
    #  el valor predeterminado es el parámetro global vrrp_version, pero las instancias IPv6 siempre
    #  usarán la versión 3.
    version <2 or 3>
    # Lo siguiente habilita la comprobación de que cuando está en modo unicast,
    # la dirección de origen de un paquete VRRP sea una de nuestros pares unicast.
    check_unicast_src
    # No enviar anuncios VRRP a través de un grupo multicast VRRP.
    # En su lugar, envía anuncios a la siguiente lista de
    # direcciones IP usando unicast. Puede ser interesante usar
    # la FSM VRRP y sus características en un entorno de red
    # donde no se soporta multicast.
    # Las direcciones IP especificadas pueden ser IPv4 así como IPv6.
    # Si se especifican min_ttl y/o max_ttl, el TTL/límite de salto
    # de cualquier paquete recibido se comprueba contra el rango de TTL
    # especificado, y se descarta si está fuera del rango.
    # Especificar min_ttl o max_ttl activa check_unicast_src.
    unicast_peer {
        <IPADDR> [min_ttl {0..255}] [max_ttl {0..255}]
        ...
    }
    # No es posible operar en modo unicast sin ningún par.
    # Hasta v2.2.4, keepalived operaría silenciosamente en modo multicast
    # si no se especificaban pares pero se había especificado una palabra clave unicast.
    # Usar esta palabra clave evita que se use multicast por defecto si no se especifican
    # pares y pone la instancia VRRP en estado de fallo.
    unicast_fault_no_peer
    # Especificar el TTL/HLIM unicast para enviar anuncios unicast
    unicast_ttl {0..255}
    # El cálculo de la suma de comprobación al usar VRRPv3 cambió después de v1.3.6.
    #  La razón del cambio es que keepalived estaba calculando la
    #  suma de comprobación usando la dirección multicast incluso cuando usaba
    #  unicast, mientras que la suma de comprobación debería calcularse usando la
    #  dirección real que está en el encabezado IPv4.
    #  Establecer este indicador fuerza el uso del antiguo algoritmo de suma de comprobación
    #  para mantener la compatibilidad con versiones anteriores, aunque keepalived
    #  intentará mantener la compatibilidad de todos modos si ve una suma de comprobación de una versión
    #  antigua. Especificar never desactivará la detección automática
    #  de sumas de comprobación antiguas. [Esta opción puede no estar habilitada - compruebe la salida
    #  de `keepalived -v` para OLD_CHKSUM_COMPAT.]
    old_unicast_checksum [never]
    # Algunos fabricantes (p. ej. Cisco y Juniper) interpretan RFC5798 5.2.8
    #  como aplicable solo a IPv6, ya que la cabecera pseudo en RFC2460 se
    #  especifica solo para IPv6, aunque la mayoría de las implementaciones de código abierto,
    #  incluyendo tcpdump/wireshark, incluyen la cabecera pseudo para IPv4.
    #  Keepalived por defecto usa una cabecera pseudo para VRRPv3 IPv4 también.
    #  Establecer esta opción desactiva la inclusión de la cabecera pseudo en el
    #  cálculo de la suma de comprobación para VRRPv3 IPv4.
    # Para cumplir con RFC9568, se debe establecer esta opción.
    v3_checksum_as_v2 [<BOOL>]
    # configuraciones específicas de la interfaz, igual que los parámetros globales.
    # tienen como valor predeterminado los parámetros globales
    garp_master_delay 10
    garp_master_repeat 1
    garp_lower_prio_delay 10
    garp_lower_prio_repeat 1
    garp_master_refresh 60
    garp_master_refresh_repeat 2
    garp_extra_if [all] 100	# especificar 0 desactiva la función
    # Las RFC de VRRP establecen que el temporizador de caída del maestro es 3 intervalos de anuncio más
    # un tiempo de sesgo. Establecer down_timer_adverts significa que el temporizador de caída del maestro será
    # down_timer_adverts intervalos de anuncio.
    # El valor predeterminado es 3, para cumplir con las RFC de VRRP. Establecer esto a cualquier otro
    # valor es una desviación del protocolo VRRP. Todos los routers virtuales de una instancia
    # VRRP dada DEBEN usar el mismo valor.
    down_timer_adverts [1-100]
    # Algunos usuarios experimentan mensajes de registro "thread timer expired". Estos son causados
    # porque el kernel no programa keepalived lo suficientemente rápido después de que expire un temporizador,
    # lo que siempre se debe a que no hay suficientes recursos de CPU disponibles (si se ejecuta
    # keepalived en una VM, podría deberse a que la propia VM no está siendo programada), o
    # a que keepalived no se ejecuta con una prioridad lo suficientemente alta (vea las opciones de programación
    # en tiempo real anteriores).
    # Si está configurado nopreempt y otra instancia se ha convertido en maestra, entonces hay
    # circunstancias en las que se requiere que esta instancia no se reanude como maestra, sino
    # que pase a ser de respaldo.
    # Si usa esta opción (y está configurado nopreempt), keepalived calculará
    # si otra instancia puede haberse hecho cargo (basándose en el intervalo de anuncio y
    # la prioridad más alta de las otras instancias - 254 por defecto a menos que se especifique con
    # esta opción), y si ese tiempo ha expirado desde que se envió el último anuncio,
    # la instancia VRRP volverá al estado de respaldo (recuerde incluir los pesos de
    # track_script etc. al calcular la prioridad más alta de otras instancias).
    timer_expired_backup [PRIORIDAD_MÁS_ALTA_DE_OTRAS_INSTANCIAS]
    # Si keepalived se retrasa más de 2 intervalos de anuncio para una instancia VRRP,
    # es posible que otra instancia haya tomado el control como maestra.
    # Si se recibe un anuncio de menor prioridad, no se envía otro anuncio.
    # Esto provoca el cumplimiento de las RFC (por defecto es global
    # vrrp_lower_priority_dont_send_advert).
    lower_prio_no_advert [<BOOL>]
    # Si somos maestros y recibimos un anuncio de mayor prioridad, se envía un anuncio
    # (que tendrá una prioridad menor que la del otro maestro), antes de transicionar
    # a respaldo. Esto significa que si el otro maestro tiene configurado
    # garp_lower_prio_repeat, reenviará los mensajes GARP. Esto es para sortear el
    # problema de que hayan habido dos maestros simultáneos, y los últimos mensajes
    # GARP vistos fueran nuestros.
    higher_prio_send_advert [<BOOL>]
    # número único arbitrario del 1 al 255
    # usado para diferenciar múltiples instancias de vrrpd
    # ejecutándose en la misma interfaz de red y familia
    # de direcciones y multicast/unicast (y por lo tanto el mismo socket).
    # Nota: se sabe que usar el mismo virtual_router_id con la misma
    # familia de direcciones en diferentes interfaces causa
    # problemas con algunos switches de red; si está
    # experimentando problemas al usar el mismo
    # virtual_router_id en diferentes interfaces, pero los problemas
    # se resuelven al no duplicar virtual_router_ids, sus
    # switches de red probablemente no están funcionando correctamente.
    #
    # Aunque en general es importante no duplicar un
    # virtual_router_id en la misma interfaz de red, hay un
    # caso especial al usar unicast si los pares unicast de las
    # instancias vrrp con virtual_router_ids duplicados en la
    # interfaz de red no se superponen, en cuyo caso los
    # virtual_router_ids pueden duplicarse.
    # También es posible duplicar virtual_router_ids en una
    # interfaz con multicast si se usan diferentes direcciones
    # multicast (ver mcast_dst_ip).
    virtual_router_id 51
    # para elegir al MAESTRO, gana la prioridad más alta.
    # El rango válido de valores para la prioridad es [1-255], con prioridad
    # 255 significando "propietario de la dirección".
    # Para ser MAESTRO, se recomienda hacerlo 50 más que en
    # otras máquinas. Todos los sistemas deben tener prioridades
    # diferentes para hacer el comportamiento determinista. Si desea
    # evitar que una instancia de mayor prioridad tome el control como
    # maestra al iniciar, configure no_preempt en lugar de usar
    # prioridades iguales.
    # Si no_accept está configurado (o vrrp_strict # que también establece
    # el modo no_accept), entonces a menos que la vrrp_instance tenga
    # prioridad 255, el sistema no recibirá paquetes dirigidos a las
    # VIPs/eVIPs, y las VIPs/eVIPs solo podrán usarse para propósitos
    # de enrutamiento.
    # Además, si una instancia tiene configurada prioridad 255, la
    # prioridad no puede ser reducida por track_scripts, track_process etc,
    # e igualmente track_scripts etc no pueden aumentar la prioridad a 255
    # si la prioridad configurada no es 255.
    priority 100
    # Intervalo de anuncio VRRP en segundos (ej. 0.92) (usar por defecto)
    advert_int 1
    # Nota: la autenticación fue eliminada de la especificación VRRPv2 por
    # RFC3768 en 2004.
    #   El uso de esta opción no es conforme y puede causar problemas; evite
    #   usarla si es posible, excepto al usar unicast, donde puede ser útil.
    authentication {
        # PASS|AH
        # PASS - Contraseña simple (sugerido)
        # AH - IPSEC (no recomendado)
        auth_type PASS
        # Contraseña para acceder a vrrpd.
        # debería ser la misma en todas las máquinas.
        # Solo se usan los primeros ocho (8) caracteres.
        auth_pass 1234
    }
    # direcciones add|del al cambiar a MAESTRO, a RESPALDO.
    # Con las mismas entradas en otras máquinas,
    # ocurrirá la transición opuesta.
    # Para virtual_ipaddress, virtual_ipaddress_excluded,
    #   virtual_routes y virtual_rules la mayoría de las opciones
    #   coinciden con las opciones del comando ip address/route/rule add.
    #   La opción track_group solo aplica a direcciones/rutas/reglas estáticas.
    #   no_track es específica de keepalived y significa que la
    #   vrrp_instance no transicionará fuera del estado maestro
    #   si la dirección/ruta/regla es eliminada y la dirección/ruta/regla
    #   no será restablecida hasta que la instancia vrrp transicione
    #   nuevamente a maestra.
    # <LABEL>: es opcional y crea un nombre para el alias.
               Para compatibilidad con "ifconfig", debería
               ser de la forma <realdev>:<anytext>, por ejemplo
               eth0:1 para un alias en eth0.
    # <SCOPE>: ("site"|"link"|"host"|"nowhere"|"global")
    # preferred_lft se establece en 0 para deprecar direcciones IPv6 (este es el
    # valor por defecto si la máscara de la dirección es /128). Use "preferred_lft forever"
    # para especificar que una dirección /128 no debe ser deprecada.
    # NOTA: se debe tener cuidado si se especifica dev para una dirección y
    # su red usa switches con aprendizaje MAC. El protocolo VRRP asegura
    # que la dirección MAC de origen de la interfaz que envía anuncios se
    # mantiene en la caché MAC de los switches; sin embargo, por defecto esto
    # no funcionará para las MAC de las VIPs/eVIPs configuradas en
    # interfaces diferentes a la interfaz donde está configurada la
    # instancia VRRP, ya que la interfaz, especialmente si es una
    # interfaz VMAC, solo enviará usando la dirección MAC de la interfaz
    # en respuesta a peticiones ARP. Esto puede significar que las
    # direcciones MAC de la interfaz puedan expirar en las cachés MAC de
    # los switches. Para evitar esto, use las opciones garp_extra_if o
    # garp_extra_if_vmac para enviar mensajes GARP/ND periódicos en esas
    # interfaces.
    virtual_ipaddress {
        <IPADDR>[/<MASK>] [brd <IPADDR>] [dev <STRING>] [use_vmac] [scope <SCOPE>]
                          [label <LABEL>] [peer <IPADDR>] [home]
                          [-nodad] [mngtmpaddr] [noprefixroute]
                          [autojoin] [no_track] [preferred_lft nn|forever]
        192.168.200.17/24 dev eth1
        192.168.200.18/24 dev eth2 label eth2:1
    }
    # IP VRRP excluido de VRRP opcional.
    # Para casos con un gran número (ej. 200) de IPs
    # en la misma interfaz. Para disminuir el número
    # de direcciones enviadas en los anuncios, puede excluir
    # la mayoría de las IPs de los anuncios.
    # Las IPs se agregan|eliminan igual que en virtual_ipaddress.
    # También se puede usar si desea poder agregar
    # una mezcla de direcciones IPv4 e IPv6, ya que todas
    # las direcciones en virtual_ipaddress deben ser de la
    # misma familia.
    virtual_ipaddress_excluded {
        <IPADDR>[/<MASK>] [brd <IPADDR>] [dev <STRING>] [scope <SCOPE>]
                          [label <LABEL>] [peer <IPADDR>] [home]
                          [-nodad] [mngtmpaddr] [noprefixroute]
                          [autojoin] [no_track]
        <IPADDR>[/<MASK>] ...
        ...
    }
    # Especificar que no hay direcciones IP virtuales es generalmente un error
    # de configuración y VRRP versión 3 establece explícitamente que el número
    # mínimo de direcciones es 1. En consecuencia, keepalived advierte si no
    # hay VIPs configuradas.
    # Sin embargo, hay circunstancias en las que es útil no tener VIPs, por
    # ejemplo, con servidores en la nube, como AWS, donde las direcciones IP
    # flotantes se manejan administrativamente y no se configuran en el
    # servidor virtual de la nube. Especificar no_virtual_ipaddress suprime

    # ADVERTENCIA - al usar esto con VRRPv3 causa una violación del protocolo y

Debounce de cambio de estado de la interfaz arriba/abajo




 Si una interfaz que está siendo utilizada (o rastreada) por una instancia VRRP pasa a estado de inactividad (down),
    

   las instancias VRRP entrarán, por defecto, inmediatamente en estado FAULT y, cuando
    

   todas las interfaces relevantes vuelvan a estar activas, las instancias VRRP entrarán
    

   inmediatamente en estado BACKUP.



    

   Esto puede causar problemas si las interfaces están fluctuando, por lo que se pueden especificar retrasos
    

   entre el cambio de estado de la interfaz y la transición al estado FAULT/BACKUP. Si la
    

   interfaz regresa a su estado original antes de que expire el retraso, no se producirá ninguna transición de estado de la instancia VRRP asociada.



interface_up_down_delays {
    ifname down_delay [up_delay]
    ifname2 down_delay [up_delay]
    ...
}


    Los retrasos se especifican en segundos, con una resolución de microsegundos, por ejemplo, un retraso de
    0.00001 significa 10 microsegundos. Un retraso de 0 significa que no hay retraso en el cambio de estado. El retraso máximo
    que se puede especificar es de 255 segundos.
    Si se omite up_delay, se establece como igual a down delay.
    El retraso down en una interfaz debe ser menor que dos (o más precisamente, uno menos que down_timer_adverts (por defecto 3)) veces el intervalo de anuncios de cualquier instancia VRRP que utilice esa interfaz (de lo contrario, una instancia de respaldo, mientras no recibe anuncios, puede agotar el tiempo de espera y convertirse en maestro antes de que esta instancia transicione al estado FAULT).
    En consecuencia, los retrasos de arriba/abajo se pueden reducir dinámicamente si otra instancia es maestra con un intervalo de anuncios más corto.
    Si la instancia VRRP utiliza una VMAC, heredará los retrasos de debounce de arriba/abajo de su interfaz principal.







CONFIGURACIÓN DE LVS


contiene subbloques de Grupo(s) de servidores virtuales y Servidor(es) virtuales


Los subbloques contienen argumentos para configurar la función IPVS (LVS) de Linux. El conocimiento de ipvsadm(8) será útil aquí. La configuración de LVS se logra definiendo grupos de servidores virtuales, servidores virtuales y, opcionalmente, configuración SSL. Cada servidor virtual define un conjunto de servidores reales; puede adjuntar verificadores de estado a cada servidor real. Keepalived luego dirigirá la operación de LVS manteniendo dinámicamente la topología.


Para conocer las combinaciones de configuración válidas, consulte la página del manual de ipvsadm(8).


Nota: Donde una opción se puede configurar para un servidor virtual, un servidor real y posiblemente un verificador, la configuración del servidor virtual es el valor predeterminado para los servidores reales, y la configuración del servidor real es el valor predeterminado para los verificadores.


Nota: Los servidores reales/de respaldo en modo túnel pueden diferir de la familia de direcciones del servidor virtual y los servidores reales/de respaldo que no están en modo túnel, que deben ser todos iguales. Si un servidor virtual utiliza un fwmark y todos los servidores reales/de respaldo están en modo túnel, la familia de direcciones del servidor virtual será la misma que la familia de direcciones de los servidores reales/de respaldo si todos son iguales, de lo contrario, será IPv4 por defecto (use ip_family inet6 para anular esto).


Nota: El puerto para el servidor virtual solo se puede omitir si el servicio virtual es persistente.






Grupo(s) de servidores virtuales


Esta función ofrece una forma de simplificar su configuración al factorizar las definiciones de servidores virtuales. Si necesita definir un conjunto de servidores virtuales con exactamente la misma topología de servidores reales, esta función hará que su configuración sea mucho más legible, optimizará la duplicación de servidores virtuales IPVS si se utiliza nftables_ipvs y optimizará la tarea de verificación de estado al generar solo un verificador de estado donde la declaración de múltiples servidores virtuales generaría un verificador de estado dedicado para cada servidor real, lo que desperdiciaría recursos del sistema.


Se puede usar cualquier combinación de direcciones IP, rangos de direcciones IP y marcas de firewall, siempre que la familia de las direcciones IP del grupo de servidores virtuales coincida con la familia de direcciones IP de todos los servidores reales de cualquier servidor virtual que utilice el grupo de servidores virtuales. La única excepción a esto es que el grupo de servidores virtuales se puede configurar con direcciones y marcas de firewall IPv4 e IPv6, siempre que todos los servidores reales (y de respaldo) de todos los servidores virtuales que utilizan el grupo de servidores virtuales utilicen reenvío de túnel; si se especifican marcas de firewall en este caso, se debe especificar la familia de direcciones (la única excepción es si el grupo de servidores virtuales no tiene direcciones IP (es decir, solo marcas de firewall) y todos los servidores reales/de respaldo están en modo túnel, será IPv4 por defecto; no es una buena práctica confiar en esto y se deben configurar las familias de direcciones de las marcas de firewall). El uso de esta opción está destinado a LVS muy grandes, pero tenga en cuenta que esto puede crear un gran número de servidores virtuales a menos que se utilice nftables_ipvs. Se recomienda encarecidamente el uso de nftables_ipvs debido a las optimizaciones y eficiencias muy significativas que proporciona.


NOTA: no configure más de un servidor virtual TCP, uno UDP y uno SCTP con la misma familia de direcciones IP utilizando el mismo grupo de servidores virtuales (o, dicho de otra manera, no tenga dos servidores virtuales con el mismo protocolo y familia de direcciones utilizando el mismo grupo de servidores virtuales); si todos los servidores reales están en modo túnel, entonces no debe tener servidores virtuales IPv4 e IPv6 con el mismo protocolo.

AVANZADA

El analizador de configuración se ha extendido para admitir características avanzadas como con

figuración condicional y sustitución de parámetros. Estas características son muy útiles para c
ualquier entorno de scripting donde se generan plantillas de configuración (centros de datos).

Configuración condicional e id de

configuración

El config-id por defecto es la primera parte del nombre del nodo tal como lo devuelve uname, y se puede sobrescribir con la opción de línea de comandos -i o

--config-id.

Cualquier línea de configuración que comience con '@' es una línea de configuración condicional. La palabra que sigue inmediatamente (es decir, sin ningún espacio) al carácter '@' se compara con el config-id, y si no coinciden, la línea de configuración se

ignora.

Alternativamente, '@^' es una comparación negativa, de modo que si la palabra que sigue inmediatamente NO coincide con el config-id, la línea de configuración SÍ se

incluye.

El propósito de esto es permitir que un solo archivo de configuración se use para múltiples sistemas, donde las únicas diferencias probablemente serán el router_id, las prioridades de las instancias VRRP, y posiblemente los nombres de interfaz y direcciones

unicast.

Por

ejemplo: 
    global_defs {
        @main   router_id main_router
        @backup router_id backup_router
    }
    ...
    vrrp_instance VRRP {
        ...
        @main    unicast_src_ip 1.2.3.4
        @backup  unicast_src_ip 1.2.3.5
        @backup2 unicast_src_ip 1.2.3.6
        unicast_peer {
            @^main    1.2.3.4
            @^backup  1.2.3.5
            @^backup2 1.2.3.6
        }
        ...
}

Si keepalived se invoca con -i main, entonces el router_id se establecerá a main_router; si se i

nvoca con -i backup, entonces backup_router; si no se invoca con -i, o con -i cualquier otra cos
a, entonces el router_id no se establecerá. Los pares unicast para main serán 1.2.3.5 y 1.2.3.6.

Sustitución de

parámetros

Se pueden especificar parámetros sustituibles. El formato para definir un parámetro

es:

$PARAMETER=VALU

E

donde no debe haber espacio antes del '=' y solo puede haber espacio en blanco antes de '$'. Se permiten valores

vacíos.

Los nombres de los parámetros pueden estar compuestos por cualquier combinación de A-Za-z0-9 y _, pero no pueden comenzar con un dígito. Los nombres de parámetros que comienzan con un guion bajo deben considerarse nombres reservados que keepalived definirá para varias opciones

predefinidas.

Después de que se define un parámetro, cualquier aparición de $PARAMETER seguido de espacio en blanco, o cualquier aparición de ${PARAMETER} (que no necesita ser seguido de espacio en blanco) será reemplazada por

VALUE.

El reemplazo es recursivo, de modo que si el valor de un parámetro en sí mismo incluye un parámetro reemplazable, entonces después de la primera sustitución, el parámetro en el valor será reemplazado; la sustitución se realiza en el momento del reemplazo y no en el momento de la definición, así que por

ejemplo: 
    $ADDRESS_BASE=10.2.${ADDRESS_BASE_SUB}
    $ADDRESS_BASE_SUB=0
    ${ADDRESS_BASE}.100/32
    $ADDRESS_BASE_SUB=10
    ${ADDRESS_BASE}.100/32
    producirá:
        10.2.0.100/32
        10.2.10.
100/32

Nótese en los ejemplos anteriores el uso tanto de ADDRESS_BASE como de ADDRESS_BASE_SUB requirió llaves ({}) ya que los parámetros no eran seguidos por espacio en blanco (después de la primera sustitución que produjo 10.2.${ADDRESS_BASE_SUB}.100/32 el parámetro todavía no es seguido por espacio en blanco)

.

Si un parámetro no está definido, no será reemplazado en absoluto, así que por ejemplo ${UNDEF_PARAMETER} permanecerá en la configuración si está indefinido; esto significa que la configuración existente que contiene un carácter '$' (por ejemplo en una definición de script) no será cambiada siempre que no se agreguen nuevas definiciones de parámetros a la

configuración.

La sustitución de parámetros funciona en conjunto con la configuración condicional. Por

ejemplo:

        ...

            priority 240

        priority 240

            @main priority

Note:

The purpose of this document is to describe the configuration file syntax for the Keepalived manager. It is not a tutorial on how to configure Keepalived, and there is no guarantee that the syntax described herein will remain the same in future versions of Keepalived. Users wishing to configure Keepalived are advised to consult the examples provided with the Keepalived source code distribution, and to take advantage of the checksums and signatures provided with the Keepalived distribution. The syntax described herein is complex, and prone to error. It is recommended that users wishing to deploy Keepalived in a production environment use the checksums and signatures provided.

DESCRIPTION

This document describes the syntax of the Keepalived configuration file, which is typically located at /etc/keepalived/keepalived.conf.

PARAMETER SYNTAX

Keepalived configuration parameters are configured using a simple syntax. Parameters are grouped into configuration blocks, denoted by braces {}. For example:

    vrrp_instance VI_1 {
        state MASTER
        interface eth0
        virtual_router_id 51
        priority 150
        advert_int 1
        authentication {
            auth_type PASS
            auth_pass 1234
        }
        virtual_ipaddress {
            10.0.0.1/24 dev eth0 label eth0:1
            10.0.0.2/24 dev eth0 label eth0:2
        }
    }

The configuration file is parsed sequentially. The indentation level is ignored. Comments begin with a # character and continue to the end of the line. The parser is tolerant of whitespace and newlines.

SCRIPTS

Keepalived can execute scripts in response to various events. These scripts are defined using the vrrp_script directive.

    vrrp_script chk_http {
        script "/path/to/check/http.sh"
        interval 2
        weight 20
        fall 2
        rise 2
    }

The script parameter specifies the command to be executed. The interval parameter specifies the time in seconds between script executions. The weight parameter is added to the VRRP instance priority if the script succeeds. The fall parameter specifies the number of consecutive script failures required to consider the script failed. The rise parameter specifies the number of consecutive script successes required to consider the script succeeded.

Scripts are executed with the following exit codes:

0
Script succeeded.
1
Script failed.
2
Script did not run or timed out.

Quoted strings

Strings containing whitespace or special characters should be enclosed in double quotes ("). For example:

    auth_pass "my secret password"

CONFIGURATION PARSER

The configuration file parser is recursive. This allows for complex configurations to be built up from smaller, more manageable blocks. The parser recognizes the following directives:

TOP HIERACHY

Keepalived configuration is organized into a hierarchy of blocks. The top-level block is the global configuration block.

GLOBAL CONFIGURATION

The global configuration block contains settings that apply to the entire Keepalived instance.

Global definitions

The global_defs block contains global configuration options.

    global_defs {
        router_id LVS_DEVEL
        enable_script_security update
        # ...
    }

Parameters:

router_id
Unique identifier for the Keepalived router. Defaults to the hostname.
enable_script_security
Controls script security. Can be set to update, def false, or update default.

Linkbeat interfaces

The linkbeat_interfaces directive defines a list of interfaces to monitor for link status. If any of the specified interfaces go down, Keepalived will transition to the FAULT state.

Static track groups

The static_track directive defines groups of IP addresses that should be tracked. If any of the IP addresses in a tracked group become unreachable, Keepalived will transition to the FAULT state.

Static routes/addresses/rules

The static_routes, static_ipaddress, and static_rules directives define static routes, IP addresses, and rules that should be managed by Keepalived.

Track files

The track_file directive specifies a file to monitor. If the file is modified, Keepalived will perform a configured action.

VRRP track processes

The vrrp_track_process directive specifies a process to monitor. If the process terminates, Keepalived will perform a configured action.

BFD CONFIGURATION

Keepalived supports Bidirectional Forwarding Detection (BFD) for faster failure detection. BFD configuration is done within the bfd_ கொள்ளுங்கள் block.

VRRPD CONFIGURATION

Keepalived supports the VRRP protocol for failover. VRRP configuration is done within the vrrp_ கொள்ளுங்கள் block.

VRRP script(s)

The vrrp_script directive defines a script that will be executed periodically. The script's exit code is used to determine the health of a service.

VRRP synchronization group(s)

The vrrp_sync_group directive groups multiple VRRP instances together. Failover of one instance in the group will cause failover of all instances in the group.

VRRP gratuitous ARP and unsolicited neighbour advert delay group(s)

The vrrp_garp_master and vrrp_gna_interval directives control the sending of gratuitous ARP requests and unsolicited neighbour advertisements.

VRRP instance(s)

The vrrp_instance directive defines a VRRP instance. This is the core of Keepalived's VRRP functionality.

    vrrp_instance VI_1 {
        state BACKUP
        interface eth0
        virtual_router_id 51
        priority 100
        advert_int 1
        # ...
    }

Key parameters include:

state
Initial state of the VRRP instance (MASTER or BACKUP).
interface
The network interface to use for VRRP.
virtual_router_id
A unique identifier for the VRRP router.
priority
The priority of the router. Higher values have higher priority.
advert_int
The interval in seconds between VRRP advertisements.
authentication
Authentication settings for VRRP.
virtual_ipaddress
A list of virtual IP addresses to manage.
track_script
A list of scripts to monitor. If any script fails, the instance priority is reduced.

Interface up/down status change debouncing

Keepalived provides options to debounce interface state changes, preventing rapid transitions due to transient link failures.

Virtual server group(s)

The virtual_server_group directive defines a group of virtual servers.

Virtual server(s)

The virtual_server directive defines a virtual server.

    virtual_server 192.168.1.100 80 {
        weight 100
        # ...

lb_kind

ADVANCED CONFIGURATION

Keepalived offers advanced features for configuration management and parameter substitution.

Conditional configuration and configuration id

The configuration parser supports conditional processing based on configuration IDs. This allows for dynamic configuration changes.

Parameter substitution

Variables can be defined and substituted within the configuration file using the $variable syntax. This allows for reuse of configuration parameters.

Pre-defined definitions

Keepalived pre-defines certain variables that can be used in the configuration file. These typically relate to the system environment.

Sequence blocks

Sequence blocks, denoted by ~SEQ(...), allow for the generation of multiple configuration lines by incrementing a variable over a specified range.

The syntax is as follows:

    ~SEQ(var, start, end, step) configuration_line

Here:

  • $var is the variable to be incremented.
  • start is the initial value of the variable.
  • end is the final value of the variable (inclusive).
  • step is the increment value.

If step is omitted, it defaults to 1 or -1, depending on whether end is greater or less than start. If start is omitted, it defaults to 1 if end > 0, or -1 if end < 0.

The ~SEQx(...) directive is similar to ~SEQ(...), but the variable $var is formatted in hexadecimal.

Note: It is currently necessary to use different variables for ~SEQ blocks than any previously defined variables, including those used in previous ~SEQ blocks. This behavior may change in the future, so do not rely on a ~SEQ block variable being defined after the end of the block.

Examples:

    ~SEQ(SUBNET, 0, 3) ip_address 10.0.${SUBNET}.1
    produces:
        ip_address 10.0.0.1
        ip_address 10.0.1.1
        ip_address 10.0.2.1
        ip_address 10.0.3.1
and
    ~SEQx(SUBNET, 144, 16, 192) ip_address fe80::20:${SUBNET}:1
  or better
    ~SEQx(SUBNET, 0x90, 0x10, 0xc0) ip_address fe80::20:${SUBNET}:1
    produces:
        ip_address fe80::20:90:1
        ip_address fe80::20:a0:1
        ip_address fe80::20:b0:1
        ip_address fe80::20:c0:1
   Another example:
	virtual_ipaddress {
	    ~SEQx(AD2, 0x90, 0x10, 0xc0) ~SEQx(AD1, 0x12, -1, 0x0c) fe81::10:${AD2}:${AD1}
	}

Multiple ~SEQ elements can be used on a line:

    $VI4= \
    track_file offset_instance_4.${IF}.${NUM}.${ID} { \
        file "${_PWD}/679/track_files/4.${IF}.${NUM}.${ID}" \
        weight -100 \
    } \
    vrrp_instance vrrp4.${IF}.${NUM}.${ID} { \
        interface bond${IF}.${NUM} \
        use_vmac vrrp4.${IF}.${NUM}.${ID} \
        virtual_router_id ${ID} \
        priority 130 \
        virtual_ipaddress { \
            10.${IF}.${NUM}.${ID}/24 \
        } \
        track_file { \
            offset_instance_4.${IF}.${NUM}.${ID} \
        } \
    }
    ~SEQ(IF,0,7) ~SEQ(NUM,0,31) ~SEQ(ID,1,254) $VI4
    produces 65024 vrrp instances named vrrp4.0.0.1 through to
    vrrp4.7.31.254.

List blocks

List blocks are similar to sequence blocks, but the values to be substituted into the variable are explicitly listed in the ~LST specification.

A line starting with ~LST(var, val1, val2, val3) will cause the remainder of the line to be processed multiple times. The variable $var will be set first to val1, then val2, and finally val3. Any number of values can be specified, as long as at least one value is provided (although only one value would be pointless).

If multiple variables need to be substituted simultaneously, the variables and their corresponding values must be enclosed in {...} blocks. For example:


~LST({IP, IP1}, {10,1},{20,4},{5,6},{12,8}) 192.168.${IP}.${IP1}

This will first set IP=10 and IP1=1, then IP=20 and IP1=4, and so on, producing:


192.168.10.1
192.168.20.4
192.168.5.6
192.168.12.8

192.169.3.7
192.169.4.5
192.169.4.6
192.169.4.7

It has been identified that if proxy_arp and proxy_arp_pvlan are enabled on an interface that has VIPs or eVIPs configured on it, it can cause incorrect replies to ARP requests due to the proxy replying to the ARP request as well as the keepalived host. Both need to be set to 0 to function properly.
