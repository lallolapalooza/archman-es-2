Nombre

kitten-ssh - Documentación de kitten

Descripción general

  • Integración automática de Shell <#shell-integration> en hosts remotos
  • Clona fácilmente la configuración local del shell/editor en hosts remotos
  • Reutilización automática de conexiones existentes para evitar la latencia en la configuración de la conexión
  • Haz que el binario de kitten esté disponible en el host remoto bajo demanda
  • Cambia fácilmente los colores de la terminal al conectarte a hosts remotos
  • Reenvía automáticamente el socket de control remoto de kitty a los hosts configurados

Añadido en la versión 0.25.0: Integración automática de Shell, transferencia de archivos y reutilización de conexiones

Añadido en la versión 0.30.0: Reenvío automático de sockets de control remoto

El kitten ssh te permite iniciar sesión fácilmente en hosts remotos y configurar automáticamente el entorno allí para que sea tan cómodo como tu shell local. Puedes especificar variables de entorno para establecer en el host remoto y archivos para copiar allí, haciendo que tu experiencia remota sea igual que tu shell local. Además, configura automáticamente la Integración de Shell <#shell-integration> en el host remoto y copia la base de datos terminfo de kitty allí.

El kitten ssh es un envoltorio delgado alrededor del programa de línea de comandos tradicional ssh https://man.openbsd.org/ssh y soporta todas las mismas opciones, argumentos y configuración. En escenarios de uso interactivo es un reemplazo directo para ssh. Para probarlo, simplemente ejecuta:

kitten ssh nombre-de-host-a-conectar

Deberías terminar en un prompt de shell en el host remoto, con la integración de shell habilitada. Si te gusta, puedes añadirle un alias en los archivos rc de tu shell:

alias s="kitten ssh"

Así que ahora puedes escribir simplemente s nombrehost para conectarte.

Si defines un mapeo en kitty.conf como:

map f1 new_window_with_cwd

Entonces, al presionar F1 se abrirá una nueva ventana conectada automáticamente al mismo host usando el kitten ssh, en el mismo directorio.

El kitten ssh se puede configurar usando el archivo ~/.config/kitty/ssh.conf donde puedes especificar variables de entorno para establecer en el host remoto y archivos para copiar del local al remoto. Veamos un ejemplo rápido:

# Copia los archivos y directorios necesarios para configurar algunas herramientas comunes
copy .zshrc .vimrc .vim
# Configura algunas variables de entorno
env SOME_VAR=x
# COPIED_VAR tendrá el mismo valor en el host remoto que localmente
env COPIED_VAR=_kitty_copy_env_var_
# Crea algunas configuraciones por nombre de host
hostname someserver-*
copy env-files
env SOMETHING=else
hostname someuser@somehost
copy --dest=foo/bar some-file
copy --glob some/files.*

Ver más abajo los detalles completos de la sintaxis y opciones de ssh.conf. Adicionalmente, puedes pasar opciones de configuración en la línea de comandos:

kitten ssh --kitten interpreter=python nombre-servidor

El argumento --kitten se puede especificar varias veces, con directivas de ssh.conf. Estas anulan las opciones finales utilizadas para el host coincidente, como si se hubieran añadido al final de la sección coincidente para ese host en ssh.conf. Solo se aplican al host al que se está conectando SSH con esta invocación, por lo que se ignoran las directivas hostname.

Advertencia:

Debido a las limitaciones en el diseño de SSH, cualquier escritura que hagas antes de que aparezca el prompt del shell puede perderse. Así que, idealmente, no empieces a escribir hasta que veas el prompt del shell. 😇

Un ejemplo del mundo real

Supongamos que te conectas frecuentemente por SSH a un servidor de producción y quieres configurar tu shell y editor allí usando tu configuración personalizada. Sin embargo, otras personas también podrían conectarse por SSH y no quieres sobrescribir su configuración. Aquí te explicamos cómo se podría lograr usando el kitten ssh con zsh y vim como shell y editor, respectivamente:

# Que estas configuraciones se apliquen a servidores de mi organización
hostname myserver-*
# Configura zsh para leer sus archivos desde my-conf/zsh
env ZDOTDIR=$HOME/my-conf/zsh
copy --dest my-conf/zsh/.zshrc .zshrc
copy --dest my-conf/zsh/.zshenv .zshenv
# Si usas otros archivos de inicialización de zsh, añádelos de manera similar
# Configura vim para leer su configuración desde my-conf/vim
env VIMINIT=$HOME/my-conf/vim/vimrc
env VIMRUNTIME=$HOME/my-conf/vim
copy --dest my-conf/vim .vim
copy --dest my-conf/vim/vimrc .vimrc

Cómo funciona

El kitten ssh funciona haciendo que SSH transmita y ejecute un script de arranque POSIX sh (o opcionalmente Python) en el host remoto usando un interpreter. Este script lee los datos de configuración a través del dispositivo TTY, que kitty envía como un tarball comprimido codificado en Base64. El script lo extrae y coloca los archivos y establece las variables de entorno, antes de finalmente lanzar el shell de inicio de sesión con la integración de shell habilitada. Los datos son solicitados por el kitten a través del TTY con una contraseña aleatoria de un solo uso. kitty lee la solicitud y si la contraseña coincide con una contraseña pre-almacenada en memoria compartida en el localhost por el kitten, se permite la transmisión. Si tu versión local de OpenSSH https://www.openssh.com/ es >= 8.4, los datos se transmiten instantáneamente sin ningún retraso de ida y vuelta.

Nota:

Al conectarte a hosts BSD, es posible que el script de arranque falle o se ejecute lentamente, porque los shells predeterminados están limitados de diversas maneras. Tu mejor opción es instalar Python en el host remoto, asegurarte de que el shell de inicio de sesión sea compatible con POSIX sh y usar python como interpreter en ssh.conf.

Nota:

Esto puede funcionar o no cuando se utilizan multiplicadores de terminal, dependiendo de si pasan los códigos de escape y de si los valores de las variables de entorno KITTY_PID <#envvar-KITTY_PID> y KITTY_WINDOW_ID <#envvar-KITTY_WINDOW_ID> son correctos en la sesión actual (pueden ser incorrectos al conectarse a una sesión de tmux ejecutándose en otra ventana) y el kitten ssh se ejecuta en la ventana del multiplicador actualmente activa.

Configuración del arranque del host

hostname
hostname *

El nombre de host al que se aplican las siguientes opciones. Se puede usar un patrón glob para coincidir con varios hosts. También se pueden especificar varios nombres de host, separados por espacios. El nombre de host puede incluir un nombre de usuario opcional en la forma usuario@host. Cuando no se especifica, las opciones se aplican a todos los hosts, hasta que se encuentra la primera especificación de nombre de host. Ten en cuenta que la coincidencia del nombre de host se realiza contra el nombre que especificas en la línea de comandos para conectarte al host remoto. Si deseas incluir la misma configuración básica para muchos hosts diferentes, puedes hacerlo con la directiva include <#include>. En la versión 0.28.0, el comportamiento de esta opción se modificó ligeramente; ahora, cuando se encuentra un nombre de host, todos sus valores de configuración se establecen en los valores predeterminados en lugar de heredarse de un bloque de nombre de host coincidente anterior. En particular, esto significa que los nombres de host no heredan configuraciones, evitando así acciones a distancia difíciles de entender.

interpreter
interpreter sh

El intérprete a utilizar en el host remoto. Debe ser un shell compatible con POSIX o un ejecutable de python. Si el sh predeterminado no está disponible o está roto, usar un intérprete alternativo puede ser útil.

remote_dir
remote_dir .local/share/kitty-ssh-kitten

La ubicación en el host remoto donde se instalan los archivos necesarios para este kitten. Las rutas relativas se resuelven con respecto a $HOME. Absoluta

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

los paths que comienzan con / son eliminados y también se resuelven con respecto a $HOME.

copy

Copia archivos y directorios de hosts locales a remotos. Se asume que los archivos especificados son relativos al directorio HOME y se copian a HOME en el sistema remoto. Los directorios se copian recursivamente. Si se usan rutas absolutas, se copian tal cual. Por ejemplo:

copy .vimrc .zshrc .config/some-dir

Use --dest para copiar un archivo a otro destino en el host remoto:

copy --dest some-other-name some-file

Se pueden especificar patrones de glob para copiar múltiples archivos, con --glob:

copy --glob images/*.png

Se pueden excluir archivos al copiar con --exclude:

copy --glob --exclude *.jpg --exclude *.bmp images/*

Los archivos cuyo nombre remoto coincida con el patrón de exclusión no se copiarán. Para más detalles, ver El comando copy.

Entorno del shell de inicio de sesión

shell_integration
shell_integration inherited

Controla la integración del shell en el host remoto. Ver Integración de shell <#shell-integration> para más detalles sobre cómo funciona esta configuración. El valor especial inherited significa usar la configuración de kitty.conf. Esta configuración es útil para sobrescribir la integración por host.

login_shell

El shell de inicio de sesión a ejecutar en el host remoto. Por defecto, se utiliza el shell de inicio de sesión de la cuenta de usuario remoto.

env

Especifica las variables de entorno que se establecerán en el host remoto. Usar el nombre con un signo igual (ej. env VAR=) la establecerá a la cadena vacía. Especificar solo el nombre (ej. env VAR) eliminará la variable del entorno del shell remoto. El valor especial _kitty_copy_env_var_ hará que el valor de la variable se copie del entorno local. Las definiciones se procesan alfabéticamente. Tenga en cuenta que las variables de entorno se expanden recursivamente, por ejemplo:

env VAR1=a
env VAR2=${HOME}/${VAR1}/b

El valor de VAR2 será <ruta al directorio home>/a/b.

cwd

El directorio de trabajo en el host remoto al que cambiar. Las variables de entorno en este valor se expanden. El valor por defecto está vacío, por lo que no se realiza ningún cambio, lo que generalmente significa que se usa el directorio HOME.

color_scheme

Especifica un esquema de color a usar al conectarse al host remoto. Si esta opción termina en .conf, se asume que es el nombre de un archivo de configuración a cargar desde el directorio de configuración de kitty, de lo contrario, se asume que es el nombre de un tema de color a cargar a través del kitten de temas <>. Tenga en cuenta que solo se cambian los colores que se aplican al texto/fondo; otras configuraciones de los archivos .conf/temas se ignoran.

remote_kitty
remote_kitty if-needed

Hace que kitten esté disponible en el host remoto. Útil para ejecutar kittens como el kitten icat <> para mostrar imágenes o el kitten de transferencia de archivos <> para transferir archivos. Solo funciona si el host remoto tiene una arquitectura para la cual hay binarios precompilados de kitten disponibles en https://github.com/kovidgoyal/kitty/releases. Tenga en cuenta que kitten no se copia realmente al host remoto; en su lugar, se copia un pequeño script de arranque que descargará y ejecutará kitten cuando se ejecute kitten por primera vez en el host remoto. Un valor de if-needed significa que kitten se instala solo si no está presente en el PATH del sistema. Un valor de yes significa que kitten se instala incluso si ya está presente, y el kitten instalado tiene prioridad. Finalmente, no significa que no se instala ningún kitten en el host remoto. El kitten instalado se puede actualizar ejecutando: kitten update-self en el host remoto.

Configuración de Ssh

share_connections
share_connections yes

Dentro de una sola instancia de kitty, todas las conexiones a un servidor particular pueden ser compartidas. Esto reduce la latencia de inicio para conexiones posteriores y significa que solo tiene que introducir la contraseña una vez. Internamente, utiliza SSH ControlMasters y estos se limpian automáticamente por kitty cuando se cierra. Puede mapear un atajo a close_shared_ssh_connections <#action-close_shared_ssh_connections> para desconectar todas las conexiones compartidas activas.

askpass
askpass unless-set

Controla el programa que SSH usa para pedir contraseñas o confirmación de claves de host, etc. El valor por defecto es usar el askpass nativo de kitty, a menos que la variable de entorno SSH_ASKPASS <#envvar-SSH_ASKPASS> esté definida. Establezca esta opción a ssh para no interferir en absoluto con el mecanismo normal de askpass de ssh, lo que típicamente significa que ssh pedirá la información en la terminal. Establézcala a native para usar siempre la implementación nativa incorporada de askpass de kitty. Tenga en cuenta que no usar la implementación de askpass de kitty significa que SSH podría necesitar usar la terminal antes de que se establezca la conexión, por lo que el kitten no podrá usar la terminal para enviar datos sin un viaje de ida y vuelta adicional, lo que aumenta la latencia inicial de conexión.

delegate

No utilice el kitten SSH para este host. En su lugar, ejecute el comando especificado como delegado. Por ejemplo, usando delegate ssh se ejecutará el comando ssh con todos los argumentos pasados al kitten, excepto los específicos de kitten. Esto es útil si algunos hosts no son capaces de soportar el kitten ssh.

forward_remote_control
forward_remote_control no

Reenvía el socket de control remoto de kitty al host remoto. Esto permite usar las facilidades de control remoto de kitty desde el host remoto. ADVERTENCIA: Esto permite que cualquier software en el host remoto tenga acceso completo al ordenador local, así que solo hágalo para hosts remotos de confianza. Tenga en cuenta que esto no funciona con sockets UNIX abstractos como @mykitty debido a las limitaciones de SSH. Esta opción utiliza el reenvío de sockets SSH para reenviar el socket al que apunta la variable de entorno KITTY_LISTEN_ON <#envvar-KITTY_LISTEN_ON>.

Automatización de Askpass

password

Especifica una contraseña a usar cuando SSH solicite una contraseña. El formato del valor es "backend:secret". Actualmente, solo se soporta el backend "text", que almacena el secreto en texto plano en el archivo de configuración. Por ejemplo:

password text:mi_contraseña

Si se omite el prefijo del backend, se trata como "text:" por compatibilidad con versiones anteriores. Tenga cuidado, ya que almacenar contraseñas en texto plano no es seguro.

totp_secret

Especifica un secreto compartido TOTP para rellenar automáticamente códigos de un solo uso cuando SSH los solicite. El formato del valor es "backend:secret". Actualmente, solo se soporta el backend "text". Por ejemplo:

totp_secret text:JBSWY3DPEHPK3PXP

Si se omite el prefijo del backend, se trata como "text:" por compatibilidad con versiones anteriores.

totp_digits
totp_digits 6

Número de dígitos para los códigos TOTP generados. El valor por defecto es 6.

totp_period
totp_period 30

Período de tiempo en segundos para la validez del código TOTP. El valor por defecto es 30.

El comando copy

copy [opciones] archivo_o_directorio_a_copiar ...

Copia archivos y directorios de hosts locales a remotos. Se asume que los archivos especificados son relativos al directorio HOME y se copian a HOME en el sistema remoto. Los directorios se copian recursivamente. Si se usan rutas absolutas, se copian tal cual.

Opciones

--glob [=no]
Interpreta los argumentos de archivo como patrones de glob. El globbing se basa en comodines estándar con la adición de que /**/ coincide con cualquier número de directorios. Ver la sintaxis detallada en htt kitten-ssh(1)

NAME

kitten-ssh - Manage files on remote hosts.

SYNOPSIS

kitten-ssh OPTIONS ... copy FROM TO

kitten-ssh OPTIONS ... copy FROM...

kitten-ssh OPTIONS ... copy --source-is-dir FROM... TO

kitten-ssh OPTIONS ... copy --source-is-dir FROM... TO...

kitten-ssh OPTIONS ... copy --dest-is-dir FROM... TO...

OVERVIEW

The kitten-ssh is a wrapper around the scp command. It simplifies copying files to/from remote hosts. It automatically handles SSH host key verification, can optionally copy files without SSH prompting, and can be configured to automatically install terminfo files to the remote host, for full Kitty terminal support.

A REAL WORLD EXAMPLE

Copy the entire contents of the local ~/Documents directory to the remote host user@remote.com in the /home/user/docs directory.

kitten-ssh copy ~/Documents user@remote.com:/home/user/docs

Copy the file ~/myconfig.conf to the remote host user@remote.com in the home directory.

kitten-ssh copy ~/myconfig.conf user@remote.com:

Copy all files ending in .txt from the current directory to the remote host user@remote.com in the ~/data directory.

kitten-ssh copy *.txt user@remote.com:~/data

Copy the directory ~/myproject to the remote host user@remote.com. The directory will be created as ~/myproject on the remote host.

kitten-ssh copy --source-is-dir ~/myproject user@remote.com:

HOW IT WORKS

This command is a wrapper around scp. It takes the same arguments as scp, with a few additions. The main difference is that it automatically handles SSH host key verification. If the host key is not known, it will be added to ~/.ssh/known_hosts and you will be prompted to accept it. Subsequent connections will not prompt for the host key.

The command also supports several options to control the copying behavior, such as excluding files, preserving symlinks, and specifying the destination directory.

HOST BOOTSTRAP CONFIGURATION

To ensure full Kitty terminal support on the remote host, the terminfo files need to be installed. Kitten-ssh attempts to do this automatically for you. If it fails, or if you prefer to do it manually, refer to the Copying terminfo files manually section.

LOGIN SHELL ENVIRONMENT

Kitten-ssh attempts to ensure that your login shell environment is set up correctly on the remote host. This includes setting environment variables and sourcing appropriate configuration files.

SSH CONFIGURATION

Kitten-ssh uses your existing SSH configuration, including settings from ~/.ssh/config. This means you can configure host aliases, ports, users, and other SSH options in your config file, and kitten-ssh will use them automatically.

ASKPASS AUTOMATION

If your SSH connection requires a password or passphrase, kitten-ssh can be configured to automate this process. This typically involves setting up SSH keys or using an SSH agent.

THE COPY COMMAND

The core functionality of kitten-ssh is the copy command. It allows you to transfer files and directories between your local machine and remote hosts. The syntax is similar to scp, but with added flexibility.

--source-is-dir
When copying a single source file, this option tells kitten-ssh to treat the source as a directory and copy its contents. This is useful when you want to copy a directory that happens to be specified as a single source.
--dest-is-dir
When copying multiple source files, this option tells kitten-ssh to treat the destination as a directory. If the destination does not exist, it will be created. If it exists, the source files will be copied into it.
--exclude <EXCLUDE>
A glob pattern. Files with names matching this pattern are excluded from being transferred. Only used when copying directories. Can be specified multiple times, if any of the patterns match the file will be excluded. If the pattern includes a / then it will match against the full path, not just the filename. In such patterns you can use /**/ to match zero or more directories. For example, to exclude a directory and everything under it use **/directory_name. See the detailed syntax https://github.com/bmatcuk/doublestar#patterns for how wildcards match.
--symlink-strategy <SYMLINK_STRATEGY>
Control what happens if the specified path is a symlink. The default is to preserve the symlink, re-creating it on the remote machine. Setting this to resolve will cause the symlink to be followed and its target used as the file/directory to copy. The value of keep-path is the same as resolve except that the remote file path is derived from the symlink's path instead of the path of the symlink's target. Note that this option does not apply to symlinks encountered while recursively copying directories, those are always preserved. Default: preserve Choices: keep-path, preserve, resolve
--dest <DEST>
The destination on the remote host to copy to. Relative paths are resolved relative to HOME on the remote host. When this option is not specified, the local file path is used as the remote destination (with the HOME directory getting automatically replaced by the remote HOME). Note that environment variables and ~ are not expanded.

COPYING TERMINFO FILES MANUALLY

Sometimes, the ssh kitten can fail, or maybe you dont like to use it. In such cases, the terminfo files can be copied over manually to a server with the following one liner:

infocmp -a xterm-kitty | ssh myserver tic -x -o \~/.terminfo /dev/stdin

If you are behind a proxy (like Balabit) that prevents this, or you are SSHing into macOS where the tic does not support reading from STDIN, you must redirect the first command to a file, copy that to the server and run tic manually. If you connect to a server, embedded, or Android system that doesn't have tic, copy over your local file terminfo to the other system as ~/.terminfo/x/xterm-kitty.

If the server is running a relatively modern Linux distribution and you have root access to it, you could simply install the kitty-terminfo package on the server to make the terminfo files available.

Really, the correct solution for this is to convince the OpenSSH maintainers to have ssh do this automatically, if possible, when connecting to a server, so that all terminals work transparently.

If the server is running FreeBSD, or another system that relies on termcap rather than terminfo, you will need to convert the terminfo file on your local machine by running (on local machine with kitty):

infocmp -CrT0 xterm-kitty

The output of this command is the termcap description, which should be appended to /usr/share/misc/termcap on the remote server. Then run the following command to apply your change (on the server):

cap_mkdb /usr/share/misc/termcap
