KILL(3P) Manual de Programador POSIX KILL(3P)

PRÓLOGO

Esta página del manual es parte del Manual del Programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

kill — enviar una señal a un proceso o a un grupo de procesos

SINOPSIS

#include <signal.h>
int kill(pid_t pid, int sig);

DESCRIPCIÓN

La función kill() envía una señal a un proceso o a un grupo de procesos especificados por pid. La señal a enviar se especifica por sig y es una de la lista dada en <signal.h> o 0. Si sig es 0 (la señal nula), se realiza la comprobación de errores pero en realidad no se envía ninguna señal. La señal nula puede usarse para comprobar la validez de pid.

Para que un proceso tenga permiso para enviar una señal a un proceso designado por pid, a menos que el proceso emisor tenga privilegios adecuados, el ID de usuario real o efectivo del proceso emisor deberá coincidir con el ID de usuario real o el ID de usuario guardado del proceso receptor.

Si pid es mayor que 0, sig se enviará al proceso cuyo ID de proceso es igual a pid.

Si pid es 0, sig se enviará a todos los procesos (excluyendo un conjunto no especificado de procesos del sistema) cuyo ID de grupo de procesos sea igual al ID de grupo de procesos del emisor, y para los cuales el proceso tenga permiso para enviar una señal.

Si pid es -1, sig se enviará a todos los procesos (excluyendo un conjunto no especificado de procesos del sistema) para los cuales el proceso tenga permiso para enviar esa señal.

Si pid es negativo, pero no -1, sig se enviará a todos los procesos (excluyendo un conjunto no especificado de procesos del sistema) cuyo ID de grupo de procesos sea igual al valor absoluto de pid, y para los cuales el proceso tenga permiso para enviar una señal.

Si el valor de pid provoca que sig se genere para el proceso emisor, y si sig no está bloqueada para el hilo que llama, y si ningún otro hilo tiene sig desbloqueada o está esperando en una función sigwait() para sig, se entregará sig o al menos una señal pendiente no bloqueada al proceso emisor antes de que kill() retorne.

Las pruebas de ID de usuario descritas anteriormente no se aplicarán al enviar SIGCONT a un proceso que sea miembro de la misma sesión que el proceso emisor.

Una implementación que proporcione controles de seguridad ampliados puede imponer restricciones adicionales definidas por la implementación en el envío de señales, incluida la señal nula. En particular, el sistema puede negar la existencia de algunos o todos los procesos especificados por pid.

La función kill() tiene éxito si el proceso tiene permiso para enviar sig a cualquiera de los procesos especificados por pid. Si kill() falla, no se enviará ninguna señal.

VALOR DE RETORNO

Al completarse con éxito, se devolverá 0. De lo contrario, se devolverá -1 y errno se establecerá para indicar el error.

ERRORES

La función kill() fallará si:

EINVAL
El valor del argumento sig es un número de señal inválido o no soportado.
EPERM
El proceso no tiene permiso para enviar la señal a ningún proceso receptor.
ESRCH
No se puede encontrar ningún proceso o grupo de procesos que corresponda al especificado por pid.

JUSTIFICACIÓN

Las semánticas para la comprobación de permisos para kill() diferían entre System V y la mayoría de las otras implementaciones, como Version 7 o 4.3 BSD. Las semánticas elegidas para este volumen de POSIX.1‐2017 coinciden con System V. Específicamente, un proceso set-user-ID no puede protegerse contra señales (o al menos contra SIGKILL) a menos que cambie su ID de usuario real. Esta elección permite al usuario que inicia una aplicación enviarle señales incluso si cambia su ID de usuario efectivo. Las otras semánticas otorgan más poder a una aplicación que desea protegerse del usuario que la ejecutó.

Algunas implementaciones proporcionan extensiones semánticas a la función kill() cuando el valor absoluto de pid es mayor que algún valor máximo, o de otro modo especial. Los valores negativos son una bandera para kill(). Dado que la mayoría de las implementaciones devuelven [ESRCH] en este caso, este comportamiento no se incluye en este volumen de POSIX.1‐2017, aunque una implementación que cumpla los estándares podría proporcionar tal extensión.

Los procesos no especificados a los que no se puede enviar una señal pueden incluir al planificador o a init.

Inicialmente hubo una fuerte opinión de especificar que, si pid especifica que se envíe una señal al proceso que llama y esa señal no está bloqueada, esa señal se entregaría antes de que kill() retornara. Esto permitiría a un proceso llamar a kill() y tener la garantía de que la llamada nunca retorna. Sin embargo, las implementaciones históricas que solo proporcionan la función signal() hacen solo la garantía más débil en este volumen de POSIX.1‐2017, porque solo entregan una señal cada vez que un proceso entra en el kernel. Las modificaciones a tales implementaciones para admitir la función sigaction() generalmente requieren la entrada al kernel después del retorno de una función de captura de señales, para restaurar la máscara de señales. Dichas modificaciones tienen el efecto de satisfacer el requisito más fuerte, al menos cuando se utiliza sigaction(), pero no necesariamente cuando se utiliza signal(). Los desarrolladores del estándar consideraron hacer el requisito más fuerte excepto cuando se usa signal(), pero sintieron que esto sería innecesariamente complejo. Se anima a los implementadores a cumplir el requisito más fuerte siempre que sea posible. En la práctica, el requisito más débil es el mismo, excepto en el raro caso en que dos señales llegan durante una ventana de tiempo muy corta. Este razonamiento también se aplica a un requisito similar para sigprocmask().

En 4.2 BSD, la señal SIGCONT se puede enviar a cualquier proceso descendiente independientemente de las comprobaciones de seguridad del ID de usuario. Esto permite que un shell de control de trabajos continúe un trabajo incluso si los procesos del trabajo han alterado sus IDs de usuario (como en el comando su). En consonancia con la adición del concepto de sesiones, se proporciona una funcionalidad similar al permitir que la señal SIGCONT se envíe a cualquier proceso de la misma sesión independientemente de las comprobaciones de seguridad del ID de usuario. Esto es menos restrictivo que BSD en el sentido de que los procesos ancestros (en la misma sesión) ahora pueden ser el receptor. Es más restrictivo que BSD en el sentido de que los procesos descendientes que forman nuevas sesiones ahora están sujetos a las comprobaciones del ID de usuario. No es necesaria una relajación similar de la seguridad para las otras señales de control de trabajos, ya que esas señales son típicamente enviadas por el controlador del terminal en reconocimiento de caracteres especiales que se teclean; el controlador del terminal omite todas las comprobaciones de seguridad.

En implementaciones seguras, un proceso puede estar restringido de enviar una señal a un proceso que tenga una etiqueta de seguridad diferente. Para evitar que la existencia o no existencia de un proceso se utilice como un canal encubierto, dichos procesos deben parecer inexistentes para el emisor; es decir, se debe devolver [ESRCH], en lugar de [EPERM], si pid se refiere solo a tales procesos.

Las implementaciones históricas variaron en el resultado de una llamada kill() con pid indicando un proceso zombi. Algunos indicaron éxito en tal llamada (sujeto a la comprobación de permisos), mientras que otros dieron un error de [ESRCH]. Dado que la definición de ciclo de vida del proceso en este volumen de POSIX.1‐2017 cubre los procesos zombi, el error [ESRCH] tal como se describe es inapropiado en este caso y las implementaciones que dan este error no cumplen con el estándar.
