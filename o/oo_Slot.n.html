NAME

oo::define, oo::objdefine, oo::Slot - define and configure classes and objects

SYNOPSIS

package require TclOO
oo::define class defScript
oo::define class subcommand arg ?arg ...?
oo::objdefine object defScript
oo::objdefine object subcommand arg ?arg ...?
oo::Slot arg...

CLASS HIERARCHY

oo::object
   → oo::Slot

DESCRIPTION

The oo::define command is used to control the configuration of classes, and the oo::objdefine command is used to control the configuration of objects (including classes as instance objects), with the configuration being applied to the entity named in the class or the object argument. Configuring a class also updates the configuration of all subclasses of the class and all objects that are instances of that class or which mix it in (as modified by any per-instance configuration). The way in which the configuration is done is controlled by either the defScript argument or by the subcommand and following arg arguments; when the second is present, it is exactly as if all the arguments from subcommand onwards are made into a list and that list is used as the defScript argument.

CONFIGURING CLASSES

The following commands are supported in the defScript for oo::define, each of which may also be used in the subcommand form:

constructor argList bodyScript
This creates or updates the constructor for a class. The formal arguments to the constructor (defined using the same format as for the Tcl proc command) will be argList, and the body of the constructor will be bodyScript. When the body of the constructor is evaluated, the current namespace of the constructor will be a namespace that is unique to the object being constructed. Within the constructor, the next command should be used to call the superclasses' constructors. If bodyScript is the empty string, the constructor will be deleted.
deletemethod name ?name ...?
This deletes each of the methods called name from a class. The methods must have previously existed in that class. Does not affect the superclasses of the class, nor does it affect the subclasses or instances of the class (except when they have a call chain through the class being modified) or the class object itself.
destructor bodyScript
This creates or updates the destructor for a class. Destructors take no arguments, and the body of the destructor will be bodyScript. The destructor is called when objects of the class are deleted, and when called will have the object's unique namespace as the current namespace. Destructors should use the next command to call the superclasses' destructors. Note that destructors are not called in all situations (e.g. if the interpreter is destroyed). If bodyScript is the empty string, the destructor will be deleted.
Note that errors during the evaluation of a destructor are not returned to the code that causes the destruction of an object. Instead, they are passed to the currently-defined bgerror handler.
export name ?name ...?
This arranges for each of the named methods, name, to be exported (i.e. usable outside an instance through the instance object's command) by the class being defined. Note that the methods themselves may be actually defined by a superclass; subclass exports override superclass visibility, and may in turn be overridden by instances.
filter ?-slotOperation? ?methodName ...?
This slot (see SLOTTED DEFINITIONS below) sets or updates the list of method names that are used to guard whether method call to instances of the class may be called and what the method's results are. Each methodName names a single filtering method (which may be exposed or not exposed); it is not an error for a non-existent method to be named since they may be defined by subclasses. By default, this slot works by appending.
forward name cmdName ?arg ...?
This creates or updates a forwarded method called name. The method is defined be forwarded to the command called cmdName, with additional arguments, arg etc., added before those arguments specified by the caller of the method. The cmdName will always be resolved using the rules of the invoking objects' namespaces, i.e., when cmdName is not fully-qualified, the command will be searched for in each object's namespace, using the instances' namespace's path, or by looking in the global namespace. The method will be exported if name starts with a lower-case letter, and non-exported otherwise.
method name argList bodyScript
This creates or updates a method that is implemented as a procedure-like script. The name of the method is name, the formal arguments to the method (defined using the same format as for the Tcl proc command) will be argList, and the body of the method will be bodyScript. When the body of the method is evaluated, the current namespace of the method will be a namespace that is unique to the current object. The method will be exported if name starts with a lower-case letter, and non-exported otherwise; this behavior can be overridden via export and unexport.
mixin ?-slotOperation? ?className ...?
This slot (see SLOTTED DEFINITIONS below) sets or updates the list of additional classes that are to be mixed into all the instances of the class being defined. Each className argument names a single class that is to be mixed in. By default, this slot works by replacement.
renamemethod fromName toName
This renames the method called fromName in a class to toName. The method must have previously existed in the class, and toName must not previously refer to a method in that class. Does not affect the superclasses of the class, nor does it affect the subclasses or instances of the class (except when they have a call chain through the class being modified), or the class object itself. Does not change the export status of the method; if it was exported before, it will be afterwards.

This command is equivalent to calling oo::objdefine on the class being defined (see CONFIGURING OBJECTS below for a description of the supported values of subcommand). It follows the same general pattern of argument handling as the oo::define and oo::objdefine commands, and “oo::define cls self subcommand ...” operates identically to “oo::objdefine cls subcommand ...”.

This slot (see SLOTTED DEFINITIONS below) allows the alteration of the superclasses of the class being defined. By default, this slot works by replacement.

SLOTTED DEFINITIONS

Several of the oo::define and oo::objdefine subcommands refer to a concept called a "slotted definition". These commands operate on an internal slot within the class or object being defined. The contents of these slots are lists of names, or other configuration values, which control the behavior of the class or object.

When the defScript form of the commands are used, the slot is configured by evaluating the body of the slot definition, and the value derived from that evaluation is used to configure the slot. The default behavior of the slot is then determined by the operator used.

The following slot operations are supported:

append
The value derived from the evaluation of the slot definition is appended to the existing value of the slot. This is the default behavior for the filter, mixin and superclass slots.
clear
The slot is reset to its default value (which is normally the empty list).
prepend
The value derived from the evaluation of the slot definition is prepended to the existing value of the slot.
replace
The slot is set to the value derived from the evaluation of the slot definition. This is the default behavior for the superclass slot, and is the only supported operation for the mixin slot.
union
The value derived from the evaluation of the slot definition is taken as a union with the existing value of the slot (i.e. elements are added only if they are not already present).

When the subcommand form of the commands are used, the operation is implied by the form of the subcommand.

filter ?-clear? ?-append? ?-prepend? ?-replace? ?-union? ?methodName ...?
Sets or updates the list of filter methods. The default operation is append.
mixin ?-clear? ?-append? ?-prepend? ?-replace? ?-union? ?className ...?
Sets or updates the list of classes to be mixed in. The default operation is replace.
superclass ?-clear? ?-append? ?-prepend? ?-replace? ?-union? ?className ...?
Sets or updates the list of superclasses. The default operation is replace.

OO::SLOT

The oo::Slot command is used to define the syntax and semantics of a new type of slot definition. It is intended for use by developers defining new classes of objects, and is not expected to be used by typical Tcl programmers.

The arguments to oo::Slot are the same as the arguments to the oo::define and oo::objdefine commands that define slots, and are used to define the behavior of those commands.

CONFIGURACIÓN DE CLASES

Los siguientes comandos se admiten en el defScript para oo::define, cada uno de los cuales también puede usarse en la forma de subcomando:

export name ?name ...?
Esto organiza que cada uno de los métodos nombrados, nombre, se exporten (es decir, utilizables fuera de la clase a través del comando de la clase) por la clase que se está definiendo. Tenga en cuenta que los métodos en sí mismos pueden definirse realmente por una superclase; las exportaciones de clase anulan la visibilidad de la superclase y pueden ser anuladas por exportaciones de instancia.
filter ?-slotOperation? ?methodName ...?
Esta ranura (consulte DEFINICIONES CON RANURAS a continuación) establece o actualiza la lista de nombres de métodos que se utilizan para controlar si una llamada de método a la clase puede ser llamada y cuáles son los resultados del método. Cada methodName nombra un único método de filtrado (que puede estar expuesto o no); no es un error que se nombren métodos inexistentes. Tenga en cuenta que la lista real de filtros también depende de los filtros establecidos en las superclases de las que la clase es instancia. Por defecto, esta ranura funciona añadiendo.
method name argList bodyScript
Esto crea, actualiza o elimina un método de clase. El nombre del método es nombre, los argumentos formales para el método (definidos usando el mismo formato que para el comando proc de Tcl) serán argList, y el cuerpo del método será bodyScript. Cuando se evalúa el cuerpo del método, el espacio de nombres actual del método será un espacio de nombres único para la clase. El método se exportará si nombre comienza con una letra minúscula, y no se exportará de lo contrario.
mixin ?-slotOperation? ?className ...?
Esta ranura (consulte DEFINICIONES CON RANURAS a continuación) establece o actualiza una lista por clase de clases adicionales que se mezclarán en la clase. Cada argumento, className, nombra una única clase que se va a mezclar. Por defecto, esta ranura funciona por reemplazo.
renamefilter fromName toName
Esto renombra el filtro llamado fromName en una clase a toName. El filtro debe haber existido previamente en la clase, y toName no debe referirse previamente a un filtro en esa clase. No afecta a las clases de las que la clase es instancia y no puede renombrar en una clase instancia los filtros proporcionados por esas clases. No cambia el estado de exportación del filtro; si se exportó antes, se hará después.
unexport name ?name ...?
Esto organiza que cada uno de los métodos nombrados, nombre, no se exporten (es decir, no utilizables fuera de la clase a través del comando de la clase, sino solo a través del comando my visible en el contexto de cada objeto) por la clase que se está definiendo. Tenga en cuenta que los métodos en sí mismos pueden definirse realmente por una superclase; las no exportaciones de clase anulan la visibilidad de la superclase y pueden ser anuladas por exportaciones de instancia.
variable ?-slotOperation? ?name ...?
Esta ranura (consulte DEFINICIONES CON RANURAS a continuación) organiza que cada una de las variables nombradas esté automáticamente disponible en los métodos, constructor y destructor declarados por la clase que se está definiendo. Cada nombre de variable no debe tener separadores de espacio de nombres y no debe parecer un acceso a un array. Todas las variables estarán realmente presentes en el objeto instancia en el que se ejecuta el método. Tenga en cuenta que las listas de variables declaradas por una superclase o subclase son completamente disjuntas, al igual que las listas de variables declaradas por las instancias; la lista de nombres de variables es solo para métodos (y constructores y destructores) declarados por esta clase. Por defecto, esta ranura funciona añadiendo.

DEFINICIONES CON RANURAS

Algunas de las definiciones configurables de una clase u objeto son definiciones con ranuras. Esto significa que la configuración se implementa mediante un objeto ranura, que es una instancia de la clase oo::Slot, que administra una lista de valores (nombres de clases, nombres de variables, etc.) que comprende el contenido de la ranura.

La clase oo::Slot define tres operaciones (como métodos) que se pueden realizar en la ranura:

slot -append ?member ...?
Esto añade los elementos miembro dados a la definición de la ranura.
slot -clear
Esto establece la definición de la ranura en la lista vacía.
slot -set ?member ...?
Esto reemplaza la definición de la ranura con los elementos miembro dados.

Una consecuencia de esto es que cualquier uso de la operación predeterminada de una ranura donde el primer argumento miembro comience con un guion será un error. Una de las operaciones anteriores debe usarse explícitamente en esas circunstancias.

Solo necesita hacer una instancia de oo::Slot si está definiendo su propia ranura que se comporte como una ranura estándar.

IMPLEMENTACIÓN DE RANURAS

Internamente, los objetos ranura también definen un método --default-operation que se reenvía a la operación predeterminada de la ranura (por lo tanto, para la ranura de clase “variable”, esto se reenvía a “my -append”), y estos métodos que proporcionan la interfaz de implementación:

slot Get
Devuelve una lista que es el contenido actual de la ranura. Este método debe llamarse siempre desde un marco de pila creado por una llamada a oo::define u oo::objdefine.
slot Resolve element
Esto convierte un elemento de la colección con ranuras en su forma resuelta; para un valor simple, podría simplemente devolver el valor, pero para una ranura que contiene referencias a comandos o clases debería convertir esos en sus formas completamente calificadas (para que puedan compararse con string equals): eso podría hacerse reenviando a namespace which o similar.
slot Set elementList
Establece el contenido de la ranura en la lista elementList y devuelve la cadena vacía. Este método debe llamarse siempre desde un marco de pila creado por una llamada a oo::define u oo::objdefine.

La implementación de estos métodos depende de la ranura (y es responsable de acceder a la parte correcta de la definición de la clase u objeto). Las ranuras también tienen un manejador de métodos desconocido para unir todas estas piezas, y ocultan su método destroy para que no se invoque inadvertidamente. Se *recomienda* que cualquier cambio del usuario en el propio mecanismo de ranura se restrinja a la definición de nuevas operaciones cuyos nombres comiencen con un guion.

Tenga en cuenta que no se espera que las instancias de ranura contengan el almacenamiento para la ranura que administran; ese estará en o adjunto a la clase u objeto que administran. Esas instancias deben proporcionar sus propias implementaciones de los métodos Get y Set (y opcionalmente Resolve; eso se configura por defecto como un pase sin hacer nada).

NAME

oo::Slot, oo::objdefine - Define slots and object properties

SYNOPSIS

package require TclOO
oo::object create obj
oo::objdefine obj slot name ?defaultValue?
oo::objdefine obj slot name value
oo::objdefine obj slot name { ... }
oo::objdefine obj slot name -append value
oo::objdefine obj slot name -prepend value
oo::objdefine obj slot name -replace value
oo::objdefine obj slot name -clear
oo::objdefine obj slot name -delete
oo::objdefine obj slot name - { value | { ... } }
oo::objdefine obj slot name - { value | { ... } } - { value | { ... } }
oo::objdefine obj slot name - { value | { ... } } - { value | { ... } } ...

CLASS HIERARCHY

oo::Slot

DESCRIPTION

The oo::Slot command (and the closely related oo::objdefine command) is used to manage named slots, or properties, of an object. Slots are essentially named variables associated with an object instance. They are initialized when the object is created, and can be modified later.

A slot can be defined to hold a single value, or a list of values. Methods are not created when slots are defined; slots are simply data. Slots are accessed directly as instance variables, without requiring explicit method calls.

The oo::objdefine command is used to add slots to an existing object.

SLOTTED DEFINITIONS

The oo::objdefine command can be used to define slots for an object. The syntax is:

oo::objdefine obj slot name ?defaultValue?

This defines a slot named name on object obj. If defaultValue is provided, it is used to initialize the slot. If not provided, the slot is initialized to an empty string.

Slots can also be defined with an initial value using the syntax:

oo::objdefine obj slot name value

This is equivalent to:

oo::objdefine obj slot name value

Or, if the value is a list:

oo::objdefine obj slot name {val1 val2 ...}

To modify an existing slot, use the oo::objdefine command with the desired options:

-append value
Appends value to the slot. If the slot is not already a list, it is converted to a list before appending.
-prepend value
Prepends value to the slot. If the slot is not already a list, it is converted to a list before prepending.
-replace value
Replaces the entire contents of the slot with value.
-clear
Removes all elements from the slot, making it an empty list.
-delete
Removes the slot entirely from the object.

Multiple options can be combined in a single oo::objdefine command. For example:

oo::objdefine obj slot data {a b} -append c -prepend d

This would result in the slot data having the value {d a b c}.

Slots are accessed directly using the object name followed by the slot name, similar to how instance variables are accessed in other object-oriented languages.

Example:

oo::object create myobj
oo::objdefine myobj slot foo "initial value"
oo::objdefine myobj slot bar {a b c}

puts $myobj::foo    → prints "initial value"
puts $myobj::bar    → prints "a b c"

set myobj::foo "new value"
puts $myobj::foo    → prints "new value"

lappend $myobj::bar d
puts $myobj::bar    → prints "a b c d"

Defining a slot with the same name multiple times is an error.

EXAMPLES

Defining a simple slot:

oo::object create person
oo::objdefine person slot name "Alice"
oo::objdefine person slot age 30

puts $person::name  → prints "Alice"
puts $person::age   → prints "30"

Modifying a slot with list operations:

oo::object create listobj
oo::objdefine listobj slot items {}
listobj::items append {apple banana}
puts $listobj::items → prints "apple banana"
oo::objdefine listobj slot items -append cherry
puts $listobj::items → prints "apple banana cherry"
oo::objdefine listobj slot items -prepend date
puts $listobj::items → prints "date apple banana cherry"
oo::objdefine listobj slot items -replace {fig grape}
puts $listobj::items → prints "fig grape"
oo::objdefine listobj slot items -clear
puts $listobj::items → prints ""

Defining a slot with a script block (though this is less common for slots, it's possible):

oo::object create scriptobj
oo::objdefine scriptobj slot greeting {
    set greeting_message "Hello, "
    proc greet {name} {
        global greeting_message
        puts $greeting_message$name
    }
    greet
}
scriptobj::greeting("World") → prints "Hello, World"

Mixing methods and slots:

oo::class create greeter {
    variable greeting "Hello"
    method greet {name} {
        puts "$greeting $name"
    }
}
oo::object create obj1 -superclass greeter
oo::objdefine obj1 slot name "World"

obj1 greet $obj1::name → prints "Hello World"

oo::objdefine obj1 slot greeting "Greetings"
obj1 greet $obj1::name → prints "Greetings World"

Using oo::objdefine to rename a method (this is not its primary purpose, but demonstrates flexibility):

oo::object create o
o sayHello             → error "unknown method sayHello"
oo::objdefine o
    method sayHello {msg} {
        puts $msg
    }
o sayHello "hello world" → prints "hello world"
oo::objdefine o
    renamemethod sayHello bye
o bye "hello world"  → prints "hello world"
o sayHello             → error "unknown method sayHello"

This example shows how additional classes can be mixed into an object. It also shows how mixin is a slot that supports appending:

oo::object create inst
inst m1                  → error "unknown method m1"
inst m2                  → error "unknown method m2"
oo::class create A {
    method m1 {} {
        puts "red brick"
    }
}
oo::objdefine inst {
    mixin A
}
inst m1                  → prints "red brick"
inst m2                  → error "unknown method m2"
oo::class create B {
    method m2 {} {
        puts "blue brick"
    }
}
oo::objdefine inst {
    mixin -append B
}
inst m1                  → prints "red brick"
inst m2                  → prints "blue brick"
