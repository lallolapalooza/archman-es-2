NOMBRE

ovs-vsctl - utilidad para consultar y configurar ovs-vswitchd

SINOPSIS

ovs-vsctl [opciones] -- [opciones] comando [argumentos] [-- [opciones] comando [argumentos]]...

DESCRIPCIÓN

El programa ovs-vsctl configura ovs-vswitchd(8) proporcionando una interfaz de alto nivel a su base de datos de configuración. Consulte ovs-vswitchd.conf.db(5) para obtener documentación completa sobre el esquema de la base de datos.

ovs-vsctl se conecta a un proceso ovsdb-server que mantiene una base de datos de configuración de Open vSwitch. Utilizando esta conexión, consulta y posiblemente aplica cambios a la base de datos, dependiendo de los comandos proporcionados. Luego, si aplicó algún cambio, por defecto espera hasta que ovs-vswitchd haya terminado de reconfigurarse antes de salir. (Si utiliza ovs-vsctl cuando ovs-vswitchd no se está ejecutando, utilice --no-wait.)

ovs-vsctl puede realizar cualquier número de comandos en una sola ejecución, implementados como una única transacción atómica contra la base de datos.

La línea de comandos ovs-vsctl comienza con opciones globales (consulte OPCIONES a continuación para más detalles). Las opciones globales van seguidas de uno o más comandos. Cada comando debe comenzar con -- por sí solo como argumento de línea de comandos, para separarlo de los comandos siguientes. (El -- antes del primer comando es opcional.) El comando en sí comienza con opciones específicas del comando, si las hay, seguidas del nombre del comando y cualquier argumento. Consulte EJEMPLOS a continuación para ver ejemplos de sintaxis.

Compatibilidad con VLAN Bridging de Linux

El programa ovs-vsctl soporta el modelo de un puente implementado por Open vSwitch, en el cual un único puente soporta puertos en múltiples VLAN. En este modelo, cada puerto de un puente es un puerto trunk que potencialmente pasa paquetes etiquetados con cabeceras 802.1Q que designan VLAN, o se le asigna una única VLAN implícita que nunca se etiqueta con una cabecera 802.1Q.

Para compatibilidad con software diseñado para el puente de Linux, ovs-vsctl también soporta un modelo en el que el tráfico asociado con una determinada VLAN 802.1Q se segrega en un puente separado. Una forma especial del comando add-br (ver más abajo) crea un "puente falso" dentro de un puente Open vSwitch para simular este comportamiento. Cuando dicho "puente falso" está activo, ovs-vsctl lo tratará de manera muy similar a un puente separado de su "puente padre", pero la implementación real en Open vSwitch utiliza solo un único puente, con los puertos del puente falso asignados a la VLAN implícita del puente falso del cual son miembros. (Un puente falso para VLAN 0 recibe paquetes que no tienen etiqueta 802.1Q o una etiqueta con VLAN 0.)

OPCIONES

Las siguientes opciones afectan el comportamiento de ovs-vsctl en su conjunto. Algunos comandos individuales también aceptan sus propias opciones, que se dan justo antes del nombre del comando. Si el primer comando en la línea de comandos tiene opciones, entonces esas opciones deben separarse de las opciones globales mediante --.

--db=servidor
Establece servidor como el servidor de base de datos al que ovs-vsctl se conecta para consultar o modificar la configuración. servidor puede ser un método de conexión activo o pasivo de OVSDB, como se describe en ovsdb(7). El valor predeterminado es unix:/run/openvswitch/db.sock.
--no-wait
Impide que ovs-vsctl espere a que ovs-vswitchd se reconfigure según la base de datos modificada. Esta opción debe usarse si ovs-vswitchd no se está ejecutando; de lo contrario, ovs-vsctl no saldrá hasta que ovs-vswitchd se inicie.
Esta opción no tiene efecto si los comandos especificados no modifican la base de datos.
--no-syslog
Por defecto, ovs-vsctl registra sus argumentos y los detalles de cualquier cambio que realice en el registro del sistema. Esta opción deshabilita este registro.
Esta opción es equivalente a --verbose=vsctl:syslog:warn.
--oneline
Modifica el formato de salida para que la salida de cada comando se imprima en una sola línea. Los caracteres de nueva línea que de otro modo separarían líneas se imprimen como \n, y cualquier instancia de \ que de otro modo aparecería en la salida se duplica. Imprime una línea en blanco por cada comando que no tenga salida. Esta opción no afecta el formato de la salida de los comandos list o find; consulte Opciones de Formato de Tabla a continuación.
--dry-run
Impide que ovs-vsctl modifique realmente la base de datos.
-t segundos

--timeout=segundos
Por defecto, o con un valor de segundos de 0, ovs-vsctl espera para siempre una respuesta de la base de datos. Esta opción limita el tiempo de ejecución a aproximadamente segundos segundos. Si expira el tiempo de espera, ovs-vsctl saldrá con una señal SIGALRM. (Normalmente, un tiempo de espera solo ocurriría si la base de datos no se puede contactar o si el sistema está sobrecargado.)
--retry
Sin esta opción, si ovs-vsctl se conecta externamente al servidor de la base de datos (el valor predeterminado), entonces ovs-vsctl intentará conectarse una vez y saldrá con un error si la conexión falla (lo que generalmente significa que ovsdb-server no se está ejecutando).
Con esta opción, o si --db especifica que ovs-vsctl debe escuchar una conexión entrante del servidor de la base de datos, entonces ovs-vsctl esperará indefinidamente una conexión a la base de datos.
Independientemente de esta configuración, --timeout siempre limita cuánto tiempo esperará ovs-vsctl.

Opciones de Formato de Tabla

Estas opciones controlan el formato de la salida de los comandos list y find.

-f formato

--format=formato
Establece el tipo de formato de tabla. Los siguientes tipos de formato están disponibles:
table
Tablas de texto 2D con columnas alineadas.
list (predeterminado)
Una lista con una columna por línea y filas separadas por una línea en blanco.
html
Tablas HTML.
csv
Valores separados por comas según se definen en RFC 4180.
json
Formato JSON según se define en RFC 4627. La salida es una secuencia de objetos JSON, cada uno de los cuales corresponde a una tabla. Cada objeto JSON tiene los siguientes miembros con los valores indicados:
caption
El título de la tabla. Este miembro se omite si la tabla no tiene título.
headings
Un array con un elemento por columna de la tabla. Cada elemento del array es una cadena que indica el encabezado de la columna correspondiente.
data
Un array con un elemento por fila de la tabla. Cada elemento es también un array con un elemento por columna de la tabla. Los elementos de este array de segundo nivel son las celdas que constituyen la tabla. Las celdas que representan datos o tipos de datos de OVSDB se expresan en el formato descrito en la especificación OVSDB; otras celdas simplemente se expresan como cadenas de texto.
-d formato

--data=formato
Establece el formato para las celdas dentro de las tablas de salida a menos que el formato de tabla se establezca en json,

El formato simple con la puntuación eliminada: [] y {} se omiten alrededor de conjuntos, mapas y columnas vacías, los elementos dentro de conjuntos y mapas están separados por espacios, y las cadenas nunca se citan. Este formato puede ser más fácil de analizar para scripts.

Esta opción suprime la fila de encabezado que de otro modo aparecería en la primera fila de la salida de la tabla.

Por defecto, JSON en la salida se imprime de la forma más compacta posible. Esta opción hace que el JSON en la salida se imprima de una manera más legible. Los miembros de objetos y los elementos de matrices se imprimen uno por línea, con indentación.

Equivalente a --format=list --data=bare --no-headings.

Solo para salida de tabla, limita el ancho de cualquier columna en la salida a n columnas. Los datos de celda más largos se truncan para que quepan, según sea necesario. Las columnas siempre son lo suficientemente anchas como para mostrar los nombres de las columnas, si la fila de encabezado se imprime.

Opciones de infraestructura de clave pública

-p privkey.pem

--private-key=privkey.pem
Especifica un archivo PEM que contiene la clave privada utilizada como identidad de ovs-vsctl para las conexiones SSL/TLS salientes.
-c cert.pem

--certificate=cert.pem
Especifica un archivo PEM que contiene un certificado que certifica que la clave privada especificada en -p o --private-key es confiable. El certificado debe estar firmado por la autoridad certificadora (CA) que el par en las conexiones SSL/TLS utilizará para verificarlo.
-C cacert.pem

--ca-cert=cacert.pem
Especifica un archivo PEM que contiene el certificado CA que ovs-vsctl debe utilizar para verificar los certificados que le presentan los pares SSL/TLS. (Este puede ser el mismo certificado que los pares SSL/TLS utilizan para verificar el certificado especificado en -c o --certificate, o puede ser uno diferente, dependiendo del diseño de PKI en uso.)
-C none

--ca-cert=none
Deshabilita la verificación de los certificados presentados por los pares SSL/TLS. Esto introduce un riesgo de seguridad, ya que significa que los certificados no se pueden verificar como los de hosts conocidos y confiables.
--bootstrap-ca-cert=cacert.pem
Cuando cacert.pem existe, esta opción tiene el mismo efecto que -C o --ca-cert. Si no existe, entonces ovs-vsctl intentará obtener el certificado CA del par SSL/TLS en su primera conexión SSL/TLS y lo guardará en el archivo PEM con nombre. Si tiene éxito, inmediatamente cerrará la conexión y se reconectará, y a partir de entonces todas las conexiones SSL/TLS deberán ser autenticadas por un certificado firmado por el certificado CA obtenido de esa manera.
Esta opción expone la conexión SSL/TLS a un ataque de man-in-the-middle al obtener el certificado CA inicial, pero puede ser útil para el arranque.
Esta opción solo es útil si el par SSL/TLS envía su certificado CA como parte de la cadena de certificados SSL/TLS. Los protocolos SSL/TLS no requieren que el servidor envíe el certificado CA.
Esta opción es mutuamente excluyente con -C y --ca-cert.
--peer-ca-cert=peer-cacert.pem
Especifica un archivo PEM que contiene uno o más certificados adicionales para enviar a los pares SSL/TLS. peer-cacert.pem debe ser el certificado CA utilizado para firmar el propio certificado de ovs-vsctl, es decir, el certificado especificado en -c o --certificate. Si el certificado de ovs-vsctl es autofirmado, entonces --certificate y --peer-ca-cert deben especificar el mismo archivo.
Esta opción no es útil en operación normal, ya que el par SSL/TLS ya debe tener el certificado CA para que el par tenga alguna confianza en la identidad de ovs-vsctl. Sin embargo, esto ofrece una forma para que una nueva instalación arranque el certificado CA en su primera conexión SSL/TLS.
-v[spec]

--verbose=[spec]
Establece los niveles de registro. Sin ningún spec, establece el nivel de registro para cada módulo y destino a dbg. De lo contrario, spec es una lista de palabras separadas por espacios, comas o dos puntos, hasta una de cada categoría a continuación:
  • Un nombre de módulo válido, como se muestra en el comando vlog/list en ovs-appctl(8), limita el cambio de nivel de registro al especificado módulo.
  • syslog, console o file, para limitar el cambio de nivel de registro solo al registro del sistema, a la consola o a un archivo, respectivamente. (Si se especifica --detach, ovs-vsctl cierra sus descriptores de archivo estándar, por lo que el registro en la consola no tendrá ningún efecto.)
En la plataforma Windows, syslog se acepta como una palabra y solo es útil junto con la opción --syslog-target (la palabra no tiene ningún efecto de lo contrario).
•
off, emer, err, warn, info o dbg, para controlar el nivel de registro. Se registrarán los mensajes de la gravedad dada o superior, y se filtrarán los mensajes de menor gravedad. off filtra todos los mensajes. Consulte ovs-appctl(8) para obtener una definición de cada nivel de registro.
La capitalización no es significativa dentro de spec.
Independientemente de los niveles de registro establecidos para file, el registro en un archivo no se realizará a menos que también se especifique --log-file (ver abajo).
Para compatibilidad con versiones anteriores de OVS, any se acepta como una palabra pero no tiene ningún efecto.
-v

--verbose
Establece el nivel máximo de verbosidad de registro, equivalente a --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Establece el patrón de registro para destination a pattern. Consulte ovs-appctl(8) para una descripción de la sintaxis válida para pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Establece la instalación RFC5424 del mensaje de registro. facility puede ser uno de kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 o local7. Si esta opción no se especifica, se utiliza daemon como predeterminado para el syslog del sistema local y se utiliza local0 al enviar un mensaje al destino proporcionado a través de la opción --syslog-target.
--log-file[=file]
Habilita el registro en un archivo. Si se especifica file, entonces se utiliza como el nombre exacto del archivo de registro. El nombre de archivo de registro predeterminado que se utiliza si se omite file es /var/log/openvswitch/ovs-vsctl.log.
--syslog-target=host:port
Envía mensajes de syslog al puerto UDP port en host, además del syslog del sistema. El host debe ser una dirección IP numérica, no un nombre de host.
--syslog-method=method
Especifica el method mediante el cual se deben enviar los mensajes de syslog al demonio de syslog. Se admiten las siguientes formas:
  • libc, utiliza la función syslog() de libc. La desventaja de usar esta opción es que libc añade un prefijo fijo a cada mensaje antes de que se envíe realmente al demonio de syslog a través del socket de dominio UNIX /dev/log.
  • unix:file, utiliza directamente el socket de dominio UNIX. Es posible especificar un formato de mensaje arbitrario con esta opción. Sin embargo, rsyslogd 8.9 y versiones anteriores utilizan de todos modos una función de análisis codificada que limita el uso del socket de dominio UNIX. Si desea utilizar un formato de mensaje arbitrario con versiones anteriores de rsyslogd, utilice en su lugar un socket UDP a la dirección IP de localhost.
  • udp:ip:port, utiliza un socket UDP. Con este método es posible utilizar un formato de mensaje arbitrario también con versiones anteriores de rsyslogd. Al enviar mensajes de syslog a través de un socket UDP, se deben tener en cuenta precauciones adicionales, por ejemplo, el demonio de syslog debe configurarse para escuchar en el puerto UDP especificado, las reglas de iptables accidentales podrían interferir con el tráfico de syslog local y existen algunas consideraciones de seguridad que se aplican a los sockets UDP, pero no se aplican a los sockets de dominio UNIX.
  • null, descarta todos los mensajes registrados en syslog.

Comandos de Interfaz

Estos comandos examinan las interfaces conectadas a un bridge de Open vSwitch. Estos comandos tratan un puerto bond como una colección de dos o más interfaces, en lugar de como un solo puerto.

list-ifaces bridge
Lista todas las interfaces dentro de bridge en la salida estándar, una por línea. El puerto local bridge no se incluye en la lista.
iface-to-br iface
Imprime el nombre del bridge que contiene iface en la salida estándar.

Configuración de Fallo del Controlador

Cuando se configura un controlador, este es, por lo general, el responsable de configurar todos los flujos en el switch. Por lo tanto, si la conexión al controlador falla, no se pueden establecer nuevas conexiones de red. Si la conexión al controlador permanece inactiva el tiempo suficiente, no podrán pasar paquetes a través del switch.

Si el valor es standalone, o si ninguna de estas configuraciones está establecida, ovs-vswitchd asumirá la responsabilidad de configurar los flujos cuando no se haya recibido ningún mensaje del controlador durante tres veces el intervalo de sondeo de inactividad. En este modo, ovs-vswitchd hace que el datapath actúe como un switch de aprendizaje de MAC ordinario. ovs-vswitchd continuará intentando conectarse al controlador en segundo plano y, cuando la conexión tenga éxito, dejará de operar en modo independiente.

Si esta opción se establece en secure, ovs-vswitchd no configurará flujos por sí mismo cuando falle la conexión del controlador.

del-fail-mode bridge
Elimina el modo de fallo configurado.
set-fail-mode bridgestandalone|secure
Establece el modo de fallo configurado.

Arranque de Certificado CA

Normalmente, todos los archivos nombrados en la configuración SSL/TLS deben existir cuando ovs-vswitchd arranca. Sin embargo, si el archivo cert-ca no existe y se proporciona la opción --bootstrap, entonces ovs-vswitchd intentará obtener el certificado CA del controlador en su primera conexión SSL/TLS y lo guardará en el archivo PEM especificado. Si tiene éxito, abandonará inmediatamente la conexión y se reconectará, y a partir de entonces todas las conexiones SSL/TLS deberán ser autenticadas por un certificado firmado por el certificado CA así obtenido.

Comandos de Base de Datos

Estos comandos consultan y modifican el contenido de las tablas de ovsdb. Son una ligera abstracción de la interfaz de ovsdb y, como tal, operan a un nivel más bajo que otros comandos de ovs-vsctl.

Identificación de Tablas, Registros y Columnas

Cada uno de estos comandos tiene un parámetro table para identificar una tabla dentro de la base de datos. Muchos de ellos también toman un parámetro record que identifica un registro particular dentro de una tabla. El parámetro record puede ser el UUID de un registro, y muchas tablas ofrecen formas adicionales de identificar registros. Algunos comandos también toman parámetros column que identifican un campo particular dentro de los registros de una tabla.

Para obtener una lista de tablas y sus columnas, consulte ovs-vswitchd.conf.db(5) o consulte la lista de tablas de la opción --help.

Los nombres de los registros deben especificarse completos y con la capitalización correcta, excepto que los UUIDs pueden abreviarse a sus primeros 4 (o más) dígitos hexadecimales, siempre que sean únicos dentro de la tabla. Los nombres de tablas y columnas no distinguen entre mayúsculas y minúsculas, y los caracteres - y _ se tratan indistintamente. Se aceptan abreviaturas únicas de nombres de tablas y columnas, por ejemplo, net o n es suficiente para identificar la tabla NetFlow.

Valores de la Base de Datos

Cada columna en la base de datos acepta un tipo fijo de datos. Los tipos básicos actualmente definidos, y sus representaciones, son:

integer
Un entero decimal en el rango de -2**63 a 2**63-1, inclusive.
real
Un número de punto flotante.
Boolean
Verdadero o falso, escrito true o false, respectivamente.
string
Una cadena de texto Unicode arbitraria, excepto que los bytes nulos no están permitidos. Las comillas son opcionales para la mayoría de las cadenas que comienzan con una letra del alfabeto inglés o un guión bajo y consisten únicamente en letras, guiones bajos, guiones y puntos. Sin embargo, true y false y las cadenas que coinciden con la sintaxis de los UUIDs (ver abajo) deben estar entre comillas dobles para distinguirlas de otros tipos básicos. Cuando se usan comillas dobles, la sintaxis es la de las cadenas en JSON, por ejemplo, las barras invertidas pueden usarse para escapar caracteres especiales. La cadena vacía debe representarse como un par de comillas dobles ("").
UUID
Un identificador universalmente único al estilo de RFC 4122, por ejemplo, f81d4fae-7dec-11d0-a765-00a0c91e6bf6, o un nombre @nombre definido por un comando get o create dentro de la misma invocación de ovs-vsctl.

Múltiples valores en una sola columna pueden separarse por espacios o una sola coma. Cuando hay múltiples valores, los duplicados no están permitidos y el orden no es importante. Por el contrario, algunas columnas de la base de datos pueden tener un conjunto vacío de valores, representado como [], y los corchetes pueden encerrar opcionalmente otros conjuntos no vacíos o valores individuales también. Para una columna que acepta un conjunto de enteros, los comandos de la base de datos aceptan un rango. Un rango se representa por dos enteros separados por -. Un rango es inclusivo. Un rango tiene un tamaño máximo de 4096 elementos. Si se necesitan más elementos, se pueden especificar en rangos separados.

Algunas columnas de la base de datos son "mapas" de pares clave-valor, donde la clave y el valor son cada uno algún tipo fijo de base de datos. Estos se especifican en el formato clave=valor, donde clave y valor siguen la sintaxis del tipo de clave y tipo de valor de la columna, respectivamente. Cuando hay múltiples pares (separados por espacios o una coma), las claves duplicadas no están permitidas y, de nuevo, el orden no es importante. Los valores duplicados están permitidos. Un mapa vacío se representa como {}. Los corchetes pueden encerrar opcionalmente mapas no vacíos también (pero use comillas para evitar que el shell expanda other-config={0=x,1=y} a other-config=0=x other-config=1=y, lo que puede no tener el efecto deseado).

Sintaxis de los Comandos de Base de Datos
[--if-exists] [--columns=columna[,columna]...] list tabla [registro]...
Lista los datos en cada registro especificado. Si no se especifican registros, lista todos los registros en tabla.
Si se especifica --columns, solo se listan las columnas solicitadas, en el orden especificado. De lo contrario, se listan todas las columnas, en orden alfabético por nombre de columna.
Sin --if-exists, es un error si algún registro especificado no existe. Con --if-exists, el comando ignora cualquier registro que no exista, sin producir ninguna salida.
[--columns=columna[,columna]...] find tabla [columna[:clave]=valor]...
Lista los datos en cada registro de tabla cuyo columna sea igual a valor o, si se especifica clave, cuyo columna contenga una clave con el valor especificado. Los siguientes operadores pueden usarse donde = está escrito en el resumen de sintaxis:
= != < > <= >=
Selecciona registros en los que columna[:clave] es igual, no es igual, es menor que, es mayor que, es menor o igual que, o es mayor o igual que valor, respectivamente.
Considere columna[:clave] y valor como conjuntos de elementos. Los conjuntos idénticos se consideran iguales. De lo contrario, si los conjuntos tienen un número diferente de elementos, el conjunto con más elementos se considera mayor. De lo contrario, considere un elemento de cada conjunto par a par, en orden ascendente dentro de cada conjunto. El primer par que difiere determina el resultado. (Para una columna que contiene pares clave-valor, primero se comparan todas las claves, y los valores solo se consideran si los dos conjuntos contienen claves idénticas)..
{=} {!=}
Prueba igualdad o desigualdad de conjuntos, respectivamente.
{<=}
Selecciona registros en los que columna[:clave] es un subconjunto de valor. Por ejemplo, flood-vlans{<=}1,2 selecciona registros en los que la columna flood-vlans es el conjunto vacío o contiene 1 o 2 o ambos.
{<}
Selecciona registros en los que columna[:clave] es un subconjunto propio de valor. Por ejemplo, flood-vlans{<}1,2 selecciona registros en los que la columna flood-vlans es el conjunto vacío o contiene 1 o 2 pero no ambos.
{>=} {>}
Igual que {<=} y {<}, respectivamente, excepto que la relación está invertida. Por ejemplo, flood-vlans{>=}1,2 selecciona registros en los que la columna flood-vlans contiene tanto 1 como 2.

Los siguientes operadores están disponibles solo en Open vSwitch 2.16 y posteriores:

{in}
Selecciona registros en los que cada elemento en columna[:clave] también está en valor. (Esto es lo mismo que {<=}).
{not-in}
Selecciona registros en los que cada elemento en columna[:clave] no está en valor.
Para operadores aritméticos (= != < > <= >=), cuando se especifica clave pero la columna de un registro particular no contiene clave, el registro se omite de los resultados. Por lo tanto, la condición other-config:mtu!=1500 coincide con registros que tienen una clave mtu cuyo valor no es 1500, pero no con aquellos que carecen de una clave mtu.

column[!][=|~|<|<=|>|>=]value
Matches rows where column equals value. The operators can be varied, as follows:
!
Negates the operator. For example, != means not equal.
=
Equal.
~
Regular expression match. The value is a POSIX regular expression.
<, <=, >, >=
Less than, less than or equal to, greater than, or greater than or equal to, respectively. These operators work on numbers, strings, and IP addresses.

If the type of a column is not specified but a particular record's column does not contain key, the comparison is done against an empty set. Caution (ovs-vsctl as example)
Records in the Open vSwitch database are significant only when they can be reached directly or indirectly from the Open_vSwitch table. Except for records in the QoS or Queue tables, records that are not reachable from the Open_vSwitch table are automatically deleted from the database. This deletion happens immediately, without waiting for additional ovs-vsctl commands or other database activity. Thus, a create command must generally be accompanied by additional commands within the same ovs-vsctl invocation to add a chain of references to the newly created record from the top-level Open_vSwitch record. The EXAMPLES section gives some examples that show how to do this.

Deletes all records from the table.
Caution (ovs-vsctl as example)
The destroy command is only useful for records in the QoS or Queue tables. Records in other tables are automatically deleted from the database when they become unreachable from the Open_vSwitch table. This means that deleting the last reference to a record is sufficient for deleting the record itself. For records in these tables, destroy is silently ignored. See the EXAMPLES section below for more information.

Usually wait-until should be placed at the beginning of a set of ovs-vsctl commands. For example, wait-until bridge br0 -- get bridge br0 datapath_id waits until a bridge named br0 is created, then prints its datapath_id column, whereas get bridge br0 datapath_id -- wait-until bridge br0 will abort if no bridge named br0 exists when ovs-vsctl initially connects to the database.

EJEMPLOS

Create a new bridge named br0 and add port eth0 to it:

ovs-vsctl add-br br0
ovs-vsctl add-port br0 eth0

Alternatively, perform both operations in a single atomic transaction:

ovs-vsctl add-br br0 -- add-port br0 eth0

Delete bridge br0, reporting an error if it does not exist:

ovs-vsctl del-br br0

Delete bridge br0 if it exists:

ovs-vsctl --if-exists del-br br0

Set the qos column of the Port record for eth0 to point to a new QoS record, which in turn points with its queue 0 to a new Queue record:

ovs-vsctl -- set port eth0 qos=@newqos -- --id=@newqos create qos type=linux-htb other-config:max-rate=1000000 queues:0=@newqueue -- --id=@newqueue create queue other-config:min-rate=1000000 other-config:max-rate=1000000

-- --id=@eth1 get Port eth1 \
-- --id=@eth2 get Port eth2 \
-- --id=@m create Mirror name=mymirror select-dst-port=@eth0,@eth1 select-src-port=@eth0,@eth1 output-port=@eth2

Remove the mirror created above from br0, which also destroys the Mirror record (since it is now unreferenced):

ovs-vsctl -- --id=@rec get Mirror mymirror \
-- remove Bridge br0 mirrors @rec

The following simpler command also works:

ovs-vsctl clear Bridge br0 mirrors

Calidad de Servicio (QoS)

Create a linux-htb QoS record that points to a few queues and use it on eth0 and eth1:

ovs-vsctl -- set Port eth0 qos=@newqos \
-- set Port eth1 qos=@newqos \
-- --id=@newqos create QoS type=linux-htb other-config:max-rate=1000000000 queues=0=@q0,1=@q1 \
-- --id=@q0 create Queue other-config:min-rate=100000000 other-config:max-rate=100000000 \
-- --id=@q1 create Queue other-config:min-rate=500000000

Deconfigure the QoS record above from eth1 only:

ovs-vsctl clear Port eth1 qos

To deconfigure the QoS record from both eth0 and eth1 and then delete the QoS record (which must be done explicitly because unreferenced QoS records are not automatically destroyed):

ovs-vsctl -- destroy QoS eth0 -- clear Port eth0 qos -- clear Port eth1 qos

(This command will leave two unreferenced Queue records in the database. To delete them, use "ovs-vsctl list Queue" to find their UUIDs, then "ovs-vsctl destroy Queue uuid1 uuid2" to destroy each of them or use "ovs-vsctl -- --all destroy Queue" to delete all records.)

Monitorización de Conectividad

Monitor connectivity to a remote maintenance point on eth0.

ovs-vsctl set Interface eth0 cfm_mpid=1

Deconfigure connectivity monitoring from above:

ovs-vsctl clear Interface eth0 cfm_mpid

NetFlow

Configure bridge br0 to send NetFlow records to UDP port 5566 on host 192.168.0.34, with an active timeout of 30 seconds:

ovs-vsctl -- set Bridge br0 netflow=@nf \
-- --id=@nf create NetFlow targets=\"192.168.0.34:5566\" active-timeout=30

Update the NetFlow configuration created by the previous command to instead use an active timeout of 60 seconds:

ovs-vsctl set NetFlow br0 active_timeout=60

Deconfigure the NetFlow settings from br0, which also destroys the NetFlow record (since it is now unreferenced):

ovs-vsctl clear Bridge br0 netflow

sFlow

Configure bridge br0 to send sFlow records to a collector on 10.0.0.1 at port 6343, using eth1's IP address as the source, with specific sampling parameters:

ovs-vsctl -- --id=@s create sFlow agent=eth1 target=\"10.0.0.1:6343\" header=128 sampling=64 polling=10 \
-- set Bridge br0 sflow=@s

Deconfigure sFlow from br0, which also destroys the sFlow record (since it is now unreferenced):

ovs-vsctl -- clear Bridge br0 sflow

IPFIX

Configure bridge br0 to send one IPFIX flow record per packet sample to UDP port 4739 on host 192.168.0.34, with Observation Domain ID 123 and Observation Point ID 456, a flow cache active timeout of 1 minute (60 seconds), maximum flow cache size of 13 flows, and flows sampled on output port with tunnel info(sampling on input and output port is enabled by default if not disabled) :

ovs-vsctl -- set Bridge br0 ipfix=@i \
-- --id=@i create IPFIX targets=\"192.168.0.34:4739\" obs_domain_id=123 obs_point_id=456 cache_active_timeout=60 cache_max_flows=13 \
other_config:enable-input-sampling=false other_config:enable-tunnel-sampling=true

Deconfigure the IPFIX settings from br0, which also destroys the IPFIX record (since it is now unreferenced):

ovs-vsctl clear Bridge br0 ipfix

802.1D Protocolo de Árbol de Expansión (STP)

Configure bridge br0 to participate in an 802.1D spanning tree:

ovs-vsctl set Bridge br0 stp_enable=true

Set the bridge priority of br0 to 0x7800:

ovs-vsctl set Bridge br0 other_config:stp-priority=0x7800

Set the path cost of port eth0 to 10:

ovs-vsctl set Port eth0 other_config:stp-path-cost=10

Deconfigure STP from above:

ovs-vsctl set Bridge br0 stp_enable=false

Reenvío de Multidifusión (Multicast Snooping)

Configure bridge br0 to enable multicast snooping:

ovs-vsctl set Bridge br0 mcast_snooping_enable=true

Set the multicast snooping aging time br0 to 300 seconds:

ovs-vsctl set Bridge br0 other_config:mcast-snooping-aging-time=300

Set the multicast snooping table size br0 to 2048 entries:

ovs-vsctl set Bridge br0 other_config:mcast-snooping-table-size=2048

Disable flooding of unregistered multicast packets to all ports. When set to true, the switch will send unregistered multicast packets only to ports connected to multicast routers. When it is set to false, the switch will send them to all ports. This command disables the flood of unregistered packets on bridge br0.

ovs-vsctl set Bridge br0 other_config:mcast-snooping-disable-flood-unregistered=true

Enable flooding of multicast packets (except Reports) on a specific port.

ovs-vsctl set Port eth1 other_config:mcast-snooping-flood=true

Enable flooding of Reports on a specific port.

ovs-vsctl set Port eth1 other_config:mcast-snooping-flood-reports=true

Deconfigure multicasting snooping from above:

ovs-vsctl set Bridge br0 mcast_snooping_enable=false

802.1D-2004 Protocolo de Árbol de Expansión Rápido (RSTP)

Configure bridge br0 to participate in an 802.1D-2004 Rapid Spanning Tree:

ovs-vsctl set Bridge br0 rstp_enable=true

Set the bridge address of br0 to 00:aa:aa:aa:aa:aa :

ovs-vsctl set Bridge br0 other_config:rstp-address=00:aa:aa:aa:aa:aa

Set the bridge priority of br0 to 0x7000. The value must be specified in decimal notation and should be a multiple of 4096 (if not, it is rounded down to the nearest multiple of 4096). The default priority value is 0x800 (32768).

ovs-vsctl set Bridge br0 other_config:rstp-priority=28672

Set the bridge ageing time of br0 to 1000 s. The ageing time value should be between 10 s and 1000000 s. The default value is 300 s.

ovs-vsctl set Bridge br0 other_config:rstp-ageing-time=1000

Set the bridge force protocol version of br0 to 0. The force protocol version has two acceptable values: 0 (STP compatibility mode) and 2 (normal operation).

ovs-vsctl set Bridge br0 other_config:rstp-force-protocol-version=0

Set the bridge max age of br0 to 10 s. The max age value should be between 6 s and 40 s. The default value is 20 s.

ovs-vsctl set Bridge br0 other_config:rstp-max-age=10

Set the bridge forward delay of br0 to 15 s. This value should be between 4 s and 30 s. The default value is 15 s.

ovs-vsctl set Bridge br0 other_config:rstp-forward-delay=15

Set the bridge transmit hold count of br0 to 7 s. This value should be between 1 s and 10 s. The default value is 6 s.

ovs-vsctl set Bridge br0 other_config:rstp-transmit-hold-count=7

Enable RSTP on the Port eth0:

ovs-vsctl set Port eth0 other_config:rstp-enable=true

Disable RSTP on the Port eth0:

ovs-vsctl set Port eth0 other_config:rstp-enable=false

Set the priority of port eth0 to 32. The value must be specified in decimal notation and should be a multiple of 16 (if not, it is rounded down to the nearest multiple of 16). The default priority value is 0x80 (128).

ovs-vsctl set Port eth0 other_config:rstp-port-priority=32

Establecer el número de puerto del puerto eth0 a 3:

ovs-vsctl set Port eth0 other_config:rstp-port-num=3

Establecer el costo de ruta del puerto eth0 a 150:

ovs-vsctl set Port eth0 other_config:rstp-path-cost=150

Establecer el valor de borde administrativo del puerto eth0:

ovs-vsctl set Port eth0 other_config:rstp-port-admin-edge=true

Establecer el valor de borde automático del puerto eth0:

ovs-vsctl set Port eth0 other_config:rstp-port-auto-edge=true

Establecer el valor de MAC de punto a punto administrativo del puerto eth0. Los valores aceptables son 0 (no es punto a punto), 1 (punto a punto, el valor predeterminado) o 2 (detección automática). El modo de detección automática no está implementado actualmente y el valor 2 tiene el mismo efecto que 0 (no es punto a punto).

ovs-vsctl set Port eth0 other_config:rstp-admin-p2p-mac=1

Establecer el valor de estado del puerto administrativo del puerto eth0. true es el valor predeterminado.

ovs-vsctl set Port eth0 other_config:rstp-admin-port-state=false

Establecer el valor mcheck del puerto eth0:

ovs-vsctl set Port eth0 other_config:rstp-port-mcheck=true

Desconfigurar RSTP de lo anterior:

ovs-vsctl set Bridge br0 rstp_enable=false

Versión de OpenFlow

Configurar el puente br0 para que admita las versiones de OpenFlow 1.0, 1.2 y 1.3:

ovs-vsctl set bridge br0 protocols=OpenFlow10,OpenFlow12,OpenFlow13

Configuración de tabla de flujo

Hacer que la tabla de flujo 0 en el puente br0 se niegue a aceptar más de 100 flujos:

ovs-vsctl -- --id=@ft create Flow_Table flow_limit=100 overflow_policy=refuse -- set Bridge br0 flow_tables=0=@ft

Hacer que la tabla de flujo 0 en el puente br0 elimine flujos, con equidad basada en el puerto de entrada coincidente, cuando haya más de 100:

ovs-vsctl -- --id=@ft create Flow_Table flow_limit=100 overflow_policy=evict groups='"NXM_OF_IN_PORT[]"' -- set Bridge br0 flow_tables:0=@ft
