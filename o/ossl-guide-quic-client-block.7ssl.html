NOMBRE

ossl-guide-quic-client-block - Guía de OpenSSL: Escribiendo un cliente QUIC bloqueante simple

EJEMPLO DE CLIENTE QUIC BLOQUEANTE SIMPLE

Esta página presentará varios ejemplos de código fuente que demuestran cómo escribir una aplicación cliente QUIC bloqueante simple que se conecta a un servidor, le envía una solicitud HTTP/1.0 y lee la respuesta. Tenga en cuenta que HTTP/1.0 sobre QUIC no es estándar y no será compatible con servidores del mundo real. Esto es solo para fines de demostración.

Suponemos que ya tiene OpenSSL instalado en su sistema; que ya tiene una comprensión fundamental de los conceptos de OpenSSL, TLS y QUIC (ver ossl-guide-libraries-introduction(7), ossl-guide-tls-introduction(7) y ossl-guide-quic-introduction(7)); y que sabe cómo escribir y compilar código C y enlazarlo contra las bibliotecas libcrypto y libssl que proporciona OpenSSL. También asume que tiene una comprensión básica de UDP/IP y sockets. El código de ejemplo que construiremos en este tutorial modificará el ejemplo de cliente TLS bloqueante que se cubre en ossl-guide-tls-client-block(7). Solo se discutirán las diferencias entre ese cliente y este, por lo que también asumimos que ha revisado y comprendido ese tutorial.

Para este tutorial, nuestro cliente utilizará un único stream QUIC. Un tutorial posterior discutirá cómo escribir un cliente multi-stream (ver ossl-guide-quic-multi-stream(7)).

El código fuente completo para este cliente QUIC bloqueante de ejemplo está disponible en el directorio "demos/guide" de la distribución fuente de OpenSSL en el archivo "quic-client-block.c". También está disponible en línea en https://github.com/openssl/openssl/blob/master/demos/guide/quic-client-block.c.

Creación de los objetos SSL_CTX y SSL

En el tutorial de TLS (ossl-guide-tls-client-block(7)) creamos un objeto SSL_CTX para nuestro cliente y lo usamos para crear un objeto SSL para representar la conexión TLS. Una conexión QUIC funciona exactamente de la misma manera. Primero creamos un objeto SSL_CTX y luego lo usamos para crear un objeto SSL para representar la conexión QUIC.

Al igual que en el ejemplo de TLS, el primer paso es crear un objeto SSL_CTX para nuestro cliente. Esto se hace de la misma manera que antes, excepto que usamos un "método" diferente. OpenSSL ofrece dos métodos de cliente QUIC diferentes, es decir, OSSL_QUIC_client_method(3) y OSSL_QUIC_client_thread_method(3).

El primero es el equivalente de TLS_client_method(3) pero para el protocolo QUIC. El segundo es el mismo, pero además creará un hilo secundario para manejar eventos basados en el tiempo (conocido como "modo asistido por hilo", ver ossl-guide-quic-introduction(7)). Para este tutorial, utilizaremos OSSL_QUIC_client_method(3) porque no dejaremos inactiva la conexión QUIC en nuestra aplicación y, por lo tanto, el modo asistido por hilo no es necesario.

/*
 * Crea un SSL_CTX que podemos usar para crear objetos SSL a partir de él.
 * Queremos un SSL_CTX para crear clientes, así que usamos OSSL_QUIC_client_method()
 * aquí.
 */
ctx = SSL_CTX_new(OSSL_QUIC_client_method());
if (ctx == NULL) {
    printf("Failed to create the SSL_CTX\n");
    goto end;
}

Los otros pasos de configuración que aplicamos al SSL_CTX para TLS también se aplican a QUIC, excepto la restricción de las versiones de TLS que estamos dispuestos a aceptar. La implementación del protocolo QUIC en OpenSSL actualmente solo admite TLSv1.3. No es necesario llamar a SSL_CTX_set_min_proto_version(3) o SSL_CTX_set_max_proto_version(3) en una aplicación QUIC de OpenSSL, y cualquier llamada de este tipo será ignorada.

Una vez creado el SSL_CTX, el objeto SSL se construye de la misma manera que para la aplicación TLS.

Creación del socket y BIO

Una diferencia importante entre TLS y QUIC es el protocolo de transporte subyacente. TLS usa TCP mientras que QUIC usa UDP. La forma en que se crea el socket QUIC en nuestro código de ejemplo es muy similar a la de TLS. Utilizamos las funciones auxiliares BIO_lookup_ex(3) y BIO_socket(3) como hicimos en el tutorial anterior, excepto que pasamos SOCK_DGRAM como argumento para indicar UDP (en lugar de SOCK_STREAM para TCP).

/*
 * Busca la información de la dirección IP del servidor.
 */
if (!BIO_lookup_ex(hostname, port, BIO_LOOKUP_CLIENT, family, SOCK_DGRAM, 0,
                   &res))
    return NULL;
/*
 * Itera a través de todas las direcciones posibles para el servidor y encuentra una
 * a la que podamos conectarnos.
 */
for (ai = res; ai != NULL; ai = BIO_ADDRINFO_next(ai)) {
    /*
     * Crea un socket TCP. Podríamos usar igualmente llamadas que no sean de OpenSSL
     * como "socket" aquí para estas y las funciones posteriores de conexión y cierre.
     * Pero por razones de portabilidad y también para obtener
     * errores en la pila de OpenSSL en caso de fallo, usamos
     * las versiones de OpenSSL de estas funciones.
     */
    sock = BIO_socket(BIO_ADDRINFO_family(ai), SOCK_DGRAM, 0, 0);
    if (sock == -1)
        continue;
    /* Conecta el socket a la dirección del servidor */
    if (!BIO_connect(sock, BIO_ADDRINFO_address(ai), 0)) {
        BIO_closesocket(sock);
        sock = -1;
        continue;
    }
    /* Configúralo en modo no bloqueante */
    if (!BIO_socket_nbio(sock, 1)) {
        BIO_closesocket(sock);
        sock = -1;
        continue;
    }
    break;
}
if (sock != -1) {
    *peer_addr = BIO_ADDR_dup(BIO_ADDRINFO_address(ai));
    if (*peer_addr == NULL) {
        BIO_closesocket(sock);
        return NULL;
    }
}
/* Libera los recursos de información de direcciones que asignamos anteriormente */
BIO_ADDRINFO_free(res);

Puede notar un par de otras diferencias entre este código y la versión que utilizamos para TLS.

Primero, configuramos el socket en modo no bloqueante. Esto siempre debe hacerse para una aplicación QUIC de OpenSSL. Esto puede ser sorprendente considerando que estamos tratando de escribir un cliente bloqueante. A pesar de esto, el objeto SSL seguirá teniendo un comportamiento bloqueante. Ver ossl-guide-quic-introduction(7) para más información sobre esto.

Segundo, tomamos nota de la dirección IP del par al que nos conectamos. Almacenamos esa información. La necesitaremos más tarde.

Ver BIO_lookup_ex(3), BIO_socket(3), BIO_connect(3), BIO_closesocket(3), BIO_ADDRINFO_next(3), BIO_ADDRINFO_address(3), BIO_ADDRINFO_free(3) y BIO_ADDR_dup(3) para más información sobre las funciones utilizadas aquí. En el código de ejemplo anterior, las variables hostname y port son cadenas, por ejemplo, "www.example.com" y "443".

Al igual que con nuestro cliente TLS, una vez que se ha creado y conectado el socket, debemos asociarlo con un objeto BIO:

BIO *bio;
/* Crea un BIO para envolver el socket */
bio = BIO_new(BIO_s_datagram());
if (bio == NULL) {
    BIO_closesocket(sock);
    return NULL;
}
/*
 * Asocia el BIO recién creado con el socket subyacente. Al
 * pasar BIO_CLOSE aquí, el socket se cerrará automáticamente cuando
 * el BIO sea liberado. Alternativamente, puede usar BIO_NOCLOSE, en cuyo
 * caso debe cerrar el socket explícitamente cuando ya no sea necesario.
 */
BIO_set_fd(bio, sock, BIO_CLOSE);

Observe el uso de BIO_s_datagram(3) aquí en lugar de BIO_s_socket(3) que usamos para nuestro cliente TLS. Esto se debe nuevamente al hecho de que QUIC usa UDP en lugar de TCP para su capa de transporte. Ver BIO_new(3), BIO_s_datagram(3) y BIO_set_fd(3) para

Estableciendo el nombre de host del servidor

Al igual que en el tutorial de TLS, necesitamos establecer el nombre de host del servidor tanto para SNI (Server Name Indication) como para fines de validación de certificados. Los pasos para esto son idénticos a los del tutorial de TLS y no se repetirán aquí.

Estableciendo el ALPN

ALPN (Application-Layer Protocol Negotiation) es una característica de TLS que permite a la aplicación negociar qué protocolo se utilizará sobre la conexión. Por ejemplo, si pretende usar HTTP/3 sobre la conexión, el valor ALPN para eso es "h3" (ver https://www.iana.org/assignments/tls-extensiontype-values/tls-extensiontype-values.xml#alpn-protocol-ids). OpenSSL proporciona la capacidad para que un cliente especifique el ALPN a utilizar a través de la función SSL_set_alpn_protos(3). Esto es opcional para un cliente TLS, por lo que nuestro cliente simple que desarrollamos en ossl-guide-tls-client-block(7) no lo utilizó. Sin embargo, QUIC exige que el handshake TLS utilizado para establecer una conexión QUIC deba usar ALPN.

unsigned char alpn[] = { 8, 'h', 't', 't', 'p', '/', '1', '.', '0' };
/* ¡SSL_set_alpn_protos devuelve 0 para éxito! */
if (SSL_set_alpn_protos(ssl, alpn, sizeof(alpn)) != 0) {
    printf("Fallo al establecer el ALPN para la conexión\n");
    goto end;
}

El ALPN se especifica utilizando un array de caracteres sin signo precedido por su longitud (no es una cadena terminada en NUL). Nuestra demo original de cliente bloqueante TLS utilizaba HTTP/1.0. Usaremos el mismo para este ejemplo. A diferencia de la mayoría de las funciones de OpenSSL, SSL_set_alpn_protos(3) devuelve cero para el éxito y un valor distinto de cero para el fallo.

Estableciendo la dirección del par

Una aplicación QUIC de OpenSSL debe especificar la dirección de destino del servidor al que se está conectando. En "Creando el socket y BIO" arriba, guardamos esa dirección para uso futuro. Ahora necesitamos usarla a través de la función SSL_set1_initial_peer_addr(3).

/* Establecer la dirección IP del par remoto */
if (!SSL_set1_initial_peer_addr(ssl, peer_addr)) {
    printf("Fallo al establecer la dirección inicial del par\n");
    goto end;
}

Tenga en cuenta que necesitaremos liberar el valor de peer_addr que asignamos previamente a través de BIO_ADDR_dup(3):

BIO_ADDR_free(peer_addr);

El handshake y la transferencia de datos de la aplicación

Una vez completada la configuración inicial del objeto SSL, realizamos el handshake a través de SSL_connect(3) de la misma manera que lo hicimos para el cliente TLS, por lo que no lo repetiremos aquí.

También podemos realizar la transferencia de datos utilizando un stream QUIC predeterminado que se asocia automáticamente con el objeto SSL para nosotros. Podemos transmitir datos usando SSL_write_ex(3) y recibir datos usando SSL_read_ex(3) de la misma manera que para TLS. La principal diferencia es que tenemos que tener en cuenta los fallos de forma un poco diferente. Con QUIC, el stream puede ser reiniciado por el par (lo cual es fatal para ese stream), pero la conexión subyacente en sí misma puede seguir estando operativa.

Primero, escribimos toda la solicitud al stream. También debemos asegurarnos de indicar al servidor que hemos terminado de escribir. Esto se puede hacer pasando el flag SSL_WRITE_FLAG_CONCLUDE a SSL_write_ex2(3) o llamando a SSL_stream_conclude(3). Dado que la primera forma es más eficiente, elegimos hacerlo así.

/* Escribir una solicitud HTTP GET al par */
if (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
    printf("Fallo al escribir el inicio de la solicitud HTTP\n");
    goto end;
}
if (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
    printf("Fallo al escribir el nombre de host en la solicitud HTTP\n");
    goto end;
}
if (!SSL_write_ex2(ssl, request_end, strlen(request_end),
    SSL_WRITE_FLAG_CONCLUDE, &written)) {
    printf("Fallo al escribir el final de la solicitud HTTP\n");
    goto end;
}

Luego, leemos la respuesta del servidor.

/*
 * Obtener hasta sizeof(buf) bytes de la respuesta. Seguimos leyendo hasta
 * que el servidor cierre la conexión.
 */
while (SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
    /*
    * OpenSSL no garantiza que los datos devueltos sean una cadena o
    * que estén terminados en NUL, por lo que usamos fwrite() para escribir
    * el número exacto de bytes que leímos. Los datos podrían no ser
    * imprimibles o tener caracteres NUL en medio. Para este ejemplo simple,
    * lo imprimiremos en stdout de todos modos.
    */
    fwrite(buf, 1, readbytes, stdout);
}
/* En caso de que la respuesta no terminara con una nueva línea, la añadimos ahora */
printf("\n");
/*
 * Comprobar si terminamos el bucle while anterior normalmente o como resultado
 * de un error. El argumento 0 a SSL_get_error() es el código de retorno que
 * recibimos de la llamada SSL_read_ex(). Debe ser 0 para llegar aquí. La
 * finalización normal se indica con SSL_ERROR_ZERO_RETURN. En términos de
 * QUIC, esto significa que el par ha enviado FIN en el stream para indicar
 * que no se enviarán más datos.
 */
switch (SSL_get_error(ssl, 0)) {
case SSL_ERROR_ZERO_RETURN:
    /* Finalización normal del stream */
    break;
case SSL_ERROR_SSL:
    /*
     * Ocurrió algún error fatal en el stream. Esto podría deberse a un reinicio
     * del stream o a algún fallo en la conexión subyacente.
     */
    switch (SSL_get_stream_read_state(ssl)) {
    case SSL_STREAM_STATE_RESET_REMOTE:
        printf("Ocurrió un reinicio del stream\n");
        /* El stream se ha reiniciado, pero la conexión sigue estando operativa. */
        break;
    case SSL_STREAM_STATE_CONN_CLOSED:
        printf("Conexión cerrada\n");
        /* La conexión ya está cerrada. Omitir SSL_shutdown() */
        goto end;
    default:
        printf("Fallo desconocido del stream\n");
        break;
    }
    break;
default:
    /* Ocurrió algún otro error inesperado */
    printf ("Fallo al leer los datos restantes\n");
    break;
}

En el ejemplo de código anterior, puede ver que SSL_ERROR_SSL indica un error fatal del stream. Podemos usar SSL_get_stream_read_state(3) para determinar si el stream ha sido reiniciado o si ha ocurrido algún otro error fatal.

Cerrando la conexión

En el tutorial de TLS, sabíamos que el servidor había terminado de enviar datos porque SSL_read_ex(3) devolvía 0, y SSL_get_error(3) devolvía SSL_ERROR_ZERO_RETURN. Lo mismo ocurre con QUIC, excepto que SSL_ERROR_ZERO_RETURN debe interpretarse de forma ligeramente diferente. Con TLS, sabíamos que esto significaba que el servidor había enviado una alerta de "close_notify". No se enviarán más datos desde el servidor en esa conexión.

Con QUIC, significa que el servidor ha indicado "FIN" en el stream, lo que significa que ya no enviará más datos en ese stream. Sin embargo, esto solo nos da información sobre el stream en sí y no nos dice nada sobre la conexión subyacente. Todavía se podrían enviar más datos desde el servidor en algún otro stream. Además, aunque el servidor no enviará más datos al cliente, esto no impide que el cliente envíe más datos al servidor.

En este tutorial, una vez que hayamos terminado de leer datos del servidor en el único stream que estamos utilizando, cerraremos la conexión. Como antes, lo hacemos a través de la función SSL_shutdown(3). Este ejemplo para QUIC es muy similar a la versión de TLS. Sin embargo, la función SSL_shutdown(3) deberá llamarse más de una vez:

/*
 * Llamar repetidamente a SSL_shutdown() hasta que la conexión esté completamente
 * cerrada.
 */
do {
    ret = SSL_shutdown(ssl);
    if (ret < 0) {
        printf("Error al cerrar: %d\n", ret);
        goto end;
    }
} while (ret != 1);

El proceso de cierre consta de dos etapas. En la primera etapa, esperamos hasta que todos los datos que hemos almacenado en búfer para enviar en cualquier stream se hayan enviado y confirmado correctamente por el par, y luego enviamos un CONNECTION_CLOSE al par para indicar que la conexión ya no es utilizable. Esto cierra inmediatamente la conexión y no se pueden enviar ni recibir más datos. SSL_shutdown(3) devuelve 0 una vez completada la primera etapa.

En la segunda etapa, la conexión entra en un estado de "cierre". Los datos de la aplicación no se pueden enviar ni recibir en este estado, pero los paquetes que llegan tarde del par se manejarán adecuadamente. Una vez que esta etapa se completa con éxito, SSL_shutdown(3) devolverá 1 para indicar el éxito.
