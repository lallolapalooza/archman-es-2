NOMBRE

os-release, initrd-release, extension-release - Identificación del sistema operativo

SINOPSIS

/etc/os-release
/usr/lib/os-release
/etc/initrd-release
/usr/lib/extension-release.d/extension-release.IMAGEN

DESCRIPCIÓN

Los archivos /etc/os-release y /usr/lib/os-release contienen datos de identificación del sistema operativo.

El formato de os-release es una lista separada por saltos de línea de asignaciones de variables compatibles con el shell, similar a las variables de entorno. Es posible cargar la configuración desde scripts de shell de Bourne, sin embargo, más allá de las meras asignaciones de variables, no se admiten características del shell (lo que significa que la expansión de variables no es compatible explícitamente), lo que permite a las aplicaciones leer el archivo sin implementar un motor de ejecución compatible con el shell. Los valores de asignación de variables deben ir entre comillas dobles o simples si contienen espacios, puntos y comas u otros caracteres especiales fuera de A-Z, a-z, 0-9. (Las asignaciones que no contengan estos caracteres especiales también pueden ir entre comillas, pero esto es opcional). Los caracteres especiales del shell ("$", comillas, barra invertida, acento grave) deben escaparse con barras invertidas, siguiendo el estilo del shell. Todas las cadenas deben estar codificadas en UTF-8 y no deben usarse caracteres no imprimibles. No se admite la concatenación de múltiples cadenas citadas individualmente. Las líneas que comienzan con "#" se tratan como comentarios. Se permiten y se ignoran las líneas en blanco.

El archivo /etc/os-release tiene precedencia sobre /usr/lib/os-release. Las aplicaciones deben comprobar el primero y utilizar exclusivamente sus datos si existe, y solo recurrir a /usr/lib/os-release si este falta. Las aplicaciones no deben combinar los datos de ambos archivos. /usr/lib/os-release es el lugar recomendado para almacenar la información de la versión del SO como parte de los árboles de proveedores. /etc/os-release debe ser un enlace simbólico relativo a /usr/lib/os-release, para proporcionar compatibilidad con aplicaciones que solo buscan en /etc/. Un enlace simbólico relativo en lugar de uno absoluto es necesario para evitar romper el enlace en un entorno chroot o initrd.

os-release contiene datos definidos por el proveedor del sistema operativo y, en general, el administrador no debería cambiarlos.

Dado que este archivo solo codifica nombres e identificadores, no debe ser localizado.

Los archivos /etc/os-release y /usr/lib/os-release pueden ser enlaces simbólicos a otros archivos, pero es importante que el archivo esté disponible desde el inicio del arranque y, por lo tanto, debe ubicarse en el sistema de archivos raíz.

os-release no debe contener claves repetidas. Sin embargo, los lectores deben elegir las entradas que aparecen más adelante en el archivo en caso de repeticiones, de manera similar a como lo haría un shell al cargar el archivo. Un lector puede advertir sobre entradas repetidas.

Para una justificación más detallada de os-release, consulte el Anuncio de /etc/os-release[1].

/etc/initrd-release

En el initrd[2] y exitrd, /etc/initrd-release juega el mismo papel que os-release en el sistema principal. Además, la presencia de ese archivo significa que el sistema se encuentra en la fase initrd/exitrd. /etc/os-release debe ser un enlace simbólico a /etc/initrd-release (o viceversa), para que los programas que solo buscan /etc/os-release (como se describe anteriormente) funcionen correctamente.

El resto de este documento que habla sobre os-release debe entenderse que también se aplica a initrd-release.

/usr/lib/extension-release.d/extension-release.IMAGEN

/usr/lib/extension-release.d/extension-release.IMAGEN desempeña el mismo papel para las imágenes de extensión que os-release para el sistema principal, y sigue la sintaxis y las reglas descritas en la página Servicios Portátiles[3]. El propósito de este archivo es identificar la extensión y permitir que el sistema operativo verifique que la imagen de extensión coincide con el SO base. Esto se implementa típicamente verificando que la opción ID= de la extensión coincida con la opción ID= del host o esté incluida en la opción ID_LIKE= del host, y que exista SYSEXT_LEVEL= y coincida, o si no está presente, que exista VERSION_ID= y coincida. Esto garantiza la compatibilidad ABI/API entre las capas y previene la fusión de una imagen incompatible en una superposición.

Para identificar la propia imagen de extensión, los mismos campos definidos a continuación pueden agregarse al archivo extension-release con un prefijo SYSEXT_ (para desambiguar de los campos utilizados para hacer coincidir la imagen base). Por ejemplo: SYSEXT_ID=myext, SYSEXT_VERSION_ID=1.2.3.

En el nombre de archivo extension-release.IMAGEN, la parte IMAGEN debe coincidir exactamente con el nombre del archivo de la imagen que contiene, sin el sufijo. En caso de que no sea posible garantizar que el nombre del archivo de una imagen sea estable y no cambie entre las fases de compilación y despliegue, es posible relajar esta verificación: si solo hay un archivo cuyo nombre coincide con "extension-release.*" en este directorio, y el archivo está etiquetado con un xattr(7) llamado user.extension-release.strict con la cadena "0", se utilizará en su lugar.

El resto de este documento que habla sobre os-release debe entenderse que también se aplica a extension-release.

OPCIONES

Los siguientes parámetros de identificación del SO pueden establecerse usando os-release:

Información general que identifica el sistema operativo

NAME=

Una cadena que identifica el sistema operativo, sin un componente de versión, y adecuada para presentar al usuario. Si no se establece, se puede usar un valor predeterminado de "NAME=Linux".

Ejemplos: "NAME=Fedora", "NAME="Debian GNU/Linux"".

ID=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0-9, a-z, ".", "_" y "-") que identifica el sistema operativo, excluyendo cualquier información de versión y adecuada para ser procesada por scripts o utilizada en nombres de archivo generados. Si no se establece, se puede usar un valor predeterminado de "ID=linux". Tenga en cuenta que, aunque esta cadena no puede incluir caracteres que requieran comillas en el shell, las comillas se pueden utilizar de todos modos.

Ejemplos: "ID=fedora", "ID=debian".

ID_LIKE=

Una lista separada por espacios de identificadores del sistema operativo en la misma sintaxis que la configuración ID=. Debe listar identificadores de sistemas operativos que están estrechamente relacionados con el sistema operativo local en lo que respecta a la gestión de paquetes y las interfaces de programación, por ejemplo, listar uno o más identificadores de SO de los que el SO local es un derivado. Un SO generalmente solo debe listar otros identificadores de SO de los que es derivado, y no SO de los que se derivan, aunque son posibles relaciones simétricas. Los scripts de compilación y similares deben verificar esta variable si necesitan identificar el sistema operativo local y el valor de ID= no es reconocido. Los sistemas operativos deben listarse en orden de cuán estrechamente se relaciona el sistema operativo local con los listados, comenzando por el más cercano. Este campo es opcional.

Ejemplos: para un sistema operativo con "ID=centos", una asignación de "ID_LIKE="rhel fedora"" sería apropiada. Para un sistema operativo con "ID=ubuntu", una asignación de "ID_LIKE=debian" es apropiada.

PRETTY_NAME=

Un nombre de sistema operativo bonito en un formato adecuado para su presentación al usuario. Puede contener o no un nombre en clave de lanzamiento o una versión del SO de algún tipo, según corresponda. Si no se establece, se puede usar un valor predeterminado de "PRETTY_NAME="Linux""

Ejemplo: "PRETTY_NAME="Fedora 17 (Beefy Miracle)"".

CPE_NAME=

Un nombre CPE para el sistema operativo, en sintaxis de enlace URI, siguiendo la Especificación de Enumeración Común de Plataformas[4] propuesta por el NIST. Este campo es opcional.

Ejemplo: "CPE_N

VARIANT=

Una cadena que identifica una variante o edición específica del sistema operativo, adecuada para su presentación al usuario. Este campo puede utilizarse para informar al usuario que la configuración de este sistema está sujeta a un conjunto específico de reglas divergentes o a una configuración predeterminada. Este campo es opcional y puede no estar implementado en todos los sistemas.

Ejemplos: "VARIANT="Server Edition"", "VARIANT="Smart Refrigerator Edition"".

Nota: este campo es solo para fines de visualización. El campo VARIANT_ID debe utilizarse para tomar decisiones programáticas.

Añadido en la versión 220.

VARIANT_ID=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica una variante o edición específica del sistema operativo. Otros paquetes pueden interpretarla para determinar una configuración predeterminada divergente. Este campo es opcional y puede no estar implementado en todos los sistemas.

Ejemplos: "VARIANT_ID=server", "VARIANT_ID=embedded".

Añadido en la versión 220.

Información sobre la versión del sistema operativo

VERSION=

Una cadena que identifica la versión del sistema operativo, excluyendo cualquier información del nombre del sistema operativo, que posiblemente incluya un nombre en clave de lanzamiento, y adecuada para su presentación al usuario. Este campo es opcional.

Ejemplos: "VERSION=17", "VERSION="17 (Beefy Miracle)"".

VERSION_ID=

Una cadena en minúsculas (principalmente numérica, sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica la versión del sistema operativo, excluyendo cualquier información del nombre del sistema operativo o nombre en clave de lanzamiento, y adecuada para su procesamiento por scripts o su uso en nombres de archivo generados. Este campo es opcional.

Ejemplos: "VERSION_ID=17", "VERSION_ID=11.04".

VERSION_CODENAME=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica el nombre en clave de lanzamiento del sistema operativo, excluyendo cualquier información del nombre del sistema operativo o versión de lanzamiento, y adecuada para su procesamiento por scripts o su uso en nombres de archivo generados. Este campo es opcional y puede no estar implementado en todos los sistemas.

Ejemplos: "VERSION_CODENAME=buster", "VERSION_CODENAME=xenial".

Añadido en la versión 231.

BUILD_ID=

Una cadena que identifica de forma única la imagen del sistema utilizada originalmente como base de instalación. En la mayoría de los casos, VERSION_ID o IMAGE_ID+IMAGE_VERSION se actualizan cuando se reemplaza toda la imagen del sistema durante una actualización. BUILD_ID puede utilizarse en distribuciones donde la versión original de la imagen de instalación es importante: VERSION_ID cambiaría durante las actualizaciones incrementales del sistema, pero BUILD_ID no. Este campo es opcional.

Ejemplos: "BUILD_ID="2013-03-20.3"", "BUILD_ID=201303203".

Añadido en la versión 200.

IMAGE_ID=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica una imagen específica del sistema operativo. Está pensada para entornos donde las imágenes del sistema operativo se preparan, construyen, envían y actualizan como imágenes completas y consistentes del sistema operativo. Este campo es opcional y puede no estar implementado en todos los sistemas, en particular en aquellos que no se gestionan mediante imágenes sino que se ensamblan y actualizan a partir de paquetes individuales y en el sistema local.

Ejemplos: "IMAGE_ID=vendorx-cashier-system", "IMAGE_ID=netbook-image".

Añadido en la versión 249.

IMAGE_VERSION=

Una cadena en minúsculas (principalmente numérica, sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica la versión de la imagen del sistema operativo. Está pensada para ser utilizada junto con IMAGE_ID descrito anteriormente, para distinguir diferentes versiones de la misma imagen.

Ejemplos: "IMAGE_VERSION=33", "IMAGE_VERSION=47.1rc1".

Añadido en la versión 249.

RELEASE_TYPE=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0-9, a-z, ".", "_" y "-") que describe qué tipo de lanzamiento es esta versión del sistema operativo. Los valores conocidos son:
•"stable" es para lanzamientos normales del sistema, adecuados para uso en producción. En general, los lanzamientos estables quedan fuera de soporte poco después de que salga el siguiente lanzamiento estable principal, aunque esto puede no ser así si, por ejemplo, una distribución adopta un modelo de lanzamiento continuo y sigue siendo apta para producción. Ejemplos incluyen Fedora 40, Ubuntu 23.10, OpenSUSE Tumbleweed y Arch Linux.
•"lts" es para lanzamientos de soporte a largo plazo del sistema, adecuados para uso en producción y con soporte durante un período de tiempo extendido. En general, los lanzamientos LTS continúan recibiendo soporte incluso si hay disponibles versiones principales más nuevas de la distribución. Ejemplos incluyen Ubuntu 24.04, Debian 12 Bookworm y RHEL 9.4.
•"development" es para versiones inestables del sistema, inadecuadas para uso en producción, como lanzamientos alfa, beta o inestables continuos. Ejemplos incluyen Fedora Rawhide, Debian Testing, Fedora 40 Beta y GNOME OS Nightly.
•"experiment" es para compilaciones experimentales del sistema, creadas específicamente para probar alguna característica en desarrollo. Esto está destinado a ser utilizado en combinación con EXPERIMENT=.

Si no está establecido, o tiene un valor desconocido, se asume que el lanzamiento es "stable".

Ejemplos: "RELEASE_TYPE=development", "RELEASE_TYPE=lts".

Añadido en la versión 257.

Para resumir: si las actualizaciones de la imagen se construyen y envían como unidades completas, IMAGE_ID+IMAGE_VERSION es la mejor opción. De lo contrario, si las actualizaciones reemplazan completamente el contenido instalado previamente, como en una distribución binaria típica, VERSION_ID debe utilizarse para identificar las versiones principales del sistema operativo. BUILD_ID puede utilizarse en lugar de o además de VERSION_ID cuando la versión original de la imagen del sistema es importante.

Información de presentación y enlaces

HOME_URL=, DOCUMENTATION_URL=, SUPPORT_URL=, BUG_REPORT_URL=, PRIVACY_POLICY_URL=

Enlaces a recursos en Internet relacionados con el sistema operativo. HOME_URL= debe referirse a la página de inicio del sistema operativo o, alternativamente, a alguna página de inicio de la versión específica del sistema operativo. DOCUMENTATION_URL= debe referirse a la página principal de documentación de este sistema operativo. SUPPORT_URL= debe referirse a la página principal de soporte del sistema operativo, si existe. Esto está destinado principalmente a sistemas operativos cuyos proveedores ofrecen soporte. BUG_REPORT_URL= debe referirse a la página principal de reporte de errores del sistema operativo, si existe. Esto está destinado principalmente a sistemas operativos que dependen de QA comunitaria. PRIVACY_POLICY_URL= debe referirse a la página principal de política de privacidad del sistema operativo, si existe. Estas configuraciones son opcionales, y es común proporcionar solo algunas de ellas. Estas URL están destinadas a ser expuestas en las interfaces de usuario de "Acerca de este sistema" detrás de enlaces con leyendas como "Acerca de este Sistema Operativo", "Obtener Soporte", "Reportar un Error" o "Política de Privacidad". Los valores deben estar en formato RFC3986[5], y deben ser URL de tipo "http:" o "https:", y posiblemente "mailto:" o "tel:". Solo se listará una URL en cada configuración. Si se necesitan referenciar varios recursos, se recomienda proporcionar una página de destino en línea que enlace todos los recursos disponibles.

Ejemplos: "HOME_URL="https://fedoraproject.org/"", "BUG_REPORT_URL="https://bugzilla.redhat.com/"".

SUPPORT_END=

La fecha en la que finaliza el soporte para esta versión del SO. (Qué significa exactamente "falta de soporte" varía entre los proveedores, pero en general los usuarios deben asumir que no se proporcionarán actualizaciones, incluidas las correcciones de seguridad). El valor es una fecha en formato ISO 8601 "YYYY-MM-DD", y especifica el primer día en el que el soporte no se proporciona.

Por ejemplo, "SUPPORT_END=2001-01-01" significa que el sistema tuvo soporte hasta el final del último día del milenio anterior.

Añadido en la versión 252.

LOGO=

Una cadena que especifica el nombre de un icono según se define en la Especificación de Temas de Iconos de freedesktop.org[6]. Esto puede ser utilizado por aplicaciones gráficas para mostrar el logotipo de un sistema operativo o distribuidor. Este campo es opcional y puede que no esté necesariamente implementado en todos los sistemas.

Ejemplos: "LOGO=fedora-logo", "LOGO=distributor-logo-opensuse"

Añadido en la versión 240.

ANSI_COLOR=

Un color de presentación sugerido al mostrar el nombre del SO en la consola. Esto debe especificarse como una cadena adecuada para su inclusión en el código de escape ANSI/ECMA-48 ESC [ m para establecer la representación gráfica. Este campo es opcional.

Ejemplos: "ANSI_COLOR="0;31"" para rojo, "ANSI_COLOR="1;34"" para azul claro, o "ANSI_COLOR="0;38;2;60;110;180"" para azul Fedora.

VENDOR_NAME=

El nombre del proveedor del SO. Este es el nombre de la organización o empresa que produce el SO. Este campo es opcional.

Este nombre está destinado a ser expuesto en interfaces de usuario de "Acerca de este sistema" o en interfaces de actualización de software cuando sea necesario para distinguir al proveedor del SO del propio SO. Está destinado a ser legible por humanos.

Ejemplos: "VENDOR_NAME="Fedora Project"" para Fedora Linux, "VENDOR_NAME="Canonical"" para Ubuntu.

Añadido en la versión 254.

VENDOR_URL=

La página de inicio del proveedor del SO. Este campo es opcional. El campo VENDOR_NAME= debe establecerse si este se establece, aunque los clientes deben ser robustos ante la ausencia de cualquiera de los campos.

El valor

lue debe estar en **formato RFC3986**[5], y debe ser URLs de "http:" o "https:". Solo se listará una URL en la configuración.

Ejemplos: "VENDOR_URL="https://fedoraproject.org/"", "VENDOR_URL="https://canonical.com/"" .

Añadido en la versión 254.

EXPERIMENT=

Una descripción presentable por humanos de lo que hace que esta compilación del sistema operativo sea experimental. Este campo es opcional. El campo RELEASE_TYPE debe establecerse en "experiment" si este campo está establecido, de lo contrario los clientes deben ignorar este campo.

Esta descripción está destinada a ser expuesta en el momento de la instalación del sistema o en las interfaces de usuario de "Acerca de este sistema", para advertir al usuario que está instalando/ejecutando una compilación experimental del sistema operativo. Si RELEASE_TYPE es "experiment" pero este campo no está establecido, la interfaz de usuario aún debería advertir al usuario, pero no podrá explicar qué es exactamente experimental en la compilación actual del sistema operativo.

Ejemplos: "EXPERIMENT="Switch to DNF5"" para una compilación experimental de Fedora Linux hecha para probar DNF5, "EXPERIMENT="Port to Apple M3 chip"" para compilaciones experimentales de Asahi Linux portadas al SoC Apple M3, "EXPERIMENT="Mutter !1441: Dynamic triple/double buffering (v4)"" para compilaciones de GNOME OS creadas por el CI de Mutter para la solicitud de fusión !1441.

Añadido en la versión 257.

EXPERIMENT_URL=

La página principal informativa sobre lo que hace que la compilación actual del sistema operativo sea experimental, donde los usuarios pueden aprender más sobre el estado del experimento y potencialmente dejar comentarios. Este campo es opcional. El campo EXPERIMENT= debe establecerse si este lo está, aunque los clientes deben ser robustos ante la posibilidad de que cualquiera de los campos no esté establecido.

El valor debe estar en **formato RFC3986**[5], y debe ser URLs de "http:" o "https:". Solo se listará una URL en la configuración.

Ejemplos, correspondientes a los ejemplos anteriores en EXPERIMENT=: "EXPERIMENT_URL="https://fedoraproject.org/wiki/Changes/SwitchToDnf5"" , "EXPERIMENT_URL="https://github.com/AsahiLinux/docs/wiki/M3-Series-Feature-Support"" , "EXPERIMENT_URL="https://gitlab.gnome.org/GNOME/mutter/-/merge_requests/1441"" .

Añadido en la versión 257.

Valores predeterminados y metadatos a nivel de distribución

DEFAULT_HOSTNAME=

Una cadena que especifica el nombre de host si el archivo hostname(5) no está presente y ninguna otra fuente de configuración especifica el nombre de host. Debe ser una única etiqueta DNS (una cadena compuesta por caracteres en minúsculas del alfabeto ASCII de 7 bits y sin espacios ni puntos, limitada al formato permitido para las etiquetas de nombres de dominio DNS) o una secuencia de tales etiquetas separadas por puntos simples que formen un FQDN DNS válido. El nombre de host no debe exceder los 64 caracteres, lo cual es una limitación de Linux (DNS permite nombres más largos).

Si el carácter de interrogación "?" aparece en el nombre de host, se sustituye automáticamente por un carácter hexadecimal derivado del machine-id(5) cuando se aplica, de forma segura y determinista mediante hash criptográfico. Ejemplo: "foobar-????-????", se expandirá automáticamente a "foobar-92a9-061c" o similar, dependiendo del ID de máquina local.

Consulte org.freedesktop.hostname1(5) para obtener una descripción de cómo systemd-hostnamed.service(8) determina el nombre de host de reserva.

Añadido en la versión 248.

ARCHITECTURE=

Una cadena que especifica para qué arquitectura de CPU requieren los binarios del espacio de usuario. Los identificadores de arquitectura son los mismos que para ConditionArchitecture= descritos en systemd.unit(5). El campo es opcional y solo debe usarse cuando solo se admite una única arquitectura. Puede proporcionar información redundante cuando se usa en una partición GPT con un tipo GUID que ya codifica la arquitectura. Si este no es el caso, la arquitectura debe especificarse, por ejemplo, en una imagen de extensión, para evitar que un host incompatible la cargue.

Añadido en la versión 252.

SYSEXT_LEVEL=

Una cadena en minúsculas (principalmente numérica, sin espacios ni otros caracteres fuera de 0-9, a-z, ".", "_" y "-") que identifica el nivel de soporte de extensiones del sistema operativo, para indicar qué imágenes de extensión son compatibles. Consulte /usr/lib/extension-release.d/extension-release.IMAGE, **initrd**[2] y systemd-sysext(8) para obtener más información.

Ejemplos: "SYSEXT_LEVEL=2", "SYSEXT_LEVEL=15.14".

Añadido en la versión 248.

CONFEXT_LEVEL=

Semánticamente lo mismo que SYSEXT_LEVEL= pero para imágenes confext. Consulte /etc/extension-release.d/extension-release.IMAGE para obtener más información.

Ejemplos: "CONFEXT_LEVEL=2", "CONFEXT_LEVEL=15.14".

Añadido en la versión 254.

SYSEXT_SCOPE=

Toma una lista separada por espacios de una o más de las cadenas "system", "initrd" y "portable". Este campo solo se admite en archivos extension-release.d/ e indica a qué entornos son aplicables las extensiones del sistema: es decir, a sistemas regulares, a initrds y exitrds, o a imágenes de servicio portátiles. Si no se especifica, se implica "SYSEXT_SCOPE=system portable", es decir, cualquier extensión del sistema sin este campo es aplicable a sistemas regulares y a entornos de servicio portátiles, pero no a entornos de initrd/exitrd.

Añadido en la versión 250.

CONFEXT_SCOPE=

Semánticamente lo mismo que SYSEXT_SCOPE= pero para imágenes confext.

Añadido en la versión 254.

PORTABLE_PREFIXES=

Toma una lista separada por espacios de una o más cadenas de coincidencia de prefijo válidas para la lógica de **Servicios Portátiles**[3]. Este campo sirve para dos propósitos: es informativo, identifica las imágenes de servicio portátiles como tales (y por lo tanto permite distinguirlas de otras imágenes del sistema operativo, como las imágenes de sistema arrancables). También se utiliza cuando se adjunta una imagen de servicio portátil: el prefijo de servicio portátil especificado o implícito se verifica con la lista especificada aquí, para imponer restricciones sobre cómo se pueden adjuntar las imágenes a un sistema.

Añadido en la versión 250.

Notas

Si está utilizando este archivo para determinar el sistema operativo o una versión específica del mismo, utilice los campos ID y VERSION_ID, posiblemente con ID_LIKE como respaldo para ID. Al buscar una cadena de identificación del sistema operativo para presentarla al usuario, utilice el campo PRETTY_NAME.

Tenga en cuenta que los proveedores de sistemas operativos pueden optar por no proporcionar información de versión, por ejemplo, para adaptarse a las versiones continuas. En este caso, VERSION y VERSION_ID pueden no estar establecidos. Las aplicaciones no deben depender de que estos campos estén establecidos.

Los proveedores de sistemas operativos pueden extender el formato del archivo e introducir nuevos campos. Se recomienda encarecidamente anteponer un nombre específico del sistema operativo a los nuevos campos para evitar conflictos de nombres. Las aplicaciones que lean este archivo deben ignorar los campos desconocidos.

Ejemplo: "DEBIAN_BTS="debbugs://bugs.debian.org/"" .

Los gestores de entornos de contenedores y sandboxing pueden poner a disposición de las aplicaciones los datos de identificación del host proporcionando el archivo /etc/os-release del host (si está disponible, de lo contrario /usr/lib/os-release como respaldo) como /run/host/os-release.

**Ejemplo 3. Lectura de os-release en sh(1)**

#!/bin/sh -eu
# SPDX-License-Identifier: MIT-0
test -e /etc/os-release && os_release='/etc/os-release' || os_release='/usr/lib/os-release'
. "${os_release}"
echo "Running on ${PRETTY_NAME:-Linux}"
if [ "${ID:-linux}" = "debian" ] || [ "${ID_LIKE#*debian*}" != "${ID_LIKE}" ]; then
    echo "Looks like Debian!"
fi

**Ejemplo 4. Lectura de os-release en python(1) (versiones >= 3.10)**

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
import platform
os_release = platform.freedesktop_os_release()
pretty_name = os_release.get('PRETTY_NAME', 'Linux')
print(f'Running on {pretty_name!r}')
if 'fedora' in [os_release.get('ID', 'linux'),
                *os_release.get('ID_LIKE', '').split()]:
    print('Looks like Fedora!')

Consulte la documentación de **platform.freedesktop_os_release**[7] para obtener más detalles.

**Ejemplo 5. Lectura de os-release en python(1) (cualquier versión)**

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
import ast
import re
import sys
def read_os_release():
    try:
        filename = '/etc/os-release'
        f = open(filename)
    except FileNotFoundError:
        filename = '/usr/lib/os-release'
        f = open(filename)
    for line_number, line in enumerate(f, start=1):
        line = line.rstrip()
        if not line or line.startswith('#'):
            continue
        m = re.match(r'([A-Z][A-Z_0-9]+)=(.*)', line)
        if m:
            name, val = m.groups()
            if val and val[0] in '"'\'':
                val = ast.literal_eval(val)
            yield name, val
        else:
            print(f'{filename}:{line_number}: bad line {line!r}',
                  file=sys.stderr)
os_release = dict(read_os_release())
pretty_name = os_release.get('PRETTY_NAME', 'Linux')
print(f'Corriendo en {pretty_name!r}')
if 'debian' in [os_release.get('ID', 'linux'),
                *os_release.get('ID_LIKE', '').split()]:
    print('¡Parece Debian!')

Tenga en cuenta que la versión anterior que utiliza la implementación integrada es preferible en la mayoría de los casos, y la versión codificada abiertamente aquí se proporciona como referencia.
