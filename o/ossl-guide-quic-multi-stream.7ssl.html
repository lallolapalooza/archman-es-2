NOMBRE

ossl-guide-quic-multi-stream - Guía de OpenSSL: Escritura de un cliente QUIC multi-stream simple

INTRODUCCIÓN

Esta página introducirá algunos conceptos importantes necesarios para escribir una aplicación QUIC multi-stream simple. Asume una comprensión básica de QUIC y cómo se utiliza en OpenSSL. Ver ossl-guide-quic-introduction(7) y ossl-guide-quic-client-block(7).

STREAMS QUIC

En una aplicación QUIC multi-stream separamos los conceptos de una "conexión" QUIC y un "stream" QUIC. Un objeto de conexión representa los detalles generales de la conexión entre un cliente y un servidor, incluyendo todos sus parámetros negociados y configurados. Usamos el objeto SSL para eso en una aplicación OpenSSL (conocido como el objeto SSL de conexión). Es creado por una aplicación llamando a SSL_new(3).

Por separado, una conexión puede tener cero o más streams asociados a ella (aunque una conexión con cero streams probablemente no sea muy útil, por lo que normalmente tendrías al menos uno). Un stream se utiliza para enviar y recibir datos entre los dos pares. Cada stream también está representado por un objeto SSL. Un stream es lógicamente independiente de todos los demás streams asociados con la misma conexión. Se garantiza que los datos enviados en un stream se entregarán en el orden en que se enviaron dentro de ese stream. Lo mismo no es cierto entre streams, por ejemplo, si una aplicación envía datos en el stream 1 primero y luego envía más datos en el stream 2 segundo, el par remoto puede recibir los datos enviados en el stream 2 antes de recibir los datos enviados en el stream 1.

Una vez que el objeto SSL de conexión ha completado su handshake (es decir, SSL_connect(3) ha devuelto 1), los objetos SSL de stream son creados por la aplicación llamando a SSL_new_stream(3) o SSL_accept_stream(3) (ver "CREACIÓN DE NUEVOS STREAMS" abajo).

Las mismas reglas de hilos se aplican a los objetos SSL como a la mayoría de los objetos OpenSSL (ver ossl-guide-libraries-introduction(7)). En particular, la mayoría de las funciones de OpenSSL son seguras para hilos, pero el objeto SSL no lo es. Esto significa que puedes usar un objeto SSL que representa un stream al mismo tiempo que otro hilo está usando un objeto SSL diferente para un stream diferente en la misma conexión. Pero no puedes usar el mismo objeto SSL en dos hilos diferentes al mismo tiempo (sin bloqueo adicional a nivel de aplicación).

EL STREAM PREDETERMINADO

Un objeto SSL de conexión también puede (opcionalmente) estar asociado con un stream. Este stream se conoce como el stream predeterminado. El stream predeterminado se crea y asocia automáticamente con el objeto SSL cuando la aplicación llama a SSL_read_ex(3), SSL_read(3), SSL_write_ex(3) o SSL_write(3) y pasa el objeto SSL de conexión como parámetro.

Si una aplicación cliente llama primero a SSL_write_ex(3) o SSL_write(3), entonces (por defecto) el stream predeterminado será un stream bidireccional iniciado por el cliente. Si una aplicación cliente llama primero a SSL_read_ex(3) o SSL_read(3), entonces el primer stream iniciado por el servidor se utilizará como el stream predeterminado (ya sea bidireccional o unidireccional).

Este comportamiento se puede controlar a través del modo de stream predeterminado. Ver SSL_set_default_stream_mode(3) para más detalles.

Se recomienda que las nuevas aplicaciones multi-stream no utilicen ningún stream predeterminado en absoluto y en su lugar utilicen un objeto SSL de stream separado para cada stream que se utilice. Esto requiere llamar a SSL_set_default_stream_mode(3) y establecer el modo en SSL_DEFAULT_STREAM_MODE_NONE.

CREACIÓN DE NUEVOS STREAMS

Un punto final puede crear un nuevo stream llamando a SSL_new_stream(3). Esto crea un stream iniciado localmente. Para hacerlo, debes pasar el objeto SSL de conexión QUIC como parámetro. También puedes especificar si deseas un stream bidireccional o unidireccional.

La función devuelve un nuevo objeto SSL de stream QUIC para enviar y recibir datos en ese stream.

El par también puede iniciar streams. Una aplicación puede usar la función SSL_get_accept_stream_queue_len(3) para determinar el número de streams que el par ha iniciado y que están esperando que la aplicación los maneje. Una aplicación puede llamar a SSL_accept_stream(3) para crear un nuevo objeto SSL para un stream iniciado remotamente. Si el par no ha iniciado ninguno, esta llamada se bloqueará hasta que uno esté disponible si el objeto de conexión está en modo de bloqueo (ver SSL_set_blocking_mode(3)).

Cuando se utiliza un stream predeterminado, OpenSSL evitará que se acepten nuevos streams. Para anular este comportamiento, debes llamar a SSL_set_incoming_stream_policy(3) para establecer la política en SSL_INCOMING_STREAM_POLICY_ACCEPT. Ver la página man para más detalles. Esto no es relevante si el stream predeterminado ha sido deshabilitado como se describe en "EL STREAM PREDETERMINADO" arriba.

Cualquier stream puede ser bidireccional o unidireccional. Si es unidireccional, el iniciador puede escribir en él pero no leer de él, y viceversa para el par. Puedes determinar qué tipo de stream representa un objeto SSL llamando a SSL_get_stream_type(3). Ver la página man para más detalles.

USAR UN STREAM PARA ENVIAR Y RECIBIR DATOS

Una vez que tienes un objeto SSL de stream (que incluye el objeto SSL de conexión si se está utilizando un stream predeterminado), puedes enviar y recibir datos a través de él utilizando las funciones SSL_write_ex(3), SSL_write(3), SSL_read_ex(3) o SSL_read(3). Ver las páginas man para más detalles.

En caso de que una de estas funciones no devuelva un código de éxito, debes llamar a SSL_get_error(3) para obtener más detalles sobre el error. En modo de bloqueo, será un error fatal (por ejemplo, SSL_ERROR_SYSCALL o SSL_ERROR_SSL), o será SSL_ERROR_ZERO_RETURN, que puede ocurrir al intentar leer datos de un stream y el par ha indicado que el stream ha concluido (es decir, se ha señalado un "FIN" en el stream). Esto significa que el par no enviará más datos en ese stream. Ten en cuenta que la interpretación de SSL_ERROR_ZERO_RETURN es ligeramente diferente para una aplicación QUIC en comparación con una aplicación TLS. En TLS ocurre cuando el par ha cerrado la conexión. En QUIC, esto solo te dice que el stream actual ha sido concluido por el par. No te dice nada sobre la conexión subyacente. Si el par ha concluido el stream, no se recibirán más datos en él, sin embargo, una aplicación aún puede enviar datos al par hasta que el lado de envío del stream también haya sido concluido. Esto puede ocurrir llamando a SSL_stream_conclude(3). Es un error intentar enviar más datos en un stream después de que se haya llamado a SSL_stream_conclude(3).

También es posible abandonar un stream de forma anormal llamando a SSL_stream_reset(3).

Una vez que un objeto de stream ya no es necesario, debe liberarse mediante una llamada a SSL_free(3). Una aplicación no debe llamar a SSL_shutdown(3) en él, ya que esto solo tiene sentido para objetos SSL a nivel de conexión. La liberación del stream señalará automáticamente STOP_SENDING al par.

STREAMS Y CONEXIONES

Dado un objeto stream, es posible obtener el objeto SSL correspondiente a la conexión mediante una llamada a SSL_get0_connection(3). Se aplican restricciones de hilos múltiples, por lo que se debe tener cuidado al usar el objeto de conexión devuelto. Específicamente, si está manejando cada uno de sus objetos stream en un hilo diferente y llama a SSL_get0_connection(3) desde dentro de ese hilo, debe tener cuidado de no llamar a ninguna función que utilice el objeto de conexión al mismo tiempo que otro hilo está utilizando ese objeto de conexión (con la excepción de SSL_accept_stream(3) y SSL_get_accept_stream_queue_len(3) que son seguros para hilos).

Un objeto stream no hereda todas sus configuraciones y valores de su objeto de conexión SSL padre. Por lo tanto, ciertas llamadas a funciones que son relevantes para la conexión en su conjunto no funcionarán en un stream. Por ejemplo, la función SSL_get_certificate(3) se puede usar para obtener un identificador del certificado del par cuando se llama con un objeto SSL de conexión. Cuando se llama con un objeto SSL de stream, devolverá NULL.

EJEMPLO SIMPLE DE CLIENTE QUIC MULTIHILO

Esta sección presentará varios ejemplos de código que demuestran cómo escribir una aplicación cliente QUIC multihilo simple que se conecta a un servidor, le envía algunas solicitudes HTTP/1.0 y lee las respuestas. Tenga en cuenta que HTTP/1.0 sobre QUIC no es estándar y no será soportado por servidores del mundo real. Esto es solo para fines de demostración.

Nos basaremos en el código de ejemplo del cliente QUIC bloqueante simple que se cubre en la página ossl-guide-quic-client-block(7) y asumimos que está familiarizado con él. Solo describiremos las diferencias entre el cliente QUIC bloqueante simple y el cliente QUIC multihilo. Aunque el código de ejemplo utiliza objetos SSL bloqueantes, también puede utilizar objetos SSL no bloqueantes. Consulte ossl-guide-quic-client-non-block(7) para obtener más información sobre cómo escribir un cliente QUIC no bloqueante.

El código fuente completo de este cliente QUIC multihilo de ejemplo está disponible en el directorio "demos/guide" de la distribución fuente de OpenSSL en el archivo "quic-multi-stream.c". También está disponible en línea en https://github.com/openssl/openssl/blob/master/demos/guide/quic-multi-stream.c.

Desactivar el stream predeterminado

Como se discutió anteriormente en "EL STREAM PREDETERMINADO", seguiremos la recomendación de deshabilitar el stream predeterminado para nuestro cliente multihilo. Para hacer esto, llamamos a la función SSL_set_default_stream_mode(3) y pasamos nuestro objeto SSL de conexión y el valor SSL_DEFAULT_STREAM_MODE_NONE.

/*
 * Usaremos múltiples streams, por lo que deshabilitaremos el modo de stream predeterminado.
 * Esto no es un requisito para usar múltiples streams, pero se recomienda.
 */
if (!SSL_set_default_stream_mode(ssl, SSL_DEFAULT_STREAM_MODE_NONE)) {
    printf("Falló al deshabilitar el modo de stream predeterminado\n");
    goto end;
}

Crear los streams de solicitud

Para los fines de este ejemplo, crearemos dos streams diferentes para enviar dos solicitudes HTTP diferentes al servidor. Para fines de demostración, el primero de ellos será un stream bidireccional y el segundo será unidireccional:

/*
 * Creamos dos nuevos streams iniciados por el cliente. El primero será
 * bidireccional y el segundo será unidireccional.
 */
stream1 = SSL_new_stream(ssl, 0);
stream2 = SSL_new_stream(ssl, SSL_STREAM_FLAG_UNI);
if (stream1 == NULL || stream2 == NULL) {
    printf("Falló al crear los streams\n");
    goto end;
}

Escribir datos en los streams

Una vez que los streams se crean con éxito, podemos comenzar a escribir datos en ellos. En este ejemplo, enviaremos una solicitud HTTP diferente en cada stream. Para evitar repetir demasiado código, escribimos una función auxiliar simple para enviar una solicitud HTTP a un stream:

int write_a_request(SSL *stream, const char *request_start,
                    const char *hostname)
{
    const char *request_end = "\r\n\r\n";
    size_t written;
    if (!SSL_write_ex(stream, request_start, strlen(request_start), &written))
        return 0;
    if (!SSL_write_ex(stream, hostname, strlen(hostname), &written))
        return 0;
    if (!SSL_write_ex(stream, request_end, strlen(request_end), &written))
        return 0;
    return 1;
}

Asumimos que las cadenas request1_start y request2_start contienen las solicitudes HTTP apropiadas. Luego podemos llamar a nuestra función auxiliar anterior para enviar las solicitudes en los dos streams. Por simplicidad, este ejemplo lo hace secuencialmente, escribiendo primero en stream1 y, cuando esto es exitoso, escribiendo en stream2 segundo. Recuerde que nuestro cliente es bloqueante, por lo que estas llamadas solo devolverán una vez que se hayan completado con éxito. Una aplicación real no necesitaría hacer estas escrituras secuencialmente ni en ningún orden particular. Por ejemplo, podríamos iniciar dos hilos (uno por cada stream) y escribir las solicitudes en cada stream simultáneamente.

/* Escribir una solicitud HTTP GET en cada uno de nuestros streams al peer */
if (!write_a_request(stream1, request1_start, hostname)) {
    printf("Falló al escribir la solicitud HTTP en el stream 1\n");
    goto end;
}
if (!write_a_request(stream2, request2_start, hostname)) {
    printf("Falló al escribir la solicitud HTTP en el stream 2\n");
    goto end;
}

Leer datos de un stream

En este ejemplo, stream1 es un stream bidireccional, por lo que, una vez que hayamos enviado la solicitud en él, podemos intentar leer la respuesta del servidor. Aquí llamamos repetidamente a SSL_read_ex(3) hasta que esa función falla (indicando que ha habido un problema, o que el peer ha señalado el stream como concluido).

printf("Datos del Stream 1:\n");
/*
 * Obtener hasta sizeof(buf) bytes de la respuesta del stream 1 (que es un
 * stream bidireccional). Seguimos leyendo hasta que el servidor cierra
 * la conexión.
 */
while (SSL_read_ex(stream1, buf, sizeof(buf), &readbytes)) {
    /*
    * OpenSSL no garantiza que los datos devueltos sean una cadena o
    * que terminen en NUL, por lo que usamos fwrite() para escribir la cantidad exacta
    * de bytes que leímos. Los datos podrían ser no imprimibles o
    * tener caracteres NUL en medio. Para este ejemplo simple,
    * lo imprimiremos en stdout de todos modos.
    */
    fwrite(buf, 1, readbytes, stdout);
}
/* En caso de que la respuesta no terminara con una nueva línea, la agregamos ahora */
printf("\n");

En una aplicación bloqueante como esta, las llamadas a SSL_read_ex(3) tendrán éxito inmediatamente devolviendo datos que ya están disponibles, o se bloquearán esperando que haya más datos disponibles y los devolverán cuando los haya, o fallarán con un código de respuesta de 0.

Una vez que salimos del bucle while anterior, sabemos que la última llamada a SSL_read_ex(3) devolvió un código de respuesta de 0, por lo que llamamos a la función SSL_get_error(3) para obtener más detalles. Dado que esta es una aplicación bloqueante, esto devolverá SSL_ERROR_SYSCALL o SSL_ERROR_SSL indicando un problema fundamental, o devolverá SSL_ERROR_ZERO_RETURN indicando que el stream está concluido y no habrá más datos disponibles para leer de él. Se debe tener cuidado para distinguir entre un error a nivel de stream (es decir, un reinicio de stream) y un error a nivel de conexión (es decir, una conexión cerrada). La función SSL_get_stream_read_state(3) puede usarse para distinguir entre estos diferentes casos.

/*
 * Comprueba si terminamos el bucle while anterior normalmente o como resultado de un error.
 * El argumento 0 para SSL_get_error() es el código de retorno que recibimos de la llamada a SSL_read_ex().
 * Debe ser 0 para llegar aquí. La finalización normal se indica mediante SSL_ERROR_ZERO_RETURN. En
 * términos de QUIC, esto significa que el peer ha enviado FIN en el stream para
 * indicar que no se enviarán más datos.
 */
switch (SSL_get_error(stream1, 0)) {
case SSL_ERROR_ZERO_RETURN:
    /* Finalización normal del stream */
    break;
case SSL_ERROR_SSL:
    /*
     * Ocurrió algún error fatal en el stream. Esto podría deberse a un reinicio
     * del stream, o a algún fallo ocurrido en la conexión subyacente.
     */
    switch (SSL_get_stream_read_state(stream1)) {
    case SSL_STREAM_STATE_RESET_REMOTE:
        printf("Ocurrió un reinicio de stream\n");
        /* El stream se ha reiniciado pero la conexión sigue en buen estado. */
        break;
    case SSL_STREAM_STATE_CONN_CLOSED:
        printf("Conexión cerrada\n");
        /* La conexión ya está cerrada. Omitir SSL_shutdown() */
        goto end;
    default:
        printf("Fallo desconocido del stream\n");
        break;
    }
    break;
default:
    /* Ocurrió algún otro error inesperado */
    printf("Falló al leer los datos restantes\n");
    break;
}

Aceptar un stream entrante

Nuestro objeto stream2 que creamos anteriormente era un stream unidireccional, por lo que no se puede utilizar para recibir datos del servidor. En este ejemplo hipotético, asumimos que el servidor inicia un nuevo stream para enviarnos de vuelta los datos que solicitamos. Para hacer eso, llamamos a SSL_accept_stream(3). Dado que esta es una aplicación bloqueante, esperará indefinidamente hasta que llegue el nuevo stream y esté disponible para que lo aceptemos. En caso de error, devolverá NULL.

/*
 * En nuestro protocolo hipotético HTTP/1.0 sobre QUIC que estamos usando, asumimos
 * que el servidor responderá con un stream iniciado por el servidor
 * que contiene los datos solicitados en nuestro stream unidireccional. Esto no
 * tiene mucho sentido hacerlo en un protocolo real, pero es solo para
 * fines de demostración.
 *
 * Estamos usando el modo bloqueante, por lo que esto se bloqueará hasta que un stream
* disponible. Podríamos anular este comportamiento si quisiéramos estableciendo * la bandera SSL_ACCEPT_STREAM_NO_BLOCK en el segundo argumento a continuación. */ stream3 = SSL_accept_stream(ssl, 0); if (stream3 == NULL) { printf("No se pudo aceptar un nuevo flujo\n"); goto end; }

Ahora podemos leer datos del flujo de la misma manera que lo hicimos para stream1 arriba. No repetiremos eso aquí.

Limpieza de los flujos

Una vez que hayamos terminado de usar nuestros flujos, podemos simplemente liberarlos llamando a SSL_free(3). Opcionalmente, podríamos llamar a SSL_stream_conclude(3) sobre ellos si queremos indicarle a la contraparte que no le enviaremos más datos, pero no lo hacemos en este ejemplo porque asumimos que el protocolo de aplicación HTTP proporciona suficiente información para que la contraparte sepa cuándo hemos terminado de enviar los datos de la solicitud.

No debemos llamar a SSL_shutdown(3) o SSL_shutdown_ex(3) en los objetos de flujo, ya que esas llamadas no deben usarse para flujos.

SSL_free(stream1);
SSL_free(stream2);
SSL_free(stream3);
