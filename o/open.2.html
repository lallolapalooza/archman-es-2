NOMBRE

open, openat, creat - abrir y posiblemente crear un archivo

DESCRIPCIÓN

La llamada al sistema open() abre el archivo especificado por path. Si el archivo especificado no existe, puede ser creado opcionalmente (si O_CREAT está especificado en flags) por open().

El valor de retorno de open() es un descriptor de archivo, un entero pequeño, no negativo, que es un índice en la tabla de descriptores de archivo abiertos del proceso. El descriptor de archivo se usa en llamadas posteriores al sistema (read(2), write(2), lseek(2), fcntl(2), etc.) para referirse al archivo abierto. El descriptor de archivo devuelto por una llamada exitosa será el descriptor de archivo de menor número no abierto actualmente para el proceso.

Por defecto, el nuevo descriptor de archivo se establece para que permanezca abierto durante un execve(2) (es decir, la bandera del descriptor de archivo FD_CLOEXEC descrita en fcntl(2) está deshabilitada inicialmente); la bandera O_CLOEXEC, descrita a continuación, puede usarse para cambiar este comportamiento predeterminado. El desplazamiento del archivo se establece al principio del archivo (ver lseek(2)).

Una llamada a open() crea una nueva *descripción de archivo abierto*, una entrada en la tabla de archivos abiertos a nivel de sistema. La descripción de archivo abierto registra el desplazamiento del archivo y las banderas de estado del archivo (ver a continuación). Un descriptor de archivo es una referencia a una descripción de archivo abierto; esta referencia no se ve afectada si posteriormente se elimina o se modifica path para que se refiera a un archivo diferente. Para más detalles sobre descripciones de archivo abiertas, ver NOTAS.

El argumento flags debe incluir uno de los siguientes *modos de acceso*: O_RDONLY, O_WRONLY, o O_RDWR. Estos solicitan abrir el archivo solo para lectura, solo para escritura, o para lectura/escritura, respectivamente.

Además, cero o más banderas de creación de archivo y banderas de estado de archivo pueden combinarse mediante OR bit a bit en flags. Las *banderas de creación de archivo* son O_CLOEXEC, O_CREAT, O_DIRECTORY, O_EXCL, O_NOCTTY, O_NOFOLLOW, O_TMPFILE y O_TRUNC. Las *banderas de estado de archivo* son todas las banderas restantes listadas a continuación. La distinción entre estos dos grupos de banderas es que las banderas de creación de archivo afectan la semántica de la operación de apertura en sí, mientras que las banderas de estado de archivo afectan la semántica de las operaciones de I/O posteriores. Las banderas de estado de archivo pueden recuperarse y (en algunos casos) modificarse; ver fcntl(2) para más detalles.

La lista completa de banderas de creación de archivo y banderas de estado de archivo es la siguiente:

O_APPEND
El archivo se abre en modo de añadir. Antes de cada write(2), el desplazamiento del archivo se posiciona al final del archivo, como si fuera con lseek(2). La modificación del desplazamiento del archivo y la operación de escritura se realizan como un único paso atómico.
O_APPEND puede provocar corrupción de archivos en sistemas de archivos NFS si más de un proceso añade datos a un archivo a la vez. Esto se debe a que NFS no soporta añadir datos a un archivo, por lo que el kernel del cliente tiene que simularlo, lo que no se puede hacer sin una condición de carrera.
O_ASYNC
Habilita I/O controlada por señales: genera una señal (SIGIO por defecto, pero esto se puede cambiar a través de fcntl(2)) cuando la entrada o la salida se vuelven posibles en este descriptor de archivo. Esta característica solo está disponible para terminales, pseudoterminales, sockets y (desde Linux 2.6) pipes y FIFOs. Ver fcntl(2) para más detalles. Ver también ERRORES, abajo.
O_CLOEXEC (desde Linux 2.6.23)
Habilita la bandera de cierre al ejecutar (close-on-exec) para el nuevo descriptor de archivo. Especificar esta bandera permite a un programa evitar operaciones adicionales de fcntl(2) F_SETFD para establecer la bandera FD_CLOEXEC.
Tenga en cuenta que el uso de esta bandera es esencial en algunos programas multihilo, ya que usar una operación separada de fcntl(2) F_SETFD para establecer la bandera FD_CLOEXEC no es suficiente para evitar condiciones de carrera en las que un hilo abre un descriptor de archivo e intenta establecer su bandera de cierre al ejecutar usando fcntl(2) al mismo tiempo que otro hilo realiza un fork(2) más un execve(2). Dependiendo del orden de ejecución, la condición de carrera puede provocar que el descriptor de archivo devuelto por open() se filtre involuntariamente al programa ejecutado por el proceso hijo creado por fork(2). (Este tipo de condición de carrera es en principio posible para cualquier llamada al sistema que cree un descriptor de archivo cuya bandera de cierre al ejecutar deba establecerse, y varias otras llamadas al sistema de Linux proporcionan un equivalente a la bandera O_CLOEXEC para abordar este problema).
O_CREAT
Si path no existe, créalo como un archivo regular.
El propietario (ID de usuario) del nuevo archivo se establece en el ID de usuario efectivo del proceso.
La propiedad del grupo (ID de grupo) del nuevo archivo se establece ya sea en el ID de grupo efectivo del proceso (semántica de System V) o en el ID de grupo del directorio padre (semántica de BSD). En Linux, el comportamiento depende de si la bandera de modo set-group-ID está establecida en el directorio padre: si esa bandera está establecida, se aplican las semánticas de BSD; de lo contrario, se aplican las semánticas de System V. Para algunos sistemas de archivos, el comportamiento también depende de las opciones de montaje bsdgroups y sysvgroups descritas en mount(8).
El argumento mode especifica las banderas de modo del archivo que se aplicarán cuando se crea un nuevo archivo. Si ni O_CREAT ni O_TMPFILE están especificados en flags, entonces mode se ignora (y por lo tanto puede especificarse como 0, o simplemente omitirse). El argumento mode **debe** suministrarse si O_CREAT o O_TMPFILE están especificados en flags; si no se suministra, se aplicarán bytes arbitrarios de la pila como modo del archivo.
El modo efectivo se modifica por el umask del proceso de la manera habitual: en ausencia de una ACL predeterminada, el modo del archivo creado es (mode & ~umask).
Tenga en cuenta que mode solo se aplica a los accesos futuros del archivo recién creado; la llamada open() que crea un archivo de solo lectura bien puede devolver un descriptor de archivo de lectura/escritura.
Las siguientes constantes simbólicas se proporcionan para mode:
S_IRWXU
00700 el usuario (propietario del archivo) tiene permiso de lectura, escritura y ejecución
S_IRUSR
00400 el usuario tiene permiso de lectura
S_IWUSR
00200 el usuario tiene permiso de escritura

DESCRIPCIÓN

Las opciones especificadas en el argumento flags determinan la acción que toma open(2). Las opciones se interpretan en grupos. La forma de un argumento flags es una opción, o un OR bit a bit de dos o más opciones.

El valor de flags debe ser una opción o una opción OR bit a bit de una o más de las siguientes opciones:

O_APPEND
El archivo se abre en modo de adición. Cada escritura en el archivo, sin importar la posición del puntero del archivo, se realizará al final del archivo.
Este modo puede ser habilitado o deshabilitado con la opción fcntl(2) F_SETFL.
O_CLOEXEC (desde Linux 2.6.23)
Habilita el flag de cierre en la ejecución (close-on-exec). Si el archivo está siendo abierto y este flag está habilitado, el descriptor de archivo resultante tendrá habilitado el flag FD_CLOEXEC (ver fcntl(2)). Esto evita que el descriptor de archivo sea heredado por procesos hijos creados por fork(2) y que el descriptor de archivo sea heredado por la ejecución de un programa en el mismo proceso (ver execve(2)).
O_CREAT
Si el archivo no existe, debe ser creado. El permiso de archivo para los nuevos archivos es determinado por mode (ver más abajo).
O_DIRECT (desde Linux 2.4.10)
Intenta minimizar los efectos de caché de las E/S hacia y desde este archivo. En general, esto degradará el rendimiento, pero es útil en situaciones especiales, como cuando las aplicaciones hacen su propio caching. Las E/S de archivo se realizan directamente a/desde buffers del espacio de usuario. El flag O_DIRECT por sí solo hace un esfuerzo para transferir datos de forma síncrona, pero no garantiza que los datos y metadatos necesarios se transfieran, como lo hace el flag O_SYNC. Para garantizar E/S síncrona, se debe usar O_SYNC además de O_DIRECT. Ver NOTAS abajo para más discusión.
Una interfaz semánticamente similar (pero obsoleta) para dispositivos de bloque se describe en raw(8).
O_DIRECTORY
Si path no es un directorio, causa que open() falle. Este flag se añadió en Linux 2.1.126, para evitar problemas de denegación de servicio si opendir(3) se llama en un FIFO o dispositivo de cinta.
O_DSYNC
Las operaciones de escritura en el archivo se completarán de acuerdo con los requisitos de la integridad de los *datos* de las E/S síncronas.
Cuando write(2) (y similares) regresan, los datos de salida se han transferido al hardware subyacente, junto con cualquier metadato de archivo que fuera necesario para recuperar esos datos (es decir, como si cada write(2) fuera seguido por una llamada a fdatasync(2)). Ver VERSIONES.
O_EXCL
Asegura que esta llamada cree el archivo: si este flag se especifica junto con O_CREAT, y path ya existe, entonces open() falla con el error EEXIST.
Cuando se especifican estas dos flags, los enlaces simbólicos no son seguidos: si path es un enlace simbólico, entonces open() falla independientemente de a dónde apunte el enlace simbólico.
En general, el comportamiento de O_EXCL no está especificado si se usa sin O_CREAT. Hay una excepción: en Linux 2.6 y posteriores, O_EXCL puede usarse sin O_CREAT si path se refiere a un dispositivo de bloque. Si el dispositivo de bloque está en uso por el sistema (por ejemplo, montado), open() falla con el error EBUSY.
En NFS, O_EXCL solo es soportado cuando se usa NFSv3 o posterior en el kernel 2.6 o posterior. En entornos NFS donde no se proporciona soporte para O_EXCL, los programas que dependen de él para realizar tareas de bloqueo contendrán una condición de carrera. Los programas portables que quieran realizar bloqueos de archivos atómicos usando un archivo de bloqueo, y necesiten evitar depender del soporte de NFS para O_EXCL, pueden crear un archivo único en el mismo sistema de archivos (por ejemplo, incorporando el nombre del host y el PID), y usar link(2) para crear un enlace al archivo de bloqueo. Si link(2) devuelve 0, el bloqueo es exitoso. De lo contrario, usa stat(2) en el archivo único para verificar si su recuento de enlaces ha aumentado a 2, en cuyo caso el bloqueo también es exitoso.
O_LARGEFILE
(LFS) Permite abrir archivos cuyos tamaños no pueden ser representados en un off_t (pero sí en un off64_t). La macro _LARGEFILE64_SOURCE debe ser definida (antes de incluir cualquier archivo de cabecera) para obtener esta definición. Establecer la macro de prueba de características _FILE_OFFSET_BITS a 64 (en lugar de usar O_LARGEFILE) es el método preferido para acceder a archivos grandes en sistemas de 32 bits (ver feature_test_macros(7)).
O_NOATIME (desde Linux 2.6.8)
No actualiza el tiempo de último acceso del archivo (st_atime en el inodo) cuando el archivo es leído (read(2)).
Este flag solo puede ser empleado si una de las siguientes condiciones es verdadera:
•
El UID efectivo del proceso coincide con el UID del propietario del archivo.
•
El proceso que llama tiene la capacidad CAP_FOWNER en su espacio de nombres de usuario y el UID del propietario del archivo tiene un mapeo en el espacio de nombres.
Este flag está pensado para ser utilizado por programas de indexación o copia de seguridad, donde su uso puede reducir significativamente la actividad del disco. Este flag puede no ser efectivo en todos los sistemas de archivos. Un ejemplo es NFS, donde el servidor mantiene el tiempo de acceso.
O_NOCTTY
Si path se refiere a un dispositivo terminal—ver tty(4)—no se convertirá en el terminal de control del proceso, incluso si el proceso no tiene uno.
O_NOFOLLOW
Si el componente final (es decir, basename) de path es un enlace simbólico, entonces el open falla, con el error ELOOP. Los enlaces simbólicos en componentes anteriores del nombre de ruta aún serán seguidos. (Tenga en cuenta que el error ELOOP que puede ocurrir en este caso es indistinguible del caso en que un open falla porque hay demasiados enlaces simbólicos encontrados al resolver componentes en el prefijo de la ruta del nombre de ruta.)
Este flag es una extensión de FreeBSD, que se añadió en Linux 2.1.126, y posteriormente se ha estandarizado en POSIX.1-2008.
Ver también O_PATH abajo.
O_NONBLOCK o O_NDELAY
Cuando sea posible, el archivo se abre en modo no bloqueante. Ni open() ni las operaciones de E/S subsiguientes en el descriptor de archivo que se devuelve harán que el proceso que llama espere.
Tenga en cuenta que el establecimiento de este flag no tiene efecto en la operación de poll(2), select(2), epoll(7) y similares, ya que esas interfaces solo informan al llamante si un descriptor de archivo está "listo", lo que significa que una operación de E/S realizada en el descriptor de archivo con el flag O_NONBLOCK *limpio* no bloquearía.
Tenga en cuenta que este flag no tiene efecto para archivos regulares y dispositivos de bloque; es decir, las operaciones de E/S se bloquearán (brevemente) cuando se requiera actividad del dispositivo, independientemente de si O_NONBLOCK está establecido. Dado que la semántica de O_NONBLOCK podría implementarse eventualmente, las aplicaciones no deberían depender del comportamiento de bloqueo al especificar este flag para archivos regulares y dispositivos de bloque.
Para el manejo de FIFOs (tuberías con nombre), ver también fifo(7). Para una discusión sobre el efecto de O_NONBLOCK junto con bloqueos de archivos obligatorios y con leases de archivos, ver fcntl(2).
O_PATH (desde Linux 2.6.39)
Obtiene un descriptor de archivo que puede usarse para dos propósitos: indicar una ubicación en el árbol del sistema de archivos y realizar operaciones que actúan puramente a nivel de descriptor de archivo. El archivo en sí no se abre, y otras operaciones de archivo (por ejemplo, read(2), write(2), fchmod(2), fchown(2), fgetxattr(2), ioctl(2), mmap(2)) fallan con el error EBADF.
Las siguientes operaciones *pueden* realizarse en el descriptor de archivo resultante:
•
close(2).
•
fchdir(2), si el descriptor de archivo se refiere a un directorio (desde Linux 3.5).
•
fstat(2) (desde Linux 3.6).
•
fstatfs(2) (desde Linux 3.12).
•
Duplicar el descriptor de archivo (dup(2), fcntl(2) F_DUPFD, etc.).
•
Obtener y establecer flags de descriptor de archivo (fcntl(2) F_GETFD y F_SETFD).
•
Recuperar flags de estado de archivo abierto usando la operación fcntl(2) F_GETFL: los flags devueltos incluirán el bit O_PATH.
•

E/S Sincronizada

La opción de E/S sincronizada de POSIX.1-2008 especifica diferentes variantes de E/S sincronizada, y especifica las banderas O_SYNC, O_DSYNC y O_RSYNC de open() para controlar el comportamiento. Independientemente de si una implementación soporta esta opción, debe al menos soportar el uso de O_SYNC para archivos regulares.

Linux implementa O_SYNC y O_DSYNC, pero no O_RSYNC. De forma algo incorrecta, glibc define O_RSYNC para tener el mismo valor que O_SYNC. (O_RSYNC se define en el archivo de cabecera de Linux <asm/fcntl.h> en HP PA-RISC, pero no se usa.)

O_SYNC proporciona finalización de integridad de archivo de E/S sincronizada, lo que significa que las operaciones de escritura vaciarán los datos y todos los metadatos asociados al hardware subyacente. O_DSYNC proporciona finalización de integridad de datos de E/S sincronizada, lo que significa que las operaciones de escritura vaciarán los datos al hardware subyacente, pero solo vaciarán las actualizaciones de metadatos que sean necesarias para permitir que una operación de lectura posterior se complete correctamente. La finalización de integridad de datos puede reducir el número de operaciones de disco que son necesarias para aplicaciones que no necesitan las garantías de finalización de integridad de archivo.

Para entender la diferencia entre los dos tipos de finalización, considere dos piezas de metadatos de archivo: la marca de tiempo de la última modificación del archivo (st_mtime) y la longitud del archivo. Todas las operaciones de escritura actualizarán la marca de tiempo de la última modificación del archivo, pero solo las escrituras que añadan datos al final del archivo cambiarán la longitud del archivo. La marca de tiempo de la última modificación no es necesaria para asegurar que una lectura se complete correctamente, pero la longitud del archivo sí lo es. Por lo tanto, O_DSYNC solo garantizaría vaciar las actualizaciones de los metadatos de longitud de archivo (mientras que O_SYNC también vaciaría siempre los metadatos de la marca de tiempo de la última modificación).

Antes de Linux 2.6.33, Linux solo implementaba la bandera O_SYNC para open(). Sin embargo, cuando se especificaba esa bandera, la mayoría de los sistemas de archivos proporcionaban en realidad el equivalente a la finalización de integridad de datos de E/S sincronizada (es decir, O_SYNC se implementaba en realidad como el equivalente a O_DSYNC).

Desde Linux 2.6.33, se proporciona el soporte adecuado para O_SYNC. Sin embargo, para garantizar la compatibilidad binaria hacia atrás, O_DSYNC se definió con el mismo valor que el O_SYNC histórico, y O_SYNC se definió como un nuevo valor de bandera (de dos bits) que incluye el valor de bandera O_DSYNC. Esto asegura que las aplicaciones compiladas con cabeceras nuevas obtengan al menos las semánticas de O_DSYNC antes de Linux 2.6.33.

Desde glibc 2.26, la función de envoltura de glibc para open() utiliza la llamada al sistema openat(), en lugar de la llamada al sistema open() del kernel. Para ciertas arquitecturas, esto también es cierto antes de glibc 2.26.

POSIX

POSIX.1-2024 especifica

DESCRIPCIÓN

open() crea un nuevo descriptor de archivo, o reutiliza uno existente, para un archivo abierto. El nuevo descriptor de archivo, devuelto por la llamada, es el entero más pequeño que no está actualmente abierto para el proceso. La tabla de descriptores de archivo y la tabla de descriptores de archivo abiertos siguen las reglas de copia en escritura de fork(2).

El parámetro pathname es la ruta del archivo.

El parámetro flags contiene una variedad de banderas que controlan la forma en que se abre el archivo. Estas banderas se forman mediante la operación OR bit a bit de valores individuales:

O_RDONLY
Abrir solo para lectura.
O_WRONLY
Abrir solo para escritura.
O_RDWR
Abrir para leer y escribir.

Solo se debe especificar uno de O_RDONLY, O_WRONLY o O_RDWR. Estos tres valores definen los dos bits menos significativos de flags.

Las siguientes banderas se pueden OR-ear bit a bit con una de las banderas anteriores para especificar el comportamiento de la apertura:

O_CREAT
Si el archivo no existe, crear el archivo. Se requiere el argumento mode para crear el archivo; vea open(2). Si la bandera O_CREAT está presente, open() solo tendrá éxito si el archivo no existe. Consulte la descripción de O_EXCL para ver un caso especial.
O_EXCL
Se utiliza junto con O_CREAT. Si el archivo existe, es un error. Esta bandera evita que una carrera ocurra si dos procesos intentan crear el mismo archivo simultáneamente.
O_NOCTTY
Si la ruta apunta a un descriptor de terminal, entonces no convierta este descriptor en el descriptor de terminal de control del proceso. El uso de esta bandera por parte de un proceso no impide que un terminal se convierta en el descriptor de terminal de control de un proceso posterior. Esta bandera está destinada a ser utilizada por programas que nunca deben interactuar con un descriptor de terminal de control (por ejemplo, demonios que podrían ser invocados de forma no interactiva en una máquina remota para abrir un terminal de la máquina local).
O_TRUNC
Si el archivo existe y se abre para escribir (por ejemplo, no se especifica O_RDONLY), se truncará a longitud cero. ¡Precaución! Esto tiene el efecto de descartar el contenido del archivo. Si se especifica O_TRUNC y el archivo no existe, se creará el archivo (si la bandera O_CREAT está presente).
O_APPEND
El archivo se abre en modo de adición. Cada operación de escritura se produce en la posición final del archivo, independientemente de la posición actual del descriptor de archivo. O_APPEND se ignora si se especifica junto con O_RDONLY.
O_NONBLOCK
Cuando se abre un dispositivo (por ejemplo, un FIFO, un dispositivo de terminal o un socket), esta bandera evita que el descriptor de archivo se bloquee. Si un FIFO no tiene un lector o escritor, o un socket no está conectado, entonces open() no se bloqueará. Sin embargo, la llamada podría seguir devolviendo EAGAIN si la apertura posterior no tiene éxito, o EWOULDBLOCK si la apertura posterior es exitosa.
O_DSYNC
Escribir solo actualizaciones de datos. La llamada de escritura no regresará hasta que los datos sean escritos en el medio físico. Sin embargo, no se garantiza que las actualizaciones de metadatos (como el tiempo de acceso y modificación) se escriban.
O_RSYNC
Las actualizaciones de datos y metadatos se escriben de forma sincrónica. Esto es similar a O_DSYNC, pero también asegura que las actualizaciones de metadatos se escriban de forma sincrónica. Cuando se abre un archivo con O_RDONLY y O_RSYNC, las lecturas no se bloquearán hasta que los datos sean leídos del medio físico.
O_SYNC
Equivalente a O_DSYNC | O_RSYNC. Esto significa que las actualizaciones de datos y metadatos se escriben de forma sincrónica. (En versiones anteriores del kernel, O_SYNC era equivalente a O_DSYNC).
O_DIRECTORY
Si la ruta no es un directorio, se producirá un error. Solo se puede usar con O_RDONLY (o O_RDONLY | O_DIRECTORY). Esta bandera se introdujo para permitir la apertura de directorios para inspeccionarlos de forma segura. Anteriormente, esto se lograba mediante la apertura de un archivo normal con las marcas O_RDONLY y O_NOFOLLOW, que podría fallar si el archivo tenía un enlace simbólico con el mismo nombre.
O_NOFOLLOW
No seguir enlaces simbólicos. Si el último componente de la ruta es un enlace simbólico, se producirá un error.
O_CLOEXEC
Establecer la bandera de cierre en la ejecución (FD_CLOEXEC) en el nuevo descriptor de archivo. Vea fcntl(2) para más información sobre FD_CLOEXEC.
O_DIRECT
Intentar minimizar la cantidad de caché de página utilizada para las E/S de este descriptor de archivo. Las lecturas y escrituras se intentarán realizar directamente en el dispositivo de almacenamiento. Esto puede ofrecer ganancias de rendimiento en ciertas situaciones, pero también puede degradar el rendimiento si se usa incorrectamente. La alineación de búferes y el tamaño de E/S pueden ser restricciones importantes cuando se usa O_DIRECT.
O_LOCAL
(Solo Sun) Especificar que la apertura de un archivo en un sistema de archivos de red no debe implicar un acceso de red. Si el archivo no está disponible localmente, la apertura fallará.
O_NONBLOCK
Similar a la bandera de apertura, pero afecta las llamadas posteriores a lectura y escritura. Si se especifica esta bandera, las operaciones de lectura y escritura en un FIFO que no tiene lectores o escritores, respectivamente, devuelven inmediatamente un código de error EAGAIN en lugar de bloquearse. Para la mayoría de los otros tipos de archivos, esta bandera no tiene ningún efecto.
O_LARGEFILE
Manejar archivos de más de 2 GB. Este comportamiento está habilitado de forma predeterminada en Linux y está obsoleto.
O_PATH
Permitir la obtención de un descriptor de archivo para un archivo o directorio sin tener que abrirlo para lectura o escritura. Esto se puede usar en combinación con otras operaciones de descriptor de archivo como fstatat(2) o openat(2). La apertura con O_PATH no produce ningún acceso al sistema de archivos para el archivo o directorio especificado. Sin embargo, se requiere acceso de búsqueda al directorio padre. Solo se puede combinar con O_DIRECTORY, O_NOFOLLOW, O_CLOEXEC y O_SYNC.
O_TMPFILE
Crear un archivo temporal anónimo. Esto se hace abriendo un directorio con esta bandera y sin especificar un nombre de archivo. El descriptor de archivo resultante se puede usar para crear un archivo temporal que no tenga nombre en el sistema de archivos. El archivo se elimina automáticamente cuando se cierra el último descriptor de archivo. Esto puede usarse con o sin O_CREAT. Si se usa con O_CREAT, entonces se requiere O_TMPFILE junto con un descriptor de archivo de directorio.
O_CLOFORK
Marca el descriptor de archivo para que se cierre automáticamente si el proceso se bifurca usando fork(2). El descriptor de archivo permanecerá abierto en el proceso padre, pero se cerrará en el proceso hijo. Esta bandera está obsoleta y Linux no la soporta.

NOTAS

En Linux, la bandera O_NONBLOCK se usa a veces en casos en los que se desea abrir pero no necesariamente leer o escribir. Por ejemplo, se puede usar para abrir un dispositivo y obtener un descriptor de archivo para usarlo con ioctl(2).

Tenga en cuenta que open() puede abrir archivos especiales de dispositivo, pero creat() no puede crearlos; use mknod(2) en su lugar.

Si el archivo se crea nuevo, sus campos st_atime, st_ctime, st_mtime (respectivamente, tiempo del último acceso, tiempo del último cambio de estado y tiempo de la última modificación; vea stat(2)) se establecen a la hora actual, y lo mismo ocurre con los campos st_ctime y st_mtime del directorio padre. De lo contrario, si el archivo se modifica debido a la bandera O_TRUNC, sus campos st_ctime y st_mtime se establecen a la hora actual.

Los archivos en el directorio /proc/pid/fd muestran los descriptores de archivo abiertos del proceso con el PID pid. Los archivos en el directorio /proc/pid/fdinfo muestran aún más información sobre estos descriptores de archivo. Vea proc(5) para más detalles sobre ambos directorios.

El archivo de cabecera de Linux <asm/fcntl.h> no define O_ASYNC; en su lugar se define el sinónimo (derivado de BSD) FASYNC.

Descripciones de archivos abiertos

El término descripción de archivo abierto es el que usa POSIX para referirse a las entradas en la tabla global del sistema de archivos abiertos. En otros contextos, este objeto se denomina de diversas formas "objeto de archivo abierto", "descriptor de archivo", "entrada de tabla de archivo abierto" o, en jerga de desarrolladores del kernel, un struct file.

Cuando un descriptor de archivo se duplica (usando dup(2) o similar), el duplicado se refiere a la misma descripción de archivo abierto que el descriptor de archivo original, y los dos descriptores de archivo comparten en consecuencia el desplazamiento del archivo y las banderas de estado del archivo. Dicho intercambio también puede ocurrir entre procesos: un proceso hijo creado a través de fork(2) hereda duplicados de los descriptores de archivo de su padre, y esos duplicados se refieren a las mismas descripciones de archivo abiertas.

Cada open() de un archivo crea una nueva descripción de archivo abierto; por lo tanto, puede haber múltiples descripciones de archivo abierto correspondientes a un inodo de archivo.

En Linux, se puede usar la operación KCMP_FILE de kcmp(2) para probar si dos descriptores de archivo (en el mismo proceso o en dos procesos diferentes) se refieren a la misma descripción de archivo abierto.

NFS

Hay muchas infelicidades en el protocolo subyacente de NFS, que afectan entre otros a O_SYNC y O_NDELAY.

En sistemas de archivos NFS con mapeo de UID habilitado, open() puede devolver un descriptor de archivo pero, por ejemplo, las solicitudes de read(2) se deniegan con EACCES. Esto se debe a que el cliente realiza open() comprobando los permisos, pero el mapeo de UID lo realiza el servidor al leer y escribir solicitudes.

FIFOs

Abrir el extremo de lectura o escritura de un FIFO se bloquea hasta que el otro extremo también se abre (por otro proceso o hilo). Vea fifo(7) para más detalles.

Modo de acceso al archivo

A diferencia de los otros valores que se pueden especificar en flags, los valores del modo de acceso O_RDONLY, O_WRONLY y O_RDWR no especifican bits individuales. Más bien, definen los dos bits menos significativos de flags, y se definen respectivamente como 0, 1 y 2. En otras palabras, la combinación O_RDONLY | O_WRONLY es un error lógico, y ciertamente no tiene el mismo significado que O_RDWR.

Linux reserva el modo de acceso especial y no estándar 3 (binario 11) en flags para significar: comprobar el permiso de lectura y escritura en el archivo y devolver un descriptor de archivo que no se puede usar para leer o escribir. Este modo de acceso no estándar es utilizado por algunos controladores de Linux para devolver un descriptor de archivo que se utilizará solo para operaciones ioctl(2) específicas del dispositivo.

Razones de openat() y otras APIs de descriptores de archivo de directorio

openat() y las otras llamadas al sistema y funciones de biblioteca que toman un argumento de descriptor de archivo de directorio (es decir, execveat(2), faccessat(2), fanotify_mark(2), fchmodat(2), fchownat(2), fspick(2), fstatat(2), futimesat(2), linkat(2), mkdirat(2), mknodat(2), mount_setattr(2), move_mount(2), name_to_handle_at(2), open_tree(2), openat2(2), readlinkat(2), renameat(2), renameat2(2), statx(2), symlinkat(2), unlinkat(2), utimensat(2), mkfifoat(3), y scandirat(3)) abordan dos problemas con las interfaces más antiguas que las precedieron. Aquí, la explicación es en términos de la llamada openat(), pero el razonamiento es análogo para las otras interfaces.

Primero, openat() permite que una aplicación evite condiciones de carrera que podrían ocurrir al usar open() para abrir archivos en directorios que no sean el directorio de trabajo actual. Estas condiciones de carrera resultan del hecho de que algún componente del prefijo del directorio dado a open() podría modificarse en paralelo con la llamada a open(). Supongamos, por ejemplo, que deseamos crear el archivo dir1/dir2/xxx.dep si existe el archivo dir1/dir2/xxx. El problema es que entre la comprobación de existencia y el paso de creación del archivo, dir1 o dir2 (que podrían ser enlaces simbólicos) podrían modificarse para apuntar a una ubicación diferente. Dichas carreras se pueden evitar abriendo un descriptor de archivo para el directorio de destino, y luego especificando ese descriptor de archivo como el argumento dirfd de (por ejemplo) fstatat(2) y openat(). El uso del descriptor de archivo dirfd también tiene otros beneficios:

•
el descriptor de archivo es una referencia estable al directorio, incluso si el directorio se renombra; y
•
el descriptor de archivo abierto evita que el sistema de archivos subyacente se desmonte, al igual que cuando un proceso tiene un directorio de trabajo actual en un sistema de archivos.

Segundo, openat() permite la implementación de un "directorio de trabajo actual" por hilo, a través de descriptores de archivo mantenidos por la aplicación. (Esta funcionalidad también se puede obtener mediante trucos basados en el uso de /proc/self/fd/dirfd, pero de forma menos eficiente).

El argumento dirfd para estas API se puede obtener usando open() o openat() para abrir un directorio (con la bandera O_RDONLY o O_PATH). Alternativamente, dicho descriptor de archivo se puede obtener aplicando dirfd(3) a un flujo de directorio creado usando opendir(3).

Cuando estas API reciben un argumento dirfd de AT_FDCWD o la ruta especificada es absoluta, manejan su argumento de ruta de la misma manera que las API convencionales correspondientes. Sin embargo, en este caso, varias de las API tienen un argumento flags que proporciona acceso a funcionalidades que no están disponibles con las API convencionales correspondientes.

O_DIRECT

La bandera O_DIRECT puede imponer restricciones de alineación en la longitud y la dirección de los búferes del espacio de usuario y en el desplazamiento del archivo de las E/S. En Linux, las restricciones de alineación varían según el sistema de archivos y la versión del kernel y podrían estar completamente ausentes. El manejo de E/S O_DIRECT mal alineadas también varía; pueden fallar con EINVAL o recurrir a E/S en búfer.

Desde Linux 6.1, el soporte de O_DIRECT y las restricciones de alineación para un archivo se pueden consultar usando statx(2), utilizando la bandera STATX_DIOALIGN. El soporte para STATX_DIOALIGN varía según el sistema de archivos; vea statx(2).

NOTAS

Algunos sistemas de archivos proporcionan sus propias interfaces para consultar restricciones de alineación de O_DIRECT, por ejemplo, la operación XFS_IOC_DIOINFO en xfsctl(3). Se debe utilizar STATX_DIOALIGN en su lugar cuando esté disponible.

Si ninguna de las opciones anteriores está disponible, el soporte de E/S directa y las restricciones de alineación solo se pueden inferir de las características conocidas del sistema de archivos, el archivo individual, el (los) dispositivo(s) de almacenamiento subyacente(s) y la versión del kernel. En Linux 2.4, la mayoría de los sistemas de archivos basados en dispositivos de bloque requieren que el desplazamiento del archivo y la longitud y la dirección de memoria de todos los segmentos de E/S sean múltiplos del tamaño de bloque del sistema de archivos (típicamente 4096 bytes). En Linux 2.6.0, esto se relajó al tamaño de bloque lógico del dispositivo de bloque (típicamente 512 bytes). El tamaño de bloque lógico de un dispositivo de bloque se puede determinar usando la operación ioctl(2) BLKSSZGET o desde la shell usando el comando:


blockdev --getss

Las E/S de O_DIRECT nunca deben ejecutarse concurrentemente con la llamada al sistema fork(2), si el búfer de memoria es un mapeo privado (es decir, cualquier mapeo creado con la bandera MAP_PRIVATE de mmap(2); esto incluye la memoria asignada en el heap y los búferes asignados estáticamente). Cualquiera de dichas E/S, ya sea enviada a través de una interfaz de E/S asíncrona o desde otro hilo en el proceso, debe completarse antes de llamar a fork(2). No hacerlo puede provocar corrupción de datos y comportamiento indefinido en los procesos padre e hijo. Esta restricción no se aplica cuando el búfer de memoria para las E/S de O_DIRECT se creó utilizando shmat(2) o mmap(2) con la bandera MAP_SHARED. Tampoco se aplica esta restricción cuando el búfer de memoria ha sido marcado como MADV_DONTFORK con madvise(2), asegurando que no estará disponible para el hijo después de fork(2).

La bandera O_DIRECT se introdujo en SGI IRIX, donde tiene restricciones de alineación similares a las de Linux 2.4. IRIX también tiene una llamada fcntl(2) para consultar alineaciones y tamaños apropiados. FreeBSD 4.x introdujo una bandera del mismo nombre, pero sin restricciones de alineación.

El soporte O_DIRECT se añadió en Linux 2.4.10. Los kernels de Linux anteriores simplemente ignoran esta bandera. Algunos sistemas de archivos pueden no implementar la bandera, en cuyo caso open() falla con el error EINVAL si se utiliza.

Las aplicaciones deben evitar mezclar O_DIRECT y E/S normal en el mismo archivo, y especialmente en regiones de bytes superpuestas en el mismo archivo. Incluso cuando el sistema de archivos maneja correctamente los problemas de coherencia en esta situación, el rendimiento general de E/S probablemente será más lento que el uso de cualquiera de los modos por separado. Del mismo modo, las aplicaciones deben evitar mezclar mmap(2) de archivos con E/S directa en los mismos archivos.

El comportamiento de O_DIRECT con NFS diferirá de los sistemas de archivos locales. Los kernels más antiguos, o los kernels configurados de ciertas maneras, pueden no admitir esta combinación. El protocolo NFS no admite el paso de la bandera al servidor, por lo que las E/S de O_DIRECT omitirán la caché de páginas solo en el cliente; el servidor aún puede almacenar en caché las E/S. El cliente solicita al servidor que haga que las E/S sean síncronas para preservar la semántica síncrona de O_DIRECT. Algunos servidores tendrán un rendimiento deficiente en estas circunstancias, especialmente si el tamaño de la E/S es pequeño. Algunos servidores también pueden configurarse para mentir a los clientes sobre que las E/S han llegado al almacenamiento estable; esto evitará la penalización de rendimiento a riesgo de la integridad de los datos en caso de fallo de energía del servidor. El cliente NFS de Linux no impone restricciones de alineación en las E/S de O_DIRECT.

En resumen, O_DIRECT es una herramienta potencialmente poderosa que debe usarse con precaución. Se recomienda que las aplicaciones traten el uso de O_DIRECT como una opción de rendimiento que está deshabilitada por defecto.

ERRORES

Actualmente, no es posible habilitar la E/S controlada por señales especificando O_ASYNC al llamar a open(); use fcntl(2) para habilitar esta bandera.

Se deben comprobar dos códigos de error diferentes, EISDIR y ENOENT, al intentar determinar si el kernel admite la funcionalidad de O_TMPFILE.
