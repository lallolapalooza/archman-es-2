NOMBRE

ovsdb-server - Servidor de base de datos Open vSwitch

SINOPSIS

ovsdb-server [base_de_datos]... [relay:nombre_esquema:remoto]... [--remote=remoto]... [--config-file=archivo] [--run=comando]

Opciones de demonio:
[--pidfile[=archivo_pid]] [--overwrite-pidfile] [--detach] [--no-chdir] [--no-self-confinement]
Opciones de servicio:
[--service] [--service-monitor]
Opciones de registro:
[-v[módulo[:destino[:nivel]]]]...
[--verbose[=módulo[:destino[:nivel]]]]...
[--log-file[=archivo]]
Opciones de copia de seguridad activa:
[--sync-from=servidor] [--sync-exclude-tables=bd:tabla[,bd:tabla]...] [--active]
Opciones de infraestructura de clave pública:
[--private-key=clave_privada.pem]
[--certificate=certificado.pem]
[--ca-cert=cert_ca.pem]
[--bootstrap-ca-cert=cert_ca.pem]
[--peer-ca-cert=cert_ca_par.pem]
Opciones de conexión SSL/TLS:
[--ssl-protocols=protocolos]
[--ssl-ciphers=cifrados]
[--ssl-ciphersuites=ciphersuites]
Opciones de gestión en tiempo de ejecución:
--unixctl=socket
Opciones de reproducción:
[--record[=directorio]] [--replay[=directorio]]
Opciones comunes:
[-h | --help] [-V | --version]

DESCRIPCIÓN

El programa ovsdb-server proporciona interfaces RPC a una o más bases de datos de Open vSwitch (OVSDB). Soporta conexiones cliente JSON-RPC sobre sockets TCP/IP o de dominio Unix, activos o pasivos. Para una introducción a OVSDB y su implementación en Open vSwitch, consulte ovsdb(7).

Cada archivo OVSDB puede especificarse en la línea de comandos como base_de_datos. Las bases de datos de retransmisión pueden especificarse en la línea de comandos como relay:nombre_esquema:remoto. Para una descripción detallada del argumento de la base de datos de retransmisión, consulte ovsdb(7). Si no se especifica ningún archivo de base de datos o base de datos de retransmisión, el valor predeterminado es /etc/openvswitch/conf.db. Los archivos de base de datos deben haber sido creados e inicializados previamente usando, por ejemplo, el comando create, create-cluster o join-cluster de ovsdb-tool.

Todos los tipos de bases de datos pueden ser añadidos alternativamente usando un archivo de configuración proporcionado a través de la opción --config-file. Esta opción es mutuamente excluyente con la especificación de base_de_datos en la línea de comandos. Para una descripción detallada del formato del archivo de configuración, consulte ovsdb(7).

Esta implementación de OVSDB soporta modelos de servicio de base de datos autónomos, de copia de seguridad activa, de retransmisión y agrupados, así como replicación de bases de datos. Consulte la sección Modelos de Servicio de ovsdb(7) para obtener más información.

Para bases de datos agrupadas, cuando se utiliza la opción --detach, ovsdb-server se separa sin esperar a que el servidor se una exitosamente a un grupo (si el archivo de base de datos se crea recientemente con ovsdb-tool join-cluster) o se conecte a un grupo al que ya se ha unido. Utilice ovsdb-client wait (consulte ovsdb-client(1)) para esperar hasta que el servidor se haya unido y conectado exitosamente a un grupo. Lo mismo ocurre con las bases de datos de retransmisión. Se pueden usar los mismos comandos para esperar a que una base de datos de retransmisión se conecte a la fuente de retransmisión (remoto).

Además de las bases de datos especificadas por el usuario, ovsdb-server versión 2.9 y posteriores siempre aloja una base de datos integrada llamada _Server. Consulte ovsdb-server(5) para obtener documentación sobre el esquema de esta base de datos.

OPCIONES

--remote=remoto
Añade remoto como un método de conexión utilizado por ovsdb-server. El remoto puede ser un método de conexión activo o pasivo de OVSDB, p. ej., pssl:6640, como se describe en ovsdb(7). También se admite el siguiente formato adicional:
db:bd,tabla,columna
Lee métodos de conexión adicionales de columna en todas las filas de tabla dentro de bd. A medida que el contenido de columna cambia, ovsdb-server también añade y elimina métodos de conexión en consecuencia.
Si el tipo de columna es cadena o conjunto de cadenas, entonces los métodos de conexión se toman directamente de la columna. Los métodos de conexión en la columna deben tener uno de los formatos descritos anteriormente.
Si el tipo de columna es UUID o conjunto de UUIDs y hace referencia a una tabla, cada UUID se busca en la tabla referenciada para obtener una fila. Las siguientes columnas de la fila, si están presentes y son del tipo correcto, configuran un método de conexión. Cualquier columna adicional se ignora.
target (cadena)
Método de conexión, en uno de los formatos descritos anteriormente. Esta columna es obligatoria: si falta o está vacía, no se puede configurar ningún método de conexión.
max_backoff (entero)
Número máximo de milisegundos a esperar entre intentos de conexión.
inactivity_probe (entero)
Número máximo de milisegundos de tiempo de inactividad en la conexión con el cliente antes de enviar un mensaje de sondeo de inactividad.
read_only (booleano)
Si es verdadero, solo se permiten transacciones de solo lectura en esta conexión.
Es un error que columna tenga otro tipo.
Para conectar o escuchar en varios métodos de conexión, utilice múltiples opciones --remote.
Alternativamente, los remotos pueden especificarse en una sección "remotes" del archivo de configuración, si se proporciona a través de la opción --config-file. Las opciones --config-file y --remote son mutuamente excluyentes.
--config-file=archivo
Especifica un archivo de configuración para ovsdb-server. Este archivo puede contener métodos de conexión y bases de datos utilizados por el servidor. El archivo contiene un objeto JSON con dos elementos principales:
remotes
Objeto JSON que contiene un conjunto de métodos de conexión en el siguiente formato: "target": { "opción": valor, ... }. Donde target tiene el mismo formato que remoto en la opción --remote. opción puede ser max-backoff (entero), inactivity-probe (entero), read-only (booleano), role (cadena) o dscp (entero) con sus valores permitidos respectivamente. El significado de estas opciónes es el mismo que en la configuración de remoto a través de una fila de base de datos con la opción --remote.
databases
Objeto JSON que describe las bases de datos que deben añadirse a ovsdb-server en el siguiente formato: "nombre":{ "opción": valor, ... }. Donde nombre es ya sea un nombre de archivo de una base de datos creada e inicializada previamente o un nombre de esquema en el caso de bases de datos de retransmisión. Las opciónes disponibles son:

Describe el modelo de servicio de esta base de datos. Uno de: standalone, clustered, active-backup o relay. Esta opción es obligatoria para todos los tipos, excepto para standalone y clustered. Para estas bases de datos, el modelo de servicio se inferirá del archivo, si no se especifica explícitamente. ovsdb-server se negará a agregar una base de datos si el service-model especificado no coincide con el archivo proporcionado.

Describe el método de conexión a la base de datos activa o a la fuente de retransmisión (relay). Es un objeto JSON con exactamente un elemento en el mismo formato que los elementos de "remotes", excepto que las opciones read-only y role no son aplicables. La opción --config-file es mutuamente excluyente con --remote así como con la especificación de database en la línea de comandos. También es mutuamente excluyente con todas las Opciones de Copia de Seguridad Activa y todos los COMANDOS DE GESTIÓN EN TIEMPO DE EJECUCIÓN que pueden cambiar la configuración del servidor en conflicto con el contenido del archivo, es decir, todos los comandos que manipulan remotes y bases de datos. Los comandos de solo lectura aún se pueden usar.
En caso de cambios en el archivo, los usuarios deben ejecutar el comando ovsdb-server/reload con ovs-appctl(8) para que los cambios surtan efecto.

--run=comando]
Por lo general, ovsdb-server se ejecuta de forma continua o hasta que se le indica que salga (ver COMANDOS DE GESTIÓN EN TIEMPO DE EJECUCIÓN a continuación). Con esta opción, ovsdb-server inicia en su lugar un subproceso shell que ejecuta comando. Cuando el subproceso termina, ovsdb-server también sale de forma ordenada. Si el subproceso sale normalmente con el código de salida 0, entonces ovsdb-server sale también con el código de salida 0; de lo contrario, sale con el código de salida 1.
Esta opción puede ser útil cuando un servidor de base de datos solo se necesita para ejecutar un solo comando, por ejemplo: ovsdb-server --remote=punix:socket --run='ovsdb-client dump unix:socket Open_vSwitch'
Esta opción no es compatible en la plataforma Windows.

Opciones de Demonio (Daemon)

Las siguientes opciones son válidas en plataformas basadas en POSIX.

--pidfile[=pidfile]
Causa la creación de un archivo (por defecto, ovsdb-server.pid) que indica el PID del proceso en ejecución. Si el argumento pidfile no se especifica, o si no comienza con /, se crea en /run/openvswitch.
Si no se especifica --pidfile, no se crea ningún archivo pidfile.
--overwrite-pidfile
Por defecto, cuando se especifica --pidfile y el archivo pidfile especificado ya existe y está bloqueado por un proceso en ejecución, ovsdb-server se niega a iniciarse. Especifique --overwrite-pidfile para que sobrescriba en su lugar el archivo pidfile.
Cuando no se especifica --pidfile, esta opción no tiene ningún efecto.
--detach
Ejecuta ovsdb-server como un proceso en segundo plano. El proceso se bifurca y, en el hijo, inicia una nueva sesión, cierra los descriptores de archivo estándar (lo que tiene el efecto secundario de deshabilitar el registro en la consola) y cambia su directorio actual a la raíz (a menos que se especifique --no-chdir). Después de que el hijo completa su inicialización, el padre sale. ovsdb-server se separa solo después de que comienza a escuchar en todos los remotes configurados. En este punto, todas las bases de datos standalone y active-backup están listas para usarse. Las bases de datos agrupadas (clustered) solo estarán listas para usarse después de que terminen de unirse a sus clústeres (lo que podría haber sucedido ya en ejecuciones anteriores de ovsdb-server).
--monitor
Crea un proceso adicional para monitorear el demonio ovsdb-server. Si el demonio muere debido a una señal que indica un error de programación (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU, o SIGXFSZ), el proceso monitor inicia una nueva copia de él. Si el demonio muere o sale por otra razón, el proceso monitor sale.
Esta opción normalmente se usa con --detach, pero también funciona sin ella.
--no-chdir
Por defecto, cuando se especifica --detach, ovsdb-server cambia su directorio de trabajo actual al directorio raíz después de separarse. De lo contrario, invocar ovsdb-server desde un directorio elegido descuidadamente impediría al administrador desmontar el sistema de archivos que contiene ese directorio.
Especificar --no-chdir suprime este comportamiento, impidiendo que ovsdb-server cambie su directorio de trabajo actual. Esto puede ser útil para recopilar volcados de memoria (core dumps), ya que es un comportamiento común escribir volcados de memoria en el directorio de trabajo actual y el directorio raíz no es un buen directorio para usar.
Esta opción no tiene efecto cuando no se especifica --detach.
--no-self-confinement
Por defecto, el demonio intentará auto-restringirse para trabajar con archivos en directorios conocidos determinados durante la compilación. Es mejor apegarse a este comportamiento predeterminado y no usar esta bandera a menos que se utilice algún otro Control de Acceso para restringir el demonio. Tenga en cuenta que, a diferencia de otras implementaciones de control de acceso que se aplican típicamente desde el espacio del kernel (por ejemplo, DAC o MAC), la auto-restricción se impone desde el demonio del espacio de usuario y, por lo tanto, no debe considerarse como una estrategia de confinamiento completa, sino más bien como una capa adicional de seguridad.
--user
Causa que ovsdb-server se ejecute como un usuario diferente especificado en "user:group", soltando así la mayoría de los privilegios de root. También se permiten las formas cortas "user" y ":group", asumiendo el usuario o grupo actual respectivamente. Solo los demonios iniciados por el usuario root aceptan este argumento.
En Linux, a los demonios se les otorgará CAP_IPC_LOCK y CAP_NET_BIND_SERVICES antes de soltar los privilegios de root. A los demonios que interactúan con un plano de datos (datapath), como ovs-vswitchd, se les otorgarán tres capacidades adicionales, a saber, CAP_NET_ADMIN, CAP_NET_BROADCAST y CAP_NET_RAW. El cambio de capacidad se aplicará incluso si el nuevo usuario es root.
En Windows, esta opción no es compatible actualmente. Por razones de seguridad, especificar esta opción hará que el proceso demonio no se inicie.

Opciones de Servicio

Las siguientes opciones solo son válidas en la plataforma Windows.

--service
Hace que ovsdb-server se ejecute como un servicio en segundo plano. El servicio ya debería haber sido creado a través de herramientas externas como SC.exe.
--service-monitor
Hace que el servicio ovsdb-server sea reiniciado automáticamente por el administrador de servicios de Windows si el servicio muere o sale por razones inesperadas.
Cuando no se especifica --service, esta opción no tiene ningún efecto.

Establece el nivel máximo de detalle de registro, equivalente a --verbose=dbg.
-vPATTERN:destino:patrón

--verbose=PATTERN:destino:patrón
Establece el patrón de registro para destino a patrón. Consulte ovs-appctl(8) para una descripción de la sintaxis válida para patrón.
-vFACILITY:instalación

--verbose=FACILITY:instalación
Establece la instalación RFC5424 del mensaje de registro. instalación puede ser uno de kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 o local7. Si esta opción no se especifica, se utiliza daemon como valor predeterminado para el registro del sistema local y se utiliza local0 al enviar un mensaje al destino proporcionado a través de la opción --syslog-target.
--log-file[=archivo]
Habilita el registro en un archivo. Si se especifica archivo, se utiliza como el nombre exacto para el archivo de registro. El nombre de archivo de registro predeterminado que se utiliza si se omite archivo es /var/log/openvswitch/ovsdb-server.log.
--syslog-target=host:puerto
Envía mensajes syslog al puerto UDP en host, además del syslog del sistema. El host debe ser una dirección IP numérica, no un nombre de host.
--syslog-method=método
Especifica el método mediante el cual se deben enviar los mensajes syslog al demonio syslog. Se admiten las siguientes formas:
  • libc, utiliza la función syslog() de libc. La desventaja de usar esta opción es que libc agrega un prefijo fijo a cada mensaje antes de que se envíe realmente al demonio syslog a través del socket de dominio UNIX /dev/log.
  • unix:archivo, utiliza directamente un socket de dominio UNIX. Es posible especificar un formato de mensaje arbitrario con esta opción. Sin embargo, las versiones anteriores de rsyslogd, 8.9 y anteriores, utilizan de todos modos una función de análisis codificada que limita el uso del socket de dominio UNIX. Si desea utilizar un formato de mensaje arbitrario con versiones anteriores de rsyslogd, utilice un socket UDP a la dirección IP de localhost en su lugar.
  • udp:ip:puerto, utiliza un socket UDP. Con este método es posible utilizar un formato de mensaje arbitrario también con versiones anteriores de rsyslogd. Al enviar mensajes syslog a través de un socket UDP, se deben tener precauciones adicionales, por ejemplo, el demonio syslog debe configurarse para escuchar en el puerto UDP especificado, las reglas de iptables accidentales podrían interferir con el tráfico syslog local y existen algunas consideraciones de seguridad que se aplican a los sockets UDP, pero no se aplican a los sockets de dominio UNIX.
  • null, descarta todos los mensajes registrados en syslog.
El valor predeterminado se toma de la variable de entorno OVS_SYSLOG_METHOD; si no está establecida, el valor predeterminado es libc.

Opciones de Copia de Seguridad Activa

Estas opciones admiten el modelo de servicio de copia de seguridad activa y la replicación de bases de datos de ovsdb-server. Estas opciones se aplican solo a bases de datos en el formato utilizado para bases de datos independientes y de copia de seguridad activa, que es el formato de base de datos creado por ovsdb-tool create. Por predeterminado, al servir una base de datos en este formato, ovsdb-server se ejecuta como un servidor independiente. Estas opciones pueden configurarlo para uso de copia de seguridad activa:

  • Utilice --sync-from=servidor para iniciar el servidor en el rol de copia de seguridad, replicando datos desde servidor. Cuando ovsdb-server se ejecuta como servidor de copia de seguridad, rechaza todas las transacciones que pueden modificar el contenido de la base de datos, incluidos los comandos de bloqueo. La misma forma se puede utilizar para configurar la base de datos local como una réplica de servidor.
  • Utilice --sync-from=servidor --active para iniciar el servidor en el rol activo, pero preparado para cambiar al rol de copia de seguridad en el que replicaría datos desde servidor. Cuando ovsdb-server se ejecuta en modo activo, permite todas las transacciones, incluidas las que modifican la base de datos.

En tiempo de ejecución, los comandos de administración pueden cambiar el rol de un servidor y, de lo contrario, administrar las funciones de copia de seguridad activa. Consulte Comandos de Copia de Seguridad Activa, a continuación, para obtener más información.

--sync-from=servidor
Configura ovsdb-server para sincronizar sus bases de datos con las bases de datos en servidor, que debe ser un método de conexión activo en una de las formas documentadas en ovsdb-client(1). Cada transacción confirmada por servidor se replicará a ovsdb-server. Esta opción hace que ovsdb-server se inicie como un servidor de copia de seguridad; agregue --active para que se inicie como un servidor activo.
--sync-exclude-tables=db:tabla[,db:tabla]...
Hace que las tablas especificadas se excluyan de la replicación.
--active
Por defecto, --sync-from hace que ovsdb-server se inicie como una copia de seguridad para servidor. Sin embargo, con --active, ovsdb-server se inicia como un servidor activo. Utilice esta opción para permitir que las opciones de sincronización se especifiquen mediante opciones de línea de comandos, pero inicie el servidor, como servidor activo predeterminado. Para cambiar el servidor en ejecución al modo de copia de seguridad, utilice ovs-appctl(1) para ejecutar el comando ovsdb-server/connect-active-ovsdb-server.

Estas opciones son mutuamente excluyentes con --config-file.

Opciones de Infraestructura de Clave Pública

Las opciones descritas a continuación para configurar la infraestructura de clave pública SSL aceptan una sintaxis especial para obtener su configuración de la base de datos. Si alguna de estas opciones recibe db:db,tabla,columna como argumento, entonces el nombre de archivo real se lee de la columna especificada en tabla dentro de la base de datos db. La columna debe tener el tipo cadena o conjunto de cadenas. La primera cadena no vacía en la tabla se toma como el nombre del archivo. (Esto significa que normalmente debería haber como máximo una fila en tabla).

-p privkey.pem

--private-key=privkey.pem
Especifica un archivo PEM que contiene la clave privada utilizada como identidad de ovsdb-server para conexiones SSL/TLS salientes.
-c cert.pem

--certificate=cert.pem
Especifica un archivo PEM que contiene un certificado que certifica que la clave privada especificada en -p o --private-key es de confianza. El certificado debe ser firmado por la autoridad certificadora (CA) que el par en las conexiones SSL/TLS utilizará para verificarlo.
-C cacert.pem

--ca-cert=cacert.pem
Especifica un archivo PEM que contiene el certificado CA que ovsdb-server debe utilizar para verificar los certificados presentados por los pares SSL/TLS. (Este puede ser el mismo certificado que los pares SSL/TLS utilizan para verificar el certificado especificado en -c o --certificate, o puede ser uno diferente, dependiendo del diseño de PKI en uso).
-C none

--ca-cert=none
Deshabilita la verificación de los certificados presentados por los pares SSL/TLS. Esto introduce un riesgo de seguridad, ya que significa que los certificados no se pueden verificar como los de hosts conocidos y de confianza.
--bootstrap-ca-cert=cacert.pem
Cuando existe cacert.pem, esta opción tiene el mismo efecto que -C o --ca-cert. Si no existe, entonces ovsdb-server intentará obtener el certificado CA del par SSL/TLS en su primera conexión SSL/TLS y lo guardará en el archivo PEM con nombre. Si tiene éxito, descartará inmediatamente la conexión y la volverá a conectar, y a partir de entonces todas las conexiones SSL/TLS deberán ser autenticadas por un certificado firmado por el certificado CA obtenido de esa manera.
Esta opción expone la conexión SSL/TLS a un ataque de hombre en el medio al obtener el certificado CA inicial, pero puede ser útil para el arranque.
Esta opción solo es útil si el par SSL/TLS envía su certificado CA como parte de la cadena de certificados SSL/TLS. Los protocolos SSL/TLS no requieren que el servidor envíe el certificado CA.
Esta opción es mutuamente excluyente con -C y --ca-cert.
--peer-ca-cert=peer-cacert.pem
Especifica un archivo PEM que contiene uno o más certificados adicionales para enviar a los pares SSL/TLS. peer-cacert.pem debe ser el certificado CA utilizado para firmar el propio certificado de ovsdb-server, es decir, el certificado especificado en -c o --certificate. Si el certificado de ovsdb-server es autofirmado, entonces --certificate y --peer-ca-cert deben especificar el mismo archivo.
Esta opción no es útil en funcionamiento normal, porque el par SSL/TLS ya debe tener el certificado CA para que el par tenga alguna confianza en la identidad de ovsdb-server.
y. Sin embargo, esto ofrece una forma para que una nueva instalación arranque el certificado de CA en su primera conexión SSL/TLS.

Opciones de conexión SSL

--ssl-protocols=protocolos
Especifica un rango o una lista de protocolos SSL/TLS delimitada por comas o espacios que ovsdb-server habilitará para las conexiones SSL/TLS. Los protocolos admitidos incluyen TLSv1 (obsoleto), TLSv1.1 (obsoleto), TLSv1.2 y TLSv1.3. Los rangos se pueden proporcionar en forma de dos nombres de protocolo separados por un guion, o como un solo nombre de protocolo con un signo más. Por ejemplo, use TLSv1.1-TLSv1.3 para permitir TLSv1.1, TLSv1.2 y TLSv1.3. Use TLSv1.2+ para permitir TLSv1.2 y cualquier protocolo posterior. La opción acepta una lista de protocolos o exactamente un rango. El rango es la forma preferida de especificar los protocolos y la opción siempre se comporta como si se proporcionara el rango entre la versión mínima y máxima especificada; es decir, si la opción se establece en TLSv1.1,TLSv1.3, también se habilitará TLSv1.2 como si fuera un rango. Independientemente del orden, se elegirá el protocolo más alto admitido por ambas partes al establecer la conexión. El valor predeterminado cuando se omite esta opción es TLSv1.2 o posterior.
--ssl-ciphers=cifrados
Especifica, en formato de cadena de cifrado OpenSSL, los cifrados que ovsdb-server admitirá para conexiones SSL/TLS con TLSv1.2 y anteriores. El valor predeterminado cuando se omite esta opción es DEFAULT:@SECLEVEL=2.
--ssl-ciphersuites=conjuntos-de-cifrado
Especifica, en formato de cadena de conjuntos de cifrado OpenSSL, los conjuntos de cifrado que ovsdb-server admitirá para conexiones SSL/TLS con TLSv1.3 y posteriores. El valor predeterminado de OpenSSL se utilizará cuando se omita esta opción.

Otras opciones

--unixctl=socket
Establece el nombre del socket de control en el que ovsdb-server escucha los comandos de administración en tiempo de ejecución (consulte COMANDOS DE ADMINISTRACIÓN EN TIEMPO DE EJECUCIÓN, más abajo). Si socket no comienza con /, se interpreta como relativo a /run/openvswitch. Si no se usa --unixctl, el socket predeterminado es /run/openvswitch/ovsdb-server.pid.ctl, donde pid es el ID de proceso de ovsdb-server.
En Windows, se utiliza una tubería con nombre local para escuchar los comandos de administración en tiempo de ejecución. Se crea un archivo en la ruta absoluta indicada por socket o, si no se usa --unixctl en absoluto, se crea un archivo como ovsdb-server.ctl en el directorio configurado OVS_RUNDIR. El archivo existe solo para imitar el comportamiento de un socket de dominio Unix.
Especificar none para socket deshabilita la función de socket de control.
--record[=directorio]
Establece el proceso en modo de "grabación", en el que registrará todas las conexiones, los datos de los flujos (sockets de dominio Unix y de red) y algunos otros bits importantes necesarios, para que puedan ser reproducidos más tarde. Los datos grabados se almacenan en archivos de reproducción en el directorio especificado. Si directorio no comienza con /, se interpreta como relativo a /run/openvswitch. Si no se especifica directorio, se utilizará /run/openvswitch.
--replay[=directorio]
Establece el proceso en modo de "reproducción", en el que leerá la información sobre conexiones, datos de flujos (sockets de dominio Unix y de red) y algunos otros bits necesarios directamente de los archivos de reproducción en lugar de usar sockets reales. Se utilizarán los archivos de reproducción del directorio. Si directorio no comienza con /, se interpreta como relativo a /run/openvswitch. Si no se especifica directorio, se utilizará /run/openvswitch.

COMANDOS DE ADMINISTRACIÓN EN TIEMPO DE EJECUCIÓN

ovs-appctl(8) puede enviar comandos a un proceso en ejecución de ovsdb-server. Los comandos actualmente admitidos se describen a continuación.

Comandos de ovsdb-server

Estos comandos son específicos de ovsdb-server.

exit
Provoca la terminación elegante de ovsdb-server.
ovsdb-server/compact [bd]
Compacta la base de datos bd en el lugar. Si no se especifica bd, compacta todas las bases de datos en el lugar. Una base de datos también se compacta automáticamente cuando se registra una transacción si es más de 2 veces el tamaño de su tamaño compactado anterior (y al menos 10 MB), pero no antes de que se agreguen 100 confirmaciones o hayan transcurrido 10 minutos desde la última compactación. También se compactará automáticamente después de 24 horas desde la última compactación si se agregaron 100 confirmaciones, independientemente de su tamaño.
ovsdb-server/memory-trim-on-compaction activado|desactivado
Si esta opción está activada, ovsdb-server intentará recuperar toda la memoria de montón no utilizada al sistema después de cada compactación de base de datos exitosa para reducir el consumo de memoria del proceso. Desactivado por defecto.
ovsdb-server/reconnect
Hace que ovsdb-server desconecte todas las conexiones JSON-RPC con los clientes de la base de datos y se reconecte.
Este comando puede ser útil para depurar problemas con los clientes de la base de datos.
ovsdb-server/add-remote remoto
Agrega un remoto, como si se hubiera especificado --remote=remoto en la línea de comandos de ovsdb-server. (Si remoto ya es un remoto, este comando se ejecuta correctamente sin cambiar la configuración).
Mutuamente excluyente con la opción --config-file.
ovsdb-server/remove-remote remoto
Elimina el remoto especificado de la configuración, fallando con un error si remoto no está configurado como remoto. Este comando solo funciona con remotos que fueron nombrados en --remote o ovsdb-server/add-remote; es decir, no eliminará remotos agregados indirectamente porque se leyeron de la base de datos configurando un remoto db:bd,tabla,columna. (Puede eliminar una fuente de base de datos con ovsdb-server/remove-remote db:bd,tabla,columna, pero no remotos individuales encontrados indirectamente a través de la base de datos).
Mutuamente excluyente con la opción --config-file.
ovsdb-server/list-remotes
Muestra una lista de los remotos actualmente configurados nombrados en --remote o ovsdb-server/add-remote; es decir, no muestra los remotos agregados indirectamente porque se leyeron de la base de datos al configurar un remoto db:bd,tabla,columna.
ovsdb-server/add-db base-de-datos
Agrega la base-de-datos al ovsdb-server en ejecución. base-de-datos puede ser un archivo de base de datos o una descripción de relé en el siguiente formato: relay:schema_name:remote. El archivo de base de datos ya debe haber sido creado e inicializado usando, por ejemplo, ovsdb-tool create.
Mutuamente excluyente con la opción --config-file.
ovsdb-server/remove-db base-de-datos
Elimina la base-de-datos del ovsdb-server en ejecución. base-de-datos debe ser un nombre de base de datos como los que se muestran en ovsdb-server/list-dbs.
Si se ha configurado un remoto que apunta a la base-de-datos especificada (por ejemplo, --remote=db:base-de-datos,... en la línea de comandos), se deshabilitará hasta que se agregue nuevamente otra base de datos con el mismo nombre (con ovsdb-server/add-db).
Cualquier opción de infraestructura de clave pública especificada a través de esta base de datos (por ejemplo, --private-key=db:base-de-datos,... en la línea de comandos) se deshabilitará hasta que se agregue nuevamente otra base de datos con el mismo nombre (con ovsdb-server/add-db).
Mutuamente excluyente con la opción --config-file.
ovsdb-server/list-dbs
Muestra una lista de las bases de datos actualmente configuradas, agregadas a través de la línea de comandos o del comando ovsdb-server/add-db.
ovsdb-server/tlog-set base-de-datos:tabla activado|desactivado
Habilita o deshabilita el registro de todas las operaciones ejecutadas en la base de datos y tabla especificadas. Los registros se generan a nivel INFO y están limitados en tasa.
ovsdb-server/tlog-list
Muestra el estado de registro para todas las bases de datos y tablas configuradas actualmente.

Comandos de replicación

ovsdb-server/set-active-ovsdb-server server
Establece el servidor desde el cual ovsdb-server sincronizará actualmente sus bases de datos. Esto anula la opción de línea de comandos --sync-from.
ovsdb-server/get-active-ovsdb-server
Obtiene el servidor activo desde el cual ovsdb-server está sincronizando actualmente sus bases de datos.
ovsdb-server/connect-active-ovsdb-server
Cambia el servidor a un rol de respaldo. El servidor comienza a sincronizar sus bases de datos con el servidor activo especificado por ovsdb-server/set-active-ovsdb-server (o la opción de línea de comandos --sync-from) y cierra todas las conexiones de clientes existentes, lo que requiere que los clientes se reconecten.
ovsdb-server/disconnect-active-ovsdb-server
Cambia el servidor a un rol activo. El servidor deja de sincronizar sus bases de datos con un servidor activo y cierra todas las conexiones de clientes existentes, lo que requiere que los clientes se reconecten.
ovsdb-server/set-active-ovsdb-server-probe-interval intervalo de sondeo
Establece el intervalo de sondeo (en milisegundos) para la conexión al servidor activo.
ovsdb-server/set-sync-exclude-tables db:tabla[,db:tabla]...
Establece la tabla dentro de db que será excluida de la sincronización. Esto anula la opción de línea de comandos --sync-exclude-tables.
ovsdb-server/get-sync-exclude-tables
Obtiene las tablas que están actualmente excluidas de la sincronización.
ovsdb-server/sync-status
Imprime un resumen de la información del tiempo de ejecución de la replicación. La información de estado siempre se proporciona, indicando si el servidor se está ejecutando en modo activo o de respaldo. Para todas las bases de datos con el modelo de servicio activo-respaldo, se muestra el estado de la conexión de replicación, que puede ser conectando, replicando o error. Cuando la conexión está en estado de replicando, la salida adicional muestra las tablas que están actualmente excluidas de la replicación.

Comandos de clúster

Estos comandos admiten el modelo de servicio de clúster de ovsdb-server. Solo se aplican a las bases de datos en el formato utilizado para bases de datos agrupadas, que es el formato de base de datos creado por ovsdb-tool create-cluster y ovsdb-tool join-cluster.

cluster/cid db
Imprime el ID del clúster para db, que es un UUID que identifica al clúster. Si db es una base de datos recién creada por ovsdb-tool cluster-join que aún no se ha unido correctamente a su clúster, y no se especificó --cid en la línea de comandos de cluster-join, entonces este comando informará un error porque el ID del clúster aún no se conoce.
cluster/sid db
Imprime el ID del servidor para db, que es un UUID que identifica a este servidor dentro del clúster.
cluster/status db
Imprime el estado de este servidor dentro del clúster y el estado de sus conexiones con otros servidores del clúster.
cluster/leave db
Este comando inicia la eliminación controlada del servidor del clúster. Debe permanecer al menos un servidor y el clúster debe estar en buen estado, es decir, más de la mitad de los servidores del clúster deben estar en línea.
Cuando el servidor abandona el clúster con éxito, deja de servir db, como si se hubiera ejecutado ovsdb-server/remove-db db.
Use ovsdb-client wait (ver ovsdb-client(1)) para esperar hasta que el servidor haya abandonado el clúster.
Una vez que un servidor abandona un clúster, nunca puede volver a unirse a él. En su lugar, cree un nuevo servidor y únase al clúster.
Tenga en cuenta que la eliminación del servidor del clúster altera el tamaño total del clúster. Por ejemplo, si elimina dos servidores de un clúster de tres servidores, el "clúster" se convierte en un solo servidor funcional. Esto no resulta en un clúster de tres servidores que carece de quórum.
cluster/kick db servidor
Inicia la eliminación controlada de servidor del clúster de db, similar a cluster/leave, excepto que puede eliminar cualquier servidor, no solo este.
servidor puede ser un ID de servidor, como el impreso por cluster/sid, o la dirección de red local del servidor pasada al comando create-cluster o join-cluster de ovsdb-tool. Use cluster/status para ver una lista de los miembros del clúster.
cluster/change-election-timer db tiempo
Cambia el valor base del tiempo de espera de la elección del líder del clúster, en milisegundos.
Un seguidor iniciará la elección del líder si no se recibe ninguna señal de latido del líder dentro de este tiempo más un tiempo aleatorio dentro de 1 segundo.
El valor predeterminado es 1000, si no se cambia con este comando. Este comando se puede usar para ajustar el valor cuando sea necesario, según la carga esperada y el tiempo de respuesta de los servidores.
Este comando debe ejecutarse en el líder. Inicia el cambio en el clúster. Para ver si el cambio surte efecto (se confirma), use cluster/status para mostrar la configuración actual. Una vez que un cambio se confirma, persiste en los reinicios del servidor.
cluster/set-backlog-threshold db n_mensajes n_bytes
Establece los límites de la cola para las conexiones RAFT de db a un máximo de n_mensajes mensajes o n_bytes bytes. Si la cola en una de las conexiones alcanza el límite, se desconectará (y se restablecerá). Los valores se comprueban solo si la cola contiene más de 50 mensajes.

Estos comandos administran la configuración de registro de ovsdb-server.

vlog/set [especificación]
Establece los niveles de registro. Sin ninguna especificación, establece el nivel de registro para cada módulo y destino en dbg. De lo contrario, especificación es una lista de palabras separadas por espacios, comas o dos puntos, hasta una de cada categoría a continuación:

En la plataforma Windows, se acepta syslog como palabra y solo es útil junto con la opción --syslog-target (la palabra no tiene efecto de lo contrario).
•
off, emer, err, warn, info o dbg, para controlar el nivel de registro. Se registrarán los mensajes de la severidad dada o superior, y los mensajes de menor severidad se filtrarán. off filtra todos los mensajes. Consulte ovs-appctl(8) para una definición de cada nivel de registro.

vlog/list
Enumera los módulos de registro compatibles y sus niveles actuales.
vlog/list-pattern
Enumera los patrones de registro utilizados para cada destino.
vlog/close
Hace que ovsdb-server cierre su archivo de registro, si está abierto. (Use vlog/reopen para reabrirlo más tarde).
vlog/reopen
Hace que ovsdb-server cierre su archivo de registro, si está abierto, y luego lo reabra. (Esto es útil después de rotar los archivos de registro, para hacer que se utilice un nuevo archivo de registro).
Esto no tiene ningún efecto a menos que ovsdb-server se haya invocado con la opción --log-file.
vlog/disable-rate-limit [módulo]...

vlog/enable-rate-limit [módulo]...
Por defecto, ovsdb-server limita la velocidad a la que se pueden registrar ciertos mensajes. Cuando un mensaje aparece con más frecuencia que el límite, se suprime. Esto ahorra espacio en disco, hace que los registros sean más fáciles de leer y acelera la ejecución, pero ocasionalmente la solución de problemas requiere más detalles. Por lo tanto, vlog/disable-rate-limit permite deshabilitar los límites de velocidad a nivel de un módulo de registro individual. Especifique uno o más nombres de módulo, como se muestra en el comando vlog/list. Especificar ningún nombre de módulo o la palabra clave any deshabilita los límites de velocidad para todos los módulos de registro.
El comando vlog/enable-rate-limit, cuya sintaxis es la misma que vlog/disable-rate-limit, se puede utilizar para volver a habilitar un límite de velocidad que se deshabilitó previamente.

NAME

ovsdb-server

Open vSwitch database server

SYNOPSIS

<ovsdb-server [OPTION]... [DATABASE]...

DESCRIPTION

ovsdb-server is the server component of the Open vSwitch database management protocol. It accepts database connections from clients over JSON-RPC, manages the database content, and applies changes to Open vSwitch.

A single ovsdb-server instance can manage multiple databases. The databases to be managed are specified as command-line arguments. If no databases are specified, ovsdb-server will attempt to load conf.db from the Open vSwitch configuration directory.

The configuration file format is described in ovsdb-server(5).

Most runtime operations on ovsdb-server are performed using the ovsdb-client utility, although some management commands are available directly through the ovsdb-server command-line interface.

OPTIONS

The following options are accepted:

-d DIR
--data-dir=DIR
Specifies the directory that contains the database files. If not specified, ovsdb-server will use the default data directory (typically /var/lib/openvswitch/db).
-p FILE
--pidfile=FILE
Writes the process ID of the main ovsdb-server process to FILE. If not specified, no PID file is written.
-r REMOTE
--remote=REMOTE
Adds REMOTE to the set of servers that ovsdb-server will listen on for incoming JSON-RPC connections. REMOTE can be a network address (e.g. 127.0.0.1:6640 or [::1]:6640) or a Unix socket path (e.g. /var/run/openvswitch/db.sock). If this option is not specified, ovsdb-server will listen on the default Unix socket (/var/run/openvswitch/db.sock) and the default TCP port (6640).
--local-address=LOCAL-ADDRESS
Specifies the local IP address to bind to when listening on TCP sockets. This option is only effective when REMOTE specifies a TCP address. If not specified, ovsdb-server binds to all available local IP addresses.
--unix-group=GROUP
Specifies the group that should own the Unix domain sockets used for JSON-RPC communication. If not specified, the default is the group that owns the Open vSwitch data directory.
--no-chdir
Do not change the current directory to the data directory. This is useful for debugging or when running ovsdb-server from an environment where changing directories is not desired.
--detach
Run as a background daemon. If this option is not specified, ovsdb-server will run in the foreground.
--overwrite-schema
If specified, ovsdb-server will overwrite any existing schema file in the data directory with the default schema file when starting up. This is useful for resetting the schema to its default state.
--log-file=FILE
Logs messages to FILE. If not specified, messages are logged to stderr.
--syslog
Log messages to syslog instead of stderr. This option is ignored if --log-file is also specified.
-v
Sets the logging level to INFO. This option can be specified multiple times to increase the verbosity.
--log-error
Sets the logging level to ERR.
--log-warn
Sets the logging level to WARN.
--log-info
Sets the logging level to INFO.
--log-dbg
Sets the logging level to DBG.
-h
--help
Display a help message and exit.
-V
--version
Print version information on standard output and exit.

RUNTIME MANAGEMENT COMMANDS

The following commands can be used to manage a running ovsdb-server process via the ovsdb-client utility.

memory-usage
Displays the current memory usage of ovsdb-server. This is useful for monitoring memory consumption and identifying potential memory leaks. ovsdb-server also logs this information soon after startup and periodically as its memory consumption grows.

COVERAGE COMMANDS

These commands manage ovsdb-server's ``coverage counters,'' which count the number of times particular events occur during a daemon's runtime. In addition to these commands, ovsdb-server automatically logs coverage counter values, at INFO level, when it detects that the daemon's main loop takes unusually long to run.

Coverage counters are useful mainly for performance analysis and debugging.

coverage/show
Displays the averaged per-second rates for the last few seconds, the last minute and the last hour, and the total counts of all of the coverage counters.
coverage/read-counter counter
Displays the total count for the given coverage counter.

BUGS

In Open vSwitch before version 2.4, when ovsdb-server sent JSON-RPC error responses to some requests, it incorrectly formulated them with the result and error swapped, so that the response appeared to indicate success (with a nonsensical result) rather than an error. The requests that suffered from this problem were:

transact

get_schema
Only if the request names a nonexistent database.
monitor

lock

unlock
In all error cases.

Of these cases, the only error that a well-written application is likely to encounter in practice is monitor of tables or columns that do not exist, in an situation where the application has been upgraded but the old database schema is still temporarily in use. To handle this situation gracefully, we recommend that clients should treat a monitor response with a result that contains an error key-value pair as an error (assuming that the database being monitored does not contain a table named error).
