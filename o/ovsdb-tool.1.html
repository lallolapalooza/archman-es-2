NOMBRE

ovsdb-tool - Utilidad de gestión de bases de datos de Open vSwitch

SINOPSIS

Comandos de creación de base de datos:
ovsdb-tool [opciones] create [db [esquema]]
ovsdb-tool [opciones] [--election-timer=ms] create-cluster db contenidos dirección
ovsdb-tool [opciones] [--cid=uuid] join-cluster db nombre local remoto...
Comandos de gestión de versión:
ovsdb-tool [opciones] convert [db [esquema [destino]]]
ovsdb-tool [opciones] needs-conversion [db [esquema]]
ovsdb-tool [opciones] db-version [db]
ovsdb-tool [opciones] schema-version [esquema]
ovsdb-tool [opciones] db-cksum [db]
ovsdb-tool [opciones] schema-cksum [esquema]
ovsdb-tool [opciones] compare-versions a op b
Otros comandos:
ovsdb-tool [opciones] compact [db [destino]]
ovsdb-tool [opciones] [--rbac-role=rol] query [db] transacción
ovsdb-tool [opciones] [--rbac-role=rol] transact [db] transacción
ovsdb-tool [opciones] [-m | --more]... show-log [db]
ovsdb-tool [opciones] check-cluster db...
ovsdb-tool [opciones] db-name [db]
ovsdb-tool [opciones] schema-name [esquema]
ovsdb-tool [opciones] db-cid db
ovsdb-tool [opciones] db-sid db
ovsdb-tool [opciones] db-local-address db
ovsdb-tool help
Opciones de registro:
[-v[módulo[:destino[:nivel]]]]...
[--verbose[=módulo[:destino[:nivel]]]]...
[--log-file[=archivo]]
Opciones comunes:
[-h | --help] [-V | --version]

DESCRIPCIÓN

El programa ovsdb-tool es una herramienta de línea de comandos para gestionar archivos de base de datos Open vSwitch (OVSDB). No interactúa directamente con servidores de bases de datos Open vSwitch en ejecución (en su lugar, use ovsdb-client). Para una introducción a OVSDB y su implementación en Open vSwitch, consulte ovsdb(7).

Cada comando que toma un argumento opcional db o esquema tiene una ubicación de archivo predeterminada si no se especifica. El db predeterminado es /etc/openvswitch/conf.db. El esquema predeterminado es /usr/share/openvswitch/vswitch.ovsschema.

Esta implementación de OVSDB admite modelos de servicio de base de datos independientes y de respaldo activo con un formato de archivo en disco y un modelo de servicio de base de datos agrupado con un formato diferente. ovsdb-tool admite ambos formatos, pero algunos comandos son apropiados solo para un formato, como se documenta para comandos individuales a continuación. Para una especificación de estos formatos, consulte ovsdb(5). Para obtener más información sobre los modelos de servicio de OVSDB, consulte la sección Modelos de Servicio en ovsdb(7).

Comandos de creación de base de datos

Estos comandos crean un nuevo archivo de base de datos OVSDB. No sobrescribirán un archivo de base de datos existente. Para reemplazar una base de datos existente con una nueva, primero elimine la antigua.

create [db [esquema]]
Utilice este comando para crear la base de datos para controlar ovs-vswitchd u otra base de datos independiente o de respaldo activo. Crea el archivo de base de datos db con el esquema dado, que debe ser el nombre de un archivo que contenga un esquema OVSDB en formato JSON, según se especifica en la especificación OVSDB. La nueva base de datos está inicialmente vacía. (Puede usar cp para copiar una base de datos, incluyendo tanto su esquema como sus datos).
[--election-timer=ms] create-cluster db contenidos local
Utilice este comando para inicializar el primer servidor en un clúster de alta disponibilidad de 3 (o más) servidores de bases de datos, por ejemplo, para una base de datos en un entorno que no puede tolerar un único punto de fallo. Crea el archivo de base de datos agrupado db y configura el servidor para escuchar en local, que debe tener el formato protocolo:ip:puerto, donde protocolo es tcp o ssl, ip es la IP del servidor (una dirección IPv4 o una dirección IPv6 entre corchetes), y puerto es un número de puerto TCP. Solo se especifica una dirección, para el primer servidor del clúster, normalmente la del servidor que ejecuta create-cluster. La dirección se utiliza para la comunicación dentro del clúster, no para la comunicación con clientes OVSDB, y no debe usar el mismo puerto utilizado para el protocolo OVSDB.
La nueva base de datos se inicializa con contenidos, que debe nombrar un archivo que contenga un esquema OVSDB en formato JSON o una base de datos OVSDB independiente. Si es un archivo de esquema, la nueva base de datos estará inicialmente vacía, con el esquema dado. Si es un archivo de base de datos, la nueva base de datos tendrá el mismo esquema y contenido.
La elección de líder será iniciada por un seguidor si no se recibe ninguna señal de latido del líder del clúster dentro del temporizador de elección especificado. El temporizador de elección de líder predeterminado es de 1000 milisegundos. Para usar un valor diferente al crear la base de datos, especifique --election-timer=ms, donde ms es un valor en milisegundos entre 100 y 600000 inclusive.
[--cid=uuid] join-cluster db nombre local remoto...
Utilice este comando para inicializar cada servidor después del primero en un clúster de alta disponibilidad OVSDB. Crea el archivo de base de datos agrupado db para una base de datos llamada nombre, y configura el servidor para escuchar en local y para conectarse inicialmente a remoto, que debe ser un servidor que ya pertenezca al clúster. local y remoto usan la misma sintaxis protocolo:ip:puerto que create-cluster.
El nombre debe ser el nombre del esquema o base de datos pasado a create-cluster. Por ejemplo, el nombre del esquema de base de datos OVN Southbound es OVN_Southbound. Use el comando schema-name u db-name de ovsdb-tool para averiguar el nombre de un esquema o base de datos, respectivamente.
Este comando no realiza ningún acceso de red, lo que significa que no puede unir realmente el nuevo servidor al clúster. En su lugar, el archivo db que crea prepara al servidor para unirse al clúster la primera vez que ovsdb-server lo sirva. Como parte de la unión al clúster, el nuevo servidor recupera el esquema de la base de datos y obtiene la lista de todos los miembros del clúster. Solo después de eso se convierte en un miembro completo del clúster.
Opcionalmente, se pueden especificar varios remoto; por ejemplo, en un clúster que ya contiene varios servidores, se podrían especificar todos los servidores existentes. Esto es beneficioso si algunos de los servidores existentes están inactivos mientras se une el nuevo servidor, pero no es necesario en otros casos.
Por defecto, la db creada por join-cluster se unirá a cualquier base de datos agrupada llamada nombre que esté disponible en un remoto. En teoría, si las máquinas suben y bajan y las direcciones IP cambian de la manera correcta, podría unirse al clúster de base de datos equivocado. Para evitar esta posibilidad, especifique --cid=uuid, donde uuid es el ID del clúster al que unirse, como se imprime con ovsdb-tool get-cid.

Comandos de gestión de versiones

Un esquema de OVSDB tiene un número de versión de esquema, y una base de datos de OVSDB incorpora una versión particular de un esquema de OVSDB. Estos números de versión tienen el formato x.y.z, por ejemplo, 1.2.3. La implementación de OVSDB no impone un esquema de numeración de versiones particular, pero los esquemas gestionados dentro del proyecto Open vSwitch utilizan el siguiente enfoque. Cada vez que el esquema de la base de datos se cambia de una manera no compatible con versiones anteriores (por ejemplo, eliminando una columna o una tabla), se incrementa x (y y y z se restablecen a 0). Cuando el esquema de la base de datos se cambia de manera compatible con versiones anteriores (por ejemplo, agregando una nueva columna), se incrementa y (y z se restablece a 0). Cuando el esquema de la base de datos se cambia de forma cosmética (por ejemplo, reindentando su sintaxis), se incrementa z.

Algunas bases de datos y esquemas de OVSDB, especialmente las muy antiguas, no tienen un número de versión.

Los números de versión del esquema y los números de versión de Open vSwitch son independientes.

Estos comandos funcionan con diferentes versiones de esquemas y bases de datos de OVSDB.

convert [db [schema [target]]]
Lee db, traduciéndolo al esquema especificado en schema, y escribe la nueva interpretación. Si se especifica target, la versión traducida se escribe como un nuevo archivo llamado target, que no debe existir previamente. Si se omite target, la versión traducida de la base de datos reemplaza db en su lugar. La conversión en el lugar no puede realizarse si la base de datos está siendo servida actualmente por ovsdb-server (en su lugar, detenga ovsdb-server primero o utilice el comando convert de ovsdb-client).
Este comando puede realizar "actualizaciones" y "reversiones" simples en el esquema de una base de datos. Los datos en db deben ser válidos cuando se interpretan bajo schema, con una sola excepción: los datos en db para tablas y columnas que no existen en schema se ignoran. Las columnas que existen en schema pero no en db se establecen a sus valores predeterminados. Todas las restricciones de schema se aplican en su totalidad.
Algunos usos de este comando pueden causar pérdida de datos irrecuperable. Por ejemplo, convertir una base de datos de un esquema que tiene una columna o tabla dada a uno que no la tiene, eliminará todos los datos de esa columna o tabla. Haga una copia de seguridad de las bases de datos críticas antes de convertirlas.
Este comando es solo para bases de datos independientes y de respaldo activo. Para bases de datos agrupadas, utilice el comando convert de ovsdb-client para convertirlas en línea.
needs-conversion [db [schema]]
Lee el esquema incrustado en db y el esquema JSON de schema y los compara. Si los esquemas son los mismos, imprime no en stdout; si difieren, imprime yes.
Este comando es solo para bases de datos independientes y de respaldo activo. Para bases de datos agrupadas, utilice el comando needs-conversion de ovsdb-client en su lugar.
db-version [db]

schema-version [schema]
Imprime el número de versión en el esquema incrustado dentro de la base de datos db o en el esquema JSON schema en stdout. Si schema o db se crearon antes de que se introdujera la versión del esquema, no tendrán un número de versión y este comando imprimirá una línea en blanco.
El comando db-version es solo para bases de datos independientes y de respaldo activo. Para bases de datos agrupadas, utilice el comando schema-version de ovsdb-client en su lugar.
db-cksum [db]

schema-cksum [schema]
Imprime la suma de verificación en el esquema incrustado dentro de la base de datos db o del esquema JSON schema en stdout. Si schema o db se crearon antes de que se introdujeran las sumas de verificación de esquemas, no tendrán una suma de verificación y este comando imprimirá una línea en blanco.
El comando db-cksum es solo para bases de datos independientes y de respaldo activo. Para bases de datos agrupadas, utilice el comando schema-cksum de ovsdb-client en su lugar.
compare-versions a op b
Compara a y b según op. Tanto a como b deben ser números de versión de esquema OVSDB en el formato x.y.z, como se describe en ovsdb(7), y op debe ser uno de < <= == >= > !=. Si la comparación es verdadera, sale con estado 0; si es falsa, sale con estado 2. (El estado de salida 1 indica un error, por ejemplo, a o b tiene la sintaxis incorrecta para una versión OVSDB o op no es un operador de comparación válido).

Otros comandos

compact [db [target]]
Lee db y escribe una versión compactada. Si se especifica target, la versión compactada se escribe como un nuevo archivo llamado target, que no debe existir previamente. Si se omite target, la versión compactada de la base de datos reemplaza db en su lugar. Este comando no es necesario en operación normal porque ovsdb-server, de vez en cuando, compacta automáticamente una base de datos que crece mucho más allá de su tamaño mínimo.
Este comando no funciona si db está siendo servida actualmente por ovsdb-server, o si está bloqueada para escritura por otro proceso. Este comando tampoco funciona con bases de datos agrupadas. En su lugar, en cualquiera de los casos, envíe el comando ovsdb-server/compact a ovsdb-server, a través de ovs-appctl).
[--rbac-role=role] query [db] transaction
Abre db, ejecuta transaction sobre él e imprime los resultados. La transaction debe ser una matriz JSON en el formato de la matriz params para el método JSON-RPC transact, como se describe en la especificación de OVSDB.
Este comando abre db para acceso de solo lectura, por lo que puede ejecutarse de forma segura concurrentemente con otras actividades de la base de datos, incluyendo ovsdb-server y otros escritores de bases de datos. La transaction puede especificar modificaciones en la base de datos, pero estas no tendrán ningún efecto en db.
Por defecto, la transacción se ejecuta utilizando el rol RBAC de "superusuario". Utilice --rbac-role para especificar un rol diferente.
Este comando no funciona con bases de datos agrupadas. En su lugar, utilice el comando query de ovsdb-client para enviar la consulta a ovsdb-server.
[--rbac-role=role] transact [db] transaction
Abre db, ejecuta transaction sobre él, imprime los resultados y confirma cualquier cambio en db. La transaction debe ser una matriz JSON en el formato de la matriz params para el método JSON-RPC transact, como se describe en la especificación de OVSDB.
Este comando no funciona si db está siendo servida actualmente por ovsdb-server, o si está bloqueada para escritura por otro proceso. Este comando tampoco funciona con bases de datos agrupadas. En su lugar, en cualquiera de los casos, utilice el comando transact de ovsdb-client para enviar la consulta a ovsdb-server.
Por defecto, la transacción se ejecuta utilizando el rol RBAC de "superusuario". Utilice --rbac-role para especificar un rol diferente.
[-m | --more]... show-log [db]
Imprime un resumen de los registros en el registro de db, incluyendo la hora y fecha en que ocurrió cada cambio en la base de datos y cualquier comentario asociado. Esto puede ser útil para la depuración.
Para aumentar la verbosidad de la salida, agregue -m (o --more) una o más veces a la línea de comandos. Con un -m, show-log imprime un resumen de los registros agregados, eliminados o modificados por cada transacción. Con dos -m, show-log también imprime los valores de las columnas modificadas por cada cambio en un registro.
Este comando funciona con bases de datos independientes y de respaldo activo y con bases de datos agrupadas, pero los formatos de salida son diferentes.
check-cluster db...
Lee todos los registros en las bases de datos proporcionadas, que deben ser recopiladas de diferentes servidores (y, idealmente, de todos los servidores) en un solo clúster. Comprueba la autoconsistencia de cada base de datos y el conjunto en conjunto para la interconsistencia. Si ovsdb-tool detecta contenido inusual pero no necesariamente incorrecto, imprime una advertencia o advertencias en stdout. Si ovsdb-tool encuentra errores de consistencia, imprime un error en stderr y sale con estado 1. Los errores generalmente indican errores en ovsdb-server; considere informarlos a los desarrolladores de Open vSwitch.
db-name [db]

schema-name [schema]
Imprime el nombre del esquema incrustado dentro de la base de datos db o en el esquema JSON schema en stdout.
db-cid db
Imprime el ID del clúster, que es un UUID que identifica al clúster, para db. Si db es una base de datos recién creada por ovsdb-tool cluster-join que aún no se ha unido con éxito a su clúster, y no se especificó --cid en la línea de comandos de cluster-join, entonces este comando generará un error y saldrá con el estado 2, porque el ID del clúster aún no se conoce. Este comando solo funciona con bases de datos agrupadas.
El UUID de todos ceros no es un ID de clúster válido.
db-sid db
Imprime el ID del servidor, que es un UUID que identifica al servidor, para db. Este comando solo funciona con bases de datos agrupadas. Funciona incluso si db es una base de datos recién creada por ovsdb-tool cluster-join que aún no se ha unido con éxito a su clúster.

COMANDOS DE BASE DE DATOS

db-local-address db
Imprime la dirección local utilizada para la agrupación en clúster de bases de datos para db, en el mismo formato protocolo:ip:puerto que se utiliza en create-cluster y join-cluster.
db-is-clustered db

db-is-standalone db
Comprueba si db es un archivo de base de datos en formato agrupado o independiente, respectivamente. Si es así, sale con el estado 0; si no, sale con el estado 2. (El estado de salida 1 indica un error, por ejemplo, que db no es una base de datos OVSDB o no existe).

OPCIONES

Opciones de registro

-v[espec]

--verbose=[espec]
Establece los niveles de registro. Sin ningún espec, establece el nivel de registro para cada módulo y destino en dbg. De lo contrario, espec es una lista de palabras separadas por espacios, comas o dos puntos, hasta una de cada categoría a continuación:
  • Un nombre de módulo válido, como se muestra en el comando vlog/list en ovs-appctl(8), limita el cambio del nivel de registro al módulo especificado.
  • syslog, console o file, para limitar el cambio del nivel de registro solo al registro del sistema, a la consola o a un archivo, respectivamente. (Si se especifica --detach, ovsdb-tool cierra sus descriptores de archivo estándar, por lo que el registro en la consola no tendrá ningún efecto).
En la plataforma Windows, se acepta syslog como palabra y solo es útil junto con la opción --syslog-target (la palabra no tiene ningún efecto de lo contrario).
•
off, emer, err, warn, info o dbg, para controlar el nivel de registro. Se registrarán los mensajes de la gravedad dada o superior, y se filtrarán los mensajes de menor gravedad. off filtra todos los mensajes. Consulte ovs-appctl(8) para obtener una definición de cada nivel de registro.
La mayúscula o minúscula no es significativa dentro de espec.
Independientemente de los niveles de registro establecidos para file, el registro en un archivo no se realizará a menos que también se especifique --log-file (ver más abajo).
Por compatibilidad con versiones anteriores de OVS, se acepta any como palabra pero no tiene ningún efecto.
-v

--verbose
Establece el nivel máximo de verbosidad del registro, equivalente a --verbose=dbg.
-vPATTERN:destino:patrón

--verbose=PATTERN:destino:patrón
Establece el patrón de registro para destino en patrón. Consulte ovs-appctl(8) para obtener una descripción de la sintaxis válida para patrón.
-vFACILITY:instalación

--verbose=FACILITY:instalación
Establece la instalación RFC5424 del mensaje de registro. instalación puede ser una de kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 o local7. Si esta opción no se especifica, se utiliza daemon como valor predeterminado para el registro del sistema local y se utiliza local0 al enviar un mensaje al destino proporcionado a través de la opción --syslog-target.
--log-file[=archivo]
Habilita el registro en un archivo. Si se especifica archivo, se utiliza como el nombre exacto del archivo de registro. El nombre de archivo de registro predeterminado que se utiliza si se omite archivo es /var/log/openvswitch/ovsdb-tool.log.
--syslog-target=host:puerto
Envía mensajes de syslog al puerto UDP en host, además del registro del sistema. El host debe ser una dirección IP numérica, no un nombre de host.
--syslog-method=método
Especifica el método de cómo se deben enviar los mensajes de syslog al demonio de syslog. Se admiten las siguientes formas:
  • libc, utiliza la función syslog() de libc. La desventaja de usar esta opción es que libc agrega un prefijo fijo a cada mensaje antes de que se envíe realmente al demonio de syslog a través del socket de dominio UNIX /dev/log.
  • unix:archivo, utiliza directamente el socket de dominio UNIX. Es posible especificar un formato de mensaje arbitrario con esta opción. Sin embargo, rsyslogd 8.9 y versiones anteriores utilizan de todos modos una función de análisis codificada que limita el uso del socket de dominio UNIX. Si desea utilizar un formato de mensaje arbitrario con versiones anteriores de rsyslogd, utilice en su lugar un socket UDP a la dirección IP de localhost.
  • udp:ip:puerto, utiliza un socket UDP. Con este método es posible utilizar un formato de mensaje arbitrario también con versiones anteriores de rsyslogd. Al enviar mensajes de syslog a través de un socket UDP, se deben tener en cuenta precauciones adicionales, por ejemplo, el demonio de syslog debe configurarse para escuchar en el puerto UDP especificado, las reglas de iptables accidentales podrían interferir con el tráfico de syslog local y existen algunas consideraciones de seguridad que se aplican a los sockets UDP, pero no a los sockets de dominio UNIX.
  • null, descarta todos los mensajes registrados en syslog.
El valor predeterminado se toma de la variable de entorno OVS_SYSLOG_METHOD; si no está establecida, el valor predeterminado es libc.

Otras opciones

-h

--help
Imprime un breve mensaje de ayuda en la consola.
-V

--version
Imprime la información de la versión en la consola.

ARCHIVOS

El valor predeterminado de db es /etc/openvswitch/conf.db. El valor predeterminado de schema es /usr/share/openvswitch/vswitch.ovsschema. El comando help también muestra estos valores predeterminados.
