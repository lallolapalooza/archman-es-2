NOMBRE

ossl-guide-quic-introduction - Guía de OpenSSL: Introducción a QUIC en OpenSSL

INTRODUCCIÓN

Esta página proporcionará una introducción a algunos conceptos y antecedentes básicos de QUIC y cómo se utiliza dentro de OpenSSL. Asume que usted tiene una comprensión básica de UDP/IP y sockets. También asume que está familiarizado con algunos fundamentos de OpenSSL y TLS (ver ossl-guide-libraries-introduction(7) y ossl-guide-tls-introduction(7)).

¿QUÉ ES QUIC?

QUIC es un protocolo de propósito general para permitir que las aplicaciones se comuniquen de forma segura a través de una red. Está definido en RFC9000 (ver https://datatracker.ietf.org/doc/rfc9000/). QUIC integra partes del protocolo TLS para el establecimiento de conexiones, pero protege los paquetes de forma independiente. Proporciona garantías de seguridad similares a TLS, como confidencialidad, integridad y autenticación (ver ossl-guide-tls-introduction(7)).

QUIC ofrece una serie de ventajas:

Múltiples streams
Soporta múltiples streams de comunicación (ver "STREAMS QUIC" abajo), permitiendo que los protocolos de aplicación construidos sobre QUIC creen un número arbitrario de streams de bytes para la comunicación entre un cliente y un servidor. Esto permite que un protocolo de aplicación evite problemas donde un paquete de datos se retrasa esperando que otro paquete sea entregado (comúnmente referido como "bloqueo de cabeza de línea"). También permite a una aplicación abrir streams lógicos adicionales sin requerir un intercambio de paquetes de ida y vuelta entre el cliente y el servidor, como se requiere al abrir una conexión TLS/TCP adicional.
HTTP/3
Dado que QUIC es la base de HTTP/3, el soporte para QUIC también permite a las aplicaciones usar HTTP/3 utilizando una biblioteca de terceros adecuada.
Rápida iniciación de conexión
Las futuras versiones de OpenSSL ofrecerán soporte para la iniciación de conexiones 0-RTT, permitiendo iniciar una conexión a un servidor y transmitir datos de aplicación sin tiempo de espera. Esto es similar a la funcionalidad 0-RTT de TLS 1.3, pero también evita el viaje de ida y vuelta necesario para abrir un socket TCP; por lo tanto, es similar a una combinación de 0-RTT de TLS 1.3 y TCP Fast Open.
Migración de conexión
Las futuras versiones de OpenSSL ofrecerán soporte para la migración de conexiones, permitiendo que las conexiones sobrevivan sin problemas a cambios de dirección IP.
Casos de uso basados en datagramas
Las futuras versiones de OpenSSL ofrecerán soporte para la extensión de datagramas de QUIC, permitiendo el soporte para casos de uso tipo TLS y DTLS en una sola conexión.
Implementada como biblioteca de aplicaciones
Debido a que la mayoría de las implementaciones de QUIC, incluida la de OpenSSL, se implementan como una biblioteca de aplicaciones en lugar de un sistema operativo, una aplicación puede beneficiarse de QUIC sin necesidad de esperar a que se implemente una actualización del sistema operativo. Las futuras evoluciones y mejoras del protocolo QUIC se pueden entregar tan rápidamente como se pueda actualizar una aplicación, sin depender del cadencia de actualización del sistema operativo.
Multiplexación sobre un solo socket UDP
Debido a que QUIC se basa en UDP, es posible multiplexar una conexión QUIC en el mismo socket UDP que otros protocolos basados en UDP, como RTP.

EVENTOS BASADOS EN TIEMPO QUIC

Una diferencia clave entre la implementación TLS y la implementación QUIC en OpenSSL es cómo se maneja el tiempo. El protocolo QUIC requiere que se realicen diversas acciones de forma regular, independientemente de si se están transmitiendo o recibiendo datos de aplicación.

OpenSSL introduce una nueva función SSL_handle_events(3) que procesará automáticamente cualquier evento pendiente basado en tiempo que deba ser manejado. Alternativamente, llamar a cualquier función de E/S como SSL_read_ex(3) o SSL_write_ex(3) también procesará estos eventos. También existe SSL_get_event_timeout(3) que indica a la aplicación cuánto tiempo queda hasta que SSL_handle_events(3) (o cualquier función de E/S) deba ser llamada.

Afortunadamente, una aplicación bloqueante que no deja la conexión QUIC inactiva y llama regularmente a funciones de E/S, normalmente no necesita preocuparse por esto. Sin embargo, si está desarrollando una aplicación no bloqueante o una que pueda dejar la conexión QUIC inactiva durante un período de tiempo, necesitará organizar la llamada a estas funciones.

OpenSSL proporciona un "modo asistido por hilos" opcional que creará automáticamente un hilo secundario y llamará regularmente a SSL_handle_events(3) de forma segura para hilos. Esto proporciona una forma sencilla para que una aplicación cumpla los requisitos de QUIC para eventos basados en tiempo sin tener que implementar lógica especial para lograrlo.

QUIC Y TLS

QUIC reutiliza partes del protocolo TLS en su implementación. Específicamente, el handshake TLS también existe en QUIC. Los mensajes de handshake TLS se empaquetan en mensajes del protocolo QUIC para enviarlos al par. Una vez que el handshake TLS se completa, todos los datos de aplicación se envían completamente usando mensajes del protocolo QUIC sin usar TLS, aunque algunos mensajes de handshake TLS aún pueden enviarse en algunas circunstancias.

Esta relación entre QUIC y TLS significa que muchas de las funciones de API en OpenSSL que se aplican a las conexiones TLS también se aplican a las conexiones QUIC y las aplicaciones pueden usarlas exactamente de la misma manera. Algunas funciones no se aplican a QUIC en absoluto, y otras tienen semánticas alteradas. Debe consultar las páginas de documentación de cada función para obtener información sobre cómo se aplica a QUIC. Típicamente, si QUIC no se menciona en las páginas del manual, las funciones se aplican tanto a TLS como a QUIC.

STREAMS QUIC

QUIC introduce el concepto de "streams". Un stream proporciona un mecanismo fiable para enviar y recibir datos de aplicación entre los puntos finales. Se garantiza que los bytes transmitidos se recibirán en el mismo orden en que se enviaron, sin pérdida de datos ni reordenación de los bytes. Una aplicación TLS tiene efectivamente un stream bidireccional disponible por conexión TLS. Una aplicación QUIC puede tener múltiples streams unidireccionales o bidireccionales disponibles por conexión.

En OpenSSL, un objeto SSL se utiliza para representar tanto conexiones como streams. Una aplicación QUIC crea un objeto SSL inicial para representar la conexión (conocido como el objeto SSL de conexión). Una vez que la conexión se completa, se pueden crear objetos SSL adicionales para representar streams (conocidos como objetos SSL de stream). A menos que se configure lo contrario, también se asocia un stream "predeterminado" con el objeto SSL de conexión, por lo que aún puede escribir y leer datos desde/hacia él. Algunas funciones de la API de OpenSSL solo se pueden usar con objetos SSL de conexión, y algunas solo se pueden usar con objetos SSL de stream. Consulte la documentación de cada función para confirmar qué tipo de objeto SSL se puede usar en un contexto particular. Un objeto SSL de conexión que tiene un stream predeterminado adjunto se puede usar en contextos que requieren un objeto SSL de conexión o en contextos que requieren un objeto SSL de stream.

SOCKETS Y BLOQUEO

TLS asume semánticas de tipo "stream" para su protocolo de capa de transporte subyacente (generalmente logrado mediante el uso de TCP). Sin embargo, QUIC asume semánticas de tipo "datagrama" al utilizar UDP. Una aplicación OpenSSL que utiliza QUIC es responsable de crear un BIO para representar la capa de transporte subyacente. SOCKETS AND BLOCKING

In OpenSSL applications, the concept of bio(7) is available. See bio(7) for an introduction to OpenSSL's BIO concept.

A significant difference between OpenSSL TLS applications and OpenSSL QUIC applications is the way that blocking is implemented. In TLS if your application expects blocking behaviour then you configure the underlying socket for blocking. Conversely if your application wants nonblocking behaviour then the underlying socket is configured to be nonblocking.

With an OpenSSL QUIC application the underlying socket must always be configured to be nonblocking. Howevever the SSL object will, by default, still operate in blocking mode. So, from an application's perspective, calls to functions such as SSL_read_ex(3), SSL_write_ex(3) and other I/O functions will still block. OpenSSL itself provides that blocking capability for QUIC instead of the socket. If nonblocking behaviour is desired then the application must call SSL_set_blocking_mode(3).
