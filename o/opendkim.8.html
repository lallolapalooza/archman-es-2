NOMBRE

opendkim - Filtro para firmar y verificar DKIM para MTAs

SINOPSIS

opendkim [-A] [-b modos] [-c canon] [-d dominio[,...]] [-D] [-e nombre] [-f] [-F tiempo] [-k archivo_clave] [-l] [-L min] [-n] [-o list_encabezados] [-p espec_sockets] [-P archivo_pid] [-Q] [-r] [-s selector] [-S sigalg] [-t archivos_prueba] [-T secs] [-u userid[:group]] [-v] [-V] [-W] [-x archivo_config] [-X]

DESCRIPCIÓN

opendkim implementa el estándar DKIM para firmar y/o verificar mensajes de correo electrónico de forma individual por dominio.

opendkim utiliza la interfaz milter, distribuida originalmente como parte de la versión 8.11 de sendmail(8), para proporcionar servicio de firma y/o verificación DKIM para el correo que transita por un MTA compatible con milter.

La mayoría, si no todas, de las opciones de línea de comandos listadas a continuación también se pueden configurar mediante un archivo de configuración. Consulte la opción -x para obtener más detalles.

CONJUNTOS DE DATOS

Muchos de los parámetros de línea de comandos y archivos de configuración se referirán a un "conjunto de datos" como sus valores. Esto se refiere a una cadena que contiene la lista de valores deseables, o a un archivo que los contiene, o (si está habilitado en tiempo de compilación) a una base de datos que contiene los datos.

Algunos conjuntos de datos requieren que el valor contenga más de una entrada. Cómo se hace esto depende del tipo de conjunto de datos que se utilice.

Qué tipo se utiliza depende del formato de la cadena de especificación. Tenga en cuenta que no todas estas opciones pueden ser soportadas en todas las instalaciones; la mayoría dependen de la disponibilidad de una biblioteca de terceros particular en tiempo de compilación.

En particular:

a)
Si la cadena comienza con "file:", entonces el resto de la cadena se presume que se refiere a un archivo plano que contiene elementos del conjunto de datos, uno por línea. Si una línea contiene valores separados por espacios en blanco, entonces se presume que la línea define una clave y su valor correspondiente. Se ignoran las líneas en blanco y el carácter de almohadilla ("#") indica el inicio de un comentario. Si un valor contiene varias entradas, las entradas deben estar separadas por dos puntos.
b)
Si la cadena comienza con "refile:", entonces se presume que el resto de la cadena especifica un archivo que contiene un conjunto de patrones, uno por línea, y sus valores asociados. El patrón se toma como el inicio de la línea hasta el primer espacio en blanco, y la porción después de ese espacio en blanco se toma como el valor que se usará cuando ese patrón coincida. Los patrones son patrones comodín simples, que coinciden con todo el texto excepto que el carácter asterisco ("*") se considera un comodín. Si un valor contiene varias entradas, las entradas deben estar separadas por dos puntos.
c)
Si la cadena comienza con "db:" y el programa fue compilado con soporte de Sleepycat DB, entonces se presume que el resto de la cadena identifica una base de datos Sleepycat que contiene claves y valores correspondientes. Estos solo pueden usarse para probar la pertenencia al conjunto de datos, o para almacenar claves y valores correspondientes. Si un valor contiene varias entradas, las entradas deben estar separadas por dos puntos.
d)
Si la cadena comienza con "dsn:" y la biblioteca OpenDKIM fue compilada para soportar ese tipo de base de datos, entonces el resto de la cadena es un Nombre de Almacén de Datos que describe el tipo, parámetros de ubicación y credenciales de acceso para una base de datos ODBC o SQL. El DSN tiene el formato:

backend://[usuario[:pwd]@][puerto+]host/basedatos[/clave=valor[?...]]

donde backend es el nombre de un mecanismo de base de datos de backend soportado (por ejemplo, "mysql"), usuario y contraseña son credenciales de inicio de sesión opcionales para la base de datos, puerto y host describen el destino de una conexión TCP para conectarse a esa base de datos, basedatos es el nombre de la base de datos a la que se accederá, y los pares clave=valor deben especificar al menos los valores "tabla", "col_clave" y "col_datos" especificando el nombre de la tabla, el nombre de la columna a considerar como clave, y el/los nombre(s) de la(s) columna(s) a considerar como valores (separados por comas). Por ejemplo (todo en una línea):

mysql:://usuario_db:contraseña_db@3306+host_db/odkim/tabla=macros
?col_clave=host?col_datos=v1,v2

define una base de datos MySQL escuchando en el puerto 3306 en el host "host_db"; se deben usar el ID de usuario "usuario_db" y la contraseña "contraseña_db" para acceder a la base de datos; el nombre de la base de datos es "odkim", y los datos están en las columnas "host" (las claves) y "v1" y "v2" (los valores) dentro de la tabla "macros". Este ejemplo, por lo tanto, devolvería dos valores cuando se encuentra una coincidencia.

La clave también puede incluir un valor de "filtro" que se incluirá en todos los SQL generados como una cláusula AND después de la cláusula WHERE que declara los criterios de búsqueda. Por ejemplo, dada la especificación DSN anterior con un valor de "filtro" adicional de "ID > 1000", el SQL generado para una consulta para "foo" se vería así:

SELECT v1,v2 FROM macros WHERE host = 'foo' AND ID > 1000

Ningún valor dentro del DSN puede contener ninguno de los seis caracteres de puntuación (":", "/", "@", "+", "?" y "=") utilizados para delimitar partes del DSN. Para incluir dichos caracteres dentro de un valor, codifíquelos en estilo quoted-printable (por ejemplo, "=20" se traducirá en un solo carácter de espacio). También se recomienda la codificación de espacios.

e)
Si la cadena comienza con "ldap:", "ldaps:" o "ldapi:", se presume que es un conjunto de una o más URL LDAP separadas por espacios que identifican un conjunto de servidores a consultar. La primera debe ser una URL LDAP RFC4516 completa que indique una plantilla de DN base y un ámbito, filtro y nombres de atributos opcionales a usar en las consultas. Al construir una plantilla de DN o un filtro, los tokens especiales "$d" y "$D" se reemplazan con la clave que se está consultando y la clave desglosada en componentes, separados por "." caracteres, cada componente precedido por "dc=" y seguido por "," (por lo que "example.com" se convertiría en "dc=example,dc=com"). Si un conjunto de datos requiere que se devuelvan varios valores, los nombres de atributos apropiados deben darse en el orden correcto para satisfacer dichas solicitudes.
f)
Si la cadena comienza con "lua:", se presume que se refiere a un archivo que contiene un script Lua que se ejecutará cada vez que se realice una consulta. La clave de la consulta se coloca en una variable global llamada "query", a la que el script llamado puede acceder. El script puede devolver cualquier número de valores según sea necesario para el tipo de consulta que se esté realizando.
g)
Si la cadena comienza con "memcache:", se presume que se refiere a una base de datos de caché en memoria proporcionada por memcached. El resto de la cadena es una lista separada por comas de hosts a los que se deben hacer intentos de consulta, cada uno opcionalmente seguido por ":" y un número de puerto; esa lista debe ir seguida por un carácter de barra diagonal ("/") y una cadena que se utilizará para prefijar las consultas enviadas a la caché. Por ejemplo:

memcache:localhost,otrohost/nombre_clave

Esto usaría "localhost" u "otrohost" para realizar consultas, y todas las cadenas enviadas al conjunto de datos se prefijarán con "nombre_clave:".

h)
Si la cadena no contiene ninguno de estos prefijos pero termina con ".db", se presume que es una base de datos Sleepycat como se describió anteriormente (si el soporte para la misma está compilado).
i)
Si la cadena no contiene ninguno de estos prefijos pero comienza con un carácter de barra diagonal ("/"), se presume que es un archivo plano como se describió anteriormente.
j)
Si la cadena comienza con "csl:", la cadena se trata como una lista separada por comas como se describe en m) a continuación.
k)
Si la cadena comienza con "erlang:", se presume que se refiere a una función que se llama para

make to the specified distributed Erlang node(s). The specification is of the form

erlang:node@host[,...]:cookie:module:function

where node[,...] is a list of comma-separated erlang nodes, cookie is the cookie for the known nodes of the distributed Erlang setup, module is the name of the Erlang module where the function to be called resides, function is the name of the Erlang function to be called. For example, (all in one line):

erlang:mynode@myhost,myothernode@myotherhost:
chocolate:dkim:lookup

will join the distributed Erlang setup connecting to either "mynode@myhost" or "myothernode@myotherhost" (connections to nodes are tried in order) using "chocolate" as the cookie, and use the function "dkim:lookup/1" for lookups.

l)
If the string begins with "mdb:", it refers to a directory that contains a memory database, as provided by libmdb from OpenLDAP.
m)
In any other case, the string is presumed to be a comma-separated list. Elements in the list are either simple data elements that are part of the set or, in the case of an entry of the form "x=y", are stored as key-value pairs as described above.

OPCIONES

-A
Reinicia automáticamente en caso de fallos. Usar con precaución; si el filtro falla instantáneamente después de iniciarse, esto puede causar un bucle de fork(2) cerrado. Esto puede mitigarse usando algunos valores en el archivo de configuración para limitar los reinicios. Véase opendkim.conf(5).
-b modos
Selecciona los modos de operación. modos es una concatenación de caracteres que indican qué modo(s) de operación se desean. Los modos válidos son s (firmante) y v (verificador). El valor predeterminado es sv excepto en modo de prueba (véase -t a continuación) en cuyo caso el valor predeterminado es v.
-c canon
Selecciona el(los) método(s) de canonicalización a ser utilizados al firmar mensajes. Al verificar, la cabecera DKIM-Signature: del mensaje especifica el método de canonicalización. Los valores reconocidos son relaxed y simple según se definen en la especificación DKIM. El valor predeterminado es simple. El valor puede incluir dos canonicalizaciones diferentes separadas por una barra ("/"), en cuyo caso la primera se aplicará a las cabeceras y la segunda al cuerpo.
-d conjunto_datos
Un conjunto de dominios cuyo correo debe ser firmado por este filtro. El correo de otros dominios será verificado en lugar de ser firmado.
-D
Firma también los subdominios de aquellos listados por la opción -d, así como los dominios reales.
-e nombre
Extrae el valor de nombre del archivo de configuración (si existe).
-f
Normalmente opendkim se bifurca y sale inmediatamente, dejando el servicio ejecutándose en segundo plano. Esta bandera suprime ese comportamiento para que se ejecute en primer plano.
-F tiempo
Especifica un tiempo fijo a utilizar al generar firmas. Se ignora a menos que se use también junto con -t (véase a continuación). El tiempo debe expresarse en el formato estándar time_t de UNIX (segundos desde la época).
-k archivo_clave
Indica la ubicación de una clave privada en formato PEM a ser utilizada para firmar todos los mensajes. Se ignora si se referencia un archivo de configuración que define una KeyTable.
-l
Registra mediante llamadas a syslog(3) cualquier actividad interesante.
-L min[%+]
Instruye al código de verificación para que rechace mensajes para los cuales se recibió una firma parcial. Existen tres formatos posibles: min indicando que al menos min bytes del mensaje deben ser firmados (o si el mensaje es menor que min, entonces todo él debe ser firmado); min% requiriendo que al menos min por ciento del mensaje recibido debe ser firmado; y min+ significando que no puede haber más de min bytes de datos no firmados añadidos al mensaje para que sea considerado válido.
-n
Analiza el archivo de configuración y los argumentos de la línea de comandos, informando cualquier error encontrado, y luego sale. El valor de salida será 0 si el filtro se iniciaría sin quejas, o no cero en caso contrario.
-o conjunto_datos
Especifica una lista de cabeceras que deben omitirse al generar firmas. Si una entrada en la lista nombra cualquier cabecera que sea requerida por la especificación DKIM, la entrada es ignorada. Un conjunto de cabeceras se lista en la especificación DKIM como que "NO DEBERÍAN" ser firmadas; la lista predeterminada para este parámetro contiene esas cabeceras (Return-Path, Received, Comments, Keywords, Bcc, Resent-Bcc y DKIM-Signature). Para omitir ninguna cabecera, simplemente use la cadena "-" (o cualquier cadena que no coincida con ninguna cabecera).
-p espec_socket
Especifica el socket que debe ser establecido por el filtro para recibir conexiones de sendmail(8) para proporcionar servicio. espec_socket tiene una de dos formas: local:ruta que crea un socket de dominio UNIX en la ruta especificada, o inet:puerto[@host] o inet6:puerto[@host] que crea un socket TCP en el puerto especificado usando la familia de protocolos solicitada. Si el host no se proporciona como un nombre de host o una dirección IP, el socket escuchará en todas las interfaces. Una dirección IP literal debe estar encerrada entre corchetes. Si no se especifica ningún tipo de socket, se asume local, lo que significa que el parámetro se interpreta como una ruta en la que se debe crear el socket. Este parámetro es obligatorio, ya sea aquí o en el archivo de configuración.
-P archivo_pid
Especifica un archivo en el que el filtro debe escribir su ID de proceso al iniciar.
-Q
Modo de prueba de consulta. El filtro leerá dos líneas de la entrada estándar, una que contiene una descripción de la base de datos a abrir y otra que contiene una cadena de la forma "q/n" donde "q" es la consulta a realizar y "n" es el número de campos a recuperar.
-r
Comprueba todos los mensajes para determinar si cumplen con los requisitos de recuento de cabeceras de RFC5322. Los mensajes no conformes son rechazados.
-s selector
Define el nombre del selector a utilizar al firmar mensajes. Véase la especificación DKIM para detalles.
-S sigalg
Selecciona el algoritmo de firma a utilizar al generar firmas. Use 'opendkim -V' para ver la lista de algoritmos soportados. El valor predeterminado es rsa-sha256 si está disponible, de lo contrario será rsa-sha1.
-t archivos_prueba
Evalúa (verifica) uno o más mensajes con formato RFC5322 encontrados en archivos_prueba y sale. El valor de archivos_prueba debe ser una lista separada por comas de uno o más nombres de archivo, uno de los cuales puede ser "-" si el mensaje debe leerse de la entrada estándar.
-T secs
Establece el tiempo de espera de DNS en segundos. Un valor de 0 causa una espera infinita. El valor predeterminado es 5. Se ignora si no se usa un paquete de resolución asíncrono. Véase también la sección NOTAS a continuación.
-u userid[:group]
Intenta convertirse en el userid especificado antes de iniciar las operaciones. Al proceso se le asignarán todos los grupos y el ID de grupo primario del userid nombrado, a menos que se especifique un group alternativo. Véase la sección PERMISOS DE ARCHIVO para más información.
-v
Aumenta la salida detallada durante el modo de prueba (véase -t arriba). Puede especificarse más de una vez para solicitar cantidades crecientes de salida.
-V
Imprime el número de versión y los algoritmos de canonicalización y firma soportados, y luego sale sin hacer nada más.
-W
Si el registro está habilitado (véase -l arriba), emite registros muy detallados sobre la lógica detrás de la decisión del filtro de firmar un mensaje o verificarlo. La "W" significa "¡Por qué?!" ya que la lógica detrás de la decisión no es trivial y puede ser confusa para los administradores que no están familiarizados con su funcionamiento. Una descripción de cómo se toma la decisión se puede encontrar en la sección OPERACIÓN de este documento. Esto causa un gran aumento en la cantidad de datos de registro generados para cada mensaje, por lo que debe limitarse al uso de depuración y no habilitarse para la operación general.
-x archivo_config
Lee el archivo de configuración nombrado. Véase la página man opendkim.conf(5) para más detalles. Los valores en el archivo de configuración son anulados cuando sus equivalentes se proporcionan en la línea de comandos hasta que ocurre una recarga de configuración. La sección OPERACIÓN describe cómo se activan las recargas. El valor predeterminado es leer un archivo de configuración de /etc/opendkim/opendkim.conf si existe, o de lo contrario aplicar los valores predeterminados a todos los valores.
-X
Tolerar elementos del archivo de configuración que han sido marcados internamente como "obsoletos". Normalmente, cuando un elemento del archivo de configuración se elimina del paquete, se marca de esta manera durante al menos un ciclo de lanzamiento completo. La presencia de un elemento de archivo de configuración obsoleto típicamente causa que el filtro devuelva un error y se niegue a iniciarse. Establecer esta bandera permitirá que el filtro se inicie y se registrará una advertencia. En una versión futura cuando el elemento se elimine por completo, se producirá un error diferente y no será posible iniciar el filtro. NO SE RECOMIENDA el uso de esta bandera; podría ocultar efectivamente un cambio importante de configuración con graves implicaciones de seguridad.

OPERACIÓN

Un mensaje será verificado a menos que

OPERACIÓN

Se ajusta a los criterios de firma, que son: (1) el dominio en la dirección From: (si está presente) debe estar listado por el cambio de línea -d o la configuración del archivo de configuración Domain, y (2) (a) el cliente que se conecta a la MTA debe haberse autenticado, o (b) el cliente que se conecta a la MTA debe estar listado en el archivo referenciado por la configuración del archivo de configuración InternalHosts (o estar en la lista predeterminada para esa opción), o (c) el cliente debe estar conectado a un puerto de demonio nombrado por la configuración del archivo de configuración MTAs, o (d) la MTA debe haber configurado una o más macros que coincidan con los criterios establecidos por la configuración del archivo de configuración MacroList.

Para (a) anterior, la prueba es si la macro MTA "{auth_type}" está configurada y contiene algún valor no vacío. Esto significa que la MTA debe pasar el valor de esa macro al filtro antes o durante la fase de fin de encabezado (EOH) para que su valor pueda ser probado. Consulte la documentación de configuración de su MTA para obtener detalles.

Para (1) anterior, se pueden seleccionar otros campos de encabezado usando la configuración del archivo de configuración SenderHeaders. Consulte opendkim.conf(5) para obtener más información.

Al firmar un mensaje, se antepondrá un encabezado DKIM-Signature: al mensaje. La firma se calcula utilizando la clave privada proporcionada. Debe estar ejecutando una versión de sendmail(8) lo suficientemente reciente como para poder realizar operaciones de anteposición de encabezados (8.13.0 o posterior).

Al verificar un mensaje, se antepondrá un encabezado Authentication-Results: para indicar la presencia de una firma y si pudo ser validada contra el cuerpo del mensaje utilizando la clave pública anunciada por el servidor de nombres del remitente. El valor de este encabezado puede ser utilizado por los agentes de usuario de correo para ordenar o descartar mensajes que no fueron firmados o que no pudieron ser verificados.

Al recibir SIGUSR1, si el filtro se inició con un archivo de configuración, este se volverá a leer y se utilizarán los nuevos valores. Tenga en cuenta que cualquier anulación de línea de comandos proporcionada en el momento del inicio se perderá al hacer esto. Además, los siguientes valores del archivo de configuración (y sus elementos de línea de comandos correspondientes, si los hay) no se recargan a través de este proceso: AutoRestart (-A), AutoRestartCount, AutoRestartRate, Background, MilterDebug, PidFile (-P), POPDBFile, Quarantine (-q), QueryCache, Socket (-p), StrictTestMode, TestPublicKeys, UMask, UserID (-u). El filtro no verifica automáticamente el archivo de configuración en busca de cambios y no se recarga.

MACROS DE LA MTA

opendkim utiliza tres macros proporcionadas por la MTA, además de las que se soliciten por configuración. Las tres básicas son: "i" (el ID del sobre, también conocido como ID del trabajo o ID de la cola), que se utiliza para el registro; "daemon_name" (el nombre simbólico asignado a la instancia de la MTA que aceptó la conexión), que se utiliza al realizar pruebas contra cualquier configuración de "MTAs" utilizada; y "auth_type", que se utiliza para determinar si el cliente SMTP se autenticó ante la MTA. Si la MTA no se las proporciona a opendkim, entonces no puede aplicar sus pruebas correspondientes ni hacer un registro útil. Consulte la documentación de configuración de su MTA para determinar cómo ajustar su configuración si algunas o todas estas no están disponibles.

PERMISOS DE ARCHIVO

Cuando el filtro se inicia como superusuario y se utiliza la configuración UserID (-u), el filtro renuncia a sus privilegios de root al cambiar al usuario especificado después de que se toman los siguientes pasos: (1) se carga el archivo de configuración (si existe); (2) si se utiliza la configuración KeyFile (-k), esa clave se carga en memoria; (3) se abren todos los conjuntos de datos en el archivo de configuración, y aquellos que se basan en archivos planos también se leen en memoria; y (4) si está configurado ChangeRootDirectory, la raíz del proceso se cambia a ese directorio. Esto significa que al recargar la configuración, el filtro no accederá a estos archivos ni al archivo de configuración como superusuario (y posiblemente desde una raíz diferente), y cualquier archivo de clave referenciado por KeyTable también será accedido por el nuevo usuario.

Por lo tanto, las claves referenciadas por KeyTable siempre deben ser accesibles para lectura por el usuario no privilegiado. Además, las recargas en tiempo de ejecución no son posibles si alguno de los otros archivos no será legible por el usuario no privilegiado.

ENTORNO

La(s) siguiente(s) variable(s) de entorno se pueden usar para ajustar el comportamiento de este filtro:

DKIM_TMPDIR
El directorio a usar al crear archivos temporales. El valor predeterminado es /tmp.

NOTAS

Al usar tiempos de espera de DNS (ver la opción -T anterior), asegúrese de no usar un tiempo de espera mayor que el tiempo de espera utilizado para la interacción entre sendmail y el filtro. De lo contrario, la MTA podría abortar un mensaje mientras espera una respuesta del filtro, que a su vez todavía está esperando una respuesta de DNS.

La base de datos de autenticación POP se espera que sea un archivo Sleepycat DB (anteriormente conocido como Berkeley DB) en formato hash con claves que contienen la dirección IP en forma de texto sin un NULL final. Los valores de estos registros no se verifican; solo la existencia de dichos registros es de interés. El filtro intentará establecer un bloqueo compartido en la base de datos antes de leer de ella, por lo que cualquier programa que escriba en la base de datos debe mantener su uso de bloqueo al mínimo o este filtro parecerá colgarse mientras espera que la operación de bloqueo se complete.

Las características que implican la especificación de direcciones IPv4 o bloques CIDR utilizarán la función inet_addr(3) para analizar esa información. Los usuarios deben estar familiarizados con la forma en que esa función maneja los casos no triviales (por ejemplo, "192.0.2/24" y "192.0.2.0/24" no son lo mismo).

ESTADO DE SALIDA

Los códigos de estado de salida del filtro se seleccionan de acuerdo con sysexits(3).
