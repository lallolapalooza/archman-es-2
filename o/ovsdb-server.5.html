NOMBRE

ovsdb-server - Esquema de la base de datos del servidor

Cada ovsdb-server (versión 2.9 o posterior) siempre aloja una instancia de este esquema, que contiene información sobre el estado y la configuración del propio servidor. Esta base de datos es de solo lectura. Esta página de manual describe el esquema de esta base de datos.

RESUMEN DE TABLAS

La siguiente lista resume el propósito de cada una de las tablas de la base de datos _Server. Cada tabla se describe con más detalle en una página posterior.

Tabla
Propósito
Database
Bases de datos.

TABLA Database

Esta tabla describe las bases de datos alojadas por el servidor de base de datos, con una fila por base de datos. A medida que su configuración y estado de la base de datos cambian, el servidor actualiza la tabla automática e inmediatamente para que coincida.

El protocolo OVSDB especificado en RFC 7047 no proporciona una manera para que un cliente OVSDB descubra ciertos tipos de cambios de configuración, como bases de datos agregadas o eliminadas mientras un cliente está conectado al servidor, o bases de datos que cambian entre lectura/escritura y solo lectura debido a una transición entre roles activo y de respaldo. Esta tabla proporciona una solución: los clientes pueden monitorear el contenido de la tabla para enterarse de cambios importantes.

Tradicionalmente, ovsdb-server desconecta a todos sus clientes cuando ocurre un cambio de configuración significativo, ya que esto fuerza a un cliente bien escrito a reevaluar lo que está disponible desde el servidor al reconectarse. Dado que esta tabla proporciona una forma alternativa y más eficiente de enterarse de esos cambios, OVS 2.9 también introduce la RPC set_db_change_aware, documentada en ovsdb-server(7), para permitir a los clientes suprimir este comportamiento de desconexión.

Cuando se elimina una base de datos del servidor, además de las actualizaciones de la tabla Database, el servidor envía mensajes canceled, como se describe en la sección 4.1.4 de RFC 7047, en respuesta a transacciones pendientes para la base de datos eliminada. El servidor también cancela cualquier monitoreo pendiente iniciado por monitor o monitor_cond solicitado en la base de datos eliminada, enviando la RPC monitor_canceled descrita en ovsdb-server(7). Solo los clientes que deshabilitan la desconexión con set_db_change_aware reciben estos mensajes.

Los clientes pueden usar la columna _uuid en esta tabla como un número de generación. El servidor genera un nuevo _uuid cada vez que agrega una base de datos, de modo que eliminar y luego volver a agregar una base de datos al servidor hace que el _uuid de su fila cambie.

Detalles:

name: string
El nombre de la base de datos, tal como se especifica en su esquema.
model: string, uno de clustered, relay o standalone
El modelo de almacenamiento: standalone para una base de datos autónoma o activo-respaldo, clustered para una base de datos en clúster, relay para una base de datos de retransmisión.
schema: string opcional
El esquema de la base de datos, como una cadena JSON. En el caso de una base de datos en clúster, está vacía hasta que termina de unirse a su clúster. En el caso de una base de datos de retransmisión, está vacía hasta que se conecta a la fuente de retransmisión.
connected: boolean
Verdadero si la base de datos está conectada a su almacenamiento. Una base de datos autónoma siempre está conectada. Una base de datos en clúster está conectada si el servidor está en contacto con una mayoría de su clúster. Una base de datos de retransmisión está conectada si el servidor está en contacto con la fuente de retransmisión, es decir, está conectada al servidor del que se sincroniza. Una base de datos no conectada no se puede modificar y sus datos pueden no estar disponibles o estar desactualizados.
Bases de datos en Clúster:

Estas columnas son más interesantes y, en algunos casos, solo relevantes para bases de datos en clúster, es decir, aquellas donde la columna model es clustered.

leader: boolean
Verdadero si la base de datos es la líder en su clúster. Para una base de datos autónoma o activo-respaldo, esto siempre es verdadero. Para una base de datos de retransmisión, esto siempre es falso.
cid: uuid opcional
El ID del clúster para esta base de datos, que es el mismo para todos los servidores que alojan esta base de datos en clúster particular. Para una base de datos autónoma, activo-respaldo o de retransmisión, esto está vacío.
sid: uuid opcional
El ID del servidor para esta base de datos, diferente para cada servidor que aloja una base de datos en clúster particular. Un servidor que aloja más de una base de datos en clúster tendrá un sid diferente en cada una. Para una base de datos autónoma, activo-respaldo o de retransmisión, esto está vacío.
index: entero opcional
Para una base de datos en clúster, el índice de la entrada de registro que actualmente se expone a los clientes. Para un servidor dado, esto aumenta monotónicamente. Cuando un cliente cambia de un servidor a otro en un clúster, puede asegurarse de que nunca vea una instantánea de datos más antigua evitando servidores que tengan un index menor que el valor más alto que ya han observado.
Para una base de datos autónoma, activo-respaldo o de retransmisión, esto está vacío.
