NOMBRE

ossl-guide-tls-server-block - Guía de OpenSSL: Escribiendo un servidor TLS bloqueante simple

EJEMPLO DE SERVIDOR TLS BLOQUEANTE SIMPLE

Esta página presentará varios ejemplos de código fuente que demuestran cómo escribir una aplicación de servidor TLS de "eco" simple y no concurrente que acepta una conexión de cliente a la vez, devolviendo la entrada del cliente al mismo cliente. Una vez que el cliente actual se desconecta, se acepta la siguiente conexión de cliente.

Tanto el socket del aceptador como las conexiones del cliente son "bloqueantes". Un servidor más típico podría usar sockets no bloqueantes con un bucle de eventos y devoluciones de llamada para eventos de E/S.

El código fuente completo para este servidor TLS bloqueante de ejemplo está disponible en el directorio demos/guide de la distribución fuente de OpenSSL, en el archivo tls-server-block.c. También está disponible en línea en https://github.com/openssl/openssl/blob/master/demos/guide/tls-server-block.c.

Suponemos que ya tiene OpenSSL instalado en su sistema; que ya tiene una comprensión fundamental de los conceptos de OpenSSL y TLS (ver ossl-guide-libraries-introduction(7) y ossl-guide-tls-introduction(7)); y que sabe cómo escribir y compilar código C y vincularlo contra las bibliotecas libcrypto y libssl que proporciona OpenSSL. También asume que tiene una comprensión básica de TCP/IP y sockets.

Creación de los objetos SSL_CTX y SSL

El primer paso es crear un objeto SSL_CTX para nuestro servidor. Utilizamos la función SSL_CTX_new(3) para este propósito. Alternativamente, podríamos usar SSL_CTX_new_ex(3) si queremos asociar el SSL_CTX con un OSSL_LIB_CTX particular (ver ossl-guide-libraries-introduction(7) para aprender sobre OSSL_LIB_CTX). Pasamos como argumento el valor de retorno de la función TLS_server_method(3). Debería usar este método siempre que esté escribiendo un servidor TLS. Este método utilizará automáticamente la negociación de la versión TLS para seleccionar la versión más alta del protocolo que sea mutuamente compatible tanto para el servidor como para el cliente.

/*
 * Un SSL_CTX contiene información de configuración compartida para múltiples
 * conexiones SSL posteriores por cliente.
 */
ctx = SSL_CTX_new(TLS_server_method());
if (ctx == NULL) {
    ERR_print_errors_fp(stderr);
    errx(res, "Fallo al crear el SSL_CTX del servidor");
}

También nos gustaría restringir las versiones de TLS que estamos dispuestos a aceptar a TLSv1.2 o superior. Las versiones anteriores del protocolo TLS en general deben evitarse siempre que sea posible. Podemos hacer eso usando SSL_CTX_set_min_proto_version(3):

/*
 * Las versiones de TLS anteriores a TLS 1.2 son obsoletas por IETF y DEBERÍAN
 * evitarse si es posible.
 */
if (!SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION)) {
    SSL_CTX_free(ctx);
    ERR_print_errors_fp(stderr);
    errx(res, "Fallo al establecer la versión mínima del protocolo TLS");
}

A continuación, configuramos algunas opciones, consulte SSL_CTX_set_options(3) para obtener detalles:

/*
 * Tolera que los clientes se desconecten sin un "apagado" TLS. Apropiado en todos
 * los protocolos de aplicación que realizan su propio "framing" de mensajes, y
 * no dependen de TLS para defenderse de ataques de "truncamiento".
 */
opts = SSL_OP_IGNORE_UNEXPECTED_EOF;
/*
 * Bloquea posibles ataques de agotamiento de CPU por parte de clientes que solicitan
 * frecuentes renegociaciones. Esto, por supuesto, solo es efectivo si existen
 * límites en la negociación TLS completa inicial o en las tasas de conexión.
 */
opts |= SSL_OP_NO_RENEGOTIATION;
/*
 * La mayoría de los servidores optan por usar su propia preferencia de cifrado, grupo o firma
 * en lugar de la del cliente.
 */
opts |= SSL_OP_SERVER_PREFERENCE;
/* Aplicar las opciones de selección */
SSL_CTX_set_options(ctx, opts);

Los servidores necesitan una clave privada y un certificado. Aunque los cifrados anónimos (sin certificado de servidor) son posibles en TLS 1.2, rara vez son aplicables y actualmente no están definidos para TLS 1.3. A menudo, también se requieren certificados adicionales de CA emisora intermedios, y tanto el certificado del servidor (entidad final o EE) como los certificados del emisor ("cadena") se configuran más fácilmente en un único "archivo de cadena". A continuación, cargamos dicho archivo de cadena (el certificado EE debe aparecer primero), y luego cargamos la clave privada correspondiente, verificando que coincida con el certificado del servidor. No se realizan comprobaciones para verificar la integridad de la cadena (firmas de CA o fechas de vencimiento de certificados, por ejemplo).

/*
 * Cargar el archivo de *cadena* de certificado del servidor (formato PEM), que incluye
 * no solo el certificado del servidor hoja (entidad final), sino también cualquier
 * certificado de CA emisora intermedio. El certificado hoja debe ser el
 * primer certificado en el archivo.
 *
 * En casos de uso avanzados, esto se puede llamar varias veces, una vez por clave pública
 * algoritmo para el que el servidor tiene un certificado correspondiente.
 * Sin embargo, la clave privada correspondiente (ver abajo) debe cargarse primero,
 * *antes* de pasar al siguiente archivo de cadena.
 */
if (SSL_CTX_use_certificate_chain_file(ctx, "chain.pem") <= 0) {
    SSL_CTX_free(ctx);
    ERR_print_errors_fp(stderr);
    errx(res, "Fallo al cargar el archivo de cadena de certificado del servidor");
}
/*
 * Cargar la clave privada correspondiente; esto también comprueba que la clave
 * privada coincide con el certificado de entidad final recién cargado. No comprueba
 * si la cadena de certificados es válida, los certificados podrían estar
 * caducados o de lo contrario podrían no formar una cadena que un cliente pueda validar.
 */
if (SSL_CTX_use_PrivateKey_file(ctx, "pkey.pem", SSL_FILETYPE_PEM) <= 0) {
    SSL_CTX_free(ctx);
    ERR_print_errors_fp(stderr);
    errx(res, "Error al cargar el archivo de clave privada del servidor, "
              "¿posible desajuste de clave/certificado???");
}

A continuación, habilitamos el almacenamiento en caché de sesiones, lo que permite a los clientes realizar conexiones TLS adicionales de manera más eficiente después de completar una negociación TLS completa inicial. Con TLS 1.3, la reanudación de sesiones generalmente aún realiza un nuevo acuerdo de claves, pero se evita el intercambio de certificados.

/*
 * Los servidores que desean habilitar la reanudación de sesiones deben especificar una matriz
 * de bytes de ID de sesión que identifique la aplicación del servidor y reduzca la
 * posibilidad de compartir caché inapropiada.
 */
SSL_CTX_set_session_id_context(ctx, (void *)cache_id, sizeof(cache_id));
SSL_CTX_set_session_cache_mode(ctx, SSL_SESS_CACHE_SERVER);
/*
 * Cuántas sesiones TLS de cliente almacenar en caché. El valor predeterminado es
 * SSL_SESSION_CACHE_MAX_SIZE_DEFAULT (20k en versiones recientes de OpenSSL),
 * que puede ser demasiado pequeño o demasiado grande.
 */
SSL_CTX_sess_set_cache_size(ctx, 1024);
/*
 * Las sesiones más antiguas que esto se consideran un error de caché de sesión incluso si todavía están en
 * la caché. El valor predeterminado es dos horas. Los servidores ocupados cuyos clientes realizan
 * muchas conexiones en un breve período pueden desear un tiempo de espera más corto; en servidores
 * con poca carga y conexiones esporádicas de un cliente determinado, un tiempo
 * más largo puede ser apropiado.
 */
SSL_CTX_set_timeout(ctx, 3600);

La mayoría de los servidores, incluido este, no solicitan certificados de cliente. Por lo tanto, no necesitamos un "almacén de confianza" y permitimos que la negociación se complete incluso cuando el cliente no presenta un certificado. Nota: Incluso si un cliente presentara un certificado de confianza, para que sea útil, la aplicación del servidor aún necesitaría código personalizado para usar la identidad verificada para otorgar acceso no predeterminado a ese cliente en particular. Algunos servidores otorgan acceso a todos los clientes con certificados de una CA privada; esto requiere el procesamiento de listas de revocación de certificados para desautorizar a un cliente. A menudo es más simple y seguro mantener una lista de claves públicas autorizadas.

Aunque esta es la configuración predeterminada, llamamos explícitamente a la función SSL_CTX_set_verify(3) y le pasamos el valor SSL_VERIFY_NONE. El argumento final de esta función es una función de devolución de llamada que opcionalmente puede proporcionar para anular el manejo predeterminado de la verificación de certificados. La mayoría de las aplicaciones no necesitan hacer esto, por lo que se puede establecer de forma segura en NULL para obtener el manejo predeterminado.

/*
 * Los clientes rara vez utilizan la autenticación basada en certificados, y por lo tanto no
 * requerimos autenticación mutua TLS (de hecho, no hay forma de saber
 * si y cómo el cliente autenticó al servidor, por lo que el término "mutuo"
 * es potencialmente engañoso).
 *
 * Dado que no solicitamos ni procesamos certificados de cliente, no
 * necesitamos configurar un almacén de certificados de confianza, por lo que no se necesita una llamada a
 * SSL_CTX_set_default_verify_paths().

NAME

ossl-guide-tls-server-block - Simple blocking TLS server example

SIMPLE BLOCKING TLS SERVER EXAMPLE

This example shows how to set up a simple blocking TLS server. It listens on a given port, accepts incoming client connections, performs an SSL handshake, and then echoes any received data back to the client.

The code is derived from the OpenSSL documentation on BIOs and SSL/TLS.

Server setup

First, we initialize the OpenSSL library and create an SSL_CTX structure. This structure holds the configuration for our TLS server, including the certificate and private key to be used.

/* Load up the libraries */
SSL_library_init();
SSL_load_error_strings();
OpenSSL_add_all_algorithms();

/* Create our context */
ctx = SSL_CTX_new(TLS_server_method());
if (ctx == NULL) {
    ERR_print_errors_fp(stderr);
    errx(res, "Error creating SSL context");
}

Next, we configure the context to load the server certificate and private key. In a real-world application, these would be loaded from files.

/* Load our certificate bundle and private key */
if (SSL_CTX_use_certificate_chain_file(ctx, "server-chain.pem") <= 0) {
    ERR_print_errors_fp(stderr);
    errx(res, "Error loading certificate chain file");
}
if (SSL_CTX_use_PrivateKey_file(ctx, "server-key.pem",
    SSL_FILETYPE_PEM) <= 0) {
    ERR_print_errors_fp(stderr);
    errx(res, "Error loading private key file");
}

For simplicity in this example, we disable certificate verification for incoming client connections. In a production environment, you would typically want to verify client certificates.

/*
 * The server's own
 * certificate chain is assumed valid.
 */
SSL_CTX_set_verify(ctx, SSL_VERIFY_NONE, NULL);

That is all the setup that we need to do for the SSL_CTX. Next we create an acceptor BIO on which to accept client connections. This just records the intended port (and optional "host:" prefix), without actually creating the socket. This delayed processing allows the programmer to specify additional behaviours before the listening socket is actually created.

/*
 * Create a listener socket wrapped in a BIO.
 * The first call to BIO_do_accept() initialises the socket
 */
acceptor_bio = BIO_new_accept(hostport);
if (acceptor_bio == NULL) {
    SSL_CTX_free(ctx);
    ERR_print_errors_fp(stderr);
    errx(res, "Error creating acceptor bio");
}

Servers almost always want to use the "SO_REUSEADDR" option to avoid startup failures if there are still lingering client connections, so we do that before making the first call to BIO_do_accept(3) which creates the listening socket, without accepting a client connection. Subsequent calls to the same function will accept new connections.

BIO_set_bind_mode(acceptor_bio, BIO_BIND_REUSEADDR);
if (BIO_do_accept(acceptor_bio) <= 0) {
    SSL_CTX_free(ctx);
    ERR_print_errors_fp(stderr);
    errx(res, "Error setting up acceptor socket");
}

Server loop

The server now enters a "forever" loop handling one client connection at a time. Before each connection we clear the OpenSSL error stack, so that any error reports are related to just the new connection.

/* Pristine error stack for each new connection */
ERR_clear_error();

At this point the server blocks to accept the next client:

/* Wait for the next client to connect */
if (BIO_do_accept(acceptor_bio) <= 0) {
    /* Client went away before we accepted the connection */
    continue;
}

On success the accepted client connection has been wrapped in a fresh BIO and pushed onto the end of the acceptor BIO chain. We pop it off returning the acceptor BIO to its initial state.

/* Pop the client connection from the BIO chain */
client_bio = BIO_pop(acceptor_bio);
fprintf(stderr, "New client connection accepted\n");

Next, we create an SSL object by calling the SSL_new(3) function and passing the SSL_CTX we created as an argument. The client connection BIO is configured as the I/O conduit for this SSL handle. SSL_set_bio transfers ownership of the BIO or BIOs involved (our client_bio) to the SSL handle.

/* Associate a new SSL handle with the new connection */
if ((ssl = SSL_new(ctx)) == NULL) {
    ERR_print_errors_fp(stderr);
    warnx("Error creating SSL handle for new connection");
    BIO_free(client_bio);
    continue;
}
SSL_set_bio(ssl, client_bio, client_bio);

And now we're ready to attempt the SSL handshake. With a blocking socket OpenSSL will perform all the read and write operations required to complete the handshake (or detect and report a failure) before returning.

/* Attempt an SSL handshake with the client */
if (SSL_accept(ssl) <= 0) {
    ERR_print_errors_fp(stderr);
    warnx("Error performing SSL handshake with client");
    SSL_free(ssl);
    continue;
}

With the handshake complete, the server loops echoing client input back to the client:

while (SSL_read_ex(ssl, buf, sizeof(buf), &nread) > 0) {
    if (SSL_write_ex(ssl, buf, nread, &nwritten) > 0 &&
        nwritten == nread) {
        total += nwritten;
        continue;
    }
    warnx("Error echoing client input");
    break;
}

Once the client closes its connection, we report the number of bytes sent to stderr and free the SSL handle, which also frees the client_bio and closes the underlying socket.

fprintf(stderr, "Client connection closed, %zu bytes sent\n", total);
SSL_free(ssl);

The server is now ready to accept the next client connection.

Final clean up

If the server could somehow manage to break out of the infinite loop, and be ready to exit, it would first deallocate the constructed SSL_CTX.

/*
 * Unreachable placeholder cleanup code, the above loop runs forever.
 */
SSL_CTX_free(ctx);
return EXIT_SUCCESS;
