NOMBRE

ossl-guide-libraries-introduction - Guía de OpenSSL: Introducción a las bibliotecas de OpenSSL

INTRODUCCIÓN

OpenSSL proporciona dos bibliotecas que pueden ser utilizadas por aplicaciones, conocidas como "libcrypto" y "libssl".

La biblioteca "libcrypto" proporciona APIs para criptografía de propósito general, como cifrado, firmas digitales, funciones hash, etc. Adicionalmente, suministra APIs de soporte para estándares relacionados con la criptografía, por ejemplo, para leer y escribir certificados digitales (también conocidos como certificados X.509). Finalmente, también suministra varias APIs de soporte adicionales que no están directamente relacionadas con la criptografía pero que son, no obstante, útiles y dependen de otras APIs. Por ejemplo, las funciones "BIO" proporcionan capacidades para abstraer la E/S, por ejemplo, a través de un archivo o por red.

La biblioteca "libssl" proporciona funciones para realizar comunicaciones seguras entre dos pares a través de una red. Lo más significativo es que implementa soporte para los estándares SSL/TLS, DTLS y QUIC.

La biblioteca "libssl" depende y utiliza muchas de las capacidades proporcionadas por "libcrypto". Cualquier aplicación enlazada contra "libssl" también se enlazará contra "libcrypto", y la mayoría de las aplicaciones que lo hacen utilizarán directamente funciones de la API proporcionadas por ambas bibliotecas.

Se pueden escribir aplicaciones que solo utilicen las capacidades de "libcrypto" y no se enlacen contra "libssl" en absoluto.

PROVEEDORES

Además de las dos bibliotecas principales, OpenSSL también viene con un conjunto de proveedores.

Un proveedor en OpenSSL es un componente que agrupa implementaciones de algoritmos (por ejemplo, una implementación del algoritmo de cifrado simétrico AES). Para utilizar un algoritmo, debes tener al menos un proveedor cargado que contenga una implementación del mismo. OpenSSL viene con varios proveedores y también se pueden obtener de terceros.

Los proveedores pueden ser "incorporados" (built-in) o en forma de un archivo de módulo cargable por separado (típicamente uno que termina en ".so" o ".dll", dependiendo de la plataforma). Un proveedor incorporado es uno que ya está presente en "libcrypto" o uno que la aplicación ha proporcionado directamente. Los terceros también pueden proporcionar proveedores en forma de módulos cargables.

Si no cargas un proveedor explícitamente (ya sea en el código del programa o a través de la configuración), el proveedor "predeterminado" incorporado de OpenSSL se cargará automáticamente.

Ver "PROVEEDORES DE OPENSSL" más abajo para una descripción de los proveedores que OpenSSL mismo suministra.

Cargar y descargar proveedores es una operación bastante costosa. Normalmente se realiza una vez, al principio del ciclo de vida de la aplicación, y esos proveedores se mantienen cargados durante la ejecución de la aplicación.

CONTEXTOS DE BIBLIOTECA

Muchas funciones de la API de OpenSSL utilizan un contexto de biblioteca. Un contexto de biblioteca puede considerarse un "ámbito" dentro del cual surten efecto las opciones de configuración. Cuando se carga un proveedor, solo se carga dentro del ámbito de un contexto de biblioteca determinado. De esta manera, es posible que diferentes componentes de una aplicación compleja utilicen cada uno un contexto de biblioteca diferente y tengan diferentes proveedores cargados con diferentes configuraciones.

Si una aplicación no crea explícitamente un contexto de biblioteca, se utilizará el contexto de biblioteca "predeterminado".

Los contextos de biblioteca se representan mediante el tipo OSSL_LIB_CTX. Muchas funciones de la API de OpenSSL toman un contexto de biblioteca como parámetro. Las aplicaciones siempre pueden pasar NULL para este parámetro para simplemente usar el contexto de biblioteca predeterminado.

El contexto de biblioteca predeterminado se crea automáticamente la primera vez que se necesita. Esto cargará automáticamente cualquier archivo de configuración disponible e inicializará OpenSSL para su uso. A diferencia de las versiones anteriores de OpenSSL (anteriores a 1.1.0), no es necesario tomar medidas explícitas de inicialización.

Del mismo modo, cuando la aplicación finaliza, el contexto de biblioteca predeterminado se destruye automáticamente. No es necesario tomar medidas explícitas de desinicialización.

Ver OSSL_LIB_CTX(3) para más información sobre contextos de biblioteca. Ver también "BÚSQUEDA DE ALGORITMOS" en ossl-guide-libcrypto-introduction(7).

CADENAS DE CONSULTA DE PROPIEDADES

En algunos casos, los proveedores disponibles pueden significar que más de una implementación de cualquier algoritmo dado podría estar disponible. Por ejemplo, el proveedor FIPS de OpenSSL suministra implementaciones alternativas de muchos de los mismos algoritmos que están disponibles en el proveedor predeterminado de OpenSSL.

El proceso de selección de una implementación de algoritmo se conoce como "búsqueda" (fetching). Cuando OpenSSL busca un algoritmo para usar, es posible especificar una "cadena de consulta de propiedades" para guiar el proceso de selección. Por ejemplo, se podría utilizar una cadena de consulta de propiedades de "provider=default" para forzar que la selección considere solo las implementaciones de algoritmos en el proveedor predeterminado.

Las cadenas de consulta de propiedades se pueden especificar explícitamente como un argumento de una función. También es posible especificar una cadena de consulta de propiedades predeterminada para todo el contexto de biblioteca utilizando las funciones EVP_set_default_properties(3) o EVP_default_properties_enable_fips(3). Donde se especifican tanto propiedades predeterminadas como propiedades específicas de la función, estas se combinan. Las propiedades específicas de la función anularán las propiedades predeterminadas donde haya un conflicto.

Ver "BÚSQUEDA DE ALGORITMOS" en ossl-guide-libcrypto-introduction(7) para más información sobre la búsqueda. Ver property(7) para más información sobre propiedades.

APLICACIONES MULTIHILO

Siempre que OpenSSL se haya compilado con soporte para hilos (el caso predeterminado en la mayoría de las plataformas), la mayoría de las *funciones* de OpenSSL son seguras para hilos en el sentido de que es seguro llamar a la misma función desde múltiples hilos al mismo tiempo. Sin embargo, la mayoría de las *estructuras de datos* de OpenSSL no son seguras para hilos. Por ejemplo, las funciones BIO_write(3) y BIO_read(3) son seguras para hilos. Sin embargo, no sería seguro para hilos llamar a BIO_write() desde un hilo mientras se llama a BIO_read() en otro, donde ambas funciones se pasan el mismo objeto BIO, ya que ambas pueden intentar realizar cambios en el mismo objeto BIO.

Hay excepciones a estas reglas. Un pequeño número de funciones no son seguras para hilos en absoluto. Donde este sea el caso, esta restricción debe notarse en la documentación de la función. De manera similar, algunas estructuras de datos pueden ser parcial o totalmente seguras para hilos. Por ejemplo, siempre es seguro usar un OSSL_LIB_CTX en múltiples hilos.

Ver openssl-threads(7) para una discusión más detallada sobre el soporte de hilos de OpenSSL.

MANEJO DE ERRORES

La mayoría de las funciones de OpenSSL proporcionarán un valor de retorno que indicará si la función ha tenido éxito o no. Se considera una buena práctica comprobar siempre el valor de retorno de las funciones de OpenSSL (donde esté disponible).

La mayoría de las funciones que devuelven un valor de puntero devolverán NULL en caso de fallo.

La mayoría de las funciones que devuelven un valor entero devolverán un entero positivo para indicar éxito. Algunas de estas funciones devolverán 0 para indicar un fallo. Otras pueden devolver 0 o un valor negativo para indicar un fallo.

Algunas funciones no pueden fallar y tienen un tipo de retorno void. También hay un pequeño número de funciones que no se ajustan a las convenciones anteriores (por ejemplo, pueden devolver 0 para indicar éxito).

ERRORS

OpenSSL functions typically return an integer value indicating success or failure. The specific return value indicating failure depends on the function. For example, some functions may return 0 for failure, others may return -1, and still others may return a NULL pointer. It is important to consult the manual page for each function for specific information about how to interpret the return value.

It is sometimes necessary to get further information about the cause of a failure (e.g. for debugging or logging purposes). Many (but not all) functions will add further information about a failure to the OpenSSL error stack. By using the error stack you can find out information such as a reason code/string for the error as well as the exact file and source line within OpenSSL that emitted the error.

OpenSSL supplies a set of error handling functions to query the error stack. See ERR_get_error(3) for information about the functions available for querying error data. Also see ERR_print_errors(3) for information on some simple helper functions for printing error data. Finally look at ERR_clear_error(3) for how to clear old errors from the error stack.

OPENSSL PROVIDERS

OpenSSL comes with a set of providers.

The algorithms available in each of these providers may vary due to build time configuration options. The openssl-list(1) command can be used to list the currently available algorithms.

The names of the algorithms shown from openssl-list(1) can be used as an algorithm identifier to the appropriate fetching function. Also see the provider specific manual pages linked below for further details about using the algorithms available in each of the providers.

As well as the OpenSSL providers third parties can also implement providers. For information on writing a provider see provider(7).

Default provider

The default provider is built-in as part of the libcrypto library and contains all of the most commonly used algorithm implementations. Should it be needed (if other providers are loaded and offer implementations of the same algorithms), the property query string "provider=default" can be used as a search criterion for these implementations. The default provider includes all of the functionality in the base provider below.

If you don't load any providers at all then the "default" provider will be automatically loaded. If you explicitly load any provider then the "default" provider would also need to be explicitly loaded if it is required.

See OSSL_PROVIDER-default(7).

Base provider

The base provider is built in as part of the libcrypto library and contains algorithm implementations for encoding and decoding of OpenSSL keys. Should it be needed (if other providers are loaded and offer implementations of the same algorithms), the property query string "provider=base" can be used as a search criterion for these implementations. Some encoding and decoding algorithm implementations are not FIPS algorithm implementations in themselves but support algorithms from the FIPS provider and are allowed for use in "FIPS mode". The property query string "fips=yes" can be used to select such algorithms.

See OSSL_PROVIDER-base(7).

FIPS provider

The FIPS provider is a dynamically loadable module, and must therefore be loaded explicitly, either in code or through OpenSSL configuration (see config(5)). It contains algorithm implementations that have been validated according to FIPS standards. Should it be needed (if other providers are loaded and offer implementations of the same algorithms), the property query string "provider=fips" can be used as a search criterion for these implementations. All approved algorithm implementations in the FIPS provider can also be selected with the property "fips=yes". The FIPS provider may also contain non-approved algorithm implementations and these can be selected with the property "fips=no".

Typically the "Base provider" will also need to be loaded because the FIPS provider does not support the encoding or decoding of keys.

See OSSL_PROVIDER-FIPS(7) and fips_module(7).

Legacy provider

The legacy provider is a dynamically loadable module, and must therefore be loaded explicitly, either in code or through OpenSSL configuration (see config(5)). It contains algorithm implementations that are considered insecure, or are no longer in common use such as MD2 or RC4. Should it be needed (if other providers are loaded and offer implementations of the same algorithms), the property "provider=legacy" can be used as a search criterion for these implementations.

See OSSL_PROVIDER-legacy(7).

Null provider

The null provider is built in as part of the libcrypto library. It contains no algorithms in it at all. When fetching algorithms the default provider will be automatically loaded if no other provider has been explicitly loaded. To prevent that from happening you can explicitly load the null provider.

You can use this if you create your own library context and want to ensure that all API calls have correctly passed the created library context and are not accidentally using the default library context. Load the null provider into the default library context so that the default library context has no algorithm implementations available.

See OSSL_PROVIDER-null(7).

CONFIGURATION

By default OpenSSL will load a configuration file when it is first used. This will set up various configuration settings within the default library context. Applications that create their own library contexts may optionally configure them with a config file using the OSSL_LIB_CTX_load_config(3) function.

The configuration file can be used to automatically load providers and set up default property query strings.

For information on the OpenSSL configuration file format see config(5).

LIBRARY CONVENTIONS

Many OpenSSL functions that "get" or "set" a value follow a naming convention using the numbers 0 and 1, i.e. "get0", "get1", "set0" and "set1". This can also apply to some functions that "add" a value to an existing set, i.e. "add0" and "add1".

For example the functions:

int X509_CRL_add0_revoked(X509_CRL *crl, X509_REVOKED *rev);
int X509_add1_trust_object(X509 *x, const ASN1_OBJECT *obj);

In the 0 version the ownership of the object is passed to (for an add or set) or retained by (for a get) the parent object. For example after calling the X509_CRL_add0_revoked() function above, ownership of the rev object is passed to the crl object. Therefore, after calling this function rev should not be freed directly. It will be freed implicitly when crl is freed.

In the 1 version the ownership of the object is not passed to or retained by the parent object. Instead a copy or "up ref" of the object is performed. So after calling the X509_add1_trust_object() function above the application will still be responsible for freeing the obj value where appropriate.

Many OpenSSL functions conform to a naming convention of the form CLASSNAME_func_name(). In this naming convention the CLASSNAME is the name of an OpenSSL data structure (given in capital letters) that the function is primarily operating on. The func_name portion of the name is usually in lowercase letters and indicates the purpose of the function.

DEMO APPLICATIONS

OpenSSL is distributed with a set of demo applications which provide some examples of how to use the various API functions. To look at them download the OpenSSL source code from the OpenSSL website (https://www.openssl.org/source/). Extract the downloaded .tar.gz file for the version of OpenSSL that you are using and look at the various files in the demos sub-directory.

The Makefiles in the subdirectories give instructions on how to build and run the demo applications.

OpenSSL(1) Library Introduction

NAME

ossl-guide-libraries-introduction - OpenSSL library introduction

INTRODUCTION

This document introduces the OpenSSL 3.0 library. This is a major new release with significant changes in the internal architecture and API compared to previous versions.

The key new feature is the introduction of the Provider concept. Providers are dynamically loadable shared objects that implement cryptographic algorithms and other functionalities. This modular architecture allows for easier integration of new algorithms, algorithms from third-party vendors, and optimized implementations.

This document describes the basic concepts of the OpenSSL 3.0 library and how to use it.

PROVIDERS

Providers are the core of the new architecture. They are responsible for implementing cryptographic algorithms and functionalities. OpenSSL ships with several built-in providers:

  • default: Provides a comprehensive set of algorithms, including software implementations and, where available, hardware acceleration.
  • legacy: Provides algorithms that were deprecated in OpenSSL 3.0 but are still available for compatibility purposes.
  • null: A provider that implements nothing. Useful for testing and benchmarking.

You can also create your own providers to implement custom algorithms or use third-party implementations.

LIBRARY CONTEXTS

A OSSL_LIB_CTX (library context) is a central object that holds configuration information, loaded providers, and other global state. Most OpenSSL functions now operate within a library context. This allows for:

  • Isolation of configurations and providers between different parts of an application.
  • Dynamic loading and unloading of providers.
  • Customization of the library's behavior.

You can obtain the default library context using OSSL_LIB_CTX_get_default(). For more advanced use cases, you can create your own library contexts using OSSL_LIB_CTX_new().

PROPERTY QUERY STRINGS

Providers and algorithms can expose properties, which are key-value pairs describing their capabilities and characteristics. For example, an algorithm might have properties like:

  • provider=default
  • algorithm=aes256-cbc
  • ciphers=aes
  • security_bits=256
  • implementation=openssl

These properties are used to select the desired algorithm when creating cryptographic operations. You can specify property requirements using property query strings, which are a comma-separated list of key=value pairs. For example:

OSSL_PARAM_get_property(prop)

OSSL_PROVIDER_do_all(NULL, foo, NULL);

EVP_MD_fetch(ctx, "sha256", "provider=default,digest=sha256");

MULTI-THREADED APPLICATIONS

OpenSSL 3.0 is designed with thread safety in mind. However, you must manage library contexts appropriately in multi-threaded applications. Each thread can use its own library context, or multiple threads can share a context if it's properly protected against concurrent access.

It's generally recommended to use separate library contexts for different threads or components to avoid potential race conditions and ensure proper isolation.

ERROR HANDLING

Error handling in OpenSSL 3.0 has been improved. Functions that can fail typically return a value indicating success or failure (e.g., a pointer to a valid object or NULL, an integer 1 or 0). In case of failure, detailed error information can be retrieved using ERR_get_error() and related functions.

The error queue mechanism remains the same, allowing you to retrieve error codes and associated reasons.

OPENSSL PROVIDERS

As mentioned earlier, providers are dynamically loaded modules that supply cryptographic algorithms. When OpenSSL needs to perform an operation (e.g., encryption, hashing), it queries the loaded providers to find an implementation that matches the requested algorithm and properties.

The default provider is usually loaded automatically. You can explicitly load or unload providers using functions like OSSL_PROVIDER_load() and OSSL_PROVIDER_unload().

CONFIGURATION

The configuration of OpenSSL 3.0 is primarily managed through library contexts and providers. Instead of a global openssl.cnf file, configuration can be provided per-context or through specific API calls.

However, for compatibility and convenience, OpenSSL still looks for an openssl.cnf file in standard locations if no other configuration is explicitly provided.

LIBRARY CONVENTIONS

  • API functions often take an OSSL_LIB_CTX pointer as their first argument.
  • Functions for fetching algorithms (e.g., EVP_MD_fetch(), EVP_CIPHER_fetch()) accept a property query string to specify requirements.
  • The return values and error handling mechanisms are generally consistent across the library.

DEMO APPLICATIONS

The OpenSSL source distribution includes example applications demonstrating how to use the new library APIs. These can be found in the demos/ directory.
