NOMBRE

ossl-guide-tls-introduction - Guía de OpenSSL: Una introducción a SSL/TLS en OpenSSL

INTRODUCCIÓN

Esta página proporcionará una introducción a algunos conceptos y antecedentes básicos de SSL/TLS y cómo se utiliza dentro de OpenSSL. Asume que usted tiene una comprensión básica de TCP/IP y sockets.

¿QUÉ ES TLS?

TLS significa Transport Layer Security. TLS permite a las aplicaciones comunicarse de forma segura entre sí a través de una red, de modo que se proteja la confidencialidad de la información intercambiada (es decir, evita que los fisgones escuchen la comunicación). Además, protege la integridad de la información intercambiada para evitar que un atacante la modifique. Finalmente, proporciona autenticación para que una o ambas partes puedan estar seguras de que están hablando con quien creen que están hablando y no con algún impostor.

A veces, TLS se conoce por el nombre de su predecesor, SSL (Secure Sockets Layer). OpenSSL data de una época en la que el nombre SSL todavía estaba en uso común y, por lo tanto, muchas de las funciones y nombres utilizados por OpenSSL contienen la abreviatura "SSL". No obstante, OpenSSL contiene una implementación completa de TLS.

TLS se basa en un modelo cliente/servidor. La aplicación que inicia una comunicación se conoce como cliente. La aplicación que responde a una comunicación iniciada remotamente es el servidor. El término "endpoint" se refiere a cualquiera de los dos, el cliente o el servidor, en una comunicación. El término "peer" se refiere al endpoint en el otro extremo de la comunicación al que nos estamos refiriendo actualmente. Así, si actualmente estamos hablando del cliente, el peer sería el servidor.

TLS es un protocolo estandarizado y existen numerosas implementaciones diferentes del mismo. Debido a los estándares, un cliente o servidor de OpenSSL puede comunicarse sin problemas con una aplicación que utiliza una implementación diferente de TLS. TLS (y su predecesor SSL) han existido durante un período de tiempo significativo y el protocolo ha sufrido varios cambios a lo largo de los años. En consecuencia, existen diferentes versiones del protocolo disponibles. TLS incluye la capacidad de realizar la negociación de versiones para que se utilice la versión de protocolo más alta que el cliente y el servidor compartan en común.

TLS actúa como una capa de seguridad sobre algún protocolo de transporte de nivel inferior. Típicamente, la capa de transporte será TCP.

VERSIONES SSL Y TLS

SSL fue desarrollado inicialmente por Netscape Communications y su primera versión lanzada públicamente fue SSLv2 en 1995. Tenga en cuenta que SSLv1 nunca fue lanzado públicamente. SSLv3 llegó poco después en 1996. Posteriormente, el desarrollo del protocolo se trasladó a la IETF, que lanzó la primera versión de TLS (TLSv1.0) en 1999 como RFC2246. TLSv1.1 se lanzó en 2006 como RFC4346 y TLSv1.2 llegó en 2008 como RFC5246. La versión más reciente del estándar es TLSv1.3, que se lanzó en 2018 como RFC8446.

Hoy en día, TLSv1.3 y TLSv1.2 son las versiones más comúnmente desplegadas del protocolo. La IETF ha declarado formalmente obsoletos TLSv1.1 y TLSv1.0, por lo que se debe evitar todo lo que esté por debajo de TLSv1.2, ya que las versiones de protocolo más antiguas son susceptibles a problemas de seguridad.

OpenSSL no admite SSLv2 (fue eliminado en OpenSSL 1.1.0). El soporte para SSLv3 está disponible como una opción de tiempo de compilación, pero no está habilitado por defecto. El soporte para TLSv1.0, TLSv1.1, TLSv1.2 y TLSv1.3 está disponible por defecto en una compilación estándar de OpenSSL. Sin embargo, se requiere una configuración especial en tiempo de ejecución para que TLSv1.0 y TLSv1.1 funcionen correctamente.

OpenSSL siempre intentará negociar la versión de protocolo más alta que se haya configurado para admitir. En la mayoría de los casos, esto significará que se elegirá TLSv1.3 o TLSv1.2.

CERTIFICADOS

Para que un cliente establezca una conexión con un servidor, debe autenticar la identidad de ese servidor, es decir, debe confirmar que el servidor es realmente el servidor que dice ser y no un impostor. Para hacer esto, el servidor enviará al cliente un certificado digital (también conocido comúnmente como certificado X.509). El certificado contiene diversa información sobre el servidor, incluido su nombre de host DNS completo. Dentro del certificado también se encuentra la clave pública del servidor. El operador del servidor tendrá una clave privada que está vinculada a la clave pública y no debe publicarse.

Junto con el certificado, el servidor también enviará al cliente una prueba de que conoce la clave privada asociada con la clave pública del certificado. Lo hace firmando digitalmente un mensaje al cliente utilizando esa clave privada. El cliente puede verificar la firma utilizando la clave pública del certificado. Si la firma se verifica correctamente, el cliente sabe que el servidor posee la clave privada correcta.

El certificado que envía el servidor también será firmado por una Autoridad Certificadora. La Autoridad Certificadora (comúnmente conocida como CA) es una organización de terceros responsable de verificar la información en el certificado del servidor (incluido su nombre de host DNS). La CA solo debe firmar el certificado si ha podido confirmar que el operador del servidor tiene control sobre el servidor asociado con su nombre de host DNS y que el operador del servidor tiene control sobre la clave privada.

De esta manera, si el cliente confía en la CA que ha firmado el certificado del servidor y puede verificar que el servidor tiene la clave privada correcta, puede confiar en que el servidor representa verdaderamente el nombre de host DNS dado en el certificado. El cliente también debe verificar que el nombre de host dado en el certificado coincide con el nombre de host al que originalmente envió la solicitud.

Una vez que se han realizado todas estas comprobaciones, el cliente ha verificado con éxito la identidad del servidor. OpenSSL puede realizar todas estas comprobaciones automáticamente, pero se le debe proporcionar cierta información para hacerlo, es decir, el conjunto de CA en las que confía el cliente, así como el nombre de host DNS del servidor al que este cliente intenta conectarse.

Tenga en cuenta que es común que los certificados se construyan en una cadena. Por ejemplo, el certificado de un servidor puede ser firmado por una clave propiedad de una CA intermedia. Esa CA intermedia también tiene un certificado que contiene su clave pública, que a su vez está firmada por una clave propiedad de una CA raíz. El cliente puede confiar solo en la CA raíz, pero si el servidor envía tanto su propio certificado como el certificado de la CA intermedia, el cliente aún puede verificar con éxito la identidad del servidor. Existe una cadena de confianza entre la CA raíz y el servidor.

Por defecto, solo el cliente autentica al servidor utilizando este método. Sin embargo, también es posible configurar las cosas de manera que el servidor autentique adicionalmente al cliente. Esto se conoce como "autenticación de cliente". En este enfoque, el cliente seguirá autenticando al servidor de la misma manera, pero el servidor solicitará un certificado al cliente. El cliente le envía su certificado al servidor y el servidor lo autentica de la misma manera que lo hace el cliente.

ALMACÉN DE CERTIFICADOS DE CONFIANZA

El sistema descrito anteriormente solo funciona si se puede construir una cadena de confianza entre el conjunto de CA en las que confía el endpoint y el certificado que utiliza el peer. Por lo tanto, el endpoint debe tener un conjunto de certificados de CA en los que confíe antes de que pueda tener lugar cualquier comunicación. OpenSSL en sí mismo no proporciona tal conjunto de certificados. Por lo tanto, deberá asegurarse de tenerlos antes de comenzar si va a verificar certificados (es decir, siempre si el endpoint es un cliente, y solo si se utiliza la autenticación de cliente para un servidor).

Afortunadamente, otras organizaciones mantienen dicho conjunto de certificados. Si ha obtenido su copia de OpenSSL de un proveedor de Sistema Operativo (SO) (por ejemplo, una distribución de Linux), entonces normalmente el conjunto de certificados de CA también se distribuirá con esa copia.

Puede verificar esto ejecutando la aplicación de línea de comandos de OpenSSL de la siguiente manera:

openssl version -d

CERTIFICATE STORES

OpenSSL relies on a set of trusted CA certificates in order to verify that a server is genuine. Where these certificates are stored depends on how you installed OpenSSL. Most operating systems come with a default set of trusted CA certificates installed, and OpenSSL will typically use these by default. If they are not already present then they may be found in the file cert.pem which is usually found in the OPENSSLDIR directory.

If you are running your version of OpenSSL on Windows then OpenSSL (from version 3.2 onwards) will use the default Windows set of trusted CAs.

If you have built your version of OpenSSL from source, or obtained it from some other location and it does not have a set of trusted CA certificates then you will have to obtain them yourself. One such source is the Curl project. See the page https://curl.se/docs/caextract.html where you can download trusted certificates in a single file. Rename the file to "cert.pem" and store it directly in OPENSSLDIR. For example if OPENSSLDIR is "/usr/local/ssl", then save it as "/usr/local/ssl/cert.pem".

You can also use environment variables to override the default location that OpenSSL will look for its trusted certificate store. Set the SSL_CERT_PATH environment variable to give the directory where OpenSSL should looks for its certificates or the SSL_CERT_FILE environment variable to give the name of a single file containing all of the certificates. See openssl-env(7) for further details about OpenSSL environment variables. For example you could use this capability to have multiple versions of OpenSSL all installed on the same system using different values for OPENSSLDIR but all using the same trusted certificate store.

You can test that your trusted certificate store is setup correctly by using it via the OpenSSL command line. Use the following command to connect to a TLS server:

openssl s_client www.openssl.org:443

Once the command has connected type the letter "Q" followed by "<enter>" to exit the session. This will print a lot of information on the screen about the connection. Look for a block of text like this:

SSL handshake has read 4584 bytes and written 403 bytes
Verification: OK

Hopefully if everything has worked then the "Verification" line will say "OK". If its not working as expected then you might see output like this instead:

SSL handshake has read 4584 bytes and written 403 bytes
Verification error: unable to get local issuer certificate

The "unable to get local issuer certificate" error means that OpenSSL has been unable to find a trusted CA for the chain of certificates provided by the server in its trusted certificate store. Check your trusted certificate store configuration again.

Note that s_client is a testing tool and will still allow you to connect to the TLS server regardless of the verification error. Most applications should not do this and should abort the connection in the event of a verification error.

IMPORTANT OBJECTS FOR AN OPENSSL TLS APPLICATION

A TLS connection is represented by the SSL object in an OpenSSL based application. Once a connection with a remote peer has been established an endpoint can "write" data to the SSL object to send data to the peer, or "read" data from it to receive data from the server.

A new SSL object is created from an SSL_CTX object. Think of an SSL_CTX as a "factory" for creating SSL objects. You can create a single SSL_CTX object and then create multiple connections (i.e. SSL objects) from it. Typically you can set up common configuration options on the SSL_CTX so that all the SSL object created from it inherit the same configuration options.

Note that internally to OpenSSL various items that are shared between multiple SSL objects are cached in the SSL_CTX for performance reasons. Therefore it is considered best practice to create one SSL_CTX for use by multiple SSL objects instead of having one SSL_CTX for each SSL object that you create.

Each SSL object is also associated with two BIO objects. A BIO object is used for sending or receiving data from the underlying transport layer. For example you might create a BIO to represent a TCP socket. The SSL object uses one BIO for reading data and one BIO for writing data. In most cases you would use the same BIO for each direction but there could be some circumstances where you want them to be different.

It is up to the application programmer to create the BIO objects that are needed and supply them to the SSL object. See ossl-guide-tls-client-block(7) and ossl-guide-tls-server-block(7) for usage examples.

Finally, an endpoint can establish a "session" with its peer. The session holds various TLS parameters about the connection between the client and the server. The session details can then be reused in a subsequent connection attempt to speed up the process of connecting. This is known as "resumption". Sessions are represented in OpenSSL by the SSL_SESSION object. In TLSv1.2 there is always exactly one session per connection. In TLSv1.3 there can be any number per connection including none.

PHASES OF A TLS CONNECTION

A TLS connection starts with an initial "set up" phase. The endpoint creates the SSL_CTX (if one has not already been created) and configures it.

A client then creates an SSL object to represent the new TLS connection. Any connection specific configuration parameters are then applied and the underlying socket is created and associated with the SSL via BIO objects.

A server will create a socket for listening for incoming connection attempts from clients. Once a connection attempt is made the server will create an SSL object in the same way as for a client and associate it with a BIO for the newly created incoming socket.

After set up is complete the TLS "handshake" phase begins. A TLS handshake consists of the client and server exchanging a series of TLS handshake messages to establish the connection. The client starts by sending a "ClientHello" handshake message and the server responds with a "ServerHello". The handshake is complete once an endpoint has sent its last message (known as the "Finished" message) and received a Finished message from its peer. Note that this might occur at slightly different times for each peer. For example in TLSv1.3 the server always sends its Finished message before the client. The client later responds with its Finished message. At this point the client has completed the handshake because it has both sent and received a Finished message. The server has sent its Finished message but the Finished message from the client may still be in-flight, so the server is still in the handshake phase. It is even possible that the server will fail to complete the handshake (if it considers there is some problem with the messages sent from the client), even though the client may have already progressed to sending application data. In TLSv1.2 this can happen the other way around, i.e. the server finishes first and the client finishes second.

Once the handshake is complete the application data transfer phase begins. Strictly speaking there are some situations where the client can start sending application data even earlier (using the TLSv1.3 "early data" capability) - but we're going to skip over that for this basic introduction.

During application data transfer the client and server can read and write data to the connection freely. The details of this are typically left to some higher level application protocol (for example HTTP). Not all information exchanged during this phase is application data. Some protocol level messages may still be exchanged - so it is not necessarily the case that, just because the underlying socket is "readable", that application data will be available to read.

When the connection is no longer required then it should be shutdown. A shutdown may be initiated by either the client or the server via a message known as a "close_notify" alert. The client or server that receives a close_notify may respond with one and then the connection is fully closed and application data can no longer be sent or received.

Once shutdown is complete a TLS application must clean up by freeing the SSL object.
