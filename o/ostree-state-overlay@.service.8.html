NOMBRE

ostree-state-overlay@.service - Configurar superposiciones de estado

SINOPSIS

ostree-state-overlay@.service

MANEJO DE /OPT

Nota: En general, la preferencia para manejar software en /opt es usar enlaces simbólicos solo para las partes que necesitan ser mutables a algún lugar en /var que pueda ser creado, por ejemplo, por un dropin de tmpfiles.d. Para más información, ver https://bootc-dev.github.io/bootc/building/guidance.html#handling-read-only-vs-writable-locations.

DESCRIPCIÓN

En algunos casos, es útil poder tener un directorio como parte del commit de OSTree y aún así tener este directorio escribible en el lado del cliente. Un ejemplo es el software que se distribuye en /opt. /opt es su propia jerarquía de archivos alternativa con nombres de proveedor que puede contener tanto código como estado. Con las superposiciones de estado, es posible tener la parte de código integrada en OSTree, pero aún así permitir que el directorio sea escribible para que el estado pueda mantenerse allí.

Dado que es escribible, nada impide que código suficientemente privilegiado modifique o elimine contenido que proviene del commit de OSTree. Esto contrasta marcadamente con el contenido en /usr, y se parece más a una distribución basada en un gestor de paquetes.

Crucialmente, este estado se vuelve a basar automáticamente durante las actualizaciones (o más generalmente, cada vez que se arranca un commit de OSTree diferente). La semántica de la reorganización es la siguiente: se elimina cualquier archivo o directorio de estado que modificó el contenido de OSTree, de lo contrario, se mantiene y se fusiona con el nuevo contenido base (usando overlayfs). Esto coincide en su mayor parte con la semántica de un gestor de paquetes.

Para habilitar esta función, simplemente instancie la unidad de plantilla, utilizando la ruta de destino (en notación de ruta de systemd escapada) como nombre de instancia. Por ejemplo, para habilitarla en /opt:

    $ systemctl enable --now ostree-state-overlay@opt.service
