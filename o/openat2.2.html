openat2(2) Manual de llamadas al sistema openat2(2)

NOMBRE

openat2 - abrir y posiblemente crear un archivo (extendido)

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <fcntl.h>          /* Definición de constantes O_* y S_* */
#include <linux/openat2.h>  /* Definición de constantes RESOLVE_* */
#include <sys/syscall.h>    /* Definición de constantes SYS_* */
#include <unistd.h>
long syscall(SYS_openat2, int dirfd, const char *path,
             struct open_how *how, size_t size);

Nota: glibc no proporciona un envoltorio para openat2(), lo que requiere el uso de syscall(2).

DESCRIPCIÓN

La llamada al sistema openat2() es una extensión de openat(2) y proporciona un superconjunto de su funcionalidad.

La llamada al sistema openat2() abre el archivo especificado por path. Si el archivo especificado no existe, opcionalmente puede ser creado (si O_CREAT está especificado en how.flags).

Al igual que con openat(2), si path es relativo, se interpreta en relación con el directorio al que se refiere el descriptor de archivo dirfd (o el directorio de trabajo actual del proceso que llama, si dirfd es el valor especial AT_FDCWD). Si path es absoluto, entonces dirfd se ignora (a menos que how.resolve contenga RESOLVE_IN_ROOT, en cuyo caso path se resuelve en relación con dirfd).

En lugar de tomar un único argumento flags, se pasa una estructura extensible (how) para permitir extensiones futuras. El argumento size debe especificarse como sizeof(struct open_how).

La estructura open_how

El argumento how especifica cómo se debe abrir path y actúa como un superconjunto de los argumentos flags y mode de openat(2). Este argumento es un puntero a una estructura open_how, descrita en open_how(2type).

Cualquier extensión futura a openat2() se implementará como nuevos campos añadidos a la estructura open_how, con un valor cero en un nuevo campo que hará que el kernel se comporte como si ese campo de extensión no estuviera presente. Por lo tanto, el llamador debe rellenar esta estructura con ceros al inicializarla. (Ver la sección "Extensibilidad" de las NOTAS para más detalles sobre por qué esto es necesario).

Los campos de la estructura open_how son los siguientes:

flags
Este campo especifica las banderas de creación de archivo y estado del archivo que se utilizarán al abrir el archivo. Todas las banderas O_* definidas para openat(2) son valores de bandera válidos para openat2().
Mientras que openat(2) ignora los bits desconocidos en su argumento flags, openat2() devuelve un error si se especifican banderas desconocidas o conflictivas en how.flags.
mode
Este campo especifica el modo para el nuevo archivo, con semántica idéntica al argumento mode de openat(2).
Mientras que openat(2) ignora los bits distintos de los del rango 07777 en su argumento mode, openat2() devuelve un error si how.mode contiene bits distintos de 07777. De manera similar, se devuelve un error si se llama a openat2() con un how.mode distinto de cero y how.flags no contiene O_CREAT u O_TMPFILE.
resolve
Esta es una máscara de bits de banderas que modifican la forma en que se resolverán todos los componentes de path. (Ver path_resolution(7) para información de fondo).
El caso de uso principal de estas banderas es permitir que programas de confianza restrinjan cómo se resuelven rutas no confiables (o rutas dentro de directorios no confiables). La lista completa de banderas resolve es la siguiente:
RESOLVE_BENEATH
No permitir que la resolución de la ruta tenga éxito si algún componente de la resolución no es un descendiente del directorio indicado por dirfd. Esto rechaza enlaces simbólicos absolutos (y valores absolutos de path).
Actualmente, esta bandera también deshabilita la resolución de enlaces mágicos (ver más abajo). Sin embargo, esto puede cambiar en el futuro. Por lo tanto, para asegurar que los enlaces mágicos no se resuelvan, el llamador debe especificar explícitamente RESOLVE_NO_MAGICLINKS.
RESOLVE_IN_ROOT
Tratar el directorio al que se refiere dirfd como el directorio raíz mientras se resuelve path. Los enlaces simbólicos absolutos se interpretan en relación con dirfd. Si un componente de prefijo de path es igual a dirfd, entonces un componente de .. inmediatamente siguiente también es igual a dirfd (así como /.. es tradicionalmente equivalente a /). Si path es absoluto, también se interpreta en relación con dirfd.
El efecto de esta bandera es como si el proceso que llama hubiera usado chroot(2) para modificar (temporalmente) su directorio raíz (al directorio al que se refiere dirfd). Sin embargo, a diferencia de chroot(2) (que cambia la raíz del sistema de archivos permanentemente para un proceso), RESOLVE_IN_ROOT permite a un programa restringir eficientemente la resolución de rutas por apertura.
Actualmente, esta bandera también deshabilita la resolución de enlaces mágicos. Sin embargo, esto puede cambiar en el futuro. Por lo tanto, para asegurar que los enlaces mágicos no se resuelvan, el llamador debe especificar explícitamente RESOLVE_NO_MAGICLINKS.
RESOLVE_NO_MAGICLINKS
No permitir la resolución de enlaces mágicos durante la resolución de rutas.
Los enlaces mágicos son objetos similares a enlaces simbólicos que se encuentran principalmente en proc(5); los ejemplos incluyen /proc/pid/exe y /proc/pid/fd/*. (Ver symlink(7) para más detalles).
Abrir enlaces mágicos sin saberlo puede ser arriesgado para algunas aplicaciones. Ejemplos de tales riesgos incluyen los siguientes:
•
Si el proceso que abre un nombre de ruta es un proceso de control que actualmente no tiene una terminal de control (ver credentials(7)), entonces abrir un enlace mágico dentro de /proc/pid/fd que resulte referirse a una terminal haría que el proceso adquiera una terminal de control.
•
En un entorno contenedorizado, un enlace mágico dentro de /proc puede referirse a un objeto fuera del contenedor y, por lo tanto, puede proporcionar un medio para escapar del contenedor.
Debido a tales riesgos, una aplicación puede preferir deshabilitar la resolución de enlaces mágicos utilizando la bandera RESOLVE_NO_MAGICLINKS.
Si el componente final (es decir, el nombre base) de path es un enlace mágico, how.resolve contiene RESOLVE_NO_MAGICLINKS y how.flags contiene tanto O_PATH como O_NOFOLLOW, se devolverá un descriptor de archivo O_PATH que hace referencia al enlace mágico.
RESOLVE_NO_SYMLINKS
No permitir la resolución de enlaces simbólicos durante la resolución de rutas. Esta opción implica RESOLVE_NO_MAGICLINKS.
Si el componente final (es decir, el nombre base) de path es un enlace simbólico, how.resolve contiene RESOLVE_NO_SYMLINKS y how.flags contiene tanto O_PATH como O_NOFOLLOW, se devolverá un descriptor de archivo O_PATH que hace referencia al enlace simbólico.
Tenga en cuenta que el efecto ect of the RESOLVE_NO_SYMLINKS flag, which affects the treatment of symbolic links in all of the components of path, differs from the effect of the O_NOFOLLOW file creation flag (in how.flags), which affects the handling of symbolic links only in the final component of path.
Applications that employ the RESOLVE_NO_SYMLINKS flag are encouraged to make its use configurable (unless it is used for a specific security purpose), as symbolic links are very widely used by end-users. Setting this flag indiscriminately—i.e., for purposes not specifically related to security—for all uses of openat2() may result in spurious errors on previously functional systems. This may occur if, for example, a system pathname that is used by an application is modified (e.g., in a new distribution release) so that a pathname component (now) contains a symbolic link.
RESOLVE_NO_XDEV
Disallow traversal of mount points during path resolution (including all bind mounts). Consequently, path must either be on the same mount as the directory referred to by dirfd, or on the same mount as the current working directory if dirfd is specified as AT_FDCWD.
Applications that employ the RESOLVE_NO_XDEV flag are encouraged to make its use configurable (unless it is used for a specific security purpose), as bind mounts are widely used by end-users. Setting this flag indiscriminately—i.e., for purposes not specifically related to security—for all uses of openat2() may result in spurious errors on previously functional systems. This may occur if, for example, a system pathname that is used by an application is modified (e.g., in a new distribution release) so that a pathname component (now) contains a bind mount.
RESOLVE_CACHED (desde Linux 5.12)
Hacer que la operación de apertura falle a menos que todos los componentes de la ruta ya estén presentes en la caché de búsqueda del kernel. Si se necesita algún tipo de revalidación o E/S para satisfacer la búsqueda, openat2() falla con el error EAGAIN. Esto es útil para proporcionar una apertura de ruta rápida que se puede realizar sin recurrir a la descarga de hilos u otros mecanismos que una aplicación podría usar para descargar operaciones más lentas.
Si se establecen bits distintos de los enumerados anteriormente en how.resolve, se devuelve un error.

VALOR DE RETORNO

En caso de éxito, se devuelve un nuevo descriptor de archivo. En caso de error, se devuelve -1 y se establece errno para indicar el error.

ERRORES

El conjunto de errores devueltos por openat2() incluye todos los errores devueltos por openat(2), así como los siguientes errores adicionales:

E2BIG
Se especificó una extensión que este kernel no soporta en how. (Ver la sección "Extensibilidad" de NOTAS para más detalles sobre cómo se manejan las extensiones).
EAGAIN
how.resolve contiene RESOLVE_IN_ROOT o RESOLVE_BENEATH, y el kernel no pudo asegurar que un componente ".." no escapara (debido a una condición de carrera o un ataque potencial). El llamador puede optar por reintentar la llamada a openat2().
EAGAIN
Se estableció RESOLVE_CACHED, y la operación de apertura no se puede realizar utilizando solo información en caché. El llamador debe reintentar sin RESOLVE_CACHED establecido en how.resolve.
EINVAL
Se especificó una bandera desconocida o un valor inválido en how.
EINVAL
mode no es cero, pero how.flags no contiene O_CREAT o O_TMPFILE.
EINVAL
size fue menor que cualquier versión conocida de struct open_how.
ELOOP
how.resolve contiene RESOLVE_NO_SYMLINKS, y uno de los componentes de la ruta era un enlace simbólico (o enlace mágico).
ELOOP
how.resolve contiene RESOLVE_NO_MAGICLINKS, y uno de los componentes de la ruta era un enlace mágico.
EXDEV
how.resolve contiene RESOLVE_IN_ROOT o RESOLVE_BENEATH, y se detectó un escape de la raíz durante la resolución de la ruta.
EXDEV
how.resolve contiene RESOLVE_NO_XDEV, y un componente de la ruta cruza un punto de montaje.

ESTANDARES

Linux.

HISTORIA

Linux 5.6.

La semántica de RESOLVE_BENEATH se modeló a partir de O_BENEATH de FreeBSD, pero evitó un error de corrección bien conocido en la implementación de FreeBSD que lo hacía efectivamente inseguro. Más tarde, FreeBSD 13 introdujo O_RESOLVE_BENEATH para reemplazar el inseguro O_BENEATH. La semántica de O_RESOLVE_BENEATH de FreeBSD se basa en RESOLVE_BENEATH de Linux y ambas son ahora funcionalmente equivalentes.

NOTAS

Extensibilidad

Para permitir la extensibilidad futura, openat2() requiere que la aplicación de espacio de usuario especifique el tamaño de la estructura open_how que está pasando. Al proporcionar esta información, es posible que openat2() proporcione compatibilidad hacia adelante y hacia atrás, con size actuando como un número de versión implícito. (Debido a que los nuevos campos de extensión siempre se agregarán, el tamaño de la estructura siempre aumentará). Este diseño de extensibilidad es muy similar a otras llamadas al sistema como sched_setattr(2), perf_event_open(2) y clone3(2).

Si dejamos que usize sea el tamaño de la estructura según lo especificado por la aplicación de espacio de usuario, y ksize sea el tamaño de la estructura que soporta el kernel, entonces hay tres casos a considerar:

•
Si ksize es igual a usize, entonces no hay discrepancia de versión y how se puede usar tal cual.
•
Si ksize es mayor que usize, entonces hay algunos campos de extensión que el kernel soporta y de los que la aplicación de espacio de usuario no es consciente. Dado que un valor cero en cualquier campo de extensión agregado significa una operación nula, el kernel trata todos los campos de extensión no proporcionados por la aplicación de espacio de usuario como si tuvieran valores cero. Esto proporciona compatibilidad hacia atrás.
•
Si ksize es menor que usize, entonces hay algunos campos de extensión que la aplicación de espacio de usuario conoce pero que el kernel no soporta. Dado que cualquier campo de extensión debe tener sus valores cero significando una operación nula, el kernel puede ignorar de forma segura los campos de extensión no soportados si son todos ceros. Si algún campo de extensión no soportado es distinto de cero, se devuelve -1 y se establece errno en E2BIG. Esto proporciona compatibilidad hacia adelante.

Dado que la definición de struct open_how puede cambiar en el futuro (con la adición de nuevos campos al actualizar las cabeceras del sistema), las aplicaciones de espacio de usuario deben poner a cero la estructura struct open_how para garantizar que la recompilación del programa con cabeceras nuevas no resulte en errores espurios en tiempo de ejecución. La forma más sencilla es utilizar un inicializador designado:


struct open_how how = { .flags = O_RDWR,
                        .resolve = RESOLVE_IN_ROOT };

o explícitamente usando memset(3) o similar:


struct open_how how;
memset(&how, 0, sizeof(how));
how.flags = O_RDWR;
how.resolve = RESOLVE_IN_ROOT;

Una aplicación de espacio de usuario que desee determinar qué extensiones soporta el kernel en ejecución puede hacerlo realizando una búsqueda binaria en size con una estructura que tenga cada byte distinto de cero (para encontrar el valor más grande que no produzca un error de E2BIG).

    NOMBRE

    openat2 - abrir un archivo en un directorio especificado por un descriptor de archivo

    SINOPSIS

    #include <fcntl.h>

    int openat2(int dirfd, const char *pathname, const struct open_how *openhow);

    DESCRIPCIÓN

    La llamada al sistema openat2() es una extensión de la llamada al sistema openat(). Permite a un proceso abrir un archivo especificando un descriptor de archivo para un directorio (dirfd) y un nombre de archivo (pathname), de forma similar a openat(). Sin embargo, openat2() utiliza una estructura struct open_how para pasar los flags de apertura y otros parámetros, en lugar de un argumento flags de tipo entero y un argumento mode de tipo mode_t.

    La estructura struct open_how se define en <fcntl.h> como:

    struct open_how {
                    uint64_t flags;          /* Flags de apertura */
                    uint64_t mode;           /* Modo de permisos (si se crea el archivo) */
                    uint64_t mask;           /* Máscara para el modo de permisos (si se crea el archivo) */
                };

    Los campos de la estructura open_how son:

    • flags: Este campo contiene los flags de apertura, que son similares a los utilizados con la llamada al sistema open() y openat() (por ejemplo, O_RDONLY, O_WRONLY, O_RDWR, O_CREAT, O_TRUNC, O_APPEND, etc.). Consulte la página del manual open(2) para una lista completa de los flags.
    • mode: Si el flag O_CREAT está presente en flags, este campo especifica el modo de permisos para el nuevo archivo. Este valor se aplica después de que se aplica la umask del proceso.
    • mask: Este campo se utiliza para especificar una máscara de bits que se aplicará al campo mode antes de que este último se utilice para crear el archivo. Esto permite un control más granular sobre los permisos, especialmente en sistemas donde la umask no es suficiente.

    El argumento pathname puede ser una ruta absoluta o una ruta relativa al directorio representado por el descriptor de archivo dirfd. Si dirfd es AT_FDCWD, pathname se interpreta como una ruta absoluta o relativa al directorio de trabajo actual.

    openat2() proporciona una forma más flexible y extensible de abrir archivos en comparación con openat(), ya que permite añadir nuevos flags o parámetros en el futuro sin romper la compatibilidad con las versiones anteriores de la interfaz.

    VALOR DE RETORNO

    Al éxito, openat2() devuelve un nuevo descriptor de archivo no negativo que se refiere al archivo abierto. Al fallo, devuelve -1 y establece errno para indicar el error.

    ERRORES

    Los posibles errores son los mismos que para openat(2), además de los relacionados con la estructura open_how si esta no es válida o contiene combinaciones de flags no permitidas.

    ESTÁNDARES

    openat2() es una extensión de Linux y no está estandarizada por POSIX.

    HISTORIA

    openat2() apareció por primera vez en el kernel de Linux 5.6.

    NOTAS

    Al igual que con openat(), el uso de openat2() con un dirfd válido puede ser más seguro que el uso de open() con rutas absolutas o relativas, ya que evita ciertas condiciones de carrera.

    La estructura struct open_how permite una mayor flexibilidad que los flags pasados directamente a open() o openat(). Esto es particularmente útil para opciones de seguridad avanzadas o configuraciones específicas del sistema de archivos.
