NOMBRE

openssl-quic - OpenSSL QUIC

DESCRIPCIÓN

OpenSSL 3.2 y versiones posteriores incluyen soporte para el protocolo de transporte QUIC. Puede utilizar las capacidades QUIC de OpenSSL tanto para aplicaciones cliente como servidor. Esta página del manual describe cómo permitir que las aplicaciones utilicen el protocolo QUIC utilizando la API de libssl.

El protocolo QUIC se mapea a la API SSL estándar. Una conexión QUIC se representa mediante un objeto SSL de la misma manera que una conexión TLS. Solo se necesitan cambios mínimos en las aplicaciones existentes que utilizan la API de libssl para incorporar el soporte del protocolo QUIC. Los clientes QUIC pueden usar OSSL_QUIC_client_method(3) o OSSL_QUIC_client_thread_method(3) con SSL_CTX_new(3). Consulte a continuación para obtener más detalles sobre la diferencia entre los dos. Para los servidores, solo hay una opción: el método SSL OSSL_QUIC_server_method(3) con SSL_CTX_new(3).

El resto de esta página del manual discute, en orden:

  • Modo de transmisión predeterminado versus modo multransmisión para clientes;
  • Los cambios en las APIs existentes de libssl que son impulsados por los requisitos de implementación relacionados con QUIC, que las aplicaciones existentes deben tener en cuenta;
  • Aspectos que deben ser considerados por las aplicaciones existentes al adoptar QUIC, incluyendo posibles cambios que puedan ser necesarios.
  • Enfoques de uso recomendados para nuevas aplicaciones.
  • Nuevas APIs específicas de QUIC.

MODOS DE OPERACIÓN DEL CLIENTE

Cuando un cliente crea una conexión QUIC, por defecto, opera en modo de transmisión predeterminada, que está diseñado para proporcionar compatibilidad con los patrones de uso de aplicaciones existentes que no son QUIC. En este modo, la conexión tiene una única transmisión asociada a ella. Las llamadas a SSL_read(3) y SSL_write(3) en el objeto SSL de la conexión QUIC leen y escriben desde esa transmisión. Si la transmisión es iniciada por el cliente o por el servidor desde la perspectiva de QUIC depende de si se llama primero a SSL_read(3) o SSL_write(3).

El modo de transmisión predeterminada está diseñado principalmente para la compatibilidad con aplicaciones existentes. Para nuevas aplicaciones que utilizan QUIC, se recomienda deshabilitar este modo y adoptar en su lugar la API multransmisión. Consulte la sección RECOMENDACIONES PARA NUEVAS APLICACIONES para obtener más detalles.

Modo de Transmisión Predeterminada

Una conexión cliente QUIC puede usarse en modo de transmisión predeterminada o en modo multransmisión. Por defecto, un objeto SSL de conexión QUIC recién creado utiliza el modo de transmisión predeterminada.

En el modo de transmisión predeterminada, se crea implícitamente una transmisión y se vincula al objeto SSL de la conexión QUIC; las llamadas a SSL_read(3) y SSL_write(3) en el objeto SSL de la conexión QUIC funcionan por defecto y se mapean a esa transmisión.

Cuando se utiliza el modo de transmisión predeterminada, cualquier función de API que se pueda llamar en un objeto SSL de transmisión QUIC también se puede llamar en un objeto SSL de conexión QUIC, en cuyo caso afecta a la transmisión predeterminada vinculada a la conexión.

La identidad de una transmisión QUIC, incluido su ID de transmisión, varía según si la transmisión es iniciada por el cliente o por el servidor. En el modo de transmisión predeterminada, si una aplicación cliente llama primero a SSL_read(3) antes de cualquier llamada a SSL_write(3) en la conexión, se asume que el protocolo de la aplicación está utilizando una transmisión iniciada por el servidor, y la llamada a SSL_read(3) no se completará (ya sea bloqueando o fallando apropiadamente si el modo no bloqueante está configurado) hasta que el servidor inicie una transmisión. Por el contrario, si la aplicación cliente llama a SSL_write(3) antes de cualquier llamada a SSL_read(3) en la conexión, se asume que se utilizará una transmisión iniciada por el cliente y se creará automáticamente dicha transmisión.

El modo de transmisión predeterminada está diseñado para ayudar a la compatibilidad con aplicaciones heredadas. Las nuevas aplicaciones que adopten QUIC deben usar el modo multransmisión, descrito a continuación, y evitar el uso de la funcionalidad de transmisión predeterminada.

Es posible utilizar transmisiones adicionales en el modo de transmisión predeterminada utilizando SSL_new_stream(3) y SSL_accept_stream(3); tenga en cuenta que la política de transmisión entrante predeterminada deberá cambiarse usando SSL_set_incoming_stream_policy(3) para poder usar SSL_accept_stream(3) en este caso. Sin embargo, se recomienda encarecidamente a las aplicaciones que utilizan transmisiones adicionales que utilicen el modo multransmisión en su lugar.

Llamar a SSL_new_stream(3) o SSL_accept_stream(3) antes de que se haya asociado una transmisión predeterminada al objeto SSL de la conexión QUIC, impedirá la creación futura de una transmisión predeterminada.

Modo Multransmisión

El modo de uso recomendado para nuevas aplicaciones que adoptan QUIC es el modo multransmisión, en el que no hay ninguna transmisión predeterminada asociada al objeto SSL de la conexión QUIC y los intentos de llamar a SSL_read(3) y SSL_write(3) en el objeto SSL de la conexión QUIC fallan. En su lugar, una aplicación llama a SSL_new_stream(3) o SSL_accept_stream(3) para crear objetos SSL de transmisión individuales para enviar y recibir datos de la aplicación utilizando SSL_read(3) y SSL_write(3).

Para usar el modo multransmisión, llame a SSL_set_default_stream_mode(3) con un argumento de SSL_DEFAULT_STREAM_MODE_NONE; esta función debe llamarse antes de iniciar la conexión. El modo de transmisión predeterminado no se puede cambiar después de iniciar una conexión.

Cuando se utiliza el modo multransmisión, lo que significa que no hay ninguna transmisión predeterminada asociada a la conexión, las llamadas a funciones de API definidas para operar en una transmisión QUIC fallan si se llaman en el objeto SSL de la conexión QUIC. Por ejemplo, llamadas como SSL_write(3) o SSL_get_stream_id(3) fallarán.

CAMBIOS A LAS APIS EXISTENTES

La mayoría de las API SSL, como SSL_read(3) y SSL_write(3), funcionan como lo hacen para las conexiones TLS y no tienen semántica modificada, con algunas excepciones. Los cambios en la semántica de las API existentes son los siguientes:

•
Dado que QUIC usa UDP, SSL_set_bio(3), SSL_set0_rbio(3) y SSL_set0_wbio(3) funcionan como antes, pero ahora deben recibir un BIO con semántica de datagrama. Hay cuatro opciones generales para que las aplicaciones las usen como BIO de red:
  • BIO_s_datagram(3), recomendado para la mayoría de las aplicaciones, reemplaza a BIO_s_socket(3) y proporciona un socket UDP.
  • BIO_s_dgram_pair(3) proporciona una funcionalidad similar a un par de BIO pero con semántica de datagrama, y se recomienda para aplicaciones existentes que utilizan un par de BIO o un BIO de memoria para gestionar la comunicación de libssl con la red.
  • BIO_s_dgram_mem(3) proporciona una interfaz simple similar a un BIO de memoria pero con semántica de datagrama. A diferencia de BIO_s_dgram_pair(3), es unidireccional.
  • Una aplicación también puede optar por implementar un BIO personalizado. Las nuevas API BIO_sendmmsg(3) y BIO_recvmmsg(3) deben ser soportadas.
  • SSL_set_fd(3), SSL_set_rfd(3) y SSL_set_wfd(3) instancian tradicionalmente un BIO_s_socket(3). Para QUIC, estas funciones instancian en su lugar un BIO_s_datagram(3). Esto es equivalente

NOTES ON USING LIBSSL WITH QUIC

The following are notes on using libssl with QUIC:

  • The SSL_set_cert_cb(3) API is used to set a callback that will be invoked when the server needs to provide a certificate. This callback should return a certificate that is compatible with the peer's certificate identification. For more details on how certificate callbacks work, see the description of the SSL_CTX_set_cert_cb(3) function.
  • The SSL_set_server_hello_cb(3) API is used to set a callback that will be invoked when the server needs to send its ServerHello message. This callback should provide the server's chosen cipher suite and other relevant information.
  • The SSL_set_signature_algorithms(3) API has been extended to support QUIC. You can now specify the signature algorithms that the server is willing to use for the QUIC handshake.
  • The underlying network I/O must be performed using datagrams. This means that any BIO passed to the SSL object must have datagram semantics. The BIO_s_datagram(3) BIO is suitable for this purpose. You may need to modify your application to use this BIO instead of a socket BIO. This involves instantiating a BIO_s_datagram(3) and using SSL_set0_rbio(3) and SSL_set0_wbio(3).
  • Traditionally, whether the application-level I/O APIs (such as SSL_read(3) and SSL_write(3) operated in a blocking fashion was directly correlated with whether the underlying network socket was configured in a blocking fashion. This is no longer the case; applications must explicitly configure the desired application-level blocking mode using SSL_set_blocking_mode(3). See SSL_set_blocking_mode(3) for details.
  • Network-level I/O must always be performed in a nonblocking manner. The application can still enjoy blocking semantics for calls to application-level I/O functions such as SSL_read(3) and SSL_write(3), but the underlying network BIO provided to QUIC (such as a BIO_s_datagram(3)) must be configured in nonblocking mode. For application-level blocking functionality, see SSL_set_blocking_mode(3).
  • BIO_new_ssl_connect(3) has been changed to automatically use a BIO_s_datagram(3) when used with QUIC, therefore applications which use this do not need to change the BIO they use.
  • BIO_new_buffer_ssl_connect(3) cannot be used with QUIC and applications must change to use BIO_new_ssl_connect(3) instead.
  • SSL_shutdown(3) has significant changes in relation to how QUIC connections must be shut down. In particular, applications should be advised that the full RFC-conformant QUIC shutdown process may take an extended amount of time. This may not be suitable for short-lived processes which should exit immediately after their usage of a QUIC connection is completed. A rapid shutdown mode is available for such applications. For details, see SSL_shutdown(3).
  • SSL_want(3), SSL_want_read(3) and SSL_want_write(3) no longer reflect the I/O state of the network BIO passed to the QUIC SSL object, but instead reflect the flow control state of the QUIC stream associated with the SSL object.

    When used in nonblocking mode, SSL_ERROR_WANT_READ indicates that the receive part of a QUIC stream does not currently have any more data available to be read, and SSL_ERROR_WANT_WRITE indicates that the stream's internal buffer is full.

    To determine if the QUIC implementation currently wishes to be informed of incoming network datagrams, use the new function SSL_net_read_desired(3); likewise, to determine if the QUIC implementation currently wishes to be informed when it is possible to transmit network datagrams, use the new function SSL_net_write_desired(3). Only applications which wish to manage their own event loops need to use these functions; see APPLICATION-DRIVEN EVENT LOOPS for further discussion.

  • The use of ALPN is mandatory when using QUIC. Attempts to connect without configuring ALPN will fail. For information on how to configure ALPN, see SSL_set_alpn_protos(3).
  • Whether QUIC operates in a client or server mode is determined by the SSL_METHOD used, rather than by calls to SSL_set_connect_state(3) or SSL_set_accept_state(3). It is not necessary to call either of SSL_set_connect_state(3) or SSL_set_accept_state(3) before connecting, but if either of these are called, the function called must be congruent with the SSL_METHOD being used.
  • The SSL_set_min_proto_version(3) and SSL_set_max_proto_version(3) APIs are not used and the values passed to them are ignored, as OpenSSL QUIC currently always uses TLS 1.3.
  • The following libssl functionality is not available when used with QUIC.
  • Async functionality
  • SSL_MODE_AUTO_RETRY
  • Record Padding and Fragmentation (SSL_set_block_padding(3), etc.)
  • SSL_stateless(3) support
  • SRTP functionality
  • TLSv1.3 Early Data
  • TLS Next Protocol Negotiation cannot be used and is superseded by ALPN, which must be used instead. The use of ALPN is mandatory with QUIC.
  • Post-Handshake Client Authentication is not available as QUIC prohibits its use.
  • QUIC requires the use of TLSv1.3 or later, therefore functionality only relevant to older TLS versions is not available.
  • Some cipher suites which are generally available for TLSv1.3 are not available for QUIC, such as TLS_AES_128_CCM_8_SHA256. Your application may need to adjust the list of acceptable cipher suites it passes to libssl.
  • CCM mode is not currently supported.

The following libssl functionality is also not available when used with QUIC, but calls to the relevant functions are treated as no-ops:

•
Readahead (SSL_set_read_ahead(3), etc.)

CONSIDERATIONS FOR EXISTING APPLICATIONS

Existing applications seeking to adopt QUIC should apply the following list to determine what changes they will need to make:

  • A client application wishing to use QUIC must use OSSL_QUIC_client_method(3) or OSSL_QUIC_client_thread_method(3) as its SSL method. For more information on the differences between these two methods, see THREAD ASSISTED MODE.
  • A server application wishing to use QUIC must use OSSL_QUIC_server_method(3). The server can then accept new connections with SSL_accept_connection(3).
  • Determine how to provide QUIC with network access. Determine which of the below apply for your application:
  • Your application uses BIO_s_socket(3) to construct a BIO which is passed to the SSL object to provide it with network access.

    Changes needed: Change your application to use BIO_s_datagram(3) instead when using QUIC. The socket must be configured in nonblocking mode. You may or may not need to use SSL_set1_initial_peer_addr(3) to set the initial peer address; see the QUIC-SPECIFIC APIS section for details.

  • Your application uses BIO_new_ssl_connect(3) to construct a BIO which is passed to the SSL object to provide it with network access.

    Changes needed: No changes needed. Use of QUIC is detected automatically and a datagram socket is created instead of a normal TCP socket.

  • Your application uses any other I/O strategy in this list but combines it with a BIO_f_buffer(3), for example using BIO_push(3).

    Changes needed: Disable the usage of BIO_f_buffer(3) when using QUIC. Usage of such a buffer is incompatible with QUIC as QUIC requires datagram semantics in its interaction with the network.

  • Your application uses a BIO pair to cause the SSL object to read and write network traffic to a memory buffer. Your application manages the transmission and reception of buffered data itself in a way unknown to libssl.

    Changes needed: Switch from using a conventional BIO pair to using BIO_s_dgram_pair(3) instead, which has the necessary datagram semantics. You will need to modify your application to transmit and receive using a UDP socket and to use datagram semantics when interacting with the BIO_s_dgram_pair(3) instance.

  • Your application uses a custom BIO method to provide the SSL object with network access.

    Changes needed: The custom BIO must be re-architected to have datagram semantics. BIO_sendmmsg(3) and BIO_recvmmsg(3) must be implemented. These calls must operate in a nonblocking fashion. Optionally, implement the BIO_get_rpoll_descriptor(3) and BIO_get_wpoll_descriptor(3) methods if desired. Implementing these methods is required if blocking semantics at the SSL API level are desired.

  • An application must explicitly configure whether it wishes to use the SSL APIs in blocking mode or not. Traditionally, an SSL object has automatically operated in blocking or nonblocking mode based on whether the underlying network BIO operates in blocking or nonblocking mode. QUIC requires the use of a nonblocking network BIO, therefore the blocking mode at the application level can be explicitly configured by the application using the new SSL_set_blocking_mode(3) API. The default mode is blocking. If an application wishes to use the SSL object APIs at application level in a nonblocking manner, it must add a call to SSL_set_blocking_mode(3) to disable blocking mode.
  • If your client application does not choose to use thread assisted mode, it must ensure that it calls an I/O function on the SSL object (for example, SSL_read(3) or SSL_write(3)), or the new function SSL_handle_events(3), regularly. If the SSL object is used in blocking mode, an ongoing blocking call to an I/O function satisfies this requirement. This is required to ensure that timer events required by QUIC are handled in a timely fashion.

    If the SSL object is used in nonblocking mode, then the application must explicitly call SSL_handle_events(3). It is recommended that an application calls this function whenever the underlying network BIO indicates that it is possible to read or write data.

  • La mayoría de las aplicaciones utilizarán el objeto SSL llamando regularmente a SSL_read(3) o SSL_write(3). Si una aplicación no lo hace, debe asegurarse de que SSL_handle_events(3) se llame regularmente.
  • Se puede utilizar SSL_get_event_timeout(3) para determinar cuándo debe llamarse a SSL_handle_events(3).
  • Si el objeto SSL se está utilizando con un BIO de red subyacente que se puede sondear (como BIO_s_datagram(3)), la aplicación puede usar SSL_get_rpoll_descriptor(3), SSL_get_wpoll_descriptor(3) para obtener recursos que se pueden utilizar para determinar cuándo se debe llamar a SSL_handle_events(3) debido a E/S de red.
  • Las aplicaciones cliente que utilizan el modo asistido por hilos no deben preocuparse por este requisito, ya que la implementación QUIC garantiza que los eventos de tiempo de espera se manejen de manera oportuna. Consulte MODO ASISTIDO POR HILOS para obtener más detalles.
  • Asegúrese de que su uso de SSL_want(3), SSL_want_read(3) y SSL_want_write(3) refleje los cambios en la API descritos en CAMBIOS EN LAS API EXISTENTES. En particular, debe utilizar estas API para determinar la capacidad de un flujo QUIC para recibir o proporcionar datos de aplicación, no para determinar si se requiere E/S de red.
  • Evalúe el uso de SSL_shutdown(3) de su aplicación a la luz de los cambios discutidos en CAMBIOS EN LAS API EXISTENTES. Dependiendo de si su aplicación desea priorizar la conformidad con RFC o un cierre rápido, considere usar la nueva API SSL_shutdown_ex(3) en su lugar. Consulte API ESPECÍFICAS DE QUIC para obtener más detalles.

USO RECOMENDADO EN NUEVAS APLICACIONES

El uso recomendado en nuevas aplicaciones varía según tres decisiones de diseño independientes:

  • Si la aplicación utilizará E/S bloqueante o no bloqueante a nivel de aplicación (configurado mediante SSL_set_blocking_mode(3)).

    Si la aplicación realiza E/S no bloqueante a nivel de aplicación, puede optar por gestionar su propio sondeo y bucle de eventos; consulte BUCLES IMPULSADOS POR LA APLICACIÓN.

  • Si la aplicación tiene la intención de dar a la implementación QUIC acceso directo a un socket de red (por ejemplo, a través de BIO_s_datagram(3)) o si tiene la intención de almacenar en búfer datagramas transmitidos y recibidos a través de un BIO_s_dgram_pair(3) o un BIO personalizado.

    Se prefiere lo primero siempre que sea posible, ya que reduce la latencia a la red, lo que permite a QUIC lograr un mayor rendimiento y una estimación más precisa del tiempo de ida y vuelta (RTT) de la conexión.

  • Si se utilizará el modo asistido por hilos (consulte MODO ASISTIDO POR HILOS).

Las demostraciones sencillas para el uso de QUIC en estos diversos escenarios se pueden encontrar en https://github.com/openssl/openssl/tree/master/doc/designs/ddd.

Las aplicaciones que deseen implementar protocolos específicos de QUIC deben tener en cuenta las API enumeradas en API ESPECÍFICAS DE QUIC, que proporcionan acceso a la funcionalidad específica de QUIC. Por ejemplo, SSL_stream_conclude(3) se puede utilizar para indicar el final de la parte de envío de un flujo, y SSL_shutdown_ex(3) se puede utilizar para proporcionar un código de error de aplicación QUIC al cerrar una conexión.

Independientemente de las decisiones de diseño elegidas anteriormente, se recomienda que las nuevas aplicaciones eviten el uso del modo de flujo predeterminado y utilicen la API multi-flujo llamando a SSL_set_default_stream_mode(3); consulte la sección MODOS DE OPERACIÓN para obtener más detalles.

API ESPECÍFICAS DE QUIC

Esta sección detalla las nuevas API que están directa o indirectamente relacionadas con QUIC. Para obtener detalles sobre el funcionamiento de cada API, consulte las páginas man referenciadas.

Las siguientes API SSL son nuevas pero relevantes tanto para QUIC como para DTLS:

SSL_get_event_timeout(3)
Determina cuándo se debe despertar la implementación QUIC la próxima vez a través de una llamada a SSL_handle_events(3) (o otra función de E/S como SSL_read(3) o SSL_write(3)), si es que alguna vez.

Esto también se puede usar con DTLS y reemplaza DTLSv1_get_timeout(3) para uso nuevo.

SSL_handle_events(3)
Esta es una operación de E/S no específica que intenta hacer un mejor esfuerzo para realizar cualquier E/S pendiente o procesamiento de tiempo de espera. Se puede utilizar para avanzar la máquina de estados QUIC al procesar tráfico de red entrante, generar tráfico de red saliente y manejar cualquier evento de tiempo de espera expirado. La mayoría de las otras funciones de E/S en un objeto SSL, como SSL_read(3) y SSL_write(3), realizan implícitamente el manejo de eventos en el objeto SSL, por lo que llamar a esta función solo es necesario si no se va a llamar a ninguna otra función de E/S.

Esto también se puede usar con DTLS y reemplaza DTLSv1_handle_timeout(3) para uso nuevo.

Las siguientes API SSL son específicas de QUIC:

SSL_new_listener(3)
Crea un objeto SSL de escucha, que difiere de un objeto SSL ordinario en que se utiliza para proporcionar una abstracción para la aceptación de conexiones de red de manera independiente del protocolo.

Actualmente, los objetos SSL de escucha solo se admiten para uso de servidor QUIC o uso exclusivo de cliente. La interfaz de escucha puede expandirse para admitir protocolos adicionales en el futuro.

SSL_new_listener_from(3)
Crea un objeto SSL de escucha que está subordinado a un objeto SSL de dominio QUIC ssl. Consulte SSL_new_domain(3) y openssl-quic-concurrency(7) para obtener detalles sobre los objetos SSL de dominio QUIC.
SSL_is_listener(3)
Devuelve 1 si y solo si un objeto SSL es un objeto SSL de escucha.
SSL_get0_listener(3)
Devuelve un puntero a un objeto SSL (potencialmente al mismo objeto en el que se llama) o NULL.
SSL_listen(3)
Comienza a escuchar después de que se ha creado un objeto de escucha. Normalmente, no es necesario llamar a esto porque se llamará automáticamente en la primera llamada a SSL_accept_connection(3).
SSL_accept_connection(3)
Acepta una nueva conexión entrante para un objeto SSL de escucha. Se crea un nuevo objeto SSL que representa la conexión aceptada y se devuelve en caso de éxito. Si no hay ninguna conexión entrante disponible y el objeto SSL de escucha está configurado en modo no bloqueante, se devuelve NULL.
SSL_get_accept_connection_queue_len(3)
Devuelve un valor informativo que enumera el número de conexiones que esperan ser extraídas de la cola mediante llamadas a SSL_accept_connection().
SSL_new_from_listener(3)
Crea una conexión de cliente bajo un objeto SSL de escucha determinado. Para QUIC, también es posible utilizar SSL_new_from_listener() en conjunción con un objeto de escucha que acepte conexiones entrantes (es decir, que no se creó utilizando SSL_LISTENER_FLAG_NO_ACCEPT), lo que da lugar a un punto final de red UDP que tiene tanto conexiones entrantes como salientes.
SSL_new_domain(3)
Crea un nuevo dominio de eventos QUIC, representado como un objeto SSL. Esto se conoce como un objeto SSL de dominio QUIC. El concepto de un dominio de eventos QUIC se discute en detalle en openssl-quic-concurrency(7).
SSL_is_domain(3)
Devuelve 1 si un objeto SSL es un objeto SSL de dominio QUIC.
SSL_get0_domain(3)
SSL_get0_domain() obtiene un puntero al objeto SSL de dominio QUIC en una jerarquía de objetos SSL (si la hay).
SSL_set_blocking_mode(3), SSL_get_blocking_mode(3)
Configura si se utilizan semánticas de bloqueo a nivel de aplicación. Esto determina si las llamadas a funciones como SSL_read(3) y SSL_write(3) se bloquearán.
SSL_get_rpoll_descriptor(3), SSL_get_wpoll_descriptor(3)
Estas funciones facilitan la operación en modo no bloqueante.

LOS_BUCLES_DE_EVENTOS_IMPULSADOS_POR_LA_APLICACIÓN

La implementación QUIC de OpenSSL está diseñada para facilitar aplicaciones que deseen usar las API de SSL de forma bloqueante, pero también está diseñada para facilitar aplicaciones que deseen usar las API de SSL de forma no bloqueante y gestionar sus propios bucles de eventos y sondeos directamente. Esto es útil cuando es deseable alojar la implementación QUIC de OpenSSL sobre la infraestructura de E/S no bloqueante existente de una aplicación.

Esto se admite a través del concepto de descriptores de sondeo; consulte BIO_get_rpoll_descriptor(3) para obtener más detalles. En general, un BIO_POLL_DESCRIPTOR es una estructura que expresa algún tipo de recurso del sistema operativo que puede utilizarse para sincronizar eventos de E/S. La implementación QUIC proporciona un BIO_POLL_DESCRIPTOR basado en el descriptor de sondeo proporcionado por el BIO de red subyacente. Típicamente, es un manejador de socket del sistema operativo, aunque los BIO personalizados podrían optar por implementar su propio formato de descriptor de sondeo personalizado.

En general, una aplicación que desee gestionar su propio bucle de eventos debería interactuar con el objeto SSL de la siguiente manera:

  • Debería proporcionar BIOs de lectura y escritura con semántica de datagramas no bloqueantes al objeto SSL utilizando SSL_set0_rbio(3) y SSL_set0_wbio(3). Esto podría ser un BIO que abstraiga un socket de red como BIO_s_datagram(3), o un BIO que abstraiga algún tipo de búfer de memoria como BIO_s_dgram_pair(3). El uso de un BIO personalizado también es posible.
  • Debería configurar el objeto SSL en modo no bloqueante llamando a SSL_set_blocking_mode(3).
  • Debería configurar el objeto SSL según sea necesario, establecer un par inicial según sea necesario utilizando SSL_set1_initial_peer_addr(3), y activar el proceso de conexión llamando a SSL_connect(3).
  • Si los BIOs de lectura y escritura de red proporcionados eran sondeables (por ejemplo, un BIO_s_datagram(3), o un BIO personalizado que implemente BIO_get_rpoll_descriptor(3) y BIO_get_wpoll_descriptor(3)), debe realizar los siguientes pasos repetidamente:
  • La aplicación debe llamar a SSL_get_rpoll_descriptor(3) y SSL_get_wpoll_descriptor(3) para identificar los recursos del sistema operativo que se pueden utilizar para la sincronización.
  • Debe llamar a SSL_net_read_desired(3) y SSL_net_write_desired(3) para determinar si la implementación QUIC está actualmente interesada en eventos de legibilidad y escriturabilidad en el BIO de red subyacente que se proporcionó, y llamar a SSL_get_event_timeout(3) para determinar si algún evento de tiempo de espera será aplicable en el futuro.
  • Debe esperar hasta que ocurra uno de los siguientes eventos:
  • El descriptor de sondeo devuelto por SSL_get_rpoll_descriptor(3) se vuelve legible (si SSL_net_read_desired(3) devolvió 1);
  • El descriptor de sondeo devuelto por SSL_get_wpoll_descriptor(3) se vuelve escribible (si SSL_net_write_desired(3) devolvió 1);
  • El tiempo de espera devuelto por SSL_get_event_timeout(3) (si existe) expira.

Una vez que ocurra cualquiera de estos eventos, se debe llamar a SSL_handle_events(3).

•
Si los BIOs de lectura y escritura de red proporcionados no eran sondeables (por ejemplo, en el caso de BIO_s_dgram_pair(3)), la aplicación es responsable de gestionar y sincronizar la E/S de red. Debería llamar a SSL_handle_events(3) después de escribir datos en un BIO_s_dgram_pair(3) o tomar otra acción para que la implementación QUIC pueda leer nuevos datagramas mediante una llamada a BIO_recvmmsg(3) en el BIO de red subyacente. La implementación QUIC puede generar datagramas mediante una llamada a BIO_sendmmsg(3) y la aplicación es responsable de garantizar que se transmitan.

La aplicación debe llamar a SSL_get_event_timeout(3) después de cada llamada a SSL_handle_events(3) (o a otra función de E/S en el objeto SSL), y asegurarse de que se realiza una llamada a SSL_handle_events(3) después de que expire el tiempo de espera especificado (si existe).
