NOMBRE

ovs-testcontroller - controlador OpenFlow simple para pruebas

SINOPSIS

ovs-testcontroller [opciones] método [método]...

DESCRIPCIÓN

ovs-testcontroller es un controlador OpenFlow simple que gestiona uno o más switches a través del protocolo OpenFlow, haciéndolos funcionar como switches L2 que aprenden MAC o hubs. Es adecuado para pruebas iniciales de redes OpenFlow. No es una parte necesaria ni deseable de una implementación OpenFlow en producción.

ovs-testcontroller controla uno o más switches OpenFlow, especificados como uno o más de los siguientes métodos de conexión OpenFlow:

pssl:[puerto][:host]

ptcp:[puerto][:host]
Escucha conexiones OpenFlow en el puerto. El puerto por defecto es 6653. Por defecto, se permiten conexiones desde cualquier dirección IPv4. Especifique host como una dirección IPv4 o una dirección IPv6 entre corchetes (ej: ptcp:6653:[::1]). En Linux, use %dispositivo para designar un alcance para direcciones de nivel de enlace IPv6, ej: ptcp:6653:[fe80::1234%eth0]. Se pueden usar nombres DNS si se compiló con la biblioteca unbound. Para pssl, las opciones --private-key, --certificate y --ca-cert son obligatorias.
punix:archivo
Escucha conexiones OpenFlow en el socket de servidor de dominio Unix llamado archivo.
ssl:host[:puerto]

tcp:host[:puerto]
El puerto especificado en el host dado, que puede ser expresado como un nombre DNS (si se compiló con la biblioteca unbound) o una dirección IP en formato IPv4 o IPv6. Encierre las direcciones IPv6 en corchetes, ej: tcp:[::1]:6653. En Linux, use %dispositivo para designar un alcance para direcciones de nivel de enlace IPv6, ej: tcp:[fe80::1234%eth0]:6653. Para ssl, las opciones --private-key, --certificate y --ca-cert son obligatorias.
Si no se especifica puerto, el valor predeterminado es 6653.
unix:archivo
En POSIX, un socket de servidor de dominio Unix llamado archivo.
En Windows, se conecta a una tubería nombrada local que se representa como un archivo creado en la ruta archivo para imitar el comportamiento de un socket de dominio Unix.

OPCIONES

-n

--noflow
Por defecto, ovs-testcontroller configura un flujo en cada switch OpenFlow cuando recibe un paquete cuyo destino se conoce mediante el aprendizaje de MAC. Esta opción deshabilita la configuración de flujos, de modo que cada paquete en la red pasa por el controlador.
Esta opción es muy útil para depuración. Reduce el rendimiento de conmutación, por lo que no debe usarse en producción.
--max-idle=segundos|permanente
Establece segundos como el número de segundos que un flujo configurado por el controlador permanecerá en la tabla de flujos del switch sin que se vean paquetes coincidentes. Si se especifica permanente, lo cual no se recomienda, los flujos nunca expirarán. El valor predeterminado es 60 segundos.
Esta opción no tiene efecto cuando se usa -n (o --noflow) (porque el controlador no configura flujos en ese caso).
-H

--hub
Por defecto, el controlador actúa como un switch L2 que aprende MAC. Esta opción cambia su comportamiento al de un hub que inunda paquetes en todos los puertos excepto en el de entrada.
Si se usan -H (o --hub) y -n (o --noflow) juntos, el efecto acumulativo es que cada paquete pasa por el controlador y cada paquete se inunda.
Esta opción es muy útil para depuración. Reduce el rendimiento de conmutación, por lo que no debe usarse en producción.
-w[máscara_comodín]

--wildcards[=máscara_comodín]
Por defecto, ovs-testcontroller configura flujos de coincidencia exacta. Esta opción le permite configurar flujos comodín, lo que puede reducir la latencia de configuración de flujos al enviar menos tráfico al controlador.
La máscara_comodín opcional es una máscara de bits comodín de OpenFlow en hexadecimal que especifica los campos a comodín. Si no se especifica máscara_comodín, se utiliza el valor predeterminado 0x2820F0, que especifica conmutación solo L2 y comodines en campos L3 y L4. Otro valor interesante es 0x2000EC, que especifica conmutación solo L3 y comodines en campos L2 y L4.
Esta opción no tiene efecto cuando se usa -n (o --noflow) (porque el controlador no configura flujos en ese caso).
-N

--normal
Por defecto, ovs-testcontroller dirige los paquetes a un puerto específico o los inunda. Esta opción hace que dirija los paquetes no inundados al puerto OFPP_NORMAL de OpenFlow. Esto permite que el propio switch tome decisiones sobre los destinos de los paquetes. El soporte para OFPP_NORMAL es opcional en OpenFlow, por lo que esta opción puede no funcionar bien con algunos switches que no sean Open vSwitch.
--mute
Impide que ovs-testcontroller responda a cualquier mensaje OpenFlow enviado por los switches.
Esta opción es solo para depurar la implementación de Open vSwitch del modo ``fail open''. No debe usarse en producción.
-q id

--queue=id
Por defecto, ovs-testcontroller utiliza la cola OpenFlow predeterminada para enviar paquetes y configurar flujos. Use una de estas opciones, suministrando id como un ID de cola OpenFlow en número decimal, para utilizar esa cola específica en su lugar.
Esta opción es incompatible con -N o --normal y con -H o --hub. Si se especifican varias, esta opción tiene precedencia.
Esta opción puede ser útil para probar o depurar configuraciones de calidad de servicio.
-Q nombre-puerto:id-cola
--port-queue nombre-puerto:id-cola
Configura los paquetes recibidos en el puerto llamado nombre-puerto (ej: eth0) para ser enviados a la cola OpenFlow con ID id-cola (especificado como número decimal). Para el puerto especificado, esta opción anula la predeterminada especificada en -q o --queue.
Esta opción puede especificarse cualquier número de veces con diferentes argumentos nombre-puerto.
Esta opción es incompatible con -N o --normal y con -H o --hub. Si se especifican varias, esta opción tiene precedencia.
Esta opción puede ser útil para probar o depurar configuraciones de calidad de servicio.
--with-flows archivo
Cuando un switch se conecta, inserta las entradas de flujo descritas en archivo. Cada línea en archivo es una entrada de flujo en el formato descrito para el comando add-flows en la sección Sintaxis de Flujo de la página del manual ovs-ofctl(8).
Use esta opción más de una vez para agregar flujos de múltiples archivos.

Opciones de Infraestructura de Clave Pública

-p privk

--private-key=privk
Especifica un archivo que contiene un certificado de clave privada para usar con SSL. La cadena privk debe ser la ruta a un archivo PEM.
Si se usa pssl o ssl, esto es obligatorio.
-c cert

--certificate=cert
Especifica un archivo que contiene un certificado X.509 para usar con SSL. La cadena cert debe ser la ruta a un archivo PEM. Si se usa pssl o ssl, esto es obligatorio.
-C peer

--ca-cert=peer
Especifica un archivo que contiene un conjunto de certificados de autoridad de certificación X.509 para verificar los certificados de los pares de conexión SSL. La cadena peer debe ser la ruta a un archivo PEM. Si se usa pssl o ssl, esto es obligatorio.
-h

--help
Muestra un resumen de las opciones de línea de comandos.
-v

--version
Muestra información sobre la versión y sale.

SSL/TLS

-h host.pem

--host-key=host.pem
Specifies a PEM file containing a certificate that certifies the private key specified on -p or --private-key to be trustworthy. The certificate must be signed by the certificate authority (CA) that the peer in SSL/TLS connections will use to verify it.
--private-key=privkey.pem
Especifica un archivo PEM que contiene la clave privada utilizada como identidad de ovs-testcontroller para las conexiones SSL/TLS salientes.
-c cert.pem

--certificate=cert.pem
Especifica un archivo PEM que contiene un certificado que certifica que la clave privada especificada en -p o --private-key es digna de confianza. El certificado debe estar firmado por la autoridad certificadora (CA) que el par en las conexiones SSL/TLS utilizará para verificarlo.
-C cacert.pem

--ca-cert=cacert.pem
Especifica un archivo PEM que contiene el certificado de la CA que ovs-testcontroller debe utilizar para verificar los certificados presentados por los pares SSL/TLS. (Este puede ser el mismo certificado que los pares SSL/TLS utilizan para verificar el certificado especificado en -c o --certificate, o puede ser uno diferente, dependiendo del diseño de PKI en uso.)
-C none

--ca-cert=none
Desactiva la verificación de los certificados presentados por los pares SSL/TLS. Esto introduce un riesgo de seguridad, ya que significa que los certificados no pueden ser verificados como los de hosts conocidos y confiables.
--peer-ca-cert=peer-cacert.pem
Especifica un archivo PEM que contiene uno o más certificados adicionales para enviar a los pares SSL/TLS. peer-cacert.pem debe ser el certificado de la CA utilizado para firmar el propio certificado de ovs-testcontroller, es decir, el certificado especificado en -c o --certificate. Si el certificado de ovs-testcontroller es autofirmado, entonces --certificate y --peer-ca-cert deben especificar el mismo archivo.
Esta opción no es útil en operación normal, ya que el par SSL/TLS ya debe tener el certificado de la CA para que el par tenga alguna confianza en la identidad de ovs-testcontroller. Sin embargo, esto ofrece una forma para que una nueva instalación inicialice el certificado de la CA en su primera conexión SSL/TLS.

Opciones del Demonio

Las siguientes opciones son válidas en plataformas basadas en POSIX.

--pidfile[=pidfile]
Causa que se cree un archivo (por defecto, ovs-testcontroller.pid) indicando el PID del proceso en ejecución. Si el argumento pidfile no se especifica, o si no comienza con /, entonces se crea en /run/openvswitch.
Si no se especifica --pidfile, no se crea ningún archivo pidfile.
--overwrite-pidfile
Por defecto, cuando se especifica --pidfile y el archivo pidfile especificado ya existe y está bloqueado por un proceso en ejecución, ovs-testcontroller se niega a iniciarse. Especificar --overwrite-pidfile hará que sobrescriba el archivo pidfile en su lugar.
Cuando no se especifica --pidfile, esta opción no tiene efecto.
--detach
Ejecuta ovs-testcontroller como un proceso en segundo plano. El proceso se bifurca, y en el hijo inicia una nueva sesión, cierra los descriptores de archivo estándar (lo que tiene el efecto secundario de deshabilitar el registro en la consola) y cambia su directorio actual a la raíz (a menos que se especifique --no-chdir). Después de que el hijo completa su inicialización, el padre sale.
--monitor
Crea un proceso adicional para monitorear el demonio ovs-testcontroller. Si el demonio muere debido a una señal que indica un error de programación (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU, o SIGXFSZ), entonces el proceso monitor inicia una nueva copia de él. Si el demonio muere o sale por otra razón, el proceso monitor sale.
Esta opción normalmente se usa con --detach, pero también funciona sin ella.
--no-chdir
Por defecto, cuando se especifica --detach, ovs-testcontroller cambia su directorio de trabajo actual al directorio raíz después de desvincularse. De lo contrario, invocar ovs-testcontroller desde un directorio elegido descuidadamente impediría al administrador desmontar el sistema de archivos que contiene ese directorio.
Especificar --no-chdir suprime este comportamiento, impidiendo que ovs-testcontroller cambie su directorio de trabajo actual. Esto puede ser útil para recopilar volcados centrales, ya que es un comportamiento común escribir volcados centrales en el directorio de trabajo actual y el directorio raíz no es un buen directorio para usar.
Esta opción no tiene efecto cuando no se especifica --detach.
--no-self-confinement
Por defecto, el demonio intentará auto-confinarse para trabajar con archivos bajo directorios bien conocidos determinados durante la compilación. Es mejor apegarse a este comportamiento predeterminado y no usar esta bandera a menos que se utilice alguna otra Control de Acceso para confinar el demonio. Tenga en cuenta que, a diferencia de otras implementaciones de control de acceso que se imponen típicamente desde el espacio del kernel (por ejemplo, DAC o MAC), el auto-confinamiento es impuesto desde el demonio de espacio de usuario en sí y, por lo tanto, no debe considerarse una estrategia de confinamiento completa, sino que debe verse como una capa adicional de seguridad.
--user
Hace que ovs-testcontroller se ejecute como un usuario diferente especificado en "usuario:grupo", soltando así la mayoría de los privilegios de root. Las formas cortas "usuario" y ":grupo" también son aceptadas, con el usuario o grupo actual asumido respectivamente. Solo los demonios iniciados por el usuario root aceptan este argumento.
En Linux, a los demonios se les otorgarán CAP_IPC_LOCK y CAP_NET_BIND_SERVICES antes de soltar los privilegios de root. A los demonios que interactúan con un plano de datos, como ovs-vswitchd, se les otorgarán tres capacidades adicionales, a saber CAP_NET_ADMIN, CAP_NET_BROADCAST y CAP_NET_RAW. El cambio de capacidad se aplicará incluso si el nuevo usuario es root.
En Windows, esta opción no es compatible actualmente. Por razones de seguridad, especificar esta opción hará que el proceso demonio no se inicie.
-v[spec]

--verbose=[spec]
Establece los niveles de registro. Sin ningún spec, establece el nivel de registro para cada módulo y destino a dbg. De lo contrario, spec es una lista de palabras separadas por espacios, comas o dos puntos, hasta una de cada categoría a continuación:
  • Un nombre de módulo válido, como se muestra en el comando vlog/list en ovs-appctl(8), limita el cambio de nivel de registro al módulo especificado.
  • syslog, console, o file, para limitar el cambio de nivel de registro solo al registro del sistema, a la consola o a un archivo, respectivamente. (Si se especifica --detach, ovs-testcontroller cierra sus descriptores de archivo estándar, por lo que el registro en la consola no tendrá efecto.)
En la plataforma Windows, syslog se acepta como una palabra y solo es útil junto con la opción --syslog-target (la palabra no tiene efecto de lo contrario).
•
off, emer, err, warn, info, o dbg, para controlar el nivel de registro. Se registrarán los mensajes de la severidad dada o superior, y los mensajes de menor severidad serán filtrados. off filtra todos los mensajes. Consulte ovs-appctl(8) para obtener una definición de cada nivel de registro.
La capitalización no es sensible dentro de spec.
Independientemente de los niveles de registro establecidos para file, el registro en un archivo no tendrá lugar a menos que también se especifique --log-file (ver más abajo).
Para compatibilidad con versiones anteriores de OVS, any se acepta como una palabra pero no tiene ningún efecto.
-v

--verbose
Establece el nivel máximo de verbosidad del registro, equivalente a --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Establece el patrón de registro para destination a pattern. Consulte ovs-appctl(8) para obtener una descripción de la sintaxis válida para pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Establece la instalación RFC5424 del mensaje de registro. facility puede ser uno de kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 o local7. Si esta opción no se especifica, se utiliza daemon como predeterminado para el syslog del sistema local y se utiliza local0 al enviar un mensaje al destino proporcionado a través de la opción --syslog-target.
--log-file[=file]
Habilita el registro en un archivo. Si se especifica file, entonces se utiliza como el nombre exacto del archivo de registro. El nombre predeterminado del archivo de registro utilizado si se omite file es /var/log/openvswitch/ovs-testcontroller.log.
--syslog-target=server
Envía mensajes de registro a un servidor syslog remoto en server, que debe ser una dirección IP o nombre de host seguido opcionalmente por un número de puerto, separado por dos puntos. Si el puerto se omite, se utiliza el puerto predeterminado de syslog (514).
--disable-syslog-remote-log-tag
Por defecto, el demonio añade la cadena de identificación de registro remota predeterminada ("Open_vSwitch_Daemon_Log") a los mensajes de registro enviados al servidor syslog remoto especificado por --syslog-target. Esta opción deshabilita la adición de esta cadena de identificación.
--mlockall
Intenta bloquear toda la memoria utilizada por el proceso en la memoria RAM, para que la memoria no se intercambie en el disco. Esto puede mejorar el rendimiento al evitar las pausas de intercambio, pero puede consumir una gran cantidad de memoria RAM y, en sistemas que no son Linux, puede requerir privilegios especiales.
Esta opción está disponible en Linux y Windows. El comportamiento subyacente es llamar a la función `mlockall()` en Linux y `VirtualLock` en Windows.
En Windows, esta opción requiere privilegios de administrador.
--strict-memory-usage
Si se especifica, el demonio saldrá con un error si el uso de memoria alcanza el 90% del límite de memoria establecido por --memory-limit o si se excede el límite establecido por --memory-limit. Si no se especifica, el demonio intentará reducir su uso de memoria, pero no saldrá con un error.
--memory-limit=limit
Establece un límite para el uso de memoria del demonio en bytes. Si el uso de memoria excede el límite, el demonio saldrá con un error (a menos que se especifique --strict-memory-usage no se especifica, en cuyo caso intentará reducir su uso de memoria).
El valor predeterminado es 1 Gibibyte (1024 MiB).
En Windows, esta opción solo se aplica a los procesos que no se ejecutan como SYSTEM. En esos casos, el límite se establece llamando a `SetProcessMemoryLimit`.
--rlimit-core=value
Establece el límite de tamaño del archivo central del proceso. El valor value se interpreta como un número de bloques de 512 bytes. Use `unlimited` para indicar sin límite.
Esto puede ser útil para garantizar que se generen volcados centrales para un proceso en caso de caída.
--rlimit-data=value
Establece el límite del tamaño de datos del proceso. El valor value se interpreta como un número de bloques de 1 kilobyte. Use `unlimited` para indicar sin límite.
--rlimit-nofile=value
Establece el límite del número de descriptores de archivo abiertos. El valor value debe ser un entero positivo. Use `unlimited` para indicar sin límite.
En sistemas POSIX, el valor predeterminado es 1024.
--rlimit-stack=value
Establece el límite del tamaño de la pila del proceso. El valor value se interpreta como un número de bloques de 1 kilobyte. Use `unlimited` para indicar sin límite.
En Linux, el valor predeterminado es 8 MB.

Opciones de Registro

--log-file-max-size=size
Establece el tamaño máximo del archivo de registro antes de que se rotará. El valor predeterminado es 10 MiB. Si se omite, el registro en archivo está deshabilitado.
Esta opción solo se aplica si el registro en archivo está habilitado por --log-file.
--log-file-backlog=size
Establece el número máximo de archivos de registro de respaldo que se conservarán. El valor predeterminado es 5. Si se omite, el registro en archivo está deshabilitado.
Esta opción solo se aplica si el registro en archivo está habilitado por --log-file.
ermalink" href="#syslog">--syslog-target=host:puerto
Envía mensajes syslog al puerto UDP puerto en host, además del syslog del sistema. El host debe ser una dirección IP numérica, no un nombre de host.
--syslog-method=método
Especifica el método mediante el cual se deben enviar los mensajes syslog al demonio syslog. Se admiten las siguientes formas:
  • libc, utiliza la función syslog() de libc. La desventaja de utilizar esta opción es que libc añade un prefijo fijo a cada mensaje antes de que se envíe realmente al demonio syslog a través del socket de dominio UNIX /dev/log.
  • unix:archivo, utiliza directamente un socket de dominio UNIX. Es posible especificar un formato de mensaje arbitrario con esta opción. Sin embargo, rsyslogd 8.9 y versiones anteriores utilizan de todos modos una función de análisis codificada que limita el uso del socket de dominio UNIX. Si desea utilizar un formato de mensaje arbitrario con versiones anteriores de rsyslogd, utilice en su lugar un socket UDP a la dirección IP de localhost.
  • udp:ip:puerto, utiliza un socket UDP. Con este método es posible utilizar un formato de mensaje arbitrario también con versiones anteriores de rsyslogd. Al enviar mensajes syslog a través de un socket UDP, se deben tener precauciones adicionales, por ejemplo, el demonio syslog debe estar configurado para escuchar en el puerto UDP especificado, las reglas de iptables accidentales podrían interferir con el tráfico syslog local y existen algunas consideraciones de seguridad que se aplican a los sockets UDP, pero no a los sockets de dominio UNIX.
  • null, descarta todos los mensajes registrados en syslog.
El valor predeterminado se toma de la variable de entorno OVS_SYSLOG_METHOD; si no está establecida, el valor predeterminado es libc.
--unixctl=socket
Establece el nombre del socket de control en el que ovs-testcontroller escucha los comandos de gestión en tiempo de ejecución (consulte COMANDOS DE GESTIÓN EN TIEMPO DE EJECUCIÓN, a continuación). Si socket no comienza con /, se interpreta como relativo a /run/openvswitch. Si no se utiliza --unixctl, el socket predeterminado es /run/openvswitch/ovs-testcontroller.pid.ctl, donde pid es el ID de proceso de ovs-testcontroller.
En Windows se utiliza una tubería con nombre local para escuchar los comandos de gestión en tiempo de ejecución. Se crea un archivo en la ruta absoluta apuntada por socket o, si no se utiliza --unixctl, se crea un archivo como ovs-testcontroller.ctl en el directorio OVS_RUNDIR configurado. El archivo existe solo para imitar el comportamiento de un socket de dominio UNIX.
Especificar none para socket deshabilita la función de socket de control.
-h

--help
Imprime un breve mensaje de ayuda en la consola.
-V

--version
Imprime la información de la versión en la consola.
-O [version[,version]...]

--protocols=[version[,version]...]
Establece las versiones del protocolo OpenFlow que están permitidas al establecer una sesión OpenFlow.
Estas versiones de protocolo están habilitadas de forma predeterminada:
•
OpenFlow10, para OpenFlow 1.0.
Las siguientes versiones de protocolo son compatibles en general, pero para la compatibilidad con versiones anteriores de Open vSwitch no están habilitadas por defecto:
  • OpenFlow11, para OpenFlow 1.1.
  • OpenFlow12, para OpenFlow 1.2.
  • OpenFlow13, para OpenFlow 1.3.
  • OpenFlow14, para OpenFlow 1.4.
  • OpenFlow15, para OpenFlow 1.5.
