OD(1P) Manual del Programador POSIX OD(1P)

PROLOGO

Esta página del manual forma parte del Manual del Programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux) o la interfaz puede no estar implementada en Linux.

NOMBRE

od — volcar archivos en varios formatos

SINOPSIS

od [-v] [-A base_direccionamiento] [-j salto] [-N contador] [-t cadena_tipo]...
    [archivo...]
od [-bcdosx] [archivo] [[+]desplazamiento[.][b]]

DESCRIPCION

La utilidad od escribirá el contenido de sus archivos de entrada en la salida estándar en un formato especificado por el usuario.

OPCIONES

La utilidad od cumplirá con el volumen de Definiciones Base de POSIX.1‐2017, Sección 12.2, Directrices de Sintaxis de Utilidades, excepto que el orden de presentación de las opciones -t y las opciones -bcdosx es significativo.

Se admitirán las siguientes opciones:

-A base_direccionamiento

Especifica la base del desplazamiento de entrada. Consulte la sección DESCRIPCIÓN EXTENDIDA. La aplicación garantizará que el argumento de opción base_direccionamiento sea un carácter. Los caracteres 'd', 'o' y 'x' especifican que la base del desplazamiento se escribirá en decimal, octal o hexadecimal, respectivamente. El carácter 'n' especifica que el desplazamiento no se escribirá.
-b
Interpreta los bytes en octal. Esto será equivalente a -t o1.
-c
Interpreta los bytes como caracteres especificados por la configuración actual de la categoría LC_CTYPE. Ciertos caracteres no imprimibles aparecen como escapes C: "NUL=\0", "BS=\b", "FF=\f", "NL=\n", "CR=\r", "HT=\t"; otros aparecen como números octales de 3 dígitos.
-d
Interpreta las palabras (unidades de dos bytes) en decimal sin signo. Esto será equivalente a -t u2.
-j salto
Salta salto bytes desde el inicio de la entrada. La utilidad od leerá o buscará más allá de los primeros salto bytes en los archivos de entrada concatenados. Si la entrada combinada no tiene al menos salto bytes, la utilidad od escribirá un mensaje diagnóstico en la salida de error estándar y saldrá con un estado de salida distinto de cero.

Por defecto, el argumento de opción salto se interpretará como un número decimal. Con un prefijo 0x o 0X, el desplazamiento se interpretará como un número hexadecimal; de lo contrario, con un prefijo '0', el desplazamiento se interpretará como un número octal. Añadir el carácter 'b', 'k' o 'm' al desplazamiento hará que se interprete como un múltiplo de 512, 1024 o 1048576 bytes, respectivamente. Si el número salto es hexadecimal, cualquier 'b' añadido se considerará el último dígito hexadecimal.

-N contador
Formatea no más de contador bytes de entrada. Por defecto, contador se interpretará como un número decimal. Con un prefijo 0x o 0X, contador se interpretará como un número hexadecimal; de lo contrario, con un prefijo '0', se interpretará como un número octal. Si no hay disponibles contador bytes de entrada (después de saltar con éxito, si se especifica -j salto), no se considerará un error; la utilidad od formateará la entrada disponible.
-o
Interpreta las palabras (unidades de dos bytes) en octal. Esto será equivalente a -t o2.
-s
Interpreta las palabras (unidades de dos bytes) en decimal con signo. Esto será equivalente a -t d2.
-t cadena_tipo

Especifica uno o más tipos de salida. Consulte la sección DESCRIPCIÓN EXTENDIDA. La aplicación garantizará que el argumento de opción cadena_tipo sea una cadena que especifique los tipos a utilizar al escribir los datos de entrada. La cadena consistirá en los caracteres de especificación de tipo a, c, d, f, o, u y x, que especifican caracteres con nombre, caracteres, decimal con signo, punto flotante, octal, decimal sin signo y hexadecimal, respectivamente. Los caracteres de especificación de tipo d, f, o, u y x pueden ir seguidos de un entero decimal opcional que especifique el número de bytes que se transformarán por cada instancia del tipo de salida. El carácter de especificación de tipo f puede ir seguido de una F, D o L opcional que indique que la conversión se aplicará a un elemento de tipo float, double o long double, respectivamente. Los caracteres de especificación de tipo d, o, u y x pueden ir seguidos de una C, S, I o L opcional que indique que la conversión se aplicará a un elemento de tipo char, short, int o long, respectivamente. Se pueden concatenar varios tipos dentro de la misma cadena_tipo y se pueden especificar varias opciones -t. Las líneas de salida se escribirán para cada tipo especificado en el orden en que se especifican los caracteres de especificación de tipo.
-v
Escribe todos los datos de entrada. Sin la opción -v, cualquier número de grupos de líneas de salida, que serían idénticos al grupo de líneas de salida inmediatamente anterior (excepto por los desplazamientos de bytes), será reemplazado por una línea que contiene solo un asterisco ('*').
-x
Interpreta las palabras (unidades de dos bytes) en hexadecimal. Esto será equivalente a -t x2.

Se pueden especificar varios tipos utilizando varias opciones -bcdostx. Las líneas de salida se escriben para cada tipo especificado en el orden en que se especifican los tipos.

OPERANDOS

Se admitirán los siguientes operandos:

archivo
Una ruta de un archivo a leer. Si no se especifican operandos de archivo, se utilizará la entrada estándar.

Si no hay más de dos operandos, no se especifica ninguna de las opciones -A, -j, -N, -t o -v, y se cumple alguna de las siguientes condiciones: el primer carácter del último operando es un signo más ('+'), o hay dos operandos y el primer carácter del último operando es numérico; el último operando se interpretará como un operando de desplazamiento en sistemas conformes a XSI. Bajo estas condiciones, los resultados no están especificados en sistemas que no son conformes a XSI.

[+]desplazamiento[.][b]
El operando desplazamiento especifica el desplazamiento en el archivo donde comenzará el volcado. Este operando se interpreta normalmente en bytes octales. Si se añade '.', el desplazamiento se interpretará en decimal. Si se añade 'b', el desplazamiento se interpretará en unidades de 512 bytes.

ENTRADA ESTÁNDAR

La entrada estándar se utilizará si no se especifican operandos de archivo, y se utilizará si un operando de archivo es '-' y la implementación trata el '-' como entrada estándar. De lo contrario, la entrada estándar no se utilizará. Consulte la sección ARCHIVOS DE ENTRADA.

ARCHIVOS DE ENTRADA

Los archivos de entrada pueden ser de cualquier tipo.

VARIABLES DE ENTORNO

Las siguientes variables de entorno afectarán la ejecución de od:

LANG
Se utilizará para determinar la configuración regional a utilizar para los algoritmos de interpretación de texto que dependen de la configuración regional.
LC_ALL
Se utilizará para determinar la configuración regional a utilizar para los algoritmos de interpretación de texto que dependen de la configuración regional.
LC_CTYPE
Se utilizará para determinar la configuración regional a utilizar para la interpretación de caracteres.
LC_MESSAGES
Se utilizará para determinar la configuración regional a utilizar para los mensajes que se escriben en el error estándar.
NLSPATH
Se utilizará para determinar la ubicación de los archivos de mensajes para la configuración regional.

EJEMPLOS

Mostrar el archivo abc como octal, decimal y caracteres:

od -a -b -c abc

Mostrar los primeros 12 bytes del archivo abc como palabras de 4 bytes en hexadecimal:

od -N 12 -t x4 abc

Mostrar el archivo abc empezando en el desplazamiento de 32 kilobytes, con los desplazamientos en octal y los datos en formato de carácter:

od -j 32k -A o -t c abc

SALIDA ESTÁNDAR

Las líneas de salida contienen desplazamientos seguidos de la representación de datos en el formato solicitado.

La salida de los desplazamientos de fila (la primera columna) está determinada por la opción -A. Sin opciones, el desplazamiento se escribe en octal, comenzando en 0.

Sin la opción -v, se pueden sustituir líneas de salida idénticas (excepto por el desplazamiento) por un único asterisco ('*').

CÓDIGO DE SALIDA

Se devolverán los siguientes valores de salida:

0
Se realizó correctamente la operación.
>0
Se produjo un error.

ERRORES

Si ocurre un error de lectura, se escribirá un mensaje de diagnóstico en el error estándar, y la utilidad saldrá con un estado distinto de cero.

NOTAS DE IMPLEMENTACIÓN

La especificación POSIX define el comportamiento básico y proporciona varias opciones de extensión. Los comportamientos que no son comunes a todos los sistemas, pero que están definidos en la especificación POSIX, se marcan como no especificados o se definen explícitamente como extensiones XSI.

La versión de od proporcionada por GNU Coreutils implementa la mayoría de las opciones estándar y algunas de las extensiones XSI. Las opciones -A, -j, -N, -t y -v son las definidas por POSIX. Las opciones -bcdosx son anteriores y se implementan como atajos para ciertas combinaciones de -t.

En la especificación POSIX, el operando de desplazamiento solo se define como una extensión XSI si no se utilizan las opciones de formato de línea de comandos estándar y si no hay más de dos operandos. El comportamiento de la opción de desplazamiento está sujeto a estas restricciones.

El manejo de los operandos de desplazamiento se implementa tal como se describe en la especificación POSIX, con las limitaciones indicadas. La adición de 'k' o 'm' al operando de desplazamiento, o el uso de -j, -N o -t con tipos de datos numéricos no admitidos (por ejemplo, punto flotante), pueden no ser compatibles con todas las implementaciones.

La opción -c puede producir resultados diferentes en función de la configuración regional. Los caracteres no imprimibles se escapan de forma estándar. Para una representación más detallada, utilice la opción -t c.

DESCRIPCIÓN EXTENDIDA

La utilidad od copiará secuencialmente cada archivo de entrada a la salida estándar, transformando los datos de entrada de acuerdo con los tipos de salida especificados por la opción -t o las opciones -bcdosx. Si no se especifica ningún tipo de salida, la salida predeterminada será como si se hubiera especificado -t oS.

El número de bytes transformados por el especificador de tipo de salida c puede variar según la categoría LC_CTYPE.

El número predeterminado de bytes transformados por los especificadores de tipo d, f, o, u y x corresponde a los diversos tipos del lenguaje C de la siguiente manera. Si el compilador c99 está presente en el sistema, estos especificadores corresponderán a los tamaños utilizados por defecto en ese compilador. De lo contrario, estos tamaños pueden variar entre sistemas que cumplen con POSIX.1‐2008.

*
Para los caracteres especificadores de tipo d, o, u y x, el número predeterminado de bytes corresponderá al tamaño del tipo entero básico de la implementación subyacente. Para estos caracteres especificadores, la implementación admitirá valores del número opcional de bytes a convertir correspondientes al número de bytes en los tipos del lenguaje C char, short, int y long. Estos números también pueden ser especificados por una aplicación como los caracteres 'C', 'S', 'I' y 'L', respectivamente. La implementación también admitirá los valores 1, 2, 4 y 8, incluso si no proporciona tipos del lenguaje C de esos tamaños. La implementación admitirá el valor decimal correspondiente al tipo del lenguaje C long long. El orden de bytes utilizado al interpretar valores numéricos es definido por la implementación, pero corresponderá al orden en que una constante del tipo correspondiente se almacena en la memoria del sistema.
*
Para el carácter especificador de tipo f, el número predeterminado de bytes corresponderá al número de bytes en el tipo de datos de punto flotante de doble precisión básico de la implementación subyacente. La implementación admitirá valores del número opcional de bytes a convertir correspondientes al número de bytes en los tipos del lenguaje C float, double y long double. Estos números también pueden ser especificados por una aplicación como los caracteres 'F', 'D' y 'L', respectivamente.

El carácter especificador de tipo a especifica que los bytes se interpretarán como caracteres con nombre de la versión de referencia internacional (IRV) del estándar ISO/IEC 646:1991. Solo los siete bits menos significativos de cada byte se utilizarán para esta especificación de tipo. Los bytes con los valores que figuran en la siguiente tabla se escribirán utilizando los nombres correspondientes para esos caracteres.

El carácter especificador de tipo c especifica que los bytes se interpretarán como caracteres especificados por la configuración actual de la categoría de configuración regional LC_CTYPE. Los caracteres enumerados en la tabla del volumen de Definiciones Base de POSIX.1‐2017, Capítulo 5, Notación de formato de archivo ('\\', '\a', '\b', '\f', '\n', '\r', '\t', '\v') se escribirán como las secuencias de escape correspondientes, excepto que <barra invertida> se escribirá como una sola <barra invertida> y un NUL se escribirá como '\0'. Otros caracteres no imprimibles se escribirán como un número octal de tres dígitos por cada byte del carácter. Los caracteres multibyte imprimibles se escribirán en el área correspondiente al primer byte del carácter; la secuencia de dos caracteres "**" se escribirá en el área correspondiente a cada byte restante del carácter, como indicación de que el carácter está continuado. Cuando se especifica la opción -j skip o -N count junto con el especificador de tipo c, y esto da como resultado un intento de iniciar o finalizar en medio de un carácter multibyte, el resultado es definido por la implementación.

Los datos de entrada se manipularán en bloques, donde un bloque se define como un múltiplo del mínimo común múltiplo del número de bytes transformados por los tipos de salida especificados. Si el mínimo común múltiplo es mayor que 16, los resultados no están especificados. Cada bloque de entrada se escribirá transformado por cada tipo de salida, uno por línea escrita, en el orden en que se especificaron los tipos de salida. Si el tamaño del bloque de entrada es mayor que el número de bytes transformados por el tipo de salida, el tipo de salida transformará secuencialmente las partes del bloque de entrada, y la salida de cada una de las transformaciones estará separada por uno o más caracteres <espacio en blanco>.

Si, como resultado de la especificación de la opción -N o de la llegada del fin de archivo en el último archivo de entrada, los datos de entrada satisfacen parcialmente un tipo de salida, la entrada se extenderá suficientemente con bytes nulos para escribir el último byte de la entrada.

A menos que se especifique -A n, la primera línea de salida producida para cada bloque de entrada irá precedida por el desplazamiento de entrada, acumulado a través de los archivos de entrada, del siguiente byte a escribir. El formato del desplazamiento de entrada no está especificado; sin embargo, no contendrá ningún carácter <espacio en blanco>, comenzará en el primer carácter de la línea de salida y será seguido por uno o más caracteres <espacio en blanco>. Además, el desplazamiento del byte que sigue al último byte escrito se escribirá después de que se hayan procesado todos los datos de entrada, pero no irá seguido de ningún carácter <espacio en blanco>.

Si no se especifica ninguna opción -A, la base del desplazamiento de entrada no está especificada.

USO_DE_LA_APLICACION

Se advierte a las aplicaciones conformes con XSI que no utilicen nombres de archivo que comiencen con '+' o un primer operando que comience con un carácter numérico para que las implementaciones puedan mantener la funcionalidad anterior, a menos que especifiquen una de las opciones -A, -j o -N. Para garantizar que un nombre de archivo de este tipo siempre se interprete como un nombre de archivo, una aplicación podría especificar siempre el formato base de dirección con la opción -A.

RATICIONALE

El utilidad od pasó por varios nombres en las primeras propuestas, incluyendo hd, xd y, más recientemente, hexdump. Hubo varias objeciones a todos ellos basándose en las siguientes razones:

*
Los nombres hd y xd entraron en conflicto con utilidades históricas que se comportaban de manera diferente.
*
La descripción de hexdump era mucho más compleja de lo necesario para una utilidad de volcado simple.
*
La utilidad od ha estado disponible en todas las implementaciones históricas y no hubo necesidad de crear un nuevo nombre para una utilidad tan similar a la utilidad histórica od.

Las razones originales para no estandarizar el od histórico también estaban bastante extendidas. Esas razones se presentan a continuación junto con la justificación que explica por qué los desarrolladores del estándar creen que esta versión no sufre el problema indicado:

*
Las versiones BSD y System V de od han divergido, y la intersección de características proporcionadas por ambas no satisface las necesidades de la comunidad de usuarios. De hecho, la versión de System V solo proporciona un mecanismo para volcar bytes octales y shorts, shorts decimales con signo y sin signo, shorts hexadecimales y caracteres ASCII. BSD agregó la capacidad de volcar floats, doubles, caracteres ASCII con nombre y longs octales, decimales con signo, decimales sin signo y hexadecimales. La versión presentada aquí proporciona formas más normalizadas para volcar bytes, shorts, ints y longs en octal, decimal con signo, decimal sin signo y hexadecimal; float, double y long double; y caracteres ASCII con nombre, así como caracteres de la configuración regional actual.
*
No sería posible crear un superconjunto compatible de los indicadores BSD y System V que cumpliera los requisitos de los desarrolladores del estándar. La salida predeterminada histórica de od es la salida predeterminada especificada de esta utilidad. Ninguna de las letras de opción elegidas para esta versión de od entra en conflicto con ninguna de las opciones de las versiones históricas de od.
*
En sistemas con diferentes tamaños para short, int y long, no había forma de solicitar volcados de ints, incluso en la versión BSD. Debido a la forma en que se nombran las opciones, el espacio de nombres no se pudo extender para resolver estos problemas. Es por eso que se agregó la opción -t (con especificadores de tipo que coinciden más estrechamente con los formatos de printf() utilizados en el resto de este volumen de POSIX.1-2017) y se agregaron los tamaños de campo opcionales a los especificadores de tipo d, f, o, u y x. También es una de las razones por las que la práctica histórica no se impuso como una forma obsoleta requerida de od. (Aunque las versiones antiguas de od no se enumeran como una forma obsoleta, se insta a las implementaciones a continuar reconociendo las formas más antiguas durante varios años más). Los tipos a, c, f, o y x coinciden con el significado de los caracteres de formato correspondientes en las implementaciones históricas de od, excepto por los tamaños predeterminados de los campos convertidos. El formato d es con signo en este volumen de POSIX.1-2017 para que coincida con la notación de printf(). (Las versiones históricas de od usaban d como sinónimo de u en esta versión. La implementación de System V usa s para decimal con signo; BSD usa i para decimal con signo y s para cadenas terminadas en nulo). Aparte de d y u, todos los especificadores de tipo coinciden con los caracteres de formato en la versión BSD histórica de od.

Se utilizan los tamaños de los tipos del lenguaje C char, short, int, long, float, double y long double, aunque se reconoce que puede haber cero o más de un compilador para el lenguaje C en una implementación y que pueden usar diferentes tamaños para algunos de estos tipos. (Por ejemplo, un compilador podría usar shorts de 2 bytes, ints de 2 bytes y longs de 4 bytes, mientras que otro compilador (o una opción del mismo compilador) usa shorts de 2 bytes, ints de 4 bytes y longs de 4 bytes). Sin embargo, debe haber un tamaño básico conocido por la implementación para estos tipos, correspondiente a los valores informados por las invocaciones de la utilidad getconf cuando se llama con operandos system_var {UCHAR_MAX}, {USHORT_MAX}, {UINT_MAX} y {ULONG_MAX} para los tipos char, short, int y long, respectivamente. Existen constantes similares requeridas por el estándar ISO C, pero no requeridas por el volumen de Interfaces del Sistema de POSIX.1-2017 ni por este volumen de POSIX.1-2017. Son {FLT_MANT_DIG}, {DBL_MANT_DIG} y {LDBL_MANT_DIG} para los tipos float, double y long double, respectivamente. Si la utilidad opcional c99 es proporcionada por la implementación y utilizada según lo especificado por este volumen de POSIX.1-2017, estos serán los tamaños que se proporcionarán. Si se utiliza una opción que especifica tamaños diferentes para estos tipos, no hay garantía de que la utilidad od pueda interpretar correctamente los datos binarios producidos por dicho programa.

Este volumen de POSIX.1-2017 requiere que los valores numéricos de estas longitudes sean reconocidos por la utilidad od y que también se reconozcan las formas simbólicas. Por lo tanto, una aplicación conforme siempre puede examinar una matriz de elementos de datos unsigned long usando od -t uL.

*
El método de especificar el formato para el campo de dirección basándose en la especificación de un desplazamiento de inicio en un archivo ató innecesariamente los dos. La opción -A ahora especifica la base de dirección y la opción -S especifica un desplazamiento de inicio.
*
Sería difícil romper la dependencia de US ASCII para lograr una utilidad internacionalizada. No parece ser más difícil para od volcar caracteres en la configuración regional actual que para los comandos l de ed o sed. El especificador de tipo c lo hace sin dificultad y es completamente compatible con las implementaciones históricas del carácter de formato c cuando la configuración regional actual utiliza un superconjunto del estándar ISO/IEC 646:1991 como conjunto de códigos. El especificador de tipo a (del carácter de formato a de BSD) se dejó como un medio portable para volcar ASCII (o más correctamente ISO/IEC 646:1991 (IRV)) para que las cabeceras producidas por pax pudieran descifrarse incluso en sistemas que no utilizan el estándar ISO/IEC 646:1991 como subconjunto de su conjunto de códigos base.

El uso de "**" como indicación de continuación de un carácter multibyte en la salida del especificador c se eligió basándose en la observación de una implementación que utiliza este método. Los bytes de continuación deben marcarse de una manera que no sea ambigua con otro carácter de un solo byte o multibyte.

Una propuesta temprana utilizó -S y -n, respectivamente, para las opciones -j y -N seleccionadas finalmente. Estos se cambiaron para evitar conflictos con implementaciones históricas.

El estándar original especificó -t o2 como valor predeterminado cuando no se especificaba ningún tipo de salida

se proporcionó. Esto se cambió a -t oS (la longitud de un short) para acomodar una implementación de supercomputadora que históricamente usaba 64 bits como su valor predeterminado (y que definía los shorts como de 64 bits). Este cambio no debería afectar a las aplicaciones que cumplen con el estándar. El requisito de admitir longitudes de 1, 2 y 4 se agregó al mismo tiempo para abordar una implementación histórica que no tenía tipos de datos de dos bytes en su compilador C.

El uso de un tipo de dato entero básico está destinado a permitir que la implementación elija un tamaño de palabra comúnmente utilizado por las aplicaciones en esa arquitectura.

Las versiones anteriores de este estándar permitían implementaciones con bytes distintos de ocho bits, pero esto se ha modificado en esta versión.
