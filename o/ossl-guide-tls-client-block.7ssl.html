NOMBRE

ossl-guide-tls-client-block - Guía de OpenSSL: Escritura de un cliente TLS simple bloqueante

EJEMPLO DE CLIENTE TLS SIMPLE BLOQUEANTE

Esta página presentará varios ejemplos de código fuente que demuestran cómo escribir una aplicación cliente TLS simple que se conecta a un servidor, le envía una solicitud HTTP/1.0 y lee la respuesta.

Utilizamos un socket bloqueante para este ejemplo. Esto significa que intentar leer datos de un socket que no tiene datos disponibles para leer se bloqueará (y la función no retornará) hasta que los datos estén disponibles. Por ejemplo, esto puede ocurrir si hemos enviado nuestra solicitud, pero aún estamos esperando la respuesta del servidor. De manera similar, cualquier intento de escribir en un socket que no puede escribir en ese momento se bloqueará hasta que la escritura sea posible.

Este comportamiento bloqueante simplifica la implementación de un cliente porque no tiene que preocuparse por lo que sucede si los datos aún no están disponibles. La aplicación simplemente esperará hasta que estén disponibles.

El código fuente completo de este cliente TLS bloqueante de ejemplo está disponible en el directorio demos/guide de la distribución de fuentes de OpenSSL, en el archivo tls-client-block.c. También está disponible en línea en https://github.com/openssl/openssl/blob/master/demos/guide/tls-client-block.c.

Asumimos que ya tiene OpenSSL instalado en su sistema; que ya tiene alguna comprensión fundamental de los conceptos de OpenSSL y TLS (vea ossl-guide-libraries-introduction(7) y ossl-guide-tls-introduction(7)); y que sabe cómo escribir y compilar código C y enlazarlo contra las bibliotecas libcrypto y libssl que proporciona OpenSSL. También asume que tiene una comprensión básica de TCP/IP y sockets.

Creación de los objetos SSL_CTX y SSL

El primer paso es crear un objeto SSL_CTX para nuestro cliente. Utilizamos la función SSL_CTX_new(3) para este propósito. Alternativamente, podríamos usar SSL_CTX_new_ex(3) si queremos asociar el SSL_CTX con un OSSL_LIB_CTX particular (vea ossl-guide-libraries-introduction(7) para aprender sobre OSSL_LIB_CTX). Pasamos como argumento el valor de retorno de la función TLS_client_method(3). Debe usar este método siempre que esté escribiendo un cliente TLS. Este método utilizará automáticamente la negociación de la versión TLS para seleccionar la versión más alta del protocolo que sea compatible mutuamente tanto por el cliente como por el servidor.

/*
 * Crea un SSL_CTX que podemos usar para crear objetos SSL.
 * Queremos un SSL_CTX para crear clientes, por lo que usamos TLS_client_method()
 * aquí.
 */
ctx = SSL_CTX_new(TLS_client_method());
if (ctx == NULL) {
    printf("Fallo al crear el SSL_CTX\n");
    goto end;
}

Como estamos escribiendo un cliente, debemos asegurarnos de verificar el certificado del servidor. Hacemos esto llamando a la función SSL_CTX_set_verify(3) y pasándole el valor SSL_VERIFY_PEER. El último argumento de esta función es una devolución de llamada que puede proporcionar opcionalmente para anular el manejo por defecto para la verificación de certificados. La mayoría de las aplicaciones no necesitan hacer esto, por lo que se puede establecer de forma segura en NULL para obtener el manejo por defecto.

/*
 * Configura el cliente para que aborte el handshake si la verificación del
 * certificado falla. Prácticamente todos los clientes deberían hacer esto,
 * a menos que realmente sepa lo que está haciendo.
 */
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL);

Para que la verificación del certificado sea exitosa, debe haber configurado la ubicación del almacén de certificados de confianza que se va a utilizar (vea ossl-guide-tls-introduction(7)). En la mayoría de los casos, solo desea utilizar el almacén por defecto, por lo que llamamos a SSL_CTX_set_default_verify_paths(3).

/* Usa el almacén de certificados de confianza por defecto */
if (!SSL_CTX_set_default_verify_paths(ctx)) {
    printf("Fallo al establecer el almacén de certificados de confianza por defecto\n");
    goto end;
}

También nos gustaría restringir las versiones TLS que estamos dispuestos a aceptar a TLSv1.2 o superior. Las versiones del protocolo TLS anteriores a esa generalmente deben evitarse siempre que sea posible. Podemos hacer eso usando SSL_CTX_set_min_proto_version(3):

/*
 * TLSv1.1 o anterior son deprecados por el IETF y generalmente deben
 * evitarse si es posible. Requerimos una versión mínima de protocolo TLS de TLSv1.2.
 */
if (!SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION)) {
    printf("Fallo al establecer la versión mínima del protocolo TLS\n");
    goto end;
}

Eso es toda la configuración que necesitamos hacer para el SSL_CTX, así que a continuación necesitamos crear un objeto SSL para representar la conexión TLS. En una aplicación real, podríamos esperar crear más de una conexión TLS con el tiempo. En ese caso, esperaríamos reutilizar el SSL_CTX que ya creamos cada vez. No hay necesidad de repetir esos pasos. De hecho, es mejor no hacerlo, ya que ciertos recursos internos se almacenan en caché en el SSL_CTX. Obtendrá un mejor rendimiento reutilizando un SSL_CTX existente en lugar de crear uno nuevo cada vez.

Crear el objeto SSL es una simple cuestión de llamar a la función SSL_new(3) y pasar el SSL_CTX que creamos como argumento.

/* Crea un objeto SSL para representar la conexión TLS */
ssl = SSL_new(ctx);
if (ssl == NULL) {
    printf("Fallo al crear el objeto SSL\n");
    goto end;
}

Creación del socket y BIO

Los datos TLS se transmiten a través de una capa de transporte subyacente. Normalmente un socket TCP. Es responsabilidad de la aplicación asegurarse de que el socket se cree y se asocie con un objeto SSL (a través de un BIO).

La creación de sockets para uso por un cliente suele ser un proceso de 2 pasos, es decir, la construcción del socket; y la conexión del socket.

Cómo construir un socket es específico de la plataforma, pero la mayoría de las plataformas (incluida Windows) proporcionan una interfaz compatible con POSIX a través de la función socket, por ejemplo, para crear un socket TCP IPv4:

int sock;
sock = socket(AF_INET, SOCK_STREAM, 0);
if (sock == -1)
    return NULL;

Una vez que el socket está construido, debe conectarse al servidor remoto. Nuevamente, los detalles son específicos de la plataforma, pero la mayoría de las plataformas (incluida Windows) proporcionan la función compatible con POSIX connect. Por ejemplo:

struct sockaddr_in serveraddr;
struct hostent *server;
server = gethostbyname("www.openssl.org");
if (server == NULL) {
    close(sock);
    return NULL;
}
memset(&serveraddr, 0, sizeof(serveraddr));
serveraddr.sin_family = server->h_addrtype;
serveraddr.sin_port = htons(443);
memcpy(&serveraddr.sin_addr.s_addr, server->h_addr, server->h_length);
if (connect(sock, (struct sockaddr *)&serveraddr,
            sizeof(serveraddr)) == -1) {
    close(sock);
    return NULL;
}

OpenSSL proporciona funciones auxiliares portátiles para realizar estas tareas, que también se integran en el sistema de errores de OpenSSL para registrar datos de error, por ejemplo:

int sock = -1;
BIO_ADDRINFO *res;
const BIO_ADDRINFO *ai = NULL;
/*
 * Busca información de dirección IP para el servidor.
 */
if (!BIO_lookup_ex(hostname, port, BIO_LOOKUP_CLIENT, family, SOCK_STREAM, 0,
                   &res))
    return NULL;
/*
 * Recorre todas las direcciones posibles para el servidor y encuentra una
 * a la que podamos conectarnos.
 */
for (ai = res; ai != NULL; ai = BIO_ADDRINFO_next(ai)) {
    /*
     * Crea un socket TCP. Podríamos usar igualmente llamadas no-OpenSSL
     * como "socket" aquí para esto y las funciones posteriores de
     * conexión y cierre. Pero por razones de portabilidad y también para
     * que obtengamos errores en la pila de OpenSSL en caso de fallo,
     * usamos las versiones de OpenSSL de estas funciones.
     */
    sock = BIO_socket(BIO_ADDRINFO_family(ai), SOCK_STREAM, 0, 0);
    if (sock == -1)
        continue;
    /* Conecta el socket a la dirección del servidor */
    if (!BIO_connect(sock, BIO_ADDRINFO_address(ai), BIO_SOCK_NODELAY)) {
        BIO_closesocket(sock);
        sock = -1;
        continue;
    }
    /* Tenemos un socket conectado, así que salimos del bucle */
    break;
}
/* Libera los recursos de información de dirección que asignamos anteriormente */
BIO_ADDRINFO_free(res);

Ver BIO_lookup_ex(3), BIO_ADDRINFO_free(3), BIO_socket(3), BIO_connect(3), BIO_closesocket(3) y BIO_addrinfo_next(3).

Una vez que hemos creado el socket, necesitamos crear un BIO (Basic Input/Output) que se asocie con él. OpenSSL utiliza BIOn como su interfaz de entrada/salida subyacente. La forma más fácil de hacer esto es usar la función BIO_new_socket(3) que toma el descriptor del socket como argumento. Luego podemos adjuntar este nuevo BIO al objeto SSL usando la función SSL_set_bio(3). Los dos primeros argumentos a SSL_set_bio() son el BIO de lectura y el BIO de escritura respectivamente. En este caso, simplemente usamos el mismo BIO para ambas:

/*
 * Crea un BIO asociado con el socket. El BIO se usa para leer y escribir
 * datos.
 */
bio = BIO_new_socket(sock, BIO_NOCLOSE);
if (bio == NULL) {
    printf("Failed to create the socket BIO\n");
    goto end;
}
/*
 * Asocia el BIO con el objeto SSL. A partir de ahora, cualquier operación
 * de lectura o escritura en el objeto SSL se hará a través de este BIO.
 */
SSL_set_bio(ssl, bio, bio);

Es importante observar que OpenSSL ahora es responsable de la gestión del BIO (y por lo tanto del socket subyacente). Si llama a SSL_free(3), también liberará el BIO. Si llama a BIO_free(3), también liberará el socket.

Realización del handshake TLS

Ahora que hemos configurado nuestro objeto SSL y lo hemos asociado con un BIO, estamos listos para realizar el handshake TLS. Este es el proceso en el que el cliente y el servidor negocian los parámetros de la conexión, intercambian certificados (si son requeridos) y establecen claves de sesión seguras. El handshake se realiza llamando a la función SSL_connect(3).

/*
 * Realiza la conexión TLS al servidor. Esto incluye la negociación del
 * protocolo TLS, el intercambio de certificados y el establecimiento de
 * claves de sesión seguras.
 */
if (SSL_connect(ssl) <= 0) {
    printf("Failed to perform TLS connect\n");
    /* El error se puede obtener llamando a ERR_print_errors_fp(stderr); */
    goto end;
}

Si SSL_connect(3) devuelve un valor positivo, el handshake se ha realizado correctamente. Si devuelve 0 o un valor negativo, ha ocurrido un error. Para obtener más detalles sobre el error, puede llamar a la función ERR_print_errors_fp(3), que imprimirá información detallada sobre el error en la secuencia de archivos proporcionada. En nuestro ejemplo, lo estamos imprimiendo a stderr.

También es una buena idea imprimir la versión del protocolo TLS y el conjunto de cifrado que se negociaron. Esto se puede hacer llamando a SSL_get_version(3) y SSL_get_cipher(3):

printf("TLS connection established.\n");
printf("TLS version: %s\n", SSL_get_version(ssl));
printf("Cipher negotiated: %s\n", SSL_get_cipher(ssl));

Escribiendo la solicitud HTTP

Ahora que el handshake TLS se ha completado, la conexión está lista para usarse para enviar y recibir datos. En este ejemplo, vamos a enviar una solicitud HTTP/1.0 simple al servidor.

La solicitud HTTP se construye como una cadena de caracteres normal. Simplemente la escribimos en la conexión TLS usando la función SSL_write(3). Es importante tener en cuenta que, dado que estamos utilizando un BIO de socket bloqueante, SSL_write(3) bloqueará si no puede escribir todos los datos de inmediato. Esto sucede si el búfer de salida subyacente está lleno. En esta situación, SSL_write(3) intentará escribir tantos datos como sea posible y luego devolverá el número de bytes escritos. Repetiríamos la llamada hasta que todos los datos se hayan escrito.

/*
 * Envía una solicitud HTTP/1.0 GET simple al servidor.
 */
const char *request = "GET / HTTP/1.0\r\nHost: www.openssl.org\r\n\r\n";
int ret;
ret = SSL_write(ssl, request, strlen(request));
if (ret <= 0) {
    printf("Failed to send HTTP request\n");
    /* El error se puede obtener llamando a ERR_print_errors_fp(stderr); */
    goto end;
}

Al igual que con SSL_connect(3), SSL_write(3) devuelve el número de bytes escritos, o un valor menor o igual a cero si se ha producido un error. Nuevamente, puede usar ERR_print_errors_fp(3) para obtener información sobre el error.

Leyendo la respuesta HTTP

Después de enviar la solicitud, esperamos la respuesta del servidor. Leemos los datos de la conexión TLS usando la función SSL_read(3). Al igual que con SSL_write(3), esta función puede bloquear si no hay datos disponibles para leer. Seguiremos llamando a SSL_read(3) hasta que hayamos recibido todos los datos o hasta que ocurra un error.

/*
 * Lee la respuesta del servidor. El bucle leerá los datos en trozos
 * hasta que no haya más datos para leer.
 */
char buffer[1024];
int n = 0;
do {
    n = SSL_read(ssl, buffer, sizeof(buffer) - 1);
    if (n > 0) {
        buffer[n] = '\0'; /* Asegurar la terminación nula */
        printf("%s", buffer);
    } else if (n <= 0) {
        int err = SSL_get_error(ssl, n);
        if (err == SSL_ERROR_WANT_READ || err == SSL_ERROR_WANT_WRITE) {
            /* Esperar datos o poder escribir */
            continue;
        }
        printf("Failed to read HTTP response\n");
        /* El error se puede obtener llamando a ERR_print_errors_fp(stderr); */
        goto end;
    }
} while (n > 0 || SSL_want_read(ssl)); /* Continuar si hay más datos o si estamos esperando leer */

En el código anterior, usamos un búfer de 1024 bytes para leer los datos. Cada vez que llamamos a SSL_read(3), leemos un máximo de 1023 bytes (dejando espacio para el carácter nulo terminador). Si la llamada es exitosa (devuelve un valor positivo), imprimimos los datos leídos en la consola. Si devuelve un valor menor o igual a cero, comprobamos si el error se debe a que estamos esperando leer o escribir más datos (lo cual es normal en un contexto bloqueante, aunque menos común con sockets bloqueantes puros). Si el error es diferente, consideramos que es un fallo y salimos. El bucle continúa mientras se lean datos o mientras estemos esperando leer más datos.

Limpieza

Finalmente, cuando hayamos terminado con la conexión, debemos liberar todos los recursos que hemos asignado. Esto incluye el objeto SSL, el objeto SSL_CTX y el socket.

end:
    /*
     * Cerrar la conexión TLS y liberar los recursos asociados.
     */
    SSL_free(ssl);
    /*
     * Cerrar el SSL_CTX y liberar los recursos asociados.
     */
    SSL_CTX_free(ctx);
    /*
     * Cerrar el socket y liberar los recursos asociados.
     */
    close(sock); /* O BIO_closesocket(sock); si se usó */
    return ret;

Nota: si el programa salió temprano, por ejemplo, debido a un error en la configuración del SSL_CTX, entonces el socket podría no haber sido creado o conectado. Por lo tanto, la llamada a `close(sock)` debe ser segura incluso si `sock` no se ha inicializado o se ha establecido en -1.

NAME

SSL_connect - establish a TLS/SSL connection to a server

SYNOPSIS

#include <openssl/ssl.h>
#include <openssl/err.h>
#include <openssl/bio.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <string.h>

/*
 * Example of how to connect to a server using SSL/TLS.
 * This example assumes a blocking socket.
 */
SSL *
do_connect(const char *hostname, int port)
{
    BIO *bio;
    SSL *ssl;
    int sock;
    struct sockaddr_in server_addr;
    int family = AF_INET;
    /* Other families like AF_INET6 are also possible */

    /*
     * Create a socket and connect it to the server.
     */
    sock = socket(family, SOCK_STREAM, 0);
    if (sock < 0) {
        fprintf(stderr, "Failed to create socket\n");
        return NULL;
    }

    memset(&server_addr, 0, sizeof(server_addr));
    server_addr.sin_family = family;
    server_addr.sin_port = htons(port);

    if (inet_pton(family, hostname, &server_addr.sin_addr) <= 0) {
        /*
         * If inet_pton fails, it may be a hostname. Try to resolve it.
         * In a real application you'd want to use getaddrinfo() for
         * proper IPv6 support.
         */
        struct hostent *host = gethostbyname(hostname);
        if (!host) {
            fprintf(stderr, "Failed to resolve hostname %s\n", hostname);
            close(sock);
            return NULL;
        }
        memcpy(&server_addr.sin_addr, host->h_addr, host->h_length);
    }

    if (connect(sock, (struct sockaddr *)&server_addr, sizeof(server_addr)) < 0) {
        fprintf(stderr, "Failed to connect to server %s:%d\n", hostname, port);
        close(sock);
        return NULL;
    }

    /* Create a BIO to wrap the socket */
    bio = BIO_new(BIO_s_socket());
    if (bio == NULL) {
        BIO_closesocket(sock);
        return NULL;
    }
    /*
     * Associate the newly created BIO with the underlying socket. By
     * passing BIO_CLOSE here the socket will be automatically closed when
     * the BIO is freed. Alternatively you can use BIO_NOCLOSE, in which
     * case you must close the socket explicitly when it is no longer
     * needed.
     */
    BIO_set_fd(bio, sock, BIO_CLOSE);

    /* Create a new SSL structure */
    ssl = SSL_new(ctx); /* Assumes ctx is an initialised SSL_CTX */
    if (ssl == NULL) {
        BIO_free(bio);
        return NULL;
    }

    /* Associate the SSL object with the BIO */
    SSL_set_bio(ssl, bio, bio);

    /*
     * Tell the server during the handshake which hostname we are attempting
     * to connect to in case the server supports multiple hosts.
     */
    if (!SSL_set_tlsext_host_name(ssl, hostname)) {
        printf("Failed to set the SNI hostname\n");
        goto end;
    }

    /*
     * Ensure we check during certificate verification that the server has
     * supplied a certificate for the hostname that we were expecting.
     * Virtually all clients should do this unless you really know what you
     * are doing.
     */
    if (!SSL_set1_host(ssl, hostname)) {
        printf("Failed to set the certificate verification hostname");
        goto end;
    }

    /* Do the handshake with the server */
    if (SSL_connect(ssl) < 1) {
        printf("Failed to connect to the server\n");
        /*
         * If the failure is due to a verification error we can get more
         * information about it from SSL_get_verify_result().
         */
        if (SSL_get_verify_result(ssl) != X509_V_OK)
            printf("Verify error: %s\n",
                X509_verify_cert_error_string(SSL_get_verify_result(ssl)));
        goto end;
    }

    /*
     * If we are here, the handshake was successful. We can now perform
     * I/O operations on the SSL object.
     */

    /* ... application logic ... */

    /* Close down the connection */
    SSL_shutdown(ssl);
    SSL_free(ssl);
    return ssl; /* Note: ssl is freed here, so this is probably wrong. */

end:
    SSL_free(ssl);
    return NULL;
}

/*
 * Example of how to use the do_connect function.
 */
int
main(int argc, char **argv)
{
    SSL_CTX *ctx;
    SSL *ssl;
    const char *hostname = "www.example.com";
    int port = 443;
    size_t written;
    char buf[160];

    /* Initialize SSL */
    SSL_library_init();
    SSL_load_error_strings();
    OpenSSL_add_all_algorithms();

    /* Create a context */
    ctx = SSL_CTX_new(TLS_client_method());
    if (ctx == NULL) {
        fprintf(stderr, "Failed to create SSL context\n");
        return 1;
    }

    /* Load the default verification locations */
    if (!SSL_CTX_set_default_verify_paths(ctx)) {
        fprintf(stderr, "Failed to set default verify paths\n");
        SSL_CTX_free(ctx);
        return 1;
    }

    /* Set to require peer verification */
    SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL);

    /* Connect to the server */
    ssl = do_connect(hostname, port);
    if (ssl == NULL) {
        fprintf(stderr, "Failed to connect to server %s:%d\n", hostname, port);
        SSL_CTX_free(ctx);
        return 1;
    }

    /* We have connected successfully. Now send an HTTP request. */
    const char *request_start = "GET / HTTP/1.0\r\nConnection: close\r\nHost: ";
    const char *request_end = "\r\n\r\n";

    /* Write an HTTP GET request to the peer */
    if (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
        printf("Failed to write start of HTTP request\n");
        goto cleanup;
    }
    if (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
        printf("Failed to write hostname in HTTP request\n");
        goto cleanup;
    }
    if (!SSL_write_ex(ssl, request_end, strlen(request_end), &written)) {
        printf("Failed to write end of HTTP request\n");
        goto cleanup;
    }

    /* Get up to sizeof(buf) bytes of the response. */
    size_t readbytes;
    while (SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
        /*
         * OpenSSL does not guarantee that the returned data is a string or
         * that it is NUL terminated so we use fwrite() to write the exact
         * number of bytes that we read. The data could be non-printable or
         * have NUL characters in the middle of it. For this simple example
         * we're going to print it to stdout anyway.
         */
        fwrite(buf, 1, readbytes, stdout);
    }
    /* In case the response didn't finish with a newline we add one now */
    printf("\n");

    /*
     * Check whether we finished the while loop above normally or as the
     * result of an error. The 0 argument to SSL_get_error() is the return
     * code we received from the SSL_read_ex() call. It must be 0 in order
     * to get here. Normal completion is indicated by SSL_ERROR_ZERO_RETURN.
     */
    if (SSL_get_error(ssl, 0) != SSL_ERROR_ZERO_RETURN) {
        /*
         * Some error occurred other than a graceful close down by the
         * peer
         */
        printf ("Failed reading remaining data\n");
    }

cleanup:
    /* Clean up */
    SSL_shutdown(ssl);
    SSL_free(ssl);
    SSL_CTX_free(ctx);
    return 0;
}

DESCRIPTION

The example code above demonstrates how to establish a TLS/SSL connection to a server. It assumes a blocking socket and that the client will be making a single request to the server, which will then close the connection.

Creating the socket

The first step is to create a socket and connect it to the server. This is achieved using the standard POSIX socket functions, e.g.:

sock = socket(family, SOCK_STREAM, 0);
/* ... connect() ... */

You should consult the man pages for socket(2) and connect(2) for more information on how these functions are used. Note that the example code uses inet_pton(3) to convert the hostname into an IP address. In a real application you would want to use getaddrinfo(3) for proper IPv6 support.

See also BIO_socket(3), BIO_connect(3), BIO_closesocket(3), BIO_ADDRINFO_next(3), BIO_ADDRINFO_address(3) and BIO_ADDRINFO_free(3) for further information on the functions used here. In the above example code the hostname and port variables are strings, e.g. "www.example.com" and "443". Note also the use of the family variable, which can take the values of AF_INET or AF_INET6 based on the command line -6 option, to allow specific connections to an ipv4 or ipv6 enabled host.

Sockets created using the methods described above will automatically be blocking sockets - which is exactly what we want for this example.

Once the socket has been created and connected we need to associate it with a BIO object:

BIO *bio;
/* Create a BIO to wrap the socket */
bio = BIO_new(BIO_s_socket());
if (bio == NULL) {
    BIO_closesocket(sock);
    return NULL;
}
/*
 * Associate the newly created BIO with the underlying socket. By
 * passing BIO_CLOSE here the socket will be automatically closed when
 * the BIO is freed. Alternatively you can use BIO_NOCLOSE, in which
 * case you must close the socket explicitly when it is no longer
 * needed.
 */
BIO_set_fd(bio, sock, BIO_CLOSE);

See BIO_new(3), BIO_s_socket(3) and BIO_set_fd(3) for further information on these functions.

Finally we associate the SSL object we created earlier with the BIO using the SSL_set_bio(3) function. Note that this passes ownership of the BIO object to the SSL object. Once ownership is passed the SSL object is responsible for its management and will free it automatically when the SSL is freed. So, once SSL_set_bio(3) has been been called, you should not call BIO_free(3) on the BIO.

SSL_set_bio(ssl, bio, bio);

Setting the server's hostname

We have already connected our underlying socket to the server, but the client still needs to know the server's hostname. It uses this information for 2 key purposes and we need to set the hostname for each one.

Firstly, the server's hostname is included in the initial ClientHello message sent by the client. This is known as the Server Name Indication (SNI). This is important because it is common for multiple hostnames to be fronted by a single server that handles requests for all of them. In other words a single server may have multiple hostnames associated with it and it is important to indicate which one we want to connect to. Without this information we may get a handshake failure, or we may get connected to the "default" server which may not be the one we were expecting.

To set the SNI hostname data we call the SSL_set_tlsext_host_name(3) function like this:

/*
 * Tell the server during the handshake which hostname we are attempting
 * to connect to in case the server supports multiple hosts.
 */
if (!SSL_set_tlsext_host_name(ssl, hostname)) {
    printf("Failed to set the SNI hostname\n");
    goto end;
}

Here the "hostname" argument is a string representing the hostname of the server, e.g. "www.example.com".

Secondly, we need to tell OpenSSL what hostname we expect to see in the certificate coming back from the server. This is almost always the same one that we asked for in the original request. This is important because, without this, we do not verify that the hostname in the certificate is what we expect it to be and any certificate is acceptable unless your application explicitly checks this itself. We do this via the SSL_set1_host(3) function:

/*
 * Ensure we check during certificate verification that the server has
 * supplied a certificate for the hostname that we were expecting.
 * Virtually all clients should do this unless you really know what you
 * are doing.
 */
if (!SSL_set1_host(ssl, hostname)) {
    printf("Failed to set the certificate verification hostname");
    goto end;
}

All of the above steps must happen before we attempt to perform the handshake otherwise they will have no effect.

Performing the handshake

Before we can start sending or receiving application data over a TLS connection the TLS handshake must be performed. We can do this explicitly via the SSL_connect(3) function.

/* Do the handshake with the server */
if (SSL_connect(ssl) < 1) {
    printf("Failed to connect to the server\n");
    /*
     * If the failure is due to a verification error we can get more
     * information about it from SSL_get_verify_result().
     */
    if (SSL_get_verify_result(ssl) != X509_V_OK)
        printf("Verify error: %s\n",
            X509_verify_cert_error_string(SSL_get_verify_result(ssl)));
    goto end;
}

The SSL_connect(3) function can return 1, 0 or less than 0. Only a return value of 1 is considered a success. For a simple blocking client we only need to concern ourselves with whether the call was successful or not. Anything else indicates that we have failed to connect to the server.

A common cause of failures at this stage is due to a problem verifying the server's certificate. For example if the certificate has expired, or it is not signed by a CA in our trusted certificate store. We can use the SSL_get_verify_result(3) function to find out more information about the verification failure. A return value of X509_V_OK indicates that the verification was successful (so the connection error must be due to some other cause). Otherwise we use the X509_verify_cert_error_string(3) function to get a human readable error message.

Sending and receiving data

Once the handshake is complete we are able to send and receive application data. Exactly what data is sent and in what order is usually controlled by some application level protocol. In this example we are using HTTP 1.0 which is a very simple request and response protocol. The client sends a request to the server. The server sends the response data and then immediately closes down the connection.

To send data to the server we use the SSL_write_ex(3) function and to receive data from the server we use the SSL_read_ex(3) function. In HTTP 1.0 the client always writes data first. Our HTTP request will include the hostname that we are connecting to. For simplicity, we write the HTTP request in three chunks. First we write the start of the request. Secondly we write the hostname we are sending the request to. Finally we send the end of the request.

size_t written;
const char *request_start = "GET / HTTP/1.0\r\nConnection: close\r\nHost: ";
const char *request_end = "\r\n\r\n";
/* Write an HTTP GET request to the peer */
if (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
    printf("Failed to write start of HTTP request\n");
    goto end;
}
if (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
    printf("Failed to write hostname in HTTP request\n");
    goto end;
}
if (!SSL_write_ex(ssl, request_end, strlen(request_end), &written)) {
    printf("Failed to write end of HTTP request\n");
    goto end;
}

The SSL_write_ex(3) function returns 0 if it fails and 1 if it is successful. If it is successful then we can proceed to waiting for a response from the server.

size_t readbytes;
char buf[160];
/*
 * Get up to sizeof(buf) bytes of the response. We keep reading until the
 * server closes the connection.
 */
while (SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
    /*
    * OpenSSL does not guarantee that the returned data is a string or
    * that it is NUL terminated so we use fwrite() to write the exact
    * number of bytes that we read. The data could be non-printable or
    * have NUL characters in the middle of it. For this simple example
    * we're going to print it to stdout anyway.
    */
    fwrite(buf, 1, readbytes, stdout);
}
/* In case the response didn't finish with a newline we add one now */
printf("\n");

We use the SSL_read_ex(3) function to read the response. We don't know exactly how much data we are going to receive back so we enter a loop reading blocks of data from the server and printing each block that we receive to the screen. The loop ends as soon as SSL_read_ex(3) returns 0 - meaning that it failed to read any data.

A failure to read data could mean that there has been some error, or it could simply mean that server has sent all the data that it wants to send and has indicated that it has finished by sending a "close_notify" alert. This alert is a TLS protocol level message indicating that the endpoint has finished sending all of its data and it will not send any more. Both of these conditions result in a 0 return value from SSL_read_ex(3) and we need to use the function SSL_get_error(3) to determine the cause of the 0 return value.

/*
 * Check whether we finished the while loop above normally or as the
 * result of an error. The 0 argument to SSL_get_error() is the return
 * code we received from the SSL_read_ex() call. It must be 0 in order
 * to get here. Normal completion is indicated by SSL_ERROR_ZERO_RETURN.
 */
if (SSL_get_error(ssl, 0) != SSL_ERROR_ZERO_RETURN) {
    /*
     * Some error occurred other than a graceful close down by the
     * peer
     */
    printf ("Failed reading remaining data\n");
    goto end;
}

If SSL_get_error(3) returns SSL_ERROR_ZERO_RETURN then we know that the server has finished sending its data. Otherwise an error has occurred.

NAME

ossl-guide-tls-client-block - Simple Blocking TLS Client Example

SIMPLE BLOCKING TLS CLIENT EXAMPLE

This guide describes a simple TLS client application using OpenSSL's BIO interface. The application connects to a server, sends a message, receives a response, and then closes the connection.

The example code is designed to be run as a client, so it connects to a remote server. It uses OpenSSL's BIO interface for handling I/O. The BIO interface abstracts away the underlying I/O mechanism (e.g. sockets) and provides a consistent interface for reading and writing data.

Performing the TLS Handshake

The TLS handshake is performed by calling SSL_connect(3). This function will perform all the necessary steps to establish a secure TLS connection with the server. The function will return 1 on success, and 0 or a negative value on failure. A return value of 0 indicates that the handshake is in progress and needs to be retried. A negative return value indicates an error.

The handshake involves exchanging cryptographic information between the client and the server to agree on encryption algorithms and keys. This process is crucial for ensuring the confidentiality and integrity of the subsequent communication.

    ret = SSL_connect(ssl);
    if (ret < 1) {
        /*
         * SSL_connect() can return 0 if the handshake is still in progress.
         * We should retry in that case.
         */
        int err = SSL_get_error(ssl, ret);
        if (err == SSL_ERROR_WANT_READ || err == SSL_ERROR_WANT_WRITE) {
            /* Retry later */
            printf("Handshake still in progress, retrying...\n");
            /* In a real application, you would handle this using non-blocking
               I/O and event notification. For this blocking example, we'll
               treat it as an indication that we need more data or need to write. */
            goto end; /* Simplified for blocking example */
        } else {
            printf("SSL_connect failed: %d\n", err);
            goto end;
        }
    }

Writing and Reading Data

Once the TLS handshake is successfully completed, the client can start sending and receiving encrypted data using functions like SSL_write(3) and SSL_read(3). These functions handle the encryption and decryption of data automatically.

    /* Write data to the server */
    ret = SSL_write(ssl, msg, strlen(msg));
    if (ret < 1) {
        printf("SSL_write failed\n");
        goto end;
    }

For reading data, we typically use SSL_read_ex(3), which is a more robust function for reading data from the TLS connection. It handles various scenarios, including partial reads and errors.

    /* Read data from the server */
    char buffer[1024];
    ret = SSL_read_ex(ssl, buffer, sizeof(buffer) - 1, &bytes_read);
    if (ret < 1) {
        /*
         * SSL_ERROR_ZERO_RETURN means the peer has shut down the connection.
         * SSL_ERROR_SSL means a TLS/SSL error occurred.
         * Other errors might indicate network issues.
         */
        int err = SSL_get_error(ssl, ret);
        if (err == SSL_ERROR_ZERO_RETURN) {
            printf("Peer has closed the connection.\n");
            /* We can proceed to close our side */
        } else {
            printf("SSL_read_ex failed: %d\n", err);
            goto end;
        }
    } else {
        buffer[bytes_read] = '\0';
        printf("Received: %s\n", buffer);
    }

Closing the Connection

To properly close a TLS connection, we need to send a "close_notify" alert to the server. This is done using the SSL_shutdown(3) function. The function should be called after all data has been sent and received.

The SSL_shutdown(3) function ensures that both peers gracefully terminate the connection. It handles the exchange of closing alerts.

/*
 * The peer already shutdown gracefully (we know this because of the
 * SSL_ERROR_ZERO_RETURN above). We should do the same back.
 */
ret = SSL_shutdown(ssl);
if (ret < 1) {
    /*
     * ret < 0 indicates an error. ret == 0 would be unexpected here
     * because that means "we've sent a close_notify and we're waiting
     * for one back". But we already know we got one from the peer
     * because of the SSL_ERROR_ZERO_RETURN above.
     */
    printf("Error shutting down\n");
    goto end;
}

The SSL_shutdown(3) function will either return 1, 0, or less than 0. A return value of 1 is a success, and a return value less than 0 is an error. More precisely a return value of 1 means that we have sent a "close_notify" alert to the server, and that we have also received one back. A return value of 0 means that we have sent a "close_notify" alert to the server, but we have not yet received one back. Usually in this scenario you would call SSL_shutdown(3) again which (with a blocking socket) would block until the "close_notify" is received. However in this case we already know that the server has sent us a "close_notify" because of the SSL_ERROR_ZERO_RETURN that we received from the call to SSL_read_ex(3). So this scenario should never happen in practice. We just treat it as an error in this example.

Final clean up

Before the application exits we have to clean up some memory that we allocated. If we are exiting due to an error we might also want to display further information about that error if it is available to the user:

   /* Success! */
   res = EXIT_SUCCESS;
end:
   /*
    * If something bad happened then we will dump the contents of the
    * OpenSSL error stack to stderr. There might be some useful diagnostic
    * information there.
    */
   if (res == EXIT_FAILURE)
       ERR_print_errors_fp(stderr);
   /*
    * Free the resources we allocated. We do not free the BIO object here
    * because ownership of it was immediately transferred to the SSL object
    * via SSL_set_bio(). The BIO will be freed when we free the SSL object.
    */
   SSL_free(ssl);
   SSL_CTX_free(ctx);
   return res;

To display errors we make use of the ERR_print_errors_fp(3) function which simply dumps out the contents of any errors on the OpenSSL error stack to the specified location (in this case stderr).

We need to free up the SSL object that we created for the connection via the SSL_free(3) function. Also, since we are not going to be creating any more TLS connections we must also free up the SSL_CTX via a call to SSL_CTX_free(3).

TROUBLESHOOTING

There are a number of things that might go wrong when running the demo application. This section describes some common things you might encounter.

Failure to connect the underlying socket

This could occur for numerous reasons. For example if there is a problem in the network route between the client and the server; or a firewall is blocking the communication; or the server is not in DNS. Check the network configuration.

Verification failure of the server certificate

A verification failure of the server certificate would result in a failure when running the SSL_connect(3) function. ERR_print_errors_fp(3) would display an error which would look something like this:

Verify error:unable to get local issuer certificate
40E74AF1F47F0000:error:0A000086:SSL routines:tls_post_process_server_certificate:certificate verify failed:ssl/statem/statem_clnt.c:2069:

A server certificate verification failure could be caused for a number of reasons. For example

Failure to correctly setup the trusted certificate store
See the page ossl-guide-tls-introduction(7) and check that your trusted certificate store is correctly configured
Unrecognised CA
If the CA used by the server's certificate is not in the trusted certificate store for the client then this will cause a verification failure during connection. Often this can occur if the server is using a self-signed certificate (i.e. a test certificate that has not been signed by a CA at all).
Missing intermediate CAs
This is a server misconfiguration where the client has the relevant root CA in its trust store, but the server has not supplied all of the intermediate CA certificates between that root CA and the server's own certificate. Therefore a trust chain cannot be established.
Mismatched hostname
If for some reason the hostname of the server that the client is expecting does not match the hostname in the certificate then this will cause verification to fail.
Expired certificate
The date that the server's certificate is valid to has passed.

The "unable to get local issuer certificate" we saw in the example above means that we have been unable to find the issuer of the server's certificate (or one of its intermediate CA certificates) in our trusted certificate store (e.g. because the trusted certificate store is misconfigured, or there are missing intermediate CAs, or the issuer is simply unrecognised).
