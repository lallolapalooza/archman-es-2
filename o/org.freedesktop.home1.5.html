NOMBRE

org.freedesktop.home1 - La interfaz D-Bus de systemd-homed

INTRODUCCIÓN

systemd-homed.service(8) es un servicio del sistema que puede utilizarse para crear, eliminar, cambiar o inspeccionar áreas de inicio. Esta página describe la interfaz D-Bus.

EL OBJETO MANAGER

El servicio expone las siguientes interfaces en el objeto Manager en el bus:

Métodos

GetHomeByName() devuelve información básica del usuario (un subconjunto mínimo del registro completo del usuario), dado un nombre de usuario. La información proporcionada se parece más o menos a lo que devuelve getpwnam(3): el UID y GID numéricos, el nombre real, el directorio de inicio y el shell. Además, devuelve un identificador de estado que describe el estado en el que se encuentra el directorio de inicio del usuario, así como una ruta de bus que se refiere al objeto de bus que encapsula el registro del usuario y el directorio de inicio. Este objeto implementa la interfaz org.freedesktop.home1.Home documentada a continuación. Este método, y la mayoría de los otros en esta interfaz que toman nombres de usuario, intentarán usar el área de inicio del llamante si el nombre de usuario especificado es una cadena vacía.

GetHomeByUID() es similar a GetHomeByName() pero obtiene la información basándose en el UID numérico del usuario.

GetUserRecordByName() es también similar a GetHomeByName() pero devuelve los datos completos del registro de usuario en formato JSON en lugar de los registros desglosados. Un booleano devuelto adicional indica si el registro está completo o no. Un registro se considera completo cuando se incluye su sección "privileged", e incompleto si se eliminó (ver Registros de Usuario JSON[1] para detalles sobre las diversas secciones de un registro de usuario). Generalmente, solo los clientes privilegiados y los clientes que se ejecutan bajo la identidad del propio usuario obtienen acceso a la sección "privileged" y, por lo tanto, verán registros completos.

GetUserRecordByUID() es similar a GetUserRecordByName() pero devuelve el registro de usuario que coincide con el UID numérico especificado.

ListHomes() devuelve una matriz de todos los usuarios administrados localmente. La matriz contiene los mismos campos que devuelve GetHomeByName(): nombre de usuario, UID numérico, estado, GID numérico, nombre real, directorio de inicio, shell y ruta de bus del objeto de bus coincidente.

ActivateHome() activa (es decir, monta) el directorio de inicio del usuario especificado. El segundo argumento debe contener un registro de usuario que consista únicamente en una sección "secret" (todas las demás secciones deben eliminarse, ver Registros de Usuario JSON[1] para detalles), y debe contener solo las credenciales secretas necesarias para desbloquear el directorio de inicio. Típicamente, un cliente invocaría esta función primero con un registro completamente vacío (lo que podría ser suficiente si se configura la autenticación de un solo factor con un token de seguridad enchufado), y luego volvería a intentarlo con un registro poblado con más información, dependiendo del código de error devuelto, en caso de que se necesiten más credenciales. Esta función es síncrona y regresa solo después de que el directorio de inicio se haya activado por completo (o la operación haya fallado), lo que puede llevar algún tiempo. Los clientes deben estar preparados para ello y, por lo general, deben extender el tiempo de espera de la llamada al método D-Bus en consecuencia. Este método es equivalente al método Activate() en la interfaz org.freedesktop.home1.Home documentada a continuación, pero puede ser llamado en el objeto manager y toma un nombre de usuario como argumento adicional.

ActivateHomeIfReferenced() es idéntico a ActivateHome(). Sin embargo, la llamada solo tiene éxito si el directorio de inicio está actualmente referenciado. Útil en conjunto con RefHomeUnrestricted(), que permite crear una referencia a un directorio de inicio incluso si el directorio de inicio no está activo.

DeactivateHome() desactiva (es decir, desmonta) el directorio de inicio del usuario especificado. Es equivalente al método Deactivate() en la interfaz org.freedesktop.home1.Home documentada a continuación.

RegisterHome() registra un nuevo directorio de inicio localmente. Recibe el registro de usuario JSON como único argumento (que típicamente excluye la sección "secret"). Registrar un directorio de inicio simplemente hace que el registro del usuario sea conocido por el sistema, no crea un directorio de inicio ni nada parecido (se espera que ya exista, o se cree más tarde). Esta operación es útil para registrar directorios de inicio localmente que no se encuentran donde systemd-homed.service los encontraría automáticamente.

AdoptHome() también registra un nuevo directorio de inicio localmente. Toma una ruta a un directorio de inicio y lo registrará localmente. Esto solo funciona para directorios de inicio *.home y *.homedir/. Esta operación se realiza automáticamente para todas las áreas de inicio de este tipo que aparecen en /home/, pero puede solicitarse explícitamente con esta llamada para directorios en otros lugares. Las flags deben establecerse en cero, actualmente.

UnregisterHome() anula el registro de un directorio de inicio existente. Toma un nombre de usuario como argumento y deshace lo que hace RegisterHome(). No intenta eliminar el directorio de inicio en sí, solo lo anula del registro.

it con el sistema local. Tenga en cuenta que si el directorio principal se coloca donde systemd-homed.service lo busca de todos modos, esta llamada solo deshará la fijación (ver más abajo), pero el registro permanecerá conocido por systemd-homed.service y se listará entre los registros conocidos. Dado que el registro de usuario está incrustado en el directorio principal, esta operación generalmente no descarta datos que pertenecen al usuario o a su registro. Este método es equivalente a Unregister() en la interfaz org.freedesktop.home1.Home.

CreateHome() registra y crea un nuevo directorio principal. Esto toma un registro de usuario JSON completamente especificado como argumento (incluida la sección "secret"). Esto registra el registro de usuario localmente y crea un directorio principal que coincide con él, dependiendo de la configuración especificada en el registro en combinación con la configuración local.

CreateHomeEx() es como CreateHome(), pero permite que el directorio principal se cree con un directorio de blobs precargado (ver Directorios de Blobs de Registros de Usuario[2] para más información). Esto se puede hacer a través del diccionario pasado como argumento blobs a este método: los valores son descriptores de archivos abiertos a archivos regulares, y las claves son los nombres de archivo que deben contener los datos de cada archivo respectivo en el directorio de blobs. Tenga en cuenta que por razones de seguridad, los descriptores de archivo pasados a este método deben tener privilegios suficientes para leer su archivo de destino y, por lo tanto, no pueden ser "O_PATH"; esto se hace para garantizar que el llamador tenga permiso real para leer el archivo que está solicitando publicar en los directorios de blobs. Si el registro de usuario pasado como primer argumento contiene un campo "blobManifest", se aplicará; de lo contrario, se generará e insertará un campo "blobManifest" en el registro. El argumento flags puede utilizarse para futuras expansiones, pero por ahora pase 0.

RealizeHome() crea un directorio principal cuyo registro de usuario ya está registrado localmente. Esto toma un nombre de usuario más un registro de usuario que consiste solo en la sección "secret". Invocar RegisterHome() seguido de RealizeHome() es en gran medida equivalente a llamar a CreateHome(), excepto que este último combina ambas operaciones de forma atómica. Este método es equivalente a Realize() en la interfaz org.freedesktop.home1.Home.

RemoveHome() anula el registro de un registro de usuario localmente y elimina el directorio principal que le pertenece, si es accesible. Toma un nombre de usuario como argumento. Este método es equivalente a Remove() en la interfaz org.freedesktop.home1.Home.

FixateHome() "fija" un directorio principal descubierto automáticamente. systemd-homed.service descubre automáticamente directorios principales insertados o enchufados y los agrega a la lista en tiempo de ejecución de registros de usuario que administra. Un registro de usuario descubierto de esa manera puede ser "fijado", en cuyo caso se copia del directorio principal, al almacenamiento persistente, para fijar la asignación de UID/GID del registro, y extraer datos adicionales del registro de usuario (típicamente previamente cifrados) del directorio principal. Un directorio principal debe ser fijado antes de poder iniciar sesión en él. Esta llamada al método toma un nombre de usuario y un registro de usuario JSON que consta solo de la sección "secret" como argumento. Este método es equivalente a Fixate() en la interfaz org.freedesktop.home1.Home.

AuthenticateHome() verifica contraseñas u otras credenciales de autenticación asociadas con el directorio principal. Toma un nombre de usuario y un registro de usuario JSON que consiste solo en la sección "secret" como argumento. Tenga en cuenta que muchas de las otras llamadas a métodos autentican al usuario primero, para ejecutar alguna otra operación. Esta llamada al método solo autentica y no ejecuta ninguna operación adicional. Al igual que ActivateHome(), generalmente se invoca primero con un registro de usuario JSON vacío, que luego se rellena para intentos posteriores con datos de autenticación adicionales suministrados. Esta llamada al método es equivalente a Authenticate() en la interfaz org.freedesktop.home1.Home.

UpdateHome() actualiza un registro de usuario registrado localmente. Toma un registro de usuario JSON completamente especificado como argumento (posiblemente incluyendo la sección "secret"). Un usuario con un nombre y dominio coincidentes debe estar registrado localmente, y la marca de tiempo del último cambio del registro recién proporcionado debe ser más reciente que el registro de usuario preexistente. Tenga en cuenta que esta operación solo actualiza el registro de usuario, no propaga contraseñas/tokens de autenticación del registro de usuario al backend de almacenamiento, ni redimensiona el backend de almacenamiento. Típicamente, un directorio principal se actualiza primero, y luego la contraseña del almacenamiento subyacente se actualiza usando ChangePasswordHome(), así como el almacenamiento se redimensiona usando ResizeHome(). Este método es equivalente a Update() en la interfaz org.freedesktop.home1.Home.

UpdateHomeEx() es como UpdateHome(), pero permite cambios en el directorio de blobs (ver Directorios de Blobs de Registros de Usuario[2] para más información). El argumento blobs funciona de la misma manera que CreateHomeEx(), así que consulte allí para ver los detalles. El nuevo contenido del directorio de blobs pasado a este método reemplazará completamente el directorio de blobs existente del usuario. El argumento flags se puede usar para personalizar aún más el comportamiento de este método mediante flags definidas como sigue:

#define SD_HOMED_UPDATE_OFFLINE (UINT64_C(1) << 0)

Cuando se establece SD_HOMED_UPDATE_OFFLINE (0x01), no se intenta actualizar las copias del registro de usuario y del directorio de blobs que están incrustadas en el directorio principal. Los cambios se almacenarán, sin embargo, y pueden propagarse al directorio principal la próxima vez que se reconcilie (lo más probable es que cuando el usuario inicie sesión por próxima vez). Tenga en cuenta que cualquier cambio realizado con este flag establecido puede perderse si el área principal tiene un registro más reciente, lo que puede suceder si el área principal se actualiza en otra máquina después de esta llamada al método. Este método es equivalente a UpdateEx() en la interfaz org.freedesktop.home1.Home.

ResizeHome() redimensiona el almacenamiento asociado con un registro de usuario. Toma un nombre de usuario, un tamaño de disco en bytes y opcionalmente un registro de usuario que consta solo de la sección "secret" como argumentos. Si el tamaño se especifica como UINT64_MAX, el almacenamiento se redimensiona al tamaño ya especificado en el registro de usuario. Típicamente, si el registro de usuario se actualiza usando UpdateHome() arriba, esto se usa para propagar el tamaño configurado allí al backend de almacenamiento subyacente. Este método es equivalente a Resize() en la interfaz org.freedesktop.home1.Home.

ChangePasswordHome() cambia las contraseñas/tokens de autenticación de un directorio principal. Toma un nombre de usuario y dos objetos de registro de usuario JSON, cada uno compuesto solo por la sección "secret", para las contraseñas/tokens de autenticación antiguos y nuevos. Si el registro de usuario con los nuevos datos de contraseñas/tokens de autenticación se especifica como vacío, la configuración del registro de usuario existente se propaga al almacenamiento del directorio principal. Esto se usa típicamente después de que un registro de usuario se actualiza usando UpdateHome() para propagar los secretos/tokens de autenticación al almacenamiento. Antecedentes: dependiendo del backend, las credenciales de autenticación del usuario se almacenan en varios lugares: el registro de usuario mantenido en el host, el registro de usuario mantenido en el directorio principal y la ranura del volumen LUKS cifrado. Si el directorio principal se usa temporalmente en una máquina diferente y la contraseña se cambia allí, y luego se devuelve a la máquina original, las contraseñas de los tres pueden desincronizarse. Al emitir ChangePasswordHome(), las tres ubicaciones se actualizan para que coincidan con la información más reciente. Este método es equivalente a ChangePassword() en la interfaz org.freedesktop.home1.Home.

LockHome() suspende temporalmente el acceso a un directorio principal, vaciando las claves criptográficas de la memoria. Esto solo se admite en algunos backends y generalmente se hace durante la suspensión del sistema, para asegurar efectivamente los directorios principales mientras el sistema duerme. Toma un nombre de usuario como único argumento. Si una aplicación intenta acceder a un directorio principal mientras está bloqueado, normalmente se congelará hasta que el directorio principal se desbloquee de nuevo. Este método es equivalente a Lock() en la interfaz org.freedesktop.home1.Home.

UnlockHome() deshace el efecto de LockHome(). Toma un nombre de usuario y un registro de usuario que consta solo de la sección "secret" como argumentos. Este método es equivalente a Unlock() en la interfaz org.freedesktop.home1.Home.

AcquireHome() activa o desbloquea un directorio principal en un modo de operación con conteo de referencias. Toma un nombre de usuario y un registro de usuario que consta solo de la sección "secret" como argumento. Si el directorio principal aún no está activo, se activa. Si está actualmente bloqueado, se desbloquea. Después de la finalización, se devuelve una referencia a la activación/desbloqueo del directorio principal a través de un descriptor de archivo. Cuando el último cliente que adquirió dicho descriptor de archivo lo cierra, el directorio principal se desactiva automáticamente de nuevo. Este método se invoca típicamente cuando un usuario inicia sesión, y el descriptor de archivo se mantiene hasta que el usuario cierra sesión de nuevo, asegurando así que el directorio principal del usuario pueda ser desmontado automáticamente de nuevo, de forma robusta, cuando el usuario cierra sesión. El tercer argumento es un booleano que indica si el cliente que invoca la llamada puede volver a autenticarse automáticamente cuando el sistema regresa de la suspensión. Debe ser establecido por todos los clientes que implementan una pantalla de bloqueo segura que se ejecuta fuera del contexto del usuario, que se activa cuando el sistema regresa de la suspensión y se puede utilizar para recuperar las credenciales para desbloquear el directorio principal del usuario. Si un directorio principal tiene al menos un cliente con una referencia abierta al directorio principal que no admite esto, no se suspende automáticamente en la suspensión del sistema; de lo contrario, sí lo hace. Este método es equivalente a Acquire() en la interfaz org.freedesktop.home1.Home.

RefHome() es similar a AcquireHome() pero no toma ningún registro de usuario con sección "secret", es decir, tomará una referencia adicional a un directorio principal ya activado/desbloqueado sin intentar activarlo/desbloquearlo él mismo. Fallará si el directorio principal aún no está activado. Este método es equivalente a Ref() en la interfaz org.freedesktop.home1.Home.

RefHomeUnrestricted() es idéntico a RefHome() pero tiene éxito incluso si el área principal no está activa actualmente. Esto es útil en conjunto con ActivateHomeIfReferenced().

ReleaseHome() libera un directorio principal de nuevo, si todos los descriptores de archivo que lo referencian ya están cerrados, que se adquirieron a través de AcquireHome() o RefHome(). Tenga en cuenta que esta llamada no causa realmente la desactivación del directorio principal (que ocurre automáticamente cuando se cierra el último descriptor de archivo de referencia), sino que es simplemente un mecanismo de sincronización que permite retrasar la terminación de la sesión del usuario hasta que se complete cualquier desactivación desencadenada. Este método es equivalente t

o Release() en la interfaz org.freedesktop.home1.Home.

LockAllHomes() bloquea todos los directorios de inicio activos que solo tienen referencias que optaron por la suspensión automática durante la suspensión del sistema. Esto se invoca normalmente de forma automática poco antes de la suspensión del sistema.

DeactivateAllHomes() desactiva todas las áreas de inicio que están actualmente activas. Esto se invoca normalmente de forma automática poco antes del apagado del sistema.

Rebalance() reequilibra de forma síncrona el espacio libre en disco entre las áreas de inicio. Esto solo ejecuta una operación si al menos un área de inicio que utiliza el backend LUKS2 está activa y tiene el reequilibrio habilitado, y en caso contrario es una operación nula (NOP).

ListSigningKeys() obtiene una lista de las claves de firma de áreas de inicio instaladas. Devuelve una matriz de nombres de claves con sus datos de clave pública codificados en PEM. Cada entrada también viene con un valor de banderas que actualmente no se utiliza y debe ser ignorado por los clientes.

GetSigningKey() obtiene la parte pública codificada en PEM de la clave de firma de área de inicio especificada del nombre especificado. También devuelve un valor de banderas actualmente no utilizado que debe ser ignorado. El parámetro flags debe establecerse en cero, actualmente.

AddSigningKey() agrega una nueva clave a la lista de claves de firma de áreas de inicio. Toma una cadena de nombre (de forma libre, adecuada como nombre de archivo, con el sufijo ".public"), los datos de clave pública codificados en PEM y un valor de banderas actualmente no utilizado que debe ser cero. El parámetro flags debe establecerse en cero, actualmente.

RemoveSigningKey() elimina una clave de la lista de claves de firma de áreas de inicio. Toma el nombre de la clave a eliminar y un valor de banderas actualmente no utilizado que debe ser cero. El parámetro flags debe establecerse en cero, actualmente.

Propiedades

AutoLogin expone una matriz de estructuras que consisten en el nombre de usuario, el nombre del asiento y la ruta del objeto de un objeto de directorio de inicio. Aquí se listan todos los usuarios gestionados localmente que tienen el campo "autoLogin" establecido, con el nombre del asiento al que están asociados. Un gestor de pantalla puede observar esta propiedad y pre-rellenar la pantalla de inicio de sesión con los usuarios expuestos de esta manera.

Métodos

Activate(), ActivateIfReferenced(), Deactivate(), Unregister(), Realize(), Remove(), Fixate(), Authenticate(), Update(), UpdateEx(), Resize(), ChangePassword(), Lock(), Unlock(), Acquire(), Ref(), RefUnrestricted(), Release(), operan como sus contrapartes coincidentes en la interfaz org.freedesdel.home1.Manager (ver arriba). La principal diferencia es que son métodos de los objetos del directorio de inicio y, por lo tanto, no llevan un parámetro de nombre de usuario adicional. Cuál de las dos variantes de métodos llamar depende de los identificadores del usuario conocidos en el lado del cliente: si solo se conoce el nombre de usuario, es preferible utilizar los métodos del objeto manager ya que operan solo con nombres de usuario. Los clientes también pueden operar fácilmente en su propia área de inicio utilizando los métodos del objeto manager con una cadena vacía como nombre de usuario. Si el cliente ya tiene la ruta del objeto del directorio de inicio adquirida de alguna manera, sin embargo, es preferible operar en los objetos org.freedesktop.home1.Home en su lugar.

Propiedades

UserName contiene el nombre de usuario de la cuenta de usuario/directorio de inicio.

UID contiene el UID numérico de UNIX de la cuenta de usuario.

UnixRecord contiene una estructura que encapsula los seis campos que típicamente contiene una estructura passwd (el campo de contraseña está suprimido).

State expone el estado actual del directorio de inicio.

UserRecord contiene la cadena completa del registro de usuario JSON de la cuenta de usuario.
