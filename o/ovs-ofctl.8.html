NOMBRE

ovs-ofctl - administrar switches OpenFlow

SINOPSIS

ovs-ofctl [opciones] comando [switch] [args...]

DESCRIPCIÓN

ovs-ofctl es una herramienta de línea de comandos para monitorizar y administrar switches OpenFlow. También puede mostrar el estado actual de un switch OpenFlow, incluyendo sus características, configuración y entradas de tabla. Debería funcionar con cualquier switch OpenFlow, no solo con Open vSwitch.

Comandos de Administración de Switches OpenFlow

Estos comandos permiten a ovs-ofctl monitorizar y administrar un switch OpenFlow. Es capaz de mostrar el estado actual de un switch, incluyendo características, configuración y entradas de tabla.

La mayoría de estos comandos toman un argumento que especifica el método para conectarse a un switch OpenFlow. Los siguientes métodos de conexión son soportados:

ssl:host[:puerto]

tcp:host[:puerto]
El puerto especificado en el host dado, que puede ser expresado como un nombre DNS (si se compiló con la biblioteca unbound) o una dirección IP en formato IPv4 o IPv6. Envuelve las direcciones IPv6 entre corchetes, por ejemplo, tcp:[::1]:6653. En Linux, usa %dispositivo para designar un alcance para direcciones de enlace de nivel de enlace IPv6, por ejemplo, tcp:[fe80::1234%eth0]:6653. Para ssl, las opciones --private-key, --certificate y --ca-cert son obligatorias.
Si no se especifica el puerto, se usará el valor predeterminado 6653.
unix:archivo
En POSIX, un socket de servidor de dominio Unix llamado archivo.
En Windows, conéctate a una canalización con nombre local que está representada por un archivo creado en la ruta archivo para imitar el comportamiento de un socket de dominio Unix.
archivo
Esto es una abreviatura de unix:archivo, siempre que archivo no contenga dos puntos.
bridge
Esto es una abreviatura de unix:/run/openvswitch/bridge.mgmt, siempre que bridge no contenga dos puntos.
[tipo@]dp
Intenta buscar el bridge asociado con dp y abrirlo como se indica arriba. Si se proporciona tipo, especifica el proveedor del datapath de dp, de lo contrario se asume el proveedor predeterminado system.
show switch
Imprime en la consola información sobre switch, incluyendo información sobre sus tablas de flujos y puertos.
dump-tables switch
Imprime en la consola estadísticas para cada una de las tablas de flujos utilizadas por switch.
dump-table-features switch
Imprime en la consola las características de cada una de las tablas de flujos utilizadas por switch.
dump-table-desc switch
Imprime en la consola la configuración de cada una de las tablas de flujos utilizadas por switch para OpenFlow 1.4+.
mod-table switch tabla configuración
Este comando configura los ajustes de la tabla de flujos en switch para la tabla OpenFlow tabla, que puede expresarse como un número o (a menos que se especifique --no-names) un nombre.
Las configuraciones disponibles dependen de la versión de OpenFlow en uso. En OpenFlow 1.1 y 1.2 (que deben habilitarse con la opción -O) solamente, mod-table configura el comportamiento cuando no se encuentra ningún flujo al buscar un paquete en una tabla de flujos. Los siguientes valores de configuración están disponibles:
drop
Descarta el paquete.
continue
Continúa a la siguiente tabla en la canalización. (Así es como un switch OpenFlow 1.0 siempre maneja los paquetes que no coinciden con ningún flujo, en tablas distintas de la última).
controller
Envía al controlador. (Así es como un switch OpenFlow 1.0 siempre maneja los paquetes que no coinciden con ningún flujo en la última tabla).
En OpenFlow 1.3 y posteriores (que deben habilitarse con la opción -O) y Open vSwitch 2.11 y posteriores solamente, mod-table puede cambiar el nombre de una tabla:
name:nuevo-nombre
Cambia el nombre de la tabla a nuevo-nombre. Usa un nuevo-nombre vacío para borrar el nombre. (Esto será ineficaz si el nombre se establece a través de la columna name en la tabla Flow_Table en la base de datos Open_vSwitch como se describe en ovs-vswitchd.conf.db(5).)
En OpenFlow 1.4 y posteriores (que deben habilitarse con la opción -O) solamente, mod-table configura el comportamiento cuando un controlador intenta agregar un flujo a una tabla de flujos que está llena. Los siguientes valores de configuración están disponibles:
evict
Elimina un flujo existente de la tabla de flujos, de acuerdo con el algoritmo descrito para la tabla Flow_Table en ovs-vswitchd.conf.db(5).
noevict
Rechaza agregar el nuevo flujo. (La expulsión aún puede estar habilitada a través de la columna overflow_policy en la tabla Flow_Table documentada en ovs-vswitchd.conf.db(5).)
vacancy:bajo,alto
Habilita el envío de eventos de vacancia a los controladores usando mensajes TABLE_STATUS, basado en los umbrales de porcentaje bajo y alto.
novacancy
Deshabilita los eventos de vacancia.
dump-ports switch [netdev]
Imprime en la consola estadísticas para los dispositivos de red asociados con switch. Si se especifica netdev, solo se imprimirán las estadísticas asociadas con ese dispositivo. netdev puede ser un número de puerto asignado por OpenFlow o un nombre de dispositivo, por ejemplo, eth0.
dump-ports-desc switch [puerto]
Imprime en la consola información detallada sobre los dispositivos de red asociados con switch. Para volcar solo un puerto específico, especifica su número como puerto. De lo contrario, si puerto se omite, o si se especifica como ANY, se imprimirán todos los puertos. Esto es un subconjunto de la información proporcionada por el comando show.
Si la conexión con switch negocia OpenFlow 1.0, 1.1 o 1.2, este comando utiliza una extensión de OpenFlow implementada solo en Open vSwitch (versión 1.7 y posteriores).
Solo OpenFlow 1.5 y posteriores soportan volcar un puerto específico. Versiones anteriores de OpenFlow siempre vuelcan todos los puertos.
mod-port switch puerto acción
Modifica las características del puerto puerto en switch. puerto puede ser un número de puerto OpenFlow o un nombre (a menos que se especifique --no-names) o la palabra clave LOCAL (la forma preferida de referirse al puerto local de OpenFlow). La acción puede ser cualquiera de las siguientes:

up

down
Habilita o deshabilita la interfaz. Esto es equivalente a ip link set up o ip link set down en un sistema Unix.
stp

no
Habilita o deshabilita el protocolo Spanning Tree.
interface puerto
Establece el puerto como un puerto de tipo interfaz. Esto es equivalente a up o down, pero con la capacidad de especificar los parámetros que se obtienen mediante la configuración de la interfaz de red.
mirror puerto
Establece el puerto como un puerto de tipo espejo.
normal
Establece el puerto como un puerto de tipo normal.
ofp_1_0
Establece el puerto como un puerto de tipo 1.0.
ofp_1_1
Establece el puerto como un puerto de tipo 1.1.
ofp_1_2
Establece el puerto como un puerto de tipo 1.2.
ofp_1_3
Establece el puerto como un puerto de tipo 1.3.
ofp_1_4
Establece el puerto como un puerto de tipo 1.4.
ofp_1_5
Establece el puerto como un puerto de tipo 1.5.

Las variables son: speed, duplex, hwaddr, remote_hwaddr, link_res, advertised_speed, advertised_duplex, advertised_pause_control, advertised_flow_control, force_speed, force_duplex, force_adv_speed, force_adv_duplex, force_adv_pause_control, force_adv_flow_control, rx_pause, tx_pause, rx_flow_control, tx_flow_control, rate, burst, priority, queues.

Configura el tratamiento de fragmentos IPv4 e IPv6 de switch. Las opciones para frag_mode son:
normal
Los fragmentos pasan a través de la tabla de flujos como paquetes no fragmentados. Los puertos TCP, los puertos UDP y los campos de tipo y código ICMP se establecen siempre a 0, incluso para fragmentos donde esa información estaría disponible (fragmentos con desplazamiento 0). Este es el modo de manejo de fragmentos predeterminado para un switch OpenFlow.
drop
Los fragmentos se descartan sin pasar por la tabla de flujos.
reassemble
El switch reensambla los fragmentos en paquetes IP completos antes de pasarlos a través de la tabla de flujos. Open vSwitch no implementa este modo de manejo de fragmentos.

Los fragmentos pasan a través de la tabla de flujos como paquetes no fragmentados. Los puertos TCP, los puertos UDP y los campos de tipo y código ICMP están disponibles para la coincidencia de fragmentos con desplazamiento 0, y se establecen a 0 en fragmentos con desplazamiento distinto de cero. ct-flush switch [zone=N] [mark=X[/M]] [labels=Y[/N]] [ct-orig-tuple [ct-reply-tuple]]
Vacía las entradas de conexión en switch basándose en zone, mark, labels y tuplas de seguimiento de conexión ct-[orig|reply]-tuple.
Si no se proporciona ct-[orig|reply]-tuple, vacía todas las entradas de conexión. Si se especifica zone, solo vacía las conexiones en zone. si se proporciona mark o labels, vaciará solo las entradas que coincidan con los mark/labels específicos.
Si se proporciona ct-[orig|reply]-tuple, vacía la entrada de conexión especificada por ct-[orig|reply]-tuple en zone. La zona se establece por defecto en 0 si no se proporciona. La mark y las labels se establecen por defecto en "0/0" si no se proporcionan. El rastreador de conexiones en el espacio de usuario requiere vaciado con la tupla original pre-NAT y de lo contrario se generará un registro de advertencia. La tupla puede ser parcial y eliminará todas las conexiones que coincidan con los campos especificados. Para especificar solo ct-reply-tuple, proporcione una cadena vacía como ct-orig-tuple.
Nota: Actualmente existe una limitación para la coincidencia de ICMP; para coincidir parcialmente con parámetros ICMP, ct-[orig|reply]-tuple debe incluir el origen o el destino de la IP.
Un ejemplo de una tupla ct-[orig|reply]-tuple ICMP IPv4:
"ct_nw_src=10.1.1.1,ct_nw_dst=10.1.1.2,ct_nw_proto=1,icmp_type=8,icmp_code=0,icmp_id=10"
Un ejemplo de una tupla ct-[orig|reply]-tuple TCP IPv6:
"ct_ipv6_src=fc00::1,ct_ipv6_dst=fc00::2,ct_nw_proto=6,ct_tp_src=1,ct_tp_dst=2"
Este comando utiliza una extensión de Open vSwitch que solo está en Open vSwitch 3.1 y posteriores. El soporte para coincidir con mark y labels solo está en Open vSwitch 3.3 y posteriores.

Comandos de tabla TLV de túnel de switch OpenFlow

Open vSwitch mantiene una tabla de mapeo entre los TLV de opción de túnel (definidos por <clase, tipo, longitud>) y los campos NXM tun_metadatan, donde n varía de 0 a 63, que pueden ser operados para propósitos de coincidencias, acciones, etc. Esta tabla TLV puede ser utilizada para TLV de opciones Geneve u otros protocolos con opciones en el mismo formato TLV que las opciones Geneve. Este mapeo debe ser especificado explícitamente por el usuario a través de los siguientes comandos.

Se especifica un mapeo TLV con la sintaxis {clase=clase,tipo=tipo,len=longitud}->tun_metadatan. Cuando existe un mapeo de opción para un tun_metadatan dado, la coincidencia en el campo definido se vuelve posible, por ejemplo:

ovs-ofctl add-tlv-map br0 "{class=0xffff,type=0,len=4}->tun_metadata0"

ovs-ofctl add-flow br0 tun_metadata0=1234,actions=controller

No se debe modificar un mapeo mientras esté en uso activo por un flujo. El resultado de hacerlo no está definido.

Estos comandos son extensiones de Nicira a OpenFlow y requieren Open vSwitch 2.5 o posterior.

add-tlv-map switch opción[,opción]...
Añade cada opción a las tablas del switch. Los campos duplicados son rechazados.
del-tlv-map switch [opción[,opción]]...
Elimina cada opción de la tabla del switch, o todos los mapeos TLV de opciones si no se especifica ninguna opción. Los campos que no están mapeados se ignoran.
dump-tlv-map switch
Muestra los campos actualmente mapeados en la tabla de opciones del switch, así como las capacidades del switch.

Comandos de Monitoreo de Switch OpenFlow

snoop switch
Se conecta al switch e imprime en la consola todos los mensajes OpenFlow recibidos. A diferencia de otros comandos de ovs-ofctl, si switch es el nombre de un puente, entonces el comando snoop se conecta a un socket de dominio Unix llamado /run/openvswitch/switch.snoop. ovs-vswitchd escucha en dicho socket para cada puente y le envía todos los mensajes OpenFlow enviados o recibidos de su controlador OpenFlow configurado. Por lo tanto, este comando puede usarse para ver la actividad del protocolo OpenFlow entre un switch y su controlador.
Cuando un switch tiene más de un controlador configurado, solo se muestra el tráfico hacia y desde un único controlador. Si ninguno de los controladores está configurado como primario o secundario (usando una extensión de Nicira a OpenFlow 1.0 o 1.1, o una solicitud estándar en OpenFlow 1.2 o posterior), se elige un controlador de forma arbitraria entre ellos. Si hay un controlador primario, se elige; de lo contrario, si hay algún controlador que no sea primario o secundario, se elige uno de forma arbitraria; de lo contrario, se elige un controlador secundario de forma arbitraria. Esta elección se realiza una vez al momento de la conexión y no cambia a medida que los controladores reconfiguran sus roles.
Si un switch no tiene ningún controlador configurado, o si el controlador configurado está desconectado, no se envía tráfico, por lo que el monitoreo no mostrará ningún tráfico.
monitor switch [miss-len] [invalid_ttl] [watch:[spec...]]
Se conecta al switch e imprime en la consola todos los mensajes OpenFlow recibidos. Normalmente, switch debe especificar el nombre de un puente en la base de datos de ovs-vswitchd. Esto solo está disponible en OpenFlow 1.0 como una extensión de Nicira.
Si se proporciona miss-len, ovs-ofctl envía un mensaje OpenFlow ``set configuration'' al configurar la conexión que solicita miss-len bytes de cada paquete que no coincide con la tabla de flujo. Open vSwitch no envía estos ni otros mensajes asíncronos a una conexión cliente de ovs-ofctl monitor a menos que se especifique un valor distinto de cero en este argumento. (Por lo tanto, si no se especifica miss-len, normalmente se imprimirá muy poco tráfico.)
Si se pasa invalid_ttl, ovs-ofctl envía un mensaje OpenFlow ``set configuration'' al configurar la conexión que solicita INVALID_TTL_TO_CONTROLLER, de modo que ovs-ofctl monitor pueda recibir mensajes ``packet-in'' cuando el TTL llega a cero en la acción dec_ttl. Solo OpenFlow 1.1 y 1.2 soportan invalid_ttl; Open vSwitch también lo implementa para OpenFlow 1.0 como una extensión.
watch:[spec...] hace que ovs-ofctl envíe un mensaje de extensión Nicira ``monitor request'' al switch al configurar la conexión. Este mensaje hace que el switch envíe información sobre los cambios en la tabla de flujo a medida que ocurren. La siguiente sintaxis de spec separada por comas está disponible:
!initial
No informar del contenido inicial de la tabla de flujo del switch.
!add
No informar de los flujos añadidos recientemente.
!delete
No informar de los flujos eliminados.
!modify
No informar de las modificaciones a los flujos existentes.
!own
Abreviar los cambios realizados en la tabla de flujo por la propia conexión de ovs-ofctl al switch. (Estos solo podrían ocurrir usando el comando ofctl/send descrito a continuación en COMANDOS DE GESTIÓN EN TIEMPO DE EJECUCIÓN.)
!actions
No informar de las acciones como parte de las actualizaciones de flujo.
table=tabla
Limita el monitoreo a la tabla con el table dado, que puede expresarse como un número entre 0 y 254 o (a menos que se especifique --no-names) un nombre. Por defecto, se monitorean todas las tablas.
out_port=puerto
Si se establece, solo se monitorean los flujos que salen al puerto. El puerto puede ser un número de puerto OpenFlow o una palabra clave (por ejemplo, LOCAL).
out_group=grupo
Si se establece, solo se monitorean los flujos que salen al número de grupo. Este campo requiere OpenFlow 1.4 (-OOpenFlow14) o posterior.
campo=valor
Monitorea solo los flujos que tienen el campo especificado como el valor dado. Se puede usar cualquier sintaxis válida para coincidir en dump-flows.

Comandos de Switch y Controlador OpenFlow

Los siguientes comandos, al igual que los de la sección anterior, pueden aplicarse a switches OpenFlow, utilizando cualquiera de los métodos de conexión descritos en esa sección. A diferencia de esos comandos, estos también pueden aplicarse a controladores OpenFlow.

probe objetivo
Envía un único mensaje de eco-solicitud OpenFlow a objetivo y espera la respuesta. Con la opción -t o --timeout, este comando puede probar si un switch o controlador OpenFlow está activo y funcionando.
ping objetivo [n]
Envía una serie de 10 paquetes de solicitud de eco a objetivo y mide el tiempo de cada respuesta. Los paquetes de solicitud de eco consisten en una cabecera OpenFlow más n bytes (por defecto: 64) de carga útil generada aleatoriamente. Esto mide la latencia de las solicitudes individuales.
benchmark objetivo n conteo
Envía conteo paquetes de solicitud de eco que consisten cada uno en una cabecera OpenFlow más n bytes de carga útil y espera cada respuesta. Informa del tiempo total requerido. Esta es una medida del ancho de banda máximo hacia objetivo para viajes de ida y vuelta de mensajes de n bytes.

Otros Comandos

ofp-parse archivo
Lee el archivo (o stdin si archivo es -) como una serie de mensajes OpenFlow en el formato binario utilizado en una conexión OpenFlow, y los imprime en la consola. Esto puede ser útil para imprimir mensajes OpenFlow capturados de un stream TCP.
ofp-parse-pcap archivo [puerto...]
Lee el archivo, que debe estar en formato PCAP utilizado por herramientas de captura de red como tcpdump o wireshark, extrae todos los streams TCP para conexiones OpenFlow, e imprime los mensajes OpenFlow en esas conexiones en formato legible por humanos en stdout.
Las conexiones OpenFlow se distinguen por el número de puerto TCP. Los paquetes que no son OpenFlow se ignoran. Por defecto, los datos en los puertos TCP 6633 y 6653 se consideran OpenFlow. Especifique uno o más argumentos de puerto para anular el valor predeterminado.
Este comando no puede imprimir tráfico cifrado SSL/TLS de manera útil. No entiende IPv6.

Sintaxis de Flujo

Algunos comandos de ovs-ofctl aceptan un argumento que describe uno o más flujos. Dichas descripciones de flujo comprenden una serie de asignaciones campo=valor, separadas por comas o espacios en blanco. (Incrustar espacios en una descripción de flujo normalmente requiere comillas para evitar que el shell divida la descripción en múltiples argumentos.)

Las descripciones de flujo deben estar en forma normal. Esto significa que un flujo solo puede especificar un valor para un campo L3 si también especifica un protocolo L2 particular, y que un flujo solo puede especificar un campo L4 si también especifica tipos de protocolo L2 y L3 particulares. Por ejemplo, si el tipo de protocolo L2 d

ovs-fields(7) describe los campos compatibles y cómo coincidirlos. Además de los campos de coincidencia, los comandos que operan en flujos aceptan algunos pares clave-valor adicionales:

table=tabla
Para los comandos de volcado de flujos, limita los flujos volcados a los de la tabla, que puede expresarse como un número entre 0 y 255 o (a menos que se especifique --no-names) un nombre. Si no se especifica (o si se especifica 255 como tabla), entonces se volcán los flujos de todas las tablas.
Para los comandos de modificación de tablas de flujos, el comportamiento varía según la versión de OpenFlow utilizada para conectarse al switch:
OpenFlow 1.0
OpenFlow 1.0 no admite table para modificar flujos. ovs-ofctl saldrá con un error si se especifica table (aparte de table=255) para un switch que solo admite OpenFlow 1.0.
En OpenFlow 1.0, el switch elige la tabla en la que insertar un nuevo flujo. El switch de software Open vSwitch siempre elige la tabla 0. Otros datapath de Open vSwitch y otras implementaciones de OpenFlow pueden elegir tablas diferentes.
El comportamiento de OpenFlow 1.0 en Open vSwitch para modificar o eliminar flujos depende de si se utiliza --strict. Sin --strict, el comando se aplica a los flujos coincidentes en todas las tablas. Con --strict, el comando operará sobre cualquier flujo coincidente único en cualquier tabla; no hará nada si hay coincidencias en más de una tabla. (La distinción entre estos comportamientos solo importa si también se utilizaron comandos que no son de OpenFlow 1.0, ya que OpenFlow 1.0 por sí solo no puede agregar flujos con los mismos criterios de coincidencia a múltiples tablas).
OpenFlow 1.0 con extensión table_id
Open vSwitch implementa una extensión de OpenFlow que permite al controlador especificar la tabla en la que operar. ovs-ofctl habilita automáticamente la extensión cuando se especifica table y se utiliza OpenFlow 1.0. ovs-ofctl detecta automáticamente si el switch admite la extensión. Hasta la fecha, se sabe que esta extensión solo está implementada por Open vSwitch.
Con esta extensión, ovs-ofctl opera en la tabla solicitada cuando se especifica table, y actúa como se describe para OpenFlow 1.0 arriba cuando no se especifica table (o para table=255).
OpenFlow 1.1
OpenFlow 1.1 requiere que los comandos de modificación de tablas de flujos especifiquen una tabla. Cuando no se especifica table (o se especifica table=255), ovs-ofctl utiliza la tabla 0 por defecto.
OpenFlow 1.2 y posteriores
OpenFlow 1.2 y posteriores permiten comandos de eliminación de flujos, pero no otros comandos de modificación de tablas de flujos, para operar en todas las tablas de flujos, con el comportamiento descrito anteriormente para OpenFlow 1.0.
duration=...

n_packet=...

n_bytes=...
ovs-ofctl ignora las asignaciones a estos ``campos'' para permitir que la salida del comando dump-flows se utilice como entrada para otros comandos que analizan flujos.

Los comandos add-flow, add-flows y mod-flows requieren un campo adicional, que debe ser el último campo especificado:

actions=[accion][,accion...]
Especifica una lista separada por comas de acciones a realizar en un paquete cuando la entrada de flujo coincida. Si no se especifica ninguna accion, los paquetes que coincidan con el flujo se descartan. Consulte ovs-actions(7) para obtener detalles sobre la sintaxis y la semántica de las acciones. K

Un identificador opaco llamado cookie se puede utilizar como manejador para identificar un conjunto de flujos:

cookie=valor
Se puede asociar una cookie con un flujo utilizando los comandos add-flow, add-flows y mod-flows. El valor puede ser cualquier número de 64 bits y no necesita ser único entre los flujos. Si se omite este campo, se utiliza el valor de cookie predeterminado de 0.
cookie=valor/máscara
Al utilizar NXM, la cookie se puede usar como manejador para consultar, modificar y eliminar flujos. Se pueden proporcionar valor y máscara para los comandos del-flows, mod-flows, dump-flows y dump-aggregate para limitar las cookies coincidentes. Un bit 1 en la máscara indica que el bit correspondiente en la cookie debe coincidir exactamente, y un bit 0 descarta ese bit. Se puede usar una máscara de -1 para coincidir exactamente con una cookie.
El comando mod-flows puede actualizar las cookies de los flujos que coinciden con una cookie especificando el campo cookie dos veces (una vez con una máscara para la coincidencia y otra sin ella para indicar el nuevo valor):
ovs-ofctl mod-flows br0 cookie=1,actions=normal
Cambia las cookies de todos los flujos a 1 y cambia sus acciones a normal.
ovs-ofctl mod-flows br0 cookie=1/-1,cookie=2,actions=normal
Actualiza las cookies con un valor de 1 a 2 y cambia sus acciones a normal.
La capacidad de coincidir con cookies se agregó en Open vSwitch 1.5.0.

El siguiente campo adicional establece la prioridad para los flujos agregados por los comandos add-flow y add-flows. Para mod-flows y del-flows cuando se especifica --strict, la prioridad debe coincidir junto con el resto de la especificación del flujo. Para mod-flows sin --strict, la prioridad solo es significativa si el comando crea un nuevo flujo, es decir, mod-flows no estricto no coincide con la prioridad y no cambiará la prioridad de los flujos existentes. Otros comandos no permiten especificar la prioridad.

priority=valor
La prioridad con la que una entrada comodín coincidirá en comparación con otras. valor es un número entre 0 y 65535, inclusive. Un valor más alto coincidirá antes que uno más bajo. Una entrada de coincidencia exacta siempre tendrá prioridad sobre una entrada que contenga comodines, por lo que tiene un valor de prioridad implícito de 65535. Al agregar un flujo, si el campo no se especifica, la prioridad del flujo será por defecto 32768.
OpenFlow deja el comportamiento indefinido cuando dos o más flujos con la misma prioridad pueden coincidir con un solo paquete. Algunos usuarios esperan un comportamiento ``sensato'', como que los flujos más específicos tengan precedencia sobre los menos específicos, pero OpenFlow no lo especifica y Open vSwitch no lo implementa. Por lo tanto, los usuarios deben tener cuidado de utilizar prioridades para garantizar el comportamiento que esperan.

Los comandos add-flow, add-flows y mod-flows admiten las siguientes opciones adicionales. Estas opciones solo afectan a los flujos nuevos. Por lo tanto, para add-flow y add-flows, estas opciones son siempre significativas, pero para mod-flows solo son significativas si el comando crea un nuevo flujo, es decir, sus valores no actualizan ni afectan a los flujos existentes.

idle_timeout=segundos
Hace que el flujo expire después del número dado de segundos de inactividad. Un valor de 0 (el predeterminado) evita que un flujo expire debido a la inactividad.
hard_timeout=segundos
Hace que el flujo expire después del número dado de segundos, independientemente de la actividad. Un valor de 0 (el predeterminado) no le da al flujo un plazo de expiración fijo.
importance=valor
Establece la importancia de un flujo. El mecanismo de descarte de entradas de flujo puede utilizar la importancia como factor para decidir qué flujo descartar. Un valor de 0 (el predeterminado) hace que el flujo no sea descartable por importancia. Especifique un valor entre 0 y 65535.
Solo OpenFlow 1.4 y posteriores admiten importance.
send_flow_rem
Marca el flujo con una bandera que hace que el switch genere un mensaje de ``flujo eliminado'' y lo envíe a los controladores interesados cuando el flujo expire o sea eliminado posteriormente.
check_overlap
Obliga al switch a comprobar que la coincidencia del flujo no se superpone con la de ningún otro flujo con la misma prioridad en la misma tabla. (Esta comprobación es costosa, por lo que es mejor evitarla).
reset_counts
Cuando se especifica esta bandera en un flujo que se está agregando a un switch, y el switch ya tiene un flujo con una coincidencia idéntica, un switch OpenFlow 1.2 (o posterior) reinicia los contadores de paquetes y bytes del flujo a 0. Sin la bandera, se conservan los contadores de paquetes y bytes.
Los switches OpenFlow 1.0 y 1.1 siempre reinician los contadores en esta situación, como si reset_counts siempre se especificara.
Open vSwitch 1.10 agregó soporte para reset_counts.
no_packet_counts

no_byte_counts
Agregar estas banderas a un flujo indica a un switch OpenFlow 1.3 (o posterior) que el controlador no necesita contadores de paquetes o bytes, respectivamente, para el flujo. Algunas implementaciones de switch podrían lograr un mayor rendimiento o reducir el consumo de recursos cuando se utilizan estas banderas. Estas banderas no proporcionan ningún beneficio a la implementación del switch de software Open vSwitch.
OpenFlow 1.2 y anteriores no admiten estas banderas.
Open vSwitch 1.10 agregó soporte para no_packet_counts y no_byte_counts.

Salida de entrada de tabla

Los comandos dump-tables y dump-aggregate imprimen información sobre las entradas de las tablas de un plano de datos. Cada línea de salida es una entrada de flujo como se describe en Sintaxis de flujo, más algunos campos adicionales:

El tiempo, en segundos, que la entrada ha estado en la tabla. secs incluye tanta precisión como el conmutador proporciona, posiblemente hasta resolución de nanosegundos.

El número de paquetes que han coincidido con la entrada.
n_bytes
El número total de bytes de los paquetes que han coincidido con la entrada.

El número entero de segundos desde que se agregó o modificó el flujo. hard_age se muestra solo si difiere de la parte entera de duration. (Esto está separado de duration porque mod-flows reinicia el temporizador hard_timeout sin poner a cero duration.)

El número entero de segundos que han transcurrido sin que ningún paquete atraviese el flujo.

Algunos comandos de ovs-ofctl aceptan un argumento que describe uno o más grupos. Dichas descripciones de flujo comprenden una serie de asignaciones de campo=valor, separadas por comas o espacios en blanco. (Incrustar espacios en una descripción de grupo normalmente requiere comillas para evitar que el shell divida la descripción en múltiples argumentos.). El ID de grupo entero del grupo. Cuando se especifica este campo en del-groups o dump-groups, la palabra clave "all" puede usarse para designar todos los grupos. Este campo es obligatorio.
type=tipo
El tipo del grupo. Los comandos add-group, add-groups y mod-groups requieren este campo. Está prohibido para otros comandos. Las siguientes palabras clave designan los tipos permitidos:
all
Ejecuta todos los cubos del grupo.
select
Ejecuta un cubo del grupo, balanceando entre los cubos según sus pesos. Para seleccionar un cubo, para cada cubo activo, Open vSwitch calcula un hash de los datos del flujo con el ID del cubo y lo multiplica por el peso del cubo para obtener una ``puntuación'', y luego selecciona el cubo con la puntuación más alta. Use selection_method para controlar los datos del flujo utilizados para la selección.
indirect
Ejecuta el único cubo del grupo.
ff

fast_failover
Ejecuta el primer cubo activo del grupo que está asociado con un puerto o grupo activo.
command_bucket_id=id
El cubo sobre el que operar. Los comandos insert-buckets y remove-buckets requieren este campo. Está prohibido para otros comandos. id puede ser un entero o una de las siguientes palabras clave:
all
Opera sobre todos los cubos del grupo. Solo válido cuando se usa con el comando remove-buckets, en cuyo caso el efecto es eliminar todos los cubos del grupo.
first
Opera sobre el primer cubo presente en el grupo. En el caso del comando insert-buckets, el efecto es insertar nuevos cubos justo antes del primer cubo ya presente en el grupo; o reemplazar los cubos del grupo si no hay cubos ya presentes en el grupo. En el caso del comando remove-buckets, el efecto es eliminar el primer cubo del grupo; o no hacer nada si no hay cubos presentes en el grupo.
last
Opera sobre el último cubo presente en el grupo. En el caso del comando insert-buckets, el efecto es insertar nuevos cubos justo después del último cubo ya presente en el grupo; o reemplazar los cubos del grupo si no hay cubos ya presentes en el grupo. En el caso del comando remove-buckets, el efecto es eliminar el último cubo del grupo; o no hacer nada si no hay cubos presentes en el grupo.
Si id es un entero, entonces debe corresponder al bucket_id de un cubo presente en el grupo. En el caso del comando insert-buckets, el efecto es insertar cubos justo antes del cubo en el grupo cuyo bucket_id es id. En el caso del comando iremove-buckets, el efecto es eliminar el cubo en el grupo cuyo bucket_id es id. Es un error si no hay un cubo presente en el grupo cuyo bucket_id sea id.
selection_method=método
El método de selección utilizado para seleccionar un cubo para un grupo de tipo select. Esta es una cadena de 1 a 15 bytes de longitud conocida por las capas inferiores. Este campo es opcional para los comandos add-group, add-groups y mod-group en grupos de tipo select. Prohibido de lo contrario. Si no se especifica ningún método de selección, Open vSwitch hasta la versión 2.9 aplica el método hash con campos predeterminados. A partir de la versión 2.10, Open vSwitch utiliza por defecto el método dp_hash con un algoritmo de hash L3/L4 simétrico, siempre que los cubos de grupo ponderados puedan mapearse a valores dp_hash con suficiente precisión. En la versión 2.10 esto se limitó a un máximo de 64 cubos, y en la versión 2.17 el límite se elevó a 256 cubos. En esos casos raros, Open vSwitch 2.10 y posteriores vuelven al método hash con el conjunto predeterminado de campos de hash.
dp_hash
Usa un valor hash calculado por el plano de datos. El algoritmo de hash varía entre las diferentes implementaciones del plano de datos. dp_hash utiliza los 32 bits superiores de selection_method_param como selector del algoritmo de hash del plano de datos. Los valores admitidos son 0 (correspondiente al cálculo de hash sobre la tupla IP 5) y 1 (correspondiente a un cálculo de hash *simétrico* sobre la tupla IP 5). La selección de campos específicos con la opción fields no es compatible con dp_hash). Los 32 bits inferiores se utilizan como base del hash.
Usar dp_hash tiene la ventaja de que no requiere que los flujos de plano de datos generados coincidan exactamente con campos de encabezado de paquete adicionales. Por ejemplo, incluso si varias conexiones TCP con hash en diferentes cubos de grupo seleccionados tienen números de puerto de origen diferentes, generalmente todas se manejarán con un pequeño conjunto de flujos de plano de datos ya establecidos, lo que resulta en una menor latencia para los paquetes SYN de TCP. La desventaja es que los flujos de plano de datos compartidos deben coincidir con cada paquete dos veces, ya que el cálculo del valor hash del plano de datos solo ocurre cuando es necesario, y se requiere una segunda coincidencia para coincidir con algunos bits de él.

Group Syntax The group table commands accept arguments that describe groups. A group description comprises a list of field=value assignments, separated by whitespace or commas. The type of group. This keyword is required. The following keywords designate the allowed group types: all All buckets in the group are executed. The algorithm used for selecting a bucket within a group. The allowed methods are: hash A hash computed over the fields specified with the fields option. See below. If no hash fields are specified, hash defaults to a symmetric hash over the combination of MAC addresses, VLAN tags, Ether type, IP addresses and L4 port numbers. hash uses the selection_method_param as the hash basis. For example, if the TCP source port is hashed, the created datapath flows will match the specific TCP source port value present in the packet received. The algorithm uses the selection_method_param to determine the hash basis. The choice of fields is determined by the fields option. This double-matching incurs a small additional latency cost for each packet, but this latency is orders of magnitude less than the latency of creating new datapath flows for new TCP connections.

Every OpenFlow port has a name and a number, and every OpenFlow flow table has a number and sometimes a name. By default, ovs-ofctl commands accept both port and table names and numbers, and they display port and table names if ovs-ofctl is running on an interactive console, numbers otherwise. Ejecuta ovs-ofctl como un proceso en segundo plano. El proceso se bifurca, y en el hijo inicia una nueva sesión, cierra los descriptores de archivo estándar (lo que tiene el efecto secundario de deshabilitar el registro en la consola) y cambia su directorio actual a la raíz (a menos que se especifique --no-chdir). Después de que el hijo complete su inicialización, el padre sale. ovs-ofctl se desconecta solo al ejecutar los comandos monitor o snoop.
--monitor
Crea un proceso adicional para monitorear el demonio ovs-ofctl. Si el demonio muere debido a una señal que indica un error de programación (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU, o SIGXFSZ) entonces el proceso monitor inicia una nueva copia de él. Si el demonio muere o sale por alguna otra razón, el proceso monitor sale.
Esta opción se usa normalmente con --detach, pero también funciona sin ella.
--no-chdir
Por defecto, cuando se especifica --detach, ovs-ofctl cambia su directorio de trabajo actual a la raíz después de desconectarse. De lo contrario, invocar ovs-ofctl desde un directorio elegido descuidadamente impediría al administrador desmontar el sistema de archivos que contiene ese directorio.
Especificar --no-chdir suprime este comportamiento, impidiendo que ovs-ofctl cambie su directorio de trabajo actual. Esto puede ser útil para recolectar core dumps, ya que es un comportamiento común escribir core dumps en el directorio de trabajo actual y la raíz no es un buen directorio para usar.
Esta opción no tiene efecto cuando no se especifica --detach.
--no-self-confinement
Por defecto, el demonio intentará auto-restringirse para trabajar con archivos bajo directorios conocidos determinados durante la compilación. Es mejor adherirse a este comportamiento predeterminado y no usar esta bandera a menos que se utilice algún otro Control de Acceso para restringir el demonio. Tenga en cuenta que, a diferencia de otras implementaciones de control de acceso que normalmente se aplican desde el espacio del kernel (por ejemplo, DAC o MAC), la auto-restricción se impone desde el propio demonio del espacio de usuario y, por lo tanto, no debe considerarse una estrategia de restricción completa, sino más bien una capa adicional de seguridad.
--user
Hace que ovs-ofctl se ejecute como un usuario diferente especificado en "user:group", lo que reduce la mayoría de los privilegios de root. También se permiten formas cortas "user" y ":group", asumiendo el usuario o grupo actual respectivamente. Solo los demonios iniciados por el usuario root aceptan este argumento.
En Linux, a los demonios se les otorgarán CAP_IPC_LOCK y CAP_NET_BIND_SERVICES antes de renunciar a los privilegios de root. A los demonios que interactúan con un datapath, como ovs-vswitchd, se les otorgarán tres capacidades adicionales, a saber, CAP_NET_ADMIN, CAP_NET_BROADCAST y CAP_NET_RAW. El cambio de capacidad se aplicará incluso si el nuevo usuario es root.
En Windows, esta opción no está soportada actualmente. Por razones de seguridad, especificar esta opción hará que el proceso demonio no se inicie.
--unixctl=socket
Establece el nombre del socket de control en el que ovs-ofctl escucha los comandos de gestión en tiempo de ejecución (ver COMANDOS DE GESTIÓN EN TIEMPO DE EJECUCIÓN, más abajo). Si socket no comienza con /, se interpreta como relativo a /run/openvswitch. Si no se utiliza --unixctl en absoluto, el socket predeterminado es /run/openvswitch/ovs-ofctl.pid.ctl, donde pid es el ID de proceso de ovs-ofctl.
En Windows se utiliza una tubería con nombre local para escuchar los comandos de gestión en tiempo de ejecución. Se crea un archivo en la ruta absoluta apuntada por socket o, si no se utiliza --unixctl, se crea un archivo como ovs-ofctl.ctl en el directorio OVS_RUNDIR configurado. El archivo existe solo para imitar el comportamiento de un socket de dominio Unix.
Especificar none para socket deshabilita la función de socket de control.

Opciones de Infraestructura de Clave Pública

-p privkey.pem

--private-key=privkey.pem
Especifica un archivo PEM que contiene la clave privada utilizada como identidad de ovs-ofctl para las conexiones SSL/TLS salientes.
-c cert.pem

--certificate=cert.pem
Especifica un archivo PEM que contiene un certificado que certifica la clave privada especificada en -p o --private-key como confiable. El certificado debe estar firmado por la autoridad certificadora (CA) que el par en las conexiones SSL/TLS utilizará para verificarlo.
-C cacert.pem

--ca-cert=cacert.pem
Especifica un archivo PEM que contiene el certificado de CA que ovs-ofctl debería utilizar para verificar los certificados presentados por los pares SSL/TLS. (Este puede ser el mismo certificado que los pares SSL/TLS usan para verificar el certificado especificado en -c o --certificate, o puede ser uno diferente, dependiendo del diseño de PKI en uso.)
-C none

--ca-cert=none
Deshabilita la verificación de los certificados presentados por los pares SSL/TLS. Esto introduce un riesgo de seguridad, ya que significa que los certificados no pueden ser verificados como los de hosts conocidos y confiables.
-v[spec]

--verbose=[spec]
Establece los niveles de registro. Sin ningún spec, establece el nivel de registro para cada módulo y destino a dbg. De lo contrario, spec es una lista de palabras separadas por espacios, comas o dos puntos, hasta una de cada categoría a continuación:
  • Un nombre de módulo válido, como se muestra en el comando vlog/list en ovs-appctl(8), limita el cambio del nivel de registro al módulo especificado.
  • syslog, console o file, para limitar el cambio del nivel de registro solo al registro del sistema, a la consola o a un archivo, respectivamente. (Si se especifica --detach, ovs-ofctl cierra sus descriptores de archivo estándar, por lo que el registro en la consola no tendrá efecto).
En la plataforma Windows, syslog se acepta como palabra y solo es útil junto con la opción --syslog-target (la palabra no tiene efecto de lo contrario).
•
off, emer, err, warn, info o dbg, para controlar el nivel de registro. Los mensajes de la gravedad dada o superior se registrarán, y los mensajes de menor gravedad se filtrarán. off filtra todos los mensajes. Consulte ovs-appctl(8) para obtener una definición de cada nivel de registro.
La capitalización no es significativa dentro de spec.
Independientemente de los niveles de registro establecidos para file, el registro en un archivo no tendrá lugar a menos que también se especifique --log-file (ver más abajo).
Para compatibilidad con versiones anteriores de OVS, any se acepta como palabra pero no tiene efecto.
-v

--verbose
Establece el nivel máximo de verbosidad del registro, equivalente a --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Establece el patrón de registro para destination a pattern. Consulte ovs-appctl(8) para una descripción de la sintaxis válida para pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Establece la instalación RFC5424 del mensaje de registro. facility puede ser uno de kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 o local7. Si esta opción no se especifica, se utiliza daemon como valor predeterminado para el syslog del sistema local y se utiliza local0 al enviar un mensaje al destino proporcionado a través de la opción --syslog-target.
--log-file[=file]
Habilita el registro en un archivo. Si se especifica file, entonces se utiliza como el nombre exacto para el archivo de registro. El nombre de archivo de registro predeterminado que se utiliza si se omite file es /var/log/openvswitch/ovs-ofctl.log.
--syslog-target=host:puerto
Envía mensajes syslog al puerto UDP en host, además del syslog del sistema. El host debe ser una dirección IP numérica, no un nombre de host.
--syslog-method=método
Especifica el método con el que se deben enviar los mensajes syslog al demonio syslog. Se admiten las siguientes formas:
  • libc, usa la función syslog() de libc. La desventaja de usar esta opción es que libc agrega un prefijo fijo a cada mensaje antes de que se envíe realmente al demonio syslog a través del socket de dominio UNIX /dev/log.
  • unix:archivo, usa directamente un socket de dominio UNIX. Es posible especificar un formato de mensaje arbitrario con esta opción. Sin embargo, las versiones rsyslogd 8.9 y anteriores usan una función de análisis codificada de todos modos, lo que limita el uso del socket de dominio UNIX. Si deseas usar un formato de mensaje arbitrario con versiones anteriores de rsyslogd, utiliza en su lugar un socket UDP a la dirección IP de localhost.
  • udp:ip:puerto, usa un socket UDP. Con este método es posible utilizar un formato de mensaje arbitrario también con versiones anteriores de rsyslogd. Al enviar mensajes syslog a través de un socket UDP, se deben tener precauciones adicionales, por ejemplo, el demonio syslog debe estar configurado para escuchar en el puerto UDP especificado, las reglas iptables accidentales podrían interferir con el tráfico syslog local y existen algunas consideraciones de seguridad que se aplican a los sockets UDP, pero no a los sockets de dominio UNIX.
  • null, descarta todos los mensajes registrados en syslog.
El valor predeterminado se toma de la variable de entorno OVS_SYSLOG_METHOD; si no está establecida, el valor predeterminado es libc.
--color[=cuándo]
Colorea la salida (para algunos comandos); cuándo puede ser never (nunca), always (siempre) o auto (predeterminado).

Solo algunos comandos admiten la coloración de la salida. Los nombres de colores y los colores predeterminados pueden cambiar en futuras versiones.

La variable de entorno OVS_COLORS se puede usar para especificar colores definidos por el usuario y otros atributos utilizados para resaltar varias partes de la salida. Si está establecida, su valor es una lista separada por dos puntos de capacidades que, por defecto, es ac:01;31:dr=34:le=31:pm=36:pr=35:sp=33:vl=32. Las capacidades admitidas se diseñaron inicialmente para colorear flujos del comando ovs-ofctl dump-flows switch, y son las siguientes.

ac=01;31
Subcadena SGR para la palabra clave actions= en un flujo. El valor predeterminado es un texto frontal rojo en negrita.
dr=34
Subcadena SGR para la palabra clave drop. El valor predeterminado es un texto frontal azul oscuro.
le=31
Subcadena SGR para la palabra clave learn= en un flujo. El valor predeterminado es un texto frontal rojo.
pm=36
Subcadena SGR para los nombres de atributos de coincidencia de flujo. El valor predeterminado es un texto frontal cian.
pr=35
Subcadena SGR para palabras clave en un flujo que van seguidas de argumentos entre paréntesis. El valor predeterminado es un texto frontal magenta.
sp=33
Subcadena SGR para algunas palabras clave especiales en un flujo, en particular: table=, priority=, load:, output:, move:, group:, CONTROLLER:, set_field:, resubmit:, exit. El valor predeterminado es un texto frontal amarillo.
vl=32
Subcadena SGR para un atributo de coincidencia de flujo solitario sin nombre de campo. El valor predeterminado es un texto frontal verde.

Consulte la sección Selección de Representación Gráfica (SGR) en la documentación del terminal de texto que se está utilizando para conocer los valores permitidos y su significado como atributos de caracteres.

COMANDOS DE GESTIÓN EN TIEMPO DE EJECUCIÓN

ovs-appctl(8) puede enviar comandos a un proceso ovs-ofctl en ejecución. Los comandos compatibles se enumeran a continuación.

exit
Hace que ovs-ofctl termine de forma controlada. Este comando solo se aplica al ejecutar los comandos monitor o snoop.
ofctl/set-output-file archivo
Hace que toda la salida posterior se dirija a archivo en lugar de a stderr. Este comando solo se aplica al ejecutar los comandos monitor o snoop.
ofctl/send ofmsg...
Envía cada ofmsg, especificado como una secuencia de dígitos hexadecimales que expresan un mensaje OpenFlow, en la conexión OpenFlow. Este comando solo es útil al ejecutar el comando monitor.
ofctl/packet-out packet-out
Envía un mensaje OpenFlow PACKET_OUT especificado en la Sintaxis Packet-Out, en la conexión OpenFlow. Consulte la sección Sintaxis Packet-Out para obtener más información. Este comando solo es útil al ejecutar el comando monitor.
ofctl/barrier
Envía una solicitud de barrera OpenFlow en la conexión OpenFlow y espera una respuesta. Este comando solo es útil para el comando monitor.

EJEMPLOS

Los siguientes ejemplos asumen que ovs-vswitchd tiene un puente llamado br0 configurado.

ovs-ofctl dump-tables br0
Imprime las estadísticas de tablas del switch. (Esto es más interesante después de que haya pasado algo de tráfico.)
ovs-ofctl dump-flows br0
Imprime las entradas de flujo en el switch.
ovs-ofctl add-flow table=0 actions=learn(table=1,hard_timeout=10, NXM_OF_VLAN_TCI[0..11],output:NXM_OF_IN_PORT[]), resubmit(,1)
ovs-ofctl add-flow table=1 priority=0 actions=flood Implementa un switch de aprendizaje de MAC de nivel 2 utilizando learn.
ovs-ofctl add-flow br0 'table=0,priority=0 actions=load:3->NXM_NX_REG0[0..15],learn(table=0,priority=1,idle_timeout=10,NXM_OF_ETH_SRC[],NXM_OF_VLAN_TCI[0..11],output:NXM_NX_REG0[0..15]),output:2
En este uso de una acción learn, el primer paquete de cada MAC de origen se enviará al puerto 2. Los paquetes posteriores se enviarán al puerto 3, con un tiempo de espera inactivo de 10 segundos. Se aceptan nombres de campos NXM y nombres de campos de coincidencia, por ejemplo, NXM_NX_REG0 o reg0 para el primer registro, y los corchetes vacíos se pueden omitir.
Se pueden encontrar ejemplos adicionales documentados como parte de secciones relacionadas.
