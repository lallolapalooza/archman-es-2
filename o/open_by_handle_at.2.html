NOMBRE

name_to_handle_at, open_by_handle_at - obtener un manejador para una ruta y abrir un archivo a través de un manejador

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#define _GNU_SOURCE         /* Véase feature_test_macros(7) */
#include <fcntl.h>
int name_to_handle_at(int dirfd, const char *path,
                      struct file_handle *handle,
                      int *mount_id, int flags);
int open_by_handle_at(int mount_fd, struct file_handle *handle,
                      int flags);

DESCRIPCIÓN

Las llamadas al sistema name_to_handle_at() y open_by_handle_at() dividen la funcionalidad de openat(2) en dos partes: name_to_handle_at() devuelve un manejador opaco que corresponde a un archivo especificado; open_by_handle_at() abre el archivo correspondiente a un manejador devuelto por una llamada anterior a name_to_handle_at() y devuelve un descriptor de archivo abierto.

name_to_handle_at()

La llamada al sistema name_to_handle_at() devuelve un manejador de archivo y un ID de montaje correspondientes al archivo especificado por los argumentos dirfd y path. El manejador de archivo se devuelve a través del argumento handle, que es un puntero a una estructura del siguiente tipo:


struct file_handle {
    unsigned int  handle_bytes;   /* Tamaño de f_handle [entrada, salida] */
    int           handle_type;    /* Tipo de manejador [salida] */
    unsigned char f_handle[0];    /* Identificador de archivo (dimensionado por
                                     el llamador) [salida] */
};

Es responsabilidad del llamador asignar la estructura con un tamaño lo suficientemente grande como para contener el manejador devuelto en f_handle. Antes de la llamada, el campo handle_bytes debe inicializarse para contener el tamaño asignado para f_handle. (La constante MAX_HANDLE_SZ, definida en <fcntl.h>, especifica el tamaño máximo esperado para un manejador de archivo. No es un límite superior garantizado, ya que los sistemas de archivos futuros pueden requerir más espacio.) Tras el retorno exitoso, el campo handle_bytes se actualiza para contener el número de bytes escritos realmente en f_handle.

El llamador puede descubrir el tamaño requerido para la estructura file_handle realizando una llamada en la que handle->handle_bytes sea cero; en este caso, la llamada falla con el error EOVERFLOW y handle->handle_bytes se establece para indicar el tamaño requerido; el llamador puede entonces usar esta información para asignar una estructura del tamaño correcto (ver EJEMPLOS más abajo). Se requiere cierta precaución aquí, ya que EOVERFLOW también puede indicar que no hay un manejador de archivo disponible para este nombre en particular en un sistema de archivos que normalmente soporta la búsqueda por manejador de archivo. Este caso se puede detectar cuando el error EOVERFLOW se devuelve sin que handle_bytes haya aumentado.

Aparte del uso del campo handle_bytes, el llamador debe tratar la estructura file_handle como un tipo de dato opaco: los campos handle_type y f_handle se pueden usar en una llamada posterior a open_by_handle_at(). El llamador también puede usar el file_handle opaco para comparar la identidad de los objetos del sistema de archivos que se consultaron en diferentes momentos y posiblemente en diferentes rutas. El subsistema fanotify(7) puede informar eventos con un registro de información que contiene un file_handle para identificar el objeto del sistema de archivos.

El argumento flags es una máscara de bits construida mediante la combinación OR de cero o más de AT_HANDLE_FID, AT_HANDLE_MNT_ID_UNIQUE, AT_HANDLE_CONNECTABLE, AT_EMPTY_PATH y AT_SYMLINK_FOLLOW, descritos a continuación.

Cuando flags contiene el flag AT_HANDLE_FID (desde Linux 6.5), el llamador indica que el file_handle devuelto se necesita para identificar el objeto del sistema de archivos, y no para abrir el archivo más tarde, por lo que se debe esperar que una llamada posterior a open_by_handle_at() con el file_handle devuelto pueda fallar.

Cuando flags contiene el flag AT_HANDLE_MNT_ID_UNIQUE (desde Linux 6.12), el llamador indica que el ancho del búfer mount_id es de al menos 64 bits, y entonces el ID de montaje devuelto en ese búfer es el ID de montaje único, similar al devuelto por statx(2) con el flag STATX_MNT_ID_UNIQUE.

Cuando flags contiene el flag AT_HANDLE_CONNECTABLE (desde Linux 6.13), el llamador indica que el file_handle devuelto se necesita para abrir un archivo con una ruta conocida más tarde, por lo que se debe esperar que una llamada posterior a open_by_handle_at() con el file_handle devuelto pueda fallar si el archivo se movió, pero de lo contrario, se espera que la ruta del archivo abierto sea visible desde el enlace mágico /proc/pid/fd/*. Este flag no se puede usar en combinación con los flags AT_HANDLE_FID y/o AT_EMPTY_PATH.

Juntos, los argumentos path y dirfd identifican el archivo para el cual se debe obtener un manejador. Hay cuatro casos distintos:

•
Si path es una cadena no vacía que contiene una ruta absoluta, entonces se devuelve un manejador para el archivo al que se refiere esa ruta. En este caso, se ignora dirfd.
•
Si path es una cadena no vacía que contiene una ruta relativa y dirfd tiene el valor especial AT_FDCWD, entonces path se interpreta en relación con el directorio de trabajo actual del llamador, y se devuelve un manejador para el archivo al que se refiere.
•
Si path es una cadena no vacía que contiene una ruta relativa y dirfd es un descriptor de archivo que se refiere a un directorio, entonces path se interpreta en relación con el directorio al que se refiere dirfd, y se devuelve un manejador para el archivo al que se refiere. (Consulte openat(2) para obtener una explicación de por qué son útiles los "descriptores de archivo de directorio").
•
Si path es una cadena vacía y flags especifica el valor AT_EMPTY_PATH, entonces dirfd puede ser un descriptor de archivo abierto que se refiere a cualquier tipo de archivo, o AT_FDCWD, que significa el directorio de trabajo actual, y se devuelve un manejador para el archivo al que se refiere.

El argumento mount_id devuelve un identificador para el montaje del sistema de archivos que corresponde a path. Esto corresponde al primer campo en uno de los registros en /proc/self/mountinfo. Abrir la ruta en el quinto campo de ese registro produce un descriptor de archivo para el punto de montaje; ese descriptor de archivo puede usarse en una llamada posterior a open_by_handle_at(). mount_id se devuelve tanto para una llamada exitosa como para una llamada que resulta en el error EOVERFLOW.

Por defecto, name_to_handle_at() no desreferencia path si es un enlace simbólico, y por lo tanto devuelve un manejador para el propio enlace. Si se especifica AT_SYMLINK_FOLLOW en flags, path se desreferencia si es un enlace simbólico (para que la llamada devuelva un manejador para el archivo al que se refiere el enlace).

name_to_handle_at() no activa un montaje cuando el último componente de la ruta es un punto de montaje automático. Cuando un sistema de archivos soporta tanto manejadores de archivo como puntos de montaje automáticos, una llamada name_to_handle_at() a un punto de montaje automático devolverá con error EOVERFLOW sin haber aumentado handle_bytes. Esto puede ocurrir desde Linux 4.13 con NFS al acceder a un directorio que está en un sistema de archivos separado en el servidor. En este caso, el montaje automático se puede activar añadiendo una "/" al final de la ruta.

# NAME name_to_handle_at, open_by_handle_at - obtain and open a file by file handle # SYNOPSIS ```c #include <fcntl.h> int name_to_handle_at(int dirfd, const char *path, struct file_handle *handle, int *mount_id, int flags); int open_by_handle_at(int mount_fd, struct file_handle *handle, int flags); ``` # DESCRIPTION The **name_to_handle_at**() system call creates a file handle for the file referred to by path. The file handle is a filesystem-specific representation of a file that can be used later with **open_by_handle_at**() to open the file. The file handle is returned in the structure pointed to by handle. The first time this system call is made, handle->handle_bytes should be set to zero. On a successful call, *handle->handle_bytes* will be updated to the size of the file handle required. The caller must then allocate sufficient memory for *handle* and call **name_to_handle_at**() again. The mount_id argument is a pointer to an integer where the mount ID of the filesystem containing the file will be stored. This is the ID of the mount point where the file resides. The dirfd argument is a file descriptor referring to a directory. path is interpreted relative to the directory referred to by dirfd, unless path is an absolute pathname. If dirfd is the special value **AT_FDCWD** or path is an absolute pathname, then path can identify a file anywhere in the filesystem. The flags argument specifies how the file name lookup and handle generation should be performed. The following flags can be included: * **AT_SYMLINK_FOLLOW** If path is a symbolic link, then it is followed. By default (if this flag is not specified), name_to_handle_at() returns a handle for the symbolic link itself. * **AT_EMPTY_PATH** If path is an empty string, then refer to the file referred to by dirfd (which must refer to a directory or a process-init file descriptor). **open_by_handle_at**() opens a file using a file handle previously obtained using **name_to_handle_at**(). The mount_fd argument is a file descriptor for the mount point of the filesystem containing the file represented by the handle. This file descriptor can be obtained by opening the mount point directory itself. Alternatively, mount IDs can be obtained from `/proc/self/mountinfo` and used to find the correct mount point to open. The handle argument points to a structure containing the file handle and its size. The flags argument consists of **open**(2) flags. The flags **O_PATH** and **O_NOFOLLOW** are the only flags that are permitted and supported. If **O_PATH** is specified, the file is opened as a file descriptor that can be used in subsequent system calls as an argument to functions such as **fstat**(2), **readlinkat**(2), and **fchownat**(2). In this case, the symbolic link is not dereferenced; the **O_NOFOLLOW** flag, if specified, is ignored. The caller must have the **CAP_DAC_READ_SEARCH** capability to invoke **open_by_handle_at**(). # RETURN VALUE On success, **name_to_handle_at**() returns 0, and **open_by_handle_at**() returns a file descriptor (a nonnegative integer). In the event of an error, both system calls return -1 and set *errno* to indicate the error. # ERRORS **name_to_handle_at**() and **open_by_handle_at**() can fail for the same errors as **openat**(2). In addition, they can fail with the errors noted below. **name_to_handle_at**() can fail with the following errors: * **EFAULT** path, mount_id, or handle points outside your accessible address space. * **EINVAL** flags includes an invalid bit value or an invalid bit combination. * **EINVAL** handle->handle_bytes is greater than **MAX_HANDLE_SZ**. * **ENOENT** path is an empty string, but **AT_EMPTY_PATH** was not specified in flags. * **ENOTDIR** The file descriptor supplied in dirfd does not refer to a directory, and it is not the case that both flags includes **AT_EMPTY_PATH** and path is an empty string. * **EOPNOTSUPP** The filesystem does not support decoding of a pathname to a file handle. * **EOVERFLOW** The handle->handle_bytes value passed into the call was too small. When this error occurs, handle->handle_bytes is updated to indicate the required size for the handle. **open_by_handle_at**() can fail with the following errors: * **EBADF** mount_fd is not an open file descriptor. * **EBADF** path is relative but dirfd is neither **AT_FDCWD** nor a valid file descriptor. * **EFAULT** handle points outside your accessible address space. * **EINVAL** handle->handle_bytes is greater than **MAX_HANDLE_SZ** or is equal to zero. * **ELOOP** handle refers to a symbolic link, but **O_PATH** was not specified in flags. * **EPERM** The caller does not have the **CAP_DAC_READ_SEARCH** capability. * **ESTALE** The specified handle is not valid for opening a file. This error will occur if, for example, the file has been deleted. This error can also occur if the handle was acquired using the **AT_HANDLE_FID** flag and the filesystem does not support **open_by_handle_at**(). This error can also occur if the handle was acquired using the **AT_HANDLE_CONNECTABLE** flag and the file was moved to a different parent. # VERSIONS FreeBSD has a broadly similar pair of system calls in the form of **getfh**() and **fhopen**(). # STANDARDS Linux. # HISTORY Linux 2.6.39, glibc 2.14. # NOTES A file handle can be generated in one process using **name_to_handle_at**() and later used in a different process that calls **open_by_handle_at**(). Some filesystem don't support the translation of pathnames to file handles, for example, /proc, /sys, and various network filesystems. Some filesystems support the translation of pathnames to file handles, but do not support using those file handles in **open_by_handle_at**(). A file handle may become invalid ("stale") if a file is deleted, or for other filesystem-specific reasons. Invalid handles are notified by an **ESTALE** error from **open_by_handle_at**(). These system calls are designed for use by user-space file servers. For example, a user-space NFS server might generate a file handle and pass it to an NFS client. Later, when the client wants to open the file, it could pass the handle back to the server. This sort of functionality allows a user-space file server to operate in a stateless fashion with respect to the files it serves. If path refers to a symbolic link and flags does not specify **AT_SYMLINK_FOLLOW**, then **name_to_handle_at**() returns a handle for the link (rather than the file to which it refers). The process receiving the handle can later perform operations on the symbolic link by converting the handle to a file descriptor using **open_by_handle_at**() with the **O_PATH** flag, and then passing the file descriptor as the dirfd argument in system calls such as **readlinkat**(2) and **fchownat**(2). ## Obtaining a persistent filesystem ID The mount IDs in `/proc/self/mountinfo` can be reused as filesystems are unmounted and mounted. Therefore, the mount ID returned by **name_to_handle_at**() (in *mount_id*) should not be treated as a persistent identifier for the corresponding mounted filesystem. However, an application can use the information in the *mountinfo* record that corresponds to the mount ID to derive a persistent identifier. For example, one can use the device name in the fifth field of the *mountinfo* record to search for the corresponding device UUID via the symbolic links in `/dev/disks/by-uuid`. (A more comfortable way of obtaining the UUID is to use the **libblkid**(3) library.) That process can then be reversed, using the UUID to look up the device name, and then obtaining the corresponding mount point, in order to produce the mount_fd argument used by **open_by_handle_at**(). # EXAMPLES The two programs below demonstrate the use of **name_to_handle_at**() and **open_by_handle_at**(). The first program (*t_name_to_handle_at.c*) uses **name_to_handle_at**() to obtain the file handle and mount ID for the file specified in its command-line argument; the handle and mount ID are written to standard output. The second program (*t_open_by_handle_at.c*) reads a mount ID and file handle from standard input. The program then employs **open_by_handle_at**() to open the file using that handle. If an optional command-line argument is supplied, then the *mount_fd* argument for **open_by_handle_at**() is obtained by opening the directory named in that argument. Otherwise, *mount_fd* is obtained by scanning */proc/self/mountinfo* to find a record whose mount ID matches the mount ID read from standard input, and the mount directory specified in that record is opened. (These programs do not deal with the fact that mount IDs are not persistent.) #define _GNU_SOURCE
#include <err.h>
#include <fcntl.h>

/* Escanea /proc/self/mountinfo para encontrar la línea cuya ID de montaje coincide
   con 'mount_id'. (Una forma más fácil de hacer esto es instalar y usar la
   biblioteca 'libmount' proporcionada por el proyecto 'util-linux'.)
   Abre la ruta de montaje correspondiente y devuelve el descriptor de archivo
   resultante.  */
static int
open_mount_path_by_id(int mount_id)
{
    int      mi_mount_id, found;
    char     mount_path[PATH_MAX];
    char     *linep;
    FILE     *fp;
    size_t   lsize;
    ssize_t  nread;
    fp = fopen("/proc/self/mountinfo", "r");
    if (fp == NULL)
        err(EXIT_FAILURE, "fopen");
    found = 0;
    linep = NULL;
    while (!found) {
        nread = getline(&linep, &lsize, fp);
        if (nread == -1)
            break;
        nread = sscanf(linep, "%d %*d %*s %*s %s",
                       &mi_mount_id, mount_path);
        if (nread != 2) {
            fprintf(stderr, "Bad sscanf()
");
            exit(EXIT_FAILURE);
        }
        if (mi_mount_id == mount_id)
            found = 1;
    }
    free(linep);
    fclose(fp);
    if (!found) {
        fprintf(stderr, "Could not find mount point
");
        exit(EXIT_FAILURE);
    }
    return open(mount_path, O_RDONLY);
}

    if (mount_fd == -1)
        err(EXIT_FAILURE, "opening mount fd");
    /* Abre el archivo usando el manejador y el punto de montaje.  */
    fd = open_by_handle_at(mount_fd, fhp, O_RDONLY);
    if (fd == -1)
        err(EXIT_FAILURE, "open_by_handle_at");
    /* Intenta leer unos pocos bytes del archivo.  */
    nread = read(fd, buf, sizeof(buf));
    if (nread == -1)
        err(EXIT_FAILURE, "read");
    printf("Read %zd bytes
", nread);
    exit(EXIT_SUCCESS);
}
