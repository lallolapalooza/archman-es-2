NOMBRE

offlineimap - Sincroniza buzones y Maildirs en ambos sentidos o en uno de ellos.

SINOPSIS

offlineimap (opciones)

DESCRIPCIÓN

Sincroniza las cuentas configuradas en el archivo de configuración a través de IMAP. Cada cuenta tiene dos lados. Uno de los lados debe ser un servidor IMAP. El otro lado puede ser un Maildir u otro servidor IMAP.

Funciona con Python 2.

OPCIONES

-h, --help

Muestra un resumen de las opciones.

--version

Muestra la versión.

-V

Muestra la versión de offlineimap e información adicional de imaplib2.

--dry-run

Ejecuta en modo de simulación.

No modifica ninguna tienda, sino que comprueba e imprime qué acciones de sincronización se tomarían si se realizara una sincronización. No proporcionará información exacta sobre lo que sucederá. Si, por ejemplo, necesitamos crear una carpeta, simplemente mostrará Se crearía la carpeta X, pero no cuántos y qué correos transferiría.

--info

Muestra información sobre los repositorios de correo configurados.

Útil para depuración y reporte de errores. Úselo junto con la opción ‘-a’ para limitar la salida a una sola cuenta. Este modo evitará cualquier sincronización real y saldrá después de mostrar la información de depuración.

-1

Limita las operaciones de subprocesos y ejecuta una sincronización de un solo hilo.

Esto establece efectivamente las variables de archivo de configuración maxsyncaccounts y todas las maxconnections a 1 (el número).

-P <directorio>

Establece OfflineIMAP en modo de perfilado.

El programa creará DIR (no debe existir previamente). A medida que se ejecuta, la información de perfilado de Python sobre cada hilo se registra en profildir. Tenga en cuenta: esta opción está presente solo para depuración y optimización, y NO debe usarse a menos que tenga una razón específica para hacerlo. Disminuirá significativamente el rendimiento del programa, puede reducir la fiabilidad y puede generar enormes cantidades de datos. Esta opción implica la opción ‘-1’.

-a <cuenta1[,cuenta2[,...]]>

Anula la sección de cuentas en el archivo de configuración.

Permite especificar una cuenta o un conjunto de cuentas particulares para sincronizar sin tener que editar el archivo de configuración.

-c <ruta/al/archivo_de_configuración>

Especifica un archivo de configuración para usar.

-d <tipo1[,tipo2[,...]]>

Habilita la depuración para OfflineIMAP.

Esto es útil si desea rastrear un mal funcionamiento o averiguar qué está sucediendo internamente. Esta opción requiere uno o más tipos de depuración, separados por comas. Estos definen qué se depurará exactamente, e incluyen hasta ahora las opciones: "imap", "thread", "maildir" o "ALL". La opción imap habilitará la depuración del flujo del protocolo IMAP y el análisis. Tenga en cuenta que la salida puede contener contraseñas, así que tenga cuidado de eliminarla de la salida de depuración antes de enviarla a cualquier otra persona. La opción maildir habilitará la depuración para ciertas operaciones de Maildir. El uso de cualquier opción de depuración (a menos que se incluya "thread") implica la opción de un solo hilo ‘-1’.

-l <ruta/al/archivo.log>

Envía los registros a <archivo.log>.

-s

Envía los registros a syslog.

-f <carpeta1[,carpeta1[,...]]>

Sincroniza solo las carpetas especificadas.

Los nombres de las carpetas son los nombres de las carpetas sin traducir del repositorio remoto. Esta opción de línea de comandos anula cualquier opción folderfilter y folderincludes en el archivo de configuración.

-k <[sección:]opción=valor

Anula cualquier opción del archivo de configuración.

Si se omite "sección", se usa por defecto "general". Cualquier guion bajo en el nombre de la sección se reemplaza por espacios: por ejemplo, para anular la opción "autorefresh" en la sección "[Cuenta Personal]" en el archivo de configuración, usaría ‘-k Account_Personal:autorefresh=30’. Repita esta opción tantas veces como sea necesario para redefinir varias opciones.

-o

Ejecuta solo una vez.

Ignora cualquier configuración de autorefresh en el archivo de configuración.

-q

Ejecuta solo sincronizaciones rápidas.

Ignora cualquier actualización de banderas en los servidores IMAP. Si una bandera en el IMAP remoto cambia, y tenemos el mensaje localmente, se dejará intacto en una ejecución rápida. Esta opción se ignora si se establece maxage.

-u <UI>

Especifica una interfaz de usuario alternativa para usar.

Esto anula la predeterminada especificada en el archivo de configuración. La interfaz especificada con ‘-u’ se forzará a usarse, incluso si las comprobaciones determinan que no es utilizable. Las posibles opciones de interfaz son: quiet, basic, syslog, ttyui, blinkenlights, machineui.

--delete-folder

Elimina una carpeta en el repositorio remoto.

Solo se debe especificar/configurar una cuenta para que esta función funcione, o debe proporcionar una cuenta con -a. El nombre de la carpeta debe proporcionarse con los separadores remotos (probablemente /) en UTF-8 si utf8foldernames está habilitado o en IMAP de lo contrario. Por ejemplo: "Carpeta/remota/nombre".

--migrate-fmd5-using-nametrans

Migra hashes FMD5 de versiones anteriores a 6.3.5.

La forma en que se calculan los hashes FMD5 se cambió en la versión 6.3.5 (ahora usando el nombre de carpeta nametrans), introduciendo una regresión que podría provocar la recarga de todos los mensajes. Intenta corregir la regresión anterior calculando los valores FMD5 correctos y renombrando los mensajes correspondientes.


Precaución

Dado que la parte FMD5 del nombre del archivo cambia, esto puede provocar conflictos de UID. Asegúrese de tener una copia de seguridad adecuada de la caché y del Maildir antes de ejecutar esta corrección, así como de verificar los resultados utilizando la bandera ‘--dry-run’ primero.

--mbnames-prune

Elimina entradas colgantes para cuentas eliminadas o si mbnames no está habilitado/usado más.

Internamente, offlineimap crea archivos intermedios de mbnames. Se añaden automáticamente cuando mbnames está habilitado. Sin embargo, deshabilitar cuentas para que ya no se sincronicen no significa necesariamente que deban eliminarse del archivo creado por mbnames. Es necesario iniciar offlineimap con esta opción CLI cada vez que se eliminan cuentas. Cuando se ejecuta, cualquier cuenta que no esté en la opción de configuración accounts se elimina del archivo mbnames.

Es posible eliminar manualmente archivos intermedios en <metadatos>/mbnames/.

Observe que esta opción respeta --dry-run.

RENDIMIENTO DE LA SINCRONIZACIÓN

Por defecto, utilizamos configuraciones bastante conservadoras que son seguras para la sincronización pero que podrían no ser las de mejor rendimiento. Una vez que tenga todo configurado y funcionando, es posible que desee buscar formas de acelerar su sincronización. Aquí hay un par de pistas y consejos sobre cómo lograrlo.

1.Sincroniza más de una cuenta.

Por defecto, solo usamos una conexión a un servidor IMAP. Usar 2 o incluso 3 acelera considerablemente las cosas en la mayoría de los casos. Para sincronizar más de una cuenta a la vez, considere iniciar una instancia de offlineimap por cuenta.

OPTIMIZATION

3.Use a quick status cache.

The plain status cache might be slow because it's a text file that needs to be read and written often. The latest status cache is SQLite. This saves a lot of disk activity.

The old plain text status cache is no longer supported, but migrating from a very old installation using it is still possible. In this case, you might want to manually delete the old cache directory in <metadata>/Account-<account>/LocalStatus (the sqlite cache is in the LocalStatus-sqlite folder). First, make sure you have run the new version of offlineimap for all your accounts so that the status cache has been migrated.

4.Use quick sync.

A regular sync requests all flags and UIDs of all emails in each folder, which takes a considerable amount of time. A quick sync only compares the number of messages in a folder on the IMAP side (though it detects flag changes on the Maildir side). A quick sync on my smallish account takes 7 seconds instead of 40. For example, run a cron script that does a regular sync once a day and performs quick syncs ('-q') only for the 'INBOX' folder ('-f INBOX') in between.

5.Turn off fsync.

In the [general] section, you can set fsync to True or False. If you want to be absolutely safe and wait for all operations to hit the disk before proceeding, set this to True. If you set it to False, you sacrifice some safety for speed.

SECURITY AND SSL

By default, OfflineIMAP connects using any method supported by openssl, which includes SSLv2, SSLv3, or TLSv1.

Note that SSLv2 is notoriously insecure and deprecated. Unfortunately, python2 does not provide easy ways to disable SSLv2. It is recommended that you test your setup and ensure that your mail server does not use an SSLv2 connection. Use, for example, "openssl s_client -host mail.server -port 443" to determine the connection used by default.

• Certificate checking

Unfortunately, by default, we do not verify the certificate of an IMAP TLS/SSL server we connect to. Therefore, connecting via SSL does not guarantee protection against man-in-the-middle attacks. It is recommended to verify the server certificate by checking its fingerprint. Currently, there is only one secure way to ensure you connect to the correct server in an encrypted manner: you can specify a sslcacertfile setting in the repository section of your offlineimap.conf file. This setting should point to a file containing (among other things) a CA Certificate in PEM format that validates your server certificate. In this case, we will check that:

1. The server SSL certificate is validated by the CA Certificate.
2. The server's hostname matches the SSL certificate.
3. The server certificate has not expired.

The FAQ contains an entry on how to create your own certificate and CA certificate.

• StartTLS

If you have not already configured your account to connect via SSL, OfflineIMAP will still attempt to establish an SSL connection using the STARTTLS function, in case the IMAP server supports it.

There is no certificate or fingerprint checking involved when using STARTTLS (the underlying imaplib library does not yet support this). This means you will be protected against passively listening eavesdroppers, who will not be able to see your password or email contents. However, this will not protect you from active attacks, such as Man-In-The-Middle attacks, which cause you to connect to the wrong server and pretend to be your mail server.

DO NOT RELY ON STARTTLS AS A GUARANTEE OF THE AUTHENTICITY OF YOUR IMAP SERVER!

UNIX SIGNALS

OfflineIMAP listens for the Unix signals SIGUSR1, SIGUSR2, SIGTERM, SIGINT, SIGHUP, SIGQUIT.

• If sent SIGUSR1, it will abort any current (or next future) sleep of all accounts configured for autorefresh. In effect, this will trigger a full sync of all accounts to be performed as soon as possible.
• If sent SIGUSR2 or SIGABRT, it will stop autorefresh mode for all accounts. That is, accounts will abort any current sleep and will exit after a currently running synchronization has finished. This signal can be used to gracefully exit a running offlineimap "daemon".
• SIGTERM, SIGINT, SIGHUP are all treated to gracefully terminate as soon as possible. This means it will finish syncing the current folder in each account, close keep-alive connections, remove locks on the accounts, and exit.

This may take up to 10 seconds if the autorefresh option is used.

More than one SIGTERM will behave like SIGQUIT.

• If sent SIGQUIT, it dumps stack traces for all threads and attempts to dump a process core.

KNOWN ISSUES

• Deletions.

While deletions are usually propagated, to prevent data loss, removing a folder causes offlineimap to re-sync the folder. However, propagating the removal of the entire content of a folder can occur in the following two cases:

• The entire content of a folder is deleted but the folder directory still exists.
• The parent directory of the folder was deleted.
• SSL3 write pending.

Users enabling SSL may encounter a bug related to "SSL3 write pending". If this happens, the account(s) will remain unsynchronized from the time the bug appeared. Running OfflineIMAP again can help. We are still working on this bug. Patches or detailed bug reports would be appreciated. Please check that you are running the latest stable version and send us a report to the mailing list, including the full log.

• IDLE support is incomplete and experimental. Bugs may be encountered.
• No hook exists for "run after an IDLE response".

Emails will appear, but may not be processed until the next refresh cycle.

• nametrans may not be supported correctly.
• IMAP IDLE <→ IMAP IDLE doesn't work yet.
• IDLE might stop syncing on system suspend/resume.
• IDLE may only work "once" per refresh.

If you encounter this bug, please send a report to the list!

• Maildir support on Windows drives.

Maildir uses the colon character (:) in message filenames. However, the colon is a forbidden character in Windows drive names. There are several workarounds for this situation:

1. Enable filename character translation in the Windows registry (not tested).
• http://support.microsoft.com/kb/289627
2. Use a cygwin-managed mount (not tested).
• not available anymore since cygwin 1.7
3. Use "maildir-windows-compatible = yes" in the account's OfflineIMAP configuration.
• This makes OfflineIMAP use an exclamation mark (!) instead of a colon for storing messages. Such files can be written to Windows partitions. However, you will likely lose compatibility with other programs trying to read the same Maildir.
• The exclamation mark was chosen due to the note in http://docs.python.org/library/mailbox.html
• If you have already stored some messages without this option, you will have to re-sync them.
• OfflineIMAP confused after system suspend.

When resuming a suspended session, OfflineIMAP does not cleanly handle broken socket(s) if the socktimeout option is not set. You should enable this option with a value like 10.

• OfflineIMAP confused when mails change during a sync.

When OfflineIMAP is syncing, events that occur on the remote or local side since the invocation are handled poorly. OfflineIMAP will not track changes during the sync.

• Sharing a Maildir with multiple IMAP servers.

Generally, a word of caution when mixing IMAP repositories on the same Maildir root. You must be careful to **never** use the same Maildir folder for two IMAP servers. In the best case, the folder MD5 will differ, and you will get a loop where it uploads your emails to both servers in turn (infinitely!), as it thinks you have placed new emails in the local Maildir. In the worst case, the MD5 is the same (likely) and email UIDs overlap (also likely!), and it will fail to sync some emails as it thinks they already exist.

I would create a new local Maildir Repository for the Personal Gmail and use a different root to be safe. You could, for example, use

`~/mail/Pro' as the Maildir root for ProGmail and
`~/mail/Personal' as the root for the personal one.

If you then point your local mutt, or whatever MUA you use, to '~/mail/' as the root, it should still recognize all folders.

• Edge cases with maxage causing too many messages to be synced.

All messages from at most maxage days ago (+/- a few hours, depending on time zones) are synced, but there are cases where older messages may also be synced. This happens when a message's UID is significantly higher than those of other messages with similar dates. For example, when messages are added to the local folder behind offlineimap's back, causing them to be assigned a new UID, or when offlineimap first syncs a pre-existing Maildir. In the latter case, it may appear that a noticeable and random subset of old messages are synced.

• Offlineimap hangs.

When experiencing unexpected hangs, it is advised to set 'singlethreadperfolder' to yes, especially in IMAP/IMAP mode (no Maildir).

• Passwords in netrc.

Offlineimap does not know how to retrieve passwords when more than one account is stored in the netrc file. See https://github.com/OfflineIMAP/offlineimap/issues/295.

• XOAUTH2

XOAUTH2 might be a bit tricky to set up. Make sure you have followed the step-by-step guide in offlineimap.conf. The known bugs about Gmail

KNOWN ISSUES

• Gmail IMAP IDLE problems

The Gmail IMAP server doesn't support IDLE. So, please ensure that you have disabled IMAP IDLE in your settings:

[[(account)]]
#...
#IMAP4.connection.ssl.args {'ca_certs': '/etc/ssl/certs/ca-certificates.crt'}
#...
# Enable IMAP IDLE command
#imap.enable_idle = yes
imap.enable_idle = no

Problems with Gmail OAuth2 are tracked at https://github.com/OfflineIMAP/offlineimap/labels/Gmail.

Sometimes, you might hit one of the following error:

•[imap]: xoauth2handler: response "{u’error': u’invalid_grant'}"
•oauth2handler got: {u’error': u’invalid_grant'}

In such case, we had reports that generating a new refresh token from the same client ID and secret can help.

Google documentation on "invalid_grant".

When you try to use a refresh token, the following returns you an
invalid_grant error:
  - Your server's clock is not in sync with network time protocol - NTP.
  - The refresh token limit has been exceeded.

Token expiration.

It is possible that a granted token might no longer work. A token might stop
working for one of these reasons:
  - The user has revoked access.
  - The token has not been used for six months.
  - The user changed passwords and the token contains Gmail scopes.
  - The user account has exceeded a certain number of token requests.
There is currently a limit of 50 refresh tokens per user account per client. If
the limit is reached, creating a new token automatically invalidates the oldest
token without warning. This limit does not apply to service accounts.

See https://developers.google.com/analytics/devguides/config/mgmt/v3/authorization and https://developers.google.com/identity/protocols/OAuth2#expiration to know more.

`ERROR: IMAP server 'Server ### Remote' does not have a message with UID 'xxx'`

Microsoft IMAP servers are not compliant with the RFC. It is currently required to folderfilter some faulting folders. See http://www.offlineimap.org/doc/FAQ.html#exchange-and-office365 for a detailed list.
