DESCRIPCIÓN

La llamada al sistema open() abre el archivo especificado por path. Si el archivo especificado no existe, puede ser creado opcionalmente (si se especifica O_CREAT en flags) por open().

El valor de retorno de open() es un descriptor de archivo, un entero pequeño, no negativo, que es un índice en una entrada de la tabla de descriptores de archivo abiertos del proceso. El descriptor de archivo se utiliza en llamadas posteriores al sistema (read(2), write(2), lseek(2), fcntl(2), etc.) para referirse al archivo abierto. El descriptor de archivo devuelto por una llamada exitosa será el descriptor de archivo de menor número que no esté actualmente abierto para el proceso.

Por defecto, el nuevo descriptor de archivo se establece para que permanezca abierto durante una execve(2) (es decir, la bandera del descriptor de archivo FD_CLOEXEC descrita en fcntl(2) está inicialmente deshabilitada); la bandera O_CLOEXEC, descrita a continuación, puede utilizarse para cambiar este valor predeterminado. El desplazamiento del archivo se establece al principio del archivo (ver lseek(2)).

Una llamada a open() crea una nueva *descripción de archivo abierto*, una entrada en la tabla global del sistema de archivos abiertos. La descripción de archivo abierto registra el desplazamiento del archivo y las banderas de estado del archivo (ver más abajo). Un descriptor de archivo es una referencia a una descripción de archivo abierto; esta referencia no se ve afectada si path es eliminado posteriormente o modificado para referirse a un archivo diferente. Para más detalles sobre las descripciones de archivo abierto, ver NOTAS.

El argumento flags debe incluir uno de los siguientes *modos de acceso*: O_RDONLY, O_WRONLY, o O_RDWR. Estos solicitan la apertura del archivo en modo solo lectura, solo escritura o lectura/escritura, respectivamente.

Además, se pueden aplicar mediante OR bit a bit cero o más banderas de creación de archivo y banderas de estado de archivo en flags. Las *banderas de creación de archivo* son O_CLOEXEC, O_CREAT, O_DIRECTORY, O_EXCL, O_NOCTTY, O_NOFOLLOW, O_TMPFILE y O_TRUNC. Las *banderas de estado de archivo* son todas las banderas restantes listadas a continuación. La distinción entre estos dos grupos de banderas es que las banderas de creación de archivo afectan la semántica de la operación de apertura en sí, mientras que las banderas de estado de archivo afectan la semántica de las operaciones de I/O posteriores. Las banderas de estado de archivo se pueden recuperar y (en algunos casos) modificar; ver fcntl(2) para más detalles.

La lista completa de banderas de creación de archivo y banderas de estado de archivo es la siguiente:

O_APPEND
El archivo se abre en modo de adjuntar. Antes de cada write(2), el desplazamiento del archivo se posiciona al final del archivo, como si se usara lseek(2). La modificación del desplazamiento del archivo y la operación de escritura se realizan como un solo paso atómico.
O_APPEND puede provocar archivos corruptos en sistemas de archivos NFS si más de un proceso adjunta datos a un archivo a la vez. Esto se debe a que NFS no admite la adjunción a un archivo, por lo que el kernel del cliente tiene que simularla, lo que no se puede hacer sin una condición de carrera.
O_ASYNC
Habilita la I/O controlada por señales: genera una señal (SIGIO por defecto, pero esto se puede cambiar a través de fcntl(2)) cuando la entrada o salida es posible en este descriptor de archivo. Esta función solo está disponible para terminales, pseudoterminales, sockets y (desde Linux 2.6) pipes y FIFOs. Ver fcntl(2) para más detalles. Ver también BUGS, abajo.
O_CLOEXEC (desde Linux 2.6.23)
Habilita la bandera de cierre al ejecutar para el nuevo descriptor de archivo. Especificar esta bandera permite a un programa evitar operaciones adicionales de fcntl(2) F_SETFD para establecer la bandera FD_CLOEXEC.
Tenga en cuenta que el uso de esta bandera es esencial en algunos programas multihilo, ya que el uso de una operación separada de fcntl(2) F_SETFD para establecer la bandera FD_CLOEXEC no es suficiente para evitar condiciones de carrera en las que un hilo abre un descriptor de archivo e intenta establecer su bandera de cierre al ejecutar usando fcntl(2) al mismo tiempo que otro hilo realiza un fork(2) más execve(2). Dependiendo del orden de ejecución, la condición de carrera puede llevar a que el descriptor de archivo devuelto por open() se filtre involuntariamente al programa ejecutado por el proceso hijo creado por fork(2). (Este tipo de condición de carrera es en principio posible para cualquier llamada al sistema que cree un descriptor de archivo cuya bandera de cierre al ejecutar deba ser establecida, y varias otras llamadas al sistema de Linux proporcionan un equivalente de la bandera O_CLOEXEC para abordar este problema).
O_CREAT
Si path no existe, créalo como un archivo regular.
El propietario (ID de usuario) del nuevo archivo se establece al ID de usuario efectivo del proceso.
La propiedad del grupo (ID de grupo) del nuevo archivo se establece ya sea al ID de grupo efectivo del proceso (semántica de System V) o al ID de grupo del directorio padre (semántica de BSD). En Linux, el comportamiento depende de si la bandera de modo set-group-ID está establecida en el directorio padre: si esa bandera está establecida, se aplican las semánticas de BSD; de lo contrario, se aplican las semánticas de System V. Para algunos sistemas de archivos, el comportamiento también depende de las opciones de montaje bsdgroups y sysvgroups descritas en mount(8).
El argumento mode especifica las banderas de modo de archivo que se aplicarán cuando se cree un nuevo archivo. Si no se especifica ni O_CREAT ni O_TMPFILE en flags, entonces mode se ignora (y por lo tanto puede especificarse como 0, o simplemente omitirse). El argumento mode **debe** ser suministrado si se especifica O_CREAT o O_TMPFILE en flags; si no se suministra, se aplicarán bytes arbitrarios de la pila como modo de archivo.
El modo efectivo se modifica por el umask del proceso de la manera habitual: en ausencia de una ACL predeterminada, el modo del archivo creado es (mode  &  ~umask).
Tenga en cuenta que mode solo se aplica a los accesos futuros del archivo recién creado; la llamada open() que crea un archivo de solo lectura bien podría devolver un descriptor de archivo de lectura/escritura.

O_DIRECTORY (desde Linux 2.7.19)
Si path no es un directorio, el error ENOTDIR se devuelve y el descriptor de archivo no se abre.
O_DSYNC
Escribir para que todas las escrituras subsiguientes devuelvan datos y metadatos del archivo a disco. La actualización de los metadatos del archivo puede realizarse antes que la actualización de los datos. La llamada al sistema se bloquea hasta que se garantiza que la escritura se ha transferido al disco. Ver también fsync(2).
O_EXCL
Cuando se utiliza con O_CREAT, este flag hace que el archivo sea exclusivo. No se puede utilizar sin O_CREAT.
Si el archivo ya existe, falla con el error EEXIST, incluso si O_RDWR o O_WRONLY se especifican y el archivo está abierto. Si el archivo no existe, se crea con los permisos especificados por mode. No se garantiza que esto sea atómico con respecto a otras operaciones de archivo; es decir, una condición de carrera puede ocurrir si dos procesos intentan crear el mismo archivo simultáneamente.
O_LARGEFILE
Los sistemas de archivos Linux (desde el kernel 2.2) manejan de forma transparente los archivos de más de 2 GB. Este flag se define para la compatibilidad con sistemas más antiguos, pero no tiene ningún efecto actual.
O_NDELAY
Obsoleto y tiene el mismo efecto que O_NONBLOCK.
O_NOATIME (desde Linux 2.6.8)
No actualiza la marca de tiempo de acceso del archivo. Esto puede mejorar el rendimiento en algunos sistemas de archivos, pero puede hacer que el archivo se marque como "obsoleto" para copias de seguridad o sistemas de montaje que dependen de las marcas de tiempo de acceso.
O_NOCTTY
Si path se refiere a un terminal de control, entonces open() no lo tomará como el terminal de control del proceso. Esto es útil en programas que abren un terminal para su uso pero no quieren que ese terminal se convierta en el terminal de control del proceso. Por ejemplo, los daemons que abren un terminal para registrar mensajes.
O_NOFOLLOW (desde Linux 2.6.32)
No seguir enlaces simbólicos. Si el último componente de path es un enlace simbólico, entonces se devuelve un error.
O_NONBLOCK
Establece el descriptor de archivo en modo no bloqueante.
Las llamadas posteriores a read(2) que bloquearían esperarán hasta que haya datos disponibles para leer. Si no hay datos disponibles, read(2) regresará inmediatamente con un valor de -1 y establecerá errno a EAGAIN.
Las llamadas posteriores a write(2) que bloquearían esperarán hasta que haya espacio disponible para escribir. Si no hay espacio disponible, write(2) regresará inmediatamente con un valor de -1 y establecerá errno a EAGAIN.
Esto es útil para operaciones de I/O concurrente y para que los programas no se bloqueen indefinidamente si el otro extremo de una conexión de red deja de responder.
O_PATH (desde Linux 2.6.39)
Obtiene un descriptor de archivo que puede ser utilizado para obtener un descriptor de archivo en el mismo archivo con otras banderas. Por ejemplo, para obtener un descriptor de archivo para el archivo con la bandera O_PATH, puede hacer: fd = open("foo.txt", O_PATH). Luego, puede obtener un descriptor de archivo para leer y escribir en el archivo abriendo de nuevo el descriptor de archivo: rfd = openat(fd, "", O_RDWR | O_CREAT, 0666). Esto es útil para abrir archivos en directorios que el proceso actual no tiene permisos de acceso (por ejemplo, si los permisos del directorio padre solo permiten ejecución). Ver openat(2).
O_SYNC
Asegura que las escrituras subsiguientes en el archivo se sincronicen en el disco. La llamada al sistema se bloquea hasta que se garantiza que la escritura se ha transferido al disco.
Esto se realiza actualizando tanto los datos del archivo como los metadatos del archivo. Ver también fsync(2).
O_TMPFILE (desde Linux 2.6.33)
Crea un archivo temporal anónimo. El archivo se creará en un sistema de archivos que lo admita (por ejemplo, ext4, btrfs, xfs). Las llamadas a open() con O_TMPFILE solo se admiten con O_RDWR o O_WRONLY. El archivo se elimina automáticamente cuando se cierra el último descriptor de archivo para él.
El nombre del archivo es irrelevante. Utiliza un descriptor de archivo obtenido con open() de esta manera, pero no le asigna un nombre. Si el directorio que contiene el archivo se elimina, el archivo no se elimina. Si el sistema se reinicia, el archivo se elimina. Para obtener el nombre del archivo temporal, puedes crear un enlace simbólico al mismo en el sistema de archivos deseado y luego eliminar el enlace simbólico. Se puede especificar un nombre de archivo o un descriptor de directorio para el argumento path. Si se especifica un descriptor de directorio, el archivo se creará en ese directorio. Si se especifica un nombre de archivo, será ignorado. El argumento mode se utiliza para establecer los permisos del archivo. Si se especifica O_EXCL junto con O_TMPFILE, no tendrá ningún efecto adicional.
O_TRUNC
Si el archivo ya existe y se abre para escritura (O_RDWR o O_WRONLY), su longitud se trunca a cero. Los permisos de archivo no se ven afectados. Si el archivo no existe, este flag se ignora, a menos que se especifique O_CREAT, en cuyo caso se crea el archivo.

El argumento mode se utiliza para establecer los permisos del archivo cuando se crea un nuevo archivo (es decir, cuando se especifica O_CREAT o O_TMPFILE). El argumento mode se ignora si el archivo ya existe y no se está creando. El modo efectivo es la máscara de permisos del proceso (umask) aplicada al valor especificado. Ver chmod(2) para más detalles.

creat() se puede utilizar para crear un archivo nuevo. Es equivalente a llamar a open() con flags = O_WRONLY | O_CREAT | O_TRUNC. El mode se aplica de la misma manera que se describe anteriormente.

openat() es la versión de open() que opera en un directorio relativo a un descriptor de archivo. Permite el acceso a archivos sin tener que adquirir permisos en los directorios intermedios. Si path es una ruta absoluta, dirfd se ignora. Si path es relativa, se interpreta en relación con el directorio representado por dirfd. Si path es una ruta relativa y dirfd es AT_FDCWD (o es un valor inválido), entonces path se interpreta en relación con el directorio de trabajo actual, igual que open().

La bandera O_PATH se puede combinar con otras banderas de acceso (por ejemplo, O_RDWR) para obtener un descriptor de archivo para un archivo existente, sin abrirlo para I/O. Este descriptor de archivo se puede utilizar luego con openat() para obtener un descriptor de archivo real con las banderas deseadas. Esto permite abrir archivos en directorios que no se pueden leer o atravesar, pero cuyos nombres se conocen.

Si se especifica O_TMPFILE, path debe ser un directorio válido y el archivo temporal se creará en ese directorio.

Si se utiliza O_CREAT y el archivo existe, el valor de mode se ignora.

El valor devuelto es un descriptor de archivo nuevo, o -1 si ocurrió un error.

ERRORES

Se pueden devolver los siguientes errores:

EACCES
El acceso al archivo está denegado. Esto puede ocurrir si el modo de acceso especificado en flags no está permitido por los permisos del archivo, o si el archivo es un directorio y se especifica un modo de acceso distinto de lectura (por ejemplo, escritura). También ocurre si el directorio padre no tiene permisos de búsqueda o escritura (si se va a crear un archivo). Finalmente, ocurre si O_TMPFILE se utiliza sin un directorio válido como path.
EAGAIN
El descriptor de archivo está configurado en modo no bloqueante y no hay datos disponibles para leer o espacio disponible para escribir.
EBADF
El descriptor de archivo dirfd no es válido.
EBUSY
El archivo está bloqueado, o el sistema de archivos está montado de forma de solo lectura y se intenta una operación de escritura.
EINTR
Una llamada al sistema fue interrumpida por una señal.
EINVAL
El valor de flags no es válido, o no se aplicó una bandera obligatoria (por ejemplo, O_TMPFILE sin un modo de acceso).
EISDIR
El archivo es un directorio, pero se solicitó un modo de acceso distinto de lectura (es decir, se solicitó escritura o lectura/escritura).
ELOOP

EMFILE

ENAMETOOLONG

ENFILE

ETXTBSY

NOTAS

Notas sobre la implementación de Linux

El comportamiento de open() cuando se llama con la bandera O_CREAT y un archivo ya existente depende de la implementación y de las opciones de montaje del sistema de archivos. Generalmente, si el archivo ya existe, se comportará como si O_CREAT no se hubiera especificado.

La bandera O_ASYNC ya no se recomienda, y es posible que se elimine en el futuro. Se debe utilizar la notificación de eventos basada en epoll o inotify en su lugar.

Las banderas O_NDELAY y O_NONBLOCK son equivalentes. En sistemas que no son Linux, O_NDELAY puede tener un significado diferente, así que se recomienda usar O_NONBLOCK.

Linux tiene una implementación especial de O_TMPFILE. Para crear un archivo temporal, se llama a open() con O_TMPFILE y el flag O_CREAT, junto con un `pathname` que representa un directorio. El archivo se crea en ese directorio, pero no tiene nombre. El archivo se elimina cuando se cierra el último descriptor de archivo para él.

La bandera O_PATH permite obtener un descriptor de archivo que representa un archivo o directorio. Este descriptor de archivo se puede utilizar en llamadas posteriores a `openat(2)` para abrir el archivo original con un conjunto diferente de flags. Esto es útil para abrir archivos en directorios para los cuales el proceso no tiene permisos de acceso, pero sí permisos de ejecución.

Open file descriptions

Las llamadas al sistema `open`, `openat`, `creat` y `openat2` crean una nueva *descripción de archivo abierto* en el kernel para cada llamada exitosa. Una descripción de archivo abierto es un conjunto de atributos que se asocia con un archivo abierto, incluyendo: el desplazamiento del archivo, las banderas de estado del archivo (como `O_RDONLY`, `O_NONBLOCK`, etc.), y un puntero a la entrada de la tabla de archivos del inode.

Cada descriptor de archivo dentro de un proceso es una referencia a una descripción de archivo abierto. Si se llama `open` varias veces con los mismos `flags`, se crearán varias descripciones de archivo abierto distintas. Si se llama `open` varias veces con los mismos `flags` y el mismo `pathname`, cada llamada creará una nueva descripción de archivo abierto.

Si se llama `open` dos veces con el mismo `pathname` y los mismos `flags`, se crearán dos descriptores de archivo distintos, cada uno apuntando a una descripción de archivo abierto diferente. Sin embargo, ambos descriptores apuntarán al mismo inode y la misma tabla de archivos. Esto significa que el desplazamiento del archivo para ambos descriptores de archivo se mantendrá sincronizado. Si se lee de un descriptor de archivo, el desplazamiento se incrementará para ambos.

Las llamadas `dup` y `fcntl` con `F_DUPFD` duplican un descriptor de archivo. Esto crea un nuevo descriptor de archivo que apunta a la *misma* descripción de archivo abierto. Por lo tanto, `dup` y `fcntl` no crean una nueva descripción de archivo abierto.

Las llamadas `pipe` y `socketpair` también crean nuevas descripciones de archivo abierto, una para cada extremo del pipe o socket.

La diferencia entre un descriptor de archivo y una descripción de archivo abierto es que los descriptores de archivo son específicos del proceso, mientras que las descripciones de archivo abierto son globales del sistema. Los descriptores de archivo son simplemente índices en la tabla de archivos abiertos de un proceso, y los procesos pueden tener diferentes descriptores de archivo que apuntan a la misma descripción de archivo abierto.

Para obtener más información sobre las descripciones de archivo abierto y su relación con los descriptores de archivo, consulte open(2) y dup(2).

EJEMPLOS

Abrir un archivo para lectura:

int fd = open("myfile.txt", O_RDONLY);
if (fd == -1) {
    perror("open");
    exit(EXIT_FAILURE);
}

Crear un archivo para escritura, truncándolo si existe, y abriéndolo con permisos de lectura y escritura para el propietario:

int fd = open("newfile.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (fd == -1) {
    perror("open");
    exit(EXIT_FAILURE);
}

Usando openat() para abrir un archivo en un directorio específico:

int dir_fd = open("/tmp", O_RDONLY | O_DIRECTORY);
if (dir_fd == -1) {
    perror("open /tmp");
    exit(EXIT_FAILURE);
}
int file_fd = openat(dir_fd, "myfile.txt", O_RDONLY);
if (file_fd == -1) {
    perror("openat");
    exit(EXIT_FAILURE);
}
close(dir_fd);
close(file_fd);

O_DIRECT (desde Linux 2.4.10)
Intentar minimizar los efectos de caché de la E/S hacia y desde este archivo. En general esto degradará el rendimiento, pero es útil en situaciones especiales, tales como cuando las aplicaciones realizan su propio almacenamiento en caché. La E/S de archivo se realiza directamente a/desde buffers del espacio de usuario. La bandera O_DIRECT por sí sola hace un esfuerzo por transferir datos de forma síncrona, pero no da las garantías de la bandera O_SYNC de que los datos y metadatos necesarios se transfieren. Para garantizar E/S síncrona, se debe usar O_SYNC además de O_DIRECT. Ver NOTAS abajo para mayor discusión.
Una interfaz semánticamente similar (pero obsoleta) para dispositivos de bloque se describe en raw(8).
O_DIRECTORY
Si path no es un directorio, hacer que open() falle. Esta bandera se añadió en Linux 2.1.126, para evitar problemas de denegación de servicio si opendir(3) se llama en un FIFO o dispositivo de cinta.
O_DSYNC
Las operaciones de escritura en el archivo se completarán según los requisitos de la integridad de datos de E/S síncrona.
Para cuando write(2) (y similares) retornen, los datos de salida se habrán transferido al hardware subyacente, junto con cualquier metadato de archivo que fuera necesario para recuperar esos datos (es decir, como si cada write(2) fuera seguido por una llamada a fdatasync(2)). Ver VERSIONS.
O_EXCL
Asegurar que esta llamada crea el archivo: si esta bandera se especifica junto con O_CREAT, y path ya existe, entonces open() falla con el error EEXIST.
Cuando estas dos banderas se especifican, los enlaces simbólicos no se siguen: si path es un enlace simbólico, entonces open() falla independientemente de dónde apunte el enlace simbólico.
En general, el comportamiento de O_EXCL no está especificado si se usa sin O_CREAT. Hay una excepción: en Linux 2.6 y posteriores, O_EXCL puede usarse sin O_CREAT si path se refiere a un dispositivo de bloque. Si el dispositivo de bloque está en uso por el sistema (por ejemplo, montado), open() falla con el error EBUSY.
En NFS, O_EXCL solo se admite al usar NFSv3 o posterior en el kernel 2.6 o posterior. En entornos NFS donde no se proporciona soporte para O_EXCL, los programas que dependen de él para realizar tareas de bloqueo contendrán una condición de carrera. Los programas portátiles que quieran realizar bloqueo atómico de archivos usando un archivo de bloqueo, y necesiten evitar la dependencia del soporte NFS para O_EXCL, pueden crear un archivo único en el mismo sistema de archivos (por ejemplo, incorporando el nombre del host y el PID), y usar link(2) para crear un enlace al archivo de bloqueo. Si link(2) retorna 0, el bloqueo es exitoso. De lo contrario, use stat(2) en el archivo único para verificar si su contador de enlaces ha aumentado a 2, en cuyo caso el bloqueo también es exitoso.
O_LARGEFILE
(LFS) Permite abrir archivos cuyos tamaños no se pueden representar en un off_t (pero sí en un off64_t). El macro _LARGEFILE64_SOURCE debe definirse (antes de incluir cualquier archivo de cabecera) para obtener esta definición. Establecer el macro de prueba de características _FILE_OFFSET_BITS a 64 (en lugar de usar O_LARGEFILE) es el método preferido para acceder a archivos grandes en sistemas de 32 bits (ver feature_test_macros(7)).
O_NOATIME (desde Linux 2.6.8)
No actualizar la última hora de acceso del archivo (st_atime en el inodo) cuando el archivo se lee (read(2)).
Esta bandera solo se puede emplear si se cumple una de las siguientes condiciones:
•
El UID efectivo del proceso coincide con el UID propietario del archivo.
•
El proceso llamante tiene la capacidad CAP_FOWNER en su espacio de nombres de usuario y el UID propietario del archivo tiene una asignación en el espacio de nombres.
Esta bandera está pensada para ser utilizada por programas de indexación o copia de seguridad, donde su uso puede reducir significativamente la actividad del disco. Esta bandera puede no ser efectiva en todos los sistemas de archivos. Un ejemplo es NFS, donde el servidor mantiene la hora de acceso.
O_NOCTTY
Si path se refiere a un dispositivo de terminal—ver tty(4)—no se convertirá en la terminal controladora del proceso incluso si el proceso no tiene una.
O_NOFOLLOW
Si el componente final (es decir, el nombre base) de path es un enlace simbólico, entonces la apertura falla, con el error ELOOP. Los enlaces simbólicos en componentes anteriores del nombre de ruta todavía se seguirán. (Tenga en cuenta que el error ELOOP que puede ocurrir en este caso es indistinguible del caso en que una apertura falla porque hay demasiados enlaces simbólicos encontrados al resolver componentes en el prefijo de ruta del nombre de ruta.)
Esta bandera es una extensión de FreeBSD, que se añadió en Linux 2.1.126, y posteriormente se ha estandarizado en POSIX.1-2008.
Ver también O_PATH abajo.
O_NONBLOCK o O_NDELAY
Cuando sea posible, el archivo se abre en modo no bloqueante. Ni la operación open() ni ninguna operación de E/S posterior en el descriptor de archivo que se devuelve harán que el proceso llamante espere.
Tenga en cuenta que el ajuste de esta bandera no tiene efecto en la operación de poll(2), select(2), epoll(7), y similares, ya que esas interfaces solo informan al llamante sobre si un descriptor de archivo está "listo", lo que significa que una operación de E/S realizada en el descriptor de archivo con la bandera O_NONBLOCK *despejada* no bloquearía.
Tenga en cuenta que esta bandera no tiene efecto para archivos regulares y dispositivos de bloque; es decir, las operaciones de E/S se bloquearán (brevemente) cuando se requiera actividad del dispositivo, independientemente de si O_NONBLOCK está establecido. Dado que la semántica de O_NONBLOCK podría implementarse eventualmente, las aplicaciones no deben depender del comportamiento de bloqueo al especificar esta bandera para archivos regulares y dispositivos de bloque.
Para el manejo de FIFOs (tuberías con nombre), ver también fifo(7). Para una discusión del efecto de O_NONBLOCK en conjunción con bloqueos de archivo obligatorios y con arrendamientos de archivo, ver fcntl(2).
O_PATH (desde Linux 2.6.39)
Obtener un descriptor de archivo que se puede usar para dos propósitos: para indicar una ubicación en el árbol del sistema de archivos y para realizar operaciones que actúan puramente a nivel de descriptor de archivo. El archivo en sí no se abre, y otras operaciones de archivo (por ejemplo, read(2), write(2), fchmod(2), fchown(2), fgetxattr(2), ioctl(2), mmap(2)) fallan con el error EBADF.
Las siguientes operaciones *pueden* realizarse en el descriptor de archivo resultante:
•
close(2).
•
fchdir(2), si el descriptor de archivo se refiere a un directorio (desde Linux 3.5).
•
fstat(2) (desde Linux 3.6).
•
fstatfs(2) (desde Linux 3.12).
•
Duplicar el descriptor de archivo (dup(2), fcntl(2) F_DUPFD, etc.).
•
Obtener y establecer las banderas del descriptor de archivo (fcntl(2) F_GETFD y F_SETFD).
•
Recuperar las banderas de estado del archivo abierto usando la operación fcntl(2) F_GETFL : las banderas devueltas incluirán el bit O_PATH.
•
Pasar el descriptor de archivo como argumento dirfd de openat() y las otras llamadas al sistema "*at()". Esto incluye linkat(2) con AT_EMPTY_PATH (o a través de procfs usando AT_SYMLINK_FOLLOW) incluso si el archivo no es un directorio.
•
Pasar el descriptor de archivo a otro proceso a través de un socket de dominio UNIX (ver SCM_RIGHTS en unix(7)).
Cuando O_PAT
H se especifica en flags, los bits de bandera distintos de O_CLOEXEC, O_DIRECTORY y O_NOFOLLOW se ignoran.
Abrir un archivo o directorio con la bandera O_PATH no requiere permisos sobre el objeto en sí (pero sí requiere permiso de ejecución en los directorios del prefijo de ruta). Dependiendo de la operación subsiguiente, se puede realizar una verificación de los permisos de archivo adecuados (por ejemplo, fchdir(2) requiere permiso de ejecución en el directorio al que se refiere su argumento de descriptor de archivo). Por el contrario, obtener una referencia a un objeto del sistema de archivos abriéndolo con la bandera O_RDONLY requiere que el llamante tenga permiso de lectura sobre el objeto, incluso cuando la operación subsiguiente (por ejemplo, fchdir(2), fstat(2)) no requiere permiso de lectura sobre el objeto.
Si path es un enlace simbólico y también se especifica la bandera O_NOFOLLOW, la llamada devuelve un descriptor de archivo que se refiere al enlace simbólico. Este descriptor de archivo se puede usar como argumento dirfd en llamadas a fchownat(2), fstatat(2), linkat(2) y readlinkat(2) con un nombre de ruta vacío para que las llamadas operen sobre el enlace simbólico.
Si path se refiere a un punto de montaje automático que aún no se ha activado, de modo que ningún otro sistema de archivos esté montado en él, la llamada devuelve un descriptor de archivo que se refiere al directorio de montaje automático sin activar un montaje. Luego se puede usar fstatfs(2) para determinar si es, de hecho, un punto de montaje automático no activado (.f_type == AUTOFS_SUPER_MAGIC).
Un uso de O_PATH para archivos regulares es proporcionar el equivalente a la funcionalidad O_EXEC de POSIX.1. Esto nos permite abrir un archivo para el cual tenemos permiso de ejecución pero no permiso de lectura, y luego ejecutar ese archivo, con pasos como los siguientes:

char buf[PATH_MAX];
fd = open("some_prog", O_PATH);
snprintf(buf, PATH_MAX, "/proc/self/fd/%d", fd);
execl(buf, "some_prog", (char *) NULL);

Un descriptor de archivo O_PATH también puede pasarse como argumento de fexecve(3).
O_SYNC
Las operaciones de escritura en el archivo se completarán de acuerdo con los requisitos de finalización de la integridad del archivo de E/S sincronizada (en contraste con la finalización de la integridad de los datos de E/S sincronizada proporcionada por O_DSYNC).
En el momento en que write(2) (o similar) regrese, los datos de salida y la metainformación asociada del archivo se habrán transferido al hardware subyacente (es decir, como si cada write(2) fuera seguido por una llamada a fsync(2)). Ver VERSIONES.
O_TMPFILE (desde Linux 3.11)
Crea un archivo regular temporal sin nombre. El argumento path especifica un directorio; se creará un inode sin nombre en el sistema de archivos de ese directorio. Cualquier cosa escrita en el archivo resultante se perderá cuando se cierre el último descriptor de archivo, a menos que el archivo tenga un nombre.
O_TMPFILE debe especificarse con O_RDWR o O_WRONLY y, opcionalmente, O_EXCL. Si no se especifica O_EXCL, entonces se puede usar linkat(2) para enlazar el archivo temporal al sistema de archivos, haciéndolo permanente, utilizando código como el siguiente:

char path[PATH_MAX];
fd = open("/path/to/dir", O_TMPFILE | O_RDWR,
                        S_IRUSR | S_IWUSR);
/* E/S de archivo en 'fd'...  */
linkat(fd, "", AT_FDCWD, "/path/for/file", AT_EMPTY_PATH);
/* Si el llamante no tiene la capacidad CAP_DAC_READ_SEARCH
   (necesaria para usar AT_EMPTY_PATH con linkat(2)),
   y hay un sistema de archivos proc(5) montado, entonces la
   llamada linkat(2) anterior se puede reemplazar por:
snprintf(path, PATH_MAX,  "/proc/self/fd/%d", fd);
linkat(AT_FDCWD, path, AT_FDCWD, "/path/for/file",
                        AT_SYMLINK_FOLLOW);
*/

En este caso, el argumento mode de open() determina el modo de permiso del archivo, como con O_CREAT.
Especificar O_EXCL junto con O_TMPFILE evita que un archivo temporal se enlace al sistema de archivos de la manera anterior. (Tenga en cuenta que el significado de O_EXCL en este caso es diferente del significado de O_EXCL en otros casos).
Existen dos casos de uso principales para O_TMPFILE:
•
Funcionalidad mejorada de tmpfile(3): creación libre de condiciones de carrera de archivos temporales que (1) se eliminan automáticamente al cerrarse; (2) nunca se pueden alcanzar a través de ningún nombre de ruta; (3) no están sujetos a ataques de enlaces simbólicos; y (4) no requieren que el llamante invente nombres únicos.
•
Creación de un archivo que inicialmente es invisible, que luego se llena con datos y se ajusta para tener los atributos adecuados del sistema de archivos (fchown(2), fchmod(2), fsetxattr(2), etc.) antes de enlazarlo atómicamente al sistema de archivos en un estado completamente formado (usando linkat(2) como se describe anteriormente).
O_TMPFILE requiere soporte del sistema de archivos subyacente; solo un subconjunto de sistemas de archivos Linux proporciona ese soporte. En la implementación inicial, el soporte se proporcionó en los sistemas de archivos ext2, ext3, ext4, UDF, Minix y tmpfs. Posteriormente se añadió soporte para otros sistemas de archivos: XFS (Linux 3.15); Btrfs (Linux 3.16); F2FS (Linux 3.16); y ubifs (Linux 4.9)
O_TRUNC
Si el archivo ya existe y es un archivo regular y el modo de acceso permite la escritura (es decir, es O_RDWR u O_WRONLY), se truncará a longitud 0. Si el archivo es una FIFO o un archivo de dispositivo de terminal, la bandera O_TRUNC se ignora. De lo contrario, el efecto de O_TRUNC no está especificado.

creat()

Una llamada a creat() es equivalente a llamar a open() con flags igual a O_CREAT|O_WRONLY|O_TRUNC.

openat()

La llamada al sistema openat() funciona exactamente de la misma manera que open(), excepto por las diferencias que se describen aquí.

El argumento dirfd se utiliza junto con el argumento path de la siguiente manera:

•
Si el nombre de ruta proporcionado en path es absoluto, se ignora dirfd.
•
Si el nombre de ruta proporcionado en path es relativo y dirfd es el valor especial AT_FDCWD, entonces path se interpreta relativamente al directorio de trabajo actual del proceso llamante (como open()).
•
Si el nombre de ruta proporcionado en path es relativo, entonces se interpreta relativamente al directorio al que se refiere el descriptor de archivo dirfd (en lugar de relativamente al directorio de trabajo actual del proceso llamante, como hace open() para un nombre de ruta relativo). En este caso, dirfd debe ser un directorio que se abrió para lectura (O_RDONLY) o utilizando la bandera O_PATH.

Si el nombre de ruta proporcionado en path es relativo, y dirfd no es un descriptor de archivo válido, se produce un error (EBADF). (Especificar un número de descriptor de archivo no válido en dirfd se puede usar como medio para garantizar que path sea absoluto).

openat2(2)

La llamada al sistema openat2(2) es una extensión de openat(), y proporciona un superconjunto de las características de openat(). Se documenta por separado, en openat2(2).

VALOR DE RETORNO

En caso de éxito, open(), openat() y creat() devuelven el nuevo descriptor de archivo (un entero no negativo). En caso de error, se devuelve -1 y se establece errno para indicar el error.

E/S Sincronizada

La opción "E/S sincronizada" de POSIX.1-2008 especifica diferentes variantes de E/S sincronizada, y especifica las banderas open() O_SYNC, O_DSYNC y O_RSYNC para controlar el comportamiento. Independientemente de si una implementación admite esta opción, debe al menos admitir el uso de O_SYNC para archivos regulares.

Linux implementa O_SYNC y O_DSYNC, pero no O_RSYNC. De forma algo incorrecta, glibc define O_RSYNC para que tenga el mismo valor que O_SYNC. (O_RSYNC se define en el archivo de encabezado de Linux <asm/fcntl.h> en HP PA-RISC, pero no se utiliza.)

O_SYNC proporciona la finalización de la integridad de archivo de E/S sincronizada, lo que significa que las operaciones de escritura vaciarán los datos y todos los metadatos asociados al hardware subyacente. O_DSYNC proporciona la finalización de la integridad de datos de E/S sincronizada, lo que significa que las operaciones de escritura vaciarán los datos al hardware subyacente, pero solo vaciarán las actualizaciones de metadatos que sean necesarias para permitir que una operación de lectura posterior se complete correctamente. La finalización de la integridad de los datos puede reducir el número de operaciones de disco que son necesarias para aplicaciones que no necesitan las garantías de finalización de la integridad del archivo.

Para comprender la diferencia entre los dos tipos de finalización, considere dos piezas de metadatos de archivo: la marca de tiempo de la última modificación del archivo (st_mtime) y la longitud del archivo. Todas las operaciones de escritura actualizarán la marca de tiempo de la última modificación del archivo, pero solo las escrituras que añadan datos al final del archivo cambiarán la longitud del archivo. La marca de tiempo de la última modificación no es necesaria para garantizar que una lectura se complete correctamente, pero la longitud del archivo sí lo es. Por lo tanto, O_DSYNC solo garantizaría vaciar las actualizaciones de los metadatos de longitud del archivo (mientras que O_SYNC también vaciaría siempre los metadatos de la marca de tiempo de la última modificación).

Antes de Linux 2.6.33, Linux solo implementaba la bandera O_SYNC para open(). Sin embargo, cuando se especificaba esa bandera, la mayoría de los sistemas de archivos proporcionaban en realidad el equivalente a la finalización de la integridad de datos de E/S sincronizada (es decir, O_SYNC se implementaba en realidad como el equivalente de O_DSYNC).

Desde Linux 2.6.33, se proporciona el soporte adecuado de O_SYNC. Sin embargo, para garantizar la compatibilidad binaria con versiones anteriores, O_DSYNC se definió con el mismo valor que el O_SYNC histórico, y O_SYNC se definió como un nuevo valor de bandera (de dos bits) que incluye el valor de bandera O_DSYNC. Esto asegura que las aplicaciones compiladas con encabezados nuevos obtengan al menos las semánticas de O_DSYNC antes de Linux 2.6.33.

Diferencias entre la biblioteca C y el kernel

Desde glibc 2.26, la función de envoltura de glibc para open() utiliza la llamada al sistema openat(), en lugar de la llamada al sistema open() del kernel. Para ciertas arquitecturas, esto también es cierto antes de glibc 2.26.

POSIX

POSIX.1-2024 especifica O_CLOFORK, pero Linux no lo admite.

NAME

openat, openat2 - open a file relative to a directory file descriptor

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

#include <fcntl.h>

int openat(int dirfd, const char *pathname, int flags);
int openat(int dirfd, const char *pathname, int flags, mode_t mode);

Link with -lrt (for O_TMPFILE).

DESCRIPTION

The openat() system call is the modern way to open files and directories. It behaves like the original open(2) system call, except for a few details related to how `pathname` is interpreted.

If `pathname` is relative, then it is interpreted relative to the directory referred to by the file descriptor `dirfd` instead of the current working directory. If `pathname` is absolute, then the `dirfd` argument is ignored.

If `pathname` is empty, then it refers to the file described by `dirfd` itself. In this case, the call must be made with read-only flags (e.g., O_RDONLY), and the open(2) equivalent will be a no-op. This behavior is useful for auditing and debugging.

If `pathname` specifies a symbolic link, and the open(2) equivalent would follow the symbolic link, then `openat`() will also follow the symbolic link.

The value of `dirfd` must be a valid file descriptor. The special value `AT_FDCWD` (defined in fcntl.h) causes `pathname` to be interpreted relative to the current working directory. `AT_FDCWD` is the default behavior if `openat`() is not used.

The `flags` argument must contain one of the file access modes (e.g., `O_RDONLY`, `O_WRONLY`, `O_RDWR`). These flags can be combined with other flags which control the behavior of the open(2) call.

The `mode` argument specifies the file permission bits to be set for the newly created file. It is used only when the open(2) equivalent creates a new file (i.e., when `flags` includes `O_CREAT`). The `mode` argument is modified by the process's `umask`.

The open(2) equivalent of openat() is equivalent to:

    open(pathname, flags, mode)

if `dirfd` is `AT_FDCWD`.

Otherwise, it is equivalent to:

    openat_equivalent(dirfd, pathname, flags, mode)

NOTES

The primary motivation for openat() is to allow applications to safely open files in directories that they do not have permission to `stat`. This is important for applications that handle user-supplied directory paths, as a malicious user could create a symbolic link that points to a sensitive file, and then have the application open that symbolic link. By using openat() with a file descriptor for the directory containing the symbolic link, the application can open the target file without race conditions.

The flags O_DIRECT, O_SYNC, and O_DSYNC have complex interactions with the filesystem and the kernel. The following notes apply:

Alignment restrictions can only be assumed from known characteristics of the filesystem, the individual file, the underlying storage device(s), and the kernel version. In Linux 2.4, most filesystems based on block devices require that the file offset and the length and memory address of all I/O segments be multiples of the filesystem block size (typically 4096 bytes). In Linux 2.6.0, this was relaxed to the logical block size of the block device (typically 512 bytes). A block device's logical block size can be determined using the ioctl(2) BLKSSZGET operation or from the shell using the command:


blockdev --getss

O_DIRECT I/Os should never be run concurrently with the fork(2) system call, if the memory buffer is a private mapping (i.e., any mapping created with the mmap(2) MAP_PRIVATE flag; this includes memory allocated on the heap and statically allocated buffers). Any such I/Os, whether submitted via an asynchronous I/O interface or from another thread in the process, should be completed before fork(2) is called. Failure to do so can result in data corruption and undefined behavior in parent and child processes. This restriction does not apply when the memory buffer for the O_DIRECT I/Os was created using shmat(2) or mmap(2) with the MAP_SHARED flag. Nor does this restriction apply when the memory buffer has been advised as MADV_DONTFORK with madvise(2), ensuring that it will not be available to the child after fork(2).

The O_DIRECT flag was introduced in SGI IRIX, where it has alignment restrictions similar to those of Linux 2.4. IRIX has also a fcntl(2) call to query appropriate alignments, and sizes. FreeBSD 4.x introduced a flag of the same name, but without alignment restrictions.

O_DIRECT support was added in Linux 2.4.10. Older Linux kernels simply ignore this flag. Some filesystems may not implement the flag, in which case open() fails with the error EINVAL if it is used.

Applications should avoid mixing O_DIRECT and normal I/O to the same file, and especially to overlapping byte regions in the same file. Even when the filesystem correctly handles the coherency issues in this situation, overall I/O throughput is likely to be slower than using either mode alone. Likewise, applications should avoid mixing mmap(2) of files with direct I/O to the same files.

The behavior of O_DIRECT with NFS will differ from local filesystems. Older kernels, or kernels configured in certain ways, may not support this combination. The NFS protocol does not support passing the flag to the server, so O_DIRECT I/O will bypass the page cache only on the client; the server may still cache the I/O. The client asks the server to make the I/O synchronous to preserve the synchronous semantics of O_DIRECT. Some servers will perform poorly under these circumstances, especially if the I/O size is small. Some servers may also be configured to lie to clients about the I/O having reached stable storage; this will avoid the performance penalty at some risk to data integrity in the event of server power failure. The Linux NFS client places no alignment restrictions on O_DIRECT I/O.

In summary, O_DIRECT is a potentially powerful tool that should be used with caution. It is recommended that applications treat use of O_DIRECT as a performance option which is disabled by default.
