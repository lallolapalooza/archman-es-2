DESCRIPCIÓN

El programa ovsdb-client es un cliente de línea de comandos para interactuar con un proceso ovsdb-server en ejecución. Cada comando se conecta al servidor OVSDB especificado, que puede ser un método de conexión activo o pasivo de OVSDB, como se describe en ovsdb(7). El servidor predeterminado es unix:/run/openvswitch/db.sock y la base_de_datos predeterminada es Open_vSwitch.

ovsdb-client admite la sintaxis método1,método2,...,métodoN descrita en ovsdb(7) para conectarse a un clúster. Cuando se utiliza esta sintaxis, ovsdb-client intenta los miembros del clúster en orden aleatorio hasta que encuentra el líder del clúster. Especifique la opción --no-leader-only para aceptar en su lugar cualquier servidor que esté conectado al clúster.

Para obtener una introducción a OVSDB y su implementación en Open vSwitch, consulte ovsdb(7).

Las siguientes secciones describen los comandos que ovsdb-client admite.

Comandos de nivel de servidor

La mayoría de los comandos de ovsdb-client funcionan con una base de datos individual, pero estos comandos se aplican a un servidor de base de datos completo.

list-dbs [servidor]
Se conecta a servidor, recupera la lista de bases de datos conocidas y las imprime una por línea. Estos nombres de bases de datos son los que otros comandos pueden usar para base_de_datos.

Comandos de esquema de base de datos

Estos comandos obtienen el esquema de una base de datos y lo imprimen o parte de él.

get-schema [servidor] [base_de_datos]
Se conecta a servidor, recupera el esquema para base_de_datos e imprime en formato JSON.
list-tables [servidor] [base_de_datos]
Se conecta a servidor, recupera el esquema para base_de_datos e imprime una tabla que enumera el nombre de cada tabla dentro de la base de datos.
list-columns [servidor] [base_de_datos] tabla
Se conecta a servidor, recupera el esquema para base_de_datos e imprime una tabla que enumera el nombre y el tipo de cada columna. Si se especifica tabla, solo se enumeran las columnas de esa tabla; de lo contrario, las tablas incluyen columnas de todas las tablas.

Comandos de gestión de versiones de base de datos

Un esquema OVSDB tiene un número de versión de esquema, y una base de datos OVSDB incrusta una versión particular de un esquema OVSDB. Estos números de versión tienen el formato x.y.z, por ejemplo, 1.2.3. La implementación de OVSDB no aplica un esquema de numeración de versiones particular, pero los esquemas gestionados dentro del proyecto Open vSwitch utilizan el siguiente enfoque. Siempre que el esquema de la base de datos se cambia de forma no compatible con versiones anteriores (por ejemplo, eliminando una columna o una tabla), se incrementa x (y se reinician y y z a 0). Cuando el esquema de la base de datos se cambia de forma compatible con versiones anteriores (por ejemplo, agregando una nueva columna), se incrementa y (y se reinicia z a 0). Cuando el esquema de la base de datos se cambia cosméticamente (por ejemplo, reindentando su sintaxis), se incrementa z.

Algunas bases de datos y esquemas OVSDB, especialmente las muy antiguas, no tienen un número de versión.

Los números de versión del esquema y los números de versión de Open vSwitch son independientes.

Estos comandos funcionan con diferentes versiones de esquemas y bases de datos OVSDB.

convert [servidor] esquema
Lee el esquema especificado desde un archivo JSON y lo convierte a la versión más reciente. Imprime el esquema convertido en la salida estándar.
needs-conversion [servidor] esquema
Lee el esquema especificado desde un archivo JSON y determina si necesita ser convertido a la versión más reciente. Si es necesario, imprime el esquema convertido en la salida estándar. Si no es necesario, no imprime nada.
get-schema-version [servidor] [base_de_datos]
Se conecta a servidor y recupera el número de versión del esquema de base_de_datos.

Comandos de gestión de datos

Estos comandos realizan operaciones de lectura y escritura en los datos de una base de datos OVSDB.

transact [servidor] transacción
Ejecuta una transacción OVSDB en servidor. La transacción debe estar en formato JSON, que describe una secuencia de operaciones a realizar. Las operaciones se ejecutan atómicamente. Imprime el resultado de la transacción en formato JSON. Consulte la documentación de libovsdb para obtener más detalles sobre el formato de la transacción.
query [servidor] transacción
Similar a transact, pero solo realiza operaciones de consulta dentro de la transacción. Esto se puede usar para leer datos de la base de datos sin modificarla.
dump [servidor] [base_de_datos] [tabla [columna...]]
Lee y imprime todo el contenido de tabla dentro de base_de_datos en servidor. Si se especifican columnas, solo se imprimen esos campos. Si no se especifica tabla, imprime el contenido de todas las tablas. Si no se especifica base_de_datos, usa la base de datos predeterminada.
backup [servidor] [base_de_datos] > instantánea
Realiza una copia de seguridad de base_de_datos de servidor en el archivo instantánea. La copia de seguridad se realiza en formato JSON.
restore [servidor] [base_de_datos] < instantánea
Restaura base_de_datos en servidor desde el archivo instantánea. La opción --force anulará las tablas existentes sin pedir confirmación.
monitor [servidor] [base_de_datos] tabla [columna[,columna]...]...
Se suscribe a actualizaciones en tabla para recibir notificaciones cuando los datos en las columnas especificadas cambien. Esto es útil para mantener la información sincronizada entre procesos.
monitor [servidor] [base_de_datos] ALL
Se suscribe a actualizaciones en todas las tablas de la base de datos.
monitor-cond [servidor] [base_de_datos] condiciones tabla [columna[,columna]...]...
Similar a monitor, pero solo recibe notificaciones cuando los datos cambian y cumplen ciertas condiciones.
monitor-cond-since [servidor] [base_de_datos] [último-id] condiciones tabla [columna[,columna]...]...
Similar a monitor-cond, pero solo recibe notificaciones de cambios que ocurrieron después de un último-id específico.
wait [servidor] base_de_datos estado
Espera hasta que base_de_datos en servidor alcance el estado especificado. El estado debe ser un valor JSON válido.

Comandos de prueba

Estos comandos se utilizan para probar la funcionalidad de bloqueo de OVSDB.

lock [servidor] bloqueo
Intenta adquirir un bloqueo llamado bloqueo en servidor.
steal [servidor] bloqueo
Intenta robar un bloqueo llamado bloqueo en servidor de otro cliente.
unlock [servidor] bloqueo
Libera un bloqueo llamado bloqueo en servidor.

Opciones comunes

-h | --help
Muestra un resumen de los comandos y opciones disponibles.
-V | --version
Muestra la información de la versión del programa y sale.

Opciones de formato de salida

--format=formato
Especifica el formato de salida. Los formatos admitidos son `json`, `jsonf`, `csv`, `table` y `html`.
--data=formato
Especifica el formato de los datos dentro de una tabla. Los formatos admitidos son `bare` y `string`.
--no-headings
No imprime las cabeceras de las columnas en la salida.
--pretty
Imprime la salida JSON de forma legible para humanos.
--bare
Imprime solo los valores de los datos, sin nombres de columna ni información adicional.
--timestamp
Incluye marcas de tiempo en la salida, útil para registrar eventos.

Opciones de demonio

Estas opciones se utilizan para ejecutar ovsdb-client como un demonio en segundo plano.

--pidfile[=archivo-pid]
Escribe el ID del proceso del demonio en archivo-pid. Si no se especifica archivo-pid, se usa un nombre predeterminado.
--overwrite-pidfile
Si archivo-pid ya existe, sobrescribe el archivo en lugar de fallar.
--detach
Ejecuta el demonio en segundo plano.
--no-chdir
No cambia el directorio de trabajo actual cuando se ejecuta como demonio.
--no-self-confinement
Deshabilita el modo de autoconfinamiento. Esto permite que el demonio acceda a recursos fuera de su directorio de trabajo restringido.

Opciones de registro

-v[módulo[:destino[:nivel]]]...
Habilita el registro detallado. Se puede especificar un módulo (por ejemplo, `vswitchd`), un destino (por ejemplo, `console` o `file`) y un nivel de registro (por ejemplo, `dbg`, `info`, `warn`, `err`). Si no se especifica nada, se habilitan todos los módulos con el nivel `info` en la consola.
--verbose[=módulo[:destino[:nivel]]]
Similar a -v, pero permite especificar más detalles sobre el registro.
--log-file[=archivo]
Dirige la salida del registro al archivo especificado. Si no se especifica un archivo, se utiliza un nombre predeterminado.

Opciones de infraestructura de clave pública

Estas opciones se utilizan para configurar la autenticación mediante certificados SSL/TLS.

--private-key=privkey.pem
Especifica la ruta al archivo de clave privada del cliente.
--certificate=cert.pem
Especifica la ruta al archivo de certificado del cliente.
--ca-cert=cacert.pem
Especifica la ruta al archivo de certificado de la autoridad certificadora (CA).
--bootstrap-ca-cert=cacert.pem
Especifica la ruta a un certificado de CA utilizado para la autenticación de bootstrap. Esto se usa para la primera conexión cuando el certificado de CA del servidor aún no es de confianza.

Opciones de conexión SSL/TLS

--ssl-protocols=protocolos
Especifica los protocolos SSL/TLS permitidos (por ejemplo, `TLSv1.2`, `TLSv1.3`).
--ssl-ciphers=cifrados
Especifica los conjuntos de cifrado SSL/TLS permitidos.
--ssl-ciphersuites=cifrados-suite
Especifica los conjuntos de cifrados SSL/TLS permitidos para TLS 1.3.

Opciones de reproducción

Estas opciones se utilizan para grabar y reproducir las interacciones con ovsdb-server para pruebas o depuración.

--record[=directorio]
Graba todas las interacciones con ovsdb-server en el directorio especificado. Si no se especifica un directorio, se utiliza un nombre predeterminado.
--replay[=directorio]
Reproduce las interacciones grabadas desde el directorio especificado. Esto permite probar el comportamiento de ovsdb-client sin necesidad de un servidor real.

Comandos de prueba

Estos comandos son principalmente de interés para probar la corrección del servidor OVSDB.

lock [servidor] lock

steal [servidor] lock

unlock [servidor] lock
Se conecta a servidor y emite las operaciones de bloqueo RFC 7047 correspondientes en lock. Imprime la respuesta json o los mensajes de actualización posteriores. La opción --detach hace que ovsdb-client se desvincule después de recibir e imprimir correctamente la respuesta inicial.
Al ejecutar con la opción --detach, los comandos lock, steal, unlock y exit se pueden emitir usando ovs-appctl. El comando exit hace que ovsdb-client cierre su conexión con ovsdb-server antes de salir. Los comandos lock, steal y unlock se pueden usar para emitir operaciones de bloqueo adicionales sobre la misma conexión ovsdb-server. Todos los comandos anteriores toman un único argumento lock, que no tiene que ser el mismo que el lock con el que se inició ovsdb-client.

OPCIONES

Opciones de formato de salida

Gran parte de la salida de ovsdb-client tiene el formato de tablas. Las siguientes opciones controlan el formato de la salida:

-f formato

--format=formato
Establece el tipo de formato de la tabla. Los siguientes tipos de formato están disponibles:
table (por defecto)
Tablas de texto 2D con columnas alineadas.
list
Una lista con una columna por línea y filas separadas por una línea en blanco.
html
Tablas HTML.
csv
Valores separados por comas según se define en RFC 4180.
json
Formato JSON según se define en RFC 4627. La salida es una secuencia de objetos JSON, cada uno de los cuales corresponde a una tabla. Cada objeto JSON tiene los siguientes miembros con los valores indicados:
caption
El título de la tabla. Este miembro se omite si la tabla no tiene título.
headings
Un array con un elemento por columna de la tabla. Cada elemento del array es una cadena que indica el encabezado de la columna correspondiente.
data
Un array con un elemento por fila de la tabla. Cada elemento es también un array con un elemento por columna de la tabla. Los elementos de este array de segundo nivel son las celdas que constituyen la tabla. Las celdas que representan datos o tipos de datos OVSDB se expresan en el formato descrito en la especificación OVSDB; otras celdas se expresan simplemente como cadenas de texto.
-d formato

--data=formato
Establece el formato para las celdas dentro de las tablas de salida, a menos que el formato de la tabla se establezca en json, en cuyo caso el formato json siempre se utiliza al formatear las celdas. Los siguientes tipos de formato están disponibles:
string (por defecto)
El formato simple descrito en la sección Valores de la base de datos de ovs-vsctl(8).
bare
El formato simple sin signos de puntuación: se omiten [] y {} alrededor de conjuntos, mapas y columnas vacías, los elementos dentro de conjuntos y mapas se separan por espacios, y las cadenas nunca se citan. Este formato puede ser más fácil de analizar para scripts.
json
El formato JSON RFC 4627 como se describe anteriormente.
--no-headings
Esta opción suprime la fila de encabezado que de otro modo aparece en la primera fila de la salida de la tabla.
--pretty
Por defecto, el JSON en la salida se imprime de la forma más compacta posible. Esta opción hace que el JSON en la salida se imprima de una manera más legible. Los miembros de los objetos y los elementos de los arrays se imprimen uno por línea, con indentación.
Esta opción no afecta al JSON en las tablas, que siempre se imprime de forma compacta.
--bare
Equivalente a --format=list --data=bare --no-headings.
--max-column-width=n
Solo para salida de tabla, limita el ancho de cualquier columna en la salida a n columnas. Los datos de celda más largos se truncarán para que quepan, si es necesario. Las columnas siempre serán lo suficientemente anchas como para mostrar los nombres de las columnas, si se imprime la fila de encabezado.
--timestamp
Para los comandos monitor, monitor-cond y monitor-cond-since, añade una marca de tiempo a cada actualización de tabla. La mayoría de los formatos de salida añaden la marca de tiempo en una línea propia justo encima de la tabla. El formato de salida JSON coloca la marca de tiempo en un miembro del objeto JSON de nivel superior llamado time.
-t

--timeout=secs
Limita el tiempo de ejecución de ovsdb-client a aproximadamente secs segundos. Si expira el tiempo de espera, ovsdb-client saldrá con una señal SIGALRM.

Opciones de demonio

Las opciones de demonio se aplican solo a los comandos monitor, monitor-cond y monitor-cond-since. Con cualquier otro comando, no tienen ningún efecto.

Las siguientes opciones son válidas en plataformas basadas en POSIX.

--pidfile[=pidfile]
Hace que se cree un archivo (por defecto, ovsdb-client.pid) que indica el PID del proceso en ejecución. Si no se especifica el argumento pidfile, o si no comienza con /, se crea en /run/openvswitch.
Si no se especifica --pidfile, no se crea ningún pidfile.
--overwrite-pidfile
Por defecto, cuando se especifica --pidfile y el pidfile especificado ya existe y está bloqueado por un proceso en ejecución, ovsdb-client se niega a iniciarse. Especifique --overwrite-pidfile para que en su lugar sobrescriba el pidfile.
Cuando no se especifica --pidfile, esta opción no tiene ningún efecto.
--detach
Ejecuta ovsdb-client como un proceso en segundo plano. El proceso se bifurca y, en el hijo, inicia una nueva sesión, cierra los descriptores de archivo estándar (lo que tiene el efecto secundario de deshabilitar el registro en la consola) y cambia su directorio actual a la raíz (a menos que se especifique --no-chdir). Después de que el hijo complete su inicialización, el padre sale.
--monitor
Crea un proceso adicional para monitorear el demonio ovsdb-client. Si el demonio muere debido a una señal que indica un error de programación (SIGABRT, SIGALRM, SIGBUS, SIGFPE, SIGILL, SIGPIPE, SIGSEGV, SIGXCPU o SIGXFSZ), el proceso de monitoreo inicia una nueva copia. Si el demonio muere o sale por alguna otra razón, el proceso de monitoreo sale.
Esta opción se usa normalmente con --detach, pero también funciona sin ella.
--no-chdir
Por defecto, cuando se especifica --detach, ovsdb-client cambia su directorio de trabajo actual al directorio raíz después de desvincularse. De lo contrario, invocar ovsdb-client desde un directorio elegido descuidadamente evitaría que el administrador desmontara el sistema de archivos que contiene ese directorio.
Especificar --no-chdir suprime este comportamiento, impidiendo que ovsdb-client cambie su directorio de trabajo actual. Esto puede ser útil para recopilar volcados principales, ya que es un comportamiento común escribir volcados principales en el directorio de trabajo actual y el directorio raíz no es un buen directorio para usar.
Esta opción no tiene ningún efecto cuando no se especifica --detach.
--no-self-confinement
Por defecto, el demonio intentará confinarse a sí mismo para trabajar con archivos bajo directorios conocidos determinados durante la compilación. Es mejor mantener este comportamiento predeterminado y no usar esta bandera a menos que se utilice alguna otra medida de control de acceso para confinar el demonio. Tenga en cuenta que, a diferencia de otras implementaciones de control de acceso que generalmente se aplican desde el kernel (por ejemplo, DAC o MAC), el autocofinamiento se impone desde el demonio del espacio de usuario y, por lo tanto, no debe considerarse como una estrategia de confinamiento completa, sino como una capa adicional de seguridad.
--user
Hace que ovsdb-client se ejecute como un usuario diferente especificado en "usuario:grupo", soltando así la mayoría de los privilegios de root. También se permiten formas cortas "usuario" y ":grupo", asumiendo el usuario o grupo actual, respectivamente. Solo los demonios iniciados por el usuario root aceptan este argumento.
En Linux, a los demonios se les otorgarán CAP_IPC_LOCK y CAP_NET_BIND_SERVICES antes de soltar los privilegios de root. Los demonios que interactúan con un plano de datos, como
>ovs-vswitchd, se le otorgarán tres capacidades adicionales, a saber, CAP_NET_ADMIN, CAP_NET_BROADCAST y CAP_NET_RAW. El cambio de capacidad se aplicará incluso si el nuevo usuario es root.
En Windows, esta opción no es compatible actualmente. Por motivos de seguridad, la especificación de esta opción hará que el proceso daemon no se inicie.

Opciones de registro

-v[espec]

--verbose=[espec]
Establece los niveles de registro. Sin ningún espec, establece el nivel de registro para cada módulo y destino en dbg. De lo contrario, espec es una lista de palabras separadas por espacios, comas o dos puntos, hasta una de cada categoría a continuación:
  • Un nombre de módulo válido, como se muestra en el comando vlog/list en ovs-appctl(8), limita el cambio de nivel de registro al módulo especificado.
  • syslog, console o file, para limitar el cambio de nivel de registro solo al registro del sistema, a la consola o a un archivo, respectivamente. (Si se especifica --detach, ovsdb-client cierra sus descriptores de archivo estándar, por lo que el registro en la consola no tendrá efecto).
En la plataforma Windows, syslog se acepta como palabra y solo es útil junto con la opción --syslog-target (la palabra no tiene ningún efecto de lo contrario).
•
off, emer, err, warn, info o dbg, para controlar el nivel de registro. Se registrarán los mensajes de la gravedad dada o superior, y se filtrarán los mensajes de menor gravedad. off filtra todos los mensajes. Consulte ovs-appctl(8) para obtener una definición de cada nivel de registro.
Las mayúsculas y minúsculas no son significativas dentro de espec.
Independientemente de los niveles de registro establecidos para file, el registro en un archivo no se realizará a menos que también se especifique --log-file (ver más abajo).
Por compatibilidad con versiones anteriores de OVS, se acepta any como palabra pero no tiene ningún efecto.
-v

--verbose
Establece el nivel máximo de verbosidad de registro, equivalente a --verbose=dbg.
-vPATTERN:destino:patrón

--verbose=PATTERN:destino:patrón
Establece el patrón de registro para destino a patrón. Consulte ovs-appctl(8) para obtener una descripción de la sintaxis válida para patrón.
-vFACILITY:instalación

--verbose=FACILITY:instalación
Establece la instalación RFC5424 del mensaje de registro. instalación puede ser una de kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 o local7. Si esta opción no se especifica, se utiliza daemon como valor predeterminado para el syslog del sistema local y se utiliza local0 al enviar un mensaje al destino proporcionado a través de la opción --syslog-target.
--log-file[=archivo]
Habilita el registro en un archivo. Si se especifica archivo, se utiliza como el nombre exacto del archivo de registro. El nombre de archivo de registro predeterminado que se utiliza si se omite archivo es /var/log/openvswitch/ovsdb-client.log.
--syslog-target=host:puerto
Envía mensajes syslog al puerto UDP en host, además del syslog del sistema. El host debe ser una dirección IP numérica, no un nombre de host.
--syslog-method=método
Especifica el método por el cual se deben enviar los mensajes syslog al demonio syslog. Se admiten las siguientes formas:
  • libc, utiliza la función syslog() de libc. La desventaja de utilizar esta opción es que libc agrega un prefijo fijo a cada mensaje antes de que se envíe realmente al demonio syslog a través del socket de dominio UNIX /dev/log.
  • unix:archivo, utiliza directamente el socket de dominio UNIX. Es posible especificar un formato de mensaje arbitrario con esta opción. Sin embargo, rsyslogd 8.9 y versiones anteriores utilizan de todos modos una función de análisis codificada que limita el uso del socket de dominio UNIX. Si desea utilizar un formato de mensaje arbitrario con versiones anteriores de rsyslogd, utilice en su lugar un socket UDP a la dirección IP de localhost.
  • udp:ip:puerto, utiliza un socket UDP. Con este método es posible utilizar un formato de mensaje arbitrario también con versiones anteriores de rsyslogd. Al enviar mensajes syslog a través de un socket UDP, se deben tener en cuenta precauciones adicionales, por ejemplo, el demonio syslog debe configurarse para escuchar en el puerto UDP especificado, las reglas de iptables accidentales podrían interferir con el tráfico syslog local y existen algunas consideraciones de seguridad que se aplican a los sockets UDP, pero no a los sockets de dominio UNIX.
  • null, descarta todos los mensajes registrados en syslog.
El valor predeterminado se toma de la variable de entorno OVS_SYSLOG_METHOD; si no está configurada, el valor predeterminado es libc.

Opciones de infraestructura de clave pública

-p privkey.pem

--private-key=privkey.pem
Especifica un archivo PEM que contiene la clave privada utilizada como identidad de ovsdb-client para conexiones SSL/TLS salientes.
-c cert.pem

--certificate=cert.pem
Especifica un archivo PEM que contiene un certificado que certifica que la clave privada especificada en -p o --private-key es confiable. El certificado debe ser firmado por la autoridad certificadora (CA) que el par en las conexiones SSL/TLS utilizará para verificarlo.
-C cacert.pem

--ca-cert=cacert.pem
Especifica un archivo PEM que contiene el certificado CA que ovsdb-client debe utilizar para verificar los certificados presentados por los pares SSL/TLS. (Este puede ser el mismo certificado que los pares SSL/TLS utilizan para verificar el certificado especificado en -c o --certificate, o puede ser uno diferente, dependiendo del diseño de PKI en uso).
-C none

--ca-cert=none
Deshabilita la verificación de los certificados presentados por los pares SSL/TLS. Esto introduce un riesgo de seguridad, ya que significa que los certificados no se pueden verificar como pertenecientes a hosts conocidos y confiables.
--bootstrap-ca-cert=cacert.pem
Cuando cacert.pem existe, esta opción tiene el mismo efecto que -C o --ca-cert. Si no existe, ovsdb-client intentará obtener el certificado CA del par SSL/TLS en su primera conexión SSL/TLS y lo guardará en el archivo PEM especificado. Si tiene éxito, cerrará inmediatamente la conexión y la volverá a conectar, y a partir de entonces todas las conexiones SSL/TLS deberán ser autenticadas por un certificado firmado por el certificado CA obtenido de esta manera.
Esta opción expone la conexión SSL/TLS a un ataque de hombre en el medio al obtener el certificado CA inicial, pero puede ser útil para el arranque.
Esta opción solo es útil si el par SSL/TLS envía su certificado CA como parte de la cadena de certificados SSL/TLS. Los protocolos SSL/TLS no requieren que el servidor envíe el certificado CA.
Esta opción es mutuamente excluyente con -C y --ca-cert.

Los protocolos admitidos incluyen TLSv1 (obsoleto), TLSv1.1 (obsoleto), TLSv1.2 y TLSv1.3. Se pueden proporcionar rangos en forma de dos nombres de protocolo separados por un guion, o como un solo nombre de protocolo con un signo más. La opción acepta una lista de protocolos o exactamente un rango. NAME

ovsdb-client

a simple database client for Open vSwitch Database.

SYNOPSIS

ovsdb-client [OPTIONS] COMMAND [ARG...]

DESCRIPTION

The ovsdb-client utility provides an interface to an Open vSwitch Database (OVSDB) server. It can be used to query and update the database, as well as to configure and manage Open vSwitch.

This manual page describes the command-line options and general usage of ovsdb-client. Refer to the Open vSwitch documentation for more detailed information on the OVSDB protocol and database schema.

OPTIONS

-a
--addr=ADDRESS
Connect to the OVSDB server at the given ADDRESS. The default is a Unix domain socket at /var/run/openvswitch/db.sock.
-C
--config=FILE
Read OVSDB configuration from FILE. This option can be used multiple times. If not specified, a default configuration file is used.
-d
--debug[=FACILITY]
Enable debugging messages. If FACILITY is specified, only messages from that facility are printed. Otherwise, all debugging messages are printed. See ovs-appctl(8) for a list of possible facilities.
-f
--format=FORMAT
Prints query results in FORMAT. The default is text. Other supported formats are json.
-m
--monitor[=FACILITY]
Prints monitor events. If FACILITY is specified, only events from that facility are printed. Otherwise, all monitor events are printed.
-p
--progress
Prints a progress indicator while waiting for the OVSDB server to respond.
-t
--timeout=MSEC
Sets the connection timeout to MSEC milliseconds. If this option is omitted, a default timeout of 10 seconds is used.

Other Options

--record[=directory]
Sets the process in "recording" mode, in which it will record all the connections, data from streams (Unix domain and network sockets) and some other important necessary bits, so they could be replayed later. Recorded data is stored in replay files in specified directory. If directory does not begin with /, it is interpreted as relative to /run/openvswitch. If directory is not specified, /run/openvswitch will be used.
--replay[=directory]
Sets the process in "replay" mode, in which it will read information about connections, data from streams (Unix domain and network sockets) and some other necessary bits directly from replay files instead of using real sockets. Replay files from the directory will be used. If directory does not begin with /, it is interpreted as relative to /run/openvswitch. If directory is not specified, /run/openvswitch will be used.
-h

--help
Prints a brief help message to the console.
-V

--version
Prints version information to the console.
