NOMBRE

ossl-guide-tls-client-non-block - Guía de OpenSSL: Escribiendo un cliente TLS simple no bloqueante

EJEMPLO DE CLIENTE TLS SIMPLE NO BLOQUEANTE

Esta página se basará en el ejemplo desarrollado en la página ossl-guide-tls-client-block(7) que demuestra cómo escribir un cliente TLS simple bloqueante. En esta página modificaremos ese código de demostración para que admita un socket no bloqueante.

El código fuente completo de este cliente TLS no bloqueante de ejemplo está disponible en el directorio demos/guide de la distribución fuente de OpenSSL, en el archivo tls-client-non-block.c. También está disponible en línea en https://github.com/openssl/openssl/blob/master/demos/guide/tls-client-non-block.c.

Como vimos en el ejemplo anterior, un socket bloqueante es aquel que espera (bloquea) hasta que haya datos disponibles para leer si intentas leer de él cuando aún no hay datos. De manera similar, espera al escribir si el socket actualmente no puede escribir en ese momento. Esto puede simplificar el desarrollo del código porque no tienes que preocuparte por qué hacer en estos casos. La ejecución del código simplemente se detendrá hasta que pueda continuar. Sin embargo, en muchos casos, no quieres este comportamiento. En lugar de detenerte y esperar, tu aplicación puede necesitar realizar otras tareas mientras el socket no puede leer/escribir, por ejemplo, actualizar una GUI o realizar operaciones en otro socket.

Con un socket no bloqueante, intentar leer o escribir en un socket que actualmente no puede leer o escribir devolverá inmediatamente un error no fatal. Aunque OpenSSL realiza la lectura/escritura en el socket, este comportamiento no bloqueante se propaga a la aplicación, de modo que las funciones de E/S de OpenSSL como SSL_read_ex(3) o SSL_write_ex(3) no se bloquearán.

Dado que esta página se basa en el ejemplo desarrollado en la página ossl-guide-tls-client-block(7), asumimos que estás familiarizado con ella y solo explicamos en qué se diferencia este ejemplo.

Establecer el socket en modo no bloqueante

El primer paso para escribir una aplicación que admita el modo no bloqueante es configurar el socket en modo no bloqueante. Un socket estará bloqueante por defecto. Los detalles exactos sobre cómo hacerlo pueden diferir de una plataforma a otra. Afortunadamente, OpenSSL ofrece una función portátil que hará esto por ti:

/* Establecer en modo no bloqueante */
if (!BIO_socket_nbio(sock, 1)) {
    sock = -1;
    continue;
}

No tienes que usar la función de OpenSSL para esto. Por supuesto, puedes llamar directamente a las funciones que tu Sistema Operativo proporcione para este propósito en tu plataforma.

Realizar trabajo mientras se espera el socket

En una aplicación no bloqueante, necesitarás trabajo que realizar en caso de que queramos leer o escribir en el socket, pero actualmente no podamos. De hecho, este es el propósito de usar un socket no bloqueante, es decir, dar a la aplicación la oportunidad de hacer otra cosa. Sea lo que sea que la aplicación tenga que hacer, también debe estar preparada para volver y reintentar periódicamente la operación que intentó anteriormente para ver si ahora puede completarse. Idealmente, solo lo haría en el caso de que el estado del socket subyacente realmente haya cambiado (por ejemplo, se haya vuelto legible cuando antes no lo era), pero este no tiene por qué ser el caso. Puede reintentar en cualquier momento.

Tenga en cuenta que es importante que reintente exactamente la misma operación que intentó la última vez. No puedes empezar algo nuevo. Por ejemplo, si estabas intentando escribir el texto "Hola Mundo" y la operación falló porque el socket actualmente no puede escribir, entonces no puedes intentar escribir otro texto cuando reintentes la operación.

En esta aplicación de demostración, crearemos una función auxiliar que simula la realización de otro trabajo. De hecho, por simplicidad, no hará nada más que esperar a que cambie el estado del socket.

Llamamos a nuestra función wait_for_activity() porque todo lo que hace es esperar hasta que el socket subyacente se vuelva legible o escribible cuando antes no lo era.

static void wait_for_activity(SSL *ssl, int write)
{
    fd_set fds;
    int width, sock;
    /* Obtener el descriptor de archivo subyacente del socket */
    sock = SSL_get_fd(ssl);
    FD_ZERO(&fds);
    FD_SET(sock, &fds);
    width = sock + 1;
    /*
     * Esperar hasta que el socket sea escribible o legible. Usamos select aquí
     * por simplicidad y portabilidad, pero podrías usar
     * poll/epoll o funciones similares.
     *
     * NOTA: Para los propósitos de este código de demostración, esto efectivamente
     * hace que esta demo se bloquee hasta que tenga algo más útil que hacer. En una
     * aplicación real probablemente querrás hacer otro trabajo aquí (por ejemplo,
     * actualizar una GUI o atender otras conexiones).
     *
     * Digamos, por ejemplo, que quieres actualizar el contador de progreso en
     * una GUI cada 100ms. Una forma de hacerlo sería añadir un timeout de 100ms
     * en el último parámetro de "select" a continuación. Luego, cuando select retorne,
     * compruebas si lo hizo debido a actividad en los descriptores de archivo o
     * debido al timeout. Si es debido al timeout, actualizas la
     * GUI y reinicias el "select".
     */
    if (write)
        select(width, NULL, &fds, NULL, NULL);
    else
        select(width, &fds, NULL, NULL, NULL);
}

En este ejemplo estamos utilizando la función "select" porque es muy simple de usar y está disponible en la mayoría de los Sistemas Operativos. Sin embargo, podrías usar cualquier otra función similar para hacer lo mismo. "select" espera a que el estado de los sockets subyacentes se vuelvan legibles/escribibles antes de retornar. También admite un "timeout" (al igual que la mayoría de las otras funciones similares), por lo que en tus propias aplicaciones puedes usar esto para despertarte periódicamente y realizar trabajo mientras esperas que cambie el estado del socket. Pero no usamos esa capacidad de timeout en este ejemplo por simplicidad.

Manejo de errores de las funciones de E/S de OpenSSL

Una aplicación que utiliza un socket no bloqueante deberá estar preparada para manejar los errores devueltos por las funciones de E/S de OpenSSL como SSL_read_ex(3) o SSL_write_ex(3). Los errores pueden ser fatales (por ejemplo, porque la conexión subyacente ha fallado) o no fatales (por ejemplo, porque estamos intentando leer del socket subyacente pero los datos aún no han llegado del par).

SSL_read_ex(3) y SSL_write_ex(3) devolverán 0 para indicar un error y SSL_read(3) y SSL_write(3) devolverán 0 o un valor negativo para indicar un error. SSL_shutdown(3) devolverá un valor negativo para indicar un error.

En caso de error, una aplicación debe llamar a SSL_get_error(3) para averiguar qué tipo de error ha ocurrido. Si el error no es fatal y puede reintentarse, SSL_get_error(3) devolverá SSL_ERROR_WANT_READ o SSL_ERROR_WANT_WRITE dependiendo de si OpenSSL quería leer o escribir en el socket pero no pudo. Tenga en cuenta que una llamada a SSL_read_ex(3) o SSL_read(3) puede generar SSL_ERROR_WANT_WRITE porque OpenSSL puede necesitar escribir mensajes de protocolo (como para actualizar claves criptográficas) incluso si la aplicación solo intenta leer datos. De manera similar, las llamadas a SSL_write_ex(3) o SSL_write(3) podrían generar SSL_ERROR_WANT_READ.

Otro tipo de error no fatal que puede ocurrir es SSL_ERROR_ZERO_RETURN. Esto indica un EOF (Fin de Archivo), que puede ocurrir si intentas leer datos de un objeto SSL pero el par ha indicado que no enviará más datos en él. En este caso, es posible que aún desees escribir datos en la conexión, pero no recibirás más datos.

SSL_ERROR_SYSCALL indica que OpenSSL intentó realizar una llamada al sistema que falló. Puede consultar errno para obtener más detalles. SSL_ERROR_SSL indica que ocurrió un error en OpenSSL. Puede consultar la pila de errores de OpenSSL para obtener más detalles (por ejemplo, llamando a ERR_print_errors(3) para imprimir los detalles de los errores que han ocurrido).

En nuestra aplicación de demostración, escribiremos una función para manejar estos errores de las funciones de E/S de OpenSSL:

static int handle_io_failure(SSL *ssl, int res)
{
    switch (SSL_get_error(ssl, res)) {
    case SSL_ERROR_WANT_READ:
        /* Fallo temporal. Espere hasta que podamos leer e inténtelo de nuevo */
        wait_for_activity(ssl, 0);
        return 1;
    case SSL_ERROR_WANT_WRITE:
        /* Fallo temporal. Espere hasta que podamos escribir e inténtelo de nuevo */
        wait_for_activity(ssl, 1);
        return 1;
    case SSL_ERROR_ZERO_RETURN:
        /* EOF */
        return 0;
    case SSL_ERROR_SYSCALL:
        return -1;
    case SSL_ERROR_SSL:
        /*
        * Si el fallo se debe a un error de verificación, podemos obtener más
        * información sobre él de SSL_get_verify_result().
        */
        if (SSL_get_verify_result(ssl) != X509_V_OK)
            printf("Error de verificación: %s\n",
                X509_verify_cert_error_string(SSL_get_verify_result(ssl)));
        return -1;
    default:
        return -1;
    }
}

Esta función toma como argumentos el objeto SSL que representa la conexión, así como el código de retorno de la función de E/S que falló. En caso de un fallo no fatal, espera hasta que un nuevo intento de la operación de E/S pueda tener éxito (utilizando la función wait_for_activity() que desarrollamos en la sección anterior). Devuelve 1 en caso de un error no fatal (excepto EOF), 0 en caso de EOF, o -1 si ocurrió un error fatal.

Creación de los objetos SSL_CTX y SSL

Para conectarse a un servidor, debemos crear objetos SSL_CTX y SSL para ello. Los pasos para hacerlo son los mismos que para un cliente bloqueante y se explican en la página ossl-guide-tls-client-block(7). No repetiremos esa información aquí.

Realización del handshake

Al igual que en la demostración para un cliente TLS bloqueante, usamos la función SSL_connect(3) para realizar el handshake TLS con el servidor. Dado que estamos utilizando un socket no bloqueante, es muy probable que las llamadas a esta función fallen con un error no fatal mientras esperamos que el servidor responda a nuestros mensajes de handshake. En tal caso, debemos reintentar la misma llamada a SSL_connect(3) más tarde. En esta demostración, lo hacemos en un bucle:

/* Realizar el handshake con el servidor */
while ((ret = SSL_connect(ssl)) != 1) {
    if (handle_io_failure(ssl, ret) == 1)
        continue; /* Reintentar */
    printf("Fallo al conectar con el servidor\n");
    goto end; /* No se puede reintentar: error */
}

Llamamos continuamente a SSL_connect(3) hasta que nos dé una respuesta de éxito. De lo contrario, usamos la función handle_io_failure() que creamos anteriormente para determinar qué debemos hacer a continuación. Tenga en cuenta que no esperamos que ocurra un EOF en esta etapa, por lo que tal respuesta se trata de la misma manera que un error fatal.

Envío y recepción de datos

Al igual que con la demostración del cliente TLS bloqueante, utilizamos la función SSL_write_ex(3) para enviar datos al servidor. Al igual que con SSL_connect(3) anteriormente, debido a que estamos utilizando un socket no bloqueante, esta llamada podría fallar con un error no fatal. En ese caso, debemos reintentar exactamente la misma llamada a SSL_write_ex(3). Tenga en cuenta que los parámetros deben ser *exactamente* los mismos, es decir, el mismo puntero al búfer para escribir con la misma longitud. No debe intentar enviar datos diferentes en un reintento. Existe un modo opcional (SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER) que configura OpenSSL para permitir que el búfer que se está escribiendo cambie de un reintento al siguiente. Sin embargo, en este caso, todavía debe reintentar exactamente los mismos datos, incluso si el búfer que contiene esos datos cambia de ubicación. Consulte SSL_CTX_set_mode(3) para obtener más detalles. Al igual que en el tutorial del cliente TLS bloqueante (ossl-guide-tls-client-block(7)), escribimos la solicitud en tres partes.

/* Escribir una solicitud GET HTTP al par */
while (!SSL_write_ex(ssl, request_start, strlen(request_start), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Reintentar */
    printf("Fallo al escribir el inicio de la solicitud HTTP\n");
    goto end; /* No se puede reintentar: error */
}
while (!SSL_write_ex(ssl, hostname, strlen(hostname), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Reintentar */
    printf("Fallo al escribir el nombre de host en la solicitud HTTP\n");
    goto end; /* No se puede reintentar: error */
}
while (!SSL_write_ex(ssl, request_end, strlen(request_end), &written)) {
    if (handle_io_failure(ssl, 0) == 1)
        continue; /* Reintentar */
    printf("Fallo al escribir el final de la solicitud HTTP\n");
    goto end; /* No se puede reintentar: error */
}

En una escritura, no esperamos ver una respuesta EOF, por lo que tratamos ese caso de la misma manera que un error fatal.

Leer una respuesta del servidor es similar:

do {
    /*
     * Obtener hasta sizeof(buf) bytes de la respuesta. Seguimos leyendo hasta
     * que el servidor cierre la conexión.
     */
    while (!eof && !SSL_read_ex(ssl, buf, sizeof(buf), &readbytes)) {
        switch (handle_io_failure(ssl, 0)) {
        case 1:
            continue; /* Reintentar */
        case 0:
            eof = 1;
            continue;
        case -1:
        default:
            printf("Fallo al leer los datos restantes\n");
            goto end; /* No se puede reintentar: error */
        }
    }
    /*
     * OpenSSL no garantiza que los datos devueltos sean una cadena o
     * que terminen en NUL, por lo que usamos fwrite() para escribir el número exacto
     * de bytes que leímos. Los datos podrían ser no imprimibles o
     * tener caracteres NUL en medio. Para este simple ejemplo,
     * lo imprimiremos en stdout de todos modos.
     */
    if (!eof)
        fwrite(buf, 1, readbytes, stdout);
} while (!eof);
/* En caso de que la respuesta no terminara con una nueva línea, la añadimos ahora */
printf("\n");

La principal diferencia esta vez es que es válido que recibamos una respuesta EOF al intentar leer datos del servidor. Esto ocurrirá cuando el servidor cierre la conexión después de enviar todos los datos de su respuesta.

En esta demostración, simplemente imprimimos todos los datos que hemos recibido en la respuesta del servidor. Continuamos dando vueltas al bucle hasta que encontremos un error fatal o recibamos un EOF (lo que indica un final gracioso).

Cierre de la conexión

Al igual que en el ejemplo del cliente TLS bloqueante, debemos cerrar la conexión cuando hayamos terminado con ella.

Si nuestra aplicación estuviera iniciando el cierre, esperaríamos que SSL_shutdown(3) devolviera un valor de 0, y luego continuaríamos llamándola hasta que recibiéramos un valor de 1 (lo que significa que hemos completado el cierre exitosamente). En este ejemplo en particular, no esperamos que SSL_shutdown() devuelva 0 porque ya hemos recibido EOF del servidor, lo que indica que ya se ha cerrado. Por lo tanto, seguimos llamándola hasta que SSL_shutdown() devuelva 1. Dado que estamos utilizando un socket no bloqueante, es posible que tengamos que reintentar esta operación varias veces. Si SSL_shutdown(3) devuelve un resultado negativo, debemos llamar a SSL_get_error(3) para determinar qué hacer a continuación. Utilizamos nuestra función handle_io_failure() que desarrollamos anteriormente para esto:

/*
 * El par ya se cerró correctamente (lo sabemos porque el
 * SSL_ERROR_ZERO_RETURN (es decir, EOF) anterior). Deberíamos hacer lo mismo.
 */
while ((ret = SSL_shutdown(ssl)) != 1) {
    if (ret < 0 && handle_io_failure(ssl, ret) == 1)
        continue; /* Reintentar */
    /*
     * ret == 0 es inesperado aquí porque significa "hemos enviado un
     * close_notify y estamos esperando uno de vuelta". Pero ya sabemos
     * que recibimos uno del par debido al SSL_ERROR_ZERO_RETURN
     * (es decir, EOF) anterior.
     */
    printf("Error al cerrar la conexión\n");
    goto end; /* No se puede reintentar: error */
}

Limpieza final

Al igual que en el ejemplo del cliente TLS bloqueante, una vez que nuestra conexión haya terminado, debemos liberarla. Los pasos para hacerlo en este ejemplo son los mismos que para el ejemplo bloqueante, por lo que no lo repetiremos aquí.
