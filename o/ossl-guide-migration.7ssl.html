ossl-guide-migration, migration_guide - Guía de OpenSSL: Migración desde versiones anteriores de OpenSSL

SINOPSIS

Ver las páginas del manual individuales para obtener detalles.

DESCRIPCIÓN

Esta guía detalla los cambios necesarios para migrar a nuevas versiones de OpenSSL. Actualmente esto cubre OpenSSL 3.0 y 3.1. Para versiones anteriores consulte https://github.com/openssl/openssl/blob/master/CHANGES.md. Para una visión general de algunos de los conceptos clave introducidos en OpenSSL 3.0, consulte crypto(7).

OPENSSL 3.6

Cambios Principales desde OpenSSL 3.5

Las funciones EVP_PKEY_asn1_*() y EVP_PKEY_get0_asn1(3) fueron marcadas como obsoletas en favor de la API de proveedor. EVP_PKEY_assign_[DSA|SIPHASH]() también fueron marcadas como obsoletas. Por favor, utilice la nueva API de alto nivel y de proveedor.

OPENSSL 3.1

Cambios Principales desde OpenSSL 3.0

El proveedor FIPS en OpenSSL 3.1 incluye algunos algoritmos no validados por FIPS, consecuentemente la consulta de propiedades "fips=yes" es obligatoria para aplicaciones que deseen operar de manera aprobada por FIPS. Los algoritmos son:

Triple DES ECB
Triple DES CBC
EdDSA

No hay otros cambios que requieran medidas de migración adicionales desde OpenSSL 3.0.

OPENSSL 3.0

Cambios Principales desde OpenSSL 1.1.1

Lanzamiento Mayor

OpenSSL 3.0 es un lanzamiento mayor y consecuentemente cualquier aplicación que actualmente utilice una versión anterior de OpenSSL necesitará como mínimo ser recompilada para funcionar con la nueva versión. La intención es que la gran mayoría de las aplicaciones funcionen sin cambios con OpenSSL 3.0 si esas aplicaciones funcionaban previamente con OpenSSL 1.1.1. Sin embargo, esto no está garantizado y pueden ser necesarios algunos cambios en algunos casos. También pueden ser necesarios cambios si las aplicaciones necesitan aprovechar algunas de las nuevas características disponibles en OpenSSL 3.0, como la disponibilidad del módulo FIPS.

Cambio de Licencia

En versiones anteriores, OpenSSL se licenció bajo las licencias duales OpenSSL y SSLeay https://www.openssl.org/source/license-openssl-ssleay.txt (ambas licencias se aplican). A partir de OpenSSL 3.0, esto se reemplaza por la Licencia Apache v2 https://www.openssl.org/source/apache-license-2.0.txt.

Proveedores y soporte FIPS

Uno de los cambios clave de OpenSSL 1.1.1 es la introducción del concepto de Proveedor. Los proveedores agrupan y ponen a disposición implementaciones de algoritmos. Con OpenSSL 3.0, es posible especificar, ya sea programáticamente o a través de un archivo de configuración, qué proveedores desea utilizar para cualquier aplicación dada. OpenSSL 3.0 viene con 5 proveedores diferentes como estándar. Con el tiempo, terceros pueden distribuir proveedores adicionales que se pueden conectar a OpenSSL. Todas las implementaciones de algoritmos disponibles a través de proveedores se acceden a través de las APIs de "alto nivel" (por ejemplo, las funciones prefijadas con "EVP"). No se puede acceder a ellas utilizando las "APIs de bajo nivel".

Uno de los proveedores estándar disponibles es el proveedor FIPS. Este pone a disposición algoritmos criptográficos validados por FIPS. El proveedor FIPS está deshabilitado por defecto y necesita ser habilitado explícitamente en tiempo de configuración utilizando la opción "enable-fips". Si se habilita, el proveedor FIPS se compila e instala además de los otros proveedores estándar. No se requiere un procedimiento de instalación separado. Sin embargo, existe un "install_fips" de destino de compilación dedicado, que cumple el propósito especial de instalar solo el proveedor FIPS en una instalación existente de OpenSSL.

No todos los algoritmos pueden estar disponibles para la aplicación en un momento determinado. Si el código de la aplicación utiliza cualquier algoritmo de resumen o cifrado a través de la interfaz EVP, la aplicación debe verificar el resultado de las funciones EVP_EncryptInit(3), EVP_EncryptInit_ex(3) y EVP_DigestInit(3). En caso de que el algoritmo solicitado no esté disponible, estas funciones fallarán.

Consulte también "Algoritmos Heredados" para obtener información sobre el proveedor heredado.

Consulte también "Completar la instalación del Módulo FIPS" y "Usar el Módulo FIPS en aplicaciones".

APIs de Bajo Nivel

Históricamente, OpenSSL ha proporcionado dos conjuntos de APIs para invocar algoritmos criptográficos: las APIs de "alto nivel" (como las APIs de "EVP") y las APIs de "bajo nivel". Las APIs de alto nivel están diseñadas típicamente para funcionar en todos los tipos de algoritmos. Las APIs de "bajo nivel" están dirigidas a una implementación de algoritmo específica. Por ejemplo, las APIs EVP proporcionan las funciones EVP_EncryptInit_ex(3), EVP_EncryptUpdate(3) y EVP_EncryptFinal(3) para realizar cifrado simétrico. Esas funciones pueden usarse con los algoritmos AES, CHACHA, 3DES, etc. Por otro lado, para realizar cifrado AES utilizando las APIs de bajo nivel, tendría que llamar a funciones específicas de AES como AES_set_encrypt_key(3), AES_encrypt(3), y así sucesivamente. Las funciones para 3DES son diferentes. El uso de las APIs de bajo nivel ha sido desaconsejado informalmente por el equipo de desarrollo de OpenSSL durante mucho tiempo. Sin embargo, en OpenSSL 3.0 esto se formaliza más. Todas esas APIs de bajo nivel han sido marcadas como obsoletas. Todavía puede usarlas en sus aplicaciones, pero es posible que empiece a ver advertencias de obsolescencia durante la compilación (dependiendo del soporte del compilador para esto). Las APIs obsoletas pueden eliminarse en futuras versiones de OpenSSL, por lo que se le recomienda encarecidamente que actualice su código para usar las APIs de alto nivel en su lugar.

Esto se describe con más detalle en "Obsolescencia de Funciones de Bajo Nivel".

Algoritmos Heredados

Algunos algoritmos criptográficos como MD2 y DES que estaban disponibles a través de las APIs EVP ahora se consideran heredados y su uso está fuertemente desaconsejado. Estos algoritmos EVP heredados todavía están disponibles en OpenSSL 3.0 pero no por defecto. Si desea utilizarlos, debe cargar el proveedor heredado. Esto puede ser tan simple como un cambio en el archivo de configuración, o puede hacerse programáticamente. Consulte OSSL_PROVIDER-legacy(7) para obtener una lista completa de algoritmos. Las aplicaciones que utilizan las APIs EVP para acceder a estos algoritmos deberían utilizar en su lugar algoritmos más modernos. Si eso no es posible, estas aplicaciones deben asegurarse de que se haya cargado el proveedor heredado. Esto se puede lograr programáticamente o a través de la configuración. Consulte la página del manual crypto(7) para obtener más información sobre los proveedores.

Motores y APIs "METHOD"

La refactorización para soportar Proveedores entra en conflicto internamente con las APIs utilizadas para soportar motores, incluyendo la API de MOTOR y cualquier función que cree o modifique "MÉTODOS" personalizados (por ejemplo, EVP_MD_meth_new(3), EVP_CIPHER_meth_new(3), EVP_PKEY_meth_new(3), RSA_meth_new(3), EC_KEY_METHOD_new(3), etc.). Estas funciones están siendo obsoletas en OpenSSL 3.0, y los usuarios de estas APIs deben saber que su uso puede eludir la selección y configuración de proveedores, con consecuencias no deseadas. Soporte de motores heredados

Si openssl no se compila sin soporte de motores o soporte de API obsoletas, los motores seguirán funcionando. Sin embargo, su aplicabilidad será limitada.

Los nuevos algoritmos proporcionados a través de motores seguirán funcionando.

Las claves respaldadas por motores se pueden cargar a través de una implementación personalizada de OSSL_STORE. En este caso, los objetos EVP_PKEY creados a través de ENGINE_load_private_key(3) se considerarán heredados y continuarán funcionando.

Para garantizar la compatibilidad futura, los motores deben convertirse en proveedores. Para preferir la descarga de hardware basada en proveedores, puede especificar las propiedades predeterminadas para preferir su proveedor.

Todavía es posible establecer métodos criptográficos de bajo nivel predeterminados basados en motores o aplicaciones, como RSA_METHOD o EC_KEY_METHOD, y las claves dentro del proveedor predeterminado utilizarán la implementación basada en motores para las operaciones criptográficas. Sin embargo, los EVP_PKEY creados mediante la decodificación utilizando OSSL_DECODER, PEM_ o las API d2i_ serán basados en proveedores. Para crear EVP_PKEY completamente heredados, se deben usar funciones como EVP_PKEY_set1_RSA(3), EVP_PKEY_set1_EC_KEY(3) o similares.

Esquema de versionado

El esquema de versionado de OpenSSL ha cambiado con la versión 3.0 de OpenSSL. El nuevo esquema de versionado tiene este formato:

MAYOR.MENOR.PARCHE

Para OpenSSL 1.1.1 y versiones anteriores, los diferentes niveles de parche se indicaban con una letra al final del número de versión de la versión. Esto ya no se utilizará y, en su lugar, el nivel de parche se indicará con el número final de la versión. Un cambio en el segundo número (MENOR) indica que se pueden haber agregado nuevas características. Las versiones de OpenSSL con el mismo número principal son compatibles con API y ABI. Si cambia el número principal, la compatibilidad con API y ABI no está garantizada.

Para más información, consulte OpenSSL_version(3).

Otras nuevas características principales

Protocolo de Gestión de Certificados (CMP, RFC 4210)

Esto también cubre CRMF (RFC 4211) y la transferencia HTTP (RFC 6712). Consulte openssl-cmp(1) y OSSL_CMP_exec_certreq(3) como puntos de partida.

Cliente HTTP(S)

Un cliente HTTP(S) adecuado que soporta GET y POST, redirecciones, contenidos codificados en plano y ASN.1, proxies y tiempos de espera.

API de Función de Derivación de Clave (EVP_KDF)

Esto simplifica el proceso de añadir nuevas implementaciones de KDF y PRF.

Anteriormente, los algoritmos KDF se adaptaban a la fuerza utilizando el objeto EVP_PKEY, lo que no era una correspondencia lógica. Las aplicaciones existentes que utilizan algoritmos KDF que usan EVP_PKEY (scrypt, TLS1 PRF y HKDF) pueden ser más lentas ya que utilizan un puente EVP_KDF internamente. Todas las aplicaciones nuevas deben utilizar la nueva interfaz EVP_KDF(3). Consulte también "Función de Derivación de Clave (KDF)" en OSSL_PROVIDER-default(7) y "Función de Derivación de Clave (KDF)" en OSSL_PROVIDER-FIPS(7).

API de Código de Autenticación de Mensajes (EVP_MAC)

Esto simplifica el proceso de añadir implementaciones de MAC.

Esto incluye un puente genérico EVP_PKEY a EVP_MAC, para facilitar el uso continuado de MACs a través de claves privadas sin procesar en funcionalidades como EVP_DigestSign(3) y EVP_DigestVerify(3).

Todas las aplicaciones nuevas deben utilizar la nueva interfaz EVP_MAC(3). Consulte también "Código de Autenticación de Mensajes (MAC)" en OSSL_PROVIDER-default(7) y "Código de Autenticación de Mensajes (MAC)" en OSSL_PROVIDER-FIPS(7).

Obtención de Algoritmos

El uso de llamadas a funciones de conveniencia como EVP_sha256() y EVP_aes_256_gcm() puede implicar una penalización de rendimiento al utilizar proveedores. La obtención de algoritmos de los proveedores implica buscar un algoritmo por nombre. Esto es mucho más lento que acceder directamente a una tabla de métodos. Se recomienda prefetch de algoritmos si un algoritmo se utiliza muchas veces. Consulte "Rendimiento" en crypto(7), "Obtención explícita" en crypto(7) y "Obtención implícita" en crypto(7).

Soporte para Linux Kernel TLS

Para utilizar KTLS, se debe compilar su soporte utilizando la opción de configuración "enable-ktls". También debe habilitarse en tiempo de ejecución utilizando la opción SSL_OP_ENABLE_KTLS.

Actualizaciones de CMS y PKCS#7

  • Se añadió soporte para la verificación de firmas CAdES-BES.
  • Se añadió soporte para el esquema de firma y los atributos CAdES-BES (RFC 5126) a la API de CMS.
  • Se añadió la estructura de tipo de contenido AuthEnvelopedData (RFC 5083) utilizando AES_GCM.

    Esto utiliza el parámetro AES-GCM (RFC 5084) para la Sintaxis de Mensajes Criptográficos. Su propósito es soportar la codificación y descodificación de un sobre digital que está autenticado y codificado utilizando el modo AES GCM.

  • Se publicaron PKCS7_get_octet_string(3) y PKCS7_type_is_other(3).

Actualizaciones de la API PKCS#12

Los algoritmos predeterminados para la creación de pkcs12 con la función PKCS12_create() se cambiaron a algoritmos más modernos basados en PBKDF2 y AES. El recuento de iteraciones MAC predeterminado se cambió a PKCS12_DEFAULT_ITER para que sea igual al recuento de iteraciones de cifrado basado en contraseña. El algoritmo de hash predeterminado para el cálculo del MAC se cambió a SHA-256. La aplicación pkcs12 ahora soporta la opción -legacy que restaura los algoritmos predeterminados anteriores para soportar la interoperabilidad con sistemas heredados.

Se añadieron APIs PKCS#12 mejoradas que aceptan un contexto de biblioteca OSSL_LIB_CTX y (cuando sea relevante) una consulta de propiedades. Otras APIs que manejan objetos PKCS#7 y PKCS#8 también se han mejorado cuando ha sido necesario. Esto incluye:

PKCS12_add_key_ex(3), PKCS12_add_safe_ex(3), PKCS12_add_safes_ex(3), PKCS12_create_ex(3), PKCS12_decrypt_skey_ex(3), PKCS12_init_ex(3), PKCS12_item_decrypt_d2i_ex(3), PKCS12_item_i2d_encrypt_ex(3), PKCS12_key_gen_asc_ex(3), PKCS12_key_gen_uni_ex(3), PKCS12_key_gen_utf8_ex(3), PKCS12_pack_p7encdata_ex(3), PKCS12_pbe_crypt_ex(3), PKCS12_PBE_keyivgen_ex(3), PKCS12_SAFEBAG_create_pkcs8_encrypt_ex(3), PKCS5_pbe2_set_iv_ex(3), PKCS5_pbe_set0_algor_ex(3), PKCS5_pbe_set_ex(3), PKCS5_pbkdf2_set_ex(3), PKCS5_v2_PBE_keyivgen_ex(3), PKCS5_v2_scrypt_keyivgen_ex(3), PKCS8_decrypt_ex(3), PKCS8_encrypt_ex(3), PKCS8_set0_pbe_ex(3).

Como parte de este cambio, las APIs EVP_PBE_xxx también pueden aceptar un contexto de biblioteca y una consulta de propiedades y llamarán a una versión extendida de la función de derivación de clave/IV que soporta estos parámetros. Esto incluye EVP_PBE_CipherInit_ex(3), EVP_PBE_find_ex(3) y EVP_PBE_scrypt_ex(3).

KDF PKCS#12 frente a FIPS

A diferencia de en 1.x.y, el algoritmo PKCS12KDF utilizado cuando se crea una estructura PKCS#12 con un MAC que no funciona con el proveedor FIPS, ya que PKCS12KDF no es un mecanismo aprobado por FIPS.

Consulte EVP_KDF-PKCS12KDF(7), PKCS12_create(3), openssl-pkcs12(1), OSSL_PROVIDER-FIPS(7).

Cambios en la sincronización de hilos de Windows

La sincronización de hilos de Windows utiliza primitivas de lectura/escritura (SRWLock) cuando son soportadas por el sistema operativo; de lo contrario, sigue utilizándose CriticalSection.

API de Trazas

Se ha añadido una nueva API genérica de trazas que proporciona soporte para habilitar la instrumentación a través de la salida de trazas. Esta característica está principalmente destinada a ayudar a los desarrolladores y está deshabilitada por defecto. Para utilizarla, OpenSSL necesita ser configurado con la opción "enable-trace".

OpenSSL 3.0 Release Notes

This document outlines the changes that have been made in OpenSSL 3.0.

OpenSSL 3.0 is a major new version. It is not backwards compatible with OpenSSL 1.1.1. Applications written for OpenSSL 1.1.1 will need to be modified to work with OpenSSL 3.0.

The main changes are:

  • A new provider based API

    OpenSSL 3.0 introduces a new internal API based on the concept of Providers. This is a major change that affects almost every part of OpenSSL.

    A Provider is a dynamic library that implements cryptographic algorithms. The core OpenSSL library (libcrypto) loads Providers and uses them to perform cryptographic operations. This has several advantages:

    • Easier to add new algorithms

    • Easier to remove algorithms that are no longer needed

    • Easier to use algorithms from third-party sources

    • A much cleaner separation between the application facing APIs and the internal implementations.

    The new API is centered around the EVP_xxx functions (e.g. EVP_EncryptInit(3), EVP_DigestInit(3), etc.). Applications are strongly encouraged to use these APIs instead of the older, legacy APIs (e.g. AES_set_encrypt_key(3), MD5_Init(3), etc.).

    The legacy APIs are still available for compatibility purposes, but they are deprecated and may be removed in a future version. They will also be removed from the FIPS module.

    Details of the Provider API can be found in the man page for OSSL_PROVIDER(3).

  • New Encoder/Decoder framework

    OpenSSL 3.0 introduces a new framework for encoding and decoding data structures such as keys and certificates. This is documented in the man page for OSSL_ENCODER(3) and OSSL_DECODER(3).

    Existing applications that use functions such as i2d_X509(3), PEM_write_X509(3), i2d_PrivateKey(3), PEM_write_PrivateKey(3), etc. will continue to work as before.

    However, new applications should use the new Encoder/Decoder APIs.

  • New RAND API

    OpenSSL 3.0 introduces a new RAND API that is designed to be more flexible and extensible. The new API is documented in the man page for EVP_RAND(3).

    The old RAND API (e.g. RAND_bytes(3), RAND_pseudo_bytes(3), etc.) is still available for compatibility purposes, but it is deprecated and may be removed in a future version.

If the tracing API is enabled, the application can activate trace output by registering BIOs as trace channels for a number of tracing and debugging categories. See OSSL_trace_enabled(3).

Key validation updates

EVP_PKEY_public_check(3) and EVP_PKEY_param_check(3) now work for more key types. This includes RSA, DSA, ED25519, X25519, ED448 and X448. Previously (in 1.1.1) they would return -2. For key types that do not have parameters EVP_PKEY_param_check(3) will always return 1.

Other notable deprecations and changes

The function code part of an OpenSSL error code is no longer relevant

This code is now always set to zero. Related functions are deprecated.

STACK and HASH macros have been cleaned up

The type-safe wrappers are declared everywhere and implemented once. See DEFINE_STACK_OF(3) and DEFINE_LHASH_OF_EX(3).

The RAND_DRBG subsystem has been removed

The new EVP_RAND(3) is a partial replacement: the DRBG callback framework is absent. The RAND_DRBG API did not fit well into the new provider concept as implemented by EVP_RAND and EVP_RAND_CTX.

Removed FIPS_mode() and FIPS_mode_set()

These functions are legacy APIs that are not applicable to the new provider model. Applications should instead use EVP_default_properties_is_fips_enabled(3) and EVP_default_properties_enable_fips(3).

Key generation is slower

The Miller-Rabin test now uses 64 rounds, which is used for all prime generation, including RSA key generation. This affects the time for larger keys sizes.

The default key generation method for the regular 2-prime RSA keys was changed to the FIPS186-4 B.3.6 method (Generation of Probable Primes with Conditions Based on Auxiliary Probable Primes). This method is slower than the original method.

Change PBKDF2 to conform to SP800-132 instead of the older PKCS5 RFC2898

This checks that the salt length is at least 128 bits, the derived key length is at least 112 bits, and that the iteration count is at least 1000. For backwards compatibility these checks are disabled by default in the default provider, but are enabled by default in the FIPS provider.

To enable or disable the checks see OSSL_KDF_PARAM_PKCS5 in EVP_KDF-PBKDF2(7). The parameter can be set using EVP_KDF_derive(3).

Enforce a minimum DH modulus size of 512 bits

Smaller sizes now result in an error.

SM2 key changes

EC EVP_PKEYs with the SM2 curve have been reworked to automatically become EVP_PKEY_SM2 rather than EVP_PKEY_EC.

Unlike in previous OpenSSL versions, this means that applications cannot call EVP_PKEY_set_alias_type(pkey, EVP_PKEY_SM2) to get SM2 computations.

Parameter and key generation is also reworked to make it possible to generate EVP_PKEY_SM2 parameters and keys. Applications must now generate SM2 keys directly and must not create an EVP_PKEY_EC key first. It is no longer possible to import an SM2 key with domain parameters other than the SM2 elliptic curve ones.

Validation of SM2 keys has been separated from the validation of regular EC keys, allowing to improve the SM2 validation process to reject loaded private keys that are not conforming to the SM2 ISO standard. In particular, a private scalar k outside the range 1 <= k < n-1 is now correctly rejected.

EVP_PKEY_set_alias_type() method has been removed

This function made a EVP_PKEY object mutable after it had been set up. In OpenSSL 3.0 it was decided that a provided key should not be able to change its type, so this function has been removed.

Functions that return an internal key should be treated as read only

Functions such as EVP_PKEY_get0_RSA(3) behave slightly differently in OpenSSL 3.0. Previously they returned a pointer to the low-level key used internally by libcrypto. From OpenSSL 3.0 this key may now be held in a provider. Calling these functions will only return a handle on the internal key where the EVP_PKEY was constructed using this key in the first place, for example using a function or macro such as EVP_PKEY_assign_RSA(3), EVP_PKEY_set1_RSA(3), etc. Where the EVP_PKEY holds a provider managed key, then these functions now return a cached copy of the key. Changes to the internal provider key that take place after the first time the cached key is accessed will not be reflected back in the cached copy. Similarly any changes made to the cached copy by application code will not be reflected back in the internal provider key.

For the above reasons the keys returned from these functions should typically be treated as read-only. To emphasise this the value returned from EVP_PKEY_get0_RSA(3), EVP_PKEY_get0_DSA(3), EVP_PKEY_get0_EC_KEY(3) and EVP_PKEY_get0_DH(3) have been made const. This may break some existing code. Applications broken by this change should be modified. The preferred solution is to refactor the code to avoid the use of these deprecated functions. Failing this the code should be modified to use a const pointer instead. The EVP_PKEY_get1_RSA(3), EVP_PKEY_get1_DSA(3), EVP_PKEY_get1_EC_KEY(3) and EVP_PKEY_get1_DH(3) functions continue to return a non-const pointer to enable them to be "freed". However they should also be treated as read-only.

The public key check has moved from EVP_PKEY_derive() to EVP_PKEY_derive_set_peer()

This may mean result in an error in EVP_PKEY_derive_set_peer(3) rather than during EVP_PKEY_derive(3). To disable this check use EVP_PKEY_derive_set_peer_ex(dh, peer, 0).

The print format has cosmetic changes for some functions

The output from numerous "printing" functions such as X509_signature_print(3), X509_print_ex(3), X509_CRL_print_ex(3), and other similar functions has been amended such that there may be cosmetic differences between the output observed in 1.1.1 and 3.0. This also applies to the -text output from the openssl x509 and openssl crl applications.

Interactive mode from the openssl program has been removed

From now on, running it without arguments is equivalent to openssl help.

The error return values from some control calls (ctrl) have changed

One significant change is that controls which used to return -2 for invalid inputs, now return -1 indicating a generic error condition instead.

DH and DHX key types have different settable parameters

Previously (in 1.1.1) these conflicting parameters were allowed, but will now result in errors. See EVP_PKEY-DH(7) for further details. This affects the behaviour of openssl-genpkey(1) for DH parameter generation.

EVP_CIPHER_CTX_set_flags() ordering change

If using a cipher from a provider the EVP_CIPH_FLAG_LENGTH_BITS flag can only be set after the cipher has been assigned to the cipher context. See "FLAGS" in EVP_EncryptInit(3) for more information.

Validation of operation context parameters

Due to move of the implementation of cryptographic operations to the providers, validation of various operation parameters can be postponed until the actual operation is executed where previously it happened immediately when an operation parameter was set.

For example when setting an unsupported curve with EVP_PKEY_CTX_set_ec_paramgen_curve_nid() this function call will not fail but later keygen operations with the EVP_PKEY_CTX will fail.

Removal of function code from the error codes

The function code part of the error code is now always set to 0. For that reason the ERR_GET_FUNC() macro was removed. Applications must resolve the error codes only using the library number and the reason code.

ChaCha20-Poly1305 cipher does not allow a truncated IV length to be used

In OpenSSL 3.0 setting the IV length to any value other than 12 will result in an error. Prior to OpenSSL 3.0 the ivlen could be smaller that the required 12 byte length, using EVP_CIPHER_CTX_ctrl(ctx, EVP_CRTL_AEAD_SET_IVLEN, ivlen, NULL). This resulted in an IV that had leading zero padding.

Actualización desde OpenSSL 1.0.2

Actualizar a OpenSSL 3.0 desde OpenSSL 1.0.2 probablemente será significativamente más difícil. Además de los problemas discutidos anteriormente en la sección sobre "Actualización desde OpenSSL 1.1.1", las principales cosas a tener en cuenta son:

1.
El procedimiento de compilación e instalación ha cambiado significativamente.

Consulte el archivo INSTALL.md en la parte superior de la instalación para obtener instrucciones sobre cómo compilar e instalar OpenSSL para su plataforma. Lea también los diversos archivos NOTES en el mismo directorio, según corresponda para su plataforma.

2.
Muchas estructuras se han vuelto opacas en OpenSSL 3.0.

Las definiciones de estructuras se han eliminado de los archivos de cabecera públicos y se han movido a archivos de cabecera internos. En la práctica, esto significa que ya no puede asignar en pila algunas estructuras. EVP_MD_CTX md_ctx;

EVP_MD_CTX_init(&md_ctx);

El código debe modificarse para que se vea así:

EVP_MD_CTX *md_ctx;
md_ctx = EVP_MD_CTX_new();
...
...
EVP_MD_CTX_free(md_ctx);
3.
Se ha agregado soporte para TLSv1.3.

Esto tiene una serie de implicaciones para las aplicaciones SSL/TLS. Consulte la página TLS1.3 https://github.com/openssl/openssl/wiki/TLS1.3 para obtener más detalles.

Actualización desde el Módulo de Objeto FIPS de OpenSSL 2.0

Contexto de librería

Un contexto de librería permite que diferentes componentes de una aplicación compleja utilicen cada uno un contexto de librería diferente y tengan diferentes proveedores cargados con diferentes configuraciones. Consulte "Contextos de librería" en crypto(7) para más información.

Uso de un contexto de librería - Funciones antiguas que deben cambiarse

Si se necesita un contexto de librería, entonces todas las funciones de digestión EVP_* que devuelven un const EVP_MD *, como EVP_sha256(), deben reemplazarse por una llamada a EVP_MD_fetch(3). Consulte "ALGORITHM FETCHING" en crypto(7).

El uso de funciones de firma de bajo nivel como DSA_sign(3) ha sido desalentado informalmente durante mucho tiempo. En su lugar, las aplicaciones deberían usar EVP_DigestSign(3) y EVP_DigestVerify(3). Ver también EVP_SIGNATURE-RSA(7), EVP_SIGNATURE-DSA(7), EVP_SIGNATURE-ECDSA(7) y EVP_SIGNATURE-ED25519(7).

Tenga en cuenta que el método de un solo disparo HMAC() todavía está disponible por motivos de compatibilidad, pero esto también puede reemplazarse usando EVP_Q_MAC si se requiere un contexto de biblioteca.

Funciones de validación de bajo nivel obsoletas

Las funciones de validación de bajo nivel como DH_check(3) han sido desalentadas informalmente durante mucho tiempo. Muchas funciones de bajo nivel han sido desalentadas informalmente de uso durante mucho tiempo. Las aplicaciones deberían usar en su lugar EVP_PKEY_derive(3). Ver EVP_KEYEXCH-DH(7), EVP_KEYEXCH-ECDH(7) y EVP_KEYEXCH-X25519(7).

Funciones de generación de claves de bajo nivel obsoletas

Muchas funciones de bajo nivel han sido desalentadas informalmente de uso durante mucho tiempo. Las aplicaciones deberían usar en su lugar EVP_PKEY_keygen_init(3) y EVP_PKEY_generate(3) como se describe en EVP_PKEY-DSA(7), EVP_PKEY-DH(7), EVP_PKEY-RSA(7), EVP_PKEY-EC(7) y EVP_PKEY-X25519(7). La función rápida de un solo disparo EVP_PKEY_Q_keygen(3) y las macros para los casos más comunes: <EVP_RSA_gen(3)> y EVP_EC_gen(3) también pueden ser utilizadas.

Funciones de lectura y escritura de claves de bajo nivel obsoletas

El uso de objetos de bajo nivel (como DSA) ha sido desalentado informalmente durante mucho tiempo. Las funciones para leer y escribir estos objetos de bajo nivel (como PEM_read_DSA_PUBKEY()) deben ser reemplazadas. Las aplicaciones deberían usar en su lugar OSSL_ENCODER_to_bio(3) y OSSL_DECODER_from_bio(3).

Funciones de impresión de claves de bajo nivel obsoletas

El uso de objetos de bajo nivel (como DSA) ha sido desalentado informalmente durante mucho tiempo. Las funciones para imprimir estos objetos de bajo nivel como DSA_print() deben ser reemplazadas con las funciones EVP_PKEY equivalentes.     Cambios en la aplicación de línea de comandos OpenSSL

    Nuevas aplicaciones

    openssl kdf utiliza la nueva API EVP_KDF(3). openssl kdf utiliza la nueva API EVP_MAC(3).

    Opciones añadidas

    -provider_path y -provider están disponibles para todas las aplicaciones y se pueden usar varias veces para cargar cualquier proveedor, como el proveedor 'legacy' o proveedores de terceros. Si se utilizan, el proveedor 'default' también tendría que especificarse si fuera necesario. El -provider_path debe especificarse antes de la opción -provider.

    La aplicación list tiene muchas opciones nuevas. Ver openssl-list(1) para más información.

    -crl_lastupdate y -crl_nextupdate utilizados por openssl ca permiten el establecimiento explícito de campos en la CRL generada.

    Opciones eliminadas

    El modo interactivo ya no está disponible.

    La opción -crypt utilizada por openssl passwd. La opción -c utilizada por openssl x509, openssl dhparam, openssl dsaparam y openssl ecparam.

    Otros Cambios

    La salida de las aplicaciones de línea de comandos puede tener cambios menores. Estos son principalmente cambios en mayúsculas y espacios en blanco. Sin embargo, en algunos casos, hay diferencias adicionales. Por ejemplo, la salida de los parámetros DH de openssl dhparam ahora lista 'P', 'Q', 'G' y 'pcounter' en lugar de 'prime', 'generator', 'subgroup order' y 'counter' respectivamente.

    Los comandos openssl que leen claves, certificados y CRLs ahora detectan automáticamente el formato PEM o DER de los archivos de entrada, por lo que no es necesarioya no es necesario especificar explícitamente el formato de entrada. Sin embargo, si se utiliza la opción de formato de entrada, se requerirá el formato especificado.

    openssl speed ya no utiliza llamadas a la API de bajo nivel. Esto implica que algunos números de rendimiento podrían no ser comparables con las versiones anteriores debido a una mayor sobrecarga. Esto se aplica particularmente a la medición del rendimiento en fragmentos de datos más pequeños.

    openssl dhparam, openssl dsa, openssl gendsa, openssl dsaparam, openssl genrsa y openssl rsa se han modificado para utilizar las API de PKEY. openssl genrsa y openssl rsa ahora escriben claves PKCS #8 por defecto.

    Configuraciones por defecto

    "SHA256" es ahora el digest por defecto para las consultas TS utilizadas por openssl ts.

    Aplicaciones obsoletas

    openssl rsautl está obsoleto, use openssl pkeyutl en su lugar. openssl dhparam, openssl dsa, openssl gendsa, openssl dsaparam, openssl genrsa, openssl rsa, openssl genrsa y openssl rsa están ahora en modo de mantenimiento y no se añadirán nuevas funcionalidades a ellos.

    Cambios TLS

    • Se añadió soporte para el intercambio de claves FFDHE de TLS 1.3

      Esto utiliza grupos seguros de primos DH.

    • Soporte para grupos TLSv1.3 totalmente "enchufables".

      Esto significa que los proveedores pueden proporcionar sus propias implementaciones de grupos (utilizando los métodos de "intercambio de claves" o de "encapsulación de claves") que serán detectados y utilizados automáticamente por libssl.

    • Las opciones SSL y SSL_CTX son ahora de 64 bits en lugar de 32 bits.

      Las firmas de las funciones para obtener y establecer opciones en los objetos SSL y SSL_CTX cambiaron del tipo "unsigned long" a "uint64_t".

      Esto puede requerir cambios en el código fuente. Por ejemplo, ya no es posible utilizar los valores de las macros SSL_OP_ en condiciones de preprocesador "#if". Sin embargo, todavía es posible probar si estas macros están definidas o no.

      Ver SSL_CTX_get_options(3), SSL_CTX_set_options(3), SSL_get_options(3) y SSL_set_options(3).

    • Cambios en SSL_set1_host() y SSL_add1_host()

      Estas funciones ahora aceptan direcciones literales IP, así como nombres de host reales.

    • Se añadió la opción SSL SSL_OP_CLEANSE_PLAINTEXT

      Si la opción está establecida, openssl limpia (borra a cero) los bytes de texto plano de los búferes internos después de entregarlos a la aplicación. Nota: la aplicación sigue siendo responsable de limpiar otras copias (por ejemplo: los datos recibidos por SSL_read(3)).

    • La renegociación iniciada por el cliente está deshabilitada por defecto.

      Para permitirla, use la opción -client_renegotiation, la bandera SSL_OP_ALLOW_CLIENT_RENEGOTIATION, o el parámetro de configuración "ClientRenegotiation" según corresponda.

    • La renegociación segura ahora es requerida por defecto para las conexiones TLS.

      El soporte para la renegociación segura RFC 5746 ahora es requerido por defecto para que las conexiones SSL o TLS tengan éxito. Las aplicaciones que requieran la capacidad de conectarse a peers heredados necesitarán establecer explícitamente SSL_OP_LEGACY_SERVER_CONNECT. En consecuencia, SSL_OP_LEGACY_SERVER_CONNECT ya no se establece como parte de SSL_OP_ALL.

    • La combinación de las opciones de configuración no-ec y no-dh ya no deshabilita TLSv1.3.

      Típicamente, si OpenSSL no tiene algoritmos EC o DH, no puede soportar conexiones con TLSv1.3. Sin embargo, OpenSSL ahora soporta grupos "enchufables" a través de proveedores. Por lo tanto, los proveedores de terceros pueden proporcionar implementaciones de grupos incluso donde no hay ninguna incorporada. Intentar crear conexiones TLS en una compilación así sin deshabilitar también TLSv1.3 en tiempo de ejecución o usar grupos de proveedores de terceros puede resultar en fallos de handshake. TLSv1.3 puede ser deshabilitado en tiempo de compilación usando la opción de configuración "no-tls1_3".

    • Cambios en SSL_CTX_set_ciphersuites() y SSL_set_ciphersuites().

      Los métodos ahora ignoran los cifrados desconocidos.

    • Cambio en el callback de seguridad.

      El callback de seguridad, que puede ser personalizado por el código de la aplicación, soporta la operación de seguridad SSL_SECOP_TMP_DH. Esto está definido para tomar un EVP_PKEY en el parámetro "other". En la mayoría de los lugares, esto es lo que se pasa. Todos estos lugares ocurren en el lado del servidor. Sin embargo, hubo una llamada en el lado del cliente para esta operación de seguridad y pasó un objeto DH en su lugar. Esto es incorrecto según la definición de SSL_SECOP_TMP_DH, e inconsistente con todas las otras ubicaciones. Por lo tanto, esta llamada del lado del cliente ha sido modificada para pasar un EVP_PKEY en su lugar.

    • Nueva opción SSL SSL_OP_IGNORE_UNEXPECTED_EOF

      Se introduce la opción SSL SSL_OP_IGNORE_UNEXPECTED_EOF. Si esa opción está establecida, un EOF inesperado se ignora, se simula que se recibió un close notify en su lugar y por lo tanto el error devuelto se convierte en SSL_ERROR_ZERO_RETURN.

    • La fuerza de seguridad de las firmas basadas en SHA1 y MD5 en TLS se ha reducido.

      Esto resulta en que SSL 3, TLS 1.0, TLS 1.1 y DTLS 1.0 ya no funcionan con el nivel de seguridad por defecto de 1 y en su lugar requieren el nivel de seguridad 0. El nivel de seguridad se puede cambiar ya sea usando la cadena de cifrado con @SECLEVEL, o llamando a SSL_CTX_set_security_level(3). Esto también significa que cuando la extensión de algoritmos de firma falta en un ClientHello, el handshake fallará en TLS 1.2 con el nivel de seguridad 1. Esto se debe a que, aunque esta extensión es opcional, la falta de proporcionar una significa que OpenSSL recurrirá a un conjunto por defecto de algoritmos de firma. Este conjunto por defecto requiere la disponibilidad de SHA1.

    • Los certificados X509 firmados usando SHA1 ya no están permitidos en el nivel de seguridad 1 y superior.

      En TLS/SSL, el nivel de seguridad por defecto es 1. Se puede establecer ya sea usando la cadena de cifrado con @SECLEVEL, o llamando a SSL_CTX_set_security_level(3). Si el certificado hoja está firmado con SHA-1, una llamada a SSL_CTX_use_certificate(3) fallará si el nivel de seguridad no se reduce primero. Fuera de TLS/SSL, el nivel de seguridad por defecto es -1 (efectivamente 0). Se puede establecer usando X509_VERIFY_PARAM_set_auth_level(3) o usando las opciones -auth_level de los comandos.
