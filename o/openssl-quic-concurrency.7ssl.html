NOMBRE

openssl-quic-concurrency - Modelo de concurrencia de OpenSSL QUIC

DESCRIPCIÓN

Un dominio QUIC es un grupo de recursos QUIC, como oyentes (ver SSL_new_listener(3)) y conexiones, que comparten recursos comunes de procesamiento de eventos, como polleros internos, temporizadores y bloqueos. Todo uso de OpenSSL QUIC ocurre dentro de un dominio QUIC.

Estos recursos pueden ser accedidos y utilizados de forma concurrente dependiendo de las circunstancias. Esta página del manual discute los modelos de concurrencia disponibles y cómo pueden ser utilizados.

DOMINIOS QUIC EXPLÍCITOS E IMPLÍCITOS

Un dominio QUIC se instancia explícitamente (SSL_new_domain(3)) o implícitamente llamando a SSL_new(3) o SSL_new_listener(3):

  • Un dominio QUIC explícito es creado por y visible para la aplicación como un objeto SSL de dominio QUIC y tiene otros objetos SSL QUIC creados debajo de él, como oyentes o conexiones.
  • Un dominio QUIC implícito es uno que se crea internamente debido a la creación directa de una conexión QUIC o un objeto SSL de oyente; la aplicación no crea explícitamente un objeto SSL de dominio QUIC y nunca hace referencia directa al dominio.

La creación explícita de un dominio QUIC proporciona el mayor nivel de control para una aplicación. Las aplicaciones pueden usar un dominio QUIC implícito para facilitar su uso y evitar la necesidad de crear un objeto SSL de dominio QUIC separado.

Independientemente de si un dominio QUIC se crea explícitamente, el modelo de procesamiento interno es el mismo y la aplicación debe elegir un modelo de concurrencia apropiado como se discute a continuación.

MODELOS DE CONCURRENCIA

La implementación OpenSSL QUIC soporta múltiples modelos de concurrencia para soportar una amplia variedad de escenarios de uso.

Los modelos de concurrencia disponibles son los siguientes:

  • El Modelo de Concurrencia de un Solo Hilo (SCM), que solo soporta uso de un solo hilo sincronizado por la aplicación.
  • El Modelo de Concurrencia Selectiva (CCM), que soporta uso multihilo.
  • El Modelo de Concurrencia Asistida por Hilo (TACM), que también soporta uso multihilo y proporciona asistencia a una aplicación para manejar eventos de temporizador QUIC.

Los méritos de estos modelos son los siguientes:

  • El Modelo de Concurrencia de un Solo Hilo (SCM) no realiza ningún bloqueo ni sincronización. Es completamente responsabilidad de la aplicación sincronizar el acceso al dominio QUIC y sus objetos SSL subsidiarios.

    Este modelo de concurrencia también es útil para una aplicación que quiere usar la implementación OpenSSL QUIC como una máquina de estados pura.

  • El Modelo de Concurrencia Selectiva (CCM) realiza bloqueos automáticos al realizar llamadas a la API a objetos SSL en un dominio QUIC. Esto proporciona sincronización automática para el uso multihilo de objetos QUIC. Por ejemplo, diferentes objetos SSL de flujo QUIC en la misma conexión QUIC pueden ser accedidos de forma segura desde diferentes hilos.

    Este modelo de concurrencia añade la sobrecarga de bloqueo sobre el Modelo de Concurrencia de un Solo Hilo para soportar el uso multihilo, pero proporciona un rendimiento limitado en uso multihilo altamente disputado debido a su enfoque simple. Sin embargo, aún puede resultar una buena solución para una amplia clase de aplicaciones que pasan la mayor parte de su tiempo en la lógica de la aplicación y no en el procesamiento de E/S QUIC.

    Una ventaja de este modelo en comparación con los modelos de concurrencia más sofisticados a continuación es que no crea ningún hilo del sistema operativo.

  • El Modelo de Concurrencia Asistida por Hilo (TACM) es idéntico al Modelo de Concurrencia Selectiva, excepto que se crea un hilo en segundo plano para garantizar que los eventos del temporizador QUIC se manejen de manera oportuna. Esto asegura que los eventos de tiempo de espera de QUIC se manejen incluso si una aplicación no llama periódicamente al dominio QUIC para garantizar que se manejen los eventos de E/S de red o de temporizador pendientes relacionados con QUIC. El hilo de asistencia compite por los mismos recursos como cualquier otro hilo. Sin embargo, los eventos de la capa de enlace (TLS) nunca son procesados por el hilo de asistencia.

El modelo de concurrencia predeterminado es CCM o TACM, dependiendo del SSL_METHOD utilizado con un SSL_CTX. El uso de OSSL_QUIC_client_method(3) resulta en un modelo de concurrencia predeterminado de CCM, mientras que el uso de OSSL_QUIC_client_thread_method(3) resulta en un modelo de concurrencia predeterminado de TACM.

Es posible que se ofrezcan modelos de concurrencia adicionales en futuras versiones de OpenSSL.

CAPACIDADES DE E/S BLOQUEANTES

Todos los modelos de concurrencia soportados son capaces de soportar llamadas de E/S bloqueantes, donde las llamadas de E/S a nivel de aplicación (por ejemplo, a SSL_read_ex(3) o SSL_write_ex(3) en un objeto SSL de flujo QUIC) se bloquean hasta que la solicitud puede ser atendida. Esto incluye el uso de SSL_poll(3) de forma bloqueante.

Soportar llamadas a la API bloqueantes de forma fiable con uso multihilo requiere la creación de recursos adicionales del sistema operativo, como descriptores de archivo internos, para permitir que los hilos sean despertados cuando sea necesario. La creación de estos recursos internos del sistema operativo es opcional y puede ser solicitada explícitamente por una aplicación dependiendo del modelo de concurrencia elegido. Si esta funcionalidad está deshabilitada, dependiendo del modelo de concurrencia elegido, las llamadas de E/S bloqueantes pueden no estar disponibles y las llamadas a SSL_set_blocking_mode(3) que intentan habilitar el modo de bloqueo pueden fallar, a pesar de la siguiente sección.

Compatibilidad con el soporte de bloqueo heredado

OpenSSL 3.2 y 3.3 contenían una implementación defectuosa de llamadas de E/S QUIC bloqueantes que solo es fiable bajo uso de un solo hilo. Esta funcionalidad está siempre disponible en el Modelo de Concurrencia de un Solo Hilo (SCM), donde funciona de manera fiable.

Por razones de compatibilidad, esta funcionalidad también está disponible bajo el modelo de concurrencia predeterminado si la aplicación no especifica explícitamente un modelo de concurrencia o lo deshabilita. Esto se conoce como Modo de Compatibilidad de Bloqueo Heredado, y su uso no se recomienda para aplicaciones multihilo.

USO RECOMENDADO

Se recomienda a las nuevas aplicaciones que elijan un modelo de concurrencia de la siguiente manera:

  • Una aplicación puramente de un solo hilo, o una aplicación que desee utilizar OpenSSL QUIC como una máquina de estados y gestionar la sincronización por sí misma, debe seleccionar explícitamente el modelo de concurrencia SCM.
  • Una aplicación que desee participar en el uso multihilo de diferentes conexiones QUIC o flujos en el mismo dominio QUIC debe a) seleccionar el modelo de concurrencia CCM o TACM y b) optar explícitamente por el soporte de E/S bloqueantes o no (dependiendo de si la aplicación desea realizar llamadas de E/S bloqueantes), deshabilitando el Modo de Compatibilidad de Bloqueo Heredado.

    Una aplicación debe seleccionar el modelo de concurrencia CCM si la aplicación puede garantizar que un dominio QUIC será atendido regularmente (por ejemplo, porque la aplicación puede garantizar que el tiempo de espera devuelto por SSL_get_event_timeout(3) será manejado). Si una aplicación no puede hacer esto, debe seleccionar el modelo de concurrencia TACM.

  • Las aplicaciones deben configurar explícitamente un modelo de concurrencia durante la inicialización.

CONFIGURACIÓN DE UN MODELO DE CONCURRENCIA

Si se utiliza un dominio QUIC explícito, se elige un modelo de concurrencia al llamar a SSL_new_domain(3) especificando cero o más de las siguientes banderas:

SSL_DOMAIN_FLAG_SINGLE_THREAD
Especificar esta bandera configura el modelo de Concurrencia de un Solo Hilo (SCM).

Modelo de concurrencia

SSL_DOMAIN_FLAG_SINGLE_THREAD
Especificar esta bandera configura el Modelo de Concurrencia de un Solo Hilo (SCM).
SSL_DOMAIN_FLAG_MULTI_THREAD
Especificar esta bandera configura el Modelo de Concurrencia de Contenido (CCM) (a menos que también se especifique SSL_DOMAIN_FLAG_THREAD_ASSISTED).
SSL_DOMAIN_FLAG_THREAD_ASSISTED
Especificar esta bandera configura el Modelo de Concurrencia Asistido por Hilo (TACM). Implica SSL_DOMAIN_FLAG_MULTI_THREAD.
SSL_DOMAIN_FLAG_BLOCKING
Habilita soporte confiable para llamadas de E/S bloqueantes, asignando los recursos del sistema operativo necesarios para realizar esto. Si se especifica esta bandera, se ignora SSL_DOMAIN_FLAG_LEGACY_BLOCKING.

Los detalles sobre los recursos del sistema operativo asignados se pueden encontrar en "CONSUMO DE RECURSOS DEL SO" a continuación.

SSL_DOMAIN_FLAG_LEGACY_BLOCKING
Habilita el modo de compatibilidad de bloqueo heredado. Consulte "Compatibilidad con soporte de bloqueo heredado".

Las combinaciones de banderas mutuamente excluyentes resultan en un error (por ejemplo, combinar SSL_DOMAIN_FLAG_SINGLE_THREAD y SSL_DOMAIN_FLAG_MULTI_THREADED).

El modelo de concurrencia de un dominio no se puede cambiar después de que se crea el dominio.

Comportamiento por defecto

Si no se proporcionan SSL_DOMAIN_FLAG_SINGLE_THREAD, SSL_DOMAIN_FLAG_MULTI_THREAD o SSL_DOMAIN_FLAG_THREAD_ASSISTED a SSL_new_domain(3) o a otra función constructora que pueda aceptar las banderas anteriores, se utiliza el modelo de concurrencia por defecto configurado en el SSL_CTX. Este valor por defecto se puede establecer y obtener utilizando SSL_CTX_set_domain_flags(3) y SSL_CTX_get_domain_flags(3). Las banderas adicionales proporcionadas (por ejemplo, SSL_DOMAIN_FLAG_BLOCCKING) se añaden al conjunto de banderas heredadas.

El modelo de concurrencia por defecto en un SSL_CTX recién creado se determina de la siguiente manera:

  • Si se utiliza un SSL_METHOD de OSSL_QUIC_client_thread_method(3), se utiliza el Modelo de Concurrencia Asistido por Hilo (TACM) con la bandera SSL_DOMAIN_FLAG_BLOCKING. Esto proporciona una funcionalidad de bloqueo confiable.
  • De lo contrario, si OpenSSL se compiló sin soporte de hilos, se utiliza el Modelo de Concurrencia de un Solo Hilo (SCM), con la bandera SSL_DOMAIN_FLAG_LEGACY_BLOCKING.
  • De lo contrario, si se utiliza un SSL_METHOD de OSSL_QUIC_client_method(3), se utiliza el Modelo de Concurrencia de Contenido (CCM) con la bandera SSL_DOMAIN_FLAG_LEGACY_BLOCKING.
  • De lo contrario, se utiliza el Modelo de Concurrencia de Contenido (CCM).

El modelo de concurrencia por defecto puede variar entre versiones de OpenSSL. Una aplicación puede especificar una o más de las banderas de dominio anteriores para garantizar un uso consistente de un modelo de concurrencia específico entre versiones.

Configuración de modelos de concurrencia con dominios QUIC implícitos

Si no se crea explícitamente un dominio QUIC explícito utilizando SSL_new_domain(3), se crea un dominio QUIC implícito al llamar a SSL_new_listener(3) o SSL_new(3). Dicho dominio utilizará las banderas de dominio por defecto configuradas en el SSL_CTX, como se describe anteriormente.

CONSUMO DE RECURSOS DEL SO

Si se selecciona soporte completo de E/S bloqueantes utilizando SSL_DOMAIN_FLAG_BLOCKING, se debe asignar al menos un socket, un manejador de SO similar a un socket o un descriptor de archivo para permitir que un hilo despierte a otros hilos que puedan estar bloqueados en llamadas a interfaces de sondeo de sockets del SO, como select(2) o poll(2). Esto lo asigna automáticamente OpenSSL internamente.

Si se selecciona el Modelo de Concurrencia Asistido por Hilo (TACM), se genera un hilo en segundo plano. Esto también implica SSL_DOMAIN_FLAG_BLOCKING y lo anterior.

El consumo interno de mutexes, variables de condición, bloqueos de giro u otros primitivos de sincronización de hilos similares por parte de OpenSSL no está especificado bajo ningún modelo de concurrencia.

El consumo interno de hilos por parte de OpenSSL no está especificado bajo el Modelo de Concurrencia Asistido por Hilo.

El consumo interno de sockets, manejadores de SO similares a sockets o descriptores de archivo por parte de OpenSSL, u otros recursos necesarios para soportar la notificación entre hilos, no está especificado bajo el Modelo de Concurrencia Asistido por Hilo o al usar SSL_DOMAIN_FLAG_BLOCKING.

COMPORTAMIENTO DE LOS OBJETOS SSL

Un objeto SSL QUIC tiene el modo de bloqueo habilitado por defecto cuando se cumplen **todos** los siguientes criterios:

  • SSL_DOMAIN_FLAG_BLOCKING o SSL_DOMAIN_FLAG_LEGACY_BLOCKING está habilitado; y
  • La conexión QUIC se está utilizando con BIOs de lectura y escritura de red que exponen descriptores de sondeo compatibles. Consulte openssl-quic(7) para obtener detalles.

En todos los demás casos, un objeto SSL QUIC tiene el modo de bloqueo deshabilitado por defecto. El modo de bloqueo se puede cambiar explícitamente usando SSL_set_blocking_mode(3).
