Nombre

openvpn - Demonio de túnel IP seguro

SINOPSIS

openvpn [ opciones ... ]
openvpn  --help

INTRODUCCIÓN

OpenVPN es un demonio VPN de código abierto de James Yonan. Debido a que OpenVPN intenta ser una herramienta VPN universal que ofrece una gran flexibilidad, hay muchas opciones en esta página de manual. Si eres nuevo en OpenVPN, es posible que desees saltar a la sección de ejemplos, donde verás cómo construir VPNs simples desde la línea de comandos sin necesidad de un archivo de configuración.

También ten en cuenta que hay más documentación y ejemplos en el sitio web de OpenVPN: https://openvpn.net/

Y si deseas ver una versión más corta de este manual, consulta el mensaje de uso de openvpn que se puede obtener ejecutando openvpn sin parámetros.

DESCRIPCIÓN

OpenVPN es un demonio VPN robusto y altamente flexible. OpenVPN soporta transporte de túnel SSL/TLS, bridging de Ethernet, TCP o UDP a través de proxies o NAT, soporte para direcciones IP dinámicas y DHCP, escalabilidad a cientos o miles de usuarios y portabilidad a la mayoría de las plataformas de sistemas operativos.

OpenVPN está estrechamente ligado a la biblioteca OpenSSL y deriva gran parte de sus capacidades criptográficas de ella.

OpenVPN soporta cifrado convencional utilizando una clave secreta precompartida (modo Clave Estática) o seguridad de clave pública (modo SSL/TLS) utilizando certificados de cliente y servidor. OpenVPN también soporta túneles TCP/UDP no cifrados.

OpenVPN está diseñado para trabajar con la interfaz de red virtual TUN/TAP que existe en la mayoría de las plataformas.

En general, OpenVPN tiene como objetivo ofrecer muchas de las características clave de IPSec pero con una huella relativamente ligera.

OPCIONES

OpenVPN permite que cualquier opción se coloque ya sea en la línea de comandos o en un archivo de configuración. Aunque todas las opciones de la línea de comandos van precedidas de un guion doble ("--"), este prefijo puede eliminarse cuando una opción se coloca en un archivo de configuración.

Opciones Generales

Esta sección cubre las opciones generales que son accesibles independientemente del modo en que esté configurado OpenVPN.

--help
Muestra las opciones.
--auth-nocache
No almacenar en caché los nombres de usuario/contraseñas de --askpass o --auth-user-pass en la memoria virtual.

Si se especifica, esta directiva hará que OpenVPN olvide inmediatamente las entradas de nombre de usuario/contraseña después de que se utilicen. Como resultado, cuando OpenVPN necesite un nombre de usuario/contraseña, solicitará la entrada desde stdin, lo que puede ser varias veces durante la duración de una sesión de OpenVPN.

Al usar --auth-nocache en combinación con un archivo de usuario/contraseña y --chroot o --daemon, asegúrate de usar una ruta absoluta.

--cd dir
Cambia el directorio a dir antes de leer cualquier archivo, como archivos de configuración, archivos de clave, scripts, etc. dir debe ser una ruta absoluta, con un "/" inicial y sin referencias al directorio actual como . o ...

Esta opción es útil cuando ejecutas OpenVPN en modo --daemon y deseas consolidar todos tus archivos de control de OpenVPN en una ubicación.

--chroot dir
Cambia la raíz del sistema de archivos a dir después de la inicialización. --chroot esencialmente redefine dir como el árbol de directorios de nivel superior (/). Por lo tanto, OpenVPN no podrá acceder a ningún archivo fuera de este árbol. Esto puede ser deseable desde el punto de vista de la seguridad.

Dado que la operación de chroot se retrasa hasta después de la inicialización, la mayoría de las opciones de OpenVPN que hacen referencia a archivos operarán en un contexto pre-chroot.

En muchos casos, el parámetro dir puede apuntar a un directorio vacío; sin embargo, pueden surgir complicaciones cuando se ejecutan scripts o reinicios después de la operación de chroot.

Nota: Es probable que la biblioteca SSL necesite que /dev/urandom esté disponible dentro del directorio chroot dir. Esto se debe a que las bibliotecas SSL ocasionalmente necesitan recopilar aleatoriedad fresca. Los kernels de Linux más recientes y algunos BSD implementan una llamada al sistema getrandom() o getentropy() que elimina la necesidad de que /dev/urandom esté disponible.

--compat-mode version
Esta opción proporciona una forma conveniente de alterar los valores predeterminados de OpenVPN para que sean más compatibles con la versión version especificada. Todos los cambios que aplica esta opción se pueden lograr también utilizando opciones de configuración individuales.

La versión especificada con esta opción es la versión de OpenVPN con la que el peer de OpenVPN debe intentar ser compatible. En general, OpenVPN debería ser compatible con las dos versiones anteriores sin esta opción. Por ejemplo, OpenVPN 2.6.0 debería ser compatible con 2.5.x y 2.4.x sin esta opción. Sin embargo, puede haber algunos casos extremos que aún requieran esta opción incluso en estos casos.

Nota: Usar esta opción revierte los valores predeterminados a valores ya no recomendados y debe evitarse si es posible. Establecer esta opción puede reducir la seguridad o deshabilitar características como la descarga de datos.

La siguiente tabla detalla qué valores predeterminados se cambian según la versión especificada.

  • 2.5.x o inferior: --allow-compression asym se agrega automáticamente a la configuración si no hay otras opciones de compresión presentes.
  • 2.4.x o inferior: El cifrado en --cipher se agrega a --data-ciphers.
  • 2.3.x o inferior: --data-ciphers-fallback se agrega automáticamente con el mismo cifrado que --cipher.
  • 2.3.6 o inferior: --tls-version-min 1.0 se agrega a la configuración cuando --tls-version-min no se establece explícitamente.

Si no es necesario, se debe evitar esta opción. Establecer esta opción puede reducir la seguridad o deshabilitar características como la descarga de datos.

--config archivo
Carga opciones de configuración adicionales desde archivo donde cada línea corresponde a una opción de línea de comandos, pero con el prefijo -- eliminado.

Si --config archivo es la única opción para el comando openvpn, se puede eliminar el --config y el comando se puede dar como openvpn archivo

Tenga en cuenta que los archivos de configuración se pueden anidar hasta una profundidad razonable.

Los caracteres de comillas dobles o simples ('', '') se pueden usar para encerrar parámetros individuales que contienen espacios en blanco, y los caracteres de '#' o ';' en la primera columna se pueden usar para indicar comentarios.

Tenga en cuenta que OpenVPN 2.0 y superior realiza el escape de shell basado en barras invertidas para caracteres que no están entre comillas simples, por lo que se deben observar las siguientes correspondencias:

\\       Se mapea a un carácter de barra invertida simple (\).
\"       Pasa un carácter de comillas dobles literal ("), no
         lo interpretes como delimitador de un parámetro.
\[ESPACIO] Pasa un carácter de espacio o tabulación literal, no
         lo interpretes como delimitador de un parámetro.

Por ejemplo, en Windows, use barras invertidas dobles para representar nombres de ruta:

secret "c:\\OpenVPN\\secret.key"

Para ver ejemplos de archivos de configuración, consulte https://openvpn.net/community-resources/how-to/

Aquí tienes un ejemplo de archivo de configuración:

#
# Archivo de configuración de ejemplo de OpenVPN para
# usar una clave estática precompartida.
#
# '#' o ';' se pueden usar para delimitar comentarios.
# Usa un dispositivo tun dinámico.
dev tun
# Nuestro par remoto
remote mypeer.mydomain
# 10.1.0.1 es nuestro punto final de VPN local
# 10.1.0.2 es nuestro punto final de VPN remoto
ifconfig 10.1.0.1 10.1.0.2
# Nuestra clave estática precompartida
secret static.key
--daemon nombre_prog
Conviértete en un demonio después de completar todas las funciones de inicialización.

Sintaxis válida:

daemon
daemon progname

Esta opción hará que toda la salida de mensajes y errores se envíe al archivo syslog (como /var/log/messages), excepto la salida de scripts y comandos ifconfig, que se enviarán a /dev/null a menos que se redirijan de otra manera. La redirección de syslog ocurre inmediatamente en el punto en que se analiza --daemon en la línea de comandos, aunque el punto de daemonización ocurre más tarde. Si está presente alguna de las opciones --log, anulará la redirección de syslog.

El parámetro opcional progname hará que OpenVPN informe su nombre de programa al registrador del sistema como progname. Esto puede ser útil para vincular los mensajes de OpenVPN en el archivo syslog con túneles específicos. Cuando no se especifica, progname tiene el valor predeterminado de openvpn.

Cuando OpenVPN se ejecuta con la opción --daemon, intentará retrasar la daemonización hasta que la mayoría de las funciones de inicialización que son capaces de generar errores fatales se hayan completado. Esto significa que los scripts de inicialización pueden probar el estado de retorno del comando openvpn para obtener una indicación bastante confiable de si el comando se ha inicializado correctamente y ha entrado en el bucle de eventos de reenvío de paquetes.

En OpenVPN, la gran mayoría de los errores que ocurren después de la inicialización no son fatales.

Nota: tan pronto como OpenVPN se haya daemonizado, ya no podrá solicitar nombres de usuario, contraseñas o frases de contraseña de clave. Esto tiene ciertas consecuencias, a saber, que el uso de una clave privada protegida por contraseña fallará a menos que se utilice la opción --askpass para indicar a OpenVPN que solicite la frase de contraseña (este requisito es nuevo en la versión 2.3.7 y es una consecuencia de llamar a daemon() antes de inicializar la capa criptográfica).

Además, el uso de --daemon junto con --auth-user-pass (introducido en la consola) y --auth-nocache fallará tan pronto como ocurra la renegociación de claves (y la reautenticación).

--disable-dco
Deshabilita la "descarga del canal de datos" (DCO).

En Linux, no utiliza el controlador de dispositivo ovpn-dco, sino que se basa en el módulo tun heredado.

Es posible que desee utilizar esta opción si su servidor necesita permitir la conexión de clientes anteriores a la versión 2.4.

--disable-occ
EN DESUSO Deshabilita la "comprobación de consistencia de opciones" (OCC) en configuraciones que no utilizan TLS.

No muestra un mensaje de advertencia si se detectan inconsistencias en las opciones entre pares. Un ejemplo de inconsistencia de opciones sería que un par utiliza --dev tun mientras que el otro par utiliza --dev tap.

No se recomienda el uso de esta opción, pero se proporciona como una solución temporal en situaciones en las que una versión reciente de OpenVPN debe conectarse a una versión antigua.

--engine nombre-motor
Habilita la funcionalidad del motor criptográfico basado en hardware de OpenSSL.

Sintaxis válidas:

engine
engine nombre-motor

Si se especifica nombre-motor, utiliza un motor criptográfico específico. Utilice la opción independiente --show-engines para ver los motores criptográficos que admite OpenSSL.

--fast-io
Optimiza las escrituras de E/S de TUN/TAP/UDP evitando una llamada a poll/epoll/select antes de la operación de escritura. El propósito de dicha llamada normalmente sería bloquear hasta que el dispositivo o el socket estén listos para aceptar la escritura. Dicho bloqueo es innecesario en algunas plataformas que no admiten el bloqueo de escritura en sockets UDP o dispositivos TUN/TAP. En tales casos, se puede optimizar el bucle de eventos evitando la llamada poll/epoll/select, mejorando la eficiencia de la CPU entre un 5% y un 10%.

Esta opción solo se puede utilizar en sistemas que no sean de Windows, cuando se especifica --proto udp y cuando --shaper *no* se especifica.

--group grupo
Similar a la opción --user, esta opción cambia el ID de grupo del proceso OpenVPN a grupo después de la inicialización.
--ignore-unknown-option args
Sintaxis válida:
ignore-unknown-options opt1 opt2 opt3 ... optN

Cuando se encuentra una de las opciones opt1 ... optN en el archivo de configuración, el análisis del archivo de configuración no falla si esta versión de OpenVPN no admite la opción. Se pueden dar múltiples opciones --ignore-unknown-option para admitir un mayor número de opciones a ignorar.

Esta opción debe usarse con precaución, ya que existen buenas razones de seguridad para que OpenVPN falle si detecta problemas en un archivo de configuración. Dicho esto, existen razones válidas para querer que las nuevas funciones de software degraden con gracia cuando son encontradas por versiones de software antiguas.

--ignore-unknown-option está disponible desde OpenVPN 2.3.3.

--iproute cmd
Establece un comando alternativo para ejecutar en lugar del comando predeterminado iproute2. Se puede utilizar para ejecutar OpenVPN en un entorno sin privilegios.
--keying-material-exporter args
Guarda el material de clave exportado [RFC5705] de len bytes (debe estar entre 16 y 4095 bytes) utilizando la etiqueta en el entorno (exported_keying_material) para su uso por parte de los complementos en la devolución de llamada OPENVPN_PLUGIN_TLS_FINAL.

Sintaxis válida:

keying-material-exporter label len

Tenga en cuenta que las etiquetas del exportador tienen el potencial de entrar en conflicto con las etiquetas PRF existentes. Para evitar esto, las etiquetas *deben* comenzar con EXPORTER.

--mlock
Deshabilita la paginación llamando a la función POSIX mlockall. Requiere que OpenVPN se ejecute inicialmente como root (aunque OpenVPN puede posterioresmente reducir sus privilegios de UID utilizando la opción --user).

El uso de esta opción garantiza que el material de clave y los datos del túnel nunca se escriban en el disco debido a las operaciones de paginación de memoria virtual que ocurren en la mayoría de los sistemas operativos modernos. Asegura que incluso si un atacante pudiera comprometer la máquina que ejecuta OpenVPN, no podría escanear el archivo de intercambio del sistema para recuperar claves efímeras usadas previamente, que se utilizan durante un período de tiempo regido por las opciones --reneg (ver más abajo) y luego se descartan.

La desventaja de usar --mlock es que reducirá la cantidad de memoria física disponible para otras aplicaciones.

El límite de cuánta memoria se puede bloquear y cómo se aplica ese límite dependen del sistema operativo. En Linux, el límite predeterminado que un proceso sin privilegios puede bloquear (RLIMIT_MEMLOCK) es bajo, y si los privilegios se reducen más tarde, las futuras asignaciones de memoria muy probablemente fallarán. El límite se puede aumentar usando directivas ulimit o systemd dependiendo de cómo se inicie OpenVPN.

Si la plataforma tiene la llamada al sistema getrlimit(2), OpenVPN verificará la cantidad de memoria bloqueable con mlock antes de llamar a mlockall(2), y trata de aumentar el límite a 100 MB si se configura menos que eso. 100 MB es algo arbitrario: es suficiente para una implementación de OpenVPN de tamaño moderado, pero el uso de memoria podría superar eso si el número de clientes concurrentes es alto.

--nice n
Cambia la prioridad del proceso después de la inicialización (n mayor que 0 es menor prioridad, n menor que cero es mayor prioridad).
--persist-key
No vuelva a leer los archivos de clave después de SIGUSR1 o --ping-restart.

Esta opción se puede combinar con --user para permitir reinicios activados por la señal SIGUSR1. Normalmente, si se eliminan los privilegios de root en OpenVPN, el demonio no se puede reiniciar ya que ahora no podrá volver a leer los archivos de clave protegidos.

Esta opción resuelve el problema manteniendo las claves a través de los reinicios de SIGUSR1, por lo que no es necesario volver a leerlas.

--providers proveedores
Carga la lista de proveedores (OpenSSL). Esto es útil principalmente para utilizar un proveedor externo para la gestión de claves como tpm2-openssl o para cargar el proveedor heredado con
--providers legacy default

El comportamiento de cambiar esta opción entre SIGHUP puede no ser el correcto. Si necesita cambiar/agregar/eliminar esta opción, reinicie completamente OpenVPN.

--remap-usr1 signal
Controla si las señales SIGUSR1 generadas interna o externamente se reconfiguran a SIGHUP (reiniciar sin persistir el estado) o SIGTERM (salir).

signal se puede establecer en SIGHUP o SIGTERM. Por defecto, no se realiza ninguna reconfiguración.

--script-security level
Esta directiva ofrece control a nivel de política sobre el uso de programas y scripts externos por parte de OpenVPN. Valores de level más bajos son más restrictivos, valores más altos son más permisivos. Ajustes para level:
0
Estrictamente no llamar a programas externos.
1
(Predeterminado) Solo llama a ejecutables integrados como ifconfig, ip, route o netsh.
2
Permite llamar a ejecutables integrados y scripts definidos por el usuario.
3
Permite pasar contraseñas a scripts a través de variables de entorno (potencialmente inseguro).

Las versiones de OpenVPN anteriores a la v2.3 también admitían un indicador method que indicaba cómo OpenVPN debía llamar a los comandos y scripts externos. Este podía ser execve o system. A partir de OpenVPN 2.3, este indicador ya no se acepta. En la mayoría de los entornos *nix, se ha utilizado el enfoque execve() sin ningún problema.

Algunas directivas como --up permiten pasar opciones al script externo. En estos casos, asegúrese de que el nombre del script no contenga espacios o el analizador de configuración fallará porque no puede determinar dónde termina el nombre del script y comienzan las opciones del script.

Para ejecutar scripts en Windows en versiones anteriores de OpenVPN, necesitaba agregar una ruta completa al intérprete de scripts que pudiera analizar el script o usar el método de sistema

OpenVPN scripts

There are several ways to run scripts from OpenVPN. The most basic is to use the --up, --down, and --pre-up options. These options allow you to specify a script that will be executed at certain points in the OpenVPN process. For example, the --up script is executed after the tunnel is up and the interface is configured.

Scripts can be written in any scripting language, such as Perl, Python, or shell scripts. However, it is important to note that as of OpenVPN 2.3, you must use the full path to the script interpreter when running non-executable files. This is not needed for executable files, such as .exe, .com, .bat or .cmd files.

For example, if you have a Visual Basic script, you must use this syntax now:

--up 'C:\\Windows\\System32\\wscript.exe C:\\Program\ Files\\OpenVPN\\config\\my-up-script.vbs'

Please note the single quote marks and the escaping of the backslashes (\) and the space character.

The reason the support for the system flag was removed is due to the security implications with shell expansions when executing scripts via the system() call.

--setcon context
Apply SELinux context after initialization. This essentially provides the ability to restrict OpenVPN's rights to only network I/O operations, thanks to SELinux. This goes further than --user and --chroot in that those two, while being great security features, unfortunately do not protect against privilege escalation by exploitation of a vulnerable system call. You can of course combine all three, but please note that since setcon requires access to /proc you will have to provide it inside the chroot directory (e.g. with mount --bind).

Since the setcon operation is delayed until after initialization, OpenVPN can be restricted to just network-related system calls, whereas by applying the context before startup (such as the OpenVPN one provided in the SELinux Reference Policies) you will have to allow many things required only during initialization.

Like with chroot, complications can result when scripts or restarts are executed after the setcon operation, which is why you should really consider using the --persist-key and --persist-tun options.

--status args
Write operational status to file every n seconds. n defaults to 60 if not specified.

Valid syntaxes:

status file
status file n

Status can also be written to the syslog by sending a SIGUSR2 signal.

With multi-client capability enabled on a server, the status file includes a list of clients and a routing table. The output format can be controlled by the --status-version option in that case.

For clients or instances running in point-to-point mode, it will contain the traffic statistics.

--status-version n
Set the status file format version number to n.

This only affects the status file on servers with multi-client capability enabled. Valid status version values:

1
Traditional format (default). The client list contains the following fields comma-separated: Common Name, Real Address, Bytes Received, Bytes Sent, Connected Since.
2
A more reliable format for external processing. Compared to version 1, the client list contains some additional fields: Virtual Address, Virtual IPv6 Address, Username, Client ID, Peer ID, Data Channel Cipher. Future versions may extend the number of fields.
3
Identical to 2, but fields are tab-separated.
--test-crypto
Do a self-test of OpenVPN's crypto options by encrypting and decrypting test packets using the data channel encryption options specified above. This option does not require a peer to function, and therefore can be specified without --dev or --remote.

The typical usage of --test-crypto would be something like this:

openvpn --test-crypto --secret key

or

openvpn --test-crypto --secret key --verb 9

This option is very useful to test OpenVPN after it has been ported to a new platform, or to isolate problems in the compiler, OpenSSL crypto library, or OpenVPN's crypto code. Since it is a self-test mode, problems with encryption and authentication can be debugged independently of network and tunnel issues.

--tmp-dir dir
Specify a directory dir for temporary files instead of the default TMPDIR (or "/tmp" if unset). Note that it must be writable by the main process after it has dropped root privileges.

This directory will be used to communicate with scripts and plugins:

  • --client-connect scripts and OPENVPN_PLUGIN_CLIENT_CONNECT plug-in hook to dynamically generate client-specific configuration client_connect_config_file and return success/failure via client_connect_deferred_file when using deferred client connect method
  • OPENVPN_PLUGIN_AUTH_USER_PASS_VERIFY plug-in hooks returns success/failure via auth_control_file when using deferred auth method and pending authentication via auth_pending_file.
--use-prediction-resistance
Enable prediction resistance on mbed TLS's RNG.

Enabling prediction resistance causes the RNG to reseed in each call for random. Reseeding this often can quickly deplete the kernel entropy pool.

If you need this option, please consider running a daemon that adds entropy to the kernel pool.

--user user
Change the user ID of the OpenVPN process to user after initialization, dropping privileges in the process. This option is useful to protect the system in the event that some hostile party was able to gain control of an OpenVPN session. Though OpenVPN's security features make this unlikely, it is provided as a second line of defense.

By setting user to an unprivileged user dedicated to run openvpn, the hostile party would be limited in what damage they could cause. Of course once you take away privileges, you cannot return them to an OpenVPN session. This means, for example, that if you want to reset an OpenVPN daemon with a SIGUSR1 signal (for example in response to a DHCP reset), you should make use of one or more of the --persist options to ensure that OpenVPN doesn't need to execute any privileged operations in order to restart (such as re-reading key files or running ifconfig on the TUN device).

NOTE: Previous versions of openvpn used nobody as the example unpriviledged user. It is not recommended to actually use that user since it is usually used by other system services already. Always create a dedicated user for openvpn.

Opciones de protocolo

Las opciones en esta sección afectan a las funcionalidades disponibles en el protocolo de red de OpenVPN. Muchas de estas opciones también definen las opciones de cifrado del canal de datos en el protocolo de red de OpenVPN. Estas opciones deben configurarse de manera compatible entre el lado local y el remoto.

--allow-compression modo
Como se describe en la opción --compress, la compresión es una opción potencialmente peligrosa. Esta opción permite controlar el comportamiento de OpenVPN cuando se utiliza y se permite la compresión.

Sintaxis válidas:

allow-compression
allow-compression mode

El argumento mode puede ser uno de los siguientes valores:

asym
OpenVPN solo descifrará paquetes de bajada pero no comprimirá los paquetes de subida. Esto también permite la migración para deshabilitar la compresión cuando no es factible cambiar simultáneamente las configuraciones del servidor y del cliente para eliminar la compresión.
no (predeterminado)
OpenVPN rechazará cualquier compresión. Si la descarga de canal de datos está habilitada, OpenVPN también rechazará el encapsulado de compresión (stub).
yes
OpenVPN enviará y recibirá paquetes comprimidos.
--auth alg
Autentica los paquetes del canal de datos y (si están habilitados) los paquetes del canal de control tls-auth con HMAC utilizando el algoritmo de resumen de mensajes alg. (El valor predeterminado es SHA1). HMAC es un algoritmo de autenticación de mensajes (MAC) de uso común que utiliza una cadena de datos, un algoritmo de hash seguro y una clave para producir una firma digital.

El protocolo de canal de datos de OpenVPN utiliza cifrado-luego-MAC (es decir, primero cifra un paquete y luego aplica HMAC al texto cifrado resultante), lo que previene ataques de relleno oracle.

Si se elige un modo de cifrado AEAD (por ejemplo, GCM), el algoritmo --auth especificado se ignora para el canal de datos y se utiliza el método de autenticación del cifrado AEAD en su lugar. Tenga en cuenta que alg todavía especifica el resumen utilizado para tls-auth.

En el modo de cifrado de clave estática, la clave HMAC se incluye en el archivo de clave generado por --genkey. En el modo TLS, la clave HMAC se genera dinámicamente y se comparte entre pares a través del canal de control TLS. Si OpenVPN recibe un paquete con un HMAC incorrecto, lo descartará. HMAC generalmente agrega 16 o 20 bytes por paquete. Establezca alg=none para deshabilitar la autenticación.

Para obtener más información sobre HMAC, consulte https://tools.ietf.org/html/rfc2104

--cipher alg
Esta opción ya no debe usarse en modo TLS y todavía existe por dos razones:
  • compatibilidad con configuraciones antiguas que aún la tienen;
  • permitir que los usuarios que se conectan a pares de OpenVPN anteriores a 2.6.0 tengan --cipher configurado de la misma manera que el interlocutor remoto. Esto puede evitar advertencias de MTU/tamaño de trama.

Antes de 2.4.0, esta opción se usaba para seleccionar el cifrado que se configuraría en el canal de datos; sin embargo, las versiones posteriores generalmente ignoraban esta directiva en favor de un cifrado negociado. A partir de 2.6.0, esta opción siempre se ignora en modo TLS en lo que respecta a la configuración del cifrado y solo controlará el cifrado para el modo de clave precompartida --secret (nota: este modo está obsoleto y estrictamente no se recomienda).

Si desea especificar el cifrado a utilizar en el canal de datos, consulte --data-ciphers (para negociación regular) y --data-ciphers-fallback (para una opción de respaldo cuando la negociación no puede realizarse porque el otro par es antiguo o tiene la negociación deshabilitada).

Para ver los cifrados disponibles con OpenVPN, use la opción --show-ciphers.

Establezca alg en none para deshabilitar el cifrado.

--compress algorithm
OBSOLETO Habilita un algoritmo de compresión. La compresión generalmente no se recomienda. Los túneles VPN que utilizan compresión son susceptibles al vector de ataque VORALCE. Consulte también el parámetro migrate a continuación.

El parámetro algorithm puede ser lzo, lz4, lz4-v2, stub, stub-v2, migrate o vacío. LZO y LZ4 son diferentes algoritmos de compresión, y LZ4 generalmente ofrece el mejor rendimiento con el menor uso de CPU.

Las variantes lz4-v2 y stub-v2 implementan un encapsulado mejorado que no agrega sobrecarga cuando los paquetes no se pueden comprimir. Todas las demás variantes siempre agregan un byte de encapsulado adicional en comparación con la ausencia de encapsulado de compresión.

Especialmente stub-v2 es esencialmente idéntico a no tener compresión ni encapsulado de compresión, ya que su encabezado indica la versión IP 5 en una configuración tun y puede usarse (y abusarse) para deshabilitar completamente la compresión a los clientes. (Ver la opción migrate a continuación)

Si el parámetro algorithm es stub, stub-v2 o está vacío, la compresión se desactivará, pero el encapsulado de paquete para la compresión permanecerá habilitado, permitiendo que se envíe una configuración diferente más adelante. Además, stub y stub-v2 deshabilitarán el anuncio de soporte de compresión lzo y lz4 a través de las variables IV_ al servidor.

Nota: la opción stub (o vacía) NO es compatible con la opción anterior --comp-lzo no.

Usar migrate como algoritmo de compresión habilita un modo de migración especial. Permite la migración de las opciones --compress/--comp-lzo a la no compresión. Esta opción establece el servidor en modo de no compresión y el servidor se comporta de manera idéntica a un servidor sin opción de compresión para todos los clientes sin compresión en su configuración. Sin embargo, si se detecta un cliente que indica que se utiliza compresión (a través de OCC), el servidor agregará automáticamente --push compress stub-v2 a la configuración específica del cliente si es compatible con el cliente y, de lo contrario, cambiará a comp-lzo no y agregará --push comp-lzo a la configuración específica del cliente.

*Consideraciones de seguridad*

La compresión y el cifrado son una combinación delicada. Si un atacante conoce o puede controlar (partes de) el texto plano de los paquetes que contienen secretos, podría ser capaz de extraer el secreto si la compresión está habilitada. Consulte, por ejemplo, los ataques CRIME y BREACH en TLS y VORACLE en VPN, que también se aprovechan para romper el cifrado. Si no está completamente seguro de que lo anterior no se aplica a su tráfico, se le recomienda no habilitar la compresión.

--comp-lzo mode
OBSOLETO Habilita el algoritmo de compresión LZO. La compresión generalmente no se recomienda. Los túneles VPN que utilizan compresión son susceptibles al vector de ataque VORALCE.

Utiliza compresión LZO; puede añadir hasta 1 byte por paquete para datos incompresibles. mode puede ser yes, no o adaptive (predeterminado).

En una configuración de modo servidor, es posible activar o desactivar selectivamente la compresión para clientes individuales.

Primero, asegúrese de que el archivo de configuración del lado del cliente habilite la compresión selectiva teniendo al menos una directiva --comp-lzo, como --comp-lzo no. Esto desactivará la compresión por defecto, pero permitirá que una directiva futura enviada desde el servidor cambie dinámicamente la configuración on/off/adaptive.

A continuación, en un archivo --client-config-dir, especifique la configuración de compresión para el cliente, por ejemplo:

comp-lzo yes
push "comp-lzo yes"

La primera línea establece la configuración comp-lzo para el lado del servidor del enlace, la segunda establece el lado del cliente.

--comp-noadapt
OBSOLETO Cuando se utiliza junto con --comp-lzo, esta opción deshabilitará el algoritmo de compresión adaptativa de OpenVPN. Normalmente, la compresión adaptativa está habilitada con --comp-lzo.

La compresión adaptativa intenta optimizar el caso en el que tiene la compresión habilitada, pero está enviando predominantemente paquetes incompresibles (o precomprimidos) a través del túnel, como una transferencia FTP o rsync de un archivo grande y comprimido. Con compresión adaptativa, OpenVPN muestreará periódicamente el proceso de compresión para medir su eficiencia. Si los datos que se envían a través del túnel ya están comprimidos, la eficiencia de la compresión será muy baja, lo que hará que openvpn desactive la compresión durante un período de tiempo hasta la próxima prueba de muestreo.

--secret args
OBSOLETO Habilita el modo de cifrado de clave estática (no TLS). Utiliza el secreto precompartido file que fue generado con --genkey.

Sintaxis válidas:

secret archivo
secret archivo direccion

El parámetro opcional direction habilita el uso de 4 claves distintas (HMAC-envío, cifrado-encriptación, HMAC-recepción, cifrado-desencriptación), de modo que cada dirección de flujo de datos tenga un conjunto diferente de claves HMAC y de cifrado. Esto tiene una serie de propiedades de seguridad deseables, incluido la eliminación de ciertos tipos de ataques de denegación de servicio y de repetición de mensajes.

Cuando se omite el parámetro direction, se utilizan 2 claves de forma bidireccional, una para HMAC y la otra para cifrado/desencriptación.

El parámetro direction siempre debe ser complementario en cada lado de la conexión, es decir, un lado debe usar 0 y el otro debe usar 1, o ambos lados deben omitirlo por completo.

El parámetro direction requiere que file contenga una clave de 2048 bits. Mientras que las versiones anteriores a 1.5 de OpenVPN generan archivos de clave de 1024 bits, cualquier versión de OpenVPN que admita el parámetro direction también admitirá la generación de archivos de clave de 2048 bits utilizando la opción --genkey.

El modo de cifrado de clave estática tiene ciertas ventajas, la principal es la facilidad de configuración.

No hay certificados ni autoridades certificadoras ni complejas negociaciones, protocolos ni apretones de manos. El único requisito es que tenga un canal seguro preexistente con su par (como ssh) para copiar inicialmente la clave. Este requisito, junto con el hecho de que su clave nunca cambia a menos que genere una nueva manualmente, lo hace algo menos seguro que el modo TLS (ver más abajo). Si un atacante logra robar su clave, todo lo que se haya cifrado con ella se verá comprometido. Compárelo con las características de secreto perfecto hacia adelante del modo TLS (que utiliza el intercambio de claves Diffie-Hellman), donde incluso si un atacante pudiera robar su clave privada, no obtendría ninguna información que le ayude a descifrar sesiones pasadas.

Otro aspecto ventajoso del modo de cifrado de clave estática es que es un protocolo sin apretón de manos sin ninguna firma o característica distintiva (como un encabezado o una secuencia de apretón de manos de protocolo) que marque los paquetes de texto cifrado como generados por OpenVPN. Cualquiera que escuche en la red no verá más que datos de apariencia aleatoria.

--auth-token token
Esta no es una opción para usar directamente en ningún archivo de configuración, sino que se envía desde un script --client-connect o un --plugin que se engancha a las llamadas OPENVPN_PLUGIN_CLIENT_CONNECT o OPENVPN_PLUGIN_CLIENT_CONNECT_V2. Esta opción proporciona la posibilidad de reemplazar la contraseña de los clientes con un token de autenticación durante la vida útil del cliente OpenVPN.

Cada vez que se renegocia la conexión y se activa el script --auth-user-pass-verify o el --plugin que utiliza el hook OPENVPN_PLUGIN_AUTH_USER_PASS_VERIFY, pasará este token como contraseña en lugar de la contraseña que el usuario proporcionó. El token de autenticación solo se puede restablecer mediante una reconexión completa donde el servidor pueda enviar nuevas opciones al cliente. La contraseña que ingresó el usuario nunca se conserva una vez que se ha configurado un token de autenticación. Si el lado del servidor de OpenVPN rechaza el token de autenticación, el cliente recibirá un AUTH_FAILED y se desconectará.

El propósito de esto es permitir métodos de autenticación de dos factores, como HOTP o TOTP, sin necesidad de recuperar un nuevo código OTP cada vez que se renegocia la conexión. Otro caso de uso es almacenar en caché los datos de autenticación en el cliente sin necesidad de tener la contraseña del usuario almacenada en memoria durante la vida útil de la sesión.

Para utilizar esta función, el script --client-connect o --plugin debe colocar

push "auth-token VALOR_UNICO_DEL_TOKEN"

en el archivo/búfer de datos de configuración dinámicos. Esto hará que el servidor OpenVPN envíe este valor al cliente, lo que reemplazará la contraseña local con el VALOR_UNICO_DEL_TOKEN.

Los clientes más recientes (2.4.7+) volverán al método de contraseña original después de un error de autenticación. Los clientes más antiguos seguirán utilizando el valor del token y reaccionarán de acuerdo con --auth-retry.

Controla cómo responde OpenVPN a los errores de verificación de nombre de usuario/contraseña, como la respuesta del lado del cliente a un mensaje AUTH_FAILED del servidor o la falla de verificación de la contraseña de la clave privada.

--explicit-exit-notify n
En modo cliente UDP o modo punto a punto, envía una notificación de salida al servidor/par si el túnel se reinicia o el proceso OpenVPN se cierra. En modo cliente, al salir/reiniciar, esta opción indicará al servidor que cierre inmediatamente su instancia de cliente en lugar de esperar a un tiempo de espera.

Si tanto el servidor como el cliente admiten el envío de este mensaje utilizando el canal de control, el mensaje se enviará como un mensaje del canal de control. De lo contrario, el mensaje se enviará como un mensaje del canal de datos, que será ignorado por los pares con descarga de canal de datos.

El parámetro n (predeterminado 1 si no está presente) controla el número máximo de intentos que el cliente intentará reenviar el mensaje de notificación de salida si los mensajes se envían en modo de canal de datos.

En modo servidor UDP, envía el comando del canal de control RESTART a los clientes conectados. El parámetro n (predeterminado 1 si no está presente) controla el comportamiento del cliente. Con n = 1 el cliente intentará reconectarse al mismo servidor, con n = 2 el cliente avanzará al siguiente servidor.

OpenVPN no enviará ninguna notificación de salida a menos que esta opción esté habilitada.

--proto-force p
Al iterar a través de perfiles de conexión, solo considere los perfiles que usan el protocolo p (tcp | udp).

Tenga en cuenta que esto solo filtra por el protocolo de capa de transporte, es decir, UDP o TCP. Esto no afecta si se utiliza IPv4 o IPv6 como protocolo IP.

--pull
Esta opción debe usarse en un cliente que se conecta a un servidor multi-cliente. Indica a OpenVPN que acepte opciones enviadas por el servidor, siempre que formen parte del conjunto legal de opciones que se pueden enviar (tenga en cuenta que la opción --pull está implícita por --client).

En particular, --pull permite al servidor enviar rutas al cliente, por lo que no debe usar --pull o --client en situaciones en las que no confíe en que el servidor tenga control sobre la tabla de enrutamiento del cliente.

--pull-filter args
Filtra las opciones enviadas por el servidor al cliente.

Sintaxis válidas:

pull-filter accept texto
pull-filter ignore texto
pull-filter reject texto

Filtra las opciones recibidas del servidor si la opción comienza con texto. La bandera de acción accept permite la opción, ignore la elimina y reject marca un error y desencadena un reinicio SIGUSR1. Los filtros se pueden especificar varias veces, y cada filtro se aplica en el orden en que se especifica. El filtrado de cada opción se detiene tan pronto como se encuentra una coincidencia. Las opciones no coincidentes se aceptan por defecto.

Se utiliza una comparación de prefijos para hacer coincidir texto con la opción recibida, de modo que

pull-filter ignore "route"

eliminaría todas las opciones enviadas que comiencen con route, lo que incluiría, por ejemplo, route-gateway. Encierre texto entre comillas para incluir espacios.

pull-filter accept "route 192.168.1."
pull-filter ignore "route "

eliminaría todas las rutas que no comiencen con 192.168.1.

Tenga en cuenta que reject puede resultar en un ciclo repetido de fallo y reconexión, a menos que se especifiquen varios remotos y la conexión al siguiente remoto tenga éxito. Para ignorar silenciosamente una opción enviada por el servidor, use ignore.

Opciones de Servidor

A partir de OpenVPN 2.0, se admite el modo servidor TCP/UDP multi-cliente, que se puede habilitar con la opción --mode server. En modo servidor, OpenVPN escuchará en un único puerto las conexiones de clientes entrantes. Todas las conexiones de clientes se enrutarán a través de una única interfaz tun o tap. Este modo está diseñado para escalabilidad y debería ser capaz de soportar cientos o incluso miles de clientes en hardware suficientemente rápido. Se debe utilizar la autenticación SSL/TLS en este modo.

--auth-gen-token args
Devuelve un token de autenticación a los clientes autenticados correctamente.

Sintaxis válida:

auth-gen-token [lifetime] [renewal-time] [external-auth]

Después de una autenticación exitosa de usuario/contraseña, el servidor OpenVPN, con esta opción, generará un token de autenticación temporal y lo enviará al cliente. En las siguientes renegociaciones, el cliente OpenVPN pasará este token en lugar de la contraseña del usuario. En el lado del servidor, el servidor realizará la autenticación del token internamente y NO realizará ninguna autenticación adicional contra los mecanismos de autenticación de usuario/contraseña externos configurados.

Los tokens implementados por este mecanismo incluyen una marca de tiempo inicial y una marca de tiempo de renovación, y están protegidos por HMAC.

El argumento lifetime define cuánto tiempo es válido el token generado. El tiempo de vida se define en segundos. Si no se establece lifetime o se establece en 0, el token nunca caducará.

Si renewal-time no se establece, se toma por defecto reneg-sec.

El token caducará ya sea después de que se alcance el lifetime configurado del token o después de no haber sido renovado durante más de 2 * renewal-time segundos. Los clientes recibirán tokens renovados en cada renegociación TLS. Si renewal-time es menor que reneg-sec, el servidor enviará un token de autenticación temporal actualizado cada reneweal-time segundos. Esto se hace para invalidar un token si un cliente está desconectado durante un tiempo suficiente, al mismo tiempo que se permiten tiempos de vida de token mucho más largos para clientes activos.

Esta característica es útil para entornos que están configurados para usar Contraseñas de Un Solo Uso (OTP) como parte de las autenticaciones de usuario/contraseña, y ese mecanismo de autenticación no implementa ningún soporte de token de autenticación.

Cuando está presente la palabra clave external-auth, el método de autenticación normal siempre se llamará incluso si auth-token tiene éxito. Normalmente, otros métodos de autenticación se omiten si la verificación de auth-token tiene éxito o falla.

Esta opción pospone esta decisión a los métodos de autenticación externos y verifica la validez de la cuenta y realiza otras comprobaciones.

En este modo, el entorno tendrá una variable session_id que contiene el ID de sesión de auth-gen-token. También está presente una variable de entorno session_state. Esta variable indica si el token de autenticación ha tenido éxito o no. Puede tener los siguientes valores:

Initial
No hay token del cliente.
Authenticated
El token es válido y no ha caducado.
Expired
El token es válido pero ha caducado.
Invalid
El token no es válido (fallo HMAC o longitud incorrecta)
AuthenticatedEmptyUser / ExpiredEmptyUser
El token no es válido con el nombre de usuario enviado por el cliente, pero sería válido (o caducado) si asumiéramos que se usó un nombre de usuario vacío en su lugar. Estos dos casos son una solución alternativa para el comportamiento en OpenVPN 3. Si esta solución alternativa no es necesaria, estos dos casos deben tratarse de la misma manera que Invalid.

Advertencia: Utilice esta función solo si desea que su método de autenticación se llame en cada verificación. Dado que se llama a la autenticación externa, también debe indicar un éxito o fallo de la autenticación. Se recomienda encarecidamente devolver un fallo de autenticación en el caso de auth-token inválido/caducado con la opción external-auth, a menos que el cliente pueda autenticarse de otra manera aceptable (por ejemplo, certificado de cliente), de lo contrario, devolver éxito conducirá a la omisión de la autenticación (al igual que devolver éxito con una contraseña incorrecta de un script).

--auth-user-pass-optional
Permite conexiones de clientes que no especifican un nombre de usuario/contraseña. --client-config-dir dir
Especifica un directorio dir para archivos de configuración de cliente personalizados. Después de que un cliente conectado haya sido autenticado, OpenVPN buscará en este directorio un archivo con el mismo nombre que el nombre común X509 del cliente. Si existe un archivo coincidente, se abrirá y se analizará en busca de opciones de configuración específicas del cliente. Si no se encuentra ningún archivo coincidente, OpenVPN intentará abrir y analizar un archivo predeterminado llamado "DEFAULT", que puede proporcionarse pero no es obligatorio. --client-to-client
Dado que el modo servidor de OpenVPN maneja múltiples clientes a través de un único tu

o la interfaz de red, es efectivamente un router. La bandera --client-to-client indica a OpenVPN que enrute internamente el tráfico de cliente a cliente en lugar de enviar todo el tráfico originado por el cliente a la interfaz TUN/TAP.

Cuando se utiliza esta opción, cada cliente "verá" a los demás clientes que estén conectados actualmente. De lo contrario, cada cliente solo verá al servidor. No utilice esta opción si desea aplicar reglas de firewall al tráfico del túnel utilizando reglas personalizadas por cliente.

Tenga en cuenta que al utilizar la descarga del canal de datos, esta opción no tiene ningún efecto. Los paquetes siempre se envían a la interfaz del túnel y luego se enrutan según la tabla de enrutamiento del sistema.

Impide que un cliente específico (basado en el nombre común) se conecte. No utilice esta opción para deshabilitar a un cliente debido al compromiso de clave o contraseña. Utilice una CRL (lista de revocación de certificados) en su lugar (consulte la opción --crl-verify).

Esta opción debe asociarse con una instancia de cliente específica, lo que significa que debe especificarse en un archivo de configuración de instancia de cliente usando --client-config-dir o generarse dinámicamente usando un script --client-connect.

--connect-freq argumentos
Permite un máximo de n nuevas conexiones por sec segundos desde los clientes.

Sintaxis válida:

connect-freq n sec

Esto está diseñado para contener ataques DoS que inundan el servidor con solicitudes de conexión utilizando certificados que finalmente fallarán la autenticación.

Este límite se aplica después de --connect-freq-initial y solo se aplica a los clientes que han completado el handshake de tres vías o a los clientes que utilizan --tls-crypt-v2 sin soporte de cookies (argumento allow-noncookie para --tls-crypt-v2).

Sin embargo, esta es una solución imperfecta, porque en un escenario real de DoS, las conexiones legítimas también podrían ser rechazadas.

Para obtener la mejor protección contra ataques DoS en modo servidor, utilice --proto udp y --tls-auth o --tls-crypt.

--connect-freq-initial argumentos
(Solo UDP) Permite un máximo de n respuestas de paquetes de conexión iniciales por sec segundos desde el servidor OpenVPN a los clientes.

Sintaxis válida:

connect-freq-initial n sec

OpenVPN a partir de la versión 2.6 es muy eficiente al responder a los paquetes de conexión iniciales. Cuando no se limita las respuestas iniciales, un demonio de OpenVPN puede ser abusado en ataques de reflexión. Esta opción está diseñada para limitar la velocidad a la que OpenVPN responderá a los ataques iniciales.

Los intentos de conexión que completan el handshake inicial de tres vías no se contarán en el límite. El valor predeterminado es permitir 100 conexiones iniciales cada 10 segundos.

Permite que varios clientes con el mismo nombre común se conecten concurrentemente. En ausencia de esta opción, OpenVPN desconectará una instancia de cliente al conectarse un nuevo cliente con el mismo nombre común.

--iroute argumentos
Genera una ruta interna hacia un cliente específico. La máscara de red netmask, si se omite, por defecto es 255.255.255.255.

Sintaxis válida:

Esta directiva se puede utilizar para enrutar una subred fija desde el servidor a un cliente particular, independientemente de desde dónde se conecte el cliente. Recuerde que también debe agregar la ruta a la tabla de enrutamiento del sistema (por ejemplo, usando la directiva --route). La razón por la que se necesitan dos rutas es que la directiva --route enruta el paquete desde el kernel a OpenVPN. Una vez en OpenVPN, la directiva --iroute enruta al cliente específico.

Sin embargo, al usar DCO, la directiva --iroute suele ser suficiente para que DCO configure completamente la tabla de enrutamiento. La directiva adicional --route solo se requiere si el comportamiento esperado es enrutar el tráfico de una red específica a la interfaz VPN incluso cuando el cliente responsable no está conectado (el tráfico se descartará entonces).

Si desea que otros clientes puedan acceder a la subred de A, puede usar --push "route ..." junto con --client-to-client para lograrlo. Para que todos los clientes vean la subred de A, OpenVPN debe enviar esta ruta a todos los cli

EXCEpciones para A, ya que la subred ya es propiedad de A. OpenVPN lo logra al no enviar una ruta a un cliente si coincide con una de las irutas del cliente.

--push opción
Envía una opción del archivo de configuración al cliente para su ejecución remota. Tenga en cuenta que opción debe estar entre comillas dobles (""). El cliente debe especificar --pull en su archivo de configuración. El conjunto de opciones que se pueden enviar está limitado tanto por la viabilidad como por la seguridad. Algunas opciones, como las que ejecutarían scripts, están prohibidas, ya que efectivamente permitirían que un servidor comprometido ejecutara código arbitrario en el cliente. Otras opciones, como los parámetros TLS o MTU, no se pueden enviar porque el cliente necesita conocerlos antes de que se pueda iniciar la conexión con el servidor.

Esta es una lista parcial de opciones que actualmente se pueden enviar: --route, --route-gateway, --route-delay, --redirect-gateway, --ip-win32, --dhcp-option, --dns, --inactive, --ping, --ping-exit, --ping-restart, --setenv, --auth-token, --persist-key, --persist-tun, --echo, --comp-lzo, --socket-flags, --sndbuf, --rcvbuf, --session-timeout

--push-remove opt
Elimina selectivamente todas las opciones --push que coincidan con "opt" de la lista de opciones para un cliente. opt se compara como una subcadena contra toda la cadena de opción que se enviará al cliente, por lo que --push-remove route eliminaría todas las declaraciones --push route ... y --push route-ipv6 ..., mientras que --push-remove "route-ipv6 2001:" solo eliminaría las rutas IPv6 para las redes 2001:....

--push-remove solo se puede usar en un contexto específico del cliente, como en un archivo de --client-config-dir, o un script o plugin de --client-connect, similar a --push-reset, solo que más selectivo.

NOTA: para *cambiar* una opción, se puede usar --push-remove para eliminar primero el valor antiguo y luego agregar una nueva opción --push con el nuevo valor.

NOTA 2: debido a detalles de implementación, 'ifconfig' y 'ifconfig-ipv6' solo se pueden eliminar con una coincidencia exacta de la opción (push-remove ifconfig), no es posible la coincidencia de subcadenas ni la coincidencia con el argumento de la dirección IPv4/IPv6.

--push-reset
No heredar la lista de push global para una instancia de cliente específica. Especifique esta opción en un contexto específico del cliente, como con un archivo de configuración de --client-config-dir. Esta opción ignorará las opciones --push en el nivel del archivo de configuración global.

NOTA: --push-reset es muy exhaustivo: eliminará casi todas las opciones de la lista de opciones a enviar. En muchos casos, algunas de estas opciones deberán reconfigurarse posteriormente; en particular, se perderán --topology subnet y --route-gateway, lo que romperá las configuraciones de los clientes en muchos casos. Por lo tanto, para la mayoría de los propósitos, --push-remove es más adecuado para eliminar selectivamente las opciones de push para clientes individuales.

--server argumentos
Una directiva auxiliar diseñada para simplificar la configuración del modo servidor de OpenVPN. Esta directiva configurará un servidor OpenVPN que asignará direcciones a los clientes de la red/máscara de red dada. El servidor en sí tomará la dirección .1 de la red dada para usarla como punto final del lado del servidor de la interfaz TUN/TAP local. Sintaxis válida:

Por ejemplo, --server 10.8.0.0 255.255.255.0 se expande como sigue:

modo servidor
tls-servidor
push "topology [topology]"
si dev tun Y (topology == net30 O topology == p2p):
  ifconfig 10.8.0.1 10.8.0.2
  si !nopool:
    ifconfig-pool 10.8.0.4 10.8.0.251
  ruta 10.8.0.0 255.255.255.0
  si cliente-a-cliente:
    push "ruta 10.8.0.0 255.255.255.0"
  si no topology == net30:
    push "ruta 10.8.0.1"
si dev tap O (dev tun Y topology == subnet):
  ifconfig 10.8.0.1 255.255.255.0
  si !nopool:
    ifconfig-pool 10.8.0.2 10.8.0.253 255.255.255.0
  push "ruta-gateway 10.8.0.1"
  si ruta-gateway sin definir:
    ruta-gateway 10.8.0.2

No utilice --server si está realizando puente Ethernet. Utilice --server-bridge en su lugar.

Una directiva auxiliar similar a --server que está diseñada para simplificar la configuración del modo servidor de OpenVPN en configuraciones de puente Ethernet.

--verify-client-cert mode
Especifica si se requiere que el cliente proporcione un certificado válido.

Las opciones de mode posibles son:

none
No se requiere un certificado de cliente. El cliente necesita autenticarse solo con nombre de usuario/contraseña. Tenga en cuenta que el uso de esta directiva es menos seguro que requerir certificados de todos los clientes.

--verify-client-cert none es funcionalmente equivalente a --client-cert-not-required.

optional
Un cliente puede presentar un certificado, pero no está obligado a hacerlo. Al utilizar esta directiva, también debe usar un script --auth-user-pass-verify para garantizar que los clientes se autentiquen mediante un certificado, un nombre de usuario y una contraseña, o posiblemente ambos.

De nuevo, toda la responsabilidad de la autenticación recaerá en su script --auth-user-pass-verify, por lo que tenga en cuenta que los errores en su script podrían comprometer la seguridad de su VPN.

require
Esta es la opción por defecto. Se requiere que un cliente presente un certificado, de lo contrario se deniega el acceso a la VPN.

Si no utiliza esta directiva (o usa --verify-client-cert require) pero también especifica un script --auth-user-pass-verify, OpenVPN realizará una doble autenticación. La verificación del certificado del cliente Y el script --auth-user-pass-verify deberán tener éxito para que un cliente sea autenticado y aceptado en la VPN.

--vlan-tagging
Opción exclusiva del servidor. Convierte la instancia del servidor OpenVPN en un switch que entiende el etiquetado VLAN, basado en IEEE 802.1Q.

El dispositivo TAP del servidor y cada uno de los clientes conectados se ven como puertos del switch. Todos los puertos de cliente están en modo sin etiquetar y el dispositivo TAP del servidor está etiquetado con VLAN, sin etiquetar o acepta ambos, dependiendo de la configuración de --vlan-accept.

Los fotogramas Ethernet con una etiqueta 802.1Q insertada se denominan "etiquetados". Si el campo Identificador de VLAN (VID) en dicha etiqueta no es cero, el fotograma se denomina "etiquetado con VLAN". Si el VID es cero, pero el Punto de Control de Prioridad (PCP) no es cero, el fotograma se denomina "etiquetado con prioridad". Si no hay una etiqueta 802.1Q, el fotograma no está "etiquetado".

Usando la opción --vlan-pvid v una vez por cliente (ver --client-config-dir), cada puerto puede asociarse con un VID específico. Los paquetes solo pueden ser reenviados entre puertos con el mismo VID. Por lo tanto, los clientes con VIDs diferentes están completamente separados entre sí, incluso si --client-to-client está activado.

El filtrado de paquetes tiene lugar en el servidor OpenVPN. Los clientes no deben tener configurado ningún etiquetado VLAN.

La opción --vlan-tagging está desactivada por defecto. Mientras está desactivada, OpenVPN acepta cualquier fotograma Ethernet y no realiza ningún procesamiento especial para paquetes etiquetados con VLAN.

Esta opción solo se puede activar en el modo --dev tap.

--vlan-accept args
Configura la política de etiquetado VLAN para el dispositivo TAP del servidor.

Sintaxis válida:

vlan-accept  all|tagged|untagged

Los siguientes modos están disponibles:

tagged
Admitir solo fotogramas etiquetados con VLAN. Solo se aceptan paquetes etiquetados con VLAN, mientras que los paquetes sin etiquetar o etiquetados con prioridad se descartan al entrar en el dispositivo TAP del servidor.
untagged
Admitir solo fotogramas sin etiquetar y con etiqueta de prioridad. Los paquetes etiquetados con VLAN no se aceptan, mientras que los paquetes sin etiquetar o con etiqueta de prioridad que entran en el dispositivo TAP del servidor se etiquetan con el valor configurado para la configuración global --vlan-pvid.
all (por defecto)
Admitir todos los fotogramas. Todos los paquetes son admitidos y luego tratados como en modo sin etiquetar o etiquetado respectivamente.
Nota:
Algunos proveedores se refieren a los puertos de switch que se ejecutan en modo tagged como "puertos troncales" (trunk ports) y a los puertos de switch que se ejecutan en modo untagged como "puertos de acceso" (access ports).

Los paquetes reenviados de los clientes al servidor se etiquetan con VLAN con el PVID del cliente de origen, a menos que el VID coincida con el --vlan-pvid global, en cuyo caso se elimina la etiqueta.

Si no se configura ningún PVID para un cliente determinado (ver --vlan-pvid), los paquetes se etiquetan con 1 por defecto.

--vlan-pvid v
Especifica con qué identificador de VLAN está asociado un "puerto". Solo es válido cuando se especifica --vlan-tagging.

En el contexto del cliente, la configuración especifica con qué ID de VLAN está asociado un cliente. En el contexto global, se establece el ID de VLAN del dispositivo TAP del servidor. Esto último solo tiene sentido para los modos --vlan-accept untagged y --vlan-accept all.

Los valores válidos para v van de 1 a 4094. El valor global por defecto es 1. Si no se especifica --vlan-pvid en el contexto del cliente, se hereda el valor global.

En algunas implementaciones de switch, el PVID también se denomina "VLAN Nativa" (Native VLAN).

Renegociación del canal de datos

Al ejecutar OpenVPN en modo cliente/servidor, el canal de datos utilizará una clave de cifrado efímera separada que se rotará a intervalos regulares.

--reneg-bytes n
Renegociar la clave del canal de datos después de enviar o recibir n bytes (deshabilitado por defecto con una excepción, ver abajo). OpenVPN permite que la vida útil de una clave se exprese como un número de bytes cifrados/descifrados, un número de paquetes o un número de segundos. Se forzará una renegociación de clave si cualquiera de estos tres criterios es cumplido por alguno de los pares.

Si se utilizan cifrados con tamaños de bloque de cifrado inferiores a 128 bits, --reneg-bytes se establece en 64 MB por defecto, a menos que se deshabilite explícitamente estableciendo el valor en 0, pero esto está ALTAMENTE DESACONSEJADO ya que está diseñado para añadir cierta protección contra el vector de ataque SWEET32. Para más información, consulte la opción --cipher.

--reneg-pkts n
Renegociar la clave del canal de datos después de enviar y recibir n paquetes (deshabilitado por defecto).
--reneg-sec args
Renegociar la clave del canal de datos después de un máximo de max segundos (por defecto 3600) y un mínimo de min segundos (por defecto es el 90% de max para servidores y igual a max para clientes).
reneg-sec max [min]

El valor efectivo de --reneg-sec utilizado es pseudo-aleatorio por sesión entre min y max.

Con el valor por defecto de 3600, esto da como resultado un valor efectivo por sesión en el rango de 3240 .. 3600 segundos para servidores, o solo 3600 para clientes.

Al utilizar autenticación de doble factor, tenga en cuenta que este valor por defecto puede hacer que el usuario final reciba una solicitud de reautorización una vez por hora.

Además, tenga en cuenta que esta opción se puede utilizar tanto en el cliente como en el servidor, y el que utilice el valor más bajo será el que desencadene la renegociación. Un error común es establecer --reneg-sec a un valor más alto en el cliente o en el servidor, mientras que el otro lado de la conexión todavía usa el valor por defecto de 3600 segundos, lo que significa que la renegociación todavía ocurrirá una vez cada 3600 segundos. La solución es aumentar --reneg-sec tanto en el cliente como en el servidor, o establecerlo en 0 en un lado de la conexión (para deshabilitarlo) y en el valor elegido en el otro lado.

Opciones del modo TLS

El modo TLS es el modo de cifrado más potente de OpenVPN, tanto en seguridad como en flexibilidad. El modo TLS funciona estableciendo canales de control y datos que se multiplexan a través de un único puerto TCP/UDP. OpenVPN inicia una sesión TLS a través del canal de control y la utiliza para intercambiar claves de cifrado y HMAC para proteger el canal de datos. El modo TLS utiliza una capa de fiabilidad robusta sobre la conexión UDP para todas las comunicaciones del canal de control, mientras que el canal de datos, a través del cual pasan los datos cifrados del túnel, se reenvía sin mediación. El resultado es lo mejor de ambos mundos: un canal de datos rápido que se reenvía sobre UDP con solo la sobrecarga de las funciones de cifrar, descifrar y HMAC, y un canal de control que proporciona todas las funciones de seguridad de TLS, incluida la autenticación basada en certificados y la seguridad de reenvío Diffie-Hellman.

Para utilizar el modo TLS, cada par que ejecuta OpenVPN debe tener su propio par de certificado/clave local (--cert y --key), firmado por el certificado raíz que se especifica en --ca.

Cuando dos pares de OpenVPN se conectan, cada uno presenta su certificado local al otro. Cada par comprobará entonces que su par asociado presentó un certificado que fue firmado por el certificado raíz maestro, según lo especificado en --ca.

Si esa comprobación en ambos pares tiene éxito, la negociación TLS tendrá éxito, ambos pares de OpenVPN intercambiarán claves de sesión temporales y el túnel comenzará a pasar datos.

El proyecto OpenVPN proporciona un conjunto de scripts para gestionar certificados y claves RSA: https://github.com/OpenVPN/easy-rsa

--tls-auth args
Añade una capa adicional de autenticación HMAC sobre el canal de control TLS para mitigar ataques DoS y ataques en la pila TLS.

Sintaxis válidas:

tls-auth archivo 0

En resumen, --tls-auth habilita una especie de "firewall HMAC" en el puerto TCP/UDP de OpenVPN, donde los paquetes del canal de control TLS que llevan una firma HMAC incorrecta pueden ser descartados inmediatamente sin respuesta.

archivo (requerido) es un archivo en formato de clave estática de OpenVPN que puede ser generado por --genkey.

Versiones anteriores (hasta OpenVPN 2.3) soportaban un archivo de contraseña de formato libre. Esto ya no es compatible en versiones más nuevas (v2.4+).

Consulte la opción --secret para obtener más información sobre el parámetro opcional direction.

Se recomienda --tls-auth cuando se ejecuta OpenVPN en un modo en el que está escuchando paquetes de cualquier dirección IP, como cuando no se especifica --remote, o se especifica --remote con --float.

El razonamiento para esta característica es el siguiente. TLS requiere un intercambio de varios paquetes antes de poder autenticar a un par. Durante este tiempo, antes de la autenticación, OpenVPN está asignando recursos (memoria y CPU) a este par potencial. El par potencial también está exponiendo muchas partes de OpenVPN y la biblioteca OpenSSL a los paquetes que envía. La mayoría de los ataques de red exitosos de hoy en día buscan explotar errores en los programas (como ataques de desbordamiento de búfer) o forzar a un programa a consumir tantos recursos que se vuelva inutilizable. Por supuesto, la primera línea de defensa es siempre producir código limpio y bien auditado. OpenVPN ha sido escrito priorizando la prevención de ataques de desbordamiento de búfer. Pero como la historia ha demostrado, muchas de las aplicaciones de red más utilizadas han caído, de vez en cuando, en ataques de desbordamiento de búfer.

Así que, como segunda línea de defensa, OpenVPN ofrece esta capa especial de autenticación sobre el canal de control TLS para que cada paquete del canal de control sea autenticado por una firma HMAC y un ID único para protección contra repetición. Esta firma también ayudará a proteger contra ataques DoS (Denegación de Servicio). Una regla general importante para reducir la vulnerabilidad a los ataques DoS es minimizar la cantidad de recursos que un cliente potencial, pero aún no autenticado, puede consumir.

--tls-auth hace esto firmando cada paquete del canal de control TLS con una firma HMAC, incluyendo los paquetes que se envían antes de que el nivel TLS haya tenido la oportunidad de autenticar al par. El resultado es que los paquetes sin la firma correcta pueden ser descartados inmediatamente al recibirlos, antes de que consuman recursos adicionales del sistema, como iniciar un handshake TLS. --tls-auth puede fortalecerse añadiendo la opción --replay-persist, que mantendrá el estado de protección contra repetición de OpenVPN en un archivo para que no se pierda entre reinicios.

Cabe enfatizar que esta característica es opcional y que el archivo de clave utilizado con --tls-auth no otorga a un par más que el poder de iniciar un handshake TLS. No se utiliza para cifrar ni autenticar ningún dato del túnel.

Utiliza --tls-crypt en su lugar si deseas usar el archivo de clave no solo para autenticar, sino también para cifrar el canal de control TLS.

Consideraciones de seguridad

Todos los pares utilizan la misma clave de grupo precompartida --tls-crypt para autenticar y cifrar mensajes del canal de control. Para garantizar que las colisiones de IV sigan siendo poco probables, esta clave no debe utilizarse para cifrar más de 2^48 mensajes del canal de control de cliente a servidor o de servidor a cliente. Una negociación inicial típica consta de unos 10 paquetes en cada dirección. Suponiendo que tanto la negociación inicial como las renegociaciones no superen los 2^16 (65536) paquetes (por precaución), y que las (re)negociaciones ocurran cada minuto para cada usuario (24/7), esto limita la vida útil de la clave tls-crypt a 8171 años dividido por el número de usuarios. Por lo tanto, una configuración con 1000 usuarios debería rotar la clave al menos una vez cada ocho años. (Y una configuración con 8000 usuarios cada año).

Si ocurrieran colisiones de IV, esto podría degradar la seguridad de --tls-crypt a la misma seguridad que usar --tls-auth. Es decir, el canal de control aún se beneficia de la protección adicional contra ataques activos de tipo man-in-the-middle y ataques de denegación de servicio, pero puede que ya no ofrezca privacidad adicional y seguridad post-cuántica además de lo que ofrece TLS.

Para configuraciones grandes o configuraciones donde los clientes no son de confianza, considere usar --tls-crypt-v2 en su lugar. Este utiliza claves únicas por cliente, y por lo tanto mejora los límites a 'rotar una clave de cliente al menos una vez cada 8000 años'.

Esta clave debe ser la misma que la clave utilizada para generar la clave específica del cliente (consulte --genkey tls-crypt-v2-client).

En los servidores, esta opción se puede usar junto con la opción --tls-auth o --tls-crypt. En ese caso, el servidor detectará si el cliente está utilizando claves específicas del cliente y seleccionará automáticamente el modo correcto.

Los parámetros opcionales forzar-cookie solo permite clientes tls-crypt-v2 que admiten un handshake de tres vías sin estado basado en cookies que evita ataques de repetición y agotamiento de estado en el lado del servidor (OpenVPN 2.6 y posteriores). La opción permitir-no-cookie permite explícitamente clientes tls-crypt-v2 más antiguos. El valor predeterminado es (actualmente) permitir-no-cookie.

Negociación de cifrado del canal de datos

OpenVPN 2.4 y versiones posteriores tienen la capacidad de negociar el cifrado de datos que se utiliza para cifrar paquetes de datos. Esta sección describe el mecanismo con más detalle y los diferentes mecanismos de compatibilidad con versiones anteriores de servidores y clientes.

Comportamiento de OpenVPN 2.5 y posteriores

Cuando tanto el cliente como el servidor ejecutan al menos OpenVPN 2.5, se utiliza el orden de los cifrados de --data-ciphers del servidor para elegir el cifrado de datos. Esto significa que se elige el primer cifrado de esa lista que también se encuentra en la lista --data-ciphers del cliente. Si no se encuentra ningún cifrado común, el cliente es rechazado con un mensaje AUTH_FAILED (como se ve en el log del cliente):

AUTH: Received control message: AUTH_FAILED,Data channel cipher negotiation failed (no shared cipher)

OpenVPN 2.5 y versiones posteriores solo permitirán los cifrados especificados en --data-ciphers. Si --data-ciphers no está establecido, el valor predeterminado es AES-256-GCM:AES-128-GCM. En 2.6 y versiones posteriores, el valor predeterminado se cambia a AES-256-GCM:AES-128-GCM:CHACHA20-POLY1305 cuando Chacha20-Poly1305 está disponible.

Para compatibilidad con versiones anteriores, OpenVPN 2.6 y posteriores con --compat-mode 2.4.x (o inferior) y OpenVPN 2.5 agregarán automáticamente un cifrado especificado usando la opción --cipher a esta lista.

Clientes de OpenVPN 2.4

El soporte de negociación en OpenVPN 2.4 fue la primera iteración de la implementación y todavía tenía algunas peculiaridades. Su objetivo principal era "actualizar a AES-256-GCM cuando sea posible". Un cliente de OpenVPN 2.4 compilado contra una biblioteca criptográfica que soporta AES en modo GCM y que no tiene --ncp-disable siempre anunciará el soporte para AES-256-GCM y AES-128-GCM a un servidor enviando IV_NCP=2.

Esto solo causa un problema si la opción --ncp-ciphers ha sido cambiada del valor predeterminado de AES-256-GCM:AES-128-GCM a un valor que no incluye estos dos cifrados. Cuando un servidor OpenVPN intenta usar AES-256-GCM o AES-128-GCM, la conexión fallará. Por lo tanto, se recomienda incluir siempre los cifrados AES-256-GCM y AES-128-GCM en las opciones --ncp-ciphers para evitar este comportamiento.

Clientes de OpenVPN 3

Los clientes basados en la biblioteca OpenVPN 3.x (https://github.com/openvpn/openvpn3/) no tienen una opción configurable --ncp-ciphers o --data-ciphers. Las versiones más recientes deshabilitan por defecto los cifrados heredados AES-CBC, BF-CBC y DES-CBC. Estos clientes siempre anunciarán el soporte para todos sus cifrados AEAD soportados (AES-256-GCM, AES-128-GCM y en versiones más recientes también Chacha20-Poly1305).

Para soportar clientes basados en OpenVPN 3.x, se debe incluir al menos uno de estos cifrados en la opción --data-ciphers del servidor.

Clientes de OpenVPN 2.3 y anteriores (y clientes con --ncp-disable)

Cuando un cliente sin soporte de negociación de cifrado se conecta a un servidor, el cifrado especificado con la opción --cipher en la configuración del cliente debe incluirse en la opción --data-ciphers del servidor para permitir que el cliente se conecte. De lo contrario, al cliente se le enviará el mensaje AUTH_FAILED que indica que no hay un cifrado compartido.

Si el cliente es 2.3 o anterior y ha sido configurado con el argumento --enable-small de ./configure, es necesario usar data-ciphers-fallback cipher en el archivo de configuración del servidor con el cifrado explícito utilizado por el cliente.

Servidor OpenVPN 2.4

Cuando un cliente indica soporte para AES-128-GCM y AES-256-GCM (con IV_NCP=2), un servidor OpenVPN 2.4 enviará el primer cifrado de --ncp-ciphers al cliente OpenVPN independientemente de cuál sea el cifrado. Para emular el comportamiento de un cliente OpenVPN 2.4 lo más fielmente posible y tener compatibilidad con una configuración que dependa de esta peculiaridad, es necesario agregar AES-128-GCM y AES-256-GCM a la opción --data-ciphers del cliente. OpenVPN 2.5+ solo anunciará el flag IV_NCP=2 si esos cifrados están presentes.

Servidores OpenVPN 2.3 y anteriores (y servidores con --ncp-disable)

El cifrado utilizado por el servidor debe incluirse en --data-ciphers para permitir que el cliente se conecte a un servidor sin soporte de negociación de cifrado. (Para compatibilidad, OpenVPN 2.5 también aceptará el cifrado establecido con --cipher).

Si el servidor es 2.3 o anterior y ha sido configurado con el argumento --enable-small de ./configure, es necesario agregar --data-ciphers-fallback cipher a la configuración del cliente con el cifrado explícito utilizado por el servidor.

Deprecación de Blowfish en modo CBC (BF-CBC)

La opción --cipher tenía por defecto BF-CBC en OpenVPN 2.4 y versiones anteriores. El valor predeterminado nunca se cambió para garantizar la compatibilidad con versiones anteriores. En OpenVPN 2.5, este comportamiento ha sido modificado para que si no se establece explícitamente --cipher, ya no permita el cifrado débil BF-CBC y necesite ser añadido explícitamente como --cipher BF-CBC o añadido a --data-ciphers.

Recomendamos encarecidamente cambiar de BF-CBC a un cifrado más seguro lo antes posible.

CONFIGURACIÓN DE RED

OpenVPN consta de dos lados de configuración de red. Un lado es el *enlace* entre el lado local y el remoto, el otro lado es el *adaptador de red virtual* (dispositivo tun/tap).

Opciones de Enlace

Esta sección de opciones de enlace cubre las opciones relacionadas con la conexión entre el host local y el remoto.

--bind keywords
Enlazar a la dirección y puerto local. Este es el valor predeterminado a menos que se utilicen --proto tcp-client, --http-proxy o --socks-proxy.

Si la palabra clave opcional ipv6only está presente, OpenVPN se enlazará solo a IPv6 (en lugar de IPv6 e IPv4) cuando se abra un socket IPv6.

--float
Permitir que el par remoto cambie su dirección IP y/o número de puerto, como debido a DHCP (este es el valor predeterminado si no se usa --remote). --float cuando se especifica con --remote permite que una sesión de OpenVPN se conecte inicialmente a un par en una dirección conocida, sin embargo, si llegan paquetes de una nueva dirección y pasan todas las pruebas de autenticación, la nueva dirección tomará el control de la sesión. Esto es útil cuando se conecta a un par que tiene una dirección dinámica, como un usuario de acceso telefónico o un cliente DHCP.

Esencialmente, --float le dice a OpenVPN que acepte paquetes autenticados de cualquier dirección, no solo de la dirección que se especificó en la opción --remote.

--fragment args
Valid syntax:
fragment max
fragment max mtu

Habilita la fragmentación interna de datagramas para que no se envíen datagramas UDP mayores que max bytes.

Si está presente el parámetro mtu, el parámetro max se interpreta para incluir la sobrecarga de encapsulación IP y UDP. El parámetro mtu se introdujo en la versión 2.6.0 de OpenVPN.

Si el parámetro mtu está ausente, el parámetro max se interpreta de la misma manera que el parámetro --link-mtu, es decir, el tamaño del paquete UDP después de agregar la sobrecarga de encapsulación, pero sin incluir la cabecera UDP en sí.

La opción --fragment solo tiene sentido cuando se utiliza el protocolo UDP (--proto udp).

--fragment agrega 4 bytes de sobrecarga por datagrama.

Véase la opción --mssfix más abajo para una opción importante relacionada con --fragment.

También se debe tener en cuenta que esta opción no pretende reemplazar la fragmentación UDP a nivel de pila IP. Sólo se pretende como último recurso cuando el descubrimiento de la MTU de la ruta está roto. El uso de esta opción es menos eficiente que la corrección del descubrimiento de la MTU de la ruta para su enlace IP y el uso de la fragmentación IP nativa en su lugar.

Dicho esto, hay circunstancias en las que el uso de la capacidad de fragmentación interna de OpenVPN puede ser su única opción, como la tunelización de un flujo de multidifusión UDP que requiere fragmentación.

--keepalive args
Una directiva auxiliar diseñada para simplificar la expresión de --ping y --ping-restart.

Envía un ping cada intervalo segundos, reinicia si no se recibe el ping durante tiempo_espera segundos.

Esta opción se puede usar tanto en el lado del cliente como en el del servidor, pero es suficiente añadirla en el lado del servidor, ya que enviará las opciones --ping y --ping-restart adecuadas al cliente. si modo servidor:
    ping 10                    # Argumento: intervalo
    ping-restart 120           # Argumento: tiempo_espera*2
    push "ping 10"             # Argumento: intervalo
    push "ping-restart 60"     # Argumento: tiempo_espera
else
    ping 10                    # Argumento: intervalo
    ping-restart 60            # Argumento: tiempo_espera

mssfix max [fijo]
mssfix

Anuncia a las sesiones TCP que se ejecutan a través del túnel que deben limitar sus tamaños de paquete de envío de tal manera que después de que OpenVPN las haya encapsulado, el tamaño resultante del paquete UDP que OpenVPN envía a su par no excederá max bytes. El valor predeterminado es 1492 mtu. Utilice 0 como max para deshabilitar mssfix.

Si se especifica el parámetro mtu, el valor max se interpreta como el tamaño resultante del paquete de los paquetes VPN, incluido el encabezado IP y UDP. El soporte para el parámetro mtu se añadió con la versión 2.6.0 de OpenVPN.

Si no se especifica el parámetro mtu, el parámetro max se interpreta de la misma manera que el parámetro --link-mtu, es decir, el tamaño del paquete UDP después de que se haya añadido la sobrecarga de encapsulación, pero sin incluir el propio encabezado UDP. El paquete resultante sería como máximo 28 bytes mayor para IPv4 y 48 bytes para IPv6 (20/40 bytes para el encabezado IP y 8 bytes para el encabezado UDP). El valor predeterminado de 1450 permite que los paquetes OpenVPN se transmitan sobre IPv4 en un enlace con MTU 1478 o superior sin fragmentación a nivel IP (y 1498 para IPv6).

Si se especifica el parámetro fijo, OpenVPN no intentará calcular la sobrecarga de encapsulación VPN, sino que establecerá el MSS para limitar el tamaño de los paquetes IP de carga útil al número especificado. Los paquetes IPv4 tendrán el valor MSS reducido a mssfix - 40 y los paquetes IPv6 a mssfix - 60.

Si --mssfix se especifica sin ningún parámetro, hereda los parámetros de --fragment si se especifican o utiliza el valor predeterminado para --mssfix en caso contrario.

La opción --mssfix sólo tiene sentido cuando se utiliza el protocolo UDP para la comunicación entre pares de OpenVPN, es decir, --proto udp.

--mssfix y --fragment se pueden usar idealmente juntos, donde --mssfix intentará evitar que TCP necesite la fragmentación de paquetes en primer lugar, y si de todos modos llegan paquetes grandes (de protocolos distintos a TCP), --fragment los fragmentará internamente.

--max-packet-size, --fragment y --mssfix están diseñados para solucionar casos en los que el descubrimiento de la MTU de la ruta está roto en la ruta de red entre pares de OpenVPN.

El síntoma habitual de una avería de este tipo es una conexión OpenVPN que se inicia correctamente, pero luego se detiene durante el uso activo.

Si se utilizan --fragment y --mssfix juntos, --mssfix tomará su parámetro max predeterminado de la opción --fragment max.

Por lo tanto, se podría reducir el tamaño máximo del paquete UDP a 1300 (un buen primer intento para resolver problemas de conexión relacionados con la MTU) con las siguientes opciones:

--tun-mtu 1500 --fragment 1300 --mssfix

Si se utiliza la opción --max-packet-size size en la configuración, también actuará como si se especificara mssfix size mtu en la configuración.

--ping-exit n
Hace que OpenVPN salga después de que pasen n segundos sin recibir un ping u otro paquete del remoto. Esta opción se puede combinar con --inactive, --ping y --ping-exit para crear una desconexión de inactividad de dos niveles.

Por ejemplo,

openvpn [opciones...] --inactive 3600 --ping 10 --ping-exit 60

cuando se usa en ambos pares, hará que OpenVPN salga en 60 segundos si su par se desconecta, pero saldrá después de una hora si no se intercambian datos reales del túnel.

--ping-restart n
Similar a --ping-exit, pero activa un reinicio SIGUSR1 después de que pasen n segundos sin recibir un ping u otro paquete del remoto.

Esta opción es útil en casos donde el par remoto tiene una dirección IP dinámica y se utiliza un nombre DNS de TTL bajo para rastrear la dirección IP utilizando un servicio como https://www.nsupdate.info/ + un cliente DNS dinámico como ddclient.

Si el par no se puede alcanzar, se activará un reinicio, lo que hará que el nombre de host utilizado con --remote se resuelva de nuevo (si --resolv-retry también se especifica).

En modo servidor, --ping-restart, --inactive o cualquier otro tipo de señal generada internamente siempre se aplicará a instancias de cliente individuales, nunca al servidor completo. Tenga en cuenta también que en modo servidor, cualquier señal generada internamente que normalmente provocaría un reinicio, provocará la eliminación del objeto de instancia del cliente en su lugar.

En modo cliente, el parámetro --ping-restart se establece en 120 segundos por defecto. Este valor predeterminado se mantendrá hasta que el cliente reciba un valor de reemplazo del

configuración del servidor. Para deshabilitar el valor predeterminado de 120 segundos, establezca --ping-restart 0 en el cliente.

Consulte la sección de señales a continuación para obtener más información sobre SIGUSR1.

Tenga en cuenta que el comportamiento de SIGUSR1 puede modificarse mediante las opciones --persist-tun, --persist-key, --persist-local-ip y --persist-remote-ip.

Tenga en cuenta también que --ping-exit y --ping-restart son mutuamente excluyentes y no se pueden usar juntos.

--proto p
Utilice el protocolo p para comunicarse con el host remoto. p puede ser udp, tcp-client o tcp-server. También puede limitar OpenVPN a usar solo IPv4 o solo IPv6 especificando p como udp4, tcp4-client, tcp4-server o udp6, tcp6-client, tcp6-server, respectivamente.

El protocolo predeterminado es udp cuando no se especifica --proto.

Para la operación UDP, se debe especificar --proto udp en ambos pares.

Para la operación TCP, un par debe usar --proto tcp-server y el otro debe usar --proto tcp-client. Un par iniciado con tcp-server esperará indefinidamente una conexión entrante. Un par iniciado con tcp-client intentará conectarse y, si falla, dormirá durante 5 segundos (ajustable a través de la opción --connect-retry) y lo intentará de nuevo infinitamente o hasta N reintentos (ajustable a través de la opción --connect-retry-max). Tanto el cliente como el servidor TCP simularán una señal de reinicio SIGUSR1 si alguno de los lados restablece la conexión.

OpenVPN está diseñado para funcionar de manera óptima sobre UDP, pero la capacidad TCP se proporciona para situaciones en las que UDP no puede utilizarse. En comparación con UDP, TCP generalmente será algo menos eficiente y menos robusto cuando se usa en redes poco fiables o congestionadas.

Este artículo describe algunos de los problemas con la túnelización de IP sobre TCP: https://web.archive.org/web/20141025181658/http://sites.inka.de/sites/bigred/devel/tcp-tcp.html

Sin embargo, existen ciertos casos en los que el uso de TCP puede ser ventajoso desde una perspectiva de seguridad y robustez, como la túnelización de protocolos UDP no IP o a nivel de aplicación, o la túnelización de protocolos que no poseen una capa de confiabilidad incorporada.

--replay-window args
Modifique el tamaño de la ventana deslizante de protección contra repetición y la ventana de tiempo.

Sintaxis válidas:

replay-window n
replay-window n t

Utilice una ventana deslizante de protección contra repetición de tamaño n y una ventana de tiempo de t segundos.

Por defecto, n es 64 (el valor predeterminado de IPSec) y t es 15 segundos.

Esta opción solo es relevante en modo UDP, es decir, cuando se especifica --proto udp o no se especifica ninguna opción --proto.

Cuando OpenVPN túneliza paquetes IP sobre UDP, existe la posibilidad de que los paquetes se pierdan o se entreguen desordenados. Dado que OpenVPN, al igual que IPSec, emula la capa de red física, aceptará una secuencia de paquetes desordenados y entregará dichos paquetes en el mismo orden en que se recibieron a la pila de protocolos TCP/IP, siempre que cumplan varias restricciones.

a.
El paquete no puede ser una repetición (a menos que se especifique --no-replay, que deshabilita la protección contra repetición por completo).
b.
Si un paquete llega desordenado, solo se aceptará si la diferencia entre su número de secuencia y el número de secuencia más alto recibido hasta ahora es inferior a n.
c.
Si un paquete llega desordenado, solo se aceptará si llega no más tarde de t segundos después de cualquier paquete que contenga un número de secuencia más alto.

Si está utilizando un enlace de red con un gran pipeline (lo que significa que el producto de ancho de banda y latencia es alto), es posible que desee utilizar un valor mayor para n. Los enlaces satelitales en particular a menudo requieren esto.

Si ejecuta OpenVPN en --verb 4, verá el mensaje "PID_ERR replay-window backtrack occurred [x]" cada vez que el retroceso máximo de número de secuencia visto hasta ahora aumente. Esto se puede usar para calibrar n.

Existe cierta controversia sobre el método apropiado para manejar la reordenación de paquetes en la capa de seguridad.

En concreto, ¿hasta qué punto debe la capa de seguridad proteger el protocolo encapsulado de ataques que se enmascaran como los tipos de pérdida y reordenación de paquetes normales que ocurren en las redes IP?

El enfoque de IPSec y OpenVPN es permitir la reordenación de paquetes dentro de una cierta ventana de número de secuencia fija.

OpenVPN se suma al modelo IPSec al limitar el tamaño de la ventana en tiempo y en espacio de secuencia.

OpenVPN también añade el transporte TCP como una opción (no ofrecida por IPSec) en cuyo caso OpenVPN puede adoptar una actitud muy estricta hacia la eliminación y reordenación de mensajes: No lo permitas. Dado que TCP garantiza la confiabilidad, se puede suponer que cualquier evento de pérdida o reordenación de paquetes es un ataque.

En este sentido, se podría argumentar que el transporte de túnel TCP es preferible al túnelizar protocolos de aplicación no IP o UDP que podrían ser vulnerables a un ataque de eliminación o reordenación de mensajes que cae dentro de los parámetros operativos normales de las redes IP.

Por lo tanto, afirmaría que nunca se debe túnelizar un protocolo no IP o un protocolo de aplicación UDP sobre UDP, si el protocolo podría ser vulnerable a un ataque de eliminación o reordenación de mensajes que cae dentro de los parámetros operativos normales de lo que se espera de la capa física IP. El problema se soluciona fácilmente simplemente usando TCP como capa de transporte VPN.

--session-timeout n
Genera SIGTERM para la instancia del cliente después de n segundos desde el inicio de la sesión, forzando a OpenVPN a desconectarse. En modo cliente, OpenVPN se desconectará y saldrá, mientras que en modo servidor se terminarán todas las sesiones de cliente.

Esta opción también se puede especificar en un archivo de configuración de instancia de cliente usando --client-config-dir o generarse dinámicamente mediante un script de --client-connect. En estos casos, solo se termina la sesión de cliente relacionada.

--socket-flags flags
Aplica las banderas dadas al socket de transporte de OpenVPN. Actualmente, solo se admite TCP_NODELAY.

La bandera de socket TCP_NODELAY es útil en modo TCP y hace que el kernel envíe los paquetes del túnel inmediatamente a través de la conexión TCP sin intentar agrupar varios paquetes más pequeños en un paquete más grande. Esto puede resultar en una mejora considerable de la latencia.

Esta opción se puede enviar del servidor al cliente, y debe utilizarse tanto en el cliente como en el servidor para obtener el máximo efecto.

--tcp-nodelay
Esta macro establece la bandera de socket TCP_NODELAY en el servidor, así como la envía a los clientes que se conectan. La bandera TCP_NODELAY deshabilita el algoritmo de Nagle en los sockets TCP, haciendo que los paquetes se transmitan inmediatamente con baja latencia, en lugar de esperar un corto período de tiempo para agregar varios paquetes en un paquete contenedor más grande. En aplicaciones VPN sobre TCP, TCP_NODELAY es generalmente una buena optimización de latencia.

La macro se expande de la siguiente manera:

if modo servidor:
    socket-flags TCP_NODELAY
    push "socket-flags TCP_NODELAY"
--max-packet-size tamaño
Esta opción instruirá a OpenVPN a intentar limitar el tamaño máximo del paquete en la escritura restringiendo el tamaño del paquete del canal de control y estableciendo --mssfix.

OpenVPN intentará mantener sus mensajes del canal de control por debajo de este tamaño, pero debido a algunas restricciones en el protocolo, esto no siempre es posible. Si la opción no está establecida, el tamaño máximo del paquete de control tiene un valor predeterminado de 1250. El tamaño del paquete del canal de control se restringirá a valores entre 154 y 2048. El tamaño máximo del paquete incluye la sobrecarga de encapsulación como UDP e IP.

En términos de --mssfix, se expandirá a:

Si necesita establecer --mssfix para el canal de datos y el tamaño máximo del paquete del canal de control de forma independiente, use --max-packet-size primero, seguido de un --mssfix en la configuración.

En general, el tamaño predeterminado de 1250 funcionará casi universalmente

--block-ipv6
En el cliente, en lugar de enviar paquetes IPv6 a través del túnel VPN, todos los paquetes IPv6 se responden con un mensaje ICMPv6 de no hay ruta al host. --block-ipv6
Configuración del Servidor
Empuja una configuración IPv6 "válida" al cliente y bloquea en el servidor

--dev dispositivo
Dispositivo de red virtual TUN/TAP que puede ser tunX, tapX, null o un nombre de cadena arbitrario (X puede omitirse para un dispositivo dinámico).

Consulta la sección de ejemplos más abajo para ver un ejemplo de configuración de un dispositivo TUN.

Debes usar dispositivos tun en ambos extremos de la conexión o dispositivos tap en ambos extremos. No puedes mezclarlos, ya que representan diferentes capas de red subyacentes:

tun
Los dispositivos encapsulan IPv4 o IPv6 (Capa 3 del modelo OSI)
tap
Los dispositivos encapsulan Ethernet 802.3 (Capa 2 del modelo OSI).

Sintaxis válidas:

dev tun2
dev tap4
dev ovpn

Lo que sucede si el nombre del dispositivo no es tun o tap depende de la plataforma.

En la mayoría de las plataformas, tunN (por ejemplo, tun2, tun30) y tapN (por ejemplo, tap3) crearán una interfaz tun/tap numerada con el número especificado; esto es útil si hay varias instancias de OpenVPN activas y se necesita conocer la asignación instancia-dispositivo. Algunas plataformas no admiten "tap numerado", por lo que intentar --dev tap3 fallará.

Los nombres de dispositivo arbitrarios (por ejemplo, --dev tun-home) solo funcionarán en FreeBSD (con el controlador del kernel DCO para dispositivos tun) y Linux (tanto para dispositivos tun como tap, DCO y controlador tun/tap).

Si tal nombre de dispositivo comienza con tun o tap (por ejemplo, tun-home), OpenVPN elegirá el tipo de dispositivo correcto automáticamente. De lo contrario, el tipo de dispositivo deseado debe especificarse con --dev-type tun o --dev-type tap.

En Windows, solo se admiten los nombres tun y tap. La selección entre múltiples controladores o instancias de controladores instalados se realiza con --dev-node y --windows-driver.

--dev-node nodo
Esta es una opción muy dependiente del sistema para influir en la selección del controlador tun/tap.

En Linux, los dispositivos tun/tap se crean accediendo a /dev/net/tun, y este nombre de dispositivo se puede cambiar usando --dev-node ....

En Mac OS X, esta opción se puede usar para especificar la implementación tun predeterminada. Usar --dev-node utun fuerza el uso del soporte nativo del kernel tun de Darwin. Options

Options are used to configure OpenVPN.

OpenVPN supports a wide variety of options that can be used to configure its operation. Options can be specified on the OpenVPN configuration file (see openvpn(5)) or on the command line.

This man page lists the options supported by OpenVPN. Where options affect OpenVPN's core functionality, OpenVPN's default values are documented here.

Some options are valid on the client-side only, others on the server-side only, and some are valid on both sides.

This man page lists options in alphabetical order.

Remember that this man page is a reference document; for examples and tutorials, consult the OpenVPN website and Wiki.

--allow-pull-filter rule
This option allows for filtering of options pushed by the server. It can be used on the client side to restrict what options the server can push.
--pull-filter rule
This option allows for filtering of options pushed by the server. It can be used on the client side to restrict what options the server can push.

A rule is composed of a filter type and a filter value. The filter type indicates whether the rule applies to options being accepted or rejected. The filter value specifies the option to be filtered.

--route-gateway arg
Specify a default gateway for use with --route.

If dhcp is specified as the parameter, the gateway address will be extracted from a DHCP negotiation with the OpenVPN server-side LAN.

Valid syntaxes:

route-gateway gateway
route-gateway dhcp
--route-ipv6-gateway gw
Specify a default gateway gw for use with --route-ipv6.
--route-metric m
Specify a default metric m for use with --route.
--route-noexec
Don't add or remove routes automatically. Instead pass routes to --route-up script using environmental variables.
--route-nopull
When used with --client or --pull, accept options pushed by server EXCEPT for routes, block-outside-dns and dhcp options like DNS servers.

When used on the client, this option effectively bars the server from adding routes to the client's routing table, however note that this option still allows the server to set the TCP/IP properties of the client's TUN/TAP interface.

--topology mode
Configure virtual addressing topology when running in --dev tun mode. This directive has no meaning in --dev tap mode, which always uses a subnet topology.

If you set this directive on the server, the --server and --server-bridge directives will automatically push your chosen topology setting to clients as well. This directive can also be manually pushed to clients. Like the --dev directive, this directive must always be compatible between client and server.

mode can be one of:

net30
Use a point-to-point topology, by allocating one /30 subnet per client. This is designed to allow point-to-point semantics when some or all of the connecting clients might be Windows systems. This is the default.
p2p
Use a point-to-point topology where the remote endpoint of the client's tun interface always points to the local endpoint of the server's tun interface. This mode allocates a single IP address per connecting client. Only use when none of the connecting clients are Windows systems.
subnet
Use a subnet rather than a point-to-point topology by configuring the tun interface with a local IP address and subnet mask, similar to the topology used in --dev tap and ethernet bridging mode. This mode allocates a single IP address per connecting client and works on Windows as well.

Note: Using --topology subnet changes the interpretation of the arguments of --ifconfig to mean "address netmask", no longer "local remote".

--tun-mtu args
Valid syntaxes:
tun-mtu tun-mtu
tun-mtu tun-mtu occ-mtu

Take the TUN device MTU to be tun-mtu and derive the link MTU from it. In most cases, you will probably want to leave this parameter set to its default value.

The default for tun-mtu is 1500.

The OCC MTU can be used to avoid warnings about mismatched MTU from clients. If occ-mtu is not specified, it will to default to the tun-mtu.

The MTU (Maximum Transmission Units) is the maximum datagram size in bytes that can be sent unfragmented over a particular network path. OpenVPN requires that packets on the control and data channels be sent unfragmented.

MTU problems often manifest themselves as connections which hang during periods of active usage.

It's best to use the --fragment and/or --mssfix options to deal with MTU sizing issues.

Note: Depending on the platform, the operating system allows one to receive packets larger than tun-mtu (e.g. Linux and FreeBSD) but other platforms (like macOS) limit received packets to the same size as the MTU.

--tun-max-mtu maxmtu
This configures the maximum MTU size that a server can push to maxmtu, by configuring the internal buffers to allow at least this packet size. The default for maxmtu is 1600. Currently, only increasing beyond 1600 is possible, and attempting to reduce max-mtu below 1600 will be ignored.
--tun-mtu-extra n
Assume that the TUN/TAP device might return as many as n bytes more than the --tun-mtu size on read. This parameter defaults to 0, which is sufficient for most TUN devices. TAP devices may introduce additional overhead in excess of the MTU size, and a setting of 32 is the default when TAP devices are used. This parameter only controls internal OpenVPN buffer sizing, so there is no transmission overhead associated with using a larger value.

TUN/TAP standalone operations

These two standalone operations will require --dev and optionally --user and/or --group.

--mktun
(Standalone) Create a persistent tunnel on platforms which support them such as Linux. Normally TUN/TAP tunnels exist only for the period of time that an application has them open. This option takes advantage of the TUN/TAP driver's ability to build persistent tunnels that live through multiple instantiations of OpenVPN and die only when they are deleted or the machine is rebooted.

One of the advantages of persistent tunnels is that they eliminate the need for separate --up and --down scripts to run the appropriate ifconfig(8) and route(8) commands. These commands can be placed in the same shell script which starts or terminates an OpenVPN session.

Another advantage is that open connections through the TUN/TAP-based tunnel will not be reset if the OpenVPN peer restarts. This can be useful to provide uninterrupted connectivity through the tunnel in the event of a DHCP reset of the peer's public IP address (see the --ipchange option above).

One disadvantage of persistent tunnels is that it is harder to automatically configure their MTU value (see --link-mtu and --tun-mtu above).

On some platforms such as Windows, TAP-Win32 tunnels are persistent by default.

--rmtun
(Standalone) Remove a persistent tunnel.

--auth-user-pass-verify args
Requiere que el cliente proporcione un nombre de usuario/contraseña (posiblemente además de un certificado de cliente) para la autenticación.

Sintaxis válida:

auth-user-pass-verify cmd método

OpenVPN ejecutará el comando cmd para validar el nombre de usuario/contraseña proporcionado por el cliente.

cmd consta de una ruta a un script (o programa ejecutable), opcionalmente seguido de argumentos. La ruta y los argumentos pueden estar entre comillas simples o dobles y/o escapados usando una barra invertida, y deben estar separados por uno o más espacios.

Si método se establece en via-env, OpenVPN llamará a cmd con las variables de entorno username y password establecidas en las cadenas de nombre de usuario/contraseña proporcionadas por el cliente. *Tenga cuidado* de que este método no es seguro en algunas plataformas que hacen que el entorno de un proceso sea visible públicamente para otros procesos no privilegiados.

Si método se establece en via-file, OpenVPN escribirá el nombre de usuario y la contraseña en las dos primeras líneas de un archivo temporal. El nombre del archivo se pasará como argumento a cmd, y el archivo será eliminado automáticamente por OpenVPN después de que el script retorne. La ubicación del archivo temporal se controla mediante la opción --tmp-dir. Por seguridad, considere configurarlo en un medio de almacenamiento volátil como /dev/shm (si está disponible) para evitar que el archivo de nombre de usuario/contraseña toque el disco duro.

El script debe examinar el nombre de usuario y la contraseña, devolviendo un código de salida de éxito (0) si la solicitud de autenticación del cliente debe ser aceptada, un código de fallo (1) para rechazar al cliente, o un código de que la autenticación se aplaza (2). Si la autenticación se aplaza, el script debe bifurcar/iniciar una operación en segundo plano o alguna otra operación no bloqueante para continuar la autenticación en segundo plano. Al finalizar la autenticación, se debe escribir un 1 o un 0 en el archivo especificado por auth_control_file.

Si el archivo especificado por auth_failed_reason_file existe y tiene contenido no vacío, el contenido de este archivo se usará como mensaje AUTH_FAILED. Para evitar condiciones de carrera, este archivo debe escribirse antes que auth_control_file.

La razón de fallo de autenticación puede ser algo simple como "El usuario ha sido permanentemente deshabilitado", pero también hay algunos mensajes especiales de fallo de autenticación.

El mensaje TEMP indica que la autenticación falló temporalmente y que el cliente debe continuar intentando conectarse. El servidor puede opcionalmente proporcionar un mensaje legible por el usuario y dar una pista al cliente sobre cómo proceder. Las palabras clave del mensaje AUTH_FAILED,TEMP son claves/valores separados por comas y proporcionan una pista al cliente sobre cómo proceder. Las palabras clave definidas actualmente son:

backoff s
instruye al cliente a esperar al menos s segundos antes del próximo intento de conexión. Si el cliente ya utiliza un retraso mayor para el intento de reconexión, el retraso no se acortará.
advance addr
Instruye al cliente a conectarse a la siguiente dirección (IP) del servidor actual.
advance remote
Instruye al cliente a omitir las direcciones IP restantes del servidor actual y, en su lugar, conectarse al siguiente servidor especificado en el archivo de configuración.
advance no
Instruye al cliente a intentar conectarse nuevamente al mismo servidor.

Por ejemplo, el mensaje TEMP[backoff 42,advance no]: No hay direcciones IP libres indica que la conexión VPN no puede tener éxito actualmente e instruye al cliente a intentarlo de nuevo en 42 segundos.

Cuando se utiliza la autenticación diferida, el script también puede solicitar la autenticación pendiente escribiendo en el archivo especificado por auth_pending_file. La primera línea debe ser el tiempo de espera en segundos, el método requerido en la segunda línea (por ejemplo, crtext) y la tercera línea debe ser el EXTRA, como se documenta en la sección client-pending-auth de doc/management.txt.

Esta directiva está diseñada para habilitar una interfaz de estilo de plugin para extender las capacidades de autenticación de OpenVPN.

Para protegerse contra un cliente que pasa una cadena de nombre de usuario o contraseña formada maliciosamente, la cadena de nombre de usuario debe consistir solo en estos caracteres: alfanuméricos, guión bajo ('_'), guión ('-'), punto ('.') o arroba ('@'). La cadena de contraseña puede consistir en cualquier carácter imprimible excepto CR o LF. Cualquier carácter ilegal en la cadena de nombre de usuario o contraseña se convertirá en un guión bajo ('_').

Cualquier script definido por el usuario debe tener cuidado para evitar crear una vulnerabilidad de seguridad en la forma en que se manejan estas cadenas. Nunca use estas cadenas de tal manera que puedan ser escapadas o evaluadas por un intérprete de shell.

Para obtener un script de ejemplo que realiza la autenticación PAM, consulte sample-scripts/auth-pam.pl en la distribución fuente de OpenVPN.

Típicamente, cmd ejecutará

.Sh --up A script to add routes to the tunnel.

Normally the up script is called after the TUN/TAP device is opened. In this context, the last command line parameter passed to the script will be init. If the --up-restart option is also used, the up script will be called for restarts as well. A restart is considered to be a partial reinitialization of OpenVPN where the TUN/TAP instance is preserved (the --persist-tun option will enable such preservation). A restart can be generated by a SIGUSR1 signal, a --ping-restart timeout, or a connection reset when the TCP protocol is enabled with the --proto option. If a restart occurs, and --up-restart has been specified, the up script will be called with restart as the last parameter.

NOTE:
On restart, OpenVPN will not pass the full set of environment variables to the script. Namely, everything related to routing and gateways will not be passed, as nothing needs to be done anyway - all the routing setup is already in place. Additionally, the up-restart script will run with the downgraded UID/GID settings (if configured).

The following standalone example shows how the --up script can be called in both an initialization and restart context. (NOTE: for security reasons, don't run the following example unless UDP port 9999 is blocked by your firewall. Also, the example will run indefinitely, so you should abort with control-c).

openvpn --dev tun --port 9999 --verb 4 --ping-restart 10 \
        --up 'echo up' --down 'echo down' --persist-tun  \
        --up-restart

Note that OpenVPN also provides the --ifconfig option to automatically ifconfig the TUN device, eliminating the need to define an --up script, unless you also want to configure routes in the --up script.

If --ifconfig is also specified, OpenVPN will pass the ifconfig local and remote endpoints on the command line to the --up script so that they can be used to configure routes such as:

route add -net 10.0.0.0 netmask 255.255.255.0 gw $5

String Types and Remapping

In certain cases, OpenVPN will perform remapping of characters in strings. Essentially, any characters outside the set of permitted characters for each string type will be converted to underbar ('_').

Q: Why is string remapping necessary?
It's an important security feature to prevent the malicious coding of strings from untrusted sources to be passed as parameters to scripts, saved in the environment, used as a common name, translated to a filename, etc.
Q: Can string remapping be disabled?
Yes, by using the --no-name-remapping option, however this should be considered an advanced option.

Here is a brief rundown of OpenVPN's current string types and the permitted character class for each string:

X509 Names
Alphanumeric, underbar ('_'), dash ('-'), dot ('.'), at ('@'), colon (':'), slash ('/'), and equal ('='). Alphanumeric is defined as a character which will cause the C library isalnum() function to return true.
Common Names
Alphanumeric, underbar ('_'), dash ('-'), dot ('.'), and at ('@').
--auth-user-pass username
Same as Common Name, with one exception: starting with OpenVPN 2.0.1, the username is passed to the OPENVPN_PLUGIN_AUTH_USER_PASS_VERIFY plugin in its raw form, without string remapping.
--auth-user-pass password
Any "printable" character except CR or LF. Printable is defined to be a character which will cause the C library isprint() function to return true.
--client-config-dir filename as derived from common name or`username
Alphanumeric, underbar ('_'), dash ('-'), and dot ('.') except for "." or ".." as standalone strings. As of v2.0.1-rc6, the at ('@') character has been added as well for compatibility with the common name character class.
Environmental variable names
Alphanumeric or underbar ('_').
Environmental variable values
Any printable character.

For all cases, characters in a string which are not members of the legal character class for that string type will be remapped to underbar ('_').

Management Interface Options

OpenVPN provides a feature rich socket based management interface for both server and client mode operations.

--management args
Enable a management server on a socket-name Unix socket on those platforms supporting it, or on a designated TCP port.

Valid syntaxes:

management socket-name unix          #
management socket-name unix pw-file  # (recommended)
management IP port                   # (INSECURE)
management IP port pw-file           #

pw-file, if specified, is a password file where the password must be on first line. Instead of a filename it can use the keyword stdin which will prompt the user for a password to use when OpenVPN is starting.

For unix sockets, the default behaviour is to create a unix domain socket that may be connected to by any process. Use the --management-client-user and --management-client-group directives to restrict access.

The management interface provides a special mode where the TCP management link can operate over the tunnel itself. To enable this mode, set IP to tunnel. Tunnel mode will cause the management interface to listen for a TCP connection on the local VPN address of the TUN/TAP interface.

*BEWARE* of enabling the management interface over TCP. In these cases you should ALWAYS make use of pw-file to password protect the management interface. Any user who can connect to this TCP IP:port will be able to manage and control (and interfere with) the OpenVPN process. It is also strongly recommended to set IP to 127.0.0.1 (localhost) to restrict accessibility of the management server to local clients.

While the management port is designed for programmatic control of OpenVPN by other applications, it is possible to telnet to the port, using a telnet client in "raw" mode. Once connected, type help for a list of commands.

For detailed documentation on the management interface, see the management-notes.txt file in the management folder of the OpenVPN source distribution.

--management-client
Management interface will connect as a TCP/unix domain client to IP:port specified by --management rather than listen as a TCP server or on a unix domain socket.

If the client connection fails to connect or is disconnected, a SIGTERM signal will be generated causing OpenVPN to quit.

--management-client-auth
Gives management interface client the responsibility to authenticate clients after their client certificate has been verified. See management-notes.txt in OpenVPN distribution for detailed notes.
--management-client-group g
When the management interface is listening on a unix domain socket, only allow connections from group g.
--management-client-user u
When the management interface is listening on a unix domain socket, only allow connections from user u.
--management-external-cert certificate-hint
Allows usage for external certificate instead of --cert option (client-only). certificate-hint is an arbitrary string which is passed to a management interface client as an argument of NEED-CERTIFICATE notification. Requires --management-external-key.
--management-external-key args
Allows usage for external private key file instead of --key option (client-only).

Valid syntaxes:

management-external-key
management-external-key nopadding
management-external-key pkcs1
management-external-key pss

or any combination like:

management-external-key nopadding pkcs1
management-external-key pkcs1 pss

The optional parameters nopadding pkcs1 and pss signal support for different padding algorithms. See doc/mangement-notes.txt for a complete description of this feature.

--management-forget-disconnect
Make OpenVPN forget passwords when management session disconnects.

This directive does not affect the --http-proxy username/password. It is always cached.

--management-hold
Start OpenVPN in a hibernating state, until a client of the management interface explicitly starts it with the hold release command.
--management-log-cache n
Cache the most recent n lines of log file history for usage by the management channel.
--management-query-passwords
Query management channel for private key password and --auth-user-pass username/password. Only query the management channel for inputs which ordinarily would have been queried from the console.

Allow management interface to override --remote directives (client-only).

Plug-in Interface Options

OpenVPN can be extended by loading external plug-in modules at runtime. These plug-ins must be prebuilt and adhere to the OpenVPN Plug-In API.

--plugin args
Loads an OpenVPN plug-in module.

Valid syntax:

plugin module-name
plugin module-name "arguments"

The module

-nombre debe ser el primer argumento, indicando el plugin a cargar. El segundo argumento es una cadena de inicialización opcional que se pasará directamente al plugin. Si la inicialización consta de varios argumentos, debe ir entre comillas dobles ("). Se pueden cargar varios módulos de plugin en un solo proceso OpenVPN.

El argumento nombre-plugin puede ser solo un nombre de archivo o un nombre de archivo con una ruta relativa o absoluta. El formato del nombre de archivo y la ruta definen si el plugin se cargará desde un directorio de plugins predeterminado o fuera de este directorio.

--plugin ruta         Directorio efectivo utilizado
===================== =============================
 myplug.so            DIRECTORIO_PREDETERMINADO/myplug.so
 subdir/myplug.so     DIRECTORIO_PREDETERMINADO/subdir/myplug.so
 ./subdir/myplug.so   CWD/subdir/myplug.so
 /usr/lib/my/plug.so  /usr/lib/my/plug.so

DIRECTORIO_PREDETERMINADO se reemplaza por el directorio de plugins predeterminado, que se configura en el momento de la compilación de OpenVPN. CWD es el directorio actual donde se inició OpenVPN o el directorio al que OpenVPN ha cambiado a través de la opción --cd antes de la opción --plugin.

Para obtener más información y ejemplos sobre cómo compilar módulos de plugins de OpenVPN, consulte el archivo README en la carpeta plugin de la distribución fuente de OpenVPN.

Si está utilizando una instalación RPM de OpenVPN, consulte /usr/share/openvpn/plugin. La documentación se encuentra en doc y los módulos de plugin reales están en lib.

Se pueden encadenar varios módulos de plugin, y los módulos se pueden usar junto con scripts. OpenVPN llamará a los módulos en el orden en que se declaran en el archivo de configuración. Si tanto un plugin como un script están configurados para la misma devolución de llamada, el script se llamará el último. Si el código de retorno del módulo/script controla una función de autenticación (como tls-verify, auth-user-pass-verify o client-connect), cada módulo y script debe devolver éxito (0) para que la conexión se autentique.

ADVERTENCIA:
Los plugins pueden realizar ejecución diferida, lo que significa que el plugin devolverá el control al proceso principal de OpenVPN y proporcionará el resultado del plugin más tarde a través de un hilo o proceso diferente. OpenVPN **NO** admite múltiples plugins de autenticación **donde más de un plugin** intenta realizar una autenticación diferida. Si se detecta este comportamiento, OpenVPN se cerrará tras la primera autenticación.

Establece automáticamente la dirección IP y la máscara de red respondiendo a los mensajes de consulta DHCP generados por el kernel. Este modo es probablemente la solución "más limpia" para establecer las propiedades TCP/IP, ya que utiliza el conocido protocolo DHCP. Sin embargo, hay dos requisitos previos para usar este modo:
1.
Las propiedades TCP/IP del adaptador TAP-Win32 deben establecerse en "Obtener una dirección IP automáticamente", y
2.
OpenVPN necesita reclamar una dirección IP en la subred para usarla como la dirección del servidor DHCP virtual.

Por defecto en el modo --dev tap, OpenVPN tomará la primera dirección normalmente no utilizada en la subred. Por ejemplo, si su subred es 192.168.4.0 máscara 255.255.255.0, entonces OpenVPN tomará la dirección IP 192.168.4.0 para usarla como la dirección del servidor DHCP virtual. En el modo --dev tun, OpenVPN hará que el servidor DHCP se enmascare como si proviniera del punto final remoto.

El parámetro opcional de desplazamiento es un entero que es mayor que -256 y menor que 256 y que por defecto es 0. Si el desplazamiento es positivo, el servidor DHCP se enmascarará como la dirección IP en la dirección de red + desplazamiento. Si el desplazamiento es negativo, el servidor DHCP se enmascarará como la dirección IP en la dirección de broadcast + desplazamiento.

El comando ipconfig /all de Windows se puede utilizar para mostrar lo que Windows piensa que es la dirección del servidor DHCP. OpenVPN "reclamará" esta dirección, así que asegúrese de usar una dirección libre. Dicho esto, diferentes instancias de OpenVPN, incluyendo diferentes extremos de la misma conexión, pueden compartir la misma dirección de servidor DHCP virtual.

El parámetro tiempo-concesion controla el tiempo de concesión de la asignación DHCP dada al adaptador TAP-Win32, y se indica en segundos. Normalmente se prefiere un tiempo de concesión muy largo, ya que evita que las rutas que involucran al adaptador TAP-Win32 se pierdan cuando el sistema entra en modo de suspensión. El tiempo de concesión por defecto es de un año.

Set the Windows system directory pathname to use when looking for system executables such as route.exe and netsh.exe. By default, if this directive is not specified, OpenVPN will use the SystemRoot environment variable.

This option has changed behaviour since OpenVPN 2.3. Earlier you had to define --win-sys env to use the SystemRoot environment variable, otherwise it defaulted to C:\\WINDOWS. It is not needed to use the env keyword any more, and it will just be ignored. A warning is logged when this is found in the configuration file.

--windows-driver drv
Specifies which tun driver to use. Values are ovpn-dco (default), tap-windows6 and wintun. ovpn-dco and wintun require --dev tun. wintun also requires OpenVPN process to run elevated, or be invoked using the Interactive Service.

Opciones de depuración independientes

--show-gateway args
(Standalone) Show current IPv4 and IPv6 default gateway and interface towards the gateway (if the protocol in question is enabled).

Valid syntax:

--show-gateway
--show-gateway IPv6-target

For IPv6 this queries the route towards ::/128, or the specified IPv6 target address if passed as argument. For IPv4 on Linux, Windows, MacOS and BSD it looks for a 0.0.0.0/0 route. If there are more specific routes, the result will not always be matching the route of the IPv4 packets to the VPN gateway.

Opciones avanzadas para expertos

These are options only required when special tweaking is needed, often used when debugging or testing out special usage scenarios.

--hash-size args
Set the size of the real address hash table to r and the virtual address table to v.

Valid syntax:

hash-size r v

By default, both tables are sized at 256 buckets.

--bcast-buffers n
Allocate n buffers for broadcast datagrams (default 256).
--persist-local-ip
Preserve initially resolved local IP address and port number across SIGUSR1 or --ping-restart restarts.
--persist-remote-ip
Preserve most recently authenticated remote IP address and port number across SIGUSR1 or --ping-restart restarts.
--rcvbuf size
Set the TCP/UDP socket receive buffer size. Defaults to operating system default.
--shaper n
Limit bandwidth of outgoing tunnel data to n bytes per second on the TCP/UDP port. Note that this will only work if mode is set to p2p. If you want to limit the bandwidth in both directions, use this option on both peers.

OpenVPN uses the following algorithm to implement traffic shaping: Given a shaper rate of n bytes per second, after a datagram write of b bytes is queued on the TCP/UDP port, wait a minimum of (b / n) seconds before queuing the next write.

It should be noted that OpenVPN supports multiple tunnels between the same two peers, allowing you to construct full-speed and reduced bandwidth tunnels at the same time, routing low-priority data such as off-site backups over the reduced bandwidth tunnel, and other data over the full-speed tunnel.

Also note that for low bandwidth tunnels (under 1000 bytes per second), you should probably use lower MTU values as well (see above), otherwise the packet latency will grow so large as to trigger timeouts in the TLS layer and TCP connections running over the tunnel.

OpenVPN allows n to be between 100 bytes/sec and 100 Mbytes/sec.

--sndbuf size
Set the TCP/UDP socket send buffer size. Defaults to operating system default.
--tcp-queue-limit n
Maximum number of output packets queued before TCP (default 64).

When OpenVPN is tunneling data from a TUN/TAP device to a remote client over a TCP connection, it is possible that the TUN/TAP device might produce data at a faster rate than the TCP connection can support. When the number of output packets queued before sending to the TCP socket reaches this limit for a given client connection, OpenVPN will start to drop outgoing packets directed at this client.

--txqueuelen n
(Linux only) Set the TX queue length on the TUN/TAP interface. Currently defaults to operating system default.
--disable-dco
Disables the opportunistic use of data channel offloading if available. Without this option, OpenVPN will opportunistically use DCO mode if the config options and the running kernel supports using DCO.

Data channel offload currently requires data-ciphers to only contain AEAD ciphers (AES-GCM and Chacha20-Poly1305) and Linux with the ovpn-dco module.

Note that some options have no effect or cannot be used when DCO mode is enabled.

On platforms that do not support DCO disable-dco has no effect.
