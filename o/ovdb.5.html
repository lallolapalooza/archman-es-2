NOMBRE

ovdb - Método de almacenamiento de vistas generales para INN

DESCRIPCIÓN

El método de vistas generales ovdb es un método de almacenamiento que utiliza la biblioteca Berkeley DB para almacenar datos de vistas generales. Requiere la versión 4.4 o posterior de la biblioteca Berkeley DB (se recomiendan 4.7+ ya que las versiones anteriores sufren de varios problemas).

El método de vistas generales ovdb hace uso de la funcionalidad completa de transacciones/registro/bloqueo del entorno Berkeley DB. Berkeley DB puede descargarse desde https://www.oracle.com/database/technologies/related/berkeleydb.html y es necesario para compilar el backend de ovdb.

Este método viene con una utilidad de soporte que permite la manipulación de información de vistas generales. Consulte ovdb_stat(8) para más detalles.

ACTUALIZACIÓN

Existen varias versiones del método de almacenamiento ovdb:

  • Versión 1, la versión inicial enviada con INN 2.3.0 hasta INN 2.3.5.
  • Versión 2, con rendimiento mejorado, desde INN 2.4.0.
  • Versión 3, correspondiente a la versión 2 con compresión habilitada, a partir de INN 2.5.0.

Si tiene una base de datos creada con una versión anterior de ovdb, su base de datos deberá actualizarse usando ovdb_init. Consulte la página del manual ovdb_init(8) para obtener instrucciones de actualización, así como la sección "COMPRESIÓN" a continuación.

Tenga en cuenta que cuando la biblioteca Berkeley DB se actualiza a una versión más reciente, la base de datos ovdb también debe actualizarse.

INSTALACIÓN

Si la biblioteca Berkeley DB se encuentra durante la configuración, INN se compilará con soporte Berkeley DB a menos que se pase explícitamente el flag --without-bdb a configure. Por defecto, configure buscará Berkeley DB en ubicaciones estándar; habrá un mensaje en la salida de configuración indicando la ruta del archivo que se utilizará.

Puede anular esta ruta añadiendo una ruta a la opción, por ejemplo --with-bdb=/usr/BerkeleyDB.4.4. Se espera que este directorio tenga los subdirectorios include y lib (también se comprueban lib32 y lib64), que contienen respectivamente db.h y la biblioteca misma. En caso de que se utilicen rutas no estándar a las bibliotecas Berkeley DB, se pueden dar una o ambas opciones --with-bdb-include y --with-bdb-lib a configure con una ruta.

La base de datos ovdb puede ocupar más espacio en disco para un spool dado que los otros métodos de vistas generales. Planifique necesitar al menos 1.1 KB por cada artículo en su spool (sin contar crossposts). Por lo tanto, si tiene 5 millones de artículos, necesitará al menos 5.5 GB de espacio en disco para ovdb. Con la compresión habilitada, esta estimación cambia a 0.9 KB por artículo, por lo que necesitará al menos 4.5 GB de espacio en disco para 5 millones de artículos. Consulte la sección "COMPRESIÓN" a continuación. Además, necesitará espacio adicional para los registros de transacciones: al menos 100 MB. Por defecto, los registros de transacciones van en el mismo directorio que la base de datos. Para mejorar el rendimiento, pueden colocarse en un disco diferente -- consulte la sección "DB_CONFIG".

CONFIGURACIÓN

Para habilitar el método de vistas generales ovdb, establezca el parámetro ovmethod en inn.conf a "ovdb". La base de datos ovdb se almacena en el directorio especificado por el parámetro pathoverview en inn.conf. Este es el directorio "DB_HOME". Para empezar, este directorio debe estar vacío (aparte de un archivo DB_CONFIG opcional; consulte "DB_CONFIG" para más detalles), y innd (o makehistory) creará los archivos según sea necesario en ese directorio. Además, asegúrese de que el directorio sea propiedad del usuario de noticias.

Otros parámetros para configurar ovdb se encuentran en el archivo de configuración ovdb.conf. Los siguientes parámetros se pueden establecer en ese archivo:

compress
Si INN se compiló con zlib, y este parámetro compress es verdadero, ovdb comprimirá los registros de vistas generales que tengan más de 600 bytes. Consulte la sección "COMPRESIÓN" a continuación.
cachesize
Tamaño de la caché del pool de memoria, en kilobytes. La caché tendrá un archivo de almacenamiento de respaldo en el directorio DB que será al menos tan grande. En general, cuanto mayor sea la caché, mejor. Use "ovdb_stat -m" para ver los porcentajes de aciertos de caché. Para que un cambio de este parámetro tenga efecto, apague y reinicie INN (asegúrese de matar a todos los procesos nnrpd al apagar). El valor predeterminado es 8000 (KB), lo cual es adecuado para servidores pequeños y medianos. Los servidores grandes probablemente necesitarán al menos 20000 (KB).
ncache
Número de regiones entre las cuales dividir la caché. El tamaño de la región es igual a cachesize dividido por ncache. El valor predeterminado es 1 para ncache, es decir, la caché se asignará de forma contigua en memoria.
numdbfiles
Los datos de vistas generales se dividen entre este número de archivos. Actualmente, innd mantendrá todos los archivos abiertos, así que no establezca este valor demasiado alto o innd podría quedarse sin descriptores de archivo. nnrpd solo abre uno a la vez, independientemente. Puede establecerse en uno, o solo unos pocos, pero solo haga eso si su sistema operativo soporta archivos grandes (> 2 GB). Cambiar este parámetro no tiene efecto en una base de datos ya establecida. El valor predeterminado es 32.
txn_nosync
Si txn_nosync se establece en falso, Berkeley DB vaciará el registro después de cada transacción. Esto minimiza el número de transacciones que pueden perderse en caso de un fallo, pero resulta en una degradación significativa del rendimiento. El valor predeterminado es verdadero, en cuyo caso ovdb_monitor vacía los registros de transacciones cada 30 segundos.
useshm
Si useshm se establece en verdadero, Berkeley DB utilizará memoria compartida en lugar de mmap para sus regiones de entorno (caché, bloqueo, etc.). En algunas plataformas, esto puede mejorar el rendimiento. El valor predeterminado es falso.
shmkey
Establece la clave de memoria compartida utilizada por Berkeley DB cuando useshm es verdadero. Berkeley DB creará varios (generalmente 5) segmentos de memoria compartida, utilizando claves numeradas secuencialmente comenzando con "shmkey". Elija una clave que no entre en conflicto con ningún segmento de memoria compartida existente en su sistema. El valor predeterminado es 6400.
pagesize
Establece el tamaño de página para los archivos DB (en bytes). Debe ser una potencia de 2. Las mejores opciones son 4096 o 8192. El valor predeterminado es 8192. Cambiar este parámetro no tiene efecto en una base de datos ya establecida.
minkey
Establece el número mínimo de claves por página. Consulte la documentación de Berkeley DB para obtener más información. El valor predeterminado se basa en el tamaño de página y si la compresión está habilitada: 
default_minkey = MAX(2, pagesize / 2600) si compress es falso
default_minkey = MAX(2, pagesize / 1500) si compress es verdadero

El valor más bajo permitido de minkey es 2. No se recomienda establecer minkey más alto que el valor predeterminado, ya que provocará que las bases de datos tengan muchas páginas de desbordamiento. Cambiar este parámetro no tiene efecto en una base de datos ya establecida.

maxlocks
Establece el parámetro lk_max de Berkeley DB, que es el número máximo de bloqueos que pueden existir en la base de datos al mismo tiempo. El valor predeterminado es 4000.
nocompact
El parámetro nocompact afecta el comportamiento de expireover. La función expireover en ovdb puede hacer su trabajo de dos maneras: simplemente eliminando registros expirados de la base de datos; o reescribiendo los registros de vistas generales en una ubicación diferente

CONFIGURATION

La configuración de ovdb se realiza principalmente a través del archivo inn.conf(5) y del archivo ovdb.conf(5).

ovmethod
Este parámetro, que se encuentra en inn.conf(5), determina qué método se utilizará para el almacenamiento de la información general. Debe establecerse en "ovdb" para utilizar este método.
pathoverview
Este parámetro, que también se encuentra en inn.conf(5), especifica el directorio donde se almacenarán los archivos de la base de datos de ovdb. Berkeley DB lo llama el directorio "DB_HOME".
ovdb_compact
Este parámetro controla si y cómo expireover compactará los newsgroups. Al compactar, se eliminan los registros caducados y se reorganizan los registros restantes para eliminar los "huecos" dejados por los registros eliminados. Esto puede mejorar la eficiencia del espacio en disco.

Existen dos métodos principales para eliminar registros caducados: el método rápido que simplemente marca los registros como eliminados y el método de compactación que reescribe los registros. El primer método es más rápido, pero deja "huecos" que resultan en espacio que no puede ser reutilizado inmediatamente. El segundo método "compacta" los registros reescribiéndolos.

Si este parámetro se establece en 0, expireover compactará todos los newsgroups; si se establece en 1, expireover no compactará ningún newsgroups; y si se establece en un valor superior a uno, expireover solo compactará los grupos que tengan menos que ese número de artículos.

La experiencia ha demostrado que la compactación tiene un efecto mínimo (aparte de hacer que expireover tarde más) por lo que el valor predeterminado es 1. Es probable que este parámetro se elimine en el futuro.

readserver
Cuando el parámetro readserver se establece en false, cada proceso nnrpd accede directamente al entorno de Berkeley DB. El proceso de conexión a la base de datos (y desconexión al terminar) es bastante costoso, y puede resultar en cargas elevadas en situaciones en las que hay muchas conexiones de lectores de corta duración relativa.

Cuando el parámetro readserver se establece en true, los procesos nnrpd accederán a la vista general a través de un servidor auxiliar (ovdb_server -- que es iniciado por ovdb_init). Todas las lecturas de ovdb se canalizarán a través de un solo proceso con una interfaz más limpia a la base de datos subyacente de Berkeley DB. Esto resultará en cierres más limpios para la base de datos, mejorando la estabilidad y evitando interbloqueos, problemas de temporización y bases de datos corruptas. Es por eso que debería intentar establecer este parámetro en true si está experimentando alguna inestabilidad en el método de vista general de ovdb.

El valor predeterminado es true.

numrsprocs
Este parámetro solo se utiliza cuando readserver es true. Establece el número de procesos ovdb_server. Como cada ovdb_server solo puede procesar una transacción a la vez, ejecutar más servidores puede mejorar los tiempos de respuesta del lector. El valor predeterminado es 5.
maxrsconn
Este parámetro solo se utiliza cuando readserver es true. Establece un número máximo de lectores que un proceso ovdb_server dado servirá a la vez. Esto significa que el número máximo de lectores para todos los procesos ovdb_server es (numrsprocs * maxrsconn). Esto *no* limita el número real de lectores, ya que nnrpd recurrirá a abrir la base de datos directamente si no puede conectarse a un ovdb_server. El valor predeterminado es 0, lo que significa que se permite un número ilimitado de conexiones.

COMPRESIÓN

El método de almacenamiento ovdb tiene la capacidad de comprimir los datos de la vista general antes de que se almacenen en la base de datos. Además de consumir menos espacio en disco, la compresión mantiene el tamaño promedio de las claves de la base de datos más pequeño. Esto, a su vez, aumenta el número promedio de claves por página, lo que puede mejorar significativamente el rendimiento y también ayuda a mantener la base de datos más compacta. Esta función requiere que INN se compile con zlib. Solo los registros de más de 600 bytes se comprimen, porque ese es el punto en el que la compresión comienza a ser significativa.

Si la compresión no está habilitada (ya sea por la opción compress en ovdb.conf o porque INN no se compiló con soporte para zlib), la base de datos será compatible con versiones anteriores de ovdb. Sin embargo, si la compresión está habilitada, la base de datos se marca con una versión más reciente que evitará que las versiones antiguas de ovdb abran la base de datos.

Puede actualizar una base de datos existente para utilizar la compresión simplemente estableciendo compress en true en ovdb.conf. Tenga en cuenta que los registros existentes en la base de datos permanecerán sin comprimir; solo los registros nuevos añadidos después de habilitar la compresión se comprimirán.

Si deshabilita la compresión en una base de datos que la tenía previamente habilitada, los nuevos registros se almacenarán sin comprimir, pero la base de datos seguirá siendo incompatible con versiones anteriores de ovdb (y también será incompatible con esta versión de ovdb si INN no se compiló con soporte para zlib). Por lo tanto, para degradar a una base de datos completamente sin comprimir, deberá reconstruir la base de datos usando makehistory.

DB_CONFIG

Un archivo llamado DB_CONFIG puede colocarse en el directorio de la base de datos (pathoverview en inn.conf) para personalizar dónde se escribirán los diversos archivos de la base de datos y los registros de transacciones. Por defecto, todos los archivos se escriben en el directorio "DB_HOME". Una forma de mejorar el rendimiento es colocar los registros de transacciones en un disco diferente. Para hacer esto, coloque:

DB_LOG_DIR /path/to/logs

en el archivo DB_CONFIG. Si el nombre del camino que proporciona comienza con un "/", se trata como una ruta absoluta; de lo contrario, es relativo al directorio "DB_HOME". Asegúrese de que cualquier directorio que especifique exista y tenga la propiedad/modo correctos antes de iniciar INN, ya que no se crearán automáticamente. Además, no cambie el archivo DB_CONFIG mientras cualquier cosa que use ovdb esté en ejecución.

Otra cosa que puede hacer con este archivo es dividir la base de datos de vista general en varios discos. En el archivo DB_CONFIG, puede enumerar directorios en los que Berkeley DB buscará cuando vaya a abrir una base de datos.

Por ejemplo, digamos que tiene pathoverview establecido en /mnt/overview y tiene cuatro sistemas de archivos adicionales creados en /mnt/ovX. Crearía un archivo /mnt/overview/DB_CONFIG que contenga las siguientes líneas:

set_data_dir /mnt/overview
set_data_dir /mnt/ov1
set_data_dir /mnt/ov2
set_data_dir /mnt/ov3
set_data_dir /mnt/ov4

Distribuya sus archivos ovNNNNN en los cuatro sistemas de archivos (digamos, 8 cada uno). Cuando se le solicite abrir un archivo de base de datos, la biblioteca de db buscará en cada uno de los directorios especificados (en orden). Si dicho archivo no se encuentra, se creará en el primer directorio de esos.

Cada vez que cambie DB_CONFIG o mueva archivos de base de datos, asegúrese de que todos los procesos de noticias que usan la base de datos se detengan primero (incluidos los procesos nnrpd).

La funcionalidad DB_CONFIG es parte de Berkeley DB en sí, en lugar de algo proporcionado por ovdb. Consulte la documentación de Berkeley DB para obtener detalles completos sobre la versión de Berkeley DB que está ejecutando.

EJECUCIÓN

Al iniciar el sistema de noticias, rc.news invocará al programa ovdb_init. Consulte la página del manual de ovdb_init(8) para obtener información sobre las tareas que realiza. ovdb_init debe ejecutarse antes de utilizar la base de datos.

Y al detener INN, rc.news mata los procesos ovdb_monitor después de que los otros procesos de INN se hayan detenido.

DIAGNÓSTICOS

Los problemas relacionados con ovdb se registran en news.err con "OVDB" en el mensaje de error.

Los programas de INN que usan la vista general fallarán al iniciarse si los procesos ovdb_monitor no se están ejecutando. Asegúrese de ejecutar ovdb_init antes de ejecutar cualquier cosa que acceda a la vista general.

Además, los programas de INN que usan la vista general fallarán al iniciarse si el usuario que los ejecuta no es el usuario de noticias.

Si un programa que accede a la base de datos se bloquea o, de lo contrario, sale de forma poco limpia, podría dejar un bloqueo obsoleto en la base de datos. Este bloqueo podría hacer que otros procesos se bloqueen en ese bloqueo obsoleto. Para solucionar esto, detenga todos los procesos de noticias (usando "kill -9" si es necesario) y luego reinicie. ovdb_init debería realizar una operación de recuperación que eliminará los bloqueos y reparará los daños causados por matar los procesos bloqueados.

ARCHIVOS

pathetc/inn.conf
Los parámetros ovmethod y pathoverview son relevantes para ovdb.
pathetc/ovdb.conf
Archivo de configuración opcional para ajustar. Consulte "CONFIGURACIÓN" arriba.
pathoverview
Directorio donde va la base de datos. Berkeley DB lo llama el directorio "DB_HOME".
pathoverview/DB_CONFIG
Archivo opcional para configurar el diseño de los archivos de la base de datos.
pathrun/ovdb.sem
Un archivo que es bloqueado por cada proceso que accede a la base de datos. Esto es utilizado por ovdb_init para determinar si la base de datos está activa o inactiva.
pathrun/ovdb_monitor.pid
Contiene el ID del proceso de ovdb_monitor.

POR HACER

Implementar una forma de limitar cuántas bases de datos se pueden abrir a la vez (para reducir el uso de descriptores de archivo); tal vez utilizando algo similar al código de caché en el archivo legado ov3.c.

NAME

ovdb - ONC RPC well-known port database

DESCRIPTION

The ONC RPC (Open Network Computing Remote Procedure Call) system is a distributed computing system developed by Sun Microsystems. It allows a client program to call routines in a remote server program. The ONC RPC well-known port database, /etc/rpc, maps RPC program numbers to names and vice versa. This file is a colon-separated database with each line formatted as:

name:number:alias1:alias2:...

The rpcbind daemon (also known as portmapper) uses this file to translate RPC program numbers to the network addresses on which the services are registered. The rpc.bfs daemon also uses this database.

UPGRADING

When upgrading the rpcbind package, the package manager (pacman) will prompt you to replace your /etc/rpc file. If you have made customizations to this file, you should back it up before answering the prompt. It is recommended to keep your customizations in sync with the new file.

INSTALLATION

The /etc/rpc file is installed by the rpcbind package. If you need to add a new RPC service to the system, you should edit this file and add a new entry for the service.

CONFIGURATION

The /etc/rpc file is the primary configuration file for mapping RPC program numbers to names. No other configuration files are typically used for this purpose.

COMPRESSION

This file is not compressed and is typically small.

DB_CONFIG

There is no db_config file associated with the /etc/rpc database.

RUNNING

The /etc/rpc file is not a program that is run directly. It is read by daemons such as rpcbind and rpc.bfs.

DIAGNOSTICS

Errors related to the /etc/rpc file usually manifest as problems connecting to or using RPC services. If a service fails to start or a client cannot connect to a remote procedure, checking the syntax and content of /etc/rpc may be necessary. The rpcinfo command can be used to query RPC services and may provide diagnostic information.

FILES

  • /etc/rpc: The ONC RPC well-known port database.

TO DO

No specific "to do" items are associated with this manual page.

HISTORY

The /etc/rpc file has been a standard part of ONC RPC implementations for many years. Its format and purpose have remained largely consistent.
