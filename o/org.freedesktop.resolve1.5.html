NOMBRE

org.freedesktop.resolve1 - La interfaz D-Bus de systemd-resolved

INTRODUCCIÓN

systemd-resolved.service(8) es un servicio del sistema que proporciona resolución de nombres de host y caché utilizando DNS, LLMNR y mDNS. También realiza validación DNSSEC. Esta página describe la semántica de resolución y la interfaz D-Bus.

Esta página contiene solo una referencia de API. Si está buscando una explicación más detallada sobre cómo usar esta API, consulte Escritura de Gestores de Configuración de Red[1] y Escritura de Clientes Resolutores[2].

Métodos

ResolveHostname() toma un nombre de host y lo resuelve a una o más direcciones IP. Como parámetros, toma el índice de la interfaz de red de Linux en la que ejecutar la consulta, o 0 si se puede hacer en cualquier interfaz adecuada. El parámetro name especifica el nombre de host a resolver. Tenga en cuenta que si es necesario, se aplica la conversión IDNA a este nombre a menos que se resuelva a través de LLMNR o MulticastDNS. El parámetro family limita los resultados a una familia de direcciones específica. Puede ser AF_INET, AF_INET6 o AF_UNSPEC. Si se especifica AF_UNSPEC (recomendado), se recuperan ambos tipos, sujetos a la configuración de red local (es decir, si no se encuentra una dirección IPv6 local y enrutable, no se recupera ninguna dirección IPv6; y de manera similar para IPv4). Un campo flags de 64 bits puede usarse para modificar el comportamiento de la operación del resolutor (ver más abajo). El método devuelve una matriz de registros de direcciones. Cada registro de dirección consta del índice de la interfaz al que pertenece la dirección, una familia de direcciones, así como una matriz de bytes con los datos reales de la dirección IP (que tiene 4 o 16 elementos, dependiendo de la familia de direcciones). La familia de direcciones devuelta será AF_INET o AF_INET6. Para IPv6, el índice de interfaz de la dirección devuelta debe usarse para inicializar el campo .sin6_scope_id de una instancia de struct sockaddr_in6 para permitir el soporte de resolución a direcciones IP de enlace local. La matriz de direcciones va seguida del nombre canónico del host, que puede o no ser idéntico al nombre de host resuelto. Finalmente, se devuelve un campo flags de 64 bits que se define de manera similar al campo flags que se pasó, pero contiene información sobre los datos resueltos (ver más abajo). Si el nombre de host pasado es una dirección IPv4 o IPv6 formateada como cadena, se analiza y se devuelve el resultado. En este caso, no se realiza ninguna comunicación de red.

ResolveAddress() ejecuta la operación inversa: toma una dirección IP y adquiere uno o más nombres de host para ella. Como parámetros, toma el índice de la interfaz para ejecutar la consulta, o 0 si todas las interfaces adecuadas están bien. El parámetro family indica la familia de direcciones de la dirección IP a resolver. Puede ser AF_INET o AF_INET6. El parámetro address toma los datos crudos de la dirección IP (como una matriz de 4 o 16 bytes). El parámetro de entrada flags puede usarse para modificar la operación del resolutor (ver más abajo). El método devuelve una matriz de registros de nombres, cada uno consistente en un índice de interfaz y un nombre de host. El campo de salida flags contiene información adicional sobre la operación del resolutor (ver más abajo).

ResolveRecord() toma un tipo de registro de recursos (RR) DNS, una clase y un nombre, y recupera el conjunto completo de registros de recursos (RRset), incluyendo el RDATA, para él. Como parámetro, toma el índice de la interfaz de red de Linux en la que ejecutar la consulta, o 0 si se puede hacer en cualquier interfaz adecuada. El parámetro name especifica el nombre de dominio RR a buscar (no se aplica conversión IDNA), seguido de los campos de clase y tipo de 16 bits (que pueden ser ANY). Finalmente, se puede pasar un campo flags para modificar el comportamiento de la búsqueda (ver más abajo). Al finalizar, se devuelve una matriz de elementos RR. Cada entrada de matriz consta del índice de la interfaz de red en la que se descubrió el RR, los campos de tipo y clase del RR encontrado, y una matriz de bytes del RR crudo descubierto. Los datos del RR crudo comienzan con el nombre de dominio del RR, en la capitalización original, seguido por el tipo de RR, clase, TTL y RDATA, en el formato binario documentado en RFC 1035[3]. Tenga en cuenta que actualmente, el campo class debe especificarse como IN o ANY. Especificar una clase diferente devolverá un error que indica que las búsquedas de este tipo no son compatibles. De manera similar, tampoco se admiten algunos tipos especiales (AXFR, OPT, ...). ResolveService() puede usarse para resolver un registro de servicio DNS SRV, así como los nombres de host a los que se hace referencia en él, y posiblemente un registro TXT de DNS-SD adjunto que contenga metadatos adicionales del servicio. El beneficio principal de usar este método sobre ResolveRecord() especificando el tipo SRV es que resolverá los RR SRV y TXT, así como los nombres de host a los que se hace referencia en el SRV en una sola operación. Como parámetros, toma un índice de interfaz de red de Linux, un nombre de servicio, un tipo de servicio y un dominio de servicio. Este método puede invocarse en tres modos diferentes:

1. Para resolver un servicio DNS-SD, especifique el nombre del servicio (por ejemplo, "Lennart's Files"), el tipo de servicio (por ejemplo, "_webdav._tcp") y el dominio en el que buscar (por ejemplo, "local") como los tres parámetros de servicio. El nombre del servicio debe estar en formato UTF-8, y no se le aplica ninguna conversión IDNA en este modo (según lo exigen las especificaciones de DNS-SD). Sin embargo, si es necesario, se aplica la conversión IDNA al parámetro de dominio.
2. Para resolver un registro SRV simple, establezca el parámetro de nombre de servicio en una cadena vacía y establezca el tipo de servicio y el dominio correctamente. (La conversión IDNA se aplica al dominio, si es necesario).
3. Alternativamente, deje vacíos tanto el nombre del servicio como el tipo, y especifique el nombre de dominio completo del registro SRV (es decir, prefijado con el tipo de servicio) en el parámetro de dominio. (No se aplica ninguna conversión IDNA en este modo).

El parámetro family del método ResolveService() codifica la familia deseada de las direcciones a resolver (use AF_INET, AF_INET6 o AF_UNSPEC). Si esto está habilitado (Use la bandera NO_ADDRESS para desactivar la resolución de direcciones, ver abajo). El parámetro flags toma un par de banderas que se pueden usar para modificar la operación del resolvedor.

Al finalizar, ResolveService() devuelve una matriz de estructuras de registro SRV. Cada elemento consta de los campos de prioridad, peso y puerto, así como el nombre de host al que contactar, según lo codificado en el registro SRV. Inmediatamente después, sigue una matriz de las direcciones de este nombre de host, con cada elemento que consta del índice de interfaz, la familia de direcciones y los datos de la dirección en una matriz de bytes. Esta matriz de direcciones va seguida del nombre de host canonizado. Después de esta matriz de estructuras de registro SRV, sigue una matriz de matrices de bytes que codifica las cadenas de registro TXT, en caso de que las búsquedas de DNS-SD estén habilitadas. Los siguientes parámetros son el nombre de servicio canónico, el tipo y el dominio. Esto puede o no ser idéntico a los parámetros pasados. Finalmente, se devuelve un campo flags que contiene información sobre la operación del resolvedor realizada.

El método ResetStatistics() restablece los diversos contadores de estadísticas que systemd-resolved mantiene a cero. (Para obtener detalles, consulte las propiedades de estadísticas a continuación).

El método GetLink() toma un índice de interfaz de red y devuelve la ruta del objeto al objeto org.freedesktop.resolve1.Link correspondiente.

El método SetLinkDNS() establece los servidores DNS a utilizar en una interfaz específica. Este método (y los siguientes) pueden ser utilizados por el software de gestión de red para configurar ajustes de DNS por interfaz. Toma un índice de interfaz de red, así como una matriz de registros de direcciones IP de servidores DNS. Cada elemento de la matriz consta de una familia de direcciones (ya sea AF_INET o AF_INET6), seguido de una matriz de 4 u 8 bytes con los datos brutos de la dirección. Este método es un atajo de un solo paso para recuperar el objeto Link para una interfaz de red usando GetLink() (ver arriba) y luego invocar el método SetDNS() (ver abajo) en él.

SetLinkDNSEx() es similar a SetLinkDNS(), pero permite especificar un puerto IP (en lugar del valor predeterminado 53) y un nombre DNS para cada servidor DNS. El nombre del servidor se utiliza para la Indicación de Nombre de Servidor (SNI), lo cual es útil cuando se utiliza DNS-over-TLS. C.f. DNS= en resolved.conf(5).

SetLinkDefaultRoute() especifica si el enlace se utilizará como ruta predeterminada para las consultas de nombres. Consulte la descripción del enrutamiento de nombres en systemd-resolved.service(8) para obtener detalles.

El método SetLinkDomains() establece los dominios de búsqueda y enrutamiento a utilizar en una interfaz de red específica para las búsquedas DNS. Toma un índice de interfaz de red y una matriz de dominios, cada uno con un parámetro booleano que indica si el dominio especificado se utilizará como dominio de búsqueda (falso) o solo como dominio de enrutamiento (verdadero). Los dominios de búsqueda se utilizan para calificar nombres de un solo nivel a FQDN al buscar nombres de host, así como para tomar decisiones de enrutamiento sobre qué interfaz enviar consultas que terminan en el dominio. Los dominios de enrutamiento solo se utilizan para decisiones de enrutamiento y no para la calificación de nombres de un solo nivel. Pase los dominios de búsqueda en el orden en que deben usarse.

El método SetLinkLLMNR() habilita o deshabilita el soporte LLMNR en una interfaz de red específica. Toma un índice de interfaz de red, así como una cadena que puede estar vacía o ser una de "yes", "no" o "resolve". Si está vacía, se utiliza la configuración LLMNR predeterminada en todo el sistema. Si es "yes", LLMNR se utiliza para la resolución de nombres de un solo nivel y el nombre de host local se registra en todas las LAN locales para la resolución LLMNR por parte de los pares. Si es "no", LLMNR se desactiva por completo en esta interfaz. Si es "resolve", LLMNR solo se habilita para resolver nombres, pero el nombre de host local no se registra para que lo utilicen otros pares.

De manera similar, el método SetLinkMulticastDNS() habilita o deshabilita el soporte MulticastDNS en una interfaz específica. Toma los mismos parámetros que SetLinkLLMNR() descritos anteriormente.

El método SetLinkDNSSEC() habilita o deshabilita la validación DNSSEC en una interfaz de red específica. Toma un índice de interfaz de red, así como una cadena que puede estar vacía o ser una de "yes", "no" o "allow-downgrade". Cuando está vacía, se utiliza la configuración DNSSEC predeterminada en todo el sistema. Si es "yes", se realiza una validación DNSSEC completa para todas las búsquedas. Si el servidor DNS seleccionado no admite DNSSEC, las búsquedas fallarán si se utiliza este modo. Si es "no", la validación DNSSEC se deshabilita por completo. Si es "allow-downgrade", la validación DNSSEC está habilitada, pero se desactiva automáticamente si el servidor seleccionado no la admite (abriendo así el comportamiento a ataques de degradación). Tenga en cuenta que DNSSEC solo se aplica al DNS tradicional, no a LLMNR o MulticastDNS.

El método SetLinkDNSSECNegativeTrustAnchors() puede utilizarse para configurar Anclas de Confianza Negativas DNSSEC (NTA) para una interfaz de red específica. Toma un índice de interfaz de red y una lista de dominios como argumentos.

El método SetLinkDNSOverTLS() habilita o deshabilita DNS-over-TLS. C.f. DNSOverTLS= en systemd-resolved.service(8) para obtener detalles.

El software de gestión de red que se integra con systemd-resolved debe llamar a SetLinkDNS() o SetLinkDNSEx(), SetLinkDefaultRoute(), SetLinkDomains() y otros después de que la interfaz aparezca en el kernel (y, por lo tanto, después de que se haya asignado un índice de interfaz de red), pero antes de que la interfaz de red se active (se establezca IFF_UP) para que todos los ajustes surtan efecto durante todo el tiempo que la interfaz de red esté activa. Sin embargo, es seguro alterar los ajustes mientras la interfaz está activa. Utilice RevertLink() (descrito a continuación) para restablecer todos los ajustes por interfaz.

El método RevertLink() puede usarse para revertir todos los ajustes por enlace descritos anteriormente a los predeterminados.

El método FlushCaches() vacía todas las cachés de registros de recursos mantenidas por el resolvedor y garantiza que las búsquedas posteriores vuelvan a solicitar sus respuestas a sus fuentes.

El método ResetServerFeatures() vacía cualquier información de características aprendida sobre los servidores DNS remotos. Esto garantiza que las búsquedas posteriores se intenten inicialmente en el nivel de característica de protocolo DNS más alto nuevamente, lo que posiblemente requiera un ciclo de degradación (potencialmente lento) para reconocer nuevamente el nivel de característica compatible.

El método RegisterService() puede usarse para registrar un servicio DNS-SD en el host. Esta funcionalidad está estrechamente relacionada con la funcionalidad proporcionada por los archivos systemd.dnssd(5). Toma una cadena de identificador de servidor como primer parámetro (este es solo un identificador local y debe elegirse de manera que no colisione ni con el nombre base de los archivos *.dnssd ni con los nombres elegidos por otros clientes IPC). También toma una cadena de plantilla de nombre para el nombre del servicio DNS-SD visible en la red. Esta cadena está sujeta a expansión de especificadores, como se documenta para la configuración Name= en los archivos *.dnssd. También toma una cadena de tipo de servicio que contiene el tipo de servicio DNS-SD, así como un puerto IP, un par de prioridad/peso para el registro SRV de DNS-SD. Finalmente, toma una matriz de datos de registro TXT. Devuelve una ruta de objeto que puede usarse como identificador para el servicio registrado.

El método UnregisterService() deshace el efecto de RegisterService() y elimina un servicio DNS-SD creado previamente a través de IPC.

El método GetDelegate() devuelve la ruta del objeto D-Bus para el ID de delegado DNS especificado.

El método ListDelegates() devuelve una lista de los IDs y las rutas de objeto D-Bus de los delegados DNS actualmente configurados.

En la entrada, las primeras cinco banderas controlan los protocolos a utilizar para la consulta. Se refieren al DNS unicast clásico, LLMNR a través de IPv4/UDP e IPv6/UDP respectivamente, así como MulticastDNS a través de IPv4/UDP e IPv6/UDP. Si todos estos cinco bits están desactivados en la entrada (lo cual es muy recomendable), la consulta se realizará a través de todos los protocolos adecuados para la consulta específica. Tenga en cuenta que estas banderas operan solo como filtro, pero no pueden forzar que una consulta se realice a través de un protocolo. Específicamente, systemd-resolved solo enrutará consultas dentro del TLD .local a MulticastDNS (más algunos dominios de búsqueda de direcciones de resolución inversa), y nombres de etiqueta única a LLMNR (más algunos dominios de búsqueda de direcciones de resolución inversa). Tampoco dirigirá ninguno de estos a servidores DNS Unicast. Además, solo realizará LLMNR y Multicast DNS en interfaces adecuadas para multidifusión.

En la salida, estas cinco banderas indican qué protocolo se utilizó para ejecutar la operación y, por lo tanto, dónde se encontraron los datos.

Los casos de uso principales para estas cinco banderas son las consultas de seguimiento basadas en datos DNS recuperados anteriormente. En este caso, a menudo es una buena idea limitar la consulta de seguimiento al protocolo que se utilizó para descubrir el primer resultado DNS.

La bandera NO_CNAME controla si los registros de recursos CNAME/DNAME deben seguirse durante la consulta. Esta bandera solo está disponible en la entrada, ninguna de las funciones la devolverá en la salida. Si se descubre un RR CNAME/DNAME al resolver un nombre de host, se devuelve un error en su lugar. Por defecto, cuando la bandera está desactivada, se siguen los RR CNAME/DNAME.

Las banderas NO_TXT y NO_ADDRESS solo influyen en la operación del método ResolveService(). Solo están definidas para la entrada, no para la salida. Si se establece NO_TXT, la consulta de RR TXT de DNS-SD no se realiza en la misma operación. Si se establece NO_ADDRESS, los nombres de host descubiertos no se traducen implícitamente a sus direcciones.

La bandera NO_SEARCH desactiva la lógica del dominio de búsqueda. Solo está definida para la entrada en ResolveHostname(). Cuando se especifica, los nombres de host de etiqueta única no se califican utilizando dominios de búsqueda definidos, si los hay configurados. Tenga en cuenta que ResolveRecord() nunca calificará los nombres de dominio de etiqueta única utilizando dominios de búsqueda. También tenga en cuenta que los nombres de host de etiqueta múltiple nunca están sujetos a la expansión de la lista de búsqueda.

NO_VALIDATE se puede establecer para deshabilitar la validación a través de DNSSEC, incluso si normalmente se utilizaría.

Los siguientes seis bits permiten deshabilitar ciertas fuentes durante la resolución. NO_SYNTHESIZE deshabilita los registros sintéticos, por ejemplo, el nombre de host local, consulte la sección REGISTROS SINTÉTICOS en systemd-resolved.service(8) para más información. NO_CACHE deshabilita el uso de la caché de registros resueltos previamente. NO_ZONE deshabilita las respuestas utilizando registros de recursos LLMNR/mDNS públicos registrados localmente. NO_TRUST_ANCHOR deshabilita las respuestas utilizando anclajes de confianza configurados localmente. NO_NETWORK requiere que todas las respuestas se proporcionen sin utilizar la red, es decir, desde fuentes locales o la caché. La bandera NO_STALE se puede establecer para deshabilitar la respuesta a solicitudes con registros obsoletos.

El bit AUTHENTICATED solo está definido en las banderas de salida de las cuatro funciones. Si está establecido, los datos devueltos han sido completamente autenticados. Específicamente, este bit se establece para todos los datos protegidos por DNSSEC para los cuales se puede establecer una cadena de confianza completa a un anclaje de dominio de confianza. También se establece para datos sintetizados localmente, como "localhost" o datos de /etc/hosts. Además, se establece para todos los RR de LLMNR o mDNS que se originan en el host local. Las aplicaciones que requieren datos RR autenticados para su funcionamiento deben verificar esta bandera antes de confiar en los datos. Tenga en cuenta que systemd-resolved nunca devolverá datos no válidos, por lo que esta bandera simplemente permite discernir los casos en los que se sabe que los datos son de confianza, o donde hay pruebas de que los datos están "legítimamente" sin autenticar (lo que incluye casos en los que el protocolo o servidor subyacente no admite la autenticación de datos).

CONFIDENTIAL significa que la consulta se resolvió a través de canales cifrados o nunca salió de este sistema.

Los siguientes cinco bits de banderas se utilizan en la salida y proporcionan información sobre el origen de la respuesta. FROM_SYNTHETIC significa que la consulta se sintetizó (al menos parcialmente) localmente. FROM_CACHE significa que la consulta se respondió (al menos parcialmente) utilizando la caché. FROM_ZONE significa que la consulta se respondió (al menos parcialmente) basándose en registros públicos registrados localmente. FROM_TRUST_ANCHOR significa que la consulta se respondió (al menos parcialmente) utilizando anclajes de confianza locales. FROM_NETWORK significa que la consulta se respondió (al menos parcialmente) utilizando la red.

Propiedades

Las propiedades LLMNR y MulticastDNS informan si LLMNR y MulticastDNS están habilitados (globalmente). Cada uno puede ser uno de "yes", "no" y "resolve". Consulte SetLinkLLMNR() y SetLinkMulticastDNS() arriba.

LLMNRHostname contiene el nombre de host expuesto actualmente en la red a través de LLMNR. Generalmente sigue al nombre de host del sistema que se puede consultar a través de gethostname(3), pero puede diferir si se detecta un conflicto en la red.

DNS y DNSEx contienen matrices de todos los servidores DNS utilizados actualmente por systemd-resolved. DNS contiene información similar a los datos del servidor DNS en /run/systemd/resolve/resolv.conf. Cada estructura en la matriz consta de un índice numérico de interfaz de red, una familia de direcciones y una matriz de bytes que contiene la dirección del servidor DNS (ya sea de 4 bytes de longitud para IPv4 o de 16 bytes de longitud para IPv6). DNSEx es similar, pero además contiene el puerto IP y el nombre del servidor (utilizado para Server Name Indication, SNI). Ambas matrices contienen servidores DNS configurados a nivel de sistema, incluidos los que posiblemente se leyeron de un /etc/resolv.conf externo o la configuración DNS= en /etc/systemd/resolved.conf, así como información de servidor DNS por interfaz recuperada de systemd-networkd(8), o configurada por software externo a través de SetLinkDNS() o SetLinkDNSEx() (ver arriba). El índice de la interfaz de red será 0 para los servicios configurados a nivel de sistema y distinto de cero para los servidores por enlace.

FallbackDNS y FallbackDNSEx contienen matrices de todos los servidores DNS configurados como servidores de reserva, si los hay, con el mismo formato que DNS y DNSEx descritos anteriormente. Consulte la descripción de FallbackDNS= en resolved.conf(5) para la descripción de cuándo se utilizan esos servidores.

CurrentDNSServer y CurrentDNSServerEx especifican el servidor que se utiliza actualmente para la resolución de consultas, en el mismo formato que una sola entrada en las matrices DNS y DNSEx descritas anteriormente.

De manera similar, la propiedad Domains contiene una matriz de todos los dominios de búsqueda y enrutamiento utilizados actualmente por systemd-resolved. Cada entrada consta de un índice de interfaz de red (de nuevo, 0 codifica entradas a nivel de sistema), el nombre de dominio real y si la entrada se utiliza solo para enrutamiento (verdadero) o tanto para enrutamiento como para búsqueda (falso).

TransactionStatistics contiene información sobre el número de transacciones que systemd-resolved ha procesado. Contiene un par de contadores sin signo de 64 bits, el primero contiene el número de transacciones actualmente en curso, el segundo el número total de transacciones que systemd-resolved está procesando o ha procesado. Este último valor puede restablecerse utilizando el método ResetStatistics() descrito anteriormente. Tenga en cuenta que el número de transacciones no se mapea directamente al número de llamadas de método de bus del resolvedor emitidas. Si bien las consultas simples generalmente requieren solo una transacción, las consultas más complejas pueden resultar en más, por ejemplo, cuando se utilizan CNAME o DNSSEC.

CacheStatistics contiene información sobre las operaciones de caché ejecutadas hasta ahora. Expone tres contadores de 64 bits: el primero es el número total de entradas de caché actuales (tanto positivas como negativas), el segundo el número de aciertos de caché y el tercero el número de fallos de caché. Los últimos contadores pueden restablecerse utilizando ResetStatistics() (ver arriba).

La propiedad DNSSEC especifica el estado actual de la validación DNSSEC. Es uno de "yes" (se fuerza la validación), "no" (no se realiza ninguna validación), "allow-downgrade" (se realiza la validación si el servidor DNS actual lo admite). Consulte la descripción de DNSSEC= en resolved.conf(5).

DNSSECStatistics contiene información sobre las validaciones DNSSEC ejecutadas hasta ahora. Contiene cuatro contadores de 64 bits: el número de validaciones DNSSEC seguras, inseguras, anómalas e indeterminadas hasta ahora. Los contadores se incrementan para cada conjunto de registros validado y cada prueba de no existencia. El contador seguro se incrementa para cada operación que verificó con éxito una respuesta firmada, el contador inseguro se incrementa para cada operación que verificó con éxito que una respuesta sin firmar es legítimamente sin firmar. El contador anómalo se incrementa para cada operación en la que la validación no se corresponde y es probable que los datos hayan sido manipulados. Finalmente, el contador indeterminado se incrementa para cada operación que no se completó porque no se pudieron adquirir las claves necesarias o los algoritmos criptográficos eran desconocidos.

La propiedad booleana DNSSECSupported informa si DNSSEC está habilitado y si los servidores DNS seleccionados lo admiten. Combina información sobre la configuración DNS a nivel de sistema y por enlace (ver abajo), y solo informa verdadero si DNSSEC está habilitado y es compatible en cada interfaz para la que está configurado DNS y para la configuración a nivel de sistema si existe alguna. Tenga en cuenta que systemd-resolved asume que los servidores DNS admiten DNSSEC hasta que verifica que este no es el caso. Por lo tanto, el valor informado puede ser verdadero inicialmente, hasta que se ejecuten las primeras transacciones.

La propiedad booleana DNSOverTLS informa si DNS-over-TLS está habilitado.

La propiedad ResolvConfMode expone cómo se gestiona /etc/resolv.conf en el host. Actualmente, los valores "uplink", "stub", "static" (estos tres corresponden a los tres archivos diferentes que proporciona systemd-resolved.service), "foreign" (el fi

de 'admin' u otro servicio, systemd-resolved.service solo lo consume), "missing" (/etc/resolv.conf falta).

La propiedad DNSStubListener informa si el oyente stub en el puerto 53 está habilitado. Los valores posibles son "yes" (habilitado), "no" (deshabilitado), "udp" (solo el oyente UDP está habilitado) y "tcp" (solo el oyente TCP está habilitado).

La propiedad DNSSECNegativeTrustAnchors contiene una lista de anclas de confianza negativas DNSSEC reconocidas y contiene una lista de dominios.

Para cada interfaz de red de Linux se crea un objeto "Link" que expone la configuración y el estado de DNS por enlace. Utilice GetLink() en la interfaz Manager para recuperar la ruta del objeto para un objeto de enlace dado el índice de la interfaz de red (ver arriba).

Métodos

Los diversos métodos expuestos por la interfaz Link son equivalentes a sus contrapartes con nombres similares en la interfaz Manager. Por ejemplo, SetDNS() en el objeto Link se corresponde con SetLinkDNS() en el objeto Manager, la principal diferencia es que este último espera que se especifique un índice de interfaz. Invocar los métodos en la interfaz Manager tiene el beneficio de reducir los viajes de ida y vuelta, ya que no es necesario solicitar primero la ruta del objeto Link a través de GetLink() antes de invocar los métodos. La misma relación se aplica a SetDNSEx(), SetDomains(), SetDefaultRoute(), SetLLMNR(), SetMulticastDNS(), SetDNSOverTLS(), SetDNSSEC(), SetDNSSECNegativeTrustAnchors(), y Revert(). Para más detalles sobre estos métodos, consulte la documentación del Manager anterior.

Propiedades

ScopesMask define qué ámbitos del resolvedor están actualmente activos en esta interfaz. Este campo entero sin signo de 64 bits es una máscara de bits que consiste en un subconjunto de los bits del parámetro flags descrito anteriormente. Específicamente, puede tener los bits DNS, LLMNR y MDNS (este último en sabores IPv4 e IPv6) establecidos. Cada bit individual se establece cuando el protocolo se aplica a una interfaz específica y está habilitado para ella. Se desactiva en caso contrario. Específicamente, una interfaz con capacidad multicast en el estado "UP" con una dirección IP es adecuada para LLMNR o MulticastDNS, y cualquier interfaz que esté UP y tenga una dirección IP es adecuada para DNS. Tenga en cuenta la relación de los bits expuestos aquí con las propiedades LLMNR y MulticastDNS también expuestas en la interfaz Link. Estas últimas exponen lo que está *configurado* para ser utilizado en la interfaz, las primeras exponen lo que se utiliza realmente en la interfaz, teniendo en cuenta las capacidades de la interfaz.

DNSSECSupported expone un campo booleano que indica si DNSSEC está actualmente configurado y en uso en la interfaz. Tenga en cuenta que si DNSSEC está habilitado en una interfaz, se asume que está disponible hasta que se detecte que el servidor configurado realmente no lo admite. Por lo tanto, esta propiedad puede inicialmente informar que DNSSEC es compatible con una interfaz.

DefaultRoute expone un campo booleano que indica si la interfaz se utilizará como ruta predeterminada para las consultas de nombre. Consulte SetLinkDefaultRoute() arriba.

Las otras propiedades reflejan el estado de la configuración de los diversos ajustes para el enlace, que pueden ser establecidos con varias llamadas a métodos como SetDNS() o SetLLMNR().

ERRORES COMUNES

Muchos métodos de bus que systemd-resolved expone (en particular los métodos del resolvedor como ResolveHostname() en la interfaz Manager) pueden devolver algunos de los siguientes errores:

org.freedesktop.resolve1.NoNameServers

No se encontraron servidores DNS adecuados para resolver una solicitud.

Añadido en la versión 246.

org.freedesktop.resolve1.InvalidReply

No se pudo entender una respuesta del servidor DNS seleccionado.

Añadido en la versión 246.

org.freedesktop.resolve1.NoSuchRR

El nombre solicitado existe, pero no hay un registro de recurso del tipo solicitado para él. (Este es el caso DNS NODATA).

Añadido en la versión 246.

org.freedesktop.resolve1.CNameLoop

La búsqueda falló porque se detectó un bucle CNAME o DNAME.

Añadido en la versión 246.

org.freedesktop.resolve1.Aborted

La búsqueda se abortó porque el protocolo seleccionado dejó de estar disponible mientras la operación estaba en curso.

Añadido en la versión 246.

org.freedesktop.resolve1.NoSuchService

Una búsqueda de servicio fue exitosa, pero el registro SRV informó que el servicio no está disponible.

Añadido en la versión 246.

org.freedesktop.resolve1.DnssecFailed

La respuesta adquirida no pasó la validación DNSSEC.

Añadido en la versión 246.

org.freedesktop.resolve1.NoTrustAnchor

No se pudo establecer una cadena de confianza para la respuesta a una ancla de confianza DNSSEC configurada.

Añadido en la versión 246.

org.freedesktop.resolve1.ResourceRecordTypeUnsupported

El tipo de registro de recurso solicitado no es compatible con los servidores DNS seleccionados. Este error se genera, por ejemplo, cuando se solicita un registro RRSIG a un servidor DNS que no admite DNSSEC.

Añadido en la versión 246.

org.freedesktop.resolve1.NoSuchLink

No existe una interfaz de red con el índice de interfaz de red especificado.

Añadido en la versión 246.

org.freedesktop.resolve1.LinkBusy

No se pudo realizar el cambio de configuración solicitado porque systemd-networkd(8), ya tomó posesión de la interfaz y suministró datos de configuración para ella.

Añadido en la versión 246.

org.freedesktop.resolve1.NetworkDown

La búsqueda solicitada falló porque el sistema no está actualmente conectado a ninguna red adecuada.

Añadido en la versión 246.

org.freedesktop.resolve1.DnsError.NXDOMAIN, org.freedesktop.resolve1.DnsError.REFUSED, ...

La búsqueda falló con un código de retorno DNS que informaba de un error. Los nombres de error utilizados como sufijos aquí están definidos por IANA en Códigos RCODE de DNS[4].

Añadido en la versión 246.
