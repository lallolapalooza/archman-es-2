NOMBRE

openssl-ca - aplicación de ejemplo mínima de CA

SINOPSIS

openssl ca [-help] [-verbose] [-quiet] [-config archivo] [-name sección] [-section sección] [-gencrl] [-revoke archivo] [-valid archivo] [-status serial] [-updatedb] [-crl_reason razón] [-crl_hold instrucción] [-crl_compromise hora] [-crl_CA_compromise hora] [-crl_lastupdate fecha] [-crl_nextupdate fecha] [-crldays días] [-crlhours horas] [-crlsec segundos] [-crlexts sección] [-startdate fecha] [-not_before fecha] [-enddate fecha] [-not_after fecha] [-days arg] [-md arg] [-policy arg] [-keyfile archivo|uri] [-keyform DER|PEM|P12|ENGINE] [-key arg] [-passin arg] [-cert archivo] [-certform DER|PEM|P12] [-selfsign] [-in archivo] [-inform DER|<PEM>] [-out archivo] [-notext] [-dateopt] [-outdir dir] [-infiles] [-spkac archivo] [-ss_cert archivo] [-preserveDN] [-noemailDN] [-batch] [-msie_hack] [-extensions sección] [-extfile sección] [-subj arg] [-utf8] [-sigopt nm:v] [-vfyopt nm:v] [-create_serial] [-rand_serial] [-multivalue-rdn] [-rand archivos] [-writerand archivo] [-engine id] [-provider nombre] [-provider-path ruta] [-provparam [nombre:]clave=valor] [-propquery propq] [certreq...]

DESCRIPCIÓN

Este comando emula una aplicación de CA. Ver las ADVERTENCIAS especialmente si considera usarlo de forma productiva.

Genera certificados que llevan la versión 3 de X.509. A menos que se especifique lo contrario, se incluyen extensiones de identificador de clave como se describe en x509v3_config(5).

Se puede utilizar para firmar solicitudes de certificados (CSR) en una variedad de formas y generar listas de revocación de certificados (CRL). También mantiene una base de datos de texto de los certificados emitidos y su estado. Al firmar certificados, se puede especificar una única solicitud con la opción -in, o se pueden procesar varias solicitudes especificando un conjunto de archivos certreq después de todas las opciones.

Tenga en cuenta que también hay formas muy eficientes de generar certificados: los comandos req y x509 se pueden usar para crear certificados directamente. Ver openssl-req(1) y openssl-x509(1) para detalles.

Las descripciones de las opciones del comando ca se dividen según cada propósito.

OPCIONES

-help
Imprime un mensaje de uso.
-verbose
Esto imprime detalles adicionales sobre las operaciones que se están realizando.
-quiet
Esto imprime menos detalles sobre las operaciones que se están realizando, lo que puede ser útil durante scripts por lotes o tuberías.
-config archivo
Especifica el archivo de configuración a utilizar. Opcional; para una descripción del valor predeterminado, ver "RESUMEN DEL COMANDO" en openssl(1).
-name sección, -section sección
Especifica la sección del archivo de configuración a utilizar (anula default_ca en la sección ca).
-in archivo
Un nombre de archivo de entrada que contiene una única solicitud de certificado (CSR) a ser firmada por la CA.
-inform DER|PEM
El formato a utilizar al cargar archivos de entrada de solicitud de certificado (CSR); por defecto, se prueba PEM primero. Ver openssl-format-options(1) para detalles.
-ss_cert archivo
Un único certificado autofirmado a ser firmado por la CA.
-spkac archivo
Un archivo que contiene una clave pública y desafío firmados por Netscape, además de valores de campos adicionales, a ser firmados por la CA. Ver la sección FORMATO SPKAC para obtener información sobre el formato de entrada y salida requerido.
-infiles
Si está presente, esta debe ser la última opción; todos los argumentos subsiguientes se toman como los nombres de los archivos que contienen solicitudes de certificado.
-out archivo
El archivo de salida para emitir los certificados. El valor predeterminado es la salida estándar. Los detalles del certificado también se imprimirán en este archivo en formato PEM (excepto que -spkac emite formato DER).
-outdir directorio
El directorio para emitir los certificados. El certificado se escribirá en un nombre de archivo que consiste en el número de serie en hexadecimal con .pem añadido.
-cert archivo
El certificado de la CA, que debe coincidir con -keyfile.
-certform DER|PEM|P12
El formato de los datos en los archivos de entrada del certificado; no especificado por defecto. Ver openssl-format-options(1) para detalles.
-keyfile archivo|uri
La clave privada de la CA para firmar solicitudes de certificado. Debe coincidir con -cert.
-keyform DER|PEM|P12|ENGINE
El formato del archivo de entrada de la clave privada; no especificado por defecto. Ver openssl-format-options(1) para detalles.
-sigopt nm:v
Pasa opciones al algoritmo de firma durante las operaciones de firma. Los nombres y valores de estas opciones son específicos del algoritmo y se documentan en "Parámetros de firma" en provider-signature(7).
-vfyopt nm:v
Pasa opciones al algoritmo de firma durante las operaciones de verificación. Los nombres y valores de estas opciones son específicos del algoritmo.

Esto a menudo necesita ser especificado al firmar también, porque la autofirma de una solicitud de certificado (CSR) se verifica contra la clave pública incluida, y esa verificación puede necesitar su propio conjunto de opciones.

-key contraseña
La contraseña utilizada para cifrar la clave privada. Dado que en algunos sistemas los argumentos de línea de comandos son visibles (por ejemplo, al usar ps(1) en Unix), esta opción debe usarse con precaución. Es mejor usar -passin.
-passin arg
La fuente de la contraseña de la clave para archivos de clave y archivos PKCS#12 de certificado. Para más información sobre el formato de arg ver openssl-passphrase-options(1).
-selfsign
Indica que los certificados emitidos deben ser firmados con la clave con la que se firmaron las solicitudes de certificado (proporcionada con -keyfile). Las solicitudes de certificado firmadas con una clave diferente se ignoran. Si se proporcionan -spkac, -ss_cert o -gencrl, se ignora -selfsign.

Una consecuencia de usar -selfsign es que el certificado autofirmado aparece entre las entradas de la base de datos de certificados (ver la opción de configuración database), y utiliza el mismo contador de números de serie que todos los demás certificados firmados con el certificado autofirmado.

-notext
No produzca la forma textual de un certificado en el archivo de salida.
-dateopt
Especifique el formato de salida de la fecha. Los valores son: rfc_822 e iso_8601. El valor predeterminado es rfc_822.
-startdate fecha, -not_before fecha
Esto permite establecer explícitamente la fecha de inicio. El formato de la fecha es YYMMDDHHMMSSZ (igual que una estructura ASN1 UTCTime), o YYYYMMDDHHMMSSZ (igual que una estructura ASN1 GeneralizedTime). En ambos formatos, los segundos SS y la zona horaria Z deben estar presentes. Alternativamente, también puede usar "today".
-enddate fecha, -not_after fecha
Esto permite establecer explícitamente la fecha de caducidad. El formato de la fecha es YYMMDDHHMMSSZ (igual que una estructura ASN1 UTCTime), o YYYYMMDDHHMMSSZ (igual que una estructura ASN1 GeneralizedTime). En ambos formatos, los segundos SS y la zona horaria Z deben estar presentes. Alternativamente, también puede usar "today".

Esto anula la opción -days.

-days arg
El número de días a partir de hoy para certificar el certificado.

Independientemente de la opción -not_before, los días se cuentan siempre a partir de hoy. Cuando se utiliza junto con la opción -not_after/-startdate, la fecha de caducidad explícita tiene precedencia.

-md alg
El resumen del mensaje a utilizar. Se puede utilizar cualquier resumen admitido por el comando openssl-dgst(1). Para algoritmos de firma que no admiten un resumen (es decir, Ed25519 y Ed448), se ignora cualquier resumen de mensaje establecido. Esta opción también se aplica a las CRL.
-policy arg
Esta opción define la "política" de la CA a utilizar. Esta es una sección en el archivo de configuración que decide qué campos deben ser obligatorios o coincidir con el certificado de la CA. Consulte la sección FORMATO DE LA POLÍTICA para obtener más información.
-msie_hack
Esta es una opción obsoleta para que este comando funcione con versiones muy antiguas del control de inscripción de certificados de IE "certenr3". Utilizaba UniversalStrings para casi todo. Dado que el control antiguo tiene varios errores de seguridad, su uso se desaconseja enérgicamente.
-preserveDN
Normalmente, el orden del DN de un certificado es el mismo que el orden de los campos en la sección de política relevante. Cuando se establece esta opción, el orden es el mismo que el de la solicitud. Esto es en gran medida para la compatibilidad con el control de inscripción de IE anterior, que solo aceptaba certificados si sus DN coincidían con el orden de la solicitud. Esto no es necesario para Xenroll.
-noemailDN
El DN de un certificado puede contener el campo EMAIL si está presente en el DN de la solicitud; sin embargo, es una buena política tener solo el correo electrónico establecido en la extensión altName del certificado. Cuando se establece esta opción, el campo EMAIL se elimina del sujeto del certificado y solo se establece en las extensiones (si las hay). La palabra clave email_in_dn se puede utilizar en el archivo de configuración para habilitar este comportamiento.
-batch
Esto establece el modo por lotes. En este modo, no se harán preguntas y todos los certificados se certificarán automáticamente.
-extensions sección
La sección del archivo de configuración que contiene las extensiones de certificado que se añadirán cuando se emita un certificado (por defecto x509_extensions a menos que se utilice la opción -extfile).

Consulte la página del manual x509v3_config(5) para obtener detalles sobre el formato de la sección de extensiones.

-extfile archivo
Un archivo de configuración adicional del que leer las extensiones de certificado (utilizando la sección predeterminada a menos que también se utilice la opción -extensions).
-subj arg
Sustituye el nombre del sujeto proporcionado en la solicitud.

El arg debe tener el formato "/tipo0=valor0/tipo1=valor1/tipo2=...". Los caracteres especiales pueden escaparse con "\" (barra invertida), los espacios en blanco se conservan. Los valores vacíos están permitidos, pero el tipo correspondiente no se incluirá en el certificado resultante. Proporcionar una sola "/" resultará en una secuencia vacía de RDN (un NULL-DN). Los RDN multivalor se pueden formar colocando un "+" en lugar de una "/" entre las Asersiones de Valor de Atributo (AVA) que especifican los miembros del conjunto. Ejemplo:

"/DC=org/DC=OpenSSL/DC=users/UID=123456+CN=John Doe"

-utf8
Esta opción hace que los valores de los campos se interpreten como cadenas UTF8; por defecto, se interpretan como ASCII. Esto significa que los valores de los campos, ya sea que se soliciten desde una terminal o se obtengan de un archivo de configuración, deben ser cadenas UTF8 válidas.
-create_serial
Si la lectura de números de serie desde el archivo de texto especificado en la configuración falla, especificar esta opción crea un nuevo número de serie aleatorio para ser utilizado como el próximo número de serie. Para obtener números de serie aleatorios, utilice la opción -rand_serial; esto solo debe usarse para una recuperación de errores simple.
-rand_serial
Genere un número aleatorio grande para usarlo como número de serie. Esto anula cualquier opción o configuración para usar un archivo de número de serie.
-multivalue-rdn
Esta opción ha sido obsoleta y no tiene ningún efecto.
-rand archivos, -writerand archivo
Consulte "Opciones de Estado Aleatorio" en openssl(1) para obtener detalles.
-engine id
Consulte "Opciones de Motor" en openssl(1). Esta opción está obsoleta.
-provider nombre
-provider-path ruta
-provparam [nombre:]clave=valor
-propquery propq
Consulte "Opciones del Proveedor" en openssl(1), provider(7) y property(7).

OPCIONES DE CRL

-gencrl
Esta opción genera una CRL basándose en la información del archivo índice.
-crl_lastupdate tiempo
Permite establecer explícitamente el valor del campo lastUpdate de la CRL; si no está presente esta opción, se utiliza la hora actual. Acepta tiempos en formato YYMMDDHHMMSSZ (igual que una estructura ASN1 UTCTime) o formato YYYYMMDDHHMMSSZ (igual que una estructura ASN1 GeneralizedTime structure).
-crl_nextupdate tiempo
Permite establecer explícitamente el valor del campo nextUpdate de la CRL; si está presente esta opción, se ignoran los valores proporcionados para -crldays, -crlhours y -crlsec. Acepta tiempos en los mismos formatos que -crl_lastupdate.
-crldays num
El número de días antes de que venza la próxima CRL. Es decir, los días desde ahora que se incluirán en el campo nextUpdate de la CRL.
-crlhours num
El número de horas antes de que venza la próxima CRL.
-crlsec num
El número de segundos antes de que venza la próxima CRL.
-revoke nombre_archivo
Un nombre de archivo que contiene un certificado a revocar.
-valid nombre_archivo
Un nombre de archivo que contiene un certificado para añadir una entrada de certificado válido.
-status serie
Muestra el estado de revocación del certificado con el número de serie especificado y sale.
-updatedb
Actualiza el índice de la base de datos para purgar los certificados caducados.
-crl_reason razon
Razón de la revocación, donde razón es una de: unspecified, keyCompromise, CACompromise, affiliationChanged, superseded, cessationOfOperation, certificateHold o removeFromCRL. La coincidencia de razón no distingue entre mayúsculas y minúsculas. Establecer cualquier razón de revocación hará que la CRL sea v2.

En la práctica, removeFromCRL no es particularmente útil ya que solo se utiliza en CRL delta, que actualmente no están implementadas.

-crl_hold instruccion
Esto establece el código de razón de revocación de la CRL en certificateHold y la instrucción de retención en instruccion, que debe ser un OID. Aunque se puede utilizar cualquier OID, normalmente solo se utilizarán holdInstructionNone (cuyo uso está obsoleto en RFC 5280), holdInstructionCallIssuer o holdInstructionReject.
-crl_compromise tiempo
Esto establece la razón de revocación en keyCompromise y el tiempo de compromiso en tiempo. tiempo debe estar en formato GeneralizedTime, es decir, AAAA MM DD HH MM SS Z.
-crl_CA_compromise

OPCIONES

-crl_compromise
Esto es lo mismo que crl_compromise excepto que la razón de revocación se establece en CACompromise.
-crlexts sección
La sección del archivo de configuración que contiene las extensiones CRL a incluir. Si no hay una sección de extensiones CRL presente, se crea una CRL V1. Si la sección de extensiones CRL está presente (incluso si está vacía), se crea una CRL V2. Las extensiones CRL especificadas son extensiones CRL y no extensiones de entrada CRL. Cabe señalar que algunos programas (por ejemplo, Netscape) no pueden manejar CRLs V2. Ver la página del manual x509v3_config(5) para obtener detalles sobre el formato de la sección de extensiones.

OPCIONES DEL ARCHIVO DE CONFIGURACIÓN

La sección del archivo de configuración que contiene las opciones para este comando se encuentra de la siguiente manera: Si se utiliza la opción de línea de comandos -name, entonces nombra la sección a utilizar. De lo contrario, la sección a utilizar debe ser nombrada en la opción default_ca de la sección ca del archivo de configuración (o en la sección predeterminada del archivo de configuración). Además de default_ca, las siguientes opciones se leen directamente de la sección ca:
RANDFILE
preserve
msie_hack Con la excepción de RANDFILE, esto es probablemente un error y puede cambiar en futuras versiones.

Muchas de las opciones del archivo de configuración son idénticas a las opciones de la línea de comandos. Cuando la opción está presente en el archivo de configuración y en la línea de comandos, se utiliza el valor de la línea de comandos. Cuando una opción se describe como obligatoria, debe estar presente en el archivo de configuración o se debe utilizar el equivalente en la línea de comandos (si existe).

oid_file
Esto especifica un archivo que contiene IDENTIFICADORES DE OBJETO adicionales. Cada línea del archivo debe consistir en la forma numérica del identificador de objeto seguido de un espacio en blanco, luego el nombre corto seguido de un espacio en blanco y finalmente el nombre largo.
oid_section
Esto especifica una sección en el archivo de configuración que contiene identificadores de objeto adicionales. Cada línea debe consistir en el nombre corto del identificador de objeto seguido de = y la forma numérica. Los nombres cortos y largos son los mismos cuando se utiliza esta opción.
new_certs_dir
Lo mismo que la opción de línea de comandos -outdir. Especifica el directorio donde se colocarán los nuevos certificados. Obligatorio.
certificate
Lo mismo que -cert. Proporciona el archivo que contiene el certificado de la CA. Obligatorio.
private_key
Igual que la opción -keyfile. El archivo que contiene la clave privada de la CA. Obligatorio.
RANDFILE
Al inicio, el archivo especificado se carga en el generador de números aleatorios y, al salir, se escribirán 256 bytes en él. (Nota: Ya no es necesario usar un RANDFILE, ver la sección "HISTORIA").
default_days
Lo mismo que la opción -days. El número de días a partir de hoy para certificar un certificado.
default_startdate
Lo mismo que la opción -startdate. La fecha de inicio para certificar un certificado. Si no se establece, se utiliza la hora actual.
default_enddate
Lo mismo que la opción -enddate. Debe estar presente alguna de estas opciones o default_days (o sus equivalentes en la línea de comandos).
default_crl_hours default_crl_days
Lo mismo que las opciones -crlhours y -crldays. Estas solo se utilizarán si ninguna opción de la línea de comandos está presente. Debe estar presente al menos una de estas opciones para generar una CRL.
default_md
Lo mismo que la opción -md. Obligatorio, excepto donde el algoritmo de firma no requiere un resumen (es decir, Ed25519 y Ed448).
database
El archivo de base de datos de texto a utilizar. Obligatorio. Este archivo debe estar presente, aunque inicialmente estará vacío.
unique_subject
Si se da el valor yes, las entradas de certificados válidos en la base de datos deben tener sujetos únicos. Si se da el valor no, varias entradas de certificados válidos pueden tener el mismo sujeto exacto. El valor predeterminado es yes, para ser compatible con versiones anteriores (anteriores a 0.9.8) de OpenSSL. Sin embargo, para facilitar el cambio de certificado de la CA, se recomienda usar el valor no, especialmente si se combina con la opción de línea de comandos -selfsign.

Tenga en cuenta que es válido en algunas circunstancias crear certificados sin ningún sujeto. En el caso de que haya varios certificados sin sujetos, esto no cuenta como un duplicado.

serial
Un archivo de texto que contiene el próximo número de serie a utilizar en formato hexadecimal. Obligatorio. Este archivo debe estar presente y contener un número de serie válido.
crlnumber
Un archivo de texto que contiene el próximo número de CRL a utilizar en formato hexadecimal. El número de CRL se insertará en las CRL solo si este archivo existe. Si este archivo está presente, debe contener un número de CRL válido.
x509_extensions
Una opción de reserva para la opción -extensions.
crl_extensions
Una opción de reserva para la opción -crlexts.
preserve
Lo mismo que -preserveDN
email_in_dn
Lo mismo que -noemailDN. Si desea que el campo EMAIL se elimine del DN del certificado, simplemente establézcalo en 'no'. Si no está presente, el valor predeterminado es permitir el campo EMAIL en el DN del certificado.
msie_hack
Lo mismo que -msie_hack
policy
Lo mismo que -policy. Obligatorio. Ver la sección FORMATO DE POLÍTICA para más información.
name_opt, cert_opt
Estas opciones permiten el formato utilizado para mostrar los detalles del certificado al solicitar al usuario que confirme la firma. Todas las opciones soportadas por los modificadores -nameopt y -certopt de las utilidades x509 se pueden usar aquí, excepto que no_signame y no_sigdump se establecen permanentemente y no se pueden deshabilitar (esto se debe a que la firma del certificado no se puede mostrar ya que el certificado no ha sido firmado en este punto).

Para mayor comodidad, ambos aceptan el valor ca_default para producir una salida razonable.

Si ninguna de las opciones está presente, se utiliza el formato de versiones anteriores de OpenSSL. El uso del formato antiguo está fuertemente desaconsejado porque solo muestra los campos mencionados en la sección policy, maneja mal los tipos de cadena multicarácter y no muestra las extensiones.

copy_extensions
Determina cómo se deben manejar las extensiones en las solicitudes de certificado. Si se establece en none o esta opción no está presente, las extensiones se ignoran y no se copian al certificado. Si se establece en copy, se copian al certificado cualquier extensión presente en la solicitud que aún no esté presente. Si se establece en copyall, se copian todas las extensiones de la solicitud al certificado: si la extensión ya está presente en el certificado, se elimina primero. Consulte la sección ADVERTENCIAS antes de usar esta opción.

El uso principal de esta opción es permitir que una solicitud de certificado proporcione valores para ciertas extensiones, como subjectAltName.

FORMATO DE POLÍTICA

La sección de políticas consiste en un conjunto de variables que corresponden a los campos DN del certificado. Si el valor es "match", el valor del campo debe coincidir con el mismo campo en el certificado de la CA. Si el valor es "supplied", debe estar presente. Si el valor es "optional", puede estar presente. Cualquier campo no mencionado en la sección de políticas se elimina silenciosamente, a menos que se establezca la opción -preserveDN, pero esto puede considerarse más una peculiaridad que un comportamiento intencional.

FORMATO SPKAC

La entrada para la opción de línea de comandos -spkac es una clave pública y un desafío firmados por Netscape. Esto generalmente provendrá de la etiqueta KEYGEN en un formulario HTML para crear una nueva clave privada. Sin embargo, es posible crear SPKACs usando openssl-spkac(1).

El archivo debe contener la variable SPKAC establecida en el valor del SPKAC y también los componentes DN requeridos como pares nombre-valor. Si necesita incluir el mismo componente dos veces, puede ir precedido por un número y un punto.

Al procesar el formato SPKAC, la salida es DER si se usa la bandera -out, pero en formato PEM si se envía a stdout o se usa la bandera -outdir.

EJEMPLOS

Nota: estos ejemplos asumen que la estructura de directorios que este comando asume ya está configurada y los archivos relevantes ya existen. Esto generalmente implica crear un certificado de CA y una clave privada con openssl-req(1), un archivo de número de serie y un archivo de índice vacío, y colocarlos en los directorios relevantes.

Para usar el archivo de configuración de ejemplo a continuación, se crearían los directorios demoCA, demoCA/private y demoCA/newcerts. El certificado de la CA se copiaría a demoCA/cacert.pem y su clave privada a demoCA/private/cakey.pem. Se crearía un archivo demoCA/serial que contuviera, por ejemplo, "01" y el archivo de índice vacío demoCA/index.txt.

DESCRIPCIÓN

The ca command is a generic utility for managing a CA (Certification Authority). It can be used to issue and revoke certificates, and to create and update CRLs (Certificate Revocation Lists).

The functionality of ca is largely controlled by a configuration file. A default configuration file openssl.cnf is used, and specific CA settings are contained within sections specified by the -config option or environment variables.

The behaviour of the ca command is determined by the settings in the configuration file, which are read using the config(5) library. The [ ca ] section specifies the default CA section to use, or a list of CA sections to use.

OPCIONES

The ca command supports a wide range of options that control its behavior. Some of the most important options include:

-config file
Use the specified configuration file. If not specified, the default openssl.cnf is used.
-in file
The input certificate request file.
-out file
The output certificate file.
-cert file
The CA certificate file.
-keyfile file
The CA private key file.
-days arg
The number of days the certificate will be valid.
-md arg
The message digest algorithm to use for signing.
-policy arg
The policy to use for certificate validation.
-extensions section
Use the specified extensions section from the configuration file.
-spkac file
Certify a Netscape SPKAC request.
-infiles file:file...
Process multiple certificate requests.
-gencrl
Generate a CRL.
-revoke file
Revoke a certificate.
-new
Generate a new certificate.
-x509
Output a self-signed certificate instead of a certificate request.
-section name
Use the specified section from the configuration file for CA settings.

CRL OPTIONS

The following options are used for generating and updating CRLs:

-crl_days arg
The number of days until the next CRL is issued.
-crl_hours arg
The number of hours until the next CRL is issued.
-crl_sec arg
The number of seconds until the next CRL is issued.
-crl_firstupdate arg
The time for the first update of the CRL.
-crl_nextupdate arg
The time for the next update of the CRL.

CONFIGURATION FILE OPTIONS

The following options relate to the configuration file:

policy_any
This policy allows any value for any field, except for the country name, common name and email address, which must be supplied.
policy_match
This policy requires that all fields in the certificate request must match the corresponding fields in the CA certificate's subject name.
copy_extensions
Controls how extensions from the request are handled. Can be none, copy, or copyall.

POLICY FORMAT

A policy section in the configuration file defines the requirements for certificate subject names. Each field is specified with a level of allowance: supplied, optional, or ignore.

SPKAC FORMAT

An SPKAC (Simple Public Key Certificate) is a text-based format for exchanging public keys and certificate signing requests. It typically contains a Base64 encoded SubjectPublicKeyInfo structure and a distinguished name.

EJEMPLOS

Sign a certificate request:

openssl ca -in req.pem -out newcert.pem

Sign an SM2 certificate request:

openssl ca -in sm2.csr -out sm2.crt -md sm3 \
        -sigopt "distid:1234567812345678" \
        -vfyopt "distid:1234567812345678"

Sign a certificate request, using CA extensions:

openssl ca -in req.pem -extensions v3_ca -out newcert.pem

Generate a CRL

openssl ca -gencrl -out crl.pem

Sign several requests:

openssl ca -infiles req1.pem req2.pem req3.pem

Certify a Netscape SPKAC:

openssl ca -spkac spkac.txt

A sample SPKAC file (the SPKAC line has been truncated for clarity):

SPKAC=MIG0MGAwXDANBgkqhkiG9w0BAQEFAANLADBIAkEAn7PDhCeV/xIxUg8V70YRxK2A5
CN=Steve Test
emailAddress=steve@openssl.org
0.OU=OpenSSL Group
1.OU=Another Group

A sample configuration file with the relevant sections for this command:

[ ca ]
default_ca      = CA_default            # The default ca section
[ CA_default ]
dir            = ./demoCA              # top dir
database       = $dir/index.txt        # index file.
new_certs_dir  = $dir/newcerts         # new certs dir
certificate    = $dir/cacert.pem       # The CA cert
serial         = $dir/serial           # serial no file
#rand_serial    = yes                  # for random serial#'s
private_key    = $dir/private/cakey.pem# CA private key
default_days   = 365                   # how long to certify for
default_crl_days= 30                   # how long before next CRL
default_md     = sha256                # md to use
policy         = policy_any            # default policy
email_in_dn    = no                    # Don't add the email into cert DN
name_opt       = ca_default            # Subject name display option
cert_opt       = ca_default            # Certificate display option
copy_extensions = none                 # Don't copy extensions from request
[ policy_any ]
countryName            = supplied
stateOrProvinceName    = optional
organizationName       = optional
organizationalUnitName = optional
commonName             = supplied
emailAddress           = optional

RESTRICCIONES

The text database index file is a critical part of the process and if corrupted it can be difficult to fix. It is theoretically possible to rebuild the index file from all the issued certificates and a current CRL: however there is no option to do this.

V2 CRL features like delta CRLs are not currently supported.

Although several requests can be input and handled at once it is only possible to include one SPKAC or self-signed certificate.

BUGS

This command is quirky and at times downright unfriendly.

The use of an in-memory text database can cause problems when large numbers of certificates are present because, as the name implies the database has to be kept in memory.

This command really needs rewriting or the required functionality exposed at either a command or interface level so that a more user-friendly replacement could handle things properly. The script CA.pl helps a little but not very much.

Any fields in a request that are not present in a policy are silently deleted. This does not happen if the -preserveDN option is used. To enforce the absence of the EMAIL field within the DN, as suggested by RFCs, regardless the contents of the request' subject the -noemailDN option can be used. The behaviour should be more friendly and configurable.

Canceling some commands by refusing to certify a certificate can create an empty file.

ADVERTENCIAS

This command was originally meant as an example of how to do things in a CA. Its code does not have production quality. It was not supposed to be used as a full blown CA itself, nevertheless some people are using it for this purpose at least internally. When doing so, specific care should be taken to properly secure the private key(s) used for signing certificates. It is advisable to keep them in a secure HW storage such as a smart card or HSM and access them via a suitable engine or crypto provider.

This command is effectively a single user command: no locking is done on the various files and attempts to run more than one openssl ca command on the same database can have unpredictable results.

The copy_extensions option should be used with caution. If care is not taken then it can be a security risk. For example if a certificate request contains a basicConstraints extension with CA:TRUE and the copy_extensions value is set to copyall and the user does not spot this when the certificate is displayed then this will hand the requester a valid CA certificate. This situation can be avoided by setting copy_extensions to copy and including basicConstraints with CA:FALSE in the configuration file. Then if the request contains a basicConstraints extension it will be ignored.

It is advisable to also include values for other extensions such as keyUsage to prevent a request supplying its own values.

Additional restrictions can be placed on the CA certificate itself. For example if the CA certificate has:

basicConstraints = CA:TRUE, pathlen:0

then even if a certificate is issued with CA:TRUE it will not be valid.

HISTORIA

Since OpenSSL 1.1.1, the program follows RFC5280. Specifically, certificate validity period (specified by any of -startdate, -enddate and -days) and CRL last/next update time (specified by any of -crl_lastupdate, -crl_nextupdate, -crldays, -crlhours and -crlsec) will be encoded as UTCTime if the dates are earlier than year 2049 (included), and as GeneralizedTime if the dates are in year 2050 or later.

OpenSSL 1.1.1 introduced a new random generator (CSPRNG) with an improved seeding mechanism. The new seeding mechanism makes it unnecessary to define a RANDFILE for saving and restoring randomness. This option is retained mainly for compatibility reasons.

The -section option was added in OpenSSL 3.0.0.

The -multivalue-rdn option has become obsolete in OpenSSL 3.0.0 and has no effect.

The -engine option was deprecated in OpenSSL 3.0.

Since OpenSSL 3.2, generated certificates bear X.509 version 3, and key identifier extensions are included by default.
