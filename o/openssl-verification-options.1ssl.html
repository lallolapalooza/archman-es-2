NOMBRE

openssl-verification-options - opciones genéricas de verificación de certificados X.509

SINOPSIS

openssl comando [ opciones ... ] [ parámetros ... ]

DESCRIPCIÓN

Hay muchas situaciones en las que se verifican certificados X.509 dentro de las bibliotecas OpenSSL y en varios comandos de OpenSSL.

La verificación de certificados se implementa mediante X509_verify_cert(3). Es un proceso complicado que consta de una serie de pasos y depende de numerosas opciones. Las más importantes se detallan en las siguientes secciones.

En resumen, se debe construir y verificar una cadena válida de certificados comenzando desde el certificado objetivo que se va a verificar y terminando en un certificado que, por alguna política, es de confianza. La validación de certificados se puede realizar en el contexto de un propósito, que es una especificación de alto nivel del uso previsto del certificado objetivo, como "sslserver" para servidores TLS, o (por defecto) para cualquier propósito.

Los detalles de cómo cada comando de OpenSSL maneja los errores se documentan en la página específica del comando.

El soporte DANE se documenta en openssl-s_client(1), SSL_CTX_dane_enable(3), SSL_set1_host(3), X509_VERIFY_PARAM_set_flags(3), y X509_check_host(3).

Anclas de confianza

En general, de acuerdo con RFC 4158 y RFC 5280, un ancla de confianza es cualquier clave pública y nombre distinguido (DN) de sujeto relacionado que por alguna razón se considera confiable y, por lo tanto, es aceptable como raíz de una cadena de certificados.

En la práctica, las anclas de confianza se proporcionan en forma de certificados, donde sus campos esenciales son la clave pública y el DN del sujeto. Además de los requisitos de RFC 5280, OpenSSL verifica el período de validez de dichos certificados y utiliza algunos campos adicionales. En particular, la extensión del identificador de clave del sujeto, si está presente, se utiliza para hacer coincidir las anclas de confianza durante la construcción de la cadena.

En el caso más simple y común, las anclas de confianza son por defecto todos los certificados de CA "raíz" autofirmados que se colocan en el almacén de confianza, que es una colección de certificados en los que se confía para ciertos usos. Esto es similar a lo que se utiliza en los almacenes de confianza de Mozilla Firefox, o en los almacenes de certificados de Apple y Microsoft, ...

Desde la perspectiva de OpenSSL, un ancla de confianza es un certificado que debe complementarse con una designación explícita de para qué usos del certificado objetivo puede servir el certificado como ancla de confianza. En codificación PEM, esto se indica con la cadena "TRUSTED CERTIFICATE". Dicha designación proporciona un conjunto de atributos de confianza positivos que declaran explícitamente confianza para los propósitos enumerados y/o un conjunto de atributos de confianza negativos que rechazan explícitamente el uso para los propósitos enumerados. Los propósitos se codifican utilizando los valores definidos para los usos extendidos de clave (EKU) que pueden proporcionarse en extensiones X.509 de certificados de entidad final. Consulte también la sección "Uso extendido de clave" a continuación.

Los usos reconocidos actualmente son clientAuth (uso de cliente SSL), serverAuth (uso de servidor SSL), emailProtection (uso de correo S/MIME), codeSigning (uso de firmante de objeto), OCSPSigning (uso de respondedor OCSP), OCSP (uso de solicitud OCSP), timeStamping (uso de servidor TSA) y anyExtendedKeyUsage. A partir de OpenSSL 1.1.0, el último de estos bloquea todos los usos cuando se rechaza o habilita todos los usos cuando se confía.

Un certificado, que puede ser un certificado de CA o un certificado de entidad final, se considera un ancla de confianza para el uso dado si y solo si se cumplen todas las siguientes condiciones:

  • Es un elemento del almacén de confianza.
  • No tiene un atributo de confianza negativo que rechace el uso dado.
  • Tiene un atributo de confianza positivo que acepta el uso dado o (por defecto) se aplican una de las siguientes condiciones de compatibilidad: Es autofirmado o se proporciona la opción -partial_chain (que corresponde al establecimiento del flag X509_V_FLAG_PARTIAL_CHAIN).

Construcción de la ruta de certificación

Primero, se construye una cadena de certificados comenzando desde el certificado objetivo y terminando en un ancla de confianza.

La cadena se construye iterativamente, buscando sucesivamente un certificado con uso de clave adecuado que coincida como emisor del "sujeto" actual del certificado, como se describe a continuación. Si existe tal certificado, se toma el primero encontrado que sea válido actualmente, de lo contrario, se toma el que expiró más recientemente de todos esos certificados. Por eficiencia, no se realiza retroceso, por lo que se ignoran los certificados emisores candidatos adicionales que coincidirían de manera similar.

Cuando se agrega un certificado autofirmado, la construcción de la cadena se detiene. En este caso, debe coincidir completamente con un ancla de confianza, de lo contrario, la construcción de la cadena falla.

Un certificado emisor candidato coincide con un certificado sujeto si se cumplen todas las siguientes condiciones:

  • Su nombre de sujeto coincide con el nombre del emisor del certificado sujeto.
  • Si el certificado sujeto tiene una extensión de identificador de clave de autoridad, cada uno de sus subcampos es igual al identificador de clave de sujeto correspondiente, número de serie y campo del emisor del certificado emisor candidato, en la medida en que los campos respectivos estén presentes en ambos certificados.
  • El algoritmo de firma del certificado utilizado para firmar el certificado sujeto es compatible y coincide con el algoritmo de clave pública del certificado emisor candidato.

La búsqueda primero busca certificados emisores en el almacén de confianza. Si no encuentra una coincidencia allí, consulta la lista de certificados de CA intermedios ("no confiables"), si se proporcionan.

Validación de la ruta de certificación

Cuando el proceso de construcción de la cadena de certificados fue exitoso, los componentes de la cadena y sus enlaces se verifican exhaustivamente.

El primer paso es verificar que cada certificado esté bien formado. Parte de estas verificaciones solo se habilitan si se proporciona la opción -x509_strict.

El segundo paso es verificar las extensiones X.509v3 de cada certificado para su consistencia con el propósito específico previsto, si lo hubiera. Si no se proporciona la opción -purpose, no se realizan dichas verificaciones, excepto para la verificación de firmas CMS, donde por defecto se verifica "smimesign", y para la configuración de conexiones SSL/(D)TLS, donde por defecto se verifica "sslserver" o "sslclient". Las extensiones X.509v3 del certificado objetivo o "hoja" deben ser compatibles con el propósito especificado. Todos los demás certificados en la cadena se verifican para que sean certificados de CA válidos y, posiblemente, también se realizan verificaciones adicionales no estándar. Las extensiones precisas requeridas se describen en detalle en la sección "Extensiones de Certificados" a continuación.

El tercer paso es verificar la configuración de confianza en el último certificado (que típicamente es un certificado de CA raíz autofirmado). Debe ser de confianza para el uso dado. Para compatibilidad con versiones anteriores de OpenSSL, un certificado autofirmado sin atributos de confianza se considera válido para todos los usos.

El cuarto y último paso es verificar la validez de la cadena de certificados. Para cada elemento de la cadena, incluido el certificado de CA raíz, se verifica el período de validez especificado por los campos "notBefore" y "notAfter" con la hora actual del sistema. La bandera -attime puede usarse para utilizar una hora de referencia distinta de "ahora". También se verifica la firma del certificado (excepto la firma del certificado de CA raíz típicamente autofirmado, que solo se verifica si se proporciona la opción -check_ss_sig). Al verificar la firma de un certificado, se verifica la extensión keyUsage (si está presente) del certificado emisor candidato para permitir digitalSignature para firmar certificados proxy o keyCertSign para firmar otros certificados, respectivamente. OPCIONES

Opciones de Certificado de Confianza

Las siguientes opciones especifican cómo proporcionar los certificados que pueden usarse como anclas de confianza para ciertos usos. Como se mencionó, una colección de dichos certificados se llama un almacén de confianza.

Tenga en cuenta que OpenSSL no proporciona un conjunto predeterminado de anclas de confianza. Muchas distribuciones de Linux incluyen un valor predeterminado del sistema y configuran OpenSSL para apuntar a él. Mozilla mantiene un almacén de confianza influyente que se puede encontrar en https://www.mozilla.org/en-US/about/governance/policies/security-group/certs/.

Los certificados que se añadirán al almacén de confianza se pueden especificar utilizando las siguientes opciones.

-CAfile archivo
Carga el archivo especificado que contiene un certificado de confianza en formato DER o potencialmente varios de ellos en caso de que la entrada esté en formato PEM. Los certificados codificados en PEM también pueden tener atributos de confianza establecidos.
-no-CAfile
No carga el archivo predeterminado de certificados de confianza.
-CApath directorio
Utiliza el directorio especificado como una colección de certificados de confianza, es decir, un almacén de confianza. Los archivos deben nombrarse con el valor hash del Nombre del Sujeto X.509 de cada certificado. Esto es para que la biblioteca pueda extraer el Nombre del Emisor, hashearlo y buscar directamente el archivo para obtener el certificado del emisor. Consulte openssl-rehash(1) para obtener información sobre cómo crear este tipo de directorio.
-no-CApath
No utiliza el directorio predeterminado de certificados de confianza.
-CAstore uri
Utiliza uri como un almacén de certificados CA. La URI puede indicar un certificado único, así como una colección de ellos. Con URIs en el esquema "file:", esto actúa como -CAfile o -CApath, dependiendo de si la URI indica un archivo único o un directorio. Consulte ossl_store-file(7) para obtener más información sobre el esquema "file:".

Estos certificados también se utilizan al construir la cadena de certificados del servidor (por ejemplo, con openssl-s_server(1)) o la cadena de certificados del cliente (por ejemplo, con openssl-s_time(1)).

-no-CAstore
No utiliza el almacén predeterminado de certificados CA de confianza.

Opciones de Verificación

La verificación del certificado se puede ajustar con las siguientes banderas.

-verbose
Imprime información adicional sobre las operaciones que se están realizando.
-attime marca_de_tiempo
Realiza las comprobaciones de validación utilizando la hora especificada por marca_de_tiempo y no la hora actual del sistema. marca_de_tiempo es el número de segundos transcurridos desde el 1 de enero de 1970 (es decir, la Época Unix).
-no_check_time
Esta opción suprime la comprobación del período de validez de los certificados y CRLs con respecto a la hora actual. Si se utiliza la opción -attime para especificar una hora de verificación, la comprobación no se suprime.
-x509_strict
Esto deshabilita las soluciones alternativas no conformes para certificados rotos. Por lo tanto, se lanzan errores en certificados que no cumplen con RFC 5280.

Cuando se establece esta opción, entre otras, se comprueban las siguientes condiciones de corrección de certificados:

  • Los basicConstraints de los certificados CA deben estar marcados como críticos.
  • Los certificados CA deben incluir explícitamente la extensión keyUsage.
  • Si se proporciona un pathlenConstraint, el keyCertSign de keyUsage debe estar permitido.
  • El pathlenConstraint no debe proporcionarse para certificados no CA.
  • El nombre del emisor de cualquier certificado no debe estar vacío.
  • Los nombres de sujeto de los certificados CA, los certificados con crlSign de keyUsage y los certificados sin subjectAlternativeName no deben estar vacíos.
  • Si se proporciona una extensión subjectAlternativeName, no debe estar vacía.
  • El campo signatureAlgorithm y la firma del certificado deben ser consistentes.
  • Cualquier authorityKeyIdentifier y subjectKeyIdentifier proporcionado no debe estar marcado como crítico.
  • El authorityKeyIdentifier debe proporcionarse para los certificados X.509v3, a menos que sean auto-firmados.
  • El subjectKeyIdentifier debe proporcionarse para todos los certificados CA X.509v3.
-ignore_critical
Normalmente, si está presente una extensión crítica no manejada que no es compatible con OpenSSL, el certificado es rechazado (como lo requiere RFC5280). Si se establece esta opción, las extensiones críticas se ignoran.
-issuer_checks
Ignorado.
-crl_check
Comprueba la validez del certificado de la entidad final intentando buscar una CRL válida. Si no se encuentra una CRL válida, se produce un error.
-crl_check_all
Comprueba la validez de todos los certificados de la cadena intentando buscar CRLs válidas.
-use_deltas
Habilita el soporte para CRLs delta.
-extended_crl
Habilita características de CRL extendidas como CRLs indirectas y claves de firma de CRL alternativas.
-suiteB_128_only, -suiteB_128, -suiteB_192
Habilita la operación en modo Suite B con un nivel de seguridad de 128 bits, 128 bits o 192 bits, o solo 192 bits respectivamente. Consulte RFC6460 para obtener detalles. En particular, los algoritmos de firma admitidos se reducen para admitir solo ECDSA y SHA256 o SHA384 y solo las curvas elípticas P-256 y P-384.
-auth_level nivel
Establece el nivel de seguridad de autenticación de la cadena de certificados a nivel. El nivel de seguridad de autenticación determina la fortaleza de la firma y la clave pública aceptable al verificar cadenas de certificados. Para que una cadena de certificados sea válida, las claves públicas de todos los certificados deben cumplir el nivel de seguridad especificado. El nivel de seguridad de la firma se aplica a todos los certificados de la cadena, excepto al ancla de confianza de la cadena, que es directamente de confianza o validada por medios distintos a su firma. Consulte SSL_CTX_set_security_level(3) para las definiciones de los niveles disponibles. El nivel de seguridad predeterminado es -1, o "no establecido". En el nivel de seguridad 0 o inferior, todos los algoritmos son aceptables. El nivel de seguridad 1 requiere una seguridad equivalente a al menos 80 bits y es ampliamente interoperable, aunque, por ejemplo, rechazará firmas MD5 o claves RSA de menos de 1024 bits.
-partial_chain
Permite que la verificación tenga éxito si se puede construir una cadena incompleta. Es decir, una cadena que termina en un certificado que normalmente no sería de confianza (porque no tiene atributos de confianza positivos coincidentes y no es auto-firmado) pero que es un elemento del almacén de confianza. Este certificado puede ser auto-emitido o pertenecer a una CA intermedia.
-check_ss_sig
Verifica la firma del último certificado de una cadena si se supone que el certificado es auto-firmado. Esto está prohibido y resultará en un error si es un certificado CA no conforme con restricciones de uso de clave que no incluyen el bit keyCertSign. Esta verificación está deshabilitada por defecto porque no añade ninguna seguridad.
-allow_proxy_certs
Permite la verificación de certificados proxy.
-trusted_first
A partir de OpenSSL 1.1.0, esta opción está activada por defecto y no se puede deshabilitar.

Al construir la cadena de certificados, los certificados de confianza especificados a través de -CAfile, -CApath, -CAstore o -trusted siempre se utilizan antes que cualquier certificado especificado a través de -untrusted.

-no_alt_chains
A partir de OpenSSL 1.1.0, como -trusted_first está siempre activado, esta opción no tiene efecto.
-trusted archivo
Analiza archivo como un conjunto de uno o más certificados. Cada uno de ellos califica como de confianza si tiene un atributo de confianza positivo adecuado o si es auto-firmado o si se especifica la opción -partial_chain. Esta opción implica las opciones -no-CAfile, -no-CApath y -no-CAstore y no se puede utilizar con las opciones -CAfile, -CApath o -CAstore, por lo que solo los certificados especificados mediante la opción -trusted son anclas de confianza. Esta opción se puede utilizar varias veces.
-untrusted archivo
Analiza archivo como un conjunto de uno o más certificados. Todos los certificados (típicamente de CAs intermedias) se consideran no confiables y pueden utilizarse para construir una cadena de certificados desde el certificado de destino hasta un ancla de confianza. Esta opción puede utilizarse varias veces.
-policy arg
Habilita el procesamiento de políticas y añade arg al conjunto de políticas iniciales del usuario (ver RFC5280). La política arg puede ser un nombre de objeto o un OID en forma numérica. Este argumento puede aparecer más de una vez.
-explicit_policy
Establece la variable de política require-explicit-policy (ver RFC5280).
-policy_check
Habilita el procesamiento de políticas de certificados.

OPTIONS

-policy_print
Imprime diagnósticos relacionados con el procesamiento de políticas.
-inhibit_any
Establece la variable de política inhibit-any-policy (ver RFC5280).
-inhibit_map
Establece la variable de política inhibit-policy-mapping (ver RFC5280).
-purpose propósito
Una especificación de alto nivel del uso previsto del certificado de destino. Actualmente, los propósitos predefinidos son "sslclient", "sslserver", "nssslserver", "smimesign", "smimeencrypt", "crlsign", "ocsphelper", "timestampsign", "codesign" y "any". Si la verificación del certificado del par está habilitada, por defecto la implementación TLS y, por lo tanto, los comandos openssl-s_client(1) y openssl-s_server(1) comprueban la consistencia con el servidor TLS ("sslserver") o el cliente TLS ("sslclient"), respectivamente. Por defecto, la validación de firmas de CMS, que se puede realizar a través de openssl-cms(1), comprueba la consistencia con el uso de firma S/MIME ("smimesign").

Si bien el RFC 5280 de la IETF dice que id-kp-serverAuth y id-kp-clientAuth son solo para uso WWW, en la práctica se utilizan para todo tipo de clientes y servidores TLS, y esto es lo que OpenSSL asume también.

-verify_depth num
Limita la cadena de certificados a num certificados de CA intermedios. Una cadena de profundidad máxima puede tener hasta num+2 certificados, ya que ni el certificado de entidad final ni el certificado de anclaje de confianza cuentan contra el límite de -verify_depth.
-verify_email email
Verifica si email coincide con la dirección de correo electrónico en el Nombre Alternativo del Sujeto o el correo electrónico en el Nombre Distinguido del sujeto.
-verify_hostname hostname
Verifica si hostname coincide con el nombre DNS en el Nombre Alternativo del Sujeto o el Nombre Común en el certificado del sujeto.
-verify_ip ip
Verifica si ip coincide con la dirección IP en el Nombre Alternativo del Sujeto del certificado del sujeto.
-verify_name name
Utiliza un conjunto de parámetros de verificación, también conocido como método de verificación, identificado por name. Los métodos predefinidos actualmente se denominan "ssl_client", "ssl_server", "smime_sign" con el alias "pkcs7", "code_sign" y "default". Estos imitan las combinaciones de propósito y configuración de confianza utilizados en SSL/(D)TLS, CMS/PKCS7 (incluyendo S/MIME) y firma de código.

Los parámetros de verificación incluyen el modelo de confianza, varias banderas que se pueden establecer parcialmente a través de otras opciones de línea de comandos, y el propósito de verificación, que a su vez implica el uso de clave del certificado y los requisitos de uso extendido de clave.

El modelo de confianza determina qué OIDs de confianza o rechazo auxiliares son aplicables para verificar la cadena de certificados dada. Se pueden proporcionar utilizando las opciones -addtrust y -addreject para openssl-x509(1).

Opciones de Verificación Extendida

A veces puede haber más de una cadena de certificados que conduzca a un certificado de entidad final. Esto suele ocurrir cuando una CA raíz o intermedia firma un certificado para otra CA en otra organización. Otro motivo es cuando una CA puede tener intermedias que utilizan dos formatos de firma diferentes, como un resumen SHA-1 y SHA-256.

Las siguientes opciones se pueden utilizar para proporcionar datos que permitirán al comando OpenSSL generar una cadena alternativa.

-xkey archivo_entrada, -xcert archivo_entrada, -xchain
Especifica un certificado, clave privada y cadena de certificados adicionales. Estos se comportan de la misma manera que las opciones -cert, -key y -cert_chain. Cuando se especifican, la devolución de llamada que devuelve la primera cadena válida estará en uso por el cliente.
-xchain_build
Especifica si la aplicación debe construir la cadena de certificados que se proporcionará al servidor para los certificados adicionales a través de las opciones -xkey, -xcert y -xchain.
-xcertform DER|PEM|P12
El formato de entrada para el certificado adicional. Esta opción no tiene efecto y se conserva solo por compatibilidad con versiones anteriores.
-xkeyform DER|PEM|P12
El formato de entrada para la clave adicional. Esta opción no tiene efecto y se conserva solo por compatibilidad con versiones anteriores.

Extensiones de Certificado

Opciones como -purpose y -verify_name activan el procesamiento de extensiones de certificado específicas, que determinan para qué se pueden usar los certificados.

Restricciones Básicas

La bandera CA de la extensión basicConstraints se utiliza para determinar si el certificado se puede utilizar como CA. Si la bandera CA es verdadera, entonces es una CA; si la bandera CA es falsa, entonces no es una CA. **Todas** las CA deben tener la bandera CA establecida en verdadera.

Si la extensión basicConstraints está ausente, lo que incluye el caso de que sea un certificado X.509v1, entonces el certificado se considera una "CA posible" y se comprueban otras extensiones de acuerdo con el uso previsto del certificado. El tratamiento de los certificados sin basicConstraints como CA se soporta actualmente, pero esto podría cambiar en el futuro.

Uso de Clave

Si la extensión keyUsage está presente, entonces se imponen restricciones adicionales al uso del certificado. Un certificado de CA **debe** tener el bit keyCertSign establecido si la extensión keyUsage está presente.

Uso Extendido de Clave

La extensión extKeyUsage (EKU) impone restricciones adicionales al uso del certificado. Si esta extensión está presente (ya sea crítica o no) en un certificado de entidad final, la clave solo se permite para los usos especificados, mientras que la EKU especial anyExtendedKeyUsage permite todos los usos.

Tenga en cuenta que de acuerdo con la sección 4.2.1.12 del RFC 5280, la extensión Extended Key Usage solo aparecerá en certificados de entidad final, y en consecuencia la validación estándar de la ruta de certificación descrita en su sección 6 no incluye verificaciones de EKU para certificados de CA. El Foro de CA/Navegador requiere para uso de servidor TLS, S/MIME y firma de código la presencia de EKUs respectivas en certificados de CA subordinados (excluyéndolas para certificados de CA raíz), mientras que se hace cargo del RFC 5280 el concepto de validez del certificado y la validación de la ruta del certificado.

Por razones históricas, OpenSSL tiene su propia forma de interpretar y verificar las extensiones EKU en certificados de CA, lo que puede cambiar en el futuro. No requiere la presencia de extensiones EKU en certificados de CA, pero en caso de que el propósito de verificación sea "sslclient", "nssslserver", "sslserver", "smimesign", o "smimeencrypt", comprueba que cualquier extensión EKU presente (que no contenga anyExtendedKeyUsage) contenga la EKU respectiva como se detalla a continuación. Además, realiza estas verificaciones incluso para certificados de anclaje de confianza.

Verificaciones Implícitas por Políticas Predefinidas Específicas

A continuación se presenta una descripción específica de cada verificación. Los comentarios sobre basicConstraints y keyUsage y certificados X.509v1 anteriores se aplican a **todas** las certificados de CA.

Cliente (D)TLS ("sslclient")
Cualquier extensión de uso extendido de clave dada debe permitir "clientAuth" ("Autenticación de cliente WWW TLS").

Para los certificados de destino, el uso de clave debe permitir "digitalSignature" y/o "keyAgreement". El tipo de certificado Netscape debe estar ausente o tener el bit de cliente SSL establecido.

Para todos los demás certificados se aplican las verificaciones normales de CA. Además, el tipo de certificado Netscape debe estar ausente o tener el bit de CA SSL establecido. Esto se utiliza como solución alternativa si la extensión basicConstraints está ausente.

Servidor (D)TLS ("sslserver")
Cualquier extensión de uso extendido de clave dada debe permitir "serverAuth" ("Autenticación de servidor WWW TLS") y/o incluir uno de los OIDs SGC.

Para los certificados de destino, el uso de clave debe permitir "digitalSignature", "keyEncipherment", y/o "keyAgreement". El tipo de certificado Netscape debe estar ausente o tener el bit de servidor SSL establecido.

Para todos los demás certificados se aplican las verificaciones normales de CA. Además, el tipo de certificado Netscape debe estar ausente o tener el bit de CA SSL establecido. Esto se utiliza como solución alternativa si la extensión basicConstraints está ausente.

Servidor SSL Netscape ("nssslserver")
Además de lo descrito para sslserver, para que un cliente SSL Netscape se conecte a un servidor SSL, su certificado de EE debe tener el bit de keyEncipherment establecido si la extensión keyUsage está presente. Esto no siempre es válido ya que algunas suites de cifrado utilizan la clave para la firma digital. De lo contrario, es lo mismo que un servidor SSL normal.

VERIFICATION OPTIONS

This section describes the checks performed when verifying a certificate chain, either directly using the X509_verify_cert(3) function or indirectly using the openssl-verify(1) command.

The checks can be enabled or disabled using the appropriate flags in the X509_VERIFY_PARAM structure, or by using the flags in the openssl verify command.

Note: The openssl verify command refers to these checks as "policies".

Common Checks

These checks are performed for all certificate types, except where noted otherwise.

Specific Checks

Common S/MIME
Any given extended key usage extension must allow for "emailProtection".

For target certificates, the Netscape certificate type must be absent or should have the S/MIME bit set. If the S/MIME bit is not set in the Netscape certificate type then the SSL client bit is tolerated as an alternative but a warning is shown. This is because some Verisign certificates don't set the S/MIME bit.

For all other certificates the normal CA checks apply. In addition, the Netscape certificate type must be absent or have the S/MIME CA bit set. This is used as a workaround if the basicConstraints extension is absent.

S/MIME Signing ("smimesign")
In addition to the common S/MIME checks, for target certificates the key usage must allow for "digitalSignature" and/or nonRepudiation (or its alias name contentCommitment).
S/MIME Encryption ("smimeencrypt")
In addition to the common S/MIME checks, for target certificates the key usage must allow for "keyEncipherment".
CRL Signing ("crlsign")
For target certificates, the key usage must allow for "cRLSign".

For all other certificates the normal CA checks apply. Except in this case the basicConstraints extension must be present.

OCSP Helper ("ocsphelper")
For target certificates, no checks are performed at this stage, but special checks apply; see OCSP_basic_verify(3).

For all other certificates the normal CA checks apply.

Timestamp Signing ("timestampsign")
For target certificates, if the key usage extension is present, it must include "digitalSignature" and/or "nonRepudiation" (or its alias name "contentCommitment") and must not include other bits. The EKU extension must be present and contain "timeStamping" only. Moreover, it must be marked as critical.

For all other certificates the normal CA checks apply.

Code Signing ("codesign")
For target certificates, the key usage extension must be present and marked critical and include <digitalSignature>, but must not include "keyCertSign" nor "cRLSign". The EKU extension must be present and contain "codeSign", but must not include "anyExtendedKeyUsage" nor "serverAuth".

For all other certificates the normal CA checks apply.

BUGS

The issuer checks still suffer from limitations in the underlying X509_LOOKUP API. One consequence of this is that trusted certificates with matching subject name must appear in a file (as specified by the -CAfile option), a directory (as specified by -CApath), or a store (as specified by -CAstore). If there are multiple such matches, possibly in multiple locations, only the first one (in the mentioned order of locations) is recognised.
