NOMBRE

openssl-threads - Visión general de la seguridad de hilos en OpenSSL

DESCRIPCIÓN

En esta página del manual, utilizamos el término seguro para hilos para indicar que un objeto o función puede ser utilizado por múltiples hilos al mismo tiempo.

OpenSSL se puede compilar con o sin soporte para hilos. El uso más importante de este soporte es para que OpenSSL pueda utilizar una API única y consistente, como se muestra en "EJEMPLOS" en CRYPTO_THREAD_run_once(3). Las aplicaciones multiplataforma también pueden utilizar esta API.

En particular, estar configurado para el soporte de hilos no implica que todos los objetos de OpenSSL sean seguros para hilos. Para enfatizar: la mayoría de los objetos no son seguros para uso simultáneo. Las excepciones a esto deben documentarse en las páginas del manual específicas, y aquí se ofrece una guía general de alto nivel.

Un uso importante de la API de hilos de OpenSSL es implementar el conteo de referencias. Muchos objetos dentro de OpenSSL se cuentan por referencias, por lo que los recursos no se liberan hasta que se elimina la última referencia. Las referencias a menudo se incrementan automáticamente (por ejemplo, cuando un objeto de certificado X509 se añade a un almacén de confianza X509_STORE). A menudo existe una función objeto_up_ref() que se puede usar para incrementar el contador de referencias. El no igualar las llamadas a objeto_up_ref() con el número correcto de llamadas a objeto_free() es una fuente común de fugas de memoria cuando un programa finaliza.

Muchos objetos tienen API de establecer y obtener para establecer atributos en el objeto. Un "set0" pasa la propiedad del llamante al objeto y un "get0" devuelve un puntero, pero la propiedad del atributo permanece con el objeto y se devuelve una referencia al mismo. Una función "set1" o "get1" no cambia la propiedad, sino que actualiza el contador de referencias del atributo para que el objeto sea compartido entre el llamante y el objeto; el llamante debe liberar el atributo devuelto cuando termine. Las funciones que involucran atributos que tienen contadores de referencias, pero que se nombran solo con "set" o "get" son históricas; y la documentación debe indicar cómo se manejan las referencias. Los métodos de obtención suelen ser seguros para hilos siempre que se cumplan los requisitos de propiedad y los objetos compartidos no se modifiquen. Los métodos de establecimiento, o la modificación de objetos compartidos, generalmente no son seguros para hilos, como se discute a continuación.

Los objetos son seguros para hilos siempre que las API que se invocan no modifiquen el objeto; en este caso, el parámetro generalmente se marca en la API como "const". No todos los parámetros están marcados de esta manera. Tenga en cuenta que una declaración "const" no significa inmutable; por ejemplo, X509_cmp(3) toma punteros a objetos "const", pero la implementación utiliza un cast de C para eliminarlo para poder bloquear objetos, generar y almacenar en caché una codificación DER, etc.

Otra instancia de seguridad de hilos es cuando las actualizaciones del estado interno de un objeto, como los valores almacenados en caché, se realizan con bloqueos. Un ejemplo de esto son las API de conteo de referencias descritas anteriormente.

En todos los casos, sin embargo, generalmente no es seguro que un hilo mutile un objeto, como establecer elementos de una clave privada o pública, mientras otro hilo está utilizando ese objeto, como verificar una firma.

Las mismas API generalmente se pueden usar simultáneamente en diferentes objetos sin interferencia. Por ejemplo, dos hilos pueden calcular una firma utilizando dos objetos EVP_PKEY_CTX diferentes.

Para el estado global implícito o los singleton, la seguridad de hilos depende de la funcionalidad. Las API CRYPTO_secure_malloc(3) y relacionadas tienen su propio bloqueo, mientras que CRYPTO_malloc(3) asume que la asignación de la plataforma subyacente realizará cualquier bloqueo necesario. Algunas API, como NCONF_load(3) y relacionadas, no realizan ningún bloqueo en absoluto; esto puede considerarse un error.

Una cuestión separada, aunque relacionada, es la modificación de objetos "fábrica" cuando se han creado otros objetos a partir de ellos. Por ejemplo, un objeto SSL_CTX creado por SSL_CTX_new(3) se utiliza para crear objetos SSL por conexión llamando a SSL_new(3). En este caso específico, y probablemente para los métodos de fábrica en general, no es seguro modificar el objeto fábrica después de que se haya utilizado para crear otros objetos.
