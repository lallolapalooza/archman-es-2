DESCRIPCIÓN

gcov es un programa de cobertura de pruebas. Úsalo junto con GCC para analizar tus programas y ayudar a crear código más eficiente y rápido, y para descubrir partes no probadas de tu programa. Puedes usar gcov como una herramienta de perfilado para ayudarte a descubrir dónde tus esfuerzos de optimización tendrán el mejor impacto en tu código. También puedes usar gcov junto con la otra herramienta de perfilado, gprof, para evaluar qué partes de tu código utilizan la mayor cantidad de tiempo de cómputo.

Las herramientas de perfilado te ayudan a analizar el rendimiento de tu código. Usando un perfilador como gcov o gprof, puedes obtener estadísticas básicas de rendimiento, como:

  • con qué frecuencia se ejecuta cada línea de código
  • qué líneas de código se ejecutan realmente
  • cuánto tiempo de cómputo utiliza cada sección de código

Una vez que conoces estos datos sobre cómo funciona tu código cuando se compila, puedes examinar cada módulo para ver cuáles deberían ser optimizados. gcov te ayuda a determinar dónde trabajar en la optimización.

Los desarrolladores de software también utilizan la prueba de cobertura junto con conjuntos de pruebas (test suites) para asegurar que el software es realmente lo suficientemente bueno para una versión. Los conjuntos de pruebas pueden verificar que un programa funciona como se espera; un programa de cobertura verifica qué parte del programa es ejercitada por el conjunto de pruebas. Los desarrolladores pueden entonces determinar qué tipos de casos de prueba deben agregarse a los conjuntos de pruebas para crear tanto pruebas mejores como un producto final mejor.

Deberías compilar tu código sin optimización si planeas usar gcov porque la optimización, al combinar algunas líneas de código en una función, puede no darte tanta información como necesitas para buscar 'puntos calientes' donde el código está utilizando una gran cantidad de tiempo de computadora. De manera similar, dado que gcov acumula estadísticas por línea (en la resolución más baja), funciona mejor con un estilo de programación que coloca solo una instrucción por línea. Si usas macros complicadas que se expanden a bucles o a otras estructuras de control, las estadísticas son menos útiles; solo informan sobre la línea donde aparece la llamada a la macro. Si tus macros complejas se comportan como funciones, puedes reemplazarlas con funciones en línea para resolver este problema.

gcov crea un archivo de registro llamado archivo-fuente.gcov que indica cuántas veces se ha ejecutado cada línea de un archivo fuente archivo-fuente.c. Puedes usar estos archivos de registro junto con gprof para ayudar a afinar el rendimiento de tus programas. gprof proporciona información de temporización que puedes usar junto con la información que obtienes de gcov.

gcov solo funciona en código compilado con GCC. No es compatible con ningún otro mecanismo de perfilado o cobertura de pruebas.

OPCIONES

-a
--all-blocks
Escribe recuentos de ejecución individuales para cada bloque básico. Normalmente gcov solo muestra recuentos de ejecución para los bloques principales de una línea. Con esta opción puedes determinar si los bloques dentro de una sola línea no se están ejecutando.
-b
--branch-probabilities
Escribe las frecuencias de bifurcación en el archivo de salida, y escribe un resumen de bifurcaciones en la salida estándar. Esta opción te permite ver cuántas veces se tomó cada bifurcación en tu programa. Las bifurcaciones incondicionales no se mostrarán, a menos que se proporcione la opción -u.
-c
--branch-counts
Escribe las frecuencias de bifurcación como el número de bifurcaciones tomadas, en lugar del porcentaje de bifurcaciones tomadas.
-g
--conditions
Escribe la cobertura de condiciones en el archivo de salida, y escribe un resumen de condiciones en la salida estándar. Esta opción te permite ver si las condiciones en tu programa tuvieron al menos una vez un efecto independiente en el resultado de la expresión booleana (cobertura de condición/decisión modificada). Esto requiere que compiles el código fuente con -fcondition-coverage.
-d
--display-progress
Muestra el progreso en la salida estándar.
-f
--function-summaries
Muestra resúmenes para cada función además del resumen a nivel de archivo.
-h
--help
Muestra ayuda sobre el uso de gcov (en la salida estándar) y sale sin realizar ningún procesamiento adicional.
-j
--json-format
Genera el archivo gcov en un formato intermedio JSON fácil de analizar que no requiere código fuente para su generación. El archivo JSON se comprime con el algoritmo de compresión gzip y los archivos tienen la extensión .gcov.json.gz.

La estructura del JSON es la siguiente:

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$archivo"]
}

Los campos del elemento raíz tienen la siguiente semántica:

  • current_working_directory: directorio de trabajo donde se compiló una unidad de compilación
  • data_file: nombre del archivo de datos (GCDA)
  • format_version: versión semántica del formato

    Cambios en la versión 2:

*
calls: se agrega información sobre las llamadas a funciones
*
gcc_version: versión del compilador GCC

Cada archivo tiene la siguiente forma:

{
  "file": "a.c",
  "functions": ["$funcion"],
  "lines": ["$linea"]
}

Los campos del elemento archivo tienen la siguiente semántica:

*
file_name: nombre del archivo fuente

Cada function tiene la siguiente forma:

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Los campos del elemento function tienen la siguiente semántica:

  • blocks: número de bloques que están en la función
  • blocks_executed: número de bloques ejecutados de la función
  • demangled_name: nombre "desenmascarado" de la función
  • end_column: columna en el archivo fuente donde termina la función
  • end_line: línea en el archivo fuente donde termina la función
  • execution_count: número de ejecuciones de la función
  • name: nombre de la función
  • start_column: columna en el arc

Cada line tiene la siguiente forma:

{
  "blocks_executed": 1,
  "count": 1,
  "execution_count": 1,
  "line_number": 3
}

Los campos del elemento line tienen la siguiente semántica:

  • blocks_executed: número de bloques que se ejecutan en esta línea
  • count: número de veces que se ejecutan los bloques de esta línea
  • execution_count: número de veces que se ejecuta esta línea
  • line_number: número de línea en el archivo fuente
-H
--human-readable
Con esta opción, gcov puede imprimir en formato legible para humanos. Esto incluye unidades como KB, MB, etc. para el tamaño de los archivos. La salida estándar se aplica a los resúmenes y la salida de los archivos a los archivos .gcov.
-k
--use-colors
Usa colores para la salida estándar. Los bloques de código con alta ejecución se marcarán con rojo, los bloques de baja ejecución con verde y los no ejecutados con amarillo. La salida de los archivos .gcov se verá afectada de manera similar.
-l
--long-file-names
Para cada archivo fuente, imprime el nombre completo del archivo, incluyendo la ruta de directorio, en el archivo .gcov. Por defecto, gcov solo imprime el nombre base del archivo.
-m
--demangled-names
Desenmascara los nombres de las funciones. Esto es útil para mostrar los nombres de las funciones de C++ en su forma legible.
-n
--no-output
No generar ningún archivo de salida. Esto es útil si solo deseas imprimir resúmenes en la salida estándar y no generar los archivos .gcov.
-o
--object-directory directorio|archivo
Busca los archivos de datos de cobertura de ejecución (archivos .gcno y .gcda) en el directorio especificado o archivo. Si se especifica un archivo, gcov busca en el mismo directorio que el archivo especificado. Esto es útil si compilaste tu código en un directorio de compilación separado.
-p
--preserve-paths
No elimina las rutas de los nombres de archivo. Por defecto, gcov elimina las rutas de los nombres de archivo para simplificar la salida. Esta opción es útil si necesitas las rutas completas de los archivos.
-q
--use-hotness-colors
Colorea la salida en función de la "calidez" (hotness) del código. Las líneas con alta ejecución se marcan con colores más cálidos (rojo), y las líneas con baja ejecución con colores más fríos (azul). Esta opción es una alternativa a --use-colors y se aplica tanto a la salida estándar como a los archivos .gcov.
-r
--relative-only
Solo imprime la parte relativa de las rutas de los nombres de archivo. Esto es útil cuando se trabaja con proyectos que tienen estructuras de directorios profundas y se desea ver solo la jerarquía de directorios relativa a la raíz del proyecto.
-s
--source-prefix directorio
Elimina el prefijo de directorio dado de los nombres de archivo fuente. Esto es útil para simplificar la salida cuando se compila código de un subdirectorio.
-t
--stdout
Escribe la salida de gcov a la salida estándar en lugar de a los archivos .gcov. Esto es útil para canalizar la salida a otros programas o para verla directamente en la terminal.
-u
--unconditional-branches
Incluye las bifurcaciones incondicionales en la salida de cobertura de ramas. Por defecto, estas no se muestran a menos que se especifique -b.
-v
--version
Muestra la información de la versión de gcov y sale.
-x
--hash-filenames
Codifica los nombres de archivo fuente como hashes de 64 bits. Esto puede ser útil para evitar problemas con nombres de archivo largos o caracteres especiales, o para garantizar la unicidad de los nombres de archivo en entornos distribuidos.

archivo fuente donde comienza la función
  • start_line: línea en el archivo fuente donde comienza la función

    • Tenga en cuenta que los números de línea y columna se cuentan a partir de 1. En la implementación actual, start_line y start_column no incluyen parámetros de plantilla ni el tipo de retorno principal, pero es probable que esto se corrija en el futuro.

    Cada line tiene el siguiente formato:

    {
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

    Las ramas y llamadas solo están presentes con la opción -b. Los campos del elemento line tienen la siguiente semántica:

    • block_ids: IDs de los bloques básicos que pertenecen a la línea
    • count: número de ejecuciones de la línea
    • line_number: número de línea
    • unexecuted_block: indicador de si la línea contiene un bloque no ejecutado (no todas las sentencias de la línea se ejecutan)
    • function_name: nombre de una función a la que pertenece esta line (puede no estar configurado para una línea con sentencias en línea)

    Cada branch tiene el siguiente formato:

    {
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

    Los campos del elemento branch tienen la siguiente semántica:

    • count: número de ejecuciones de la rama
    • fallthrough: true cuando la rama es una rama de caída
    • throw: true cuando la rama es una rama excepcional
    • isource_block_id: ID del bloque básico donde ocurre esta rama
    • destination_block_id: ID del bloque básico al que salta esta rama

    Cada call tiene el siguiente formato:

    {
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

    Los campos del elemento call tienen la siguiente semántica:

    • returned: número de veces que una llamada a función retornó (el recuento de llamadas es igual a line::count)
    • isource_block_id: ID del bloque básico donde ocurre esta llamada
    • destination_block_id: ID del bloque básico donde continúa la llamada después del retorno

    Cada condition tiene el siguiente formato:

    {
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

    Los campos del elemento condition tienen la siguiente semántica:

    • count: número de resultados de la condición en esta expresión
    • covered: número de resultados de la condición cubiertos en esta expresión
    • not_covered_true: términos, por índice, que no se vieron como verdaderos en esta expresión
    • not_covered_false: términos, por índice, que no se vieron como falsos en esta expresión
    -H
    --human-readable
    Escribe los recuentos en formato legible por humanos (como 24.6k).
    -k
    --use-colors
    Usa colores para las líneas de código que tienen cobertura cero. Usamos color rojo para las líneas no excepcionales y cian para las excepcionales. Los mismos colores se usan para los bloques básicos con la opción -a.
    -l
    --long-file-names
    Crea nombres de archivo largos para los archivos fuente incluidos. Por ejemplo, si el archivo de encabezado x.h contiene código y fue incluido en el archivo a.c, ejecutar gcov en el archivo a.c producirá un archivo de salida llamado a.c##x.h.gcov en lugar de x.h.gcov. Esto puede ser útil si x.h se incluye en varios archivos fuente y desea ver las contribuciones individuales. Si usa la opción -p, tanto el nombre del archivo que incluye como el del archivo incluido serán rutas completas.
    -m
    --demangled-names
    Muestra los nombres de función desmanglados en la salida. El valor predeterminado es mostrar los nombres de función manglados.
    -n
    --no-output
    No crea el archivo de salida gcov.
    -o directorio|archivo
    --object-directory directorio
    --object-file archivo
    Especifica el directorio que contiene los archivos de datos de gcov o la ruta del archivo objeto. Los archivos de datos .gcno y .gcda se buscan utilizando esta opción. Si se especifica un directorio, los archivos de datos se encuentran en ese directorio y se nombran según el nombre del archivo de entrada, sin su extensión. Si se especifica un archivo aquí, los archivos de datos se nombran según ese archivo, sin su extensión.
    -p
    --preserve-paths
    Conserva la información completa de la ruta en los nombres de los archivos .gcov generados. Sin esta opción, solo se utiliza el componente del nombre de archivo. Con esta opción, se utilizan todos los directorios, los caracteres / se traducen a caracteres #, los componentes de directorio . se eliminan y los componentes .. irremovibles se renombran a ^. Esto es útil si los archivos fuente están en varios directorios diferentes.
    -q
    --use-hotness-colors
    Emite una salida con colores similar a perf para las líneas de alta actividad. La leyenda de la escala de colores se imprime al principio del archivo de salida.
    -r
    --relative-only
    Solo muestra información sobre archivos fuente con un nombre de ruta relativo (después de la elisión del prefijo de origen). Las rutas absolutas suelen ser archivos de encabezado del sistema y la cobertura de cualquier función en línea en ellos normalmente no es interesante.
    -s directorio
    --source-prefix directorio
    Un prefijo para los nombres de archivo fuente que se eliminará al generar los archivos de cobertura de salida. Esta opción es útil cuando se compila en un directorio separado y no se desea la ruta al directorio fuente al determinar los nombres de los archivos de salida. Tenga en cuenta que esta detección de prefijo se aplica antes de determinar si el archivo fuente es absoluto.
    -t
    --stdout
    Salida al estándar de salida en lugar de a los archivos de salida.
    -u
    --unconditional-branches
    Cuando se proporcionan probabilidades de rama, incluye las de las ramas incondicionales. Las ramas incondicionales normalmente no son interesantes.
    -v
    --version
    Muestra el número de versión de gcov (en la salida estándar) y sale sin realizar ningún procesamiento adicional.
    -w
    --verbose
    Imprime información detallada relacionada con los bloques básicos y arcos.
    -x
    --hash-filenames
    Cuando se usa --preserve-paths, gcov usa la ruta completa de los archivos fuente para crear un nombre de archivo de salida. Esto puede generar nombres de archivo largos que pueden exceder los límites del sistema de archivos. Esta opción crea nombres de la forma source-file##md5.gcov, donde el componente source-file es la parte final del nombre de archivo y el componente md5 se calcula a partir del nombre manglado completo que se habría utilizado de otra manera. La opción es una alternativa a --preserve-paths en sistemas que tienen un límite de sistema de archivos.

    gcov debe ejecutarse con el directorio actual siendo el mismo que cuando invocó al compilador. De lo contrario, no podrá localizar los archivos fuente. gcov produce archivos llamados mangledname.gcov en el directorio actual. Estos contienen la información de cobertura del archivo fuente al que corresponden. Se produce un archivo .gcov por cada archivo fuente (o de encabezado) que contiene código, que se compiló para producir los archivos de datos. La parte mangledname del nombre del archivo de salida suele ser simplemente el nombre del archivo fuente, pero puede ser algo más complicado si se dan las opciones -l o -p. Consulte esas opciones para obtener detalles.

    Si invoca gcov con varios archivos de entrada, se suman las contribuciones de cada archivo de entrada. Normalmente, lo invocaría con la misma lista de archivos que el enlace final de su ejecutable.

    Los archivos .gcov contienen campos separados por : junto con el código fuente del programa. El formato es

    <execution_count>:<line_number>:<source line text>

    Información adicional del bloque puede seguir a cada línea, cuando se solicita por opción de línea de comandos. El execution_count es - para las líneas que no contienen código. Las líneas no ejecutadas se marcan ##### o =====, dependiendo de si son alcanzables por caminos no excepcionales o solo por caminos excepcionales como los manejadores de excepciones de C++, respectivamente. Dada la opción -a, los bloques no ejecutados se marcan $$$$$ o %%%%%, dependiendo de si un bloque básico es alcanzable a través de caminos no excepcionales o excepcionales. Los bloques básicos ejecutados que tienen una sentencia con recuento de ejecución 0 terminan con el carácter * y se colorean con color magenta con la opción -k. Esta funcionalidad no es compatible con Ada.

    Tenga en cuenta que GCC puede eliminar completamente los cuerpos de las funciones que no son necesarias, por ejemplo, si se insertan en línea en todas partes. Dichas funciones se marcan con -, lo que puede ser confuso. Utilice la opción -fkeep-inline-func

    NAME

    gcov - code coverage analysis tool

    SYNOPSIS

        gcov [-a | --all-blocks]
         [-b | --branch-probabilities]
         [-c | --compare-coverage]
         [-d | --delete]
         [-f | --force]
         [-m | --hash-branches]
         [-n | --no-output]
         [-o OUTDIR | --object-directory OUTDIR]
         [-p | --preserve-paths]
         [-r | --relative-only]
         [-u | --unconditional-branches]
         [-v | --version]
         [-x | --hash-functions]
         [--help]
         [--]
         <sourcefile>
    
    gcov --capture-full [-o OUTDIR | --object-directory OUTDIR]
         [--]
         <executable>
    
    gcov --restore-paths [-o OUTDIR | --object-directory OUTDIR]
         [--]
         <executable>

    DESCRIPTION

    gcov is a tool to help developers analyze the amount of testing a program has had, to help him find which parts of his program are being tested, in particular which line of a given source file’s executable lines have not been executed.

    The utility works in two main stages. First, compile your program with the GCC option -fprofile-arcs. This generates an instrumented executable. Run this executable. When it exits, it creates a .gcda file (usually containing execution counts for each basic block) for each source file.

    Second, use gcov to process the .gcno files (generated by the compiler) and the .gcda files. gcov reads the .gcno file to determine the program’s control flow graph. It then reads the .gcda file to get the execution counts. Finally, it outputs a .gcov file for each source file, which is the original source code annotated with execution counts of each line. The annotated source code is printed to standard output. If you also use the -b option, gcov will also print branch analysis.

    The format of the output is:

            execution_count:line_number:source_line

    Lines that have an execution count of zero are listed; lines that were not executed are shown with no count. Lines that have an execution count that is not zero are shown with that count. For exception handling, there may be lines containing no executable code, which will not be counted. Some lines may have a count indicating that they were executed, but the count may not be the same as the number of times the line was executed. This can occur with code that is optimized away by GCC.

    If gcov encounters a

    If the executable file is loaded through the use of a dynamic linker and if the executable file is not the main program, the .gcda file is not created. In this case, the executable file must be linked with the -lgcov library, and the file .gcda is created on exit of the executable.

    When compiling with -fprofile-arcs, the profiling code first attempts to read in an existing .gcda file; if the file doesn't match the executable (differing number of basic block counts) it will ignore the contents of the file. It then adds in the new execution counts and finally writes the data to the file.

    Using gcov with GCC Optimization

    If you plan to use gcov to help optimize your code, you must first compile your program with a special GCC option --coverage. Aside from that, you can use any other GCC options; but if you want to prove that every single line in your program was executed, you should not compile with optimization at the same time. On some machines the optimizer can eliminate some simple code lines by combining them with other lines. For example, code like this:

    if (a != b)
  c = 1;
else
  c = 0;

    can be compiled into one instruction on some machines. In this case, there is no way for gcov to calculate separate execution counts for each line because there isn't separate code for each line. Hence the gcov output looks like this if you compiled the program with optimization:

    100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

    The output shows that this block of code, combined by optimization, executed 100 times. In one sense this result is correct, because there was only one instruction representing all four of these lines. However, the output does not indicate how many times the result was 0 and how many times the result was 1.

    Inlineable functions can create unexpected line counts. Line counts are shown for the source code of the inlineable function, but what is shown depends on where the function is inlined, or if it is not inlined at all.

    If the function is not inlined, the compiler must emit an out of line copy of the function, in any object file that needs it. If fileA.o and fileB.o both contain out of line bodies of a particular inlineable function, they will also both contain coverage counts for that function. When fileA.o and fileB.o are linked together, the linker will, on many systems, select one of those out of line bodies for all calls to that function, and remove or ignore the other. Unfortunately, it will not remove the coverage counters for the unused function body. Hence when instrumented, all but one use of that function will show zero counts.

    If the function is inlined in several places, the block structure in each location might not be the same. For instance, a condition might now be calculable at compile time in some instances. Because the coverage of all the uses of the inline function will be shown for the same source lines, the line counts themselves might seem inconsistent.

    Long-running applications can use the "__gcov_reset" and "__gcov_dump" facilities to restrict profile collection to the program region of interest. Calling "__gcov_reset(void)" will clear all run-time profile counters to zero, and calling "__gcov_dump(void)" will cause the profile information collected at that point to be dumped to .gcda output files. Instrumented applications use a static destructor with priority 99 to invoke the "__gcov_dump" function. Thus "__gcov_dump" is executed after all user defined static destructors, as well as handlers registered with "atexit".

    If an executable loads a dynamic shared object via dlopen functionality, -Wl,--dynamic-list-data is needed to dump all profile data.

    Profiling run-time library reports various errors related to profile manipulation and profile saving. Errors are printed into standard error output or GCOV_ERROR_FILE file, if environment variable is used. In order to terminate immediately after an errors occurs set GCOV_EXIT_AT_ERROR environment variable. That can help users to find profile clashing which leads to a misleading profile.
