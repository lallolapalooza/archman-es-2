NOMBRE

rawshark - Volcar y analizar datos pcap brutos

SINOPSIS

rawshark [ -d <encap:linktype>|<proto:nombreproto> ] [ -F <campo a mostrar> ] [ -l ] [ -m <bytes> ] [ -o <configuración preferida> ] ... [ -p ] [ -r <tubería>|- ] [ -R <filtro de lectura (visualización)> ] [ -s ] [ -S <formato de campo> ] [ opciones ]

rawshark -h|--help

rawshark -v|--version

DESCRIPCIÓN

Rawshark lee un flujo de paquetes desde un archivo o tubería, y imprime una línea describiendo su salida, seguida de un conjunto de campos coincidentes para cada paquete en la salida estándar.

ENTRADA

A diferencia de TShark, Rawshark no hace suposiciones sobre la encapsulación o la entrada. Las banderas -d y -r deben especificarse para que funcione. Se deben especificar una o más banderas -F para que la salida sea útil. Las otras banderas listadas arriba siguen las mismas convenciones que Wireshark y TShark.

Rawshark espera registros de entrada con el siguiente formato por defecto. Esto coincide con el formato de la cabecera del paquete y los datos del paquete en un archivo con formato pcap en disco.

struct rawshark_rec_s {
    uint32_t ts_sec;      /* Marca de tiempo (segundos) */
    uint32_t ts_usec;     /* Marca de tiempo (microsegundos) */
    uint32_t caplen;      /* Longitud del buffer del paquete */
    uint32_t len;         /* Longitud del paquete "en el aire" */
    uint8_t data[caplen]; /* Datos del paquete */
};

Si se proporciona -p, rawshark espera el siguiente formato. Esto coincide con la estructura struct pcap_pkthdr y los datos del paquete utilizados en libpcap o Npcap. El formato de esta estructura depende de la plataforma; el tamaño del campo tv_sec en la estructura struct timeval podría ser de 32 o 64 bits. Para que rawshark funcione, la disposición de la estructura en la entrada debe coincidir con la disposición de la estructura en rawshark. Tenga en cuenta que este formato probablemente será el mismo que el formato anterior si rawshark es un programa de 32 bits, pero no necesariamente lo será si rawshark es un programa de 64 bits.

struct rawshark_rec_s {
    struct timeval ts;    /* Marca de tiempo */
    uint32_t caplen;      /* Longitud del buffer del paquete */
    uint32_t len;         /* Longitud del paquete "en el aire" */
    uint8_t data[caplen]; /* Datos del paquete */
};

En cualquier caso, el orden de bytes (endianness) de cada entero debe coincidir con el sistema en el que se está ejecutando rawshark.

SALIDA

Si se especifican uno o más campos mediante la bandera -F, Rawshark imprime el número, el tipo de campo y el formato de visualización de cada campo en la primera línea como número de "paquete" 0. Para cada registro, se imprimen el número de paquete, los campos coincidentes y un "1" o "0" para indicar si el campo coincidió con algún filtro de visualización proporcionado. Se utiliza un "-" para señalar el final de la descripción de un campo y al final de cada línea de paquete. Por ejemplo, las banderas -F ip.src -F dns.qry.type podrían generar la siguiente salida:

0 FT_IPv4 BASE_NONE - 1 FT_UINT16 BASE_HEX -
1 1="1" 0="192.168.77.10" 1 -
2 1="1" 0="192.168.77.250" 1 -
3 0="192.168.77.10" 1 -
4 0="74.125.19.104" 1 -

Tenga en cuenta que los paquetes 1 y 2 son consultas DNS, y los 3 y 4 no lo son. Añadir -R "not dns" todavía imprime cada línea, pero hay una indicación de que los paquetes 1 y 2 no pasaron el filtro:

0 FT_IPv4 BASE_NONE - 1 FT_UINT16 BASE_HEX -
1 1="1" 0="192.168.77.10" 0 -
2 1="1" 0="192.168.77.250" 0 -
3 0="192.168.77.10" 1 -
4 0="74.125.19.104" 1 -

También tenga en cuenta que la salida puede estar en cualquier orden y que pueden mostrarse múltiples campos coincidentes.

OPCIONES

-d <encapsulación>

Especifica cómo se deben diseccionar los datos del paquete. La encapsulación es del tipo tipo:valor, donde tipo es uno de:

encap:nombre Los datos del paquete deben diseccionarse utilizando el tipo de enlace de datos (DLT) de libpcap/Npcap nombre, por ejemplo, encap:EN10MB para Ethernet. Los nombres se convierten usando pcap_datalink_name_to_val(). Una lista completa de DLTs se puede encontrar en https://www.tcpdump.org/linktypes.html.

encap:número Los datos del paquete deben diseccionarse utilizando el LINKTYPE_ de libpcap/Npcap número, por ejemplo, encap:105 para IEEE 802.11 sin procesar o encap:101 para IP sin procesar.

proto:protocolo Los datos del paquete deben pasarse al disector de protocolo de Wireshark especificado, por ejemplo, proto:http para datos HTTP.

-F <campo a mostrar>

Añade el campo coincidente a la salida. Los campos son cualquier campo de filtro de visualización válido. Se puede especificar más de una bandera -F, y cada campo puede coincidir varias veces en un paquete dado. Se puede especificar un solo campo por bandera -F. Si desea aplicar un filtro de visualización, utilice la bandera -R.

-h|--help

Imprime el número de versión y las opciones y sale.

-l

Vacía la salida estándar después de que se imprime la información para cada paquete. (Esto no es, estrictamente hablando, con búfer de línea si se especificó -V; sin embargo, es lo mismo que con búfer de línea si no se especificó -V, ya que solo se imprime una línea para cada paquete y, como -l se usa normalmente al canalizar una captura en vivo a un programa o script, para que la salida de un paquete se muestre tan pronto como se vea y diseccione el paquete, debería funcionar igual de bien que el búfer de línea real. Hacemos esto como una solución alternativa a una deficiencia en la biblioteca C de Microsoft Visual C++.)

Esto puede ser útil al canalizar la salida de TShark a otro programa, ya que significa que el programa al que se canaliza la salida verá los datos diseccionados de un paquete tan pronto como TShark vea el paquete y genere esa salida, en lugar de verlo solo cuando el búfer de salida estándar que contiene esos datos se llena.

-m <bytes de límite de memoria>

Limita el uso de memoria de rawshark al número especificado de bytes. Solo POSIX (no Windows).

-o <preferencia>:<valor>

Establece un valor de preferencia, reemplazando el valor predeterminado y cualquier valor leído de un archivo de preferencias. El argumento de la opción es una cadena del formato nombrepreferencia:valor, donde nombrepreferencia es el nombre de la preferencia (que es el mismo nombre que aparecería en el archivo de preferencias) y valor es el valor al que debe establecerse.

-p

Asume que los datos del paquete van precedidos por una estructura pcap_pkthdr según se define en pcap.h. En algunos sistemas, el tamaño de los datos de la marca de tiempo será diferente de los datos escritos en el disco. En otros sistemas, son idénticos y esta bandera no tiene ningún efecto.

-r <tubería>|-

Lee datos de paquetes desde la fuente de entrada. Puede ser el nombre de una FIFO (tubería con nombre) o "-" para leer datos de la entrada estándar, y debe tener el formato de registro especificado anteriormente.

Si está enviando datos a rawshark desde un proceso padre en Windows, no debe cerrar el manejador de entrada estándar de rawshark prematuramente, de lo contrario, el tiempo de ejecución de C podría generar una excepción.

-R|--read-filter <filtro de lectura (visualización)>

Hace que el filtro especificado (que utiliza la sintaxis de los filtros de lectura/visualización, en lugar de la de los filtros de captura) se aplique antes de imprimir la salida. Los filtros de lectura y los filtros de visualización son sinónimos en rawshark.

-s

Permite utilizar archivos pcap estándar como entrada, omitiendo la cabecera del archivo pcap de 24 bytes.

-S

Utiliza la cadena de formato especificada para imprimir cada campo. Los siguientes formatos están disponibles:

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

supported:

%D Nombre o descripción del campo, por ej. "Tipo" para dns.qry.type

%N Valor numérico del campo en base 10.

%S Valor de cadena del campo.

Para algo similar a la visualización estándar de Wireshark ("Tipo: A (1)") podrías usar %D: %S (%N).

-v|--version

Imprime la información completa de la versión y sale.

-Y|--display-filter <filtro de lectura (visualización)>

Aplica el filtro especificado (que usa la sintaxis de los filtros de lectura/visualización, en lugar de la de los filtros de captura) antes de imprimir la salida. Los filtros de lectura y los filtros de visualización son sinónimos en rawshark.

OPCIONES DE DISECCIÓN

--disable-all-protocols

Deshabilita la disección de todos los protocolos.

--disable-protocol <nombre_proto>[,<nombre_proto>,...]

Deshabilita la disección de nombre_proto. Usa un nombre_proto de ALL para anular la lista de protocolos habilitados por defecto de tu perfil elegido y deshabilitar temporalmente todos los protocolos.

--disable-heuristic <nombre_corto>

Deshabilita la disección de protocolos heurísticos.

--enable-protocol <nombre_proto>[,<nombre_proto>,...]

Habilita la disección de nombre_proto. Usa un nombre_proto de ALL para anular la lista de protocolos deshabilitados por defecto de tu perfil elegido y habilitar temporalmente todos los protocolos que están habilitados por defecto.

Si un protocolo está implicado tanto en --disable-protocol como en --enable-protocol, el protocolo se habilita. Esto te permite deshabilitar temporalmente todos los protocolos excepto una lista de excepciones. Ejemplo: --disable-protocol ALL --enable-protocol eth,ip

--enable-heuristic <nombre_corto>

Habilita la disección de protocolos heurísticos.

-K <archivo_keytab>

Carga las claves criptográficas Kerberos desde el archivo keytab especificado. Esta opción se puede usar varias veces para cargar claves desde varios archivos.

Ejemplo: -K krb5.keytab

-n

Deshabilita la resolución de nombres de objetos de red (como nombres de host, nombres de puertos TCP y UDP); la opción -N podría anular esta.

-N <flags_resolución_nombres>

Habilita la resolución de nombres solo para tipos particulares de direcciones y números de puerto, con la resolución de nombres para otros tipos de direcciones y números de puerto deshabilitada. Esta opción (junto con -n) se puede especificar varias veces; el último valor proporcionado anula los anteriores. Esta opción y -n anulan las opciones de las preferencias, incluidas las preferencias establecidas a través de la opción -o. Si no están presentes las opciones -N y -n, se utilizan los valores de las preferencias, que por defecto son -N dmN.

El argumento es una cadena que puede contener las letras:

d para habilitar la resolución a partir de paquetes DNS capturados

g para habilitar la búsqueda de información de geolocalización de direcciones IP desde las bases de datos MaxMind configuradas

m para habilitar la resolución de direcciones MAC

n para habilitar la resolución de direcciones de red

N para habilitar el uso de resolvedores externos (por ejemplo, DNS) para la resolución de direcciones de red; sin efecto si tampoco está habilitada la n.

s para habilitar la resolución de direcciones usando información SNI encontrada en los paquetes de handshake capturados

t para habilitar la resolución de números de puerto de capa de transporte

v para habilitar la resolución de IDs de VLAN a nombres

--only-protocols <protocolos>

Solo habilita la disección de estos protocolos, separados por comas. Deshabilita todo lo demás.

-t (a|ad|adoy|d|dd|e|r|u|ud|udoy)[.[N]]|.[N]

Establece el formato de la marca de tiempo del paquete que se muestra en la columna de tiempo predeterminada. El formato puede ser uno de los siguientes:

a absoluto: La hora absoluta, como hora local en tu zona horaria, es la hora real en que se capturó el paquete, sin mostrar la fecha

ad absoluto con fecha: La fecha absoluta, mostrada como AAAA-MM-DD, y la hora, como hora local en tu zona horaria, son la hora y fecha reales en que se capturó el paquete

adoy absoluto con fecha usando día del año: La fecha absoluta, mostrada como AAAA/DOY, y la hora, como hora local en tu zona horaria, son la hora y fecha reales en que se capturó el paquete

d delta: El tiempo delta es el tiempo transcurrido desde que se capturó el paquete anterior

dd delta_displayed: El tiempo delta_displayed es el tiempo transcurrido desde que se mostró el paquete anterior

e epoch: El tiempo en segundos desde la época (1 de enero de 1970, 00:00:00)

r relativo: El tiempo relativo es el tiempo transcurrido entre el primer paquete y el paquete actual

u UTC: La hora absoluta, como UTC con un sufijo "Z", es la hora real en que se capturó el paquete, sin mostrar la fecha

ud UTC con fecha: La fecha absoluta, mostrada como AAAA-MM-DD, y la hora, como UTC con un sufijo "Z", son la hora y fecha reales en que se capturó el paquete

udoy UTC con fecha usando día del año: La fecha absoluta, mostrada como AAAA/DOY, y la hora, como UTC con un sufijo "Z", son la hora y fecha reales en que se capturó el paquete

.[N] Establece la precisión: N es el número de decimales (0 a 9). Si se usa "." sin N, la precisión se determina automáticamente a partir del rastreo.

El formato predeterminado es relativo con precisión basada en el formato de captura.

-u <s|hms>

Especifica cómo se muestran los formatos de marca de tiempo de paquete en -t que son tiempos relativos (es decir, relative, delta y delta_displayed). Las opciones válidas son:

s para segundos

hms para horas, minutos y segundos

El formato predeterminado es segundos.

OPCIONES DE DIAGNÓSTICO

--log-level <nivel>

Establece el nivel de registro activo. Los niveles admitidos en orden de menor a mayor son "noisy", "debug", "info", "message", "warning", "critical" y "error". Los mensajes en cada nivel y superiores se imprimirán, por ejemplo, "warning" imprime mensajes "warning", "critical" y "error", y "noisy" imprime todos los mensajes. Los niveles no distinguen entre mayúsculas y minúsculas.

--log-fatal <nivel>

Aborta el programa si se registran mensajes en el nivel especificado o superior. Por ejemplo, "warning" aborta ante cualquier mensaje de "warning", "critical" o "error".

--log-domains <lista>

Solo imprime mensajes para los dominios de registro especificados, por ejemplo, "GUI,Epan,sshdump". La lista de dominios debe estar separada por comas. Se puede negar con "!" como primer carácter (invierte la coincidencia).

--log-debug <lista>

Fuerza a los dominios especificados a registrarse en el nivel "debug". La lista de dominios debe estar separada por comas. Se puede negar con "!" como primer carácter (invierte la coincidencia).

--log-noisy <lista>

Fuerza a los dominios especificados a registrarse en el nivel "noisy". La lista de dominios debe estar separada por comas. Se puede negar con "!" como primer carácter (invierte la coincidencia).

--log-fatal-domains <lista>

Aborta el programa si se registran mensajes para los dominios de registro especificados. La lista de dominios debe estar separada por comas.

--log-file <ruta>

Escribe mensajes de registro y salida de stderr en el archivo especificado.

SINTAXIS DEL FILTRO DE LECTURA

Para ver una tabla completa de protocolos y campos de protocolo que son filtrables en Rawshark, consulta la página del manual wireshark-filter(4).

ARCHIVOS

Estos archivos contienen varias configuraciones de Wireshark.

Preferencias

Los archivos de *preferencias* contienen configuraciones de preferencias globales (para todo el sistema) y personales. Si existe el archivo de preferencias del sistema, se lee primero, anulando la configuración predeterminada. Si existe el archivo de preferencias personales, se lee a continuación, anulando cualquier valor anterior. Nota: Si se utiliza la opción de línea de comandos -o (posiblemente más de una vez), anulará a su vez los valores de los archivos de preferencias.

La configuración de preferencias tiene el formato *nombre_preferencia:valor*, una por línea, donde *nombre_preferencia* es el nombre de la preferencia y *valor* es el valor al que se debe establecer; se permite espacio en blanco entre : y *valor*. Una configuración de preferencia puede continuar en líneas posteriores indentando las líneas de continuación con espacios en blanco. Un carácter # inicia un comentario que se extiende hasta el final de la línea:

# ¿Deben estar las barras de desplazamiento verticales a la derecha?
# TRUE o FALSE (sin distinción de mayúsculas y minúsculas).
gui.scrollbar_on_right: TRUE

El archivo de preferencias global se busca en el subdirectorio *wireshark* dentro del subdirectorio *share* del directorio de instalación principal. En macOS, esto sería típicamente /Application/Wireshark.app/Contents/Resources/share; en otros sistemas compatibles con UNIX, como Linux, \*BSD, Solaris y AIX, esto sería típicamente /usr/share/wireshark/preferences para paquetes instalados en el sistema y /usr/local/share/wireshark/preferences para paquetes instalados localmente; en Windows, esto sería típicamente C:\Program Files\Wireshark\preferences.

En sistemas compatibles con UNIX, el archivo de preferencias personales se busca en $XDG_CONFIG_HOME/wireshark/preferences, (o, si $XDG_CONFIG_HOME/wireshark no existe mientras $HOME/.wireshark sí existe, $HOME/.wireshark/preferences); esto es típicamente $HOME/.config/wireshark/preferences. En Windows, el archivo de preferencias personales se busca en %APPDATA%\Wireshark\preferences (o, si %APPDATA% no está definido, %USERPROFILE%\Application Data\Wireshark\preferences).

Protocolos Deshabilitados (Habilitados)

Los archivos *disabled_protos* contienen listas globales y personales de protocolos que han sido deshabilitados, de modo que sus disectores nunca se llamen. Los archivos contienen nombres de protocolos, uno por línea, donde el nombre del protocolo es el mismo na me que se usaría en un filtro de visualización para el protocolo:

http
tcp     # un comentario

Si un protocolo está listado en el archivo global disabled_protos, no puede ser habilitado por el usuario.

El archivo global disabled_protos usa el mismo directorio que el archivo de preferencias global.

El archivo personal disabled_protos usa el mismo directorio que el archivo de preferencias personal.

Los archivos disabled_protos solo listan protocolos que están habilitados por defecto pero han sido deshabilitados; los protocolos que están deshabilitados por defecto (como algunos postdissectores) no se listan. Existen archivos análogos enabled_protos para protocolos que están deshabilitados por defecto pero han sido habilitados.

Disectores Heurísticos

Los archivos heuristic_protos contienen listas a nivel de sistema y personales de disectores heurísticos e indican si están habilitados o deshabilitados. Los archivos contienen nombres cortos únicos de disectores heurísticos, uno por línea, seguido de una coma y 0 para deshabilitado y 1 para habilitado:

quic,1
rtcp_stun,1
rtcp_udp,1
rtp_stun,0
rtp_udp,0
tls_tcp,1

El archivo global heuristic_protos usa el mismo directorio que el archivo de preferencias global.

El archivo personal heuristic_protos usa el mismo directorio que el archivo de preferencias personal.

Resolución de Nombres (hosts)

Las entradas en los archivos hosts en los directorios de preferencias global y personal se usan para resolver direcciones IPv4 e IPv6 antes de que se intenten resolver de cualquier otra manera. El archivo tiene la sintaxis estándar de los archivos hosts; cada línea contiene una dirección IP y un nombre, separados por espacios en blanco. El archivo personal hosts, si existe, anula al del directorio global.

La resolución de nombres de filtros de captura es manejada por libpcap en sistemas compatibles con UNIX, como Linux, macOS, \*BSD, Solaris y AIX, y por Npcap en Windows. Como tal, el archivo personal hosts de Wireshark no será consultado para la resolución de nombres de filtros de captura.

Resolución de Nombres (subnets)

Si una dirección IPv4 no se puede traducir mediante resolución de nombres (no se encuentra una coincidencia exacta) entonces se intenta una coincidencia parcial a través del archivo subnets. Tanto el archivo global subnets como los archivos personales subnets se utilizan si existen.

Cada línea de este archivo consiste en una dirección IPv4, una longitud de máscara de subred separada únicamente por un / y un nombre separado por espacios en blanco. Si bien la dirección debe ser una dirección IPv4 completa, cualquier valor posterior a la longitud de la máscara se ignora posteriormente.

Un ejemplo es:

# ¡Los comentarios deben ir precedidos por el signo #! 192.168.0.0/24 ws_test_network

Un nombre coincidente parcialmente se imprimirá como "nombre-subred.direccion-restante". Por ejemplo, "192.168.0.1" bajo la subred anterior se imprimiría como "ws_test_network.1"; si la longitud de la máscara anterior hubiera sido 16 en lugar de 24, la dirección impresa sería "ws_test_network.0.1".

Resolución de Nombres (ethers)

Los archivos ethers se consultan para correlacionar direcciones de hardware EUI-48 de 6 bytes y EUI-64 de 8 bytes con nombres. Primero se intenta el archivo personal ethers y si no se encuentra una dirección allí, se intenta a continuación el archivo global ethers.

El archivo tiene un formato similar al definido por ethers(5) en algunos sistemas tipo UNIX. Cada línea contiene una dirección de hardware y un nombre, separados por espacios en blanco (tabulaciones o espacios). Los dígitos hexadecimales de la dirección de hardware están separados por dos puntos (:), guiones (-) o puntos (.). El mismo carácter separador debe usarse consistentemente en una dirección. Un # indica un comentario que se extiende hasta el resto de la línea. Se admiten direcciones MAC de 6 bytes y EUI-64 de 8 bytes. Las siguientes cuatro líneas son líneas válidas de un archivo ethers:

ff:ff:ff:ff:ff:ff          Broadcast
c0-00-ff-ff-ff-ff          TR_broadcast
00.00.00.00.00.00          Zero_broadcast
00:00:00:00:00:00:00:00    EUI64_zero_broadcast

Tenga en cuenta que esto acepta una variedad de formatos mayor que el archivo definido por ethers(5) en la mayoría de los sistemas UN*X.

El archivo global ethers se busca en el directorio /etc en sistemas compatibles con UNIX, como Linux, macOS, \*BSD, Solaris y AIX, y en el directorio de instalación principal (por ejemplo, C:\Program Files\Wireshark) en sistemas Windows.

El archivo personal ethers se busca en el mismo directorio que el archivo de preferencias personal.

La resolución de nombres de filtros de captura es manejada por libpcap en sistemas compatibles con UNIX y por Npcap en Windows. Como tal, el archivo personal ethers de Wireshark no será consultado para la resolución de nombres de filtros de captura.

Resolución de Nombres (manuf)

El archivo manuf se utiliza para hacer coincidir la porción de proveedor de 3 bytes de una dirección de hardware de 6 bytes con el nombre del fabricante; también puede contener direcciones MAC conocidas y rangos de direcciones especificados con una máscara de red. El formato del archivo es similar al de los archivos ethers, excepto que se pueden proporcionar entradas como:

00:00:0C      Cisco     Cisco Systems, Inc

con el OUI de 3 bytes y un nombre abreviado y uno largo para un proveedor, y entradas como:

00-00-0C-07-AC/40     All-HSRP-routers

se pueden especificar, con una dirección MAC y una máscara que indican cuántos bits de la dirección deben coincidir. La entrada anterior, por ejemplo, tiene 40 bits significativos, o 5 bytes, y coincidiría con direcciones desde 00-00-0C-07-AC-00 hasta 00-00-0C-07-AC-FF. La máscara no tiene que ser un múltiplo de 8.

Se busca un archivo global manuf en el mismo directorio que el archivo de preferencias global, y se busca un archivo personal manuf en el mismo directorio que el archivo de preferencias personal.

En versiones anteriores de Wireshark, la información oficial de la Autoridad de Registro IEEE se distribuía en este formato como archivo global manuf. Esta información ahora se compila para acelerar el inicio del programa, pero la información interna se puede escribir en este formato con tshark -G manuf.

Además del archivo manuf, se busca otro archivo con el mismo formato, wka, en el directorio global. Este archivo se distribuye con Wireshark y contiene datos sobre direcciones MAC y rangos de direcciones conocidos, ensamblados de varias fuentes no IEEE pero respetadas.

Resolución de Nombres (services)

El archivo services se utiliza para traducir números de puerto a nombres. Tanto el archivo global services como los archivos personales services se utilizan si existen.

El archivo tiene la sintaxis estándar de los archivos services; cada línea contiene un nombre (de servicio) y un identificador de transporte separados por espacios en blanco. El identificador de transporte incluye un número de puerto y un nombre de protocolo de transporte (típicamente tcp, udp o sctp) separados por una /.

Un ejemplo es:

mydns 5045/udp # Mi propio Servidor de Nombres de Dominio mydns 5045/tcp # Mi propio Servidor de Nombres de Dominio

En versiones anteriores de Wireshark, la información oficial del Registro IANA se distribuía en este formato como archivo global services. Esta información ahora se compila para acelerar el inicio del programa, pero la información interna se puede escribir en este formato con tshark -G services.

Resolución de Nombres (ipxnets)

Los archivos ipxnets se utilizan para correlacionar números de red IPX de 4 bytes con nombres. Primero se intenta el archivo global ipxnets y si esa dirección no se encuentra allí, se intenta el personal a continuación.

El formato es el mismo que el archivo ethers, excepto que cada dirección es de cuatro bytes en lugar de seis. Además, la dirección puede representarse como un único número hexadecimal, como es más común en el mundo IPX, en lugar de cuatro octetos hexadecimales. Por ejemplo, estas cuatro líneas son líneas válidas de un archivo ipxnets:

C0.A8.2C.00              HR
c0-a8-1c-00              CEO
00:00:BE:EF              IT_Server1
110f                     FileServer3

El archivo global ipxnets se busca en el directorio /etc en sistemas compatibles con UNIX, como Linux, macOS, \*BSD, Solaris y AIX, y en el directorio de instalación principal (por ejemplo, C:\Program Files\Wireshark) en sistemas Windows.

El archivo personal ipxnets se busca en el mismo directorio que el archivo de preferencias personal.

Resolución de Nombres (ss7pcs)

El archivo ss7pcs se utiliza para traducir códigos de punto SS7 a nombres. Se lee del directorio de configuración personal.

Cada línea de este archivo consiste en un indicador de red seguido de un guion seguido de un código de punto en decimal y un nombre de nodo separados por espacios en blanco. Un ejemplo es:

2-1234 MyPointCode1

Resolución de Nombres (vlans)

El archivo vlans se utiliza para traducir IDs de etiquetas VLAN a nombres. Se lee del directorio de configuración personal.

Cada línea de este archivo consiste en un ID de etiqueta VLAN separado por espacios en blanco de un nombre. Un ejemplo es:

123    Server-Lan
2049   HR-Client-LAN

Filtros de Color (Reglas de Coloreado)

Los archivos colorfilters contienen filtros de color a nivel de sistema y personales. Cada línea contiene un filtro, comenzando con la cadena que se muestra en el cuadro de diálogo, seguido del filtro de visualización correspondiente. Luego se agregan los colores de fondo y primer plano:

# un comentario
@tcp@tcp@[59345,58980,65534][0,0,0]
@udp@udp@[28834,57427,65533][0,0,0]

El archivo global colorfilters usa el mismo directorio que el archivo de preferencias global.

El archivo personal colorfilters usa el mismo directorio que el archivo de preferencias personal. Se escribe a través del diálogo Ver: Reglas de Coloreado.

Si el archivo global colorfilters existe, solo se utiliza si el archivo personal colorfilters no existe; los filtros de color globales y personales no se combinan.

Plugins

Wireshark busca plugins tanto en una carpeta de plugins personal como en una carpeta de plugins global.

En sistemas compatibles con UNIX, como Linux, macOS, \*BSD, Solaris y AIX, el directorio de plugins global es lib/wireshark/plugins/ (en algunos sistemas, sustituya lib64 por lib) dentro del directorio de instalación principal (por ejemplo, /usr/local/lib/wireshark/plugins/). El directorio de plugins personal es $HOME/.local/lib/wireshark/plugins.

ARCHIVOS

Los plugins y otros archivos de datos se cargan desde directorios definidos por el sistema. En sistemas compatibles con UNIX, como Linux, macOS, \*BSD, Solaris y AIX, la ubicación de los archivos de datos es /usr/share/wireshark. El directorio de configuración personal está en el directorio de configuración del usuario (generalmente $XDG_CONFIG_HOME/wireshark o, si ese directorio no existe, pero $HOME/.wireshark sí, $HOME/.wireshark). En Windows, los archivos de datos están en el directorio de instalación (por ejemplo, C:\Program Files\Wireshark\data\) y los archivos de configuración personal están en %APPDATA%\Wireshark (o, si %APPDATA% no está definido, %USERPROFILE%\Application Data\Wireshark).

En macOS, si Wireshark está instalado como un paquete de aplicación, la carpeta de plugins global es en cambio %APPDIR%/Contents/PlugIns/wireshark.

En Windows, la carpeta de plugins global es plugins/ bajo el directorio de instalación principal (por ejemplo, C:\Program Files\Wireshark\plugins\). La carpeta de plugins personal es %APPDATA%\Wireshark\plugins (o, si %APPDATA% no está definido, %USERPROFILE%\Application Data\Wireshark\plugins).

Los plugins de Lua se almacenan en las carpetas de plugins; los plugins compilados se almacenan en subcarpetas de las carpetas de plugins, siendo el nombre de la subcarpeta el número de versión menor de Wireshark (X.Y). Hay otro nivel jerárquico para cada tipo de plugin de Wireshark (libwireshark, libwiretap y codecs). Por ejemplo, la ubicación de un plugin de libwireshark foo.so (foo.dll en Windows) sería PLUGINDIR/X.Y/epan (libwireshark solía llamarse libepan; los otros nombres de carpetas son codecs y wiretap).


Nota

En sistemas compatibles con UNIX, los plugins de Lua (pero no los plugins binarios) también pueden colocarse en $XDG_CONFIG_HOME/wireshark/plugins, (o, si $XDG_CONFIG_HOME/wireshark no existe mientras que $HOME/.wireshark sí existe, $HOME/.wireshark/plugins.)

Tenga en cuenta que un módulo de plugin de dissector puede admitir más de un protocolo; no necesariamente hay una correspondencia uno a uno entre los módulos de plugin de dissector y los protocolos. Los protocolos admitidos por un módulo de plugin de dissector se habilitan y deshabilitan de la misma manera que los protocolos integrados en Wireshark.

VARIABLES DE ENTORNO

WIRESHARK_CONFIG_DIR

Esta variable de entorno anula la ubicación de los archivos de configuración personales. En sistemas compatibles con UNIX, como Linux, macOS, \*BSD, Solaris y AIX, tiene como valor predeterminado $XDG_CONFIG_HOME/wireshark (o, si ese directorio no existe pero $HOME/.wireshark sí existe, $HOME/.wireshark); esto suele ser $HOME/.config/wireshark. En Windows, tiene como valor predeterminado %APPDATA%\Wireshark (o, si %APPDATA% no está definido, %USERPROFILE%\Application Data\Wireshark). Disponible desde Wireshark 3.0.

WIRESHARK_DEBUG_WMEM_OVERRIDE

Establecer esta variable de entorno obliga al framework wmem a utilizar el backend de asignador especificado para **todas** las asignaciones, independientemente de qué backend sea especificado normalmente por el código. Esto es principalmente útil para los desarrolladores al probar o depurar. Consulte README.wmem en la distribución fuente para obtener más detalles.

WIRESHARK_RUN_FROM_BUILD_DIRECTORY

Esta variable de entorno hace que los plugins y otros archivos de datos se carguen desde el directorio de compilación (donde se compiló el programa) en lugar de desde las ubicaciones estándar. No tiene ningún efecto cuando el programa en cuestión se ejecuta con permisos de root (o setuid) en sistemas compatibles con UNIX, como Linux, macOS, \*BSD, Solaris y AIX.

WIRESHARK_DATA_DIR

Esta variable de entorno hace que los diversos archivos de datos se carguen desde un directorio distinto de las ubicaciones estándar. No tiene ningún efecto cuando el programa en cuestión se ejecuta con permisos de root (o setuid) en sistemas compatibles con UNIX.

ERF_RECORDS_TO_CHECK

Esta variable de entorno controla el número de registros ERF que se comprueban al decidir si un archivo está realmente en formato ERF. Establecer esta variable de entorno a un número superior al predeterminado (20) haría menos probables los falsos positivos.

IPFIX_RECORDS_TO_CHECK

Esta variable de entorno controla el número de registros IPFIX que se comprueban al decidir si un archivo está realmente en formato IPFIX. Establecer esta variable de entorno a un número superior al predeterminado (20) haría menos probables los falsos positivos.

WIRESHARK_ABORT_ON_DISSECTOR_BUG

Si esta variable de entorno está establecida, Rawshark llamará a abort(3) cuando se encuentre un error en el dissector. abort(3) provocará que el programa termine de forma anormal; si está ejecutando Rawshark en un depurador, debería detenerse en el depurador y permitir la inspección del proceso, y, si no lo está ejecutando en un depurador, en algunos sistemas operativos, asumiendo que su entorno está configurado correctamente, generará un archivo de volcado (core dump). Esto puede ser útil para los desarrolladores que intentan solucionar un problema con un dissector de protocolo.

WIRESHARK_ABORT_ON_TOO_MANY_ITEMS

Si esta variable de entorno está establecida, Rawshark llamará a abort(3) si un dissector intenta añadir demasiados elementos a un árbol (generalmente esto es una indicación de que el dissector no sale de un bucle lo suficientemente pronto). abort(3) provocará que el programa termine de forma anormal; si está ejecutando Rawshark en un depurador, debería detenerse en el depurador y permitir la inspección del proceso, y, si no lo está ejecutando en un depurador, en algunos sistemas operativos, asumiendo que su entorno está configurado correctamente, generará un archivo de volcado (core dump). Esto puede ser útil para los desarrolladores que intentan solucionar un problema con un dissector de protocolo.
