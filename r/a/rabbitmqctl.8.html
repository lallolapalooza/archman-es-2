NOMBRE

rabbitmqctl — herramienta para administrar nodos RabbitMQ

SINOPSIS

rabbitmqctl [-q] [-s] [-l] [-n nodo] [-t tiempo_espera] comando [opciones_comando]

DESCRIPCIÓN

RabbitMQ es un broker de mensajería de código abierto y multiprotocolo.

rabbitmqctl es la herramienta principal de línea de comandos para administrar un nodo servidor RabbitMQ, junto con rabbitmq-diagnostics, rabbitmq-upgrade, y otros.

Realiza todas las acciones conectándose al nodo RabbitMQ de destino en un puerto de comunicación dedicado para herramientas CLI y autenticándose mediante un secreto compartido (conocido como archivo cookie).

Se muestra información diagnóstica si la conexión falló, el nodo de destino no se estaba ejecutando o rabbitmqctl no pudo autenticarse correctamente en el nodo de destino.

Para obtener más información, consulte la guía de herramientas CLI de RabbitMQ

OPCIONES

-n nodo
El nodo predeterminado es "rabbit@nombre_host_destino", donde nombre_host_destino es el host local. En un host llamado "miservidor.example.com", el nombre del nodo será generalmente "rabbit@miservidor" (a menos que RABBITMQ_NODENAME se haya anulado, en cuyo caso necesitará usar
--longnames
). La salida de "hostname -s" es generalmente el nombre de host correcto a usar después del signo "@". Consulte rabbitmq-server(8) para obtener detalles sobre la configuración de un nodo RabbitMQ.
-q, --quiet
Se selecciona el modo de salida silencioso. Los mensajes informativos se reducen cuando el modo silencioso está activo.
-s, --silent
Se selecciona el modo de salida mudo. Los mensajes informativos se reducen y se suprimen los encabezados de tabla cuando el modo mudo está activo.
--no-table-headers
No mostrar encabezados para datos tabulares.
--dry-run
No ejecutar el comando. Solo imprimir mensajes informativos.
-t tiempo_espera, --timeout tiempo_espera
Tiempo de espera de la operación en segundos. No todos los comandos admiten tiempos de espera. El valor predeterminado es infinito.
-l, --longnames
Debe especificarse cuando el clúster está configurado para usar nombres de nodo largos (FQDN). Para obtener más información, consulte la guía de clústeres de RabbitMQ
--erlang-cookie cookie
Secreto compartido a utilizar para autenticarse en el nodo de destino. Prefiera usar un archivo local o la variable de entorno RABBITMQ_ERLANG_COOKIE en lugar de especificar esta opción en la línea de comandos. Para obtener más información, consulte la guía de herramientas CLI de RabbitMQ

Nodos

await_startup

Espera a que la aplicación RabbitMQ se inicie en el nodo de destino

Por ejemplo, para esperar a que la aplicación RabbitMQ se inicie:

rabbitmqctl await_startup
reset

Devuelve un nodo RabbitMQ a su estado original.

Elimina el nodo de cualquier clúster al que pertenezca, elimina todos los datos de la base de datos de gestión, como usuarios y vhosts configurados, y elimina todos los mensajes persistentes.

Para que reset y force_reset tengan éxito, la aplicación RabbitMQ debe haberse detenido, por ejemplo con stop_app.

Por ejemplo, para restablecer el nodo RabbitMQ:

rabbitmqctl reset
rotate_logs

Instruye al nodo RabbitMQ para que realice una rotación interna de logs.

La rotación de logs se realiza de acuerdo con la configuración de registro especificada en el archivo de configuración. La operación de rotación es asíncrona, no hay garantía de que se complete antes de que este comando devuelva el control.

Tenga en cuenta que no es necesario llamar a este comando en caso de rotación externa de logs (por ejemplo, desde logrotate(8)).

Por ejemplo, para realizar la rotación inicial de logs:

rabbitmqctl rotate_logs
shutdown

Apaga el nodo, tanto RabbitMQ como su tiempo de ejecución. El comando es bloqueante y devolverá el control después de que el proceso de tiempo de ejecución salga. Si RabbitMQ no se detiene, devolverá un código de salida distinto de cero. Este comando infiere el PID del sistema operativo del nodo de destino y, por lo tanto, solo se puede usar para apagar nodos que se ejecutan en el mismo host (o en general, en el mismo sistema operativo, por ejemplo, en la misma VM o contenedor).

A diferencia del comando stop, el comando shutdown:

  • no requiere un pid_file para esperar a que el proceso de tiempo de ejecución termine
  • devuelve un código de salida distinto de cero si el nodo RabbitMQ no se está ejecutando

Por ejemplo, esto apagará un nodo RabbitMQ local que se ejecuta con el nombre de nodo predeterminado:

rabbitmqctl shutdown
start_app

Inicia la aplicación RabbitMQ.

Este comando se ejecuta típicamente después de realizar otras acciones de gestión que requieren que la aplicación RabbitMQ se detenga, por ejemplo, reset.

Por ejemplo, para instruir al nodo RabbitMQ que inicie la aplicación RabbitMQ:

rabbitmqctl start_app
stop [pid_file]

Detiene el nodo Erlang en el que se está ejecutando RabbitMQ. Para reiniciar el nodo, siga las instrucciones para "Ejecutar el servidor" en la guía de instalación.

Si se especifica un pid_file, también espera a que termine el proceso especificado allí.

Gestión del nodo

reset

Devuelve un nodo RabbitMQ a su estado virgen.

Este comando borra todos los recursos del nodo, incluidas las colas, los exchanges, los bindings, los usuarios y los permisos. El nodo se reinicia después de la operación. El nodo debe detenerse antes de ejecutar este comando, por ejemplo, con stop_app.

Por ejemplo, para devolver el nodo RabbitMQ a su estado original:

rabbitmqctl reset
rotate_logs [--all]

Cierra y reabre los archivos de registro.

Esto permite que los archivos de registro se roten sin reiniciar el nodo.

Si se proporciona el argumento --all, todos los registros de todos los nodos de RabbitMQ en la máquina se rotarán.

Por ejemplo, para rotar los registros del nodo actual:

rabbitmqctl rotate_logs

Por ejemplo, para rotar todos los registros de todos los nodos de RabbitMQ en la máquina:

rabbitmqctl rotate_logs --all
set_log_level level

Establece el nivel de registro de RabbitMQ.

Los niveles de registro válidos son: debug, info, warning, error, critical.

Por ejemplo, para establecer el nivel de registro en «debug»:

rabbitmqctl set_log_level debug
shutdown

Solicita al nodo RabbitMQ que se apague.

Este comando intenta apagar el nodo RabbitMQ de forma ordenada. El nodo se detendrá y todos los procesos de RabbitMQ se terminarán.

Consulte la descripción del comando wait para obtener más detalles sobre este archivo.

Por ejemplo, para indicar al nodo RabbitMQ que termine:

rabbitmqctl stop
stop_app

Detiene la aplicación RabbitMQ, dejando en ejecución el tiempo de ejecución (VM de Erlang).

Este comando se ejecuta normalmente antes de realizar otras acciones de gestión que requieran que la aplicación RabbitMQ se detenga, por ejemplo, reset.

Por ejemplo, para indicar al nodo RabbitMQ que detenga la aplicación RabbitMQ:

rabbitmqctl stop_app
wait pid_file, wait --pid pid

Espera a que la aplicación RabbitMQ se inicie.

Este comando esperará a que la aplicación RabbitMQ se inicie en el nodo. Esperará a que se cree el archivo pid si se especifica pidfile, luego a que un proceso con un pid especificado en el archivo pid o el argumento --pid, y luego a que la aplicación RabbitMQ se inicie en ese proceso. Fallará si el proceso termina sin iniciar la aplicación RabbitMQ.

Si el archivo pid especificado no se crea o el nodo erlang no se inicia dentro de --timeout, el comando fallará. El tiempo de espera predeterminado es de 10 segundos.

El script rabbitmq-server(8) crea un archivo pid adecuado. Por defecto, este se encuentra en el directorio Mnesia. Modifique la variable de entorno RABBITMQ_PID_FILE para cambiar la ubicación.

Por ejemplo, este comando se completará cuando el nodo RabbitMQ se haya iniciado:

rabbitmqctl wait /var/run/rabbitmq/pid

Gestión de clúster

await_online_nodes count

Espera a que count nodos se unan al clúster

Por ejemplo, para esperar a que se inicien dos nodos RabbitMQ:

rabbitmqctl await_online_nodes 2
change_cluster_node_type type

Cambia el tipo del nodo del clúster.

El type debe ser uno de los siguientes:

  • disc
  • ram

El nodo debe detenerse para que esta operación tenga éxito, y al convertir un nodo en un nodo RAM, el nodo no debe ser el único nodo de disco en el clúster.

Por ejemplo, este comando convertirá un nodo RAM en un nodo de disco:

rabbitmqctl change_cluster_node_type disc
cluster_status

Muestra todos los nodos del clúster agrupados por tipo de nodo, junto con los nodos que se están ejecutando actualmente.

Por ejemplo, este comando muestra los nodos del clúster:

rabbitmqctl cluster_status
force_boot

Asegura que el nodo se iniciará la próxima vez, incluso si no fue el último en apagarse.

Normalmente, cuando apaga un clúster RabbitMQ por completo, el primer nodo que reinicia debe ser el último en apagarse, ya que puede haber visto cosas que otros nodos no vieron. Pero a veces eso no es posible: por ejemplo, si todo el clúster pierde energía, entonces todos los nodos pueden pensar que no fueron los últimos en apagarse.

En tal caso, puede invocar force_boot mientras el nodo está apagado. Esto indicará al nodo que se inicie incondicionalmente la próxima vez que se le solicite. Se perderán todos los cambios realizados en el clúster después de que este nodo se apagara.

Si el último nodo en apagarse se pierde permanentemente, debería usar forget_cluster_node --offline en lugar de este comando, ya que asegurará que las colas replicadas cuyo réplica líder estaba en el nodo perdido se promuevan.

Por ejemplo, esto forzará al nodo a no esperar a otros nodos la próxima vez que se inicie:

rabbitmqctl force_boot
force_reset (obsoleto)

Devuelve forzadamente un nodo RabbitMQ a su estado virgen.

El comando force_reset difiere de reset en que restablece el nodo incondicionalmente, independientemente del estado actual de la base de datos de gestión y la configuración del clúster. Solo debe usarse como último recurso si la base de datos o la configuración del clúster se han corrompido.

El comando force_reset está obsoleto. Sigue estando disponible cuando se utiliza el almacén de metadatos Mnesia. No está soportado con el almacén de metadatos Khepri.

Para que reset y force_reset tengan éxito, la aplicación RabbitMQ debe haberse detenido, por ejemplo, con stop_app.

Por ejemplo, para restablecer el nodo RabbitMQ:

rabbitmqctl force_reset
forget_cluster_node [--offline]
--offline
Permite la eliminación de nodos de un nodo sin conexión. Esto solo es útil en la situación en la que todos los nodos están sin conexión y el último nodo en apagarse no puede conectarse, lo que impide que todo el clúster se inicie. No debe usarse en ninguna otra circunstancia, ya que puede provocar inconsistencias.

Elimina un nodo del clúster de forma remota. El nodo que se está eliminando debe estar sin conexión, mientras que el nodo del que estamos eliminando debe estar en línea, excepto cuando se utiliza la bandera --offline.

Cuando se utiliza la bandera --offline, rabbitmqctl no intentará conectarse a un nodo normalmente; en su lugar, se convertirá temporalmente en el nodo para realizar el cambio. Esto es útil si el nodo no se puede iniciar normalmente. En este caso, el nodo se convertirá en la fuente canónica para los metadatos del clúster (por ejemplo, qué colas existen), incluso si no lo era antes. Por lo tanto, debería usar este comando en el nodo más reciente en apagarse si es posible.

Por ejemplo, este comando eliminará el nodo «rabbit@stringer» del nodo «hare@mcnulty»:

rabbitmqctl -n hare@mcnulty forget_cluster_node rabbit@stringer
join_cluster seed-node [--ram]
seed-node
Miembro existente del clúster (nodo semilla) con el que formar el clúster.
--ram
Si se proporciona, el nodo se unirá al clúster como un nodo RAM. Se desaconseja el uso de nodos RAM. Úselos solo si comprende por qué exactamente necesita usarlos.

Indica al nodo que se convierta en miembro del clúster al que pertenece el nodo especificado. Antes de formar el clúster, el nodo se restablece, así que tenga cuidado al usar este comando. Para que este comando tenga éxito, la aplicación RabbitMQ debe haberse detenido, por ejemplo, con stop_app.

Los nodos del clúster pueden ser de dos tipos: disco o RAM. Los nodos de disco replican datos en RAM y en disco, proporcionando así redundancia en caso de fallo del nodo y recuperación de eventos globales como cortes de energía en todos los nodos. Los nodos RAM solo replican datos en RAM (excepto el contenido de las colas, que puede residir en disco si la cola es persistente o demasiado grande para caber en memoria) y se utilizan principalmente para la escalabilidad. Los nodos RAM son más eficientes solo cuando gestionan recursos (por ejemplo, agregar/eliminar colas, exchanges o bindings). Un clúster siempre debe tener al menos un nodo de disco y, por lo general, debería tener más de uno.

El nodo será un nodo de disco por defecto. Si desea crear un nodo RAM, proporcione la bandera --ram.

Después de ejecutar el comando join_cluster, siempre que la aplicación RabbitMQ se inicie en el nodo actual, intentará conectarse a los nodos que estaban en el clúster cuando el nodo se apagó.

Para abandonar un clúster, reset el nodo. También puede eliminar nodos de forma remota con el comando forget_cluster_node.

Por ejemplo, este comando indica al nodo RabbitMQ que se una al clúster al que pertenece «hare@elena», como un nodo ram:

rabbitmqctl join_cluster hare@elena --ram

Para obtener más información, consulte la guía de Clustering de RabbitMQ.

    rabbitmqCTL(8)

    rabbitmqctl utility for managing RabbitMQ.

    Description

    The rabbitmqctl utility is used for managing your RabbitMQ server. It provides commands for managing users, permissions, vhosts, exchanges, queues, and more. Most of these commands require the RabbitMQ server to be running.

    Usage

    rabbitmqctl [-n node] [--longnames | --nodename node] [-q] [--quiet] [-s path] [--ssl] [--ssl-protocol protocol] [--ssl-versions versions] [--ssl-certfile file] [--ssl-keyfile file] [--ssl-fail-if-no-peer-cert] [--ssl-depth depth] [--cacertfile file] [--auth user:password] [--auth-mechanism mechanism] [--connection-timeout timeout] [--vm-timeout timeout] [--log-file file] [-t timeout] [--timeout timeout] command [args...] [user @host] [password]

    rabbitmqctl provides a number of commands for inspecting and managing the broker. See the sub-sections below for more details on each command.

    rabbitmqctl attempts to connect to the broker using the Erlang distribution protocol. The connection is made to the node specified by the -n option, or to the node specified by the RABBITMQ_NODENAME environment variable, or to the node named rabbit@localhost if neither is set. If RABBITMQ_NODE_PORT is set, it is used to connect to the node.

    If the node is running with long names (e.g. rabbit@internal.rabbitmq.com), then rabbitmqctl must be invoked with the --longnames option.

    All commands take optional user and password arguments at the end, which are used to authenticate the connection to the broker. If they are omitted, then rabbitmqctl will attempt to connect to the broker as the Erlang 'guest' user. If the broker is running in cluster mode, it is customary to use the user name of the node you are running the command against, e.g. user@host.

    Commands that manage users, vhosts, permissions, etc. may require that the rabbitmq_management plugin is enabled and running.

    list_stomp_connections [stomp_connectioninfoitem]
    Similar to the list_connections command, but returns fields that make sense for STOMP connections. stomp_connectioninfoitem parameter is used to indicate which connection information items to include in the results. The column order in the results will match the order of the parameters. stomp_connectioninfoitem can take any value from the list that follows:
    conn_name
    Readable name for the connection.
    connection
    Id of the Erlang process associated with the internal amqp direct connection.
    connection_state
    Connection state; one of:
    • running
    • blocking
    • blocked
    session_id
    STOMP protocol session identifier
    channel
    AMQP channel associated with the connection
    version
    Negotiated STOMP protocol version for the connection.
    implicit_connect
    Indicates if the connection was established using implicit connect (without CONNECT frame)
    auth_login
    Effective username for the connection.
    auth_mechanism
    STOMP authorization mechanism. Can be one of:
    • config
    • ssl
    • stomp_headers
    port
    Server port.
    host
    Server hostname obtained via reverse DNS, or its IP address if reverse DNS failed or was not enabled.
    peer_port
    Peer port.
    peer_host
    Peer hostname obtained via reverse DNS, or its IP address if reverse DNS failed or was not enabled.
    protocol
    STOMP protocol version, which can be one of the following:
    • {'STOMP', 0}
    • {'STOMP', 1}
    • {'STOMP', 2}
    channels
    The number of channels using the connection.
    channel_max
    Maximum number of channels on this connection.
    frame_max
    Maximum frame size (bytes).
    client_properties
    Informational properties transmitted by the client during connection
    ssl
    Boolean indicating whether the connection is secured with SSL.
    ssl_protocol
    TLS protocol (e.g. "tlsv1").
    ssl_key_exchange
    TLS key exchange algorithm (e.g. "rsa").
    ssl_cipher
    TLS cipher algorithm (e.g. "aes_256_cbc").
    ssl_hash
    SSL hash function (e.g. "sha").

    Management agent plugin

    reset_stats_db [--all]
    Reset the management stats database for the RabbitMQ node.
    --all
    Reset the stats database for all nodes in the cluster.
