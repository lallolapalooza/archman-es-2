rmic(1) Herramientas de Invocación de Métodos Remotos (RMI) rmic(1)

NOMBRE

rmic - Genera clases stub, skeleton y tie para objetos remotos que utilizan el Protocolo de Métodos Remotos de Java (JRMP) o el Protocolo Internet Inter-Orb (IIOP). También genera el Lenguaje de Definición de Interfaces (IDL) del Object Management Group (OMG)

SINOPSIS

rmic [ opciones ] nombres-de-clases-calificados-por-paquete
opciones
Las opciones de la línea de comandos. Ver Opciones.
nombres-de-clases-calificados-por-paquete
Nombres de clases que incluyen sus paquetes, por ejemplo, java.awt.Color.

DESCRIPCIÓN

Nota de Deprecación: El soporte para la generación estática de stubs y skeletons del Protocolo de Métodos Remotos de Java (JRMP) ha sido deprecado. Oracle recomienda utilizar stubs JRMP generados dinámicamente en su lugar, eliminando la necesidad de usar esta herramienta para aplicaciones basadas en JRMP. Ver la especificación de java.rmi.server.UnicastRemoteObject en http://docs.oracle.com/javase/8/docs/api/java/rmi/server/UnicastRemoteObject.html para más información.

El compilador rmic genera archivos de clase stub y skeleton utilizando el Protocolo de Métodos Remotos de Java (JRMP) y archivos de clase stub y tie (protocolo IIOP) para objetos remotos. Estos archivos de clase se generan a partir de clases de lenguaje de programación Java compiladas que son clases de implementación de objetos remotos. Una clase de implementación remota es una clase que implementa la interfaz java.rmi.Remote. Los nombres de clase en el comando rmic deben ser para clases que se compilaron exitosamente con el comando javac y deben estar completamente calificados por paquete. Por ejemplo, ejecutar el comando rmic en el nombre de archivo de clase HelloImpl como se muestra aquí crea el archivo HelloImpl_Stub.class en el subdirectorio hello (nombrado según el paquete de la clase):

rmic hello.HelloImpl

Un skeleton para un objeto remoto es una entidad del lado del servidor del protocolo JRMP que tiene un método que distribuye llamadas a la implementación del objeto remoto.

Un tie para un objeto remoto es una entidad del lado del servidor similar a un skeleton, pero se comunica con el cliente usando el protocolo IIOP.

Un stub es un proxy del lado del cliente para un objeto remoto que es responsable de comunicar las invocaciones de métodos en objetos remotos al servidor donde reside la implementación real del objeto remoto. La referencia de un cliente a un objeto remoto, por lo tanto, es en realidad una referencia a un stub local.

Por defecto, el comando rmic genera clases stub que usan solo la versión 1.2 del protocolo de stubs JRMP, como si se hubiera especificado la opción -v1.2. La opción -vcompat era la predeterminada en versiones anteriores a la 5.0. Utilice la opción -iiop para generar clases stub y tie para el protocolo IIOP. Ver Opciones.

Un stub implementa solo las interfaces remotas, y no cualquier interfaz local que el objeto remoto también implemente. Debido a que un stub JRMP implementa el mismo conjunto de interfaces remotas que el objeto remoto, un cliente puede usar los operadores integrados del lenguaje de programación Java para casting y verificación de tipos. Para IIOP, se debe usar el método PortableRemoteObject.narrow.

OPCIONES

-bootclasspath ruta

Anula la ubicación de los archivos de clase de arranque.
-classpath ruta

Especifica la ruta que utiliza el comando rmic para buscar clases. Esta opción anula el valor predeterminado o la variable de entorno CLASSPATH cuando está configurada. Los directorios están separados por dos puntos. El formato general para ruta es: .:<tu_ruta>, por ejemplo: .:/usr/local/java/classes.
-d directorio

Especifica el directorio de destino raíz para la jerarquía de clases generada. Puede usar esta opción para especificar un directorio de destino para los archivos stub, skeleton y tie. Por ejemplo, el siguiente comando coloca las clases stub y skeleton derivadas de MyClass en el directorio /java/classes/exampleclass. 
rmic -d /java/classes exampleclass.MyClass

Si no se especifica la opción -d, el comportamiento predeterminado es como si se especificara -d .. La jerarquía de paquetes de la clase objetivo se crea en el directorio actual, y los archivos stub/tie/skeleton se colocan dentro de ella. En algunas versiones anteriores del comando rmic, si no se especificaba la opción -d, entonces no se creaba la jerarquía de paquetes y todos los archivos de salida se colocaban directamente en el directorio actual.

-extdirs ruta

Anula la ubicación de las extensiones instaladas.
-g

Habilita la generación de toda la información de depuración, incluidas las variables locales. Por defecto, solo se genera información de número de línea.
-idl

Hace que el comando rmic genere OMG IDL para las clases especificadas y cualquier clase referenciada. IDL proporciona una forma puramente declarativa e independiente del lenguaje de programación para especificar una API para un objeto. El IDL se utiliza como especificación para métodos y datos que pueden escribirse y llamarse desde cualquier lenguaje que proporcione enlaces CORBA. Esto incluye Java y C++ entre otros. Ver Java IDL: Mapeo del Lenguaje IDL a Java en http://docs.oracle.com/javase/8/docs/technotes/guides/idl/mapping/jidlMapping.html

Cuando se usa la opción -idl, otras opciones también incluyen:

•
Las opciones -always o -alwaysgenerate fuerzan la regeneración incluso cuando los stubs/ties/IDL existentes son más nuevos que la clase de entrada.
•
La opción -factory utiliza la palabra clave factory en el IDL generado.
•
-idlModule de JavaPackage[.class]toIDLModule especifica el mapeo del paquete IDLEntity, por ejemplo: -idlModulemy.module my::real::idlmod.
•
-idlFilefromJavaPackage[.class] toIDLFile especifica el mapeo de archivo IDLEntity, por ejemplo: -idlFile test.pkg.X TEST16.idl.
-iiop

Hace que el comando rmic genere clases stub y tie IIOP, en lugar de clases stub y skeleton JRMP. Una clase stub es un proxy local para un objeto remoto y es utilizada por los clientes para enviar llamadas a un servidor. Cada interfaz remota requiere una clase stub, que implementa esa interfaz remota. Una referencia de cliente a un objeto remoto es una referencia a un stub. Las clases tie se utilizan en el lado del servidor para procesar llamadas entrantes y distribuir las llamadas a la clase de implementación apropiada. Cada clase de implementación requiere una clase tie.

Si llama al comando rmic con -iiop, entonces genera stubs y ties que se ajustan a esta convención de nomenclatura:

_<nombreImplementacion>_stub.class
_<nombreInterfaz>_tie.class
•
Cuando utiliza la opción -iiop, otras opciones también incluyen:
•
Las opciones -always o -alwaysgenerate fuerzan la regeneración incluso cuando los stubs/ties/IDL existentes son más nuevos que la clase de entrada.
•
La opción -nolocalstubs significa no crear stubs optimizados para clientes y servidores del mismo proceso.
•
La opción -noValueMethods debe usarse con la opción -idl. La opción -noValueMethods evita la adición de métodos y inicializadores de valuetype al IDL emitido. Estos métodos e inicializadores son opcionales para los valuetypes, y se generan a menos que se especifique la opción -noValueMethods con la opción -idl.
•
La opción -poa cambia la herencia de org.omg.CORBA_2_3.portable.ObjectImpl a

rmic-openjdk8 1

NAME

rmic - Genera la ligadura (stub) del compilador de RMI.

SYNOPSIS

rmic [options] FullyQualifiedClassName ...

DESCRIPTION

rmic

compila archivos de clase Java que contienen definiciones de métodos remotos.

rmic

genera archivos de ligadura (stub) de la máquina virtual remota de Java (JRMP) que permiten que los objetos Java se comuniquen a través de redes.

La aplicación `rmic` genera un archivo de ligadura (stub) para cada clase de objeto remoto especificada en la línea de comandos. Por ejemplo, si se compila `MyRemoteClass.class`, el archivo de ligadura generado es `MyRemoteClass_Stub.class`.

Los archivos de ligadura (stub) son necesarios para que los clientes puedan comunicarse con las implementaciones de objetos remotos. El código del cliente carga el archivo de ligadura (stub) generado, el cual contiene el código necesario para invocar métodos en el objeto remoto.

La herramienta `rmic` implementa el estándar de mapeo del lenguaje IDL a Java de OMG. El nombre de archivo de salida es el nombre de la clase especificada, seguido de `_Stub.class` para las ligaduras JRMP o `_Skel.class` para los esqueletos JRMP.

La herramienta `rmic` se utiliza para generar ligaduras y esqueletos para aplicaciones que utilizan Java Remote Method Invocation (RMI).

org.omg.PortableServer.Servant. El módulo PortableServer para el Adaptador de Objetos Portátil (POA) define el tipo nativo Servant. En el lenguaje de programación Java, el tipo Servant se mapea a la clase Java org.omg.PortableServer.Servant. Sirve como clase base para todas las implementaciones de servant POA y proporciona una serie de métodos que pueden ser llamados por el programador de la aplicación, y métodos que son llamados por la POA y que pueden ser sobrescritos por el usuario para controlar aspectos del comportamiento del servant. Basado en la Especificación de Mapeo del Lenguaje IDL a Java de OMG, CORBA V 2.3.1 ptc/00-01-08.pdf.

OPTIONS

-J

Usado con cualquier comando Java, la opción -J pasa el argumento que sigue a -J (sin espacios entre -J y el argumento) al intérprete de Java.
-keep o -keepgenerated

Conserva los archivos fuente generados .java para las clases stub, skeleton y tie y los escribe en el mismo directorio que los archivos .class.
-nowarn

Desactiva las advertencias. Cuando se utiliza la opción -nowarn, el compilador no imprime ninguna advertencia.
-nowrite

No escribe las clases compiladas en el sistema de archivos.
-vcompat (obsoleto)

Genera clases stub y skeleton que son compatibles con ambas versiones del protocolo de stub JRMP 1.1 y 1.2. Esta opción era el valor predeterminado en las versiones anteriores a la 5.0. Las clases stub generadas utilizan la versión 1.1 del protocolo de stub cuando se cargan en una máquina virtual JDK 1.1 y utilizan la versión 1.2 del protocolo de stub cuando se cargan en una máquina virtual 1.2 (o posterior). Las clases skeleton generadas soportan ambas versiones del protocolo de stub 1.1 y 1.2. Las clases generadas son relativamente grandes para soportar ambos modos de operación. Nota: Esta opción ha sido obsoleta. Ver Descripción.
-verbose

Hace que el compilador y el enlazador impriman mensajes sobre qué clases se están compilando y qué archivos de clase se están cargando.
-v1.1 (obsoleto)

Genera clases stub y skeleton solo para la versión 1.1 del protocolo de stub JRMP. La opción -v1.1 solo es útil para generar clases stub que sean compatibles con la serialización con clases stub preexistentes, desplegadas estáticamente, que fueron generadas por el comando rmic desde JDK 1.1 y que no pueden ser actualizadas (y no se está utilizando la carga dinámica de clases). Nota: Esta opción ha sido obsoleta. Ver Descripción.
-v1.2 (obsoleto)

(Predeterminado) Genera clases stub solo para la versión 1.2 del protocolo de stub JRMP. No se generan clases skeleton porque las clases skeleton no se utilizan con la versión 1.2 del protocolo de stub. Las clases stub generadas no funcionan cuando se cargan en una máquina virtual JDK 1.1. Nota: Esta opción ha sido obsoleta. Ver Descripción.

VARIABLES DE ENTORNO

CLASSPATH
Se utiliza para proporcionar al sistema una ruta a las clases definidas por el usuario. Los directorios están separados por dos puntos, por ejemplo: .:/usr/local/java/classes.
