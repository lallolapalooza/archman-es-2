rmic(1) Herramientas de Invocación de Método Remoto (RMI) rmic(1)

NOMBRE

rmic - Genera clases stub, skeleton y tie para objetos remotos que utilizan el protocolo de método remoto (JRMP) o el protocolo Internet Inter-Orb (IIOP). También genera el lenguaje de definición de interfaz (IDL) del Object Management Group (OMG).

SINOPSIS

rmic [ opciones ] nombres-de-clase-cualificados-por-paquete
opciones
Las opciones de línea de comandos. Ver Opciones.
nombres-de-clase-cualificados-por-paquete
Nombres de clase que incluyen sus paquetes, por ejemplo, java.awt.Color.

DESCRIPCIÓN

Nota de desaprobación: El soporte para la generación estática de stubs y skeletons del protocolo de método remoto (JRMP) ha sido desaprobado. Oracle recomienda que utilice stubs JRMP generados dinámicamente en su lugar, eliminando la necesidad de utilizar esta herramienta para aplicaciones basadas en JRMP. Consulte la especificación de java.rmi.server.UnicastRemoteObject en http://docs.oracle.com/javase/8/docs/api/java/rmi/server/UnicastRemoteObject.html para obtener más información.

El compilador rmic genera archivos de clase stub y skeleton utilizando el protocolo de método remoto (JRMP) y archivos de clase stub y tie (protocolo IIOP) para objetos remotos. Estos archivos de clase se generan a partir de clases de lenguaje de programación Java compiladas que son clases de implementación de objetos remotos. Una clase de implementación remota es una clase que implementa la interfaz java.rmi.Remote. Los nombres de clase en el comando rmic deben ser para clases que se compilaron correctamente con el comando javac y deben estar completamente cualificados por paquete. Por ejemplo, la ejecución del comando rmic en el nombre del archivo de clase HelloImpl como se muestra aquí crea el archivo HelloImpl_Stub.class en el subdirectorio hello (nombrado según el paquete de la clase):

rmic hello.HelloImpl

Un skeleton para un objeto remoto es una entidad del lado del servidor del protocolo JRMP que tiene un método que distribuye llamadas a la implementación del objeto remoto.

Un tie para un objeto remoto es una entidad del lado del servidor similar a un skeleton, pero se comunica con el cliente utilizando el protocolo IIOP.

Un stub es un proxy del lado del cliente para un objeto remoto que es responsable de comunicar las invocaciones de métodos en objetos remotos al servidor donde reside la implementación real del objeto remoto. Por lo tanto, una referencia de cliente a un objeto remoto es en realidad una referencia a un stub local.

Por defecto, el comando rmic genera clases stub que utilizan solo la versión 1.2 del protocolo de stub JRMP, como si se especificara la opción -v1.2. La opción -vcompat era la predeterminada en versiones anteriores a la 5.0. Utilice la opción -iiop para generar clases stub y tie para el protocolo IIOP. Ver Opciones.

Un stub implementa solo las interfaces remotas, y no ninguna de las interfaces locales que el objeto remoto también implementa. Dado que un stub JRMP implementa el mismo conjunto de interfaces remotas que el objeto remoto, un cliente puede utilizar los operadores integrados del lenguaje de programación Java para la conversión de tipos y la comprobación de tipos. Para IIOP, se debe utilizar el método PortableRemoteObject.narrow.

OPCIONES

-bootclasspath ruta

Anula la ubicación de los archivos de clase de arranque.
-classpath ruta

Especifica la ruta que utiliza el comando rmic para buscar clases. Esta opción anula la predeterminada o la variable de entorno CLASSPATH cuando está establecida. Los directorios están separados por dos puntos. El formato general para la ruta es: .:<tu_ruta>, por ejemplo: .:/usr/local/java/classes.
-d directorio

Especifica el directorio de destino raíz para la jerarquía de clases generada. Puede utilizar esta opción para especificar un directorio de destino para los archivos de stub, skeleton y tie. Por ejemplo, el siguiente comando coloca las clases de stub y skeleton derivadas de MyClass en el directorio /java/classes/exampleclass. 
rmic -d /java/classes exampleclass.MyClass

Si no se especifica la opción -d, el comportamiento predeterminado es como si se especificara -d .. La jerarquía de paquetes de la clase de destino se crea en el directorio actual y los archivos de stub/tie/skeleton se colocan dentro de ella. En algunas versiones anteriores del comando rmic, si no se especificaba la opción -d, la jerarquía de paquetes no se creaba y todos los archivos de salida se colocaban directamente en el directorio actual.

-extdirs ruta

Anula la ubicación de las extensiones instaladas.
-g

Habilita la generación de toda la información de depuración, incluidas las variables locales. Por defecto, solo se genera información de números de línea.
-idl

Hace que el comando rmic genere OMG IDL para las clases especificadas y cualquier clase referenciada. IDL proporciona una forma puramente declarativa e independiente del lenguaje de programación de especificar una API para un objeto. El IDL se utiliza como especificación para métodos y datos que se pueden escribir y llamar desde cualquier lenguaje que proporcione enlaces CORBA. Esto incluye Java y C++ entre otros. Ver Java IDL: Mapeo del lenguaje IDL a Java en http://docs.oracle.com/javase/8/docs/technotes/guides/idl/mapping/jidlMapping.html

Cuando se utiliza la opción -idl, otras opciones también incluyen:

•
Las opciones -always o -alwaysgenerate fuerzan la regeneración incluso cuando los stubs/ties/IDL existentes son más recientes que la clase de entrada.
•
La opción -factory utiliza la palabra clave factory en el IDL generado.
•
-idlModule de JavaPackage[.class]aIDLModule especifica el mapeo del paquete IDLEntity, por ejemplo: -idlModule my.module my::real::idlmod.
•
-idlFiledeJavaPackage[.class] aIDLFile especifica el mapeo de archivos IDLEntity, por ejemplo: -idlFile test.pkg.X TEST16.idl.
-iiop

Hace que el comando rmic genere clases stub y tie IIOP, en lugar de clases stub y skeleton JRMP. Una clase stub es un proxy local para un objeto remoto y es utilizada por los clientes para enviar llamadas a un servidor. Cada interfaz remota requiere una clase stub, que implementa esa interfaz remota. Una referencia de cliente a un objeto remoto es una referencia a un stub. Las clases tie se utilizan en el lado del servidor para procesar llamadas entrantes y distribuir las llamadas a la clase de implementación adecuada. Cada clase de implementación requiere una clase tie.

Si llama al comando rmic con -iiop, genera stubs y ties que se ajustan a esta convención de nombres:

_<nombreImplementacion>_stub.class
_<nombreInterfaz>_tie.class
•
Cuando utiliza la opción -iiop, otras opciones también incluyen:
•
Las opciones -always o -alwaysgenerate fuerzan la regeneración incluso cuando los stubs/ties/IDL existentes son más recientes que la clase de entrada.
•
La opción -nolocalstubs significa no crear stubs optimizados para clientes y servidores del mismo proceso.
•
La opción -noValueMethods debe usarse con la opción -idl. La opción -noValueMethods evita la adición de métodos y inicializadores valuetype al IDL emitido. Estos métodos e inicializadores son opcionales para los valuetypes, y se generan a menos que se especifique la opción -noValueMethods con la opción -idl.

NOMBRE

rmic - Compilador de interfaces remotas de Java

SINOPSIS

rmic [OPCIONES] clase...

DESCRIPCIÓN

El compilador de interfaces remotas de Java (rmic) genera código dependiente de la plataforma de stub y skeleton. La rmic está obsoleta y ya no es necesaria para el desarrollo de aplicaciones que utilizan las API de Java para la invocación de métodos remotos (RMI).

En el pasado, la rmic se utilizaba para generar las siguientes clases:

  • Stub: Una clase cliente que actúa como un proxy para un objeto remoto. El cliente invoca métodos en el stub, que luego serializa la llamada al método y la envía al objeto remoto.
  • Skeleton: Una clase servidor que recibe llamadas a métodos remotos de los stubs cliente, deserializa la llamada, invoca el método en el objeto remoto y luego serializa el resultado o la excepción y lo envía de vuelta al stub cliente.
  • Tie: Una clase opcional que permite que un objeto remoto implemente varias interfaces remotas.

Los desarrolladores de aplicaciones que utilizan las API de Java para RMI no necesitan invocar explícitamente rmic. El proceso de compilación de RMI se maneja automáticamente mediante el uso de las clases stub y skeleton generadas por el compilador javac.

Para las versiones de JDK anteriores a la 5.0, la rmic era necesaria para generar clases de stub y skeleton. A partir de la versión 5.0, rmic sigue estando disponible pero ya no es necesaria. Las versiones posteriores de las API de Java para RMI manejan la generación de código stub y skeleton de forma nativa.

El Portable Object Adapter (POA) define el tipo nativo Servant. En el lenguaje de programación Java, el tipo Servant se mapea a la clase Java org.omg.PortableServer.Servant. Sirve como clase base para todas las implementaciones de servant POA y proporciona una serie de métodos que pueden ser llamados por el programador de la aplicación, y métodos que son llamados por la POA y que pueden ser sobrescritos por el usuario para controlar aspectos del comportamiento del servant. Basado en la Especificación de Mapeo de Lenguaje IDL a Java de OMG, CORBA V 2.3.1 ptc/00-01-08.pdf.

OPCIONES

-J

Utilizado con cualquier comando Java, la opción -J pasa el argumento que sigue a -J (sin espacios entre -J y el argumento) al intérprete de Java.
-keep o -keepgenerated

Conserva los archivos fuente .java generados para las clases stub, skeleton y tie y los escribe en el mismo directorio que los archivos .class.
-nowarn

Desactiva las advertencias. Cuando se utiliza la opción -nowarn. El compilador no imprime ninguna advertencia.
-nowrite

No escribe las clases compiladas en el sistema de archivos.
-vcompat (obsoleto)

Genera clases stub y skeleton que son compatibles con las versiones de protocolo de stub JRMP 1.1 y 1.2. Esta opción era el valor predeterminado en versiones anteriores a la 5.0. Las clases stub generadas utilizan el protocolo de stub versión 1.1 cuando se cargan en una máquina virtual JDK 1.1 y utilizan el protocolo de stub versión 1.2 cuando se cargan en una máquina virtual 1.2 (o posterior). Las clases skeleton generadas admiten ambas versiones del protocolo de stub 1.1 y 1.2. Las clases generadas son relativamente grandes para admitir ambos modos de operación. Nota: Esta opción ha sido obsoleta. Ver Descripción.
-verbose

Hace que el compilador y el enlazador impriman mensajes sobre qué clases se están compilando y qué archivos de clase se están cargando.
-v1.1 (obsoleto)

Genera clases stub y skeleton solo para la versión del protocolo de stub JRMP 1.1. La opción -v1.1 solo es útil para generar clases stub que son compatibles con la serialización con clases stub preexistentes, desplegadas estáticamente que fueron generadas por el comando rmic desde JDK 1.1 y que no se pueden actualizar (y no se está utilizando la carga dinámica de clases). Nota: Esta opción ha sido obsoleta. Ver Descripción.
-v1.2 (obsoleto)

(Predeterminado) Genera clases stub solo para la versión del protocolo de stub JRMP 1.2. No se generan clases skeleton porque las clases skeleton no se utilizan con la versión del protocolo de stub 1.2. Las clases stub generadas no funcionan cuando se cargan en una máquina virtual JDK 1.1. Nota: Esta opción ha sido obsoleta. Ver Descripción.

VARIABLES DE ENTORNO

CLASSPATH
Se utiliza para proporcionar al sistema una ruta a las clases definidas por el usuario. Los directorios están separados por dos puntos, por ejemplo: .:/usr/local/java/classes.
