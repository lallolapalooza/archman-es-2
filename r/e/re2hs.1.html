NOMBRE

re2hs - genera analizadores léxicos rápidos para Haskell

SINOPSIS

re2hs [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para la entrada estándar.

INTRODUCCIÓN

re2hs funciona como un preprocesador. Lee el archivo de entrada (que suele ser un programa en Haskell, pero puede ser cualquier cosa) y busca bloques de código encerrados entre marcadores especiales de inicio/fin. El texto fuera de estos bloques se copia literalmente al archivo de salida. El contenido de los bloques es procesado por re2hs. Los traduce a código en Haskell y emite el código generado en lugar del bloque.

Aquí hay un ejemplo de un pequeño programa que comprueba si una cadena dada contiene un número decimal:

-- re2hs $INPUT -o $OUTPUT -i
{-# LANGUAGE OverloadedStrings #-}
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
import Data.ByteString (ByteString, index)
data State = State {
    _yyinput :: ByteString,
    _yycursor :: Int
}
%{
    re2c:YYFN = ["lexer;Bool", "State{..};State"];
    re2c:yyfill:enable = 0;
    [1-9][0-9]* { True }
    *           { False }
%}
main :: IO ()
main = case lexer State{_yyinput = "1234\0", _yycursor = 0} of
    True -> return ()
    False -> error "lexer failed!"

En la salida, re2hs reemplazó el bloque del medio con el código generado:

-- Generado por re2hs
{-# LANGUAGE RecordWildCards #-}
-- re2hs $INPUT -o $OUTPUT -i
{-# LANGUAGE OverloadedStrings #-}
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
import Data.ByteString (ByteString, index)
data State = State {
    _yyinput :: ByteString,
    _yycursor :: Int
}
yy0 :: State -> Bool
yy0 State{..} =
    let yych = index _yyinput _yycursor in
    let __ = _yycursor + 1 in let _yycursor = __ in
    case yych of
        _c | 0x31 <= _c && _c <= 0x39 ->
            yy2 State{..}
        _c | True ->
            yy1 State{..}
yy1 :: State -> Bool
yy1 State{..} =
    False
yy2 :: State -> Bool
yy2 State{..} =
    let yych = index _yyinput _yycursor in
    case yych of
        _c | 0x30 <= _c && _c <= 0x39 ->
            let __ = _yycursor + 1 in let _yycursor = __ in
            yy2 State{..}
        _c | True ->
            yy3 State{..}
yy3 :: State -> Bool
yy3 State{..} =
    True
lexer :: State -> Bool
lexer State{..} =
    yy0 State{..}
main :: IO ()
main = case lexer State{_yyinput = "1234\0", _yycursor = 0} of
    True -> return ()
    False -> error "lexer failed!"

BASES

Un programa re2hs consiste en una secuencia de bloques intercalados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresión-regular ;
Una definición asocia nombre con expresión-regular. Los nombres pueden contener caracteres alfanuméricos y guiones bajos. La sección de expresiones regulares proporciona una visión general de la sintaxis de re2hs para expresiones regulares. Una vez definido, el nombre puede usarse en otras expresiones regulares y en reglas. La recursión en definiciones con nombre no está permitida, y cada nombre debe definirse antes de usarse. Un bloque hereda las definiciones con nombre del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite cambiar el comportamiento de re2hs y personalizar el código generado. Para una lista completa de configuraciones admitidas por re2hs, consulte la sección de configuraciones. Dependiendo de una configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista en caracteres alfanuméricos. Un bloque hereda las configuraciones del ámbito global y puede redefinirlas o añadir nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final del mismo.
expresión-regular código
Una regla asocia una expresión-regular con su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en una nueva línea seguida de cualquier carácter que no sea un espacio en blanco). Si la expresión-regular coincide, se ejecuta el código asociado. Si coinciden varias reglas, la coincidencia más larga tiene prioridad. Si varias reglas coinciden con la misma cadena, la primera tiene prioridad. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse, tiene la menor prioridad independientemente de su lugar en el bloque, y coincide con cualquier unidad de código (no necesariamente un carácter válido, consulte la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para manejar el fin de entrada. Con las condiciones de inicio, las reglas tienen una sintaxis más compleja.
!acción código
Una acción asocia un bloque de código definido por el usuario con un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas asocian código con los estados finales). Consulte la sección de acciones para obtener una lista completa de acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias especiales predefinidas. Cada directiva tiene un propósito único. Consulte la sección de directivas para obtener más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (se admiten ambos estilos). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que les permiten ser referenciados en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2hs compila las expresiones regulares asociadas con cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se añaden al ámbito global y se vuelven visibles para los bloques subsiguientes. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera código por sí mismo, ni añade definiciones al ámbito global; está destinado a ser reutilizado en otros bloques. Esta es una forma de compartir código (más detalles en la sección de bloques reutilizables). Antes de la versión 2.2 de re2hs, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2hs busca bloques de reglas con este nombre. De lo contrario, se utiliza el bloque de reglas más reciente (ya sea con nombre o sin nombre). Un bloque de uso puede añadir sus propias definiciones, configuraciones y reglas, que se añaden a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2hs, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macrodefinición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Se puede personalizar con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXFILL.

%{YYMAXNMATCH[:<name1>[:<name2>...]] ... %}
Un bloque que genera la definición YYMAXNMATCH (requiere la opción -P --posix-captures). Una lista opcional de nombres de bloques especifica cuáles bloques se incluirán al calcular el valor de YYMAXNMATCH (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macro-definición para C (#define YYMAXNMATCH <n>), o una variable global para Go (var YYMAXNMATCH int = <n>). Puede personalizarse con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para acortar) se reemplaza con el valor numérico de YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ o %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Bloques que especifican una pieza de código de plantilla que se expande para cada variable de etiqueta s/etiqueta m generada por re2hs. Una lista opcional de nombres de bloques especifica cuáles bloques se incluirán al calcular el conjunto de variables de etiqueta (si la lista está vacía, se incluyen todos los bloques). Hay dos configuraciones opcionales: format y separator. La configuración format especifica una cadena de plantilla donde @@{tag} (o @@ para acortar) se reemplaza con el nombre de cada variable de etiqueta. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes variables de etiqueta.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ o %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Bloques que especifican una pieza de código de plantilla que se expande para cada etiqueta s/etiqueta m que se menciona explícitamente en las reglas (con la opción --tags) o se genera implícitamente por re2hs (con las opciones --captvars o --posix-captvars). Una lista opcional de nombres de bloques especifica cuáles bloques se incluirán al calcular el conjunto de etiquetas (si la lista está vacía, se incluyen todas las etiquetas). Hay dos configuraciones opcionales: format y separator. La configuración format especifica una cadena de plantilla donde @@{tag} (o @@ para acortar) se reemplaza con el nombre de cada etiqueta. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes etiquetas.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ o %{getstate[:<name1>[:<name2>...]] ... %}
Un bloque que genera un dispatch condicional en el estado del lexer (requiere la opción --storable-state). Una lista opcional de nombres de bloques especifica cuáles bloques se incluirán en el dispatch de estado. La transición por defecto va a la etiqueta de inicio del primer bloque de la lista. Si la lista está vacía, se incluyen todos los bloques, y la transición por defecto va al primer bloque del archivo que tiene una etiqueta de inicio. Este tipo de bloque es incompatible con la opción --loop-switch, ya que requiere transiciones entre bloques que no son compatibles sin goto o llamadas a funciones.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ o %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
Un bloque que genera la enumeración de condiciones (requiere la opción --conditions). Una lista opcional de nombres de bloques especifica cuáles bloques se incluirán al calcular el conjunto de condiciones (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una enumeración YYCONDTYPE. Puede personalizarse con las configuraciones opcionales format y separator. La configuración format especifica una cadena de plantilla donde @@{cond} (o @@ para acortar) se reemplaza con el nombre de cada condición, y @@{num} se reemplaza con un índice numérico de esa condición. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes condiciones.
/*!include:re2c <file> */ o %{include <file> %}
Este bloque permite incluir <file>, que debe ser una ruta de archivo entre comillas dobles. El contenido del archivo se sustituye literalmente en lugar del bloque, de la misma manera que funciona #include en C/C++. Este bloque se puede usar junto con la opción --depfile para generar dependencias del sistema de compilación en los archivos incluidos.
/*!header:re2c:on*/ o %{header:on %}
Este bloque marca el inicio del archivo de cabecera. Todo lo que sigue y hasta el siguiente bloque header:off es procesado por re2hs y escrito en el archivo de cabecera especificado con la opción -t --type-header.
/*!header:re2c:off*/ o %{header:off %}
Este bloque marca el final del archivo de cabecera iniciado con el bloque header:on*/.
/*!ignore:re2c ... */ o %{ignore ... %}
Un bloque cuyo contenido se ignora y se elimina del archivo de salida.

Configuraciones

Aquí hay una lista completa de las configuraciones compatibles con re2hs:

re2c:api, re2c:input
Igual que la opción --api.
re2c:api:sigil
Especifica el marcador ("sigil") que se utiliza para los marcadores de posición de argumentos en las primitivas de la API. El valor por defecto es @@. Un marcador de posición comienza con el sigil seguido del nombre del argumento entre llaves. Por ejemplo, si el sigil se establece en $, los marcadores de posición tendrán la forma ${nombre}. Las API de un solo argumento pueden usar notación abreviada sin el nombre entre llaves. Esta opción puede ser anulada por opciones para primitivas de API individuales, por ejemplo, re2c:YYFILL@len para YYFILL.
re2c:api:style
Especifica el estilo de la API. Los valores posibles son functions (el valor por defecto para C) y free-form (el valor por defecto para Go y Rust). En el estilo functions, las primitivas de la API se generan con una lista de argumentos entre paréntesis después del nombre de la primitiva. Los argumentos se proporcionan solo para parámetros autogenerados (como el número de caracteres pasados a YYFILL), pero no para el contexto general del lexer, por lo que las primitivas se comportan más como macros en C/C++ o closures en Go y Rust. En el estilo free-form, las primitivas de la API no tienen una forma fija: deben definirse como cadenas que contienen piezas de código de forma libre con variables interpoladas de la forma @@{var} o @@ (corresponden a argumentos en estilo similar a funciones). Esta configuración puede ser anulada para primitivas de API individuales, ver por ejemplo la configuración re2c:YYFILL:naked para YYFILL.

Especifica el nombre de la etiqueta opcional que sigue al interruptor YYGETSTATE en el modo de estado almacenable (habilitado con re2c:state:nextlabel). El valor por defecto es yyNext.

Obsoleto (ver la opción obsoleta --no-lookahead).

Igual que la opción --tags, pero se puede configurar por bloque.
re2c:tags:expression
Especifica la expresión utilizada para las variables de etiqueta. Por defecto, re2hs genera expresiones de la forma yyt<N>. Esto puede ser inconveniente, por ejemplo, si las variables de etiqueta se definen como campos en una estructura. Todas las ocurrencias de @@{tag} o @@ se reemplazan con el nombre real de la etiqueta. Por ejemplo, re2c:tags:expression = "s.@@"; resulta en expresiones de la forma s.yyt<N> en el código generado. Ver también la configuración re2c:api:sigil.
re2c:tags:negative
Especifica la expresión constante que se utiliza para el valor negativo de la etiqueta (típicamente sería -1 si las etiquetas son desplazamientos enteros en la cadena de entrada, o un puntero nulo si son punteros).
re2c:tags:prefix
Especifica el prefijo para los nombres de las variables de etiqueta. El valor por defecto es yyt.
re2c:sentinel
Especifica el símbolo centinela utilizado para las comprobaciones de fin de entrada (cuando las comprobaciones de límites están deshabilitadas con re2c:yyfill:enable = 0; y re2c:eof no está establecido). Esta configuración no afecta la generación de código: su propósito es verificar que el centinela no esté permitido en medio de una regla y asegurar que el lexer no lea más allá del final del búfer. El valor por defecto es -1` (en ese caso re2hs asume que el centinela es cero, que es el caso más común). Solo se reconocen números decimales.
re2c:state:abort
Si se establece en un valor entero positivo, el caso predeterminado en el despacho de estado generado aborta la ejecución del programa, y un caso explícito de -1 contiene una transición al inicio del bloque.
re2c:state:nextlabel

Alternativamente, se puede usar re2c:label:start para generar una etiqueta de inicio específica, o un bloque getstate explícito para generar el interruptor YYGETSTATE por separado del bloque lexer.

Acciones

Aquí tienes una lista de acciones predefinidas compatibles con re2hs:

!entry code
La acción de entrada vincula un bloque de code definido por el usuario al estado de inicio de la máquina de estados finitos actual. Si se utilizan condiciones de inicio, la acción de entrada se puede establecer individualmente para cada condición. Esta acción se puede utilizar para realizar inicializaciones, por ejemplo, para guardar la ubicación de inicio de un lexema.
!pre_rule code
La acción pre-regla antepone un bloque de code definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para factorizar la parte común de todas las acciones semánticas (por ejemplo, guardar la ubicación final de un lexema).
!post_rule code
La acción post-regla anexa un bloque de code definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para emitir sentencias de trampa que protejan contra flujos de control no deseados.

Directivas

Aquí tienes una lista completa de las directivas compatibles con re2hs:

!use:name ;
Una directiva de uso dentro de un bloque que fusiona un bloque de reglas definido previamente con el nombre especificado en el bloque actual. Las definiciones con nombre, las configuraciones y las reglas del bloque referenciado se añaden a las actuales. Los conflictos entre reglas y configuraciones superpuestas se resuelven de la manera habitual: la primera regla tiene prioridad y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y <!> para las cuales una definición local del bloque siempre tiene prioridad. Una directiva de uso se puede colocar en cualquier lugar dentro de un bloque, y se permiten múltiples directivas de uso.
!include file ;
Esta directiva es la misma que el bloque include: inserta el contenido de file literalmente en lugar de la directiva.

Interfaz del programa

El código generado interactúa con el programa exterior con la ayuda de primitivas, denominadas colectivamente API. Qué primitivas deben definirse para un programa en particular depende de múltiples factores, incluida la complejidad de las expresiones regulares, la representación de la entrada, el almacenamiento en búfer y el uso de varias funciones. Todas las primitivas necesarias deben ser definidas por el usuario en forma de macros, funciones, variables o cualquier otra forma adecuada que haga que el código generado sea sintáctica y semánticamente correcto. re2hs no comprueba (y no puede comprobar) las definiciones, por lo que si falta algo o está definido incorrectamente, el programa generado puede tener errores de compilación o de tiempo de ejecución. Este manual proporciona ejemplos de definiciones de API en los casos más comunes.

re2hs tiene dos sabores de API que definen el conjunto central de primitivas utilizadas por un programa:

API de Registro
La API de registro es la API predeterminada para el backend de Haskell. Esta API consiste en una vinculación yyrecord (el nombre se puede anular con re2c:yyrecord) que debe definirse como un registro con los campos _yyinput, _yycursor, _yymarker, _yyctxmarker, _yylimit. Solo los campos utilizados por el código generado deben definirse, y sus nombres se pueden configurar.
API Genérica
Esta es la API más flexible. Se habilita con la opción --api generic o la configuración re2c:api = generic. Contiene primitivas para operaciones genéricas: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYCOPYSTAG, YYCOPYMTAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Aquí tienes una lista completa de las primitivas de la API que pueden ser utilizadas por el código generado para interactuar con el programa exterior.

YYCTYPE
El tipo de los caracteres de entrada (unidades de código). Para codificaciones ASCII, EBCDIC y UTF-8 debe ser un entero sin signo de 1 byte. Para UTF-16 o UCS-2 debe ser un entero sin signo de 2 bytes. Para UTF-32 debe ser un entero sin signo de 4 bytes.
YYCURSOR
Un l-valor que almacena la posición actual de entrada (un puntero o un desplazamiento entero en YYINPUT). Inicialmente, YYCURSOR debe apuntar al primer carácter de entrada, y más tarde es avanzado por el código generado. Cuando una regla coincide, la posición de YYCURSOR es la que está después del último carácter coincidente.
YYLIMIT
Un r-valor que almacena la posición del final de la entrada (un puntero o un desplazamiento entero en YYINPUT). Inicialmente, YYLIMIT debe apuntar a la posición después del último carácter de entrada disponible. No es modificado por el código generado. El lexer compara YYCURSOR con YYLIMIT para determinar si quedan suficientes caracteres de entrada.
YYMARKER
Un l-valor que almacena la posición de la última coincidencia de regla (un puntero o un desplazamiento entero en YYINPUT). Se utiliza para restaurar la posición de YYCURSOR si la coincidencia más larga falla y el lexer necesita retroceder. No se necesita inicialización.
YYCTXMARKER
Un l-valor que almacena la posición del contexto de cola (un puntero o un desplazamiento entero en YYINPUT). No se necesita inicialización. YYCTXMARKER solo es necesario si se utiliza el operador lookahead /.
YYFILL
Una primitiva de API genérica con una variable len. YYFILL debe proporcionar al menos len caracteres de entrada más o fallar. Si se utiliza re2c:eof, entonces len es siempre 1 y YYFILL siempre debe devolver el control a la función que llama; un valor de retorno cero indica éxito. Si no se utiliza re2c:eof, el valor de retorno de YYFILL se ignora y no debe devolver en caso de fallo. El valor máximo de len es YYMAXFILL.
YYFN
Una primitiva que define el prototipo de la función en el modelo de código --recursive-functions. Su valor debe ser un array de una o más cadenas, donde cada cadena contiene dos o tres componentes separados por la cadena especificada en la configuración re2c:fn:sep (normalmente un punto y coma). El primer elemento del array define el nombre de la función y el tipo de retorno (vacío para una función void). Los elementos subsiguientes definen los argumentos de la función: primero, la expresión para el argumento utilizado en el cuerpo de la función (generalmente solo un nombre); segundo, el tipo del argumento; tercero, un parámetro formal opcional (por defecto es el primer componente; generalmente tanto el argumento como el parámetro son el mismo identificador).

Habilita la extracción de subcoincidencias con grupos de captura codiciosos de izquierda a derecha. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla de coincidencia.
--captvars, --leftmost-captvars
Habilita la extracción de subcoincidencias con grupos de captura codiciosos de izquierda a derecha. El resultado se recopila en las variables yytl<k>, yytr<k> para el grupo de captura k.
--case-insensitive
Trata las cadenas entre comillas simples y dobles como si no distinguieran entre mayúsculas y minúsculas.
--case-inverted
Invierte el significado de las cadenas entre comillas simples y dobles: trata las cadenas entre comillas simples como sensibles a mayúsculas y minúsculas y las cadenas entre comillas dobles como insensibles a mayúsculas y minúsculas.
--case-ranges
Colapsa casos consecutivos en una sentencia switch en un rango de la forma low ... high. Esta sintaxis es una extensión del lenguaje C/C++ que es compatible con compiladores como GCC, Clang y Tcc. La principal ventaja sobre el uso de casos individuales es un código generado más pequeño y un tiempo de generación más rápido, aunque para algunos compiladores como Tcc también resulta en un tamaño de binario más pequeño.
--computed-gotos -g
Optimiza los saltos condicionales utilizando la extensión no estándar "computed goto" (que debe ser compatible con el compilador). re2hs genera tablas de saltos solo en casos complejos con muchas ramas condicionales. El umbral de complejidad se puede configurar con la configuración cgoto:threshold. Se pueden habilitar los desplazamientos relativos con la configuración cgoto:relative. Esta opción implica --bit-vectors.
--computed-gotos-relative
Similar a --computed-gotos pero genera desplazamientos relativos para las tablas de saltos en su lugar (lo que debe ser compatible con el compilador). Esta opción implica --computed-gotos.
--conditions --start-conditions -c
Habilita el soporte para "condiciones" tipo Flex: múltiples analizadores léxicos interrelacionados dentro de un bloque. Esta es una alternativa a especificar manualmente diferentes bloques re2hs conectados con goto o llamadas a funciones.
--depfile FILE
Escribe la información de dependencia en FILE en forma de una regla de Makefile <output-file> : <input-file> [include-file ...]. Esto permite rastrear las dependencias de compilación en presencia de bloques/directivas include, para que la actualización de los archivos include active la regeneración del archivo de salida. Esta opción depende de la opción --output.
--ebcdic --ecb -e
Genera un analizador léxico que lee la entrada en codificación EBCDIC. re2hs asume que el rango de caracteres es 0 -- 0xFF y el tamaño del carácter es de 1 byte.
--empty-class <match-empty | match-none | error>
Define la forma en que re2hs trata las clases de caracteres vacías. Con match-empty (el valor predeterminado) la clase vacía coincide con la entrada vacía (lo cual es ilógico, pero compatible con versiones anteriores). Con match-none la clase vacía siempre falla al coincidir. Con error la clase vacía genera un error de compilación.
--encoding-policy <fail | substitute | ignore>
Define la forma en que re2hs trata los sustitutos Unicode. Con fail re2hs aborta con un error al encontrar un sustituto. Con substitute re2hs reemplaza silenciosamente los sustitutos con el punto de código de error 0xFFFD. Con ignore (el valor predeterminado) re2hs trata los sustitutos como puntos de código normales. El estándar Unicode dice que los sustitutos independientes no son válidos, pero las bibliotecas y programas del mundo real se comportan de manera diferente.
--flex-syntax -F
Soporte parcial para la sintaxis de Flex: en este modo, las definiciones nombradas no necesitan el signo igual ni el punto y coma de terminación, y cuando se usan deben estar rodeadas por llaves. Los nombres sin llaves se tratan como cadenas entre comillas dobles.
--goto-label
Utiliza el modelo de código "goto/label": codifica el DFA en forma de bloques de código etiquetados conectados por transiciones goto entre bloques. Esto solo es compatible con lenguajes que tienen una sentencia goto.
--header --type-header -t HEADER
Genera un archivo HEADER. El contenido del archivo se puede especificar utilizando bloques especiales header:on y header:off. Si se utilizan condiciones, el encabezado generado tendrá un enum de condición agregado automáticamente (a menos que haya un bloque conditions explícito).
-I PATH
Agrega PATH a la lista de ubicaciones que se utilizan al buscar archivos include. Esta opción es útil en combinación con el bloque o directiva include. re2hs busca FILE en el directorio del archivo padre y en las ubicaciones include especificadas con la opción -I.
--input <default | custom>
Alias obsoleto para --api. La opción default corresponde a simple (es de hecho el valor predeterminado para la mayoría de los backends, pero no para todos). La opción custom corresponde a generic.
--input-encoding <ascii | utf8>
Especifica la forma en que re2hs analiza las expresiones regulares. Con ascii (el valor predeterminado) re2hs maneja la entrada como codificada en ASCII: cualquier secuencia de unidades de código es una secuencia de caracteres independientes de 1 byte. Con utf8 re2hs maneja la entrada como codificada en UTF8 y reconoce caracteres multibyte.
--invert-captures
Invierte el significado de los grupos de captura y no captura. Por defecto (...) es de captura y (! ...) no es de captura. Con esta opción (! ...) es de captura y (...) no es de captura.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Especifica el lenguaje de destino. Los lenguajes compatibles son C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (se pueden agregar más lenguajes a través de archivos de sintaxis definidos por el usuario, consulta la opción --syntax). La opción none deshabilita las configuraciones de sintaxis predeterminadas, de modo que el lenguaje de destino sea indefinido.
--location-format <gnu | msvc>
Especifica el formato de ubicación en los mensajes. Con gnu las ubicaciones se imprimen como 'filename:line:column: ...'. Con msvc las ubicaciones se imprimen como 'filename(line,column) ...'. El valor predeterminado es gnu.
--loop-switch
Utiliza el modelo de código "loop/switch": codifica el DFA en forma de un bucle sobre una sentencia switch, donde los estados individuales son casos del switch. El estado se almacena en una variable yystate. Las transiciones entre estados actualizan yystate a la etiqueta del caso del estado de destino y continúan la ejecución hasta el inicio del bucle.
--nested-ifs -s
Utiliza sentencias if anidadas en lugar de sentencias switch en los saltos condicionales. Esto generalmente resulta en un código más eficiente con compiladores que no optimizan.
--no-debug-info -i
No genera directivas de línea. Esto puede ser útil cuando el código generado se almacena en un sistema de control de versiones (para evitar grandes diferencias autogeneradas en pequeños cambios).
--no-generation-date
Suprime la salida de la fecha en el archivo generado.
--no-version
Suprime la salida de la versión en el archivo generado.
--no-unsafe
No genera un wrapper unsafe sobre YYPEEK (esta opción es específica de Rust). Por razones de rendimiento, YYPEEK debe evitar la verificación de límites, ya que el analizador léxico ya realiza comprobaciones de fin de entrada de manera más eficiente. El usuario puede optar por proporcionar una definición YYPEEK segura, o una definición que solo sea insegura en compilaciones de lanzamiento, en cuyo caso la opción --no-unsafe ayuda a evitar advertencias sobre bloques unsafe redundantes.
--output -o OUTPUT
Especifica el archivo OUTPUT.
--posix-captures, -P
Habilita la extracción de subcoincidencias con grupos de captura estilo POSIX. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla de coincidencia.
--posix-captvars
Habilita la extracción de subcoincidencias con grupos de captura estilo POSIX. El resultado se recopila en las variables yytl<k>, yytr<k> para el grupo de captura k.
--recursive-functions
Utiliza el modelo de código basado en funciones co-recursivas, donde cada estado del DFA es una función separada que puede llamar a otras funciones de estado o a sí misma.
--reusable -r
Obsoleto desde la versión 2.2 (los bloques reutilizables están permitidos por defecto ahora).
--skeleton -S
Ignora el código de interfaz definido por el usuario y genera un programa "esqueleto" autocontenido. Además, genera archivos de entrada con cadenas derivadas de la gramática regular y resultados de coincidencia comprimidos que se utilizan para verificar el comportamiento del "esqueleto" en todas las entradas. Esta opción es útil para encontrar errores en optimizaciones y generación de código. Esta opción solo es compatible con C.
--storable-state -f
Genera un analizador léxico que puede almacenar su estado interno. Esto es útil en analizadores léxicos de modelo push que son detenidos por un pro externo

Enable context-sensitive lexing. This option is useful for lexing languages with complex syntax, such as XML or HTML.

Count characters instead of bytes. This option is useful for lexing variable-length character encodings, such as UTF-8.

Enable debug mode. This option is useful for debugging the lexer. When debug mode is enabled, the lexer will output debugging information to the standard error stream.

Enable default skip mode. In this mode, the lexer skips all characters that are not matched by any rule. This option is useful for lexing languages with a lot of whitespace or comments.

--eof-action
Enable EOF action. This option is useful for handling end-of-file conditions.

"Fixed" tags are those that are located within a fixed distance to some other tag (called "base"). In such cases only the base tag needs to be tracked, and the value of the fixed tag can be computed as the value of the base tag plus a static offset. -j

Internal option: DFA minimization algorithm used by re2hs. The moore option is the Moore algorithm (it is the default). The table option is the "table filling" algorithm. Both algorithms should produce the same DFA up to states relabeling; table filling is simpler and much slower and serves as a reference implementation.
--eager-skip
Internal option: make the generated lexer advance the input position eagerly -- immediately after reading the input symbol. This changes the default behavior when the input position is advanced lazily -- after transition to the next state.
--no-lookahead
Internal option, deprecated. It used to enable TDFA(0) algorithm. Unlike TDFA(1), TDFA(0) algorithm does not use one-symbol lookahead. It applies register operations to the incoming transitions rather than the outgoing ones. Benchmarks showed that TDFA(0) algorithm is less efficient than TDFA(1).
--no-optimize-tags
Internal option: suppress optimization of tag variables (useful for debugging).

Internal option: specify shortest-path algorithm used for the construction of epsilon-closure with POSIX disambiguation semantics: gor1 (the default) stands for Goldberg-Radzik algorithm, and gtop stands for "global topological order" algorithm.

Internal option: specify the algorithm used to compute POSIX precedence table. The complex algorithm computes precedence table in one traversal of tag history tree and has quadratic complexity in the number of TNFA states; it is the default. The naive algorithm has worst-case cubic complexity in the number of TNFA states, but it is much simpler than complex and may be slightly faster in non-pathological cases.
--stadfa
Internal option, deprecated. It used to enable staDFA algorithm, which differs from TDFA in that register operations are placed in states rather than on transitions. Benchmarks showed that staDFA algorithm is less efficient than TDFA.
--fixed-tags <none | toplevel | all>
Internal option: specify whether the fixed-tag optimization should be applied to all tags (all), none of them (none), or only those in toplevel concatenation (toplevel). The default is all. For tags that are under alternative or repetition it is also necessary to check if the base tag has a no-match value (in that case fixed tag should also be set to no-match, disregarding the offset). For tags in top-level concatenation the check is not needed, because they always match.

Warnings

Warnings can be invividually enabled, disabled and turned into an error.

-W
Turn on all warnings.
-Werror
Turn warnings into errors. Note that this option alone doesn't turn on any warnings; it only affects those warnings that have been turned on so far or will be turned on later.
-W<warning>
Turn on warning.
-Wno-<warning>
Turn off warning.
-Werror-<warning>
Turn on warning and treat it as an error (this implies -W<warning>).
-Wno-error-<warning>
Don't treat this particular warning as an error. This doesn't turn off the warning itself.
-Wcondition-order
Warn if the generated program makes implicit assumptions about condition numbering. One should use either --header option or conditions block to generate a mapping of condition names to numbers and then use the autogenerated condition names.
-Wempty-character-class
Warn if a regular expression contains an empty character class. Trying to match an empty character class makes no sense: it should always fail. However, for backwards compatibility reasons re2hs permits empty character classes and treats them as empty strings. Use the --empty-class option to change the default behavior.

Warn if a rule is nullable (matches an empty string). If the lexer runs in a loop and the empty match is unintentional, the lexer may unexpectedly hang in an infinite loop.

Warn if the lower bound of a range is greater than its upper bound. The default behavior is to silently swap the range bounds.

Advertencias

Las siguientes advertencias están disponibles:

-Wempty-rules
Advertir sobre reglas vacías (reglas que nunca coinciden).
-Wdefault-rule-is-empty
Advertir si la regla predeterminada (la última regla en un conjunto de reglas con el mismo nombre) está vacía. El comportamiento de re2c es actualmente el de ignorar silenciosamente las reglas vacías, pero esto puede indicar un error tipográfico o una regla no utilizada. Esta advertencia se establecerá como un error si la directiva de configuración re2c:api:empty-rule:error está habilitada.
-Wtrailing-condition
Advertir sobre condiciones finales de entrada sin usar. Estas son advertencias que solo se generan en el modo de depuración de re2c y solo si se utiliza la opción de línea de comandos -d.
-Wfallthrough-condition
Advertir sobre la falta de una condición de continuación de entrada en condiciones finales de entrada. Las condiciones finales de entrada (finales de línea o finales de entrada) pueden ser seguidas por condiciones de continuación de entrada (similares a las reglas normales de re2c), o pueden ser seguidas por el final de una regla.
-Wempty-semantics
Advertir sobre semánticas vacías. Las semánticas vacías no producen ningún código y el analizador de re2c las ignora silenciosamente. Sin embargo, esto puede indicar un error tipográfico o una semántica no utilizada. Esta advertencia se establecerá como un error si la directiva de configuración re2c:semantics:empty:error está habilitada.
-Wempty-body
Advertir sobre cuerpos de reglas vacíos. Un cuerpo de regla vacío no tiene acciones y, por lo tanto, no consume ninguna unidad de código.
-Wunreachable-rules
Advertir sobre reglas que están sombreadas por otras reglas y que nunca coincidirán.
-Wdeprecated-eof_rule
Advertir sobre reglas de fin de entrada independientes $ que se verán afectadas por cambios futuros y requerirán correcciones. En este momento, estas reglas tienen precedencia cuando entran en conflicto con otras reglas, pero después de la introducción del símbolo generalizado de fin de entrada $, el orden de precedencia cambiará y estas reglas quedarán sombreadas por otras reglas.
-Wuseless-escape
Advertir si un símbolo está escapado cuando no debería. Por defecto, re2hs ignora silenciosamente tales escapes, pero esto también puede indicar un error tipográfico o un error en la secuencia de escape.
-Wnondeterministic-tags
Advertir si una etiqueta tiene un grado de n-ésimo de no determinismo, donde n es mayor que 1.
-Wsentinel-in-midrule
Advertir si el símbolo centinela ocurre en medio de una regla --- esto puede causar lecturas más allá del final del búfer, bloqueos o corrupción de memoria en el analizador léxico generado. Esta advertencia solo es aplicable si se utiliza el método centinela para verificar el final de la entrada. Se establece como un error si se utiliza la configuración re2c:sentinel.
-Wundefined-syntax-config
Advertir si el archivo de sintaxis especificado con la opción --syntax carece de definiciones para algunas configuraciones. Esto ayuda a mantener los archivos de sintaxis definidos por el usuario: si una nueva versión agrega configuraciones, el archivo de sintaxis antiguo generará una advertencia y se notificará al usuario. Si algunas configuraciones no se utilizan y no necesitan una definición, deben establecerse explícitamente en <undefined>.

Archivos de sintaxis

El soporte para diferentes lenguajes en re2c se basa en la idea de archivos de sintaxis. Un archivo de sintaxis es un archivo de configuración que define la sintaxis del lenguaje de destino, no todo el lenguaje, sino una pequeña parte de él que es utilizada por el código generado. Los archivos de sintaxis hacen que re2c sea muy flexible, pero no deben usarse como un reemplazo para las configuraciones re2c:: su propósito es definir la sintaxis del lenguaje de destino, no personalizar un analizador léxico particular. Todos los lenguajes admitidos tienen archivos de sintaxis predeterminados que forman parte de la distribución (ver el subdirectorio include/syntax); también están incrustados en el binario de re2hs. Los usuarios pueden proporcionar un archivo de sintaxis personalizado que anule algunas configuraciones para uno de los lenguajes admitidos, o pueden optar por redefinir todas las configuraciones (en ese caso, se debe usar la opción --lang none). Los archivos de sintaxis contienen configuraciones de cuatro tipos diferentes: listas de características, configuraciones de lenguaje, configuraciones "inplace" y plantillas de código.

Listas de características

Algunas configuraciones de lista definen varias características admitidas por un backend determinado, de modo que re2hs pueda generar un error claro si el usuario intenta habilitar una característica no admitida:
supported_apis
Una lista de API admitidas con elementos posibles simple, record, generic.
supported_api_styles
Una lista de estilos de API admitidos con elementos posibles functions, free-form.
supported_code_models
Una lista de modelos de código admitidos con elementos posibles goto-label, loop-switch, recursive-functions.
supported_targets
Una lista de destinos de generación de código admitidos con elementos posibles code, dot, skeleton.
supported_features
Una lista de características admitidas con elementos posibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Configuraciones de lenguaje

Algunas configuraciones booleanas describen características del lenguaje de destino que afectan al analizador y al generador de código de re2hs:
semicolons
Distinto de cero si el lenguaje utiliza punto y coma después de las sentencias.
backtick_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas invertidas.
single_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas simples.
indentation_sensitive
Distinto de cero si el lenguaje es sensible a la indentación.
wrap_blocks_in_braces
Distinto de cero si los bloques de sentencias compuestas deben estar entre llaves.

Configuraciones "inplace"

Los archivos de sintaxis definen los valores iniciales de todas las configuraciones re2c:, ya que pueden diferir para diferentes lenguajes. Consulte la sección de configuraciones para obtener una lista completa de todas las configuraciones "inplace" y su significado.

Plantillas de código

Las plantillas de código definen la sintaxis del lenguaje de destino. Están escritas en un lenguaje simple específico del dominio con la siguiente gramática formal: 
plantilla-codigo ::
      nombre '=' expresiones-codigo ';'
    | PLANTILLA_CODIGO ';'
    | '<undefined>' ';'
expresiones-codigo ::
      <VACIO>
    | expresiones-codigo expresion-codigo
expresion-codigo ::
      CADENA
    | VARIABLE
    | opcional
    | lista
opcional ::
      '(' CONDICIONAL '?' expresiones-codigo ')'
    | '(' CONDICIONAL '?' expresiones-codigo ':' expresiones-codigo ')'
lista ::
      '[' VARIABLE ':' expresiones-codigo ']'
    | '[' VARIABLE '{' NUMERO '}' ':' expresiones-codigo ']'
    | '[' VARIABLE '{' NUMERO ',' NUMERO '}' ':' expresiones-codigo ']'

Una plantilla de código es una secuencia de literales de cadena, variables, elementos opcionales y listas, o una referencia a otra plantilla de código, o un valor especial <undefined>. Las variables son marcadores de posición que se sustituyen durante la fase de generación de código. Las variables de lista son especiales: al expandir plantillas de lista, re2hs repite las expresiones del lado derecho de la columna varias veces, sustituyendo cada vez las ocurrencias de la variable de lista con un valor específico para esa repetición. Las listas tienen límites opcionales (los valores negativos se cuentan desde el final, por ejemplo, -1 significa el último elemento). Los nombres condicionales comienzan con un punto. Tanto los condicionales como las variables pueden ser locales (específicos de la plantilla de código dada) o globales (permitidos en todas las plantillas de código). Cuando re2hs lee el archivo de sintaxis, verifica que cada plantilla de código utilice solo las variables y condicionales que están permitidos en ella.

Por ejemplo, la siguiente plantilla de código define la construcción if-then-else para un lenguaje similar a C:

codigo:if_then_else =
    [rama{0}: indentacion_superior "if " cond " {" nl
        indentar [stmt: stmt] desindentar]
    [rama{1:-1}: indentacion_superior "} else" (.cond ? " if " cond) " {" nl
        indentar [stmt: stmt] desindentar]
    indentacion_superior "}" nl;

Aquí rama es una variable de lista: rama{0} se expande a la primera rama (que es especial, ya que no hay parte else), rama{1:-1} se expande a todas las ramas restantes (si las hay). stmt es también una variable de lista: [stmt: stmt] es una lista anidada que se expande a una lista de sentencias en el cuerpo de la rama actual. indentacion_superior, indentar, desindentar y nl son variables globales, y .cond es un condicional local (su significado se describe a continuación). Esta plantilla de código podría producir el siguiente código:

if x {
    // hacer algo
} else if y {
    // hacer otra cosa
} else {
    // no hacer nada
}

HANDLING THE END OF INPUT

One of the main problems for the lexer is to know when to stop. There are a few terminating conditions:

  • the lexer may match some rule (including default rule *) and come to a final state
  • the lexer may fail to match any rule and come to a default state
  • the lexer may reach the end of input

The first two conditions terminate the lexer in a "natural" way: it comes to a state with no outgoing transitions, and the matching automatically stops. The third condition, end of input, is different: it may happen in any state, and the lexer should be able to handle it. Checking for the end of input interrupts the normal lexer workflow and adds conditional branches to the generated program, therefore it is necessary to minimize the number of such checks. re2hs supports a few different methods for handling the end of input. Which one to use depends on the complexity of regular expressions, the need for buffering, performance considerations and other factors. Here is a list of methods:

  • Sentinel. This method eliminates the need for the end of input checks altogether. It is simple and efficient, but limited to the case when there is a natural "sentinel" character that can never occur in valid input. This character may still occur in invalid input, but it should not be allowed by the regular expressions, except perhaps as the last character of a rule. The sentinel is appended at the end of input and serves as a stop signal: when the lexer reads this character, it is either a syntax error or the end of input. In both cases the lexer should stop. This method is used if YYFILL is disabled with re2c:yyfill:enable = 0; and re2c:eof has the default value -1.
  • Sentinel with bounds checks. This method is generic: it allows one to handle any input without restrictions on the regular expressions. The idea is to reduce the number of end of input checks by performing them only on certain characters. Similar to the "sentinel" method, one of the characters is chosen as a "sentinel" and appended at the end of input. However, there is no restriction on where the sentinel may occur (in fact, any character can be chosen for a sentinel). When the lexer reads this character, it additionally performs a bounds check. If the current position is within bounds, the lexer resumes matching and handles the sentinel as a regular character. Otherwise it invokes YYFILL (unless it is disabled). If more input is supplied, the lexer will rematch the last character and continue as if the sentinel wasn't there. Otherwise it must be the real end of input, and the lexer stops. This method is used when re2c:eof has non-negative value (it should be set to the numeric value of the sentinel). YYFILL is optional.
  • Bounds checks with padding. This method is generic, and it may be faster than the "sentinel with bounds checks" method, but it is also more complex. The idea is to partition DFA states into strongly connected components (SCCs) and generate a single check per SCC for enough characters to cover the longest non-looping path in this SCC. This reduces the number of checks, but there is a problem with short lexemes at the end of input, as the check requires enough characters to cover the longest lexeme. This can be fixed by padding the input with a few fake characters that do not form a valid lexeme suffix (so that the lexer cannot match them). The length of padding should be YYMAXFILL, generated with a max block. If there is not enough input, the lexer invokes YYFILL which should supply at least the required number of characters or not return. This method is used if YYFILL is enabled and re2c:eof is -1 (this is the default configuration).
  • Custom checks. Generic API allows one to override basic operations like reading a character, which makes it possible to include the end-of-input checks as part of them. This approach is error-prone and should be used with caution. To use a custom method, enable generic API with --api custom or re2c:api = custom; and disable default bounds checks with re2c:yyfill:enable = 0; or re2c:yyfill:check = 0;.

The following subsections contain an example of each method.

Sentinel

This example uses a sentinel character to handle the end of input. The program counts space-separated words in a null-terminated string. The sentinel is null: it is the last character of each input string, and it is not allowed in the middle of a lexeme by any of the rules (in particular, it is not included in character ranges where it is easy to overlook). If a null occurs in the middle of a string, it is a syntax error and the lexer will match default rule *, but it won't read past the end of input or crash (use -Wsentinel-in-midrule warning and re2c:sentinel configuration to verify this). Configuration re2c:yyfill:enable = 0; suppresses the generation of bounds checks and YYFILL invocations.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad (when)
import Data.ByteString (ByteString, index)
data State = State {
    _yyinput :: ByteString,
    _yycursor :: Int,
    _count :: Int
}
-- expect a null-terminated string
%{
    re2c:YYFN = ["lexer;Int", "State{..};State"];
    re2c:yyfill:enable = 0;
    *      { (-1) }
    [\x00] { _count }
    [a-z]+ { lexer State{_count = _count + 1, ..} }
    [ ]+   { lexer State{..} }
%}
main :: IO ()
main = do
    let test s n = when (lexer st  /= n) $ error "failed"
                   where st = State{_yyinput = s, _yycursor = 0, _count = 0}
    test "\0" 0
    test "one two three\0" 3
    test "f0ur\0" (-1)

Sentinel with bounds checks

This example uses sentinel with bounds checks to handle the end of input (this method was added in version 1.2). The program counts space-separated single-quoted strings. The sentinel character is null, which is specified with re2c:eof = 0; configuration. As in the sentinel method, null is the last character of each input string, but it is allowed in the middle of a rule (for example, 'aaa\0aa'\0 is valid input, but 'aaa\0 is a syntax error). Bounds checks are generated in each state that matches an input character, but they are scoped to the branch that handles null. Bounds checks are of the form YYLIMIT <= YYCURSOR or YYLESSTHAN(1) with generic API. If the check condition is true, lexer has reached the end of input and should stop (YYFILL is disabled with re2c:yyfill:enable = 0; as the input fits into one buffer, see the YYFILL with sentinel section for an example that uses YYFILL). Reaching the end of input opens three possibilities: if the lexer is in the initial state it will match the end-of-input rule $, otherwise it may fallback to a previously matched rule (including default rule *) or go to a default state, causing -Wundefined-control-flow.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad (when)
import qualified Data.ByteString as BS
import Data.Word
data State = State {
    _yyinput :: BS.ByteString,
    _yycursor :: Int,
    _yymarker :: Int,
    _yylimit :: Int,
    _count :: Int
}
-- expect a null-terminated string
%{
    re2c:YYFN = ["lexer;Int", "State{..};State"];
    re2c:YYCTYPE = "Word8";
    re2c:YYPEEK = "BS.index";
    re2c:eof = 0;
    re2c:yyfill:enable = 0;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { (-1) }
    $    { _count }
    str  { lexer State{_count = _count + 1, ..} }
    [ ]+ { lexer State{..} }
%}
main :: IO ()
main = do
    let test s n = do
            let st = State {
                    _yyinput = s,
                    _yycursor = 0,
                    _yymarker = 0,
                    _yylimit = BS.length s - 1, -- terminating null not included
                    _count = 0}
            when (lexer st /= n) $ error "failed"
    test "\0" 0
    test "'one' 'two' 'three'\0" 3
    test "'f0ur'\0" (-1)

YYFILL with sentinel

This example uses sentinel with bounds checks and YYFILL to handle the end of input. The program counts space-separated single-quoted strings. The sentinel character is null, which is specified with re2c:eof = 0; configuration. Null is the last character of each input string, but it is allowed in the middle of a rule. Bounds checks are generated in each state that matches an input character, but they are scoped to the branch that handles null. Bounds checks are of the form YYLIMIT <= YYCURSOR or YYLESSTHAN(1) with generic API. If the check condition is true, lexer has reached the end of input and should stop. Otherwise it invokes YYFILL. YYFILL is a function that should fill the input buffer. If it returns, the lexer continues scanning. If it does not return, it means that the end of input has been reached, and the lexer must stop.

    if lim < len -1 then return st
    else do
        putStrLn "YYFILL called"
        return st {_yyinput = BS.append inp "\0", _yylimit = len}

Custom checks

This example demonstrates custom end-of-input checks using the generic API. The lexer counts space-separated words. The sentinel character is null, which is specified with re2c:eof = 0; configuration. The generic API allows overriding basic operations like reading a character. Comprobaciones de límites con relleno

Este ejemplo utiliza comprobaciones de límites con relleno para manejar el final de la entrada (este método está habilitado por defecto). El programa cuenta cadenas de un solo comillas separadas por espacios. Hay un relleno de caracteres nulos de YYMAXFILL añadidos al final de la entrada, donde el valor de YYMAXFILL se autogenera con un bloque max. No es necesario usar nulos para el relleno, se pueden usar cualquier carácter siempre que no formen un sufijo de lexema válido (en este ejemplo, el relleno no debe contener comillas simples, ya que pueden ser confundidas con un sufijo de una cadena de comillas simples). Hay una regla de "parada" que coincide con el primer carácter de relleno (nulo) y termina el lexer (tenga en cuenta que verifica si el nulo está al principio del relleno, de lo contrario, es un error de sintaxis). Las comprobaciones de límites solo se generan en algunos estados determinados por los componentes fuertemente conectados del autómata subyacente. Las comprobaciones tienen la forma (YYLIMIT - YYCURSOR) < n o YYLESSTHAN(n) con la API genérica, donde n es el número mínimo de caracteres necesarios para que el lexer continúe (también significa que la próxima comprobación de límites ocurrirá en como máximo n caracteres). Si la condición de comprobación es verdadera, el lexer ha llegado al final de la entrada e invocará YYFILL(n), que debe suministrar al menos n caracteres de entrada o no devolver nada. En este ejemplo, YYFILL siempre falla y termina el lexer con un error (lo cual está bien porque la entrada cabe en un solo búfer). Consulte la sección YYFILL con relleno para ver un ejemplo que vuelve a llenar el búfer de entrada con YYFILL.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Exception
import Control.Monad (when)
import qualified Data.ByteString as BS
data State = State {
    _yyinput :: BS.ByteString,
    _yycursor :: Int,
    _yylimit :: Int,
    _count :: Int
}
data FillException = UnexpectedFill deriving (Show)
instance Exception FillException
yymaxfill :: Int
%{max %}
%{
    re2c:YYFN  = ["lexer;IO Int", "State{..};State"];
    re2c:YYPEEK = "BS.index";
    re2c:YYFILL = "throw UnexpectedFill";
    re2c:monadic = 1; // YYFILL requiere notación do-monádica para condiciones `when`
    str = ['] ([^'\\] | [\\][^])* ['];
    [\x00] {
        -- comprueba que es el centinela, no un nulo inesperado
        return $ if _yycursor == BS.length _yyinput - yymaxfill + 1 then _count else (-1)
    }
    str  { lexer State{_count = _count + 1, ..} }
    [ ]+ { lexer State{..} }
    *    { return (-1) }
%}
main :: IO ()
main = do
    let test s n = do
            let buf = BS.concat [s, BS.replicate yymaxfill 0]
            let st = State {
                    _yyinput = buf,
                    _yycursor = 0,
                    _yylimit = BS.length buf,
                    _count = 0}
            m <- catch (lexer st) (\(_ :: FillException) -> return (-2))
            when (m /= n) $ error "failed"
    test "" 0
    test "'unterminated\\'" (-2)
    test "'qu\0tes' 'are' 'fine: \\'' " 3
    test "'unexpected' \0 'null'" (-1)

Comprobaciones personalizadas

Este ejemplo utiliza un método personalizado de manejo del fin de entrada basado en la API genérica. El programa cuenta cadenas de un solo comillas separadas por espacios. Es lo mismo que el ejemplo de centinela, excepto que la entrada no está terminada con nulo. Para compensar la ausencia de un carácter centinela al final de la entrada, YYPEEK se redefine para realizar una comprobación de límites antes de leer el siguiente carácter de entrada. Esto es ineficiente porque las comprobaciones se realizan muy a menudo. Si la condición de comprobación falla, YYPEEK devuelve el carácter real, de lo contrario, devuelve un carácter centinela falso.

import qualified Data.ByteString as BS
data State = State {
    _str :: BS.ByteString,
    _cur :: Int,
    _lim :: Int,
    _cnt :: Int
}
-- Espera una cadena sin nulo final.
%{
    re2c:api = generic;
    re2c:YYFN = ["lexer;Int", "State{..};State"];
    re2c:YYPEEK = "if _cur < _lim then BS.index _str _cur else 0";
    re2c:YYSKIP = "let cur = _cur + 1 in let _cur = cur in";

    test "f0ur" (-1)

RECARGA DE BÚFER

La necesidad de búfer surge cuando la entrada no se puede mapear en memoria a la vez: o es demasiado grande o proviene de forma secuencial (como leer de un socket). La técnica habitual en tales casos es asignar un búfer de memoria de tamaño fijo y procesar la entrada en fragmentos que quepan en el búfer. Cuando se procesa el fragmento actual, se saca y se introduce nueva información. En la práctica es algo más complejo, ya que el estado del lexer consiste no en una sola posición de entrada, sino en un conjunto de posiciones interrelacionadas:

  • cursor: el siguiente carácter de entrada a leer (YYCURSOR en la API de punteros C o YYSKIP/YYPEEK en la API genérica)
  • límite: la posición después del último carácter de entrada disponible (YYLIMIT en la API de punteros C, manejado implícitamente por YYLESSTHAN en la API genérica)
  • marcador: la posición de la coincidencia más reciente, si la hay (YYMARKER en la API predeterminada o YYBACKUP/YYRESTORE en la API genérica)
  • token: el inicio del lexema actual (implícito en la API re2hs, ya que no es necesario para la operación normal del lexer y puede ser definido y actualizado por el usuario)
  • marcador de contexto: la posición del contexto de cola (YYCTXMARKER en la API de punteros C o YYBACKUPCTX/YYRESTORECTX en la API genérica)
  • variables de etiqueta: posiciones de subcoincidencia (definidas con bloques stags y mtags y primitivas de API genérica YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

No todos estos se utilizan en todos los casos, pero si se utilizan, deben ser actualizados por YYFILL. Todas las posiciones activas están contenidas en el segmento entre el token y el cursor, por lo tanto, todo lo que esté entre el inicio del búfer y el token se puede descartar, el segmento desde el token hasta el límite debe moverse al principio del búfer, y el espacio libre al final del búfer debe rellenarse con nuevos datos. Para evitar llamadas frecuentes a YYFILL, es mejor rellenar tantos caracteres de entrada como sea posible (aunque menos caracteres podrían ser suficientes para reanudar el lexer). Los detalles de la implementación de YYFILL son ligeramente diferentes dependiendo de qué método de manejo de EOF se utilice: el caso de la regla EOF es algo más simple que el caso de la comprobación de límites con relleno. Tenga en cuenta también que si se utiliza la opción -f --storable-state, YYFILL tiene una semántica ligeramente diferente (descrita en la sección sobre estado almacenable).

YYFILL con centinela

Si se utiliza la regla EOF, YYFILL es una primitiva similar a una función que no acepta argumentos y devuelve un valor que se compara con cero. La invocación de YYFILL se activa mediante la condición YYLIMIT <= YYCURSOR en la API de punteros C y YYLESSTHAN() en la API genérica. Un valor de retorno distinto de cero significa que YYFILL ha fallado. Una llamada exitosa a YYFILL debe suministrar al menos un carácter y ajustar las posiciones de entrada en consecuencia. El límite siempre debe establecerse en uno después de la última posición de entrada en el búfer, y el carácter en la posición límite debe ser el símbolo centinela especificado por la configuración re2c:eof. %{
    re2c:YYFN = ["lexer;IO Int", "State{..};State;!State{..}"];

El código que re2hs genera para las condiciones depende de si re2hs utiliza el enfoque de goto/etiqueta o el enfoque de bucle/switch para codificar los autómatas.

En lenguajes que tienen la instrucción goto (como C/C++ y Go) las condiciones se implementan naturalmente como bloques de código precedidos por etiquetas del tipo yyc_<cond>, donde cond es un nombre de condición (el prefijo de etiqueta se puede cambiar con re2c:cond:prefix). Las transiciones entre condiciones se implementan usando goto y etiquetas de condición. Antes de todas las condiciones, re2hs genera un switch inicial sobre YYGETSTATE que salta al estado inicial de la condición actual. Las reglas de acceso directo :=> evitan el switch inicial y saltan directamente a la condición especificada (se puede usar re2c:cond:goto para cambiar el comportamiento por defecto). Las reglas con acciones semánticas no saltan automáticamente a la siguiente condición; esto debe ser hecho por el código de acción definido por el usuario.

En lenguajes que no tienen goto (como Rust) re2hs reutiliza la variable yystate para almacenar los números de condición. Cada condición obtiene un identificador numérico igual al número de su estado de inicio, y un switch entre condiciones no es diferente de un switch entre estados DFA de una sola condición. No hay necesidad de un switch de condición inicial separado. Estado almacenable

Con la opción --storable-state re2hs genera un analizador léxico que puede almacenar su estado actual, devolver el control al llamador y, posteriormente, reanudar las operaciones exactamente donde las dejó. El modo de operación por defecto en re2hs es un modelo de "pull" (tirar), en el que el analizador léxico "tira" de más entrada cuando la necesita. Esto puede ser inaceptable en casos en los que la entrada se presenta pieza por pieza (por ejemplo, si el analizador léxico es invocado por el analizador sintáctico, o si el programa analizador léxico se comunica a través de un protocolo de socket con algún otro programa que debe esperar una respuesta del analizador léxico antes de transmitir el siguiente mensaje). La característica de estado almacenable está pensada precisamente para tales casos: permite generar analizadores léxicos que funcionan en un modelo de "push" (empujar). Cuando el analizador léxico necesita más entrada, almacena su estado y devuelve el control al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el analizador léxico exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo de "pull":

  • Definir las primitivas YYSETSTATE() y YYGETSTATE(state).
  • Definir las variables yych, yyaccept (si se usa) y state como parte del estado persistente del analizador léxico. La variable state debe inicializarse a -1.
  • YYFILL debe devolver el control al programa externo en lugar de intentar proporcionar más entrada. El código de retorno debe indicar que el analizador léxico necesita más entrada.
  • El programa externo debe reconocer las situaciones en las que el analizador léxico necesita más entrada y responder apropiadamente.
  • Opcionalmente, usar el bloque getstate para generar el switch YYGETSTATE separado del analizador léxico principal. Esto solo funciona para lenguajes que tienen goto (no en modo --loop-switch).
  • Utilizar re2c:eof y el método de centinela con comprobaciones de límites para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo añadir el relleno: el final actual de la entrada puede no ser el final definitivo de la entrada, y añadir relleno demasiado pronto puede cortar un lexema codicioso leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del búfer (que ya está bloqueado debido a la condición de fin de entrada).

Aquí hay un ejemplo de un analizador léxico en modelo de "push" que simula la lectura de paquetes desde un socket. El analizador léxico se ejecuta en un bucle hasta que encuentra el fin de la entrada y devuelve el control a la función llamante. La función llamante proporciona más entrada "enviando" el siguiente paquete y reanuda el análisis. Este proceso se detiene cuando se han enviado todos los paquetes, o cuando hay un error.

-- re2hs $INPUT -o $OUTPUT -fi
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Concurrent.Chan
import Control.Monad
import Data.ByteString as BS
import Text.Printf
debug :: IO () -> IO ()
debug = when False
data State = State {
    _pipe :: !(Chan BS.ByteString),
    _yyinput :: !BS.ByteString,
    _yycursor :: !Int,
    _yymarker :: !Int,
    _yylimit :: !Int,
    _token :: !Int,
    _eof :: !Bool,
    _yystate :: !Int,
    _recv :: !Int
}
data Status = End | Ready | Waiting | BadPacket deriving (Eq)
%{
    re2c:YYFN = ["lexer;IO (State, Status)", "State{..};State;!State{..}"];
    re2c:YYPEEK = "BS.index";
    re2c:YYFILL = "return (State{..}, Waiting)";
    re2c:eof = 0;
    re2c:monadic = 1;
    packet = [a-z]+[;];
    *      { return (State{..}, BadPacket) }
    $      { return (State{..}, End) }
    packet { lexer State{_token = _yycursor, _recv = _recv + 1, ..} }
%}
fill :: State -> IO (State, Status)
fill st@State{..} = do
    case _eof of
        True -> return (st, End)
        False -> do
            -- Discard everything up to the current token, cut off terminating null,
            -- read new chunk from file and reappend terminating null at the end.
            chunk <- readChan _pipe
            return (State {
                _yyinput = BS.concat [(BS.init . BS.drop _token) _yyinput, chunk, "\0"],
                _yycursor = _yycursor - _token,
                _yymarker = _yymarker - _token,
                _yylimit = _yylimit - _token + BS.length chunk, -- exclude terminating null
                _token = 0,
                _eof = BS.null chunk, -- end of file?
                ..}, Ready)
loop :: State -> [BS.ByteString] -> IO Status
loop State{..} packets = do
    (State{..}, status) <- lexer State{..}
    case status of
        End -> do
            debug $ printf "done: got %d packets\n" _recv
            return End
        Waiting -> do
            debug $ printf "waiting...\n"
            packets' <- case packets of
                [] -> do
                    writeChan _pipe BS.empty
                    return []
                p:ps -> do
                    debug $ printf "sent packet '%s'\n" (show p)
                    writeChan _pipe p
                    return ps
            (State{..}, status') <- fill State{..}
            case status' of
                Ready -> loop State{..} packets'
                _ -> error "unexpected status after fill"
        BadPacket -> do
            debug $ printf "error: ill-formed packet\n"
            return BadPacket
        _ -> error "unexpected status"
test :: [BS.ByteString] -> Status -> IO ()
test packets expect = do
    pipe <- newChan -- emulate pipe using a chan of bytestrings
    let st = State {
        _pipe = pipe,
        _yyinput = BS.singleton 0, -- null sentinel triggers YYFILL
        _yycursor = 0,
        _yymarker = 0,
        _token = 0,
        _yylimit = 0,
        _eof = False,
        _yystate = -1,
        _recv = 0
    }
    status <- loop st packets
    when (status /= expect) $ error "failed"
    return ()

main = do
    test [] End
    test ["ze", "ro;o", "ne", ";t", "wo;thr", "e", "e", ";", "four;"] End

Bloques reutilizables

Los bloques reutilizables de la forma /*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %} se pueden reutilizar cualquier número de veces y combinar con otros bloques de re2hs. El <nombre> es opcional. Un bloque de reglas se puede usar en un bloque o directiva use. El código para un bloque de reglas se genera en cada punto de uso.

Los bloques de uso se definen con /*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}. El <nombre> es opcional: si no se especifica, el bloque de reglas asociado es el más reciente (con nombre o sin nombre). Un bloque de uso puede agregar definiciones, configuraciones y reglas propias con nombre. Un caso de uso importante para los bloques de uso es un analizador léxico que admite múltiples codificaciones de entrada: el mismo bloque de reglas se reutiliza varias veces con configuraciones específicas de codificación (consulte el ejemplo a continuación).

La directiva de uso dentro del bloque !use:<nombre>; se puede usar desde dentro de un bloque re2hs. Fusiona el bloque referenciado <nombre> en el actual. Si algunas de las reglas y configuraciones fusionadas se superponen con las definidas previamente, los conflictos se resuelven de la manera habitual: la regla más temprana tiene prioridad y la configuración más reciente anula las anteriores. Una excepción son las reglas especiales *, $ y (en modo de condición) <!>, para las cuales una definición local del bloque anula cualquier herencia. La directiva de uso permite combinar diferentes bloques re2hs en un solo bloque (consulte el ejemplo a continuación).

Los bloques con nombre y la directiva de uso dentro del bloque se agregaron en la versión 2.2 de re2hs. Desde esa versión, los bloques reutilizables están permitidos por defecto (no se necesita una opción especial). Antes de la versión 2.2, el modo de reutilización se habilitaba con la opción -r --reusable. Antes de la versión 1.2, los bloques reutilizables no se podían mezclar con bloques normales.

Ejemplo de una directiva !use

-- re2hs $INPUT -o $OUTPUT

-- Este ejemplo muestra cómo combinar bloques re2c reutilizables: dos bloques

-- en ambos bloques; el bloque 'fish' tiene prioridad porque se usa

Extracción de subcoincidencias

re2hs tiene dos opciones para la extracción de subcoincidencias.

Etiquetas
La primera opción es usar etiquetas independientes de la forma @etiqueta o #etiqueta, donde etiqueta y etiqueta son nombres definidos por el usuario. Las etiquetas se habilitan con la opción -T --tags o la configuración re2c:tags = 1. Semánticamente, las etiquetas son marcadores de posición: se pueden insertar en cualquier lugar de una expresión regular y se vinculan a la posición (o posiciones) correspondiente en la cadena de entrada. Las etiquetas s se vinculan a la última posición coincidente, y las etiquetas m se vinculan a una lista de posiciones (pueden usarse en subexpresiones de repetición, donde una sola posición en una expresión regular corresponde a múltiples posiciones en la cadena de entrada). Todas las etiquetas deben ser definidas por el usuario, ya sea manualmente o con la ayuda de bloques svars y mvars. Si hay más de una forma en que las etiquetas puedan coincidir con la entrada, la ambigüedad se resuelve utilizando la estrategia de desambiguación codiciosa de la izquierda.
Capturas
La segunda opción es usar grupos de captura. Se habilitan con la opción --captures o la configuración re2c:captures = 1. Hay dos variantes para diferentes políticas de desambiguación, --leftmost-captures (la predeterminada) es para la política codiciosa de la izquierda, y --posix-captures es para la política de coincidencia más larga de POSIX. En este modo, todas las subexpresiones entre paréntesis se consideran grupos de captura, y se puede usar un signo de exclamación para marcar grupos sin captura: (! ... ). Con la opción --invert-captures o la configuración re2c:invert-captures = 1, el significado del signo de exclamación se invierte. El número de grupos para la regla coincidente se almacena en una variable yynmatch (la expresión regular completa es el grupo número cero), y los resultados de las subcoincidencias se almacenan en el arreglo yypmatch. Tanto yynmatch como yypmatch deben ser definidos por el usuario, y el tamaño de yypmatch debe ser al menos [yynmatch * 2]. Use el bloque maxnmatch para definir YYMAXNMATCH, una constante que es igual al valor máximo de yynmatch entre todas las reglas.
Captvars
Otra forma de usar grupos de captura es la opción --captvars o la configuración re2c:captvars = 1. La única diferencia con --captures es en la forma en que el código generado almacena los resultados de las subcoincidencias: en lugar de yynmatch y yypmatch, re2hs genera las variables yytl<k> y yytr<k> para el grupo de captura k (el usuario debe declararlas usando un bloque svars). Las capturas con variables admiten dos políticas de desambiguación: --leftmost-captvars o re2c:leftmost-captvars = 1 para la política codiciosa de la izquierda (la predeterminada) y --posix-captvars o re2c:posix-captvars para la política de coincidencia más larga de POSIX.

Internamente, todas estas opciones se traducen en etiquetas y *Autómatas Finitos Deterministas Etiquetados con Lookahead*. La idea central de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es simplemente un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es apenas perceptible. El TDFA generado utiliza una serie de *variables de etiqueta* que no se mapean directamente a las etiquetas: una sola variable puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples variables para almacenar todos sus valores posibles. Eventualmente, se resuelve la ambigüedad, y solo sobrevive una variable final por etiqueta. Las variables de etiqueta deben definirse usando bloques stags o mtags. Si el estado del analizador léxico se almacena, las variables de etiqueta deben ser parte de él. También deben actualizarse mediante YYFILL.

Las etiquetas s admiten las siguientes operaciones:

  • guardar la posición de entrada en una etiqueta s: t = YYCURSOR con la API de punteros C o una operación definida por el usuario YYSTAGP(t) con la API genérica
  • guardar un valor predeterminado en una etiqueta s: t = NULL con la API de punteros C o una operación definida por el usuario YYSTAGN(t) con la API genérica
  • copiar una etiqueta s a otra: t1 = t2

Las etiquetas m admiten las siguientes operaciones:

  • agregar una posición de entrada a una etiqueta m: una operación definida por el usuario YYMTAGP(t) con la API predeterminada y genérica
  • agregar un valor predeterminado a una etiqueta m: una operación definida por el usuario YYMTAGN(t) con la API predeterminada y genérica
  • copiar una etiqueta m a otra: t1 = t2

Las etiquetas s se pueden implementar como valores escalares (punteros o desplazamientos). Las etiquetas m necesitan una representación más compleja, ya que deben almacenar una secuencia de valores de etiqueta. La representación más ingenua e ineficiente de una etiqueta m es una lista (arreglo, vector) de valores de etiqueta; una representación más eficiente es almacenar todas las etiquetas m en un árbol de prefijos representado como un arreglo de nodos (v, p), donde v es el valor de la etiqueta y p es un puntero al nodo padre.

Incluir archivos

re2hs permite incluir otros archivos usando un bloque de la forma /*!include:re2c FILE */ o %{include FILE %}, o una directiva dentro de un bloque !include FILE ;, donde FILE es la ruta al archivo a incluir. re2hs busca los archivos de inclusión en el directorio del archivo que los incluye y en las ubicaciones de inclusión, que se pueden especificar con la opción -I. Los bloques/directivas de inclusión en re2hs funcionan de la misma manera que #include de C/C++: el contenido de FILE se copia textualmente en el lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias. Utilice la opción --depfile para rastrear las dependencias de compilación del archivo de salida en los archivos de inclusión. re2hs proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como categorías Unicode) y forman algo así como una biblioteca estándar para re2hs. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivo de inclusión 1 (definitions.hs)

data Number = INum | FNum | NNaN deriving (Eq)

    number = [1-9][0-9]*;

Archivo de inclusión 2 (extra_rules.re.inc)

Archivos de cabecera

re2hs permite generar un archivo de cabecera a partir del archivo de entrada .re usando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de cabecera, y el segundo bloque marca el final. Todo lo que está entre estos bloques es procesado por re2hs, y el código generado se escribe en el archivo especificado con la opción --header o la configuración re2c:header (o stdout si no se usa ninguna opción ni configuración). El archivo de cabecera autogenerado puede ser necesario en casos en los que re2hs se utiliza para generar definiciones que deben ser visibles desde otras unidades de traducción.

Aquí hay un ejemplo de generación de un archivo de cabecera que contiene la definición del estado del analizador léxico con variables de etiqueta (las variables de número dependen de la gramática regular y no son conocidas por el programador).

Programas esqueleto

Con la opción -S, --skeleton, re2hs ignora todo el código que no sea de re2hs y genera un programa C autocontenido que puede ser compilado y ejecutado posteriormente. El programa consta de código del analizador léxico y datos de entrada. Para cada DFA construido (bloque o condición), re2hs genera un analizador léxico independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados de la coincidencia esperados. El programa ejecuta cada analizador léxico en el archivo .input correspondiente y compara los resultados con las expectativas. Los programas esqueleto son muy útiles por varias razones:

  • Pueden verificar la corrección de varias optimizaciones de re2hs (los datos se generan temprano en el proceso, antes de que se realicen las transformaciones del DFA).
  • La generación de un conjunto de datos de entrada con buena cobertura puede ser útil tanto para pruebas como para benchmarking.
  • La generación de programas ejecutables autocontenidos permite obtener casos de prueba minimizados (el código original puede ser grande o tener muchas dependencias).

La dificultad de generar datos de entrada es que, para todos los casos excepto los más triviales, el número de cadenas de entrada posibles es demasiado grande (incluso si la longitud de la cadena está limitada). re2hs resuelve esta dificultad generando suficientes cadenas para cubrir casi todas las transiciones del DFA. Utiliza el siguiente algoritmo. Primero, construye un esqueleto del DFA. Para codificaciones con tamaño de unidad de código de 1 byte (como ASCII, UTF-8 y EBCDIC), el esqueleto es simplemente una copia exacta del DFA original. Para codificaciones con unidades de código multibyte, el esqueleto es una copia del DFA con ciertas transiciones omitidas: es decir, re2hs toma como máximo 256 unidades de código para cada rango continuo desarticulado que corresponde a una transición del DFA. Los valores elegidos están distribuidos uniformemente e incluyen los límites del rango. En lugar de intentar cubrir todos los caminos posibles en el esqueleto (lo cual es inviable), re2hs genera suficientes caminos para cubrir todas las transiciones del esqueleto, y por lo tanto, activar los saltos condicionales correspondientes en el analizador léxico. La implementación del algoritmo está limitada a ~1 GB de transiciones y consume una cantidad constante de memoria (re2hs escribe los datos en el archivo tan pronto como se generan).

Visualización y depuración

Con la opción -D, --emit-dot, re2hs no genera código. En su lugar, exporta el DFA generado en formato DOT. Se puede convertir esta exportación a una imagen del DFA utilizando Graphviz u otra biblioteca. Tenga en cuenta que esta opción muestra el DFA final después de haber pasado por una serie de optimizaciones y transformaciones. Las etapas anteriores se pueden exportar con varias opciones de depuración, como --dump-nfa, --dump-dfa-raw, etc. (consulte la lista completa de opciones).
