NOMBRE

re2ocaml - genera analizadores léxicos rápidos para OCaml

SINOPSIS

re2ocaml [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para la entrada estándar.

INTRODUCCIÓN

re2ocaml funciona como un preprocesador. Lee el archivo de entrada (que suele ser un programa en OCaml, pero puede ser cualquier cosa) y busca bloques de código encerrados en marcadores especiales de inicio/fin. El texto fuera de estos bloques se copia textualmente al archivo de salida. El contenido de los bloques es procesado por re2ocaml. Lo traduce a código en OCaml y emite el código generado en lugar del bloque.

Aquí tienes un ejemplo de un pequeño programa que comprueba si una cadena dada contiene un número decimal:

(* re2ocaml $INPUT -o $OUTPUT -i *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
}
%{
    re2c:YYFN = ["lex;bool", "yyrecord;state"];
    re2c:yyfill:enable = 0;
    [1-9][0-9]* { true }
    *           { false }
%}
let main () =
    let st = {yyinput = "1234"; yycursor = 0}
    in if not (lex st) then raise (Failure "error")
let _ = main ()

En la salida, re2ocaml reemplazó el bloque del medio con el código generado:

(* Generated by re2ocaml *)
(* re2ocaml $INPUT -o $OUTPUT -i *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
}
let rec yy0 (yyrecord : state) : bool =
    let yych = unsafe_get yyrecord.yyinput yyrecord.yycursor in
    yyrecord.yycursor <- yyrecord.yycursor + 1;
    match yych with
        | '1'..'9' -> (yy2 [@tailcall]) yyrecord
        | _ -> (yy1 [@tailcall]) yyrecord
and yy1 (yyrecord : state) : bool =
    false
and yy2 (yyrecord : state) : bool =
    let yych = unsafe_get yyrecord.yyinput yyrecord.yycursor in
    match yych with
        | '0'..'9' ->
            yyrecord.yycursor <- yyrecord.yycursor + 1;
            (yy2 [@tailcall]) yyrecord
        | _ -> (yy3 [@tailcall]) yyrecord
and yy3 (yyrecord : state) : bool =
    true
and lex (yyrecord : state) : bool =
    (yy0 [@tailcall]) yyrecord
let main () =
    let st = {yyinput = "1234"; yycursor = 0}
    in if not (lex st) then raise (Failure "error")
let _ = main ()

BÁSICOS

Un programa re2ocaml consiste en una secuencia de bloques intercalados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresión-regular ;
Una definición enlaza nombre con expresión-regular. Los nombres pueden contener caracteres alfanuméricos y guiones bajos. La sección de expresiones regulares ofrece una visión general de la sintaxis de re2ocaml para expresiones regulares. Una vez definida, el nombre puede usarse en otras expresiones regulares y en reglas. La recursión en definiciones nombradas no está permitida, y cada nombre debe definirse antes de usarse. Un bloque hereda definiciones nombradas del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite cambiar el comportamiento de re2ocaml y personalizar el código generado. Para una lista completa de configuraciones admitidas por re2ocaml, consulta la sección de configuraciones. Dependiendo de una configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista en caracteres alfanuméricos. Un bloque hereda configuraciones del ámbito global y puede redefinirlas o añadir nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final del mismo.
expresión-regular código
Una regla enlaza expresión-regular con su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en un salto de línea seguido de cualquier carácter no espacial). Si la expresión-regular coincide, se ejecuta el código asociado. Si coinciden varias reglas, la coincidencia más larga tiene precedencia. Si varias reglas coinciden con la misma cadena, la primera tiene precedencia. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse, tiene la menor prioridad independientemente de su posición en el bloque, y coincide con cualquier unidad de código (no necesariamente un carácter válido, ver la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para manejar el fin de entrada. Con las condiciones de inicio*, las reglas tienen una sintaxis más compleja.
!código de acción
Una acción enlaza un bloque de código definido por el usuario con un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas enlazan código con los estados finales). Consulta la sección de acciones para obtener una lista completa de acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias especiales predefinidas. Cada directiva tiene un propósito único. Consulta la sección de directivas para más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (se admiten ambos estilos). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que permiten referenciarlos en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2ocaml compila las expresiones regulares asociadas a cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y las configuraciones definidas en un bloque global se añaden al ámbito global y se vuelven visibles para los bloques posteriores. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y las configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera código por sí mismo, ni añade definiciones al ámbito global; está pensado para ser reutilizado en otros bloques. Esta es una forma de compartir código (más detalles en la sección de bloques reutilizables). Antes de la versión 2.2 de re2ocaml, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2ocaml busca bloques de reglas con ese nombre. De lo contrario, se utiliza el bloque de reglas más reciente (ya sea con nombre o sin nombre). Un bloque de uso puede añadir definiciones, configuraciones y reglas propias, que se añaden a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2ocaml, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloque especifica qué bloques deben incluirse al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macrodefinición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Puede personalizarse con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXFILL.
/*!maxnmatch:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{maxnmatch[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXNMATCH (requiere la opción -P --posix-captures). Una lista opcional de nombres de bloque especifica qué bloques deben incluirse al calcular Y

Expresiones regulares

re2ocaml utiliza la siguiente sintaxis para expresiones regulares:

"foo"
Literal de cadena sensible a mayúsculas y minúsculas.
'foo'
Literal de cadena insensible a mayúsculas y minúsculas.
[a-xyz], [^a-xyz]
Clase de caracteres (posiblemente negada).
.
Cualquier carácter excepto nueva línea.
R \ S
Diferencia de las clases de caracteres R y S.
R*
Cero o más ocurrencias de R.
R+
Una o más ocurrencias de R.
R?
R opcional.
R{n}
Repetición de R exactamente n veces.
R{n,}
Repetición de R al menos n veces.
R{n,m}
Repetición de R de n a m veces.
(R)
Simplemente R; los paréntesis se utilizan para anular la precedencia. Si la extracción de subcoincidencias está habilitada, (R) es un grupo de captura o no captura dependiendo de la opción --invert-captures.
(!R)
Si la extracción de subcoincidencias está habilitada, (!R) es un grupo no de captura o de captura dependiendo de la opción --invert-captures.
R S
Concatenación: R seguido de S.
R | S
Alternativa: R o S.
R / S
Lookahead: R seguido de S, pero S no se consume.
name
Expresión regular definida como name (o cadena literal "name" en modo de compatibilidad Flex).
{name}
Expresión regular definida como name en modo de compatibilidad Flex.
@stag
Una s-tag: guarda la última posición de entrada en la que @stag coincide en una variable llamada stag.
#mtag
Una m-tag: guarda todas las posiciones de entrada en las que #mtag coincide en una variable llamada mtag.

Las clases de caracteres y los literales de cadena pueden contener las siguientes secuencias de escape: \a, \b, \f, \n, \r, \t, \v, \\, escapes octales \ooo y escapes hexadecimales \xhh, \uhhhh y \Uhhhhhhhh.

Acciones

Aquí hay una lista de acciones predefinidas admitidas por re2ocaml:

!entry code
La acción de entrada vincula un bloque de código definido por el usuario a el estado de inicio de la máquina de estados finitos actual. Si se utilizan condiciones de inicio, la acción de entrada se puede establecer individualmente para cada condición. Esta acción se puede utilizar para realizar inicializaciones, por ejemplo, para guardar la ubicación de inicio de un lexema.
!pre_rule code
La acción pre_rule antepone un bloque de código definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para factorizar la parte común de todas las acciones semánticas (por ejemplo, guardar la ubicación final de un lexema).
!post_rule code
La acción post_rule adjunta un bloque de código definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para emitir sentencias de trampa que protejan contra flujos de control no deseados.

Directivas

Aquí hay una lista completa de directivas admitidas por re2ocaml:

!use:name ;
Una directiva de uso en bloque que fusiona un bloque de reglas definido previamente con el nombre especificado en el bloque actual. Las definiciones nombradas, configuraciones y reglas del bloque referenciado se agregan a las actuales. Los conflictos entre reglas y configuraciones superpuestas se resuelven de la manera habitual: la primera regla tiene prioridad, y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y <!> para las cuales una definición local del bloque siempre tiene prioridad. Una directiva de uso puede colocarse en cualquier lugar dentro de un bloque, y se permiten múltiples directivas de uso.
!include file ;
Esta directiva es lo mismo que el bloque include: inserta el contenido de file textualmente en lugar de la directiva.

Interfaz de programa

El código generado interactúa con el programa externo mediante primitivas, denominadas colectivamente API. Qué primitivas deben definirse para un programa particular depende de múltiples factores, incluyendo la complejidad de las expresiones regulares, la representación de entrada, el búfer y el uso de varias características. Todas las primitivas necesarias deben ser definidas por el usuario en forma de macros, funciones, variables o cualquier otra forma adecuada que haga que el código generado sea sintáctica y semánticamente correcto. re2ocaml no verifica (y no puede verificar) las definiciones, por lo que si algo falta o está definido incorrectamente, el programa generado puede tener errores de tiempo de compilación o de ejecución. Este manual proporciona ejemplos de definiciones de API en los casos más comunes.

re2ocaml tiene dos sabores de API que definen el conjunto central de primitivas utilizadas por un programa:

API de Registro
La API de registro es la API predeterminada para el backend de OCaml. Esta API consiste en una variable yyrecord (el nombre se puede anular con re2c:yyrecord) que debe definirse como un registro con los campos _yyinput, _yycursor, _yymarker, _yyctxmarker, _yylimit. Solo los campos utilizados por el código generado deben definirse, y sus nombres se pueden configurar.
API Genérica
Esta es la API más flexible. Se habilita con la opción --api generic o la configuración re2c:api = generic. Contiene primitivas para operaciones genéricas: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Aquí hay una lista completa de primitivas de API que pueden ser utilizadas por el código generado para interactuar con el programa externo.

YYCTYPE
El tipo de los caracteres de entrada (unidades de código). Para las codificaciones ASCII, EBCDIC y UTF-8, debe ser un entero sin signo de 1 byte. Para UTF-16 o UCS-2, debe ser un entero sin signo de 2 bytes. Para UTF-32, debe ser un entero sin signo de 4 bytes.
YYCURSOR
Un valor l que almacena la posición de entrada actual (un puntero o un desplazamiento entero en YYINPUT). Inicialmente, YYCURSOR debe apuntar al primer carácter de entrada, y luego el código generado lo avanza. Cuando una regla coincide, la posición de YYCURSOR es la que sigue al último carácter coincidente.
YYLIMIT
Un valor r que almacena el final de la posición de entrada (un puntero o un desplazamiento entero en YYINPUT). Inicialmente, YYLIMIT debe apuntar a la posición después del último carácter de entrada disponible. El código generado no lo modifica. El lexer compara YYCURSOR con YYLIMIT para determinar si quedan suficientes caracteres de entrada.
YYMARKER
Un valor l que almacena la posición de la última regla coincidente (un puntero o un desplazamiento entero en YYINPUT). Se utiliza para restaurar la posición de YYCURSOR si la coincidencia más larga falla y el lexer necesita retroceder. No se necesita inicialización.
YYCTXMARKER
Un valor l que almacena la posición del contexto de cola (un puntero o un desplazamiento entero en YYINPUT). No se necesita inicialización. YYCTXMARKER solo es necesario si se utiliza el operador de lookahead /.
YYFILL
Una primitiva de API genérica con una variable len. YYFILL debe proporcionar al menos len caracteres de entrada adicionales o fallar. Si se utiliza re2c:eof, entonces len es siempre 1 y YYFILL siempre debe devolver a la función que lo llamó; un valor de retorno cero indica éxito. Si re2c:eof no se utiliza, entonces se ignora el valor de retorno de YYFILL y no debe devolver en caso de fallo. El valor máximo de len es YYMAXFILL.
YYFN
Una primitiva que define el prototipo de la función en el modelo de código --recursive-functions. Su valor debe ser una matriz de una o más cadenas, donde cada cadena contiene dos o tres componentes separados por la cadena especificada en la configuración re2c:fn:sep (típicamente un punto y coma). El primer elemento de la matriz define el nombre de la función y el tipo de retorno (vacío para una función void). Los elementos subsiguientes definen los argumentos de la función: primero, la expresión para el argumento utilizado en el cuerpo de la función (generalmente solo un nombre); segundo, el tipo del argumento; tercero, un parámetro formal opcional (por defecto es el primer componente, generalmente ambos son el mismo identificador).
YYINPUT
Un valor r que almacena la secuencia de entrada actual (cadena, búfer, etc.).

A generic API primitive with two variables, lhs and rhs that should copy right-hand-side m-tag variable rhs to the left-hand-side m-tag variable lhs. For most languages this primitive has a default definition that assigns lhs to rhs.
YYSHIFTSTAG
A generic API primitive with two variables, tag and shift that should shift tag by shift code units (the shift value may be negative).
YYSHIFTMTAG
A generic API primitive with two variables, tag and shift that should shift the latest value in the history of tag by shift code units (the shift value may be negative).
YYMAXNMATCH
An integral constant equal to the maximal number of POSIX capturing groups in a rule. It is generated with a maxnmatch block.
YYCONDTYPE
The type of the condition enum. It can be generated either with conditions block or --header option.
YYGETACCEPT
A primitive with one variable var that stores numeric selector of the accepted rule. For most languages this primitive has a default definition that reads from var.
YYSETACCEPT
A primitive with two variables: var (an l-value that stores numeric selector of the accepted rule), and val (the value of selector). For most languages this primitive has a default definition that assigns var to val.
YYGETCOND
An r-value of type YYCONDTYPE that is equal to the current condition identifier.
YYSETCOND
A primitive with one variable cond that should set the current condition identifier to cond.
YYGETSTATE
An r-value of integer type that is equal to the current lexer state. It should be initialized to -1.
YYSETSTATE
A primitive with one variable state that should set the current lexer state to state.
YYDEBUG
This primitive is generated only with -d, --debug-output option. Its purpose is to add logging to the generated code (typical YYDEBUG definition is a print statement). YYDEBUG statements are generated in every state and have two variables: state (either a DFA state index or -1) and symbol (the current input symbol).
yyaccept
An l-value of unsigned integral type that stores the number of the latest matched rule. User definition is necessary only with --storable-state option.
yybm
A table containing compressed bitmaps for up to 8 transitions (used with the --bitmaps option). The table contains 256 elements and is indexed by 1-byte code units. Each 8-bit element combines boolean values for up to 8 transitions. k-Th bit of n-th element is true iff n-th code unit is in the range of k-th transition. The idea of this bitmap is to replace many if branches or switch cases with one check of a single bit in the table.
yych
An l-value of type YYCTYPE that stores the current input character. User definition is necessary only with -f --storable-state option.
yyctable
Jump table generated for the initial condition dispatch (enabled with the combination of --conditions and --computed-gotos options).
yyfill
An l-value that stores the result of YYFILL call (this may be necessary for pure functional languages, where YYFILL is a monadic function with complex return value).
yynmatch
An l-value of unsigned integral type that stores the number of POSIX capturing groups in the matched rule. Used only with -P --posix-captures option.
yypmatch
An array of l-values that are used to hold the tag values corresponding to the capturing parentheses in the matching rule. Array length must be at least yynmatch * 2 (usually YYMAXNMATCH * 2 is a good choice). Used only with -P --posix-captures option.
yystable
Deprecated.
yystate
An l-value used with the --loop-switch option to store the current DFA state.
yytarget
Jump table that contains jump targets (label addresses) for all transitions from a state. This table is local to each state. Generation of yytarget tables is enabled with --computed-gotos option.

Some of the options have corresponding configurations, others are global and cannot be changed after re2c starts reading the input file. Debug options generally require building re2c in debug configuration. Internal options are useful for experimenting with the algorithms used in re2c.

Option record should be used when lexer state needs to be stored in a record (struct, class, etc.). Option generic should be used in complex cases when the other two APIs are not flexible enough.

Esta opción depende de la opción --output.
--ebcdic --ecb -e
Genera un lexer que lee la entrada en codificación EBCDIC. re2ocaml asume que el rango de caracteres es 0 -- 0xFF y el tamaño de carácter es de 1 byte.
--empty-class <match-empty | match-none | error>
Define la forma en que re2ocaml trata las clases de caracteres vacías. Con match-empty (el predeterminado) la clase vacía coincide con la entrada vacía (lo cual es ilógico, pero compatible con versiones anteriores). Con match-none la clase vacía siempre falla al coincidir. Con error la clase vacía genera un error de compilación.
--encoding-policy <fail | substitute | ignore>
Define la forma en que re2ocaml trata los sustitutos de Unicode. Con fail re2ocaml aborta con un error cuando se encuentra un sustituto. El estándar Unicode dice que los sustitutos independientes son inválidos, pero las bibliotecas y programas del mundo real se comportan de diferentes maneras.

Genera un archivo HEADER. El contenido del archivo se puede especificar usando bloques especiales header:on y header:off. Si se usan condiciones, la cabecera generada tendrá un enum de condiciones agregado automáticamente (a menos que haya un bloque conditions explícito).

Agrega PATH a la lista de ubicaciones que se utilizan al buscar archivos de inclusión. Esta opción es útil en combinación con el bloque o directiva include. re2ocaml busca FILE en el directorio del archivo padre y en las ubicaciones de inclusión especificadas con la opción -I.
--input <default | custom>
Alias obsoleto para --api. La opción default corresponde a simple (es de hecho el predeterminado para la mayoría de los backends, pero no para todos). La opción custom corresponde a generic.
--input-encoding <ascii | utf8>
Especifica la forma en que re2ocaml analiza las expresiones regulares. Con ascii (el predeterminado) re2ocaml maneja la entrada como codificada en ASCII: cualquier secuencia de unidades de código es una secuencia de caracteres independientes de 1 byte. Con utf8 re2ocaml maneja la entrada como codificada en UTF8 y reconoce caracteres multibyte.
--invert-captures
Invierte el significado de los grupos de captura y no captura. Por defecto (...) es de captura y (! ...) no es de captura. Con esta opción (! ...) es de captura y (...) no es de captura.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Especifica el lenguaje de destino. Los lenguajes soportados son C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (se pueden agregar más lenguajes a través de archivos de sintaxis definidos por el usuario, ver la opción --syntax). --location-format <gnu | msvc>
Especifica el formato de ubicación en los mensajes. Con gnu las ubicaciones se imprimen como 'filename:line:column: ...'. Con msvc las ubicaciones se imprimen como 'filename(line,column) ...'. El predeterminado es gnu.
--loop-switch
Utiliza el modelo de código "loop/switch": codifica el DFA en forma de un bucle sobre una sentencia switch, donde los estados individuales son casos del switch. El estado se almacena en una variable yystate. Las transiciones entre estados actualizan yystate a la etiqueta del caso del estado de destino y continúan la ejecución hasta el inicio del bucle.

--no-debug-info -i

Ambos algoritmos deberían producir el mismo DFA hasta el etiquetado de estados; el relleno de tabla es más simple y mucho más lento, y sirve como implementación de referencia.

Opción interna: hace que el lexer generado avance la posición de entrada agresivamente, inmediatamente después de leer el símbolo de entrada. Esto cambia el comportamiento predeterminado donde la posición de entrada se avanza perezosamente, después de la transición al siguiente estado.
--no-lookahead
Opción interna, obsoleta. Solía habilitar el algoritmo TDFA(0). A diferencia de TDFA(1), el algoritmo TDFA(0) no usa lookahead de un símbolo. Aplica operaciones de registro a las transiciones entrantes en lugar de las salientes. Los benchmarks mostraron que el algoritmo TDFA(0) es menos eficiente que TDFA(1).

Opción interna: suprime la optimización de variables de etiqueta (útil para depuración).
--posix-closure <gor1 | gtop>
Opción interna: especifica el algoritmo de camino más corto utilizado para la construcción de la clausura epsilon con semántica de desambiguación POSIX: gor1 (el predeterminado) significa el algoritmo de Goldberg-Radzik, y gtop significa el algoritmo de "orden topológico global".
--posix-prectable <complex | naive>
Opción interna: especifica el algoritmo utilizado para calcular la tabla de precedencia POSIX. El algoritmo complex calcula la tabla de precedencia en una sola traversa del árbol de historial de etiquetas y tiene una complejidad cuadrática en el número de estados TNFA; es el predeterminado. El algoritmo naive tiene una complejidad cúbica en el peor de los casos en el número de estados TNFA, pero es mucho más simple que complex y puede ser ligeramente más rápido en casos no patológicos.
--stadfa
Opción interna, obsoleta. Solía habilitar el algoritmo staDFA, que difiere de TDFA en que las operaciones de registro se colocan en estados en lugar de en transiciones. Los benchmarks mostraron que el algoritmo staDFA es menos eficiente que TDFA.
--fixed-tags <none | toplevel | all>
Opción interna: especifica si la optimización de etiquetas fijas debe aplicarse a todas las etiquetas (all), a ninguna de ellas (none), o solo a las de concatenación de nivel superior (toplevel). El valor predeterminado es all. Las etiquetas "fijas" son aquellas que se encuentran a una distancia fija de otra etiqueta (llamada "base"). En tales casos, solo la etiqueta base necesita ser rastreada, y el valor de la etiqueta fija se puede calcular como el valor de la etiqueta base más un desplazamiento estático. Para etiquetas que están bajo alternativa o repetición, también es necesario verificar si la etiqueta base tiene un valor de no coincidencia (en ese caso, la etiqueta fija también debe establecerse en no coincidencia, sin tener en cuenta el desplazamiento). Para etiquetas en concatenación de nivel superior, la verificación no es necesaria, ya que siempre coinciden.

Advertencias

Las advertencias se pueden habilitar, deshabilitar y convertir en error individualmente.

-W
Activa todas las advertencias.
-Werror
Convierte las advertencias en errores. Ten en cuenta que esta opción por sí sola no activa ninguna advertencia; solo afecta a las advertencias que se han activado hasta ahora o que se activarán más tarde.
-W<advertencia>
Activa advertencia.
-Wno-<advertencia>
Desactiva advertencia.
-Werror-<advertencia>
Activa advertencia y la trata como un error (esto implica -W<advertencia>).
-Wno-error-<advertencia>
No trata esta advertencia en particular como un error. Esto no desactiva la advertencia en sí.
-Wcondition-order
Advierte si el programa generado hace suposiciones implícitas sobre la numeración de las condiciones. Se debe usar la opción --header o el bloque conditions para generar un mapeo de nombres de condiciones a números y luego usar los nombres de condiciones autogenerados.
-Wempty-character-class
Advierte si una expresión regular contiene una clase de caracteres vacía. Intentar coincidir con una clase de caracteres vacía no tiene sentido: siempre debería fallar. Sin embargo, por razones de compatibilidad con versiones anteriores, re2ocaml permite clases de caracteres vacías y las trata como cadenas vacías. Usa la opción --empty-class para cambiar el comportamiento predeterminado.
-Wmatch-empty-string
Advierte si una regla es anulable (coincide con una cadena vacía). Si el lexer se ejecuta en un bucle y la coincidencia vacía es no intencionada, el lexer puede colgarse inesperadamente en un bucle infinito.
-Wswapped-range
Advierte si el límite inferior de un rango es mayor que su límite superior. El comportamiento predeterminado es intercambiar silenciosamente los límites del rango.
-Wundefined-control-flow
Advierte si algunas cadenas de entrada causan un flujo de control indefinido en el lexer (se informan los patrones erróneos). Este es un error peligroso y común. Se puede solucionar fácilmente agregando la regla predeterminada *, que tiene la prioridad más baja, coincide con cualquier unidad de código y consume siempre una sola unidad de código.
-Wunreachable-rules
Advierte sobre reglas que están ocultas por ot
sus reglas y nunca coincidirán.
-Wdeprecated-eof_rule
Advierte sobre reglas de fin de entrada independientes $ que se romperán con cambios futuros y requerirán corrección. Por el momento, estas reglas tienen precedencia cuando entran en conflicto con otras reglas, pero después de la introducción del símbolo de fin de entrada generalizado $, el orden de precedencia cambiará y estas reglas quedarán ocultas por otras reglas.
-Wuseless-escape
Advierte si un símbolo se escapa cuando no debería. Por defecto, re2ocaml ignora silenciosamente dichos escapes, pero esto también puede indicar un error tipográfico o un error en la secuencia de escape.
-Wnondeterministic-tags
Advierte si una etiqueta tiene un grado n de no determinismo, donde n es mayor que 1.
-Wsentinel-in-midrule
Advierte si el símbolo centinela ocurre en medio de una regla; esto puede causar lecturas fuera del búfer, fallos o corrupción de memoria en el lexicador generado. Esta advertencia solo es aplicable si se utiliza el método centinela para verificar el fin de la entrada. Se establece como un error si se utiliza la configuración re2c:sentinel.
-Wundefined-syntax-config
Advierte si el archivo de sintaxis especificado con la opción --syntax carece de definiciones para algunas configuraciones. Esto ayuda a mantener los archivos de sintaxis definidos por el usuario: si una nueva versión agrega configuraciones, el archivo de sintaxis antiguo generará una advertencia y se notificará al usuario. Si algunas configuraciones no se utilizan y no necesitan una definición, deben establecerse explícitamente como <undefined>.

Archivos de sintaxis

El soporte para diferentes lenguajes en re2c se basa en la idea de archivos de sintaxis. Un archivo de sintaxis es un archivo de configuración que define la sintaxis del lenguaje de destino, no todo el lenguaje, sino una pequeña parte de él que es utilizada por el código generado. Los archivos de sintaxis hacen que re2c sea muy flexible, pero no deben usarse como un reemplazo para las configuraciones de re2c:; su propósito es definir la sintaxis del lenguaje de destino, no personalizar un lexicador en particular. Todos los lenguajes soportados tienen archivos de sintaxis por defecto que forman parte de la distribución (ver el subdirectorio include/syntax); también están incrustados en el binario re2ocaml. Los usuarios pueden proporcionar un archivo de sintaxis personalizado que anule algunas configuraciones para uno de los lenguajes soportados, o pueden optar por redefinir todas las configuraciones (en ese caso, se debe usar la opción --lang none). Los archivos de sintaxis contienen configuraciones de cuatro tipos diferentes: listas de características, configuraciones de lenguaje, configuraciones in situ y plantillas de código.

Listas de características

Algunas configuraciones de lista definen varias características soportadas por un backend dado, de modo que re2ocaml pueda emitir un error claro si el usuario intenta habilitar una característica no soportada:
supported_apis
Una lista de APIs soportadas con elementos posibles: simple, record, generic.
supported_api_styles
Una lista de estilos de API soportados con elementos posibles: functions, free-form.
supported_code_models
Una lista de modelos de código soportados con elementos posibles: goto-label, loop-switch, recursive-functions.
supported_targets
Una lista de destinos de generación de código soportados con elementos posibles: code, dot, skeleton.
supported_features
Una lista de características soportadas con elementos posibles: nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Configuraciones de lenguaje

Algunas configuraciones booleanas describen características del lenguaje de destino que afectan al analizador y al generador de código de re2ocaml:
semicolons
Distinto de cero si el lenguaje utiliza puntos y coma después de las sentencias.
backtick_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas invertidas.
single_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas simples.
indentation_sensitive
Distinto de cero si el lenguaje es sensible a la indentación.
wrap_blocks_in_braces

Plantillas de código

Las plantillas de código definen la sintaxis del lenguaje de destino. Están escritas en un lenguaje de dominio específico simple con la siguiente gramática formal: 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Una plantilla de código es una secuencia de literales de cadena, variables, elementos opcionales y listas, o una referencia a otra plantilla de código, o un valor especial <undefined>. Las variables son marcadores de posición que se sustituyen durante la fase de generación de código. Las variables de lista son especiales: al expandir plantillas de lista, re2ocaml repite expresiones en el lado derecho de la columna varias veces, reemplazando cada vez las ocurrencias de la variable de lista con un valor específico para esa repetición. Las listas tienen límites opcionales (los valores negativos se cuentan desde el final, por ejemplo, -1 significa el último elemento). Los nombres condicionales comienzan con un punto. Tanto los condicionales como las variables pueden ser locales (específicos de la plantilla de código dada) o globales (permitidos en todas las plantillas de código). Cuando re2ocaml lee el archivo de sintaxis, verifica que cada plantilla de código utilice solo las variables y condicionales que están permitidos en ella.

Por ejemplo, la siguiente plantilla de código define la construcción if-then-else para un lenguaje similar a C:

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Aquí, branch es una variable de lista: branch{0} se expande a la primera rama (que es especial, ya que no hay parte else), branch{1:-1} se expande a todas las ramas restantes (si las hay). stmt también es una variable de lista: [stmt: stmt] es una lista anidada que se expande a una lista de sentencias en el cuerpo de la rama actual. topindent, indent, dedent y nl son variables globales, y .cond es un condicional local (su significado se describe a continuación). Esta plantilla de código podría producir el siguiente código:

if x {
    // hacer algo
} else if y {
    // hacer otra cosa
} else {
    // no hacer nada
}

HANDLING THE END OF INPUT

One of the main problems for the lexer is to know when to stop. There are a few terminating conditions:

  • the lexer may match some rule (including default rule *) and come to a final state
  • the lexer may fail to match any rule and come to a default state
  • the lexer may reach the end of input

The first two conditions terminate the lexer in a "natural" way: it comes to a state with no outgoing transitions, and the matching automatically stops. The third condition, end of input, is different: it may happen in any state, and the lexer should be able to handle it. Checking for the end of input interrupts the normal lexer workflow and adds conditional branches to the generated program, therefore it is necessary to minimize the number of such checks. re2ocaml supports a few different methods for handling the end of input. Which one to use depends on the complexity of regular expressions, the need for buffering, performance considerations and other factors. Here is a list of methods:

  • Sentinel. This method eliminates the need for the end of input checks altogether. It is simple and efficient, but limited to the case when there is a natural "sentinel" character that can never occur in valid input. This character may still occur in invalid input, but it should not be allowed by the regular expressions, except perhaps as the last character of a rule. The sentinel is appended at the end of input and serves as a stop signal: when the lexer reads this character, it is either a syntax error or the end of input. In both cases the lexer should stop. This method is used if YYFILL is disabled with re2c:yyfill:enable = 0; and re2c:eof has the default value -1.
  • Sentinel with bounds checks. This method is generic: it allows one to handle any input without restrictions on the regular expressions. The idea is to reduce the number of end of input checks by performing them only on certain characters. Similar to the "sentinel" method, one of the characters is chosen as a "sentinel" and appended at the end of input. However, there is no restriction on where the sentinel may occur (in fact, any character can be chosen for a sentinel). When the lexer reads this character, it additionally performs a bounds check. If the current position is within bounds, the lexer resumes matching and handles the sentinel as a regular character. Otherwise it invokes YYFILL (unless it is disabled). If more input is supplied, the lexer will rematch the last character and continue as if the sentinel wasn't there. Otherwise it must be the real end of input, and the lexer stops. This method is used when re2c:eof has non-negative value (it should be set to the numeric value of the sentinel). YYFILL is optional.
  • Bounds checks with padding. This method is generic, and it may be faster than the "sentinel with bounds checks" method, but it is also more complex. The idea is to partition DFA states into strongly connected components (SCCs) and generate a single check per SCC for enough characters to cover the longest non-looping path in this SCC. This reduces the number of checks, but there is a problem with short lexemes at the end of input, as the check requires enough characters to cover the longest lexeme. This can be fixed by padding the input with a few fake characters that do not form a valid lexeme suffix (so that the lexer cannot match them). The length of padding should be YYMAXFILL, generated with a max block. If there is not enough input, the lexer invokes YYFILL which should supply at least the required number of characters or not return. This method is used if YYFILL is enabled and re2c:eof is -1 (this is the default configuration).
  • Custom checks. Generic API allows one to override basic operations like reading a character, which makes it possible to include the end-of-input checks as part of them. This approach is error-prone and should be used with caution. To use a custom method, enable generic API with --api custom or re2c:api = custom; and disable default bounds checks with re2c:yyfill:enable = 0; or re2c:yyfill:check = 0;.

The following subsections contain an example of each method.

Sentinel

This example uses a sentinel character to handle the end of input. The program counts space-separated words in a null-terminated string. The sentinel is null: it is the last character of each input string, and it is not allowed in the middle of a lexeme by any of the rules (in particular, it is not included in character ranges where it is easy to overlook). If a null occurs in the middle of a string, it is a syntax error and the lexer will match default rule *, but it won't read past the end of input or crash (use -Wsentinel-in-midrule warning and re2c:sentinel configuration to verify this). Configuration re2c:yyfill:enable = 0; suppresses the generation of bounds checks and YYFILL invocations.

(* re2ocaml $INPUT -o $OUTPUT *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
}
(* expect a null-terminated string *)
%{

Sentinel with bounds checks

This example uses sentinel with bounds checks to handle the end of input (this method was added in version 1.2). The program counts space-separated single-quoted strings. The sentinel character is null, which is specified with re2c:eof = 0; configuration. As in the sentinel method, null is the last character of each input string, but it is allowed in the middle of a rule (for example, 'aaa\0aa'\0 is valid input, but 'aaa\0 is a syntax error). Bounds checks are generated in each state that matches an input character, but they are scoped to the branch that handles null. Bounds checks are of the form YYLIMIT <= YYCURSOR or YYLESSTHAN(1) with generic API. If the check condition is true, lexer has reached the end of input and should stop (YYFILL is disabled with re2c:yyfill:enable = 0; as the input fits into one buffer, see the YYFILL with sentinel section for an example that uses YYFILL). Reaching the end of input opens three possibilities: if the lexer is in the initial state it will match the end-of-input rule $, otherwise it may fallback to a previously matched rule (including default rule *) or go to a default state, causing -Wundefined-control-flow.

(* re2ocaml $INPUT -o $OUTPUT *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
    mutable yymarker: int;
    yylimit: int;
}
(* expect a null-terminated string *)
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:yyfill:enable = 0;
    re2c:eof = 0;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { -1 }
    $    { count }
    str  { lex yyrecord (count + 1) }
    [ ]+ { lex yyrecord count }
%}
let test(str, count) =
    let st = {
        yyinput = str;
        yycursor = 0;
        yymarker = 0;
        yylimit = length str - 1; (* terminating null not included *)
    }
    in if not (lex st 0 = count) then raise (Failure "error")
let main () =
    test("", 0);
    test("'qu\x00tes' 'are' 'fine: \\'' ", 3);
    test("'unterminated\\'", -1)
let _ = main ()

Bounds checks with padding

This example uses bounds checks with padding to handle the end of input (this method is enabled by default). The program counts space-separated single-quoted strings. There is a padding of YYMAXFILL null characters appe

nded al final de la entrada, donde el valor YYMAXFILL se autogenera con un bloque max. No es necesario usar nulo para el relleno: se pueden usar caracteres cualesquiera siempre que no formen un sufijo de lexema válido (en este ejemplo, el relleno no debe contener comillas simples, ya que pueden confundirse con el sufijo de una cadena entre comillas simples). Hay una regla de "stop" que coincide con el primer carácter de relleno (nulo) y termina el lexer (ten en cuenta que comprueba si el nulo está al principio del relleno, de lo contrario es un error de sintaxis). Las comprobaciones de límites solo se generan en algunos estados determinados por los componentes fuertemente conectados del autómata subyacente. Las comprobaciones tienen la forma (YYLIMIT - YYCURSOR) < n o YYLESSTHAN(n) con la API genérica, donde n es el número mínimo de caracteres necesarios para que el lexer continúe (también significa que la próxima comprobación de límites ocurrirá en como máximo n caracteres). Si la condición de comprobación es verdadera, el lexer ha llegado al final de la entrada e invocará YYFILL(n), que debería proporcionar al menos n caracteres de entrada o no devolver nada. En este ejemplo YYFILL siempre falla y termina el lexer con un error (lo cual está bien porque la entrada cabe en un solo búfer). Consulta la sección YYFILL con relleno para ver un ejemplo que rellena el búfer de entrada con YYFILL.

(* re2ocaml $INPUT -o $OUTPUT *)
open String
exception Fill
type state = {
    yyinput: string;
    mutable yycursor: int;
    yylimit: int;
}
%{max %}
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:YYFILL = "raise Fill;";
    str = ['] ([^'\\] | [\\][^])* ['];
    [\x00] {
        (* comprueba que sea el centinela, no un nulo inesperado *)
        if yyrecord.yycursor = length yyrecord.yyinput - yymaxfill + 1 then count else -1
    }
    str  { lex yyrecord (count + 1) }
    [ ]+ { lex yyrecord count }
    *    { -1 }
%}
let test(str, count) =
    let buf = cat str (make yymaxfill '\x00') in
    let st = {yyinput = buf; yycursor = 0; yylimit = length buf} in
    let result = try lex st 0 with Fill -> -1 in
    if not (result = count) then raise (Failure "error")
let main () =
    test("", 0);
    test("'unterminated\\'", -1);
    test("'qu\x00tes' 'are' 'fine: \\'' ", 3);
    test("'unexpected \x00 null", -1)
let _ = main ()

Es igual que el ejemplo del centinela, excepto que la entrada no está terminada en nulo. REEMPLAZO DE BÚFER

La necesidad de almacenamiento en búfer surge cuando la entrada no se puede mapear en memoria a la vez: o es demasiado grande o proviene de forma continua (como al leer de un socket). La técnica habitual en tales casos es asignar un búfer de memoria de tamaño fijo y procesar la entrada en fragmentos que quepan en el búfer. Cuando se procesa el fragmento actual, se mueve y se introducen nuevos datos. En la práctica, es algo más complejo, porque el estado del lexer consiste no en una única posición de entrada, sino en un conjunto de posiciones interrelacionadas:

  • cursor: el siguiente carácter de entrada a leer (YYCURSOR en la API de punteros C o YYSKIP/YYPEEK en la API genérica)
  • límite: la posición después del último carácter de entrada disponible (YYLIMIT en la API de punteros C, manejado implícitamente por YYLESSTHAN en la API genérica)
  • marcador: la posición de la coincidencia más reciente, si la hay (YYMARKER en la API predeterminada o YYBACKUP/YYRESTORE en la API genérica)
  • token: el inicio del lexema actual (implícito en la API re2ocaml, ya que no es necesario para el funcionamiento normal del lexer y puede ser definido y actualizado por el usuario)
  • marcador de contexto: la posición del contexto final (YYCTXMARKER en la API de punteros C o YYBACKUPCTX/YYRESTORECTX en la API genérica)
  • variables de etiqueta: posiciones de subcoincidencia (definidas con bloques stags y mtags y primitivas de API genérica YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

No todas estas se utilizan en todos los casos, pero si se utilizan, deben ser actualizadas por YYFILL. Todas las posiciones activas se contienen en el segmento entre el token y el cursor, por lo tanto, todo lo que está entre el inicio del búfer y el token se puede descartar, el segmento desde el token hasta el límite debe moverse al principio del búfer, y el espacio libre al final del búfer debe rellenarse con nuevos datos. Para evitar llamadas frecuentes a YYFILL, es mejor rellenar tantos caracteres de entrada como sea posible (aunque puedan bastar menos caracteres para reanudar el lexer). Los detalles de la implementación de YYFILL son ligeramente diferentes según el método de manejo de EOF utilizado: el caso de la regla EOF es algo más sencillo que el caso de las comprobaciones de límites con relleno. También ten en cuenta que si se utiliza la opción -f --storable-state, YYFILL tiene una semántica ligeramente diferente (descrita en la sección sobre estado almacenable).

YYFILL con centinela

Si se utiliza la regla EOF, YYFILL es una primitiva similar a una función que no acepta argumentos y devuelve un valor que se comprueba contra cero. La invocación de YYFILL se activa mediante la condición YYLIMIT <= YYCURSOR en la API de punteros C y YYLESSTHAN() en la API genérica. Un valor de retorno distinto de cero significa que YYFILL ha fallado. Una llamada exitosa a YYFILL debe proporcionar al menos un carácter y ajustar las posiciones de entrada en consecuencia. El límite siempre debe establecerse en uno después de la última posición de entrada en el búfer, y el carácter en la posición límite debe ser el símbolo centinela especificado por la configuración re2c:eof. Las figuras a continuación muestran la ubicación relativa de las posiciones de entrada en el búfer antes y después de la llamada a YYFILL (el símbolo centinela se marca con #, y la segunda imagen muestra el caso en el que no hay suficiente entrada para llenar todo el búfer).

               <-- desplazar -->
             >-A------------B---------C-------------D#-----------E->
             búfer        token    marcador         límite,
                                                  cursor
>-A------------B---------C-------------D------------E#->
             búfer,   marcador        cursor        límite
             token
               <-- desplazar -->
             >-A------------B---------C-------------D#--E
             búfer       token    marcador         límite,
                                                  cursor
>-A------------B---------C-------------D---E#........
             búfer,  marcador       cursor límite
             token

Aquí hay un ejemplo de un programa que lee el archivo de entrada input.txt en fragmentos de 4096 bytes y utiliza la regla EOF.

(* re2ocaml $INPUT -o $OUTPUT *)
open Bytes
let bufsize = 4096
type state = {
    file: in_channel;
    yyinput: bytes;
    mutable yycursor: int;
    mutable yymarker: int;
    mutable yylimit: int;
    mutable token: int;
    mutable eof: bool;
}
type status = Ok | Eof | LongLexeme
let fill(st: state) : status =
    if st.eof then Eof else
    (* Error: lexema demasiado largo. En la vida real se podría reasignar un búfer más grande. *)
    if st.token < 1 then LongLexeme else (
    (* Desplaza el contenido del búfer (descarta todo hasta el token actual). *)
    blit st.yyinput st.token st.yyinput 0 (st.yylimit - st.token);
    st.yycursor <- st.yycursor - st.token;
    st.yymarker <- st.yymarker - st.token;
    st.yylimit <- st.yylimit - st.token;
    st.token <- 0;
    (* Rellena el espacio libre al final del búfer con nuevos datos del archivo. *)
    let n = input st.file st.yyinput st.yylimit (bufsize - st.yylimit - 1) in (* -1 para el centinela *)
    st.yylimit <- st.yylimit + n;
    if n = 0 then
        st.eof <- true; (* fin de archivo *)
        set st.yyinput st.yylimit '\x00'; (* añade centinela *)
    Ok)
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:YYFILL = "fill yyrecord = Ok";
    re2c:eof = 0;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { -1 }
    $    { count }
    str  { lex_loop yyrecord (count + 1) }
    [ ]+ { lex_loop yyrecord count }
%}
and lex_loop st count =
    st.token <- st.yycursor;
    lex st count
let main () =
    let fname = "input" in
    (* Prepara el archivo de entrada. *)
    Out_channel.with_open_bin fname
        (fun oc -> for i = 1 to bufsize do
            output_string oc "'qu\x00tes' 'are' 'fine: \\'' "
        done);
    (* Ejecuta el lexer en el archivo preparado. *)
    In_channel.with_open_bin fname
        (fun ic ->
            let yylimit = bufsize - 1 in
            let st = {
                file = ic;
                yyinput = create bufsize;
                yycursor = yylimit;
                yymarker = yylimit;
                yylimit = yylimit;
                token = yylimit;
                eof = false;
            } in if not (lex_loop st 0 = 3 * bufsize) then
                raise (Failure "error"));
    (* Limpieza. *)
    Sys.remove fname
let _ = main ()

YYFILL con relleno

En el caso predeterminado (cuando no se utiliza la regla EOF), YYFILL es una primitiva similar a una función que acepta un solo argumento y no devuelve ningún valor. La invocación de YYFILL se activa mediante la condición (YYLIMIT - YYCURSOR) < n en la API de punteros C y YYLESSTHAN(n) en la API genérica. El argumento pasado a YYFILL es el número mínimo de caracteres que deben proporcionarse. Si no se consigue hacerlo

Múltiples bloques

A veces es necesario tener múltiples lexers interrelacionados (por ejemplo, si hay una máquina de estados de alto nivel que transita entre modos de lexer). Esto se puede implementar usando múltiples bloques conectados de re2ocaml. Otra opción es usar condiciones de inicio.

La implementación de las conexiones entre bloques depende del lenguaje de destino. En lenguajes que tienen una declaración goto (como C/C++ y Go) se pueden tener todos los bloques en una sola función, cada uno prefijado con una etiqueta. La transición de un bloque a otro es un simple goto. En lenguajes que no tienen goto (como Rust) es necesario usar un bucle con un switch en una variable de estado, similar al bucle/switch yystate generado por re2ocaml, o envolver cada bloque en una función y usar llamadas a funciones.

El ejemplo a continuación utiliza múltiples bloques para analizar números binarios, octales, decimales y hexadecimales. Cada base tiene su propio bloque. El bloque inicial determina la base y se dirige a otros bloques. Las configuraciones comunes se definen en un bloque separado al principio del programa; son heredadas por los otros bloques.

(* re2ocaml $INPUT -o $OUTPUT -i *)
open Int64
open Option
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
    mutable yymarker: int;
} 
let add (num: int option) (dgt: int) (base: int) : int option =
    match num with
        | None -> None
        | Some n ->
            let n' = add (mul (of_int n) (of_int base)) (of_int dgt)
            in if n' > (of_int32 Int32.max_int) then None else Some (to_int n')
%{
    re2c:yyrecord = "st";
    re2c:yyfill:enable = 0;
%}
%{local
    re2c:YYFN = ["parse_bin;int option", "st;state", "num;int option"];
    [01] { parse_bin st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 2) }
    *    { num }
%}
%{local
    re2c:YYFN = ["parse_oct;int option", "st;state", "num;int option"];
    [0-7] { parse_oct st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 8) }
    *     { num }
%}
%{local
    re2c:YYFN = ["parse_dec;int option", "st;state", "num;int option"];
    [0-9] { parse_dec st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 10) }
    *     { num }
%}
%{local
    re2c:YYFN = ["parse_hex;int option", "st;state", "num;int option"];
    [0-9] { parse_hex st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 16) }
    [a-f] { parse_hex st (add num (Char.code st.yyinput.[st.yycursor - 1] - 87) 16) }
    [A-F] { parse_hex st (add num (Char.code st.yyinput.[st.yycursor - 1] - 55) 16) }
    *     { num }
%}
%{local
    re2c:YYFN = ["parse;int option", "st;state"];
    '0b' / [01]        { parse_bin st (Some 0) }
    "0"                { parse_oct st (Some 0) }
    "" / [1-9]         { parse_dec st (Some 0) }
    '0x' / [0-9a-fA-F] { parse_hex st (Some 0) }
    *                  { None }
%}
let test (yyinput: string) (result: int option) =
    let st = {yyinput = yyinput; yycursor = 0; yymarker = 0} in
    if not (parse st = result) then raise (Failure "error")
let main () =
    test "\x00" None;
    test "1234567890\x00" (Some 1234567890);
    test "0b1101\x00" (Some 13);
    test "0x7Fe\x00" (Some 2046);
    test "0644\x00" (Some 420);
    test "9999999999\x00" None
let _ = main ()

Condiciones de inicio

Las condiciones de inicio se habilitan con la opción --start-conditions. Proporcionan una forma de codificar múltiples autómatas interrelacionados dentro del mismo bloque re2ocaml.

Cada condición corresponde a un solo autómata y tiene un nombre único especificado por el usuario y un número interno único definido por re2ocaml. Los números se utilizan para cambiar entre condiciones: el código generado usa primitivas YYGETCOND y YYSETCOND para obtener la condición actual o establecerla en el número dado. Use el bloque conditions, la opción --header o la configuración re2c:header para generar identificadores numéricos de condición. La configuración re2c:cond:enumprefix especifica el prefijo del identificador generado.

En modo de condición, cada regla debe ir precedida por una lista de nombres de condición separados por comas en corchetes angulares, o un comodín <*> para denotar todas las condiciones. La sintaxis de la regla se extiende de la siguiente manera:

< lista-de-condiciones > expresión-regular código
Una regla que se fusiona a cada condición en la lista-de-condiciones. Coincide con la expresión-regular y ejecuta el código asociado.
< lista-de-condiciones > expresión-regular => condición código
Una regla que se fusiona a cada condición en la lista-de-condiciones. Coincide con la expresión-regular, establece la condición actual a condición y ejecuta el código asociado.
< lista-de-condiciones > expresión-regular :=> condición
Una regla que se fusiona a cada condición en la lista-de-condiciones. Coincide con la expresión-regular y transiciona inmediatamente a condición (no hay acción semántica).
< lista-de-condiciones > !acción código
Una regla que une el código a la ubicación definida por la acción en cada condición de la lista-de-condiciones (consulte la sección de acciones para ver varios tipos de acciones).
<! lista-de-condiciones > código
Una regla que antepone el código a las acciones semánticas de todas las reglas para cada condición en la lista-de-condiciones. Esta sintaxis está obsoleta y se debe usar la acción !pre_rule en su lugar (hace exactamente lo mismo).
< > código
Una regla que crea una condición de entrada especial con el número cero y el nombre "0" que ejecuta el código antes de saltar a otras condiciones. Esta sintaxis está obsoleta, y se debe usar la acción !entry en su lugar (proporciona un control más detallado, ya que el código puede especificarse por condición, y se puede saltar directamente al inicio de la condición sin pasar por la selección de condición).
< > => condición código
Igual que la regla anterior, excepto que establece la siguiente condición.
< > :=> condición
Igual que la regla anterior, excepto que no tiene código asociado y salta inmediatamente a la condición.

El código que re2ocaml genera para las condiciones depende de si

ther: re2ocaml usa un enfoque de goto/etiqueta o un enfoque de bucle/switch para codificar el autómata.

En lenguajes que tienen una declaración goto (como C/C++ y Go) las condiciones se implementan de forma natural como bloques de código precedidos por etiquetas de la forma yyc_<cond>, donde cond es un nombre de condición (el prefijo de etiqueta se puede cambiar con re2c:cond:prefix). Las transiciones entre condiciones se implementan usando goto y etiquetas de condición. Antes de todas las condiciones, re2ocaml genera un switch inicial sobre YYGETSTATE que salta al estado de inicio de la condición actual. Las reglas de acceso directo :=> evitan el switch inicial y saltan directamente a la condición especificada ( re2c:cond:goto se puede usar para cambiar el comportamiento predeterminado). Las reglas con acciones semánticas no saltan automáticamente a la siguiente condición; esto debe ser realizado por el código de acción definido por el usuario.

En lenguajes que no tienen goto (como Rust) re2ocaml reutiliza la variable yystate para almacenar números de condición. Cada condición obtiene un identificador numérico igual al número de su estado de inicio, y un switch entre condiciones no es diferente de un switch entre estados DFA de una sola condición. No hay necesidad de un switch de condición inicial separado. (Dado que se utiliza el mismo enfoque para implementar estados almacenables, YYGETCOND/YYSETCOND son redundantes si se utilizan tanto estados almacenables como condiciones).

Estado almacenable

Con la opción --storable-state, re2ocaml genera un lexer que puede almacenar su estado actual, devolver el control al llamador y, más tarde, reanudar las operaciones exactamente donde se quedó. El modo de operación predeterminado en re2ocaml es un modelo de "pull" (tirar), en el que el lexer "tira" de más entrada cuando la necesita. Esto puede ser inaceptable en casos en los que la entrada está disponible pieza por pieza (por ejemplo, si el lexer es invocado por el parser, o si el programa lexer se comunica a través de un protocolo de socket con algún otro programa que debe esperar una respuesta del lexer antes de transmitir el siguiente mensaje). La característica de estado almacenable está destinada precisamente a tales casos: permite generar lexers que funcionan en un modelo de "push" (empujar). Cuando el lexer necesita más entrada, almacena su estado y devuelve el control al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el lexer exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo de "pull":

  • Definir los primitivos YYSETSTATE() y YYGETSTATE(state).
  • Definir las variables yych, yyaccept (si se usan) y state como parte del estado persistente del lexer. La variable state debe inicializarse a -1.
  • YYFILL debe devolver el control al programa externo en lugar de intentar suministrar más entrada. El código de retorno debe indicar que el lexer necesita más entrada.
  • El programa externo debe reconocer situaciones en las que el lexer necesita más entrada y responder apropiadamente.
  • Opcionalmente, use el bloque getstate para generar el switch YYGETSTATE separado del lexer principal. Esto solo funciona para lenguajes que tienen goto (no en modo --loop-switch).
  • Utilice re2c:eof y el método del *centinela con comprobaciones de límites* para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo agregar el relleno: el final actual de la entrada puede no ser el final definitivo de la entrada, y agregar relleno demasiado pronto puede cortar un lexema codicioso leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del búfer (que ya está bloqueado debido a la condición de fin de entrada).

Aquí hay un ejemplo de un lexer de modelo "push" que simula la lectura de paquetes de un socket. El lexer se ejecuta en un bucle hasta que encuentra el final de la entrada y devuelve el control a la función llamadora. La función llamadora proporciona más entrada "enviando" el siguiente paquete y reanuda el lexing. Este proceso se detiene cuando se han enviado todos los paquetes, o cuando hay un error.

(* re2ocaml $INPUT -o $OUTPUT -fi *)
open Bytes
(* Utiliza un búfer pequeño para cubrir el caso en que un lexema no cabe.
   En la vida real, usa un búfer más grande. *)
let bufsize = 10
let debug = false
let log format = (if debug then Printf.eprintf else Printf.ifprintf stderr) format
type state = {
    file: in_channel;
    yyinput: bytes;
    mutable yycursor: int;
    mutable yymarker: int;
    mutable yylimit: int;
    mutable token: int;
    mutable yystate: int;
    mutable recv: int;
}
type status = End | Ready | Waiting | BadPacket | BigPacket
let fill(st: state) : status =
    (* Error: lexema demasiado largo. En la vida real se podría reasignar un búfer más grande. *)
    if st.token < 1 then BigPacket else (
    (* Desplaza el contenido del búfer (descarta todo hasta el token actual). *)
    blit st.yyinput st.token st.yyinput 0 (st.yylimit - st.token);
    st.yycursor <- st.yycursor - st.token;
    st.yymarker <- st.yymarker - st.token;
    st.yylimit <- st.yylimit - st.token;
    st.token <- 0;
    (* Llena el espacio libre al final del búfer con nuevos datos del archivo. *)
    let n = In_channel.input st.file st.yyinput st.yylimit (bufsize - st.yylimit - 1) in
    st.yylimit <- st.yylimit + n;
    set st.yyinput st.yylimit '\x00'; (* agrega centinela *)
    Ready)
%{
    re2c:YYFN = ["lex;status", "yyrecord;state"];
    re2c:YYFILL = "Waiting";
    re2c:eof = 0;
    packet = [a-z]+[;];
    *      { BadPacket }
    $      { End }
    packet { yyrecord.recv <- yyrecord.recv + 1; lex_loop yyrecord }
%}
and lex_loop st =
    st.token <- st.yycursor;
    lex st
let test (packets: string list) (sts: status) =
    let fname = "pipe" in
    let oc = Out_channel.open_bin fname in
    let ic = In_channel.open_bin fname in
    let yylimit = bufsize - 1 in
    let st = {
        file = ic;
        (* El centinela (en el offset `yylimit`) se establece a nulo, lo que activa YYFILL. *)
        yyinput = create bufsize;
        yycursor = yylimit;
        yymarker = yylimit;
        yylimit = yylimit;
        token = yylimit;
        yystate = -1;
        recv = 0;
    } in
    let rec loop packets = match lex_loop st with
        | End ->
            log "done: got %d packets\n" st.recv;
            End
        | Waiting ->
            log "waiting...\n";
            let packets' = match packets with
                | [] -> []
                | p :: ps ->
                    log "sent packet '%s'\n" p;
                    Out_channel.output_string oc p;
                    Out_channel.flush oc; (* sin `flush`, la escritura ocurre demasiado tarde *)
                    ps
            in (match fill st with
                | BigPacket ->
                    log "error: packet too big\n";
                    BigPacket
                | Ready -> loop packets'
                | _ -> raise (Failure "unexpected status after fill"))
        | BadPacket ->
            log "error: ill-formed packet\n";
            BadPacket
        | _ -> raise (Failure "unexpected status")
    in if not (loop packets = sts) then
        raise (Failure "error");
    In_channel.close ic;
    Out_channel.close oc;
    Sys.remove fname
let main () =
    test [] End;
    test ["zero;"; "one;"; "two;"; "three;"; "four;"] End;
    test ["zer0;"] BadPacket;
    test ["goooooooooogle;"] BigPacket
let _ = main ()

Bloques reutilizables

Los bloques reutilizables de la forma /*!rules:re2c[:<name>] ... */ o %{rules[:<name>] ... %} se pueden reutilizar cualquier número de veces y combinar con otros bloques de re2ocaml. El <name> es opcional. Un bloque de reglas se puede usar en un bloque o directiva use. El código para un bloque de reglas se genera en cada punto de uso.

Los bloques de uso se definen con /*!use:re2c[:<name>] ... */ o %{use[:<name>] ... %}. El <name> es opcional: si no se especifica, el bloque de reglas asociado es el más reciente (ya sea nombrado o sin nombre). Un bloque de uso puede agregar definiciones, configuraciones y reglas propias y nombradas. Un caso de uso importante para los bloques de uso es un lexer que admite múltiples codificaciones de entrada: el mismo bloque de reglas se reutiliza varias veces con configuraciones específicas de codificación (ver el ejemplo a continuación).

La directiva de uso dentro de un bloque !use:<name>; se puede usar desde dentro de un bloque de re2ocaml. Fusiona el bloque referenciado <name> en el actual. Si algunas de las reglas y configuraciones fusionadas se superponen con las definidas previamente, los conflictos se resuelven en el último

al way: la regla más antigua tiene prioridad, y la configuración más reciente anula las anteriores. Una excepción son las reglas especiales *, $ y (en modo de condición) <!>, para las cuales una definición local de bloque anula las heredadas. La directiva Use permite combinar diferentes bloques re2ocaml entre sí en un solo bloque (ver el ejemplo a continuación).

Los bloques con nombre y la directiva de uso dentro de bloque se añadieron en la versión 2.2 de re2ocaml. Desde esa versión, los bloques reutilizables están permitidos por defecto (no se necesita una opción especial). Antes de la versión 2.2, el modo de reutilización se habilitaba con la opción -r --reusable. Antes de la versión 1.2, los bloques reutilizables no podían mezclarse con bloques normales.

Ejemplo de directiva !use

(* re2ocaml $INPUT -o $OUTPUT *)
(* Este ejemplo muestra cómo combinar bloques re2c reutilizables: dos bloques
   ('colors' y 'fish') se fusionan en uno. La regla 'salmon' aparece en ambos
   bloques; el bloque 'fish' tiene prioridad porque se usa antes. La regla
   predeterminada * aparece en los tres bloques; la definición local (no

    yyinput: string;

    mutable yymarker: int;
}
%{rules:colors
    *                            { raise (Failure "ah"); }
    "red" | "salmon" | "magenta" { Color }
%}
%{rules:fish
    *                            { raise (Failure "oh"); }
    "haddock" | "salmon" | "eel" { Fish }
%}
%{

    re2c:yyfill:enable = 0;

%}

Extracción de subcoincidencias

re2ocaml tiene dos opciones para la extracción de subcoincidencias.

Etiquetas
La primera opción es usar etiquetas independientes de la forma @etiqueta o #metiqueta, donde etiqueta y metiqueta son nombres arbitrarios definidos por el usuario. Las etiquetas se habilitan con la opción -T --tags o la configuración re2c:tags = 1. Semánticamente, las etiquetas son marcadores de posición: se pueden insertar en cualquier parte de una expresión regular y se enlazan a la posición (o posiciones) correspondiente(s) en la cadena de entrada. Las e-etiquetas se enlazan a la última posición de coincidencia, y las m-etiquetas se enlazan a una lista de posiciones (pueden usarse en subexpresiones de repetición, donde una única posición en una expresión regular corresponde a múltiples posiciones en la cadena de entrada). Todas las etiquetas deben ser definidas por el usuario, ya sea manualmente o con la ayuda de bloques svars y mvars. Si hay más de una forma en que las etiquetas pueden coincidir con la entrada, la ambigüedad se resuelve utilizando la estrategia de desambiguación voraz de izquierda a derecha.
Capturas
La segunda opción es usar grupos de captura. Se habilitan con la opción --captures o la configuración re2c:captures = 1. Hay dos variantes para diferentes políticas de desambiguación, --leftmost-captures (la predeterminada) es para la política voraz de izquierda a derecha, y --posix-captures es para la política de coincidencia más larga POSIX. En este modo, todas las subexpresiones parentizadas se consideran grupos de captura, y se puede usar un signo de exclamación para marcar grupos que no capturan: (! ... ). Con la opción --invert-captures o la configuración re2c:invert-captures = 1, el significado del signo de exclamación se invierte. El número de grupos para la regla de coincidencia se almacena en una variable yynmatch (la expresión regular completa es el grupo número cero), y los resultados de subcoincidencia se almacenan en el array yypmatch. Tanto yynmatch como yypmatch deben ser definidos por el usuario, y el tamaño de yypmatch debe ser al menos [yynmatch * 2]. Use el bloque maxnmatch para definir YYMAXNMATCH, una constante que es igual al valor máximo de yynmatch entre todas las reglas.
Captvars
Otra forma de usar grupos de captura es la opción --captvars o la configuración re2c:captvars = 1. La única diferencia con --captures es la forma en que el código generado almacena los resultados de subcoincidencia: en lugar de yynmatch y yypmatch, re2ocaml genera las variables yytl<k> y yytr<k> para el grupo de captura k (el usuario debe declararlas usando un bloque svars). Captures with variables soporta dos políticas de desambiguación: --leftmost-captvars o re2c:leftmost-captvars = 1 para la política voraz de izquierda a derecha (la predeterminada) y --posix-captvars o re2c:posix-captvars para la política de coincidencia más larga POSIX.

En segundo plano, todas estas opciones se traducen en etiquetas y Autómatas Finitos Deterministas Etiquetados con Lookahead (TDFA). La idea central de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En el extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es solo un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es apenas perceptible. El TDFA generado utiliza un número de variables de etiqueta que no se mapean directamente a las etiquetas: una única variable puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples variables para almacenar todos sus valores posibles. Finalmente, la ambigüedad se resuelve y solo sobrevive una variable final por etiqueta. Las variables de etiqueta deben definirse usando bloques stags o mtags. Si se almacena el estado del lexer, las variables de etiqueta deben ser parte de él. También necesitan ser actualizadas por YYFILL.

Las e-etiquetas soportan las siguientes operaciones:

  • guardar la posición de entrada en una e-etiqueta: t = YYCURSOR con la API de puntero C o una operación definida por el usuario YYSTAGP(t) con la API genérica
  • guardar un valor predeterminado en una e-etiqueta: t = NULL con la API de puntero C o una operación definida por el usuario YYSTAGN(t) con la API genérica
  • copiar una e-etiqueta a otra: t1 = t2

Las m-etiquetas soportan las siguientes operaciones:

  • agregar la posición de entrada a una m-etiqueta: una operación definida por el usuario YYMTAGP(t) con la API predeterminada y genérica
  • agregar un valor predeterminado a una m-etiqueta: una operación definida por el usuario YYMTAGN(t) con la API predeterminada y genérica
  • copiar una m-etiqueta a otra: t1 = t2

Las e-etiquetas se pueden implementar como valores escalares (punteros u offsets). Las m-etiquetas necesitan una representación más compleja, ya que deben almacenar una secuencia de valores de etiqueta. La representación más ingenua e ineficiente de una m-etiqueta es una lista (array, vector) de valores de etiqueta; una representación más eficiente es almacenar todas las m-etiquetas en un árbol prefijo representado como un array de nodos (v, p), donde v es el valor de la etiqueta y p es un puntero al nodo padre.

        if i >= j then n else f s (i + 1) j (n * 10 + Char.code (get s i) - 48)
    in f str i1 i2 0

let fill(st: state) : status =
    if st.eof then Eof else
    (* Error: lexeme too long. In real life could reallocate a larger buffer. *)
    if st.token < 1 then LongLexeme else (
    (* Shift buffer contents (discard everything up to the current token). *)
    blit st.yyinput st.token st.yyinput 0 (st.yylimit - st.token);
    st.yycursor <- st.yycursor - st.token;
    st.yymarker <- st.yymarker - st.token;
    st.yylimit <- st.yylimit - st.token;
    %{stags format = "\n\tst.@@ <- if st.@@ = -1 then -1 else st.@@ - st.token;"; %}
    st.token <- 0;
    (* Fill free space at the end of buffer with new data from file. *)
    let n = input st.file st.yyinput st.yylimit (bufsize - st.yylimit - 1) in (* -1 for sentinel *)
    st.yylimit <- st.yylimit + n;
    if n = 0 then
        st.eof <- true; (* end of file *)
        set st.yyinput st.yylimit '\x00'; (* append sentinel *)
    Ok)

%{
    re2c:YYFN = ["lex;(semver list) option", "st;state", "vers;semver list"];
    re2c:YYFILL = "fill st = Ok";
    re2c:yyrecord = "st";
    re2c:tags = 1;
    re2c:eof = 0;
    num = [0-9]+;
    @t1 num @t2 "." @t3 num @t4 ("." @t5 num)? [\n] {
        let ver = {
            major = s2n st.yyinput st.t1 st.t2;
            minor = s2n st.yyinput st.t3 st.t4;
            patch = if st.t5 = -1 then 0 else s2n st.yyinput st.t5 (st.yycursor - 1)
        } in lex_loop st (ver :: vers)
    }
    $ { Some (List.rev vers) }
    * { None }
%}
and lex_loop st vers =
    st.token <- st.yycursor;
    lex st vers

let main () =
    let fname = "input" in
    (* Prepare input file. *)
    Out_channel.with_open_bin fname
        (fun oc -> for i = 1 to bufsize do
            output_string oc "1.22.333\n"
        done);
    (* Construct the expected result to compare against. *)
    let expect = Some (List.init bufsize
            (fun _ -> {major = 1; minor = 22; patch = 333;})) in
    (* Run lexer on the prepared file. *)
    In_channel.with_open_bin fname
        (fun ic ->
            let yylimit = bufsize - 1 in
            let st = {
                file = ic;
                yyinput = create bufsize;
                yycursor = yylimit;
                yymarker = yylimit;
                yylimit = yylimit;
                token = yylimit;
                eof = false;
                %{svars format = "\n\t\t@@{tag} = -1;"; %}
                %{stags format = "\n\t\t@@{tag} = -1;"; %}
            } in if (lex_loop st [] <> expect) then
                raise (Failure "error"));
    (* Cleanup. *)
    Sys.remove fname

let _ = main ()

# Soporte de codificación

Es necesario comprender la diferencia entre **puntos de código** y **unidades de código**. Un punto de código es un identificador numérico de un símbolo. Una unidad de código es la unidad de almacenamiento más pequeña en el texto codificado. Un solo punto de código puede representarse con una o más unidades de código. En una codificación de longitud fija, todos los puntos de código se representan con el mismo número de unidades de código. En una codificación de longitud variable, los puntos de código pueden representarse con un número diferente de unidades de código. Tenga en cuenta que la regla "cualquiera" **[^]** coincide con cualquier punto de código, pero no necesariamente con cualquier unidad de código (la única forma de que coincida con cualquier unidad de código independientemente de la codificación es la regla predeterminada **\***). El lexer generado funciona con un flujo de unidades de código: **yych** almacena una unidad de código y **YYCTYPE** es el tipo de unidad de código. Las expresiones regulares, por otro lado, se especifican en términos de puntos de código. Cuando re2ocaml compila expresiones regulares en autómatas, traduce los puntos de código a unidades de código. Esto generalmente no es una simple asignación: en codificaciones de longitud variable, un solo rango de puntos de código puede traducirse a un gráfico de unidades de código complejo. Se admiten las siguientes codificaciones:

*   **ASCII** (habilitado por defecto). Es una codificación de longitud fija con espacio de código **[0-255]** y puntos de código y unidades de código de 1 byte.
*   **EBCDIC** (habilitado con **--ebcdic** o **re2c:encoding:ebcdic**). Es una codificación de longitud fija con espacio de código **[0-255]** y puntos de código y unidades de código de 1 byte.
*   **UCS2** (habilitado con **--ucs2** o **re2c:encoding:ucs2**). Es una codificación de longitud fija con espacio de código **[0-0xFFFF]** y puntos de código y unidades de código de 2 bytes.
*   **UTF8** (habilitado con **--utf8** o **re2c:encoding:utf8**). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
*   **UTF16** (habilitado con **--utf16** o **re2c:encoding:utf16**). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 a 2 unidades de código.
*   **UTF32** (habilitado con **--utf32** o **re2c:encoding:utf32**). Es una codificación Unicode de longitud fija con espacio de código **[0-0x10FFFF]** y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión **include/unicode_categories.re** proporciona definiciones de re2ocaml para las categorías estándar de Unicode.

La opción **--input-encoding** especifica la codificación del archivo fuente, que se puede utilizar para habilitar literales Unicode en expresiones regulares. Por ejemplo, **--input-encoding utf8** le dice a re2ocaml que el archivo fuente está en UTF8 (difiere de **--utf8** que establece la codificación del texto de entrada). La opción **--encoding-policy** especifica la forma en que re2ocaml maneja los sustitutos Unicode (puntos de código en el rango **[0xD800-0xDFFF]**).

A continuación, se muestra un ejemplo de un lexer para identificadores Unicode codificados en UTF8.

```ocaml
(* re2ocaml $INPUT -o $OUTPUT --utf8 -i *)
open String
%{include "unicode_categories.re" %}
type state = {
    yyinput: string;
    mutable yycursor: int;
    mutable yymarker: int;
    mutable yyaccept: int;
}

    re2c:YYFN = ["lex;bool", "yyrecord;state"];

    }
```

# Archivos de inclusión

re2ocaml permite incluir otros archivos utilizando un bloque de la forma **/*!include:re2c FILE */** o **%{include FILE %}**, o un in-block directive !include FILE ;, donde FILE es una ruta
    al archivo a incluir. re2ocaml busca archivos de inclusión en el directorio
    del archivo que incluye y en las ubicaciones de inclusión, que se pueden especificar con
    la opción -I. Los bloques/directivas de inclusión en re2ocaml funcionan de la misma
    manera que #include en C/C++: el contenido de FILE se copia y pega literalmente
    en lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias.
    Utilice la opción --depfile para rastrear las dependencias de compilación
    del archivo de salida en los archivos de inclusión. re2ocaml proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto.
    Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como categorías Unicode) y forman algo así como una biblioteca estándar para
    re2ocaml. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivo de inclusión 1 (definitions.ml)

type number = Int | Float | NaN
%{
    number = [1-9][0-9]*;
%}

Archivo de inclusión 2 (extra_rules.re.inc)

// números de punto flotante
frac  = [0-9]* "." [0-9]+ | [0-9]+ ".";
exp   = 'e' [+-]? [0-9]+;
float = frac exp? | [0-9]+ exp;
float { Float }

Archivos de encabezado

re2ocaml permite generar un archivo de encabezado a partir del archivo .re de entrada usando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de encabezado, y el segundo bloque marca su final. Todo lo que esté entre estos bloques es procesado por re2ocaml, y el código generado se escribe en el archivo especificado con la opción --header o la configuración re2c:header (o stdout si no se usa ninguna opción ni configuración). Puede ser necesario un archivo de encabezado autogenerado en los casos en que re2ocaml se utilice para generar definiciones que deban ser visibles desde otras unidades de traducción.

Aquí hay un ejemplo de generación de un archivo de encabezado que contiene la definición del estado del analizador léxico con variables de etiqueta (el número de variables depende de la gramática regular y es desconocido para el programador).

Archivo de entrada

    yyinput: string;
    mutable yycursor: int;
    mutable tag: int;

%{header:off %}
%{
    re2ocaml:YYFN = ["lex;int", "yyrecord;State.state"];
    re2ocaml:tags = 1;
    re2ocaml:yyfill:enable = 0;

    [a]* @tag [b]* { yyrecord.tag }

    let st = {
        yyinput = "ab";
        yycursor = 0;
        tag = 0;

Programas esqueleto

Con la opción -S, --skeleton, re2ocaml ignora todo el código que no sea de re2ocaml y genera un programa C autocontenido que puede ser compilado y ejecutado posteriormente. El programa consta de código del analizador léxico y datos de entrada. Para cada DFA construido (bloque o condición), re2ocaml genera un analizador léxico independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados esperados de la coincidencia. El programa ejecuta cada analizador léxico en el archivo .input correspondiente y compara los resultados con las expectativas. Los programas esqueleto son muy útiles por varias razones:

  • Pueden verificar la corrección de varias optimizaciones de re2ocaml (los datos se generan en una etapa temprana del proceso, antes de que se hayan realizado transformaciones del DFA).
  • La generación de un conjunto de datos de entrada con buena cobertura puede ser útil tanto para pruebas como para benchmarking.
  • La generación de programas ejecutables autocontenidos permite obtener casos de prueba minimizados (el código original puede ser grande o tener muchas dependencias).

La dificultad para generar datos de entrada radica en que, para todos los casos excepto los más triviales, el número de cadenas de entrada posibles es demasiado grande (incluso si la longitud de la cadena está limitada). re2ocaml resuelve esta dificultad generando suficientes cadenas para cubrir casi todas las transiciones del DFA. Utiliza el siguiente algoritmo. Primero, construye un esqueleto del DFA. Para codificaciones con tamaño de unidad de código de 1 byte (como ASCII, UTF-8 y EBCDIC), el esqueleto es simplemente una copia exacta del DFA original. Para codificaciones con unidades de código multibyte, el esqueleto es una copia del DFA con ciertas transiciones omitidas: a saber, re2ocaml toma como máximo 256 unidades de código por cada rango continuo y desvinculado que corresponde a una transición del DFA. Los valores elegidos se distribuyen uniformemente e incluyen los límites del rango. En lugar de intentar cubrir todos los caminos posibles en el esqueleto (lo cual es inviable), re2ocaml genera suficientes caminos para cubrir todas las transiciones del esqueleto, y así activar los saltos condicionales correspondientes en el analizador léxico. La implementación del algoritmo está limitada a ~1 GB de transiciones y consume una cantidad constante de memoria (re2ocaml escribe los datos en un archivo tan pronto como se generan).

Visualización y depuración

Con la opción -D, --emit-dot, re2ocaml no genera código. En su lugar, vuelca el DFA generado en formato DOT. Se puede convertir este volcado en una imagen del DFA utilizando Graphviz u otra biblioteca. Tenga en cuenta que esta opción muestra el DFA final después de haber pasado por una serie de optimizaciones y transformaciones. Las etapas anteriores se pueden volcar con varias opciones de depuración, como --dump-nfa, --dump-dfa-raw, etc. (consulte la lista completa de opciones).
