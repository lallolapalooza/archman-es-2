NOMBRE

re2zig - generar analizadores léxicos rápidos para Zig

SINOPSIS

re2zig [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para stdin.

INTRODUCCIÓN

re2zig funciona como un preprocesador. Lee el archivo de entrada (que suele ser un programa en Zig, pero puede ser cualquier cosa) y busca bloques de código encerrados entre marcadores especiales de inicio/fin. El texto fuera de estos bloques se copia tal cual al archivo de salida. El contenido de los bloques es procesado por re2zig. Los traduce a código en Zig y genera el código resultante en lugar del bloque.

Este es un ejemplo de un pequeño programa que comprueba si una cadena dada contiene un número decimal:

// re2zig $INPUT -o $OUTPUT
const std = @import("std");
fn lex(yyinput: [:0]const u8) bool {
    var yycursor: u32 = 0;
    %{
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    %}
}

En la salida, re2zig reemplazó el bloque intermedio con el código generado:

// Generado por re2zig
// re2zig $INPUT -o $OUTPUT
const std = @import("std");
fn lex(yyinput: [:0]const u8) bool {
    var yycursor: u32 = 0;
    var yych: u8 = 0;
    var yystate: u32 = 0;
    yyl: while (true) {
        switch (yystate) {
            0 => {
                yych = yyinput[yycursor];
                yycursor += 1;
                switch (yych) {
                    0x31...0x39 => {
                        yystate = 2;
                        continue :yyl;
                    },
                    else => {
                        yystate = 1;
                        continue :yyl;
                    },
                }
            },
            1 => { return false; },
            2 => {
                yych = yyinput[yycursor];
                switch (yych) {
                    0x30...0x39 => {
                        yycursor += 1;
                        yystate = 2;
                        continue :yyl;
                    },
                    else => {
                        yystate = 3;
                        continue :yyl;
                    },
                }
            },
            3 => { return true; },
            else => { @panic("error interno del analizador"); },
        }
    }
}

CONCEPTOS BÁSICOS

Un programa re2zig consiste en una secuencia de bloques intercalados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresión-regular ;
Una definición une nombre con expresión-regular. Los nombres pueden contener caracteres alfanuméricos y guión bajo. La sección expresiones regulares ofrece una visión general de la sintaxis de re2zig para expresiones regulares. Una vez definida, el nombre se puede utilizar en otras expresiones regulares y en reglas. No se permite la recursión en definiciones con nombre, y cada nombre debe definirse antes de ser utilizado. Un bloque hereda definiciones con nombre del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite cambiar el comportamiento de re2zig y personalizar el código generado. Para obtener una lista completa de configuraciones compatibles con re2zig, consulte la sección configuraciones. Dependiendo de una configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista en caracteres alfanuméricos. Un bloque hereda configuraciones del ámbito global y puede redefinirlas o añadir nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final del mismo.
expresión-regular código
Una regla une expresión-regular con su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en una nueva línea seguida de cualquier carácter no espacio en blanco). Si la expresión-regular coincide, se ejecuta el código asociado. Si varias reglas coinciden, prevalece la coincidencia más larga. Si varias reglas coinciden con la misma cadena, prevalece la primera. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse, tiene la menor prioridad independientemente de su lugar en el bloque, y coincide con cualquier unidad de código (no necesariamente un carácter válido, consulte la sección soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para manejar el fin de entrada. Con condiciones de inicio, las reglas tienen una sintaxis más compleja.
!acción código
Una acción une un bloque de código definido por el usuario con un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas unen código a los estados finales). Vea la sección acciones para obtener una lista completa de acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias especiales predefinidas. Cada directiva tiene un propósito único. Vea la sección directivas para obtener más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (ambos estilos son compatibles). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que permiten referenciarlos en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2zig compila las expresiones regulares asociadas a cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se añaden al ámbito global y se vuelven visibles para los bloques subsiguientes. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y las configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera ningún código por sí mismo, ni añade ninguna definición al ámbito global; está destinado a ser reutilizado en otros bloques. Esta es una forma de compartir código (más detalles en la sección bloques reutilizables). Antes de la versión 2.2 de re2zig, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2zig busca bloques de reglas con ese nombre. De lo contrario, se utiliza el bloque de reglas más reciente (ya sea nombrado o sin nombre). Un bloque de uso puede añadir sus propias definiciones, configuraciones y reglas, que se añaden a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2zig, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macrodefinición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Se puede personalizar con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXFILL.
/*!maxnmatch:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{maxnmatch[:<nombre1>[:<nombre2>...]] ... %}

Tipos de bloques

/*!maxnmatch:re2c[:<name1>[:<name2>...]] ... */ or %{maxnmatch[:<name1>[:<name2>...]] ... %}
Un bloque que genera la definición de YYMAXNMATCH (requiere la opción -P --posix-captures). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXNMATCH (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una definición de macro para C ( #define YYMAXNMATCH <n>), o una variable global para Go ( var YYMAXNMATCH int = <n>). Se puede personalizar con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ o %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Bloques que especifican una pieza de código de plantilla que se expande para cada variable de s-tag/m-tag generada por re2zig. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el conjunto de variables de etiqueta (si la lista está vacía, se incluyen todos los bloques). Hay dos configuraciones opcionales: format y separator. La configuración format especifica una cadena de plantilla donde @@{tag} (o @@ para abreviar) se reemplaza con el nombre de cada variable de etiqueta. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes variables de etiqueta.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ o %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Bloques que especifican una pieza de código de plantilla que se expande para cada s-tag/m-tag que se menciona explícitamente en las reglas (con la opción --tags) o se genera implícitamente por re2zig (con las opciones --captvars o --posix-captvars). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el conjunto de etiquetas (si la lista está vacía, se incluyen todos los bloques). Hay dos configuraciones opcionales: format y separator. La configuración format especifica una cadena de plantilla donde @@{tag} (o @@ para abreviar) se reemplaza con el nombre de cada etiqueta. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes etiquetas.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ o %{getstate[:<name1>[:<name2>...]] ... %}
Un bloque que genera un dispatch condicional en el estado del lexer (requiere la opción --storable-state). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse en el dispatch de estado. La transición por defecto va a la etiqueta de inicio del primer bloque de la lista. Si la lista está vacía, se incluyen todos los bloques y la transición por defecto va al primer bloque del archivo que tenga una etiqueta de inicio. Este tipo de bloque es incompatible con la opción --loop-switch, ya que requiere transiciones entre bloques que no son compatibles sin goto o llamadas a funciones.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ o %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
Un bloque que genera una enumeración de condiciones (requiere la opción --conditions). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el conjunto de condiciones (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una enumeración YYCONDTYPE. Se puede personalizar con las configuraciones opcionales format y separator. La configuración format especifica una cadena de plantilla donde @@{cond} (o @@ para abreviar) se reemplaza con el nombre de cada condición, y @@{num} se reemplaza con un índice numérico de esa condición. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes condiciones.
/*!include:re2c <file> */ o %{include <file> %}
Este bloque permite incluir <file>, que debe ser una ruta de archivo entre comillas dobles. El contenido del archivo se sustituye literalmente en lugar del bloque, de la misma manera que funciona #include en C/C++. Este bloque se puede usar junto con la opción --depfile para generar dependencias del sistema de compilación en los archivos incluidos.
/*!header:re2c:on*/ o %{header:on %}
Este bloque marca el inicio del archivo de encabezado. Todo lo que sigue y hasta el siguiente bloque header:off es procesado por re2zig y escrito en el archivo de encabezado especificado con la opción -t --type-header.
/*!header:re2c:off*/ o %{header:off %}
Este bloque marca el final del archivo de encabezado iniciado con el bloque header:on*/.
/*!ignore:re2c ... */ o %{ignore ... %}
Un bloque cuyo contenido se ignora y se elimina del archivo de salida.

Configuraciones

Aquí hay una lista completa de las configuraciones admitidas por re2zig:

re2c:api, re2c:input
Igual que la opción --api.
re2c:api:sigil
Especifica el marcador ("sigilo") que se utiliza para los marcadores de posición de argumentos en las primitivas de la API. El valor predeterminado es @@. Un marcador de posición comienza con el sigilo seguido del nombre del argumento entre llaves. Por ejemplo, si el sigilo se establece en $, los marcadores de posición tendrán la forma ${nombre}. Las APIs de un solo argumento pueden usar una notación abreviada sin el nombre entre llaves. Esta opción puede ser anulada por opciones para primitivas de API individuales, por ejemplo, re2c:YYFILL@len para YYFILL.
re2c:api:style
Especifica el estilo de la API. Los valores posibles son functions (el valor predeterminado para C) y free-form (el valor predeterminado para Go y Rust). En el estilo functions, las primitivas de la API se generan con una lista de argumentos entre paréntesis después del nombre de la primitiva. Los argumentos se proporcionan solo para parámetros autogenerados (como el número de caracteres pasados a YYFILL), pero no para el contexto general del lexer, por lo que las primitivas se comportan más como macros en C/C++ o cierres en Go y Rust. En el estilo free-form, las primitivas de la API no tienen una forma fija: deben definirse como cadenas que contienen piezas de código de forma libre con variables interpoladas de la forma @@{var} o @@ (corresponden a argumentos en estilo similar a una función). Esta configuración puede ser anulada para primitivas de API individuales, vea por ejemplo la configuración re2c:YYFILL:naked para YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Igual que la opción --bit-vectors, pero se puede configurar por bloque.
re2c:captures, re2c:leftmost-captures
Igual que la opción --leftmost-captures, pero se puede configurar por bloque.
re2c:captvars, re2c:leftmost-captvars
Igual que la opción --leftmost-captvars, pero se puede configurar por bloque.
re2c:case-insensitive, re2c:flags:case-insensitive
Igual que la opción --case-insensitive, pero se puede configurar por bloque.
re2c:case-inverted, re2c:flags:case-inverted
Igual que la opción --case-inverted, pero se puede configurar por bloque.
re2c:case-ranges, re2c:flags:case-ranges
Igual que la opción --case-ranges, pero se puede configurar por bloque.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Igual que la opción --computed-gotos, pero se puede configurar por bloque.
re2c:computed-gotos:relative, re2c:cgoto:relative
Igual que la opción --computed-gotos-relative, pero se puede configurar por bloque.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si se utiliza goto calculado, esta configuración especifica el umbral de complejidad que desencadena la generación de tablas de salto en lugar de declaraciones if anidadas y mapas de bits. El valor predeterminado es 9.
re2c:cond:abort
Si se establece en un valor entero positivo, el caso predeterminado en el dispatch de condición generado aborta la ejecución del programa.
re2c:cond:goto
Especifica una pieza de código utilizada para las reglas de atajo autogeneradas :=> en las condiciones. El valor predeterminado es goto @@;. El marcador de posición @@ se sustituye con el nombre de la condición (ver configuraciones re2c:api:sigil y re2c:cond:goto@cond).
re2c:cond:goto@cond
Especifica el sigilo utilizado para la sustitución de argumentos en la definición de re2c:cond:goto. El valor predeterminado es @@. Anula la configuración más genérica re2c:api:sigil.
re2c:cond:divider
Define el divisor para los bloques de condiciones. El valor predeterminado es /* *********************************** */. Los marcadores de posición se sustituyen con el nombre de la condición (ver re2c:api;sigil y re2c:cond:divider@cond).
re2c:cond:divider@cond
Especifica el sigilo utilizado para la sustitución de argumentos en la definición de re2c:cond:divider. El valor predeterminado es @@. Anula la configuración más genérica re2c:api:sigil.

INTERNAL TOKENS

These tokens are used internally by re2c to communicate with the generated lexer. Most of them are optional and depend on the generation options.

YYACCEPT
An action that stops the lexer. It takes one argument: the rule number (zero-based) that should be reported as matched. The argument is an r-value.
YYBACKUP
An action that saves the current input position (to be restored with YYRESTORE later).
YYBACKUPCTX
An action that saves the current input position as the position of the trailing context (to be restored with YYRESTORECTX later).
YYCharacters
The type of the characters used in the input. This must be an integral type and it is generated by default. Users are supposed to use this type in their custom definitions of YYSTYPE and YYST

vacuously true.

YYCODE
A block of code that is inserted in the generated lexer. The first element is the code itself; subsequent elements define function arguments: first, the expression for the argument used in the function body (usually just a name); second, the argument type; third, an optional formal parameter (it defaults to the first component - usually both the argument and the parameter are the same identifier).
YYCTYPE
The type of the characters used in the input. This must be an integral type and it is generated by default. Users are supposed to use this type in their custom definitions of YYSTYPE and YYST.
YYFILL
A generic API primitive with one variable n. It should be defined as an r-value of integral type that returns the number of characters filled in the input buffer. Returns 0 if there are no more characters in the input.
YYLESSTHAN
A generic API primitive with one variable len. It should be defined as an r-value of boolean type that equals true if and only if there are less than len input characters left.
YYMAXFILL
An integral constant equal to the maximum value of the argument to YYFILL. It can be generated with a max block.
YYMAXNMATCH
An integral constant equal to the maximal number of POSIX capturing groups in a rule. It is generated with a maxnmatch block.
YYMTAGN
A generic API primitive with one variable tag. YYMTAGN should append a value that represents non-existent input position position to the submatch history of tag (see the submatch extraction section for details).
YYMTAGP
A generic API primitive with one variable tag. YYMTAGP should append the current position to the submatch history of tag (see the submatch extraction section for details).
YYPOP
An action that pops the current state from the state stack. It takes one argument: the rule number that should be returned.
YYPUSH
An action that pushes the current state onto the state stack. It takes one argument: the rule number that should be returned.
YYPEEK
A generic API primitive with no variables. It should be defined as an r-value of type YYCTYPE that is equal to the character at the current input position.
YYRESTORE
A generic API primitive that should restore the current input position to the value saved by YYBACKUP.
YYRESTORECTX
A generic API primitive that should restore the trailing context position saved with YYBACKUPCTX.
YYRESTORETAG
A generic API primitive with one variable tag that should restore the trailing context position to the value of tag.
YYSETCONDITION
Sets the current condition. It takes one argument: the condition name.
YYSHIFT
A generic API primitive with one variable shift that should shift the current input position by shift characters (the shift value may be negative).
YYSHIFTSTAG
A generic API primitive with two variables, tag and shift that should shift tag by shift code units (the shift value may be negative).
YYSHIFTMTAG
A generic API primitive with two variables, tag and shift that should shift the latest value in the history of tag by shift code units (the shift value may be negative).
YYSKIP
A generic API primitive that should advance the current input position by one code unit.
YYSTAGN
A generic API primitive with one variable tag, where tag can be a pointer or an offset in YYINPUT (see submatch extraction section for details). YYSTAGN should to set tag to a value that represents non-existent input position.
YYSTAGP
A generic API primitive with one variable tag, where tag can be a pointer or an offset in YYINPUT (see submatch extraction section for details). YYSTAGP should set tag to the current input position.
YYSTEXTEND
An action that extends the current match. Takes one argument, the number of characters to extend the match with.
YYTEXTPREVIOUS
An action that sets the current match to the previous one. Takes no arguments.
YYTEXTSWAP
An action that swaps the current match with the previous one. Takes no arguments.
YYTRANSLATE
An action that translates the input buffer. It takes one argument: a pointer to the translation table.
YYVERIFY
An action that verifies the input buffer. It takes two arguments: the starting position of the buffer and the length of the buffer.
YYWIDTH
An action that sets the width of the current match. Takes one argument: the width of the match.
YYWIDTHPREVIOUS
An action that sets the width of the current match to the previous one. Takes no arguments.
YY_RETURN
An action that returns a value from the lexer. It takes one argument: the value to return. The return type is defined by the lexer's return type.
yyaccept
An l-value of unsigned integral type that stores the number of the latest matched rule. User definition is necessary only with --storable-state option.
yybm
A table containing compressed bitmaps for up to 8 transitions (used with the --bitmaps option). The table contains 256 elements and is indexed by 1-byte code units. Each 8-bit element combines boolean values for up to 8 transitions. k-Th bit of n-th element is true iff n-th code unit is in the range of k-th transition. The idea of this bitmap is to replace many if branches or switch cases with one check of a single bit in the table.
yych
An l-value of type YYCTYPE that stores the current input character. User definition is necessary only with -f --storable-state option.
yyctable
Jump table generated for the initial condition dispatch (enabled with the combination of --conditions and --computed-gotos options).
yyfill
An l-value that stores the result of YYFILL call (this may be necessary for pure functional languages, where YYFILL is a monadic function with complex return value).
yynmatch
An l-value of unsigned integral type that stores the number of POSIX capturing groups in the matched rule. Used only with -P --posix-captures option.
yypmatch
An array of l-values that are used to hold the tag values corresponding to the capturing parentheses in the matching rule. Array length must be at least yynmatch * 2 (usually YYMAXNMATCH * 2 is a good choice). Used only with -P --posix-captures option.
yystable
Deprecated.
yystate
An l-value used with the --loop-switch option to store the current DFA state.
yytarget
Jump table that contains jump targets (label addresses) for all transitions from a state. This table is local to each state. Generation of yytarget tables is enabled with --computed-gotos option.

Options

Some of the options have corresponding configurations, others are global and cannot be changed after re2c starts reading the input file. Debug options generally require building re2c in debug configuration. Internal options are useful for experimenting with the algorithms used in re2c.

-? --help -h
Show help message.
--api <simple | record | generic>
Specify the API used by the generated code to interface with used-defined code. Option simple shold be used in simple cases when there's
no necesidad de recargar el búfer y almacenar el estado del lexer. La opción record debería usarse cuando el estado del lexer necesita ser almacenado en un registro (struct, clase, etc.). La opción generic debería usarse en casos complejos cuando las otras dos APIs no son lo suficientemente flexibles.
--bit-vectors -b
Optimiza los saltos condicionales usando máscaras de bits. Esta opción implica --nested-ifs.
--captures, --leftmost-captures
Habilita la extracción de subcoincidencias con grupos de captura codiciosos de izquierda a derecha. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla de coincidencia.
--captvars, --leftmost-captvars
Habilita la extracción de subcoincidencias con grupos de captura codiciosos de izquierda a derecha. El resultado se recopila en variables yytl<k>, yytr<k> para el k-ésimo grupo de captura.
--case-insensitive
Trata las cadenas entre comillas simples y comillas dobles como si no distinguieran entre mayúsculas y minúsculas.
--case-inverted
Invierte el significado de las cadenas entre comillas simples y comillas dobles: trata las cadenas entre comillas simples como sensibles a mayúsculas y minúsculas y las cadenas entre comillas dobles como insensibles a mayúsculas y minúsculas.
--case-ranges
Colapsa casos consecutivos en sentencias switch en un rango de la forma bajo ... alto. Esta sintaxis es una extensión del lenguaje C/C++ que es soportada por compiladores como GCC, Clang y Tcc. La principal ventaja sobre usar casos individuales es un código generado más pequeño y un tiempo de generación más rápido, aunque para algunos compiladores como Tcc también resulta en un tamaño de binario más pequeño.
--computed-gotos -g
Optimiza los saltos condicionales usando la extensión no estándar "computed goto" (que debe ser soportada por el compilador). re2zig genera tablas de saltos solo en casos complejos con muchas ramas condicionales. El umbral de complejidad puede configurarse con la configuración cgoto:threshold. Los desplazamientos relativos pueden habilitarse con la configuración cgoto:relative. Esta opción implica --bit-vectors.
--computed-gotos-relative
Similar a --computed-gotos pero genera desplazamientos relativos para las tablas de saltos en su lugar (lo que debe ser soportado por el compilador). Esta opción implica --computed-gotos.
--conditions --start-conditions -c
Habilita el soporte de "condiciones" al estilo Flex: múltiples lexers interrelacionados dentro de un solo bloque. Esta es una alternativa a especificar manualmente diferentes bloques de re2zig conectados con goto o llamadas a funciones.
--depfile FILE
Escribe la información de dependencias en FILE en forma de una regla de Makefile <archivo-salida> : <archivo-entrada> [archivo-incluido ...]. Esto permite rastrear las dependencias de compilación en presencia de bloques/directivas include, de modo que la actualización de los archivos de inclusión active la regeneración del archivo de salida. Esta opción depende de la opción --output.
--ebcdic --ecb -e
Genera un lexer que lee la entrada en codificación EBCDIC. re2zig asume que el rango de caracteres es 0 -- 0xFF y el tamaño del carácter es de 1 byte.
--empty-class <match-empty | match-none | error>
Define la forma en que re2zig trata las clases de caracteres vacías. Con match-empty (el predeterminado) la clase vacía coincide con la entrada vacía (lo cual es ilógico, pero compatible con versiones anteriores). Con match-none la clase vacía siempre falla al coincidir. Con error la clase vacía genera un error de compilación.
--encoding-policy <fail | substitute | ignore>
Define la forma en que re2zig trata los sustitutos Unicode. Con fail re2zig termina con un error cuando se encuentra un sustituto. Con substitute re2zig reemplaza silenciosamente los sustitutos con el punto de código de error 0xFFFD. Con ignore (el predeterminado) re2zig trata los sustitutos como puntos de código normales. El estándar Unicode dice que los sustitutos independientes no son válidos, pero las bibliotecas y programas del mundo real se comportan de diferentes maneras.
--flex-syntax -F
Soporte parcial para la sintaxis de Flex: en este modo las definiciones nombradas no necesitan el signo igual ni el punto y coma de terminación, y cuando se usan deben estar rodeadas con llaves. Los nombres sin llaves se tratan como cadenas entre comillas dobles.
--goto-label
Utiliza el modelo de código "goto/label": codifica el DFA en forma de bloques de código con etiquetas conectados con transiciones goto entre bloques. Esto solo es compatible con lenguajes que tienen una sentencia goto.
--header --type-header -t HEADER
Genera un archivo HEADER. El contenido del archivo puede especificarse usando bloques especiales header:on y header:off. Si se usan condiciones, la cabecera generada tendrá un enum de condiciones añadido automáticamente (a menos que haya un bloque conditions explícito).
-I PATH
Agrega PATH a la lista de ubicaciones que se utilizan al buscar archivos de inclusión. Esta opción es útil en combinación con bloques o directivas include. re2zig busca FILE en el directorio del archivo padre y en las ubicaciones de inclusión especificadas con la opción -I.
--input <default | custom>
Alias obsoleto para --api. La opción default corresponde a simple (es de hecho el predeterminado para la mayoría de los backends, pero no para todos). La opción custom corresponde a generic.
--input-encoding <ascii | utf8>
Especifica la forma en que re2zig analiza las expresiones regulares. Con ascii (el predeterminado) re2zig maneja la entrada como codificada en ASCII: cualquier secuencia de unidades de código es una secuencia de caracteres independientes de 1 byte. Con utf8 re2zig maneja la entrada como codificada en UTF8 y reconoce caracteres multibyte.
--invert-captures
Invierte el significado de los grupos de captura y no captura. Por defecto (...) es de captura y (! ...) no es de captura. Con esta opción (! ...) es de captura y (...) no es de captura.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Especifica el lenguaje de destino. Los lenguajes soportados son C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (se pueden añadir más lenguajes a través de archivos de sintaxis definidos por el usuario, consulte la opción --syntax). La opción none deshabilita las configuraciones de sintaxis predeterminadas, de modo que el lenguaje de destino no esté definido.
--location-format <gnu | msvc>
Especifica el formato de ubicación en los mensajes. Con gnu las ubicaciones se imprimen como 'nombrearchivo:línea:columna: ...'. Con msvc las ubicaciones se imprimen como 'nombrearchivo(línea,columna) ...'. El predeterminado es gnu.
--loop-switch
Utiliza el modelo de código "loop/switch": codifica el DFA en forma de un bucle sobre una sentencia switch, donde los estados individuales son casos del switch. El estado se almacena en una variable yystate. Las transiciones entre estados actualizan yystate a la etiqueta del caso del estado de destino y continúan la ejecución hasta el inicio del bucle.
--nested-ifs -s
Utiliza sentencias if anidadas en lugar de sentencias switch en los saltos condicionales. Esto generalmente resulta en un código más eficiente con compiladores que no optimizan.
--no-debug-info -i
No genera directivas de línea. Esto puede ser útil cuando el código generado se almacena en un sistema de control de versiones (para evitar diffs autogenerados enormes en pequeños cambios).
--no-generation-date
Suprime la salida de fecha en el archivo generado.
--no-version
Suprime la salida de versión en el archivo generado.
--no-unsafe
No genera un wrapper unsafe sobre YYPEEK (esta opción es específica para Rust). Por razones de rendimiento, YYPEEK debería evitar la comprobación de límites, ya que el lexer ya realiza comprobaciones de fin de entrada de manera más eficiente. El usuario puede optar por proporcionar una definición YYPEEK segura, o una definición que solo sea insegura en compilaciones de lanzamiento, en cuyo caso la opción --no-unsafe ayuda a evitar advertencias sobre bloques unsafe redundantes.
--output -o OUTPUT
Especifica el archivo OUTPUT.
--posix-captures, -P
Habilita la extracción de subcoincidencias con grupos de captura al estilo POSIX. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla de coincidencia.
--posix-captvars
Habilita la extracción de subcoincidencias con grupos de captura al estilo POSIX. El resultado se recopila en variables yytl<k>, yytr<k> para el k-ésimo grupo de captura.
--recursive-functions
Utiliza el modelo de código basado en funciones co-recursivas, donde cada estado del DFA es una función separada que puede llamar a otras funciones de estado o a sí misma.
--reusable -r
Obsoleto desde la versión 2.2 (los bloques reutilizables están permitidos por defecto ahora).
--skeleton -S
Ignora el código de interfaz definido por el usuario y genera un programa "esqueleto" autocontenido. Adicionalmente, genera archivos de entrada con cadenas derivadas de la gramática regular
r y resultados de coincidencias comprimidos que se utilizan para verificar el comportamiento del "esqueleto" en todas las entradas. Esta opción es útil para encontrar errores en las optimizaciones y la generación de código. Esta opción solo se admite para C.
--storable-state -f
Genera un lexer que puede almacenar su estado interno. Esto es útil en lexers de modelo push que son detenidos por un programa externo cuando no hay suficiente entrada y luego se reanudan cuando hay más entrada disponible. En este modo, los usuarios deben definir adicionalmente las primitivas YYGETSTATE y YYSETSTATE, y las variables yych, yyaccept y state deben formar parte del estado del lexer almacenado.
--syntax FILE
Carga configuraciones del FILE especificado y las aplica sobre el archivo de sintaxis predeterminado. Tenga en cuenta que FILE puede definir solo unas pocas configuraciones (si se utiliza para modificar el archivo de sintaxis predeterminado), o puede definir un backend de lenguaje completamente nuevo (en este último caso, se recomienda utilizar la opción --lang none).
--tags -T
Habilita la extracción de subcoincidencias con etiquetas.
--ucs2 --wide-chars -w
Genera un lexer que lee entrada codificada en UCS2. re2zig asume que el rango de caracteres es 0 -- 0xFFFF y el tamaño del carácter es de 2 bytes. Esta opción implica --nested-ifs.
--utf8 --utf-8 -8
Genera un lexer que lee entrada en codificación UTF-8. re2zig asume que el rango de caracteres es 0 -- 0x10FFFF y el tamaño del carácter es de 1 byte.
--utf16 --utf-16 -x
Genera un lexer que lee entrada codificada en UTF16. re2zig asume que el rango de caracteres es 0 -- 0x10FFFF y el tamaño del carácter es de 2 bytes. Esta opción implica --nested-ifs.
--utf32 --unicode -u
Genera un lexer que lee entrada codificada en UTF32. re2zig asume que el rango de caracteres es 0 -- 0x10FFFF y el tamaño del carácter es de 4 bytes. Esta opción implica --nested-ifs.

Emite un mensaje corto en caso de éxito.
--vernum -V
Muestra información de la versión en formato MMmmpp (mayor, menor, parche).

Muestra información de la versión.

Emite invocaciones de YYDEBUG en el código generado. Esto es útil para rastrear la ejecución del lexer.

Opción de depuración: emite el DFA después de la canalización (en formato .dot).
--dump-cfg
Opción de depuración: emite el grafo de flujo de control de variables de etiqueta (en formato .dot).

Opción de depuración: emite estadísticas sobre el número de estados en el cierre.

Opción de depuración: emite el DFA inmediatamente después de la determinización (en formato .dot).
--dump-dfa-min
Opción de depuración: emite el DFA después de la minimización (en formato .dot).
--dump-dfa-tagopt
Opción de depuración: emite el DFA después de las optimizaciones de etiquetas (en formato .dot).

Opción de depuración: emite el DFA en construcción con estados representados como árboles de historial de etiquetas (en formato .dot).
--dump-dfa-raw
Opción de depuración: emite el DFA en construcción con conjuntos de estados expandidos (en formato .dot).

Opción de depuración: emite la tabla de interferencia producida por el análisis de vivacidad de variables de etiqueta.

Opción de depuración: emite el NFA (en formato .dot).

En lugar de la salida normal, genera el grafo del lexer en formato .dot. La salida se puede convertir en una imagen con la ayuda de Graphviz (por ejemplo, algo como dot -Tpng -odfa.png dfa.dot).
--dfa-minimization <moore | table>
Opción interna: algoritmo de minimización de DFA utilizado por re2zig. La opción moore es el algoritmo de Moore (es el predeterminado). La opción table es el algoritmo de "llenado de tablas". Ambos algoritmos deberían producir el mismo DFA hasta el reetiquetado de estados; el llenado de tablas es más simple y mucho más lento, y sirve como implementación de referencia.
--eager-skip
Opción interna: hace que el lexer generado avance la posición de entrada activamente, inmediatamente después de leer el símbolo de entrada. Esto cambia el comportamiento predeterminado cuando la posición de entrada se avanza perezosamente, después de la transición al siguiente estado.
--no-lookahead
Opción interna, obsoleta. Solía habilitar el algoritmo TDFA(0). A diferencia de TDFA(1), el algoritmo TDFA(0) no utiliza la previsualización de un solo símbolo. Aplica operaciones de registro a las transiciones entrantes en lugar de las salientes. Las pruebas benchmarks mostraron que el algoritmo TDFA(0) es menos eficiente que TDFA(1).
--no-optimize-tags
Opción interna: suprime la optimización de variables de etiqueta (útil para depuración).
--posix-closure <gor1 | gtop>
Opción interna: especifica el algoritmo de camino más corto utilizado para la construcción del cierre epsilon con semántica de desambiguación POSIX: gor1 (el predeterminado) significa el algoritmo de Goldberg-Radzik, y gtop significa el algoritmo de "orden topológico global".
--posix-prectable <complex | naive>
Opción interna: especifica el algoritmo utilizado para calcular la tabla de precedencia POSIX. El algoritmo complex calcula la tabla de precedencia en una sola travesía del árbol de historial de etiquetas y tiene una complejidad cuadrática en el número de estados TNFA; es el predeterminado. El algoritmo naive tiene una complejidad cúbica en el peor de los casos en el número de estados TNFA, pero es mucho más simple que complex y puede ser ligeramente más rápido en casos no patológicos.
--stadfa
Opción interna, obsoleta. Solía habilitar el algoritmo staDFA, que se diferencia de TDFA en que las operaciones de registro se colocan en los estados en lugar de en las transiciones. Las pruebas benchmarks mostraron que el algoritmo staDFA es menos eficiente que TDFA.
--fixed-tags <none | toplevel | all>
Opción interna: especifica si la optimización de etiquetas fijas debe aplicarse a todas las etiquetas (all), a ninguna de ellas (none), o solo a las de la concatenación de nivel superior (toplevel). El valor predeterminado es all. Las etiquetas "fijas" son aquellas que se encuentran a una distancia fija de alguna otra etiqueta (llamada "base"). En tales casos, solo es necesario rastrear la etiqueta base, y el valor de la etiqueta fija se puede calcular como el valor de la etiqueta base más un desplazamiento estático. Para etiquetas que están bajo alternativas o repeticiones, también es necesario verificar si la etiqueta base tiene un valor de no coincidencia (en ese caso, la etiqueta fija también debe establecerse en no coincidencia, ignorando el desplazamiento). Para etiquetas en concatenación de nivel superior, no es necesario verificar, ya que siempre coinciden.

Advertencias

Las advertencias se pueden habilitar, deshabilitar individualmente y convertir en un error.

-W
Activa todas las advertencias.
-Werror
Convierte las advertencias en errores. Tenga en cuenta que esta opción sola no activa ninguna advertencia; solo afecta a las advertencias que se han activado hasta ahora o que se activarán más adelante.
-W<warning>
Activa la advertencia.
-Wno-<warning>
Desactiva la advertencia.
-Werror-<warning>
Activa la advertencia y la trata como un error (esto implica -W<warning>).
-Wno-error-<warning>
No trata esta advertencia en particular como un error. Esto no desactiva la advertencia en sí.
-Wcondition-order
Advierte si el programa generado hace suposiciones implícitas sobre la numeración de las condiciones. Se debe usar la opción --header o el bloque conditions para generar un mapeo de nombres de condiciones a números y luego usar los nombres de condiciones autogenerados.
-Wempty-character-class
Advierte si una expresión regular contiene una clase de caracteres vacía. Intentar coincidir con una clase de caracteres vacía no tiene sentido: siempre debería fallar. Sin embargo, por razones de compatibilidad con versiones anteriores, re2zig permite clases de caracteres vacías y las trata como cadenas vacías. Utilice la opción --empty-class para cambiar el comportamiento predeterminado.
-Wmatch-empty-string
Advierte si una regla es anulable (coincide con una cadena vacía). Si el lexer se ejecuta en un bucle y la coincidencia vacía no es intencional, el lexer puede colgarse inesperadamente en un bucle infinito.
-Wswapped-range
Advierte si el límite inferior de un rango es mayor que
en su límite superior. El comportamiento predeterminado es intercambiar silenciosamente los límites del rango.
-Wundefined-control-flow
Advertir si algunas cadenas de entrada causan un flujo de control indefinido en el lexer (se informan los patrones erróneos). Este es un error peligroso y común. Se puede solucionar fácilmente agregando la regla predeterminada * que tiene la menor prioridad, coincide con cualquier unidad de código y siempre consume una sola unidad de código.
-Wunreachable-rules
Advertir sobre reglas que están ocultas por otras reglas y que nunca coincidirán.
-Wdeprecated-eof_rule
Advertir sobre reglas de fin de entrada independientes $ que se romperán por cambios futuros y requerirán corrección. En este momento, estas reglas tienen precedencia al entrar en conflicto con otras reglas, pero después de la introducción del símbolo de fin de entrada generalizado $ el orden de precedencia cambiará y estas reglas quedarán ocultas por otras reglas.
-Wuseless-escape
Advertir si un símbolo se escapa cuando no debería. Por defecto, re2zig ignora silenciosamente tales escapes, pero esto también puede indicar un error tipográfico o un error en la secuencia de escape.
-Wnondeterministic-tags
Advertir si una etiqueta tiene un grado de nondeterminismo de n, donde n es mayor que 1.
-Wsentinel-in-midrule
Advertir si el símbolo centinela ocurre en medio de una regla --- esto puede causar lecturas más allá del final del búfer, fallos o corrupción de memoria en el lexer generado. Esta advertencia solo es aplicable si se utiliza el método centinela para verificar el final de la entrada. Se establece como un error si se utiliza la configuración re2c:sentinel.
-Wundefined-syntax-config
Advertir si el archivo de sintaxis especificado con la opción --syntax carece de definiciones de algunas configuraciones. Esto ayuda a mantener los archivos de sintaxis definidos por el usuario: si una nueva versión agrega configuraciones, el archivo de sintaxis antiguo generará una advertencia y se notificará al usuario. Si algunas configuraciones no se utilizan y no necesitan una definición, deben establecerse explícitamente en <undefined>.

Archivos de sintaxis

El soporte para diferentes lenguajes en re2c se basa en la idea de *archivos de sintaxis*. Un archivo de sintaxis es un archivo de configuración que define la sintaxis del lenguaje de destino — no todo el lenguaje, sino una pequeña parte de él que es utilizada por el código generado. Los archivos de sintaxis hacen que re2c sea muy flexible, pero no deben usarse como un reemplazo para las configuraciones de re2c:: su propósito es definir la sintaxis del lenguaje de destino, no personalizar un lexer en particular. Todos los lenguajes compatibles tienen archivos de sintaxis predeterminados que forman parte de la distribución (ver subdirectorio include/syntax); también están incrustados en el binario re2zig. Los usuarios pueden proporcionar un archivo de sintaxis personalizado que anule algunas configuraciones para uno de los lenguajes compatibles, o pueden optar por redefinir todas las configuraciones (en ese caso se debe usar la opción --lang none). Los archivos de sintaxis contienen configuraciones de cuatro tipos diferentes: listas de características, configuraciones de lenguaje, configuraciones in-situ y plantillas de código.

Listas de características

Algunas configuraciones de lista definen varias características soportadas por un backend dado, para que re2zig pueda dar un error claro si el usuario intenta habilitar una característica no soportada:
supported_apis
Una lista de APIs soportadas con elementos posibles simple, record, generic.
supported_api_styles
Una lista de estilos de API soportados con elementos posibles functions, free-form.
supported_code_models
Una lista de modelos de código soportados con elementos posibles goto-label, loop-switch, recursive-functions.
supported_targets
Una lista de destinos de generación de código soportados con elementos posibles code, dot, skeleton.
supported_features
Una lista de características soportadas con elementos posibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Plantillas de código

Las plantillas de código definen la sintaxis del lenguaje de destino. Están escritas en un lenguaje simple específico del dominio con la siguiente gramática formal: 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Una plantilla de código es una secuencia de literales de cadena, variables, elementos opcionales y listas, o una referencia a otra plantilla de código, o un valor especial <undefined>. Las variables son marcadores de posición que se sustituyen durante la fase de generación de código. Las variables de lista son especiales: al expandir plantillas de lista, re2zig repite las expresiones del lado derecho de la columna varias veces, reemplazando cada vez las ocurrencias de la variable de lista con un valor específico para esa repetición. Las listas tienen límites opcionales (los valores negativos se cuentan desde el final, por ejemplo, -1 significa el último elemento). Los nombres condicionales comienzan con un punto. Tanto los condicionales como las variables pueden ser locales (específicos de la plantilla de código dada) o globales (permitidos en todas las plantillas de código). Cuando re2zig lee el archivo de sintaxis, verifica que cada plantilla de código utilice solo las variables y los condicionales permitidos en ella.

Por ejemplo, la siguiente plantilla de código define una construcción if-then-else para un lenguaje similar a C:

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Aquí branch es una variable de lista: branch{0} se expande a la primera rama (que es especial, ya que no hay parte else), branch{1:-1} se expande a todas las ramas restantes (si las hay). stmt también es una variable de lista: [stmt: stmt] es una lista anidada que se expande a una lista de sentencias en el cuerpo de la rama actual. topindent, indent, dedent y nl son variables globales, y .cond es una condición local (su significado se describe a continuación). Esta plantilla de código podría producir el siguiente código:

if x {
    // haz algo
} else if y {
    // haz otra cosa
} else {
    // no hagas nada
}

Aquí hay una lista de todas las plantillas de código soportadas por re2zig con sus variables y condiciones locales. Tenga en cuenta que una definición particular puede, pero no tiene por qué, utilizar variables y condiciones locales. Todas las plantillas de código no utilizadas deben establecerse en <undefined>.

code:var_local
Declaración o definición de una variable local. Variables soportadas: type (el tipo de la variable), name (su nombre) e init (valor inicial, si lo hay). Condiciones: .init (verdadero si hay un inicializador).
code:var_global
Igual que code:var_local, excepto que se utiliza en el nivel superior.
code:const_local
Definición de una constante local. Variables soportadas: type (el tipo de la constante), name (su nombre) e init (valor inicial).
code:const_global
Igual que code:const_local, excepto que se utiliza en el nivel superior.

Comprobaciones de límites con relleno

Este ejemplo utiliza comprobaciones de límites con relleno para manejar el final de la entrada (este método está habilitado por defecto). El programa cuenta cadenas de un solo guion entrecomilladas separadas por espacios. Hay un relleno de YYMAXFILL caracteres nulos añadidos al final de la entrada, donde el valor de YYMAXFILL se genera automáticamente con un bloque max. No es necesario utilizar nulos para el relleno; se pueden utilizar cualesquiera caracteres siempre que no formen un sufijo de lexema válido (en este ejemplo, el relleno no debe contener comillas simples, ya que pueden confundirse con un sufijo de una cadena entre comillas simples). Hay una regla de “stop” que coincide con el primer carácter de relleno (nulo) y termina el lexer (tenga en cuenta que comprueba si el nulo está al principio del relleno, de lo contrario es un error de sintaxis). Las comprobaciones de límites solo se generan en algunos estados determinados por los componentes fuertemente conectados del autómata subyacente. Las comprobaciones tienen la forma (YYLIMIT - YYCURSOR) < n o YYLESSTHAN(n) con la API genérica, donde n es el número mínimo de caracteres necesarios para que el lexer continúe (esto también significa que la próxima comprobación de límites ocurrirá en como máximo n caracteres). Si la condición de comprobación es verdadera, el lexer ha llegado al final de la entrada e invocará YYFILL(n) que debería suministrar al menos n caracteres de entrada o no devolver. En este ejemplo, YYFILL siempre falla y termina el lexer con un error (lo cual está bien porque la entrada cabe en un solo búfer). Vea la sección YYFILL con relleno para ver un ejemplo que rellena el búfer de entrada con YYFILL.

// re2zig $INPUT -o $OUTPUT
const std = @import("std");
%{max %}
fn lex(str: []const u8) !i32 {
    // Create a copy of the input string padded with yymaxfill zeroes at the end.
    var yyinput = try std.testing.allocator.alloc(u8, str.len + yymaxfill);
    defer std.testing.allocator.free(yyinput);
    std.mem.copyForwards(u8, yyinput[0..], str);
    std.mem.copyForwards(u8, yyinput[str.len..], &[_]u8{0} ** yymaxfill); // zero padding
    var yycursor: usize = 0;
    const yylimit: usize = yyinput.len;
    var count: i32 = 0;
    loop: while (true) {
        %{
            re2c:YYFILL = "return -1;";
            str = ['] ([^'\\] | [\\][^])* ['];
            [\x00] {
                // Check that it is the sentinel, not some unexpected null.
                return if (yycursor - 1 == str.len) count else -1;
            }
            str  { count += 1; continue :loop; }
            [ ]+ { continue :loop; }
            *    { return -1; }
        %}
    }
}
test {
    try std.testing.expectEqual(lex(""), 0);
    try std.testing.expectEqual(lex("'qu\x00tes' 'are' 'fine: \\'' "), 3);
    try std.testing.expectEqual(lex("'unterminated\\'"), -1);
    try std.testing.expectEqual(lex("'unexpected \x00 null\\'"), -1);
}

Comprobaciones personalizadas

Este ejemplo utiliza un método personalizado de manejo del final de la entrada basado en la API genérica. El programa cuenta cadenas de un solo guion entrecomilladas separadas por espacios. Es igual que el ejemplo de sentinela, excepto que la entrada no está terminada en nulo. Para compensar la ausencia de un carácter centinela al final de la entrada, YYPEEK se redefine para realizar una comprobación de límites antes de leer el siguiente carácter de entrada. Esto es ineficiente porque las comprobaciones se realizan con mucha frecuencia. Si la condición de comprobación falla, YYPEEK devuelve el carácter real, de lo contrario devuelve un carácter centinela falso.

// re2zig $INPUT -o $OUTPUT
const std = @import("std");
// Expects a string without terminating null.
fn lex(str: []const u8) i32 {
    var cur: usize = 0;
    var count: i32 = 0;
    loop: while (true) {
        %{
            re2c:api = generic;
            re2c:yyfill:enable = 0;
            // YYPEEK returns "fake" terminating null if cursor has reached limit.
            re2c:YYPEEK = "if (cur >= str.len) 0 else str[cur]";
            re2c:YYSKIP = "cur += 1;";
            *      { return -1; }
            [\x00] { return count; }
            [a-z]+ { count += 1; continue :loop; }
            [ ]+   { continue :loop; }
        %}
    }
}
test {
    try std.testing.expectEqual(lex(""), 0);
    try std.testing.expectEqual(lex("one two three"), 3);
    try std.testing.expectEqual(lex("f0ur"), -1);
}

RELLENO DEL BÚFER

La necesidad de almacenamiento en búfer surge cuando la entrada no se puede mapear en memoria a la vez: o bien es demasiado grande, o bien proviene de forma continua (como al leer de un socket). La técnica habitual en tales casos es asignar un búfer de memoria de tamaño fijo y procesar la entrada en fragmentos que quepan en el búfer. Cuando se procesa el fragmento actual, se extrae y se introduce nueva información. En la práctica es algo más complejo, ya que el estado del lexer consta no de una sola posición de entrada, sino de un conjunto de posiciones interrelacionadas:

  • cursor: el siguiente carácter de entrada a leer (YYCURSOR en la API de punteros C o YYSKIP/YYPEEK en la API genérica)
  • límite: la posición después del último carácter de entrada disponible (YYLIMIT en la API de punteros C, manejado implícitamente por YYLESSTHAN en la API genérica)
  • marcador: la posición de la coincidencia más reciente, si la hay (YYMARKER en la API por defecto o YYBACKUP/YYRESTORE en la API genérica)
  • token: el inicio del lexema actual (implícito en la API de re2zig, ya que no es necesario para el funcionamiento normal del lexer y puede ser definido y actualizado por el usuario)
  • marcador de contexto: la posición del contexto de cola (YYCTXMARKER en la API de punteros C o YYBACKUPCTX/YYRESTORECTX en la API genérica)
  • variables de etiquetas: posiciones de subcoincidencia (definidas con bloques stags y mtags y primitivas de API genérica YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

No todas estas se utilizan en todos los casos, pero si se utilizan, deben ser actualizadas por YYFILL. Todas las posiciones activas están contenidas en el segmento entre el token y el cursor, por lo tanto, todo lo que esté entre el inicio del búfer y el token puede ser descartado, el segmento desde el token hasta el límite debe moverse al principio del búfer, y el espacio libre al final del búfer debe llenarse con nueva información. Para evitar llamadas frecuentes a YYFILL, es mejor introducir tantos caracteres de entrada como sea posible (aunque menos caracteres podrían ser suficientes para reanudar el lexer). Los detalles de la implementación de YYFILL son ligeramente diferentes dependiendo de qué método de manejo de EOF se utilice: el caso de la regla de EOF es algo más simple que el caso de la comprobación de límites con relleno. Tenga en cuenta también que si se utiliza la opción -f --storable-state, YYFILL tiene una semántica ligeramente diferente (descrita en la sección sobre estado almacenable).

YYFILL con centinela

Si se utiliza la regla de EOF, YYFILL es una primitiva similar a una función que no acepta argumentos y devuelve un valor que se comprueba frente a cero. La invocación de YYFILL es activada por la condición YYLIMIT <= YYCURSOR en la API de punteros C y YYLESSTHAN() en la API genérica. Un valor de retorno distinto de cero significa que YYFILL ha fallado. Una llamada exitosa a YYFILL debe suministrar al menos un carácter y ajustar las posiciones de entrada en consecuencia. El límite siempre debe establecerse en uno después de la última posición de entrada en el búfer, y el carácter en la posición del límite debe ser el símbolo centinela especificado por la configuración re2c:eof. // re2zig $INPUT -o $OUTPUT
const std = @import("std");
const bufsize = 4095;
const State = struct {
    yyinput: [bufsize + 1]u8,
    yycursor: usize,
    yymarker: usize,
    yylimit: usize,
    token: usize,
    eof: bool
};
fn fill(st: *State, file: anytype) i32 {
    if (st.eof) { return -1; } // unexpected EOF
    // Error: lexeme too long. In real life can reallocate a larger buffer.
    if (st.token < 1) { return -2; }
    // Shift buffer contents (discard everything up to the current token).
    std.mem.copyBackwards(
        u8, st.yyinput[0..st.yylimit - st.token], st.yyinput[st.token..st.yylimit]);
    st.yycursor -= st.token;
    st.yymarker = @subWithOverflow(st.yymarker, st.token)[0];
    st.yylimit -= st.token;
    st.token = 0;
    // Fill free space at the end of buffer with new data from file.
    st.yylimit += file.read(st.yyinput[st.yylimit..bufsize]) catch 0;
    st.yyinput[st.yylimit] = 0; // append sentinel symbol
    // If read less than expected, this is the end of input.
    st.eof = st.yylimit < bufsize;
    return 0;
}
fn lex(yyrecord: *State, file: anytype) i32 {
    var count: i32 = 0;
    loop: while (true) {
        yyrecord.token = yyrecord.yycursor;
        %{
            re2c:api = record;
            re2c:eof = 0;
            re2c:YYFILL = "fill(yyrecord, file) == 0";
            str = ['] ([^'\\] | [\\][^])* ['];
            *    { return -1; }
            $    { return count; }
            str  { count += 1; continue :loop; }
            [ ]+ { continue :loop; }
        %}
    }
}

YYFILL con relleno

En el caso predeterminado (cuando no se utiliza la regla EOF), YYFILL es una primitiva similar a una función que acepta un único argumento y no devuelve ningún valor. La invocación de YYFILL se dispara por la condición (YYLIMIT - YYCURSOR) < n en la API de punteros de C y YYLESSTHAN(n) en la API genérica. El argumento pasado a YYFILL es el número mínimo de caracteres que deben ser suministrados. Si falla en hacerlo, YYFILL no debe devolver el control al lexer (por esa razón es mejor implementarlo como una macro que retorna de la función llamante en caso de fallo). En caso de una invocación exitosa de YYFILL, la posición límite debe establecerse bien en uno después de la última posición de entrada en el búfer, o al final del relleno de YYMAXFILL (en caso de que YYFILL haya leído con éxito al menos n caracteres, pero no suficientes para llenar todo el búfer). // re2zig $INPUT -o $OUTPUT
const std = @import("std");

const bufsize = 4096;
const State = struct {
    yyinput: [bufsize + yymaxfill]u8,
    yycursor: usize,
    yymarker: usize,
    yylimit: usize,
    token: usize,
    eof: bool
};
fn fill(st: *State, need: usize, file: anytype) i32 {
    if (st.eof) { return -1; } // EOF inesperado
    // Error: lexema demasiado largo. En la vida real se puede reasignar un búfer más grande.
    if (st.token < need) { return -2; }
    // Desplazar el contenido del búfer (descartar todo hasta el token actual).
    std.mem.copyBackwards(
        u8, st.yyinput[0..st.yylimit - st.token], st.yyinput[st.token..st.yylimit]);
    st.yycursor -= st.token;
    st.yymarker = @subWithOverflow(st.yymarker, st.token)[0];
    st.yylimit -= st.token;
    st.token = 0;
    // Rellenar el espacio libre al final del búfer con nuevos datos del archivo.
    st.yylimit += file.read(st.yyinput[st.yylimit..bufsize]) catch 0;
    // Si se lee menos de lo esperado, este es el final de la entrada.
    if (st.yylimit < bufsize) {
        st.eof = true;
        @memset(st.yyinput[st.yylimit..st.yylimit + yymaxfill], 0);
        st.yylimit += yymaxfill;
    }
    return 0;
}

    var count: i32 = 0;

        %{
            re2c:api = record;
            re2c:YYFILL = "{ if (fill(yyrecord, @@, file) != 0) return -2; }";
            str = ['] ([^'\\] | [\\][^])* ['];
            [\x00] {
                // Comprobar que es el centinela, no una nulidad inesperada.
                return if (yyrecord.token == yyrecord.yylimit - yymaxfill) count else -1;
            }
            str  { count += 1; continue :loop; }
            [ ]+ { continue :loop; }
            *    { return -1; }
        %}
    }
}
test {
    const fname = "input";
    const content = "'qu\x00tes' 'are' 'fine: \\'' " ** bufsize;
    const count = 3 * bufsize; // número de cadenas entrecomilladas escritas en el archivo
    // Preparar archivo de entrada: varias veces el tamaño del búfer, conteniendo
    // cadenas con ceros y comillas escapadas.

    var fr = try std.fs.cwd().openFile(fname, .{ .mode = .read_only});

    @memset(st.yyinput[st.yylimit..st.yylimit + yymaxfill], 0); // relleno de ceros al final

CARACTERÍSTICAS

Múltiples bloques

A veces es necesario tener múltiples lexers interrelacionados (por ejemplo, si hay una máquina de estados de alto nivel que transiciona entre modos de lexer). Esto se puede implementar utilizando múltiples bloques re2zig conectados. Otra opción es usar condiciones de inicio.

La implementación de conexiones entre bloques depende del lenguaje destino. En lenguajes que tienen la instrucción goto (como C/C++ y Go) se pueden tener todos los bloques en una sola función, cada uno de ellos precedido por una etiqueta. La transición de un bloque a otro es un simple goto. En lenguajes que no tienen goto (como Rust) es necesario utilizar un bucle con un switch sobre una variable de estado, similar al bucle/switch yystate generado por re2zig, o bien encapsular cada bloque en una función y usar llamadas a funciones.

El ejemplo a continuación utiliza múltiples bloques para analizar números binarios, octales, decimales y hexadecimales. Cada base tiene su propio bloque. El bloque inicial determina la base y despacha a otros bloques. Las configuraciones comunes se definen en un bloque separado al principio del programa; son heredadas por los otros bloques.

// re2zig $INPUT -o $OUTPUT
const std = @import("std");
// Almacenar número u32 en u64 durante el análisis para simplificar el manejo de desbordamiento.
const State = struct {
    yyinput: [:0]const u8,
    yycursor: usize,
    yymarker: usize,
    num: u64,
};
// Definiciones comunes de re2c compartidas entre todas las funciones.
%{
    re2c:api = record;
    re2c:yyrecord = st;
    re2c:yyfill:enable = 0;
%}
const ERROR: u64 = @as(u64, std.math.maxInt(u32)) + 1; // desbordamiento
// Añadir dígito con la base dada, comprobando desbordamiento.
fn add(st: *State, offs: u8, base: u64) void {
    const digit = st.yyinput[st.yycursor - 1] - offs;
    st.num = @min(st.num * base + digit, ERROR);
}
// Convertir u64 a u32 opcional (null significa desbordamiento o error de análisis).
fn maybeU32(num: u64) ?u32 {
    return if (num < ERROR) @intCast(num) else null;
}
fn parse_u32(s: [:0]const u8) ?u32 {
    var st = State {.yyinput = s, .yycursor = 0, .yymarker = 0, .num = 0};
    %{
        '0b' / [01]        { return parse_bin(&st); }
        "0"                { return parse_oct(&st); }
        "" / [1-9]         { return parse_dec(&st); }
        '0x' / [0-9a-fA-F] { return parse_hex(&st); }
        *                  { return null; }
    %}
}
fn parse_bin(st: *State) ?u32 {
    bin: while (true) {%{
        [01] { add(st, 48, 2); continue :bin; }
        *    { return maybeU32(st.num); }
    %}}
}
fn parse_oct(st: *State) ?u32 {
    oct: while (true) {%{
        [0-7] { add(st, 48, 8); continue :oct; }
        *     { return maybeU32(st.num); }
    %}}
}
fn parse_dec(st: *State) ?u32 {
    dec: while (true) {%{
        [0-9] { add(st, 48, 10); continue :dec; }
        *     { return maybeU32(st.num); }
    %}}
}
fn parse_hex(st: *State) ?u32 {
    hex: while (true) {%{
        [0-9] { add(st, 48, 16); continue :hex; }
        [a-f] { add(st, 87, 16); continue :hex; }
        [A-F] { add(st, 55, 16); continue :hex; }
        *     { return maybeU32(st.num); }
    %}}
}
test {
    try std.testing.expectEqual(parse_u32(""), null);
    try std.testing.expectEqual(parse_u32("1234567890"), 1234567890);
    try std.testing.expectEqual(parse_u32("0b1101"), 13);
    try std.testing.expectEqual(parse_u32("0x7Fe"), 2046);
    try std.testing.expectEqual(parse_u32("0644"), 420);
    try std.testing.expectEqual(parse_u32("9999999999"), null);
}

Condiciones de inicio

Las condiciones de inicio se habilitan con la opción --start-conditions. Proporcionan una forma de codificar múltiples autómatas interrelacionados dentro del mismo bloque re2zig.

Cada condición corresponde a un autómata individual y tiene un nombre único especificado por el usuario y un número interno único definido por re2zig. Los números se utilizan para cambiar entre condiciones: el código generado utiliza las primitivas YYGETCOND y YYSETCOND para obtener la condición actual o establecerla a un número dado. Utilice el bloque conditions, la opción --header o la configuración re2c:header para generar identificadores de condición numéricos. La configuración re2c:cond:enumprefix especifica el prefijo del identificador generado.

En modo de condición, cada regla debe ir precedida por una lista de nombres de condición separados por comas entre corchetes angulares, o un comodín <*> para denotar todas las condiciones. La sintaxis de la regla se extiende de la siguiente manera:

< lista-condicion > expresion-regular codigo
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular y ejecuta el codigo asociado.
< lista-condicion > expresion-regular => condicion codigo
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular, establece la condición actual a condicion y ejecuta el codigo asociado.
< lista-condicion > expresion-regular :=> condicion
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con
regular-expression y transiciona inmediatamente a condition (no hay ninguna acción semántica).
< condition-list > !action code
Una regla que vincula code al lugar definido por action en cada condición de la condition-list (ver la sección de *actions* para varios tipos de acciones).
<! condition-list > code
Una regla que antepone code a las acciones semánticas de todas las reglas para cada condición en la condition-list. Esta sintaxis está obsoleta y se debe usar la acción !pre_rule en su lugar (hace exactamente lo mismo).
< > code
Una regla que crea una condición de entrada especial con número cero y nombre "0" que ejecuta code antes de saltar a otras condiciones. Esta sintaxis está obsoleta y se debe usar la acción !entry en su lugar (proporciona un control más detallado, ya que el código se puede especificar por condición y se puede saltar directamente al inicio de la condición sin pasar por el despacho de condiciones).
< > => condition code
Igual que la regla anterior, excepto que establece la siguiente condition.
< > :=> condition
Igual que la regla anterior, excepto que no tiene código asociado y salta inmediatamente a condition.

El código que re2zig genera para las condiciones depende de si re2zig utiliza el enfoque de `goto/label` o el enfoque de `loop/switch` para codificar los autómatas.

En lenguajes que tienen la sentencia goto (como C/C++ y Go) las condiciones se implementan de forma natural como bloques de código prefijados con etiquetas de la forma yyc_<cond>, donde cond es un nombre de condición (el prefijo de etiqueta se puede cambiar con re2c:cond:prefix). Las transiciones entre condiciones se implementan usando goto y etiquetas de condición. Antes de todas las condiciones, re2zig genera un `switch` inicial en YYGETSTATE que salta al estado de inicio de la condición actual. Las reglas de acceso directo :=> omiten el `switch` inicial y saltan directamente a la condición especificada (se puede usar re2c:cond:goto para cambiar el comportamiento predeterminado). Las reglas con acciones semánticas no saltan automáticamente a la siguiente condición; esto debe hacerlo el código de acción definido por el usuario.

En lenguajes que no tienen goto (como Rust), re2zig reutiliza la variable yystate para almacenar números de condición. Cada condición recibe un identificador numérico igual al número de su estado de inicio, y un `switch` entre condiciones no es diferente de un `switch` entre estados de DFA de una sola condición. No hay necesidad de un `switch` de condición inicial separado. (Dado que se utiliza el mismo enfoque para implementar estados almacenables, YYGETCOND/YYSETCOND son redundantes si se utilizan tanto estados almacenables como condiciones).

El siguiente programa utiliza condiciones de inicio para analizar números binarios, octales, decimales y hexadecimales. Hay un único bloque donde cada base tiene su propia condición, y la condición inicial está conectada a todas ellas. La variable definida por el usuario cond almacena el número de la condición actual; se inicializa con el número de la condición inicial generada con el bloque conditions.

// re2zig $INPUT -o $OUTPUT -c
const std = @import("std");
%{conditions %}
const ERROR: u64 = @as(u64, std.math.maxInt(u32)) + 1; // desbordamiento
// Añade un dígito con la base dada, comprobando desbordamiento.
fn add(num: *u64, str: [:0]const u8, cur: usize, offs: u8, base: u64) void {
    num.* = @min(num.* * base + (str[cur - 1] - offs), ERROR);
}
fn parse_u32(yyinput: [:0]const u8) ?u32 {
    var yycursor: usize = 0;
    var yymarker: usize = 0;
    var yycond = yycinit;
    var num: u64 = 0; // Almacena el número en u64 para simplificar las comprobaciones de desbordamiento.
    loop: while(true) {
    %{
        re2c:yyfill:enable = 0;
        <init> '0b' / [01]        :=> bin
        <init> "0"                :=> oct
        <init> "" / [1-9]         :=> dec
        <init> '0x' / [0-9a-fA-F] :=> hex
        <init> * { return null; }
        <bin> [01]  { add(&num, yyinput, yycursor, 48, 2);  continue :loop; }
        <oct> [0-7] { add(&num, yyinput, yycursor, 48, 8);  continue :loop; }
        <dec> [0-9] { add(&num, yyinput, yycursor, 48, 10); continue :loop; }
        <hex> [0-9] { add(&num, yyinput, yycursor, 48, 16); continue :loop; }
        <hex> [a-f] { add(&num, yyinput, yycursor, 87, 16); continue :loop; }
        <hex> [A-F] { add(&num, yyinput, yycursor, 55, 16); continue :loop; }
        <bin, oct, dec, hex> * {
            return if (num < ERROR) @intCast(num) else null;
        }
    %}}
}
test {
    try std.testing.expectEqual(parse_u32(""), null);
    try std.testing.expectEqual(parse_u32("1234567890"), 1234567890);
    try std.testing.expectEqual(parse_u32("0b1101"), 13);
    try std.testing.expectEqual(parse_u32("0x7Fe"), 2046);
    try std.testing.expectEqual(parse_u32("0644"), 420);
    try std.testing.expectEqual(parse_u32("9999999999"), null);
}

Estado almacenable

Con la opción --storable-state, re2zig genera un lexer que puede almacenar su estado actual, devolver el control al llamador y luego reanudar las operaciones exactamente donde las dejó. El modo de operación predeterminado en re2zig es un modelo "pull" (tirar), en el que el lexer "tira" de más entrada cuando la necesita. Esto puede ser inaceptable en casos en los que la entrada se pone a disposición pieza por pieza (por ejemplo, si el lexer es invocado por el analizador sintáctico, o si el programa del lexer se comunica a través de un protocolo de socket con otro programa que debe esperar una respuesta del lexer antes de transmitir el siguiente mensaje). La característica de estado almacenable está destinada precisamente a tales casos: permite generar lexers que funcionan en un modelo "push" (empujar). Cuando el lexer necesita más entrada, almacena su estado y devuelve el control al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el lexer exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo "pull":

  • Definir primitivas YYSETSTATE() y YYGETSTATE(state).
  • Definir las variables yych, yyaccept (si se usan) y state como parte del estado persistente del lexer. La variable state debe inicializarse a -1.
  • YYFILL debe devolver el control al programa externo en lugar de intentar proporcionar más entrada. El código de retorno debe indicar que el lexer necesita más entrada.
  • El programa externo debe reconocer situaciones en las que el lexer necesita más entrada y responder apropiadamente.
  • Opcionalmente, usar el bloque getstate para generar el `switch` YYGETSTATE separado del lexer principal. Esto solo funciona para lenguajes que tienen goto (no en el modo --loop-switch).
  • Usar re2c:eof y el método *centinela con comprobaciones de límites* para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo añadir el relleno: el final actual de la entrada puede no ser el final definitivo de la entrada, y añadir relleno demasiado pronto puede cortar un lexema codicioso leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del búfer (lo que ya está bloqueado debido a la condición de fin de entrada).

Aquí hay un ejemplo de un lexer de modelo "push" que simula la lectura de paquetes de un socket. El lexer se ejecuta en un bucle hasta que encuentra el final de la entrada y devuelve el control a la función llamadora. La función llamadora proporciona más entrada "enviando" el siguiente paquete y reanuda el análisis léxico. Este proceso se detiene cuando se envían todos los paquetes, o cuando hay un error.

// re2zig $INPUT -o $OUTPUT -f
const std = @import("std");
const Status = enum {
    end,
    ready,
    waiting,
    bad_packet,
    big_packet
};
// Usa un búfer pequeño para cubrir el caso en que un lexema no cabe.
// En uso real, usa un búfer más grande.
const bufsize = 10;
const State = struct {
    yyinput: [bufsize + 1]u8,
    yycursor: usize,
    yymarker: usize,
    yylimit: usize,
    token: usize,
    yystate: i32,
    received: usize,
};
fn fill(st: *State, file: anytype) Status {
    // Error: lexema demasiado largo. En la vida real, se puede reasignar un búfer más grande.
    if (st.token < 1) { return Status.big_packet; }
    // Desplaza el contenido del búfer (descarta todo hasta el token actual).
    std.mem.copyBackwards(
        u8, st.yyinput[0..st.yylimit - st.token], st.yyinput[st.token..st.yylimit]);
    st.yycursor -= st.token;
    st.yymarker = @subWithOverflow(st.yymarker, st.token)[0];
    st.yylimit -= st.token;
    st.token = 0;
    // Rellena el espacio libre al final del búfer con nuevos datos del archivo.
    st.yylimit += file.read(st.yyinput[st.yylimit..bufsize]) catch 0;
    st.yyinput[st.yylimit] = 0; // añade símbolo centinela
    return Status.ready;
}
fn lex(yyrecord: *State) Status {
    var yych: u8 = 0;
    loop: while (true) {
        yyrecord.token = yyrecord.yycursor;
        %{
            re2c:api = record;
            re2c:eof = 0;
            re2c:YYFILL = "return Status.waiting;";
            packet = [a-z]+[;];
            *      { return Status.bad_packet; }
            $      { return Status.end; }
            packet { yyrecord.received += 1; continue :loop; }
        %}
    }
}
fn run(expect: Status, packets: []const []const u8) !void {
    // Crea una "tubería" (abre el mismo archivo para lectura y escritura).
    const fname = "input";
    var fw = try std.fs.cwd().createFile(fname, .{});
    var fr = try std.fs.cwd().openFile(fname, .{ .mode = .read_only});
    // Inicializa el estado del lexer: el valor de `state` es -1, todos los desplazamientos están al final
    // del búfer. Normalmente, el archivo sería parte del estado, pero el tipo BufferedReader
    // no está claro.
    var br = std.io.bufferedReader(fr.reader());
    var st = State{
        .yyinput = undefined,
        .yycursor = bufsize,
        .yymarker = bufsize,
        .yylimit = bufsize,
        .token = bufsize,
        .yystate = -1,
        .received = 0,
    };
    // El centinela en el desplazamiento `yylimit` se establece en cero, lo que activa YYFILL.
    st.yyinput[st.yylimit] = 0;
    // Bucle principal. El búfer contiene datos incompletos que aparecen paquete a
    // paquete. Cuando el lexer necesita más entrada, guarda su estado interno y
    // devuelve el control al llamador, que debe proporcionar más entrada y reanudar el análisis.
    var status = Status.ready;
    var send: usize = 0;
    while (true) {
        status = lex(&st);
        if (status == Status.end) {
            break;
        } else if (status == Status.waiting) {
            if (send < packets.len) {
                std.log.debug("sending packet {}", .{send});
                try fw.writeAll(packets[send]);
                send += 1;
            }
            status = fill(&st, &br);
            std.log.debug("filled buffer [{s}], status {}", .{st.yyinput, status});
            if (status != Status.ready) {
                break;
            }
        } else if (status == Status.bad_packet) {
            break;
        }
    }
    // Comprobar resultados.
    try std.testing.expectEqual(status, expect);
    if (status == Status.end) { try std.testing.expectEqual(st.received, send); }
    // Limpieza: eliminar archivo de entrada.
    fw.close();
    fr.close();
    try std.fs.cwd().deleteFile(fname);
}
test {
    try run(Status.end, &[_][]const u8{});
    try run(Status.end, &[_][]const u8{"zero;", "one;", "two;", "three;", "four;"});
    try run(Status.bad_packet, &[_][]const u8{"??;"});
    try run(Status.big_packet, &[_][]const u8{"looooooooooooong;"});
}
```

Bloques reutilizables

Los bloques reutilizables de la forma /*!rules:re2c[:<name>] ... */ o %{rules[:<name>] ... %} se pueden reutilizar cualquier número de veces y combinar con otros bloques re2zig. El <name> es opcional. Un bloque de reglas puede usarse en un bloque o directiva use. El código para un bloque de reglas se genera en cada punto de uso.

Los bloques use se definen con /*!use:re2c[:<name>] ... */ o %{use[:<name>] ... %}. El <name> es opcional: si no se especifica, el bloque de reglas asociado es el más reciente (ya sea nombrado o sin nombre). Un bloque use puede agregar definiciones, configuraciones y reglas propias con nombre. Un caso de uso importante para los bloques use es un analizador léxico que admite múltiples codificaciones de entrada: el mismo bloque de reglas se reutiliza varias veces con configuraciones específicas de codificación (ver el ejemplo a continuación).

La directiva use dentro de un bloque !use:<name>; se puede usar desde dentro de un bloque re2zig. Fusiona el bloque referenciado <name> en el actual. Si algunas de las reglas y configuraciones fusionadas se superponen con las definidas previamente, los conflictos se resuelven de la manera habitual: la primera regla tiene prioridad, y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y (en modo de condición) <!>, para las cuales una definición local del bloque anula cualquier herencia. La directiva use permite combinar diferentes bloques re2zig en uno solo (ver el ejemplo a continuación).

Los bloques con nombre y la directiva use dentro de un bloque se añadieron en la versión 2.2 de re2zig. Desde esa versión, los bloques reutilizables están permitidos por defecto (no se necesita una opción especial). Antes de la versión 2.2, el modo de reutilización se activaba con la opción -r --reusable. Antes de la versión 1.2, los bloques reutilizables no se podían mezclar con bloques normales.

Ejemplo de una directiva !use

// re2zig $INPUT -o $OUTPUT
// Este ejemplo muestra cómo combinar bloques re2c reutilizables: dos bloques
// ('colors' y 'fish') se fusionan en uno. La regla 'salmon' aparece en ambos
// bloques; el bloque 'fish' tiene prioridad porque se usa antes. La regla por
// defecto * aparece en los tres bloques; la definición local (no heredada)
// tiene prioridad.
const std = @import("std");
const Ans = enum {color, fish, dunno};
%{rules:colors
    *                            { @panic("ah"); }
    "red" | "salmon" | "magenta" { return Ans.color; }
%}
%{rules:fish
    *                            { @panic("oh"); }
    "haddock" | "salmon" | "eel" { return Ans.fish; }
%}
fn lex(yyinput: [:0]const u8) Ans {
    var yycursor: usize = 0;
    var yymarker: usize = 0;
    %{
        re2c:yyfill:enable = 0;
        !use:fish;
        !use:colors;
        * { return Ans.dunno; } // anula las reglas '*' heredadas
    %}
}
test {
    try std.testing.expectEqual(lex("salmon"), Ans.fish);
    try std.testing.expectEqual(lex("what?"), Ans.dunno);
}

Ejemplo de un bloque /*!use:re2c ... */

// re2zig $INPUT -o $OUTPUT --input-encoding utf8
// Este ejemplo admite múltiples codificaciones de entrada: UTF-8 y UTF-32.
// Ambos analizadores léxicos se generan a partir del mismo bloque de reglas,
// y los bloques use solo agregan configuraciones específicas de codificación.
const std = @import("std");
%{rules

%}

    var yycursor: usize = 0;
    var yymarker: usize = 0;
    %{use
        re2c:encoding:utf8 = 1;
        re2c:YYCTYPE = u8; // el valor por defecto
    %}
}
fn lex_utf32(yyinput: []const u32) ?usize {
    var yycursor: usize = 0;

        re2c:YYCTYPE = u32;

test {
    const s8 = [_]u8{0xe2, 0x88, 0x80, 0x78, 0x20, 0xe2, 0x88, 0x83, 0x79};
    try std.testing.expectEqual(lex_utf8(&s8), s8.len);
    const s32 = [_]u32{0x2200, 0x78, 0x20, 0x2203, 0x79};

}

Extracción de subcoincidencias

re2zig tiene dos opciones para la extracción de subcoincidencias.

Etiquetas
La primera opción es usar etiquetas independientes de la forma @stag o #mtag, donde stag y mtag son nombres arbitrarios definidos por el usuario. Las etiquetas se activan con la opción -T --tags o la configuración re2c:tags = 1. Semánticamente, las etiquetas son marcadores de posición: se pueden insertar en cualquier lugar de una expresión regular y se vinculan a la posición (o posiciones) correspondiente en la cadena de entrada. Las s-etiquetas se vinculan a la última posición de coincidencia, y las m-etiquetas se vinculan a una lista de posiciones (se pueden usar en subexpresiones de repetición, donde una única posición en una expresión regular corresponde a múltiples posiciones en la cadena de entrada). Todas las etiquetas deben ser definidas por el usuario, ya sea manualmente o con la ayuda de bloques svars y mvars. Si hay más de una forma en que las etiquetas pueden coincidir con la entrada, la ambigüedad se resuelve utilizando una estrategia de desambiguación codiciosa de izquierda a derecha.
Capturas
La segunda opción es usar grupos de captura. Se activan con la opción --captures o la configuración re2c:captures = 1. Hay dos variantes para diferentes políticas de desambiguación, --leftmost-captures (el valor por defecto) es para la política codiciosa de izquierda a derecha, y --posix-captures es para la política de coincidencia más larga POSIX. En este modo, todas las subexpresiones entre paréntesis se consideran grupos de captura, y se puede usar un signo de exclamación para marcar grupos sin captura: (! ... ). Con la opción --invert-captures o la configuración re2c:invert-captures = 1, el significado del signo de exclamación se invierte. El número de grupos para la regla de coincidencia se almacena en una variable yynmatch (la expresión regular completa es el grupo número cero), y los resultados de las subcoincidencias se almacenan en el array yypmatch. Tanto yynmatch como yypmatch deben ser definidos por el usuario, y el tamaño de yypmatch debe ser al menos [yynmatch * 2]. Utilice el bloque maxnmatch para definir YYMAXNMATCH, una constante que es igual al valor máximo de yynmatch entre todas las reglas.
Captvars
Otra forma de usar grupos de captura es la opción --captvars o la configuración re2c:captvars = 1. La única diferencia con --captures es la forma en que re2zig genera el código para almacenar los resultados de las subcoincidencias: en lugar de yynmatch y yypmatch, re2zig genera las variables yytl<k> y yytr<k> para el grupo de captura k-ésimo (el usuario debe declararlas usando un bloque svars). Las capturas con variables admiten dos políticas de desambiguación: --leftmost-captvars o re2c:leftmost-captvars = 1 para la política codiciosa de izquierda a derecha (el valor por defecto) y --posix-captvars o re2c:posix-captvars para la política de coincidencia más larga POSIX.

En esencia, todas estas opciones se traducen en etiquetas y *Autómatas Finitos Deterministas Etiquetados con Lookahead*. La idea central de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En el extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es simplemente un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es apenas perceptible. El TDFA generado utiliza una serie de *variables de etiqueta* que no se mapean directamente a las etiquetas: una única variable puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples variables para almacenar todos sus valores posibles. Eventualmente, la ambigüedad se resuelve y solo una variable final por etiqueta sobrevive. Las variables de etiqueta deben definirse usando bloques stags o mtags. Si se almacena el estado del analizador léxico, las variables de etiqueta deben formar parte de él. También necesitan ser actualizadas por YYFILL.

Las s-etiquetas admiten las siguientes operaciones:

  • guardar la posición de entrada en una s-etiqueta: t = YYCURSOR con la API de puntero C o una operación definida por el usuario YYSTAGP(t) con la API genérica
  • guardar un valor por defecto en una s-etiqueta: t = NULL con la API de puntero C o una operación definida por el usuario YYSTAGN(t) con la API genérica
  • copiar una s-etiqueta a otra: t1 = t2

Las m-etiquetas admiten las siguientes operaciones:

  • agregar la posición de entrada a una m-etiqueta: una operación definida por el usuario YYMTAGP(t) con la API por defecto y la genérica
  • agregar un valor por defecto a una m-etiqueta: una operación definida por el usuario YYMTAGN(t) con la API por defecto y la genérica
  • copiar una m-etiqueta a otra: t1 = t2

Las s-etiquetas se pueden implementar como valores escalares (punteros o desplazamientos). Las m-etiquetas necesitan una representación más compleja, ya que necesitan almacenar una secuencia de valores de etiqueta. La representación más ingenua e ineficiente de una m-etiqueta es una lista (array, vector) de valores de etiqueta; una representación más eficiente es almacenar todas las m-etiquetas en un árbol de prefijos representado como un array de nodos (v, p), donde v es el valor de la etiqueta y p es un puntero al nodo padre.

Un punto de código es un identificador numérico de un símbolo. Una unidad de código es la unidad más pequeña de almacenamiento en el texto codificado. Un solo punto de código puede representarse con una o más unidades de código. En una codificación de longitud fija, todos los puntos de código se representan con el mismo número de unidades de código. En una codificación de longitud variable, los puntos de código pueden representarse con un número diferente de unidades de código. Ten en cuenta que la regla "cualquiera" `[^]` coincide con cualquier punto de código, pero no necesariamente con cualquier unidad de código (la única forma de coincidircualquier unidad de código independientemente de la codificación es la regla predeterminada *). El lexer generado funciona con un flujo de unidades de código: yych almacena una unidad de código y YYCTYPE es el tipo de unidad de código. Las expresiones regulares, por otro lado, se especifican en términos de puntos de código. Cuando re2zig compila expresiones regulares a autómatas, traduce puntos de código a unidades de código. Esto generalmente no es una correspondencia simple: en codificaciones de longitud variable, un solo rango de puntos de código puede traducirse a un gráfico complejo de unidades de código. Las siguientes codificaciones son compatibles:
  • ASCII (habilitado por defecto). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • EBCDIC (habilitado con --ebcdic o re2c:encoding:ebcdic). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • UCS2 (habilitado con --ucs2 o re2c:encoding:ucs2). Es una codificación de longitud fija con espacio de código [0-0xFFFF] y puntos de código y unidades de código de 2 bytes.
  • UTF8 (habilitado con --utf8 o re2c:encoding:utf8). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
  • UTF16 (habilitado con --utf16 o re2c:encoding:utf16). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 a 2 unidades de código.
  • UTF32 (habilitado con --utf32 o re2c:encoding:utf32). Es una codificación Unicode de longitud fija con espacio de código [0-0x10FFFF] y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión include/unicode_categories.re proporciona definiciones de re2zig para las categorías estándar de Unicode.

La opción --input-encoding especifica la codificación del archivo fuente, que puede usarse para habilitar literales Unicode en expresiones regulares. Por ejemplo, --input-encoding utf8 le indica a re2zig que el archivo fuente está en UTF8 (esto difiere de --utf8, que establece la codificación del texto de entrada). La opción --encoding-policy especifica la forma en que re2zig maneja los sustitutos de Unicode (puntos de código en el rango [0xD800-0xDFFF]).

Archivos de Inclusión

re2zig permite incluir otros archivos usando un bloque de la forma /*!include:re2c FILE */ o %{include FILE %}, o una directiva dentro de un bloque !include FILE ;, donde FILE es la ruta al archivo a incluir. re2zig busca archivos de inclusión en el directorio del archivo que los incluye y en las ubicaciones de inclusión, que se pueden especificar con la opción -I. Los bloques/directivas de inclusión en re2zig funcionan de la misma manera que el #include de C/C++: el contenido de FILE se copia literalmente en el lugar del bloque/directiva. Los archivos de inclusión pueden tener sus propias inclusiones. Utilice la opción --depfile para rastrear las dependencias de compilación del archivo de salida en los archivos de inclusión. re2zig proporciona algunos archivos de inclusión predefinidos que se encuentran en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como las categorías Unicode) y forman algo así como una biblioteca estándar para re2zig. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivo de Inclusión 1 (definitions.zig)

const Num = enum { integer, floating, nan };
%{

Archivo de Inclusión 2 (extra_rules.re.inc)

// números de punto flotante

Archivos de Cabecera

re2zig permite generar un archivo de cabecera a partir del archivo .re de entrada usando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El archivo de cabecera autogenerado puede ser necesario en casos donde re2zig se usa para generar definiciones que deben ser visibles desde otras unidades de traducción.

Programas Esqueleto

Con la opción -S, --skeleton, re2zig ignora todo el código que no es de re2zig y genera un programa C autocontenido que puede compilarse y ejecutarse posteriormente. El programa consta del código del lexer y los datos de entrada. Para cada DFA construido (bloque o condición), re2zig genera un lexer independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados de coincidencia esperados. El programa ejecuta cada lexer en el archivo .input correspondiente y compara los resultados con las expectativas. Los programas esqueleto son muy útiles por varias razones:

  • Pueden verificar la corrección de varias optimizaciones de re2zig (los datos se generan en una etapa temprana del proceso, antes de que se hayan realizado transformaciones del DFA).
  • La generación de un conjunto de datos de entrada con buena cobertura puede ser útil tanto para pruebas como para benchmarking.
  • La generación de programas ejecutables autocontenidos permite obtener casos de prueba minimizados (el código original puede ser grande o tener muchas dependencias).

La dificultad al generar datos de entrada es que, para todos los casos excepto los más triviales, el número de cadenas de entrada posibles es demasiado grande (incluso si la longitud de la cadena está limitada). re2zig resuelve esta dificultad generando suficientes cadenas para cubrir casi todas las transiciones del DFA. Utiliza el siguiente algoritmo. Primero, construye un esqueleto del DFA. Para codificaciones con un tamaño de unidad de código de 1 byte (como ASCII, UTF-8 y EBCDIC), el esqueleto es simplemente una copia exacta del DFA original. Para codificaciones con unidades de código multibyte, el esqueleto es una copia del DFA con ciertas transiciones omitidas: es decir, re2zig toma como máximo 256 unidades de código para cada rango continuo y disjunto que corresponde a una transición del DFA. Los valores elegidos están distribuidos uniformemente e incluyen los límites del rango. En lugar de intentar cubrir todos los caminos posibles en el esqueleto (lo cual es inviable), re2zig genera suficientes caminos para cubrir todas las transiciones del esqueleto y, por lo tanto, activar los saltos condicionales correspondientes en el lexer. La implementación del algoritmo está limitada a aproximadamente 1 GB de transiciones y consume una cantidad constante de memoria (re2zig escribe los datos en el archivo tan pronto como se generan).

Visualización y Depuración

Con la opción -D, --emit-dot, re2zig no genera código. En su lugar, vuelca el DFA generado en formato DOT. Se puede convertir este volcado en una imagen del DFA utilizando Graphviz u otra biblioteca. Tenga en cuenta que esta opción muestra el DFA final después de que ha pasado por una serie de optimizaciones y transformaciones. Se pueden volcar etapas anteriores con varias opciones de depuración, como --dump-nfa, --dump-dfa-raw, etc. (ver la lista completa de opciones).
