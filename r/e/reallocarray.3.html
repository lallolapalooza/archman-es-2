NOMBRE

malloc, free, calloc, realloc, reallocarray - asignar y liberar memoria dinámica

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <stdlib.h>
void *malloc(size_t size);
void free(void *_Nullable p);
void *calloc(size_t n, size_t size);
void *realloc(void *_Nullable p, size_t size);
void *reallocarray(void *_Nullable p, size_t n, size_t size);
Requisitos de macro de prueba de características para glibc (ver feature_test_macros(7)):

reallocarray():

    Desde glibc 2.29:
        _DEFAULT_SOURCE
    glibc 2.28 y anteriores:
        _GNU_SOURCE

DESCRIPCIÓN

malloc()

La función malloc() asigna size bytes y devuelve un puntero a la memoria asignada. La memoria no está inicializada. Si size es 0, entonces malloc() devuelve un valor de puntero único que posteriormente se puede pasar correctamente a free(). (Ver "Comportamiento no portable" para problemas de portabilidad).

free()

La función free() libera el espacio de memoria apuntado por p, que debe haber sido devuelto por una llamada anterior a malloc() o funciones relacionadas. De lo contrario, o si p ya ha sido liberado, ocurre un comportamiento indefinido. Si p es NULL, no se realiza ninguna operación.

calloc()

La función calloc() asigna memoria para un array de n elementos de size bytes cada uno y devuelve un puntero a la memoria asignada. La memoria se establece a cero. Si n o size es 0, entonces calloc() devuelve un valor de puntero único que posteriormente se puede pasar correctamente a free().

Si la multiplicación de n y size resultara en desbordamiento entero, entonces calloc() devuelve un error. Por el contrario, no se detectaría un desbordamiento entero en la siguiente llamada a malloc(), con el resultado de que se asignaría un bloque de memoria de tamaño incorrecto:


malloc(n * size);

realloc()

La función realloc() cambia el tamaño del bloque de memoria apuntado por p a size bytes. Los contenidos de la memoria no cambiarán en el rango desde el inicio de la región hasta el mínimo del tamaño antiguo y el nuevo. Si el nuevo tamaño es mayor que el tamaño antiguo, la memoria añadida no se inicializará.

Si p es NULL, entonces la llamada es equivalente a malloc(size), para todos los valores de size.

Si size es igual a cero, y p no es NULL, entonces la llamada es equivalente a free(p) (pero ver "Comportamiento no portable" para problemas de portabilidad).

A menos que p sea NULL, debe haber sido devuelto por una llamada anterior a malloc o funciones relacionadas. Si el área apuntada fue movida, se realiza un free(p).

reallocarray()

La función reallocarray() cambia el tamaño de (y posiblemente mueve) el bloque de memoria apuntado por p para que sea lo suficientemente grande para un array de n elementos, cada uno de los cuales es de size bytes. Es equivalente a la llamada


realloc(p, n * size);

Sin embargo, a diferencia de esa llamada a realloc(), reallocarray() falla de forma segura en el caso en que la multiplicación desbordara. Si ocurre tal desbordamiento, reallocarray() devuelve un error.

VALOR DE RETORNO

Las funciones malloc(), calloc(), realloc() y reallocarray() devuelven un puntero a la memoria asignada, que está adecuadamente alineada para cualquier tipo que quepa en el tamaño solicitado o menos. En caso de error, estas funciones devuelven NULL y establecen errno. Intentar asignar más de PTRDIFF_MAX bytes se considera un error, ya que un objeto tan grande podría provocar un desbordamiento posterior de la resta de punteros.

La función free() no devuelve ningún valor y preserva errno.

Las funciones realloc() y reallocarray() devuelven NULL si p es NULL y el tamaño solicitado es cero; esto no se considera un error. (Ver "Comportamiento no portable" para problemas de portabilidad.) De lo contrario, el puntero devuelto puede ser el mismo que p si la asignación no se movió (por ejemplo, había espacio para expandir la asignación en el lugar), o diferente de p si la asignación se movió a una nueva dirección. Si estas funciones fallan, el bloque original no se modifica; no se libera ni se mueve.

ERRORES

calloc(), malloc(), realloc() y reallocarray() pueden fallar con el siguiente error:

ENOMEM
Sin memoria. Posiblemente, la aplicación alcanzó el límite RLIMIT_AS o RLIMIT_DATA descrito en getrlimit(2). Otra razón podría ser que el número de mapeos creados por el proceso llamante excedió el límite especificado en /proc/sys/vm/max_map_count.

realloc(p, 0)

El comportamiento de realloc(p, 0) en glibc no cumple con ninguna de las versiones C99, C11, POSIX.1-2001, POSIX.1-2004, POSIX.1-2008, POSIX.1-2013, POSIX.1-2017 o POSIX.1-2024. La especificación C17 se modificó para que cumpliera, pero esa especificación hizo imposible escribir código que determine de forma fiable si el puntero de entrada se libera después de realloc(p, 0), y C23 lo cambió nuevamente para hacer que esto sea un comportamiento indefinido, reconociendo que la especificación C17 era lo suficientemente amplia, por lo que el comportamiento indefinido no era peor que eso.

reallocarray() sufre los mismos problemas en glibc.

musl libc y los BSD cumplen con todas las versiones de ISO C y POSIX.1.

gnulib proporciona el módulo realloc-posix, que proporciona envolturas realloc() y reallocarray() que cumplen con todas las versiones de ISO C y POSIX.1.

Existe una propuesta para estandarizar el comportamiento de BSD: https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3621.txt.

NAME

reallocarray, realloc — reallocate memory

LIBRARY

Memory Allocation Manipulation (libucrtd.a, libucrt.so)

SYNOPSIS

#include <stdlib.h>

void *reallocarray(void *ptr, size_t n, size_t size);

void *realloc(void *ptr, size_t size);

DESCRIPTION

The reallocarray() function is a wrapper around the realloc() function that checks for integer overflow before calling realloc(). The reallocarray() function allocates space for an array of n elements, each of size bytes. The total number of bytes allocated is n*size. If the multiplication n*size would overflow, reallocarray() returns NULL and sets ENOMEM. Otherwise, it calls realloc(ptr, n * size).

The realloc() function changes the size of the memory block pointed to by ptr to size bytes. The contents of the memory allocating up to the smaller of the new and old sizes remain unchanged.

If ptr is NULL, then the call is equivalent to a call to malloc() with size as the size parameter.

If size is 0, and ptr is not NULL, then the call is equivalent to a call to free() with ptr as the value of the argument. If size is 0 and ptr is NULL, then realloc() may return NULL or a unique pointer that can be passed to free().

If memory is allocated so that it may be shared amongst the calling process and its children via calls such as fork(2), the new memory address will be valid in the child process. When the address space is shared, the reallocation is done within the address space of the child process.

RETURN VALUE

Upon successful completion, realloc() and reallocarray() return a pointer to the newly allocated memory area. Otherwise, they return a NULL pointer and set errno to indicate the error.

The returned pointer is guaranteed to be suitably aligned for any kind of variable. The returned pointer may be the same as ptr, or it may be a new address.

ERRORS

ENOMEM
Insufficient memory is available. Or the argument size requested overflowed.
EINVAL
The value of size was invalid.

ATTRIBUTES

For explanations of the terms used in this section, see attributes(7).

Interface Attribute Value
reallocarray(), realloc() Thread safety thread-safe

STANDARDS

The realloc() function conforms to C99, C11, POSIX.1-2001, and POSIX.1-2008.

The reallocarray() function is a FreeBSD extension that also appears in OpenBSD and some other systems.

HISTORY

The realloc() function first appeared in Version 3 of the Bell System's Unix.

The reallocarray() function first appeared in FreeBSD 7.0.

glibc
The glibc implementation of realloc() allocates memory from the heap. The heap is managed by brk(2). Memory chunks are managed by a linked list of chunks. When the size of the memory requested is larger than MMAP_THRESHOLD bytes (128 kB by default), the glibc implementation uses mmap(2) to allocate memory. The mmap(2) calls are unaffected by the RLIMIT_DATA resource limit.
glibc 2.0. Use of mmap(2) was enabled.
glibc 2.1.1. realloc(p, 0) behavior changed.
glibc 2.30. malloc() and related functions rejected sizes greater than PTRDIFF_MAX.
glibc 2.33. free() preserved errno.

realloc(p, 0)

C89 was ambiguous in its specification of realloc(p, 0). C99 partially fixed this.

The original implementation in glibc would have been conforming to C99. However, and ironically, trying to comply with C99 before the standard was released, glibc changed its behavior in glibc 2.1.1 into something that ended up not conforming to the final C99 specification (but this is debated, as the wording of the standard seems self-contradicting).

NOTES

By default, Linux follows an optimistic memory allocation strategy. This means that when malloc() returns non-NULL there is no guarantee that the memory really is available. In case it turns out that the system is out of memory, one or more processes will be killed by the OOM killer. For more information, see the description of /proc/sys/vm/overcommit_memory and /proc/sys/vm/oom_adj in proc(5), and the Linux kernel source file Documentation/vm/overcommit-accounting.rst.

Normally, malloc() allocates memory from the heap, and adjusts the size of the heap as required, using sbrk(2). When allocating blocks of memory larger than MMAP_THRESHOLD bytes, the glibc malloc() implementation allocates the memory as a private anonymous mapping using mmap(2). MMAP_THRESHOLD is 128 kB by default, but is adjustable using mallopt(3). Prior to Linux 4.7 allocations performed using mmap(2) were unaffected by the RLIMIT_DATA resource limit; since Linux 4.7, this limit is also enforced for allocations performed using mmap(2).

To avoid corruption in multithreaded applications, mutexes are used internally to protect the memory-management data structures employed by these functions. In a multithreaded application in which threads simultaneously allocate and free memory, there could be contention for these mutexes. To scalably handle memory allocation in multithreaded applications, glibc creates additional memory allocation arenas if mutex contention is detected. Each arena is a large region of memory that is internally allocated by the system (using brk(2) or mmap(2)), and managed with its own mutexes.

If your program uses a private memory allocator, it should do so by replacing malloc(), free(), calloc(), and realloc(). The replacement functions must implement the documented glibc behaviors, including errno handling, size-zero allocations, and overflow checking; otherwise, other library routines may crash or operate incorrectly. For example, if the replacement free() does not preserve errno, then seemingly unrelated library routines may fail without having a valid reason in errno. Private memory allocators may also need to replace other glibc functions; see "Replacing malloc" in the glibc manual for details.

Crashes in memory allocators are almost always related to heap corruption, such as overflowing an allocated chunk or freeing the same pointer twice.

The malloc() implementation is tunable via environment variables; see mallopt(3) for details.

Nonportable behavior

The behavior of these functions when the requested size is zero is glibc specific; other implementations may return NULL without setting errno, and portable POSIX programs should tolerate such behavior. See realloc(3p).

POSIX requires memory allocators to set errno upon failure. However, the C standard does not require this, and applications portable to non-POSIX platforms should not assume this.

Portable programs should not use private memory allocators, as POSIX and the C standard do not allow replacement of malloc(), free(), calloc(), and realloc().

BUGS

Programmers would naturally expect by induction that realloc(p, size) is consistent with free(p) and malloc(size), as that is the behavior in the general case. This is not explicitly required by POSIX.1-2024 or C11, but all conforming implementations are consistent with that.

The glibc implementation of realloc() is not consistent with that, and as a consequence, it is dangerous to call realloc(p, 0) in glibc.

A trivial workaround for glibc is calling it as realloc(p, size?size:1).

The workaround for reallocarray() in glibc —which shares the same bug— would be reallocarray(p, n?n:1, size?size:1).

EXAMPLES

#include <err.h>
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define MALLOCARRAY(n, type)  ((type *) my_mallocarray(n, sizeof(type)))
#define MALLOC(type)          MALLOCARRAY(1, type)
static inline void *my_mallocarray(size_t n, size_t size);
int
main(void)
{
    char  *p;
    p = MALLOCARRAY(32, char);
    if (p == NULL)
        err(EXIT_FAILURE, "malloc");
    strlcpy(p, "foo", 32);
    puts(p);
}
static inline void *
my_mallocarray(size_t n, size_t size)
{
    return reallocarray(NULL, n, size);
}
