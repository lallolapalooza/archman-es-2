NOMBRE

re2d - genera analizadores léxicos rápidos para D

SINOPSIS

re2d [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para stdin.

INTRODUCCIÓN

re2d funciona como un preprocesador. Lee el archivo de entrada (que normalmente es un programa en D, pero puede ser cualquier cosa) y busca bloques de código encerrados en marcadores especiales de inicio/fin. El texto fuera de estos bloques se copia literalmente al archivo de salida. El contenido de los bloques es procesado por re2d. Los traduce a código en D y genera el código resultante en lugar del bloque.

Aquí hay un ejemplo de un pequeño programa que comprueba si una cadena dada contiene un número decimal:

// re2d $INPUT -o $OUTPUT -i
module main;
private bool lex(const(char)* yycursor) {
    /*!re2c
        re2c:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    */
}
void main() {
    assert(lex("1234"));
}

En la salida, re2d reemplazó el bloque intermedio con el código generado:

/* Generado por re2d */
// re2d $INPUT -o $OUTPUT -i
module main;
private bool lex(const(char)* yycursor) {
{
    char yych;
    yych = *yycursor;
    switch (yych) {
        case '1': .. case '9': goto yy2;
        default: goto yy1;
    }
yy1:
    ++yycursor;
    { return false; }
yy2:
    yych = *++yycursor;
    switch (yych) {
        case '0': .. case '9': goto yy2;
        default: goto yy3;
    }
yy3:
    { return true; }
}
}
void main() {
    assert(lex("1234"));
}

BÁSICOS

Un programa re2d consiste en una secuencia de bloques entremezclados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresión-regular ;
Una definición asocia nombre con expresión-regular. Los nombres pueden contener caracteres alfanuméricos y guion bajo. La sección de expresiones regulares ofrece una visión general de la sintaxis de re2d para expresiones regulares. Una vez definido, el nombre puede ser utilizado en otras expresiones regulares y en reglas. La recursión en definiciones con nombre no está permitida, y cada nombre debe ser definido antes de ser usado. Un bloque hereda definiciones con nombre del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite cambiar el comportamiento de re2d y personalizar el código generado. Para obtener una lista completa de las configuraciones compatibles con re2d, consulte la sección de configuraciones. Dependiendo de una configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista en caracteres alfanuméricos. Un bloque hereda configuraciones del ámbito global y puede redefinirlas o añadir nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final del mismo.
expresión-regular código
Una regla asocia expresión-regular con su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en un salto de línea seguido de cualquier carácter no espaciado). Si la expresión-regular coincide, el código asociado se ejecuta. Si varias reglas coinciden, la coincidencia más larga tiene precedencia. Si varias reglas coinciden con la misma cadena, la primera que aparezca tiene precedencia. Hay dos reglas especiales: la regla predeterminada * y la regla de fin de entrada $. La regla predeterminada siempre debe definirse, tiene la menor prioridad independientemente de su lugar en el bloque y coincide con cualquier unidad de código (no necesariamente un carácter válido, véase la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para el *manejo del fin de entrada*. Con las *condiciones de inicio*, las reglas tienen una sintaxis más compleja.
!acción código
Una acción asocia un bloque de código definido por el usuario a un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas asocian código a los estados finales). Consulte la sección de *acciones* para obtener una lista completa de las acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias predefinidas especiales. Cada directiva tiene un propósito único. Consulte la sección de *directivas* para más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (ambos estilos son compatibles). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que permiten referenciarlos en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2d compila las expresiones regulares asociadas a cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se añaden al ámbito global y se vuelven visibles para los bloques posteriores. Al inicio del programa, el ámbito global se inicializa con las *opciones* de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y las configuraciones en él tienen un ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera código por sí mismo, ni añade definiciones al ámbito global, sino que está destinado a ser reutilizado en otros bloques. Es una forma de compartir código (más detalles en la sección de *bloques reutilizables*). Antes de la versión 2.2 de re2d, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2d busca bloques de reglas con ese nombre. De lo contrario, se utiliza el bloque de reglas más reciente (ya sea con nombre o sin nombre). Un bloque de uso puede añadir sus propias definiciones, configuraciones y reglas, que se añaden a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2d, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques se incluirán al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macrodefinición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Se puede personalizar con una configuración opcional formato que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXFILL.
/*!maxnmatch:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{maxnmatch[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXNMATCH (requiere la opción -P --posix-captures). Una lista opcional de nombres de bloques especifica qué bloques se incluirán al calcular el valor de YYMAXNMATCH (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macrodefinición para C (#define YYMAXNMATCH <n>), o una variable global para Go (var YYMAXNMATCH int = <n>). Se puede personalizar con una configuración opcional formato que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXNMATCH.

Bloques que especifican un fragmento de código de plantilla que se expande para cada variable de etiqueta s/m generada por re2d. Una lista opcional de nombres de bloque especifica qué bloques deben incluirse al calcular el conjunto de variables de etiqueta (si la lista está vacía, se incluyen todos los bloques). Hay dos configuraciones opcionales: formato y separador. La configuración formato especifica una cadena de plantilla donde @@{etiqueta} (o @@ para abreviar) se reemplaza con el nombre de cada variable de etiqueta. Bloques que especifican un fragmento de código de plantilla que se expande para cada etiqueta s/m que se menciona explícitamente en las reglas (con la opción --tags) o se genera implícitamente por re2d (con las opciones --captvars o --posix-captvars). Una lista opcional de nombres de bloque especifica qué bloques deben incluirse al calcular el conjunto de etiquetas (si la lista está vacía, se incluyen todas las etiquetas). Hay dos configuraciones opcionales: formato y separador. La configuración formato especifica una cadena de plantilla donde @@{etiqueta} (o @@ para abreviar) se reemplaza con el nombre de cada etiqueta. La configuración separador especifica un fragmento de código utilizado para unir los fragmentos de formato generados para diferentes etiquetas.
/*!getstate:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{getstate[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera un despacho condicional en el estado del lexer (requiere la opción --storable-state). Una lista opcional de nombres de bloque especifica qué bloques deben incluirse en el despacho de estado. La transición predeterminada va a la etiqueta de inicio del primer bloque de la lista. Si la lista está vacía, se incluyen todos los bloques y la transición predeterminada va al primer bloque del archivo que tiene una etiqueta de inicio. Este tipo de bloque es incompatible con la opción --loop-switch, ya que requiere transiciones entre bloques que no son compatibles sin goto o llamadas a funciones.
/*!conditions:re2c[:<nombre1>[:<nombre2>...]] ... */, /*!types:re2c... */ o %{conditions[:<nombre1>[:<nombre2>...]] ... %}, %{types... %}
Un bloque que genera una enumeración de condiciones (requiere la opción --conditions). Una lista opcional de nombres de bloque especifica qué bloques deben incluirse al calcular el conjunto de condiciones (si la lista está vacía, se incluyen todas las condiciones). Por defecto, el código generado es una enumeración YYCONDTYPE. Puede personalizarse con las configuraciones opcionales formato y separador. La configuración formato especifica una cadena de plantilla donde @@{cond} (o @@ para abreviar) se reemplaza con el nombre de cada condición, y @@{num} se reemplaza con un índice numérico de esa condición. La configuración separador especifica un fragmento de código utilizado para unir los fragmentos de formato generados para diferentes condiciones.
/*!include:re2c <archivo> */ o %{include <archivo> %}
Este bloque permite incluir <archivo>, que debe ser una ruta de archivo entre comillas dobles. El contenido del archivo se sustituye literalmente en lugar del bloque, de la misma manera que funciona #include en C/C++. Este bloque se puede usar junto con la opción --depfile para generar dependencias del sistema de compilación en los archivos incluidos.
/*!header:re2c:on*/ o %{header:on %}
Este bloque marca el inicio del archivo de encabezado. Todo lo que sigue hasta el siguiente bloque header:off es procesado por re2d y escrito en el archivo de encabezado especificado con la opción -t --type-header.
/*!header:re2c:off*/ o %{header:off %}
Este bloque marca el final del archivo de encabezado iniciado con el bloque header:on*/.
/*!ignore:re2c ... */ o %{ignore ... %}
Un bloque cuyo contenido se ignora y se elimina del archivo de salida.

Configuraciones

Aquí hay una lista completa de las configuraciones admitidas por re2d:

re2c:api, re2c:input
Igual que la opción --api.
re2c:api:sigil
Especifica el marcador ("sigilo") que se utiliza para los marcadores de posición de argumentos en las primitivas de API. El valor predeterminado es @@. Un marcador de posición comienza con el sigilo seguido del nombre del argumento entre llaves. Por ejemplo, si el sigilo se establece en $, entonces los marcadores de posición tendrán la forma ${nombre}. Las API de un solo argumento pueden usar una notación abreviada sin el nombre entre llaves. Esta opción puede ser anulada por opciones para primitivas de API individuales, por ejemplo, re2c:YYFILL@len para YYFILL.
re2c:api:style
Especifica el estilo de la API. Los valores posibles son functions (el valor predeterminado para C) y free-form (el valor predeterminado para Go y Rust). En el estilo functions, las primitivas de la API se generan con una lista de argumentos entre paréntesis después del nombre de la primitiva. Los argumentos solo se proporcionan para parámetros autogenerados (como el número de caracteres pasados a YYFILL), pero no para el contexto general del lexer, por lo que las primitivas se comportan más como macros en C/C++ o clausuras en Go y Rust. En el estilo free-form, las primitivas de la API no tienen una forma fija: deben definirse como cadenas que contienen fragmentos de código de forma libre con variables interpoladas de la forma @@{var} o @@ (corresponden a argumentos en estilo similar a funciones). Esta configuración puede ser anulada para primitivas de API individuales, ver por ejemplo la configuración re2c:YYFILL:naked para YYFILL.

Especifica la expresión constante que se utiliza para el valor negativo de la etiqueta (típicamente sería -1 si las etiquetas son desplazamientos enteros en la cadena de entrada, o un puntero nulo si son punteros).

Expresiones regulares

re2d utiliza la siguiente sintaxis para las expresiones regulares:

"foo"
Literal de cadena sensible a mayúsculas y minúsculas.
'foo'
Literal de cadena insensible a mayúsculas y minúsculas.
[a-xyz], [^a-xyz]
Clase de caracteres (posiblemente negada).
.
Cualquier carácter excepto nueva línea.
R \ S
R - S
Diferencia de clases de caracteres R y S.
R*
Cero o más ocurrencias de R.
R+
Una o más ocurrencias de R.
R?
Opcional R.
R{n}
Repetición de R exactamente n veces.
R{n,}
Repetición de R al menos n veces.
R{n,m}
Repetición de R de n a m veces.
(R)
Simplemente R; los paréntesis se usan para anular la precedencia. Si la extracción de subcoincidencias está habilitada, (R) es un grupo de captura o un grupo sin captura dependiendo de la opción --invert-captures.
(!R)
Si la extracción de subcoincidencias está habilitada, (!R) es un grupo sin captura o un grupo de captura dependiendo de la opción --invert-captures.
R S
Concatenación: R seguido de S.
R | S
Alternativa: R o S.
R / S
Lookahead: R seguido de S, pero S no se consume.
name
Expresión regular definida como name (o cadena literal "name" en modo de compatibilidad con Flex).
{name}
Expresión regular definida como name en modo de compatibilidad con Flex.
@stag
Una etiqueta s: guarda la última posición de entrada en la que coincide @stag en una variable llamada stag.
#mtag
Una etiqueta m: guarda todas las posiciones de entrada en las que coincide #mtag en una variable llamada mtag.

Las clases de caracteres y las cadenas literales pueden contener las siguientes secuencias de escape: \a, \b, \f, \n, \r, \t, \v, \\, escapes octales \ooo y escapes hexagonales \xhh, \uhhhh y \Uhhhhhhhh.

Acciones

Aquí hay una lista de acciones predefinidas compatibles con re2d:

!entry code
La acción de entrada vincula un bloque de código definido por el usuario al estado de inicio de la máquina de estados finitos actual. Si se utilizan condiciones de inicio, la acción de entrada se puede establecer individualmente para cada condición. Esta acción se puede utilizar para realizar inicializaciones, por ejemplo, para guardar la ubicación de inicio de un lexema.
!pre_rule code
La acción pre-regla antepone un bloque de código definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para factorizar la parte común de todas las acciones semánticas (por ejemplo, guardar la ubicación final de un lexema).
!post_rule code
La acción post-regla añade un bloque de código definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para emitir sentencias de interrupción (trap) que eviten flujos de control no deseados.

Directivas

Aquí hay una lista completa de directivas compatibles con re2d:

!use:name ;
Una directiva de uso dentro de un bloque que fusiona un bloque de reglas definido previamente con el nombre especificado en el bloque actual. Las definiciones nombradas, las configuraciones y las reglas del bloque referenciado se agregan a las actuales. Los conflictos entre reglas y configuraciones superpuestas se resuelven de la manera habitual: la primera regla tiene prioridad, y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y <!> para las cuales una definición local del bloque siempre tiene prioridad. Una directiva de uso se puede colocar en cualquier lugar dentro de un bloque, y se permiten múltiples directivas de uso.
!include file ;
Esta directiva es la misma que el bloque include: inserta el contenido de file literalmente en lugar de la directiva.

Interfaz del programa

El código generado interactúa con el programa externo con la ayuda de primitivas, denominadas colectivamente API. Qué primitivas deben definirse para un programa en particular depende de múltiples factores, incluyendo la complejidad de las expresiones regulares, la representación de la entrada, el almacenamiento en búfer y el uso de varias características. Todas las primitivas necesarias deben ser definidas por el usuario en forma de macros, funciones, variables o cualquier otra forma adecuada que haga que el código generado sea sintáctica y semánticamente correcto. re2d no verifica (y no puede verificar) las definiciones, por lo que si algo falta o está definido incorrectamente, el programa generado puede tener errores en tiempo de compilación o en tiempo de ejecución. Este manual proporciona ejemplos de definiciones de API en los casos más comunes.

re2d tiene tres sabores de API que definen el conjunto central de primitivas utilizadas por un programa:

API Simple
Esta es la API predeterminada para el backend D. Consiste en las primitivas YYCURSOR, YYMARKER, YYCTXMARKER y YYLIMIT, que deben definirse como punteros del tipo YYCTYPE*.
API Record
La API Record es útil en casos en los que el estado del lexer debe almacenarse en una struct. Se habilita con la opción --api record o la configuración re2c:api = record. Esta API consiste en una variable yyrecord (el nombre se puede anular con re2c:yyrecord) que debe definirse como una struct con los campos yycursor, yymarker, yyctxmarker, yylimit (solo los campos utilizados por el código generado necesitan ser definidos, y sus nombres se pueden configurar).
API Genérica
Esta es la API más flexible. Se habilita con la opción --api generic o la configuración re2c:api = generic. Contiene primitivas para operaciones genéricas: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Aquí hay una lista completa de primitivas de API que pueden ser utilizadas por el código generado para interactuar con el programa externo.

YYCTYPE
El tipo de los caracteres de entrada (unidades de código). Para las codificaciones ASCII, EBCDIC y UTF-8 debe ser un entero sin signo de 1 byte. Para UTF-16 o UCS-2 debe ser un entero sin signo de 2 bytes. Para UTF-32 debe ser un entero sin signo de 4 bytes.
YYCURSOR
Un l-valor que almacena la posición de entrada actual (un puntero o un desplazamiento de entero en YYINPUT). Inicialmente, YYCURSOR debe apuntar al primer carácter de entrada, y más tarde es avanzado por el código generado. Cuando una regla coincide, la posición de YYCURSOR es la que sigue al último carácter coincidente.
YYLIMIT
Un r-valor que almacena la posición del final de la entrada (un puntero o un desplazamiento de entero en YYINPUT). Inicialmente, YYLIMIT debe apuntar a la posición después del último carácter de entrada disponible. No es modificado por el código generado. El lexer compara YYCURSOR con YYLIMIT para determinar si quedan suficientes caracteres de entrada.
YYMARKER
Un l-valor que almacena la posición de la última regla coincidente (un puntero o un desplazamiento de entero en YYINPUT). Se utiliza para restaurar la posición de YYCURSOR si la coincidencia más larga falla y el lexer necesita retroceder. No se necesita inicialización.
YYCTXMARKER
Un l-valor que almacena la posición del contexto de cola (un puntero o un desplazamiento de entero en YYINPUT). No se necesita inicialización. YYCTXMARKER solo es necesario si se utiliza el operador de lookahead /.
YYFILL
Una primitiva API genérica con una variable len. YYFILL debe proporcionar al menos len caracteres de entrada adicionales o fallar. Si se utiliza re2c:eof, entonces len es siempre 1 y YYFILL siempre debe devolver a la función que llama; un valor de retorno cero indica éxito. Si no se utiliza re2c:eof, entonces el valor de retorno de YYFILL se ignora y no debe devolver en caso de fallo. El valor máximo de len es YYMAXFILL.
YYFN
Una primitiva que define el prototipo de función en el modelo de código --recursive-functions. Su valor debe ser una matriz de una o más cadenas, donde cada cadena contiene dos o tres componentes separados por la cadena especificada en la configuración re2c:fn:sep (típicamente un punto y coma). El primer elemento de la matriz define el nombre de la función y el tipo de retorno (vacío para una función void). Los elementos subsiguientes definen los argumentos de la función: primero, la expresión para el argumento utilizado en el cuerpo de la función (generalmente solo un nombre); segundo, el tipo del argumento; tercero, un parámetro formal opcional (por defecto es el primer componente, generalmente tanto el argumento como el parámetro son el mismo identificador).
YYINPUT
Un r-valor que almacena la secuencia de entrada actual (cadena, búfer, etc.).
YYMAXFILL
Una constante integral igual al valor máximo del argumento de YYFILL. Puede ser generado con un bloque max.
YYLESSTHAN
Una primitiva API genérica con una variable len. Debe definirse como un r-valor de tipo booleano que sea true si y solo si hay menos de **len caracteres de entrada.
YYRESTORE
Una primitiva de API genérica que debe restaurar la posición de entrada actual al valor guardado por YYBACKUP.
YYBACKUPCTX
Una primitiva de API genérica que debe guardar la posición de entrada actual como la posición del contexto final (para ser restaurada más tarde con YYRESTORECTX).
YYRESTORECTX
Una primitiva de API genérica que debe restaurar la posición del contexto final guardada con YYBACKUPCTX.
YYRESTORETAG
Una primitiva de API genérica con una variable tag que debe restaurar la posición del contexto final al valor de tag.
YYSTAGP
Una primitiva de API genérica con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para más detalles). YYSTAGP debe establecer tag a la posición de entrada actual.
YYSTAGN
Una primitiva de API genérica con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para más detalles). YYSTAGN debe establecer tag a un valor que representa una posición de entrada inexistente.
YYMTAGP
Una primitiva de API genérica con una variable tag. YYMTAGP debe agregar la posición actual al historial de subcoincidencias de tag (ver sección de extracción de subcoincidencias para más detalles).
YYMTAGN
Una primitiva de API genérica con una variable tag. YYMTAGN debe agregar un valor que representa una posición de entrada inexistente al historial de subcoincidencias de tag (ver sección de extracción de subcoincidencias para más detalles).
YYSHIFT
Una primitiva de API genérica con una variable shift que debe desplazar la posición de entrada actual en shift caracteres (el valor de desplazamiento puede ser negativo).
YYCOPYSTAG
Una primitiva de API genérica con dos variables, lhs y rhs que debe copiar la variable s-tag del lado derecho rhs a la variable s-tag del lado izquierdo lhs. Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que asigna lhs a rhs.
YYCOPYMTAG
Una primitiva de API genérica con dos variables, lhs y rhs que debe copiar la variable m-tag del lado derecho rhs a la variable m-tag del lado izquierdo lhs. Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que asigna lhs a rhs.
YYSHIFTSTAG
Una primitiva de API genérica con dos variables, tag y shift que debe desplazar tag en shift unidades de código (el valor de desplazamiento puede ser negativo).
YYSHIFTMTAG
Una primitiva de API genérica con dos variables, tag y shift que debe desplazar el último valor en el historial de tag en shift unidades de código (el valor de desplazamiento puede ser negativo).
YYMAXNMATCH
Una constante integral igual al número máximo de grupos de captura POSIX en una regla. Se genera con un bloque maxnmatch.
YYCONDTYPE
El tipo del enum de condición. Puede generarse ya sea con el bloque conditions o con la opción --header.
YYGETACCEPT
Una primitiva con una variable var que almacena el selector numérico de la regla aceptada. Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que lee de var.
YYSETACCEPT
Una primitiva con dos variables: var (un l-valor que almacena el selector numérico de la regla aceptada) y val (el valor del selector). Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que asigna var a val.
YYGETCOND
Un r-valor de tipo YYCONDTYPE que es igual al identificador de condición actual.
YYSETCOND
Una primitiva con una variable cond que debe establecer el identificador de condición actual a cond.
YYGETSTATE
Un r-valor de tipo entero que es igual al estado actual del lexer. Debe inicializarse a -1.
YYSETSTATE
Una primitiva con una variable state que debe establecer el estado actual del lexer a state.
YYDEBUG
Esta primitiva se genera solo con la opción -d, --debug-output. Su propósito es agregar registro al código generado (la definición típica de YYDEBUG es una sentencia print). Las sentencias YYDEBUG se generan en cada estado y tienen dos variables: state (un índice de estado DFA o -1) y symbol (el símbolo de entrada actual).
yyaccept
Un l-valor de tipo integral sin signo que almacena el número de la última regla coincidente. La definición del usuario es necesaria solo con la opción --storable-state.
yybm
Una tabla que contiene mapas de bits comprimidos para hasta 8 transiciones (utilizado con la opción --bitmaps). La tabla contiene 256 elementos y se indexa por unidades de código de 1 byte. Cada elemento de 8 bits combina valores booleanos para hasta 8 transiciones. El bit k-ésimo del n-ésimo elemento es verdadero si la unidad de código n-ésima está en el rango de la transición k-ésima. La idea de este mapa de bits es reemplazar muchas ramas if o casos switch con una sola comprobación de un solo bit en la tabla.
yych
Un l-valor de tipo YYCTYPE que almacena el carácter de entrada actual. La definición del usuario es necesaria solo con la opción -f --storable-state.
yyctable
Tabla de saltos generada para la distribución de condiciones iniciales (habilitada con la combinación de las opciones --conditions y --computed-gotos).
yyfill
Un l-valor que almacena el resultado de la llamada a YYFILL (esto puede ser necesario para lenguajes puramente funcionales, donde YYFILL es una función monádica con un valor de retorno complejo).
yynmatch
Un l-valor de tipo integral sin signo que almacena el número de grupos de captura POSIX en la regla coincidente. Se utiliza solo con la opción -P --posix-captures.
yypmatch
Un array de l-valores que se utilizan para mantener los valores de etiqueta correspondientes a los paréntesis de captura en la regla coincidente. La longitud del array debe ser al menos yynmatch * 2 (generalmente YYMAXNMATCH * 2 es una buena opción). Se utiliza solo con la opción -P --posix-captures.
yystable
Obsoleto.
yystate
Un l-valor utilizado con la opción --loop-switch para almacenar el estado DFA actual.
yytarget
Tabla de saltos que contiene destinos de salto (direcciones de etiquetas) para todas las transiciones desde un estado. Esta tabla es local a cada estado. La generación de tablas yytarget está habilitada con la opción --computed-gotos.

Opciones

Algunas de las opciones tienen configuraciones correspondientes, otras son globales y no se pueden cambiar después de que re2c comience a leer el archivo de entrada. Las opciones de depuración generalmente requieren compilar re2c en configuración de depuración. Las opciones internas son útiles para experimentar con los algoritmos utilizados en re2c.

-? --help -h
Mostrar mensaje de ayuda.
--api <simple | record | generic>
Especifica la API utilizada por el código generado para interactuar con el código definido por el usuario. La opción simple debe usarse en casos simples cuando no hay necesidad de recarga de búfer y almacenamiento del estado del lexer. La opción record debe usarse cuando el estado del lexer necesita ser almacenado en un registro (struct, class, etc.). La opción generic debe usarse en casos complejos cuando las otras dos APIs no son lo suficientemente flexibles.
--bit-vectors -b
Optimiza los saltos condicionales usando máscaras de bits. Esta opción implica --nested-ifs.
--captures, --leftmost-captures
Habilita la extracción de subcoincidencias con grupos de captura codiciosos más a la izquierda. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla coincidente.
--captvars, --leftmost-captvars
Habilita la extracción de subcoincidencias con grupos de captura codiciosos más a la izquierda. El resultado
se recopila en las variables yytl<k>, yytr<k> para el grupo de captura k.
--case-insensitive
Trata las cadenas entre comillas simples y dobles como si no distinguieran entre mayúsculas y minúsculas.
--case-inverted
Invierte el significado de las cadenas entre comillas simples y dobles: trata las cadenas entre comillas simples como si distinguieran entre mayúsculas y minúsculas, y las cadenas entre comillas dobles como si no las distinguieran.
--case-ranges
Colapsa casos consecutivos en sentencias switch en un rango de la forma low ... high. Esta sintaxis es una extensión del lenguaje C/C++ que soportan compiladores como GCC, Clang y Tcc. La principal ventaja sobre el uso de casos individuales es un código generado más pequeño y un tiempo de generación más rápido, aunque para algunos compiladores como Tcc también resulta en un tamaño de binario menor.
--computed-gotos -g
Optimiza saltos condicionales usando la extensión no estándar "computed goto" (que debe ser soportada por el compilador). re2d genera tablas de saltos solo en casos complejos con muchas ramas condicionales. El umbral de complejidad se puede configurar con cgoto:threshold. Los desplazamientos relativos se pueden habilitar con la configuración cgoto:relative. Esta opción implica --bit-vectors.
--computed-gotos-relative
Similar a --computed-gotos pero genera desplazamientos relativos para las tablas de saltos en su lugar (que deben ser soportados por el compilador). Esta opción implica --computed-gotos.
--conditions --start-conditions -c
Habilita el soporte de "condiciones" al estilo Flex: múltiples lexers interrelacionados dentro de un solo bloque. Esta es una alternativa a especificar manualmente diferentes bloques de re2d conectados con goto o llamadas a funciones.
--depfile FILE
Escribe información de dependencia en FILE en forma de una regla de Makefile <output-file> : <input-file> [include-file ...]. Esto permite rastrear dependencias de compilación en presencia de bloques/directivas include, de modo que la actualización de archivos de inclusión active la regeneración del archivo de salida. Esta opción depende de la opción --output.
--ebcdic --ecb -e
Genera un lexer que lee la entrada en codificación EBCDIC. re2d asume que el rango de caracteres es 0 -- 0xFF y el tamaño del carácter es de 1 byte.
--empty-class <match-empty | match-none | error>
Define la forma en que re2d trata las clases de caracteres vacías. Con match-empty (el valor predeterminado) la clase vacía coincide con la entrada vacía (lo cual es ilógico, pero compatible con versiones anteriores). Con match-none la clase vacía siempre falla al coincidir. Con error la clase vacía genera un error de compilación.
--encoding-policy <fail | substitute | ignore>
Define la forma en que re2d trata los sustitutos Unicode. Con fail re2d se aborta con un error al encontrar un sustituto. Con substitute re2d reemplaza silenciosamente los sustitutos con el punto de código de error 0xFFFD. Con ignore (el valor predeterminado) re2d trata los sustitutos como puntos de código normales. El estándar Unicode dice que los sustitutos independientes son inválidos, pero las bibliotecas y programas del mundo real se comportan de maneras diferentes.
--flex-syntax -F
Soporte parcial de sintaxis Flex: en este modo, las definiciones nombradas no necesitan el signo igual ni el punto y coma de terminación, y cuando se usan deben estar rodeadas por llaves. Los nombres sin llaves se tratan como cadenas entre comillas dobles.
--goto-label
Utiliza el modelo de código "goto/label": codifica el DFA en forma de bloques de código etiquetados conectados con transiciones goto entre bloques. Esto solo se soporta para lenguajes que tienen una sentencia goto.
--header --type-header -t HEADER
Genera un archivo HEADER. El contenido del archivo se puede especificar usando bloques especiales header:on y header:off. Si se usan condiciones, la cabecera generada tendrá un enum de condiciones agregado automáticamente (a menos que haya un bloque explícito conditions).
-I PATH
Agrega PATH a la lista de ubicaciones que se utilizan al buscar archivos de inclusión. Esta opción es útil en combinación con el bloque o directiva include. re2d busca FILE en el directorio del archivo padre y en las ubicaciones de inclusión especificadas con la opción -I.
--input <default | custom>
Alias obsoleto para --api. La opción default corresponde a simple (es de hecho el valor predeterminado para la mayoría de los backends, pero no para todos). La opción custom corresponde a generic.
--input-encoding <ascii | utf8>
Especifica la forma en que re2d analiza las expresiones regulares. Con ascii (el valor predeterminado) re2d maneja la entrada como codificada en ASCII: cualquier secuencia de unidades de código es una secuencia de caracteres independientes de 1 byte. Con utf8 re2d maneja la entrada como codificada en UTF8 y reconoce caracteres multibyte.
--invert-captures
Invierte el significado de los grupos de captura y no captura. Por defecto (...) es de captura y (! ...) es de no captura. Con esta opción (! ...) es de captura y (...) es de no captura.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Especifica el lenguaje de destino. Los lenguajes soportados son C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (se pueden agregar más lenguajes a través de archivos de sintaxis definidos por el usuario, consulta la opción --syntax). La opción none deshabilita las configuraciones de sintaxis predeterminadas, de modo que el lenguaje de destino no está definido.
--location-format <gnu | msvc>
Especifica el formato de ubicación en los mensajes. Con gnu las ubicaciones se imprimen como 'nombrearchivo:línea:columna: ...'. Con msvc las ubicaciones se imprimen como 'nombrearchivo(línea,columna) ...'. El valor predeterminado es gnu.
--loop-switch
Utiliza el modelo de código "loop/switch": codifica el DFA en forma de un bucle sobre una sentencia switch, donde los estados individuales son casos del switch. El estado se almacena en una variable yystate. Las transiciones entre estados actualizan yystate a la etiqueta del caso del estado de destino y continúan la ejecución hasta el inicio del bucle.
--nested-ifs -s
Utiliza sentencias if anidadas en lugar de sentencias switch en saltos condicionales. Esto generalmente resulta en un código más eficiente con compiladores no optimizadores.
--no-debug-info -i
No genera directivas de línea. Esto puede ser útil cuando el código generado se almacena en un sistema de control de versiones (para evitar diffs autogenerados enormes en pequeños cambios).
--no-generation-date
Suprime la salida de la fecha en el archivo generado.
--no-version
Suprime la salida de la versión en el archivo generado.
--no-unsafe
No genera un wrapper unsafe sobre YYPEEK (esta opción es específica para Rust). Por razones de rendimiento, YYPEEK debería evitar la verificación de límites, ya que el lexer ya realiza comprobaciones de fin de entrada de manera más eficiente. El usuario puede optar por proporcionar una definición YYPEEK segura, o una definición que solo sea insegura en compilaciones de lanzamiento, en cuyo caso la opción --no-unsafe ayuda a evitar advertencias sobre bloques unsafe redundantes.
--output -o OUTPUT
Especifica el archivo OUTPUT.
--posix-captures, -P
Habilita la extracción de subcoincidencias con grupos de captura al estilo POSIX. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla de coincidencia.
--posix-captvars
Habilita la extracción de subcoincidencias con grupos de captura al estilo POSIX. El resultado se recopila en las variables yytl<k>, yytr<k> para el grupo de captura k.
--recursive-functions
Utiliza un modelo de código basado en funciones co-recursivas, donde cada estado del DFA es una función separada que puede llamar a otras funciones de estado o a sí misma.
--reusable -r
Obsoleto desde la versión 2.2 (los bloques reutilizables están permitidos por defecto ahora).
--skeleton -S
Ignora el código de interfaz definido por el usuario y genera un programa "esqueleto" autocontenido. Adicionalmente, genera archivos de entrada con cadenas derivadas de la gramática regular y resultados de coincidencia comprimidos que se utilizan para verificar el comportamiento del "esqueleto" en todas las entradas. Esta opción es útil para encontrar errores en optimizaciones y generación de código. Esta opción solo se soporta para C.
--storable-state -f
Genera un lexer que puede almacenar su estado interno. Esto es útil en lexers de modelo push que son detenidos por un programa externo cuando no hay suficiente entrada, y luego reanudados cuando hay más entrada disponible. En este modo, los usuarios deben definir adicionalmente las primitivas YYGETSTATE y YYSETSTATE, y las variables yych, yyaccept y state deben ser parte del estado almacenado del lexer.
--syntax FILE
Carga configuraciones desde el FILE especificado y las aplica además del archivo de sintaxis predeterminado. Ten en cuenta que FILE solo puede definir unas pocas configuraciones (si se utiliza para modificar la sintaxis predeterminada

Opción interna: algoritmo de minimización de DFA utilizado por re2d. La opción moore es el algoritmo de Moore (es la predeterminada). La opción table es el algoritmo de "relleno de tablas". Ambos algoritmos deberían producir el mismo DFA hasta el reetiquetado de estados; el relleno de tablas es más simple y mucho más lento, y sirve como implementación de referencia.
--eager-skip
Opción interna: hace que el lexer generado avance la posición de entrada activamente, inmediatamente después de leer el símbolo de entrada. Esto cambia el comportamiento predeterminado cuando la posición de entrada se avanza perezosamente, después de la transición al siguiente estado.
--no-lookahead
Opción interna, obsoleta. Solía habilitar el algoritmo TDFA(0). A diferencia de TDFA(1), el algoritmo TDFA(0) no utiliza la búsqueda anticipada de un solo símbolo. Aplica operaciones de registro a las transiciones entrantes en lugar de a las salientes. Las pruebas de rendimiento mostraron que el algoritmo TDFA(0) es menos eficiente que TDFA(1).
--no-optimize-tags
Opción interna: suprime la optimización de las variables de etiqueta (útil para depuración).
--posix-closure <gor1 | gtop>
Opción interna: especifica el algoritmo de camino más corto utilizado para la construcción del cierre epsilon con semántica de desambiguación POSIX: gor1 (predeterminado) significa el algoritmo de Goldberg-Radzik, y gtop significa el algoritmo de "orden topológico global".
--posix-prectable <complex | naive>
Opción interna: especifica el algoritmo utilizado para calcular la tabla de precedencia POSIX. El algoritmo complex calcula la tabla de precedencia en una sola traversa del árbol de historial de etiquetas y tiene complejidad cuadrática en el número de estados TNFA; es el predeterminado. El algoritmo naive tiene una complejidad cúbica en el peor de los casos en el número de estados TNFA, pero es mucho más simple que complex y puede ser ligeramente más rápido en casos no patológicos.
--stadfa
Opción interna, obsoleta. Solía habilitar el algoritmo staDFA, que difiere de TDFA en que las operaciones de registro se colocan en los estados en lugar de en las transiciones. Las pruebas de rendimiento mostraron que el algoritmo staDFA es menos eficiente que TDFA.
--fixed-tags <none | toplevel | all>
Opción interna: especifica si la optimización de etiquetas fijas debe aplicarse a todas las etiquetas (all), a ninguna de ellas (none), o solo a aquellas en concatenación de nivel superior (toplevel). El valor predeterminado es all. Las etiquetas "fijas" son aquellas que se encuentran dentro de una distancia fija de alguna otra etiqueta (llamada "base"). En tales casos, solo la etiqueta base necesita ser rastreada, y el valor de la etiqueta fija se puede calcular como el valor de la etiqueta base más un desplazamiento estático. Para las etiquetas que están bajo alternativas o repetición, también es necesario verificar si la etiqueta base tiene un valor de no coincidencia (en ese caso, la etiqueta fija también debe establecerse en no coincidencia, ignorando el desplazamiento). Para las etiquetas en concatenación de nivel superior, la verificación no es necesaria, ya que siempre coinciden.

Activa todas las advertencias.
-Werror
Convierte las advertencias en errores. Ten en cuenta que esta opción por sí sola no activa ninguna advertencia; solo afecta a aquellas advertencias que se han activado hasta ahora o se activarán más adelante.

Activa la advertencia warning.

Activa la advertencia warning y la trata como un error (esto implica -W<warning>).

No trata esta warning en particular como un error. Esto no desactiva la advertencia en sí misma.

Advierte si el programa generado hace suposiciones implícitas sobre la numeración de condiciones. Se debe usar la opción --header o el bloque conditions para generar un mapeo de nombres de condiciones a números y luego usar los nombres de condiciones autogenerados.

Advierte si una expresión regular contiene una clase de caracteres vacía. Intentar coincidir con una clase de caracteres vacía no tiene sentido: siempre debería fallar. Usa la opción --empty-class para cambiar el comportamiento predeterminado.

Advierte si una regla es nula (coincide con una cadena vacía). Si el lexer se ejecuta en un bucle y la coincidencia vacía es no intencionada, el lexer puede colgarse inesperadamente en un bucle infinito.

Advierte sobre reglas que están ocultas por otras reglas y que nunca coincidirán.
-Wdeprecated-eof_rule
Advierte sobre reglas de fin de entrada independientes $ que se romperán por cambios futuros y requerirán corrección. Por el momento, estas reglas tienen precedencia cuando entran en conflicto con otras reglas, pero después de la introducción del símbolo generalizado de fin de entrada $ prece

Advierte si un símbolo está escapado cuando no debería serlo. Por defecto, re2d ignora silenciosamente tales escapes, pero esto bien podría indicar un error tipográfico o un error en la secuencia de escape.
-Wnondeterministic-tags
Advierte si una etiqueta tiene un grado de n-ésimo de no determinismo, donde n es mayor que 1.

Archivos de sintaxis

El soporte para diferentes lenguajes en re2c se basa en la idea de archivos de sintaxis. Un archivo de sintaxis es un archivo de configuración que define la sintaxis del lenguaje de destino --- no todo el lenguaje, sino una pequeña parte de él que es utilizada por el código generado. Los archivos de sintaxis hacen que re2c sea muy flexible, pero no deben usarse como reemplazo de las configuraciones re2c: : su propósito es definir la sintaxis del lenguaje de destino, no personalizar un lexer en particular. Todos los lenguajes soportados tienen archivos de sintaxis predeterminados que forman parte de la distribución (ver subdirectorio include/syntax); también están incrustados en el binario re2d. Los usuarios pueden proporcionar un archivo de sintaxis personalizado que anule algunas configuraciones para uno de los lenguajes admitidos, o pueden optar por redefinir todas las configuraciones (en ese caso se debe usar la opción --lang none). Los archivos de sintaxis contienen configuraciones de cuatro tipos diferentes: listas de características, configuraciones de lenguaje, configuraciones in situ y plantillas de código.

Listas de características

Algunas configuraciones de lista definen varias características soportadas por un backend dado, de modo que re2d pueda generar un error claro si el usuario intenta habilitar una característica no soportada:
supported_apis
Una lista de APIs soportadas con elementos posibles simple, record, generic.
supported_api_styles
Una lista de estilos de API soportados con elementos posibles functions, free-form.
supported_code_models
Una lista de modelos de código soportados con elementos posibles goto-label, loop-switch, recursive-functions.
supported_targets
Una lista de destinos de generación de código soportados con elementos posibles code, dot, skeleton.
supported_features
Una lista de características soportadas con elementos posibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

semicolons
Distinto de cero si el lenguaje utiliza puntos y comas después de las sentencias.
backtick_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas invertidas.
single_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas simples.
indentation_sensitive
Distinto de cero si el lenguaje es sensible a la indentación.
wrap_blocks_in_braces
Distinto de cero si los bloques compuestos deben ir entre llaves.

Plantillas de código

Las plantillas de código definen la sintaxis del lenguaje de destino. Están escritas en un lenguaje simple específico del dominio con la siguiente gramática formal: 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Una plantilla de código es una secuencia de literales de cadena, variables, elementos opcionales y listas, o una referencia a otra plantilla de código, o un valor especial <undefined>. Las variables son marcadores de posición que se sustituyen durante la fase de generación de código. Las variables de lista son especiales: al expandir plantillas de lista, re2d repite expresiones el lado derecho de la columna varias veces, reemplazando cada vez las ocurrencias de la variable de lista con un valor específico para esta repetición. Las listas tienen límites opcionales (los valores negativos se cuentan desde el final, por ejemplo, -1 significa el último elemento). Los nombres condicionales comienzan con un punto. Tanto los condicionales como las variables pueden ser locales (específicos de la plantilla de código dada) o globales (permitidos en todas las plantillas de código). Cuando re2d lee el archivo de sintaxis, verifica que cada plantilla de código utilice solo las variables y condicionales permitidos en ella.

Por ejemplo, la siguiente plantilla de código define la construcción if-then-else para un lenguaje similar a C:

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Aquí branch es una variable de lista: branch{0} se expande a la primera rama (que es especial, ya que no hay parte else), branch{1:-1} se expande a todas las ramas restantes (si las hay). stmt también es una variable de lista: [stmt: stmt] es una lista anidada que se expande a una lista de sentencias en el cuerpo de la rama actual. topindent, indent, dedent y nl son variables globales, y .cond es un condicional local (su significado se describe a continuación). Esta plantilla de código podría producir el siguiente código:

if x {
    // do something
} else if y {
    // do something else
} else {
    // don't do anything
}

Aquí hay una lista de todas las plantillas de código admitidas por re2d con sus variables y condicionales locales. Tenga en cuenta que una definición particular puede, pero no tiene por qué, usar variables y condicionales locales. Cualquier plantilla de código no utilizada debe establecerse en <undefined>.

code:var_local
Declaración o definición de una variable local. Variables admitidas: type (el tipo de la variable), name (su nombre) e init (valor inicial, si lo hay). Condicionales: .init (verdadero si hay un inicializador).
code:var_global
Igual que code:var_local, excepto que se usa en el nivel superior.
code:const_local
Definición de una constante local. Variables admitidas: type (el tipo de la constante), name (su nombre) e init (valor inicial).
code:const_global
Igual que code:const_local, excepto que se usa en el nivel superior.

private int lex(immutable char[] s) {
    // Make a copy of the string with YYMAXFILL zeroes at the end.
    char *buf = cast(char*) malloc(s.length + YYMaxFill);
    memcpy(buf, cast(const(void*)) s, s.length);
    memset(buf + s.length, 0, YYMaxFill);
    const(char)* yycursor = buf;
    const(char)* yylimit = buf + s.length + YYMaxFill;
    int count = 0;
loop:
    /*!re2c
        re2c:YYCTYPE = char;
        re2c:YYFILL = "goto fail;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Check that it is the sentinel, not some unexpected null.
            if (yycursor - 1 == buf + s.length) goto exit; else goto fail;
        }
        str  { ++count; goto loop; }
        [ ]+ { goto loop; }
        *    { goto fail; }
    */
fail:
    count = -1;
exit:
    free(buf);
    return count;
}
void main() {
    assert(lex("") == 0);
    assert(lex("'qu\0tes' 'are' 'fine: \\'' ") == 3);
    assert(lex("'unterminated\\'") == -1);
    assert(lex("'unexpected \0 null\\'") == -1);
}

Comprobaciones personalizadas

Este ejemplo utiliza un método personalizado de manejo del final de la entrada basado en la API genérica. El programa cuenta cadenas entrecomilladas separadas por espacios. Es el mismo que el ejemplo de centinela, excepto que la entrada no está terminada en nulo. Para compensar la ausencia de un carácter centinela al final de la entrada, YYPEEK se redefine para realizar una verificación de límites antes de leer el siguiente carácter de entrada. Esto es ineficiente porque las comprobaciones se realizan con mucha frecuencia. Si la condición de comprobación falla, YYPEEK devuelve el carácter real, de lo contrario, devuelve un carácter centinela falso.

// re2d $INPUT -o $OUTPUT
module main;
import core.stdc.stdlib;
import core.stdc.string;
private int lex(immutable char[] s) {
    // For the sake of example create a string without terminating null.
    char *buf = cast(char*) malloc(s.length);
    memcpy(buf, cast(const(void*)) s, s.length);
    const(char) *cur = buf, lim = buf + s.length;
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:api = generic;
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = char;
        re2c:YYPEEK = "cur < lim ? *cur : 0";  // fake null
        re2c:YYSKIP = "++cur;";
        *      { count = -1; break; }
        [\x00] { break;{} }
        [a-z]+ { ++count; continue;{} }
        [ ]+   { continue; }
    */
    }
    free(buf);
    return count;
}
void main() {
    assert(lex("") == 0);
    assert(lex("one two three ") == 3);
    assert(lex("f0ur") == -1);
}

RELLENO DE BÚFER

La necesidad de almacenar en búfer surge cuando la entrada no se puede mapear en memoria a la vez: o bien es demasiado grande, o bien proviene de forma secuencial (como leer de un socket). La técnica habitual en tales casos es asignar un búfer de memoria de tamaño fijo y procesar la entrada en fragmentos que quepan en el búfer. Cuando se procesa el fragmento actual, se elimina y se introducen nuevos datos. En la práctica, es algo más complejo, porque el estado del analizador léxico no consiste en una única posición de entrada, sino en un conjunto de posiciones interrelacionadas:

  • cursor: el siguiente carácter de entrada a leer (YYCURSOR en la API de punteros C o YYSKIP/YYPEEK en la API genérica)
  • límite: la posición después del último carácter de entrada disponible (YYLIMIT en la API de punteros C, manejado implícitamente por YYLESSTHAN en la API genérica)
  • marcador: la posición de la coincidencia más reciente, si la hay (YYMARKER en la API predeterminada o YYBACKUP/YYRESTORE en la API genérica)
  • token: el inicio del lexema actual (implícito en la API de re2d, ya que no es necesario para la operación normal del analizador léxico y puede ser definido y actualizado por el usuario)
  • marcador de contexto: la posición del contexto de cola (YYCTXMARKER en la API de punteros C o YYBACKUPCTX/YYRESTORECTX en la API genérica)
  • variables de etiqueta: posiciones de subcoincidencias (definidas con bloques stags y mtags y primitivas de API genérica YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

No todas estas se utilizan en todos los casos, pero si se utilizan, deben ser actualizadas por YYFILL. Todas las posiciones activas están contenidas en el segmento entre el token y el cursor, por lo tanto, todo lo que esté entre el inicio del búfer y el token puede ser descartado, el segmento desde el token hasta el límite debe moverse al principio del búfer, y el espacio libre al final del búfer debe llenarse con nuevos datos. Para evitar llamadas frecuentes a YYFILL, es mejor introducir tantos caracteres de entrada como sea posible (aunque menos caracteres podrían ser suficientes para reanudar el análisis léxico). Los detalles de la implementación de YYFILL son ligeramente diferentes dependiendo de qué método de manejo de EOF se utilice: el caso de la regla EOF es algo más simple que el caso de la verificación de límites con relleno. Tenga en cuenta también que si se utiliza la opción -f --storable-state, YYFILL tiene una semántica ligeramente diferente (descrita en la sección sobre estado almacenable).

YYFILL con centinela

Si se utiliza la regla EOF, YYFILL es una primitiva similar a una función que no acepta argumentos y devuelve un valor que se verifica contra cero. La invocación de YYFILL se activa por la condición YYLIMIT <= YYCURSOR en la API de punteros C y YYLESSTHAN() en la API genérica. Un valor de retorno distinto de cero significa que YYFILL ha fallado. Una llamada exitosa a YYFILL debe suministrar al menos un carácter y ajustar las posiciones de entrada en consecuencia. El límite siempre debe establecerse en uno después de la última posición de entrada en el búfer, y el carácter en la posición límite debe ser el símbolo centinela especificado por la configuración re2c:eof. // re2d $INPUT -o $OUTPUT
module main;
import core.stdc.string;
import core.stdc.stdio;
enum BUFSIZE = 4095;
struct Input {
    FILE* file;
    char[BUFSIZE + 1] buffer;// +1 for sentinel
    char* yylimit, yycursor, yymarker, token;
    bool eof;
};
private int fill(ref Input it) {
    if (it.eof) return 1;
    const size_t shift = it.token - it.buffer.ptr;
    const size_t used = it.yylimit - it.token;
    // Error: lexeme too long. In real life could reallocate a larger buffer.
    if (shift < 1) return 2;
    // Shift buffer contents (discard everything up to the current token).
    memmove(cast(void*)it.buffer.ptr, it.token, used);
    it.yylimit -= shift;
    it.yycursor -= shift;
    it.yymarker -= shift;
    it.token -= shift;
    // Fill free space at the end of buffer with new data from file.
    it.yylimit += fread(it.yylimit, 1, BUFSIZE - used, it.file);
    it.yylimit[0] = 0;
    it.eof = it.yylimit < (it.buffer.ptr + BUFSIZE);
    return 0;
}
private int lex(ref Input yyrecord) {
    int count = 0;
    for (;;) {
        yyrecord.token = yyrecord.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:YYFILL = "fill(yyrecord) == 0";
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1; }
        $    { return count; }
        str  { ++count; continue; }
        [ ]+ { continue; }
    */
    }
    assert(0);
}
void main() {
    const char[] fname = "input";
    const char[] content = "'qu\0tes' 'are' 'fine: \\'' ";
    // Prepare input file: a few times the size of the buffer, containing
    // strings with zeroes and escaped quotes.
    FILE* f = fopen(fname.ptr, "w");
    for (int i = 0; i < BUFSIZE; ++i) {
        fwrite(cast(const(void*)) content.ptr, 1, content.length - 1, f);
    }
    fclose(f);
    int count = 3 * BUFSIZE; // number of quoted strings written to file
    // Initialize lexer state: all pointers are at the end of buffer.
    Input it;
    it.file = fopen(fname.ptr, "r");
    it.yycursor = it.yymarker = it.token = it.yylimit = it.buffer.ptr + BUFSIZE;
    it.eof = 0;
    // Sentinel (at YYLIMIT pointer) is set to zero, which triggers YYFILL.
    it.yylimit[0] = 0;
    // Run the lexer.
    assert(lex(it) == count);
    // Cleanup: remove input file.
    fclose(it.file);
    remove(fname.ptr);
}

YYFILL con relleno

En el caso predeterminado (cuando la regla EOF no se utiliza) YYFILL es una primitiva similar a una función que acepta un único argumento y no devuelve ningún valor. La invocación de YYFILL se activa por la condición (YYLIMIT - YYCURSOR) < n en la API de punteros C y YYLESSTHAN(n) en la API genérica. El argumento pasado a YYFILL es el número mínimo de caracteres que deben suministrarse. Si no logra hacerlo, YYFILL no debe regresar al analizador léxico (por esa razón se implementa mejor como una macro que regresa de la función que llama en caso de fallo). En caso de una invocación exitosa de YYFILL, la posición límite debe establecerse en uno después de la última posición de entrada en el búfer, o hasta el final del relleno YYMAXFILL (en caso de que YYFILL haya leído con éxito al menos n caracteres, pero no los suficientes para llenar todo el búfer). // re2d $INPUT -o $OUTPUT
module main;
import core.stdc.string;
import core.stdc.stdio;
/*!max:re2c*/
enum BufSize = (4096 - YYMaxFill);
struct Input {
    FILE* file;
    char[BufSize + YYMaxFill] buffer;
    char* yylimit, yycursor, token;
    bool eof;
};
private int fill(ref Input it, size_t need) {
    if (it.eof) return 1;
    const size_t shift = it.token - it.buffer.ptr;
    const size_t used = it.yylimit - it.token;
    // Error: lexema demasiado largo. En la vida real podría reasignarse un búfer más grande.
    if (shift < need) return 2;
    // Desplaza el contenido del búfer (descarta todo hasta el token actual).
    memmove(it.buffer.ptr, it.token, used);
    it.yylimit -= shift;
    it.yycursor -= shift;
    it.token -= shift;
    // Rellena el espacio libre al final del búfer con nuevos datos del archivo.
    it.yylimit += fread(it.yylimit, 1, BufSize - used, it.file);
    // Si se leyó menos de lo esperado, es el final de la entrada => añade relleno de cero
    // para que el analizador léxico pueda acceder a los caracteres al final del búfer.
    if (it.yylimit < it.buffer.ptr + BufSize) {
        it.eof = true;
        memset(it.yylimit, 0, YYMaxFill);
        it.yylimit += YYMaxFill;
    }
    return 0;
}
private int lex(ref Input yyrecord) {
    int count = 0;
    for (;;) {
        yyrecord.token = yyrecord.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:YYFILL = "if (fill(yyrecord, @@) != 0) return -1;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Comprueba que sea el centinela, no una cadena nula inesperada.
            return yyrecord.token == yyrecord.yylimit - YYMaxFill ? count : -1;
        }
        str  { ++count; continue; }
        [ ]+ { continue; }
        *    { return -1; }
    */
    }
    assert(0);
}
void main() {
    const char[] fname = "input";
    const char[] content = "'qu\0tes' 'are' 'fine: \\'' ";
    // Prepara el archivo de entrada: varias veces el tamaño del búfer, que contiene
    // cadenas con ceros y comillas escapadas.
    FILE* f = fopen(fname.ptr, "w");
    for (int i = 0; i < BufSize; ++i) {
        fwrite(content.ptr, 1, content.length - 1, f);
    }
    fclose(f);
    int count = 3 * BufSize; // número de cadenas entrecomilladas escritas en el archivo
    // Inicializa el estado del analizador léxico: todos los punteros están al final del búfer.
    // Esto activa inmediatamente YYFILL, ya que la comprobación `it.yycursor < it.yylimit` falla.
    Input it;
    it.file = fopen(fname.ptr, "r");
    it.yycursor = it.token = it.yylimit = it.buffer.ptr + BufSize;
    it.eof = 0;
    // Ejecuta el analizador léxico.
    assert(lex(it) == count);
    // Limpieza: elimina el archivo de entrada.
    fclose(it.file);
    remove(fname.ptr);
}

CARACTERÍSTICAS

Múltiples bloques

A veces es necesario tener varios analizadores léxicos interrelacionados (por ejemplo, si hay una máquina de estados de alto nivel que transiciona entre modos de analizador léxico). Esto se puede implementar utilizando múltiples bloques conectados de re2d. Otra opción es utilizar condiciones de inicio.

La implementación de las conexiones entre bloques depende del lenguaje de destino. En lenguajes que tienen la sentencia goto (como C/C++ y Go) se pueden tener todos los bloques en una sola función, cada uno prefijado con una etiqueta. La transición de un bloque a otro es una simple sentencia goto. En lenguajes que no tienen goto (como Rust) es necesario utilizar un bucle con un switch sobre una variable de estado, similar al bucle/switch yystate generado por re2d, o envolver cada bloque en una función y usar llamadas a funciones.

El siguiente ejemplo utiliza varios bloques para analizar números binarios, octales, decimales y hexadecimales. Cada base tiene su propio bloque. El bloque inicial determina la base y se dirige a otros bloques. Las configuraciones comunes se definen en un bloque separado al principio del programa; son heredadas por los otros bloques.

// re2d $INPUT -o $OUTPUT -i
module main;
enum ERROR = ulong.max;
private void add(ulong BASE)(ref ulong u, int d) {
    u = u * BASE + d;
    if (u > uint.max) { u = ERROR; }
}
private ulong parse_u32(const(char)* s) {
    const(char)* yycursor = s, yymarker;
    ulong u = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = char;
        end = "\x00";
        '0b' / [01]        { goto bin; }
        "0"                { goto oct; }
        "" / [1-9]         { goto dec; }
        '0x' / [0-9a-fA-F] { goto hex; }
        *                  { return ERROR; }
    */
bin:
    /*!re2c
        end   { return u; }
        [01]  { add!(2)(u, yycursor[-1] - '0'); goto bin; }
        *     { return ERROR; }
    */
oct:
    /*!re2c
        end   { return u; }
        [0-7] { add!(8)(u, yycursor[-1] - '0'); goto oct; }
        *     { return ERROR; }
    */
dec:
    /*!re2c
        end   { return u; }
        [0-9] { add!(10)(u, yycursor[-1] - '0'); goto dec; }
        *     { return ERROR; }
    */
hex:
    /*!re2c
        end   { return u; }
        [0-9] { add!(16)(u, yycursor[-1] - '0');      goto hex; }
        [a-f] { add!(16)(u, yycursor[-1] - 'a' + 10); goto hex; }
        [A-F] { add!(16)(u, yycursor[-1] - 'A' + 10); goto hex; }
        *     { return ERROR; }
    */
}
void main() {
    assert(parse_u32("") == ERROR);
    assert(parse_u32("1234567890") == 1234567890);
    assert(parse_u32("0b1101") == 13);
    assert(parse_u32("0x7Fe") == 2046);
    assert(parse_u32("0644") == 420);
    assert(parse_u32("9999999999") == ERROR);
}

Condiciones de inicio

Las condiciones de inicio se habilitan con la opción --start-conditions. Proporcionan una forma de codificar múltiples autómatas interrelacionados dentro del mismo bloque de re2d.

Cada condición corresponde a un solo autómata y tiene un nombre único especificado por el usuario y un número interno único definido por re2d. Los números se utilizan para cambiar entre condiciones: el código generado utiliza los primitivos YYGETCOND y YYSETCOND para obtener la condición actual o establecerla en el número dado. Utiliza el bloque conditions, la opción --header o la configuración re2c:header para generar identificadores numéricos de condición. La configuración re2c:cond:enumprefix especifica el prefijo del identificador generado.

En modo de condición, cada regla debe ir precedida por una lista de nombres de condición separados por comas entre corchetes angulares, o un comodín <*> para denotar todas las condiciones. La sintaxis de la regla se extiende de la siguiente manera:

< lista-condicion > expresion-regular código
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular y ejecuta el código asociado.
< lista-condicion > expresion-regular => condicion código
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular, establece la condición actual a condicion y ejecuta el código asociado.
< lista-condicion > expresion-regular :=> condicion
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular y transiciona inmediatamente a condicion (no hay acción semántica).
< lista-condicion > !acción código
Una regla que vincula el código al lugar definido por acción en cada condición de la lista-condicion (ver la sección de acciones para varios tipos de acciones).
<! lista-condicion > código
Una regla que antepone el código a las acciones semánticas de todas las reglas para cada condición de la lista-condicion. Esta sintaxis está obsoleta y se debe usar la acción !pre_rule en su lugar (hace exactamente lo mismo).
< > código
Una regla que crea una condición de entrada especial con el número cero y el nombre "0" que ejecuta el código antes de saltar a otras condiciones. Esta sintaxis está obsoleta y se debe usar la acción !entry en su lugar (proporciona un control más detallado, ya que el código puede especificarse por condición, y se puede saltar directamente al inicio de la condición sin pasar por la distribución de condiciones).
< > => condicion código
Igual que la regla anterior, excepto que establece la siguiente condicion.
< > :=> condicion
Igual que la regla anterior, excepto que no tiene código asociado y salta inmediatamente a condicion.

El código que re2d genera para las condiciones depende de si re2d utiliza el enfoque de goto/etiqueta o el enfoque de bucle/switch para codificar los autómatas.

En lenguajes que tienen la sentencia goto (como C/C++ y Go), las condiciones se implementan de forma natural como bloques de código prefijados con etiquetas de la forma yyc_<cond>, donde cond es un nombre de condición (el prefijo de etiqueta se puede cambiar con re2c:cond:prefix). Las transiciones entre condiciones se implementan utilizando goto y etiquetas de condición. Antes de todas las condiciones, re2d genera un switch inicial sobre YYGETSTATE que salta al estado inicial de la condición actual. Las reglas de acceso directo :=> omiten el switch inicial y saltan directamente a la condición especificada (se puede usar re2c:cond:goto para cambiar el comportamiento predeterminado). Las reglas con acciones semánticas no saltan automáticamente a la siguiente condición; esto debe ser hecho por el código de acción definido por el usuario.

En lenguajes que no tienen goto (como Rust), re2d reutiliza la variable yystate para almacenar los números de condición. Cada condición obtiene un identificador numérico igual al número de su estado de inicio, y un switch entre condiciones no es diferente de un switch entre los estados DFA de un si

a que la condición de inicio no necesita un selector de condición inicial separado. (Dado que el mismo enfoque se utiliza para implementar estados almacenables, YYGETCOND/YYSETCOND son redundantes si se usan tanto estados almacenables como condiciones).

El programa a continuación utiliza condiciones de inicio para analizar números binarios, octales, decimales y hexadecimales. Hay un solo bloque donde cada base tiene su propia condición, y la condición inicial está conectada a todas ellas. La variable definida por el usuario cond almacena el número de la condición actual; se inicializa con el número de la condición inicial generada con el bloque conditions.

// re2d $INPUT -o $OUTPUT -ci
module main;
enum ERROR = ulong.max;
/*!conditions:re2c*/
private void add(ulong BASE)(ref ulong u, int d) {
    u = u * BASE + d;
    if (u > uint.max) { u = ERROR; }
}
private ulong parse_u32(const(char)* s) {
    const(char)* yycursor = s, yymarker;
    YYCond yycond = YYCond.yycinit;
    ulong u = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = char;
        <*> * { return ERROR; }
        <init> '0b' / [01]        :=> bin
        <init> "0"                :=> oct
        <init> "" / [1-9]         :=> dec
        <init> '0x' / [0-9a-fA-F] :=> hex
        <bin, oct, dec, hex> "\x00" { return u; }
        <bin> [01]  { add!(2)(u,  yycursor[-1] - '0');      goto yyc_bin; }
        <oct> [0-7] { add!(8)(u,  yycursor[-1] - '0');      goto yyc_oct; }
        <dec> [0-9] { add!(10)(u, yycursor[-1] - '0');      goto yyc_dec; }
        <hex> [0-9] { add!(16)(u, yycursor[-1] - '0');      goto yyc_hex; }
        <hex> [a-f] { add!(16)(u, yycursor[-1] - 'a' + 10); goto yyc_hex; }
        <hex> [A-F] { add!(16)(u, yycursor[-1] - 'A' + 10); goto yyc_hex; }
    */
}

    assert(parse_u32("") == ERROR);
    assert(parse_u32("1234567890") == 1234567890);
    assert(parse_u32("0b1101") == 13);

Estado almacenable

Con la opción --storable-state, re2d genera un lexer que puede almacenar su estado actual, devolver el control al llamador y, más tarde, reanudar las operaciones exactamente donde se detuvo. El modo de operación predeterminado en re2d es un modelo de "pull" (tirar), en el que el lexer "tira" de más entrada cuando la necesita. Esto puede ser inaceptable en casos en que la entrada se recibe pieza por pieza (por ejemplo, si el lexer es invocado por el analizador, o si el programa lexer se comunica mediante un protocolo de socket con algún otro programa que debe esperar una respuesta del lexer antes de transmitir el siguiente mensaje). La característica de estado almacenable está destinada precisamente a tales casos: permite generar lexers que funcionan en un modelo de "push" (empujar). Cuando el lexer necesita más entrada, almacena su estado y devuelve el control al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el lexer exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo de "pull":

  • Definir los primitivos YYSETSTATE() y YYGETSTATE(state).
  • Definir las variables yych, yyaccept (si se usa) y state como parte del estado persistente del lexer. La variable state debe inicializarse en -1.
  • YYFILL debe devolver el control al programa externo en lugar de intentar proporcionar más entrada. El código de retorno debe indicar que el lexer necesita más entrada.
  • El programa externo debe reconocer situaciones en las que el lexer necesita más entrada y responder apropiadamente.
  • Opcionalmente, usar el bloque getstate para generar un switch YYGETSTATE desacoplado del lexer principal. Esto solo funciona para lenguajes que tienen goto (no en modo --loop-switch).
  • Utilizar re2c:eof y el método de *sentinel con comprobaciones de límites* para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo añadir el relleno: el final de entrada actual puede no ser el final definitivo de la entrada, y añadir relleno demasiado pronto puede cortar un lexema glotón leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del buffer (lo cual ya está bloqueado debido a la condición de fin de entrada).

Aquí hay un ejemplo de un lexer con modelo "push" que simula la lectura de paquetes desde un socket. El lexer se ejecuta en un bucle hasta que encuentra el final de la entrada y devuelve el control a la función llamadora. La función llamadora proporciona más entrada "enviando" el siguiente paquete y reanuda el lexing. Este proceso se detiene cuando se han enviado todos los paquetes, o cuando hay un error.

// re2d $INPUT -o $OUTPUT -f
module main;
import core.stdc.stdio;
import core.stdc.string;
// Usar un buffer pequeño para cubrir el caso en que un lexema no cabe.
// En un uso real, se usaría un buffer más grande.
enum BUFSIZE = 10;
struct State {
    FILE* file;
    char[BUFSIZE + 1] buffer;
    char* yylimit, yycursor, yymarker, token;
    int yystate;
};
enum Status {END, READY, WAITING, BAD_PACKET, BIG_PACKET};
private Status fill(ref State st) {
    const size_t shift = st.token - cast(char*)st.buffer;
    const size_t used = st.yylimit - st.token;
    const size_t free = BUFSIZE - used;
    // Error: no hay espacio. En la vida real se podría reasignar un buffer más grande.
    if (free < 1) return Status.BIG_PACKET;
    // Desplaza el contenido del buffer (descarta los datos ya procesados).
    memmove(cast(void*)st.buffer, st.token, used);
    st.yylimit -= shift;
    st.yycursor -= shift;
    st.yymarker -= shift;
    st.token -= shift;
    // Llena el espacio libre al final del buffer con nuevos datos.
    const size_t read = fread(st.yylimit, 1, free, st.file);
    st.yylimit += read;
    st.yylimit[0] = 0; // añade el símbolo centinela
    return Status.READY;
}
private Status lex(ref State yyrecord, uint* recv) {
    char yych;
    /*!getstate:re2c*/
    for (;;) {
        yyrecord.token = yyrecord.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = char;
        re2c:YYFILL = "return Status.WAITING;";
        re2c:eof = 0;
        packet = [a-z]+[;];
        *      { return Status.BAD_PACKET; }
        $      { return Status.END; }
        packet { *recv = *recv + 1; continue; }
    */
    }
    assert(0); // inalcanzable

private void test(string[] packets, Status expect) {
    // Crea una tubería (abre el mismo archivo para lectura y escritura).
    const(char*) fname = "pipe";
    FILE* fw = fopen(fname, "w");
    FILE* fr = fopen(fname, "r");
    setvbuf(fw, null, _IONBF, 0);
    setvbuf(fr, null, _IONBF, 0);
    // Inicializa el estado del lexer: el valor de `state` es -1, todos los punteros
    // están al final del buffer.
    State st;
    st.file = fr;
    st.yycursor = st.yymarker = st.token = st.yylimit = cast(char*)st.buffer + BUFSIZE;
    // El centinela (en el puntero YYLIMIT) se establece en cero, lo que activa
    // YYFILL.
    st.yylimit[0] = 0;
    st.yystate = -1;
    // Bucle principal. El buffer contiene datos incompletos que aparecen paquete
    // por paquete. Cuando el lexer necesita más entrada, guarda su estado
    // interno y devuelve el control al llamador, que debe proporcionar más
    // entrada y reanudar el lexing.
    Status status;
    uint send = 0, recv = 0;
    for (;;) {
        status = lex(st, &recv);
        if (status == Status.END) {
            debug{printf("terminado: recibidos %u paquetes\n", recv);}
            break;
        } else if (status == Status.WAITING) {
            debug{printf("esperando...\n");}
            if (send < packets.length) {
                debug{printf("enviado paquete %u\n", send);}
                fprintf(fw, "%s", cast(char*)packets[send]);
                ++send;
            }
            status = fill(st);
            debug{printf("cola: '%s'\n", cast(char*)st.buffer);}
            if (status == Status.BIG_PACKET) {
                debug{printf("error: paquete demasiado grande\n");}
                break;
            }
            assert(status == Status.READY);
        } else {
            assert(status == Status.BAD_PACKET);
            debug{printf("error: paquete mal formado\n");}
            break;
        }
    }
    // Comprueba los resultados.
    assert(status == expect);
    if (status == Status.END) assert(recv == send);
    // Limpieza: elimina el archivo de entrada.
    fclose(fw);
    fclose(fr);
    remove(fname);
}
void main() {
    string[] packets1 = [];
    string[] packets2 = ["zero;", "one;", "two;", "three;", "four;"];
    string[] packets3 = ["zer0;"];
    string[] packets4 = ["looooooooooong;"];
    test(packets1, Status.END);
    test(packets2, Status.END);
    test(packets3, Status.BAD_PACKET);
    test(packets4, Status.BIG_PACKET);
}

Bloques reutilizables

Los bloques reutilizables de la forma /*!rules:re2c[:<name>] ... */ o %{rules[:<name>] ... %} se pueden reutilizar cualquier número de veces y combinar con otros bloques de re2d. El <name> es opcional. Un bloque de reglas se puede usar en un bloque o directiva use. El código de un bloque de reglas se genera en cada punto de uso.

Los bloques de uso se definen con /*!use:re2c[:<name>] ... */ o %{use[:<name>] ... %}. El <name> es opcional: si no se especifica, el bloque de reglas asociado es el más reciente (ya sea con nombre o sin nombre). Un bloque de uso puede añadir definiciones, configuraciones y reglas nombradas propias. Un caso de uso importante para los bloques de uso es un lexer que admite múltiples codificaciones de entrada: el mismo bloque de reglas se reutiliza varias veces con configuraciones específicas de codificación (ver el ejemplo a continuación).

La directiva de uso dentro de un bloque !use:<name>; se puede usar desde dentro de un bloque de re2c. Fusiona el bloque referenciado <name> en el actual. Si algunas de las reglas y configuraciones fusionadas se superponen con las definidas previamente, los conflictos se resuelven de la manera habitual: la regla más temprana tiene prioridad, y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y (en modo de condición) <!>, para las cuales una definición local del bloque tiene prioridad sobre cualquier heredada. La directiva de uso permite combinar diferentes bloques de re2c entre sí en un solo bloque (ver el ejemplo a continuación).

Los bloques con nombre y la directiva de uso dentro de bloques se añadieron en la versión 2.2 de re2c. Desde esa versión, los bloques reutilizables están permitidos por defecto (no se necesita ninguna opción especial). Antes de la versión 2.2, el modo de reutilización se habilitaba con la opción -r --reusable. Antes de la versión 1.2, los bloques reutilizables no se podían mezclar con bloques normales.

Extracción de subcoincidencias

re2d tiene dos opciones para la extracción de subcoincidencias.

Etiquetas
La primera opción es usar etiquetas independientes de la forma @stag o #mtag, donde stag y mtag son nombres arbitrarios definidos por el usuario. Las etiquetas se habilitan con la opción -T --tags o la configuración re2c:tags = 1. Semánticamente, las etiquetas son marcadores de posición: se pueden insertar en cualquier lugar de una expresión regular y se enlazan a la posición (o posiciones) correspondiente(s) en la cadena de entrada. Las etiquetas s se enlazan a la última posición coincidente, y las etiquetas m se enlazan a una lista de posiciones (pueden usarse en expresiones de repetición, donde una única posición en una expresión regular corresponde a múltiples posiciones en la cadena de entrada). Todas las etiquetas deben ser definidas por el usuario, ya sea manualmente o con la ayuda de los bloques svars y mvars. Si hay más de una forma en que las etiquetas pueden coincidir con la entrada, la ambigüedad se resuelve utilizando la estrategia de desambiguación codiciosa más a la izquierda.
Capturas
La segunda opción es usar grupos de captura. Se habilitan con la opción --captures o la configuración re2c:captures = 1. Hay dos variantes para diferentes políticas de desambiguación, --leftmost-captures (el predeterminado) es para la política codiciosa más a la izquierda, y --posix-captures es para la política de coincidencia más larga de POSIX. En este modo, todas las subexpresiones entre paréntesis se consideran grupos de captura, y un signo de exclamación puede usarse para marcar grupos que no capturan: (! ... ). Con la opción --invert-captures o la configuración re2c:invert-captures = 1 el significado del signo de exclamación se invierte. El número de grupos para la regla de coincidencia se almacena en una variable yynmatch (la expresión regular completa es el grupo número cero), y los resultados de las subcoincidencias se almacenan en el array yypmatch. Tanto yynmatch como yypmatch deben ser definidos por el usuario, y el tamaño de yypmatch debe ser al menos [yynmatch * 2]. Usa el bloque maxnmatch para definir YYMAXNMATCH, una constante que es igual al valor máximo de yynmatch entre todas las reglas.
Captvars
Otra forma de usar grupos de captura es la opción --captvars o la configuración re2c:captvars = 1. La única diferencia con --captures está en la forma en que el código generado almacena los resultados de las subcoincidencias: en lugar de yynmatch y yypmatch, re2d genera las variables yytl<k> y yytr<k> para el grupo de captura k-ésimo (el usuario debe declararlas usando un bloque svars). Las capturas con variables soportan dos políticas de desambiguación: --leftmost-captvars o re2c:leftmost-captvars = 1 para la política codiciosa más a la izquierda (la predeterminada) y --posix-captvars o re2c:posix-captvars para la política de coincidencia más larga de POSIX.

Internamente, todas estas opciones se traducen en etiquetas y Autómatas Finitos Deterministas Etiquetados con Lookahead. La idea central de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En el extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es simplemente un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es apenas perceptible. El TDFA generado utiliza una serie de variables de etiqueta que no se mapean directamente a las etiquetas: una única variable puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples variables para almacenar todos sus valores posibles. Finalmente, se resuelve la ambigüedad y solo sobrevive una variable final por etiqueta. Las variables de etiqueta deben definirse usando los bloques stags o mtags. Si el estado del lexer se almacena, las variables de etiqueta deben formar parte de él. También deben actualizarse mediante YYFILL.

Las etiquetas s soportan las siguientes operaciones:

  • guardar la posición de entrada en una etiqueta s: t = YYCURSOR con la API de puntero C o una operación definida por el usuario YYSTAGP(t) con la API genérica
  • guardar un valor predeterminado en una etiqueta s: t = NULL con la API de puntero C o una operación definida por el usuario YYSTAGN(t) con la API genérica
  • copiar una etiqueta s a otra: t1 = t2

Las etiquetas m soportan las siguientes operaciones:

  • añadir una posición de entrada a una etiqueta m: una operación definida por el usuario YYMTAGP(t) con la API predeterminada y genérica
  • añadir un valor predeterminado a una etiqueta m: una operación definida por el usuario YYMTAGN(t) con la API predeterminada y genérica
  • copiar una etiqueta m a otra: t1 = t2

Las etiquetas s se pueden implementar como valores escalares (punteros u offsets). Las etiquetas m necesitan una representación más compleja, ya que deben almacenar una secuencia de valores de etiqueta. La representación más ingenua e ineficiente de una etiqueta m es una lista (array, vector) de valores de etiqueta; una representación más eficiente es almacenar todas las etiquetas m en un árbol de prefijos representado como un array de nodos (v, p), donde v es el valor de la etiqueta y p es un puntero al nodo padre.

    int minor;

    /*!svars:re2c format = 'const(char)* @@;\n'; */
    // Variables de etiqueta intermedias utilizadas por el lexer (deben generarse automáticamente).
    /*!stags:re2c format = 'const(char)* @@;\n'; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:tags = 1;

    */
}

    /*!svars:re2c format = 'const(char)* @@;\n'; */
    // Variables de etiqueta intermedias utilizadas por el lexer (deben generarse automáticamente).
    /*!stags:re2c format = 'const(char)* @@;\n'; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:captvars = 1;
        re2c:YYCTYPE = "char";
        num = [0-9]+;
        (num) "." (num) ("." num)? [\x00] {
            ver.major = s2n(yytl1, yytr1);
            ver.minor = s2n(yytl2, yytr2);
            ver.patch = yytl3 ? s2n(yytl3 + 1, yytr3) : 0;
            return true;
        }
        * { return false; }

}
void main() {
    SemVer v;
    assert(lex("23.34", v) && v.major == 23 && v.minor == 34 && v.patch == 0);

Aquí hay un ejemplo de uso de m-tags para analizar una versión
    con un número variable de componentes. Las variables de etiqueta se almacenan
    en un trie.






// re2d $INPUT -o $OUTPUT
module main;
enum MtagRoot = -1;
// Un árbol de m-tags es una forma de almacenar historiales con una operación de copia O(1).
// Los historiales forman naturalmente un árbol, ya que tienen un inicio común y se bifurcan en algún momento.
// El árbol se almacena como una matriz de pares (valor de etiqueta, enlace al padre).
// Un m-tag se representa con un solo enlace en el árbol (índice de matriz).
struct Mtag {
    const(char)* elem; // valor de la etiqueta
    int pred; // índice del nodo predecesor o la raíz
};
alias MtagTrie = Mtag[];
alias Ver = int[];
private int s2n(const(char)* s, const(char)* e) { // cadena pre-analizada a número
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
// Añade un único valor a un historial de m-tags.
private void add_mtag(ref MtagTrie trie, ref int mtag, const(char)* value) {
    Mtag m = {value, mtag};
    mtag = cast(int)trie.length;
    trie ~= [m];
}
// Desenvuelve recursivamente los historiales de etiquetas y recopila los componentes de la versión.
private void unfold(const ref MtagTrie trie, int x, int y, ref Ver ver) {
    // Se llegó a la raíz del árbol de m-tags, detiene la recursión.
    if (x == MtagRoot && y == MtagRoot) return;
    // Desenvuelve el historial más a fondo.
    unfold(trie, trie[x].pred, trie[y].pred, ver);
    // Obtiene los valores de las etiquetas. Los historiales de etiquetas deben tener la misma longitud.
    assert(x != MtagRoot && y != MtagRoot);
    const(char)* ex = trie[x].elem, ey = trie[y].elem;
    if (ex != null && ey != null) {
        // Ambas etiquetas son punteros válidos, extrae el componente.
        ver ~= [s2n(ex, ey)];
    } else {
        // Ambas etiquetas son nulas (esto corresponde a cero repeticiones).
        assert(ex == null && ey == null);
    }
}
private bool parse(const(char)* str, ref Ver ver) {
    const(char)* yycursor = str, yymarker;
    MtagTrie mt;
    // Variables de etiqueta finales disponibles en la acción semántica.
    /*!svars:re2c format = "const(char)* @@;"; */
    /*!mvars:re2c format = "int @@;"; */
    // Variables de etiqueta intermedias utilizadas por el lexer (deben generarse automáticamente).
    /*!stags:re2c format = "const(char)* @@ = null;"; */
    /*!mtags:re2c format = "int @@ = MtagRoot;"; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        re2c:YYCTYPE = "char";
        re2c:YYMTAGP = "add_mtag(mt, @@, yycursor);";
        re2c:YYMTAGN = "add_mtag(mt, @@, null);";
        num = [0-9]+;
        @t1 num @t2 (". " #t3 num #t4)* [\x00] {
            ver = [];
            ver ~= [s2n(t1, t2)];
            unfold(mt, t3, t4, ver);
            return true;
        }
        * { return false; }
    */
}
void main() {
    Ver v;
    assert(parse("1", v) && v == [1]);
    assert(parse("1.2.3.4.5.6.7", v) && v == [1, 2, 3, 4, 5, 6, 7]);
    assert(!parse("1.2.", v));
}

Soporte de codificación

Es necesario comprender la diferencia entre puntos de código y unidades de código. Un punto de código es un identificador numérico de un símbolo. Una unidad de código es la unidad de almacenamiento más pequeña en el texto codificado. Un solo punto de código puede representarse con una o más unidades de código. En una codificación de longitud fija, todos los puntos de código se representan con el mismo número de unidades de código. En una codificación de longitud variable, los puntos de código pueden representarse con un número diferente de unidades de código. Tenga en cuenta que la regla "cualquiera" [^] coincide con cualquier punto de código, pero no necesariamente con cualquier unidad de código (la única forma de coincidir con cualquier unidad de código independientemente de la codificación es la regla predeterminada *). El lexer generado funciona con un flujo de unidades de código: yych almacena una unidad de código y YYCTYPE es el tipo de unidad de código. Las expresiones regulares, por otro lado, se especifican en términos de puntos de código. Cuando re2d compila expresiones regulares a autómatas, traduce puntos de código a unidades de código. Esto generalmente no es una asignación simple: en codificaciones de longitud variable, un solo rango de puntos de código puede traducirse a un gráfico complejo de unidades de código. Se soportan las siguientes codificaciones:

  • ASCII (habilitado por defecto). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • EBCDIC (habilitado con --ebcdic o re2c:encoding:ebcdic). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • UCS2 (habilitado con --ucs2 o re2c:encoding:ucs2). Es una codificación de longitud fija con espacio de código [0-0xFFFF] y puntos de código y unidades de código de 2 bytes.
  • UTF8 (habilitado con --utf8 o re2c:encoding:utf8). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
  • UTF16 (habilitado con --utf16 o re2c:encoding:utf16). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 a 2 unidades de código.
  • UTF32 (habilitado con --utf32 o re2c:encoding:utf32). Es una codificación Unicode de longitud fija con espacio de código [0-0x10FFFF] y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión include/unicode_categories.re proporciona definiciones de re2d para las categorías estándar de Unicode.

La opción --input-encoding especifica la codificación del archivo fuente, que se puede utilizar para habilitar literales Unicode en expresiones regulares. Por ejemplo, --input-encoding utf8 le dice a re2d que el archivo fuente está en UTF8 (difiere de --utf8 que establece la codificación del texto de entrada). La opción --encoding-policy especifica la forma en que re2d maneja los sustitutos Unicode (puntos de código en el rango [0xD800-0xDFFF]).

A continuación, se muestra un ejemplo de un lexer para identificadores Unicode codificados en UTF8.

// re2d $INPUT -o $OUTPUT -8 -i
module main;
/*!include:re2c "unicode_categories.re" */
private int lex(const(char)* s) {
    const(char)* yycursor = s, yymarker;
    /*!re2c
        re2c:YYCTYPE = "char";
        re2c:yyfill:enable = 0;
        // "Sintaxis simplificada de Identificador y Patrón Unicode"
        // (ver https://unicode.org/reports/tr31)
        id_start    = L | Nl | [$_];
        id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
        identifier  = id_start id_continue*;
        identifier { return 0; }
        *          { return 1; }
    */
}
void main() {
    assert(lex("_Ыдентификатор") == 0);
    assert(lex("!!!")==1);
}

Archivos de inclusión

re2d permite incluir otros archivos utilizando un bloque de la forma /*!include:re2c FILE */ o %{include FILE %}, o una directiva dentro del bloque !include FILE ;, donde FILE es una ruta al archivo a incluir. re2d busca archivos de inclusión en el directorio del archivo que incluye y en las ubicaciones de inclusión, que se pueden especificar con la opción -I. Los bloques/directivas de inclusión en re2d funcionan de la misma manera que #include de C/C++: el contenido de FILE se copia literalmente en lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias. Utilice la opción --depfile para rastrear las dependencias de compilación del archivo de salida en los archivos de inclusión. re2d proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como las categorías de Unicode) y forman algo así como una biblioteca estándar para re2d. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivo de inclusión 1 (definitions.d)

enum Result{ OK, FAIL };
/*!re2c
    number = [1-9][0-9]*;
*/

Archivo de inclusión 2 (extra_rules.re.inc)

/*!re2c
    // This rule is defined in file definitions.d
    // number = [1-9][0-9]*;

    identifier = [a-zA-Z_][a-zA-Z0-9_]*;
    whitespace = [ \t\n\r]+;
*/

Ejemplo de uso de archivos de inclusión (main.d)

import definitions;
import extra_rules;

module main;

// Turn on "autogenerate all rule variables" option.
// This is necessary to use predefined rule "number".
// re2c:autogen:rules:variable = 1;

private int lex(const(char)* str) {
    const(char)* yycursor = str, yymarker;
    const(char)* yyeol; // end-of-line tag variable

    // use rule "number" from definitions.d and
    // rules "identifier", "whitespace" from extra_rules.re.inc
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:yyfill:enable = 0;

        // Rule `yyeol` is needed to match end-of-line and
        // to detect lines with no tokens.
        yyeol = [\n];

        // Turn on re-use of rules from other files.
        re2c:rules:reuse = 1;

        // Use rule "number" and "identifier".
        // Need to adjust definition of "number" rule for dlang,
        // because integer literals in D are not allowed to start with zero.
        // Use `number` rule from definitions.d for parsing.
        // We use `[1-9][0-9]*` instead of the original `[1-9][0-9]*`
        number_d = [1-9][0-9]*;
        identifier {
            return 0; // OK
        }
        number_d {
            return 1; // OK
        }
        whitespace {
            // skip whitespace
            yycursor = yymarker; // use yymarker to skip token
            continue;
        }
        yyeol {
            return 2; // EOL
        }
        * {
            return -1; // FAIL
        }
    */
}

void main() {
    assert(lex("123 abc\n") == 1); // number
    assert(lex("abc 123\n") == 0); // identifier
    assert(lex(" \t \n") == 2); // whitespace then EOL
    assert(lex(" ") == 2); // whitespace then EOL
    assert(lex("abc") == 0); // identifier
    assert(lex("123") == 1); // number
    assert(lex("\n") == 2); // EOL
    assert(lex("") == -1); // FAIL
}

La palabra clave `defined`

La palabra clave `defined` se puede utilizar para comprobar si una etiqueta se ha definido en un análisis de línea de tiempo. Esto es útil para analizar formatos como CSV, donde algunos campos pueden estar vacíos.

// re2d $INPUT -o $OUTPUT
module main;
struct Record {
    const(char)* f1, f2, f3;
};
private bool lex(const(char)* str, ref Record r) {
    const(char)* yycursor = str, yymarker;
    // Variables de etiqueta finales disponibles en la acción semántica.
    /*!svars:re2c format = 'const(char)* @@;\n'; */
    // Variables de etiqueta intermedias utilizadas por el lexer (deben generarse automáticamente).
    /*!stags:re2c format = 'const(char)* @@;\n'; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = "char";
        // Campo 1: cadena
        f1 = *;
        // Campo 2: cadena o vacío
        f2 = *;
        // Campo 3: cadena o vacío
        f3 = *;
        // Fin de línea
        [\n] {
            if (defined(f1) && defined(f2) && defined(f3)) {
                r.f1 = f1; r.f2 = f2; r.f3 = f3;
                return true;
            }
            return false;
        }
        * { return false; }
    */
}
void main() {
    Record r;
    assert(lex("abc,def,ghi", r));
    assert(r.f1 == "abc" && r.f2 == "def" && r.f3 == "ghi");
    assert(lex("abc,,ghi", r));
    assert(r.f1 == "abc" && r.f2 == "" && r.f3 == "ghi");
    assert(lex(",,", r));
    assert(r.f1 == "" && r.f2 == "" && r.f3 == "");
    assert(!lex("abc,def")); // falta el tercer campo
}

En el ejemplo anterior, la regla de la última línea ([\n]) se activa solo si los campos f1, f2 y f3 se definen en la línea actual. La condición defined(f2) es verdadera si el campo f2 es un campo vacío (por ejemplo, "abc,,ghi") o si se analiza un valor real (por ejemplo, "abc,def,ghi"). Por el contrario, si el campo está ausente (por ejemplo, "abc,def"), la condición defined(f3) será falsa y el análisis fallará.

La palabra clave `empty`

La palabra clave `empty` se puede utilizar para detectar la ausencia de un patrón. Esto es útil para analizar formatos donde algunos campos son opcionales o pueden estar ausentes.

// re2d $INPUT -o $OUTPUT
module main;
struct Record {
    const(char)* f1, f2, f3;
};
private bool lex(const(char)* str, ref Record r) {
    const(char)* yycursor = str, yymarker;
    // Variables de etiqueta finales disponibles en la acción semántica.
    /*!svars:re2c format = 'const(char)* @@;\n'; */
    // Variables de etiqueta intermedias utilizadas por el lexer (deben generarse automáticamente).
    /*!stags:re2c format = 'const(char)* @@;\n'; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = "char";
        // Campo 1: cadena
        f1 = *;
        // Campo 2: cadena o vacío
        f2 = *;
        // Campo 3: cadena o vacío
        f3 = *;
        // Fin de línea
        [\n] {
            // El campo f1 debe estar presente. Los campos f2 y f3 son opcionales
            // y pueden estar vacíos.
            if (!empty(f1) && !empty(f2) && !empty(f3)) {
                r.f1 = f1; r.f2 = f2; r.f3 = f3;

        * { return false; }
    */

void main() {
    Record r;
    assert(lex("abc,def,ghi", r));
    assert(r.f1 == "abc" && r.f2 == "def" && r.f3 == "ghi");
    assert(lex("abc,,ghi", r));
    assert(r.f1 == "abc" && r.f2 == "" && r.f3 == "ghi");

    assert(r.f1 == "" && r.f2 == "" && r.f3 == "");

}

En el ejemplo anterior, la regla de la última línea ([\n]) se activa solo si los campos f1, f2 y f3 se definen en la línea actual. La condición !empty(f2) es verdadera si el campo f2 no está vacío. La condición !empty(f3) es verdadera si el campo f3 no está vacío.

Reglas Anidadas

re2c admite la definición y el uso de reglas anidadas. Las reglas anidadas son útiles cuando una regla es una subparte de otra regla. Por ejemplo, en un analizador de código fuente, un identificador puede contener una cadena, que a su vez puede contener caracteres de escape. re2c permite definir estas relaciones de anidamiento utilizando la sintaxis RULE = OUTER_RULE.

// re2d $INPUT -o $OUTPUT
module main;
// Definir reglas anidadas.
// Una cadena puede contener caracteres de escape.
// Un carácter de escape puede ser '\' seguido de cualquier carácter.
/*!re2c
    re2c:api = record;
    re2c:YYCTYPE = "char";
    re2c:yyfill:enable = 0;

    // Reglas de nivel superior
    str = "\"";
    esc = "\\."; // coincidir con '\' seguido de cualquier carácter
    ch = [^\"\\]; // coincidir con cualquier carácter que no sea " o \

    // Regla anidada: `string` es parte de `str`
    string = str esc* ch* str; // El contenido de la cadena

    // Acción semántica para analizar la cadena
    string {
        // Aquí puedes procesar el contenido de la cadena analizada
        // Por ejemplo, podrías decodificar caracteres de escape, etc.
        // printf("Cadena analizada: %.*s\n", len(str), str);
        return 0; // Éxito
    }
    * {
        return -1; // Fallo
    }
*/
void main() {
    // Ejemplos de cadenas válidas
    assert(lex("\"hello world\"") == 0);
    assert(lex("\"hello \\\" world\"") == 0); // Cadena con comilla escapada
    assert(lex("\"hello \\\\ world\"") == 0); // Cadena con barra invertida escapada
    assert(lex("\"\"") == 0); // Cadena vacía

    // Ejemplos de cadenas inválidas
    // assert(lex("\"hello world") == -1); // Falta comilla de cierre
    // assert(lex("\"hello\\") == -1); // Barra invertida al final
}

En este ejemplo:

  • La regla str coincide con una comilla de apertura o cierre.
  • La regla esc coincide con un carácter de escape (una barra invertida seguida de cualquier carácter).
  • La regla ch coincide con cualquier carácter que no sea una comilla o una barra invertida.
  • La regla string está anidada dentro de str. Coincide con una cadena válida, que puede contener caracteres de escape (esc) y caracteres normales (ch), delimitada por comillas (str).

La acción semántica se adjunta a la regla anidada string, lo que permite procesar el contenido de la cadena analizada.

Usando `yyaccept` y `yyabort`

Las directivas `yyaccept` y `yyabort` se pueden usar en acciones semánticas para controlar el flujo del análisis. `yyaccept` finaliza el análisis con éxito, mientras que `yyabort` finaliza el análisis con un error.

// re2d $INPUT -o $OUTPUT
module main;
private int lex(const(char)* str) {
    const(char)* yycursor = str, yymarker;
    // Variables de etiqueta finales disponibles en la acción semántica.
    /*!svars:re2c format = 'const(char)* @@;\n'; */
    // Variables de etiqueta intermedias utilizadas por el lexer (deben generarse automáticamente).
    /*!stags:re2c format = 'const(char)* @@;\n'; */
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:yyfill:enable = 0;

        // Regla para números enteros
        number = [0-9]+;

        // Acción semántica para la regla "number"
        number {
            // Imprime el número analizado y acepta
            // printf("Número analizado: %.*s\n", len(number), number);
            yyaccept; // Aceptar y terminar análisis con éxito
        }

        // Acción semántica para el final del archivo
        $ {
            // Si se llega al final del archivo sin analizar ningún número,
            // abortar el análisis con un error.
            yyabort; // Abortar análisis con error
        }

        // Regla comodín para cualquier otro carácter
        * {
            // Ignorar otros caracteres
            continue;
        }
    */
}
void main() {
    // Cadena que contiene un número
    assert(lex("12345") == 0);

    // Cadena que contiene un número y otros caracteres
    assert(lex("abc 12345 def") == 0);

    // Cadena vacía (provocará yyabort)
    // assert(lex("") == -1); // Esto fallará porque yyabort no devuelve un valor específico

    // Cadena que solo contiene caracteres no numéricos (provocará yyabort)
    // assert(lex("abc def") == -1); // Esto fallará porque yyabort no devuelve un valor específico
}

En este ejemplo:

  • La regla number coincide con una secuencia de dígitos. Cuando se encuentra un número, se ejecuta la acción semántica asociada.
  • Dentro de la acción semántica, `yyaccept` se llama para indicar que el análisis ha tenido éxito y debe finalizar.
  • La regla comodín * coincide con cualquier carácter que no sea un número. La acción semántica asociada simplemente continúa el análisis, ignorando estos caracteres.
  • La regla del final de archivo $ coincide con el final de la entrada. Si se alcanza el final del archivo sin haber encontrado ningún número (es decir, sin haber ejecutado `yyaccept`), se ejecuta la acción semántica asociada, que llama a `yyabort` para indicar un error en el análisis.

El uso de `yyaccept` y `yyabort` permite un control más fino sobre el flujo del análisis y la gestión de errores en comparación con simplemente devolver valores desde las acciones semánticas.

Usando `YYPOS` y `YYCTL`

re2c proporciona dos variables especiales, `YYPOS` y `YYCTL`, que pueden ser útiles para la manipulación de estado avanzado durante el análisis.

// re2d $INPUT -o $OUTPUT
module main;
// Definir un tipo de estado personalizado
struct State {
    int counter;
};
private bool lex(const(char)* str, ref State s) {
    const(char)* yycursor = str, yymarker;
    // Variables de etiqueta finales disponibles en la acción semántica.
    /*!svars:re2c format = 'const(char)* @@;\n'; */
    // Variables de etiqueta intermedias utilizadas por el lexer (deben generarse automáticamente).
    /*!stags:re2c format = 'const(char)* @@;\n'; */
    // Usar YYPOS para pasar el estado personalizado a través del análisis.
    // YYCTL se puede usar para controlar el comportamiento del lexer.
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:yyfill:enable = 0;
        re2c:YYPOS = "State*"; // Especificar el tipo de puntero de estado
        re2c:YYCTL = "int";    // Especificar el tipo de control

        // Regla para incrementar el contador
        "+" {
            // Incrementar el contador en el estado personalizado
            YYPOS.counter++;
            // Continuar el análisis
            continue;
        }

        // Regla para mostrar el valor del contador
        "show" {
            // Imprimir el valor actual del contador
            // printf("Valor del contador: %d\n", YYPOS.counter);
            // Establecer un valor de control para indicar que el valor se ha mostrado
            YYCTL = 1;
            continue;
        }

        // Regla para finalizar el análisis
        "$" {
            // Aceptar el análisis
            yyaccept;
        }

        // Regla comodín para cualquier otro carácter
        * {
            // Ignorar otros caracteres
            continue;
        }
    */
}
void main() {
    State s;
    s.counter = 0; // Inicializar el contador
    // Cadena de entrada para probar el análisis
    const(char)* input = "+++show+++";
    // Ejecutar el lexer
    assert(lex(input, s));
    // Verificar el valor final del contador
    assert(s.counter == 6); // 3 '+' al principio + 3 '+' después de 'show'
}

En este ejemplo:

  • `re2c:YYPOS = "State*";` especifica que `YYPOS` es un puntero a la estructura `State`. Esto permite pasar el estado personalizado a través de las llamadas al lexer.
  • `re2d:YYCTL = "int";` especifica que `YYCTL` es de tipo entero. Se puede utilizar para devolver valores de control desde el lexer, por ejemplo, para indicar que se ha realizado una acción específica.
  • Dentro de la acción semántica para la regla "+", incrementamos el contador en la estructura `State` a la que apunta `YYPOS`.
  • Dentro de la acción semántica para la regla "show", imprimimos el valor actual del contador y establecemos `YYCTL` a 1 para indicar que se ha mostrado el valor.
  • La regla "$" coincide con el final de la entrada y llama a `yyaccept` para finalizar el análisis correctamente.

El uso de `YYPOS` y `YYCTL` permite implementar un análisis con estado más sofisticado y un control más fino sobre el comportamiento del lexer.

Opciones de línea de comandos

re2c se puede invocar desde la línea de comandos. Aquí se muestra una lista de las opciones más comunes:

  • -h, --help: Muestra un mensaje de ayuda y sale.
  • -V, --version: Muestra información sobre la versión y sale.
  • -o, --output=FILE: Escribe la salida en FILE. Si no se especifica, la salida se escribe en stdout.
  • -i, --case-insensitive: Realiza coincidencias de expresiones regulares sin distinción entre mayúsculas y minúsculas.
  • -8, --utf8: Habilita el análisis de cadenas UTF-8.
  • -1, --encoding=NAME: Habilita el análisis de cadenas con codificación NAME. Los valores posibles para NAME son: ascii, ebcdic, ucs2, utf8, utf16, utf32.
  • -P, --encoding-policy=POLICY: Especifica la política de manejo de sustitutos Unicode. Los valores posibles para POLICY son: fail (falla en sustitutos), ignore (ignora sustitutos), substitute (reemplaza sustitutos con un carácter de reemplazo).
  • -I, --include-dir=DIR: Agrega un directorio a la ruta de búsqueda de archivos de inclusión.
  • --depfile=FILE: Escribe las dependencias de compilación en el archivo FILE.
  • --source-encoding=NAME: Especifica la codificación del archivo fuente de entrada. Esto es útil para analizar literales Unicode en expresiones regulares.
  • --input-encoding=NAME: Especifica la codificación del texto de entrada que se va a analizar.
  • -d, --decl=LANG: Genera declaraciones de tipo para el lenguaje de programación LANG. Los valores posibles para LANG son: c, cpp, d, go, java, javascript, json, pascal, python, ruby, rust, swift.
  • -s, --skeleton=FILE: Genera un archivo esqueleto con el nombre FILE. El archivo esqueleto contiene solo las definiciones de expresiones regulares y puede ser incluido por otros archivos re2c.
  • --tags: Habilita el uso de etiquetas (tags) para la captura de subcadenas.
  • --nested-tags: Habilita el uso de etiquetas anidadas.
  • --posix-captures: Habilita el uso de sintaxis de captura POSIX (por ejemplo, `(sub)*`).
  • --posix-groups: Habilita el uso de grupos de captura POSIX (por ejemplo, `(sub)?`).
  • --greedy-loops: Habilita bucles codiciosos (por ejemplo, `(sub)*` coincidirá con tantas subcadenas como sea posible).
  • --independent-loops: Habilita bucles independientes (por ejemplo, `(sub)*` coincidirá con cero o más subcadenas, sin la dependencia de que la parte restante de la expresión coincida).
  • --bbackup: Habilita la copia de seguridad de Bidi (necesario para algunas codificaciones de texto bidireccional).

Opciones de configuración

Además de las opciones de línea de comandos, re2d también puede configurarse mediante directivas en el propio archivo de entrada. Estas directivas suelen aparecer al principio del archivo, dentro de un bloque /*!re2c ... */ o %{% ... %}.

  • re2c:api = API: Especifica la interfaz de programación de aplicaciones (API) que se utilizará. Los valores posibles son:
    • c: API estándar de C (predeterminada).
    • record: API basada en registros para C/C++.
    • go: API para Go.
    • rust: API para Rust.
    • swift: API para Swift.
    • python: API para Python.
  • re2c:YYCTYPE = TYPE: Especifica el tipo de unidad de código utilizado en el texto de entrada. Los valores comunes incluyen char, short, int, wchar_t.
  • re2c:YYFILL = CONDITION: Especifica la condición que se debe cumplir para que se active la función de relleno de búfer.
  • re2c:eof = VALUE: Especifica el valor que representa el fin del archivo. El valor predeterminado es 0.
  • re2c:tags = 1: Habilita el uso de etiquetas para la captura de subcadenas.
  • re2c:nested-tags = 1: Habilita el uso de etiquetas anidadas.
  • re2c:posix-groups = 1: Habilita el uso de grupos de captura POSIX.
  • re2c:greedy-loops = 1: Habilita bucles codiciosos.
  • re2c:independent-loops = 1: Habilita bucles independientes.
  • re2c:case-insensitive = 1: Realiza coincidencias de expresiones regulares sin distinción entre mayúsculas y minúsculas.
  • re2c:encoding = NAME: Especifica la codificación del texto de entrada. Los valores posibles son los mismos que para la opción de línea de comandos --encoding.
  • re2c:encoding-policy = POLICY: Especifica la política de manejo de sustitutos Unicode. Los valores posibles son los mismos que para la opción de línea de comandos --encoding-policy.
  • re2c:indent = STRING: Especifica la cadena de indentación que se utilizará en el código generado.
  • re2c:line-directives = 1: Genera directivas de línea para el compilador (por ejemplo, `#line ...`).
  • re2c:skip-decls = 1: Omite la generación de declaraciones de tipo.
  • re2c:autogen:rules:variable = 1: Permite que las reglas definidas en archivos incluidos se utilicen como variables en el archivo principal.
  • re2c:constants = 1: Habilita la generación de constantes para los valores de retorno del lexer.
  • re2c:debug = 1: Habilita la salida de depuración.

Por ejemplo, para habilitar el análisis de UTF-8 y usar la API de Go, puede usar las siguientes directivas:

/*!re2c
    re2c:encoding = utf8;
    re2c:api = go;
    re2c:YYCTYPE = "rune";
*/

Autogeneración de variables de regla

Si necesita usar una regla definida en otro archivo (por ejemplo, a través de una directiva /*!include:re2c ... */), puede habilitar la autogeneración de variables de regla con la directiva:

/*!re2c
    re2c:autogen:rules:variable = 1;
*/

Esto permite que las reglas definidas en otros archivos se traten como variables en el archivo principal. Por ejemplo, si un archivo incluido define la regla `number = [0-9]+;`, y ha habilitado esta opción, puede usar `number` como una variable en su archivo principal.

Reutilización de reglas con `re2c:rules:reuse`

Para reutilizar reglas de archivos incluidos, debe habilitar la directiva `re2c:rules:reuse = 1;` en su archivo re2c principal. De forma predeterminada, re2c no permite la reutilización de reglas de archivos incluidos para evitar posibles conflictos de nombres y mantener la claridad del código. Al habilitar esta opción, le indica a re2c que debe buscar definiciones de reglas en los archivos incluidos, además de las definidas localmente.

/*!re2c
    re2c:rules:reuse = 1;
    // Ahora puedes usar reglas definidas en archivos incluidos
    // Por ejemplo, si definitions.d contiene "number = [0-9]+;",
    // puedes usar la regla "number" aquí.
    number { ... }
*/

Generación de constantes

Para habilitar la generación de constantes para los valores de retorno del lexer, utilice la siguiente directiva:

/*!re2c
    re2c:constants = 1;
*/

Esto generará constantes con nombres como `yyrule1`, `yyrule2`, etc., que corresponden a los valores de retorno de las reglas definidas en el archivo re2c. Esto puede hacer que el código generado sea más legible y fácil de mantener.

Por ejemplo, si tiene las siguientes reglas:

rule1 { return 1; }
rule2 { return 2; }

Con la directiva `re2c:constants = 1;`, re2c generará constantes similares a:

const int yyrule1 = 1;
const int yyrule2 = 2;

Y el código generado utilizará estas constantes en lugar de los valores numéricos literales.

Salida de depuración

Para habilitar la salida de depuración detallada del proceso de generación de código de re2c, utilice la siguiente directiva:

/*!re2c
    re2c:debug = 1;
*/

Esto puede ser útil para comprender cómo re2c construye los autómatas y cómo se mapean las expresiones regulares a las transiciones de estado. La salida de depuración generalmente se imprime en stderr.

Archivos de cabecera

re2d permite generar un archivo de cabecera a partir del archivo .re de entrada utilizando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de cabecera y el segundo bloque marca el final. Todo lo que esté entre estos bloques es procesado por re2d, y el código generado se escribe en el archivo especificado con la opción --header o la configuración re2c:header (o stdout si no se utiliza ni la opción ni la configuración). El archivo de cabecera autogenerado puede ser necesario en casos en los que re2d se utiliza para generar definiciones que deben ser visibles desde otras unidades de traducción.

Aquí hay un ejemplo de generación de un archivo de cabecera que contiene la definición del estado del analizador léxico con variables de etiqueta (el número de variables depende de la gramática regular y es desconocido para el programador).

Archivo de entrada

// re2d $INPUT -o $OUTPUT -i --header lexer/state.d
module main;
import core.stdc.stddef;
import lexer.state; // el módulo es generado por re2c
/*!header:re2c:on*/
module lexer.state;
struct LexerState {
    const(char)* str, yycursor;
    /*!stags:re2c format = "const(char)* @@;"; */
};
/*!header:re2c:off*/
private long lex(ref LexerState yyrecord) {
    const(char)* t;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:tags = 1;
        re2c:yyfill:enable = 0;
        re2c:header = "lexer/state.d";
        [a]* @t [b]* { return t - yyrecord.str; }
    */
}
void main() {
    const(char)* s = "ab";
    LexerState st = {s, s /*!stags:re2c format = ", null"; */};
    assert(lex(st) == 1);
    const(char)* s2 = "aaabbbbbbbb";
    LexerState st2 = {s2, s2 /*!stags:re2c format = ", null"; */};
    assert(lex(st2) == 3);
}

Programas esqueleto

Con la opción -S, --skeleton, re2d ignora todo el código que no es de re2d y genera un programa C autocontenido que puede ser compilado y ejecutado posteriormente. El programa consta del código del analizador léxico y los datos de entrada. Para cada DFA construido (bloque o condición) re2d genera un analizador léxico independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados de coincidencia esperados. El programa ejecuta cada analizador léxico en el archivo .input correspondiente y compara los resultados con las expectativas. Los programas esqueleto son muy útiles por varias razones:

  • Pueden verificar la corrección de varias optimizaciones de re2d (los datos se generan al principio del proceso, antes de que se haya realizado cualquier transformación del DFA).
  • La generación de un conjunto de datos de entrada con buena cobertura puede ser útil tanto para pruebas como para puntos de referencia.
  • La generación de programas ejecutables autocontenidos permite obtener casos de prueba minimizados (el código original puede ser grande o tener muchas dependencias).

La dificultad para generar datos de entrada es que, para todos los casos excepto los más triviales, el número de cadenas de entrada posibles es demasiado grande (incluso si la longitud de la cadena es limitada). re2d resuelve esta dificultad generando suficientes cadenas para cubrir casi todas las transiciones del DFA. Utiliza el siguiente algoritmo. Primero, construye un esqueleto del DFA. Para codificaciones con tamaño de unidad de código de 1 byte (como ASCII, UTF-8 y EBCDIC), el esqueleto es solo una copia exacta del DFA original. Para codificaciones con unidades de código de varios bytes, el esqueleto es una copia del DFA con ciertas transiciones omitidas: en particular, re2d toma como máximo 256 unidades de código para cada rango continuo y disjunto que corresponde a una transición del DFA. Los valores elegidos están distribuidos uniformemente e incluyen los límites del rango. En lugar de intentar cubrir todos los caminos posibles en el esqueleto (lo cual es inviable), re2d genera suficientes caminos para cubrir todas las transiciones del esqueleto, y por lo tanto, activar los saltos condicionales correspondientes en el analizador léxico. La implementación del algoritmo está limitada a ~1 GB de transiciones y consume una cantidad constante de memoria (re2d escribe los datos en el archivo tan pronto como se generan).

Visualización y depuración

Con la opción -D, --emit-dot, re2d no genera código. En su lugar, vuelca el DFA generado en formato DOT. Se puede convertir este volcado en una imagen del DFA utilizando Graphviz u otra biblioteca. Tenga en cuenta que esta opción muestra el DFA final después de haber pasado por una serie de optimizaciones y transformaciones. Las etapas anteriores se pueden volcar con varias opciones de depuración, como --dump-nfa, --dump-dfa-raw, etc. (consulte la lista completa de opciones).
