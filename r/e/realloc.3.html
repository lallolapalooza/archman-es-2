NOMBRE

malloc, free, calloc, realloc, reallocarray - asignar y liberar memoria dinámica

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <stdlib.h>
void *malloc(size_t tamaño);
void free(void *_Nullable p);
void *calloc(size_t n, size_t tamaño);
void *realloc(void *_Nullable p, size_t tamaño);
void *reallocarray(void *_Nullable p, size_t n, size_t tamaño);
Requisitos de Macro de Prueba de Características para glibc (ver feature_test_macros(7)):

reallocarray():

    Desde glibc 2.29:
        _DEFAULT_SOURCE
    glibc 2.28 y anteriores:
        _GNU_SOURCE

DESCRIPCIÓN

malloc()

La función malloc() asigna tamaño bytes y devuelve un puntero a la memoria asignada. La memoria no está inicializada. Si tamaño es 0, entonces malloc() devuelve un valor de puntero único que más tarde puede pasarse exitosamente a free(). (Ver "Comportamiento no portable" para problemas de portabilidad).

free()

La función free() libera el espacio de memoria apuntado por p, que debe haber sido devuelto por una llamada anterior a malloc() o funciones relacionadas. De lo contrario, o si p ya ha sido liberado, ocurre un comportamiento indefinido. Si p es NULL, no se realiza ninguna operación.

calloc()

La función calloc() asigna memoria para un array de n elementos de tamaño bytes cada uno y devuelve un puntero a la memoria asignada. La memoria se establece a cero. Si n o tamaño es 0, entonces calloc() devuelve un valor de puntero único que más tarde puede pasarse exitosamente a free().

Si la multiplicación de n y tamaño resultara en un desbordamiento entero, entonces calloc() devuelve un error. Por el contrario, no se detectaría un desbordamiento entero en la siguiente llamada a malloc(), con el resultado de que se asignaría un bloque de memoria de tamaño incorrecto:


malloc(n * tamaño);

realloc()

La función realloc() cambia el tamaño del bloque de memoria apuntado por p a tamaño bytes. Los contenidos de la memoria no cambiarán en el rango desde el inicio de la región hasta el mínimo entre el tamaño antiguo y el nuevo. Si el nuevo tamaño es mayor que el tamaño antiguo, la memoria añadida no será inicializada.

Si p es NULL, entonces la llamada es equivalente a malloc(tamaño), para todos los valores de tamaño.

Si tamaño es igual a cero, y p no es NULL, entonces la llamada es equivalente a free(p) (pero ver "Comportamiento no portable" para problemas de portabilidad).

A menos que p sea NULL, debe haber sido devuelto por una llamada anterior a malloc o funciones relacionadas. Si el área apuntada fue movida, se realiza un free(p).

reallocarray()

La función reallocarray() cambia el tamaño de (y posiblemente mueve) el bloque de memoria apuntado por p para que sea lo suficientemente grande para un array de n elementos, cada uno de los cuales tiene tamaño bytes. Es equivalente a la llamada


realloc(p, n * tamaño);

Sin embargo, a diferencia de esa llamada a realloc(), reallocarray() falla de forma segura en el caso en que la multiplicación desbordaría. Si ocurre tal desbordamiento, reallocarray() devuelve un error.

VALOR DE RETORNO

Las funciones malloc(), calloc(), realloc() y reallocarray() devuelven un puntero a la memoria asignada, que está adecuadamente alineado para cualquier tipo que quepa en el tamaño solicitado o menos. En caso de error, estas funciones devuelven NULL y establecen errno. Intentar asignar más de PTRDIFF_MAX bytes se considera un error, ya que un objeto tan grande podría causar un desbordamiento posterior en la resta de punteros.

La función free() no devuelve valor y preserva errno.

Las funciones realloc() y reallocarray() devuelven NULL si p no es NULL y el tamaño solicitado es cero; esto no se considera un error. (Ver "Comportamiento no portable" para problemas de portabilidad). De lo contrario, el puntero devuelto puede ser el mismo que p si la asignación no se movió (por ejemplo, había espacio para expandir la asignación in situ), o diferente de p si la asignación se movió a una nueva dirección. Si estas funciones fallan, el bloque original permanece intacto; no se libera ni se mueve.

ERRORES

calloc(), malloc(), realloc() y reallocarray() pueden fallar con el siguiente error:

ENOMEM
Sin memoria. Posiblemente, la aplicación alcanzó el límite RLIMIT_AS o RLIMIT_DATA descrito en getrlimit(2). Otra razón podría ser que el número de mapeos creados por el proceso llamante excedió el límite especificado por /proc/sys/vm/max_map_count.

realloc(p, 0)

El comportamiento de realloc(p, 0) en glibc no se conforma a ninguna de las versiones C99, C11, POSIX.1-2001, POSIX.1-2004, POSIX.1-2008, POSIX.1-2013, POSIX.1-2017, o POSIX.1-2024. La especificación C17 fue cambiada para que fuera conforme, pero esa especificación hizo imposible escribir código que determinara de forma fiable si el puntero de entrada se libera después de realloc(p, 0), y C23 lo cambió de nuevo para que esto sea un comportamiento indefinido, reconociendo que la especificación C17 era lo suficientemente amplia como para que el comportamiento indefinido no fuera peor que eso.

reallocarray() sufre los mismos problemas en glibc.

musl libc y los BSD se conforman a todas las versiones de ISO C y POSIX.1.

gnulib proporciona el módulo realloc-posix, que proporciona envolturas realloc() y reallocarray() que se conforman a todas las versiones de ISO C y POSIX.1.

Hay una propuesta para estandarizar el comportamiento de BSD: https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3621.txt.

NOMBRE

realloc, reallocarray — reasignar tamaño de un bloque de memoria

BIBLIOTECA

Biblioteca C estándar (libc)

SINOPSIS

#include <stdlib.h>
void *realloc(void *ptr, size_t size);
void *reallocarray(void *ptr, size_t n, size_t size);

DESCRIPCIÓN

Las funciones realloc() y reallocarray() cambian el tamaño de un bloque de memoria previamente asignado a ptr a size bytes, o n elementos de size bytes respectivamente. El nuevo tamaño del bloque es size para realloc() y n * size para reallocarray().

El contenido del bloque de memoria se conserva hasta el mínimo del tamaño original y el nuevo tamaño. Si el nuevo tamaño es mayor que el tamaño original, el contenido adicional no está inicializado. Si ptr es NULL, entonces se comporta de manera similar a malloc(), asignando un nuevo bloque de memoria del tamaño solicitado. Si size (o n * size) es cero, y ptr no es NULL, entonces se libera el bloque de memoria apuntado por ptr y se devuelve un puntero NULL válido, o un puntero que se puede pasar posteriormente a free(). El comportamiento exacto es especificado por la implementación.

Si realloc() o reallocarray() fallan al reasignar el bloque de memoria, se devuelve un puntero NULL y el bloque de memoria original apuntado por ptr no se modifica.

Si se produce una asignación exitosa, realloc() o reallocarray() devuelven un puntero al bloque de memoria recién asignado. Este puntero es diferente del puntero ptr original si el bloque tuvo que ser movido para acomodar el nuevo tamaño.

La función reallocarray() está diseñada para prevenir desbordamientos de enteros al calcular el tamaño total a asignar. Calcula n * size de una manera que detecta y falla si el resultado excedería el valor máximo representable por size_t.

VALOR DE RETORNO

En caso de éxito, realloc() y reallocarray() devuelven un puntero al bloque de memoria recién asignado. En caso de error, devuelven NULL.

ERRORES

Las funciones realloc() y reallocarray() pueden fallar si no hay suficiente memoria disponible para satisfacer la solicitud de asignación.

Además, al igual que otras funciones de asignación de memoria, pueden fallar si size (o n * size) es demasiado grande, lo que provoca un desbordamiento de tamaño.

ATRIBUTOS

SOBRE_EL_USO_DE_SEÑALES

Las funciones realloc() y reallocarray() son seguras para su uso con señales.

CONTENCIÓN_DE_DATOS_ESTRUCTURALES_DE_MEMORIA

Las llamadas a realloc() y reallocarray() son seguras para su uso en hilos.

ESTÁNDARES

El comportamiento de realloc() con un tamaño de cero ha sido ambiguo en los estándares C anteriores. C99 y estándares posteriores lo aclaran. reallocarray() es una adición más reciente y no está estandarizada formalmente por POSIX o C.

HISTORIA

glibc 2.26
OpenBSD 5.6, FreeBSD 11.0.

malloc() y funciones relacionadas rechazaron tamaños mayores que PTRDIFF_MAX a partir de glibc 2.30.

free() preservó errno a partir de glibc 2.33.

realloc(p, 0)

C89 fue ambiguo en su especificación de realloc(p, 0). C99 lo arregló parcialmente.

La implementación original en glibc habría sido conforme a C99. Sin embargo, irónicamente, al intentar cumplir con C99 antes de que se lanzara el estándar, glibc cambió su comportamiento en glibc 2.1.1 a algo que terminó no siendo conforme a la especificación final de C99 (pero esto es debatido, ya que la redacción del estándar parece autocontradictoria).

NOTAS

Por defecto, Linux sigue una estrategia optimista de asignación de memoria. Esto significa que cuando malloc() devuelve un valor distinto de NULL, no hay garantía de que la memoria esté realmente disponible. En caso de que resulte que el sistema se ha quedado sin memoria, uno o más procesos serán eliminados por el asesino OOM. Para más información, véase la descripción de /proc/sys/vm/overcommit_memory y /proc/sys/vm/oom_adj en proc(5), y el archivo fuente del kernel de Linux Documentation/vm/overcommit-accounting.rst.

Normalmente, malloc() asigna memoria del heap, y ajusta el tamaño del heap según sea necesario, usando sbrk(2). Al asignar bloques de memoria mayores que MMAP_THRESHOLD bytes, la implementación malloc() de glibc asigna la memoria como un mapeo anónimo privado usando mmap(2). MMAP_THRESHOLD es de 128 KiB por defecto, pero es ajustable usando mallopt(3). Antes de Linux 4.7, las asignaciones realizadas usando mmap(2) no se vieron afectadas por el límite de recursos RLIMIT_DATA; desde Linux 4.7, este límite también se aplica a las asignaciones realizadas usando mmap(2).

Para evitar la corrupción en aplicaciones multihilo, se utilizan mutex internos para proteger las estructuras de datos de gestión de memoria empleadas por estas funciones. En una aplicación multihilo en la que los hilos asignan y liberan memoria simultáneamente, podría haber contención por estos mutex. Para manejar de forma escalable la asignación de memoria en aplicaciones multihilo, glibc crea *arenas de asignación de memoria* adicionales si se detecta contención de mutex. Cada arena es una región grande de memoria que se asigna internamente por el sistema (usando brk(2) o mmap(2)), y se gestiona con sus propios mutex.

Si su programa utiliza un asignador de memoria privado, debería hacerlo reemplazando malloc(), free(), calloc() y realloc(). Las funciones de reemplazo deben implementar los comportamientos documentados de glibc, incluyendo el manejo de errno, las asignaciones de tamaño cero y la verificación de desbordamiento; de lo contrario, otras rutinas de la biblioteca podrían fallar o operar incorrectamente. Por ejemplo, si el free() de reemplazo no preserva errno, entonces rutinas de biblioteca aparentemente no relacionadas podrían fallar sin tener una razón válida en errno. Los asignadores de memoria privados también podrían necesitar reemplazar otras funciones de glibc; véase "Reemplazar malloc" en el manual de glibc para más detalles.

Los fallos en los asignadores de memoria casi siempre están relacionados con la corrupción del heap, como el desbordamiento de un fragmento asignado o la liberación del mismo puntero dos veces.

La implementación de malloc() es configurable a través de variables de entorno; véase mallopt(3) para más detalles.

Comportamiento no portable

El comportamiento de estas funciones cuando el tamaño solicitado es cero es específico de glibc; otras implementaciones pueden devolver NULL sin establecer errno, y los programas POSIX portátiles deberían tolerar dicho comportamiento. Véase realloc(3p).

POSIX requiere que los asignadores de memoria establezcan errno ante un fallo. Sin embargo, el estándar C no requiere esto, y las aplicaciones portátiles a plataformas no POSIX no deberían asumir esto.

Los programas portátiles no deben usar asignadores de memoria privados, ya que POSIX y el estándar C no permiten el reemplazo de malloc(), free(), calloc() y realloc().

BUGS

Los programadores esperarían naturalmente por inducción que realloc(p, size) sea consistente con free(p) y malloc(size), ya que ese es el comportamiento en el caso general. Esto no está explícitamente requerido por POSIX.1-2024 o C11, pero todas las implementaciones conformes son consistentes con eso.

La implementación de realloc() en glibc no es consistente con eso y, como consecuencia, es peligroso llamar a realloc(p, 0) en glibc.

Una solución trivial para glibc es llamarla como realloc(p, size?size:1).

La solución para reallocarray() en glibc —que comparte el mismo error— sería reallocarray(p, n?n:1, size?size:1).

EJEMPLOS

#include <err.h>
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define MALLOCARRAY(n, type)  ((type *) my_mallocarray(n, sizeof(type)))
#define MALLOC(type)          MALLOCARRAY(1, type)
static inline void *my_mallocarray(size_t n, size_t size);
int
main(void)
{
    char  *p;
    p = MALLOCARRAY(32, char);
    if (p == NULL)
        err(EXIT_FAILURE, "malloc");
    strlcpy(p, "foo", 32);
    puts(p);
}
static inline void *
my_mallocarray(size_t n, size_t size)
{
    return reallocarray(NULL, n, size);
}
