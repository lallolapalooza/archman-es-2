NOMBRE

re2rust - genera analizadores léxicos rápidos para Rust

SINOPSIS

re2rust [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para stdin.

INTRODUCCIÓN

re2rust funciona como un preprocesador. Lee el archivo de entrada (que generalmente es un programa en Rust, pero puede ser cualquier cosa) y busca bloques de código encerrados en marcadores especiales de inicio/fin. El texto fuera de estos bloques se copia literalmente al archivo de salida. El contenido de los bloques es procesado por re2rust. Lo traduce a código en Rust y genera el código resultante en lugar del bloque.

Aquí hay un ejemplo de un pequeño programa que verifica si una cadena dada contiene un número decimal:

// re2rust $INPUT -o $OUTPUT --no-unsafe --api simple
fn lex(yyinput: &[u8]) -> bool {
    let mut yycursor = 0;
    /*!re2c
        re2c:YYCTYPE = u8;
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    */
}
fn main() {
    assert!(lex(b"1234\0"));
}

En la salida, re2rust reemplazó el bloque intermedio con el código generado:

/* Generado por re2rust */
// re2rust $INPUT -o $OUTPUT --no-unsafe --api simple
fn lex(yyinput: &[u8]) -> bool {
    let mut yycursor = 0;
{
    #[allow(unused_assignments)]
    let mut yych : u8 = 0;
    let mut yystate : usize = 0;
    'yyl: loop {
        match yystate {
            0 => {
                yych = yyinput[yycursor];
                yycursor += 1;
                match yych {
                    0x31 ..= 0x39 => {
                        yystate = 2;
                        continue 'yyl;
                    }
                    _ => {
                        yystate = 1;
                        continue 'yyl;
                    }
                }
            }
            1 => { return false; },
            2 => {
                yych = yyinput[yycursor];
                match yych {
                    0x30 ..= 0x39 => {
                        yycursor += 1;
                        yystate = 2;
                        continue 'yyl;
                    }
                    _ => {
                        yystate = 3;
                        continue 'yyl;
                    }
                }
            }
            3 => { return true; },
            _ => panic!("error interno del analizador"),
        }
    }
}
}
fn main() {
    assert!(lex(b"1234\0"));
}

BÁSICOS

Un programa re2rust consiste en una secuencia de bloques intercalados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresión-regular ;
Una definición une nombre a expresión-regular. Los nombres pueden contener caracteres alfanuméricos y guiones bajos. La sección de expresiones regulares ofrece una visión general de la sintaxis de re2rust para expresiones regulares. Una vez definido, el nombre puede usarse en otras expresiones regulares y en reglas. No se permite la recursión en definiciones nombradas, y cada nombre debe definirse antes de ser usado. Un bloque hereda definiciones nombradas del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite cambiar el comportamiento de re2rust y personalizar el código generado. Para obtener una lista completa de las configuraciones compatibles con re2rust, consulte la sección de configuraciones. Dependiendo de una configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista en caracteres alfanuméricos. Un bloque hereda las configuraciones del ámbito global y puede redefinirlas o añadir nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final del mismo.
expresión-regular código
Una regla une expresión-regular a su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en un salto de línea seguido de cualquier carácter no blanco). Si la expresión-regular coincide, se ejecuta el código asociado. Si coinciden varias reglas, prevalece la coincidencia más larga. Si varias reglas coinciden con la misma cadena, prevalece la primera. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse, tiene la menor prioridad independientemente de su posición en el bloque y coincide con cualquier unidad de código (no necesariamente un carácter válido, ver la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para el manejo del fin de la entrada. Con las condiciones de inicio, las reglas tienen una sintaxis más compleja.
!acción código
Una acción une un bloque de código definido por el usuario a un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas unen código a los estados finales). Ver la sección de acciones para una lista completa de acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias predefinidas especiales. Cada directiva tiene un propósito único. Ver la sección de directivas para más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (se admiten ambos estilos). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que permiten referenciarlos en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2rust compila las expresiones regulares asociadas a cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se añaden al ámbito global y se vuelven visibles para los bloques posteriores. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y las configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera ningún código por sí mismo, ni añade definiciones al ámbito global; está destinado a ser reutilizado en otros bloques. Esta es una forma de compartir código (más detalles en la sección de bloques reutilizables). Antes de la versión 2.2 de re2rust, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2rust busca bloques de reglas con ese nombre. De lo contrario, se usa el bloque de reglas más reciente (ya sea nombrado o sin nombre). Un bloque de uso puede añadir sus propias definiciones, configuraciones y reglas, que se añaden a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2rust, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macro-definición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Se puede personalizar con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ en resumen) se reemplaza con el valor numérico de YYMAXFILL.

Block Types

%%{YYMAXNMATCH[:<name1>[:<name2>...]] ... %}
A block that generates YYMAXNMATCH definition (it requires -P --posix-captures option). An optional list of block names specifies which blocks should be included when computing YYMAXNMATCH value (if the list is empty, all blocks are included). By default the generated code is a macro-definition for C (#define YYMAXNMATCH <n>), or a global variable for Go (var YYMAXNMATCH int = <n>). It can be customized with an optional configuration format that specifies a template string where @@{max} (or @@ for short) is replaced with the numeric value of YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ or %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag variable generated by re2rust. An optional list of block names specifies which blocks should be included when computing the set of tag variables (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag variable. Configuration separator specifies a piece of code used to join the generated format pieces for different tag variables.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ or %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag that is either explicitly mentioned by the rules (with --tags option) or implicitly generated by re2rust (with --captvars or --posix-captvars options). An optional list of block names specifies which blocks should be included when computing the set of tags (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag. Configuration separator specifies a piece of code used to join the generated format pieces for different tags.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ or %{getstate[:<name1>[:<name2>...]] ... %}
A block that generates conditional dispatch on the lexer state (it requires --storable-state option). An optional list of block names specifies which blocks should be included in the state dispatch. The default transition goes to the start label of the first block on the list. If the list is empty, all blocks are included, and the default transition goes to the first block in the file that has a start label. This block type is incompatible with the --loop-switch option, as it requires cross-block transitions that are unsupported without goto or function calls.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ or %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
A block that generates condition enumeration (it requires --conditions option). An optional list of block names specifies which blocks should be included when computing the set of conditions (if the list is empty, all blocks are included). By default the generated code is an enumeration YYCONDTYPE. It can be customized with optional configurations format and separator. Configuration format specifies a template string where @@{cond} (or @@ for short) is replaced with the name of each condition, and @@{num} is replaced with a numeric index of that condition. Configuration separator specifies a piece of code used to join the generated format pieces for different conditions.
/*!include:re2c <file> */ or %{include <file> %}
This block allows one to include <file>, which must be a double-quoted file path. The contents of the file are literally substituted in place of the block, in the same way as #include works in C/C++. This block can be used together with the --depfile option to generate build system dependencies on the included files.
/*!header:re2c:on*/ or %{header:on %}
This block marks the start of header file. Everything after it and up to the following header:off block is processed by re2rust and written to the header file specified with -t --type-header option.
/*!header:re2c:off*/ or %{header:off %}
This block marks the end of header file started with header:on*/ block.
/*!ignore:re2c ... */ or %{ignore ... %}
A block which contents are ignored and removed from the output file.

Configurations

Here is a full list of configurations supported by re2rust:

re2c:api, re2c:input
Same as the --api option.
re2c:api:sigil
Specify the marker ("sigil") that is used for argument placeholders in the API primitives. The default is @@. A placeholder starts with sigil followed by the argument name in curly braces. For example, if sigil is set to $, then placeholders will have the form ${name}. Single-argument APIs may use shorthand notation without the name in braces. This option can be overridden by options for individual API primitives, e.g. re2c:YYFILL@len for YYFILL.
re2c:api:style
Specify API style. Possible values are functions (the default for C) and free-form (the default for Go and Rust). In functions style API primitives are generated with an argument list in parentheses following the name of the primitive. The arguments are provided only for autogenerated parameters (such as the number of characters passed to YYFILL), but not for the general lexer context, so the primitives behave more like macros in C/C++ or closures in Go and Rust. In free-form style API primitives do not have a fixed form: they should be defined as strings containing free-form pieces of code with interpolated variables of the form @@{var} or @@ (they correspond to arguments in function-like style). This configuration may be overridden for individual API primitives, see for example re2c:YYFILL:naked configuration for YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Same as the --bit-vectors option, but can be configured on per-block basis.

If computed goto is used, this configuration specifies the complexity threshold that triggers the generation of jump tables instead of nested if statements and bitmaps. The default value is 9.
re2c:cond:abort
If set to a positive integer value, the default case in the generated condition dispatch aborts program execution.
re2c:cond:goto
Specifies a piece of code used for the autogenerated shortcut rules :=> in conditions. The default is goto @@;. The @@ placeholder is substituted with condition name (see configurations re2c:api:sigil and re2c:cond:goto@cond).
re2c:cond:goto@cond
Specifies the sigil used for argument substitution in re2c:cond:goto definition. The default value is @@. Overrides the more generic re2c:api:sigil configuration.
re2c:cond:divider
Defines the divider for condition blocks. The default value is /* *********************************** */. Placeholders are substituted with condition name (see re2c:api;sigil and re2c:cond:divider@cond).
re2c:cond:divider@cond
Specifies the sigil used for argument substitution in re2c:cond:divider definition. The default is @@. Overrides the more generic re2c:api:sigil configuration.
re2c:cond:prefix, re2c:condprefix
Especifica el prefijo utilizado para las etiquetas de condición. El valor predeterminado es yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Especifica el prefijo utilizado para los identificadores de condición. El valor predeterminado es yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d

re2c:label:start, re2c:startlabel

Esta configuración solo se aplica al bloque actual (se restablece al valor predeterminado para el siguiente bloque).

Especifica el prefijo de las etiquetas YYFILL utilizadas con re2c:eof y en el modo de estado almacenable.

Especifica el nombre de la etiqueta que marca el inicio del bucle del lexer con la opción --loop-switch. El valor predeterminado es yyloop.

Especifica el nombre de la etiqueta opcional que sigue al cambio YYGETSTATE en el modo de estado almacenable (habilitado con re2c:state:nextlabel). El valor predeterminado es yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsoleto (ver la opción obsoleta --no-lookahead).
re2c:monadic
Si se establece en un valor distinto de cero, el lexer generado utilizará notación monádica (esta configuración es específica de Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Igual que la opción --nested-ifs, pero se puede configurar por bloque.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P

re2c:posix-captvars

re2c:tags, re2c:flags:tags, re2c:flags:T
Igual que la opción --tags, pero se puede configurar por bloque.
re2c:tags:expression
Especifica la expresión utilizada para las variables de etiqueta. Por defecto, re2rust genera expresiones de la forma yyt<N>. Esto puede ser inconveniente, por ejemplo, si las variables de etiqueta se definen como campos en una estructura. Todas las ocurrencias de @@{tag} o @@ se reemplazan con el nombre real de la etiqueta. Por ejemplo, re2c:tags:expression = "s.@@"; resulta en expresiones de la forma s.yyt<N> en el código generado. Ver también la configuración re2c:api:sigil.
re2c:tags:negative
Especifica la expresión constante que se utiliza para el valor de etiqueta negativo (típicamente sería -1 si las etiquetas son desfases enteros en la cadena de entrada, o un puntero nulo si son punteros).
re2c:tags:prefix
Especifica el prefijo para los nombres de las variables de etiqueta. El valor predeterminado es yyt.
re2c:sentinel
Especifica el símbolo centinela utilizado para las comprobaciones de fin de entrada (cuando las comprobaciones de límites están deshabilitadas con re2c:yyfill:enable = 0; y no se establece re2c:eof). Esta configuración no afecta la generación de código: su propósito es verificar que el centinela no está permitido en medio de una regla y asegurar que el lexer no lea más allá del final del búfer. El valor predeterminado es -1` (en ese caso, re2rust asume que el centinela es cero, que es el caso más común). Solo se reconocen números decimales.

Expresiones regulares

re2rust utiliza la siguiente sintaxis para las expresiones regulares:

"foo"
Literal de cadena sensible a mayúsculas y minúsculas.
'foo'
Literal de cadena insensible a mayúsculas y minúsculas.
[a-xyz], [^a-xyz]
Clase de caracteres (posiblemente negada).
.
Cualquier carácter excepto nueva línea.
R \ S
Diferencia de clases de caracteres R y S.
R*
Cero o más ocurrencias de R.
R+
Una o más ocurrencias de R.
R?
Ocurrencia opcional de R.
R{n}
Repetición de R exactamente n veces.
R{n,}
Repetición de R al menos n veces.
R{n,m}
Repetición de R entre n y m veces.
(R)
Simplemente R; los paréntesis se usan para anular la precedencia. Si la extracción de subcoincidencias está habilitada, (R) es un grupo de captura o no de captura dependiendo de la opción --invert-captures.
(!R)
Si la extracción de subcoincidencias está habilitada, (!R) es un grupo de no captura o de captura dependiendo de la opción --invert-captures.
R S
Concatenación: R seguido de S.
R | S
Alternativa: R o S.
R / S
Lookahead: R seguido de S, pero S no se consume.
name
Expresión regular definida como name (o cadena literal "name" en modo de compatibilidad con Flex).
{name}
Expresión regular definida como name en modo de compatibilidad con Flex.
@stag
Una s-tag: guarda la última posición de entrada en la que @stag coincide en una variable llamada stag.
#mtag
Una m-tag: guarda todas las posiciones de entrada en las que #mtag coincide en una variable llamada mtag.

Las clases de caracteres y los literales de cadena pueden contener las siguientes secuencias de escape: \a, \b, \f, \n, \r, \t, \v, \\, escapes octales \ooo y escapes hexadecimales \xhh, \uhhhh y \Uhhhhhhhh.

Acciones

Aquí hay una lista de acciones predefinidas admitidas por re2rust:

!entry code
La acción de entrada vincula un bloque de code definido por el usuario al estado de inicio de la máquina de estados finitos actual. Si se utilizan condiciones de inicio, la acción de entrada se puede establecer individualmente para cada condición. Esta acción se puede utilizar para realizar inicializaciones, por ejemplo, para guardar la ubicación de inicio de un lexema.
!pre_rule code
La acción pre-regla antepone un bloque de code definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para factorizar la parte común de todas las acciones semánticas (por ejemplo, guardar la ubicación final de un lexema).
!post_rule code
La acción post-regla añade un bloque de code definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para emitir sentencias de trampa que protejan contra flujos de control no deseados.

Directivas

Aquí hay una lista completa de directivas admitidas por re2rust:

!use:name ;
Una directiva de uso dentro de un bloque que fusiona un bloque de reglas definido previamente con el name especificado en el bloque actual. Las definiciones nombradas, configuraciones y reglas del bloque referenciado se agregan a las actuales. Los conflictos entre reglas y configuraciones superpuestas se resuelven de la manera habitual: la primera regla tiene prioridad y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y <!> para las cuales una definición local del bloque siempre tiene prioridad. Una directiva de uso se puede colocar en cualquier lugar dentro de un bloque y se permiten múltiples directivas de uso.
!include file ;
Esta directiva es igual que el bloque include: inserta el contenido de file verbatim en lugar de la directiva.

Interfaz del programa

El código generado interactúa con el programa exterior con la ayuda de primitivas, denominadas colectivamente la API. Qué primitivas deben definirse para un programa particular depende de múltiples factores, incluida la complejidad de las expresiones regulares, la representación de entrada, el almacenamiento en búfer y el uso de varias características. Todas las primitivas necesarias deben ser definidas por el usuario en forma de macros, funciones, variables o cualquier otra forma adecuada que haga que el código generado sea sintáctica y semánticamente correcto. re2rust no (y no puede) verificar las definiciones, por lo que si falta algo o está definido incorrectamente, el programa generado puede tener errores de compilación o tiempo de ejecución. Este manual proporciona ejemplos de definiciones de API en los casos más comunes.

re2rust tiene tres sabores de API que definen el conjunto central de primitivas utilizadas por un programa:

API Simple
(añadido en la versión 4.0) Esta es una API básica que se puede habilitar con la opción --api simple o la configuración re2c:api = simple. Consiste en las siguientes primitivas: YYINPUT (que debe definirse como una secuencia de unidades de código, por ejemplo, una cadena) y YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (que deben definirse como índices en YYINPUT).
API de Registro
(añadido en la versión 4.0) La API de registro es útil en casos donde el estado del analizador léxico debe almacenarse en una estructura. Se habilita con la opción --api record o la configuración re2c:api = record. Esta API consiste en una variable yyrecord (el nombre se puede anular con re2c:yyrecord) que debe definirse como una estructura con los campos yyinput, yycursor, yymarker, yyctxmarker, yylimit (solo los campos utilizados por el código generado deben definirse y sus nombres se pueden configurar).
API Genérica
Esta es la API más flexible y la API predeterminada para el backend de Rust. Esta API contiene primitivas para operaciones genéricas: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN. Por ejemplo, si la entrada es un slice de bytes buffer: &[u8], las variables cursor, limit, marker y ctxmarker de tipo usize representan posiciones de entrada, y una constante NONE representa una posición inválida, entonces la API genérica se puede definir como:

  re2c:YYBACKUPCTX  = "ctxmarker = cursor;";
  re2c:YYRESTORECTX = "cursor = ctxmarker;";

  re2c:YYLESSTHAN   = "limit - cursor < @@{len}";
  re2c:YYSTAGP      = "@@{tag} = cursor;";
  re2c:YYSTAGN      = "@@{tag} = NONE;";

Especifica la API utilizada por el código generado para interactuar con código definido por el usuario. La opción simple debe usarse en casos sencillos cuando no hay necesidad de recargar el búfer y almacenar el estado del lexer. La opción record debe usarse cuando el estado del lexer necesita almacenarse en un registro (struct, clase, etc.). La opción generic debe usarse en casos complejos cuando las otras dos APIs no son lo suficientemente flexibles.
--bit-vectors -b
Optimiza los saltos condicionales utilizando máscaras de bits. Esta opción implica --nested-ifs.
--captures, --leftmost-captures
Habilita la extracción de subcoincidencias con grupos de captura ávidos más a la izquierda. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla de coincidencia.
--captvars, --leftmost-captvars
Habilita la extracción de subcoincidencias con grupos de captura ávidos más a la izquierda. El resultado se recopila en las variables yytl<k>, yytr<k> para el grupo de captura k-ésimo.
--case-insensitive
Trata las cadenas entre comillas simples y dobles como si no distinguieran entre mayúsculas y minúsculas.
--case-inverted
Invierte el significado de las cadenas entre comillas simples y dobles: trata las cadenas entre comillas simples como sensibles a mayúsculas y minúsculas y las cadenas entre comillas dobles como insensibles a mayúsculas y minúsculas.
--case-ranges
Colapsa casos consecutivos en sentencias switch en un rango de la forma bajo ... alto. Esta sintaxis es una extensión del lenguaje C/C++ que es compatible con compiladores como GCC, Clang y Tcc. La principal ventaja sobre el uso de casos individuales es un código generado más pequeño y un tiempo de generación más rápido, aunque para algunos compiladores como Tcc también resulta en un tamaño binario más pequeño.
--computed-gotos -g
Optimiza los saltos condicionales utilizando la extensión no estándar "computed goto" (que debe ser compatible con el compilador). re2rust genera tablas de saltos solo en casos complejos con muchas ramas condicionales. El umbral de complejidad se puede configurar con la configuración cgoto:threshold. Los desplazamientos relativos se pueden habilitar con la configuración cgoto:relative. Esta opción implica --bit-vectors.
--computed-gotos-relative
Similar a --computed-gotos pero genera desplazamientos relativos para las tablas de saltos en su lugar (que deben ser compatibles con el compilador). Esta opción implica --computed-gotos.
--conditions --start-conditions -c
Habilita el soporte de "condiciones" tipo Flex: múltiples lexers interrelacionados dentro de un solo bloque. Esta es una alternativa a especificar manualmente diferentes bloques de re2rust conectados con goto o llamadas a funciones.
--depfile FILE
Escribe la información de dependencia en FILE en forma de una regla de Makefile <archivo-salida> : <archivo-entrada> [archivo-incluido ...]. Esto permite rastrear las dependencias de compilación en presencia de bloques/directivas include, de modo que la actualización de los archivos incluidos active la regeneración del archivo de salida. Esta opción depende de la opción --output.
--ebcdic --ecb -e
Genera un lexer que lee entrada en codificación EBCDIC. re2rust asume que el rango de caracteres es 0 -- 0xFF y el tamaño del carácter es de 1 byte.
--empty-class <match-empty | match-none | error>
Define la forma en que re2rust trata las clases de caracteres vacías. Con match-empty (el valor predeterminado), la clase vacía coincide con entrada vacía (lo cual es ilógico, pero compatible con versiones anteriores). Con match-none, la clase vacía siempre falla al coincidir. Con error, la clase vacía genera un error de compilación.
--encoding-policy <fail | substitute | ignore>
Define la forma en que re2rust trata los sustitutos Unicode. Con fail, re2rust se interrumpe con un error al encontrar un sustituto. Con substitute, re2rust reemplaza silenciosamente los sustitutos con el punto de código de error 0xFFFD. Con ignore (el valor predeterminado), re2rust trata los sustitutos como puntos de código normales. El estándar Unicode dice que los sustitutos independientes no son válidos, pero las bibliotecas y programas del mundo real se comportan de diferentes maneras.
--flex-syntax -F
Soporte parcial para la sintaxis de Flex: en este modo, las definiciones con nombre no necesitan el signo igual ni el punto y coma final, y cuando se usan deben estar rodeadas de llaves. Los nombres sin llaves se tratan como cadenas entre comillas dobles.
--goto-label
Utiliza el modelo de código "goto/label": codifica el DFA en forma de bloques de código etiquetados conectados con transiciones goto entre bloques. Esto solo es compatible con lenguajes que tienen una sentencia goto.
--header --type-header -t HEADER
Genera un archivo HEADER. El contenido del archivo se puede especificar usando bloques especiales header:on y header:off. Si se usan condiciones, el encabezado generado tendrá un enum de condición agregado automáticamente (a menos que haya un bloque conditions explícito).
-I PATH
Agrega PATH a la lista de ubicaciones que se utilizan al buscar archivos de inclusión. Esta opción es útil en combinación con el bloque o directiva include. re2rust busca FILE en el directorio del archivo padre y en las ubicaciones de inclusión especificadas con la opción -I.
--input <default | custom>
Alias obsoleto para --api. La opción default corresponde a simple (es de hecho el predeterminado para la mayoría de los backends, pero no para todos). La opción custom corresponde a generic.
--input-encoding <ascii | utf8>
Especifica la forma en que re2rust analiza las expresiones regulares. Con ascii (el valor predeterminado), re2rust maneja la entrada como codificada en ASCII: cualquier secuencia de unidades de código es una secuencia de caracteres independientes de 1 byte. Con utf8, re2rust maneja la entrada como codificada en UTF8 y reconoce caracteres multibyte.
--invert-captures
Invierte el significado de los grupos de captura y no captura. Por defecto, (...) es de captura y (! ...) no es de captura. Con esta opción, (! ...) es de captura y (...) no es de captura.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Especifica el lenguaje de destino. Los lenguajes admitidos son C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (se pueden agregar más lenguajes a través de archivos de sintaxis definidos por el usuario, consulte la opción --syntax). La opción none deshabilita las configuraciones de sintaxis predeterminadas, de modo que el lenguaje de destino no esté definido.
--location-format <gnu | msvc>
Especifica el formato de ubicación en los mensajes. Con gnu, las ubicaciones se imprimen como 'nombre-archivo:línea:columna: ...'. Con msvc, las ubicaciones se imprimen como 'nombre-archivo(línea,columna) ...'. El valor predeterminado es gnu.
--loop-switch
Utiliza el modelo de código "loop/switch": codifica el DFA en forma de un bucle sobre una sentencia switch, donde los estados individuales son casos del switch. El estado se almacena en una variable yystate. Las transiciones entre estados actualizan yystate a la etiqueta del caso del estado de destino y continúan la ejecución hasta el inicio del bucle.
--nested-ifs -s
Utiliza sentencias if anidadas en lugar de sentencias switch en los saltos condicionales. Esto generalmente resulta en un código más eficiente con compiladores no optimizadores.
--no-debug-info -i
No genera directivas de línea. Esto puede ser útil cuando el código generado se almacena en un sistema de control de versiones (para evitar enormes diferencias generadas automáticamente en pequeños cambios).
--no-generation-date
Suprime la salida de la fecha en el archivo generado.
--no-version
Suprime la salida de la versión en el archivo generado.
--no-unsafe
No genera un wrapper unsafe sobre YYPEEK (esta opción es específica de Rust). Por razones de rendimiento, YYPEEK debe evitar la verificación de límites, ya que el lexer ya realiza comprobaciones de fin de entrada de manera más eficiente. El usuario puede optar por proporcionar una definición YYPEEK segura, o una definición que solo sea insegura en compilaciones de lanzamiento, en cuyo caso la opción --no-unsafe ayuda a evitar advertencias sobre bloques unsafe redundantes.
--output -o OUTPUT
Especifica el archivo OUTPUT.
--posix-captures, -P
Habilita la extracción de subcoincidencias con grupos de captura al estilo POSIX. El resultado se recopila en un array yybmatch de capacidad 2 * YYMAXNMATCH, y yynmatch se establece al número de grupos para la regla de coincidencia.
--posix-captvars
Habilita la extracción de subcoincidencias con grupos de captura al estilo POSIX. El resultado se recopila en variables yytl<k>, yytr<k> para el k-ésimo grupo de captura.
--recursive-functions
Utiliza un modelo de código basado en funciones co-recursivas, donde cada estado de DFA es una función separada que puede llamar a otras funciones de estado o a sí misma.
--reusable -r
Obsoleto desde la versión 2.2 (los bloques reutilizables están permitidos por defecto ahora).
--skeleton -S
Ignora el código de interfaz definido por el usuario y genera un programa "esqueleto" autocontenido. Adicionalmente, genera archivos de entrada con cadenas derivadas de la gramática regular y resultados de coincidencia comprimidos que se utilizan para verificar el comportamiento del "esqueleto" en todas las entradas. Esta opción es útil para encontrar errores en las optimizaciones y la generación de código. Esta opción solo es compatible con C.
--storable-state -f
Genera un lexer que puede almacenar su estado interno. Esto es útil en lexers de modelo push que son detenidos por un programa externo cuando no hay suficiente entrada, y luego reanudados cuando hay más entrada disponible. En este modo, los usuarios deben definir adicionalmente las primitivas YYGETSTATE y YYSETSTATE, y las variables yych, yyaccept y state deben formar parte del estado del lexer almacenado.
--syntax FILE
Carga configuraciones del archivo FILE especificado y las aplica encima del archivo de sintaxis predeterminado. Ten en cuenta que FILE puede definir solo unas pocas configuraciones (si se utiliza para modificar el archivo de sintaxis predeterminado), o puede definir un backend de lenguaje completamente nuevo (en cuyo caso se recomienda usar la opción --lang none).
--tags -T
Habilita la extracción de subcoincidencias con etiquetas.
--ucs2 --wide-chars -w
Genera un lexer que lee entrada codificada en UCS2. re2rust asume que el rango de caracteres es 0 -- 0xFFFF y el tamaño del carácter es de 2 bytes. Esta opción implica --nested-ifs.
--utf8 --utf-8 -8
Genera un lexer que lee entrada en codificación UTF-8. re2rust asume que el rango de caracteres es 0 -- 0x10FFFF y el tamaño del carácter es de 1 byte.
--utf16 --utf-16 -x
Genera un lexer que lee entrada codificada en UTF16. re2rust asume que el rango de caracteres es 0 -- 0x10FFFF y el tamaño del carácter es de 2 bytes. Esta opción implica --nested-ifs.
--utf32 --unicode -u
Genera un lexer que lee entrada codificada en UTF32. re2rust asume que el rango de caracteres es 0 -- 0x10FFFF y el tamaño del carácter es de 4 bytes. Esta opción implica --nested-ifs.
--verbose
Muestra un mensaje corto en caso de éxito.
--vernum -V
Muestra información de la versión en formato MMmmpp (mayor, menor, parche).
--version -v
Muestra información de la versión.
--single-pass -1
Obsoleto. No hace nada (el pase único es el predeterminado ahora).
--debug-output -d
Emite invocaciones de YYDEBUG en el código generado. Esto es útil para rastrear la ejecución del lexer.
--dump-adfa
Opción de depuración: muestra el DFA después de la canalización (en formato .dot).
--dump-cfg
Opción de depuración: muestra el grafo de flujo de control de las variables de etiqueta (en formato .dot).
--dump-closure-stats
Opción de depuración: muestra estadísticas sobre el número de estados en el cierre.
--dump-dfa-det
Opción de depuración: muestra el DFA inmediatamente después de la determinización (en formato .dot).
--dump-dfa-min
Opción de depuración: muestra el DFA después de la minimización (en formato .dot).
--dump-dfa-tagopt
Opción de depuración: muestra el DFA después de las optimizaciones de etiquetas (en formato .dot).
--dump-dfa-tree
Opción de depuración: muestra el DFA en construcción con estados representados como árboles de historial de etiquetas (en formato .dot).
--dump-dfa-raw
Opción de depuración: muestra el DFA en construcción con conjuntos de estados expandidos (en formato .dot).
--dump-interf
Opción de depuración: muestra la tabla de interferencia producida por el análisis de vivacidad de variables de etiqueta.
--dump-nfa
Opción de depuración: muestra el NFA (en formato .dot).

En lugar de la salida normal, genera el grafo del lexer en formato .dot. La salida puede convertirse en una imagen con la ayuda de Graphviz (por ejemplo, algo como dot -Tpng -odfa.png dfa.dot).
--dfa-minimization <moore | table>
Opción interna: algoritmo de minimización de DFA utilizado por re2rust. La opción moore es el algoritmo de Moore (es el predeterminado). La opción table es el algoritmo de "relleno de tabla". Ambos algoritmos deberían producir el mismo DFA hasta el reetiquetado de estados; el relleno de tabla es más simple y mucho más lento, y sirve como implementación de referencia.
--eager-skip
Opción interna: hace que el lexer generado avance la posición de entrada agresivamente, inmediatamente después de leer el símbolo de entrada. Esto cambia el comportamiento predeterminado en el que la posición de entrada se avanza perezosamente, después de la transición al siguiente estado.
--no-lookahead
Opción interna, obsoleta. Solía habilitar el algoritmo TDFA(0). A diferencia de TDFA(1), el algoritmo TDFA(0) no utiliza la búsqueda anticipada de un símbolo. Aplica operaciones de registro a las transiciones entrantes en lugar de a las salientes. Las pruebas comparativas mostraron que el algoritmo TDFA(0) es menos eficiente que TDFA(1).
--no-optimize-tags
Opción interna: suprime la optimización de variables de etiqueta (útil para depuración).
--posix-closure <gor1 | gtop>
Opción interna: especifica el algoritmo de camino más corto utilizado para la construcción del cierre epsilon con semántica de desambiguación POSIX: gor1 (el predeterminado) significa el algoritmo de Goldberg-Radzik, y gtop significa el algoritmo de "orden topológico global".
--posix-prectable <complex | naive>
Opción interna: especifica el algoritmo utilizado para calcular la tabla de precedencia POSIX. El algoritmo complex calcula la tabla de precedencia en una sola travesía del árbol de historial de etiquetas y tiene complejidad cuadrática en el número de estados TNFA; es el predeterminado. El algoritmo naive tiene complejidad cúbica en el peor de los casos en el número de estados TNFA, pero es mucho más simple que complex y puede ser ligeramente más rápido en casos no patológicos.
--stadfa
Opción interna, obsoleta. Solía habilitar el algoritmo staDFA, que difiere de TDFA en que las operaciones de registro se colocan en los estados en lugar de en las transiciones. Las pruebas comparativas mostraron que el algoritmo staDFA es menos eficiente que TDFA.
--fixed-tags <none | toplevel | all>
Opción interna: especifica si la optimización de etiquetas fijas debe aplicarse a todas las etiquetas (all), ninguna de ellas (none), o solo a las de concatenación de nivel superior (toplevel). El valor predeterminado es all. Las etiquetas "fijas" son aquellas que se encuentran a una distancia fija de otra etiqueta (llamada "base"). En tales casos, solo la etiqueta base necesita ser rastreada, y el valor de la etiqueta fija puede calcularse como el valor de la etiqueta base más un desplazamiento estático. Para etiquetas que están bajo alternativas o repeticiones, también es necesario verificar si la etiqueta base tiene un valor de no coincidencia (en ese caso, la etiqueta fija también debe establecerse en no coincidencia, ignorando el desplazamiento). Para etiquetas en concatenación de nivel superior, la verificación no es necesaria, ya que siempre coinciden.

Advertencias

Las advertencias se pueden habilitar, deshabilitar e incluso convertir en errores de forma individual.

-W
Habilita todas las advertencias.
-Werror
Convierte las advertencias en errores. Ten en cuenta que esta opción por sí sola no habilita ninguna advertencia; solo afecta a aquellas advertencias que se han habilitado hasta ahora o que se habilitarán más adelante.
-W<advertencia>
Habilita la advertencia.
-Wno-<advertencia>
Deshabilita la advertencia.
-Werror-<advertencia>
Habilita la advertencia y la trata como un error (esto implica -W<advertencia>).
-Wno-error-<advertencia>
No trata esta advertencia en particular como un error. Esto no deshabilita la advertencia en sí misma.
-Wcondition-order
Advierte si el programa generado hace suposiciones implícitas sobre la numeración de condiciones. Se debe usar la opción --header o el bloque conditions para generar un mapeo de nombres de condiciones a números y luego usar los nombres de condiciones autogenerados.
-Wempty-character-class
Advierte si una expresión regular contiene una clase de caracteres vacía. Intentar hacer coincidir una clase de caracteres vacía no tiene sentido: siempre debería fallar. Sin embargo, por razones de compatibilidad con versiones anteriores, re2rust permite clases de caracteres vacías y las trata como cadenas vacías. Use la opción --empty-class para cambiar el comportamiento predeterminado.
-Wmatch-empty-string
Advierte si una regla es nula (coincide con una cadena vacía). Si el analizador léxico se ejecuta en un bucle y la coincidencia vacía es no intencional, el analizador léxico puede colgarse inesperadamente en un bucle infinito.
-Wswapped-range
Advierte si el límite inferior de un rango es mayor que su límite superior. El comportamiento predeterminado es intercambiar silenciosamente los límites del rango.
-Wundefined-control-flow
Advierte si algunas cadenas de entrada causan un flujo de control no definido en el analizador léxico (se informan los patrones defectuosos). Este es un error peligroso y común. Se puede corregir fácilmente agregando la regla predeterminada * que tiene la menor prioridad, coincide con cualquier unidad de código y siempre consume una sola unidad de código.
-Wunreachable-rules
Advierte sobre reglas que están ocultas por otras reglas y que nunca coincidirán.
-Wdeprecated-eof_rule
Advierte sobre reglas de fin de entrada independientes $ que se romperán con cambios futuros y requerirán corrección. Por el momento, estas reglas tienen precedencia cuando entran en conflicto con otras reglas, pero después de la introducción del símbolo generalizado de fin de entrada $, el orden de precedencia cambiará y estas reglas serán ocultadas por otras reglas.
-Wuseless-escape
Advierte si un símbolo se escapa cuando no debería. Por defecto, re2rust ignora silenciosamente tales escapes, pero esto también puede indicar un error tipográfico o un error en la secuencia de escape.
-Wnondeterministic-tags
Advierte si una etiqueta tiene un grado de indeterminación de n, donde n es mayor que 1.
-Wsentinel-in-midrule
Advierte si el símbolo centinela ocurre en medio de una regla; esto puede causar lecturas más allá del final del búfer, bloqueos o corrupción de memoria en el analizador léxico generado. Esta advertencia solo es aplicable si se utiliza el método centinela para verificar el final de la entrada. Se establece como error si se utiliza la configuración re2c:sentinel.
-Wundefined-syntax-config
Advierte si el archivo de sintaxis especificado con la opción --syntax carece de definiciones para algunas configuraciones. Esto ayuda a mantener los archivos de sintaxis definidos por el usuario: si una nueva versión agrega configuraciones, el archivo de sintaxis antiguo generará una advertencia y se notificará al usuario. Si algunas configuraciones no se utilizan y no necesitan una definición, deben establecerse explícitamente en <undefined>.

Archivos de sintaxis

El soporte para diferentes lenguajes en re2c se basa en la idea de archivos de sintaxis. Un archivo de sintaxis es un archivo de configuración que define la sintaxis del lenguaje de destino, no el lenguaje completo, sino una pequeña parte del mismo que es utilizada por el código generado. Los archivos de sintaxis hacen que re2c sea muy flexible, pero no deben usarse como un reemplazo para las configuraciones de re2c: su propósito es definir la sintaxis del lenguaje de destino, no personalizar un analizador léxico en particular. Todos los lenguajes soportados tienen archivos de sintaxis predeterminados que forman parte de la distribución (ver el subdirectorio include/syntax); también están incrustados en el binario re2rust. Los usuarios pueden proporcionar un archivo de sintaxis personalizado que anule algunas configuraciones para uno de los lenguajes soportados, o pueden optar por redefinir todas las configuraciones (en ese caso, se debe usar la opción --lang none). Los archivos de sintaxis contienen configuraciones de cuatro tipos diferentes: listas de características, configuraciones de lenguaje, configuraciones in situ y plantillas de código.

Listas de características

Unas pocas configuraciones de lista definen varias características soportadas por un backend dado, de modo que re2rust pueda dar un error claro si el usuario intenta habilitar una característica no soportada:
supported_apis
Una lista de APIs soportadas con elementos posibles simple, record, generic.
supported_api_styles
Una lista de estilos de API soportados con elementos posibles functions, free-form.
supported_code_models
Una lista de modelos de código soportados con elementos posibles goto-label, loop-switch, recursive-functions.
supported_targets
Una lista de objetivos de generación de código soportados con elementos posibles code, dot, skeleton.
supported_features
Una lista de características soportadas con elementos posibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Configuraciones de lenguaje

Unas pocas configuraciones booleanas describen características del lenguaje de destino que afectan al analizador y al generador de código de re2rust:
semicolons
Distinto de cero si el lenguaje utiliza punto y coma después de las sentencias.
backtick_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas invertidas.
single_quoted_strings
Distinto de cero si el lenguaje tiene cadenas entre comillas simples.
indentation_sensitive
Distinto de cero si el lenguaje es sensible a la indentación.
wrap_blocks_in_braces
Distinto de cero si los bloques de sentencias compuestos deben encerrarse entre llaves.

Configuraciones in situ

Los archivos de sintaxis definen los valores iniciales de todas las configuraciones de re2c:, ya que pueden diferir para diferentes lenguajes. Consulte la sección de configuraciones para obtener una lista completa de todas las configuraciones in situ y su significado.

Plantillas de código

Las plantillas de código definen la sintaxis del lenguaje de destino. Están escritas en un lenguaje simple específico del dominio con la siguiente gramática formal: 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Una plantilla de código es una secuencia de literales de cadena, variables, elementos opcionales y listas, o una referencia a otra plantilla de código, o un valor especial <undefined>. Las variables son marcadores de posición que se sustituyen durante la fase de generación de código. Las variables de lista son especiales: al expandir plantillas de lista, re2rust repite las expresiones del lado derecho de la columna varias veces, reemplazando en cada ocasión las ocurrencias de la variable de lista con un valor específico para esa repetición. Las listas tienen límites opcionales (los valores negativos se cuentan desde el final, por ejemplo, -1 significa el último elemento). Los nombres de las condicionales comienzan con un punto. Tanto las condicionales como las variables pueden ser locales (específicas de la plantilla de código dada) o globales (permitidas en todas las plantillas de código). Cuando re2rust lee el archivo de sintaxis, verifica que cada plantilla de código utilice solo las variables y condicionales que están permitidos en ella.

Por ejemplo, la siguiente plantilla de código define la construcción if-then-else para un lenguaje similar a C:

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

MANEJO DEL FIN DE LA ENTRADA

Uno de los principales problemas para el lexer es saber cuándo detenerse. Hay algunas condiciones de terminación:

  • el lexer puede coincidir con alguna regla (incluida la regla por defecto *) y llegar a un estado final
  • el lexer puede no coincidir con ninguna regla y llegar a un estado por defecto
  • el lexer puede alcanzar el final de la entrada

Las dos primeras condiciones terminan el lexer de forma "natural": llega a un estado sin transiciones salientes, y la coincidencia se detiene automáticamente. La tercera condición, el fin de la entrada, es diferente: puede ocurrir en cualquier estado, y el lexer debe poder manejarlo. La comprobación del fin de la entrada interrumpe el flujo normal del lexer y añade ramas condicionales al programa generado, por lo tanto, es necesario minimizar el número de tales comprobaciones. re2rust admite algunos métodos diferentes para manejar el fin de la entrada. Cuál usar depende de la complejidad de las expresiones regulares, la necesidad de almacenamiento en búfer, las consideraciones de rendimiento y otros factores. Aquí hay una lista de métodos:

  • Centinela. Este método elimina la necesidad de comprobaciones de fin de entrada por completo. Es simple y eficiente, pero se limita al caso en que hay un carácter "centinela" natural que nunca puede ocurrir en la entrada válida. Este carácter aún puede ocurrir en entradas no válidas, pero no debe ser permitido por las expresiones regulares, excepto quizás como el último carácter de una regla. El centinela se añade al final de la entrada y sirve como señal de parada: cuando el lexer lee este carácter, es un error de sintaxis o el fin de la entrada. En ambos casos, el lexer debe detenerse. Este método se utiliza si YYFILL está deshabilitado con re2c:yyfill:enable = 0; y re2c:eof tiene el valor por defecto -1.
  • Centinela con comprobaciones de límites. Este método es genérico: permite manejar cualquier entrada sin restricciones en las expresiones regulares. La idea es reducir el número de comprobaciones de fin de entrada realizándolas solo en ciertos caracteres. De manera similar al método "centinela", se elige uno de los caracteres como "centinela" y se añade al final de la entrada. Sin embargo, no hay restricciones sobre dónde puede ocurrir el centinela (de hecho, cualquier carácter puede ser elegido como centinela). Cuando el lexer lee este carácter, realiza adicionalmente una comprobación de límites. Si la posición actual está dentro de los límites, el lexer reanuda la coincidencia y maneja el centinela como un carácter regular. De lo contrario, invoca a YYFILL (a menos que esté deshabilitado). Si se suministra más entrada, el lexer volverá a coincidir con el último carácter y continuará como si el centinela no estuviera allí. De lo contrario, debe ser el final real de la entrada, y el lexer se detiene. Este método se utiliza cuando re2c:eof tiene un valor no negativo (debe configurarse en el valor numérico del centinela). YYFILL es opcional.
  • Comprobaciones de límites con relleno. Este método es genérico y puede ser más rápido que el método "centinela con comprobaciones de límites", pero también es más complejo. La idea es particionar los estados del DFA en componentes fuertemente conectados (SCC) y generar una sola comprobación por SCC para suficientes caracteres para cubrir el camino más largo sin bucle en esta SCC. Esto reduce el número de comprobaciones, pero hay un problema con lexemas cortos al final de la entrada, ya que la comprobación requiere suficientes caracteres para cubrir el lexema más largo. Esto se puede solucionar rellenando la entrada con algunos caracteres ficticios que no forman un sufijo de lexema válido (para que el lexer no pueda coincidir con ellos). La longitud del relleno debe ser YYMAXFILL, generado con un bloque max. Si no hay suficiente entrada, el lexer invoca a YYFILL, que debe suministrar al menos el número de caracteres requerido o no devolver nada. Este método se utiliza si YYFILL está habilitado y re2c:eof es -1 (esta es la configuración por defecto).
  • Comprobaciones personalizadas. La API genérica permite anular operaciones básicas como la lectura de un carácter, lo que hace posible incluir las comprobaciones de fin de entrada como parte de ellas. Este enfoque es propenso a errores y debe usarse con precaución. Para usar un método personalizado, habilite la API genérica con --api custom o re2c:api = custom; y deshabilite las comprobaciones de límites por defecto con re2c:yyfill:enable = 0; o re2c:yyfill:check = 0;.

END OF FILE HANDLING

When the lexer reaches the end of the input, it should terminate. re2c provides several mechanisms for detecting the end of the input and acting upon it. The primary mechanism is the EOF rule, which is explicitly defined by the user. This rule is typically used with a sentinel character (like a null character) appended to the input. The EOF rule will match this sentinel character, signaling the end of the input stream.

Alternatively, re2c can be configured to perform bounds checks automatically. When the lexer is about to read past the end of the input buffer, it triggers a bounds check. If the check fails, it indicates the end of input. This mechanism can be combined with padding, where a fixed number of characters are appended to the input buffer to simplify handling of boundary conditions. The lexer can also be made to perform custom checks, allowing for more fine-grained control over end-of-input detection.

The choice of EOF handling method influences how the lexer behaves when it encounters the end of the input. The lexer might attempt to fallback to a previously matched rule, enter a default state, or trigger an undefined control flow warning if not handled properly. The following sections detail various approaches to EOF handling in re2c.

EOF rule

The EOF rule is a special rule that matches the end of input. It is configured using the re2c:eof directive. When the lexer reaches the end of input and the EOF rule is defined, it will be matched. This is typically used with a sentinel character (e.g., null terminator) appended to the input. The example below demonstrates the use of the EOF rule with a null-terminated string. YYFILL is disabled because the input fits within a single buffer. Reaching the end of input can lead to three scenarios: if the lexer is in the initial state, it matches the EOF rule $. Otherwise, it might fallback to a previously matched rule (including the default rule *) or transition to a default state, potentially causing an -Wundefined-control-flow warning.

// re2rust $INPUT -o $OUTPUT --api simple
fn lex(yyinput: &[u8]) -> isize {
    // The input must be null-terminated, otherwise the function has UB.
    assert_eq!(yyinput.last(), Some(&0));
    let (mut yycursor, mut yymarker) = (0, 0);
    let yylimit = yyinput.len() - 1; // null-terminator not included
    let mut count = 0;
    'lex: loop { /*!re2c
        re2c:YYCTYPE = u8;
        re2c:yyfill:enable = 0;
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1; }
        $    { return count; }
        str  { count += 1; continue 'lex; }
        [ ]+ { continue 'lex; }
    */}
}
fn main() {
    assert_eq!(lex(b"\0"), 0);
    assert_eq!(lex(b"'qu\0tes' 'are' 'fine: \\'' \0"), 3);
    assert_eq!(lex(b"'unterminated\\'\0"), -1);
}

Bounds checks with padding

This example utilizes bounds checks with padding, which is enabled by default, to manage the end of input. The program counts space-separated single-quoted strings. A padding of YYMAXFILL null characters is appended to the end of the input. The value of YYMAXFILL is automatically generated using a max block. Padding characters need not be null; any characters that do not form a valid lexeme suffix can be used. In this example, padding should not contain single quotes, as they might be misinterpreted as the suffix of a single-quoted string. A "stop" rule is included to match the first padding character (null) and terminate the lexer. It verifies that the null is at the beginning of the padding; otherwise, it's a syntax error. Bounds checks are generated only for specific states, determined by the strongly connected components of the underlying automaton. These checks take the form (YYLIMIT - YYCURSOR) < n or YYLESSTHAN(n) with the generic API, where n is the minimum number of characters required for the lexer to proceed. This also implies that the next bounds check will occur within at most n characters. If the check condition is true, the lexer has reached the end of the input and invokes YYFILL(n), which should either supply at least n input characters or not return. In this example, YYFILL always fails and terminates the lexer with an error, which is acceptable as the input fits within a single buffer. Refer to the YYFILL with padding section for an example demonstrating buffer refill using YYFILL.

// re2rust $INPUT -o $OUTPUT --api simple
/*!max:re2c*/
fn lex(s: &[u8]) -> isize {
    let mut count = 0;
    let mut yycursor = 0;
    let yylimit = s.len() + YYMAXFILL;
    // Copy string to a buffer and add YYMAXFILL zero padding.
    let mut yyinput = Vec::with_capacity(yylimit);
    yyinput.extend_from_slice(s);
    yyinput.extend([0 as u8; YYMAXFILL]);
    'lex: loop { /*!re2c
        re2c:YYCTYPE = u8;
        re2c:YYFILL = "return -1;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Check that it is the sentinel, not some unexpected null.
            return if yycursor == s.len() + 1 { count } else { -1 }
        }
        str  { count += 1; continue 'lex; }
        [ ]+ { continue 'lex; }
        *    { return -1; }
    */}
}
fn main() {
    assert_eq!(lex(b""), 0);
    assert_eq!(lex(b"'qu\0tes' 'are' 'fine: \\'' "), 3);
    assert_eq!(lex(b"'unterminated\\'"), -1);
    assert_eq!(lex(b"'unexpected \0 null"), -1);
}

Custom checks

This example employs a custom end-of-input handling strategy using the generic API. The program counts space-separated single-quoted strings. It mirrors the sentinel example, with the exception that the input is not null-terminated. To compensate for the lack of a sentinel character at the end of the input, YYPEEK is redefined to perform a bounds check before reading the next input character. This approach is less efficient because checks are performed frequently. If the check condition fails, YYPEEK returns the actual character; otherwise, it returns a fabricated sentinel character.

// re2rust $INPUT -o $OUTPUT
// Expect a string without terminating null.
fn lex(s: &[u8]) -> isize {
    let mut count = 0;
    let mut cur = 0;
    let lim = s.len();
    'lex: loop {/*!re2c
        re2c:YYCTYPE = u8;
        re2c:YYPEEK = "if cur < lim {*s.get_unchecked(cur)} else {0}";
        re2c:YYSKIP = "cur += 1;";
        re2c:yyfill:enable  = 0;
        *      { return -1; }
        [\x00] { return count; }
        [a-z]+ { count += 1; continue 'lex; }
        [ ]+   { continue 'lex; }
    */}
}
fn main() {
    assert_eq!(lex(b""), 0);
    assert_eq!(lex(b"one two three "), 3);
    assert_eq!(lex(b"f0ur"), -1);
}

BUFFER REFILLING

Buffering becomes necessary when the input cannot be fully memory-mapped at once, either due to its size or its streaming nature (e.g., reading from a socket). The common practice is to allocate a fixed-size buffer and process input in manageable chunks. Once a chunk is processed, it's moved out, and new data is loaded in. In practice, this process is slightly more intricate as the lexer's state involves multiple interrelated positions, not just a single input position:

  • cursor: The next input character to be read (YYCURSOR in the C pointer API or YYSKIP/YYPEEK in the generic API).
  • limit: The position immediately following the last available input character (YYLIMIT in the C pointer API, implicitly handled by YYLESSTHAN in the generic API).
  • marker: The position of the most recent match, if any (YYMARKER in the default API or YYBACKUP/YYRESTORE in the generic API).
  • token: The starting position of the current lexeme (implicit in the re2rust API, as it's not required for normal lexer operation and can be defined and managed by the user).
  • context marker: The position of the trailing context (YYCTXMARKER in the C pointer API or YYBACKUPCTX/YYRESTORECTX in the generic API).
  • tag variables: Positions for submatches (defined using stags and mtags blocks and generic API primitives like YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN).

Not all these positions are necessarily used in every scenario. However, if they are used, they must be updated by YYFILL. All active positions are contained within the segment between the token and the cursor. Consequently, any data before the token can be discarded. The segment from the token up to the limit should be moved to the beginning of the buffer, and the remaining space at the end of the buffer should be filled with new data. To minimize YYFILL calls, it is advisable to read as many input characters as possible, even if a smaller amount would suffice to resume the lexer. The implementation details of YYFILL vary slightly depending on the chosen EOF handling method: the EOF rule case is somewhat simpler than the bounds-checking with padding approach. Additionally, if the -f --storable-state option is employed, YYFILL operates with subtly different semantics, as detailed in the section on storable state.

YYFILL with sentinel

When the EOF rule is in effect, YYFILL functions as a primitive resembling a function call. It takes no arguments and returns a value that is checked against zero. The condition YYLIMIT <= YYCURSOR in the C pointer API and YYLESSTHAN() in the generic API triggers the invocation of YYFILL. A non-zero return value indicates that YYFILL has failed. A successful YYFILL call must provide at least one character and adjust the input positions accordingly. The limit must always be set to one position after the last input character in the buffer, and the character at this limit position must be the sentinel symbol specified by the re2c:eof configuration. use std::fs::File;
use std::io::{Read, Write};
const BUFSIZE: usize = 4096;
struct State {
    file: File,
    yyinput: [u8; BUFSIZE],
    yylimit: usize,
    yycursor: usize,
    yymarker: usize,
    token: usize,
    eof: bool,
}
#[derive(PartialEq)]
enum Fill { Ok, Eof, LongLexeme }
fn fill(st: &mut State) -> Fill {
    if st.eof { return Fill::Eof; }
    // Error: lexeme too long. In real life could reallocate a larger buffer.
    if st.token < 1 { return Fill::LongLexeme; }
    // Shift buffer contents (discard everything up to the current token).
    st.yyinput.copy_within(st.token..st.yylimit, 0);
    st.yylimit -= st.token;
    st.yycursor -= st.token;
    st.yymarker = st.yymarker.overflowing_sub(st.token).0; // may underflow if marker is unused
    st.token = 0;
    // Fill free space at the end of buffer with new data from file.
    match st.file.read(&mut st.yyinput[st.yylimit..BUFSIZE - 1]) { // -1 for sentinel
        Ok(n) => {
            st.yylimit += n;
            st.eof = n == 0; // end of file
            st.yyinput[st.yylimit] = 0; // append sentinel
        }
        Err(why) => panic!("cannot read from file: {}", why)
    }
    return Fill::Ok;
}

Multiple blocks

Sometimes it is necessary to have multiple interrelated lexers (for example, if there is a high-level state machine that transitions between lexer modes). This can be implemented using multiple connected re2rust blocks. Another option is to use start conditions.

The implementation of connections between blocks depends on the target language. In languages that have goto statement (such as C/C++ and Go) one can have all blocks in one function, each of them prefixed with a label. Transition from one block to another is a simple goto. In languages that do not have goto (such as Rust) it is necessary to use a loop with a switch on a state variable, similar to the yystate loop/switch generated by re2rust, or else wrap each block in a function and use function calls.

The example below uses multiple blocks to parse binary, octal, decimal and hexadecimal numbers. Each base has its own block. The initial block determines base and dispatches to other blocks. Common configurations are defined in a separate block at the beginning of the program; they are inherited by the other blocks.

// re2rust $INPUT -o $OUTPUT
// Store u32 number in u64 during parsing to simplify overflow handling.
struct State<'a> {
    yyinput: &'a [u8],
    yycursor: usize,
    yymarker: usize,
    num: u64,
}
/*!re2c // Common re2c definitions shared between all functions.
    re2c:api = record;
    re2c:yyrecord = st;
    re2c:yyfill:enable = 0;
    re2c:YYCTYPE = u8;
*/
const ERROR: u64 = std::u32::MAX as u64 + 1; // overflow
macro_rules! maybe { // Convert the number from u64 to optional u32.
    ($n:expr) => { if $n < ERROR { Some($n as u32) } else { None } }
}
// Add digit with the given base, checking for overflow.
fn add(st: &mut State, offs: u8, base: u64) {
    let digit = unsafe { st.yyinput.get_unchecked(st.yycursor - 1) } - offs;
    st.num = std::cmp::min(st.num * base + digit as u64, ERROR);
}
fn parse_u32(s: & [u8]) -> Option<u32> {
    assert_eq!(s.last(), Some(&0)); // expect null-terminated input
    let mut st = State {yyinput: s, yycursor: 0, yymarker: 0, num: 0};
/*!re2c
    '0b' / [01]        { return parse_bin(&mut st); }
    "0"                { return parse_oct(&mut st); }
    "" / [1-9]         { return parse_dec(&mut st); }
    '0x' / [0-9a-fA-F] { return parse_hex(&mut st); }
    *                  { return None; }
*/
}
fn parse_bin(st: &mut State) -> Option<u32> {
    'bin: loop {/*!re2c
        [01] { add(st, 48, 2); continue 'bin; }
        *    { return maybe!(st.num); }
    */}
}
fn parse_oct(st: &mut State) -> Option<u32> {
    'oct: loop {/*!re2c
        [0-7] { add(st, 48, 8); continue 'oct; }
        *     { return maybe!(st.num); }
    */}
}
fn parse_dec(st: &mut State) -> Option<u32> {
    'dec: loop {/*!re2c
        [0-9] { add(st, 48, 10); continue 'dec; }
        *     { return maybe!(st.num); }
    */}
}
fn parse_hex(st: &mut State) -> Option<u32> {
    'hex: loop {/*!re2c
        [0-9] { add(st, 48, 16); continue 'hex; }
        [a-f] { add(st, 87, 16); continue 'hex; }
        [A-F] { add(st, 55, 16); continue 'hex; }
        *     { return maybe!(st.num); }
    */}
}

    assert_eq!(parse_u32(b"\0"), None);
    assert_eq!(parse_u32(b"1234567890\0"), Some(1234567890));
    assert_eq!(parse_u32(b"0b1101\0"), Some(13));
    assert_eq!(parse_u32(b"0x7Fe\0"), Some(2046));
    assert_eq!(parse_u32(b"0644\0"), Some(420));
    assert_eq!(parse_u32(b"9999999999\0"), None);
}

Start conditions

Start conditions allow a lexer to maintain multiple states. Each state is a set of rules. One can switch from one state to another using the YY_SWITCH command. This command is a macro that accepts one argument: the name of the target state.

Start conditions are useful for implementing lexers for languages that have sections with different lexical rules, such as markup languages (HTML, XML, etc.), programming languages with string and comment syntax, etc. The example below shows how to use start conditions to distinguish between comments and regular text in a simple markup language.

// re2rust $INPUT -o $OUTPUT
use re2c_rs::State;
fn lex(st: &mut State) -> isize {
    let mut count = 0;
    // Start conditions are defined via named blocks:
    // `<INITIAL>` for the initial state, and `<TAG>` for other states.
    // `re2c` uses these blocks to generate state-specific code.
    // `re2c:api = record` tells re2c to use the record-based API,
    // where the lexer state is passed as a mutable reference to a struct.
    // `re2c:tag:begin` and `re2c:tag:end` define how tags (capturing groups)
    // are handled. Here, we use them to mark the beginning and end of tags.
    /*!re2c
        re2c:api = record;
        re2c:yyrecord = st;
        re2c:tag:begin = "st.tag_start = st.yycursor";
        re2c:tag:end = "st.tag_end = st.yycursor";
        re2c:YYCTYPE = u8;
        re2c:YYFILL:enable = 0; // Disable automatic buffer filling for this example.
    */
    // Initial state:
    <INITIAL>
    '<' / [@'a'..'z'] { // Start of a tag
        // Switch to the TAG state.
        // The `YY_SWITCH` macro is generated by re2c based on the start condition name.
        // Here, it translates to setting a state variable in the `State` struct.
        // `st.yy_state = StateName::TAG` in the generated Rust code.
        YY_SWITCH(TAG);
        // Reset tag start position to current cursor.
        st.tag_start = st.yycursor;
        continue;
    }
    [^'\n']* ['\n'] { // Text line
        // In a real lexer, you would probably do something with the text.
        // Here, we just count the lines.
        count += 1;
        continue;
    }
    * { return -1; } // Unrecognized input

    // TAG state:
    <TAG>
    // Match the tag name (using the tag:begin/end markers).
    // `st.tag_start` and `st.tag_end` store the positions of the tag name.
    [@'a'..'z']* ['\n'] { // End of tag
        // `st.tag_end` is updated by re2c when the rule matches.
        // We could use `st.tag_start` and `st.tag_end` here to extract the tag name.
        // For example: let tag_name = &st.yyinput[st.tag_start..st.tag_end];
        // Switch back to the INITIAL state.
        YY_SWITCH(INITIAL);
        continue;
    }
    [^>\n]* // Any character within the tag, except '>' and newline.
    > { // End of tag.
        // Switch back to the INITIAL state.
        YY_SWITCH(INITIAL);
        continue;
    }
    * { // Any other character within the tag.
        // Ignore characters within the tag.
        continue;
    }
}
fn main() {
    let mut st = State::new(b"Text line 1.\n<tag1>\nText line 2.\n<tag2 att=val>\n");
    assert_eq!(lex(&mut st), 2); // Counts lines of text.
}

Condiciones de inicio

Las condiciones de inicio se habilitan con la opción --start-conditions. Proporcionan una forma de codificar varios autómatas interrelacionados dentro del mismo bloque re2rust.

Cada condición corresponde a un único autómata y tiene un nombre único especificado por el usuario y un número interno único definido por re2rust. Los números se utilizan para cambiar entre condiciones: el código generado utiliza las primitivas YYGETCOND y YYSETCOND para obtener la condición actual o establecerla en el número dado. Utilice el bloque conditions, la opción --header o la configuración re2c:header para generar identificadores numéricos de condición. La configuración re2c:cond:enumprefix especifica el prefijo del identificador generado.

En modo de condición, cada regla debe ir precedida por una lista de nombres de condición separados por comas entre corchetes angulares, o un comodín <*> para denotar todas las condiciones. La sintaxis de la regla se extiende de la siguiente manera:

< lista-condiciones > expresión-regular código
Una regla que se fusiona a cada condición en la lista-condiciones. Coincide con la expresión-regular y ejecuta el código asociado.
< lista-condiciones > expresión-regular => condición código
Una regla que se fusiona a cada condición en la lista-condiciones. Coincide con la expresión-regular, establece la condición actual en condición y ejecuta el código asociado.
< lista-condiciones > expresión-regular :=> condición
Una regla que se fusiona a cada condición en la lista-condiciones. Coincide con la expresión-regular y transiciona inmediatamente a condición (no hay acción semántica).
< lista-condiciones > !acción código
Una regla que vincula el código a la ubicación definida por acción en cada condición de la lista-condiciones (ver la sección acciones para varios tipos de acciones).
<! lista-condiciones > código
Una regla que antepone el código a las acciones semánticas de todas las reglas para cada condición en la lista-condiciones. Esta sintaxis está obsoleta y se debe usar la acción !pre_rule en su lugar (hace exactamente lo mismo).
< > código
Una regla que crea una condición de entrada especial con el número cero y el nombre "0" que ejecuta el código antes de saltar a otras condiciones. Esta sintaxis está obsoleta y se debe usar la acción !entry en su lugar (proporciona un control más granular, ya que el código se puede especificar por condición y se puede saltar directamente al inicio de la condición sin pasar por la distribución de condiciones).
< > => condición código
Igual que la regla anterior, excepto que establece la siguiente condición.
< > :=> condición
Igual que la regla anterior, excepto que no tiene código asociado y salta inmediatamente a condición.

El código que re2rust genera para las condiciones depende de si re2rust utiliza el enfoque de goto/label o el enfoque de bucle/switch para codificar los autómatas.

En lenguajes que tienen la sentencia goto (como C/C++ y Go), las condiciones se implementan de forma natural como bloques de código precedidos por etiquetas del tipo yyc_<cond>, donde cond es un nombre de condición (el prefijo de la etiqueta se puede cambiar con re2c:cond:prefix). Las transiciones entre condiciones se implementan utilizando goto y etiquetas de condición. Antes de todas las condiciones, re2rust genera un switch inicial en YYGETSTATE que salta al estado de inicio de la condición actual. Las reglas de acceso directo :=> omiten el switch inicial y saltan directamente a la condición especificada (se puede usar re2c:cond:goto para cambiar el comportamiento predeterminado). Las reglas con acciones semánticas no saltan automáticamente a la siguiente condición; esto debe hacerlo el código de acción definido por el usuario.

En lenguajes que no tienen goto (como Rust), re2rust reutiliza la variable yystate para almacenar los números de condición. Cada condición obtiene un identificador numérico igual al número de su estado de inicio, y un switch entre condiciones no es diferente a un switch entre estados de DFA de una sola condición. No hay necesidad de un switch de condición inicial separado. (Dado que se utiliza el mismo enfoque para implementar estados almacenables, YYGETCOND/YYSETCOND son redundantes si se utilizan tanto estados almacenables como condiciones).

Estado almacenable

Con la opción --storable-state, re2rust genera un lexer que puede almacenar su estado actual, devolver el control al llamador y, más tarde, reanudar las operaciones exactamente donde las dejó. El modo de operación predeterminado en re2rust es un modelo de "pull" (arrastrar), en el que el lexer "arrastra" más entrada cada vez que la necesita. Esto puede ser inaceptable en casos en los que la entrada está disponible pieza por pieza (por ejemplo, si el lexer es invocado por el analizador, o si el programa lexer se comunica a través de un protocolo de socket con algún otro programa que debe esperar una respuesta del lexer antes de transmitir el siguiente mensaje). La característica de estado almacenable está diseñada precisamente para tales casos: permite generar lexers que funcionan en un modelo de "push" (empujar). Cuando el lexer necesita más entrada, almacena su estado y devuelve el control al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el lexer exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo "pull":

  • Definir las primitivas YYSETSTATE() y YYGETSTATE(state).
  • Definir las variables yych, yyaccept (si se usa) y state como parte del estado persistente del lexer. La variable state debe inicializarse a -1.
  • YYFILL debe devolver el control al programa externo en lugar de intentar proporcionar más entrada. El código de retorno debe indicar que el lexer necesita más entrada.
  • El programa externo debe reconocer las situaciones en las que el lexer necesita más entrada y responder de manera adecuada.
  • Opcionalmente, utilice el bloque getstate para generar el switch YYGETSTATE separado del lexer principal. Esto solo funciona para lenguajes que tienen goto (no en modo --loop-switch).
  • Utilice re2c:eof y el método de *centinela con comprobaciones de límites* para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo añadir el relleno: el final actual de la entrada puede no ser el final definitivo de la entrada, y añadir relleno demasiado pronto puede cortar un lexema codicioso leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del búfer (que ya está bloqueado debido a la condición de fin de entrada).

// Fills the input buffer with data from the file.
fn fill(yyrecord: &mut State) -> Status {

    let mut i = yyrecord.yycursor;
    let mut j = 0;
    while i < yyrecord.yylimit {
        yyrecord.yyinput[j] = yyrecord.yyinput[i];
        i += 1;
        j += 1;

    yyrecord.yycursor = 0;
    yyrecord.yymarker = yyrecord.yymarker.saturating_sub(yyrecord.yycursor);

Soporte de codificación

Es necesario comprender la diferencia entre puntos de código y unidades de código. Un punto de código es un identificador numérico de un símbolo. Una unidad de código es la unidad de almacenamiento más pequeña en el texto codificado. Un solo punto de código puede representarse con una o más unidades de código. En una codificación de longitud fija, todos los puntos de código se representan con el mismo número de unidades de código. En una codificación de longitud variable, los puntos de código pueden representarse con un número diferente de unidades de código. Tenga en cuenta que la regla "cualquiera" [^] coincide con cualquier punto de código, pero no necesariamente con cualquier unidad de código (la única forma de coincidir con cualquier unidad de código independientemente de la codificación es la regla predeterminada *). El analizador léxico generado trabaja con un flujo de unidades de código: yych almacena una unidad de código y YYCTYPE es el tipo de unidad de código. Las expresiones regulares, por otro lado, se especifican en términos de puntos de código. Cuando re2rust compila expresiones regulares en autómatas, traduce puntos de código a unidades de código. Esto generalmente no es una asignación simple: en codificaciones de longitud variable, un rango de puntos de código puede traducirse a un gráfico complejo de unidades de código. Las siguientes codificaciones son compatibles:

  • ASCII (habilitado por defecto). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • EBCDIC (habilitado con --ebcdic o re2c:encoding:ebcdic). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • UCS2 (habilitado con --ucs2 o re2c:encoding:ucs2). Es una codificación de longitud fija con espacio de código [0-0xFFFF] y puntos de código y unidades de código de 2 bytes.
  • UTF8 (habilitado con --utf8 o re2c:encoding:utf8). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
  • UTF16 (habilitado con --utf16 o re2c:encoding:utf16). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 a 2 unidades de código.
  • UTF32 (habilitado con --utf32 o re2c:encoding:utf32). Es una codificación Unicode de longitud fija con espacio de código [0-0x10FFFF] y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión include/unicode_categories.re proporciona definiciones de re2rust para las categorías Unicode estándar.

La opción --input-encoding especifica la codificación del archivo fuente, que se puede utilizar para habilitar literales Unicode en expresiones regulares. Por ejemplo, --input-encoding utf8 le dice a re2rust que el archivo fuente está en UTF8 (difiere de --utf8 que establece la codificación del texto de entrada). La opción --encoding-policy especifica la forma en que re2rust maneja los sustitutos Unicode (puntos de código en el rango [0xD800-0xDFFF]).

A continuación se muestra un ejemplo de un analizador léxico para identificadores Unicode codificados en UTF8.

// re2rust $INPUT -o $OUTPUT --utf8 --api simple
/*!include:re2c "unicode_categories.re" */

        re2c:YYCTYPE = u8;

        // (ver https://unicode.org/reports/tr31)

        id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];

        identifier { return true; }

    assert!(lex("_Ыдентификатор\0".as_bytes()));

Archivos de inclusión

re2rust permite incluir otros archivos usando un bloque de la forma /*!include:re2c ARCHIVO */ o %{include ARCHIVO %}, o una directiva dentro del bloque !include ARCHIVO ;, donde ARCHIVO es una ruta al archivo a incluir. re2rust busca archivos de inclusión en el directorio del archivo que incluye y en las ubicaciones de inclusión, que se pueden especificar con la opción -I. Los bloques/directivas de inclusión en re2rust funcionan de la misma manera que el #include de C/C++: el contenido de ARCHIVO se copia literalmente en lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias. Utilice la opción --depfile para rastrear las dependencias de compilación del archivo de salida en los archivos de inclusión. re2rust proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como las categorías Unicode) y forman algo así como una biblioteca estándar para re2rust. A continuación se muestra un ejemplo de uso de archivos de inclusión.

Archivo de inclusión 1 (definitions.rs)

#[derive(Debug, PartialEq)]
enum Num { Int, Float, NaN }
/*!re2c
    number = [1-9][0-9]*;
*/

Archivo de inclusión 2 (extra_rules.re.inc)

// números de punto flotante

Archivos de cabecera

re2rust permite generar un archivo de cabecera a partir del archivo .re de entrada usando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de cabecera y el segundo bloque marca el final. Todo lo que esté entre estos bloques es procesado por re2rust, y el código generado se escribe en el archivo especificado con la opción --header o la configuración re2c:header (o stdout si no se utiliza ninguna opción ni configuración). El archivo de cabecera autogenerado puede ser necesario en casos donde re2rust se utiliza para generar definiciones que deben ser visibles desde otras unidades de traducción.

Aquí hay un ejemplo de generación de un archivo de cabecera que contiene la definición del estado del analizador léxico con variables de etiqueta (las variables numéricas dependen de la gramática regular y son desconocidas para el programador).

INTRODUCTION

re2rust is a lexer generator that generates C code. It is used for high-speed pattern matching of character streams. For details see re2c(1).

re2rust is a skeleton generator. It is used to generate skeleton programs which test re2c scanners. A skeleton program is a C program that takes an input file, runs it through the scanner generated by re2c, and compares the results with the expectations. Skeleton programs are very useful for a number of reasons:

  • They can check correctness of various re2rust optimizations (the data is generated early in the process, before any DFA transformations have taken place).
  • Generating a set of input data with good coverage may be useful for both testing and benchmarking.
  • Generating self-contained executable programs allows one to get minimized test cases (the original code may be large or have a lot of dependencies).

The difficulty with generating input data is that for all but the most trivial cases the number of possible input strings is too large (even if the string length is limited). re2rust solves this difficulty by generating sufficiently many strings to cover almost all DFA transitions. It uses the following algorithm. First, it constructs a skeleton of the DFA. For encodings with 1-byte code unit size (such as ASCII, UTF-8 and EBCDIC) skeleton is just an exact copy of the original DFA. For encodings with multibyte code units skeleton is a copy of DFA with certain transitions omitted: namely, re2rust takes at most 256 code units for each disjoint continuous range that corresponds to a DFA transition. The chosen values are evenly distributed and include range bounds. Instead of trying to cover all possible paths in the skeleton (which is infeasible) re2rust generates sufficiently many paths to cover all skeleton transitions, and thus trigger the corresponding conditional jumps in the lexer. The algorithm implementation is limited by ~1Gb of transitions and consumes constant amount of memory (re2rust writes data to file as soon as it is generated).

Visualization and debug

With the -D, --emit-dot option, re2rust does not generate code. Instead, it dumps the generated DFA in DOT format. One can convert this dump to an image of the DFA using Graphviz or another library. Note that this option shows the final DFA after it has gone through a number of optimizations and transformations. Earlier stages can be dumped with various debug options, such as --dump-nfa, --dump-dfa-raw etc. (see the full list of options).
