READ(3P) Manual del programador de POSIX READ(3P)

PROLOG

Esta página del manual forma parte del Manual del programador de POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual correspondiente de Linux para obtener detalles sobre el comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

pread, read — leer de un archivo

SINOPSIS

#include <unistd.h>
ssize_t pread(int fildes, void *buf, size_t nbyte, off_t offset);
ssize_t read(int fildes, void *buf, size_t nbyte);

DESCRIPCIÓN

La función read() intenta leer nbyte bytes del archivo asociado con el descriptor de archivo abierto, fildes, en el búfer apuntado por buf. El comportamiento de lecturas concurrentes múltiples en la misma tubería (pipe), FIFO o dispositivo terminal no está especificado.

Antes de que se tome alguna de las acciones descritas a continuación, y si nbyte es cero, la función read() puede detectar y devolver errores como se describe a continuación. En ausencia de errores, o si no se realiza la detección de errores, la función read() devolverá cero y no tendrá otros resultados.

En archivos que admiten búsqueda (por ejemplo, un archivo regular), read() comenzará en una posición del archivo dada por el desplazamiento de archivo asociado con fildes. El desplazamiento de archivo se incrementará en el número de bytes realmente leídos.

Los archivos que no admiten búsqueda —por ejemplo, terminales— siempre leen desde la posición actual. El valor de un desplazamiento de archivo asociado con dicho archivo no está definido.

No se transferirá ningún dato más allá del final del archivo actual. Si la posición de inicio está en el final del archivo o más allá, se devolverá 0. Si el archivo se refiere a un archivo especial de dispositivo, el resultado de las solicitudes de read() posteriores depende de la implementación.

Si el valor de nbyte es mayor que {SSIZE_MAX}, el resultado depende de la implementación.

Al intentar leer de una tubería o FIFO vacía:

*
Si ningún proceso tiene la tubería abierta para escritura, read() devolverá 0 para indicar el final del archivo.
*
Si algún proceso tiene la tubería abierta para escritura y O_NONBLOCK está establecido, read() devolverá -1 y establecerá errno en [EAGAIN].
*
Si algún proceso tiene la tubería abierta para escritura y O_NONBLOCK no está establecido, read() bloqueará el hilo de llamada hasta que se escriban algunos datos o la tubería sea cerrada por todos los procesos que la tenían abierta para escritura.

Al intentar leer un archivo (que no sea una tubería o FIFO) que admite lecturas no bloqueantes y no tiene datos disponibles actualmente:

*
Si O_NONBLOCK está establecido, read() devolverá -1 y establecerá errno en [EAGAIN].
*
Si O_NONBLOCK no está establecido, read() bloqueará el hilo de llamada hasta que estén disponibles algunos datos.
*
El uso de la bandera O_NONBLOCK no tiene efecto si hay algunos datos disponibles.

La función read() lee datos previamente escritos en un archivo. Si alguna porción de un archivo regular anterior al final del archivo no ha sido escrita, read() devolverá bytes con valor 0. Por ejemplo, lseek() permite establecer el desplazamiento del archivo más allá del final de los datos existentes en el archivo. Si posteriormente se escriben datos en este punto, las lecturas posteriores en el espacio entre el final de datos anterior y los datos recién escritos devolverán bytes con valor 0 hasta que se escriban datos en el espacio.

Tras una finalización exitosa, donde nbyte es mayor que 0, read() marcará para actualización la última marca de tiempo de acceso a los datos del archivo, y devolverá el número de bytes leídos. Este número nunca será mayor que nbyte. El valor devuelto puede ser menor que nbyte si el número de bytes restantes en el archivo es menor que nbyte, si la solicitud de read() fue interrumpida por una señal, o si el archivo es una tubería o FIFO o archivo especial y tiene menos de nbyte bytes inmediatamente disponibles para leer. Por ejemplo, una read() de un archivo asociado con una terminal puede devolver una línea de datos escrita.

Si una read() es interrumpida por una señal antes de leer algún dato, devolverá -1 con errno establecido en [EINTR].

Si una read() es interrumpida por una señal después de haber leído correctamente algunos datos, devolverá el número de bytes leídos.

Para archivos regulares, no se transferirá ningún dato más allá del desplazamiento máximo establecido en la descripción del archivo abierto asociada con fildes.

Si fildes se refiere a un socket, read() será equivalente a recv() sin ninguna bandera establecida.

Si se han establecido las banderas O_DSYNC y O_RSYNC, las operaciones de E/S de lectura en el descriptor de archivo se completarán según lo definido por la finalización de la integridad de los datos de E/S sincronizada. Si se han establecido las banderas O_SYNC y O_RSYNC, las operaciones de E/S de lectura en el descriptor de archivo se completarán según lo definido por la finalización de la integridad del archivo de E/S sincronizada.

Si fildes se refiere a un objeto de memoria compartida, el resultado de la función read() no está especificado.

Si fildes se refiere a un objeto de memoria tipificada, el resultado de la función read() no está especificado.

Una read() de un archivo STREAMS puede leer datos en tres modos diferentes: modo de flujo de bytes, modo de mensaje no descartable, y modo de mensaje descartable. El valor predeterminado será el modo de flujo de bytes. Esto se puede cambiar usando la solicitud ioctl() I_SRDOPT, y se puede verificar con ioctl() I_GRDOPT. En modo de flujo de bytes, read() recuperará datos del STREAM hasta que se transfieran tantos bytes como se solicitaron, o hasta que no haya más datos para recuperar. El modo de flujo de bytes ignora los límites de los mensajes.

En modo de mensaje no descartable de STREAMS, read() recuperará datos hasta que se transfieran tantos bytes como se solicitaron, o hasta que se alcance el límite de un mensaje. Si read() no recupera todos los datos de un mensaje, los datos restantes quedarán en el STREAM y podrán ser recuperados por la siguiente llamada a read(). El modo de mensaje descartable también recupera datos hasta que se transfieran tantos bytes como se solicitaron, o se alcance el límite de un mensaje. Sin embargo, los datos no leídos que queden en un mensaje después de que read() devuelva serán descartados y no estarán disponibles para una llamada posterior a read(), getmsg() o getpmsg().

Cómo read() maneja mensajes de STREAMS de cero bytes depende de la configuración actual del modo de lectura. En modo de flujo de bytes, read() aceptará datos hasta que haya leído nbyte bytes, o hasta que no haya más datos para leer, o hasta que se encuentre un bloque de mensaje de cero bytes. La función read() devolverá entonces el número de bytes leídos y devolverá el mensaje de cero bytes al STREAM para ser recuperado por la siguiente llamada a read(), getmsg() o getpmsg(). En modo de mensaje no descartable o mensaje descartable, un mensaje de cero bytes devolverá 0 y el mensaje será eliminado del STREAM. Cuando se lee un mensaje de cero bytes como el primer mensaje en un STREAM, el mensaje se eliminará del STREAM y se devolverá 0, independientemente del modo de lectura.

Una read() de un archivo STREAMS devolverá los datos en el mensaje en el frente de la cola de lectura de la cabeza del STREAM, independientemente de la banda de prioridad del mensaje.

Por defecto, los STREAMs están en modo de control normal, en el que una read() de un archivo STREAMS solo puede procesar mensajes que contienen una parte de datos pero no contienen una parte de control. read() fallará si se encuentra un mensaje que contiene una parte de control en la cabeza del STREAM. Esta acción predeterminada se puede cambiar colocando el STREAM en modo de datos de control o modo de descarte de control con el comando ioctl() I_SRDOPT. En modo de datos de control, read() convertirá cualquier parte de control en datos y la pasará a la aplicación antes de pasar cualquier parte de datos presente originalmente en el mismo mensaje. En modo de descarte de control, read() descartará las partes de control del mensaje pero devolverá al proceso cualquier parte de datos en el mensaje.

Además, read() fallará si la cabeza del STREAM había procesado un error asíncrono antes de la llamada. En este caso, el valor de errno no reflejará el resultado de read(), sino que reflejará el error previo. Si ocurre una desconexión (hangup) en el STREAM que se está leyendo, read() continuará operando normalmente hasta que la cola de lectura de la cabeza del STREAM esté vacía. A partir de entonces, devolverá 0.

VALOR DE RETORNO

Al completarse con éxito, estas funciones devolverán un entero no negativo que indica el número de bytes leídos realmente. De lo contrario, las funciones devolverán -1 y establecerán errno para indicar el error.

ERRORES

Estas funciones fallarán si:

EAGAIN
El archivo no es una tubería, ni una FIFO, ni un socket, la bandera O_NONBLOCK está establecida para el descriptor de archivo y el hilo se retrasaría en la operación de lectura.
EBADF
El argumento fildes no es un descriptor de archivo válido abierto para lectura.
EBADMSG
El archivo es un archivo STREAM establecido en modo de control-normal y el mensaje que espera para ser leído incluye una parte de control.
EINTR
La operación de lectura se interrumpió debido a la recepción de una señal y no se transfirieron datos.
EINVAL
El STREAM o multiplexor referenciado por fildes está enlazado (directa o indirectamente) aguas abajo de un multiplexor.
EIO
El proceso es miembro de un grupo de procesos en segundo plano que intenta leer de su terminal de control, y ya sea que el hilo que llama esté bloqueando SIGTTIN o el proceso esté ignorando SIGTTIN o el grupo de procesos del proceso esté huérfano. Este error también puede generarse por razones definidas por la implementación.
EISDIR
El argumento fildes se refiere a un directorio y la implementación no permite leer el directorio usando read() o pread(). Se debe usar la función readdir() en su lugar.
EOVERFLOW
El archivo es un archivo regular, nbyte es mayor que 0, la posición de inicio está antes del final del archivo y la posición de inicio es mayor o igual que el máximo de desplazamiento establecido en la descripción del archivo abierto asociado con fildes.

La función pread() fallará si:

EINVAL
El archivo es un archivo regular o un archivo especial de bloque, y el argumento offset es negativo. El desplazamiento del archivo no cambiará.
ESPIPE
El archivo es incapaz de buscar.

La función read() fallará si:

EAGAIN
El archivo es una tubería o FIFO, la bandera O_NONBLOCK está establecida para el descriptor de archivo y el hilo se retrasaría en la operación de lectura.
EAGAIN o EWOULDBLOCK

El archivo es un socket, la bandera O_NONBLOCK está establecida para el descriptor de archivo y el hilo se retrasaría en la operación de lectura.
ECONNRESET
Se intentó una lectura en un socket y la conexión fue cerrada forzosamente por su par.
ENOTCONN
Se intentó una lectura en un socket que no está conectado.
ETIMEDOUT
Se intentó una lectura en un socket y ocurrió un tiempo de espera de transmisión.

Estas funciones pueden fallar si:

EIO
Ha ocurrido un error físico de E/S.
ENOBUFS
No había suficientes recursos disponibles en el sistema para realizar la operación.
ENOMEM
No había suficiente memoria disponible para satisfacer la solicitud.
ENXIO
Se realizó una solicitud a un dispositivo inexistente, o la solicitud estuvo fuera de las capacidades del dispositivo.

EJEMPLOS

Lectura de datos en un búfer

El siguiente ejemplo lee datos del archivo asociado con el descriptor de archivo fd en el búfer apuntado por buf.

#include <unistd.h>
...
char buf[20];
size_t nbytes;
ssize_t bytes_read;
int fd;
...
nbytes = sizeof(buf);
bytes_read = read(fd, buf, nbytes);
...

Ninguno.

FUNDAMENTO

Este volumen de POSIX.1‐2017 no especifica el valor del desplazamiento del archivo después de que se devuelve un error; hay demasiados casos. Para errores de programación, como [EBADF], el concepto no tiene sentido ya que no hay ningún archivo involucrado. Para errores que se detectan de inmediato, como [EAGAIN], claramente el desplazamiento no debería cambiar. Después de una interrupción o un error de hardware, sin embargo, un valor actualizado sería muy útil y es el comportamiento de muchas implementaciones.

Tenga en cuenta que una lectura de cero bytes no modifica la marca de tiempo del último acceso a datos. Se requiere que una lectura que solicite más de cero bytes, pero que devuelva cero, modifique la marca de tiempo del último acceso a datos.

Se permite a las implementaciones, pero no se les exige, que realicen comprobaciones de errores para solicitudes de lectura de cero bytes.

Entrada y Salida

El uso de E/S con grandes recuentos de bytes siempre ha presentado problemas. En un momento se consideraron ideas como lread() y lwrite() (usando y devolviendo longs). La solución actual es utilizar tipos abstractos en la función del estándar ISO C para read() y write(). Los tipos abstractos se pueden declarar de forma que las funciones existentes funcionen, pero también se pueden declarar de forma que los tipos más grandes se puedan representar en futuras implementaciones. Se supone que cualquier restricción que limite el rango máximo de size_t también limita las solicitudes de E/S portátiles al mismo rango. Este volumen de POSIX.1‐2017 también limita el rango además al requerir que el recuento de bytes se limite de manera que un valor de retorno con signo siga siendo significativo. Dado que el tipo de retorno también es un tipo abstracto (con signo), el recuento de bytes puede ser definido por la implementación para que sea mayor de lo que un int puede contener.

Los desarrolladores del estándar consideraron agregar requisitos de atomicidad a una tubería o FIFO, pero reconocieron que debido a la naturaleza de las tuberías y FIFOs no podría haber garantía de atomicidad de las lecturas de {PIPE_BUF} o cualquier otro tamaño que pudiera ayudar a la portabilidad de las aplicaciones.

Este volumen de POSIX.1‐2017 requiere que no se tome ninguna acción para read() o write() cuando nbyte es cero. Esto no pretende prevalecer sobre la detección de errores (como punteros de búfer inválidos o descriptores de archivo). Esto es coherente con el resto de este volumen de POSIX.1‐2017, pero la redacción aquí podría malinterpretarse para requerir la detección del caso cero antes que cualquier otro error. Un valor de cero debe considerarse un valor correcto, para el cual la semántica es una operación nula.

Se pretende que la E/S sea atómica para archivos ordinarios y tuberías y FIFOs. Atómico significa que todos los bytes de una única operación que empezaron juntos terminan juntos, sin intercalarse con otras operaciones de E/S. Es un atributo conocido de los terminales que esto no se cumple, y los terminales están explícitamente (e implícitamente permanentemente) exceptuados, haciendo que el comportamiento no esté especificado. El comportamiento para otros tipos de dispositivos también se deja sin especificar, pero la redacción está destinada a implicar que los futuros estándares podrían optar por especificar la atomicidad (o no).

Se hicieron recomendaciones para agregar parámetros de formato a read() y write() para manejar transferencias de red entre sistemas de archivos heterogéneos y tipos de hardware base. Tal instalación puede ser necesaria para el soporte de la presentación de servicios de capa de OSI. Sin embargo, se determinó que esto debería corresponderse con instalaciones similares del lenguaje C, y eso está más allá del alcance de este volumen de POSIX.1‐2017. El concepto se sugirió a los desarrolladores del estándar ISO C para su consideración como posible área de trabajo futura.

En 4.3 BSD, una read() o write() que es interrumpida por una señal antes de transferir datos no devuelve por defecto un error [EINTR], sino que se reinicia. En 4.2 BSD, 4.3 BSD y la Octava Edición, hay una función adicional, select(), cuyo propósito es pausar hasta que se detecte actividad especificada (datos para leer, espacio para escribir, etc.) en descriptores de archivo especificados. Es común en aplicaciones escritas para esos sistemas que select() se utilice antes de read() en situaciones (como la entrada del teclado) donde se desea la interrupción de E/S debido a una señal.

La cuestión de qué archivos o tipos de archivo son interrumpibles se considera un problema de diseño de la implementación. Esto a menudo se ve afectado principalmente por problemas de hardware y fiabilidad.

No hay referencias a las acciones tomadas después de un "error irrecuperable". Se considera que está más allá del alcance de este volumen de POSIX.1‐2017 describir qué sucede en el caso de errores de hardware.

Las versiones anteriores de este estándar permitían dos comportamientos muy diferentes con respecto al manejo de interrupciones. Para minimizar la confusión resultante, se decidió que POSIX.1‐2008 solo debería admitir uno de estos comportamientos. RATIONALE

The read() function is fundamental for input operations. The standard has always required that when a signal interrupts a read that has been processing less than the number of bytes requested, the number of bytes actually transferred before the interrupt should be returned. If -1 is returned when any data is transferred, it is difficult to recover from the error on a seekable device and impossible on a non-seekable device. Most new implementations support this behavior. The behavior required by POSIX.1‐2008 is to return the number of bytes transferred.

POSIX.1‐2008 does not specify when an implementation that buffers read()s actually moves the data into the user-supplied buffer, so an implementation may choose to do this at the latest possible moment. Therefore, an interrupt arriving earlier may not cause read() to return a partial byte count, but rather to return -1 and set errno to [EINTR].

Consideration was also given to combining the two previous options, and setting errno to [EINTR] while returning a short count. However, not only is there no existing practice that implements this, it is also contradictory to the idea that when errno is set, the function responsible shall return -1.

This volume of POSIX.1‐2017 intentionally does not specify any pread() errors related to pipes, FIFOs, and sockets other than [ESPIPE].
