DESCRIPCIÓN

La función val_resolve_and_check() consulta un conjunto de servidores de nombres para la tupla <nombre_dominio, tipo, clase> y verifica y valida la respuesta. La verificación implica comprobar los RRSIGs, y la validación es la verificación de una cadena de autenticación desde un ancla de confianza configurada.

El parámetro flags se puede utilizar para controlar los resultados de la validación. Los siguientes valores, que pueden combinarse con OR, están definidos actualmente para este campo:

VAL_QUERY_DONT_VALIDATE
Esta bandera hace que el validador deshabilite la validación para esta consulta.
VAL_QUERY_IGNORE_SKEW
Esta bandera hace que el validador deshabilite la comprobación de los tiempos de inicio y expiración de las firmas en los RRSIGs.
VAL_QUERY_AC_DETAIL
Esta bandera hace que el validador copie los detalles de la cadena de autenticación en el miembro val_rc_answer dentro de la estructura val_result_chain devuelta.
VAL_QUERY_ASYNC
Esta bandera habilita la resolución asíncrona de consultas para esa búsqueda.
VAL_QUERY_NO_DLV
Esta bandera hace que el validador deshabilite el procesamiento DLV para esta consulta. Esto solo está disponible si la biblioteca libval(3) ha sido compilada con soporte DLV.
VAL_QUERY_NO_EDNS0_FALLBACK
Al consultar varios servidores de nombres, libsres(3) también intentará varios tamaños de EDNS0, terminando con una consulta que tiene EDNS0 deshabilitado (es decir, sin el bit CD establecido). Esta bandera hace que libval deshabilite la recuperación de EDNS0 para la consulta.
VAL_QUERY_ITERATE
Esta bandera obliga a libval a realizar una búsqueda iterativa consultando varios servidores de nombres en la jerarquía de delegación, en lugar de solicitar esta información a cualquier servidor de nombres en caché que pueda estar configurado en dnsval.conf.
VAL_QUERY_SKIP_RESOLVER
Esta bandera obliga a libval a mirar solo su caché mientras intenta resolver un nombre.
VAL_QUERY_SKIP_CACHE
Hay dos niveles de caché que ocurren dentro de libval: a nivel de aserción y a nivel de respuesta. Esta bandera obliga a libval a ignorar los datos en ambas cachés mientras intenta resolver un nombre.
VAL_QUERY_SKIP_ANS_CACHE
Hay dos niveles de caché que ocurren dentro de libval: a nivel de aserción y a nivel de respuesta. Esta bandera obliga a libval a ignorar los datos en la caché de respuestas mientras intenta resolver un nombre. Si ya existe una aserción para el nombre, clase y tipo dados, se reutiliza esa aserción hasta que expire. Una vez que expira, el nombre se busca a través de una consulta, incluso si un registro más nuevo (obtenido por otra aserción en el mismo u otro contexto) está disponible en su caché de respuestas.

El primer parámetro de val_resolve_and_check() es el contexto del validador. Las aplicaciones pueden crear un nuevo contexto de validador usando la función val_create_context(). Esta función analiza los archivos de configuración del resolvedor y del validador y crea el manejador newcontext para esta información analizada. La información almacenada como parte del contexto del validador incluye la política de validación y la política del resolvedor.

Las políticas del validador y del resolvedor se leen de los archivos /etc/dnsval.conf y /etc/resolv.conf por defecto. /etc/root.hints proporciona información de arranque para el validador cuando funciona como un resolvedor completo (ver dnsval.conf(3)). Estos valores predeterminados pueden ser diferentes si se especificó algún otro valor en el momento de la configuración de la biblioteca. Si el archivo de configuración del resolvedor predeterminado no se encuentra en la ubicación especificada, libval también intentará recurrir a /etc/resolv.conf como último recurso.

Las aplicaciones también pueden crear un contexto de validador con una política personalizada usando la función val_create_context_ex().

El argumento opt en val_create_context_ex() apunta a la siguiente estructura:

typedef struct val_context_opt {
    unsigned int vc_qflags;
    unsigned int vc_polflags;
    char *vc_valpol;
    char *vc_nslist;
    char *vc_val_conf;
    char *vc_res_conf;
    char *vc_root_conf;
    val_global_opt_t *gopt, 
} val_context_opt_t;

vc_qflags especifica las banderas de consulta predeterminadas para las consultas asociadas con el contexto. Este campo es idéntico al argumento flags en la función val_resolve_and_check().

Los campos vc_val_conf, vc_res_conf y vc_root_conf se pueden usar para especificar archivos de configuración alternativos en lugar de los archivos predeterminados utilizados para la información de configuración del validador, del resolvedor y de las raíces.

El campo vc_valpol se puede usar para proporcionar un "fragmento" de configuración de validador personalizado al validador. El validador analiza esta información y la aplica a la configuración del validador predeterminada, ya sea como una extensión o como una anulación, según lo especificado por el campo vc_polflags. El campo vc_nslist, de manera similar, se puede usar para proporcionar una lista personalizada de servidores de nombres recursivos a los que enviar consultas, además de (o en lugar de) la lista de servidores de nombres especificados en el archivo resolv.conf. La lista de servidores de nombres en vc_res_conf debe especificarse como una lista separada por espacios de direcciones IP o IPv6.

Se puede crear un mapeo personalizado entre una zona y un servidor de nombres utilizando la función val_context_store_ns_for_zone().

vc_polflags se puede configurar con los siguientes valores:

CTX_DYN_POL_VAL_OVR
Cuando esta bandera está establecida, solo la configuración del validador especificada en el campo vc_valpol se utiliza para la configuración del validador. Las opciones especificadas en el archivo dnsval.conf se ignoran.

NAME

libval - DNSSEC validator library

This library provides functions for validating DNSSEC signed data.

SYNOPSIS

#include <libval.h>

Initialize validator context:

    val_context_t *ctx;
    val_init_context(&ctx, NULL);

Set validation policies:

    val_context_set_dnssec_policy(ctx, VAL_POLICY_SECURE);
    val_context_set_validation_policy(ctx, VAL_POLICY_SECURE);
    val_context_set_rev_policy(ctx, VAL_POLICY_SECURE);

Resolve and validate a name:

    struct val_results *results;
    val_status_t status;

    status = val_resolve_and_check(ctx, "example.com", ns_t_a, NS_CLASS_IN,
                                   &results);

Check validation status:

    if (val_isvalidated(status)) {
        // Data is cryptographically verified and validated.
    } else if (val_istrusted(status)) {
        // Data is locally trusted but not validated.
    } else if (val_does_not_exist(status)) {
        // Data does not exist.
    }

Free results:

    free_result_chain(results);

Destroy context:

    val_free_context(ctx);

DESCRIPTION

The libval library provides a high-level interface for performing DNSSEC validation. It allows applications to query DNS names and have the returned data automatically validated against locally configured trust anchors.

The primary data structure used by the library is the validation context, represented by `val_context_t`. This context holds configuration information, including trust anchors, validation policies, and resolver settings.

Applications typically perform the following steps when using libval:

  1. Initialize a validation context using val_init_context(). This function can optionally take a configuration file path as an argument. If no path is provided, the library will attempt to load default configuration files (e.g., dnsval.conf).
  2. Set various validation policies and options within the context using functions like val_context_set_dnssec_policy(), val_context_set_validation_policy(), and val_context_set_rev_policy(). These functions allow fine-grained control over how the validator behaves.
  3. Perform DNS queries and validation using val_resolve_and_check(). This function takes the context, query name, query type, query class, and a pointer to a results structure. It returns a validation status code and populates the results structure with the validated data.
  4. Process the validation results. The results are returned as a linked list of val_result_chain structures, each containing the validation status and the authenticated data. Helper functions like val_isvalidated(), val_istrusted(), and val_does_not_exist() can be used to interpret the validation status.
  5. Free the allocated memory for the results using free_result_chain().
  6. Destroy the validation context when it is no longer needed using val_free_context().

The validation context can be configured with various flags that modify its behavior. These flags are typically set via the dnsval.conf file or programmatically. The following flags are particularly relevant:

CTX_DYN_POL_RES_OVR
When this flag is set only the name servers specified in the vc_nslist field is used for the resolver configuration. Options specified in the resolv.conf file are ignored.
CTX_DYN_POL_GLO_OVR
When this flag is set only the global options set in gopt field are used. Global options specified in the dnsval.conf file are ignored.
CTX_DYN_POL_RES_NRD
When this flag is set outgoing queries have the Recursion Desired (RD) bit set to 0. This is useful if queries need to be sent to an authoritative-only name server.

The gopt field points to the following structure:

typedef struct val_global_opt {
    int local_is_trusted;
    long edns0_size;
    int env_policy;
    int app_policy;
    char *log_target;
    int closest_ta_only;
    int rec_fallback;
    long max_refresh;
    int proto;
} val_global_opt_t;

Setting a value of 1 for local_is_trusted is equivalent to specifying the trust-oob-answers option in the dnsval.conf file to yes. Similarly, setting the closest_ta_only and rec_fallback members to 1 is equivalent to setting the closest-ta-only and rec-fallback options to yes in the dnsval.conf file. A value of 0 is equivalent to the no setting for these option.

Setting the edns0_size member to a particular value has the same effect setting the edns0-size option in the dnsval.conf file.

Setting the max_refresh member to a particular value has the same effect setting the max-refresh option in the dnsval.conf file.

Setting the proto member to a particular value has the same effect setting the proto option in the dnsval.conf file.

env_policy and app_policy can be set to one of VAL_POL_GOPT_DISABLE, VAL_POL_GOPT_ENABLE, or VAL_POL_GOPT_OVERRIDE. These values correspond directly to the disable, enable and override options for the env-policy and app-policy settings in the dnsval.conf file.

Values of -1 for the above fields are treated as "ignore" conditions in that the validator will not include dynamically supplied global options with a value of -1 when creating its context. This allows an application to overriding a subset of global options while using the global options supplied in the dnsval.conf file by default.

The log_target field enables the application to supply log targets in addition to the ones configured in the configuration file.

See dnsval.conf(3) for more details on specifying validator policy.

Default query flags can be set and unset for a given context using val_context_setqflags(). This allows an application to alter the DNSSEC validator processing, while still having most of the more granular default configuration specified in its configuration file. The action parameter can be set to one of the following.

VAL_CTX_FLAG_SET
This option causes the validator to set the given flag as one of the default query flags.
VAL_CTX_FLAG_RESET
This option causes the validator to reset the given flag if it was set as one of the default query flags for the context.

Answers returned by val_resolve_and_check() are made available in the *results linked list. Each answer corresponds to a distinct RRset; multiple RRs within the RRset are part of the same answer. Multiple answers are possible when type is ns_t_any or ns_t_rrsig.

Individual elements in *results point to val_authentication_chain linked lists. The authentication chain elements in val_authentication_chain contain the actual RRsets returned by the name server in response to the query.

Validation result values returned in val_result_chain can be can be converted into ASCII format using the p_val_status(). Authentication chain status values returned in each element of the val_authentication_chain linked list can be can be converted into ASCII format using the p_ac_status() functions.

While some applications such as DNSSEC troubleshooting utilities and packet inspection tools may look at individual authentication chain elements to identify the actual reasons for validation error, most applications will only be interested in a single error code for determining the authenticity of data.

val_isvalidated() identifies if a given validation result status value corresponds to an answer that was cryptographically verified and validated using a locally configured trust anchor.

val_istrusted() identifies if a given validator status value is trusted. An answer may be locally trusted without being validated.

val_does_not_exist() identifies if a given validator status value corresponds to one of the non-existence types.

The libval library internally allocates memory for *results and this must be freed by the invoking application using the free_result_chain() interface.

DATA STRUCTURES

struct val_result_chain
struct val_result_chain
{
    val_status_t                     val_rc_status;
    char                            *val_rc_alias;
    struct val_rrset_rec            *val_rc_rrset;
    struct val_authentication_chain *val_rc_answer;
    int                              val_rc_proof_count;
    struct val_authentication_chain *val_rc_proofs[MAX_PROOFS];
    struct val_result_chain         *val_rc_next;
};
val_rc_answer
Authentication chain for a given RRset.
val_rc_next
Pointer to the next RRset in the set of answers returned for a query.
val_rc_proofs
Pointer to authentication chains for any proof of non-existence that were returned for the query.
val_rc_proof_count
Number of proof elements stored in val_rc_proofs. The number cannot exceed MAX_PROOFS.
val_rc_alias
For an val_result_chain element that points to a name alias, this field contains the target value.
val_rc_rrset
For a val_result_chain element that contains a valid (not NULL) val_rc_answer field, the val_rc_rrset field points to the top-most val_rrset_rec element in the val_rc_answer authentication chain.
val_rc_status
Validation status for a given RRset. This can be one of the following:
VAL_SUCCESS
Answer received and validated successfully.
VAL_NONEXISTENT_NAME
No name was present and a valid proof of non-existence confirming the missing name (NSEC or NSEC3 span) was returned. The components of the proof were also individually validated.
VAL_NONEXISTENT_TYPE
No type exists for the name and a valid proof of non-existence confirming the missing name was returned. The components of the proof were also individually validated.
VAL_NONEXISTENT_NAME_NOCHAIN
No name was present and a valid proof of non-existence confirming the missing name was returned. The components of the proof were also identified to be trustworthy, but they were not individually validated.
VAL_NONEXISTENT_TYPE_NOCHAIN
No type exists for the name and a valid proof of non-existence confirming the missing name (NSEC or NSEC3 span) was returned. The components of the proof were also identified to be trustworthy, but they were not individually validated.
VAL_PINSECURE
The record or some ancestor of the record in the authentication chain towards the trust anchor was known to be provably insecure.
VAL_PINSECURE_UNTRUSTED
The record or some ancestor of the record in the authentication chain towards the trust anchor was known to be provably insecure. But the provably insecure condition was configured as untrustworthy.
VAL_BARE_RRSIG
No DNSSEC validation possible, query was for an RRSIG.
VAL_IGNORE_VALIDATION
Local policy was configured to ignore validation for the zone from which this data was received.
VAL_UNTRUSTED_ZONE
Local policy was configured to reject any data received from the given zone.
VAL_OOB_ANSWER
Answer was obtained using some Out Of Band method, such as a local configuration file.
VAL_BOGUS
Response could not be validated due to signature verification failures or the inability to verify proofs in the authentication chain.
VAL_DNS_ERROR
Some error was encountered during DNS processing.
VAL_INDETERMINATE
Response could not be validated due to missing DNSSEC meta-data.

REGISTRO (LOGGING)

libval proporciona la función val_log_add_optarg() para controlar la verbosidad y la ubicación de la salida de los mensajes de registro.

La función val_log_add_optarg() toma dos argumentos: el primer argumento, args, es un valor de cadena de caracteres que especifica la ubicación y la verbosidad. El segundo argumento, use_stderr, si se establece en un valor mayor que 0, permite que libval envíe mensajes de registro a stderr.

La cadena de caracteres que especifica la ubicación y la verbosidad del destino del registro tiene un formato específico:

<nivel-depuración>:<tipo-destino>[:<opciones-destino>]

donde
<nivel-depuración> es 1-7, para niveles crecientes de verbosidad
<tipo-destino> es uno de file, net, syslog, stderr, stdout
<opciones-destino> depende de <tipo-destino>
file:<nombre-archivo> (abierto en modo de añadir)
net[:<nombre-host>:<puerto-host>] (127.0.0.1:1053)
syslog[:facility] (0-23 (predeterminado 1 USER))

Los niveles de registro se pueden traducir aproximadamente en diferentes tipos de mensajes de registro de la siguiente manera (los mensajes devueltos para cada nivel en esta lista subsumen los mensajes devueltos para el nivel superior):

3 : Error   : error encontrado
4 : Advertencia : recuperándose de un error
5 : Noticia  : proporciona los resultados finales de validación para una consulta
              y detalles sobre archivos de política y etiquetas utilizadas
6 : Info
: da detalles sobre cadenas de autenticación 7 : Debug : da información de nivel de depuración

VALORES DE RETORNO

Los valores de retorno para varias funciones se dan a continuación. Estos valores se pueden mostrar en formato ASCII utilizando la función p_val_error().

VAL_NO_ERROR
No se encontró ningún error.
VAL_NOT_IMPLEMENTED
Funcionalidad aún no implementada.
VAL_RESOURCE_UNAVAILABLE
Algún recurso (posiblemente criptográfico) no estaba disponible. Actualmente no implementado.
VAL_BAD_ARGUMENT
Se pasaron argumentos incorrectos como parámetros.
VAL_INTERNAL_ERROR
Se encontró algún error interno.
VAL_NO_PERMISSION
No hay permiso para realizar la operación. Actualmente no implementado.
VAL_CONF_PARSE_ERROR
Error al analizar algún archivo de configuración.
VAL_CONF_NOT_FOUND
No se encontró un archivo de configuración.
VAL_NO_POLICY
El identificador de política al que se hacía referencia no era válido.

ARCHIVOS

La biblioteca del validador lee información de configuración de dos archivos: resolv.conf y dnsval.conf.

Consulte dnsval.conf(5) para obtener una descripción de la sintaxis de estos archivos.
