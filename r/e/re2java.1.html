NOMBRE

re2java - genera analizadores léxicos rápidos para Java

SINOPSIS

re2java [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para stdin.

INTRODUCCIÓN

re2java funciona como un preprocesador. Lee el archivo de entrada (que suele ser un programa en Java, pero puede ser cualquier cosa) y busca bloques de código encerrados en marcadores especiales de inicio/fin. El texto fuera de estos bloques se copia textualmente al archivo de salida. El contenido de los bloques es procesado por re2java. Los traduce a código en Java y genera el código resultante en lugar del bloque.

Aquí tienes un ejemplo de un pequeño programa que comprueba si una cadena dada contiene un número decimal:

// re2java $INPUT -o $OUTPUT
class Main {
    static boolean lex(String yyinput) {
        int yycursor = 0;
        /*!re2c
            re2c:YYCTYPE = "char";
            re2c:YYPEEK = "yyinput.charAt(yycursor)";
            re2c:yyfill:enable = 0;
            [1-9][0-9]* { return true; }
            *           { return false; }
        */
    }
    public static void main(String []args) {
        assert lex("1234\0");
    }
};

En la salida, re2java reemplazó el bloque central con el código generado:

// Generado por re2java
// re2java $INPUT -o $OUTPUT
class Main {
    static boolean lex(String yyinput) {
        int yycursor = 0;
{
    char yych = 0;
    int yystate = 0;
    yyl: while (true) {
        switch (yystate) {
            case 0:
                yych = yyinput.charAt(yycursor);
                yycursor += 1;
                switch (yych) {
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yystate = 2;
                        continue yyl;
                    default:
                        yystate = 1;
                        continue yyl;
                }
            case 1:
                { return false; }
            case 2:
                yych = yyinput.charAt(yycursor);
                switch (yych) {
                    case 0x30:
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yycursor += 1;
                        yystate = 2;
                        continue yyl;
                    default:
                        yystate = 3;
                        continue yyl;
                }
            case 3:
                { return true; }
            default:
                throw new IllegalStateException("internal lexer error");
        }
    }
}
    }
    public static void main(String []args) {
        assert lex("1234\0");
    }
};

BÁSICOS

Un programa re2java consiste en una secuencia de bloques intercalados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresion-regular ;
Una definición asocia nombre con expresion-regular. Los nombres pueden contener caracteres alfanuméricos y guión bajo. La sección expresiones regulares ofrece una visión general de la sintaxis de re2java para expresiones regulares. Una vez definida, el nombre puede usarse en otras expresiones regulares y en reglas. La recursión en definiciones con nombre no está permitida, y cada nombre debe definirse antes de usarse. Un bloque hereda definiciones con nombre del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuracion = valor ;
Una configuración permite cambiar el comportamiento de re2java y personalizar el código generado. Para una lista completa de configuraciones soportadas por re2java, consulta la sección de configuraciones. Dependiendo de una configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista en caracteres alfanuméricos. Un bloque hereda configuraciones del ámbito global y puede redefinirlas o añadir nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final.
expresion-regular codigo
Una regla asocia expresion-regular con su acción semántica (un bloque de código entre llaves, o un bloque de código que empieza con := y termina en una nueva línea seguida de cualquier carácter no blanco). Si la expresion-regular coincide, el código asociado se ejecuta. Si varias reglas coinciden, prevalece la coincidencia más larga. Si varias reglas coinciden con la misma cadena, prevalece la primera. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse, tiene la menor prioridad independientemente de su lugar en el bloque, y coincide con cualquier unidad de código (no necesariamente un carácter válido, ver la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para manejar el fin de entrada. Con condiciones de inicio, las reglas tienen una sintaxis más compleja.
!codigo_accion
Una acción asocia un bloque de código definido por el usuario a un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas asocian código a los estados finales). Ver la sección de acciones para una lista completa de acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias especiales predefinidas. Cada directiva tiene un propósito único. Ver la sección de directivas para más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (ambos estilos son soportados). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que permiten referenciarlos en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2java compila las expresiones regulares asociadas a cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se añaden al ámbito global y se vuelven visibles para los bloques subsiguientes. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera ningún código por sí mismo, ni añade definiciones al ámbito global; está pensado para ser reutilizado en otros bloques. Es una forma de compartir código (más detalles en la sección de bloques reutilizables). Antes de la versión 2.2 de re2java, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2java busca bloques de reglas con ese nombre. De lo contrario, se utiliza el bloque de reglas más reciente (ya sea nombrado o sin nombre). Un bloque de uso puede añadir definiciones, configuraciones y reglas propias, que se añaden a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2java, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular

Blocks

Blocks are used to configure the generated lexer. re2java processes a file from top to bottom, and for each block it checks if it has been enabled. Blocks can be enabled or disabled by specifying a comma-separated list of block names as an argument to the block's name. If the list is empty, all blocks are enabled.

/*!maxfill:re2c[:<name1>[:<name2>...]] ... */ or %{maxfill[:<name1>[:<name2>...]] ... %}
A block that generates YYMAXFILL definition (if the list is empty, all blocks are included). By default the generated code is a macro-definition for C (#define YYMAXFILL <n>), or a global variable for Go (var YYMAXFILL int = <n>). It can be customized with an optional configuration format that specifies a template string where @@{max} (or @@ for short) is replaced with the numeric value of YYMAXFILL.
/*!maxnmatch:re2c[:<name1>[:<name2>...]] ... */ or %{maxnmatch[:<name1>[:<name2>...]] ... %}
A block that generates YYMAXNMATCH definition (it requires -P --posix-captures option). An optional list of block names specifies which blocks should be included when computing YYMAXNMATCH value (if the list is empty, all blocks are included). By default the generated code is a macro-definition for C (#define YYMAXNMATCH <n>), or a global variable for Go (var YYMAXNMATCH int = <n>). It can be customized with an optional configuration format that specifies a template string where @@{max} (or @@ for short) is replaced with the numeric value of YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ or %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag variable generated by re2java. An optional list of block names specifies which blocks should be included when computing the set of tag variables (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag variable. Configuration separator specifies a piece of code used to join the generated format pieces for different tag variables.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ or %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag that is either explicitly mentioned by the rules (with --tags option) or implicitly generated by re2java (with --captvars or --posix-captvars options). An optional list of block names specifies which blocks should be included when computing the set of tags (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag. Configuration separator specifies a piece of code used to join the generated format pieces for different tags.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ or %{getstate[:<name1>[:<name2>...]] ... %}
A block that generates conditional dispatch on the lexer state (it requires --storable-state option). An optional list of block names specifies which blocks should be included in the state dispatch. The default transition goes to the start label of the first block on the list. If the list is empty, all blocks are included, and the default transition goes to the first block in the file that has a start label. This block type is incompatible with the --loop-switch option, as it requires cross-block transitions that are unsupported without goto or function calls.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ or %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
A block that generates condition enumeration (it requires --conditions option). An optional list of block names specifies which blocks should be included when computing the set of conditions (if the list is empty, all blocks are included). By default the generated code is an enumeration YYCONDTYPE. It can be customized with optional configurations format and separator. Configuration format specifies a template string where @@{cond} (or @@ for short) is replaced with the name of each condition, and @@{num} is replaced with a numeric index of that condition. Configuration separator specifies a piece of code used to join the generated format pieces for different conditions.
/*!include:re2c <file> */ or %{include <file> %}
This block allows one to include <file>, which must be a double-quoted file path. The contents of the file are literally substituted in place of the block, in the same way as #include works in C/C++. This block can be used together with the --depfile option to generate build system dependencies on the included files.
/*!header:re2c:on*/ or %{header:on %}
This block marks the start of header file. Everything after it and up to the following header:off block is processed by re2java and written to the header file specified with -t --type-header option.
/*!header:re2c:off*/ or %{header:off %}
This block marks the end of header file started with header:on*/ block.
/*!ignore:re2c ... */ or %{ignore ... %}
A block which contents are ignored and removed from the output file.

Configurations

Here is a full list of configurations supported by re2java:

re2c:api, re2c:input
Same as the --api option.
re2c:api:sigil
Specify the marker ("sigil") that is used for argument placeholders in the API primitives. The default is @@. A placeholder starts with sigil followed by the argument name in curly braces. For example, if sigil is set to $, then placeholders will have the form ${name}. Single-argument APIs may use shorthand notation without the name in braces. This option can be overridden by options for individual API primitives, e.g. re2c:YYFILL@len for YYFILL.
re2c:api:style
Specify API style. Possible values are functions (the default for C) and free-form (the default for Go and Rust). In functions style API primitives are generated with an argument list in parentheses following the name of the primitive. The arguments are provided only for autogenerated parameters (such as the number of characters passed to YYFILL), but not for the general lexer context, so the primitives behave more like macros in C/C++ or closures in Go and Rust. In free-form style API primitives do not have a fixed form: they should be defined as strings containing free-form pieces of code with interpolated variables of the form @@{var} or @@ (they correspond to arguments in function-like style). This configuration may be overridden for individual API primitives, see for example re2c:YYFILL:naked configuration for YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Same as the --bit-vectors option, but can be configured on per-block basis.
re2c:captures, re2c:leftmost-captures
Same as the --leftmost-captures option, but can be configured on per-block basis.
re2c:captvars, re2c:leftmost-captvars
Same as the --leftmost-captvars option, but can be configured on per-block basis.
re2c:case-insensitive, re2c:flags:case-insensitive
Same as the --case-insensitive option, but can be configured on per-block basis.
re2c:case-inverted, re2c:flags:case-inverted
Same as the --case-inverted option, but can be configured on per-block basis.
re2c:case-ranges, re2c:flags:case-ranges
Same as the --case-ranges option, but can be configured on per-block basis.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Same as the --computed-gotos option, but can be configured on per-block basis.
re2c:computed-gotos:relative, re2c:cgoto:relative
Same as the --computed-gotos-relative option, but can be configured on per-block basis.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
If computed goto is used, this configuration specifies the complexity threshold that triggers the generation of jump tables instead of nested if statements and bitmaps. The default value is 9.
re2c:cond:abort
If set to a positive integer value, the default case in the generated condition dispatch aborts program execution.
re2c:cond:goto
Specifies a piece of code used for the autogenerated shortcut rules :=> in conditions. The default is goto @@;. The @@ placeholder is substituted with condition name (see configurations re2c:api:sigil and re2c:cond:goto@cond).
re2c:cond:goto@cond
Specifies the sigil used for argument substitution in re2c:cond:goto definition. The default value is @@. Overrides the more generic re2c:api:sigil configuration.
re2c:cond:divider
Defines the divider for condition blocks. The default value is /* *************
********************** */. Los marcadores de posición son sustituidos con el nombre de la condición (ver re2c:api;sigil y re2c:cond:divider@cond).
re2c:cond:divider@cond
Especifica el sigilo utilizado para la sustitución de argumentos en la definición de re2c:cond:divider. El valor por defecto es @@. Anula la configuración más genérica re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Especifica el prefijo utilizado para las etiquetas de condición. El valor por defecto es yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Especifica el prefijo utilizado para los identificadores de condición. El valor por defecto es yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d
Igual que la opción --debug-output, pero puede configurarse por bloque.
re2c:empty-class, re2c:flags:empty-class
Igual que la opción --empty-class, pero puede configurarse por bloque.
re2c:encoding:ebcdic, re2c:flags:ecb, re2c:flags:e
Igual que la opción --ebcdic, pero puede configurarse por bloque.
re2c:encoding:ucs2, re2c:flags:wide-chars, re2c:flags:w
Igual que la opción --ucs2, pero puede configurarse por bloque.
re2c:encoding:utf8, re2c:flags:utf-8, re2c:flags:8
Igual que la opción --utf8, pero puede configurarse por bloque.
re2c:encoding:utf16, re2c:flags:utf-16, re2c:flags:x
Igual que la opción --utf16, pero puede configurarse por bloque.
re2c:encoding:utf32, re2c:flags:unicode, re2c:flags:u
Igual que la opción --utf32, pero puede configurarse por bloque.
re2c:encoding-policy, re2c:flags:encoding-policy
Igual que la opción --encoding-policy, pero puede configurarse por bloque.
re2c:eof
Especifica el símbolo centinela utilizado con la regla de fin de entrada $. El valor por defecto es -1 (la regla $ no se utiliza). Otros valores posibles incluyen todas las unidades de código válidas. Solo se reconocen números decimales.
re2c:header, re2c:flags:type-header, re2c:flags:t
Especifica el nombre del archivo de cabecera generado en relación con el directorio del archivo de salida. Igual que la opción --header excepto que la ruta del archivo es relativa.
re2c:indent:string
Especifica la cadena utilizada para la indentación. El valor por defecto es un solo carácter de tabulación "\t". La cadena de indentación debe contener solo caracteres de espacio en blanco. Para deshabilitar la indentación por completo, establezca esta configuración a una cadena vacía.
re2c:indent:top
Especifica la cantidad mínima de indentación a utilizar. El valor por defecto es cero. El valor debe ser un número entero no negativo.
re2c:invert-captures
Igual que la opción --invert-captures, pero puede configurarse por bloque.
re2c:label:prefix, re2c:labelprefix
Especifica el prefijo utilizado para las etiquetas de estado del DFA. El valor por defecto es yy.
re2c:label:start, re2c:startlabel
Controla la generación de una etiqueta de inicio de bloque. El valor por defecto es cero, lo que significa que la etiqueta de inicio solo se genera si se utiliza. Un valor entero mayor que cero fuerza la generación de la etiqueta de inicio incluso si no es utilizada por el lexer. Un valor de cadena también fuerza la generación de la etiqueta de inicio y establece el nombre de la etiqueta a la cadena especificada. Esta configuración se aplica solo al bloque actual (se restablece a su valor predeterminado para el siguiente bloque).
re2c:label:yyFillLabel
Especifica el prefijo de las etiquetas YYFILL utilizadas con re2c:eof y en el modo de estado almacenable.
re2c:label:yyloop
Especifica el nombre de la etiqueta que marca el inicio del bucle del lexer con la opción --loop-switch. El valor por defecto es yyloop.
re2c:label:yyNext
Especifica el nombre de la etiqueta opcional que sigue al `switch` YYGETSTATE en el modo de estado almacenable (habilitado con re2c:state:nextlabel). El valor por defecto es yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsoleto (ver la opción obsoleta --no-lookahead).
re2c:monadic
Si se establece a un valor distinto de cero, el lexer generado utilizará notación monádica (esta configuración es específica de Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Igual que la opción --nested-ifs, pero puede configurarse por bloque.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Igual que la opción --posix-captures, pero puede configurarse por bloque.
re2c:posix-captvars
Igual que la opción --posix-captvars, pero puede configurarse por bloque.
re2c:tags, re2c:flags:tags, re2c:flags:T
Igual que la opción --tags, pero puede configurarse por bloque.
re2c:tags:expression
Especifica la expresión utilizada para las variables de etiqueta. Por defecto, re2java genera expresiones de la forma yyt<N>. Esto puede ser inconveniente, por ejemplo, si las variables de etiqueta se definen como campos en una estructura. Todas las ocurrencias de @@{tag} o @@ se reemplazan con el nombre de etiqueta real. Por ejemplo, re2c:tags:expression = "s.@@"; da como resultado expresiones de la forma s.yyt<N> en el código generado. Ver también la configuración re2c:api:sigil.
re2c:tags:negative
Especifica la expresión constante que se utiliza para el valor negativo de la etiqueta (típicamente sería -1 si las etiquetas son desplazamientos enteros en la cadena de entrada, o un puntero nulo si son punteros).
re2c:tags:prefix
Especifica el prefijo para los nombres de variables de etiqueta. El valor por defecto es yyt.
re2c:sentinel
Especifica el símbolo centinela utilizado para las comprobaciones de fin de entrada (cuando las comprobaciones de límites están deshabilitadas con re2c:yyfill:enable = 0; y re2c:eof no está establecido). Esta configuración no afecta la generación de código: su propósito es verificar que el centinela no está permitido en medio de una regla, y asegurar que el lexer no leerá más allá del final del búfer. El valor por defecto es -1` (en ese caso, re2java asume que el centinela es cero, que es el caso más común). Solo se reconocen números decimales.
re2c:state:abort
Si se establece a un valor entero positivo, el caso por defecto en la distribución de estado generada abortará la ejecución del programa, y un caso explícito -1 contendrá la transición al inicio del bloque.
re2c:state:nextlabel
Controla si el `switch` YYGETSTATE va seguido de una etiqueta yyNext (el valor por defecto es cero, que corresponde a ninguna etiqueta). Alternativamente, se puede usar re2c:label:start para generar una etiqueta de inicio específica, o un bloque explícito getstate para generar el `switch` YYGETSTATE por separado del bloque lexer.
re2c:unsafe, re2c:flags:unsafe
Igual que la opción --no-unsafe, pero puede configurarse por bloque. Si se establece a cero, suprime la generación de envoltorios unsafe alrededor de YYPEEK. El valor por defecto es distinto de cero (se generan envoltorios). Esta configuración es específica de Rust.

Define el primitivo de API genérico YYBACKUP.

Define el primitivo de API genérico YYBACKUPCTX.

Define el primitivo de API YYCONDTYPE.

Define el primitivo de API YYCTYPE.

Expresiones regulares

re2java utiliza la siguiente sintaxis para expresiones regulares:

"foo"
Literal de cadena sensible a mayúsculas y minúsculas.
'foo'
Literal de cadena insensible a mayúsculas y minúsculas.
[a-xyz], [^a-xyz]
Clase de caracteres (posiblemente negada).
.
Cualquier carácter excepto salto de línea.
R \ S
Diferencia de clases de caracteres R y S.
R*
Cero o más ocurrencias de R.
R+
Una o más ocurrencias de R.
R?
Opcional R.
R{n}
Repetición de R exactamente n veces.
R{n,}
Repetición de R al menos n veces.
R{n,m}
Repetición de R de n a m veces.
(R)
Solo R; los paréntesis se utilizan para anular la precedencia. Si la extracción de subcoincidencias está habilitada, (R) es un grupo de captura o no de captura, dependiendo de la opción --invert-captures.
(!R)
Si la extracción de subcoincidencias está habilitada, (!R) es un grupo sin captura o de captura, dependiendo de la opción --invert-captures.
R S
Concatenación: R seguido de S.
R | S
Alternativa: R o S.
R / S
Lookahead: R seguido de S, pero S no se consume.
name
Expresión regular definida como name (o cadena literal "name" en modo de compatibilidad con Flex).
{name}
Expresión regular definida como name en modo de compatibilidad con Flex.
@stag
Una etiqueta s: guarda la última posición de entrada en la que coincide @stag en una variable llamada stag.
#mtag
Una etiqueta m: guarda todas las posiciones de entrada en las que coincide #mtag en una variable llamada mtag.

Las clases de caracteres y los literales de cadena pueden contener las siguientes secuencias de escape: \a, \b, \f, \n, \r, \t, \v, \\, escapes octales \ooo y escapes hexadecimales \xhh, \uhhhh y \Uhhhhhhhh.

Acciones

Aquí tienes una lista de acciones predefinidas compatibles con re2java:

!entry code
La acción de entrada vincula un bloque de código definido por el usuario al estado de inicio del autómata finito actual. Si se utilizan condiciones de inicio, la acción de entrada se puede establecer individualmente para cada condición. Esta acción se puede utilizar para realizar inicializaciones, por ejemplo, para guardar la ubicación de inicio de un lexema.
!pre_rule code
La acción pre-regla antepone un bloque de código definido por el usuario a las acciones semánticas de todas las reglas del bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para factorizar la parte común de todas las acciones semánticas (por ejemplo, guardar la ubicación final de un lexema).
!post_rule code
La acción post-regla añade un bloque de código definido por el usuario a las acciones semánticas de todas las reglas del bloque actual (o condición, si se utilizan condiciones de inicio). Esta acción se puede utilizar para emitir sentencias de trampa que protejan contra flujos de control no intencionados.

Directivas

Aquí tienes una lista completa de las directivas compatibles con re2java:

!use:name ;
Una directiva `use` dentro de un bloque que fusiona un bloque de reglas definido previamente con el nombre especificado en el bloque actual. Las definiciones nombradas, las configuraciones y las reglas del bloque referenciado se añaden a las actuales. Los conflictos entre reglas y configuraciones superpuestas se resuelven de la forma habitual: la primera regla tiene prioridad y la última configuración anula las precedentes. Una excepción son las reglas especiales *, $ y <!> para las cuales una definición local del bloque siempre tiene prioridad. Una directiva `use` se puede colocar en cualquier lugar dentro de un bloque, y se permiten múltiples directivas `use`.
!include file ;
Esta directiva es igual que el bloque include: inserta el contenido del archivo literalmente en lugar de la directiva.

Interfaz de programa

El código generado interactúa con el programa externo mediante primitivas, denominadas colectivamente API. Qué primitivas deben definirse para un programa particular depende de múltiples factores, incluyendo la complejidad de las expresiones regulares, la representación de entrada, el búfer y el uso de varias características. Todas las primitivas necesarias deben ser definidas por el usuario en forma de macros, funciones, variables o cualquier otra forma adecuada que haga que el código generado sea sintáctica y semánticamente correcto. re2java no comprueba (y no puede comprobar) las definiciones, por lo que si falta algo o está definido incorrectamente, el programa generado puede tener errores de compilación o de ejecución. Este manual proporciona ejemplos de definiciones de API en los casos más comunes.

re2java tiene tres estilos de API que definen el conjunto principal de primitivas utilizadas por un programa:

API Simple
Esta es la API por defecto para el backend de Java. Consiste en las siguientes primitivas: YYINPUT (que debe definirse como una secuencia de unidades de código, por ejemplo, una cadena) y YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (que deben definirse como índices en YYINPUT).
API de Registro
La API de registro es útil en los casos en que el estado del lexer debe almacenarse en una clase. Se habilita con la opción --api record o la configuración re2c:api = record. Esta API consiste en una variable yyrecord (el nombre se puede anular con re2c:yyrecord) que debe definirse como una clase con los campos yyinput, yycursor, yymarker, yyctxmarker, yylimit (solo los campos utilizados por el código generado deben definirse, y sus nombres se pueden configurar).
API Genérica
Esta es la API más flexible. Se habilita con la opción --api generic o la configuración re2c:api = generic. Contiene primitivas para operaciones genéricas: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Aquí tienes una lista completa de las primitivas de API que pueden ser utilizadas por el código generado para interactuar con el programa externo.

YYCTYPE
El tipo de los caracteres de entrada (unidades de código). Para codificaciones ASCII, EBCDIC y UTF-8, debe ser un entero sin signo de 1 byte. Para UTF-16 o UCS-2, debe ser un entero sin signo de 2 bytes. Para UTF-32, debe ser un entero sin signo de 4 bytes.
YYCURSOR
Un valor l que almacena la posición actual de entrada (un puntero o un desplazamiento entero en YYINPUT). Inicialmente, YYCURSOR debe apuntar al primer carácter de entrada y, posteriormente, es avanzado por el código generado. Cuando una regla coincide, la posición de YYCURSOR es la posterior al último carácter coincidente.
YYLIMIT
Un valor r que almacena la posición final de la entrada (un puntero o un desplazamiento entero en YYINPUT). Inicialmente, YYLIMIT debe apuntar a la posición posterior al último carácter de entrada disponible. No es modificado por el código generado. El lexer compara YYCURSOR con YYLIMIT para determinar si quedan suficientes caracteres de entrada.
YYMARKER
Un valor l que almacena la posición de la última regla coincidente (un puntero o un desplazamiento entero en YYINPUT). Se utiliza para restaurar la posición de YYCURSOR si la coincidencia más larga falla y el lexer necesita retroceder. No se necesita inicialización.
YYCTXMARKER
Un valor l que almacena la posición del contexto de cola (un puntero o un desplazamiento entero en YYINPUT). No se necesita inicialización. YYCTXMARKER solo es necesario si se utiliza el operador de lookahead /.
YYFILL
Una primitiva de API genérica con una variable len. YYFILL debe proporcionar al menos len caracteres de entrada más o fallar. Si se utiliza re2c:eof, entonces len es siempre 1 y YYFILL siempre debe devolver el control a la función llamante; un valor de retorno cero indica s. If re2c:eof no se usa, el valor de retorno de YYFILL se ignora y no debe retornar en caso de fallo. El valor máximo de len es YYMAXFILL.
YYFN
Una primitiva que define el prototipo de función en el modelo de código --recursive-functions. Su valor debe ser un array de una o más cadenas, donde cada cadena contiene dos o tres componentes separados por la cadena especificada en la configuración re2c:fn:sep (típicamente un punto y coma). El primer elemento del array define el nombre de la función y el tipo de retorno (vacío para una función void). Los elementos subsiguientes definen los argumentos de la función: primero, la expresión para el argumento utilizada en el cuerpo de la función (generalmente solo un nombre); segundo, el tipo del argumento; tercero, un parámetro formal opcional (por defecto es el primer componente, generalmente tanto el argumento como el parámetro son el mismo identificador).
YYINPUT
Un r-valor que almacena la secuencia de caracteres de entrada actual (cadena, búfer, etc.).
YYMAXFILL
Una constante entera igual al valor máximo del argumento para YYFILL. Puede ser generada con un bloque max.
YYLESSTHAN
Una primitiva genérica de API con una variable len. Debe definirse como un r-valor de tipo booleano que sea true si y solo si quedan menos de len caracteres de entrada.
YYPEEK
Una primitiva genérica de API sin variables. Debe definirse como un r-valor de tipo YYCTYPE que sea igual al carácter en la posición de entrada actual.
YYSKIP
Una primitiva genérica de API que debe avanzar la posición de entrada actual en una unidad de código.
YYBACKUP
Una primitiva genérica de API que debe guardar la posición de entrada actual (para ser restaurada más tarde con YYRESTORE).
YYRESTORE
Una primitiva genérica de API que debe restaurar la posición de entrada actual al valor guardado por YYBACKUP.
YYBACKUPCTX
Una primitiva genérica de API que debe guardar la posición de entrada actual como la posición del contexto final (para ser restaurada más tarde con YYRESTORECTX).
YYRESTORECTX
Una primitiva genérica de API que debe restaurar la posición del contexto final guardada con YYBACKUPCTX.
YYRESTORETAG
Una primitiva genérica de API con una variable tag que debe restaurar la posición del contexto final al valor de tag.
YYSTAGP
Una primitiva genérica de API con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para detalles). YYSTAGP debe establecer tag a la posición de entrada actual.
YYSTAGN
Una primitiva genérica de API con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para detalles). YYSTAGN debe establecer tag a un valor que represente una posición de entrada inexistente.
YYMTAGP
Una primitiva genérica de API con una variable tag. YYMTAGP debe añadir la posición actual al historial de subcoincidencias de tag (ver sección de extracción de subcoincidencias para detalles).
YYMTAGN
Una primitiva genérica de API con una variable tag. YYMTAGN debe añadir un valor que represente una posición de entrada inexistente al historial de subcoincidencias de tag (ver sección de extracción de subcoincidencias para detalles).
YYSHIFT
Una primitiva genérica de API con una variable shift que debe desplazar la posición de entrada actual en shift caracteres (el valor de desplazamiento puede ser negativo).
YYCOPYSTAG
Una primitiva genérica de API con dos variables, lhs y rhs, que debe copiar la variable s-tag del lado derecho rhs a la variable s-tag del lado izquierdo lhs. Para la mayoría de los lenguajes, esta primitiva tiene una definición por defecto que asigna lhs a rhs.
YYCOPYMTAG
Una primitiva genérica de API con dos variables, lhs y rhs, que debe copiar la variable m-tag del lado derecho rhs a la variable m-tag del lado izquierdo lhs. Para la mayoría de los lenguajes, esta primitiva tiene una definición por defecto que asigna lhs a rhs.
YYSHIFTSTAG
Una primitiva genérica de API con dos variables, tag y shift, que debe desplazar tag en shift unidades de código (el valor de desplazamiento puede ser negativo).
YYSHIFTMTAG
Una primitiva genérica de API con dos variables, tag y shift, que debe desplazar el último valor en el historial de tag en shift unidades de código (el valor de desplazamiento puede ser negativo).
YYMAXNMATCH
Una constante entera igual al número máximo de grupos de captura POSIX en una regla. Se genera con un bloque maxnmatch.
YYCONDTYPE
El tipo del enum de condición. Puede ser generado ya sea con un bloque conditions o con la opción --header.
YYGETACCEPT
Una primitiva con una variable var que almacena el selector numérico de la regla aceptada. Para la mayoría de los lenguajes, esta primitiva tiene una definición por defecto que lee de var.
YYSETACCEPT
Una primitiva con dos variables: var (un l-valor que almacena el selector numérico de la regla aceptada) y val (el valor del selector). Para la mayoría de los lenguajes, esta primitiva tiene una definición por defecto que asigna var a val.
YYGETCOND
Un r-valor de tipo YYCONDTYPE que es igual al identificador de condición actual.
YYSETCOND
Una primitiva con una variable cond que debe establecer el identificador de condición actual a cond.
YYGETSTATE
Un r-valor de tipo entero que es igual al estado actual del analizador léxico. Debe inicializarse a -1.
YYSETSTATE
Una primitiva con una variable state que debe establecer el estado actual del analizador léxico a state.
YYDEBUG
Esta primitiva solo se genera con la opción -d, --debug-output. Su propósito es agregar registro al código generado (la definición típica de YYDEBUG es una instrucción de impresión). Las instrucciones YYDEBUG se generan en cada estado y tienen dos variables: state (ya sea un índice de estado DFA o -1) y symbol (el símbolo de entrada actual).
yyaccept
Un l-valor de tipo entero sin signo que almacena el número de la última regla coincidente. La definición del usuario solo es necesaria con la opción --storable-state.
yybm
Una tabla que contiene mapas de bits comprimidos para hasta 8 transiciones (se usa con la opción --bitmaps). La tabla contiene 256 elementos y se indexa por unidades de código de 1 byte. Cada elemento de 8 bits combina valores booleanos para hasta 8 transiciones. El k-ésimo bit del n-ésimo elemento es verdadero si y solo si la n-ésima unidad de código está en el rango de la k-ésima transición. La idea de este mapa de bits es reemplazar muchas ramas de if o casos de switch con una única verificación de un solo bit en la tabla.
yych
Un l-valor de tipo YYCTYPE que almacena el carácter de entrada actual. La definición del usuario solo es necesaria con la opción -f --storable-state.
yyctable
Tabla de saltos generada para la distribución de la condición inicial (habilitada con la combinación de las opciones --conditions y --computed-gotos).
yyfill
Un l-valor que almacena el resultado de la llamada YYFILL (esto puede ser necesario para lenguajes puramente funcionales, donde YYFILL es una función monádica con un valor de retorno complejo).
yynmatch
Un l-valor de tipo entero sin signo que almacena el número de grupos de captura POSIX en la regla coincidente. Se usa solo con la opción -P --posix-captures.
yypmatch
Un array de l-valores que se utilizan para mantener los valores de las etiquetas correspondientes a los paréntesis de captura en la regla coincidente. La longitud del array debe ser al menos yynmatch * 2 (generalmente YYMAXNMATCH * 2 es una buena opción). Se usa solo con la opción -P --posix-captures.
yystable
Obsoleto.
yystate
Un l-valor utilizado con la opción --loop-switch para almacenar el estado actual del DFA.
yytarget
Tabla de saltos que contiene los destinos de salto (direcciones de etiquetas) para todas las transiciones desde un estado. Esta tabla es local a cada estado. La generación de tablas yytarget se habilita con la opción --computed-gotos.

Archivos de sintaxis

El soporte para diferentes lenguajes en re2c se basa en la idea de archivos de sintaxis. Un archivo de sintaxis es un archivo de configuración que define la sintaxis del lenguaje de destino -- no todo el lenguaje, sino una pequeña parte de él que es utilizada por el código generado. Los archivos de sintaxis hacen que re2c sea muy flexible, pero no deben usarse como reemplazo de las configuraciones re2c:: su propósito es definir la sintaxis del lenguaje de destino, no personalizar un analizador léxico particular. Todos los lenguajes soportados tienen archivos de sintaxis predeterminados que forman parte de la distribución (ver el subdirectorio include/syntax); también están incrustados en el binario re2java. Los usuarios pueden proporcionar un archivo de sintaxis personalizado que anule algunas configuraciones para uno de los lenguajes soportados, o pueden optar por redefinir todas las configuraciones (en ese caso se debe usar la opción --lang none). Los archivos de sintaxis contienen configuraciones de cuatro tipos diferentes: listas de características, configuraciones de lenguaje, configuraciones "in-place" y plantillas de código.

Plantillas de código

Las plantillas de código definen la sintaxis del lenguaje de destino. Están escritas en un lenguaje de dominio específico simple con la siguiente gramática formal: 
plantilla-código ::
      nombre '=' expresiones-código ';'
    | PLANTILLA_CODIGO ';'
    | '<undefined>' ';'
expresiones-código ::
      <VACIO>
    | expresiones-código expresion-código
expresion-código ::
      CADENA
    | VARIABLE
    | opcional
    | lista
opcional ::
      '(' CONDICIONAL '?' expresiones-código ')'
    | '(' CONDICIONAL '?' expresiones-código ':' expresiones-código ')'
lista ::
      '[' VARIABLE ':' expresiones-código ']'
    | '[' VARIABLE '{' NUMERO '}' ':' expresiones-código ']'
    | '[' VARIABLE '{' NUMERO ',' NUMERO '}' ':' expresiones-código ']

Una plantilla de código es una secuencia de literales de cadena, variables, elementos opcionales y listas, o una referencia a otra plantilla de código, o un valor especial <undefined>. Las variables son marcadores de posición que se sustituyen durante la fase de generación de código. Las variables de lista son especiales: al expandir plantillas de lista, re2java repite las expresiones del lado derecho de la columna varias veces, sustituyendo en cada repetición las ocurrencias de la variable de lista por un valor específico para esa repetición. Las listas tienen límites opcionales (los valores negativos se cuentan desde el final, por ejemplo, -1 significa el último elemento). Los nombres condicionales comienzan con un punto. Tanto los condicionales como las variables pueden ser locales (específicos de la plantilla de código dada) o globales (permitidos en todas las plantillas de código). Cuando re2java lee el archivo de sintaxis, verifica que cada plantilla de código utilice solo las variables y condicionales que están permitidos en ella.

Por ejemplo, la siguiente plantilla de código define la estructura de if-then-else para un lenguaje similar a C:

code:if_then_else =
    [branch{0}: topindent "if " cond " {\n"
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {\n"
        indent [stmt: stmt] dedent]
    topindent "}\n";

Aquí branch es una variable de lista: branch{0} se expande a la primera rama (que es especial, ya que no hay parte else), branch{1:-1} se expande a todas las ramas restantes (si las hay). stmt es también una variable de lista: [stmt: stmt] es una lista anidada que se expande a una lista de sentencias en el cuerpo de la rama actual. topindent, indent, dedent y nl son variables globales, y .cond es un condicional local (su significado se describe a continuación). Esta plantilla de código podría producir el siguiente código:

if x {
    // hacer algo
} else if y {
    // hacer otra cosa
} else {
    // no hacer nada
}

HANDLING THE END OF INPUT

One of the main problems for the lexer is to know when to stop. There are a few terminating conditions:

  • the lexer may match some rule (including default rule *) and come to a final state
  • the lexer may fail to match any rule and come to a default state
  • the lexer may reach the end of input

The first two conditions terminate the lexer in a "natural" way: it comes to a state with no outgoing transitions, and the matching automatically stops. The third condition, end of input, is different: it may happen in any state, and the lexer should be able to handle it. Checking for the end of input interrupts the normal lexer workflow and adds conditional branches to the generated program, therefore it is necessary to minimize the number of such checks. re2java supports a few different methods for handling the end of input. Which one to use depends on the complexity of regular expressions, the need for buffering, performance considerations and other factors. Here is a list of methods:

  • Sentinel. This method eliminates the need for the end of input checks altogether. It is simple and efficient, but limited to the case when there is a natural "sentinel" character that can never occur in valid input. This character may still occur in invalid input, but it should not be allowed by the regular expressions, except perhaps as the last character of a rule. The sentinel is appended at the end of input and serves as a stop signal: when the lexer reads this character, it is either a syntax error or the end of input. In both cases the lexer should stop. This method is used if YYFILL is disabled with re2c:yyfill:enable = 0; and re2c:eof has the default value -1.
  • Sentinel with bounds checks. This method is generic: it allows one to handle any input without restrictions on the regular expressions. The idea is to reduce the number of end of input checks by performing them only on certain characters. Similar to the "sentinel" method, one of the characters is chosen as a "sentinel" and appended at the end of input. However, there is no restriction on where the sentinel may occur (in fact, any character can be chosen for a sentinel). When the lexer reads this character, it additionally performs a bounds check. If the current position is within bounds, the lexer resumes matching and handles the sentinel as a regular character. Otherwise it invokes YYFILL (unless it is disabled). If more input is supplied, the lexer will rematch the last character and continue as if the sentinel wasn't there. Otherwise it must be the real end of input, and the lexer stops. This method is used when re2c:eof has non-negative value (it should be set to the numeric value of the sentinel). YYFILL is optional.
  • Bounds checks with padding. This method is generic, and it may be faster than the "sentinel with bounds checks" method, but it is also more complex. The idea is to partition DFA states into strongly connected components (SCCs) and generate a single check per SCC for enough characters to cover the longest non-looping path in this SCC. This reduces the number of checks, but there is a problem with short lexemes at the end of input, as the check requires enough characters to cover the longest lexeme. This can be fixed by padding the input with a few fake characters that do not form a valid lexeme suffix (so that the lexer cannot match them). The length of padding should be YYMAXFILL, generated with a max block. If there is not enough input, the lexer invokes YYFILL which should supply at least the required number of characters or not return. This method is used if YYFILL is enabled and re2c:eof is -1 (this is the default configuration).
  • Custom checks. Generic API allows one to override basic operations like reading a character, which makes it possible to include the end-of-input checks as part of them. This approach is error-prone and should be used with caution. To use a custom method, enable generic API with --api custom or re2c:api = custom; and disable default bounds checks with re2c:yyfill:enable = 0; or re2c:yyfill:check = 0;.

The following subsections contain an example of each method.

Sentinel

This example uses a sentinel character to handle the end of input. The program counts space-separated words in a null-terminated string. The sentinel is null: it is the last character of each input string, and it is not allowed in the middle of a lexeme by any of the rules (in particular, it is not included in character ranges where it is easy to overlook). If a null occurs in the middle of a string, it is a syntax error and the lexer will match default rule *, but it won't read past the end of input or crash (use -Wsentinel-in-midrule warning and re2c:sentinel configuration to verify this). Configuration re2c:yyfill:enable = 0; suppresses the generation of bounds checks and YYFILL invocations.

// re2java $INPUT -o $OUTPUT
class Main {
    // Expects a null-terminated string.
    static int lex(String yyinput) {
        int yycursor = 0;
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:YYCTYPE = "char";
                re2c:YYPEEK = "yyinput.charAt(yycursor)";
                re2c:yyfill:enable = 0;
                *      { return -1; }
                [\x00] { return count; }
                [a-z]+ { count += 1; continue loop; }
                [ ]+   { continue loop; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("\0") == 0;
        assert lex("one two three\0") == 3;
        assert lex("f0ur\0") == -1;
    }
};

Sentinel with bounds checks

This example uses sentinel with bounds checks to handle the end of input (this method was added in version 1.2). The program counts space-separated single-quoted strings. The sentinel character is null, which is specified with re2c:eof = 0; configuration. As in the sentinel method, null is the last character of each input string, but it is allowed in the middle of a rule (for example, 'aaa\0aa'\0 is valid input, but 'aaa\0 is a syntax error). Bounds checks are generated in each state that matches an input character, but they are scoped to the branch that handles null. Bounds checks are of the form YYLIMIT <= YYCURSOR or YYLESSTHAN(1) with generic API. If the check condition is true, lexer has reached the end of input and should stop (YYFILL is disabled with re2c:yyfill:enable = 0; as the input fits into one buffer, see the YYFILL with sentinel section for an example that uses YYFILL). Reaching the end of input opens three possibilities: if the lexer is in the initial state it will match the end-of-input rule $, otherwise it may fallback to a previously matched rule (including default rule *) or go to a d

de estado predeterminado, causando -Wundefined-control-flow.

// re2java $INPUT -o $OUTPUT
class Main {
    // Espera una cadena terminada en nulo.
    static int lex(String yyinput) {
        int yycursor = 0;
        int yymarker = 0;
        int yylimit = yyinput.length() - 1; // yylimit apunta al nulo terminador
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:YYCTYPE = "char";
                re2c:YYPEEK = "yyinput.charAt(yycursor)";
                re2c:yyfill:enable = 0;
                re2c:eof = 0;
                str = ['] ([^'\\] | [\\][^])* ['];
                *    { return -1; }
                $    { return count; }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("\0") == 0;
        assert lex("'qu\0tes' 'are' 'fine: \\'' \0") == 3;
        assert lex("'unterminated\\'\0") == -1;
    }
};

Comprobaciones de límites con relleno

Este ejemplo utiliza comprobaciones de límites con relleno para manejar el final de la entrada (este método está habilitado por defecto). El programa cuenta cadenas entre comillas simples separadas por espacios. Hay un relleno de YYMAXFILL caracteres nulos añadidos al final de la entrada, donde el valor de YYMAXFILL se genera automáticamente con un bloque max. No es necesario usar nulos para el relleno; se pueden usar cualquier carácter siempre que no formen un sufijo de lexema válido (en este ejemplo, el relleno no debe contener comillas simples, ya que podrían confundirse con el sufijo de una cadena entre comillas simples). Hay una regla de "parada" que coincide con el primer carácter de relleno (nulo) y termina el lexer (tenga en cuenta que comprueba si el nulo está al principio del relleno, de lo contrario, es un error de sintaxis). Las comprobaciones de límites solo se generan en algunos estados determinados por los componentes fuertemente conectados del autómata subyacente. Las comprobaciones tienen la forma (YYLIMIT - YYCURSOR) < n o YYLESSTHAN(n) con la API genérica, donde n es el número mínimo de caracteres necesarios para que el lexer continúe (esto también significa que la próxima comprobación de límites ocurrirá en como máximo n caracteres). Si la condición de comprobación es verdadera, el lexer ha llegado al final de la entrada e invocará YYFILL(n) que debe suministrar al menos n caracteres de entrada o no retornar. En este ejemplo, YYFILL siempre falla y termina el lexer con un error (lo cual está bien porque la entrada cabe en un solo búfer). Consulte la sección YYFILL con relleno para ver un ejemplo que rellena el búfer de entrada con YYFILL.

// re2java $INPUT -o $OUTPUT
class Main {
    /*!max:re2c*/
    // Espera una cadena con relleno yymaxfill.
    static int lex(String str) {
        // Rellena la cadena con ceros yymaxfill al final.
        byte[] yyinput = new byte[str.length() + YYMAXFILL];
        System.arraycopy(str.getBytes(), 0, yyinput, 0, str.length()); 
        int yycursor = 0;
        int yylimit = yyinput.length;
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyinput[yycursor]";
                re2c:YYFILL = "return -1;";
                str = ['] ([^'\\] | [\\][^])* ['];
                [\x00] {
                    // Comprueba que sea el centinela, no un nulo inesperado.
                    return (yycursor - 1 == str.length()) ? count : -1;
                }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
                *    { return -1; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("") == 0;
        assert lex("'qu\0tes' 'are' 'fine: \\'' ") == 3;
        assert lex("'unterminated\\'") == -1;
        assert lex("'unexpected \00 null\\'") == -1;
    }
};

Comprobaciones personalizadas

Este ejemplo utiliza un método personalizado de manejo de fin de entrada basado en la API genérica. El programa cuenta cadenas entre comillas simples separadas por espacios. Es lo mismo que el ejemplo de centinela, excepto que la entrada no está terminada en nulo. Para compensar la ausencia de un carácter centinela al final de la entrada, se redifine YYPEEK para realizar una comprobación de límites antes de leer el siguiente carácter de entrada. Esto es ineficiente porque las comprobaciones se realizan con mucha frecuencia. Si la condición de comprobación falla, YYPEEK devuelve el carácter real, de lo contrario, devuelve un carácter centinela falso.

// re2java $INPUT -o $OUTPUT
class Main {
    // Espera una cadena sin nulo terminador.
    static int lex(String str) {
        byte[] yyinput = str.getBytes();
        int yycursor = 0;
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:api = generic;
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "(yycursor < yyinput.length) ? yyinput[yycursor] : 0";
                re2c:YYSKIP = "yycursor += 1;";
                re2c:yyfill:enable = 0;
                *      { return -1; }
                [\x00] { return count; }
                [a-z]+ { count += 1; continue loop; }
                [ ]+   { continue loop; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("") == 0;
        assert lex("one two three") == 3;
        assert lex("f0ur") == -1;
    }
};

RELLENO DE BÚFER

La necesidad de búfer surge cuando la entrada no se puede asignar en memoria de una vez: o es demasiado grande o proviene de forma secuencial (como leer de un socket). La técnica habitual en tales casos es asignar un búfer de memoria de tamaño fijo y procesar la entrada en fragmentos que caben en el búfer. Cuando se procesa el fragmento actual, se extrae y se introduce nueva información. En la práctica, es algo más complejo, ya que el estado del lexer no consiste en una única posición de entrada, sino en un conjunto de posiciones interrelacionadas:

  • cursor: el siguiente carácter de entrada a leer (YYCURSOR en la API de punteros C o YYSKIP/YYPEEK en la API genérica)
  • límite: la posición después del último carácter de entrada disponible (YYLIMIT en la API de punteros C, manejado implícitamente por YYLESSTHAN en la API genérica)
  • marcador: la posición de la coincidencia más reciente, si la hay (YYMARKER en la API predeterminada o YYBACKUP/YYRESTORE en la API genérica)
  • token: el inicio del lexema actual (implícito en la API de re2java, ya que no es necesario para la operación normal del lexer y puede ser definido y actualizado por el usuario)
  • marcador de contexto: la posición del contexto de cola (YYCTXMARKER en la API de punteros C o YYBACKUPCTX/YYRESTORECTX en la API genérica)
  • variables de etiqueta: posiciones de subcoincidencia (definidas con bloques stags y mtags y primitivas de API genérica YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

No todos se utilizan en todos los casos, pero si se usan, deben ser actualizados por YYFILL. Todas las posiciones activas están contenidas en el segmento entre el token y el cursor, por lo tanto, todo lo que esté entre el inicio del búfer y el token puede ser descartado, el segmento desde el token hasta el límite debe moverse al principio del búfer, y el espacio libre al final del búfer debe rellenarse con nueva información. Para evitar llamadas frecuentes a YYFILL, es mejor rellenar tantos caracteres de entrada como sea posible (aunque menos caracteres podrían ser suficientes para reanudar el lexer). Los detalles de la implementación de YYFILL son ligeramente diferentes dependiendo de qué método de manejo de EOF se utilice: el caso de la regla de EOF es algo más simple que el caso de la comprobación de límites con relleno. Tenga en cuenta también que si se utiliza la opción -f --storable-state, YYFILL tiene una semántica ligeramente diferente (descrita en la sección sobre estado almacenable).

YYFILL con centinela

Si se utiliza la regla de EOF, YYFILL es una primitiva similar a una función que no acepta argumentos y devuelve un valor que se comprueba contra cero. La invocación de YYFILL se activa por la condición YYLIMIT <= YYCURSOR en la API de punteros C y YYLESSTHAN() en la API genérica. Un valor de retorno distinto de cero significa que YYFILL ha fallado. Una llamada exitosa a YYFILL debe suministrar al menos un carácter y ajustar las posiciones de entrada correspondientemente. El límite siempre debe establecerse en uno después de la última posición de entrada en el búfer, y el carácter en la posición del límite debe ser el símbolo centinela especificado por la configuración re2c:eof. Las figuras a continuación muestran las ubicaciones relativas de las posiciones de entrada en el búfer antes y después de la llamada a YYFILL (el símbolo centinela se marca con #, y la segunda figura muestra el caso en que no hay suficiente entrada para llenar todo el búfer).

             >-A------------B---------C-------------D#-----------E->
             buffer       token    marker         limit,
                                                  cursor
>-A------------B---------C-------------D------------E#->
             buffer,  marker        cursor        limit
             token
               <-- shift -->
             >-A------------B---------C-------------D#--E (EOF)
             buffer       token    marker         limit,

>-A------------B---------C-------------D---E#........

Aquí hay un ejemplo de un programa que lee el archivo de entrada input.txt en fragmentos de 4096 bytes y utiliza la regla de EOF.

// re2java $INPUT -o $OUTPUT
import java.io.*;
import java.nio.file.*;
class Lexer {
    public static final int BUFSIZE = 4096;
    private BufferedInputStream stream;
    private byte[] yyinput;
    private int yycursor;
    private int yymarker;
    private int yylimit;
    private int token;
    private boolean eof;
    public Lexer(File file) throws FileNotFoundException {
        stream = new BufferedInputStream(new FileInputStream(file));
        // El centinela en el desplazamiento `yylimit` se establece en cero, lo que activa YYFILL.
        yyinput = new byte[BUFSIZE + 1];
        yycursor = yymarker = yylimit = token = BUFSIZE;
        eof = false;
    }
    private int fill() throws IOException {
        if (eof) { return -1; } // EOF inesperado
        // Error: lexema demasiado largo. En la vida real se puede reasignar un búfer más grande.
        if (token < 1) { return -2; }
        // Desplaza el contenido del búfer (descarta todo hasta el token actual).
        System.arraycopy(yyinput, token, yyinput, 0, yylimit - token); 
        yycursor -= token;
        yymarker -= token;
        yylimit -= token;
        token = 0;
        // Rellena el espacio libre al final del buffer con nuevos datos del archivo.
        yylimit += stream.read(yyinput, yylimit, BUFSIZE - yylimit);
        yyinput[yylimit] = 0; // añade símbolo centinela
        // Si se lee menos de lo esperado, este es el final de la entrada.
        eof = yylimit < BUFSIZE;
        return 0;
    }
    // Espera una cadena terminada en nulo.
    public int lex() throws IOException {
        int count = 0;
        loop: while (true) {
            token = yycursor;
            /*!re2c
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyinput[yycursor]";
                re2c:YYFILL = "fill() == 0";
                re2c:eof = 0;
                str = ['\] ([^'\\] | [\\][^])* ['\];
                *    { return -1; }
                $    { return count; }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
            */
        }
    }
    public static void main(String []args) throws FileNotFoundException, IOException {
        String fname = "input";
        String content = "'qu\0tes' 'are' 'fine: \\'' ".repeat(Lexer.BUFSIZE);
        // Prepara el archivo de entrada: varias veces el tamaño del buffer, que contiene
        // cadenas con ceros y comillas escapadas.
        Files.writeString(Paths.get(fname), content);
        int count = 3 * Lexer.BUFSIZE; // número de cadenas entre comillas escritas en el archivo
        // Prepara el estado del lexer: todos los desplazamientos están al final del buffer.
        File file = new File(".", fname);
        Lexer lexer = new Lexer(file);
        // Ejecuta el lexer.
        int n = lexer.lex();
        assert n == count;
        // Limpieza: elimina el archivo de entrada.
        file.delete();
    }
};

YYFILL con relleno

En el caso predeterminado (cuando no se utiliza la regla EOF) YYFILL es una primitiva similar a una función que acepta un único argumento y no devuelve ningún valor. La invocación de YYFILL se dispara por la condición (YYLIMIT - YYCURSOR) < n en la API de punteros C y YYLESSTHAN(n) en la API genérica. El argumento pasado a YYFILL es el número mínimo de caracteres que deben suministrarse. Si falla en hacerlo, YYFILL no debe regresar al lexer (por esa razón se implementa mejor como una macro que regresa de la función llamante en caso de fallo). En caso de una invocación exitosa de YYFILL, la posición límite debe establecerse bien una posición después de la última posición de entrada en el buffer, o al final del relleno de YYMAXFILL (en caso de que YYFILL haya leído con éxito al menos n caracteres, pero no suficientes para llenar todo el buffer). Las imágenes a continuación muestran las ubicaciones relativas de las posiciones de entrada en el buffer antes y después de la invocación de YYFILL (el relleno de YYMAXFILL en la segunda imagen está marcado con símbolos #).

             buffer       token    marcador cursor  límite
>-A------------B---------C-----D-------E---F--------G->
             buffer,  marcador cursor               límite
             token
               <-- desplazamiento -->               <-- necesidad -->
             >-A------------B---------C-----D-------E-F        (EOF)

>-A------------B---------C-----D-------E-F###############

Aquí hay un ejemplo de un programa que lee el archivo de entrada input.txt en bloques de 4096 bytes y utiliza la verificación de límites con relleno.

// re2java $INPUT -o $OUTPUT
import java.io.*;
import java.nio.file.*;
import java.util.Arrays;
class Lexer {
    /*!max:re2c*/
    public static final int BUFSIZE = 4096;
    private BufferedInputStream stream;
    private byte[] yyinput;
    private int yycursor;
    private int yylimit;
    private int token;
    private boolean eof;
    public Lexer(File file) throws FileNotFoundException {
        stream = new BufferedInputStream(new FileInputStream(file));
        // Prepara el estado del lexer: todos los desplazamientos están al final del buffer.
        // Esto activa inmediatamente YYFILL, ya que la condición YYLESSTHAN es verdadera.
        yyinput = new byte[BUFSIZE + YYMAXFILL];
        yycursor = yylimit = token = BUFSIZE;
        eof = false;
    }
    private int fill(int need) throws IOException {
        if (eof) { return -1; } // EOF inesperado
        // Error: lexema demasiado largo. En la vida real se puede reasignar un buffer más grande.
        if (token < need) { return -2; }
        // Desplaza el contenido del buffer (descarta todo hasta el token actual).
        System.arraycopy(yyinput, token, yyinput, 0, yylimit - token);
        yycursor -= token;
        yylimit -= token;
        token = 0;
        // Rellena el espacio libre al final del buffer con nuevos datos del archivo.
        yylimit += stream.read(yyinput, yylimit, BUFSIZE - yylimit);
        yyinput[yylimit] = 0; // añade símbolo centinela
        // Si se lee menos de lo esperado, este es el final de la entrada.
        if (yylimit < BUFSIZE) {
            eof = true;
            Arrays.fill(yyinput, yylimit, yylimit + YYMAXFILL, (byte)0);
            yylimit += YYMAXFILL;
        }
        return 0;
    }
    // Espera una cadena terminada en nulo.
    public int lex() throws IOException {
        int count = 0;
        loop: while (true) {
            token = yycursor;
            /*!re2c
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyinput[yycursor]";
                re2c:YYFILL = "if (fill(@@) != 0) { return -2; }";
                str = ['\] ([^'\\] | [\\][^])* ['\];
                [\x00] {
                    // Comprueba que sea el centinela, no un nulo inesperado.
                    return (token == yylimit - YYMAXFILL) ? count : -1;
                }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
                *    { return -1; }
            */
        }
    }
    public static void main(String []args) throws FileNotFoundException, IOException {
        String fname = "input";
        String content = "'qu\0tes' 'are' 'fine: \\'' ".repeat(Lexer.BUFSIZE);
        // Prepara el archivo de entrada: varias veces el tamaño del buffer, que contiene
        // cadenas con ceros y comillas escapadas.
        Files.writeString(Paths.get(fname), content);
        int count = 3 * Lexer.BUFSIZE; // número de cadenas entre comillas escritas en el archivo
        // Prepara el estado del lexer: todos los desplazamientos están al final del buffer.
        File file = new File(".", fname);
        Lexer lexer = new Lexer(file);
        // Ejecuta el lexer.
        int n = lexer.lex();
        assert n == count;
        // Limpieza: elimina el archivo de entrada.
        file.delete();
    }
};

CARACTERÍSTICAS

Múltiples bloques

A veces es necesario tener múltiples lexers interrelacionados (por ejemplo, si hay una máquina de estados de alto nivel que transiciona entre modos de lexer). Esto se puede implementar usando múltiples bloques conectados de re2java. Otra opción es usar condiciones de inicio.

La implementación de conexiones entre bloques depende del lenguaje de destino. En lenguajes que tienen la sentencia goto (como C/C++ y Go) se pueden tener todos los bloques en una sola función, cada uno prefijado con una etiqueta. La transición de un bloque a otro es un simple goto. En lenguajes que no tienen goto (como Rust) es necesario usar un bucle con un switch en una variable de estado, similar al bucle/switch yystate generado por re2java, o bien envolver cada bloque en una función y usar llamadas a funciones.

El siguiente ejemplo utiliza múltiples bloques para analizar números binarios, octales, decimales y hexadecimales. Cada base tiene su propio bloque. El bloque inicial determina la base y se dirige a otros bloques. Las configuraciones comunes se definen en un bloque separado al principio del programa; son heredadas por los otros bloques.

// re2java $INPUT -o $OUTPUT
class Parser {
    private String yyinput;
    private int yycursor;
    private int yymarker;
    private int number;
    private void add_digit(int base, int offset) throws ArithmeticException {
        number = Math.addExact(
            Math.multiplyExact(number, base),
            yyinput.charAt(yycursor - 1) - offset);
    }
    public int parse(String str) throws ArithmeticException, IllegalArgumentException {
        yyinput = str;
        yycursor = 0;
        number = 0;
        try {
            /*!re2c
                re2c:YYCTYPE = "char";
                re2c:YYPEEK = "yyinput.charAt(yycursor)";
                re2c:yyfill:enable = 0;
                end = "\x00";
                '0b' / [01]        { return parse_bin(); }
                "0"                { return parse_oct(); }
                ""   / [1-9]       { return parse_dec(); }
                '0x' / [0-9a-fA-F] { return parse_hex(); }
                *                  { throw new IllegalArgumentException("not a number"); }
            */
        } catch (Exception e) {
            return -1;
        }
    }
    private int parse_bin() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [01]  { add_digit(2, 48); return parse_bin(); }
            *     { throw new IllegalArgumentException("ill-formed binary number"); }
        */
    }
    private int parse_oct() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [0-7] { add_digit(8, 48); return parse_oct(); }
            *     { throw new IllegalArgumentException("ill-formed octal number"); }
        */
    }
    private int parse_dec() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [0-9] { add_digit(10, 48); return parse_dec(); }
            *     { throw new IllegalArgumentException("ill-formed decimal number"); }
        */
    }
    private int parse_hex() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [0-9] { add_digit(16, 48); return parse_hex(); }
            [a-f] { add_digit(16, 87); return parse_hex(); }
            [A-F] { add_digit(16, 55); return parse_hex(); }
            *     { throw new IllegalArgumentException("ill-formed hexadecimal number"); }
        */
    }
    public static void main(String []args) {
        Parser parser = new Parser();
        assert parser.parse("1234567890\0") == 1234567890;
        assert parser.parse("0b1101\0") == 0b1101;
        assert parser.parse("0x007Fe\0") == 0x7fe;
        assert parser.parse("0644\0") == 0644;
        assert parser.parse("9999999999\0") == -1;
        assert parser.parse("123??\0") == -1;
    }
};

Start conditions

Start conditions are enabled with --start-conditions option. They provide a way to encode multiple interrelated automata within the same re2java block.

Each condition corresponds to a single automaton and has a unique name specified by the user and a unique internal number defined by re2java. The numbers are used to switch between conditions: the generated code uses YYGETCOND and YYSETCOND primitives to get the current condition or set it to the given number. Use conditions block, --header option or re2c:header configuration to generate numeric condition identifiers. Configuration re2c:cond:enumprefix specifies the generated identifier prefix.

In condition mode every rule must be prefixed with a list of comma-separated condition names in angle brackets, or a wildcard <*> to denote all conditions. The rule syntax is extended as follows:

< condition-list > regular-expression code
A rule that is merged to every condition on the condition-list. It matches regular-expression and executes the associated code.
< condition-list > regular-expression => condition code
A rule that is merged to every condition on the condition-list. It matches regular-expression, sets the current condition to condition and executes the associated code.
< condition-list > regular-expression :=> condition
A rule that is merged to every condition on the condition-list. It matches regular-expression and immediately transitions to condition (there is no semantic action).
< condition-list > !action code
A rule that binds code to the place defined by action in every condition on the condition-list (see the actions section for various types of actions).
<! condition-list > code
A rule that prepends code to semantic actions of all rules for every condition on the condition-list. This syntax is deprecated, and the !pre_rule action should be used instead (it does exactly the same).
< > code
A rule that creates a special entry condition with number zero and name "0" that executes code before jumping to other conditions. This syntax is deprecated, and the !entry action should be used instead (it provides a more fine-grained control, as the code can be specified on a per-condition basis, and one can jump directly to condition start without going through condition dispatch).
< > => condition code
Same as the previous rule, except that it sets the next condition.
< > :=> condition
Same as the previous rule, except that it has no associated code and immediately jumps to condition.

The code re2java generates for conditions depends on whether re2java uses goto/label approach or loop/switch approach to encode the automata.

In languages that have goto statement (such as C/C++ and Go) conditions are naturally implemented as blocks of code prefixed with labels of the form yyc_<cond>, where cond is a condition name (label prefix can be changed with re2c:cond:prefix). Transitions between conditions are implemented using goto and condition labels. Before all conditions re2java generates an initial switch on YYGETSTATE that jumps to the start state of the current condition. The shortcut rules :=> bypass the initial switch and jump directly to the specified condition (re2c:cond:goto can be used to change the default behavior). The rules with semantic actions do not automatically jump to the next condition; this should be done by the user-defined action code.

In languages that do not have goto (such as Rust) re2java reuses the yystate variable to store condition numbers. Each condition gets a numeric identifier equal to the number of its start state, and a switch between conditions is no different than a switch between DFA states of a single condition. There is no need for a separate initial condition switch. (Since the same approach is used to implement storable states, YYGETCOND/YYSETCOND are redundant if both storable states and conditions are used).

The program below uses start conditions to parse binary, octal, decimal and hexadecimal numbers. There is a single block where each base has its own condition, and the initial condition is connected to all of them. User-defined variable cond stores the current condition number; it is initialized to the number of the initial condition generated with conditions block.

// re2java $INPUT -o $OUTPUT -c
class Parser {
    /*!conditions:re2c*/
    private String yyinput;
    private int yycursor;
    private int yymarker;
    private int number;
    private void add_digit(int base, int offset) throws ArithmeticException {
        number = Math.addExact(
            Math.multiplyExact(number, base),
            yyinput.charAt(yycursor - 1) - offset);
    }
    public int parse(String str) throws ArithmeticException, IllegalArgumentException {
        yyinput = str;
        yycursor = 0;
        int yycond = YYC_init;
        number = 0;
        try {
            loop: while (true) {
            /*!re2c
                re2c:YYCTYPE = "char";
                re2c:YYPEEK = "yyinput.charAt(yycursor)";
                re2c:yyfill:enable = 0;
                <*> * { throw new IllegalArgumentException("ill-formed number"); }
                <init> '0b' / [01]        :=> bin
                <init> "0"                :=> oct
                <init> ""   / [1-9]       :=> dec
                <init> '0x' / [0-9a-fA-F] :=> hex
                <bin, oct, dec, hex> "\x00" { return number; }
                <bin> [01]  { add_digit(2, 48); continue loop; }
                <oct> [0-7] { add_digit(8, 48); continue loop; }
                <dec> [0-9] { add_digit(10, 48); continue loop; }
                <hex> [0-9] { add_digit(16, 48); continue loop; }
                <hex> [a-f] { add_digit(16, 87); continue loop; }
                <hex> [A-F] { add_digit(16, 55); continue loop; }
            */
            }
        } catch (Exception e) {
            return -1;
        }
    }
    public static void main(String []args) {
        Parser parser = new Parser();
        assert parser.parse("1234567890\0") == 1234567890;
        assert parser.parse("0b1101\0") == 0b1101;
        assert parser.parse("0x007Fe\0") == 0x7fe;
        assert parser.parse("0644\0") == 0644;
        assert parser.parse("9999999999\0") == -1;
        assert parser.parse("123??\0") == -1;
    }

Storable state

With --storable-state option re2java generates a lexer that can store its current state, return to the caller, and later resume operations exactly where it left off. The default mode of operation in re2java is a "pull" model, in which the lexer "pulls" more input whenever it needs it. This may be unacceptable in cases when the input becomes available piece by piece (for example, if the lexer is invoked by the parser, or if the lexer program communicates via a socket protocol with some other program that must wait for a reply from the lexer before it transmits the next message). Storable state feature is intended exactly for such cases: it allows one to generate lexers that work in a "push" model. When the lexer needs more input, it stores its state and returns to the caller. Later, when more input becomes available, the caller resumes the lexer exactly where it stopped. There are a few changes necessary compared to the "pull" model:

  • Define YYSETSTATE() and YYGETSTATE(state) primitives.
  • Define yych, yyaccept (if used) and state variables as a part of persistent lexer state. The state variable should be initialized to -1.
  • YYFILL should return to the outer program instead of trying to supply more input. Return code should indicate that lexer needs more input.
  • The outer program should recognize situations when lexer needs more input and respond appropriately.
  • Optionally use getstate block to generate YYGETSTATE switch detached from the main lexer. This only works for languages that have goto (not in --loop-switch mode).
  • Use re2c:eof and the sentinel with bounds checks method to handle the end of input. Padding-based method may not work because it is unclear when to append padding: the current end of input may not be the ultimate end of input, and appending padding too early may cut off a partially read greedy lexeme. Furthermore, due to high-level program logic getting more input may depend on processing the lexeme at the end of buffer (which already is blocked due to the end-of-input condition).

Las etiquetas se habilitan con la opción `-T --tags` o la configuración `re2c:tags = 1`. Semánticamente, las etiquetas son marcadores de posición: se pueden insertar en cualquier lugar de una expresión regular y se vinculan a la posición (o posiciones) correspondiente(s) en la cadena de entrada. Las *etiquetas S* se vinculan a la última posición coincidente, y las *etiquetas m* se vinculan a una lista de posiciones (se pueden usar en subexpresiones de repetición, donde una sola posición en una expresión regular corresponde a múltiples posiciones en la cadena de entrada). Todas las etiquetas deben ser definidas por el usuario, ya sea manualmente o con la ayuda de bloques `svars` y `mvars`. Si hay más de una forma en que las etiquetas puedan coincidir con la entrada, la ambigüedad se resuelve utilizando la estrategia de desambiguación voraz de izquierda a derecha. * **Capturas**: La segunda opción es usar **grupos de captura**. Se habilitan con la opción `--captures` o la configuración `re2c:captures = 1`. Hay dos variantes para diferentes políticas de desambiguación, `--leftmost-captures` (el predeterminado) es para la política voraz de izquierda a derecha, y `--posix-captures` es para la política de coincidencia más larga POSIX. En este modo, todas las subexpresiones entre paréntesis se consideran grupos de captura, y se puede usar un signo de exclamación para marcar grupos que no capturan: `(! ... )`. Con la opción `--invert-captures` o la configuración `re2c:invert-captures = 1`, el significado del signo de exclamación se invierte. El número de grupos para la regla coincidente se almacena en la variable `yynmatch` (la expresión regular completa es el grupo número cero), y los resultados de las subcoincidencias se almacenan en la matriz `yypmatch`. Tanto `yynmatch` como `yypmatch` deben ser definidos por el usuario, y el tamaño de `yypmatch` debe ser al menos `[yynmatch * 2]`. Utilice el bloque `maxnmatch` para definir `YYMAXNMATCH`, una constante que es igual al valor máximo de `yynmatch` entre todas las reglas. * **Captvars**: Otra forma de usar grupos de captura es la opción `--captvars` o la configuración `re2c:captvars = 1`. La única diferencia con `--captures` es la forma en que el código generado almacena los resultados de las subcoincidencias: en lugar de `yynmatch` y `yypmatch`, re2java genera las variables `yytl` y `yytr` para el grupo de captura *k* (el usuario debe declararlos usando un bloque `svars`). Las capturas con variables admiten dos políticas de desambiguación: `--leftmost-captvars` o `re2c:leftmost-captvars = 1`. para la política greedy de izquierda a derecha (la predeterminada) y --posix-captvars o re2c:posix-captvars para la política de coincidencia más larga POSIX.

Internamente, todas estas opciones se traducen en etiquetas y Autómatas Finitos Deterministas Etiquetados con Lookahead. La idea principal de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En el extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es simplemente un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es apenas perceptible. El TDFA generado utiliza una serie de variables de etiqueta que no se mapean directamente a las etiquetas: una sola variable puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples variables para almacenar todos sus posibles valores. Finalmente, la ambigüedad se resuelve y solo sobrevive una variable final por etiqueta. Las variables de etiqueta deben definirse usando bloques stags o mtags. Si se almacena el estado del lexer, las variables de etiqueta deben formar parte de él. También deben actualizarse con YYFILL.

Las S-tags soportan las siguientes operaciones:

  • guardar la posición de entrada en una s-tag: t = YYCURSOR con la API de punteros C o una operación definida por el usuario YYSTAGP(t) con la API genérica
  • guardar un valor predeterminado en una s-tag: t = NULL con la API de punteros C o una operación definida por el usuario YYSTAGN(t) con la API genérica
  • copiar una s-tag a otra: t1 = t2

Las M-tags soportan las siguientes operaciones:

  • añadir una posición de entrada a una m-tag: una operación definida por el usuario YYMTAGP(t) con la API predeterminada y la genérica
  • añadir un valor predeterminado a una m-tag: una operación definida por el usuario YYMTAGN(t) con la API predeterminada y la genérica
  • copiar una m-tag a otra: t1 = t2

Las S-tags se pueden implementar como valores escalares (punteros u offsets). Las M-tags necesitan una representación más compleja, ya que deben almacenar una secuencia de valores de etiqueta. La representación más ingenua e ineficiente de una m-tag es una lista (array, vector) de valores de etiqueta; una representación más eficiente es almacenar todas las m-tags en un árbol de prefijos representado como un array de nodos (v, p), donde v es el valor de la etiqueta y p es un puntero al nodo padre.

        // Variables de etiqueta finales disponibles en la acción semántica.
        /*!svars:re2c format = "int @@;"; */
        /*!mvars:re2c format = "List<Integer> @@;"; */
       // Variables de etiqueta intermedias usadas por el lexer (deben ser autogeneradas).
        /*!stags:re2c format = "int @@ = -1;"; */
        /*!mtags:re2c format = "List @@ = new ArrayList<>();"; */
        /*!re2c
            re2c:YYCTYPE = "char";
            re2c:YYPEEK = "yyinput.charAt(yycursor)";
            re2c:YYMTAGP = "@@.add(yycursor);";
            re2c:YYMTAGN = ""; // no hacer nada
            re2c:yyfill:enable = 0;
            re2c:tags = 1;
            num = [0-9]+;
            @t1 num @t2 (".?" #t3 num #t4)* [\x00] {
                int[] vers = new int[t3.size() + 1];
                vers[0] = Integer.valueOf(yyinput.substring(t1, t2));
                for (int i = 0; i < t3.size(); ++i) {
                    vers[i + 1] = Integer.valueOf(yyinput.substring(t3.get(i), t4.get(i)));
                }
                return Optional.of(vers);
            }
            * { return Optional.empty(); }
        */
    }
    public static void main(String []args) {
        assert Arrays.equals(parse("1\0").get(), new int[]{1});
        assert Arrays.equals(parse("1.2.3.4.5.6.7\0").get(), new int[]{1, 2, 3, 4, 5, 6, 7});
        assert !parse("1.2.\0").isPresent();
    }
};

Soporte de Codificación

Es necesario comprender la diferencia entre puntos de código y unidades de código. Un punto de código es un identificador numérico de un símbolo. Una unidad de código es la unidad de almacenamiento más pequeña en el texto codificado. Un solo punto de código puede representarse con una o más unidades de código. En una codificación de longitud fija, todos los puntos de código se representan con el mismo número de unidades de código. En una codificación de longitud variable, los puntos de código pueden representarse con un número diferente de unidades de código. Tenga en cuenta que la regla "cualquiera" [^] coincide con cualquier punto de código, pero no necesariamente con cualquier unidad de código (la única forma de coincidir con cualquier unidad de código independientemente de la codificación es la regla predeterminada *). El lexer generado trabaja con un flujo de unidades de código: yych almacena una unidad de código y YYCTYPE es el tipo de unidad de código. Las expresiones regulares, por otro lado, se especifican en términos de puntos de código. Cuando re2java compila expresiones regulares a autómatas, traduce puntos de código a unidades de código. Esto generalmente no es una correspondencia simple: en codificaciones de longitud variable, un solo rango de puntos de código puede traducirse a un gráfico complejo de unidades de código. Se admiten las siguientes codificaciones:

  • ASCII (habilitado por defecto). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • EBCDIC (habilitado con --ebcdic o re2c:encoding:ebcdic). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • UCS2 (habilitado con --ucs2 o re2c:encoding:ucs2). Es una codificación de longitud fija con espacio de código [0-0xFFFF] y puntos de código y unidades de código de 2 bytes.
  • UTF8 (habilitado con --utf8 o re2c:encoding:utf8). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
  • UTF16 (habilitado con --utf16 o re2c:encoding:utf16). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 a 2 unidades de código.
  • UTF32 (habilitado con --utf32 o re2c:encoding:utf32). Es una codificación Unicode de longitud fija con espacio de código [0-0x10FFFF] y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión include/unicode_categories.re proporciona definiciones de re2java para las categorías estándar de Unicode.

La opción --input-encoding especifica la codificación del archivo fuente, que se puede utilizar para habilitar literales Unicode en expresiones regulares. Por ejemplo, --input-encoding utf8 le dice a re2java que el archivo fuente está en UTF8 (difiere de --utf8 que establece la codificación del texto de entrada). La opción --encoding-policy especifica la forma en que re2java maneja los sustitutos Unicode (puntos de código en el rango [0xD800-0xDxDFFF]).

A continuación, se muestra un ejemplo de un lexer para identificadores Unicode codificados en UTF8.

// re2java $INPUT -o $OUTPUT --utf8 -s
/*!include:re2c "unicode_categories.re" */
class Main {
    static boolean lex(String yyinput) {
        int yycursor = 0;
        int yymarker = 0;
        /*!re2c
            re2c:YYCTYPE = "char";
            re2c:YYPEEK = "yyinput.charAt(yycursor)";
            re2c:yyfill:enable = 0;
            // "Sintaxis de Identificador y Patrones Unicode" simplificada
            // (ver https://unicode.org/reports/tr31)
            id_start    = L | Nl | [$_];
            id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
            identifier  = id_start+;
            // Debería ser `id_start id_continue*`, pero eso causa `error: code too large`
            identifier { return true; }
            *          { return false; }
        */
    }
    public static void main(String []args) {
        assert lex("_\u042B\u0434\u0435\u043D\u0442\u0438\u0444\u0438\u043A\u0430\u0442\u043E\u0440\0");
    }
};

Archivos de Inclusión

re2java permite incluir otros archivos usando un bloque de la forma /*!include:re2c ARCHIVO */ o %{include ARCHIVO %}, o una directiva dentro de un bloque !include ARCHIVO ;, donde ARCHIVO es una ruta al archivo a incluir. re2java busca archivos de inclusión en el directorio del archivo que incluye y en las ubicaciones de inclusión, que se pueden especificar con la opción -I. Los bloques/directivas de inclusión en re2java funcionan de la misma manera que el #include de C/C++: el contenido de ARCHIVO se copia y pega textualmente en el lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias. Use la opción --depfile para rastrear las dependencias de compilación del archivo de salida en los archivos de inclusión. re2java proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como categorías Unicode) y forman algo así como una biblioteca estándar para re2java. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivo de Inclusión 1 (definitions.java)

/*!re2c
    number = [1-9][0-9]*;
*/

Archivo de Inclusión 2 (extra_rules.re.inc)

// números de punto flotante

Archivo de entrada

        int yycursor = 0;
        int yymarker = 0;

    }

Archivos de Cabecera

re2java permite generar un archivo de cabecera a partir del archivo .re de entrada usando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de cabecera, y el segundo bloque marca el final del mismo. Todo lo que está entre estos bloques es procesado por re2java, y el código generado se escribe en el archivo especificado con la opción --header o la configuración re2c:header (o stdout si no se usa ninguna opción o configuración). El archivo de cabecera autogenerado puede ser necesario en casos donde re2java se utiliza para generar definiciones que deben ser visibles desde otras unidades de traducción.

Aquí hay un ejemplo de generación de un archivo de cabecera que contiene la definición del estado del lexer con variables de etiqueta (las variables numéricas dependen de la gramática regular y son desconocidas para el programador).

Archivo de entrada

// re2java $INPUT -o $OUTPUT --header lexer/state.java
package headers;
import headers.lexer.State;
/*!header:re2c:on*/
package headers.lexer;
public class State {
    public String yyinput;
    public int yycursor;
    /*!stags:re2c format = "public int @@;\n"; */
    public State(String str) {
        yyinput = str;
        yycursor = 0;
        /*!stags:re2c format = "@@ = 0;\n"; */
    }
};
/*!header:re2c:off*/
class Main {
    static int lex(String str) {
        State yyrecord = new State(str);
        int t;
        /*!re2c
            re2c:api = record;
            re2c:tags = 1;
            re2c:yyfill:enable = 0;
            re2c:YYCTYPE = "char";
            re2c:YYPEEK = "yyrecord.yyinput.charAt(yyrecord.yycursor)";
            re2c:header = "lexer/state.java";
            [a]* @t [b]* { return t; }
        */
    }
    public static void main(String []args) {
        assert lex("ab\0") == 1;
    }
};

Programas Esqueleto

Con la opción -S, --skeleton, re2java ignora todo el código que no es de re2java y genera un programa C autocontenido que puede ser compilado y ejecutado posteriormente. El programa consiste en código del lexer y datos de entrada. Para cada autómata finito determinista (DFA) construido (bloque o condición), re2java genera un lexer independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados de coincidencia esperados. FEATURES

re2java features:

  • It is possible to check the correctness of various re2java optimizations (the data is generated early in the process, before any DFA transformations have taken place).
  • Generating a set of input data with good coverage may be useful for both testing and benchmarking.
  • Generating self-contained executable programs allows one to get minimized test cases (the original code may be large or have a lot of dependencies).

The difficulty with generating input data is that for all but the most trivial cases the number of possible input strings is too large (even if the string length is limited). re2java solves this difficulty by generating sufficiently many strings to cover almost all DFA transitions. It uses the following algorithm. First, it constructs a skeleton of the DFA. For encodings with 1-byte code unit size (such as ASCII, UTF-8 and EBCDIC) skeleton is just an exact copy of the original DFA. For encodings with multibyte code units skeleton is a copy of DFA with certain transitions omitted: namely, re2java takes at most 256 code units for each disjoint continuous range that corresponds to a DFA transition. The chosen values are evenly distributed and include range bounds. Instead of trying to cover all possible paths in the skeleton (which is infeasible) re2java generates sufficiently many paths to cover all skeleton transitions, and thus trigger the corresponding conditional jumps in the lexer. The algorithm implementation is limited by ~1Gb of transitions and consumes constant amount of memory (re2java writes data to file as soon as it is generated).

Visualization and debug

With the -D, --emit-dot option, re2java does not generate code. Instead, it dumps the generated DFA in DOT format. One can convert this dump to an image of the DFA using Graphviz or another library. Note that this option shows the final DFA after it has gone through a number of optimizations and transformations. Earlier stages can be dumped with various debug options, such as --dump-nfa, --dump-dfa-raw etc. (see the full list of options).
