recv(2) System Calls Manual recv(2)

NAME

recv, recvfrom, recvmsg - receive a message from a socket

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

#include <sys/socket.h>
ssize_t recv(int sockfd, void *buf, size_t size, int flags);
ssize_t recvfrom(int sockfd, void *restrict buf, size_t size, int flags,
                 struct sockaddr *_Nullable restrict src_addr,
                 socklen_t *_Nullable restrict addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

The recv(), recvfrom(), and recvmsg() calls are used to receive messages from a socket. They may be used to receive data on both connectionless and connection-oriented sockets. This page first describes common features of all three system calls, and then describes the differences between the calls.

The only difference between recv() and read(2) is the presence of flags. With a zero flags argument, recv() is generally equivalent to read(2) (but see NOTES). Also, the following call


recv(sockfd, buf, size, flags);

is equivalent to


recvfrom(sockfd, buf, size, flags, NULL, NULL);

All three calls return the size of the message on successful completion. If a message is too long to fit in the supplied buffer, excess bytes may be discarded depending on the type of socket the message is received from.

If no messages are available at the socket, the receive calls wait for a message to arrive, unless the socket is nonblocking (see fcntl(2)), in which case the value -1 is returned and errno is set to EAGAIN or EWOULDBLOCK. The receive calls normally return any data available, up to the requested amount, rather than waiting for receipt of the full amount requested.

An application can use select(2), poll(2), or epoll(7) to determine when more data arrives on a socket.

The flags argument

The flags argument is formed by ORing one or more of the following values:

MSG_CMSG_CLOEXEC (recvmsg() only; since Linux 2.6.23)
Set the close-on-exec flag for the file descriptor received via a UNIX domain file descriptor using the SCM_RIGHTS operation (described in unix(7)). This flag is useful for the same reasons as the O_CLOEXEC flag of open(2).
MSG_DONTWAIT (since Linux 2.2)
Enables nonblocking operation; if the operation would block, the call fails with EAGAIN or EWOULDBLOCK. This provides similar behavior to setting the O_NONBLOCK flag (via the fcntl(2) F_SETFL operation), but differs in that MSG_DONTWAIT is a per-call option, whereas O_NONBLOCK is a setting on the open file description (see open(2)), which will affect all threads in the calling process as well as other processes that hold file descriptors referring to the same open file description.
MSG_ERRQUEUE (since Linux 2.2)
This flag specifies that queued errors should be received from the socket error queue. The error is passed in an ancillary message with a type dependent on the protocol (for IPv4 IP_RECVERR). The user should supply a buffer of sufficient size. See cmsg(3) and ip(7) for more information. The payload of the original packet that caused the error is passed as normal data via msg_iovec. The original destination address of the datagram that caused the error is supplied via msg_name.
The error is supplied in a sock_extended_err structure:

#define SO_EE_ORIGIN_NONE    0
#define SO_EE_ORIGIN_LOCAL   1
#define SO_EE_ORIGIN_ICMP    2
#define SO_EE_ORIGIN_ICMP6   3
struct sock_extended_err
{
    uint32_t ee_errno;   /* Error number */
    uint8_t  ee_origin;  /* Where the error originated */
    uint8_t  ee_type;    /* Type */
    uint8_t  ee_code;    /* Code */
    uint8_t  ee_pad;     /* Padding */
    uint32_t ee_info;    /* Additional information */
    uint32_t ee_data;    /* Other data */
    /* More data may follow */
};
struct sockaddr *SO_EE_OFFENDER(struct sock_extended_err *);

ee_errno contains the errno number of the queued error. ee_origin is the origin code of where the error originated. The other fields are protocol-specific. The macro SO_EE_OFFENDER returns a pointer to the address of the network object where the error originated from given a pointer to the ancillary message. If this address is not known, the sa_family member of the sockaddr contains AF_UNSPEC and the other fields of the sockaddr are undefined. The payload of the packet that caused the error is passed as normal data.
For local errors, no address is passed (this can be checked with the cmsg_len member of the cmsghdr). For error receives, the MSG_ERRQUEUE flag is set in the msghdr. After an error has been passed, the pending socket error is regenerated based on the next queued error and will be passed on the next socket operation.
MSG_OOB
This flag requests receipt of out-of-band data that would not be received in the normal data stream. Some protocols place expedited data at the head of the normal data queue, and thus this flag cannot be used with such protocols.
MSG_PEEK
This flag causes the receive operation to return data from the beginning of the receive queue without removing that data from the queue. Thus, a subsequent receive call will return the same data.
MSG_TRUNC (since Linux 2.2)
For raw (AF_PACKET), Internet datagram (since Linux 2.4.27/2.6.8), netlink (since Linux 2.6.22), and UNIX datagram as well as sequenced-packet (since Linux 3.4) sockets: return the real size of the packet or datagram, even when it was longer than the passed buffer.
For use with Internet stream sockets, see tcp(7).
MSG_WAITALL (since Linux 2.2)
This flag requests that the operation block until the full request is satisfied. However, the call may still return less data than requested if a signal is caught, an error or disconnect occurs, or the next data to be received is of a different type than that returned. This flag has no effect for datagram sockets.

recvfrom()

recvfrom() places the received message into the buffer buf. The caller must specify the size of the buffer in size.

If src_addr is not NULL, and the underlying protocol provides the source address of the message, that source address is placed in the buffer pointed to by src_addr. In this case, addrlen is a value-result argument. Before the call, it should be initialized to the size of the buffer associated with src_addr. Upon return, addrlen is updated to contain the actual size of the source address. The returned address is truncated if the buffer provided is too small; in this case, addrlen will return a value greater than was supplied to the call.

NOMBRE

recv, recvfrom, recvmsg - recibir mensajes de un socket

BIBLIOTECA

Rendimiento de socket (libc, -lsocket)

SINOPSIS

#include <sys/types.h>
#include <sys/socket.h>

ssize_t recv(int sockfd, void *buf, size_t len, int flags);
ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags,
                 struct sockaddr *src_addr, socklen_t *addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPCIÓN

Las llamadas al sistema recv(), recvfrom() y recvmsg() se utilizan para leer datos de un socket. Los argumentos son:

sockfd
El descriptor de archivo del socket desde el que se van a leer los datos.
buf
Puntero al búfer donde se almacenarán los datos recibidos.
len
La longitud máxima en bytes del búfer especificado por buf.
flags
Indica el tipo de recepción a realizar. Los valores de flags son las ORs bit a bit de cero o más de las siguientes opciones:
MSG_PEEK
Echa un vistazo a los datos entrantes. Los datos se devuelven, pero se eliminan de la cola de lectura. Esto es útil para inspeccionar la cola sin consumirla.
MSG_OOB
Lee datos fuera de banda (expedited data). El uso de esto está fuera del alcance de esta página man, consulte socket(7) para más detalles.
MSG_WAITALL
Espera hasta que se puedan satisfacer todas las solicitudes. Es decir, si el número de bytes solicitados es len, entonces recv() y recvfrom() regresarán solo cuando se hayan recibido len bytes o se haya producido un error o el par haya cerrado el conexión. Si no se especifica MSG_WAITALL, recv() y recvfrom() regresarán tan pronto como lleguen algunos datos, hasta el número de bytes solicitados.
MSG_DONTWAIT
Permite que la llamada se complete sin bloqueo. Si los datos no están disponibles, la llamada regresa con un error de EAGAIN.

El comportamiento de las opciones de banderas se define en socket(7).

recv()

El propósito de recv() es leer datos de un socket. Si el socket está conectado, los datos pueden ser leídos desde buf. El número de bytes leídos se devuelve en el valor de retorno. Si el número de bytes leídos es cero, significa que el par del socket ha realizado un cierre ordenado. Si la lectura se interrumpe o se produce un error, se devuelve -1 y errno se configura para indicar el error.

Tenga en cuenta que, a diferencia de read(2), recv() puede devolver un valor menor que len, y aun así no indicar el final de la entrada. Para obtener más detalles, consulte la descripción de MSG_WAITALL.

Si flags es cero, recv() es equivalente a llamar a read(2) en un socket.

recvfrom()

El propósito de recvfrom() es leer datos de un socket y también obtener la dirección de origen de los datos. Si src_addr no es NULL, los datos de dirección de origen se copian en la estructura de dirección apuntada por src_addr. El campo addrlen, al principio, contendrá el tamaño del búfer de almacenamiento para src_addr y, al regresar, contendrá el tamaño real de la dirección de origen devuelta. Si al la aplicación no le interesa la dirección de origen, src_addr y addrlen deberían especificarse como NULL.

Si el socket está conectado, los datos se leerán de él y la dirección de origen se puede devolver en src_addr, pero este campo se puede pasar como NULL en una llamada conectada, ya que la dirección de origen no será interesante.

Los flags pueden ser utilizados para modificar el comportamiento de la recepción. Vea la descripción de recv() para más detalles.

Si el socket está sin conexión (por ejemplo, de tipo SOCK_DGRAM), src_addr y addrlen deberían especificarse como NULL si no se desea la dirección de origen.

recvmsg()

La llamada recvmsg() utiliza una estructura msghdr para minimizar el número de argumentos suministrados directamente. Esta estructura se define como sigue en <sys/socket.h>:


struct msghdr {
    void         *msg_name;       /* Dirección opcional */
    socklen_t     msg_namelen;    /* Tamaño de la dirección */
    struct iovec *msg_iov;        /* Array de dispersión/agrupación */
    size_t        msg_iovlen;     /* # de elementos en msg_iov */
    void         *msg_control;    /* Datos auxiliares, ver abajo */
    size_t        msg_controllen; /* Tamaño del búfer de datos auxiliares */
    int           msg_flags;      /* Banderas en el mensaje recibido */
};

El campo msg_name apunta a un búfer asignado por el llamador que se utiliza para devolver la dirección de origen si el socket no está conectado. El llamador debe establecer msg_namelen al tamaño de este búfer antes de esta llamada; al regresar de una llamada exitosa, msg_namelen contendrá el tamaño de la dirección devuelta. Si la aplicación no necesita conocer la dirección de origen, msg_name puede especificarse como NULL.

Los campos msg_iov y msg_iovlen describen ubicaciones de dispersión/agrupación, como se discute en readv(2).

El campo msg_control, que tiene un tamaño de msg_controllen, apunta a un búfer para otros mensajes relacionados con el control del protocolo o datos auxiliares diversos. Cuando se llama a recvmsg(), msg_controllen debe contener el tamaño del búfer disponible en msg_control; al regresar de una llamada exitosa, contendrá el tamaño de la secuencia de mensajes de control.

Los mensajes son de la forma:


struct cmsghdr {
    size_t cmsg_len;    /* Recuento de bytes de datos, incluyendo la cabecera
                           (el tipo es socklen_t en POSIX) */
    int    cmsg_level;  /* Protocolo de origen */
    int    cmsg_type;   /* Tipo específico del protocolo */
/* seguido por
    unsigned char cmsg_data[]; */
};

Los datos auxiliares solo deben accederse mediante las macros definidas en cmsg(3).

Como ejemplo, Linux utiliza este mecanismo de datos auxiliares para pasar errores extendidos, opciones IP o descriptores de archivo a través de sockets de dominio UNIX. Para más información sobre el uso de datos auxiliares en varios dominios de socket, consulte unix(7) y ip(7).

El campo msg_flags en msghdr se establece al regresar de recvmsg(). Puede contener varias banderas:

MSG_EOR
indica el final del registro; los datos devueltos completaron un registro (generalmente, se usa con sockets de tipo SOCK_SEQPACKET).
MSG_TRUNC
indica que la porción final de un datagrama fue descartada porque el datagrama era más grande que el búfer suministrado.
MSG_CTRUNC
indica que se descartaron algunos datos de control debido a la falta de espacio en el búfer para datos auxiliares.
MSG_OOB
se devuelve para indicar que se recibieron datos fuera de banda (expedited data).
MSG_ERRQUEUE
indica que no se recibieron datos pero sí un error extendido de la cola de errores del socket.
MSG_CMSG_CLOEXEC (desde Linux 2.6.23)
indica que se especificó MSG_CMSG_CLOEXEC en el argumento flags de recvmsg().

VALOR DE RETORNO

Estas llamadas devuelven el número de bytes recibidos, o -1 si ocurrió un error. En caso de error, errno se configura para indicar el error.

Cuando el par de un socket de flujo ha realizado un cierre ordenado, el valor de retorno será 0 (el tradicional retorno de "fin de archivo").

Los sockets de datagramas en varios dominios (por ejemplo, los dominios UNIX e Internet) permiten datagramas de tamaño cero. Cuando se recibe un datagrama de este tipo, el valor de retorno es 0.

El valor 0 también puede devolverse si el número de bytes solicitados para recibir de un socket de flujo era 0.

ERRORES

Estos son algunos errores estándar generados por la capa de socket. Pueden generarse y devolverse errores adicionales desde los módulos de protocolo subyacentes; consulte sus páginas man.

EAGAIN o EWOULDBLOCK
El socket está marcado como no bloqueante y la operación de recepción se bloquearía, o se había establecido un tiempo de espera de recepción y el tiempo de espera expiró antes de recibir datos. POSIX.1 permite que cualquiera de estos errores se devuelva para este caso, y no requiere que estas constantes tengan el mismo valor, por lo que una aplicación portable debe verificar ambas posibilidades.
EBADF
El argumento sockfd es un descriptor de archivo inválido.
ECONNREFUSED
Un host remoto rechazó permitir la conexión de red (típicamente porque no está ejecutando el servicio solicitado).
EFAULT
Los punteros del búfer de recepción apuntan fuera del espacio de direcciones del proceso.
EINTR
La recepción fue interrumpida por la entrega de una señal antes de que hubiera datos disponibles; consulte signal(7).
EINVAL
Se pasó un argumento inválido.
ENOMEM
No se pudo asignar memoria para recvmsg().
ENOTCONN
El socket está asociado con un protocolo orientado a la conexión y no se ha conectado (consulte connect(2) y accept(2)).
ENOTSOCK
El descriptor de archivo sockfd no se refiere a un socket.

VERSIONES

Según POSIX.1, el campo msg_controllen de la estructura msghdr debe tener el tipo socklen_t, y el campo msg_iovlen debe tener el tipo int, pero glibc actualmente los tipifica ambos como size_t.

ESTÁNDARES

POSIX.1-2024.

HISTORIA

POSIX.1-2001, 4.2BSD.

POSIX.1 solo describe las banderas MSG_OOB, MSG_PEEK y MSG_WAITALL.

NOTAS

Si hay un datagrama de tamaño cero pendiente, read(2) y recv() con un argumento flags de cero proporcionan un comportamiento diferente. En esta circunstancia, read(2) no tiene efecto (el datagrama permanece pendiente), mientras que recv() consume el datagrama pendiente.

Consulte recvmmsg(2) para obtener información sobre una llamada al sistema específica de Linux que se puede utilizar para recibir varios datagramas en una sola llamada.

NAME

recv - recibe datos de un socket

SYNOPSIS

ssize_t recv(int sockfd, void *buf, size_t len, int flags);

DESCRIPTION

La llamada al sistema recv() se utiliza para leer datos de un socket.

  • sockfd: El descriptor del socket desde el que se van a leer los datos.
  • buf: Un puntero al búfer donde se almacenarán los datos recibidos.
  • len: La longitud máxima de bytes que se pueden leer en el búfer.
  • flags: Un conjunto de opciones que modifican el comportamiento de la llamada al sistema.

Los flags comunes incluyen:

  • MSG_PEEK: Echa un vistazo a los datos entrantes sin eliminarlos de la cola de recepción.
  • MSG_WAITALL: Espera hasta que se hayan recibido todos los datos solicitados.

recv() devuelve el número de bytes recibidos, 0 si la conexión se ha cerrado o -1 en caso de error.

RETURN VALUE

En caso de éxito, recv() devuelve el número de bytes recibidos. Si se ha cerrado una conexión de forma ordenada, devuelve 0. En caso de error, devuelve -1 y establece errno para indicar la naturaleza del error.

ERRORS

  • EBADF: sockfd no es un descriptor de archivo válido.
  • ECONNRESET: La conexión se ha reiniciado.
  • EINTR: La llamada fue interrumpida por una señal antes de que los datos estuvieran disponibles.
  • EWOULDBLOCK: El socket está en modo no bloqueante y la operación de recepción habría bloqueado.

STANDARDS

POSIX.1-2008, sockets.

HISTORY

Primera aparición en la versión 1 de BSD.

NOTES

recv() es una interfaz de nivel inferior. Para la mayoría de los casos de uso, se prefiere usar read() en un socket.

EXAMPLES

Ejemplo de uso: 


char buffer[1024];
ssize_t bytes_received = recv(sockfd, buffer, sizeof(buffer), 0);
if (bytes_received < 0) {
    perror("recv");
} else if (bytes_received == 0) {
    printf("Connection closed by peer.\n");
} else {
    // Procesar los datos recibidos en el buffer
    printf("Received %zd bytes: %.*s\n", bytes_received, (int)bytes_received, buffer);
}
