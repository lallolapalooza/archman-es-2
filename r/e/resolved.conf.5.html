NAME

resolved.conf, resolved.conf.d - Archivos de configuración de resolución de nombres de red

SINOPSIS

/etc/systemd/resolved.conf
/run/systemd/resolved.conf
/usr/local/lib/systemd/resolved.conf
/usr/lib/systemd/resolved.conf
/etc/systemd/resolved.conf.d/*.conf
/run/systemd/resolved.conf.d/*.conf
/usr/local/lib/systemd/resolved.conf.d/*.conf
/usr/lib/systemd/resolved.conf.d/*.conf

DESCRIPCIÓN

Estos archivos de configuración controlan la resolución de nombres DNS y LLMNR local.

DIRECTORIOS DE CONFIGURACIÓN Y PRECEDENCIA

La configuración predeterminada se establece durante la compilación, por lo que solo se necesita configuración cuando es necesario desviarse de dichos valores predeterminados. El archivo de configuración principal se carga desde uno de los directorios listados en orden de prioridad, solo se utiliza el primer archivo encontrado: /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La versión del proveedor del archivo contiene entradas comentadas que muestran los valores predeterminados como guía para el administrador. Las anulaciones locales también se pueden crear creando "drop-ins", como se describe a continuación. El archivo de configuración principal también se puede editar para este propósito (o una copia en /etc/ si se distribuye bajo /etc/), sin embargo, se recomienda el uso de "drop-ins" para la configuración local en lugar de modificaciones en el archivo de configuración principal.

Además del archivo de configuración principal, se leen fragmentos de configuración "drop-in" de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, y /etc/systemd/*.conf.d/. Estos "drop-ins" tienen mayor precedencia y anulan el archivo de configuración principal. Los archivos en los subdirectorios de configuración *.conf.d/ se ordenan por su nombre de archivo en orden lexicográfico, independientemente de en cuál de los subdirectorios residan. Cuando varios archivos especifican la misma opción, para las opciones que aceptan solo un valor único, la entrada en el archivo ordenado último tiene precedencia, y para las opciones que aceptan una lista de valores, las entradas se recopilan a medida que ocurren en los archivos ordenados.

Cuando los paquetes necesitan personalizar la configuración, pueden instalar "drop-ins" bajo /usr/. Los archivos en /etc/ están reservados para el administrador local, que puede usar esta lógica para anular los archivos de configuración instalados por los paquetes del proveedor. Se deben usar "drop-ins" para anular los "drop-ins" de los paquetes, ya que el archivo de configuración principal tiene menor precedencia. Se recomienda prefijar todos los nombres de archivo en estos subdirectorios con un número de dos dígitos y un guion, para simplificar el orden. Esto también define un concepto de prioridades de "drop-in" para permitir que los proveedores de OS envíen "drop-ins" dentro de un rango específico inferior al rango utilizado por los usuarios. Esto debería reducir el riesgo de que los "drop-ins" de los paquetes anulen accidentalmente los "drop-ins" definidos por los usuarios. Se recomienda utilizar el rango 10-40 para los "drop-ins" en /usr/ y el rango 60-90 para los "drop-ins" en /etc/ y /run/, para asegurarse de que los "drop-ins" locales y transitorios tengan prioridad sobre los "drop-ins" enviados por el proveedor del sistema operativo.

Para deshabilitar un archivo de configuración proporcionado por el proveedor, la forma recomendada es colocar un enlace simbólico a /dev/null en el directorio de configuración en /etc/, con el mismo nombre de archivo que el archivo de configuración del proveedor.

OPCIONES

Las siguientes opciones están disponibles en la sección [Resolve]:

DNS=

Una lista separada por espacios de direcciones IPv4 e IPv6 a utilizar como servidores DNS del sistema. Cada dirección puede tener opcionalmente un número de puerto separado con ":", un nombre de interfaz de red o un índice separado con "%", y un Indicador de Nombre de Servidor (SNI) separado con "#". Cuando se especifica una dirección IPv6 con un número de puerto, la dirección debe estar entre corchetes. Es decir, los formatos completos aceptables son "111.222.333.444:9953%ifname#example.com" para IPv4 y "[1111:2222::3333]:9953%ifname#example.com" para IPv6. Las solicitudes DNS se envían a uno de los servidores DNS listados en paralelo a servidores DNS por enlace adecuados adquiridos de systemd-networkd.service(8) o establecidos en tiempo de ejecución por aplicaciones externas. Por razones de compatibilidad, si esta configuración no se especifica, se utilizan en su lugar los servidores DNS listados en /etc/resolv.conf, si ese archivo existe y hay servidores configurados en él. Esta configuración, por defecto, es una lista vacía.

Añadido en la versión 213.

FallbackDNS=

Una lista separada por espacios de direcciones IPv4 e IPv6 a utilizar como servidores DNS de respaldo. Consulte DNS= para ver el formato aceptable de las direcciones. Cualquier servidor DNS por enlace obtenido de systemd-networkd.service(8) tiene precedencia sobre esta configuración, al igual que cualquier servidor configurado mediante DNS= arriba o /etc/resolv.conf. Por lo tanto, esta configuración solo se utiliza si no se conoce ninguna otra información del servidor DNS. Si no se proporciona esta opción, se utiliza en su lugar una lista de servidores DNS compilada.

Añadido en la versión 216.

Domains=

Una lista separada por espacios de dominios, opcionalmente precedidos por "~", utilizados para dos propósitos distintos descritos a continuación. Por defecto, es una lista vacía.

Cualquier dominio que *no* esté precedido por "~" se utiliza como sufijos de búsqueda al resolver nombres de host de etiqueta única (nombres de dominio que no contienen puntos), para calificarlos en nombres de dominio completos (FQDN). Estos "dominios de búsqueda" se procesan estrictamente en el orden en que se especifican, hasta que se encuentre el nombre con el sufijo adjunto. Por razones de compatibilidad, si esta configuración no se especifica, se utilizan en su lugar los dominios de búsqueda listados en /etc/resolv.conf con la palabra clave search, si ese archivo existe y hay dominios configurados en él.

Los dominios precedidos por "~" se denominan "dominios solo de ruta". Todos los dominios listados aquí ( *tanto dominios de búsqueda como dominios solo de ruta* después de eliminar el prefijo "~") definen una ruta de búsqueda que dirige preferentemente las consultas DNS a esta interfaz. Esta ruta de búsqueda solo tiene efecto cuando se conocen servidores DNS adecuados por enlace. Dichos servidores pueden definirse a través de la configuración DNS= (ver arriba) y dinámicamente en tiempo de ejecución, por ejemplo, a partir de concesiones DHCP. Si no se conocen servidores DNS por enlace, los dominios solo de ruta no tienen ningún efecto.

Utilice la construcción "~." (que se compone de "~" para indicar un dominio solo de ruta y "." para indicar el dominio raíz DNS, que es el sufijo implícito de todos los dominios DNS) para usar los servidores DNS definidos para este enlace preferentemente para todos los dominios.

Consulte "Protocolos y Enrutamiento" en systemd-resolved.service(8) para obtener detalles sobre cómo se utilizan los dominios de búsqueda y solo de ruta.

Tenga en cuenta que la configuración del dominio MulticastDNS "local" como dominio de búsqueda o de ruta tiene el efecto de dirigir las búsquedas para este dominio al DNS unicast clásico. Esto puede utilizarse para proporcionar compatibilidad con instalaciones heredadas que utilizan este dominio en un contexto DNS unicast, en contra de la asignación de la IANA de este dominio para fines exclusivamente de MulticastDNS. Los dominios de búsqueda y de ruta son un concepto de DNS unicast, *no pueden* utilizarse para resolver búsquedas de etiqueta única a través de MulticastDNS.

Añadido en la versión 229.

LLMNR=

Acepta un argumento booleano o "resolve". Controla el soporte de resolución de nombres multicast de enlace local (RFC 4795[2]) en el host local. Si es verdadero, habilita el soporte completo de respondedor y resolutor LLMNR. Si es falso, deshabilita ambos. Si se establece en "resolve", solo se habilita el soporte de resolución, pero se deshabilita la respuesta. Tenga en cuenta que systemd-networkd.service(8) también mantiene la configuración LLMNR por enlace. LLMNR se habilitará en un enlace solo si la configuración por enlace y la global están activadas.

DNSSEC=

Acepta un argumento booleano o "allow-downgrade".

Si se establece en true, todas las búsquedas de DNS se validarán con DNSSEC localmente (excluyendo LLMNR y Multicast DNS). Si se detecta que la respuesta a una solicitud de búsqueda es inválida, se devolverá un error de búsqueda a las aplicaciones. Tenga en cuenta que este modo requiere un servidor DNS que admita DNSSEC. Si el servidor DNS no admite DNSSEC correctamente, todas las validaciones fallarán.

Si se establece en "allow-downgrade", se intentará la validación DNSSEC, pero si el servidor no admite DNSSEC correctamente, el modo DNSSEC se desactivará automáticamente. Tenga en cuenta que este modo hace que la validación DNSSEC sea vulnerable a ataques de "downgrade", donde un atacante podría desencadenar una degradación a un modo sin DNSSEC al sintetizar una respuesta DNS que sugiera que DNSSEC no era compatible.

Si se establece en false, las búsquedas DNS no se validarán con DNSSEC.

Tenga en cuenta que la validación DNSSEC requiere la recuperación de datos DNS adicionales, y por lo tanto, resulta en una pequeña penalización en el tiempo de búsqueda DNS.

DNSSEC requiere conocimiento de "anclas de confianza" para probar la integridad de los datos. El ancla de confianza para el dominio raíz de Internet está integrada en el resolvedor; se pueden definir anclas de confianza adicionales con dnssec-trust-anchors.d(5). Las anclas de confianza pueden cambiar a intervalos regulares, y las anclas de confianza antiguas pueden ser revocadas. En tal caso, la validación DNSSEC no será posible hasta que se configuren anclas de confianza nuevas localmente o se actualice el paquete de software del resolvedor con la nueva ancla de confianza raíz. En efecto, cuando el ancla de confianza integrada sea revocada y DNSSEC= sea true, todas las búsquedas posteriores fallarán, ya que ya no se podrá probar si las búsquedas están firmadas correctamente o sin firmar válidamente. Si DNSSEC= se establece en "allow-downgrade", el resolvedor desactivará automáticamente la validación DNSSEC en tal caso.

Los programas cliente que busquen datos DNS serán informados si las búsquedas pudieron ser verificadas usando DNSSEC, o si los datos devueltos no pudieron ser verificados (ya sea porque los datos se encontraron sin firmar en el DNS, o el servidor DNS no admitía DNSSEC o no se conocían las anclas de confianza apropiadas). En este último caso, se asume que los programas cliente emplean un esquema secundario para validar los datos DNS devueltos, en caso de que sea necesario.

Se recomienda establecer DNSSEC= en true en sistemas donde se sabe que el servidor DNS admite DNSSEC correctamente, y donde las actualizaciones de software o anclas de confianza ocurren regularmente. En otros sistemas, se recomienda establecer DNSSEC= en "allow-downgrade".

Además de esta configuración global de DNSSEC, systemd-networkd.service(8) también mantiene configuraciones de DNSSEC por enlace. Para los servidores DNS del sistema (ver arriba), solo la configuración global de DNSSEC está en vigor. Para los servidores DNS por enlace, la configuración por enlace está en vigor, a menos que se desactive, en cuyo caso se utiliza la configuración global en su lugar.

Las zonas DNS privadas del sitio generalmente entran en conflicto con la operación de DNSSEC, a menos que se configure un ancla de confianza negativa (si la zona privada no está firmada) o positiva (si la zona privada está firmada) para ellas. Si se selecciona el modo "allow-downgrade", se intenta detectar zonas DNS privadas del sitio utilizando dominios de nivel superior (TLD) que no son conocidos por el servidor raíz de DNS. Esta lógica no funciona en todas las configuraciones de zona privada.

Por defecto es "no".

Añadido en la versión 229.

DNSOverTLS=

Acepta un argumento booleano o "opportunistic". Si es true, todas las conexiones al servidor se cifrarán. Tenga en cuenta que este modo requiere un servidor DNS que admita DNS-over-TLS y tenga un certificado válido. Si el nombre de host se especificó en DNS= usando el formato "address#server_name", se utiliza para validar su certificado y también para habilitar Server Name Indication (SNI) al abrir una conexión TLS. De lo contrario, el certificado se verifica contra la IP del servidor. Si el servidor DNS no admite DNS-over-TLS, todas las solicitudes DNS fallarán.

Cuando se establece en "opportunistic", se intentan enviar solicitudes DNS cifradas con DNS-over-TLS. Si el servidor DNS no admite TLS, DNS-over-TLS se deshabilita. Tenga en cuenta que este modo hace que DNS-over-TLS sea vulnerable a ataques de "downgrade", donde un atacante podría desencadenar una degradación a un modo no cifrado al sintetizar una respuesta que sugiera que DNS-over-TLS no era compatible. Si se establece en false, las búsquedas DNS se envían sobre UDP.

Tenga en cuenta que DNS-over-TLS requiere datos adicionales para establecer una conexión cifrada, y por lo tanto, resulta en una pequeña penalización en el tiempo de búsqueda DNS.

Tenga en cuenta que en el modo "opportunistic", el resolvedor no es capaz de autenticar el servidor, por lo que es vulnerable a ataques "man-in-the-middle".

Además de esta configuración global DNSOverTLS=, systemd-networkd.service(8) también mantiene configuraciones DNSOverTLS= por enlace. Para los servidores DNS del sistema (ver arriba), solo la configuración global DNSOverTLS= está en vigor. Para los servidores DNS por enlace, la configuración por enlace está en vigor, a menos que se desactive, en cuyo caso se utiliza la configuración global en su lugar.

Por defecto es "no".

Añadido en la versión 239.

Cache=

Acepta un booleano o "no-negative" como argumento. Si es "yes" (el valor predeterminado), la resolución de un nombre de dominio que ya se consultó anteriormente devolverá el resultado anterior siempre que aún sea válido, y por lo tanto, no resultará en una nueva solicitud de red. Tenga en cuenta que desactivar el almacenamiento en caché tiene una penalización de rendimiento, que es particularmente alta cuando se utiliza DNSSEC. Si es "no-negative", solo se almacenan en caché las respuestas positivas.

Tenga en cuenta que el almacenamiento en caché está desactivado por defecto para los servidores DNS locales del host. Consulte CacheFromLocalhost= para obtener más detalles.

Añadido en la versión 231.

CacheFromLocalhost=

Acepta un argumento booleano. Si es "no" (el valor predeterminado), y la respuesta proviene de una dirección IP local del host (como 127.0.0.1 o ::1), el resultado no se almacenará en caché para evitar un posible almacenamiento en caché local duplicado.

Añadido en la versión 248.

DNSStubListener=

Acepta un argumento booleano o uno de "udp" y "tcp". Si es "udp", un resolvedor stub DNS escuchará las solicitudes UDP en las direcciones 127.0.0.53 y 127.0.0.54, puerto 53. Si es "tcp", el stub escuchará las solicitudes TCP en las mismas direcciones y puerto. Si es "yes" (el valor predeterminado), el stub escucha las solicitudes UDP y TCP. Si es "no", el oyente stub se deshabilita.

El resolvedor stub DNS en 127.0.0.53 proporciona el conjunto completo de funciones del resolvedor local, que incluye la resolución LLMNR/MulticastDNS. El resolvedor stub DNS en 127.0.0.54 proporciona un resolvedor más limitado, que opera solo en modo "proxy", es decir, pasará la mayoría de los mensajes DNS relativamente sin modificar a los servidores DNS ascendentes actuales y de vuelta, pero no intentará procesar los mensajes localmente, y por lo tanto, no valida DNSSEC ni ofrece LLMNR/MulticastDNS. (Sin embargo, traducirá la comunicación a DNS-over-TLS si es necesario).

Tenga en cuenta que el oyente stub DNS se desactiva implícitamente cuando su dirección y puerto de escucha ya están en uso.

Añadido en la versión 232.

RefuseRecordTypes=

Acepta una lista de tipos de registros DNS separados por espacios. Se rechazarán los tipos de registro especificados en cada consulta. Esta opción se puede especificar varias veces. Si se especifica una cadena vacía, se borrarán todas las asignaciones anteriores.

Ejemplos:

RefuseRecordTypes=AAAA SRV TXT

Tenga en cuenta que para rechazar el registro AAAA (a diferencia de SRV, TXT, etc.) completamente, por favor, desactive también la pila IPv6 en el kernel con "sysctl -w net.ipv6.conf.all.disable_ipv6=1".

Añadido en la versión 258.

DNSStubListenerExtra=

Acepta una dirección IPv4 o IPv6 para escuchar. La dirección puede ir opcionalmente prefijada con un nombre de protocolo ("udp" o "tcp") separado por ":". Si no se especifica el protocolo, el servicio escuchará en UDP y TCP. También puede ir opcionalmente seguida de un número de puerto numérico con el separador ":". Cuando se especifica una dirección IPv6 con un número de puerto, la dirección debe estar entre corchetes. Si no se especifica el puerto, el servicio utiliza el puerto 53. Tenga en cuenta que esto es independiente del stub DNS principal configurado con DNSStubListener=, y solo configura sockets *adicionales* para escuchar. Esta opción se puede especificar varias veces. Si se asigna una cadena vacía, se borrarán todas las asignaciones anteriores. Por defecto está sin configurar.

Ejemplos:

DNSStubListenerExtra=192.168.10.10
DNSStubListenerExtra=2001:db8:0:f102::10
DNSStubListenerExtra=192.168.10.11:9953
DNSStubListenerExtra=[2001:db8:0:f102::11]:9953
DNSStubListenerExtra=tcp:192.168.10.12
DNSStubListenerExtra=udp:2001:db8:0:f102::12
DNSStubListenerExtra=tcp:192.168.10.13:9953
DNSStubListenerExtra=udp:[2001:db8:0:f102::13]:9953

Añadido en la versión 247.

ReadEtcHosts=

Acepta un argumento booleano. Si es "yes" (el valor predeterminado), systemd-resolved leerá /etc/hosts e intentará resolver hosts o direcciones utilizando las entradas del archivo antes de enviar la consulta a los servidores DNS.

Añadido en la versión 240.

ResolveUnicastSingleLabel=

Acepta un argumento booleano. Cuando es false (el valor predeterminado), systemd-resolved no resolverá consultas A y AAAA para nombres de etiqueta única a través de DNS clásico. Tenga en cuenta que dichos nombres aún pueden resolverse si se especifican dominios de búsqueda (consulte Domains= arriba), o mediante otros mecanismos, en particular a través de LLMNR o desde /etc/hosts. Cuando es true, las consultas para nombres de etiqueta única se reenviarán a los servidores DNS globales incluso si no se definen dominios de búsqueda.

Esta opción se proporciona para compatibilidad con configuraciones donde *no se utilizan servidores DNS públicos*. Reenviar nombres de etiqueta única a servidores que no están bajo su control no cumple con los estándares, consulte la **Declaración de la IAB**[4], y puede crear un riesgo para la privacidad y la seguridad.

Añadido en la versión 246.

resolved.conf — network name resolution configuration files

SYNOPSIS

/etc/systemd/resolved.conf, /run/systemd/resolved.conf, /usr/lib/systemd/resolved.conf

DESCRIPTION

The files resolved.conf are used to configure the systemd-resolved.service(8) system service, which is responsible for network name resolution.

The main file is read from /etc/systemd/resolved.conf. Additionally, the file from /usr/lib/systemd/resolved.conf may be included if it exists, as may be the file from /run/systemd/resolved.conf if it exists and is not empty.

See CONFIGURATION DIRECTORIES AND PRECEDENCE for more information about the directory-based configuration.

The configuration is split into sections, introduced by a single period (.) followed by the section name. Sections are case-insensitive.

Valid sections are [Resolve].

CONFIGURATION DIRECTORIES AND PRECEDENCE

The configuration files are initialized from a list of snippet files in the order described in systemd(1). Usually, these are /etc/systemd/resolved.conf, /run/systemd/resolved.conf and /usr/lib/systemd/resolved.conf. Each configuration file is a simple key=value mapping. Settings in files read later override settings in files read earlier. For more details on the precedence rules, see systemd(1).

If /etc/systemd/resolved.conf exists, the settings from /usr/lib/systemd/resolved.conf are ignored. If /run/systemd/resolved.conf exists and is not empty, the settings from /usr/lib/systemd/resolved.conf are ignored.

OPTIONS

The following options are available in the [Resolve] section:

DNS=
A space-separated list of IP addresses to use for DNS servers. If not specified, the DNS servers are discovered automatically via DHCP or from /etc/resolv.conf.
FallbackDNS=
A space-separated list of IP addresses to use as fallback DNS servers. These are used only if the primary DNS servers configured via DNS= or DHCP fail. If not specified, a set of well-known public DNS servers (currently 1.1.1.1, 1.0.0.1, 8.8.8.8, 8.8.4.4) are used.
Domains=
A space-separated list of domain names to be used for routing DNS queries. This is useful for split-horizon DNS setups. If not specified, the domain names are discovered automatically via DHCP.
DNSSEC=
Controls DNSSEC (DNS Security Extensions) processing. Takes a boolean argument or allow-downgrade. If no (default), DNSSEC is disabled. If yes, DNSSEC is enabled and authenticated DNS responses are required. If allow-downgrade, DNSSEC is enabled, but DNSSEC authentication is not required for responses from DNS servers that do not provide DNSSEC records. This is useful for compatibility with older DNS servers. Default is no.
DNSOverTLS=
Controls DNS-over-TLS (DoT) processing. Takes a boolean argument or opportunistic. If no (default), DoT is disabled. If yes, DoT is enabled and authenticated DNS responses are required. If opportunistic, DoT is enabled, but DNS responses are not authenticated. This is useful for compatibility with older DNS servers. Default is no.
MulticastDNS=
Controls Multicast DNS (mDNS) processing. Takes a boolean argument. If yes, mDNS is enabled. If no (default), mDNS is disabled. Default is no.
LLMNR=
Controls Link-Local Multicast Name Resolution (LLMNR) processing. Takes a boolean argument. If yes, LLMNR is enabled. If no (default), LLMNR is disabled. Default is no.
DHCPv6C=
Controls whether DHCPv6 client functionality is enabled. Takes a boolean argument. If yes, the DHCPv6 client is enabled. If no (default), it is disabled. Default is no.
NDPServer=
A space-separated list of IPv6 addresses of NDP servers. NDP stands for Neighbor Discovery Protocol, which is used in IPv6 for address resolution, router discovery, and prefix discovery. If not specified, NDP servers are not used.
NATKeepalive=
Controls whether NAT keepalive probes are sent. Takes a boolean argument. If yes, NAT keepalive probes are sent to keep NAT mappings alive. If no (default), NAT keepalive probes are disabled. Default is no.
ReadEtcHosts=
Controls whether /etc/hosts is read. Takes a boolean argument. If yes, /etc/hosts is read and entries are used. If no (default), /etc/hosts is not read. Default is no.
Cache=
Controls the caching of DNS records. Takes a boolean argument. If yes, DNS records are cached. If no (default), DNS records are not cached. Default is no.
StaleSe chấpTtl=

Controls the time-to-live (TTL) for stale DNS records. Stale records are DNS records that have expired according to their TTL, but are still kept in the cache. This feature allows systemd-resolved(8) continues to use the stale records to answer DNS queries, particularly when no valid response can be obtained from the upstream DNS servers. However, this does not apply to NXDOMAIN responses, as those are still perfectly valid responses. This feature enhances resilience against DNS infrastructure failures and outages.

systemd-resolved always attempts to reach the upstream DNS servers first, before providing the client application with any stale data. If this feature is enabled, cache will not be flushed when changing servers.

Added in version 254.
