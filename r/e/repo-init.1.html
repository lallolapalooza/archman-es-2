NOMBRE

repo - repo init - página del manual para repo init

SINOPSIS

repo init [opciones] [url del manifiesto]

DESCRIPCIÓN

Resumen

Inicializa un checkout del cliente repo en el directorio actual

OPCIONES

-h, --help
muestra este mensaje de ayuda y sale

Opciones de registro:

-v, --verbose
muestra toda la salida
-q, --quiet
solo muestra errores

Opciones de manifiesto:

-u URL, --manifest-url=URL
ubicación del repositorio de manifiesto
-b REVISIÓN, --manifest-branch=REVISIÓN
rama o revisión del manifiesto (usa HEAD para el predeterminado)
--manifest-upstream-branch=BRANCH
cuando se proporciona un commit a --manifest-branch, este es el nombre del ref de git en el que se puede encontrar el commit
-m NOMBRE.xml, --manifest-name=NOMBRE.xml
archivo de manifiesto inicial
-g GRUPO, --groups=GRUPO
restringe los proyectos del manifiesto a aquellos con grupo(s) especificado(s) [predeterminado|todos|G1,G2,G3|G4,-G5,-G6]
-p PLATAFORMA, --platform=PLATAFORMA
restringe los proyectos del manifiesto a aquellos con un grupo de plataforma especificado [auto|todos|ninguno|linux|darwin|...]
--submodules
sincroniza cualquier submódulo asociado con el repositorio del manifiesto
--standalone-manifest
descarga el manifiesto como un archivo estático en lugar de crear un checkout de git del repositorio del manifiesto
--manifest-depth=DEPTH
crea un clon superficial del repositorio del manifiesto con la profundidad dada (0 para clonación completa); consulta git clone (predeterminado: 0)

Opciones de checkout de manifiesto (solo):

-c, --current-branch
busca solo la rama del manifiesto actual del servidor (predeterminado)
--no-current-branch
busca todas las ramas del manifiesto del servidor
--tags
busca las etiquetas en el manifiesto
--no-tags
no busca las etiquetas en el manifiesto

Modos de checkout:

--mirror
crea una réplica de los repositorios remotos en lugar de un directorio de trabajo de cliente
--archive
realiza el checkout de un archivo en lugar de un repositorio git para cada proyecto. Consulta git archive.
--worktree
usa git-worktree para administrar proyectos

Optimizaciones de checkout de proyecto:

--reference=DIR
ubicación del directorio espejo
--dissociate
desasociar de los espejos de referencia después de la clonación
--depth=DEPTH
crea un clon superficial con la profundidad dada; consulta git clone
--partial-clone
realiza clonación parcial (https://gitscm.com/docs/gitrepositorylayout#_code_partialclone_code)
--no-partial-clone
desactiva el uso de clonación parcial (https://gitscm.com/docs/gitrepositorylayout#_code_partialclone_code)
--partial-clone-exclude=PARTIAL_CLONE_EXCLUDE
excluye los proyectos especificados (nombres de proyectos separados por comas) de la clonación parcial (https://gitscm.com/docs/gitrepositorylayout#_code_partialclone_code)
--clone-filter=CLONE_FILTER
filtro para usar con --partial-clone [predeterminado: blob:none]
--use-superproject
usa el superproyecto de manifiesto para sincronizar proyectos; implica -c
--no-use-superproject
desactiva el uso de superproyectos de manifiesto
--clone-bundle
habilita el uso de /clone.bundle en HTTP/HTTPS (predeterminado si no es --partial-clone)
--no-clone-bundle
desactiva el uso de /clone.bundle en HTTP/HTTPS (predeterminado si es --partial-clone)
--git-lfs
habilita el soporte de Git LFS
--no-git-lfs
desactiva el soporte de Git LFS

Opciones de versión de repo:

--repo-url=URL
ubicación del repositorio de repo ($REPO_URL)
--repo-rev=REV
rama o revisión de repo ($REPO_REV)
--no-repo-verify
no verifica el código fuente de repo

Otras opciones:

--config-name
Siempre pregunta por el nombre/correo electrónico

Multi-manifiesto:

--outer-manifest
opera comenzando desde el manifiesto más externo
--no-outer-manifest
no opera en manifiestos externos
--this-manifest-only
opera solo en este (sub)manifiesto
--no-this-manifest-only, --all-manifests
opera en este manifiesto y sus submanifiestos

Ejecuta `repo help init` para ver el manual detallado.

DETALLES

El comando 'repo init' se ejecuta una vez para instalar e inicializar repo. El código fuente más reciente de repo y la colección de manifiestos se descargan del servidor y se instalan en el directorio .repo/ dentro del directorio de trabajo actual.

Al crear un nuevo checkout, la URL del manifiesto es la única configuración requerida. Puede especificarse usando la opción --manifest-url, o como el primer argumento opcional.

El argumento opcional -b puede usarse para seleccionar la rama del manifiesto a descargar y usar. Si no se especifica ninguna rama, se usa la rama predeterminada del remoto. Esto es equivalente a usar -b HEAD.

El argumento opcional --manifest-upstream-branch puede usarse cuando se proporciona un commit a --manifest-branch (o -b), para especificar el nombre

NAME

repo init - Initialize a new workspace

SYNOPSIS

repo init [-h | --help]

repo init [-u URL] [-m MANIFEST] [-b BRANCH] [-d DIR] [-g GROUP] [-f] [--upload-history] [--dissociate] [--reference=DIR] [--dissociate-git-dir=DIR] [--template=TEMPLATE] [--online-only] [--depth=DEPTH] [--archive] [--no-clone-bundle] [--standalone-manifest] [--manifest-url=URL] [--no-tags] [--mirror]

DESCRIPTION

Initializes a new working directory for use with repo. This command will create a new directory in the current location, initialize the repo client within it, and then download the manifest. The manifest is an XML file that describes the Git repositories that make up the project, along with other metadata.

The manifest is fetched from the remote repository specified by the -u argument. If -u is not supplied, repo will look for a manifest in a file named .repo in the parent directory.

OPTIONS

-h, --help
Show the help message and exit.
-u URL
Remote repository where the manifest is located. This is usually a Git URL, e.g., https://github.com/example/project.
-m MANIFEST
Name of the manifest file to check out. Defaults to default.xml.
-b BRANCH
Manifest branch or tag to check out. Defaults to the branch or tag specified in the manifest, or master if not specified.
-d DIR
Directory to initialize. Defaults to the current directory.
-g GROUP
Manifest group to load. Defaults to default. This option is used to filter the projects included in the manifest.
-f
Always fetch unnecessary objects. Normally, repo tries to avoid fetching objects that are already available in the local repository.
--upload-history
Upload the Git history for the manifest repository to the server. This is used when creating a new manifest repository.
--reference=DIR
Local directory containing the content of a --mirror sync. This option is used to optimize the initial clone by reusing objects from the reference directory, thus reducing network traffic.
--dissociate-git-dir=DIR
Used with --reference to specify the Git directory from which objects are borrowed. This option is only effective if the Git repository has already been cloned.
--template=TEMPLATE
Directory containing the template files to be copied into the new repository. This can be used to pre-populate the working directory with common files and directories.
--online-only
Do not download any objects locally. This option is useful when creating a mirror or when initializing a client on a machine with limited network access.
--depth=DEPTH
Create a shallow clone with a history truncated to the specified number of commits. This option can significantly reduce the size of the repository and the time it takes to clone it.
--archive
Create an archive of the manifest instead of a Git clone. This option is useful for creating reproducible builds or for distributing the project to users who do not have Git installed.
--no-clone-bundle
Disable the use of clone bundles to bootstrap a new Git repository. This option may be necessary if there are issues with the local HTTP client or proxy configuration.
--standalone-manifest
Download the manifest directly from the specified --manifest-url as a static file, rather than setting up a manifest Git checkout. With this option, the manifest will be fully static and will not be re-downloaded during subsequent `repo init` and `repo sync` calls.
--manifest-url=URL
Specifies the URL from which to download the manifest file when --standalone-manifest is used.
--no-tags
Do not download tags for any Git repository. This option can save disk space and network bandwidth, especially for projects with a large number of tags.
--mirror
Create a mirror of the repository. A mirror contains all branches and tags of the repository, and is intended for use with the --reference option to speed up clones.

DETAILS

The -b argument can be used to specify a manifest branch or tag to check out. This is useful if you want to initialize your client with a specific version of the manifest. For example, to check out the v1.0 tag, you would use repo init -b v1.0.

The -m argument can be used to specify an alternate manifest to be used. If no manifest is specified, the manifest default.xml will be used.

If the --standalone-manifest argument is set, the manifest will be downloaded directly from the specified --manifest-url as a static file (rather than setting up a manifest git checkout). With --standalone-manifest, the manifest will be fully static and will not be re-downloaded during subsesquent `repo init` and `repo sync` calls.

The --reference option can be used to point to a directory that has the content of a --mirror sync. This will make the working directory use as much data as possible from the local reference directory when fetching from the server. This will make the sync go a lot faster by reducing data traffic on the network.

The --dissociate option can be used to borrow the objects from the directory specified with the --reference option only to reduce network transfer, and stop borrowing from them after a first clone is made by making necessary local copies of borrowed objects.

The --no-clone-bundle option disables any attempt to use $URL/clone.bundle to bootstrap a new Git repository from a resumeable bundle file on a content delivery network. This may be necessary if there are problems with the local Python HTTP client or proxy configuration, but the Git binary works.

Switching Manifest Branches

To switch to another manifest branch, `repo init -b otherbranch` may be used in an existing client. However, as this only updates the manifest, a subsequent `repo sync` (or `repo sync -d`) is necessary to update the working directory files.
