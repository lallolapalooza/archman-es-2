NOMBRE

resolved.conf, resolved.conf.d - Archivos de configuración de resolución de nombres de red

SINOPSIS

/etc/systemd/resolved.conf
/run/systemd/resolved.conf
/usr/local/lib/systemd/resolved.conf
/usr/lib/systemd/resolved.conf
/etc/systemd/resolved.conf.d/*.conf
/run/systemd/resolved.conf.d/*.conf
/usr/local/lib/systemd/resolved.conf.d/*.conf
/usr/lib/systemd/resolved.conf.d/*.conf

DESCRIPCIÓN

Estos archivos de configuración controlan la resolución de nombres DNS y LLMNR local.

DIRECTORIOS DE CONFIGURACIÓN Y PREFERENCIA

La configuración predeterminada se establece durante la compilación, por lo que la configuración solo es necesaria cuando es preciso desviarse de los valores predeterminados. El archivo de configuración principal se carga desde uno de los directorios enumerados en orden de prioridad, solo se utiliza el primer archivo encontrado: /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La versión del proveedor del archivo contiene entradas comentadas que muestran los valores predeterminados como guía para el administrador. También se pueden crear anulaciones locales creando "drop-ins", como se describe a continuación. El archivo de configuración principal también puede ser editado para este propósito (o una copia en /etc/ si se distribuye bajo /etc/), sin embargo, se recomienda usar "drop-ins" para la configuración local en lugar de modificar el archivo de configuración principal.

Además del archivo de configuración principal, los fragmentos de configuración "drop-in" se leen desde /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/ y /etc/systemd/*.conf.d/. Estos "drop-ins" tienen una mayor precedencia y anulan el archivo de configuración principal. Los archivos en los subdirectorios de configuración *.conf.d/ se ordenan por su nombre de archivo en orden lexicográfico, independientemente de en cuál de los subdirectorios residan. Cuando varios archivos especifican la misma opción, para las opciones que aceptan solo un valor único, la entrada en el archivo que se ordena último tiene precedencia, y para las opciones que aceptan una lista de valores, las entradas se recopilan a medida que ocurren en los archivos ordenados.

Cuando los paquetes necesitan personalizar la configuración, pueden instalar "drop-ins" bajo /usr/. Los archivos en /etc/ están reservados para el administrador local, quien puede usar esta lógica para anular los archivos de configuración instalados por los paquetes del proveedor. Se deben usar "drop-ins" para anular los "drop-ins" de paquetes, ya que el archivo de configuración principal tiene menor precedencia. Se recomienda prefijar todos los nombres de archivo en estos subdirectorios con un número de dos dígitos y un guion, para simplificar el orden. Esto también define un concepto de prioridades de "drop-in" para permitir que los proveedores de distribuciones envíen "drop-ins" dentro de un rango específico inferior al rango utilizado por los usuarios. Esto debería reducir el riesgo de que los "drop-ins" de paquetes anulen accidentalmente los "drop-ins" definidos por los usuarios. Se recomienda utilizar el rango 10-40 para los "drop-ins" en /usr/ y el rango 60-90 para los "drop-ins" en /etc/ y /run/, para asegurarse de que los "drop-ins" locales y transitorios tengan prioridad sobre los "drop-ins" enviados por el proveedor de la distribución.

Para deshabilitar un archivo de configuración proporcionado por el proveedor, la forma recomendada es colocar un enlace simbólico a /dev/null en el directorio de configuración en /etc/, con el mismo nombre de archivo que el archivo de configuración del proveedor.

OPCIONES

Las siguientes opciones están disponibles en la sección [Resolve]:

DNS=

Una lista separada por espacios de direcciones IPv4 e IPv6 a utilizar como servidores DNS del sistema. Cada dirección puede tomar opcionalmente un número de puerto separado por ":", un nombre o índice de interfaz de red separado por "%", y un Indicador de Nombre del Servidor (SNI) separado por "#". Cuando se especifica una dirección IPv6 con un número de puerto, la dirección debe estar entre corchetes. Es decir, los formatos completos aceptables son "111.222.333.444:9953%ifname#example.com" para IPv4 y "[1111:2222::3333]:9953%ifname#example.com" para IPv6. Las solicitudes DNS se envían a uno de los servidores DNS listados en paralelo a los servidores DNS adecuados por enlace adquiridos de systemd-networkd.service(8) o establecidos en tiempo de ejecución por aplicaciones externas. Por razones de compatibilidad, si esta configuración no se especifica, se utilizan los servidores DNS listados en /etc/resolv.conf en su lugar, si ese archivo existe y hay servidores configurados en él. Esta configuración se establece por defecto en la lista vacía.

Añadido en la versión 213.

FallbackDNS=

Una lista separada por espacios de direcciones IPv4 e IPv6 a utilizar como servidores DNS de reserva. Por favor, consulte DNS= para ver el formato aceptable de las direcciones. Cualquier servidor DNS por enlace obtenido de systemd-networkd.service(8) tiene precedencia sobre esta configuración, al igual que cualquier servidor establecido a través de DNS= arriba o /etc/resolv.conf. Por lo tanto, esta configuración solo se utiliza si no se conoce ninguna otra información de servidor DNS. Si esta opción no se proporciona, se utiliza una lista de servidores DNS compilada internamente en su lugar.

Añadido en la versión 216.

Domains=

Una lista separada por espacios de dominios, opcionalmente precedidos por "~", utilizados para dos propósitos distintos descritos a continuación. Por defecto, la lista está vacía.

Cualquier dominio no precedido por "~" se utiliza como sufijos de búsqueda al resolver nombres de host de un solo nivel (nombres de dominio que no contienen puntos), para calificarlos en nombres de dominio completos (FQDN). Estos "dominios de búsqueda" se procesan estrictamente en el orden en que se especifican, hasta que se encuentre el nombre con el sufijo añadido. Por razones de compatibilidad, si esta configuración no se especifica, se utilizan en su lugar los dominios de búsqueda listados en /etc/resolv.conf con la palabra clave search, si ese archivo existe y hay dominios configurados en él.

Los dominios precedidos por "~" se denominan "dominios solo de enrutamiento". Todos los dominios listados aquí (tanto dominios de búsqueda como dominios solo de enrutamiento después de eliminar el prefijo "~") definen una ruta de búsqueda que dirige preferentemente las consultas DNS a esta interfaz. Esta ruta de búsqueda solo tiene efecto cuando se conocen servidores DNS adecuados por enlace. Dichos servidores pueden definirse a través de la configuración DNS= (ver arriba) y dinámicamente en tiempo de ejecución, por ejemplo, a partir de arrendamientos DHCP. Si no se conocen servidores DNS por enlace, los dominios solo de enrutamiento no tienen efecto.

Utilice la construcción "~." (que se compone de "~" para indicar un dominio solo de enrutamiento y "." para indicar el dominio raíz DNS que es el sufijo implícito de todos los dominios DNS) para utilizar los servidores DNS definidos para este enlace preferentemente para todos los dominios.

Consulte "Protocolos y Enrutamiento" en systemd-resolved.service(8) para obtener detalles sobre cómo se utilizan los dominios de búsqueda y solo de enrutamiento.

Tenga en cuenta que configurar el dominio DNS Multicast "local" como dominio de búsqueda o de enrutamiento tiene el efecto de enrutar las búsquedas para este dominio al DNS unicast clásico. Esto puede utilizarse para proporcionar compatibilidad con instalaciones heredadas que utilizan este dominio en un contexto DNS unicast, en contra de la asignación de la IANA de este dominio a propósitos puramente DNS Multicast. Los dominios de búsqueda y de enrutamiento son un concepto de DNS unicast, no pueden utilizarse para resolver búsquedas de un solo nivel a través de DNS Multicast.

Añadido en la versión 229.

LLMNR=

Acepta un argumento booleano o "resolve". Controla el soporte de Resolución de Nombres de Multicast de Enlace Local (LLMNR) (RFC 4795[2]) en el host local. Si es true, habilita el soporte completo de respondedor y resolvedor de LLMNR. Si es false, deshabilita ambos. Si se establece en "resolve", solo se habilita el soporte de resolución, pero se deshabilita la respuesta. Tenga en cuenta que systemd-networkd.service(8) también mantiene configuraciones de LLMNR por enlace. LLMNR se habilitará en un enlace solo si la configuración por enlace y la global están activadas.

Añadido en la versión 216.

MulticastDNS=

Acepta un argumento booleano o "resolve". Controla el soporte de DNS Multicast (RFC 6762[3]) en el host local. Si es true, habilita el soporte completo de respondedor y resolvedor de DNS Multicast. Si es false, deshabilita ambos. Si se establece en "resolve", solo se habilita el soporte de resolución, pero se deshabilita la respuesta. Tenga en cuenta que systemd-networkd.service(8) también mantiene configuraciones de DNS Multicast por enlace. El DNS Multicast se habilitará en un enlace solo si la configuración por enlace y la global están activadas. habilitado en un enlace solamente si la configuración por enlace y la global están activadas.

Añadido en la versión 234.

DNSSEC=

Acepta un argumento booleano o "allow-downgrade".

Si se establece en true, todas las consultas DNS se validarán con DNSSEC localmente (excluyendo LLMNR y Multicast DNS). Si la respuesta a una solicitud de consulta se detecta como inválida, se devolverá un error de consulta a las aplicaciones. Tenga en cuenta que este modo requiere un servidor DNS que admita DNSSEC. Si el servidor DNS no admite DNSSEC correctamente, todas las validaciones fallarán.

Si se establece en "allow-downgrade", se intentará la validación DNSSEC, pero si el servidor no admite DNSSEC correctamente, el modo DNSSEC se deshabilitará automáticamente. Tenga en cuenta que este modo hace que la validación DNSSEC sea vulnerable a los ataques de "downgrade", donde un atacante podría ser capaz de provocar una degradación a modo no DNSSEC al sintetizar una respuesta DNS que sugiera que DNSSEC no era compatible.

Si se establece en false, las consultas DNS no se validarán con DNSSEC.

Tenga en cuenta que la validación DNSSEC requiere la recuperación de datos DNS adicionales y, por lo tanto, resulta en una pequeña penalización en el tiempo de consulta DNS.

DNSSEC requiere el conocimiento de "anclas de confianza" para probar la integridad de los datos. El ancla de confianza para el dominio raíz de Internet está integrada en el resolvedor; se pueden definir anclas de confianza adicionales con dnssec-trust-anchors.d(5). Las anclas de confianza pueden cambiar a intervalos regulares y las anclas de confianza antiguas pueden ser revocadas. En tal caso, la validación DNSSEC no es posible hasta que se configuren nuevas anclas de confianza localmente o el paquete de software del resolvedor se actualice con la nueva ancla de confianza raíz. En efecto, cuando el ancla de confianza integrada se revoca y DNSSEC= es true, todas las consultas posteriores fallarán, ya que ya no se puede demostrar si las consultas están firmadas correctamente o si no están firmadas válidamente. Si DNSSEC= se establece en "allow-downgrade", el resolvedor desactivará automáticamente la validación DNSSEC en tal caso.

Los programas cliente que consultan datos DNS serán informados si las consultas pudieron ser verificadas usando DNSSEC, o si los datos devueltos no pudieron ser verificados (ya sea porque los datos se encontraron sin firmar en el DNS, o porque el servidor DNS no admitía DNSSEC o no se conocían anclas de confianza apropiadas). En este último caso, se asume que los programas cliente emplean un esquema secundario para validar los datos DNS devueltos, si esto es necesario.

Se recomienda establecer DNSSEC= en true en sistemas donde se sabe que el servidor DNS admite DNSSEC correctamente, y donde las actualizaciones de software o de anclas de confianza ocurren regularmente. En otros sistemas, se recomienda establecer DNSSEC= en "allow-downgrade".

Además de esta configuración global de DNSSEC, systemd-networkd.service(8) también mantiene configuraciones de DNSSEC por enlace. Para los servidores DNS del sistema (ver arriba), solo la configuración global de DNSSEC está en efecto. Para los servidores DNS por enlace, la configuración por enlace está en efecto, a menos que no esté configurada, en cuyo caso se utiliza la configuración global en su lugar.

Las zonas DNS privadas del sitio generalmente entran en conflicto con la operación de DNSSEC, a menos que se configure un ancla de confianza negativa (si la zona privada no está firmada) o positiva (si la zona privada está firmada) para ellas. Si se selecciona el modo "allow-downgrade", se intenta detectar zonas DNS privadas del sitio utilizando dominios de nivel superior (TLD) que no son conocidos por el servidor raíz de DNS. Esta lógica no funciona en todas las configuraciones de zona privada.

Por defecto es "no".

Añadido en la versión 229.

DNSOverTLS=

Acepta un argumento booleano o "opportunistic". Si true, todas las conexiones al servidor estarán encriptadas. Tenga en cuenta que este modo requiere un servidor DNS que admita DNS-over-TLS y tenga un certificado válido. Si el nombre de host se especificó en DNS= usando el formato "address#server_name", se utiliza para validar su certificado y también para habilitar Server Name Indication (SNI) al abrir una conexión TLS. De lo contrario, el certificado se verifica contra la IP del servidor. Si el servidor DNS no admite DNS-over-TLS, todas las solicitudes DNS fallarán.

Cuando se establece en "opportunistic", se intentan enviar solicitudes DNS encriptadas con DNS-over-TLS. Si el servidor DNS no admite TLS, DNS-over-TLS se deshabilitará. Tenga en cuenta que este modo hace que DNS-over-TLS sea vulnerable a los ataques de "downgrade", donde un atacante podría ser capaz de provocar una degradación a modo no encriptado al sintetizar una respuesta que sugiera que DNS-over-TLS no era compatible. Si se establece en false, las consultas DNS se envían a través de UDP.

Tenga en cuenta que DNS-over-TLS requiere datos adicionales para enviar para configurar una conexión encriptada, y por lo tanto resulta en una pequeña penalización en el tiempo de consulta DNS.

Tenga en cuenta que en el modo "opportunistic", el resolvedor no es capaz de autenticar el servidor, por lo que es vulnerable a ataques "man-in-the-middle".

Además de esta configuración global DNSOverTLS=, systemd-networkd.service(8) también mantiene configuraciones DNSOverTLS= por enlace. Para los servidores DNS del sistema (ver arriba), solo la configuración global DNSOverTLS= está en efecto. Para los servidores DNS por enlace, la configuración por enlace está en efecto, a menos que no esté configurada, en cuyo caso se utiliza la configuración global en su lugar.

Por defecto es "no".

Añadido en la versión 239.

Cache=

Acepta un booleano o "no-negative" como argumento. Si es "yes" (por defecto), resolver un nombre de dominio que ya fue consultado anteriormente devolverá el resultado anterior siempre que siga siendo válido, y por lo tanto no resultará en una nueva solicitud de red. Tenga en cuenta que desactivar el caché tiene una penalización de rendimiento, que es particularmente alta cuando se usa DNSSEC. Si es "no-negative", solo se almacenan en caché las respuestas positivas.

Tenga en cuenta que el caché está desactivado por defecto para los servidores DNS locales del host. Consulte CacheFromLocalhost= para obtener más detalles.

Añadido en la versión 231.

CacheFromLocalhost=

Acepta un argumento booleano. Si es "no" (por defecto), y la respuesta proviene de una dirección IP local del host (como 127.0.0.1 o ::1), el resultado no se almacenará en caché para evitar un posible duplicado de caché local.

Añadido en la versión 248.

DNSStubListener=

Acepta un argumento booleano o uno de "udp" y "tcp". Si es "udp", un resolvedor stub DNS escuchará las solicitudes UDP en las direcciones 127.0.0.53 y 127.0.0.54, puerto 53. Si es "tcp", el stub escuchará las solicitudes TCP en las mismas direcciones y puerto. Si es "yes" (por defecto), el stub escuchará solicitudes UDP y TCP. Si es "no", el oyente stub estará deshabilitado.

El resolvedor stub DNS en 127.0.0.53 proporciona el conjunto completo de características del resolvedor local, que incluye ofrecer resolución LLMNR/MulticastDNS. El resolvedor stub DNS en 127.0.0.54 proporciona un resolvedor más limitado, que opera solo en modo "proxy", es decir, pasará la mayoría de los mensajes DNS relativamente sin modificar a los servidores DNS upstream actuales y de vuelta, pero no intentará procesar los mensajes localmente, y por lo tanto no valida DNSSEC, ni ofrece LLMNR/MulticastDNS. (Sin embargo, se traducirá a comunicación DNS-over-TLS si es necesario).

Tenga en cuenta que el oyente stub DNS se desactiva implícitamente cuando su dirección y puerto de escucha ya están en uso.

Añadido en la versión 232.

RefuseRecordTypes=

Acepta una lista de tipos de registro DNS separados por espacios. Los tipos de registro especificados en cada consulta serán rechazados. Esta opción se puede especificar varias veces. Si se especifica una cadena vacía, se borrarán todas las asignaciones anteriores.

Ejemplos:

RefuseRecordTypes=AAAA SRV TXT

Tenga en cuenta que para rechazar completamente el registro AAAA (a diferencia de SRV, TXT, etc.), desactive también la pila IPv6 en el kernel con "sysctl -w net.ipv6.conf.all.disable_ipv6=1".

Añadido en la versión 258.

DNSStubListenerExtra=

Acepta una dirección IPv4 o IPv6 para escuchar. La dirección puede tener opcionalmente un prefijo de nombre de protocolo ("udp" o "tcp") separado por ":". Si el protocolo no se especifica, el servicio escuchará tanto en UDP como en TCP. También puede tener opcionalmente un número de puerto numérico con el separador ":". Cuando se especifica una dirección IPv6 con un número de puerto, la dirección debe estar entre corchetes. Si el puerto no se especifica, el servicio utiliza el puerto 53. Tenga en cuenta que esto es independiente del stub DNS principal configurado con DNSStubListener=, y solo configura sockets *adicionales* para escuchar. Esta opción se puede especificar varias veces. Si se asigna una cadena vacía, se borrarán todas las asignaciones anteriores. Por defecto no está configurada.

Ejemplos:

DNSStubListenerExtra=192.168.10.10
DNSStubListenerExtra=2001:db8:0:f102::10
DNSStubListenerExtra=192.168.10.11:9953
DNSStubListenerExtra=[2001:db8:0:f102::11]:9953
DNSStubListenerExtra=tcp:192.168.10.12
DNSStubListenerExtra=udp:2001:db8:0:f102::12
DNSStubListenerExtra=tcp:192.168.10.13:9953
DNSStubListenerExtra=udp:[2001:db8:0:f102::13]:9953

Añadido en la versión 247.

ReadEtcHosts=

Acepta un argumento booleano. Si es "yes" (por defecto), systemd-resolved leerá /etc/hosts, e intentará resolver nombres o direcciones utilizando las entradas del archivo antes de enviar la consulta a los servidores DNS.

Añadido en la versión 240.

ResolveUnicastSingleLabel=

Acepta un argumento booleano. Cuando es false (por defecto), systemd-resolved no resolverá consultas A y AAAA para nombres de etiqueta única a través de DNS clásico. Tenga en cuenta que dichos nombres aún pueden resolverse si se especifican dominios de búsqueda (ver Domains= arriba), o mediante otros mecanismos, en particular a través de LLMNR o desde /etc/hosts. Cuando es true, las consultas para nombres de etiqueta única se reenviarán a los servidores DNS globales incluso si no hay dominios de búsqueda definidos.

Esta opción se proporciona para la compatibilidad con configuraciones donde *no se utilizan servidores DNS públicos*. Reenviar nombres de etiqueta única a servidores que no están bajo su control no cumple con los estándares, ver **Declaración del IAB**[4], y puede crear un riesgo de privacidad y seguridad.

Añadido en la versión 246.

StaleRetentionSec=SEGUNDOS

Acepta un valor de duración, que determina el tiempo que los registros de recursos DNS pueden retenerse en la caché más allá de su Tiempo de Vida (TTL). Esto permite que estos registros se devuelvan como registros obsoletos. Por defecto, este valor se establece en cero, lo que significa que los registros de recursos DNS no se almacenan en la caché después de que expira su TTL.

Esto es útil cuando ocurre un fallo en el servidor DNS o este se vuelve inaccesible. En tales casos, systemd-resolved(8) continúa utilizando los registros obsoletos para responder

NAME

resolved.conf.d — DNS server configuration directory

SYNOPSIS

resolved.conf.d/

DESCRIPTION

This directory is used to configure systemd-resolved.service(8). Configuration files are processed in lexicographical order, and the settings in later files override those in earlier ones. The files in this directory are included after the main resolved.conf(5) file.

This allows for modular configuration, where drop-in files can be used to extend or override settings defined in the main configuration file.

The following configuration options can be set:

DNS=address...
A space-separated list of IPv4 and/or IPv6 addresses to use for DNS queries. If this is set, the DNS servers listed in resolv.conf(5) are ignored.
FallbackDNS=address...
A space-separated list of IPv4 and/or IPv6 addresses to use as fallback DNS servers, if the primary DNS servers are unavailable. These servers are used only if the primary DNS servers fail to respond.
Domains=domain...
A space-separated list of DNS domains to use for search. If this is set, the search domains listed in resolv.conf(5) are ignored.
DNSSEC=setting
Controls DNSSEC validation. Possible values are no, allow-downgrade, and yes. Default is no.
DNSOverTLS=setting
Controls DNS-over-TLS (DoT) usage. Possible values are no, opportunistic, and yes. Default is no.
MulticastDNS=setting
Controls Multicast DNS (mDNS) usage. Possible values are no and yes. Default is yes.
LLMNR=setting
Controls Link-Local Multicast Name Resolution (LLMNR) usage. Possible values are no and yes. Default is yes.
DHCP=setting
Controls DHCP client usage. Possible values are no, yes, and ipv4. Default is yes.
NDPServer=address...
A space-separated list of IPv4 and/or IPv6 addresses to use for DNS-SD server discovery. This is used in conjunction with MulticastDNS.
DNSStubListener=setting
Controls whether the DNS stub listener is enabled. Possible values are no and yes. Default is yes.
DNSStubListenerOnly=setting
If set to yes, systemd-resolved.service(8) will only listen on the DNS stub listener socket (127.0.0.53:53). This is useful for preventing conflicts with other DNS servers.
ReadEtcHosts=setting
If set to no, systemd-resolved.service(8) will not read the /etc/hosts file. Default is yes.
ResolveUnicastSingleLabel=setting
If set to yes, systemd-resolved.service(8) will attempt to resolve single-label hostnames using DNS. This is generally discouraged, as it can lead to security vulnerabilities. Default is no.
ResolveSquashedNetworks=setting
If set to yes, systemd-resolved.service(8) will attempt to resolve squashed networks. This is useful for some internal networks that use private IP addresses. Default is no.
UPnpxRetransmissionIntervalSec=time
Sets the retransmission interval for UPnP requests. Default is 250ms.
UPnpxQueueLength=count
Sets the queue length for UPnP requests. Default is 10.
UPnpxServerQueueLength=count
Sets the queue length for UPnP server requests. Default is 10.
UPnpxDefaultTTL=time
Sets the default TTL for UPnP records. Default is 300 seconds.
UPnpxLLMNR=setting
Enables or disables LLMNR for UPnP. Default is yes.
UPnpxMDNS=setting
Enables or disables mDNS for UPnP. Default is yes.
UPnpxDNS=setting
Enables or disables DNS for UPnP. Default is yes.
UPnpxDHCP=setting
Enables or disables DHCP for UPnP. Default is yes.
UPnpxDNSSEC=setting
Enables or disables DNSSEC for UPnP. Default is no.
UPnpxDNSOverTLS=setting
Enables or disables DNS-over-TLS for UPnP. Default is no.
UPnpxMulticastDNS=setting
Enables or disables Multicast DNS for UPnP. Default is yes.
UPnpxLLMNR=setting
Enables or disables LLMNR for UPnP. Default is yes.
UPnpxResolveUnicastSingleLabel=setting
If set to yes, systemd-resolved.service(8) will attempt to resolve single-label hostnames using UPnP. Default is no.
UPnpxResolveSquashedNetworks=setting
If set to yes, systemd-resolved.service(8) will attempt to resolve squashed networks using UPnP. Default is no.
Cache=setting
Controls DNS caching. Possible values are no and yes. Default is yes.
CacheSize=size
Sets the DNS cache size. Default is 1000 entries.
DNSSECValidation=setting
Controls DNSSEC validation. Possible values are no, allow-downgrade, and yes. Default is no.
DNSSECRootKey=key
Sets the DNSSEC root key. This is used for validating DNSSEC signatures.
DNSSECAllowDowngrade=setting
If set to yes, DNSSEC validation will allow downgrades. Default is no.
DNSSECEnableCache=setting
If set to yes, DNSSEC cache will be enabled. Default is yes.
DNSSECNoCache=setting
If set to yes, DNSSEC cache will be disabled. Default is no.
DNSSECNoCheckChain=setting
If set to yes, DNSSEC chain checking will be disabled. Default is no.
DNSSECNoCheckExpired=setting
If set to yes, DNSSEC expired checking will be disabled. Default is no.
DNSSECNoCheckSig=setting
If set to yes, DNSSEC signature checking will be disabled. Default is no.
DNSSECNoCheckValid=setting
If set to yes, DNSSEC valid checking will be disabled. Default is no.
DNSSECNoCheckNSEC=setting
If set to yes, DNSSEC NSEC checking will be disabled. Default is no.
DNSSECNoCheckNSEC3=setting
If set to yes, DNSSEC NSEC3 checking will be disabled. Default is no.
DNSSECNoCheckNSEC3Hash=setting
