DESCRIPCIÓN

Resumen

Utilidad de inspección de manifiestos

OPCIONES

-h, --help
mostrar esta ayuda y salir
-r, --revision-as-HEAD
guardar revisiones como HEAD actual
-m NOMBRE.xml, --manifest-name=NOMBRE.xml
manifiesto temporal a usar para esta sincronización
--suppress-upstream-revision
si está en modo -r, no escribir el campo upstream (solo útil si los nombres de rama para un manifiesto sha1 son sensibles)
--suppress-dest-branch
si está en modo -r, no escribir el campo dest-branch (solo útil si los nombres de rama para un manifiesto sha1 son sensibles)
--format=FORMATO
formato de salida: xml, json (por defecto: xml)
--pretty
formatear la salida para que sea legible por humanos
--no-local-manifests
ignorar manifiestos locales
-o -|NOMBRE.xml, --output-file=-|NOMBRE.xml
archivo donde guardar el manifiesto. (Prefijo de nombre de archivo para árbol múltiple.)

Opciones de registro:

-v, --verbose
mostrar toda la salida
-q, --quiet
mostrar solo errores

Opciones multimanifiesto:

--outer-manifest
operar comenzando desde el manifiesto más externo
--no-outer-manifest
no operar en manifiestos externos
--this-manifest-only
operar solo en este (sub)manifiesto
--no-this-manifest-only, --all-manifests
operar en este manifiesto y sus submanifiestos

Ejecute `repo help manifest` para ver el manual detallado.

DETALLES

Con la opción -o, exporta el manifiesto actual para su inspección. El manifiesto y (si está presente) los local_manifests/ se combinan para producir un único archivo de manifiesto. Este archivo puede almacenarse en un repositorio Git para usarlo durante futuras invocaciones de 'repo init'.

La opción -r se puede usar para generar un archivo de manifiesto con las revisiones de proyecto establecidas en el hash del commit actual. Estos se conocen como "manifiestos con revisiones bloqueadas", ya que no siguen una rama en particular. En este caso, el atributo 'upstream' se establece en la referencia en la que estábamos cuando se generó el manifiesto. El atributo 'dest-branch' se establece para indicar la referencia remota a la que se enviarán los cambios a través de 'repo upload'.

Se admiten varios formatos de salida a través de --format. La salida predeterminada es XML, y los formatos son generalmente "condensados". Use --pretty para variaciones más legibles por humanos.

Formato de manifiesto de repo

Un manifiesto de repo describe la estructura de un cliente de repo; es decir, los directorios que son visibles y de dónde deben obtenerse con git.

La estructura básica de un manifiesto es un repositorio Git vacío que contiene un único archivo XML `default.xml` en el directorio superior.

Los manifiestos se controlan inherentemente por versión, ya que se conservan dentro de un repositorio Git. Las actualizaciones de los manifiestos se obtienen automáticamente durante `repo sync`.

Por motivos de compatibilidad entre las versiones del repositorio, todos los elementos desconocidos se ignoran silenciosamente. Sin embargo, repo se reserva todos los nombres posibles para sí mismo para uso futuro. Si desea utilizar elementos personalizados, el espacio de nombres `x-*` está reservado para ese propósito, y repo garantiza que nunca asignará nombres correspondientes.

A continuación, se describe cada elemento y sus atributos.

Elemento manifest

El elemento raíz del archivo.

Elemento notice

Texto arbitrario que se muestra a los usuarios cada vez que `repo sync` finaliza. El contenido se pasa tal cual existe en el manifiesto.

Elemento remote

Se pueden especificar uno o más elementos remote. Cada elemento remote especifica una URL de Git compartida por uno o más proyectos y (opcionalmente) el servidor de revisión de Gerrit a través del cual estos proyectos suben cambios.

Atributo `name`: Un nombre corto único para este archivo de manifiesto. El nombre especificado aquí se utiliza como el nombre remoto en el `.git/config` de cada proyecto y, por lo tanto, está disponible automáticamente para comandos como `git fetch`, `git remote`, `git pull` y `git push`.

Atributo `alias`: El alias, si se especifica, se utiliza para anular `name` y establecerlo como el nombre remoto en el `.git/config` de cada proyecto. Su valor puede duplicarse, mientras que el atributo `name` debe ser único en el archivo de manifiesto. Esto ayuda a que cada proyecto pueda tener el mismo nombre remoto que en realidad apunta a una URL remota diferente.

Atributo `fetch`: El prefijo de la URL de Git para todos los proyectos que utilizan este remoto. El nombre de cada proyecto se agrega a este prefijo para formar la URL real utilizada para clonar el proyecto.

Atributo `pushurl`: El prefijo de la URL de "push" de Git para todos los proyectos que utilizan este remoto. El nombre de cada proyecto se agrega a este prefijo para formar la URL real utilizada para hacer "git push" al proyecto. Este atributo es opcional; si no se especifica, "git push" utilizará la misma URL que el atributo `fetch`.

Atributo `review`: Nombre de host del servidor Gerrit donde se suben las revisiones mediante `repo upload`. Este atributo es opcional; si no se especifica, `repo upload` no funcionará.

Atributo `revision`: Nombre de una rama de Git (por ejemplo, `main` o `refs/heads/main`). Los remotos con su propia revisión anularán la revisión predeterminada.

Elemento default

Se puede especificar como máximo un elemento default. Sus atributos remote y revision se utilizan cuando un elemento project no especifica su propio atributo remote o revision.

Atributo `remote`: Nombre de un elemento remote previamente definido. Los elementos project que carecen de su propio atributo remote utilizarán este remoto.

Atributo `revision`: Nombre de una rama de Git (por ejemplo, `main` o `refs/heads/main`). Los elementos project que carecen de su propio atributo revision utilizarán esta revisión.

Atributo `dest-branch`: Nombre de una rama de Git (por ejemplo, `main`). Los elementos project que no establezcan su propio `dest-branch` heredarán este valor. Si este valor no se establece, los proyectos utilizarán `revision` por defecto en su lugar.

Atributo `upstream`: Nombre de la referencia de Git en la que se puede encontrar un sha1. Se utiliza al sincronizar un manifiesto con revisión bloqueada en modo -c para evitar tener que sincronizar todo el espacio de referencias. Los elementos project que no establezcan su propio `upstream` heredarán este valor.

Atributo `sync-j`: Número de trabajos paralelos a utilizar al sincronizar.

Atributo `sync-c`: Se establece en `true` para sincronizar solo la rama de Git dada (especificada en el atributo `revision`) en lugar de todo el espacio de referencias. Los elementos project que carezcan de su propio elemento `sync-c` utilizarán este valor.

Atributo `sync-s`: Se establece en `true` para sincronizar también los subproyectos.

Atributo `sync-tags`: Se establece en `false` para sincronizar solo la rama de Git dada (especificada en el atributo `revision`) en lugar de las otras etiquetas de referencia.

Elemento manifest-server

Se puede especificar como máximo un manifest-server. El atributo url se utiliza para especificar la URL de un servidor de manifiestos, que es un servicio XML RPC.

Consulte la [documentación de sync inteligente](./smart-sync.md) para obtener más detalles.

Elemento submanifest

Se pueden especificar uno o más elementos submanifest. Cada elemento describe un único manifiesto que se extraerá como hijo.

Atributo `name`: Un nombre único (dentro del (sub)manifiesto actual) para este submanifiesto. Actúa como valor predeterminado para `revision` más abajo. Se puede usar el mismo nombre para submanifiestos con diferentes (sub)manifiestos padres.

Atributo `remote`: Nombre de un elemento remote previamente definido. Si no se proporciona, se utiliza el remoto dado por el elemento default.

Atributo `project`: El nombre del proyecto del manifiesto. El nombre del proyecto se agrega a la URL de fetch de su remoto para generar la URL real con la que configurar el remoto de Git. La URL se forma como:

${remote_fetch}/${project_name}.git

donde ${remote_fetch} es el atributo fetch del remoto y ${project_name} es el atributo name del proyecto. El sufijo ".git" siempre se agrega ya que repo asume que el upstream es un bosque de repositorios Git en desuso. Si el proyecto tiene un elemento padre, su nombre se prefijará con el del padre.

El nombre del proyecto debe coincidir con el nombre que conoce Gerrit, si Gerrit se está utilizando para revisiones de código.

`project` no debe estar vacío y no puede ser una ruta absoluta ni utilizar componentes de ruta "." o "..". Siempre se interpreta en relación con la configuración de fetch del remoto, por lo que si se necesita una ruta base diferente, declare un remoto diferente con la nueva configuración necesaria.

Si no se proporciona, se utilizarán el remoto y el proyecto de este manifiesto: `remote` no puede ser suministrado.

Los proyectos de un submanifiesto y sus submanifiestos se agregan al grupo `submanifest::path:<prefijo_ruta>`.

Atributo `manifest-name`: El nombre del archivo de manifiesto en el proyecto de manifiesto. Si no se proporciona, se utiliza `default.xml`.

Atributo `revision`: Nombre de una rama de Git (por ejemplo, "main" o "refs/heads/main"), etiqueta (por ejemplo, "refs/tags/stable") o un hash de commit. Si no se proporciona, se utiliza `name`.

Atributo `path`: Una ruta opcional relativa al directorio superior del cliente de repo donde se colocará el directorio de trabajo del submanifiesto del cliente de repo. Si no se proporciona, se utiliza `revision`. Si el proyecto tiene un elemento padre, su ruta se prefijará con la del padre.

`path` no puede ser una ruta absoluta ni utilizar componentes de ruta "." o "..". Estas restricciones no se aplican a [Manifiestos Locales].

Atributo `groups`: Lista de grupos adicionales a los que pertenecen todos los proyectos del submanifiesto incluido. Esto se aplica de forma acumulativa y recursiva, lo que significa que todos los proyectos de los submanifiestos llevan todos los grupos de submanifiestos padres. Misma sintaxis que el elemento correspondiente de `project`.

Atributo `default-groups`: La lista de grupos de manifiestos a sincronizar si no se especificó ningún parámetro `--groups=` al inicializar. Cuando esa lista está vacía, utilice esta lista en lugar de "default" como la lista de grupos a sincronizar.

Elemento project

Se pueden especificar uno o más elementos project. Cada elemento describe un único repositorio Git que se clonará en el espacio de trabajo del cliente de repo. Puede especificar sub-módulos de Git creando un proyecto anidado. Los sub-módulos de Git serán reconocidos automáticamente y heredarán los atributos de su padre, pero estos pueden ser anulados por un elemento project especificado explícitamente.

Atributo `name`: Un nombre único para este proyecto. El nombre del proyecto se agrega a la URL de fetch de su remoto para generar la URL real con la que configurar el remoto de Git. La URL se forma como:

${remote_fetch}/${project_name}.git

donde ${remote_fetch} es el atributo fetch del remoto y ${project_name} es el atributo name del proyecto. El sufijo ".git" siempre se agrega ya que repo asume que el upstream es un bosque de repositorios Git en desuso. Si el proyecto tiene un elemento padre, su nombre se prefijará con el del padre.

El nombre del proyecto debe coincidir con el nombre que conoce Gerrit, si Gerrit se está utilizando para revisiones de código.

"name" no debe estar vacío y no puede ser una ruta absoluta ni utilizar componentes de ruta "." o "..". Siempre se interpreta en relación con la configuración de fetch del remoto, por lo que si se necesita una ruta base diferente, declare un remoto diferente con la nueva configuración necesaria. Estas restricciones no se aplican a [Manifiestos Locales].

Atributo `path`: Una ruta opcional relativa al directorio superior del cliente de repo donde se colocará el directorio de trabajo de Git para este proyecto. Si no se proporciona, se utiliza el `name` del proyecto. Si el proyecto tiene un elemento padre, su ruta se prefijará con la del padre.

"path" no puede ser una ruta absoluta ni utilizar componentes de ruta "." o "..". Estas restricciones no se aplican a [Manifiestos Locales].

Si desea colocar archivos en la raíz de la extracción (por ejemplo, un README o un Makefile u otro script de compilación), utilice los elementos [copyfile] o [linkfile] en su lugar.

Atributo `remote`: Nombre de un elemento remote previamente definido. Si no se proporciona, se utiliza el remoto dado por el elemento default.

Atributo `revision`: Nombre de la rama de Git que el manifiesto quiere rastrear para este proyecto. Los nombres pueden ser relativos a refs/heads (por ejemplo, solo "main") o absolutos (por ejemplo, "refs/heads/main"). Las etiquetas y/o SHA-1 explícitos deberían funcionar en teoría, pero no se han probado exhaustivamente. Si no se proporciona, se utiliza la revisión dada por el elemento remote, si corresponde, de lo contrario, se utiliza el elemento default.

Atributo `dest-branch`: Nombre de una rama de Git (por ejemplo, `main`). Al usar `repo upload`, los cambios se enviarán para revisión de código en esta rama. Si no se especifica ni aquí ni en el elemento default, se utiliza `revision` en su lugar.

Atributo `groups`: Lista de grupos a los que pertenece este proyecto, separados por espacios en blanco o comas. Todos los proyectos pertenecen al grupo "all", y cada proyecto pertenece automáticamente a un grupo con su nombre: `name` y ruta: `path`. Por ejemplo, para `<project name="monkeys" path="barrel-of"/>`, esa definición de proyecto está implícitamente en los siguientes grupos de manifiesto: default, name:monkeys y path:barrel-of. Si coloca un proyecto en el grupo "notdefault", no será descargado automáticamente por repo. Si el proyecto tiene un elemento padre, el `name` y `path` aquí son los que tienen prefijo.

Atributo `sync-c`: Se establece en `true` para sincronizar solo la rama de Git dada (especificada en el atributo `revision`) en lugar de todo el espacio de referencias.

Atributo `sync-s`: Se establece en `true` para sincronizar también los subproyectos.

Atributo `upstream`: Nombre de la referencia de Git en la que se puede encontrar un sha1. Se utiliza al sincronizar un manifiesto con revisión bloqueada en modo -c para evitar tener que sincronizar todo el espacio de referencias.

>

Atributo `clone-depth`: Establece la profundidad a utilizar al buscar este proyecto. Si se especifica, este valor anulará cualquier valor dado a `repo init` con la opción --depth en la línea de comandos.

Atributo `force-path`: Establece en verdadero para forzar que este proyecto cree el repositorio espejo local de acuerdo con su atributo `path` (si se proporciona) en lugar del atributo `name`. Este atributo solo se aplica a los espejos locales que se sincronizan; se ignorará al sincronizar los proyectos en el directorio de trabajo de un cliente.

Elemento extend-project

Modifica los atributos del proyecto con nombre.

Este elemento es principalmente útil en un archivo de manifiesto local, para modificar los atributos de un proyecto existente sin reemplazar completamente la definición existente del proyecto. Esto hace que el manifiesto local sea más robusto frente a cambios en el manifiesto original.

Atributo `path`: Si se especifica, limita el cambio a los proyectos registrados en la ruta especificada, en lugar de a todos los proyectos con el nombre dado.

Atributo `dest-path`: Si se especifica, una ruta relativa al directorio principal del cliente de repo donde debe colocarse el directorio de trabajo de Git para este proyecto. Esto se utiliza para mover un proyecto en la extracción al anular la configuración existente de `path`.

Atributo `groups`: Lista de grupos adicionales a los que pertenece este proyecto. Misma sintaxis que el elemento correspondiente de `project`.

Atributo `revision`: Si se especifica, anula la revisión del proyecto original. Misma sintaxis que el elemento correspondiente de `project`.

Atributo `remote`: Si se especifica, anula el remoto del proyecto original. Misma sintaxis que el elemento correspondiente de `project`.

Atributo `dest-branch`: Si se especifica, anula el `dest-branch` del proyecto original. Misma sintaxis que el elemento correspondiente de `project`.

Atributo `upstream`: Si se especifica, anula el `upstream` del proyecto original. Misma sintaxis que el elemento correspondiente de `project`.

Atributo `base-rev`: Si se especifica, agrega una verificación contra la revisión que se está extendiendo. El análisis del manifiesto fallará y dará una lista de extensiones que no coinciden si las revisiones que se están extendiendo han cambiado desde que se estableció `base-rev`. Está destinado a su uso con manifiestos en capas que utilizan revisiones de hash para evitar que las ramas de parche oculten revisiones de upstream más nuevas. También compara referencias nombradas como ramas o etiquetas, pero es engañoso si se utilizan ramas como `base-rev`. Misma sintaxis que el elemento correspondiente de `project`.

Elemento annotation

Se pueden especificar cero o más elementos `annotation` como hijos de un elemento `project` o `remote`. Cada elemento describe un par nombre-valor. Para los proyectos, este par nombre-valor se exportará al entorno de cada proyecto durante un comando `forall`, prefijado con `REPO__`. Además, hay un atributo opcional "keep" que acepta los valores no sensibles a mayúsculas y minúsculas "true" (por defecto) o "false". Este atributo determina si la anotación se mantendrá o no cuando se exporte con el subcomando `manifest`.

Elemento copyfile

Se pueden especificar cero o más elementos `copyfile` como hijos de un elemento `project`. Cada elemento describe un par origen-destino de archivos; el archivo "src" se copiará al lugar "dest" durante el comando `repo sync`.

"src" es relativo al proyecto, "dest" es relativo a la parte superior del árbol. No se permite copiar desde rutas fuera del proyecto o hacia rutas fuera del cliente de repo.

"src" y "dest" deben ser archivos. Los directorios o enlaces simbólicos no están permitidos. Las rutas intermedias tampoco deben ser enlaces simbólicos.

Los directorios padre de "dest" se crearán automáticamente si faltan.

Elemento linkfile

Es como `copyfile` y se ejecuta al mismo tiempo que `copyfile`, pero en lugar de copiar, crea un enlace simbólico.

El enlace simbólico se crea en "dest" (relativo a la parte superior del árbol) y apunta a la ruta especificada por "src", que es una ruta en el proyecto.

Los directorios padre de "dest" se crearán automáticamente si faltan.

El destino del enlace simbólico puede ser un archivo o un directorio, pero no puede apuntar fuera del cliente de repo.

Elemento remove-project

Elimina un proyecto de la tabla de manifiestos interna, permitiendo posiblemente que un elemento de proyecto posterior en el mismo archivo de manifiesto reemplace el proyecto con una fuente diferente.

Este elemento es principalmente útil en un archivo de manifiesto local, donde el usuario puede eliminar un proyecto y, posiblemente, reemplazarlo con su propia definición.

Se puede usar el `name` del proyecto o la `path` del proyecto para especificar el objetivo de eliminación, lo que significa que uno de ellos es obligatorio. Si solo se especifica `name`, se eliminan todos los proyectos con ese nombre.

Si se especifican tanto `name` como `path`, solo se eliminan los proyectos con el mismo nombre y ruta, lo que significa que se conservan los proyectos con el mismo nombre pero en otras ubicaciones.

Si solo se especifica `path`, se elimina un proyecto coincidente independientemente de su nombre. La lógica se comporta de manera similar a si ambos estuvieran especificados.

Atributo `optional`: Establece en verdadero para ignorar los elementos `remove-project` sin un elemento `project` coincidente.

Atributo `base-rev`: Si se especifica, agrega una verificación contra la revisión que se está eliminando. El análisis del manifiesto fallará y dará una lista de eliminaciones que no coinciden si las revisiones que se están eliminando han cambiado desde que se estableció `base-rev`. Está destinado a su uso con manifiestos en capas que utilizan revisiones de hash para evitar que las ramas de parche oculten revisiones de upstream más nuevas. También compara referencias nombradas como ramas o etiquetas, pero es engañoso si se utilizan ramas como `base-rev`. Misma sintaxis que el elemento correspondiente de `project`.

Elemento repo-hooks

NB: Consulte la [documentación práctica](./repo-hooks.md) para utilizar los ganchos de repo.

Solo se puede especificar un elemento `repo-hooks` a la vez. Intentar redefinirlo fallará el análisis.

Atributo `in-project`: El proyecto donde se definen los ganchos. El valor debe coincidir con el atributo `name` (no con el atributo `path`) de un elemento `project` definido previamente.

Atributo `enabled-list`: Lista de ganchos a usar, separados por espacios en blanco o comas.

Elemento superproject

*** *Nota*: Esto es actualmente un trabajo en curso. ***

NB: Consulte la [documentación de git superprojects]( https://en.wikibooks.org/wiki/Git/Submodules_and_Superprojects) para obtener información de fondo.

Este elemento se utiliza para especificar la URL del superproyecto. Tiene "name" y "remote" como atributos. Solo "name" es obligatorio, mientras que los otros tienen valores predeterminados razonables. Se puede especificar como máximo un superproyecto. Intentar redefinirlo fallará el análisis.

Atributo `name`: Un nombre único para el superproyecto. Este atributo tiene el mismo significado que el atributo `name` del proyecto. Consulte el [elemento project](#element-project) para obtener más información.

Atributo `remote`: Nombre de un elemento remoto definido previamente. Si no se proporciona, se utiliza el remoto dado por el elemento predeterminado.

Atributo `revision`: Nombre de la rama de Git que el manifiesto quiere rastrear para este superproyecto. Si no se proporciona, se utiliza la revisión dada por el elemento `remote` si es aplicable, de lo contrario se utiliza el elemento predeterminado.

Elemento contactinfo

*** *Nota*: Esto es actualmente un trabajo en curso. ***

Este elemento se utiliza para permitir que los autores de manifiestos se registren a sí mismos con información de contacto. Tiene "bugurl" como atributo obligatorio. Este elemento puede repetirse, y cualquier entrada posterior anulará las anteriores. Esto permitiría a los autores de manifiestos que extienden manifiestos especificar su propia información de contacto.

Atributo `bugurl`: La URL para registrar un error contra el propietario del manifiesto.

Elemento include

Este elemento proporciona la capacidad de incluir otro archivo de manifiesto en el manifiesto de origen. Se aplican las reglas normales para incluir el manifiesto de destino: debe ser un manifiesto utilizable por sí mismo.

Atributo `name`: el manifiesto a incluir, especificado en relación con la raíz del repositorio de manifiestos.

"name" no puede ser una ruta absoluta ni utilizar componentes de ruta "." o "..". Estas restricciones no se aplican a [Manifiestos Locales].

Atributo `groups`: Lista de grupos adicionales a los que pertenecen todos los proyectos del manifiesto incluido. Esto se agrega y se aplica recursivamente, lo que significa que todos los proyectos en los manifiestos incluidos llevan todos los grupos de inclusión padre. Misma sintaxis que el elemento correspondiente de `project`.

Atributo `revision`: Nombre de una rama de Git (por ejemplo, `main` o `refs/heads/main`) a la que pertenecen todos los proyectos del manifiesto incluido por defecto.

Manifiestos Locales

Se pueden agregar remotos y proyectos adicionales a través de archivos de manifiestos locales almacenados en `$TOP_DIR/.repo/local_manifests/*.xml`.

Por ejemplo:

$ ls .repo/local_manifests
local_manifest.xml another_local_manifest.xml
$ cat .repo/local_manifests/local_manifest.xml
<?xml version="1.0" encoding="UTF-8"?> <manifest>
<project path="manifest"
name="tools/manifest" />
<project path="platform-manifest"
name="platform/manifest" />
</manifest>

Los usuarios pueden agregar proyectos al(los) manifiesto(s) local(es) antes de una invocación de `repo sync`, lo que instruye a repo para que descargue y gestione automáticamente estos proyectos adicionales.

Los archivos de manifiesto almacenados en `$TOP_DIR/.repo/local_manifests/*.xml` se cargarán en orden alfabético.

Los proyectos de los archivos de manifiesto locales se agregan al grupo local::<nombre del archivo de manifiesto local>.

La ruta antigua `$TOP_DIR/.repo/local_manifest.xml` ya no es compatible.

DESCRIPCIÓN

El comando repo se utiliza para inicializar un repositorio Git, descargar los diferentes proyectos de código fuente y gestionar los cambios. Es una capa sobre Git que facilita el trabajo con un gran número de repositorios, como los utilizados en el proyecto Android.

DETAILS

El comando repo se utiliza para inicializar un entorno de desarrollo para proyectos que utilizan múltiples repositorios Git. El flujo de trabajo típico es el siguiente:

  1. Inicialización: Ejecuta repo init -u <URL> -b <branch> para inicializar el repositorio. Esto descarga el archivo de manifiesto que describe la estructura de los repositorios.

  2. Sincronización: Ejecuta repo sync para descargar el código fuente de todos los proyectos definidos en el manifiesto.

  3. Desarrollo: Trabaja en los diferentes proyectos utilizando comandos de Git estándar dentro de cada directorio de proyecto.

  4. Gestión de cambios: Utiliza comandos de repo como repo upload para subir tus cambios a los repositorios remotos.

El archivo de manifiesto (normalmente .repo/manifest.xml) es un archivo XML que define la estructura del proyecto, incluyendo:

  • Los diferentes repositorios Git que componen el proyecto.
  • La ubicación remota de cada repositorio.
  • La rama o etiqueta que se debe usar para cada repositorio.
  • Grupos de proyectos para facilitar la sincronización selectiva.

repo proporciona una forma de gestionar eficientemente un gran número de repositorios, permitiendo operaciones atómicas y simplificando el flujo de trabajo de desarrollo.
