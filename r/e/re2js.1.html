NOMBRE

re2js - genera analizadores léxicos rápidos para JavaScript

SINOPSIS

re2js [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para stdin.

INTRODUCCIÓN

re2js funciona como un preprocesador. Lee el archivo de entrada (que suele ser un programa en JavaScript, pero puede ser cualquier cosa) y busca bloques de código encerrados entre marcadores de inicio/fin de forma especial. El texto fuera de estos bloques se copia textualmente al archivo de salida. El contenido de los bloques es procesado por re2js. Los traduce a código en JavaScript y genera el código resultante en lugar del bloque.

Aquí hay un ejemplo de un pequeño programa que verifica si una cadena dada contiene un número decimal:

// re2js $INPUT -o $OUTPUT
function lex(yyinput) {
    let yycursor = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    */
}
if (!lex("1234\0")) {
    throw "error!"
}

En la salida, re2js reemplazó el bloque del medio con el código generado:

// Generado por re2js
// re2js $INPUT -o $OUTPUT
function lex(yyinput) {
    let yycursor = 0;
{
    let yych = 0
    let yystate = 0
    yyl: while (true) {
        switch (yystate) {
            case 0:
                yych = yyinput.charCodeAt(yycursor)
                yycursor += 1;
                switch (yych) {
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yystate = 2
                        continue yyl
                    default:
                        yystate = 1
                        continue yyl
                }
            case 1:
                { return false; }
            case 2:
                yych = yyinput.charCodeAt(yycursor)
                switch (yych) {
                    case 0x30:
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yycursor += 1;
                        yystate = 2
                        continue yyl
                    default:
                        yystate = 3
                        continue yyl
                }
            case 3:
                { return true; }
            default:
                throw "error interno del analizador léxico"
        }
    }
}
}
if (!lex("1234\0")) {
    throw "error!"
}

BÁSICOS

Un programa re2js consta de una secuencia de bloques intercalados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresion-regular ;
Una definición vincula nombre a expresion-regular. Los nombres pueden contener caracteres alfanuméricos y guion bajo. La sección de expresiones regulares proporciona una descripción general de la sintaxis de re2js para expresiones regulares. Una vez definida, el nombre puede usarse en otras expresiones regulares y en reglas. La recursión en definiciones con nombre no está permitida, y cada nombre debe definirse antes de usarse. Un bloque hereda definiciones con nombre del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite cambiar el comportamiento de re2js y personalizar el código generado. Para obtener una lista completa de las configuraciones admitidas por re2js, consulte la sección de configuraciones. Dependiendo de una configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista solo en caracteres alfanuméricos. Un bloque hereda configuraciones del ámbito global y puede redefinirlas o agregar nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final del mismo.
expresion-regular codigo
Una regla vincula expresion-regular a su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en un salto de línea seguido de cualquier carácter que no sea un espacio en blanco). Si la expresion-regular coincide, se ejecuta el código asociado. Si coinciden varias reglas, la coincidencia más larga tiene prioridad. Si varias reglas coinciden con la misma cadena, la primera tiene prioridad. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse; tiene la menor prioridad independientemente de su posición en el bloque y coincide con cualquier unidad de código (no necesariamente un carácter válido, véase la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para el manejo del fin de entrada. Con las condiciones de inicio, las reglas tienen una sintaxis más compleja.
!accion codigo
Una acción vincula un bloque de código definido por el usuario a un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas vinculan código a los estados finales). Consulte la sección de acciones para obtener una lista completa de las acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias predefinidas especiales. Cada directiva tiene un propósito único. Consulte la sección de directivas para obtener más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (ambos estilos son compatibles). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que les permiten ser referenciados en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2js compila las expresiones regulares asociadas con cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se agregan al ámbito global y se vuelven visibles para los bloques subsiguientes. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera ningún código por sí mismo, ni agrega definiciones al ámbito global; está destinado a ser reutilizado en otros bloques. Esta es una forma de compartir código (más detalles en la sección de bloques reutilizables). Antes de la versión 2.2 de re2js, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2js busca bloques de reglas con ese nombre. De lo contrario, se utiliza el bloque de reglas más reciente (con nombre o sin nombre). Un bloque de uso puede agregar sus propias definiciones, configuraciones y reglas, que se agregan a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2js, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macrodefinición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Se puede personalizar con una configuración opcional

RE2C BLOCKS

re2c supports the following blocks:

/*!max:re2c[:<name1>[:<name2>...]] ... */ or %{max[:<name1>[:<name2>...]] ... %}
A block that generates YYMAXFILL definition (it requires -f --fill option). An optional list of block names specifies which blocks should be included when computing YYMAXFILL value (if the list is empty, all blocks are included). By default the generated code is a macro-definition for C (#define YYMAXFILL <n>), or a global variable for Go (var YYMAXFILL int = <n>). It can be customized with an optional configuration format that specifies a template string where @@{max} (or @@ for short) is replaced with the numeric value of YYMAXFILL.
/*!maxnmatch:re2c[:<name1>[:<name2>...]] ... */ or %{maxnmatch[:<name1>[:<name2>...]] ... %}
A block that generates YYMAXNMATCH definition (it requires -P --posix-captures option). An optional list of block names specifies which blocks should be included when computing YYMAXNMATCH value (if the list is empty, all blocks are included). By default the generated code is a macro-definition for C (#define YYMAXNMATCH <n>), or a global variable for Go (var YYMAXNMATCH int = <n>). It can be customized with an optional configuration format that specifies a template string where @@{max} (or @@ for short) is replaced with the numeric value of YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ or %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag variable generated by re2js. An optional list of block names specifies which blocks should be included when computing the set of tag variables (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag variable. Configuration separator specifies a piece of code used to join the generated format pieces for different tag variables.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ or %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag that is either explicitly mentioned by the rules (with --tags option) or implicitly generated by re2js (with --captvars or --posix-captvars options). An optional list of block names specifies which blocks should be included when computing the set of tags (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag. Configuration separator specifies a piece of code used to join the generated format pieces for different tags.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ or %{getstate[:<name1>[:<name2>...]] ... %}
A block that generates conditional dispatch on the lexer state (it requires --storable-state option). An optional list of block names specifies which blocks should be included in the state dispatch. The default transition goes to the start label of the first block on the list. If the list is empty, all blocks are included, and the default transition goes to the first block in the file that has a start label. This block type is incompatible with the --loop-switch option, as it requires cross-block transitions that are unsupported without goto or function calls.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ or %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
A block that generates condition enumeration (it requires --conditions option). An optional list of block names specifies which blocks should be included when computing the set of conditions (if the list is empty, all blocks are included). By default the generated code is an enumeration YYCONDTYPE. It can be customized with optional configurations format and separator. Configuration format specifies a template string where @@{cond} (or @@ for short) is replaced with the name of each condition, and @@{num} is replaced with a numeric index of that condition. Configuration separator specifies a piece of code used to join the generated format pieces for different conditions.
/*!include:re2c <file> */ or %{include <file> %}
This block allows one to include <file>, which must be a double-quoted file path. The contents of the file are literally substituted in place of the block, in the same way as #include works in C/C++. This block can be used together with the --depfile option to generate build system dependencies on the included files.
/*!header:re2c:on*/ or %{header:on %}
This block marks the start of header file. Everything after it and up to the following header:off block is processed by re2js and written to the header file specified with -t --type-header option.
/*!header:re2c:off*/ or %{header:off %}
This block marks the end of header file started with header:on*/ block.
/*!ignore:re2c ... */ or %{ignore ... %}
A block which contents are ignored and removed from the output file.

Configurations

Here is a full list of configurations supported by re2js:

re2c:api, re2c:input
Same as the --api option.
re2c:api:sigil
Specify the marker ("sigil") that is used for argument placeholders in the API primitives. The default is @@. A placeholder starts with sigil followed by the argument name in curly braces. For example, if sigil is set to $, then placeholders will have the form ${name}. Single-argument APIs may use shorthand notation without the name in braces. This option can be overridden by options for individual API primitives, e.g. re2c:YYFILL@len for YYFILL.
re2c:api:style
Specify API style. Possible values are functions (the default for C) and free-form (the default for Go and Rust). In functions style API primitives are generated with an argument list in parentheses following the name of the primitive. The arguments are provided only for autogenerated parameters (such as the number of characters passed to YYFILL), but not for the general lexer context, so the primitives behave more like macros in C/C++ or closures in Go and Rust. In free-form style API primitives do not have a fixed form: they should be defined as strings containing free-form pieces of code with interpolated variables of the form @@{var} or @@ (they correspond to arguments in function-like style). This configuration may be overridden for individual API primitives, see for example re2c:YYFILL:naked configuration for YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Same as the --bit-vectors option, but can be configured on per-block basis.
re2c:captures, re2c:leftmost-captures
Same as the --leftmost-captures option, but can be configured on per-block basis.
re2c:captvars, re2c:leftmost-captvars
Same as the --leftmost-captvars option, but can be configured on per-block basis.
re2c:case-insensitive, re2c:flags:case-insensitive

re2c:case-inverted, re2c:flags:case-inverted

re2c:case-ranges, re2c:flags:case-ranges
Same as the --case-ranges option, but can be configured on per-block basis.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g

re2c:computed-gotos:relative, re2c:cgoto:relative
Same as the --computed-gotos-relative option, but can be configured on per-block basis.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
If computed goto is used, this configuration specifies the complexity threshold that triggers the generation of jump tables instead of nested if statements and bitmaps. The default value is 9.
re2c:cond:abort
If set to a positive integer value, the default case in the generated condition dispatch aborts program execution.
re2c:cond:goto

re2c:cond:goto@cond
Specifies the sigil used for argument substitution in re2c:cond:goto definition. The default value is @@. Overrides the more generic re2c:api:sigil configuration.
re2c:cond:divider
Defines the divider for condition blocks. The default value is /* *********************************** */. Placeholders are substituted with condition name (see re2c:api;sigil and re2c:cond:divider@cond).
re2c:cond:divider@cond
Specifies the sigil used for arg
sustitución de cadenas en la definición de re2c:cond:divider. El valor predeterminado es @@. Anula la configuración más genérica re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Especifica el prefijo utilizado para las etiquetas de condición. El valor predeterminado es yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Especifica el prefijo utilizado para los identificadores de condición. El valor predeterminado es yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d

re2c:empty-class, re2c:flags:empty-class

re2c:encoding:ebcdic, re2c:flags:ecb, re2c:flags:e

re2c:encoding:ucs2, re2c:flags:wide-chars, re2c:flags:w

re2c:encoding:utf8, re2c:flags:utf-8, re2c:flags:8

re2c:encoding:utf16, re2c:flags:utf-16, re2c:flags:x

re2c:label:start, re2c:startlabel
Controla la generación de una etiqueta de inicio de bloque. El valor predeterminado es cero, lo que significa que la etiqueta de inicio se genera solo si se utiliza. Un valor entero mayor que cero fuerza la generación de la etiqueta de inicio incluso si no es utilizada por el analizador léxico. Un valor de cadena también fuerza la generación de la etiqueta de inicio y establece el nombre de la etiqueta en la cadena especificada. Esta configuración se aplica solo al bloque actual (se restablece al valor predeterminado para el siguiente bloque).
re2c:label:yyFillLabel
Especifica el prefijo de las etiquetas YYFILL utilizadas con re2c:eof y en el modo de estado almacenable.
re2c:label:yyloop
Especifica el nombre de la etiqueta que marca el inicio del bucle del analizador léxico con la opción --loop-switch. El valor predeterminado es yyloop.
re2c:label:yyNext
Especifica el nombre de la etiqueta opcional que sigue al cambio YYGETSTATE en el modo de estado almacenable (habilitado con re2c:state:nextlabel). El valor predeterminado es yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsoleto (ver la opción obsoleta --no-lookahead).
re2c:monadic
Si se establece en un valor distinto de cero, el analizador léxico generado utilizará la notación monádica (esta configuración es específica de Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Igual que la opción --nested-ifs, pero se puede configurar por bloque.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Igual que la opción --posix-captures, pero se puede configurar por bloque.
re2c:posix-captvars
Igual que la opción --posix-captvars, pero se puede configurar por bloque.
re2c:tags, re2c:flags:tags, re2c:flags:T
Igual que la opción --tags, pero se puede configurar por bloque.
re2c:tags:expression
Especifica la expresión utilizada para las variables de etiqueta. Por defecto, re2js genera expresiones de la forma yyt<N>. Esto puede ser inconveniente, por ejemplo, si las variables de etiqueta se definen como campos en una estructura. Todas las ocurrencias de @@{etiqueta} o @@ se reemplazan con el nombre de la etiqueta real. Por ejemplo, re2c:tags:expression = "s.@@"; da como resultado expresiones de la forma s.yyt<N> en el código generado. Ver también la configuración re2c:api:sigil.
re2c:tags:negative
Especifica la expresión constante que se utiliza para el valor de etiqueta negativo (normalmente sería -1 si las etiquetas son desfases enteros en la cadena de entrada, o un puntero nulo si son punteros).
re2c:tags:prefix
Especifica el prefijo para los nombres de las variables de etiqueta. El valor predeterminado es yyt.
re2c:sentinel
Especifica el símbolo centinela utilizado para las comprobaciones de fin de entrada (cuando las comprobaciones de límites están deshabilitadas con re2c:yyfill:enable = 0; y re2c:eof no está establecido). Esta configuración no afecta a la generación de código: su propósito es verificar que el centinela no está permitido en medio de una regla y asegurar que el analizador léxico no leerá más allá del final del búfer. El valor predeterminado es -1` (en ese caso, re2js asume que el centinela es cero, que es el caso más común). Solo se reconocen números decimales.
re2c:state:abort
Si se establece en un valor entero positivo, el caso predeterminado en el despacho de estados generado aborta la ejecución del programa, y un caso explícito -1 contiene la transición al inicio del bloque.
re2c:state:nextlabel
Controla si el cambio YYGETSTATE va seguido de una etiqueta yyNext (el valor predeterminado es cero, lo que corresponde a ninguna etiqueta). Alternativamente, se puede usar re2c:label:start para generar una etiqueta de inicio específica, o un bloque explícito getstate para generar el cambio YYGETSTATE por separado del bloque del analizador léxico.
re2c:unsafe, re2c:flags:unsafe
Igual que la opción --no-unsafe, pero se puede configurar por bloque. Si se establece en cero, suprime la generación de envolturas unsafe alrededor de YYPEEK. El valor predeterminado es distinto de cero (se generan envolturas). Esta configuración es específica de Rust.

Expresiones regulares

re2js utiliza la siguiente sintaxis para las expresiones regulares:

"foo"
Literal de cadena sensible a mayúsculas y minúsculas.
'foo'
Literal de cadena insensible a mayúsculas y minúsculas.
[a-xyz], [^a-xyz]
Clase de caracteres (posiblemente negada).
.
Cualquier carácter excepto salto de línea.
R \ S
Diferencia de clases de caracteres R y S.
R*
Cero o más ocurrencias de R.
R+
Una o más ocurrencias de R.
R?
Opcional R.
R{n}
Repetición de R exactamente n veces.
R{n,}
Repetición de R al menos n veces.
R{n,m}
Repetición de R de n a m veces.
(R)
Simplemente R; los paréntesis se utilizan para anular la precedencia. Si la extracción de subcoincidencias está habilitada, (R) es un grupo de captura o no de captura dependiendo de la opción --invert-captures.
(!R)
Si la extracción de subcoincidencias está habilitada, (!R) es un grupo de captura o no de captura dependiendo de la opción --invert-captures.
R S
Concatenación: R seguido de S.
R | S
Alternativa: R o S.
R / S
Lookahead: R seguido de S, pero S no se consume.
name
Expresión regular definida como name (o cadena literal "name" en modo de compatibilidad con Flex).
{name}
Expresión regular definida como name en modo de compatibilidad con Flex.
@stag
Una s-tag: guarda la última posición de entrada en la que coincide @stag en una variable llamada stag.
#mtag
Una m-tag: guarda todas las posiciones de entrada en las que coincide #mtag en una variable llamada mtag.

Las clases de caracteres y los literales de cadena pueden contener las siguientes secuencias de escape: \a, \b, \f, \n, \r, \t, \v, \\, escapes octales \ooo y escapes hexadecimales \xhh, \uhhhh y \Uhhhhhhhh.

Acciones

Aquí hay una lista de acciones predefinidas compatibles con re2js:

!entry code
La acción de entrada vincula un bloque definido por el usuario de code al estado inicial de la máquina de estados finitos actual. Si se utilizan *condiciones de inicio*, la acción de entrada se puede establecer individualmente para cada condición. Esta acción puede usarse para realizar inicializaciones, por ejemplo, para guardar la ubicación de inicio de un lexema.
!pre_rule code
La acción pre-regla antepone un bloque definido por el usuario de code a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan *condiciones de inicio*). Esta acción puede usarse para factorizar la parte común de todas las acciones semánticas (por ejemplo, guardar la ubicación final de un lexema).
!post_rule code
La acción post-regla añade un bloque definido por el usuario de code a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se utilizan *condiciones de inicio*). Esta acción puede usarse para emitir sentencias de trampa que protejan contra flujos de control no deseados.

Directivas

Aquí hay una lista completa de directivas compatibles con re2js:

!use:name ;
Una directiva de uso dentro de un bloque que fusiona un bloque de reglas previamente definido con el name especificado en el bloque actual. Las definiciones nombradas, configuraciones y reglas del bloque referenciado se agregan a las actuales. Los conflictos entre reglas y configuraciones superpuestas se resuelven de la manera habitual: la primera regla tiene prioridad y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y <!> para las cuales una definición local del bloque siempre tiene prioridad. Una directiva de uso se puede colocar en cualquier lugar dentro de un bloque, y se permiten múltiples directivas de uso.
!include file ;
Esta directiva es la misma que el bloque include: inserta el contenido del file verbatim en lugar de la directiva.

Interfaz del programa

El código generado interactúa con el programa externo con la ayuda de *primitivas*, denominadas colectivamente *API*. Qué primitivas deben definirse para un programa particular depende de múltiples factores, incluyendo la complejidad de las expresiones regulares, la representación de la entrada, el almacenamiento en búfer y el uso de varias características. Todas las primitivas necesarias deben ser definidas por el usuario en forma de macros, funciones, variables o cualquier otra forma adecuada que haga que el código generado sea sintáctica y semánticamente correcto. re2js no comprueba (y no puede comprobar) las definiciones, por lo que si algo falta o está definido incorrectamente, el programa generado puede tener errores de compilación o de tiempo de ejecución. Este manual proporciona ejemplos de definiciones de API en los casos más comunes.

re2js tiene tres estilos de API que definen el conjunto central de primitivas utilizadas por un programa:

API Simple
Esta es la API predeterminada para el backend de JavaScript. Consiste en las siguientes primitivas: YYINPUT (que debe definirse como una secuencia de unidades de código, por ejemplo, una cadena) y YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (que deben definirse como índices en YYINPUT).
API de Registro
La API de registro es útil en casos donde el estado del lexer debe almacenarse en un objeto. Se habilita con la opción --api record o la configuración re2c:api = record. Esta API consiste en una variable yyrecord (el nombre puede ser anulado con re2c:yyrecord) que debe definirse como un objeto con las propiedades yyinput, yycursor, yymarker, yyctxmarker, yylimit (solo los campos utilizados por el código generado necesitan definirse, y sus nombres pueden ser configurados).
API Genérica
Esta es la API más flexible. Se habilita con la opción --api generic o la configuración re2c:api = generic. Contiene primitivas para operaciones genéricas: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Aquí hay una lista completa de primitivas de API que pueden ser utilizadas por el código generado para interactuar con el programa externo.

YYCTYPE
El tipo de los caracteres de entrada (unidades de código). Para codificaciones ASCII, EBCDIC y UTF-8, debe ser un entero sin signo de 1 byte. Para UTF-16 o UCS-2, debe ser un entero sin signo de 2 bytes. Para UTF-32, debe ser un entero sin signo de 4 bytes.
YYCURSOR
Un valor l que almacena la posición actual de entrada (un puntero o un desplazamiento de entero en YYINPUT). Inicialmente, YYCURSOR debe apuntar al primer carácter de entrada, y más tarde es avanzado por el código generado. Cuando una regla coincide, la posición de YYCURSOR es la que está después del último carácter coincidente.
YYLIMIT
Un valor r que almacena la posición final de entrada (un puntero o un desplazamiento de entero en YYINPUT). Inicialmente, YYLIMIT debe apuntar a la posición después del último carácter de entrada disponible. No es modificado por el código generado. El lexer compara YYCURSOR con YYLIMIT para determinar si quedan suficientes caracteres de entrada.
YYMARKER
Un valor l que almacena la posición de la última regla coincidente (un puntero o un desplazamiento de entero en YYINPUT). Se utiliza para restaurar la posición de YYCURSOR si la coincidencia más larga falla y el lexer necesita retroceder. No se necesita inicialización.
YYCTXMARKER
Un valor l que almacena la posición del contexto de cola (un puntero o un desplazamiento de entero en YYINPUT). No se necesita inicialización. YYCTXMARKER solo se necesita si se utiliza el operador lookahead /.
YYFILL
Una primitiva de API genérica con una variable len. YYFILL debe proporcionar al menos len caracteres de entrada más o fallar. Si se utiliza re2c:eof, entonces len es siempre 1 y YYFILL siempre debe devolver el control a la función de llamada; un valor de retorno cero indica éxito. Si re2c:eof no se utiliza, el valor de retorno de YYFILL se ignora y no debe devolver en caso de fallo. El valor máximo de len es YYMAXFILL.
YYFN
Una primitiva que define el prototipo de función en --recursive-functions modelo de código. Su valor debe ser un array de una o más cadenas, donde cada cadena contiene dos o tres componentes separados por la cadena especificada en la configuración re2c:fn:sep (típicamente un punto y coma). El primer elemento del array define el nombre de la función y el tipo de retorno (vacío para una función void). Los elementos subsiguientes definen los argumentos de la función: primero, la expresión para el argumento utilizada en el cuerpo de la función (generalmente solo un nombre); segundo, el tipo del argumento; tercero, un parámetro formal opcional (que por defecto es el primer componente; generalmente, tanto el argumento como el parámetro son el mismo identificador).
YYINPUT
Un valor r que almacena la secuencia de entrada actual (cadena, buffer, etc.).
YYMAXFILL
Una constante integral igual al valor máximo del argumento de YYFILL. Puede ser generada con un bloque max.
YYLESSTHAN
Una primitiva API genérica con una variable len. Debe definirse como un valor r de tipo booleano que sea true si y solo si quedan menos de len caracteres de entrada.
YYPEEK
Una primitiva API genérica sin variables. Debe definirse como un valor r de tipo YYCTYPE igual al carácter en la posición de entrada actual.
YYSKIP
Una primitiva API genérica que debe avanzar la posición de entrada actual en una unidad de código.
YYBACKUP
Una primitiva API genérica que debe guardar la posición de entrada actual (para ser restaurada más tarde con YYRESTORE).
YYRESTORE
Una primitiva API genérica que debe restaurar la posición de entrada actual al valor guardado por YYBACKUP.
YYBACKUPCTX
Una primitiva API genérica que debe guardar la posición de entrada actual como la posición del contexto de cola (para ser restaurada más tarde con YYRESTORECTX).
YYRESTORECTX
Una primitiva API genérica que debe restaurar la posición del contexto de cola guardada con YYBACKUPCTX.
YYRESTORETAG
Una primitiva API genérica con una variable tag que debe restaurar la posición del contexto de cola al valor de tag.
YYSTAGP
Una primitiva API genérica con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para más detalles). YYSTAGP debe establecer tag a la posición de entrada actual.
YYSTAGN
Una primitiva API genérica con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para más detalles). YYSTAGN debe establecer tag a un valor que represente una posición de entrada inexistente.
YYMTAGP
Una primitiva API genérica con una variable tag. YYMTAGP debe añadir la posición actual al historial de subcoincidencias de tag (ver sección de extracción de subcoincidencias para más detalles.)
YYMTAGN
Una primitiva API genérica con una variable tag. YYMTAGN debe añadir un valor que represente una posición de entrada inexistente al historial de subcoincidencias de tag (ver sección de extracción de subcoincidencias para más detalles.)
YYSHIFT
Una primitiva API genérica con una variable shift que debe desplazar la posición de entrada actual en shift caracteres (el valor de desplazamiento puede ser negativo).
YYCOPYSTAG
Una primitiva API genérica con dos variables, lhs y rhs, que debe copiar la variable s-tag del lado derecho rhs a la variable s-tag del lado izquierdo lhs. Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que asigna lhs a rhs.
YYCOPYMTAG
Una primitiva API genérica con dos variables, lhs y rhs, que debe copiar la variable m-tag del lado derecho rhs a la variable m-tag del lado izquierdo lhs. Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que asigna lhs a rhs.
YYSHIFTSTAG
Una primitiva API genérica con dos variables, tag y shift, que debe desplazar tag en shift unidades de código (el valor de desplazamiento puede ser negativo).
YYSHIFTMTAG
Una primitiva API genérica con dos variables, tag y shift, que debe desplazar el último valor en el historial de tag en shift unidades de código (el valor de desplazamiento puede ser negativo).
YYMAXNMATCH
Una constante integral igual al número máximo de grupos de captura POSIX en una regla. Se genera con un bloque maxnmatch.
YYCONDTYPE
El tipo del enum de condición. Puede ser generado con el bloque conditions o la opción --header.
YYGETACCEPT
Una primitiva con una variable var que almacena el selector numérico de la regla aceptada. Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que lee de var.
YYSETACCEPT
Una primitiva con dos variables: var (un valor l que almacena el selector numérico de la regla aceptada) y val (el valor del selector). Para la mayoría de los lenguajes, esta primitiva tiene una definición predeterminada que asigna var a val.
YYGETCOND
Un valor r de tipo YYCONDTYPE que es igual al identificador de condición actual.
YYSETCOND
Una primitiva con una variable cond que debe establecer el identificador de condición actual a cond.
YYGETSTATE
Un valor r de tipo entero que es igual al estado actual del analizador léxico. Debe inicializarse a -1.
YYSETSTATE
Una primitiva con una variable state que debe establecer el estado actual del analizador léxico a state.
YYDEBUG
Esta primitiva solo se genera con la opción -d, --debug-output. Su propósito es añadir registro al código generado (la definición típica de YYDEBUG es una sentencia de impresión). Las sentencias de YYDEBUG se generan en cada estado y tienen dos variables: state (un índice de estado DFA o -1) y symbol (el símbolo de entrada actual).
yyaccept
Un valor l de tipo integral sin signo que almacena el número de la última regla coincidente. La definición del usuario solo es necesaria con la opción --storable-state.
yybm
Una tabla que contiene mapas de bits comprimidos para hasta 8 transiciones (se usa con la opción --bitmaps). La tabla contiene 256 elementos y se indexa por unidades de código de 1 byte. Cada elemento de 8 bits combina valores booleanos para hasta 8 transiciones. El k-ésimo bit del n-ésimo elemento es verdadero si y solo si la n-ésima unidad de código está en el rango de la k-ésima transición. La idea de este mapa de bits es reemplazar muchas ramas if o casos switch con una sola comprobación de un solo bit en la tabla.
yych
Un valor l de tipo YYCTYPE que almacena el carácter de entrada actual. La definición del usuario solo es necesaria con la opción -f --storable-state.
yyctable
Tabla de salto generada para la distribución de condiciones iniciales (habilitada con la combinación de las opciones --conditions y --computed-gotos).
yyfill
Un valor l que almacena el resultado de la llamada a YYFILL (esto puede ser necesario para lenguajes puramente funcionales, donde YYFILL es una función monádica con un valor de retorno complejo).
yynmatch
Un valor l de tipo integral sin signo que almacena el número de grupos de captura POSIX en la regla coincidente. Se usa solo con la opción -P --posix-captures.
yypmatch
Un array de valores l que se utilizan para mantener los valores de etiqueta correspondientes a los paréntesis de captura en la regla coincidente. La longitud del array debe ser al menos yynmatch * 2 (generalmente YYMAXNMATCH * 2 es una buena opción). Se usa solo con la opción -P --posix-captures.
yystable
Obsoleto.
yystate
Un valor l utilizado con la opción --loop-switch para almacenar el estado DFA actual.
yytarget
Tabla de saltos que contiene los destinos de salto (direcciones de etiqueta) para todas las transiciones desde un estado. Esta tabla es local a cada estado. La generación de tablas yytarget se habilita con la opción --computed-gotos.

Opciones

Algunas de las opciones tienen configuraciones correspondientes, mientras que otras son globales y no se pueden cambiar después de que re2c comience a leer el archivo de entrada. Las opciones de depuración generalmente requieren compilar re2c en configuración de depuración. Las opciones internas son útiles para experimentar con los algoritmos utilizados en re2c.

-? --help -h
Mostrar mensaje de ayuda.
--api <simple | record | generic>
Especificar la API utilizada por el código generado para interactuar con código definido por el usuario. La opción simple debe usarse en casos simples cuando no hay necesidad de rellenar búferes y almacenar el estado del analizador léxico. La opción record debe usarse cuando el estado del analizador léxico necesita almacenarse en un registro (struct, clase, etc.). La opción generic debe usarse en casos complejos cuando las otras dos API no son lo suficientemente flexibles.
--bit-vectors -b
Optimizar saltos condicionales usando máscaras de bits. Esta opción implica --nested-ifs.
--captures, --leftmost-captures
Habilitar la extracción de subcoincidencias con grupos de captura codiciosos más a la izquierda. El resultado se recopila en una matriz yybmatch con capacidad 2 * YYMAXNMATCH, y yynmatch se establece en el número de grupos para la regla de coincidencia.
--captvars, --leftmost-captvars
Habilitar la extracción de subcoincidencias con grupos de captura codiciosos más a la izquierda. El resultado se recopila en las variables yytl<k>, yytr<k> para el grupo de captura k-ésimo.
--case-insensitive
Tratar las cadenas entre comillas simples y comillas dobles como si no distinguieran entre mayúsculas y minúsculas.
--case-inverted
Invertir el significado de las cadenas entre comillas simples y comillas dobles: tratar las cadenas entre comillas simples como sensibles a mayúsculas y minúsculas y las cadenas entre comillas dobles como insensibles a mayúsculas y minúsculas.
--case-ranges
Colapsar casos consecutivos en sentencias switch en un rango de la forma low ... high. Esta sintaxis es una extensión del lenguaje C/C++ que es compatible con compiladores como GCC, Clang y Tcc. La principal ventaja sobre el uso de casos individuales es un código generado más pequeño y un tiempo de generación más rápido, aunque para algunos compiladores como Tcc también resulta en un tamaño binario más pequeño.
--computed-gotos -g
Optimizar saltos condicionales usando la extensión no estándar "computed goto" (que debe ser compatible con el compilador). re2js genera tablas de saltos solo en casos complejos con muchas ramas condicionales. El umbral de complejidad se puede configurar con la configuración cgoto:threshold. Los desplazamientos relativos se pueden habilitar con la configuración cgoto:relative. Esta opción implica --bit-vectors.

Archivos de sintaxis

El soporte para diferentes lenguajes en re2c se basa en la idea de archivos de sintaxis. Un archivo de sintaxis es un archivo de configuración que define la sintaxis del lenguaje de destino, no todo el lenguaje, sino una pequeña parte del mismo que es utilizada por el código generado. Los archivos de sintaxis hacen que re2c sea muy flexible, pero no deben utilizarse como sustituto de las configuraciones re2c:; su propósito es definir la sintaxis del lenguaje de destino, no personalizar un lexer en particular. Todos los lenguajes compatibles tienen archivos de sintaxis predeterminados que forman parte de la distribución (ver el subdirectorio include/syntax); también están incrustados en el binario re2js. Los usuarios pueden proporcionar un archivo de sintaxis personalizado que anule algunas configuraciones para uno de los lenguajes soportados, o pueden optar por redefinir todas las configuraciones (en cuyo caso se debe usar la opción --lang none). Los archivos de sintaxis contienen configuraciones de cuatro tipos diferentes: listas de características, configuraciones de lenguaje, configuraciones in situ y plantillas de código.

Plantillas de código

Las plantillas de código definen la sintaxis del lenguaje de destino. Están escritas en un lenguaje de dominio específico simple con la siguiente gramática formal: 
plantilla-codigo ::=
      nombre '=' expresiones-codigo ';'
    | PLANTILLA_CODIGO ';'
    | '<undefined>' ';'
expresiones-codigo ::=
      <VACIO>
    | expresiones-codigo expresion-codigo
expresion-codigo :: =
      CADENA
    | VARIABLE
    | opcional
    | lista
opcional ::
      '(' CONDICIONAL '?' expresiones-codigo ')'
    | '(' CONDICIONAL '?' expresiones-codigo ':' expresiones-codigo ')'
lista ::
      '[' VARIABLE ':' expresiones-codigo ']'
    | '[' VARIABLE '{' NUMERO '}' ':' expresiones-codigo ']'
    | '[' VARIABLE '{' NUMERO ',' NUMERO '}' ':' expresiones-codigo ']'.

Una plantilla de código es una secuencia de literales de cadena, variables, elementos opcionales y listas, o una referencia a otra plantilla de código, o un valor especial <undefined>. Las variables son marcadores de posición que se sustituyen durante la fase de generación de código. Las variables de lista son especiales: al expandir plantillas de lista, re2js repite las expresiones del lado derecho de la columna varias veces, cada vez reemplazando las ocurrencias de la variable de lista con un valor específico para esta repetición. Las listas tienen límites opcionales (los valores negativos se cuentan desde el final, por ejemplo, -1 significa el último elemento). Los nombres condicionales comienzan con un punto. Tanto los condicionales como las variables pueden ser locales (específicos de la plantilla de código dada) o globales (permitidos en todas las plantillas de código). Cuando re2js lee el archivo de sintaxis, verifica que cada plantilla de código utilice solo las variables y condicionales que están permitidos en ella.

Por ejemplo, la siguiente plantilla de código define la construcción if-then-else para un lenguaje similar a C:

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Aquí branch es una variable de lista: branch{0} se expande a la primera rama (que es especial, ya que no hay parte else), branch{1:-1} se expande a todas las ramas restantes (si las hay). stmt también es una variable de lista: [stmt: stmt] es una lista anidada que se expande a una lista de sentencias en el cuerpo de la rama actual. topindent, indent, dedent y nl son variables globales, y .cond es un condicional local (su significado se describe a continuación). Esta plantilla de código podría producir el siguiente código:

if x {
    // hacer algo
} else if y {
    // hacer otra cosa
} else {
    // no hacer nada
}

Tenga en cuenta que una definición particular puede, pero no tiene que, usar variables y condicionales locales. Las plantillas de código no utilizadas deben establecerse en <undefined>.

MANEJO DEL FIN DE LA ENTRADA

Uno de los principales problemas para el lexer es saber cuándo detenerse. Hay algunas condiciones de terminación:

  • el lexer puede coincidir con alguna regla (incluida la regla por defecto *) y llegar a un estado final
  • el lexer puede no coincidir con ninguna regla y llegar a un estado por defecto
  • el lexer puede alcanzar el fin de la entrada

Las dos primeras condiciones terminan el lexer de una forma "natural": llega a un estado sin transiciones de salida, y la coincidencia se detiene automáticamente. La tercera condición, fin de entrada, es diferente: puede ocurrir en cualquier estado, y el lexer debe ser capaz de manejarlo. La comprobación del fin de entrada interrumpe el flujo normal del lexer y añade ramas condicionales al programa generado, por lo tanto es necesario minimizar el número de tales comprobaciones. re2js soporta algunos métodos diferentes para manejar el fin de entrada. Cuál usar depende de la complejidad de las expresiones regulares, la necesidad de buffering, consideraciones de rendimiento y otros factores. Aquí hay una lista de métodos:

  • Centinela. Este método elimina la necesidad de comprobaciones de fin de entrada por completo. Es simple y eficiente, pero limitado al caso en que hay un carácter "centinela" natural que nunca puede ocurrir en una entrada válida. Este carácter puede ocurrir todavía en entradas inválidas, pero no debe ser permitido por las expresiones regulares, excepto quizás como el último carácter de una regla. El centinela se añade al final de la entrada y sirve como señal de parada: cuando el lexer lee este carácter, es ya sea un error de sintaxis o el fin de la entrada. En ambos casos, el lexer debe detenerse. Este método se utiliza si YYFILL está deshabilitado con re2c:yyfill:enable = 0; y re2c:eof tiene el valor por defecto -1.
  • Centinela con comprobaciones de límites. Este método es genérico: permite manejar cualquier entrada sin restricciones en las expresiones regulares. La idea es reducir el número de comprobaciones de fin de entrada realizándolas solo en ciertos caracteres. Similar al método "centinela", uno de los caracteres se elige como "centinela" y se añade al final de la entrada. Sin embargo, no hay restricción en dónde puede ocurrir el centinela (de hecho, cualquier carácter puede ser elegido como centinela). Cuando el lexer lee este carácter, además realiza una comprobación de límites. Si la posición actual está dentro de los límites, el lexer reanuda la coincidencia y maneja el centinela como un carácter regular. De lo contrario, invoca YYFILL (a menos que esté deshabilitado). Si se proporciona más entrada, el lexer volverá a coincidir con el último carácter y continuará como si el centinela no hubiera estado allí. De lo contrario, debe ser el fin real de la entrada, y el lexer se detiene. Este método se utiliza cuando re2c:eof tiene un valor no negativo (debe establecerse en el valor numérico del centinela). YYFILL es opcional.
  • Comprobaciones de límites con relleno. Este método es genérico, y puede ser más rápido que el método "centinela con comprobaciones de límites", pero también es más complejo. La idea es particionar los estados del DFA en componentes fuertemente conectados (SCC) y generar una sola comprobación por SCC para suficientes caracteres para cubrir el camino más largo sin bucles en esta SCC. Esto reduce el número de comprobaciones, pero hay un problema con los lemas cortos al final de la entrada, ya que la comprobación requiere suficientes caracteres para cubrir el lema más largo. Esto se puede solucionar rellenando la entrada con algunos caracteres falsos que no forman un sufijo de lema válido (para que el lexer no pueda coincidir con ellos). La longitud del relleno debe ser YYMAXFILL, generado con un bloque max. Si no hay suficiente entrada, el lexer invoca YYFILL que debe suministrar al menos el número requerido de caracteres o no regresar. Este método se utiliza si YYFILL está habilitado y re2c:eof es -1 (esta es la configuración por defecto).
  • Comprobaciones personalizadas. La API genérica permite anular operaciones básicas como leer un carácter, lo que hace posible incluir las comprobaciones de fin de entrada como parte de ellas. Este enfoque es propenso a errores y debe usarse con precaución. Para usar un método personalizado, habilite la API genérica con --api custom o re2c:api = custom; y deshabilite las comprobaciones de límites por defecto con re2c:yyfill:enable = 0; o re2c:yyfill:check = 0;.

Las siguientes subsecciones contienen un ejemplo de cada método.

Centinela

Este ejemplo utiliza un carácter centinela para manejar el fin de entrada. El programa cuenta palabras separadas por espacios en una cadena terminada en nulo. El centinela es nulo: es el último carácter de cada cadena de entrada, y no está permitido en medio de un lema por ninguna de las reglas (en particular, no está incluido en rangos de caracteres donde es fácil pasarlo por alto). Si un nulo ocurre en medio de una cadena, es un error de sintaxis y el lexer coincidirá con la regla por defecto *, pero no leerá más allá del fin de la entrada ni fallará (use la advertencia -Wsentinel-in-midrule y la configuración re2c:sentinel para verificar esto). La configuración re2c:yyfill:enable = 0; suprime la generación de comprobaciones de límites y las invocaciones de YYFILL.

// re2js $INPUT -o $OUTPUT
// espera una cadena terminada en nulo
function lex(yyinput) {
    let yycursor = 0;
    let count = 0
    loop: while (true) {
    /*!re2c
        re2c:yyfill:enable = 0;
        *      { return -1 }
        [\x00] { return count }
        [ ]+   { continue loop }
        [a-z]+ { count += 1; continue loop }
    */
    }
}
function test(s, n) { if (lex(s) != n) throw "error!"; }
test("\0", 0)
test("one two three\0", 3)
test("f0ur\0", -1)

Centinela con comprobaciones de límites

Este ejemplo utiliza un centinela con comprobaciones de límites para manejar el fin de entrada (este método se añadió en la versión 1.2). El programa cuenta cadenas de comillas simples separadas por espacios. El carácter centinela es nulo, que se especifica con la configuración re2c:eof = 0;. Al igual que en el método centinela, el nulo es el último carácter de cada cadena de entrada, pero está permitido en medio de una regla (por ejemplo, 'aaa\0aa'\0 es una entrada válida, pero 'aaa\0 es un error de sintaxis). Se generan comprobaciones de límites en cada estado que coincide con un carácter de entrada, pero están limitadas a la rama que maneja el nulo. Las comprobaciones de límites son de la forma YYLIMIT <= YYCURSOR o YYLESSTHAN(1) con API genérica. Si la condición de comprobación es verdadera, el lexer ha alcanzado el fin de entrada y debe detenerse (YYFILL está deshabilitado con re2c:yyfill:enable = 0; ya que la entrada cabe en un solo búfer, ver la sección YYFILL con centinela para un ejemplo que utiliza YYFILL). Al alcanzar el fin de entrada se abren tres posibilidades: si el lexer está en el estado inicial coincidirá con la regla de fin de entrada $, de lo contrario puede retroceder a una regla coincidente previamente (incluida la regla por defecto *) o ir a un estado por defecto, causando -Wundefined-control-flow.

// re2js $INPUT -o $OUTPUT
// espera una cadena terminada en nulo
function lex(yyinput) {
    let yycursor = 0;
    let yylimit = yyinput.length - 1 // el nulo terminador no está incluido
    let count = 0
    loop: while (true) {
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1 }
        $    { return count }
        [ ]+ { continue loop }
        str  { count += 1; continue loop }
    */
    }
}
function test(s, n) { if (lex(s) != n) throw "error!"; }
test("\0", 0)
test("'qu\0tes' 'are' 'fine: \\'' \0", 3)
test("'unterminated\\'\0", -1)

Comprobaciones de límites con relleno

Este ejemplo utiliza comprobaciones de límites con relleno para manejar el final de la entrada (este método está habilitado por defecto). El programa cuenta cadenas de caracteres de comillas simples separadas por espacios. Hay un relleno de YYMAXFILL caracteres nulos añadidos al final de la entrada, donde el valor de YYMAXFILL se genera automáticamente con un bloque max. No es necesario usar nulos para el relleno --- se pueden usar cualesquiera caracteres siempre que no formen un sufijo de lexema válido (en este ejemplo, el relleno no debe contener comillas simples, ya que podrían confundirse con un sufijo de una cadena de comillas simples). Hay una regla de "parada" que coincide con el primer carácter de relleno (nulo) y termina el analizador léxico (tenga en cuenta que comprueba si el nulo está al principio del relleno, de lo contrario es un error de sintaxis). Las comprobaciones de límites solo se generan en algunos estados determinados por los componentes fuertemente conectados del autómata subyacente. Las comprobaciones tienen la forma (YYLIMIT - YYCURSOR) < n o YYLESSTHAN(n) con la API genérica, donde n es el número mínimo de caracteres necesarios para que el analizador léxico proceda (también significa que la próxima comprobación de límites ocurrirá en como máximo n caracteres). Si la condición de comprobación es verdadera, el analizador léxico ha llegado al final de la entrada e invocará YYFILL(n) que debe suministrar al menos n caracteres de entrada o no devolver nada. En este ejemplo, YYFILL siempre falla y termina el analizador léxico con un error (lo cual está bien porque la entrada cabe en un solo búfer). Consulte la sección YYFILL con relleno para ver un ejemplo que rellena el búfer de entrada con YYFILL.

// re2js $INPUT -o $OUTPUT
/*!max:re2c*/
function lex(yyinput) {
    let yycursor = 0;
    let yylimit = yyinput.length
    let count = 0
    loop: while (true) {
    /*!re2c
        re2c:YYFILL = "return -1";
        str = [' ([^'\\] | [\\][^])* '];
        [\x00] {
            // comprueba que es el centinela, no un nulo inesperado
            return (yycursor == yylimit - YYMAXFILL + 1) ? count : -1
        }
        str  { count += 1; continue loop }
        [ ]+ { continue loop }
        *    { return -1 }
    */
    }
}
function test(s, n) {
    let padded_s = s + "\0".repeat(YYMAXFILL)
    if (lex(padded_s) != n) throw "error!"
}
test("", 0)
test("'unterminated\\'", -1)
test("'qu\0tes' 'are' 'fine: \\'' ", 3)
test("'unexpected \0 null", -1)

Este ejemplo utiliza un método personalizado de manejo del fin de entrada basado en la API genérica. El programa cuenta cadenas de caracteres de comillas simples separadas por espacios. Es el mismo que el ejemplo de centinela, excepto que la entrada no está terminada en nulo. Relleno de búfer

La necesidad de búferes surge cuando la entrada no se puede mapear en memoria de una vez: o es demasiado grande, o proviene de forma de flujo (como leer de un socket). La técnica habitual en tales casos es asignar un búfer de memoria de tamaño fijo y procesar la entrada en fragmentos que caben en el búfer. Cuando se procesa el fragmento actual, se retira y se introduce nueva información. En la práctica, es algo más complejo, porque el estado del analizador léxico consiste no en una única posición de entrada, sino en un conjunto de posiciones interrelacionadas:

  • cursor: el siguiente carácter de entrada a leer (YYCURSOR en la API de punteros C o YYSKIP/YYPEEK en la API genérica)
  • límite: la posición después del último carácter de entrada disponible (YYLIMIT en la API de punteros C, manejado implícitamente por YYLESSTHAN en la API genérica)
  • marcador: la posición de la coincidencia más reciente, si la hay (YYMARKER en la API por defecto o YYBACKUP/YYRESTORE en la API genérica)
  • token: el inicio del lexema actual (implícito en la API de re2js, ya que no es necesario para la operación normal del analizador léxico y puede ser definido y actualizado por el usuario)
  • marcador de contexto: la posición del contexto de cola (YYCTXMARKER en la API de punteros C o YYBACKUPCTX/YYRESTORECTX en la API genérica)
  • variables de etiqueta: posiciones de subcoincidencia (definidas con bloques stags y mtags y primitivas de la API genérica YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

No todos estos se utilizan en todos los casos, pero si se utilizan, deben ser actualizados por YYFILL. Todas las posiciones activas están contenidas en el segmento entre el token y el cursor, por lo tanto, todo lo que está entre el inicio del búfer y el token puede ser descartado, el segmento desde el token hasta el límite debe moverse al principio del búfer, y el espacio libre al final del búfer debe rellenarse con nuevos datos. Para evitar llamadas frecuentes a YYFILL, es mejor rellenar tantos caracteres de entrada como sea posible (aunque menos caracteres podrían ser suficientes para reanudar el analizador léxico). Los detalles de la implementación de YYFILL son ligeramente diferentes dependiendo de qué método de manejo de EOF se utilice: el caso de la regla EOF es algo más sencillo que el caso de comprobación de límites con relleno. Tenga en cuenta también que si se utiliza la opción -f --storable-state, YYFILL tiene una semántica ligeramente diferente (descrita en la sección sobre estado almacenable).

YYFILL con centinela

Si se utiliza la regla EOF, YYFILL es una primitiva similar a una función que no acepta argumentos y devuelve un valor que se comprueba frente a cero. La invocación de YYFILL es desencadenada por la condición YYLIMIT <= YYCURSOR en la API de punteros C y YYLESSTHAN() en la API genérica. Un valor de retorno distinto de cero significa que YYFILL ha fallado. Una llamada exitosa a YYFILL debe suministrar al menos un carácter y ajustar las posiciones de entrada en consecuencia. El límite debe establecerse siempre a uno después de la última posición de entrada en el búfer, y el carácter en la posición del límite debe ser el símbolo centinela especificado por la configuración re2c:eof. // re2js $INPUT -o $OUTPUT
const fs = require('fs')
const BUFSIZE = 4096
const OK = 0
const EOF = 1
const LONG_LEXEME = 2
function fill(st) {
    if (st.eof) return EOF
    // Error: lexema demasiado largo. En la vida real se podría reasignar un búfer más grande.
    if (st.token < 1) return LONG_LEXEME
    // Desplaza el contenido del búfer (descarta todo hasta el token actual).
    st.yyinput.copy(st.yyinput, 0, st.token, st.yylimit)
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    // Lee un nuevo fragmento de datos del archivo y lo añade a `yyinput`.
    let want = BUFSIZE - st.yylimit - 1 // -1 para el centinela
    let nread = fs.readSync(st.file, st.yyinput, st.yylimit, want)
    st.eof = nread < want // ¿fin del archivo?
    st.yylimit += nread
    st.yyinput.writeUInt8(0, st.yylimit) // centinela
    return OK
}
function lex(yyrecord, count) {
    loop: while (true) {
        yyrecord.token = yyrecord.yycursor
        /*!re2c
            re2c:api = record;
            re2c:YYPEEK = "readUInt8";
            re2c:YYFILL = "fill(yyrecord) == OK";
            re2c:eof = 0;
            str = [' ([^'\\] | [\\][^])* '];
            *    { return -1 }
            $    { return count }
            [ ]+ { continue loop }
            str  { count += 1; continue loop }
        */
    }
}
function main() {
    let fname = "input"
    // Crea el archivo de entrada.
    let content = "'qu\0tes' 'are' 'fine: \\'' ".repeat(BUFSIZE)
    fs.writeFileSync(fname, content, function(err) { if (err) throw err; })
    // Inicializa el estado del analizador léxico.
    let limit = BUFSIZE - 1 // excluye el nulo de terminación
    let st = {
        file: fs.openSync(fname, 'r'),
        yyinput: Buffer.alloc(BUFSIZE),
        yylimit: limit,
        yycursor: limit,
        yymarker: limit,
        token: limit,
        eof: false
    }
    // Ejecuta el analizador léxico en el archivo preparado.
    if (lex(st, 0) != 3 * BUFSIZE) { throw "error :[" }
    // Limpieza.
    fs.unlink(fname, function(err){ if (err) throw err; })
}

En el caso por defecto (cuando la regla EOF no se usa) YYFILL es una primitiva similar a una función que acepta un solo argumento y no devuelve ningún valor. La invocación de YYFILL es desencadenada por la condición (YYLIMIT - YYCURSOR) < n en la API de punteros C y YYLESSTHAN(n) en la API genérica. El argumento pasado a YYFILL es el número mínimo de caracteres que deben ser suministrados. Si no logra hacerlo, YYFILL no debe devolver el control al analizador léxico (para eso r

Múltiples bloques

A veces es necesario tener múltiples lexers interrelacionados (por ejemplo, si hay una máquina de estados de alto nivel que transiciona entre modos de lexer). Esto se puede implementar utilizando múltiples bloques conectados de re2js. Otra opción es usar *condiciones de inicio*.

La implementación de conexiones entre bloques depende del lenguaje de destino. En lenguajes que tienen la sentencia goto (como C/C++ y Go) se pueden tener todos los bloques en una sola función, cada uno prefijado con una etiqueta. La transición de un bloque a otro es un simple goto. En lenguajes que no tienen goto (como Rust) es necesario usar un bucle con un switch en una variable de estado, similar al bucle/switch yystate generado por re2js, o bien envolver cada bloque en una función y usar llamadas a funciones.

El ejemplo a continuación utiliza múltiples bloques para analizar números binarios, octales, decimales y hexadecimales. Cada base tiene su propio bloque. El bloque inicial determina la base y se dirige a otros bloques. Las configuraciones comunes se definen en un bloque separado al principio del programa; son heredadas por los otros bloques.

// re2js $INPUT -o $OUTPUT
/*!re2c // Definiciones comunes de re2c compartidas entre todas las funciones.

Condiciones de inicio

Las condiciones de inicio se habilitan con la opción --start-conditions. Proporcionan una forma de codificar múltiples autómatas interrelacionados dentro del mismo bloque re2js.

Cada condición corresponde a un autómata individual y tiene un nombre único especificado por el usuario y un número interno único definido por re2js. Los números se utilizan para cambiar entre condiciones: el código generado utiliza primitivas YYGETCOND y YYSETCOND para obtener la condición actual o establecerla a un número dado. Use el bloque conditions, la opción --header o la configuración re2c:header para generar identificadores numéricos de condición. La configuración re2c:cond:enumprefix especifica el prefijo del identificador generado.

En modo de condición, cada regla debe ir precedida por una lista de nombres de condición separados por comas entre corchetes angulares, o un comodín <*> para denotar todas las condiciones. La sintaxis de la regla se extiende de la siguiente manera:

< lista-condicion > expresion-regular codigo
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular y ejecuta el codigo asociado.
< lista-condicion > expresion-regular => condicion codigo
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular, establece la condición actual a condicion y ejecuta el codigo asociado.
< lista-condicion > expresion-regular :=> condicion
Una regla que se fusiona a cada condición en la lista-condicion. Coincide con la expresion-regular y transiciona inmediatamente a condicion (no hay acción semántica).
< lista-condicion > !accion codigo
Una regla que une el codigo al lugar definido por la accion en cada condición de la lista-condicion (ver la sección *acciones* para varios tipos de acciones).
<! lista-condicion > codigo
Una regla que antepone el codigo a las acciones semánticas de todas las reglas para cada condición en la lista-condicion. Esta sintaxis está obsoleta y se debe usar la acción !pre_rule en su lugar (hace exactamente lo mismo).
< > codigo
Una regla que crea una condición de entrada especial con el número cero y el nombre "0" que ejecuta el codigo antes de saltar a otras condiciones. Esta sintaxis está obsoleta y se debe usar la acción !entry en su lugar (proporciona un control más detallado, ya que el código se puede especificar por condición, y se puede saltar directamente al inicio de la condición sin pasar por la distribución de condiciones).
< > => condicion codigo
Igual que la regla anterior, excepto que establece la siguiente condicion.
< > :=> condicion
Igual que la regla anterior, excepto que no tiene código asociado y salta inmediatamente a la condicion.

El código que re2js genera para las condiciones depende de si re2js utiliza el enfoque goto/etiqueta o el enfoque bucle/switch para codificar los autómatas.

En lenguajes que tienen la sentencia goto (como C/C++ y Go) las condiciones se implementan naturalmente como bloques de código prefijados con etiquetas del tipo yyc_<cond>, donde cond es un nombre de condición (el prefijo de etiqueta se puede cambiar con re2c:cond:prefix). Las transiciones entre condiciones se implementan usando goto y etiquetas de condición. Antes de todas las condiciones, re2js genera un switch inicial en YYGETSTATE que salta al estado de inicio de la condición actual. Las reglas de acceso directo :=> evitan el switch inicial y saltan directamente a la condición especificada (se puede usar re2c:cond:goto para cambiar el comportamiento por defecto). Las reglas con acciones semánticas no saltan automáticamente a la siguiente condición; esto debe hacerlo el código de acción definido por el usuario.

En lenguajes que no tienen goto (como Rust) re2js reutiliza la variable yystate para almacenar la condición n

Condiciones iniciales

Las condiciones iniciales son un mecanismo para definir conjuntos de reglas de análisis sintáctico que se aplican a diferentes partes de la entrada. Se definen con el bloque conditions, que es similar al bloque rules, excepto que cada regla de análisis sintáctico va precedida por un identificador de condición inicial. Las condiciones iniciales se numeran automáticamente; el primer estado se numera 0, el segundo estado 1, y así sucesivamente. Un interruptor entre condiciones no es diferente de un interruptor entre estados de DFA de una sola condición. No necesita un interruptor de condición inicial separado. (Dado que el mismo enfoque se utiliza para implementar estados almacenables, YYGETCOND/YYSETCOND son redundantes si se utilizan tanto estados almacenables como condiciones).

El programa a continuación utiliza condiciones iniciales para analizar números binarios, octales, decimales y hexadecimales. Hay un solo bloque donde cada base tiene su propia condición, y la condición inicial está conectada a todas ellas. La variable definida por el usuario cond almacena el número de condición actual; se inicializa con el número de la condición inicial generada con el bloque conditions.

// re2js $INPUT -o $OUTPUT -c
/*!conditions:re2c*/
function parse_u32(yyinput) {
    let yycursor = 0
    let yycond = YYC_INIT
    let n = 0
    loop: while (true) {
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:indent:top = 2;
        <INIT> '0b' / [01]        :=> BIN
        <INIT> "0"                :=> OCT
        <INIT> "" / [1-9]         :=> DEC
        <INIT> '0x' / [0-9a-fA-F] :=> HEX
        <INIT> * { return null }
        <BIN> [01]  { n = n * 2 + (yyinput.charCodeAt(yycursor - 1) - 48); continue loop }
        <OCT> [0-7] { n = n * 8 + (yyinput.charCodeAt(yycursor - 1) - 48); continue loop }
        <DEC> [0-9] { n = n * 10 + (yyinput.charCodeAt(yycursor - 1) - 48); continue loop }
        <HEX> [0-9] { n = n * 16 + (yyinput.charCodeAt(yycursor - 1) - 48); continue loop }
        <HEX> [a-f] { n = n * 16 + (yyinput.charCodeAt(yycursor - 1) - 87); continue loop }
        <HEX> [A-F] { n = n * 16 + (yyinput.charCodeAt(yycursor - 1) - 55); continue loop }

Estado almacenable

Con la opción --storable-state, re2js genera un analizador léxico que puede almacenar su estado actual, devolver el control al llamador y, más tarde, reanudar las operaciones exactamente donde lo dejó. El modo de operación predeterminado en re2js es un modelo "pull", en el que el analizador léxico "tira" de más entrada cada vez que la necesita. Esto puede ser inaceptable en casos en los que la entrada se recibe pieza por pieza (por ejemplo, si el analizador léxico es invocado por el analizador sintáctico, o si el programa del analizador léxico se comunica a través de un protocolo de socket con algún otro programa que debe esperar una respuesta del analizador léxico antes de transmitir el siguiente mensaje). La función de estado almacenable está destinada precisamente a tales casos: permite generar analizadores léxicos que funcionan en un modelo "push". Cuando el analizador léxico necesita más entrada, almacena su estado y devuelve el control al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el analizador léxico exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo "pull":

  • Definir las primitivas YYSETSTATE() y YYGETSTATE(state).
  • Definir las variables yych, yyaccept (si se usa) y state como parte del estado persistente del analizador léxico. La variable state debe inicializarse a -1.
  • YYFILL debe devolver el control al programa externo en lugar de intentar suministrar más entrada. El código de retorno debe indicar que el analizador léxico necesita más entrada.
  • El programa externo debe reconocer las situaciones en las que el analizador léxico necesita más entrada y responder adecuadamente.
  • Opcionalmente, use el bloque getstate para generar un interruptor YYGETSTATE separado del analizador léxico principal. Esto solo funciona para lenguajes que tienen goto (no en modo --loop-switch).
  • Utilice re2c:eof y el método *del centinela con comprobaciones de límites* para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo agregar el relleno: el final actual de la entrada puede no ser el final definitivo de la entrada, y agregar el relleno demasiado pronto puede cortar un lexema codicioso leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del búfer (que ya está bloqueado debido a la condición de fin de entrada).

Aquí hay un ejemplo de un analizador léxico en modelo "push" que simula la lectura de paquetes de un socket. El analizador léxico se ejecuta en un bucle hasta que encuentra el final de la entrada y devuelve el control a la función llamadora. La función llamadora proporciona más entrada "enviando" el siguiente paquete y reanuda el análisis léxico. Este proceso se detiene cuando se han enviado todos los paquetes, o cuando hay un error.

Bloques reutilizables

Los bloques reutilizables del tipo /*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %} se pueden reutilizar cualquier número de veces y combinar con otros bloques de re2js. El <nombre> es opcional. Un bloque de reglas se puede usar en un bloque o directiva use. El código de un bloque de reglas se genera en cada punto de uso.

Los bloques de uso se definen con /*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}. El <nombre> es opcional: si no se especifica, el bloque de reglas asociado es el más reciente (con nombre o sin nombre). Un bloque de uso puede agregar definiciones nombradas, configuraciones y reglas propias. Un caso de uso importante para los bloques de uso es un analizador léxico que admite múltiples codificaciones de entrada: el mismo bloque de reglas se reutiliza varias veces con configuraciones específicas de codificación (ver el ejemplo a continuación).

La directiva de uso dentro de un bloque !use:<nombre>; se puede usar desde dentro de un bloque de re2c. Fusiona el bloque de referencia <nombre> en el actual. Si algunas de las reglas y configuraciones fusionadas se superponen con las definidas previamente, los conflictos se resuelven de la manera habitual: la primera regla tiene prioridad y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y (en modo de condición) <!>, para las cuales una definición local del bloque anula cualquier definición heredada. La directiva de uso permite combinar diferentes bloques de re2c entre sí en un solo bloque (ver el ejemplo a continuación).

Los bloques con nombre y la directiva de uso dentro de un bloque se agregaron en la versión 2.2 de re2js. Desde esa versión, los bloques reutilizables están permitidos por defecto (no se necesita una opción especial). Antes de la versión 2.2, el modo reutilizable se habilitaba con la opción -r --reusable. Antes de la versión 1.2, los bloques reutilizables no se podían mezclar con bloques normales.

Etiquetas
La primera opción es usar etiquetas independientes de la forma @etiqueta o #metiqueta, donde etiqueta y metiqueta son nombres definidos por el usuario. Las etiquetas se habilitan con la opción -T --tags o la configuración re2c:tags = 1. Semánticamente, las etiquetas son marcadores de posición: pueden insertarse en cualquier lugar de una expresión regular y se vinculan a la posición (o múltiples posiciones) correspondiente en la cadena de entrada. Las etiquetas-s se vinculan a la última posición coincidente, y las etiquetas-m se vinculan a una lista de posiciones (pueden usarse en subexpresiones de repetición, donde una sola posición en una expresión regular corresponde a múltiples posiciones en la cadena de entrada). Todas las etiquetas deben ser definidas por el usuario, ya sea manualmente o con la ayuda de los bloques svars y mvars. Si hay más de una forma en que las etiquetas puedan coincidir con la entrada, la ambigüedad se resuelve utilizando la estrategia de desambiguación voraz por la izquierda.
Capturas
La segunda opción es usar grupos de captura. Se habilitan con la opción --captures o la configuración re2c:captures = 1. Hay dos variantes para diferentes políticas de desambiguación, --leftmost-captures (el valor predeterminado) es para la política voraz por la izquierda, y --posix-captures es para la política de coincidencia más larga POSIX. En este modo, todas las subexpresiones entre paréntesis se consideran grupos de captura, y se puede usar un signo de exclamación para marcar grupos que no capturan: (! ... ). Con la opción --invert-captures o la configuración re2c:invert-captures = 1, el significado del signo de exclamación se invierte. El número de grupos para la regla de coincidencia se almacena en una variable yynmatch (la expresión regular completa es el grupo número cero), y los resultados de las subcoincidencias se almacenan en el array yypmatch. Tanto yynmatch como yypmatch deben ser definidos por el usuario, y el tamaño de yypmatch debe ser al menos [yynmatch * 2]. Use el bloque maxnmatch para definir YYMAXNMATCH, una constante que es igual al valor máximo de yynmatch entre todas las reglas.
Captvars
Otra forma de usar grupos de captura es la opción --captvars o la configuración re2c:captvars = 1. La única diferencia con --captures es en la forma en que el código generado almacena los resultados de las subcoincidencias: en lugar de yynmatch y yypmatch, re2js genera las variables yytl<k> y yytr<k> para el k-ésimo grupo de captura (el usuario debe declararlas usando un bloque svars). Las capturas con variables soportan dos políticas de desambiguación: --leftmost-captvars o re2c:leftmost-captvars = 1 para la política voraz por la izquierda (la predeterminada) y --posix-captvars o re2c:posix-captvars para la política de coincidencia más larga POSIX.
En el fondo, todas estas opciones se traducen en etiquetas y Autómatas Finitos Deterministas Etiquetados con Lookahead. La idea central de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En el extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es solo un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es apenas notable. El TDFA generado utiliza una serie de variables de etiqueta que no se mapean directamente a las etiquetas: una sola variable puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples variables para almacenar todos sus valores posibles. Finalmente, la ambigüedad se resuelve y solo sobrevive una variable final por etiqueta. Las variables de etiqueta deben definirse usando los bloques stags o mtags. Si el estado del lexer se almacena, las variables de etiqueta deben formar parte de él. También necesitan ser actualizadas por YYFILL. Las etiquetas-s soportan las siguientes operaciones:
  • guardar la posición de entrada en una etiqueta s: t = YYCURSOR con la API de puntero C o una operación definida por el usuario YYSTAGP(t) con la API genérica
  • guardar un valor predeterminado en una etiqueta s: t = NULL con la API de puntero C o una operación definida por el usuario YYSTAGN(t) con la API genérica
  • copiar una etiqueta s a otra: t1 = t2
Las etiquetas-m soportan las siguientes operaciones:
  • añadir una posición de entrada a una etiqueta m: una operación definida por el usuario YYMTAGP(t) con la API predeterminada y la genérica
  • añadir un valor predeterminado a una etiqueta m: una operación definida por el usuario YYMTAGN(t) con la API predeterminada y la genérica
  • copiar una etiqueta m a otra: t1 = t2

Las etiquetas-m necesitan una representación más compleja, ya que necesitan almacenar una secuencia de valores de etiqueta. La representación más ingenua e ineficiente de una etiqueta-m es una lista (array, vector) de valores de etiqueta; una representación más eficiente es almacenar todas las etiquetas-m en un árbol prefijo representado como un array de nodos (v, p), donde v es el valor de la etiqueta y p es un puntero al nodo padre. Soporte de codificación

Es necesario comprender la diferencia entre puntos de código y unidades de código. Un punto de código es un identificador numérico de un símbolo. Una unidad de código es la unidad de almacenamiento más pequeña en el texto codificado. Un solo punto de código puede representarse con una o más unidades de código. En una codificación de longitud fija, todos los puntos de código se representan con el mismo número de unidades de código. En una codificación de longitud variable, los puntos de código pueden representarse con un número diferente de unidades de código. Tenga en cuenta que la regla "cualquiera" [^] coincide con cualquier punto de código, pero no necesariamente con cualquier unidad de código (la única forma de coincidir con cualquier unidad de código independientemente de la codificación es la regla predeterminada *). El lexer generado trabaja con un flujo de unidades de código: yych almacena una unidad de código y YYCTYPE es el tipo de unidad de código. Las expresiones regulares, por otro lado, se especifican en términos de puntos de código. Cuando re2js compila expresiones regulares a autómatas, traduce puntos de código a unidades de código. Esto generalmente no es una correspondencia simple: en codificaciones de longitud variable, un rango de puntos de código único puede traducirse a un gráfico complejo de unidades de código. Las siguientes codificaciones son compatibles:

  • ASCII (habilitado por defecto). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • EBCDIC (habilitado con --ebcdic o re2c:encoding:ebcdic). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • UCS2 (habilitado con --ucs2 o re2c:encoding:ucs2). Es una codificación de longitud fija con espacio de código [0-0xFFFF] y puntos de código y unidades de código de 2 bytes.
  • UTF8 (habilitado con --utf8 o re2c:encoding:utf8). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
  • UTF16 (habilitado con --utf16 o re2c:encoding:utf16). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 o 2 unidades de código.
  • UTF32 (habilitado con --utf32 o re2c:encoding:utf32). Es una codificación Unicode de longitud fija con espacio de código [0-0x10FFFF] y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión include/unicode_categories.re proporciona definiciones de re2js para las categorías Unicode estándar.

La opción --input-encoding especifica la codificación del archivo fuente, que se puede utilizar para habilitar literales Unicode en expresiones regulares. Por ejemplo, --input-encoding utf8 le dice a re2js que el archivo fuente está en UTF8 (difiere de --utf8 que establece la codificación del texto de entrada). La opción --encoding-policy especifica la forma en que re2js maneja los sustitutos Unicode (puntos de código en el rango [0xD800-0xDFFF]).

A continuación, se muestra un ejemplo de un lexer para identificadores Unicode codificados en UTF8.

// re2js $INPUT -o $OUTPUT --utf8 -s
/*!include:re2c "unicode_categories.re" */
function lex(yyinput) {
    let yycursor = 0
    /*!re2c
        re2c:yyfill:enable = 0;
        // "Sintaxis simplificada de identificadores y patrones Unicode"
        // (ver https://unicode.org/reports/tr31)
        id_start    = L | Nl | [$_];
        id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
        identifier  = id_start id_continue*;
        identifier { return true }
        *          { return false }
    */
}
if (!lex("_Ыдентификатор\0")) throw "error!"

Archivos de inclusión

re2js permite incluir otros archivos utilizando un bloque de la forma /*!include:re2c FILE */ o %{include FILE %}, o una directiva dentro de un bloque !include FILE ;, donde FILE es una ruta al archivo a incluir. re2js busca los archivos de inclusión en el directorio del archivo que los incluye y en las ubicaciones de inclusión, que se pueden especificar con la opción -I. Los bloques/directivas de inclusión en re2js funcionan de la misma manera que #include de C/C++: el contenido de FILE se copia y pega literalmente en lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias. Utilice la opción --depfile para rastrear las dependencias de compilación del archivo de salida en los archivos de inclusión. re2js proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como categorías Unicode) y forman algo así como una biblioteca estándar para re2js. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivo de inclusión 1 (definitions.js)

const INT = 1
const FLOAT = 2
const NAN = 3
/*!re2c
    number = [1-9][0-9]*;
*/

Archivo de inclusión 2 (extra_rules.re.inc)

// números de punto flotante
frac  = [0-9]* "." [0-9]+ | [0-9]+ ".";
exp   = 'e' [+-]? [0-9]+;
float = frac exp? | [0-9]+ exp;
float { return FLOAT }

Archivo de entrada

// re2js $INPUT -o $OUTPUT
/*!include:re2c "definitions.js" */
function lex(yyinput) {
    let yycursor = 0
    /*!re2c
        re2c:yyfill:enable = 0;
        *      { return NAN }
        number { return INT }
        !include "extra_rules.re.inc";
    */
}
function test(s, n) {
    if (lex(s) != n) throw "error!"
}
test("123\0", INT)
test("123.4567\0", FLOAT)

Archivos de cabecera

re2js permite generar un archivo de cabecera a partir del archivo .re de entrada utilizando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de cabecera y el segundo bloque marca su fin. Todo lo que esté entre estos bloques es procesado por re2js y el código generado se escribe en el archivo especificado con la opción --header o la configuración re2c:header (o stdout si no se usa ninguna opción ni configuración). El archivo de cabecera autogenerado puede ser necesario en casos donde re2js se utiliza para generar definiciones que deben ser visibles desde otras unidades de traducción.

Aquí hay un ejemplo de generación de un archivo de cabecera que contiene la definición del estado del lexer con variables de etiqueta (el número de variables depende de la gramática regular y es desconocido para el programador).

let state = require('./lexer/state.js');

exports.mk_state = function(str) {
    return {
        yyinput: str,
        /*!stags:re2c format = "@@: 0,\n"; */
        yycursor: 0
    }
}
/*!header:re2c:off*/
function lex(yyrecord) {
    let t
    /*!re2c
        re2c:api = record;
        re2c:tags = 1;
        re2c:yyfill:enable = 0;
        re2c:header = "lexer/state.js";

    */
}

    throw "error!"
}

Programas esqueleto

Con la opción -S, --skeleton, re2js ignora todo el código que no sea de re2js y genera un programa C autocontenido que puede compilarse y ejecutarse posteriormente. El programa consta de código lexer y datos de entrada. Para cada DFA construido (bloque o condición), re2js genera un lexer independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados esperados de las coincidencias. NAME

re2js - a re2c lexer generator

SYNOPSIS

re2js [-D|--emit-dot] [-h|--help] [-V|--version] [--dump-nfa] [--dump-dfa-raw] [input file]

INTRODUCTION

re2c generates C/C++ lexers from regular expressions. re2js is a variant of re2c that generates JavaScript lexers. It takes a description of a lexer as input and produces a JavaScript function that implements the lexer.

The generated lexer is typically used for parsing text, but it can also be used for finding patterns in strings or other sequences.

BASICS

The input to re2js consists of a set of regular expressions and the actions to be performed when a regular expression is matched. The syntax is similar to that of flex and re2c.

Here is a simple example:

/* re2js example */
/*!re2c
re2c:flags:case-insensitive;
[^]    { return ILLEGAL_CHARACTER; }
[0-9]+ { return NUMBER; }
[a-z]+ { return WORD; }
.      { return ANY_CHARACTER; }

This input defines a lexer with four rules:

  • Match any character that is not a digit or a letter.
  • Match one or more digits.
  • Match one or more lowercase letters.
  • Match any other character.

The actions associated with these rules are JavaScript code snippets that will be executed when the corresponding regular expression is matched.

The output of re2js is a JavaScript function that takes a string as input and returns a sequence of tokens. Each token represents a matched regular expression and its associated action.

HANDLING THE END OF INPUT

re2js provides mechanisms for handling the end of input gracefully. You can define specific rules to match the end of the input stream, allowing you to perform cleanup actions or signal the end of parsing.

BUFFER REFILLING

For large inputs, re2js supports buffer refilling to avoid loading the entire input into memory at once. This is done by specifying how the lexer should read more input when it reaches the end of the current buffer.

The following options control buffer refilling:

  • -b, --buffer-fill: Enable buffer refilling.
  • --buffer-size=size: Set the buffer size.

FEATURES

re2js programs are very useful for a number of reasons:

  • They can check correctness of various re2js optimizations (the data is generated early in the process, before any DFA transformations have taken place).
  • Generating a set of input data with good coverage may be useful for both testing and benchmarking.
  • Generating self-contained executable programs allows one to get minimized test cases (the original code may be large or have a lot of dependencies).

The difficulty with generating input data is that for all but the most trivial cases the number of possible input strings is too large (even if the string length is limited). re2js solves this difficulty by generating sufficiently many strings to cover almost all DFA transitions. It uses the following algorithm. First, it constructs a skeleton of the DFA. For encodings with 1-byte code unit size (such as ASCII, UTF-8 and EBCDIC) skeleton is just an exact copy of the original DFA. For encodings with multibyte code units skeleton is a copy of DFA with certain transitions omitted: namely, re2js takes at most 256 code units for each disjoint continuous range that corresponds to a DFA transition. The chosen values are evenly distributed and include range bounds. Instead of trying to cover all possible paths in the skeleton (which is infeasible) re2js generates sufficiently many paths to cover all skeleton transitions, and thus trigger the corresponding conditional jumps in the lexer. The algorithm implementation is limited by ~1Gb of transitions and consumes constant amount of memory (re2js writes data to file as soon as it is generated).

Visualization and debug

With the -D, --emit-dot option, re2js does not generate code. Instead, it dumps the generated DFA in DOT format. One can convert this dump to an image of the DFA using Graphviz or another library. Note that this option shows the final DFA after it has gone through a number of optimizations and transformations. Earlier stages can be dumped with various debug options, such as --dump-nfa, --dump-dfa-raw etc. (see the full list of options).
