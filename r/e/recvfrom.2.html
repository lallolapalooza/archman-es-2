recv(2) Manual de llamadas al sistema recv(2)

NOMBRE

recv, recvfrom, recvmsg - recibir un mensaje de un socket

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/socket.h>
ssize_t recv(int sockfd, void buf[restrict size], size_t size,
                 int flags);
ssize_t recvfrom(int sockfd, void buf[restrict size], size_t size,
                 int flags,
                 struct sockaddr *_Nullable restrict src_addr,
                 socklen_t *_Nullable restrict addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPCIÓN

Las llamadas recv(), recvfrom() y recvmsg() se utilizan para recibir mensajes de un socket. Pueden usarse para recibir datos tanto en sockets sin conexión como orientados a conexión. Esta página describe primero las características comunes de las tres llamadas al sistema y luego las diferencias entre ellas.

La única diferencia entre recv() y read(2) es la presencia de flags. Con un argumento flags cero, recv() es generalmente equivalente a read(2) (pero vea NOTAS). Además, la siguiente llamada


recv(sockfd, buf, size, flags);

es equivalente a


recvfrom(sockfd, buf, size, flags, NULL, NULL);

Todas las tres llamadas devuelven el tamaño del mensaje en caso de éxito. Si un mensaje es demasiado largo para caber en el búfer proporcionado, los bytes excedentes pueden ser descartados dependiendo del tipo de socket desde el cual se recibe el mensaje.

Si no hay mensajes disponibles en el socket, las llamadas de recepción esperan a que llegue un mensaje, a menos que el socket no esté en modo bloqueo (vea fcntl(2)), en cuyo caso se devuelve el valor -1 y errno se establece en EAGAIN o EWOULDBLOCK. Las llamadas de recepción normalmente devuelven los datos disponibles, hasta la cantidad solicitada, en lugar de esperar la recepción de la cantidad completa solicitada.

Una aplicación puede usar select(2), poll(2), o epoll(7) para determinar cuándo llegan más datos a un socket.

El argumento flags

El argumento flags se forma combinando uno o más de los siguientes valores:

MSG_CMSG_CLOEXEC (solo recvmsg(); desde Linux 2.6.23)
Establece la bandera de cierre al ejecutar para el descriptor de archivo recibido a través de un descriptor de archivo de dominio UNIX usando la operación SCM_RIGHTS (descrita en unix(7)). Esta bandera es útil por las mismas razones que la bandera O_CLOEXEC de open(2).
MSG_DONTWAIT (desde Linux 2.2)
Habilita la operación sin bloqueo; si la operación bloquearía, la llamada falla con EAGAIN o EWOULDBLOCK. Esto proporciona un comportamiento similar a establecer la bandera O_NONBLOCK (a través de la operación F_SETFL de fcntl(2)), pero difiere en que MSG_DONTWAIT es una opción por llamada, mientras que O_NONBLOCK es una configuración en la descripción del archivo abierto (vea open(2)), lo que afectará a todos los hilos del proceso que llama, así como a otros procesos que posean descriptores de archivo que se refieran a la misma descripción de archivo abierto.
MSG_ERRQUEUE (desde Linux 2.2)
Esta bandera especifica que se deben recibir errores en cola de la cola de errores del socket. El error se pasa en un mensaje auxiliar con un tipo dependiente del protocolo (para IPv4 IP_RECVERR). El usuario debe proporcionar un búfer de tamaño suficiente. Vea cmsg(3) y ip(7) para más información. La carga útil del paquete original que causó el error se pasa como datos normales a través de msg_iovec. La dirección de destino original del datagrama que causó el error se suministra a través de msg_name.
El error se proporciona en una estructura sock_extended_err:

#define SO_EE_ORIGIN_NONE    0
#define SO_EE_ORIGIN_LOCAL   1
#define SO_EE_ORIGIN_ICMP    2
#define SO_EE_ORIGIN_ICMP6   3
struct sock_extended_err
{
    uint32_t ee_errno;   /* Número de error */
    uint8_t  ee_origin;  /* De dónde provino el error */
    uint8_t  ee_type;    /* Tipo */
    uint8_t  ee_code;    /* Código */
    uint8_t  ee_pad;     /* Relleno */
    uint32_t ee_info;    /* Información adicional */
    uint32_t ee_data;    /* Otros datos */
    /* Pueden seguir más datos */
};
struct sockaddr *SO_EE_OFFENDER(struct sock_extended_err *);

ee_errno contiene el número errno del error en cola. ee_origin es el código de origen de dónde provino el error. Los otros campos son específicos del protocolo. La macro SO_EE_OFFENDER devuelve un puntero a la dirección del objeto de red de donde provino el error dado un puntero al mensaje auxiliar. Si esta dirección no se conoce, el miembro sa_family de sockaddr contiene AF_UNSPEC y los otros campos de sockaddr no están definidos. La carga útil del paquete que causó el error se pasa como datos normales.
Para errores locales, no se pasa ninguna dirección (esto se puede verificar con el miembro cmsg_len de cmsghdr). Para recepciones de errores, la bandera MSG_ERRQUEUE está establecida en msghdr. Después de que se ha pasado un error, el error pendiente del socket se regenera basándose en el siguiente error en cola y se pasará en la próxima operación de socket.
MSG_OOB
Esta bandera solicita la recepción de datos fuera de banda que no se recibirían en el flujo de datos normal. Algunos protocolos colocan datos urgentes al principio de la cola de datos normal, y por lo tanto, esta bandera no se puede usar con tales protocolos.
MSG_PEEK
Esta bandera hace que la operación de recepción devuelva datos desde el principio de la cola de recepción sin eliminar esos datos de la cola. Por lo tanto, una llamada de recepción posterior devolverá los mismos datos.
MSG_TRUNC (desde Linux 2.2)
Para sockets raw (AF_PACKET), datagramas de Internet (desde Linux 2.4.27/2.6.8), netlink (desde Linux 2.6.22), y datagramas UNIX, así como paquetes secuenciales (desde Linux 3.4): devuelve el tamaño real del paquete o datagrama, incluso cuando era más largo que el búfer proporcionado.
Para usar con sockets de transmisión de Internet, vea tcp(7).
MSG_WAITALL (desde Linux 2.2)
Esta bandera solicita que la operación se bloquee hasta que se complete la solicitud completa. Sin embargo, la llamada aún puede devolver menos datos de los solicitados si se captura una señal, ocurre un error o desconexión, o los próximos datos a recibir son de un tipo diferente a los devueltos. Esta bandera no tiene efecto para sockets de datagramas.

recvfrom()

recvfrom() coloca el mensaje recibido en el búfer buf. El llamante debe especificar el tamaño del búfer en size.

Si src_addr no es NULL, y el protocolo subyacente proporciona la dirección de origen del mensaje, esa dirección de origen se coloca en el búfer apuntado por src_addr. En este caso, addrlen es un argumento de valor-resultado. Antes de la llamada, debe inicializarse al tamaño del búfer asociado con src_addr. Al regresar, addrlen se actualiza para contener el tamaño real de la dirección de origen. La dirección devuelta se trunca si el búfer proporcionado es demasiado pequeño; en este caso, addrlen devolverá un valor mayor que el que se suministró a la llamada.

Si al llamante no le interesa la dirección de origen, src_addr y addrlen deben especificarse como NULL.

NAME

recv, recvfrom, recvmsg - receive a message from a socket

LIBRARY

Socket API (-lsocket -lnsl)

SYNOPSIS

cc ... -lsocket -lnsl

#include <sys/types.h>
#include <sys/socket.h>
ssize_t recv(int sockfd, void *buf, size_t len, int flags);
ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags,
                 struct sockaddr *src_addr, socklen_t *addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

These system calls are used to receive messages from sockets. recv() is equivalent to recvmsg() with a NULL msg_name and msg_iovlen equal to 1. recvfrom() is equivalent to recvmsg() with a NULL msg_iov.

The calling process must have the appropriate permissions on the socket referred to by sockfd to receive data. The data is copied from the socket into the buffer pointed to by buf, and the data is not discarded from the socket until the data is read by recv(), recvfrom() or recvmsg().

If the socket is defined as non-blocking and no messages are available to be received on the socket, recv(), recvfrom() and recvmsg() return -1 and set errno to EAGAIN.

If messages may be larger than the buffer size, the MSG_TRUNC flag should be used. If this flag is set, a receiving call may return a message larger than the length specified by len. If the message is larger than the buffer, the bufffer will be filled with the data available, and the remainder of the message will be discarded.

The parameter flags can be used to modify the behavior of socket data reception. MSG_PEEK will peek at incoming messages without removing them from the input queue. MSG_WAITALL will wait for all of the requested data to be received. The MSG_DONTWAIT flag is equivalent to setting the O_NONBLOCK flag (see fcntl(2)) on the socket file description. MSG_ERRQUEUE will receive error messages, not data messages. MSG_OOB will receive out-of-band data.

The recvfrom() call additionally retrieves the origin address of the message, which is stored in the buffer pointed to by src_addr. The addrlen argument is a value-result argument, which should be initialized to the size of the buffer pointed to by src_addr, and contain the actual length of the address upon return.

The recvmsg() call uses a structure msghdr to minimize the number of directly supplied arguments. This structure is defined as follows in <sys/socket.h>:

struct msghdr {
    void         *msg_name;       /* Optional address */
    socklen_t     msg_namelen;    /* Size of address */
    struct iovec *msg_iov;        /* Scatter/gather array */
    size_t        msg_iovlen;     /* # elements in msg_iov */
    void         *msg_control;    /* Ancillary data, see below */
    size_t        msg_controllen; /* Ancillary data buffer size */
    int           msg_flags;      /* Flags on received message */
};

The msg_name field points to a caller-allocated buffer that is used to return the source address if the socket is unconnected. The caller should set msg_namelen to the size of this buffer before this call; upon return from a successful call, msg_namelen will contain the size of the returned address. If the application does not need to know the source address, msg_name can be specified as NULL.

The fields msg_iov and msg_iovlen describe scatter-gather locations, as discussed in readv(2).

The field msg_control, which has size msg_controllen, points to a buffer for other protocol control-related messages or miscellaneous ancillary data. When recvmsg() is called, msg_controllen should contain the size of the available buffer in msg_control; upon return from a successful call it will contain the size of the control message sequence.

The messages are of the form:

struct cmsghdr {
    size_t cmsg_len;    /* Data byte count, including header
                           (type is socklen_t in POSIX) */
    int    cmsg_level;  /* Originating protocol */
    int    cmsg_type;   /* Protocol-specific type */
/* followed by
    unsigned char cmsg_data[]; */
};

Ancillary data should be accessed only by the macros defined in cmsg(3).

As an example, Linux uses this ancillary data mechanism to pass extended errors, IP options or file descriptors over UNIX domain sockets. For further information on the use of ancillary data in various socket domains, see unix(7) and ip(7).

The msg_flags field in the msghdr is set on return of recvmsg(). It can contain several flags:

MSG_EOR
indicates end-of-record; the data returned completed a record (generally, used with sockets of type SOCK_SEQPACKET).
MSG_TRUNC
indicates that the trailing portion of a datagram was discarded because the datagram was larger than the buffer supplied.
MSG_CTRUNC
indicates that some control data was discarded due to lack of space in the buffer for ancillary data.
MSG_OOB
is returned to indicate that expedited or out-of-band data was received.
MSG_ERRQUEUE
indicates that no data was received but an extended error from the socket error queue.
MSG_CMSG_CLOEXEC (since Linux 2.6.23)
indicates that MSG_CMSG_CLOEXEC was specified in the flags argument of recvmsg().

RETURN VALUE

These calls return the number of bytes received, or -1 if an error occurred. In the event of an error, errno is set to indicate the error.

When a stream socket peer has performed an orderly shutdown, the return value will be 0 (the traditional "end-of-file" return).

Datagram sockets in various domains (e.g., the UNIX and Internet domains) permit zero-size datagrams. When such a datagram is received, the return value is 0.

The value 0 may also be returned if the requested number of bytes to receive from a stream socket was 0.

ERRORS

These are some standard errors generated by the socket layer. Additional errors may be generated and returned from the underlying protocol modules; see their manual pages.

EAGAIN or EWOULDBLOCK
The socket is marked nonblocking and the receive operation would block, or a receive timeout had been set and the timeout expired before data was received. POSIX.1 allows either error to be returned for this case, and does not require these constants to have the same value, so a portable application should check for both possibilities.
EBADF
The argument sockfd is an invalid file descriptor.
ECONNREFUSED
A remote host refused to allow the network connection (typically because it is not running the requested service).
EFAULT
The receive buffer pointer(s) point outside the process's address space.
EINTR
The receive was interrupted by delivery of a signal before any data was available; see signal(7).
EINVAL
Invalid argument passed.
ENOMEM
Could not allocate memory for recvmsg().
ENOTCONN
The socket is associated with a connection-oriented protocol and has not been connected (see connect(2) and accept(2)).
ENOTSOCK
The file descriptor sockfd does not refer to a socket.

VERSIONS

According to POSIX.1, the msg_controllen field of the msghdr structure should be typed as socklen_t, and the msg_iovlen field should be typed as int, but glibc currently types both as size_t.

STANDARDS

POSIX.1-2024.

HISTORY

POSIX.1-2001, 4.2BSD.

POSIX.1 describes only the MSG_OOB, MSG_PEEK, and MSG_WAITALL flags.

NOTES

If a zero-size datagram is pending, read(2) and recv() with a flags argument of zero provide different behavior. In this circumstance, read(2) has no effect (the datagram remains pending), while recv() consumes the pending datagram.

See recvmmsg(2) for information about a Linux-specific system call that can be used to receive multiple datagrams in a single call.

EXAMPLES

An example of the use of recvfrom() is shown in getaddrinfo(3).

recvfrom(2)

NAME

recvfrom - receive a message from a socket

SYNOPSIS

#include <sys/types.h>
#include <sys/socket.h>

ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags,
struct sockaddr *src_addr,
socklen_t *addrlen);

DESCRIPTION

The recvfrom() function shall retrieve the next available message from the network and store it into the buffer pointed to by buf. The calling process must have permission to receive messages from the socket. If the message is longer than the size specified by len, the message shall be truncated.

If the socket is a connectionless socket, recvfrom() is used to receive datagrams until the $<$code>recvfrom</code> call returns with a value less than 0. If the socket is connection-oriented, recvfrom() is equivalent to recv().

The sockfd argument is the file descriptor of the socket from which to receive.

The buf argument is a buffer into which the data will be placed.

The len argument specifies the length of the buffer.

The flags argument are bits that modify the behavior of the function call. The flags are:

MSG_PEEK
Peek at incoming messages. The data is returned, but is not consumed from the input queue. If the message is longer than len, recvfrom() returns -1 and sets errno to EMSGSIZE. The next receive operation will see the same message data.
MSG_WAITALL
Wait for the full amount of data requested to be received. This option may be used with both stream and datagram sockets. If the message is longer than len, recvfrom() returns -1 and sets errno to EMSGSIZE.

If src_addr is not a null pointer, the address of the sender of the message shall be placed in the buffer pointed to by src_addr. The actual length of the address is returned in the location pointed to by addrlen. If src_addr is a null pointer, the address information is not returned.

RETURN VALUE

If the call completes successfully, recvfrom() shall return the number of bytes received, which may be less than the requested number of bytes. If there are no messages available to be received and the socket has been placed in non-blocking mode, recvfrom() shall return -1 and set errno to EAGAIN or EWOULDBLOCK. If there are no messages available to be received and the socket has been placed in blocking mode, the value returned shall be the transmission of the calling process or thread until data is available or an error occurs. If an error occurs, -1 shall be returned and errno shall be set to indicate the error.

ERRORS

EBADF
The argument sockfd is not a valid file descriptor.
ECONNRESET
Connection reset by peer.
EINTR
The call was interrupted by a signal before any data was available.
EINVAL
The socket is not in a valid state, or len is negative.
ENOTCONN
The socket is not connected.
ENOTSOCK
The argument sockfd is a file descriptor referring to a file, not a socket.
EWOULDBLOCK
The socket is marked non-blocking and no messages were available to be received.
EAGAIN
Same as EWOULDBLOCK.
EMSGSIZE
The message is too long to fit in the buffer supplied or if the MSG_PEEK or MSG_WAITALL flags are used and the message is longer than the supplied buffer.
EFAULT
The buf argument points to an invalid address.

EXAMPLES


                    #include <stdio.h>
                    #include <stdlib.h>
                    #include <string.h>
                    #include <sys/types.h>
                    #include <sys/socket.h>
                    #include <netinet/in.h>
                    #include <arpa/inet.h>
                    #include <unistd.h>

                    #define PORT 4321
                    #define MAX_MSG_SIZE 1024

                    int main() {
                        int sockfd;
                        struct sockaddr_in servaddr, cliaddr;
                        char buffer[MAX_MSG_SIZE];
                        socklen_t clilen;
                        ssize_t numbytes;

                        // Create socket file descriptor
                        if ((sockfd = socket(AF_INET, SOCK_DGRAM, 0)) < 0) {
                            perror("socket creation failed");
                            exit(EXIT_FAILURE);
                        }

                        memset(&servaddr, 0, sizeof(servaddr));
                        memset(&cliaddr, 0, sizeof(cliaddr));

                        // Fill server address structure
                        servaddr.sin_family = AF_INET; // IPv4
                        servaddr.sin_addr.s_addr = INADDR_ANY; // Any address
                        servaddr.sin_port = htons(PORT); // Port number

                        // Bind the socket with the server address
                        if (bind(sockfd, (const struct sockaddr *)&servaddr, sizeof(servaddr)) < 0) {
                            perror("bind failed");
                            close(sockfd);
                            exit(EXIT_FAILURE);
                        }

                        printf("Server listening on port %d...\n", PORT);

                        clilen = sizeof(cliaddr); // Length of the client address structure

                        // Receive message from client
                        numbytes = recvfrom(sockfd, buffer, MAX_MSG_SIZE, 0,
                                          (struct sockaddr *)&cliaddr, &clilen);
                        if (numbytes < 0) {
                            perror("recvfrom failed");
                            close(sockfd);
                            exit(EXIT_FAILURE);
                        }

                        buffer[numbytes] = '\0'; // Null-terminate the received data

                        char client_ip[INET_ADDRSTRLEN];
                        inet_ntop(AF_INET, &cliaddr.sin_addr, client_ip, INET_ADDRSTRLEN);
                        printf("Received message from %s:%d: %s\n", client_ip, ntohs(cliaddr.sin_port), buffer);

                        // You can then send a response back using sendto() if needed
                        // const char *response = "Message received";
                        // sendto(sockfd, response, strlen(response), 0,
                        //        (const struct sockaddr *)&cliaddr, clilen);

                        close(sockfd);
                        return 0;
                    }
