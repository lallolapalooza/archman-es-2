recv(2) Manual de llamadas al sistema recv(2)

NOMBRE

recv, recvfrom, recvmsg - recibir un mensaje de un socket

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/socket.h>
ssize_t recv(int sockfd, void buf[size], size_t size,
                 int flags);
ssize_t recvfrom(int sockfd, void buf[restrict size], size_t size,
                 int flags,
                 struct sockaddr *_Nullable restrict src_addr,
                 socklen_t *_Nullable restrict addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPCIÓN

Las llamadas recv(), recvfrom(), y recvmsg() se usan para recibir mensajes de un socket. Pueden usarse para recibir datos tanto en sockets sin conexión como orientados a conexión. Esta página primero describe las características comunes de las tres llamadas al sistema y luego describe las diferencias entre ellas.

La única diferencia entre recv() y read(2) es la presencia de flags. Con un argumento flags cero, recv() es generalmente equivalente a read(2) (pero véase NOTAS). Además, la siguiente llamada


recv(sockfd, buf, size, flags);

es equivalente a


recvfrom(sockfd, buf, size, flags, NULL, NULL);

Las tres llamadas devuelven el tamaño del mensaje al completarse con éxito. Si un mensaje es demasiado largo para caber en el búfer proporcionado, los bytes en exceso pueden ser descartados dependiendo del tipo de socket del que se reciba el mensaje.

Si no hay mensajes disponibles en el socket, las llamadas de recepción esperan a que llegue un mensaje, a menos que el socket no esté en modo de bloqueo (véase fcntl(2)), en cuyo caso se devuelve el valor -1 y errno se establece en EAGAIN o EWOULDBLOCK. Las llamadas de recepción normalmente devuelven cualquier dato disponible, hasta la cantidad solicitada, en lugar de esperar la recepción de la cantidad total solicitada.

Una aplicación puede usar select(2), poll(2), o epoll(7) para determinar cuándo llegan más datos a un socket.

El argumento flags

El argumento flags se forma combinando uno o más de los siguientes valores:

MSG_CMSG_CLOEXEC (solo recvmsg(); desde Linux 2.6.23)
Establece la bandera de cierre al ejecutar para el descriptor de archivo recibido a través de un descriptor de archivo de dominio UNIX usando la operación SCM_RIGHTS (descrita en unix(7)). Esta bandera es útil por las mismas razones que la bandera O_CLOEXEC de open(2).
MSG_DONTWAIT (desde Linux 2.2)
Habilita la operación sin bloqueo; si la operación bloquearía, la llamada falla con EAGAIN o EWOULDBLOCK. Esto proporciona un comportamiento similar a establecer la bandera O_NONBLOCK (a través de la operación F_SETFL de fcntl(2)), pero difiere en que MSG_DONTWAIT es una opción por llamada, mientras que O_NONBLOCK es una configuración en la descripción del archivo abierto (véase open(2)), que afectará a todos los hilos en el proceso de llamada, así como a otros procesos que posean descriptores de archivo que se refieran a la misma descripción de archivo abierto.
MSG_ERRQUEUE (desde Linux 2.2)
Esta bandera especifica que se deben recibir errores en cola del socket de la cola de errores. El error se pasa en un mensaje auxiliar con un tipo dependiente del protocolo (para IPv4 IP_RECVERR). El usuario debe proporcionar un búfer de tamaño suficiente. Consulte cmsg(3) y ip(7) para más información. La carga útil del paquete original que causó el error se pasa como datos normales a través de msg_iovec. La dirección de destino original del datagrama que causó el error se proporciona a través de msg_name.
El error se proporciona en una estructura sock_extended_err:

#define SO_EE_ORIGIN_NONE    0
#define SO_EE_ORIGIN_LOCAL   1
#define SO_EE_ORIGIN_ICMP    2
#define SO_EE_ORIGIN_ICMP6   3
struct sock_extended_err
{
    uint32_t ee_errno;   /* Número de error */
    uint8_t  ee_origin;  /* Dónde se originó el error */
    uint8_t  ee_type;    /* Tipo */
    uint8_t  ee_code;    /* Código */
    uint8_t  ee_pad;     /* Relleno */
    uint32_t ee_info;    /* Información adicional */
    uint32_t ee_data;    /* Otros datos */
    /* Pueden seguir más datos */
};
struct sockaddr *SO_EE_OFFENDER(struct sock_extended_err *);

ee_errno contiene el número errno del error en cola. ee_origin es el código de origen de dónde se originó el error. Los otros campos son específicos del protocolo. La macro SO_EE_OFFENDER devuelve un puntero a la dirección del objeto de red donde se originó el error, dado un puntero al mensaje auxiliar. Si esta dirección no se conoce, el miembro sa_family de sockaddr contiene AF_UNSPEC y los otros campos de sockaddr no están definidos. La carga útil del paquete que causó el error se pasa como datos normales.
Para errores locales, no se pasa ninguna dirección (esto se puede comprobar con el miembro cmsg_len de cmsghdr). Para recepciones de errores, la bandera MSG_ERRQUEUE se establece en msghdr. Después de que se haya pasado un error, el error de socket pendiente se regenera basándose en el siguiente error en cola y se pasará en la siguiente operación de socket.
MSG_OOB
Esta bandera solicita la recepción de datos fuera de banda que no se recibirían en el flujo de datos normal. Algunos protocolos colocan datos acelerados al principio de la cola de datos normal, por lo que esta bandera no se puede usar con tales protocolos.
MSG_PEEK
Esta bandera hace que la operación de recepción devuelva datos desde el principio de la cola de recepción sin eliminar esos datos de la cola. Por lo tanto, una llamada de recepción posterior devolverá los mismos datos.
MSG_TRUNC (desde Linux 2.2)
Para sockets raw (AF_PACKET), datagrama de Internet (desde Linux 2.4.27/2.6.8), netlink (desde Linux 2.6.22), y datagrama UNIX, así como secuenciados por paquetes (desde Linux 3.4): devuelve el tamaño real del paquete o datagrama, incluso cuando era más largo que el búfer proporcionado.
Para uso con sockets de flujo de Internet, véase tcp(7).
MSG_WAITALL (desde Linux 2.2)
Esta bandera solicita que la operación bloquee hasta que se satisfaga la solicitud completa. Sin embargo, la llamada aún puede devolver menos datos de los solicitados si se detecta una señal, ocurre un error o una desconexión, o los siguientes datos a recibir son de un tipo diferente al devuelto. Esta bandera no tiene efecto para sockets de datagrama.

recvfrom()

recvfrom() coloca el mensaje recibido en el búfer buf. El llamante debe especificar el tamaño del búfer en size.

Si src_addr no es NULL, y el protocolo subyacente proporciona la dirección de origen del mensaje, esa dirección de origen se coloca en el búfer apuntado por src_addr. En este caso, addrlen es un argumento de valor-resultado. Antes de la llamada, debe inicializarse al tamaño del búfer asociado con src_addr. Tras la devolución, addrlen se actualiza para contener el tamaño real de la dirección de origen. La dirección devuelta se trunca si el búfer proporcionado es demasiado pequeño; en este caso, addrlen devolverá un valor mayor del que se proporcionó a la llamada.

Si el llamante no está interesado en la dirección de origen, src_addr y addrlen deben especificarse como NULL.

recvmsg()

recvmsg() es una interfaz más general que puede usar para recibir datos y información auxiliar. El argumento msg es un puntero a una estructura msghdr, que se define como sigue:


struct msghdr {
    void         *msg_name;       /* Puntero a la estructura de la dirección de origen */
    socklen_t     msg_namelen;    /* Tamaño de la estructura de la dirección de origen */
    struct iovec *msg_iov;        /* Puntero a un array de estructuras iovec */
    int           msg_iovlen;     /* Número de estructuras en msg_iov */
    void         *msg_control;    /* Puntero a datos auxiliares */
    socklen_t     msg_controllen; /* Tamaño del búfer de datos auxiliares */
    int           msg_flags;      /* Flags de entrada y salida */
};

La estructura msghdr se utiliza para enviar y recibir datos junto con información adicional, como descriptores de archivos (a través de SCM_RIGHTS), información de control de red (como información de paquetes de nivel inferior o información de enrutamiento), o información de seguridad.

Los campos msg_name y msg_namelen especifican la dirección de la entidad que envía el mensaje (igual que en recvfrom()).

Los campos msg_iov y msg_iovlen especifican una lista de búferes en los que se deben colocar los datos recibidos. Esto se conoce como "scatter/gather I/O".

Los campos msg_control y msg_controllen especifican un búfer para los datos auxiliares. El tamaño del búfer se especifica en msg_controllen. Si el búfer es demasiado pequeño, msg_controllen contendrá el número de bytes que realmente se utilizaron. Si no se esperan datos auxiliares, estos campos deben establecerse en NULL y 0, respectivamente.

El campo msg_flags contiene banderas adicionales que afectan el comportamiento de la recepción, o banderas que se establecen en la salida. Las banderas de entrada son las mismas que el argumento flags. Las banderas de salida incluyen:

MSG_CMSG_COMPLETED
Indica que todos los mensajes auxiliares disponibles han sido procesados.
MSG_CTRUNC
Indica que se ha truncado un mensaje de control porque el búfer proporcionado era demasiado pequeño.
MSG_DONTWAIT
(Igual que la bandera de entrada.)
MSG_ERRQUEUE
(Igual que la bandera de entrada.)
MSG_PEEK
(Igual que la bandera de entrada.)
MSG_TRUNC
(Igual que la bandera de entrada.)

VALOR_DE_RETORNO

En caso de éxito, estas llamadas devuelven el número de bytes recibidos. Si el socket está conectado y se ha recibido una marca de fin de archivo, 0 se devuelve.

En caso de error, se devuelve -1 y errno se establece para indicar el error.

ERRORES

En una llamada de recepción sin bloqueo, si no hay datos disponibles para recibir, el valor devuelto es -1 y errno se establece a EAGAIN o EWOULDBLOCK.

Los errores se pueden devolver por una variedad de razones, incluyendo:

EBADF
El argumento del descriptor de archivo sockfd no es válido.
ECONNRESET
La conexión se reinició por una excepción en el host remoto, por ejemplo, después de que un paquete de reinicio fuera recibido en el socket.
EFAULT
La dirección del búfer buf o msg es inválida.
EINTR
Se capturó una señal antes de que se recibiera ningún dato.
EINVAL
Se solicitó un argumento inválido (por ejemplo, msg_iovlen es negativo).
ENOTCONN
El socket no está conectado.
ENOTSOCK
El argumento sockfd no es un socket.
EOPNOTSUPP
No se admite la operación solicitada en el socket o protocolo.
ENOBUFS
El sistema no tiene suficientes recursos de búfer para realizar la operación.
EWOULDBLOCK
El socket está configurado como no bloqueante y la operación de recepción bloquearía.
EAGAIN
El socket está configurado como no bloqueante y la operación de recepción bloquearía. Esto es un sinónimo de EWOULDBLOCK.

ESTÁNDARES

Estas llamadas al sistema son parte de la interfaz de sockets POSIX.

HISTORIA

La llamada al sistema recv() apareció en BSD 4.3.

El argumento flags para recv(), recvfrom(), y recvmsg() apareció en FreeBSD 2.2.

La bandera MSG_WAITALL se añadió en Linux 2.2.

La bandera MSG_TRUNC se añadió en Linux 2.2 (para sockets raw) y se extendió a sockets de datagramas de Internet, netlink y UNIX en versiones posteriores.

La bandera MSG_ERRQUEUE se añadió en Linux 2.2.

La bandera MSG_CMSG_CLOEXEC se añadió en Linux 2.6.23.

NAME

recv, recvfrom, recvmsg - receive a message from a socket

LIBRARY

lib-core

SYNOPSIS

#include <sys/types.h>
#include <sys/socket.h>

ssize_t recv(int sockfd, void *buf, size_t len, int flags);
ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags,
                 struct sockaddr *src_addr, socklen_t *addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

The recv(), recvfrom(), and recvmsg() calls are used to receive messages from a socket. The sender and receiver must be on the same host, or on a network that supports the communication domain in use. Connections based on sockets.

recv()

The recv() call is normally used only on a connected socket (see connect(2)). It is equivalent to the call:


recvfrom(fd, buf, size, flags, NULL, NULL);

recvfrom()

The recvfrom() call receives a message from a socket and stores the source address in the src_addr argument. addrlen is a value-result argument: the caller must initialize it to contain the size of the buffer pointed to by src_addr; upon return it will contain the actual length of the source address. If src_addr is NULL, the source address is not returned.

The flags argument is an integer in which zero or more of the following, ORed together, may be supplied:

MSG_OOB
Peek at incoming out-of-band data. send(2).
MSG_PEEK
Leave the data in the socket receive buffer even after retrieving it.
MSG_WAITALL
Wait for the full amount of data requested to be received. The call only returns when the requested amount of data has been received or an error occurs.

A 0-length datagram is a valid datagram and will be received as such with a return value of 0.

If the MSG_WAITALL flag is set, then EAGAIN or EWOULDBLOCK error shall not be returned.

recvmsg()

The recvmsg() call uses a msghdr structure to minimize the number of directly supplied arguments. This structure is defined as follows in <sys/socket.h>:


struct msghdr {
    void         *msg_name;       /* Optional address */
    socklen_t     msg_namelen;    /* Size of address */
    struct iovec *msg_iov;        /* Scatter/gather array */
    size_t        msg_iovlen;     /* # elements in msg_iov */
    void         *msg_control;    /* Ancillary data, see below */
    size_t        msg_controllen; /* Ancillary data buffer size */
    int           msg_flags;      /* Flags on received message */
};

The msg_name field points to a caller-allocated buffer that is used to return the source address if the socket is unconnected. The caller should set msg_namelen to the size of this buffer before this call; upon return from a successful call, msg_namelen will contain the size of the returned address. If the application does not need to know the source address, msg_name can be specified as NULL.

The fields msg_iov and msg_iovlen describe scatter-gather locations, as discussed in readv(2).

The field msg_control, which has size msg_controllen, points to a buffer for other protocol control-related messages or miscellaneous ancillary data. When recvmsg() is called, msg_controllen should contain the size of the available buffer in msg_control; upon return from a successful call it will contain the size of the control message sequence.

The messages are of the form:


struct cmsghdr {
    size_t cmsg_len;    /* Data byte count, including header
                           (type is socklen_t in POSIX) */
    int    cmsg_level;  /* Originating protocol */
    int    cmsg_type;   /* Protocol-specific type */
/* followed by
    unsigned char cmsg_data[]; */
};

Ancillary data should be accessed only by the macros defined in cmsg(3).

As an example, Linux uses this ancillary data mechanism to pass extended errors, IP options or file descriptors over UNIX domain sockets. For further information on the use of ancillary data in various socket domains, see unix(7) and ip(7).

The msg_flags field in the msghdr is set on return of recvmsg(). It can contain several flags:

MSG_EOR
indicates end-of-record; the data returned completed a record (generally, used with sockets of type SOCK_SEQPACKET).
MSG_TRUNC
indicates that the trailing portion of a datagram was discarded because the datagram was larger than the buffer supplied.
MSG_CTRUNC
indicates that some control data was discarded due to lack of space in the buffer for ancillary data.
MSG_OOB
is returned to indicate that expedited or out-of-band data was received.
MSG_ERRQUEUE
indicates that no data was received but an extended error from the socket error queue.
MSG_CMSG_CLOEXEC (since Linux 2.6.23)
indicates that MSG_CMSG_CLOEXEC was specified in the flags argument of recvmsg().

RETURN VALUE

These calls return the number of bytes received, or -1 if an error occurred. In the event of an error, errno is set to indicate the error.

When a stream socket peer has performed an orderly shutdown, the return value will be 0 (the traditional "end-of-file" return).

Datagram sockets in various domains (e.g., the UNIX and Internet domains) permit zero-size datagrams. When such a datagram is received, the return value is 0.

The value 0 may also be returned if the requested number of bytes to receive from a stream socket was 0.

ERRORS

These are some standard errors generated by the socket layer. Additional errors may be generated and returned from the underlying protocol modules; see their manual pages.

EAGAIN or EWOULDBLOCK
The socket is marked nonblocking and the receive operation would block, or a receive timeout had been set and the timeout expired before data was received. POSIX.1 allows either error to be returned for this case, and does not require these constants to have the same value, so a portable application should check for both possibilities.
EBADF
The argument sockfd is an invalid file descriptor.
ECONNREFUSED
A remote host refused to allow the network connection (typically because it is not running the requested service).
EFAULT
The receive buffer pointer(s) point outside the process's address space.
EINTR
The receive was interrupted by delivery of a signal before any data was available; see signal(7).
EINVAL
Invalid argument passed.
ENOMEM
Could not allocate memory for recvmsg().
ENOTCONN
The socket is associated with a connection-oriented protocol and has not been connected (see connect(2) and accept(2)).
ENOTSOCK
The file descriptor sockfd does not refer to a socket.

VERSIONS

According to POSIX.1, the msg_controllen field of the msghdr structure should be typed as socklen_t, and the msg_iovlen field should be typed as int, but glibc currently types both as size_t.

STANDARDS

POSIX.1-2024.

HISTORY

POSIX.1-2001, 4.2BSD.

POSIX.1 describes only the MSG_OOB, MSG_PEEK, and MSG_WAITALL flags.

NOTES

If a zero-size datagram is pending, read(2) and recv() with a flags argument of zero provide different behavior. In this circumstance, read(2) has no effect (the datagram remains pending), while recv() consumes the pending datagram.

See recvmmsg(2) for information about a Linux-specific system call that can be used to receive multiple datagrams in a single call.
