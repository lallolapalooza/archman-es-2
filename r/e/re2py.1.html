NOMBRE

re2py - genera analizadores léxicos rápidos para Python

SINOPSIS

re2py [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para la entrada estándar.

INTRODUCCIÓN

re2py funciona como un preprocesador. Lee el archivo de entrada (que normalmente es un programa en Python, pero puede ser cualquier cosa) y busca bloques de código encerrados en marcadores especiales de inicio/fin. El texto fuera de estos bloques se copia tal cual al archivo de salida. El contenido de los bloques es procesado por re2py. Los traduce a código en Python y genera el código resultante en lugar del bloque.

Aquí hay un ejemplo de un pequeño programa que verifica si una cadena dada contiene un número decimal:

# re2py $INPUT -o $OUTPUT
def lex(yyinput):
    yycursor = 0
%{
    re2c:yyfill:enable = 0;
    re2c:indent:top = 1;
    [1-9][0-9]* { return True }
    *           { return False }
%}
assert lex(b"1234\0")

En la salida, re2py reemplazó el bloque intermedio con el código generado:

# Generado por re2py
# re2py $INPUT -o $OUTPUT
def lex(yyinput):
    yycursor = 0
    yystate = 0
    while True:
        match yystate:
            case 0:
                yych = yyinput[yycursor]
                yycursor += 1
                if yych <= 0x30:
                    yystate = 1
                    continue
                if yych <= 0x39:
                    yystate = 2
                    continue
                yystate = 1
                continue
            case 1:
                return False
            case 2:
                yych = yyinput[yycursor]
                if yych <= 0x2F:
                    yystate = 3
                    continue
                if yych <= 0x39:
                    yycursor += 1
                    yystate = 2
                    continue
                yystate = 3
                continue
            case 3:
                return True
            case _:
                raise "error interno del analizador léxico"
assert lex(b"1234\0")

BÁSICOS

Un programa re2py consiste en una secuencia de bloques intercalados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresión-regular ;
Una definición asocia nombre con expresión-regular. Los nombres pueden contener caracteres alfanuméricos y guion bajo. La sección de expresiones regulares ofrece una visión general de la sintaxis de re2py para expresiones regulares. Una vez definido, el nombre puede usarse en otras expresiones regulares y en reglas. La recursión en definiciones con nombre no está permitida, y cada nombre debe definirse antes de usarse. Un bloque hereda definiciones con nombre del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite modificar el comportamiento de re2py y personalizar el código generado. Para obtener una lista completa de configuraciones compatibles con re2py, consulte la sección de configuraciones. Dependiendo de la configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista solo en caracteres alfanuméricos. Un bloque hereda configuraciones del ámbito global y puede redefinirlas o agregar nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final.
expresión-regular código
Una regla asocia una expresión-regular con su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en una nueva línea seguida de cualquier carácter no blanco). Si la expresión-regular coincide, se ejecuta el código asociado. Si coinciden varias reglas, la coincidencia más larga tiene precedencia. Si varias reglas coinciden con la misma cadena, la más temprana tiene precedencia. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse, tiene la menor prioridad independientemente de su lugar en el bloque, y coincide con cualquier unidad de código (no necesariamente un carácter válido, ver la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para el manejo del fin de entrada. Con las condiciones de inicio, las reglas tienen una sintaxis más compleja.
!acción código
Una acción asocia un bloque de código definido por el usuario a un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas asocian código a los estados finales). Ver la sección de acciones para una lista completa de acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias especiales predefinidas. Cada directiva tiene un propósito único. Ver la sección de directivas para más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (se admiten ambos estilos). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que permiten referenciarlos en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2py compila las expresiones regulares asociadas a cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se agregan al ámbito global y se vuelven visibles para los bloques subsiguientes. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera código por sí mismo, ni agrega definiciones al ámbito global; está destinado a ser reutilizado en otros bloques. Esta es una forma de compartir código (más detalles en la sección de bloques reutilizables). Antes de la versión 2.2 de re2py, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2py busca bloques de reglas con ese nombre. De lo contrario, se usa el bloque de reglas más reciente (ya sea nombrado o sin nombre). Un bloque de uso puede agregar sus propias definiciones, configuraciones y reglas, que se agregan a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2py, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macro-definición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Puede personalizarse con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXFILL.
/*!maxnmatch:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{maxnmatch[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXNMATCH (requiere la opción -P --posix-captures). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXNMATCH (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macro-definición para C (#define YYMAXNMATCH <n>), o una variable global para Go (var YYM
AXNMATCH int = <n>). Puede personalizarse con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXNMATCH.
/*!stags:re2c[:<nombre1>[:<nombre2>...]] ... */, /*!mtags:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{stags[:<nombre1>[:<nombre2>...]] ... %}, %{mtags[:<nombre1>[:<nombre2>...]] ... %{
Bloques que especifican una pieza de código de plantilla que se expande para cada etiqueta s/etiqueta m generada por re2py. Una lista opcional de nombres de bloque especifica qué bloques se incluirán al calcular el conjunto de variables de etiqueta (si la lista está vacía, se incluyen todos los bloques). Hay dos configuraciones opcionales: format y separator. La configuración format especifica una cadena de plantilla donde @@{tag} (o @@ para abreviar) se reemplaza con el nombre de cada variable de etiqueta. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes variables de etiqueta.
/*!svars:re2c[:<nombre1>[:<nombre2>...]] ... */, /*!mvars:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{svars[:<nombre1>[:<nombre2>...]] ... %}, %{mvars[:<nombre1>[:<nombre2>...]] ... %{
Bloques que especifican una pieza de código de plantilla que se expande para cada etiqueta s/etiqueta m que se menciona explícitamente en las reglas (con la opción --tags) o se genera implícitamente por re2py (con las opciones --captvars o --posix-captvars). Una lista opcional de nombres de bloque especifica qué bloques se incluirán al calcular el conjunto de etiquetas (si la lista está vacía, se incluyen todas las etiquetas). Hay dos configuraciones opcionales: format y separator. La configuración format especifica una cadena de plantilla donde @@{tag} (o @@ para abreviar) se reemplaza con el nombre de cada etiqueta. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes etiquetas.
/*!getstate:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{getstate[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera un dispatch condicional según el estado del lexer (requiere la opción --storable-state). Una lista opcional de nombres de bloque especifica qué bloques se incluirán en el dispatch de estado. La transición por defecto va a la etiqueta de inicio del primer bloque de la lista. Si la lista está vacía, se incluyen todos los bloques, y la transición por defecto va al primer bloque del archivo que tenga una etiqueta de inicio. Este tipo de bloque es incompatible con la opción --loop-switch, ya que requiere transiciones entre bloques que no se admiten sin goto o llamadas a funciones.
/*!conditions:re2c[:<nombre1>[:<nombre2>...]] ... */, /*!types:re2c... */ o %{conditions[:<nombre1>[:<nombre2>...]] ... %}, %{types... %}
Un bloque que genera una enumeración de condiciones (requiere la opción --conditions). Una lista opcional de nombres de bloque especifica qué bloques se incluirán al calcular el conjunto de condiciones (si la lista está vacía, se incluyen todas las condiciones). Por defecto, el código generado es una enumeración YYCONDTYPE. Se puede personalizar con las configuraciones opcionales format y separator. La configuración format especifica una cadena de plantilla donde @@{cond} (o @@ para abreviar) se reemplaza con el nombre de cada condición, y @@{num} se reemplaza con un índice numérico de esa condición. La configuración separator especifica una pieza de código utilizada para unir las piezas de format generadas para diferentes condiciones.
/*!include:re2c <archivo> */ o %{include <archivo> %}
Este bloque permite incluir <archivo>, que debe ser una ruta de archivo entre comillas dobles. El contenido del archivo se sustituye literalmente en lugar del bloque, de la misma manera que funciona #include en C/C++. Este bloque se puede usar junto con la opción --depfile para generar dependencias del sistema de compilación en los archivos incluidos.
/*!header:re2c:on*/ o %{header:on %}
Este bloque marca el inicio del archivo de cabecera. Todo lo que viene después y hasta el siguiente bloque header:off es procesado por re2py y escrito en el archivo de cabecera especificado con la opción -t --type-header.
/*!header:re2c:off*/ o %{header:off %}
Este bloque marca el final del archivo de cabecera iniciado con el bloque header:on*/.
/*!ignore:re2c ... */ o %{ignore ... %}
Un bloque cuyo contenido se ignora y se elimina del archivo de salida.

Configuraciones

Aquí hay una lista completa de las configuraciones admitidas por re2py:

re2c:api, re2c:input
Igual que la opción --api.
re2c:api:sigil
Especifica el marcador ("sigilo") que se utiliza para los marcadores de posición de argumentos en las primitivas de la API. El valor predeterminado es @@. Un marcador de posición comienza con el sigilo seguido del nombre del argumento entre llaves. Por ejemplo, si el sigilo se establece en $, entonces los marcadores de posición tendrán el formato ${nombre}. Las API de un solo argumento pueden usar notación abreviada sin el nombre entre llaves. Esta opción puede ser anulada por opciones para primitivas de API individuales, por ejemplo, re2c:YYFILL@len para YYFILL.
re2c:api:style
Especifica el estilo de la API. Los valores posibles son functions (el valor predeterminado para C) y free-form (el valor predeterminado para Go y Rust). En el estilo functions, las primitivas de la API se generan con una lista de argumentos entre paréntesis después del nombre de la primitiva. Los argumentos se proporcionan solo para parámetros autogenerados (como el número de caracteres pasados a YYFILL), pero no para el contexto general del lexer, por lo que las primitivas se comportan más como macros en C/C++ o cierres en Go y Rust. En el estilo free-form, las primitivas de la API no tienen una forma fija: deben definirse como cadenas que contienen piezas de código de formato libre con variables interpoladas de la forma @@{var} o @@ (corresponden a argumentos en estilo similar a funciones). Esta configuración puede ser anulada para primitivas de API individuales, ver por ejemplo la configuración re2c:YYFILL:naked para YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Igual que la opción --bit-vectors, pero se puede configurar por bloques.
re2c:captures, re2c:leftmost-captures
Igual que la opción --leftmost-captures, pero se puede configurar por bloques.
re2c:captvars, re2c:leftmost-captvars
Igual que la opción --leftmost-captvars, pero se puede configurar por bloques.
re2c:case-insensitive, re2c:flags:case-insensitive
Igual que la opción --case-insensitive, pero se puede configurar por bloques.
re2c:case-inverted, re2c:flags:case-inverted

re2c:case-ranges, re2c:flags:case-ranges

re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g

re2c:computed-gotos:relative, re2c:cgoto:relative

re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si se utiliza goto calculado, esta configuración especifica el umbral de complejidad que activa la generación de tablas de saltos en lugar de sentencias if anidadas y mapas de bits. El valor predeterminado es 9.
re2c:cond:abort
Si se establece en un valor entero positivo, el caso predeterminado en el dispatch de condiciones generado aborta la ejecución del programa.
re2c:cond:goto
Especifica una pieza de código utilizada para las reglas de acceso directo autogeneradas :=> en las condiciones. El valor predeterminado es goto @@;. El marcador de posición @@ se sustituye con el nombre de la condición (ver configuraciones re2c:api:sigil y re2c:cond:goto@cond).
re2c:cond:goto@cond
Especifica el sigilo utilizado para la sustitución de argumentos en la definición de re2c:cond:goto. El valor predeterminado es @@. Anula la configuración más genérica re2c:api:sigil.
re2c:cond:divider
Define el divisor para los bloques de condiciones. El valor predeterminado es /* *********************************** */. Los marcadores de posición se sustituyen con el nombre de la condición (ver re2c:api;sigil y re2c:cond:divider@cond).
re2c:cond:divider@cond
Especifica el sigilo utilizado para la sustitución de argumentos en la definición de re2c:cond:divider. El valor predeterminado es @@. Anula la configuración más genérica re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Especifica el prefijo utilizado para las etiquetas de condición. El valor predeterminado es yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Especifica el prefijo utilizado para los identificadores de condición. El valor predeterminado es yyc.

re2c:eof
Especifica el símbolo centinela utilizado con la regla de fin de entrada $. El valor predeterminado es -1 (la regla $ no se utiliza). Otros valores posibles incluyen todas las unidades de código válidas. Solo se reconocen números decimales.
re2c:header, re2c:flags:type-header, re2c:flags:t
Especifica el nombre del archivo de cabecera generado en relación con el directorio del archivo de salida. Igual que la opción --header, excepto que la ruta del archivo es relativa.
re2c:indent:string
Especifica la cadena utilizada para la indentación. El valor predeterminado es un solo carácter de tabulación "\t". La cadena de indentación debe contener solo caracteres de espacio en blanco. Para deshabilitar la indentación por completo, establezca esta configuración en una cadena vacía.
re2c:indent:top
Especifica la cantidad mínima de indentación a utilizar. El valor predeterminado es cero. El valor debe ser un número entero no negativo.
re2c:invert-captures
Igual que la opción --invert-captures, pero se puede configurar por bloques.
re2c:label:prefix, re2c:labelprefix
Especifica el prefijo utilizado para las etiquetas de los estados DFA. El valor predeterminado es yy.
re2c:label:start, re2c:startlabel
Controla la generación de una etiqueta de inicio de bloque. El valor predeterminado es cero, lo que significa que la etiqueta de inicio se genera solo si se utiliza. Un valor entero mayor que cero fuerza la generación de la etiqueta de inicio incluso si no es utilizada por el lexer. Un valor de cadena también fuerza la generación de la etiqueta de inicio y establece el nombre de la etiqueta a la cadena especificada. Esta configuración se aplica solo al bloque actual (se restablece al valor predeterminado para el siguiente bloque).
re2c:label:yyFillLabel
Especifica el prefijo de las etiquetas YYFILL utilizadas con re2c:eof y en el modo de estado almacenable.
re2c:label:yyloop
Especifica el nombre de la etiqueta que marca el inicio del bucle del lexer con la opción --loop-switch. El valor predeterminado es yyloop.
re2c:label:yyNext
Especifica el nombre de la etiqueta opcional que sigue al switch YYGETSTATE en el modo de estado almacenable (habilitado con re2c:state:nextlabel). El valor predeterminado es yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsoleto (ver la opción obsoleta --no-lookahead).
re2c:monadic
Si se establece en un valor distinto de cero, el lexer generado utilizará notación monádica (esta configuración es específica de Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Igual que la opción --nested-ifs, pero se puede configurar por bloques.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Igual que la opción --posix-captures, pero se puede configurar por bloques.
re2c:posix-captvars
Igual que la opción --posix-captvars, pero se puede configurar por bloques.
re2c:tags, re2c:flags:tags, re2c:flags:T
Igual que la opción --tags, pero se puede configurar por bloques.
re2c:tags:expression
Especifica la expresión utilizada para las variables de etiquetas. Por defecto, re2py genera expresiones de la forma yyt<N>. Esto puede ser inconveniente, por ejemplo, si las variables de etiquetas se definen como campos en una estructura. Todas las ocurrencias de @@{tag} o @@ se reemplazan con el nombre real de la etiqueta. Por ejemplo, re2c:tags:expression = "s.@@"; da como resultado expresiones de la forma s.yyt<N> en el código generado. Ver también la configuración re2c:api:sigil.
re2c:tags:negative
Especifica la expresión constante que se utiliza para el valor negativo de la etiqueta (típicamente sería -1 si las etiquetas son desplazamientos enteros en la cadena de entrada, o un puntero nulo si son punteros).
re2c:tags:prefix
Especifica el prefijo para los nombres de las variables de etiquetas. El valor predeterminado es yyt.
re2c:sentinel
Especifica el símbolo centinela utilizado para las comprobaciones de fin de entrada (cuando las comprobaciones de límites se deshabilitan con re2c:yyfill:enable = 0; y no se establece re2c:eof). Esta configuración no afecta la generación de código: su propósito es verificar que el centinela no está permitido en medio de una regla y asegurar que el lexer no leerá más allá del final del búfer. El valor predeterminado es -1` (en ese caso, re2py asume que el centinela es cero, que es el caso más común). Solo se reconocen números decimales.
re2c:state:abort
Si se establece en un valor entero positivo, el caso predeterminado en la despachación de estados generada aborta la ejecución del programa, y un caso explícito de -1 contiene una transición al inicio del bloque.
re2c:state:nextlabel
Controla si el switch YYGETSTATE va seguido de una etiqueta yyNext (el valor predeterminado es cero, lo que corresponde a ninguna etiqueta). Alternativamente, se puede usar re2c:label:start para generar una etiqueta de inicio específica, o un bloque getstate explícito para generar el switch YYGETSTATE por separado del bloque lexer.
re2c:unsafe, re2c:flags:unsafe
Igual que la opción --no-unsafe, pero se puede configurar por bloques. Si se establece en cero, suprime la generación de wrappers unsafe alrededor de YYPEEK. El valor predeterminado es distinto de cero (se generan wrappers). Esta configuración es específica de Rust.

Regular expressions

SYNTAX

re2py uses the following syntax for regular expressions:

"foo"
Case-sensitive string literal.
'foo'
Case-insensitive string literal.
[a-xyz], [^a-xyz]
Character class (possibly negated).
.
Any character except newline.
R \ S
Difference of character classes R and S.
R*
Zero or more occurrences of R.
R+
One or more occurrences of R.
R?
Optional R.
R{n}
Repetition of R exactly n times.
R{n,}
Repetition of R at least n times.
R{n,m}
Repetition of R from n to m times.
(R)
Just R; parentheses are used to override precedence. If submatch extraction is enabled, (R) is a capturing or a non-capturing group depending on --invert-captures option.
(!R)
If submatch extraction is enabled, (!R) is a non-capturing or a capturing group depending on --invert-captures option.
R S
Concatenation: R followed by S.
R | S
Alternative: R or S.
R / S
Lookahead: R followed by S, but S is not consumed.
name
Regular expression defined as name (or literal string "name" in Flex compatibility mode).
{name}
Regular expression defined as name in Flex compatibility mode.
@stag
An s-tag: saves the last input position at which @stag matches in a variable named stag.
#mtag
An m-tag: saves all input positions at which #mtag matches in a variable named mtag.

Character classes and string literals may contain the following escape sequences: \a, \b, \f, \n, \r, \t, \v, \\, octal escapes \ooo and hexadecimal escapes \xhh, \uhhhh and \Uhhhhhhhh.

Actions

Here is a list of predefined actions supported by re2py:

!entry code
Entry action binds a user-defined block of code to the start state of the current finite state machine. If start conditions are used, the entry action can be set individually for each condition. This action may be used to perform initialization, e.g. to save start location of a lexeme.
!pre_rule code
Pre-rule action prepends a user-defined block of code to semantic actions of all rules in the current block (or condition, if start conditions are used). This action may be used to factor out the common part of all semantic actions (e.g. saving the end location of a lexeme).
!post_rule code
Post-rule action appends a user-defined block of code to semantic actions of all rules in the current block (or condition, if start conditions are used). This action may be used to emit trap statements that guard against unintended control flow.

Directives

Here is a full list of directives supported by re2py:

!use:name ;
An in-block use directive that merges a previously defined rules block with the specified name into the current block. Named definitions, configurations and rules of the referenced block are added to the current ones. Conflicts between overlapping rules and configurations are resolved in the usual way: the first rule takes priority, and the latest configuration overrides the preceding ones. One exception is the special rules *, $ and <!> for which a block-local definition always takes priority. A use directive can be placed anywhere inside of a block, and multiple use directives are allowed.
!include file ;
This directive is the same as include block: it inserts file contents verbatim in place of the directive.

Program interface

The generated code interfaces with the outer program with the help of primitives, collectively referred to as the API. Which primitives should be defined for a particular program depends on multiple factors, including the complexity of regular expressions, input representation, buffering and the use of various features. All the necessary primitives should be defined by the user in the form of macros, functions, variables or any other suitable form that makes the generated code syntactically and semantically correct. re2py does not (and cannot) check the definitions, so if anything is missing or defined incorrectly, the generated program may have compile-time or run-time errors. This manual provides examples of API definitions in the most common cases.

re2py has three API flavors that define the core set of primitives used by a program:

Simple API
This is the default API for the Python backend. It consists of the following primitives: YYINPUT (which should be defined as a sequence of code units, e.g. a string) and YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (which should be defined as indices in YYINPUT).
Record API
Record API is useful in cases when lexer state must be stored in a class. It is enabled with --api record option or re2c:api = record configuration. This API consists of a variable yyrecord (the name can be overridden with re2c:yyrecord) that should be defined as a class with attributes yyinput, yycursor, yymarker, yyctxmarker, yylimit (only the fields used by the generated code need to be defined, and their names can be configured).
Generic API
This is the most flexible API. It is enabled with --api generic option or re2c:api = generic configuration. It contains primitives for generic operations: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Here is a full list of API primitives that may be used by the generated code in order to interface with the outer program.

YYCTYPE
The type of the input characters (code units). For ASCII, EBCDIC and UTF-8 encodings it should be 1-byte unsigned integer. For UTF-16 or UCS-2 it should be 2-byte unsigned integer. For UTF-32 it should be 4-byte unsigned integer.
YYCURSOR
An l-value that stores the current input position (a pointer or an integer offset in YYINPUT). Initially YYCURSOR should point to the first input character, and later it is advanced by the generated code. When a rule matches, YYCURSOR position is the one after the last matched character.
YYLIMIT
An r-value that stores the end of input position (a pointer or an integer offset in YYINPUT). Initially YYLIMIT should point to the position after the last available input character. It is not changed by the generated code. The lexer compares YYCURSOR to YYLIMIT in order to determine if there are enough input characters left.
YYMARKER
An l-value that stores the position of the latest matched rule (a pointer or an integer offset in YYINPUT). It is used to restore the YYCURSOR position if the longer match fails and the lexer needs to rollback. Initialization is not needed.
YYCTXMARKER
An l-value that stores the position of the trailing context (a pointer or an integer offset in YYINPUT). No initialization is needed. YYCTXMARKER is needed only if the lookahead operator / is used.
YYFILL
A generic API primitive with one variable len. YYFILL should provide at least len more input characters or fail. If re2c:eof is used, then len is always 1 and YYFILL should always return to the calling function; zero return value indicates success. If re2c:eof is not used, then YYFILL return value is ignored and it should not return on failure. The maximum value of len is YYMAXFILL.
YYFN
A primitive that defines function prototype in --recursive-functions code model. Its value should be an array of one or more strings, where each string contains two or three components separated by the string specified in re2c:fn:sep configuration (typically a semicolon). The first array element defines function name and return type (empty for a void function). Subsequent elements define function arguments: first, the expression for the argument used in function body (usually just a name); second, argument type; third, an optional formal parameter (it defaults to the first component - usually both the argument and the parameter are the same identifier).
YYINPUT
An l-value that holds the input buffer. It can be a pointer to the beginning of the buffer or an integer offset, depending on the API flavor and target language. For the Simple API, it is usually a string or a byte array. For other APIs, it might be part of a larger structure like a file handle or a stream.
YYINPUT
Un valor r que almacena la secuencia de entrada actual (cadena, buffer, etc.).
YYMAXFILL
Una constante integral igual al valor máximo del argumento de YYFILL. Se puede generar con un bloque max.
YYLESSTHAN
Un primitivo de API genérico con una variable len. Debe definirse como un valor r de tipo booleano que sea igual a true si y solo si quedan menos de len caracteres de entrada.
YYPEEK
Un primitivo de API genérico sin variables. Debe definirse como un valor r de tipo YYCTYPE que sea igual al carácter en la posición de entrada actual.
YYSKIP
Un primitivo de API genérico que debe avanzar la posición de entrada actual en una unidad de código.
YYBACKUP
Un primitivo de API genérico que debe guardar la posición de entrada actual (para ser restaurada con YYRESTORE más tarde).
YYRESTORE
Un primitivo de API genérico que debe restaurar la posición de entrada actual al valor guardado por YYBACKUP.
YYBACKUPCTX
Un primitivo de API genérico que debe guardar la posición de entrada actual como la posición del contexto de cola (para ser restaurada con YYRESTORECTX más tarde).
YYRESTORECTX
Un primitivo de API genérico que debe restaurar la posición del contexto de cola guardada con YYBACKUPCTX.
YYRESTORETAG
Un primitivo de API genérico con una variable tag que debe restaurar la posición del contexto de cola al valor de tag.
YYSTAGP
Un primitivo de API genérico con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para más detalles). YYSTAGP debe establecer tag a la posición de entrada actual.
YYSTAGN
Un primitivo de API genérico con una variable tag, donde tag puede ser un puntero o un desplazamiento en YYINPUT (ver sección de extracción de subcoincidencias para más detalles). YYSTAGN debe establecer tag a un valor que represente una posición de entrada inexistente.
YYMTAGP
Un primitivo de API genérico con una variable tag. YYMTAGP debe añadir la posición actual al historial de subcoincidencias de tag (ver la sección de extracción de subcoincidencias para más detalles).
YYMTAGN
Un primitivo de API genérico con una variable tag. YYMTAGN debe añadir un valor que represente una posición de entrada inexistente al historial de subcoincidencias de tag (ver la sección de extracción de subcoincidencias para más detalles).
YYSHIFT

YYCOPYSTAG

YYSHIFTSTAG

YYSHIFTMTAG

YYMAXNMATCH

YYCONDTYPE

YYSETCOND
Un primitivo con una variable cond que debe establecer el identificador de condición actual a cond.
YYGETSTATE
Un valor r de tipo entero que es igual al estado actual del lexer. Debe inicializarse a -1.
YYSETSTATE
Un primitivo con una variable state que debe establecer el estado actual del lexer a state.
YYDEBUG
Este primitivo solo se genera con la opción -d, --debug-output. Su propósito es agregar registro al código generado (la definición típica de YYDEBUG es una sentencia print). Las sentencias YYDEBUG se generan en cada estado y tienen dos variables: state (un índice de estado DFA o -1) y symbol (el símbolo de entrada actual).
yyaccept
Un valor l de tipo integral sin signo que almacena el número de la última regla coincidente. La definición del usuario solo es necesaria con la opción --storable-state.
yybm
Una tabla que contiene mapas de bits comprimidos para hasta 8 transiciones (se usa con la opción --bitmaps). La tabla contiene 256 elementos y se indexa por unidades de código de 1 byte. Cada elemento de 8 bits combina valores booleanos para hasta 8 transiciones. El k-ésimo bit del n-ésimo elemento es verdadero si y solo si la n-ésima unidad de código está en el rango de la k-ésima transición. La idea de este mapa de bits es reemplazar muchas ramas if o casos switch con una sola comprobación de un solo bit en la tabla.
yych
Un valor l de tipo YYCTYPE que almacena el carácter de entrada actual. La definición del usuario solo es necesaria con la opción -f --storable-state.
yyctable
Tabla de saltos generada para la distribución inicial de condiciones (activada con la combinación de las opciones --conditions y --computed-gotos).
yyfill
Un valor l que almacena el resultado de la llamada a YYFILL (esto puede ser necesario para lenguajes puramente funcionales, donde YYFILL es una función monádica con un valor de retorno complejo).
yynmatch
Un valor l de tipo integral sin signo que almacena el número de grupos de captura POSIX en la regla coincidente. Se usa solo con la opción -P --posix-captures.
yypmatch
Una matriz de valores l que se utilizan para mantener los valores de etiqueta correspondientes a los paréntesis de captura en la regla coincidente. La longitud de la matriz debe ser al menos yynmatch * 2 (generalmente YYMAXNMATCH * 2 es una buena opción). Se usa solo con la opción -P --posix-captures.
yystable
Obsoleto.
yystate
Un valor l que se usa con la opción --loop-switch para almacenar el estado actual del DFA.
yytarget
Tabla de saltos que contiene destinos de saltos (direcciones de etiquetas) para todas las transiciones desde un estado. Esta tabla es local a cada estado. La generación de tablas yytarget se habilita con la opción --computed-gotos.

La opción record debe usarse cuando el estado del lexer necesita almacenarse en un registro (struct, clase, etc.). La opción generic debe usarse en casos complejos cuando las otras dos APIs no son lo suficientemente flexibles.

Colapsa casos consecutivos en sentencias switch en un rango de la forma bajo ... alto. Esta sintaxis es una extensión del lenguaje C/C++ que es soportada por compiladores como GCC, Clang y Tcc. La principal ventaja sobre el uso de casos individuales es un código generado más pequeño y un tiempo de generación más rápido, aunque para algunos compiladores como Tcc también resulta en un tamaño de binario más pequeño.

Esta opción depende de la opción --output.
--ebcdic --ecb -e
Genera un analizador léxico que lee la entrada en codificación EBCDIC. re2py asume que el rango de caracteres es 0 -- 0xFF y el tamaño del carácter es de 1 byte.

Define la forma en que re2py trata las clases de caracteres vacías. Con match-empty (el valor predeterminado) la clase vacía coincide con la entrada vacía (lo cual es ilógico, pero compatible con versiones anteriores). Con match-none la clase vacía siempre falla al coincidir. Con error la clase vacía genera un error de compilación.
--encoding-policy <fail | substitute | ignore>
Define la forma en que re2py trata los sustitutos Unicode. Con fail re2py se aborta con un error cuando se encuentra un sustituto. Con substitute re2py reemplaza silenciosamente los sustitutos con el punto de código de error 0xFFFD. Con ignore (el valor predeterminado) re2py trata los sustitutos como puntos de código normales. El estándar Unicode dice que los sustitutos independientes son inválidos, pero las bibliotecas y programas del mundo real se comportan de diferentes maneras.

Soporte parcial para sintaxis Flex: en este modo, las definiciones nombradas no necesitan el signo igual ni el punto y coma de terminación, y cuando se usan deben estar rodeadas por llaves. Los nombres sin llaves se tratan como cadenas entre comillas dobles.
--goto-label
Usa el modelo de código "goto/label": codifica el DFA en forma de bloques de código etiquetados conectados con transiciones goto entre bloques. Esto solo se soporta para lenguajes que tienen una sentencia goto.

Agrega PATH a la lista de ubicaciones que se utilizan al buscar archivos de inclusión. Esta opción es útil en combinación con el bloque o directiva include. re2py busca FILE en el directorio del archivo padre y en las ubicaciones de inclusión especificadas con la opción -I.
--input <default | custom>
Alias obsoleto para --api. La opción default corresponde a simple (es de hecho el valor predeterminado para la mayoría de los backends, pero no para todos). La opción custom corresponde a generic.
--input-encoding <ascii | utf8>
Especifica la forma en que re2py analiza las expresiones regulares. Con ascii (el valor predeterminado) re2py maneja la entrada como codificada en ASCII: cualquier secuencia de unidades de código es una secuencia de caracteres independientes de 1 byte. Con utf8 re2py maneja la entrada como codificada en UTF8 y reconoce caracteres multibyte.
--invert-captures
Invierte el significado de los grupos de captura y no captura. Por defecto (...) es de captura y (! ...) no es de captura. Con esta opción (! ...) es de captura y (...) no es de captura.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>

Los lenguajes soportados son C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (se pueden agregar más lenguajes a través de archivos de sintaxis definidos por el usuario, consulte la opción --syntax). Especifica el formato de ubicación en los mensajes. Con gnu las ubicaciones se imprimen como 'nombre_archivo:línea:columna: ...'. Con msvc las ubicaciones se imprimen como 'nombre_archivo(línea,columna) ...'. El valor predeterminado es gnu.

El estado se almacena en una variable yystate. Las transiciones entre estados actualizan yystate a la etiqueta del caso del estado de destino y continúan la ejecución hasta el inicio del bucle.

Aplica operaciones de registro a las transiciones entrantes en lugar de a las salientes. Las pruebas comparativas demostraron que el algoritmo TDFA(0) es menos eficiente que TDFA(1).

Opción interna: especifica el algoritmo utilizado para calcular la tabla de precedencia POSIX. El algoritmo complex calcula la tabla de precedencia en una sola travesía del árbol de historial de etiquetas y tiene una complejidad cuadrática en el número de estados TNFA; es el predeterminado. El algoritmo naive tiene una complejidad cúbica en el peor de los casos en el número de estados TNFA, pero es mucho más simple que complex y puede ser un poco más rápido en casos no patológicos.

Opción interna, obsoleta. Solía habilitar el algoritmo staDFA, que difiere de TDFA en que las operaciones de registro se colocan en los estados en lugar de en las transiciones. Las pruebas comparativas demostraron que el algoritmo staDFA es menos eficiente que TDFA.
--fixed-tags <none | toplevel | all>
Opción interna: especifica si la optimización de etiquetas fijas debe aplicarse a todas las etiquetas (all), a ninguna de ellas (none), o solo a las de la concatenación de nivel superior (toplevel). El valor predeterminado es all. Las etiquetas "fijas" son aquellas que se encuentran a una distancia fija de alguna otra etiqueta (llamada "base"). En tales casos, solo la etiqueta base necesita ser rastreada, y el valor de la etiqueta fija se puede calcular como el valor de la etiqueta base más un desplazamiento estático. Para las etiquetas que están bajo alternativa o repetición, también es necesario verificar si la etiqueta base tiene un valor de no coincidencia (en ese caso, la etiqueta fija también debe establecerse en no coincidencia, sin tener en cuenta el desplazamiento). Para las etiquetas en la concatenación de nivel superior, no es necesario realizar la comprobación, ya que siempre coinciden.

Command-line options

A full list of re2c command-line options follows.

-Wconflicting-rules
Warn about rules that match the same input strings. This warning is an error if re2c:conflicting-rules configuration is used. By default, re2c selects the first rule in the list that matches the input. This may lead to unexpected behavior if rules are not ordered correctly.
-Wempty-rules
Warn about rules that match an empty string. Such rules are always expanded and consume a single code unit, but they do not advance the scanner position. This may lead to infinite loops in generated lexer. This warning is an error if re2c:empty-rules configuration is used.
-Wmatch-empty-rules
Warn about rules that match an empty string. Unlike -Wempty-rules, these rules may advance the scanner position and may be potentially useful. This warning is an error if re2c:match-empty-rules configuration is used.
-Wredundant-rules
Warn about rules that are shadowed by other rules and will never match.
-Wunreachable-rules
Warn about rules that are shadowed by other rules and will never match.
-Wdeprecated-eof_rule
Warn about standalone end of input rules $ that will be broken by the future changes and require fixing. At the moment these rules take precedence when conflicting with other rules, but after the introduction of generalized end of input symbol $ precedence order will change and these rules will become shadowed by other rules.
-Wuseless-escape
Warn if a symbol is escaped when it shouldn't be. By default, re2py silently ignores such escapes, but this may as well indicate a typo or an error in the escape sequence.
-Wnondeterministic-tags
Warn if a tag has n-th degree of nondeterminism, where n is greater than 1.
-Wsentinel-in-midrule
Warn if the sentinel symbol occurs in the middle of a rule --- this may cause reads past the end of buffer, crashes or memory corruption in the generated lexer. This warning is only applicable if the sentinel method of checking for the end of input is used. It is set to an error if re2c:sentinel configuration is used.
-Wundefined-syntax-config
Warn if the syntax file specified with --syntax option is missing definitions of some configurations. This helps to maintain user-defined syntax files: if a new release adds configurations, old syntax file will raise a warning, and the user will be notified. If some configurations are unused and do not need a definition, they should be explicitly set to <undefined>.

Syntax files

Support for different languages in re2c is based on the idea of syntax files. A syntax file is a configuration file that defines syntax of the target language -- not the whole language, but a small part of it that is used by the generated code. Syntax files make re2c very flexible, but they should not be used as a replacement for re2c: configurations: their purpose is to define syntax of the target language, not to customize one particular lexer. All supported languages have default syntax files that are part of the distribution (see include/syntax subdirectory); they are also embedded in the re2py binary. Users may provide a custom syntax file that overrides a few configurations for one of supported languages, or they may choose to redefine all configurations (in that case --lang none option should be used). Syntax files contain configurations of four different kinds: feature lists, language configurations, inplace configurations and code templates.

Feature lists

A few list configurations define various features supported by a given backend, so that re2py may give a clear error if the user tries to enable an unsupported feature:
supported_apis
A list of supported APIs with possible elements simple, record, generic.
supported_api_styles
A list of supported API styles with possible elements functions, free-form.
supported_code_models
A list of supported code models with possible elements goto-label, loop-switch, recursive-functions.
supported_targets
A list of supported codegen targets with possible elements code, dot, skeleton.
supported_features
A list of supported features with possible elements nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Language configurations

A few boolean configurations describe features of the target language that affect re2py parser and code generator:
semicolons
Non-zero if the language uses semicolons after statements.
backtick_quoted_strings
Non-zero if the language has backtick-quoted strings.
single_quoted_strings
Non-zero if the language has single-quoted strings.
indentation_sensitive
Non-zero if the language is indentation sensitive.
wrap_blocks_in_braces
Non-zero if compound statements must be wrapped in curly braces.

Inplace configurations

Syntax files define initial values of all re2c: configurations, as they may differ for different languages. See configurations section for a full list of all inplace configurations and their meaning.

Code templates

Code templates define syntax of the target language. They are written in a simple domain-specific language with the following formal grammar: 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

A code template is a sequence of string literals, variables, optional elements and lists, or a reference to another code template, or a special value <undefined>. Variables are placeholders that are substituted during code generation phase. List variables are special: when expanding list templates, re2py repeats expressions the right hand side of the column a few times, each time replacing occurrences of the list variable with a value specific to this repetition. Lists have optional bounds (negative values are counted from the end, e.g. -1 means the last element). Conditional names start with a dot. Both conditionals and variables may be either local (specific to the given code template) or global (allowed in all code templates). When re2py reads syntax file, it checks that each code template uses only the variables and conditionals that are allowed in it.

For example, the following code template defines if-then-else construct for a C-like language:

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Here branch is a list variable: branch{0} expands to the first branch (which is special, as there is no else part), branch{1:-1} expands to all remaining branches (if any). stmt is also a list variable: [stmt: stmt] is a nested list that expands to a list of statements in the body of the current branch. topindent, indent, dedent and nl are global variables, and .cond is a local conditional (their meaning is described below). This code template could produce the following code:

if x {
    // do something
} else if y {
    // do something else
} else {
    // don't do anything
}

MANEJO DEL FIN DE LA ENTRADA

Uno de los principales problemas para el lexer es saber cuándo detenerse. Existen algunas condiciones de terminación:

  • el lexer puede coincidir con alguna regla (incluida la regla por defecto *) y llegar a un estado final
  • el lexer puede fallar al coincidir con alguna regla y llegar a un estado por defecto
  • el lexer puede alcanzar el final de la entrada

Las dos primeras condiciones terminan el lexer de una manera "natural": llega a un estado sin transiciones salientes y la coincidencia se detiene automáticamente. La tercera condición, el final de la entrada, es diferente: puede ocurrir en cualquier estado y el lexer debe poder manejarlo. La comprobación del final de la entrada interrumpe el flujo normal del lexer y añade ramas condicionales al programa generado, por lo tanto, es necesario minimizar el número de tales comprobaciones. re2py soporta algunos métodos diferentes para manejar el final de la entrada. Cuál usar depende de la complejidad de las expresiones regulares, la necesidad de buffering, consideraciones de rendimiento y otros factores. Aquí hay una lista de métodos:

  • Centinela. Este método elimina la necesidad de comprobaciones del final de la entrada por completo. Es simple y eficiente, pero se limita al caso en que hay un carácter "centinela" natural que nunca puede ocurrir en una entrada válida. Este carácter aún puede ocurrir en una entrada no válida, pero no debe ser permitido por las expresiones regulares, excepto quizás como el último carácter de una regla. El centinela se añade al final de la entrada y sirve como señal de parada: cuando el lexer lee este carácter, es un error de sintaxis o el final de la entrada. En ambos casos, el lexer debe detenerse. Este método se utiliza si YYFILL está deshabilitado con re2c:yyfill:enable = 0; y re2c:eof tiene el valor por defecto -1.
  • Centinela con comprobaciones de límites. Este método es genérico: permite manejar cualquier entrada sin restricciones en las expresiones regulares. La idea es reducir el número de comprobaciones del final de la entrada realizándolas solo en ciertos caracteres. Similar al método "centinela", se elige uno de los caracteres como "centinela" y se añade al final de la entrada. Sin embargo, no hay restricciones sobre dónde puede ocurrir el centinela (de hecho, cualquier carácter puede ser elegido para un centinela). Cuando el lexer lee este carácter, realiza adicionalmente una comprobación de límites. Si la posición actual está dentro de los límites, el lexer reanuda la coincidencia y maneja el centinela como un carácter regular. De lo contrario, invoca YYFILL (a menos que esté deshabilitado). Si se suministra más entrada, el lexer volverá a coincidir con el último carácter y continuará como si el centinela no estuviera allí. De lo contrario, debe ser el final real de la entrada y el lexer se detiene. Este método se utiliza cuando re2c:eof tiene un valor no negativo (debe establecerse en el valor numérico del centinela). YYFILL es opcional.
  • Comprobaciones de límites con relleno. Este método es genérico y puede ser más rápido que el método "centinela con comprobaciones de límites", pero también es más complejo. La idea es particionar los estados del DFA en componentes fuertemente conectados (SCCs) y generar una sola comprobación por SCC para suficientes caracteres para cubrir el camino más largo sin bucles en esa SCC. Esto reduce el número de comprobaciones, pero hay un problema con lexemas cortos al final de la entrada, ya que la comprobación requiere suficientes caracteres para cubrir el lexema más largo. Esto se puede solucionar rellenando la entrada con algunos caracteres ficticios que no forman un sufijo de lexema válido (para que el lexer no pueda coincidirlos). La longitud del relleno debe ser YYMAXFILL, generado con un bloque max. Si no hay suficiente entrada, el lexer invoca YYFILL, que debe suministrar al menos el número requerido de caracteres o no regresar. Este método se utiliza si YYFILL está habilitado y re2c:eof es -1 (esta es la configuración por defecto).
  • Comprobaciones personalizadas. La API genérica permite anular operaciones básicas como la lectura de un carácter, lo que hace posible incluir las comprobaciones de fin de entrada como parte de ellas. Este enfoque es propenso a errores y debe usarse con precaución. Para usar un método personalizado, habilite la API genérica con --api custom o re2c:api = custom; y deshabilite las comprobaciones de límites por defecto con re2c:yyfill:enable = 0; o re2c:yyfill:check = 0;.

Centinela

Este ejemplo utiliza un carácter centinela para manejar el final de la entrada. El programa cuenta palabras separadas por espacios en una cadena terminada en nulo. El centinela es nulo: es el último carácter de cada cadena de entrada y no está permitido en el medio de un lexema por ninguna de las reglas (en particular, no está incluido en rangos de caracteres donde es fácil pasarlo por alto). Si un nulo ocurre en el medio de una cadena, es un error de sintaxis y el lexer coincidirá con la regla por defecto *, pero no leerá más allá del final de la entrada ni fallará (use la advertencia -Wsentinel-in-midrule y la configuración re2c:sentinel para verificar esto). La configuración re2c:yyfill:enable = 0; suprime la generación de comprobaciones de límites y las invocaciones de YYFILL.

# re2py $INPUT -o $OUTPUT
# espera una cadena terminada en nulo
def lex(yyinput):
    yycursor = 0
    count = 0
    while True: %{
        re2c:yyfill:enable = 0;
        re2c:indent:top = 2;
        *      { return -1 }
        [\x00] { return count }
        [ ]+   { break }
        [a-z]+ {
            count += 1
            break
        }
    %}

Centinela con comprobaciones de límites

Este ejemplo utiliza un centinela con comprobaciones de límites para manejar el final de la entrada (este método se añadió en la versión 1.2). El programa cuenta cadenas de comillas simples separadas por espacios. El carácter centinela es nulo, lo que se especifica con la configuración re2c:eof = 0;. Al igual que en el método centinela, el nulo es el último carácter de cada cadena de entrada, pero se permite en el medio de una regla (por ejemplo, 'aaa\0aa'\0 es una entrada válida, pero 'aaa\0 es un error de sintaxis). Se generan comprobaciones de límites en cada estado que coincide con un carácter de entrada, pero están limitadas a la rama que maneja el nulo. Las comprobaciones de límites tienen la forma YYLIMIT <= YYCURSOR o YYLESSTHAN(1) con la API genérica. Si la condición de comprobación es verdadera, el lexer ha alcanzado el final de la entrada y debe detenerse (YYFILL está deshabilitado con re2c:yyfill:enable = 0; ya que la entrada cabe en un solo búfer, vea la sección YYFILL con centinela para un ejemplo que utiliza YYFILL). Alcanzar el final de la entrada abre tres posibilidades: si el lexer está en el estado inicial, coincidirá con la regla de fin de entrada $, de lo contrario, puede retroceder a una regla previamente coincidente (incluida la regla por defecto *) o ir a un estado por defecto, causando -Wundefined-control-flow.

        re2c:eof = 0;
        re2c:indent:top = 2;

        $    { return count }
        [ ]+ { break }
        str  {
            count += 1
            break
        }
    %}
def test(str, count):
    # el nulo terminador no está incluido en `lim`

test(b"\0", 0);
test(b"'qu\0tes' 'are' 'fine: \\'' \0", 3);

Comprobaciones de límites con relleno

Este ejemplo utiliza comprobaciones de límites con relleno para manejar el final de la entrada (este método está habilitado por defecto). El programa cuenta cadenas de comillas simples separadas por espacios. Hay un relleno de YYMAXFILL caracteres nulos añadidos al final de la entrada, donde el valor de YYMAXFILL se autogenera con un bloque max. No es necesario usar nulo para el relleno --- se pueden usar caracteres siempre que no f

orm a valid lexeme suffix (in this example padding should not contain single quotes, as they may be mistaken for a suffix of a single-quoted string). There is a "stop" rule that matches the first padding character (null) and terminates the lexer (note that it checks if null is at the beginning of padding, otherwise it is a syntax error). Bounds checks are generated only in some states that are determined by the strongly connected components of the underlying automaton. Checks have the form (YYLIMIT - YYCURSOR) < n or YYLESSTHAN(n) with generic API, where n is the minimum number of characters that are needed for the lexer to proceed (it also means that the next bounds check will occur in at most n characters). If the check condition is true, the lexer has reached the end of input and will invoke YYFILL(n) that should either supply at least n input characters or not return. In this example YYFILL always fails and terminates the lexer with an error (which is fine because the input fits into one buffer). See the YYFILL with padding section for an example that refills the input buffer with YYFILL.

# re2py $INPUT -o $OUTPUT
%{max %}
def lex(yyinput):
    yycursor = 0
    yylimit = len(yyinput)
    count = 0
    while True: %{
        re2c:YYFILL = "return -1";
        re2c:indent:top = 2;
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            # check that it is the sentinel, not some unexpected null
            return count if yycursor == yylimit - YYMAXFILL + 1 else -1
        }
        str {
            count += 1
            break
        }
        [ ]+ { break }
        *    { return -1 }
    %}
def test(str, count):
    padded_str = str + (b"\0" * YYMAXFILL)
    assert lex(padded_str) == count
test(b"", 0)
test(b"'unterminated\\'", -1)
test(b"'qu\x00tes' 'are' 'fine: \\'' ", 3)
test(b"'unexpected \x00 null", -1)

This example uses a custom end-of-input handling method based on generic API. The program counts space-separated single-quoted strings.             break
        }

BUFFER REFILLING

The need for buffering arises when the input cannot be mapped in memory all at once: either it is too large, or it comes in a streaming fashion (like reading from a socket). The usual technique in such cases is to allocate a fixed-sized memory buffer and process input in chunks that fit into the buffer. When the current chunk is processed, it is moved out and new data is moved in. In practice it is somewhat more complex, because lexer state consists not of a single input position, but a set of interrelated positions:

  • cursor: the next input character to be read (YYCURSOR in C pointer API or YYSKIP/YYPEEK in generic API)
  • limit: the position after the last available input character (YYLIMIT in C pointer API, implicitly handled by YYLESSTHAN in generic API)
  • marker: the position of the most recent match, if any (YYMARKER in default API or YYBACKUP/YYRESTORE in generic API)
  • token: the start of the current lexeme (implicit in re2py API, as it is not needed for the normal lexer operation and can be defined and updated by the user)
  • context marker: the position of the trailing context (YYCTXMARKER in C pointer API or YYBACKUPCTX/YYRESTORECTX in generic API)
  • tag variables: submatch positions (defined with stags and mtags blocks and generic API primitives YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Not all these are used in every case, but if used, they must be updated by YYFILL. All active positions are contained in the segment between token and cursor, therefore everything between buffer start and token can be discarded, the segment from token and up to limit should be moved to the beginning of buffer, and the free space at the end of buffer should be filled with new data. In order to avoid frequent YYFILL calls it is best to fill in as many input characters as possible (even though fewer characters might suffice to resume the lexer). The details of YYFILL implementation are slightly different depending on which EOF handling method is used: the case of EOF rule is somewhat simpler than the case of bounds-checking with padding. Also note that if -f --storable-state option is used, YYFILL has slightly different semantics (described in the section about storable state).

YYFILL with sentinel

If EOF rule is used, YYFILL is a function-like primitive that accepts no arguments and returns a value which is checked against zero. YYFILL invocation is triggered by condition YYLIMIT <= YYCURSOR in C pointer API and YYLESSTHAN() in generic API. A non-zero return value means that YYFILL has failed. A successful YYFILL call must supply at least one character and adjust input positions accordingly. Limit must always be set to one after the last input position in buffer, and the character at the limit position must be the sentinel symbol specified by re2c:eof configuration. # re2py $INPUT -o $OUTPUT
from enum import Enum
import os
BUFSIZE = 4096
class State:
    def __init__(self, fname):
        self.file = open(fname, "rb")
        self.yyinput = bytearray(BUFSIZE)
        self.yylimit = BUFSIZE - 1 # exclude terminating null
        self.yycursor = self.yylimit
        self.yymarker = self.yylimit
        self.token = self.yylimit
        self.eof = False
    def __del__(self):
        self.file.close()
class Status(Enum):
    OK = 0
    EOF = 1
    LONG_LEXEME = 2
def fill(st):
    if st.eof:
        return Status.EOF
    # Error: lexeme too long. In real life could reallocate a larger buffer.
    if st.token < 1:
        return Status.LONG_LEXEME
    # Shift buffer contents (discard everything up to the current token).
    st.yyinput = st.yyinput[st.token:st.yylimit]
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    # Fill free space at the end of buffer with new data from file.
    bytes = st.file.read(BUFSIZE - st.yylimit - 1) # -1 for sentinel
    if not bytes:
        st.eof = True # end of file
    else:
        st.yylimit += len(bytes);
        st.yyinput += bytes
    st.yyinput += b'\0' # append sentinel
    return Status.OK
def lex(yyrecord, count):
    while True:
        yyrecord.token = yyrecord.yycursor
    %{
        re2c:api = record;
        re2c:define:YYFILL = "fill(yyrecord) == Status.OK";
        re2c:eof = 0;
        re2c:indent:top = 2;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1 }
        $    { return count }
        [ ]+ { break }
        str  {
            count += 1
            break
        }
    %}
def main():
    fname = "input"
    # Prepare input file.
    f = open(fname, "w")
    for i in range(BUFSIZE):
        f.write("'qu\0tes' 'are' 'fine: \\'' ")
    f.close()
    # Run lexer on the prepared file.
    st = State(fname)
    assert lex(st, 0) == 3 * BUFSIZE
    # Cleanup.
    os.remove(fname)
if __name__ == '__main__':
    main()

Estado almacenable

Con la opción --storable-state re2py genera un lexer que puede almacenar su estado actual, retornar al llamador y luego reanudar las operaciones exactamente donde lo dejó. El modo de operación por defecto en re2py es un modelo de "pull" (tirar), en el que el lexer "tira" de más entrada cuando la necesita. Esto puede ser inaceptable en casos donde la entrada se vuelve disponible poco a poco (por ejemplo, si el lexer es invocado por el parser, o si el programa lexer se comunica a través de un protocolo de socket con algún otro programa que debe esperar una respuesta del lexer antes de transmitir el siguiente mensaje). La característica de estado almacenable está destinada precisamente a tales casos: permite generar lexers que trabajan en un modelo de "push" (empujar). Cuando el lexer necesita más entrada, almacena su estado y retorna al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el lexer exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo de "pull":

  • Definir las primitivas YYSETSTATE() y YYGETSTATE(state).
  • Definir las variables yych, yyaccept (si se usan) y state como parte del estado persistente del lexer. La variable state debe inicializarse a -1.
  • YYFILL debe retornar al programa externo en lugar de intentar proporcionar más entrada. El código de retorno debe indicar que el lexer necesita más entrada.
  • El programa externo debe reconocer las situaciones en las que el lexer necesita más entrada y responder apropiadamente.
  • Opcionalmente, usar el bloque getstate para generar el switch YYGETSTATE separado del lexer principal. Esto solo funciona para lenguajes que tienen goto (no en modo --loop-switch).
  • Usar re2c:eof y el método de la centinela con comprobaciones de límites para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo añadir relleno: el final actual de la entrada puede no ser el final definitivo de la entrada, y añadir relleno demasiado pronto puede cortar un lexema codicioso leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del buffer (que ya está bloqueado debido a la condición de fin de entrada).

Aquí hay un ejemplo de un lexer modelo "push" que simula la lectura de paquetes desde un socket. El lexer bucea hasta que encuentra el final de la entrada y retorna a la función llamadora. La función llamadora proporciona más entrada "enviando" el siguiente paquete y reanuda la lexia. Este proceso se detiene cuando se han enviado todos los paquetes o cuando hay un error.

from enum import Enum
import os
# Usar un buffer pequeño para cubrir el caso en que un lexema no encaja.
# En la vida real, usar un buffer más grande.
BUFSIZE = 10
DEBUG = False
class State:
    def __init__(self, file):
        self.file = file
        self.yyinput = bytearray(BUFSIZE)
        self.yylimit = BUFSIZE - 1 # excluir el nulo terminador
        self.yycursor = self.yylimit
        self.yymarker = self.yylimit
        self.token = self.yylimit
        self.yystate = -1
class Status(Enum):
    END = 0
    READY = 1
    WAITING = 2
    BIG_PACKET = 3
    BAD_PACKET = 4
def fill(st):
    # Error: lexema demasiado largo. En la vida real, se podría reasignar un buffer más grande.
    if st.token < 1:
        return Status.BIG_PACKET
    # Desplaza el contenido del buffer (descarta todo hasta el token actual).
    st.yyinput = st.yyinput[st.token:st.yylimit]
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    # Rellena el espacio libre al final del buffer con nuevos datos del archivo.
    bytes = st.file.read(BUFSIZE - st.yylimit - 1) # -1 para la centinela
    if bytes:
        st.yylimit += len(bytes);
        st.yyinput += bytes
    st.yyinput += b'\0' # añade la centinela
    return Status.READY
def lex(yyrecord, recv):
    while True:
        yyrecord.token = yyrecord.yycursor
    %{
        re2c:api = record;
        re2c:YYFILL = "return Status.WAITING, recv";
        re2c:eof = 0;
        re2c:indent:top = 2;
        packet = [a-z]+[;];
        *      { return Status.BAD_PACKET, recv }
        $      { return Status.END, recv }
        packet {
            recv += 1
            break
        }
    %}
def test(packets, expect):
    # Crea una tubería (abre el mismo archivo para leer y escribir).
    fname = "pipe"
    fw = open(fname, "wb")
    fr = open(fname, "rb")
    # Inicializa el estado del lexer
    st = State(fr)
    # Bucle principal. El buffer contiene datos incompletos que aparecen paquete por
    # paquete. Cuando el lexer necesita más entrada, guarda su estado interno y
    # retorna al llamador, que debe proporcionar más entrada y reanudar la lexia.
    send = 0
    recv = 0
    while True:
        status, recv = lex(st, recv)
        if status == Status.END:
            if DEBUG: print("terminado: se recibieron {} paquetes".format(recv))
            break
        elif status == Status.WAITING:
            if DEBUG: print("esperando...");
            if send < len(packets):
                if DEBUG: print("se envió paquete {}: {}".format(send, packets[send]))
                fw.write(packets[send])
                fw.flush()
                send += 1
            status = fill(st)
            if DEBUG: print("cola: '{}', estado: {}".format(st.yyinput, status))
            if status == Status.BIG_PACKET:
                if DEBUG: print("error: paquete demasiado grande")
                break
            assert status == Status.READY
        else:
            assert status == Status.BAD_PACKET
            if DEBUG: print("error: paquete mal formado")
            break
    # Comprueba los resultados.
    assert status == expect
    if status == Status.END:
        assert recv == send
    # Limpieza: elimina el archivo de entrada.
    fr.close()
    fw.close()
    os.remove(fname)
def main():
    test([], Status.END)
    test([b"zero;", b"one;", b"two;", b"three;", b"four;"], Status.END)
    test([b"zer0;"], Status.BAD_PACKET)
    test([b"goooooooooogle;"], Status.BIG_PACKET)

    main()

Bloques reutilizables

Los bloques reutilizables de la forma /*!rules:re2c[:<name>] ... */ o %{rules[:<name>] ... %} se pueden reutilizar cualquier número de veces y combinar con otros bloques re2py. El <name> es opcional. Un bloque de reglas se puede usar en un bloque o directiva use. El código para un bloque de reglas se genera en cada punto de uso.

Los bloques de uso se definen con /*!use:re2c[:<name>] ... */ o %{use[:<name>] ... %}. El <name> es opcional: si no se especifica, el bloque de reglas asociado es el más reciente (ya sea con nombre o sin nombre). Un bloque de uso puede añadir definiciones, configuraciones y reglas nombradas propias. Un caso de uso importante para los bloques de uso es un lexer que admite múltiples codificaciones de entrada: el mismo bloque de reglas se reutiliza varias veces con configuraciones específicas de codificación (ver el ejemplo a continuación).

La directiva de uso dentro de un bloque !use:<name>; puede usarse desde dentro de un bloque re2py. Fusiona el bloque referenciado <name> en el actual. Si algunas de las reglas y configuraciones fusionadas se superponen con las definidas previamente, los conflictos se resuelven de la manera habitual: la regla más temprana tiene prioridad y la configuración más reciente anula las anteriores. Una excepción son las reglas especiales *, $ y (en modo condicional) <!>, para las cuales una definición local del bloque tiene prioridad sobre cualquier otra heredada. La directiva de uso permite combinar diferentes bloques re2py en un solo bloque (ver el ejemplo a continuación).

Los bloques nombrados y la directiva de uso dentro de un bloque se añadieron en la versión 2.2 de re2py. Desde esa versión, los bloques reutilizables están permitidos por defecto (no se necesita una opción especial). Antes de la versión 2.2, el modo de reutilización se habilitaba con la opción -r --reusable. Antes de la versión 1.2, los bloques reutilizables no se podían mezclar con bloques normales.

## Extracción de subcoincidencias

re2py tiene dos opciones para la extracción de subcoincidencias.



  
Etiquetas

  
La primera opción es usar etiquetas independientes de la forma @stag
      o #mtag, donde stag y mtag son nombres definidos por el usuario
      arbitrarios. Las etiquetas se habilitan con la opción -T --tags o la
      configuración re2c:tags = 1. Semánticamente, las etiquetas son marcadores
      de posición: se pueden insertar en cualquier lugar de una expresión regular y se
      vinculan a la posición (o posiciones) correspondiente(s) en la cadena de entrada.
      Las s-etiquetas se vinculan a la última posición coincidente, y las
      m-etiquetas se vinculan a una lista de posiciones (pueden usarse en
      subexpresiones de repetición, donde una sola posición en una expresión regular
      corresponde a múltiples posiciones en la cadena de entrada). Todas las etiquetas
      deben ser definidas por el usuario, ya sea manualmente o con la ayuda de bloques
      svars y mvars. Si hay más de una forma en que las etiquetas pueden
      coincidir con la entrada, la ambigüedad se resuelve utilizando una estrategia de
      desambiguación voraz por la izquierda.

  
Capturas

  
La segunda opción es usar grupos de captura. Se habilitan con la opción
      --captures o la configuración re2c:captures = 1. Hay dos variantes para
      diferentes políticas de desambiguación, --leftmost-captures (la opción por
      defecto) es para la política voraz por la izquierda, y --posix-captures es
      para la política de coincidencia más larga POSIX. En este modo, todas las subexpresiones
      entre paréntesis se consideran grupos de captura, y se puede usar un signo de exclamación
      para marcar grupos sin captura: (! ... ). Con la opción --invert-captures
      o la configuración re2c:invert-captures = 1, el significado del signo de
      exclamación se invierte. El número de grupos para la regla de coincidencia se almacena
      en una variable yynmatch (la expresión regular completa es el grupo número
      cero), y los resultados de las subcoincidencias se almacenan en el array yypmatch.
      Tanto yynmatch como yypmatch deben ser definidos por el usuario, y
      el tamaño de yypmatch debe ser al menos [yynmatch * 2]. Use el bloque
      maxnmatch para definir YYMAXNMATCH, una constante que es igual al valor
      máximo de yynmatch entre todas las reglas.

  
Variables de captura

  
Otra forma de usar grupos de captura es la opción --captvars o la
      configuración re2c:captvars = 1. La única diferencia con
      --captures radica en la forma en que el código generado almacena los resultados
      de las subcoincidencias: en lugar de yynmatch y yypmatch, re2py
      genera las variables yytl<k> y yytr<k> para el grupo de
      captura k-ésimo (el usuario debe declararlas usando un bloque svars).
      Las capturas con variables admiten dos políticas de desambiguación:
      --leftmost-captvars o re2c:leftmost-captvars = 1 para la política
      voraz por la izquierda (la predeterminada) y --posix-captvars o
      re2c:posix-captvars para la política de coincidencia más larga POSIX.

Internamente, todas estas opciones se traducen en etiquetas y Autómatas Finitos Deterministas Etiquetados con Lookahead. La idea central de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En el extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es simplemente un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es apenas perceptible. El TDFA generado utiliza un número de variables de etiqueta que no se mapean directamente a las etiquetas: una sola variable puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples variables para almacenar todos sus valores posibles. Finalmente, la ambigüedad se resuelve y solo una variable final por etiqueta sobrevive. Las variables de etiqueta deben definirse usando bloques stags o mtags. Si se almacena el estado del lexer, las variables de etiqueta deben ser parte de él. También deben actualizarse mediante YYFILL.

Las s-etiquetas admiten las siguientes operaciones:

  • guardar la posición de entrada en una s-etiqueta: t = YYCURSOR con la API de puntero C o una operación definida por el usuario YYSTAGP(t) con la API genérica
  • guardar un valor predeterminado en una s-etiqueta: t = NULL con la API de puntero C o una operación definida por el usuario YYSTAGN(t) con la API genérica
  • copiar una s-etiqueta a otra: t1 = t2

Las m-etiquetas admiten las siguientes operaciones:

  • agregar una posición de entrada a una m-etiqueta: una operación definida por el usuario YYMTAGP(t) con la API predeterminada y la genérica
  • agregar un valor predeterminado a una m-etiqueta: una operación definida por el usuario YYMTAGN(t) con la API predeterminada y la genérica
  • copiar una m-etiqueta a otra: t1 = t2

Las s-etiquetas se pueden implementar como valores escalares (punteros o desplazamientos). Las m-etiquetas necesitan una representación más compleja, ya que deben almacenar una secuencia de valores de etiqueta. La representación más ingenua e ineficiente de una m-etiqueta es una lista (array, vector) de valores de etiqueta; una representación más eficiente es almacenar todas las m-etiquetas en un árbol de prefijos representado como un array de nodos (v, p), donde v es el valor de la etiqueta y p es un puntero al nodo padre.

Aquí hay un ejemplo simple de uso de s-etiquetas para analizar versiones semánticas que consisten en tres componentes numéricos: mayor, menor, parche (este último es opcional). Vea más abajo un ejemplo más complejo que utiliza YYFILL.

Las variables de etiqueta son parte del estado del lexer y se ajustan en YYFILL como otras posiciones de entrada. Tenga en cuenta que esto es necesario para las s-etiquetas porque sus valores se invalidan después de desplazar el contenido del búfer. Puede que no sea necesario en una implementación personalizada donde las variables de etiqueta almacenan desplazamientos relativos al inicio de la cadena de entrada en lugar del búfer, lo que puede ocurrir con las m-etiquetas.

# re2py $INPUT -o $OUTPUT
from collections import namedtuple
from enum import Enum
import os
BUFSIZE = 4096
SemVer = namedtuple('SemVer', 'major minor patch')
class State:
    def __init__(self, fname):
        self.file = open(fname, "rb")
        self.yyinput = bytearray(BUFSIZE)
        self.yylimit = BUFSIZE - 1 # exclude terminating null
        self.yycursor = self.yylimit
        self.yymarker = self.yylimit
        self.token = self.yylimit
        self.eof = False
        %{stags format = "\n        self.@@ = -1"; %}
    def __del__(self):
        self.file.close()
class Status(Enum):
    OK = 0
    EOF = 1
    LONG_LEXEME = 2
def fill(st):
    if st.eof:
        return Status.EOF
    # Error: lexeme too long. In real life could reallocate a larger buffer.
    if st.token < 1:
        return Status.LONG_LEXEME
    # Shift buffer contents (discard everything up to the current token).
    st.yyinput = st.yyinput[st.token:st.yylimit]
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    %{stags format = "\n    if st.@@ != -1: st.@@ -= st.token"; %}
    st.token = 0;
    # Fill free space at the end of buffer with new data from file.
    bytes = st.file.read(BUFSIZE - st.yylimit - 1) # -1 for sentinel
    if not bytes:
        st.eof = True # end of file
    else:
        st.yylimit += len(bytes);
        st.yyinput += bytes
    st.yyinput += b'\0' # append sentinel
    return Status.OK
def lex(st, count):
    vers = []
    while True:
        st.token = st.yycursor
    %{
        re2c:api = record;
        re2c:yyrecord = st;
        re2c:YYFILL = "fill(st) == Status.OK";
        re2c:eof = 0;
        re2c:indent:top = 2;
        re2c:tags = 1;
        num = [0-9]+;
        num @t1 "." @t2 num @t3 ("." @t4 num)? [\n] {
            major = int(st.yyinput[st.token:t1])
            minor = int(st.yyinput[t2:t3])
            patch = int(st.yyinput[t4:st.yycursor - 1]) if t4 != -1 else 0
            vers.append(SemVer(major, minor, patch))
            break
        }
        $ { return vers }
        * { return None }
    %}
def main():
    fname = "input"
    verstr = b"1.22.333\n"
    expect = [SemVer(1, 22, 333)] * BUFSIZE
    # Prepare input file.
    f = open(fname, "wb")
    for i in range(BUFSIZE):
        f.write(verstr)
    f.close()
    # Run lexer on the prepared file.
    st = State(fname)
    assert lex(st, 0) == expect
    # Cleanup.
    os.remove(fname)
if __name__ == '__main__':
    main()

Soporte de codificación

Es necesario entender la diferencia entre puntos de código y unidades de código. Un punto de código es un identificador numérico de un símbolo. Una unidad de código es la unidad más pequeña de almacenamiento en el texto codificado. Un solo punto de código puede representarse con una o más unidades de código. En una codificación de longitud fija, todos los puntos de código se representan con el mismo número de unidades de código. En una codificación de longitud variable, los puntos de código pueden representarse con un número diferente de unidades de código. Tenga en cuenta que la regla de "cualquiera" [^] coincide con cualquier punto de código, pero no necesariamente con cualquier unidad de código (la única forma de coincidir con cualquier unidad de código independientemente de la codificación es la regla predeterminada *). El analizador léxico generado funciona con un flujo de unidades de código: yych almacena una unidad de código y YYCTYPE es el tipo de unidad de código. Las expresiones regulares, por otro lado, se especifican en términos de puntos de código. Cuando re2py compila expresiones regulares a autómatas, traduce puntos de código a unidades de código. Esto generalmente no es una asignación simple: en codificaciones de longitud variable, un solo rango de puntos de código puede traducirse a un gráfico complejo de unidades de código. Se admiten las siguientes codificaciones:

  • ASCII (habilitado por defecto). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • EBCDIC (habilitado con --ebcdic o re2c:encoding:ebcdic). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • UCS2 (habilitado con --ucs2 o re2c:encoding:ucs2). Es una codificación de longitud fija con espacio de código [0-0xFFFF] y puntos de código y unidades de código de 2 bytes.
  • UTF8 (habilitado con --utf8 o re2c:encoding:utf8). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
  • UTF16 (habilitado con --utf16 o re2c:encoding:utf16). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 a 2 unidades de código.
  • UTF32 (habilitado con --utf32 o re2c:encoding:utf32). Es una codificación Unicode de longitud fija con espacio de código [0-0x10FFFF] y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión include/unicode_categories.re proporciona definiciones de re2py para las categorías estándar de Unicode.

La opción --input-encoding especifica la codificación del archivo fuente, que puede utilizarse para habilitar literales Unicode en expresiones regulares. Por ejemplo, --input-encoding utf8 indica a re2py que el archivo fuente está en UTF8 (difiere de --utf8, que establece la codificación del texto de entrada). La opción --encoding-policy especifica la forma en que re2py maneja los sustitutos Unicode (puntos de código en el rango [0xD800-0xDFFF]).

A continuación, se muestra un ejemplo de un analizador léxico para identificadores Unicode codificados en UTF8.

# re2py $INPUT -o $OUTPUT --utf8
%{include "unicode_categories.re" %}
def lex(yyinput):
    yycursor = 0
%{
    re2c:yyfill:enable = 0;
    re2c:indent:top = 1;
    // Simplificado "Sintaxis de Identificadores y Patrones Unicode"
    // (ver https://unicode.org/reports/tr31)
    id_start    = L | Nl | [$_];
    id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
    identifier  = id_start id_continue*;
    identifier { return True }
    *          { return False }
%}
assert lex(bytes("_Ыдентификатор\0", "utf-8"))

Archivos de inclusión

re2py permite incluir otros archivos utilizando un bloque de la forma /*!include:re2c FILE */ o %{include FILE %}, o una directiva dentro de un bloque !include FILE ;, donde FILE es la ruta al archivo a incluir. re2py busca los archivos de inclusión en el directorio del archivo que los incluye y en las ubicaciones de inclusión, que se pueden especificar con la opción -I. Los bloques/directivas de inclusión en re2py funcionan de la misma manera que #include en C/C++: el contenido de FILE se copia textualmente en lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias. Utilice la opción --depfile para rastrear las dependencias de compilación del archivo de salida con respecto a los archivos de inclusión. re2py proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como las categorías Unicode) y forman algo así como una biblioteca estándar para re2py. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivos de cabecera

re2py permite generar un archivo de cabecera a partir del archivo .re de entrada utilizando la opción --header o la configuración re2c:header y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de cabecera y el segundo bloque marca el final. Programas esqueleto

Con la opción -S, --skeleton, re2py ignora todo el código que no es de re2py y genera un programa C autocontenido que puede ser compilado y ejecutado posteriormente. El programa consta de código del analizador léxico y datos de entrada. Para cada DFA construido (bloque o condición), re2py genera un analizador léxico independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados esperados de las coincidencias. El programa ejecuta cada analizador léxico en el archivo .input correspondiente y compara los resultados con las expectativas. Los programas esqueleto son muy útiles por varias razones:

  • Pueden verificar la corrección de varias optimizaciones de re2py (los datos se generan al principio del proceso, antes de que se hayan realizado las transformaciones del DFA).
  • Generar un conjunto de datos de entrada con buena cobertura puede ser útil tanto para pruebas como para benchmarking.
  • Generar programas ejecutables autocontenidos permite obtener casos de prueba minimizados (el código original puede ser grande o tener muchas dependencias).

La dificultad para generar datos de entrada es que, para todos los casos excepto los más triviales, el número de cadenas de entrada posibles es demasiado grande (incluso si la longitud de la cadena está limitada). re2py resuelve esta dificultad generando suficientes cadenas para cubrir casi todas las transiciones del DFA. Utiliza el siguiente algoritmo. Primero, construye un esqueleto del DFA. Para codificaciones con un tamaño de unidad de código de 1 byte (como ASCII, UTF-8 y EBCDIC), el esqueleto es simplemente una copia exacta del DFA original. Para codificaciones con unidades de código multibyte, el esqueleto es una copia del DFA con ciertas transiciones omitidas: concretamente, re2py toma como máximo 256 unidades de código para cada rango continuo discreto que corresponde a una transición del DFA. Los valores elegidos están distribuidos uniformemente e incluyen los límites del rango. En lugar de intentar cubrir todos los caminos posibles en el esqueleto (lo cual es inviable), re2py genera suficientes caminos para cubrir todas las transiciones del esqueleto y, por lo tanto, activar los saltos condicionales correspondientes en el analizador léxico. La implementación del algoritmo está limitada a ~1 Gb de transiciones y consume una cantidad constante de memoria (re2py escribe los datos en el archivo tan pronto como se generan).
