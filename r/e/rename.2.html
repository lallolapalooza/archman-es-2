rename(2) Manual de llamadas al sistema rename(2)

NOMBRE

rename, renameat, renameat2 - cambiar el nombre o la ubicación de un archivo

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <stdio.h>
int rename(const char *oldpath, const char *newpath);
#include <fcntl.h>           /* Definición de las constantes AT_* */
#include <stdio.h>
int renameat(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath);
int renameat2(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath, unsigned int flags);

DESCRIPCIÓN

rename() renombra un archivo, moviéndolo entre directorios si es necesario. Cualquier otro enlace físico al archivo (creado con link(2)) no se ve afectado. Los descriptores de archivo abiertos para oldpath tampoco se ven afectados.

Varias restricciones determinan si la operación de renombrar tiene éxito o no: ver ERRORES abajo.

Si newpath ya existe, será reemplazado atómicamente, de modo que no habrá ningún punto en el que otro proceso que intente acceder a newpath lo encuentre ausente. Sin embargo, probablemente habrá una ventana en la que tanto oldpath como newpath se refieran al archivo que se está renombrando.

Si oldpath y newpath son enlaces físicos existentes que se refieren al mismo archivo, entonces rename() no hace nada y devuelve un estado de éxito.

Si newpath existe pero la operación falla por alguna razón, rename() garantiza dejar una instancia de newpath en su lugar.

oldpath puede especificar un directorio. En este caso, newpath debe o bien no existir, o bien especificar un directorio vacío.

Si oldpath se refiere a un enlace simbólico, se renombra el enlace; si newpath se refiere a un enlace simbólico, se sobrescribirá el enlace.

renameat()

La llamada al sistema renameat() opera exactamente de la misma manera que rename(), excepto por las diferencias descritas aquí.

Si la ruta de acceso dada en oldpath es relativa, entonces se interpreta en relación con el directorio al que se refiere el descriptor de archivo olddirfd (en lugar de en relación con el directorio de trabajo actual del proceso llamante, como hace rename() para una ruta relativa).

Si oldpath es relativa y olddirfd es el valor especial AT_FDCWD, entonces oldpath se interpreta en relación con el directorio de trabajo actual del proceso llamante (como rename()).

Si oldpath es absoluta, entonces olddirfd se ignora.

La interpretación de newpath es la misma que para oldpath, excepto que una ruta relativa se interpreta en relación con el directorio al que se refiere el descriptor de archivo newdirfd.

Ver openat(2) para una explicación de la necesidad de renameat().

renameat2()

renameat2() tiene un argumento adicional flags. Una llamada a renameat2() con un argumento flags cero es equivalente a renameat().

El argumento flags es una máscara de bits que consiste en cero o más de las siguientes banderas:

RENAME_EXCHANGE
Intercambia atómicamente oldpath y newpath. Ambas rutas deben existir pero pueden ser de tipos diferentes (por ejemplo, una podría ser un directorio no vacío y la otra un enlace simbólico).
RENAME_NOREPLACE
No sobrescribir newpath durante el renombrado. Devolver un error si newpath ya existe.
RENAME_NOREPLACE no se puede utilizar junto con RENAME_EXCHANGE.
RENAME_NOREPLACE requiere soporte del sistema de archivos subyacente. El soporte para varios sistemas de archivos se añadió de la siguiente manera:
•
ext4 (Linux 3.15);
•
btrfs, tmpfs y cifs (Linux 3.17);
•
xfs (Linux 4.0);
•
Se añadió soporte para muchos otros sistemas de archivos en Linux 4.9, incluyendo ext2, minix, reiserfs, jfs, vfat y bpf.
RENAME_WHITEOUT (desde Linux 3.18)
Esta operación solo tiene sentido para implementaciones de sistemas de archivos overlay/union.
Especificar RENAME_WHITEOUT crea un objeto de "whiteout" en la fuente del renombrado al mismo tiempo que se realiza el renombrado. Toda la operación es atómica, de modo que si el renombrado tiene éxito, también se habrá creado el whiteout.
Un "whiteout" es un objeto que tiene un significado especial en construcciones de sistemas de archivos union/overlay. En estas construcciones, existen varias capas y solo la superior se modifica alguna vez. Un whiteout en una capa superior ocultará efectivamente un archivo coincidente en la capa inferior, haciendo parecer que el archivo no existía.
Cuando se renombra un archivo que existe en la capa inferior, primero se copia el archivo a la capa superior (si aún no está allí) y luego se renombra en la capa superior de solo lectura. Al mismo tiempo, el archivo de origen necesita ser "blanqueado" (para que la versión del archivo de origen en la capa inferior se vuelva invisible). Toda la operación debe realizarse atómicamente.
Cuando no forma parte de una union/overlay, el whiteout aparece como un dispositivo de caracteres con un número de dispositivo {0,0}. (Tenga en cuenta que otras implementaciones de union/overlay pueden emplear métodos diferentes para almacenar entradas de whiteout; en concreto, el montaje union de BSD utiliza un tipo de inodo separado, DT_WHT, que, aunque es soportado por algunos sistemas de archivos disponibles en Linux, como CODA y XFS, es ignorado por el código de soporte de whiteout del kernel, a partir de Linux 4.19, al menos).
RENAME_WHITEOUT requiere los mismos privilegios que la creación de un nodo de dispositivo (es decir, la capacidad CAP_MKNOD).
RENAME_WHITEOUT no se puede emplear junto con RENAME_EXCHANGE.
RENAME_WHITEOUT requiere soporte del sistema de archivos subyacente. Entre los sistemas de archivos que lo soportan se encuentran tmpfs (desde Linux 3.18), ext4 (desde Linux 3.18), XFS (desde Linux 4.1), f2fs (desde Linux 4.2), btrfs (desde Linux 4.7) y ubifs (desde Linux 4.9).

VALOR DE RETORNO

Si tiene éxito, se devuelve cero. En caso de error, se devuelve -1 y errno se establece para indicar el error.

ERRORES

EACCES
Se deniega el permiso de escritura en el directorio que contiene oldpath o newpath, o bien se deniega el permiso de búsqueda en uno de los directorios del prefijo de ruta de oldpath o newpath, o oldpath es un directorio y no permite permiso de escritura (necesario para actualizar la entrada ..). (Ver también path_resolution(7)).

ERRORES

EACCES
Permiso denegado. El directorio que contiene el archivo que se va a eliminar tiene el bit pegajoso (S_ISVTX) establecido y el ID de usuario efectivo del proceso no es ni el ID de usuario del archivo a eliminar ni el del directorio que lo contiene, y el proceso no tiene privilegios (Linux: no tiene la capacidad CAP_FOWNER). O bien, newpath es un archivo existente y el directorio que lo contiene tiene el bit pegajoso establecido y el ID de usuario efectivo del proceso no es ni el ID de usuario del archivo a reemplazar ni el del directorio que lo contiene, y el proceso no tiene privilegios (Linux: no tiene la capacidad CAP_FOWNER). O bien, el sistema de archivos que contiene oldpath no admite el tipo de renombramiento solicitado. (Para rename(), el permiso de escritura no es necesario en el directorio si el archivo se está moviendo a otro directorio y ambos son propiedad del usuario llamante.)
EBUSY
oldpath es un punto de montaje y también se está intentando eliminar o mover el propio punto de montaje. En este caso, el sistema considera esto un error. (Tenga en cuenta que no hay requisito de devolver EBUSY en tales casos; no hay nada de malo en realizar el renombramiento de todos modos; pero está permitido devolver EBUSY si el sistema no puede manejar de otra manera tales situaciones).

El sistema de archivos en el que se encuentra el archivo está montado en varios lugares y se está intentando mover un archivo a un directorio que está en un montaje diferente del mismo sistema de archivos.

Se está intentando renombrar un archivo que está siendo utilizado por un proceso (por ejemplo, un archivo abierto con O_TMPFILE).

EDQUOT
Se ha agotado la cuota de bloques de disco del usuario en el sistema de archivos.
EFAULT
oldpath o newpath apunta fuera de su espacio de direcciones accesible.
EINVAL
La nueva ruta contenía un prefijo de ruta de la antigua, o, más generalmente, se intentó hacer de un directorio un subdirectorio de sí mismo.
EISDIR
newpath es un directorio existente, pero oldpath no es un directorio.
ELOOP
Se encontraron demasiados enlaces simbólicos al resolver oldpath o newpath.
EMLINK
oldpath ya tiene el número máximo de enlaces, o era un directorio y el directorio que contiene newpath tiene el número máximo de enlaces.
ENAMETOOLONG
oldpath o newpath era demasiado largo.
ENOENT
El enlace llamado por oldpath no existe; o, un componente de directorio en newpath no existe; o, oldpath o newpath es una cadena vacía.
ENOMEM
No había suficiente memoria del kernel disponible.
ENOSPC
Al dispositivo que contiene el archivo no le queda espacio para la nueva entrada de directorio.
ENOTDIR
Un componente utilizado como directorio en oldpath o newpath no es, de hecho, un directorio. O bien, oldpath es un directorio, y newpath existe pero no es un directorio.
ENOTEMPTY o EEXIST
newpath es un directorio no vacío, es decir, contiene entradas distintas de "." y "..".
EPERM o EACCES
El directorio que contiene oldpath tiene el bit pegajoso (S_ISVTX) establecido y el ID de usuario efectivo del proceso no es ni el ID de usuario del archivo a eliminar ni el del directorio que lo contiene, y el proceso no tiene privilegios (Linux: no tiene la capacidad CAP_FOWNER); o newpath es un archivo existente y el directorio que lo contiene tiene el bit pegajoso establecido y el ID de usuario efectivo del proceso no es ni el ID de usuario del archivo a reemplazar ni el del directorio que lo contiene, y el proceso no tiene privilegios (Linux: no tiene la capacidad CAP_FOWNER); o el sistema de archivos que contiene oldpath no admite el tipo de renombramiento solicitado.
EROFS
El archivo está en un sistema de archivos de solo lectura.
EXDEV
oldpath y newpath no están en el mismo sistema de archivos montado. (Linux permite que un sistema de archivos se monte en varios puntos, pero rename() no funciona entre diferentes puntos de montaje, incluso si el mismo sistema de archivos está montado en ambos).

Los siguientes errores adicionales pueden ocurrir para renameat() y renameat2():

EBADF
oldpath (newpath) es relativo pero olddirfd (newdirfd) no es un descriptor de archivo válido.
ENOTDIR
oldpath es relativo y olddirfd es un descriptor de archivo que se refiere a un archivo que no es un directorio; o similar para newpath y newdirfd

Los siguientes errores adicionales pueden ocurrir para renameat2():

EEXIST
flags contiene RENAME_NOREPLACE y newpath ya existe.
EINVAL
Se especificó una bandera inválida en flags.
EINVAL
Tanto RENAME_NOREPLACE como RENAME_EXCHANGE se especificaron en flags.
EINVAL
Tanto RENAME_WHITEOUT como RENAME_EXCHANGE se especificaron en flags.
EINVAL
El sistema de archivos no admite una de las banderas en flags.
ENOENT
flags contiene RENAME_EXCHANGE y newpath no existe.
EPERM
Se especificó RENAME_WHITEOUT en flags, pero el llamante no tiene la capacidad CAP_MKNOD.

Notas de glibc

En kernels más antiguos donde renameat() no está disponible, la función de envoltura de glibc recurre al uso de rename(). Cuando oldpath y newpath son rutas relativas, glibc construye rutas basándose en los enlaces simbólicos en /proc/self/fd que corresponden a los argumentos olddirfd y newdirfd.

BUGS

En los sistemas de archivos NFS, no se puede asumir que si la operación falló, el archivo no fue renombrado. Si el servidor realiza la operación de renombramiento y luego falla, el RPC retransmitido que se procesará cuando el servidor vuelva a estar en funcionamiento provoca un fallo. Se espera que la aplicación se encargue de esto. Consulte link(2) para un problema similar.
