NOMBRE

readers.conf - Control de acceso y configuración para nnrpd

EN RESUMEN

El archivo readers.conf define quién tiene permitido conectarse como lector de noticias y qué pueden hacer después de conectarse. Ten en cuenta que en readers.conf, la autenticación y la autorización se configuran en bloques diferentes. Primero, un usuario es autenticado y se le asigna una identidad (en un bloque "auth"). Luego, esta identidad es autorizada para acceder a ciertos grupos de noticias con ciertos derechos (en un bloque "access").

En cuanto a la autenticación, tu bloque "auth" para usuarios con contraseña podría verse así:

auth "foreignokay" {
    auth: "ckpasswd -f <ruta de la base de datos en inn.conf>/newsusers"
    default: "<unauthenticated>"
}

Consulta la documentación de la opción -f en la página del manual de ckpasswd(8) para saber cómo generar contraseñas y utilizar este archivo newsusers.

De esta manera, con el bloque de autenticación "foreignokay", un usuario autenticado exitosamente como usuario "miusuario" recibirá la identidad "miusuario". Si la autenticación falla, se le asignará la identidad predeterminada "<unauthenticated>" que luego será comprobada en los bloques "access".

Los bloques de autenticación se comprueban desde el último al primero en el archivo readers.conf (de abajo hacia arriba). Tan pronto como uno coincida, se asigna la identidad correspondiente al usuario.

En cuanto a la autorización, hagamos algo en un bloque "access" para las personas autenticadas exitosamente con contraseñas:

access "authenticatedpeople" {
    users: "*"
    newsgroups: "*,!junk,!control,!control.*"
}

Y luego algo como uno de los dos siguientes, dependiendo de si los usuarios no autenticados obtienen algún acceso:

access "restrictive" {
    users: "<unauthenticated>"
    newsgroups: "!*"
}
access "readonly" {
    users: "<unauthenticated>"
    read: "local.*"
    post: "!*"
}

Ten en cuenta que el bloque "authenticatedpeople" debe aparecer en readers.conf antes que los bloques "restrictive" o "readonly" porque los bloques de acceso se comprueban desde el último al primero en el archivo readers.conf (de abajo hacia arriba). Tan pronto como uno coincida con la identidad previamente asignada por un bloque de autenticación, se elige. El bloque de acceso "authenticatedpeople" coincide con cualquier usuario al que no se le haya asignado "<unauthenticated>" como identidad.

Más ejemplos y características se detallan a continuación en esta página del manual (notablemente sin ningún archivo de contraseñas, con PAM, con hooks de Perl o Python).

No necesitas recargar nada después de modificar readers.conf; cada vez que un cliente de noticias se conecta al servidor, se genera un nuevo proceso nnrpd que lee su configuración desde el disco. No obstante, después de cualquier cambio, puedes ejecutar "inncheck" para realizar comprobaciones básicas de sintaxis contra el archivo readers.conf modificado.

DESCRIPCIÓN

readers.conf en pathetc especifica el control de acceso para nnrpd(8). Controla quién tiene permiso para conectarse como lector de noticias y qué pueden hacer después de conectarse. nnrpd lee este archivo cada vez que un cliente de noticias se conecta al servidor, incluso cuando se ejecuta en modo demonio con -D, lo que significa que cualquier cambio en este archivo entra en vigor inmediatamente en todas las conexiones subsiguientes. (La ubicación de readers.conf en pathetc es solo la predeterminada; el mismo formato se aplica a cualquier archivo especificado con "nnrpd -c".)

Hay dos tipos de entradas en readers.conf: pares parámetro/valor y grupos de configuración. Las líneas en blanco y todo lo que siga a un signo de almohadilla ("#") se ignoran, a menos que el carácter "#" sea escapado con "\". El número máximo de caracteres en cada línea es 8.191.

Los pares parámetro/valor consisten en una palabra clave seguida inmediatamente por dos puntos, al menos un espacio en blanco, y un valor. La distinción entre mayúsculas y minúsculas en el parámetro es importante (el parámetro generalmente debe estar en minúsculas), y un parámetro puede contener cualquier carácter excepto dos puntos, "#" y espacios en blanco. Un ejemplo:

hosts: *.example.com

Los valores que contienen espacios en blanco deben entrecomillarse con comillas dobles, como en:

hosts: "*.example.com, *.example.net"

Si el parámetro no contiene espacios en blanco, como:

hosts: *.example.com,*.example.net

no es necesario entrecomillarlo, aunque puede que desees hacerlo de todos modos por claridad.

No hay forma de continuar una línea en la siguiente línea, y por lo tanto, no hay forma de tener un solo parámetro con un valor de más de unos 8.180 caracteres.

Muchos parámetros aceptan un valor booleano. Para todos estos parámetros, el valor puede especificarse como "true", "yes" o "on" para activarlo y puede ser cualquiera de "false", "no" o "off" para desactivarlo. La distinción entre mayúsculas y minúsculas en estos valores no es importante.

Hay dos tipos básicos de grupos de configuración: auth y access. El grupo auth proporciona mecanismos para establecer la identidad del usuario, quién es. El grupo access determina, dada la identidad del usuario, qué se le permite hacer. Escribir un archivo readers.conf para tu configuración es un proceso de dos pasos: primero asignar una identidad a cada conexión entrante usando grupos auth, y luego dar a cada identidad los privilegios apropiados con grupos access. Recomendamos *no* mezclar grupos auth y access en el archivo de configuración; a menudo es más sensato (en ausencia del parámetro key) poner todos los grupos auth primero, y todos los grupos access debajo.

Una identidad de usuario, tal como la establece un grupo auth, se parece a una dirección de correo electrónico si se especifica un dominio (como "<nombredeusuario>@<dominio>") o, de lo contrario, solo "<nombredeusuario>".

Si nnrpdauthsender está configurado en inn.conf, la identidad del usuario también se inserta en el campo de cabecera Sender de las publicaciones realizadas por ese usuario. Consulta la documentación de esa opción en inn.conf(5) para más detalles.

Una definición de grupo auth se ve así:

auth <nombre> {
    hosts: <comodín-de-host>
    auth: <programa-de-autenticación>
    res: <programa-de-resumen>
    default: <usuario-predeterminado>
    default-domain: <dominio-predeterminado>
    # ...posiblemente otras configuraciones
}

El <nombre> se usa como etiqueta para el grupo y es solo para fines de documentación. (Si tu configuración de syslog registra la instalación "news.debug", el <nombre> aparecerá en la salida de depuración de nnrpd. Examinar esa salida puede ser muy útil para entender por qué tu configuración no hace lo que esperas.)

Un grupo auth determinado solo se aplica a los hosts cuyo nombre o dirección IP coincide con la expresión comodín dada en el parámetro hosts (se permiten expresiones comodín separadas por comas, pero "@" no es compatible). En lugar de expresiones comodín, también puedes usar notación CIDR para hacer coincidir cualquier dirección IP en un bloque de red; por ejemplo, "10.10.10.0/24" coincidirá con cualquier dirección IP entre 10.10.10.0 y 10.10.10.255 inclusive.

Si se compila contra las bibliotecas TLS/SSL o SASL, un grupo auth con el parámetro require_encryption establecido en true solo se aplica si la conexión entrante está utilizando una capa de cifrado, ya sea desde el principio si se pasó el flag -S a nnrpd, o después de un uso exitoso de STARTTLS, o después de una autenticación exitosa utilizando un mecanismo SASL que negocia una capa de cifrado.

Para cualquier conexión desde un host que coincida con esa expresión comodín o bloque de red, cada <programa-de-resumen> (puede haber varias líneas res en un bloque; se ejecutan en secuencia hasta que una tenga éxito), si existe, se ejecuta para determinar la identidad del usuario solo a partir de la información de la conexión.

Si todos los resolutores fallan, o si el parámetro res no está presente, al usuario se le asigna una identidad de "<defuser>@<defdomain>"; en otras palabras, se utilizan los valores de los parámetros default y default-domain. Si <res-program> solo devuelve un nombre de usuario, se utiliza <defdomain> como dominio.

Si el usuario se autentica más tarde a través de los comandos AUTHINFO USER/PASS, el nombre de usuario y la contraseña proporcionados se pasan a cada <auth-program> (puede haber múltiples líneas auth, perl_auth o python_auth en un bloque; se ejecutan en secuencia hasta que una tenga éxito). Si una tiene éxito y devuelve una identidad diferente a la asignada en el momento de la conexión, se compara nuevamente con los grupos de acceso disponibles y las acciones para las que el usuario está autorizado pueden cambiar. El <auth-program> más común a utilizar es ckpasswd, que soporta varias formas de verificar contraseñas, incluyendo el uso de PAM. Consulte la página del manual de ckpasswd(8) para obtener más detalles.

Al comparar grupos de autenticación, se utiliza el último grupo de autenticación en el archivo que coincide con una determinada combinación de conexión y nombre de usuario/contraseña.

Una definición de grupo de acceso suele tener este aspecto:

access <name> {
    users: <identity-wildmat>
    newsgroups: <group-wildmat>
    # ...posiblemente otras configuraciones
}

De nuevo, <name> es solo para fines de documentación. Esto dice que todos los usuarios cuya identidad coincide con <identity-wildmat> pueden leer y publicar en todos los grupos de noticias que coinciden con <group-wildmat> (como antes, se permiten expresiones wildmat separadas por comas, pero "@" no es compatible). Alternativamente, puede usar el formato:

access <name> {
    users: <identity-wildmat>
    read: <read-wildmat>
    post: <post-wildmat>
}

y los usuarios que coincidan podrán leer cualquier grupo que coincida con <read-wildmat> y publicar en cualquier grupo que coincida con <post-wildmat>. También puede configurar varias otras cosas en el grupo de acceso, así como anular varios parámetros de inn.conf(5) para un grupo de usuarios en particular.

Al igual que con los grupos de autenticación, al comparar grupos de acceso, se utiliza el último que coincide en el archivo para determinar los permisos del usuario. Hay una excepción a esta regla: si el grupo de autenticación que coincidió con el cliente contiene un parámetro perl_access o python_access, entonces el script dado como argumento se utiliza para generar dinámicamente un grupo de acceso. Este nuevo grupo de acceso se utilizará para determinar los derechos de acceso del cliente; los grupos de acceso en el archivo se ignoran.

Hay un caso especial adicional a tener en cuenta. Al formar reglas de autenticación y autorización particularmente complejas, a veces es útil que las identidades proporcionadas por un grupo de autenticación determinado solo se apliquen a grupos de acceso particulares; en otras palabras, en lugar de verificar la identidad contra el parámetro users de cada grupo de acceso, se verifica contra el parámetro users de solo algunos grupos de acceso específicos. Esto se hace con el parámetro key. Por ejemplo:

auth example {
    key: special
    hosts: *.example.com
    default: <SPECIAL>
}
access example {
    key: special
    users: <SPECIAL>
    newsgroups: *
    addcanlockuser: none
}

En este caso, los dos parámetros key vinculan este grupo de autenticación con este grupo de acceso. Para cualquier conexión entrante que coincida con "*.example.com" (suponiendo que no haya ningún grupo de autenticación posterior que también coincida con tales hosts), ningún grupo de acceso que no tenga "key: special" será considerado. De manera similar, el grupo de acceso anterior solo se verificará si el usuario fue autenticado con un grupo de autenticación que contiene "key: special". Este mecanismo normalmente no es útil; casi siempre hay una mejor manera de lograr el mismo resultado.

También observe en el ejemplo que no hay un parámetro default-domain, lo que significa que no se agrega ningún dominio al nombre de usuario predeterminado y la identidad para tales conexiones es solo "<SPECIAL>". Tenga en cuenta que algunos complementos adicionales para INN pueden preferir que las identidades autenticadas siempre devuelvan una dirección de correo electrónico completa (incluido un dominio), por lo que es posible que desee configurar su sistema de esa manera si está utilizando complementos. Como varias personas diferentes pueden tener asignada la misma identidad "<SPECIAL>", no se deben generar hashes de Cancel-Lock específicos del usuario.

Los archivos de configuración se pueden incluir en otros archivos de configuración a través de la sintaxis:

include <filename>

Se incluye el archivo llamado <filename>. Esta sintaxis solo está permitida en el nivel superior.

A continuación, se presenta la lista completa de parámetros permitidos para los grupos de autenticación y acceso, y después de eso hay algunos ejemplos que pueden hacer que esto sea algo más claro.

PARÁMETROS DE GRUPO DE AUTENTICACIÓN

Un grupo de autenticación sin al menos uno de los parámetros res, auth, perl_auth, python_auth o default no tiene sentido (y en la práctica simplemente se ignorará).

auth
Una línea de comandos simple para un autenticador de usuario (los metacaracteres del shell no son compatibles). Si no se proporciona una ruta completa, el programa ejecutado debe estar ubicado en el directorio pathbin/auth/passwd. Un autenticador es un programa utilizado para manejar un nombre de usuario y una contraseña proporcionados por el usuario, a través de un mecanismo como AUTHINFO USER/PASS. Al igual que con res, un grupo de autenticación puede tener múltiples parámetros auth; se intentarán en orden y se utilizarán los resultados del primero exitoso. Consulte también perl_auth.

El autenticador más común a utilizar es ckpasswd(8); consulte su página del manual para obtener más información.

default
El nombre de usuario predeterminado para las conexiones que coinciden con este grupo de autenticación. Este es el nombre de usuario asignado al usuario en el momento de la conexión si todos los resolutores fallan o si no hay parámetros res. Tenga en cuenta que puede ser un nombre de usuario simple, en cuyo caso default-domain (si está presente) se agrega después de un "@", o una cadena de identidad completa que contiene un "@", en cuyo caso se usará textualmente.
default-domain
La cadena de dominio predeterminada para este grupo de autenticación. Si un resolutor de usuarios o un autenticador no proporciona un dominio, o si se utiliza el nombre de usuario predeterminado y no contiene un "@", este dominio se utiliza para formar la identidad del usuario. (Tenga en cuenta que para muchas configuraciones, no es realmente necesario que las identidades de los usuarios estén calificadas con un nombre de dominio, en cuyo caso no es necesario usar este parámetro).
hosts
Una lista separada por comas de hosts remotos, patrones wildmat que coinciden con nombres de host o direcciones IP, o bloques de red IP especificados en notación CIDR. Si un usuario se conecta desde un host que no coincide con este parámetro, este grupo de autenticación no coincidirá con la conexión y se ignorará.

Tenga en cuenta que si tiene una gran cantidad de patrones que no pueden fusionarse en patrones más amplios (como una gran cantidad de sistemas individuales dispersos por la red que deberían tener acceso), el parámetro hosts puede exceder la longitud máxima de línea de 8192 caracteres. En ese caso, deberá dividir ese grupo de autenticación en múltiples grupos de autenticación, cada uno con una parte de los hosts listados en su parámetro hosts, y cada uno asignando la misma identidad de usuario.

Todos los hosts coinciden si este parámetro no se proporciona.

key
Si este parámetro está presente, los privilegios de cualquier conexión que coincida con este grupo de autenticación solo se determinarán por el subconjunto de grupos de acceso que contengan un parámetro de clave coincidente.
localaddress
Una lista separada por comas de hosts locales o patrones de direcciones con la misma sintaxis que el parámetro hosts. Si se especifica este parámetro, su grupo de autenticación solo coincidirá con las conexiones realizadas a una interfaz local coincidente. (Obviamente, esto solo es útil para servidores con múltiples interfaces).

Todas las direcciones locales coinciden si este parámetro no se proporciona.

perl_access
Una ruta a un script de Perl para generar dinámicamente un grupo de acceso. Si un grupo de autenticación coincide con éxito y contiene un parámetro perl_access, entonces el script de Perl del argumento se utilizará para crear un grupo de acceso. Este grupo determinará los derechos de acceso del cliente, anulando cualquier grupo de acceso en readers.conf. Si y solo si un grupo de autenticación exitoso contiene el parámetro perl_access, los grupos de acceso de readers.conf se ignoran y los derechos del cliente se determinan dinámicamente. Este parámetro solo es válido si INN está compilado con soporte de Perl (se pasó --with-perl a "configure"). Se puede encontrar más información en el archivo doc/hook-perl.
perl_auth
Una ruta a un script de Perl para la autenticación. El parámetro perl_auth funciona exactamente como auth, excepto que llama al script nombrado utilizando el hook de Perl en lugar de un programa externo. Se permite el uso múltiple/mixto de los parámetros auth, perl_auth y python_auth dentro de cualquier grupo de autenticación; cada línea se intenta en el orden en que aparece. perl_auth tiene más potencia que auth ya que proporciona al programa de autenticación información adicional sobre el cliente y la capacidad de devolver una cadena de error y un nombre de usuario. Este parámetro solo es válido si INN está compilado con soporte de Perl (se pasó --with-perl a "configure"). Se puede encontrar más información en doc/hook-perl.
python_access
Un script de Python para generar dinámicamente un grupo de acceso. Si un grupo de autenticación coincide con éxito y contiene un parámetro python_access, entonces el script del argumento (sin su extensión ".py") ubicado en el directorio pathfilter se utilizará para crear un grupo de acceso. Este grupo determinará los derechos de acceso del cliente, anulando cualquier grupo de acceso en readers.conf.

Si y solo si un grupo de autenticación exitoso contiene el parámetro python_access, los grupos de acceso de readers.conf se ignoran y los derechos del cliente se determinan dinámicamente.

Este parámetro solo es válido si INN se compila con soporte de Python (se pasa --with-python a "configure"). Puede encontrar más información en el archivo doc/hook-python.

python_auth
Un script de Python para la autenticación. El parámetro python_auth funciona exactamente como auth, excepto que llama al script nombrado (sin su extensión ".py") ubicado en el directorio pathfilter utilizando el hook de Python en lugar de un programa externo. Se permite el uso múltiple/mixto de los parámetros auth, perl_auth y python_auth dentro de cualquier grupo de autenticación; cada línea se intenta en el orden en que aparece. python_auth tiene más potencia que auth ya que proporciona al programa de autenticación información adicional sobre el cliente y la capacidad de devolver una cadena de error y un nombre de usuario.

Este parámetro solo es válido si INN se compila con soporte de Python (se pasa --with-python a "configure"). Puede encontrar más información en doc/hook-python.

python_dynamic
Un script de Python para aplicar control de acceso dinámicamente por grupo de noticias. Si un grupo de autenticación coincide con éxito y contiene un parámetro python_dynamic, entonces el script argumento (sin su extensión ".py") ubicado en el directorio pathfilter se utilizará para determinar los derechos del cliente cada vez que el usuario intente ver un grupo de noticias, o leer o publicar un artículo. Los derechos de acceso determinados por python_dynamic anulan los valores de los parámetros del grupo de acceso, como newsgroups, read y post.

Este parámetro solo es válido si INN se compila con soporte de Python (se pasa --with-python a "configure"). Puede encontrar más información en el archivo doc/hook-python.

require_encryption
Si se establece en verdadero, una conexión entrante solo coincide con este grupo de autenticación si está cifrada, ya sea desde el principio si se pasó el indicador -S a nnrpd, o después de un uso exitoso de STARTTLS, o después de una autenticación exitosa utilizando un mecanismo SASL que negocia una capa cifrada. Este parámetro solo es válido si INN se compila con soporte TLS/SSL o SASL (por defecto si las bibliotecas SSL y criptográficas de OpenSSL o la biblioteca Cyrus SASL se encuentran en tiempo de configuración, de lo contrario, consulte las banderas --with-openssl y --with-sasl pasadas a "configure").
res
Una línea de comandos simple para un resolvedor de usuarios (los metacaracteres de shell no son soportados). Si no se proporciona una ruta completa, el programa ejecutado debe estar en el directorio pathbin/auth/resolv. Un resolvedor es un programa de autenticación que intenta descubrir la identidad del usuario que se conecta utilizando nada más que la información de conexión (es decir, el usuario no ha proporcionado un nombre de usuario y contraseña). Un ejemplo de resolvedor sería un programa que asigna una identidad a partir de una devolución de llamada ident o del nombre de host del usuario.

Un grupo de autenticación puede tener múltiples parámetros res, y se intentarán en el orden en que están listados. Se utilizarán los resultados del primero que tenga éxito.

Alternativamente, se puede usar un bloque res en lugar de un parámetro res. Los parámetros reconocidos en dichos bloques res son:

log
Una cadena para registrar en pathlog/news.notice (con "res also-log:" delante) antes de que se intente el resolvedor. Un grupo res puede tener múltiples parámetros log, y se registrarán en el orden en que están listados.
program
Este parámetro es obligatorio en un bloque res. Su significado es el mismo que el parámetro res utilizado directamente en un bloque auth. 
auth <auth-name> {
    res: <res-program>
}

es por lo tanto equivalente a:

auth <auth-name> {
    res <res-name> {
        program: <res-program>
    }
}

PARÁMETROS DE GRUPO DE ACCESO

access
Un conjunto de letras que especifican los permisos otorgados al cliente. Las letras se eligen del siguiente conjunto:
A
El cliente puede publicar artículos con encabezados Approved (en otras palabras, puede aprobar artículos para grupos de noticias moderados). Por defecto, esto no está permitido.
I
El cliente puede inyectar artículos con IHAVE. Tenga en cuenta que para inyectar artículos con el comando IHAVE, el usuario también debe tener permiso POST (la opción "P"). Los artículos inyectados con IHAVE se tratan como si hubieran sido inyectados con POST, es decir, dichos artículos no deben haber sido inyectados previamente (no deben contener campos de encabezado como Injection-Info).
L
El cliente puede publicar en grupos de noticias que están configurados para desactivar la publicación local (campos de estado "j", "n" y "x" en el archivo active(5)).
N
El cliente puede usar el comando NEWNEWS, anulando la configuración global.
P
El cliente puede publicar artículos.
R
El cliente puede leer artículos.

Tenga en cuenta que si se proporciona este parámetro, se ignora allownewnews en inn.conf para las conexiones que coinciden con este grupo de acceso y la capacidad del cliente para usar NEWNEWS está completamente determinada por la presencia de "N" en la cadena de acceso. Si desea admitir NEWNEWS, asegúrese de incluir "N" en la cadena de acceso cuando utilice este parámetro.

Tenga en cuenta que si se proporciona este parámetro y "R" no está presente en la cadena de acceso, el cliente no puede leer independientemente de los parámetros newsgroups o read. De manera similar, si se proporciona este parámetro y "P" no está presente, el cliente no puede publicar. Este uso de access está obsoleto y es confuso; se recomienda encarecidamente que si se utiliza el parámetro access, "R" y "P" siempre se incluyan en la cadena de acceso y que newsgroups, read y post se utilicen para controlar el acceso. (Para otorgar acceso de lectura pero no de publicación, se puede tener solo un parámetro read y ningún parámetro post.)

addcanlockuser
Si se establece en "none", las publicaciones realizadas por estos usuarios no tendrán un hash específico del usuario en el campo de encabezado Cancel-Lock (solo se generará el hash del administrador). No habrá ningún campo de encabezado Cancel-Key en las solicitudes de cancelación o sustitución. Este es un valor de cadena y el valor por defecto es "username", es decir, se utiliza un hash específico del usuario basado en la identidad asignada a la conexión.

Otro valor posible para este parámetro es "ip", en cuyo caso se utiliza un hash específico del usuario basado en la IP de la conexión (que debe ser una IP estática para identificar realmente a los usuarios).

Consulte inn-secrets.conf(5) para obtener más información sobre Cancel-Lock. La razón principal de este parámetro es desactivar este mecanismo de autenticación cuando la misma identidad o IP puede ser asignada por un grupo de acceso a diferentes personas. De lo contrario, cualquiera de estas personas podría enviar una retirada autenticada de un artículo enviado originalmente por otra persona con la misma identidad o IP.

domain
Cuando se establece, el valor de este parámetro se utiliza para la parte del dominio (el lado derecho después de "@") de los Message-IDs autogenerados, así como para el nombre del servidor indicado en los campos de encabezado Injection-Info.

Por defecto, el valor de este parámetro se hereda del parámetro epónimo en inn.conf. Sin embargo, si domain no se establece explícitamente en readers.conf, el comportamiento específico descrito anteriormente no se activará a menos que virtualhost se establezca en verdadero.

También puede desear establecer el parámetro fromhost (heredado de inn.conf) para la dirección de quejas en el campo de encabezado Injection-Info, si su valor por defecto debe cambiarse, y el parámetro complaints no está ya establecido o newsmaster no contiene ya un "@".

groupexactcount
Este parámetro controla el umbral por debajo del cual nnrpd informará el número exacto de artículos existentes en los grupos de noticias en lugar de una estimación. El número exacto se actualiza generalmente una vez al día durante el proceso de expiración por expirover (ejecutado por news.daily), y se actualiza cuando llegan nuevos artículos, pero no necesariamente cuando los artículos se cancelan o sobrescriben en métodos de almacenamiento de autoexpiración como CNFS.

Cuando el recuento estimado de artículos es estrictamente menor que groupexactcount, nnrpd volverá a contar el número de artículos existentes y reportará el valor exacto. Si groupexactcount se establece en 0, nnrpd volverá a contar siempre. Si se establece en 1, nunca volverá a contar.

Aunque los recuentos exactos de artículos no son requeridos, pueden ser útiles para distinguir grupos de noticias vacíos informando un recuento exacto de 0 en lugar de una estimación de 1 (cuando sucede, el cliente de noticias puede mostrar que hay 1 artículo presente en el grupo de noticias, luego intenta recuperar el artículo y, finalmente, no muestra nada al usuario).

No se recomienda establecer un valor alto para este par

SUMMARY

Here's a basic summary of what happens when a client connects:

  • All auth groups are scanned and the ones that don't match the client (due to hosts, localaddress, require_encryption, etc.) are eliminated.
  • The remaining auth groups are scanned from the last to the first, and an attempt is made to apply it to the current connection. This means running res programs, if any, and otherwise applying default. The first auth group (starting from the bottom) to return a valid user is kept as the active auth group.
  • If no auth groups yield a valid user (none have default parameters or successful res programs) but some of the auth groups have auth lines (indicating a possibility that the user can authenticate and then obtain permissions), the connection is considered to have no valid auth group (which means that the access groups are ignored completely) but the connection isn't closed. Instead, a 480 response code (meaning that authentication is required) is returned for everything until the user authenticates.
  • When the user authenticates, the auth groups are rescanned, and only the matching ones which contain at least one auth, perl_auth, or python_auth line are considered. These auth groups are scanned from the last to the first, running auth programs and perl_auth or python_auth scripts. The first auth group (starting from the bottom) to return a valid user is kept as the active auth group.
  • Regardless of how an auth group is established, as soon as one is, that auth group is used to assign a user identity by taking the result of the successful res, auth, perl_auth, or python_auth line (or the default if necessary), and appending default-domain if necessary. (If the perl_access or python_access parameter is present.)
  • Finally, an access group is selected by scanning the access groups from bottom up and finding the first match. (If the established auth group contained a perl_access or python_access line, the dynamically generated access group returned by the script is used instead.) User permissions are granted based on the established access group.

EXAMPLES

Probably the simplest useful example of a complete readers.conf, this gives permissions to read and post to all groups to any connections from the "example.com" domain, except for Bob's machine, and no privileges for anyone connecting elsewhere:

auth example.com {
    hosts: "*.example.com, example.com, !bob.example.com"
    default: "<EXAMPLE>"
}
access full {
    users: "<EXAMPLE>"
    newsgroups: *
    addcanlockuser: none
}

Note that the above access realm could also be written without the users key, in which case it applies to any user identity (though in this example, the user identity that will be assigned to all matching connections is "<EXAMPLE>"). It is however recommended to keep an explicit users key so as to better view to whom the access block applies.

As the only available auth realm only matches hosts in the "example.com" domain, any connections from other hosts will be rejected immediately.

Aquí tienes un ejemplo similar para un servidor de noticias que acepta conexiones desde cualquier lugar pero requiere que el usuario especifique un nombre de usuario y una contraseña. El nombre de usuario y la contraseña se verifican primero contra una base de datos externa de nombres de usuario y contraseñas, y luego utilizan PAM:

auth all {
    auth: "ckpasswd -f <ruta.db en inn.conf>/newsusers"
    auth: ckpasswd
}
access full {
    users: *
    newsgroups: *
}

Cuando el usuario se conecta por primera vez, no hay claves res ni valor predeterminado, por lo que no recibe ninguna identidad válida y la conexión no coincide con ningún grupo de acceso (incluso con los que tienen "users: *"). Dichos usuarios no reciben nada más que respuestas de solicitud de autenticación de nnrpd hasta que se autentican.

Si posteriormente se autentican, el nombre de usuario y la contraseña se verifican primero ejecutando ckpasswd con la opción -f para un archivo externo de contraseñas cifradas, y luego se usa PAM (si INN se compiló con soporte PAM) para verificar la contraseña (y si esto falla, intenta verificar la contraseña contra el campo de contraseña devuelto por getpwnam(3)). Si ambos fallan, el usuario seguirá sin identidad; de lo contrario, se asignará una identidad (generalmente el nombre de usuario proporcionado, quizás con un dominio añadido, aunque un autenticador técnicamente puede proporcionar un nombre de usuario completamente diferente para la identidad), y el grupo de acceso coincidirá, otorgando acceso completo.

Puede ser educativo considerar cómo combinar los ejemplos anteriores; los grupos generales siempre van primero. El orden de los grupos de autenticación en realidad no importa, ya que el que tiene "hosts: example.com" solo coincide con las conexiones antes de que se envíe el nombre de usuario/contraseña, y el que tiene "auth: ckpasswd" solo coincide después; el orden importaría si alguno de los grupos se aplicara a ambos casos. El orden de los grupos de acceso en este caso sí importa, siempre que las líneas de newsgroups difieran; el grupo de acceso sin línea de users debe ir primero, con el grupo "users: <LOCAL>" después.

Aquí tienes un ejemplo de otro caso común: un servidor que solo permite conexiones de un dominio local y tiene una jerarquía adicional con restricciones de contraseña.

auth "example.com" {
    hosts: "*.example.com"
    auth: "ckpasswd -f <ruta.db en inn.conf>/newsusers"
    default: "anonymous"
}
access regular {
    newsgroups: "*,!example.restricted.*"
    addcanlockuser: none
}
access full {
    users: "*,!anonymous"
    newsgroups: *
}

En este ejemplo, los usuarios no autenticados obtienen la identidad "anonymous", que solo coincide con el primer grupo de acceso y, por lo tanto, no obtienen acceso a la jerarquía "example.restricted.*". No se deben generar elementos de bloqueo de cancelación específicos del usuario para usuarios anónimos. Cualquiera que se autentique utilizando una contraseña en el archivo newsusers obtiene acceso completo a todos los grupos. Sin embargo, ten en cuenta que el único bloque de autenticación se limita a los nombres de host en el dominio example.com; las conexiones fuera de ese dominio nunca tendrán permitido el acceso ni tendrán la oportunidad de autenticarse.

Esto es para una organización que tiene una jerarquía interna "example.*" solo disponible para usuarios de shell locales, que están en máquinas donde identd(8) es de confiar. Los usuarios de acceso telefónico deben proporcionar un nombre de usuario y una contraseña, que luego se verifica contra RADIUS. Finalmente, el personal administrativo (usuarios "joe" y "jane") pueden publicar en cualquier lugar (incluidos los grupos "example.admin.*" que son de solo lectura para todos los demás), y están exentos del filtro Perl. Como un giro adicional, las publicaciones de los usuarios de acceso telefónico tienen su campo de encabezado Sender reemplazado por su identidad autenticada.

Dado que esta organización tiene algunos grupos de noticias moderados internos, el personal administrativo también puede publicar mensajes con campos de encabezado Approved, pero otros usuarios no.

auth default {
    auth: "ckpasswd -f <ruta.db en inn.conf>/newsusers"
    default: <FAIL>
    default-domain: example.com
}
auth shell {
    hosts: *.shell.example.com
    res: ident
    auth: ckpasswd
    default: <FAIL>
    default-domain: shell.example.com
}
auth dialup {
    hosts: *.dialup.example.com
    auth: radius
    default: <FAIL>
    default-domain: dialup.example.com
}
access shell {
    users: *@shell.example.com
    read: *
    post: "*, !example.admin.*"
}
access dialup {
    users: *@dialup.example.com
    newsgroups: *,!example.*
    nnrpdauthsender: true
}
access other {
    users: "*@example.com, !<FAIL>@example.com"
    newsgroups: *,!example.*
}
access fail {
    users: "<FAIL>@*"
    newsgroups: !*
}
access admin {
    users: "joe@*,jane@*"
    newsgroups: *
    access: "RPA"
    perlfilter: false
}

Nótese el uso de diferentes dominios para separar fácilmente a los usuarios de acceso telefónico de los de shell. Otra forma de hacerlo sería con parámetros key, pero esta forma proporciona cadenas de identidad ligeramente más intuitivas. Nótese también que el grupo de acceso fail captura no solo las conexiones fallidas de usuarios externos, sino también la autenticación fallida de usuarios de shell y de acceso telefónico antes de que se hayan autenticado. La cadena de identidad dada para, digamos, los usuarios de acceso telefónico antes de que se haya intentado la autenticación RADIUS coincide tanto con el grupo de acceso dialup como con el grupo de acceso fail, ya que es "<FAIL>@dialup.example.com", pero el grupo fail está al final, por lo que tiene precedencia.

El grupo de autenticación shell tiene un parámetro auth para que los usuarios "joe" y "jane" puedan, si lo desean, usar la autenticación de nombre de usuario y contraseña para obtener sus privilegios especiales incluso si han iniciado sesión como otro usuario en las máquinas shell (o si ident no está funcionando). Cuando se conectan por primera vez, tendrían el acceso predeterminado para ese usuario, pero luego podrían autenticarse para obtener su acceso extendido.

También nótese que si los usuarios "joe" y "jane" están usando sus propias cuentas, obtienen sus privilegios especiales independientemente de cómo se conecten, ya sea por acceso telefónico, máquinas shell, o incluso externamente con un nombre de usuario y contraseña.

Finalmente, aquí tienes un ejemplo muy simple de configuración para un servidor público para una jerarquía particular.

auth default {
    hosts: *
    default: <PUBLIC>
}
access default {
    users: <PUBLIC>
    newsgroups: example.*
    addcanlockuser: none
}

Se observa que a los clientes no se les permite leer ningún otro grupo; esto les impide acceder a grupos administrativos o leer mensajes de control, solo como precaución. Al ejecutar un servidor público como este, ten en cuenta que muchas jerarquías públicas se descargarán y se reinyectarán en el Usenet principal, por lo que se recomienda encarecidamente que también ejecutes un filtro Perl o Python para rechazar cualquier mensaje publicado fuera de tu jerarquía local, y cualquier mensaje que contenga un campo de encabezado Supersedes. Esto evitará que los mensajes publicados en tu jerarquía pública dañen el resto de Usenet si se filtran.

Para casos más complejos, o si simplemente prefieres usar una base de datos para almacenar información de autenticación y/o autorización, puedes usar scripts de Perl o Python para autenticar dinámicamente a los usuarios y/o generar sus bloques de acceso. Puedes entonces colocar toda la información relacionada (usuario, contraseña, grupos de noticias para lectura, grupos de noticias para publicación, etc.) por ejemplo en una base de datos SQLite, y usar un script nnrpd_auth.pl o nnrpd_auth.py para autenticar a los usuarios, y/o un script nnrpd_access.pl o nnrpd_access.py para otorgar el acceso. Entonces readers.conf solo necesita definirse:

auth checkcredentials {
    perl_auth: "/ruta/al/script/nnrpd_auth.pl"
    perl_access: "/ruta/al/script/nnrpd_access.pl"
}

o:

auth checkcredentials {
    python_auth: "nnrpd_auth"
    python_access: "nnrpd_access"
}

La ventaja de estos scripts externos es que puedes codificar las reglas que desees, posiblemente basándote en una base de datos compartida entre tu servicio de noticias y otros servicios que puedas ofrecer a tus usuarios. Puedes manejar más fácilmente cientos o miles de usuarios con scripts externos que con el simple uso de bloques estándar de readers.conf y un archivo plano para las credenciales de cada usuario listado.

CONSIDERACIONES DE SEGURIDAD

En general, se deben usar contraseñas separadas para NNTP siempre que sea posible; el protocolo NNTP en sí mismo no protege las contraseñas de intercepciones casuales, y muchas implementaciones (incluida esta) no "bloquean" cuentas ni disuaden de otra manera los ataques de adivinación de contraseñas. Por lo tanto, es mejor asegurarse de que una contraseña comprometida tenga efectos mínimos.

La autenticación mediante los comandos AUTHINFO USER/PASS se transmite sin cifrar a través de la red. Por lo tanto, se debe tener extrema precaución, especialmente con las contraseñas del sistema (por ejemplo, "auth: ckpasswd -s"). Las contraseñas se pueden proteger mediante NNTP sobre TLS/SSL o a través de túneles ssh, y este uso puede ser forzado por una configuración de servidor bien pensada que solo permita aplicar ciertos grupos de autenticación en ciertos casos. También se puede autenticar utilizando un mecanismo SASL robusto. Aquí hay algunas ideas:

  • Para restringir las conexiones en el puerto NNTP estándar (119) a usar una capa de cifrado para algunos (o todos) los grupos de autenticación a coincidir, use el parámetro require_encryption. Tenga en cuenta que un cliente puede usar STARTTLS para negociar una conexión TLS cifrada. También se puede negociar una capa segura durante la autenticación a través de AUTHINFO SASL.
  • Si considera que su red local (pero no Internet) es segura, tenga algunos grupos de autenticación con un parámetro hosts restrictivo; irían arriba, con los de aplicabilidad global debajo.
  • Considere ejecutar nnrpd con la bandera -S (ya sea también con -D, o desde un "super-servidor" como inetd) en el puerto NNTPS (563) para clientes que admiten TLS/SSL. Consulte nnrpd(8) para más detalles sobre cómo configurar eso. Puede usar el parámetro require_encryption o la bandera -c para especificar un archivo readers.conf alternativo si desea una configuración sustancialmente diferente para este caso.

IN A NUTSHELL

This file controls access to the news server for readers, including authentication and authorization.

DESCRIPTION

The readers.conf file is used by innd(8) and nnrpd(8) to control which remote news readers are allowed to connect to the server, and what they are allowed to do. It is located in the INN configuration directory (usually /etc/inn/).

The file consists of a series of directives, each on its own line. Lines starting with # are comments. Directives can be grouped into sections using auth and access keywords. These directives are described below.

AUTH GROUP PARAMETERS

The auth directive defines a group of authentication parameters. These parameters are used to determine how clients should authenticate themselves.

auth.default
Specifies the default authentication methods to try. This is a comma-separated list of authentication methods (e.g., auth.default: krb5, password).
auth.realm
Specifies the Kerberos realm to use for Kerberos authentication. This parameter is only relevant if Kerberos is one of the authentication methods.
auth.passwd-program
Specifies the program to use for password authentication. This program should accept a username on standard input and return the encrypted password on standard output. If this is not specified, password authentication is disabled.
auth.reject-message
Specifies the message to send to clients that are rejected. This can be a simple string or a reference to a file.

ACCESS GROUP PARAMETERS

The access directive defines a group of access control parameters. These parameters are used to determine whether a client is allowed to connect and what actions they are permitted to perform.

access.allow
Specifies a list of clients that are allowed to connect. This can be hostnames, IP addresses, or wildcards. Connections not matching any access.allow directive are denied.
access.deny
Specifies a list of clients that are denied access. This can be hostnames, IP addresses, or wildcards. Connections matching any access.deny directive are denied, even if they match an access.allow directive.
access.reject-message
Specifies the message to send to clients that are denied access.
access.max-connections
Specifies the maximum number of simultaneous connections allowed from a single client host.
access.localonly
If set to true, only connections originating from localhost (127.0.0.1) will be allowed for this group. This is useful for restricting access to local users or services.

SUMMARY

The readers.conf file allows administrators to finely control access to the news server. By combining auth and access directives, administrators can create complex access control policies that meet their specific security needs.

EXAMPLES

The following example allows connections from example.com and 192.168.1.0/24, requires Kerberos authentication, and denies access to all others.

auth.default: krb5
auth.realm: EXAMPLE.COM
access.allow: example.com
access.allow: 192.168.1.0/24

The following example allows only loopback connections (for users running newsreaders on localhost or connecting via an SSH tunnel) and uses the localaddress parameter.

auth.default: password
auth.passwd-program: /usr/lib/news/bin/ckpasswd
access.allow: 127.0.0.1
access.localonly: true

SECURITY CONSIDERATIONS

It is crucial to configure readers.conf carefully to prevent unauthorized access to the news server. Use strong authentication methods and restrict access to only trusted hosts and users. Be particularly careful when configuring password authentication, ensuring that the password program is secure and properly configured.

To restrict an auth group to only match loopback connections (for users running newsreaders on localhost or connecting via an SSH tunnel), use the localaddress parameter.
