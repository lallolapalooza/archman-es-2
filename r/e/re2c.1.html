NOMBRE

re2c - genera analizadores léxicos rápidos para C/C++

SINOPSIS

Nota: algunos ejemplos están en C++ (pero se pueden adaptar a C).

re2c [ OPCIONES ] [ ADVERTENCIAS ] ENTRADA

La entrada puede ser un archivo o - para la entrada estándar.

INTRODUCCIÓN

re2c funciona como un preprocesador. Lee el archivo de entrada (que es usualmente un programa en C/C++, pero puede ser cualquier cosa) y busca bloques de código encerrados en marcadores de inicio/fin de forma especial. El texto fuera de estos bloques se copia tal cual al archivo de salida. Los contenidos de los bloques son procesados por re2c. Los traduce a código en C/C++ y genera el código de salida en lugar del bloque.

Aquí hay un ejemplo de un pequeño programa que verifica si una cadena dada contiene un número decimal:

// re2c $INPUT -o $OUTPUT -i --case-ranges
#include <assert.h>
int lex(const char *s) {
    const char *YYCURSOR = s;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:define:YYCTYPE = char;
        [1-9][0-9]* { return 0; }
        *           { return 1; }
    */
}
int main() {
    assert(lex("1234") == 0);
    return 0;
}

En la salida, re2c reemplazó el bloque intermedio con el código generado:

/* Generado por re2c */
// re2c $INPUT -o $OUTPUT -i --case-ranges
#include <assert.h>
int lex(const char *s) {
    const char *YYCURSOR = s;
{
    char yych;
    yych = *YYCURSOR;
    switch (yych) {
        case '1' ... '9': goto yy2;
        default: goto yy1;
    }
yy1:
    ++YYCURSOR;
    { return 1; }
yy2:
    yych = *++YYCURSOR;
    switch (yych) {
        case '0' ... '9': goto yy2;
        default: goto yy3;
    }
yy3:
    { return 0; }
}
}
int main() {
    assert(lex("1234") == 0);
    return 0;
}

BÁSICOS

Un programa re2c consiste en una secuencia de bloques entremezclados con código en el lenguaje de destino. Un bloque puede contener definiciones, configuraciones, reglas, acciones y directivas en cualquier orden:

nombre = expresión-regular ;
Una definición vincula nombre con expresión-regular. Los nombres pueden contener caracteres alfanuméricos y guion bajo. La sección expresiones regulares ofrece una descripción general de la sintaxis de re2c para expresiones regulares. Una vez definido, el nombre puede ser utilizado en otras expresiones regulares y en reglas. La recursión en definiciones nombradas no está permitida, y cada nombre debe ser definido antes de ser utilizado. Un bloque hereda definiciones nombradas del ámbito global. Redefinir un nombre que existe en el ámbito actual es un error.
configuración = valor ;
Una configuración permite cambiar el comportamiento de re2c y personalizar el código generado. Para una lista completa de configuraciones soportadas por re2c, consulte la sección de configuraciones. Dependiendo de la configuración particular, el valor puede ser una palabra clave, un número entero no negativo o una cadena de una sola línea que debe ir entre comillas dobles o simples, a menos que consista en caracteres alfanuméricos. Un bloque hereda configuraciones del ámbito global y puede redefinirlas o agregar nuevas. Las configuraciones definidas dentro de un bloque afectan a todo el bloque, incluso si aparecen al final del mismo.
expresión-regular código
Una regla vincula expresión-regular a su acción semántica (un bloque de código entre llaves, o un bloque de código que comienza con := y termina en una nueva línea seguida de cualquier carácter no blanco). Si la expresión-regular coincide, el código asociado se ejecuta. Si coinciden múltiples reglas, la coincidencia más larga tiene precedencia. Si múltiples reglas coinciden con la misma cadena, la más temprana tiene precedencia. Hay dos reglas especiales: la regla por defecto * y la regla de fin de entrada $. La regla por defecto siempre debe definirse, tiene la menor prioridad independientemente de su lugar en el bloque, y coincide con cualquier unidad de código (no necesariamente un carácter válido, vea la sección de soporte de codificación). La regla de fin de entrada debe definirse si se utiliza el método correspondiente para el manejo del fin de entrada. Con los estados de inicio, las reglas tienen una sintaxis más compleja.
!acción código
Una acción vincula un bloque de código definido por el usuario a un lugar particular en la máquina de estados finitos generada (de la misma manera que las acciones semánticas vinculan código a los estados finales). Vea la sección de acciones para una lista completa de acciones predefinidas.
!directiva ;
Una directiva es una de las sentencias predefinidas especiales. Cada directiva tiene un propósito único. Consulte la sección de directivas para obtener más detalles.

Bloques

Los marcadores de inicio y fin de bloque son /*!re2c y */, o %{ y %} (ambos estilos son soportados). A partir de la versión 2.2, los bloques pueden tener nombres opcionales que permiten referenciarlos en otros bloques. Hay diferentes tipos de bloques:

/*!re2c[:<nombre>] ... */ o %{[:<nombre>] ... %}
Un bloque global contiene definiciones, configuraciones, reglas y directivas. re2c compila las expresiones regulares asociadas con cada regla en un autómata finito determinista, lo codifica en forma de saltos condicionales en el lenguaje de destino y reemplaza el bloque con el código generado. Los nombres y configuraciones definidos en un bloque global se agregan al ámbito global y se vuelven visibles para los bloques subsecuentes. Al inicio del programa, el ámbito global se inicializa con las opciones de la línea de comandos.
/*!local:re2c[:<nombre>] ... */ o %{local[:<nombre>] ... %}
Un bloque local es como un bloque global, pero los nombres y configuraciones en él tienen ámbito local (no afectan a otros bloques).
/*!rules:re2c[:<nombre>] ... */ o %{rules[:<nombre>] ... %}
Un bloque de reglas es como un bloque local, pero no genera ningún código por sí mismo, ni agrega definiciones al ámbito global, sino que está destinado a ser reutilizado en otros bloques. Esta es una forma de compartir código (más detalles en la sección de bloques reutilizables). Antes de la versión 2.2 de re2c, los bloques de reglas requerían la opción -r --reusable.
/*!use:re2c[:<nombre>] ... */ o %{use[:<nombre>] ... %}
Un bloque de uso que hace referencia a un bloque de reglas definido previamente. Si se especifica el nombre, re2c busca bloques de reglas con ese nombre. De lo contrario, se utiliza el bloque de reglas más reciente (ya sea uno con nombre o sin él). Un bloque de uso puede agregar sus propias definiciones, configuraciones y reglas, que se agregan a las del bloque de reglas referenciado. Antes de la versión 2.2 de re2c, los bloques de uso requerían la opción -r --reusable.
/*!max:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{max[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXFILL. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXFILL (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macro-definición para C (#define YYMAXFILL <n>), o una variable global para Go (var YYMAXFILL int = <n>). Puede personalizarse con una configuración opcional format que especifica una cadena de plantilla donde @@{max} (o @@ para abreviar) se reemplaza con el valor numérico de YYMAXFILL.
/*!maxnmatch:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{maxnmatch[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera la definición YYMAXNMATCH (requiere la opción -P --posix-captures). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el valor de YYMAXNMATCH (si la lista está vacía, se incluyen todos los bloques). Por defecto, el código generado es una macro-definición para C (#define YYMAXNMATCH <n>), o una variable global para Go (var YYMAXNMATCH int = <n>). Bloques

Los bloques de código para re2c se definen usando comentarios especiales con la sintaxis de C/C++. Hay dos tipos de bloques: aquellos que son procesados por re2c y aquellos que son ignorados. Los bloques procesados por re2c se identifican por la cadena `re2c` o `tags` que sigue inmediatamente al comentario especial. Si la cadena `re2c` o `tags` está presente, el contenido del bloque se procesa de acuerdo con las directivas de re2c. Si no está presente, el contenido se ignora y se elimina del archivo de salida.

/*!stags:re2c[:<nombre1>[:<nombre2>...]] ... */, /*!mtags:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{stags[:<nombre1>[:<nombre2>...]] ... %}, %{mtags[:<nombre1>[:<nombre2>...]] ... %{
Bloques que especifican una plantilla de código que se expande para cada variable de etiqueta s/m generada por re2c. Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el conjunto de variables de etiqueta (si la lista está vacía, se incluyen todos los bloques). Hay dos configuraciones opcionales: formato y separador. La configuración formato especifica una cadena plantilla donde @@{etiqueta} (o @@ para abreviar) se reemplaza con el nombre de cada variable de etiqueta. La configuración separador especifica un fragmento de código utilizado para unir los fragmentos de formato generados para diferentes variables de etiqueta.
/*!svars:re2c[:<nombre1>[:<nombre2>...]] ... */, /*!mvars:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{svars[:<nombre1>[:<nombre2>...]] ... %}, %{mvars[:<nombre1>[:<nombre2>...]] ... %{
Bloques que especifican una plantilla de código que se expande para cada etiqueta s/m que se menciona explícitamente en las reglas (con la opción --tags) o se genera implícitamente por re2c (con las opciones --captvars o --posix-captvars). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el conjunto de etiquetas (si la lista está vacía, se incluyen todas las etiquetas). Hay dos configuraciones opcionales: formato y separador. La configuración formato especifica una cadena plantilla donde @@{etiqueta} (o @@ para abreviar) se reemplaza con el nombre de cada etiqueta. La configuración separador especifica un fragmento de código utilizado para unir los fragmentos de formato generados para diferentes etiquetas.
/*!getstate:re2c[:<nombre1>[:<nombre2>...]] ... */ o %{getstate[:<nombre1>[:<nombre2>...]] ... %}
Un bloque que genera un desvío condicional según el estado del lexer (requiere la opción --storable-state). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse en el desvío de estado. La transición por defecto va a la etiqueta de inicio del primer bloque de la lista. Si la lista está vacía, se incluyen todos los bloques y la transición por defecto va al primer bloque en el archivo que tiene una etiqueta de inicio. Este tipo de bloque es incompatible con la opción --loop-switch, ya que requiere transiciones entre bloques que no son compatibles sin goto o llamadas a funciones.
/*!conditions:re2c[:<nombre1>[:<nombre2>...]] ... */, /*!types:re2c... */ o %{conditions[:<nombre1>[:<nombre2>...]] ... %}, %{types... %}
Un bloque que genera enumeración de condiciones (requiere la opción --conditions). Una lista opcional de nombres de bloques especifica qué bloques deben incluirse al calcular el conjunto de condiciones (si la lista está vacía, se incluyen todas las condiciones). Por defecto, el código generado es una enumeración YYCONDTYPE. Puede personalizarse con las configuraciones opcionales formato y separador. La configuración formato especifica una cadena plantilla donde @@{cond} (o @@ para abreviar) se reemplaza con el nombre de cada condición, y @@{num} se reemplaza con un índice numérico de esa condición. La configuración separador especifica un fragmento de código utilizado para unir los fragmentos de formato generados para diferentes condiciones.
/*!include:re2c <archivo> */ o %{include <archivo> %}
Este bloque permite incluir <archivo>, que debe ser una ruta de archivo entre comillas dobles. El contenido del archivo se sustituye literalmente en lugar del bloque, de la misma manera que funciona #include en C/C++. Este bloque se puede utilizar junto con la opción --depfile para generar dependencias del sistema de compilación en los archivos incluidos.
/*!header:re2c:on*/ o %{header:on %}
Este bloque marca el inicio de un archivo de cabecera. Todo lo que siga y hasta el siguiente bloque header:off será procesado por re2c y escrito en el archivo de cabecera especificado con la opción -t --type-header.
/*!header:re2c:off*/ o %{header:off %}
Este bloque marca el final de un archivo de cabecera iniciado con el bloque header:on*/.
/*!ignore:re2c ... */ o %{ignore ... %}
Un bloque cuyo contenido se ignora y se elimina del archivo de salida.

Configuraciones

Aquí hay una lista completa de las configuraciones admitidas por re2c:

re2c:api, re2c:input
Igual que la opción --api.
re2c:api:sigil
Especifica el marcador ("sigilo") que se utiliza para los marcadores de posición de argumentos en las primitivas de la API. El valor por defecto es @@. Un marcador de posición comienza con el sigilo seguido del nombre del argumento entre llaves. Por ejemplo, si el sigilo se establece en $, los marcadores de posición tendrán la forma ${nombre}. Las API de un solo argumento pueden usar notación abreviada sin el nombre entre llaves. Esta opción puede ser anulada por opciones para primitivas individuales de la API, por ejemplo, re2c:YYFILL@len para YYFILL.
re2c:api:style
Especifica el estilo de la API. Los valores posibles son functions (el valor por defecto para C) y free-form (el valor por defecto para Go y Rust). En el estilo functions, las primitivas de la API se generan con una lista de argumentos entre paréntesis después del nombre de la primitiva. Los argumentos solo se proporcionan para parámetros autogenerados (como el número de caracteres pasados a YYFILL), pero no para el contexto general del lexer, por lo que las primitivas se comportan más como macros en C/C++ o closures en Go y Rust. En el estilo free-form, las primitivas de la API no tienen una forma fija: deben definirse como cadenas que contienen fragmentos de código de forma libre con variables interpoladas de la forma @@{var} o @@ (corresponden a argumentos en el estilo similar a funciones). Esta configuración puede ser anulada para primitivas individuales de la API, ver por ejemplo la configuración re2c:YYFILL:naked para YYFILL.

Especifica la expresión utilizada para las variables de etiqueta. Por defecto, re2c genera expresiones de la forma yyt<N>. re2c:tags:negative
Especifica la expresión constante que se utiliza para el valor negativo de la etiqueta (normalmente sería -1 si las etiquetas son desplazamientos enteros en la cadena de entrada, o un puntero nulo si son punteros).

Operadores

Los siguientes operadores son reconocidos por re2c:

[[:digit:]]
Clase de caracteres (posiblemente negada).
.
Cualquier carácter excepto nueva línea.
R \ S
Diferencia de clases de caracteres R y S.
R*
Cero o más ocurrencias de R.
R+
Una o más ocurrencias de R.
R?
Opcional R.
R{n}
Repetición de R exactamente n veces.

Repetición de R al menos n veces.
R{n,m}
Repetición de R de n a m veces.
(R)
Simplemente R; los paréntesis se usan para anular la precedencia. Si se habilita la extracción de subcoincidencias, (R) es un grupo de captura o no captura dependiendo de la opción --invert-captures.
(!R)
Si se habilita la extracción de subcoincidencias, (!R) es un grupo no de captura o de captura dependiendo de la opción --invert-captures.

Alternativa: R o S.

Lookahead: R seguido de S, pero S no se consume.

Acciones

Aquí hay una lista de acciones predefinidas soportadas por re2c:

!entry code
La acción de entrada vincula un bloque definido por el usuario de code al estado de inicio de la máquina de estados finitos actual. Si se usan condiciones de inicio, la acción de entrada se puede establecer individualmente para cada condición. Esta acción puede usarse para realizar inicializaciones, por ejemplo, para guardar la ubicación de inicio de un léxico.
!pre_rule code
La acción pre-regla antepone un bloque de code definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se usan condiciones de inicio). Esta acción puede usarse para factorizar la parte común de todas las acciones semánticas (por ejemplo, guardar la ubicación final de un léxico).
!post_rule code
La acción post-regla añade un bloque de code definido por el usuario a las acciones semánticas de todas las reglas en el bloque actual (o condición, si se usan condiciones de inicio). Esta acción puede usarse para emitir sentencias de trampa que protejan contra flujos de control no intencionados.

Directivas

Aquí hay una lista completa de directivas soportadas por re2c:

!use:name ;
Una directiva de uso dentro de un bloque que fusiona un bloque de reglas definido previamente con el nombre especificado name en el bloque actual. Las definiciones nombradas, configuraciones y reglas del bloque referenciado se agregan a las actuales. Los conflictos entre reglas y configuraciones superpuestas se resuelven de la manera habitual: la primera regla tiene prioridad, y la última configuración anula las anteriores. Una excepción son las reglas especiales *, $ y <!> para las cuales una definición local del bloque siempre tiene prioridad. Una directiva de uso puede colocarse en cualquier lugar dentro de un bloque, y se permiten múltiples directivas de uso.
!include file ;
Esta directiva es la misma que el bloque include: inserta el contenido de file literalmente en el lugar de la directiva.

Interfaz del Programa

El código generado interactúa con el programa externo con la ayuda de primitivas, denominadas colectivamente API. Qué primitivas deben definirse para un programa particular depende de múltiples factores, incluyendo la complejidad de las expresiones regulares, la representación de entrada, el almacenamiento en búfer y el uso de varias características. Todas las primitivas necesarias deben ser definidas por el usuario en forma de macros, funciones, variables o cualquier otra forma adecuada que haga que el código generado sea sintácticamente y semánticamente correcto. re2c no (y no puede) verificar las definiciones, por lo que si algo falta o está definido incorrectamente, el programa generado puede tener errores de compilación o tiempo de ejecución. Este manual proporciona ejemplos de definiciones de API en los casos más comunes.

re2c tiene tres sabores de API que definen el conjunto central de primitivas utilizadas por un programa:

API Simple
Esta es la API predeterminada para el backend de C/C++. Consiste en las primitivas YYCURSOR, YYMARKER, YYCTXMARKER y YYLIMIT, que deben definirse como punteros de tipo YYCTYPE*.
API Record
(añadida en la versión 4.0) La API Record es útil en casos donde el estado del lexer debe almacenarse en una estructura. Se habilita con la opción --api record o la configuración re2c:api = record. Esta API consiste en una variable yyrecord (el nombre puede ser anulado con re2c:yyrecord) que debe definirse como una estructura con los campos yycursor, yymarker, yyctxmarker, yylimit (solo los campos utilizados por el código generado deben definirse, y sus nombres pueden configurarse).
API Genérica
(añadida en la versión 0.14) Esta es la API más flexible. Se habilita con la opción --api generic o la configuración re2c:api = generic. Esta API contiene primitivas para operaciones genéricas: YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN. La API Genérica soporta dos estilos que determinan la forma en que deben definirse las primitivas:
Forma Libre
El estilo de forma libre se habilita con la configuración re2c:api:style = free-form. En este estilo, las primitivas de la interfaz deben definirse como fragmentos de código de forma libre con variables interpoladas de la forma @@{var} o, opcionalmente, solo @@ si hay una sola variable. El conjunto de variables es específico para cada primitiva. Aquí se muestra cómo se puede definir la API genérica de forma libre en términos de punteros cursor, limit, marker y ctxmarker: 
/*!re2c
  re2c:YYPEEK       = "*cursor";
  re2c:YYSKIP       = "++cursor;";
  re2c:YYBACKUP     = "marker = cursor;";
  re2c:YYRESTORE    = "cursor = marker;";
  re2c:YYBACKUPCTX  = "ctxmarker = cursor;";
  re2c:YYRESTORECTX = "cursor = ctxmarker;";
  re2c:YYRESTORETAG = "cursor = ${tag};";
  re2c:YYLESSTHAN   = "limit - cursor < @@{len}";
  re2c:YYSTAGP      = "@@{tag} = cursor;";
  re2c:YYSTAGN      = "@@{tag} = NULL;";
  re2c:YYSHIFT      = "cursor += @@{shift};";
  re2c:YYSHIFTSTAG  = "@@{tag} += @@{shift};";
*/
Similar a Función
Históricamente, el estilo similar a función es el predeterminado. También se puede habilitar con la configuración re2c:api:style = functions. En este estilo, las primitivas deben definirse como funciones o macros con paréntesis, aceptando los argumentos necesarios. Aquí se muestra cómo se puede definir la API genérica similar a función en términos de punteros cursor, limit, marker y ctxmarker usando macros del preprocesador: 
#define  YYPEEK()                 *cursor
#define  YYSKIP()                 ++cursor
#define  YYBACKUP()               marker = cursor
#define  YYRESTORE()              cursor = marker
#define  YYBACKUPCTX()            ctxmarker = cursor
#define  YYRESTORECTX()           cursor = ctxmarker
#define  YYRESTORETAG(tag)        cursor = tag
#define  YYLESSTHAN(len)          limit - cursor < len
#define  YYSTAGP(tag)             tag = cursor
#define  YYSTAGN(tag)             tag = NULL
#define  YYSHIFT(shift)           cursor += shift
#define  YYSHIFTSTAG(tag, shift)  tag += shift

Options

MANEJO DEL FIN DE LA ENTRADA

Uno de los principales problemas para el lexer es saber cuándo parar. Existen algunas condiciones de terminación:

  • el lexer puede coincidir con alguna regla (incluida la regla por defecto *) y llegar a un estado final
  • el lexer puede no coincidir con ninguna regla y llegar a un estado por defecto
  • el lexer puede llegar al final de la entrada

Las dos primeras condiciones terminan el lexer de forma "natural": llega a un estado sin transiciones salientes y la coincidencia se detiene automáticamente. La tercera condición, el fin de la entrada, es diferente: puede ocurrir en cualquier estado y el lexer debe ser capaz de manejarlo. La comprobación del fin de la entrada interrumpe el flujo de trabajo normal del lexer y añade ramas condicionales al programa generado, por lo tanto, es necesario minimizar el número de tales comprobaciones. re2c admite varios métodos para manejar el fin de la entrada. Cuál usar depende de la complejidad de las expresiones regulares, la necesidad de almacenamiento en búfer, las consideraciones de rendimiento y otros factores. Aquí tienes una lista de métodos:

  • Centinela. Este método elimina por completo la necesidad de comprobaciones de fin de entrada. Es simple y eficiente, pero se limita al caso en que existe un carácter "centinela" natural que nunca puede ocurrir en una entrada válida. Este carácter aún puede ocurrir en una entrada inválida, pero no debe ser permitido por las expresiones regulares, excepto quizás como el último carácter de una regla. El centinela se añade al final de la entrada y sirve como señal de parada: cuando el lexer lee este carácter, es un error de sintaxis o el fin de la entrada. En ambos casos, el lexer debe detenerse. Este método se utiliza si YYFILL está deshabilitado con re2c:yyfill:enable = 0; y re2c:eof tiene el valor por defecto -1.
  • Centinela con comprobaciones de límites. Este método es genérico: permite manejar cualquier entrada sin restricciones en las expresiones regulares. La idea es reducir el número de comprobaciones de fin de entrada realizándolas solo en ciertos caracteres. Similar al método "centinela", se elige uno de los caracteres como "centinela" y se añade al final de la entrada. Sin embargo, no hay restricciones sobre dónde puede ocurrir el centinela (de hecho, cualquier carácter puede ser elegido como centinela). Cuando el lexer lee este carácter, realiza adicionalmente una comprobación de límites. Si la posición actual está dentro de los límites, el lexer reanuda la coincidencia y maneja el centinela como un carácter normal. De lo contrario, invoca YYFILL (a menos que esté deshabilitado). Si se proporciona más entrada, el lexer volverá a coincidir con el último carácter y continuará como si el centinela no estuviera allí. De lo contrario, debe ser el fin real de la entrada y el lexer se detiene. Este método se utiliza cuando re2c:eof tiene un valor no negativo (debe establecerse en el valor numérico del centinela). YYFILL es opcional.
  • Comprobaciones de límites con relleno. Este método es genérico y puede ser más rápido que el método "centinela con comprobaciones de límites", pero también es más complejo. La idea es particionar los estados del DFA en componentes fuertemente conectados (SCC) y generar una sola comprobación por SCC para suficientes caracteres para cubrir el camino no bucle más largo en esa SCC. Esto reduce el número de comprobaciones, pero hay un problema con los lexemas cortos al final de la entrada, ya que la comprobación requiere suficientes caracteres para cubrir el lexema más largo. Esto se puede solucionar rellenando la entrada con algunos caracteres falsos que no forman un sufijo de lexema válido (para que el lexer no pueda coincidir con ellos). La longitud del relleno debe ser YYMAXFILL, generada con un bloque max. Si no hay suficiente entrada, el lexer invoca YYFILL, que debería proporcionar al menos el número requerido de caracteres o no devolver nada. Este método se utiliza si YYFILL está habilitado y re2c:eof es -1 (esta es la configuración por defecto).
  • Comprobaciones personalizadas. La API genérica permite anular operaciones básicas como la lectura de un carácter, lo que hace posible incluir las comprobaciones de fin de entrada como parte de ellas. Este enfoque es propenso a errores y debe usarse con precaución. Para usar un método personalizado, habilite la API genérica con --api custom o re2c:api = custom; y deshabilite las comprobaciones de límites por defecto con re2c:yyfill:enable = 0; o re2c:yyfill:check = 0;.

Las siguientes subsecciones contienen un ejemplo de cada método.

Centinela

Este ejemplo utiliza un carácter centinela para manejar el fin de la entrada. El programa cuenta palabras separadas por espacios en una cadena nula terminada. El centinela es nulo: es el último carácter de cada cadena de entrada, y no está permitido en medio de un lexema por ninguna de las reglas (en particular, no está incluido en los rangos de caracteres donde es fácil pasarlo por alto). Si aparece un nulo en medio de una cadena, es un error de sintaxis y el lexer coincidirá con la regla por defecto *, pero no leerá más allá del final de la entrada ni fallará (use la advertencia -Wsentinel-in-midrule y la configuración re2c:sentinel para verificar esto). La configuración re2c:yyfill:enable = 0; suprime la generación de comprobaciones de límites e invocaciones de YYFILL.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
// Espera una cadena terminada en nulo.
static int lex(const char *YYCURSOR) {
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:define:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        *      { return -1; }
        [\x00] { return count; }
        [a-z]+ { ++count; continue; }
        [ ]+   { continue; }
    */
    }
}
int main() {
    assert(lex("") == 0);
    assert(lex("one two three") == 3);
    assert(lex("f0ur") == -1);
    return 0;
}

Centinela con comprobaciones de límites

Este ejemplo utiliza el centinela con comprobaciones de límites para manejar el fin de la entrada (este método se añadió en la versión 1.2). El programa cuenta cadenas de un solo comilla separadas por espacios. El carácter centinela es nulo, lo cual se especifica con la configuración re2c:eof = 0;. Al igual que en el método centinela, el nulo es el último carácter de cada cadena de entrada

, pero se permite en medio de una regla (por ejemplo, 'aaa\0aa'\0 es una entrada válida, pero 'aaa\0 es un error de sintaxis). Las comprobaciones de límites se generan en cada estado que coincide con un carácter de entrada, pero se limitan a la rama que maneja el nulo. Las comprobaciones de límites son de la forma YYLIMIT <= YYCURSOR o YYLESSTHAN(1) con API genérica. Si la condición de comprobación es verdadera, el lexer ha llegado al final de la entrada y debe detenerse (YYFILL se deshabilita con re2c:yyfill:enable = 0; ya que la entrada cabe en un solo búfer, vea la sección YYFILL con centinela para ver un ejemplo que usa YYFILL). Llegar al final de la entrada abre tres posibilidades: si el lexer está en el estado inicial, coincidirá con la regla de fin de entrada $, de lo contrario, puede retroceder a una regla previamente coincidida (incluida la regla predeterminada *) o ir a un estado predeterminado, causando -Wundefined-control-flow.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
// Espera una cadena terminada en nulo.
static int lex(const char *str, unsigned int len) {
    const char *YYCURSOR = str, *YYLIMIT = str + len, *YYMARKER;
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:define:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1; }
        $    { return count; }
        str  { ++count; continue; }
        [ ]+ { continue; }
    */
    }
}
#define TEST(s, r) assert(lex(s, sizeof(s) - 1) == r)
int main() {
    TEST("", 0);
    TEST("'qu\0tes' 'are' 'fine: \\'' ", 3);
    TEST("'unterminated\\'", -1);
    return 0;
}

Comprobaciones de límites con relleno

Este ejemplo utiliza comprobaciones de límites con relleno para manejar el final de la entrada (este método está habilitado por defecto). El programa cuenta cadenas entre comillas simples separadas por espacios. Hay un relleno de YYMAXFILL caracteres nulos añadidos al final de la entrada, donde el valor YYMAXFILL se autogenera con un bloque max. No es necesario utilizar nulo para el relleno; se pueden usar caracteres siempre que no formen un sufijo léxico válido (en este ejemplo, el relleno no debe contener comillas simples, ya que podrían confundirse con un sufijo de una cadena entre comillas simples). Hay una regla de "parada" que coincide con el primer carácter de relleno (nulo) y termina el lexer (tenga en cuenta que comprueba si el nulo está al principio del relleno, de lo contrario es un error de sintaxis). Las comprobaciones de límites se generan solo en algunos estados que se determinan por los componentes fuertemente conectados del autómata subyacente. Las comprobaciones tienen la forma (YYLIMIT - YYCURSOR) < n o YYLESSTHAN(n) con API genérica, donde n es el número mínimo de caracteres que se necesitan para que el lexer continúe (esto también significa que la próxima comprobación de límites ocurrirá en como máximo n caracteres). Si la condición de comprobación es verdadera, el lexer ha llegado al final de la entrada y llamará a YYFILL(n), que debería proporcionar al menos n caracteres de entrada o no devolver nada. En este ejemplo, YYFILL siempre falla y termina el lexer con un error (lo cual está bien porque la entrada cabe en un solo búfer). Vea la sección YYFILL con relleno para ver un ejemplo que rellena el búfer de entrada con YYFILL.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
#include <stdlib.h>
#include <string.h>
/*!max:re2c*/
static int lex(const char *str, unsigned int len) {
    // Copia la cadena con YYMAXFILL ceros al final.
    char *buf = (char*) malloc(len + YYMAXFILL);
    memcpy(buf, str, len);
    memset(buf + len, 0, YYMAXFILL);
    const char *YYCURSOR = buf, *YYLIMIT = buf + len + YYMAXFILL;
    int count = 0;
loop:
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYFILL = "goto fail;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Comprueba que sea el centinela, no un nulo inesperado.
            if (YYCURSOR - 1 == buf + len) goto exit; else goto fail;
        }
        str  { ++count; goto loop; }
        [ ]+ { goto loop; }
        *    { goto fail; }
    */
fail:
    count = -1;
exit:
    free(buf);
    return count;
}
#define TEST(s, r) assert(lex(s, sizeof(s) - 1) == r)
int main() {
    TEST("", 0);
    TEST("'qu\0tes' 'are' 'fine: \\'' ", 3);
    TEST("'unterminated\\'", -1);
    TEST("'unexpected \0 null\\'", -1);
    return 0;
}

Comprobaciones personalizadas

Este ejemplo utiliza un método personalizado de manejo del final de entrada basado en la API genérica. El programa cuenta cadenas entre comillas simples separadas por espacios. Es lo mismo que el ejemplo de centinela, excepto que la entrada no está terminada en nulo. Para compensar la ausencia de un carácter centinela al final de la entrada, YYPEEK se redefine para realizar una comprobación de límites antes de leer el siguiente carácter de entrada. Esto es ineficiente porque las comprobaciones se realizan con mucha frecuencia. Si la condición de comprobación falla, YYPEEK devuelve el carácter real, de lo contrario devuelve un carácter centinela falso.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
#include <stdlib.h>
#include <string.h>
static int lex(const char *str, unsigned int len) {
    // Por el bien del ejemplo, crea una cadena sin nulo terminador.
    char *buf = (char*) malloc(len);
    memcpy(buf, str, len);
    const char *cur = buf, *lim = buf + len;
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:api = custom;
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYPEEK = "cur < lim ? *cur : 0";  // centinela falso
        re2c:define:YYSKIP = "++cur;";
        *      { count = -1; break; }
        [\x00] { break;; }
        [a-z]+ { ++count; continue;; }
        [ ]+   { continue; }
    */
    }
    free(buf);
    return count;
}
#define TEST(s, r) assert(lex(s, sizeof(s) - 1) == r)
int main() {
    TEST("", 0);
    TEST("one two three ", 3);
    TEST("f0ur", -1);
    return 0;
}

RELLENO DE BUFFER

La necesidad de buffering surge cuando la entrada no se puede mapear en memoria a la vez: o bien es demasiado grande, o bien proviene de forma secuencial (como leer de un socket). La técnica habitual en tales casos es asignar un búfer de memoria de tamaño fijo y procesar la entrada en fragmentos que quepan en el búfer. Cuando el fragmento actual se procesa, se aparta y se introducen nuevos datos. En la práctica, es algo más complejo, porque el estado del lexer consiste no en una sola posición de entrada, sino en un conjunto de posiciones interrelacionadas:

  • cursor: el siguiente carácter de entrada a leer (YYCURSOR en la API de puntero C o YYSKIP/YYPEEK en la API genérica)
  • límite: la posición después del último carácter de entrada disponible (YYLIMIT en la API de puntero C, manejado implícitamente por YYLESSTHAN en la API genérica)
  • marcador: la posición de la coincidencia más reciente, si la hay (YYMARKER en la API predeterminada o YYBACKUP/YYRESTORE en la API genérica)
  • token: el inicio del lexema actual (implícito en la API re2c, ya que no es necesario para la operación normal del lexer y puede ser definido y actualizado por el usuario)
  • marcador de contexto: la posición del contexto de cola (YYCTXMARKER en la API de puntero C o YYBACKUPCTX/YYRESTORECTX en la API genérica)
  • variables de etiqueta: posiciones de subcoincidencia (definidas con bloques stags y mtags y primitivas de API genérica YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

No todos estos se utilizan en todos los casos, pero si se utilizan, deben ser actualizados por YYFILL. Todas las posiciones activas están contenidas en el segmento entre el token y el cursor, por lo tanto, todo lo que está entre el inicio del búfer y el token se puede descartar, el segmento desde el token hasta el límite se debe mover al principio del búfer, y el espacio libre al final del búfer se debe llenar con nuevos datos. Para evitar llamadas frecuentes a YYFILL, es mejor llenar tantos caracteres de entrada como sea posible (aunque puedan ser suficientes menos caracteres para reanudar el lexer). Los detalles de la implementación de YYFILL son ligeramente diferentes dependiendo de qué método de manejo de EOF se utilice: el caso de la regla EOF es algo más sencillo que el caso de las comprobaciones de límites con relleno. Tenga en cuenta también que si se utiliza la opción -f --storable-state, YYFILL tiene una semántica ligeramente diferente (descrita en la sección sobre estado almacenable).

YYFILL con centinela

Si se utiliza la regla EOF, YYFILL es una primitiva similar a una función que no acepta argumentos y devuelve un valor que se comprueba frente a cero. La invocación de YYFILL se activa mediante la condición YYLIMIT <= YYCURSOR en la API de puntero C y YYLESSTHAN() en la API genérica. Un valor de retorno distinto de cero significa que YYFILL ha fallado. Una llamada exitosa a YYFILL debe proporcionar al menos un carácter y ajustar las posiciones de entrada en consecuencia. El límite siempre debe establecerse una posición después de la última posición de entrada en el búfer, y el carácter en la posición límite debe ser el símbolo centinela especificado por la configuración re2c:eof. Las figuras a continuación muestran la ubicación relativa de las posiciones de entrada en el búfer antes y después de la llamada a YYFILL (el símbolo centinela está marcado con #, y la segunda imagen muestra el caso en que no hay suficiente entrada para llenar todo el búfer).

             búfer        token    marcador         límite,
                                                  cursor
>-A------------B---------C-------------D------------E#->

             token
               <-- desplazamiento -->
             >-A------------B---------C-------------D#--E

Aquí hay un ejemplo de un programa que lee el archivo de entrada input.txt en fragmentos de 4096 bytes y utiliza la regla EOF.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
#include <stdio.h>
#include <string.h>
#define BUFSIZE 4095
typedef struct {
    FILE *file;
    char buf[BUFSIZE + 1], *lim, *cur, *mar, *tok; // +1 para el centinela
    int eof;
} Input;
static int fill(Input *in) {
    if (in->eof) return 1;
    const size_t shift = in->tok - in->buf;
    const size_t used = in->lim - in->tok;
    // Error: lexeme too long. In real life could reallocate a larger buffer.
    if (shift < 1) return 2;
    // Shift buffer contents (discard everything up to the current token).
    memmove(in->buf, in->tok, used);
    in->lim -= shift;
    in->cur -= shift;
    in->mar -= shift;
    in->tok -= shift;
    // Fill free space at the end of buffer with new data from file.
    in->lim += fread(in->lim, 1, BUFSIZE - used, in->file);
    in->lim[0] = 0;
    in->eof = in->lim < in->buf + BUFSIZE;
    return 0;
}
static int lex(Input *in) {
    int count = 0;
loop:
        in->tok = in->cur;
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYCURSOR = in->cur;
        re2c:define:YYMARKER = in->mar;
        re2c:define:YYLIMIT = in->lim;
        re2c:define:YYFILL = "fill(in) == 0";
        re2c:eof = 0;
        str = ['\] ([^'\\] | [\\][^])* ['\];
        *    { return -1; }
        $    { return count; }
        str  { ++count; goto loop; }
        [ ]+ { goto loop; }
    */
}
int main() {
    const char *fname = "input";
    const char content[] = "'qu\0tes' 'are' 'fine: \\'' ";
    // Prepare input file: a few times the size of the buffer, containing
    // strings with zeroes and escaped quotes.
    FILE *f = fopen(fname, "w");
    for (int i = 0; i < BUFSIZE; ++i) {
        fwrite(content, 1, sizeof(content) - 1, f);
    }
    fclose(f);
    int count = 3 * BUFSIZE; // number of quoted strings written to file
    // Initialize lexer state: all pointers are at the end of buffer.
    Input in;
    in.file = fopen(fname, "r");
    in.cur = in.mar = in.tok = in.lim = in.buf + BUFSIZE;
    in.eof = 0;
    // Sentinel (at YYLIMIT pointer) is set to zero, which triggers YYFILL.
    in.lim[0] = 0;
    // Run the lexer.
    assert(lex(&in) == count);
    // Cleanup: remove input file.
    fclose(in.file);
    remove(fname);
    return 0;
}

## YYFILL with padding

In the default case (when EOF rule is not used) **YYFILL** is a function-like primitive that accepts a single argument and does not return any value. **YYFILL** invocation is triggered by condition **(YYLIMIT - YYCURSOR) < n** in C pointer API and **YYLESSTHAN(n)** in generic API. The argument passed to **YYFILL** is the minimal number of characters that must be supplied. If it fails to do so, **YYFILL** must not return to the lexer (for that reason it is best implemented as a macro that returns from the calling function on failure). In case of a successful **YYFILL** invocation the limit position must be set either to one after the last input position in buffer, or to the end of **YYMAXFILL** padding (in case **YYFILL** has successfully read at least **n** characters, but not enough to fill the entire buffer). The pictures below show the relative locations of input positions in buffer before and after **YYFILL** invocation (**YYMAXFILL** padding on the second picture is marked with **#** symbols).

```text
               <-- shift -->                 <-- need -->
             >--A------------B---------C-----D-------E---F--------G-->
             buffer       token    marker cursor  limit
>--A------------B---------C-----D-------E---F--------G-->
             buffer,  marker cursor               limit
             token
               <-- shift -->                 <-- need -->
             >--A------------B---------C-----D-------E-F        (EOF)
             buffer       token    marker cursor  limit
>--A------------B---------C-----D-------E-F###############
             buffer,  marker cursor                   limit
             token                        <- YYMAXFILL ->
```

Here is an example of a program that reads input file **input.txt** in chunks of 4096 bytes and uses bounds-checking with padding.

```c
// re2c $INPUT -o $OUTPUT
#include 
#include 
#include 
/*!max:re2c*/
#define BUFSIZE (4096 - YYMAXFILL)
typedef struct {
    FILE *file;
    char buf[BUFSIZE + YYMAXFILL], *lim, *cur, *tok;
    int eof;
} Input;
static int fill(Input *in, size_t need) {
    if (in->eof) return 1;
    const size_t shift = in->tok - in->buf;
    const size_t used = in->lim - in->tok;
    // Error: lexeme too long. In real life could reallocate a larger buffer.
    if (shift < need) return 2;
    // Shift buffer contents (discard everything up to the current token).
    memmove(in->buf, in->tok, used);
    in->lim -= shift;
    in->cur -= shift;
    in->tok -= shift;
    // Fill free space at the end of buffer with new data from file.
    in->lim += fread(in->lim, 1, BUFSIZE - used, in->file);
    // If read less than expected, this is end of input => add zero padding
    // so that the lexer can access characters at the end of buffer.
    if (in->lim < in->buf + BUFSIZE) {
        in->eof = 1;
        memset(in->lim, 0, YYMAXFILL);
        in->lim += YYMAXFILL;
    }
    return 0;
}
static int lex(Input *in) {
    int count = 0;
loop:
        in->tok = in->cur;
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYCURSOR = in->cur;
        re2c:define:YYLIMIT = in->lim;
        re2c:define:YYFILL = "if (fill(in, @@) != 0) return -1;";
        str = ['\] ([^'\\] | [\\][^])* ['\];
        [\x00] {
            // Check that it is the sentinel, not some unexpected null.
            return in->tok == in->lim - YYMAXFILL ? count : -1;
        }
        str  { ++count; goto loop; }
        [ ]+ { goto loop; }
        *    { return -1; }
    */
}
int main() {
    const char *fname = "input";
    const char content[] = "'qu\0tes' 'are' 'fine: \\'' ";
    // Prepare input file: a few times the size of the buffer, containing
    // strings with zeroes and escaped quotes.
    FILE *f = fopen(fname, "w");
    for (int i = 0; i < BUFSIZE; ++i) {
        fwrite(content, 1, sizeof(content) - 1, f);
    }
    fclose(f);
    int count = 3 * BUFSIZE; // number of quoted strings written to file
    // Initialize lexer state: all pointers are at the end of buffer.
    // This immediately triggers YYFILL, as the check `in->cur < in->lim` fails.
    Input in;
    in.file = fopen(fname, "r");
    in.cur = in.tok = in.lim = in.buf + BUFSIZE;
    in.eof = 0;
    // Run the lexer.
    assert(lex(&in) == count);
    // Cleanup: remove input file.
    fclose(in.file);
    remove(fname);
    return 0;
}
```

# FEATURES

## Multiple blocks

Sometimes it is necessary to have multiple interrelated lexers (for example, if there is a high-level state machine that transitions between lexer modes). This can be implemented using multiple connected re2c blocks. Another option is to use *start conditions*.

The implementation of connections between blocks depends on the target language. In languages that have `goto` statement (such as C/C++ and Go) one can have all blocks in one function, each of them prefixed with a label. Transition from one block to another is a simple `goto`. In languages that do not have `goto` (such as Rust) it is necessary to use a loop with a switch on a state variable, similar to the `yystate` loop/switch generated by re2c, or else wrap each block in a function and use function calls.

The example below uses multiple blocks to parse binary, octal, decimal and hexadecimal numbers. Each base has its own block. The initial block determines base and dispatches to other blocks. Common configurations are defined in a separate block at the beginning of the program; they are inherited by the other blocks.

```c

#include 
#include 
static const uint64_t ERROR = UINT64_MAX;
#define CHECK(n) if (n > UINT32_MAX) return ERROR;
static uint64_t parse_u32(const char *s) {
    const char *YYCURSOR = s, *YYMARKER;
    uint64_t u = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:define:YYCTYPE = char;
        end = "\x00";
        '0b' / [01]        { goto bin; }
        "0"                { goto oct; }
        "" / [1-9]         { goto dec; }
        '0x' / [0-9a-fA-F] { goto hex; }
        *                  { return ERROR; }
    */
bin:
    /*!re2c
        end   { return u; }
        [01]  { u = u * 2 + (YYCURSOR[-1] - '0'); CHECK(u); goto bin; }
        *     { return ERROR; }
    */
oct:
    /*!re2c
        end   { return u; }
        [0-7] { u = u * 8 + (YYCURSOR[-1] - '0'); CHECK(u); goto oct; }
        *     { return ERROR; }
    */
dec:
    /*!re2c
        end   { return u; }
        [0-9] { u = u * 10 + (YYCURSOR[-1] - '0'); CHECK(u); goto dec; }
        *     { return ERROR; }
    */
hex:
    /*!re2c
        end   { return u; }
        [0-9] { u = u * 16 + (YYCURSOR[-1] - '0');      CHECK(u); goto hex; }
        [a-f] { u = u * 16 + (YYCURSOR[-1] - 'a' + 10); CHECK(u); goto hex; }
        [A-F] { u = u * 16 + (YYCURSOR[-1] - 'A' + 10); CHECK(u); goto hex; }
        *     { return ERROR; }
    */
}
int main() {
    assert(parse_u32("") == ERROR);
    assert(parse_u32("1234567890") == 1234567890);
    assert(parse_u32("0b1101") == 13);
    assert(parse_u32("0x7Fe") == 2046);
    assert(parse_u32("0644") == 420);
    assert(parse_u32("9999999999") == ERROR);
    return 0;
}
```

## Start conditions

Start conditions are enabled with **--start-conditions** option. They provide a way to encode multiple interrelated automata within the same re2c block.

Each condition corresponds to a single automaton and has a unique name specified by the user and a unique internal number defined by re2c. The numbers are used to switch between conditions: the generated code uses **YYGETCOND** and **YYSETCOND** primitives to get the current condition or set it to the given number. Use `conditions` block, **--header** option or `re2c:header` configuration to generate numeric condition identifiers. Configuration `re2c:cond:enumprefix` specifies the generated identifier prefix.

In condition mode every rule must be prefixed with a list of comma-separated condition names in angle brackets, or a wildcard **<*>** to denote all conditions. The rule syntax is extended as follows:

El código que re2c genera para las condiciones depende de si re2c utiliza el enfoque de `goto/etiqueta` o el enfoque de `bucle/switch` para codificar los autómatas.

En lenguajes que tienen la sentencia `goto` (como C/C++ y Go), las condiciones se implementan de forma natural como bloques de código prefijados con etiquetas del tipo `yyc_`, donde `` es el nombre de una condición (el prefijo de la etiqueta se puede cambiar con `re2c:cond:prefix`). Las transiciones entre condiciones se implementan usando `goto` y las etiquetas de condición. Antes de todas las condiciones, re2c genera un `switch` inicial en `YYGETSTATE` que salta al estado inicial de la condición actual. Las reglas de acceso directo `:=>` omiten el `switch` inicial y saltan directamente a la condición especificada (`re2c:cond:goto` se puede usar para cambiar el comportamiento predeterminado). Las reglas con acciones semánticas no saltan automáticamente a la siguiente condición; esto debe hacerlo el código de acción definido por el usuario.

En lenguajes que no tienen `goto` (como Rust), re2c reutiliza la variable `yystate` para almacenar los números de condición. Cada condición obtiene un identificador numérico igual al número de su estado inicial, y un `switch` entre condiciones no es diferente a un `switch` entre estados DFA de una sola condición. No hay necesidad de un `switch` de condición inicial separado. (Dado que se utiliza el mismo enfoque para implementar estados almacenables, `YYGETCOND`/`YYSETCOND` son redundantes si se utilizan tanto estados almacenables como condiciones).

El siguiente programa utiliza condiciones de inicio para analizar números binarios, octales, decimales y hexadecimales. Hay un solo bloque donde cada base tiene su propia condición, y la condición inicial está conectada a todas ellas. La variable definida por el usuario `cond` almacena el número de la condición actual; se inicializa al número de la condición inicial generada con el bloque `conditions`.

## Estado almacenable

Con la opción `--storable-state`, re2c genera un lexer que puede almacenar su estado actual, devolver el control al llamador y luego reanudar las operaciones exactamente donde las dejó. El modo de operación predeterminado en re2c es un modelo de "pull" (tirar), en el que el lexer "tira" de más entrada cuando la necesita. Esto puede ser inaceptable en casos en los que la entrada se vuelve disponible pieza por pieza (por ejemplo, si el lexer es invocado por el parser, o si el programa lexer se comunica a través de un protocolo de socket con algún otro programa que debe esperar una respuesta del lexer antes de transmitir el siguiente mensaje). La característica de estado almacenable está destinada precisamente a tales casos: permite generar lexers que funcionan en un modelo de "push" (empujar). Cuando el lexer necesita más entrada, almacena su estado y devuelve el control al llamador. Más tarde, cuando hay más entrada disponible, el llamador reanuda el lexer exactamente donde se detuvo. Hay algunos cambios necesarios en comparación con el modelo de "pull":

*   Definir las primitivas `YYSETSTATE()` y `YYGETSTATE(state)`.
*   Definir las variables `yych`, `yyaccept` (si se usa) y `state` como parte del estado persistente del lexer. La variable `state` debe inicializarse a `-1`.
*   `YYFILL` debe devolver el control al programa externo en lugar de intentar suministrar más entrada. El código de retorno debe indicar que el lexer necesita más entrada.
*   El programa externo debe reconocer las situaciones en las que el lexer necesita más entrada y responder de manera apropiada.
*   Opcionalmente, usar el bloque `getstate` para generar un `switch` de `YYGETSTATE` separado del lexer principal. Esto solo funciona para lenguajes que tienen `goto` (no en modo `--loop-switch`).
*   Usar `re2c:eof` y el método de *centinela con comprobaciones de límites* para manejar el final de la entrada. El método basado en relleno puede no funcionar porque no está claro cuándo añadir el relleno: el final actual de la entrada puede no ser el final definitivo de la entrada, y añadir relleno demasiado pronto puede cortar un lexema codicioso leído parcialmente. Además, debido a la lógica del programa de alto nivel, obtener más entrada puede depender del procesamiento del lexema al final del búfer (que ya está bloqueado debido a la condición de fin de entrada).

Aquí hay un ejemplo de un lexer de modelo "push" que simula la lectura de paquetes de un socket. El lexer se ejecuta en bucle hasta que encuentra el final de la entrada y devuelve el control a la función llamadora. La función llamadora proporciona más entrada "enviando" el siguiente paquete y reanuda el análisis léxico. Este proceso se detiene cuando se han enviado todos los paquetes, o cuando hay un error.

```c
// re2c $INPUT -o $OUTPUT -f
#include 
#include 
#include 
#define DEBUG 0
#define LOG(...) if (DEBUG) fprintf(stderr, __VA_ARGS__);
// Use a small buffer to cover the case when a lexeme doesn't fit.
// In real world use a larger buffer.
#define BUFSIZE 10
typedef struct {
    FILE *file;
    char buf[BUFSIZE + 1], *lim, *cur, *mar, *tok;
    int state;
} State;
typedef enum {END, READY, WAITING, BAD_PACKET, BIG_PACKET} Status;
static Status fill(State *st) {
    const size_t shift = st->tok - st->buf;
    const size_t used = st->lim - st->tok;
    const size_t free = BUFSIZE - used;
    // Error: no space. In real life can reallocate a larger buffer.
    if (free < 1) return BIG_PACKET;
    // Shift buffer contents (discard already processed data).
    memmove(st->buf, st->tok, used);
    st->lim -= shift;
    st->cur -= shift;
    st->mar -= shift;
    st->tok -= shift;
    // Fill free space at the end of buffer with new data.
    const size_t read = fread(st->lim, 1, free, st->file);
    st->lim += read;
    st->lim[0] = 0; // append sentinel symbol
    return READY;
}
static Status lex(State *st, unsigned int *recv) {
    char yych;
    /*!getstate:re2c*/
    for (;;) {
        st->tok = st->cur;
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = "char";
        re2c:define:YYCURSOR = "st->cur";
        re2c:define:YYMARKER = "st->mar";
        re2c:define:YYLIMIT = "st->lim";
        re2c:define:YYGETSTATE = "st->state";
        re2c:define:YYSETSTATE = "st->state = @@;";
        re2c:define:YYFILL = "return WAITING;";
        re2c:eof = 0;
        packet = [a-z]+[;];
        *      { return BAD_PACKET; }
        $      { return END; }
        packet { *recv = *recv + 1; continue; }
    */
    }
}
void test(const char **packets, Status expect) {
    // Create a "socket" (open the same file for reading and writing).
    const char *fname = "pipe";
    FILE *fw = fopen(fname, "w");
    FILE *fr = fopen(fname, "r");
    setvbuf(fw, NULL, _IONBF, 0);
    setvbuf(fr, NULL, _IONBF, 0);
    // Initialize lexer state: `state` value is -1, all pointers are at the end
    // of buffer.
    State st;
    st.file = fr;
    st.cur = st.mar = st.tok = st.lim = st.buf + BUFSIZE;
    // Sentinel (at YYLIMIT pointer) is set to zero, which triggers YYFILL.
    st.lim[0] = 0;
    st.state = -1;
    // Main loop. The buffer contains incomplete data which appears packet by
    // packet. When the lexer needs more input it saves its internal state and
    // returns to the caller which should provide more input and resume lexing.
    Status status;
    unsigned int send = 0, recv = 0;
    for (;;) {
        status = lex(&st, &recv);
        if (status == END) {
            LOG("done: got %u packets\n", recv);
            break;
        } else if (status == WAITING) {
            LOG("waiting...\n");
            if (*packets) {
LOG("sent packet %u\n", send);
fprintf(fw, "%s", *packets++);
++send;
}
status = fill(&st);
LOG("queue: '%s'\n", st.buf);
if (status == BIG_PACKET) {
    LOG("error: packet too big\n");
    break;
}
assert(status == READY);
} else {
    assert(status == BAD_PACKET);
    LOG("error: ill-formed packet\n");
    break;
}
}
// Check results.
assert(status == expect);
if (status == END) assert(recv == send);
// Cleanup: remove input file.
fclose(fw);
fclose(fr);
remove(fname);
}
int main() {
const char *packets1[] = {0};
const char *packets2[] = {"zero;", "one;", "two;", "three;", "four;", 0};
const char *packets3[] = {"zer0;", 0};
const char *packets4[] = {"looooooooooong;", 0};
test(packets1, END);
test(packets2, END);
test(packets3, BAD_PACKET);
test(packets4, BIG_PACKET);
return 0;
}
```

## Bloques Reutilizables

Los bloques reutilizables de la forma **/*!rules:re2c[:<nombre>] ...
*/** o **%{rules[:<nombre>] ... %}** pueden ser reutilizados cualquier número de
veces y combinados con otros bloques de re2c. El **<nombre>** es
opcional. Un bloque de reglas puede ser usado en un bloque o directiva
**use**. El código para un bloque de reglas se genera en cada punto de
uso.

Los bloques de uso se definen con **/*!use:re2c[:<nombre>] ...
*/** o **%{use[:<nombre>] ... %}**. El **<nombre>** es
opcional: si no se especifica, el bloque de reglas asociado es el más
reciente (ya sea con nombre o sin nombre). Un bloque de uso puede agregar
definiciones, configuraciones y reglas nombradas propias. Un caso de uso
importante para los bloques de uso es un analizador léxico que admite
múltiples codificaciones de entrada: el mismo bloque de reglas se reutiliza
varias veces con configuraciones específicas de codificación (ver el ejemplo
a continuación).

La directiva de uso dentro de un bloque **!use:<nombre>;** puede ser
utilizada desde dentro de un bloque de re2c. Fusiona el bloque referenciado
**<nombre>** en el actual. Si algunas de las reglas y configuraciones
fusionadas se superponen con las definidas previamente, los conflictos se
resuelven de la manera habitual: la regla más temprana tiene prioridad, y la
última configuración anula las precedentes. Una excepción son las reglas
especiales **, **, y (en modo condición) **<!>**, para las cuales una
definición local del bloque anula cualquier herencia. La directiva de uso
permite combinar diferentes bloques de re2c en un solo bloque (ver el ejemplo
a continuación).

Los bloques con nombre y la directiva de uso dentro de un bloque se agregaron
en la versión 2.2 de re2c. Desde esa versión, los bloques reutilizables están
permitidos por defecto (no se necesita una opción especial). Antes de la
versión 2.2, el modo de reutilización se habilitaba con la opción **-r
--reusable**. Antes de la versión 1.2, los bloques reutilizables no podían
mezclarse con bloques normales.

## Ejemplo de una directiva **!use**

```c
// re2c $INPUT -o $OUTPUT
#include
```

## Extracción de Subcoincidencias

re2c tiene dos opciones para la extracción de subcoincidencias.



  
Etiquetas

  
La primera opción es usar etiquetas independientes de la forma
      **@stag** o **#mtag**, donde **stag** y **mtag** son nombres
      definidos por el usuario arbitrarios. Las etiquetas se habilitan con la
      opción **-T --tags** o la configuración **re2c:tags = 1**.
      Semánticamente, las etiquetas son marcadores de posición: pueden insertarse
      en cualquier lugar de una expresión regular y se vinculan a la posición
      correspondiente (o múltiples posiciones) en la cadena de entrada. Las
      etiquetas s se vinculan a la última posición coincidente, y las
      etiquetas m se vinculan a una lista de posiciones (pueden usarse en
      subexpresiones de repetición, donde una sola posición en una expresión
      regular corresponde a múltiples posiciones en la cadena de entrada). Todas
      las etiquetas deben ser definidas por el usuario, ya sea manualmente o con
      la ayuda de bloques **svars** y **mvars**. Si hay más de una forma en
      que las etiquetas pueden coincidir con la entrada, la ambigüedad se
      resuelve utilizando la estrategia de desambiguación voraz más a la
      izquierda.

  
Capturas

  
La segunda opción es usar grupos de captura. Se habilitan con la
      opción **--captures** o la configuración **re2c:captures = 1**. Hay
      dos variantes para diferentes políticas de desambiguación,
      **--leftmost-captures** (el predeterminado) es para la política voraz
      más a la izquierda, y **--posix-captures** es para la política de
      coincidencia más larga POSIX. En este modo, todas las subexpresiones
      entre paréntesis se consideran grupos de captura, y se puede usar un
      signo de exclamación para marcar grupos que no capturan: **(! ... )**.
      Con la opción **--invert-captures** o la configuración
      **re2c:invert-captures = 1**, el significado del signo de
      exclamación se invierte. El número de grupos para la regla coincidente
      se almacena en la variable **yynmatch** (la expresión regular completa
      es el grupo número cero), y los resultados de las subcoincidencias se
      almacenan en el arreglo **yypmatch**. Tanto **yynmatch** como
      **yypmatch** deben ser definidos por el usuario, y el tamaño de
      **yypmatch** debe ser al menos **[yynmatch * 2]**. Use el bloque
      **maxnmatch** para definir **YYMAXNMATCH**, una constante que es
      igual al valor máximo de **yynmatch** entre todas las reglas.

  
Captvars

  
Otra forma de usar grupos de captura es la opción **--captvars** o la
      configuración **re2c:captvars = 1**. La única diferencia con
      **--captures** es la forma en que el código generado almacena los
      resultados de las subcoincidencias: en lugar de **yynmatch** y
      **yypmatch**, re2c genera las variables **yytl<k>** y **yytr<k>**
      para el grupo de captura *k* (el usuario debe declararlas usando un bloque
      **svars**). Las capturas con variables admiten dos políticas de
      desambiguación: **--leftmost-captvars** o
      **re2c:leftmost-captvars = 1** para la política voraz más a la izquierda
      (la predeterminada) y **--posix-captvars** o
      **re2c:posix-captvars** para la política de coincidencia más larga
      POSIX.




En el interior, todas estas opciones se traducen en etiquetas y
*Autómatas Finitos Deterministas Etiquetados con Lookahead*. La idea central
de TDFA es minimizar la sobrecarga en la extracción de subcoincidencias. En el
extremo, si no hay etiquetas ni capturas en una expresión regular, TDFA es solo
un DFA ordinario. Si el número de etiquetas es moderado, la sobrecarga es
apenas perceptible. El TDFA generado utiliza una serie de *variables de
etiqueta* que no se mapean directamente a las etiquetas: una sola variable
puede usarse para diferentes etiquetas, y una etiqueta puede requerir múltiples
variables para almacenar todos sus valores posibles. Finalmente, la ambigüedad
se resuelve y solo sobrevive una variable final por etiqueta. Las variables de
etiqueta deben definirse utilizando bloques **stags** o **mtags**. Si se
almacena el estado del analizador léxico, las variables de etiqueta deben ser
parte de él. También deben ser actualizadas por **YYFILL**.

Las etiquetas s admiten las siguientes operaciones:


    
  
  • guardar la posición de entrada en una etiqueta s: **t = YYCURSOR** con la API de puntero C o una operación definida por el usuario **YYSTAGP(t)** con la API genérica
    • 
  
  • guardar el valor predeterminado en una etiqueta s: **t = NULL** con la API de puntero C o una operación definida por el usuario **YYSTAGN(t)** con la API genérica
    • 
  
  • copiar una etiqueta s a otra: **t1 = t2**
    • 



Las etiquetas m admiten las siguientes operaciones:


    
  
  • agregar la posición de entrada a una etiqueta m: una operación definida por el usuario **YYMTAGP(t)** con la API predeterminada y genérica
    • 
  
  • agregar el valor predeterminado a una etiqueta m: una operación definida por el usuario **YYMTAGN(t)** con la API predeterminada y genérica
    • 
  
  • copiar una etiqueta m a otra: **t1 = t2**
    • 



Las etiquetas s se pueden implementar como valores escalares (punteros o
desplazamientos). Las etiquetas m necesitan una representación más compleja, ya
que deben almacenar una secuencia de valores de etiqueta. La representación más
ingenu y menos eficiente de una etiqueta m es una lista (arreglo, vector) de
valores de etiqueta; una representación más eficiente es almacenar todas las
etiquetas m en un árbol de prefijos representado como un arreglo de nodos
**(v, p)**, donde **v** es el valor de la etiqueta y **p** es un puntero al nodo
padre.

semánticas que consisten en tres componentes numéricos: mayor, menor y
parche (este último es opcional). Ver más abajo un ejemplo más complejo que
utiliza **YYFILL**.

Here is a more complex example of using s-tags with YYFILL
    to parse a file with newline-separated semantic versions. Tag variables are
    part of the lexer state, and they are adjusted in YYFILL like other
    input positions. Note that it is necessary for s-tags because their values
    are invalidated after shifting buffer contents. It may not be necessary in a
    custom implementation where tag variables store offsets relative to the
    start of the input string rather than the buffer, which may be the case with
    m-tags.






// re2c $INPUT -o $OUTPUT --tags
#include <assert.h>
#include <stddef.h>
#include <stdio.h>
#include <string.h>
#include <vector>
#define BUFSIZE 4095
struct Input {
    FILE *file;
    char buf[BUFSIZE + 1], *lim, *cur, *mar, *tok;
    // Tag variables must be part of the lexer state passed to YYFILL.
    // They don't correspond to tags and should be autogenerated by re2c.
    /*!stags:re2c format = 'const char *@@;'; */
    bool eof;
};
struct SemVer { int major, minor, patch; };
static bool operator==(const SemVer &x, const SemVer &y) {
    return x.major == y.major && x.minor == y.minor && x.patch == y.patch;
}
static int s2n(const char *s, const char *e) { // pre-parsed string to number
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
static int fill(Input &in) {
    if (in.eof) return 1;
    const size_t shift = in.tok - in.buf;
    const size_t used = in.lim - in.tok;
    // Error: lexeme too long. In real life could reallocate a larger buffer.
    if (shift < 1) return 2;
    // Shift buffer contents (discard everything up to the current token).
    memmove(in.buf, in.tok, used);
    in.lim -= shift;
    in.cur -= shift;
    in.mar -= shift;
    in.tok -= shift;
    // Tag variables need to be shifted like other input positions. The check
    // for non-NULL is only needed if some tags are nested inside of alternative
    // or repetition, so that they can have NULL value.
    /*!stags:re2c format = "if (in.@@) in.@@ -= shift;\n" */;
    // Fill free space at the end of buffer with new data from file.
    in.lim += fread(in.lim, 1, BUFSIZE - used, in.file);
    in.lim[0] = 0;
    in.eof = in.lim < in.buf + BUFSIZE;
    return 0;
}
static bool lex(Input &in, std::vector<SemVer> &vers) {
    // User-defined local variables that store final tag values.
    // They are different from tag variables autogenerated with `stags:re2c`,
    // as they are set at the end of match and used only in semantic actions.
    const char *t1, *t2, *t3, *t4;
    for (;;) {
        in.tok = in.cur;
    /*!re2c
        re2c:eof = 0;
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYCURSOR = in.cur;
        re2c:define:YYMARKER = in.mar;
        re2c:define:YYLIMIT = in.lim;
        re2c:define:YYFILL = "fill(in) == 0";
        re2c:tags:expression = "in.@@";
        num = [0-9]+;
        num @t1 "." @t2 num @t3 ("." @t4 num)? [\n] {
            int major = s2n(in.tok, t1);
            int minor = s2n(t2, t3);
            int patch = t4 != NULL ? s2n(t4, in.cur - 1) : 0;
            SemVer ver = {major, minor, patch};
            vers.push_back(ver);
            continue;
        }
        $ { return true; }
        * { return false; }
    */}
}
int main() {
    const char *fname = "input";
    const SemVer semver = {1, 22, 333};
    std::vector expect(BUFSIZE, semver), actual;
    // Prepare input file (make sure it exceeds buffer size).
    FILE *f = fopen(fname, "w");
    for (int i = 0; i < BUFSIZE; ++i) fprintf(f, "1.22.333\n");
    fclose(f);
    // Reopen input file for reading.
    f = fopen(fname, "r");
    // Initialize lexer state: all pointers are at the end of buffer.
    Input in;
    in.file = f;
    in.cur = in.mar = in.tok = in.lim = in.buf + BUFSIZE;
    /*!stags:re2c format = "in.@@ = in.lim;\n" */;
    in.eof = false;
    // Sentinel (at YYLIMIT pointer) is set to zero, which triggers YYFILL.
    *in.lim = 0;
    // Run the lexer and check results.
    assert(lex(in, actual) && expect == actual);
    // Cleanup: remove input file.
    fclose(f);
    remove(fname);
    return 0;
}

Here is an example of using m-tags to parse a version with a
    variable number of components. Tag variables are stored in a trie.






// re2c $INPUT -o $OUTPUT
#include <assert.h>
#include <stddef.h>
#include <vector>
static const int MTAG_ROOT = -1;
// An m-tag tree is a way to store histories with an O(1) copy operation.
// Histories naturally form a tree, as they have common start and fork at some
// point. The tree is stored as an array of pairs (tag value, link to parent).
// An m-tag is represented with a single link in the tree (array index).
struct Mtag {
    const char *elem; // tag value
    int pred; // index of the predecessor node or root
};
typedef std::vector<Mtag> MtagTrie;
typedef std::vector<int> Ver; // unbounded number of version components
static int s2n(const char *s, const char *e) { // pre-parsed string to number
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
// Append a single value to an m-tag history.
static void add_mtag(MtagTrie &trie, int &mtag, const char *value) {
    Mtag m = {value, mtag};
    mtag = (int)trie.size();
    trie.push_back(m);
}
// Recursively unwind tag histories and collect version components.
static void unfold(const MtagTrie &trie, int x, int y, Ver &ver) {
    // Reached the root of the m-tag tree, stop recursion.
    if (x == MTAG_ROOT && y == MTAG_ROOT) return;
    // Unwind history further.
    unfold(trie, trie[x].pred, trie[y].pred, ver);
    // Get tag values. Tag histories must have equal length.
    assert(x != MTAG_ROOT && y != MTAG_ROOT);
    const char *ex = trie[x].elem, *ey = trie[y].elem;
    if (ex != NULL && ey != NULL) {
        // Both tags are valid pointers, extract component.
        ver.push_back(s2n(ex, ey));
    } else {
        // Both tags are NULL (this corresponds to zero repetitions).
        assert(ex == NULL && ey == NULL);
    }
}
static bool parse(const char *str, Ver &ver) {
    const char *YYCURSOR = str, *YYMARKER;
    MtagTrie mt;
    // User-defined tag variables that are available in semantic action.
    const char *t1, *t2;
    int t3, t4;
    // Autogenerated tag variables used by the lexer to track tag values.
    /*!stags:re2c format = 'const char *@@ = NULL;'; */
    /*!mtags:re2c format = 'int @@ = MTAG_ROOT;'; */
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYSTAGP = "@@ = YYCURSOR;";
        re2c:define:YYSTAGN = "@@ = NULL;";
        re2c:define:YYMTAGP = "add_mtag(mt, @@, YYCURSOR);";
        re2c:define:YYMTAGN = "add_mtag(mt, @@, NULL);";
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        num = [0-9]+;
        @t1 num @t2 (". " #t3 num #t4)* [\x00] {
            ver.clear();
            ver.push_back(s2n(t1, t2));
            unfold(mt, t3, t4, ver);
            return true;
        }
        * { return false; }
    */
}
int main() {
    Ver v;
    assert(parse("1", v) && v == Ver({1}));
    assert(parse("1.2.3.4.5.6.7", v) && v == Ver({1, 2, 3, 4, 5, 6, 7}));
    assert(!parse("1.2.", v));
    return 0;
}

Encoding support

It is necessary to understand the difference between code points and code units. A code point is a numeric identifier of a symbol. A code unit is the smallest unit of storage in the encoded text. A single code point may be represented with one or more code units. In a fixed-length encoding all code points are represented with the same number of code units. In a variable-length encoding code points may be represented with a different number of code units. Note that the "any" rule [^] matches any code point, but not necessarily any code unit (the only way to match any code unit regardless of the encoding is the default rule *). The generated lexer works with a stream of code units: yych stores a code unit, and YYCTYPE is the code unit type. Regular expressions, on the other hand, are specified in terms of code points. When re2c compiles regular expressions to automata it translates code points to code units. Las siguientes codificaciones son compatibles:

  • ASCII (habilitado por defecto). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • EBCDIC (habilitado con --ebcdic o re2c:encoding:ebcdic). Es una codificación de longitud fija con espacio de código [0-255] y puntos de código y unidades de código de 1 byte.
  • UCS2 (habilitado con --ucs2 o re2c:encoding:ucs2). Es una codificación de longitud fija con espacio de código [0-0xFFFF] y puntos de código y unidades de código de 2 bytes.
  • UTF8 (habilitado con --utf8 o re2c:encoding:utf8). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 1 byte. Los puntos de código se representan con 1 a 4 unidades de código.
  • UTF16 (habilitado con --utf16 o re2c:encoding:utf16). Es una codificación Unicode de longitud variable. El tamaño de la unidad de código es de 2 bytes. Los puntos de código se representan con 1 o 2 unidades de código.
  • UTF32 (habilitado con --utf32 o re2c:encoding:utf32). Es una codificación Unicode de longitud fija con espacio de código [0-0x10FFFF] y puntos de código y unidades de código de 4 bytes.

El archivo de inclusión include/unicode_categories.re proporciona definiciones de re2c para las categorías estándar de Unicode.

La opción --input-encoding especifica la codificación del archivo fuente, que puede usarse para habilitar literales Unicode en expresiones regulares. Por ejemplo, --input-encoding utf8 le dice a re2c que el archivo fuente está en UTF8 (esto difiere de --utf8, que establece la codificación del texto de entrada). La opción --encoding-policy especifica la forma en que re2c maneja los sustitutos Unicode (puntos de código en el rango [0xD800-0xDFFF]).

A continuación, se muestra un ejemplo de un lexer para identificadores Unicode codificados en UTF8.

Archivos de inclusión

re2c permite incluir otros archivos mediante un bloque de la forma /*!include:re2c FILE */ o %{include FILE %}, o una directiva dentro de un bloque !include FILE ;, donde FILE es la ruta al archivo a incluir. re2c busca los archivos de inclusión en el directorio del archivo que los incluye y en las ubicaciones de inclusión, que pueden especificarse con la opción -I. Los bloques/directivas de inclusión en re2c funcionan de la misma manera que el #include de C/C++: el contenido de FILE se copia textualmente en el lugar del bloque/directiva. Los archivos de inclusión pueden tener más inclusiones propias. Use la opción --depfile para rastrear las dependencias de compilación del archivo de salida en los archivos de inclusión. re2c proporciona algunos archivos de inclusión predefinidos que se pueden encontrar en el subdirectorio include/ del proyecto. Estos archivos contienen definiciones que pueden ser útiles para otros proyectos (como las categorías Unicode) y forman algo así como una biblioteca estándar para re2c. A continuación, se muestra un ejemplo de uso de archivos de inclusión.

Archivo de inclusión 1 (definitions.h)

typedef enum { OK, FAIL } Result;
/*!re2c
    number = [1-9][0-9]*;
*/

Archivo de inclusión 2 (extra_rules.re.inc)

// números de punto flotante
frac  = [0-9]* "." [0-9]+ | [0-9]+ ".";
exp   = 'e' [+-]? [0-9]+;
float = frac exp? | [0-9]+ exp;
float { return OK; }

Archivo de entrada

// re2c $INPUT -o $OUTPUT -i
#include <assert.h>
/*!include:re2c "definitions.h" */
Result lex(const char *s) {
    const char *YYCURSOR = s, *YYMARKER;
    /*!re2c
        re2c:define:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        *      { return FAIL; }
        number { return OK; }
        !include "extra_rules.re.inc";
    */
}
int main() {
    assert(lex("123") == OK);
    assert(lex("123.4567") == OK);
    return 0;
}

Archivos de cabecera

re2c permite generar un archivo de cabecera a partir del archivo .re de entrada utilizando la opción --header o la configuración re2c:header, y pares de bloques de la forma /*!header:re2c:on*/ y /*!header:re2c:off*/, o %{header:on%} y %{header:off%}. El primer bloque marca el inicio del archivo de cabecera y el segundo bloque marca el final. Todo lo que está entre estos bloques es procesado por re2c, y el código generado se escribe en el archivo especificado con la opción --header o la configuración re2c:header (o stdout si no se usa ninguna opción ni configuración). El archivo de cabecera autogenerado puede ser necesario en casos en los que re2c se utiliza para generar definiciones que deben ser visibles desde otras unidades de traducción.

Aquí hay un ejemplo de generación de un archivo de cabecera que contiene la definición del estado del lexer con variables de etiqueta (el número de variables depende de la gramática regular y es desconocido para el programador).

Archivo de entrada

// re2c $INPUT -o $OUTPUT -i --header lexer/state.h
#include <assert.h>
#include <stddef.h>
#include "lexer/state.h" // la cabecera es generada por re2c
/*!header:re2c:on*/
typedef struct {
    const char *str, *cur;
    /*!stags:re2c format = "const char *@@;"; */
} LexerState;
/*!header:re2c:off*/
long lex(LexerState* st) {
    const char *t;
    /*!re2c
        re2c:header = "lexer/state.h";
        re2c:yyfill:enable = 0;
        re2c:define:YYCTYPE = char;
        re2c:define:YYCURSOR = "st->cur";
        re2c:tags = 1;
        re2c:tags:expression = "st->@@";
        [a]* @t [b]* { return t - st->str; }
    */
}
int main() {
    const char *s = "ab";
    LexerState st = { s, s /*!stags:re2c format = ", NULL"; */ };
    assert(lex(&st) == 1);
    return 0;
}

Programas esqueleto

Con la opción -S, --skeleton, re2c ignora todo el código que no sea de re2c y genera un programa C autocontenido que puede ser compilado y ejecutado posteriormente. El programa consta del código del lexer y los datos de entrada. Para cada Autómata Finito Determinista (DFA) construido (bloque o condición), re2c genera un lexer independiente y dos archivos: un archivo .input con cadenas derivadas del DFA y un archivo .keys con los resultados esperados de la coincidencia. El programa ejecuta cada lexer en el archivo .input correspondiente y compara los resultados con las expectativas. Los programas esqueleto son muy útiles por varias razones:

  • Pueden verificar la corrección de varias optimizaciones de re2c (los datos se generan en una etapa temprana del proceso, antes de que se hayan realizado las transformaciones del DFA).
  • La generación de un conjunto de datos de entrada con buena cobertura puede ser útil tanto para pruebas como para evaluación comparativa.
  • La generación de programas ejecutables autocontenidos permite obtener casos de prueba minimizados (el código original puede ser grande o tener muchas dependencias).

La dificultad para generar datos de entrada radica en que, excepto en los casos más triviales, el número de cadenas de entrada posibles es demasiado grande (incluso si la longitud de la cadena está limitada). re2c resuelve esta dificultad generando suficientes cadenas para cubrir casi todas las transiciones del DFA. Utiliza el siguiente algoritmo. Primero, construye un esqueleto del DFA. Para codificaciones con un tamaño de unidad de código de 1 byte (como ASCII, UTF-8 y EBCDIC), el esqueleto es solo una copia exacta del DFA original. Para codificaciones con unidades de código multibyte, el esqueleto es una copia del DFA con ciertas transiciones omitidas: a saber, re2c toma como máximo 256 unidades de código para cada rango continuo y disjunto que corresponde a una transición del DFA. Los valores elegidos se distribuyen uniformemente e incluyen los límites del rango. En lugar de intentar cubrir todas las rutas posibles en el esqueleto (lo cual es inviable), re2c genera suficientes rutas para cubrir todas las transiciones del esqueleto, y por lo tanto, activar los saltos condicionales correspondientes en el lexer. La implementación del algoritmo está limitada a ~1 GB de transiciones y consume una cantidad constante de memoria (re2c escribe los datos en el archivo tan pronto como se generan).

Visualización y depuración

Con la opción -D, --emit-dot, re2c no genera código. En su lugar, vuelca el DFA generado en formato DOT. Se puede convertir este volcado en una imagen del DFA utilizando Graphviz u otra biblioteca. Tenga en cuenta que esta opción muestra el DFA final después de haber pasado por una serie de optimizaciones y transformaciones. Las etapas anteriores se pueden volcar con varias opciones de depuración, como --dump-nfa, --dump-dfa-raw, etc. (consulte la lista completa de opciones).

NAME

re2c - a free, general-purpose, scalable, and efficient lexer generator for the C/C++ programming language

SYNOPSIS

re2c [OPTION]... [FILE]

INTRODUCTION

The re2c lexer generator is a tool that generates a lexer from a set of regular expressions. The generated lexer is highly optimized for speed and can be used in a variety of applications, such as lexical analysis, pattern matching, and text processing.

BASICS

The re2c lexer generator takes a set of regular expressions as input and produces a C/C++ source file containing the generated lexer.

The input file consists of a set of rules, where each rule is a regular expression followed by an action to be performed when the regular expression is matched.

Here is a simple example of an input file:

%{"
        /* User code */
        "}%
        
        int main() {
            char *s = "hello world";
            char *y = s;
        
        %>
            *y++ = *s++;
        <%
        
        return 0;
        }

In this example, the input file defines a single rule: match any character and copy it to the output buffer. The action associated with this rule is to copy the character from the input buffer to the output buffer.

HANDLING THE END OF INPUT

The re2c lexer generator provides several ways to handle the end of input:

  • Default behavior: When the end of input is reached, the lexer will return an empty string. This can be useful for handling empty files or strings.

  • EOF rule: You can define a special rule for the end of input, called the EOF rule. This rule will be matched only when the end of input is reached.

    Here is an example of an EOF rule:

    %{"
                /* User code */
                "}%
                
                int main() {
                    char *s = "hello world";
                    char *y = s;
                
                %>
                    *y++ = *s++;
                <% EOF {
                    /* End of file reached */
                }
                
                return 0;
                }

    In this example, the EOF rule is matched when the end of input is reached. The action associated with this rule is to print a message indicating that the end of file has been reached.

  • NULL character: The re2c lexer generator can also be configured to treat a NULL character as the end of input. This can be useful when working with C strings, which are null-terminated.

BUFFER REFILLING

The re2c lexer generator supports buffer refilling, which allows the lexer to read input from a file or other input stream in chunks. This can be useful for handling large input files, as it allows the lexer to process the file without having to load the entire file into memory at once.

The buffer refilling mechanism is implemented using a callback function that is called by the lexer whenever it needs to refill the input buffer. This callback function is responsible for reading data from the input stream and filling the buffer.

FEATURES

  • Fast and efficient lexers: re2c generates highly optimized lexers that are very fast and efficient.

  • Support for C/C++: re2c can generate lexers for both C and C++.

  • Flexible rule definition: re2c provides a flexible syntax for defining lexer rules, allowing you to specify complex patterns and actions.

  • Buffer refilling: re2c supports buffer refilling, which allows you to process large input files efficiently.

  • EOF handling: re2c provides flexible options for handling the end of input.

  • Extensible: re2c can be extended with user-defined functions and macros.
