getrlimit(2) System Calls Manual getrlimit(2)

NOMBRE

getrlimit(2), setrlimit(2), prlimit(2) - obtener/establecer límites de recursos

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/resource.h>
int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
int prlimit(pid_t pid, int resource,
            const struct rlimit *_Nullable new_limit,
            struct rlimit *_Nullable old_limit);
struct rlimit {
    rlim_t  rlim_cur;  /* Límite blando */
    rlim_t  rlim_max;  /* Límite duro (techo para rlim_cur) */
};
typedef /* ... */  rlim_t;  /* Tipo entero sin signo */
Requisitos de Macro de Prueba de Funcionalidad para glibc (ver feature_test_macros(7)):

prlimit():

    _GNU_SOURCE

DESCRIPCIÓN

Las llamadas al sistema getrlimit() y setrlimit() obtienen y establecen límites de recursos. Cada recurso tiene un límite blando y uno duro asociado, según se define en la estructura rlimit.

El límite blando es el valor que el kernel impone para el recurso correspondiente. El límite duro actúa como un techo para el límite blando: un proceso no privilegiado solo puede establecer su límite blando a un valor en el rango de 0 hasta el límite duro y (de forma irreversible) reducir su límite duro. Un proceso privilegiado (en Linux: uno con la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario inicial) puede realizar cambios arbitrarios en cualquiera de los valores límite.

El valor RLIM_INFINITY denota que no hay límite en un recurso (tanto en la estructura devuelta por getrlimit() como en la estructura pasada a setrlimit()).

El argumento resource debe ser uno de:

RLIMIT_AS
Este es el tamaño máximo de la memoria virtual (espacio de direcciones) del proceso. El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), mmap(2) y mremap(2), que fallan con el error ENOMEM al exceder este límite. Además, la expansión automática de la pila falla (y genera una señal SIGSEGV que mata al proceso si no se ha puesto a disposición una pila alternativa mediante sigaltstack(2)). Dado que el valor es un long, en máquinas con un long de 32 bits, este límite es como máximo de 2 GiB, o este recurso es ilimitado.
RLIMIT_CORE
Este es el tamaño máximo de un archivo de core dump (ver core(5)) en bytes que el proceso puede volcar. Cuando es 0, no se crean archivos de volcado de core. Cuando es distinto de cero, los volcados más grandes se truncan a este tamaño.
RLIMIT_CPU
Este es un límite, en segundos, en la cantidad de tiempo de CPU que el proceso puede consumir. Cuando el proceso alcanza el límite blando, se le envía una señal SIGXCPU. La acción predeterminada para esta señal es terminar el proceso. Sin embargo, la señal puede ser capturada y el manejador puede devolver el control al programa principal. Si el proceso continúa consumiendo tiempo de CPU, se le enviará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se le enviará SIGKILL. (Esto último describe el comportamiento de Linux. Las implementaciones varían en cómo tratan los procesos que continúan consumiendo tiempo de CPU después de alcanzar el límite blando. Las aplicaciones portátiles que necesitan capturar esta señal deben realizar una terminación ordenada al recibir por primera vez SIGXCPU).
RLIMIT_DATA
Este es el tamaño máximo del segmento de datos del proceso (datos inicializados, datos no inicializados y heap). El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), sbrk(2) y (desde Linux 4.7) mmap(2), que fallan con el error ENOMEM al encontrar el límite blando de este recurso.
RLIMIT_FSIZE
Este es el tamaño máximo en bytes de los archivos que el proceso puede crear. Los intentos de extender un archivo más allá de este límite resultan en la entrega de una señal SIGXFSZ. Por defecto, esta señal termina un proceso, pero un proceso puede capturar esta señal en su lugar, en cuyo caso la llamada al sistema relevante (por ejemplo, write(2), truncate(2)) falla con el error EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 a Linux 2.4.24)
Este es un límite en el número combinado de bloqueos de flock(2) y licencias de fcntl(2) que este proceso puede establecer.
RLIMIT_MEMLOCK
Este es el número máximo de bytes de memoria que pueden bloquearse en la RAM. Este límite se redondea hacia abajo al múltiplo más cercano del tamaño de página del sistema. Este límite afecta a mlock(2), mlockall(2) y la operación MAP_LOCKED de mmap(2). Desde Linux 2.6.9, también afecta a la operación SHM_LOCK de shmctl(2), donde establece un máximo de bytes totales en segmentos de memoria compartida (ver shmget(2)) que pueden ser bloqueados por el ID de usuario real del proceso que llama. Los bloqueos de shmctl(2) SHM_LOCK se contabilizan por separado de los bloqueos de memoria por proceso establecidos por mlock(2), mlockall(2) y mmap(2) MAP_LOCKED; un proceso puede bloquear bytes hasta este límite en cada una de estas dos categorías.
Antes de Linux 2.6.9, este límite controlaba la cantidad de memoria que podía ser bloqueada por un proceso privilegiado. Desde Linux 2.6.9, no se imponen límites a la cantidad de memoria que un proceso privilegiado puede bloquear, y este límite rige en cambio la cantidad de memoria que un proceso no privilegiado puede bloquear.
RLIMIT_MSGQUEUE (desde Linux 2.6.8)
Este es un límite en el número de bytes que se pueden asignar para colas de mensajes POSIX para el ID de usuario real del proceso que llama. Este límite se impone para mq_open(3). Cada cola de mensajes que el usuario crea cuenta (hasta que se elimina) contra este límite según la siguiente fórmula:
Desde Linux 3.5:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* Por sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Por datos del mensaje */

Linux 3.4 y anteriores:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* Por sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Por datos del mensaje */

donde attr es la estructura mq_attr especificada como cuarto argumento a mq_open(3), y las estructuras msg_msg y posix_msg_tree_node son estructuras internas del kernel.
El sumando de "sobrecarga" en la fórmula tiene en cuenta los bytes de sobrecarga requeridos por la implementación y asegura que el usuario no pueda crear un número ilimitado de mensajes de longitud cero (tales mensajes, sin embargo, consumen algo de memoria del sistema para la sobrecarga de administración).
RLIMIT_NICE (desde Linux 2.6.12, pero ver BUGS abajo)
Esto especifica un techo al que se puede elevar el valor de nice del proceso usando setpriority(2) o nice(2). El techo real para el valor de nice se calcula como 20 - rlim_cur. El útil r
ange para este límite es, por lo tanto, de 1 (correspondiente a un valor agradable de 19) a 40 (correspondiente a un valor agradable de -20). Esta elección inusual de rango fue necesaria porque los números negativos no se pueden especificar como valores de límite de recursos, ya que típicamente tienen significados especiales. Por ejemplo, RLIM_INFINITY típicamente es lo mismo que -1. Para más detalles sobre el valor agradable, véase sched(7).
RLIMIT_NOFILE
Esto especifica un valor mayor que el número máximo de descriptores de archivo que pueden ser abiertos por este proceso. Los intentos (open(2), pipe(2), dup(2), etc.) de exceder este límite producen el error EMFILE. (Históricamente, este límite se denominó RLIMIT_OFILE en BSD.)
Desde Linux 4.5, este límite también define el número máximo de descriptores de archivo que un proceso no privilegiado (uno sin la capacidad CAP_SYS_RESOURCE) puede tener "en tránsito" a otros procesos, al ser pasado a través de sockets de dominio UNIX. Este límite se aplica a la llamada al sistema sendmsg(2). Para más detalles, véase unix(7).
RLIMIT_NPROC
Este es un límite en el número de procesos existentes (o, más precisamente en Linux, hilos) para el ID de usuario real del proceso que llama. Siempre que el número actual de procesos pertenecientes al ID de usuario real de este proceso sea mayor o igual a este límite, fork(2) falla con el error EAGAIN.
El límite RLIMIT_NPROC no se aplica a los procesos que tienen la capacidad CAP_SYS_ADMIN o CAP_SYS_RESOURCE, o que se ejecutan con el ID de usuario real 0.
RLIMIT_RSS
Este es un límite (en bytes) en el conjunto residente del proceso (el número de páginas virtuales residentes en RAM). Este límite solo tiene efecto en Linux 2.4.x, x < 30, y allí solo afecta a las llamadas a madvise(2) que especifican MADV_WILLNEED.
RLIMIT_RTPRIO (desde Linux 2.6.12, pero véase BUGS)
Esto especifica un techo para la prioridad en tiempo real que puede ser establecida para este proceso usando sched_setscheduler(2) y sched_setparam(2).
Para más detalles sobre las políticas de planificación en tiempo real, véase sched(7)
RLIMIT_RTTIME (desde Linux 2.6.25)
Este es un límite (en microsegundos) en la cantidad de tiempo de CPU que un proceso planificado bajo una política de planificación en tiempo real puede consumir sin realizar una llamada al sistema bloqueante. A efectos de este límite, cada vez que un proceso realiza una llamada al sistema bloqueante, el recuento de su tiempo de CPU consumido se reinicia a cero. El recuento de tiempo de CPU no se reinicia si el proceso continúa intentando utilizar la CPU pero es desprogramado, su intervalo de tiempo expira, o llama a sched_yield(2).
Al alcanzar el límite blando, se envía una señal SIGXCPU al proceso. Si el proceso captura o ignora esta señal y continúa consumiendo tiempo de CPU, entonces se generará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se enviará una señal SIGKILL al proceso.
El uso previsto de este límite es detener un proceso en tiempo real descontrolado de bloquear el sistema.
Para más detalles sobre las políticas de planificación en tiempo real, véase sched(7)
RLIMIT_SIGPENDING (desde Linux 2.6.8)
Este es un límite en el número de señales que pueden estar en cola para el ID de usuario real del proceso que llama. Tanto las señales estándar como las de tiempo real se cuentan a efectos de comprobar este límite. Sin embargo, el límite solo se aplica a sigqueue(3); siempre es posible usar kill(2) para poner en cola una instancia de cualquiera de las señales que no estén ya en cola para el proceso.
RLIMIT_STACK
Este es el tamaño máximo de la pila del proceso, en bytes. Al alcanzar este límite, se genera una señal SIGSEGV. Para manejar esta señal, un proceso debe emplear una pila de señales alternativa (sigaltstack(2)).
Desde Linux 2.6.23, este límite también determina la cantidad de espacio utilizada para los argumentos de línea de comandos y las variables de entorno del proceso; para detalles, véase execve(2).

prlimit()

La llamada al sistema específica de Linux prlimit() combina y extiende la funcionalidad de setrlimit() y getrlimit(). Puede ser utilizada tanto para establecer como para obtener los límites de recursos de un proceso arbitrario.

El argumento resource tiene el mismo significado que para setrlimit() y getrlimit().

Si el argumento new_limit no es NULL, entonces la estructura rlimit a la que apunta se utiliza para establecer nuevos valores para los límites blando y duro para resource. Si el argumento old_limit no es NULL, entonces una llamada exitosa a prlimit() coloca los límites blando y duro anteriores para resource en la estructura rlimit apuntada por old_limit.

El argumento pid especifica el ID del proceso sobre el cual la llamada debe operar. Si pid es 0, entonces la llamada se aplica al proceso que llama. Para establecer u obtener los recursos de un proceso distinto de sí mismo, el llamador debe tener la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario del proceso cuyos límites de recursos se están cambiando, o los IDs de usuario real, efectivo y guardado del proceso de destino deben coincidir con el ID de usuario real del llamador y los IDs de grupo real, efectivo y guardado del proceso de destino deben coincidir con el ID de grupo real del llamador.

VALOR DE RETORNO

En caso de éxito, estas llamadas al sistema devuelven 0. En caso de error, se devuelve -1 y se establece errno para indicar el error.

ERRORES

EFAULT
Un argumento de puntero apunta a una ubicación fuera del espacio de direcciones accesible.
EINVAL
El valor especificado en resource no es válido; o, para setrlimit() o prlimit(): rlim->rlim_cur era mayor que rlim->rlim_max.
EPERM
Un proceso no privilegiado intentó aumentar el límite duro; se requiere la capacidad CAP_SYS_RESOURCE para hacer esto.
EPERM
El llamador intentó aumentar el límite duro RLIMIT_NOFILE por encima del máximo definido por /proc/sys/fs/nr_open (véase proc(5))
EPERM
(prlimit()) El proceso que llama no tenía permiso para establecer límites para el proceso especificado por pid.
ESRCH
No se pudo encontrar un proceso con el ID especificado en pid.

NOTAS

Un proceso hijo creado a través de fork(2) hereda los límites de recursos de su padre. Los límites de recursos se conservan a través de execve(2).

Los límites de recursos son atributos por proceso que son compartidos por todos los hilos en un proceso.

Reducir el límite blando para un recurso por debajo del consumo actual de ese recurso por parte del proceso tendrá éxito (pero impedirá que el proceso aumente aún más su consumo del recurso).

Se pueden establecer los límites de recursos del shell utilizando el comando incorporado ulimit (limit en csh(1)). Los límites de recursos del shell son heredados por los procesos que crea para ejecutar comandos.

Desde Linux 2.6.24, los límites de recursos de cualquier proceso pueden ser inspeccionados a través de /proc/pid/limits; véase proc(5).

Sistemas antiguos proporcionaban una función vlimit() con un propósito similar a setrlimit(). Para compatibilidad hacia atrás, glibc también proporciona vlimit(). Todas las aplicaciones nuevas deben escribirse utilizando setrlimit().

Diferencias entre la librería C y la ABI del kernel

Desde glibc 2.13, las funciones de envoltura getrlimit() y setrlimit() de glibc ya no invocan las llamadas al sistema correspondientes, sino que emplean prlimit(), por las razones descritas en BUGS.

El nombre de la función de envoltura de glibc es prlimit(); la llamada al sistema subyacente es prlimit64().

BUGS

En kernels de Linux anteriores, las señales SIGXCPU y SIGKILL enviadas cuando un proceso encontraba los límites blandos y duros de RLIMIT_CPU se enviaban un (segundo de CPU) más tarde de lo que deberían haber sido. Esto se corrigió en Linux 2.6.8.

En los kernels de Linux 2.6.x anteriores a Linux 2.6.17, un límite de RLIMIT_CPU de 0 se trata erróneamente como "sin límite" (como RLIM_INFINITY). Desde Linux 2.6.17, establecer un límite de 0 tiene un efecto, pero se trata como un límite de 1 segundo.

Un error del kernel significa que RLIMIT_RTPRIO no funciona en Linux 2.6.12; el problema se soluciona en Linux 2.6.13.

En Linux 2.6.12, hubo una discrepancia de un dígito entre los rangos de prioridad devueltos por getpriority(2) y RLIMIT_NICE. Esto tuvo el efecto de que el límite real para el valor de nice se calculaba como 19 - rlim_cur. Esto se corrigió en Linux 2.6.13.

Desde Linux 2.6.12, si un proceso alcanza su límite blando de RLIMIT_CPU y tiene un manejador instalado para SIGXCPU, entonces, además de invocar al manejador de señales, el kernel incrementa el límite blando en un segundo. Este comportamiento se repite si el proceso continúa consumiendo tiempo de CPU, hasta que se alcanza el límite duro, momento en el que el proceso es terminado. Otras implementaciones no cambian el límite blando de RLIMIT_CPU de esta manera, y el comportamiento de Linux probablemente no sea compatible con los estándares; las aplicaciones portátiles deben evitar depender de este comportamiento específico de Linux. El límite específico de Linux RLIMIT_RTTIME muestra el mismo comportamiento cuando se encuentra el límite blando.

Los kernels anteriores a Linux 2.4.22 no diagnosticaban el error EINVAL para setrlimit() cuando rlim->rlim_cur era mayor que rlim->rlim_max.

Linux no devuelve un error cuando un intento de establecer RLIMIT_CPU ha fallado, por razones de compatibilidad.

Representación de valores de límites de recursos "grandes" en plataformas de 32 bits

Las funciones de envoltura getrlimit() y setrlimit() de glibc utilizan un tipo de datos rlim_t de 64 bits, incluso en plataformas de 32 bits. Sin embargo, el tipo de datos rlim_t utilizado en las llamadas al sistema getrlimit() y setrlimit() es un unsigned long (de 32 bits). Además, en Linux, el kernel representa los límites de recursos en plataformas de 32 bits como unsigned long. Sin embargo, un tipo de datos de 32 bits no es lo suficientemente ancho. El límite más pertinente aquí es RLIMIT_FSIZE, que especifica el tamaño máximo al que puede crecer un archivo: para ser útil, este límite debe representarse utilizando un tipo tan ancho como el tipo utilizado para representar desplazamientos de archivo (es decir, tan ancho como un off_t de 64 bits (suponiendo un programa compilado con _FILE_OFFSET_BITS=64)).

Para solucionar esta limitación del kernel, si un programa intentaba establecer un límite de recursos a un valor mayor que el que se podía representar en un unsigned long de 32 bits, entonces la función de envoltura setrlimit() de glibc convertía silenciosamente el valor del límite a RLIM_INFINITY. En otras palabras, la configuración del límite de recursos solicitada se ignoraba silenciosamente.

Desde glibc 2.13, glibc trabaja para solucionar las limitaciones de las llamadas al sistema getrlimit() y setrlimit() implementando setrlimit() y getrlimit() como funciones de envoltura que llaman a prlimit().

EJEMPLOS

El siguiente programa demuestra el uso de prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Uso: %s <pid> [<límite-blando-nuevo> "
                "<límite-duro-nuevo>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID del proceso objetivo */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Establecer el límite de tiempo de CPU del proceso objetivo; recuperar y mostrar
       el límite anterior */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Límites anteriores: blando=%jd; duro=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Recuperar y mostrar el nuevo límite de tiempo de CPU */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("Nuevos límites: blando=%jd; duro=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
