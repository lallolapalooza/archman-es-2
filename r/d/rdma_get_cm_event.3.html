RDMA_GET_CM_EVENT(3) Manual del programador de Librdmacm RDMA_GET_CM_EVENT(3)

NOMBRE

rdma_get_cm_event - Recupera el próximo evento de comunicación pendiente.

SINOPSIS

#include <rdma/rdma_cma.h>

int rdma_get_cm_event (struct rdma_event_channel *channel, struct rdma_cm_event **event);

ARGUMENTOS

channel
Canal de eventos para verificar eventos.
event
Información asignada sobre el próximo evento de comunicación.

DESCRIPCIÓN

Recupera un evento de comunicación. Si no hay eventos pendientes, por defecto, la llamada se bloqueará hasta que se reciba un evento.

VALOR DE RETORNO

Devuelve 0 si la operación fue exitosa, o -1 si ocurrió un error. Si ocurre un error, la variable errno se establecerá para indicar la razón del fallo.

NOTAS

El comportamiento síncrono por defecto de esta rutina se puede modificar modificando el descriptor de archivo asociado con el canal dado. Todos los eventos que se informan deben ser confirmados llamando a rdma_ack_cm_event. La destrucción de un rdma_cm_id se bloqueará hasta que los eventos relacionados hayan sido confirmados.

DATOS DEL EVENTO

Los detalles del evento de comunicación se devuelven en la estructura rdma_cm_event. Esta estructura es asignada por rdma_cm y liberada por la rutina rdma_ack_cm_event. Los detalles de la estructura rdma_cm_event se indican a continuación.

id
El identificador rdma_cm asociado con el evento. Si el tipo de evento es RDMA_CM_EVENT_CONNECT_REQUEST, entonces esto hace referencia a un nuevo id para esa comunicación.
listen_id
Para los tipos de evento RDMA_CM_EVENT_CONNECT_REQUEST, esto hace referencia al identificador de solicitud de escucha correspondiente.
event
Especifica el tipo de evento de comunicación que ocurrió. Ver TIPOS DE EVENTOS a continuación.
status
Devuelve cualquier información de error asíncrona asociada con un evento. El estado es cero si la operación fue exitosa, de lo contrario el valor del estado no es cero y es un errno negativo o un valor específico del transporte. Para obtener detalles sobre los valores de estado específicos del transporte, consulte la información del tipo de evento a continuación.
param
Proporciona detalles adicionales basados en el tipo de evento. Los usuarios deben seleccionar los subcampos conn o ud según el espacio de puertos rdma_port_space del rdma_cm_id asociado con el evento. Ver DATOS DE EVENTOS UD y DATOS DE EVENTOS CONN a continuación.

DATOS DE EVENTO UD

Parámetros de eventos relacionados con servicios de datagramas no fiables (UD): RDMA_PS_UDP y RDMA_PS_IPOIB. Los datos del evento UD son válidos para los eventos RDMA_CM_EVENT_ESTABLISHED y RDMA_CM_EVENT_MULTICAST_JOIN, a menos que se indique lo contrario.

private_data
Hace referencia a cualquier dato especificado por el usuario asociado con los eventos RDMA_CM_EVENT_CONNECT_REQUEST o RDMA_CM_EVENT_ESTABLISHED. Los datos a los que hace referencia este campo coinciden con los especificados por el lado remoto al llamar a rdma_connect o rdma_accept. Este campo es NULL si el evento no incluye datos privados. El búfer al que hace referencia este puntero se libera al llamar a rdma_ack_cm_event.
private_data_len
El tamaño del búfer de datos privados. Los usuarios deben tener en cuenta que el tamaño del búfer de datos privados puede ser mayor que la cantidad de datos privados enviados por el lado remoto. Cualquier espacio adicional en el búfer se rellenará con ceros.
ah_attr
Información de dirección necesaria para enviar datos al punto final remoto. Los usuarios deben usar esta estructura al asignar su handle de dirección.
qp_num
Número QP del punto final remoto o grupo de multidifusión.
qkey
QKey necesario para enviar datos al punto final remoto.

DATOS DE EVENTO CONEXION

Parámetros de eventos relacionados con servicios de QP conectados: RDMA_PS_TCP. Los datos del evento de conexión son válidos para los eventos RDMA_CM_EVENT_CONNECT_REQUEST y RDMA_CM_EVENT_ESTABLISHED, a menos que se indique lo contrario.

private_data
Hace referencia a cualquier dato especificado por el usuario asociado con el evento. Los datos a los que hace referencia este campo coinciden con los especificados por el lado remoto al llamar a rdma_connect o rdma_accept. Este campo es NULL si el evento no incluye datos privados. El búfer al que hace referencia este puntero se libera al llamar a rdma_ack_cm_event.
private_data_len
El tamaño del búfer de datos privados. Los usuarios deben tener en cuenta que el tamaño del búfer de datos privados puede ser mayor que la cantidad de datos privados enviados por el lado remoto. Cualquier espacio adicional en el búfer se rellenará con ceros.
responder_resources
El número de recursos de respuesta solicitados del receptor. Este campo coincide con la profundidad del iniciador especificada por el nodo remoto al llamar a rdma_connect y rdma_accept.
initiator_depth
El número máximo de operaciones de lectura/atómicas RDMA pendientes que el receptor puede tener pendientes. Este campo coincide con los recursos de respuesta especificados por el nodo remoto al llamar a rdma_connect y rdma_accept.
flow_control
Indica si el remitente proporciona control de flujo a nivel de hardware.
retry_count
Solo para eventos RDMA_CM_EVENT_CONNECT_REQUEST, indica el número de veces que el receptor debe reintentar las operaciones de envío.
rnr_retry_count
El número de veces que el receptor debe reintentar los errores de "receptor no listo" (RNR).
srq
Especifica si el remitente está utilizando una cola de recepción compartida (shared-receive queue).
qp_num
Indica el número QP remoto de la conexión.

TIPOS DE EVENTOS

Los siguientes tipos de eventos de comunicación pueden ser informados.

RDMA_CM_EVENT_ADDR_RESOLVED
La resolución de dirección (rdma_resolve_addr) se completó exitosamente.
RDMA_CM_EVENT_ADDR_ERROR
La resolución de dirección (rdma_resolve_addr) falló.
RDMA_CM_EVENT_ROUTE_RESOLVED
La resolución de ruta (rdma_resolve_route) se completó exitosamente.
RDMA_CM_EVENT_ROUTE_ERROR
La resolución de ruta (rdma_resolve_route) falló.
RDMA_CM_EVENT_CONNECT_REQUEST
Generado en el lado pasivo para notificar al usuario de una nueva solicitud de conexión.
RDMA_CM_EVENT_CONNECT_RESPONSE
Generado en el lado activo para notificar al usuario de una respuesta exitosa a una solicitud de conexión. Solo se genera en rdma_cm_id's que no tienen un QP asociado con ellos.
RDMA_CM_EVENT_CONNECT_ERROR
Indica que ha ocurrido un error

rdma_get_cm_event(3) — librdmacm — Arch Linux man pages

NAME

rdma_get_cm_event, rdma_get_event, rdma_ack_cm_event - retrieve RDMA Connection Manager (CM) events

SYNOPSIS

#include <rdma/rdma_cma.h>

struct rdma_cm_event *rdma_get_cm_event(struct rdma_event_channel *event_channel);

struct rdma_cm_event *rdma_get_event(struct rdma_event_channel *event_channel);

int rdma_ack_cm_event(struct rdma_cm_event *event);

ARGUMENTS

event_channel
Event channel to retrieve an event from.
event
Pointer to the event to acknowledge.

DESCRIPTION

The RDMA Connection Manager (CM) library provides a mechanism for applications to handle asynchronous events. The rdma_get_cm_event and rdma_get_event functions are used to retrieve events from an event channel. These functions will block until an event is available. The rdma_ack_cm_event function is used to acknowledge an event once it has been processed by the application. Acknowledging events is important to prevent resource leaks.

RETURN VALUE

rdma_get_cm_event and rdma_get_event return a pointer to a struct rdma_cm_event on success, or NULL on error. The caller is responsible for freeing the event structure using free() after acknowledging it.

rdma_ack_cm_event returns 0 on success, or -1 on error.

NOTES

The rdma_get_event function is an alias for rdma_get_cm_event.

Applications should always acknowledge events using rdma_ack_cm_event after they have been processed. Failure to do so can lead to resource leaks and prevent the CM library from functioning correctly.

The struct rdma_cm_event contains a pointer to a struct rdma_cm_id, which should not be freed by the application. The CM library manages the lifecycle of struct rdma_cm_id structures.

EVENT DATA

The structure of a struct rdma_cm_event is defined as follows:

struct rdma_cm_event {
    struct rdma_cm_id *id;
    struct rdma_cm_event_data conn;
    enum rdma_cm_event_type event;
    int status;
};

The id field points to the connection identifier associated with the event.

The conn field contains connection-specific data. Its contents depend on the event type.

The event field specifies the type of event that occurred.

The status field provides additional information about the event, such as an error code.

EVENT TYPES

RDMA_CM_EVENT_CONNECT_REQUEST
Generated on the passive side to notify the user of an incoming connection request. May be generated on the active or passive side of a connection.
RDMA_CM_EVENT_UNREACHABLE
Generated on the active side to notify the user that the remote server is not reachable or unable to respond to a connection request. If this event is generated in response to a UD QP resolution request over InfiniBand, the event status field will contain an errno, if negative, or the status result carried in the IB CM SIDR REP message.
RDMA_CM_EVENT_REJECTED
Indicates that a connection request or response was rejected by the remote end point. The event status field will contain the transport specific reject reason if available. Under InfiniBand, this is the reject reason carried in the IB CM REJ message.
RDMA_CM_EVENT_ESTABLISHED
Indicates that a connection has been established with the remote end point.
RDMA_CM_EVENT_DISCONNECTED
The connection has been disconnected.
RDMA_CM_EVENT_DEVICE_REMOVAL
The local RDMA device associated with the rdma_cm_id has been removed. Upon receiving this event, the user must destroy the related rdma_cm_id.
RDMA_CM_EVENT_MULTICAST_JOIN
The multicast join operation (rdma_join_multicast) completed successfully.
RDMA_CM_EVENT_MULTICAST_ERROR
An error either occurred joining a multicast group, or, if the group had already been joined, on an existing group. The specified multicast group is no longer accessible and should be rejoined, if desired.
RDMA_CM_EVENT_ADDR_CHANGE
The network device associated with this ID through address resolution changed its HW address, eg following of bonding failover. This event can serve as a hint for applications who want the links used for their RDMA sessions to align with the network stack.
RDMA_CM_EVENT_TIMEWAIT_EXIT
The QP associated with a connection has exited its timewait state and is now ready to be re-used. After a QP has been disconnected, it is maintained in a timewait state to allow any in flight packets to exit the network. After the timewait state has completed, the rdma_cm will report this event.
RDMA_CM_EVENT_ADDRINFO_RESOLVED
Address information resolution (rdma_resolve_addrinfo) completed successfully.
RDMA_CM_EVENT_ADDRINFO_ERROR
Address information resolution (rdma_resolve_addrinfo) failed.
RDMA_CM_EVENT_USER
This allows a user-defined event to be written to the RDMA CM event channel. Event details are specified by the user and not interpreted by the librdmacm. This event is useful for a multi-threaded application to signal a thread which may be waiting on the RDMA CM event channel.
