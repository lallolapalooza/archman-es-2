RIGCTLD(1) Utilidades Hamlib RIGCTLD(1)

NOMBRE

rigctld - demonio de control de radio por TCP

SINOPSIS

rigctld [-hlLouV] [-m id] [-r dispositivo] [-p dispositivo] [-d dispositivo] [-P tipo] [-D tipo] [-s baud] [-c id] [-S caracter] [-T IPADDR] [-t numero] [-C parametro=valor] [-X segundos] [-v[-Z]]

DESCRIPCIÓN

El programa rigctld es un demonio de control de radio que maneja las solicitudes de los clientes a través de sockets TCP. Esto permite que múltiples programas de usuario compartan una radio (esto requiere más desarrollo). Múltiples radios pueden ser controladas en diferentes puertos TCP mediante el uso de múltiples procesos rigctld. Tenga en cuenta que múltiples procesos/puertos también son necesarios si algunos clientes usan respuestas extendidas y/o modo VFO. Por lo tanto, pueden ser necesarios hasta 4 procesos/puertos para cada combinación de respuesta extendida/modo VFO. La sintaxis de los comandos es la misma que la de rigctl(1). Se espera que rigctld sea especialmente útil para autores de clientes que utilizan lenguajes como Perl, Python, PHP y otros.

rigctld se comunica con un cliente a través de un socket TCP utilizando comandos de texto compartidos con rigctl. El protocolo es simple, los comandos se envían a rigctld en una línea y rigctld responde a los comandos get con los valores solicitados, uno por línea, cuando tiene éxito, de lo contrario, responde con una línea "RPRT x", donde 'x' es un número negativo que indica el código de error. Los comandos que no devuelven valores responden con la línea "RPRT x", donde 'x' es '0' cuando tiene éxito, de lo contrario, es un número negativo que indica el código de error. Cada línea está terminada por un carácter de nueva línea '\n'. Este protocolo está destinado principalmente al backend de NET rigctl (modelo de radio 2).

Un Protocolo de Respuesta Extendida separado extiende el comportamiento anterior al repetir la cadena de comando recibida como encabezado, cualquier valor devuelto como un par clave: valor, y la cadena "RPRT x" como marcador de fin de respuesta que incluye el valor de éxito o fallo de Hamlib. Consulte la sección PROTOCOLO para obtener detalles. Considere usar este protocolo para clientes que interactuarán directamente con rigctld a través de un socket TCP.

Tenga en cuenta que Hamlib es software de nivel BETA. Si bien muchas bibliotecas de backend carecen de soporte completo para radio, las funciones básicas suelen estar bien soportadas.

Por favor, informe de errores y proporcione comentarios en la dirección de correo electrónico que se indica en la sección ERRORES más abajo. Los parches y mejoras de código enviados a la misma dirección son bienvenidos.

OPCIONES

Este programa sigue la sintaxis habitual de línea de comandos de GNU. Las opciones cortas que toman un argumento pueden tener el valor inmediatamente después o separado por un espacio. Las opciones largas que comienzan con dos guiones ('-') requieren un '=' entre la opción y cualquier argumento.

Aquí hay un resumen de las opciones admitidas:

-m, --modelo=id
Selecciona el número de modelo de la radio.
El valor predeterminado es una radio ficticia.
Consulte la lista de modelos (use "rigctld -l").
Nota: rigctl (o software de terceros que utiliza la API C) utilizará el modelo de radio 2 para NET rigctl (este número de modelo no se utiliza para rigctld aunque aparezca en la lista de modelos).
-r, --archivo-radio=dispositivo
Utiliza dispositivo como nombre de archivo del puerto conectado a la radio.
Típicamente /dev/ttyS0, /dev/ttyS1, /dev/ttyUSB0, etc. en Linux, COM1, COM2, etc. en MS Windows. Las variantes BSD y Mac OS/X tienen sus propias designaciones. Consulte la documentación de su sistema.
Puede ser una dirección de red:puerto, por ejemplo, 127.0.0.1:12345
La cadena especial "uh-rig" puede ser dada para habilitar el soporte de dispositivos micro-ham.
-p, --archivo-ptt=dispositivo
Utiliza dispositivo como nombre de archivo del dispositivo Push-To-Talk utilizando un archivo de dispositivo como se describe arriba.
-d, --archivo-dcd=dispositivo
Utiliza dispositivo como nombre de archivo del dispositivo Data Carrier Detect utilizando un archivo de dispositivo como se describe arriba.
-P, --tipo-ptt=tipo
Utiliza el tipo de dispositivo Push-To-Talk.
Los tipos compatibles son 'RIG' (comando CAT), 'DTR', 'RTS', 'PARALLEL', 'CM108', 'GPIO', 'GPION', 'NONE', anulando el tipo de PTT definido en el backend de la radio.
Algunos efectos secundarios de este comando son que cuando el tipo se establece en DTR, el estado PTT leído proviene del frontend de Hamlib, no se lee de la radio. Cuando se establece en NONE, el estado PTT no puede ser leído ni establecido, incluso si el backend de la radio soporta la lectura/establecimiento del estado PTT desde la radio.
-D, --tipo-dcd=tipo
Utiliza el tipo de dispositivo Data Carrier Detect.
Los tipos compatibles son 'RIG' (comando CAT), 'DSR', 'CTS', 'CD', 'PARALLEL', 'CM108', 'GPIO', 'GPION', 'NONE'.
-s, --velocidad-serial=baud
Establece la velocidad serial a baud.
Utiliza la velocidad serial máxima de las capacidades del backend de la radio (establecida por -m anteriormente) como valor predeterminado.
-c, --civaddr=id
Utiliza id como la dirección CI-V para comunicarse con la radio.
Solo útil para radios Icom y algunas Ten-Tec.
Nota: El id está en notación decimal, a menos que sea precedido por 0x, en cuyo caso es hexadecimal.
-S, --separador=caracter
Utiliza caracter como separador en lugar de nueva línea.
El valor predeterminado es '\n'. Se recomienda usar $ o @ ya que funcionan tanto en Unix como en Windows.
-T, --direccion-escucha=IPADDR
Utiliza IPADDR como la dirección IP de escucha.
El valor predeterminado es CUALQUIERA (0.0.0.0).
rigctld se puede ejecutar y conectar de la siguiente manera:
rigctld
rigctl -m 2
rigctl -m 2 -r 127.0.0.1
rigctl -m 2 -r localhost
rigctl -m 2 -r 192.168.1.1 (dirección IP local)
rigctl -m 2 -r ::1 (en Linux rigctld no escucha en IPV6 por defecto)

rigctld -T 127.0.0.1
rigctl -m 2 (se enlaza a todas las interfaces)
rigctl -m 2 -r 127.0.0.1 (solo se enlaza a 127.0.0.1)
Excepciones: 
rigctl -m 2 -r localhost (solo funciona si localhost es una dirección IPV4)


rigctld -T localhost (se configurará en IPV4 o IPV6 según localhost)
rigctl -m 2
rigctl -m 2 -r localhost
rigctl -m 2 ip6-localhost
Excepciones: 
rigctl -m 2 -r 127.0.0.1 (solo funciona si localhost es una dirección IPV4)
rigctl -m 2 -r ::1 (solo funciona si localhost es una dirección IPV6)

En Linux, donde ip6-localhost es fe00::0: 
rigctld -T ip6-localhost
rigctl -m 2 -r ip6-localhost
-t, --puerto=numero
Utiliza numero como el puerto de escucha TCP.
El puerto predeterminado es 4532.
-C, --set-conf=parametro=valor
Permite pasar parámetros de configuración específicos para el backend. Esto debe utilizarse con precaución y solo cuando sea necesario. Los parámetros disponibles son específicos para cada backend de radio y pueden ser consultados en la documentación de Hamlib, o por el comando 'rigctl -m m -C'.
-X, --timeout=segundos
Establece el tiempo de espera de la conexión del socket TCP a segundos.
El valor predeterminado es 10.
-v, --version
Muestra la información de la versión y sale.
-v, --verbose
Activa la salida detallada. Puede especificarse varias veces. La opción -Z se utiliza para la depuración detallada, activando todas las funciones de depuración.
-h, --help
Muestra un mensaje de ayuda y sale.
-l, --list
Muestra una lista de todos los modelos de radio admitidos por Hamlib y sale.
-o, --no-owner
Cuando se opera con un dispositivo serial, la opción -o deshabilita la prohibición de que múltiples procesos accedan al dispositivo serial. Utilice esta opción con precaución, ya que el acceso concurrente podría corromper los datos transmitidos.
-L, --listen-port
Muestra la información sobre la configuración del puerto de escucha y sale.

El demonio rigctld también puede ser invocado con los siguientes argumentos:

remote_port
El argumento opcional remote_port se utiliza para la opción -r. Este argumento se utiliza para la opción -r. Si se proporciona, el formato es host:puerto. Por ejemplo, 127.0.0.1:12345.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

El valor por defecto es 4532.
Nota: Dado que el puerto por defecto de rotctld es 4533, es aconsejable usar puertos pares para rigctld, por ejemplo, 4532, 4534, 4536, etc.
-L, --show-conf
Lista todos los parámetros de configuración para la radio definida con -m arriba.
-C, --set-conf=parm=val[,parm=val]
Establece uno o más parámetros de configuración. Algunos comunes son:

      backends que lo soportan. Esto permite el uso de datos de transceive y
      espectro.
auto_power_on:True habilita la energización de radios compatibles al
      abrir.
auto_power_off:True habilita la desenergización de radios compatibles
      al cerrar.
auto_disable_screensaver:True habilita la deshabilitación del
      protector de pantalla de radios compatibles al abrir.
dcd_type:Anulación del tipo de interfaz Data Carrier Detect (o squelch).

      Detect (o squelch).

      banda al cambiar de banda para radios Yaesu.

      transverter.

ptt_share:True habilita que el puerto PTT se comparta con otras
      aplicaciones.
ptt_type:Anulación del tipo de interfaz Push-To-Talk.
ptt_pathname:Nombre de la ruta al archivo de dispositivo de Push-To-Talk.

rts_state:ON enciende RTS, OFF lo apaga, Unset lo deshabilita.

      comandos de VFOB hasta que se agote el tiempo de espera.
twiddle_rit:Suprime get_freq en VFOB para la sintonización RIT de
      satélites.
timeout:Tiempo de espera en ms.
write_delay:Retardo en ms entre cada byte enviado.
tuner_control_pathname:Nombre de la ruta a un script/programa para
      controlar un sintonizador con 1 argumento de 0/1 para Sintonizador
      Apagado/Encendido.

Use la opción -L de arriba para obtener una lista de parámetros de configuración para un número de modelo dado.
-u, --dump-caps
Muestra las capacidades de la radio definida con -m arriba y sale.
-l, --list
Lista todos los números de modelo definidos en Hamlib y sale.
La lista está ordenada por número de modelo.
Nota: En Linux la lista puede desplazarse hacia atrás usando Shift-PageUp/Shift-PageDown, o usando las barras de desplazamiento de una terminal virtual en X o la ventana de comandos en Windows. La salida puede ser redirigida a more(1) o less(1), por ejemplo, “rigctld -l | more”.
-o, --vfo
Habilita el modo VFO.
Se requerirá un argumento VFO adicional delante de cada comando apropiado (excepto set_vfo). De lo contrario, se usa ‘currVFO’ cuando esta opción no está establecida y no se usa un argumento VFO adicional.
Ver chk_vfo abajo.
-v, --verbose
Establece el modo detallado, acumulativo (ver DIAGNOSTICS abajo).
-W, --twiddle_timeout=segundos
Habilita el tiempo de espera cuando se detecta manipulación del VFO. Algunas funciones serán ignoradas.
Solo debería ser necesario cuando el software de control debe ser "pausado" para que puedas mover el VFO. El movimiento continuo extiende el tiempo de espera.
-w, --twiddle_rit=segundos
Suprime getfreq de VFOB para que RIT pueda ser manipulado.
-x, --uplink=opción
1=Sub, 2=Main
Para usar GPredict e ignorar get_freq para el VFO de enlace ascendente Sub o Main.
Debería permitir el movimiento del VFO de enlace descendente sin confundir GPredict o el enlace ascendente.
-Z, --debug-time-stamps
Habilita marcas de tiempo para los mensajes de depuración.
Úsese solo en combinación con la opción -v, ya que no genera salida por sí sola.
-A, --password
Establece una contraseña en rigctld que requiere que hamlib use rig_set_password y rigctl use \password para acceder a rigctld. Se mostrará un secreto compartido de 32 caracteres para ser usado en el lado del cliente. (NO IMPLEMENTADO)
-R, --rigctld-idle
Hará que rigctld cierre la radio cuando no haya clientes conectados. Normalmente permanece conectado para acelerar las conexiones.
-b, --bind-all
Hará que rigctld intente conectarse al primer dispositivo de red disponible.
-h, --help
Muestra un resumen de estas opciones y sale.
-V, --version
Muestra la versión de rigctld y sale.

Nota: Algunas opciones pueden no ser implementadas por un backend dado y devolverán un error. Esto es más probable que ocurra con las opciones --set-conf y --show-conf.

Tenga en cuenta que el backend para la radio a controlar, o la propia radio, puede no soportar algunos comandos. En ese caso, la operación fallará con un código de error de Hamlib.

COMANDOS

Los comandos se pueden enviar a través del socket TCP como un carácter único, o como un nombre de comando largo más los valores separados por espacios en una línea terminada por ‘\n’. Ver PROTOCOL.

Dado que la mayoría de las operaciones de Hamlib tienen un método set y uno get, se usará una única letra mayúscula para los métodos set, mientras que la letra minúscula correspondiente se refiere al método get. Cada operación también tiene un nombre largo; prefije con una barra invertida, ‘\’, para enviar un nombre de comando largo todo en minúsculas.

Ejemplo (Perl): “print $socket "\\dump_caps\n";” para ver qué puede hacer el backend de la radio (Nota: En Perl y muchos otros lenguajes, una ‘\’ necesitará ser escapada con una ‘\’ precedente para que, aunque aparezcan dos caracteres de barra invertida en el código, solo uno sea pasado a rigctld. ¡Esto es un posible error, ten cuidado!).

Nota: El backend para la radio a controlar, o la propia radio, puede no soportar algunos comandos. En ese caso, la operación fallará con un mensaje de error de Hamlib.

Aquí hay un resumen de los comandos soportados (En el caso de los comandos set, la cadena itálica entrecomillada se reemplaza por el valor en la descripción. En el caso de los comandos get, la cadena itálica entrecomillada es el nombre de la clave del valor devuelto):

F, set_freq 'Frecuencia'
Establece la 'Frecuencia', en Hz.
La frecuencia puede ser un valor de punto flotante o entero.
f, get_freq
Obtiene la 'Frecuencia', en Hz.
Devuelve un valor entero y el VFO que hamlib considera activo. Ten en cuenta que algunas radios (por ejemplo, todas las Icom) no pueden seguir el VFO actual, por lo que hamlib puede desincronizarse con la radio si el usuario presiona botones de la radio como el VFO. Los clientes de rigctld deben asegurarse de establecer el VFO deseado o usar el modo vfo.
M, set_mode 'Modo' 'AnchoDeBanda'
Establece el 'Modo' y el 'AnchoDeBanda'.
Modo es un token: ‘USB’, ‘LSB’, ‘CW’, ‘CWR’, ‘RTTY’, ‘RTTYR’, ‘AM’, ‘FM’, ‘WFM’, ‘AMS’, ‘PKTLSB’, ‘PKTUSB’, ‘PKTFM’, ‘ECSSUSB’, ‘ECSSLSB’, ‘FA’, ‘SAM’, ‘SAL’, ‘SAH’, ‘DSB’.
AnchoDeBanda está en Hz como un entero, -1 para no cambiar, o ‘0’ para el valor por defecto del backend de la radio. IC7300 puede usar 1,2,3 para seleccionar qué filtro usar.
Nota: Pasar un ‘?’ (consulta) como primer argumento en lugar de un token de Modo devolverá una lista separada por espacios de los Modos soportados por el backend de la radio. Usa esto para determinar los Modos soportados de un backend de radio dado.
m, get_mode
Obtiene el 'Modo' y el 'AnchoDeBanda'.
Devuelve el Modo como un token y el AnchoDeBanda en Hz como en set_mode arriba.
V, set_vfo 'VFO'
Establece el 'VFO'.
VFO es un token: ‘VFOA’, ‘VFOB’, ‘VFOC’, ‘currVFO’, ‘VFO’, ‘MEM’, ‘Main’, ‘Sub’, ‘TX’, ‘RX’, ‘MainA’, ‘MainB’, ‘MainC’, ‘SubA’, ‘SubB’ ‘SubC’.
En modo VFO (ver opción --vfo arriba), solo se requiere un parámetro VFO:

$ rigctl -m 229 -r /dev/rig -o
Rig command: V
VFO: VFOB
Rig command:

v, get_vfo
Obtiene el 'VFO' actual.
Devuelve el VFO como un token como en set_vfo arriba.
J, set_rit 'RIT'
Establece el 'RIT'.
RIT está en Hz y puede ser + o -. Un valor de ‘0’ reinicia RIT (Receiver Incremental Tuning) para que coincida con la frecuencia del VFO.

YYYY-MM-DDTHH:MM:SS.SSS+ZZ (donde +ZZ es un desplazamiento UTC +/- HH)

YYYY-MM-DDTHH:MM:SS+ZZ
YYYY-MM-DDTHH:MM:SS+ZZZZ
YYYY-MM-DDTHH:MM+ZZ
YYYY-MM-DDTHH:MM+ZZZZ
YYYY-MM-DD (establece solo la fecha)
local (establece ambos relojes en hora local)
utc (establece ambos relojes en hora UTC)

PROTOCOLO

Hay dos protocolos en uso por rigctld: el Protocolo Predeterminado y el Protocolo de Respuesta Extendida.

El Protocolo Predeterminado está destinado principalmente a la comunicación entre las funciones de la biblioteca Hamlib y rigctld (“NET rigctl”, disponible usando el modelo de radio ‘2’).

El Protocolo de Respuesta Extendida está destinado a ser utilizado con scripts u otros programas que interactúan directamente con rigctld, ya que se proporciona una retroalimentación consistente.

Protocolo Predeterminado

El Protocolo Predeterminado es intencionalmente simple. Los comandos se ingresan en una sola línea con los valores necesarios. En la práctica, se obtienen resultados confiables terminando cada cadena de comando con un carácter de nueva línea, ‘\n’.

Ejemplo de comandos para establecer frecuencia y modo (código Perl (texto escrito mostrado en negrita)):


print $socket "F 14250000\n";
print $socket "\\set_mode LSB 2400\n";   # el '\' inicial se escapa

Se enviará una respuesta de una línea como respuesta a los comandos set, “RPRT x\n”, donde x es el código de error de Hamlib, siendo ‘0’ el éxito del comando.

Las respuestas de los comandos get de rigctld son valores de texto y coinciden con los mismos tokens utilizados en los comandos set. Cada valor se devuelve en su propia línea. En caso de error, se devuelve la cadena “RPRT x\n”, donde x es el código de error de Hamlib.

Ejemplo de obtención de frecuencia (código Perl):


print $socket "f\n";
"14250000\n"

La mayoría de las funciones get devuelven de uno a tres valores. Una excepción notable es el comando dump_caps, que devuelve muchas líneas de pares clave:valor.

Este protocolo es utilizado principalmente por el backend “NET rigctl” (rigctl modelo 2), que permite a las aplicaciones ya escritas para la API C de Hamlib aprovechar rigctld sin necesidad de reescribir el código de la aplicación. El usuario de una aplicación puede seleccionar el modelo de rotador 2 (“NET rigctl”) y luego establecer rig_pathname en “localhost:4532” u otro host:puerto de red (establecido por las opciones -T/-t, respectivamente, anteriormente).

Protocolo de Respuesta Extendida

El protocolo de Respuesta Extendida agrega varias reglas a las cadenas devueltas por rigctld y agrega una regla para la sintaxis del comando.

1. El comando recibido por rigctld se repite con su nombre de comando largo seguido de los valores (si los hay) recibidos del cliente, terminados por el separador de respuesta especificado, como el primer registro de la respuesta.

2. El último registro de cada bloque es la cadena “RPRT x\n”, donde x es el valor numérico de retorno de la función del backend de Hamlib que fue llamada por el comando.

3. Cualquier registro que consista en valores de datos devueltos por el backend de radio se antepone con una cadena seguida inmediatamente por dos puntos, luego un espacio y luego el valor terminado por el separador de respuesta. Por ejemplo, “Frequency: 14250000\n” cuando el comando se antepuso con ‘+’.

4. Todos los comandos recibidos serán confirmados por rigctld con registros de las reglas 1 y 2. Los registros de la regla 3 solo se devuelven cuando se deben devolver valores de datos al cliente.

Un ejemplo de respuesta a un comando set_mode enviado desde el símbolo del sistema (tenga en cuenta el ‘+’ antepuesto):


$ echo "+M USB 2400" | nc -w 1 localhost 4532
set_mode: USB 2400
RPRT 0

En este caso, el nombre de comando largo y los valores se devuelven en la primera línea, y la segunda línea contiene el marcador de fin de bloque y el valor numérico del backend de radio que indica el éxito.

Un ejemplo de respuesta a una consulta get_mode:


$ echo "+\get_mode" | nc -w 1 localhost 4532
get_mode:
Mode: USB
Passband: 2400
RPRT 0
Nota: El ‘\’ todavía se requiere para el nombre de comando largo, incluso con el carácter ERP.

En este caso, como no se pasa ningún valor a rigctld, la primera línea consta únicamente del nombre de comando largo. La última línea muestra que el comando fue procesado con éxito por el backend del transceptor.

Invocar el Protocolo de Respuesta Extendida requiere anteponer un comando con un carácter de puntuación. Como se muestra en los ejemplos anteriores, anteponer un carácter ‘+’ al comando da como resultado que las respuestas se separen por un carácter de nueva línea (‘\n’). Cualquier otro carácter de puntuación reconocido por la función ispunct() de C, excepto ‘\’, ‘?’ o ‘_’, hará que ese carácter se convierta en el separador de respuesta y toda la respuesta estará en una sola línea.

Resumen de caracteres separadores:

‘+’
Cada registro de la respuesta se anexa con una nueva línea (‘\n’).
‘;’, ‘|’, o ‘,’
Cada registro de la respuesta se anexa con el carácter dado, lo que resulta en toda la respuesta en una sola línea.
Estos son separadores de registro comunes para representaciones de texto de datos de hojas de cálculo, etc.
‘?’
Reservado para ayuda en rigctl.
‘_’
Reservado para el comando corto get_info.
‘#’
Reservado para comentarios al leer un archivo de comandos.
Nota: ¡Otros caracteres de puntuación no han sido probados! Úselos bajo su propio riesgo.

Por ejemplo, invocando

Una consulta get_mode con un punto y coma inicial ‘;’ devuelve:


get_mode:;Modo: USB;Banda pasante: 2400;RPRT 0

O, usando el carácter de barra vertical ‘|’ devuelve:


get_mode:|Modo: USB|Banda pasante: 2400|RPRT 0

Y un comando set_mode precedido por un ‘|’ devuelve:


set_mode: USB 2400|RPRT 0

Dicho formato permitirá leer una respuesta como un único evento utilizando un separador de respuesta preferido. ¡No se han probado otros caracteres de puntuación!

DIAGNÓSTICOS

La opción -v, --verbose permite diferentes niveles de diagnósticos que se envían a stderr y corresponden a -v para BUG, -vv para ERR, -vvv para WARN, -vvvv para VERBOSE, o -vvvvv para TRACE.

Un nivel de verbosidad dado es útil para proporcionar la información de depuración necesaria a la dirección de correo electrónico que se indica a continuación. Por ejemplo, la salida TRACE muestra todos los valores enviados y recibidos de la radio, lo cual es muy útil para el desarrollo de bibliotecas de backend de radio y puede ser solicitado por los desarrolladores.

EJEMPLOS

Inicia rigctld para un Yaesu FT-920 utilizando un adaptador USB a serie y en segundo plano:


$ rigctld -m 1014 -r /dev/ttyUSB1 &

Inicia rigctld para un Yaesu FT-920 utilizando un adaptador USB a serie mientras se establece la velocidad en baudios y los bits de parada, y se ejecuta en segundo plano:


$ rigctld -m 1014 -r /dev/ttyUSB1 -s 4800 -C stop_bits=2 &

Inicia rigctld para un Elecraft K3 en COM2 en MS Windows:


$ rigctld -m 2029 -r COM2

Conéctate al rigctld en ejecución y establece la frecuencia a 14.266 MHz con un tiempo de espera de lectura de 1 segundo utilizando el protocolo predeterminado desde el prompt de la shell:


$ echo "\set_freq 14266000" | nc -w 1 localhost 4532

Conéctate a un rigctld en ejecución con rigctl en el host local:


$ rigctl -m2

SEGURIDAD

Ninguna autenticación; NO deje este puerto TCP abierto a Internet. Por favor, pregunte si se necesita mayor seguridad o considere usar un túnel Secure Shell (ssh(1)).

Como rigctld no necesita mayores permisos que rigctl, es aconsejable no iniciar rigctld como “root” o con otra cuenta de usuario del sistema para limitar cualquier vulnerabilidad.

ERRORES

El demonio no se está separando ni ejecutando en segundo plano por sí mismo.

No hay método para salir del demonio, por lo que se debe usar el comando kill(1) para terminarlo.

Múltiples clientes utilizando el demonio pueden experimentar contención con la radio conectada.
