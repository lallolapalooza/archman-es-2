GDBSERVER(1) GNU Development Tools GDBSERVER(1)

NOMBRE

gdbserver - Servidor Remoto para el Depurador GNU

SINOPSIS

gdbserver comm prog [args...]

gdbserver --attach comm pid

gdbserver --multi comm

DESCRIPCIÓN

gdbserver es un programa que permite ejecutar GDB en una máquina diferente a la que está ejecutando el programa que se está depurando.

Uso (lado del servidor (objetivo)):

Primero, necesitas tener una copia del programa que deseas depurar en el sistema objetivo. El programa puede ser "stripped" (eliminando símbolos de depuración) para ahorrar espacio si es necesario, ya que a gdbserver no le importan los símbolos. Todo el manejo de símbolos lo realiza GDB que se ejecuta en el sistema anfitrión.

Para usar el servidor, inicia sesión en el sistema objetivo y ejecuta el programa gdbserver. Debes indicarle (a) cómo comunicarse con GDB, (b) el nombre de tu programa y (c) sus argumentos. La sintaxis general es:

objetivo> gdbserver <comm> <programa> [<args> ...]

Por ejemplo, usando un puerto serie, podrías decir:

objetivo> gdbserver /dev/com1 emacs foo.txt

Esto le dice a gdbserver que depure emacs con el argumento foo.txt, y que se comunique con GDB a través de /dev/com1. gdbserver ahora espera pacientemente a que el GDB anfitrión se comunique con él.

Para usar una conexión TCP, podrías decir:

objetivo> gdbserver host:2345 emacs foo.txt

Esto dice prácticamente lo mismo que el último ejemplo, excepto que nos comunicaremos con el GDB "host" vía TCP. El argumento "host:2345" significa que esperamos ver una conexión TCP desde "host" al puerto TCP local 2345. (Actualmente, la parte "host" se ignora.) Puedes elegir cualquier número para el puerto siempre que no entre en conflicto con ningún servicio TCP existente en el sistema objetivo. El mismo número de puerto debe usarse en el comando "target remote" del GDB anfitrión, que se describirá en breve. Ten en cuenta que si eliges un número de puerto que entra en conflicto con otro servicio, gdbserver mostrará un mensaje de error y saldrá.

gdbserver también puede adjuntarse a programas en ejecución. Esto se logra a través del argumento --attach. La sintaxis es:

objetivo> gdbserver --attach <comm> <pid>

pid es el ID del proceso de un proceso actualmente en ejecución. No es necesario apuntar gdbserver a un binario para el proceso en ejecución.

Para iniciar "gdbserver" sin proporcionar un comando inicial para ejecutar o un ID de proceso al que adjuntarse, usa la opción de línea de comandos --multi. En ese caso, debes conectarte usando "target extended-remote" para iniciar el programa que deseas depurar.

objetivo> gdbserver --multi <comm>

Uso (lado del anfitrión):

Necesitas una copia sin "stripped" del programa objetivo en tu sistema anfitrión, ya que GDB necesita examinar sus tablas de símbolos y similares. Inicia GDB como lo harías normalmente, con el programa objetivo como primer argumento. (Puede que necesites usar la opción --baud si la línea serie funciona a una velocidad diferente a 9600 baudios.) Eso es "gdb TARGET-PROG", o "gdb --baud BAUD TARGET-PROG". Después de eso, el único comando nuevo que necesitas conocer es "target remote" (o "target extended-remote"). Su argumento es ya sea un nombre de dispositivo (generalmente un dispositivo serie, como /dev/ttyb), o un descriptor "HOST:PORT". Por ejemplo:

(gdb) target remote /dev/ttyb

se comunica con el servidor a través de la línea serie /dev/ttyb, y:

(gdb) target remote el-objetivo:2345

se comunica a través de una conexión TCP al puerto 2345 en el anfitrión `el-objetivo', donde previamente ejecutaste gdbserver con el mismo número de puerto. Ten en cuenta que para conexiones TCP, debes iniciar gdbserver antes de usar el comando `target remote', de lo contrario, podrías recibir un error como `Connection refused'.

gdbserver también puede depurar múltiples "inferiors" (procesos hijos) a la vez, descrito en el manual de GDB en el nodo "Inferiors Connections and Programs" -- comando de shell "info -f gdb -n 'Inferiors Connections and Programs'". En tal caso, usa la variante del comando GDB "extended-remote":

(gdb) target extended-remote el-objetivo:2345

La opción --multi de gdbserver puede usarse o no en tal caso.

OPCIONES

Hay tres modos diferentes para invocar gdbserver:

  • Depurar un programa específico especificado por su nombre de programa: 
    gdbserver <comm> <prog> [<args>...]

    El parámetro comm especifica cómo debe comunicarse el servidor con GDB; es el nombre de un dispositivo (para usar una línea serie), un número de puerto TCP (":1234"), o "-" o "stdio" para usar la entrada/salida estándar de "gdbserver". Especifica el nombre del programa a depurar en prog. Cualquier argumento restante se pasará al programa tal cual. Cuando el programa salga, GDB cerrará la conexión, y "gdbserver" saldrá.

  • Depurar un programa específico especificando el ID del proceso de un programa en ejecución: 
    gdbserver --attach <comm> <pid>

    El parámetro comm es como se describió anteriormente. Proporciona el ID del proceso de un programa en ejecución en pid; GDB hará el resto. Al igual que con el modo anterior, cuando el proceso pid salga, GDB cerrará la conexión y "gdbserver" saldrá.

  • Modo multi-proceso -- depurar más de un programa/proceso: 
    gdbserver --multi <comm>

    En este modo, GDB puede instruir a gdbserver qué comando(s) ejecutar. A diferencia de los otros 2 modos, GDB no cerrará la conexión cuando un proceso que se está depurando salga, por lo que puedes depurar varios procesos en la misma sesión.

En cada uno de los modos puedes especificar estas opciones:

--help
Lista todas las opciones, con breves explicaciones.
--version
Esta opción hace que gdbserver imprima su número de versión y salga.
--attach
gdbserver se adjuntará a un programa en ejecución. La sintaxis es: 
objetivo> gdbserver --attach <comm> <pid>

pid es el ID del proceso de un proceso actualmente en ejecución. No es necesario apuntar gdbserver a un binario para el proceso en ejecución.

--multi
Para iniciar "gdbserver" sin proporcionar un comando inicial para ejecutar o un ID de proceso al que adjuntarse, usa esta opción de línea de comandos. Luego puedes conectarte usando "target extended-remote" e iniciar el programa que deseas depurar. La sintaxis es: 
objetivo> gdbserver --multi <comm>
--debug[=opcion1,opcion2,...]
Instruye a "gdbserver" para que muestre información de estado adicional sobre el proceso de depuración. Esta opción está destinada al desarrollo de "gdbserver" y para informes de errores a los desarrolladores.

Cada opción es el nombre de un componente para el cual se debe habilitar la depuración. La lista de opciones posibles es all, threads, event-loop, remote. La opción especial all habilita todos los componentes. La lista de opciones se procesa de izquierda a derecha, y una opción puede ir precedida por el carácter "-" para deshabilitar la salida para ese componente, por lo que podrías escribir:

objetivo> gdbserver --debug=all,-event-loop

para activar la salida de depuración para todos los componentes excepto event-loop. Si no se pasan opciones a --debug, se trata como equivalente a --debug=thre

OPCIONES

--debug
Habilita el modo de depuración para "gdbserver". En este modo, "gdbserver" imprimirá mensajes detallados sobre su actividad, lo cual puede ser útil para diagnosticar problemas. Tenga en cuenta que la salida exacta de esta opción puede cambiar en futuras versiones de "gdbserver".
--debug-file=nombre_archivo
Instruye a "gdbserver" para que envíe cualquier salida de depuración al nombre_archivo especificado. Esta opción está pensada para el desarrollo de "gdbserver" y para reportar errores a los desarrolladores.
--debug-format=opcion1[,opcion2,...]
Instruye a "gdbserver" para que incluya información adicional en cada línea de la salida de depuración.
--wrapper
Especifica un programa envoltorio (wrapper) para lanzar programas para depurar. La opción debe ir seguida del nombre del envoltorio, luego los argumentos de línea de comandos que se pasarán al envoltorio, y luego "--" indicando el fin de los argumentos del envoltorio.
--once
Por defecto, gdbserver mantiene el puerto TCP de escucha abierto, permitiendo conexiones adicionales. Sin embargo, si inicia "gdbserver" con la opción --once, dejará de escuchar intentos de conexión después de conectarse a la primera sesión de GDB.
