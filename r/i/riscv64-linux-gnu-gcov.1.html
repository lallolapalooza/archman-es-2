DESCRIPCIÓN

gcov es un programa de cobertura de pruebas. Úselo junto con GCC para analizar sus programas y así crear código más eficiente y rápido, y para descubrir partes no probadas de su programa. Puede usar gcov como una herramienta de perfilado para ayudar a descubrir dónde sus esfuerzos de optimización afectarán mejor a su código. También puede usar gcov junto con la otra herramienta de perfilado, gprof, para evaluar qué partes de su código utilizan la mayor cantidad de tiempo de cómputo.

Las herramientas de perfilado le ayudan a analizar el rendimiento de su código. Usando un perfilador como gcov o gprof, puede obtener estadísticas básicas de rendimiento, como:

  • cuántas veces se ejecuta cada línea de código
  • qué líneas de código se ejecutan realmente
  • cuánto tiempo de cómputo utiliza cada sección de código

Una vez que conozca estos detalles sobre cómo funciona su código cuando se compila, puede examinar cada módulo para ver cuáles deberían optimizase. gcov le ayuda a determinar dónde trabajar en la optimización.

Los desarrolladores de software también utilizan la cobertura de pruebas junto con conjuntos de pruebas, para asegurarse de que el software es realmente lo suficientemente bueno para una versión. Los conjuntos de pruebas pueden verificar que un programa funciona como se espera; un programa de cobertura verifica qué parte del programa es ejercitada por el conjunto de pruebas. Los desarrolladores pueden entonces determinar qué tipos de casos de prueba deben añadirse a los conjuntos de pruebas para crear tanto mejores pruebas como un mejor producto final.

Debería compilar su código sin optimización si planea usar gcov, ya que la optimización, al combinar algunas líneas de código en una función, puede no proporcionarle tanta información como necesita para buscar `puntos calientes' donde el código utiliza una gran cantidad de tiempo de cómputo. Igualmente, dado que gcov acumula estadísticas por línea (en la resolución más baja), funciona mejor con un estilo de programación que coloca solo una instrucción por línea. Si utiliza macros complicadas que se expanden a bucles u otras estructuras de control, las estadísticas son menos útiles: solo informan sobre la línea donde aparece la llamada a la macro. Si sus macros complejas se comportan como funciones, puede reemplazarlas con funciones en línea para resolver este problema.

gcov crea un archivo de registro llamado archivo_fuente.gcov que indica cuántas veces se ha ejecutado cada línea de un archivo fuente archivo_fuente.c. Puede usar estos archivos de registro junto con gprof para ayudar a ajustar el rendimiento de sus programas. gprof proporciona información de temporización que puede usar junto con la información que obtiene de gcov.

gcov solo funciona en código compilado con GCC. No es compatible con ningún otro mecanismo de perfilado o cobertura de pruebas.

OPCIONES

-a
--all-blocks
Escribe recuentos de ejecución individuales para cada bloque básico. Normalmente gcov solo muestra los recuentos de ejecución para los bloques principales de una línea. Con esta opción puede determinar si los bloques dentro de una misma línea no se están ejecutando.
-b
--branch-probabilities
Escribe las frecuencias de las ramas en el archivo de salida, y escribe información resumen de las ramas en la salida estándar. Esta opción le permite ver con qué frecuencia se tomó cada rama en su programa. Las ramas incondicionales no se mostrarán, a menos que se proporcione la opción -u.
-c
--branch-counts
Escribe las frecuencias de las ramas como el número de ramas tomadas, en lugar del porcentaje de ramas tomadas.
-g
--conditions
Escribe la cobertura de condiciones en el archivo de salida, y escribe información resumen de las condiciones en la salida estándar. Esta opción le permite ver si las condiciones en su programa al menos una vez tuvieron un efecto independiente en el resultado de la expresión booleana (cobertura de decisión/condición modificada). Esto requiere que compile la fuente con -fcondition-coverage.
-e
--prime-paths
Escribe la cobertura de rutas en el archivo de salida, y escribe información resumen de las rutas en la salida estándar. Esta opción le permite ver cuántas rutas principales se tomaron al menos una vez. Una ruta es una secuencia de bloques básicos. Una ruta es simple si no tiene bloques repetidos (sin bucles) excepto quizás el primer y último bloque, y principal si es una ruta simple de longitud máxima. Para la salida regular, esta opción solo incluye el número de rutas cubiertas. Para obtener información más detallada sobre las rutas, puede usar --prime-paths-lines o --prime-paths-source. Con --json-format se incluyen todos los detalles de las rutas en la salida. Esto requiere que compile la fuente con -fpath-coverage.
--prime-paths-lines [=tipo]
Escribe la cobertura de rutas en el archivo de salida, y escribe información resumen de las rutas en la salida estándar. Esta opción le permite ver cuántas rutas principales se tomaron al menos una vez, y un informe denso sobre las rutas cubiertas o no cubiertas y cómo cubrirlas. Este modo es útil para informes automatizados y seguimiento del progreso. tipo puede omitirse, o ser uno de:
  • uncovered - Incluir las rutas no cubiertas (no tomadas). Este es el valor predeterminado.
  • covered - Incluir las rutas cubiertas (tomadas).
  • both - Incluir todas las rutas. Esto es equivalente a usar tanto covered como uncovered.

Este es un ejemplo de salida de --prime-paths-lines:

rutas cubiertas 12 de 15
ruta  2 no cubierta: líneas 8 8(falso) 11(verdadero) 11 13(verdadero) 13(verdadero) 14 17
ruta  3 no cubierta: líneas 8 8(falso) 11(verdadero) 11 13(verdadero) 13(falso) 16 17
ruta  4 no cubierta: líneas 8 8(falso) 11(verdadero) 11 13(falso) 16 17

Esto significa que para cubrir la ruta 2 debe ejecutar las líneas 8, 11, 13, 14 y 17, evaluando la decisión en 8 como falsa y las decisiones en 11 y 13 como "falso".

--prime-paths-source [=tipo]
Escribe la cobertura de rutas en el archivo de salida, y escribe información resumen de las rutas en la salida estándar. Esta opción le permite ver cuántas rutas principales se tomaron al menos una vez, y un informe detallado sobre las rutas no cubiertas y cómo cubrirlas. Este modo es útil para comprender las rutas y las interacciones entre secciones de su programa. tipo puede omitirse, o ser uno de:
  • uncovered - Incluir las rutas no cubiertas (no tomadas). Este es el valor predeterminado.
  • covered - Incluir las rutas cubiertas (tomadas).
  • both - Incluir todas las rutas. Esto es equivalente a usar tanto covered como uncovered.

Este es un ejemplo de --prime-paths- ruta 10 no cubierta: BB 3: 8: para (i = 0; i < 10; i++) BB 3: 9: total += i; BB 4: (falso) 8: para (i = 0; i < 10; i++) BB 5: (verdadero) 11: int v = total > 100 ? 1 : 2; BB 6: 11: int v = total > 100 ? 1 : 2; BB 8: (falso) 13: si (total != 45 && v == 1) BB 11: 16: printf ("Éxito\n"); BB 12: 17: retornar 0;

La primera columna (BB) es la secuencia de bloques básicos (ver -w). La columna central (verdadero/falso) es la decisión para esa línea. La tercera columna es el número de línea. La cuarta columna es la línea en sí. Estas líneas deben ejecutarse en este orden para cubrir la ruta 10.

-d
--display-progress
Muestra el progreso en la salida estándar.
-f
--function-summaries
Genera resúmenes para cada función además del resumen a nivel de archivo.
--include regex
Incluye funciones que coincidan con regex. Esta opción hace que gcov solo informe sobre funciones que coincidan con la expresión regular extendida regex. Esta opción se puede combinar con --exclude. Si una función coincide tanto con inclusiones como con exclusiones, la última inclusión/exclusión es la que se aplica. Por defecto, gcov informa sobre todas las funciones, pero si se utiliza --include, solo se informará sobre las funciones que coincidan con la inclusión.
--exclude regex
Excluye funciones que coincidan con regex. Esta opción hace que gcov no informe sobre funciones que coincidan con la expresión regular extendida regex. Esta opción se puede combinar con --include. Si una función coincide tanto con inclusiones como con exclusiones, la última inclusión/exclusión es la que se aplica. Por defecto, gcov informa sobre todas las funciones, y si se utiliza --exclude, se omitirán las funciones que coincidan con él.
-h
--help
Muestra ayuda sobre el uso de gcov (en la salida estándar) y sale sin realizar ningún procesamiento adicional.
-j
--json-format
Genera el archivo gcov en un formato intermedio JSON fácil de analizar que no requiere código fuente para su generación. El archivo JSON se comprime con el algoritmo de compresión gzip y los archivos tienen la extensión .gcov.json.gz.

La estructura del JSON es la siguiente:

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Los campos del elemento raíz tienen la siguiente semántica:

  • current_working_directory: directorio de trabajo donde se compiló una unidad de compilación
  • data_file: nombre del archivo de datos (GCDA)
  • format_version: versión semántica del formato

    Cambios en la versión 2:

*
calls: se añade información sobre las llamadas a funciones
*
gcc_version: versión del compilador GCC

Cada file tiene la siguiente forma:

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Los campos del elemento file tienen la siguiente semántica:

*
file_name: nombre del archivo fuente

Cada function tiene la siguiente forma:

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Los campos del elemento function tienen la siguiente semántica:

  • blocks: número de bloques que hay en la función
  • blocks_executed: número de bloques ejecutados de la función
  • demangled_name: nombre "desenredado" de la función
  • end_column: columna en el archivo fuente donde termina la función
  • end_line: línea en el archivo fuente donde termina la función
  • execution_count: número de ejecuciones de la función
  • name: nombre de la función
  • start_column: columna en el archivo fuente donde comienza la función
  • start_line: línea en el archivo fuente donde comienza la función

Tenga en cuenta que los números de línea y columna se cuentan a partir de 1. En la implementación actual, start_line y start_column no incluyen parámetros de plantilla ni el tipo de retorno inicial, pero es probable que esto se corrija en el futuro.

Cada line tiene la siguiente forma:

{
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

Las ramas y llamadas solo están presentes con la opción -b. Los campos del elemento line tienen la siguiente semántica:

  • block_ids: IDs de los bloques básicos que pertenecen a la línea
  • count: número de ejecuciones de la línea
  • line_number: número de línea
  • unexecuted_block: indicador de si la línea contiene un bloque no ejecutado (no todas las sentencias de la línea se ejecutan)
  • function_name: nombre de la función a la que pertenece esta line (para una línea con sentencias intercaladas, puede no estar establecido)

Cada branch tiene la siguiente forma:

{
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

Los campos del elemento branch tienen la siguiente semántica:

  • count: número de ejecuciones de la rama
  • fallthrough: true cuando la rama es una rama de continuación
  • throw: true cuando la rama es una rama excepcional
  • source_block_id: ID del bloque básico donde ocurre esta rama
  • destination_block_id: ID del bloque básico al que salta esta rama

Cada call tiene la siguiente forma:

{
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

Los campos del elemento call tienen la siguiente semántica:

  • returned: número de veces que una llamada a función retornó (el número de llamadas es igual a line::count)
  • source_block_id: ID del bloque básico donde ocurre esta llamada
  • destination_block_id: ID del bloque básico al que continúa la llamada después del retorno

Cada condition tiene la siguiente forma:

{
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

Los campos del elemento condition tienen la siguiente semántica:

  • count: número de resultados de condición en esta expresión
  • covered: número de resultados de condición cubiertos en esta expresión
  • not_covered_true: términos, por índice, que no se vieron como verdaderos en esta expresión
  • not_covered_false: términos, por índice, que no se vieron como falsos en esta expresión
-H
--human-readable
Escribe los recuentos en formato legible para humanos (como 24.6k).
-k
--use-colors
Utiliza colores para las líneas de código que tienen cobertura cero. Usamos color rojo para las líneas no excepcionales y cian para las excepcionales. Se usan los mismos colores para los bloques básicos con la opción -a.
-l
--long-file-names
Crea nombres de archivo largos para los archivos fuente incluidos. Por ejemplo, si el archivo de encabezado x.h contiene código y fue incluido en el archivo a.c, al ejecutar gcov en el archivo a.c se producirá un archivo de salida llamado a.c##x.h.gcov en lugar de x.h.gcov. Esto puede ser útil si x.h se incluye en varios archivos fuente y deseas ver las contribuciones individuales. Si usas la opción -p, tanto el nombre del archivo que incluye como el incluido serán nombres de ruta completos.
-m
--demangled-names
Muestra los nombres de función "desenredados" en la salida. El valor por defecto es mostrar los nombres de función "mangled".
-M
--filter-on-demangled
Hace que --include y --exclude coincidan con nombres "desenredados". Esto solo afecta a la coincidencia y no implica --demangled-names, pero se puede combinar de forma segura con ella.
-n
--no-output
No crea el archivo de salida gcov.
-o directorio|archivo
--object-directory directorio
--object-file archivo
Especifica el directorio que contiene los archivos de datos gcov, o el nombre de ruta del objeto. Los archivos de datos .gcno y .gcda se buscan utilizando esta opción. Si se especifica un directorio, los archivos de datos estarán en ese directorio y se nombrarán según el nombre del archivo de entrada, sin su extensión. Si se especifica un archivo aquí, los archivos de datos se nombrarán según ese archivo, sin su extensión.
-p
--preserve-paths
Conserva la información completa de la ruta en los nombres de los archivos .gcov generados. Sin esta opción, solo se utiliza el componente del nombre de archivo. Con esta opción, se utilizan todos los directorios, con los caracteres / traducidos a caracteres #, los componentes del directorio . eliminados y los componentes .. irremovibles renombrados a ^. Esto es útil si los archivos fuente están en varios directorios diferentes.
-q
--use-hotness-colors
Emite una salida coloreada similar a perf para líneas activas. La leyenda de la escala de colores se imprime al principio del archivo de salida.
-r
--relative-only
Solo emite información sobre archivos fuente con un nombre de ruta relativo (después de la elisión del prefijo de origen). Las rutas absolutas suelen ser archivos de cabecera del sistema y la cobertura de cualquier función en línea en ellos normalmente no es interesante.
-s directorio
--source-prefix directorio
Un prefijo para los nombres de los archivos fuente que se eliminará al generar los archivos de salida de cobertura. Esta opción es útil cuando se compila en un directorio separado y no se desea la ruta al directorio fuente al determinar los nombres de los archivos de salida. Tenga en cuenta que esta detección de prefijo se aplica antes de determinar si el archivo fuente es absoluto.
-t
--stdout
Salida al flujo de salida estándar en lugar de a archivos de salida.
-u
--unconditional-branches
Cuando se proporcionan probabilidades de rama, incluye las de ramas incondicionales. Las ramas incondicionales normalmente no son interesantes.
-v
--version
Muestra el número de versión de gcov (en la salida estándar) y sale sin realizar ningún procesamiento adicional.
-w
--verbose
Imprime información detallada relacionada con bloques básicos y arcos.
-x
--hash-filenames
Cuando se usa --preserve-paths, gcov utiliza la ruta completa de los archivos fuente para crear un nombre de archivo de salida. Esto puede dar lugar a nombres de archivo largos que pueden desbordar los límites del sistema de archivos. Esta opción crea nombres del tipo nombre-archivo-fuente##md5.gcov, donde el componente nombre-archivo-fuente es la parte final del nombre de archivo y el componente md5 se calcula a partir del nombre completo manipulado que se habría utilizado de otro modo. La opción es una alternativa a --preserve-paths en sistemas que tienen un límite en el sistema de archivos.

gcov debe ejecutarse con el directorio actual igual que cuando se invocó al compilador. De lo contrario, no podrá localizar los archivos fuente. gcov produce archivos llamados nombre-manipulado.gcov en el directorio actual. Estos contienen la información de cobertura del archivo fuente al que corresponden. Se produce un archivo .gcov por cada archivo fuente (o de cabecera) que contiene código, que se compiló para producir los archivos de datos. La parte nombre-manipulado del nombre del archivo de salida suele ser simplemente el nombre del archivo fuente, pero puede ser algo más complicado si se dan las opciones -l o -p. Consulte esas opciones para obtener detalles.

Si invoca gcov con varios archivos de entrada, se sumarán las contribuciones de cada archivo de entrada. Normalmente, lo invocaría con la misma lista de archivos que el enlace final de su ejecutable.

Los archivos .gcov contienen campos separados por : junto con el código fuente del programa. El formato es

<conteo_ejecucion>:<numero_linea>:<texto_linea_fuente>

Puede que información adicional de bloques suceda a cada línea, cuando se solicite mediante una opción de línea de comandos. El conteo_ejecucion es - para líneas que no contienen código. Las líneas no ejecutadas se marcan con ##### o =====, dependiendo de si son accesibles por rutas no excepcionales o solo por rutas excepcionales como los manejadores de excepciones de C++, respectivamente. Dada la opción -a, los bloques no ejecutados se marcan con $$$$$ o %%%%%, dependiendo de si un bloque básico es accesible a través de rutas no excepcionales o excepcionales. Los bloques básicos ejecutados que tienen una instrucción con un conteo_ejecucion cero terminan con el carácter * y se colorean con color magenta con la opción -k. Esta funcionalidad no es compatible en Ada.

Tenga en cuenta que GCC puede eliminar completamente los cuerpos de las funciones que no son necesarias, por ejemplo, si se inician en todas partes. Dichas funciones se marcan con -, lo que puede ser confuso. Utilice las opciones -fkeep-inline-functions y -fkeep-static-functions para conservar estas funciones y permitir que gcov muestre correctamente su conteo_ejecucion.

Algunas líneas de información al principio tienen el numero_linea cero. Estas líneas de preámbulo tienen el formato

-:0:<etiqueta>:<valor>

El orden y el número de estas líneas de preámbulo se aumentarán a medida que avance el desarrollo de gcov; no confíe en que permanezcan sin cambios. Utilice etiqueta para localizar una línea de preámbulo específica.

La información adicional de bloques tiene el formato

<etiqueta> <informacion>

La informacion es legible por humanos, pero está diseñada para ser lo suficientemente simple como para ser analizada por máquinas.

Al imprimir porcentajes, 0% y 100% solo se imprimen cuando los valores son exactamente 0% y 100% respectivamente. Otros valores que convencionalmente se redondearían a 0% o 100% se imprimen en su lugar como el valor no límite más cercano.

Al usar gcov, primero debe compilar su programa con la opción especial de GCC --coverage. Esto le indica al compilador que genere información adicional necesaria para gcov (básicamente un grafo de flujo del programa) y también incluye código adicional en los archivos objeto para generar la información de perfilado adicional necesaria para gcov. Estos archivos adicionales se colocan en el directorio donde se encuentra el archivo objeto.

La ejecución del programa hará que se genere una salida de perfilado. Por cada archivo fuente compilado con -fprofile-arcs, se colocará un archivo .gcda acompañante en el directorio del archivo objeto.

La ejecución de gcov con los nombres de los archivos fuente de su programa como argumentos producirá ahora un listado del código junto con la frecuencia de ejecución para cada línea. Por ejemplo, si su programa se llama tmp.cpp, esto es lo que verá cuando utilice la utilidad básica de gcov:

$ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m
File 'tmp.cpp'
Lines executed:92.86% of 14
Creating 'tmp.cpp.gcov'

Para cada función, se imprime una línea que muestra cuántas veces se llama a la función, cuántas veces retorna y qué porcentaje de los bloques de la función se ejecutaron.

Para cada bloque básico, se imprime una línea después de la última línea del bloque básico que describe la rama o llamada que finaliza el bloque básico. Puede haber múltiples ramas y llamadas listadas para una sola línea de código fuente si hay múltiples bloques básicos que terminan en esa línea. En este caso, a cada rama y llamada se le da un número. No hay una forma sencilla de mapear estas ramas y llamadas de regreso a construcciones de código fuente. En general, sin embargo, la rama o llamada con el número más bajo corresponderá a la construcción más a la izquierda en la línea de código fuente.

Para una rama, si se ejecutó al menos una vez, se imprimirá un porcentaje que indica el número de veces que se tomó la rama dividido por el número de veces que se ejecutó la rama. De lo contrario, se imprimirá el mensaje "nunca ejecutada".

Para una llamada, si se ejecutó al menos una vez, se imprimirá un porcentaje que indica el número de veces que la llamada retornó dividido por el número de veces que se ejecutó la llamada. Esto generalmente será 100%, pero puede ser menor para funciones que llaman a "exit" o "longjmp", y por lo tanto, pueden no retornar cada vez que se llaman.

Las condiciones se identifican por su índice: el índice 0 es la condición más a la izquierda. En "a || (b && c)", a es la condición 0, b la condición 1 y c la condición 2.

Los conteos de ejecución son acumulativos. Si el programa de ejemplo se ejecutara nuevamente sin eliminar el archivo .gcda, el conteo para el número de veces que cada línea en el código fuente

e se ejecutara se agregaría a los resultados de la ejecución(es) anterior(es). Esto es potencialmente útil de varias maneras. Por ejemplo, podría usarse para acumular datos a lo largo de varias ejecuciones del programa como parte de un conjunto de verificación de pruebas, o para proporcionar información más precisa a largo plazo sobre un gran número de ejecuciones del programa.

Los datos en los archivos .gcda se guardan inmediatamente antes de que el programa salga. Para cada archivo fuente compilado con -fprofile-arcs, el código de perfilado primero intenta leer un archivo .gcda existente; si el archivo no coincide con el ejecutable (diferente número de recuentos de bloques básicos) ignorará el contenido del archivo. Luego agrega los nuevos recuentos de ejecución y finalmente escribe los datos en el archivo.

Puedes informar sobre un subconjunto de funciones usando --include y --exclude. Usando gcov con Optimización de GCC

Si planeas usar gcov para ayudar a optimizar tu código, primero debes compilar tu programa con una opción especial de GCC --coverage. Aparte de eso, puedes usar cualquier otra opción de GCC; pero si quieres demostrar que cada línea de tu programa fue ejecutada, no debes compilar con optimización al mismo tiempo. En algunas máquinas, el optimizador puede eliminar algunas líneas de código simples combinándolas con otras líneas. Por ejemplo, código como este:

if (a != b)
  c = 1;
else
  c = 0;

puede compilarse en una sola instrucción en algunas máquinas. En este caso, no hay forma de que gcov calcule recuentos de ejecución separados para cada línea porque no hay código separado para cada línea. Por lo tanto, la salida de gcov se ve así si compilaste el programa con optimización:

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

La salida muestra que este bloque de código, combinado por la optimización, se ejecutó 100 veces. En cierto sentido, este resultado es correcto, porque solo había una instrucción que representaba estas cuatro líneas. Sin embargo, la salida no indica cuántas veces el resultado fue 0 y cuántas veces el resultado fue 1.

Las funciones "inlineables" pueden crear recuentos de línea inesperados. Los recuentos de línea se muestran para el código fuente de la función "inlineable", pero lo que se muestra depende de dónde se inserta la función o si no se inserta en absoluto.

Si la función no se inserta, el compilador debe emitir una copia fuera de línea de la función, en cualquier archivo objeto que la necesite. Si fileA.o y fileB.o contienen cuerpos fuera de línea de una función "inlineable" particular, también contendrán recuentos de cobertura para esa función. Cuando fileA.o y fileB.o se enlazan, el enlazador, en muchos sistemas, seleccionará uno de esos cuerpos fuera de línea para todas las llamadas a esa función, y eliminará o ignorará el otro. Desafortunadamente, no eliminará los contadores de cobertura para el cuerpo de la función no utilizado. Por lo tanto, cuando se instrumenta, todos los usos de esa función, excepto uno, mostrarán recuentos cero.

Si la función se inserta en varios lugares, la estructura del bloque en cada ubicación puede no ser la misma. Por ejemplo, una condición ahora puede calcularse en tiempo de compilación en algunas instancias. Dado que la cobertura de todos los usos de la función "inline" se mostrará para las mismas líneas de código, los recuentos de línea en sí mismos pueden parecer inconsistentes.

Las aplicaciones de larga duración pueden utilizar las funciones "__gcov_reset" y "__gcov_dump" para restringir la recopilación de perfiles a la región del programa de interés. Llamar a "__gcov_reset(void)" borrará todos los contadores de perfiles en tiempo de ejecución a cero, y llamar a "__gcov_dump(void)" hará que la información del perfil recopilada en ese momento se vuelque a los archivos de salida .gcda. Las aplicaciones instrumentadas utilizan un destructor estático con prioridad 99 para invocar la función "__gcov_dump". Por lo tanto, "__gcov_dump" se ejecuta después de todos los destructores estáticos definidos por el usuario, así como los manejadores registrados con "atexit".

Si un ejecutable carga un objeto compartido dinámico a través de la funcionalidad dlopen, se necesita -Wl,--dynamic-list-data para volcar todos los datos del perfil.

La biblioteca de tiempo de ejecución de perfilado informa varios errores relacionados con la manipulación y el guardado del perfil. Los errores se imprimen en la salida de error estándar o en el archivo GCOV_ERROR_FILE, si se utiliza la variable de entorno. Para terminar inmediatamente después de que ocurra un error, establezca la variable de entorno GCOV_EXIT_AT_ERROR. Esto puede ayudar a los usuarios a encontrar conflictos de perfil que conducen a un perfil engañoso.
