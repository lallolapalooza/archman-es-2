DESCRIPCIÓN

gcov es un programa de cobertura de pruebas. Úselo junto con GCC para analizar sus programas y ayudar a crear código más eficiente y de ejecución más rápida, y para descubrir partes no probadas de su programa. Puede usar gcov como una herramienta de perfilado para ayudar a descubrir dónde sus esfuerzos de optimización afectarán mejor a su código. También puede usar gcov junto con la otra herramienta de perfilado, gprof, para evaluar qué partes de su código utilizan la mayor cantidad de tiempo de computación.

Las herramientas de perfilado le ayudan a analizar el rendimiento de su código. Al usar un perfilador como gcov o gprof, puede obtener algunas estadísticas de rendimiento básicas, como:

  • con qué frecuencia se ejecuta cada línea de código
  • qué líneas de código se ejecutan realmente
  • cuánto tiempo de computación utiliza cada sección de código

Una vez que sepa estas cosas sobre cómo funciona su código cuando se compila, puede examinar cada módulo para ver qué módulos deben optimizarsse. gcov le ayuda a determinar dónde trabajar en la optimización.

Los desarrolladores de software también utilizan la prueba de cobertura junto con suites de pruebas para asegurarse de que el software sea realmente lo suficientemente bueno para una versión. Las suites de pruebas pueden verificar que un programa funciona como se espera; un programa de cobertura verifica cuánto del programa es ejercitado por la suite de pruebas. Los desarrolladores pueden entonces determinar qué tipos de casos de prueba deben agregarse a las suites de pruebas para crear tanto una mejor prueba como un mejor producto final.

Debería compilar su código sin optimización si planea usar gcov, ya que la optimización, al combinar algunas líneas de código en una sola función, puede no brindarle tanta información como necesita para buscar `puntos calientes' donde el código está utilizando una gran cantidad de tiempo de computación. Del mismo modo, dado que gcov acumula estadísticas por línea (en la resolución más baja), funciona mejor con un estilo de programación que coloca solo una instrucción por línea. Si utiliza macros complicadas que se expanden a bucles u otras estructuras de control, las estadísticas son menos útiles: solo informan sobre la línea donde aparece la llamada a la macro. Si sus macros complejas se comportan como funciones, puede reemplazarlas con funciones en línea para resolver este problema.

gcov crea un archivo de registro llamado archivo_fuente.gcov que indica cuántas veces se ha ejecutado cada línea de un archivo fuente archivo_fuente.c. Puede usar estos archivos de registro junto con gprof para ayudar a ajustar el rendimiento de sus programas. gprof proporciona información de temporización que puede utilizar junto con la información que obtiene de gcov.

gcov solo funciona en código compilado con GCC. No es compatible con ningún otro mecanismo de perfilado o prueba de cobertura.

OPCIONES

-a
--all-blocks
Escribir recuentos de ejecución individuales para cada bloque básico. Normalmente gcov genera recuentos de ejecución solo para los bloques principales de una línea. Con esta opción puede determinar si los bloques dentro de una sola línea no se están ejecutando.
-b
--branch-probabilities
Escribir las frecuencias de las ramas en el archivo de salida, y escribir la información resumen de las ramas en la salida estándar. Esta opción le permite ver con qué frecuencia se tomó cada rama en su programa. Las ramas incondicionales no se mostrarán, a menos que se proporcione la opción -u.
-c
--branch-counts
Escribir las frecuencias de las ramas como el número de ramas tomadas, en lugar del porcentaje de ramas tomadas.
-g
--conditions
Escribir la cobertura de condiciones en el archivo de salida, y escribir la información resumen de condiciones en la salida estándar. Esta opción le permite ver si las condiciones en su programa al menos una vez tuvieron un efecto independiente en el resultado de la expresión booleana (cobertura de condición/decisión modificada). Esto requiere que compile la fuente con -fcondition-coverage.
-d
--display-progress
Mostrar el progreso en la salida estándar.
-f
--function-summaries
Generar resúmenes para cada función además del resumen a nivel de archivo.
-h
--help
Mostrar ayuda sobre el uso de gcov (en la salida estándar) y salir sin realizar ningún procesamiento adicional.
-j
--json-format
Generar el archivo gcov en un formato intermedio JSON fácil de analizar que no requiere código fuente para su generación. El archivo JSON se comprime con el algoritmo de compresión gzip y los archivos tienen la extensión .gcov.json.gz.

La estructura del JSON es la siguiente:

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Los campos del elemento raíz tienen la siguiente semántica:

  • current_working_directory: directorio de trabajo donde se compiló una unidad de compilación
  • data_file: nombre del archivo de datos (GCDA)
  • format_version: versión semántica del formato

    Cambios en la versión 2:

*
calls: se agrega información sobre llamadas a funciones
*
gcc_version: versión del compilador GCC

Cada file tiene la siguiente forma:

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Los campos del elemento file tienen la siguiente semántica:

*
file_name: nombre del archivo fuente

Cada function tiene la siguiente forma:

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Los campos del elemento function tienen la siguiente semántica:

  • blocks: número de bloques que están en la función
  • blocks_executed: número de bloques ejecutados de la función
  • demangled_name: nombre "desenmascarado" de la función
  • end_column: columna en el archivo fuente donde termina la función
  • end_line: línea en el archivo fuente donde termina la función
  • execution_count: número de ejecuciones de la función
  • name: nombre de la función
  • start_column: columna en el archivo fuente donde comienza la función
  • start_line: línea en el archivo fuente donde comienza la función

Cada line tiene la siguiente forma:

{
  "blocks": [ "$block" ]
  "count": 2
}

Los campos del elemento line tienen la siguiente semántica:

  • blocks: información de los bloques que componen la línea
  • count: número de veces que se ha ejecutado esta línea

Cada block tiene la siguiente forma:

{
  "blocks_executed": 1,
  "num_blocks": 1
}

Los campos del elemento block tienen la siguiente semántica:

  • blocks_executed: número de bloques ejecutados en este bloque
  • num_blocks: número total de bloques en este bloque

Cada call tiene la siguiente forma:

{
  "count": 1,
  "indirect": false,
  "name": "foo"
}

Los campos del elemento call tienen la siguiente semántica:

  • count: número de veces que se realizó la llamada
  • indirect: booleano que indica si la llamada fue indirecta
  • name: nombre de la función llamada
-H
--human-readable
Imprime el número de ejecuciones de ramas en el formato más legible para humanos, como por ejemplo, `50% of 100`, en lugar de solo `50`, cuando se usa la opción -b.
-k
--use-colors
Usa colores para resaltar las partes del código que se ejecutaron. Los colores utilizados son:
*
Verde para las líneas que se ejecutaron.
*
Rojo para las líneas que no se ejecutaron.
*
Amarillo para las líneas que se ejecutaron parcialmente.
-l
--long-file-names
Incluye el nombre completo del archivo fuente en los informes. Por defecto, gcov acorta los nombres de archivo para que sean más cortos.
-m
--demangled-names
Imprime los nombres de las funciones "desenmascarados" (es decir, los nombres originales del código fuente) en lugar de los nombres codificados que usa GCC internamente. Esto es útil para depurar código con sobrecarga de funciones.
-n
--no-output
No genera ningún archivo de salida. Útil cuando solo se desea la información resumen en la salida estándar.
-o
--object-directory directorio|archivo
Busca los archivos de objeto en el directorio especificado. Esto es útil si los archivos de objeto no se encuentran en el mismo directorio que los archivos fuente.
-p
--preserve-paths
No elimina las rutas de los nombres de archivo. Esto es útil si se compila código fuente de varios directorios y se desea mantener la estructura de directorios en los informes.
-q
--use-hotness-colors
Colorea el código según la frecuencia de ejecución. Las líneas ejecutadas con más frecuencia se muestran en rojo, mientras que las que se ejecutan con menos frecuencia se muestran en verde. Esto requiere la opción -fprofile-arcs.
-r
--relative-only
Muestra solo nombres de archivo relativos al directorio actual. Esto es útil para mantener los informes concisos cuando se trabaja con proyectos grandes.
-s
--source-prefix directorio
Agrega el prefijo especificado a los nombres de archivo fuente. Esto es útil para organizar los informes cuando se compila código de múltiples directorios.
-t
--stdout
Escribe los archivos de cobertura en la salida estándar en lugar de crear archivos separados. Esto es útil para redirigir la salida a otros programas.
-u
--unconditional-branches
Incluye las ramas incondicionales en el informe de cobertura de ramas. Por defecto, las ramas incondicionales no se muestran a menos que se use la opción -b.
-x
--hash-filenames
Genera nombres de archivo hasheados en lugar de usar los nombres de archivo originales. Esto es útil para evitar problemas con nombres de archivo demasiado largos o caracteres especiales.
-v
--version
Muestra la versión de gcov y sale.

El argumento files es una lista de archivos fuente o archivos de objeto que se van a procesar.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

source file donde comienza la función
  • start_line: línea en el archivo fuente donde comienza la función

    • Tenga en cuenta que los números de línea y columna se numeran a partir de 1. En la implementación actual, start_line y start_column no incluyen parámetros de plantilla ni el tipo de retorno principal, pero es probable que esto se corrija en el futuro.

    Cada line tiene el siguiente formato:

    {
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

    Las ramas y llamadas solo están presentes con la opción -b. Los campos del elemento line tienen la siguiente semántica:

    • block_ids: IDs de los bloques básicos que pertenecen a la línea
    • count: número de ejecuciones de la línea
    • line_number: número de línea
    • unexecuted_block: indicador de si la línea contiene un bloque no ejecutado (no todas las instrucciones de la línea se ejecutan)
    • function_name: nombre de una función a la que pertenece esta line (para una línea con instrucciones insertadas, puede no estar establecida)

    Cada branch tiene el siguiente formato:

    {
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

    Los campos del elemento branch tienen la siguiente semántica:

    • count: número de ejecuciones de la rama
    • fallthrough: true cuando la rama es una rama de continuación
    • throw: true cuando la rama es una rama excepcional
    • source_block_id: ID del bloque básico donde ocurre esta rama
    • destination_block_id: ID del bloque básico al que salta esta rama

    Cada call tiene el siguiente formato:

    {
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

    Los campos del elemento call tienen la siguiente semántica:

    • returned: número de veces que se devolvió una llamada a función (el recuento de llamadas es igual a line::count)
    • source_block_id: ID del bloque básico donde ocurre esta llamada
    • destination_block_id: ID del bloque básico donde continúa la llamada después de regresar

    Cada condition tiene el siguiente formato:

    {
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

    Los campos del elemento condition tienen la siguiente semántica:

    • count: número de resultados de la condición en esta expresión
    • covered: número de resultados de la condición cubiertos en esta expresión
    • not_covered_true: términos, por índice, que no se vieron como verdaderos en esta expresión
    • not_covered_false: términos, por índice, que no se vieron como falsos en esta expresión
    -H
    --human-readable
    Escribe los recuentos en formato legible por humanos (como 24.6k).
    -k
    --use-colors
    Usa colores para las líneas de código que tienen cobertura cero. Usamos color rojo para líneas no excepcionales y cian para excepcionales. Los mismos colores se usan para bloques básicos con la opción -a.
    -l
    --long-file-names
    Crea nombres de archivo largos para archivos fuente incluidos. Por ejemplo, si el archivo de encabezado x.h contiene código y se incluyó en el archivo a.c, entonces ejecutar gcov en el archivo a.c producirá un archivo de salida llamado a.c##x.h.gcov en lugar de x.h.gcov. Esto puede ser útil si x.h se incluye en varios archivos fuente y desea ver las contribuciones individuales. Si utiliza la opción -p, tanto los nombres de archivo que incluyen como los incluidos serán rutas completas.
    -m
    --demangled-names
    Muestra nombres de funciones desanglados en la salida. Por defecto, se muestran nombres de funciones sangrados.
    -n
    --no-output
    No crear el archivo de salida gcov.
    -o directorio|archivo
    --object-directory directorio
    --object-file archivo
    Especifica el directorio que contiene los archivos de datos gcov, o la ruta del objeto. Los archivos de datos .gcno y .gcda se buscan utilizando esta opción. Si se especifica un directorio, los archivos de datos están en ese directorio y se nombran según el nombre del archivo de entrada, sin su extensión. Si se especifica un archivo aquí, los archivos de datos se nombran según ese archivo, sin su extensión.
    -p
    --preserve-paths
    Conserva información completa de la ruta en los nombres de los archivos .gcov generados. Sin esta opción, solo se utiliza el componente del nombre de archivo. Con esta opción, se utilizan todos los directorios, los caracteres / se traducen a caracteres #, los componentes de directorio . se eliminan y los componentes .. irremovibles se renombra a ^. Esto es útil si los archivos fuente están en varios directorios diferentes.
    -q
    --use-hotness-colors
    Emite una salida con colores tipo perf para líneas activas. La leyenda de la escala de colores se imprime al principio del archivo de salida.
    -r
    --relative-only
    Solo emite información sobre archivos fuente con un nombre de ruta relativo (después de la elisión de la parte del nombre del archivo fuente). Las rutas absolutas suelen ser archivos de encabezado del sistema y la cobertura de cualquier función insertada en ellos normalmente no es interesante.
    -s directorio
    --source-prefix directorio
    Un prefijo para los nombres de los archivos fuente a eliminar al generar los archivos de cobertura de salida. Esta opción es útil cuando se compila en un directorio separado, y no se desea la ruta al directorio fuente al determinar los nombres de los archivos de salida. Tenga en cuenta que esta detección de prefijo se aplica antes de determinar si el archivo fuente es absoluto.
    -t
    --stdout
    Salida a la salida estándar en lugar de a archivos de salida.
    -u
    --unconditional-branches
    Cuando se dan las probabilidades de rama, incluye las de las ramas incondicionales. Las ramas incondicionales normalmente no son interesantes.
    -v
    --version
    Muestra el número de versión de gcov (en la salida estándar) y sale sin realizar ningún otro procesamiento.
    -w
    --verbose
    Imprime información detallada relacionada con bloques básicos y arcos.
    -x
    --hash-filenames
    Al usar --preserve-paths, gcov utiliza la ruta completa de los archivos fuente para crear un nombre de archivo de salida. Esto puede generar nombres de archivo largos que pueden exceder los límites del sistema de archivos. Esta opción crea nombres de la forma archivo_fuente##md5.gcov, donde el componente archivo_fuente es la parte final del nombre de archivo y el componente md5 se calcula a partir del nombre completo sangrado que se habría utilizado de otra manera. La opción es una alternativa a --preserve-paths en sistemas que tienen un límite en el sistema de archivos.

    gcov debe ejecutarse con el directorio actual igual que cuando invocó al compilador. De lo contrario, no podrá localizar los archivos fuente. gcov produce archivos llamados nombre_sangrado.gcov en el directorio actual. Estos contienen la información de cobertura del archivo fuente al que corresponden. Se produce un archivo .gcov por cada archivo fuente (o de encabezado) que contiene código y que se compiló para producir los archivos de datos. La parte nombre_sangrado del nombre del archivo de salida suele ser simplemente el nombre del archivo fuente, pero puede ser algo más complicado si se dan las opciones -l o -p. Consulte esas opciones para obtener detalles.

    Si invoca gcov con varios archivos de entrada, las contribuciones de cada archivo de entrada se suman. Normalmente, lo invocaría con la misma lista de archivos que el enlace final de su ejecutable.

    Los archivos .gcov contienen campos separados por : junto con el código fuente del programa. El formato es

    <conteo_ejecucion>:<numero_linea>:<texto_linea_fuente>

    Información adicional de bloques puede seguir a cada línea, cuando se solicita mediante una opción de línea de comandos. El conteo_ejecucion es - para líneas que no contienen código. Las líneas no ejecutadas se marcan ##### o =====, dependiendo de si son alcanzables por rutas no excepcionales o solo por rutas excepcionales como los manejadores de excepciones de C++, respectivamente. Dada la opción -a, los bloques no ejecutados se marcan $$$$$ o %%%%%, dependiendo de si un bloque básico es alcanzable a través de rutas no excepcionales o excepcionales. Los bloques básicos ejecutados que tienen una instrucción con un conteo_ejecucion cero terminan con el carácter * y se colorean con color magenta con la opción -k. Esta funcionalidad no se admite en Ada.

    Tenga en cuenta que GCC puede eliminar completamente los cuerpos de las funciones que no son necesarias, por ejemplo, si se insertan en todas partes. Dichas funciones se marcan con -, lo que puede ser confuso. Utilice la opción -fkeep-inline-f

    NAME

    gcov - trace program execution to illustrate relative execution frequencies of code

    SYNOPSIS

    gcov [-a|--all-blocks] [-b|--branch-counts] [-c|--hash-links] [-d|--delete] [-e|--ellipse] [-f|--stdout] [-i|--initial-lines] [-l|--long-file-names] [-o objdir|--object-directory objdir] [-r|--relative-only] [-u|--unconditional-branches] [-v|--verbose] [-x|--hash-addresses] [--] [sourcefile...

    gcov -h|--help

    gcov -v|--version

    DESCRIPTION

    gcov is a tool to help you discover how much of your code is actually being executed. It uses the profiling information created by GCC when you compile your programs with the flags -fprofile-arcs and -ftest-coverage.

    When a program compiled with -fprofile-arcs is run, it creates instrumentation to record the execution counts of basic blocks and branches. When the program terminates, it writes these counts into .gcda files (or .dca files for DWARF Call Attribution data). The gcov program then uses these data files, along with the original source code, to generate reports on program execution. The default report is an annotated listing of the source code, showing the execution count for each line. Execution counts are also shown for branches.

    When a source file is compiled with -fprofile-arcs, the profiling code first attempts to read in an existing .gcda file; if the file doesn't match the executable (differing number of basic block counts) it will ignore the contents of the file. It then adds in the new execution counts and finally writes the data to the file.

    Using gcov with GCC Optimization

    If you plan to use gcov to help optimize your code, you must first compile your program with a special GCC option --coverage. Aside from that, you can use any other GCC options; but if you want to prove that every single line in your program was executed, you should not compile with optimization at the same time. On some machines the optimizer can eliminate some simple code lines by combining them with other lines. For example, code like this:

    if (a != b)
  c = 1;
else
  c = 0;

    can be compiled into one instruction on some machines. In this case, there is no way for gcov to calculate separate execution counts for each line because there isn't separate code for each line. Hence the gcov output looks like this if you compiled the program with optimization:

    100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

    The output shows that this block of code, combined by optimization, executed 100 times. In one sense this result is correct, because there was only one instruction representing all four of these lines. However, the output does not indicate how many times the result was 0 and how many times the result was 1.

    Inlineable functions can create unexpected line counts. Line counts are shown for the source code of the inlineable function, but what is shown depends on where the function is inlined, or if it is not inlined at all.

    If the function is not inlined, the compiler must emit an out of line copy of the function, in any object file that needs it. If fileA.o and fileB.o both contain out of line bodies of a particular inlineable function, they will also both contain coverage counts for that function. When fileA.o and fileB.o are linked together, the linker will, on many systems, select one of those out of line bodies for all calls to that function, and remove or ignore the other. Unfortunately, it will not remove the coverage counters for the unused function body. Hence when instrumented, all but one use of that function will show zero counts.

    If the function is inlined in several places, the block structure in each location might not be the same. For instance, a condition might now be calculable at compile time in some instances. Because the coverage of all the uses of the inline function will be shown for the same source lines, the line counts themselves might seem inconsistent.

    Long-running applications can use the "__gcov_reset" and "__gcov_dump" facilities to restrict profile collection to the program region of interest. Calling "__gcov_reset(void)" will clear all run-time profile counters to zero, and calling "__gcov_dump(void)" will cause the profile information collected at that point to be dumped to .gcda output files. Instrumented applications use a static destructor with priority 99 to invoke the "__gcov_dump" function. Thus "__gcov_dump" is executed after all user defined static destructors, as well as handlers registered with "atexit".

    If an executable loads a dynamic shared object via dlopen functionality, -Wl,--dynamic-list-data is needed to dump all profile data.

    Profiling run-time library reports various errors related to profile manipulation and profile saving. Errors are printed into standard error output or GCOV_ERROR_FILE file, if environment variable is used. In order to terminate immediately after an errors occurs set GCOV_EXIT_AT_ERROR environment variable. That can help users to find profile clashing which leads to a misleading profile.
