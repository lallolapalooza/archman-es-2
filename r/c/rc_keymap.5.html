RC_KEYMAP(5) Formatos de archivo RC_KEYMAP(5)

NOMBRE

rc_keymap - archivo toml que describe el mapa de teclas del mando a distancia

DESCRIPCIÓN

Un rc_keymap describe un mando a distancia. Enumera los protocolos utilizados y la correspondencia entre las señales IR decodificadas y los códigos de tecla de entrada de Linux. Este archivo es utilizado por ir-keytable(1) para la decodificación IR y por ir-ctl(1) para enviar IR.

El formato del archivo es toml. Dado que un mando a distancia puede utilizar múltiples protocolos, el nivel superior es una matriz de protocolos. La gran mayoría de los mandos a distancia solo utilizan un protocolo.

ENTRADA PROTOCOLO MAPA DE TECLAS

Para cada protocolo que utilice el mando a distancia, debe haber una entrada en la matriz protocols de nivel superior.

Campo Nombre

Cada entrada de protocolo tiene un campo name. ir-keytable o ir-ctl no utilizan el nombre, pero este puede usarse para dar al mando a distancia un nombre más descriptivo que el nombre del archivo, por ejemplo, el número de modelo.

Campo Protocolo

El campo protocol especifica el protocolo. Este puede ser uno de los decodificadores del kernel de Linux, en cuyo caso es nec, rc-5, rc-6, jvc, sony, sanyo, rc-5-sz, sharp, mce-kbd, xmp, imon, rc-mm, other o unknown. Si no coincide con ninguna de estas entradas, se asume que es un decodificador basado en BPF. unknown y other son protocolos decodificados por dispositivos RC específicos donde el protocolo es desconocido o propietario, respectivamente.

Existen algunos decodificadores de protocolo BPF predefinidos, que se enumeran a continuación. Consulte https://lwn.net/Articles/759188/ para saber cómo escribir el suyo propio.

Campo Variante

El campo variant especifica qué variante utiliza un protocolo determinado. Los protocolos sony, rc-5, rc-6 tienen variantes de diferentes longitudes de bits, por ejemplo. ir-ctl utiliza este campo al enviar IR.

Las siguientes variantes están definidas actualmente:

El protocolo rc-5 tiene las variantes rc-5, rc-5x-20, rc-5-sz.

El protocolo nec tiene las variantes nec, nec-x, nec-32.

El protocolo sony tiene las variantes sony-12, sony-15, sony-20.

El protocolo rc-6 tiene las variantes rc-6-0, rc-6-6a-20, rc-6-6a-24, rc-6-6a-32, rc-6-mce.

El protocolo rc-mm tiene las variantes rc-mm-12, rc-mm-24 y rc-mm-32.

Campo scancodes

La tabla scancodes enumera los códigos de escaneo y la correspondencia con el código de tecla de entrada de Linux. Múltiples códigos de escaneo pueden corresponder al mismo código de tecla. El campo scancodes no está presente para los protocolos raw.

Si el código de escaneo comienza con 0x, se interpreta como un número hexadecimal. Si comienza con 0, se interpreta como un número octal.

Los códigos de tecla válidos se enumeran en el archivo de cabecera input-event-codes.h. Ejemplos son KEY_ENTER, KEY_ESC o BTN_LEFT para el botón izquierdo del ratón. Tenga en cuenta que si el mapa de teclas solo se utiliza para enviar IR, la tecla no tiene que ser un código de tecla de Linux válido. Puede ser cualquier cadena sin espacios en blanco.

Campo Raw

Si el protocolo es raw, el campo raw es una matriz de correspondencia de código de tecla a valor bruto. Para cada entrada, hay un campo keycode y un campo raw. El keycode es un código de tecla de entrada de Linux, como se explica en el campo scancodes anterior.

El campo raw es una cadena, que enumera valores de pulso y espacio, separados por espacios en blanco. El primero es un valor de pulso en microsegundos, y el segundo un espacio, el tercero un pulso, etc. Los valores de espacio pueden ir precedidos de un signo - y el valor de pulso puede ir precedido de un signo +. Debe haber un número impar de valores para que la última entrada sea un pulso.

Campos restantes (parámetros BPF)

Si el protocolo es un decodificador basado en BPF, puede tener cualquier número de parámetros numéricos. Estos parámetros se utilizan para soportar protocolos con longitudes de señal no estándar para protocolos IR estándar. Se utilizará cualquier otro campo especificado aquí que sea requerido por el decodificador BPF seleccionado. Todos los demás campos se ignoran.

Los decodificadores de protocolos no BPF basados en el kernel no tienen parámetros.

PROTOCOLOS BPF

Algunos de los decodificadores de protocolos BPF son genéricos y requerirán parámetros para funcionar. Otros son para mandos específicos y deberían funcionar sin ningún parámetro. Los parámetros de temporización están todos en microsegundos (µs).

raw

Este decodificador debe usarse cuando el mapa de teclas es crudo; para cada tecla, hay una entrada en la matriz raw con los valores de pulso y espacio para esa tecla. No se realiza ninguna decodificación, la señal IR entrante simplemente se compara con los diferentes valores de pulso y espacio.

imon_rsc

Este decodificador es específicamente para el mando iMON RSC, que se incluía con la iMON Station (entre otros). El decodificador es para el stick direccional en el centro; lo decodificará en movimientos del ratón. Todos los botones están codificados usando nec-x, por lo que el mapa de teclas necesita dos protocolos para funcionar correctamente.

Esto no está relacionado con el protocolo imon.

margin
Define cuánta tolerancia hay para la longitud del mensaje. Por defecto 200.

grundig

Este decodificador es específicamente para mandos Grundig antiguos.

header_pulse
Longitud del primer pulso, por defecto 900.
header_space
Longitud del espacio siguiente, por defecto 2900.
leader_pulse
Longitud del segundo pulso, por defecto 1300.

xbox

Este decodificador es específicamente para el mando DVD de XBox, que es para la primera generación de XBox.

margin
Define cuánta tolerancia hay para la longitud del mensaje. Por defecto 200.

manchester

La mayoría de los mandos a distancia codificados en Manchester son rc-5, rc-6 o rc-mm. Algunos mandos utilizan una variante diferente (por ejemplo, pueden tener un pulso de cabecera) y para eso es el decodificador. Se deben especificar algunos parámetros, por defecto está configurado para rc-5.

margin
Define cuánta tolerancia hay para la longitud del mensaje. Por defecto 200.
header_pulse
Define cuánto dura un pulso de cabecera. Esto no siempre está presente. Por defecto 0.
header_space
Define cuánto dura el espacio después del pulso de cabecera. Debe establecerse si se establece header_pulse.
zero_pulse, zero_space, one_pulse, one_space
Longitudes de señal para los bits. Consulte https://clearwater.com.au/code/rc5 para ver cómo se definen.
bits
Número de bits. Por defecto 14.
scancode_mask
Bits que se enmascaran del código de escaneo resultante.
toggle_bit
Bit que especifica el alternador. Si este valor es mayor que el número de bits, no se define ningún alternador.

NAME

rc_keymap - RC-5, RC-6, JVC, SHARP, MCE, SONY, NEC, XMP, HAMA, TRAH, TSOP, RAW, PulseDistance, PulseLength - RC keymap

DESCRIPTION

The rc rc_keymap protocol configuration file is used to define the rc5, rc6, jvc, sharp, mce, sony, nec, xmp, hama, trah, tsop, raw, pulsedistance and pulselength protocols.

The configuration file is a text file which consists of one or more KEYMAP PROTOCOL ENTRY sections.

KEYMAP PROTOCOL ENTRY

A keymap protocol entry section starts with a [[protocols]] line, followed by the protocol attributes.

name
Protocol name, used for identification in log messages. Example: "Hauppauge Media Center".
protocol
Protocol name, may be followed by a variant name. Example: "nec variant=necx".
driver
The driver name that is used to decode the key presses.
scancodes
The scancodes section is a list of key code assignments.

The scancodes section is indented and starts with a [protocols.scancodes] line.

scancodes = "key name"
The scancode is a hexadecimal value, and the key name is a string which can be found in input-event-codes.h.

The attributes are:

protocol
This is a generic decoder for protocols that define bits by distance between pulses, and the pulses are always of the same length. The most well known protocol like this is nec. This decoder is cases where nec is not used. The parameters must be set.
margin
Define how much tolerance there is for message length. Default 200.
header_pulse
Length of the first leading pulse. Default 2125.
header_space
Length of the space after the leading pulse. Default 1875.
repeat_pulse
Length of the leading pulse for key repeat. Default 0.
repeat_space
Length of the space after the leading pulse for key repeat. Default 0.
bit_pulse
Length of the pulse for each bit. Default 625.
bit_0_space
Length of the space for a zero bit. Default 375.
bit_1_space
Length of the space for a one bit. Default 1625.
trailer_pulse
Length of the pulse after the last bit. Needed to bookend the last bit. Default 625.
bits
Number of bits. Default 4.
reverse
Should the bits be read in least significant bit first. Set to non-zero to enable. Default 0.
header_optional
Some remotes do not send the header pulse and space for key repeats, so set this to non-zero to make the header optional. Default 0.

An alternative implementation might only allow missing headers for repeat messages, but this would fail to decode key presses if the first message with the header did not decode correctly to due interference.

pulse_length

This is a generic decoder for protocols that define bits by length of pulses, and the spaces are always the same. The sony protocol is the most well-known protocol, but this decoder is for protocols which are not sony.

margin
Define how much tolerance there is for message length. Default 200.
header_pulse
Length of the first leading pulse. Default 2125.
header_space
Length of the space after the leading pulse. Default 1875.
repeat_pulse
Length of the leading pulse for key repeat. Default 0.
repeat_space
Length of the space after the leading pulse for key repeat. Default 0.
bit_space
Length of the space for each bit. Default 625.
bit_0_pulse
Length of the pulse for a zero bit. Default 375.
bit_1_pulse
Length of the pulse for a one bit. Default 1625.
trailer_pulse
Length of the pulse after the last bit. Optional. Default 0.
bits
Number of bits. Default 4.
reverse
Should the bits be read in least significant bit first. Set to non-zero to enable. Default 0.
header_optional
Some remotes do not send the header pulse and space for key repeats, so set this to non-zero to make the header optional. Default 0.

An alternative implementation might only allow missing headers for repeat messages, but this would fail to decode key presses if only the first message did not decode correctly to due interference.
