rtc(4) Manual de controladores de dispositivos rtc(4)

NOMBRE

rtc - reloj en tiempo real

SINOPSIS

#include <linux/rtc.h>
int ioctl(fd, RTC_petición, parametro);

DESCRIPCIÓN

Esta es la interfaz para los controladores de relojes en tiempo real (RTCs).

La mayoría de los ordenadores tienen uno o más relojes de hardware que registran la hora actual del "reloj de pared". Estos se llaman "Relojes en Tiempo Real" (RTCs). Uno de estos generalmente tiene energía de respaldo por batería para que siga registrando la hora incluso cuando el ordenador está apagado. Los RTCs a menudo proporcionan alarmas y otras interrupciones.

Todos los PCs i386 y los sistemas basados en ACPI tienen un RTC que es compatible con el chip Motorola MC146818 del PC/AT original. Hoy en día, dicho RTC generalmente está integrado en el chipset de la placa base (puente sur) y utiliza una batería de respaldo reemplazable en forma de moneda.

Los sistemas que no son PCs, como los sistemas embebidos construidos alrededor de procesadores system-on-chip, utilizan otras implementaciones. Normalmente no ofrecerán la misma funcionalidad que el RTC de un PC/AT.

RTC vs reloj del sistema

Los RTCs no deben confundirse con el reloj del sistema, que es un reloj de software mantenido por el kernel y utilizado para implementar gettimeofday(2) y time(2), así como para establecer marcas de tiempo en archivos, etc. El reloj del sistema informa de segundos y microsegundos desde un punto de partida, definido como la Época POSIX: 1970-01-01 00:00:00 +0000 (UTC). (Una implementación común cuenta interrupciones del temporizador, una por "jiffy", a una frecuencia de 100, 250 o 1000 Hz). Es decir, se supone que informa de la hora del reloj de pared, lo que también hacen los RTCs.

Una diferencia clave entre un RTC y el reloj del sistema es que los RTCs funcionan incluso cuando el sistema está en un estado de bajo consumo (incluido el modo "apagado"), y el reloj del sistema no puede. Hasta que se inicializa, el reloj del sistema solo puede informar la hora desde el arranque del sistema, no desde la Época POSIX. Por lo tanto, al arrancar y después de reanudar desde un estado de bajo consumo del sistema, el reloj del sistema a menudo se establecerá a la hora actual del reloj de pared utilizando un RTC. Los sistemas sin RTC necesitan establecer el reloj del sistema utilizando otro reloj, quizás a través de la red o introduciendo esos datos manualmente.

funcionalidad RTC

Los RTCs se pueden leer y escribir con hwclock(8), o directamente con las peticiones ioctl(2) que se listan a continuación.

Además de registrar la fecha y la hora, muchos RTCs también pueden generar interrupciones

•
en cada actualización del reloj (es decir, una vez por segundo);
•
en intervalos periódicos con una frecuencia que se puede configurar a cualquier múltiplo de potencia de 2 en el rango de 2 Hz a 8192 Hz;
•
al alcanzar una hora de alarma previamente especificada.

Cada una de estas fuentes de interrupción se puede habilitar o deshabilitar por separado. En muchos sistemas, la interrupción de alarma se puede configurar como un evento de despertar del sistema, que puede reanudar el sistema desde un estado de bajo consumo como Suspensión a RAM (STR, llamado S3 en sistemas ACPI), Hibernación (llamado S4 en sistemas ACPI), o incluso "apagado" (llamado S5 en sistemas ACPI). En algunos sistemas, el RTC respaldado por batería no puede generar interrupciones, pero otro puede hacerlo.

El dispositivo /dev/rtc (o /dev/rtc0, /dev/rtc1, etc.) solo se puede abrir una vez (hasta que se cierra) y es de solo lectura. En read(2) y select(2) el proceso que llama se bloquea hasta que se recibe la próxima interrupción de ese RTC. Después de la interrupción, el proceso puede leer un entero largo, cuyo byte menos significativo contiene una máscara de bits que codifica los tipos de interrupción que ocurrieron, mientras que los 3 bytes restantes contienen el número de interrupciones desde la última llamada a read(2).

interfaz ioctl(2)

Las siguientes peticiones de ioctl(2) se definen en los descriptores de archivo conectados a dispositivos RTC:

RTC_RD_TIME
Devuelve la hora de este RTC en la siguiente estructura:

struct rtc_time {
    int tm_sec;
    int tm_min;
    int tm_hour;
    int tm_mday;
    int tm_mon;
    int tm_year;
    int tm_wday;     /* no utilizado */
    int tm_yday;     /* no utilizado */
    int tm_isdst;    /* no utilizado */
};

Los campos de esta estructura tienen el mismo significado y rangos que para la estructura tm descrita en gmtime(3). Se debe pasar un puntero a esta estructura como tercer argumento de ioctl(2).
RTC_SET_TIME
Establece la hora de este RTC a la hora especificada por la estructura rtc_time apuntada por el tercer argumento de ioctl(2). Para establecer la hora del RTC, el proceso debe tener privilegios (es decir, tener la capacidad CAP_SYS_TIME).
RTC_ALM_READ
RTC_ALM_SET
Lee y establece la hora de la alarma, para los RTCs que admiten alarmas. La interrupción de alarma debe habilitarse o deshabilitarse por separado usando las peticiones RTC_AIE_ON, RTC_AIE_OFF. El tercer argumento de ioctl(2) es un puntero a una estructura rtc_time. Solo se utilizan los campos tm_sec, tm_min y tm_hour de esta estructura.
RTC_IRQP_READ
RTC_IRQP_SET
Lee y establece la frecuencia para las interrupciones periódicas, para los RTCs que admiten interrupciones periódicas. La interrupción periódica debe habilitarse o deshabilitarse por separado usando las peticiones RTC_PIE_ON, RTC_PIE_OFF. El tercer argumento de ioctl(2) es un unsigned long * o un unsigned long, respectivamente. El valor es la frecuencia en interrupciones por segundo. El conjunto de frecuencias permitidas son los múltiplos de dos en el rango de 2 a 8192. Solo un proceso privilegiado (es decir, uno que tenga la capacidad CAP_SYS_RESOURCE) puede establecer frecuencias por encima del valor especificado en /proc/sys/dev/rtc/max-user-freq. (Este archivo contiene el valor 64 por defecto).
RTC_AIE_ON
RTC_AIE_OFF
Habilita o deshabilita la interrupción de alarma, para los RTCs que admiten alarmas. El tercer argumento de ioctl(2) se ignora.
RTC_UIE_ON
RTC_UIE_OFF
Habilita o deshabilita la interrupción en cada actualización del reloj, para los RTCs que admiten esta interrupción una vez por segundo. El tercer argumento de ioctl(2) se ignora.
RTC_PIE_ON
RTC_PIE_OFF
Habilita o deshabilita la interrupción periódica, para los RTCs que admiten estas interrupciones periódicas. El tercer argumento de ioctl(2) se ignora. Solo un proceso privilegiado (es decir, uno que tenga la capacidad CAP_SYS_RESOURCE) puede habilitar la interrupción periódica si la frecuencia está actualmente establecida por encima del valor especificado en /proc/sys/dev/rtc/max-user-freq.
RTC_EPOCH_READ
RTC_EPOCH_SET
Muchos RTCs codifican el año en un registro de 8 bits que se interpreta como un número binario de 8 bits o como un número BCD. En ambos casos, el número se interpreta en relación con la Época de este RTC. NOTES

\n

When the kernel's system time is synchronized with an external\n reference using " }, { "type": "link", "value": "adjtimex(2)", "href": "/man/adjtimex.2.en" }, { "type": "text", "value": " it will update a designated RTC\n periodically every 11 minutes. To do so, the kernel has to briefly turn off\n periodic interrupts; this might affect programs using that RTC.

\n

An RTC's Epoch has nothing to do with the POSIX Epoch which is\n used only for the system clock.

\n

If the year according to the RTC's Epoch and the year register is\n less than 1970 it is assumed to be 100 years later, that is, between 2000\n and 2069.

\n

Some RTCs support "wildcard" values in alarm fields, to\n support scenarios like periodic alarms at fifteen minutes after every hour,\n or on the first day of each month. Such usage is nonportable; portable\n user-space code expects only a single alarm interrupt, and will either\n disable or reinitialize the alarm after receiving it.

\n

Some RTCs support periodic interrupts with periods that are\n multiples of a second rather than fractions of a second; multiple alarms;\n programmable output clock signals; nonvolatile memory; and other hardware\n capabilities that are not currently exposed by this API.
