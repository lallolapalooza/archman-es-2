NOMBRE

rcmd, rresvport, iruserok, ruserok, rcmd_af, rresvport_af, iruserok_af, ruserok_af - rutinas para devolver un flujo a un comando remoto

BIBLIOTECA

DESCRIPCIÓN

La función rcmd() es utilizada por el superusuario para ejecutar un comando en una máquina remota utilizando un esquema de autenticación basado en números de puerto privilegiados. La función rresvport() devuelve un descriptor de archivo a un socket con una dirección en el espacio de puertos privilegiados. Las funciones iruserok() y ruserok() son utilizadas por los servidores para autenticar clientes que solicitan servicio con rcmd(). Las cuatro funciones son utilizadas por el servidor rshd(8) (entre otros).

rcmd()

La función rcmd() busca el host *ahost utilizando gethostbyname(3), devolviendo -1 si el host no existe. De lo contrario, *ahost se establece al nombre estándar del host y se establece una conexión a un servidor residente en el puerto de Internet conocido inport.

Si la conexión tiene éxito, se devuelve un socket en el dominio de Internet de tipo SOCK_STREAM al llamador, y se proporciona al comando remoto como stdin y stdout. Si fd2p no es cero, entonces se configurará un canal auxiliar a un proceso de control, y se colocará un descriptor de archivo para él en *fd2p. El proceso de control devolverá la salida de diagnóstico del comando (unidad 2) en este canal, y también aceptará bytes en este canal como números de señal UNIX, para ser reenviados al grupo de procesos del comando. Si fd2p es 0, entonces el stderr (unidad 2 del comando remoto) se hará igual que el stdout y no se hará ninguna provisión para enviar señales arbitrarias al proceso remoto, aunque es posible que puedas llamar su atención utilizando datos fuera de banda.

El protocolo se describe en detalle en rshd(8).

rresvport()

La función rresvport() se utiliza para obtener un socket con un puerto privilegiado enlazado a él. Este socket es adecuado para su uso por rcmd() y varias otras funciones. Los puertos privilegiados son aquellos en el rango de 0 a 1023. Solo un proceso privilegiado (en Linux, un proceso que tiene la capacidad CAP_NET_BIND_SERVICE en el espacio de nombres de usuario que rige su espacio de nombres de red) tiene permitido enlazar a un puerto privilegiado. En la implementación de glibc, esta función restringe su búsqueda a los puertos de 512 a 1023. El argumento port es valor-resultado: el valor que suministra a la llamada se utiliza como punto de partida para una búsqueda circular del rango de puertos; al devolver (con éxito), contiene el número de puerto que se enlazó.

iruserok() y ruserok()

Las funciones iruserok() y ruserok() toman la dirección IP o el nombre del host remoto, respectivamente, dos nombres de usuario y una bandera que indica si el nombre del usuario local es el del superusuario. Luego, si el usuario *no* es el superusuario, verifica el archivo /etc/hosts.equiv. Si esa búsqueda no se realiza o no tiene éxito, se verifica el archivo .rhosts en el directorio personal del usuario local para ver si la solicitud de servicio está permitida.

Si este archivo no existe, no es un archivo regular, es propiedad de alguien que no sea el usuario o el superusuario, es escribible por alguien que no sea el propietario, o está enlazado rígidamente en alguna parte, la verificación falla automáticamente. Se devuelve cero si el nombre de la máquina está listado en el archivo hosts.equiv, o si el host y el nombre de usuario remoto se encuentran en el archivo .rhosts; de lo contrario, iruserok() y ruserok() devuelven -1. Si el dominio local (obtenido de gethostname(2)) es el mismo que el dominio remoto, solo se necesita especificar el nombre de la máquina.

Si se conoce la dirección IP del host remoto, se debe usar iruserok() en lugar de ruserok(), ya que no requiere confiar en el servidor DNS del dominio del host remoto.

variantes *_af()

Todas las funciones descritas anteriormente funcionan con sockets IPv4 (AF_INET). Las variantes "_af" toman un argumento adicional que permite especificar la familia de sockets. Para estas funciones, el argumento af se puede especificar como AF_INET o AF_INET6. Además, rcmd_af() admite el uso de AF_UNSPEC.

VALOR DE RETORNO

La función rcmd() devuelve un descriptor de socket válido en caso de éxito. Devuelve -1 en caso de error e imprime un mensaje de diagnóstico en el error estándar.

La función rresvport() devuelve un descriptor de socket válido y enlazado en caso de éxito. En caso de fallo, devuelve -1 y establece errno para indicar el error. El código de error EAGAIN se sobrecarga para significar: "Todos los puertos de red en uso".

Para obtener información sobre el retorno de ruserok() y iruserok(), véase lo anterior.

NAME

ruserok, iruserok, ruserok_af, iruserok_af - verifique si un usuario remoto tiene permiso para iniciar un proceso

LIBRARY

Network services library (libucv, -lucv)

SYNOPSIS

bool ruserok(const char *rhost, bool superuser, const char *ruser);

bool iruserok(const char *rhost, bool superuser, const char *ruser);

bool ruserok_af(const char *rhost, bool superuser, const char *ruser, int family);

bool iruserok_af(const char *rhost, bool superuser, const char *ruser, int family);

DESCRIPTION

Las funciones ruserok() y iruserok() determinan si un usuario remoto tiene permiso para iniciar un proceso en el sistema local. Estas funciones se utilizan típicamente en la implementación de servidores de red como rlogind(8) y rexec(8).

El parámetro rhost es el nombre del host o la dirección IP del host remoto desde el que se originó la solicitud. Si rhost es NULL, se considera que la solicitud proviene de un host local.

El parámetro superuser es un booleano. Si es verdadero, la verificación de permisos se relaja para permitir que el superusuario inicie procesos para cualquier usuario remoto. Si es falso, se aplican reglas de verificación de permisos más estrictas.

El parámetro ruser es el nombre de usuario en el host remoto. Si es NULL, se considera que el usuario remoto es el superusuario.

La diferencia entre ruserok() e iruserok() radica en cómo manejan la verificación del nombre de host. iruserok() realiza una verificación de nombre de host inversa (resolución inversa de DNS). Las variantes _af de estas funciones toman un parámetro adicional family, que especifica la familia de direcciones (por ejemplo, AF_INET, AF_INET6) que se utilizará para la resolución de nombres. Si rhost es NULL, se usa AF_UNSPEC.

La lógica de autorización es la siguiente:

  • Si superuser es verdadero, el acceso está permitido.
  • Si rhost es NULL (solicitud local), el acceso está permitido.
  • Se consulta el archivo /etc/hosts.equiv y el archivo .rhosts en el directorio principal del usuario local. Si una entrada en cualquiera de estos archivos coincide con el nombre de host remoto (o la dirección IP si se utiliza la verificación inversa) y el nombre de usuario remoto, se permite el acceso.
  • En ausencia de un archivo hosts.equiv o .rhosts coincidente, se consulta la base de datos de red NISPLUS para obtener información de autenticación.
  • Si ninguna de las comprobaciones anteriores permite el acceso, se deniega.

RETURN VALUE

Las funciones ruserok(), iruserok(), ruserok_af(), e iruserok_af() devuelven 1 (verdadero) si se permite el acceso, y 0 (falso) en caso contrario.

ATTRIBUTES

Para obtener una explicación de los siguientes atributos, consulte attributes(7).

Interface			   Attribute
----------------------------------------------------------------------
ruserok(), iruserok()		   thread-safe, multi-cancel-safe
ruserok_af(), iruserok_af()	   thread-safe, multi-cancel-safe

STANDARDS

Estas funciones son específicas de BSD y no forman parte de ningún estándar POSIX.

HISTORY

Las funciones ruserok() e iruserok() aparecieron por primera vez en 4.3BSD.

La variante _af fue añadida en glibc 2.2.

Solaris, 4.2BSD. Las variantes "_af" son adiciones más recientes y no están presentes en una amplia gama de sistemas.

BUGS

iruserok() e iruserok_af() solo se declaran en los encabezados de glibc desde glibc 2.12.
