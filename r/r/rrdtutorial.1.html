¿Qué es RRDtool?

RRDtool se refiere a Round Robin Database tool (herramienta de base de datos de Rondas). Rondas es una técnica que trabaja con una cantidad fija de datos y un puntero al elemento actual. Piensa en un círculo con algunos puntos dibujados en el borde. Esos puntos son los lugares donde se pueden almacenar los datos. Dibuja una flecha desde el centro del círculo hasta uno de los puntos; este es el puntero. Cuando se leen o escriben los datos actuales, el puntero se mueve al siguiente elemento. Como estamos en un círculo, no hay principio ni fin, puedes seguir y seguir y seguir. Después de un tiempo, todos los lugares disponibles se habrán utilizado y el proceso reutilizará automáticamente ubicaciones antiguas. De esta manera, el conjunto de datos no crecerá en tamaño y, por lo tanto, no requiere mantenimiento. RRDtool trabaja con bases de datos de Rondas (RRDs). Almacena y recupera datos de ellas.

¿Qué datos se pueden introducir en una RRD?

Lo que sea, probablemente encajará siempre que sean datos de series temporales. Esto significa que tienes que ser capaz de medir algún valor en varios puntos en el tiempo y proporcionar esta información a RRDtool. Si puedes hacer esto, RRDtool podrá almacenarlo. Los valores deben ser numéricos, pero no tienen que ser enteros, como es el caso de MRTG (la siguiente sección dará más detalles sobre esta aplicación más especializada).

Muchos ejemplos a continuación hablan de SNMP, que es un acrónimo de Simple Network Management Protocol (Protocolo Simple de Gestión de Redes). "Simple" se refiere al protocolo. No significa que sea simple gestionar o monitorizar una red. Después de leer este documento, deberías saber lo suficiente para entender de qué está hablando la gente. Por ahora, solo ten en cuenta que SNMP se puede usar para consultar dispositivos para obtener los valores de los contadores que mantienen. Es el valor de esos contadores lo que queremos almacenar en la RRD.

¿Qué puedo hacer con esta herramienta?

RRDtool se originó a partir de MRTG (Multi Router Traffic Grapher). MRTG comenzó como un pequeño script para graficar el uso de la conexión de una universidad a Internet. MRTG fue luego utilizado (y abusado) como una herramienta para graficar otras fuentes de datos, incluyendo temperatura, velocidad, voltaje, número de impresiones y similares.

Lo más probable es que empieces a usar RRDtool para almacenar y procesar datos recopilados a través de SNMP. Los datos serán muy probablemente bytes (o bits) transferidos desde y hacia una red o una computadora. Pero también se puede usar para mostrar olas de marea, radiación solar, consumo de energía, número de visitantes en una exposición, niveles de ruido cerca de un aeropuerto, temperatura en tu lugar de vacaciones favorito, temperatura en la nevera y cualquier cosa que tu imaginación pueda imaginar.

Solo necesitas un sensor para medir los datos y poder alimentar los números a RRDtool. RRDtool luego te permite crear una base de datos, almacenar datos en ella, recuperar esos datos y crear gráficos en formato PNG para visualizarlos en un navegador web. Esas imágenes PNG dependen de los datos que recopilaste y podrían ser, por ejemplo, una visión general del uso promedio de la red, o los picos que ocurrieron.

Tu primera base de datos de Rondas

En mi opinión, la mejor manera de aprender algo es hacerlo realmente. ¿Por qué no empezar ahora mismo? Crearemos una base de datos, pondremos algunos valores en ella y extraeremos esos datos de nuevo. Tu salida debería ser la misma que la salida incluida en este documento.

Empezaremos con algo fácil y compararemos un coche con un router, o compararemos kilómetros con bits y bytes. Todo es lo mismo: algún número en algún tiempo.

Supongamos que tenemos un dispositivo que transfiere bytes hacia y desde Internet. Este dispositivo mantiene un contador que comienza en cero cuando se enciende, aumentando con cada byte que se transfiere. Este contador probablemente tendrá un valor máximo. Si se alcanza este valor y se cuenta un byte adicional, el contador vuelve a empezar desde cero. Esto es lo mismo que muchos contadores en el mundo, como el odómetro de un coche.

La mayoría de las discusiones sobre redes hablan de bits por segundo, así que acostumbrémonos a eso de inmediato. Supongamos que un byte son ocho bits y empecemos a pensar en bits, no en bytes. ¡El contador, sin embargo, sigue contando bytes! En el mundo SNMP, la mayoría de los contadores

Hay 32 bits. Esto significa que están contando de 0 a 4294967295. Usaremos estos valores en los ejemplos. El dispositivo, cuando se le pregunta, devuelve el valor actual del contador. Sabemos el tiempo que ha pasado desde la última consulta, por lo que ahora sabemos cuántos bytes se han transferido ***en promedio*** por segundo. Esto no es muy difícil de calcular. Primero en palabras, luego en cálculos:

1.
Toma el contador actual, réstale el valor anterior.
2.
Haz lo mismo con el tiempo actual y el tiempo anterior (en segundos).
3.
Divide el resultado de (1) por el resultado de (2), el resultado es la cantidad de bytes por segundo. Multiplica por ocho para obtener el número de bits por segundo (bps).
bps = (contador_ahora - contador_antes) / (tiempo_ahora - tiempo_antes) * 8

Para algunas personas, puede ser útil traducir esto a un ejemplo automovilístico. No intentes este ejemplo, y si lo haces, no me culpes por los resultados.

Las personas que no están acostumbradas a pensar en kilómetros por hora pueden traducir la mayoría de las unidades a millas por hora dividiendo los km por 1.6 (suficientemente cerca). Usaré las siguientes abreviaturas:

m:    metro
km:   kilómetro (= 1000 metros).
h:    hora
s:    segundo
km/h: kilómetros por hora
m/s:  metros por segundo

Estás conduciendo un coche. A las 12:05 lees el contador del salpicadero y te dice que el coche ha recorrido 12345 km hasta ese momento. A las 12:10 miras de nuevo, marca 12357 km. Esto significa que has recorrido 12 km en cinco minutos. Un científico traduciría eso a metros por segundo y esto haría una buena comparación con el problema de (bytes por cinco minutos) versus (bits por segundo).

Recorrimos 12 kilómetros, que son 12000 metros. Lo hicimos en cinco minutos o 300 segundos. Nuestra velocidad es 12000m / 300s o 40 m/s.

También podríamos calcular la velocidad en km/h: 12 veces 5 minutos es una hora, por lo que tenemos que multiplicar 12 km por 12 para obtener 144 km/h. Para nuestros amigos angloparlantes nativos: eso son 90 mph, ¡así que no intentes este ejemplo en casa ni donde vivo! :)

Recuerda: estos números son solo promedios. No hay forma de saber por los números si condujiste a una velocidad constante. Hay un ejemplo más adelante en este tutorial que explica esto.

Espero que entiendas que no hay diferencia en calcular m/s o bps; solo la forma en que recopilamos los datos es diferente. Incluso la k de kilo es la misma que en términos de redes, k también significa 1000.

Ahora crearemos una base de datos donde podamos guardar todos estos números interesantes. El método utilizado para iniciar el programa puede diferir ligeramente de un sistema operativo a otro, pero supongo que puedes averiguarlo si funciona de manera diferente en el tuyo. Asegúrate de no sobrescribir ningún archivo en tu sistema al ejecutar el siguiente comando y escribe toda la línea como una sola línea larga (tuve que dividirla para mayor legibilidad) y omite todos los caracteres '\' .

rrdtool create test.rrd             \
         --start 920804400          \
         DS:speed:COUNTER:600:U:U   \
         RRA:AVERAGE:0.5:1:24       \
         RRA:AVERAGE:0.5:6:10

(Así que ingresa: "rrdtool create test.rrd --start 920804400 DS ...")

¿Qué se ha creado?

Creamos la base de datos de tiempo real llamada test (test.rrd) que comienza al mediodía del día en que comencé a escribir este documento, el 7 de marzo de 1999 (esta fecha se traduce a 920804400 segundos como se explica a continuación). Nuestra base de datos contiene una fuente de datos (DS) llamada "speed" que representa un contador. Este contador se lee cada cinco minutos (este es el valor predeterminado, por lo que no tiene que poner "--step=300"). En la misma base de datos se conservan dos archivos de tiempo real (RRA), uno promedia los datos cada vez que se lee (es decir, no hay nada que promediar) y mantiene 24 muestras (24 veces 5 minutos son 2 horas). El otro promedia 6 valores (media hora) y contiene 10 de estos promedios (por ejemplo, 5 horas).

RRDtool trabaja con marcas de tiempo especiales provenientes del mundo UNIX. Esta marca de tiempo es el número de segundos que han pasado desde el 1 de enero de 1970 UTC. El valor de la marca de tiempo se traduce a la hora local y, por lo tanto, se verá diferente para diferentes zonas horarias.

Es probable que no estés en la misma parte del mundo que yo. Esto significa que tu zona horaria es diferente. En todos los ejemplos en los que hablo de tiempo, las horas pueden ser incorrectas para ti. Esto tiene poco efecto en los resultados de los ejemplos, solo corrige las horas al leer. Como ejemplo: donde yo veré "12:05", la gente del Reino Unido verá "11:05".

tiempo 920805000, valor 12357

Como puedes ver, es posible introducir más de un valor en la base de datos en un solo comando. Tuve que parar en tres por cuestión de legibilidad, pero el máximo real por línea depende del sistema operativo.

Ahora podemos recuperar los datos de nuestra base de datos usando "rrdtool fetch":

Ten en cuenta que es posible que obtengas más filas de las esperadas. La razón de esto es que solicitas un rango de tiempo que termina en 920809200. El número que aparece detrás de 920809200: en la lista anterior cubre el rango de tiempo de 920808900 a 920809200, EXCLUYENDO 920809200. Por lo tanto, para estar seguro, también recibes la entrada de 920809200 a 920809500, ya que INCLUYE 920809200. También puedes ver "NaN" en lugar de "nan", esto depende del sistema operativo. "NaN" significa "Not A Number" (No es un número). Si tu sistema operativo escribe "U" o "UNKN" o algo similar, está bien. Si algo más está mal, probablemente se deba a un error que cometiste (asumiendo que mi tutorial es correcto, por supuesto :-). En ese caso: elimina la base de datos e inténtalo de nuevo.

El significado de la salida anterior quedará claro a continuación.

Es hora de crear algunos gráficos

Intenta el siguiente comando:

rrdtool graph speed.png                                 \
        --start 920804400 --end 920808000               \
        DEF:myspeed=test.rrd:speed:AVERAGE              \
        LINE2:myspeed#FF0000

Esto creará speed.png, que comienza a las 12:00 y termina a las 13:00. Hay una definición de una variable llamada myspeed, que utiliza los datos del RRA "speed" de la base de datos "test.rrd". La línea dibujada tiene 2 píxeles de altura y representa la variable myspeed. El color es rojo (especificado por su representación rgb, ver abajo).

Notarás que el inicio del gráfico no es a las 12:00 sino a las 12:05. Esto se debe a que tenemos datos insuficientes para determinar el promedio antes de esa hora. Esto solo sucede cuando faltan algunas muestras, lo que espero que no ocurra con frecuencia.

Si esto ha funcionado: ¡felicidades! Si no, comprueba qué salió mal.

Los colores se componen de rojo, verde y azul. Para cada uno de los componentes, especificas cuánto usar en hexadecimal, donde 00 significa no incluido y FF significa completamente incluido. El "color" blanco es una mezcla de rojo, verde y azul: FFFFFF El "color" negro es sin colores: 000000

rojo     #FF0000
verde   #00FF00
azul    #0000FF
magenta #FF00FF     (rojo mezclado con azul)
gris    #555555     (un tercio de todos los componentes)

Adicionalmente, puedes (con una versión reciente de RRDtool) añadir un canal alfa (transparencia). El valor predeterminado será "FF", lo que significa no transparente.

Puedes mostrar el PNG que acabas de crear usando tu visor de imágenes favorito. Los navegadores web mostrarán el PNG a través de la URL "file:///the/path/to/speed.png"

Gráficos con algo de matemáticas

Al observar la imagen, notas que el eje horizontal está etiquetado como 12:10, 12:20, 12:30, 12:40 y 12:50. A veces una etiqueta no encaja (12:00 y 13:00 serían candidatos probables) por lo que se omiten.

El eje vertical muestra el rango que introdujimos. Proporcionamos kilómetros y al dividirlo por 300 segundos, obtenemos números muy pequeños. Para ser exactos, el primer valor fue 12 (12357-12345) y al dividirlo por 300 da 0.04, que RRDtool muestra como "40 m" lo que significa "40/1000". La "m" (mili) no tiene nada que ver con metros (también m), kilómetros o milímetros. RRDtool no conoce las unidades físicas de nuestros datos, solo trabaja con números adimensionales.

Si hubiéramos medido nuestras distancias en metros, habría sido (12357000-12345000)/300 = 12000/300 = 40.

Como la mayoría de la gente tiene una mejor percepción de los números en este rango, lo corregiremos. Podríamos recrear nuestra base de datos y almacenar los datos correctos, pero hay una forma mejor: ¡haremos algunos cálculos mientras creamos el archivo png!

rrdtool graph speed2.png                           \
   --start 920804400 --end 920808000               \
   --vertical-label m/s                            \
   DEF:myspeed=test.rrd:speed:AVERAGE              \
   CDEF:realspeed=myspeed,1000,\*                  \
   LINE2:realspeed#FF0000

Nota: Necesito escapar el operador de multiplicación * con una barra invertida. Si no lo hago, el sistema operativo puede interpretarlo y usarlo para la expansión de nombres de archivo. También podrías poner la línea entre comillas así:

"CDEF:realspeed=myspeed,1000,*"                  \

Se reduce a esto: es RRDtool quien debería ver *, no tu shell. Y es tu shell quien interpreta \, no RRDtool. Es posible que necesites ajustar los ejemplos en consecuencia si usas un sistema operativo

Gráficos Mágicos

Me gusta creer que no hay prácticamente ningún límite en cuanto a cómo RRDtool graph puede manipular datos. No explicaré cómo funciona, pero mira el siguiente PNG:

rrdtool graph speed4.png                           \
   --start 920804400 --end 920808000               \
   --vertical-label km/h                           \
   DEF:myspeed=test.rrd:speed:AVERAGE              \
   CDEF:nonans=myspeed,UN,0,myspeed,IF             \
   CDEF:kmh=nonans,3600,*                          \
   CDEF:fast=kmh,100,GT,100,0,IF                   \
   CDEF:over=kmh,100,GT,kmh,100,-,0,IF             \
   CDEF:good=kmh,100,GT,0,kmh,IF                   \
   HRULE:100#0000FF:"Máximo permitido"              \
   AREA:good#00FF00:"Buena velocidad"                   \
   AREA:fast#550000:"Demasiado rápido"                     \
   STACK:over#FF0000:"Velocidad excesiva"

¿Recuerdas la nota del principio? Tuve que eliminar datos desconocidos de este ejemplo. El CDEF 'nonans' es nuevo, y la sexta línea (que solía ser la quinta) solía decir 'CDEF:kmh=myspeed,3600,*'.

Vamos a crear una página HTML rápida y sucia para ver los tres PNGs:

<HTML><HEAD><TITLE>Velocidad</TITLE></HEAD><BODY>
<IMG src="speed2.png" alt="Velocidad en metros por segundo">
<BR>
<IMG src="speed3.png" alt="Velocidad en kilómetros por hora">
<BR>
<IMG src="speed4.png" alt="¿Se viajó demasiado rápido?">
</BODY></HTML>

Nombra el archivo "speed.html" o similar, y ábrelo en tu navegador web.

Ahora, todo lo que tienes que hacer es medir los valores regularmente y actualizar la base de datos. Cuando quieras ver los datos, recrea los PNGs y asegúrate de actualizarlos en tu navegador. (Nota: simplemente hacer clic en recargar puede no ser suficiente, especialmente cuando hay proxies involucrados. Intenta con shift-reload o ctrl-F5).

Actualizaciones en la Realidad

Ya hemos usado el comando "update": tomó uno o más parámetros en forma de "<tiempo>:<valor>". Te alegrará saber que puedes especificar la hora actual ingresando una "N" como hora. O podrías usar la función "time" en Perl (el ejemplo más corto en este tutorial):

perl -e 'print time, "\n"'

Cómo ejecutar un programa a intervalos regulares depende del sistema operativo. Pero aquí tienes un ejemplo en pseudocódigo:

- Obtener el valor y ponerlo en la variable "$speed"
- rrdtool update speed.rrd N:$speed

(no intentes esto con nuestra base de datos de prueba, la usaremos en ejemplos posteriores)

Esto es todo. Ejecuta el script anterior cada cinco minutos. Cuando necesites saber cómo se ven los gráficos, ejecuta los ejemplos anteriores. Podrías ponerlos también en un script. Después de ejecutar ese script, mira la página speed.html que creamos anteriormente.

Algunas palabras sobre SNMP

Imagino que muy pocas personas podrán obtener datos reales de su coche cada cinco minutos. Todas las demás personas tendrán que conformarse con algún otro tipo de contador. Podrías medir el número de páginas impresas por una impresora, por ejemplo, las tazas de café hechas por la cafetera, un dispositivo que cuenta la electricidad consumida, lo que sea. Cualquier contador incremental puede ser monitoreado y graficado usando lo que has aprendido hasta ahora. Más adelante también podremos monitorear otros tipos de valores como la temperatura.

Muchas personas interesadas en RRDtool utilizarán el contador que rastrea los octetos (bytes) transferidos por un dispositivo de red. Así que hagamos eso a continuación. Comenzaremos con una descripción de cómo recopilar datos.

Algunas personas comentarán que hay herramientas que pueden hacer esta recopilación de datos por ti. ¡Tienen razón! Sin embargo, creo que es importante que entiendas que no son necesarias. Cuando tengas que determinar por qué las cosas salieron mal, necesitas saber cómo funcionan.

Una herramienta utilizada en el ejemplo se ha mencionado muy brevemente al principio de este documento, se llama SNMP. Es una forma de comunicarse con equipos en red. La herramienta que uso a continuación se llama "snmpget" y así es como funciona:

snmpget device password OID

o

snmpget -v[version] -c[password] device OID

Para `device` sustituyes el nombre, o la dirección IP, de tu dispositivo. Para `password` usas la "cadena de lectura de comunidad", como se llama en el mundo SNMP. Para algunos dispositivos, el valor predeterminado de "public" podría funcionar, sin embargo, esto puede ser deshabilitado, alterado o protegido por razones de privacidad y seguridad. Lee la documentación que viene con tu dispositivo o programa.

Luego está este parámetro, llamado OID, que significa "object identifier" (identificador de objeto).

Cuando empiezas a aprender sobre SNMP, parece muy confuso. No es tan difícil cuando miras la Base de Información de Gestión ("MIB"). Es un árbol invertido que describe datos, con un solo nodo como raíz y de ahí un número de ramas. Estas ramas terminan en otro nodo, se ramifican, etc. Todas las ramas tienen un nombre y forman el camino que seguimos hasta el final. Las ramas que seguimos se llaman: iso, org, dod, internet, mgmt y mib-2. Estos nombres también se pueden escribir en números y son 1 3 6 1 2 1.

iso.org.dod.internet.mgmt.mib-2 (1.3.6.1.2.1)

Hay mucha confusión sobre el punto inicial que usan algunos programas. *No* hay un punto inicial en un OID. A menudo, esos programas omitirán la parte predeterminada cuando te devuelvan los datos. Para empeorar las cosas, tienen varios prefijos predeterminados...

Un ejemplo del mundo real

Que comience la diversión. Primero, crea una nueva base de datos. Contiene datos de dos contadores, llamados entrada y salida. Los datos se introducen en archivos que los promedian. Toman 1, 6, 24 o 288 muestras a la vez. También van a archivos que guardan los números máximos. Esto se explicará más adelante. El tiempo entre muestras es de 300 segundos, un buen punto de partida, que es lo mismo que cinco minutos.

1 muestra "promediada" dura 1 período de 5 minutos
6 muestras promediadas se convierten en un promedio de 30 minutos
24 muestras promediadas se convierten en un promedio de 2 horas
288 muestras promediadas se convierten en un promedio de 1 día

Intentemos ser compatibles con MRTG, que almacena aproximadamente la siguiente cantidad de datos:

600 muestras de 5 minutos:    2   días y 2 horas
600 muestras de 30 minutos:  12.5 días
600 muestras de 2 horas:     50   días
732 muestras de 1 día:     732   días

Estos rangos se añaden, por lo que la cantidad total de datos almacenados en la base de datos es de aproximadamente 797 días. RRDtool almacena los datos de manera diferente, no inicia el archivo "semanal" donde terminó el archivo "diario". Para ambos archivos, los datos más recientes estarán cerca de "ahora" y, por lo tanto, ¡necesitaremos conservar más datos que MRTG!

Necesitaremos:

600 muestras de 5 minutos  (2 días y 2 horas)
700 muestras de 30 minutos (2 días y 2 horas, más 12.5 días)
775 muestras de 2 horas    (arriba + 50 días)
797 muestras de 1 día      (arriba + 732 días, redondeado a 797)

Funciones de consolidación

Hace unos párrafos mencioné la posibilidad de guardar los valores máximos en lugar de los valores promedio. Vamos a profundizar un poco más en esto.

Recuerda todo lo relacionado con la velocidad del coche. Supongamos que conduje a 144 km/h durante 5 minutos y luego me detuvo la policía durante 25 minutos. Al final de la conferencia, tomaría mi portátil y crearía y vería la imagen tomada de la base de datos. Si miráramos el segundo RRA que creamos, tendríamos el promedio de 6 muestras. Las muestras medidas serían 144+0+0+0+0+0=144, dividido entre 30 minutos, corregido por el error en 1000, traducido a km/h, con un resultado de 24 km/h. Todavía me multarían, pero ya no por exceso de velocidad :)

Obviamente, en este caso no deberíamos fijarnos en los promedios. En algunos casos son útiles. Si quieres saber cuántos km has recorrido, la imagen promediada sería la correcta para mirar. Por otro lado, para la velocidad a la que viajamos, los números máximos observados son mucho más interesantes. Más adelante veremos más tipos.

Es lo mismo para los datos. Si quieres saber la cantidad, mira los promedios. Si quieres saber la tasa, mira el máximo. Con el tiempo, se separarán cada vez más. En la última base de datos que hemos creado, hay dos archivos que guardan datos por día. El archivo que guarda promedios mostrará números bajos, el archivo que muestra máximos tendrá números más altos.

Para mi coche, esto se traduciría en promedios por día de 96/24=4 km/h (ya que viajo unos 94 kilómetros al día) durante los días laborables, y máximos de 120 km/h (mi velocidad máxima que alcanzo todos los días).

Gran diferencia. No mires el segundo gráfico para estimar las distancias que viajo y no mires el primer gráfico para estimar mi velocidad. Esto funcionará si las muestras están juntas, como lo están cada cinco minutos, pero no si promedias.

Algunos días, hago un viaje largo. Si voy por Europa y viajo durante 12 horas, el primer gráfico subirá a unos 60 km/h. El segundo mostrará 180 km/h. Esto significa que recorrí una distancia de 60 km/h por 24 h = 1440 km. Lo hice con una velocidad más alta y un máximo de alrededor de 180 km/h. ¡Sin embargo, probablemente no significa que viajé durante 8 horas a una velocidad constante de 180 km/h!

Este es un ejemplo real: fluye a través de Alemania (¡rápido!) y para unas cuantas veces para repostar y tomar café. Conduce despacio por Austria y los Países Bajos. Ten cuidado en las montañas y pueblos. Si miraras los gráficos creados a partir de los promedios de cinco minutos, obtendrías una imagen totalmente diferente. Verías los mismos valores en los gráficos de promedio y máximo (siempre que midiera cada 300 segundos). Podrías ver cuándo paré, cuándo estaba en marcha alta, cuándo conduje por autopistas rápidas, etc. La granularidad de los datos es mucho mayor, por lo que puedes ver más. Sin embargo, esto requiere 12 muestras por hora, o 288 valores por día, por lo que sería una gran cantidad de datos durante un período de tiempo más largo. Por lo tanto, lo promediamos, eventualmente a un valor por día. A partir de este único valor, no podemos ver mucho detalle, por supuesto.

Asegúrate de entender los últimos párrafos. No tiene valor solo una línea y unos pocos ejes, necesitas saber qué significan e interpretar los datos de manera apropiada. Esto es cierto para todos los datos.

El mayor error que puedes cometer es utilizar los datos recopilados para algo para lo que no son adecuados. Sería mejor si no tuvieras el gráfico en absoluto.

Tipos de fuentes de datos

Muy bien, te sientes preparado para continuar. ¡Bienvenido de nuevo y prepárate para una mayor velocidad en los ejemplos y explicaciones.

Sabes que para ver un contador a lo largo del tiempo, tienes que tomar dos números y dividir la diferencia entre ellos por el tiempo transcurrido. Esto tiene sentido para los ejemplos que te di, pero hay otras posibilidades. Por ejemplo, puedo obtener la temperatura de mi router en tres lugares: la entrada, el llamado punto caliente y el escape. Estos valores no son contadores. Si tomo la diferencia de las dos muestras y la divido por 300 segundos, estaría preguntando por el cambio de temperatura por segundo. ¡Espero que sea cero! Si no, la sala de computadoras probablemente está en llamas :)

Entonces, ¿qué podemos hacer? Podemos decirle a RRDtool que almacene los valores que medimos directamente tal como están (esto no es del todo cierto, pero es lo suficientemente cercano). Los gráficos que creemos se verán mucho mejor, mostrarán un valor bastante constante. Sé cuándo el router está ocupado (funciona -> usa más electricidad -> genera más calor -> la temperatura aumenta). Sé cuándo las puertas se dejan abiertas (la sala está acondicionada) -> el aire caliente del resto del edificio fluye hacia la sala de computadoras -> la temperatura de entrada aumenta). Etc. El tipo de datos que usamos al crear la base de datos antes era COUNTER, ahora tenemos un tipo de datos diferente y, por lo tanto, un nombre diferente para él. Se llama GAUGE. Hay más tipos de datos como este:

- COUNTER   ya lo conocemos
- GAUGE     lo acabamos de aprender
- DERIVE
- ABSOLUTE

Los dos tipos adicionales son DERIVE y ABSOLUTE. ABSOLUTE se puede usar como COUNTER con una diferencia: RRDtool asume que el contador se reinicia cuando se lee. Es decir, su delta se conoce sin cálculo por parte de RRDtool, mientras que RRDtool necesita calcularlo para el tipo COUNTER. Ejemplo: nuestro primer ejemplo (12345, 12357, 12363, 12363) se leería: desconocido, 12, 6, 0. El resto de los cálculos permanecen igual. El otro, DERIVE, es como COUNTER. A diferencia de COUNTER, también puede disminuir, por lo que puede tener un delta negativo. Nuevamente, el resto de los cálculos permanecen igual.

Probemoslos todos:

RRDtool bajo el Microscopio

  • La Línea A es de tipo COUNTER, por lo que debe incrementar continuamente y RRDtool debe calcular las diferencias. Además, RRDtool necesita dividir la diferencia por el tiempo transcurrido. Esto debería resultar en una línea recta en 1 (los incrementos son 300, el tiempo es 300).
  • La Línea B es de tipo GAUGE. Son valores "reales", por lo que deberían coincidir con lo que introducimos: una especie de onda.
  • La Línea C es de tipo DERIVE. Debe ser un contador que pueda disminuir. Lo hace entre 2400 y 0, con 1800 en el medio.
  • La Línea D es de tipo ABSOLUTE. Es como un contador pero funciona con valores sin calcular la diferencia. Los números son los mismos y, como se puede ver (esperemos) tiene un resultado diferente.

Repasemos los datos de nuevo:

  • Línea A: 300,600,900 y así sucesivamente. El delta del contador es una constante de 300, al igual que el delta de tiempo. Un número dividido por sí mismo siempre es 1 (excepto al dividir por cero, que es indefinido/ilegal).

    ¿Por qué el primer punto es desconocido? Sabemos lo que introdujimos en la base de datos, ¿verdad? Cierto. Pero no teníamos un valor para calcular el delta, así que no sabemos por dónde empezamos. Sería un error asumir que empezamos en cero, ¡así que no lo hacemos!

  • Línea B: No hay nada que calcular. Los números son como son.
  • Línea C: De nuevo, el valor inicial es desconocido. Es la misma historia que para la línea A. En este caso, los deltas no son constantes, por lo tanto, la línea tampoco lo es.   • Línea D: Aquí el dispositivo calcula los deltas. Por lo tanto, SÍ conocemos el primer delta y se grafica. Desbordamientos de Contador

Hay algunos conceptos básicos más que mostrar. Todavía quedan por cubrir algunas opciones importantes y aún no hemos visto los desbordamientos de contador. Primero, el desbordamiento de contador: En nuestro coche, notamos que el contador muestra 999987. Recorremos 20 km y el contador debería pasar a 1000007. Desafortunadamente, solo hay seis dígitos en nuestro contador, por lo que realmente muestra 000007. Si graficáramos eso en un tipo DERIVE, significaría que el contador se reinició en 999980 km. No fue así, y tiene que haber alguna protección para esto. Esta protección solo está disponible para el tipo COUNTER, que de todos modos debería usarse para este tipo de contador. ¿Cómo funciona? El tipo counter nunca debe disminuir, ¡y por lo tanto RRDtool debe asumir que se desbordó si disminuye! Si el delta es negativo, esto se puede compensar sumando el valor máximo del contador + 1. Para nuestro coche, esto sería:

Delta = 7 - 999987 = -999980    (en lugar de 1000007-999987=20)
Delta real = -999980 + 999999 + 1 = 20

En el momento de escribir este documento, RRDtool conoce contadores de 32 o 64 bits. Estos contadores pueden manejar los siguientes valores diferentes:

- 32 bits: 0 ..           4294967295
- 64 bits: 0 .. 18446744073709551615

Si estos números le parecen extraños, puede verlos en su forma hexadecimal:

- 32 bits: 0 ..         FFFFFFFF
- 64 bits: 0 .. FFFFFFFFFFFFFFFF

RRDtool maneja ambos contadores de la misma manera. Si ocurre un desbordamiento y el delta fuera negativo, RRDtool primero suma el máximo de un contador pequeño + 1 al delta. Si el delta sigue siendo negativo, tuvo que ser el contador grande el que se desbordó. Sume el valor máximo posible del contador grande + 1 y reste el pequeño valor añadido erróneamente.

Existe un riesgo en esto: suponga que el contador grande se desbordó al sumar un delta enorme, podría suceder, teóricamente, que al sumar el valor más pequeño el delta se volviera positivo. En este caso improbable, los resultados no serían correctos. El aumento debería ser casi tan alto como el valor máximo del contador para que esto suceda, por lo que es probable que tenga otros problemas y este problema en particular ni siquiera valdría la pena pensarlo. Aun así, he incluido un ejemplo, para que pueda juzgar por usted mismo.

Remuestreo de Datos

Una característica importante de RRDtool aún no se ha explicado: es prácticamente imposible recopilar datos y alimentarlos a RRDtool en intervalos exactos. Por lo tanto, RRDtool interpola los datos para que se almacenen en intervalos exactos. Si no sabe qué significa esto o cómo funciona, aquí tiene la ayuda que busca:

Supongamos que un contador aumenta exactamente uno por cada segundo. Quiere medirlo en intervalos de 300 segundos. Debería obtener valores que estén exactamente a 300 de distancia. Sin embargo, debido a diversas circunstancias, se retrasa unos segundos y el intervalo es de 303. El delta también será 303 en ese caso. Obviamente, RRDtool no debería poner 303 en la base de datos y hacerle creer que el contador aumentó 303 en 300 segundos. Aquí es donde RRDtool interpola: altera el valor 303 como si se hubiera almacenado antes y será 300 en 300 segundos. La próxima vez, estará exactamente a tiempo. Esto significa que el intervalo actual es de 297 segundos y el contador también aumentó en 297. Nuevamente, RRDtool interpola y almacena 300 como debería ser.

     en el RRD                 en la realidad
hora+000:   0 delta="U"   hora+000:    0 delta="U"
hora+300: 300 delta=300   hora+300:  300 delta=300
hora+600: 600 delta=300   hora+603:  603 delta=303
hora+900: 900 delta=300   hora+900:  900 delta=297

Creemos dos bases de datos idénticas. He elegido el rango de tiempo 920805000 a 920805900, ya que encaja muy bien con los números del ejemplo.

rrdtool create seconds1.rrd   \
   --start 920804700          \
   DS:seconds:COUNTER:600:U:U \
   RRA:AVERAGE:0.5:1:24

Haga una copia

para Unix: cp seconds1.rrd seconds2.rrd
para Dos:  copy seconds1.rrd seconds2.rrd
para vms:  ¿cómo lo sabría? :)

Introduzca algunos datos

rrdtool update seconds1.rrd \
   920805000:000 920805300:300 920805600:600 920805900:900
rrdtool update seconds2.rrd \
   920805000:000 920805300:300 920805603:603 920805900:900

Cree la salida

rrdtool graph seconds1.png                       \
   --start 920804700 --end 920806200             \
   --height 200                                  \
   --upper-limit 1.05 --lower-limit 0.95 --rigid \
   DEF:seconds=seconds1.rrd:seconds:AVERA
GE      \
   CDEF:unknown=seconds,UN                       \
   LINE2:segundos#0000FF                          \
   AREA:unknown#FF0000
rrdtool graph segundos2.png                       \
   --start 920804700 --end 920806200             \
   --height 200                                  \
   --upper-limit 1.05 --lower-limit 0.95 --rigid \
   DEF:segundos=segundos2.rrd:segundos:AVERAGE      \
   CDEF:unknown=segundos,UN                       \
   LINE2:segundos#0000FF                          \
   AREA:unknown#FF0000

Visualice ambas imágenes juntas (agréguelas a su archivo index.html) y compare. Ambos gráficos deberían mostrar lo mismo, a pesar de que la entrada sea diferente.

RESUMEN

Es hora de concluir este tutorial. Cubrimos todos los conceptos básicos para que pueda trabajar con RRDtool y leer la documentación adicional disponible. Hay mucho más por descubrir sobre RRDtool y encontrará cada vez más usos para este paquete. Puede crear fácilmente gráficos utilizando solo los ejemplos proporcionados y solo RRDtool. También puede utilizar uno de los front-ends para RRDtool que están disponibles.
