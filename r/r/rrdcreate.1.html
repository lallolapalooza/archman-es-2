RRDCREATE(1) rrdtool RRDCREATE(1)

NOMBRE

rrdcreate - Configurar una nueva base de datos redonda (Round Robin Database)

SINOPSIS

rrdtool create nombre-archivo [--start|-b hora-inicio] [--step|-s paso] [--template|-t archivo-plantilla] [--source|-r archivo-fuente] [--no-overwrite|-O] [--daemon|-d direccion] [DS:nombre-ds[=nombre-ds-mapeado[[indice-fuente]]]:DST:argumentos-dst] [RRA:CF:argumentos-cf]

DESCRIPCIÓN

La función create de RRDtool permite configurar nuevos archivos de Base de Datos Redonda (RRD). El archivo se crea en su tamaño final y completo, y se rellena con datos *DESCONOCIDO*, a menos que se hayan especificado uno o más archivos RRD fuente y estos contengan datos adecuados para "pre-rellenar" el nuevo archivo RRD.

nombre-archivo

El nombre del RRD que desea crear. Los archivos RRD deberían terminar con la extensión .rrd. Sin embargo, RRDtool aceptará cualquier nombre de archivo.

--start|-b hora de inicio (por defecto: ahora - 10s)

Especifica la hora en segundos desde 1970-01-01 UTC cuando se debe agregar el primer valor al RRD. RRDtool no aceptará ningún dato con una marca de tiempo anterior o igual a la especificada.

Consulte también "ESPECIFICACIÓN DE TIEMPO ESTILO AT" en rrdfetch para otras formas de especificar la hora.

Si se utiliza uno o más archivos fuente para pre-rellenar el nuevo RRD, la opción --start puede omitirse. En ese caso, la hora de última actualización entre todos los archivos fuente se utilizará como la hora de última actualización del nuevo archivo RRD, estableciendo efectivamente la hora de inicio.

--step|-s paso (por defecto: 300 segundos)

Especifica el intervalo base en segundos con el que se alimentarán los datos al RRD. Puede haber un factor de escala como sufijo del entero; consulte "PASO, TIEMPO DE ACTIVIDAD Y Filas Como Duraciones".

--no-overwrite|-O

No sobrescribir un archivo existente del mismo nombre.

--daemon|-d dirección

Dirección del demonio rrdcached. Para una lista de formatos aceptados, consulte la opción -l en el manual de rrdcached.

rrdtool create --daemon unix:/var/run/rrdcached.sock /var/lib/rrd/foo.rrd I<otras opciones>

[--template|-t archivo-plantilla]

Especifica un archivo RRD de plantilla para obtener definiciones de paso, DS y RRA. Esto permite basar la estructura de un nuevo archivo en algún archivo existente. Los datos del archivo plantilla NO se utilizan para el pre-relleno, pero es posible especificar el mismo archivo como archivo fuente (ver más abajo).

Se permiten definiciones adicionales de DS y RRA, y se agregarán a las tomadas de la plantilla.

--source|-r archivo-fuente

Se pueden nombrar uno o más archivos RRD fuente en la línea de comandos. Los datos de estos archivos fuente se utilizarán para pre-rellenar el archivo RRD creado. El archivo de salida y un archivo fuente pueden referirse al mismo nombre de archivo. Esto efectivamente reemplazará el archivo fuente con el nuevo archivo RRD. Si bien existe el peligro de perder el archivo fuente porque se reemplaza, no hay peligro de que el archivo fuente y el nuevo archivo se "corrompan" en ningún momento, porque el nuevo archivo siempre se creará como un archivo temporal primero y solo se moverá a su destino final una vez que se haya escrito en su totalidad.

El pre-relleno se realiza emparejando nombres de DS, RRAs y funciones de consolidación, y eligiendo la mejor resolución de datos disponible al hacerlo. El pre-relleno puede no ser matemáticamente correcto en todos los casos (por ejemplo, si las resoluciones deben cambiar debido a cambios en el paso del RRD de destino y las resoluciones antiguas y nuevas no coinciden con los límites de los bin antiguos/nuevos en los RRAs).

En otras palabras: se hace un esfuerzo máximo para preservar los datos durante el pre-relleno. Además, el pre-relleno de RRAs solo puede ser posible para ciertos tipos de DS. El pre-relleno también puede tener efectos extraños en los RRAs de pronóstico Holt-Winters. En otras palabras: no hay garantía de corrección de datos.

Al "pre-rellenar" un archivo RRD, la estructura del nuevo archivo debe especificarse como de costumbre utilizando las especificaciones DS y RRA descritas a continuación. Los datos se tomarán de los archivos fuente basándose en los nombres y tipos de DS y en el orden en que se especifican los archivos fuente. Las fuentes de datos con el mismo nombre de diferentes archivos fuente se combinarán para formar una nueva fuente de datos. Generalmente, para cualquier punto en el tiempo que el nuevo archivo RRD cubra después de su creación, solo se habrán utilizado datos de un archivo fuente para el pre-relleno. Sin embargo, los datos de múltiples fuentes pueden combinarse si se refieren a tiempos diferentes o si un archivo fuente nombrado anteriormente contiene datos desconocidos para un tiempo en el que uno posterior contiene datos conocidos.

Si esta selección automática de datos no es deseada, la sintaxis de DS permite especificar un mapeo de fuentes de datos de destino y fuente para el pre-relleno. Esta sintaxis permite renombrar fuentes de datos y restringir el pre-relleno de un DS para que solo utilice datos de un único archivo fuente.

Actualmente, el pre-relleno solo funciona de manera confiable para RRAs que utilizan una de las funciones de consolidación clásicas, es decir, una de: AVERAGE, MIN, MAX, LAST. También puede tener problemas actualmente con fuentes de datos COMPUTE.

Tenga en cuenta que la acción de pre-rellenar durante create es similar a muchas de las operaciones disponibles a través del comando tune, pero utilizando la sintaxis de create.

DS:nombre-ds[=nombre-ds-mapeado[[indice-fuente]]]:DST:argumentos-dst

Un único RRD puede aceptar entrada de varias fuentes de datos (DS), por ejemplo, tráfico entrante y saliente en una línea de comunicación específica. Con la opción de configuración DS, debe definir algunas propiedades básicas de cada fuente de datos que desee almacenar en el RRD.

nombre-ds es el nombre que utilizará para hacer referencia a esta fuente de datos particular desde un RRD. Un nombre-ds debe tener entre 1 y 19 caracteres de longitud en los caracteres [a-zA-Z0-9_].

DST define el Tipo de Fuente de Datos. Los argumentos restantes de una entrada de fuente de datos dependen del tipo de fuente de datos. Para GAUGE, COUNTER, DERIVE, DCOUNTER, DDERIVE y ABSOLUTE, el formato de una entrada de fuente de datos es:

DS:nombre-ds:{GAUGE | COUNTER | DERIVE | DCOUNTER | DDERIVE | ABSOLUTE}:tiempo-de-actividad:min:max

Para fuentes de datos COMPUTE, el formato es:

DS:nombre-ds:COMPUTE:expresion-rpn

Para decidir qué tipo de fuente de datos utilizar, revise las definiciones que siguen. Consulte también la sección sobre "CÓMO MEDIR" para obtener más información.

GAUGE
es para cosas como temperaturas o número de personas en una habitación o el valor de una participación de RedHat.
COUNTER
es para contadores que incrementan continuamente como el contador ifInOctets en un router. La fuente de datos COUNTER asume que el contador nunca disminuye, excepto cuando un contador se desborda. La función de actualización tiene en cuenta el desbordamiento. El contador se almacena como una tasa por segundo. Cuando el contador se desborda, RRDtool comprueba si el desbordamiento ocurrió en el límite de 32 bits o 64 bits y actúa en consecuencia añadiendo un valor apropiado al resultado.
DCOUNTER
lo mismo que COUNTER, pero para cantidades expresadas como un número de punto flotante de doble precisión. Podría usarse para rastrear cantidades que se incrementan en números no enteros, es decir, el número de segundos que una rutina ha tardado en ejecutarse, el peso total procesado por algún equipo tecnológico, etc. La única diferencia sustancial es que DCOUNTER puede ser de conteo ascendente o descendente, pero no ambos al mismo tiempo. DERIVE
almacenará la derivada de la línea que va desde el último hasta el valor actual de la fuente de datos. Esto puede ser útil para los medidores, por ejemplo, para medir la tasa de personas que entran o salen de una habitación. NOTA sobre COUNTER vs DERIVE

por Don Baarda <don.baarda@baesystems.com>

Si no puede tolerar confundir ocasionalmente un reinicio de contador con un envoltura de contador legítima, y prefiere "Desconocidos" para todas las envolturas y reinicios de contadores legítimos, siempre use DERIVE con min=0. De lo contrario, usar COUNTER con un máx adecuado devolverá valores correctos para todas las envolturas de contadores legítimas, marcará algunos reinicios de contadores como "Desconocido", pero puede confundir algunos reinicios de contadores con una envoltura de contador legítima.

Para un paso de 5 minutos y un contador de 32 bits, la probabilidad de confundir un reinicio de contador con una envoltura legítima es, sin duda, de aproximadamente el 0,8% por 1 Mbps de ancho de banda máximo. Tenga en cuenta que esto equivale al 80% para interfaces de 100 Mbps, por lo que para interfaces de alto ancho de banda y un contador de 32 bits, DERIVE con min=0 es probablemente preferible. Si está utilizando un contador de 64 bits, casi cualquier configuración de máx eliminará la posibilidad de confundir un reinicio con una envoltura de contador.

ABSOLUTE
es para contadores que se reinician al leerlos. Esto se utiliza para contadores rápidos que tienden a desbordarse. Por lo tanto, en lugar de leerlos normalmente, los reinicia después de cada lectura para asegurarse de tener el máximo tiempo disponible antes del próximo desbordamiento. Otro uso es para contar cosas como el número de mensajes desde la última actualización.
COMPUTE
es para almacenar el resultado de una fórmula aplicada a otras fuentes de datos en el RRD. A esta fuente de datos no se le proporciona un valor en la actualización, sino que sus Puntos de Datos Primarios (PDP) se calculan a partir de los PDP de las fuentes de datos según la expresión rpn que define la fórmula. Luego, las funciones de consolidación se aplican normalmente a los PDP de la fuente de datos COMPUTE (es decir, la expresión rpn solo se aplica para generar PDP). En el software de base de datos, dichos conjuntos de datos se conocen como columnas "virtuales" o "calculadas".

heartbeat define el número máximo de segundos que pueden transcurrir entre dos actualizaciones de esta fuente de datos antes de que el valor de la fuente de datos se suponga *DESCONOCIDO*.

min y max definen el rango esperado de valores para los datos suministrados por una fuente de datos. Si se especifican min y/o max, cualquier valor fuera del rango definido se considerará *DESCONOCIDO*. Si no conoce o no le importan los valores mínimos y máximos, establézcalos en U (desconocido). Tenga en cuenta que los valores mínimo y máximo siempre se refieren a los valores procesados de la DS. Para una DS de tipo tráfico-COUNTER, esta sería la velocidad de datos máxima y mínima esperada del dispositivo.

Si hay información disponible sobre los valores mínimos/máximos esperados, siempre establezca las propiedades min y/o max. Esto ayudará a RRDtool a realizar una simple verificación de cordura de los datos suministrados al ejecutar la actualización.

rpn-expression define la fórmula utilizada para calcular los PDP de una fuente de datos COMPUTE a partir de otras fuentes de datos en el mismo <RRD>. Es similar a definir un argumento CDEF para el comando graph. Consulte esa página del manual para obtener una lista y descripción de las operaciones RPN admitidas. Para las fuentes de datos COMPUTE, las siguientes operaciones RPN no son compatibles: COUNT, PREV, TIME y LTIME. Además, al definir la expresión RPN, la fuente de datos COMPUTE solo puede hacer referencia a los nombres de las fuentes de datos listadas previamente en el comando create. Esto es similar a la restricción de que los CDEF deben hacer referencia solo a los DEF y CDEF definidos previamente en el mismo comando graph.

Al rellenar previamente el nuevo archivo RRD utilizando una o más RRDs fuente, la especificación de la DS puede contener un mapeo opcional después del nombre de la DS. Esto toma la forma de un signo igual seguido de un nombre de DS mapeado y un índice de origen opcional entre corchetes.

Por ejemplo, la DS

DS:a=b[2]:GAUGE:120:0:U

especifica que la DS llamada a debe rellenarse previamente desde la DS llamada b en el segundo archivo fuente listado (los índices de origen son de base 1).

RRA:CF:argumentos de cf

El propósito de un RRD es almacenar datos en los archivos redondos (RRA). Un archivo consta de un número de valores de datos o estadísticas para cada una de las fuentes de datos (DS) definidas y se define con una línea RRA.

Cuando se ingresan datos en un RRD, primero se ajustan a ranuras de tiempo de la longitud definida con la opción -s, convirtiéndose así en un punto de dato primario.

Los datos también se procesan con la función de consolidación (CF) del archivo. Hay varias funciones de consolidación que consolidan puntos de datos primarios a través de una función agregada: AVERAGE, MIN, MAX, LAST.

AVERAGE
se almacena el promedio de los puntos de datos.
MIN
se almacena el valor más pequeño de los puntos de datos.
MAX
se almacena el valor más grande de los puntos de datos.
LAST
se utiliza el último punto de datos.

Tenga en cuenta que la agregación de datos inevitablemente conduce a pérdida de precisión e información. El truco consiste en elegir la función agregada de tal manera que las propiedades interesantes de sus datos se conserven durante el proceso de agregación.

El formato de la línea RRA para estas funciones de consolidación es:

RRA:{AVERAGE | MIN | MAX | LAST}:xff:steps:rows

xff El factor xfiles define qué parte de un intervalo de consolidación puede estar compuesta por datos *DESCONOCIDOS* mientras que el valor consolidado todavía se considera conocido. Se da como la proporción de PDP *DESCONOCIDOS* permitidos con respecto al número de PDP en el intervalo. Por lo tanto, varía de 0 a 1 (exclusivo).

steps define cuántos de estos puntos de datos primarios se utilizan para construir un punto de dato consolidado que luego va al archivo. Consulte también "STEP, HEARTBEAT, y Filas como Duraciones".

rows define cuántas generaciones de valores de datos se conservan en un RRA. Obviamente, esto debe ser mayor que cero. Consulte también "STEP, HEARTBEAT, y Filas como Duraciones".

Detección de Comportamiento Aberrante con Pronóstico Holt-Winters

Además de las funciones agregadas, existe un conjunto de funciones especializadas que permiten a RRDtool proporcionar suavizado de datos (a través del algoritmo de pronóstico Holt-Winters), bandas de confianza y marcado de comportamiento aberrante en la serie temporal de la fuente de datos:

  • RRA:HWPREDICT:rows:alpha:beta:periodo estacional[:rra-num]
  • RRA:MHWPREDICT:rows:alpha:beta:periodo estacional[:rra-num]
  • RRA:SEASONAL:periodo estacional:gamma:rra-num[:smoothing-window=fraccion]
  • RRA:DEVSEASONAL:periodo estacional:gamma:rra-num[:smoothing-window=fraccion]
  • RRA:DEVPREDICT:rows:rra-num
  • RRA:FAILURES:rows:umbral:longitud de ventana:rra-num

Estos RRAs difieren de las funciones de consolidación reales en varios aspectos. Primero, cada uno de los RRAs se actualiza una vez por cada punto de dato primario. Segundo, estos RRAs son interdependientes. Para generar límites de confianza en tiempo real, debe existir un conjunto coincidente de SEASONAL, DEVSEASONAL, DEVPREDICT y HWPREDICT o MHWPREDICT. Generar valores suavizados de los puntos de datos primarios requiere un RRA SEASONAL y un RRA HWPREDICT o MHWPREDICT. La detección de comportamiento aberrante requiere FAILURES, DEVSEASONAL, SEASONAL y HWPREDICT o MHWPREDICT.

Los valores predichos o suavizados se almacenan en el RRA HWPREDICT o MHWPREDICT. HWPREDICT y MHWPREDICT son en realidad dos variaciones del método Holt-Winters. Son intercambiables. Ambos intentan descomponer los datos en tres componentes: una línea base, una tendencia y un coeficiente estacional. HWPREDICT agrega su coeficiente estacional a la línea base para formar una predicción, mientras que MHWPREDICT multiplica su coeficiente estacional por la línea base para formar una predicción. La diferencia es notable cuando la línea base cambia significativamente en el transcurso de una temporada; HWPREDICT predecirá que la estacionalidad se mantendrá constante a medida que cambia la línea base, pero MHWPREDICT predecirá que la estacionalidad crecerá o disminuirá en proporción a la línea base. La elección adecuada del método depende de lo que se esté modelando. Para simplificar, el resto de esta discusión se referirá a HWPREDICT, pero MHWPREDICT puede sustituirse en su lugar.

Las desviaciones predichas se almacenan en DEVPREDICT (piense en una desviación estándar que puede escalarse para generar una banda de confianza). El RRA FAILURES almacena indicadores binarios. Un 1 marca la observación indexada como falla; es decir, el número de violaciones de límites de confianza en la ventana de observaciones anterior cumplió o superó un umbral especificado. Un ejemplo de uso de estos RRAs para graficar límites de confianza y fallas aparece en rrdgraph.

Los RRAs SEASONAL y DEVSEASONAL almacenan los coeficientes estacionales para el algoritmo de pronóstico Holt-Winters y las desviaciones estacionales, respectivamente. Hay una entrada por punto de tiempo de observación en el ciclo estacional. Por ejemplo, si los puntos de datos primarios se generan cada cinco minutos y el ciclo estacional es de 1 día, tanto SEASONAL como DEVSEASONAL tendrán 288 filas.

Here is an explanation by Don Baarda on the inner workings of RRDtool. It may help you to sort out why all this *UNKNOWN* data is popping up in your databases:

\n

RRDtool gets fed samples/updates at arbitrary times. From these it builds Primary Data Points (PDPs) on every "step" interval. The PDPs are then accumulated into the RRAs.

\n

The "heartbeat" defines the maximum acceptable interval between samples/updates. If the interval between samples is less than "heartbeat", then an average rate is calculated and applied for that interval. If the interval between samples is longer than "heartbeat", then that entire interval is considered "unknown". Note that there are other things that can make a sample interval "unknown", such as the rate exceeding limits, or a sample that was explicitly marked as unknown.

\n

The known rates during a PDP's "step" interval are used to calculate an average rate for that PDP. If the total "unknown" time accounts for more than half the "step", the entire PDP is marked as "unknown". This means that a mixture of known and "unknown" sample times in a single PDP "step" may or may not add up to enough "known" time to warrant a known PDP.

\n

The "heartbeat" can be short (unusual) or long (typical) relative to the "step" interval between PDPs. A short "heartbeat" means you require multiple samples per PDP, and if you don't get them mark the PDP unknown. A long heartbeat can span multiple "steps", which means it is acceptable to have multiple PDPs calculated from a single sample. An extreme example of this might be a "step" of 5 minutes and a "heartbeat" of one day, in which case a single sample every day will result in all the PDPs for that entire day period being set to the same average rate. -- Don Baarda <don.baarda@baesystems.com>

DESCRIPCIÓN

La mayor parte de la configuración de las bases de datos RRD se realiza en el momento de la creación. Consulte rrdcreate(1) para obtener más información.

Este documento describe cómo obtener datos de una base de datos RRD existente y cómo utilizarlos para predecir valores futuros o anormales.

Detección de comportamiento anómalo con pronóstico de Holt-Winters

Si tiene datos que siguen un ciclo estacional, por ejemplo, datos de tráfico de red que suelen ser más altos durante el día y más bajos durante la noche, entonces puede utilizar el pronóstico de Holt-Winters. El pronóstico de Holt-Winters es un método de pronóstico de series temporales que puede modelar tendencias y estacionalidad.

RRDtool puede utilizar el pronóstico de Holt-Winters para detectar comportamientos anómalos en sus datos. Un comportamiento anómalo es un valor que es significativamente diferente de lo que se espera basándose en los datos históricos. Por ejemplo, si el tráfico de red es típicamente de 100 Mbps durante el día, pero de repente salta a 1 Gbps, esto podría ser un comportamiento anómalo.

Para utilizar el pronóstico de Holt-Winters para la detección de comportamientos anómalos, debe:

  1. Crear un archivo RRD con un único almacén de datos (DS) que contenga los datos que desea monitorizar. Este DS debe ser de tipo COUNTER, DERIVE o ABSOLUTE.

  2. Crear un RRA de tipo HWPREDICT. Este RRA se utilizará para almacenar las predicciones y las desviaciones del pronóstico de Holt-Winters.

  3. Utilizar la función rrdpredict(1) para predecir valores futuros y detectar comportamientos anómalos.

La función rrdpredict(1) tomará la base de datos RRD y el RRA HWPREDICT como entrada y generará un informe que indica si se han detectado comportamientos anómalos.

PASO, LATIDO, y Filas Como Duraciones

Al crear una base de datos RRD con rrdcreate(1), especifica un valor de STEP. Este es el intervalo de tiempo en segundos entre los puntos de datos que se espera que entren en la base de datos RRD. Por ejemplo, un STEP de 300 significa que se espera un nuevo punto de datos cada 300 segundos (5 minutos).

También especifica un valor de HEARTBEAT. Este es el número máximo de segundos que pueden transcurrir entre puntos de datos antes de que el punto de datos se considere desconocido. Si la base de datos RRD no recibe un nuevo punto de datos dentro del intervalo de HEARTBEAT, el valor se establecerá en UNKNOWN.

El argumento rows-as-durations para algunos RRAs (como HWPREDICT, SEASONAL, DEVSEASONAL, DEVPREDICT y FAILURES) es un argumento numérico que indica el número de segundos que cada fila en el RRA representa. Por ejemplo, si STEP es 300 y establece rows-as-durations en 1440, entonces cada fila en el RRA representa 1440 * 300 segundos = 12 horas.

El LATIDO y el PASO

El HEARTBEAT es el número máximo de segundos que pueden transcurrir entre puntos de datos antes de que el punto de datos se considere desconocido. El STEP es el intervalo de tiempo en segundos entre los puntos de datos que se espera que entren en la base de datos RRD.

Generalmente, el HEARTBEAT debe ser un múltiplo del STEP. Por ejemplo, si su STEP es 300, entonces un HEARTBEAT de 600 significaría que si no recibe un punto de datos cada 600 segundos, el valor se considerará desconocido.

Si el HEARTBEAT es menor que el STEP, RRDtool aún esperará un punto de datos en cada intervalo de STEP, pero marcará el punto de datos como desconocido si no se recibe ningún dato dentro del intervalo de HEARTBEAT.

CÓMO MEDIR

Al obtener datos de RRDtool, como se describe en rrdtool(1), puede obtener el número de mensajes por segundo que se transportaron en un día. Puede obtener el promedio de mensajes por segundo de RRDtool para el día en cuestión y multiplicar este número por el número de segundos en un día. Debido a que todas las matemáticas se ejecutan con Doubles, la precisión debería ser aceptable.

Siempre es una Tasa
RRDtool almacena tasas en cantidad/segundo para datos COUNTER, DERIVE, DCOUNTER, DDÉRIVE y ABSOLUTE. Cuando grafica los datos, obtendrá en el eje y cantidad/segundo, lo que podría tentar a convertir en una cantidad absoluta multiplicando por el tiempo delta entre los puntos. RRDtool grafica datos continuos y, como tal, no es apropiado para graficar cantidades absolutas como, por ejemplo, "total de bytes" enviados y recibidos en un enrutador. Lo que probablemente desee es graficar tasas que pueda escalar a bytes/hora, por ejemplo, o graficar cantidades absolutas con otra herramienta que dibuja gráficos de barras, donde el tiempo delta es claro en el gráfico para cada punto (tal que cuando lea el gráfico, vea, por ejemplo, GB en el eje y, días en el eje x y una barra para cada día).

EJEMPLO

rrdtool create temperature.rrd --step 300 \
 DS:temp:GAUGE:600:-273:5000 \
 RRA:AVERAGE:0.5:1:1200 \
 RRA:MIN:0.5:12:2400 \
 RRA:MAX:0.5:12:2400 \
 RRA:AVERAGE:0.5:12:2400

Esto configura un RRD llamado temperature.rrd que acepta un valor de temperatura cada 300 segundos. Si no se suministran datos nuevos durante más de 600 segundos, la temperatura se convierte en *DESCONOCIDO*. El valor mínimo aceptable es -273 y el máximo es 5'000.

También se definen algunas áreas de archivo. La primera almacena las temperaturas suministradas durante 100 horas (1'200 * 300 segundos = 100 horas). El segundo RRA almacena la temperatura mínima registrada durante cada hora (12 * 300 segundos = 1 hora), durante 100 días (2'400 horas). El tercero y el cuarto RRA hacen lo mismo para la temperatura máxima y promedio, respectivamente.

EJEMPLO 2

rrdtool create monitor.rrd --step 300 \
  DS:ifOutOctets:COUNTER:1800:0:4294967295 \
  RRA:AVERAGE:0.5:1:2016 \
  RRA:HWPREDICT:1440:0.1:0.0035:288

Este ejemplo es un monitor de una interfaz de enrutador. El primer RRA rastrea el flujo de tráfico en octetos; el segundo RRA genera las funciones especializadas RRAs para la detección de comportamiento anómalo. Tenga en cuenta que falta el argumento rra-num de HWPREDICT, por lo que los otros RRAs se crearán implícitamente con valores de parámetros predeterminados. En este ejemplo, la línea base del algoritmo de pronóstico se adapta rápidamente; de hecho, la hora más reciente de observaciones (cada una a intervalos de 5 minutos) representa el 75% de la predicción de la línea base. El pronóstico de tendencia lineal se adapta mucho más lentamente. Las observaciones realizadas durante el último día (a 288 observaciones por día) representan solo el 65% de la tendencia lineal predicha. Nota: estos cálculos se basan en una fórmula de suavizado exponencial descrita en el artículo de LISA 2000.

El ciclo estacional es de un día (288 puntos de datos a intervalos de 300 segundos), y el parámetro de adaptación estacional se establecerá en 0.1. El archivo RRD almacenará 5 días (1'440 puntos de datos) de pronósticos y predicciones de desviación antes de la vuelta. El archivo almacenará 1 día (un ciclo estacional) de indicadores de 0-1 en el RRA FAILURES.

Se crean el mismo archivo RRD y los mismos RRAs con el siguiente comando, que crea explícitamente todos los RRAs de función especializada utilizando "STEP, HEARTBEAT y Filas como Duraciones".

rrdtool create monitor.rrd --step 5m \
  DS:ifOutOctets:COUNTER:30m:0:4294967295 \
  RRA:AVERAGE:0.5:1:2016 \
  RRA:HWPREDICT:5d:0.1:0.0035:1d:3 \
  RRA:SEASONAL:1d:0.1:2 \
  RRA:DEVSEASONAL:1d:0.1:2 \
  RRA:DEVPREDICT:5d:5 \
  RRA:FAILURES:1d:7:9:5

Por supuesto, la creación explícita no necesita replicar la creación implícita, se podría cambiar un número de argumentos.

EJEMPLO 3

rrdtool create proxy.rrd --step 300 \
  DS:Requests:DERIVE:1800:0:U \
  DS:Duration:DERIVE:1800:0:U \
  DS:AvgReqDur:COMPUTE:Duration,Requests,0,EQ,1,Requests,IF,/ \
  RRA:AVERAGE:0.5:1:2016

Este ejemplo está monitorizando la duración promedio de las solicitudes durante cada intervalo de 300 segundos para las solicitudes procesadas por un proxy web durante el intervalo. En este caso, el proxy expone dos contadores, el número de solicitudes procesadas desde el arranque y la duración acumulada total de todas las solicitudes procesadas. Claramente, ambos contadores tienen algún punto de desbordamiento, pero el uso de la fuente de datos DERIVE también maneja el reinicio que ocurre cuando el proxy web se detiene y reinicia.

En el RRD, la primera fuente de datos almacena la tasa de solicitudes por segundo durante el intervalo. La segunda fuente de datos almacena la duración total de todas las solicitudes procesadas durante el intervalo dividida por 300. La fuente de datos COMPUTE divide cada PDP de AccumDuration por el PDP correspondiente de TotalRequests y almacena la duración promedio de la solicitud. El resto de la expresión RPN maneja el caso de división por cero.

SEGURIDAD

Tenga en cuenta que los nuevos archivos rrd tendrán el permiso 0644 independientemente de su configuración umask. Si un archivo con el mismo nombre existe previamente, sus configuraciones de permiso se copiarán al nuevo archivo.
