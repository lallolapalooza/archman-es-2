NOMBRE

rollerd - Demonio de DNSSEC-Tools para gestionar el rollover de claves DNSSEC

SINOPSIS

rollerd [-opciones] -rrfile <archivo_rollrec>

DESCRIPCIÓN

El demonio rollerd gestiona el rollover de claves para las zonas. rollerd es solo un planificador para el rollover de zonas; utiliza zonesigner para realizar la generación de claves real, la firma de zonas y la manipulación de claves.

rollerd gestiona tanto el rollover de KSK como el de ZSK, aunque solo puede tener lugar un tipo de rollover por zona a la vez. La iniciación de los rollover de KSK tiene precedencia sobre la iniciación de los rollover de ZSK.

rollerd utiliza dos métodos de rollover de claves. El Método de Pre-publicación se utiliza para los rollover de claves ZSK. El Método de Doble Firma se utiliza para los rollover de KSK. Estos métodos se describen con más detalle a continuación.

rollerd mantiene el estado de rollover de la zona en archivos llamados archivos de *rollrec*; los mapeos de zona/clave se almacenan en archivos de *keyrec*. rollerd solo modifica los archivos de *rollrec*. En su mayor parte, rollerd no modifica *keyrec* directamente, sino que confía en zonesigner para actualizar esos archivos según sea necesario. (Las excepciones son cuando rollerd modifica los archivos de *keyrec*. Al inicio, marcará el archivo *keyrec* de cada zona gestionada para indicar que la zona está bajo el control de rollerd. Durante el curso del rollover, rollerd también actualizará los tiempos de rollover de una zona en su archivo *keyrec*.)

El administrador puede controlar rollerd con el comando rollctl. Un gran número de comandos están disponibles para controlar y modificar la operación de rollerd, así como para obtener información sobre el estado del rollover y del demonio.

El administrador de la zona necesitará actualizar sus archivos de zona periódicamente. Si rollerd está gestionando zonas, podrían surgir problemas si las zonas modificadas se firman sin el conocimiento de rollerd. Para evitar tales problemas, rollerd puede configurarse para volver a firmar automáticamente una zona cuando se descubra que su archivo de zona es más nuevo que su archivo de zona firmado correspondiente. (Se comparan las marcas de tiempo de "última modificación" de los archivos.) La zona se volverá a firmar sin que ocurran otras acciones de rollover, por lo que no se generarán nuevas claves, no ocurrirán rollover de claves y los diversos temporizadores de rollover no se verán afectados.

rollerd realizará estas re-firmas por defecto, pero esto puede ser controlado además por el parámetro de configuración *autosign* y las opciones de línea de comandos -autosign/-noautosign de rollerd. Si rollerd está configurado para no realizar re-firmas automáticas, el administrador aún puede obtener este comportamiento controlado mediante el uso de los comandos zonesigner o rollctl.

Si el archivo rollrec no existe o tiene una longitud cero, rollerd mostrará un mensaje de error y continuará ejecutándose. Se activará periódicamente y verificará si hay un archivo rollrec utilizable. Una vez que encuentre que el archivo rollrec especificado existe y no está vacío, procederá con la gestión normal del rollover.

ROLLOVER DE ZSK USANDO EL MÉTODO DE PRE-PUBLICACIÓN

El Método de Pre-publicación tiene cuatro fases que se ingresan cuando es hora de realizar el rollover de ZSK:

1. esperar a que los datos de la zona antigua expiren de las cachés
2. firmar la zona con el KSK y el ZSK Publicado
3. esperar a que los datos de la zona antigua expiren de las cachés
4. ajustar claves en keyrec y firmar la zona con el nuevo ZSK Actual

rollerd utiliza el comando zonesigner durante las fases 2 y 4 del rollover de ZSK. zonesigner generará claves según sea necesario y firmará la zona durante estas dos fases.

El Método de Pre-publicación de rollover de claves se define en el Documento de Guía del Operador de Seguridad DNS Paso a Paso. Consulte ese documento para obtener información más detallada.

ROLLOVER DE KSK USANDO EL MÉTODO DE DOBLE FIRMA

El Método de Doble Firma tiene siete fases que se ingresan cuando es hora de realizar el rollover de KSK:

1 - esperar a que los datos de la caché expiren
2 - generar un nuevo KSK (publicado) y cargar la zona
3 - esperar a que el conjunto de registros DNSKEY antiguo expire de las cachés
4 - transferir el nuevo conjunto de claves al padre
5 - esperar a que el padre publique el registro DS
6 - esperar a que los datos de la caché expiren
7 - rotar los KSK y cargar la zona

Esta es una modificación del Método de Doble Firma original. En el método original, las claves KSK se rotaron antes de que el nuevo conjunto de claves se transfiriera al padre. El nuevo método rota las claves KSK después de que el padre ha publicado los nuevos registros DS y los datos antiguos han expirado para las cachés. Esto aborda un problema potencial con la firma de zonas durante los rollover de claves.

rollerd utiliza el comando zonesigner durante las fases 2 y 7 del rollover de KSK. zonesigner generará claves según sea necesario y firmará la zona durante estas dos fases.

Actualmente, el período de espera en el paso 5 se maneja manualmente. En el paso 4, rollerd informa al administrador por correo electrónico que el conjunto de claves de la zona debe transferirse a su padre para que el rollover continúe. En el paso 5, después de que el conjunto de claves se ha transferido al padre y el padre ha publicado un nuevo registro DS, el administrador utiliza rollctl para informar a rollerd que el registro DS ha sido publicado y que el rollover puede continuar.

El Método de Doble Firma de rollover de claves se define en el Documento de Guía del Operador de Seguridad DNS Paso a Paso. Consulte ese documento para obtener información más detallada.

ROLLOVER DE KSK USANDO EL MÉTODO DE DOBLE FIRMA Y RFC5011

RFC5011 describe cómo los resolvedores de validación remota deben rastrear los cambios de KSK dentro de una zona. Si está configurado para el comportamiento RFC5011, rollerd y zonesigner añaden un período de tiempo extra largo entre el momento en que se crea y publica un nuevo KSK y el momento en que se lleva a cabo el cambio real para usarlo. RFC5011 especifica que los validadores remotos deben agregar un "temporizador de retención" al proceso de rollover, de modo que la nueva clave no se agregue como un ancla de confianza hasta que hayan pasado 30 días. Por lo tanto, rollerd esperará 60 días (por defecto) durante la fase 3 del proceso de rollover de KSK si el campo "istrustanchor" de la definición de *rollrec* se ha establecido en 1 o "sí". Para esperar un período de tiempo diferente al de 60 días, use el campo holddowntime.

En este momento, no se siguen las otras convenciones de RFC5011. Específicamente, no espera un tiempo antes de eliminar la clave antigua y no agrega el bit de revocación a la clave antigua después del cambio.

ACCIONES DE ROLLOVER ESPECÍFICAS DEL SITIO

Un administrador puede especificar comandos específicos del sitio que se ejecutarán durante las diversas fases de rollover. Los comandos se pueden ejecutar en lugar de las acciones de rollover predeterminadas de rollerd, o además de ellas. Esta subsección describe cómo utilizar acciones de rollover específicas del sitio.

Esta capacidad se proporciona para permitir que diferentes instalaciones manejen el rollover de acuerdo con sus necesidades específicas. Por ejemplo, se anticipa que esto podría ser útil para sitios que utilizan hardware HSM, o para permitir una mayor generación de informes para los administradores. Esto se ha utilizado con programas de prueba simples para garantizar que realmente funcione. Sin embargo, aún no se ha utilizado en un entorno HSM real o con otros reemplazos de software a nivel de producción.

Consulte las secciones *Rollover de ZSK Usando el Método de Pre-publicación* y *Rollover de KSK* *Usando el Método de Doble Firma* para obtener descripciones de las acciones de rollover predeterminadas.

ADVERTENCIA: Esto tiene el potencial de ser una capacidad peligrosa. Tenga *mucho* cuidado al configurarla y usarla. Tenga cuidado con los comandos específicos del sitio que se ejecutarán y con los permisos y la propiedad de rollerd y sus archivos de datos.

Cambios en el Archivo de Configuración de DNSSEC-Tools

El archivo de configuración de DNSSEC-Tools debe modificarse para indicar a rollerd qué debe ejecutarse para las acciones de fase de rollover no predeterminadas. Se pueden establecer pares clave/valor para cada fase de rollover para controlar cómo difiere esa fase de la predeterminada.

La porción de valor de la entrada de configuración contiene la ruta al comando de fase específico del sitio, junto con cualquier argumento que pueda necesitar. Múltiples comandos están separados por b

ROLLERD.CONF

El archivo de configuración para rollerd se llama rollerd.conf. La mayoría de las directivas en este archivo son opcionales y proporcionan una forma de personalizar el comportamiento de rollerd. A continuación se describen las entradas directivas más comunes.

Sintaxis del archivo de configuración

El archivo rollerd.conf está compuesto por entradas de palabras clave seguidas de una cadena de texto. Las palabras clave distinguen mayúsculas de minúsculas y deben estar en minúsculas.

Una entrada típica tiene el siguiente formato:

keyword   value

Las líneas que comienzan con un carácter hash (#) se consideran comentarios y se ignoran. Las cadenas de texto que contienen espacios deben delimitarse con comillas dobles (").

Directivas

prog-ksk1
Esta directiva especifica el programa que se ejecutará para la fase 1 de rollover de la Clave de Firma de Zona (KSK). El valor de la directiva es el nombre del programa o un comando completo con argumentos. Si el valor es default, se utilizará la acción de rollover normal.
prog-ksk2
Similar a prog-ksk1, pero para la fase 2 de rollover de KSK.
prog-ksk3
Similar a prog-ksk1, pero para la fase 3 de rollover de KSK.
prog-ksk4
Similar a prog-ksk1, pero para la fase 4 de rollover de KSK.
prog-ksk5
Similar a prog-ksk1, pero para la fase 5 de rollover de KSK.
prog-ksk6
Similar a prog-ksk1, pero para la fase 6 de rollover de KSK.
prog-ksk7
Similar a prog-ksk1, pero para la fase 7 de rollover de KSK.
prog-zsk1
Esta directiva especifica el programa que se ejecutará para la fase 1 de rollover de la Clave de Firma de Zona (ZSK). El valor de la directiva es el nombre del programa o un comando completo con argumentos. Si el valor es default, se utilizará la acción de rollover normal.
prog-zsk2
Similar a prog-zsk1, pero para la fase 2 de rollover de ZSK.
prog-zsk3
Similar a prog-zsk1, pero para la fase 3 de rollover de ZSK.
prog-zsk4
Similar a prog-zsk1, pero para la fase 4 de rollover de ZSK.
prog-normal
Esta directiva especifica el programa que se ejecutará cuando la zona no esté en ninguna fase de rollover. El valor es el nombre del programa o un comando completo con argumentos. Si el valor es default, se utilizará la acción normal.
log-roll
Esta directiva especifica un archivo de registro para los eventos de rollover. Si no se especifica, los eventos de rollover se registrarán en la salida estándar.
mail-roll
Esta directiva especifica una dirección de correo electrónico para enviar notificaciones sobre eventos de rollover. Si no se especifica, no se enviarán notificaciones por correo electrónico.
mail-to
Esta directiva especifica la dirección de correo electrónico del destinatario para las notificaciones de rollover. Si no se especifica, las notificaciones se enviarán a la dirección especificada en mail-roll.
dnsd
Esta directiva especifica el comando para recargar el demonio DNS. Esto se utiliza para asegurar que los cambios de DNS se apliquen después de un rollover.

El comando reservado default le dice a rollerd que use su acción de rollover normal para una fase determinada. Esto puede combinarse con otros comandos para proporcionar cosas como registro o notificaciones especializadas.

rollerd solo alterará el comportamiento de una fase de rollover si el archivo de configuración contiene una entrada para esa fase. Si no es así, se tomará la acción predeterminada.

Por ejemplo, esta línea de configuración le dice a rollerd que para la fase de rollover ZSK 2, en lugar de usar sus ejecuciones normales de zonesigner, debería ejecutar el comando hsm-signer.

prog-zsk2        hsm-signer

En este ejemplo, esta línea de configuración informa a rollerd que al entrar en la fase 1 de rollover KSK y la fase 1 de rollover ZSK, debe ejecutar el comando log-and-mail, y luego usar la acción de rollover normal para esas fases.

prog-ksk1        /usr/local/sbin/log-and-mail mary ! default
prog-zsk1        /usr/local/sbin/log-and-mail bob!default

Las siguientes claves de configuración se utilizan para controlar las fases de rollover de KSK: prog-ksk1, prog-ksk2, prog-ksk3, prog-ksk4, prog-ksk5, prog-ksk6, y prog-ksk7.

Las siguientes claves de configuración se utilizan para controlar las fases de rollover de ZSK: prog-zsk1, prog-zsk2, prog-zsk3, y prog-zsk4.

La clave de configuración prog-normal controla el estado normal, no de rollover.

Comandos Específicos del Sitio

Para ser generalmente útil, a los comandos específicos del sitio ejecutados por rollerd se les dará un conjunto estándar de argumentos, y se reconocerá un conjunto estándar de valores de salida.

Los argumentos estándar de rollerd son:
1. zonename - Zona a manejar.
2. phase - Fase de rollover actual de la zona (ej., zsk1, ksk6, normal).
3. rollrec name - Clave de entrada de la zona en el archivo rollrec.
4. rollrec file - La ruta al archivo rollrec.
5. keyrec file - La ruta al archivo keyrec de la zona.

La entrada prog-phase en el archivo de configuración puede especificar opciones y argumentos adicionales para un comando. Estos se incluirán en la línea de comandos de ejecución *antes* de los argumentos estándar.

Los valores de salida estándar esperados por rollerd son:
0. La zona puede pasar a la siguiente fase de rollover.
Esto solo es aplicable al comando actual; otros
comandos en la lista de comandos de esta fase aún deben ejecutarse.
1. La zona debe permanecer en la fase de rollover actual.
Esto no es necesariamente el resultado de un error.
2. Se encontró un error en los argumentos proporcionados al comando.
3. Se encontró un error durante la ejecución.

Si la entrada de configuración de una fase de rollover enumera múltiples comandos, se ejecutarán en el orden en que se enumeran. Si algún comando en esa lista de comandos falla, el procesamiento se detiene allí.

El comando rp-wrapper muestra cómo se puede escribir un comando específico del sitio. rp-wrapper puede usarse como un esqueleto sobre el cual construir un comando de fase de rollover más útil.

Consideraciones para Comandos Específicos del Sitio

Lo siguiente debe tenerse en cuenta al escribir un comando específico del sitio para una fase de rollover.

longitud de la ejecución
Un comando de fase no debe ejecutarse durante mucho tiempo. Tal como está escrito actualmente, rollerd serializa el rollover de zonas. Por lo tanto, cuanto más tarde un comando de fase en ejecutarse, más tiempo tardará en pasar a la siguiente zona. Si un comando de fase duerme o espera activamente, por así decirlo, el tiempo de espera de la siguiente fase, entonces cada zona que rollerd administra se quedará esperando.
seguir las directrices de interfaz
Siga los estándares para argumentos y valores de salida. No seguir los estándares probablemente afectará negativamente al rollover de zonas.
frecuencia de ejecución del comando
Si rollerd está operando en su modo de procesamiento tradicional de "lista completa", se ejecutará una lista de comandos de fase cada vez que rollerd recorra su lista de zonas y una zona se encuentre en la fase de ese comando en particular. Por ejemplo, si <i>prog_zsk1</i> está definido para example.com, ese comando se ejecutará para example.com cada vez que rollerd ejecute su lista de zonas y encuentre que example.com está en el estado de rollover de fase ZSK 1. Un comando de fase *debe* tener esto en cuenta para no realizar sus acciones con más frecuencia de lo necesario. Este es probablemente un problema para los diversos estados de espera de rollover, y posiblemente para el estado normal.

Si rollerd está operando en el modo experimental de procesamiento de "cola próxima", se ejecutará una lista de comandos de fase para una zona solo cuando ocurra un cambio de fase. Dado que los cambios de fase se ponen en cola por tiempo, esto no debería suceder más de una vez por fase. Un comando de fase *debería* tener esto en cuenta, en caso de que la cola próxima se reordene antes de que la zona salga de la cola, o el tiempo de la cola sea relativamente rápido. Este es probablemente un problema para los diversos estados de espera de rollover.

ADVERTENCIA: El procesamiento de la "cola próxima" es *experimental*. Se debe tener cuidado al usar este método de procesamiento, ya que todavía puede tener algunos errores persistentes.

Recarga de Zonas

rollerd tiene la oportunidad de informar al demonio DNS que recargue una zona en la fase KSK 2, fase KSK 7, fase ZSK 2 y fase ZSK 4. Este es el comportamiento predeterminado de rollerd. Sin embargo, hay situaciones en las que esto no debería hacerse, como por ejemplo para la firma fuera de línea.

El campo roll_loadzone del archivo de configuración de DNSSEC-Tools es un campo booleano que anula el valor predeterminado para forzar el comportamiento de recarga de zona, activado o desactivado. Este campo tiene prioridad sobre el valor predeterminado.

De manera similar, la opción -noreload evita que rollerd solicite una recarga de zona, y tiene prioridad sobre el campo de configuración roll_loadzone y el valor predeterminado.

Archivos rollrec

Las zonas que serán administradas por rollerd se describen en un archivo rollrec. En términos generales, la mayoría de las personas querrán usar el comando rollinit para crear un archivo rollrec inicial en lugar de escribir el suyo propio desde cero. Consulte la sección INICIALIZACIÓN Y USO a continuación y la página del manual rollinit para obtener detalles. La entrada de cada zona contiene datos necesarios para rollerd y algunos datos útiles para un usuario. A continuación se muestra una entrada de ejemplo de rollrec:

roll "example.com"
        zonename        "example.com"
        zonefile        "example.com.signed"
        keyrec          "example.com.krf"
        zonegroup       "demo-zones"
        directory       "dir-example.com"
        kskphase        "0"
        zskphase        "3"
        ksk_rollsecs    "1172614842"
        ksk_rolldate    "Tue Feb 27 22:20:42 2007"
        zsk_rollsecs    "1172615087"
        zsk_rolldate    "Tue Feb 27 22:24:47 2007"
        maxttl          "60"
        display         "1"
        phasestart      "Tue Feb 27 22:25:07 2007"
        # optional records for RFC5011 rolling:
        istrustanchor   "no"
        holddowntime    "60D"

La primera línea proporciona el nombre de la entrada rollrec. El nombre la distingue de otras entradas rollrec y debe ser único. Este puede ser el nombre de la zona, pero no es un requisito. Las siguientes líneas proporcionan el nombre de la zona, el archivo de zona firmado de la zona, el archivo keyrec, las fases de rollover actuales, las marcas de tiempo de rollover y otra información. El grupo de zonas es opcional y permite controlar un conjunto de zonas relacionadas con una sola ejecución de rollctl, en lugar de una ejecución por zona.

Si los archivos zonefile o keyrec no existen, una rollrec de "roll" se cambiará a una rollrec de "skip". Ese registro no se procesará.

Se puede encontrar una explicación más detallada en rollrec(5).

Directorios

El directorio de ejecución de rollerd es el directorio en el que se ejecuta o el directorio pasado en la opción de línea de comandos -directory. Cualquier archivo utilizado por rollerd que no se especificó con rutas absolutas utiliza este directorio como base.

El campo directory de una entrada rollrec informa a rollerd dónde se pueden encontrar los archivos de la zona. Para esa zona, rollerd se moverá a ese directorio, luego regresará a su directorio de ejecución cuando termine las operaciones de rollover para esa zona. Si el valor directory es una ruta relativa, se agregará al directorio de ejecución de rollerd. Si el valor directory es una ruta absoluta, se usará tal cual.

Controlar rollerd con rollctl

El comando rollctl se utiliza para controlar el comportamiento de rollerd. Hay una serie de comandos disponibles, como iniciar o detener el rollover para una zona seleccionada o todas las zonas, activar o desactivar una visualización gráfica de rollover y detener la ejecución de rollerd. La ruta de comunicación entre rollerd y rollctl depende del sistema operativo. En sistemas tipo Unix, es una tubería de Unix que solo debe ser escribible por el usuario que ejecuta rollerd. Puede encontrar una explicación más detallada de rollctl en rollctl(8).

Una Nota Sobre Archivos y Nombres de Archivos

Hay una serie de archivos y nombres de archivos utilizados por rollerd y zonesigner. El usuario debe ser consciente de los archivos utilizados por estos programas, dónde se encuentran los archivos y dónde se ejecutan los programas.

INICIALIZACIÓN Y USO

Los siguientes pasos deben seguirse para inicializar y usar rollerd. Esto asume que los archivos de zona han sido creados y que BIND y DNSSEC-Tools han sido instalados.

0. Firmar zonas
Las zonas que serán administradas por rollerd deben estar firmadas. Use zonesigner para crear los archivos de zona firmados y los archivos keyrec necesarios para rollerd. El archivo rollrec creado en el siguiente paso debe usar los nombres de archivo keyrec y los nombres de archivo de zona firmados creados aquí.

Este paso es opcional. Si se omite, entonces (en el paso 4 y posteriores) rollerd realizará la creación inicial de claves y la firma de zona de sus zonas utilizando los valores predeterminados que se encuentran en el archivo de configuración de DNSSEC-Tools. rollerd determina si debe realizar estas operaciones iniciales buscando si puede encontrar el archivo keyrec para una zona (como se especifica en el archivo rollrec. Si no puede, realiza las operaciones iniciales; si puede, asume que las operaciones iniciales de la zona ya se han realizado.

1. Crear archivo rollrec
Antes de que pueda usarse rollerd, primero se debe crear un archivo rollrec. Si bien este archivo puede crearse manualmente, el comando rollinit fue escrito específicamente para construir el archivo.
2. Seleccionar parámetros operativos
Varios parámetros operativos de rollerd se toman del archivo de configuración de DNSSEC-Tools. Sin embargo, estos pueden ser anulados por opciones de línea de comandos. Consulte la sección OPCIONES a continuación para obtener más detalles. Si se desean utilizar siempre parámetros no estándar, los campos apropiados en el archivo de configuración de DNSSEC-Tools pueden modificarse para usar estos valores.
3. Instalar la configuración de rollover
La configuración completa de rollover — rollerd, archivo rollrec, valores del archivo de configuración de DNSSEC-Tools, archivos de zona — debe ser instalada. Los lugares apropiados para estas ubicaciones dependen tanto de la instalación como del sistema operativo.
4. Probar la configuración de rollover
La configuración completa de rollover debe ser probada.

Edite los archivos de zona para que sus zonas tengan valores TTL cortos. Un TTL de un minuto debería ser suficiente. Las pruebas de rollover a esta velocidad solo deben realizarse en un entorno de prueba sin la zona firmada real.

Ejecute el siguiente comando:

rollerd -rrfile test.rollrec -logfile - -loglevel info -sleep 60

Este comando asume que el archivo rollrec de prueba es test.rollrec. Escribe una cantidad considerable de mensajes de registro en la terminal y verifica su cola cada 60 segundos. Siga los mensajes para asegurarse de que las acciones apropiadas, según lo requiera el Método de Pre-Publicación, se estén llevando a cabo.

5. Configurar rollerd para que inicie al arrancar
Una vez que se comprueba que la configuración funciona, rollerd debe configurarse para iniciarse al arrancar el sistema. Las operaciones reales requeridas para este paso dependen del sistema operativo.
6. Reiniciar y verificar
El sistema debe reiniciarse y se debe revisar el archivo de registro de rollerd para asegurar que rollerd esté operando correctamente.

OPCIONES

Hay una serie de parámetros operativos que definen cómo funciona rollerd. Estos parámetros definen cosas como el archivo rollrec, el nivel de registro y el archivo de registro. Estos parámetros pueden establecerse en el archivo de configuración de DNSSEC-Tools o proporcionarse como opciones en la línea de comandos de rollerd. Las opciones de línea de comandos anulan los valores en el archivo de configuración.

Se reconocen las siguientes opciones:

-alwayssign
Indica a rollerd que firme las zonas que no están en medio de un proceso de rollover. Esto permite a rollerd actualizar las firmas de zona firmadas y permite que la administración completa de la firma de zona sea asumida por rollerd.

La desventaja de usar esta opción es que todas las zonas que no están en rollover se firmarán después de cada pausa, lo que puede ser costoso computacionalmente.

Nota: Los archivos de zona no se actualizan ni se instalan en este momento. Todavía se necesitan copias e instalaciones manuales.

-autosign | -noautosign
Bandera de firma automática de zona. Si está activada, el archivo de zona se volverá a firmar (y solo se volverá a firmar) si se encuentra que es más nuevo que el archivo de zona firmado correspondiente.
-directory dir
Establece el directorio de ejecución de rollerd. Debe ser un directorio válido.
-display
Inicia el programa de visualización gráfica blinkenlights para mostrar el estado de las zonas administradas por rollerd.
-dtconfig config_file
Nombre de un archivo de configuración alternativo de DNSSEC-Tools a procesar. Si se especifica, este archivo de configuración se utiliza *en lugar* del archivo de configuración normal de DNSSEC-Tools, *no* además de él. Además, se manejará antes que los archivos keyrec, los archivos rollrec y las opciones de línea de comandos.
-foreground
Ejecutar en primer plano y no bifurcarse en un demonio.
-logfile log_file
Establece el archivo de registro de rollerd en log_file. Debe ser un archivo de registro válido, lo que significa que si log_file ya existe, debe ser un archivo regular. Las únicas excepciones son si logfile es /dev/stdout, /dev/tty, -. De estos tres, usar un log_file de - es preferible ya que Perl convertirá correctamente el - a la salida estándar del proceso.
-loglevel level
Establece el nivel de registro de rollerd a level. rollmgr.pm(3) contiene una lista de los niveles de registro válidos.
-noreload
Evita que rollerd indique al demonio DNS que recargue las zonas.
-parameters
Imprime un conjunto de parámetros de rollerd y luego sale. Esto muestra los parámetros con los que ejecutará rollerd, pero se realiza muy poca validación de parámetros.
-pidfile pid_file
Almacena el PID del proceso en ejecución en pid_file. Por defecto, es /var/run/rollerd.pid en la mayoría de los sistemas.
-rrfile rollrec_file
Nombre del archivo rollrec a procesar. Esta es la única "opción" requerida.
-realm realm_name
Nombre del reino en el que se está ejecutando rollerd. Esto es para usar con el sistema de reinos de DNSSEC-Tools como un medio para identificar fácilmente diferentes instanciaciones de rollerd. Es solo informativo (por ejemplo, salida de ps y archivos de registro) y no se utiliza para nada más.
-singlerun
Procesa todos los pasos necesarios una vez y sale. Esta no es la forma ideal de ejecutar rollerd, pero puede ser útil para entornos donde el material de clave solo está disponible cuando se han puesto a disposición tokens de hardware específicos.

El tiempo entre los pasos será potencialmente más largo, ya que el tiempo entre ejecuciones de rollerd depende de cuándo se ejecuta rollerd. Se deben agregar líneas "cmd" al archivo rollrec para realizar acciones particulares.

Las siguientes líneas deben servir como ejemplos:

cmd "rollzsk example.com"
cmd "rollksk example.com"
cmd "dspub example.com"   # (para cuando el padre publica
                          # el nuevo ksk)

La opción -singlerun implica implícitamente -foreground también.

-sleep sleeptime
Establece el tiempo de espera de rollerd a sleeptime. El tiempo de espera es la cantidad de tiempo (en segundos) que rollerd espera entre el procesamiento de su cola basada en rollrec.
-username username
username es el usuario para el cual se ejecutará el demonio rollerd. La UID efectiva del proceso rollerd se establecerá en la UID correspondiente a username.

Si username es un nombre de usuario, debe corresponder a una UID válida; si es una UID, debe corresponder a un nombre de usuario válido.

Si rollerd no tiene la magia del SO apropiada (por ejemplo, en Unix, instalado como programa setuid y propiedad de root) entonces solo podrá cambiar a aquellos usuarios a los que el usuario que ejecuta tiene privilegios para cambiar. Esta restricción depende del sistema operativo y de la forma en que se instala rollerd.

Al usar esta opción, el usuario de destino debe tener acceso a los diversos directorios, registros y archivos de datos que rollerd requiere para ejecutar. Sin este acceso, no se puede producir una ejecución correcta.

-zsargs arglist
Argumentos adicionales de zonesigner que se pasarán a todas las ejecuciones de zonesigner. Estos argumentos anularán los argumentos correspondientes en el archivo de configuración de DNSSEC-Tools y los archivos keyrec de las zonas. Si la entrada zsargs del archivo rollrec de una zona contiene un campo zsargs, este se utilizará en lugar de los especificados por este argumento.

Dado el procesamiento de argumentos de rollerd, los nuevos argumentos para zonesigner no se pueden especificar como se esperaba. En cambio, los argumentos deben proporcionarse de la siguiente manera. El guión inicial debe reemplazarse por un signo igual. Si la opción toma un argumento, el espacio que separaría la opción del argumento de la opción también debe reemplazarse por un signo igual. Si se pasarán múltiples argumentos a través de -zsargs, se deben usar comillas para agruparlos en un solo argumento.

OPTIONS

-zsargs arguments
These arguments are passed directly to zonesigner. For example, if you want to run zonesigner with the “-nokrfile” option, you would run rollerd with “-zsargs -nokrfile”. If you want to run zonesigner with multiple arguments, they must be passed as a single argument to -zsargs. This argument must be quoted so that it is treated as a single argument. For example, if you want to run zonesigner with “-zskcount 5 -kskcount 3”, you would run rollerd with “-zsargs “=zskcount=5 =kskcount=3””. Note that the arguments to zonesigner are preceded by an equals sign, and that rollerd prepends this equals sign to the arguments.

rollerd traduce estos argumentos al formato apropiado para zonesigner. Estos ejemplos deberían aclarar las modificaciones:

Opción normal de zonesigner     rollerd -zsargs opción
------------------------     ----------------------
-nokrfile                    -zsargs =nokrfile
-zskcount 5 -kskcount 3      -zsargs "=zskcount=5 =kskcount=3"
-Version
Muestra la información de la versión para rollerd y el paquete DNSSEC-Tools.
-help
Muestra un mensaje de uso.
-verbose
Se dará salida detallada.

ASUNCIONES

rollerd utiliza el comando rndc para comunicarse con el demonio named de BIND. Por lo tanto, asume que se han tomado las medidas apropiadas para que esta comunicación sea posible.

PROBLEMAS CONOCIDOS

Los siguientes problemas (o problemas potenciales) son conocidos:

-
Cualquier proceso que pueda escribir en el socket de rollover puede enviar comandos a rollerd. Probablemente esto no sea bueno.
