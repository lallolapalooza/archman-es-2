NOMBRE

roc-send - enviar audio en tiempo real

SINOPSIS

roc-send OPCIONES

DESCRIPCIÓN

Lee el flujo de audio desde un dispositivo de audio o archivo y lo envía al receptor remoto.

Opciones

URI de punto final

Las opciones --source, --repair y --control definen los puntos finales de red a los que se enviará el tráfico.

ENDPOINT_URI debe tener el siguiente formato:

protocolo://host[:puerto][/ruta][?consulta]

Ejemplos:

  • rtsp://localhost:123/ruta?consulta
  • rtp+rs8m://localhost:123
  • rtp://127.0.0.1:123
  • rtp://[::1]:123
  • rtcp://10.9.8.3:123

La lista de protocolos compatibles se puede obtener usando la opción --list-supported.

El campo host debe ser un FQDN (nombre de dominio), o una dirección IPv4, o una dirección IPv6 entre corchetes.

El campo de puerto se puede omitir si el protocolo define un puerto estándar. De lo contrario, es obligatorio.

Los campos de ruta y consulta solo están permitidos para protocolos que los admitan, por ejemplo, para RTSP.

Si FEC está habilitado, se debe proporcionar un par de puntos finales de origen y reparación. Los dos puntos finales deben usar protocolos compatibles, por ejemplo, rtp+rs8m:// para el punto final de origen y rs8m:// para el punto final de reparación. Si FEC está deshabilitado, se debe proporcionar un único punto final de origen.

Protocolos de origen y reparación compatibles:

  • origen rtp://, reparación ninguna (RTP simple sin FEC)
  • origen rtp+rs8m://, reparación rs8m:// (RTP con FEC Reed-Solomon)
  • origen rtp+ldpc://, reparación ldpc:// (RTP con FEC LDPC-Staircase)

Además, se recomienda proporcionar un punto final de control. Se utiliza para intercambiar información no multimedia utilizada para identificar la sesión, transportar retroalimentación, etc. Si no se proporciona un punto final de control, la sesión opera en modo de respaldo reducido, que puede ser menos robusto y no admitir todas las funciones.

Protocolos de control compatibles:

•
rtcp://

URI de E/S

La opción --input requiere un URI de dispositivo o archivo en uno de los siguientes formatos:

  • TIPO_DISPOSITIVO://NOMBRE_DISPOSITIVO -- dispositivo de audio
  • TIPO_DISPOSITIVO://default -- dispositivo de audio predeterminado para el tipo de dispositivo dado
  • file:///RUTA/ABSOLUTA -- ruta de archivo absoluta
  • file://localhost/RUTA/ABSOLUTA -- ruta de archivo absoluta (forma alternativa; solo se admite el host "localhost")
  • file:/RUTA/ABSOLUTA -- ruta de archivo absoluta (forma alternativa)
  • file:RUTA/RELATIVA -- ruta de archivo relativa
  • file://- -- stdin
  • file:- -- stdin (forma alternativa)

Ejemplos:

  • pulse://default
  • pulse://alsa_input.pci-0000_00_1f.3.analog-stereo
  • alsa://hw:1,0
  • file:///home/usuario/test.wav
  • file://localhost/home/usuario/test.wav
  • file:/home/usuario/test.wav
  • file:./test.wav
  • file:-

La lista de esquemas y formatos de archivo compatibles se puede obtener usando la opción --list-supported.

Si se omite --input, se seleccionan el controlador y el dispositivo predeterminados.

La opción --input-format se puede usar para forzar el formato del archivo de entrada. Si se omite, el formato del archivo se detecta automáticamente. Esta opción siempre es necesaria cuando la entrada es stdin.

El componente de ruta del URI proporcionado se *descodifica de porcentaje*. Para mayor comodidad, también se permiten caracteres sin codificar, excepto que % siempre debe codificarse como %25.

Por ejemplo, el archivo llamado /foo/bar%/[baz] puede especificarse utilizando cualquiera de los siguientes URIs: file:///foo%2Fbar%25%2F%5Bbaz%5D y file:///foo/bar%25/[baz].

Múltiples ranuras

2>

Se pueden especificar múltiples conjuntos de puntos finales para enviar medios a múltiples direcciones.

Dichos conjuntos de puntos finales se denominan ranuras (slots). Todas las ranuras deben tener el mismo conjunto de tipos de puntos finales (fuente, reparación, etc.) y deben utilizar los mismos protocolos para ellos.

SO_REUSEADDR

Si se proporciona la opción --reuseaddr, la opción de socket SO_REUSEADDR se habilitará para todos los sockets.

Para TCP, permite reutilizar inmediatamente un socket cerrado recientemente en estado TIME_WAIT, lo que puede ser útil si desea reiniciar el servidor rápidamente.

Para UDP, permite que varios procesos se enlacen a la misma dirección, lo que puede ser útil si está utilizando la activación de sockets de systemd.

Independientemente de la opción, SO_REUSEADDR siempre está deshabilitado al enlazar a un puerto efímero.

Unidades de tiempo

TIEMPO debe tener una de las siguientes formas:
123ns; 1.23us; 1.23ms; 1.23s; 1.23m; 1.23h;

Unidades de tamaño

TAMAÑO debe tener una de las siguientes formas:
123; 1.23K; 1.23M; 1.23G;

EJEMPLOS

Ejemplos de puntos finales

Enviar archivo al receptor con un único punto final RTP:

$ roc-send -vv -i file:./input.wav -s rtp://192.168.0.3:10001

Enviar archivo al receptor con puntos finales de origen, reparación y control IPv4:

$ roc-send -vv -i file:./input.wav -s rtp+rs8m://192.168.0.3:10001 \
    -r rs8m://192.168.0.3:10002 -c rtcp://192.168.0.3:10003

Enviar archivo al receptor con puntos finales de origen, reparación y control IPv6:

$ roc-send -vv -i file:./input.wav -s rtp+rs8m://[2001:db8::]:10001 \
    -r rs8m://[2001:db8::]:10002 -r rtcp://[2001:db8::]:10003

Enviar archivo a dos receptores, cada uno con tres puntos finales:

$ roc-send -vv \
    -i file:./input.wav \
    -s rtp+rs8m://192.168.0.3:10001 -r rs8m://192.168.0.3:10002 \
        -c rtcp://192.168.0.3:10003 \
    -s rtp+rs8m://198.214.0.7:10001 -r rs8m://198.214.0.7:10002 \
        -c rtcp://198.214.0.7:10003

Ejemplos de E/S

Capturar sonido del dispositivo predeterminado (omitir -i):

$ roc-send -vv -s rtp://192.168.0.3:10001

Capturar sonido del dispositivo ALSA predeterminado:

$ roc-send -vv -s rtp://192.168.0.3:10001 -i alsa://default

Capturar sonido de un dispositivo PulseAudio específico:

$ roc-send -vv -s rtp://192.168.0.3:10001 -i pulse://alsa_input.pci-0000_00_1f.3.analog-stereo

Enviar archivo WAV (adivinar formato por extensión):

$ roc-send -vv -s rtp://192.168.0.3:10001 -i file:./input.wav

Enviar archivo WAV (especificar formato manualmente):

$ roc-send -vv -s rtp://192.168.0.3:10001 -i file:./input.file --input-format wav

Enviar WAV desde stdin:

$ roc-send -vv -s rtp://192.168.0.3:10001 -i file:- --input-format wav <./input.wav

Enviar archivo WAV (especificar ruta absoluta):

$ roc-send -vv -s rtp://192.168.0.3:10001 -i file:///home/user/input.wav

Ejemplos de ajuste

Forzar una tasa específica en el dispositivo de entrada:

$ roc-send -vv -s rtp://192.168.0.3:10001 --rate=44100

Seleccionar el esquema FEC LDPC-Staircase y un tamaño de bloque mayor:

$ roc-send -vv -i file:./input.wav -s rtp+ldpc://192.168.0.3:10001 \
    -r ldpc://192.168.0.3:10002 -c ldpc://192.168.0.3:10003 \
    --nbsrc=1000 --nbrpr=500

Seleccionar una longitud de paquete menor:

$ roc-send -vv -i file:./input.wav -s rtp+ldpc://192.168.0.3:10001 \
    --packet-len 2500us

Seleccionar menor latencia de E/S y longitud de trama:

$ roc-send -vv -s rtp://192.168.0.3:10001 \
    --io-latency=20ms --frame-len 4ms

Especificar manualmente los parámetros de remuestreo:

$ roc-send -vv -s rtp://192.168.0.3:10001 \
    --resampler-backend=speex --resampler-profile=high

Realizar el ajuste de latencia en el remitente en lugar del receptor:

$ roc-recv -vv -o pulse://default -s rtp+rs8m://0.0.0.0:10001 \
    -r rs8m://0.0.0.0:10002 -c rtcp://0.0.0.0:10003 \
    --latency-profile=intact --target-latency=200ms
$ roc-send -vv -i file:./input.wav -s rtp+rs8m://192.168.0.3:10001 \
    -r rs8m://192.168.0.3:10002 -c rtcp://192.168.0.3:10003 \
    --latency-profile=gradual --target-latency=200ms

VARIABLES DE ENTORNO

Las siguientes variables de entorno son compatibles:

NO_COLOR
Por defecto, la coloración de la terminal se detecta automáticamente. Esta variable de entorno puede configurarse en una cadena no vacía para deshabilitar la coloración de la terminal. Tiene menor precedencia que la opción --color.
FORCE_COLOR
Por defecto, la coloración de la terminal se detecta automáticamente. Esta variable de entorno puede configurarse en un entero positivo para habilitar/forzar la coloración de la terminal. Tiene menor precedencia que la variable NO_COLOR y la opción --color.
