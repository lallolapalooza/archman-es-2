XSD(1) Manual de Comandos Generales XSD(1)

NOMBRE

xsd - Compilador de W3C XML Schema a C++

SINOPSIS

xsd comando [ opciones ] archivo [ archivo ...]
xsd help [ comando ]
xsd version

DESCRIPCIÓN

xsd genera un mapeo C++ con tipos estáticos y específico del vocabulario a partir de definiciones de W3C XML Schema. El mapeo específico a generar se selecciona mediante un comando. Cada mapeo tiene un número de opciones específicas del mapeo que deben aparecer, si las hay, después del comando. Los archivos de entrada deben ser definiciones de W3C XML Schema. El conjunto exacto de archivos generados depende del mapeo y las opciones seleccionadas.

COMANDOS

cxx-tree
Genera el mapeo C++/Árbol. Por cada archivo de entrada con el formato nombre.xsd se generan los siguientes archivos C++: nombre.hxx (archivo de cabecera), nombre.ixx (archivo en línea, generado solo si se especifica la opción --generate-inline), nombre.cxx (archivo fuente) y nombre-fwd.hxx (archivo de declaración adelantada, generado solo si se especifica la opción --generate-forward).
cxx-parser
Genera el mapeo C++/Parser. Por cada archivo de entrada con el formato nombre.xsd se generan los siguientes archivos C++: nombre-pskel.hxx (archivo de cabecera del esqueleto del parser), nombre-pskel.ixx (archivo en línea del esqueleto del parser, generado solo si se especifica la opción --generate-inline) y nombre-pskel.cxx (archivo fuente del esqueleto del parser). Si se especifica la opción --generate-noop-impl o --generate-print-impl, se generan los siguientes archivos de implementación de ejemplo adicionales: nombre-pimpl.hxx (archivo de cabecera de la implementación del parser) y nombre-pimpl.cxx (archivo fuente de la implementación del parser). Si se especifica la opción --generate-test-driver, se genera el archivo adicional nombre-driver.cxx para el controlador de pruebas.
help
Imprime información de uso y sale. Usa
xsd help comando

para obtener ayuda específica del comando.

version
Imprime la versión y sale.

OPCIONES

Las opciones específicas del comando, si las hay, deben aparecer después del comando correspondiente.

opciones comunes

--std version
Especifica el estándar C++ con el que debe cumplir el código generado. Los valores válidos son c++98, c++11 (por defecto), c++14, c++17, c++20 y c++23.

El estándar C++ afecta a varios aspectos del código generado que se discuten con más detalle en la documentación específica de cada mapeo. En general, cuando se selecciona C++11, el código generado se basa en la semántica de movimiento y utiliza std::unique_ptr en lugar del obsoleto std::auto_ptr. Actualmente, no hay diferencia entre los modos C++11 y los estándares posteriores.

Cuando se selecciona el modo C++11, normalmente no necesita realizar ningún paso adicional aparte de habilitar C++11 en su compilador C++, si es necesario. El compilador XSD agregará automáticamente las definiciones de macro necesarias a los archivos de cabecera generados que cambiarán la biblioteca en tiempo de ejecución de XSD (libxsd), que solo requiere cabeceras, al modo C++11. Sin embargo, si incluye alguna de las cabeceras de tiempo de ejecución de XSD directamente en su aplicación (normalmente solo incluye las cabeceras generadas), entonces necesitará definir la macro XSD_CXX11 para todo su proyecto.

--char-type tipo
Genera código usando el tipo de carácter tipo proporcionado en lugar del valor por defecto char. Los valores válidos son char y wchar_t.
--char-encoding enc
Especifica la codificación de caracteres que se debe utilizar en el código generado. Los valores válidos para el tipo de carácter char son utf8 (por defecto), iso8859-1, lcp (página de código local de Xerces-C++) y custom. Si pasa custom como valor, necesitará incluir el archivo de cabecera de la implementación del transcodificador para su codificación al principio de los archivos de cabecera generados (ver la opción --hxx-prologue).

Para el tipo de carácter wchar_t, el único valor válido es auto y la codificación se selecciona automáticamente entre UTF-16 y UTF-32/UCS-4, dependiendo del tamaño del tipo wchar_t.

--output-dir dir
Escribe los archivos generados en dir en lugar del directorio actual.
--generate-inline
Genera funciones simples en línea. Esta opción activa la creación del archivo en línea.
--generate-xml-schema
Genera un archivo de cabecera C++ como si el esquema que se compila definiera el espacio de nombres XML Schema. Para el mapeo C++/Árbol, el archivo resultante contendrá definiciones para todos los tipos integrados de XML Schema. Para el mapeo C++/Parser, el archivo resultante contendrá definiciones para todos los esqueletos de parser y las implementaciones correspondientes a los tipos integrados de XML Schema.

El archivo de esquema proporcionado al compilador no tiene por qué existir y solo se utiliza para derivar el nombre del archivo de cabecera resultante. Utilice la opción --extern-xml-schema para incluir este archivo en los archivos generados para otros esquemas.

--extern-xml-schema archivo
Incluye un archivo de cabecera derivado de archivo en lugar de generar el mapeo del espacio de nombres XML Schema en línea. El archivo proporcionado no tiene por qué existir y solo se utiliza para derivar el nombre del archivo de cabecera incluido. Utilice la opción --generate-xml-schema para generar este archivo de cabecera.
--namespace-map xns=cns
Mapea el espacio de nombres XML Schema xns al espacio de nombres C++ cns. Repita esta opción para especificar el mapeo de más de un espacio de nombres XML Schema. Por ejemplo, la siguiente opción:

--namespace-map http://example.com/foo/bar=foo::bar

Mapeará el espacio de nombres XML Schema http://example.com/foo/bar al espacio de nombres C++ foo::bar.

--namespace-regex regex
Agrega regex a la lista de expresiones regulares utilizadas para traducir nombres de espacios de nombres XML Schema a nombres de espacios de nombres C++. regex es una expresión regular similar a Perl en el formato /patrón/reemplazo/. Cualquier carácter puede usarse como delimitador en lugar de '/'. No se soporta el escape del carácter delimitador en patrón o reemplazo.

Todas las expresiones regulares se insertan en una pila, considerándose primero la última expresión especificada. Se utiliza la primera coincidencia que tiene éxito. Las expresiones regulares se aplican a una cadena en el formato

nombre_archivo espacio_de_nombres

Por ejemplo, si tiene el archivo hello.xsd con el espacio de nombres http://example.com/hello y ejecuta xsd en este archivo, la cadena en cuestión será:

hello.xsd. http://example.com/hello

Para el espacio de nombres XML Schema integrado, la cadena es:

XMLSchema.xsd http://www.w3.org/2001/XMLSchema

Los siguientes tres pasos se realizan para cada expresión regular hasta que se encuentra la coincidencia:

1. Se aplica la expresión y si el resultado está vacío, se considera la siguiente expresión.

2. Todos los '/' se reemplazan por '::'.

3. El resultado se verifica

Como ejemplo, la siguiente expresión mapea espacios de nombres de esquemas XML en la forma http://example.com/foo/bar a espacios de nombres de C++ en la forma foo::bar:

%.* http://example.com/(.+)%$1%

Añade regex a la lista de expresiones regulares utilizadas para transformar las rutas de las directivas #include. regex es una expresión regular similar a Perl con el formato /patrón/reemplazo/. Como ejemplo, la siguiente expresión transforma rutas en la forma schemas/foo/bar a rutas en la forma generated/foo/bar:

%schemas/(.+)%generated/$1%

--generate-dep
Genera información de dependencias de make. Esta opción activa la creación del archivo .d que contiene las dependencias de los archivos generados en el archivo de esquema principal, así como en todos los archivos de esquema que incluye/importa, transitivamente. Este archivo de dependencia se incluye normalmente en el makefile principal para implementar el seguimiento automático de dependencias. Consulte también las opciones --dep-*.

Tenga en cuenta también que la generación automática de dependencias no es compatible en el modo de archivo por tipo (--file-per-type). En este caso, todos los archivos generados se producen con una sola invocación del compilador y dependen de todos los esquemas. Como resultado, es más fácil establecer dicha dependencia manualmente, quizás con la ayuda de las opciones --file-list*.

Como resultado, las rutas de las directivas #include para dichos esquemas tendrán la forma foo/schema.hxx y los archivos C++ generados se colocarán en el subdirectorio foo/:

%.*/foo/1.0.0/(.+)%foo/$1%

xsdcxx options

The xsdcxx compiler supports the following options:

--classes-regex regex
Generate C++ classes for the schema types matched by regex. The regex argument is in the form /name-pat/[type-sub/[base-sub/]], where name-pat is a regex pattern that will be matched against type names as defined in XML Schema and type-sub is a C++ type name substitution that should be used instead. If type-sub is not present or its substitution results in an empty string then the custom type is assumed to have the same name and be defined in the same namespace as the generated class would have. If base-sub is present and its substitution results in a non-empty string then the generated class is still generated but with the result of this substitution as its name. The pattern and substitutions are in the Perl regular expression format. See also the REGEX AND SHELL QUOTING section below.
--parts num
Split generated source code into num parts. This is useful when translating large, monolithic schemas and a C++ compiler is not able to compile the resulting source code at once (usually due to insufficient memory).
--parts-suffix suffix
Use suffix instead of the default '-' to separate the file name from the part number.

cxx-parser command options

--type-map mapfile
Read XML Schema to C++ type mapping information from mapfile. Repeat this option to specify several type maps. Type maps are considered in order of appearance and the first match is used. By default all user-defined types are mapped to void. See the TYPE MAP section below for more information.
--xml-parser parser
Use parser as the underlying XML parser. Valid values are xerces for Xerces-C++ (default) and expat for Expat.
--generate-validation
Generate validation code. The validation code ("perfect parser") ensures that instance documents conform to the schema. Validation code is generated by default when the selected underlying XML parser is non-validating (expat).
--suppress-validation
Suppress the generation of validation code. Validation is suppressed by default when the selected underlying XML parser is validating (xerces).
--generate-polymorphic
Generate polymorphism-aware code. Specify this option if you use substitution groups or xsi:type.
--generate-noop-impl
Generate a sample parser implementation that does nothing (no operation). The sample implementation can then be filled with the application-specific code. NAMING CONVENTION

The compiler can be instructed to use a particular naming convention in the generated code. A number of widely-used conventions can be selected using the --type-naming and --function-naming options. A custom naming convention can be achieved using the --type-regex, --accessor-regex, --one-accessor-regex, --opt-accessor-regex, --seq-accessor-regex, --modifier-regex, --one-modifier-regex, --opt-modifier-regex, --seq-modifier-regex, --parser-regex, --serializer-regex, --const-regex, --enumerator-regex, and --element-type-regex options.

The --type-naming option specifies the convention that should be used for naming C++ types. Possible values for this option are knr (default), ucc, and java. The knr value (stands for K&R) signifies the standard, lower-case naming convention with the underscore used as a word delimiter, for example: foo, foo_bar. The ucc (stands for upper-camel-case) and java values a synonyms for the same naming convention where the first letter of each word in the name is capitalized, for example: Foo, FooBar.

Similarly, the --function-naming option specifies the convention that should be used for naming C++ functions. Possible values for this option are knr (default), lcc, and java. The knr value (stands for K&R) signifies the standard, lower-case naming convention with the underscore used as a word delimiter, for example: foo(), foo_bar(). The lcc value (stands for lower-camel-case) signifies a naming convention where the first letter of each word except the first is capitalized, for example: foo(), fooBar(). The ucc value (stands for upper-camel-case) signifies a naming convention where the first letter of each word is capitalized, for example: Foo(), FooBar(). The java naming convention is similar to the lower-camel-case one except that accessor functions are prefixed with get, modifier functions are prefixed with set, parsing functions are prefixed with parse, and serialization functions are prefixed with serialize, for example: getFoo(), setFooBar(), parseRoot(), serializeRoot().

Note that the naming conventions specified with the --type-naming and --function-naming options perform only limited transformations on the names that come from the schema in the form of type, attribute, and element names. In other words, to get consistent results, your schemas should follow a similar naming convention as the one you would like to have in the generated code. Alternatively, you can use the --*-regex options (discussed below) to perform further transformations on the names that come from the schema.

The --type-regex, --accessor-regex, --one-accessor-regex, --opt-accessor-regex, --seq-accessor-regex, --modifier-regex, --one-modifier-regex, --opt-modifier-regex, --seq-modifier-regex, --parser-regex, --serializer-regex, --const-regex, --enumerator-regex, and --element-type-regex options allow you to specify extra regular expressions for each name category in addition to the predefined set that is added depending on the --type-naming and --function-naming options. Expressions that are provided with the --*-regex options are evaluated prior to any predefined expressions. This allows you to selectively override some or all of the predefined transformations. When debugging your own expressions, it is often useful to see which expressions match which names. The --name-regex-trace option allows you to trace the process of applying regular expressions to names.

The value for the --*-regex options should be a perl-like regular expression in the form /pattern/replacement/. Any character can be used as a delimiter instead of /. Escaping of the delimiter character in pattern or replacement is not supported. All the regular expressions for each category are pushed into a category-specific stack with the last specified expression considered first. The first match that succeeds is used. REGEX

Las expresiones regulares (regex) se utilizan como respaldo. Para las categorías --one-modifier-regex, --opt-modifier-regex y --seq-modifier-regex, las expresiones --modifier-regex se utilizan como respaldo. Para la categoría --element-type-regex, las expresiones --type-regex se utilizan como respaldo.

Las expresiones de nombres de tipo (--type-regex) se evalúan en la cadena de nombres que tiene el siguiente formato:

[namespace ]name[,name][,name][,name]

Las expresiones de nombres de tipo de elemento (--element-type-regex), efectivas solo cuando se especifica la opción --generate-element-type, se evalúan en la cadena de nombres que tiene el siguiente formato:

namespace name

En el formato del nombre de tipo, la parte namespace seguida de un espacio solo está presente para los nombres de tipo globales. Para tipos y elementos globales definidos en esquemas sin un espacio de nombres de destino, la parte namespace está vacía, pero el espacio todavía está presente. En el formato del nombre de tipo, después del componente name inicial, se pueden presentar hasta tres componentes name adicionales, separados por comas. Por ejemplo:

http://example.com/hello type

foo

foo,iterator

foo,const,iterator

El siguiente conjunto de expresiones regulares predefinidas se utiliza para transformar los nombres de tipo cuando se selecciona la convención de nomenclatura en mayúsculas y minúsculas:

/(?:[^ ]* )?([^,]+)/\u$1/

/(?:[^ ]* )?([^,]+),([^,]+)/\u$1\u$2/

/(?:[^ ]* )?([^,]+),([^,]+),([^,]+)/\u$1\u$2\u$3/

/(?:[^ ]* )?([^,]+),([^,]+),([^,]+),([^,]+)/\u$1\u$2\u$3\u$4/

Las expresiones de acceso y modificador (--*accessor-regex y --*modifier-regex) se evalúan en la cadena de nombres que tiene el siguiente formato:

name[,name][,name]

Después del componente name inicial, se pueden presentar hasta dos componentes name adicionales, separados por comas. Por ejemplo:

foo

dom,document

foo,default,value

El siguiente conjunto de expresiones regulares predefinidas se utiliza para transformar los nombres de acceso cuando se selecciona la convención de nomenclatura java:

/([^,]+)/get\u$1/

/([^,]+),([^,]+)/get\u$1\u$2/

/([^,]+),([^,]+),([^,]+)/get\u$1\u$2\u$3/

Para las categorías de analizador, serializador y enumerador, las expresiones regulares correspondientes se evalúan en nombres locales de elementos y en valores de enumeración, respectivamente. Por ejemplo, la siguiente expresión regular predefinida se utiliza para transformar los nombres de funciones de análisis cuando se selecciona la convención de nomenclatura java:

/(.+)/parse\u$1/

La categoría const se utiliza para crear nombres de constantes C++ para los identificadores de contenido de elementos/comodines/texto en tipos ordenados.

Consulte también la sección REGEX Y ENTRECOMILLADO DEL SHELL a continuación.

MAPA DE TIPOS

Los archivos de mapa de tipos se utilizan en C++/Parser para definir un mapeo entre los tipos de XML Schema y C++. El compilador utiliza esta información para determinar los tipos de retorno de las funciones post_* en los esqueletos del analizador correspondientes a los tipos de XML Schema, así como los tipos de argumento para las devoluciones de llamada correspondientes a elementos y atributos de estos tipos.

El compilador tiene un conjunto de reglas de mapeo predefinidas que mapean los tipos de XML Schema integrados a tipos C++ adecuados (discutidos a continuación) y todos los demás tipos a void. Al proporcionar sus propios mapas de tipos, puede anular estas reglas predefinidas. El formato del archivo de mapa de tipos se presenta a continuación:

namespace esquema-namespace [ cxx-namespace ]
{
( include nombre-archivo; )*
([ type ] esquema-tipo cxx-ret-type [ cxx-arg-type ]; )*
}

Tanto esquema-namespace como esquema-tipo son patrones regex, mientras que cxx-namespace, cxx-ret-type y cxx-arg-type son sustituciones de patrones regex. Todos los nombres pueden estar opcionalmente entre comillas (" "), por ejemplo, para incluir espacios en blanco.

esquema-namespace determina el espacio de nombres XML Schema. El cxx-namespace opcional se antepone a cada nombre de tipo C++ en esta declaración de espacio de nombres. cxx-ret-type es un nombre de tipo C++ que se utiliza como tipo de retorno para las funciones post_*. El cxx-arg-type opcional es un tipo de argumento para las funciones de devolución de llamada correspondientes a elementos y atributos de este tipo. Si no se especifica cxx-arg-type, se utiliza por defecto cxx-ret-type si cxx-ret-type termina en * o & (es decir, es un puntero o una referencia) y const cxx-ret-type& de lo contrario. nombre-archivo es un nombre de archivo en formato " " o < > y se agrega con la directiva #include al código generado.

El carácter # inicia un comentario que termina con una nueva línea o el final del archivo. Para especificar un nombre que contenga #, enciérrelo entre comillas (" "). Por ejemplo:

namespace http://www.example.com/xmlns/my my
{
include "my.hxx";


# Pasar manzanas por valor.
#
apple apple;


# Pasar naranjas como punteros.
#
orange orange_t*;
}

En el ejemplo anterior, para el tipo XML Schema http://www.example.com/xmlns/my#orange, el tipo C++ my::orange_t* se utilizará tanto como tipo de retorno como de argumento.

Se pueden especificar varias declaraciones de espacio de nombres en un solo archivo. La declaración de espacio de nombres también se puede omitir por completo para mapear tipos en un esquema sin espacio de nombres. Por ejemplo:

include "my.hxx";
apple apple;

namespace http://www.example.com/xmlns/my
{
orange "const orange_t*";
}

El compilador tiene una serie de reglas de mapeo predefinidas que se pueden presentar como los siguientes archivos de mapa. Los tipos integrados de XML Schema basados en cadenas se mapean a std::string o std::wstring según el tipo de carácter seleccionado con la opción --char-type (char por defecto). Los tipos binarios de XML Schema se mapean a std::unique_ptr<xml_schema::buffer> o std::auto_ptr<xml_schema::buffer> según el estándar C++ seleccionado con la opción --std (c++11 por defecto).

{

byte "signed char" "signed char";

short short short;
unsignedShort "unsigned short" "unsigned short";


int int int;
unsignedInt "unsigned int" "unsigned int";


long "long long" "long long";
unsignedLong "unsigned long long" "unsigned long long";


integer "long long" "long long";


negativeInteger "long long" "long long";
nonPositiveInteger "long long" "long long";


positiveInteger "unsigned long long" "unsigned long long";
nonNegativeInteger "unsigned long long" "unsigned long long";


float float float;
double double double;
decimal double double;


string std::string;
normalizedString std::string;
token std::string;
Name std::string;
NMTOKEN std::string;
NCName std::string;
ID std::string;
IDREF std::string;
language std::string;
anyURI std::string;


NMTOKENS xml_schema::string_sequence;

base64Binary std::[unique|auto]_ptr<xml_schema::buffer>
std::[unique|auto]_ptr<xml_schema::buffer>;

La última regla predefinida mapea cualquier cosa que no haya sido mapeada por reglas anteriores a void:

namespace .*

REGEX Y ENTRECOMILLADO DEL SHELL

Al ingresar un argumento de expresión regular en la línea de comandos del shell, a menudo es necesario usar comillas (encerrar el argumento entre " " o ' ') para evitar que el shell interprete ciertos caracteres, por ejemplo, espacios como separadores de argumentos y $ como expansiones de variables.

Desafortunadamente, es difícil lograr esto de una manera portable entre shells POSIX, como los que se encuentran en GNU/Linux y UNIX, y el shell de Windows. Por ejemplo, si usa " " para entrecomillar, obtendrá un resultado incorrecto con los shells POSIX si su expresión contiene $. La forma estándar de lidiar con esto en sistemas POSIX es usar ' ' en su lugar. Desafortunadamente, el shell de Windows no elimina ' ' de los argumentos cuando se pasan a las aplicaciones. Como resultado, es posible que deba usar ' ' para POSIX y " " para Windows ($ no se trata como un carácter especial en Windows).

Alternativamente, puede guardar las opciones de expresiones regulares en un archivo, una opción por línea, y usar este archivo con la opción --options-file. Con este enfoque, no necesita preocuparse por el entrecomillado del shell.
