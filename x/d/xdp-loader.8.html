xdp-loader(8) Cargador de programas XDP xdp-loader(8)

NOMBRE

xdp-loader - un cargador de programas XDP

SINOPSIS

Xdp-loader es un cargador simple para programas XDP con soporte para enlazar múltiples programas a la misma interfaz. Para lograr esto, expone las mismas semánticas de carga y descarga expuestas por la biblioteca libxdp. Consulte la página del manual de libxdp(3) para obtener detalles sobre cómo funciona esto y en qué características del kernel se basa.

Ejecutando xdp-loader

La sintaxis para ejecutar xdp-loader es:

xdp-loader COMANDO [opciones]
Donde COMANDO puede ser uno de:
       load        - cargar un programa XDP en una interfaz
       unload      - descargar un programa XDP de una interfaz
       status      - mostrar el estado actual del programa XDP
       features    - mostrar las características XDP soportadas por la NIC
       clean       - limpiar enlaces de programas desvinculados en el directorio bpffs de XDP
       help        - mostrar la lista de comandos disponibles

Cada comando y sus opciones se explican a continuación. O use xdp-loader COMANDO --help para ver las opciones de cada comando.

El comando LOAD

El comando load carga uno o más programas XDP en una interfaz.

La sintaxis para el comando load es:

xdp-loader load [opciones] <nombre_iface> <programas>

Donde <nombre_iface> es el nombre de la interfaz en la que cargar los programas, y <programas> son uno o más nombres de archivo que contienen programas XDP. Los programas se cargarán en la interfaz en el orden de su preferencia, según lo especificado por los metadatos del programa (ver libxdp(3)).

Las opciones soportadas son:

-m, --modo <modo>

Especifica en qué modo se cargará el programa XDP a cargar. Los valores válidos son 'native', que es el modo XDP nativo en el controlador por defecto, 'skb', que causa el uso del llamado modo skb (también conocido como XDP genérico), 'hw' que causa que el programa se descargue al hardware, o 'unspecified' que deja que el kernel elija un modo (lo que hará eligiendo el modo nativo si el controlador lo soporta, o el modo genérico en caso contrario). Tenga en cuenta que usar 'unspecified' puede dificultar la predicción del modo en que terminará cargándose un programa. Por esta razón, el valor predeterminado es 'native'. Tenga en cuenta que el hardware con soporte para el modo 'hw' es raro: las tarjetas Netronome/Corigine (que usan el controlador 'nfp') son los únicos dispositivos con soporte para esto en el kernel principal de Linux.

-p, --ruta-pin <ruta>

Esto especifica una ruta raíz bajo la cual se fijarán (pin) todos los mapas que definan el atributo 'pinning' en sus definiciones. Esta ruta debe estar ubicada en un sistema de archivos bpffs. Si no se establece, los mapas no se fijarán, incluso si especifican pinning en sus definiciones. Al fijar mapas, si la ubicación fijada para un mapa ya existe, se reutilizará el mapa fijado allí si es compatible con el tipo del mapa que se está cargando.

-s, --seccion <seccion>

Especifica qué sección ELF cargar los programas XDP desde cada archivo. El valor predeterminado es usar el primer programa de cada archivo. Si se establece esta opción, se aplica a todos los programas que se están cargando.

-n, --nombre-prog <nombre_prog>

Especifica qué programa BPF con el nombre cargar los programas XDP desde cada archivo. El valor predeterminado es usar el primer programa de cada archivo. Solo se puede especificar --section o --prog-name. Si se establece esta opción, se aplica a todos los programas que se están cargando.

-P, --prio <prioridad>

Especifica la prioridad con la que cargar los programas XDP (esto afecta el orden de los programas que se ejecutan en la interfaz). El valor predeterminado es usar el valor de los metadatos en el archivo ELF del programa, o un valor de 50 si el programa no tiene dichos metadatos. Si se establece esta opción, se aplica a todos los programas que se están cargando.

-A, --acciones <acciones>

Especifica las "acciones de llamada en cadena" de los programas XDP cargados. Estas son las acciones XDP que harán que se llame al siguiente programa cargado en la interfaz, en lugar de retornar inmediatamente. El valor predeterminado es usar el valor establecido en los metadatos del archivo ELF del programa, o XDP_PASS si no se establecen dichos metadatos. Si se establece esta opción, se aplica a todos los programas que se están cargando.

-v, --verbose

Habilita el registro de depuración. Especifique dos veces para una mayor verbosidad.

-h, --help

Muestra un resumen de las opciones disponibles

El comando UNLOAD

El comando unload se utiliza para descargar programas de una interfaz.

La sintaxis para el comando unload es:

xdp-loader unload [opciones] <nombre_iface>

Donde <nombre_iface> es el nombre de la interfaz en la que cargar los programas. Se deben usar las opciones --all o --id para especificar qué programa(s) descargar.

Las opciones soportadas son:

-i, --id <id>

Descarga un solo programa de la interfaz por ID. Use xdp-loader status para obtener el ID del programa que se está descargando. Si este programa es el último cargado en la interfaz, también se eliminará el programa distribuidor (dispatcher), lo que hace que la operación sea equivalente a especificar --all.

-a, --all

Descarga todos los programas XDP de la interfaz, así como el distribuidor de múltiples programas.

-v, --verbose

Habilita el registro de depuración. Especifique dos veces para una mayor verbosidad.

-h, --help

Muestra un resumen de las opciones disponibles

El comando STATUS

El comando status muestra una lista de interfaces en el sistema y los programas XDP cargados en cada interfaz. Para cada interfaz, se muestra una lista de programas, con la prioridad de ejecución y las "acciones de cadena" para cada programa. Consulte la sección sobre metadatos del programa para conocer el significado de estos metadatos.

-v, --verbose

Habilita el registro de depuración. Especifique dos veces para una mayor verbosidad.

-h, --help

Muestra un resumen de las opciones disponibles

El comando FEATURES

El comando features muestra las características XDP soportadas por la NIC.

Las características XDP actualmente soportadas son:

NETDEV_XDP_ACT_BASIC

El dispositivo de red tiene soporte básico para ejecutar programas XDP y puede manejar el conjunto base de códigos de retorno (XDP_ABORTED, XDP_DROP, XDP_PASS, XDP_TX).

NETDEV_XDP_ACT_REDIRECT

El dispositivo de red soporta el manejo del código de retorno XDP_REDIRECT. Esto significa que los paquetes pueden ser redirigidos desde este dispositivo por XDP.

NETDEV_XDP_ACT_NDO_XMIT

Las interfaces de red implementan la devolución de llamada ndo_xdp_xmit. Esto significa que los paquetes pueden ser redirigidos

The FEATURES command

The syntax for the features command is:

xdp-loader features [ifname]

The features command enumerates the supported XDP features for a given network device. If no interface name is given, then the list of all known interfaces and their features will be displayed.

The output shows what features the network device supports. A program can then be loaded onto the device only if all required features are present. For example, if a program requires AF_XDP zero-copy support, it will fail to load on a device that does not advertise NETDEV_XDP_ACT_XSK_ZEROCOPY.

NETDEV_XDP_ACT_BASIC

The networking device has basic XDP support enabled. This means that XDP programs can be attached and executed on the device.

NETDEV_XDP_ACT_XSK_ZEROCOPY

The networking device supports AF_XDP in zero copy mode.

NETDEV_XDP_ACT_HW_OFFLOAD

The networking device supports XDP hw offloading.

NETDEV_XDP_ACT_RX_SG

The networking device supports non-linear XDP frames on the receive side. This means XDP can be used with big MTUs on this device (if the XDP program is compiled with fragments support)

NETDEV_XDP_ACT_NDO_XMIT_SG

The networking device supports non-linear XDP frames on the transmit side. This means non-linear frames can be redirected to this device.

The CLEAN command

The syntax for the clean command is:

xdp-loader clean [options] [ifname]

The clean command cleans up any detached program links in the XDP bpffs directory. When a network interface disappears, any programs loaded in software mode (e.g. skb, native) remain pinned in the bpffs directory, but become detached from the interface. These need to be unlinked from the filesystem. The clean command takes an optional interface parameter to only unlink detached programs corresponding to the interface. By default, all detached programs for all interfaces are unlinked.

The supported options are:

-v, --verbose

Enable debug logging. Specify twice for even more verbosity.

-h, --help

Display a summary of the available options

Examples

To load an XDP program on the eth0 interface simply do:

# xdp-loader load eth0 xdp_drop.o
# xdp-loader status
CURRENT XDP PROGRAM STATUS:
Interface        Prio  Program name     Mode     ID   Tag               Chain actions
-------------------------------------------------------------------------------------
lo               <no XDP program>
eth0                   xdp_dispatcher   native   50   d51e469e988d81da
 =>              50    xdp_drop                  55   57cd311f2e27366b  XDP_PASS

Which shows that a dispatcher program was loaded on the interface, and the xdp_drop program was installed as the first (and only) component program after it. In this instance, the program does not specify any of the metadata above, so the defaults (priority 50 and XDP_PASS as its chain call action) was used.

To use the automatic map pinning, include the pinning attribute into the map definition in the program, something like:

struct {
        __uint(type, BPF_MAP_TYPE_ARRAY);
        __uint(max_entries, 10);
        __type(key, __u32);
        __type(value, __u64);
        __uint(pinning, LIBBPF_PIN_BY_NAME);
} my_map SEC(".maps");

And load it with the --pin-path attribute:

# xdp-loader load eth0 my_prog.o --pin-path /sys/fs/bpf/my-prog

This will pin the map at /sys/fs/bpf/my-prog/my_map. If this already exists, the pinned map will be reused instead of creating a new one, which allows different BPF programs to share the map.
