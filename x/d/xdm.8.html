XDM(8) Manual del Administrador del Sistema XDM(8)

NOMBRE

xdm - Gestor de Pantallas X con soporte para XDMCP, selector de host

SINOPSIS

xdm [ -config archivo_configuracion ] [ -nodaemon ] [ -debug nivel_debug ] [ -error archivo_log_errores ] [ -resources archivo_recursos ] [ -server entrada_servidor ] [ -session programa_sesion ]

DESCRIPCIÓN

Xdm gestiona una colección de pantallas X, que pueden estar en el host local o en servidores remotos. El diseño de xdm se guió por las necesidades de los terminales X, así como por el protocolo XDMCP (X Display Manager Control Protocol) del Grupo Abierto. Xdm proporciona servicios similares a los proporcionados por init, getty y login en terminales de caracteres: solicitando nombre de usuario y contraseña, autenticando al usuario y ejecutando una "sesión".

Una "sesión" se define por la vida útil de un proceso particular; en el mundo tradicional de terminales basados en caracteres, es el shell de inicio de sesión del usuario. En el contexto de xdm, es un gestor de sesiones arbitrario. Esto se debe a que en un entorno de ventanas, el shell de inicio de sesión del usuario no necesariamente tiene ninguna interfaz de tipo terminal con la que conectarse. Cuando no hay un gestor de sesiones real, un gestor de ventanas o un emulador de terminal se utiliza típicamente como "gestor de sesiones", lo que significa que la terminación de este proceso finaliza la sesión del usuario.

Cuando la sesión se termina, xdm reinicia el servidor X y (opcionalmente) reinicia todo el proceso.

Cuando xdm recibe una consulta Indirecta a través de XDMCP, puede ejecutar un proceso chooser para realizar una BroadcastQuery de XDMCP (o una consulta XDMCP a hosts especificados) en nombre de la pantalla y ofrecer un menú de hosts posibles que ofrezcan gestión de pantallas XDMCP. Esta característica es útil con terminales X que no ofrecen un menú de hosts ellos mismos.

Xdm puede configurarse para ignorar los mensajes BroadcastQuery de hosts seleccionados. Esto es útil cuando no desea que el host aparezca en los menús producidos por chooser o por los propios terminales X.

Dado que xdm proporciona la primera interfaz que verán los usuarios, está diseñado para ser simple de usar y fácil de personalizar a las necesidades de un sitio en particular. Xdm tiene muchas opciones, la mayoría de las cuales tienen valores predeterminados razonables. Navegue por las diversas secciones de este manual, eligiendo las cosas que desea cambiar. Preste especial atención a la sección Programa de Sesión, que describirá cómo configurar el estilo de sesión deseado.

VISIÓN GENERAL

xdm es altamente configurable y la mayor parte de su comportamiento puede controlarse mediante archivos de recursos y scripts de shell. Los nombres de estos archivos son recursos leídos del archivo xdm-config o del archivo especificado con la opción -config.

xdm ofrece gestión de pantallas de dos maneras diferentes. Puede gestionar servidores X ejecutándose en la máquina local y especificados en Xservers, y puede gestionar servidores X remotos (típicamente terminales X) utilizando XDMCP (el protocolo de control de gestor de pantallas X) según lo especificado en el archivo Xaccess.

Los recursos de los clientes X ejecutados por xdm fuera de la sesión del usuario, incluida la ventana de inicio de sesión de xdm, pueden verse afectados al establecer recursos en el archivo Xresources.

Para los terminales X que no ofrecen un menú de hosts del cual obtener gestión de pantallas, xdm puede recopilar hosts dispuestos y ejecutar el programa chooser para ofrecer al usuario un menú. Para las pantallas X conectadas a un host, este paso generalmente no se usa, ya que el host local realiza la gestión de pantallas.

Después de reiniciar el servidor X, xdm ejecuta el script Xsetup para ayudar a configurar la pantalla que ve el usuario junto con el widget xlogin.

El widget xlogin, que presenta xdm, ofrece las familiares solicitudes de inicio de sesión y contraseña.

Después de que el usuario inicia sesión, xdm ejecuta el script Xstartup como root.

Luego xdm ejecuta el script Xsession como el usuario. Este archivo de sesión del sistema puede realizar algunas inicializaciones adicionales y típicamente ejecuta el script .xsession en el directorio principal del usuario. Cuando el script Xsession sale, la sesión termina.

Al final de la sesión, se ejecuta el script Xreset para limpiar, se reinicia el servidor X y el ciclo vuelve a comenzar.

El archivo /var/log/xdm.log contendrá mensajes de error de xdm y todo lo enviado a stderr por Xsetup, Xstartup, Xsession o Xreset. Cuando tenga problemas para que xdm funcione, verifique este archivo para ver si xdm tiene alguna pista sobre el problema.

OPCIONES

Todas estas opciones, excepto -config, especifican valores que también pueden especificarse en el archivo de configuración como recursos.

-config archivo_configuracion
Nombra el archivo de configuración, que especifica los recursos para controlar el comportamiento de xdm. /etc/X11/xdm/xdm-config es el predeterminado. Consulte la sección Archivo de Configuración.
-nodaemon
Especifica "false" como valor para el recurso DisplayManager.daemonMode. Esto suprime el comportamiento normal de demonio, que consiste en que xdm cierre todos los descriptores de archivo, se desvincule de la terminal de control y se ponga en segundo plano cuando se inicia.
-debug nivel_debug
Especifica el valor numérico para el recurso DisplayManager.debugLevel. Un valor distinto de cero hace que xdm imprima muchos mensajes de depuración en la terminal; también deshabilita el recurso DisplayManager.daemonMode, obligando a xdm a ejecutarse sincrónicamente. Para interpretar estos mensajes de depuración, es casi indispensable tener una copia del código fuente de xdm. No se ha intentado racionalizar ni estandarizar la salida.
-error archivo_log_errores
Especifica el valor para el recurso DisplayManager.errorLogFile. Este archivo contiene errores de xdm, así como cualquier cosa escrita en stderr por los diversos scripts y programas ejecutados durante el progreso de la sesión.
-resources archivo_recursos
Especifica el valor para el recurso DisplayManager*resources. Este archivo se carga utilizando xrdb(1) para especificar los parámetros de configuración para el widget de autenticación.
-server entrada_servidor
Especifica el valor para el recurso DisplayManager.servers. Consulte la sección Especificación del Servidor Local para una descripción de este recurso.
-udpPort numero_puerto
Especifica el valor para el recurso DisplayManager.requestPort. Esto establece el número de puerto que xdm supervisará para las solicitudes XDMCP. Si se establece en 0, xdm no escuchará las solicitudes XDMCP o Chooser. Dado que XDMCP utiliza el puerto UDP bien conocido y registrado 177, este recurso no debe cambiarse a un valor distinto de 0, excepto para depuración.
-session programa_sesion
Especifica el valor para el recurso DisplayManager*session. Indica el programa a ejecutar como sesión después de que el usuario haya iniciado sesión.
-xrm especificacion_recurso
Permite especificar un recurso arbitrario, como en la mayoría de las aplicaciones X Toolkit.

RECURSOS

En muchas etapas, las acciones de xdm se pueden controlar mediante el uso de su archivo de configuración, que está en el formato de recursos X. Algunos recursos modifican el comportamiento de xdm en todas las pantallas, mientras que otros modifican su comportamiento en una pantalla específica. Donde las acciones se relacionan con una pantalla específica, el nombre de la pantalla se inserta en el nombre del recurso entre "DisplayManager" y el segmento final del nombre del recurso.

Para las pantallas locales, el nombre y la clase del recurso son tal como se leen del archivo Xservers.

Para las pantallas remotas, el nombre del recurso es lo que la dirección de red de la pantalla resuelve. Consulte el recurso removeDomain. El nombre debe coincidir exactamente; xdm no es aw

Dado que el administrador de recursos utiliza dos puntos para separar el nombre del recurso de su valor y puntos para separar las partes del nombre del recurso, xdm sustituye guiones bajos tanto por puntos como por dos puntos al generar el nombre del recurso. Por ejemplo, DisplayManager.expo_x_org_0.startup es el nombre del recurso que define el archivo de shell de inicio para la pantalla ``expo.x.org:0''.

DisplayManager.servers
Este recurso especifica un nombre de archivo lleno de entradas de servidor, una por línea (si el valor comienza con una barra inclinada), o una única entrada de servidor. Consulte la sección Especificación de Servidor Local para obtener detalles.
DisplayManager.requestPort
Esto indica el número de puerto UDP que xdm utiliza para escuchar las solicitudes XDMCP entrantes. A menos que necesite depurar el sistema, deje este valor con su valor predeterminado de 177.
DisplayManager.errorLogFile
La salida de error normalmente se dirige a la consola del sistema. Para redirigirla, establezca este recurso a un nombre de archivo. Se debería desarrollar un método para enviar estos mensajes a syslog para los sistemas que lo admitan; sin embargo, la gran variedad de interfaces impide cualquier implementación independiente del sistema. Este archivo también contiene cualquier salida dirigida a stderr por los archivos Xsetup, Xstartup, Xsession y Xreset, por lo que contendrá descripciones de problemas en esos scripts también.
DisplayManager.debugLevel
Si el valor entero de este recurso es mayor que cero, se imprimirán grandes cantidades de información de depuración. También deshabilita el modo demonio, lo que redirigiría la información al "agujero negro", y permite que usuarios no root ejecuten xdm, lo cual normalmente no sería útil.
DisplayManager.daemonMode
Normalmente, xdm intenta convertirse en un proceso demonio sin asociarse a ninguna terminal. Esto se logra haciendo fork y dejando que el proceso padre salga, luego cerrando los descriptores de archivo y liberando la terminal de control. En algunos entornos, esto no se desea (en particular, al depurar). Establecer este recurso a ``false'' deshabilitará esta función.
DisplayManager.pidFile
El nombre de archivo especificado se creará para contener una representación ASCII del ID de proceso del proceso principal de xdm. Xdm también utiliza el bloqueo de archivos en este archivo para intentar eliminar la ejecución de múltiples demonios en la misma máquina, lo que causaría bastantes estragos.
DisplayManager.lockPidFile
Este es el recurso que controla si xdm utiliza el bloqueo de archivos para evitar que múltiples administradores de pantalla se salgan de control. En System V, esto utiliza la llamada a la biblioteca lockf, mientras que en BSD utiliza flock.
DisplayManager.authDir
Esto nombra un directorio bajo el cual xdm almacena los archivos de autorización al inicializar la sesión. El valor predeterminado es /var/lib/xdm. Se puede anular para pantallas específicas por DisplayManager.DISPLAY.authFile.
DisplayManager.autoRescan
Este booleano controla si xdm vuelve a escanear los archivos de configuración, servidores, control de acceso y claves de autenticación después de que una sesión termina y los archivos han cambiado. Por defecto es ``true''. Puede forzar a xdm a releer estos archivos enviando una señal SIGHUP al proceso principal.
DisplayManager.removeDomainname
Al calcular el nombre de la pantalla para los clientes XDMCP, el resolutor de nombres típicamente creará un nombre de host completamente calificado para la terminal. Como esto a veces es confuso, xdm eliminará la porción del nombre de dominio del nombre del host si es el mismo que el nombre de dominio del host local cuando esta variable está configurada. Por defecto, el valor es ``true''.
DisplayManager.keyFile
La autenticación XDMCP de estilo XDM-AUTHENTICATION-1 requiere que una clave privada se comparta entre xdm y la terminal. Este recurso especifica el archivo que contiene esos valores. Cada entrada en el archivo consiste en un nombre de pantalla y la clave compartida.
DisplayManager.accessFile
Para evitar el servicio XDMCP no autorizado y permitir el reenvío de solicitudes XDMCP IndirectQuery, este archivo contiene una base de datos de nombres de host que tienen acceso directo permitido a esta máquina, o tienen una lista de hosts a los que se deben reenviar las consultas. El formato de este archivo se describe en la sección Control de Acceso XDMCP.
DisplayManager.exportList
Una lista de variables de entorno adicionales, separadas por espacios en blanco, para pasar a los programas Xsetup, Xstartup, Xsession y Xreset.
DisplayManager.randomDevice
Un archivo del que se leerán 8 bytes para generar la semilla de las claves de autorización. El valor predeterminado es /dev/urandom . Si este archivo no se puede leer, o si una lectura se bloquea durante más de 5 segundos, xdm recurre a usar una suma de verificación de DisplayManager.randomFile para generar la semilla.
DisplayManager.greeterLib
En sistemas que admiten una biblioteca de saludo de carga dinámica, el nombre de la biblioteca. El valor predeterminado es /usr/lib/X11/xdm/libXdmGreet.so.
DisplayManager.choiceTimeout
Número de segundos a esperar a que la pantalla responda después de que el usuario haya seleccionado un host del selector. Si la pantalla envía una XDMCP IndirectQuery dentro de este tiempo, la solicitud se reenvía al host elegido. De lo contrario, se asume que es de una nueva sesión y se vuelve a ofrecer el selector. El valor predeterminado es 15.
DisplayManager.sourceAddress
Utiliza la dirección IP numérica de la conexión entrante en hosts multihome en lugar del nombre del host. Esto es para evitar intentar conectarse en la interfaz incorrecta que podría estar inactiva en este momento.
DisplayManager.willing
Esto especifica un programa que se ejecuta (como root) cuando se recibe una XDMCP BroadcastQuery y este host está configurado para ofrecer administración de pantalla XDMCP. La salida de este programa puede mostrarse en una ventana del selector. Si no se especifica ningún programa, se envía la cadena Willing to manage.
DisplayManager.DISPLAY.resources
Este recurso especifica el nombre del archivo que será cargado por xrdb como la base de datos de recursos en la ventana raíz de la pantalla 0 de la pantalla. El programa Xsetup, el widget de Inicio de sesión y chooser utilizarán los recursos configurados en este archivo. Esta base de datos de recursos se carga justo antes de que comience el procedimiento de autenticación, por lo que puede controlar la apariencia de la ventana de inicio de sesión. Consulte la sección Widget de Autenticación, que describe los diversos recursos que son apropiados para colocar en este archivo. No hay valor predeterminado para este recurso, pero /etc/X11/xdm/Xresources es el nombre convencional.
DisplayManager.DISPLAY.chooser
Especifica el programa que se ejecuta para ofrecer un menú de hosts para consultas indirectas redirigidas al nombre de host especial CHOOSER. /usr/lib/X11/xdm/chooser es el valor predeterminado. Consulte las secciones Control de Acceso XDMCP y Chooser.
DisplayManager.DISPLAY.xrdb
Especifica el programa utilizado para cargar los recursos. Por defecto, xdm utiliza /usr/bin/xrdb.
DisplayManager.DISPLAY.setup
Esto especifica un programa que se ejecuta (como root) antes de ofrecer la ventana de Inicio de sesión. Esto puede usarse para cambiar la apariencia de la pantalla alrededor de la ventana de Inicio de sesión o para mostrar otras ventanas (por ejemplo, puede desear ejecutar xconsole aquí). Por defecto, no se ejecuta ningún programa. El nombre convencional para un archivo utilizado aquí es Xsetup. Consulte la sección Programa de Configuración.
DisplayManager.DISPLAY.startup
Esto especifica un programa que se ejecuta (como root) después de que el proceso de autenticación tiene éxito. Por defecto, no se ejecuta ningún programa. El nombre convencional para un archivo utilizado aquí es Xstartup. Consulte la sección Programa de Inicio.
DisplayManager.DISPLAY.session
Esto especifica la sesión que se ejecutará (no se ejecuta como root). Por defecto, se ejecuta /usr/bin/xterm. El nombre convencional es Xsession. Consulte la sección Programa de Sesión.
DisplayManager.DISPLAY.reset
Esto especifica un programa que se ejecuta (como root) después de que la sesión termina. Por defecto, no se ejecuta ningún programa. El nombre convencional es Xreset. Consulte la sección Programa de Restablecimiento.
DisplayManager.DISPLAY.openDelay
DisplayManager.DISPLAY.openRepeat
DisplayManager.DISPLAY.openTimeout
DisplayManager.DISPLAY /i>.startAttempts
DisplayManager.DISPLAY.reservAttempts
Estos recursos numéricos controlan el comportamiento de xdm al intentar abrir servidores intransigentes. openDelay es la duración de la pausa en segundos entre intentos sucesivos, openRepeat es el número de intentos a realizar, openTimeout es el tiempo que se espera mientras se intenta abrir (es decir, el tiempo máximo empleado en la llamada al sistema connect(2)) y startAttempts es el número de veces que todo este proceso se realiza antes de renunciar al servidor. Después de haber realizado openRepeat intentos, o si transcurren openTimeout segundos en cualquier intento particular, xdm termina y reinicia el servidor, intentando conectarse de nuevo. Este proceso se repite startAttempts veces, momento en el cual la pantalla se declara muerta y deshabilitada. Aunque este comportamiento pueda parecer arbitrario, ha sido desarrollado empíricamente y funciona bastante bien en la mayoría de los sistemas. El límite reservAttempts es el número de veces que se permite que una conexión exitosa sea seguida por un error fatal. Cuando se alcanza, la pantalla se deshabilita. Los valores predeterminados son openDelay: 15, openRepeat: 5, openTimeout: 120, startAttempts: 4 y reservAttempts: 2.
DisplayManager.DISPLAY.pingInterval
DisplayManager.DISPLAY.pingTimeout
Para descubrir cuándo desaparecen las pantallas remotas, xdm las pingea ocasionalmente, utilizando una conexión X y llamadas XSync. pingInterval especifica el tiempo (en minutos) entre cada intento de ping, pingTimeout especifica el tiempo máximo (en minutos) a esperar a que el terminal responda a la solicitud. Si el terminal no responde, la sesión se declara muerta y se termina. Por defecto, ambos se establecen en 5 minutos. Si utiliza frecuentemente terminales X que pueden aislarse del host que las gestiona, es posible que desee aumentar este valor. La única preocupación es que las sesiones continuarán existiendo después de que el terminal haya sido deshabilitado accidentalmente. xdm no hará ping a las pantallas locales. Aunque parecería inofensivo, es desagradable cuando la sesión de la estación de trabajo se termina como resultado de que el servidor se cuelga por el servicio NFS y no responde al ping.
DisplayManager.DISPLAY.terminateServer
Este recurso booleano especifica si el servidor X debe ser terminado cuando una sesión termina (en lugar de reiniciarlo). Esta opción se puede utilizar cuando el servidor tiende a crecer sin límites con el tiempo, para limitar la cantidad de tiempo que se ejecuta el servidor. El valor predeterminado es ``false''.
DisplayManager.DISPLAY.userPath
Xdm establece la variable de entorno PATH para la sesión a este valor. Debe ser una lista de directorios separados por dos puntos; consulte sh(1) para una descripción completa. El valor predeterminado es ``/usr/local/bin:/usr/bin:/bin''.
DisplayManager.DISPLAY.systemPath
Xdm establece la variable de entorno PATH para los scripts de inicio y restablecimiento al valor de este recurso. El valor predeterminado para este recurso es ``/usr/local/bin:/usr/bin:/bin''. Tenga en cuenta la ausencia de ''.'' en esta entrada. Es una buena práctica para root; evita muchos esquemas comunes de penetración de sistemas de caballo de Troya.
DisplayManager.DISPLAY.systemShell
Xdm establece la variable de entorno SHELL para los scripts de inicio y restablecimiento al valor de este recurso. Es /bin/sh por defecto.
DisplayManager.DISPLAY.failsafeClient
Si la sesión predeterminada no se puede ejecutar, xdm recurrirá a este programa. Este programa se ejecuta sin argumentos, pero se ejecuta utilizando las mismas variables de entorno que tendría la sesión (consulte la sección Programa de Sesión). Por defecto, se utiliza /usr/bin/xterm.
DisplayManager.DISPLAY.grabServer
DisplayManager.DISPLAY.grabTimeout
Para mejorar la seguridad, xdm agarra el servidor y el teclado mientras lee el nombre de usuario y la contraseña. El recurso grabServer especifica si el servidor debe mantenerse durante la lectura del nombre/contraseña. Cuando es ``false'', el servidor se libera después de que la captura del teclado tenga éxito, de lo contrario, el servidor se captura hasta justo antes de que comience la sesión. El valor predeterminado es ``false''. El recurso grabTimeout especifica el tiempo máximo que xdm esperará a que la captura tenga éxito. La captura puede fallar si otro cliente tiene el servidor capturado, o posiblemente si las latencias de red son muy altas. Este recurso tiene un valor predeterminado de 3 segundos; debe tener cuidado al aumentarlo, ya que un usuario puede ser suplantado por una ventana de aspecto similar en la pantalla. Si la captura falla, xdm mata y reinicia el servidor (si es posible) y la sesión.
DisplayManager.DISPLAY.authorize
DisplayManager.DISPLAY.authName
authorize es un recurso booleano que controla si xdm genera y utiliza autorización para las conexiones de servidor locales. Si se utiliza autorización, authName es una lista de mecanismos de autorización a utilizar, separados por espacios en blanco. Las conexiones XDMCP especifican dinámicamente qué mecanismos de autorización se admiten, por lo que authName se ignora en este caso. Cuando authorize se establece para una pantalla y la autorización no está disponible, se informa al usuario mostrando un mensaje diferente en el widget de inicio de sesión. Por defecto, authorize es ``true'', authName es ``MIT-MAGIC-COOKIE-1'', o, si XDM-AUTHORIZATION-1 está disponible, ``XDM-AUTHORIZATION-1 MIT-MAGIC-COOKIE-1.''
DisplayManager.DISPLAY.authFile
Este archivo se utiliza para comunicar los datos de autorización de xdm al servidor, utilizando la opción de línea de comandos del servidor -auth. Debe mantenerse en un directorio que no sea escribible por todos, ya que podría eliminarse fácilmente, deshabilitando el mecanismo de autorización en el servidor. Si no se especifica, se genera un nombre a partir de DisplayManager.authDir y el nombre de la pantalla.
DisplayManager.DISPLAY.authComplain
Si se establece en ``false'', deshabilita el uso de unsecureGreeting en la ventana de inicio de sesión. Consulte la sección Widget de Autenticación. El valor predeterminado es ``true''.
DisplayManager.DISPLAY.resetSignal
El número de la señal que xdm envía para restablecer el servidor. Consulte la sección Control del Servidor. El valor predeterminado es 1 (SIGHUP).
DisplayManager.DISPLAY.termSignal
El número de la señal que xdm envía para terminar el servidor. Consulte la sección Control del Servidor. El valor predeterminado es 15 (SIGTERM).
DisplayManager.DISPLAY.resetForAuth
La implementación original de autorización en el servidor de ejemplo releyó el archivo de autorización al reiniciar el servidor, en lugar de al verificar la conexión inicial. Como xdm genera la información de autorización justo antes de conectarse a la pantalla, un servidor antiguo no obtendría información de autorización actualizada. Este recurso hace que xdm envíe SIGHUP al servidor después de configurar el archivo, lo que provoca un reinicio adicional del servidor, durante el cual se leerá la nueva información de autorización. El valor predeterminado es ``false'', que funcionará para todos los servidores MIT.
DisplayManager.DISPLAY.userAuthDir
Cuando xdm no puede escribir en el archivo de autorización de usuario habitual ($HOME/.Xauthority), crea un nombre de archivo único en este directorio y apunta la variable de entorno XAUTHORITY al archivo creado. Utiliza /tmp por defecto.

ARCHIVO DE CONFIGURACIÓN

Primero, se debe configurar el archivo de configuración de xdm. Cree un directorio (generalmente /etc/X11/xdm) para contener todos los archivos relevantes.

Aquí hay un archivo de configuración razonable, que podría llamarse xdm-config:

DisplayManager.servers:         /etc/X11/xdm/Xservers
DisplayManager.errorLogFile:    /var/log/xdm.log
DisplayManager*resources:       /etc/X11/xdm/Xresources
DisplayManager*startup:         /etc/X11/xdm/Xstartup
DisplayManager*session:         /etc/X11/xdm/Xsession
DisplayManager.pidFile:         /var/run/xdm-pid
DisplayManager._0.authorize:    true
DisplayManager*authorize:       false

Tenga en cuenta que este archivo contiene principalmente referencias a otros archivos. Tenga en cuenta también que algunos de los recursos se especifican con ``*'' separando los componentes. Estos recursos se pueden hacer únicos para cada pantalla diferente, reemplazando el ``*'' con el nombre de la pantalla, pero normalmente esto no es muy útil. Consulte la sección Recursos para una discusión completa.

CONTROL DE ACCESO XDMCP

El archivo de base de datos especificado por DisplayManager.accessFile proporciona información que xdm utiliza para controlar el acceso desde pantallas que solicitan servicio XDMCP. Este archivo contiene tres tipos de entradas: entradas que controlan la respuesta a consultas Directas y de Difusión, entradas que controlan la respuesta a consultas Indirectas y definiciones de macros.

El formato de las entradas Directas es simple, ya sea un nombre de host o un patrón, que se distingue de un nombre de host por la inclusió

X(5) System Manager's Manual X(5) NAME Xaccess - XDMCP control file format DESCRIPTION The X Window System Display Manager (xdm) allows the system administrator to control which hosts are allowed to display X applications via the X protocol and which remote hosts X terminals are allowed to connect to. This control is accomplished by reading a text file named Xaccess. Each line in the Xaccess file contains a single entry. Leading and trailing whitespace is ignored. Blank lines are ignored. The '#' character is treated as a comment delimiter; any characters from '#' to the end of the line are ignored. Lines may be continued using '\' followed by a newline. Entries are classified by the first word on the line. Direct A Direct entry specifies a host which is permitted to use XDMCP to request service directly from this display manager. The entry consists of the keyword Direct, followed by a space, followed by a host name or pattern. Broadcast A Broadcast entry specifies a host which is permitted to use XDMCP to send Broadcast queries to this display manager. The entry consists of the keyword Broadcast, followed by a space, followed by a host name or pattern. Indirect An Indirect entry specifies a host which may use XDMCP to request service indirectly. The entry consists of the keyword Indirect, followed by a space, followed by a host name or pattern, followed by a space, followed by a space-separated list of host names or macros. If the list contains the keyword CHOOSER, xdm will run the chooser program to allow the user to select a host. Host Names and Patterns A host name may be a fully qualified domain name, a host name, or an IP address. A pattern may contain the meta characters '*' and '?'. '*' matches any sequence of 0 or more characters, and '?' matches any single character. These meta characters may only be used in host names specified in Broadcast and Indirect entries. When matching a host name or pattern against the host name of the display device, all comparisons are done using network addresses. This means that any name which resolves to the correct network address may be used. For patterns, only canonical host names are used in the comparison; therefore, ensure that you do not attempt to match aliases. Preceding either a host name or a pattern with a '!' character causes hosts which match that entry to be excluded. NOBROADCAST To only respond to Direct queries for a host or pattern, it can be followed by the optional ``NOBROADCAST'' keyword. This can be used to prevent an xdm server from appearing on menus based on Broadcast queries. Indirect entries also contain a host name or pattern, but follow it with a list of host names and/or macros to which indirect queries should be sent. Macro A macro definition contains a macro name and a list of host names and other macros that the macro expands to. To distinguish macros from hostnames, macro names start with a '%' character. Macros may be nested. Indirect entries may also specify to have xdm run chooser to offer a menu of hosts to connect to. See the section CHOOSER. When checking access for a particular display host, each entry is scanned in turn and the first matching entry determines the response. Direct and Broadcast entries are ignored when scanning for an Indirect entry and vice-versa. Blank lines are ignored, '#' is treated as a comment delimiter causing the rest of that line to be ignored, and '\'newline' causes the newline to be ignored, allowing indirect host lists to span multiple lines. Here is an example Xaccess file: # # Xaccess - XDMCP access control file # # # Direct/Broadcast query entries # !xtra.lcs.mit.edu # disallow direct/broadcast service for xtra bambi.ogi.edu # allow access from this particular display *.lcs.mit.edu # allow access from any display in LCS *.deshaw.com NOBROADCAST # allow only direct access *.gw.com # allow direct and broadcast # # Indirect query entries # %HOSTS expo.lcs.mit.edu xenon.lcs.mit.edu \ excess.lcs.mit.edu kanga.lcs.mit.edu extract.lcs.mit.edu xenon.lcs.mit.edu #force extract to contact xenon !xtra.lcs.mit.edu dummy #disallow indirect access *.lcs.mit.edu %HOSTS #all others get to choose If compiled with IPv6 support, multicast address groups may also be included in the list of addresses indirect queries are set to. Multicast addresses may be followed by an optional / character and hop count. If no hop count is specified, the multicast hop count defaults to 1, keeping the packet on the local network. For IPv4 multicasting, the hop count is used as the TTL. Examples: rincewind.sample.net ff02::1 #IPv6 Multicast to ff02::1 #with a hop count of 1 ponder.sample.net CHOOSER 239.192.1.1/16 #Offer a menu of hosts #who respond to IPv4 Multicast #to 239.192.1.1 with a #TTL of 16 CHOOSER For X terminals that do not offer a host menu for use with Broadcast or Indirect queries, the chooser program can do this for them. In the Xaccess file, specify "CHOOSER" as the first entry in the Indirect host list. Chooser will send a Query request to each of the remaining host names in the list and offer a menu of all the hosts that respond. The list may consist of the word "BROADCAST," in which case chooser will send a Broadcast instead, again offering a menu of all hosts that respond. Note that on some operating systems, UDP packets cannot be broadcast, so this feature will not work. Example Xaccess file using chooser: extract.lcs.mit.edu CHOOSER %HOSTS #offer a menu of these hosts xtra.lcs.mit.edu CHOOSER BROADCAST #offer a menu of all hosts The program to use for chooser is specified by the DisplayManager.DISPLAY.chooser resource. For more flexibility at this step, the chooser could be a shell script. Chooser is the session manager here; it is run instead of a child xdm to manage the display. Resources for this program can be put into the file named by DisplayManager.DISPLAY.resources. When the user selects a host, chooser prints the host chosen, which is read by the parent xdm, and exits. xdm closes its connection to the X server, and the server resets and sends another Indirect XDMCP request. xdm remembers the user's choice (for DisplayManager.choiceTimeout seconds) and forwards the request to the chosen host, which starts a session on that display. LISTEN The following configuration directive is also defined for the Xaccess configuration file: LISTEN interface [list of multicast group addresses] interface may be a hostname or IP address representing a network interface on this machine, or the wildcard * to represent all available network interfaces. If one or more LISTEN lines are specified, xdm only listens for XDMCP connections on the specified interfaces. If multicast group addresses are listed on a listen line, xdm joins the multicast groups on the given interface. If no LISTEN lines are given, the original behavior of listening on all interfaces is preserved for backwards compatibility. Additionally, if no LISTEN is specified, xdm joins the default XDMCP IPv6 multicast group, when compiled with IPv6 support. To disable listening for XDMCP connections altogther, a line of LISTEN with no addresses may be specified, or the previously supported method of setting DisplayManager.requestPort to 0 may be used. Examples: LISTEN * ff02::1 # Listen on all interfaces and to the # ff02::1 IPv6 multicast group. LISTEN 10.11.12.13 # Listen only on this interface, as long # as no other listen directives appear in # file. IPv6 MULTICAST ADDRESS SPECIFICATION The Internet Assigned Numbers Authority has has assigned ff0X:0:0:0:0:0:0:12b as the permanently assigned range of multicast addresses for XDMCP. The X in the prefix may be replaced by any valid scope identifier, such as 1 for Interface-Local, 2 for Link-Local, 5 for Site-Local, and so on. (See IETF RFC 4291 or its replacement for further details and scope definitions.) xdm defaults to listening on the Link-Local scope address ff02:0:0:0:0:0:0:12b to most closely match the old IPv4 subnet broadcast behavior. LOCAL SERVER SPECIFICATION The resource DisplayManager.servers gives a server specification or, if the values starts with a slash (/), the name of a file containing server specifications, one per line. Each specification indicates a display which should constantly be managed and which is not using XDMCP. This method is used typically for local servers only. If the resource or the file named by the resource is empty, xdm will offer XDMCP service only. Each specification consists of at least three parts: a display name, a display class, a display type, and (for local servers) a command line to start the server. A typical entry for local display number 0 would be: :0 Digital-QV local /usr/bin/X :0 The display types are: local local display: xdm must run the server foreign remote display: xdm opens an X connection to a running server The display name must be something that can be passed in the -display option to an X program. This string is used to generate the display-specific resource names, so be careful to match the names (e.g., use ":0 Sun-CG3 local /usr/bin/X :0" instead of "localhost:0 Sun-CG3 local /usr/bin/X :0" if your other resources are specified as "DisplayManager._0.session"). The display class portion is also used in the display-specific resources, as the class of the resource. This is useful if you have a large collection of similar displays (such as a corral of X terminals) and would like to set resources for groups of them. When using XDMCP, the display is required to specify the display class, so the manual for your particular X terminal should document the display class string for your device. If it doesn't, you can run xdm in debug mode and look at the resource strings which it generates for that device, which will include the class string. When xdm starts a session, it sets up authorization data for the server. For local servers, xdm passes "-auth filename" on the server's command line to point it at its authorization data. For XDMCP servers, xdm passes the authorization data to the server via the Accept XDMCP request. RESOURCES FILE The Xresources file is loaded onto the display as a resource database using xrdb. As the authentication widget reads this database before starting up, it usually contains parameters for that widget: xlogin*login.translations: #override\ CtrlR: abort-display()\n\ F1: set-session-argument(failsafe) finish-field()\n\ Return: set-session-argument() finish-field() xlogin*borderWidth: 3 xlogin*greeting: CLIENTHOST SEE ALSO xdm(1), X(7) Manual Page October 26, 2023 X(5) XDM Configuration

CONFIGURACIÓN DE XDM

Los archivos de configuración para xdm están en el directorio definido por la variable de entorno XCONFIGDIR, que normalmente es /etc/X11/xdm. Los archivos de recursos se cargan con xrdb(1), por lo que pueden contener las mismas directivas que xrdb(1), como #include, #ifdef, etc. También pueden definir los valores de los recursos para el programa xlogin, el programa de configuración, y el programa de autenticación.

El archivo de recursos para el programa de inicio de sesión se denomina DisplayManager.DISPLAY.resources, donde DISPLAY es el nombre de la pantalla tal como lo conoce xdm. Por ejemplo, si el gestor de pantalla está configurado para manejar las pantallas :0 y :1, los archivos de recursos son /etc/X11/xdm/res.dir/Xresources.0 y /etc/X11/xdm/res.dir/Xresources.1 respectivamente.

#ifdef COLOR
xlogin*greetColor: CadetBlue
xlogin*failColor: red
#endif

Tenga en cuenta la entrada de traducciones; especifica algunas traducciones nuevas para el widget que permiten a los usuarios escapar de la sesión predeterminada (y evitar problemas que puedan ocurrir en ella). Tenga en cuenta que si no se especifica #override, las traducciones predeterminadas se eliminan y se reemplazan por el nuevo valor, lo que no resulta muy útil, ya que algunas de las traducciones predeterminadas son bastante útiles (como ``<Key>: insert-char ()'' que responde a la escritura normal).

Este archivo también puede contener recursos para el programa de configuración y el chooser.

PROGRAMA DE CONFIGURACIÓN

El archivo Xsetup se ejecuta después de que el servidor se reinicia, pero antes de que se ofrezca la ventana de inicio de sesión. El archivo suele ser un script de shell. Se ejecuta como root, por lo que se debe tener cuidado con la seguridad. Este es el lugar para cambiar el fondo de root o mostrar otras ventanas que deban aparecer en la pantalla junto con el widget de inicio de sesión.

Además de los especificados por DisplayManager.exportList, se pasan las siguientes variables de entorno:

DISPLAY el nombre de pantalla asociado
PATH el valor de DisplayManager.DISPLAY.systemPath
SHELL el valor de DisplayManager.DISPLAY.systemShell
XAUTHORITY puede establecerse en un archivo de autoridad

Tenga en cuenta que, dado que xdm captura el teclado, cualquier otra ventana no podrá recibir entrada del teclado. Sin embargo, podrán interactuar con el ratón; tenga cuidado con posibles agujeros de seguridad aquí. Si se establece DisplayManager.DISPLAY.grabServer, Xsetup no podrá conectarse a la pantalla en absoluto. Los recursos para este programa se pueden poner en el archivo denominado por DisplayManager.DISPLAY.resources.

Aquí hay un script Xsetup de ejemplo:

#!/bin/sh
# Xsetup_0 - script de configuración para una estación de trabajo
xcmsdb < /etc/X11/xdm/monitors/alex.0
xconsole -geometry 480x130-0-0 -notify -verbose -exitOnFail &

WIDGET DE AUTENTICACIÓN

El widget de autenticación solicita al usuario el nombre de usuario, la contraseña y/o otros datos de autenticación necesarios desde el teclado. Casi todos los parámetros imaginables se pueden controlar con un recurso. Los recursos para este widget deben colocarse en el archivo denominado por DisplayManager.DISPLAY.resources. Todos estos tienen valores predeterminados razonables, por lo que no es necesario especificar ninguno de ellos.

El archivo de recursos se carga con xrdb(1), por lo que puede utilizar las sustituciones definidas por ese programa, como CLIENTHOST para el nombre de host del cliente en el mensaje de inicio de sesión, o las directivas #ifdef del preprocesador C para producir diferentes pantallas dependiendo de la profundidad de color u otras variables.

Xdm se puede compilar con soporte para la biblioteca Xft(3) para la representación de fuentes. Si este soporte está presente, las caras de fuente se especifican utilizando los recursos con nombres que terminan en ``face'' en el formato de cara fontconfig descrito en la sección Nombres de Fuente de fonts.conf(5). Si no, las fuentes se especifican utilizando los recursos con nombres que terminan en ``font'' en el formato tradicional de X Logical Font Description descrito en la sección Nombres de Fuente de X(7).

PROGRAMA DE REINICIO

Sintético con Xstartup, el script Xreset se ejecuta después de que la sesión del usuario ha terminado. Ejecutado como root, debería contener comandos que deshacen los efectos de los comandos en Xstartup, actualizando entradas en los archivos utmp o wtmp, o desmontando directorios de servidores de archivos. Las variables de entorno que se pasaron a Xstartup también se pasan a Xreset.

Un script Xreset de ejemplo:

#!/bin/sh
#
# Xreset
#
# Este programa se ejecuta como root después de que termina la sesión
#
sessreg -d -l $DISPLAY -x /etc/X11/xdm/Xservers $LOGNAME
/etc/X11/xdm/TakeConsole
exit 0

CONTROL DEL SERVIDOR

Xdm controla los servidores locales usando señales POSIX. Se espera que SIGHUP reinicie el servidor, cerrando todas las conexiones de clientes y realizando otras tareas de limpieza. Se espera que SIGTERM termine el servidor. Si estas señales no realizan las acciones esperadas, los recursos DisplayManager.DISPLAY.resetSignal y DisplayManager.DISPLAY.termSignal pueden especificar señales alternativas.

Para controlar terminales remotas que no usan XDMCP, xdm busca en la jerarquía de ventanas de la pantalla y utiliza la solicitud de protocolo KillClient en un intento de limpiar la terminal para la próxima sesión. Esto puede no matar a todos los clientes, ya que solo se notarán aquellos que hayan creado ventanas. XDMCP proporciona un mecanismo más seguro; cuando xdm cierra su conexión inicial, la sesión ha terminado y la terminal debe cerrar todas las demás conexiones.

CONTROL DE XDM

Xdm responde a dos señales: SIGHUP y SIGTERM. Cuando se le envía un SIGHUP, xdm relee el archivo de configuración, el archivo de control de acceso y el archivo de servidores. Para el archivo de servidores, nota si se han agregado o eliminado entradas. Si se ha agregado una nueva entrada, xdm inicia una sesión en la pantalla asociada. Las entradas que se han eliminado se deshabilitan inmediatamente, lo que significa que cualquier sesión en curso se terminará sin previo aviso y no se iniciará ninguna sesión nueva.

Cuando se le envía un SIGTERM, xdm termina todas las sesiones en curso y sale. Esto se puede usar al apagar el sistema.

Xdm intenta marcar sus diversos subprocesos para ps(1) editando la lista de argumentos de la línea de comandos en su lugar. Debido a que xdm no puede asignar espacio adicional para esta tarea, es útil iniciar xdm con una línea de comandos razonablemente larga (usar el nombre completo de la ruta debería ser suficiente). Cada proceso que está atendiendo una pantalla se marca como -pantalla.

PANTALLAS LOCALES ADICIONALES

Para agregar una pantalla local adicional, agréguele una línea en el archivo Xservers. (Ver la sección Especificación de Servidor Local.)

Examine los recursos específicos de la pantalla en xdm-config (por ejemplo, DisplayManager._0.authorize) y considere cuáles de ellos deberían copiarse para la nueva pantalla. El xdm-config predeterminado tiene todas las líneas apropiadas para las pantallas :0 y :1.

OTRAS POSIBILIDADES

Puede usar xdm para ejecutar una sola sesión a la vez, utilizando las opciones de init de 4.3 o un daemon adecuado especificando el servidor en la línea de comandos:

xdm -server “:0 SUN-3/60CG4 local /usr/bin/X :0”

O, podría tener un servidor de archivos y una colección de terminales X. La configuración para esto es idéntica a la del ejemplo anterior, excepto que el archivo Xservers se vería así

extol:0 VISUAL-19 foreign
exalt:0 NCD-19 foreign
explode:0 NCR-TOWERVIEW3000 foreign

Esto dirige a xdm a administrar sesiones en las tres terminales. Consulte la sección Control de Xdm para obtener una descripción del uso de señales para habilitar y deshabilitar estas terminales de una manera que recuerda a init(8).

LIMITACIONES

Una cosa en la que xdm no es muy bueno es coexistir con otros sistemas de ventanas. Para usar múltiples sistemas de ventanas en el mismo hardware, probablemente estará más interesado en xinit.
