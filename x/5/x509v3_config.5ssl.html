NOMBRE

x509v3_config - Formato de configuración de extensiones de certificados X509 V3

DESCRIPCIÓN

Varios comandos de OpenSSL pueden añadir extensiones a un certificado o solicitud de certificado basándose en el contenido de un archivo de configuración y opciones de línea de comandos como -addext. La sintaxis de los archivos de configuración se describe en config(5). Los comandos típicamente tienen una opción para especificar el nombre del archivo de configuración y una sección dentro de ese archivo; vea la documentación del comando individual para más detalles.

Esta página usa extensions como el nombre de la sección, cuando sea necesario en los ejemplos.

Cada entrada en la sección de extensiones toma la forma:

nombre = [crítica, ]valor(es)

Si está presente crítica, entonces la extensión se marcará como crítica.

Si se procesan múltiples entradas para el mismo nombre de extensión, las entradas posteriores anulan a las anteriores con el mismo nombre.

El formato de los valores depende del valor de nombre, muchos tienen una correspondencia tipo-valor donde el tipo y el valor están separados por dos puntos. Hay cuatro tipos principales de extensión:

cadena
multivalor
raw
arbitrario

Cada uno se describe en los siguientes párrafos.

Las extensiones de cadena simplemente tienen una cadena que contiene el valor en sí o cómo se obtiene.

Las extensiones multivalor tienen una forma corta y una forma larga. La forma corta es una lista separada por comas de nombres y valores:

basicConstraints = critical, CA:true, pathlen:1

La forma larga permite que los valores se coloquen en una sección separada:

[extensiones]
basicConstraints = critical, @basic_constraints
[basic_constraints]
CA = true
pathlen = 1

Ambas formas son equivalentes.

Si una extensión es multivalor y un valor de campo debe contener una coma, se debe usar la forma larga, de lo contrario la coma se malinterpretaría como un separador de campos. Por ejemplo:

subjectAltName = URI:ldap://somehost.com/CN=foo,OU=bar

generará un error, pero la forma equivalente:

[extensiones]
subjectAltName = @subject_alt_section
[subject_alt_section]
subjectAltName = URI:ldap://somehost.com/CN=foo,OU=bar

es válida.

OpenSSL no soporta múltiples ocurrencias del mismo campo dentro de una sección. En este ejemplo:

[extensiones]
subjectAltName = @alt_section
[alt_section]
email = steve@example.com
email = steve@example.org

solo reconocerá el último valor. Para especificar múltiples valores, añada un identificador numérico, como se muestra aquí:

[extensiones]
subjectAltName = @alt_section
[alt_section]
email.1 = steve@example.com
email.2 = steve@example.org

La sintaxis de las extensiones raw está definida por el código fuente que analiza la extensión, pero debería estar documentada. Vea "Políticas de Certificados" para un ejemplo de extensión raw.

Si un tipo de extensión no es compatible, entonces se debe usar la sintaxis de extensión *arbitraria*, vea la sección "EXTENSIONES ARBITRARIAS" para más detalles.

EXTENSIONES ESTÁNDAR

Las siguientes secciones describen la sintaxis de cada extensión soportada. No definen la semántica de la extensión.

Restricciones Básicas

Esta es una extensión multivalor que indica si un certificado es un certificado CA. El primer valor es CA seguido de TRUE o FALSE. Si CA es TRUE, entonces se puede incluir un nombre opcional pathlen seguido de un valor no negativo.

Por ejemplo:

basicConstraints = CA:TRUE
basicConstraints = CA:FALSE
basicConstraints = critical, CA:TRUE, pathlen:1

Un certificado CA *debe* incluir el nombre basicConstraints con el parámetro CA establecido a TRUE. Un certificado de entidad final debe tener CA:FALSE u omitir la extensión por completo. El parámetro pathlen especifica el número máximo de CAs que pueden aparecer debajo de esta en una cadena. Un pathlen de cero significa que la CA no puede firmar ninguna sub-CA, y solo puede firmar certificados de entidad final.

Uso de Clave

El uso de clave es una extensión multivalor que consiste en una lista de nombres de los usos de clave permitidos. Los valores definidos son: "digitalSignature", "nonRepudiation" (con un nombre alternativo "contentCommitment"), "keyEncipherment", "dataEncipherment", "keyAgreement", "keyCertSign", "cRLSign", "encipherOnly" y "decipherOnly".

Ejemplos:

keyUsage = digitalSignature, nonRepudiation
keyUsage = digitalSignature, contentCommitment
keyUsage = critical, keyCertSign

Uso de Clave Extendido

Esta extensión consiste en una lista de valores que indican los propósitos para los que se puede utilizar la clave pública del certificado. Cada valor puede ser un nombre de texto corto o un OID. Los siguientes nombres de texto, y su significado previsto, son conocidos:

Valor                  Significado según RFC 5280, etc.
-----                  ----------------------------------
serverAuth             Autenticación de Servidor WWW SSL/TLS
clientAuth             Autenticación de Cliente WWW SSL/TLS
codeSigning            Firma de Código
emailProtection        Protección de Correo Electrónico (S/MIME)
timeStamping           Sellado de Tiempo Confiable
OCSPSigning            Firma OCSP
ipsecIKE               Intercambio de Claves IPsec (IPsec)
msCodeInd              Firma de Código Individual de Microsoft (authenticode)
msCodeCom              Firma de Código Comercial de Microsoft (authenticode)
msCTLSign              Firma de Lista de Confianza de Microsoft
msEFS                  Sistema de Archivos Encriptados de Microsoft

Mientras que el RFC 5280 de la IETF dice que id-kp-serverAuth y id-kp-clientAuth son solo para uso WWW, en la práctica se usan para todo tipo de clientes y servidores TLS, y esto es lo que OpenSSL asume también.

Ejemplos:

extendedKeyUsage = critical, codeSigning, 1.2.3.4
extendedKeyUsage = serverAuth, clientAuth

Identificador de Clave de Sujeto

La especificación de la extensión SKID tiene un valor con tres opciones.

ninguno
No se incluirá ninguna extensión SKID.
hash
Se sigue el proceso especificado en la sección 4.2.1.2. (1) del RFC 5280: el identificador de clave se compone del hash SHA-1 de 160 bits del valor de la cadena de bits subjectPublicKey (excluyendo la etiqueta, la longitud y el número de bits no utilizados).
Una cadena hexadecimal (posiblemente con ":" separando bytes)
El valor proporcionado se muestra directamente. Esta opción está fuertemente desaconsejada.

Por defecto, las aplicaciones x509, req y ca se comportan como si se hubiera dado hash.

Ejemplo:

subjectKeyIdentifier = hash

Identificador de Clave de Autoridad

La especificación de la extensión AKID puede tener el valor none indicando que no se incluirá ningún AKID. De lo contrario, puede tener el valor keyid o issuer o ambos, separados por ",". Cualquiera o ambos pueden tener la opción always, indicada al poner dos puntos ":" entre el valor y esta opción. Para certificados autofirmados, el AKID se suprime a menos que esté presente always.

Por defecto, las aplicaciones x509, req y ca se comportan como si se diera none para certificados autofirmados y keyid"," issuer en caso contrario.

Si keyid está presente, se intenta copiar el identificador de clave del sujeto (SKID) del certificado emisor, excepto si el certificado emisor es el mismo que el actual y no está autofirmado. El hash de la clave pública relacionada con la clave de firma se toma como respaldo si el certificado emisor es el mismo que el certificado actual. Si always está presente pero no se puede obtener ningún valor, se devuelve un error.

Authority Key Identifier

This extension provides a means of identifying the public key associated with the private key used to sign a certificate. It can be specified in several ways.

The keyid option uses the SHA1 hash of the public key of the issuer as the key identifier. If the SHA1 hash is not available, an error is returned.

The issuer option specifies that the issuer DN and serial number should be used as the key identifier. This is typically used when the issuer certificate is available.

The url option specifies a URL from which the issuer certificate can be retrieved. This is useful when the issuer certificate is not readily available.

The digest option allows you to specify a different digest algorithm to be used for calculating the key identifier. The default is SHA1.

If issuer is present, and in addition it has the option always specified or keyid is not present, then the issuer DN and serial number are copied from the issuer certificate. If this fails, an error is returned.

Examples:

authorityKeyIdentifier = keyid, issuer
authorityKeyIdentifier = keyid, issuer:always

Subject Alternative Name

This is a multi-valued extension that supports several types of name identifier, including email (an email address), URI (a uniform resource indicator), DNS (a DNS domain name), RID (a registered ID: OBJECT IDENTIFIER), IP (an IP address), dirName (a distinguished name), and otherName. The syntax of each is described in the following paragraphs.

The email option has two special values. "copy" will automatically include any email addresses contained in the certificate subject name in the extension. "move" will automatically move any email addresses from the certificate subject name to the extension.

The IP address used in the IP option can be in either IPv4 or IPv6 format.

The value of dirName is specifies the configuration section containing the distinguished name to use, as a set of name-value pairs. Multi-valued AVAs can be formed by prefacing the name with a + character.

The value of otherName can include arbitrary data associated with an OID; the value should be the OID followed by a semicolon and the content in specified using the syntax in ASN1_generate_nconf(3).

Examples:

subjectAltName = email:copy, email:my@example.com, URI:http://my.example.com/
subjectAltName = IP:192.168.7.1
subjectAltName = IP:13::17
subjectAltName = email:my@example.com, RID:1.2.3.4
subjectAltName = otherName:1.2.3.4;UTF8:some other identifier
[extensions]
subjectAltName = dirName:dir_sect
[dir_sect]
C = UK
O = My Organization
OU = My Unit
CN = My Name

Non-ASCII Email Address conforming the syntax defined in Section 3.3 of RFC 6531 are provided as otherName.SmtpUTF8Mailbox. According to RFC 8398, the email address should be provided as UTF8String. To enforce the valid representation in the certificate, the SmtpUTF8Mailbox should be provided as follows

subjectAltName=@alts
[alts]
otherName = 1.3.6.1.5.5.7.8.9;FORMAT:UTF8,UTF8String:nonasciiname.example.com

Issuer Alternative Name

This extension supports most of the options of subject alternative name; it does not support email:copy. It also adds issuer:copy as an allowed value, which copies any subject alternative names from the issuer certificate, if possible.

Example:

issuerAltName = issuer:copy

Authority Info Access

This extension gives details about how to retrieve information that related to the certificate that the CA makes available. The syntax is access_id;location, where access_id is an object identifier (although only a few values are well-known) and location has the same syntax as subject alternative name (except that email:copy is not supported).

Possible values for access_id include OCSP (OCSP responder), caIssuers (CA Issuers), ad_timestamping (AD Time Stamping), AD_DVCS (ad dvcs), caRepository (CA Repository).

Examples:

authorityInfoAccess = OCSP;URI:http://ocsp.example.com/,caIssuers;URI:http://myca.example.com/ca.cer
authorityInfoAccess = OCSP;URI:http://ocsp.example.com/

CRL distribution points

This is a multi-valued extension whose values can be either a name-value pair using the same form as subject alternative name or a single value specifying the section name containing all the distribution point values.

When a name-value pair is used, a DistributionPoint extension will be set with the given value as the fullName field as the distributionPoint value, and the reasons and cRLIssuer fields will be omitted.

When a single option is used, the value specifies the section, and that section can have the following items:

fullname
The full name of the distribution point, in the same format as the subject alternative name.
relativename
The value is taken as a distinguished name fragment that is set as the value of the nameRelativeToCRLIssuer field.
CRLIssuer
The value must in the same format as the subject alternative name.
reasons
A multi-value field that contains the reasons for revocation. The recognized values are: "keyCompromise", "CACompromise", "affiliationChanged", "superseded", "cessationOfOperation", "certificateHold", "privilegeWithdrawn", and "AACompromise".

Only one of fullname or relativename should be specified.

Simple examples:

crlDistributionPoints = URI:http://example.com/myca.crl
crlDistributionPoints = URI:http://example.com/myca.crl, URI:http://example.org/my.crl

Full distribution point example:

[extensions]
crlDistributionPoints = crldp1_section
[crldp1_section]
fullname = URI:http://example.com/myca.crl
CRLissuer = dirName:issuer_sect
reasons = keyCompromise, CACompromise
[issuer_sect]
C = UK
O = Organisation
CN = Some Name

Issuing Distribution Point

This extension should only appear in CRLs. It is a multi-valued extension whose syntax is similar to the "section" pointed to by the CRL distribution points extension. The following names have meaning:

fullname
The full name of the distribution point, in the same format as the subject alternative name.
relativename
The value is taken as a distinguished name fragment that is set as the value of the nameRelativeToCRLIssuer field.
onlysomereasons
A multi-value field that contains the reasons for revocation. The recognized values are: "keyCompromise", "CACompromise", "affiliationChanged", "superseded", "cessationOfOperation", "certificateHold", "privilegeWithdrawn", and "AACompromise".
onlyuser, onlyCA, onlyAA, indirectCRL
The value for each of these names is a boolean.

Example:

[extensions]
issuingDistributionPoint = critical, @idp_section
[idp_section]
fullname = URI:http://example.com/myca.crl
indirectCRL = TRUE
onlysomereasons = keyCompromise, CACompromise

Certificate Policies

This is a raw extension that supports all of the defined fields of the certificate extension.

Policies without qualifiers are specified by giving the OID. Multiple policies are comma-separated. For example:

certificatePolicies = 1.2.4.5, 1.1.3.4

To include policy qualifiers, use the "@section" syntax to point to a section that specifies all the information.

The section referred to must include the policy OID using the name policyIdentifier. cPSuri qualifiers can be included using the syntax:

CPS.nnn = value

where "nnn" is a number.

userNotice qualifiers can be set using the syntax:

userNotice.nnn = @notice

The value of the userNotice qualifier is specified in the relevant section. This section can include explicitText, organization, and noticeNumbers options. explicitText and organization are text strings, noticeNumbers is a comma separated list of numbers. The organization and noticeNumbers options (if included) must BOTH be present. Some software might require the ia5org option at the top level; this changes the encoding from Displaytext to IA5String.

Example:

[extensions]
certificatePolicies = ia5org, 1.2.3.4, 1.5.6.7.8, @polsect
[polsect]
policyIdentifier = 1.3.5.8
CPS.1 = "http://my.host.example.com/"
CPS.2 = "http://my.your.example.com/"
userNotice.1 = @notice
[notice]
explicitText = "Explicit Text Here"
organization = "Organisation Name"
noticeNumbers = 1, 2, 3, 4

The character encoding of explicitText can be specified by prefixing the value with UTF8, BMP, or VISIBLE followed by colon. For example:

[notice]
explicitText = "UTF8:Explicit Text Here"

Policy Constraints

This is a multi-valued extension which consisting of the names requireExplicitPolicy or inhibitPolicyMapping and a non negative integer value. At least one component must be present.

Example:

policyConstraints = requireExplicitPolicy:3

Inhibit Any Policy

This is a string extension whose value must be a non negative integer.

Example:

inhibitAnyPolicy = 2

Name Constraints

This is a multi-valued extension. The name should begin with the word permitted or excluded followed by a ;

NAME

x509v3_config - X509 V3 certificate extension configuration file format

DESCRIPTION

The OpenSSL command line utilities like openssl-ca(1), openssl-req(1) and openssl-x509(1) use a configuration file to determine certificate extensions.

Extensions are specified in a configuration file in the following format:

[ <section> ]
<extension_name> = [ critical, ] <extension_value>

The extension name is usually a standard name like basicConstraints or subjectAltName. Some extensions have numerical OIDs associated with them, these can be used instead of the name. The critical flag is optional and indicates that the extension is critical.

The value format depends on the extension.

Supported extensions are listed below.

STANDARD EXTENSIONS

authorityKeyIdentifier

This extension contains a hash of the issuer's public key and an optional serial number. It is used to identify the specific key that was used to sign the certificate. This extension is typically added automatically by openssl-ca(1). A value can be specified using the syntax keyid, issuer or serialissuer.

Example:

authorityKeyIdentifier = issuer

basicConstraints

This extension indicates whether a certificate is a CA certificate or an end-entity certificate. If the certificate is a CA, the CA parameter must be set to true. The optional pathlen parameter restricts the length of the certification path.

Example:

basicConstraints = CA:true, pathlen:0

extendedKeyUsage

This extension specifies the purposes for which the certificate can be used. It consists of a comma-separated list of key usages. Supported values include serverAuth, clientAuth, codeSigning, emailProtection, timeStamping and OCSPSigning.

Example:

extendedKeyUsage = serverAuth, clientAuth

keyUsage

This extension specifies the permitted uses of the public key contained in the certificate. It consists of a comma-separated list of usages. Supported values include digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment, keyAgreement, keyCertSign, cRLSign, encipherOnly and decipherOnly.

Example:

keyUsage = keyCertSign, cRLSign

nameConstraints

This extension is used in CA certificates to constrain the set of names that are permitted or excluded in subsequent certificates. The syntax follows the subjectAltName(5) syntax. The email:copy form is not supported and the IP form should consist of IP addresses and subnet masks separated by a /.

Examples:

nameConstraints = permitted;IP:192.168.0.0/255.255.0.0
nameConstraints = permitted;email:.example.com
nameConstraints = excluded;email:.com

OCSP No Check

This is a string extension. It is parsed, but ignored.

Example:

noCheck = ignored

TLS Feature (aka Must Staple)

This is a multi-valued extension consisting of a list of TLS extension identifiers. Each identifier may be a number (0..65535) or a supported name. When a TLS client sends a listed extension, the TLS server is expected to include that extension in its reply.

The supported names are: status_request and status_request_v2.

Example:

tlsfeature = status_request

DEPRECATED EXTENSIONS

The following extensions are non standard, Netscape specific and largely obsolete. Their use in new applications is discouraged.

Netscape String extensions

Netscape Comment (nsComment) is a string extension containing a comment which will be displayed when the certificate is viewed in some browsers. Other extensions of this type are: nsBaseUrl, nsRevocationUrl, nsCaRevocationUrl, nsRenewalUrl, nsCaPolicyUrl and nsSslServerName.

Netscape Certificate Type

This is a multi-valued extensions which consists of a list of flags to be included. It was used to indicate the purposes for which a certificate could be used. The basicConstraints, keyUsage and extended key usage extensions are now used instead.

Acceptable values for nsCertType are: client, server, email, objsign, reserved, sslCA, emailCA, objCA.

ARBITRARY EXTENSIONS

If an extension is not supported by the OpenSSL code then it must be encoded using the arbitrary extension format. It is also possible to use the arbitrary format for supported extensions. Extreme care should be taken to ensure that the data is formatted correctly for the given extension type.

There are two ways to encode arbitrary extensions.

The first way is to use the word ASN1 followed by the extension content using the same syntax as ASN1_generate_nconf(3). For example:

[extensions]
1.2.3.4 = critical, ASN1:UTF8String:Some random data
1.2.3.4.1 = ASN1:SEQUENCE:seq_sect
[seq_sect]
field1 = UTF8:field1
field2 = UTF8:field2

It is also possible to use the word DER to include the raw encoded data in any extension.

1.2.3.4 = critical, DER:01:02:03:04
1.2.3.4.1 = DER:01020304

The value following DER is a hex dump of the DER encoding of the extension Any extension can be placed in this form to override the default behaviour. For example:

basicConstraints = critical, DER:00:01:02:03

WARNINGS

There is no guarantee that a specific implementation will process a given extension. It may therefore be sometimes possible to use certificates for purposes prohibited by their extensions because a specific application does not recognize or honour the values of the relevant extensions.

The DER and ASN1 options should be used with caution. It is possible to create invalid extensions if they are not used carefully.
