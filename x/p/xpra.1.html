DESCRIPCIÓN

Xpra es una herramienta que permite ejecutar aplicaciones X - normalmente en un host remoto - y luego dirigir su pantalla a tu máquina local, desconectarte de estas aplicaciones y reconectarte desde la misma u otra máquina, todo sin perder ningún estado. Difiere del reenvío X estándar en que permite la desconexión y reconexión sin interrumpir la aplicación reenviada; difiere de VNC y tecnologías de pantalla remota similares en que xpra puede ejecutarse *sin ventana raíz*: es decir, las aplicaciones reenviadas por xpra aparecen en tu escritorio como ventanas normales administradas por tu gestor de ventanas, en lugar de estar todas "atrapadas en una caja juntas". Xpra también utiliza un protocolo personalizado que se auto-ajusta y es relativamente insensible a la latencia, por lo que es utilizable en conexiones de red que son demasiado lentas o poco fiables para el reenvío X estándar. Xpra también se puede utilizar para hacer sombra a una pantalla X11 existente, o en modo de escritorio donde se comporta más como VNC.

Por defecto, el servidor Xpra anuncia las sesiones disponibles (nombre de usuario y número de pantalla) a través de mDNS a la red local. Usa mdns=no para deshabilitarlo.

CADENAS DE CONEXIÓN

Xpra soporta muchos tipos de cadenas de conexión (algunas pueden requerir la instalación de paquetes adicionales):

:PANTALLA[,OPCIONES]

Pantallas locales: esta es la forma más simple y solo es válida para las pantallas locales actuales del usuario actual.

tcp://[[USUARIO][:CONTRASEÑA]@]HOST:PUERTO[/PANTALLA][?OPCIONES]

El modo TCP usa números de puerto y no números de pantalla. Si hay varias pantallas disponibles a través de un solo puerto TCP (por ejemplo, usando un servidor proxy), entonces también se puede especificar el número de pantalla después del número de puerto.

ssl://[[USUARIO][:CONTRASEÑA]@]HOST:PUERTO[/PANTALLA][?OPCIONES]

SSL añade una capa de socket seguro sobre el modo TCP.

vsock://[[USUARIO][:CONTRASEÑA]@]HOST:PUERTO[/?OPCIONES]

Casi idéntico al modo TCP, pero utilizando AF_VSOCK para el transporte.

ws://[[USUARIO][:CONTRASEÑA]@]HOST:PUERTO/[PANTALLA][?OPCIONES]

Conéctate usando el protocolo websocket.

wss://[[USUARIO][:CONTRASEÑA]@]HOST:PUERTO/[PANTALLA][?OPCIONES]

Conéctate usando el protocolo seguro websocket. (websocket con SSL)

ssh://[[USUARIO][:CONTRASEÑA]@]HOST[:PUERTO_SSH]/[PANTALLA][?OPCIONES]

Conéctate usando shell segura. (SSH)

Se pueden especificar opciones SSH adicionales usando la opción de línea de comandos --ssh. Las OPCIONES se pueden usar para especificar un proxy ssh: ?proxy=ssh://[USUARIO[:CONTRASEÑA]@]HOST[:PUERTO_SSH] xpra establecerá entonces una conexión SSH al host "proxy" especificado, y desde ese host xpra establecerá una conexión SSH al servidor xpra.

Para compatibilidad hacia atrás, el modo SSH también soporta la sintaxis: ssh:[USUARIO[:CONTRASEÑA]@]HOST:PANTALLA pero esta forma no soporta la especificación del número de puerto SSH. Versiones más antiguas también usaban la forma protocolo:host:puerto, pero se anima a los usuarios a moverse a un formato URI más estándar usando :// como separador.

La contraseña solo debe especificarse cuando el módulo de autenticación del servidor la requiera.

vnc://[[USUARIO][:CONTRASEÑA]@]HOST[:PUERTO_VNC]/

Conéctate usando el protocolo RFB. (también conocido como VNC) Este modo solo funciona contra servidores VNC o un servidor xpra en modo de escritorio o sombra.

EJEMPLOS

xpra start :7
Inicia un servidor xpra usando el número de pantalla :7. Nota: usar DISPLAY=:7 xterm para iniciar aplicaciones contra una pantalla específica no es recomendable. Prefiere siempre usar la opción de línea de comandos --start= de xpra. Ver el siguiente ejemplo:
xpra start --start=firefox
Inicia un servidor xpra, eligiendo una pantalla automáticamente y ejecutando Firefox en esa pantalla virtual. No aparecerá ninguna ventana hasta que te conectes con xpra attach. Los comandos hijos de inicio heredarán un entorno adaptado para ejecutarse bajo xpra.
xpra start ssh://bigbox/7 --start=xterm
Inicia un servidor xpra en bigbox con un xterm dentro y conéctate a él.
xpra start-desktop --start=xfce4-session
Inicia una sesión xfce en un servidor X11 anidado en un número de pantalla asignado automáticamente.
xpra displays
Lista todas las pantallas que se están ejecutando actualmente en el sistema. Esto incluye sesiones de escritorio interactivas, así como cualquier pantalla virtual (xvfb), ya sea que estén siendo utilizadas o no por un servidor xpra. Las pantallas en estado DEAD pueden ser recuperadas usando xpra recover.
xpra clean-displays
Termina cualquier pantalla que quede en estado DEAD.
xpra clean-sockets
Elimina cualquier socket de servidor perteneciente a servidores muertos.
xpra list
Muestra una lista

DISPLAYS: DESCRIPTION: Understanding the basic idea of displays is critical to using xpra successfully. P: The idea comes from standard X. If you have multiple X servers running on the same host, then there has to be some way to distinguish them. X does this by assigning each server a small, unique integer called (perhaps confusingly) its "display". In the common case of a desktop machine that has only one X server running, that server uses display ":0" (or sometimes you'll see ":0.0", which is effectively the same). When an application starts under X, it needs to know how to find the right X server to use; it does this by checking the environment variable $DISPLAY. P_2: Xpra faces a similar problem — there may be multiple xpra servers running on the same host, as well as multiple X servers. It solves this problem by re-using X's solution — each xpra server has a display associated with it. This display functions as both an X display (for when xpra is talking to X applications) and as an identifier by which xpra clients (like xpra attach) can locate the xpra server. P_3: You may omit the display number when using xpra start: a display will be chosen for you automatically. The display number chosen will be shown in the log output, you should also be able to see it with xpra list. On Microsoft Windows and Mac OSX, the display number should be omitted. P_4: Otherwise, when starting an xpra server, you may want to specify the name of the display to use. To do this, simply pick any number you like and stick a colon in front of it. For instance :7, :12, and :3117 are all valid display names. Just keep in mind that: BULLET_1: Every X or xpra server that is running on a single machine must use a different display name. If you pick a number that is already in use then xpra will not work. BULLET_2: The first few numbers (0, 1, 2) are commonly used by real X servers. BULLET_3: Everyone who connects to a given machine using ssh(1) with X forwarding enabled will also use a display number; ssh generally picks numbers near ten (10, 11, 12, ...). P_5: When specifying an xpra server to a client program like xpra attach, xpra detach, xpra stop, xpra exit, xpra version, xpra info, xpra list or xpra screenshot then you can use a display of the form :DISPLAY to refer to a server on the local host, or one of the form ssh://[USER@]HOST/DISPLAY to refer to a server on a remote host; xpra will automatically connect to the remote host using ssh(1). Generally, if you have only one xpra session running on a machine (which you can verify by running xpra list on that machine), then you can omit the number entirely; xpra attach alone will attach to the lone xpra server on the current machine regardless of its number, xpra attach ssh://frodo will similarly attach to the lone xpra session on a remote machine. P_6: Connecting using the display number assumes that the client and server use the same configuration for socket directories, or at least that the client can find at least one of the directories used by the unix domain sockets (see bind, socket-dir and socket-dirs). P_7: If the xpra server was given the --bind-tcp=[HOST]:PORT (or --bind-ssl, --bind-ws, --bind-wss, --bind-vsock) option when started then you can also connect to it using a display of the form tcp://HOST:PORT[/DISPLAY], ssl://HOST:PORT[/DISPLAY], ws://HOST:PORT[/DISPLAY], wss://HOST:PORT[/DISPLAY] or vsock://HOST:PORT[/DISPLAY]. Opciones de conexión del cliente

--socket-dir=DIR
Directorio donde buscar sockets existentes si no se estableció uno específico con socket-dir. Puede especificar cada directorio usando un nuevo argumento de línea de comandos --socket-dirs, o unidos por el separador de ruta (: en Posix). Las rutas serán expandidas. (ej: --socket-dirs=~/.xpra:/tmp)
--file-transfer=on|off
Habilita la transferencia de archivos.
--open-files=on|off
Esta opción se puede usar para permitir que el extremo remoto abra automáticamente archivos después de que hayan sido cargados. Esto puede ser un riesgo de seguridad si estás usando xpra para restringir lo que los clientes pueden ejecutar en el servidor.
--forward-xdg-open=on|off|auto
Intercepta la ejecución de xdg-open y reenvía la solicitud al cliente.
--open-command=COMANDO
El comando a usar para abrir archivos y URL.
--bandwidth-limit=BITS_POR_SEGUNDO
Restringe el uso de ancho de banda a menos del límite dado. El valor del cliente no puede aumentar el límite del servidor. El valor puede especificarse usando unidades estándar, ej: 1Mbps o 500K. En modo auto, el cliente establecerá el valor del límite de ancho de banda al 80% de la velocidad máxima de la interfaz de red que esté utilizando para conectarse al servidor.

--splash=yes|no|auto Muestra una pantalla de bienvenida durante el inicio del cliente o servidor. Con el valor predeterminado de auto, la pantalla de bienvenida solo se muestra si hay una GUI disponible - ej: no se intentará mostrar la pantalla de bienvenida cuando xpra se inicie desde una sesión SSH.

Opciones para start, start-desktop, upgrade, proxy y shadow

--daemon=yes|no
Por defecto, el servidor xpra se pone en segundo plano, es decir, 'daemoniza', y redirige su salida a un archivo de registro. Esto se puede usar para evitar ese comportamiento (útil principalmente para depuración).
--resize-display=yes|no|ANCHOxALTO
Redimensiona la pantalla virtual para que coincida con la resolución del cliente actualmente conectado. Esto solo se aplica a los subcomandos start y start-desktop. Si se da una resolución, esta será la resolución inicial de la pantalla y la pantalla será redimensionable. Un pequeño conjunto de alias predefinidos también se puede usar: QVGA, VGA, SVGA, XGA, 1080p, FHD, 4K.
--chdir=DIR

--ssh=CMD
Cuando usa una dirección ssh: para conectarse a una pantalla remota, xpra ejecuta ssh(1) para realizar la conexión subyacente. La mayoría de las instalaciones ahora deberían usar paramiko como el comando backend por defecto. Otro valor común para CMD es ssh o plink en Microsoft Windows. Si su programa ssh está en una ubicación inusual, tiene un nombre inusual, o desea pasar opciones especiales para cambiar el comportamiento de ssh, entonces puede usar el interruptor --ssh para indicarle a xpra cómo ejecutar ssh.

Por ejemplo, si desea usar cifrado arcfour, entonces debería ejecutar

xpra attach --ssh="ssh -c arcfour" ssh://frodo/7
Nota: No se moleste en habilitar la compresión ssh; esto es redundante con la propia compresión de xpra y solo desperdiciará su CPU.

En MS Windows, donde se usan barras invertidas para separar los elementos de la ruta y donde los espacios se usan a menudo como parte de las rutas, debe agregar comillas alrededor de las rutas. (es decir, ssh="C:\Archivos de programa\Xpra\Plink.exe" -ssh -agent)

--exit-ssh=sí|no
Elige si el proceso cliente SSH debe ser terminado forzosamente cuando xpra se desconecta del servidor. Si está usando el intercambio de conexiones SSH, puede que desee evitar detener la instancia del proceso maestro SSH generado por xpra ya que puede ser utilizado por otras sesiones SSH. Nota: el exit-ssh=no desvincula el proceso SSH de la terminal lo que impide que el proceso SSH interactúe con la entrada de la terminal, esto deshabilita la interacción del teclado requerida para la entrada de contraseñas, verificación de claves de host, etc..
--xpra-remoto=CMD
Al conectarse a un servidor remoto a través de ssh, xpra necesita poder encontrar y ejecutar el ejecutable de xpra en el host remoto. Si este ejecutable está en una ubicación no estándar, o requiere variables de entorno especiales para ser configuradas antes de poder ejecutarse, lograr esto puede no ser trivial. Si ejecutar xpra attach ssh:algo falla porque no puede encontrar el xpra remoto, entonces puede usar esta opción para especificar cómo ejecutar xpra en el host remoto.

Dicho esto, esta opción no debería ser necesaria en el uso normal, ya que xpra se esfuerza bastante por solucionar los problemas anteriores. Si se encuentra necesitándola a menudo, eso puede indicar un error del que agradeceríamos información.

ENTORNO

DISPLAY
xpra start --iniciar-hijo=... establece esta variable en el entorno del hijo para apuntar a la pantalla de xpra.

xpra attach, por otro lado, usa esta variable para determinar en qué pantalla se deben mostrar las aplicaciones remotas.

XPRA_PASSWORD puede usarse con xpra attach en lugar de la opción archivo-contraseña.

ARCHIVOS

xpra.conf almacena los valores por defecto para la mayoría de las opciones. Hay un archivo de configuración global en /etc o /usr/local/etc, y cada usuario puede anular esos valores por defecto creando el archivo .xpra/xpra.conf. También puede dividir las opciones en múltiples archivos colocándolos en un directorio conf.d con la extensión .conf. Dependiendo del sistema operativo y la versión, xpra utiliza el directorio ~/.xpra o /run/<uid>/xpra para almacenar una serie de archivos. (Los ejemplos a continuación se dan para la pantalla :7.)

~/.xpra/:7
El socket de dominio unix que los clientes usan para contactar al servidor xpra, si la configuración del sistema usa este directorio.
~/.xpra/:7.log
Cuando se ejecuta en modo demonio (el predeterminado), el servidor xpra dirige toda la salida a este archivo. Esto incluye toda la salida de depuración, si la depuración está habilitada.
~/.xpra/run-xpra
Un script de shell que, cuando se ejecuta, inicia xpra con el intérprete de python correcto, PYTHONPATH, PATH, ubicación del script principal de xpra, etc. Generado automáticamente por xpra initenv, xpra start y utilizado por xpra attach (ver también la discusión de --xpra-remoto).

ERRORES

Xpra no maneja completamente todos los aspectos del protocolo X; por ejemplo, funciones de entrada avanzadas como la sensibilidad a la presión en tabletas, algunas sugerencias del administrador de ventanas, y probablemente otras partes más oscuras del protocolo X. Sin embargo, se degrada elegantemente, y los parches para cada característica serían agradecidos.

El servidor xpra asigna un framebuffer demasiado grande cuando usa Xvfb; esto desperdicia memoria. Si Xvfb no soporta RandR, esto también puede hacer que las aplicaciones se comporten mal (por ejemplo, dejando menús fuera de pantalla). Esto no es un problema cuando se usa Xdummy, ver el interruptor --xvfb para detalles. Por el contrario, si el framebuffer es alguna vez insuficientemente grande, los clientes se comportarán mal de otras maneras (por ejemplo, los eventos de entrada se dirigirán incorrectamente).
