X11VNC(1) Comandos de usuario X11VNC(1)

NOMBRE

x11vnc - permitir conexiones VNC a pantallas X11 reales
versión: 0.9.17, última modificación: 2025-04-11

SINOPSIS

x11vnc [OPCIÓN]...

DESCRIPCIÓN

Uso típico es:

Ejecute este comando en una shell en la máquina remota "far-host" con la sesión X que desea ver:
x11vnc -display :0
Luego ejecute esto en otra ventana en la máquina en la que está sentado:
vncviewer far-host:0

Una vez que x11vnc establezca conexiones con el servidor X y comience a escuchar como servidor VNC, imprimirá una cadena: PORT=XXXX donde XXXX es típicamente 5900 (el puerto predeterminado del servidor VNC). A continuación, uno ejecutaría algo como esto en la máquina local: "vncviewer hostname:N" donde "hostname" es el nombre de la máquina que ejecuta x11vnc y N es XXXX - 5900, es decir, generalmente "vncviewer hostname:0".

Por defecto, x11vnc no permitirá compartir la pantalla y saldrá tan pronto como el cliente se desconecte. Consulte -shared y -forever a continuación para anular estas protecciones. Consulte las Preguntas Frecuentes para obtener detalles sobre cómo cifrar la conexión VNC a través de un canal cifrado como ssh(1). En resumen:

ssh -t -L 5900:localhost:5900 far-host 'x11vnc -localhost -display :0'

% vncviewer -encodings 'copyrect tight zrle hextile' localhost:0

Además, se recomienda encarecidamente el uso de una contraseña VNC (-rfbauth o -passwdfile).

Para obtener información adicional, consulte: http://www.karlrunge.com/x11vnc/ y http://www.karlrunge.com/x11vnc/faq.html

Soporte de archivos de configuración: si existe el archivo $HOME/.x11vncrc, cada línea en él se trata como una única opción de línea de comandos. Deshabilite con -norc. Para cada nombre de opción, no se requiere el carácter inicial "-". Por ejemplo, una línea que sea "forever" o "-forever" puede usarse y son líneas equivalentes. De manera similar, "wait 100" o "-wait 100" son líneas aceptables y equivalentes. El carácter "#" comenta hasta el final de la línea de la manera habitual (haga una barra invertida para un literal). Se eliminan los espacios en blanco al principio y al final. Las líneas pueden continuar con una "\" como último carácter de una línea (se convierte en un carácter de espacio).

OPCIONES

-display disp

Servidor X de visualización al que conectarse, generalmente :0. El proceso del servidor X debe ejecutarse en la misma máquina y ser compatible con MIT-SHM. Equivalente a establecer la variable de entorno DISPLAY a disp.
Consulte la descripción a continuación de las extensiones "-display WAIT:...", donde el alias "-find" encontrará la visualización del usuario automáticamente, y "-create" creará una sesión de Xvfb si no se encuentra ninguna sesión.

-auth file

Establezca el archivo de autenticación X a file, equivalente a establecer la variable de entorno XAUTHORITY a file antes del inicio. Igual que -xauth file. Consulte las páginas del manual de Xsecurity(7), xauth(1) para obtener más información.
Use '-auth guess' para que x11vnc use su mecanismo -findauth (descrito a continuación) para intentar adivinar el nombre del archivo XAUTHORITY y usarlo.
XDM/GDM/KDM: si está ejecutando x11vnc como root y desea encontrar XAUTHORITY antes de que alguien haya iniciado sesión en una sesión X, use: x11vnc -env FD_XDM=1 -auth guess ... (Esto también encontrará XAUTHORITY si un usuario ya ha iniciado sesión en la sesión X.) Al ejecutarse como root, se intentará FD_XDM=1 si la suposición inicial de -auth falla.

-N

Si la pantalla X es :N, intente establecer la pantalla VNC también como :N. Esto simplemente establece la opción -rfbport a 5900+N. El programa saldrá inmediatamente si ese puerto no está disponible. La opción -N solo funciona con el uso normal de -display, por ejemplo, :0 u :8. Se ignora -N en los modos -display WAIT:..., -create, -find, -svc, -redirect, etc.

-autoport n

Sondea automáticamente un puerto VNC libre comenzando en n. El valor predeterminado es comenzar a sondear en 5900. Use esto para evitar otros servidores VNC cerca de 5900.

-rfbport str

(Una opción de LibVNCServer) El puerto VNC en el que escuchar (por ejemplo, 5900, 5901, etc.). Si se especifica como "-rfbport PROMPT", entonces la interfaz gráfica de usuario -gui de x11vnc se utiliza para solicitar al usuario que introduzca el número de puerto.

-6

Soporte de escucha IPv6. Además de IPv4, se escucha la dirección IPv6 para las conexiones entrantes. Se utiliza el mismo número de puerto que para IPv4.
NOTA: Este binario de x11vnc se compiló para tener el modo de escucha IPv6 "-6" HABILITADO por defecto (CPPFLAGS -DX11VNC_LISTEN6=1). Por lo tanto, para deshabilitar el modo de escucha IPv6, DEBE proporcionar la opción "-no6" (ver más abajo).
El modo "-6" funciona tanto para conexiones normales como para las cifradas con -ssl. Casi todo es compatible con el caso IPv6, pero hay algunas excepciones. Consulte -stunnel para su soporte IPv6.
Actualmente, para que todo funcione correctamente, la máquina puede necesitar tener algún soporte IPv4, al menos para la interfaz de bucle invertido. Sin embargo, para casi todos los modos de uso no se requiere soporte IPv4. Consulte -noipv4.
Si tiene problemas para compilar o ejecutar en modo IPv6, establezca -DX11VNC_IPV6=0 en CPPFLAGS al configurar para deshabilitar el soporte IPv6.

-no6

Deshabilita el soporte de escucha IPv6 (solo útil si el modo "-6" se compila como predeterminado; consulte la descripción de X11VNC_LISTEN6 anteriormente bajo "-6".)

-noipv6

No intente usar IPv6 para ningún socket de escucha o de conexión. Esto incluye tanto los puertos de servicio de escucha como las conexiones salientes de -connect, -connect_or_exit, o -proxy. Use esto si tiene problemas debido a IPv6.

-noipv4

No intente usar IPv4 para ningún socket de escucha o de conexión. Esto es principalmente para explorar el comportamiento de x11vnc en un sistema solo IPv6, pero puede tener otros usos.

-reopen

Si la conexión del servidor X se desconecta, intente reabrir la pantalla X (hasta una vez). Esto es útil para administradores de pantalla como GDM (opción KillInitClients) que matan x11vnc justo después de que el usuario inicia sesión en la sesión X. Nota: el estado reabierto puede ser inestable. Establezca X11VNC_REOPEN_DISPLAY=n para reabrir n veces y establezca X11VNC_REOPEN_SLEEP_MAX al número de segundos, por defecto 10, para seguir intentando reabrir la pantalla (una vez por segundo).
Actualización: a partir de la versión 0.9.9, x11vnc intenta evitar automáticamente ser eliminado por el administrador de pantalla retrasando la creación de ventanas o usando XFIXES. Por lo tanto, no debería ser necesario usar KillInitClients=false siempre que inicie sesión lo suficientemente rápido (dentro de los 45 segundos posteriores a la conexión). Puede deshabilitar esto estableciendo X11VNC_AVOID_WINDOWS=never. También puede establecerlo en el número de segundos de retraso.

-reflect host:N

En lugar de conectarse y sondear una pantalla X, conéctese al servidor VNC remoto host:N y sea un reflector/repetidor para él. Esto es útil para intentar gestionar el caso de muchos visores VNC simultáneos (por ejemplo, transmisión en aulas) donde, por ejemplo, se coloca un repetidor en cada conmutador de red, etc., para mejorar el rendimiento distribuyendo la carga y el tráfico de red. Implica -shared (use -noshared como opción posterior para deshabilitar). Consulte la discusión a continuación bajo -rawfb vnc:host:N para obtener más detalles.

-id windowid

Mostrar la ventana X correspondiente a windowid no toda la pantalla. Las ventanas nuevas como menús emergentes, ventanas superiores transitorias, etc., pueden no verse o pueden cortarse. Deshabilitar SaveUnders o BackingStore en el servidor X puede ayudar a mostrarlas. x11vnc puede fallar si la ventana está inicialmente parcialmente oscurecida, cambia de tamaño.

, está iconizada, etc. Se toman algunas medidas para evitar esto y se utiliza el mecanismo -xrandr para rastrear los cambios de tamaño. Utilice xwininfo(1) para obtener el ID de la ventana, o utilice "-id pick" para que x11vnc ejecute xwininfo(1) por usted y extraiga el ID. La opción -id es útil para exportar aplicaciones muy simples (por ejemplo, la vista actual en una cámara web).

-sid windowid

Al igual que -id, pero en lugar de usar la ventana directamente, desplaza una vista raíz hacia ella: esto muestra menús de SaveUnders, etc., aunque se recortarán si se extienden más allá de la ventana.

-appshare

Compartición de aplicaciones simple basada en el mecanismo -id/-sid. Cada nueva ventana de nivel superior que crea la aplicación induce una nueva ventana de espectador a través de una conexión inversa. Se requieren las opciones -id/-sid y -connect. Ejecute 'x11vnc -appshare -help' para más información.

-clip WxH+X+Y

Solo muestra la subregión de la pantalla completa que corresponde a la geometría del rectángulo con tamaño WxH y desplazamiento +X+Y. La pantalla VNC tiene un tamaño WxH (es decir, menor que la pantalla completa). Esto también funciona para el modo -id/-sid donde el desplazamiento es relativo a la esquina superior izquierda de la ventana seleccionada. Un ejemplo de uso de esta opción sería dividir una pantalla grande (por ejemplo, Xinerama) en dos partes para acceder a través de espectadores separados ejecutando un x11vnc separado en cada parte.
Utilice '-clip xinerama0' para recortar a la primera subpantalla de xinerama (si xinerama está activo). xinerama1 para la segunda subpantalla, etc. De esta manera, no necesita averiguar el WxH+X+Y de la subpantalla de xinerama deseada. Las pantallas se ordenan en orden de distancia creciente desde el origen (0,0) (es decir, no en el orden del servidor X).

-flashcmap

En color indexado de 8bpp, permite que el mapa de colores instalado parpadee mientras el puntero se mueve de una ventana a otra (lento). También pruebe la opción -8to24 para evitar el parpadeo por completo.

-shiftcmap n

Problema raro, pero algunas pantallas de 8bpp utilizan menos de 256 celdas de color (por ejemplo, escala de grises de 16 colores, quizás los otros bits se utilizan para doble buffer) *y* también necesitan desplazar los valores de píxeles de 0, ..., ncells. n indica el desplazamiento que se aplicará a los valores de píxeles. Para ver los valores de píxeles, establezca DEBUG_CMAP=1 para imprimir un histograma del mapa de colores. Ejemplo: -shiftcmap 240

-notruecolor

Para pantallas de 8bpp, fuerza el color indexado (es decir, un mapa de colores) incluso si parece TrueColor de 8bpp (problema raro).

-advertise_truecolor

Si la pantalla X11 es de color indexado, mienta a los clientes cuando se conectan por primera vez diciéndoles que es truecolor. Para solucionar RealVNC: inPF tiene colorMap pero no 8bpp. Use '-advertise_truecolor reset' para restablecer también el fb del cliente.

-visual n

Esta opción probablemente no hace lo que usted piensa. Simplemente *fuerza* la visualización utilizada para el framebuffer; esto puede ser algo malo... (por ejemplo, arruinar los colores o causar un bloqueo). Es útil para pruebas y para algunas soluciones alternativas. n puede ser un número decimal o 0x hexadecimal. Ejecute xdpyinfo(1) para ver los valores. También se puede usar "TrueColor", etc. Consulte <X11/X.h> para obtener una lista. Si la cadena termina en ":m" entonces, para bien o para mal, la profundidad visual se fuerza a ser m. Es posible que desee utilizar -noshm al utilizar esta opción (para que XGetImage pueda traducir automáticamente los datos de píxeles).

-overlay

Maneja múltiples visualizaciones de profundidad en una pantalla, por ejemplo, visualizaciones superpuestas de 8+24 y 24+8 (los 32 bits por píxel se empaquetan con 8 para PseudoColor y 24 para TrueColor).
Actualmente, -overlay solo funciona en Solaris a través de XReadScreen(3X11) y en IRIX utilizando XReadDisplay(3). En Solaris hay un problema con el "sangrado" de imágenes alrededor de los menús emergentes transitorios (pero no para el menú en sí): una solución es deshabilitar SaveUnders pasando el argumento "-su" a Xsun (en /etc/dt/config/Xservers).
Utilice -overlay como solución para situaciones como estas: Algunas aplicaciones heredadas requieren que la visualización predeterminada sea 8bpp (8+24), de lo contrario, utilizarán PseudoColor de 8bpp incluso cuando la visualización predeterminada sea TrueColor de profundidad 24 (24+8). En estos casos, los colores en algunas ventanas serán incorrectos en x11vnc a menos que se utilice -overlay. Otro uso de -overlay es permitir mostrar la forma exacta del cursor del ratón (detalles a continuación).
Bajo -overlay, el rendimiento será algo más lento debido a las transformaciones de imagen adicionales requeridas. Para un rendimiento óptimo, no utilice -overlay, sino configure el servidor X para que la visualización predeterminada sea TrueColor de profundidad 24 y trate de que todas las aplicaciones utilicen esa visualización (por ejemplo, algunas aplicaciones tienen las opciones -use24 o -visual).

-overlay_nocursor

Establece -overlay, pero no intenta dibujar la forma exacta del cursor del ratón utilizando el mecanismo de superposición.

-8to24 [opts]

Pruebe esta opción si -overlay no es compatible en su sistema operativo, y tiene una aplicación heredada de 8bpp que desea ver en una pantalla multidimensional con profundidad predeterminada de 24 (y es de 32 bpp) O tiene una pantalla de profundidad predeterminada de 8 con ventanas de profundidad 24 para algunas aplicaciones. Esta opción puede no funcionar en todos los servidores X y hardware (probado en el controlador mga de XFree86/Xorg y en Xsun). La cadena "opts" no es requerida y se describe a continuación.
Este modo habilita un truco en el que x11vnc monitorea ventanas dentro de 3 niveles desde la ventana raíz. Si encuentra alguna que sea de 8bpp, extrae los valores de píxeles de color indexado utilizando XGetImage() y luego aplica una transformación utilizando el mapa de colores para crear valores RGB TrueColor que a su vez inserta en los bits 1-24 del framebuffer. Esto crea una "vista" de profundidad 24 de la pantalla que luego se exporta a través de VNC.
Por el contrario, para pantallas de profundidad 8 predeterminada, las regiones de profundidad 24 son leídas por XGetImage() y todo se transforma y se inserta en un framebuffer TrueColor de profundidad 24.
Tenga en cuenta que incluso si *no* hay visualizaciones o ventanas de profundidad 24 (es decir, puro 8bpp), este modo es potencialmente una mejora sobre -flashcmap porque evita el parpadeo y muestra cada ventana en el color correcto.
Este método funciona bien, pero aún puede tener errores y consume recursos. Si hay varias ventanas de 8bpp que utilizan diferentes mapas de colores, es posible que tenga que iconizar todas menos una para que los colores sean correctos.
Puede haber errores de pintura al recortar y cambiar entre ventanas de profundidades 8 y 24. Se aplican heurísticas para intentar minimizar los errores de pintura. También puede presionar 3 Alt_L seguidas para actualizar la pantalla si el error no se repara solo. También se puede usar la opción -fixscreen 8=3.0 o -fixscreen V=3.0 para actualizar la pantalla periódicamente a costa de ancho de banda (cada 3 segundos para este ejemplo).
La cadena [opts] puede contener la siguiente configuración. Múltiples configuraciones están separadas por comas.
Para algunos servidores X con profundidad 24 predeterminada, se puede lograr una aceleración a través de la opción "nogetimage". Esto habilita un esquema en el que XGetImage() no se utiliza para recuperar los datos de 8bpp. En su lugar, se asume que los datos de 8bpp se encuentran en los bits 25-32 de los píxeles X de 32 bits. No hay requisito de que el servidor X coloque los datos allí para nuestras solicitudes de sondeo, pero algunos lo hacen y, por lo tanto, se pueden omitir los pasos adicionales para recuperarlos. Probado con el controlador mga con XFree86/Xorg. Para el caso de profundidad 8 predeterminada, esta opción se ignora.
Para ajustar la frecuencia con la que XGetImage() se utiliza para sonder las regiones de visualización no predeterminadas en busca de cambios, utilice la opción "poll=t" donde "t" es un tiempo de punto flotante. (predeterminado: 0.05)
Establecer la opción "level2" limitará la búsqueda de ventanas de visualización no predeterminadas a dos niveles desde la ventana raíz. Haga esto en máquinas lentas donde sepa que el administrador de ventanas solo impone una ventana adicional entre la ventana de la aplicación y la ventana raíz.
También para máquinas muy lentas, use "cachewin=t" donde t es una cantidad de tiempo de punto flotante para almacenar en caché los resultados de XGetWindowAttributes. Por ejemplo, cachewin=5.0. Esto puede llevar a que las ventanas no se noten durante esta cantidad de tiempo al desiconizar, errores de pintura, etc.
Mientras probaba en un SS20 muy antiguo, estas opciones dieron una respuesta tolerable: -8to24 poll=0.2,cachewin=5.0. Para esta máquina, -overlay es compatible y da una mejor respuesta.
La depuración para este modo se puede habilitar estableciendo "dbg=1", "dbg=2" o "dbg=3".

-24to32

Problema muy raro: si el framebuffer (pantalla X o -rawfb) es de 24bpp en lugar de los 32bpp habituales, transforme dinámicamente los píxeles a 32bpp. Esto será más lento, pero se puede utilizar para solucionar problemas donde los espectadores VNC no pueden manejar 24bpp (por ejemplo, "main: setPF: not 8, 16 or 32 bpp?"). Consulte la sección de preguntas frecuentes para obtener más información.
En el caso del modo -rawfb, los píxeles se modifican directamente insertando un byte 0 para rellenarlos a 32bpp. Para pantallas X, se realiza un truco que es equivalente a "-noshm -visual TrueColor:32". (Si necesita un mejor rendimiento para este último, no dude en preguntar).

-scale fracción

Escala el framebuffer por el factor fracción. Los valores menores que 1 reducen el fb, los mayores lo expanden. Nota: la imagen puede no ser nítida y la respuesta puede ser más lenta. Si fracción contiene un punto decimal ".", se toma como un número de punto flotante, alternativamente se puede usar la notación "m/n" para denotar fracciones exactamente, por ejemplo, -scale 2/3
Para escalar asimétricamente en las direcciones horizontal y vertical, especifique una geometría WxH a la que estirar: por ejemplo, '-scale 1024x768', o también '-scale 0.9x0.75'
Opciones de escalado: se pueden agregar después de fracción a través de ":", para proporcionar múltiples opciones ":" use comas. Si solo desea un escalado rápido y aproximado sin mezcla, agregue ":nb" a fracción (por ejemplo, -scale 1/3:nb). No hay mezcla por defecto para el color indexado de 8bpp, para forzar la mezcla en este caso use ":fb".
Para deshabilitar -scrollcopyrect y -wirecopyrect bajo -scale use ":nocr
. Si necesitas habilitarlos, usa ":cr" o especifícalos explícitamente en la línea de comandos. Si se detecta un enlace lento, ":nocr" puede aplicarse automáticamente. Por defecto: :cr
Opciones más esotéricas: para compatibilidad con visores VNC, el ancho escalado se ajusta para que sea un múltiplo de 4: para deshabilitar esto, usa ":n4". ":in" usa el esquema de interpolación incluso al reducir, ":pad" rellena el ancho y alto escalados para que sean múltiplos del denominador de escalado (por ejemplo, 3 para 2/3).

-geometry AnxAl

Igual que -scale AnxAl

-scale_cursor frac

Por defecto, si se proporciona -scale, la forma del cursor se escala por el mismo factor. Dependiendo de tu uso, es posible que desees escalar el cursor independientemente de la pantalla o no hacerlo en absoluto. Si especificas -scale_cursor, el cursor se escalará por ese factor. Al usar el modo -scale para mantener el cursor en su tamaño "natural", usa ":-scale_cursor 1". La mayoría de las opciones de escalado ":" también se aplican aquí.

-viewonly

Todos los clientes VNC solo pueden observar (por defecto desactivado).

-shared

La pantalla VNC se comparte, es decir, más de un visor puede conectarse al mismo tiempo (por defecto desactivado).

-once

Sal después de que el primer visor conectado exitosamente se desconecte, lo opuesto a -forever. Este es el valor por defecto.

-forever

Continuar escuchando más conexiones en lugar de salir tan pronto como el primer cliente(s) se desconecte. Igual que -many
Para obtener el comportamiento estándar de VNC no compartido, donde cuando un nuevo cliente VNC se conecta, el cliente VNC existente se desconecta, usa: -nevershared -forever Este método también se puede usar para protegerse contra conexiones TCP colgadas que no desaparecen.

-loop

Crea un bucle externo que reinicia el proceso x11vnc cada vez que termina. -bg y -inetd se ignoran en este modo (sin embargo, consulta -loopbg a continuación).
Útil para continuar incluso si el servidor X termina y se reinicia (en ese momento, el proceso necesitará permiso para reconectarse al nuevo servidor X, por supuesto).
Usa, por ejemplo, -loop100 para esperar 100 milisegundos entre reinicios, etc. El valor por defecto es 2000ms (es decir, 2 segundos). Usa, por ejemplo, -loop300,5 para esperar 300 ms y solo repetir 5 veces.
Si se especifica -loopbg (más cualquier número) en su lugar, la opción "-bg" está implícita y el modo se aproxima al uso de inetd(8) hasta cierto punto. En este caso, cuando pasa a segundo plano, todos los sockets de escucha (es decir, puertos 5900, 5800) se cierran, de modo que el siguiente en el bucle pueda usarlos. Este modo solo será útil si un cliente VNC (el único cliente para ese proceso) ya está conectado antes de que el proceso pase a segundo plano; por ejemplo, el uso de -display WAIT:.., -svc y -connect puede hacer uso de este modo "pobre" de inetd. El tiempo de espera por defecto es de 500 ms en este modo. Este uso podría ser útil: -svc -bg -loopbg

-timeout n

Salir a menos que un cliente se conecte dentro de los primeros n segundos después de la puesta en marcha.
Si no ha habido intentos de conexión después de n segundos, x11vnc sale inmediatamente. Si un cliente intenta conectarse pero no ha progresado al estado operativo normal, x11vnc le da unos segundos más para terminar y sale si no llega al estado normal.
Para conexiones inversas a través de -connect o -connect_or_exit, se establecerá un tiempo de espera de n segundos para todas las conexiones inversas. Si la alarma de tiempo de espera de conexión se activa, x11vnc saldrá inmediatamente.

-sleepin n

Al inicio, espera n segundos antes de continuar (por ejemplo, para permitir que los redireccionamientos y los clientes de escucha se inicien)
Si se proporciona un rango: '-sleepin min-max', se espera un valor aleatorio entre min y max. Por ejemplo: '-sleepin 0-20' y '-sleepin 10-30'. Los números de punto flotante también están permitidos.

-inetd

Lanzado por inetd(8): stdio en lugar de socket de escucha. Nota: si no estás redirigiendo stderr a un archivo de registro (a través de shell 2> o la opción -o), DEBES especificar también la opción -q, de lo contrario, stderr irá al visor, lo que provocará su aborto. Especificar tanto -inetd como -q y ningún -o cerrará automáticamente stderr.

-tightfilexfer

Habilita la extensión de transferencia de archivos de TightVNC. Ten en cuenta que cuando se proporciona la opción -viewonly, todas las transferencias de archivos se deshabilitan. Además, los clientes que inician sesión como solo vista no pueden transferir archivos. Sin embargo, si el mecanismo de control remoto se utiliza para cambiar el estado global o por cliente de solo vista, los permisos de transferencia de archivos NO cambiarán.
IMPORTANTE: comprende que si se especifica -tightfilexfer y ejecutas x11vnc como root, por ejemplo, para acceso inetd o del gestor de pantalla (gdm, kdm, ...), y no cambias de usuario a través de la opción -users, entonces los visores VNC que se conecten podrán realizar lecturas y escrituras de transferencia de archivos como *root*.
Además, tightfilexfer está deshabilitado en el modo -unixpw.

-ultrafilexfer

Nota: para habilitar la transferencia de archivos de UltraVNC y hacer que funcione, probablemente necesites proporcionar estas opciones de LibVNCServer: ""-rfbversion 3.6 -permitfiletransfer" "-ultrafilexfer" es un alias para esta combinación.
IMPORTANTE: comprende que si se especifica -ultrafilexfer y ejecutas x11vnc como root, por ejemplo, para acceso inetd o del gestor de pantalla (gdm, kdm, ...), y no cambias de usuario a través de la opción -users, entonces los visores VNC que se conecten podrán realizar lecturas y escrituras de transferencia de archivos como *root*.
Ten en cuenta que, lamentablemente, no puedes usar -tightfilexfer y -ultrafilexfer al mismo tiempo porque este último requiere establecer la versión en 3.6 y tightvnc no realizará transferencias de archivos cuando vea ese número de versión.

-http

En lugar de usar -httpdir (ver más abajo) para especificar dónde está el applet del visor VNC Java, haz que x11vnc intente *adivinar* dónde está el directorio buscando de forma relativa a la ubicación del programa y en ubicaciones estándar (/usr/local/share/x11vnc/classes, etc.). Bajo -ssl o -stunnel, se buscará el subdirectorio de clases ssl.

-http_ssl

Igual que -http, pero fuerza la búsqueda del subdirectorio de clases ssl.
Ten en cuenta que para HTTPS, la entrega de applets Java en un solo puerto, puedes establecer X11VNC_HTTPS_DOWNLOAD_WAIT_TIME al número máximo de segundos para esperar a que la descarga del applet finalice. El valor por defecto es 15.

-avahi

Utiliza el protocolo Avahi/mDNS ZeroConf para anunciar este servidor VNC en la red local. (Términos relacionados: Rendezvous, Bonjour). Dependiendo de tu configuración, puede que necesites iniciar avahi-daemon y abrir el puerto udp 5353 en tu firewall.
Puedes establecer las variables de entorno X11VNC_AVAHI_NAME, X11VNC_AVAHI_HOST y/o X11VNC_AVAHI_PORT para anular los valores por defecto. Por ejemplo: -env X11VNC_AVAHI_NAME=wally
Si la API de Avahi no se encuentra en tiempo de compilación, se intentará usar un programa auxiliar como avahi- publish(1) o dns- sd(1)

-mdns

Igual que -avahi.

-zeroconf

Igual que -avahi.

-connect cadena

Para usar con conexiones inversas de "vncviewer -listen". Si cadena tiene el formato "host" o "host:puerto", la conexión se realiza una vez al inicio.
Usa comas para una lista de hosts y hosts:puertos. Por ejemplo, -connect host1,host2 o host1:0,host2:5678. Ten en cuenta que para conectarse de forma inversa a múltiples hosts al mismo tiempo, probablemente necesitarás proporcionar también: -shared
Ten en cuenta que, a diferencia de la mayoría de los servidores vnc, x11vnc requerirá una contraseña tanto para conexiones inversas como directas. (siempre que la autenticación por contraseña esté habilitada, -rfbauth, etc.) Si no deseas requerir una contraseña para conexiones inversas, establece X11VNC_REVERSE_CONNECTION_NO_AUTH=1 en tu entorno antes de iniciar x11vnc.
Si cadena contiene "/", se interpreta como un archivo para verificar periódicamente en busca de nuevos hosts. Se lee la primera línea y luego se trunca el archivo. Ten cuidado con la ubicación de este archivo si x11vnc se ejecuta como root (por ejemplo, a través de gdm(1), etc.).
Modo repetidor: Algunos servicios proporcionan un "repetidor vnc" intermedio: http://www.uvnc.com/addons/repeater.html (y también http://koti.mbnet.fi/jtko/ para el puerto de Linux) que actúa como un proxy/gateway. Modos como estos requieren el envío de una cadena inicial para la conexión inversa antes de que comience el protocolo VNC. Aquí están las formas de hacerlo:
-connect pre=alguna_cadena+host:puerto -connect pre128=alguna_cadena+host:puerto -connect repeater=ID:1234+host:puerto -connect repeater=23.45.67.89::5501+host:puerto
También se admite la notación SSVNC:
-connect repeater://host:puerto+ID:1234
Al igual que con el uso normal de -connect, si no se proporciona el puerto del repetidor, se asume 5500.
La idea básica es que entre la etiqueta especial, por ejemplo, "pre=" y "+", se encuentra la cadena previa que se enviará. Ten en cuenta que en este caso, host:puerto es el servidor repetidor, NO el visor vnc. De alguna manera, la cadena previa le dice al servidor repetidor cómo encontrar el visor vnc y conectarte a él.
En el caso pre=alguna_cadena+host:puerto, simplemente se envía "alguna_cadena". En el caso preNNN=alguna_cadena+host:puerto, se envía "alguna_cadena" en un buffer rellenado con nulos de longitud NNN. repeater= es lo mismo que pre250=, este es el tamaño del buffer del repetidor ultravnc.
Cadenas como "\n" y "\r", etc., se expanden a nueva línea y retorno de carro. "\c" se expande a "," ya que la conexión
t string está separado por comas.
Ver también la opción -proxy a continuación para formas adicionales de canalizar conexiones inversas.
SSL Inverso: usar -connect en modo -ssl hace que x11vnc actúe como un cliente SSL (inicia la conexión SSL) en lugar de un servidor SSL. La idea es que x11vnc podría conectarse a stunnel en el lado del espectador con el espectador en modo de escucha. Si no desea este comportamiento, use -env X11VNC_DISABLE_SSL_CLIENT_MODE=1. Con esto, el lado del espectador puede actuar como el cliente SSL, como lo hace normalmente para conexiones directas.
Modo Repetidor SSL Inverso: Esto funcionará, pero tenga en cuenta que si el Cliente VNC realiza algún tipo de acción de 'Buscar Certificado' antes de conectarse, el Repetidor probablemente cerrará la conexión y ambos lados deberán reiniciarse. Considere el uso de -connect_or_exit y -loop300,2 para que x11vnc se reconecte una vez al repetidor después de la búsqueda. Probablemente también querrá proporcionar -sslonly para evitar que x11vnc piense que el retraso en la respuesta significa que la conexión es VeNCrypt. La variable de entorno X11VNC_DISABLE_SSL_CLIENT_MODE=1 discutida anteriormente también puede ser útil (es decir, el espectador puede realizar una conexión directa como lo hace normalmente).
IPv6: a partir de x11vnc 0.9.10, la opción -connect debería conectarse a hosts IPv6 correctamente. Si hay problemas, puede deshabilitar IPv6 estableciendo -DX11VNC_IPV6=0 en CPPFLAGS al configurar. Si hay problemas para conectarse a hosts IPv6, considere un retransmisor como el script inet6to4 incluido o la opción -proxy.

-connect_or_exit str

Al igual que con -connect, excepto que si ninguna de las conexiones inversas tiene éxito, x11vnc se apaga inmediatamente.
Un alias más fácil de escribir para esta opción es '-coe'.
Por cierto, si no desea que x11vnc escuche en NINGUNA interfaz, use -rfbport 0, lo cual es útil para el modo -connect_or_exit.

-proxy string

Use el proxy en la cadena (por ejemplo, host:puerto) como proxy para realizar conexiones inversas (opciones -connect o -connect_or_exit).
Se admiten proxies web, pero tenga en cuenta que, de forma predeterminada, la mayoría de ellos solo admiten conexiones de destino a los puertos 443 o 563, por lo que esto podría no ser muy útil (el espectador necesitaría escuchar en ese puerto o el enrutador tendría que realizar una redirección de puerto).
Se puede especificar un proxy web como "host:puerto" o "http://host:port" (el puerto es obligatorio incluso si son las opciones comunes 80 u 8080).
También se admiten SOCKS4, SOCKS4a y SOCKS5. Los proxies SOCKS normalmente no tienen restricciones en el número de puerto de destino.
Use un formato como este: socks://host:puerto o socks5://host:puerto. Tenga en cuenta que ssh -D no admite SOCKS4a, así que use socks5://. Para socks:// SOCKS4 se usa en una IP numérica y "localhost", de lo contrario se usa SOCKS4a (y, por lo tanto, el proxy intenta realizar la búsqueda de DNS).
Un modo experimental es "-proxy http://host:port/...". Tenga en cuenta la "/" después del puerto que lo distingue de un proxy web normal. El puerto debe proporcionarse incluso si es el predeterminado 80. Para este modo, se realiza una solicitud GET a la URL proporcionada con la cadena host=H&port=P agregada. H y P serán el host y el puerto de conexión inversa de -connect. Use la cadena "__END__" para deshabilitar la adición. La idea básica aquí es que tal vez algún script cgi proporcione la conexión real del espectador y la canalización. Cómo lograr esto realmente dentro de cgi, php, etc. no está claro... Un servidor web personalizado o un módulo de Apache sería sencillo.
Otro modo experimental es "-proxy ssh://usuario@host", en cuyo caso se utiliza un túnel SSH para la proxy. "usuario@" no es necesario a menos que su nombre de usuario de Unix sea diferente en "host". Para un puerto SSH no estándar, use ssh://usuario@host:puerto. Si los proxies están encadenados (ver el siguiente párrafo), entonces el de SSH debe ser el primero. Si ssh-agent no está activo, la contraseña de SSH deberá ingresarse en la terminal donde se ejecuta x11vnc. Ejemplos:
-connect localhost:0 -proxy ssh://yo@amigos-pc:2222
-connect snoopy:0 -proxy ssh://ssh.empresa.com
Se pueden encadenar varios proxies en caso de que uno necesite rebotar en varios hosts para finalmente llegar al espectador VNC. Se pueden encadenar hasta 3, sepárelos por comas en el orden en que se conectarán. Por ejemplo: http://host1:port1,socks5://host2:port2 o tres como: primero,segundo,tercero
IPv6: a partir de x11vnc 0.9.10, la opción -proxy debería conectarse a hosts IPv6 correctamente. Si hay problemas, puede deshabilitar IPv6 estableciendo -DX11VNC_IPV6=0 en CPPFLAGS al configurar. Si hay problemas para conectarse a hosts IPv6, considere un retransmisor como el script inet6to4 incluido.

-vncconnect, -novncconnect

Monitorea la propiedad X VNC_CONNECT establecida por el programa VNC estándar vncconnect(1). Cuando la propiedad se establece en "host" o "host:puerto", establece una conexión inversa. Usar xprop(1) en lugar de vncconnect puede funcionar (ver el FAQ). El mecanismo de control -remote usa el canal X11VNC_REMOTE y esta opción lo deshabilita/habilita también. Predeterminado: -vncconnect
Para usar nombres diferentes para estas propiedades de X11 (por ejemplo, para tener canales de comunicación separados para varios x11vnc en la misma pantalla), establezca las variables de entorno VNC_CONNECT o X11VNC_REMOTE a la cadena que desee, por ejemplo: -env X11VNC_REMOTE=X11VNC_REMOTE_12345 Ambos lados del canal deben usar el mismo nombre único. Lo mismo se puede hacer para la propiedad interna X11VNC_TICKER (latido y marca de tiempo) si se desea.

-allow host1[,host2..]

Solo permite conexiones de clientes desde hosts que coincidan con la lista separada por comas de nombres de host o direcciones IP. También puede ser un prefijo de IP numérico, por ejemplo, "192.168.100." para coincidir con una subred simple, para un mayor control, compile LibVNCServer con soporte libwrap (Ver el FAQ). Si la lista contiene un "/", se interpreta como un archivo que contiene direcciones o prefijos que se releen cada vez que un nuevo cliente se conecta. Las líneas se pueden comentar con el carácter "#" de la forma habitual.
-allow se aplica en modo -ssl, pero no en modo -stunnel.
IPv6: a partir de x11vnc 0.9.10, un host puede especificarse en formato numérico IPv6, por ejemplo, 2001:4860:b009::93.

-localhost

Básicamente lo mismo que "-allow 127.0.0.1".
Nota: si desea restringir en qué interfaz de red escucha x11vnc, vea la opción -listen a continuación. Por ejemplo, "-listen localhost" o "-listen 192.168.3.21". Como caso especial, la opción "-localhost" implica "-listen localhost".
Un caso raro, pero para uso de -listen que no sea localhost, si usa el mecanismo de control remoto (-R) para cambiar la interfaz de -listen, es posible que deba ajustar manualmente la lista de -allow (y viceversa) para evitar situaciones en las que no se permitan conexiones (o demasiadas).
Si no desea que x11vnc escuche en NINGUNA interfaz (evidentemente está usando -connect o -connect_or_exit, o planea usar control remoto: -R connect:host), use -rfbport 0
IPv6: si se admite IPv6, esta opción implica automáticamente la dirección de bucle invertido IPv6 '::1' también.

-unixsock str

Escucha en el socket Unix (AF_UNIX) 'str' para conexiones. Este modo es para conexiones locales o un punto final de túnel donde se desea que el permiso de archivo del socket Unix determine qué puede conectarse a él. (Actualmente requiere una edición en libvnserver/rfbserver.c: comentar las líneas 310 y 311, 'close(sock)' y 'return NULL' en rfbserver.c después de la llamada setsockopt().) Tenga en cuenta que para deshabilitar todos los puertos de escucha TCP, especifique '-rfbport 0' y debería ser útil con este modo. Ejemplo: mkdir ~/s; chmod 700 ~/s; x11vnc -unixsock ~/s/mysock -rfbport 0 ... El espectador VNC de SSVNC puede conectarse a sockets Unix.

-listen6 str

Cuando está en modo de escucha IPv6 "-6", escucha solo en la interfaz de red con la dirección str. También funciona para direcciones de alcance de enlace (fe80::219:dbff:fee5:3f92%eth0) y cadenas de nombres de host IPv6 (por ejemplo, ipv6.google.com.). Use la opción -listen de LibVNCServer para la interfaz IPv4.

-nolookup

No utilice gethostbyname() o gethostbyaddr() para buscar nombres de host o números IP. Úselo si la resolución de nombres está configurada incorrectamente y provoca largas pausas a medida que las búsquedas de nombres expiran, etc.

-input string

Ajuste fino de la entrada de usuario permitida. Si string no contiene una coma ",", la configuración se aplica solo a los clientes normales. De lo contrario, la parte anterior a "," es para clientes normales y la parte posterior para clientes de solo visualización. "K" es para entrada de Teclado, "M" para entrada de Movimiento del Ratón, "B" para entrada de Botón (clic), "C" es para entrada del Portapapeles y "F" es para Transferencia de Archivos (solo ultravnc). Su presencia en la cadena habilita ese tipo de entrada. Por ejemplo, "-input M" significa que los usuarios normales solo pueden mover el ratón y "-input KMBCF,M" permite a los usuarios normales hacer cualquier cosa y permite a los usuarios de solo visualización mover el ratón. Esta opción se ignora cuando está activo un -viewonly global (en ese caso, se descarta toda la entrada).

-grabkbd

Cuando los espectadores VNC están conectados, intente capturar el teclado para que un usuario (no malicioso) sentado en la pantalla física no pueda ingresar pulsaciones de teclas. Este método utiliza XGrabKeyboard(3X11) y, por lo tanto, no es seguro y no descarta la posibilidad de que la persona en la pantalla física inyecte pulsaciones de teclas inundando el servidor con ellas, capturando el teclado él mismo, etc. Se asume cierto grado de cooperación por parte de la persona en la pantalla. Esto está destinado a modos de asistencia remota o uso educativo.
Nota: en algunos servidores X y/o escritorios recientes (12/2010), -grabkbd ya no funciona: impide que el administrador de ventanas redimensione ventanas y cosas similares. Pruebe -ungrabboth
abajo (puede que no funcione).

-grabptr

Igual que -grabkbd, pero para el puntero del ratón usando XGrabPointer(3X11). Desafortunadamente, debido a cómo funciona el servidor X, el usuario todavía puede mover el ratón en la pantalla física, pero no podrá cambiar el foco de la ventana con él. Además, algunos gestores de ventanas que llaman a XGrabServer(3X11) para redimensionar, etc., actuarán sobre la entrada del usuario local. De nuevo, se asume un cierto grado de cooperación de la persona en la pantalla.

-ungrabboth

Cada vez que haya alguna entrada (ya sea del teclado o del puntero), suelta *tanto* el teclado como el puntero mientras inyecta la entrada sintética. Esto es para dar a los gestores de ventanas, etc., una oportunidad de agarrar.

-grabalways

Aplica tanto -grabkbd como -grabptr incluso cuando no hay visualizadores VNC conectados. Si solo deseas uno de ellos, usa el control remoto -R para reactivar el otro, por ejemplo, -R nograbptr.

-viewpasswd cadena

Proporciona una segunda contraseña para inicios de sesión de solo vista. También debe proporcionarse la contraseña -passwd (acceso completo).

-passwdfile nombrearchivo

Especifica la contraseña de LibVNCServer a través de la primera línea del archivo nombrearchivo (en lugar de a través de -passwd en la línea de comandos, donde otros podrían verla a través de ps(1) ).
Consulta las descripciones a continuación para saber cómo proporcionar múltiples contraseñas, contraseñas de solo vista, especificar programas externos para la autenticación y otras características.
Si el nombre del archivo va precedido de "rm:", se eliminará después de leerlo. Quizás esto sea útil para limitar la legibilidad del archivo. En general, el archivo de contraseñas no debe ser legible por usuarios no confiables (por cierto: el archivo -rfbauth de VNC tampoco: NO está cifrado, solo ofuscado con una clave fija).
Si el nombre del archivo va precedido de "read:", se comprobará periódicamente si hay cambios y se volverá a leer. Se garantiza que se volverá a leer justo cuando se conecte un nuevo cliente para que se utilicen las últimas contraseñas.
Si nombrearchivo va precedido de "cmd:", entonces la cadena después de los ":" se ejecuta como un comando externo: la salida del comando se interpretará como si se hubiera leído de un archivo de contraseñas (ver abajo). Si el comando no sale con 0, entonces x11vnc termina inmediatamente. Para especificar más de 1000 contraseñas de esta manera, establece X11VNC_MAX_PASSWDS antes de iniciar x11vnc. Las variables de entorno se establecen como en -accept.
Ten en cuenta que debido al protocolo VNC, solo se utilizan los primeros 8 caracteres de una contraseña (clave DES).
Si nombrearchivo va precedido de "custom:", entonces se proporciona un verificador de contraseñas personalizado como un comando externo después de los ":". El comando se ejecutará cuando un cliente se autentique. Si el comando sale con 0, el cliente es aceptado; de lo contrario, es rechazado. Las variables de entorno se establecen como en -accept.
La entrada estándar para el comando personalizado será un dígito decimal "len" seguido de una nueva línea. "len" especifica el tamaño del desafío y suele ser 16 (la especificación VNC). Luego siguen len bytes que es la cadena de desafío aleatoria que se envió al cliente. Esto va seguido de otros len bytes que contienen la respuesta del cliente (es decir, la cadena de desafío cifrada mediante DES con la contraseña de usuario en la situación estándar).
El esquema "custom:" puede ser útil para implementar contraseñas dinámicas o para implementar métodos donde se utilizan contraseñas más largas y/o algoritmos de cifrado diferentes. Esto último requerirá personalizar también el cliente VNC. Se podría crear un esquema basado en MD5SUM, por ejemplo.
Formato de archivo para -passwdfile:
Si existen múltiples líneas no en blanco en el archivo, todas se toman como contraseñas válidas. Las líneas en blanco se ignoran. Las líneas de contraseña pueden ser "comentadas" (ignoradas) si comienzan con el carácter "#" o si la línea contiene la cadena "__SKIP__". Las líneas pueden ser anotadas mediante la cadena " __COMM__ ": desde ella hasta el final de la línea se ignora. Una contraseña vacía puede especificarse mediante la cadena "__EMPTY__" en una línea por sí sola (ten en cuenta que tu visor podría no aceptar contraseñas vacías).
Si la cadena "__BEGIN_VIEWONLY__" aparece en una línea por sí sola, las contraseñas restantes se utilizan para acceso de solo vista. Para compatibilidad, como caso especial si el archivo contiene solo dos líneas de contraseña, la segunda se toma automáticamente como la contraseña de solo vista. De lo contrario, se debe usar el token "__BEGIN_VIEWONLY__" para tener contraseñas de solo vista. (consejo: haz que la tercera y última línea sea "__BEGIN_VIEWONLY__" para tener 2 contraseñas de acceso completo)

-showrfbauth nombrearchivo

Imprime en la pantalla la contraseña VNC ofuscada que se encuentra en el archivo rfbauth nombrearchivo y luego sale.

-unixpw [lista]

Utiliza autenticación de nombre de usuario y contraseña de Unix. x11vnc utilizará el programa su(1) para verificar la contraseña del usuario. [lista] es una lista opcional separada por comas de nombres de usuario de Unix permitidos. Si la cadena [lista] comienza con el carácter "!", entonces toda la lista se toma como una lista de exclusión. Ver abajo para opciones por usuario que se pueden aplicar.
Se presenta un diálogo familiar de "login:" y "Password:" al usuario en una pantalla negra dentro del vncviewer. La conexión se interrumpe si el usuario no proporciona la contraseña correcta en 3 intentos o no envía una antes de un tiempo de espera de 45 segundos. Los clientes existentes son de solo vista durante este período.
Si el primer carácter recibido es "Escape", el nombre de usuario de Unix no se mostrará después de "login:" a medida que se escribe. Esto podría ser útil para visores VNC que escriben automáticamente el nombre de usuario y la contraseña.
Dado que el comportamiento detallado de su(1) puede variar entre sistemas operativos y configuraciones locales, prueba el modo antes de implementarlo para asegurarte de que funciona correctamente. x11vnc intentará ser conservador y rechazar un inicio de sesión si ocurre algo anormal.
Un caso a tener en cuenta: en FreeBSD y otros BSD, por defecto es imposible que el usuario que ejecuta x11vnc valide su *propia* contraseña a través de su(1) (comentar la entrada pam_self.so en /etc/pam.d/su elimina este comportamiento). Por lo tanto, el inicio de sesión de x11vnc *fallará* siempre en este caso (incluso cuando se proporcione la contraseña correcta).
Una posible solución alternativa en *BSD sería iniciar x11vnc como root con la opción "-users +nobody" para cambiar inmediatamente al usuario nobody, donde la ejecución de su procederá normalmente.
Otra fuente de posibles problemas son los módulos PAM que solicitan información adicional, por ejemplo, módulos de caducidad de contraseña. Estos inicios de sesión también fallarán incluso cuando se proporcione la contraseña correcta.
**IMPORTANTE**: para evitar que la contraseña de Unix se envíe en *texto plano* a través de la red, se aplicará uno de los dos esquemas: 1) el modo SSL integrado -ssl, o 2) exigir que tanto -localhost como -stunnel estén habilitados.
El Método 1) garantiza que el tráfico esté cifrado entre el visor y el servidor. Se requerirá un archivo PEM, consulta la discusión en -ssl a continuación (bajo ciertas circunstancias, se puede generar uno temporalmente de forma automática).
El Método 2) requiere que la conexión del visor parezca provenir de la misma máquina en la que se está ejecutando x11vnc (por ejemplo, desde una redirección de puerto -L de ssh(1)). Y que se utilice el modo SSL -stunnel para el cifrado a través de la red. (ver la descripción de -stunnel a continuación).
Nota: como conveniencia, si te conectas por ssh(1) e inicias x11vnc, comprobará si la variable de entorno SSH_CONNECTION está establecida y parece razonable. Si es así, se eliminará el requisito de -ssl o -stunnel, ya que se asume que estás utilizando ssh para la tunelización cifrada. Todavía se aplica -localhost. Utiliza -ssl o -stunnel para forzar el uso de SSL incluso si SSH_CONNECTION está establecida.
Para anular las restricciones anteriores, puedes establecer variables de entorno antes de iniciar x11vnc:
Establece UNIXPW_DISABLE_SSL=1 para deshabilitar la exigencia de -ssl o -stunnel (como en SSH_CONNECTION.) Evidentemente, utilizarás un método diferente para cifrar los datos entre el vncviewer y x11vnc: quizás ssh(1) o una VPN IPSEC. Todavía se aplica -localhost (sin embargo, ver el siguiente párrafo.)
Establece UNIXPW_DISABLE_LOCALHOST=1 para deshabilitar el requisito de -localhost en los modos -unixpw. Uno nunca debería hacer esto (es decir, permitir que las contraseñas de Unix sean esnifadas en la red). Esto también deshabilita el requisito de localhost para conexiones inversas (ver abajo).
Ten en cuenta que el uso de -localhost con ssh(1) (y sin -unixpw) es aproximadamente lo mismo que exigir un inicio de sesión de usuario de Unix (ya que sshd en la máquina donde se ejecuta x11vnc utiliza una contraseña de Unix o la autenticación de clave pública del usuario y solo se aceptan conexiones locales desde esa máquina).
Con respecto a las conexiones inversas (por ejemplo, -R connect:host y -connect host), cuando la restricción -localhost está en vigor, las conexiones inversas solo se pueden utilizar para conectarse a la misma máquina en la que se está ejecutando x11vnc (puerto 5500 por defecto). Utiliza una redirección de puerto ssh o stunnel a la máquina del visor para tunelizar la conexión inversa a través de un canal cifrado.
En el modo -inetd se aplicará el Método 1) (no el Método 2). Con -ssl en vigor, las conexiones inversas están deshabilitadas. Los nombres de usuario en la [lista] separada por comas pueden tener opciones por usuario después de ":", por ejemplo, "fred:opts" donde "opts" es una lista separada por "+" de "viewonly", "fullaccess", "input=XXXX", o "deny", por ejemplo, "karl,wally:viewonly,boss:input=M". Para "input=" son K,M,B,C descritos bajo -input.
Si un elemento de la lista es "*", eso significa que esas opciones se aplican a todos los usuarios. TAMBIÉN implica que todos los usuarios pueden iniciar sesión después de proporcionar una contraseña válida. Utiliza "de
ny" para denegar explícitamente a algunos usuarios si utiliza "*" para establecer una opción global. Si [lista] comienza con el carácter "!" entonces "*" se ignora para verificar si el usuario está permitido, pero los valores de las opciones asociados con él se aplican como normal.
También hay algunas utilidades para verificar contraseñas si [lista] comienza con el carácter "%". Consulte la función quick_pw() para obtener más detalles. Descripción: "%-" o "%stdin" significa leer una línea de stdin. "%env" significa que está en la variable de entorno $UNIXPW. Un "%/" o "%." inicial significa leer la primera línea del nombre de archivo que sigue después del carácter %. % por sí solo significa solicitar el nombre de usuario y la contraseña. De lo contrario: %usuario:contraseña Ejemplo: -unixpw %fred:swordfish Para los otros casos, usuario:contraseña se lee de la fuente indicada. Si la contraseña es correcta, se imprime "Y usuario" y el programa el código de salida es 0. Si la contraseña es incorrecta, imprime "N usuario" y el código de salida es 1. Si hay algún otro error, el código de salida es 2. Esta característica permite que x11vnc sea una herramienta general de verificación de contraseñas de usuarios de Unix; podría usarse desde scripts u otros programas. Estas comprobaciones de contraseña % también se aplican a las opciones -unixpw_nis y -unixpw_cmd.
Para la verificación de contraseña %, si la variable de entorno UNIXPW_CMD se establece en un comando, entonces se ejecuta como el usuario (suponiendo que la contraseña sea correcta). La salida del comando no se imprime, el programa o script debe gestionarla por algún otro medio. El código de salida de x11vnc dependerá del código de salida del comando que se ejecute.
Use -nounixpw para deshabilitar el modo unixpw si se habilitó anteriormente en la línea de comandos (por ejemplo, modo -svc)

-unixpw_nis [lista]

Igual que -unixpw arriba, sin embargo, no use su(1) sino que use el método tradicional getpwnam(3) + crypt(3) para verificar contraseñas. Se aplican todas las opciones y restricciones de -unixpw anteriores.
Este modo requiere que las contraseñas cifradas sean legibles. Las contraseñas cifradas almacenadas en /etc/shadow serán inaccesibles a menos que x11vnc se ejecute como root.
Este modo se llama "NIS" simplemente porque en la mayoría de las configuraciones NIS, las contraseñas cifradas de los usuarios son accesibles (por ejemplo, "ypcat passwd") por un usuario ordinario y, por lo tanto, ese usuario puede autenticar a CUALQUIER usuario.
NIS no es necesario para que este modo funcione (solo se requiere que getpwnam(3) devuelva la contraseña cifrada), pero es poco probable que funcione (como usuario ordinario) para la mayoría de los entornos modernos a menos que NIS esté disponible. Por otro lado, cuando x11vnc se ejecuta como root, podrá acceder a /etc/shadow incluso si NIS no está disponible (tenga en cuenta que ejecutar como root a menudo se hace al ejecutar x11vnc desde inetd y xdm/gdm/kdm).
Visto de otra manera, si no desea utilizar el método su(1) proporcionado por -unixpw (es decir, su_verify()), puede ejecutar x11vnc como root y usar -unixpw_nis. Cualquier usuario con contraseñas en /etc/shadow podrá ser autenticado.
En el modo -unixpw_nis, bajo ninguna circunstancia se llama a la función de verificación de contraseñas de usuario de x11vnc basada en su (es decir, la función su_verify() que ejecuta /bin/su en una pseudoterminal para verificar contraseñas). Sin embargo, si -unixpw_nis se usa junto con los modos -find y -create -display WAIT:..., entonces, si x11vnc se ejecuta como root, /bin/su puede ser llamado externamente para ejecutar los comandos find o create.

-unixpw_cmd cmd

Igual que -unixpw arriba, sin embargo, no use su(1) sino que ejecute el comando suministrado externamente cmd. La primera línea de su entrada estándar será el nombre de usuario y la segunda línea la contraseña recibida. Si el comando sale con estado 0 (éxito), el usuario VNC será aceptado. Será rechazado para cualquier otro estado de retorno.
Las contraseñas dinámicas y las contraseñas no Unix, por ejemplo, LDAP, se pueden implementar de esta manera proporcionando su propio programa auxiliar personalizado. Tenga en cuenta que al visor remoto se le dan 3 intentos para ingresar la contraseña correcta, y por lo tanto, el programa puede ser llamado en secuencia varias veces (o más).
Si se necesita una lista de usuarios permitidos para limitar quién puede iniciar sesión, use -unixpw [lista] además de esta opción.
En los modos FINDDISPLAY y FINDCREATEDISPLAY, el cmd también se ejecutará con la variable de entorno RFB_UNIXPW_CMD_RUN establecida y no vacía, correspondiente al comando de búsqueda/creación de pantalla. Las dos primeras líneas de entrada son el nombre de usuario y la contraseña, como en el caso normal descrito anteriormente. Para admitir FINDDISPLAY y FINDCREATEDISPLAY, cmd debe ejecutar el comando solicitado como el usuario (y lo más probable es que se niegue a ejecutarlo si la contraseña no es correcta). Aquí hay un script de ejemplo (¡tenga en cuenta que tiene una contraseña ficticia codificada "abc"!)
#!/bin/sh # Ejemplo de script x11vnc -unixpw_cmd. # Leer las dos primeras líneas de stdin (usuario y contraseña) leer usuario leer contraseña
debug=0 si [ $debug = 1 ]; entonces eco "usuario: $user" 1>&2 echo "contraseña: $pass" 1>&2 env | egrep -i 'rfb|vnc' 1>&2 fi
# Verificar si la contraseña es válida. # (¡Un ejemplo real usaría búsqueda ldap, etc.!) si [ "X$pass" != "Xabc" ]; entonces salir 1 # contraseña incorrecta fi
si [ "X$RFB_UNIXPW_CMD_RUN" = "X" ]; entonces salir 0 # contraseña correcta sino # Ejecutar el comando solicitado (finddisplay) si [ $debug = 1 ]; entonces echo "ejecutar: $RFB_UNIXPW_CMD_RUN" 1>&2 fi exec /bin/su - "$user" -c "$RFB_UNIXPW_CMD_RUN" fi
En el modo -unixpw_cmd, bajo ninguna circunstancia se llama a la función de verificación de contraseñas de usuario de x11vnc basada en su (es decir, la función su_verify() que ejecuta /bin/su en una pseudoterminal para verificar contraseñas). -vencrypt modo

La extensión VeNCrypt del protocolo VNC permite conexiones cifradas SSL/TLS. Si el modo -ssl está habilitado, entonces VeNCrypt también está habilitado POR DEFECTO (ambos usan un túnel SSL/TLS, solo el apretón de manos del protocolo es un poco diferente).
Para controlar cuándo y cómo se utiliza VeNCrypt, especifique la cadena de modo. Si el modo es "never", entonces VeNCrypt no se utiliza. Si el modo es "support" (el valor predeterminado), entonces VeNCrypt es compatible. Si el modo es "only", entonces el protocolo ANONTLS similar y más antiguo no se admite simultáneamente. El modo SSL normal de x11vnc (vncs://) será compatible con -ssl a menos que establezca el modo en "force".
Si el modo está precedido por "nodh:", entonces el intercambio de claves anónimo Diffie Hellman está deshabilitado. Si el modo está precedido por "nox509:", entonces el intercambio de claves X509 está deshabilitado.
Para deshabilitar todo el acceso anónimo Diffie-Hellman (susceptible a ataques Man-In-The-Middle), necesitará suministrar "-vencrypt nodh:support -anontls never" o "-vencrypt nodh:only".
Si el modo está precedido por "newdh:", entonces se generan nuevos parámetros Diffie Hellman para cada conexión (esto puede consumir tiempo: 1-60 segundos; ver -dhparams abajo para una forma más rápida) en lugar de usar los valores fijos en el programa. El uso de valores fijos y públicamente conocidos no se conoce como un problema de seguridad. Esta configuración se aplica también a ANONTLS.
Ejemplo largo: -vencrypt newdh:nox509:support
Además, si el modo está precedido por "plain:", entonces si el modo -unixpw está activo, se habilita el método VeNCrypt " *Plain" de nombre de usuario + contraseña para inicios de sesión Unix. De lo contrario, en el modo -unixpw se proporciona el panel de inicio de sesión normal.
DEBE suministrar la opción -ssl para que VeNCrypt esté activo. La opción -vencrypt solo ajusta su funcionamiento.

Si el modo va precedido por "newdh:", entonces se generan nuevos parámetros Diffie Hellman para cada conexión (esto puede consumir tiempo: 1-60 seg; vea -dhparams a continuación para una forma más rápida) en lugar de usar los valores fijos en el programa. El uso de valores fijos y públicamente conocidos no se considera un problema de seguridad. Esta configuración también se aplica a VeNCrypt. Vea la descripción de "plain:" en -vencrypt.
Ejemplo largo: -anontls newdh:plain:support
DEBE proporcionar la opción -ssl para que ANONTLS esté activo. La opción -anontls solo ajusta su operación.

-sslonly

Igual que: "-vencrypt never -anontls never" es decir, deshabilita los métodos de cifrado VeNCrypt y ANONTLS y solo permite el túnel SSL estándar. También debe proporcionar la opción -ssl ... (ver más abajo).

-dhparams file

Para algunas operaciones se necesita un conjunto de parámetros Diffie Hellman (primo y generador). Si es así, utilice los parámetros en file. En particular, VeNCrypt y el modo DH anónimo de ANONTLS los necesitan. Por defecto se usa un conjunto fijo. Si no desea hacer eso, puede especificar "newdh:" a las opciones -vencrypt y -anontls para generar un nuevo conjunto cada sesión. Si eso es demasiado lento para usted, use -dhparams file para un conjunto que creó manualmente a través de "openssl dhparam -out file 1024"

-nossl

Deshabilita la opción -ssl (ver más abajo). Dado que -ssl está desactivado por defecto, -nossl solo se usaría en la línea de comandos para anular cualquier opción -ssl *anterior* (o -svc...)

-ssl [pem]

Utiliza la biblioteca openssl (www.openssl.org) para proporcionar un túnel SSL/TLS cifrado integrado entre los espectadores VNC y x11vnc. Esto requiere que el soporte de libssl se compile en x11vnc en el momento de la compilación. Si x11vnc no está compilado con soporte de libssl, saldrá inmediatamente cuando se prescriba -ssl. Vea la opción -stunnel a continuación para una alternativa.
El lado del espectador VNC también debe admitir SSL/TLS. Vea esta URL y también la discusión a continuación para obtener ideas sobre cómo habilitar el soporte SSL para el espectador: http://www.karlrunge.com/x11vnc/faq.html#faq-ssl-tun nel-viewers. x11vnc proporciona un applet de espectador Java habilitado para SSL en el directorio classes/ssl (-http o las opciones -httpdir). El paquete de espectador SSVNC también admite túneles SSL.
Si el espectador VNC admite VeNCrypt o ANONTLS (modo de cifrado de vino), también son compatibles con el modo -ssl (vea las opciones -vencrypt y -anontls para más información; use -sslonly para deshabilitar ambos).
Utilice "-ssl /ruta/a/mi_certificado.pem" para especificar un archivo de certificado SSL en formato PEM para usarlo para identificar y proporcionar una clave para este servidor. Vea openssl(1) para más información sobre PEM y las opciones -sslGenCert y "-ssl SAVE" a continuación sobre cómo crearlos.
El túnel SSL del espectador VNC que se conecta puede (a su opción) autenticar este servidor si tiene la parte de clave pública del certificado (o una autoridad certificadora, CA, común es una forma más sofisticada de verificar el certificado de este servidor, vea -sslGenCA a continuación). Esta autenticación se realiza para prevenir ataques Man-In-The-Middle. De lo contrario, si el espectador VNC simplemente acepta la clave de este servidor SIN verificación, el tráfico está protegido contra la escucha pasiva en la red, pero *NO* contra ataques Man-In-The-Middle. Existen herramientas de hackers como dsniff/webmitm y cain que implementan ataques SSL Man-In-The-Middle.
Si [pem] está vacío o es la cadena "SAVE", entonces el comando openssl(1) debe estar disponible para generar el certificado la primera vez. Se genera un certificado autofirmado (vea -sslGenCA y -sslGenCert para el uso de una Autoridad Certificadora). Se guardará en el archivo ~/.vnc/certs/server.pem. En llamadas posteriores, si ese archivo ya existe, se usará directamente.
Use "SAVE_NOPROMPT" para evitar que se le solicite proteger la clave generada con una contraseña. Sin embargo, en los modos -inetd y -bg no habrá solicitud de contraseña en ningún caso.
Si [pem] es "SAVE_PROMPT", el certificado server.pem se creará en base a sus respuestas a sus indicaciones para toda la información, como OrganizationalName, CommonName, etc.
Use "SAVE-<string>" y "SAVE_PROMPT-<string>" para referirse al archivo ~/.vnc/certs/server-<string>.pem en su lugar (se generará si no existe). Por ejemplo, "SAVE-charlie" guardará en el archivo ~/.vnc/certs/server-charlie.pem
Ejemplos: x11vnc -ssl SAVE -display :0 ... x11vnc -ssl SAVE-someother -display :0 ...
Si [pem] es "TMP" y el comando de utilidad openssl(1) existe en PATH, entonces se generará un certificado temporal y autofirmado para esta sesión. Si openssl(1) no se puede usar para generar un certificado temporal, x11vnc sale inmediatamente. El certificado temporal se descartará cuando x11vnc salga.
Si tiene éxito al usar openssl(1) para generar un certificado temporal en los modos de creación "SAVE" o "TMP", la parte pública se mostrará en stderr (por ejemplo, se podría copiar al lado del cliente para proporcionar autenticación del servidor a los espectadores VNC).
NOTA: En el modo "TMP", a menos que copie de forma segura la parte pública del Certificado temporal al espectador para autenticar *cada vez* (poco probable...), solo se evitan los ataques de escucha pasiva y aún está expuesto a ataques Man-In-The-Middle. Es por eso que se prefiere el modo "SAVE" predeterminado (y también el modo CA más sofisticado). Solo con claves guardadas Y el espectador VNC autenticándolas (a través del certificado público), se previenen los ataques Man-In-The-Middle.
Si [pem] es "ANON", entonces se utiliza el método de intercambio de claves anónimo Diffie-Hellman. En este modo *no* hay certificados SSL y, por lo tanto, no es posible autenticar ni el servidor VNC ni el cliente VNC. Por lo tanto, solo se evitan los ataques de escucha de red pasiva: el método "ANON" es susceptible a ataques Man-In-The-Middle. "ANON" no se recomienda; en su lugar, utilice un PEM SSL que haya creado o el método predeterminado "SAVE".
Vea -ssldir a continuación para usar un directorio además del predeterminado ~/.vnc/certs
Si su binario x11vnc no fue compilado con soporte de biblioteca OpenSSL, el uso de la opción -ssl provocará un fallo inmediato y la salida. Para dichos binarios, considere usar la opción -stunnel para conexiones cifradas SSL.
Información miscelánea: En el modo de creación de certificado temporal "TMP", establezca la variable de entorno X11VNC_SHOW_TMP_PEM=1 para que x11vnc imprima todo el certificado, incluida la parte de CLAVE PRIVADA, en stderr. Hay mejores maneras de obtener/guardar esta información. Vea "SAVE" arriba y "-sslGenCert" a continuación.

-ssltimeout n

Establece el tiempo de espera de lectura SSL en n segundos. En algunas situaciones (es decir, un espectador iconizado en Windows), el espectador deja de comunicarse y la conexión se interrumpe después del tiempo de espera predeterminado (25 s durante aproximadamente el primer minuto, 43200 s después). Establézcalo en cero para sondear indefinidamente. Establézcalo en un valor negativo para usar la configuración integrada.
Tenga en cuenta que este valor NO se aplica a la conexión inicial de inicialización ssl. El tiempo de espera predeterminado para eso es 20 segundos. Use -env SSL_INIT_TIMEOUT=n para modificarlo.

-sslnofail

Salga ante el primer fallo de conexión SSL. Útil al escribir scripts de conexiones SSL (por ejemplo, x11vnc se inicia a través de ssh) y no desea que x11vnc espere más conexiones, ocupando puertos, etc.

-ssldir dir

Use dir como un directorio de nivel superior alternativo para la gestión de certificados y claves SSL. El predeterminado es ~/.vnc/certs
Este directorio se utiliza para almacenar certificados y claves del servidor y otros, así como otros materiales. Por ejemplo, en el caso más simple, "-ssl SAVE" almacenará el certificado del servidor x11vnc en dir/server.pem
El uso de directorios alternativos a través de -ssldir le permite gestionar múltiples claves de Autoridad Certificadora (CA) de VNC. Otro uso es si ~/.vnc/cert está en un recurso compartido NFS, es posible que desee que sus certificados y claves estén en un sistema de archivos local para evitar el espionaje de red (por ejemplo, -ssldir /var/lib/x11vnc-certs).
-ssldir afecta a casi todas las demás opciones -ssl*, por ejemplo, -ssl SAVE, -sslGenCert, etc.

-sslverify path

Para cualquiera de los modos -ssl o -stunnel, use path para proporcionar certificados para autenticar las conexiones entrantes de *Clientes* VNC (normalmente solo el servidor se autentica en SSL). Esto se puede usar como un método para reemplazar la autenticación estándar por contraseña de los clientes.
Si path es un directorio, contiene los certificados de cliente (o CA) en archivos separados. Si path es un archivo, contiene uno o más certificados. Vea los tokens especiales a continuación. Estos corresponden a las opciones de stunnel "CApath = dir" y "CAfile = file". Vea la página del manual de stunnel(8) para más detalles.
Ejemplos: x11vnc -ssl -sslverify ~/my.crt x11vnc -ssl
... ... ... ... openssl(1) stunnel(8) -sslverify ~/my_pem_dir/
Tenga en cuenta que si la ruta es un directorio, debe contener los certificados en archivos separados llamados como <HASH>.0, donde el valor de <HASH> se encuentra ejecutando el comando "openssl x509 -hash -noout -in file.crt". Evidentemente, uno usa <HASH>.1 si hay una colisión...
La utilidad de gestión de claves "-sslCertInfo HASHON" y "-sslCertInfo HASHOFF" creará/eliminará estos hashes automáticamente (mediante enlaces simbólicos) en los subdirectorios HASH que gestiona. Luego puede apuntar -sslverify al subdirectorio HASH.
Tokens especiales: en modo -ssl, si ruta no es un archivo o un directorio, se toma como una lista de tokens separada por comas que se interpretan de la siguiente manera:
Si un token es "CA", significa cargar el archivo CA/cacert.pem del directorio ssl. Si un token es "clients", entonces se cargan todos los archivos clients/*.crt en el directorio ssl. De lo contrario, se intenta cargar el archivo clients/token.crt. Como solución provisional, utilice un token como ../server-foo para cargar un certificado de servidor si lo considera necesario.
Use -ssldir para usar un directorio diferente al predeterminado de ~/.vnc/certs.
Tenga en cuenta que si se carga el certificado "CA", no necesita cargar ninguno de los certificados que han sido firmados por él. Sin embargo, necesitará cargar cualquier certificado autofirmado adicional.
Ejemplos: x11vnc -ssl -sslverify CA x11vnc -ssl -sslverify self:fred,self:jim x11vnc -ssl -sslverify CA,clients
Por lo general, "-sslverify CA" es lo más eficaz. Consulte las opciones -sslGenCA y -sslGenCert a continuación para saber cómo configurar y gestionar el marco de la CA.
NOTA: las siguientes utilidades, -sslGenCA, -sslGenCert, -sslEncKey, -sslCertInfo, y -sslCRL se proporcionan por completitud, pero para un uso casual son excesivas.
Proporcionan la creación de claves de Autoridad de Certificación (CA) de VNC y la generación y firma de claves de servidor/cliente. Por lo tanto, proporcionan un marco básico de gestión de Claves Públicas para VNC con x11vnc. (tenga en cuenta que requieren openssl(1) instalado en el sistema)
Sin embargo, el modo de uso más simple, "-ssl TMP" (donde x11vnc genera automáticamente su propia clave temporal autofirmada y los visores VNC siempre la aceptan, por ejemplo, aceptándola a través de un cuadro de diálogo) es probablemente lo suficientemente seguro para la mayoría de los escenarios. No se necesita gestión de CA.
Para protegerse contra ataques Man-In-The-Middle, el modo "TMP" puede mejorarse utilizando "-ssl SAVE" (igual que "-ssl", es decir, el valor predeterminado) para que x11vnc cree un certificado autofirmado a más largo plazo, y luego copie (de forma segura) la clave pública correspondiente al certificado a las máquinas cliente deseadas (se debe tener cuidado de que no se robe la parte privada de la clave; se le pedirá una contraseña).
Así que tenga en cuenta que no se necesita creación ni gestión de claves de CA (-sslGenCA y -sslGenCert) para ninguno de los dos modos de uso comunes anteriores.
Uno podría querer usar -sslGenCA y -sslGenCert si tuviera un gran número de estaciones de trabajo cliente y servidor VNC. De esta manera, el administrador podría generar una única clave de CA con -sslGenCA y distribuir su certificado a todas las estaciones de trabajo.
A continuación, podría crear claves de servidor VNC firmadas (-sslGenCert server ...) para cada estación de trabajo o usuario que x11vnc utilizaría para autenticarse ante cualquier cliente VNC que tenga el certificado de CA.
Opcionalmente, el administrador también podría hacer que los clientes VNC se autentiquen ante x11vnc (-sslGenCert client ...) Para esto, -sslverify se apuntaría al certificado de CA (y/o certificados autofirmados).
x11vnc podrá utilizar todos estos archivos de certificado y clave. En el lado del cliente VNC, necesitarán ser "importados" de alguna manera. Los navegadores web tienen acciones de "Gestionar certificados", al igual que el Panel de Control del plugin del applet de Java. stunnel también puede usar estos archivos (consulte el script de ejemplo ss_vncviewer en la FAQ y SSVNC.)

-sslCRL ruta

Establece las Listas de Revocación de Certificados (CRL) en ruta. Esta configuración se aplica tanto a los modos -ssl como -stunnel.
Si la ruta es un archivo, el archivo contiene una o más CRL en formato PEM. Si la ruta es un directorio, contiene archivos con nombres hash de CRL de la manera habitual de OpenSSL. Consulte la documentación de OpenSSL y stunnel(8) para más información.
Esta opción solo se aplica si se ha proporcionado -sslverify: verifica la revocación a lo largo de la cadena de certificados utilizada para verificar el cliente VNC. La configuración -sslCRL se ignorará cuando no se especifique -sslverify.
Tenga en cuenta que si la fecha de caducidad de una CRL ha pasado, todas las conexiones SSL fallarán independientemente de si están relacionadas con el sujeto de la CRL o no.
Solo en raras ocasiones la infraestructura -ssl de x11vnc será lo suficientemente grande como para que esta opción sea útil (ya que normalmente mantener el contenido del archivo o directorio -sslverify debería ser suficiente). Sin embargo, al usar x11vnc con una Autoridad de Certificación (ver -sslGenCA) para autenticar Clientes a través de SSL/TLS, la opción -sslCRL puede ser útil para revocar los certificados de los usuarios cuyas claves SSL privadas se perdieron o robaron (por ejemplo, un portátil). De esta manera, no es necesario crear una nueva CA cert+key y generar y distribuir nuevas claves de cliente firmadas a todos los usuarios.
Para crear un archivo CRL con certificados revocados, los comandos 'openssl ca -revoke ...' y 'openssl ca -gencrl ...' son útiles. (Ejecútelos en ~/.vnc/certs)

-sslGenCA [dir]

Genera tu propia clave privada de Autoridad de Certificación, certificado y otros archivos en el directorio [dir]. x11vnc luego sale.
Si no se proporciona [dir], se utiliza la configuración -ssldir o, de lo contrario, ~/.vnc/certs.
Este comando también crea directorios donde se almacenarán los certificados y claves de servidor y cliente. El programa openssl(1) debe estar instalado en el sistema y disponible en PATH.
Después de que se crean los archivos y directorios de la CA, el comando x11vnc sale; el servidor VNC no se ejecuta.
Se le pedirá información para incluir en el certificado de CA. La información no tiene que ser precisa, siempre que los clientes acepten el certificado para las conexiones VNC. También deberá proporcionar una contraseña de al menos 4 caracteres para la clave privada de la CA.
Una vez que haya generado la CA, puede distribuir su parte del certificado, [dir]/CA/cacert.pem, a otras estaciones de trabajo donde se ejecutarán los visores VNC. Será necesario "importar" este certificado en las aplicaciones, por ejemplo, Navegador web, plugin de applet de Java, stunnel, etc. A continuación, puede crear y firmar claves utilizando la CA con la opción -sslGenCert a continuación.
Ejemplos: x11vnc -sslGenCA x11vnc -sslGenCA ~/myCAdir x11vnc -ssldir ~/myCAdir -sslGenCA
(las dos últimas líneas son equivalentes)

-sslGenCert tipo nombre

Genera un certificado de servidor o cliente VNC y un par de claves privadas firmados por la CA creada previamente con -sslGenCA. El programa openssl(1) debe estar instalado en el sistema y disponible en PATH.
Después de generar el certificado, x11vnc sale; el servidor VNC no se ejecuta.
El tipo de clave a generar es la cadena tipo. Es "server" (es decir, para uso por x11vnc) o "client" (para un visor VNC). Tenga en cuenta que normalmente solo se utiliza "server": los clientes VNC se autentican mediante un método no de clave pública (por ejemplo, contraseña VNC o unix). tipo es obligatorio.
Un nombre de ejemplo arbitrario que desee asociar con la clave se proporciona mediante la cadena nombre. Puede cambiarlo en las indicaciones varias al crear la clave. nombre es opcional.
Si se deja en blanco el nombre para las claves de cliente, se utiliza "nobody". Si se deja en blanco para las claves de servidor, se crea la clave de servidor principal: "server.pem" (esta es la guardada a la que hace referencia "-ssl SAVE" cuando se inicia el servidor)
Si nombre comienza con la cadena "self:", se crea un certificado autofirmado en lugar de uno firmado por su clave de CA.
Si nombre comienza con la cadena "req:", solo se generan una clave (.key) y una *solicitud* de firma de certificado (.req). A continuación, puede enviar el archivo .req a una CA externa (incluso una profesional, por ejemplo, Thawte) y luego combinar el .key y el certificado recibido en el archivo .pem con el mismo nombre base.
La distinción entre "server" y "client" es simplemente la elección de los nombres de archivo de salida y el subdirectorio. Esto hace que la opción -ssl SAVE-nombre pueda capturar fácilmente el archivo PEM de x11vnc que esta opción genera. Y de manera similar facilita que la opción -sslverify capture sus certificados de cliente.
No hay nada especial en el nombre del archivo o la ubicación del directorio de los certificados de "server" y "client". Puede renombrar los archivos o moverlos a donde desee.
Anteceda esta opción con -ssldir [dir] para usar un directorio que no sea el predeterminado ~/.vnc/certs. Necesitará ejecutar -sslGenCA en ese directorio primero antes de realizar cualquier creación de clave -sslGenCert.
Tenga en cuenta que no puede recrear un certificado con exactamente el mismo nombre distinguido (DN) que uno existente. Para hacerlo, deberá editar el archivo [dir]/CA/index.txt para eliminar la línea.
Similar a -sslGenCA, se le pedirá que complete información que se registrará en el certificado cuando se cree.
Consejo: si conoce el nombre de host completo al que se conectarán otras personas, puede usarlo como el Nombre Común "CN" para evitar que algunas aplicaciones (por ejemplo, navegadores web y el plugin de Java) se quejen de que no coincide con el nombre de host.
También deberá proporcionar la contraseña de la clave privada de la CA para desbloquear la clave privada creada a partir de -sslGenCA. Esta clave privada se utiliza para firmar el certificado del servidor o cliente.
Los certificados de "server" pueden ser utilizados directamente por x11vnc apuntando a ellos a través de la opción -ssl [pem]. El archivo predeterminado será ~/.vnc/certs/server.pem. Este se utilizaría simplemente escribiendo
-ssl GUARDAR. El archivo pem contiene tanto el certificado como la clave privada. El archivo server.crt contiene solo el certificado.
El archivo del certificado + clave privada del "cliente" deberá ser copiado e importado en las aplicaciones del lado del visor VNC (navegador web, plugin de Java, stunnel, etc.). Una vez hecho esto, puedes eliminar el archivo de clave privada del "cliente" en esta máquina, ya que solo se necesita en el lado del visor VNC. El archivo, por ejemplo, ~/.vnc/certs/clients/.pem contiene tanto el certificado como la clave privada. El archivo .crt contiene solo el certificado.
NOTA: Es muy importante saber que se deben generar nuevas claves con una frase de contraseña. De lo contrario, si un usuario no confiable roba el archivo de clave, podría usarlo para hacerse pasar por el servidor x11vnc (o el cliente visor VNC). Se te preguntará si deseas cifrar la clave con una frase de contraseña o no. Se recomienda que lo hagas. Un inconveniente de una frase de contraseña es que debe escribirse CADA VEZ que se inicia x11vnc o la aplicación cliente.
Ejemplos:
x11vnc -sslGenCert server x11vnc -ssl GUARDAR -display :0 ...
y luego en el visor usando el envoltorio stunnel ss_vncviewer (ver el FAQ): ss_vncviewer -verify ./cacert.crt hostname:0
(esto asume que el certificado cacert.crt de -sslGenCA fue copiado de forma segura a la máquina del visor VNC donde se ejecuta ss_vncviewer)
Ejemplo usando un nombre:
x11vnc -sslGenCert server charlie x11vnc -ssl GUARDAR-charlie -display :0 ...
Ejemplo para un certificado de cliente (raramente usado):
x11vnc -sslGenCert client roger scp ~/.vnc/certs/clients/roger.pem somehost:. rm ~/.vnc/certs/clients/roger.pem
x11vnc se inicia entonces con la opción -sslverify ~/.vnc/certs/clients/roger.crt (o simplemente -sslverify roger), y en el visor, el usuario en somehost podría hacer, por ejemplo:
ss_vncviewer -mycert ./roger.pem hostname:0
Si estableces la variable de entorno REQ_ARGS='...' se pasará a openssl req(1). Un uso común sería REQ_ARGS='-days 1095' para aumentar la fecha de caducidad (3 años en este caso).

-sslEncKey pem

Utilidad para cifrar un archivo PEM existente con una frase de contraseña que proporciones cuando se te solicite. Para que esa clave se pueda usar (por ejemplo, por x11vnc), la frase de contraseña debe proporcionarse cada vez.
La notación "GUARDAR" descrita en -ssl también se aplica. (precede esta opción con -ssldir [dir] para referirte a un directorio además del predeterminado ~/.vnc/certs)
El programa openssl(1) debe estar instalado en el sistema y disponible en PATH. Después de que el archivo de Clave se cifre, el comando x11vnc sale; el servidor VNC no se ejecuta.
Ejemplos: x11vnc -sslEncKey /ruta/a/foo.pem x11vnc -sslEncKey GUARDAR x11vnc -sslEncKey GUARDAR-charlie

-sslCertInfo pem

Muestra información sobre un archivo PEM existente. Además, también se muestra el certificado público. El programa openssl(1) debe estar en PATH. Básicamente, se ejecuta el comando "openssl x509 -text" sobre el pem.
Después de mostrar la información, el comando x11vnc sale; el servidor VNC no se ejecuta.
La notación "GUARDAR" descrita en -ssl también se aplica.
Usar "LISTAR" proporcionará una lista de todos los certificados que se están gestionando (en el directorio ~/.vnc/certs, usa -ssldir para referirte a otro directorio). "TODOS" mostrará la información de cada clave gestionada (esto puede ser muy largo). Proporcionar un nombre corto de certificado de cliente o servidor también intentará una búsqueda (por ejemplo, -sslCertInfo charlie). Usa "LISTARL" o "LL" para una lista larga (estilo ls -l).
Usar "HASHON" creará subdirectorios [dir]/HASH y [dir]/HASH con nombres de archivo hash de OpenSSL (por ejemplo, 0d5fbbf1.0) enlaces simbólicos apuntando al archivo *.crt correspondiente. ([dir] es ~/.vnc/certs o uno proporcionado por -ssldir.) Esta es una forma útil para que otras aplicaciones OpenSSL (por ejemplo, stunnel) accedan a todos los certificados sin tener que concatenarlos. x11vnc no los usará a menos que los referencies explícitamente. "HASHOFF" elimina estos subdirectorios HASH.
Las palabras LISTAR, LISTARL, LL, TODOS, HASHON, HASHOFF también pueden estar en minúsculas, por ejemplo, "listar".

-sslDelCert pem

Te pedirá que elimines todos los archivos .crt .pem .key .req asociados con [pem]. x11vnc luego sale. Las búsquedas como "GUARDAR" y las búsquedas como en -sslCertInfo también se aplican.

-sslScripts

Muestra ambos scripts envoltorio de x11vnc openssl 'genCA' y 'genCert' para que los examines, modifiques, etc. Los scripts se imprimen en la salida estándar y luego el programa x11vnc sale.

-stunnel [pem]

Utiliza stunnel(8) (stunnel.mirt.net) para proporcionar un túnel SSL cifrado entre los visores y x11vnc.
Este método de túnel externo se implementó antes del cifrado -ssl integrado descrito anteriormente. Todavía funciona bien y evita el requisito de vincularse con las bibliotecas OpenSSL. Este modo requiere que stunnel esté instalado en el sistema y disponible a través de PATH (nota: stunnel a menudo se instala en directorios sbin). Se asume la versión 4.x de stunnel (pero ver -stunnel3 abajo).
[pem] es opcional, usa "-stunnel /ruta/a/stunnel.pem" para especificar un archivo de certificado PEM para pasar a stunnel. Consulta la opción -ssl para obtener más información sobre los archivos de certificado.
Ya sea que tu stunnel tenga su propio certificado o no depende de tu configuración de stunnel; stunnel a menudo genera uno en el momento de la instalación. Consulta la documentación de tu stunnel para obtener más detalles. En cualquier caso, si deseas usar este certificado, debes proporcionar la ruta completa a él como [pem]. Nota: el archivo puede ser legible solo por root.
[pem] también puede ser las cadenas especiales "TMP", "GUARDAR" y "GUARDAR..." como se describe en la opción -ssl. Si no se proporciona [pem], se asume "GUARDAR".
Ten en cuenta que los modos VeNCrypt, ANONTLS y "ANON" no son compatibles en el modo -stunnel.
stunnel se inicia como un proceso hijo de x11vnc y cualquier conexión SSL que reciba stunnel se descifra y se envía a x11vnc a través de un socket local. Las cadenas "The SSL VNC desktop is ..." y "SSLPORT=..." se muestran al inicio para indicar esto.
La opción -localhost se aplica por defecto para evitar que las personas se salten el canal SSL. Usa -env STUNNEL_DISABLE_LOCALHOST=1 para deshabilitar este requisito de seguridad.
Establece -env STUNNEL_DEBUG=1 para obtener más información de depuración.
Establece -env STUNNEL_PROG=xxx a la ruta completa del programa stunnel que deseas utilizar (por ejemplo, /usr/bin/stunnel4).
Establece -env STUNNEL_LISTEN=xxx a la dirección de la interfaz de red en la que escuchar (el valor predeterminado es escuchar en todas las interfaces), por ejemplo, STUNNEL_LISTEN=192.168.1.100.
Una forma sencilla de añadir soporte IPv6 es STUNNEL_LISTEN=::
Tu visor VNC también necesitará poder conectarse a través de SSL. Desafortunadamente, no muchos lo hacen. Consulta la información sobre visores SSL en la opción -ssl. SSVNC del proyecto x11vnc es una opción.
Además, en la distribución de x11vnc, se proporcionan archivos jar de applets de Java TightVNC y UltraVNC parcheados en el directorio classes/ssl que realizan conexiones SSL. Habilita su servicio con -http, -http_ssl, o -httpdir (ver las descripciones de las opciones para más información.)
Ten en cuenta que para el uso de la applet del visor de Java, el "?PORT=xxxx" en las diversas URL que se muestran al inicio deberá ser proporcionado al navegador web para conectarse correctamente.
Actualmente, el modo HTTPS automático de "puerto único" de -ssl no es totalmente compatible en el modo -stunnel. Sin embargo, se puede emular a través de:
% x11vnc -stunnel -http_ssl -http_oneport ...
En general, tampoco es demasiado difícil configurar un stunnel u otro túnel SSL en el lado del visor. Un ejemplo sencillo en Unix usando stunnel 3.x es:
% stunnel -c -d localhost:5901 -r remotehost:5900 % vncviewer localhost:1
Para Windows, stunnel ha sido portado y probablemente existen otras herramientas similares disponibles. Consulta el FAQ y SSVNC para ver más ejemplos.

-stunnel3 [pem]

Utiliza la sintaxis de línea de comandos de stunnel versión 3.x en lugar de la versión 4.x. El servicio de applets Java -http/-httpdir no está disponible actualmente en este modo.

-enc cifrado:archivo_clave

Utiliza cifrado simétrico con el cifrado "cifrado" y datos de clave secreta en "archivo_clave". Si archivo_clave es pw=<cadena> entonces se usa "cadena" como datos de clave.
NOTA: Se recomienda utilizar SSL a través de la opción -ssl en lugar de esta opción porque SSL está bien entendido y se esfuerza mucho en establecer claves de sesión únicas y es más compatible con otro software. Usa esta opción si no quieres lidiar con certificados SSL para autenticación y no quieres usar SSH pero quieres algún cifrado para tu sesión VNC. O si debes interactuar con un túnel de clave simétrica sobre el cual no tienes control.
Ten en cuenta que este modo NO funcionará con los plugins DSM de UltraVNC porque modifican el protocolo RFB además de tunelizar con el cifrado simétrico (una elección desafortunada de implementación...)
cifrado puede ser uno de: arc4, aesv2, aes-cfb, blowfish, aes256, o 3des. Consulta la documentación de OpenSSL para más información. El tamaño de la clave es de 128 bits (excepto para aes256). Aquí hay una forma de crear un archivo de clave con esa cantidad de bits:
dd if=/dev/random of=./my.key bs=16 count=1
necesitarás compartir de forma segura esta clave con el otro lado de la conexión VNC (Ver SSVNC para ejemplos).

Estos valores hacen que la clave de sesión sea única (sin ellos, la seguridad es mínima). Similarmente, el otro lado debe enviarnos su aleatorio

-solid [color]

Para mejorar el rendimiento, cuando los clientes VNC están conectados, intente cambiar el fondo del escritorio a un color sólido. El [color] es opcional: el color predeterminado es "cyan4". Para uno diferente, especifique el color X (nombre de rgb.txt, por ejemplo, "darkblue" o numérico "#RRGGBB").

-blackout cadena

Ennegrece rectángulos en la pantalla. La cadena es una lista separada por comas de geometrías de tipo WxH+X+Y para cada rectángulo. Si uno de los elementos de la lista es la cadena "noptr", no se permitirá que el puntero del ratón entre en una región ennegrecida.

-xinerama, -noxinerama

Si su pantalla está compuesta por varios monitores unidos a través de XINERAMA, y esa pantalla no es un rectángulo, esta opción intentará adivinar las áreas a ennegrecer (si su sistema tiene libXinerama). Por defecto: -xinerama
En general, hemos notado en pantallas XINERAMA que es posible que necesite usar la opción "-xwarppointer" si el puntero del ratón se comporta de forma incorrecta y está habilitado por defecto. Use "-noxwarppointer" si no desea esto.

-xtrap

Utiliza la extensión DEC-XTRAP para la inserción de entrada de teclado y ratón. Para usar en sistemas heredados, por ejemplo, X11R5, que ejecutan una extensión XTEST incompleta o faltante. Por defecto, DEC-XTRAP se usará si falta el control de "server grab" de XTEST, use -xtrap para realizar la inserción de teclado y ratón a través de DEC-XTRAP también.

-xrandr [modo]

Si la pantalla admite la extensión XRANDR (X Resize, Rotate and Reflection), y espera que ocurran eventos XRANDR en la pantalla mientras x11vnc se está ejecutando, esta opción indica que x11vnc debe intentar responder a ellos (en lugar de simplemente fallar asumiendo el tamaño de pantalla antiguo). Consulte la página del manual de xrandr(1) y ejecute 'xrandr -q' para obtener más información. [modo] es opcional y se describe a continuación.
Dado que la supervisión de eventos XRANDR y el atrapamiento de errores aumentan la sobrecarga de sondeo, use esta opción solo si se esperan cambios en XRANDR. Por ejemplo, en una PDA o portátil con pantalla rotatoria, o usando un Escritorio compatible con XRANDR donde cambia el tamaño con frecuencia. Es mejor ver con un vncviewer que admita la codificación NewFBSize, ya que sabe cómo reaccionar a los cambios de tamaño de pantalla. De lo contrario, LibVNCServer intenta hacer algo razonable para los espectadores que no pueden hacer esto (partes de la pantalla pueden cortarse, usarse sin usar, etc.).
Nota: el valor predeterminado ahora es verificar los eventos XRANDR, pero no atrapar cada llamada X que pueda fallar debido al redimensionamiento. Si se recibe un evento de redimensionamiento, se habilita el modo completo de -xrandr. Para deshabilitar incluso la verificación de eventos, proporcione: -noxrandr.
"modo" tiene como valor predeterminado "resize", que significa crear un nuevo framebuffer redimensionado y esperar que todos los espectadores puedan manejar el cambio. "newfbsize" significa desconectar primero todos los espectadores que no admiten la codificación VNC NewFBSize y luego redimensionar el framebuffer. "exit" significa desconectar a todos los clientes del espectador y luego terminar x11vnc.

-rotate cadena

Gira y/o voltea la vista del framebuffer exportada por VNC. Esta transformación es independiente de XRANDR y se realiza en software en la memoria principal, por lo que puede ser más lenta. Este modo podría ser útil en un dispositivo portátil con modos vertical u horizontal que no se corresponden con el orden de las líneas de escaneo del framebuffer real. La cadena puede ser:
x voltea a lo largo del eje x y voltea a lo largo del eje y xy voltea a lo largo de los ejes x e y +90 rota 90 grados en sentido horario -90 rota 90 grados en sentido antihorario +90x rota 90 grados en sentido horario, luego voltea a lo largo de x +90y rota 90 grados en sentido horario, luego voltea a lo largo de y
estos dan todas las rotaciones y reflejos posibles.
Alias: igual que xy: yx, +180, -180, 180 igual que -90: +270, 270 igual que +90: 90, (lo mismo para 90x, 90y)
Al igual que -scale, esta transformación se aplica al final de cualquier cadena de transformaciones de framebuffer, por lo que las opciones con geometrías, por ejemplo, -blackout, -clip, etc., son relativas al X original (o -rawfb) framebuffer, no al final que se envía a los espectadores de VNC.
Si no desea que la forma del cursor se rote, prefije la cadena con "nc:", por ejemplo, "nc:+90", "nc:xy", etc.

-padgeom WxH

Cada vez que se conecta un nuevo vncviewer, el framebuffer se reemplaza por uno falso y sólido de color negro con geometría WxH. Poco después, el framebuffer se reemplaza por el real. Esto está destinado a usarse con vncviewers que no admiten NewFBSize y se desea asegurarse de que la geometría inicial del espectador sea lo suficientemente grande como para manejar todos los redimensionamientos posteriores (por ejemplo, con -xrandr, -remote id:windowid, redimensionamiento, etc.)
En el modo -unixpw, esto establece el tamaño de la pantalla de inicio de sesión. Use "once:WxH" para ignorar padgeom después de que la pantalla de inicio de sesión se configure.

-modtweak, -nomodtweak

La opción -modtweak intenta automáticamente ajustar los modificadores AltGr y Shift para teclados de diferentes idiomas entre el cliente y el host. De lo contrario, solo se simula una única pulsación/liberación de una tecla de código de tecla (es decir, ignorando el estado de los modificadores: esto generalmente funciona para teclados idénticos). También es útil para resolver casos en los que una combinación de teclas está vinculada a varias teclas (por ejemplo, teclas "<" y ">" y "," y "<"). Por defecto: -modtweak
Si tiene problemas con las teclas y -xkb o -noxkb, y cosas similares no ayudan, intente -nomodtweak.

El fallo ocurre cuando intentas escribir "#" y obtienes "3". Si experimentas este problema, prueba a establecer la variable de entorno MODTWEAK_LOWEST=1 para ver si ayuda.
-xkb, -noxkb

Cuando estás en modo modtweak, utiliza la extensión XKEYBOARD (si la pantalla X lo soporta) para ajustar los modificadores. Esto es potente y debería probarse si todavía hay problemas de mapeo de teclado al usar -modtweak por sí solo. Por defecto, se comprueba si algunas teclas comunes, por ejemplo, !, @, [, solo son accesibles a través del modo -xkb y, en caso afirmativo, se habilita automáticamente el modo. Para deshabilitar esta detección automática, usa -noxkb.

Cuando el modo -xkb está activo, puedes establecer estas variables de entorno. Se aplican solo cuando hay ambigüedad sobre qué tecla elegir (es decir, el mapeo no es uno a uno).

  • NOKEYHINTS=1: para las pulsaciones de teclas ASCII ascendentes, no utilices las pistas de puntuación guardadas cuando la tecla se presionó.
  • NOANYDOWN=1: para las pulsaciones de teclas ascendentes, no recurras a la búsqueda entre las teclas que están actualmente presionadas.
  • KEYSDOWN=N: recuerda las últimas N teclas presionadas para desempatar cuando llega una pulsación de tecla ascendente.
-capslock

Cuando estás en modo -modtweak (por defecto) o -xkb, si llega un keysym en el rango A-Z, comprueba el servidor X para ver si está activado el bloqueo de mayúsculas (Caps_Lock). Si lo está, no presiones artificialmente Shift para generar el keysym. Esto permitirá que la tecla Bloq Mayús se comporte correctamente en algunas circunstancias: concretamente, cuando *tanto* la máquina cliente VNC como el servidor X de x11vnc están en el estado de Bloq Mayús activado. Si un lado tiene Bloq Mayús activado y el otro desactivado, y el teclado no se comporta como esperas, deberías corregir los estados de Bloq Mayús (pista: presionar Bloq Mayús dentro y fuera del visor puede ayudar a alternar ambos al estado correcto). Sin embargo, para obtener los mejores resultados, no uses esta opción, sino que *solo* activa Bloq Mayús en el lado del cliente VNC (es decir, presionando Bloq Mayús fuera de la ventana del cliente, también -skip_lockkeys a continuación). Prueba también -nomodtweak como posible solución.
-skip_lockkeys, -noskip_lockkeys

Haz que x11vnc ignore todos los keysyms Caps_Lock, Shift_Lock, Num_Lock, Scroll_Lock recibidos de los clientes. La idea es que presiones Bloq Mayús en el lado del cliente VNC, pero eso no cambia el estado de bloqueo en el servidor X de x11vnc. Sin embargo, tus letras mayúsculas llegan a través del cable y se aplican correctamente al servidor X de x11vnc. Ten en cuenta que este modo probablemente no hará lo que esperas en modo -nomodtweak. Además, siempre se aplica una solución improvisada para los dígitos KP_n en este modo: se mapean a teclas de dígitos normales. Ver también -capslock arriba. El valor predeterminado es -noskip_lockkeys.
-skip_keycodes <i>cadena</i>

Ignora la lista separada por comas de códigos de tecla decimales. Quizás estos son códigos de tecla que no están en tu teclado pero que tu servidor X cree que existen. Actualmente solo se aplica al modo -xkb. Usa esta opción para ayudar a x11vnc en el problema inverso que intenta resolver: Keysym -> Código(s) de tecla cuando existen ambigüedades (más de un Código de tecla por Keysym). Ejecuta 'xmodmap -pk' para ver tu mapeo de teclado. Ejemplo: "-skip_keycodes 94,114"
-sloppy_keys

Opción experimental que intenta corregir algunos comportamientos de teclas "descuidados". Por ejemplo, si en el cliente presionas Shift+Tecla pero luego sueltas Shift antes que Tecla, eso podría generar caracteres adicionales no deseados (generalmente solo entre teclados de diferentes idiomas). Usa esta opción solo si observas problemas con algunas pulsaciones de teclas.
-skip_dups, -noskip_dups

Algunos clientes VNC envían eventos de teclas repetidos imposibles, por ejemplo, tecla-abajo, tecla-abajo, tecla-arriba, tecla-arriba, todo para la misma tecla, ¡o 20 presiones hacia abajo seguidas para la misma tecla modificadora! Establecer -skip_dups significa omitir estos duplicados y procesar solo el primer evento. Nota: algunos clientes VNC asumen que pueden enviar presiones hacia abajo sin las correspondientes presiones hacia arriba, por lo que no deberías establecer esta opción para estos clientes (síntoma: algunas teclas no se repiten automáticamente). Por defecto: -noskip_dups
-add_keysyms, -noadd_keysyms

Si se recibe un Keysym de un cliente VNC y ese Keysym no existe en el servidor X, entonces se añade el Keysym al mapeo del teclado del servidor X en una tecla no utilizada. Los Keysyms añadidos se eliminarán periódicamente y también cuando x11vnc salga. Por defecto: -add_keysyms
-clear_mods

Al inicio y al salir, se borran las teclas modificadoras enviando KeyRelease para cada una de ellas. Se omiten los modificadores de bloqueo. Se utiliza para borrar el estado si la pantalla se dejó accidentalmente con alguna tecla presionada.
-clear_keys

Similar a -clear_mods, excepto que intenta liberar CUALQUIER tecla presionada. Ten en cuenta que esta opción y -clear_mods pueden interferir con alguien escribiendo en el teclado físico.
-clear_all

Similar a -clear_keys, excepto que intenta liberar también cualquier bloqueo de Bloq Mayús, Bloq Num, etc.
-remap <i>cadena</i>

Lee remapeos de Keysym desde el archivo llamado cadena. El formato es un par de Keysyms por línea (puede ser nombre o valor hexadecimal) separados por un espacio. Si no existe un archivo llamado cadena, se interpreta como la siguiente forma: tecla1-tecla2,tecla3-tecla4,... Consulta el archivo de cabecera <X11/keysymdef.h> para obtener una lista de nombres de Keysym, o usa xev(1).

Para mapear una tecla a un clic de botón, usa los Keysyms ficticios "Button1", ..., etc. Por ejemplo: "-remap Super_R-Button2" (útil para pegar en un portátil)

Los uso si la máquina desde la que estoy viendo no tiene rueda de desplazamiento o si no me gusta usar la que tiene:

-remap Super_R-Button4,Menu-Button5 -remap KP_Add-Button4,KP_Enter-Button5

el primero se usaría en un PC, el segundo en un MacBook. De esta manera, esas teclas poco utilizadas pueden usarse para generar saltos más grandes que las flechas Arriba y Abajo. Se puede desplazarse por texto o páginas web más rápidamente de esta manera (especialmente si la detección de desplazamiento de x11vnc está activa).

Usa Button44, Button12, etc. para clics múltiples.

Para deshabilitar un keysym (es decir, hacer que no se inyecte), remapealo a "NoSymbol" o "None".

Teclas muertas: las teclas "muertas" (o silenciosas, mudas) son teclas que no producen un carácter pero deben ir seguidas de una segunda pulsación. Esto se usa a menudo para acentuar caracteres, por ejemplo, para poner "`" encima de "a" presionando la tecla muerta y luego "a". Ten en cuenta que esta interpretación no forma parte del núcleo X11, depende del toolkit o la aplicación decidir cómo reaccionar a la secuencia. Los nombres X11 para estos keysyms son "dead_grave", "dead_acute", etc. Sin embargo, algunos clientes VNC envían los keysyms "grave", "acute" en su lugar, lo que deshabilita el acentuado. Para solucionar esto, se puede usar -remap. Por ejemplo: "-remap grave-dead_grave,acute-dead_acute"

Como conveniencia, "-remap DEAD" aplica los siguientes remapeos:

  • g grave-dead_grave
  • a acute-dead_acute
  • c asciicircum-dead_circumflex
  • t asciitilde-dead_tilde
  • m macron-dead_macron
  • b breve-dead_breve
  • D abovedot-dead_abovedot
  • d diaeresis-dead_diaeresis
  • o degree-dead_abovering
  • A doubleacute-dead_doubleacute
  • r caron-dead_caron
  • e cedilla-dead_cedilla

Si solo quieres un subconjunto, usa la etiqueta de la primera letra, por ejemplo, "-remap DEAD=ga" para obtener los dos primeros. También se pueden proporcionar remapeos adicionales separados por comas, por ejemplo, "-remap DEAD=ga,Super_R-Button2". Finalmente, "DEAD=missing" significa aplicar todo lo anterior siempre que el miembro de la mano izquierda no esté ya en el mapeo de teclas de X11.
-norepeat, -repeat

La opción -norepeat deshabilita la repetición automática de teclas del servidor X cuando los clientes VNC están conectados y la entrada del teclado VNC no está inactiva durante más de 5 minutos. Esto soluciona un error de pulsaciones de teclas repetidas (desencadenado por largos retrasos de procesamiento entre eventos de tecla-abajo y tecla-arriba del cliente: ya sea por grandes cambios de pantalla o alta latencia). Por defecto: -norepeat

Puedes establecer la variable de entorno X11VNC_IDLE_TIMEOUT al número de segundos de inactividad que deseas (5 minutos = 300 segundos).

Nota: es probable que tu cliente VNC realice repeticiones automáticas, por lo que esto no es una pérdida a menos que alguien esté simultáneamente en la pantalla X real.

Usa "-norepeat N" para establecer cuántas veces se restablecerá norepeat si algo más (por ejemplo, el gestor de sesión X) lo deshace. El valor predeterminado es 2. Usa un valor negativo para restablecimientos ilimitados.
-nofb

Ignora el framebuffer de video: solo procesa el teclado y el puntero. Diseñado para usarse con configuraciones de doble monitor Win2VNC y x2vnc.
-nobell

No vigila los eventos XBell. (no se escucharán pitidos) Nota: la monitorización de XBell requiere la extensión XKEYBOARD.
-nosel

No gestionar el intercambio de la selección/buffer de corte de X entre los clientes VNC y el servidor X en absoluto.
-noprimary

No sondear la selección PRIMARY en busca de cambios para enviar de vuelta a los clientes. (Sin embargo, PRIMARY todavía se establece en los cambios recibidos).
-nosetprimary

No establecer la selección PRIMARY para los cambios recibidos de los clientes VNC.
-noclipboard

No sondear la selección CLIPBOARD en busca de cambios para enviar de vuelta a los clientes. (Sin embargo, CLIPBOARD todavía se establece en los cambios recibidos).
-nosetclipboard

No establecer la selección CLIPBOARD para los cambios recibidos de los clientes VNC.
-seldir <i>cadena</i>

Si la cadena de dirección es "send", solo envía la selección a los clientes, y si es "recv", solo la recibe de los clientes. Para solucionar aplicaciones que establecen la selección con demasiada frecuencia y arruinan el otro extremo. "Pp">-cursor [modo], -nocursor

Establece cómo se debe manejar la forma del cursor del puntero (icono pequeño en el puntero del ratón). El "modo" es opcional y se describe a continuación. El valor predeterminado es mostrar alguna forma de cursor. Cómo se hace esto depende del visor VNC y del servidor X. Usa -nocursor para deshabilitar las formas del cursor por completo.
Algunos visores VNC soportan las extensiones TightVNC CursorPosUpdates y CursorShapeUpdates (reducen el tráfico de red al no tener que enviar la imagen del cursor cada vez que se mueve el puntero), en cuyo caso se usan estas extensiones (ver -nocursorshape y -nocursorpos a continuación para deshabilitar). Para otros visores, la forma del cursor se escribe directamente en el framebuffer cada vez que se mueve o cambia el puntero y se envía junto con las otras actualizaciones del framebuffer. En este caso, habrá un cierto retraso entre el puntero del visor vnc y la posición del cursor remoto.
Si la pantalla X soporta la recuperación de la información de la forma del cursor del servidor X, entonces el valor predeterminado es usar ese modo. En Solaris, esto se puede hacer con la extensión SUN_OVL usando -overlay (ver también la opción -overlay_nocursor). Un esquema de superposición similar se utiliza en IRIX. Xorg (por ejemplo, Linux) y los servidores Solaris Xsun recientes soportan la extensión XFIXES para recuperar la forma exacta del cursor del servidor X. Si XFIXES está presente, se prefiere a Overlay y se usa por defecto (ver -noxfixes a continuación). Esto se puede deshabilitar con -nocursor, y también con algunos valores de la opción "modo" a continuación.
Ten en cuenta que con XFIXES los cursores con transparencia (canal alfa) normalmente no se representarán exactamente y puede que prefieras Overlay. Ver también las opciones -alphacut y -alphafrac a continuación como factores de ajuste para intentar mejorar la situación de los cursores con transparencia para un tema determinado.
La cadena "modo" se puede usar para ajustar la visualización de las formas del cursor. Se puede usar de las siguientes maneras:
"-cursor arrow" - solo muestra la flecha estándar, nada más o nada menos.
"-cursor none" - igual que "-nocursor"
"-cursor X" - cuando el cursor parece estar en la ventana raíz, dibuja la familiar forma de X. Algunos entornos de escritorio como GNOME cubren completamente la ventana raíz, por lo que esto no funcionará. Intenta "X1", etc., para intentar desplazar la profundidad del árbol. En enlaces de alta latencia o máquinas lentas, habrá un retraso entre lo esperado y la forma real del cursor.
"-cursor some" - como "X", pero usa heurísticas adicionales para intentar adivinar si la ventana debería tener un cursor de redimensionamiento similar al del gestor de ventanas o un cursor de barra I para entrada de texto. Ten en cuenta que con el nuevo valor predeterminado, x11vnc será ajeno a las aplicaciones que mueven el puntero (warping) o al usuario que lo mueve en la pantalla física. December 2023 x11vnc - VNC server that uses the X11 Xtest extension to control the mouse and keyboard

x11vnc [options]

x11vnc is a professional, multi-threaded VNC server. It allows you to remotely control a running X11 session. Unlike other VNC servers, it doesn't emulate a display, but rather shares the existing X11 display. This means you can see and control exactly what a user sitting at the machine sees and controls.

This document describes the various options available for controlling x11vnc's behavior. The options can be provided on the command line or remotely via the VNC protocol itself.

-scrollcopyrect [never|keys|mouse|always]

Control the use of the XCopyArea (CopyRect) X11 protocol request. CopyRect is a request to copy a rectangular region of pixels from one place to another. It can significantly speed up screen updates, especially for scrolling windows. The default is to try it when possible.
never: Never try to use CopyRect. This will likely result in slower screen updates but may avoid some graphical glitches.
keys: Try to use CopyRect only in response to keystrokes.
mouse: Try to use CopyRect only in response to mouse events.
always: Try to use CopyRect for both keystrokes and mouse events. This is the default.
Note: When using the -scale option, graphical glitches or slow response might occur. In such cases, you might want to disable CopyRect by using "-scrollcopyrect never" on the command line or via remote control. Alternatively, you can use the "-scale xxx:nocr" scale option.

-scr_area n

Set the minimum area in pixels for a rectangle to be considered for the -scrollcopyrect detection scheme. This is to avoid wasting effort on small rectangles that would be quickly updated normally. For example, if an application first updates the position of its skinny scrollbar and then shifts the large panel it controls, this option ensures we skip the small scrollbar and focus on the large panel. Default: 60000

-scr_skip list

Skip scroll detection for applications matching the comma-separated list of strings in list. Some applications implement scrolling in unusual ways where XCopyArea, etc., also applies to invisible portions of the window. If these areas are copied, it can look awful during scrolling and may leave graphical artifacts after scrolling. `soffice.bin` is the worst known offender.
Use "##" to denote the start of the application class (e.g., "##XTerm") and "++" to denote the start of the application instance name (e.g., "++xterm"). The string your list is matched against is of the form "^^WM_NAME##Class++Instance<same-for-any-subwindows>". The command `xlsclients -la` will provide this information.
If a pattern is prefixed with "KEY:", it only applies to scrolls generated by keystrokes (e.g., the Up arrow). If it is prefixed with "MOUSE:", it only applies to scrolls induced by the mouse (e.g., dragging on a scrollbar). Default: ##Soffice.bin,##StarOffice,##OpenOffice

-scr_inc list

Opposite of -scr_skip: this list is consulted first, and if there is a match, the window will be monitored via RECORD for scrolls, irrespective of -scr_skip. Use "-scr_skip '*'" to skip anything that does not match your -scr_inc. Use "-scr_inc '*'" to include everything.

-scr_keys list

For keystroke scroll detection, only apply the RECORD heuristics to the comma-separated list of keysyms in list. You might find that the RECORD overhead for every keystroke disrupts typing too much, but you don't want to turn it off completely with "-scr mouse" and -scr_parms is either not working or too confusing.
The listed keysyms can be numeric or the keysym names found in the <X11/keysymdef.h> header file or obtained from the xev(1) program. Example: "-scr_keys Up,Down,Return". It's likely you'll want application-specific lists (e.g., for terminals), but that's too complex to consider right now...
If list begins with the "-" character, the list is taken as an exclusion list: all keysyms except those in the list will be considered. The special string "builtin" expands to an internal list of keysyms that are likely to cause scrolls. By default, modifier keys (Shift_L, Control_R, etc.) are skipped as they rarely induce scrolling by themselves.

-scr_term list

Yet another cosmetic kludge. Apply shell/terminal heuristics to applications matching the comma-separated list (same format as for -scr_skip/-scr_inc). For example, an annoying transient artifact under scroll detection occurs if you hit Enter in a terminal with a full text window; the solid text cursor block will be scrolled up. For a short time, there will be two (or more) block cursors on the screen. Similar scenarios exist (e.g., an output line is duplicated).
These transients are induced by the approximation of scroll detection (e.g., it detects the scroll but not the fact that the block cursor was cleared just before the scroll). In almost all cases, these transient errors are repaired when the true X framebuffer is consulted by normal polling. However, they are distracting, so this option provides extra "padding" near the bottom of the terminal window: a few extra lines at the bottom will not be scrolled but rather updated from the actual X framebuffer. This usually reduces the annoying artifacts. Use "none" to disable. Default: "term"

-scr_keyrepeat lo-hi

If a key is held down (or otherwise repeats rapidly) and this induces a rapid sequence of scrolls (e.g., holding down an Arrow key), the "scrollcopyrect" detection and overhead might not be able to keep up. An estimate of the time per single scroll is performed, and if that estimate predicts a sustainable scroll rate of keys per second between "lo" and "hi", then repeated keys will be DISCARDED to maintain the scroll rate. For example, your key autorepeat might be 25 keys/sec, but for a large window or slow link, only 8 scrolls per second can be sustained. In this case, roughly 2 out of every 3 repeated keys will be discarded during this period. Default: "4-20"

-scr_parms string

Set various parameters for the scrollcopyrect mode. The format is similar to that for -wireframe and packed with numerous parameters:
Format: T+B+L+R,t1+t2+t3,s1+s2+s3+s4+s5 Default: 0+64+32+32,0.02+0.10+0.9,0.03+0.06+0.5+0.1+5.0
If you leave nothing between commas (",,"), the default value is used. If you do not specify enough commas, the trailing parameters are set to their defaults.
"T+B+L+R" indicates four integers representing how close in pixels the pointer must be to the Top, Bottom, Left, or Right edges of the window to consider scrollcopyrect. If -wireframe overlaps, it takes precedence. This is a speedup to quickly exclude a window from being watched for scrollcopyrect; set them all to zero to disable this speedup (actions like text selection will likely be slower).
"t1+t2+t3" specifies three floating-point times in seconds that apply to scrollcopyrect detection with *Keystroke* input: t1 is how long to wait after a key is pressed for the first scroll, t2 is how long to keep looking for more scrolls after a Keystroke scroll is detected, and t3 is how frequently to try updating surrounding scrollbars outside the scrolling area (0.0 to disable).
"s1+s2+s3+s4+s5" specifies five floating-point times in seconds that apply to scrollcopyrect detection with *Mouse* input: s1 is how long to wait after a mouse button is pressed for the first scroll, s2 is how long to keep waiting for additional scrolls after the first Mouse scroll was detected, s3 is how frequently to try updating surrounding scrollbars outside the scrolling area (0.0 to disable), s4 is how long to buffer pointer motion (to try to get fewer, larger mouse scrolls), and s5 is the maximum time to spend just updating the scroll window without updating the rest of the screen.

-fixscreen string

Periodically "repair" the screen based on settings in string. Hopefully, you won't need this option; it's intended for cases where the -scrollcopyrect or -wirecopyrect features leave too many painting errors, but it can be used in any scenario. This option periodically performs costly operations, so interactive response may be reduced when it's active. You can use three taps of Alt_L (the left "Alt" key) in a row (as described under -scrollcopyrect) to manually request a screen repaint when needed.
string is a comma-separated list of one or more of the following: "V=t", "C=t", "X=t", and "8=t". In these, "t" stands for a time in seconds (it's a floating-point value, though values greater than 2 are usually sufficient to avoid wasting resources). This is usually a window manager. x11vnc takes care to avoid the problem, but if caught, x11vnc will freeze. Without -grab_buster, the only solution is to go to the physical display and provide some input to satisfy the grabbing application. Alternatively, manually kill and restart the window manager if feasible. With -grab_buster, x11vnc will fork a helper thread, and if x11vnc appears to be stuck in a grab after a period of time (20-30 seconds), it will inject some user input (button clicks, Escape, mouse motion, etc.) to try to break the grab. -pointer_mode n

Various pointer motion update schemes. "-pm" is an alias.
 El problema es que el movimiento del puntero puede causar cambios rápidos en la pantalla: considera los cambios rápidos cuando arrastras una ventana grande de forma opaca. Ni los rutinas de sondeo de pantalla y compresión vnc de x11vnc, ni el ancho de banda a los vncviewers pueden seguir estos cambios rápidos de pantalla: todo se ralentizará al arrastrar o desplazarse. Por lo tanto, se debe utilizar un esquema para "consumir" gran parte de esa entrada del puntero antes de volver a sondear la pantalla y enviar actualizaciones del framebuffer. El número de modo *n* puede ser de 0 a 4 y selecciona uno de los esquemas descritos a continuación.
Tenga en cuenta que -wireframe y -scrollcopyrect__mode_s complementan -pointer_mode al detectar (y mejorar) ciertos períodos de "cambio rápido de pantalla".
n=0: hace lo mismo que -nodragging. (todo el sondeo de pantalla se suspende si se presiona un botón del ratón.)
n=1: fue el esquema original utilizado hasta aproximadamente enero de 2004: básicamente, simplemente omite -input_skip eventos de teclado o puntero antes de volver a sondear la pantalla.
n=2 es un esquema mejorado: al observar la tasa actual de eventos de entrada, intenta detectar si debe intentar "consumir" eventos de puntero adicionales antes de continuar.
n=3 es básicamente un modo -nodragging dinámico: detecta cuándo el movimiento del ratón se ha pausado y luego actualiza la pantalla.
n=4 intenta medir las tasas de red y la latencia, la tasa de lectura de la tarjeta de video y cuántos mosaicos se han cambiado en la pantalla. A partir de esto, intenta agresivamente enviar "fotogramas" de pantalla cuando decide que tiene suficientes recursos para hacerlo. NO TERMINADO.
El valor predeterminado de n es 2. Tenga en cuenta que los modos 2, 3 y 4 omitirán los eventos de teclado -input_skip (pero no contarán los eventos del puntero). Tenga en cuenta también que estos modos no están disponibles en el modo -threads, que tiene su propio mecanismo de manejo de eventos del puntero.
Para probar los diferentes modos de puntero y ver cuál ofrece la mejor respuesta para su uso, es conveniente utilizar la función de control remoto, por ejemplo, "x11vnc -R pm:4" o la GUI tcl/tk (Ajuste -> pointer_mode -> n).

-pipeinput cmd

Esta opción te permite proporcionar un comando externo en cmd al que x11vnc canalizará todos los eventos de entrada del usuario en un formato simple. En el modo -pipeinput, de forma predeterminada, x11vnc no procesará ningún evento de entrada del usuario. Si antepones "tee:" a cmd, enviará los eventos tanto al comando de la tubería como los procesará. Para obtener una descripción del formato, ejecuta "-pipeinput tee:/bin/cat". Otro prefijo es "reopen", que significa reabrir la tubería si se cierra. Separa varios prefijos con comas.
En combinación con -rawfb, podrías hacer cosas divertidas (por ejemplo, controlar dispositivos que no sean X). Para facilitar esto, si -rawfb está activo, el valor se almacena en X11VNC_RAWFB_STR para que el comando de la tubería lo use si lo desea. Ejecuta 'env | grep X11VNC' para más información.
Modos de pipeinput integrados (no se requiere programa externo):
Si cmd es "VID" y estás usando -rawfb para un dispositivo de captura de video, se utiliza una lista interna de mapeos de teclado para establecer los parámetros del video. Los mapeos son:
"B" y "b" ajustan el brillo hacia arriba y hacia abajo. "H" y "h" ajustan el matiz. "C" y "c" ajustan el color. "N" y "n" ajustan el contraste. "S" y "s" ajustan el tamaño de la pantalla de captura. "I" y "i" ciclan a través de los canales de entrada. Las flechas Arriba y Abajo ajustan la estación (si es un sintonizador). F1, F2, ..., F6 cambiarán el formato de píxel de captura de video a HI240, RGB565, RGB24, RGB32, RGB555 y GREY respectivamente. Ver -rawfb video para más detalles.
Si cmd es "CONSOLE" o "CONSOLEn" donde n es un número de consola de Linux, se realiza la inserción de pulsaciones de teclado de la consola de Linux en /dev/ttyN (ver -rawfb console).
Si cmd comienza con "UINPUT", se utiliza el módulo uinput de Linux para insertar eventos de teclado y ratón en la consola de Linux (ver -rawfb arriba). Este suele ser el archivo de dispositivo /dev/input/uinput (puede que necesites crearlo con "mknod /dev/input/uinput c 10 223" e insertar el módulo con "modprobe uinput").
El modo UINPUT actualmente solo admite teclados de EE. UU. (se puede agregar una opción de código de escaneo) y no todos los keysyms son compatibles. Pero es probablemente más preciso que el método "CONSOLE".
Es posible que desees usar las opciones -cursor none y -nodragging en este modo.
Se pueden proporcionar opciones de ajuste adicionales a través de: UINPUT:opt1,opt2,... (una lista separada por comas). Si una opción comienza con "/", se toma como el archivo del dispositivo uinput.
Qué uinput se inyecta se puede controlar mediante una cadena de opciones compuesta por los caracteres "K", "M" y "B" (ver la opción -input), por ejemplo, "KM" permite pulsaciones de teclado y movimiento, pero no clics de botón.
Una opción UINPUT de la forma: accel=f, o accel=fx+fy establece la "aceleración" del movimiento del ratón. Esto se utiliza para corregir el movimiento relativo bruto del ratón en la cantidad en que se mueve el cursor de la aplicación (x11vnc no tiene control ni conocimiento de cómo la aplicación de ventanas interpreta los movimientos brutos del ratón). Típicamente, la aceleración para una pantalla X es 2 (ver la opción "m" de xset). "f" es un número de punto flotante, por ejemplo, 3.0. Usa "fx+fy" si necesitas proporcionar correcciones diferentes para x e y.
Nota: la aceleración predeterminada es 2.0 ya que parece que tanto X como qt-embedded a menudo (pero no siempre) usan este valor.
Incluso con una configuración de aceleración correcta, la posición del ratón se desincronizará (probablemente debido a una configuración de "umbral" del ratón donde la aceleración no se aplica, consulta xset(1)). Si estableces la variable de entorno X11VNC_UINPUT_THRESHOLDS, se habilitará el modo thresh=n. Actualmente no está funcionando bien. Si |dx| <= thresh y |dy| < thresh, no se aplica aceleración. Usa "thresh=+n" para usar |dx| + |dy| < thresh en su lugar (¿X11?).

"conn" significa no iniciar automáticamente x11vnc, sino intentar conectarse a un proceso x11vnc existente. "wait" significa simplemente iniciar la GUI y nada más (más tarde instruirá a la GUI para iniciar x11vnc o conectarse a uno existente).
2) La simplicidad de la GUI está desactivada por defecto (se presenta una GUI para usuarios avanzados con todas las opciones). Para comenzar con algo menos desalentador, proporcione la cadena "simple" ("ez" es un alias para esto). Una vez iniciada la GUI, puede alternar entre las dos con "Misc -> simple_gui".
3) Tenga en cuenta la posible confusión con respecto a las dos pantallas X potencialmente diferentes: x11vnc sondea una, pero es posible que desee que la GUI aparezca en otra. Por ejemplo, si se conecta por SSH y x11vnc aún no se está ejecutando, es posible que desee que la GUI regrese a través de su pantalla X redirigida por SSH (por ejemplo, localhost:10).
Si no especifica una pantalla X de GUI en "gui-opts", se intentan la variable de entorno DISPLAY y la opción -display (en ese orden). Con respecto a la pantalla X de x11vnc que la GUI intentará comunicar, primero intenta -display y luego DISPLAY. Por ejemplo, "x11vnc -display :0 -gui otherhost:0" controlará remotamente un x11vnc que sondea :0 y mostrará la GUI en otherhost:0. El modo "bandeja/icono" a continuación invierte esta preferencia, prefiriendo mostrar en la pantalla de x11vnc.
4) Cuando se especifica "tray" o "icon", la GUI se presenta como un pequeño icono con un comportamiento típico de una "bandeja del sistema" o "applet de dock". El color del icono indica el estado (clientes conectados) y también hay un estado de globo. Al hacer clic en el icono se abre un menú desde el cual se pueden configurar propiedades, etc., y la GUI completa está disponible en "Advanced". Para ser completamente funcional, el modo de GUI debe ser "start" (el predeterminado).
Tenga en cuenta que el modo de bandeja o icono implicará la opción de x11vnc -forever (si el servidor x11vnc se inicia junto con la GUI), a menos que se haya especificado -connect o -connect_or_exit. Por lo tanto, x11vnc (y la GUI de bandeja/icono) esperarán más conexiones después de que el primer cliente se desconecte. Si solo desea una conexión de visor, incluya la opción -once.
Para "icon", la GUI es solo una pequeña ventana independiente. Para "tray", intentará incrustarse en la "bandeja del sistema" si es posible. Si se añade "=setpass", se le pedirá al usuario de X11 que establezca la contraseña de la sesión VNC al iniciar. Si se añade =<hexnumber>, ese icono intentará incrustarse en la ventana dada por hexnumber. Use =noadvanced para deshabilitar la GUI completa. (Para proporcionar más de uno, use el signo "+"). Por ejemplo, -gui tray=setpass y -gui icon=0x3600028
Otros modos: "full", el predeterminado y no necesita especificarse. "-gui none", no muestre una GUI, útil para anular una configuración de ~/.x11vncrc, etc.
5) Cuando se especifica "geom=+X+Y", esa geometría se pasa a la ventana principal de la GUI. Este es el icono en modo icono/bandeja, o la GUI completa de lo contrario. También puede especificar ancho y alto, es decir, AnxAl+X+Y, pero no se recomienda. En modo "tray", la geometría se ignora a menos que el administrador de la bandeja del sistema no parezca estar en ejecución. Se podría imaginar usar algo como "-gui tray,geom=+4000+4000" con un gestor de pantallas para mantener la GUI invisible hasta que alguien inicie sesión...
Más trucos de iconos, "icon=minimal" proporciona un icono solo con el número de pantalla VNC. También puede configurar la fuente con "iconfont=...". Lo siguiente podría ser útil: "-gui icon=minimal,iconfont=5x8,geom=24x10+0-0"
Ejemplos generales de la opción -gui: "x11vnc -gui", "x11vnc -gui ez", "x11vnc -gui localhost:10", "x11vnc -gui conn,host:0", "x11vnc -gui tray,ez", "x11vnc -gui tray=setpass"
Si no tiene la intención de iniciar x11vnc desde la GUI (es decir, solo controlar remotamente uno existente), entonces el proceso de GUI puede ejecutarse en una máquina diferente a la del servidor x11vnc, siempre que los permisos X, etc., permitan la comunicación entre ambos.
FUENTES: En algunos sistemas, las fuentes de tk pueden ser demasiado pequeñas, irregulares o de otro modo ilegibles. Hay 4 variables de entorno que puede establecer para que sean la fuente de tk que prefiera:
X11VNC_FONT_BOLD fuente principal para menús y botones. X11VNC_FONT_FIXED fuente para texto de ancho fijo.
X11VNC_FONT_BOLD_SMALL fuente del icono de bandeja. X11VNC_FONT_REG_SMALL fuente del menú del icono de bandeja.
Los dos últimos solo se aplican al modo de icono de bandeja.
Aquí hay algunos ejemplos:
-env X11VNC_FONT_BOLD='Helvetica -16 bold' -env X11VNC_FONT_FIXED='Courier -14' -env X11VNC_FONT_REG_SMALL='Helvetica -12'
Puede colocar las líneas como las anteriores (sin las comillas) en su archivo ~/.x11vncrc para evitar tener que especificarlas en la línea de comandos de x11vnc.

-remote comando

Controlar remotamente algunos aspectos de un servidor x11vnc ya en ejecución. "-R" y "-r" son alias de "-remote". Después de que el comando de control remoto se envía al servidor en ejecución, el comando x11vnc "x11vnc -remote ..." sale. A menudo puede usar el comando -query (ver más abajo) para ver si el servidor x11vnc procesó su comando -remote.
El canal de comunicación predeterminado es el de las propiedades X (específicamente X11VNC_REMOTE), por lo que este comando debe ejecutarse con la configuración correcta para DISPLAY y posiblemente XAUTHORITY para conectarse al servidor X y establecer la propiedad. Alternativamente, use las opciones -display y -auth para establecerlas a los valores correctos. El servidor en ejecución no puede usar la opción -novncconnect porque eso deshabilita el canal de comunicación. Vea abajo para canales alternativos.
Por ejemplo: 'x11vnc -remote stop' (que es lo mismo que 'x11vnc -R stop') cerrará el servidor x11vnc. 'x11vnc -R shared' habilitará conexiones compartidas, y 'x11vnc -R scale:3/4' reescalará el escritorio.
Para usar un nombre diferente para la propiedad X11 (por ejemplo, para tener canales de comunicación separados para múltiples x11vnc en la misma pantalla), establezca la variable de entorno X11VNC_REMOTE a la cadena que desee, por ejemplo: -env X11VNC_REMOTE=X11VNC_REMOTE_12345 Ambos lados del canal deben usar el mismo nombre único.
Para ejecutar un conjunto de comandos en secuencia, use algo como: x11vnc -R 'script:primercomando;segundocomando;...'
Use x11vnc -R script:file=/ruta/al/archivo para leer comandos de un archivo (puede ser multilínea y usar el carácter de comentario '#') de la forma habitual. El separador ';' aún debe usarse para separar cada comando.)
Para no intentar contactar a otro proceso x11vnc y en su lugar ejecutar el comando (o consulta) directamente, prefije el comando con la cadena "DIRECT:"

bcx_xattach:str Este comando de control remoto es para uso con el programa BARCO xattach o el programa x2x. Ambos programas son para compartir 'puntero y teclado' entre pantallas X separadas. En general, las dos pantallas suelen estar cerca, por ejemplo, en el mismo escritorio, y esto permite al usuario compartir un solo puntero y teclado entre ellas. El usuario mueve el ratón hacia un borde y luego el puntero del ratón parece 'saltar' a la otra pantalla. Así, emula lo que un solo servidor X haría para dos pantallas (por ejemplo, :0.0 y :0.1). La ilusión de un solo servidor X con múltiples pantallas se logra reenviando eventos al segundo a través de la extensión XTEST.
Lo que hace el comando bcx_xattach de x11vnc es realizar algunos movimientos del puntero para intentar INDUCIR a xattach/x2x a 'saltar' a la otra pantalla. En lo que sigue, la pantalla 'maestra' se refiere a aquella que, cuando tiene 'foco', básicamente no está haciendo nada más que esperar a que el ratón cruce un borde. La pantalla 'esclava' se refiere a aquella a la que se redirige el ratón y el teclado una vez cruzado un borde en la maestra. Tenga en cuenta que el x11vnc que ejecuta el comando bcx_xattach DEBE ser el conectado a la pantalla *maestra*.
Tenga en cuenta también que cuando la entrada se está redirigiendo (a través de XTEST) desde la pantalla maestra a la pantalla esclava, el puntero y el teclado de la pantalla maestra son *grabados* por xattach/x2x. x11vnc puede utilizar esta información para verificar que el cambio de modo maestro/esclavo se ha realizado correctamente. Si especifica la opción "ifneeded" (ver más abajo) y el estado inicial de la grabación es el del estado final deseado, no se inyectan movimientos del puntero y se devuelve "DONE,GRAB_OK".
"str" debe contener una de "up", "down", "left" o "right" para indicar la dirección del 'salto'. "str" también debe contener una de "master_to_slave" o "slave_to_master" para indicar el tipo de cambio de modo inducido por el salto. Utilice "M2S" y "S2M" como alias más cortos.
"str" puede ser una lista de opciones de ajuste adicionales separadas por "+". La opción "shift=n" indica un desplazamiento de posición respecto a (0,0) (por defecto 20). "final=x+y" especifica la posición final del cursor al final de la secuencia normal de movimiento; por defecto 30+30. "extra_move=x+y" significa hacer un movimiento adicional del puntero después de "final" a x+y. "dt=n" establece el tiempo de espera en milisegundos entre movimientos del puntero (por defecto: 40ms). "retry=n" especifica el número máximo de reintentos si falla el cambio de estado de la grabación. "ifneeded" significa no aplicar los movimientos del puntero si el estado inicial de la grabación es el del estado final deseado. "nograbcheck" significa no comprobar si el estado de la grabación cambió como se esperaba y solo aplicar los movimientos del puntero (por defecto es comprobar los estados de grabación).
Si no especifica "up", etc., a bcx_xattach, no se intentará nada y el comando devolverá la cadena FAIL,NO_DIRECTION_SPECIFIED. Si no especifica "master_to_slave" o "M2S", etc., a bcx_xattach, no se intentará nada y el comando devolverá la cadena FAIL,NO_MODE_CHANGE_SPECIFIED.
En caso contrario, la cadena devuelta contendrá "DONE". Será "DONE,GRAB_OK" si el estado de la grabación cambió como se esperaba (o si se proporcionó "ifneeded" y el estado inicial de la grabación ya era el deseado). Si el estado inicial de la grabación fue incorrecto, pero el estado final de la grabación fue correcto, entonces es "DONE,GRAB_FAIL_INIT". Si el estado inicial de la grabación fue correcto, pero el estado final de la grabación fue incorrecto, entonces es "DONE,GRAB_FAIL_FINAL". Si ambos son incorrectos, será "DONE,GRAB_FAIL". En caso de fallo de grabación, la cadena irá seguida de ":p1,k1-p2,k2", donde p1,k1 indica los estados iniciales de grabación del puntero y teclado, y p2,k2 los finales. Si ocurre GRAB_FAIL o GRAB_FAIL_FINAL, la acción se intentará hasta 3 veces; intentando restablecer el estado y durmiendo un poco entre cada intento. Establezca retry=n para ajustar el número de reintentos, cero para deshabilitar los reintentos.
Ejemplos: -R bcx_xattach:down+M2S -R bcx_xattach:up+S2M -R bcx_xattach:up+S2M+nograbcheck+dt=30 -R bcx_xattach:down+M2S+extra_move=100+100
o utilice -Q en lugar de -R para recuperar el texto del resultado.
Fin de la descripción de bcx_xattach:str.
El comando vncconnect(1) de las distribuciones VNC estándar también puede utilizarse si la cadena va precedida de "cmd=". Por ejemplo, 'vncconnect cmd=stop'. Bajo ciertas circunstancias, xprop(1) puede ser utilizado si soporta -set (ver FAQ).
Si se ha proporcionado "-connect /ruta/a/archivo" al servidor x11vnc en ejecución, ese archivo puede usarse como canal de comunicación (esta es la única forma de controlar remotamente uno de los múltiples x11vnc que consultan la misma pantalla X). Simplemente ejecute: 'x11vnc -connect /ruta/a/archivo -remote ...' o puede escribir directamente en el archivo a través de algo como: "echo cmd=stop > /ruta/a/archivo", etc.

-query variable

Similar a -remote, excepto que solo consulta el valor de variable. "-Q" es un alias para "-query". Se pueden hacer múltiples consultas separando las variables por comas, por ejemplo, -query var1,var2. Los resultados vuelven en el formato ans=var1:valor1,ans=var2:valor2,... a la salida estándar. Si una variable es de solo lectura, vuelve con el prefijo "aro=" en lugar de "ans=".
Algunos comandos -remote son acciones puras que no tienen sentido como variables, por ejemplo, "stop" o "disconnect", en esos casos el valor devuelto es "N/A". Para dirigir una consulta directamente a la propiedad X11VNC_REMOTE o al archivo de conexión, use "qry=..." en lugar de "cmd=..."
