NOMBRE

xtrabackup - Documentación de Percona XtraBackup 8.0

El binario xtrabackup es un programa C compilado que está enlazado con las bibliotecas de InnoDB y las bibliotecas de cliente estándar de MySQL.

xtrabackup permite realizar copias de seguridad punto a punto de tablas InnoDB / XtraDB junto con las definiciones de esquema, tablas MyISAM y otras partes del servidor.

Las bibliotecas de InnoDB proporcionan la funcionalidad para aplicar un registro a los archivos de datos. Las bibliotecas de cliente de MySQL se utilizan para analizar las opciones de línea de comandos y el archivo de configuración.

La herramienta se ejecuta en modo --backup o --prepare, correspondientes a las dos funciones principales que realiza. Existen varias variaciones de estas funciones para realizar diferentes tareas, y hay dos modos menos utilizados, --stats y --print-param.

OTROS TIPOS DE COPIAS DE SEGURIDAD

Copias de Seguridad Incrementales

xtrabackup admite copias de seguridad incrementales. Copia solo los datos que han cambiado desde la última copia de seguridad completa. Puede realizar muchas copias de seguridad incrementales entre cada copia de seguridad completa, por lo que puede configurar un proceso de copia de seguridad como una copia completa una vez por semana y una incremental todos los días, o copias completas todos los días e incrementales cada hora.

NOTA:

Las copias de seguridad incrementales en el motor de almacenamiento MyRocks no determinan si una copia de seguridad completa o incremental anterior contiene los mismos archivos. Percona XtraBackup copia todos los archivos de MyRocks cada vez que realiza una copia de seguridad.

Las copias de seguridad incrementales funcionan porque cada página de InnoDB (generalmente de 16 kb de tamaño) contiene un número de secuencia de registro, o LSN. El LSN es el número de versión del sistema para toda la base de datos. El LSN de cada página muestra cuán recientemente se modificó. Una copia de seguridad incremental copia cada página cuyo LSN sea más nuevo que el LSN de la copia de seguridad incremental o completa anterior. Hay dos algoritmos en uso para encontrar el conjunto de tales páginas a copiar. El primero, disponible con todos los tipos y versiones de servidor, es verificar directamente el LSN de la página leyendo todas las páginas de datos. El segundo, disponible con Percona Server for MySQL, es habilitar la función de seguimiento de páginas modificadas en el servidor, que notará las páginas a medida que se modifican. Esta información se escribirá luego en un archivo separado y compacto, llamado archivo de mapa de bits. El binario xtrabackup usará ese archivo para leer solo las páginas de datos que necesita para la copia de seguridad incremental, lo que podría ahorrar muchas solicitudes de lectura. Este último algoritmo está habilitado por defecto si el binario xtrabackup encuentra el archivo de mapa de bits. Es posible especificar --incremental-force-scan para leer todas las páginas incluso si los datos del mapa de bits están disponibles.

Las copias de seguridad incrementales en realidad no comparan los archivos de datos con los archivos de datos de la copia de seguridad anterior. De hecho, puede usar --incremental-lsn para realizar una copia de seguridad incremental sin tener la copia de seguridad anterior, si conoce su LSN. Las copias de seguridad incrementales simplemente leen las páginas y comparan su LSN con el LSN de la última copia de seguridad. Sin embargo, aún necesita una copia de seguridad completa para restaurar los cambios incrementales; sin una copia de seguridad completa como base, las copias de seguridad incrementales son inútiles.

Creación de una Copia de Seguridad Incremental

Para realizar una copia de seguridad incremental, comience con una copia de seguridad completa como de costumbre. El binario xtrabackup escribe un archivo llamado xtrabackup_checkpoints en el directorio de destino de la copia de seguridad. Este archivo contiene una línea que muestra el to_lsn, que es el LSN de la base de datos al final de la copia de seguridad. Cree la copia de seguridad completa con un comando como el siguiente:

$ xtrabackup --backup --target-dir=/data/backups/base --datadir=/var/lib/mysql/

Si examina el archivo xtrabackup_checkpoints, debería ver un contenido similar al siguiente:

backup_type = full-backuped
from_lsn = 0
to_lsn = 1291135

Ahora que tiene una copia de seguridad completa, puede realizar una copia de seguridad incremental basada en ella. Utilice un comando como el siguiente:

$ xtrabackup --backup --target-dir=/data/backups/inc1 \
--incremental-basedir=/data/backups/base --datadir=/var/lib/mysql/

El directorio /data/backups/inc1/ ahora debería contener archivos delta, como ibdata1.delta y test/table1.ibd.delta. Estos representan los cambios desde el LSN 1291135. Si examina el archivo xtrabackup_checkpoints en este directorio, debería ver algo similar a lo siguiente:

backup_type = incremental
from_lsn = 1291135
to_lsn = 1291340

El significado debería ser autoevidente. Ahora es posible utilizar este directorio como base para otra copia de seguridad incremental:

$ xtrabackup --backup --target-dir=/data/backups/inc2 \
--incremental-basedir=/data/backups/inc1 --datadir=/var/lib/mysql/

Preparación de las Copias de Seguridad Incrementales

El paso --prepare para las copias de seguridad incrementales no es el mismo que para las copias de seguridad normales. En las copias de seguridad normales, se realizan dos tipos de operaciones para hacer que la base de datos sea consistente: las transacciones confirmadas se reproducen desde el archivo de registro contra los archivos de datos, y las transacciones no confirmadas se deshacen. Debe omitir la reversión de las transacciones no confirmadas al preparar una copia de seguridad, ya que las transacciones que no estaban confirmadas en el momento de su copia de seguridad pueden estar en progreso, y es probable que se confirmen en la próxima copia de seguridad incremental. Debe usar la opción --apply-log-only para evitar la fase de reversión.

NOTA:

Si no usa la opción --apply-log-only para evitar la fase de reversión, sus copias de seguridad incrementales serán inútiles. Después de que las transacciones hayan sido deshechas, no se podrán aplicar copias de seguridad incrementales posteriores.

Comenzando con la copia de seguridad completa que creó, puede prepararla y luego aplicar las diferencias incrementales. Recuerde que tiene las siguientes copias de seguridad:

/data/backups/base
/data/backups/inc1
/data/backups/inc2

Para preparar la copia de seguridad base, necesita ejecutar --prepare como de costumbre, pero evitando la fase de reversión:

xtrabackup --prepare --apply-log-only --target-dir=/data/backups/base

La salida debería terminar con algún texto como el siguiente:

101107 20:49:43  InnoDB: Shutdown completed; log sequence number 1291135

El número de secuencia de registro debe coincidir con el to_lsn de la copia de seguridad base, que vio anteriormente.

Esta copia de seguridad es en realidad segura para restaurar tal como está ahora, aunque se omitió la fase de reversión. Si la restaura e inicia MySQL, InnoDB detectará que la fase de reversión no se realizó, y lo hará en segundo plano, como suele hacer para la recuperación ante fallos al iniciar. Le notificará que la base de datos no se cerró normalmente.

Para aplicar la primera copia de seguridad incremental a la copia de seguridad completa, debe usar el siguiente comando:

xtrabackup --prepare --apply-log-only --target-dir=/data/backups/base \
--incremental-dir=/data/backups/inc1

Esto aplica los archivos delta a los archivos en /data/backups/base, lo que los actualiza hasta el momento de la copia de seguridad incremental. Luego aplica el registro de rehacer como de costumbre al resultado. Los datos finales están en /data/backups/base, no en el directorio incremental. Debería ver alguna salida como la siguiente:

incremental backup from 1291135 is enabled.
xtrabackup: cd to /data/backups/base/
xtrabackup: This target seems to be already prepared.
xtrabackup: xtrabackup_logfile detected: size=2097152, start_lsn=(1291340)
Applying /data/backups/inc1/ibdata1.delta ...
Applying /data/backups/inc1/test/table1.ibd.delta ...
.... snip
101107 20:56:30  InnoDB: Shutdown completed; log sequence number 1291340

Nuevamente, el LSN debe coincidir con lo que vio de su inspección anterior de la primera copia de seguridad incremental. Si restaura los archivos de /data/backups/base, debería ver el estado de los datos

base según la primera copia de seguridad incremental.

Preparar la segunda copia de seguridad incremental es un proceso similar: aplique las diferencias a la copia de seguridad base (modificada), y avanzará sus datos en el tiempo hasta el punto de la segunda copia de seguridad incremental:

xtrabackup --prepare --target-dir=/data/backups/base \
--incremental-dir=/data/backups/inc2

NOTA:

--apply-log-only debe usarse al fusionar todos los incrementales excepto el último. Es por eso que la línea anterior no contiene la opción --apply-log-only. Incluso si se usara --apply-log-only en el último paso, la copia de seguridad seguiría siendo consistente, pero en ese caso el servidor realizaría la fase de reversión.

Si desea evitar el aviso de que InnoDB no se apagó normalmente, cuando haya aplicado las diferencias deseadas a la copia de seguridad base, puede ejecutar --prepare nuevamente sin deshabilitar la fase de reversión.

Restauración de Copias de Seguridad Incrementales

Después de preparar las copias de seguridad incrementales, el directorio base contiene los mismos datos que la copia de seguridad completa. Para restaurar esta copia de seguridad, puede usar este comando: xtrabackup --copy-back --target-dir=BASE-DIR

Es posible que deba cambiar la propiedad como se detalla en restoring_a_backup.

Copias de Seguridad Incrementales en Streaming Usando xbstream

Las copias de seguridad incrementales en streaming se pueden realizar con la opción de streaming xbstream. Actualmente, las copias de seguridad se empaquetan en formato personalizado de xbstream. Con esta función, también debe realizar una copia de seguridad BASE. Realizando una copia de seguridad base.INDENT 0.0

$ xtrabackup --backup --target-dir=/data/backups


Realizando una copia de seguridad local.INDENT 0.0 
$ xtrabackup --backup --incremental-lsn=LSN-number --stream=xbstream --target-dir=./ > incremental.xbstream


Desempaquetando la copia de seguridad.INDENT 0.0 
$ xbstream -x < incremental.xbstream


Realizando una copia de seguridad local y transmitiéndola al servidor remoto y desempaquetándola.INDENT 0.0 
$ xtrabackup --backup --incremental-lsn=LSN-number --stream=xbstream --target-dir=./
$ ssh user@hostname " cat - | xbstream -x -C > /backup-dir/"


Copias de Seguridad Parciales

xtrabackup admite la creación de copias de seguridad parciales cuando la opción innodb_file_per_table está habilitada. Hay tres formas de crear copias de seguridad parciales:

1.
coincidiendo los nombres de las tablas con una expresión regular
2.
proporcionando una lista de nombres de tablas en un archivo
3.
proporcionando una lista de bases de datos

ADVERTENCIA:

No copie la copia de seguridad preparada.

La restauración de copias de seguridad parciales debe realizarse importando las tablas, no utilizando la opción --copy-back. No se recomienda ejecutar copias de seguridad incrementales después de ejecutar una copia de seguridad parcial.

Aunque hay algunos escenarios en los que la restauración se puede hacer copiando los archivos, esto puede provocar inconsistencias en la base de datos en muchos casos y no es una forma recomendada de hacerlo.

A efectos de esta página del manual, asumiremos que hay una base de datos llamada test que contiene las tablas llamadas t1 y t2.

ADVERTENCIA:

Si alguna de las tablas coincidentes o listadas se elimina durante la copia de seguridad, xtrabackup fallará.

Creación de Copias de Seguridad Parciales

Existen múltiples formas de especificar qué parte del total de datos se está respaldando:

  • Use la opción --tables para listar los nombres de las tablas
  • Use la opción --tables-file para listar las tablas en un archivo
  • Use la opción --databases para listar las bases de datos
  • Use la opción --databases-file para listar las bases de datos

La opción --tables

El primer método implica la opción --tables de xtrabackup. El valor de la opción es una expresión regular que se compara con el nombre de la base de datos completamente calificado y el nombre de la tabla en el formato nombrebasedatos.nombretabla.

Para respaldar solo tablas en la base de datos test, use el siguiente comando:

$ xtrabackup --backup --datadir=/var/lib/mysql --target-dir=/data/backups/ \
--tables="^test[.].*"

Para respaldar solo la tabla test.t1, use el siguiente comando:

$ xtrabackup --backup --datadir=/var/lib/mysql --target-dir=/data/backups/ \
--tables="^test[.]t1"

La opción --tables-file

La opción --tables-file especifica un archivo que puede contener múltiples nombres de tablas, un nombre de tabla por línea en el archivo. Solo las tablas nombradas en el archivo se respaldarán. Los nombres se comparan exactamente, sensibles a mayúsculas y minúsculas, sin coincidencia de patrones o expresiones regulares. Los nombres de las tablas deben estar completamente calificados en formato nombrebasedatos.nombretabla.

$ echo "mydatabase.mytable" > /tmp/tables.txt
$ xtrabackup --backup --tables-file=/tmp/tables.txt

Las opciones --databases y --databases-file

La opción ` --databases` acepta una lista separada por espacios de las bases de datos y tablas a respaldar en formato nombrebasedatos[.nombretabla]. Además de esta lista, asegúrese de especificar las bases de datos mysql, sys y

performance_schema. Estas bases de datos son necesarias al restaurar las bases de datos usando xtrabackup --copy-back.

NOTA:

Las tablas procesadas durante el paso --prepare también pueden agregarse a la copia de seguridad, incluso si no están listadas explícitamente por el parámetro, si se crearon después de que comenzó la copia de seguridad.
$ xtrabackup --databases='mysql sys performance_schema test ...'

La opción --databases-file

La opción --databases-file especifica un archivo que puede contener múltiples bases de datos y tablas en formato nombrebasedatos[.nombretabla], un nombre de elemento por línea en el archivo. Los nombres se comparan exactamente, sensibles a mayúsculas y minúsculas, sin coincidencia de patrones o expresiones regulares.

NOTA:

Las tablas procesadas durante el paso --prepare también pueden agregarse a la copia de seguridad, incluso si no están listadas explícitamente por el parámetro, si se crearon después de que comenzó la copia de seguridad.

Preparación de Copias de Seguridad Parciales

El procedimiento es análogo a restaurar tablas individuales: aplique los registros y use la opción --export:

$ xtrabackup --prepare --export --target-dir=/path/to/partial/backup

Cuando use la opción --prepare en una copia de seguridad parcial, verá advertencias sobre tablas que no existen. Esto se debe a que estas tablas existen en el diccionario de datos dentro de InnoDB, pero los archivos .ibd correspondientes no existen. No se copiaron en el directorio de copia de seguridad. Estas tablas se eliminarán del diccionario de datos y, cuando restaure la copia de seguridad e inicie InnoDB, ya no existirán y no causarán errores ni advertencias en el archivo de registro.

No se encontró ningún archivo asociado con el ID del tablespace: 5

Use --innodb-directories para encontrar los archivos del tablespace. Si eso falla, use --innodb-force-recovery=1 para ignorar esto y perder permanentemente todos los cambios en los tablespaces faltantes.

Restauración de Copias de Seguridad Parciales

La restauración debe realizarse restaurando tablas individuales de la copia de seguridad parcial en el servidor.

También se puede hacer copiando la copia de seguridad preparada a un directorio de datos "limpio" (en ese caso, asegúrese de incluir la base de datos mysql) al directorio de datos al que está moviendo la copia de seguridad. Se puede crear una base de datos del sistema con lo siguiente:

$ sudo mysql --initialize --user=mysql

Una vez que inicie el servidor, es posible que vea que mysql se queja de tablespaces faltantes:

2021-07-19T12:42:11.077200Z 1 [Warning] [MY-012351] [InnoDB] Tablespace 4, name 'test1/t1', file './d2/test1.ibd' is missing!
2021-07-19T12:42:11.077300Z 1 [Warning] [MY-012351] [InnoDB] Tablespace 4, name 'test1/t1', file './d2/test1.ibd' is missing!

Para limpiar la base de datos huérfana del diccionario de datos, debe crear manualmente el directorio de la base de datos faltante y luego DROP esta base de datos desde el servidor.

Ejemplo de creación de la base de datos faltante:

$ mkdir /var/lib/mysql/test1/d2

Ejemplo de eliminación de la base de datos del servidor:

Análisis de Estadísticas de Tablas

El binario xtrabackup puede analizar archivos de datos InnoDB en modo de solo lectura para proporcionar estadísticas sobre ellos. Para hacer esto, debe usar la opción --stats. Puede combinar esto con la opción --tables para limitar los archivos a examinar. También utiliza la opción --use-memory.

Puede realizar el análisis en un servidor en ejecución, con cierta probabilidad de errores debido a que los datos cambian durante el análisis. O bien, puede analizar una copia de seguridad de la base de datos. De cualquier manera, para usar la función de estadísticas, necesita una copia limpia de la base de datos, incluidos los archivos de registro de tamaño correcto.

es, necesitas ejecutar con --prepare dos veces para usar esta funcionalidad en una copia de seguridad.

El resultado de ejecutar en una copia de seguridad puede ser similar a lo siguiente:

<ESTADÍSTICAS DEL ÍNDICE>
  tabla: test/tabla1, índice: PRIMARY, id de espacio: 12, página raíz 3
  estadísticas estimadas en el diccionario:
    valores clave: 25265338, páginas hoja 497839, páginas de tamaño 498304
  estadísticas reales:
     páginas de nivel 2: páginas=1, datos=5395 bytes, datos/páginas=32%
     páginas de nivel 1: páginas=415, datos=6471907 bytes, datos/páginas=95%
        páginas hoja: registros=25958413, páginas=497839, datos=7492026403 bytes, datos/páginas=91%

Esto se puede interpretar de la siguiente manera:

  • La primera línea simplemente muestra el nombre de la tabla e índice y sus identificadores internos. Si ves un índice llamado GEN_CLUST_INDEX, ese es el índice agrupado de la tabla, creado automáticamente porque no creaste explícitamente una CLAVE PRIMARIA.
  • La información de estadísticas estimadas en el diccionario es similar a los datos que se recopilan a través de ANALYZE TABLE dentro de InnoDB para almacenarse como estadísticas de cardinalidad estimada y pasarse al optimizador de consultas.
  • La información de estadísticas reales es el resultado de escanear las páginas de datos y calcular información exacta sobre el índice.
  • Las páginas de nivel <X>: la salida significa que la línea muestra información sobre las páginas en ese nivel del árbol del índice. Cuanto mayor sea <X>, más lejos estará de las páginas hoja, que son el nivel 0. La primera línea es la página raíz.
  • La salida de páginas hoja muestra las páginas hoja, por supuesto. Aquí es donde se almacenan los datos de la tabla.
  • La salida de páginas externas: (no mostrada) muestra páginas externas grandes que contienen valores demasiado largos para caber en la fila misma, como valores largos de BLOB y TEXT.
  • registros es el número real de registros (filas) en las páginas hoja.
  • páginas es el recuento de páginas.
  • datos es el tamaño total de los datos en las páginas, en bytes.
  • datos/páginas se calcula como (datos / (páginas * TAMAÑO_PÁGINA)) * 100%. Nunca alcanzará el 100% debido al espacio reservado para las cabeceras y pies de página.

Script para Formatear la Salida

El siguiente script se puede utilizar para resumir y tabular la salida de la información de estadísticas:

tabulate-xtrabackup-stats.pl
#!/usr/bin/env perl
use strict;
use warnings FATAL => 'all';
my $script_version = "0.1";
my $PG_SIZE = 16_384; # InnoDB por defecto usa páginas de 16k, cambia si es necesario.
my ($cur_idx, $cur_tbl);
my (%idx_stats, %tbl_stats);
my ($max_tbl_len, $max_idx_len) = (0, 0);
while ( my $line = <> ) {
   if ( my ($t, $i) = $line =~ m/tabla: (.*), índice: (.*), id de espacio:/ ) {
      $t =~ s!/!.!;
      $cur_tbl = $t;
      $cur_idx = $i;
      if ( length($i) > $max_idx_len ) {
         $max_idx_len = length($i);
      }
      if ( length($t) > $max_tbl_len ) {
         $max_tbl_len = length($t);
      }
   }
   elsif ( my ($kv, $lp, $sp) = $line =~ m/valores clave: (\d+), \D*(\d+), \D*(\d+)/ ) {
      @{$idx_stats{$cur_tbl}->{$cur_idx}}{qw(est_kv est_lp est_sp)} = ($kv, $lp, $sp);
      $tbl_stats{$cur_tbl}->{est_kv} += $kv;
      $tbl_stats{$cur_tbl}->{est_lp} += $lp;
      $tbl_stats{$cur_tbl}->{est_sp} += $sp;
   }
   elsif ( my ($l, $pages, $bytes) = $line =~ m/(?:nivel (\d+)|hoja) pages:.*pages=(\d+), data=(\d+) bytes/ ) {
      $l ||= 0;
      $idx_stats{$cur_tbl}->{$cur_idx}->{real_pages} += $pages;
      $idx_stats{$cur_tbl}->{$cur_idx}->{real_bytes} += $bytes;
      $tbl_stats{$cur_tbl}->{real_pages} += $pages;
      $tbl_stats{$cur_tbl}->{real_bytes} += $bytes;
   }
}
my $hdr_fmt = "%${max_tbl_len}s %${max_idx_len}s %9s %10s %10s\n";
my @headers = qw(TABLA ÍNDICE PÁGINAS_TOTALES PÁGINAS_LIBRES PCT_LLENO);
printf $hdr_fmt, @headers;
my $row_fmt = "%${max_tbl_len}s %${max_idx_len}s %9d %10d %9.1f%%\n";
foreach my $t ( sort keys %tbl_stats ) {
   my $tbl = $tbl_stats{$t};
   printf $row_fmt, $t, "", $tbl->{est_sp}, $tbl->{est_sp} - $tbl->{real_pages},
      $tbl->{real_bytes} / ($tbl->{real_pages} * $PG_SIZE) * 100;
   foreach my $i ( sort keys %{$idx_stats{$t}} ) {
      my $idx = $idx_stats{$t}->{$i};
      printf $row_fmt, $t, $i, $idx->{est_sp}, $idx->{est_sp} - $idx->{real_pages},
         $idx->{real_bytes} / ($idx->{real_pages} * $PG_SIZE) * 100;
   }
}

Trabajando con Registros Binarios

El binario xtrabackup se integra con la tabla log_status. Esta integración permite a xtrabackup imprimir la posición del registro binario correspondiente a la copia de seguridad, para que pueda usar esta posición del registro binario para aprovisionar una nueva réplica o realizar una recuperación a un punto en el tiempo.

Encontrando la Posición del Registro Binario

Copias de seguridad en streaming

Percona XtraBackup admite el modo de streaming. El modo de streaming envía una copia de seguridad a STDOUT en formato xbstream en lugar de copiar los archivos al directorio de copia de seguridad.

Este método le permite utilizar otros programas para filtrar la salida de la copia de seguridad, lo que proporciona una mayor flexibilidad para el almacenamiento de la copia de seguridad. Por ejemplo, la compresión se logra canalizando la salida a una utilidad de compresión. Uno de los beneficios de las copias de seguridad en streaming y el uso de tuberías de Unix es que las copias de seguridad se pueden cifrar automáticamente.

Para utilizar la función de streaming, debe usar la opción --stream, proporcionando el formato del stream (xbstream) y dónde almacenar los archivos temporales:

$ xtrabackup --stream=xbstream --target-dir=/tmp

xtrabackup utiliza xbstream para enviar todos los archivos de datos a STDOUT, en un formato especial xbstream. Después de terminar de enviar todos los archivos de datos a STDOUT, detiene xtrabackup y también envía el archivo de registro guardado.

Cifrado de copias de seguridad

Percona XtraBackup admite el cifrado y descifrado de copias de seguridad locales y en streaming con la opción xbstream, añadiendo otra capa de protección. El cifrado se implementa utilizando la biblioteca libgcrypt de GnuPG.

Creación de copias de seguridad cifradas

Para realizar una copia de seguridad cifrada, se deben especificar las siguientes opciones (las opciones --encrypt-key y --encrypt-key-file son mutuamente excluyentes, es decir, solo una de ellas debe proporcionarse):

  • --encrypt
  • :option:` --encrypt-key`
  • :option:` --encrypt-key-file`

Tanto la opción --encrypt-key como la opción --encrypt-key-file se pueden utilizar para especificar la clave de cifrado. Se puede generar una clave de cifrado con un comando como openssl rand -base64 32

El resultado de este comando debería verse así:

U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=

Este valor se puede utilizar como clave de cifrado.

La opción --encrypt-key

Un ejemplo del comando xtrabackup que utiliza la opción --encrypt-key debería verse así:

"> 
$  xtrabackup --backup --encrypt=AES256 --encrypt-key="U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=" --target-dir=/data/backup

La opción --encrypt-key-file

Utilice la opción --encrypt-key-file de la siguiente manera:

$ xtrabackup --backup --encrypt=AES256 --encrypt-key-file=/data/backups/keyfile --target-dir=/data/backup

NOTA:

Dependiendo del editor de texto que utilice para crear el KEYFILE, el editor puede insertar automáticamente el carácter CRLF (fin de línea). Esto provocará que el tamaño de la clave aumente y, por lo tanto, que sea inválida. La forma recomendada de crear el archivo es usando la línea de comandos: echo -n "U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=" > /data/backups/keyfile.

Optimizar el proceso de cifrado

Hay dos nuevas opciones disponibles para copias de seguridad cifradas que pueden utilizarse para acelerar el proceso de cifrado. Estas son --encrypt-threads y --encrypt-chunk-size. Al utilizar la opción --encrypt-threads se pueden especificar varios hilos para ser utilizados en el cifrado en paralelo. La opción --encrypt-chunk-size se puede utilizar para especificar el tamaño (en bytes) del búfer de cifrado de trabajo para cada hilo de cifrado (el valor predeterminado es 64K).

Descifrar copias de seguridad cifradas

Las copias de seguridad se pueden descifrar con xbcrypt. La siguiente línea de comandos se puede utilizar para descifrar toda la carpeta:

$ for i in `find . -iname "*\.xbcrypt"`; do xbcrypt -d --encrypt-key-file=/root/secret_key --encrypt-algo=AES256 < $i > $(dirname $i)/$(basename $i .xbcrypt) && rm $i; done

La opción --decrypt de Percona XtraBackup se ha implementado y se puede utilizar para descifrar las copias de seguridad:

$ xtrabackup --decrypt=AES256 --encrypt-key="U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=" --target-dir=/data/backup/

Percona XtraBackup no elimina automáticamente los archivos cifrados. Para limpiar el directorio de copias de seguridad, los usuarios deben eliminar los archivos *.xbcrypt.

NOTA:

Se puede utilizar --parallel con la opción --decrypt para descifrar varios archivos simultáneamente.

Una vez descifrados los archivos, la copia de seguridad puede prepararse.

Preparar copias de seguridad cifradas

Después de que las copias de seguridad hayan sido descifradas, pueden prepararse de la misma manera que las copias de seguridad completas estándar con la opción --prepare:

$ xtrabackup --prepare --target-dir=/data/backup/

Restaurar copias de seguridad cifradas

xtrabackup ofrece la opción --copy-back para restaurar una copia de seguridad en el datadir del servidor:

$ xtrabackup --copy-back --target-dir=/data/backup/

Copiará todos los archivos relacionados con los datos de vuelta al datadir del servidor, determinado por el archivo de configuración my.cnf del servidor. Debería comprobar la última línea de la salida para ver un mensaje de éxito:

150318 11:08:13  xtrabackup: completed OK!

Opción FLUSH TABLES WITH READ LOCK

La opción FLUSH TABLES WITH READ LOCK realiza lo siguiente con un bloqueo de lectura global:

  • Cierra todas las tablas abiertas
  • Bloquea todas las tablas de todas las bases de datos

Libera el bloqueo con UNLOCK TABLES.

NOTA:

FLUSH TABLES WITH READ LOCK no impide la inserción de filas en las tablas de registro.

Para garantizar copias de seguridad consistentes, utilice la opción FLUSH TABLES WITH READ LOCK antes de realizar una copia de seguridad de archivos no InnoDB. La opción no afecta a las consultas de larga duración.

Las consultas de larga duración con FLUSH TABLES WITH READ LOCK activado pueden dejar el servidor en modo de solo lectura hasta que las consultas finalicen. Matar FLUSH TABLES WITH READ LOCK no ayuda si la base de datos se encuentra en el estado Waiting for table flush o Waiting for master to send event. Para volver a la operación normal, debe matar todas las consultas de larga duración.

NOTA:

Todo lo descrito en esta sección no tiene ningún efecto cuando se utilizan bloqueos de copia de seguridad. Percona XtraBackup utilizará bloqueos de copia de seguridad cuando estén disponibles como una alternativa ligera a FLUSH TABLES WITH READ LOCK. Esta función está disponible en Percona Server for MySQL 5.6+. Percona XtraBackup la utiliza automáticamente para copiar datos no InnoDB para evitar bloquear consultas DML que modifican tablas InnoDB.

Para evitar que esto suceda, se han implementado dos cosas:

  • xtrabackup espera un momento oportuno para emitir el bloqueo global
  • xtrabackup mata todas las consultas o solo las consultas SELECT que impiden la adquisición del bloqueo global

Esperar a que finalicen las consultas

Debe emitir un bloqueo global cuando no se estén ejecutando consultas largas. Esperar a emitir el bloqueo global durante un período de tiempo prolongado no es un buen método. La espera puede extender el tiempo necesario para realizar la copia de seguridad. La opción --ftwrl-wait-timeout puede limitar el tiempo de espera. Si no se puede emitir el bloqueo durante este tiempo, xtrabackup detiene la opción, sale con un mensaje de error y la copia de seguridad no se realiza.

El valor predeterminado para esta opción es cero (0), lo que desactiva la opción.

Otra posibilidad es especificar el tipo de consulta a esperar. En este caso --ftwrl-wait-query-type. Los valores posibles son all y update. Cuando se usa all, xtrabackup esperará a que todas las consultas de larga duración (tiempo de ejecución superior al permitido por --ftwrl-wait-threshold) finalicen antes de ejecutar FLUSH TABLES WITH READ LOCK. Cuando se usa update, xtrabackup esperará a que las consultas UPDATE/ALTER/REPLACE/INSERT finalicen.

El tiempo necesario para que una consulta específica se complete es difícil de predecir. Suponemos que las consultas de larga duración no finalizarán de manera oportuna. Otras consultas que se ejecutan durante un corto período de tiempo finalizan rápidamente. xtrabackup utiliza el valor de la opción --ftwrl-wait-threshold para especificar las consultas de larga duración y bloqueará un bloqueo global. Para utilizar esta opción, el usuario de xtrabackup debe tener los privilegios PROCESS y SUPER.

Matar las consultas de bloqueo

La segunda opción es matar todas las consultas que impiden la adquisición del bloqueo global. En este caso, todas las consultas que se ejecutan durante más tiempo que FLUSH TABLES WITH READ LOCK son bloqueadores potenciales. Aunque todas las consultas pueden ser matadas, se puede especificar tiempo adicional para que las consultas de corta duración finalicen utilizando la opción --kill-long-queries-timeout. Esta opción especifica el tiempo para que las consultas se completen, después de alcanzar el valor, todas las consultas en ejecución serán matadas. El valor predeterminado es cero, lo que desactiva esta función.

La opción --kill-long-query-type se puede utilizar para especificar todas las consultas o solo las consultas SELECT que impiden que se adquiera el bloqueo global. Para utilizar esta opción, el usuario de xtrabackup debe tener los privilegios PROCESS y SUPER.

Resumen de opciones

  • --ftwrl-wait-timeout (segundos) - cuánto tiempo esperar un momento oportuno. El valor predeterminado es 0, no esperar.
  • --ftwrl-wait-query-type - qué consultas largas deben finalizar antes de ejecutar FLUSH TABLES WITH READ LOCK. El valor predeterminado es all.
  • --ftwrl-wait-threshold (segundos) - cuánto tiempo debe ejecutarse una consulta antes de considerarla de larga duración y un posible bloqueador del bloqueo global.
  • --kill-long-queries-timeout (segundos) - cuánto tiempo damos para que las consultas se completen después de emitir FLUSH TABLES WITH READ LOCK antes de empezar a matar. El valor predeterminado es 0, no matar.
  • --kill-long-query-type - qué consultas deben ser matadas una vez expirado kill-long-queries-timeout.

Ejemplo

Ejecutar xtrabackup con las siguientes opciones hará que xtrabackup no espere más de 3 minutos a que finalicen todas las consultas con más de 40 segundos de antigüedad.

$  xtrabackup --backup --ftwrl-wait-threshold=40 \
--ftwrl-wait-query-type=all --ftwrl-wait-timeout=180 \
--kill-long-queries-timeout=20 --kill-long-query-type=all \
--target-dir=/data/backups/

Después de emitir FLUSH TABLES WITH READ LOCK, xtrabackup esperará 20 segundos para que se adquiera el bloqueo. Si el bloqueo aún no se ha adquirido después de 20 segundos, matará todas las consultas que se ejecutan durante más tiempo que FLUSH TABLES WITH READ LOCK.

Tuning for Performance

There are two options that can be used to tune xtrabackup performance:

  • --parallel
  • --compress-threads
  • --rsync

The --parallel Option

This option speeds up the backup process on servers with multiple tablespaces. This is done by streaming backup copies of multiple tablespaces in parallel.

For this option to be useful, the database must be configured with either the innodb_file_per_table option enabled, or the shared tablespace must be stored in multiple ibdata files with the innodb_data_file_path option. Having multiple files for the database (or splitting one into many) does not have a measurable impact on performance.

As this feature is implemented at the file level, concurrent file transfer can sometimes increase I/O throughput when doing a backup on highly fragmented data files, due to the overlap of a greater number of random read requests. You should consider tuning the filesystem also to obtain the maximum performance (e.g. checking fragmentation).

If the data is stored on a single file, this option will have no effect.

To use this feature, simply add the option to a local backup, for example:

$ xtrabackup --backup --parallel=4 --target-dir=/path/to/backup

By using the xbstream in streaming backups, you can additionally speed up the compression process with the --compress-threads option. This option specifies the number of threads created by xtrabackup for for parallel data compression. The default value for this option is 1.

To use this feature, simply add the option to a local backup, for example:

$ xtrabackup --backup --stream=xbstream --compress --compress-threads=4 --target-dir=./ > backup.xbstream

Before applying logs, compressed files will need to be uncompressed.

The --rsync Option

In order to speed up the backup process and to minimize the time FLUSH TABLES WITH READ LOCK is blocking the writes, the option --rsync should be used. When this option is specified, xtrabackup uses rsync to copy all non-InnoDB files instead of spawning a separate cp for each file, which can be much faster for servers with a large number of databases or tables. xtrabackup will call the rsync twice, once before the FLUSH TABLES WITH READ LOCK and once during to minimize the time the read lock is being held. During the second rsync call, it will only synchronize the changes to non-transactional data (if any) since the first call performed before the FLUSH TABLES WITH READ LOCK. Note that Percona XtraBackup will use Backup locks where available as a lightweight alternative to FLUSH TABLES WITH READ LOCK. This feature is available in Percona Server for MySQL 5.6+. Percona XtraBackup uses this automatically to copy non-InnoDB data to avoid blocking DML queries that modify InnoDB tables.

NOTE:

This option cannot be used together with the --stream option.

Point-In-Time recovery

Recovering up to particular moment in database's history can be done with xtrabackup and the binary logs of the server.

Note that the binary log contains the operations that modified the database from a point in the past. You need a full datadir as a base, and then you can apply a series of operations from the binary log to make the data match what it was at the point in time you want.

$ xtrabackup --backup --target-dir=/path/to/backup
$ xtrabackup --prepare --target-dir=/path/to/backup

For more details on these procedures, see creating_a_backup and preparing_a_backup.

Now, suppose that some time has passed, and you want to restore the database to a certain point in the past, having in mind that there is the constraint of the point where the snapshot was taken.

To find out what is the situation of binary logging in the server, execute the following queries:

mysql> SHOW BINARY LOGS;
+------------------+-----------+
| Log_name         | File_size |
+------------------+-----------+
| mysql-bin.000001 |       126 |
| mysql-bin.000002 |      1306 |
| mysql-bin.000003 |       126 |
| mysql-bin.000004 |       497 |
+------------------+-----------+

and

mysql> SHOW MASTER STATUS;
+------------------+----------+--------------+------------------+
| File             | Position | Binlog_Do_DB | Binlog_Ignore_DB |
+------------------+----------+--------------+------------------+
| mysql-bin.000004 |      497 |              |                  |
+------------------+----------+--------------+------------------+

The first query will tell you which files contain the binary log and the second one which file is currently being used to record changes, and the current position within it. Those files are stored usually in the datadir (unless other location is specified when the server is started with the --log-bin= option).

To find out the position of the snapshot taken, see the xtrabackup_binlog_info at the backup's directory:

$ cat /path/to/backup/xtrabackup_binlog_info
mysql-bin.000003      57

This will tell you which file was used at moment of the backup for the binary log and its position. That position will be the effective one when you restore the backup:

$ xtrabackup --copy-back --target-dir=/path/to/backup

As the restoration will not affect the binary log files (you may need to adjust file permissions, see restoring_a_backup), the next step is extracting the queries from the binary log with mysqlbinlog starting from the position of the snapshot and redirecting it to a file

$ mysqlbinlog /path/to/datadir/mysql-bin.000003 /path/to/datadir/mysql-bin.000004 \
    --start-position=57 > mybinlog.sql

Note that if you have multiple files for the binary log, as in the example, you have to extract the queries with one process, as shown above.

Inspect the file with the queries to determine which position or date corresponds to the point-in-time wanted. Once determined, pipe it to the server. Assuming the point is 11-12-25 01:00:00:

$ mysqlbinlog /path/to/datadir/mysql-bin.000003 /path/to/datadir/mysql-bin.000004 \
    --start-position=57 --stop-datetime="11-12-25 01:00:00" | mysql -u root -p

and the database will be rolled forward up to that Point-In-Time.

Making Backups in Replication Environments

There are options specific to back up from a replication replica.

The --slave-info Option

This option is useful when backing up a replication replica server. It prints the binary log position and name of the source server. It also writes this information to the xtrabackup_slave_info file as a CHANGE MASTER statement.

This option is useful for setting up a new replica for this source. You can start a replica server with this backup and issue the statement saved in the xtrabackup_slave_info file. More details of this procedure can be found in replication_howto.

The --safe-slave-backup Option

In order to assure a consistent replication state, this option stops the replication SQL thread and waits to start backing up until Slave_open_temp_tables in SHOW STATUS is zero. If there are no open temporary tables, the backup will take place, otherwise the SQL thread will be started and stopped until there are no open temporary tables. The backup will fail if Slave_open_temp_tables does not become zero after --safe-slave-backup-timeout seconds (defaults to 300 seconds). The replication SQL thread will be restarted when the backup finishes.

Using this option is always recommended when taking backups from a replica server.

WARNING:

Make sure your replica is a true replica of the source before using it as a source for backup. A good tool to validate a replica is pt-table-checksum.

Store backup history on the server

Percona XtraBackup supports storing the backups history on the server. This feature was implemented in Percona XtraBackup 2.2. Storing backup history on the server was implemented to provide users with additional information about backups that are being taken. Backup history information will be stored in the PERCONA_SCHEMA.XTRABACKUP_HISTORY table.

To use this feature the following options are available:

  • --history =<name> : This option enables the history feature and allows the user to specify a backup series name that will be placed within the history record.
  • --incremental-history-name =<name> : This option allows an incremental backup to be made based on a specific history series by name. xtrabackup will search the history table looking for the most recent (highest to_lsn) backup in the series and take the to_lsn value to use as it's starting lsn. This is mutually exclusive with --incremental-history-uuid, --incremental-basedir and --incremental-lsn options. If no valid LSN can be found (no series by that name) xtrabackup will return with an error.
  • --incremental-history-uuid =<uuid> : Allows an incremental backup to be made based on a specific history record identified by UUID. xtrabackup will search the history table looking for the record matching UUID and take the to_lsn value to use as it's starting LSN. This options is mutually exclusive with --incremental-basedir, --incremental-lsn and --incremental-history-name options. If no valid LSN can be found (no record by that UUID or missing to_lsn), xtrabackup will return with an error.

NOTE:

Backup that's currently being performed will NOT exist in the xtrabackup_history table within the resulting backup set as the record will not be added to that table until after the backup has been taken.

If you want access to backup history outside of your backup set in the case of some catastrophic event, you will need to either perform a mysqldump, partial backup or SELECT * on the history table after xtrabackup completes.

IMPLEMENTATION

Implementation Details

This page contains notes on various internal aspects of the xtrabackup tool's operation.

File Permissions

xtrabackup opens the source data files in read-write mode, although it does not modify the files. This means that you must run xtrabackup as a user who has permission to write the data files. The reason for opening the files in read-write mode is that xtrabackup uses the embedded InnoDB libraries to open and read the files, and InnoDB opens them in read-write mode because it normally assumes it is going to write to them.

Tuning the OS Buffers

Because xtrabackup reads large amounts of data from the filesystem, it uses posix_fadvise() where possible, to instruct the operating system not to try to cache the blocks it reads from disk. Without this hint, the operating system would prefer to cache the blocks, assuming that xtrabackup is likely to need them again, which is not the case. Caching such large files can place pressure on the operating system's virtual memory and cause other processes, such as the database server, to be swapped out. The xtrabackup tool avoids this with the following hint on both the source and destination files:

posix_fadvise(file, 0, 0, POSIX_FADV_DONTNEED)

In addition, xtrabackup asks the operating system to perform more aggressive read-ahead optimizations on the source files:

posix_fadvise(file, 0, 0, POSIX_FADV_SEQUENTIAL)

Copying Data Files

When copying the data files to the target directory, xtrabackup reads and writes 1 MB of data at a time. This is not configurable. When copying the log file, xtrabackup reads and writes 512 bytes at a time. This is also not possible to configure, and matches InnoDB's behavior (workaround exists in Percona Server for MySQL because it has an option to tune innodb_log_block_size for XtraDB, and in that case Percona XtraBackup will match the tuning).

After reading from the files, xtrabackup iterates over the 1MB buffer a page at a time, and checks for page corruption on each page with InnoDB's buf_page_is_corrupted() function. If the page is corrupt, it re-reads and retries up to 10 times for each page. It skips this check on the doublewrite buffer.

xtrabackup Exit Codes

The xtrabackup binary exits with the traditional success value of 0 after a backup when no error occurs. If an error occurs during the backup, the exit value is 1.

In certain cases, the exit value can be something other than 0 or 1, due to the command-line option code included from the MySQL libraries. An unknown command-line option, for example, will cause an exit code of 255.

You invoke xtrabackup in one of the following modes:

  • --backup mode to make a backup in a target directory
  • --prepare mode to restore data from a backup (created in --backup mode)
