XTERM(1) Sistema de ventanas X XTERM(1)

NOMBRE

xterm - emulador de terminal para X

SINOPSIS

xterm [-opcion-toolkit ...] [-opcion ...] [shell]

DESCRIPCIÓN

El programa xterm es un emulador de terminal para el Sistema de Ventanas X. Proporciona DEC VT102/VT220 y características seleccionadas de terminales de nivel superior como VT320/VT420/VT520 (VTxxx). También proporciona emulación Tektronix 4014 para programas que no pueden usar el sistema de ventanas directamente. Si el sistema operativo subyacente soporta capacidades de redimensionamiento de terminal (por ejemplo, la señal SIGWINCH en sistemas derivados de 4.3BSD), xterm utilizará las instalaciones para notificar a los programas que se ejecutan en la ventana cada vez que se redimensione.

Los terminales VTxxx y Tektronix 4014 tienen cada uno su propia ventana para que puedas editar texto en una y ver gráficos en la otra al mismo tiempo. Para mantener la relación de aspecto correcta (alto/ancho), los gráficos Tektronix se restringirán a la caja más grande con la relación de aspecto de un 4014 que quepa en la ventana. Esta caja se encuentra en el área superior izquierda de la ventana.

Aunque ambas ventanas pueden mostrarse al mismo tiempo, una de ellas se considera la ventana “activa” para recibir entrada del teclado y salida del terminal. Esta es la ventana que contiene el cursor de texto. La ventana activa se puede elegir a través de secuencias de escape, el menú Opciones VT en la ventana VTxxx y el menú Opciones Tek en la ventana 4014.

EMULACIONES

Xterm proporciona emulaciones utilizables de terminales DEC relacionados:

  • La emulación VT52 es completa.
  • La emulación VT102 es bastante completa, pero no soporta la repetición automática (porque eso afectaría al teclado utilizado por otros clientes X).
Los caracteres de doble tamaño se muestran correctamente si tu servidor de fuentes soporta fuentes de mapa de bits escalables.
  • La emulación VT220 no soporta fuentes suaves, por lo demás es completa.
  • La emulación VT420 (la predeterminada) soporta controles para manipular rectángulos de caracteres, así como márgenes izquierdo/derecho.
Xterm no soporta algunas otras características que no son adecuadas para la emulación, por ejemplo, doble sesión.

Las entradas de la base de datos de terminales (terminfo(5) o termcap(5)) que funcionan con xterm incluyen

una entrada opcional específica de la plataforma (“xterm”),
“xterm”,
“vt102”,
“vt100”,
“ansi” y
“dumb”

Xterm busca automáticamente en la base de datos de terminales en este orden estas entradas y luego establece la variable “TERM” (y la variable de entorno “TERMCAP” en algunos sistemas más antiguos). Las alternativas después de “xterm” son muy antiguas, de finales de la década de 1980.

Las emulaciones VT100 y VT102 se equiparan comúnmente, aunque en realidad difieren. El VT102 proporcionaba controles para insertar y eliminar líneas.

De manera similar, “ansi” y “vt100” se equipararan a menudo. No son realmente lo mismo. Por ejemplo, utilizan controles diferentes para el desplazamiento (pero xterm soporta ambos). Estas características difieren en una descripción de terminal “ansi” de xterm:

acsc

La pseudográfica (líneas de dibujo) utiliza un mapeo diferente.
xenl

Xterm ajusta el texto en el margen derecho utilizando el comportamiento del “fallo de nueva línea” de VT100.

Debido al comportamiento de ajuste, ocasionalmente tendrías que repintar la pantalla al usar un editor de texto con la descripción “ansi”.

También puedes usar descripciones que correspondan a las diversas emulaciones soportadas como “vt220” o “vt420”, pero debes establecer el nivel de emulación de terminal con el recurso decTerminalID.

En la mayoría de los sistemas, xterm utilizará la base de datos terminfo. Algunos sistemas más antiguos usan termcap. (La variable de entorno “TERMCAP” no se establece si xterm está enlazado con una biblioteca terminfo, ya que la información requerida no es proporcionada por la emulación termcap de las bibliotecas terminfo).

Muchas de las características especiales de xterm pueden modificarse bajo control del programa a través de un conjunto de secuencias de escape diferentes de las secuencias de escape VTxxx estándar (ver Secuencias de Control de Xterm).

La emulación Tektronix 4014 también es bastante buena. Soporta direcciones gráficas de 12 bits, escaladas al tamaño de la ventana. Se soportan cuatro tamaños de fuente diferentes y cinco tipos de línea diferentes. No hay soporte para modo de escritura directa (write-through) o modo desenfocado. Los comandos de texto y gráficos Tektronix son grabados internamente por xterm y pueden ser escritos a un archivo enviando la secuencia de escape COPY (o a través del menú Opciones Tek; ver abajo). El nombre del archivo será


“COPYaaaa-MM-dd.hh:mm:ss”

donde aaaa, MM, dd, hh, mm y ss son el año, mes, día, hora, minuto y segundo en que se realizó la COPIA (el archivo se crea en el directorio en el que se inició xterm, o en el directorio personal para un xterm de inicio de sesión).

No todas las características descritas en este manual están necesariamente disponibles en esta versión de xterm. Algunas (por ejemplo, las extensiones no VT220) solo están disponibles si fueron compiladas, aunque las más utilizadas están en la configuración predeterminada.

OTRAS CARACTERÍSTICAS

Xterm resalta automáticamente el cursor de texto cuando el puntero entra en la ventana (seleccionada) y lo deselecciona cuando el puntero sale de la ventana (no seleccionada). Si la ventana es la ventana de enfoque, entonces el cursor de texto se resalta sin importar dónde esté el puntero.

En modo VTxxx, existen secuencias de escape para activar y desactivar un búfer de pantalla alternativo, que tiene el mismo tamaño que el área de visualización de la ventana. Cuando se activa, la pantalla actual se guarda y se reemplaza con la pantalla alternativa. El guardado de líneas desplazadas desde la parte superior de la ventana se deshabilita hasta que se restaura la pantalla normal. La descripción de terminal habitual para xterm permite al editor visual vi(1) cambiar a la pantalla alternativa para editar y restaurar la pantalla al salir. Una entrada del menú emergente facilita el cambio entre las pantallas normal y alternativa para copiar y pegar.

Tanto en modo VTxxx como en modo Tektronix, existen secuencias de escape para cambiar el nombre de las ventanas. Además, en modo VTxxx, xterm implementa las secuencias de control de manipulación de ventanas de dtterm, como redimensionar la ventana, establecer su ubicación en la pantalla.

Xterm permite a las aplicaciones basadas en caracteres recibir eventos del ratón (actualmente eventos de presionar y soltar botones, y eventos de movimiento de botones) como secuencias de control del teclado. Ver Secuencias de Control de Xterm para más detalles.

OPCIONES

Debido a que xterm utiliza la biblioteca X Toolkit, acepta las opciones de línea de comandos estándar de X Toolkit. Xterm también acepta muchas opciones específicas de la aplicación.

Por convención, si una opción comienza con un “+” en lugar de un “-”, la opción se restaura a su valor predeterminado.

La mayoría de las opciones de xterm son realmente analizadas por el X Toolkit, que establece valores de recursos, y anula configuraciones de recursos correspondientes en tus archivos de recursos X. Xterm proporciona al X Toolkit una tabla de opciones. Algunas de estas están marcadas, indicando al X Toolkit que las ignore (-help, -version, -class, -e y -into). Después de que el X Toolkit ha analizado los parámetros de la línea de comandos, elimina los que maneja, dejando los parámetros especialmente marcados para que xterm los maneje.

Estas opciones no establecen un valor de recurso y se manejan especialmente:

-version
Esto hace que xterm imprima un número de versión en la salida estándar y luego salga.
.
-ayuda
Esto hace que xterm imprima un mensaje detallado que describe sus opciones, una por línea. El mensaje se escribe en la salida estándar. Después de imprimir el mensaje, xterm sale. Xterm genera este mensaje, ordenándolo y anotando si un “-opción” o un “+opción” activa o desactiva la característica, ya que algunas características históricamente han sido una u otra. Xterm genera un mensaje de ayuda conciso (múltiples opciones por línea) cuando se utiliza una opción desconocida, por ejemplo, 

xterm -z

Si la lógica para una opción particular, como el registro, no está compilada en xterm, el texto de ayuda para esa opción tampoco se muestra con la opción -ayuda.

Las opciones -version y -ayuda se interpretan incluso si xterm no puede abrir la pantalla, y son útiles para scripts de prueba y configuración. Junto con -class, se comprueban antes que otras opciones. Para hacer esto, xterm tiene su propio analizador de argumentos (mucho más simple), junto con una tabla de la lista incorporada de opciones de X Toolkit.

Confiar en X Toolkit para analizar las opciones y sus valores asociados tiene las ventajas de la simplicidad y una buena integración con el mecanismo de recursos X. Hay algunas desventajas:

  • Xterm no puede saber fácilmente si el valor de un recurso se estableció mediante uno de los archivos externos de recursos o de configuración de la aplicación, si se estableció utilizando xrdb(1), o si se estableció a través de la opción -xrm o mediante alguna opción de línea de comandos directamente relevante. Xterm solo ve el resultado final: un valor proporcionado al crear sus widgets.
  • Xterm no conoce el orden en que se evalúan las opciones particulares y los elementos de los archivos de recursos. Más bien, ve todos los valores de un widget determinado al mismo tiempo. En el diseño de estas opciones, algunas se consideran más importantes y pueden anular otras opciones.
X Toolkit utiliza patrones (constantes y comodines) para hacer coincidir los recursos. Una vez que se utiliza un patrón particular, no lo modificará. Para anular una configuración determinada, se debe usar un patrón más específico, por ejemplo, reemplazando "*" con ".". Algunos archivos de recursos mal diseñados son demasiado específicos para permitir que las opciones de línea de comandos afecten los valores de los widgets relevantes.
•
En algunos casos, X Toolkit combina sus opciones estándar de maneras que no funcionan bien con xterm. Esto sucede con las opciones de color (-fg, -bg) y de inversión (-rv). Xterm hace un caso especial de estas y ajusta su sentido de "inversión" para reducir la sorpresa del usuario.

Se puede proporcionar un parámetro (después de todas las opciones). Esto anula la elección incorporada del shell del programa por parte de xterm:

  • Si el parámetro no es una ruta relativa, es decir, comienza con "./" o "../", xterm busca el archivo en el PATH del usuario. En cualquier caso, esta comprobación falla si xterm no puede construir una ruta absoluta.
  • Si esa comprobación falla (o si no se proporciona dicho parámetro), xterm luego verifica la variable "SHELL". Si esta especifica un archivo ejecutable, xterm intentará iniciarlo. Sin embargo, xterm verifica además si es un shell válido, y establecerá "SHELL" en vacío si no lo es.
  • Si "SHELL" no está configurado en un archivo ejecutable, xterm intenta utilizar el programa shell especificado en la entrada del archivo de contraseñas del usuario. Como antes, xterm verifica si es un shell válido.
  • Finalmente, si la entrada del archivo de contraseñas no especifica un shell válido, xterm utiliza /bin/sh.

La opción -e no se puede usar con este parámetro ya que utiliza todos los parámetros posteriores a la opción.

Xterm valida los programas shell encontrando su ruta en el archivo de texto /etc/shells. Trata la variable de entorno "SHELL" especialmente porque (como "TERM"), xterm lee y actualiza la variable, y porque el programa iniciado por xterm no es necesariamente un shell.

-l
Activa el registro (logging), a menos que esté deshabilitado por el recurso logInhibit.
Algunas versiones de xterm pueden tener el registro activado. Sin embargo, normalmente el registro no está soportado, debido a preocupaciones de seguridad a principios de los 90. Ese fue un problema en X11R4 xterm (1989) que se solucionó con un parche para X11R5 a finales de 1993. X11R6 incluyó estas correcciones. La versión anterior (al ejecutarse con privilegios de root) creaba el archivo de registro con privilegios de root. La razón por la que xterm se ejecutaba con privilegios de root era para abrir pseudo-terminales. Esos privilegios ahora solo son necesarios en sistemas muy antiguos: las pseudo-terminales Unix98 hicieron innecesario el esquema BSD.
A menos que se anule con la opción -lf o el recurso logFile:
  • Si el nombre del archivo es “-”, entonces el registro se envía a la salida estándar.
  • De lo contrario, se genera un nombre de archivo y el archivo de registro se escribe en el directorio desde el cual se invoca xterm.
  • El nombre de archivo generado tiene el formato 


    XtermLog.XXXXXX

o 


Xterm.log.hostname.yyyy.mm.dd.hh.mm.ss.XXXXXX

dependiendo de cómo se compiló xterm.

Desactiva el registro (logging).

CONVERSORES DE RECURSOS

Xterm entiende todos los nombres y clases de recursos principales de X Toolkit. También utiliza los tipos de recursos de X Toolkit (como booleanos, colores, fuentes, enteros y cadenas) junto con sus respectivos conversores. Esos tipos de recursos no siempre son suficientes:

Booleanos extendidos

Los recursos booleanos de X Toolkit son útiles, pero tener más de dos valores ayuda con la configurabilidad. Xterm extiende un valor de recurso booleano (normalmente) comprobando valores adicionales en varios casos:

activeIcon, cdXtraScroll, cursorBlink, eightBitMeta, renderFont, shiftEscape, tiXtraScroll, utf8, utf8Fonts, y utf8Title

Listas separadas por comas

Xterm utiliza listas separadas por comas para ciertos recursos que denotan características para habilitar o deshabilitar:

colorEvents, disallowedColorOps, disallowedFontOps, disallowedMouseOps, disallowedPasteControls, disallowedTcapOps, y disallowedWindowOps

Los tipos de recursos de X Toolkit no incluyen listas. Xterm utiliza una cadena para el recurso y la analiza.

  • Los elementos de estas listas son las características a habilitar o deshabilitar.
  • Los elementos de la lista son nombres (o enteros decimales para disallowedWindowOps).
  • Los elementos de la lista se comparan ignorando mayúsculas y minúsculas. Xterm también permite comodines en los nombres, es decir, “*” y “?” como en los scripts de shell.
  • Cada elemento puede ir precedido de “~” (tilde) para indicar que la característica debe deshabilitarse en lugar de habilitarse.

Xterm también utiliza listas separadas por comas para algunos otros recursos para configurar tablas. Estas coinciden con nombres ignorando mayúsculas y minúsculas, y se pueden abreviar pero no admiten comodines:

eightBitSelectTypes, omitTranslation, y utf8SelectTypes

Finalmente, estos recursos son listas de datos separadas por comas:

charClass, faceNameDoublesize, faceName, y font

Recursos diferidos

Xterm puede diferir el procesamiento de un recurso hasta que sea necesario. Por ejemplo, font2 a font7 se cargan según sea necesario, para iniciar más rápido. Nuevamente, el tipo de recurso real es una cadena, que se analiza y se utiliza cuando es necesario.

Xterm traduce ciertos símbolos de teclas según sus suposiciones sobre su teclado.   • Las extensiones a los controles de color ANSI (como 16, 88 o 256 colores) se tratan de manera similar al control ANSI.

shiftEscape (clase ShiftEscape)
Xterm utiliza el recurso translations para determinar cómo invocar acciones para seleccionar y copiar texto usando el puntero (por ejemplo, un ratón). También proporciona un protocolo de ratón que pueden usar las aplicaciones que se ejecutan en un xterm para detectar clics de botones del ratón.
El protocolo de ratón hace que xterm envíe secuencias de escape especiales que permiten a una aplicación determinar si se utilizaron modificadores (es decir, uno o más de shift, control, alt y meta).
Xterm proporciona este protocolo de ratón interpretando los eventos de botón y movimiento en las funciones que el recurso translations llama para seleccionar y copiar texto:
insert-selection
select-end
select-extend
select-start
start-extend
Mientras el protocolo de ratón está activo, xterm reserva la mayoría de los eventos de botones del ratón para enviar secuencias de escape especiales a la aplicación. Xterm normalmente le permite usar la tecla shift para anular temporalmente este protocolo de ratón, permitiendo usar las acciones de selección y copia.
El ajuste del recurso shiftEscape le permite indicar a xterm si debe usar la tecla shift de esta manera (es decir, anulando el protocolo de ratón). Xterm acepta una palabra clave (ignorando mayúsculas/minúsculas) o el número mostrado entre paréntesis:
falso (0)
El protocolo de ratón no envía escapes especiales cuando se usa la tecla shift.
verdadero (1)
El protocolo de ratón puede enviar escapes especiales cuando se usa la tecla shift.
Al inicio, xterm analiza las translations para ver qué botones se utilizan en los enlaces relacionados con botones (de ratón) para seleccionar y copiar texto. Si la tecla shift no se menciona explícitamente en el enlace de un botón, xterm permite ese botón con la tecla shift para anular el protocolo de ratón.
siempre (2)
El protocolo de ratón puede enviar siempre escapes especiales cuando se usa la tecla shift.
nunca (3)
El protocolo de ratón nunca enviará escapes especiales cuando se use la tecla shift.
Xterm interpreta una secuencia de control que puede cambiar este ajuste entre "verdadero" y "falso". El valor predeterminado es "falso".

tekGeometry (clase Geometry)

tekSmall (clase TekSmall)
Especifica si la ventana del modo Tektronix debe iniciarse en su tamaño más pequeño si no se proporciona una geometría explícita. Esto es útil cuando se ejecuta xterm en pantallas pequeñas. El valor predeterminado es "falso".
tekStartup (clase TekStartup)
Especifica si xterm debe iniciarse en modo Tektronix o no. El valor predeterminado es "falso".
tiXtraScroll (clase TiXtraScroll)
Especifica si xterm debe desplazarse a una nueva página al procesar las cadenas termcap ti o te, es decir, los modos privados 47, 1047 o 1049. Esto solo está en vigor si titeInhibit es "verdadero", ya que la intención de esta opción es proporcionar una imagen de la pantalla de la aplicación a pantalla completa en el scrollback sin borrar el texto que se mostraría antes de que la aplicación se inicializara.

falso (0)
nada se añade al scrollback.
verdadero (1)
la pantalla actual se añade al scrollback.
recortar (2)
la pantalla actual se añade al scrollback, pero las líneas en blanco repetidas se recortan (se reducen a una sola línea en blanco).
El valor predeterminado para este recurso es "falso".
titeInhibit (clase TiteInhibit)
Originalmente especificaba si xterm debía eliminar o no las entradas termcap ti y te (utilizadas para cambiar entre pantallas alternativas al iniciar muchos programas orientados a pantalla) de la cadena TERMCAP.
TERMCAP se usa raramente ahora, pero xterm soporta la función en sistemas modernos:
  • Si está activado, xterm también ignora la secuencia de escape para cambiar a la pantalla alternativa.
  • Xterm soporta terminfo de una manera diferente, admitiendo secuencias de control compuestas (también conocidas como modos privados) 1047, 1048 y 1049 que tienen el mismo efecto que la secuencia de control original 47.
El valor predeterminado para este recurso es "falso".
titleModes (clase TitleModes)
Indica a xterm si debe aceptar o devolver etiquetas de ventana e icono en ISO-8859-1 (el valor predeterminado) o UTF-8. Cualquiera de los dos puede ser codificado en hexadecimal:
  • Los títulos UTF-8 requieren un tratamiento especial, ya que pueden contener bytes que pueden confundirse con caracteres de control. La codificación hexadecimal se admite para eliminar esa posibilidad.
  • Como alternativa, podría usar el recurso allowC1Printable, que suprime el análisis por parte de xterm de los caracteres de control relevantes (y como resultado, trata esos bytes como datos).
El valor predeterminado para este recurso es "0".
Cada bit (el bit "0" es 1, el bit "1" es 2, etc.) corresponde a uno de los parámetros establecidos por la secuencia de control de modos de título:
0
Establecer etiquetas de ventana/icono usando hexadecimal
1
Consultar etiquetas de ventana/icono usando hexadecimal
2
Establece las etiquetas de ventana/icono usando UTF-8 (produce el mismo efecto que el recurso utf8Title).
3
Consulta las etiquetas de ventana/icono usando UTF-8
translations (clase Translations)
Especifica las combinaciones de teclas y botones para menús, selecciones, cadenas programadas", etc. El recurso translations, que proporciona gran parte de la configurabilidad de xterm, es una característica de la biblioteca X Toolkit Intrinsics (Xt). Ver la sección Acciones.
trimSelection (clase TrimSelection)
Si estableces highlightSelection, puedes ver el texto que está seleccionado, incluyendo los espacios finales. Borrar la pantalla (o una línea) la restablece a un estado que no contiene espacios. Algunas líneas pueden contener espacios finales cuando una aplicación las escribe en la pantalla. Sin embargo, puede que no desees pegar líneas con espacios finales. Si este recurso es verdadero, xterm recortará los espacios finales del texto que se selecciona. No afecta a los espacios que resultan de un salto de línea, ni recortará la nueva línea final de tu selección. El valor predeterminado es "false".
underLine (clase UnderLine)
Esto especifica si el texto con el atributo de subrayado debe ser subrayado o no. Puede ser deseable deshabilitar el subrayado cuando se está utilizando color para el atributo de subrayado. El valor predeterminado es "true".
useBorderClipping (clase UseBorderClipping)
Indica a xterm si debe aplicar recorte cuando useClipping es falso. A diferencia de useClipping, esto simplemente limita el texto para mantenerlo dentro de los bordes de la ventana, por ejemplo, como un refinamiento de la solución alternativa scaleHeight. El valor predeterminado es "false".
useClipping (clase UseClipping)
Indica a xterm si debe usar recorte para evitar producir puntos fuera del área de dibujo de texto. Originalmente se usaba para solucionar efectos de sobreescritura, esto también es necesario para trabajar con algunas fuentes de tamaño incorrecto. El valor predeterminado es "true".
utf8 (clase Utf8)
Esto especifica si xterm se ejecutará en modo UTF-8. Si estableces este recurso, xterm también establece el recurso wideChars como efecto secundario. El recurso se puede establecer a través de la opción de menú "Codificación UTF-8". El valor predeterminado es "default".
Xterm acepta una palabra clave (ignorando mayúsculas/minúsculas) o el número mostrado entre paréntesis:
false (0)
El modo UTF-8 está inicialmente desactivado. La opción de línea de comandos +u8 establece el recurso a este valor. Se permiten secuencias de escape para activar/desactivar el modo UTF-8.
true (1)
El modo UTF-8 está inicialmente activado. Se permiten secuencias de escape para activar/desactivar el modo UTF-8.
always (2)
La opción de línea de comandos -u8 establece el recurso a este valor. Se ignoran las secuencias de escape para activar/desactivar el modo UTF-8.
default (3)
Este es el valor predeterminado del recurso. Se cambia durante la inicialización dependiendo de si el recurso locale se estableció o no, a false (0) o always (2). Consulte el recurso locale para obtener información adicional sobre locales que no son UTF-8.
Si deseas establecer el valor de utf8, debería estar en este rango. Otros valores distintos de cero se tratan igual que "1", es decir, el modo UTF-8 está inicialmente activado y se permiten secuencias de escape para activar/desactivar el modo UTF-8.
utf8Fonts (clase Utf8Fonts)
Ver la discusión sobre el recurso locale. Esto especifica si xterm usará fuentes UTF-8 especificadas a través de patrones de recursos como "*vt100.utf8Fonts.font" o fuentes normales (ISO-8859-1) a través de patrones como "*vt100.font". El recurso se puede establecer a través de la opción de menú "UTF-8 Fonts". El valor predeterminado es "default".
Xterm acepta una palabra clave (ignorando mayúsculas/minúsculas) o el número mostrado entre paréntesis:
false (0)
Usa las fuentes ISO-8859-1. La opción de menú está habilitada, permitiendo que la elección de fuentes se cambie en tiempo de ejecución.
true (1)
Usa las fuentes UTF-8. La opción de menú está habilitada, permitiendo que la elección de fuentes se cambie en tiempo de ejecución.
always (2)
Siempre usa las fuentes UTF-8. Esto también deshabilita la opción de menú.
default (3)
Al inicio, el recurso se establece en verdadero o falso, de acuerdo con el valor efectivo del recurso utf8.
utf8Latin1 (clase Utf8Latin1)
Si es verdadero, permite combinar una fuente normal ISO-8859-1 con una fuente ISO-10646-1 si esta última se proporciona a través de la opción -fw o su valor de recurso correspondiente. El valor predeterminado es "false".
utf8SelectTypes (clase Utf8SelectTypes)
Anula la lista de destinos de selección predeterminada de xterm (ver SELECCIONAR/PEGAR) para selecciones en modo de caracteres anchos (UTF-8). El valor predeterminado es una cadena vacía, es decir, "", que no anula nada.
utf8Title (clase Utf8Title)
Las aplicaciones pueden establecer el título de xterm escribiendo una secuencia de control. Normalmente, esta secuencia de control sigue la convención VT220, que codifica la cadena en ISO-8859-1 y permite un terminador de cadena de 8 bits. Si xterm se inicia en una configuración regional UTF-8, traduce la cadena ISO-8859-1 a UTF-8 para trabajar con las bibliotecas X que asumen que la cadena es UTF-8.
Sin embargo, algunos usuarios pueden desear escribir una cadena de título codificada en UTF-8. El gestor de ventanas es responsable de dibujar los títulos de las ventanas. Algunos gestores de ventanas (no todos) admiten la codificación UTF-8 de los títulos de las ventanas. Establezca este recurso a "true" para establecer también cadenas de título codificadas en UTF-8 utilizando las propiedades EWMH.
Esta característica está disponible como una opción de menú, ya que está relacionada con las aplicaciones particulares que estás ejecutando dentro de xterm. También puedes utilizar una secuencia de control (ver la discusión sobre "Modos de título" en Secuencias de Control de Xterm) para establecer un indicador equivalente (que también se puede establecer usando el recurso titleModes).
Xterm acepta una palabra clave (ignorando mayúsculas/minúsculas) o el número mostrado entre paréntesis:
false (0)
Establecer solo cadenas de título ISO-8859-1, por ejemplo, usando la propiedad ICCCM WM_NAME STRING. La opción de menú está habilitada, permitiendo que la elección de cadenas de título se cambie en tiempo de ejecución.
true (1)
Establecer tanto EWMH (cadenas UTF-8) como ICCCM WM_NAME, etc. La opción de menú está habilitada, permitiendo que la elección se cambie en tiempo de ejecución.
always (2)
Siempre establecer tanto EWMH (cadenas UTF-8) como ICCCM WM_NAME, etc. Esto también deshabilita la opción de menú.
default (3)
Al inicio, el recurso se establece en verdadero o falso, de acuerdo con el valor efectivo del recurso utf8.
El valor predeterminado es "default".
utf8Weblike (clase Utf8Weblike)
Proporciona un esquema alternativo de manejo de errores para UTF-8 mal formado como se recomienda en un documento de W3C. El estándar Unicode no requiere esto para la conformidad. Se puede encontrar información adicional aquí:
https://invisible-island.net/xterm/bad-utf8/
El valor predeterminado es "false".
veryBoldColors (clase VeryBoldColors)
Especifica si se deben combinar atributos de video con colores especificados por colorBD, colorBL, colorIT, colorRV y colorUL. El valor del recurso es la suma de los valores para cada atributo:
1 para invertir,
2 para subrayado,
4 para negrita,
8 para parpadeo, y
512 para cursiva
El valor predeterminado es "0".
visualBell (clase VisualBell)
Especifica si se debe usar una campana visual (es decir, parpadeo) en lugar de una campana audible cuando se recibe Control-G. El valor predeterminado es "false", lo que indica a xterm que use una campana audible.
visualBellDelay (clase VisualBellDelay)
Número de milisegundos de retraso al mostrar una campana visual. El valor predeterminado es 100. Si se establece en cero, no se muestra ninguna campana visual. Esto es útil para pantallas muy lentas, por ejemplo, una pantalla LCD en un portátil.

vt100Graphics (clase VT100Graphics)
Esto especifica si xterm interpretará las secuencias de escape de caracteres gráficos VT100 mientras está en modo UTF-8. Esta característica también se aplica a las páginas de códigos (por ejemplo, para VT320 y VT520) y a los conjuntos de caracteres de reemplazo nacionales (VT220 y superior), pero no a US-ASCII (el conjunto de caracteres seleccionado inicialmente), para evitar conflictos con UTF-8. El valor predeterminado es "true", para proporcionar soporte para varias aplicaciones heredadas.
wideBoldFont (clase WideBoldFont)
Esta opción especifica la fuente que se utilizará para mostrar texto ancho en negrita. Por defecto, intentará usar una fuente el doble de ancha que la fuente que se utilizará para dibujar texto en negrita. Si no se encuentra una fuente de doble ancho, improvisará estirando la fuente en negrita.
wideChars (clase WideChars)
Especifica si xterm debe responder a secuencias de control que procesan caracteres de 16 bits. El valor predeterminado es "false".
wideFont (clase WideFont)
Esta opción especifica la fuente que se utilizará para mostrar texto ancho. Por defecto, intentará usar una fuente el doble de ancha que la fuente que se utilizará para dibujar texto normal. Si no se encuentra una fuente de doble ancho, improvisará estirando la fuente normal.

Establece el límite de memoria de glifos de la biblioteca Xft (típicamente 4MB). Cuando alcanza este límite, descarta glifos "elegidos al azar" para hacer espacio para otros nuevos. El valor predeterminado es "0" para usar el valor predeterminado de Xft.

Establece el límite de fuentes cargadas de la biblioteca Xft (típicamente 16), por ejemplo, patrones coincidentes para búsquedas de respaldo, pero que en realidad no se usan. El valor predeterminado es "0" para usar el valor predeterminado de Xft.

Habilita el seguimiento de la memoria de glifos (introducido en Xft 2.3.5), lo que permite a Xft descartar eficientemente datos obsoletos cuando hay poca memoria. El valor predeterminado es "false".
ximFont (clase XimFont)
Esta opción especifica la fuente que se utilizará para mostrar la cadena de preedición en el método de entrada "OverTheSpot".
En el tipo de preedición "OverTheSpot", la cadena de preedición (preconversión) se muestra en la posición del cursor. Es responsabilidad del servidor XIM mostrar la cadena de preedición. El cliente XIM debe informar al servidor XIM de la posición del cursor. Para obtener mejores resultados, la cadena de preedición debe mostrarse con una fuente adecuada. Por lo tanto, xterm informa al servidor XIM de la fuente adecuada. La fuente se proporcionará a través de un "fontset", cuyo valor predeterminado es "*". Esto coincide con todas las fuentes, la biblioteca X elige automáticamente fuentes con conjuntos de caracteres adecuados. El recurso ximFont se proporciona para anular esta configuración de fuente predeterminada.

USO DEL PUNTERO

Una vez creada la ventana VTxxx, xterm te permite seleccionar texto y copiarlo dentro de la misma ventana u otras utilizando el puntero o el teclado.

Un "puntero" podría ser un ratón, panel táctil o dispositivo similar. Las aplicaciones X generalmente no se preocupan, ya que solo ven eventos de botón que tienen

  • posición y
  • estado de botón presionado/liberado

Xterm puede ver estos eventos siempre que tenga el foco.

El teclado también proporciona eventos, pero es menos flexible que el puntero para seleccionar/copiar texto.

Los eventos se aplican a las acciones utilizando el recurso translations. Consulte Actions para ver una lista completa, y Default Key Bindings para el conjunto integrado de recursos translations.

Funciones de Selección

Por defecto, las funciones de selección se invocan cuando se utilizan los botones del puntero sin modificadores, y cuando se utilizan con la tecla "shift". La tecla "shift" es especial, ya que xterm la usa para asegurar que las funciones de selección sigan disponibles cuando está programado para enviar secuencias de escape en uno de los modos del ratón (consulte Xterm Control Sequences, así como el recurso disallowedMouseOps).

Al inicio, xterm inspecciona el recurso translations para ver qué botones del puntero se pueden utilizar de esta manera, y recuerda estos botones al decidir si enviar secuencias de escape o realizar una selección cuando se utilizan esos botones con el modificador "shift". Otros botones del puntero, por ejemplo, los que se envían para eventos de ratón con rueda, no se ven afectados.

La asignación de las funciones descritas a continuación a teclas y botones se puede cambiar a través de la base de datos de recursos; consulte Actions a continuación.

Botón uno del puntero (normalmente el izquierdo)
se utiliza para guardar texto en el buffer de corte: 


~Meta <Btn1Down>:select-start()

Mueve el cursor al principio del texto, y luego mantén presionado el botón mientras mueves el cursor al final de la región y sueltas el botón. El texto seleccionado se resalta y se guarda en el buffer de corte global y se convierte en la selección cuando se suelta el botón: 


<BtnUp>:select-end(SELECT, CUT_BUFFER0) \n

Normalmente (pero vea la discusión sobre on2Clicks, etc.):
  • Doble clic selecciona por palabras.
  • Triple clic selecciona por líneas.
  • Cuádruple clic vuelve a caracteres, etc.
Los clics múltiples se determinan por el tiempo transcurrido entre soltar y presionar el botón, por lo que puedes cambiar la unidad de selección en medio de una selección. Las palabras lógicas y las líneas seleccionadas con doble o triple clic pueden abarcar más de una línea de pantalla si las líneas fueron envueltas por el propio xterm en lugar de por la aplicación que se ejecuta en la ventana. Si las combinaciones de teclas/botones especifican que se debe hacer una selección X, xterm dejará el texto seleccionado resaltado mientras sea el propietario de la selección.
Botón dos del puntero (normalmente el del medio)
"escribe" (pega) el texto de la selección dada, si la hay, de lo contrario del buffer de corte, insertándolo como entrada de teclado: 


~Ctrl ~Meta <Btn2Up>:insert-selection(SELECT, CUT_BUFFER0)

Botón tres del puntero (normalmente el derecho)
extiende la selección actual. 


~Ctrl ~Meta <Btn3Down>:start-extend()

(Sin pérdida de generalidad, puedes intercambiar "derecha" e "izquierda" en todas partes del resto de este párrafo). Si se presiona mientras está más cerca del borde derecho de la selección que del izquierdo, extiende/contrae el borde derecho de la selección. Si contraes la selección más allá del borde izquierdo de la selección, xterm asume que realmente querías el borde izquierdo, restaura la selección original y luego extiende/contrae el borde izquierdo de la selección. La extensión comienza en el modo de unidad de selección en el que se realizó la última selección o extensión; puedes hacer clic múltiple para ciclar a través de ellos.

Al cortar y pegar fragmentos de texto sin saltos de línea finales, puedes tomar texto de varios lugares en diferentes ventanas y formar un comando para el shell, por ejemplo, o tomar la salida de un programa e insertarla en tu editor favorito. Dado que los buffers de corte se comparten globalmente entre diferentes aplicaciones, puedes considerarlos como un "archivo" cuyo contenido conoces. El emulador de terminal y otros programas de texto deberían tratarlo como si fuera un archivo de texto, es decir, el texto está delimitado por saltos de línea.

Desplazamiento

La región de desplazamiento muestra la posición y la cantidad de texto que se muestra actualmente en la ventana (resaltado) en relación con la cantidad de texto realmente guardado. A medida que se guarda más texto (hasta el máximo), el tamaño del área resaltada disminuye.

Hacer clic en el botón uno con el puntero en la región de desplazamiento mueve la línea adyacente a la parte superior de la ventana de visualización.

Hacer clic en el botón tres mueve la línea superior de la ventana de visualización hacia abajo hasta la posición del puntero.

Hacer clic en el botón dos mueve la visualización a una posición en el texto guardado que corresponde a la posición del puntero en la barra de desplazamiento.

Puntero Tektronix

A diferencia de la ventana VTxxx, la ventana Tektronix no permite la copia de texto. Permite el modo GIN de Tektronix y, en este modo, el cursor cambiará de una flecha a una cruz. Presionar cualquier tecla enviará esa tecla y la coordenada actual del cursor en forma de cruz. Presionar los botones uno, dos o tres devolverá las letras "l", "m" y "r", respectivamente. Si se presiona la tecla "shift" al presionar un botón del puntero, se enviará la letra mayúscula correspondiente. Para distinguir un botón del puntero de una tecla, se establece el bit más alto del carácter (pero este bit normalmente se elimina

d a menos que el modo de terminal sea RAW; consulte tty(4) para más detalles).

SELECCIONAR/PEGAR

Los clientes X proporcionan compatibilidad con selección y pegado respondiendo a solicitudes transmitidas por el servidor X. El servidor X almacena datos en "átomos" que corresponden a los diferentes tipos de selección (PRIMARY, SECONDARY, CLIPBOARD) así como al mecanismo similar de búfer de corte (CUT_BUFFER0 a CUT_BUFFER7). Estos están documentados en el ICCCM.

El ICCCM se ocupa del mecanismo subyacente para seleccionar/pegar. No menciona el *resaltado*. La *selección* no es lo mismo que el *resaltado*. *Xterm* (como muchas aplicaciones) utiliza el resaltado para mostrarle el texto actualmente seleccionado. Una aplicación X puede *poseer* una selección, lo que le permite ser la fuente de datos copiados utilizando un átomo de selección dado. *Xterm* puede seguir poseyendo una selección después de dejar de resaltar (consulte keepSelection).

*Xterm* proporciona datos de selección utilizando las celdas de caracteres que muestra. Rellena esas celdas utilizando secuencias de bytes y secuencias de control:

•
Por defecto, *xterm* utiliza la codificación UTF-8 si su configuración regional utiliza esa codificación. Los recursos utf8 y locale controlan ese comportamiento.
Al decodificar UTF-8, *xterm* puede componer ciertos caracteres base y de combinación. Utilice el recurso precompose para habilitar o deshabilitar esta función.
*Xterm* tiene otros recursos para necesidades de codificación especializadas, incluyendo allowC1Printable, showMissingGlyphs y utf8Weblike.
•
*Xterm* almacena caracteres base y de combinación para cada celda en su ventana. No almacena la secuencia de bytes que compuso esos caracteres. La selección utiliza los caracteres que *xterm* almacena en cada celda.
Si el destino de la selección acepta UTF-8, *xterm* copia todos los caracteres base y de combinación al destino. Si el destino de la selección no acepta UTF-8, por ejemplo, a un búfer de corte, *xterm* copia solo lo que el destino acepta, utilizando el recurso defaultString para rellenar las celdas que no se pueden representar en el destino.
•
Todas las celdas en la ventana de *xterm* no están inicializadas al principio. Borrar la pantalla hace que las celdas no estén inicializadas. Las celdas no inicializadas se muestran como espacios.
Por defecto, la selección de filas en la ventana de *xterm* resaltará todas las celdas que atraviesa el puntero mientras selecciona. Si el recurso highlightSelection está establecido, *xterm* no resaltará las celdas no inicializadas finales en las filas seleccionadas.
El recurso trimSelection le permite descartar los espacios finales de cada fila seleccionada, tanto de celdas no inicializadas como de las escritas por una aplicación.
•
A medida que *xterm* escribe caracteres en su ventana y ajusta el texto en el margen derecho, recuerda que el texto fue ajustado. Utilice el recurso showWrapMarks para mostrar esto en la ventana.

PRIMARIA

Cuando está configurado para usar la selección primaria (la opción predeterminada), *xterm* puede proporcionar los datos de selección de maneras que ayudan a retener la información de codificación de caracteres a medida que se pega.

El token PRIMARY es una característica estándar de X, documentada en el ICCCM (Inter-Client Communication Conventions Manual), que indica

La selección nombrada por el átomo PRIMARY se utiliza para todos los comandos que toman solo un argumento y es el principal medio de comunicación entre clientes que utilizan el mecanismo de selección.

Un usuario "selecciona" texto en *xterm*, lo que resalta el texto seleccionado. Un posterior "pegado" a otro cliente reenvía una solicitud al cliente que posee la selección. Si *xterm* posee la selección primaria, pone los datos a disposición en forma de uno o más "objetivos de selección". Si no posee la selección primaria, por ejemplo, si la ha liberado o si otro cliente ha afirmado la propiedad, recurre a los búferes de corte para pasar los datos. Pero los búferes de corte solo manejan datos ISO-8859-1 (oficialmente, algunos clientes ignoran las reglas).

PORTAPAPELES

Cuando está configurado para usar el portapapeles (utilizando el recurso selectToClipboard), se evita el problema de la persistencia de la propiedad. De lo contrario, no hay diferencia en cuanto a los datos que se pueden pasar a través de la selección.

El recurso selectToClipboard es un compromiso, que permite que CLIPBOARD se trate casi como PRIMARY, a diferencia del ICCCM, que describe CLIPBOARD en términos diferentes a PRIMARY o SECONDARY. Su larga explicación comienza con los puntos esenciales:

La selección nombrada por el átomo CLIPBOARD se utiliza para almacenar datos que se están transfiriendo entre clientes, es decir, datos que generalmente se están cortando y luego pegando o copiando y luego pegando. Siempre que un cliente quiera transferir datos al portapapeles:

  • Debería afirmar la propiedad del CLIPBOARD.
  • Si tiene éxito en adquirir la propiedad, debería estar preparado para responder a una solicitud del contenido del CLIPBOARD de la manera habitual (reteniendo los datos para poder devolverlos). La solicitud puede ser generada por el cliente del portapapeles descrito a continuación.

SELECCIONAR

Sin embargo, muchas aplicaciones utilizan CLIPBOARD imitando otros sistemas de ventanas. El recurso selectToClipboard (y la entrada correspondiente del menú Select to Clipboard) introducen el token SELECT (conocido solo por *xterm*) que elige entre los tokens PRIMARY y CLIPBOARD.

Sin usar esta función, se pueden usar soluciones alternativas como el programa *xclip* para mostrar el contenido del portapapeles de X dentro de una ventana de *xterm*.

SECUNDARIA

Esta se usa con menos frecuencia que PRIMARY o CLIPBOARD. Según el ICCCM, se utiliza

  • Como segundo argumento para comandos que toman dos argumentos (por ejemplo, "intercambiar selecciones primaria y secundaria")
  • Como medio para obtener datos cuando hay una selección primaria y el usuario no quiere alterarla

Objetivos de Selección

Los diferentes tipos de datos que se pasan dependen de lo que solicite el cliente receptor. Estos se denominan *objetivos de selección*.

Al solicitar los datos de selección, *xterm* prueba los siguientes tipos en este orden:

UTF8_STRING
Esta es una extensión de XFree86, que denota que los datos están codificados en UTF-8. Cuando *xterm* se compila con soporte para caracteres anchos, tanto acepta como proporciona este tipo.
TEXT
el texto está en la codificación que corresponde a su configuración regional actual.
COMPOUND_TEXT
este es un formato para datos de múltiples conjuntos de caracteres, como texto multilingüe. Puede almacenar datos UTF-8 como un caso especial.
STRING
Estos son datos Latin 1 (ISO-8859-1).

Los dos del medio (TEXT y COMPOUND_TEXT) se añaden si *xterm* está configurado con el recurso i18nSelections establecido en "true".

UTF8_STRING es preferido (por lo tanto, el primero en la lista) ya que *xterm* almacena texto como datos Unicode cuando se ejecuta en modo de caracteres anchos, y no se necesita traducción. Por otro lado, TEXT y COMPOUND_TEXT pueden requerir traducción. Si la traducción es incompleta, insertarán el "defaultString" de X, cuyo valor no se puede establecer y puede estar simplemente vacío. El recurso defaultString de *xterm* especifica la cadena a utilizar para traducciones incompletas de UTF8_STRING.

Puede alterar los tipos que *xterm* prueba utilizando los recursos eightBitSelectTypes o utf8SelectTypes. Por ejemplo, puede tener alguna configuración regional específica que no utilice la codificación UTF-8. El valor del recurso es una lista separada por comas de los objetivos de selección, que consisten en los nombres mostrados. Puede usar el nombre especial I18N para denotar la inclusión opcional de TEXT y COMPOUND_TEXT. Los nombres se comparan ignorando mayúsculas y minúsculas, y se pueden abreviar. La lista predeterminada se puede expresar de varias maneras, por ejemplo:

UTF8_STRING,I18N,STRING
utf8,i18n,string
u,i,s

Protocolo de Ratón

Las aplicaciones pueden enviar secuencias de escape a *xterm* para que envíe secuencias de escape de vuelta al ordenador cuando presione un botón del puntero, o incluso (dependiendo de la secuencia de escape) enviar secuencias de escape de vuelta al ordenador mientras mueve el puntero.

Estas secuencias de escape y las respuestas, llamadas *protocolo de ratón*, están documentadas en *XTerm Control Sequences*. No aparecen en las *acciones* invocadas por el recurso translations porque el recurso no cambia mientras ejecuta *xterm*, mientras que las aplicaciones pueden cambiar el protocolo del ratón (es decir, habilitar, deshabilitar, usar diferentes modos).

Sin embargo, el protocolo del ratón se interpreta dentro de las *acciones* que normalmente se asocian con los botones del puntero. *Xterm* ignora el protocolo del ratón en la acción insert-selection si la tecla Shift se presiona al mismo tiempo. También modifica algunas otras acciones si se presiona la tecla Shift, por ejemplo, suprimiendo la respuesta con la posición del puntero, aunque no eliminando los cambios en el texto seleccionado.

SEGURIDAD

El modo Teclado Seguro (Secure Keyboard) está diseñado para proteger las contraseñas y otra información confidencial de ser capturada por aplicaciones maliciosas que se ejecutan en un terminal. Cuando está habilitado, xterm evita que otras aplicaciones envíen eventos de teclado a la ventana actual. Sin embargo, es importante notar que este modo no es infalible. Las aplicaciones que pueden interactuar con el sistema de ventanas X a un nivel más profundo aún podrían ser capaces de interceptar eventos de teclado. Además, si el sistema operativo subyacente ha sido comprometido, la protección del modo Teclado Seguro no será efectiva.

Para obtener más información sobre las limitaciones de seguridad de xterm, consulte la documentación de su sistema o el archivo README de xterm.

Soft Reset (resource hardreset)
A soft reset differs from a full reset in a minor detail:

formatCursorKeys, formatFunctionKeys, formatKeypadKeys, formatModifierKeys, formatOtherKeys, and formatSpecialKeys.
as well as
modifyCursorKeys, modifyFunctionKeys, modifyKeyboard, modifyKeypadKeys, modifyModifierKeys, modifyOtherKeys, and modifySpecialKeys.
  • Reset origin mode (DECOM).
  • Reset all margins (i.e., top/bottom and left/right). This can be convenient when some program has left the scroll regions set incorrectly.

A full reset does this in addition to a soft reset:
  • Clear the window.
  • Reset tab stops to every eight columns.
  • Reset the screen to match the reverseVideo resource.
  • Resize the screen to 80 columns if 132-column mode was initially enabled with the c132 resource.

  • Enable linefeed mode (ECMA-48 LNM) and send/receive mode (ECMA-48 SRM).

ASOCIACIONES DE TECLAS

Es posible reasociar teclas (o secuencias de teclas) a cadenas arbitrarias para la entrada, cambiando los recursos de translations para los widgets vt100 o tek4014. Cambiar el recurso translations para eventos distintos de los de teclado y ratón no es lo esperado y causará un comportamiento impredecible.

exec-formatted(format, sourcename [, ...])
Ejecuta un comando externo, utilizando la selección actual para parte de los parámetros del comando. El primer parámetro, format, da el comando básico. Los parámetros subsiguientes especifican la fuente de la selección como en insert-selection.
El parámetro format permite estas sustituciones:
%%
inserta un "%".
%P
la posición en pantalla al inicio de la región resaltada, como un par de enteros separados por punto y coma utilizando los valores que usaría la secuencia de control CUP.
%p
la posición en pantalla después del inicio de la región resaltada, usando la misma convención que “%P”.
%S
la longitud de la cadena que “%s” insertaría.
%s
el contenido de la selección, sin modificar.
%T
la longitud de la cadena que “%t” insertaría.
%t
la selección, recortada de espacios en blanco al principio y al final. Los espacios (y saltos de línea) incrustados se copian tal cual.
%R
la longitud de la cadena que “%r” insertaría.
%r
la selección, recortada de espacios en blanco al final.
%V
los atributos de video al inicio de la región resaltada, como una lista separada por punto y coma de enteros usando los valores que usaría la secuencia de control SGR.
%v
los atributos de video al final de la región resaltada, usando la misma convención que “%V”.
Después de construir la cadena de comandos, xterm crea un subproceso y ejecuta el comando, que se completa independientemente de xterm.
Por ejemplo, esta traducción invocaría un nuevo proceso xterm para ver un archivo cuyo nombre se selecciona mientras se mantiene presionada la tecla shift. El nuevo proceso se inicia cuando se suelta el botón del ratón: 


*VT100*translations: #override Shift \
    <Btn1Up>:exec-formatted("xterm -e view '%t'", SELECT)

Custom Key Bindings

You can modify the translations resource by overriding parts of it, or merging your resources with it.

Here is an example which uses shifted select/paste to copy to the clipboard, and unshifted select/paste for the primary selection. In each case, a (different) cut buffer is also a target or source of the select/paste operation. It is important to remember however, that cut buffers store data in ISO-8859-1 encoding, while selections can store data in a variety of formats and encodings. While xterm owns the selection, it highlights it. When it loses the selection, it removes the corresponding highlight. But you can still paste from the corresponding cut buffer.


*VT100*translations:    #override
   ~Shift~Ctrl<Btn2Up>: insert-selection(PRIMARY, CUT_BUFFER0)
    Shift~Ctrl<Btn2Up>: insert-selection(CLIPBOARD, CUT_BUFFER1)
   ~Shift     <BtnUp> : select-end(PRIMARY, CUT_BUFFER0)
    Shift     <BtnUp> : select-end(CLIPBOARD, CUT_BUFFER1)

In the example, the class name VT100 is used rather than the widget name. These are different; a class name could apply to more than one widget. A leading “*” is used because the widget hierarchy above the vt100 widget depends on whether the toolbar support is compiled into xterm.

Most of the predefined translations are related to the mouse, with a few that use some of the special keys on the keyboard. Applications use special keys (function-keys, cursor-keys, keypad-keys) with modifiers (shift, control, alt). If xterm defines a translation for a given combination of special key and modifier, that makes it unavailable for use by applications within the terminal. For instance, one might extend the use of Page Up and Page Down keys seen here:


    Shift <KeyPress> Prior : scroll-back(1,halfpage)
    Shift <KeyPress> Next  : scroll-forw(1,halfpage)

to the Home and End keys:


    Shift <KeyPress> Home : scroll-to(begin)
    Shift <KeyPress> End  : scroll-to(end)

but then shift-Home and shift-End would then be unavailable to applications.

Not everyone finds the three-button mouse bindings easy to use. In a wheel mouse, the middle button might be the wheel. As an alternative, you could add a binding using shifted keys:


*VT100*translations:      #override
    Shift <Key>Home:    copy-selection(SELECT)
    Shift <Key>Insert:  copy-selection(SELECT)
    Ctrl Shift <Key>C:  copy-selection(SELECT)
    Ctrl Shift <Key>V:  insert-selection(SELECT)

You would still use the left- and right-mouse buttons (typically 1 and 3) for beginning and extending selections.

Besides mouse problems, there are also keyboards with inconvenient layouts. Some lack a numeric keypad, making it hard to use the shifted keypad plus and minus bindings for switching between font sizes. You can work around that by assigning the actions to more readily accessed keys:


*VT100*translations:      #override
    Ctrl <Key> +:       larger-vt-font()
    Ctrl <Key> -:       smaller-vt-font()

The keymap feature allows you to switch between sets of translations. The sample below shows how the keymap() action may be used to add special keys for entering commonly-typed words:


*VT100.Translations: #override <Key>F13: keymap(dbx)
*VT100.dbxKeymap.translations:
        <Key>F14:       keymap(None)
        <Key>F17:       string("next")
                        string(0x0d)
        <Key>F18:       string("step")
                        string(0x0d)
        <Key>F19:       string("continue")
                        string(0x0d)
        <Key>F20:       string("print ")
                        insert-selection(PRIMARY, CUT_BUFFER0)

Default Scrollbar Bindings

Key bindings are normally associated with the vt100 or tek4014 widgets which act as terminal emulators. Xterm's scrollbar (and toolbar if it is configured) are separate widgets. Because all of these use the X Toolkit, they have corresponding translations resources. Those resources are distinct, and match different patterns, e.g., the differences in widget-name and number of levels of widgets which they may contain.

The scrollbar widget is a child of the vt100 widget. It is positioned on top of the vt100 widget. Toggling the scrollbar on and off causes the vt100 widget to resize.

The default bindings for the scrollbar widget use only mouse-button events:


   <Btn5Down>: StartScroll(Forward)
   <Btn1Down>: StartScroll(Forward)
   <Btn2Down>: StartScroll(Continuous) MoveThumb() NotifyThumb()
   <Btn3Down>: StartScroll(Backward)
   <Btn4Down>: StartScroll(Backward)
   <Btn2Motion>: MoveThumb() NotifyThumb()
   <BtnUp>:    NotifyScroll(Proportional) EndScroll()

Events which the scrollbar widget does not recognize at all are lost.

However, at startup, xterm augments these translations with the default translations used for the vt100 widget, together with the resource “actions” which those translations use. Because the scrollbar (or menubar) widgets do not recognize these actions (but because it has a corresponding translation), they are passed on to the vt100 widget.

This augmenting of the scrollbar's translations has a few limitations:

  • Xterm knows what the default translations are, but there is no suitable library interface for determining what customizations a user may have added to the vt100 widget. All that xterm can do is augment the scrollbar widget to give it the same starting point for further customization by the user.
  • Events in the gap between the widgets may be lost.
  • Compose sequences begun in one widget cannot be completed in the other, because the input methods for each widget do not share context information.

Most customizations of the scrollbar translations do not concern key bindings. Rather, users are generally more interested in changing the bindings of the mouse buttons. For example, some people prefer using the left pointer button for dragging the scrollbar thumb. That can be set up by altering the translations resource, e.g.,


*VT100.scrollbar.translations:  #override
   <Btn5Down>:     StartScroll(Forward)
   <Btn1Down>:     StartScroll(Continuous) MoveThumb() NotifyThumb()
   <Btn4Down>:     StartScroll(Backward)
   <Btn1Motion>:   MoveThumb() NotifyThumb()
   <BtnUp>:        NotifyScroll(Proportional) EndScroll()

CONTROL SEQUENCES AND KEYBOARD

Applications can send sequences of characters to the terminal to change its behavior. Often they are referred to as “ANSI escape sequences” or just plain “escape sequences” but both terms are misleading:

  • ANSI x3.64 (obsolete) which was replaced by ISO 6429 (ECMA-48) gave rules for the format of these sequences of characters.
  • While the original VT100 was claimed to be ANSI-compatible (against x3.64), there is no freely available version of the ANSI standard to show where the VT100 differs. Most of the documents which mention the ANSI standard have additions not found in the original (such as those based on ansi.sys). So this discussion focuses on the ISO standards.
  • The standard describes only sequences sent from the host to the terminal. There is no standard for sequences sent by special keys from the terminal to the host. By convention (and referring to existing terminals), the format of those sequences usually conforms to the host-to-terminal standard.
  • Some of xterm's sequences do not fit into the standard scheme. Technically those are “unspecified”. As an example, DEC Screen Alignment Test (DECALN) is this three-character sequence: 


    ESC N  

ESC # 8

  • Algunas secuencias encajan en el formato estándar, pero no están listadas en el estándar. Estas incluyen las secuencias usadas para configurar márgenes de desplazamiento y para realizar desplazamientos hacia adelante/atrás.
  • Algunas de las secuencias (en particular, las funciones de un solo carácter como tabulador y retroceso) no incluyen el carácter de escape.

    • Teniendo todo esto en cuenta, el estándar se refiere a estas secuencias de caracteres como "secuencias de control".

    Secuencias de Control de Xterm lista las secuencias de control que una aplicación puede enviar a xterm para que realice diversas operaciones. La mayoría de estas operaciones están estandarizadas, ya sea por las terminales DEC o Tektronix, o por estándares más utilizados como ISO-6429.

    A continuación se dan algunos ejemplos de uso.

    Títulos de Ventana e Icono

    Algunos scripts usan echo con las opciones -e y -n para indicar a la shell que interprete la cadena "\e" como el carácter de escape y que suprima un salto de línea final en la salida. Estas opciones no son portátiles ni recomendables. En su lugar, utilice printf(1) (POSIX).

    Por ejemplo, para establecer el título de la ventana a "Hola mundo!", podría usar uno de estos comandos en un script:


    printf '\033]2;Hola mundo!\033\\'
printf '\033]2;Hola mundo!\007'
printf '\033]2;%s\033\\' "Hola mundo!"
printf '\033]2;%s\007' "Hola mundo!"

    El comando printf(1) interpreta el valor octal "\033" para escape, y (dado que no se proporcionó en el formato) omite un salto de línea final de la salida.

    Algunos programas (como screen(1)) establecen simultáneamente los títulos de ventana e icono, utilizando una secuencia de control ligeramente diferente:


    printf '\033]0;Hola mundo!\033\\'
printf '\033]0;Hola mundo!\007'
printf '\033]0;%s\033\\' "Hola mundo!"
printf '\033]0;%s\007' "Hola mundo!"

    La diferencia es el parámetro "0" en cada comando. La mayoría de los gestores de ventanas respetarán el título de la ventana o el título del icono. Algunos harán una distinción y le permitirán establecer solo el título del icono. Puede indicar a xterm que solicite esto con un parámetro diferente en la secuencia de control:


    printf '\033]1;Hola mundo!\033\\'
printf '\033]1;Hola mundo!\007'
printf '\033]1;%s\033\\' "Hola mundo!"
printf '\033]1;%s\007' "Hola mundo!"

    Teclas Especiales

    Xterm, al igual que cualquier emulador de terminal compatible con VT100, tiene dos modos para las teclas especiales (teclas de cursor, teclado numérico y ciertas teclas de función):

    • modo normal, que hace que las teclas especiales transmitan secuencias "útiles" como la secuencia de control para cursor-arriba al presionar la flecha hacia arriba, y
    • modo de aplicación, que utiliza una secuencia de control diferente que no puede confundirse con las secuencias "útiles".

    La principal diferencia entre los dos modos es que las secuencias del modo normal comienzan con CSI (escape [) y las secuencias del modo de aplicación comienzan con SS3 (escape O).

    La terminal se inicializa en uno de estos dos modos (generalmente el modo normal), basándose en la descripción de la terminal (termcap o terminfo). La descripción de la terminal también tiene capacidades (cadenas) definidas para el modo de teclado utilizado en aplicaciones curses.

    Existe un problema al usar la descripción de la terminal para aplicaciones que no están destinadas a ser aplicaciones curses de pantalla completa: las definiciones de teclas especiales solo son correctas para este modo de teclado. Por ejemplo, algunos shells (a diferencia de ksh(1), que parece estar codificado, sin siquiera usar termcap) permiten a sus usuarios personalizar los enlaces de teclas, asignando acciones del shell a teclas especiales.

    • bash(1) permite asignar cadenas constantes a funciones. Esto solo tiene éxito si la terminal se inicializa en modo de aplicación por defecto, porque bash carece de flexibilidad en esta área. Utiliza un lenguaje de scripting readline (menos expresivo que el de bash) para configurar los enlaces de teclas, lo que depende de que el usuario enumere estáticamente los enlaces posibles para los valores dados de $TERM.
    • zsh(1) proporciona una característica análoga, pero acepta expresiones en tiempo de ejecución, además de proporcionar una matriz $terminfo para scripts. En particular, se puede usar la base de datos de terminales, transformando al definir un enlace de tecla. Al transformar la salida de manera que CSI y SS3 sean equivalentes, zsh puede usar la base de datos de terminales para obtener definiciones útiles para su uso en la línea de comandos, independientemente de si la terminal usa el modo normal o de aplicación inicialmente. Aquí hay un ejemplo: 


      [[ "$terminfo[kcuu1]" == "^[O"* ]] && \
bindkey -M viins "${terminfo[kcuu1]/O/[}" \
vi-up-line-or-history

    Cambio de Colores

    Algunos programas de shell brindan la capacidad para que los usuarios agreguen color y otros atributos de video a las cadenas de prompt del shell. Los usuarios pueden hacer esto estableciendo $PS1 (la cadena de prompt principal). De nuevo, bash y zsh han proporcionado características que no se encuentran en ksh. Sin embargo, existe un problema: el ancho del prompt en la pantalla no será necesariamente el mismo que el número de caracteres. Dado que no hay orientación en el estándar POSIX, cada shell aborda el problema de manera diferente:

    • bash trata los caracteres dentro de "\[" y "\]" como no imprimibles (sin ocupar ancho en la pantalla).
    • zsh trata los caracteres dentro de "%{" y "%}" como no imprimibles.

    Además de la diferencia de sintaxis, los shells proporcionan diferentes métodos para obtener secuencias de escape útiles:

    •
    Como se señaló en Teclas Especiales, zsh inicializa la matriz $terminfo con las capacidades de la terminal.
    También proporciona una función echoti que funciona como tput(1) para convertir una capacidad de terminal con sus parámetros en una cadena que se puede escribir en la terminal.
    •
    Los shells que carecen de una característica comparable (como bash) siempre pueden usar el programa tput(1) para realizar esta transformación.

    Las secuencias de escape codificadas de forma rígida son compatibles con cada shell, pero no se recomiendan porque dependen de configuraciones particulares y no se pueden mover fácilmente entre diferentes entornos de usuario.

    Tu configuración puede haber establecido LOGNAME; xterm no modifica eso. Si no está establecida, xterm usará USER si está establecida. Finalmente, si ninguna de las dos está establecida, xterm usará la función getlogin(3).
    SHELL
    cuando xterm se configura (en tiempo de compilación) para actualizar utmp. También se establece si proporcionas un nombre de shell válido como parámetro opcional.
    Xterm establece esto a una ruta absoluta. Si has establecido la variable a una ruta relativa, xterm puede establecerla a una ruta de shell diferente.
    Si has establecido esto a una ruta que no corresponde a un shell válido, xterm puede desestablecerla, para evitar confusiones.
    TERMCAP
    el contenido de la entrada termcap correspondiente a $TERM, con los valores de líneas y columnas sustituidos por el tamaño real de la ventana que has creado.
    Esta característica, al igual que LINES y COLUMNS, se usa raramente. Aborda la misma limitación de algunos sistemas antiguos al proporcionar una forma para que las aplicaciones basadas en termcap obtengan el tamaño inicial de la pantalla.
    TERMINFO
    puede definirse a una ubicación no estándar usando el script de configuración.
    XCURSOR_THEME
    Ver el recurso cursorTheme.

    PROPIEDADES DE VENTANA

    En la salida de xprop(1), hay varias propiedades.

    Propiedades establecidas por X Toolkit

    WM_CLASS
    Esto muestra el nombre de instancia y la clase de recurso X, pasada a X Toolkit durante la inicialización de xterm, por ejemplo: 


    WM_CLASS(STRING) = "xterm", "UXTerm"

    WM_CLIENT_LEADER
    Esto muestra el ID de ventana que xterm proporciona con una variable de entorno (WINDOWID), por ejemplo: 


    WM_CLIENT_LEADER(WINDOW): window id # 0x800023

    WM_COMMAND
    Esto muestra los argumentos de línea de comandos para xterm que se pasan a X Toolkit durante la inicialización, por ejemplo: 


    WM_COMMAND(STRING) = { "xterm", "-class", "UXTerm", "-title", "uxterm", "-u8" }

    WM_ICON_NAME
    Esto contiene el título del icono, que diferentes administradores de ventanas manejan de diversas maneras. Se establece a través del recurso iconName. Las aplicaciones pueden cambiarlo usando secuencias de control.
    WM_LOCALE_NAME
    Esto muestra el resultado de la función setlocale(3) para la categoría LC_CTYPE, por ejemplo: 


    WM_LOCALE_NAME(STRING) = "en_US.UTF-8"

    WM_NAME
    Esto contiene el título de la ventana, normalmente en la parte superior de la ventana de xterm. Se establece a través del recurso title. Las aplicaciones pueden cambiarlo usando secuencias de control.

    Propiedades establecidas por Xterm

    X Toolkit no administra las propiedades EWMH. Xterm hace esto directamente.

    _NET_WM_ICON_NAME
    almacena el nombre del icono.
    _NET_WM_NAME
    almacena la cadena del título.
    _NET_WM_PID
    almacena el identificador del proceso para la pantalla de xterm.

    Propiedades utilizadas por Xterm

    _NET_SUPPORTED
    Xterm comprueba esta propiedad en la ventana de soporte para decidir si el administrador de ventanas soporta estilos de maximización específicos. Esto puede incluir otras sugerencias del administrador de ventanas; xterm utiliza las llamadas a la biblioteca X para administrarlas.
    _NET_SUPPORTING_WM_CHECK
    Xterm comprueba esto para asegurarse de que solo actualizará las propiedades EWMH para un administrador de ventanas que reclame el cumplimiento de EWMH.
    _NET_WM_STATE
    Esto le dice a xterm si su ventana ha sido maximizada por el administrador de ventanas, y si es así, qué tipo de maximización:
    _NET_WM_STATE_FULLSCREEN
    _NET_WM_STATE_MAXIMIZED_HORZ
    _NET_WM_STATE_MAXIMIZED_VERT

    ARCHIVOS

    Las rutas reales dadas pueden diferir en su sistema.

    /etc/shells
    contiene una lista de programas de shell válidos, utilizada por xterm para decidir si la variable de entorno “SHELL” debe establecerse para el proceso iniciado por xterm.
    En sistemas que tienen la función getusershell, xterm usará esa función en lugar de leer directamente el archivo, ya que el archivo puede no estar presente si el sistema usa configuraciones predeterminadas.
    /var/run/utmp
    el archivo de registro del sistema, que registra los inicios de sesión de usuarios.
    /var/log/wtmp
    el archivo de registro del sistema, que registra los inicios y cierres de sesión de usuarios.
    /usr/share/X11/app-defaults//XTerm
    los recursos de aplicación predeterminados de xterm.
    /usr/share/X11/app-defaults//XTerm-color
    los recursos de aplicación de color de xterm. Si su pantalla admite color, use esto 


    *customization: -color

    en su archivo .Xdefaults para usar automáticamente este archivo de recursos en lugar de /usr/share/X11/app-defaults//XTerm. Si no hace esto, xterm usa su configuración de recursos predeterminada compilada para colores.
    /usr/share/pixmaps
    el directorio en el que se instalan los archivos de icono de mapa de bits de xterm.

    ERRORES

    Las pegas grandes no funcionan en algunos sistemas. Esto no es un error en xterm; es un error en el controlador de pseudo terminal de esos sistemas. Xterm alimenta las pegas grandes a la pty solo tan rápido como la pty aceptará datos, pero algunos controladores de pty no devuelven suficiente información para saber si la escritura ha tenido éxito.

    Cuando se conecta a un método de entrada, es posible que xterm se cuelgue si el servidor XIM se suspende o se elimina.

    Muchas de las opciones no se pueden restablecer después de que xterm comienza.

    Este programa todavía necesita ser reescrito. Debería dividirse en secciones muy modulares, con los diversos emuladores siendo widgets completamente separados que no se conocen entre sí. Idealmente, querrías poder elegir y seleccionar widgets emuladores y pegarlos en un único widget de control.

    Necesita haber un cuadro de diálogo para permitir la entrada del nombre del archivo Tek COPY.
