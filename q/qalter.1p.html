QALTER(1P) Manual del programador POSIX QALTER(1P)

PROLOGO

Esta página del manual forma parte del Manual del programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

qalter — alterar trabajo por lotes

SINOPSIS

qalter [-a fecha_hora] [-A cadena_cuenta] [-c intervalo] [-e ruta_archivo]
    [-h lista_retencion] [-j lista_union] [-k lista_mantener] [-l lista_recursos]
    [-m opciones_correo] [-M lista_correo] [-N nombre] [-o ruta_archivo]
    [-p prioridad] [-r s|n] [-S lista_rutas_archivo] [-u lista_usuarios]
    identificador_trabajo...

DESCRIPCION

Los atributos de un trabajo por lotes se alteran mediante una solicitud al servidor de lotes que administra el trabajo por lotes. La utilidad qalter es un cliente de lotes accesible por el usuario que solicita la alteración de los atributos de uno o más trabajos por lotes.

La utilidad qalter alterará los atributos de aquellos trabajos por lotes, y sólo aquellos trabajos por lotes, para los cuales se presente un identificador_trabajo por lotes a la utilidad.

La utilidad qalter alterará los atributos de los trabajos por lotes en el orden en que se presenten los identificador_trabajo por lotes a la utilidad.

Si la utilidad qalter no puede procesar un identificador_trabajo por lotes con éxito, la utilidad procederá a procesar los restantes identificador_trabajo por lotes, si los hay.

Para cada identificador_trabajo por lotes para el cual la utilidad qalter tiene éxito, cada atributo del trabajo por lotes identificado se alterará según lo indicado por todas las opciones presentadas a la utilidad.

Para cada trabajo por lotes identificado para el cual la utilidad qalter falla, la utilidad no alterará ningún atributo del trabajo por lotes.

Para cada trabajo por lotes que la utilidad qalter procesa, la utilidad no modificará ningún atributo aparte de los requeridos por las opciones y argumentos de opción presentados a la utilidad.

La utilidad qalter alterará los trabajos por lotes enviando una Solicitud de Modificación de Trabajo al servidor de lotes que administra cada trabajo por lotes. En el momento en que la utilidad qalter salga, habrá modificado el trabajo por lotes correspondiente a cada identificador_trabajo por lotes procesado con éxito. Un intento de alterar los atributos de un trabajo por lotes en estado EJECUCIÓN es de implementación definida.

OPCIONES

La utilidad qalter cumplirá con el volumen de Definiciones Base de POSIX.1‐2017, Sección 12.2, Guías de sintaxis de utilidad.

Las siguientes opciones serán soportadas por la implementación:

-a fecha_hora
Redefine la hora en que el trabajo por lotes se vuelve elegible para ejecución.

El argumento fecha_hora estará en el mismo formato y representará la misma hora que para la utilidad touch. La hora así representada se establecerá en el atributo Hora_Ejecucion del trabajo por lotes. Si la hora especificada es anterior a la hora actual, la opción -a no tendrá ningún efecto.

-A cadena_cuenta

Redefine la cuenta a la que se deben imputar los recursos consumidos por el trabajo por lotes.

La sintaxis del argumento de opción cadena_cuenta no se especifica.

La utilidad qalter establecerá el atributo Nombre_Cuenta del trabajo por lotes al valor del argumento de opción cadena_cuenta.

-c intervalo
Redefine si el trabajo por lotes debe ser verificado (checkpointed), y si es así, con qué frecuencia.

La utilidad qalter aceptará un valor para el argumento de opción de intervalo que sea uno de los siguientes:

n
No se realizará ninguna verificación para el trabajo por lotes (SIN_VERIFICACION).
s
La verificación solo se realizará cuando se apague el servidor de lotes (VERIFICACION_AL_APAGADO).
c
Se realizará una verificación periódica automática en el atributo Intervalo_CPU_Minimo de la cola de lotes, en unidades de minutos de CPU (VERIFICACION_EN_INTERVALO_CPU_MINIMO).
c=minutos
Se realizará una verificación periódica automática cada minutos de tiempo de CPU, o cada Intervalo_CPU_Minimo minutos, el que sea mayor. El argumento minutos cumplirá con la sintaxis para enteros sin signo y será mayor que cero.

Una implementación puede definir otros intervalos de verificación. El documento de conformidad de una implementación describirá cualquier intervalo de verificación alternativo, cómo se especifican, su comportamiento interno y cómo afectan el comportamiento de la utilidad.

La utilidad qalter establecerá el atributo Verificacion del trabajo por lotes al valor del argumento de opción intervalo.

-e ruta_archivo

Redefine la ruta que se utilizará para el flujo de error estándar del trabajo por lotes.

La utilidad qalter aceptará un argumento de opción ruta_archivo que cumpla con la sintaxis del elemento ruta_archivo definido en el volumen de Interfaces del Sistema de POSIX.1‐2017, que puede ir precedido por un elemento de nombre de host de la forma nombre_host:.

Si el argumento de opción ruta_archivo constituye una ruta absoluta, la utilidad qalter establecerá el atributo Ruta_Error del trabajo por lotes al valor del argumento de opción ruta_archivo, incluido el elemento de nombre de host, si está presente.

Si el argumento de opción ruta_archivo constituye una ruta relativa y no se especifica ningún elemento de nombre de host, la utilidad qalter establecerá el atributo Ruta_Error del trabajo por lotes al valor de la ruta absoluta derivada expandiendo el argumento de opción ruta_archivo en relación con el directorio actual del proceso que ejecuta la utilidad qalter.

Si el argumento de opción ruta_archivo constituye una ruta relativa y se especifica un elemento de nombre de host, la utilidad qalter establecerá el atributo Ruta_Error del trabajo por lotes al valor del argumento de opción sin expansión.

Si el argumento de opción ruta_archivo no incluye un elemento de nombre de host, la utilidad qalter antepondrá la ruta en el atributo Ruta_Error con nombre_host:, donde nombre_host es el nombre del host en el que se está ejecutando la utilidad qalter.

-h lista_retencion
Redefine los tipos de retenciones, si las hay, en el trabajo por lotes. La opción qalter -h aceptará un valor para el argumento de opción lista_retencion que sea una cadena de caracteres alfanuméricos en el conjunto de caracteres portable.

La utilidad qalter aceptará un valor para el argumento de opción lista_retencion que sea una cadena de uno o más de los caracteres 'u', 's', o 'o', o el carácter único 'n'. Para cada carácter único en el argumento de opción lista_retencion, la utilidad qalter añadirá un valor al atributo Tipos_Retencion del trabajo por lotes de la siguiente manera, cada uno representando un tipo de retención diferente:

u
USUARIO
s
SISTEMA
o
OPERADOR

Si alguno de estos caracteres se duplica en el argumento de opción lista_retencion, los duplicados se ignorarán. Un atributo Tipos_Retencion existente se puede borrar con el tipo de retención:

n
SIN_RETENCION

La utilidad qalter considerará un error si se combina cualquier tipo de retención que no sea 'n'

nido con el tipo de retención 'n'. Las aplicaciones estrictamente conformes no deben repetir ninguno de los caracteres 'u', 's', 'o' o 'n' dentro del argumento de opción hold_list. La utilidad qalter permitirá la repetición de caracteres, pero no asignará un significado adicional a los caracteres repetidos. Una implementación puede definir otros tipos de retención. El documento de conformidad de una implementación describirá cualquier tipo de retención adicional, cómo se especifican, su comportamiento interno y cómo afectan al comportamiento de la utilidad.

-j join_list
Redefine qué flujos del trabajo por lotes se fusionarán. La opción -j de qalter aceptará un valor para el argumento de opción join_list que sea una cadena de caracteres alfanuméricos del conjunto de caracteres portable.

La utilidad qalter aceptará un argumento de opción join_list que consista en uno o más de los caracteres 'e' y 'o', o el carácter único 'n'.

Todos los demás flujos de salida del trabajo por lotes especificados se fusionarán en el flujo de salida representado por el carácter listado primero en el argumento de opción join_list.

Para cada carácter único en el argumento de opción join_list, la utilidad qalter agregará un valor al atributo Join_Path del trabajo por lotes de la siguiente manera, cada uno representando un flujo diferente del trabajo por lotes para unir:

e
El error estándar del trabajo por lotes (JOIN_STD_ERROR).
o
La salida estándar del trabajo por lotes (JOIN_STD_OUTPUT).

Un atributo Join_Path existente puede ser borrado por el tipo de unión:

n
NO_JOIN

Si se especifica 'n', entonces no se unen archivos. La utilidad qalter considerará un error si se combina algún tipo de unión que no sea 'n' con el tipo de unión 'n'.

Las aplicaciones estrictamente conformes no deben repetir ninguno de los caracteres 'e', 'o' o 'n' dentro del argumento de opción join_list. La utilidad qalter permitirá la repetición de caracteres, pero no asignará un significado adicional a los caracteres repetidos.

Una implementación puede definir otros tipos de unión. El documento de conformidad de una implementación describirá cualquier flujo de trabajo por lotes adicional, cómo se especifican, su comportamiento interno y cómo afectan al comportamiento de la utilidad.

-k keep_list
Redefine qué salida del trabajo por lotes se conservará en el host de ejecución.

La opción -k de qalter aceptará un valor para el argumento de opción keep_list que sea una cadena de caracteres alfanuméricos del conjunto de caracteres portable.

La utilidad qalter aceptará un argumento de opción keep_list que consista en uno o más de los caracteres 'e' y 'o', o el carácter único 'n'.

Para cada carácter único en el argumento de opción keep_list, la utilidad qalter agregará un valor al atributo Keep_Files del trabajo por lotes de la siguiente manera, cada uno representando un flujo diferente del trabajo por lotes para conservar:

e
El error estándar del trabajo por lotes (KEEP_STD_ERROR).
o
La salida estándar del trabajo por lotes (KEEP_STD_OUTPUT).

Si se especifican tanto 'e' como 'o', se conservan ambos archivos. Un atributo Keep_Files existente puede ser borrado por el tipo de conservación:

n
NO_KEEP

Si se especifica 'n', entonces no se conservan archivos. La utilidad qalter considerará un error si se combina algún tipo de conservación que no sea 'n' con el tipo de conservación 'n'.

Las aplicaciones estrictamente conformes no deben repetir ninguno de los caracteres 'e', 'o' o 'n' dentro del argumento de opción keep_list. La utilidad qalter permitirá la repetición de caracteres, pero no asignará un significado adicional a los caracteres repetidos. Una implementación puede definir otros tipos de conservación. El documento de conformidad de una implementación describirá cualquier tipo de conservación adicional, cómo se especifican, su comportamiento interno y cómo afectan al comportamiento de la utilidad.

-l resource_list

Redefine los recursos que están permitidos o requeridos por el trabajo por lotes.

La utilidad qalter aceptará un argumento de opción resource_list que cumpla con la siguiente sintaxis:

recurso=valor[,,recurso=valor,,...]

La utilidad qalter establecerá una entrada en el valor del atributo Resource_List del trabajo por lotes por cada recurso listado en el argumento de opción resource_list.

Dado que la lista de nombres de recursos admitidos puede variar según el servidor de lotes, la utilidad qalter confiará en el servidor de lotes para validar los nombres de recursos y los valores asociados. Consulte la Sección 3.3.3, Múltiples Pares Clave-Valor para conocer un medio de eliminar pares keyword=value (y value@keyword) y otras reglas generales para atributos de trabajos por lotes orientados a listas.

-m mail_options

Redefine los puntos en la ejecución del trabajo por lotes en los que el servidor de lotes debe enviar correo sobre un cambio en el estado del trabajo por lotes.

La opción -m de qalter aceptará un valor para el argumento de opción mail_options que sea una cadena de caracteres alfanuméricos del conjunto de caracteres portable.

La utilidad qalter aceptará un valor para el argumento de opción mail_options que sea una cadena de uno o más de los caracteres 'e', 'b' y 'a', o el carácter único 'n'. Para cada carácter único en el argumento de opción mail_options, la utilidad qalter agregará un valor al atributo Mail_Users del trabajo por lotes de la siguiente manera, cada uno representando un momento diferente durante la vida de un trabajo por lotes en el que enviar correo:

e
MAIL_AT_EXIT
b
MAIL_AT_BEGINNING
a
MAIL_AT_ABORT

Si alguno de estos caracteres se duplica en el argumento de opción mail_options, los duplicados se ignorarán.

Un atributo Mail_Points existente puede ser borrado por el tipo de correo:

n
NO_MAIL

Si se especifica 'n', entonces no se envía correo. La utilidad qalter considerará un error si se combina algún tipo de correo que no sea 'n' con el tipo de correo 'n'. Las aplicaciones estrictamente conformes no deben repetir ninguno de los caracteres 'e', 'b', 'a' o 'n' dentro del argumento de opción mail_options. La utilidad qalter permitirá la repetición de caracteres pero no asignará un significado adicional a los caracteres repetidos.

Una implementación puede definir otros tipos de correo. El documento de conformidad de una implementación describirá cualquier tipo de correo adicional, cómo se especifican, su comportamiento interno y cómo afectan al comportamiento de la utilidad.

-M mail_list
Redefine la lista de usuarios a los que el servidor de lotes que ejecuta el trabajo por lotes debe enviar correo, si el servidor de lotes envía correo sobre el trabajo por lotes.

La sintaxis del argumento de opción mail_list no está especificada. Si la implementación de la utilidad qalter utiliza un servicio de nombres para localizar usuarios, la utilidad aceptará la sintaxis utilizada por el servicio de nombres.

Si la implementación de la utilidad qalter no utiliza un servicio de nombres para localizar usuarios, la implementación aceptará la siguiente sintaxis para los nombres de usuario:

dirección_correo[,,dirección_correo,,...]

La interpretación de dirección_correo es definida por la implementación.

La utilidad qalter establecerá el atributo Mail_Users del trabajo por lotes con el valor del argumento de opción mail_list.

-N name
Redefine el nombre del trabajo por lotes.

La opción -N de qalter aceptará un valor para el argumento de opción name que sea una cadena de hasta 15 caracteres alfanuméricos del conjunto de caracteres portable donde el primer carácter sea alfabético.

La sintaxis del argumento de opción name no está especificada.

La utilidad qalter establecerá el atributo Job_Name del trabajo por lotes con el valor del argumento de opción name.

-o path_name

Redefine la ruta para la salida estándar del trabajo por lotes.

La utilidad qalter aceptará un argumento de opción path_name que cumpla con la sintaxis del elemento path_name definido en el volumen de Interfaces del Sistema de POSIX.1-2017, que puede estar precedido por un elemento de nombre de host de la forma hostname:.

Si el argumento de opción path_name constituye una ruta absoluta, la utilidad qalter establecerá el atributo Output_Path del trabajo por lotes con el valor del argumento de opción path_name.

Si el argumento de opción path_name constituye una ruta relativa y no se especifica ningún elemento de nombre de host, la utilidad qalter establecerá el atributo Output_Path del trabajo por lotes con la ruta absoluta derivada al expandir el argumento de opción path_name en relación con el directorio actual del proceso que ejecuta la utilidad qalter.

Si el argumento de opción path_name constituye una ruta relativa y se especifica un elemento de nombre de host, la utilidad qalter establecerá el atributo Output_Path del trabajo por lotes con el valor del argumento de opción path_name sin ninguna expansión de la ruta.

NAME

qalter - change the attributes of a batch job

SYNOPSIS

qalter [-a
       |-A  account_string]
       [-c  interval]
       [-e  pathname]
       [-h  hold_type]
       [-i  pathname]
       [-m  mail_options]
       [-N  jobname]
       [-o  pathname]
       [-p  priority]
       [-r  y|n]
       [-S  pathname_list]
       [-u  user_list]
       job_identifier...

DESCRIPTION

The qalter utility shall submit a request to change the attributes of one or more batch jobs identified by the job_identifier operands.

The qalter utility shall support the following options:

-a
Redefine the start time of the batch job. The qalter utility shall accept a time value that conforms to the syntax for a date and time specification for the -a option of the qsub utility. See qsub(1).

The qalter utility shall set the start_time attribute of the batch job to the time specified by the option-argument.

-A account_string
Redefine the account string associated with the batch job.

The qalter utility shall set the Account_String attribute of the batch job to the value of the account_string option-argument.

-c interval
Redefine the checkpoint interval of the batch job.

The qalter utility shall accept a value for the checkpoint interval option-argument that conforms to the syntax for a positive integer. This integer shall be interpreted as a number of minutes.

The qalter utility shall set the Checkpoint_Interval attribute of the batch job to the value of the interval option-argument.

-e pathname
Redefine the pathname of the standard error stream.

The qalter utility shall set the Error_Pathname attribute of the batch job to the value of the pathname option-argument.

If the pathname does not include a hostname and the Join_Path attribute of the batch job is TRUE, the pathname shall be prefixed with the name of the host on which the qalter utility is executing.

-h hold_type
Redefine the hold state of the batch job.

The qalter utility shall accept a value for the hold_type option-argument that conforms to the syntax for a hold type. See Section 3.2.1, Hold Types.

The qalter utility shall set the Hold_Types attribute of the batch job to the value of the hold_type option-argument.

-i pathname
Redefine the pathname of the standard input stream.

The qalter utility shall set the Input_Pathname attribute of the batch job to the value of the pathname option-argument.

If the pathname does not include a hostname and the Join_Path attribute of the batch job is TRUE, the pathname shall be prefixed with the name of the host on which the qalter utility is executing.

-m mail_options
Redefine the conditions under which mail is to be sent.

The qalter utility shall accept a value for the mail_options option-argument that conforms to the syntax for mail options. See Section 3.2.4, Mail Options.

The qalter utility shall set the Mail_Options attribute of the batch job to the value of the mail_options option-argument.

-N jobname
Redefine the name of the batch job.

The qalter utility shall set the Job_Name attribute of the batch job to the value of the jobname option-argument.

-o pathname
Redefine the pathname of the standard output stream.

The qalter utility shall set the Output_Pathname attribute of the batch job to the value of the pathname option-argument.

If the Output_Path attribute does not include a host name element, the qalter utility shall prefix the pathname in the Output_Path attribute with hostname:, where hostname is the name of the host upon which the qalter utility is being executed.

-p priority
Redefine the priority of the batch job.

The qalter utility shall accept a value for the priority option-argument that conforms to the syntax for signed decimal integers, and which is not less than -1024 and not greater than 1023.

The qalter utility shall set the Priority attribute of the batch job to the value of the priority option-argument.

-r y|n
Redefine whether the batch job is rerunnable.

If the value of the option-argument is 'y', the qalter utility shall set the Rerunable attribute of the batch job to TRUE.

If the value of the option-argument is 'n', the qalter utility shall set the Rerunable attribute of the batch job to FALSE.

The qalter utility shall consider it an error if any character other than 'y' or 'n' is specified in the option-argument.

-S path_name_list

Redefine the shell that interprets the script at the destination system.

The qalter utility shall accept a path_name_list option-argument that conforms to the following syntax:

pathname[@host][,pathname[@host],...]

The qalter utility shall accept only one pathname that is missing a corresponding host name. The qalter utility shall allow only one pathname per named host.

The qalter utility shall add a value to the Shell_Path_List attribute of the batch job for each entry in the path_name_list option-argument. See Section 3.3.3, Multiple Keyword-Value Pairs for a means of removing keyword=value (and value@keyword) pairs and other general rules for list-oriented batch job attributes.

-u user_list
Redefine the user name under which the batch job is to run at the destination system.

The qalter utility shall accept a user_list option-argument that conforms to the following syntax:

username[@host][,,username[@host],,...]

The qalter utility shall accept only one user name that is missing a corresponding host name. The qalter utility shall accept only one user name per named host.

The qalter utility shall add a value to the User_List attribute of the batch job for each entry in the user_list option-argument. See Section 3.3.3, Multiple Keyword-Value Pairs for a means of removing keyword=value (and value@keyword) pairs and other general rules for list-oriented batch job attributes.

OPERANDS

The qalter utility shall accept one or more operands that conform to the syntax for a batch job_identifier (see Section 3.3.1, Batch Job Identifier).

RATIONALE

The qalter utility allows users to change the attributes of a batch job.

As a means of altering a queued job, the qalter utility is superior to deleting and requeuing the batch job insofar as an altered job retains its place in the queue with some traditional selection algorithms. In addition, the qalter utility is both shorter and simpler than a sequence of qdel and qsub utilities.

The result of an attempt on the part of a user to alter a batch job in a RUNNING state is implementation-defined because a batch job in the RUNNING state will already have opened its output files and otherwise performed any actions indicated by the options in effect at the time the batch job began execution.

The options processed by the qalter utility are identical to those of the qsub utility, with a few exceptions: -V, -v, and -q. The -V and -v are inappropriate for the qalter utility, since they capture potentially transient environment information from the submitting process. The -q option would specify a new queue, which would largely negate the previously stated advantage of using qalter; furthermore, the qmove utility provides a superior means of moving jobs.

Each of the following paragraphs provides the rationale for a qalter option.

Additional rationale concerning these options can be found in the rationale for the qsub utility.

The -a option allows users to alter the date and time at which a batch job becomes eligible to run.

The -A option allows users to change the account that will be charged for the resources consumed by the batch job. Support for the -A option is mandatory for conforming implementations of qalter, even though support of accounting is optional for servers. Whether or not to support accounting is left to the implementor of the server, but mandatory support of the -A option assures users of a consistent interface and allows them to control accounting on servers that support accounting.

The -c option allows users to alter the checkpointing interval of a batch job. A checkpointing system, which is not defined by POSIX.1‐2008, allows recovery of a batch job at the most recent checkpoint in the event of a crash. Checkpointing is typically used for jobs that consume expensive computing time or must meet a critical schedule. Users should be allowed to make the tradeoff between the overhead of checkpointing and the risk to the timely completion of the batch job; therefore, this volume of POSIX.1‐2017 provides the checkpointing interval option. Support for checkpointing is optional for servers.

The -e option allows users to alter the name and location of the standard error stream written by a batch job. However, the path of the standard error stream is meaningless if the value of the Join_Path attribute of the batch job is TRUE.

The -h option allows users to set the hold type in the Hold_Types attribute of a batch job. The qhold and qrls utilities add or remove hold types to the Hold_Types attribute, respectively. The -h option has been modified to allow for implementation-defined hold types.

The -i option allows users to alter the name and location of the standard input stream for a batch job.

The -m option allows users to control the conditions under which the batch job requests that mail be sent. The mail options are specified as a comma-separated list of keywords. The keywords are: `b' (begin), `e' (end), `a' (abort), `l' (last), and `u' (usage). The default set of mail options is `e,a,l,u'.

The -N option allows users to change the name of the batch job.

The -o option allows users to alter the name and location of the standard output stream written by a batch job. However, the path of the standard output stream is meaningless if the value of the Join_Path attribute of the batch job is TRUE.

The -p option allows users to change the priority of the batch job. A higher priority value means that the job is more likely to be selected for execution. The range of priority values is implementation-defined but shall be within the range [-1024, 1023].

The -r option allows users to specify whether the batch job should be rerunable after it has completed execution. This attribute is intended for use with batch jobs that can be restarted from intermediate points. The default value is implementation-defined.

The -S option allows users to specify the shell to be used to interpret the script for the batch job. The list of shells is specified as a comma-separated list of pathnames. Each pathname is the full path to a shell executable. An optional `@host` suffix may be appended to a pathname. If a host is specified, that shell should be used on that host. If no host is specified, the shell should be used on any host. If only one shell is specified without a host, that shell is used for all hosts.

The -u option allows users to specify the user name under which the batch job should run. The list of users is specified as a comma-separated list of user names. An optional `@host` suffix may be appended to a user name. If a host is specified, that user should be used on that host. If no host is specified, the user should be used on any host. If only one user is specified without a host, that user is used for all hosts.

OPTIONS

The -a option allows users to alter the decision to join (merge) the standard error stream of the batch job with the standard output stream of the batch job.

The -l option allows users to change the resource limits imposed on a batch job.

The -m option allows users to modify the list of points in the life of a batch job at which the designated users will receive mail notification.

The -M option allows users to alter the list of users who will receive notification about events in the life of a batch job.

The -N option allows users to change the name of a batch job.

The -o option allows users to alter the name and path to which the standard output stream of the batch job will be written.

The -P option allows users to modify the priority of a batch job. Support for priority is optional for batch servers.

The -r option allows users to alter the rerunability status of a batch job.

The -S option allows users to change the name and location of the shell image that will be invoked to interpret the script of the batch job. This option has been modified to allow a list of shell name and locations associated with different hosts.

The -u option allows users to change the user identifier under which the batch job will execute.

OPERANDS

The job_identifier operand syntax is provided so that the user can differentiate between the originating and destination (or executing) batch server. These may or may not be the same. The .server_name portion identifies the originating batch server, while the @server portion identifies the destination batch server.
