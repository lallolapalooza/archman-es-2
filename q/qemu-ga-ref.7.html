qemu-ga-ref - Referencia del Protocolo QEMU Guest Agent

Este manual describe los comandos soportados por el Protocolo QEMU Guest Agent.

Para localizar un elemento en particular, por favor vea el Índice QGA <>.

La siguiente notación se utiliza en los ejemplos:

Ejemplo:
-> ... texto enviado por el cliente (comandos) ...
<- ... texto enviado por el servidor (respuestas a comandos y eventos) ...

El texto de ejemplo está formateado para facilitar la lectura. Sin embargo, en el uso real del protocolo, comúnmente se emite como una sola línea.

Por favor, consulte la Especificación del Protocolo de Máquina QEMU <> para el formato general de comandos, respuestas y eventos.

Comando guest-sync-delimited (Desde: 1.1)
Devuelve un valor entero único, y antepone un byte centinela inicial (0xFF) a la respuesta que el cliente puede escanear para verificar.

Esto es utilizado por los clientes que se comunican con el agente invitado a través del cable para asegurar que el flujo está sincronizado y no contiene datos obsoletos del cliente anterior. Debe emitirse al conectar inicialmente y después de cualquier tiempo de espera del lado del cliente (incluyendo tiempos de espera en la recepción de una respuesta a este comando).

Después de emitir esta solicitud, todas las respuestas del agente invitado deben ser ignoradas hasta que se devuelva la respuesta que contiene el valor entero único que el cliente pasó. La recepción del byte centinela 0xFF debe manejarse como una indicación de que el estado del lexer/tokenizador/parser del cliente debe ser vaciado/reiniciado en preparación para recibir de manera confiable la respuesta subsiguiente. Como optimización, los clientes pueden optar por ignorar todos los datos hasta que se reciba un valor centinela para evitar el procesamiento innecesario de datos obsoletos.

De manera similar, los clientes también deben preceder esta solicitud con un byte 0xFF para asegurarse de que el agente invitado vacíe cualquier dato JSON leído parcialmente de una conexión de cliente anterior.

Argumentos
•
id (int) -- entero de 64 bits generado aleatoriamente
Retorno
int -- El ID entero único pasado por el cliente
Comando guest-sync (Desde: 0.15.0)
Devuelve un valor entero único.

Esto es utilizado por los clientes que se comunican con el agente invitado a través del cable para asegurar que el flujo está sincronizado y no contiene datos obsoletos del cliente anterior. Todas las respuestas del agente invitado deben ser ignoradas hasta que se devuelva el valor entero único proporcionado, y depende del cliente manejar el texto JSON completo o parcialmente entregado de tal manera que esta respuesta pueda ser obtenida.

En casos donde el cliente recibió previamente una respuesta parcial obsoleta, esto no siempre se puede hacer de manera confiable. Una situación particular es si las respuestas de qemu-ga se alimentan carácter por carácter a un analizador JSON. En estas situaciones, usar guest-sync-delimited puede ser óptimo.

Para clientes que obtienen respuestas línea por línea y las convierten en objetos JSON, guest-sync debería ser suficiente, pero tenga en cuenta que en casos donde el canal está sucio, algunos intentos de analizar la respuesta pueden resultar en un error del analizador.

Tales clientes también deben preceder este comando con un byte 0xFF para asegurarse de que el agente invitado vacíe cualquier dato JSON leído parcialmente de una sesión anterior.

Argumentos
•
id (int) -- entero de 64 bits generado aleatoriamente
Retorno
int -- El ID entero único pasado por el cliente

Comando guest-set-time (Desde: 1.5)
Establecer la hora del invitado.

Cuando un invitado se pausa o se migra a un archivo y luego se carga desde ese archivo, el sistema operativo del invitado no sabe que hubo una gran brecha en el tiempo. Dependiendo de la duración de la brecha, NTP podría no ser capaz de resincronizar al invitado.

Este comando intenta establecer la Hora del Sistema del invitado al valor dado, y luego establece el Reloj de Hardware (RTC) a la Hora del Sistema actual. Esto facilitará la resincronización del invitado sin esperar a NTP. Si no se especifica time, la hora a establecer se lee del RTC. Sin embargo, esto puede no ser soportado en todas las plataformas (es decir, Windows). Si ese es el caso, se recomienda a los usuarios que siempre pasen un valor.

Argumentos
•
time (int, opcional) -- tiempo en nanosegundos, relativo a la Época del 01-01-1970 en UTC.

Comando guest-set-vcpus (Desde: 1.5)
Disponibilidad: CONFIG_LINUX

Intentar reconfigurar (actualmente: habilitar/deshabilitar) procesadores lógicos dentro del invitado.

Argumentos
•
vcpus ([GuestLogicalProcessor]) -- Los procesadores lógicos a reconfigurar. Esta lista se procesa nodo por nodo en orden. En cada nodo, se utiliza logical-id para buscar la VCPU del invitado, para la cual online especifica el estado solicitado. Solo se requiere que el conjunto de logical-id distintos sea un subconjunto de los identificadores admitidos por el invitado. No hay restricciones en la longitud de la lista ni en la repetición del mismo logical-id (con posiblemente un campo online diferente). Preferiblemente, la lista de entrada debe describir un subconjunto modificado del valor de retorno de guest-get-vcpus.
Retorno
int --

La longitud de la sublista inicial que se ha procesado con éxito. El agente invitado maximiza este valor. Casos posibles:

  • 0: si la lista vcpus estaba vacía en la entrada. El estado del invitado no ha cambiado. De lo contrario,
  • < longitud(vcpus): se han procesado más de cero nodos iniciales, pero no la lista completa vcpus. El estado del invitado ha cambiado en consecuencia. Para recuperar el error (suponiendo que persista), repita la llamada eliminando la sublista inicial procesada con éxito. De lo contrario,
  • longitud(vcpus): llamada exitosa.
Errores
•
Si la reconfiguración del primer nodo en vcpus falló. El estado del invitado no ha cambiado.
