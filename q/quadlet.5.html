NOMBRE

podman-systemd.unit - unidades systemd usando Podman Quadlet

SINOPSIS

nombre.container, nombre.volume, nombre.network, nombre.kube nombre.image, nombre.build nombre.pod, nombre.artifact

Ruta de búsqueda de unidades rootful de Podman

Los archivos Quadlet para el usuario root se pueden colocar en los siguientes directorios, ordenados por precedencia. Esto significa que los quadlets con nombres duplicados encontrados en /run tienen prioridad sobre los de /etc, así como sobre los de /usr:

Quadlets temporales, generalmente usados para pruebas:

•
/run/containers/systemd/

Quadlets definidos por el administrador del sistema:

•
/etc/containers/systemd/

Quadlets definidos por la distribución:

•
/usr/share/containers/systemd/

Ruta de búsqueda de unidades rootless de Podman

Los archivos Quadlet para usuarios no root se pueden colocar en los siguientes directorios:

  • $XDG_RUNTIME_DIR/containers/systemd/
  • $XDG_CONFIG_HOME/containers/systemd/ o ~/.config/containers/systemd/
  • /etc/containers/systemd/users/$(UID)
  • /etc/containers/systemd/users/

Uso de enlaces simbólicos

Quadlet admite el uso de enlaces simbólicos para la base de las rutas de búsqueda y dentro de ellas.

DESCRIPCIÓN

Podman admite la creación y el inicio de contenedores (y la creación de volúmenes) a través de systemd utilizando un generador de systemd. Estos archivos se leen durante el arranque (y cuando se ejecuta systemctl daemon-reload) y generan los correspondientes archivos de unidad de servicio de systemd normales. Se admiten tanto las unidades systemd del sistema como las del usuario. Todas las opciones y tablas disponibles en los archivos de unidad de systemd estándar son compatibles. Por ejemplo, las opciones definidas en las tablas [Service] y [Install] se pasan directamente a systemd y son manejadas por él. Consulte la página del manual systemd.unit(5) para obtener más información.

El generador de Podman lee las rutas de búsqueda anteriores y lee archivos con las extensiones .container, .volume, .network, .build, .pod, .kube y .artifact, y para cada archivo genera un archivo .service con nombre similar. Tenga en cuenta que los servicios de proveedor existentes (es decir, en /usr/) se reemplazan si tienen el mismo nombre. Los archivos de unidad generados se pueden iniciar y administrar con systemctl como cualquier otro servicio systemd. systemctl {--user} list-unit-files enumera los archivos de unidad existentes en el sistema.

Los archivos Podman utilizan el mismo formato que los archivos de unidad de systemd normales. Cada tipo de archivo tiene una sección personalizada (por ejemplo, [Container]) que es manejada por Podman, y todas las demás secciones se pasan sin modificar, lo que permite el uso de cualquier opción de configuración normal de systemd, como dependencias o límites de cgroup.

Los archivos fuente también admiten drop-ins de la misma manera que systemd. Para un archivo fuente dado (foo.container), el directorio correspondiente .d (foo.container.d) se escaneará en busca de archivos con extensión .conf, que luego se fusionarán en el archivo base en orden alfabético. También se incluirán los drop-ins de tipo principal (container.d). Si la unidad contiene guiones ("-") en el nombre (foo-bar-baz.container), también se buscarán los directorios de drop-ins generados al truncar el nombre después del guion (foo-.container.d y foo-bar-.container.d). Los archivos de drop-in con el mismo nombre más abajo en la jerarquía anulan a los más arriba (foo-bar-baz.container.d/10-override.conf anula foo-bar-.container.d/10-override.conf, que anula foo-.service.d/10-override.conf, que anula container.d/10-override.conf). El formato de estos archivos de drop-in es el mismo que el del archivo base. Esto es útil para modificar o agregar configuraciones a una unidad, sin tener que modificar los archivos de unidad.

Para contenedores sin root, cuando los administradores colocan archivos Quadlet en el directorio /etc/containers/systemd/users, las sesiones de todos los usuarios ejecutan el Quadlet cuando comienza la sesión de inicio de sesión. Si el administrador coloca un archivo Quadlet en el directorio /etc/containers/systemd/users/${UID}/, entonces solo el usuario con el UID coincidente ejecuta el Quadlet cuando se inicia la sesión de inicio de sesión. Para los archivos de unidad colocados en subdirectorios dentro de /etc/containers/systemd/user/${UID}/ y las otras rutas de búsqueda de unidades de usuario, Quadlet buscará recursivamente y ejecutará los archivos de unidad presentes en estos subdirectorios.

Tenga en cuenta que las unidades Quadlet no admiten la ejecución como usuario no root definiendo las opciones del sistema User, Group o DynamicUser. Si desea ejecutar un Quadlet sin root, deberá crear el usuario y agregar el archivo de unidad a una de las rutas de búsqueda de unidades sin root anteriores.

Nota: Cuando un Quadlet se está iniciando, Podman a menudo descarga o compila una o más imágenes de contenedor, lo que puede llevar una cantidad considerable de tiempo. Systemd establece el tiempo de inicio del servicio en 90 segundos por defecto, o falla el servicio. La precarga de la imagen o la extensión del tiempo de espera de systemd para el servicio usando la opción TimeoutStartSec del Servicio puede solucionar el problema. Una advertencia: TimeoutStartSec no está disponible para unidades Type=oneshot. Consulte systemd.service(5) para obtener más información sobre cómo manejar tiempos de inicio largos para unidades que no necesitan permanecer activas una vez que su proceso principal ha finalizado.

Agregar el siguiente fragmento a un archivo Quadlet extiende el tiempo de espera de systemd a 15 minutos.

[Service]
TimeoutStartSec=900

Quadlet requiere el uso de cgroup v2, use podman info --format {{.Host.CgroupsVersion}} para verificar en el sistema.

Tipo de servicio

Por defecto, el campo Type de la sección Service del archivo Quadlet no necesita ser establecido. Quadlet lo establecerá en notify para archivos .container y .kube, forking para archivos .pod, y oneshot para archivos .volume, .network, .build, .image y .artifact.

Sin embargo, Type puede establecerse explícitamente en oneshot para archivos .container y .kube cuando no se espera que se ejecuten contenedores una vez que podman sale.

Al establecer Type=oneshot, se recomienda también establecer RemainAfterExit=yes para evitar que el estado del servicio se vuelva inactive (dead). Sin embargo, al activar un servicio a través de una unidad de temporizador, tener RemainAfterExit=yes deja el trabajo en un estado "started" que evita activaciones posteriores por el temporizador. Para más información, consulte la página del manual systemd.service(5).

Ejemplos para tales casos: - archivo .container con una imagen que sale después de que su entrypoint ha finalizado

•
archivo .kube que apunta a un archivo Yaml de Kubernetes que no define ningún contenedor. Por ejemplo, solo PVCs

Habilitación de archivos de unidad

Los servicios creados por Podman son considerados transitorios por systemd, lo que significa que no tienen las mismas reglas de persistencia que las unidades normales. En particular, no es posible usar systemctl enable para que se habiliten automáticamente en el próximo arranque.

Para compensar esto, el generador aplica manualmente la sección [Install] de los archivos de unidad de definición de contenedor durante la generación, de la misma manera que lo hace systemctl enable cuando se ejecuta más tarde.

Por ejemplo, para iniciar un contenedor en el arranque, agregue algo como esto al archivo:

[Install]
WantedBy=default.target

Actualmente, solo las claves Alias, WantedBy, RequiredBy y UpheldBy son compatibles.

La sección Install puede ser parte del archivo principal, o puede estar en un archivo de drop-in separado como se describe anteriormente. Este último permite instalar una unidad no habilitada y luego habilitarla instalando el drop-in.

Unidades de plantilla

Las unidades de plantilla se crean a partir de plantillas de unidades de systemd con el mismo nombre. Por ejemplo, un archivo foo@.service crea una plantilla de unidad de systemd, que luego puede ser instanciada como foo@bar.service. Esto permite crear múltiples instancias de un servicio a partir de una única definición.

Los quadlets admiten esto de dos maneras. En primer lugar, un quadlet con una forma de plantilla generará un servicio de systemd con una forma de plantilla, y el servicio de systemd de plantilla se puede usar como una plantilla regular. Por ejemplo, foo@.container generará foo@.service y luego podrá iniciar foo@bar.service usando systemctl start foo@bar.service.

En segundo lugar, si crea un enlace simbólico como foo@instance.container, esto generará un archivo de plantilla instanciado. Al generar este archivo, quadlet leerá archivos de tipo "drop-in" tanto del directorio de instancias (foo@instance.container.d) como del directorio de plantillas (foo@.container.d). Esto permite la personalización de instancias individuales.

Los archivos de plantilla instanciados (como foo@bar.container) se pueden habilitar al igual que los que no son plantillas. Sin embargo, los que son plantillas (foo@.container) son diferentes, ya que deben ser instanciados. Si la sección [Install] contiene una clave DefaultInstance=, esa instancia se habilitará, pero si no, no sucederá nada y las opciones solo se usarán como predeterminadas para las unidades que se instancien mediante enlaces simbólicos.

Un ejemplo de archivo de plantilla sleep@.container podría verse así:

[Unit]
Description=Un contenedor de suspensión con plantilla
[Container]
Image=quay.io/fedora/fedora
Exec=sleep %i
[Service]
# Reiniciar servicio cuando termine la suspensión
Restart=always
[Install]
WantedBy=multi-user.target
DefaultInstance=100

Si esto se instala, al arrancar habrá un servicio sleep@100.service en ejecución que espera 100 segundos. Luego, puede hacer algo como systemctl start sleep@50.service para iniciar otra instancia que espere 50 segundos, o alternativamente, otro servicio puede iniciarlo a través de una dependencia como Wants=sleep@50.service.

Además, si hace ln -s sleep@.container sleep@10.container, también tendrá una espera de 10 segundos en el arranque. Y, si desea que esa instancia en particular se ejecute con una imagen diferente, puede crear un archivo de tipo "drop-in" como sleep@10.container.d/10-image.conf:

[Container]
Image=quay.io/centos/centos

Rutas relativas

Para admitir los especificadores de Systemd, Quadlet no resuelve rutas relativas que comienzan con %. Para resolver una ruta de este tipo, antepóngale ./.

Por ejemplo, en lugar de EnvironmentFile=%n/env use EnvironmentFile=./%n/env

Depuración de archivos de unidad

Después de colocar el archivo de unidad en una de las rutas de búsqueda de unidades (mencionadas anteriormente), puede iniciarlo con systemctl start {--user}. Si falla con el mensaje "Failed to start example.service: Unit example.service not found.", entonces es posible que haya utilizado una sintaxis incorrecta o que haya utilizado una opción de una versión más reciente de Podman Quadlet y el generador no pudo crear un archivo de servicio.

Vea los archivos generados y/o los mensajes de error con:

/usr/lib/systemd/system-generators/podman-system-generator {--user} --dryrun

Alternativamente, muestre solo los errores con:

systemd-analyze {--user} --generators=true verify example.service

Ese comando también realiza comprobaciones adicionales en la unidad de servicio generada. Para obtener detalles, consulte la página del manual de systemd-analyze(1).

Depuración de un conjunto limitado de archivos de unidad

Si desea depurar un conjunto limitado de archivos de unidad, puede copiarlos a un directorio separado y establecer la variable de entorno QUADLET_UNIT_DIRS en este directorio al ejecutar el comando a continuación:

QUADLET_UNIT_DIRS=<Directorio> /usr/lib/systemd/system-generators/podman-system-generator {--user} --dryrun

Esto instruirá a Quadlet a buscar unidades en este directorio en lugar de los comunes y, por lo tanto, limitará la salida solo a las unidades que está depurando.

Dependencias implícitas de red

Quadlet agregará dependencias en network-online.target (como root) o podman-user-wait-network-online.service (como usuario) agregando propiedades After= y Wants= a la unidad. Esto es para asegurar que la red sea accesible si es necesario descargar una imagen y en el momento en que se inicie el contenedor.

El caso especial podman-user-wait-network-online.service es necesario como usuario porque las unidades de usuario no pueden esperar a las unidades del sistema (root), por lo que network-online.target no hace nada allí y se ignora. Dado que esto causó una cantidad significativa de problemas, decidimos sortear esto con nuestra propia unidad de propósito especial que simplemente verifica si la unidad network-online.target está activa con systemctl is-active network-online.target.

Este comportamiento se puede deshabilitar agregando DefaultDependencies=false en la sección [Quadlet]. Tenga en cuenta que la sección [Unit] de systemd tiene una opción con el mismo nombre pero con un significado diferente.

Dependencia entre unidades de Quadlet

Quadlet traducirá automáticamente las dependencias especificadas en las claves Wants, Requires, Requisite, BindsTo, PartOf, Upholds, Conflicts, Before y After de la sección [Unit] entre diferentes unidades de Quadlet.

Por ejemplo, la unidad fedora.container a continuación especifica una dependencia en la unidad basic.container.

[Unit]
After=basic.container
Requires=basic.container
[Container]
Image=registry.fedoraproject.org/fedora:41

Establecer nombres de recursos

Las unidades de Quadlet permiten establecer los nombres de los recursos creados (por ejemplo, VolumeName para unidades .volume o PodName para unidades .pod).

Tenga en cuenta que el uso de especificadores de systemd que hacen referencia a la unidad de servicio generada (por ejemplo, $N) rompe la capacidad de Quadlet para vincular entre recursos, ya que se traducen de manera diferente en cada servicio.

Unidades de contenedor [Container]

Las unidades de contenedor se nombran con la extensión .container y contienen una sección [Container] que describe el contenedor que se ejecuta como un servicio. El archivo de servicio resultante contiene una línea como ExecStart=podman run … image-name, y la mayoría de las claves de esta sección controlan las opciones de línea de comandos que se pasan a Podman. Sin embargo, algunas opciones también afectan los detalles de cómo systemd se configura para ejecutar e interactuar con el contenedor.

Por defecto, el contenedor de Podman tiene el mismo nombre que la unidad, pero con un prefijo systemd-, es decir, un archivo $name.container crea una unidad $name.service y un contenedor Podman systemd-$name. La opción ContainerName permite anular este nombre predeterminado con uno proporcionado por el usuario.

Solo hay una clave requerida, Image, que define la imagen del contenedor que ejecuta el servicio.

Descripción de la sección [Container]:

AddCapability=

Añade estas capacidades, además del conjunto de capacidades predeterminado de Podman, al contenedor.

Esta es una lista separada por espacios de capacidades. Esta clave puede aparecer varias veces.

Por ejemplo:

AddCapability=CAP_DAC_OVERRIDE CAP_IPC_OWNER

AddDevice=

Añade un nodo de dispositivo del host al contenedor. El formato es DISPOSITIVO_HOST[:DISPOSITIVO_CONTENEDOR][:PERMISOS], donde DISPOSITIVO_HOST es la ruta del nodo de dispositivo en el host, DISPOSITIVO_CONTENEDOR es la ruta del nodo de dispositivo en el contenedor, y PERMISOS es una lista de permisos que combinan 'r' para leer, 'w' para escribir y 'm' para mknod(2). El prefijo - indica a Quadlet que añada el dispositivo solo si existe en el host.

Esta clave puede aparecer varias veces.

AddHost=

Añade un mapeo host-a-IP a /etc/hosts. El formato es hostname:ip.

Equivalente a la opción --add-host de Podman. Esta clave puede aparecer varias veces.

Annotation=

Establece una o más anotaciones OCI en el contenedor. El formato es una lista de elementos clave=valor, similar a Environment.

Esta clave puede aparecer varias veces.

AutoUpdate=

Indica si el contenedor se actualizará automáticamente (podman-auto-update(1)). Se admiten los siguientes valores:

  • registry: Requiere una referencia de imagen completamente cualificada (por ejemplo, quay.io/podman/stable:latest) para crear el contenedor. Esta imposición es necesaria para saber qué imagen comprobar y descargar. Si se utilizó un ID de imagen, Podman no sabe qué imagen comprobar/descargar en ese momento.
  • local: Indica a Podman que compare la imagen que utiliza un contenedor con la imagen con su nombre en bruto en el almacenamiento local. Si una imagen se actualiza localmente, Podman simplemente reinicia la unidad systemd que ejecuta el contenedor.

CgroupsMode=

El modo cgroups del contenedor Podman. Equivalente a la opción --cgroups de Podman.

Por defecto, el modo cgroups del contenedor creado por Quadlet es split, lo que difiere del valor predeterminado (enabled) utilizado por la interfaz de línea de comandos de Podman.

Si el contenedor se une a un pod (es decir, si se especifica Pod=), es posible que desee cambiarlo a no-conmon o enabled para que los límites de recursos de cgroup a nivel de pod puedan surtir efecto.

ContainerName=

El nombre (opcional) del contenedor Podman. Si no se especifica, se utiliza el valor predeterminado de systemd-%N, que es el mismo que el nombre del servicio pero con un prefijo systemd- para evitar conflictos con contenedores gestionados por el usuario.

ContainersConfModule=

Carga el módulo containers.conf(5) especificado. Equivalente a la opción --module de Podman.

Esta clave puede aparecer varias veces.

DNS=

Establece el resolvedor/servidor de nombres DNS con ámbito de red para los contenedores de esta red.

Esta clave puede aparecer varias veces.

DNSOption=

Establece opciones DNS personalizadas.

Esta clave puede aparecer varias veces.

DNSSearch=

Establece dominios de búsqueda DNS personalizados. Utilice DNSSearch=. para eliminar el dominio de búsqueda.

Esta clave puede aparecer varias veces.

DropCapability=

Elimina estas capacidades del conjunto de capacidades predeterminado de podman, o all para eliminar todas las capacidades.

Esta es una lista separada por espacios de capacidades. Esta clave puede aparecer varias veces.

Por ejemplo:

DropCapability=CAP_DAC_OVERRIDE CAP_IPC_OWNER

Entrypoint=

Anula el ENTRYPOINT predeterminado de la imagen. Equivalente a la opción --entrypoint de Podman. Especifique comandos de varias opciones en forma de cadena JSON.

Environment=

Establece una variable de entorno en el contenedor. Utiliza el mismo formato que los servicios en systemd y puede aparecer varias veces.

EnvironmentFile=

Utiliza un archivo delimitado por líneas para establecer variables de entorno en el contenedor. La ruta puede ser absoluta o relativa a la ubicación del archivo de unidad. Esta clave puede utilizarse varias veces, y el orden se mantiene al pasarse a podman run.

EnvironmentHost=

Utiliza el entorno del host dentro del contenedor.

Exec=

Argumentos adicionales para el contenedor; esto tiene exactamente el mismo efecto que pasar más argumentos después de una invocación de podman run <image> <arguments>.

El formato es el mismo que para las líneas de comandos de systemd. Sin embargo, a diferencia del escenario de uso del verbo ExecStart= de systemd, que opera en el sistema de archivos raíz ambiental, es muy común que las imágenes de contenedor tengan sus propios metadatos ENTRYPOINT o CMD con los que esto interactúa.

La expectativa predeterminada para muchas imágenes es que la imagen incluya un ENTRYPOINT con un binario predeterminado, y este campo añadirá argumentos a ese punto de entrada.

Otra forma de describir esto es que funciona de la misma manera que el campo args en un pod de Kubernetes.

ExposeHostPort=

Expone un puerto, o un rango de puertos (por ejemplo, 50-59), desde el host al contenedor. Equivalente a la opción --expose de Podman.

Esta clave puede aparecer varias veces.

GIDMap=

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo GID proporcionado. Equivalente a la opción --gidmap de Podman.

Esta clave puede aparecer varias veces.

GlobalArgs=

Esta clave contiene una lista de argumentos que se pasan directamente entre podman y run en el archivo generado. Puede utilizarse para acceder a funciones de Podman no soportadas de otro modo por el generador. Dado que el generador desconoce las interacciones inesperadas que pueden causar estos argumentos, no se recomienda su uso.

El formato es una lista de argumentos separados por espacios, que opcionalmente pueden escaparse individualmente para permitir la inclusión de espacios en blanco y otros caracteres de control.

Esta clave puede aparecer varias veces.

Group=

El GID (numérico) con el que se ejecutará dentro del contenedor. No es necesario que coincida con el GID en el host, que se puede modificar con UserNS, pero si este no se especifica, este GID también se usa en el host.

Nota: cuando se especifican tanto User= como Group=, se combinan en un único argumento --user USUARIO:GRUPO que se pasa a Podman. El uso de Group= sin User= resultará en un error.

GroupAdd=

Asigna grupos adicionales al usuario principal que se ejecuta dentro del proceso del contenedor. También admite el indicador especial keep-groups. Equivalente a la opción --group-add de Podman.

HealthCmd=

Establece o modifica un comando de verificación de estado (healthcheck) para un contenedor. Un valor de none deshabilita los healthchecks existentes. Equivalente a la opción --health-cmd de Podman.

HealthInterval=

Establece un intervalo para los healthchecks. Un intervalo de disable no configura ningún temporizador automático. Equivalente a la opción --health-interval de Podman.

HealthLogDestination=

Establece el destino del registro del HealthCheck. Ruta de directorio, local o events_logger (uso local del archivo de estado del contenedor) (Predeterminado: local) Equivalente a la opción --health-log-destination de Podman.

  • local: (predeterminado) Los registros de HealthCheck se almacenan en contenedores overlay. (Por ejemplo: $runroot/healthcheck.log)
  • directory: crea un archivo de registro llamado <ID-del-contenedor>-healthcheck.log con los registros de HealthCheck en el directorio especificado.
  • events_logger: El registro se escribirá con el mecanismo de registro establecido por events_logger. También guarda el registro en un directorio predeterminado, para un rendimiento óptimo en sistemas con un gran número de registros.

HealthMaxLogCount=

Establece el número máximo de intentos en el archivo de registro del HealthCheck ('0' significa un número infinito de intentos en el archivo de registro) (Predeterminado: 5 intentos) Equivalente a la opción --Health-max-log-count de Podman.

HealthMaxLogSize=

Establece la longitud máxima en caracteres del registro de HealthCheck almacenado ("0" significa una longitud de registro infinita) (Predeterminado: 500 caracteres) Equivalente a la opción --Health-max-log-size de Podman.

HealthOnFailure=

Acción a tomar una vez que el contenedor transita a un estado no saludable. La acción "kill" se integra mejor con systemd. Una vez que el contenedor se vuelve no saludable, se elimina y systemd reinicia el servicio. Equivalente a la opción --health-on-failure de Podman.

HealthRetries=

El número de reintentos permitidos antes de que un healthcheck se considere no saludable. Equivalente a la opción --health-retries de Podman.

HealthStartPeriod=

El tiempo de inicialización necesario para que un contenedor se inicie. Equivalente a la opción --health-start-period de Podman.

HealthStartupCmd=

Establece un comando de healthcheck de inicio para un contenedor. Equivalente a la opción --health-startup-cmd de Podman.

HealthStartupInterval=

Establece un intervalo para el healthcheck de inicio. Un intervalo de disable no configura ningún temporizador automático. Equivalente a la opción --health-startup-interval de Podman.

HealthStartupRetries=

El número de intentos permitidos antes de que el healthcheck de inicio reinicie el contenedor. Equivalente a la opción --health-startup-retries de Podman.

HealthStartupSuccess=

El número de ejecuciones exitosas requeridas antes de que el healthcheck de inicio sea exitoso y comience el healthcheck regular. Equivalente a la opción --health-startup-success de Podman.

HealthStartupTimeout=

El tiempo máximo que tiene un comando de healthcheck de inicio para completarse antes de ser marcado como fallido. Equivalente a la opción --health-startup-timeout de Podman.

HealthTimeout=

El tiempo máximo permitido para completar el healthcheck antes de que un intervalo se considere fallido. Equivalente a la opción --health-timeout de Podman.

HostName=

Establece el nombre del host que está disponible dentro del contenedor. Equivalente a la opción --hostname de Podman.

HttpProxy=

Controla si las variables de entorno del proxy (http_proxy, https_proxy, ftp_proxy, no_proxy) se pasan desde el proceso Podman al contenedor durante las descargas y compilaciones de imágenes.

Establecer en true para habilitar la herencia del proxy (comportamiento predeterminado de Podman) o en false para deshabilitarlo. Esta opción es particularmente útil en sistemas que requieren configuración de proxy para el acceso a Internet pero no desean pasar la configuración del proxy al tiempo de ejecución del contenedor.

Equivalente a la opción --http-proxy de Podman.

Image=

La imagen a ejecutar en el contenedor. Se recomienda utilizar un nombre de imagen completamente calificado en lugar de un nombre corto, tanto por razones de rendimiento como de robustez.

El formato del nombre es el mismo que al pasarlo a podman pull. Por lo tanto, admite el uso de :tag o digests para garantizar la versión específica de la imagen.

Casos especiales:

  • Si el nombre de la imagen termina en .image, Quadlet usará la imagen descargada por el archivo .image correspondiente, y el servicio systemd generado contendrá una dependencia en el servicio $name-image.service (o el nombre del servicio establecido en el archivo .image). Tenga en cuenta que el archivo .image correspondiente debe existir.
  • Si el nombre de la imagen termina en .build, Quadlet usará la imagen compilada por el archivo .build correspondiente, y el servicio systemd generado contendrá una dependencia en el servicio $name-build.service. Nota: el archivo .build correspondiente debe existir.

IP=

Especifica una dirección IPv4 estática para el contenedor, por ejemplo 10.88.64.128. Equivalente a la opción --ip de Podman.

IP6=

Especifica una dirección IPv6 estática para el contenedor, por ejemplo fd46:db93:aa76:ac37::10. Equivalente a la opción --ip6 de Podman.

Label=

Establece una o más etiquetas OCI en el contenedor. El formato es una lista de elementos clave=valor, similar a Environment.

Esta clave se puede listar varias veces.

LogDriver=

Establece el controlador de registro (log-driver) utilizado por Podman al ejecutar el contenedor. Equivalente a la opción --log-driver de Podman.

LogOpt=

Establece las opciones de registro (log-opt) utilizadas por Podman al ejecutar el contenedor. Equivalente a la opción --log-opt de Podman. Esta clave se puede listar varias veces.

Mask=

Especifica las rutas a enmascarar separadas por dos puntos. Mask=/ruta/1:/ruta/2. Una ruta enmascarada no se puede acceder dentro del contenedor.

Memory=

Especifica la cantidad de memoria para el contenedor.

Mount=

Adjunta un montaje de sistema de archivos al contenedor. Esto es equivalente a la opción --mount de Podman, y generalmente tiene la forma type=TIPO,OPCIÓN-ESPECÍFICA-DEL-TIPO[,...].

Casos especiales:

  • Para type=volume, si source termina en .volume, se utiliza el volumen con nombre de Podman generado por el archivo .volume correspondiente.
  • Para type=image, si source termina en .image, se utiliza la imagen generada por el archivo .image correspondiente.

En ambos casos, el servicio systemd generado contendrá una dependencia en el servicio generado para la unidad correspondiente. Nota: el archivo .volume o .image correspondiente debe existir.

Esta clave se puede listar varias veces.

Network=

Especifica una red personalizada para el contenedor. Esto tiene el mismo formato que la opción --network de podman run. Por ejemplo, use host para usar la red del host en el contenedor, o none para no configurar la red en el contenedor.

Casos especiales:

  • Si el nombre de la red termina en .network, se utiliza una red de Podman llamada systemd-$name, y el servicio systemd generado contendrá una dependencia en el servicio $name-network.service. Dicha red puede ser creada automáticamente usando un archivo Quadlet $name.network. Nota: el archivo .network correspondiente debe existir.
  • Si el nombre termina en .container, el contenedor reutilizará la pila de red de otro contenedor creado por $name.container. El servicio systemd generado contendrá una dependencia en $name.service. Nota: el archivo .container correspondiente debe existir.

Esta clave se puede listar varias veces.

NetworkAlias=

Agrega un alias con ámbito de red para el contenedor. Esto tiene el mismo formato que la opción --network-alias de podman run. Los alias se pueden usar para agrupar contenedores en la resolución DNS: por ejemplo, establecer NetworkAlias=web en varios contenedores hará que una consulta DNS para web resuelva a todos los contenedores con ese alias.

Esta clave se puede listar varias veces.

NoNewPrivileges= (predeterminado: false)

Si está habilitado, esto deshabilita que los procesos del contenedor obtengan privilegios adicionales a través de cosas como setuid y capacidades de archivo.

Notify= (predeterminado: false)

Por defecto, Podman se ejecuta de tal manera que el comando de notificación de inicio de systemd es manejado por el tiempo de ejecución del contenedor. En otras palabras, el servicio se considera iniciado cuando el tiempo de ejecución del contenedor inicia el proceso hijo dentro del contenedor. Sin embargo, si la aplicación del contenedor soporta sd_notify,

Entonces establecer **Notify** en `true` pasa los detalles de notificación al contenedor permitiéndole notificar el inicio por sí mismo.

Además, establecer **Notify** en **healthy** pospondrá las notificaciones de inicio hasta que el contenedor se marque como saludable, según lo determinado por los healthchecks de Podman. Tenga en cuenta que esto requiere la configuración de un healthcheck de contenedor, consulte la opción **HealthCmd** para más información.

PidsLimit=

Ajusta el límite de PIDs del contenedor. Esto es equivalente a la opción --pids-limit de Podman.

Pod=

Especifica una unidad .pod de Quadlet a la que vincular el contenedor. El valor debe tener la forma <nombre>.pod y la unidad .pod debe existir.

Quadlet agregará todos los parámetros necesarios para vincular el contenedor y el pod, y sus servicios correspondientes.

PodmanArgs=

Esta clave contiene una lista de argumentos que se pasan directamente al final del comando podman run en el archivo generado (justo antes del nombre de la imagen en la línea de comandos). Se puede utilizar para acceder a funciones de Podman no soportadas de otra manera por el generador. Dado que el generador desconoce las interacciones inesperadas que pueden causar estos argumentos, no se recomienda el uso de esta opción.

El formato es una lista de argumentos separada por espacios, que opcionalmente pueden escaparse individualmente para permitir la inclusión de espacios en blanco y otros caracteres de control.

Esta clave se puede listar varias veces.

PublishPort=

Expone un puerto, o un rango de puertos (por ejemplo, 50-59), desde el contenedor al host. Equivalente a la opción --publish de Podman. El formato es similar a las opciones de Podman, que tiene la forma ip:hostPort:containerPort, ip::containerPort, hostPort:containerPort o containerPort, donde el número de puertos del host y del contenedor deben ser iguales (en el caso de un rango).

Si la IP se establece en 0.0.0.0 o no se establece en absoluto, el puerto se enlaza en todas las direcciones IPv4 del host; use [::] para IPv6.

Tenga en cuenta que no listar un puerto de host significa que Podman selecciona uno automáticamente, y puede ser diferente para cada invocación del servicio. Esto hace que sea una opción menos útil. El puerto asignado se puede encontrar con el comando podman port.

Esta clave se puede listar varias veces.

Pull=

Establece la política de extracción de imágenes. Esto es equivalente a la opción --pull de Podman

ReadOnly= (por defecto false)

Si se habilita, hace que la imagen sea de solo lectura.

ReadOnlyTmpfs= (por defecto true)

Si ReadOnly se establece en true, monta un tmpfs de lectura/escritura en /dev, /dev/shm, /run, /tmp y /var/tmp.

ReloadCmd=

Agrega una línea ExecReload al Service que ejecuta podman exec con este comando en este contenedor.

Para ejecutar la recarga, ejecute systemctl reload <Service>

Mutuamente excluyente con ReloadSignal

ReloadSignal=

Agrega una línea ExecReload al Service que ejecuta podman kill con esta señal, que envía la señal al proceso principal del contenedor.

Para ejecutar la recarga, ejecute systemctl reload <Service>

Mutuamente excluyente con ReloadCmd

Retry=

Número de veces que se reintentará la extracción de la imagen cuando ocurra un error HTTP. Equivalente a la opción --retry de Podman.

RetryDelay=

Retraso entre reintentos. Equivalente a la opción --retry-delay de Podman.

Rootfs=

El rootfs a utilizar para el contenedor. Rootfs apunta a un directorio en el sistema que contiene el contenido que se ejecutará dentro del contenedor. Esta opción entra en conflicto con la opción Image.

El formato del rootfs es el mismo que cuando se pasa a podman run --rootfs, por lo que también admite montajes overlay.

Nota: En sistemas SELinux, el rootfs necesita la etiqueta correcta, que por defecto es unconfined_u:object_r:container_file_t:s0.

RunInit= (por defecto false)

Si se habilita, el contenedor tendrá un proceso init mínimo dentro del contenedor que reenvía señales y recopila procesos.

SeccompProfile=

Establece el perfil seccomp a utilizar en el contenedor. Si no se establece, se utiliza el perfil predeterminado de podman. Establézcalo como la ruta de un archivo JSON, o como unconfined para deshabilitar los filtros seccomp.

Secret=

Utiliza un secreto de Podman en el contenedor, ya sea como un archivo o como una variable de entorno. Esto es equivalente a la opción --secret de Podman y generalmente tiene la forma secret[,opt=opt ...]

SecurityLabelDisable=

Desactiva la separación de etiquetas para el contenedor.

SecurityLabelFileType=

Establece el tipo de archivo de etiqueta para los archivos del contenedor.

SecurityLabelLevel=

Establece el nivel de proceso de etiqueta para los procesos del contenedor.

SecurityLabelNested=

Permite que las etiquetas de seguridad funcionen dentro del contenedor. Esto permite la separación de contenedores creados dentro del contenedor.

SecurityLabelType=

Establece el tipo de proceso de etiqueta para los procesos del contenedor.

ShmSize=

Tamaño de /dev/shm.

Esto es equivalente a la opción --shm-size de Podman y generalmente tiene la forma número[unidad]

StartWithPod=

Inicia el contenedor después de que se crea el pod asociado. Por defecto es true.

Si es true, el contenedor se iniciará/detendrá/reiniciará junto con el pod.

Si es false, el contenedor no se iniciará cuando se inicie el pod. El contenedor se detendrá con el pod. Reiniciar el pod también reiniciará el contenedor siempre que el contenedor también estuviera en ejecución anteriormente.

Tenga en cuenta que el contenedor aún se puede iniciar manualmente o a través de un objetivo configurando la sección [Install]. El pod se iniciará según sea necesario en cualquier caso.

StopSignal=

Señal para detener un contenedor. Por defecto es SIGTERM.

Esto es equivalente a la opción --stop-signal de Podman

StopTimeout=

Segundos de espera antes de detener forzosamente el contenedor.

Tenga en cuenta que este valor debe ser inferior al tiempo de espera real de la unidad systemd para asegurarse de que el comando podman rm no sea interrumpido por systemd.

Esto es equivalente a la opción --stop-timeout de Podman

SubGIDMap=

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo con el nombre en el archivo /etc/subgid. Equivalente a la opción --subgidname de Podman.

SubUIDMap=

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo con el nombre en el archivo /etc/subuid. Equivalente a la opción --subuidname de Podman.

Sysctl=

Configura parámetros del kernel en espacio de nombres para el contenedor. El formato es Sysctl=nombre=valor.

Esta es una lista de parámetros del kernel separada por espacios. Esta clave se puede listar varias veces.

Por ejemplo:

Sysctl=net.ipv6.conf.all.disable_ipv6=1 net.ipv6.conf.all.use_tempaddr=1

Timezone= (si no está establecido usa el predeterminado del sistema)

La zona horaria en la que se ejecutará el contenedor.

Tmpfs=

Monta un tmpfs en el contenedor. Esto es equivalente a la opción --tmpfs de Podman, y generalmente tiene la forma DIRECTORIO-CONTENEDOR[:OPCIONES].

Esta clave se puede listar varias veces.

UIDMap=

Ejecuta el contenedor en un nuevo espacio de nombres de usuario utilizando el mapeo UID proporcionado. Equivalente a la opción --uidmap de Podman.

Esta clave se puede listar varias veces.

Ulimit=

Opciones de Ulimit. Establece los valores de ulimits dentro del contenedor.

Esta clave se puede listar varias veces.

Unmask=

Especifica las rutas a desenmascarar separadas por dos puntos. unmask=ALL o /ruta/1:/ruta/2, o rutas expandidas por shell (/proc/*):

Si se establece en ALL, Podman desenmascarará todas las rutas que están enmascaradas o se hacen de solo lectura por defecto.

Las rutas enmascaradas por defecto son /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware y /sys/fs/selinux.

Las rutas por defecto que son de solo lectura son /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

User=

El UID (numérico) con el que ejecutar dentro del contenedor. No necesita coincidir con el UID en el host, que puede modificarse con UserNS, pero si este último no se especifica, este UID también se utiliza en el host.

Nota: cuando se especifican tanto User= como Group=, se combinan en un solo argumento --user USER:GROUP que se pasa a Podman.

UserNS=

Establece el modo de espacio de nombres de usuario para el contenedor. Esto es equivalente a la opción --userns de Podman y generalmente tiene la forma MODO[:OPCIONES,...].

Volume=

Monta un volumen en el contenedor. Esto es equivalente a la opción --volume de Podman, y generalmente tiene la forma [[VOLUMEN-ORIGEN|DIRECTORIO-HOST:]DIRECTORIO-CONTENEDOR[:OPCIONES]].

Si VOLUMEN-ORIGEN comienza con ., Quadlet resuelve la ruta en relación con la ubicación del archivo de unidad.

Caso especial:

•
Si VOLUMEN-ORIGEN termina con .volume, un volumen con nombre de Podman llamado systemd-$name se utiliza como fuente, y el servicio de systemd generado contiene una dependencia de $name-volume.service. Tenga en cuenta que el archivo .volume correspondiente debe existir.

Esta clave se puede listar varias veces.

WorkingDir=

Directorio de trabajo dentro del contenedor.

El directorio de trabajo predeterminado para ejecutar binarios dentro de un contenedor es el directorio raíz (/). El desarrollador de la imagen puede establecer un predeterminado diferente con la instrucción WORKDIR. Esta opción anula el directorio de trabajo utilizando la opción -w.

NOMBRE

quadlet - crear y gestionar contenedores y pods de systemd

SINOPSIS

Se utiliza mediante la creación de archivos de unidad de systemd con las extensiones de archivo `.container`, `.pod`, `.kube`, `.network`, `.volume`, `.build` y `.artifact`.

DESCRIPCIÓN

Quadlet es una herramienta que permite a los usuarios definir y gestionar contenedores y pods utilizando archivos de unidad de systemd. Estos archivos de unidad especifican la configuración del contenedor, el pod, la red, el volumen, la compilación, la imagen o el artefacto.

Los archivos de unidad de Quadlet siguen la estructura estándar de systemd con secciones y directivas específicas para la gestión de contenedores. Las siguientes secciones están disponibles:

Unidades de contenedores [Contenedor]

Define un contenedor individual.

[Container]
Image=nombre-de-la-imagen
# Otros parámetros de configuración del contenedor...

Unidades de pods [Pod]

Define un pod que puede contener uno o más contenedores.

[Pod]
PodName=nombre-del-pod
# Otros parámetros de configuración del pod...

Unidades de Kube [Kube]

Permite gestionar contenedores y pods basados en archivos YAML de Kubernetes.

[Kube]
Yaml=/ruta/a/tu/archivo.yaml

Unidades de red [Network]

Configura redes para contenedores.

[Network]
Subnet=172.16.0.0/24
Gateway=172.16.0.1

Unidades de volumen [Volume]

Define y gestiona volúmenes de almacenamiento.

[Volume]
Device=/ruta/del/dispositivo
Type=tipo-de-volumen

Unidades de compilación [Build]

Define cómo compilar una imagen de contenedor.

[Build]
ImageTag=nombre-de-la-imagen:etiqueta
# Otros parámetros de configuración de la compilación...

Unidades de imagen [Image]

Gestiona la adquisición de imágenes de contenedor.
