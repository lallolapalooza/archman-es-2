DESCRIPCIÓN

Formatos de archivos de imagen de disco

QEMU soporta muchos formatos de archivos de imagen que pueden ser usados con las máquinas virtuales, así como con cualquiera de las herramientas (como qemu-img). Esto incluye los formatos preferidos raw y qcow2, así como formatos que se soportan por compatibilidad con versiones antiguas de QEMU u otros hipervisores.

Dependiendo del formato de la imagen, se pueden pasar diferentes opciones a qemu-img create y qemu-img convert usando la opción -o. Esta sección describe cada formato y las opciones que se soportan para él.

raw
Formato de imagen de disco en bruto. Este formato tiene la ventaja de ser simple y fácilmente exportable a todos los demás emuladores. Si tu sistema de archivos soporta holes (agujeros, por ejemplo en ext2 o ext3 en Linux o NTFS en Windows), entonces solo los sectores escritos reservarán espacio. Usa qemu-img info para conocer el tamaño real utilizado por la imagen o ls -ls en Unix/Linux.

Opciones soportadas:

preallocation
Modo de preasignación (valores permitidos: off, falloc, full). El modo falloc preasigna espacio para la imagen llamando a posix_fallocate(). El modo full preasigna espacio para la imagen escribiendo datos en el almacenamiento subyacente. Estos datos pueden ser cero o no, dependiendo de la ubicación del almacenamiento.
qcow2
Formato de imagen de QEMU, el formato más versátil. Úsalo para tener imágenes más pequeñas (útil si tu sistema de archivos no soporta agujeros, por ejemplo en Windows), compresión basada en zlib y soporte para múltiples instantáneas de VM.

Opciones soportadas:

compat
Determina la versión de qcow2 a usar. compat=0.10 usa el formato de imagen tradicional que puede ser leído por cualquier QEMU desde 0.10. compat=1.1 habilita extensiones del formato de imagen que solo QEMU 1.1 y posteriores entienden (este es el valor por defecto). Entre otras cosas, esto incluye clústeres de ceros, que permiten una copia eficiente sobre la lectura para imágenes dispersas.
backing_file
Nombre del archivo de una imagen base (ver subcomando create)
backing_fmt
Formato de imagen de la imagen base
encryption
Esta opción está obsoleta y es equivalente a encrypt.format=aes
encrypt.format
Si se establece en luks, solicita que la carga útil de qcow2 (no la cabecera de qcow2) se cifre utilizando el formato LUKS. La frase de contraseña a utilizar para desbloquear la ranura de clave LUKS se proporciona mediante el parámetro encrypt.key-secret. Los parámetros de cifrado LUKS se pueden ajustar con los otros parámetros encrypt.*.

Si se establece en aes, la imagen se cifra con AES-CBC de 128 bits. La clave de cifrado se proporciona mediante el parámetro encrypt.key-secret. Este formato de cifrado se considera defectuoso según los estándares criptográficos modernos, ya que sufre una serie de problemas de diseño:

  • El cifrado AES-CBC se utiliza con vectores de inicialización predecibles basados en el número de sector. Esto lo hace vulnerable a ataques de texto plano elegido que pueden revelar la existencia de datos cifrados.
  • La frase de contraseña del usuario se utiliza directamente como clave de cifrado. Una frase de contraseña mal elegida o corta comprometerá la seguridad del cifrado.
  • En caso de que la frase de contraseña se vea comprometida, no hay forma de cambiar la frase de contraseña para proteger los datos en ninguna imagen qcow. Los archivos deben ser clonados, utilizando una frase de contraseña de cifrado diferente en el archivo nuevo. Luego, el archivo original debe borrarse de forma segura utilizando un programa como shred, aunque incluso esto es ineficaz con muchas tecnologías de almacenamiento modernas.

El uso de esto ya no está soportado en los emuladores de sistema. El soporte solo permanece en las utilidades de línea de comandos, con el fin de liberar datos e interoperabilidad con versiones antiguas de QEMU. Se debe usar el formato luks en su lugar.

encrypt.key-secret
Proporciona el ID de un objeto secret que contiene la frase de contraseña (encrypt.format=luks) o la clave de cifrado (encrypt.format=aes).
encrypt.cipher-alg
Nombre del algoritmo de cifrado y longitud de clave. Actualmente por defecto es aes-256. Solo se usa cuando encrypt.format=luks.
encrypt.cipher-mode
Nombre del modo de cifrado a usar. Actualmente por defecto es xts. Solo se usa cuando encrypt.format=luks.
encrypt.ivgen-alg
Nombre del algoritmo generador de vector de inicialización. Actualmente por defecto es plain64. Solo se usa cuando encrypt.format=luks.
encrypt.ivgen-hash-alg
Nombre del algoritmo hash a usar con el generador de vector de inicialización (si es necesario). Por defecto es sha256. Solo se usa cuando encrypt.format=luks.
encrypt.hash-alg
Nombre del algoritmo hash a usar para el algoritmo PBKDF. Por defecto es sha256. Solo se usa cuando encrypt.format=luks.
encrypt.iter-time
Cantidad de tiempo, en milisegundos, a usar para el algoritmo PBKDF por ranura de clave. Por defecto es 2000. Solo se usa cuando encrypt.format=luks.
cluster_size
Cambia el tamaño del clúster de qcow2 (debe estar entre 512 bytes y 2M). Tamaños de clúster más pequeños pueden mejorar el tamaño del archivo de imagen, mientras que tamaños de clúster más grandes generalmente proporcionan un mejor rendimiento.
preallocation
Modo de preasignación (valores permitidos: off, metadata, falloc, full). Una imagen con metadatos preasignados es inicialmente más grande, pero puede mejorar el rendimiento cuando la imagen necesita crecer. Las preasignaciones falloc y full son como las mismas opciones del formato raw, pero también configuran los metadatos.
lazy_refcounts
Si esta opción está establecida en on, las actualizaciones del contador de referencias se posponen con el objetivo de evitar E/S de metadatos y mejorar el rendimiento. Esto es particularmente interesante con cache=writethrough, que no agrupa las actualizaciones de metadatos. La contrapartida es que después de un fallo del host, las tablas del contador de referencias deben reconstruirse, es decir, en la próxima apertura se requiere una comprobación (automática) de qemu-img check -r all, lo que puede llevar algún tiempo.

Esta opción solo se puede habilitar si se especifica compat=1.1.

nocow
Si esta opción está establecida en on, deshabilitará la COW del archivo. Solo es válida en btrfs, sin efecto en otros sistemas de archivos.

Btrfs

Options

The following options are supported for the qemu-img command:

nocow
For Btrfs file system, it is observed that qemu-img has low performance when hosting a VM image file, even more when the guest on the VM also using btrfs as file system. Turning off COW is a way to mitigate this bad performance. Generally there are two ways to turn off COW on btrfs:

  • Disable it by mounting with nodatacow, then all newly created files will be NOCOW.
  • For an empty file, add the NOCOW file attribute. That's what this option does.

Note: this option is only valid to new or empty files. If there is an existing file which is COW and has data blocks already, it couldn't be changed to NOCOW by setting nocow=on. One can issue lsattr filename to check if the NOCOW flag is set or not (Capital 'C' is NOCOW flag).

qed
Old QEMU image format with support for backing files and compact image files (when your filesystem or transport medium does not support holes).

When converting QED images to qcow2, you might want to consider using the lazy_refcounts=on option to get a more QED-like behaviour.

Supported options:

backing_file
File name of a base image (see create subcommand).
backing_fmt
Image file format of backing file (optional). Useful if the format cannot be autodetected because it has no header, like some vhd/vpc files.
cluster_size
Changes the cluster size (must be power-of-2 between 4K and 64K). Smaller cluster sizes can improve the image file size whereas larger cluster sizes generally provide better performance.
table_size
Changes the number of clusters per L1/L2 table (must be power-of-2 between 1 and 16). There is normally no need to change this value but this option can between used for performance benchmarking.
qcow
Old QEMU image format with support for backing files, compact image files, encryption and compression.

Supported options:

backing_file
File name of a base image (see create subcommand)
encryption
This option is deprecated and equivalent to encrypt.format=aes
encrypt.format
If this is set to aes, the image is encrypted with 128-bit AES-CBC. The encryption key is given by the encrypt.key-secret parameter. This encryption format is considered to be flawed by modern cryptography standards, suffering from a number of design problems enumerated previously against the qcow2 image format.

The use of this is no longer supported in system emulators. Support only remains in the command line utilities, for the purposes of data liberation and interoperability with old versions of QEMU.

Users requiring native encryption should use the qcow2 format instead with encrypt.format=luks.

encrypt.key-secret
Provides the ID of a secret object that contains the encryption key (encrypt.format=aes).
luks
LUKS v1 encryption format, compatible with Linux dm-crypt/cryptsetup

Supported options:

key-secret
Provides the ID of a secret object that contains the passphrase.
cipher-alg
Name of the cipher algorithm and key length. Currently defaults to aes-256.
cipher-mode
Name of the encryption mode to use. Currently defaults to xts.
ivgen-alg
Name of the initialization vector generator algorithm. Currently defaults to plain64.
ivgen-hash-alg
Name of the hash algorithm to use with the initialization vector generator (if required). Defaults to sha256.
hash-alg
Name of the hash algorithm to use for PBKDF algorithm Defaults to sha256.
iter-time
Amount of time, in milliseconds, to use for PBKDF algorithm per key slot. Defaults to 2000.
vdi
VirtualBox 1.1 compatible image format.

Supported options:

static
If this option is set to on, the image is created with metadata preallocation.
vmdk
VMware 3 and 4 compatible image format.

Supported options:

backing_file
File name of a base image (see create subcommand).
compat6
Create a VMDK version 6 image (instead of version 4)
hwversion
Specify vmdk virtual hardware version. Compat6 flag cannot be enabled if hwversion is specified.
subformat
Specifies which VMDK subformat to use. Valid options are monolithicSparse (default), monolithicFlat, twoGbMaxExtentSparse, twoGbMaxExtentFlat and streamOptimized.
vpc
VirtualPC compatible image format (VHD).

Supported options:

subformat
Specifies which VHD subformat to use. Valid options are dynamic (default) and fixed.
VHDX
Hyper-V compatible image format (VHDX).

Supported options:

subformat
Specifies which VHDX subformat to use. Valid options are dynamic (default) and fixed.
block_state_zero
Force use of payload blocks of type 'ZERO'. Can be set to on (default) or off. When set to off, new blocks will be created as PAYLOAD_BLOCK_NOT_PRESENT, which means parsers are free to return arbitrary data for those blocks. Do not set to off when using qemu-img convert with subformat=dynamic.
block_size
Block size; min 1 MB, max 256 MB. 0 means auto-calculate based on image size.
log_size
Log size; min 1 MB.

Imágenes de disco FAT virtuales

QEMU puede crear automáticamente una imagen de disco FAT virtual a partir de una estructura de directorios. Para usarla, simplemente escribe:

qemu-system-x86_64 linux.img -hdb fat:/my_directory

Luego, puedes acceder a todos los archivos del directorio /my_directory sin tener que copiarlos en una imagen de disco o exportarlos a través de SAMBA o NFS. El acceso predeterminado es de solo lectura.

Los disquetes se pueden emular con la opción :floppy::

qemu-system-x86_64 linux.img -fda fat:floppy:/my_directory

Hay disponible soporte de lectura/escritura para pruebas (etapa beta) con la opción :rw::

qemu-system-x86_64 linux.img -fda fat:floppy:rw:/my_directory

Lo que nunca debes hacer:

  • usar nombres de archivo que no sean ASCII
  • usar "-snapshot" junto con ":rw:"
  • esperar que funcione al cargar una máquina virtual
  • escribir en el directorio FAT en el sistema host mientras se accede a él con el sistema invitado

Acceso NBD

QEMU puede acceder directamente a dispositivos de bloque exportados utilizando el protocolo Network Block Device.

qemu-system-x86_64 linux.img -hdb nbd://my_nbd_server.mydomain.org:1024/

Si el servidor NBD se encuentra en el mismo host, puedes usar un socket unix en lugar de un socket inet:

qemu-system-x86_64 linux.img -hdb nbd+unix://?socket=/tmp/my_socket

En este caso, el dispositivo de bloque debe ser exportado usando qemu-nbd:

qemu-nbd --socket=/tmp/my_socket my_disk.qcow2

El uso de qemu-nbd permite compartir un disco entre varios invitados:

qemu-nbd --socket=/tmp/my_socket --share=2 my_disk.qcow2

y luego puedes usarlo con dos invitados:

qemu-system-x86_64 linux1.img -hdb nbd+unix://?socket=/tmp/my_socket
qemu-system-x86_64 linux2.img -hdb nbd+unix://?socket=/tmp/my_socket

Si el nbd-server utiliza exportaciones nombradas (soportado desde NBD 2.9.18, o con el servidor NBD incrustado de QEMU), debes especificar un nombre de exportación en la URI:

qemu-system-x86_64 -cdrom nbd://localhost/debian-500-ppc-netinst
qemu-system-x86_64 -cdrom nbd://localhost/openSUSE-11.1-ppc-netinst

La sintaxis de URI para NBD es compatible desde QEMU 1.3. También hay disponible una sintaxis alternativa. Aquí hay algunos ejemplos de la sintaxis anterior:

qemu-system-x86_64 linux.img -hdb nbd:my_nbd_server.mydomain.org:1024
qemu-system-x86_64 linux2.img -hdb nbd:unix:/tmp/my_socket
qemu-system-x86_64 -cdrom nbd:localhost:10809:exportname=debian-500-ppc-netinst

LUNs iSCSI

iSCSI es un protocolo popular utilizado para acceder a dispositivos SCSI a través de una red informática.

Hay dos formas diferentes en que los dispositivos iSCSI pueden ser utilizados por QEMU.

El primer método es montar el LUN iSCSI en el host y hacer que aparezca como cualquier otro dispositivo SCSI ordinario en el host y luego acceder a este dispositivo como un dispositivo /dev/sd desde QEMU. Cómo hacer esto varía entre los sistemas operativos host.

El segundo método implica el uso del iniciador iSCSI incorporado en QEMU. Esto proporciona un mecanismo que funciona de la misma manera independientemente del sistema operativo host en el que se esté ejecutando QEMU. Esta sección describirá este segundo método de uso de iSCSI junto con QEMU.

En QEMU, los dispositivos iSCSI se describen utilizando URL iSCSI especiales. Sintaxis de URL:

iscsi://[<username>[%<password>]@]<host>[:<port>]/<nombre-iqn-objetivo>/<lun>

Nombre de usuario y contraseña son opcionales y solo se utilizan si tu objetivo está configurado usando autenticación CHAP para control de acceso. Alternativamente, el nombre de usuario y la contraseña también se pueden establecer a través de variables de entorno para que no aparezcan en la lista de procesos:

export LIBISCSI_CHAP_USERNAME=<nombre de usuario>
export LIBISCSI_CHAP_PASSWORD=<contraseña>
iscsi://<host>/<nombre-iqn-objetivo>/<lun>

Varios parámetros relacionados con la sesión se pueden establecer a través de opciones especiales, ya sea en un archivo de configuración proporcionado a través de '-readconfig' o directamente en la línea de comandos.

Si no se especifica el nombre del iniciador, qemu usará un nombre predeterminado de 'iqn.2008-11.org.linux-kvm[:<uuid>'] donde <uuid> es el UUID de la máquina virtual. Si no se especifica el UUID, qemu usará 'iqn.2008-11.org.linux-kvm[:<nombre>'] donde <nombre> es el nombre de la máquina virtual.

Establecer un nombre de iniciador específico para usar al iniciar sesión en el objetivo:

-iscsi initiator-name=iqn.qemu.test:my-initiator

Controlar qué tipo de digest de encabezado negociar con el objetivo:

-iscsi header-digest=CRC32C|CRC32C-NONE|NONE-CRC32C|NONE

Estos también se pueden establecer a través de un archivo de configuración:

[iscsi]
  user = "nombre de usuario CHAP"
  password = "contraseña CHAP"
  initiator-name = "iqn.qemu.test:my-initiator"
  # el digest de encabezado es uno de CRC32C|CRC32C-NONE|NONE-CRC32C|NONE
  header-digest = "CRC32C"

Establecer el nombre del objetivo permite diferentes opciones para diferentes objetivos:

[iscsi "iqn.target.name"]
  user = "nombre de usuario CHAP"
  password = "contraseña CHAP"
  initiator-name = "iqn.qemu.test:my-initiator"
  # el digest de encabezado es uno de CRC32C|CRC32C-NONE|NONE-CRC32C|NONE
  header-digest = "CRC32C"

Cómo usar un archivo de configuración para establecer opciones de configuración iSCSI:

cat >iscsi.conf <<EOF
[iscsi]
  user = "yo"
  password = "mi contraseña"
  initiator-name = "iqn.qemu.test:my-initiator"
  header-digest = "CRC32C"
EOF
qemu-system-x86_64 -drive file=iscsi://127.0.0.1/iqn.qemu.test/1 \
  -readconfig iscsi.conf

Cómo configurar un objetivo iSCSI simple en loopback y acceder a él a través de QEMU: este ejemplo muestra cómo configurar un objetivo iSCSI con un CDROM y un DISCO usando el objetivo de software STGT de Linux. Este objetivo está disponible en sistemas basados en Red Hat como el paquete 'scsi-target-utils'.

tgtd --iscsi portal=127.0.0.1:3260
tgtadm --lld iscsi --op new --mode target --tid 1 -T iqn.qemu.test
tgtadm --lld iscsi --mode logicalunit --op new --tid 1 --lun 1 \
    -b /IMAGES/disk.img --device-type=disk
tgtadm --lld iscsi --mode logicalunit --op new --tid 1 --lun 2 \
    -b /IMAGES/cd.iso --device-type=cd
tgtadm --lld iscsi --op bind --mode target --tid 1 -I ALL
qemu-system-x86_64 -iscsi initiator-name=iqn.qemu.test:my-initiator \
  -boot d -drive file=iscsi://127.0.0.1/iqn.qemu.test/1 \
  -cdrom iscsi://127.0.0.1/iqn.qemu.test/2

Imágenes de disco GlusterFS

GlusterFS es un sistema de archivos distribuido en el espacio de usuario.

NAME

    
qemu-block-drivers - QEMU block drivers





    
SYNOPSIS

    
This page describes the various block drivers available in QEMU.





    
DESCRIPTION

    
Block drivers are plugins that QEMU uses to access storage devices. They
        can be combined to create complex storage setups. For example, the
        qemu-img command can be used to create and manage disk
        images, and it supports many of the same drivers.

    
The block driver layer is structured as a tree. A root node represents the
        actual storage (e.g., a raw file or a block device), and subsequent nodes
        represent transformations applied to the data. Each node has a driver and
        a set of options.

    

        
Driver options

        
Options are passed to drivers using the driver=...,
            file.driver=..., file.filename=...,
            and so on. The specific options depend on the driver.

        
Some options are common to all drivers, such as:

        

            
file.locking

            
Controls whether file locking is enabled. This is important for
                preventing multiple QEMU instances from corrupting the same disk
                image. The option is usually in the form of "file.locking=off"
                as the protocol driver is normally placed as a "file" child
                under a format driver. For example:

            

                

                    
-blockdev driver=qcow2,file.filename=/path/to/image,file.locking=off,file.driver=file

                

            

            
To check if image locking is active, check the output of the
                "lslocks" command on host and see if there are locks held by the
                QEMU process on the image file. More than one byte could be locked by the
                QEMU instance, each byte of which reflects a particular permission that is
                acquired or protected by the running block driver.

        

    

    

        
Filter drivers

        
QEMU supports several filter drivers, which don't store any data,
            but perform some additional tasks, hooking io requests.

        

            

                
preallocate

                
The preallocate filter driver is intended to be inserted between format
                    and protocol nodes and preallocates some additional space (expanding the
                    protocol file) when writing past the file’s end. This can be useful
                    for file-systems with slow allocation.
                    
Supported options:

                

            

            

                

                    
prealloc-align

                    
On preallocation, align the file length to this value (in bytes), default
                        1M.

                

            

            

                

                    
prealloc-size

                    
How much to preallocate (in bytes), default 128M.
