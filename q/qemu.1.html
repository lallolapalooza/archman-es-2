NOMBRE

qemu - Documentación para el usuario de QEMU

SINOPSIS

qemu-system-x86_64 [opciones] [imagen_disco]

DESCRIPCIÓN

El emulador de sistema PC de QEMU simula los siguientes periféricos:

  • Puente PCI i440FX del anfitrión y puente PCI a ISA PIIX3
  • Tarjeta VGA PCI Cirrus CLGD 5446 o tarjeta VGA dummy con extensiones Bochs VESA (nivel de hardware, incluyendo todos los modos no estándar).
  • Ratón y teclado PS/2
  • 2 interfaces IDE PCI con soporte para disco duro y CD-ROM
  • Disquete
  • Adaptadores de red PCI e ISA
  • Puertos serie
  • BMC IPMI, ya sea uno interno o externo
  • Tarjeta de sonido Creative SoundBlaster 16
  • Tarjeta de sonido ENSONIQ AudioPCI ES1370
  • Tarjeta de sonido compatible con Intel 82801AA AC97 Audio
  • Controlador Intel HD Audio y códec HDA
  • Adlib (OPL2) - chip compatible con Yamaha YM3812
  • Tarjeta de sonido Gravis Ultrasound GF1
  • Tarjeta de sonido compatible con CS4231A
  • Altavoz de PC
  • Controlador USB PCI UHCI, OHCI, EHCI o XHCI y un concentrador USB 1.1 virtual.

SMP se soporta con un gran número de CPUs virtuales (el límite superior depende de la configuración).

QEMU usa la BIOS de PC del proyecto Seabios y la BIOS VGA de Plex86/Bochs LGPL.

QEMU usa emulación YM3812 de Tatsuyuki Satoh.

QEMU usa emulación GUS (GUSEMU32 http://www.deinmeister.de/gusemu/) de Tibor "TS" Schütz.

Nota que, por defecto, GUS comparte IRQ(7) con los puertos paralelos y por lo tanto QEMU debe indicarse que no tenga puertos paralelos para que GUS funcione.

qemu-system-x86_64 dos.img -device gus -parallel none

Alternativamente:

qemu-system-x86_64 dos.img -device gus,irq=5

O alguna otra IRQ no reclamada.

CS4231A es el chip utilizado en los productos Windows Sound System y GUSMAX

El dispositivo de audio del altavoz de PC se puede configurar usando la propiedad de la máquina pcspk-audiodev, es decir:

qemu-system-x86_64 some.img -audiodev <backend>,id=<nombre> -machine pcspk-audiodev=<nombre>

Opciones específicas de la máquina

Soporta las siguientes opciones específicas de la máquina:

•
x-south-bridge=PIIX3|piix4-isa (Opción experimental para seleccionar un puente sur particular. Por defecto: PIIX3)

OPCIONES

imagen_disco es una imagen de disco duro sin formato para el disco duro IDE 0. Algunos objetivos no necesitan una imagen de disco.

Al tratar con parámetros de opciones como cadenas arbitrarias que contienen comas, como en "file=my,file" y "string=a,b", es necesario duplicar las comas. Por ejemplo,"-fw_cfg name=z,string=a,,b" se analizará como "-fw_cfg name=z,string=a,b".

Opciones estándar

-h
Muestra la ayuda y sale
-version
Muestra información de la versión y sale
-machine [type=]nombre[,prop=valor[,...]]
Selecciona la máquina emulada por nombre. Usa -machine help para listar las máquinas disponibles.

Para arquitecturas que buscan soportar compatibilidad con migración en vivo entre versiones, cada versión introducirá un nuevo tipo de máquina con versión. Por ejemplo, la versión 2.8.0 introdujo los tipos de máquina "pc-i440fx-2.8" y "pc-q35-2.8" para las arquitecturas x86_64/i686.

Para permitir la migración en vivo de invitados desde la versión 2.8.0 de QEMU a la versión 2.9.0 de QEMU, la versión 2.9.0 también debe soportar las máquinas "pc-i440fx-2.8" y "pc-q35-2.8". Para permitir a los usuarios migrar en vivo VMs y saltarse múltiples versiones intermedias al actualizar, las nuevas versiones de QEMU soportarán tipos de máquina de muchas versiones anteriores.

Las propiedades de máquina soportadas son:

accel=accels1[:accels2[:...]]
Se utiliza para habilitar un acelerador. Dependiendo de la arquitectura del objetivo, kvm, xen, hvf, nvmm, whpx o tcg pueden estar disponibles. Por defecto, se utiliza tcg. Si se especifica más de un acelerador, se utiliza el siguiente si el anterior falla al inicializarse.
vmport=on|off|auto
Habilita la emulación del puerto IO de VMWare, para vmmouse, etc. auto indica seleccionar el valor basado en accel e i8042. Para accel=xen o i8042=off el valor predeterminado es off, de lo contrario, el valor predeterminado es on.
dump-guest-core=on|off
Incluye la memoria del invitado en un volcado de núcleo. El valor predeterminado es on.
mem-merge=on|off
Habilita o deshabilita el soporte de fusión de memoria. Esta característica, cuando es soportada por el anfitrión, elimina duplicados de páginas de memoria idénticas entre instancias de VMs (habilitado por defecto).
aes-key-wrap=on|off
Habilita o deshabilita el soporte de envoltura de claves AES en anfitriones s390-ccw. Esta característica controla si se crearán claves de envoltura AES para permitir la ejecución de funciones criptográficas AES. El valor predeterminado es on.
dea-key-wrap=on|off
Habilita o deshabilita el soporte de envoltura de claves DEA en anfitriones s390-ccw. Esta característica controla si se crearán claves de envoltura DEA para permitir la ejecución de funciones criptográficas DEA. El valor predeterminado es on.
nvdimm=on|off
Habilita o deshabilita el soporte NVDIMM. El valor predeterminado es off.
memory-encryption=
Objeto de cifrado de memoria a utilizar. El valor predeterminado es none.
hmat=on|off
Habilita o deshabilita el soporte de la Tabla de Atributos de Memoria Heterogénea (HMAT) de ACPI. El valor predeterminado es off.
spcr=on|off
Habilita o deshabilita el soporte de la Tabla de Redirección de Consola Serie (SPCR) de ACPI. El valor predeterminado es on.
aux-ram-share=on|off
Asigna memoria RAM auxiliar del invitado como un archivo anónimo que se puede compartir con un proceso externo. Esta opción se aplica a la memoria asignada como efecto secundario de la creación de varios dispositivos. No se aplica a objetos memory-backend, ya sea especificados explícitamente en la línea de comandos, o creados implícitamente por la opción de línea de comandos -m. El valor predeterminado es off.

Para usar el modo de migración cpr-transfer, debes establecer aux-ram-share=on.

memory-backend='id'
Una alternativa a las opciones heredadas -mem-path y mem-prealloc. Permite usar un backend de memoria como RAM principal.

Por ejemplo:

-object memory-backend-file,id=pc.ram,size=512M,mem-path=/hugetlbfs,prealloc=on,share=on
-machine memory-backend=pc.ram
-m 512M

Nota de compatibilidad de migración:

  • como id de backend se debe usar el valor de 'default-ram-id', anunciado por el tipo de máquina (disponible a través del comando QMP query-machines), si se espera migración hacia/desde QEMU antiguo (<5.0).
  • para tipos de máquina 4.0 y anteriores, el usuario debe usar la opción de backend x-use-canonical-path-for-ramblock-id=off si se espera migración hacia/desde QEMU antiguo (<5.0).

Por ejemplo:

-object memory-backend-ram,id=pc.ram,size=512M,x-use-canonical-path-for-ramblock-id=off
-machine memory-backend=pc.ram
-m 512M

-numa nodo[,memdev=id][,cpus=primeracpu[-ultimacpu]][,nodeid=nodo][,initiator=iniciador]
-numa dist,src=origen,dst=destino,val=distancia
-numa cpu,node-id=nodo[,socket-id=x][,core-id=y][,thread-id=z]
-numa hmat-lb,initiator=nodo,target=nodo,hierarchy=jerarquía,data-type=tipo[,latency=lat][,bandwidth=bw]
-numa hmat-cache,node-id=nodo,size=tamaño,level=nivel[,associativity=str][,policy=str][,line=tamaño]
Define un nodo NUMA y le asigna RAM y VCPUs. Establece la distancia NUMA desde un nodo de origen a un nodo de destino. Establece los atributos de memoria heterogénea de ACPI para los nodos dados.

La asignación heredada de VCPU utiliza la opción 'cpus' donde primeracpu y ultimacpu son índices de CPU. Cada opción 'cpus' representa un rango contiguo de índices de CPU (o una única VCPU si se omite ultimacpu). Un conjunto no contiguo de VCPUs se puede representar proporcionando múltiples opciones 'cpus'. Si se omite 'cpus' en todos los nodos, las VCPUs se dividen automáticamente entre ellos.

Por ejemplo, la siguiente opción asigna las VCPUs 0, 1, 2 y 5 a un nodo NUMA:

-numa nodo,cpus=0-2,cpus=5

La opción 'cpu' es una alternativa nueva a la opción 'cpus' que utiliza las propiedades 'socket-id|core-id|thread-id' para asignar objetos de CPU a un nodo utilizando las propiedades de diseño de topología de la CPU. El conjunto de propiedades es específico de la máquina y depende del tipo de máquina utilizado y de las opciones 'smp'. Se puede consultar con el comando del monitor 'hotpluggable-cpus'. La propiedad 'node-id' especifica el nodo al que se asignará el objeto de CPU; es necesario que el nodo se declare con la opción 'node' antes de que se utilice con la opción 'cpu'.

Por ejemplo:

-M pc \
-smp 1,sockets=2,maxcpus=2 \
-numa node,nodeid=0 -numa node,nodeid=1 \
-numa cpu,node-id=0,socket-id=0 -numa cpu,node-id=1,socket-id=1

La opción 'memdev' asigna RAM de un dispositivo backend de memoria dado a un nodo. Se recomienda utilizar la opción 'memdev' en lugar de la opción heredada 'mem'. Esto se debe a que la opción 'memdev' proporciona un mejor rendimiento y un mayor control sobre la RAM del backend (por ejemplo, el parámetro 'prealloc' de '-memory-backend-ram' permite la preasignación de memoria).

Por motivos de compatibilidad, la opción heredada 'mem' es compatible con los tipos de máquina 5.0 y anteriores. Tenga en cuenta que 'mem' y 'memdev' son mutuamente excluyentes. Si un nodo utiliza 'memdev', los nodos restantes deben utilizar la opción 'memdev', y viceversa.

Los usuarios deben especificar la memoria para todos los nodos NUMA mediante 'memdev' (o 'mem' heredado si está disponible). En QEMU 5.2, se eliminó la compatibilidad con '-numa node' sin memoria especificada.

'initiator' es una opción adicional que apunta a un nodo NUMA iniciador que tiene el mejor rendimiento (la menor latencia o el mayor ancho de banda) para este nodo NUMA. Tenga en cuenta que esta opción solo se puede establecer cuando la propiedad de la máquina 'hmat' está configurada en 'on'.

El siguiente ejemplo crea una máquina con 2 nodos NUMA, el nodo 0 tiene CPU. el nodo 1 solo tiene memoria, y su iniciador es el nodo 0. Tenga en cuenta que, dado que el nodo 0 tiene CPU, por defecto el iniciador del nodo 0 es él mismo y debe ser él mismo.

-machine hmat=on \
-m 2G,slots=2,maxmem=4G \
-object memory-backend-ram,size=1G,id=m0 \
-object memory-backend-ram,size=1G,id=m1 \
-numa node,nodeid=0,memdev=m0 \
-numa node,nodeid=1,memdev=m1,initiator=0 \
-smp 2,sockets=2,maxcpus=2  \
-numa cpu,node-id=0,socket-id=0 \
-numa cpu,node-id=0,socket-id=1

origen y destino son IDs de nodo NUMA. distancia es la distancia NUMA desde el origen hasta el destino. La distancia de un nodo a sí mismo es siempre 10. Si a algún par de nodos se le asigna una distancia, entonces se deben asignar distancias a todos los pares. Sin embargo, cuando las distancias se dan solo en una dirección para cada par de nodos, se asume que las distancias en las direcciones opuestas son las mismas. Si, sin embargo, se asigna un par de distancias asimétricas a incluso un par de nodos, entonces se deben proporcionar valores de distancia para ambas direcciones para todos los pares de nodos, incluso cuando son simétricos. Cuando un nodo es inalcanzable desde otro nodo, establezca la distancia del par en 255.

Tenga en cuenta que la opción -numa no asigna ninguno de los recursos especificados, solo asigna recursos existentes a nodos NUMA. Esto significa que todavía se tiene que usar las opciones -m, -smp para asignar RAM y VCPUs respectivamente.

Utilice 'hmat-lb' para establecer la Información de Latencia y Ancho de Banda de Localidad del Sistema entre los nodos NUMA iniciador y destino en la Tabla de Atributos de Memoria Heterogénea de ACPI (HMAT). El nodo NUMA iniciador puede crear solicitudes de memoria, generalmente tiene uno o más procesadores. El nodo NUMA destino contiene memoria direccionable.

En la opción 'hmat-lb', nodo son IDs de nodo NUMA. jerarquía es la jerarquía de memoria del nodo NUMA destino: si la jerarquía es 'memory', la estructura representa el rendimiento de la memoria; si la jerarquía es 'first-level|second-level|third-level', esta estructura representa el rendimiento agregado de las cachés del lado de la memoria para cada dominio. El tipo de 'data-type' es el tipo de datos representado por esta instancia de estructura: si 'hierarchy' es 'memory', 'data-type' es la latencia de acceso/lectura/escritura o el ancho de banda de acceso/lectura/escritura de la memoria destino; si 'hierarchy' es 'first-level|second-level|third-level', 'data-type' es la latencia de acierto o el ancho de banda de acierto de acceso/lectura/escritura de la caché del lado de la memoria destino.

lat es el valor de latencia en nanosegundos. bw es el valor de ancho de banda, los valores y unidades posibles son NUM[M|G|T], lo que significa que el valor del ancho de banda son NUM bytes por segundo (o MB/s, GB/s o TB/s dependiendo del sufijo utilizado). Tenga en cuenta que si el valor de latencia o ancho de banda es 0, significa que la información de latencia o ancho de banda correspondiente no se proporciona.

En la opción 'hmat-cache', node-id es el ID NUMA de la memoria a la que pertenece. size es el tamaño de la caché del lado de la memoria en bytes. level es el nivel de caché descrito en esta estructura; tenga en cuenta que el nivel de caché 0 no debe usarse con la opción 'hmat-cache'. associativity es la asociatividad de la caché; el valor posible es 'none/direct(direct-mapped)/complex(complex cache indexing)'. policy es la política de escritura. line es el tamaño de línea de caché en bytes.

Por ejemplo, las siguientes opciones describen 2 nodos NUMA. El nodo 0 tiene 2 cpus y una ram, el nodo 1 solo tiene una ram. Los procesadores en el nodo 0 acceden a la memoria en el nodo 0 con latencia de acceso de 5 nanosegundos, ancho de banda de acceso es de 200 MB/s; Los procesadores en el nodo NUMA 0 acceden a la memoria en el nodo NUMA 1 con latencia de acceso de 10 nanosegundos, ancho de banda de acceso es de 100 MB/s. Y para la información de caché del lado de la memoria, los nodos NUMA 0 y 1 tienen una caché de memoria de nivel 1, tamaño de 10 KB, política de escritura-back, el tamaño de línea de caché es de 8 bytes:

-machine hmat=on \
-m 2G \
-object memory-backend-ram,size=1G,id=m0 \
-object memory-backend-ram,size=1G,id=m1 \
-smp 2,sockets=2,maxcpus=2 \
-numa node,nodeid=0,memdev=m0 \
-numa node,nodeid=1,memdev=m1,initiator=0 \
-numa cpu,node-id=0,socket-id=0 \
-numa cpu,node-id=0,socket-id=1 \
-numa hmat-lb,initiator=0,target=0,hierarchy=memory,data-type=access-latency,latency=5 \
-numa hmat-lb,initiator=0,target=0,hierarchy=memory,data-type=access-bandwidth,bandwidth=200M \
-numa hmat-lb,initiator=0,target=1,hierarchy=memory,data-type=access-latency,latency=10 \
-numa hmat-lb,initiator=0,target=1,hierarchy=memory,data-type=access-bandwidth,bandwidth=100M \
-numa hmat-cache,node-id=0,size=10K,level=1,associativity=direct,policy=write-back,line=8 \
-numa hmat-cache,node-id=1,size=10K,level=1,associativity=direct,policy=write-back,line=8

-boot [order=unidades][,once=unidades][,menu=on|off][,splash=nombre_sp][,splash-time=tiempo_sp][,reboot-timeout=tiempo_rb][,strict=on|off]
Especifica las unidades de orden de arranque como una cadena de letras de unidad. Las letras de unidad válidas dependen de la arquitectura de destino. El PC x86 utiliza: a, b (disquetera 1 y 2), c (primer disco duro), d (primer CD-ROM), n-p (Etherboot desde el adaptador de red 1-4), el arranque desde disco duro es el predeterminado. Para aplicar un orden de arranque particular solo en el primer inicio, especifícalo a través de once. Ten en cuenta que los parámetros order u once no deben usarse juntos con la propiedad bootindex de los dispositivos, ya que las implementaciones de firmware normalmente no soportan ambos al mismo tiempo.

Los menús/indicaciones de arranque interactivos se pueden habilitar con menu=on siempre que el firmware/BIOS los soporte. El valor predeterminado es el arranque no interactivo.

Se puede pasar una imagen de bienvenida (splash) a la BIOS, permitiendo al usuario mostrarla como logotipo, cuando se da la opción splash=nombre_sp y menu=on, si el firmware/BIOS los soporta. Actualmente Seabios para sistemas X86 lo soporta. Limitación: El archivo splash puede ser un archivo jpeg o un archivo BMP en formato 24 BPP (color real). La resolución debe ser soportada por el modo SVGA, por lo que se recomiendan 320x240, 640x480, 800x640.

Se puede pasar un tiempo de espera a la BIOS, la máquina virtual pausará durante `tiempo_rb` ms cuando el arranque falle, y luego se reiniciará. Si `tiempo_rb` es '-1', la máquina virtual no se reiniciará, qemu pasa '-1' a la BIOS por defecto. Actualmente Seabios para sistemas X86 lo soporta.

Realiza un arranque estricto con strict=on siempre que el firmware/BIOS lo soporte. Esto solo afecta cuando la prioridad de arranque se cambia mediante las opciones de bootindex. El valor predeterminado es el arranque no estricto.

# intenta arrancar desde la red primero, luego desde el disco duro
qemu-system-x86_64 -boot order=nc
# arranca desde el CD-ROM primero, vuelve al orden predeterminado después del reinicio
qemu-system-x86_64 -boot once=d
# arranca con una imagen de bienvenida durante 5 segundos.
qemu-system-x86_64 -boot menu=on,splash=/root/boot.bmp,splash-time=5000

Nota: El formato heredado '-boot unidades' todavía es compatible, pero se desaconseja su uso ya que puede ser eliminado en futuras versiones.

-m [size=]megas[,slots=n,maxmem=tamaño]
Establece el tamaño de RAM de inicio de la máquina virtual en `megas` megabytes. El valor predeterminado es 128 MiB. Opcionalmente, se puede usar un sufijo "M" o "G" para indicar un valor en megabytes o gigabytes respectivamente. El par opcional slots, maxmem se puede usar para establecer la cantidad de ranuras de memoria conectables en caliente y la cantidad máxima de memoria. qemu-system-x86_64 -m 1G,slots=3,maxmem=4G

Si no se especifican slots y maxmem, la conexión en caliente de memoria no estará habilitada y la RAM de inicio de la máquina virtual nunca aumentará.

-audio [driver=]driver[,model=valor][,prop[=valor][,...]]
Si se especifica la opción model, -audio es una abreviatura para configurar tanto el hardware de audio de la máquina virtual como el backend de audio del host de una sola vez. Se establece una conexión a un simulador de BMC externo. Si haces esto, se recomienda encarecidamente que uses la opción de chardev "reconnect-ms=" para reconectarte al simulador si la conexión se pierde. Ten en cuenta que si esto no se usa con cuidado, puede ser un problema de seguridad, ya que la interfaz tiene la capacidad de enviar reinicios, NMI y apagar la VM. Es mejor si QEMU establece una conexión a un simulador externo que se ejecuta en un puerto seguro en localhost, para que ni el simulador ni QEMU estén expuestos a ninguna red externa.

Consulta el archivo "lanserv/README.vm" en la biblioteca OpenIPMI para obtener más detalles sobre la interfaz externa.

Opciones de dispositivo de bloque

Las opciones de manejo de dispositivos de bloque de QEMU tienen una larga historia y han pasado por varias iteraciones a medida que el conjunto de características y la complejidad de la capa de bloque han crecido. Muchas guías en línea de QEMU a menudo hacen referencia a opciones antiguas y deprecadas, lo que puede generar confusión.

La forma más explícita de describir los discos es usar una combinación de -device para especificar el dispositivo de hardware y -blockdev para describir el backend. El dispositivo define lo que el invitado ve y el backend describe cómo QEMU maneja los datos. Es la única interfaz estable garantizada para describir dispositivos de bloque y, como tal, se recomienda para herramientas de gestión y scripting.

La opción -drive combina el dispositivo y el backend en una única opción de línea de comandos, que es más amigable para el usuario. Sin embargo, no hay garantía de estabilidad de la interfaz, aunque algunos modelos de placa antiguos todavía necesitan actualizarse para funcionar con las formas modernas de blockdev.

Opciones más antiguas como -hda son esencialmente macros que se expanden en opciones -drive para varias interfaces de unidad. Las formas originales incorporan muchas suposiciones de los días en que QEMU emulaba una PC heredada; no se recomiendan para configuraciones modernas.

-FDA archivo
-FDB archivo
Usa el archivo como imagen de disquete 0/1 (ver el capítulo Imágenes de Disco <#disk-images> en la Guía del Usuario de Emulación de Sistemas).
-HDA archivo
-HDB archivo
-HDC archivo
-HDD archivo
Usa el archivo como imagen de disco duro 0, 1, 2 o 3 en el bus predeterminado de la máquina emulada (este es, por ejemplo, el bus IDE en la mayoría de las máquinas x86, pero también puede ser SCSI, virtio o algo más en otras arquitecturas de destino). Ver también el capítulo Imágenes de Disco <#disk-images> en la Guía del Usuario de Emulación de Sistemas.
-cdrom archivo
Usa el archivo como imagen de CD-ROM en el bus predeterminado de la máquina emulada (que es IDE1 maestro en x86, por lo que no puedes usar -HDC y -cdrom al mismo tiempo allí). En sistemas que lo soportan, puedes usar el CD-ROM del host usando /dev/cdrom como nombre de archivo.
-blockdev opción[,opción[,opción[,...]]]
Define un nuevo nodo de controlador de bloque. Algunas opciones se aplican a todos los controladores de bloque, otras opciones solo son aceptadas para un controlador de bloque específico. Ver abajo para una lista de opciones genéricas y opciones para los controladores de bloque más comunes.

Las opciones que esperan una referencia a otro nodo (por ejemplo, file) se pueden dar de dos maneras. O especificas el nombre del nodo de un nodo ya existente (file=nombre-nodo), o defines un nuevo nodo en línea, agregando opciones para el nodo referenciado después de un punto (file.filename=ruta,file.aio=nativo).

Un nodo de controlador de bloque creado con -blockdev puede usarse para un dispositivo invitado especificando su nombre de nodo para la propiedad drive en un argumento -device que define un dispositivo de bloque.

Opciones válidas para cualquier nodo de controlador de bloque:
driver
Especifica el controlador de bloque a usar para el nodo dado.
nombre-nodo
Esto define el nombre del nodo del controlador de bloque por el cual se referenciará más tarde. El nombre debe ser único, es decir, no debe coincidir con el nombre de otro nodo de controlador de bloque, o (si también usas -drive) el ID de una unidad.

Si no se especifica un nombre de nodo, se genera automáticamente. El nombre de nodo generado no está previsto que sea predecible y cambia entre las invocaciones de QEMU. Para el nivel superior, se debe especificar un nombre de nodo explícito.

solo-lectura
Abre el nodo en modo de solo lectura. Los intentos de escritura del invitado fallarán.

Tenga en cuenta que algunos controladores de bloque solo soportan acceso de solo lectura, ya sea generalmente o en ciertas configuraciones. En este caso, el valor predeterminado solo-lectura=desactivado no funciona y la opción debe especificarse explícitamente.

auto-solo-lectura
Si se establece auto-solo-lectura=activado, QEMU puede recurrir al uso de solo lectura incluso cuando se solicita solo-lectura=desactivado, o incluso cambiar entre modos según sea necesario, por ejemplo, dependiendo de si el archivo de imagen es escribible o de si un usuario que escribe está conectado al nodo.
compartir-forzado
Anula el sistema de bloqueo de imágenes de QEMU forzando al nodo a utilizar un acceso compartido más débil para los permisos donde normalmente solicitaría acceso exclusivo. Cuando existe la posibilidad de que múltiples instancias tengan el mismo archivo abierto (ya sea que esta invocación de QEMU sea la primera o la segunda instancia), ambas instancias deben permitir el acceso compartido para que la segunda instancia tenga éxito al abrir el archivo.

Habilitar compartir-forzado=activado requiere solo-lectura=activado.

cache.directo
Se puede evitar la caché de páginas del host con cache.directo=activado. Esto intentará realizar E/S de disco directamente en la memoria del invitado. QEMU aún puede realizar una copia interna de los datos.
cache.sin- flush
En caso de que no le importe la integridad de los datos ante fallos del host, puede usar cache.sin-flush=activado. Esta opción le dice a QEMU que nunca necesita escribir datos en el disco, sino que puede mantener las cosas en la caché. Si algo sale mal, como que el host pierda energía, se desconecte accidentalmente el almacenamiento del disco, etc., lo más probable es que su imagen quede inutilizable.
descartar=descartar
descartar es uno de "ignorar" (o "desactivado") o "desmapear" (o "activado") y controla si las solicitudes de descartar (también conocidas como trim o unmap) se ignoran o se pasan al sistema de archivos. Algunos tipos de máquina pueden no soportar solicitudes de descartar.
detectar-ceros=detectar-ceros
detectar-ceros es "desactivado", "activado" o "desmapear" y habilita la conversión automática de escrituras de ceros simples por parte del SO a comandos de escritura de ceros optimizados específicos del controlador. Incluso puedes elegir "desmapear" si descartar está configurado como "desmapear" para permitir que una escritura de ceros se convierta en una operación de desmapeo.
Opciones específicas del controlador para archivo
Este es el controlador de bloque a nivel de protocolo para acceder a archivos regulares.
nombre-archivo
La ruta al archivo de imagen en el sistema de archivos local
aio
Especifica el backend AIO (hilos/nativo/io_uring, predeterminado: hilos)
bloqueo
Especifica si el archivo de imagen está protegido con bloqueos OFD / POSIX de Linux. El valor predeterminado es usar la API de descriptores de archivo abiertos de Linux si está disponible, de lo contrario, no se aplica ningún bloqueo. (auto/activado/desactivado, predeterminado: auto)

Options are used to specify parameters for QEMU. Some options have short forms and long forms. The short forms are single letters preceded by a hyphen. The long forms are generally more descriptive and are preceded by two hyphens.

Most options can be specified multiple times. If an option is specified multiple times, the options are evaluated in order.

Options that are not recognized by QEMU are ignored.

Specifies the name of the virtual disk image file. If this option is omitted, an empty drive is created.

Specifies the format of the virtual disk image file. If this option is omitted, the format is determined automatically.
if=type
Specifies the interface type for the virtual drive. Valid values are "ide", "scsi", "sd", "floppy", "none". The default is "ide".
bus=bus
Specifies the bus for the virtual drive. Valid values are "ide", "scsi", "usb", "sd", "floppy". The default is "ide".

Specifies the unit number for the virtual drive. The default is 0.

Specifies the index of the virtual drive. The default is automatically incremented.

Specifies the media type for the virtual drive. Valid values are "disk", "cdrom", "floppy". The default is "disk".

Enable or disable detection of zeroes in the guest. If set to "on", QEMU will detect zeroes in the guest and replace them with zeroes in the host. If set to "off", this feature is disabled. If set to "unmap", QEMU will unmap blocks that are zero in the guest.

Enable or disable snapshots for the virtual drive. If set to "on", QEMU will create a temporary file to store changes. If set to "off", changes will be written directly to the virtual disk image file.

Enable or disable read-only access to the virtual drive. If set to "on", the drive will be mounted read-only. If set to "off", the drive will be mounted read-write.
driver=driver
Specifies the driver for the virtual drive. Valid values are "file", "raw", "qcow2", "vmdk". The default is "raw".
id=id
Specifies the ID of the virtual drive. This ID can be used to refer to the drive from other QEMU options.
load-on-startup=on|off
Specifies whether the virtual drive should be loaded on startup. The default is "on".
discard_granularity=bytes
Specifies the discard granularity for the virtual drive. This option is used to optimize discard operations.
iothread=iothreadid
Specifies the I/O thread for the virtual drive. This option is used to improve I/O performance.
addr=addr
Specifies the address of the virtual drive. This option is used for devices that require a specific address.

By default, the cache.writeback=on mode is used. It will report data writes as completed as soon as the data is present in the host page cache. This is safe as long as your guest OS makes sure to correctly flush disk caches where needed. If your guest OS does not handle volatile disk write caches correctly and your host crashes or loses power, then the guest may experience data corruption.

For such guests, you should consider using cache.writeback=off. This means that the host page cache will be used to read and write data, but write notification will be sent to the guest only after QEMU has made sure to flush each write to the disk. Be aware that this has a major impact on performance.

When using the -snapshot option, unsafe caching is always used.

Este argumento se puede repetir varias veces, y los valores se agregan en el orden en que se analizan. Se anima a las aplicaciones que pretenden utilizar datos de cadenas OEM a usar el nombre de su aplicación como prefijo para la cadena de valor. Esto facilita el paso de información para múltiples aplicaciones simultáneamente.

La sintaxis value=str proporciona los datos de cadena en línea, mientras que la sintaxis path=filename carga los datos desde un archivo en el disco. Tenga en cuenta que el archivo no puede contener ningún byte NUL.

Tanto las opciones value como path se pueden repetir varias veces y se agregarán a la tabla SMBIOS en el orden en que aparezcan.

Tenga en cuenta que en la arquitectura x86, el tamaño total de todas las tablas SMBIOS está limitado a 65535 bytes. Por lo tanto, los datos de cadenas OEM no son adecuados para pasar grandes cantidades de datos al invitado. En su lugar, deben usarse como un indicador para informar al invitado dónde localizar el conjunto de datos real, por ejemplo, especificando el ID de serie de un dispositivo de bloque.

                path=/some/file/with/oemstringsdata.txt

NAME

qemu-system-x86_64 - QEMU system emulator

SYNOPSIS

qemu-system-x86_64 [QEMU options] [arm options] [--] [your OS options]

DESCRIPTION

QEMU is a generic machine emulator and virtualizer. It is composed of two parts: a machine emulator which emulates a given hardware configuration, and a processor emulator which translates the guest binaries on the fly (or uses a tiny compiled code) to the host binaries.

OPTIONS

The QEMU system emulator supports a lot of options. They are split into several groups.
-netdev tap[,id=id][,fd=h][,ifname=name][,script=path][,downscript=path][,helper=path]
Connect a host TAP network interface. A TAP interface is a network interface that can be used in both user mode and kernel mode. When used in user mode, it is a TUN/TAP interface that allows you to send and receive raw IP packets. When used in kernel mode, it is a virtual network device that is connected to a virtual switch.

Use the network helper script to configure the TAP interface. The default network helper script is /path/to/qemu-ifscript.

Examples:

#launch a QEMU instance with the default network script
qemu-system-x86_64 linux.img -nic tap
#launch a QEMU instance with two NICs, each one connected
#to a TAP device
qemu-system-x86_64 linux.img \
        -netdev tap,id=nd0,ifname=tap0 -device e1000,netdev=nd0 \
        -netdev tap,id=nd1,ifname=tap1 -device rtl8139,netdev=nd1
#launch a QEMU instance with the default network helper to
#connect a TAP device to bridge br0
qemu-system-x86_64 linux.img -device virtio-net-pci,netdev=n1 \
        -netdev tap,id=n1,"helper=/path/to/qemu-bridge-helper"
-netdev bridge,id=id[,br=bridge][,helper=helper]
Connect a host TAP network interface to a host bridge device.

Use the network helper helper to configure the TAP interface and attach it to the bridge. The default network helper executable is /path/to/qemu-bridge-helper and the default bridge device is br0.

Examples:

#launch a QEMU instance with the default network helper to
#connect a TAP device to bridge br0
qemu-system-x86_64 linux.img -netdev bridge,id=n1 -device virtio-net,netdev=n1
#launch a QEMU instance with the default network helper to
#connect a TAP device to bridge qemubr0
qemu-system-x86_64 linux.img -netdev bridge,br=qemubr0,id=n1 -device virtio-net,netdev=n1
-netdev socket,id=id[,fd=h][,listen=[host]:port][,connect=host:port]
This host network backend can be used to connect the guest's network to another QEMU virtual machine using a TCP socket connection. If listen is specified, QEMU waits for incoming connections on port (host is optional). connect is used to connect to another QEMU instance using the listen option. fd=h specifies an already opened TCP socket.

Example:

# launch a first QEMU instance
qemu-system-x86_64 linux.img \
                 -device e1000,netdev=n1,mac=52:54:00:12:34:56 \
                 -netdev socket,id=n1,listen=:1234
# connect the network of this instance to the network of the first instance
qemu-system-x86_64 linux.img \
                 -device e1000,netdev=n2,mac=52:54:00:12:34:57 \
                 -netdev socket,id=n2,connect=127.0.0.1:1234
-netdev socket,id=id[,fd=h][,mcast=maddr:port[,localaddr=addr]]
Configure a socket host network backend to share the guest's network traffic with another QEMU virtual machines using a UDP multicast socket, effectively making a bus for every QEMU with same multicast address maddr and port. NOTES:
1.
Several QEMU can be running on different hosts and share same bus (assuming correct multicast setup for these hosts).
2.
mcast support is compatible with User Mode Linux (argument ethN=mcast), see http://user-mode-linux.sf.net.
3.
Use fd=h to specify an already opened UDP multicast socket.

Example:

# launch one QEMU instance
qemu-system-x86_64 linux.img \
                 -device e1000,netdev=n1,mac=52:54:00:12:34:56 \
                 -netdev socket,id=n1,mcast=230.0.0.1:1234
# launch another QEMU instance on same "bus"
qemu-system-x86_64 linux.img \
                 -device e1000,netdev=n2,mac=52:54:00:12:34:57 \
                 -netdev socket,id=n2,mcast=230.0.0.1:1234
# launch yet another QEMU instance on same "bus"
qemu-system-x86_64 linux.img \
                 -device e1000,netdev=n3,mac=52:54:00:12:34:58 \
                 -netdev socket,id=n3,mcast=230.0.0.1:1234

Opciones de dispositivo de carácter

La forma general de una opción de dispositivo de carácter es:

-chardev backend,id=id[,mux=on|off][,opciones]
Backend es uno de: null, socket, udp, msmouse, hub, vc, ringbuf, file, pipe, console, serial, pty, stdio, braille, parallel, spicevmc, spiceport. El backend específico determinará las opciones aplicables.

Utilice -chardev help para mostrar todos los tipos de backend de chardev disponibles.

Todos los dispositivos deben tener un id, que puede ser cualquier cadena de hasta 127 caracteres de longitud. Se utiliza para identificar de forma única este dispositivo en otras directivas de línea de comandos.

Un dispositivo de carácter puede ser utilizado en modo de multiplexación por múltiples front-ends. Especifique mux=on para habilitar este modo. Un multiplexor es un dispositivo "1:N", y aquí el extremo "1" es su backend de chardev especificado, y el extremo "N" son las diversas partes de QEMU que pueden hablar con un chardev. Si crea un chardev con id=myid y mux=on, QEMU creará un multiplexor con su ID especificado, y luego podrá configurar múltiples front-ends para usar ese ID de chardev para su entrada/salida. Se pueden conectar hasta cuatro front-ends diferentes a un único chardev multiplexado. (Sin la multiplexación habilitada, un chardev solo puede ser utilizado por un único front-end.) Por ejemplo, podría usar esto para permitir que un único chardev stdio sea utilizado por dos puertos serie y el monitor QEMU:

-chardev stdio,mux=on,id=char0 \
-mon chardev=char0,mode=readline \
-serial chardev:char0 \
-serial chardev:char0

Puede tener más de un multiplexor en una configuración del sistema; por ejemplo, podría tener un puerto TCP multiplexado entre UART 0 y UART 1, y stdio multiplexado entre el monitor QEMU y un puerto paralelo:

-chardev stdio,mux=on,id=char0 \
-mon chardev=char0,mode=readline \
-parallel chardev:char0 \
-chardev tcp,...,mux=on,id=char1 \
-serial chardev:char1 \
-serial chardev:char1

Cuando utiliza un dispositivo de carácter multiplexado, se interpretan algunas secuencias de escape en la entrada. Consulte el capítulo sobre Teclas en el multiplexor de backend de caracteres <#keys-in-the-character-backend-multiplexer> en la Guía del Usuario de Emulación del Sistema para obtener más detalles.

Tenga en cuenta que algunas otras opciones de línea de comandos pueden crear implícitamente backends de caracteres multiplexados; por ejemplo, -serial mon:stdio crea un backend stdio multiplexado conectado al puerto serie y al monitor QEMU, y -nographic también multiplexa la consola y el monitor a stdio.

Si necesita agregar datos en la dirección opuesta (donde una interfaz de frontend de QEMU recibe entrada y salida de múltiples dispositivos chardev de backend), consulte el párrafo siguiente sobre la configuración del dispositivo agregador hub de chardev.

Cada backend admite la opción logfile, que proporciona la ruta a un archivo para registrar todos los datos transmitidos a través del backend. La opción logappend controla si el archivo de registro se trunca o se añade al abrirlo.

Los backends disponibles son:

-chardev null,id=id
Un dispositivo vacío. Este dispositivo no emitirá ningún dato y descartará cualquier dato que reciba. El backend null no acepta ninguna opción.
-chardev socket,id=id[,opciones TCP o opciones Unix][,server=on|off][,wait=on|off][,telnet=on|off][,websocket=on|off][,reconnect-ms=milisegundos][,tls-creds=id][,tls-authz=id]
Crea un socket de flujo bidireccional, que puede ser un socket TCP o Unix. Se creará un socket Unix si se especifica path. El comportamiento no está definido si se especifican opciones TCP para un socket Unix.

server=on|off especifica que el socket debe ser un socket de escucha.

wait=on|off especifica que QEMU no debe bloquearse esperando a que un cliente se conecte a un socket de escucha.

telnet=on|off especifica que el tráfico en el socket debe interpretar secuencias de escape telnet.

websocket=on|off especifica que el socket utiliza el protocolo WebSocket para la comunicación.

reconnect-ms establece el tiempo de espera para reconectarse en sockets no servidor cuando el extremo remoto desaparece. qemu retrasará esta cantidad de milisegundos y luego intentará reconectarse. Cero deshabilita la reconexión y es el valor predeterminado.

tls-creds solicita la habilitación del protocolo TLS para cifrado y especifica el ID de las credenciales TLS a utilizar para el negociación. Las credenciales deben haberse creado previamente con el argumento -object tls-creds.

tls-auth proporciona el ID del objeto de autorización QAuthZ contra el cual se validará el nombre distinguido x509 del cliente. Este objeto solo se resuelve en el momento de su uso, por lo que puede eliminarse y recrearse sobre la marcha mientras el servidor chardev está activo. Si falta, por defecto denegará el acceso.

Las opciones de socket TCP y Unix se dan a continuación:

Opciones TCP: port=puerto[,host=host][,to=hasta][,ipv4=on|off][,ipv6=on|off][,nodelay=on|off]
host para un socket de escucha especifica la dirección local a enlazar. Para un socket de conexión, especifica el host remoto al que conectarse. host es opcional para sockets de escucha. Si no se especifica, el valor predeterminado es 0.0.0.0.

port para un socket de escucha especifica el puerto local a enlazar. Para un socket de conexión, especifica el puerto del host remoto al que conectarse. port puede darse como un número de puerto o un nombre de servicio. port es obligatorio.

to solo es relevante para sockets de escucha. Si se especifica, y no se puede enlazar el port, QEMU intentará enlazar a puertos subsiguientes hasta incluir to hasta que tenga éxito. to debe especificarse como un número de puerto.

ipv4=on|off y ipv6=on|off especifican que solo se debe usar IPv4 o IPv6. Si no se especifica ninguno, el socket puede usar cualquiera de los dos protocolos.

>

nodelay=on|off deshabilita el algoritmo de Nagle.

opciones de unix: path=ruta[,abstract=on|off][,tight=on|off]
path especifica la ruta local del socket Unix. path es obligatorio. abstract=on|off especifica el uso del espacio de nombres del socket abstracto, en lugar del sistema de archivos. Opcional, por defecto es falso. tight=on|off establece la longitud del socket para sockets abstractos a su mínimo, en lugar de la longitud completa de sun_path. Opcional, por defecto es verdadero.
-chardev udp,id=id[,host=host],port=puerto[,localaddr=direccionlocal][,localport=puertolocal][,ipv4=on|off][,ipv6=on|off]
Envía todo el tráfico del invitado a un host remoto a través de UDP.

host especifica el host remoto al que conectarse. Si no se especifica, por defecto es localhost.

port especifica el puerto en el host remoto al que conectarse. port es obligatorio.

localaddr especifica la dirección local a la que enlazarse. Si no se especifica, por defecto es 0.0.0.0.

localport especifica el puerto local al que enlazarse. Si no se especifica, se utilizará cualquier puerto local disponible.

ipv4=on|off e ipv6=on|off especifican que se debe usar IPv4 o IPv6. Si no se especifica ninguno, el dispositivo puede usar cualquiera de los protocolos.

-chardev msmouse,id=id
Reenvía los eventos emulados de msmouse de QEMU al invitado. msmouse no toma ninguna opción.
-chardev hub,id=id,chardevs.0=id[,chardevs.N=id]
Crea explícitamente un dispositivo backend hub de chardev con la posibilidad de agregar entrada de múltiples dispositivos backend y reenviarla a un único dispositivo frontend. Además, el dispositivo hub toma la salida del dispositivo frontend y la envía de vuelta a todos los dispositivos backend conectados. Esto permite una interacción fluida entre diferentes dispositivos backend y una única interfaz frontend. Se admite la agregación de hasta 4 dispositivos chardev. (Desde 10.0)

Por ejemplo, el siguiente es un caso de uso de 2 dispositivos backend: consola virtual vc0 y una TTY pseudo pty0 conectada a un único dispositivo frontend de consola hvc virtio con la ayuda de un hub hub0. La consola virtual renderiza texto en una imagen, que se puede compartir a través del protocolo VNC. A su vez, el backend pty proporciona comunicación bidireccional a la consola hvc virtio a través del archivo de TTY pseudo. La configuración de ejemplo puede ser la siguiente:

-chardev pty,path=/tmp/pty,id=pty0 \
-chardev vc,id=vc0 \
-chardev hub,id=hub0,chardevs.0=pty0,chardevs.1=vc0 \
-device virtconsole,chardev=hub0 \
-vnc 0.0.0.0:0

Una vez que QEMU se inicia, se puede usar un cliente VNC y cualquier emulador de TTY para controlar una única consola hvc:

# Iniciar emulador TTY
tio /tmp/pty
# Iniciar cliente VNC y cambiar a consola virtual Ctrl-Alt-2
vncviewer :0

No se admiten varios dispositivos frontend. Tampoco se admite el apilamiento de multiplexores y dispositivos hub.

-chardev vc,id=id[[,width=ancho][,height=alto]][[,cols=columnas][,rows=filas]]
Conecta a una consola de texto QEMU. Opcionalmente, se le puede dar a vc un tamaño específico.

width y height especifican el ancho y alto de la consola, respectivamente, en píxeles.

cols y rows especifican que la consola se redimensione para ajustarse a una consola de texto con las dimensiones dadas.

-chardev ringbuf,id=id[,size=tamaño]
Crea un búfer circular con tamaño fijo size. el tamaño debe ser una potencia de dos y por defecto es 64K.
-chardev file,id=id,path=ruta[,input-path=rutaentrada]
Registra todo el tráfico recibido del invitado en un archivo.

path especifica la ruta del archivo que se abrirá. Este archivo se creará si no existe y se sobrescribirá si existe. path es obligatorio.

Si se especifica input-path, esta es la ruta de un segundo archivo que se utilizará para la entrada. Si no se especifica input-path, no habrá entrada disponible desde el chardev.

Tenga en cuenta que input-path no es compatible con hosts de Windows.

-chardev pipe,id=id,path=ruta
Crea una conexión bidireccional con el invitado. El comportamiento difiere ligeramente entre hosts de Windows y otros hosts:

En Windows, se creará una única tubería dúplex en \\.pipe\ruta.

En otros hosts, se crearán 2 tuberías llamadas ruta.in y ruta.out. Los datos escritos en ruta.in serán recibidos por el invitado. Los datos escritos por el invitado se pueden leer de ruta.out. QEMU no creará estas tuberías FIFO y requiere que estén presentes.

path forma parte de la ruta de la tubería como se describe anteriormente. path es obligatorio.

-chardev console,id=id
Envía el tráfico del invitado a la salida estándar de QEMU. console no toma ninguna opción.

console solo está disponible en hosts de Windows.

-chardev serial,id=id,path=ruta
Envía el tráfico del invitado a un dispositivo serie en el host.

En hosts Unix, serial aceptará cualquier dispositivo tty, no solo líneas serie.

path especifica el nombre del dispositivo serie a abrir.

-chardev pty,id=id[,path=ruta]
Crea un nuevo pseudo-terminal en el host y se conecta a él.

pty no está disponible en hosts de Windows.

Si se especifica path, QEMU creará un enlace simbólico en esa ubicación que apunta al nuevo dispositivo PTY.

Esto evita tener que realizar consultas al monitor QMP o HMP para averiguar cuál es la ruta del nuevo dispositivo PTY.

Tenga en cuenta que, aunque QEMU eliminará el enlace simbólico cuando se salga de forma controlada, no lo hará en caso de fallos o ciertos errores de inicio. Se recomienda que el usuario verifique y elimine el enlace simbólico después de que QEMU termine para tener en cuenta esto.

-chardev stdio,id=id[,signal=on|off]
Conecta a la entrada y salida estándar del proceso QEMU.

signal controla si las señales están habilitadas en la terminal, lo que incluye salir de QEMU con la secuencia de teclas Control-c. Esta opción está habilitada por defecto, use signal=off para deshabilitarla.

-chardev braille,id=id
Conecta a un servidor BrlAPI local. braille no toma ninguna opción.
-chardev parallel,id=id,path=ruta
parallel solo está disponible en hosts Linux, FreeBSD y DragonFlyBSD
hosts.

Conecta a un puerto paralelo local.

path especifica la ruta al dispositivo del puerto paralelo. path es obligatorio.

-chardev spicevmc,id=id,debug=debug,name=nombre
spicevmc solo está disponible cuando el soporte spice está compilado.

debug nivel de depuración para spicevmc

name nombre del canal spice al que conectarse

Conecta a un canal de máquina virtual spice, como vdiport.

-chardev spiceport,id=id,debug=debug,name=nombre
spiceport solo está disponible cuando el soporte spice está compilado.

debug nivel de depuración para spicevmc

name nombre del puerto spice al que conectarse

Conecta a un puerto spice, permitiendo que un cliente Spice maneje el tráfico identificado por un nombre (preferiblemente un fqdn).

Opciones de dispositivo TPM

La forma general de una opción de dispositivo TPM es:

-tpmdev backend,id=id[,opciones]
El tipo específico de backend determinará las opciones aplicables. La opción -tpmdev crea el backend TPM y requiere una opción -device que especifique el modelo de interfaz frontend TPM.

Utilice -tpmdev help para imprimir todos los tipos de backend TPM disponibles.

Los backends disponibles son:

-tpmdev passthrough,id=id,path=ruta,cancel-path=rutacancelacion
(Solo host Linux) Habilita el acceso al TPM del host utilizando el controlador de paso directo.

path especifica la ruta al dispositivo TPM del host, es decir, en un host Linux sería /dev/tpm0. path es opcional y por defecto se utiliza /dev/tpm0.

cancel-path especifica la ruta a la entrada sysfs del dispositivo TPM del host que permite la cancelación de un comando TPM en curso. cancel-path es opcional y por defecto QEMU buscará la entrada sysfs a utilizar.

Algunas notas sobre el uso del TPM del host con el controlador de paso directo:

El dispositivo TPM al que accede el controlador de paso directo no debe ser utilizado por ninguna otra aplicación en el host.

Dado que el firmware del host (BIOS/UEFI) ya ha inicializado el TPM, el firmware de la VM (BIOS/UEFI) no podrá inicializar el TPM de nuevo y, por lo tanto, es posible que no muestre un menú específico del TPM que de lo contrario permitiría al usuario configurar el TPM, por ejemplo, permitir al usuario habilitar/deshabilitar o activar/desactivar el TPM. Además, si la propiedad del TPM se libera desde dentro de una VM, el TPM del host se deshabilitará y desactivará. Para habilitar y activar el TPM de nuevo después, el host tiene que ser reiniciado y se requiere que el usuario ingrese al menú del firmware para habilitar y activar.

tcp:[host]:port[,server=on|off][,wait=on|off][,nodelay=on|off][,reconnect-ms=milliseconds]
La Consola Neta TCP tiene dos modos de operación. Puede enviar la E/S serie a una ubicación o esperar una conexión desde una ubicación. Por defecto, la Consola Neta TCP se envía al host en el puerto. Si usas la opción server=on, QEMU esperará a que una aplicación cliente de socket se conecte al puerto antes de continuar, a menos que se haya especificado la opción wait=on|off. La opción nodelay=on|off deshabilita el algoritmo de buffering de Nagle. La opción reconnect-ms solo se aplica si se establece server=no; si la conexión se interrumpe, intentará reconectar en el intervalo dado. Si se omite host, se asume 0.0.0.0. Solo se acepta una conexión TCP a la vez. Puedes usar telnet=on para conectarte al dispositivo de caracteres correspondiente.
Ejemplo para enviar la consola TCP a 192.168.0.2 puerto 4444
-serial <tcp:192.168.0.2:4444>
Ejemplo para escuchar y esperar en el puerto 4444 una conexión
-serial <tcp::4444,server=on>
Ejemplo para no esperar y escuchar en la IP 192.168.0.100 puerto 4444
-serial <tcp:192.168.0.100:4444,server=on,wait=off>
telnet:host:port[,server=on|off][,wait=on|off][,nodelay=on|off]
El protocolo telnet se utiliza en lugar de sockets TCP crudos. Las opciones funcionan igual que si hubieras especificado -serial tcp. La diferencia es que el puerto actúa como un servidor o cliente telnet utilizando la negociación de opciones de telnet. Esto también te permitirá enviar la secuencia MAGIC_SYSRQ si usas un telnet que admita el envío de la secuencia de interrupción. Típicamente en el telnet de Unix, lo haces con Control-] y luego escribes "send break" seguido de presionar la tecla Enter.

El protocolo WebSocket se utiliza en lugar de un socket TCP crudo. El puerto actúa como un servidor WebSocket. El modo cliente no es compatible.

-overcommit mem-lock=on|off|on-fault
-overcommit cpu-pm=on|off
Ejecuta qemu con pistas sobre la sobreasignación de recursos del host. El valor predeterminado es asumir que el host sobreasigna todos los recursos.

El bloqueo de la memoria de qemu y del invitado se puede habilitar mediante mem-lock=on o mem-lock=on-fault (deshabilitado por defecto). Esto funciona cuando la memoria del host no está sobreasignada y reduce la latencia en el peor de los casos para el invitado. La opción on-fault es mejor para reducir la huella de memoria ya que realiza las asignaciones de forma perezosa, pero las páginas aún se bloquean en su lugar una vez que el invitado o QEMU las solicita. Tenga en cuenta que las dos opciones son mutuamente excluyentes.

La capacidad del invitado para gestionar el estado de energía de las CPU del host (aumentando la latencia para otros procesos en la misma CPU del host, pero disminuyendo la latencia para el invitado) se puede habilitar mediante cpu-pm=on (deshabilitado por defecto). Esto funciona mejor cuando la CPU del host no está sobreasignada. Cuando se utiliza, las estimaciones del host de la utilización del ciclo de CPU y la energía serán incorrectas, sin tener en cuenta el tiempo de inactividad del invitado.

Especifique base como utc o localtime para que el RTC comience en la hora UTC o local actual, respectivamente. localtime es necesario para una fecha correcta en MS-DOS o Windows. -icount [shift=N|auto][,align=on|off][,sleep=on|off][,rr=record|replay,rrfile=filename[,rrsnapshot=snapshot]]
Habilita el contador de instrucciones virtuales. La CPU virtual ejecutará una instrucción cada 2^N ns de tiempo virtual. Si se especifica auto, la velocidad de la CPU virtual se ajustará automáticamente para mantener el tiempo virtual a unos pocos segundos del tiempo real.

Tenga en cuenta que aunque esta opción puede dar un comportamiento determinista, no proporciona una emulación precisa de ciclos. Las CPU modernas contienen núcleos fuera de orden superescalares con jerarquías de caché complejas. La cantidad de instrucciones ejecutadas a menudo tiene poca o ninguna correlación con el rendimiento real.

Cuando la CPU virtual está durmiendo, el tiempo virtual avanzará a la velocidad predeterminada a menos que se especifique sleep=off. Con sleep=off, el tiempo virtual saltará al próximo plazo del temporizador instantáneamente cada vez que la CPU virtual entre en modo de suspensión y no avanzará si no hay un temporizador habilitado. Este comportamiento proporciona tiempos de ejecución deterministas desde la perspectiva del invitado. El valor predeterminado si icount está habilitado es sleep=on. sleep=off no se puede usar junto con shift=auto ni con align=on.

align=on activará el algoritmo de retardo que intentará sincronizar el reloj del host y el reloj virtual. El objetivo es tener un invitado ejecutándose a la frecuencia real impuesta por la opción shift. Cuando el reloj del invitado está por detrás del reloj del host y si se especifica align=on, imprimiremos un mensaje al usuario para informar sobre el retardo. Actualmente, esta opción no funciona cuando shift es auto. Nota: El algoritmo de sincronización funcionará para aquellos valores de shift para los cuales el reloj del invitado se adelanta al reloj del host. Típicamente esto sucede cuando el valor de shift es alto (qué tan alto depende de la máquina host). El valor predeterminado si icount está habilitado es align=off.

Cuando se especifica la opción rr, se habilita la grabación/reproducción determinista. La opción rrfile= también debe proporcionarse para especificar la ruta del archivo de registro de reproducción. En modo de grabación, los datos se escriben en este archivo, y en modo de reproducción se leen. Si se proporciona la opción rrsnapshot, especifica un nombre de instantánea de VM. En modo de grabación, se crea una nueva instantánea de VM con el nombre dado al inicio de la grabación de la ejecución. En modo de reproducción, esta opción especifica el nombre de la instantánea utilizada para cargar el estado inicial de la VM.

La acción controla qué hará QEMU cuando expire el temporizador de vigilancia. El valor predeterminado es reset (reiniciar forzosamente el invitado). Crea un objeto de backend de archivo de memoria, que se puede utilizar para respaldar la RAM del invitado con páginas grandes.

El parámetro id es un ID único que se utilizará para referenciar esta región de memoria en otros parámetros, por ejemplo, -numa, -device nvdimm, etc.

La opción size proporciona el tamaño de la región de memoria y acepta sufijos comunes, por ejemplo, 500M.

mem-path proporciona la ruta a un sistema de archivos de memoria compartida o de páginas grandes montado.

La opción booleana share determina si la región de memoria está marcada como privada para QEMU o compartida. Esta última permite que un proceso externo cooperante acceda a la región de memoria de QEMU.

Establecer share=on podría afectar la capacidad de configurar enlaces NUMA para el backend de memoria bajo ciertas circunstancias; consulte Documentation/vm/numa_memory_policy.txt en el árbol de fuentes del kernel de Linux para obtener detalles adicionales.

Establecer la opción booleana discard-data en on indica que el contenido del archivo puede ser destruido cuando QEMU sale, para evitar volcar innecesariamente datos al archivo de respaldo. Tenga en cuenta que discard-data es solo una optimización, y QEMU podría no descartar el contenido del archivo si se interrumpe inesperadamente o se termina con SIGKILL.

La opción booleana merge habilita la fusión de memoria, también conocida como MADV_MERGEABLE, para que Kernel Samepage Merging considere las páginas para la deduplicación de memoria.

Establecer la opción booleana dump en off excluye la memoria de los volcados de núcleo. Esta característica también se conoce como MADV_DONTDUMP.

La opción booleana prealloc habilita la preasignación de memoria.

La opción host-nodes vincula el rango de memoria a una lista de nodos host NUMA.

La opción policy establece la política NUMA a uno de los siguientes valores:

default
política predeterminada del host
preferred
preferir la lista de nodos host dada para la asignación
bind
restringir la asignación de memoria a la lista de nodos host dada
interleave
entrelazar las asignaciones de memoria en la lista de nodos host dada

La opción align especifica la alineación de la dirección base cuando QEMU mmap(2) mem-path, y acepta sufijos comunes, por ejemplo, 2M. Algunos backends especificados por mem-path requieren una alineación diferente a la predeterminada utilizada por QEMU, por ejemplo, el dispositivo DAX /dev/dax0.0 requiere una alineación de 2M en lugar de 4K. En tales casos, los usuarios pueden especificar la alineación requerida a través de esta opción.

La opción offset especifica el desplazamiento dentro del archivo de destino en el que comienza la región. Puede utilizar este parámetro para respaldar múltiples regiones con un solo archivo.

La opción pmem especifica si el archivo de respaldo especificado por mem-path se encuentra en memoria persistente del host a la que se puede acceder utilizando el modelo de programación NVM de SNIA (por ejemplo, Intel NVDIMM). Si pmem se establece en 'on', QEMU realizará las operaciones necesarias para garantizar la persistencia de sus propias escrituras en mem-path (por ejemplo, en la emulación de etiquetas vNVDIMM y la migración en vivo). Además, mapearemos el archivo de backend con la bandera MAP_SYNC, lo que garantiza que los metadatos del archivo estén sincronizados para mem-path en caso de fallo del host o corte de energía. MAP_SYNC requiere soporte del kernel del host (desde el kernel de Linux 4.15) y del sistema de archivos de mem-path montado con la opción DAX.

La opción readonly especifica si el archivo de respaldo se abre en modo de solo lectura o lectura/escritura (predeterminado).

La opción rom especifica si se crea Memoria de Solo Lectura (ROM) que no puede ser modificada por la VM. Se denegarán los intentos de escritura en dicha ROM. La mayoría de los casos de uso desean RAM adecuada en lugar de ROM. Sin embargo, casos de uso seleccionados, como NVDIMMs de solo lectura, pueden beneficiarse de la ROM. Si se establece en on, se crea ROM; si se establece en off, se crea RAM escribible; si se establece en auto (predeterminado), se utiliza el valor de la opción readonly. Esta opción es principalmente útil cuando queremos tener RAM escribible en configuraciones que tradicionalmente crearían ROM antes de que se introdujera la opción rom: plantillas de VM, donde queremos abrir un archivo en modo de solo lectura (readonly=on) y marcar la memoria como privada para QEMU (share=off). Para este caso de uso, necesitamos RAM escribible en lugar de ROM y también queremos establecer rom=off.

QEMU tool

The <b>-object</b> option allows to create a QEMU object. Objects are used to model various things in QEMU. Some objects are backends to devices, some objects are devices themselves.

This man page covers some of the more common objects. For a full list of available objects, please run QEMU with the <b>-object help</b> option.

The format of the command line is:

<b>-object object-type,property=value,...</b>

The <i>object-type</i> is a string identifying the type of object. The available types depend on the QEMU build configuration. The properties are comma-separated key/value pairs specific to the object type.

The <b>id</b> property is available for most objects and assigns a unique name to the object. This name can be used later by other objects to refer to this object.

The following object types are available:

-object cryptod,id=id
Creates a new crypto backend object. The id is a unique name that can be used to refer to this crypto backend.
-object memory-backend-file,id=id,memdev=memdev,size=size[,prealloc=on|off][,host-writable=on|off]
Creates a memory backend object that is backed by a file. The memdev property specifies the memory device name, size is the amount of memory in bytes. prealloc=on means the memory file will be preallocated. host-writable=on means the guest can write to the memory file, but the host cannot.
-object memory-backend-ram,id=id,size=size
Creates a memory backend object that uses host RAM. The size property is the amount of memory in bytes.
-object rng-random,id=id,source=/path/to/file
Creates a random number generator backend which obtains entropy from a specified file. The id parameter is a unique ID that will be used to reference this entropy backend from the virtio-rng device. The source parameter specifies which file to obtain entropy from and if omitted defaults to /dev/urandom.
-object rng-egd,id=id,chardev=chardevid
Creates a random number generator backend which obtains entropy from an external daemon running on the host. The id parameter is a unique ID that will be used to reference this entropy backend from the virtio-rng device. The chardev parameter is the unique ID of a character device backend that provides the connection to the RNG daemon.
-object tls-creds-anon,id=id,endpoint=endpoint,dir=/path/to/cred/dir,verify-peer=on|off
Creates a TLS anonymous credentials object, which can be used to provide TLS support on network backends. The id parameter is a unique ID which network backends will use to access the credentials. The endpoint is either server or client depending on whether the QEMU network backend that uses the credentials will be acting as a client or as a server. If verify-peer is enabled (the default) then once the handshake is completed, the peer credentials will be verified, though this is a no-op for anonymous credentials.

The dir parameter tells QEMU where to find the credential files. For server endpoints, this directory may contain a file dh-params.pem providing diffie-hellman parameters to use for the TLS server. If the file is missing, QEMU will generate a set of DH parameters at startup. This is a computationally expensive operation that consumes random pool entropy, so it is recommended that a persistent set of parameters be generated upfront and saved.

-object tls-creds-psk,id=id,endpoint=endpoint,dir=/path/to/keys/dir[,username=username]
Creates a TLS Pre-Shared Keys (PSK) credentials object, which can be used to provide TLS support on network backends. The id parameter is a unique ID which network backends will use to access the credentials. The endpoint is either server or client depending on whether the QEMU network backend that uses the credentials will be acting as a client or as a server. For clients only, username is the username which will be sent to the server. If omitted it defaults to "qemu".

The dir parameter tells QEMU where to find the keys file. It is called "dir/keys.psk" and contains "username:key" pairs. This file can most easily be created using the GnuTLS psktool program.

For server endpoints, dir may also contain a file dh-params.pem providing diffie-hellman parameters to use for the TLS server. If the file is missing, QEMU will generate a set of DH parameters at startup. This is a computationally expensive operation that consumes random pool entropy, so it is recommended that a persistent set of parameters be generated up front and saved.

-object tls-creds-x509,id=id,endpoint=endpoint,dir=/path/to/cred/dir,priority=priority,verify-peer=on|off,passwordid=id
Creates a TLS anonymous credentials object, which can be used to provide TLS support on network backends. The id parameter is a unique ID which network backends will use to access the credentials. The endpoint is either server or client depending on whether the QEMU network backend that uses the credentials will be acting as a client or as a server. If verify-peer is enabled (the default) then once the handshake is completed, the peer credentials will be verified. With x509 certificates, this implies that the clients must be provided with valid client certificates too.

The dir parameter tells QEMU where to find the credential files. For server endpoints, this directory may contain a file dh-params.pem providing diffie-hellman parameters to use for the TLS server. If the file is missing, QEMU will generate a set of DH parameters at startup. This is a computationally expensive operation that consumes random pool entropy, so it is recommended that a persistent set of parameters be generated upfront and saved.

For x509 certificate credentials the directory will contain further files providing the x509 certificates. The certificates must be stored in PEM format, in filenames ca-cert.pem, ca-crl.pem (optional), server-cert.pem (only servers), server-key.pem (only servers), client-cert.pem (only clients), and client-key.pem (only clients).

For the server-key.pem and client-key.pem files which contain sensitive private keys, it is possible to use an encrypted version by providing the passwordid parameter. This provides the ID of a previously created secret object containing the password for decryption.

The priority parameter allows to override the global default priority used by gnutls. This can be useful if the system administrator needs to use a weaker set of crypto priorities for QEMU without potentially forcing the weakness onto all applications. Or conversely if one wants wants a stronger default for QEMU than for all other applications, they can do this through this parameter. Its format is a gnutls priority string as described at https://gnutls.org/manual/html_node/Priority-Strings.html.

-object tls-cipher-suites,id=id,priority=priority
Creates a TLS cipher suites object, which can be used to control the TLS cipher/protocol algorithms that applications are permitted to use.

The id parameter is a unique ID which frontends will use to access the ordered list of permitted TLS cipher suites from the host.

The priority parameter allows to override the global default priority used by gnutls. This can be useful if the system administrator needs to use a weaker set of crypto priorities for QEMU without potentially forcing the weakness onto all applications. Or conversely if one wants wants a stronger default for QEMU than for all other applications, they can do this through this parameter. Its format is a gnutls priority string as described at https://gnutls.org/manual/html_node/Priority-Strings.html.

An example of use of this object is to control UEFI HTTPS Boot. The tls-cipher-suites object exposes the ordered list of permitted TLS cipher suites from the host side to the guest firmware, via fw_cfg. The list is represented as an array of IANA_TLS_CIPHER objects. The firmware uses the IANA_TLS_CIPHER array for configuring guest-side TLS.

In the following example, the priority at which the host-side policy is retrieved is given by the priority property. Given that QEMU uses GNUTLS, priority=@SYSTEM may be used to refer to /etc/crypto-policies/back-ends/gnutls.config.

    -fw_cfg name=etc/edk2/https/ciphers,gen_id=mysuite0

Interval t can't be 0, this filter batches the packet delivery: all packets arriving in a given interval on netdev netdevid are delayed until the end of the interval. queue all|rx|tx is an option that can be applied to any netfilter.

all: the filter is attached both to the receive and the transmit queue of the netdev (default).

rx: the filter is attached to the receive queue of the netdev, where it will receive packets sent to the netdev.

tx: the filter is attached to the transmit queue of the netdev, where it will receive packets sent by the netdev.

position head|tail|id=<id> is an option to specify where the filter should be inserted in the filter list. It can be applied to any netfilter.

head: the filter is inserted at the head of the filter list, before any existing filters.

tail: the filter is inserted at the tail of the filter list, behind any existing filters (default).

id=<id>: the filter is inserted before or behind the filter specified by <id>, see the insert option below.

insert behind|before is an option to specify where to insert the new filter relative to the one specified with position=id=<id>. It can be applied to any netfilter.

before: insert before the specified filter.

behind: insert behind the specified filter (default).

-object secret,id=id,file=nombre_archivo,format=raw|base64[,keyid=secretid,iv=cadena]
Define un secreto para almacenar una contraseña, clave de cifrado o algún otro dato sensible. Los datos sensibles pueden ser pasados directamente a través del parámetro data, o indirectamente a través del parámetro file. Usar el parámetro data no es seguro a menos que los datos sensibles estén cifrados.

Los datos sensibles pueden ser proporcionados en formato raw (el valor por defecto), o base64. Cuando se codifica como JSON, el formato raw solo admite caracteres UTF-8 válidos, por lo que se recomienda base64 para enviar datos binarios. QEMU se convertirá del formato proporcionado al formato que necesita internamente. por ejemplo, una contraseña RBD puede ser proporcionada en formato raw, aunque se codificará en base64 cuando se envíe al servidor RBD.

Para mayor protección, es posible cifrar los datos asociados a un secreto usando el cifrado AES-256-CBC. El uso del cifrado se indica proporcionando los parámetros keyid y iv. El parámetro keyid proporciona el ID de un secreto definido previamente que contiene la clave de descifrado AES-256. Esta clave debe tener 32 bytes de longitud y estar codificada en base64. El parámetro iv proporciona el vector de inicialización aleatorio utilizado para el cifrado de este secreto en particular y debe ser una cadena codificada en base64 del IV de 16 bytes.

El uso más simple (inseguro) es proporcionar el secreto en línea

# qemu-system-x86_64 -object secret,id=sec0,data=letmein,format=raw

El uso seguro más simple es proporcionar el secreto a través de un archivo

# printf "letmein" > mypasswd.txt # QEMU_SYSTEM_MACRO -object secret,id=sec0,file=mypasswd.txt,format=raw

Para mayor seguridad, se debe usar AES-256-CBC. Para ilustrar el uso, considere la herramienta de línea de comandos openssl que puede cifrar los datos. Tenga en cuenta que al cifrar, el texto plano debe rellenarse hasta el tamaño de bloque del cifrador (32 bytes) utilizando el algoritmo de relleno estándar compatible con PKCS#5/6.

Primero, se necesita crear una clave maestra en codificación base64:

# openssl rand -base64 32 > key.b64
# KEY=$(base64 -d key.b64 | hexdump  -v -e '/1 "%02X"')

Cada secreto a cifrar necesita tener generado un vector de inicialización aleatorio. Estos no necesitan ser mantenidos en secreto

# openssl rand -base64 16 > iv.b64
# IV=$(base64 -d iv.b64 | hexdump  -v -e '/1 "%02X"')

El secreto a definir ahora puede ser cifrado, en este caso estamos diciendo a openssl que codifique el resultado en base64, pero podría dejarse como bytes raw si se desea.

# SECRET=$(printf "letmein" |
           openssl enc -aes-256-cbc -a -K $KEY -iv $IV)

Al lanzar QEMU, cree un secreto maestro apuntando a key.b64 y especifique que se usará para descifrar la contraseña de usuario. Pase el contenido de iv.b64 al segundo secreto

# qemu-system-x86_64 \
    -object secret,id=secmaster0,format=base64,file=key.b64 \
    -object secret,id=sec0,keyid=secmaster0,format=base64,\
        data=$SECRET,iv=$(<iv.b64)

Crea un objeto de invitado Secure Encrypted Virtualization (SEV), que puede ser utilizado para proporcionar soporte de cifrado de memoria del invitado en procesadores AMD.

Cuando el cifrado de memoria está habilitado, uno de los bits de dirección física (también conocido como bit C) se utiliza para marcar si una página de memoria está protegida. El cbitpos se utiliza para proporcionar la posición del bit C. La posición del bit C depende de la familia del Host, por lo que el usuario debe proporcionar este valor. En EPYC, el valor debe ser 47.

Cuando el cifrado de memoria está habilitado, perdemos ciertos bits en el espacio de direcciones físicas. El reduced-phys-bits se utiliza para proporcionar el número de bits que perdemos en el espacio de direcciones físicas. Similar al bit C, el valor depende de la familia del Host. En EPYC, un invitado perderá un máximo de 1 bit, por lo que el valor debe ser 1.

El sev-device proporciona el archivo de dispositivo a utilizar para comunicarse con el firmware SEV que se ejecuta dentro del procesador seguro de AMD. El dispositivo por defecto es '/dev/sev'. Si el hardware soporta cifrado de memoria, entonces los dispositivos /dev/sev son creados por el driver CCP.

debe ser proporcionada por el propietario del guest y está vinculada al guest y no puede cambiarse durante toda la vida útil del guest. El valor por defecto es 0.

-object iothread,id=id,poll-max-ns=poll-max-ns,poll-grow=poll-grow,poll-shrink=poll-shrink,aio-max-batch=aio-max-batch
Crea un hilo de bucle de eventos dedicado al que se pueden asignar dispositivos. Esto se conoce como IOThread. Por defecto, la emulación de dispositivos ocurre en los hilos de vCPU o en el hilo del bucle de eventos principal. Esto puede convertirse en un cuello de botella de escalabilidad. Los IOThreads permiten que la emulación de dispositivos y las E/S se ejecuten en otras CPU del host.

El parámetro id es un ID único que se utilizará para referenciar este IOThread desde -device ...,iothread=id. Se pueden asignar varios dispositivos a un IOThread. Tenga en cuenta que no todos los dispositivos admiten un parámetro iothread.

El comando QMP query-iothreads lista los IOThreads e informa sus ID de hilo para que el usuario pueda configurar el anclaje/afinidad de la CPU del host.

Los IOThreads utilizan un algoritmo de sondeo adaptativo para reducir la latencia del bucle de eventos. En lugar de entrar en una llamada del sistema bloqueante para monitorizar descriptores de archivo y luego pagar el coste de ser despertado cuando ocurre un evento, el algoritmo de sondeo gira esperando eventos durante un corto período de tiempo. Los parámetros predeterminados del algoritmo son adecuados para muchos casos, pero se pueden ajustar basándose en el conocimiento de la carga de trabajo y/o la latencia del dispositivo host.

El parámetro poll-max-ns es el número máximo de nanosegundos para esperar activamente eventos. El sondeo se puede deshabilitar estableciendo este valor en 0.

El parámetro poll-grow es el multiplicador utilizado para aumentar el tiempo de sondeo cuando el algoritmo detecta que se está perdiendo eventos debido a no sondear lo suficiente.

El parámetro poll-shrink es el divisor utilizado para disminuir el tiempo de sondeo cuando el algoritmo detecta que se está dedicando demasiado tiempo a sondear sin encontrar eventos.

El parámetro aio-max-batch es el número máximo de solicitudes en un lote para el motor AIO, 0 significa que el motor usará su valor predeterminado.

Los parámetros de IOThread se pueden modificar en tiempo de ejecución utilizando el comando qom-set (donde iothread1 es el id del IOThread):

(qemu) qom-set /objects/iothread1 poll-max-ns 100000

NOTAS

Además de usar imágenes de archivo normales para los dispositivos de almacenamiento emulados, QEMU también puede usar recursos de red como dispositivos iSCSI. Estos se especifican usando una sintaxis especial de URL.

iSCSI
El soporte iSCSI permite a QEMU acceder directamente a recursos iSCSI y usarlos como imágenes para el almacenamiento del invitado. Se admiten imágenes de disco y de CD-ROM.

La sintaxis para especificar LUNs iSCSI es "iscsi://<ip-destino>[:<puerto>]/<iqn-destino>/<lun>"

Por defecto, qemu usará el nombre de iniciador iSCSI 'iqn.2008-11.org.linux-kvm[:<nombre>]' pero esto también se puede establecer desde la línea de comandos o un archivo de configuración.

Desde la versión 2.4 de QEMU, es posible especificar un tiempo de espera para las solicitudes iSCSI para detectar solicitudes bloqueadas y forzar un restablecimiento de la sesión. El tiempo de espera se especifica en segundos. El valor predeterminado es 0, lo que significa que no hay tiempo de espera. Se requiere libiscsi 1.15.0 o superior para esta función.

Ejemplo (sin autenticación):

qemu-system-x86_64 -iscsi initiator-name=iqn.2001-04.com.example:my-initiator \
                 -cdrom iscsi://192.0.2.1/iqn.2001-04.com.example/2 \
                 -drive file=iscsi://192.0.2.1/iqn.2001-04.com.example/1

Ejemplo (nombre de usuario/contraseña CHAP a través de URL):

qemu-system-x86_64 -drive file=iscsi:<//usuario%contraseña@192.0.2.1/iqn.2001-04.com.example/1>

Ejemplo (nombre de usuario/contraseña CHAP a través de variables de entorno):

LIBISCSI_CHAP_USERNAME="usuario" \
LIBISCSI_CHAP_PASSWORD="contraseña" \
qemu-system-x86_64 -drive file=iscsi://192.0.2.1/iqn.2001-04.com.example/1
NBD
QEMU soporta NBD (Network Block Devices) tanto usando el protocolo TCP como sockets de dominio Unix. Con TCP, el puerto predeterminado es 10809.

Sintaxis para especificar un dispositivo NBD usando TCP, en formato URI preferido: "nbd://<ip-servidor>[:<puerto>]/[<exportacion>]"

Sintaxis para especificar un dispositivo NBD usando sockets de dominio Unix; recuerde que '?' es un carácter comodín de shell y puede necesitar ser citado: "nbd+unix:///[<exportacion>]?socket=<socket-dominio>"

Sintaxis antigua que también se reconoce: "nbd:<ip-servidor>:<puerto>[:exportname=<exportacion>]"

Sintaxis para especificar un dispositivo NBD usando sockets de dominio Unix: "nbd:unix:<socket-dominio>[:exportname=<exportacion>]"

Ejemplo para TCP

qemu-system-x86_64 --drive file=nbd:192.0.2.1:30000

Ejemplo para sockets de dominio Unix

qemu-system-x86_64 --drive file=nbd:unix:/tmp/nbd-socket
SSH
QEMU soporta acceso SSH (Secure Shell) a discos remotos.

Ejemplos:

qemu-system-x86_64 -drive file=ssh:<//usuario@host/ruta/a/disco.img>
qemu-system-x86_64 -drive file.driver=ssh,file.user=usuario,file.host=host,file.port=22,file.path=/ruta/a/disco.img

Actualmente, la autenticación debe realizarse usando ssh-agent. Otros métodos de autenticación pueden ser soportados en el futuro.

HTTP/HTTPS/FTP/FTPS
QEMU soporta acceso de solo lectura a archivos accedidos a través de http(s) y ftp(s).

Sintaxis usando un único nombre de archivo:

<protocolo>://[<usuario>[:<contraseña>]@]<host>/<ruta>

donde:

protocolo
'http', 'https', 'ftp', o 'ftps'.
usuario
Nombre de usuario opcional para autenticación en el servidor remoto.
contraseña
Contraseña opcional para autenticación en el servidor remoto.
host
Dirección del servidor remoto.
ruta
Ruta en el servidor remoto, incluyendo cualquier cadena de consulta.

Las siguientes opciones también son compatibles:

url
La URL completa al pasar opciones explícitamente al controlador.
readahead
La cantidad de datos a leer por adelantado con cada solicitud de rango al servidor remoto. Este valor opcionalmente puede tener el sufijo 'T', 'G', 'M', 'K', 'k' o 'b'. Si no tiene sufijo, se asumirá que está en bytes. El valor debe ser un múltiplo de 512 bytes. Su valor predeterminado es 256k.
sslverify
Si verificar el certificado del servidor remoto al conectarse a través de SSL. Puede tener el valor 'on' u 'off'. Su valor predeterminado es 'on'.
cookie
Enviar esta cookie (también puede ser una lista de cookies separadas por ';') con cada solicitud saliente. Solo compatible cuando se usan protocolos como HTTP que admiten cookies, de lo contrario se ignora.
timeout
Establecer el tiempo de espera en segundos de la conexión CURL. Este tiempo de espera es el tiempo que CURL espera una respuesta del servidor remoto para obtener el tamaño de la imagen a descargar. Si no se establece, se utiliza el tiempo de espera predeterminado de 5 segundos.

Tenga en cuenta que al pasar opciones explícitamente a qemu, driver es el valor de <protocolo>.

Ejemplo: arrancar desde una imagen ISO de Fedora 20 live remota

qemu-system-x86_64 --drive media=cdrom,file=https://archives.fedoraproject.org/pub/archive/fedora/linux/releases/20/Live/x86_64/Fedora-Live-Desktop-x86_64-20-1.iso,readonly
qemu-system-x86_64 --drive media=cdrom,file.driver=http,file.url=http://archives.fedoraproject.org/pub/fedora/linux/releases/20/Live/x86_64/Fedora-Live-Desktop-x86_64-20-1.iso,readonly

NOTES

The backing file and qcow2 image can be combined by specifying the backing file directly as the source for the qcow2 image. This will create an image with copy-on-read enabled by default.

Example: use an image stored on an http server as backing file, with a local overlay for writes, a readahead of 64k and copy-on-read enabled

qemu-img create -f qcow2 -o backing_file='json:{"file.driver":"http",, "file.url":"<http://archives.fedoraproject.org/pub/archive/fedora/linux/releases/20/Images/x86_64/Fedora-x86_64-20-20131211.1-sda.qcow2>",, "file.readahead":"64k"}' /tmp/Fedora-x86_64-20-20131211.1-sda.qcow2
qemu-system-x86_64 -drive file=/tmp/Fedora-x86_64-20-20131211.1-sda.qcow2,copy-on-read=on
