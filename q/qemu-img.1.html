NOMBRE

qemu-img - Utilidad de imágenes de disco de QEMU

SINOPSIS

qemu-img [opciones estándar] comando [opciones de comando]

DESCRIPCIÓN

qemu-img permite crear, convertir y modificar imágenes sin conexión. Puede manejar todos los formatos de imagen compatibles con QEMU.

Advertencia: Nunca use qemu-img para modificar imágenes en uso por una máquina virtual en ejecución o cualquier otro proceso; esto puede destruir la imagen. Además, tenga en cuenta que consultar una imagen que está siendo modificada por otro proceso puede encontrar un estado inconsistente.

OPCIONES

Opciones estándar:

-h, --help
Mostrar esta ayuda y salir
-V, --version
Mostrar información de la versión y salir
-T, --trace [[enable=]PATRÓN][,events=ARCHIVO][,file=ARCHIVO]
Especificar opciones de rastreo.

[enable=]PATRÓN

Habilitar inmediatamente los eventos que coincidan con PATRÓN (nombre del evento o patrón de globbing). Esta opción solo está disponible si QEMU ha sido compilado con el backend de rastreo simple, log o ftrace. Para especificar múltiples eventos o patrones, especifique la opción -trace varias veces.

Use -trace help para imprimir una lista de nombres de puntos de rastreo.

events=ARCHIVO

Habilitar inmediatamente los eventos listados en ARCHIVO. El archivo debe contener un nombre de evento (como los listados en el archivo trace-events-all) por línea; los patrones de globbing también son aceptados. Esta opción solo está disponible si QEMU ha sido compilado con el backend de rastreo simple, log o ftrace.

file=ARCHIVO

Registrar las salidas de rastreo en ARCHIVO. Esta opción solo está disponible si QEMU ha sido compilado con el backend de rastreo simple.

Parámetros del comando:

NOMBRE_ARCHIVO es un nombre de archivo de imagen de disco.

FMT es el formato de la imagen de disco. Se adivina automáticamente en la mayoría de los casos. Consulte a continuación una descripción de los formatos de disco compatibles.

TAMAÑO es el tamaño de la imagen de disco en bytes. Se admiten sufijos opcionales k o K (kilobyte, 1024), M (megabyte, 1024k), G (gigabyte, 1024M) y T (terabyte, 1024G). Se ignora b.

NOMBRE_ARCHIVO_SALIDA es el nombre del archivo de imagen de disco de destino.

FMT_SALIDA es el formato de destino.

OPCIONES es una lista separada por comas de opciones específicas del formato en formato nombre=valor. Use -o help para una visión general de las opciones admitidas por el formato utilizado o consulte las descripciones de formato a continuación para obtener detalles.

PARAM_SNAPSHOT se utiliza para instantáneas internas, el formato es 'snapshot.id=[ID],snapshot.name=[NOMBRE]' o '[ID_O_NOMBRE]'.

--object OBJETO_DEF
es una definición de objeto creable por el usuario de QEMU. Consulte la página del manual de qemu(1) para obtener una descripción de las propiedades del objeto. El tipo de objeto más común es un secret, que se utiliza para proporcionar contraseñas y/o claves de cifrado.
--image-opts
Indica que el parámetro NOMBRE_ARCHIVO de origen se interpretará como una cadena de opciones completa, no como un nombre de archivo simple. Este parámetro es mutuamente exclusivo con el parámetro -f.
--target-image-opts
Indica que los parámetros de NOMBRE_ARCHIVO_SALIDA se interpretarán como una cadena de opciones completa, no como un nombre de archivo simple. Este parámetro es mutuamente exclusivo con los parámetros -O. Actualmente es necesario utilizar también el parámetro -n para omitir la creación de la imagen. Parámetros para el subcomando convert:

--bitmaps
Copia adicionalmente todos los bitmaps persistentes de la capa superior del origen
-n
Omite la creación del volumen de destino
-m
Número de corrutinas paralelas para el proceso de conversión
-W
Permite escrituras fuera de orden en el destino. Esta opción mejora el rendimiento, pero solo se recomienda para dispositivos preasignados como dispositivos de host u otros dispositivos de bloque raw.
-C
Intenta utilizar la descarga de copia para mover datos de la imagen de origen a la de destino. -r
Límite de velocidad para el proceso de conversión
--salvage
Intenta ignorar los errores de E/S al leer. A menos que esté en modo silencioso (-q), los errores se seguirán imprimiendo. Las áreas que no se pueden leer del origen se tratarán como si contuvieran solo ceros.
--target-is-zero
Asume que leer la imagen de destino siempre devolverá ceros. Este parámetro es mutuamente excluyente con una imagen de destino que tiene un archivo de respaldo. Se requiere también utilizar el parámetro -n para omitir la creación de la imagen.

Descripción del comando:

amend [--object OBJECTDEF] [--image-opts] [-p] [-q] [-f FMT] [-t CACHE] [--force] -o OPTIONS FILENAME
Modifica las OPTIONS específicas del formato de imagen para el archivo de imagen FILENAME. No todos los formatos de archivo admiten esta operación.

El conjunto de opciones que se pueden modificar depende del formato de imagen, pero tenga en cuenta que la relación de la cadena de respaldo se debe modificar con qemu-img rebase.

--force permite algunas operaciones inseguras. Actualmente para -f luks, permite borrar la última clave de cifrado y sobrescribir una clave de cifrado activa.

bench [-c COUNT] [-d DEPTH] [-f FMT] [--flush-interval=FLUSH_INTERVAL] [-i AIO] [-n] [--no-drain] [-o OFFSET] [--pattern=PATTERN] [-q] [-s BUFFER_SIZE] [-S STEP_SIZE] [-t CACHE] [-w] [-U] FILENAME
Ejecuta un punto de referencia simple de E/S secuencial en la imagen especificada. Si se especifica -w, se realiza una prueba de escritura, de lo contrario se realiza una prueba de lectura.

Se realiza un número total de COUNT solicitudes de E/S, cada una de BUFFER_SIZE bytes de tamaño, y con DEPTH solicitudes en paralelo. La primera solicitud comienza en la posición dada por OFFSET, cada solicitud siguiente aumenta la posición actual en STEP_SIZE. Si no se proporciona STEP_SIZE, se utiliza BUFFER_SIZE para su valor.

Si se especifica FLUSH_INTERVAL para una prueba de escritura, la cola de solicitudes se vacía y se emite un flush antes de realizar nuevas escrituras cada vez que el número de solicitudes restantes sea un múltiplo de FLUSH_INTERVAL. Si además se especifica --no-drain, se emite un flush sin vaciar primero la cola de solicitudes.

Si se especifica -i, la opción AIO se puede utilizar para especificar diferentes backends AIO: threads, native o io_uring.

Si se especifica -n, se utiliza el backend AIO nativo si es posible. En Linux, esta opción solo funciona si también se especifica -t none o -t directsync.

Para pruebas de escritura, por defecto se escribe un buffer lleno de ceros. Esto se puede anular con un byte de patrón especificado por PATTERN.

bitmap (--merge SOURCE | --add | --remove | --clear | --enable | --disable)... [-b SOURCE_FILE [-F SOURCE_FMT]] [-g GRANULARITY] [--object OBJECTDEF] [--image-opts | -f FMT] FILENAME BITMAP
Realiza una o más modificaciones del bitmap persistente BITMAP en la imagen de disco FILENAME. Las diversas modificaciones son:

--add para crear BITMAP, habilitado para registrar ediciones futuras.

--remove para eliminar BITMAP.

--clear para borrar BITMAP.

--enable para cambiar BITMAP y comenzar a registrar ediciones futuras.

--disable para cambiar BITMAP y dejar de registrar ediciones futuras.

--merge para fusionar el contenido del bitmap SOURCE en BITMAP.

Opciones adicionales incluyen -g que establece una GRANULARITY no predeterminada para --add, y -b y -F que seleccionan un archivo de origen alternativo para todos los bitmaps SOURCE utilizados por --merge.

Para ver qué bitmaps están presentes en una imagen, utilice qemu-img info.

check [--object OBJECTDEF] [--image-opts] [-q] [-f FMT] [--output=OFMT] [-r [leaks | all]] [-T SRC_CACHE] [-U] FILENAME
Realiza
check [--object OBJECTDEF] [--image-opts] [-r [-l | all]] [-q] [-f FMT] [-t CACHE] [-o OPTIONS] [-T SRC_CACHE] FILENAME
Realiza una comprobación de consistencia en la imagen de disco FILENAME. El comando puede producir la salida en el formato OFMT, que puede ser human o json. La salida JSON es un objeto de tipo QAPI ImageCheck.

Si se especifica -r, qemu-img intenta reparar cualquier inconsistencia encontrada durante la comprobación. -r leaks repara solo las fugas de clústeres, mientras que -r all corrige todo tipo de errores, con un mayor riesgo de elegir la reparación incorrecta u ocultar la corrupción que ya ha ocurrido.

Solo los formatos qcow2, qed, parallels, vhdx, vmdk y vdi admiten comprobaciones de consistencia.

En caso de que la imagen no tenga inconsistencias, la comprobación finaliza con 0. Otros códigos de salida indican el tipo de inconsistencia encontrada o si ocurrió otro error. La siguiente tabla resume todos los códigos de salida del subcomando check:

0
Comprobación completada, la imagen está (ahora) consistente
1
Comprobación no completada debido a errores internos
2
Comprobación completada, la imagen está corrupta
3
Comprobación completada, la imagen tiene fugas de clústeres, pero no está corrupta
63
El formato de imagen no admite las comprobaciones

Si se especifica -r, los códigos de salida que representan el estado de la imagen se refieren al estado después del (intento de) reparación. Es decir, un -r all exitoso devolverá el código de salida 0, independientemente del estado de la imagen anterior.

commit [--object OBJECTDEF] [--image-opts] [-q] [-f FMT] [-t CACHE] [-b BASE] [-r RATE_LIMIT] [-d] [-p] FILENAME
Consolida los cambios registrados en FILENAME en su imagen base o archivo de respaldo. Si el archivo de respaldo es más pequeño que la instantánea, el archivo de respaldo se redimensionará para que tenga el mismo tamaño que la instantánea. Si la instantánea es más pequeña que el archivo de respaldo, el archivo de respaldo no se truncará. Si desea que el archivo de respaldo coincida con el tamaño de la instantánea más pequeña, puede truncarlo usted mismo una vez que la operación de consolidación se complete correctamente.

La imagen FILENAME se vacía después de que la operación haya tenido éxito. Si no necesita FILENAME después y tiene la intención de eliminarla, puede omitir el vaciado de FILENAME especificando la opción -d.

Si la cadena de respaldo del archivo de imagen dado FILENAME tiene más de una capa, el archivo de respaldo en el que se consolidarán los cambios puede especificarse como BASE (que debe formar parte de la cadena de respaldo de FILENAME). Si no se especifica BASE, se utilizará el archivo de respaldo inmediato de la imagen superior (que es FILENAME). Tenga en cuenta que después de una operación de consolidación, todas las imágenes entre BASE y la imagen superior no serán válidas y pueden devolver datos basura al leerlas. Por esta razón, -b implica -d (para que la imagen superior permanezca válida).

El límite de velocidad para el proceso de consolidación se especifica mediante -r.

compare [--object OBJECTDEF] [--image-opts] [-f FMT] [-F FMT] [-T SRC_CACHE] [-p] [-q] [-s] [-U] FILENAME1 FILENAME2
Comprueba si dos imágenes tienen el mismo contenido. Puede comparar imágenes con diferentes formatos o configuraciones.

El formato se detecta automáticamente a menos que lo especifique con -f (utilizado para FILENAME1) y/o -F (utilizado para FILENAME2).

Por defecto, las imágenes con tamaño diferente se consideran idénticas si la imagen más grande contiene solo sectores no asignados y/o con ceros en el área posterior al final de la otra imagen. Además, si algún sector no está asignado en una imagen y contiene solo bytes cero en la segunda, se evalúa como igual. Puede usar el modo Estricto especificando la opción -s. Cuando compare se ejecuta en modo Estricto, falla si el tamaño de la imagen difiere o si un sector está asignado en una imagen y no está asignado en la segunda.

Por defecto, compare imprime un mensaje de resultado. Este mensaje muestra información de que ambas imágenes son iguales o la posición del primer byte diferente. Además, el mensaje de resultado puede informar de un tamaño de imagen diferente en caso de usar el modo Estricto.

Compare finaliza con 0 si las imágenes son iguales y con 1 si las imágenes difieren. Otros códigos de salida significan que ocurrió un error durante la ejecución y la salida de error estándar debe contener un mensaje de error. La siguiente tabla resume todos los códigos de salida del subcomando compare:

0
Las imágenes son idénticas (o se imprimió la ayuda solicitada)
1
Las imágenes difieren
2
Error al abrir una imagen
3
Error al comprobar la asignación de un sector
4
Error al leer datos
convert [--object OBJECTDEF] [--image-opts] [--target-image-opts] [--target-is-zero] [--bitmaps [--skip-broken-bitmaps]] [-U] [-C] [-c] [-p] [-q] [-n] [-f FMT] [-t CACHE] [-T SRC_CACHE] [-O OUTPUT_FMT] [-b BACKING_FILE [-F BACKING_FMT]] [-o OPTIONS] [-l SNAPSHOT_PARAM] [-S SPARSE_SIZE] [-r RATE_LIMIT] [-m NUM_COROUTINES] [-W] FILENAME [FILENAME2 [...]] OUTPUT_FILENAME
Convierte la imagen de disco FILENAME o una instantánea SNAPSHOT_PARAM a la imagen de disco OUTPUT_FILENAME utilizando el formato OUTPUT_FMT. Puede comprimirse opcionalmente (opción -c) o utilizar cualquier opción específica del formato, como el cifrado (opción -o).

Solo los formatos qcow y qcow2 admiten compresión. La compresión es de solo lectura. Esto significa que si se reescribe un sector comprimido, se reescribe como datos sin comprimir.

La conversión de imágenes también es útil para obtener una imagen más pequeña al utilizar un formato redimensionable como qcow: se detectan los sectores vacíos y se suprimen de la imagen de destino.

SPARSE_SIZE indica el número consecutivo de bytes (por defecto 4k) que deben contener solo ceros para que qemu-img cree una imagen dispersa durante la conversión. Si SPARSE_SIZE es 0, la fuente no se escaneará en busca de sectores no asignados o cero, y la imagen de destino siempre estará completamente asignada.

Puede utilizar la opción BACKING_FILE para forzar la creación de la imagen de salida como una imagen de copia en escritura de la imagen base especificada; BACKING_FILE debe tener el mismo contenido que la imagen base de la entrada, sin embargo, la ruta, el formato de la imagen (según lo dado por BACKING_FMT), etc., pueden diferir.

Si se proporciona un nombre de ruta relativo, el archivo de respaldo se busca en relación con el directorio que contiene OUTPUT_FILENAME.

Si se especifica la opción -n, se omitirá la creación del volumen de destino. Esto es útil para formatos como rbd si el volumen de destino ya se ha creado con opciones específicas del sitio que no se pueden proporcionar a través de qemu-img.

Las escrituras desordenadas se pueden habilitar con -W para mejorar el rendimiento. Esto solo se recomienda para dispositivos preasignados como dispositivos host u otros dispositivos de bloque crudos. La escritura desordenada no funciona en combinación con la creación de imágenes comprimidas.

NUM_COROUTINES especifica cuántas corrutinas trabajan en paralelo durante el proceso de conversión (por defecto 8).

El uso de --bitmaps solicita que cualquier mapa de bits persistente presente en el original también se copie al destino. Si algún mapa de bits es inconsistente en la fuente, la conversión fallará a menos que también se especifique --skip-broken-bitmaps para copiar solo los mapas de bits consistentes.

create [-f FMT] [-o FMT_OPTS] [-b BACKING_FILE [-B BACKING_FMT]] [-u] [-q] [--object OBJDEF] FILE [SIZE]
Crea la nueva imagen de disco FILE de tamaño SIZE y formato FMT. Dependiendo del formato del archivo, puede agregar una o más opciones FMT_OPTS que habilitan funciones adicionales de este formato.

Si se especifica la opción BACKING_FILE, la imagen solo registrará las diferencias con BACKING_FILE. No es necesario especificar el tamaño en este caso. BACKING_FILE nunca se modificará a menos que utilice el comando de monitor commit (o qemu-img commit).

Si se proporciona un nombre de ruta relativo, el archivo de respaldo se busca en relación con el directorio que contiene FILE.

Tenga en cuenta que se abrirá un archivo de respaldo dado para comprobar que es válido. Utilice la opción -u para habilitar el modo de archivo de respaldo inseguro, lo que significa que la imagen se creará incluso si el archivo de respaldo asociado no se puede abrir. Se debe crear un archivo de respaldo coincidente o utilizar opciones adicionales para que la especificación del archivo de respaldo sea válida cuando desee utilizar una imagen creada de esta manera.

El tamaño también se puede especificar utilizando la opción SIZE con -o, no es necesario especificarlo por separado en este caso.

dd [--image-opts] [-U] [-f FMT] [-O OUTPUT_FMT] [bs=BLOCK_SIZE] [count=BLOCKS] [skip=BLOCKS] if=INPUT of=OUTPUT
dd copia desde el archivo INPUT al archivo OUTPUT, convirtiéndolo del formato FMT al formato OUTPUT_FMT.

Los datos se leen y escriben por defecto utilizando bloques de 512 bytes, pero se pueden modificar especificando BLOCK_SIZE. Si se especifica count=BLOCKS, dd dejará de leer la entrada después de leer BLOCKS bloques de entrada.

La sintaxis del tamaño es similar a la sintaxis de tamaño de dd(1).

info [--object OBJECTDEF] [--image-opts] [-f FMT] [--output=OFMT] [--backing-chain] [-U] FILENAME
Proporciona información sobre la imagen de disco FILENAME. Úselo en particular para conocer el tamaño reservado en disco, que puede ser diferente del tamaño mostrado. Si las instantáneas de VM están almacenadas en la imagen de disco, también se muestran.

Si una imagen de disco tiene una cadena de archivos de respaldo, la información sobre cada imagen de disco en la cadena se puede enumerar recursivamente utilizando la opción --backing-chain.

Por ejemplo, si tiene una cadena de imágenes como:

base.qcow2 <- snap1.qcow2 <- snap2.qcow2

qemu-img(1) — Linux manual page





To enumerate information about each disk image in the above chain,
    starting from top to base, do:






qemu-img info --backing-chain snap2.qcow2






The command can output in the format OFMT which is either
    human or json. The JSON output is an object of QAPI type
    ImageInfo; with --backing-chain, it is an array of
    ImageInfo objects.


--output=human reports the following information (for every
    image in the chain):





  
image

  
The image file name

  
file
    format

  
The image format

  
virtual
    size

  
The size of the guest disk

  
disk
    size

  
How much space the image file occupies on the host file system (may be
      shown as 0 if this information is unavailable, e.g. because there is no
      file system)

  
cluster_size

  
Cluster size of the image format, if applicable

  
encrypted

  
Whether the image is encrypted (only present if so)

  
cleanly shut
    down

  
This is shown as no if the image is dirty and will have to be
      auto-repaired the next time it is opened in qemu.

  
backing
    file

  
The backing file name, if present

  
backing file
    format

  
The format of the backing file, if the image enforces it

  
Snapshot
    list

  
A list of all internal snapshots

  
Format specific
    information

  
Further information whose structure depends on the image format. This
      section is a textual representation of the respective
      ImageInfoSpecific* QAPI object (e.g. ImageInfoSpecificQCow2
      for qcow2 images).










  
map [--object OBJECTDEF]
    [--image-opts] [-f FMT] [--start-offset=OFFSET] [--max-length=LEN]
    [--output=OFMT] [-U] FILENAME

  
Dump the metadata of image FILENAME and its backing file chain. In
      particular, this commands dumps the allocation state of every sector of
      FILENAME, together with the topmost file that allocates it in the
      backing file chain.
    
Two option formats are possible. The default format
        (human) only dumps known-nonzero areas of the file. Known-zero
        parts of the file are omitted altogether, and likewise for parts that
        are not allocated throughout the chain. qemu-img output will
        identify a file from where the data can be read, and the offset in the
        file. Each line will include four fields, the first three of which are
        hexadecimal numbers. For example the first line of:

  








Offset          Length          Mapped to       File
0               0x20000         0x50000         /tmp/overlay.qcow2
0x100000        0x10000         0x95380000      /tmp/backing.qcow2






means that 0x20000 (131072) bytes starting at offset 0 in the
    image are available in /tmp/overlay.qcow2 (opened in raw format)
    starting at offset 0x50000 (327680). Data that is compressed, encrypted, or
    otherwise not available in raw format will cause an error if human
    format is in use. Note that file names can include newlines, thus it is not
    safe to parse this output format in scripts.


The alternative format json will return an array of
    dictionaries in JSON format. It will include similar information in the
    start, length, offset fields; it will also include
    other more specific information:




    
  
  • boolean field data: true if the sectors contain actual data, false
      if the sectors are either unallocated or stored as optimized all-zero
      clusters
    • 
  
  • boolean field zero: true if the data is known to read as zero
    • 
  
  • boolean field present: true if the data belongs to the backing
      chain, false if rebasing the backing chain onto a deeper file would pick
      up data from the deeper file;
    • 
  
  • integer field depth: the depth within the backing chain at which
      the data was resolved; for example, a depth of 2 refers to the backing
      file of the backing file of FILENAME.
    • 





In JSON format, the offset field is optional; it is absent
    in cases where human format would omit the entry or exit with an
    error. If data is false and the offset field is present, the
    corresponding sectors in the file are not yet in use, but they are
    preallocated.


For more information, consult include/block/block.h in
    QEMU's source code.







  
measure [--output=OFMT] [-O OUTPUT_FMT] [-o OPTIONS] [--size N | [--object
    OBJECTDEF] [--image-opts] [-f FMT] [-l SNAPSHOT_PARAM]
    FILENAME]

  
Calculate the file size required for a new image. This information can be
      used to size logical volumes or SAN LUNs appropriately for the image that
      will be placed in them. The values reported are guaranteed to be large
      enough to fit the image. The command can output in the format OFMT
      which is either human or json. The JSON output is an object
      of QAPI type BlockMeasureInfo.
    
If the size N is given then act as if creating a new
        empty image file using qemu-img create. If FILENAME is
        given then act as if converting an existing image file using qemu-img
        convert. The format of the new file is given by OUTPUT_FMT
        while the format of an existing file is given by FMT.

    
A snapshot in an existing image can be specified using
        SNAPSHOT_PARAM.

    
The following fields are reported:

  








required size: 524288
fully allocated size: 1074069504
bitmaps size: 0






The required size is the file size of the new image. It may
    be smaller than the virtual disk size if the image format supports compact
    representation.


The fully allocated size is the file size of the new image
    once data has been written to all sectors. This is the maximum size that the
    image file can occupy with the exception of internal snapshots, dirty
    bitmaps, vmstate data, and other advanced image format features.


The bitmaps size is the additional size required in order
    to copy bitmaps from a source image in addition to the guest-visible data;
    the line is omitted if either source or destination lacks bitmap support, or
    0 if bitmaps are supported but there is nothing to copy.

    -a SNAPSHOT | -c SNAPSHOT | -d SNAPSHOT] FILENAME

  
List, apply, create or delete snapshots in image FILENAME.









  
rebase [--object
    OBJECTDEF] [--image-opts] [-U] [-q] [-f FMT] [-t CACHE] [-T SRC_CACHE] [-p]
    [-u] [-c] -b BACKING_FILE [-B BACKING_FMT] FILENAME

  
Changes the backing file of an image. Only the formats qcow2 and
      qed support changing the backing file.
    
The backing file is changed to BACKING_FILE and (if the
        image format of FILENAME supports this) the backing file format
        is changed to BACKING_FMT. If BACKING_FILE is specified as
        "" (the empty string), then the image is rebased onto no
        backing file (i.e. it will exist independently of any backing file).

    
If a relative path name is given, the backing file is looked
        up relative to the directory containing FILENAME.

    
CACHE specifies the cache mode to be used for
        FILENAME, whereas SRC_CACHE specifies the cache mode for
        reading backing files.

    
There are two different modes in which rebase can
        operate:

  







  
Safe mode

  
This is the default mode and performs a real rebase operation. The new
      backing file may differ from the old one and qemu-img rebase will
      take care of keeping the guest-visible content of FILENAME
      unchanged.
    
In order to achieve this, any clusters that differ between
        BACKING_FILE and the old backing file of FILENAME are
        merged into FILENAME before actually changing the backing file.
        With the -c option specified, the clusters which are being merged
        (but not the entire FILENAME image) are compressed when
      written.

    
Note that the safe mode is an expensive operation, comparable
        to converting an image. It only works if the old backing file still
        exists.

  

  
Unsafe
    mode

  
qemu-img uses the unsafe mode if -u is specified. In this
      mode, only the backing file name and format of FILENAME is changed
      without any checks on the file contents. The user must take care of
      specifying the correct new backing file, or the guest-visible content of
      the image will be corrupted.
    
This mode is useful for renaming or moving the backing file to
        somewhere else. It can be used without an accessible old backing file,
        i.e. you can use it to fix an image whose backing file has already been
        moved/renamed.

  






You can use rebase to perform a "diff" operation
    on two disk images. This can be useful when you have copied or cloned a
    guest, and you want to get back to a thin image on top of a template or base
    image.


Say that base.img has been cloned as modified.img by
    copying it, and that the modified.img guest has run so there are now
    some changes compared to base.img. To construct a thin image called
    diff.qcow2 that contains just the differences, do:






qemu-img create -f qcow2 -b modified.img diff.qcow2
qemu-img rebase -b base.img diff.qcow2






At this point, modified.img can be disc





arded, ya que
    base.img + diff.qcow2 contiene la misma información.






  
resize [--object
    OBJECTDEF] [--image-opts] [-f FMT] [--preallocation=PREALLOC] [-q]
    [--shrink] NOMBRE_ARCHIVO [+ | -]TAMAÑO

  
Cambia la imagen del disco como si hubiera sido creada con TAMAÑO.
    
Antes de usar este comando para reducir una imagen de disco,
        DEBE usar las herramientas de sistema de archivos y particionamiento dentro
        de la VM para reducir los sistemas de archivos y los tamaños de partición
        asignados en consecuencia. ¡La falta de hacerlo resultará en pérdida de
        datos!

    
Al reducir imágenes, se debe proporcionar la opción
        --shrink. Esto informa a qemu-img que el usuario reconoce
        toda la pérdida de datos más allá del final de la imagen truncada.

    
Después de usar este comando para aumentar una imagen de disco,
        debe usar las herramientas de sistema de archivos y particionamiento dentro
        de la VM para comenzar a usar realmente el nuevo espacio en el dispositivo.

    
Al aumentar una imagen, la opción --preallocation puede
        usarse para especificar cómo se debe asignar el área adicional de la imagen
        en el host. Consulte la descripción del formato en la sección Notas para ver
        qué valores están permitidos. Usar esta opción puede resultar en que se
        asigne un poco más de datos de los necesarios.

  









NOTAS


Formatos de archivo de imagen soportados:


raw




Formato de imagen de disco raw (por defecto). Este formato
  tiene la ventaja de ser simple y fácilmente exportable a todos los demás
  emuladores. Si su sistema de archivos soporta agujeros (por ejemplo, en
  ext2 o ext3 en Linux o NTFS en Windows), entonces solo los sectores escritos
  reservarán espacio. Use qemu-img info para conocer el tamaño real
  utilizado por la imagen o ls -ls en Unix/Linux.

Opciones soportadas:





  
preallocation

  
Modo de preasignación (valores permitidos: off, falloc,
      full). El modo falloc preasigna espacio para la imagen llamando
      a posix_fallocate(). El modo full preasigna espacio para la
      imagen escribiendo datos en el almacenamiento subyacente. Estos datos pueden
      ser ceros o no, dependiendo de la ubicación del almacenamiento.










qcow2




Formato de imagen QEMU, el formato más versátil. Úselo para
  tener imágenes más pequeñas (útil si su sistema de archivos no soporta
  agujeros, por ejemplo en Windows), cifrado AES opcional, compresión basada en
  zlib o zstd y soporte de múltiples instantáneas de VM.

Opciones soportadas:





  
compat

  
Determina la versión de qcow2 a utilizar. compat=0.10 utiliza el
      formato de imagen tradicional que puede ser leído por cualquier QEMU desde
      0.10. compat=1.1 habilita extensiones del formato de imagen que solo
      QEMU 1.1 y posteriores entienden (este es el valor por defecto). Entre otras
      cosas, esto incluye clústeres de ceros, que permiten una copia eficiente al
      leer (copy-on-read) para imágenes dispersas.

  
backing_file

  
Nombre del archivo de una imagen base (ver subcomando create)

  
backing_fmt

  
Formato de imagen de la imagen base

  
compression_type

  
Esta opción configura qué algoritmo de compresión se utilizará para los
      clústeres comprimidos en la imagen. Tenga en cuenta que establecer esta
      opción aún no hace que la imagen reciba escrituras comprimidas. Se usa más
      comúnmente con la opción -c de qemu-img convert, pero también
      puede usarse con el controlador de bloques compress o trabajos de
      respaldo con compresión habilitada.
    
Los valores válidos son zlib y zstd. Para imágenes
        que usan compat=0.10, solo está disponible la compresión zlib.

  

  
encryption

  
Si esta opción se establece en on, la imagen se cifra con AES-CBC de
      128 bits.
    
El uso de cifrado en imágenes qcow y qcow2 se considera defectuoso
        según los estándares criptográficos modernos, sufriendo una serie de
        problemas de diseño:

  






    
  
  • El cifrado AES-CBC se utiliza con vectores de inicialización predecibles
      basados en el número de sector. Esto lo hace vulnerable a ataques de texto
      plano elegido que pueden revelar la existencia de datos cifrados.
    • 
  
  • La contraseña del usuario se utiliza directamente como clave de cifrado. Una
      contraseña mal elegida o corta comprometerá la seguridad del cifrado.
    • 
  
  • En caso de que la contraseña se vea comprometida, no hay forma de cambiar
      la contraseña para proteger los datos en ninguna imagen qcow. Los archivos
      deben clonarse, usando una contraseña de cifrado diferente en el nuevo
      archivo. Luego, el archivo original debe borrarse de forma segura utilizando
      un programa como shred, aunque incluso esto es ineficaz con muchas
      tecnologías de almacenamiento modernas.
    • 
  
  • Los vectores de inicialización utilizados para cifrar sectores se basan en
      el número de sector virtual del invitado, en lugar del sector físico del
      host. Cuando una imagen de disco tiene múltiples instantáneas internas, esto
      significa que los datos en múltiples sectores físicos se cifran con el mismo
      vector de inicialización. Con el modo CBC, esto abre la posibilidad de
      ataques de marca de agua si el atacante puede recopilar múltiples sectores
      cifrados con el mismo IV y algunos datos predecibles. Tener múltiples imágenes
      qcow2 con la misma contraseña también expone esta debilidad ya que la
      contraseña se utiliza directamente como clave.
    • 





Por lo tanto, se desaconseja encarecidamente el uso de cifrado
    qcow / qcow2. Se recomienda a los usuarios que utilicen una tecnología de
    cifrado alternativa, como el sistema dm-crypt / LUKS de Linux.



  
cluster_size

  
Cambia el tamaño del clúster qcow2 (debe estar entre 512 y 2M). Los tamaños
      de clúster más pequeños pueden mejorar el tamaño del archivo de imagen,
      mientras que los tamaños de clúster más grandes generalmente proporcionan un
      mejor rendimiento.

  
preallocation

  
Modo de preasignación (valores permitidos: off, metadata,
      falloc, full). Una imagen con metadatos preasignados es
      inicialmente más grande pero puede mejorar el rendimiento cuando la imagen
      necesita crecer. Las preasignaciones falloc y full son como
      las mismas opciones del formato raw, pero también configuran los
      metadatos.

  
lazy_refcounts

  
Si esta opción se establece en on, las actualizaciones del contador
      de referencias se posponen con el objetivo de evitar E/S de metadatos y
      mejorar el rendimiento. Esto es particularmente interesante con
      cache=writethrough, que no agrupa las actualizaciones de metadatos.
      La contrapartida es que después de un fallo del host, las tablas del contador
      de referencias deben reconstruirse, es decir, en la próxima apertura se
      requiere un qemu-img check -r all (automático), lo que puede llevar
      algún tiempo.
    
Esta opción solo se puede habilitar si se especifica
        compat=1.1.

  

  
nocow

  
Si esta opción se establece en on, deshabilitará COW del archivo. Solo
      es válido en btrfs, sin efecto en otros sistemas de archivos.
    
Btrfs tiene bajo rendimiento al alojar un archivo de imagen de
        VM, aún más cuando el invitado en la VM también usa btrfs como sistema de
        archivos. Deshabilitar COW es una forma de mitigar este mal rendimiento.
        Generalmente, hay dos formas de deshabilitar COW en btrfs:

  






    
  
  • Deshabilítelo montando con nodatacow, entonces todos los archivos recién
      creados serán NOCOW
    • 
  
  • Para un archivo vacío, agregue el atributo de archivo NOCOW. Eso es lo que
      hace esta opción.
    • 





Nota: esta opción solo es válida para archivos nuevos o vacíos. Si
    existe un archivo existente que es COW y ya tiene bloques de datos, no se
    puede cambiar a NOCOW estableciendo nocow=on. Se puede ejecutar
    lsattr nombre_archivo para verificar si la bandera NOCOW está establecida
    o no (una 'C' mayúscula es la bandera NOCOW).



  
data_file

  
Nombre del archivo donde se almacenarán todos los datos del invitado. Si se
      utiliza esta opción, el archivo qcow2 solo contendrá los metadatos de la
      imagen.
    
Nota: Se producirá pérdida de datos si el nombre de archivo
        proporcionado ya existe cuando se utiliza esta opción con qemu-img
        create, ya que qemu-img creará el archivo de datos de nuevo,
        sobrescribiendo el contenido original del archivo. Para simplemente
        actualizar la referencia para que apunte al archivo preexistente
        proporcionado, use qemu-img amend.

  

  
data_file_raw

  
Si esta opción se establece en on, QEMU mantendrá siempre el archivo
      de datos externo consistente como una imagen raw independiente de solo
      lectura.
    
Lo hace reenviando todas las escrituras al archivo qcow2 al
        archivo de datos raw, incluidas sus compensaciones. Por lo tanto, los
        datos que son visibles en el nodo qcow2 (es decir, para el invitado) en
        alguna compensación son visibles en la misma compensación en el archivo
        raw. Esto da como resultado una imagen raw de solo lectura. Las escrituras
        que omiten los metadatos qcow2 pueden corromper los metadatos qcow2 porque
        las escrituras fuera de banda pueden hacer que los metadatos queden
        desincronizados con la imagen raw.

    
Si esta opción está en off, QEMU utilizará el archivo de
        datos para almacenar datos de manera arbitraria. El contenido del archivo
        no tendrá sentido sin los metadatos qcow2 que lo acompañan. Dónde se
        escriben los datos no tendrá relación con su compensación vista por el
        invitado, y algunas escrituras (especialmente las escrituras de ceros)
        pueden no reenviarse al archivo de datos en absoluto, sino que solo se
        manejarán modificando los metadatos qcow2.

    
Esta opción solo se puede habilitar si se establece
        data_file.

  










Otros




QEMU también soporta varios otros formatos de archivo de
  imagen para compatibilidad con versiones anteriores de QEMU u otros
  hipervisores, incluyendo VMDK, VDI, VHD (vpc), VHDX, qcow1 y QED. Para obtener
  una lista completa de los formatos compatibles, consulte qemu-img
  --help. Para una descripción más detallada de estos formatos, consulte la
  documentación de referencia de los controladores de bloques de QEMU.

El propósito principal de los controladores de bloques para estos
    formatos es la conversión de imágenes. Para ejecutar VMs, se recomienda
    convertir las imágenes de disco a raw o qcow2 para lograr un buen
    rendimiento.
